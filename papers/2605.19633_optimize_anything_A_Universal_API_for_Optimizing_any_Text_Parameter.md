## ⚡ TL;DR

本文解決單一LLM最佳化系統能否跨不同領域匹敵專用工具的問題。
提出通用API將各領域最佳化統一為文字產物改進，支援單任務、多任務與泛化搜尋。

## 摘要翻譯

單一基於 LLM 的最佳化系統（LLM-based optimization system）能否在根本不同的領域中媲美專門工具？我們證明，當最佳化問題（optimization problem）被形式化為改進由評分函數（scoring function）評估的文字產物（text artifact）時，單一基於 AI 的最佳化系統（AI-based optimization system）——支援單任務搜尋（single-task search）、具備跨問題遷移（cross-problem transfer）的多任務搜尋（multi-task search），以及對未見輸入（unseen inputs）的泛化（generalization）——能在六項多樣化的任務上達到最先進水準（state-of-the-art）。我們的系統發現了能將 Gemini Flash 的 ARC-AGI 準確率（accuracy）提升至將近三倍的智慧體架構（agent architecture）（從 32.5% 提升至 89.5%），找到可降低 40% 的雲端成本（cloud cost）的排程演算法（scheduling algorithm），生成 CUDA 核心（CUDA kernel），當中 87% 媲美或超越 PyTorch，並優於 AlphaEvolve 所報告的圓堆積（circle packing）解方（n=26）。橫跨三個領域的消融實驗（ablation）顯示，可付諸行動的旁側資訊（actionable side information）相較於僅分數回饋（score-only feedback）能帶來更快的收斂（convergence）與顯著更高的最終分數；且在每問題預算（per-problem budget）相同的情況下，多任務搜尋透過跨任務遷移（cross-task transfer）優於獨立最佳化（independent optimization），且其效益隨相關任務（related task）數量增加而提升。綜合而言，我們首次證明，以基於 LLM 的搜尋（LLM-based search）進行文字最佳化（text optimization）是一種通用問題求解典範（general-purpose problem-solving paradigm），可將傳統上需要特定領域演算法（domain-specific algorithm）的任務統一在單一框架（framework）之下。我們將 optimize_anything 開源（open-source），支援多種後端（backend），作為 GEPA 專案（GEPA project）的一部分，網址為 https://github.com/gepa-ai/gepa。

### 核心貢獻（3～5點）
- 提出統一的基於 LLM 之文字最佳化框架 optimize_anything，以單一系統在六個截然不同的領域達到最先進水準，驗證文字最佳化是一種通用問題求解典範。
- 發現高績效智慧體架構，將 Gemini Flash 於 ARC-AGI 的準確率從 32.5% 提升至 89.5%；找到降低 40% 雲端成本的排程演算法；生成 87% 媲美或超越 PyTorch 的 CUDA 核心；並在圓堆積問題（n=26）上超越 AlphaEvolve。
- 透過跨領域消融實驗證實，可付諸行動的旁側資訊相較於僅分數回饋，能顯著加速收斂並提升最終表現。
- 證明在相同每問題預算下，多任務搜尋透過跨任務遷移優於獨立最佳化，且其效益隨相關任務數量增加而擴大。

### 適合對象
從事 LLM 應用、自動化機器學習（AutoML）、演化式計算與跨領域最佳化研究的學者與工程師；特別適合對「以文字最佳化作為通用問題求解典範」有興趣，以及希望以單一開源框架處理多樣化最佳化任務的進階讀者與開源貢獻者。

## 深度分析

#### 方法論解析

optimize_anything 的方法論建立在「將任何可序列化物件視為 text parameter (文字參數)」這一核心洞察之上。具體而言，無論待最佳化對象是 CUDA kernel (CUDA 核心)、agent architecture (智慧體架構)、系統提示或數值組態，系統都將其統一視為 text artifact (文字產物)，並透過一個通用的最佳化迴圈進行迭代改進。使用者僅需提供三項宣告式輸入：(1) seed artifact (種子產物) 或自然語言目標描述；(2) evaluator (評估器)，其必須回傳 scalar score 以及可選的 actionable side information (可付諸行動的旁側資訊)；(3) 可選的資料集。系統內部則負責 prompt construction (提示建構)、reflection (反思)、candidate selection (候選選擇) 與 search strategy (搜尋策略) 的編排。

此框架的技術骨幹是將 GEPA 的 Pareto optimization (帕累托最佳化) 機制擴展至任意文字產物。不同於傳統僅依賴 aggregate score (聚合分數) 的選擇方式，optimize_anything 採用 per-example (逐樣本) 或 per-metric (逐指標) 的 Pareto dominance (帕累托支配) 原則來篩選候選解。這意味著，若某個候選在特定輸入樣本或特定評估指標上表現突出，即使其整體平均分數並非最高，也能被保留下來參與後續迭代。這種設計保留了跨迭代間的 complementary strengths (互補強項)，對於多目標或樣本分布不均的問題尤為關鍵。

在 API 合約層面，本研究將 actionable side information (可付諸行動的旁側資訊) 提升為 evaluator (評估器) 的一等公民。無論回傳的是 stack traces (堆疊追蹤)、profiler data (分析器資料)、rendered images (渲染圖像) 或 structured error reports (結構化錯誤報告)，這些診斷資訊都透過統一介面流向 LLM proposer (LLM 提案器)。這與過去僅提供 score-only feedback (僅分數回饋) 的系統形成鮮明對比，使 LLM 能夠進行更具針對性的 reflection (反思) 與修正。

更進一步，optimize_anything 首次將三種最佳化模式統一於單一介面之下：
1. Single-task search (單任務搜尋)：針對單一問題獨立進行文字產物的演化。
2. Multi-task search (多任務搜尋)：同時處理一批 related tasks (相關任務)，透過 cross-task transfer (跨任務遷移) 讓在一個任務上發現的最佳化模式遷移至其他任務。
3. Generalization to unseen inputs (對未見輸入的泛化)：最佳化文字產物使其在整個輸入分布上表現穩健，而非僅記憶訓練樣本。

這種 declarative API (宣告式 API) 設計（受 DSPy 的「programming—not prompting」原則啟發）意味著同一組 API 呼叫無論是用於 prompt tuning (提示調校)、agent architecture search (智慧體架構搜尋) 或 code optimization (程式碼最佳化)，其介面語義都保持一致。

#### 實驗數據解讀

本研究在六個根本不同的領域進行驗證，數據呈現出幾個值得深入剖析的趨勢。首先在 ARC-AGI 基準上，系統發現的 agent architecture (智慧體架構) 將 Gemini Flash 的 accuracy (準確率) 從 32.5% 提升至 89.5%，近乎三倍的躍升。這不僅是量級上的突破，更質性地證明 LLM-based search (基於 LLM 的搜尋) 能夠自動發現具備高階抽象推理能力的複雜系統結構，而非僅進行表面層次的 prompt engineering (提示工程)。

在 cloud scheduling (雲端排程) 場景中，系統發現的 scheduling algorithm (排程演算法) 將 cloud cost (雲端成本) 降低 40%。這顯示 text optimization (文字最佳化) 不僅限於實驗室基準，更能產生具有直接經濟效益的實務政策。而在 CUDA kernel (CUDA 核心) 生成任務中，87% 的輸出匹配或超越 PyTorch 基線，這代表框架已觸及底層系統程式設計的領域，過去這通常需要高度專業的 domain-specific algorithm (特定領域演算法) 與手動調校。

在數學最佳化領域，系統在 circle packing (圓堆積) 問題（n=26）上超越了 AlphaEvolve 的已知解。考慮到 AlphaEvolve 曾改善 56 年歷史的 matrix multiplication bound (矩陣乘法界限)，此結果具有高度指標意義：它表明通用文字最佳化範式在需要深度 mathematical construction (數學構造) 的領域同樣具備競爭力。此外，在數值最佳化任務中，系統生成的自訂求解器程式碼匹配並超越了 Optuna，顯示其對傳統黑箱最佳化工具的替代潛力。

ablation (消融實驗) 的數據同樣富含資訊。在三個領域（提示最佳化、圓堆積、CUDA 核心）中，具備 actionable side information (可付諸行動的旁側資訊) 的設定相較於 score-only feedback (僅分數回饋)，達到 4–6 倍的 convergence (收斂) 速度，且最終分數顯著更高。這量化了診斷資訊對於 LLM 提案器的價值：純量分數僅能告知「好壞」，而旁側資訊則告知「為何壞」與「如何修復」，從而將隨機探索轉化為定向改進。

多任務模式的實驗則顯示，在 equivalent per-problem budget (等同每問題預算) 下，multi-task search (多任務搜尋) 透過 cross-task transfer (跨任務遷移) 顯著優於 independent optimization (獨立最佳化)，且效益隨 related tasks (相關任務) 數量增加而擴大。這揭示了文字空間中的一種 emergent scaling law (湧現規模法則)：當 LLM 同時接觸多個問題的旁側資訊時，它能抽象出跨領域的通用最佳化模式，這是過去僅支援 single-task search (單任務搜尋) 的系統所無法實現的。

#### 與現有研究的比較

在定位上，optimize_anything 並非僅是另一個領域專用工具，而是試圖統合過去分散的研究路線。FunSearch 率先展示以 LLM 進行 evolutionary search (演化式搜尋) 發現數學構造，但其僅限於 Python function (Python 函式) 且為單任務模式。AlphaEvolve 將此擴展至更廣泛的 code optimization (程式碼最佳化)，並在 Google 資料中心排程與矩陣乘法上取得突破，然而其仍僅能處理程式碼產物，且僅支援 single-task search (單任務搜尋)。optimize_anything 不僅在圓堆積問題上超越 AlphaEvolve 的數據，更重要的是將適用範圍從程式碼擴展至提示、智慧體架構與數值組態。

在提示最佳化領域，GEPA 與 MIPROv2 分別達到 state-of-the-art (最先進水準) 的 prompt optimization (提示最佳化) 並支援 generalization to unseen inputs (對未見輸入的泛化)。然而，這些系統僅限於 prompts (提示) 與 few-shot selection (少樣本選擇)。optimize_anything 繼承了 GEPA 的帕累托搜尋精神，但將其從「提示專用」解放為「任意文字產物通用」，並額外支援 single-task 與 multi-task 模式。ADAS 與 AFlow 專注於 agent architecture search (智慧體架構搜尋)，但 optimize_anything 的 generalization mode (泛化模式) 已將其涵蓋為特例，同時還能聯合演化架構與提示。

儘管成果顯著，此框架仍存在若干內在限制。首先，其高度依賴 automated evaluation (自動化評估)：evaluator (評估器) 必須能夠穩定執行並回傳結構化診斷，這在涉及物理世界互動、昂貴人類評判或高風險決策的領域中可能難以部署。其次，「萬物皆為文字」的假設雖具通用性，卻也可能造成資訊損失——某些具備豐富結構的產物（如三維網格或連續控制策略）在攤平為 text parameter (文字參數) 時，其幾何或拓撲特性可能無法被文字序列充分捕捉。最後，相較於傳統最佳化演算法（如貝葉斯最佳化或基因演算法），LLM-based search (基於 LLM 的搜尋) 的每步迭代成本顯著較高，雖然 multi-task search (多任務搜尋) 可攤銷成本，但在極低預算或需要毫秒級反應的場景中仍具挑戰性。

#### 可重現性評估

從 reproducibility (可重現性) 的角度來看，本研究採取了相對開放的姿態。作者將 optimize_anything 以 open-source (開源) 形式釋出，作為 GEPA project (GEPA 專案) 的一部分，並提供多種 backend (後端) 支援。這大幅降低了其他研究者重現核心演算法與 API 介面的門檻。此外，實驗所採用的部分基準（如 ARC-AGI、PyTorch 基線比較、circle packing (圓堆積)）屬於公開資料集或具有公開實現，有利於社群驗證。

然而，仍存在若干重現挑戰。第一，LLM 後端的隨機性與版本差異（如模型權重更新或 API 行為變更）可能導致不同執行間的結果變異，論文未明確說明是否採用固定隨機種子或多次執行統計。第二，部分高影響力實驗（如雲端成本降低 40%）可能依賴內部資料中心的 proprietary workload traces (專有負載追蹤) 或無法公開的系統拓撲，外部團隊重現時需尋找替代資料集。第三，從提供的上下文來看，諸如超參數設定、搜尋預算分配、LLM 溫度參數或 Pareto 前沿的剪枝閾值等實作細節並未完整揭露，這使得精確數值重現仍需高度依賴原始碼文件與註解的完整性。

整體而言，declarative API (宣告式 API) 的設計本身是一項可重現性資產：它將領域邏輯與最佳化邏輯分離，使其他研究者能夠在相同 framework (框架) 下替換自己的 evaluator (評估器) 與 seed artifact (種子產物)，從而進行標準化的比較研究。

#### 未來研究方向

此研究為多個後續研究方向開闢了道路。在理論層面，亟需理解 cross-task transfer (跨任務遷移) 在文字空間中的運作機制：LLM proposer (LLM 提案器) 究竟從不同領域的 actionable side information (可付諸行動的旁側資訊) 中抽象出了何種通用最佳化模式？這涉及對 LLM 在程式合成與結構搜尋中 role (角色) 的 mechanistic interpretability (機械可解釋性) 分析。

在方法論擴展上，可探索「結構感知序列化」，以緩解當前 text artifact (文字產物) 假設對非文字結構的資訊損失。例如，針對圖形或三維模型，可設計保留拓撲關係的中間表示，而非直接攤平為純字串。此外，將框架與傳統最佳化演算法（如 Bayesian Optimization (貝葉斯最佳化) 或 CMA-ES）結合，形成針對嵌入文字中之數值參數的混合搜尋策略，也是極具潛力的方向。

在應用層面，當 handcrafted evaluator (手工設計評估器) 過於昂貴或難以取得時，整合學習型評估器或 neural reward models (神經獎勵模型) 將成為必要擴展。同時，多任務模式中的動態 per-problem budget (每問題預算) 分配——即根據任務間相關性自動調整搜尋資源——可進一步提升 cross-task transfer (跨任務遷移) 的效率。

safety and robustness (安全性與穩健性) 同樣不容忽視。自動生成的 CUDA kernel (CUDA 核心) 或 agent architecture (智慧體架構) 可能在極端輸入下產生未定義行為或安全漏洞，未來研究應發展針對演化產物的形式化驗證或對抗性測試管線。最後，建立系統性的 scaling laws (規模法則)——探討效能如何隨 LLM 規模、搜尋預算與任務語料庫大小而變化——將有助於預測此通用範式的適用邊界與經濟可行性。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文探討的核心問題是，是否能設計出一套單一的、基於大型語言模型（LLM）的最佳化系統，使其在根本不同的領域中，表現能與各領域專門設計的工具相匹敵甚至超越。傳統上，最佳化任務往往依賴特定領域的演算法，例如 AlphaEvolve 專注於程式碼、GEPA 與 MIPROv2 專注於提示詞，但沒有任何單一系統能同時跨足程式碼、智慧體架構、數值最佳化與圖像生成等多元領域。作者因此提出一個根本性的問題：當各種最佳化問題都被統一表述為「改進一個由評分函數評估的文字產物」時，單一 AI 系統是否能成為通用的問題求解典範。

**Q2：現有的方法為何無法滿足跨領域通用最佳化的需求？**
A：現有的 LLM 演化式系統各自僅支援單一模式或特定產物類型，例如 AlphaEvolve、OpenEvolve 與 ShinkaEvolve 僅能在單任務模式下運作，且僅限於程式碼產物；而 GEPA 與 MIPROv2 雖然支援對未見輸入的泛化，但僅適用於提示詞最佳化。這些系統缺乏統一的介面來處理不同性質的文字產物，也無法同時支援單任務搜尋、多任務聯合搜尋與泛化模式。此外，過往框架對於評估器回傳的診斷資訊僅提供臨時性、非標準化的處理機制，無法有效利用可付諸行動的旁側資訊來加速收斂。

**Q3：建立通用文字最佳化框架的重要性與潛在影響為何？**
A：建立通用框架的重要性在於，它能將傳統上需要特定領域演算法的各種任務，統一在單一介面之下，大幅降低開發與維護不同最佳化工具的門檻與成本。這不僅證明了基於 LLM 的文字搜尋是一種通用問題求解典範，也讓研究者與工程師能以宣告式 API 快速對智慧體架構、排程策略、CUDA 核心等截然不同的事物進行最佳化。從更廣泛的角度來看，這種統一性有助於促進跨領域知識的遷移與復用，並為自動化設計與科學發現提供更具擴展性的基礎設施。

**Q4：optimize_anything 的核心方法與運作迴路為何？**
A：optimize_anything 的核心方法是將各種最佳化問題統一抽象為「文字產物」的改進過程，其運作迴路包含三個主要步驟：首先，將目前的文字產物（如程式碼、提示詞或智慧體架構）序列化為字串並傳遞給評估器；接著，評估器回傳一個分數以及可選的診斷回饋（旁側資訊）；最後，LLM 提案器根據這些資訊產生改進後的新產物，形成持續迭代的最佳化迴路。系統內部負責處理提示詞建構、反思、候選選擇與搜尋策略，使用者只需提供種子產物、評估函數與可選的資料集即可。

**Q5：此系統相較於既有方法有哪些關鍵創新？**
A：本系統首次將單任務搜尋、多任務搜尋與對未見輸入泛化這三種模式統一於單一介面之下，其中多任務搜尋更是過往系統所不具備的全新能力，能透過跨任務遷移提升整體最佳化效率。另一項關鍵創新是將「可付諸行動的旁側資訊」提升為評估器合約的一等公民，無論是堆疊追蹤、效能分析數據、渲染圖像或結構化錯誤報告，都能透過統一介面流向 LLM 提案器。此外，系統採用基於帕累托支配的候選選擇機制，針對每個範例或每個指標進行非支配排序，而非僅依賴聚合分數，從而保留不同迭代間的互補優勢。

**Q6：在系統設計上，作者為何選擇宣告式 API 與帕累托候選選擇機制？**
A：作者採用宣告式 API 的設計靈感來自 DSPy「編程而非提示」的原則，旨在讓使用者無需關心底層提示工程與搜尋細節，只需宣告目標與評估邏輯，即可將同一套介面應用於提示詞、智慧體架構或圖像等不同產物。選擇帕累托支配而非聚合分數作為候選選擇依據，是因為在複雜的多目標或多範例場景中，單一總分往往會掩蓋候選者在特定維度上的優勢；透過保留非支配解，系統能在後續迭代中組合不同候選的強項，避免過早收斂到局部最佳。這種設計也使得多任務搜尋能更有效地利用跨問題的互補特性，提升整體搜尋品質。

**Q7：論文在哪些基準任務與領域上進行了評估？**
A：論文在六個根本不同的領域進行評估，包括智慧體架構搜尋（以 ARC-AGI 準確率衡量）、雲端排程演算法設計、CUDA 核心生成、圓堆積問題、數值最佳化求解器，以及提示詞與圖像等文字產物最佳化。這些任務涵蓋了程式碼、數學構造、系統策略與神經網路提示等多元類型，且各自對應不同的評估指標，例如執行成本、執行速度、數學精度與視覺品質。如此廣泛的評估設計旨在嚴格驗證該系統作為通用最佳化典範的有效性，而非僅在單一領域內達到最先進水準。

**Q8：論文報告了哪些最具代表性的關鍵實驗結果？**
A：在智慧體架構搜尋方面，系統發現的架構將 Gemini Flash 在 ARC-AGI 上的準確率從 32.5% 大幅提升至 89.5%，幾乎達到三倍；在雲端排程領域，所發現的演算法成功降低 40% 的雲端成本；在 CUDA 核心生成任務中，有 87% 的生成核心達到或優於 PyTorch 基準表現；而在圓堆積問題上，系統更超越了 AlphaEvolve 所報告的 n=26 解決方案。這些結果顯示，單一系統不僅能與各領域的專門工具競爭，甚至能在多個截然不同的領域同時締造或超越最先進水準。

**Q9：消融實驗揭示了哪些關於回饋機制與多任務模式的重要發現？**
A：跨三個領域的消融實驗明確顯示，相較於僅提供分數的回饋，提供「可付諸行動的旁側資訊」能帶來四到六倍的收斂速度提升，並顯著提高最終分數，證明診斷資訊對 LLM 提案器的價值。在多任務模式的比較中，當給予每個問題相同的預算時，多任務聯合搜尋透過跨任務遷移，表現優於獨立的單任務最佳化，且其效益隨相關任務數量的增加而擴大。這些發現強調了統一介面下資訊豐富度與任務間知識共享的關鍵作用，為 LLM 最佳化系統的設計提供了重要的實證依據。

**Q10：在實務應用場景中，optimize_anything 適合解決哪些類型的問題？**
A：optimize_anything 特別適合那些難以用傳統梯度下降或人工設計啟發式方法解決、但可透過評分函數自動評估的文字產物最佳化問題，例如自動化設計 LLM 智慧體的推理架構、為特定硬體生成高效能的 CUDA 核心，或是為雲端叢集尋找降低成本的排程策略。由於系統僅要求使用者提供種子產物與評估器，它也能應用於快速原型設計，例如產生數值求解器、最佳化系統提示詞，甚至探索可縮放向量圖形（SVG）等結構化文字格式。這種通用性使其成為軟體工程、系統設計與科學計算領域中，自動化搜尋與設計流程的有力工具。

**Q11：若將此系統產品化，有哪些實際的考量與部署建議？**
A：產品化時，首要考量是評估器的設計必須穩定且能回傳高品質、可付諸行動的旁側資訊，因為消融實驗證明這直接影響收斂速度與最終效能，建議在評估管線中整合堆疊追蹤、效能分析或結構化錯誤報告等機制。其次，由於系統支援多種後端模型，部署時應根據任務複雜度與預算選擇適當的 LLM 後端，並利用多任務模式在相關問題批次上執行，以透過跨任務遷移最大化每單位預算的效益。此外，考量到最佳化過程涉及多次迭代與評估，建議搭配快取機制與分散式評估基礎設施，以降低延遲並提升整體吞吐量。

**Q12：這項研究對 AI 與自動化最佳化領域可能帶來哪些深遠影響？**
A：這項研究首次證明了基於 LLM 的文字最佳化不僅是程式碼或提示詞的專屬工具，而是一種真正的通用問題求解典範，這將促使學界與業界重新思考自動化設計的邊界與可能性。它統一了過去彼此割裂的領域特定最佳化社群，為未來開發更廣泛的「AI 科學家」或「自動化工程師」系統奠定了基礎架構與方法論。長遠來看，隨著多任務遷移與泛化能力的進一步提升，此類通用框架可能加速科學發現、降低系統設計的專業門檻，並推動 AI 從工具角色轉向更具自主性的創新夥伴。

**Q13：從研究設計與方法論中，可推知此系統存在哪些潛在限制？**
A：從系統設計來看，最佳化成效高度仰賴評估器能否提供豐富且可付諸行動的旁側資訊，若評估器僅回傳單一數值分數，則收斂速度與最終表現會顯著下降，這在缺乏詳細診斷資訊的領域中構成明顯瓶頸。此外，由於系統本質上是以 LLM 為核心的迭代搜尋，其所需的查詢次數與運算成本遠高於傳統特定領域演算法，對於需要即時決策或評估代價極高的場景可能不適用。再者，目前展示的成果雖橫跨六個領域，但對於維度極高或連續空間的數值最佳化問題，其相較於專門數學規劃工具的絕對優勢仍有待更全面的驗證。

**Q14：在哪些極端或特定條件下，此通用最佳化框架可能無法發揮預期效益？**
A：當最佳化問題的評估成本極高或回饋週期極長時，多次迭代的演化式搜尋將變得昂貴且緩慢，使得系統難以在實務上於合理時間內完成最佳化。若問題難以被完整序列化為文字格式，或其品質難以透過自動化評分函數精確捕捉——例如涉及深層語意理解或主觀審美判斷——則文字產物的抽象可能遺失關鍵資訊，導致搜尋失焦。此外，當多任務批次中的問題彼此關聯性過低時，跨任務遷移的效益將難以顯現，多任務模式可能退化成效率與獨立單任務最佳化相去不遠的搜尋過程。

**Q15：未來研究可朝哪些方向延伸與改進此框架？**
A：未來研究可探索將此框架與更強大的世界模型或模擬器結合，以進一步擴展至物理系統設計、機器人控制策略等難以透過靜態文字評估的領域。另一個重要方向是發展更高效的搜尋演算法與預算分配策略，例如結合貝葉斯最佳化或強化學習來指導 LLM 提案器的探索與利用權衡，從而降低對大量 LLM 查詢的依賴。此外，深入理解跨任務遷移的理論基礎，並自動識別任務間的相關性以動態組織多任務批次，將有助於進一步提升多任務模式的效益，並使通用文字最佳化在更廣泛的科學與工程問題中發揮潛力。

## 實務應用指南

### 適用場景

**1. 雲端資源排程策略自動生成**  
企業可將雲端叢集的排程規則（如 Kubernetes scheduler 的 Lua/Python 腳本或 YAML 策略）視為文字產物，以實際雲端成本或延遲作為評分函數。系統透過單任務搜尋發現能降低 40% 雲端成本的排程演算法，且無需人工編寫特定領域演算法。

**2. LLM 智慧體架構自動化設計**  
對於需要高準確率的智慧體系統（如 ARC-AGI 推理任務），可將智慧體架構（包含系統提示、工具呼叫順序、反思邏輯的 Python 程式碼）視為文字參數進行最佳化。透過泛化模式，系統能在未見輸入上發現讓 Gemini Flash 準確率從 32.5% 提升至 89.5% 的架構。

**3. GPU 核心程式碼效能調校**  
深度學習工程師可將 CUDA 核心程式碼作為文字產物，以相對於 PyTorch 基準的執行速度與正確性作為評分函數。在多任務搜尋模式下，同時最佳化一批相關的矩陣運算核心，透過跨任務遷移讓 87% 的生成核心達到或超越 PyTorch 效能。

**4. 企業級提示工程與 A/B 測試自動化**  
將客服機器人或內部知識問答的系統提示視為文字產物，結合使用者滿意度或任務完成率進行自動化評估。利用泛化模式對未見輸入進行最佳化，可取代傳統手動提示工程，並統一管理不同部門的提示版本。

**5. 數學與組合最佳化問題求解**  
研究團隊可將圓堆積（circle packing）的幾何構造描述、數值求解器的參數設定，或 SVG 圖形程式碼視為文字產物，以目標函數值（如填充密度）作為評分。系統在單任務搜尋下即可超越 AlphaEvolve 的已知最佳解。

### 實作前置條件

**資料與評估環境**  
需準備：(1) 初始種子文字產物（seed artifact）或自然語言描述的最佳化目標；(2) 可自動化執行的評分函數，能回傳數值分數與可付諸行動的旁側資訊（如錯誤堆疊、效能分析報告、渲染圖像）；(3) 若使用泛化模式，需提供涵蓋多樣輸入的資料集以驗證對未見輸入的泛化能力。

**運算資源**  
需具備 LLM API 的存取權限與預算（論文支援多種後端）。評估階段通常需大量計算（如編譯 CUDA 核心、執行雲端模擬或智慧體互動），建議具備可平行化的運算叢集或容器化環境。

**技術能力**  
團隊需熟悉 Python 與 API 設計，能將領域問題抽象為「文字產物 → 評估 → 回饋」的閉迴路。此外，需具備領域知識以設計精準的評分函數，並能判讀旁側資訊（如 profiler 數據或語法錯誤）以調整評估邏輯。

### 實作步驟建議

**步驟一：問題形式化為文字最佳化**  
將目標產物（無論是程式碼、提示、設定檔或結構化文字）序列化為字串，並確保評分函數能對該字串進行語法檢查、執行與量化評分。

**步驟二：設計高品質評估器**  
評估器應回傳分數與豐富的旁側資訊（如執行日誌、視覺化差異、資源使用率）。根據論文消融實驗，相較於僅分數回饋，可付諸行動的旁側資訊能讓收斂速度提升 4–6 倍。

**步驟三：選擇最佳化模式**  
若問題單一且獨立，採用單任務搜尋；若手邊有一批性質相關的問題（如多組 CUDA 核心或跨語言提示），採用多任務搜尋以啟動跨問題遷移；若目標是讓產物對全新輸入穩定表現，則選擇泛化模式。

**步驟四：設定種子與約束**  
提供初始種子文字產物或讓系統以 seedless 模式從自然語言生成。明確定義搜尋空間的語法約束（如必須符合特定 API 規格），避免生成無效產物浪費每問題預算。

**步驟五：執行帕累托搜尋與監控**  
利用系統內建的帕累托最佳化機制，在多目標（如速度 vs. 正確性、成本 vs. 延遲）間保留互補優勢的候選解。監控收斂曲線與候選解的多樣性，適時調整 LLM 後端或溫度參數。

**步驟六：部署與持續迭代**  
將最佳化後的文字產物整合至正式環境，並保留原始評估管線作為回歸測試。當領域需求變動時，可將既有最佳解作為新種子重新啟動搜尋。

### 潛在風險與注意事項

**評分函數設計偏差**  
若評分函數未能完整捕捉業務目標（例如只最佳化執行速度而忽略記憶體安全），系統會利用文字產物的表達能力過度擬合狹隘指標。建議採用多目標帕累托最佳化，並定期以人工審核極端候選解。

**旁側資訊不足導致收斂緩慢**  
僅提供分數會大幅拖慢基於 LLM 的搜尋效率。務必將編譯錯誤、異常追蹤、效能分析數據等轉化為結構化旁側資訊餵入系統，否則可能浪費大量 LLM 查詢預算。

**多任務模式下的負遷移**  
多任務搜尋雖能透過跨任務遷移提升效率，但若批次中的問題關聯性過低，可能導致知識干擾。建議先以領域特徵或嵌入向量評估任務相似度，再決定是否聯合最佳化。

**執行安全性風險**  
由於系統會自動生成並執行程式碼（如 CUDA 核心或智慧體腳本），需在隔離環境（沙箱容器或獨立虛擬機）中執行評估，避免惡意或錯誤程式碼影響生產系統。

**LLM 成本控管**  
演化式搜尋需多次呼叫 LLM 後端。建議設定明確的每問題預算上限，並在初期使用較便宜的模型進行搜尋空間探索，後期再切換至強大模型進行精煉。

### 與其他技術的整合建議

**與 DSPy 等宣告式框架整合**  
optimize_anything 的設計哲學與 DSPy「程式設計而非提示工程」相容。可將 DSPy 模組作為種子文字產物，利用本系統自動化搜尋最佳模組組合與提示，再將結果匯回 DSPy 管線。

**嵌入現有 CI/CD 與 MLOps 管線**  
將評估器封裝為容器化服務，透過 API 呼叫整合至 GitHub Actions 或 GitLab CI。每次程式碼提交觸發自動化評估，並將最佳化後的產物（如排程策略或提示版本）以 Pull Request 形式提交審查。

**與傳統最佳化工具互補**  
對於數值型超參數，可先以 Optuna 等傳統工具縮小範圍，再將結果轉為文字設定檔交由 optimize_anything 進行結構層級的最佳化（如調整演算法邏輯而非僅數值）。

**結合可觀測性平台**  
將評估過程中的旁側資訊（如雲端監控數據、GPU profiler 輸出）對接至 Prometheus/Grafana 或 ELK 堆疊，視覺化收斂過程並建立異常偵測，確保最佳化過程透明可控。

**多後端 LLM 路由策略**  
論文支援多種後端，實務上可設定路由邏輯：簡單變異由輕量級模型處理，複雜反思與錯誤診斷交由高階模型執行，以平衡成本與效能。

### 給不同背景讀者的閱讀建議

**初學者**  
建議從「提示工程」與「程式碼最佳化」這兩個最直觀的應用切入，先理解「任何可序列化為文字之物皆可最佳化」的核心概念。實作時可從 GEPA 專案的開源範例開始，使用單任務搜尋模式熟悉「評分函數設計」與「旁側資訊餵入」的流程，無需深入帕累托數學細節即可獲得顯著成效。

**AI 工程師**  
重點關注通用 API 的設計與評估器實作模式。論文展示如何將不同領域統一為相同介面，這對設計模組化智慧體系統極具參考價值。建議深入研究多任務搜尋的實作細節，以及如何利用多後端支援在成本與效能間取捨，並評估將此框架整合至現有 LLM 應用架構的可行性。

**研究人員**  
請聚焦於多任務搜尋中的跨問題遷移機制、帕累托最佳化在候選選擇中的角色，以及泛化模式對未見輸入的理論保證。論文首次將文字最佳化確立為通用問題求解典範，其中關於「可付諸行動的旁側資訊」對收斂速度影響的消融實驗，為未來設計更高效的基於 LLM 的搜尋演算法提供了重要實證基礎。

**產品經理**  
本論文的核心價值在於以單一框架取代多個特定領域演算法，大幅降低跨部門（從基礎設施排程到客服提示）的最佳化門檻與維護成本。建議評估貴組織內是否存在「大量仰賴人工調參的文字產物」（如排程腳本、SQL 查詢、提示模板），並將此開源框架視為統一最佳化層的候選方案，同時留意 LLM 查詢成本與自動化評估的基礎建設需求。
