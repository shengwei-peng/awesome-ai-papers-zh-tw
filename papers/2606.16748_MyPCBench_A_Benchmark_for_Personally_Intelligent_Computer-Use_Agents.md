## ⚡ TL;DR

現有電腦代理基準測試缺乏個人化情境，無法評估真實數位生活中的個人助理能力。
作者提出MyPCBench，以單一人物角色橫跨17個應用與完整桌面，建立184項個人化任務。
最強模型僅完全解決55.4%任務，跨應用與長軌跡任務最易失敗，環境與資料已開源。

## 摘要翻譯

現有的電腦使用代理（computer-use agents）基準測試在非個人化環境（impersonal environments）中評估模型，這使得評估與部署之間出現落差——個人助理（personal assistants）理應能橫跨使用者的整個數位生活運作，涵蓋其情境脈絡（context）、歷史資料（historical data）與已登入帳號（logged-in accounts）。這項落差在網頁任務（web tasks）上最為嚴重：即時網頁評測（live web evaluations）無法測試需要登入或個人資訊的網站，而這正是真實個人助理（real personal assistant）必須操作的網站類型。我們提出 MyPCBench，於搭載 17 個模擬真實世界網頁應用程式（simulated real-world web applications）與完整桌面軟體堆疊（full desktop stack）的 Linux 桌面環境（Linux desktop）中，將電腦使用代理作為個人助理進行測試。環境中的所有資料皆針對單一標準化人物角色（canonical persona）植入（seeded），即《辦公室瘋雲》（The Office）中的麥可·史考特（Michael Scott）。我們在此環境中定義了 184 項任務，每項任務的靈感皆取自 OpenClaw 社群（OpenClaw community）的真實請求，並以統一的 Computer+Bash 工具介面（computer+bash tool surface）評測六個閉源權重與開源權重模型（closed and open-weight models）。我們發現最佳模型 Claude Opus 4.6 完全解決（fully solves）了 55.4% 的任務，且為唯一完全解決率超過 50% 的模型。模型失敗案例集中在橫跨多個應用程式（span many applications）的任務以及長執行軌跡（long trajectories）上，而個人化（personalization）對助理造成的壓力於此處最大。我們於 https://mypcbench.com 釋出環境、任務集與代理測試框架（agent harness）。

### 核心貢獻（3～5點）
- 提出 MyPCBench，填補現有電腦使用代理基準測試在「非個人化環境」與真實個人助理部署之間的評估落差。
- 建構高擬真測試環境：以 Linux 桌面搭載 17 個模擬真實世界網頁應用程式與完整桌面軟體堆疊，並針對標準化人物角色植入個人化資料。
- 定義 184 項源自真實使用者請求的任務，涵蓋跨應用程式操作與長執行軌跡等個人化助理常見挑戰。
- 評測六個閉源與開源權重模型，發現即使最佳模型（Claude Opus 4.6）亦僅完全解決 55.4% 任務，且失敗集中於跨應用與長軌跡任務。
- 開源釋出環境、任務集與代理測試框架，供後續研究使用。

### 適合對象
從事電腦使用代理、個人化 AI 助理與多模態大型語言模型研究的學者與工程師；特別適合關注代理在真實使用者環境中跨應用程式執行能力、以及個人化資料對模型表現影響的研究者與開發者。

## 深度分析

#### 方法論解析

MyPCBench（個人化電腦使用代理基準測試平台）的核心方法論突破在於將評測典範從「任務導向（task-centric）」轉移至「身分導向（identity-centric）」。過往的 Computer-Use Agents（電腦使用代理）評測多在 Impersonal Environments（非個人化環境）中進行，每個任務僅植入 Minimally Seeded Databases（最小化植入資料庫），而 MyPCBench 則透過單一 Canonical Persona（標準化人物角色）— Michael Scott — 作為 Deterministic（確定性的）生成種子，建構出覆蓋完整 Digital Life（數位生活）的測試場域。

環境層面，研究團隊採用 Docker 封裝 QEMU/KVM Ubuntu 24.04 VM，搭配 GNOME Shell 與 Full Desktop Stack（完整桌面軟體堆疊），包含 Firefox、LibreOffice Suite（LibreOffice 辦公套件）與 17 個 Pre-Logged-In Web Apps（預先登入的網頁應用程式）。這些 Simulated Real-World Web Applications（模擬真實世界網頁應用程式）並非獨立運作，而是透過 Multi-Application Generator（多應用程式產生器）產生 Cross-Linked（交叉連結）的 Correlated Records（相關聯的紀錄）。例如單一旅遊行程會同步在銀行、行事曆、電子郵件與共乘服務留下一致的 Itemized Records（明細紀錄），從而構成 Deep, Cross-Application Personal Identity（深度跨應用程式個人身分）。這種設計迫使代理程式必須進行「資訊考古」，從分散的 Historical Data（歷史資料）中重建使用者的意圖與上下文，而非僅執行明確給定的步驟。

任務設計方面，184 個 Tasks（任務）並非人工合成，而是取材自 OpenClaw Community（OpenClaw 社群）的真實使用者請求。每個任務配備自然語言的 Rubric（評分標準），並以 LLM-as-a-judge 評估 Rubric-Graded Visible Side Effects（依評分標準評分的可見副作用），允許 Partial Credit（部分得分）。這對於個人助理場景至關重要，因為真實請求往往開放且多元（例如「幫我規劃週末行程」存在多種有效解決方案），傳統的二元成功/失敗指標無法捕捉細緻的能力差異。

為確保公平比較，作者設計了 Uniform Computer+Bash Tool Surface（統一的 Computer+Bash 工具介面），強制所有受測模型 — 無論是 Claude Opus 4.6（Claude Opus 4.6）、GPT-5.5 或 Qwen3.5 系列 — 均透過相同的電腦控制與指令列工具層與環境互動。Agent Harness（代理測試框架）則驅動標準的 CUA ReAct 迴圈，將模型差異嚴格限制在規劃、記憶與個人化推理能力上，而非原生工具介面的設計優劣。最後，Resettable Desktop Control（可重設桌面控制）搭配 Deterministic snapshot reset，確保每次實驗都能精確還原至 Michael Scott 的初始狀態，在 Reproducibility（可重現性）與 Personalization（個人化）之間取得關鍵平衡。

#### 實驗數據解讀

實驗結果揭示了一個嚴峻的現實：即使是最強的 Frontier Model，其個人化智慧能力仍遠未達到實用門檻。Claude Opus 4.6 以 55.4% 的 Fully Solves（完全解決）率位居第一，且是唯一突破 50% 的模型。這意味著即便在受控的模擬環境中，當前最頂尖的代理程式仍無法處理近半數的真實個人助理請求。這項數據強烈暗示，「個人化智慧」是一條獨立於一般推理或程式編寫能力的能力軸；一個在 MMLU 或 SWE-bench 上表現優異的模型，並不保證能成為稱職的 Personal Assistant（個人助理）。

更具警示性的是跨應用規模的效能崩塌。當 Tasks（任務）需要 Span Many Applications（橫跨多個應用程式）（7 個以上 apps）時，Claude Opus 4.6 的完全解決率驟降至 36%，GPT-5.5 僅剩 4.5%，而 GPT-5.4 mini、Qwen3.5 35B-A3B 與 Qwen3.5 9B 則全部歸零。這種非線性的「複雜度斷崖（complexity wall）」表明，Cross-App History（跨應用程式歷史紀錄）的整合並非單純的上下文長度問題，而是涉及高階規劃、狀態追蹤與錯誤恢復的結構性瓶頸。模型在單一應用內的操作精度或許已相當成熟，但一旦需要在多個 Logged-In Accounts（已登入帳號）與資料孤島之間建立因果關聯，其推理鏈便迅速崩解。

此外，Model Failures（模型失敗案例）明顯聚集在 Long Trajectories（長執行軌跡）上。這與機器人領域的錯誤累積（error accumulation）現象相互呼應，但在桌面個人化場景中首次被系統性量化。代理程式在長序列互動中逐漸偏離使用者意圖，或陷入重複無效的 UI 操作，反映出現有架構缺乏穩健的元認知（meta-cognition）與執行軌跡反思機制。值得注意的是，由於所有模型使用相同的 Computer+Bash 工具介面，這些差異純粹來自模型內部的認知架構，而非外部工具鏈的差別，進一步凸顯了長程個人化任務對基礎模型本身的嚴峻挑戰。

#### 與現有研究的比較

相較於 WebArena、VisualWebArena 與 Mind2Web 等 Existing Agent Benchmarks（現有代理基準測試），MyPCBench 填補了 Live Web Evaluations（即時網頁評測）長期迴避的空白：即處理需要 Personal Information（個人資訊）與登入狀態的網站互動（例如透過 Zelle 還款給朋友、在 DoorDash 重新訂購每週五的固定餐點）。這些任務正是真實使用者對 Personal Assistants（個人助理）的核心需求，卻因 Reproducibility（可重現性）考量而被排除在傳統評測之外。

在桌面基準領域，OSWorld、WindowsAgentArena 與 MacOSWorld 雖然提供了 Full Desktop（完整桌面）環境，但其本質仍是 Empty Desktops（空白桌面）或 Generic Application States（通用應用程式狀態），缺乏真實的 User History（使用者歷史紀錄）。MyPCBench 的創新在於將 Persistent Identity（持續性身分）植入整個桌面軟體堆疊，使代理程式必須在充滿歷史資料的環境中運作，而非在無菌的測試台上執行孤立指令。

AppWorld 是現有文獻中最接近的競品，其透過 API-Level Accounts（API 層級帳號）建構了 Coherent User Identity（一致的使用者身分）。然而，AppWorld 僅在 API 層面運作，缺乏真實的 GUI 桌面、瀏覽器互動與視覺化介面操作。MyPCBench 則將評測推進至真實的圖形介面層級，更貼近 Claude Cowork 等消費性產品的實際 Deployment（部署）場景。另一方面，PersonalWAB 與 Persona2Web 等 Personalization（個人化）基準將使用者脈絡作為顯式輸入（explicit profile 或 memory store）餵給模型；相對地，MyPCBench 採用「隱式個人化（implicit personalization）」設計，要求模型主動從環境中發掘並整合 Cross-App History（跨應用程式歷史紀錄），評測難度更高，也更符合真實助理的運作邏輯。

然而，MyPCBench 亦存在可討論的限制。首先，單一 Canonical Persona（標準化人物角色）Michael Scott 雖確保了 Deterministic（確定性的）與 Reproducible（可重現的）評測，卻也帶來「過度擬合單一身分」的風險。若研究社群針對 Michael Scott 的特定資料分佈進行訓練或提示工程，Benchmark 可能淪為資料集而非能力量尺。其次，17 個模擬應用雖涵蓋銀行、旅遊、外送等核心消費領域，但畢竟不是真正的 Live Web（即時網路），與真實世界不斷變動的網站結構、驗證機制與廣告干擾仍有距離。最後，評測高度依賴 LLM-as-a-judge，雖然 Visible Side Effects（可見副作用）的設計降低了黑箱評分的風險，但評審模型自身的格式偏好與文化偏見仍可能影響 Partial Credit（部分得分）的分配。

#### 可重現性評估

MyPCBench 在可重現性方面的設計堪稱嚴謹。整個環境以 Docker 容器封裝真實的 QEMU/KVM VM，內含 Ubuntu 24.04、GNOME Shell、17 個 Pre-Logged-In Web Apps（預先登入的網頁應用程式）與完整的 LibreOffice Suite（LibreOffice 辦公套件），研究者只需拉取映像檔即可獲得與論文完全一致的測試平台。這種做法有效解決了桌面基準測試常見的「依賴地獄」問題，並透過 Resettable Desktop Control（可重設桌面控制）與 snapshot reset 機制，確保每次實驗都能精確回到 Michael Scott 的初始狀態，消除了 Live Web Evaluations（即時網頁評測）中難以控制的狀態飄移。

作者已公開釋出 Environment（環境）、Task Set（任務集）與 Agent Harness（代理測試框架），包含 184 個任務的自然語言 Rubric（評分標準）與 LLM-as-a-judge 評估格式，這對社群後續的模型比較與錯誤分析極具價值。不過，有幾個實務層面的考量值得注意：首先，QEMU/KVM 需要硬體虛擬化支援，且完整桌面 VM 的資源消耗不容小覷，這可能限制部分研究者的硬體可及性；其次，17 個 custom web apps 與特定版本的 Firefox、LibreOffice 綁定，長期維護成本與安全性更新將考驗作者團隊的持續投入；最後，LLM-as-a-judge 本身引入了額外的非確定性，儘管論文透過 Visible Side Effects（可見副作用）將評分錨定在客觀的介面變化上，但若未嚴格固定評審模型的版本與溫度參數，不同實驗室之間的複現仍可能出現細微落差。

整體而言，MyPCBench 在 Reproducibility（可重現性）與 Impersonality（非個人化特性）的經典權衡中做出了明智的選擇：以模擬環境的些許真實性折損，換取了個人化評測的科學嚴謹度。這在當前技術條件下是合理且必要的妥協。

#### 未來研究方向

MyPCBench 的出現為個人化代理研究開啟了多條值得深入探索的路徑。第一，在 Persona（人物角色）多樣性方面，亟需發展能夠程序化生成千萬個 Coherent User Identity（一致的使用者身分）的生成框架，突破單一 Michael Scott 的限制。這不僅能防止 Benchmark 過度擬合，更能測試模型對不同文化、語言、職業與生活型態的泛化能力，例如非英語使用者的 Digital Life（數位生活）軌跡。

第二，時間動態性（temporal dynamics）是下一個關鍵維度。當前的 Historical Data（歷史資料）為靜態植入，未來可設計隨時間演進的環境，例如每日新增 Bank Transactions（銀行交易紀錄）、Calendar Events（行事曆事件）與 Email Threads（電子郵件串），要求代理程式具備持續學習（continual learning）與記憶更新能力，而非僅在固定快照上操作。

第三，從模擬到真實的橋接（sim-to-real transfer）。可探索以隔離的瀏覽器設定檔與測試帳號，在保留 Reproducibility（可重現性）的前提下與真實網站互動，或建立「MyPCBench-to-Real」挑戰賽，測量代理程式從模擬桌面遷移至真實使用者電腦（在知情同意與隱私保護下）的表現落差。

第四，針對長軌跡與跨應用失敗，未來研究應聚焦於認知架構的創新。例如階層式規劃器（hierarchical planner）、具備 Cross-App Memory（跨應用記憶）的外部記憶庫、以及能夠偵測自身錯誤並重新規劃的反思機制（self-reflection）。MyPCBench 提供了完美的測試平台，可用於嚴格比較這些架構與單一端到端 LLM 的差異。

第五，安全與隱私基準的擴充。Personal Assistants（個人助理）必然接觸敏感的 Personal Information（個人資訊），未來任務設計應納入「資料最小化」、「權限控管」與「主動拒絕不當請求」等維度，評估代理程式在強大能力與隱私保護之間的權衡。

最後，隨著 OpenClaw、Claude Cowork 等 LLM-Based Assistants（大型語言模型助理）走向消費市場，建立與真實使用者請求持續對齊的評測機制 — 例如從 OpenClaw Community（OpenClaw 社群）定期收集新任務並動態擴充 Task Set（任務集）— 將是維持 MyPCBench 長期效度與實務相關性的關鍵。

## 論文問答

**Q1：MyPCBench 旨在解決現有電腦使用代理基準測試中的什麼核心問題？**
A：現有的基準測試大多在非個人化環境中進行，使用空白桌面、通用應用程式狀態以及最小化植入資料庫，導致評估情境與真實部署之間存在巨大落差。真實的個人助理必須在使用者的完整數位生活中運作，包含其情境脈絡、歷史資料與已登入帳號，但目前的測試無法涵蓋這些需要個人資訊或登入後才能使用的網站與任務。MyPCBench 正是為了填補這個缺口，提供一個能測試代理程式是否真正具備個人化能力的可重現環境。

**Q2：為什麼現有的網頁與桌面代理基準測試無法有效評估個人化智慧助理？**
A：現有基準測試為了確保評分的確定性與可重現性，通常採用模擬環境，犧牲了個人化特性，每個應用程式只攜帶當前任務字面所需的資料，背後沒有使用者歷史紀錄。即時網頁評測則刻意避開需要登入或包含變動個人資訊的網站，而現有提供已登入狀態的基準也僅植入通用或極簡的個人歷史，而非深度跨應用程式的個人身分。這種非個人化特性排除了大量真實使用者會向助理提出的請求，例如透過線上支付還錢給朋友或重新訂購每週五慣用的外送。

**Q3：個人化評估對於電腦使用代理從研究展示走向消費性產品為何至關重要？**
A：隨著大型語言模型助理從研究展示轉變為真正的消費性產品，例如 OpenClaw 與 Claude Cowork，評估機制必須跟上這個轉變，確認這些系統是否真正具備個人化能力。如果一個代理能下外送訂單，卻無法找出使用者每週五實際訂購的餐廳，那麼它作為個人助理的實用性就尚未被證明。因此，需要像 MyPCBench 這樣的基準來追蹤每一版模型發布時，個人化表現是進步還是退步。

**Q4：MyPCBench 的核心設計方法是什麼？它如何同時兼顧「個人化」與「可重現性」？**
A：MyPCBench 採用固定虛擬機映像檔與確定性快照重設的機制，延續了可重現桌面的設計，但徹底改變了資料植入方式。它使用單一標準化人物角色的人物設定與確定性多應用程式產生器，將深度跨應用程式個人身分完整植入整個 Linux 桌面環境，包含 17 個預先登入的網頁應用程式、LibreOffice 辦公套件與完整的 Firefox 設定檔。這種設計讓代理必須在持續性身分與跨應用程式歷史紀錄上運作，同時因為是封裝成 Docker 容器的固定映像，每次測試都能重設到完全一致的起始狀態。

**Q5：MyPCBench 相較於 AppWorld 等最接近的現有工作，其關鍵創新差異為何？**
A：AppWorld 雖然在 API 層級植入了一致的使用者身分，但它並非在真實的、可見的桌面圖形介面環境中運作；而 MyPCBench 則是在完整的 Linux 桌面軟體堆疊中，將個人資料散佈在 17 個模擬真實世界網頁應用程式與桌面應用裡。更重要的是，MyPCBench 的資料是交叉連結的，例如一筆旅遊訂單會在銀行交易紀錄、行事曆事件與電子郵件串中留下相關聯的紀錄，代理必須透過操作電腦介面來發現與利用這些關聯。此外，它提供了依評分標準評分的可見副作用與部分得分機制，讓評估更貼近真實個人助理的複雜表現。

**Q6：在任務與評估設計上，MyPCBench 做了哪些重要選擇以確保貼近真實使用者需求？**
A：研究團隊手動檢視了 OpenClaw 社群的 Discord 頻道，從真實使用者對個人助理的請求中汲取靈感，設計出 184 個任務，確保任務集反映使用者實際會提出的問題類型。每個任務都配備自然語言評分標準，並透過代理測試框架驅動標準的 CUA ReAct 循環，讓所有模型在統一的 Computer+Bash 工具介面上運作，避免工具差異影響比較。評分則採用大型語言模型作為評審的格式，針對代理操作後在畫面上產生的可見副作用進行評分，允許給予部分得分，更細緻地衡量個人化任務的完成度。

**Q7：MyPCBench 評測了哪些模型，整體表現最佳的模型為何？**
A：研究團隊評測了六個閉源與開源權重模型，包含 Claude Opus 4.6 與 Sonnet 4.6、GPT-5.5 與 GPT-5.4 mini，以及 Qwen3.5 35B-A3B 與 9B，所有模型都使用各自原生的電腦使用代理，但統一限制在相同的 Computer+Bash 工具介面。整體表現最佳的是 Claude Opus 4.6，它完全解決了 55.4% 的任務，也是唯一一個整體成功率超過 50% 的模型。其他模型在整體或跨應用任務上的表現明顯落後，顯示目前的 frontier agent 在個人化電腦使用上仍有極大的進步空間。

**Q8：實驗結果顯示模型在哪些類型的任務上最容易失敗？這揭示了什麼樣的挑戰？**
A：模型失敗案例明顯集中在需要橫跨多個應用程式的任務以及具有長執行軌跡的任務上，而這正是個人化對助理造成最大壓力的情境。舉例來說，在需要操作 7 個以上應用程式的任務中，即使是最強的 Claude Opus 4.6，其完全解決率也僅有 36%，而 GPT-5.5 在這類任務中只有 4.5%，其餘如 GPT-5.4 mini 與 Qwen 系列模型甚至達到 0%。這揭示了當代理必須在多個已登入帳號與交叉連結的個人歷史紀錄之間進行長期規劃與推理時，現有模型的多步驟推理與記憶整合能力仍然嚴重不足。

**Q9：除了整體成功率，MyPCBench 還提供了哪些深入的分析來理解模型行為？**
A：除了整體任務成功率，作者還建立了一套失敗分類法，並針對執行軌跡長度與每個任務涉及的應用程式數量進行了兩項擴展分析。這些分析顯示，隨著任務需要串連的應用程式數量增加，所有模型的表現都呈現顯著下降，突顯出跨應用程式歷史紀錄整合是當前最困難的瓶頸之一。透過這樣的細粒度分析，研究人員與開發者可以更清楚地識別出模型在個人化情境中的具體弱點，例如無法有效利用散佈在不同軟體中的相關聯紀錄。

**Q10：在真實的個人助理產品情境中，MyPCBench 所測試的能力為何特別重要？**
A：真實的個人助理必須能夠處理深植於使用者數位生活中的請求，例如查詢過去的銀行交易紀錄、根據行事曆事件安排行程、重訂慣用的外送訂單，或是在工作聊天紀錄與電子郵件串之間交叉比對資訊。這些任務無法在空白桌面或通用應用程式狀態下完成，因為它們依賴於持續性身分與長期累積的個人歷史紀錄。MyPCBench 透過模擬這種完整的個人電腦環境，確保被評測的代理具備在真實消費性產品中協助使用者管理其工作與個人紀錄的能力。

**Q11：MyPCBench 的設計對於評估消費性 AI 產品的開發與迭代有何具體助益？**
A：MyPCBench 提供了一個確定性的評估環境，讓產品團隊可以在每次模型發布時，穩定地測試個人化表現是提升還是衰退，而不會受到即時網頁變動或外部帳號狀態的干擾。由於環境封裝在 Docker 容器中，並具備可重設桌面控制機制，開發者能夠快速重現錯誤、進行除錯，並比較不同模型在完全相同的使用者情境脈絡下的行為差異。這種可重現性對於需要嚴格品質控管的消費性產品至關重要，因為它能確保評估結果的公平性與一致性，幫助團隊做出更可靠的發布決策。

**Q12：MyPCBench 對電腦使用代理這個研究領域可能帶來什麼樣的長遠影響？**
A：MyPCBench 首次將「深度個人化」與「完整桌面評估」結合，把領域焦點從過去針對空白桌面的股票狀態測試，轉移到真實個人助理所需面對的跨應用程式、具個人身分的電腦使用情境。這將激勵後續研究不僅追求代理在單一應用中的操作準確度，更要發展能夠理解並運用跨應用程式歷史紀錄的長期推理能力。由於環境、任務集與代理測試框架皆已開源釋出，整個社群可以在此基礎上擴充更多人物角色、任務類型與作業系統，推動個人化智慧電腦使用代理的整體發展。

**Q13：MyPCBench 目前存在哪些可預見的限制或侷限性？**
A：目前 MyPCBench 僅使用單一標準化人物角色 Michael Scott，這雖然確保了跨應用程式資料的一致性，但也意味著基準尚未涵蓋不同人口統計、職業或文化背景所產生的多樣化個人化情境。此外，環境中的 17 個網頁應用程式是模擬真實世界產品的自架網站，而非真正的即時網際網路服務，這在確保可重現性的同時，可能無法完全捕捉真實網站介面的所有動態變化與邊緣案例。最後，目前僅針對 Linux 桌面環境進行評估，尚未涵蓋 Windows 或 macOS 等其他主流作業系統，這可能限制了其在不同平台消費性產品上的直接適用性。

**Q14：從實驗結果來看，目前模型的失敗模式主要集中在哪些方面？**
A：實驗結果顯示，模型失敗案例強烈集中在需要橫跨多個應用程式以及具有長執行軌跡的任務上，顯示代理在進行長期規劃與維持跨應用程式工作記憶方面存在結構性困難。特別是在涉及 7 個以上應用程式的任務中，多數模型的完全解決率極低甚至為零，代表它們無法有效整合散佈於不同軟體中的相關聯紀錄來完成複雜目標。這些失敗模式表明，目前的 frontier agent 雖然能處理單一應用內的明確指令，但在面對需要主動探索個人歷史資料、進行多步驟推理的真實個人助理情境時，其能力仍然相當脆弱。

**Q15：未來研究可以如何延伸或改進 MyPCBench 的架構與應用？**
A：未來研究可以擴充基準以包含多個不同的人物角色，測試代理在面對不同生活型態、職業與個人偏好時的泛化能力，而不僅限於單一標準化人物角色。另一個方向是將評估擴展到 Windows 或 macOS 等更多作業系統，甚至建立混合式環境，在保持可重現性的同時引入部分受控的即時網頁元素，以縮小模擬與真實部署之間的差距。此外，社群可以利用已釋出的代理測試框架與任務集，開發更先進的記憶機制、跨應用程式推理架構，以及更精細的評分模型，從而逐步提升個人化智慧助理在真實數位生活中的實用性。

## 實務應用指南

### 適用場景

1. **消費級個人助理上市前驗證**  
   適用於即將推向市場的 LLM 個人助理產品（如 OpenClaw、Claude Cowork 類服務），在真實使用者導入前，驗證其能否在充滿個人歷史資料的桌面環境中，正確執行跨應用程式任務。

2. **企業內部數位員工壓力測試**  
   將方法論遷移至企業情境，為虛擬員工建立一致的企業身分與跨系統紀錄（如 ERP、CRM、行事曆），評估其在長軌跡、多平台流程中的穩定性。

3. **長軌跡代理回歸測試**  
   作為模型迭代發布（Model Release）的自動化閘道，每次更新模型時執行標準化任務集，確保個人化表現（Personalization Performance）未隨版本升級而退化。

4. **跨應用自動化流程開發參考架構**  
   開發團隊可參考 MyPCBench 的「人物角色資料植入 → 多應用程式產生器 → 可重設桌面控制」流程，建構內部的個人化自動化測試床。

5. **人機協作任務的失敗模式分析**  
   利用論文提出的失敗分類法，針對橫跨七個以上應用程式的任務進行縮放分析，識別當前 frontier model 的能力邊界，作為功能規劃的依據。

---

### 實作前置條件

**資料需求**
- **標準化人物角色（Canonical Persona）規格書**：需定義完整的使用者輪廓（職業、消費習慣、社交網絡），並明確列出跨應用關聯邏輯（例如：一筆旅遊訂單需同步產生行事曆事件、銀行交易紀錄與電子郵件確認信）。
- **合成歷史資料**：包含銀行交易紀錄、電子郵件串、行事曆事件、網頁瀏覽紀錄等，且需交叉連結（Cross-Linked）以形成深度跨應用程式個人身分。
- **真實任務樣本**：建議從目標使用者社群（如 OpenClaw 社群）收集真實請求，作為任務集（Task Set）的靈感來源。

**運算需求**
- **虛擬化主機**：需支援 QEMU/KVM 的實體或雲端主機，以執行內含 GNOME Shell 的 Ubuntu 24.04 VM。
- **評分模型運算資源**：用於 LLM-as-a-judge 評分流程，需能呼叫閉源或開源權重模型進行自動化評分。
- **儲存空間**：Docker 映像檔需容納完整桌面軟體堆疊（Full Desktop Stack）、17 個預先登入的網頁應用程式及大量植入資料。

**技術與技能需求**
- **虛擬化與容器化**：熟悉 Docker、QEMU/KVM 與 Linux 桌面環境調校。
- **網頁應用開發**：能建構模擬真實世界網頁應用程式（Simulated Real-World Web Applications）的前後端系統，並處理登入狀態與資料持久化。
- **代理框架知識**：理解 ReAct 循環與 Computer+Bash 工具介面（Tool Surface）設計。
- **評測設計能力**：能撰寫自然語言評分標準（Rubric），並設計可見副作用（Visible Side Effects）的評分機制與部分得分（Partial Credit）邏輯。

### 實作步驟建議

**步驟一：設計人物角色與跨應用資料架構**  
定義單一標準化人物角色，繪製資料關聯圖，確保一筆事件（如外送訂單）會在相關聯的紀錄中留下一致痕跡。建立多應用程式產生器，確保輸出為確定性的（Deterministic）。

**步驟二：建構可重現的個人化桌面環境**  
將 Linux 桌面、Firefox Profile（含書籤與網頁瀏覽紀錄）、LibreOffice 辦公套件、檔案管理員與 17 個預先登入的網頁應用程式封裝為 Docker/QEMU 映像檔。實作可重設桌面控制（Resettable Desktop Control），確保每次評測起點一致。

**步驟三：開發任務集與評分標準**  
從真實使用者請求萃取 150–200 條任務，涵蓋單一應用與橫跨多個應用程式的情境。為每個任務撰寫自然語言 Rubric，定義「完全解決」與部分得分條件，並建立 LLM-as-a-judge 的自動化評分管線。

**步驟四：打造統一代理測試框架（Agent Harness）**  
開發標準化的 Computer+Bash 工具介面，將不同模型提供者的原生電腦使用代理輸出統一為相同動作空間。實作 ReAct 循環、截圖觀察與動作執行模組，並整合軌跡記錄功能。

**步驟五：執行多模型基準測試**  
選定閉源權重模型與開源權重模型各數個，在統一工具介面上執行完整任務集。記錄執行軌跡（Trajectories）、步驟數與最終評分。

**步驟六：建立失敗分類法與縮放分析**  
針對未完全解決的任務進行歸因，特別分析「橫跨應用程式數量」與「軌跡長度」兩個維度的縮放趨勢，產出模型能力邊界報告。

### 潛在風險與注意事項

- **確定性與真實性權衡**：為了可重現性而採用模擬環境，可能無法反映真實網站的動態變化（如 UI 改版、CAPTCHA、雙因素驗證）。建議在 MyPCBench 通過後，追加小規模即時網頁評測（Live Web Evaluations）作為第二道驗證。  
- **人物角色偏差**：單一標準化人物角色（如 Michael Scott）可能無法涵蓋多元使用者群體的行為模式。實務上應規劃多個人物角色，或設計可參數化的人物角色產生器。  
- **合成資料的隱私邊界**：即使使用虛構人物，植入的資料仍可能意外貼合真實個資模式。務必確保所有銀行交易紀錄、電子郵件串與工作聊天紀錄皆為演算法生成，並進行去識別化審查。  
- **長軌跡錯誤累積**：代理在長執行軌跡中容易因早期小錯誤而導致後期偏離。建議在任務設計時加入中間狀態檢查點（Checkpoint），或在代理測試框架中內建軌跡長度預警機制。  
- **工具介面相容性**：不同模型提供者的原生電腦使用代理格式各異，統一為 Computer+Bash 工具介面時，需額外處理動作解析錯誤與逾時重試邏輯，避免評測結果被介面層雜訊干擾。

---

### 與其他技術的整合建議

- **與 RAG／記憶系統整合**：將跨應用歷史紀錄（Cross-App History）匯出為結構化記憶庫，讓代理在執行任務時能透過檢索增強生成（RAG）補強個人化情境脈絡（Context），而非僅依賴畫面截圖的即時資訊。  
- **與 API 層級基準測試互補**：MyPCBench 專注於 GUI 層的個人化評測，可與 AppWorld 等 API 層級帳號（API-Level Accounts）基準測試並行。兩者結合可同時驗證「使用者看得見的操作」與「後端資料一致性」。  
- **與 CI/CD 管線整合**：將可重設桌面控制與自動化評分流程封裝為 CI 階段，作為每次模型發布前的回歸測試閘道。若個人化表現分數低於門檻，即自動阻擋部署（Deployment）。  
- **與可觀測性平台整合**：將執行軌跡、可見副作用與評分結果匯出至既有的監控系統（如 Grafana、LangSmith），支援工程師進行後續的人機協作審查與除錯。  
- **與真人使用者測試銜接**：以 MyPCBench 作為大規模自動化篩選器，僅讓通過基準測試的模型版本進入真人使用者測試，顯著降低使用者研究的時間與成本。

### 給不同背景讀者的閱讀建議

**初學者**  
請聚焦於第一章「Introduction」與圖一，理解「非個人化環境（Impersonal Environments）」與「個人化智慧電腦使用代理」的核心差異。將 MyPCBench 想像成一個為虛擬人物 Michael Scott 打造的「數位雙生測試場」：裡面有他的銀行交易紀錄、外送訂單與工作聊天紀錄，而代理必須像真人助理一樣在這些資料中穿梭完成任務。無需深入技術細節，掌握「為何需要個人化評測」即可。

**AI 工程師**  
重點研讀第三節「MYPCBENCH」與代理測試框架的實作細節，特別是統一 Computer+Bash 工具介面的設計、Docker/QEMU 環境的可重現性機制，以及 LLM-as-a-judge 的評分標準設計。這些元件可直接遷移至您內部的評測管線，用於驗證自家電腦使用代理在長軌跡與跨應用任務上的穩定性。

**研究人員**  
請深入分析論文中的失敗分類法與縮放分析（跨應用數量與軌跡長度），關注作者對「個人化為何使代理更困難」的論證。可延伸的研究方向包括：多人物角色泛化（而非僅 Michael Scott）、動態環境適應（放寬確定性限制），以及更細緻的部分得分（Partial Credit）機制設計。

**產品經理**  
從第一節與適用場景出發，評估 MyPCBench 的方法論是否適用於自家個人助理產品的品質閘道。請特別留意論文的關鍵數據：最強模型僅完全解決 55.4% 的任務，而橫跨七個以上應用程式的任務更降至 36%。這代表了當前技術天花板，可作為產品功能邊界與使用者溝通預期的務實依據。
