## ⚡ TL;DR

現有電腦使用代理受限於 GUI 介面與預定義工具，無法程式化存取系統狀態。
本文提出 CUAWright 終端機執行框架，僅以 Bash 指令作為統一動作介面。
在多項基準測試中大幅超越 GUI 介面，並降低約 37.5% 預估成本。

## 摘要翻譯

當前主流的電腦使用代理（Computer-use Agents）方法是將模型與領域專用執行框架（Domain-specific Harness）結合：瀏覽器或桌面環境配備了在任務執行（Task Execution）前即固定的人工設計工具（Human Engineered Tools）。隨著模型程式設計能力的提升，GUI 原生（GUI Native）且靜態的執行框架（Static Harness）阻礙了模型對系統狀態（System State）進行直接的程式化操作（Programmatic Operation），也限制了工具的靈活建構。為此，我們提出 CUAWright，一個約 3K 行程式碼的極簡終端機執行框架（Terminal Harness），採用 Bash 指令（Bash Commands）作為其唯一的動作介面（Action Interface），並以檔案系統（File System）作為其可演化空間（Evolvable Space），用於動態建立工具（Dynamic Tool Creation）與管理上下文（Context Management）。我們在廣泛的數位任務（Digital Tasks）上進行了全面的實驗，並證明透過賦予代理一個極簡、可程式化介面（Programmable Interface），相較於使用 GUI 或混合式 CLI 介面（Hybrid CLI Interface）的代理，能在廣泛的任務上取得顯著優異的成果。在 OSWorld 2.0 上，CUAWright 相較於已發表的 GPT-5.5 基準（Baseline），在部分獎勵（Partial Reward）上達成 33.2% 的相對改進（Relative Improvement），同時將預估成本（Estimated Cost）降低 37.5%。在 Online-Mind2Web 與長時程（Long Horizon）Odysseys 基準上，CUAWright 在成功率（Success Rate）上分別以 4.7% 與 44.0% 大幅超越 GUI 原生執行框架（GUI Native Harness）。此外，我們發現這些效益亦體現於需要精準視覺理解（Visual Understanding）與 CLI 互動的 CAD 應用程式（CAD Applications）：在 CADGenBench 與 BenchCAD 上，我們的統一執行框架搭配 GPT-5.5，相較於其他基於 CLI 的執行框架，帶來 8.1%–41.6% 的相對改進。綜合而言，這些結果顯示數位環境（Digital Environments）的可程式化程度遠高於其 GUI 介面所暗示的水準，而一個極簡、以終端機為核心的執行框架是提升效能與效率的關鍵。

### 核心貢獻（3～5點）
- **提出極簡統一介面 CUAWright**：以僅約 3K 行程式碼的終端機執行框架，採用 Bash 指令作為唯一動作介面、檔案系統作為可演化空間，使代理能動態建立工具並靈活管理上下文。
- **突破 GUI 原生靜態框架的限制**：證明賦予代理可程式化介面後，相較於 GUI 或混合式 CLI 介面，能在廣泛的數位任務上取得顯著優異的成果。
- **在多項基準上展現優異效能與效率**：於 OSWorld 2.0 達成 33.2% 相對改進並降低 37.5% 成本；於 Online-Mind2Web 與長時程 Odysseys 基準上，成功率分別超越 GUI 原生執行框架 4.7% 與 44.0%。
- **效益延伸至 CAD 應用領域**：在 CADGenBench 與 BenchCAD 上，搭配 GPT-5.5 相較於其他基於 CLI 的執行框架，帶來 8.1%–41.6% 的相對改進，驗證統一介面於需精準視覺理解與 CLI 互動之任務的適用性。
- **揭示數位環境的可程式化潛力**：論證數位環境的可程式化程度遠高於其 GUI 介面所暗示的水準，主張極簡、以終端機為核心的執行框架是提升電腦使用代理效能與效率的關鍵。

### 適合對象
本研究最適合以下讀者閱讀：從事電腦使用代理（Computer-use Agents）、網頁代理（Web Agents）與桌面代理（Desktop Agents）研究的學者與工程師；關注大型語言模型工具執行（Tool Execution）、上下文管理（Context Management）與動作介面（Action Interface）設計的研究人員；對 GUI 自動化、CLI 自動化及 CAD 應用程式（CAD Applications）中視覺理解（Visual Understanding）與程式化操作（Programmatic Operation）整合感興趣的實務開發者；以及評估 AI 代理於長時程（Long Horizon）任務中表現的基準測試（OSWorld 2.0、Online-Mind2Web、Odysseys、CADGenBench、BenchCAD）研究者與產品決策者。

## 深度分析

#### 方法論解析

**問題定位與核心洞察**

CUAWright 的方法論起點是對現行電腦使用代理（computer-use agents）範式的批判性反思。傳統做法將模型與領域專用執行框架（domain-specific harness）耦合：瀏覽器代理透過螢幕截圖（screenshot）或 DOM 樹（DOM tree）觀察網頁狀態，再以像素座標（pixel coordinates）或元素選擇進行操作；桌面代理則模擬人類的滑鼠與鍵盤動作（mouse and keyboard actions）。這種 GUI 原生執行框架（GUI native harness）存在兩個根本限制：其一，螢幕截圖僅暴露環境狀態的有限資訊；其二，低階動作（low-level actions）使代理無法直接、程式化地存取底層系統狀態（system state）。

作者的核心洞察在於：隨著模型程式碼能力的提升，GUI 介面已成為瓶頸而非助力。數位環境本質上比其 GUI 所呈現的更「可程式化」（programmable），因此應將動作介面（action interface）從 GUI 抽象提升至終端機層級。

**POMDP 形式化**

CUAWright 將數位代理任務形式化為部分可觀察馬可夫決策過程（POMDP），定義如下：

- 環境狀態空間 $S$
- 觀察空間 $O$
- 終端機動作空間 $A_{\text{term}}$
- 轉移函數 $T$

在每一步 $t$，環境處於狀態 $s_t \in S$，並產生觀察 $o_t \in O$。代理根據自然語言任務 $T$、當前觀察 $o_t$ 與互動歷史 $h_t = \{(o_i, a_i)\}_{i<t}$ 產生可執行的終端機動作：

$$a_t = \pi(T, o_t, h_t), \quad a_t \in A_{\text{term}}$$

執行動作後，環境轉移至 $s_{t+1} = T_E(s_t, a_t)$ 並產生下一觀察 $o_{t+1}$。

關鍵設計在於狀態分解：$s_t = (x_t, f_t)$，其中 $x_t$ 代表底層應用程式與系統狀態，$f_t$ 代表持久化檔案系統狀態（persistent filesystem state），包含代理工作區與互動過程中產生的工件（artifacts）。此分解使代理能透過檔案系統管理上下文並動態建構工具。

**終端機作為統一動作介面**

CUAWright 的動作空間 $A_{\text{term}}$ 在所有任務領域中保持固定，僅由可執行的終端機指令構成。具體運作方式依任務類型而異：

1. **網頁任務**：代理產生針對除錯協定（debugging protocol，文中提及 Microsoft 2025，應指 Chrome DevTools Protocol）的程式碼，透過 CDP 指令直接操控瀏覽器，繞過 GUI 抽象。
2. **桌面任務**：代理透過終端機指令、CLI 工具，或直接編輯源檔案（source file）來操作系統。
3. **GUI 強制情境**：當介面確實無法程式化控制時，代理透過 `xdotool` 或 `pyautogui` 指令執行鍵盤與滑鼠動作。

此設計實現了兩個關鍵特性：(1) 單一通用終端機動作空間，使代理能同時與系統狀態及鍵鼠動作互動；(2) 對檔案系統的直接程式化存取，使代理能管理工作上下文並透過撰寫、測試、執行程式檔案來打造新工具。

**視覺按需載入（Vision on Demand）**

傳統 GUI 代理的觀察 $o_t = \{o^{\text{screen}}_t, o^{\text{a11y}}_t\}$ 包含每一步的螢幕截圖與無障礙資訊（accessibility observations），導致長時程任務的上下文快速膨脹。CUAWright 將視覺輸入設為可選：$o_t$ 預設僅包含終端機動作的輸出。當代理需要視覺資訊時，透過兩步驟取得：(1) 呼叫螢幕截圖 Python CLI 工具並指定儲存路徑；(2) 呼叫影像載入 Python CLI 工具將截圖載入上下文。此設計在 OSWorld 2 上將成本縮減至約傳統範式的三分之一。

**持久化工作區作為外部狀態**

工作區 $w_t \subseteq f_t$ 是分配給代理的檔案系統子集，作為外部狀態（external state）運作。此設計使代理能：(1) 將中間結果、輔助資料、工具程式碼持久化；(2) 在跨步驟、跨任務間累積知識；(3) 透過檔案系統實作複雜的上下文管理策略。

**方法論的理論意涵**

CUAWright 的設計哲學可概括為「最小化、可演化、統一」。最小化體現在僅約 3K 行程式碼的精簡實作；可演化體現在檔案系統作為工具與上下文的動態建構空間；統一體現在單一動作介面跨越網頁、桌面、CAD 等異質領域。這與傳統「領域專用、人工設計工具」的範式形成鮮明對比，預示了一種「代理自建工具」的範式轉移。

#### 實驗數據解讀

**OSWorld 2.0（桌面任務基準）**

OSWorld 2.0 評測結果顯示 CUAWright 在桌面任務上取得顯著優勢：

| 系統 | 部分分數（Partial Score） |
|------|--------------------------|
| CUAWright (GPT-5.6 Sol) | 67.9% |
| CUAWright (GPT-5.5) | 63.2% |
| GPT-5.6 Sol（原生 GUI） | 62.7% |
| Claude Opus 4.8 | 54.8% |
| GPT-5.5（原生 GUI） | 47.5% |

關鍵發現：(1) CUAWright 搭配 GPT-5.5 達到 63.2%，超越 GPT-5.6 Sol 原生 GUI 的 62.7%，意味著執行框架改進帶來的增益可超越模型版本升級；(2) 相較於 GPT-5.5 基準，CUAWright 帶來 33.2% 的相對改進（relative improvement）於部分獎勵（partial reward）；(3) 同時預估成本（estimated cost）降低 37.5%。此結果驗證了「視覺按需載入」的成本效益假設。

#### 與現有研究的比較

**定位於電腦使用代理研究譜系**

CUAWright 定位於電腦使用代理研究的演進脈絡中：

1. **第一代：純 GUI 代理**（Deng et al., 2023; Zhou et al., 2024; He et al., 2024; Zheng et al., 2024; Hong et al., 2024; Pahuja et al., 2025; Shi et al., 2025; Gupta et al., 2026; Awadallah et al., 2026）：以螢幕截圖加座標點擊為主，資訊密度低、動作精度差。

2. **第二代：混合介面代理**（Song et al., 2026; Zhong et al., 2026; Parikh et al., 2026）：透過子代理分工（sub-agents）或顯式程式碼執行工具來結合 GUI 與程式化操作，但仍以 GUI 為中心且工具集固定。

3. **第三代：終端機原生代理**（CUAWright）：以終端機指令為統一動作介面，工具可動態建構。

**相較於 GUI 原生執行框架的改進**

CUAWright 相對於 GUI 原生執行框架的改進可歸納為三個維度：

- **資訊密度**：終端機輸出提供精確的文字資訊，無需從像素中推測狀態。
- **動作精度**：程式化指令避免座標點擊的累積誤差。
- **成本效率**：視覺按需載入大幅降低 token 消耗。

**相較於混合 CLI 介面的改進**

相較於混合 CLI 介面（hybrid CLI interface），CUAWright 的優勢在於：(1) 動作空間統一，無需在 GUI 與 CLI 子代理間切換；(2) 工具可動態建構而非預定義；(3) 檔案系統作為統一外部狀態，避免子代理間的狀態同步問題。

**相較於 Python 工具方法的改進**

在 BenchCAD 上，CUAWright (79.0%) 顯著超越 GPT-5.5 + Python 工具 (55.8%) 與 GPT-5.5 直接無工具 (43.8%)。這顯示僅提供 Python 執行工具不足以發揮模型潛力；真正的瓶頸在於動作介面的統一性與檔案系統的外部狀態支援。

**方法論的侷限性**

儘管結果亮眼，CUAWright 仍存在以下侷限：

1. **安全性風險**：賦予代理完整終端機存取權限帶來潛在的安全風險，包括誤刪除檔案、執行惡意指令等。論文中未深入討論沙箱化（sandboxing）與權限控制機制。

2. **GUI 強制情境的處理**：當介面確實無法程式化控制時，代理需退化至 `xdotool`/`pyautogui`，此時效能可能下降。論文中未量化此類情境的頻率與影響。

3. **模型依賴性**：CUAWright 的優勢高度依賴底層模型的程式碼能力。對於程式碼能力較弱的模型（如 Qwen-3.5-VL-9B），終端機介面可能反而成為障礙。

4. **基準偏置**：所選基準（OSWorld、Online-Mind2Web、Odysseys、CADGenBench、BenchCAD、WeaveBench）可能偏向有利於 CLI 操作的任務類型；對於高度視覺化、缺乏 CLI 等價物的任務（如圖像編輯、影片剪輯），CUAWright 的優勢可能不成立。

5. **長時程任務的評估**：Odysseys 雖為長時程基準，但 77.5% 的成功率仍意味著近四分之一的任務失敗；失敗模式分析與錯誤恢復機制未充分探討。

#### 可重現性評估

**程式碼可用性**

論文中提及 CUAWright 實作為約 3K 行程式碼的精簡終端機執行框架。然而，從提供的全文片段中未明確聲明程式碼是否開源。考量到作者為 Microsoft Research 實習生（†Work done during an internship at Microsoft Research），且 arXiv 預印本編號為 2610.04116v1（2026 年 10 月），程式碼可能隨正式發表或附錄釋出。建議讀者追蹤作者後續發布或會議版本以確認開源狀態。

**資料集與基準**

實驗採用六個公開基準：OSWorld 2.0、Online-Mind2Web、Odysseys、CADGenBench、BenchCAD、WeaveBench。這些基準均為公開可取得，促進了結果的可重現性。然而，具體的評測配置（如任務子集、評測協議、隨機種子）需參考附錄或補充材料。

**模型權重**

實驗涉及多個專有模型：GPT-5.4、GPT-5.5、GPT-5.6、GPT-5.6 Sol、Claude Opus 4.6/4.8、Claude Sonnet 4.6、Claude Fable 5、Claude Computer Use 3.7、Gemini 2.5 Computer Use、Qwen-3.5-VL-9B、Mythos 5。其中部分模型為閉源（OpenAI、Anthropic、Google），重現完整實驗需取得對應 API 存取權限。

**重現的關鍵要素**

欲重現 CUAWright 的結果，需具備：

1. 終端機執行框架的完整實作（程式碼若開源則可直接使用，否則需自行實作）。

4. CDP、除錯協定等領域專用介面的整合。

**可重現性評級**

綜合考量，CUAWright 的可重現性處於中等水準：基準公開、模型可透過 API 取得，但核心程式碼的開源狀態未明確聲明，且實作涉及多個異質環境的配置複雜度。

## 論文問答

**Q1：為什麼現有的電腦使用代理方法在處理數位任務時存在根本性的限制？**

A：現有的電腦使用代理主要依賴 GUI 原生執行框架，透過螢幕截圖或 DOM 樹觀察環境狀態，並使用低階的滑鼠與鍵盤動作來操作系統。這種設計存在兩個根本性問題：第一，螢幕截圖只能暴露有限的環境狀態資訊，無法讓代理直接存取底層系統狀態；第二，預定義的固定工具集限制了代理的靈活性，使其無法根據任務需求動態建構新工具。這些限制使得代理無法充分利用現代模型日益強大的程式設計能力，從而形成了一道隱形的天花板。

**Q2：為什麼 GUI 原生或混合式 CLI 介面無法充分發揮前沿模型的程式設計能力？**

A：GUI 原生介面將代理的動作空間限制在像素座標點擊和鍵盤輸入等低階動作上，這使得模型無法直接以程式化方式操作系統狀態，也無法靈活地建構任務專屬的工具。混合式介面雖然引入了程式碼執行能力，但通常透過預定義的工具來實現，且仍以 GUI 為中心，限制了代理的靈活性與自主性。這些靜態的執行框架無法讓模型根據任務需求動態建立、測試和重用工具，從而浪費了前沿模型強大的程式設計潛力，也阻礙了代理能力的進一步提升。

**Q3：為什麼數位環境的可程式化程度比 GUI 介面所暗示的要高得多？**

A：許多看似只能透過 GUI 操作的數位任務，實際上可以透過命令列工具、腳本或直接編輯源檔案來完成。例如，瀏覽器任務可以透過除錯協議（如 CDP）以程式化方式驅動，桌面任務則可以透過 CLI 工具或終端機指令自然執行，而 CAD 任務則可透過 CLI 互動完成。當某些介面確實阻礙程式化控制時，代理仍可透過 xdotool 或 pyautogui 等命令發送鍵盤和滑鼠動作。這種設計哲學使得終端機介面成為一個真正通用的動作空間，能夠統一處理各種數位任務，揭示了 GUI 介面所掩蓋的可程式化深度。

**Q4：CUAWright 的核心設計理念是什麼？它如何實現「最小化」與「統一性」？**

A：CUAWright 的核心設計理念是將終端機作為代理與任務環境之間的唯一介面，僅使用約 3K 行程式碼實現，這在當今複雜的代理系統中實屬罕見。其「最小化」體現在動作空間的精簡——所有動作都是 bash 指令，無需為不同領域定義不同的工具集；其「統一性」則體現在跨領域的通用性——同一個動作介面可用於網頁、桌面和 CAD 等不同任務，無需針對特定領域進行客製化。這種設計使得代理能夠直接存取系統狀態，並透過檔案系統動態建立和管理工具，從而釋放出前所未有的靈活性。

**Q5：CUAWright 的「按需視覺」設計如何降低長時程任務的成本？**

A：傳統的 GUI 代理在每一步都會將螢幕截圖附加到上下文中，導致長時程任務的互動上下文迅速膨脹，進而推高 API 成本。CUAWright 採用「按需視覺」策略，預設觀察僅包含終端機輸出，視覺資訊變成可選的；當代理需要視覺資訊時，會先呼叫截圖 CLI 工具將影像儲存到指定路徑，再呼叫影像載入工具將其納入上下文。這種設計在 OSWorld 2 上實現了約三分之一的成本降低（具體為 37.5%），證明了視覺資訊並非每一步都必要，代理可以根據任務需求智慧地決定何時需要視覺輸入。

**Q6：檔案系統在 CUAWright 中扮演什麼角色？為什麼它是代理效能的關鍵？**

A：在 CUAWright 中，檔案系統不僅是資料儲存空間，更是代理的工作區與外部狀態，扮演著「可演化空間」的核心角色。代理可以透過終端機指令在檔案系統中寫入、測試和執行程式檔案，從而動態建立任務專屬的工具，並在後續步驟中重複使用這些工具。這種設計讓代理能夠有效管理自己的上下文，避免長時程任務中的上下文膨脹問題。消融研究顯示，檔案系統對於代理效能至關重要——移除它會顯著降低表現，因為代理失去了建構和重用工具的能力，也失去了管理外部狀態的關鍵機制。

**Q7：CUAWright 在哪些基準測試上進行了評估？這些基準測試涵蓋了哪些任務類型？**

A：CUAWright 在六個基準測試上進行了全面評估，涵蓋了桌面、網頁、長時程和 CAD 等多種類型的任務。具體包括：OSWorld-V2（桌面任務）、Online-Mind2Web（網頁代理）、Odysseys（長時程任務）、CADGenBench 和 BenchCAD（CAD 生成與視覺理解）、以及 WeaveBench。這些基準測試的選擇反映了 CUAWright 設計的通用性目標——透過單一終端機介面處理各種數位任務，從而驗證其「統一介面」設計理念的可行性與有效性。

**Q8：CUAWright 在不同基準測試上的關鍵效能提升是多少？**

A：CUAWright 在多個基準測試上都展現了顯著的效能提升。在 OSWorld 2.0 上，相較於 GPT-5.5 基準，實現了 33.2% 的部分獎勵相對改進，同時預估成本降低了 37.5%。在 Online-Mind2Web 和 Odysseys 上，勝過 GUI 原生執行框架的成功率分別為 4.7% 和 44.0%，其中長時程任務的提升尤為顯著。在 CAD 相關的 CADGenBench 和 BenchCAD 上，相較於其他基於 CLI 的執行框架，獲得了 8.1% 至 41.6% 的相對改進。這些結果一致表明，終端機導向的介面在效能和效率上都優於傳統方法。

**Q9：CUAWright 進行了哪些消融研究？這些研究揭示了什麼關鍵發現？**

A：CUAWright 進行了單代理與多代理設定的消融研究，以及檔案系統角色的消融研究，以深入理解各元件的貢獻。研究發現，檔案系統對於代理效能至關重要——移除它會顯著降低表現，因為代理失去了建構和重用工具的能力。此外，詳細分析揭示了前沿模型的「湧現行為」——它們會在任務過程中自主建立創造性的工具並重複使用，展現出意想不到的自主性和創造力。這些發現表明，給予代理足夠的靈活性和可程式化介面，能夠激發模型展現出設計者未曾預料的能力。

**Q10：CUAWright 在實際應用場景中可能適用於哪些任務？**

A：CUAWright 的設計使其適用於各種需要程式化控制的數位任務，包括網頁自動化、桌面應用操作、CAD 設計與生成等。在長時程任務（如 Odysseys）中表現尤為突出，因為其終端機介面和檔案系統工作區能有效管理複雜的任務流程，避免上下文膨脹。對於需要視覺理解的任務（如 CAD 應用），按需視覺機制允許代理在必要時獲取視覺資訊，同時保持整體效率。這種通用性使得 CUAWright 能夠應對從簡單自動化到複雜多步驟任務的各種場景，展現出廣泛的實用價值。

**Q11：從產品化的角度來看，CUAWright 的設計有哪些實際優勢？**

A：從產品化角度來看，CUAWright 的「最小化」設計（僅約 3K 行程式碼）使其易於部署、維護和客製化，大幅降低了工程複雜度。其統一的終端機介面降低了跨領域應用的開發成本，無需為不同任務類型維護多套工具集，從而簡化了產品架構。按需視覺機制顯著降低了 API 呼叫成本，在 OSWorld 2 上實現了約三分之一的成本節省，對於大規模部署具有重要意義。此外，代理能夠動態建立和重用工具的能力，使得系統能夠隨著使用而「進化」，這對於長期部署的產品來說是一個關鍵優勢。

**Q12：CUAWright 的研究成果對電腦使用代理領域有什麼更廣泛的影響？**

A：CUAWright 的研究成果挑戰了「電腦使用代理必須以 GUI 為中心」的傳統假設，證明了終端機導向的介面在效能和效率上都更具優勢，為該領域提供了新的設計範式。這項工作可能會激發更多研究探索可程式化介面在數位代理中的應用，並重新思考 GUI 與 CLI 在代理設計中的角色分工。更廣泛地說，這項研究強調了「介面設計」對代理能力的關鍵影響——給予代理更靈活、可程式化的介面，能夠釋放模型的潛在能力，這一發現對整個 AI 代理研究社群都具有重要的啟示意義。

**Q13：CUAWright 存在哪些已知的限制？**

A：雖然 CUAWright 在多個基準測試上表現優異，但它仍有一些限制。首先，對於某些確實無法透過命令列控制的介面，代理仍需依賴 xdotool 或 pyautogui 等工具發送低階動作，這在某種程度上回到了傳統 GUI 代理的範式。其次，終端機介面對於某些高度視覺化或缺乏 CLI 替代方案的任務可能不是最佳選擇，例如需要精細像素操作的圖像編輯。此外，代理動態建立工具的能力雖然強大，但也可能帶來安全性和可預測性方面的挑戰，因為代理可能會建立出意料之外的工具行為。

**Q14：CUAWright 在哪些情況下可能會失敗？**

A：CUAWright 在以下情況下可能會面臨挑戰：當任務環境嚴重依賴 GUI 且缺乏 CLI 替代方案時，終端機介面的優勢就會被削弱；當任務需要極其精細的視覺操作（如像素級的圖像編輯或複雜的圖形設計）時，按需視覺機制可能無法提供足夠的視覺資訊；以及當代理建立的工具出現錯誤或意外行為時，可能會導致任務失敗或產生不可預測的結果。此外，對於需要即時視覺反饋的任務（如影片編輯或遊戲），按需視覺機制可能會引入額外的延遲，影響任務執行的流暢性。

**Q15：CUAWright 的未來研究方向是什麼？**

A：CUAWright 的未來研究方向可能包括以下幾個方面：探索更豐富的終端機動作原語，以處理更廣泛的任務類型；研究如何更好地平衡按需視覺與即時視覺的需求，開發更智慧的視覺資訊請求策略；以及深入理解代理湧現的工具建立行為，以設計更安全、更可預測的系統。此外，將 CUAWright 的設計理念擴展到其他領域（如機器人控制或物聯網裝置）也是一個值得探索的方向，因為其「可程式化介面」的核心思想具有跨領域的普適性。這些研究方向將有助於進一步釋放數位代理的潛力，推動整個領域的發展。

## 實務應用指南

### 適用場景

1. **企業內部自動化流程（桌面代理）**：用於自動化處理 Office 文件批次轉換、ERP 系統資料匯入、CRM 操作等需要跨多個桌面應用程式的繁瑣工作。終端機介面可直接呼叫 CLI 工具（如 `libreoffice --headless`、`xdotool`）繞過 GUI 限制，特別適合需要處理大量結構化操作的後台任務。

2. **網頁爬取與互動式網頁任務（網頁代理）**：透過 Chrome DevTools Protocol（CDP）以程式化方式驅動瀏覽器，適用於需要登入、表單填寫、動態內容擷取的場景，例如自動化測試、競品價格監控、跨網站資料彙整等，比傳統 GUI 截圖驅動方式更穩定且成本更低。

3. **CAD 設計輔助與批次處理**：在 FreeCAD、OpenSCAD 等開源 CAD 環境中，透過 Python CLI 工具直接操作幾何模型，適用於參數化設計、模型變體生成、設計驗證等需要精確視覺理解與程式化操作的場景。

4. **長時程研究與開發助理**：例如自動化撰寫並執行測試、跨多個檔案系統進行重構、批次處理程式碼審查等需要持久化工作區與工具累積的任務。檔案系統作為外部狀態可讓代理在多次會話間累積自製工具。

5. **雲端基礎設施管理**：透過 SSH 終端機操作遠端伺服器，執行系統管理、部署、監控等任務。終端機原生介面與雲端環境的 CLI 工具（如 `kubectl`、`terraform`、`aws-cli`）天然契合。

### 實作前置條件

**模型需求**：
- 需具備強健程式碼生成能力的基礎模型（如 GPT-5.5/5.6、Claude Opus 4.6+ 等前沿模型），這是終端機介面能發揮效益的前提。模型必須能正確撰寫並除錯 Bash、Python 指令。
- 支援長上下文視窗（建議 128K tokens 以上），因為終端機輸出會累積在歷史中。

**運算資源**：
- 執行環境需為 Linux 桌面或容器（建議 Ubuntu 22.04+），預先安裝目標應用程式（如 LibreOffice、瀏覽器、FreeCAD）。
- 需安裝 `xdotool`、`pyautogui` 等鍵鼠自動化工具作為 GUI 操作的 fallback。
- 建議配備 GPU 推論資源或 API 金鑰（OpenAI、Anthropic 等），並準備成本監控機制。

**技能需求**：
- 熟悉 Linux 終端機操作、Bash 腳本撰寫、Python 程式設計。
- 理解 CDP（Chrome DevTools Protocol）以便整合網頁自動化。
- 具備基本的代理系統設計概念（MDP、觀察-動作循環）。
- 對目標領域應用程式（瀏覽器、CAD、Office 等）的 CLI 介面有一定掌握。

**資料準備**：
- 準備評估基準（如 OSWorld 2.0、Online-Mind2Web、Odysseys、CADGenBench、BenchCAD、WeaveBench）以驗證效能。
- 蒐集目標任務的範例與成功軌跡，用於提示工程與錯誤分析。

### 實作步驟建議

**階段一：核心執行框架建置（2-4 週）**
1. 參考 CUAWright 開源程式碼（約 3K 行），建立最小可行版本：終端機動作介面、觀察回傳機制、回合管理迴圈。
2. 設計檔案系統工作區結構：區分任務上下文、代理自製工具、持久化狀態三個目錄。
3. 實作「按需視覺」機制：提供 `screenshot.py` 與 `load_image.py` 兩個 CLI 工具，讓代理主動決定何時擷取與載入影像。

**階段二：環境與工具整合（3-6 週）**
4. 為目標領域（網頁、桌面、CAD）預先安裝並測試 CLI 工具鏈。
5. 整合 CDP 驅動的瀏覽器自動化模組，撰寫 Python 工具封裝常見網頁操作。
6. 為 GUI 不可繞過的場景保留 `xdotool`/`pyautogui` fallback 路徑。

**階段三：代理迴圈與提示工程（2-4 週）**
7. 設計系統提示詞，明確告知代理：動作空間為終端機指令、視覺需主動請求、可在檔案系統中建立並重用工具。
8. 實作回合歷史管理：保留終端機輸出、壓縮冗餘資訊、控制上下文長度。
9. 加入錯誤恢復機制：指令失敗時提供明確錯誤訊息，鼓勵代理自我除錯。

**階段四：評估與迭代（持續）**
10. 在標準基準上評估，比較與 GUI 原生執行框架的效能差距與成本差異。
11. 進行消融實驗：單代理 vs 多代理、有無檔案系統工作區、視覺預設 vs 按需。
12. 分析代理自製工具的軌跡，萃取出可預先提供的工具清單，優化提示詞。

**階段五：產品化（4-8 週）**
13. 包裝為可部署服務，加入任務佇列、並行執行、成本追蹤、稽核日誌。
14. 建立安全沙箱：限制可執行的指令範圍、隔離檔案系統、加入人為審核節點。
15. 設計使用者介面：讓使用者能提交任務、檢視代理軌跡、介入關鍵決策。

### 潛在風險與注意事項

**安全性風險**：
- **風險**：終端機介面具備完整系統存取權，惡意或錯誤的指令可能造成資料損毀、權限外洩。
- **緩解**：在容器或 VM 沙箱中執行；採用白名單機制限制危險指令（如 `rm -rf`、`dd`）；關鍵操作前要求人為確認。

**成本失控風險**：
- **風險**：代理可能陷入除錯迴圈，反覆執行失敗指令導致 token 消耗暴增。
- **緩解**：設定每任務最大回合數與預算上限；實作早期停止條件；監控單步成本並設置告警閾值。

**視覺理解不足風險**：
- **風險**：當任務高度依賴視覺判斷（如複雜 CAD 模型的細節調整）時，按需視覺可能錯過關鍵畫面。
- **緩解**：在提示詞中明確教導代理何時該主動擷取螢幕；對視覺密集任務預設較高的截圖頻率。

**模型能力依賴風險**：
- **風險**：終端機介面高度依賴模型的程式碼能力，較弱的模型可能無法有效操作。
- **緩解**：為弱模型設計更結構化的指令模板；提供領域專用的 Python 工具降低編寫複雜度；建立模型能力評估流程。

**確定性與可重現性風險**：
- **風險**：終端機輸出含時間戳、隨機 ID 等非確定性資訊，干擾代理判斷。
- **緩解**：在環境層標準化輸出格式；過濾非必要資訊；提供可重現的測試環境。

**工具膨脹風險**：
- **風險**：代理在工作區中累積過多自製工具，導致後續選擇困難。
- **緩解**：定期清理未使用的工具；提供工具索引與描述機制；限制單任務工具數量上限。

### 與其他技術的整合建議

**與既有 RPA 平台整合**：可將 CUAWright 作為進階代理層，處理傳統 RPA（UiPath、Power Automate）難以應對的非結構化任務；透過 CLI 呼叫既有 RPA 機器人執行結構化部分。

**與 LLM 框架整合**：可基於 LangChain、AutoGen 等框架包裝 CUAWright 的終端機動作為自訂工具；或將 CUAWright 整合進多代理系統，作為「執行者」角色搭配規劃者、審查者代理。

**與 CI/CD 流程整合**：將 CUAWright 部署於 CI 環境，用於自動化測試、文件生成、跨系統資料同步；透過 webhook 觸發任務並回傳結果至 Jira、GitHub 等系統。

**與企業知識庫整合**：代理可從內部文件、API 規範、Confluence 等擷取操作指南，作為終端機指令的補充上下文；任務完成後將成功軌跡回寫至知識庫供後續參考。

**與監控與可觀測性平台整合**：整合 OpenTelemetry、LangSmith 等工具，追蹤代理的每一步動作、token 消耗、成功率；建立儀表板監控生產環境的代理效能。

**與 GUI 代理混合部署**：對於確實需要 GUI 操作的場景（如某些封閉應用程式），可讓 CUAWright 透過 `xdotool` 呼叫 GUI 代理，形成「CLI 為主、GUI 為輔」的混合架構。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「為什麼終端機介面比 GUI 介面更適合代理」這個核心論點；接著跳到圖 1 的基準比較結果，直觀感受 CUAWright 的效能優勢；最後閱讀第 2 節的「Vision on demand」與「Persistent workspace」兩個設計理念，掌握「最小介面」與「外部狀態」這兩個關鍵概念即可，無需深入數學形式化。

**給 AI 工程師**：重點閱讀第 2 節的形式化定義與「Persistent workspace as external state」段落，理解如何將檔案系統設計為代理的外部記憶體；仔細研究圖 2 的架構圖，掌握終端機動作介面、觀察回傳、視覺按需載入的實作細節；接著閱讀消融實驗部分，理解單代理 vs 多代理、檔案系統的必要性等設計取捨；最後建議直接閱讀開源程式碼，從最小可執行版本開始重現並改造。

**給研究者**：重點關注第 1 節對 GUI 原生、混合 CLI、終端機原生三種執行框架的分類與批判，這是本文的核心貢獻；深入分析基準實驗的設計，特別是 OSWorld 2.0、Odysseys 等長時程任務的評估方式；關注消融實驗中揭示的「emergent behaviors」——代理自製工具的現象，這對理解代理能力邊界與工具學習研究有重要啟發；可進一步探索的方向包括：不同模型在終端機介面下的能力差異、工具重用機制、與規劃演算法的結合等。

**給產品經理**：重點閱讀摘要中的量化成果（OSWorld 2.0 提升 33.2%、成本降低 37.5%、Odysseys 提升 44.0%），這些數字是評估商業價值的關鍵；理解 CUAWright 的「最小介面」哲學如何轉化為實際的成本與維護優勢；評估自身產品場景中哪些任務適合採用終端機代理、哪些仍需 GUI 介面；關注「潛在風險」章節中的安全性與成本失控問題，這是產品化時必須正視的議題；建議從內部工具自動化或後台批次任務等低風險場景開始試點，逐步擴展至面向使用者的場景。
