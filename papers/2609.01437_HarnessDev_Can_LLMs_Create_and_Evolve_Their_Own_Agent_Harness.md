# HarnessDev：大型語言模型能否創建並演化自己的智能體執行架構？

## ⚡ TL;DR

現有評估多聚焦固定執行架構下的任務表現，忽略模型自行開發執行架構的能力。
本文提出 HarnessDev 基準，透過創建與演化兩階段評估可執行的智能體執行架構。
自建架構在寫作與機器學習實驗可超越人類設計，但在程式碼、搜尋與研究落後，演化增益不穩且難跨模型泛化。

## 摘要翻譯

隨著智能體（agent）從研究原型邁向實際部署工具，其能力日益仰賴模型外部的執行基礎設施（execution infrastructure），通常稱為智能體執行架構（agent harness）。在模型權重（model weights）固定的前提下，改變此執行架構可能大幅改變任務表現。現有的智能體評估通常報告在選定執行架構下的下游任務表現（downstream performance），使得模型自行開發執行架構的能力相對未被充分探索。本研究提出 HarnessDev，一個將評估單位（unit of evaluation）從任務輸出轉移到可執行基礎設施（runnable infrastructure）的基準測試（benchmark）。HarnessDev 包含兩個階段。在創建階段（Creation），智能體從最小種子（minimal seed）與少量案例出發，建構完整的執行系統。在演化階段（Evolution），智能體從自身創建的執行架構出發，利用下游執行回饋（downstream execution feedback）迭代修訂，目標為提升基準測試表現。我們接著根據能力（capability，以保留測試基準（held-out benchmarks）上的任務成功率（task success）衡量）與效率（efficiency，以執行 token 成本（execution-token cost）衡量）評估每個建構出的執行架構。創建階段結果涵蓋六個作為創建者（creator）的大型語言模型（LLM / Large Language Model）、四個領域，以及五個下游基準測試（downstream benchmarks），共計 2,207 個獨特的下游實例（downstream instances），並將隱藏評估任務（hidden evaluation tasks）保留於開發階段、不予開放。我們發現，在程式碼、搜尋與研究等領域，生成的執行架構仍明顯落後於成熟的人工設計參考執行架構；而在寫作與機器學習實驗方面則達到或超越所選的人工設計參考架構，但執行 token 成本差異顯著。演化階段產生若干表現提升，但這些提升不穩定，且僅部分遷移至保留任務（held-out tasks）。以固定執行模型（runtime model）進行的實驗進一步顯示，這些提升高度依賴執行該執行架構的模型，顯示跨模型遷移（transfer across models）能力有限。

### 核心貢獻（3～5點）
- 提出 HarnessDev 基準測試，將評估單位從任務輸出轉移至可執行的智能體執行架構（agent harness），填補現有評估對模型自行開發 harness 能力探索的缺口。
- 設計 Creation 與 Evolution 兩階段：Creation 讓模型從最小種子建構完整執行系統；Evolution 則利用下游執行回饋迭代修訂 harness。
- 建立兼顧能力（capability，保留測試基準上的任務成功率）與效率（efficiency，執行 token 成本）的雙重評估指標，並納入隱藏評估任務以檢驗泛化性。
- 大規模實證：涵蓋六個 creator LLM、四個領域、五個下游基準測試與 2,207 個獨特下游實例，發現生成 harness 在寫作與機器學習實驗可匹敵或超越人工參考，但在程式碼與搜尋研究仍落後。
- 揭示演化提升的不穩定性與有限遷移性：對保留任務僅部分遷移，且高度依賴執行 harness 的模型，跨模型遷移能力有限。

### 適合對象
適合對智能體（agent）系統設計、大型語言模型評估、自動化程式生成與元認知（meta-cognition）研究感興趣的研究人員與工程師，特別是關注 harness 設計、執行基礎設施效率，以及模型能否自我改進其外部執行架構的讀者。

## 深度分析

#### 方法論解析

HarnessDev 的核心貢獻在於將評估單位（unit of evaluation）從「單一任務輸出」轉移到「可執行的基礎設施（runnable infrastructure）」，也就是 Agent harness（智能體執行架構）。這個架構包含執行迴圈（execution loop）、工具使用（tool use）、上下文管理（context）、故障恢復（failure recovery）與結果驗證（result verification）等元件。傳統評測通常固定 harness，只比較不同模型權重（model weights）在下游基準測試（downstream benchmarks）上的表現；HarnessDev 則反過來，把 harness 本身當成被評估的產物，並區分「開發 harness 的模型」與「執行 harness 的模型」，從而檢驗大型語言模型（LLM，Large Language Model）能否擔任系統工程師的角色。

整個基準分為兩個階段：

1. **Creation（創建階段）**：Creator LLM 從一個刻意設計得脆弱但可執行的最小種子（minimal seed）出發，並僅使用少量開發案例，逐步建構出能處理整個任務家族的完整執行系統。這個階段模擬的是「從零開始打造 harness」的需求，挑戰模型對工具編排、迴圈控制、錯誤處理與記憶體壓縮等系統層級設計的理解。

2. **Evolution（演化階段）**：Creator LLM 從自己在 Creation 階段產生的 harness 出發，根據下游執行回饋（downstream execution feedback）持續迭代修訂。與一次性程式碼編輯不同，Evolution 要求模型辨識自身行為限制、診斷結構瓶頸，並做出能累積成長期、可重複使用的能力提升，而非僅是針對單一任務的權宜之計。

為了避免 harness 過度擬合（overfit）到開發案例或開發模型，HarnessDev 採用兩條評估軸線：

- **Capability（能力）**：將凍結後的 harness 部署在保留測試基準（held-out benchmarks）與隱藏評估任務（hidden evaluation tasks）上，計算任務成功率（task success）。隱藏任務在開發過程中完全不可見，用以檢驗通用性與遷移能力。
- **Efficiency（效率）**：測量 harness 在實際執行時所消耗的執行 token 成本（execution-token cost）。這讓評估不只看「能不能做對」，也看「做得貴不貴」。

此外，實驗設計還引入「固定執行模型（fixed runtime model）」的對照：同一個演化後的 harness 由不同執行模型（runtime model）來跑，以觀察 harness 的增益是否來自於開發模型與執行模型之間的默契，還是真的具備跨模型遷移（transfer across models）的結構性價值。

#### 實驗數據解讀

根據文中揭露的 Creation 結果，六個 creator LLM 橫跨四個領域、五個下游基準測試，共計 2,207 個獨立的下游實例（downstream instances）。整體發現可歸納為以下幾點：

**領域差異顯著，人類工程參考仍具優勢**
- 在程式碼（code）以及搜尋與研究（search and research）領域，模型自動生成的 harness 與成熟的人類工程參考（human-engineered references）之間仍有明顯差距。這可能反映這兩個領域需要更精細的錯誤處理、長程規劃與對外部工具語義的深層理解。
- 在短篇寫作（short-form writing）上，模型生成的 harness 已能與參考系統匹敵。
- 在機器學習實驗（machine-learning experimentation）上，模型 harness 甚至超過所選的參考系統。這暗示當任務回饋相對明確、實驗流程可透過反覆試誤收斂時，LLM 較容易設計出有效的執行架構。

**執行成本差異大**
- 不同 creator 產生的 harness 在 execution-token cost 上呈現高度變異。某些 harness 可能透過更激進的上下文壓縮（context compaction）或子代理（subagents）來降低成本，另一些則可能因過度呼叫工具或冗餘驗證而昂貴。這凸顯 capability 與 efficiency 之間存在權衡，未來的 harness 設計需要納入成本意識。

**Evolution 的增益不穩定且遷移有限**
- Evolution 階段確實能帶來部分性能提升，但這些提升不穩定，且對隱藏任務（held-out tasks）的遷移僅是部分有效。這表示模型在根據下游回饋調整 harness 時，容易落入「對可見回饋過度擬合」的陷阱，產生只對特定錯誤模式有效的局部修補。
- 固定執行模型實驗進一步顯示，harness 的增益強烈依賴於實際執行它的模型。換句話說，一個由模型 A 開發並針對模型 A 微調的 harness，換到模型 B 執行時效果會打折。這指出目前自動生成的 harness 仍帶有濃厚的「開發者—執行者耦合」特性，距離真正通用、可跨模型遷移的執行架構還有一段距離。

綜合來看，實驗數據描繪出一幅「局部可行、整體仍脆弱」的圖像：LLM 已經能夠把一個弱種子擴展成功能性的 harness，但在需要深度推理、長期穩定與跨模型泛化的場景上，仍遜於人類設計的成熟系統。

#### 與現有研究的比較

**相對於傳統 Agent 評測**
傳統評測如 SWE-bench、GAIA、WebArena、τ-bench 等，通常選定一個固定 harness 後比較不同 LLM 的下游任務表現（downstream performance）。這種做法適合控制變因、比較模型權重，但把 harness 視為實驗配置的一部分，而非可被開發與迭代的產物。HarnessDev 填補了這個缺口，把「可執行基礎設施」本身變成評估對象，並同時檢視能力、效率、遷移性與迴歸風險。

**相對於自動化 Agent 設計與 harness 表示學習**
近期研究已開始探討 harness 表示、自動化 agent 設計，以及能夠建構或改進 agent 系統的模型。然而，這些工作大多聚焦於一次性設計或搜尋最佳提示／工具組合。HarnessDev 的獨特之處在於強調「持續開發（development）」的雙階段：Creation 對應從零建構，Evolution 對應長期維護。這更接近真實部署情境，因為生產級 harness 需要隨著需求變化而不斷演進，而非只做一次。

**主要改進**
1. **分離 creator 與 runtime model**：避免把「模型會寫 harness」與「模型會用 harness」混為一談，能更精確衡量 harness 作為獨立產物的價值。
2. **隱藏評估任務與 held-out benchmarks**：降低開發階段記憶案例或過度擬合的風險。
3. **效率指標**：引入 execution-token cost，讓 harness 的實用性不只看準確率，也看部署成本。
4. **持久化與可檢視性**：每個版本都必須是凍結、可執行且經過測試的，這強調 harness 是長期存在的軟體工件。

**限制**
- 從目前可得的摘要與引言來看，HarnessDev 涵蓋的領域與基準仍屬有限，是否能推廣到更廣泛的任務類型（例如多模態、即時協作、安全關鍵系統）尚待驗證。
- Execution-token cost 雖然是重要指標，但並未完全涵蓋延遲、記憶體佔用、API 呼叫次數或實際牆上時間（wall-clock time）等部署成本。
- Evolution 的不穩定性顯示，目前尚缺乏可靠的自動驗證機制來防止迴歸（regression）：一個改動可能提升某項能力，卻同時損害另一項能力。
- 由於 harness 的表現與執行模型高度耦合，現有結果可能難以直接比較不同 creator LLM 的「絕對」harness 設計能力。

#### 可重現性評估

根據文中提供的資訊，HarnessDev 設有專案頁面（Project Page: https://self-developing-agents.github.io/），但摘要與引言並未明確說明原始碼、資料集、開發紀錄或評估腳本是否完全開源。從可重現性（reproducibility）的角度來看，有以下幾點值得注意：

- **資料與隱藏任務**：為了防止過度擬合，隱藏評估任務（hidden evaluation tasks）在開發階段被保留。這雖然是合理的設計，但也意味著外部研究者若無法取得這些隱藏任務，就難以完全複製官方數字或進行公平比較。
- **模型權重與 API**：實驗涉及六個 creator LLM 與多個執行模型，其中許多可能是商業 API（如 GPT 系列）或尚未公開權重的模型。這會讓結果對 API 版本、溫度參數（temperature）、呼叫方式等細節高度敏感。
- **開發環境紀錄**：HarnessDev 強調記錄開發環境，這對重現至關重要。若未來能釋出完整的容器化環境、seed harness、開發案例與版本控制紀錄，將大幅提升可重現性。
- **評估指標實作**：Capability 與 efficiency 的計算方式（例如 task success 的判定標準、token 計算範圍）需要詳細文件，否則不同團隊可能得出不同結論。

總體而言，專案頁面的存在是正向訊號，但目前仍缺乏足夠資訊判斷其開源程度。建議作者群釋出原始碼、資料分割方式、執行環境配置與詳細的超參數，以符合頂尖 AI 基準測試對可重現性的期待。

#### 未來研究方向

HarnessDev 揭示的現象為後續研究開啟了多條值得探索的路徑：

1. **穩定的 Evolution 演算法**
   現有 Evolution 增益不穩定，未來可研究結合形式化驗證、單元測試生成與迴歸偵測的演化框架，讓 harness 在迭代過程中維持既有能力不被破壞。

2. **跨模型遷移的 harness 設計**
   既然 harness 增益高度依賴執行模型，未來可探索「模型無關」的 harness 表示法，例如透過中間抽象層或標準化工具介面，降低開發模型與執行模型之間的耦合。

3. **成本感知的能力最佳化**
   將 execution-token cost 納入多目標最佳化，發展能同時提升 capability 與 efficiency 的 harness 搜尋或學習演算法，例如以強化學習或神經架構搜尋（NAS）的精神來設計 agent 架構。

4. **模組化與可組合 harness**
   將 harness 拆解為可獨立開發、測試與替換的模組（例如規劃模組、記憶模組、驗證模組），讓 LLM 能針對特定瓶頸進行局部改進，並透過組合現有參考模組加速收斂。

5. **Harness 作為版本化軟體工件**
   建立 harness 的版本控制、差異比較與升級機制，讓 agent 能夠像人類工程師一樣管理長期演化的程式碼庫，並支援協作式開發。

6. **多智能體 harness 開發**
   讓多個專精不同領域的 LLM 分別負責設計、測試、審查與最佳化 harness，透過協作降低單一模型的盲點。

7. **領域專用的 harness 語言**
   針對程式碼、研究、寫作、機器學習實驗等不同領域，設計更高階的領域專用語言（DSL）或規範，讓 LLM 在更有結構的空間中搜尋 harness 設計。

8. **安全性與對齊**
   當 LLM 能夠修改自己的執行架構時，也帶來自我修改與目標偏移的風險。未來需要研究如何確保 harness 演化過程符合人類意圖，並避免產生難以預測的執行行為。

9. **Scaling law 與 harness 複雜度**
   探討隨著模型規模、運算預算與開發輪數增加，harness 能力與效率是否呈現可預測的 scaling 規律，以及是否存在「湧現」的系統設計能力。

10. **與人類工程師的協作介面**
    發展能讓 LLM 提出 harness 改進建議、由人類審查後合併的混合式工作流程，在短期內可能比完全自動化更務實，也能累積高品質的 harness 開發資料。

## 論文問答

**Q1：HarnessDev 主要想解決什麼問題？**

A：HarnessDev 旨在填補現有評估框架中對「大型語言模型能否自行開發並持續維護智能體執行架構」這一能力的評量缺口。隨著智能體從研究原型走向實際部署工具，其表現越來越仰賴模型權重之外的執行基礎設施，也就是智能體執行架構；然而現有評測通常只報告在固定執行架構下的下游任務表現，忽略了模型本身作為「系統構建者」的潛能。因此，本研究將評估單位從單次任務輸出轉移到可執行、可重複使用的基礎設施，以檢驗模型能否從頭打造並不斷演化執行架構。

**Q2：現有的智能體評估方法為何無法衡量執行架構的開發能力？**

A：現有方法大多選定一個固定的智能體執行架構後，再比較不同模型在下游基準測試上的任務成功率，這種做法把執行架構視為實驗設定的一部分，而非被評估的產出物。這類評測無法區分「開發執行架構的模型」與「實際執行任務的模型」，也無法觀察到架構在不同執行模型之間的遷移性、穩定性或成本效益。更重要的是，它們評估的是一次性答案，而非可持續運行、可檢視、可重複使用的可執行基礎設施，因此難以反映真實部署場景中對執行架構長期維護的需求。

**Q3：為什麼智能體執行架構的開發能力如此重要？**

A：智能體執行架構負責管理執行迴圈、工具使用、上下文、故障恢復與結果驗證，是將模型輸出轉化為實際行動的關鍵層；研究顯示，在模型權重固定的情況下，僅改變執行架構就可能顯著改變任務表現，例如 GPT-5 在 Terminal-Bench 2.1 中於 Terminus 2 內達到 35.2%，但在 Codex CLI 內則達到 49.6%。隨著智能體逐漸專精於不同領域，對專用執行架構的需求只會持續增加，而這些系統需要持續開發與維護，而非一次性實作。因此，評估模型是否能協助甚至接手執行架構工程，對於降低部署成本與加速智能體落地具有重要意義。

**Q4：HarnessDev 的核心方法包含哪些階段？**

A：HarnessDev 包含創建階段與演化階段兩個核心階段。在創建階段中，創建者大型語言模型從一個刻意設計得較弱但可執行的最小種子出發，並根據少量案例建構出完整的執行系統；在演化階段中，模型則從自己先前創建的執行架構開始，根據下游執行回饋反覆修訂，以提升在基準測試上的表現。這兩個階段共同評估模型是否能完成從無到有的架構建構，並持續維護與改進可執行的基礎設施。

**Q5：HarnessDev 相較於過去研究有哪些關鍵創新？**

A：HarnessDev 最大的創新在於將評估單位從傳統的任務輸出轉移到「可執行的基礎設施」，也就是直接評量模型產出的執行架構本身。它明確區分了開發執行架構的創建者模型與實際執行下游任務的執行模型，並同時從能力與效率兩個維度進行評估：能力以保留測試基準上的任務成功率衡量，效率則以執行 token 成本衡量。此外，透過隱藏評估任務與跨模型執行實驗，本研究能夠檢驗執行架構是否過度擬合開發案例、是否發生能力迴歸，以及是否具備跨模型遷移性。

**Q6：HarnessDev 在實驗設計上做了哪些重要選擇？**

A：研究團隊刻意使用較弱但可執行的最小種子作為起點，避免直接給出完整解答，從而測試模型從頭建構執行架構的能力。開發任務對模型可見，但隱藏評估任務會被保留起來，用於檢驗產出架構的泛化能力與是否過度擬合。每一個演化版本都會被凍結、執行並測試，以確保評估的是真實可運行的基礎設施，而非僅存在於提示中的概念設計。

**Q7：HarnessDev 的實驗涵蓋哪些模型、領域與基準測試？**

A：創建階段的結果涵蓋六個創建者大型語言模型、四個領域與五個下游基準測試，總計 2,207 個獨特的下游實例。領域包括程式碼、搜尋與研究、寫作，以及機器學習實驗；使用的下游基準測試包含 SWE-bench、GAIA、WebArena 與 τ-bench 等。這些測試中還包含開發過程中未開放給模型的隱藏評估任務，用以檢驗執行架構的泛化與遷移能力。

**Q8：HarnessDev 的主要實驗結果是什麼？**

A：研究發現，模型生成的執行架構在不同領域的表現差異很大：在程式碼與搜尋研究領域，它們仍明顯落後於成熟的人類工程參考架構；但在寫作與機器學習實驗領域，則能達到與參考架構相當甚至超越的水準。此外，不同架構之間的執行 token 成本存在極大差異，顯示能力與效率之間並非簡單正相關。演化階段雖然能帶來一些性能提升，但這些提升並不穩定，且僅能部分遷移到保留測試任務上。

**Q9：研究中有哪些重要的消融實驗或額外分析？**

A：研究團隊進行了固定執行模型的實驗，結果顯示演化帶來的性能提升強烈依賴於實際執行該執行架構的模型，這代表跨模型遷移性仍然有限。這項發現指出，執行架構可能會過度擬合到創建它的模型或執行它的模型上，而無法在不同模型間穩定發揮相同效果。這也凸顯了在評估執行架構時，必須將創建者模型與執行模型分開檢驗，才能避免高估架構的通用性。

**Q10：HarnessDev 的研究成果可應用在哪些實務場景？**

A：這項研究可應用於讓大型語言模型協助執行架構工程師，甚至自動化部分執行架構的開發工作，特別是在需要為新領域快速打造專用智能體時。例如，企業可以讓模型根據少量範例生成瀏覽器工作者、資料分析副駕駛或研究流程的初始執行架構，並在部署後持續根據執行回饋進行優化。這有助於降低從研究原型過渡到實際產品所需的人力與時間成本，加速智能體工具的普及。

**Q11：在產品化過程中需要考慮哪些因素？**

A：產品化時必須同時考量執行架構的能力與執行 token 成本，因為本研究發現兩者之間存在顯著差異，高能力不一定伴隨高效率。此外，演化階段帶來的提升不穩定，且可能無法轉移到隱藏任務或不同執行模型，因此需要建立穩定的驗證機制來避免迴歸。產品團隊也應明確決定最終部署時使用的執行模型，因為執行架構的表現會隨著執行模型而顯著變化。

**Q12：HarnessDev 對整個智能體研究領域可能帶來什麼影響？**

A：HarnessDev 將研究焦點從單純比較任務層級表現，拓展到基礎設施層級的評估，促使社群更重視「能夠建構系統的系統」。這種典範轉移可能推動更多關於自動化智能體設計、執行架構表示學習與自我改進機制的研究。長遠來看，若模型能可靠地開發與維護自己的執行架構，將大幅加速智能體在多元領域的部署與規模化。

**Q13：本研究承認哪些主要限制？**

A：研究坦承，目前模型生成的執行架構在程式碼與搜尋研究等複雜領域仍明顯落後於人類工程師打造的成熟參考架構。演化階段雖有進展，但提升不穩定，且對保留任務與不同執行模型的遷移性有限。此外，執行 token 成本的變異很大，顯示現有方法在效率與穩定性方面仍有顯著改進空間。

**Q14：哪些情況下模型生成的執行架構會失敗或表現不佳？**

A：在需要深度推理、長期規劃與多步驟驗證的程式碼與搜尋研究任務中，模型生成的執行架構最容易落後於人類參考架構。演化過程中也可能出現「只提升回饋集分數、卻無法泛化到隱藏評估任務」的過度擬合現象。另外，某些改進可能會在提升某項能力的同時，悄悄導致其他能力發生迴歸，這正是為何需要持續進行多維度評估的原因。

**Q15：未來研究可以朝哪些方向發展？**

A：未來研究可以著重提升執行架構的跨模型遷移性，讓同一套架構在不同執行模型上都能穩定發揮。也可以開發更穩定的演化演算法，減少性能波動並確保改進能持續累積到保留任務上。此外，擴展到更多領域、優化能力與執行 token 成本之間的權衡，以及探索讓模型透過元學習自動發現更優執行架構的方法，都是值得深入的方向。

## 實務應用指南

### 適用場景

1. **企業內部專用 Agent 的執行架構開發**  
   當公司需要把通用大型語言模型封裝成具備記憶體、工具呼叫、錯誤恢復與結果驗證的內部 Agent（例如客服、財務報表分析、法規查詢）時，可利用 Creation 階段從最小種子與少量案例自動生成可執行的 智能體執行架構，再透過 Evolution 階段依據實際下游任務回饋持續調整。

2. **研究或資料分析流程自動化**  
   對於需要反覆搜尋、整理文獻、執行實驗腳本並驗證結果的研究流程，可讓模型自行建構研究管線的執行架構。特別適合機器學習實驗場景，因為論文發現模型生成的 harness 在 ML 實驗上可達到甚至超過成熟人工程式。

3. **程式編寫助手與終端機 Agent 的 harness 迭代**  
   開發者工具（如 CLI coding assistant、SWE-bench 類型的修 bug Agent）可受益於自動化 harness 開發，但需特別注意：論文顯示程式碼與搜尋研究類 harness 與人工程式仍有明顯差距，因此適合做為輔助起點而非完全替代。

4. **多模型部署環境的 harness 移植評估**  
   若組織計畫在不同執行模型之間共用同一套 智能體執行架構，HarnessDev 的評估框架可用來檢驗跨模型遷移效果，避免某個模型開發的 harness 只在特定模型上表現良好。

5. **成本敏感場景的 Agent 效率優化**  
   當執行 token 成本是主要考量（例如高頻呼叫的客服或資料處理 Agent），可透過 HarnessDev 的效率指標比較不同 harness 版本，選擇能力與成本的最佳平衡點。

### 實作前置條件

- **資料準備**
  - 每個目標領域需要一組「最小種子」程式碼：可執行但功能極弱，僅包含基本輸入輸出或簡單迴圈。
  - 少量開發案例（development cases）與對應的期望行為說明，供 Creation 階段學習。
  - 獨立的 保留測試基準 與 隱藏評估任務，用於客觀衡量 harness 的下游任務表現與泛化能力。

- **運算資源**
  - 能夠反覆執行 harness 的 sandbox 或容器環境，因為 Creation 與 Evolution 都需要實際跑下游任務並收集執行軌跡。
  - 足夠的 LLM API 預算：除了開發 harness 的 creator LLM，還需要執行模型反覆測試，並記錄 執行 token 成本。
  - 版本控制與回歸測試機制：每個 harness 版本都必須是凍結、可執行且可測試的。

- **技能與團隊配置**
  - 熟悉 Agent 系統設計的工程師，能判斷 harness 的結構瓶頸。
  - 具備領域知識的審查者，用於檢驗生成 harness 是否過度擬合開發案例。
  - 維運人員負責 sandbox 安全、工具權限管理與成本監控。

### 實作步驟建議

1. **定義評估單位與目標**  
   把評估單位從「單題答案」轉為「可執行基礎設施」。明確要優化的兩個軸：能力（保留測試基準上的任務成功率）與效率（執行 token 成本）。

2. **建立最小種子與開發案例**  
   為目標領域撰寫一個刻意簡化但可執行的 seed，並準備少量具代表性的開發案例。種子應包含最基本的執行迴圈，但缺少工具使用、上下文管理、故障恢復等進階機制。

3. **執行 Creation：讓 creator LLM 建構完整 harness**  
   讓 creator LLM 根據種子與開發案例，逐步加入工具呼叫、記憶體管理、驗證邏輯等。產出必須是凍結、可執行、可重複測試的程式碼。

4. **在保留基準上驗證能力**  
   將生成的 harness 在開發時未見過的下游基準測試上執行，記錄任務成功率。同時與成熟人工程式比較，找出明顯落後的領域。

5. **執行 Evolution：依下游回饋迭代修訂**  
   讓同一個或不同的 creator LLM 根據執行軌跡與失敗案例，持續修改 harness。每次修改後都要重新跑保留測試與隱藏評估任務，確認沒有回歸。

6. **進行跨模型與成本評估**  
   用不同的執行模型跑同一套 harness，檢驗跨模型遷移效果。同時監控每個版本的 執行 token 成本，避免能力微幅提升卻帶來成本暴增。

7. **部署與持續維護**  
   將通過驗證的 harness 版本納入正式部署，並建立持續監控機制：當下游任務分佈改變或執行模型更新時，重新觸發 Evolution。

### 潛在風險與注意事項

- **過度擬合開發案例**  
  模型可能只針對少數開發案例做特化調整，導致在隱藏評估任務上表現不佳。  
  **緩解方式**：保留足夠多且多樣化的隱藏評估任務，並把泛化能力列為主要評估指標。

- **能力進步但某處悄悄回歸**  
  Evolution 可能提升某類任務表現，卻降低另一類任務表現。  
  **緩解方式**：每次迭代都執行完整的回歸測試，並比較所有下游基準測試的任務成功率。

- **跨模型遷移有限**  
  論文顯示 harness 的增益強烈依賴執行它的模型。  
  **緩解方式**：若計畫更換執行模型，必須重新評估並可能重新進行 Evolution。

- **執行 token 成本暴增**  
  自動生成的 harness 可能加入過多工具呼叫、重試或子 Agent，導致成本大幅上升。  
  **緩解方式**：把效率與能力並列為停止條件，設定單次任務的成本上限。

- **程式碼與搜尋研究類 harness 仍落後人工程式**  
  在這些領域，模型自動生成的 harness 與成熟參考實作仍有顯著差距。  
  **緩解方式**：將自動生成結果視為初稿，由工程師進行關鍵結構審查與補強。

- **安全性與權限控管**  
  harness 會實際執行工具與程式碼，自動生成過程可能引入未預期的權限濫用。  
  **緩解方式**：在隔離 sandbox 中開發與測試，嚴格限制工具權限，並進行安全審查。

### 與其他技術的整合建議

- **與現有 Agent 框架整合**  
  可將 HarnessDev 的評估流程套用在 LangChain、AutoGen、OpenAI Agents SDK 等框架上，把框架預設的執行架構當作「最小種子」，再讓 LLM 進行客製化擴充。

- **與持續整合／持續部署（CI/CD）整合**  
  把 harness 的 Creation 與 Evolution 納入 CI pipeline：每次提交都自動跑保留測試基準、檢查任務成功率與執行 token 成本，並阻擋回歸版本進入生產環境。

- **與可觀測性工具整合**  
  串接執行軌跡記錄與分析工具，幫助模型在 Evolution 階段從真實失敗案例診斷結構瓶頸，而非僅憑靜態程式碼猜測。

- **與模型評估平台整合**  
  將 HarnessDev 的能力與效率指標納入現有模型評估儀表板，與其他任務級基準並列，讓團隊同時追蹤「模型本身」與「執行架構」的進步。

- **與人機協作審查流程整合**  
  對於程式碼與搜尋研究類 harness，建議採用「模型生成 + 工程師審查」的混合模式，讓人類專注在關鍵結構決策，模型負責反覆迭代與測試。

### 給不同背景讀者的閱讀建議

**初學者**  
這篇論文討論的是「讓 AI 不只回答問題，還能自己打造與改進執行問題的系統」。如果你剛接觸 Agent，建議先理解「智能體執行架構」是什麼：它包含記憶體、工具、錯誤處理與驗證機制。接著把重點放在 Creation 與 Evolution 兩個階段的概念，以及為什麼要用「保留測試基準」來驗證，避免被大量技術細節淹沒。

**AI 工程師**  
對你來說，這份研究提供了一套可落地的開發與評估流程。請特別關注論文中 harness 的具體設計空間、如何從最小種子擴充到完整系統，以及 Evolution 階段的回饋迴路該如何實作。實務上最關鍵的提醒是：務必把「跨模型遷移」與「執行 token 成本」納入驗收標準，否則很容易產出只在特定模型或特定案例上有效的 harness。

**研究人員**  
HarnessDev 把評估單位從任務輸出轉移到可執行基礎設施，這是一個值得深入探討的方法論轉變。建議關注其實驗設計如何分離 creator LLM 與執行模型、如何設計隱藏評估任務，以及 Evolution 增益不穩定與跨模型遷移有限的現象。這些發現對未來自動化 Agent 設計、自我改進系統與 meta-learning 研究都有重要啟發。

**產品經理**  
這篇論文的核心商業意涵是：AI Agent 的競爭力不只取決於模型權重，還取決於「執行架構」的品質。對你而言，重點在於理解哪些場景適合讓模型自動開發 harness（如寫作、機器學習實驗），哪些場景仍需要人工程式介入（如程式碼、搜尋研究）。同時要把成本與穩定性納入產品規劃，避免過度樂觀地將自動化 harness 視為萬靈丹。
