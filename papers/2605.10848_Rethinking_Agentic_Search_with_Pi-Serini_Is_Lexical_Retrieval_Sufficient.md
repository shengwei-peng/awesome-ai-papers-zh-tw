## 摘要翻譯

隨著大型語言模型（LLMs）在智能體循環（Agentic Loop）中變得更加強大，詞彙檢索器（Lexical Retriever）是否足夠？此問題在構建深度研究（Deep Research）系統時自然浮現。我們將 BM25 與具有更佳推理（Reasoning）與工具使用能力（Tool-use Ability）的前沿大型語言模型（Frontier LLMs）配對，重新審視此問題。為協助提出相同問題的研究者，我們推出 Pi-Serini——一個配備三種工具（用於檢索、瀏覽與閱讀文件）的搜索智能體（Search Agent）。我們的結果顯示，在 BrowseComp-Plus 上，配置良好且具備足夠檢索深度（Retrieval Depth）的詞彙檢索器，在與更強大的大型語言模型配對時，能夠支援有效的深度研究。具體而言，配備 gpt-5.5 的 Pi-Serini 達到 83.1% 的答案準確率（Answer Accuracy）與 94.7% 的浮現證據召回率（Surfaced Evidence Recall），超越了使用稠密檢索器（Dense Retriever）的已發布搜索智能體。受控消融實驗（Controlled Ablations）進一步顯示，相較於預設 BM25 設置，BM25 調參（BM25 Tuning）將答案準確率提升 18.0%，浮現證據召回率提升 11.1%；而相較於淺層檢索（Shallow Retrieval）設置，增加檢索深度進一步將浮現證據召回率提升 25.3%。原始碼可於 https://github.com/justram/pi-serini 取得。

### 核心貢獻（3～5點）
- 提出 Pi-Serini 搜索智能體，配備檢索、瀏覽、閱讀三項工具，為研究者提供可重現且易於擴展的實驗平台。
- 證明在 BrowseComp-Plus 基準上，配置良好的詞彙檢索器搭配前沿大型語言模型即可支援有效的深度研究，挑戰「必須使用稠密檢索器」的既有假設。
- 配備 gpt-5.5 的 Pi-Serini 達到 83.1% 答案準確率與 94.7% 浮現證據召回率，超越使用稠密檢索器的已發布搜索智能體。
- 透過受控消融實驗量化各項設計選擇的增益：BM25 調參使答案準確率提升 18.0%、浮現證據召回率提升 11.1%；增加檢索深度使浮現證據召回率再提升 25.3%。

### 適合對象
從事檢索增強生成（RAG）、深度研究系統、智能體搜索與信息檢索研究的學者與工程師；以及關注大型語言模型推理與工具使用能力、詞彙檢索器在現代智能體系統中角色定位的研究者。

## 深度分析

#### 方法論解析

本文提出 Pi-Serini 系統，其方法論核心在於**重新審視詞彙檢索器在智能體循環中的角色**，並透過系統化的設計將「檢索器能力」與「系統配置」分離開來進行獨立評估。

**整體架構設計**

Pi-Serini 採用 ReAct（Reasoning + Acting）循環框架，由兩個主要組件構成：

1. **LLM 智能體（LLM Agent）**：負責推理與決策，運行 ReAct 循環
2. **檢索控制器（Retrieval Controller）**：作為中介層，管理所有對 ANSERINI BM25 後端的訪問

這種分離設計的關鍵在於**檢索控制器作為隔離點**，它暴露受限的工具 API（constrained tool API）、維護檢索緩存排序（cached ranking），並控制檢索證據如何進入智能體上下文。

**三工具介面設計**

Pi-Serini 配備三個搜索相關工具，使文件檢索、結果瀏覽、文件閱讀成為**獨立的決策步驟**：

| 工具 | 功能 |
|------|------|
| `search` | 執行 BM25 檢索，獲取排序結果 |
| `read_search_results` | 瀏覽檢索結果列表（metadata） |
| `read_document` | 讀取完整文件內容 |

這種設計的精妙之處在於：透過 LLM 的工具使用能力，智能體可以**緩存檢索排序**、**探索更深層的檢索結果**，並**決定哪些證據進入上下文窗口**。這解決了 LLM 上下文窗口受限的核心問題——並非所有檢索結果都需要進入昂貴的 LLM 上下文。

**時間預算引導（Time-Budget Steering）**

與先前研究使用固定迭代次數上限（fixed iteration cap）不同，Pi-Serini 採用**牆鐘時間預算**（wall-clock time budget）作為終止條件。這更貼近真實的深度研究工作負載，因為：
- 深度研究本質上具有時間敏感性
- 需要平衡答案品質與延遲、成本約束
- 固定迭代次數無法反映實際部署中的資源限制

**前綴緩存友好設計（Prefix-Cache-Friendly）**

Pi-Serini 的智能體循環設計使得許多重複的輸入 token 可以從緩存中讀取，使**前綴緩存（prefix caching）成為成本效率的核心**。結合 BM25 調參和時間預算，這些設計共同實現了顯著的成本節省。

**方法論的關鍵洞見**

本文最重要的方法論貢獻在於**分離變量**的思路：將 BM25 的「詞彙檢索能力」與「配置選擇」和「檢索深度」分開評估。這使得作者能夠回答一個更精確的問題——先前 BM25 表現不佳，究竟是因為詞彙檢索本身的限制，還是因為配置不當或檢索深度不足？

#### 實驗數據解讀

**主要實驗結果**

在 BrowseComp-Plus 基準測試上，Pi-Serini 搭配 gpt-5.5 達到了：
- **答案準確率（Answer Accuracy）**：83.1%
- **浮現證據召回率（Surfaced Evidence Recall）**：94.7%

這兩個指標的含義需要仔細理解：
- **答案準確率**衡量最終答案的正確性
- **浮現證據召回率**衡量系統是否能夠「浮現」出回答問題所需的證據，這是一個更細粒度的指標

值得注意的是，Pi-Serini **超越了使用稠密檢索器的已發布搜索智能體**，這直接挑戰了「稠密檢索器必然優於詞彙檢索器」的傳統觀點。

**消融實驗分析**

| 配置變更 | 答案準確率提升 | 浮現證據召回率提升 |
|----------|---------------|-------------------|
| BM25 調參 vs. 默認 BM25 | +18.0% | +11.1% |
| 增加檢索深度 vs. 淺層檢索 | — | +25.3% |

這些數據揭示了幾個重要現象：

1. **BM25 調參的顯著影響**：18.0% 的準確率提升說明先前許多 BM25 基線表現不佳，很大程度上是因為**配置不當**而非詞彙檢索本身的限制。

2. **檢索深度的關鍵作用**：25.3% 的證據召回率提升表明，在智能體循環中，**讓 LLM 能夠探索更深層的檢索結果**比淺層檢索更為重要。這支持了「檢索深度是詞彙檢索在智能體設置中成功的關鍵因素」的觀點。

3. **準確率與召回率的非對稱性**：增加檢索深度主要提升召回率而非準確率，這暗示了**證據的可及性**與**證據的有效利用**之間存在差距。

**成本效益分析**

圖 1 展示了準確率與成本的權衡關係，Pi-Serini 系統（無論搭配 DeepSeek、OpenAI 還是 Anthropic 的模型）都位於**帕累托前沿的效率區域**。具體而言：
- 評估成本降低 **3.3×–10×**
- 這來自於 BM25 調參、時間預算控制、前綴緩存友好的循環設計三者的綜合效果

**實驗設計的侷限性**

需要指出的是，實驗僅在 BrowseComp-Plus 這一個基準上進行。雖然該基準提供了固定語料庫的受控比較環境，但單一基準的結果可能無法完全推廣到所有深度研究場景。

#### 與現有研究的比較

**定位於研究譜系中**

本文處於**深度研究系統**與**檢索器設計**兩個研究方向的交叉點：

1. **相對於 RAG 系統**：傳統 RAG（Lewis et al., 2020）僅執行單步檢索，而深度研究需要迭代搜索、文件檢查、跨源證據合成。Pi-Serini 屬於後者。

2. **相對於推理增強檢索器**：近期工作（如 Zhang et al., 2025; Shao et al., 2025; Chen et al., 2026）致力於開發能夠推理複雜查詢的檢索器。Pi-Serini 的立場是：**與其讓檢索器變得更聰明，不如讓 LLM 在智能體循環中更有效地使用簡單的檢索器**。

3. **相對於 SAGE 等分析工作**：SAGE（Hu et al., 2026）研究基於 LLM 的檢索器的有效性；Sharifymoghaddam 和 Lin（2026）、Meng et al.（2026）研究重排序和文件排序對搜索智能體的影響。然而，這些工作**未能分離 BM25 的詞彙檢索能力與周邊設計選擇**。Pi-Serini 正是填補了這一空白。

**相對於基準測試的演進**

- **BrowseComp**（Wei et al., 2025）和 **BrowseComp-ZH**（Zhou et al., 2025）：評估開放網路瀏覽能力
- **BrowseComp-Plus**（Chen et al., 2025）：提供固定語料庫設置，用於搜索智能體的受控比較

Pi-Serini 選擇 BrowseComp-Plus 是合理的，因為它允許隔離檢索器變量，避免開放網路帶來的混雜因素。

**改進與侷限性**

**改進**：
- 證明了詞彙檢索在智能體設置中的可行性
- 提供了顯著的成本效益
- 方法論上的「分離變量」思路具有示範價值

**侷限性**：
1. **基準單一性**：僅在 BrowseComp-Plus 上驗證，需要更多基準來確認結論的普適性
2. **語言模型依賴**：高度依賴前沿 LLM 的推理和工具使用能力，這意味著結論可能隨 LLM 能力變化而改變
3. **BM25 的固有限制**：對於需要深層語義理解的查詢，BM25 仍然可能不足；本文未深入探討詞彙檢索的失敗模式
4. **時間預算的設定**：未詳細討論如何為不同任務設定合適的時間預算

## 論文問答

**Q1：這篇論文試圖回答的核心問題是什麼？**
A：論文的核心問題是：隨著大型語言模型（LLM）在智能體循環（agentic loop）中的推理與工具使用能力日益增強，詞彙檢索器（lexical retriever，例如 BM25）是否仍足以支撐深度研究（deep research）系統？作者指出，過去文獻普遍將檢索器效能視為資訊檢索系統的「硬天花板」，因此傾向投入資源開發更強的稠密檢索器（dense retriever）或推理感知檢索器。然而，當 LLM 本身已具備強大的工具使用與多步推理能力時，檢索器的角色與其在整體系統中的相對重要性需要被重新檢視。這個問題若未被釐清，研究界可能會持續過度強調檢索器改進，而忽略其他同樣關鍵的設計選擇。

**Q2：為什麼過去基於 BM25 的詞彙檢索在深度研究系統中表現不佳？**
A：根據本文的分析，過去 BM25 在端到端任務中表現較差，往往不是因為詞彙檢索本身的語意匹配能力不足，而是因為「周邊設計選擇」不當所致。具體而言，預設的 BM25 參數設置（parameter setting）並未針對任務進行調校，且檢索深度（retrieval depth）過淺，導致相關文件在送入 LLM 之前就被丟棄。作者透過消融實驗證明，僅僅是 BM25 調參（BM25 tuning）就能將答案準確率提升 18.0%、浮現證據召回率提升 11.1%，這顯示過去的「BM25 弱勢」很大程度是配置問題而非本質缺陷。

**Q3：為什麼這個問題在當前特別重要？**
A：這個問題的重要性來自於 LLM 能力的典範轉移——當前沿 LLM（frontier LLM）已能在智能體循環中自主推理、規劃並使用工具時，傳統「檢索器決定一切」的假設需要被重新審視。若詞彙檢索在良好配置下已足夠，則研究資源可重新分配到工具介面設計、時間預算控制、快取管理等其他被低估的環節。此外，深度研究本質上具有時間敏感性，使用者在意的不只是品質，還有延遲與成本；若 BM25 方案能在維持品質的同時大幅降低成本，將對實際部署產生深遠影響。

**Q4：Pi-Serini 的核心架構與設計理念是什麼？**
A：Pi-Serini 是一個刻意設計為「極簡」的搜索智能體（search agent），其核心架構由 LLM 智能體執行的 ReAct 循環與一個檢索控制器（retrieval controller）組成，後者中介所有對 Anserini BM25 後端的存取。這個檢索控制器是主要的隔離點，它暴露受限的工具 API、維護緩存排序（cached ranking），並控制檢索證據如何進入智能體的上下文窗口（context window）。這種設計理念是「將文件檢索、結果瀏覽、文件閱讀區分為獨立決策」，讓 LLM 能根據自身推理決定何時深入挖掘、何時將證據納入上下文。

**Q5：Pi-Serini 提供哪三個工具？為什麼要將它們區分開來？**
A：Pi-Serini 提供三個工具：search（搜索）、read_search_results（讀取搜索結果）以及 read_document（讀取文件）。將這三個動作區分為獨立工具，是因為 LLM 經常受限於有限的上下文窗口，需要一個介面來幫助它提取對後續動作有用的資訊。透過這種分離，Pi-Serini 能夠緩存檢索排序、探索更深的檢索結果，並決定哪些證據最終進入上下文，從而避免寶貴的上下文空間被低價值的初步結果佔據。這種設計也讓「檢索」與「閱讀」的成本與效益能被清楚區分與管理。

**Q6：Pi-Serini 在成本效率上做了哪些關鍵設計選擇？**
A：Pi-Serini 在成本效率上做了三項關鍵設計選擇：第一，採用時間預算引導（time-budget steering）取代過去文獻中常見的固定迭代次數上限，讓智能體能在硬性時鐘時間預算內自行決定何時終止；第二，其智能體循環對前綴快取（prefix cache）友善，許多重複的輸入詞元可從快取中提供，使前綴快取成為成本效率的核心；第三，BM25 調參與時間預算設計本身也帶來額外的成本節省。整體而言，這些設計使 Pi-Serini 在 BrowseComp-Plus 上將評估成本降低了 3.3 倍至 10 倍。

**Q7：為什麼選擇 BrowseComp-Plus 作為評測基準？**
A：BrowseComp-Plus 是一個固定語料庫（fixed-corpus）的設定，能夠對搜索智能體進行受控比較，這對於隔離檢索器與智能體互動的效應至關重要。相較於開放網路瀏覽的基準（如 BrowseComp 或 BrowseComp-ZH），固定語料庫設定排除了網路變動、網站結構差異等干擾因素，讓研究者能更精準地歸因效能差異的來源。此外，BrowseComp-Plus 將檢索與證據互動置於智能體表現的核心位置，這正好契合本文想釐清的問題——究竟有多少觀察到的效能差異真正來自檢索模型本身。

**Q8：Pi-Serini 的主要實驗結果為何？**
A：在 BrowseComp-Plus 上，Pi-Serini 搭配 gpt-5.5 達到了 83.1% 的答案準確率（answer accuracy）與 94.7% 的浮現證據召回率（surfaced evidence recall），超越了使用稠密檢索器的已釋出搜索智能體。從圖 1 的準確率—成本權衡曲線可看出，Pi-Serini 系列系統（涵蓋 DeepSeek、OpenAI、Anthropic 等不同 LLM 後端）一致地落在帕累托前沿（Pareto frontier）的高效區域。這意味著在品質與成本的雙重考量下，BM25 搭配良好設計的智能體介面，比稠密檢索器方案更具競爭力。

**Q9：消融實驗揭示了哪些關鍵發現？**
A：受控消融實驗（controlled ablation）揭示了兩個關鍵發現：第一，BM25 調參相較於預設 BM25 設置，能將答案準確率提升 18.0%、浮現證據召回率提升 11.1%，證明參數調校對詞彙檢索的影響遠比想像中大；第二，將檢索深度從淺層提升至深層，可進一步將浮現證據召回率提升 25.3%，顯示「相關文件是否被檢索到」與「檢索深度是否足夠」之間存在顯著關聯。這兩個發現共同支持了本文的核心論點：詞彙檢索的弱勢主要來自配置與深度，而非檢索範式本身的限制。

**Q10：Pi-Serini 的設計適用於哪些實際應用場景？**
A：Pi-Serini 的設計特別適用於需要深度研究且對成本敏感的場景，例如企業內部知識庫問答、學術文獻綜述、法律案件研究以及新聞事實查核等任務。這些場景的共同特徵是：需要從大量文件中提取並整合證據、對回答品質有高要求、但同時面臨預算或回應時間的限制。此外，由於 BM25 不需要昂貴的嵌入模型運算，Pi-Serini 也適合部署在資源受限的環境，例如邊緣裝置或中小型組織，使其無需依賴大型稠密檢索基礎設施即可建構高品質的問答系統。

**Q11：將 Pi-Serini 概念產品化時需要考量哪些因素？**
A：產品化時需考量以下因素：首先，BM25 雖然成本低，但需要針對特定語料庫進行調參，這在跨領域部署時會增加維護成本；其次，時間預算引導機制需要仔細設計，過短的預算會犧牲品質，過長則失去成本優勢；第三，前綴快取的效益高度依賴查詢與工作流程的重複模式，對於高度多樣化的工作負載，快取命中率可能下降；最後，雖然 Pi-Serini 介面極簡，但實際使用者可能期望更豐富的功能（如多模態支援、引用追蹤），這需要在簡潔性與功能性之間取得平衡。

**Q12：這項研究對資訊檢索與深度研究領域的整體影響為何？**
A：這項研究的整體影響在於「重新校準」學界與業界對檢索器角色的認知——它挑戰了「必須使用稠密或推理感知檢索器才能做好深度研究」的隱含假設，並指出工具介面設計、時間預算控制、快取管理等「被低估的環節」同樣值得投入研究資源。從更宏觀的角度看，這也呼應了 Yang 等人（2019）對過度優化單一元件的警告，提醒研究者應以系統整體效能為目標，而非單獨追求某個元件的極致表現。此外，3.3 倍至 10 倍的成本降低對深度研究的普及化具有實質意義，可能讓更多組織與個人能負擔得起高品質的研究助理系統。

**Q13：本文承認哪些研究限制？**
A：本文的限制主要來自評測設定的範圍：所有實驗均在 BrowseComp-Plus 上進行，這是一個固定語料庫的基準，雖然有利於受控比較，但未必能完全反映開放網路環境的複雜性。此外，論文中也提到部分先前工作的結果（如 Cao 等人，2026）是基於抽樣評估，僅供參考，這意味著跨論文的直接比較需謹慎解讀。最後，雖然 BM25 在本文設定下表現優異，但作者並未聲稱詞彙檢索在所有任務、所有領域都優於稠密檢索，結論的適用範圍仍受限於所測試的任務類型與語料特性。

**Q14：Pi-Serini 在哪些情境下可能會失敗？**
A：Pi-Serini 在以下情境可能會表現不佳：第一，當查詢需要深層語意理解（例如同義詞替換、隱含概念關聯）且 BM25 無法透過調參補償時，詞彙匹配的固有限制仍會顯現；第二，當相關證據分散在多個需要複雜推理鏈才能串連的文件時，即使檢索到所有相關文件，LLM 是否能正確整合仍取決於其推理能力；第三，對於極大規模或高度動態更新的語料庫，BM25 的索引更新成本與檢索效率可能成為瓶頸；第四，當使用者查詢極為模糊或需要多輪澄清時，極簡的工具介面可能不足以支援細緻的互動。

**Q15：基於本文的發現，未來有哪些值得探索的研究方向？**
A：基於本文發現，未來值得探索的方向包括：首先，將「檢索器配置與深度」與「智能體介面設計」解耦的研究框架可應用於其他檢索範式（如稠密、稀疏混合），檢驗是否存在類似的「被低估環節」；其次，可進一步研究如何自動學習 BM25 參數或動態調整檢索深度，使系統能適應不同任務特性；第三，前綴快取與時間預算的聯合最佳化是一個尚未充分探索的方向，可能進一步釋放成本效益；最後，將本文的「極簡介面」理念擴展到多模態檢索、跨語言檢索等場景，檢驗其結論的普適性，也是值得投入的研究路線。

## 實務應用指南

### 適用場景

1. **企業內部知識庫問答系統**：適用於員工需要查詢公司內部文件、技術手冊、政策法規等場景。透過 BM25 詞彙檢索搭配前沿 LLM，可在不依賴昂貴稠密嵌入模型的情況下，提供高準確率的內部知識問答服務。

2. **法律與合規文件檢索**：律師事務所或合規部門需要從大量法律條文、判例書、合約文件中查找特定資訊。BM25 對精確法律術語的匹配能力優於稠密檢索器，且成本僅為後者的十分之一。

3. **技術支援與故障排除**：IT 服務台或產品客服需要從技術文件、錯誤代碼資料庫中快速定位解決方案。Pi-Serini 的三層工具介面（搜尋、瀏覽、閱讀）能有效處理多步驟的故障排查流程。

4. **學術文獻深度研究**：研究人員需要從固定語料庫（如 arXiv、PubMed）中進行多輪文獻檢索與證據整合，特別適合需要高證據召回率（94.7%）的系統性文獻回顧。

5. **客戶支援聊天機器人升級**：將傳統 FAQ 系統升級為具備深度研究能力的對話式助手，在控制成本的同時維持高回應品質。

### 實作前置條件

**資料需求：**
- 結構化或半結構化的文件集合（建議至少數萬份文件以發揮 BM25 深度檢索的優勢）
- 文件需經預處理（分詞、標準化），BM25 對英文效果最佳，中文需搭配適當斷詞器（如 jieba）
- 需具備文件元資料（如標題、來源、日期）以輔助證據追蹤

**計算資源：**
- LLM API 存取權限（OpenAI GPT-5.5、Anthropic Claude Opus-4.7 或 DeepSeek 系列）
- Anserini BM25 索引建置環境（建議 16GB 以上 RAM，SSD 儲存）
- 支援 prefix caching 的推論服務以發揮成本效益

**技能需求：**
- 熟悉 Python 開發與 LLM API 整合
- 具備資訊檢索基礎概念（TF-IDF、倒排索引）
- 了解 ReAct 智能體循環與工具呼叫（tool-use）機制
- 具備 BM25 參數調校經驗（k1、b 參數）

### 實作步驟建議

**步驟一：環境建置與索引準備**
從 GitHub 取得 Pi-Serini 原始碼，安裝 Anserini 與必要依賴。將文件集合匯入並建立 BM25 倒排索引，建議預先進行文本標準化處理（小寫化、停用詞過濾、詞幹化）。

**步驟二：BM25 參數調校**
這是論文強調的關鍵步驟。預設 BM25 參數（k1=1.2, b=0.75）並非最佳選擇。建議在驗證集上進行網格搜尋，調整 k1（詞頻飽和度，通常 0.9–2.0）與 b（文件長度正規化，通常 0.3–0.9）。論文顯示此步驟可帶來 18.0% 的準確率提升。

**步驟三：設定檢索深度**
避免使用淺層檢索（top-10 或 top-25）。論文建議將檢索深度提升至數百甚至上千筆文件，讓 LLM 透過 `read_search_results` 工具主動探索更深層的結果。此步驟可額外提升 25.3% 的證據召回率。

**步驟四：實作三層工具介面**
依照論文設計實作三個核心工具：
- `search`：執行 BM25 查詢並緩存完整排序結果
- `read_search_results`：讓 LLM 瀏覽緩存中的特定範圍結果
- `read_document`：將選定文件的完整內容載入上下文窗口

**步驟五：整合 ReAct 智能體循環**
使用支援工具呼叫的前沿 LLM（如 gpt-5.5）驅動 ReAct 循環。設計清晰的系統提示詞，明確說明三個工具的使用時機與策略。

**步驟六：導入時間預算控制**
取代傳統的固定迭代次數上限，改用牆鐘時間預算（wall-clock time budget）。根據實際部署需求設定每個查詢的最大執行時間，讓系統在時間壓力下自動收斂。

**步驟七：優化 Prefix Caching**
設計智能體循環時，盡量保持系統提示詞與早期對話內容的穩定性，使多數輸入 token 可從快取提供。結合 BM25 調參與時間預算，整體可降低 3.3×–10× 的評估成本。

**步驟八：評估與迭代**
使用 BrowseComp-Plus 或自建評估集，衡量答案準確率與證據召回率。持續監控成本-準確率權衡曲線，確保系統落在帕累托前沿的效率區域。

### 潛在風險與注意事項

**風險一：BM25 的語意匹配限制**
BM25 對同義詞、詞形變化與跨語言查詢的處理能力有限。緩解方式：建立領域同義詞字典、搭配查詢擴展技術，或在關鍵場景輔以輕量級 reranker。

**風險二：檢索深度過深的延遲問題**
將檢索深度提升至數百筆文件會增加排序計算時間。緩解方式：使用 Anserini 的高效索引結構、設定合理的時間預算上限、預先計算常用查詢的排序結果。

**風險三：LLM 上下文窗口限制**
即使有工具介面，LLM 仍受限於上下文窗口大小。緩解方式：設計證據摘要機制、實作增量式文件閱讀、優先載入高相關性段落而非完整文件。

**風險四：時間預算的不可預測性**
牆鐘時間預算可能因系統負載而波動，導致結果不穩定。緩解方式：設定最小迭代次數下限、記錄時間消耗日誌、進行多次評估取平均。

**風險五：Prefix Caching 的失效情境**
當查詢差異過大或系統提示詞變動時，快取命中率會下降。緩解方式：標準化提示詞模板、批次處理相似查詢、監控快取命中率指標。

**風險六：評估基準的代表性**
BrowseComp-Plus 為固定語料庫設定，與真實開放網路環境有落差。緩解方式：在自家領域資料上建立評估集、進行小規模線上 A/B 測試。

### 與其他技術的整合建議

**給初學者**：建議先閱讀第 1 節的問題意識，理解「為什麼詞彙檢索在 LLM 時代仍值得重新審視」，再跳讀第 3 節了解 Pi-Serini 的三個工具如何運作。重點掌握「BM25 調參」與「檢索深度」這兩個非顯而易見但效果顯著的概念。

**給研究者**：論文的消融實驗設計值得深入分析——它清楚分離了「BM25 容量」與「配置選擇」對效能的貢獻，這是方法論上的重要示範。圖 1 的成本-準確率帕累托前沿提供了寶貴的基準比較資料。後續研究方向可考慮：BM25 與推理感知檢索器的理論比較、prefix caching 對智能體設計的更廣泛影響。

**給產品經理**：核心訊息是「在 LLM 能力足夠強時，昂貴的稠密檢索器未必必要」——這對成本敏感的產品具有重大意義。圖 1 顯示 Pi-Serini 在維持高準確率（83.1%）的同時，成本僅為稠密檢索方案的十分之一。建議評估自家產品的問答場景是否屬於「可由詞彙檢索覆蓋」的範疇，並將 BM25 調參與檢索深度列為優先優化項目，而非直接投入稠密檢索器的開發。
