## ⚡ TL;DR

現有 GUI 代理多在離線軌跡與模擬環境中訓練，與真實應用場景落差顯著。
本文提出 Xiaomi-GUI-0，以真機主導混合基礎設施搭配三階段漸進式訓練。
模型在 RealMobile 與 AndroidWorld 上分別達 72.0% 與 78.9% 成功率。

## 摘要翻譯

圖形使用者介面（GUI）代理基於視覺語言模型，透過點擊、滑動、文字輸入和導航等介面動作，在真實應用程式中端到端完成使用者任務。然而，現有的 GUI 代理主要在離線軌跡、模擬環境和標準化基準上進行訓練與評估。這些與真實應用程式在介面佈局、互動邏輯和異常狀態分佈方面存在顯著差異，無法忠實地刻畫真實世界使用中的執行穩定性。在真實世界中，帳號狀態、權限對話框、支付認證和風險控制不斷重塑狀態分佈，並在基準分數與真實可用性之間形成持續的落差。為彌合此落差，我們提出 Xiaomi-GUI-0，一個用於真實行動環境的原生多模態 GUI 代理，在真機閉環中進行訓練與評估。其核心是一個真機主導的混合基礎設施，其中實體裝置為主要執行環境，沙盒提供輔助支援，使資料收集、訓練、推論部署和評估共享接近真實部署的執行分佈。我們建構了多源訓練資料，涵蓋高頻頭部任務、用於長尾意圖的高泛化資料，以及用於反思和記憶的能力增強資料，並引入一個錯誤驅動的資料飛輪，將失敗軌跡轉化為修正動作、反思性解釋和恢復示範。該模型透過監督式微調、步級強化學習和代理式強化學習的漸進式三階段流程進行訓練。在公開基準和我們的內部基準 RealMobile 上評估，Xiaomi-GUI-0 在 RealMobile 上達到 72.0% 的成功率，在 AndroidWorld 上達到 78.9%，同時大幅提升了真實世界任務中的執行穩定性與異常狀態識別。

### 核心貢獻（3～5點）
- **真機閉環訓練與評估框架**：提出真機主導的混合基礎設施，以實體裝置為主要執行環境、沙盒為輔，使資料收集、訓練、推論部署與評估共享接近真實部署的執行分佈，彌合基準分數與真實可用性之間的落差。
- **多源訓練資料與錯誤驅動的資料飛輪**：建構涵蓋高頻頭部任務、長尾意圖高泛化資料，以及反思與記憶能力增強資料的多源訓練資料；並設計錯誤驅動的資料飛輪，將失敗軌跡轉化為修正動作、反思性解釋與恢復示範。
- **漸進式三階段訓練流程**：採用監督式微調（SFT）、步級強化學習與代理式強化學習的漸進式三階段流程，提升模型在真實行動環境中的執行穩定性與異常狀態識別能力。
- **優異的基準評測表現**：在內部基準 RealMobile 上達到 72.0% 成功率，在公開基準 AndroidWorld 上達到 78.9% 成功率，同時在真實世界任務中展現顯著優於既有方法的執行穩定性。

### 適合對象
從事 GUI 代理、視覺語言模型、行動智慧代理、多模態強化學習及人機互動研究的學者與工程師；同時適合關注大模型實際部署穩定性、真機測試基礎設施，以及 AI 代理在真實應用程式中落地應用的產業研發團隊與技術決策者閱讀。

## 深度分析

#### 方法論解析

Xiaomi-GUI-0 的方法論核心在於建立「真機閉環 (Real-Device Closed Loop)」，從根本上挑戰 GUI 代理領域長期依賴模擬環境的訓練與評估範式。其方法論可從基礎設施、資料建構、訓練流程三個層面進行深度解析。

**基礎設施層面：真機主導的混合架構 (Real-Device-Dominant Hybrid Infrastructure)**

傳統 GUI 代理訓練依賴 emulator（模擬器）或 sandbox（沙盒），但商業應用普遍部署 anti-emulator detection（反模擬器偵測）機制，使得支付認證、驗證碼、風險控制等關鍵異常狀態無法被系統性地收集與評估。Xiaomi-GUI-0 採用「真機為主、沙盒為輔」的混合架構，物理裝置作為主要執行環境，sandbox 提供輔助支援。此設計的核心洞見在於：資料收集、訓練、rollout（推論部署）與評估必須共享「接近真實部署 (Real Deployment)」的執行分佈 (Execution Distribution)，而非僅在模型開發完成後才考慮部署時的偶發狀況。該基礎設施涵蓋智慧型手機、平板，並延伸至車載座艙 (in-vehicle cockpit)，體現了對「消費終端多樣性」的考量。

**資料建構層面：多源異質資料與錯誤驅動飛輪**

資料建構是 Xiaomi-GUI-0 最具特色的環節，採用三類異質資料並結合錯誤驅動的資料飛輪 (Error-Driven Data Flywheel)：

1. **高頻頭部任務資料 (High-Frequency Head Task Data)**：針對使用者日常高頻操作（如通訊、支付、導航），確保模型在主流場景的執行穩定性 (Execution Stability)。

2. **高泛化資料 (High-Generalization Data)**：為解決長尾意圖 (Long-Tail Intent) 問題，採用「功能樹建構 (Function Tree Construction) → 查詢合成 (Query Synthesis) → 軌跡合成與清洗 (Trajectory Synthesis and Cleaning)」三步流程。功能樹將應用程式功能結構化分解，查詢合成基於功能節點生成多樣化使用者查詢，軌跡合成則在真機上執行並清洗低品質樣本。此設計借鑑了程式合成領域的思路，將應用功能視為可組合的語義單元。

3. **能力增強資料 (Agent-Capability Enhancement Data)**：專門針對反思 (Reflection) 與記憶 (Memory) 能力，這是 GUI 代理在長程任務中維持狀態一致性的關鍵。

4. **錯誤驅動資料飛輪 (Error-Driven Data Flywheel)**：此為最具創新性的設計。傳統訓練資料以「乾淨的成功軌跡」為主，模型對真實 rollout 中最常見的失敗模式缺乏暴露。飛輪機制將失敗軌跡 (Failure Trajectory) 轉化為三類監督信號：修正動作 (Corrected Action)、反思性解釋 (Reflective Explanation)、恢復示範 (Recovery Demonstration)。這實質上構建了一個自我完善的閉環：模型犯錯 → 錯誤被分析 → 修正資料回流 → 模型學會恢復。

**訓練流程層面：漸進式三階段管線 (Progressive Three-Stage Pipeline)**

訓練採用 SFT → 步級強化學習 (Step-Level RL) → 代理式強化學習 (Agentic RL) 的漸進式設計：

- **監督式微調 (Supervised Fine-Tuning, SFT)**：建立基礎動作預測與介面理解能力。
- **步級強化學習 (Step-Level RL)**：在單步動作層級進行優化，可能採用 GRPO 或類似演算法，獎勵正確的單步決策。
- **代理式強化學習 (Agentic RL)**：在完整軌跡層級進行優化，獎勵任務級成功率，培養長程規劃與異常恢復能力。

此三階段設計呼應了「從模仿到探索、從局部到全局」的學習範式：SFT 提供先驗，步級 RL 精細化動作選擇，代理式 RL 優化整體策略。

#### 實驗數據解讀

根據摘要揭露的關鍵數據：Xiaomi-GUI-0 在內部基準 RealMobile 上達到 72.0% 成功率，在公開基準 AndroidWorld 上達到 78.9% 成功率，並在真實世界任務中「實質性提升執行穩定性與異常狀態識別 (Abnormal-State Recognition)」。

**數據解讀的關鍵維度：**

1. **基準差異的意義**：RealMobile (72.0%) 與 AndroidWorld (78.9%) 的差距並非單純反映模型能力差異，而是反映兩個基準的「分佈特性」。AndroidWorld 作為公開基準，採用標準化任務與模擬環境，狀態分佈相對乾淨；RealMobile 作為內部基準，基於真實應用與真實異常狀態建構，更貼近部署場景。72.0% 在更困難的真實基準上仍屬強勁表現，說明模型在異常狀態識別上的泛化能力。

2. **「實質性提升」的相對意義**：摘要使用「substantially improving」描述執行穩定性與異常狀態識別的提升，但未提供具體的對比基準數據。從方法論推斷，這些提升主要來自錯誤驅動資料飛輪與代理式強化學習的結合——前者提供異常狀態的監督信號，後者獎勵恢復行為。

3. **評估協議的細粒度設計**：RealMobile 基準採用「細粒度評分 (Fine-Grained Scoring)」與「可執行驗證規則 (Executable Verification Rule)」，並配備自動評估流程 (Auto-Eval Pipeline)。這意味著評估不僅關注最終成功與否，還對中間步驟的正確性進行評分，這對 GUI 代理的可解釋性與除錯具有重要價值。

4. **基準建構的代表性**：RealMobile 涵蓋應用程式選擇 (Application Selection) 與任務建構 (Task Construction) 兩個維度，強調任務來源的多樣性（系統啟動器、中間應用頁面、異常狀態頁面、跨應用相似頁面），這直接對應於真實使用者的查詢分佈。

**實驗數據的侷限性：**

- 摘要未提供消融實驗 (ablation study) 數據，無法量化各模組（錯誤飛輪、三階段訓練、真機基礎設施）的獨立貢獻。
- 缺乏與 Mobile-Agent-v3.5、UI-TARS-2、UI-Venus-1.5 等同類模型在 RealMobile 上的直接對比數據。
- 「執行穩定性」的量化指標未明確披露，可能涉及任務完成步數、波動率或恢復成功率等指標。

#### 與現有研究的比較

**領域定位：**

Xiaomi-GUI-0 屬於「原生多模態 GUI 代理 (Native Multimodal GUI Agent)」範式，與 Mobile-Agent-v3.5、UI-TARS-2、UI-Venus-1.5 同屬基於視覺語言模型 (Vision-Language Model, VLM) 的端到端 (End-to-End) GUI 代理。與依賴 API 或 function calling 的代理相比，GUI 代理不需應用程式提供者暴露後端介面，原則上具有更廣泛的適用性。

**核心差異化優勢：**

1. **真機閉環 vs. 模擬環境**：現有 GUI 代理的訓練與評估「主要依賴離線軌跡、模擬環境與標準化基準」，而 Xiaomi-GUI-0 將真實裝置、真實應用、真實使用者請求、真實失敗狀態視為「訓練方法論的核心組成部分，而非部署時的偶發事件」。此差異化定位挑戰了領域內「benchmark 導向」的研發範式。

2. **錯誤驅動 vs. 成功軌跡導向**：現有訓練資料以「乾淨的成功軌跡」為主，雖然已有研究關注「修正導向監督 (correction-oriented supervision)」，但 Xiaomi-GUI-0 將錯誤驅動的資料飛輪系統化為閉環機制，這在領域內屬於較為激進的設計。

3. **三階段漸進訓練**：SFT → 步級 RL → 代理式 RL 的設計整合了模仿學習與強化學習的優勢，但此管線在 GUI 代理領域並非 Xiaomi-GUI-0 首創，其創新在於將此管線與真機基礎設施、錯誤飛輪深度耦合。

**相對局限性：**

1. **領域內已有類似工作**：UI-TARS-2 與 UI-Venus-1.5 等模型同樣基於 VLM 並採用強化學習訓練，Xiaomi-GUI-0 需在公開基準上展示更顯著的優勢才能確立領先地位。

2. **真機基礎設施的可擴展性**：真機為主的架構雖然提升了資料品質，但對硬體成本、運維複雜度、資料採集吞吐量提出更高要求，這可能限制方法的普及性。

3. **異常狀態的倫理與合規**：在真機上收集支付認證、風險控制等異常狀態資料涉及隱私與合規問題，論文中未充分討論資料收集的倫理框架。

4. **跨平台泛化**：雖然基礎設施涵蓋手機、平板、車載座艙，但模型在跨裝置類型、跨作業系統版本、跨應用版本上的泛化能力仍需驗證。

#### 可重現性評估

**可重現性要素分析：**

1. **模型權重 (Model Weights)**：根據技術報告的慣例與摘要內容，小米尚未明確宣布 Xiaomi-GUI-0 的開源計畫。考慮到該模型定位於小米內部產品生態，模型權重的開源可能性較低，可能僅透過 API 或授權方式提供。

2. **訓練資料 (Datasets)**：訓練資料涉及真實應用、真實使用者查詢、真實異常狀態，這些資料的開源面臨嚴峻的隱私與商業機密挑戰。功能樹建構、查詢合成、軌跡合成的「方法論」可能被開源，但具體資料集難以公開。

3. **程式碼 (Code)**：訓練管線（SFT、步級 RL、代理式 RL）、錯誤驅動資料飛輪的演算法、RealMobile 基準的評估協議等「方法論層面」的程式碼具有開源潛力，但真機基礎設施的硬體配置、自動化部署、異常狀態觸發機制等「工程層面」的程式碼難以完全重現。

4. **基準 (Benchmarks)**：RealMobile 作為內部基準 (In-House Benchmark)，其完整建構細節（應用程式選擇標準、任務建構流程、可執行驗證規則）若能公開，將對領域具有重要價值。AndroidWorld 為公開基準，可直接用於重現評估。

**可重現性的關鍵障礙：**

- **真機基礎設施的硬體依賴**：重現需要大量物理裝置、自動化控制系統、異常狀態觸發裝置，這對學術機構構成較高門檻。
- **商業應用的版本演進**：真實應用持續更新，導致資料與基準的「時效性衰減」，這是可重現性的根本挑戰。
- **異常狀態的稀有性**：驗證碼、支付認證、風險控制等異常狀態在真實環境中本就稀有，系統性收集需要特殊基礎設施。

**促進可重現性的建議：**

- 開源「方法論層面」的程式碼（訓練管線、評估協議、資料合成演算法）。
- 釋出「去識別化」的基準任務定義與驗證規則，使其他研究者可在自有裝置上重建基準。
- 提供「sandbox 適配版本」的訓練流程，使無真機基礎設施的研究者可進行近似重現。

#### 未來研究方向

**1. 真機閉環的理論化與形式化**

當前真機閉環主要作為「工程實踐」被提出，缺乏形式化的理論框架。未來研究可探索：
- 將「執行分佈 (Execution Distribution)」形式化為機率分佈，並量化「模擬環境分佈」與「真實部署分佈」的差異（例如透過 KL 散度或最大均值差異）。
- 建立「分佈偏移 (Distribution Shift)」下的 GUI 代理泛化理論，分析錯誤飛輪對分佈偏移的緩解機制。

**2. 錯誤驅動資料飛輪的演算法深化**

錯誤飛輪目前將失敗軌跡轉化為修正動作、反思性解釋、恢復示範三類信號，未來可探索：
- **失敗模式分類 (Failure Mode Taxonomy)**：系統化分類 GUI 代理的失敗模式（點擊錯誤、文字輸入錯誤、路徑選擇錯誤、終止決策錯誤），並針對不同模式設計專門的修正策略。
- **反思品質評估**：反思性解釋的品質如何評估？是否可透過反事實推理 (counterfactual reasoning) 驗證反思的正確性？
- **恢復策略的可遷移性**：恢復示範是否可跨應用、跨任務遷移？

**3. 異常狀態識別與處理的專門化**

異常狀態（驗證碼、支付認證、權限對話框）是 GUI 代理實用化的關鍵障礙。未來方向包括：
- **異常狀態偵測器 (Anomaly Detector)**：將異常狀態識別建模為獨立的視覺分類任務，並與主代理解耦。
- **異常狀態處理策略庫**：針對不同異常狀態設計專門的處理策略（如「等待使用者介入」、「請求權限」、「切換帳號」）。
- **異常狀態的合成生成**：在 sandbox 中主動合成異常狀態，以緩解真實異常狀態的稀有性問題。

**4. 評估協議的標準化與生態建構**

RealMobile 採用細粒度評分與可執行驗證規則，未來可推動：
- **領域共識的評估指標**：除成功率外，引入「步數效率」、「恢復成功率」、「異常狀態識別率」等多維指標。
- **跨平台、跨應用、跨版本的基準生態**：建立類似 ImageNet 的「GUI 代理基準生態」，涵蓋不同作業系統、不同應用類別、不同任務難度。
- **人機協作評估**：在真實使用場景中評估 GUI 代理與人類使用者的協作效率。

**5. 跨模態與跨裝置的擴展**

當前模型主要處理視覺與文字模態，未來可探索：

## 論文問答

**Q1：現有 GUI 代理在實際部署中面臨的核心問題是什麼？**
A：現有的 GUI 代理主要在離線軌跡、模擬環境與標準化基準上進行訓練與評估，導致其與真實應用環境之間存在根本性的落差。這些訓練與評估管線往往依賴簡化的模擬應用、受限的任務情境或模擬器環境，無法完整捕捉主流商業應用中的互動模式、系統行為與罕見邊緣案例。更關鍵的是，許多生產應用採用反模擬器偵測機制，使得驗證碼、支付認證、過期的登入狀態、風險控制介入與系統權限對話框等異常狀態難以被系統性地收集與評估，進而造成基準分數與真實可用性之間的持續落差。

**Q2：為何僅依靠公開基準無法反映 GUI 代理的真實能力？**
A：公開基準通常建立在乾淨的成功軌跡與靜態環境之上，無法反映真實部署中動態的狀態分佈變化。真實使用者查詢本質上具有更強的長尾性與情境敏感性，任務執行可能源自系統啟動器、中間應用頁面、異常狀態頁面，甚至是不同應用中語意相似的頁面，這些都會造成執行期間狀態分佈的偏移。此外，實際部署還必須應對持續演進的應用版本、非同步的頁面載入、動態的帳號狀態以及其他環境不確定性，使得僅憑基準分數無法可靠預測模型在真實世界中的可操作性。

**Q3：為何縮小基準分數與真實可用性之間的落差如此重要？**
A：行動 GUI 代理是運作於動態環境中的序列決策系統，模型所採取的每個動作都會改變後續的介面狀態，而點擊、文字輸入、路徑選擇或終止決策上的錯誤可能導致執行軌跡持續偏離預期的任務目標。當訓練資料仍以離線成功軌跡為主時，模型對於真實推論中最常出現的失敗模式缺乏足夠的曝光，導致錯誤識別、反思修正與狀態恢復等能力發展不足。因此，真機、真實應用、真實使用者請求與真實失敗狀態應被視為行動 GUI 代理訓練與評估方法論的核心組成部分，而非僅在模型開發完成後才處理的部署階段偶發事件。

**Q4：Xiaomi-GUI-0 的核心方法論是什麼？**
A：Xiaomi-GUI-0 的核心方法論是建立一個真機閉環（real-device closed loop），將真實裝置作為主要的執行環境，並以沙盒作為輔助支援，使資料收集、訓練、推論部署與評估共享接近真實部署的執行分佈。這個真機主導的混合基礎設施涵蓋智慧型手機、平板等行動裝置，並延伸至車載座艙，使模型能夠在多元的真實終端上進行訓練與評估。透過這種方式，模型從一開始就在真實的介面佈局、互動邏輯與異常狀態分佈中學習，而非僅在模擬環境中進行知識蒸餾。

**Q5：訓練資料建構上的關鍵創新為何？**
A：訓練資料建構上的關鍵創新在於採用多源訓練資料的設計，涵蓋高頻頭部任務資料、用於長尾意圖的高泛化資料，以及用於反思與記憶的能力增強資料。其中高泛化資料透過功能樹建構、查詢合成與軌跡合成及清洗等步驟產生，能夠系統性地覆蓋應用程式的功能空間並合成多樣化的使用者查詢。更具突破性的設計是錯誤驅動的資料飛輪（error-driven data flywheel），它將失敗軌跡轉化為修正動作、反思性解釋與恢復示範，使模型能夠從錯誤中學習並發展出真正的錯誤恢復能力，而非僅模仿成功軌跡。

**Q6：漸進式三階段訓練流程的設計考量為何？**

   - 錯誤驅動資料飛輪：將 rollout 失敗軌跡自動轉為修正動作、反思解釋、恢復示範，回灌訓練集。

3. **執行三階段漸進式訓練**：
   - 階段一：監督式微調（SFT），建立基礎動作生成與任務理解能力。
   - 階段二：步級強化學習（Step-Level RL），針對單步動作正確性進行細粒度優化。
   - 階段三：代理式強化學習（Agentic RL），以整體任務成功率作為獎勵，優化長程決策與異常狀態恢復能力。

4. **建構內部評測基準（RealMobile）**：挑選主流商業 App、涵蓋異常狀態任務、設計細粒度評分與可執行驗證規則，建立自動化評估流程，作為模型迭代的核心指標。

5. **部署與持續迭代**：將模型部署至真機農場，啟動資料飛輪持續蒐集新版本 App、新異常狀態的軌跡，定期重新訓練並以 RealMobile 與公開基準（如 AndroidWorld）雙軌驗證。

6. **產品化整合**：包裝為 SDK 或系統服務，與語音助理、客服系統、自動化測試平台等既有系統對接，並設計人工接管（human-in-the-loop）機制處理高風險動作（支付、刪除等）。

---

### 潛在風險與注意事項

- **真機資料蒐集的隱私與合規風險**：操作軌跡可能包含個資、支付資訊、對話內容，必須建立嚴格的脫敏、加密與存取控制機制，並符合各地隱私法規（如 GDPR、台灣個資法）。

- **App 版本漂移導致效能衰退**：商業 App 介面更新頻繁，模型可能在版本升級後效能驟降；需建立版本感知評測與快速再訓練流程，並設計 fallback 機制。

- **異常狀態覆蓋不足**：驗證碼、風控彈窗等場景高度動態且難以預測，僅靠蒐集難以窮舉；應結合合成資料、規則引擎與人工接管作為補充。

- **強化學習訓練不穩定**：代理式 RL 在長程任務中獎勵稀疏、方差大，可能出現訓練崩塌；建議採用保守的學習率、KL 約束、價值函數裁剪，並保留 SFT 模型作為安全錨點。

- **高風險動作的誤觸風險**：支付、刪除、發送等動作一旦誤觸可能造成不可逆損失；必須設計確認對話框、動作白名單、單次任務金額上限等防護機制。

- **真機農場的營運成本與穩定性**：數百台實體裝置的電力、網路、維護成本高昂，且裝置老化、系統更新會中斷實驗；需建構自動化健康檢查與任務排程系統。

- **基準分數與真實可用性的落差**：即便在 AndroidWorld 達到 78.9%，仍可能在特定 App 或特定異常狀態下失效；應以內部 RealMobile 為主要決策依據，並持續追蹤真實使用者回饋。

---

### 與其他技術的整合建議

- **與語音助理整合**：將 GUI 代理作為語音助理的「執行層」，由語音助理負責意圖理解與對話管理，GUI 代理負責跨 App 動作執行，可形成完整的「說→做」閉環。

- **與傳統 RPA／自動化測試整合**：將 GUI 代理作為高階任務規劃器，底層呼叫既有 Appium／uiautomator2 腳本處理穩定子流程，僅在動態決策點交由模型處理，可兼顧穩定性與彈性。

- **與 RAG／知識庫整合**：對於需要查詢特定政策、條款、使用者歷史的任務，可先透過 RAG 取得結構化資訊，再交由 GUI 代理執行操作，提升長尾任務成功率。

- **與多代理系統整合**：將 GUI 代理與規劃代理、反思代理、工具呼叫代理組成多代理系統，由規劃代理拆解任務、GUI 代理執行、反思代理檢查結果並決定是否重試或升級人工。

- **與裝置端小模型整合**：對於延遲敏感或離線場景，可將大模型蒸餾為裝置端小模型（如 3B–7B 參數），搭配雲端大模型處理複雜任務，形成雲端協同架構。

- **與可觀測性系統整合**：將每次 rollout 的螢幕、動作、反思、錯誤完整記錄至可觀測性平台（如 Langfuse、Phoenix），便於除錯、資料飛輪回挖與合規稽核。

---

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節了解 GUI 代理的基本概念與「為何需要真機閉環」的動機，再跳讀第 5 節的 RealMobile 基準介紹，理解一個完整的 GUI 代理評測是如何設計的；技術細節可先略過，重點掌握「模型＋真機＋資料飛輪」三者的關係。

**給 AI 工程師**：重點研讀第 3 節的訓練資料建構（特別是功能樹建構、查詢合成、錯誤驅動資料飛輪）與第 4 節的三階段訓練配方（SFT → 步級 RL → 代理式 RL），這些是將論文方法落地為自有系統的核心；同時參考第 2 節的混合基礎設施架構，規劃真機農場的工程實作。

**給研究者**：建議從第 1 節的「基準分數與真實可用性落差」問題陳述出發，深入閱讀第 3.4 節的錯誤驅動資料飛輪、第 4.3–4.4 節的步級與代理式強化學習設計，以及第 5 節的細粒度評分與可執行驗證規則，這些都是 GUI 代理領域尚未充分探索的研究方向。

**給產品經理**：聚焦於第 1 節的問題動機、第 5 節的 RealMobile 基準設計（理解「什麼是真實可用」），以及第 6 節的實驗結果（72.0% RealMobile、78.9% AndroidWorld）；重點思考如何將 GUI 代理包裝為使用者可感知的產品功能（例如「一句話完成跨 App 任務」），以及如何設計人工接管、風險防護等產品機制。
