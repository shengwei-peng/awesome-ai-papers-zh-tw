## ⚡ TL;DR

現有技能路由要麼塞滿上下文，要麼仰賴外部模型，難以兼顧規模與代理理解力。
Gavel 從凍結代理 LLM 的中層狀態，用兩個線性映射做瞥視與裁決，選出合適技能。
在 Qwen3-32B 上，Gavel 零樣本遷移至四個基準，領先數十億參數管線最多21.9分。

## 摘要翻譯

技能（skills）能讓大型語言模型代理（LLM agent）超越其參數化知識（parametric knowledge），而它們所帶來的增益取決於是否選對技能。已部署的代理框架（harness）通常將每個技能的中繼資料（metadata）預先載入上下文（context）以進行路由（routing），但這會分散代理的注意力（attention），也為庫大小（library size）設下上限（cap）。檢索管線（retrieval pipeline）雖將選擇（selection）移出上下文，卻也使其脫離了代理能力（agent capability）。我們證明，凍結的代理 LLM（frozen agent LLM）在其自身的前向傳遞（forward pass）中已攜帶路由訊號（routing signal），且僅需兩個線性映射（linear maps）即可在上下文中無任何技能文字的情況下將其讀出。Gavel（Glance And Verdict from a frozen LLM）分兩步讀取此訊號。瞥視（Glance）階段將任務與各技能的中層狀態（mid-layer states）透過這兩個線性映射（唯一訓練的參數）投影，並以安裝時單次前向傳遞所建立的緊湊的逐技能庫（compact per-skill banks）為基準，對整個庫評分。接著，判決（Verdict）階段則接續入圍技能（shortlisted skills）的前向傳遞，讀取模型自身的似然（likelihood）與是非判斷，並與瞥視以專家乘積（product of experts）方式融合。Gavel 只需訓練一次，即可零樣本遷移至三個公開基準測試（benchmarks），以及 SkillTraj——我們提出的 372 條模擬代理軌跡（simulated agent trajectories）新基準測試。在 Qwen3-32B 上，它優於漸進式揭露（progressive disclosure）與檢索後重排（retrieve-and-rerank）管線，這些管線額外增加 12 億至 160 億個外部參數（external parameters）；在書面任務（written tasks）上領先最多 13.4 分，而當技能需求於展開中期（mid-rollout）才浮現時，領先最多 21.9 分。路由準確率（routing accuracy）隨骨幹模型（backbone）提升而改善，且在 Bash 代理框架（Bash-agent harness）中，同樣的 32B 模型於 Skill-Use 上觸發正確技能的頻率，高於在 Codex 中執行、規模大得多的前沿模型（frontier models）。

### 核心貢獻（3～5點）
- 提出 Gavel，證明凍結的代理 LLM 在前向傳遞中已內建路由訊號，僅需兩個線性映射即可在無需技能文字進入上下文的情況下完成原生技能路由。
- 設計兩階段路由機制：瞥視（Glance）以緊湊的逐技能庫對全庫快速評分，判決（Verdict）則接續入圍技能的前向傳遞並讀取模型自身的似然與是非判斷，最後以專家乘積融合兩者。
- 建立 SkillTraj 新基準測試，包含 372 條模擬代理軌跡，並驗證 Gavel 在三個公開基準與 SkillTraj 上具備零樣本遷移能力。
- 在 Qwen3-32B 上，Gavel 優於額外增加 1.2B–16B 外部參數的漸進式揭露與檢索後重排管線，於書面任務領先最多 13.4 分，在展開中期才需技能的場景領先最多 21.9 分。
- 顯示路由準確率隨骨幹模型提升而改善，且 32B 模型在 Bash 代理框架中的 Skill-Use 表現可勝過 Codex 中規模大得多的前沿模型。

### 適合對象
適合對大型語言模型代理、工具使用、技能路由與檢索增強生成有興趣的研究者與工程師，特別是關注如何從凍結 LLM 中挖掘內在能力、減少外部參數與上下文負擔，以及需要評估代理在展開中期觸發正確技能機制的實務開發者。

## 深度分析

#### 方法論解析

##### 核心問題與設計動機
論文指出，現有技能路由（skill routing）主要採用兩條路徑：**漸進式揭露（progressive disclosure）** 與 **檢索後重排（retrieve-and-rerank）**。前者將所有技能的中繼資料（metadata）塞入上下文（context），導致注意力（attention）分散、庫大小（library size）受限；後者雖然保持上下文乾淨，卻把選擇權交給外部模型（external models），使其無法隨代理 LLM（agent LLM）的能力同步成長。Gavel（Glance And Verdict from a frozen LLM）提出第三條路：從**凍結的大型語言模型（Frozen LLM）** 自身的前向傳遞（forward pass）中讀取**路由訊號（routing signal）**，僅訓練兩個線性映射（linear map），在選定技能前不讓任何技能文本進入上下文。

##### 兩階段路由架構
Gavel 由兩個階段組成：**瞥視（glance）** 與 **裁決（verdict）**。

1. **瞥視（Glance）**
   - 在代理 LLM 的某個中層（mid-layer）取出隱藏狀態，透過一個 query map 投影任務（task）每個 token 的狀態，再透過一個 key map 投影每個技能（skill）各 token 的狀態。
   - 這相當於在凍結模型上「嫁接」一個新的注意力頭（attention head），但將完整的內積注意力分解為兩個線性映射，使訓練參數量極小（總共 7.9M）。
   - 每個任務 token 獨立對所有技能投票，避免決定性 token 被平均掉。
   - 技能在安裝時只需一次前向傳遞（forward pass）即可建立**緊湊的逐技能庫（compact per-skill banks）**；論文進一步用 𝜀-cover 對這些庫進行稀疏化，並保證失真有界。

2. **裁決（Verdict）**
   - 瞥視產生一個**入圍技能（shortlisted skills）** 清單後，裁決階段對每個入圍技能重新執行一次「安裝前向傳遞 + 任務文本」的完整前向傳遞。
   - 從這次完整前向傳遞中讀取兩個訊號：
     - **似然（likelihood）**：技能文本對任務的生成機率（generative evidence）。
     - **是／否判斷（yes/no judgment）**：模型對「此技能是否適用於此任務」的判別機率（discriminative evidence）。
   - 瞥視分數、似然、判斷三者都被視為同一個對數後驗 log P(skill | task)，因此可用 **專家乘積（product of experts）** 融合，結合對比式、生成式與判別式三種證據。

##### 訓練與推論成本
- 僅在 **SkillRet** 的合成查詢–技能對上以對比損失訓練兩個線性映射。
- 安裝新技能只需一次前向傳遞，無需重新訓練。
- 推論時，瞥視可對整個技能庫打分，成本低廉；裁決只對少數入圍技能執行完整前向傳遞，成本可控。

#### 實驗數據解讀

##### 評估場景
論文評估分為兩大類：

1. **書面任務（written tasks）**：三個公開基準測試（benchmark），與訓練資料 SkillRet 在查詢作者、文件類型與庫規模上皆有差異，用於測試零樣本遷移（zero-shot transfer）。
2. **展開中期（mid-rollout）需求**：論文自建 **SkillTraj**，包含 372 條模擬代理軌跡（simulated agent trajectories），在四種帶雜訊的多輪上下文情境下，評估路由器在「需求於軌跡中段浮現」時的準確率。

##### 主要結果
- 在 **SRA-Bench** 上，Gavel 比最強的檢索後重排管線（retrieve-and-rerank pipeline）高出 **13.4 點**。
- 在 SkillTraj 的四種情境中，領先幅度介於 **8.6 至 21.9 點**。
- 在 **Skill-Use** 的 Bash 代理框架（bash-agent harness）中，同樣使用 **Qwen3-32B** 作為骨幹模型（backbone）時，Gavel 觸發正確技能的頻率，甚至高於 Claude Code 與 Codex 中更大的前沿模型（frontier models）。

##### 結果意涵
- **規模不等於能力**：添加 1.2B 至 16B 外部參數（external parameters）的檢索管線，並未勝過僅 7.9M 訓練參數、直接從凍結 LLM 讀取訊號的 Gavel。這顯示「路由訊號已內建於代理 LLM 的前向傳遞中」，外部模型難以比模型自身更準確判斷任務需求。
- **中期需求更顯優勢**：當技能需求在展開中期（mid-rollout）出現、上下文充滿雜訊時，Gavel 的領先幅度（最高 21.9 點）大於書面任務。這呼應了論文主張：外部檢索器無法看到完整軌跡，而凍結 LLM 本身對當前狀態有更深理解。
- **骨幹模型進化可遷移**：論文觀察到路由準確率（routing accuracy）隨骨幹模型能力提升而提升，這是「原生技能路由（native skill routing）」相較於外部管線的結構性優勢。

##### 消融實驗
雖然文中未詳列所有數字，但提到消融實驗（ablations）證實瞥視與裁決兩階段各有貢獻：
- 僅有瞥視時，能對全庫快速篩選，但可能遺漏需要細緻推理的配對。
- 僅有裁決時，雖然精確但無法負擔全庫比對。
- 兩者以專家乘積（product of experts）融合後，互補效果最佳。

#### 與現有研究的比較

##### 相對於漸進式揭露（Progressive Disclosure）
Claude Code、Codex 等部署系統採用漸進式揭露，將所有技能名稱與描述預載入系統提示。其缺點包括：
- 中繼資料（metadata）隨庫大小線性佔用上下文視窗（context window）。
- Codex 甚至將技能中繼資料上限（cap）設為上下文視窗的 2%，其餘直接丟棄。
- 路由準確率（routing accuracy）隨技能數量增加而對數衰減。

Gavel 的改進：
- 選定前不放入任何技能文本，上下文（context）保持乾淨。
- 不受庫大小直接壓縮上下文，理論上可擴展到更大技能庫。
- 透過 token 級瞥視，避免「摘要遺失關鍵資訊」的問題。

##### 相對於檢索後重排（Retrieve-and-Rerank）
現有工具學習（tool learning）與技能路由研究常使用嵌入模型（embedding model）+ 重排器（reranker）的外部管線。其缺點包括：
- 選擇過程脫離代理 LLM，無法利用其對任務與技能的深層理解。
- 在雜訊多、需求於展開中期（mid-rollout）浮現的情境下表現較差。
- 外部模型不會隨代理 LLM 升級而自動變強。

Gavel 的改進：
- 所有訊號來自凍結 LLM 自身，路由能力隨骨幹模型（backbone）進步而提升。
- 在書面任務與中期需求情境均顯著領先，且參數量極小。
- 不需要額外的嵌入模型或重排器，部署架構更簡潔。

##### 相對於 ToolkenGPT 等凍結 LLM 工具方法
ToolkenGPT 讓凍結 LLM 將工具視為特殊 token 生成，但這類方法通常需要改變詞表或生成過程。Gavel 的差異在於：
- 不改動詞表或解碼流程，僅在 mid-layer 加入兩個線性映射讀取路由訊號。
- 透過「瞥視 + 裁決」兩階段，兼顧效率與精確度。

##### 限制
- **單一骨幹模型驗證**：論文主要使用 Qwen3-32B，雖然提到路由準確率隨骨幹提升，但未在其他系列（如 Llama、GPT 等）上給出完整數據。
- **訓練資料依賴合成查詢**：瞥視在 SkillRet 的合成查詢–技能對上訓練，對於極度偏離該分佈的真實任務，遷移能力仍需更多驗證。
- **裁決仍需多次前向傳遞**：雖然只對入圍技能執行，但相較於純檢索管線仍有額外計算成本。
- **安裝時的記憶體與儲存成本**：每個技能需建立並儲存緊湊狀態庫，超大規模技能庫的儲存與索引策略未深入討論。

#### 未來研究方向

##### 1. 跨骨幹模型與跨規模驗證
未來可在更多骨幹模型（backbone）上驗證 Gavel，例如 Llama-3、Mixtral、GPT-4o 等，並探討模型規模與路由準確率之間的縮放律（scaling law）。特別是驗證「路由能力隨代理 LLM 提升而提升」是否在不同架構上皆成立。

##### 2. 動態與持續學習技能庫
Gavel 安裝新技能只需一次前向傳遞，但未討論技能更新、版本控制與遺忘問題。未來可研究：
- 技能庫持續擴充時，線性映射是否需要定期微調。
- 新舊技能語義衝突時的解析策略。
- 長期記憶與技能庫的整合。

##### 3. 多技能組合與條件式路由
目前 Gavel 主要處理「選擇一個最適技能」。實際代理任務常需：
- 同時載入多個互補技能。
- 依序觸發技能（例如先查詢再執行）。
- 在條件分支中動態切換技能。

未來可將瞥視擴展為多標籤預測或序列決策問題。

##### 4. 與工具學習（Tool Learning）的統一框架
Gavel 的技能路由機制可視為工具學習的一個特例。未來可探討：
- 將 API、函式呼叫（function calling）、檔案讀取等統一視為「技能」。
- 讓凍結 LLM 同時進行工具發現、參數填充與路由決策。
- 結合 Gavel 的內部訊號與外部檢索，形成混合式路由器。

##### 5. 降低裁決階段計算成本
裁決雖只針對入圍技能，但仍需多次完整前向傳遞。未來可研究：
- 使用推測解碼（speculative decoding）或快取機制加速裁決。
- 以輕量判別頭（discriminative head）替代部分完整前向傳遞。
- 在瞥視階段進一步壓縮入圍名單，減少裁決次數。

##### 6. 可解釋性與錯誤分析
Gavel 的 token 級瞥視提供了天然的可解釋性：可視化哪些任務 token 對哪些技能投了票。未來可：
- 建立錯誤案例分類（例如語義相似技能混淆、中期需求被忽略）。
- 利用可解釋性回饋改進訓練資料與映射設計。
- 開發人機協作介面，讓使用者審查路由決策。

##### 7. 真實世界代理部署
SkillTraj 是模擬軌跡，未來需在真實代理框架（harness）中進行長期部署研究，包括：
- 與 Claude Code、Codex、OpenAI Agents SDK 等整合。
- 在真實軟體工程、資料分析、科學計算任務中評估端到端效能。
- 收集使用者回饋並進行線上學習（online learning）。

## 論文問答

**[Background & Motivation]**

**Q1：這篇論文想要解決的核心問題是什麼？**
A：隨著大型語言模型代理的能力不斷擴展，技能庫（skill library）已成為補充其參數化知識的主要方式，但從動輒數萬筆條目中挑選出正確技能，已成為代理系統的關鍵瓶頸。選對技能能顯著提升任務表現，選錯則可能讓表現比不使用技能還差，而且庫越大，這個選擇問題就越困難。因此，本論文聚焦於如何在不犧牲代理能力或上下文空間的前提下，實現可擴展且準確的技能路由。

**Q2：現行主流做法「漸進式揭露」（progressive disclosure）為何會失效？**
A：漸進式揭露把所有技能的名稱與描述中繼資料都預先塞進系統提示，導致上下文被大量中繼資料佔據，代理的注意力被分散到整個技能庫上。這種擁擠會隨著庫大小線性惡化任務表現，例如 Codex 只能把技能中繼資料限制在上下文視窗的 2%，其餘直接丟棄。即使保留部分摘要，路由準確率仍會隨技能數量對數下降，且摘要往往遺漏了判斷所需的重要細節。

**Q3：「檢索後重排」（retrieve-and-rerank）管線又有哪些根本缺陷？**
A：檢索管線把選擇權交給外部嵌入模型與重排器，雖然能讓代理的上下文保持乾淨，但選擇過程脫離了代理本身的能力。外部模型擅長文字匹配，卻不如代理 LLM 那樣理解任務真正需要什麼，尤其是在展開中期、上下文充滿雜訊的時刻。此外，這些外部模型的能力不會隨著代理骨幹模型的升級而自動提升，形成能力脫節。

**[Method & Innovation]**

**Q4：Gavel 的核心方法論與創新點是什麼？**
A：Gavel 主張凍結的代理 LLM 本身已經在前向傳遞中攜帶了技能路由訊號，只需要兩個線性映射就能讀取出來。它不需要任何額外的大型模型，也不把任何技能文本放進上下文，直到真正選定某個技能為止。這種「原生技能路由」讓路由能力能隨著骨幹模型一起進步，同時只引入約 790 萬個可訓練參數。

**Q5：請詳細說明 Gavel 的「瞥視」（glance）階段如何運作。**
A：瞥視階段在代理 LLM 的某一中層狀態上嫁接一個新的注意力頭：一個查詢映射把任務 token 的中層狀態投影出來，一個鍵映射把每個技能 token 在安裝時的中層狀態投影出來。這兩個線性映射以對比式學習訓練，使得任務 token 會對真正適用的技能產生最強匹配，並讓每個任務 token 各自投票，避免關鍵 token 被平均掉。新技能加入時只需一次前向傳遞建立緊湊的逐技能庫，無需重新訓練。

**Q6：「裁決」（verdict）階段與「專家乘積」融合策略的設計理由是什麼？**
A：因子化的注意力頭可能遺漏細微推理，因此裁決階段只對瞥視選出的入圍技能進行完整前向傳遞，把任務附加到技能後讓模型重新計算。從這次前向傳遞中，Gavel 同時讀取生成式證據（似然）與判別式證據（是／否判斷），再加上瞥視的對比式分數。由於三者都可視為「給定任務下技能適用」的對數後驗，因此以專家乘積方式融合，能互補各自的強項。

**[Experiments & Results]**

**Q7：論文使用了哪些基準測試來評估 Gavel？**
A：論文在 SkillRet 的合成查詢—技能對上訓練後，直接零樣本轉移到三個公開基準測試，並另外自建了 SkillTraj。SkillTraj 包含 372 條模擬代理軌跡，專門評估路由器在展開中期、技能需求突然浮現時的表現，並設計了四種帶有雜訊的多輪上下文情境。這樣的組合同時涵蓋了書面任務與真實代理執行過程中的動態需求。

**Q8：Gavel 的關鍵實驗結果有哪些？**
A：在 Qwen3-32B 上，Gavel 超越了漸進式揭露與增加 12 億到 160 億外部參數的檢索後重排管線，在書面任務的 SRA-Bench 上領先最強管線達 13.4 分。在 SkillTraj 的四種情境中，領先幅度介於 8.6 到 21.9 分之間，顯示它在展開中期的雜訊環境中優勢更大。此外，在一個最小化的 Bash 代理框架中，同樣是 32B 的 Qwen3-32B 在 Skill-Use 上觸發正確技能的頻率，甚至高於 Claude Code 與 Codex 中更大的前沿模型。

**Q9：消融實驗與模型縮放趨勢揭示了什麼？**
A：消融實驗分別檢視了瞥視與裁決兩個階段的貢獻，證明兩者結合才能達到最佳路由表現。論文也發現，隨著骨幹模型能力提升，Gavel 的路由準確率隨之提高，這印證了「路由能力內建於代理 LLM」的核心假設。此外，透過 ε-cover 把逐技能庫壓縮到緊湊表示，能在控制儲存與計算成本的同時保持有界失真。

**[Applications & Impact]**

**Q10：Gavel 在實際部署上有什麼優勢？**
A：Gavel 不需要額外部署龐大的嵌入模型或重排器，僅靠代理 LLM 本身與兩個小型線性映射就能完成路由，大幅降低系統複雜度。由於技能文本在選定前不進入上下文，上下文視窗可以保留給真正的任務內容，讓技能庫規模不再受限於上下文長度。新增技能時只需一次前向傳遞建立狀態庫，無需重新訓練整個路由系統，非常適合快速演化的生產環境。

**Q11：從產品設計角度，Gavel 在延遲、儲存與訓練成本上需要注意什麼？**
A：瞥視階段只需對任務做一次前向傳遞並與緊湊的逐技能庫比對，延遲相對低廉；裁決階段雖需對入圍技能進行額外前向傳遞，但候選數量遠小於整個技能庫，成本可控。儲存方面，每個技能只需保留經過壓縮的中層狀態庫，而非完整文本，空間開銷小。訓練上，兩個線性映射只需在 SkillRet 這類合成資料上訓練一次，就能零樣本轉移到多個公開基準，部署門檻較低。

**Q12：這項研究對 LLM 代理與工具學習領域可能帶來什麼影響？**
A：Gavel 把技能路由從「外部檢索」或「上下文塞滿中繼資料」的典範，轉向「讀取凍結 LLM 內部狀態」的新方向。這證明 LLM 的中層表示已經蘊含足夠的任務—技能相關性訊號，可以透過極少參數讀取。這種思路未來可能擴展到工具選擇、API 呼叫、多模態能力路由等場景，推動更精簡、更原生的代理架構。

**[Limitations & Future]**

**Q13：論文承認了哪些主要限制？**
A：Gavel 目前仍需要在合成查詢—技能對上訓練兩個線性映射，雖然參數量小，但訓練資料的品質與覆蓋範圍會影響泛化。其表現也高度依賴骨幹模型，若中層狀態對某些任務或技能語義編碼不足，路由準確率可能下降。此外，主要實驗集中在 Qwen3-32B，對於其他架構或規模的模型，映射與層位的選擇可能需要額外驗證。

**Q14：Gavel 可能在哪些情況下表現不佳或失敗？**
A：當任務需求非常隱晦、需要多步推理才能與技能對應時，因子化的瞥視頭可能無法捕捉細微關聯。若技能庫中存在大量語義高度重疊的技能，或技能名稱與描述無法反映其真正用途，模型內部訊號也可能混淆。在嚴重偏離訓練分布的任務、對抗性輸入，或上下文雜訊極強的長篇多輪軌跡中，裁決階段的判斷同樣可能出錯。

**Q15：未來可以朝哪些方向延伸這項工作？**
A：未來可以探索如何讓 Gavel 同時選擇並組合多個技能，而不只是單一最佳技能，以處理更複雜的代理任務。也可以研究把路由訊號蒸餾成更輕量的專用路由器，或將此方法擴展到動態工具庫、API 生態系與多模態能力選擇。此外，更深入理解 LLM 中哪些層、哪些狀態維度承載了任務—技能相關性，將有助於設計更通用、更可解釋的原生路由機制。

## 實務應用指南

### 適用場景

1. **企業內部程式開發代理**：當工程團隊累積數百份 `SKILL.md`（如各服務的 API 呼叫規範、部署腳本、程式碼審查準則），可將 Gavel 嵌入 Claude Code / Codex 類框架，避免把全部技能中繼資料塞進系統提示，讓代理 LLM 在展開中期自動挑選正確技能。

2. **多工具客戶服務代理**：客服代理需要同時查詢訂單、退換貨、發票、知識庫等多種外部能力。Gavel 的「瞥視」可在不干擾對話上下文的前提下，從凍結 LLM 的前向傳遞讀出當前輪次最該觸發的技能。

3. **資料分析與科學計算代理**：面對大量分析腳本、視覺化模板與統計方法說明時，Gavel 能在任務描述出現的當下，透過中層狀態與緊湊逐技能庫比對，選出最適合的 Python/R 技能文件。

4. **DevOps / SRE 自動化代理**：runbook、故障排查指令、kubectl/bash 腳本等技能庫龐大且常在展開中期才被需要。Gavel 可讓 Bash 代理框架在正確時機載入正確 runbook，減少因上下文擁擠導致的誤判。

5. **多步研究助理**：當代理在長篇對話或工具呼叫序列中逐步發現需要引用某個專業領域技能時，Gavel 能利用模型自身狀態進行原生技能路由，而非依賴外部檢索器對上下文的片面理解。

---

### 實作前置條件

- **資料**：
  - 一份結構化的技能庫，每個技能至少包含名稱、描述與完整技能文件（如 `SKILL.md`）。
  - 用於訓練兩個線性映射的查詢–技能配對資料；若沒有真實標註，可仿照 SkillRet 合成。
  - 評估用的基準測試資料，建議包含書面任務與模擬代理軌跡（如 SkillTraj）兩種情境。

- **運算資源**：
  - 一個可載入凍結骨幹模型（如 Qwen3-32B）的推理環境。
  - 訓練兩個線性映射所需算力相對輕量（論文僅 7.9M 參數），一般單張 A100 等級 GPU 即可；但安裝階段需對每個技能執行一次前向傳遞並儲存中層狀態。

- **技能與系統前提**：
  - 能夠存取代理 LLM 的中層隱藏狀態（mid-layer states）。
  - 能在安裝時為每個技能建立並維護緊湊的逐技能庫（compact per-skill banks）。
  - 推理框架需支援「任務接上技能後恢復前向傳遞」的 verdict 階段。
  - 團隊需熟悉對比式學習與專家乘積（product of experts）等基本概念。

---

### 實作步驟建議

1. **鎖定骨幹模型與技能庫**：選定實際執行代理任務的凍結 LLM，並將所有技能文件標準化為統一格式。

2. **安裝階段建立逐技能庫**：對每個技能執行一次前向傳遞，擷取指定中層的技能 token 狀態，並可選擇使用 𝜀-cover 等方法壓縮為緊湊表徵，儲存為 per-skill bank。

3. **訓練瞥視階段的線性映射**：以對比式目標訓練 query map（任務 token 狀態）與 key map（技能 token 狀態），使任務 token 能對全技能庫打分；每個任務 token 獨立投票，避免少數關鍵 token 被平均掉。

4. **實作判決階段**：對瞥視選出的入圍技能（shortlisted skills），將任務接在技能文件後恢復前向傳遞，讀取模型自身的似然（likelihood）與 yes/no 判斷。

5. **以專家乘積融合三種訊號**：將瞥視的對比分數、判決的生成式似然、判決的判別式 yes/no 機率視為同一後驗的不同專家，進行乘積融合。

6. **嵌入代理框架**：在代理 harness 中攔截「需要技能」的時機，呼叫 Gavel 選出技能，再將選定的技能文件注入上下文；未選中的技能文字不進入上下文。

7. **評估與迭代**：先在公開基準測試驗證零樣本遷移能力，再於 SkillTraj 這類模擬代理軌跡上測試展開中期的路由準確率，並根據錯誤案例重新採樣訓練資料。

---

### 潛在風險與注意事項

- **中層狀態並非專為路由而設**：LLM 中層狀態同時編碼了下一個 token 預測所需的資訊，可能與路由訊號糾纏。建議透過對比訓練與 verdict 階段雙重驗證，降低單一線性映射的偏差。

- **領域轉移有限**：雖然論文顯示零樣本遷移可行，但若產品場景與訓練資料（如 SkillRet）差異極大，兩個線性映射可能退化。應保留領域適應（domain adaptation）的再訓練流程。

- **判決階段仍有計算成本**：verdict 需要對入圍技能各做一次前向傳遞，雖然只針對短名單，但在延遲敏感的互動場景中仍需控制入圍數量（例如 top-5 到 top-20）。

- **技能更新與版本管理**：新增或修改技能時，只需對該技能重新建立 per-skill bank，但必須確保 bank 版本與技能文件同步，避免路由依據過時表徵。

- **隱私與敏感內容**：per-skill bank 儲存了模型內部狀態，若技能文件包含敏感資訊，需對 bank 進行存取控制與加密，並評估是否會透過狀態洩漏原始內容。

- **過度依賴單一模型能力**：Gavel 的路由準確率會隨骨幹模型能力提升而提升，但也會隨之受限。在關鍵業務流程中，建議保留檢索後重排或人工確認的後備機制。

---

### 與其他技術的整合建議

- **取代漸進式揭露（progressive disclosure）**：直接移除「把所有技能名稱與描述預載進系統提示」的做法，改由 Gavel 在需要時選擇單一技能注入，顯著減少上下文擁擠。

- **作為檢索後重排（retrieve-and-rerank）的上層精煉器**：對於極大技能庫，可先以輕量嵌入模型召回 top-k 候選，再由 Gavel 的瞥視與判決進行精準重排，兼顧效率與代理能力。

- **嵌入現有代理框架**：無論是 Claude Code、Codex、LangChain 或自研 Bash 代理框架，都可將 Gavel 包裝成獨立路由服務，透過 API 接收任務與 rollout 狀態，回傳應載入的技能 ID。

- **結合向量資料庫**：將 per-skill bank 的索引與向量資料庫搭配使用，可加速大規模技能庫的初始篩選，並利用 Gavel 的線性映射分數作為二次排序依據。

- **快取與批次化**：在安裝階段預先計算並快取技能 bank；在 verdict 階段對入圍技能進行批次前向傳遞，以降低端到端延遲。

---

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從圖 1 的三種設計比較開始，理解「漸進式揭露會讓上下文擁擠」與「檢索管線會把選擇移出代理能力」這兩個痛點，再聚焦 Gavel 的兩階段直覺——先用輕量「瞥視」掃過全庫，再讓模型自己「判決」入圍技能。

- **AI 工程師**：重點閱讀技術實作細節，包括如何從凍結 LLM 擷取中層狀態、對比式訓練 query/key 線性映射、建立與壓縮 per-skill bank、恢復前向傳遞讀取似然與 yes/no 判斷，以及專家乘積融合的程式實現與延遲評估。

- **研究人員**：關注論文的方法論創新，例如為何單純讀取中層狀態不足以路由、token 級瞥視如何避免平均化關鍵 token、𝜀-cover 在壓縮技能表徵時的理論保證，以及 SkillTraj 基準測試在展開中期評估路由的設計意義。

- **產品經理**：著重評估商業價值與落地條件——Gavel 能以極少額外參數（僅兩個線性映射）提升路由準確率、減少上下文消耗、讓技能庫規模不再受上下文視窗硬性上限限制；同時需評估團隊是否具備存取中層狀態與維護 per-skill bank 的基礎建設，並規劃好領域適應與後備機制。
