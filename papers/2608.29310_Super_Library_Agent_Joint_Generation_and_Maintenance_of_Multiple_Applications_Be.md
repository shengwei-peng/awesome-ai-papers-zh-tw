## ⚡ TL;DR

解決多應用程式開發中共享邏輯重複與結構侵蝕的問題。
提出超級函式庫智慧體，透過候選引導抽取與情境感知遷移，聯合生成應用程式並維護跨程式共享元件庫。

## 摘要翻譯

組織經常開發並維護相關應用程式組合（portfolios of related applications）：這些可獨立部署的程式碼庫（independently deployable codebases）共享大量領域邏輯（domain logic）、介面模式（interface patterns）與操作慣例（operational conventions）。隨著大型語言模型程式設計智慧體（LLM coding agents）日益被用於生成與維護此類軟體，簡易的逐應用程式工作流程（application-by-application workflow）會在不同程式碼庫中重複共享邏輯（shared logic），並使長期的智慧體維護（agentic maintenance）累積冗長度（verbosity）、無用程式碼（dead code）與結構侵蝕（structural erosion）。我們提出超級函式庫智慧體（Super Library Agent）問題，其中智慧體依序生成 N 個相關應用程式組合（portfolio of N related applications），同時維護一個共享的超級函式庫（Super Library），其中包含可重複使用的跨應用程式元件（reusable cross-application components）。最小化的循序式腳手架（sequential scaffold）原則上可以抽取共享程式碼，並將應用程式遷移至持續演進的函式庫，但實際上卻面臨抽取召回率（extraction recall）偏低與相依性遷移（dependency migration）脆弱的問題。我們透過基於程式碼片段摘要（code chunk summaries）的候選引導抽取（candidate-guided extraction）、抽取前程式碼庫整合（pre-extraction codebase consolidation），以及利用抽取追蹤（extraction traces）與呼叫圖資訊（call-graph information）的情境感知遷移（context-aware migration），來解決這些問題。在 WebGen-Bench 與 PaperBench 上，我們的方法在保留應用程式功能的同時，相較於零樣本（zero-shot）方法顯著降低冗餘與 Token 佔用量（token footprint；包含冗長度〔verbosity〕與 Token 長度〔token length〕），並避免簡易函式庫建構（naive library construction）所導致的結構侵蝕（structural erosion），同時進一步降低原始碼行數（LOC）與最小描述長度（MDL）。我們的程式碼已公開於 https://github.com/sbigstar0310/super-library-agent。

### 核心貢獻（3～5點）
- 提出「超級函式庫智慧體（Super Library Agent）」問題，將多個相關應用程式的依序生成與共享函式庫的持續維護聯合考量，突破傳統單一程式碼庫（Single Codebase）的開發範式。
- 指出簡易循序式腳手架（sequential scaffold）在實務上的兩大缺陷：共享程式碼的抽取召回率（extraction recall）偏低，以及將應用程式遷移至函式庫的相依性遷移（dependency migration）過於脆弱。
- 設計三項對應技術：基於程式碼片段摘要（code chunk summaries）的候選引導抽取（candidate-guided extraction）、抽取前程式碼庫整合（pre-extraction codebase consolidation），以及結合抽取追蹤（extraction traces）與呼叫圖資訊（call-graph information）的情境感知遷移（context-aware migration）。
- 在 WebGen-Bench 與 PaperBench 上驗證，方法能在保留應用程式功能的前提下，顯著降低冗餘與 Token 佔用量（token footprint），避免簡易函式庫建構造成的結構侵蝕（structural erosion），並進一步減少原始碼行數（LOC）與最小描述長度（MDL）。

### 適合對象
本論文適合對大型語言模型程式設計智慧體（LLM coding agents）、多應用程式／多倉庫軟體開發、程式碼重複使用與函式庫學習（library learning），以及程式碼可維護性與結構侵蝕（structural erosion）議題感興趣的研究者與工程實務者閱讀；特別是正在建構或維護跨應用程式共享元件庫的平台工程與軟體維護團隊。

## 深度分析

#### 方法論解析

本文提出 **Super Library Agent（超級函式庫智慧體）** 問題，核心在於讓單一智慧體在依序生成 **N 個相關應用程式組合（portfolio of N related applications）** 的同時，動態維護一份跨應用程式共享的 **Super Library（超級函式庫）**。與傳統「逐應用程式工作流程（application-by-application workflow）」不同，此設定要求智慧體在每次新增應用程式時，都必須回頭檢視既有程式碼，把可重複使用的跨應用程式元件（reusable cross-application components）抽離至共享函式庫，並將已完成的應用程式遷移到新的抽象層。

作者首先建立一個 **循序式腳手架（sequential scaffold）** 作為基線：每個時間步 t，先由 **coding agent（程式生成智慧體）** 根據需求 x_t 與現有 Super Library L_{t-1} 生成新程式碼庫 c_t^0；接著由單一 **library agent（函式庫智慧體）** 執行兩件事：(1) 從目前已實作的應用程式中抽取共享元件，更新為 L_t；(2) 把受影響的舊應用程式遷移到更新後的函式庫。理想上，這能達成 **功能性與可維護性權衡（functionality–maintainability trade-off）** 的 Pareto 改善，即同時最大化功能正確性 S_func(C_N, X) 與聯合程式碼庫可維護性 S_maint(C_N, L_N)。

然而，作者指出此基線在實務上會遭遇兩大障礙：

1. **抽取召回率（extraction recall）** 過低：隨著應用程式數量增加，功能等價但語法結構迥異的實作會大量出現，僅靠表面相似度的檢索機制容易遺漏可重複使用的候選元件，導致 Super Library 覆蓋率不足。
2. **相依性遷移（dependency migration）** 脆弱：把本地實作搬進函式庫並非局部編輯，還涉及 import、呼叫點（call sites）、相依輔助函式乃至周邊 API 的更新。若遷移智慧體只看見被抽出的區塊，容易留下無效引用、重複實作或 **死碼（dead code）**。

針對上述問題，作者提出三項強化機制：

- **候選引導抽取（candidate-guided extraction）**：不讓模型僅做隱式發現（implicit discovery），而是先為每個程式碼區塊建立 **摘要化程式碼索引（summarized code indexes）**，再由 **基於 LLM 的選擇器（LLM-based selector）** 主動提出跨應用程式重複使用候選（cross-application reuse candidates）。這種「先產生候選、再驗證抽取」的方式，能顯著提升對語法變異但語義等價程式碼的召回。
- **抽取前程式碼庫整合（pre-extraction codebase consolidation）**：在正式抽取共享元件之前，先對程式碼庫進行整合與清理，減少雜訊與不一致，使後續抽象化更穩定。
- **情境感知遷移（context-aware migration）**：遷移時提供 **抽取追蹤（extraction traces）** 與 **呼叫圖情境（call-graph context）**，讓 **相依性遷移智慧體（dependency-migration agent）** 明確知道哪些本地區塊（local blocks）被合併、哪些 **函式庫元件（library components）** 應該取代它們，以及哪些周邊呼叫點或相依關係必須同步更新。

整體而言，方法論的設計哲學是把「函式庫學習（library learning）」從傳統的離線、後設壓縮，轉變為線上、與應用程式生成交錯進行的聯合生成與維護（joint generation and maintenance）流程。透過候選引導與呼叫圖情境，智慧體得以在擴充應用程式組合的同時，持續抑制 **冗贅（verbosity）**、重複與 **結構侵蝕（structural erosion）** 的累積。

#### 實驗數據解讀

作者在 **WebGen-Bench** 與 **PaperBench** 兩個基準上進行評估。雖然全文未列出完整數值表格，但從摘要與引言可歸納出以下實驗結論與其意涵：

- **功能正確性（accuracy）得以保留**：相較於獨立生成每個應用程式的 **零樣本（zero-shot）** 基線，Super Library Agent 在應用程式功能滿足度上並未下降。這點至關重要，因為許多為了可維護性而進行的重構或抽象化，常會意外改變行為；本文方法顯示抽象化與功能正確性可以並存。
- **冗贅與 Token 佔用量（token footprint）顯著降低**：由於共享邏輯被抽入 Super Library，各應用程式不再重複實作相同功能，因此整體程式碼的 **原始碼行數（LOC）** 與模型所見的 token 總量都下降。這對於長期由 **智慧體維護（agentic maintenance）** 的系統尤為重要，因為較短的上下文與較少的重複程式碼能降低後續推理成本與錯誤率。
- **最小描述長度（MDL）下降**：MDL 在此可被視為衡量聯合程式碼庫壓縮效率的指標。MDL 降低代表以「函式庫 + 各應用程式對函式庫的引用」來描述整個專案組合，比獨立描述每個應用程式更簡潔，也暗示抽象品質（abstraction quality）較高。
- **避免簡易函式庫建構帶來的結構侵蝕**：單純把重複程式碼抽出成函式庫，若遷移不正確，會留下破碎引用、死碼或過度參數化的 API，反而使結構更混亂。本文強調其方法在提升可維護性指標的同時，沒有引入這類 **結構侵蝕（structural erosion）**，顯示 **情境感知遷移（context-aware migration）** 與 **抽取追蹤（extraction traces）** 的實質貢獻。
- **函式庫利用率（library utilization）與抽象品質提升**：相較於基線，Super Library 中的元件被更多應用程式實際引用，代表抽取出的抽象並非「為壓縮而壓縮」的死程式碼，而是真正被重複使用的設計單元。

從指標設計來看，本文同時關注 **功能性（functionality）** 與 **可維護性（maintainability）**，並以 **LOC**、**MDL**、**token footprint**、**redundancy** 與 **structural erosion** 等多維度衡量後者，避免單一指標過度簡化。這樣的評估框架對於未來研究 **多個應用程式（multiple applications）** 的聯合生成具有參考價值。不過，由於缺乏詳細數值，我們無法判斷各項改進的效應量（effect size）與統計顯著性，也無法比較 WebGen-Bench 與 PaperBench 上差異的來源。

#### 與現有研究的比較

本文定位於多個研究方向的交會處，並針對既有工作的缺口提出明確改進：

1. **相較於單一程式碼庫的可維護性研究**：  
   諸如 MaintainCoder、SlopCodeBench、CodeTaste、Agentic Refactoring 等研究主要探討單一演進中程式碼庫的冗贅與架構債務。本文則把視角擴展到 **可獨立部署的程式碼庫（independently deployable codebases）** 組合，強調跨應用程式的共享邏輯（shared logic）與 **共享關注點（shared concerns）** 若未被抽象化，會在多個 **維護週期（maintenance cycle）** 中加速劣質累積程式碼（slop）的產生。

2. **相較於離線函式庫學習（library learning）**：  
   DreamCoder、Stitch、LILO、Librarian 等方法多從既有程式語料中離線挖掘抽象，或假設所有檔案位於單一 **邏輯專案（logical project）** 內。本文明確指出 **大規模多倉庫函式庫建立（large-scale multi-repo library creation）** 仍是開放問題，並提出線上設定：應用程式依序到達、Super Library 在生成新應用程式時即被使用、且更新後的抽象會被遷移回舊應用程式。這種「生成—抽取—遷移」的循環是對傳統離線壓縮範式的延伸。

3. **相較於通用程式碼重構工具**：  
   RefAgent、Meng et al.、Yue et al. 等系統雖然也將重構拆解為規劃、執行與修復，但它們通常面對已完成且靜態的專案。本文的 **抽取追蹤（extraction traces）** 與 **呼叫圖情境（call-graph context）** 則專為線上、跨程式碼庫的抽象化設計，強調遷移不只是替換本地實作，而是需要追蹤非局部的相依關係。

4. **相較於 Librarian 等 LLM 函式庫學習方法**：  
   Librarian 假設輸入檔案位於單一邏輯專案，而 Super Library Agent 處理的是多個獨立程式碼庫。此外，Berlot-Attwell et al. 指出 LLM 函式庫學習的效益可能被額外推理預算混淆，且學到的成品常被低度重用。本文透過 **候選引導抽取（candidate-guided extraction）** 與實際遷移機制，試圖確保學到的抽象確實被後續應用程式引用，從而提升真正的重用率而非僅是壓縮率。

**主要限制**包括：

- 目前設定僅考慮 **應用程式需求（application requests）** 依序到達且無後續修補（no subsequent patches），與真實軟體工程中持續迭代、需求變更的情境仍有距離。
- 理想 Super Library 的定義要求「任何被至少兩個應用程式使用的元件都應被抽出」，這在實務中可能導致過度抽象，尤其當兩個應用程式的相似程式碼只是巧合或語義細節不同時。
- 方法高度依賴 **基於 LLM 的選擇器（LLM-based selector）** 與 **相依性遷移智慧體（dependency-migration agent）** 的推理品質，若 LLM 對語義等價性的判斷有誤，可能產生錯誤抽象或破壞引用。
- 呼叫圖（call graph）的建構在動態語言或高度反射式程式碼中可能不完整，進而影響 **情境感知遷移（context-aware migration）** 的可靠性。
- 評估僅涵蓋 WebGen-Bench 與 PaperBench，對於企業級、多語言、長期演化的應用程式組合，方法的泛化能力仍需驗證。

#### 可重現性評估

根據摘要，作者已將程式碼釋出於 https://github.com/sbigstar0310/super-library-agent，這對可重現性（reproducibility）是正面訊號。然而，從提供的上下文無法確認以下關鍵細節：

- **資料集**：WebGen-Bench 與 PaperBench 是否為公開基準？若為公開，則其他研究者可直接比較；若包含私有資料，則重現會受限。
- **模型權重與 API 版本**：方法依賴 LLM 進行候選選擇與遷移，但文中未說明使用的模型（例如 GPT-4、Claude、Gemini 等）及其版本、溫度參數、提示模板（prompt templates）。由於 LLM 輸出具有隨機性，缺乏這些資訊會使精確重現變得困難。
- **評估腳本與指標實作**：雖然 GitHub 倉庫可能包含評估程式，但文中未描述 S_func 與 S_maint 的具體計算方式，例如功能正確性是否透過單元測試、人工判斷或自動評分器衡量；MDL 的計算是否包含提示長度或僅計算程式碼。
- **實驗設定**：N 的範圍、應用程式順序是否隨機、每個設定重複幾次、是否報告標準差等，都會影響結果的穩健性。

建議作者在釋出程式碼時，一併提供 `README`、環境設定檔、模型 API 設定、提示模板、以及完整的實驗日誌（logs），以提升社群重現與延伸研究的可能性。

#### 未來研究方向

基於本文的貢獻與限制，可延伸的研究方向包括：

1. **持續維護與需求變更**：將設定從「單一初始需求」擴展到應用程式會持續接收修補（patches）與需求變更的情境，研究 Super Library 如何隨時間演進而不累積技術債。
2. **函式庫版本控制與向後相容性**：當 Super Library 更新後，如何管理版本、棄用（deprecation）策略與向後相容性，避免遷移舊應用程式時產生連鎖破壞。
3. **多智慧體協作架構**：目前由單一 library agent 負責抽取與遷移，未來可探索專責「發現」、「抽象化」、「遷移」、「驗證」的多智慧體協作，並引入對抗式檢查者（adversarial checker）來降低錯誤抽象風險。
4. **更強大的語義等價檢驗**：結合符號執行、單元測試生成與形式化驗證，輔助 LLM 判斷兩段程式碼是否真正語義等價，而不僅依賴摘要相似度。
5. **階層式與領域特定函式庫**：研究如何自動建立多層次抽象（例如基礎工具層、領域邏輯層、介面模式層），並針對特定領域（如網頁前端、資料處理、嵌入式系統）設計領域特定的 **操作慣例（operational conventions）** 與抽取啟發式規則。
6. **動態候選檢索與記憶機制**：隨著 N 增大，程式碼索引規模也會增加。可研究如何以向量資料庫、圖神經網路或更精細的程式碼嵌入（code embedding）來維持高 **抽取召回率（extraction recall）**，同時控制檢索成本。
7. **與軟體工程流程整合**：將 Super Library Agent 嵌入持續整合／持續部署（CI/CD）流程，讓每次提交都觸發共享元件的偵測、抽取與遷移，形成自動化的 **結構性防禦（structural defense）**。
8. **擴展至非程式碼資產**：除了程式碼，應用程式組合也常共享設定檔、資料庫綱要（schema）、文件、測試案例等。未來可研究如何聯合維護這些跨應用程式資產。
9. **人機協作與可解釋抽象**：讓開發者能審查、接受或拒絕 LLM 提出的抽象候選，並要求智慧體解釋為何兩段程式碼應被合併，以提升信任度與可維護性。
10. **更大規模與多語言評估**：在更多基準、更多程式語言、更大 N 與更長維護歷程下驗證方法，並建立標準化的 **多倉庫函式庫建立（multi-repo library creation）** 評測協定。

## 論文問答

**Q1：什麼是 Super Library Agent 問題，為什麼它在真實軟體開發中很重要？**

A：Super Library Agent 問題要求一個智慧體在依序生成 N 個相關且可獨立部署的應用程式組合時，同時維護一個跨應用程式共享的 Super Library，把可重複使用的元件抽取到這個共享函式庫中。這個問題之所以重要，是因為真實組織很少只維護單一程式碼庫，而是同時開發與維護多個共享領域邏輯、介面模式或操作慣例的應用程式。若沒有這種跨應用程式的結構性防禦，智慧體會在每個應用程式中重複實作相同邏輯，並在每次維護週期中累積冗贅、無用程式碼與結構侵蝕，最終產生功能正確但難以維護的劣質累積程式碼（slop）。

**Q2：現有的逐應用程式工作流程與簡易循序架構分別在哪裡失敗？**

A：逐應用程式工作流程會在多個程式碼庫中重複產生共享邏輯，導致大量冗餘與不一致。即使是較強的循序式腳手架——依序生成應用程式並把共享元件抽取到 Super Library——在實務上也會因為兩個關鍵障礙而失敗：第一是抽取召回率過低，智慧體難以發現語法結構不同但功能等價的程式碼；第二是相依性遷移過於脆弱，把本地實作搬到函式庫後，呼叫點、匯入與相依輔助函式若未同步更新，就會留下損壞的參照或死碼。

**Q3：為什麼「大規模多倉庫函式庫建立」過去被視為開放問題，本文如何填補這個缺口？**

A：過去的函式庫學習方法，例如 Librarian，通常假設所有輸入檔案都位於同一個邏輯專案內，因此無法處理多個獨立部署的程式碼庫。本文提出的 Super Library Agent 則研究一個線上設定：應用程式依序到達，Super Library 在生成新應用程式時被使用，而更新後的抽象化元件會被遷移回先前的應用程式。這種跨應用程式的聯合生成與維護機制，填補了既有研究在「多倉庫函式庫建立」上的空白。

**Q4：本文提出的核心方法包含哪三大技術，各自對應什麼挑戰？**

A：本文的核心方法包含候選引導抽取、抽取前程式碼庫整合，以及情境感知遷移。候選引導抽取透過摘要化程式碼索引與基於 LLM 的選擇器，主動提出跨應用程式重複使用候選，以解決抽取召回率過低的問題。情境感知遷移則把抽取追蹤與呼叫圖情境提供給相依性遷移智慧體，確保本地區塊被正確替換為函式庫元件，並同步更新所有相關呼叫點與相依性，從而解決遷移正確性的問題。

**Q5：候選引導抽取如何運作，為什麼能改善抽取召回率？**

A：候選引導抽取首先為各個程式碼片段建立摘要化程式碼索引，然後使用一個基於 LLM 的選擇器來主動提出可能的跨應用程式重複使用候選。這種做法不同於僅依賴模型隱式發現共享元件，因為功能等價的實作可能在語法與結構上差異很大，單靠表面相似度檢索容易遺漏。透過讓選擇器明確比對摘要並產出候選清單，系統能顯著提升發現潛在共享元件的召回率。

**Q6：情境感知遷移如何確保把本地實作換成函式庫元件後，應用程式仍然正確運作？**

A：情境感知遷移會把抽取追蹤與呼叫圖資訊一併提供給相依性遷移智慧體，讓它明確知道哪些本地區塊已經被整合到 Super Library、應該用哪個函式庫元件取代，以及哪些周圍呼叫點或相依性必須更新。由於抽取不是局部編輯，單純替換可見實作可能遺漏非局部的匯入、輔助函式或 API 調整，因此呼叫圖情境能幫助智慧體追蹤這些連鎖影響。這樣的設計大幅降低了遷移後出現損壞參照、重複實作或死碼的風險。

**Q7：本文在哪些基準上進行評估，這些基準各有什麼特性？**

A：本文在 WebGen-Bench 與 PaperBench 兩個基準上進行評估。WebGen-Bench 主要用於評估網頁應用程式的生成能力，適合觀察跨應用程式共享的介面模式與領域邏輯；PaperBench 則聚焦於學術論文相關的程式生成任務，能檢驗方法在較為複雜、結構化需求下的表現。這兩個基準共同提供了功能正確性與多項程式碼可維護性指標，讓作者能同時檢驗準確率與聯合程式碼庫的維護品質。

**Q8：實驗結果顯示本文方法相較於基線有哪些主要優勢？**

A：實驗結果顯示，本文方法在保留應用程式功能的前提下，顯著降低了冗餘與 Token 佔用量，包括程式碼的冗長度與整體 token 長度。相較於零樣本基線，它在維持準確率的同時改善了可維護性；相較於簡易的函式庫建構基線，它則避免了因遷移錯誤所造成的結構侵蝕。此外，方法還進一步減少了原始碼行數（LOC）與最小描述長度（MDL），顯示出更好的抽象化品質與壓縮效果。

**Q9：若移除候選引導抽取或情境感知遷移，預期會對結果造成什麼影響？**

A：若移除候選引導抽取，智慧體將回到僅依賴隱式發現或表面相似度檢索的模式，導致大量功能等價但語法不同的共享元件被遺漏，進而降低 Super Library 的覆蓋率與重複使用率。若移除情境感知遷移，則遷移智慧體缺乏抽取追蹤與呼叫圖情境，容易只替換局部實作而忽略非局部相依性，產生損壞參照或死碼。這兩個元件的消融實驗預期會顯示維護性指標、函式庫利用率與功能正確性同步下降，證明它們對整體方法的貢獻。

**Q10：在實務上，Super Library Agent 最適合應用在哪些場景？**

A：Super Library Agent 最適合應用於組織同時維護多個相關應用程式的場景，例如一系列共享業務邏輯的內部工具、使用相似前端元件的網頁應用程式，或採用共通資料處理流程的微服務組合。在這些情境中，各應用程式雖然可獨立部署，卻在領域邏輯、介面模式與操作慣例上高度重疊，正是跨應用程式重複使用的最佳候選。透過自動建立與維護 Super Library，團隊可以減少重複開發、統一實作風格，並降低長期維護成本。

**Q11：若要將這套方法產品化，需要考慮哪些工程與管理議題？**

A：產品化時必須為 Super Library 建立版本控制與發布流程，確保更新後的函式庫元件不會破壞既有應用程式的穩定性。此外，遷移過程應整合持續整合／持續部署（CI/CD）與自動化測試，並保留人工審查機制，因為 LLM 仍可能在抽象化或遷移時做出不當設計決策。最後，還需考慮 API 穩定性、向後相容性、Token 與推理成本，以及如何在多團隊共享函式庫時協調命名規範與責任劃分。

**Q12：這項研究對 LLM 程式設計智慧體與軟體工程領域可能帶來什麼影響？**

A：這項研究把 LLM 程式設計智慧體的視角從單一程式碼庫擴展到整個應用程式組合，強調聯合程式碼庫的維護品質而非僅關注個別應用程式的功能正確性。它為函式庫學習、智慧體重構與可維護程式碼生成等領域提供了一個新的問題設定與評估維度。未來這類方法可能成為企業級代理開發平台的基礎，協助組織在規模化使用 AI 生成程式碼時，主動抑制結構侵蝕與技術債累積。

**Q13：本文方法有哪些已知的限制？**

A：本文目前考慮的是依序到達且沒有後續修補的設定，也就是每個應用程式只會收到一次初始需求，這與真實世界中持續演化的維護週期有所不同。此外，方法假設應用程式之間具有足夠的相關性，若應用程式差異過大，Super Library 的價值會大幅降低。最後，基於 LLM 的候選選擇器與遷移智慧體仍可能出現錯誤，且其推理成本與延遲在大型專案組合中也需要進一步評估。

**Q14：在哪些情況下，Super Library Agent 可能會失敗或產生不如預期的結果？**

A：當功能等價的程式碼在語法與結構上差異極大，甚至連摘要化索引也難以捕捉其相似性時，候選引導抽取仍可能遺漏這些共享元件。若應用程式之間存在複雜的非局部相依性，例如透過動態匯入、反射或外部設定檔耦合，情境感知遷移也可能無法完整更新所有呼叫點。此外，過度抽象化有時會把僅有細微差異的程式碼強行統一，反而降低可讀性並增加未來修改的難度。

**Q15：未來研究可以朝哪些方向延伸這項工作？**

A：未來可以將設定擴展到應用程式持續接收修補與需求變更的情境，研究如何在動態維護週期中保持 Super Library 的穩定與演化。另一個方向是建立多層次或領域專屬的函式庫結構，以支援更大規模與更多樣化的應用程式組合。此外，結合人機協作、強化學習選擇器，以及在更多領域基準上進行評估，也都有助於提升方法的穩健性、可擴展性與實用價值。

## 實務應用指南

### 適用場景

**企業內部 SaaS 產品線**  
當組織同時維護多個面向相似客群的 SaaS 應用程式（例如 CRM、專案管理、工單系統）時，各產品間常重複出現權限驗證、通知中心、報表匯出等領域邏輯。超級函式庫智慧體（Super Library Agent）可在生成新產品的同時，把這些共享關注點抽取為跨應用程式重複使用的元件，避免每個產品各自實作。

**電商平台多店鋪 / 多市場應用**  
同一電商平台可能為不同品牌、地區或銷售通路建立獨立部署的店鋪前台與後台。這些應用程式共享購物車、庫存查詢、金流介接等模式，卻又因市場差異而需要客製化。透過循序式腳手架，可在新增店鋪時自動識別並遷移至超級函式庫，降低冗贅與結構侵蝕。

**金融機構合規與報表系統**  
銀行或保險公司常需因應不同法規產出多套報表與資料驗證流程。這些系統可獨立部署，但共享資料清洗、格式轉換、稽核軌跡等邏輯。候選引導抽取能協助發現語法結構不同但功能等價的實作，提升抽取召回率。

**物聯網裝置管理後台**  
不同裝置類型（感測器、閘道器、攝影機）通常對應獨立的後台應用程式，但共享裝置註冊、韌體更新、告警規則等操作慣例。超級函式庫可作為跨裝置的共用層，並在新增裝置類型時自動遷移既有後台。

**學術研究工具鏈**  
研究團隊在開發一系列實驗管線、資料視覺化或論文輔助工具時，常重複使用資料前處理、統計檢定、圖表生成等區塊。此方法能協助建立可重複使用的研究函式庫，並維持各工具的可獨立部署性。

### 實作前置條件

**資料準備**  
需要完整的應用程式需求描述、現有程式碼庫（若已存在部分應用程式）、領域詞彙表，以及跨應用程式的相依性圖譜。若從零開始，建議先建立一份「共用關注點清單」，作為引導抽取的種子候選。此外，需準備測試案例或驗收準則，以確保遷移後功能不被破壞。

**運算資源**  
需具備可呼叫的大型語言模型 API 配額（用於程式碼生成、候選選擇與遷移），以及向量資料庫或摘要化程式碼索引的儲存空間。CI/CD 環境與自動化測試基礎建設也必不可少，因為情境感知遷移必須在每次函式庫更新後驗證所有受影響應用程式。

**技能組合**  
團隊至少需要一名熟悉軟體架構與重構的工程師、一名具備提示工程與 LLM 流程設計經驗的 AI 工程師，以及一名能建立靜態分析與呼叫圖工具的開發者。DevOps 能力則用於維護多個可獨立部署的程式碼庫與持續整合流程。

---

### 實作步驟建議

**步驟一：建立領域詞彙與共用關注點清單**  
在生成任何應用程式前，先整理領域邏輯、介面模式與操作慣例的清單。這份清單將成為後續候選引導抽取的初始依據，避免僅依賴隱式發現而遺漏重要共享元件。

**步驟二：部署循序式腳手架**  
讓智慧體依序處理每個應用程式需求。第一個應用程式可獨立生成；從第二個開始，智慧體必須先檢視超級函式庫中是否已有可重複使用的元件，再決定要引用、改寫或新增本地實作。

**步驟三：實作候選引導抽取**  
為每個已完成的應用程式建立程式碼片段摘要與摘要化程式碼索引。使用基於 LLM 的選擇器比對跨應用程式的區塊，主動提出跨應用程式重複使用候選，再由工程師或自動化規則決定是否抽取至超級函式庫。

**步驟四：建立抽取追蹤與呼叫圖**  
每次抽取都必須記錄抽取追蹤：哪些本地區塊被整合、對應到哪些函式庫元件、涉及哪些呼叫點。同時產生或更新呼叫圖資訊，作為後續遷移的上下文。

**步驟五：執行情境感知遷移**  
由相依性遷移智慧體根據抽取追蹤與呼叫圖情境，更新受影響應用程式的匯入、呼叫點與周邊相依性。遷移後必須執行完整測試，確認無遺漏的本地實作或無用程式碼。

**步驟六：建立持續驗證迴路**  
將上述流程整合至 CI/CD，每次超級函式庫更新後自動觸發多應用程式測試、重複度檢查與最小描述長度（MDL）評估，防止智慧體維護過程中累積 slop。

---

### 潛在風險與注意事項

**抽取召回率不足**  
若僅仰賴表面相似度檢索，功能等價但語法結構差異大的區塊容易被忽略。建議結合摘要化程式碼索引與基於 LLM 的選擇器，並定期由領域專家審閱候選清單。

**遷移後功能退化**  
相依性遷移並非局部編輯，遺漏任何呼叫點或輔助函式都可能導致程式損壞。遷移智慧體必須取得完整的抽取追蹤與呼叫圖情境，並在遷移後執行回歸測試。

**函式庫過度抽象**  
過度積極抽取可能把僅有細微相似處的本地區塊硬塞進超級函式庫，反而增加複雜度。應設定明確門檻：只有被至少兩個已實作應用程式使用的元件才納入函式庫。

**版本相依性管理**  
多個可獨立部署的程式碼庫引用同一超級函式庫時，更新函式庫可能引發連鎖影響。建議採用語意化版本控制，並在遷移階段明確記錄每個應用程式所依賴的函式庫版本。

**智慧體累積 slop**  
長時間由智慧體維護可能導致程式碼逐漸冗贅、結構混亂。應定期監控 LOC、Token 佔用量與 MDL 等可維護性指標，並將結構性防禦納入開發規範。

---

### 與其他技術的整合建議

**RAG 與向量資料庫**  
將摘要化程式碼索引儲存於向量資料庫中，可讓候選引導抽取具備檢索增強生成的能力，提升跨應用程式重複使用候選的發現效率。

**靜態分析工具**  
整合呼叫圖分析器、重複程式碼偵測器與相依性掃描工具，可為 LLM 提供更精確的上下文，降低情境感知遷移出錯的機率。

**CI/CD 與自動化測試**  
每次抽取與遷移都應觸發自動化建置、單元測試、整合測試與功能驗收。多應用程式的測試矩陣是確保遷移正確性的關鍵。

**單體倉庫 / 多倉庫策略**  
雖然本文聚焦多倉庫函式庫建立，但實務上可根據組織規模選擇單體倉庫或獨立倉庫。超級函式庫本身建議以獨立倉庫或子模組形式管理，並透過套件管理器分發。

**現有程式碼生成工具**  
可將此方法疊加於現有的 LLM 程式設計智慧體（如 Cursor、GitHub Copilot Workspace、Devin）之上，透過額外的函式庫維護層強化多應用程式情境下的可維護性。

### 給不同背景讀者的閱讀建議

**給初學者**  
這篇論文處理的是「如何讓 AI 同時寫很多個相關程式，又不讓它們變成一堆亂七八糟的重複程式碼」的問題。如果你剛開始學習軟體開發，建議先理解「什麼是函式庫」「什麼是重構」以及「為什麼重複程式碼不好」，再回頭閱讀本文的問題定義與適用場景，會更容易掌握核心概念。

**給 AI 工程師**  
本文提供了一個可落地的多智慧體流程：循序式腳手架、候選引導抽取、情境感知遷移。建議你重點關注方法章節中的提示設計、LLM-based selector 的實作細節，以及如何利用抽取追蹤與呼叫圖降低遷移錯誤。這些設計可直接應用於你正在建構的程式碼生成管線。

**給研究人員**  
Super Library Agent 問題將函式庫學習從「事後壓縮」推進到「線上聯合生成與維護」的設定，並明確提出抽取召回率與遷移正確性兩大挑戰。建議從問題定義與相關工作切入，思考如何進一步結合程式合成、神經程式搜尋或形式化驗證來強化遷移保證。

**給產品經理**  
這項技術適合擁有多條相似產品線、長期受重複開發與維護成本困擾的組織。閱讀時請聚焦適用場景與潛在風險：它能幫助團隊在加速開發的同時控制技術債，但需要前期投入於領域整理、測試基礎建設與版本管理，否則容易淪為另一個難以維護的共用元件庫。
