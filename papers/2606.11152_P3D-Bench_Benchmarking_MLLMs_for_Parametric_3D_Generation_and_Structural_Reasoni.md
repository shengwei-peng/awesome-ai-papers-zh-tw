## ⚡ TL;DR

現有基準缺乏對參數化3D生成的全面評估，無法同時檢驗可執行程式碼、幾何精確度與零件結構。
P3D-Bench提出統一評測協議，涵蓋文字、影像與組裝三種3D生成任務，並支援四種程式碼格式。
評測顯示模型語意對齊佳（J-Sem≈0.8），幾何精確度低（J-Geo≈0.35），零件F1僅約0.5。

## 摘要翻譯

多模態大型語言模型（Multimodal Large Language Model, MLLM）能夠撰寫程式碼以產生複雜程式，也能運用程式進行 3D 建模，這開啟了一條由其先驗（priors）、世界知識（World Knowledge）與推理（Reasoning）所驅動的 3D 生成新途徑。然而現有的基準測試（Benchmark）很少透過程式碼評估 3D 建模。此類建模所需不僅止於可執行的程式碼（Executable Code）：模型必須根據文字提示（Text Prompt）或視覺規格（Visual Specification），產生一個幾何精確（Geometric Precision）、語意對齊（Semantic Alignment）且具組裝一致性（Assembly-consistent）的參數化 3D 程式（Parametric 3D Program）。我們提出 P3D-Bench，一個用於參數化 3D 生成（Parametric 3D Generation）的基準測試。與 3D 網格（Mesh）不同，參數化 3D 程式揭示了明確的尺寸、建構運算（Construction Operations）與零件關係（Part Relations），能夠檢驗模型是否還原了設計（Design）的結構（Structure），而非僅止於其外觀（Appearance）。在統一評測協議（Unified Protocol）下，P3D-Bench 涵蓋三個任務類別（Task Family）：文字到 3D（Text-to-3D）、影像到 3D（Image-to-3D）與組裝 3D（Assembly-3D），並針對每個輸出評分其可執行性（Executability）、幾何保真度（Geometric Fidelity）、拓撲（Topology）、文字約束對齊（Text-grounded Constraints）、多視角語意對齊（Multiview Semantic Alignment）與零件級結構（Part-level Structure）。我們在 400 個文字案例、400 個影像案例與 203 個帶註解（Annotation）的組裝樣本上評測前沿 MLLM（Frontier MLLMs）與純文字 LLM（Text-only LLMs），並以領域專用模型（Domain-specific Models）作為參考基準。我們的廣泛評測得出三項發現。首先，組裝是最困難的設定，模型在此仍無法將多個零件組合成一致性結構（Coherent Structure）。其次，模型通常能還原目標物件（Target Object）的全域形狀（Global Shape）與語意身分（Semantic Identity），卻無法重現輸入所指定的精確參數化幾何（Parametric Geometry）。第三，零件級建模在組裝任務上仍然薄弱，模型既無法還原各零件的幾何（Geometry），也無法給出正確的零件數量。這些結果將 P3D-Bench 定位為評測參數化 3D 生成中精確參數化幾何與零件級結構的基準測試。

### 核心貢獻（3～5點）
- 提出 **P3D-Bench**，首個專門透過程式碼評測 3D 建模能力的基準測試，聚焦於參數化 3D 程式（Parametric 3D Program）而非 3D 網格，能揭示模型是否還原設計的結構而非僅止於外觀。
- 在統一評測協議下涵蓋三大任務類別：**文字到 3D（Text-to-3D）**、**影像到 3D（Image-to-3D）** 與 **組裝 3D（Assembly-3D）**，並建立六項評測指標（Evaluation Metric），涵蓋可執行性、幾何保真度、拓撲、文字約束對齊、多視角語意對齊與零件級結構。
- 建構具規模的評測資料集，包含 400 個文字案例、400 個影像案例與 203 個帶組裝級註解（Assembly-level Annotation）與零件級註解（Part-level Annotation）的組裝樣本，並以領域專用模型作為參考基準。
- 透過對前沿 MLLM 與純文字 LLM 的廣泛評測，揭示三項關鍵發現：組裝任務最為困難；模型可還原全域形狀與語意身分卻難以重現精確參數化幾何；零件級建模在組裝任務上尤其薄弱。
- 將 P3D-Bench 定位為推動**精確參數化幾何**與**零件級結構**研究的基準測試，為未來 MLLM 在 CAD（Computer-Aided Design）領域的發展提供明確的評測依據。

### 適合對象
本研究最適合以下讀者閱讀：
1. **MLLM 研究者**：關注多模態大型語言模型在程式碼生成、空間推理（Spatial Reasoning）與結構推理（Structural Reasoning）能力的研究人員，可藉此了解前沿模型在 3D 建模任務上的優勢與瓶頸。
2. **CAD 與 3D 建模領域研究者**：從事電腦輔助設計、參數化建模（Parametric 3D Generation）與文字到 3D／影像到 3D 生成技術開發的學者與工程師。
3. **基準測試（Benchmark）設計者**：對 AI 評測方法論、評測指標（Evaluation Metric）設計與多任務統一評測協議感興趣的研究者。
4. **產業界實務應用者**：從事自動化設計、智慧製造、數位孿生等領域，需要評估 AI 模型生成可執行且精確之 3D 模型能力的工程團隊與產品負責人。

## 深度分析

#### 方法論解析

P3D-Bench 的方法論核心在於將「參數化 3D 生成」(parametric 3D generation) 視為一個需要多能力聯合 (joint capability) 協作的任務，而非單一能力的延伸。論文的設計哲學可從三個層面剖析：

**1. 任務設計的三層遞進結構**

論文將參數化 3D 生成拆解為三個任務類別 (task families)，形成由簡至難的階梯式評測：

- **Text-to-3D (文字到 3D)**：輸入為文字描述，輸出為單一零件 (single part)。此任務測試模型從自然語言規格中提取幾何與語意資訊的能力。
- **Image-to-3D (影像到 3D)**：輸入為單一渲染影像，輸出為多零件物件 (multi-part object)。此任務要求模型從單一視角推論不可見的幾何與零件佈局 (part layout)，考驗空間推理 (spatial reasoning) 與視覺理解。
- **Assembly-3D (組裝 3D)**：輸入為影像加上組裝級與零件級註解 (assembly-level and part-level annotations)，輸出為完整組裝。此任務要求模型同時處理零件內部幾何、零件間空間關係 (spatial relations) 與整體結構一致性 (assembly-consistent)。

此設計的關鍵洞察在於：參數化 3D 生成不僅是「視覺品質」的問題，更是「結構推理」(structural reasoning) 的問題。從單零件到多零件再到組裝，難度的增加不僅來自幾何複雜度，更來自零件關係 (part relations) 與組裝關係 (assembly relations) 的推論需求。

**2. 統一評測協議 (Unified Protocol) 的設計**

P3D-Bench 採用「執行-渲染-評分」(execute-render-score) 的統一流程：

- **四種輸出格式 (Output Format)**：JSON、OpenSCAD、CadQuery、Three.js。這四種格式代表了不同的程式設計典範——JSON 為結構化資料描述、OpenSCAD 為宣告式腳本、CadQuery 為 Python 程式庫、Three.js 為 JavaScript 場景描述。支援多種格式使基準測試能評估模型在不同程式語境下的泛化能力。
- **四個評測維度 (Evaluation Dimensions)**：
  - **Geometry (幾何)**：幾何保真度 (geometric fidelity)，衡量生成模型與目標物件在尺寸、形狀上的精確度。
  - **Topology (拓撲)**：衡量網格結構的合理性，如流形性 (manifoldness)、孔洞正確性等。
  - **Judge (判斷)**：基於 MLLM 的判斷 (MLLM-based judgment)，涵蓋多視角語意對齊 (multiview semantic alignment) 與文字約束對齊 (text-grounded constraints)。
  - **Part (零件)**：零件級結構 (part-level structure)，專門評估組裝任務中的零件數量、幾何與空間配置。

此四維度設計的精妙之處在於：將「可執行性」(executability) 視為基本門檻，再從幾何、拓撲、語意、結構四個面向進行細粒度評分，避免單一指標的偏頗。

**3. 資料集建構管線 (P3D-Dataset Pipeline)**

論文從 Text2CAD v1.1 與 Fusion 360 Gallery 兩個來源出發，經過篩選 (filtering)、去重 (near-duplicates removal)、平衡 (balancing across complexity levels)、註解 (annotation) 與自動驗證 (automatic validation) 五個步驟，最終產出 400 個文字案例、400 個影像案例與 203 個組裝案例。此管線的設計重點在於：

- **品質控制**：過濾模糊模型 (ambiguous models)，確保每個案例都有明確的設計意圖。
- **結構化註解**：為每個案例生成描述性規格 (descriptive specification)、參數化規格 (parametric specification) 與零件級註解，使三個任務能共享底層資料。
- **複雜度平衡**：在複雜度等級 (complexity level) 上進行平衡，避免資料集偏向簡單或複雜極端。

#### 實驗數據解讀

論文的實驗結果揭示了當前 MLLM 在參數化 3D 生成任務上的三個關鍵發現，這些發現具有深遠的啟示：

**1. 組裝任務的難度鴻溝**

實驗顯示，組裝任務 (Assembly-3D) 是三個任務中最困難的。這不僅是因為組裝涉及更多零件，更因為它要求模型同時處理：(a) 每個零件的內部幾何正確性；(b) 零件間的空間關係正確性；(c) 整體結構的一致性。論文的數據顯示，即使是最強的 MLLM，在組裝任務上的 PartMatchF1 僅約 0.5，意味著模型在零件數量與幾何匹配上都存在顯著不足。

**2. 幾何對齊與語意對齊的不對稱**

這是論文中最引人深思的發現之一：最強的 MLLM 在語意對齊上已達到 J-Sem ≈ 0.8，但在幾何對齊上僅 J-Geo ≈ 0.35。這意味著：

- 模型能正確識別「這是一把椅子」或「這是一個齒輪」，但在精確重現「椅子的座面寬度為 400mm、靠背傾角為 15 度」時表現不佳。
- 這種不對稱反映了當前 MLLM 的訓練偏重於語意理解而非精確數值推理。模型傾向於生成「看起來像」的物件，而非「規格上正確」的物件。
- 對工業應用而言，這是一個嚴重的瓶頸——CAD 的核心價值在於精確性，而非僅僅是視覺相似性。

**3. 零件級建模的雙重失敗**

在組裝任務中，模型不僅在零件的空間配置上出錯，更在零件本身的重建上失敗。PartMatchF1 ≈ 0.5 意味著模型既無法正確預測零件數量，也無法準確重建每個零件的幾何。這揭示了當前方法的根本限制：模型缺乏對「零件作為獨立設計單元」的結構化理解。

**4. 評測指標的設計意涵**

論文的四維度評測（Geo、Topo、Judge、Part）並非冗餘，而是針對不同失敗模式的診斷工具：
- Geo 低分 → 尺寸與形狀不精確
- Topo 低分 → 網格結構異常
- Judge 低分 → 語意或視覺不合理
- Part 低分 → 零件分解與組裝錯誤

這種設計使研究者能定位失敗的具體環節，而非僅得到一個籠統的「好」或「壞」。

#### 與現有研究的比較

P3D-Bench 在基準測試生態系中的定位可從 Table 1 的比較中清晰看出：

**1. 與程式碼基準的比較 (SWE-bench)**

SWE-bench 評估的是程式碼修復能力，僅測試程式是否能通過測試，與 3D 幾乎無關。P3D-Bench 將程式碼生成與 3D 幾何執行結合，要求程式碼不僅能執行，還需產生幾何精確的結果。

**2. 與空間推理基準的比較 (InfiniBench, Theory of Space)**

這些基準評估的是空間佈局推理，但通常以抽象題目或 2D 圖形呈現。P3D-Bench 將空間推理具體化為 3D 零件佈局與組裝，要求模型在可執行的 3D 環境中驗證其空間推論。

**3. 與網格生成基準的比較 (T3Bench, 3DGen-Bench)**

這些基準評估的是直接生成網格 (mesh) 的視覺品質，不涉及程式碼或參數化結構。P3D-Bench 的獨特之處在於評估「程式作為 3D 表示」的品質，這使得設計的可編輯性與結構清晰度成為可評測的維度。

**4. 與程序化 3D 生成基準的比較 (VoxelCodeBench, 3DCodeBench)**

這些基準與 P3D-Bench 最為接近，都評估程式碼生成的 3D 內容。但 P3D-Bench 的差異化在於：(a) 涵蓋四種輸出格式而非單一格式；(b) 包含組裝任務；(c) 明確評估零件級結構；(d) 強調參數化精確度 (parametric accuracy)。

**5. 與 CAD 生成基準的比較 (Text2CAD-Bench, UniCAD, BenchCAD, MUSE)**

這些基準專注於 CadQuery 格式的 CAD 生成。P3D-Bench 不限於 CadQuery，而是涵蓋四種格式，並明確將「參數化精確度」與「零件級結構」列為評測維度，填補了現有基準的空白。

**6. 領域專用模型與通用模型的比較**

論文將領域專用模型 (domain-specific models) 作為參考點，與通用 MLLM/LLM 進行比較。這種設計揭示了一個重要問題：通用模型是否能在參數化 3D 生成上超越專用模型？目前的實驗結果暗示，專用模型在精確幾何上仍有優勢，但通用模型在語意理解與靈活性上更具潛力。

**7. 局限性**

- **資料集規模**：400 + 400 + 203 的規模相對有限，可能無法完全覆蓋所有設計領域。
- **格式偏重**：雖然支援四種格式，但不同格式的案例數量可能不均衡，影響跨格式比較的公平性。
- **MLLM 判斷的偏見**：使用 MLLM 作為 Judge 可能引入模型偏見，尤其當評測對象也是 MLLM 時。
- **靜態評測**：目前的評測是單輪的，未涵蓋 agentic 迴圈 (agentic loop) 中迭代修訂的情境。

#### 可重現性評估

P3D-Bench 的可重現性可從以下幾個面向評估：

**1. 資料集可及性**

論文明確描述了 P3D-Dataset 的建構管線，從 Text2CAD v1.1 與 Fusion 360 Gallery 兩個公開來源出發，經過可追蹤的篩選、註解與驗證步驟。這兩個來源本身是公開可得的，使得資料集建構過程具有可重現性。然而，論文中未明確說明 P3D-Dataset 是否會隨論文一同釋出，以及其授權方式。若資料集本身不公開，則第三方研究者難以獨立驗證實驗結果。

**2. 評測管線的標準化**

論文的「執行-渲染-評分」流程基於成熟的開源工具（CadQuery、OpenSCAD、Three.js），這些工具本身具有良好的可重現性。評測指標（Geo、Topo、Judge、Part）的計算方式若能在論文中以公式或演算法形式明確給出，將有助於重現。

**3. 模型評測的完整性**

論文評測了「前沿 MLLM」(frontier MLLMs)、「純文字 LLM」(text-only LLMs) 與領域專用模型，但未列出具體的模型名單與版本號。對於基準測試而言，明確列出受測模型的完整識別資訊（如 GPT-5.5 的具體版本、API 呼叫參數等）是可重現性的基本要求。

**4. 開源程式碼的可用性**

論文中未明確提及是否會釋出評測程式碼。對於一個基準測試而言，開源評測腳本是至關重要的——它使其他研究者能在 P3D-Bench 上評測自己的模型，並與論文的結果進行比較。

**5. 整體可重現性評級**

基於現有資訊，P3D-Bench 的可重現性處於中等水平。資料來源公開、評測流程基於成熟工具，但資料集本身與評測程式碼的釋出狀態尚不明確。建議論文作者在最終版本中補充：(a) P3D-Dataset 的公開連結與授權；(b) 評測程式碼的 GitHub 倉庫；(c) 受測模型的完整清單與版本資訊。

#### 未來研究方向

P3D-Bench 的發表為參數化 3D 生成領域開啟了多條值得探索的研究路徑：

**1. 增強幾何精確度的專用架構**

論文的發現——語意對齊強但幾何對齊弱——暗示需要專門增強 MLLM 的精確數值推理能力。未來研究可探索：

- 在 MLLM 訓練中加入 CAD 專用資料，使模型學習精確的尺寸與公差概念。
- 結合符號推理 (symbolic reasoning) 與神經生成，使模型能在語意理解與數值精確性之間取得平衡。
- 開發專門的「參數感知」(parameter-aware) 模組，使模型能更可靠地處理數值規格。

**2. 零件級結構推理的突破**

PartMatchF1 ≈ 0.5 的結果顯示，零件級建模是當前最大的瓶頸。未來方向包括：

- 將「零件分解」(part decomposition) 與「零件重建」(part reconstruction) 解耦為兩個子任務，分別優化。
- 引入層級式生成 (hierarchical generation)：先生成零件清單與空間關係，再生成每個零件的詳細幾何。
- 借鑒 ArtiCAD 與 ArtiCraft 的關節建模思路，將零件間的運動學約束 (kinematic constraints) 納入考量。

**3. Agentic 迴圈與迭代修訂**

目前的評測是單輪的，但實際設計過程中，模型會透過執行與視覺回饋進行迭代修訂。未來可探索：

- 將 P3D-Bench 擴展為多輪評測，允許模型根據渲染結果修改程式碼。
- 設計專門的「錯誤診斷」指標，評估模型是否能識別自身生成的幾何錯誤。
- 結合強化學習 (reinforcement learning) 與幾何回饋，訓練模型在迭代中自我改進。

**4. 多格式泛化與格式轉換**

P3D-Bench 支援四種輸出格式，但模型在不同格式上的表現可能差異顯著。未來研究可探索：

- 格式無關的 3D 表示學習，使模型能在不同格式間無縫轉換。
- 跨格式的遷移學習，例如在 CadQuery 上訓練的模型如何泛化到 OpenSCAD。
- 統一格式標準的可能性，例如開發一種「中間表示」(intermediate representation) 作為不同格式間的橋樑。

**5. 領域專用模型與通用模型的融合**

論文的實驗顯示，領域專用模型在精確幾何上仍有優勢。未來可探索：

- 將領域專用模型作為「幾何驗證器」(geometry verifier)，與通用 MLLM 的「語意生成器」(semantic generator) 結合。
- 開發混合架構，使通用模型負責高層設計意圖，專用模型負責低層幾何執行。
- 探索蒸餾 (distillation) 技術，將專用模型的幾何精確性蒸餾到通用模型中。

**6. 評測方法的深化**

P3D-Bench 的評測方法本身也有改進空間：

- 引入人類專家評測 (human expert evaluation) 作為 MLLM 判斷的補充或對照。
- 開發更細粒度的零件級指標，例如零件間的對齊誤差、裝配公差等。
- 探索「可編輯性」(editability) 的量化評測，例如修改一個尺寸後整體設計的合理性能否保持。

**7. 應用領域的擴展**

P3D-Bench 目前主要基於機械 CAD 案例，未來可擴展至：

- 建築資訊模型 (BIM) 的參數化生成。
- 電子設計自動化 (EDA) 中的電路板與晶片佈局。
- 機器人設計中的機構與運動學建模。
- 遊戲與動畫中的程序化資產生成。

這些方向的共同核心是：將 MLLM 的語意理解與世界知識 (world knowledge) 與精確的工程參數化設計相結合，使 AI 不僅能「畫出」物件，更能「設計出」可製造、可編輯、可驗證的工程產物。P3D-Bench 作為首個專注於此目標的基準測試，為這條研究路徑提供了重要的評測基礎。

## 論文問答

**Q1：為什麼需要專門的基準測試來評估參數化 3D 生成？現有的基準測試為何無法滿足這個需求？**

A：現有的基準測試各自只涵蓋參數化 3D 生成所需的部分能力，卻無法同時評估這些能力的綜合表現。程式碼基準（如 SWE-bench）僅檢查程式是否能編譯並通過測試；空間推理基準（如 InfiniBench、Theory of Space）僅評估物件佈局與關係推理；文字到 3D 基準（如 T3Bench、3DGen-Bench）則只關注生成形狀的視覺品質。然而，參數化 3D 生成要求模型同時具備這些能力——生成的程式不僅要能編譯為有效幾何，還必須透過推論零件結構與組裝關係，產出視覺合理且幾何精確的結果。P3D-Bench 的提出正是為了填補這個缺口，提供一個能夠聯合評估可執行性、幾何保真度、拓撲、文字約束對齊與零件級結構的統一基準。

**Q2：參數化 3D 生成與傳統的網格生成相比有何根本差異？為什麼這種差異很重要？**

A：參數化 3D 生成與傳統網格生成的根本差異在於表示方式的本質：網格僅記錄物件的外觀（頂點與面），而參數化 3D 程式則以程式碼形式明確表達設計的維度、建構運算與零件關係。這種差異至關重要，因為參數化程式是可編輯的明確表示——其尺寸、建構步驟與零件分解都寫在程式碼中，重新執行時可使用不同參數產生新的有效模型。這意味著參數化 3D 不僅僅是視覺重建，而是結構與設計意圖的恢復，能揭示模型是否真正理解設計的內在邏輯，而不僅僅是模仿其外觀。

**Q3：為什麼組裝任務（Assembly-3D）被認為是最困難的設定？這對評估模型能力有何啟示？**

A：組裝任務之所以最困難，是因為它要求模型同時具備單一零件的幾何生成能力以及跨零件的空間關係與結構組合能力。相較於 Text-to-3D 只需生成單一零件、Image-to-3D 需從單一視角推論多零件物件，Assembly-3D 還加入了組裝級與零件級的文字註解，要求完整的組裝結果。實驗結果顯示，即使是最強的 MLLM 在組裝任務上的 PartMatchF1 也僅約 0.5，意味著模型不僅在空間中錯誤放置零件，更在零件數量與個別幾何上恢復不佳。這啟示我們，當前的 MLLM 雖然具備一定的視覺與程式碼生成能力，但在多零件結構推理與精確空間組合方面仍有顯著不足。

**Q4：P3D-Bench 的核心設計理念是什麼？它如何統一評估不同任務和輸出格式？**

A：P3D-Bench 的核心設計理念是「以程式碼為媒介的統一評測」，透過執行程式並渲染結果來客觀評估生成品質。它涵蓋三個任務類別（Text-to-3D、Image-to-3D、Assembly-3D）並支援四種輸出格式（JSON、OpenSCAD、CadQuery、Three.js），所有輸出都會被統一執行並渲染，再從幾何、拓撲、MLLM 判斷與零件結構四個維度評分。這種設計使得不同輸入規格與目標格式之間能夠公平比較，避免了傳統基準測試中「各說各話」的問題，並能精確區分「程式能執行」與「程式產生正確幾何」這兩個層次的能力差異。

**Q5：P3D-Bench 採用了哪些評測指標？為什麼需要從多個維度來評估？**

A：P3D-Bench 採用了四個維度的評測指標：幾何（Geometry，幾何保真度）、拓撲（Topology）、MLLM 判斷（Judge，基於 MLLM 的多視角語意對齊評估）以及零件（Part，零件級結構）。需要多維度評估是因為單一指標無法完整捕捉參數化 3D 生成的品質——一個程式可能執行成功且視覺上看似合理，卻在精確尺寸上與規格不符；也可能語意上對應正確的物件，卻在拓撲結構上存在缺陷。透過結合可執行性、幾何精確度、語意對齊與零件級結構等多重視角，P3D-Bench 能更細緻地揭示模型在不同能力維度上的強弱。

**Q6：P3D-Dataset 的建構流程有何特點？如何確保資料品質？**

A：P3D-Dataset 的建構流程從 Text2CAD v1.1 與 Fusion 360 Gallery 兩個 CAD 資料源出發，經過篩選模糊模型、移除近重複樣本，並依複雜度等級平衡資料分佈，再生成各任務所需的描述性規格、參數化規格以及組裝級與零件級註解，最後進行自動化驗證。這種多階段流程的特點在於同時兼顧了資料的品質與任務的多樣性：透過過濾與平衡確保資料乾淨且具代表性，透過註解生成賦予每筆資料支援三種任務所需的結構化資訊，並透過自動化驗證保證註解的正確性，最終形成 400 個文字案例、400 個影像案例與 203 個組裝案例的標準化資料集。

**Q7：P3D-Bench 評估了哪些模型？為什麼要同時評估前沿 MLLM、純文字 LLM 和領域專用模型？**

A：P3D-Bench 評估了前沿 MLLM（如 GPT-5.5 等）、純文字 LLM 以及領域專用模型（如 Text2CAD 等）。同時評估這三類模型的目的在於建立多層次的比較基準：前沿 MLLM 代表當前通用模型在多模態理解與程式碼生成上的最先進能力；純文字 LLM 用於對照，揭示視覺輸入對任務表現的實際貢獻；領域專用模型則作為參考點，顯示專門訓練的模型在特定任務上的優勢與局限。這種三方對比不僅能揭示不同模型類型的能力邊界，也能幫助研究者理解哪些能力來自通用預訓練、哪些需要領域專門化才能獲得。

**Q8：評估結果揭示了哪些關鍵發現？這些發現對未來研究有何啟示？**

A：評估揭示了三個關鍵發現：第一，組裝是最困難的設定，模型仍無法將多個零件組合成一致性結構；第二，模型通常能恢復目標物件的全域形狀與語意身分，卻難以重現輸入所指定的精確參數化幾何（最強 MLLM 的 J-Sem 約 0.8，但 J-Geo 僅約 0.35）；第三，在組裝任務中，零件級建模仍然薄弱，最強 MLLM 的 PartMatchF1 僅約 0.5。這些發現對未來研究的啟示在於：提升參數化 3D 生成品質的關鍵不在於語意理解，而在於精確的尺寸與幾何推理；同時，零件級結構推理需要新的方法論突破，而非僅靠擴大模型規模或訓練資料。

**Q9：在不同任務和格式上，模型的表現有何差異？這反映了什麼？**

A：模型在不同任務上的表現呈現明顯的難度梯度：Text-to-3D 相對最易，Image-to-3D 因需從單一視角推論未見幾何而更難，Assembly-3D 則因需同時處理多零件與空間關係而成為最難設定。在格式方面，JSON、OpenSCAD、CadQuery 與 Three.js 各有其語法特性，模型表現會因訓練資料中對應格式的暴露程度而異。這種差異反映了兩個重要現象：一是視覺資訊的單視角限制對幾何推論構成根本挑戰；二是模型對不同程式語言與 CAD 框架的掌握程度不均，凸顯了訓練資料偏差對通用模型在特定領域表現的深遠影響。

**Q10：P3D-Bench 的研究成果對實際的 CAD 設計工作流程有何影響？**

A：P3D-Bench 的研究成果對實際 CAD 設計工作流程的影響主要體現在兩個方面：首先，它揭示了當前 MLLM 在精確參數化幾何上的不足，提醒設計實務工作者不能完全依賴通用模型進行生產級 CAD 設計，仍需領域專用工具或人工校驗；其次，它為 CAD 工具整合 AI 助手提供了明確的改進方向——未來的 CAD 系統應結合 MLLM 的語意理解能力與專門的幾何推理模組，以兼顧設計意圖理解與尺寸精確性。這也意味著在短期內，AI 輔助 CAD 更適合用於概念設計與快速原型，而非最終的製造級設計。

**Q11：這項研究對 3D 生成領域的產業應用有何意義？**

A：這項研究對 3D 生成領域的產業應用具有重要的指導意義。它明確指出，僅憑「能執行程式」並不足以支撐工業級應用，產業界在採用 AI 生成 3D 模型時，必須區分「視覺原型」與「可製造設計」兩個層次。對於遊戲、影視等對視覺品質要求高但對精確尺寸容忍度較高的場景，當前 MLLM 已具備一定實用價值；但對於機械工程、工業設計等需要精確參數化幾何的場景，則仍需領域專用模型或人機協作流程。此外，P3D-Bench 提供的標準化評測協議也將促進產業內不同 AI 工具之間的公平比較，加速技術成熟。

**Q12：這項基準測試如何推動多模態大型語言模型在結構推理方面的發展？**

A：P3D-Bench 透過將結構推理能力具體化、可測量化，推動 MLLM 在此方向的發展。它不僅評估最終輸出的視覺品質，更深入檢驗模型是否能恢復零件數量、空間關係與組裝層級——這些都是傳統基準測試忽略的維度。這種評測壓力將促使研究者開發新的方法來增強 MLLM 的結構推理能力，例如引入顯式的空間推理模組、結合符號推理與神經生成、或設計專門的預訓練任務來學習 CAD 結構先驗。同時，公開的基準與資料集也降低了相關研究的進入門檻，吸引更多團隊投入這個方向。

**Q13：P3D-Bench 目前存在哪些局限性？**

A：P3D-Bench 目前存在幾個明顯的局限性：首先，資料規模相對有限（400 文字、400 影像、203 組裝案例），可能無法完全覆蓋真實世界中 CAD 設計的多樣性與複雜度；其次，評測依賴 MLLM 進行部分判斷（如 Judge 維度），這引入了評估者的偏見風險；再者，目前僅支援四種輸出格式，無法涵蓋所有 CAD 生態系統；最後，組裝任務的評測主要集中在零件數量與幾何匹配，對於更細緻的物理合理性（如公差配合、力學合理性）尚未充分評估。這些局限性提示我們，P3D-Bench 是一個起點而非終點。

**Q14：模型在哪些方面最容易失敗？失敗案例揭示了什麼問題？**

A：模型最容易失敗的方面集中在三個層次：在幾何層次，模型難以精確重現指定的尺寸與比例，即使語意正確，參數化數值仍常有偏差；在結構層次，模型經常生成錯誤數量的零件，或將零件放置在不正確的相對位置上；在組合層次，模型難以維持零件之間的組裝一致性，例如連接關係、對齊約束等。這些失敗案例揭示了當前 MLLM 的根本問題：它們擅長從大量資料中學習表面模式，卻缺乏精確的數值推理與三維空間組合能力，這是純粹擴大模型規模或訓練資料可能無法解決的結構性挑戰。

**Q15：未來的研究方向有哪些？基準測試本身可以如何擴展？**

A：未來研究方向可從兩個層面展開：在模型層面，需要探索結合符號推理與神經生成的新架構、引入專門的 CAD 預訓練任務、設計更好的 agentic 迴圈以支援迭代修正；在基準測試層面，P3D-Bench 可從多方向擴展——增加更多任務類型（如物理模擬、機構運動）、擴大資料規模與多樣性、引入更細緻的評測指標（如公差分析、製造可行性）、支援更多輸出格式與領域（如機械、建築、電子設計）。此外，加入互動式評測（如讓模型根據回饋迭代改進）以及人機協作評測框架，也將是重要的發展方向，能更全面地反映真實應用場景中的模型能力。

## 實務應用指南

### 適用場景

P3D-Bench 所評測的「從文字或影像規格生成可執行的參數化 3D 程式」能力，在以下場景具有明確的實務價值：

1. **工業設計與快速打樣**：設計師以自然語言或參考圖描述產品意圖（例如「一個直徑 80mm、高 120mm、底部有 M6 螺孔的圓柱體」），由 MLLM 直接生成 CadQuery 或 OpenSCAD 代碼，設計師再以參數微調尺寸，縮短從概念到可製造模型的時間。

2. **CAD 教育與技能訓練**：教師可將 P3D-Bench 的「文字規格 → 程式碼」對作為教材範例，讓學生比較自己撰寫的 CadQuery 程式與基準答案在幾何保真度（Geo）、拓撲（Topo）與零件結構（Part）上的差異，學習如何寫出符合工程意圖的參數化模型。

3. **逆向工程輔助**：當只有單張產品照片時，工程師可借助 Image-to-3D 任務的能力，讓模型推測多零件結構與佈局，再由人工修正無法從單一視角還原的隱藏幾何，作為後續量測與重建的起點。

4. **組裝級機構設計驗證**：在機器人、家具或機械設備的概念設計階段，使用 Assembly-3D 任務評估模型是否能同時產出多個零件並維持正確的空間關係，作為「AI 是否能勝任組裝設計」的早期篩選工具。

5. **領域專用模型選型基準**：企業在導入 CAD 生成式 AI（例如 ArtiCAD、ArtiCraft 等代理式系統）時，可將 P3D-Bench 的四項分數（Geo、Topo、Judge、Part）作為供應商宣稱能力的客觀驗證依據，避免僅憑視覺樣本判斷模型優劣。

### 實作前置條件

**資料面**
- 需取得 **Text2CAD v1.1**（Khan et al., 2024）與 **Fusion 360 Gallery**（Willis et al., 2021）作為原始 CAD 來源，並依 P3D-Dataset 的流程進行篩選（去除模糊模型、近重複樣本）、跨複雜度等級平衡。
- 需準備每個案例的「描述性規格」、「參數化規格」、「組裝級註解」與「零件級註解」，並通過自動驗證。
- 評估階段需準備每個案例的 ground-truth 3D 模型（用於計算幾何與零件比對）以及多視角渲染圖（用於 MLLM-based Judge）。

**算力面**
- 推論端：執行前沿 MLLM（如 GPT-5.5 等）需具備 API 存取權或本地 GPU（建議 ≥ 24GB VRAM 用於 7B–13B 等開源模型）。
- 執行端：每個生成的程式需在沙箱中執行（CadQuery、OpenSCAD、Three.js、JSON 解析器），並透過 Blender 或等效渲染器產出多視角影像；CPU 渲染時間隨零件數量線性增加，組裝案例建議預留每案 30–120 秒。
- 評估端：MLLM-based Judge 需額外一次模型呼叫，總成本約為生成成本的 1.5–2 倍。

**技能面**
- 熟悉至少一種目標格式（CadQuery 為主，OpenSCAD / Three.js / JSON 為輔）。
- 具備 MLLM 提示工程（prompt engineering）經驗，特別是針對結構化輸出與多步推理。
- 了解基本 CAD 概念（草圖、擠出、布林運算、零件關係）以正確解讀評估結果。
- 具備 3D 幾何處理經驗（網格比對、拓撲檢查、座標系對齊）以自訂或擴充評估指標。

### 實作步驟建議

1. **釐清目標任務與格式**：先決定要評估 Text-to-3D、Image-to-3D 還是 Assembly-3D，並選定輸出格式。建議從 CadQuery 開始，因為它在文獻中支援最完整、且 P3D-Bench 的基準結果多以此格式呈現。

2. **建置或取得 P3D-Dataset 子集**：完整資料集為 400 文字 + 400 影像 + 203 組裝案例。初期可先用 50–100 案例的子集驗證流程，再逐步擴大。務必保留「描述性規格」與「參數化規格」兩種輸入，因為它們對應不同的評估難度。

3. **準備執行與渲染管線**：建立沙箱環境，依格式安裝對應依賴（CadQuery 透過 conda 或 Docker、OpenSCAD 透過 CLI、Three.js 透過 Node.js + headless browser）。撰寫一個統一介面，接收程式字串、執行、回傳渲染網格與多視角影像，並捕捉例外以計算 Valid（可執行率）。

4. **設計提示詞模板**：為每個任務與格式撰寫專屬 prompt，明確要求模型輸出「單一完整程式區塊」，並指定座標系、單位（建議 mm）與零件命名規則。對 Assembly-3D，提示詞需引導模型先列舉零件清單再寫程式，以降低漏件率。

5. **串接候選模型**：依序評估（a）前沿通用 MLLM、（b）純文字 LLM（僅 Text-to-3D）、（c）領域專用模型作為參考點。記錄每次推論的耗時、token 用量與 Valid 比例，作為成本/品質取捨依據。

6. **執行四維評估**：
   - **Geo**：將生成網格對齊 ground-truth 後計算 IoU / Chamfer 距離。
   - **Topo**：檢查零件數量、封閉性、自相交、布林運算一致性。
   - **Judge**：呼叫 MLLM 對多視角渲染圖與輸入規格進行語意與約束對齊評分。
   - **Part**：以零件分割與匹配演算法計算 PartMatch F1，特別關注 Assembly-3D。

7. **分析失敗模式並迭代**：依據論文的三大發現（組裝最難、幾何對齊遠難於語意對齊、零件級建模弱）建立分類標籤，統計各模型的失敗分布，找出是「程式無法執行」、「幾何偏差過大」還是「零件結構錯誤」，再針對性調整 prompt 或後處理。

8. **產出可比較的報告**：以表格形式彙整 Valid、Geo、Topo、Judge、Part 五項分數，並附上代表性成功/失敗案例的渲染圖，便於跨模型、跨格式、跨任務的橫向比較。

### 潛在風險與注意事項

- **「可執行 ≠ 正確」的陷阱**：論文顯示即使 Valid 比例高，模型仍可能在幾何精度（J-Geo ≈ 0.35）上大幅落後於語意對齊（J-Sem ≈ 0.8）。實作時切勿僅以 Valid 率作為模型優劣的唯一指標，必須同時報告 Geo 與 Part 分數。

- **組裝任務的零件錯置**：Assembly-3D 是當前最弱的一環，模型不僅會放錯零件位置，還會搞錯零件數量與幾何。建議在評估報告中單獨列出組裝子集的分數，避免被單件任務的高分掩蓋。

- **MLLM-based Judge 的偏誤**：Judge 分數仰賴另一個 MLLM 對渲染圖打分，若評審模型與生成模型同源，可能產生自我偏好。建議至少使用兩個獨立的 MLLM 作為 Judge，並對評分標準做錨定（anchoring）以降低飄移。

- **座標系與單位不一致**：不同格式（CadQuery、Three.js、OpenSCAD）的預設座標方向與單位不同，若未在執行管線中強制統一，會導致 Geo 分數出現系統性偏差。建議在執行前顯式轉換至同一座標系（建議 Y-up、mm）。

- **資料集偏差**：P3D-Dataset 源自 Text2CAD 與 Fusion 360 Gallery，偏重機械零件與工程物件，對有機形體、軟體物件或抽象設計的代表性不足。導入至非機械領域時，應自行補充領域案例並重新驗證。

- **評估成本失控**：完整評估 1003 個案例 × 多模型 × 多格式，僅 Judge 階段就可能消耗數十萬 token。建議先以小樣本估單價，再決定是否採用抽樣評估或蒸餾後的輕量 Judge。

- **領域專用模型並非萬靈藥**：論文中領域專用模型作為「參考點」而非「上限」，其表現未必全面優於前沿通用 MLLM。選型時應以 P3D-Bench 的四維分數為依據，而非僅憑「專用」標籤。

### 與其他技術的整合建議

- **與既有 CAD/CAM 系統整合**：將 P3D-Bench 的執行管線包裝為 CLI 或 REST API，使其輸出可直接匯入 Fusion 360、SolidWorks 或 FreeCAD。建議保留 CadQuery 的 `.step` 匯出路徑，以利下游 CAM 軟體接手。

- **與 PLM/PDM 系統整合**：把每個案例的「描述性規格 → 程式碼 → 渲染圖 → 評估分數」打包為一個工件（artifact），存入 Teamcenter 或 Windchill 等 PLM 系統，建立可追溯的設計決策紀錄。

- **與代理式（agentic）生成管線整合**：論文中提及的 ArtiCAD、ArtiCraft 等代理式系統會反覆「生成 → 執行 → 修正」。可將 P3D-Bench 的四維評分作為代理的回饋訊號（reward signal），用於強化學習或 best-of-N 篩選。

- **與 RAG 與企業知識庫整合**：將企業內部的 CAD 範本、設計規範與零件庫建立為向量庫，在生成前先檢索相似案例並注入 prompt，可望緩解「零件數量錯誤」與「幾何精度不足」兩大弱點。

- **與數位孿生（Digital Twin）平台整合**：將生成的參數化程式視為「可調整的數位孿生源」，透過修改參數快速產生多個變體，用於模擬、有限元素分析或製造公差分析。

- **與版本控制與 CI/CD 整合**：把評估腳本納入 GitHub Actions 或 GitLab CI，每次模型更新自動跑 P3D-Bench 子集並比對分數變化，避免退化（regression）悄悄上線。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第一節的「三大發現」，理解 P3D-Bench 想回答的核心問題是「AI 能否寫出可執行且精確的 3D 程式」，再瀏覽 Figure 2 認識任務、格式與評估維度的全貌。實際操作時，可從 Text-to-3D + CadQuery 的最小子集（10–20 案例）開始，親手跑一次生成、執行、評估的循環，比直接讀完所有指標定義更有感。

**給 AI 工程師**：重點放在 §3 的評估協議與四維評分實作，特別是 MLLM-based Judge 的 prompt 設計、座標系對齊、以及如何把 Valid / Geo / Topo / Judge / Part 串成一條可平行化的管線。論文中「幾何對齊遠難於語意對齊」的結論，是設計後處理（例如參考圖比對、尺寸約束檢查）的關鍵出發點。

**給研究者**：應深入 §3.2 的資料集建構流程（篩選、平衡、註解、驗證）以及 Table 1 的基準比較，這兩部分揭示了 P3D-Bench 相較於既有基準的獨特價值（同時涵蓋 Executable、Parametric、Spatial、Assembly、Part 五個維度）。後續可考慮擴充至更多格式（如 Blender Python）、更多領域（建築、有機形體），或將評估指標與人類專家評分做相關性研究。

**給產品經理**：聚焦於「適用場景」與「潛在風險」兩節，理解這項技術目前的成熟度邊界——它已能勝任單零件的概念發想與快速打樣，但在組裝級、零件級精度上仍不足以直接產出製造用模型。導入時建議設定務實的期望：把 P3D-Bench 的高分模型定位為「設計助理」而非「自動設計師」，並把評估分數納入供應商 SLA。
