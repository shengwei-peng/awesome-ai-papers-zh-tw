## 摘要翻譯

大型語言模型（LLM）日益廣泛地部署多層防禦機制，但惡意提示（malicious prompt）仍可能繞過這些防禦。可解釋性方法（interpretability method）能夠揭露生成路徑（generation path）上的模型內部訊號（model-internal signal），這些訊號可為強制執行（enforcement）提供資訊，但其本身並非安全控制機制（security control）。為安全目的採用這些訊號的部署，通常會將每個訊號與其各自的校準（calibration）、策略邏輯（policy logic）和介入程式碼緊密耦合，因此每個新產物（artifact）都產生整合工作（integration work），而非強化共享防禦（shared defense）。我們提出語言模型安全模組（LMSM），這是一個將 Linux 安全模組（LSM）背後的分離（separation）概念應用於 LLM 服務的安全框架（security framework）。在 LMSM 中，選定的安全後端（security backend）會暴露經校準的證據（evidence），版本化策略（versioned policy）會根據受信任的每請求上下文（trusted per-request context）評估作用中規則（active rule），而獨立的閘道（gate）則授權緩衝輸出釋放（buffered output release）。此設計將仲介正確性（mediation correctness）與策略有效性（policy effectiveness）分離，並允許後端、規則或排程（schedule）變更，而無需重建請求處理或強制執行。我們的原型（prototype）展示了此分離在實務上的運作：搭配 Hugging Face Transformers 與連續批次化 vLLM（continuously batched vLLM），相同的底層平台（substrate）可承載以產物為基礎的稀疏自動編碼器（artifact-backed sparse autoencoder, SAE）與轉碼器（transcoder）部署，以及任務擬合密集探針（task-fitted dense probe），並在排程器變動（scheduler churn）下保留請求特定的決策，且能針對每個請求選擇性地強制執行並組合多條規則。在 Qwen3-4B 上，LMSM-Checkpoint 將 HarmBench 攻擊成功率（attack success rate）從 39.20% 降至 3.32%，XSTest 誤拒絕率（false refusal）則從 2.40% 上升至 4.40%，同時在 32 個作用中序列（active sequence）下，保留對照的服務路徑（matched serving path）98.14% 的吞吐量（throughput），而該路徑不執行任何監控工作（monitoring work）。LMSM 為可解釋性與模型內部分析（model-internal analysis）的進展提供了一條通往執行期強制執行（runtime enforcement）的共同路徑。

### 核心貢獻（3～5點）
- 提出 LMSM 框架，將 LSM 的「分離」設計原則引入 LLM 服務，使安全後端、版本化策略與執行閘道彼此獨立。
- 區分仲介正確性與策略有效性，讓後端、規則或排程變更時無需重建請求處理或強制執行機制。
- 提供共享執行底層平台與共同後端合約，統一承載 SAE、transcoder 與 dense probe 等可解釋性產物。
- 在 Hugging Face Transformers 與連續批次化 vLLM 上實作原型，證明能在排程器變動下保留請求特定決策，並選擇性地組合多條規則。
- 在 Qwen3-4B 上驗證安全性與效能權衡：HarmBench 攻擊成功率從 39.20% 降至 3.32%，同時保留 98.14% 的對照服務吞吐量。

### 適合對象
從事 LLM 安全部署、模型可解釋性研究，以及大型語言模型服務架構設計的研究人員與工程師；特別適合希望將模型內部訊號轉化為可維護、可版本化之執行期安全控制機制的安全架構師與模型提供者。

## 深度分析

#### 方法論解析

LMSM（Language Model Security Modules，語言模型安全模組）的核心貢獻，是將「可解釋性產物（interpretability artifact）」與「執行期強制執行（runtime enforcement）」解耦，並參考 Linux Security Modules（LSM）的參考監控器原則（reference-monitor principle），建立一個可重複使用的共享執行底層平台（shared enforcement substrate）。傳統上，每一種模型內部防護機制（model-internal guard）都會自帶校準（calibration）、策略邏輯（policy logic）與介入程式，導致新增後端（backend）時必須重新設計請求處理與強制執行路徑；LMSM 則把這些功能拆成三個穩定介面：安全後端（security backend）、版本化策略評估器（versioned policy evaluator）與執行閘道（enforcement gate）。

**三項核心分離**

1. **後端合約（backend contract）**：後端負責從模型內部狀態產出已校準的證據（evidence）。無論是已發布的稀疏自動編碼器（sparse autoencoder，SAE）、轉碼器（transcoder），或是任務擬合密集探針（task-fitted dense probe），都必須符合共同介面，向策略評估器提供結構化的目標（target）·證據（evidence）·條件（condition）資訊。這使得後端替換不需要改變請求處理或閘道實作。

2. **版本化策略評估器（versioned policy evaluator）**：操作者（operator）透過版本化規則庫（versioned rule library）管理作用中規則（active rule）。評估器在受信任的每請求上下文（trusted per-request context）上執行比較（compare）、解析（resolve）與決策（decide），並處理規則排程（schedule）與組合（composition）。策略版本（policy version）的更新可以獨立於執行底層平台，讓「仲介正確性（mediation correctness）」與「策略有效性（policy effectiveness）」分開驗證。

3. **執行閘道（enforcement gate）**：閘道位於緩衝輸出釋放（buffered output release）之前，根據評估器的決策（decision）執行允許（allow）、拒絕並回覆固定訊息（refuse fixed reply）或終止（terminate）等動作。由於閘道操作的是服務端已緩衝的輸出，而非使用者可直接影響的提示通道，它形成了一個受信任的執行邊界。

**後端整合流程**

LMSM 支援兩種後端來源。第一種是「以產物為基礎（artifact-backed）」：操作者將已發表的 SAE 或 transcoder 等表徵（representation）進行綁定（bind）與校準（calibrate），即可對應到特定安全目標。第二種是「任務擬合（task-fitted）」：當沒有現成產物時，操作者使用領域內範例（in-domain example）學習或改編後端，例如擬合線性模型（fitted linear）。這兩種路徑在介面上無區別，差別僅在於產出來源（provenance）。

**與 vLLM 的整合**

原型實作以 Hugging Face Transformers 與連續批次化 vLLM（continuously batched vLLM）為基礎。由於 vLLM 的排程器（scheduler）會動態重用批次槽位（batch slot），LMSM 必須確保每個請求的決策狀態不會因排程器變動（scheduler churn）而錯置。論文顯示，在 32 對重複請求中，所有請求的動作、選定類別、介入步驟與每條規則的門檻跨越結果都完整保留，證明分離式設計在真實服務條件下仍然穩定。

#### 實驗數據解讀

評估主要圍繞四個面向：攻擊防禦效果、誤拒絕（false refusal）代價、服務吞吐量（throughput）損失，以及排程器變動與多規則組合下的穩定性。

**HarmBench 與 XSTest**

在 Qwen3-4B 上，LMSM-Checkpoint 將 HarmBench 攻擊成功率（attack success rate）從 39.20% 降至 3.32%，降幅超過九成；同時 XSTest 的誤拒絕率僅從 2.40% 微升至 4.40%。這組數據顯示，任務擬合密集探針能夠在大幅壓制有害輸出的同時，維持相對溫和的正常請求誤擋率。對於一個不需要重新訓練模型權重、僅透過後端證據與規則覆蓋（rule overlay）即可部署的安全框架而言，這樣的效能相當突出。

**吞吐量與規則組合**

在 32 個作用中序列（active sequence）的設定下，LMSM-Checkpoint 相較於一條完全不做監控工作（monitoring work）的對照服務路徑（matched serving path），仍保留 98.14% 的吞吐量。更進一步，當同時啟動 15 條作用中規則時，吞吐量仍達 96.89%。這說明策略評估器與執行閘道的額外計算成本極低，連續批次化的 overhead 主要來自後端證據提取，而非策略解析或規則組合。

**有害輸出率與後端比較**

任務擬合策略可降低「對照有害輸出率」82.5%–91.5%。這個範圍暗示不同後端或不同規則目標之間存在效果差異：以產物為基礎的 SAE/transcoder 與任務擬合 dense probe 各有適用場景。論文並未詳細拆解個別後端的數字，但從整體趨勢可推論，模型內部訊號（model-internal signal）確實能在生成路徑（generation path）上提供及時且有效的安全證據。

**Scheduler churn 穩定性**

所有 32 對重複請求在排程器移動與批次槽位重用後，仍保留相同的動作、類別、介入步驟與每條規則的門檻跨越向量。這是方法論中「受信任的每請求上下文」與「閘道授權緩衝輸出釋放」設計的關鍵驗證：即使底層 vLLM 的執行順序被打亂，安全決策仍繫結於請求本身，而非批次位置。

**綜合解讀**

實驗結果支持 LMSM 的核心主張：透過穩定的後端合約、版本化策略與獨立閘道，可以將可解釋性進展轉化為執行期安全控制，而不必為每個新產物重建防護堆疊（guard stack）。不過，3.32% 的攻擊成功率仍非零，且誤拒絕率翻倍，顯示後端校準與規則門檻仍有精進空間。

#### 與現有研究的比較

論文將現有 LLM 安全控制機制（security control）分為四大類，並以表 1 總結其控制點、優勢與限制：

1. **外部防護（external guards）**：如 LlamaGuard、NeMo Guardrails，作用於文字輸入輸出邊界。優點是模型無關且易更新；缺點是無法使用模型內部狀態，且必須在系統邊界對文字採取行動。
2. **提示控制（prompt controls）**：如 instruction hierarchy，在生成前調整模型上下文。優點是不需要執行期插樁；缺點是與對手共享同一條受對手影響的上下文通道，缺乏受信任的執行邊界。
3. **對齊訓練（alignment training）**：如 RLHF、DPO、Constitutional AI。優點是提供廣泛的模型層級安全預設；缺點是義務編碼在模型權重中，難以因應操作者特定或快速變化的規範。
4. **內部執行期方法（internal-runtime methods）**：如 circuit breakers、refusal directions、HiddenDetect。優點是可檢查或修改生成過程中的計算；缺點是通常將後端、校準與介入程式緊密耦合。

LMSM 的定位介於第四類與框架層之間：它保留了內部方法的觀測優勢，但透過共享執行底層平台將後端、策略與強制執行分離。相較於單一後端防護，LMSM 允許操作者疊加多條規則、切換後端來源，並在不重新訓練模型或不改寫強制執行程式的前提下更新策略版本。這是對現有「每個產物各自為政」現狀的結構性改進。

**限制**

LMSM 並未宣稱提供核心層級的隔離保證（isolation guarantee），僅借用 LSM 的分離概念；它仍需要受信任的執行期整合，且每個後端都需經過校準或擬合（fit）。此外，若後端本身被對手針對性繞過，閘道決策也會失效，因此後端品質仍是安全上限。

#### 可重現性評估

從提供的文本來看，論文並未明確指出是否公開原始碼、策略檔案或校準資料。然而，其所使用的基礎元件多為開放資源：

- **模型權重**：Qwen3-4B 為可公開取得之權重。
- **服務框架**：Hugging Face Transformers 與 vLLM 均為開源。
- **評測資料集**：HarmBench 與 XSTest 為公開安全評測基準。
- **可解釋性產物**：SAE 與 transcoder 相關實作在社群中已有開源參考。

**可能缺失的細節**

若要完整重現，仍需要以下資訊：LMSM 對 vLLM 的具體修改點（特別是連續批次化狀態與請求上下文的綁定方式）、後端合約的確切 API 與資料結構、SAE/transcoder 產物的下載位置與對應層級、密集探針的訓練資料與超參數、每條規則的門檻與組合邏輯，以及 LMSM-Checkpoint 的完整策略版本內容。

**重現難度評估**

在作者釋出原型程式碼與校準腳本的前提下，重現難度為中等：基礎環境易於搭建，但後端校準與規則調校需要領域資料與實驗迭代。若僅依賴論文描述，則重現難度偏高，因為執行閘道與 vLLM 的整合細節對結果影響甚大。

#### 未來研究方向

1. **多模態與工具使用擴展**：將 LMSM 的後端合約與閘道機制延伸至視覺語言模型、語音模型，以及具備工具呼叫（tool use）或代理流程（agentic workflow）的系統，使內部證據能涵蓋更多模態與行動決策點。

2. **串流生成而非僅緩衝輸出**：目前閘道授權的是緩衝輸出釋放；未來可研究如何在 token-by-token 串流場景中維持受信任的強制執行邊界，同時不犧牲使用者體驗。

3. **自動化校準與規則探勘**：發展從可解釋性產物自動推導規則條件與門檻的方法，降低操作者手動校準的成本，並提升跨模型遷移能力。

4. **後端對抗穩健性**：針對 SAE、transcoder 與 dense probe 設計對抗訓練或認證程序，確保後端證據在面對適應性攻擊時仍可靠。

5. **形式化驗證仲介正確性**：對執行閘道與策略評估器的互動進行形式化分析，證明在給定後端證據下，閘道決策滿足特定安全不變量（safety invariant）。

6. **混合外部與內部訊號**：將 LMSM 與外部防護（external guards）結合，讓外部模型無關檢查與內部模型狀態互補，並在策略層統一決策。

7. **隱私保護後端**：探索在不暴露原始模型內部啟動值的前提下，仍能提供足夠證據給策略評估器的技術，例如差分隱私或安全多方運算。

8. **動態規則排程與成本最佳化**：根據請求風險分數動態調整作用中規則數量與評估頻率，在安全性與吞吐量之間取得更細緻的權衡。

9. **標準化後端合約**：推動產業與學界共同制定模型內部安全後端的互通標準，使不同研究團隊的產物能直接插入 LMSM 類型的框架。

10. **降低誤拒絕率**：進一步研究規則門檻、後端組合與上下文感知條件，以將 XSTest 等正常請求的誤拒絕率壓至更低，同時維持高攻擊阻擋率。

## 論文問答

## 【背景與動機】

**Q1：LMSM 主要想解決什麼問題？**

A：LMSM 針對的是大型語言模型在實際部署中，惡意提示仍能繞過層層防禦的問題。雖然可解釋性方法能揭露模型生成路徑上的內部訊號，但這些訊號本身並不是安全控制機制。更糟的是，現有部署往往把每個新產物都與各自的校準、策略邏輯和介入程式碼綁在一起，導致每次新增防禦工件都變成額外的整合工作，而非強化共享的執行期防線。

**Q2：為什麼現有的模型內部執行期方法不足以應對這個問題？**

A：現有的內部執行期方法通常把單一後端、校準流程、策略判斷與介入實作緊密耦合在一起，形成彼此獨立的防護堆疊。這種設計讓不同後端無法共享同一套強制執行路徑，也無法隨著策略需求快速演進。結果是操作者必須為每種新產物重建請求處理與執行邏輯，無法像傳統安全框架那樣把仲介正確性與策略有效性分開。

**Q3：為什麼「仲介正確性」與「策略有效性」的分離對 LLM 安全很重要？**

A：這種分離讓策略可以獨立演進，而不需要每次改規則就重建整個生成與執行路徑。對實際服務而言，操作者常面臨司法管轄區或組織層級的快速變動義務，例如禁止提供特定病人劑量建議，這些需求無法完全依賴模型提供者預先對齊。透過把後端證據、版本化規則與執行閘道拆開，LMSM 讓操作者能在不改變模型權重的情況下疊加專屬規則。

## 【方法與創新】

**Q4：LMSM 的三大核心元件各自扮演什麼角色？**

A：第一個元件是安全後端，負責暴露經過校準的模型內部證據，例如 SAE、轉碼器或密集探針的輸出。第二個元件是版本化策略評估器，它會根據受信任的每請求上下文，解析作用中規則的觸發條件與組合方式。第三個元件是執行閘道，負責在緩衝輸出釋放前做出最終決策，例如允許、終止或回覆固定拒絕訊息。

**Q5：相較於傳統 Linux Security Modules，LMSM 的關鍵創新是什麼？**

A：LMSM 借鏡的是 LSM 的「分離」設計哲學，而非複製核心層級的隔離保證。它把後端選擇、版本化規則庫與輸出授權閘道解耦，使得新增後端只需要綁定、校準與必要時的擬合，而不用重新設計請求處理或執行路徑。這讓「如何正確執行強制措施」與「規則是否有效」成為兩個可以獨立演進的問題。

**Q6：LMSM 為什麼要區分「以產物為基礎」與「任務擬合」兩種後端供應方式？**

A：這兩種方式的區別在於產物來源，而非表徵形式：以產物為基礎時，操作者直接綁定並校準已釋放的表徵，例如 SAE 或轉碼器；任務擬合時，則是從領域內範例學習或大幅調整後端。這樣的設計讓操作者可以根據可用資源與目標選擇最適合的後端，同時兩種路徑都能使用稀疏或密集表徵。最重要的是，無論採用哪種供應方式，都不需要改變模型權重或底層執行路徑。

## 【實驗與結果】

**Q7：論文使用了哪些評測基準與指標來驗證 LMSM？**

A：主要的安全評測基準包括 HarmBench 與 XSTest，分別用來衡量攻擊成功率與誤拒絕率。服務效能方面則以吞吐量為指標，並在 32 個作用中序列的條件下與關閉監控的對照服務路徑比較。此外，作者也進行了規則組合實驗，同時啟動 15 條規則，並檢驗排程器變動下請求決策是否保持一致。

**Q8：LMSM-Checkpoint 在實驗中取得了哪些關鍵量化結果？**

A：在 Qwen3-4B 上，LMSM-Checkpoint 將 HarmBench 攻擊成功率從 39.20% 降至 3.32%，顯著降低有害輸出風險。相對地，XSTest 的誤拒絕率從 2.40% 微升至 4.40%，顯示安全性提升伴隨輕微的過度保守。在吞吐量方面，與完全關閉監控的對照路徑相比，LMSM-Checkpoint 在 32 個作用中序列下保留了 98.14% 的吞吐量，而在 15 條規則同時作用時仍保留 96.89%。

**Q9：實驗中有哪些關於穩健性與後端替換的發現？**

A：在排程器變動的測試中，全部 32 組重複請求對都完整保留了動作、選定類別、介入步驟，以及每條規則閾值跨越結果的完整向量。這證明 LMSM 的分離設計能夠在連續批次化 vLLM 的排程器重排與批次槽位重用下維持決策一致性。此外，任務擬合策略能將對應有害輸出率降低 82.5% 至 91.5%，而替換後端綁定不需要修改請求處理、評估器介面或執行閘道。

## 【應用與影響】

**Q10：論文中的遠距醫療範例如何具體說明 LMSM 的應用？**

A：在遠距醫療服務中，操作者可能需要禁止模型提供針對特定病人的劑量指示，這是司法管轄區規定的義務，而非模型提供者預先對齊的範圍。操作者可以綁定一個與該目標對齊的 SAE 或轉碼器產物，並校準一條劑量建議規則；若沒有合適產物，也可以從領域內範例擬合後端。這條規則進入版本化規則庫後，執行閘道會在生成過程中攔截被禁止的緩衝回應，並以設定的固定訊息取代。

**Q11：從產品部署角度來看，LMSM 有哪些實務優勢？**

A：LMSM 的原型直接建立在 Hugging Face Transformers 與連續批次化 vLLM 之上，對現代 LLM 服務基礎設施具有良好的相容性。由於後端、規則與排程變更都被侷限在各自的介面內，操作者可以逐步新增或更新安全規則，而不需要重寫整個請求處理管線。實驗也顯示其吞吐量損失極小，這對延遲敏感與高併發的產品環境來說是關鍵優勢。

**Q12：LMSM 對整個 LLM 安全領域可能帶來什麼影響？**

A：LMSM 為可解釋性與模型內部分析的最新進展提供了一條通往執行期強制執行的共同路徑。它讓操作者能夠在模型提供者對齊之外，疊加符合自身法規與業務需求的規則，從而縮短研究產物到實際防禦的距離。這種架構也有助於建立更清晰的責任分界：模型提供者專注於基礎對齊，操作者則負責部署特定的安全策略。

## 【限制與未來方向】

**Q13：論文承認 LMSM 有哪些主要限制？**

A：LMSM 借鏡的是 LSM 的分離設計，而非作業系統核心提供的隔離保證，因此它仍然依賴受信任的執行期整合環境。每個後端仍需要專屬的校準或擬合工作，這並非完全自動化。此外，目前的評估主要集中在 Qwen3-4B 模型上，對於更大規模或分散式服務設定的泛化性仍需進一步驗證。

**Q14：LMSM 在哪些情況下可能失效或表現不佳？**

A：如果後端校準不當，閾值可能過高而漏掉攻擊，或過低而產生大量誤拒絕，實驗中 XSTest 誤拒絕率上升就是一例。面對專門針對內部表徵設計的對抗提示，現有後端證據也可能被繞過。此外，若策略規則在解碼過程中的不同時間點觸發，而緩衝與排程機制未能妥善保存每請求上下文，則可能導致時間性決策錯誤。

**Q15：未來研究可以朝哪些方向延伸 LMSM？**

A：未來可以擴充更多類型的安全後端，例如基於電路斷路器、拒絕方向或其他可解釋性產物的後端，並發展自動化校準工具以降低操作門檻。也可以探索更豐富的規則組合語意，例如條件式、權重式或階層式策略，並對仲介正確性進行形式化驗證。最後，將 LMSM 擴展到更大模型、多模態生成與分散式推論服務，將是驗證其實用價值的重要下一步。

## 實務應用指南

### 適用場景

1. **遠距醫療問答服務的合規防護**  
   服務已部署對齊模型，但司法管轄區要求不得輸出針對特定病人的劑量指示。操作者可將「劑量建議規則」綁定到已發布的 SAE 或轉碼器產物，或從領域內範例擬合一個密集探針後端，透過 LMSM 的執行閘道攔截並以固定回覆替代違規輸出，無需重新訓練模型。

2. **企業內部 LLM API 的多層內容控管**  
   內部聊天或程式碼生成 API 需要同時攔截機密資料外洩、惡意程式碼生成與不當言論。LMSM 允許每條規則對應不同後端（例如機密資料用轉碼器、程式碼風險用密集探針），由版本化策略評估器組合多條規則，統一由執行閘道決定允許、終止或拒絕並回覆固定訊息。

3. **客服機器人的即時有害請求攔截**  
   面對越獄或誘導性提示，可在生成路徑上部署 LMSM-Checkpoint 類配置。以 Qwen3-4B 為例，論文顯示 HarmBench 攻擊成功率可從 39.20% 降至 3.32%，同時 XSTest 誤拒絕僅從 2.40% 微升至 4.40%，適合對誤拒絕容忍度較低的客服場景。

4. **多租戶模型服務的差異化安全策略**  
   同一個 vLLM 服務實例承載多個客戶，每個客戶需要不同的作用中規則組合與排程。LMSM 的受信任的每請求上下文讓不同請求攜帶各自的策略版本與規則啟用狀態，排程器變動時仍能保留每請求決策，適合 SaaS 化模型託管平台。

5. **可解釋性產物的產品化落地**  
   研究團隊已訓練出與特定危險概念對齊的 SAE 或轉碼器，但缺乏上線路徑。LMSM 提供共同後端合約，讓這些產物只需經過校準與規則綁定即可進入生產環境，避免為每個新產物重建防護堆疊。

### 實作前置條件

**資料條件**
- 若採用產物為基礎的後端：需取得與目標風險概念對應的已發布 SAE、轉碼器或類似表徵產物，並準備涵蓋正例與負例的校準資料集。
- 若採用任務擬合後端：需收集領域內範例，包含目標行為的觸發樣本與正常樣本，用於訓練與驗證密集探針。
- 無論哪種後端，都建議準備獨立的攻擊測試集（如 HarmBench）與誤拒絕測試集（如 XSTest）以評估策略有效性。

**運算條件**
- 推論基礎設施：需支援 Hugging Face Transformers 與連續批次化 vLLM 的 GPU 伺服器。
- 監控開銷：論文顯示在 32 個作用中序列下，LMSM-Checkpoint 相較無監控的對照服務路徑仍保留 98.14% 吞吐量，但仍需預留額外記憶體與計算資源給後端證據提取與策略評估。
- 開發環境：Python、PyTorch、vLLM、Transformers，以及 SAE 分析工具鏈（如 sae-lens 或自訂轉碼器實作）。

**技能條件**
- 熟悉 LLM 推論服務化與 vLLM 連續批次機制。
- 具備可解釋性方法基礎，能理解稀疏自動編碼器、轉碼器或線性探針的輸出意義。
- 具備資安思維，能區分「監控訊號」與「安全控制機制」，並設計適當的執行動作與降級方案。

### 實作步驟建議

1. **定義受保護狀態變更與風險目標**  
   先釐清哪些輸出屬於安全相關操作，例如生成劑量建議、洩漏個資、輸出惡意程式碼。將每個風險轉換為具體的目標、證據與條件，作為後續規則設計的基礎。

2. **選擇並整合安全後端**  
   根據資料與產物可得性決定採用產物為基礎的後端（SAE、轉碼器）或任務擬合的密集探針。實作共同後端合約，使所有後端都輸出統一格式的校準證據，供策略評估器使用。

3. **校準與擬合**  
   對產物後端進行校準，決定閾值與特徵選擇；對密集探針則在領域內範例上訓練擬合線性模型。此階段要同時評估召回率與誤報率，避免過度敏感。

4. **建立版本化規則庫與策略**  
   將每條規則寫入版本化規則庫，定義作用中規則、排程（例如每個解碼步驟檢查或僅在 checkpoint 檢查）、組合方式（全數觸發即攔截或優先級解析）。每次變更都更新策略版本，確保可追溯。

5. **實作執行閘道與輸出緩衝**  
   在生成路徑上插入執行閘道，讓候選輸出先進入緩衝區，待策略評估器完成比較、解析與決策後，再決定允許、終止或拒絕並回覆固定訊息。閘道必須獨立於後端與策略邏輯。

6. **在連續批次化環境中驗證穩定性**  
   於 vLLM 上進行壓力測試，確認排程器變動、批次 slot 重用、多請求交錯時，每個請求的作用中繫結、選定類別、介入步驟與閾值穿越結果都能保持一致。

7. **上線與持續監控**  
   部署後持續收集生產請求、誤拒絕回報與攻擊樣本，定期更新後端綁定、規則條件與策略版本。保留無監控的對照服務路徑，定期測量吞吐量衰減。

### 潛在風險與注意事項

- **後端證據不等同安全控制**  
  可解釋性訊號可能與風險相關，但本身沒有強制執行力。若未經校準就直接接入閘道，容易產生高誤拒絕或漏攔截。應透過獨立的策略評估器與執行閘道將其轉化為真正的安全控制機制。

- **排程器變動導致狀態錯亂**  
  連續批次化會讓不同請求共享 batch slot，若每請求上下文未正確隔離，可能發生 A 請求的證據被誤用於 B 請求的決策。務必在每次 forward 時攜帶受信任的每請求上下文，並在 slot 重用時完整重置後端狀態。

- **多規則組合的意外交互**  
  多條作用中規則同時啟用時，可能出現規則衝突或疊加誤報。建議先在小規模測試集上進行組合實驗，明確定義解析優先級，並保留單一規則的對照結果。

- **吞吐量與延遲開銷被低估**  
  雖然論文顯示在 32 作用中序列下僅損失約 2% 吞吐量，但實際開銷會隨後端複雜度、規則數量與生成長度變化。應在生產規模下測量 P99 延遲，並設計當後端逾時時的降級策略。

- **模型或後端更新後規則失效**  
  更換基礎模型或後端產物版本可能使原本校準的閾值偏移。應將後端綁定與策略版本一併管理，並在更新後重新執行攻擊測試集與誤拒絕測試集。

### 與其他技術的整合建議

- **外部輸入輸出防護（LlamaGuard、NeMo Guardrails）**  
  LMSM 專注於生成期間的模型內部訊號，可與邊界文字過濾器互補。建議將 LMSM 作為「生成中」層，外部防護作為「生成前後」層，形成縱深防禦。

- **提示層控制（Instruction Hierarchy、System Prompt）**  
  LMSM 不取代提示工程，而是為已對齊模型增加操作者可更新的規則覆蓋層。可將提示層控制用於一般性行為引導，LMSM 用於高風險、需精確攔截的特定目標。

- **對齊訓練（RLHF、DPO、Constitutional AI）**  
  對齊訓練提供模型層級的安全預設，LMSM 則處理操作者特定、變化快速的義務。兩者整合時，對齊訓練負責降低基礎違規傾向，LMSM 負責在服務端強制執行動態規則。

- **可觀測性與日誌平台**  
  將策略版本、後端證據向量、閘道決策與介入步驟寫入結構化日誌，便於後續稽核、攻擊樣本回收與規則效果分析。

- **模型服務編排（Kubernetes、Seldon、Triton）**  
  LMSM 可封裝為 vLLM 外掛或自訂推論引擎模組，透過容器化部署在模型服務後方。建議將無監控對照路徑與 LMSM 路徑並行部署，方便 A/B 測試與緊急降級。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「為什麼需要 LMSM」開始理解：現有 LLM 安全控制各自為政，每新增一種模型內部分析方法就要重建一套防護堆疊。LMSM 借鏡 Linux Security Modules 的分離思想，把「誰來監控」（後端）、「什麼時候攔截」（策略）、「怎麼攔截」（閘道）拆開，讓操作者像換 AppArmor 或 SELinux 政策一樣更換安全規則，而不必改寫整個服務。重點看圖 1 與遠距醫療範例即可建立直覺。

**AI 工程師**  
請聚焦共同後端合約、策略評估器與執行閘道的介面設計。論文的核心貢獻在於把 SAE、轉碼器與密集探針統一成可替換後端，並在連續批次化 vLLM 中保持每請求決策穩定。實作時需特別注意排程器變動下的上下文隔離、slot 重用狀態清理，以及多規則組合時的解析邏輯。吞吐量與延遲數據可作為容量規劃參考。

**研究人員**  
本文把可解釋性產物從「分析工具」重新定位為「安全後端」，並提出一組穩定的執行期強制執行抽象。值得深入探討的問題包括：後端證據的因果有效性、多後端組合下的誤差傳播、參考監控器原則在 LLM 服務中的形式化邊界，以及如何在保留隔離保證與效能之間取得平衡。論文提供的 HarmBench 與 XSTest 數據可作為後續研究的基線。

**產品經理**  
LMSM 的商業價值在於讓營運團隊能夠在不重新訓練模型的情況下，針對法規、客戶或場景需求快速上線與迭代安全規則。請關注三個指標：攻擊成功率下降幅度、誤拒絕上升幅度，以及相對無監控路徑的吞吐量保留率。與法務、資安團隊溝通時，可強調版本化策略與執行閘道帶來的可稽核性與可回滾性。
