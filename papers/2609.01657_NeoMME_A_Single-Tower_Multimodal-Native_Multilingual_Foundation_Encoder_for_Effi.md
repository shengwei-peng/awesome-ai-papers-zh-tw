## ⚡ TL;DR

現有多模態檢索器沿用生成式 VLM，造成非生成任務的參數與計算冗餘。
提出 NeoMME 單塔雙向多語言多模態編碼器，以遮罩離散擴散目標從頭預訓練文字與原始影像區塊。
ViDoRe v3 上 260M/800M 達 0.523/0.556，編碼快兩倍、嵌入壓縮 255 倍。

## 摘要翻譯

多模態模型（Multimodal Model）通常建立在為生成式視覺語言建模（Generative Vision-Language Modeling）設計的架構（Architecture）之上，典型做法是將分別預訓練的視覺編碼器（Vision Encoder）與因果語言模型（Causal Language Model）結合。ColPali 等視覺文件檢索器（Visual Document Retriever）將這些模型重新用作編碼器（Encoder），使得非生成式任務（Non-Generative Task）也須承擔視覺語言模型（Visual Language Model, VLM）的參數（Parameter）與計算開銷（Compute Overhead）。

我們提出 NeoMME，一系列參數量為 260M 與 800M 的多模態且多語言（Multilingual）雙向編碼器（Bidirectional Encoder），可在單一雙向 Transformer 編碼器（Bidirectional Transformer Encoder）中處理多語言文字（Multilingual Text）與原始影像區塊（Raw Image Patch）。兩個模型均從頭預訓練（Pretrained from Scratch），採用遮罩式離散擴散文字目標（Masked Discrete-Diffusion Text Objective），並在多模態範例（Multimodal Example）中以可見影像區塊（Visible Image Patches）為條件。兩者皆支援 16,384 詞元的上下文長度（16,384-Token Context），足以編碼最多兩張標準 4K UHD 影像（4K UHD Image）。

為展示其下游能力（Downstream Capability），我們透過聯合訓練（Jointly Trained）的稠密頭部（Dense Head）與晚期互動頭部（Late-Interaction Head）對 NeoMME 進行微調（Fine-Tuning）。在 ViDoRe v3 基準測試上，所得到的 NeoMME-Retriever 260M 達到 0.523 的標準化折損累積增益@10（Normalized Discounted Cumulative Gain@10, nDCG@10），優於所有經評估且參數量嚴格低於 800M 的模型；NeoMME-Retriever 800M 則達到 0.556。在 NVIDIA L40S 上採用相同的 2048×2048 影像輸入尺寸（2048×2048 Image Input Size），NeoMME-260M 編碼頁面的吞吐量（Throughput）約為 ColModernVBERT 的 2 倍。階層式詞元池化（Hierarchical Token Pooling）與非對稱量化（Asymmetric Quantization）可將晚期互動多模態文件嵌入（Late-Interaction Multimodal Document Embedding）壓縮 255 倍，同時保留基線 nDCG@10（Baseline nDCG@10）的 95% 以上。我們將 NeoMME 貢獻至 Hugging Face Transformers，並在 Apache 2.0 授權條款下釋出預訓練骨幹網路（Pretrained Backbone）與檢索相容檢查點（Retrieval-Compatible Checkpoint），網址為 https://hf.co/collections/Hcompany/neomme。

### 核心貢獻（3～5點）
- 提出單塔式原生多模態多語言基礎編碼器 NeoMME，以單一雙向 Transformer 編碼器同時處理多語言文字與原始影像區塊，並從頭預訓練，避免繼承生成式 VLM 的冗餘參數與計算開銷。
- 支援 16,384 詞元上下文，可編碼最多兩張 4K UHD 影像，並透過聯合訓練的稠密頭部與晚期互動頭部進行下游檢索微調。
- 在 ViDoRe v3 基準測試上，NeoMME-Retriever 260M 與 800M 分別達到 0.523 與 0.556 nDCG@10，優於同規模模型。
- 具備高效推論與嵌入壓縮能力：在 NVIDIA L40S 上吞吐量約為 ColModernVBERT 的 2 倍，並可將晚期互動多模態文件嵌入壓縮 255 倍，同時保留 95% 以上基線效能。
- 開源貢獻：將 NeoMME 整合至 Hugging Face Transformers，並以 Apache 2.0 釋出預訓練骨幹網路與檢索相容檢查點。

### 適合對象
從事多模態檢索、視覺文件理解、資訊檢索與高效模型部署的研究人員與工程師，特別是關注單塔式編碼器架構、多語言多模態預訓練、下游檢索微調與開源模型應用的讀者。

## 深度分析

#### 方法論解析

NeoMME 的核心設計可概括為「單塔式（Single-Tower）、原生多模態（Multimodal-Native）、雙向編碼器（Bidirectional Encoder）」。與主流視覺語言模型（Visual Language Model, VLM）將預訓練視覺編碼器（Vision Encoder）輸出投影到因果語言模型（Causal Language Model）的解碼器（Decoder）路徑不同，NeoMME 從隨機初始化開始，將多語言文字（Multilingual Text）與原始影像區塊（Raw Image Patch）送入同一個雙向 Transformer 編碼器（Bidirectional Transformer Encoder），讓兩種模態共享所有層級的計算路徑。

**1. 輸入表示與影像區塊化**

影像部分採用未經預訓練視覺塔處理的原始 32×32 像素區塊（Raw 32×32 Pixel Patches）。文字與影像分別經過模態專屬投影（Modality-Specific Projections）後進入共享骨幹網路（Backbone）。動態解析度（Dynamic Resolution）機制保留影像長寬比，配合 32 像素區塊與長上下文架構，使高解析度輸入在 16,384 詞元上下文（16,384-Token Context）內可行，足以編碼最多兩張標準 4K UHD 影像。這種設計避免了獨立影像塔與語言塔之間不對稱的前向傳播（Forward Pass）與架構差異。

**2. 預訓練目標：影像條件化的遮罩式離散擴散文字目標**

預訓練採用遮罩式離散擴散文字目標（Masked Discrete-Diffusion Text Objective）。對純文字範例，模型須對被遮罩的文字詞元進行去噪；對多模態範例（Multimodal Example），同樣的文字去噪目標會條件化於可見影像區塊（Conditioned on Visible Image Patches），即模型根據對應自然影像或文件影像的未遮罩區塊來重建文字。這相當於把 BERT 風格的遮罩語言模型擴展到連續時間的擴散軌跡，並將影像作為條件訊號，強迫模型學習跨模態對齊，而非僅學習單一模態的表徵。

**3. 下游檢索頭部：稠密與晚期互動聯合訓練**

為了驗證骨幹網路的下游能力（Downstream Capability），作者將 NeoMME 微調為 NeoMME-Retriever。單次骨幹前向傳播即可同時產生兩種輸出：

- 稠密頭部（Dense Head）：輸出單一 pooled 向量，適合傳統密集檢索（Dense Retrieval）。
- 晚期互動頭部（Late-Interaction Head）：輸出多向量表徵，支援 ColBERT 風格的晚期互動（Late-Interaction），可捕捉文件內細粒度區塊對應關係。

兩個頭部聯合訓練（Jointly Trained），讓同一模型兼顧儲存效率與檢索精度。

**4. 推論加速與嵌入壓縮**

為降低晚期互動的記憶體與計算成本，作者釋出 Late-Interaction Kernels（LIK），一套融合式 MaxSim 核心，用於減少晚期互動推論與訓練時的峰值 VRAM 與執行時間。此外，階層式詞元池化（Hierarchical Token Pooling）搭配非對稱量化（Asymmetric Quantization）（查詢用 int8、文件用 binary）可將晚期互動多模態文件嵌入（Late-Interaction Multimodal Document Embedding）大幅壓縮 255 倍，同時保留超過 95% 的基線 nDCG@10（Baseline nDCG@10）。

#### 實驗數據解讀

**1. ViDoRe v3 檢索效能**

在視覺文件檢索基準 ViDoRe v3 上：

- NeoMME-Retriever 260M 達到 0.523 nDCG@10，超越所有評估中低於 800M 參數（Parameter）的模型。
- NeoMME-Retriever 800M 達到 0.556 nDCG@10。

這顯示即使僅有 260M 參數，單塔原生多模態編碼器也能在視覺文件檢索上取得強勁表現；800M 版本則進一步逼近或超越更大模型的水準。由於作者強調模型在 ViDoRe v1、v2、v3 上呈現 Pareto-optimal，這意味著在參數量—效能權衡曲線上，NeoMME-Retriever 佔據了較佳位置。

**2. 編碼吞吐量**

在 NVIDIA L40S 上，以 2048×2048 影像輸入尺寸（2048×2048 Image Input Size）編碼頁面：

- NeoMME-260M 達到 51.3 pages/s。
- 相較於 ColModernVBERT，吞吐量（Throughput）提升約 1.97 倍（接近 2×）。

這項結果凸顯單塔架構在服務端的優勢：省去獨立視覺編碼器與解碼器之間的資料搬移與冗餘計算，對非生成式任務（Non-Generative Task）而言計算開銷（Compute Overhead）顯著降低。

**3. 嵌入壓縮與品質保留**

針對 NeoMME-260M 在 ViDoRe v3 文件上的晚期互動嵌入：

- 原始嵌入約 1.5 MB / 文件。
- 經階層式詞元池化（因子 8）與非對稱量化後，降至約 6 kB / 文件。
- 壓縮倍率達 255×，且保留超過 95% 基線 nDCG@10。

這對大規模語料索引極具實務意義：高解析度視覺文件檢索若無壓縮，索引儲存與頻寬成本會迅速失控；255× 壓縮讓數百萬甚至數億頁文件的可行性大幅提升。

**4. 綜合意涵**

實驗數據共同傳達一個訊息：NeoMME 在「效能—參數量—推論效率—儲存效率」四個維度上取得了良好平衡。這對於需要將多模態檢索部署於生產環境的應用（例如企業文件搜尋、RAG 系統）特別重要。

#### 與現有研究的比較

**1. 相較於生成式 VLM 改裝的檢索器**

ColPali 等視覺文件檢索器（Visual Document Retriever）通常沿用生成式 VLM 的架構：先以預訓練視覺編碼器抽取影像特徵，再投影到因果語言模型。這類方法雖然強大，但承襲了 VLM 的參數與計算開銷，對於非生成式檢索任務而言並非最有效率。NeoMME 從頭預訓練（Pretrained from Scratch）一個專為編碼設計的雙向模型，去除了解碼器與獨立視覺塔，顯著降低推論成本。

**2. 相較於 ModernVBERT 與 ColModernVBERT**

ModernVBERT 以 250M 參數將因果解碼器替換為雙向編碼器，但保留了預訓練 SigLIP2 視覺塔。ColModernVBERT 則在此基礎上引入晚期互動。NeoMME 更進一步移除視覺塔，採用單塔共享 Transformer，並在吞吐量上達到約 2× 優勢。這說明「原生多模態」不僅是概念差異，也帶來實質的硬體效率提升。

**3. 相較於 CLIP / SigLIP 等雙塔對比模型**

CLIP 與 SigLIP 將影像與文字分別編碼於獨立塔，再透過對比學習對齊。這類模型在跨模態檢索上非常成功，但獨立塔限制了細粒度互動，且通常需要額外設計才能處理文件級高解析度輸入。NeoMME 的單塔設計讓文字詞元與影像區塊在同一 Transformer 內進行雙向注意力，天然適合晚期互動與高解析度文件理解。

**4. 相較於 ViLT、OneR、M3AE 等單塔雙向模型**

ViLT、OneR、M3AE 已嘗試在雙向架構中共享影像與文字。NeoMME 的差異在於：

- 使用連續原始影像區塊（Continuous Raw Patches），而非外部影像 tokenizer 產生的離散詞元。
- 採用遮罩式離散擴散文字目標，並以影像作為條件。
- 同時支援稠密與晚期互動檢索頭部，並針對大規模部署進行量化與核心最佳化。

**5. 相較於近期 tower-free VLM**

近期 tower-free VLM（如某些將投影影像區塊直接餵入生成式骨幹的模型）也採用單塔路徑，但目標仍是生成。NeoMME 則專注於編碼與檢索，並證明原生雙向編碼器在分類與檢索任務上優於因果解碼器或其改編版本。

**6. 限制與潛在弱點**

- **生成能力缺失**：作為編碼器，NeoMME 不具備生成式 VLM 的開放式文字生成能力，無法直接用於視覺問答或影像描述等生成任務。
- **從頭訓練成本**：雖然最終模型高效，但從頭預訓練需要大量計算與資料調配，論文對預訓練資料規模與訓練成本的描述相對有限。
- **評估範圍**：主要強調 ViDoRe 系列與檢索任務，對於更廣泛的多模態理解基準（如視覺問答、圖表理解、OCR 任務）的表現尚待更多驗證。
- **解析度與計算權衡**：16,384 詞元上下文雖可容納 4K 影像，但高解析度輸入仍會顯著增加計算量，實際部署需根據場景權衡。

#### 可重現性評估

**1. 開源釋出**

作者已將 NeoMME 貢獻至 Hugging Face Transformers 函式庫，並在 Hugging Face 上釋出預訓練骨幹網路（Pretrained Backbone）與檢索相容檢查點（Retrieval-Compatible Checkpoint），授權為 Apache 2.0。這大幅降低了研究與工程社群重現與部署的門檻。

**2. 模型與工具鏈**

- **NeoMME-Retriever**：可輸出稠密與晚期互動兩種表示，並與 Sentence Transformers 相容，方便整合現有檢索流程。
- **Late-Interaction Kernels（LIK）**：提供融合 MaxSim 核心，降低晚期互動訓練與推論的 VRAM 與執行時間。
- **Hugging Face 文件**：論文提及 NeoMME 模型文件說明公開架構與 API，有助於正確載入與使用。

**3. 可重現性亮點**

- 使用廣泛採用的 Transformers 生態系，降低環境建置成本。
- Apache 2.0 授權允許商業與學術用途。
- 提供檢索相容檢查點，使用者可直接進行微調或推論，無需從頭預訓練。

**4. 可重現性缺口**

- 預訓練資料的詳細組成、清洗流程與規模在提供的上下文中未完整揭露，這會影響從頭復現預訓練結果的難度。
- 微調配方（學習率、批次大小、訓練步數、正負樣本採樣策略）的細節需要進一步查閱完整論文或釋出訓練腳本。
- LIK 核心的底層實作與支援硬體範圍（例如是否支援多種 GPU 架構）需參考釋出文件確認。

#### 未來研究方向

**1. 擴展至多模態生成任務**

雖然 NeoMME 專注編碼，但其單塔共享 Transformer 與原始影像區塊輸入的設計，為未來加入生成頭部（如因果解碼器或離散擴散解碼器）提供了基礎。可探索「編碼器—解碼器」統一架構，讓同一骨幹同時服務檢索與生成。

**2. 更廣泛的多模態理解基準**

未來可在視覺問答（VQA）、圖表問答、文件 OCR、資訊擷取、多模態分類等任務上評估 NeoMME，以驗證其作為通用多模態基礎編碼器（Foundation Encoder）的泛化能力。

**3. 長上下文與多頁文件**

16,384 詞元已能容納兩張 4K 影像，但實際應用常需處理數十頁文件。可研究更高效的長上下文機制（如稀疏注意力、記憶體壓縮、分層編碼），在保持單塔優勢的同時擴展至多頁場景。

**4. 更激進的壓縮與邊緣部署**

目前的 255× 壓縮已相當出色，但未來可探索：

- 更極端的量化（如 4-bit、二值化查詢與文件向量）。
- 知識蒸餾（Knowledge Distillation）將 800M 模型能力轉移至更小模型，服務於行動裝置或瀏覽器端檢索。
- 與近似最近鄰搜尋（ANN）引擎的深度整合，進一步降低延遲。

**5. 多語言與跨語言檢索

NeoMME 強調多語言（Multilingual）能力，未來可系統性評估其在低資源語言、跨語言文件檢索、多語言 OCR 與翻譯檢索上的表現，並擴充多語言預訓練資料。

**6. 與 RAG 系統的整合**

NeoMME-Retriever 的稠密與晚期互動輸出非常適合檢索增強生成（Retrieval-Augmented Generation, RAG）。未來可研究如何將其嵌入多模態 RAG 管線，並與大型語言模型（Large Language Model, LLM）進行端到端最佳化。

**7. 預訓練目標的進一步探索**

遮罩式離散擴散目標已展現潛力，但未來可嘗試：

- 同時對影像區塊進行遮罩重建，強化視覺表徵。
- 引入對比目標與擴散目標的混合，進一步提升跨模態對齊。
- 探索不同遮罩率排程與擴散時間步對檢索效能的影響。

**8. 模型規模擴展

目前釋出 260M 與 800M 兩個版本。未來可訓練 1B+ 甚至數 B 參數版本，檢驗單塔原生多模態編碼器在更大規模下是否能持續保持效率與效能的 Pareto 優勢。

## 論文問答

## 【Background & Motivation】

**Q1：NeoMME 主要想解決什麼問題？**

A：NeoMME 主要解決現有多模態模型在視覺文件檢索這類非生成式任務上計算開銷過高的問題。目前主流方法通常將獨立預訓練的視覺編碼器與因果語言模型結合，這種為生成式視覺語言建模設計的架構在轉作編碼器使用時會帶來不必要的參數與計算負擔。此外，像 ColPali 這類視覺文件檢索器雖然效果不錯，但本質上仍是將生成式 VLM 重新定位為編碼器，未能針對檢索任務從頭設計更精簡高效的架構。

**Q2：為何現有方法在視覺文件檢索上存在不足？**

A：現有方法大多建立在生成式視覺語言模型的架構之上，這些架構包含獨立的視覺編碼塔和因果解碼器，兩者在計算路徑上並不對稱，導致推論時需要額外的記憶體與計算資源。以 ColPali 為例，它雖然利用晚期互動機制保留了影像區塊層級的細粒度表徵，但其底層仍是龐大的生成式 VLM，對於只需要編碼表示的非生成式檢索任務來說過於沉重。ModernVBERT 雖然改用雙向編碼器，但仍保留預訓練的 SigLIP2 視覺塔，無法讓文字與影像在每一層 Transformer 中共享相同的計算路徑與模型生命週期。

**Q3：原生多模態編碼器為何重要？**

A：原生多模態編碼器能讓文字與影像從輸入開始就進入同一個共享的 Transformer，統一兩種模態的計算路徑與模型生命週期，避免分離式架構帶來的不對稱性與冗餘。這種設計讓模型在預訓練、微調、平行化與部署階段都能以單一骨幹網路處理多模態資料，大幅降低工程複雜度。此外，針對分類與檢索等非生成式任務，文獻已指出原生雙向編碼器通常優於因果解碼器或其改編版本，因此從頭設計原生多模態編碼器對於提升檢索效能與效率具有重要意義。

## 【Method & Innovation】

**Q4：NeoMME 的核心方法是什麼？**

A：NeoMME 採用單塔式雙向 Transformer 編碼器，將多語言文字嵌入與 32×32 像素的原始影像區塊透過模態專屬投影後送入共享的每一層 Transformer。模型從頭預訓練，對純文字樣本使用遮罩式離散擴散文字目標，對影像–文字配對則讓相同的文字去噪目標條件化於對應自然或文件影像的可見影像區塊。這種設計讓單一骨幹網路同時學習多語言文字表徵與視覺文件理解能力，並支援長達 16,384 詞元的上下文，足以編碼兩張標準 4K UHD 影像。

**Q5：NeoMME 相較於現有方法有哪些關鍵創新？**

A：NeoMME 的關鍵創新在於它是首個結合連續原始影像區塊、無視覺塔的共享雙向 Transformer、從隨機初始化從頭訓練、影像條件化遮罩文字擴散，以及後續稠密與晚期互動視覺文件檢索的模型。不同於 CLIP／SigLIP 的獨立雙塔或生成式 VLM 的視覺編碼器加因果解碼器設計，NeoMME 讓文字與影像在每一層都共享計算路徑。此外，它同時輸出稠密池化表徵與晚期互動多向量表徵，並透過階層式詞元池化與非對稱量化實現 255 倍的嵌入壓縮，兼顧檢索品質與部署效率。

**Q6：NeoMME 有哪些重要的設計選擇？**

A：NeoMME 選擇使用原始 32×32 像素影像區塊而非依賴預訓練視覺編碼器，這讓模型能直接從像素學習視覺表徵並與文字在同一 Transformer 中聯合處理。動態解析度設計保留影像長寬比，結合長上下文架構使高解析度輸入在計算上可行。預訓練目標採用遮罩式離散擴散而非傳統的遮罩語言模型，讓模型在多重遮罩率軌跡上學習更強健的文字表徵，並透過影像條件化將視覺資訊融入文字去噪過程。

## 【Experiments & Results】

**Q7：NeoMME 在哪些基準測試上進行評估，結果如何？**

A：NeoMME-Retriever 主要在視覺文件檢索基準 ViDoRe v1、v2 與 v3 上進行評估，其中在 ViDoRe v3 上，260M 模型達到 0.523 的標準化折損累積增益@10（nDCG@10），超越所有評估中低於 800M 參數的模型；800M 模型則達到 0.556 的 nDCG@10。這些結果顯示 NeoMME-Retriever 在參數規模與檢索效能之間達到帕雷托最適。除了視覺文件檢索，論文也評估了文字檢索任務，以展示其多語言編碼能力。

**Q8：NeoMME 進行了哪些效率與消融研究？**

A：論文在 NVIDIA L40S 上比較了 NeoMME-260M 與 ColModernVBERT 在 2048×2048 影像輸入尺寸下的編碼吞吐量，結果顯示 NeoMME-260M 每秒可處理 51.3 頁，約為 ColModernVBERT 的 1.97 倍。研究也探討了輸入解析度對檢索效能的影響，以及不同表示儲存與壓縮策略對索引吞吐量與查詢編碼延遲的影響。這些實驗證明單塔式原生編碼器架構在高解析度視覺文件檢索上同時具備速度與準確度優勢。

**Q9：壓縮與量化如何影響 NeoMME-Retriever 的效能？**

A：透過階層式詞元池化（池化因子為 8）與非對稱量化（查詢 int8、文件二值化），NeoMME-260M 的晚期互動多模態文件嵌入可從每份文件約 1.5 MB 壓縮至 6 kB，達到 255 倍的壓縮率。在 ViDoRe v3 上的實驗顯示，這種壓縮仍保留超過 95% 的基線 nDCG@10 檢索品質。這項結果對於大規模語料庫的視覺文件檢索至關重要，因為它讓高解析度文件嵌入的儲存與檢索在實務上變得可行。

## 【Applications & Impact】

**Q10：NeoMME-Retriever 適合哪些實際應用場景？**

A：NeoMME-Retriever 特別適合需要對掃描文件、PDF 頁面截圖或高解析度影像進行語意檢索的企業知識管理系統。例如法律、醫療與金融領域經常需要從大量掃描報告或表格中檢索特定資訊，NeoMME-Retriever 能同時理解影像版面與多語言文字內容。由於模型支援長上下文與動態解析度，它也適用於需要編碼整頁文件或多頁文件拼接後進行檢索的場景。

**Q11：NeoMME 在產品與工程部署上有哪些考量？**

A：NeoMME 在設計上同時輸出稠密池化表徵與晚期互動多向量表徵，讓開發者能依據延遲、儲存與準確度需求選擇合適的檢索模式。論文釋出的 Late-Interaction Kernels（LIK）透過融合 MaxSim 核心降低晚期互動訓練與推論時的峰值 VRAM 與執行時間。此外，模型已整合至 Hugging Face Transformers 並與 Sentence Transformers 相容，大幅降低在現有檢索管線中部署與微調的門檻。

**Q12：NeoMME 對多模態檢索領域有何更廣泛影響？**

A：NeoMME 證明了從頭訓練的單塔式原生多模態雙向編碼器，在視覺文件檢索上能同時達到優於改編自生成式 VLM 的模型效能與效率。這項工作挑戰了「必須依賴大型生成式 VLM 或獨立視覺塔才能做好多模態理解」的既有假設，為輕量級多模態編碼器開闢了新方向。由於模型與檢查點以 Apache 2.0 授權釋出，學術界與產業界都能在此基礎上進行研究與產品開發，加速多模態檢索技術的普及。

## 【Limitations & Future】

**Q13：NeoMME 有哪些已承認或隱含的限制？**

A：雖然論文未明確列出詳細限制，但從設計可推知 NeoMME 作為編碼器主要針對非生成式任務，無法直接用於需要生成文字回應的應用。此外，模型從頭預訓練需要大量多模態資料與計算資源，對於資源有限的研究者來說門檻較高。由於採用原始影像區塊輸入，對於極高解析度或特殊長寬比的影像，仍可能需要仔細調整動態解析度與上下文長度設定。

**Q14：NeoMME-Retriever 可能出現哪些失效案例？**

A：當文件影像包含極小字體、複雜表格結構或高度風格化的版面時，32×32 像素區塊可能無法充分捕捉細粒度文字與空間關係，導致檢索失準。對於訓練資料中少見的語言或專業領域術語，多語言編碼器可能產生較差的表徵。此外，雖然壓縮策略能大幅節省儲存空間，但在極端量化下仍可能遺失細微的視覺或語意資訊，影響對罕見查詢的檢索效果。

**Q15：NeoMME 未來有哪些可能的研究方向？**

A：未來研究可探索將 NeoMME 的單塔式原生編碼器架構擴展到更大規模，並在更多樣化的多模態任務上進行微調與評估。另一個方向是進一步優化壓縮與量化技術，在更高壓縮率下維持檢索品質，或開發針對不同硬體的專用推論核心。此外，結合 NeoMME 的編碼能力與輕量級生成頭，也可能發展出統一編碼與生成能力的多模態模型，拓展其在問答與摘要等任務上的應用。

## 實務應用指南

### 適用場景

**企業知識庫視覺文件檢索**
適合需要同時搜尋掃描合約、發票、報表、說明書等文件的場景。NeoMME-Retriever 可直接接收原始影像區塊，無需預先 OCR 或版面分析，就能根據頁面視覺與文字內容回傳相關文件。

**多語言電商與產品型錄搜尋**
由於骨幹網路具備多語言能力，可用於跨語言的商品圖文檢索，例如使用者以德文查詢，系統能從英文或中文的產品型錄圖片中找出對應項目。

**法律與金融文件比對**
長上下文（16,384 詞元）支援單次編碼多頁文件，適合條文比對、盡職調查文件查核，以及從大量 PDF 中找出與查詢條件視覺與語義皆相似的頁面。

**醫療與科學圖表檢索**
可處理高解析度影像輸入（如 2048×2048），適合檢索醫學影像報告、科學論文圖表或工程圖面，並透過晚期互動多向量表示保留細粒度對應關係。

### 實作前置條件

**資料準備**
需要成對或單模態的影像–文字資料。多模態範例建議包含文件影像與對應描述或問答；文字資料則需涵蓋目標語言與領域詞彙。若僅做微調，可準備數千至數萬筆標註的查詢–文件對。

**運算資源**
微調 NeoMME-Retriever 260M 建議至少單張 24 GB VRAM 的 GPU；800M 版本或處理 4K UHD 影像時，建議使用 48 GB 以上 VRAM 或多卡訓練。推論階段在 NVIDIA L40S 上已驗證 2048×2048 輸入可達約 51.3 頁每秒。

**技術能力**
團隊需熟悉 Hugging Face Transformers、Sentence Transformers 與 PyTorch，並具備向量資料庫操作經驗。若使用晚期互動檢索，需理解 MaxSim 運算與嵌入壓縮（階層式詞元池化與非對稱量化）的權衡。

### 實作步驟建議

1. **選擇檢查點**：從 Hugging Face 下載預訓練骨幹網路或 NeoMME-Retriever 檢索相容檢查點，依據延遲與品質需求選擇 260M 或 800M。
2. **資料格式轉換**：將文件頁面渲染為影像，並依動態解析度調整尺寸；查詢與文件分別整理為文字與影像輸入對。
3. **微調檢索頭部**：在領域資料上聯合訓練稠密頭部與晚期互動頭部，使用對比式損失讓正例查詢–文件對靠近。
4. **建立索引**：對文件側執行單次骨幹網路向前傳播，產生稠密向量與多向量表示，並寫入向量資料庫。
5. **壓縮與部署**：應用階層式詞元池化（如 factor 8）與非對稱量化（int8 查詢、binary 文件），將儲存需求降低約 255 倍。
6. **推論優化**：整合 Late-Interaction Kernels（LIK）以降低峰值 VRAM 與執行時間，並針對查詢端與文件端分別設定批次大小。

### 潛在風險與注意事項

**高解析度帶來的記憶體壓力**
4K UHD 影像會產生大量原始影像區塊，容易超出 GPU 記憶體。建議先評估業務所需的最低解析度，並善用動態解析度與梯度檢查點。

**晚期互動的儲存與檢索成本**
多向量表示雖然提升 nDCG@10，但每份文件的嵌入體積遠大於稠密向量。若未經壓縮，大規模索引會顯著增加儲存與 I/O 負擔，應優先導入階層式詞元池化與量化。

**領域適配不足**
從頭預訓練的骨幹網路雖具通用能力，但在高度專業領域（如特殊醫療影像或罕見語言）可能需要額外領域預訓練，而非僅做檢索頭部微調。

**量化後的品質衰減**
非對稱量化雖保留超過 95% 基線 nDCG@10，但對極度依賴細粒度比對的任務仍可能下降。建議在正式上線前以保留測試集驗證壓縮後指標。

### 與其他技術的整合建議

**向量資料庫**
稠密頭部輸出可無縫對接 FAISS、Milvus、Weaviate 或 pgvector；晚期互動表示則需資料庫支援多向量欄位或自訂 MaxSim 檢索外掛。

**文件處理管線**
上游可銜接 PDF 渲染、版面分析或圖表偵測工具，將頁面轉為影像後送入 NeoMME。由於模型本身接受原始影像區塊，可減少對傳統 OCR 引擎的依賴，但在需要精確文字抽取的場景仍可並行使用 OCR 作為後處理。

**生成式 VLM**
NeoMME-Retriever 適合作為檢索增強生成（RAG）的檢索器，將找到的視覺文件頁面與查詢一併餵給生成式視覺語言模型進行摘要或問答。

**現有搜尋系統**
可將 NeoMME 的稠密分數與傳統 BM25 或關鍵字分數進行加權融合，在混合檢索架構中兼顧語義理解與精確字詞比對。

### 給不同背景讀者的閱讀建議

**初學者**
建議先理解「編碼器」與「解碼器」的區別，以及為何視覺文件檢索需要同時看懂圖片與文字。接著從 Hugging Face 上的範例程式碼入手，嘗試用 NeoMME-Retriever 對幾份 PDF 頁面做查詢，再回頭對照論文中的 nDCG@10 與吞吐量數字，會更容易掌握實務意義。

**AI 工程師**
重點閱讀模型架構、預訓練目標與檢索頭部的聯合訓練方式，並評估 LIK 核心與非對稱量化對自家推論管線的影響。建議直接下載檢查點，在相同輸入尺寸下與 ColModernVBERT 或 ColPali 進行延遲與品質的對照實驗。

**研究人員**
值得深入分析單塔式雙向 Transformer 與獨立視覺編碼器加因果語言模型的設計差異，特別是遮罩式離散擴散目標在多模態情境下的條件化機制。晚期互動與稠密表示的聯合學習、階層式詞元池化的理論保證，也是可延伸的研究方向。

**產品經理**
關注 260M 與 800M 兩個版本在準確率、速度與成本之間的權衡，以及 255 倍壓縮如何影響大規模部署的儲存預算。評估時應以 ViDoRe v3 的 nDCG@10 作為品質參考，同時將 4K UHD 支援與多語言能力納入產品差異化賣點。
