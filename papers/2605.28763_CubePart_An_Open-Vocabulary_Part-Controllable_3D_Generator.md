現有3D生成模型僅產出整體網格或無法對齊應用需求的部件分解。

## 摘要翻譯

遊戲與模擬中使用的互動式 3D 資產（3D assets）通常會被分解為特定的語義部件（semantic parts），以支援動畫（animation）、物理（physics）與腳本化行為（scripted behaviors），然而大多數生成式 3D 模型所產生的要不是整體式網格（monolithic mesh），就是無法對齊特定應用需求的任意部件分解（part decomposition）。我們提出了 CubePart，一個用於開放詞彙（open-vocabulary）、部件可控（part-controllable）3D 網格（3D mesh）生成的生成式框架（generative framework），它將部件結構明確地作為推理時控制信號（inference-time control signal）呈現。給定一個全局文本提示（text prompt）以及一個由使用者定義、以開放式部件名稱列表（open-ended list of part names）形式表達的部件架構（part schema），我們的方法會生成一組網格——每個架構元素對應一個——這些網格在遵循指定語義結構的同時，組合成一個協調一致的物件。為實現此能力，我們引入了一個可擴展的數據管線（data pipeline），用以建構一個大型的開放詞彙、部件標註 3D 數據集（part-labeled 3D dataset），並提出了一個將全局形狀合成（global shape synthesis）與部件級解碼（part-level decoding）分離的兩階段生成架構（two-stage generative architecture）。我們展示了這些資產可直接整合到遊戲引擎（game engines）中，並由動畫與行為腳本（behavior scripts）驅動，無需手動後處理（post-processing）。專案頁面（project page）：https://cubepart.github.io/

### 核心貢獻（3～5點）
- **提出 CubePart 生成式框架**：首個將部件結構（part structure）作為明確推理時控制信號的開放詞彙、部件可控 3D 網格生成框架，使生成結果能對齊應用特定的語義需求。
- **支援使用者自訂部件架構**：給定全局文本提示與使用者定義的開放式部件名稱列表，方法可一次生成多個網格（multi-part mesh），各部件組裝成協調一致的物件。
- **可擴展的數據管線與大型部件標註數據集**：建構了一套可擴展的數據管線，用以產生大規模的開放詞彙、部件標註 3D 數據集，為訓練奠定基礎。
- **兩階段生成架構**：將全局形狀合成與部件級解碼分離，有效兼顧整體形狀的一致性與部件層級的細節控制。
- **可直接整合至下游應用**：所生成的資產無需手動後處理，即可整合至遊戲引擎並由動畫與行為腳本驅動，具備實務可用性。

### 適合對象
- **3D 內容生成與 AIGC 研究者**：關注文字生成 3D（text-to-3D）、擴散模型（diffusion models）於網格生成之應用者。
- **電腦圖學與幾何處理研究者**：對網格分解（mesh decomposition）、部件級表徵學習有興趣者。
- **遊戲與模擬產業開發者**：需要可即時整合、具語義部件結構之 3D 資產的遊戲引擎（game engines）開發者與技術美術（technical artist）。
- **機器人學與物理模擬研究者**：需要結構化、可動化 3D 物件以支援物理模擬行為（physically simulated behaviors）與腳本化行為（scripted behaviors）者。

## 深度分析

#### 方法論解析

CubePart 提出了一套針對「部件級可控 3D 生成」的端到端框架，其方法論核心在於將「部件架構（Part Schema）」提升為一階推理時控制信號（first-class inference-time control signal），而非僅作為後處理約束。以下從三個層面深入解析其技術路線。

**1. 問題形式化（Problem Formulation）**

傳統 3D 生成模型（如基於 diffusion 或 transformer 的網格合成器）通常將整體物件視為單一不可分割的幾何體，輸出結果為 monolithic mesh（整體式網格）。即便部分近期工作（如 OmniPart、PartCraft 等）嘗試引入部件分解，其分解結果往往是「模型自行決定」的，無法對齊下游應用所需的語義結構。CubePart 將此問題重新定義為一個條件式生成任務：

$$G: (P_{global}, S_{parts}) \rightarrow \{M_1, M_2, ..., M_n\}$$

其中 $P_{global}$ 為描述整體物件的文本提示，$S_{parts} = \{s_1, s_2, ..., s_n\}$ 為使用者定義的開放式部件名稱列表，輸出為對應每個部件名稱的獨立網格集合。這種形式化的關鍵在於：(a) 部件數量 $n$ 由使用者動態決定，無需預先封閉詞彙；(b) 每個輸出網格 $M_i$ 必須是「結構完整（structurally complete）」的獨立網格，而非從整體網格上切割下來的薄片；(c) 全集合必須在語義與幾何上組裝為連貫物件。

**2. 兩階段生成架構（Two-Stage Generative Architecture）**

論文明確指出其採用「分離全局形狀合成（Global Shape Synthesis）與部件級解碼（Part-Level Decoding）」的兩階段策略，這一設計選擇具有明確的技術動機：

- **第一階段（全局形狀合成）**：以 $(P_{global}, S_{parts})$ 為條件，生成一個隱式或顯式的全局形狀表示。此階段負責捕捉物件的整體輪廓、尺度與部件間的空間佈局關係。可推測其採用了類似 latent diffusion 或 autoregressive transformer 的架構，將部件名稱編碼為 token 序列，與全局提示共同注入條件機制。

- **第二階段（部件級解碼）**：以全局形狀為先驗，針對每個部件名稱 $s_i$ 解碼出對應的結構完整網格 $M_i$。此階段需解決的核心難題包括：(a) 部件間的幾何一致性（避免穿插、重疊或斷裂）；(b) 部件內部的拓撲完整性；(c) 部件間銜接處的視覺與物理合理性。

兩階段分離的優勢在於：全局形狀提供了強烈的空間先驗，使部件解碼器無需從零學習整體結構，從而大幅降低每個部件的生成難度；同時，全局階段的輸出可作為「幾何骨架」用於約束部件的相對位置與比例。

**3. 可擴展數據管線（Scalable Data Pipeline）**

開放詞彙部件生成的最大瓶頸在於訓練數據。現有 3D 數據集（如 ShapeNet、PartNet）僅覆蓋封閉詞彙的固定部件類別，無法支撐開放詞彙泛化。CubePart 引入了一套可擴展的數據管線來構建大規模、開放詞彙、部件標註的 3D 數據集。從論文描述可推斷其管線可能包含以下環節：

- **多源 3D 資產採集**：從遊戲資產庫、開源 3D 模型平台（如 Sketchfab、Thingiverse）以及程序化生成資產中獲取原始網格。
- **語義標註自動化**：利用視覺語言模型（VLM）或大型多模態模型，結合網格的多視角渲染圖，為部件生成自然語言描述。
- **部件分割與標籤對齊**：將現有的部件分割結果與語義標註進行對齊，過濾低品質或不一致的樣本。
- **品質過濾與標準化**：統一網格表示格式（如 watertight mesh）、部件命名規範化、拓撲清理等。

此數據管線的設計哲學在於「以規模換泛化」——透過自動化流程降低標註成本，使模型能從海量多樣化的部件名稱中學習到開放詞彙的語義對齊能力。

**4. 額外能力：現有網格的部件分解**

除從文本生成外，論文 Figure 1 最後一列展示 CubePart 亦可接受現有網格作為輸入，將其分解為符合輸入部件架構的多部件網格。這是一個重要的擴展功能，使其不僅是「生成器」，也是「分解器」，大幅提升了實用價值。其技術實現可能採用了類似 inverse rendering 或 conditional refinement 的策略：以輸入網格為幾何先驗，結合部件架構約束，輸出語義對齊的部件集合。

#### 實驗數據解讀

由於提供的全文僅包含摘要與引言部分，具體的定量實驗數據（如 FID、CLIP score、部件 IoU、使用者研究評分等）尚未揭露。以下基於論文所展示的定性結果與方法論特性進行推導式解讀。

**1. 定性結果分析（Figure 1 揭示的能力邊界）**

從 Figure 1 的結果展示可觀察到以下關鍵特性：

- **語義多樣性**：展示案例涵蓋生物（海龜、鳥、龍）、交通工具（汽車、戰車）、人造物體（茶壺、容器）等截然不同的領域，驗證了開放詞彙泛化能力。
- **部件複雜度跨度**：從簡單的 2 部件分解（如茶壺的 Lid + Base）到高度複雜的 7 部件分解（如海龜的 Head + Shell + Flippers + CastleTowers + MainKeep + Cannons），展現了對任意部件數量的彈性支援。
- **創意組合能力**：「海龜背上承載石造城堡」這類跨領域語義組合的生成結果，說明模型具備強大的語義組合泛化能力，而非僅記憶訓練集。
- **下游可用性**：Figure 1 底部展示的動畫網格（Animated Mesh）直接證明了輸出資產可無需手動後處理即整合至遊戲引擎並驅動動畫，這是相較於現有方法最關鍵的實用性突破。

**2. 預期評估指標體系**

基於此類工作的標準評估慣例，可推測 CubePart 的實驗應包含以下維度：

- **生成品質指標**：可能採用 FID（Fréchet Inception Distance）評估整體生成品質；CLIP-based score 衡量文本-3D 對齊程度。
- **部件分割準確度**：可能採用 PartIoU（部件級 IoU）、mIoU 等指標衡量部件邊界的準確性。
- **部件完整性**：可能引入「部件結構完整性比率」——即輸出部件中具備閉合拓撲、可獨立渲染的比例。
- **下游可用性評估**：可能透過遊戲引擎整合測試，量化「無需後處理即可驅動動畫/物理」的資產比例。
- **使用者研究**：可能邀請遊戲開發者或 3D 藝術家對生成結果的「部件語義合理性」、「組裝連貫性」、「動畫驅動便利性」進行主觀評分。

**3. 消融實驗的預期設計**

兩階段架構的消融實驗預期會驗證：(a) 移除全局形狀合成階段直接從部件名稱生成部件的品質下降幅度；(b) 部件解碼器在不同全局先驗強度下的表現差異；(c) 數據管線中各環節（如語義標註自動化、部件分割對齊）對最終性能的貢獻。

**4. 結果的實質意義**

若 CubePart 確實實現了「無需後處理即可整合至遊戲引擎」的承諾，其意義遠超學術層面——它直接解決了 3D 內容生產管線中最昂貴的環節（手動部件分解與標註），將原本需要數小時的專業工作壓縮為數秒的自動化生成，這對於 Roblox 等 UGC（User-Generated Content）平台具有巨大的商業價值。

#### 與現有研究的比較

**1. 與整體式 3D 生成器的比較**

近期整體式 3D 生成器（如 Xiang et al. 2025a,b 的 Hunyuan3D 系列、Yang et al. 2025b 的工作）雖然能從文本生成高品質網格，但輸出為單一 monolithic mesh，無法支援下游的部件級操作。CubePart 的核心優勢在於將「部件架構」作為一階控制信號，使生成結果天然具備語義可分解性，這對於遊戲、模擬、動畫等場景是不可或缺的。

**2. 與現有部件生成方法的比較**

- **OmniPart（Yang et al. 2025c）**：採用 2D mask 作為部件控制信號，存在根本性的視角依賴問題——無法控制被遮擋的部件（如動物的後腿、尾巴）。CubePart 採用 3D-native 的部件架構作為控制信號，從根本上避免了 2D 控制的歧義性與不完整性。
- **PartCraft、3D-Part 等方法**：通常採用封閉詞彙的部件類別，無法適應開放場景的多樣化需求。CubePart 的開放詞彙設計使其能處理任意使用者定義的部件名稱。
- **PartGym、PartDiffusion 等**：雖然支援部件生成，但其部件分解由模型自行決定，無法對齊下游應用的特定架構需求。

**3. 與 2D 接地（2D Grounding）路線的比較**

論文引言明確批評了「透過 2D 分割模型（如 SAM、Mask2Former）獲取部件級控制」的路線。除了前述的視角依賴問題外，2D mask 在提升至 3D 時存在根本性的幾何歧義——同一 2D 分割可能對應無數種 3D 結構。CubePart 的 3D-native 控制介面從根本上消除了這種歧義。

**4. CubePart 的獨特定位**

綜合來看，CubePart 在 3D 生成領域的定位可概括為：

| 維度 | 整體式生成器 | 2D 接地部件生成 | CubePart |
|------|-------------|----------------|----------|
| 部件控制 | ✗ | 部分（視角依賴） | ✓（3D-native） |
| 開放詞彙 | ✓ | 部分 | ✓ |
| 部件架構對齊 | ✗ | ✗ | ✓ |
| 結構完整性 | N/A | ✗（薄片） | ✓ |
| 遊戲引擎直接可用 | ✗ | ✗ | ✓ |

**5. 現有限制與未解決問題**

儘管 CubePart 取得了顯著進展，仍存在以下潛在限制：

- **部件間銜接品質**：當部件數量增加時，部件間的銜接處（如汽車車身與車門的接縫）可能出現視覺瑕疵或幾何不連續。
- **複雜拓撲部件**：對於需要複雜內部結構的部件（如可開啟的引擎蓋內部），生成品質可能下降。
- **物理合理性**：雖然輸出可整合至物理引擎，但部件的質量分佈、碰撞體積等物理屬性仍需手動設定。
- **計算成本**：兩階段生成架構的推理延遲可能高於單階段方法，對即時互動應用構成挑戰。

- **數據規模**：構建大規模開放詞彙部件標註數據集需要大量計算資源與儲存空間，完整釋出可能受限於商業考量（尤其考慮到作者來自 Roblox）。

- **商業資產依賴**：若訓練數據包含 Roblox 平台的部分專屬資產，可能無法完全公開。

**3. 評估建議**

#### 未來研究方向

**1. 部件間互動建模（Inter-Part Interaction Modeling）**

當前 CubePart 主要關注部件的「靜態結構完整性」，但遊戲與模擬場景中的部件往往需要動態互動（如車門開啟、輪胎轉動、翅膀拍動）。未來可探索：

- 在部件解碼階段引入「鉸鏈（hinge）」、「滑軌（slider）」等運動約束的顯式建模。
- 學習部件間的運動學關係，使生成結果天然具備可動畫性。
- 結合物理模擬器進行聯合訓練，使部件在物理層面合理。

**2. 階層化部件架構（Hierarchical Part Schema）**

現有部件架構為扁平列表，但現實物件的部件往往具有階層結構（如「汽車 → 車身 → 車門 → 車窗」）。未來可探索：

- 支援樹狀或圖狀的部件架構定義。
- 學習部件間的「父子」與「包含」關係。
- 實現「由粗到細」的階層化生成策略。

**3. 跨模態部件控制（Cross-Modal Part Control）**

雖然文本是自然的控制介面，但部分場景下圖像、草圖或點雲可能更直觀：

- 結合文本與草圖的混合控制：使用者可用草圖指定部件大致形狀，用文本指定語義。
- 從單張參考圖像提取部件架構，實現「風格遷移式」的部件生成。
- 支援點雲或體素形式的粗略幾何先驗作為部件生成的引導。

**4. 物理屬性聯合生成（Joint Generation of Physical Properties）**

當前輸出主要為幾何網格，但遊戲引擎需要質量、摩擦係數、碰撞體等物理屬性：

- 在部件解碼階段聯合預測物理參數。
- 學習從幾何特徵到物理屬性的映射，使生成資產可直接用於物理模擬。
- 探索「物理合理性」作為額外的生成約束。

**5. 大型語言模型驅動的部件架構自動設計（LLM-Driven Schema Auto-Design）**

對於非專業使用者，設計合理的部件架構本身具有門檻：

- 利用 LLM 根據全局提示自動建議合理的部件架構。
- 支援多輪對話式部件架構細化（如「將車身進一步拆分為車頂與底盤」）。
- 結合領域知識（如遊戲類型、動畫需求）進行架構推薦。

**6. 部件級編輯與組合（Part-Level Editing and Composition）**

- 支援部件級的局部編輯（如「將車輪換成更大尺寸」），保持整體一致性。
- 跨物件的部件組合（如「將跑車引擎安裝到卡車上」）。
- 部件庫的構建與檢索，實現「部件級的資產重用」。

**7. 效率優化與即時互動（Efficiency Optimization for Real-Time Interaction）**

- 蒸餾或量化兩階段架構，降低推理延遲。
- 探索單階段的端到端部件生成架構。
- 結合快取與增量生成策略，支援互動式部件設計。

**8. 評估基準與協議的標準化（Standardization of Evaluation Benchmarks）**

目前部件級 3D 生成缺乏統一的評估基準：

- 建立涵蓋多領域、多部件複雜度的標準測試集。
- 定義統一的評估指標（部件 IoU、結構完整性、語義對齊度等）。
- 推動遊戲引擎整合測試的標準化流程，使「實用性」成為可量化的評估維度。

**9. 倫理與版權考量（Ethical and Copyright Considerations）**

開放詞彙生成帶來了潛在的版權與倫理風險：

- 訓練數據中的資產版權歸屬問題。
- 生成結果與現有 IP 的相似度控制。
- 探索「風格解耦」的部件生成，避免對特定藝術家風格的過度模仿。

---

**總結**：CubePart 代表了 3D 生成領域從「整體式合成」向「結構化、可控生成」演進的重要一步。其將部件架構作為一階控制信號的設計哲學，與遊戲、模擬等下游應用的實際需求深度契合，為 3D 內容生產的自動化開闢了新的可能性。後續研究若能在部件互動、階層化架構、物理屬性聯合生成等方向取得突破，將進一步推動 3D 生成技術從「視覺逼真」邁向「功能完整」的更高階段。

## 論文問答

**Q1：CubePart 主要解決了什麼核心問題？**
A：CubePart 解決的是互動式 3D 資產生成中的「部件結構控制」問題。在現代遊戲與模擬應用中，3D 資產通常需要被分解為特定的語義部件（例如車子的四個輪子與一個車體），才能支援動畫、物理模擬與腳本化行為。然而現有的 3D 生成模型只能產出整體式網格或無法對齊應用需求的任意部件分解，使得開發者難以直接使用生成結果。CubePart 透過讓使用者以開放詞彙的部件架構作為推理時控制信號，填補了這個從「生成幾何」到「可用於遊戲邏輯」之間的關鍵缺口。

**Q2：為什麼現有的 3D 生成方法或基於 2D 的方法無法解決這個問題？**
A：現有的 3D 生成模型（如整體式網格生成器）雖然能合成複雜幾何，但完全缺乏明確的部件結構；而部分支援部件分解的方法（如 OmniPart 等）所產出的部件集合是任意的，無法對齊到應用程式所要求的特定部件架構。另一方面，基於 2D 分割遮罩的方法（如利用 SAM 等模型）受限於視角依賴性，無法表示或控制在當前視角下被遮擋的部件（例如從正面視角無法指定動物的尾巴）。更根本地說，2D 控制信號在提升至 3D 時本質上是模糊且視角相關的，因此並不適合用於定義完整的 3D 語義分解。

**Q3：為什麼這項研究對該領域而言是重要的？**
A：這項研究的重要性在於它直指一個產業瓶頸——目前創建符合目標部件組成的網格仍高度依賴人工，藝術家必須手動分解幾何、分配一致的標籤，並確保部件能乾淨地組裝，這項工作在資產多樣性增加時難以規模化。CubePart 提出了一個 3D 原生、以架構為驅動的控制介面，使得使用者能在生成階段就明確指定物件的語義結構，同時保有靈活性以適應不同應用對同一物件的不同分解需求。這種「文字即通用控制介面」的設計理念，為可控 3D 生成設立了新的範式，並能直接服務於遊戲、模擬與機器人等下游應用。

**Q4：CubePart 的核心方法論是什麼？**
A：CubePart 的核心方法論是一個兩階段生成架構，將「全局形狀合成」與「部件級解碼」明確分離。在第一階段，模型根據全局文字提示與部件架構（開放式部件名稱列表）合成物件的整體形狀與部件佈局；在第二階段，模型對每個部件進行解碼，產出結構完整的單部件網格。這種設計使得每個部件都是獨立、結構完整的網格，能夠組裝成連貫的物件，同時尊重使用者指定的語義結構。

**Q5：CubePart 的關鍵創新點有哪些？**
A：第一項關鍵創新是將「部件架構」提升為推理時的顯式控制信號，使用者可以透過開放式列表自由定義部件名稱，而非受限於預定義的封閉詞彙。第二項創新是可擴展的數據管線，用於建構一個大規模的開放詞彙、部件標註 3D 數據集，這是支撐模型學習的基礎。第三項創新是兩階段生成架構的設計理念——將全局形狀合成與部件級解碼解耦，使得模型能在保持整體一致性的同時，產出每個部件都結構完整且語義正確的網格。

**Q6：為什麼採用兩階段架構而非端到端設計？**
A：兩階段架構的設計選擇反映了「關注點分離」的原則：全局形狀合成負責捕捉物件的整體幾何與部件間的空間關係，而部件級解碼則專注於每個部件自身的細節與結構完整性。這種分離使得模型能在兩個層級上分別最佳化，避免端到端模型常見的「部件融合」或「部件殘缺」問題。此外，兩階段設計也提供了模組化優勢——未來可以獨立替換或升級全局合成器與部件解碼器，而無需重新訓練整個系統。

**Q7：CubePart 使用了哪些基準測試或資料集進行評估？**
A：CubePart 引入了一個可擴展的數據管線來建構大規模的開放詞彙、部件標註 3D 數據集，這是該研究能夠實現的基礎設施。在評估上，論文將 CubePart 與現有的單部件網格生成器（如產生整體式網格的方法）以及任意部件分解方法（如 OmniPart 等）進行比較，並展示了在部件對齊準確性、組裝一致性與下游可用性上的優勢。具體的定量指標與定性比較涵蓋了部件語義對齊、幾何品質以及在遊戲引擎中的整合表現。

**Q8：CubePart 的關鍵實驗結果為何？**
A：關鍵結果顯示 CubePart 能根據使用者定義的部件架構（例如「車體、排氣管、車輪、頭燈、槍管、蓋子、底座」）生成多個結構完整的單部件網格，並且這些部件能組裝成連貫的物件。相較於 OmniPart 等基於 2D 遮罩的方法，CubePart 不受視角限制，能完整指定包括被遮擋部件在內的所有語義組件。此外，生成的資產可直接整合進遊戲引擎，無需手動後處理即可由動畫與行為腳本驅動，這在實務上是一大突破。

**Q9：有哪些消融實驗支持了設計選擇？**
A：雖然完整細節需參閱論文，但可預期消融實驗涵蓋了：移除兩階段架構改為端到端生成時的部件品質下降、移除部件架構控制時模型退回到任意分解的表現、數據管線規模對開放詞彙泛化能力的影響，以及不同部件架構複雜度下的模型表現。這些消融共同驗證了「部件架構作為顯式控制信號」與「兩階段分離」這兩個核心設計選擇的必要性。

**Q10：哪些實際應用場景最能受益於 CubePart？**
A：遊戲開發是最直接的受益場景——開發者可以快速生成符合遊戲邏輯預期部件架構的車輛、角色、武器、容器等資產，省去大量手動建模與分解工作。物理模擬應用（如機器人模擬、虛擬環境訓練）也能直接利用這些部件化資產進行剛體動力學、可動關節等模擬。此外，動畫綁定（rigging）流程可以從已分解的部件網格直接開始，無需先切割網格再製作骨架，大幅縮短製作管線。

**Q11：CubePart 如何與現有工具鏈整合？**
A：CubePart 生成的資產是標準的多部件網格格式，可直接匯入 Unity、Unreal、Roblox 等主流遊戲引擎，無需額外的網格切割或標籤對齊後處理。這意味著現有的動畫系統、物理模擬系統與行為腳本可以直接以「部件」為單位操作這些資產，例如讓車門打開、輪子旋轉、砲塔轉向等。此外，論文也展示了 CubePart 能接受現有網格作為輸入，將其分解為符合輸入部件架構的多部件網格，這對於改造既有資產庫特別有價值。

**Q12：CubePart 對該領域的更廣泛影響是什麼？**
A：CubePart 的更廣泛影響在於它推動了 3D 生成從「幾何合成」走向「結構化、可控合成」的典範轉移，證明了文字不僅能描述物件外觀，也能作為結構藍圖來控制生成過程。這種「文字即通用控制介面」的理念可望延伸到機器人（指定可操作部件）、AR/VR（場景物件互動）、數位孿生（工業設備部件化）等領域。同時，開放詞彙的設計降低了 3D 內容創作的門檻，使得非專業使用者也能透過自然語言描述生成符合應用需求的部件化資產。

**Q13：CubePart 論文承認了哪些限制？**
A：作為一個生成式框架，CubePart 的輸出品質仍受限於訓練資料的覆蓋範圍與標註品質，對於極為罕見或高度風格化的物件類別可能表現不佳。此外，部件架構的複雜度（部件數量與語義粒度）可能存在實際上限，過於細碎的部件分解可能挑戰模型的組裝一致性。文字描述本身的模糊性也可能導致不同使用者對同一部件名稱有不同預期，這在開放詞彙設定下是難以完全避免的。

**Q14：CubePart 可能出現哪些失敗案例？**
A：可能的失敗案例包括：當部件架構中的部件在語義上高度重疊（例如「車體」與「車身」同時存在）時，模型可能產生冗餘或衝突的部件；對於具有複雜內部結構的物件（如機械裝置的內部齒輪），模型可能難以產出語義正確的內部部件；當輸入部件名稱極為罕見或抽象時，模型可能無法將其對應到合理的幾何區域。此外，在部件之間的接縫處，網格品質可能不如單一整體式網格平滑。

**Q15：基於 CubePart 的未來研究方向有哪些？**
A：未來方向可包括：提升單部件網格的幾何與紋理品質，使其能與頂級整體式生成器媲美；擴展支援更複雜的部件關係（如階層式部件、可動關節的顯式標註）；結合其他控制模態（如草圖、參考圖、點雲）以提供更豐富的創作介面；以及探索即時互動式生成，使遊戲開發者能在編輯器中即時調整部件架構並看到結果。此外，將 CubePart 與大型多模態模型結合，使其能理解更抽象的部件功能描述（例如「可開合的容器」），也是值得探索的方向。

## 實務應用指南

### 適用場景

1. **遊戲資產自動化生產**：MMO、沙盒或 Roguelike 類遊戲需要大量具備語義部件的 3D 資產（車輛、武器、怪物、家具）。CubePart 可讓策劃直接以「賽車 + {車身、前左輪、前右輪、後左輪、後右輪、排氣管、頭燈}」的描述批次生成符合動畫骨架與物理碰撞體設定的部件化網格，省去美術拆件流程。

2. **Roblox / UGC 平台創作者工具**：將 CubePart 封裝為創作者後台的「部件生成器」，讓一般玩家透過自然語言描述產生可被 Lua/Luau 腳本直接操控的部件化 Mesh（如可開啟的門、可旋轉的砲塔），降低 UGC 內容的技術門檻。

3. **機器人與自駕車模擬環境**：模擬器需要大量可拆解的場景物件（可開啟的後車廂、可分離的車門、可翻倒的椅子）以測試邊界情況互動。CubePart 的部件可控特性可直接生成符合物理模擬需求的資產。

4. **VR/AR 互動教學與工業訓練**：例如醫療訓練需要可拆解的人體模型（頭顱、肋骨、心臟），或工業 AR 需要可拆解的機械模型（馬達、齒輪、外殼）。CubePart 可根據教學腳本自動產生對應部件，便於逐步拆解演示。

5. **既有資產的語義重組**：對於已存在的單體 Mesh（如藝術家手刻的高品質模型），CubePart 可作為「逆向拆件工具」，依使用者定義的 schema 重新切割出語義部件，便於導入新專案或新遊戲引擎。

### 實作前置條件

**資料層面**
- 需要一個大規模、開放詞彙、部件標註的 3D 數據集。論文中提到他們建構了可擴展的數據管線（scalable data pipeline），實作者需具備從原始 3D 模型庫（如 Objaverse、PartNet、ShapeNet）自動產生部件標註的能力，或取得作者釋出的資料集。
- 部件標註需具備一致性（同一語義在不同物件中標註方式一致）與覆蓋率（涵蓋足夠多樣的物件類別）。

**運算資源**
- 訓練階段：兩階段架構（全局形狀合成 + 部件級解碼）通常需要多張高階 GPU（如 A100/H100），建議至少 8 卡以上節點。
- 推論階段：單張高階消費級 GPU（如 RTX 4090）即可運行單次生成，但若要批次服務需考慮 GPU 池化與排程。

**技能門檻**
- 3D 深度學習基礎：diffusion model、transformer、NeRF / 3D Gaussian / mesh 表徵。
- 網格處理：mesh segmentation、mesh repair、UV unwrapping、bounding volume hierarchy。
- 遊戲引擎整合：Unity / Unreal / Roblox Studio 的 mesh 匯入管線、rigging、collider 設定。
- 資料工程：自動化部件標註的 LLM 輔助流程、3D 模型品質過濾。

### 實作步驟建議

1. **釐清目標產出與 schema 設計**
   - 與下游應用方（遊戲策劃、模擬工程師）共同定義常用物件類別的部件 schema 範本。
   - 將 schema 抽象為可程式化的 JSON / YAML 格式，作為模型輸入契約。

2. **建立或取得部件標註資料集**
   - 若無現成資料，可參考論文資料管線：先用 LLM 為 3D 模型產生候選部件名稱，再以 3D segmentation 模型驗證，最後由人工抽樣校正。
   - 確保資料集涵蓋目標應用場景的物件類別。

3. **訓練兩階段模型**
   - 第一階段：訓練全局形狀合成模型（輸入全域文本提示，輸出整體形狀潛在表示）。
   - 第二階段：訓練部件級解碼模型（輸入全域潛在表示 + 部件名稱，輸出對應部件網格）。
   - 採用分離架構的好處是可動態調整 schema 長度，無需重新訓練。

4. **建立推論服務**
   - 將模型封裝為 REST / gRPC API，輸入為文本提示 + schema，輸出為多個 mesh 檔案（建議採 glTF / FBX 格式以利遊戲引擎匯入）。
   - 加入 schema 合法性檢查、部件數量上限、生成時間預估等保護機制。

5. **遊戲引擎整合層**
   - 撰寫引擎插件（Unity AssetPostprocessor、Unreal Editor Utility、Roblox Studio Plugin），自動將生成的多部件 mesh 綁定到對應的節點、附加 collider、生成動畫 rig。
   - 提供行為腳本範本（如「車輪旋轉」、「門開啟」），讓使用者一鍵套用。

6. **既有 mesh 拆件功能**
   - 若需支援「輸入既有 mesh、輸出部件化 mesh」，需額外訓練或串接 mesh segmentation 模型作為前置處理。

7. **品質評估與迭代**
   - 建立評估指標：部件語義一致性（部件名稱與實際幾何的對應）、部件組裝完整性（拼合後是否無縫）、下游可用性（能否直接被動畫 / 物理系統驅動）。
   - 收集使用者反饋，持續優化資料集與模型。

### 潛在風險與注意事項

- **開放詞彙的歧義性**：使用者輸入的部件名稱可能過於抽象（「前面」、「頂部」）或過於細碎（「左前輪第二根輻條」），導致生成結果不穩定。**緩解**：在 API 端提供 schema 範本與自動補全，並對部件粒度做合理性檢查。

- **部件組裝錯位**：各部件獨立生成後，拼合時可能出現縫隙、重疊或錯位。**緩解**：在訓練階段加入部件間的空間一致性約束；推論後加入 mesh repair 後處理（孔洞填補、邊界對齊）。

- **資料集偏誤**：若訓練資料集中某些物件類別（如車輛）佔比過高，模型在其他類別（如家具、生物）表現可能下降。**緩解**：採用均衡抽樣、類別感知損失權重，或在推論時加入 few-shot 範例。

- **下游引擎相容性**：不同遊戲引擎對 mesh 格式、座標系、scale 預設不同，可能導致匯入後部件錯位。**緩解**：在匯入層加入座標系與單位轉換，並提供引擎專屬預設。

- **智慧財產權與內容審核**：開放詞彙生成可能被濫用產生不當內容。**緩解**：在文本輸入端加入內容過濾器，並對生成結果做安全審核。

- **推論成本**：每生成一個完整物件需執行多次部件解碼，單次推論成本可能偏高。**緩解**：採用部件並行解碼、模型蒸餾、或快取常見 schema 的結果。

### 與其他技術的整合建議

- **與既有 3D 生成模型互補**：對於需要高品質整體形狀但不在意部件結構的場景，可繼續使用 Hunyuan3D、Trellis、3D-DiT 等單體生成模型；CubePart 適用於明確需要部件控制的場景。兩者可組成「先單體生成、再部件化」的管線。

- **與 2D 分割模型互補**：若使用者已有 2D 參考圖，可先用 SAM 2 / Grounding DINO 產生 2D mask，再將 mask 投影到 3D 作為 CubePart 的額外條件輸入，補強文本描述的不足。

- **與動畫 / 物理引擎整合**：生成的部件 mesh 可直接接入 Unity Mecanim、Unreal Control Rig、Roblox Animation Editor，並透過 PhysX / Chaos / Bullet 設定剛體。建議在引擎層封裝「部件 → 動畫節點 → 物理體」的自動化綁定流程。

- **與 LLM 整合**：可讓 LLM 根據使用者的高層次描述（如「一輛可開門的跑車」）自動推導出 schema，再餵給 CubePart，形成「自然語言 → schema → 部件化 mesh」的端到端管線。

- **與資產管理系統整合**：將 CubePart 整合進 DAM（Digital Asset Management）系統，自動為生成的部件打 metadata 標籤（部件名稱、語義類別、適用動畫），便於搜尋與重用。

### 給不同背景讀者的閱讀建議

**初學者**：建議先閱讀第 1 節（Introduction）了解問題動機——為什麼「部件可控」對遊戲與模擬至關重要。圖 1 的視覺化範例（海龜背城堡、賽車、人體模型）能幫助直觀理解輸出形態。可暫時跳過技術細節，專注於「輸入是什麼、輸出是什麼、能解決什麼問題」。

**AI 工程師**：重點閱讀方法章節中的「兩階段生成架構」與「資料管線」部分。理解全局形狀合成與部件級解碼如何解耦，可借鑑此設計模式應用於其他需要結構化控制的生成任務（如場景佈局、文件版面）。同時關注開放詞彙條件如何注入 diffusion / transformer 架構。

**研究者**：建議深入閱讀資料管線的設計（如何從無標註 3D 模型自動產生部件標註）以及評估實驗。開放詞彙部件生成是一個新興方向，可延伸的研究問題包括：部件間的物理合理性、跨類別泛化能力、與 LLM 結合的 schema 自動推導、部件動畫的端到端生成。

**產品經理**：重點關注第 1 節的應用場景與結論中的「可直接整合進遊戲引擎、無需後處理」聲明。評估此技術對自家產品的價值時，應思考：現有資產生產流程中「拆件」環節佔多少成本？下游應用（動畫、物理、腳本）對部件 schema 的需求有多強烈？CubePart 的開放詞彙特性是否足以覆蓋多樣化的業務場景？建議先以小範圍 POC 驗證生成品質與下游可用性，再評估大規模導入的 ROI。
