# LLM 代理能夠看見程式碼倉庫

**原文標題：** LLM Agents Can See Code Repositories

## ⚡ TL;DR

現有 LLM 編碼代理僅以文字形式讀取程式碼倉庫，忽略了資料夾層級與依賴關係等視覺結構資訊。
本文提出 SeeRepo，透過 AST 分析建構依賴圖並渲染為圖片，作為文字介面的輔助模態。
實驗顯示混合設計降低輸入 token 達 26%，維持或提升修復準確率，視覺化於故障定位最有效。

## 摘要翻譯

由大型語言模型 (Large Language Models, LLMs) 驅動的編碼代理 (Coding Agents) 已在軟體工程 (Software Engineering, SE) 任務中展現出強大的效能。然而，大多數代理幾乎完全以文字形式處理程式碼倉庫 (Code Repositories)，這與人類開發者使用資料夾層級結構 (Folder Hierarchies) 和依賴關係 (Dependency Relationships) 等視覺結構來在大型程式碼庫 (Codebase) 中掌握整體結構的方式有所不同。鑒於多模態大型語言模型 (Multimodal Large Language Models, MLLMs) 的發展，代理是否能有效受益於倉庫的視覺化表示 (Visual Representations) 仍是一個開放性問題。本文提出了第一個針對基於 LLM 的代理在倉庫層級議題修復 (Repository-level Issue Resolution) 上使用視覺化倉庫表示的系統性實證研究 (Empirical Study)。我們評估了四個近期多模態模型。我們的結果顯示，嚴格的純視覺設定 (Vision-only Setup) 會降低議題修復準確率 (Issue Resolution Accuracy) 並增加 Token 成本，因為代理缺乏足夠的符號細節 (Symbolic Detail)，而必須以重複的視覺查詢 (Visual Queries) 來補償。相較之下，將倉庫結構的視覺化圖 (Visual Graphs) 作為輔助模態 (Supplementary Modality) 與標準文字介面 (Text Interfaces) 整合，能幫助代理更有效率地理解結構：輸入 Token 消耗 (Input Token Consumption) 最多可減少 26%，同時議題修復準確率得以維持或提升。視覺化在故障定位 (Fault Localization) 以及代理自主控制探索深度 (Exploration Depth) 時最為有用。這些發現為下一代編碼代理指明了一個實用的混合文字與視覺設計 (Hybrid Text-and-Vision Design) 方向。

### 核心貢獻（3～5點）
- **首創系統性實證研究**：針對基於 LLM 的代理在倉庫層級議題修復任務上，首次系統性地比較視覺化倉庫表示與純文字介面的效能差異。
- **揭示純視覺設定的局限性**：證實嚴格的純視覺設定會降低議題修復準確率並增加 Token 成本，原因在於代理缺乏足夠的符號細節，需以重複的視覺查詢補償。
- **驗證混合模態設計的效益**：將視覺化圖作為輔助模態與文字介面整合，可使輸入 Token 消耗最多減少 26%，同時維持或提升議題修復準確率。
- **釐清視覺化的最佳適用情境**：視覺化在故障定位階段以及代理自主控制探索深度時最為有用，為視覺化工具的調用時機提供實證指引。
- **提出下一代編碼代理的設計方向**：為編碼代理的設計提出「混合文字與視覺」的實用架構，兼顧結構理解效率與符號細節保留。

### 適合對象
- **LLM 代理與編碼代理研究者**：從事 AI 輔助軟體工程、自動化程式修復的學者與工程師。
- **多模態模型應用開發者**：關注 MLLMs 在程式碼理解、結構化資料處理等非傳統領域應用的研究人員。
- **軟體工程實務工作者**：大型程式碼庫維護者、開發工具設計師，以及對提升開發者生產力工具感興趣的技術主管。
- **人機互動 (HCI) 領域學者**：研究視覺化介面如何輔助人類與 AI 代理理解複雜資訊結構的跨領域研究者。

## 深度分析

#### 方法論解析

本文提出 SeeRepo，一個專為倉庫層級議題修復 (Repository-level Issue Resolution) 設計的多模態增強 (Multimodal Augmentation) 工具，其核心方法論可從三個層面深入剖析：

**1. 圖結構建構：基於 AST 的多關係依賴圖**

SeeRepo 並非簡單地將檔案系統層級視覺化，而是採用基於抽象語法樹 (Abstract Syntax Tree, AST) 的靜態分析技術，從原始碼中萃取四種關鍵的結構關係 (Structural Relationships)：
- **包含關係 (Containment)**：類別與方法、模組與套件之間的巢狀結構
- **匯入關係 (Import)**：模組間的引用
- **呼叫關係 (Invocation)**：函數之間的執行依賴
- **繼承關係 (Inheritance)**：類別層級體系

這種多關係圖 (Multi-relation Dependency Graph) 的設計，超越了傳統僅以資料夾層級結構 (Folder Hierarchies) 表示倉庫的方式，能捕捉程式碼語意層面的耦合關係。相較於既有研究將圖編碼 (Graph Encodings) 線性化 (Linearizing) 後輸入模型的做法，SeeRepo 保留了圖的非線性拓樸資訊。

**2. 視覺化渲染：Graphviz 子圖轉 PNG**

給定一個查詢節點 (Query Node)，SeeRepo 以該節點為中心渲染 Graphviz 子圖，並輸出為 PNG 影像。這項設計的關鍵在於：
- **空間分組 (Spatial Grouping)**：利用二維佈局 (Two-dimensional Layout) 呈現節點間的相對位置，使模型能透過空間鄰近性 (Spatial Proximity) 推斷語意關聯
- **中心化視角**：以目標節點為中心的子圖避免了全域圖的爆炸問題，符合長時程倉庫工作流程 (Long-horizon Repository Workflows) 中的漸進式探索需求
- **影像格式選擇**：PNG 為靜態點陣圖，雖然犧牲了互動性，但換來了與多模態大型語言模型 (MLLMs) 介面的無縫整合

**3. 混合介面設計：文字與視覺的互補**

SeeRepo 並非要取代文字介面 (Text Interfaces)，而是作為輔助模態 (Supplementary Modality) 與標準的 bash 文字存取並存。代理 (Agent) 可在需要結構性理解時呼叫視覺查詢 (Visual Queries)，在需要精確符號細節 (Symbolic Detail) 時回歸文字存取。這種設計呼應了人類開發者實際的工作模式——既閱讀程式碼，也瀏覽架構圖。

方法論上的限制值得注意：SeeRepo 採用靜態分析，無法捕捉動態執行路徑；PNG 渲染為靜態影像，無法支援互動式縮放或過濾；圖的深度與廣度由預設策略決定，可能不適應所有探索情境。

#### 實驗數據解讀

本文以四個研究問題 (RQ1–RQ4) 為骨幹，系統性地驗證視覺化表示對編碼代理 (Coding Agents) 的影響。以下逐一解讀關鍵數據：

**RQ1：純視覺設定的效能邊界**

實驗將 Mini-SWE-Agent 設定為純視覺模式 (Vision-only Setup)，bash 導航指令僅回傳圖像。數據揭示了嚴峻的效能衰退：

| 模型 | 文字模式 Pass@1 | 純視覺模式 Pass@1 | 準確率下降 | Token 成本變化 |
|------|----------------|------------------|-----------|---------------|
| GPT-5-mini | 55.0% | 41.4% | −13.6 | +42% |
| Doubao-Seed-2.0-Lite | 51.0% | 16.9% | −34.1 | +268% |
| Kimi K2.5 | 70.3% | 55.0% | −15.3 | +27% |

這組數據的深層意涵在於：**當代理失去文字存取能力時，會以反覆的視覺查詢 (Repeated Visual Queries) 來補償缺失的符號資訊**，導致 Token 消耗不降反升。Doubao-Seed-2.0-Lite 的 +268% 成本增幅尤為驚人，顯示部分模型在缺乏文字錨點時會陷入「視覺搜尋迴圈」。此結果明確劃定了純視覺範式的效能邊界——當前 MLLMs 仍高度依賴符號線索 (Symbolic Cues) 進行程式碼推理。

**RQ2：混合文字+視覺的整合效益**

將 SeeRepo 作為輔助模態整合後，數據呈現截然不同的趨勢：

| 模型 | Pass@1 變化 | 輸入 Token 減少 | 成本減少 |
|------|------------|----------------|---------|
| GPT-5-mini | +0.4 (55.0%→55.4%) | −25% | −26% |
| GPT-5.1 | −2.2 | — | −46% |
| Kimi K2.5 | +1.8 (68.8%→70.6%) | — | −3% |
| Doubao-Seed-2.0-Lite | +1.0 | — | −6% |

關鍵發現是**準確率維持或提升的同時，輸入 Token 消耗降低達 26%**。這驗證了視覺化表示的「資訊密度優勢」——一張圖能在較少的 Token 中傳達比線性文字更豐富的結構資訊。GPT-5.1 的 −46% 成本降幅特別值得關注，顯示視覺化對不同模型架構的效益存在差異化。

**RQ3：視覺化佈局設計的影響**

實驗比較了三種渲染策略——圖形 (Graph)、巢狀 (Nested)、表格 (Tabular)——在不同層級深度下的表現：

- **圖形佈局**：Token 減少最多（−25% 輸入、−26% 成本），Pass@1 為 55.4%（+0.4）
- **巢狀佈局**：Token 成本略高，Pass@1 提升 +0.8
- **表格佈局**：Token 成本略高，Pass@1 提升 +1.2

在層級深度方面，**動態深度策略 (Dynamic Depth)** 表現最佳，在所有深度配置中達成最大的 Token 與成本降幅，同時維持 +0.4 的 Pass@1 增益。這暗示由代理自主控制探索深度 (Exploration Depth) 比預設固定深度更有效率。

**RQ4：視覺化工具的最佳調用階段**

將視覺化整合至議題修復管線的三個階段——故障定位 (Fault Localization)、修復 (Repair)、補丁驗證 (Patch Validation)——結果顯示**故障定位階段是視覺化效益最大的環節**：Pass@1 達 55.4%（+0.4），輸入 Token 減少 25%，成本降低 26%。這與軟體工程實務中的經驗法則一致——理解「在哪裡改」往往比「怎麼改」更需要全域結構視野。

#### 與現有研究的比較

本文在程式碼倉庫理解的文獻譜系中佔據獨特位置，可從三個面向進行定位：

**1. 與圖基表示研究的比較**

既有研究如基於圖的抽象 (Graph-based Abstractions) [6, 15, 21] 已探索過結構化表示，但這些方法最終仍將圖線性化為序列輸入 [20]，導致關聯線索 (Relational Cues) 的損失。SeeRepo 的突破在於**保留了圖的二維空間特性**，使 MLLMs 能直接感知非線性表示 (Non-linear Representations) 中的拓樸結構。這填補了「結構化表示」與「模型輸入形式」之間的轉譯鴻溝。

**2. 與多模態程式碼理解的比較**

過去的多模態程式碼研究多聚焦於 UI 截圖、流程圖或設計稿與程式碼的對應 [37]，較少觸及倉庫層級的結構視覺化。本文將多模態典範從「視覺輸入→程式碼生成」擴展至「結構視覺→導航決策」，拓展了多模態模型在軟體工程 (SE) 任務中的應用邊界。

**3. 與代理框架研究的比較**

SWE-Agent 系列 [9, 11, 16, 39, 43–45] 已建立成熟的文字代理範式，但本文是第一個系統性評估視覺化增強對代理效能影響的工作。相較於純粹擴展上下文視窗 (Context Window) 或精調檢索策略的做法，SeeRepo 提供了一條「不改變模型架構，僅改變輸入模態」的輕量化路徑。

**限制與不足**

- **模型覆蓋面**：僅評估四個 MLLMs，缺乏對開源模型（如 LLaVA、Qwen-VL）的系統性測試
- **任務範圍**：聚焦於議題修復，未涵蓋程式碼審查、重構、測試生成等其他 SE 任務
- **靜態分析侷限**：AST 為基礎的圖無法反映動態行為，如執行時的間接呼叫
- **缺乏人類對照**：未與人類開發者使用 IDE 視覺化工具的表現進行基準比較

#### 可重現性評估

從可重現性角度審視，本文存在若干優勢與隱憂：

**有利因素**

- **任務基準明確**：採用 SWE-Bench 類型的議題修復任務，並在 SWE-Rebench Leaderboard 2026.03 [2] 與 SWE-QA [27] 上進行額外驗證，提升了結果的外部效度
- **模型版本具體**：明確列出 GPT-5-mini [25]、GPT-5.1 [26]、Doubao-Seed-2.0-Lite [3]、Kimi K2.5 [22] 等具體模型版本
- **工具鏈透明**：SeeRepo 的核心元件——AST 靜態分析、Graphviz 渲染、PNG 輸出——皆為成熟開源技術，重建門檻低
- **評估指標標準**：採用 Pass@1 與 Token 成本作為雙重指標，符合業界慣例

**潛在障礙**

- **API 存取成本**：四個評估模型中有三個為閉源商業 API（GPT-5-mini、GPT-5.1、Doubao-Seed-2.0-Lite），重現實驗需承擔顯著的 API 費用
- **代理框架相依**：基於 Mini-SWE-Agent 進行改造，其內部提示詞與決策邏輯的細節未完全公開
- **圖渲染參數**：Graphviz 的佈局演算法選擇（dot、neato、fdp 等）、節點大小、邊權重等參數對結果有敏感性，但論文中未充分披露
- **基準資料集版本**：SWE-Bench 系列基準持續演進，不同快照的結果可能不可直接比較

**建議補強措施**

若要提升可重現性，作者應釋出 SeeRepo 的完整源碼、預設渲染配置、提示詞範本，以及在固定隨機種子下的評估日誌。此外，提供 Docker 映像檔以封裝完整的代理執行環境，將大幅降低重現門檻。

#### 未來研究方向

本文開啟了多模態編碼代理的研究新維度，以下方向值得深入探索：

**1. 動態與互動式視覺化**

當前的 PNG 靜態影像無法支援縮放、篩選、展開等互動操作。**未來可探索將 SeeRepo 升級為支援代理主動操作的互動式視覺化介面**，例如允許代理點擊節點以展開子圖，或透過文字指令動態調整視覺化焦點。這將更貼近人類開發者使用 IDE 的體驗。

**2. 跨模態注意力機制研究**

視覺化圖與文字程式碼如何在不同模型層級中融合？**可深入分析 MLLMs 內部的跨模態注意力 (Cross-modal Attention) 模式**，釐清視覺資訊在哪些 Transformer 層被整合，以及結構線索如何影響符號推理。這將為模型架構設計提供理論指引。

**3. 從靜態圖到時序演化**

軟體倉庫是動態演化的系統。**追蹤圖結構隨 commit 的變化**，並將時序資訊編碼為視覺化維度（如節點顏色表示變更頻率），可能幫助代理理解技術債累積、模組耦合演化等高階議題。

**4. 領域特定視覺化語言**

不同程式語言與框架有不同的結構慣例。**為特定領域（如深度學習框架、嵌入式系統、分散式系統）設計專屬的視覺化語法**，可能比通用圖佈局更有效。例如，TensorFlow 的計算圖與微服務的呼叫圖應有不同的視覺化策略。

**5. 與其他增強技術的組合**

SeeRepo 的效益可與其他代理增強技術疊加：
- **檢索增強生成 (RAG)**：以視覺化圖作為檢索的結構索引
- **思維鏈 (Chain-of-Thought) 提示**：引導代理在視覺觀察後進行結構化推理
- **工具使用學習**：讓代理學會在何時呼叫視覺化工具最為划算

**6. 從議題修復到更廣泛的 SE 任務**

將 SeeRepo 範式擴展至：
- **程式碼審查**：視覺化變更影響範圍
- **重構建議**：以圖呈現重構前後的結構差異
- **測試生成**：視覺化覆蓋率與依賴路徑
- ** onboarding 新成員**：以視覺化圖輔助理解陌生倉庫

**7. 人機協作視覺化**

最終極的問題是：**人類開發者與 AI 代理能否共享同一視覺化語境？** 若 SeeRepo 的圖能被投射到 IDE 中供人類審閱，將開創新型的人機協作除錯模式——代理以視覺化呈現推理過程，人類以視覺化引導代理探索方向。

這些方向不僅延伸了本文的技術貢獻，更指向一個更宏觀的願景：**讓程式碼倉庫成為人類與 AI 都能「看見」的共享認知空間**。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文探討的是 LLM 編碼代理如何與程式碼倉庫互動的根本問題。現有代理幾乎完全將倉庫扁平化為文字序列來處理，這與人類開發者透過資料夾層級結構、依賴關係等視覺結構來理解大型程式碼庫的方式截然不同。論文的核心理念在於質疑「文字是否真的是呈現倉庫上下文給現代基礎模型的最有效模態」，並提出多模態視覺化表示作為潛在的解決方案。

**Q2：為什麼現有的以文字為中心的方法存在不足？**
A：現有的文字為中心範式將異質產物（包括原始碼、文件、結構關係等）線性化為序列輸入，這迫使模型必須從線性文字中推論原本以非線性或視覺化方式呈現的結構資訊。即使是基於圖的抽象或圖編碼，最終在推論時仍會被線性化以供模型輸入，導致重要的關聯線索與空間分組資訊流失。這種資訊損失在有限的上下文預算下尤其嚴重，使代理難以有效掌握長時程倉庫工作流程中的整體結構。

**Q3：這項研究為何重要？**
A：這是首個針對倉庫層級任務的多模態基礎模型系統性實證研究，填補了現有文獻中關於視覺化表示如何影響編碼代理效能的空白。隨著多模態大型語言模型（MLLMs）的快速發展，理解視覺化表示是否能真正幫助代理導航大型程式碼庫變得至關重要。論文的發現指向一個務實的混合文字與視覺設計方向，對下一代編碼代理的設計具有直接的實務指導意義。

**Q4：本論文提出的核心方法是什麼？**
A：本論文提出了 SeeRepo，一個專為倉庫層級議題修復設計的多模態增強工具。SeeRepo 使用基於 AST 的靜態分析來建構多關係依賴圖，捕捉包含、匯入、調用、繼承等關係。給定一個查詢節點後，它會以 Graphviz 將以該節點為中心的子圖渲染為 PNG 圖片，與傳統的基於文字的程式碼存取一同提供給代理，從而結合視覺帶來的空間結構感知與文字帶來的符號精確性。

**Q5：本研究的關鍵創新點為何？**
A：本研究的關鍵創新在於提出了一種混合文字與視覺的設計理念，而非單純地用視覺取代文字。SeeRepo 將視覺化圖渲染作為輔助模態，與標準的文字介面並行運作，使代理能同時享有視覺的空間結構優勢與文字的符號細節優勢。這種設計突破了純視覺設定的效能瓶頸，同時避免了純文字方法在結構理解上的不足，為編碼代理的設計提供了嶄新的範式。

**Q6：本研究探討了哪些設計選擇？**
A：本研究系統性地探討了四個設計維度：表示模態（純文字、純視覺、混合）、圖文平衡、視覺化佈局設計（圖形、巢狀、表格三種策略），以及視覺化工具調用階段（定位、修復、補丁驗證三個階段）。此外還研究了不同的階層深度策略，包括固定深度與動態深度的比較，以及代理自主控制探索深度的能力。這些設計選擇的全面探索為未來的混合設計提供了具體的指引。

**Q7：本研究使用了哪些基準測試與模型？**
A：本研究以倉庫層級議題修復為核心任務，使用 Mini-SWE-Agent 作為基礎代理框架，並評估了四個最新的多模態模型：GPT-5-mini、GPT-5.1、豆包 Seed-2.0-Lite 以及 Kimi K2.5。除了主要的評估外，研究還在 SWE-Rebench Leaderboard 2026.03 與 SWE-QA 上進行了額外的 GPT-5-mini 評估，以驗證結論的泛化性。

**Q8：本研究的主要實驗結果為何？**
A：純視覺設定在所有模型上都顯著降低了議題修復準確率，例如豆包 Seed-2.0-Lite 從 51.0% 暴跌至 16.9%，且 Token 成本不降反升（最高增加 268%）。相對地，將 SeeRepo 作為輔助模態整合後，輸入 Token 消耗最多減少 26%，同時維持或提升了準確率，例如 GPT-5-mini 的 Pass@1 微升至 55.4%。視覺化在故障定位階段效果最為顯著，顯示出混合設計的實用價值。

**Q9：本研究進行了哪些消融實驗？**
A：本研究比較了三種視覺化佈局策略（圖形、巢狀、表格）在不同階層深度下的表現。結果顯示圖形佈局達成最大的 Token 減少（輸入 Token 減少 25%、成本減少 26%），Pass@1 達到 55.4%；巢狀與表格佈局則以略高的 Token 成本換取微幅的準確率提升（分別為 +0.8 與 +1.2）。在階層深度方面，動態深度策略在所有深度配置中達成最大的輸入 Token 與成本減少，同時維持具競爭力的 Pass@1 增益。

**Q10：本研究的實際應用場景為何？**
A：本研究最直接的應用場景是大型程式碼庫中的軟體議題修復，特別是當開發者需要快速理解陌生倉庫結構時。SeeRepo 的混合設計可整合至現有的編碼代理框架中，幫助代理在故障定位階段更有效率地掌握程式碼結構。對於企業級軟體開發、開源專案維護以及程式碼審查等場景，這種結合視覺與文字的方法都能帶來顯著的效率提升。

**Q11：從產品化的角度，這項研究帶來哪些考量？**
A：產品設計者需要在準確率與 Token 成本之間取得平衡，而本研究的混合設計提供了最佳平衡點。視覺化工具應優先在故障定位階段調用，以獲得最大效益；動態深度探索策略則賦予代理自主控制視覺上下文消耗量的能力。此外，產品應支援多種視覺化佈局選項，讓使用者能根據任務特性選擇最適合的呈現方式。

**Q12：本研究對學術與產業領域的影響為何？**
A：本研究開啟了編碼代理多模態表示的新研究方向，挑戰了長期主導的以文字為中心範式。其發現促使學界重新思考視覺化表示在軟體工程任務中的角色，並可能影響未來基礎模型的設計方向。對產業而言，這項研究為下一代編碼代理的設計提供了實證基礎，推動更高效、更貼近人類開發者工作方式的 AI 輔助工具的發展。

**Q13：本論文承認的限制有哪些？**
A：本研究聚焦於倉庫層級議題修復任務，因此其結論未必能直接泛化至所有軟體工程任務。研究中使用的視覺化表示僅限於圖形渲染，未探索互動式視覺化、三維佈局等其他可能的視覺格式。此外，實驗僅針對四個特定的多模態模型進行評估，結果可能因模型架構或訓練資料的不同而有所差異。

**Q14：本研究揭示了哪些失敗案例？**
A：純視覺設定是最主要的失敗案例：當代理僅能透過視覺化圖存取倉庫時，會因為缺乏足夠的符號細節而反覆進行視覺查詢以補償缺失的資訊，導致 Token 成本飆升卻無法恢復準確率。例如豆包 Seed-2.0-Lite 在純視覺設定下成本暴增 268%，但準確率反而從 51.0% 跌至 16.9%。這顯示當前的 MLLMs 在程式碼推理上仍高度依賴符號線索，純視覺圖無法提供足夠的語意指引。

**Q15：本研究指出哪些未來研究方向？**
A：未來可探索更豐富的視覺化表示方式，例如互動式視覺化、三維佈局或結合動畫效果的呈現，以提供更全面的結構資訊。另一個方向是設計更智慧的混合架構，能根據任務上下文動態調整文字與視覺的比例與調用時機。此外，將視覺化表示的應用擴展至其他軟體工程任務（如程式碼審查、重構、測試生成等）也是值得探索的重要方向。

## 實務應用指南

### 適用場景

1. **大型企業內部程式碼庫的故障定位與修復**：在數百萬行等級的 monorepo 中，傳統文字搜尋容易讓代理迷失在無關檔案中。SeeRepo 的視覺化依賴圖能在故障定位階段提供二維空間線索，幫助代理快速收斂到可疑模組，特別適用於金融、電商等擁有複雜內部依賴的系統。

2. **開源專案的 Issue Triage 與自動化修復**：對於 GitHub 等平台上 issue 數量龐大的開源專案（如 Kubernetes、React），將 SeeRepo 整合進 SWE-Bench 類型的自動化修復流程，可在維持準確率的前提下降低 26% 的 token 成本，使大規模批次修復在經濟上可行。

3. **新進工程師的 Onboarding 與程式碼探索助手**：將 SeeRepo 作為 IDE 外掛或 CLI 工具，讓新人透過視覺化圖譜快速理解陌生倉庫的模組劃分與呼叫關係，彌補文字閱讀時缺乏的全域視角。

4. **程式碼審查（Code Review）輔助工具**：在 PR 審查流程中，自動渲染變更檔案周邊的依賴子圖，讓審查者與 AI 審查代理同時看見結構性影響（例如「此函數被 12 個模組呼叫」），提升審查深度。

5. **CI/CD Pipeline 中的回歸測試與自動修復**：在 nightly build 失敗時，SeeRepo 可輔助代理在大型測試倉庫中定位失敗根因，視覺化圖譜在故障定位階段的效益最為顯著（Pass@1 +0.4、token −25%）。

### 實作前置條件

**資料前置條件**
- 目標程式碼倉庫需可被 AST 解析器完整處理（Python、Java、TypeScript、Go 等主流語言優先；C/C++ 巨集與模板需特殊處理）。
- 需具備倉庫的檔案系統存取權限，以及建置索引所需的磁碟空間（依賴圖通常為原始碼體積的 10–30%）。
- 評估資料集建議採用 SWE-Bench Verified、SWE-Rebench 或 SWE-QA 等標準基準，以利與論文結果對照。

**運算前置條件**
- 需串接支援影像輸入的多模態 LLM API（GPT-5-mini、GPT-5.1、Doubao-Seed-2.0-Lite、Kimi K2.5 等），並確認其 context window 足以容納文字 + 圖片。
- 圖渲染端需安裝 Graphviz（或等效工具如 Mermaid、dagre），並具備 PNG 編碼能力。
- 建議準備獨立的快取層儲存已渲染的子圖，避免重複渲染造成延遲。

**技能前置條件**
- 熟悉 LLM Agent 框架（如 Mini-SWE-Agent、LangGraph、AutoGen）的工具呼叫與狀態管理。
- 具備靜態分析基礎，能使用 tree-sitter、jedi、pyright 等工具建構 AST 與跨檔案依賴。
- 理解 token 經濟學與 prompt 工程，能設計圖文比例與調用時機。

### 實作步驟建議

**步驟一：建構多關係依賴圖**
使用 AST 靜態分析掃描整個倉庫，抽取四類關係：包含關係（檔案→類別→函數）、import 關係、呼叫關係（invocation）、繼承關係。將結果儲存為圖資料庫（如 Neo4j）或記憶體中的 NetworkX 物件，並為每個節點附加中繼資料（檔案路徑、行號、簽章）。

**步驟二：實作子圖渲染器**
撰寫 `render_subgraph(center_node, depth, layout)` 函式：以查詢節點為中心向外展開 N 層鄰居，依選定佈局（graph / nested / tabular）呼叫 Graphviz 產生 PNG。論文中 dynamic depth 策略表現最佳，建議預設採用 dynamic 並允許 agent 控制深度。

**步驟三：設計混合介面的 Agent 工具集**
保留傳統 bash 文字介面（檔案讀取、grep、編輯），新增視覺化工具 `view_repo_graph(query, depth)`。關鍵設計原則：視覺化僅作為輔助模態，不可取代文字存取——純視覺模式會使 GPT-5-mini 從 55.0% 降至 41.4%，且 token 成本上升 42%。

**步驟四：將視覺化綁定至故障定位階段**
依據 RQ4 結論，視覺化在故障定位階段效益最大（Pass@1 +0.4、token −25%、成本 −26%）。建議在 agent 流程中，於「讀取 issue → 定位可疑檔案」之間插入視覺化查詢，而非在修復或驗證階段強行使用。

**步驟五：建立評估管線**
採用 SWE-Bench 格式的資料集，記錄每個任務的 Pass@1、輸入/輸出 token、總成本、調用階段。對照四組配置：text-only、vision-only、hybrid（不同佈局）、hybrid（不同階段），找出符合自家倉庫特性的最佳配置。

**步驟六：調校圖文比例與快取策略**
監控實際部署中的 token 消耗分佈。若發現 agent 反覆查詢同一子圖，應加入 LRU 快取；若圖片過大導致 context 擠壓，可考慮降解析度或限制節點數量上限。

### 潛在風險與注意事項

**風險一：純視覺化的災難性退化**
若誤將 SeeRepo 設為唯一介面（vision-only），所有受測模型皆出現準確率大幅下滑與 token 暴增。GPT-5-mini 成本上升 42%，Doubao-Seed-2.0-Lite 甚至飆漲 268%，因為代理會反覆查詢圖片以補償缺失的符號細節。**緩解措施**：在系統層級強制保留文字介面，視覺化僅作為輔助。

**風險二：模型對視覺品質的敏感度**
MLLM 對圖片中的節點標籤、邊箭頭、佈局擁擠程度相當敏感。過深的展開（depth > 3）容易產生「毛球圖」，模型難以解析。**緩解措施**：限制最大節點數（如 50–80 個）、使用 dynamic depth、優先選用 graph 佈局（成本最低、效益最高）。

**風險三：靜態分析的覆蓋率限制**
動態語言、反射呼叫、生成程式碼無法被 AST 完整捕捉，可能導致依賴圖不完整，誤導代理。**緩解措施**：結合執行期 profiling 或符號執行補強，並在 prompt 中標註「圖中未顯示的依賴可能存在」。

**風險四：跨模型效益不一致**
論文中 GPT-5.1 在加入 SeeRepo 後出現 −2.2 的準確率微降（雖成本降 46%），顯示並非所有模型都能從混合介面中獲益。**緩解措施**：上線前必須在目標模型上做 A/B 測試，不可假設效益普適。

**風險五：圖片帶來的 context 擠壓**
高解析度 PNG 會佔用大量 token（尤其在低壓縮模型中）。**緩解措施**：控制圖片尺寸、量化節點標籤長度、僅在必要時渲染。

### 與其他技術的整合建議

**與 RAG 系統整合**：SeeRepo 的視覺化圖可作為 RAG 的「結構性檢索結果」，與傳統的語意向量檢索互補——語意檢索找「相關程式碼」，視覺化圖找「相關結構」。建議在 RAG pipeline 中，將 issue 描述先做實體抽取（檔名、類別名、函數名），再以這些實體作為 SeeRepo 的查詢中心節點。

**與 IDE 整合**：將 SeeRepo 渲染器封裝為 VS Code 或 JetBrains 的擴充功能，提供「右鍵 → 查看依賴圖」的操作。圖片可顯示於側邊面板，並支援點擊節點跳轉至對應程式碼。

**與 CI/CD 整合**：在 GitHub Actions 或 GitLab CI 中加入 SeeRepo 預渲染步驟——當 PR 開啟時，自動渲染變更檔案周邊的依賴子圖並上傳為 artifact，供後續的 AI 審查代理使用。

**與既有的 SWE Agent 框架整合**：SeeRepo 的設計與 Mini-SWE-Agent 相容，只需新增一個視覺化工具即可。對於 LangGraph 或 AutoGen 使用者，可將 `view_repo_graph` 註冊為標準工具，agent 會依據任務需求自主決定調用時機。

**與監控與可觀測性平台整合**：將每次視覺化查詢的 token、成本、效益記錄至 OpenTelemetry 或 LangSmith，便於持續追蹤 ROI 並調校策略。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與 RQ1 的結論，理解「視覺化不是萬靈丹」這個核心訊息——純視覺模式反而會讓代理變笨且變貴。重點掌握「混合介面」這個設計哲學：文字負責精確符號，視覺負責空間結構，兩者互補而非取代。

**給 AI 工程師**：直接深入 RQ2 與 RQ3 的實驗數據，特別關注圖文比例、佈局選擇（graph 勝出）、dynamic depth 的設計。實作時請嚴格遵守「視覺化作為輔助模態」的原則，並為目標模型建立專屬評估管線，因為跨模型效益不一致（GPT-5.1 為反例）。

**給研究者**：本文最大的價值在於「否定了一個直覺假設」並「框定了效益邊界」。建議從 RQ1 的失敗案例出發，思考為何 MLLM 無法從純視覺圖中提取足夠符號資訊——這涉及視覺編碼的資訊密度、token 化方式、以及 MLLM 對結構性符號的內化能力等開放問題。RQ4 揭示的「階段敏感性」也值得延伸至其他長時程任務。

**給產品經理**：核心訊息是「視覺化能省錢」——在維持或提升準確率的前提下降低 26% 成本，這對 LLM 應用的單位經濟至關重要。建議將 SeeRepo 定位為「成本優化工具」而非「能力增強工具」來推動內部採用，並優先在故障定位場景（ROI 最高）試行，再逐步擴展至審查、探索等場景。
