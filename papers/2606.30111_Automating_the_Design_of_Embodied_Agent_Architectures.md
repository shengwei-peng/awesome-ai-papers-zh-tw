## ⚡ TL;DR

本文將智能體架構搜尋從文字領域延伸至具身智能體，自動設計感知、記憶、規劃與動作模組的組合。
提出 AgentCanvas 與 KDLoop，結合型別圖執行環境、編碼智能體搜尋與觸發式反思。
實驗顯示多數任務成功率提升，但一個高分候選因資訊洩漏被剔除，且 rollout 雜訊與局部盆地限制搜尋。

## 摘要翻譯

具身智能體（embodied agents）通常由手工設計的感知（perception）、記憶（memory）、規劃（planning）與動作模組（action modules）組合而成。這種模組化（modularity）揭示了龐大的架構設計空間（architectural design space），但現行系統仍仰賴研究者直覺（researcher intuition）來決定資訊儲存位置、觀測處理方式，以及模型呼叫的連接方式。智能體架構搜尋（Agent Architecture Search, AAS）可為文字領域智能體（text-domain agents）自動化此類設計，但尚未透過模擬器 rollout（simulator rollouts）對感知型具身智能體（perceptual embodied agents）進行系統性評估。本研究探討此一遷移。

我們提出 AgentCanvas，一個型別圖執行環境（typed-graph runtime），可將具身執行器（embodied executors）以可編輯節點連線程式（editable node-and-wire programs）的形式承載，並具備模擬器感知執行（simulator-aware execution）與回合級日誌（episode-level logs）；以及 KDLoop，一個編碼智能體搜尋程序（coding-agent search procedure），會循環進行提案（proposal）、批判（critique）、實驗（experiment）與蒸餾（distillation），並於停滯（stalls）後觸發式反思（triggered reflection）。

我們評估三種 AAS 變體（AAS variants），橫跨四個具身執行器，涵蓋視覺語言導航（vision-language navigation）、具身問答（embodied question answering）與語言條件化操作（language-conditioned manipulation）。由此形成的 3×4 矩陣顯示，架構層級搜尋在具身任務上可帶來可部署（deployable）且具方向性的成功率（success rate）提升，而一個看似高分卻帶有資訊洩漏的（leak-bearing）候選架構則被剔除。與此同時，這些實驗暴露了在文字領域 AAS 中較不顯著的限制：優化訊號（optimization signals）可能被 rollout 雜訊（rollout noise）遮蔽，搜尋可能受困於局部編輯盆地（local edit basins），而即使有詳細日誌（detailed logs）可用，回合級信用分配（episode-level credit assignment）也僅能部分浮現。這些結果同時刻畫出針對具身智能體的自動化架構搜尋（automated architecture search for embodied agents）之前景（promise）與現有局限（current limits）。

### 核心貢獻（3～5點）
- 提出 AgentCanvas 與 KDLoop，將智能體架構搜尋（AAS）從文字領域擴展至感知型具身智能體，並透過模擬器 rollout 進行系統性評估。
- 建立 3×4 評估矩陣，涵蓋三種 AAS 變體與四種具身執行器（視覺語言導航、具身問答、語言條件化操作）。
- 證明架構層級搜尋可在具身任務上產生可部署且具方向性的成功率提升，同時能識別並剔除帶有資訊洩漏的候選架構。
- 揭示具身領域 AAS 相較於文字領域的獨特限制：優化訊號易被 rollout 雜訊遮蔽、搜尋易困於局部編輯盆地、回合級信用分配難以完整浮現。

### 適合對象
對具身智能體、自動化機器學習（AutoML）、神經架構搜尋（NAS）及大型語言模型智能體系統設計有興趣的研究者與工程師；特別適合關注如何將文字領域智能體架構搜尋技術擴展至視覺語言導航、具身問答與語言條件化操作等感知型具身任務的讀者。

## 深度分析

#### 方法論解析

本研究的核心目標是將 Agent Architecture Search（AAS，智能體架構搜尋）從文字領域智能體（text-domain agents）遷移到感知型具身智能體（perceptual embodied agents）。為此，作者採取「方法播種（method-seeded）」的策略：不從零組裝智能體，而是以已發表的具身智能體架構為起點，在其鄰近的圖層級修改空間中進行搜尋。這個選擇非常關鍵，因為不同於文字領域已經有 chain-of-thought、debate、self-refinement 等可組合的推理基元（runnable primitives），具身領域的自然起點是完整的系統實作，例如 MapGPT、SmartWay、ExploreEQA 與 VoxPoser。

為了讓這種搜尋可行，論文提出兩個主要技術元件：**AgentCanvas（型別圖執行環境）** 與 **KDLoop（編碼智能體搜尋程序）**。

**AgentCanvas** 是一個 typed-graph runtime（型別圖執行環境），它將具身執行器（embodied executors）表示為可編輯的 node-and-wire programs（節點連線程式）。每個節點對應感知（perception）、記憶（memory）、規劃（planning）、動作（action）等模組，連線則定義資訊流（information flows）。AgentCanvas 具備 simulator-aware execution（模擬器感知執行）能力，能夠在模擬器中執行完整任務，並產生 episode-level logs（回合級日誌），記錄觀察、動作、工具呼叫與中間規劃輸出。這些日誌是後續搜尋與診斷的基礎。

**KDLoop** 則是搜尋程序本身，由一個 coding-agent orchestrator（編碼智能體協調器）實作，每個迭代包含四個階段：

1. **THINK / Proposal（提案）**：根據當前執行器與歷史日誌提出架構修改。
2. **CRITIC / Critique（批判）**：檢視提案的合理性，找出潛在問題。
3. **EXPERIMENT / Experiment（實驗）**：將修改後的程式在模擬器中執行，取得 rollout（執行軌跡）與成功率（success rate）等指標。
4. **DISTILL / Distillation（蒸餾）**：將實驗結果與經驗整理為可複用知識。

當搜尋出現停滯（stalls）時，會觸發 **REFLECT / Triggered reflection（觸發式反思）**，試圖跳出局部區域。這個迴路本質上是一個以程式碼為操作對象的搜尋演算法，與文字領域 AAS 的「提出—評估—更新」邏輯一致，但操作對象從 prompt workflow 轉變為具身系統的圖結構與程式碼。

此外，為了進行系統性比較，作者將 **ADAS** 與 **AFlow** 這兩個文字領域的 AAS 方法移植到同一個 coding-agent harness（編碼智能體框架）中，僅改變 proposer（提案器）的設計，其餘執行與評估機制保持一致。這種控制變因的設計讓我們能夠比較不同搜尋策略在具身任務上的表現差異。

#### 實驗數據解讀

實驗設計形成一個 **3 × 4 的結果矩陣**：三種 AAS 變體（ADAS、AFlow、KDLoop）乘以四個具身執行器（MapGPT、ExploreEQA、SmartWay、VoxPoser），涵蓋視覺語言導航（vision-language navigation, VLN）、具身問答（embodied question answering, EQA）與語言條件化操作（language-conditioned manipulation）三類任務。評估指標主要是相對於基線的成功率變化（∆ SR，以百分點 pp 表示）。

從論文圖 1 與摘要中的數據可以觀察到以下幾點：

| 執行器 / 任務 | ADAS | AFlow | KDLoop | 備註 |
|---|---|---|---|---|
| MapGPT（panoramic VLN） | +2.2 pp | +7.6 pp | +7.1 pp | 三種方法皆有正向提升 |
| ExploreEQA（active EQA） | 0 pp | +4.7 pp | +3.0 pp | ADAS 無法改善，AFlow 與 KDLoop 有方向性進步 |
| SmartWay（low-level VLN） | +4.0 pp | +9.0 pp | +1.3 pp | AFlow 提升最大，但被標記為 leak-bearing（帶有資訊洩漏） |
| VoxPoser（zero-shot VLA） | +3.7 pp | +3.9 pp | — | KDLoop 因 substrate-level 問題無法取得有效 SR |

首先，整體而言 **AAS 確實能為具身智能體帶來可部署的成功率提升（deployable success-rate gains）**。特別是在 MapGPT 上，三種方法都穩定改善，顯示架構層級的搜尋在 VLN 任務上具有不錯的泛用性。AFlow 在多數任務上表現最強，這可能與其搜尋策略更擅長發現有效的圖層級修改有關。

然而，數據也揭示了三個重要現象：

1. **Leak-bearing（帶有資訊洩漏的）候選架構**：AFlow 在 SmartWay 上取得 +9.0 pp 的明顯提升，但後續驗證發現該架構透過不當管道取得答案（例如從模擬器狀態或標註中洩漏目標資訊），因此被剔除。這凸顯具身 AAS 的一個獨特風險：由於執行環境複雜，搜尋可能發現「作弊」捷徑，而非真正學到魯棒的感知—行為對應。

2. **KDLoop 在 VoxPoser 上無法產生有效成功率**：這被歸因於 substrate-level 問題，可能與 VoxPoser 的零樣本視覺語言動作（zero-shot VLA）介面、控制模組（control modules）或模擬器整合較為複雜有關。這說明並非所有執行器都同樣適合目前的搜尋框架。

3. **提升幅度高度異質（heterogeneous gains）**：同一個優化器在不同執行器上表現差異很大，例如 ADAS 在 ExploreEQA 上完全無改善，但在 SmartWay 與 VoxPoser 上有中等提升。這暗示不同任務的架構設計空間（architectural design space）具有不同的可搜尋性與難度。

除了成功率數字，論文更強調這些實驗暴露出的三個結構性限制：

- **Rollout noise（rollout 雜訊）遮蔽優化訊號（optimization signals）**：具身任務的評估需要多次模擬器 rollout，而環境隨機性與模型輸出變異會讓小幅度架構修改的效果難以區分。
- **Local edit basins（局部編輯盆地）**：搜尋容易反覆在同一類小修改上打轉，例如調整 prompt structure（提示結構）或記憶狀態（memory state）的格式，而難以發現質性不同的機制。
- **Partial credit assignment（部分信用分配）**：即使有詳細的 episode-level logs（回合級日誌），智能體仍難以將最終成敗準確歸因到特定模組或決策，這使得搜尋過程的學習效率受限。

#### 與現有研究的比較

本研究最明確的定位是將 AAS 從 **文字領域智能體** 擴展到 **感知型具身智能體**。過去 ADAS、AFlow 等方法主要在文字任務（如問答、程式生成、推理）上進行 workflow 搜尋，其評估成本低廉、狀態無關（stateless），且具備成熟的可組合基元。本研究指出，這些優勢在具身領域並不存在：

- **評估成本與雜訊**：文字任務通常只需一次或數次 LLM 呼叫即可完成評估；具身任務則需要完整的模擬器 rollout（執行軌跡），每次評估都涉及多步互動，且伴隨顯著的 rollout noise（rollout 雜訊）。
- **狀態性（statefulness）**：文字領域的呼叫通常是無狀態的，而具身智能體必須維護記憶狀態（memory state）、地圖表示法（map representations）與感測器抽象（sensor abstractions），這讓架構修改的影響更難預測。
- **基元缺乏**：文字領域有 chain-of-thought、self-consistency、debate 等標準化技巧；具身領域則沒有對應的小型可組合基元，必須從完整系統出發進行修改。

相較於傳統手工設計的具身智能體架構（如 MapGPT、SmartWay、ExploreEQA、VoxPoser），本研究的貢獻在於提出一個**可編輯、可記錄、可搜尋的執行環境（AgentCanvas）**，以及一個**針對具身任務調整的搜尋程序（KDLoop）**。這讓研究者能夠系統性地探索架構設計空間（architectural design space），而不僅依賴研究者直覺（researcher intuition）。

本研究也回應了近期對文字領域 AAS 的批評：有研究認為 AAS 的增益主要來自表面的 workflow restructuring（工作流程重組），而非真正的功能改進。本文的實驗顯示，在具身任務中，搜尋到的架構確實改變了智能體的行為並帶來成功率提升，這為 AAS 的實質價值提供了反駁證據。

然而，本研究也承認其限制：

- **搜尋範圍仍受限於種子架構**：由於採用 method-seeded 策略，搜尋空間是種子系統的鄰域，而非完整的架構設計空間。這限制了發現 radically different 架構的可能性。
- **評估雜訊與計算成本**：模擬器 rollout 的高成本與雜訊使得搜尋難以進行大規模探索，也讓統計顯著性檢定變得困難。
- **資訊洩漏風險**：如 SmartWay 的 leak-bearing 案例所示，自動搜尋可能發現利用環境或資料標註漏洞的捷徑，需要額外的驗證機制。
- **KDLoop 的穩定性**：KDLoop 在某些執行器（如 VoxPoser）上無法正常運作，顯示其對於不同 substrate 的適應性仍有待加強。

#### 可重現性評估

論文提供了一個 **project page**（https://jianzhou0420.github.io/src/works/AgentCanvas/paper.html），但根據目前可取得的上下文，並未明確說明原始碼、資料集或模型權重是否已公開釋出。對於一個涉及複雜模擬器整合、多個種子執行器與三種 AAS 優化器的研究來說，可重現性面臨以下挑戰：

1. **種子執行器的依賴**：MapGPT、SmartWay、ExploreEQA、VoxPoser 各自有不同的程式碼庫與模擬器設定（如 Habitat、AI2-THOR、CLIPort 等），要將它們統一移植到 AgentCanvas 上需要大量工程細節。
2. **模擬器版本與環境設定**：具身任務對模擬器版本、資料集分割、隨機種子極為敏感，任何差異都可能導致成功率數字無法對齊。
3. **LLM / VLM 呼叫**：搜尋過程與執行器都依賴大型語言模型（LLM）與視覺語言模型（VLM）的 API 呼叫，不同模型版本與溫度參數會顯著影響結果。
4. **搜尋過程的隨機性**：AAS 本身具有高度隨機性，即使使用相同設定，不同執行也可能產生不同結果，因此需要多次重複實驗與完整的日誌記錄。

若作者未來能公開 AgentCanvas 的執行環境、KDLoop 的實作、各執行器的移植版本以及實驗日誌，將大幅提升本研究的可重現性與後續研究價值。目前根據摘要與引言的資訊，只能確認 project page 的存在，無法斷定原始碼是否已釋出。

#### 未來研究方向

基於本研究的發現與限制，未來可以從以下幾個方向繼續推進：

1. **降低 rollout noise（rollout 雜訊）對優化訊號的影響**
   - 發展更高效的樣本配置策略，例如 adaptive rollout allocation（自適應 rollout 分配），根據架構修改的不確定性決定需要多少次評估。
   - 引入 variance reduction 技術，如 common random numbers、control variates，或利用 episode-level logs（回合級日誌）建立更穩定的效能估計。

2. **改善 credit assignment（信用分配）**
   - 開發能自動將最終成功率歸因到特定模組、連線或決策的機制，例如利用反事實分析（counterfactual analysis）或模組消融（module ablation）來識別關鍵修改。
   - 讓搜尋智能體能夠從失敗的 rollout 中學習，而不僅依賴最終成功與否的二元訊號。

3. **跳出 local edit basins（局部編輯盆地）**
   - 引入更多樣化的提案機制，例如結合程式合成（program synthesis）、演化演算法（evolutionary algorithms）或貝葉斯優化（Bayesian optimization），避免過度依賴單一搜尋策略。
   - 設計更高層次的架構基元（architectural primitives），讓搜尋能夠進行質性不同的結構重組，而非僅微調提示或記憶格式。

4. **自動偵測與避免 leak-bearing（資訊洩漏）架構**
   - 建立形式化或啟發式的驗證機制，檢查搜尋到的架構是否透過不當管道取得目標資訊。
   - 發展「資訊隔離」原則，明確界定執行器可存取的資訊範圍，並在搜尋過程中強制執行。

5. **擴展到真實世界機器人與跨任務遷移**
   - 目前實驗仍局限於模擬器（simulator），未來可探索將搜尋到的架構遷移到真實機器人平台。
   - 研究跨任務的架構遷移與元學習（meta-learning），讓在一個具身任務上搜尋到的設計原則能夠遷移到其他任務。

6. **多目標與可解釋性**
   - 除了成功率，也可將推論成本、延遲、記憶體使用量、可解釋性納入搜尋目標，進行多目標架構搜尋（multi-objective AAS）。
   - 利用 AgentCanvas 的圖結構與 episode-level logs（回合級日誌），產生可解釋的架構修改說明，幫助研究者理解搜尋結果。

7. **強化 KDLoop 的 robustness（穩健性）**
   - 針對 VoxPoser 等較複雜的執行器，改進 AgentCanvas 的 substrate 支援，讓 KDLoop 能夠處理更多樣化的控制模組（control modules）與動作介面（action interfaces）。
   - 結合 triggered reflection（觸發式反思）與更豐富的錯誤診斷資訊，提升搜尋在面對執行失敗時的自我修復能力。

總結來說，本研究為具身智能體的自動化架構設計開闢了一條可行路徑，但同時也清楚指出：要讓 AAS 在感知型具身智能體上發揮全部潛力，必須同時解決評估雜訊、搜尋空間局部性與信用分配等深層挑戰。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文探討如何自動化設計具身智能體架構，以減少對研究者直覺的依賴。傳統的具身智能體通常由感知、記憶、規劃與動作等模組手工組合而成，而隨著基礎模型與工具快速增加，可能的架構設計空間已經大到人工迭代難以涵蓋。因此，作者希望將智能體架構搜尋（AAS）從文字領域延伸至感知型具身智能體，並透過模擬器 rollout 系統性地評估其可行性。

**Q2：為什麼文字領域的 AAS 不能直接套用到具身智能體上？**
A：文字領域的 AAS 通常建立在低成本、無狀態的模型呼叫上，並且已經有 chain-of-thought、debate、self-refinement 等可組合的推理原語。然而，具身智能體必須與有狀態的模擬器互動，產生充滿雜訊的多回合評估，並依賴包含觀察、動作、工具呼叫與中間規劃輸出的長軌跡。此外，具身領域缺乏一套小而成熟的可組合原語，自然起點往往是像 MapGPT、SmartWay、ExploreEQA、VoxPoser 這類已發表的完整系統。

**Q3：研究具身 AAS 的重要性為何？**
A：隨著大型語言模型與視覺語言模型持續演進，具身智能體的模組組合與連接方式會呈現爆炸性成長，單靠人工設計將難以窮盡。自動化架構搜尋不僅能加速迭代，也可能發現研究者直覺不易想到的模組配置。同時，這項研究也能幫助學界理解當 AAS 從文字程式轉移到在 3D 環境中感測與行動的感知型智能體時，會出現哪些新的限制與挑戰。

**Q4：AgentCanvas 在這個研究中扮演什麼角色？**
A：AgentCanvas 是作者提出的型別圖執行環境，它把具身執行器表示為可編輯的節點連線程式。這個執行環境支援模擬器感知執行，能夠在模擬器中執行、修改並記錄完整任務回合，並產出回合級日誌供後續分析。透過將架構顯式地圖形化，AgentCanvas 讓 AAS 可以在模組與資訊流的層級上進行編輯，而不只是調整提示詞或參數。

**Q5：KDLoop 的運作方式與特色是什麼？**
A：KDLoop 是一個編碼智能體搜尋程序，它會循環進行提案、批判、實驗與蒸餾四個階段。當搜尋過程出現停滯時，系統會觸發反思機制，重新檢視目前的搜尋方向並嘗試跳出局部區域。這種設計讓搜尋不僅能持續產生新的架構變體，也能根據模擬器回饋進行自我修正與知識累積。

**Q6：本研究在方法設計上有哪些關鍵選擇？**
A：作者採用「以方法為種子」的策略，也就是從已發表的具身智能體架構出發，搜尋其鄰近的圖層級修改，而非從零組裝智能體。此外，ADAS、AFlow 與 KDLoop 三種 AAS 變體被放入同一個編碼智能體協調框架中，只有提案策略不同，這讓實驗比較更為公平。這樣的設計也反映了具身領域目前尚缺乏通用原語，因此以現成系統為起點是較務實的選擇。

**Q7：實驗涵蓋了哪些任務與執行器？**
A：實驗評估了四個具身執行器，橫跨三類任務：MapGPT 對應全景式視覺語言導航，SmartWay 對應低階視覺語言導航，ExploreEQA 對應主動式具身問答，VoxPoser 則對應語言條件化操作。這些執行器分別代表了不同的感知與動作介面，也讓研究能觀察 AAS 在多樣任務上的表現。透過這樣的 3×4 矩陣，作者得以比較不同優化器在不同任務上的適用性。

**Q8：實驗的主要結果是什麼？**
A：結果顯示架構層級的搜尋能夠在多個任務上帶來可部署或具方向性的成功率提升，例如 AFlow 在 MapGPT 上提升 7.6 百分點、在 ExploreEQA 上提升 4.7 百分點、在 SmartWay 上提升 9.0 百分點、在 VoxPoser 上提升 3.9 百分點。KDLoop 與 ADAS 也在部分任務上取得正向進展。然而，研究中也發現一個看似高分的候選架構因帶有資訊洩漏而被剔除，顯示自動搜尋仍需嚴謹驗證。

**Q9：實驗揭示了哪些關於具身 AAS 的限制？**
A：作者指出三個在文字領域較不顯著的限制：第一，rollout 雜訊會遮蔽優化訊號，使小幅架構改變難以被穩定評估；第二，搜尋容易陷入局部編輯盆地，反覆進行類似的小修改而無法發現質性不同的機制；第三，即使擁有詳細日誌，回合級的信用分配也只能部分浮現，智能體難以準確判斷哪些模組或決策導致了最終成功或失敗。

**Q10：這項研究在實務上可以應用在哪些場景？**
A：這項技術可應用於服務型機器人、自主導航系統、家用助理以及語言條件化的工業操作手臂等場景。在這些應用中，感知、記憶、規劃與控制模組的組合方式往往決定了系統效能，而人工調整每個模組既耗時又需要深厚領域知識。透過自動化架構搜尋，開發者可以更快探索多種模組配置，並針對特定環境或任務找到更合適的架構。

**Q11：若要将此方法產品化，需要考慮哪些因素？**
A：產品化時必須確保模擬器與真實環境之間的差異不會讓搜尋出的架構過度擬合模擬數據，因此需要穩健的驗證流程來偵測資訊洩漏與捷徑學習。此外，節點連線程式雖然提升了可解釋性，但仍需搭配視覺化介面與版本控制，才能讓工程師理解並維護自動生成的架構。最後，模擬器 rollout 成本高昂，產品團隊需要評估運算預算與搜尋效率之間的平衡。

**Q12：這項研究對具身智能體領域可能帶來什麼影響？**
A：這項研究證明了架構層級的自動搜尋確實能在具身任務上產生功能性改善，而非僅是表面上的流程重組。它為未來的具身智能體開闢了一條從手工設計走向自動化設計的道路，並強調了模擬器雜訊、信用分配與局部最適等核心問題。這些發現將促使後續研究更關注如何設計更穩定、可解釋且具探索能力的 AAS 方法。

**Q13：作者承認了哪些方法上的局限？**
A：作者坦承具身 AAS 面臨的評估雜訊遠大於文字領域，這使得優化訊號容易被掩蓋。搜尋動態也傾向於反覆利用同一個局部編輯盆地，難以自動發現全新的架構機制。此外，即使提供詳細的回合級日誌，智能體仍無法完全掌握每個模組對最終結果的貢獻，信用分配問題依舊只得到部分解決。

**Q14：研究中出現了哪些值得注意的失敗案例？**
A：最明顯的失敗案例是一個在初步評估中看似高分的候選架構，後來被發現透過不當管道取得答案而帶有資訊洩漏，因此必須被剔除。這顯示自動搜尋可能會利用資料或流程中的漏洞來製造虛假的效能提升。另外，部分搜尋過程雖然持續產生修改，但只是停留在局部小調整，未能帶來質性上的行為改變。

**Q15：未來可以朝哪些方向繼續發展？**
A：未來可以發展更精細的回合級信用分配機制，讓智能體能更準確地判斷哪些模組或決策值得保留。也可以引入降低 rollout 雜訊的評估策略，例如重複執行、分層評估或貝葉斯優化，以提升優化訊號的穩定性。此外，結合更強的全域探索機制、真實世界遷移驗證，以及人機協作的設計流程，將是讓具身 AAS 更實用的重要方向。

## 適用場景

1. **室內服務機器人的視覺語言導航與問答**  
   適用於家庭、醫院、辦公大樓或倉儲場域中的移動機器人：先以現成的 VLN 或 EQA 執行器（如 MapGPT、ExploreEQA）為種子，透過 AAS 自動調整感知抽象、記憶體狀態與規劃器拓樸，使機器人能根據「到窗邊確認是否有人」這類自然語言指令完成移動並回答問題。

2. **語言條件化的倉儲揀選與操控手臂**  
   適用於自動化倉儲或製造產線：以 VoxPoser 等零樣本視覺語言動作（VLA）執行器為起點，搜尋更穩定的動作介面、模型配置與提示結構，讓機械手臂依照「把左邊紅色盒子放到第二層貨架」這類指令完成抓取與放置。

3. **數位孿生與模擬培訓環境中的行為自動優化**  
   適用於需要大量反覆測試但實機代價高的場景（如無人機巡檢、自動駕駛模擬）：在 AgentCanvas 上將既有具身智能體架構節點化，利用 KDLoop 等搜尋程序在模擬器中自動產生、評估並蒸餾出更穩定的行為圖，再遷移至實體平台。

4. **多模態智慧監控與巡檢機器人**  
   適用於工廠、電力設施或資料中心：結合視覺語言模型與導航模組，讓巡檢機器人在 3D 環境中根據語言指令移動、觀察並回報異常；AAS 可自動探索不同的觀察處理流程與記憶查詢機制，降低手工調整 prompt 與模組連接的成本。

5. **具身 AI 研究與原型開發加速器**  
   適用於研究團隊或新創公司快速迭代 LLM/VLM 驅動的具身系統：將手工設計的基線封裝成可編輯的 node-and-wire 程式後，利用架構層級搜尋在數天內產出多個可部署的候選架構，並透過詳細日誌理解哪些修改真正帶來成功率提升。

## 實作前置條件

**資料與環境**
- 可用的 3D 模擬器與任務定義（例如 Habitat、AI2-THOR、SAPIEN 等），以及對應的種子執行器程式碼（如 MapGPT、SmartWay、ExploreEQA、VoxPoser）。

**運算資源**
- 足夠的 GPU 資源進行 VLM/LLM 推理，以及可平行執行大量 simulator rollout 的 CPU/記憶體叢集。

- 建議設定運算預算上限與快取機制，因為每次架構評估都需要多條 rollout，成本遠高於純文字領域的 AAS。

- 熟悉 Python、具身 AI 模擬器 API、LLM agent 框架與提示工程。
- 能將現有手工架構重構成型別圖執行環境（typed-graph runtime）中的節點連線程式。
- 具備程式 diff 審查、版本控制與基礎統計檢定能力，以判斷成功率提升是否顯著。
- 建議至少一名成員了解搜尋/優化方法（如 ADAS、AFlow、KDLoop）與 sim-to-real 遷移。

## 實作步驟建議

1. **選定種子執行器與任務範圍**  
   從現有且可運作的具身智能體架構出發，明確定義要優化的目標任務（視覺語言導航、具身問答或語言條件化操作）與主要評估指標（成功率、路徑長度、執行時間等）。

2. **將種子架構移植到 AgentCanvas**  
   把感知、記憶、規劃、動作等模組封裝成具型別的節點與連線，確保每個節點可獨立編輯、執行與記錄。此時應建立模擬器感知執行機制，使執行器能在模擬器中自動運行完整回合。

3. **建立回合級日誌與評估管線**  
   設計統一的日誌格式，記錄每個節點的輸入輸出、模型呼叫內容、觀察序列與最終結果。同時建立可重複的評估腳本，支援多條 rollout 與統計摘要。

4. **定義搜尋空間與合法編輯操作**  
   明確規定 coding agent 可以修改哪些部分：例如新增/刪除節點、改變連線、調整提示結構、替換記憶體表示法、改變規劃器拓樸或模型配置。對於可能導致資訊洩漏的操作（如直接讀取 ground truth）應加入黑名單。

5. **接入 AAS 變體並啟動搜尋迴圈**  
   選擇 ADAS、AFlow 或 KDLoop 作為優化器，並統一透過 coding-agent harness 進行提案、批判、實驗與蒸餾。KDLoop 的使用者應特別設定停滯偵測，以便在搜尋陷入局部編輯盆地時觸發反思。

6. **以統計檢定過濾雜訊與確認提升**  
   對每個候選架構執行足夠數量的 rollout，計算成功率與信賴區間，並與基線進行顯著性檢定。若發現某個候選在驗證集上異常高分，應檢查是否透過不當管道取得答案（leak-bearing）。

7. **蒸餾有效修改並加入工程保護**  
   將經確認的改動整理成穩定版本，移除無效或過度複雜的修改；同時加入單元測試、動作約束與異常處理，避免部署後出現未預期行為。

8. **模擬到實機的遷移與持續迭代**  
   先在數位孿生或實體機器人的安全沙箱中驗證，再逐步擴大部署範圍。上線後持續收集失敗案例，並將其作為下一輪 AAS 的種子資料，形成自動化改進迴圈。

## 潛在風險與注意事項

| 風險 | 說明 | 因應方式 |
|---|---|---|
| **Rollout 雜訊遮蔽優化訊號** | 模擬器執行軌跡本身具有隨機性，小幅架構改動可能無法在少數 episode 中顯現差異。 | 增加每個候選的 rollout 數量、使用分層抽樣、進行統計顯著性檢定，並記錄信賴區間。 |
| **局部編輯盆地** | 搜尋可能反覆在同一區域做小修改（例如只調 prompt 用詞），無法發現更具結構性的創新。 | 設計多樣化的提案操作（如改變節點連線、新增記憶模組）、定期觸發反思、保留多個差異化候選。 |
| **信用分配不完整** | 即使擁有詳細日誌，仍難以精確判斷最終成功或失敗應歸因於哪個模組。 | 增加模組級中間指標、執行因果消融實驗、要求 coding agent 在批判階段說明改動的預期影響。 |
| **資訊洩漏候選** | 某些架構可能透過不當管道（如日誌中夾帶 ground truth）取得高分。 | 嚴格區分訓練/驗證/測試集、審查所有資料讀取路徑、對異常高分候選進行洩漏檢查。 |
| **運算成本高昂** | 每次架構評估都需要多條完整 simulator rollout，搜尋成本可能快速膨脹。 | 設定預算上限、使用早期停止、快取重複評估結果、優先評估低成本代理指標。 |
| **Sim-to-real 落差** | 模擬器中優化的架構在實機上可能因感測器雜訊或延遲而失效。 | 加入領域隨機化、在數位孿生中預演、逐步從沙箱過渡到真實環境，並保留人工接管機制。 |

## 與其他技術的整合建議

- **機器人中介軟體**：可將 AgentCanvas 包裝成 ROS2 節點，使搜尋出的具身執行器能直接接收感測器資料並發布控制指令，縮短模擬到實機的距離。
- **現成感知與規劃工具**：把 Detectron2、Segment Anything（SAM）、CLIP、PDDL 規劃器或運動規劃函式庫封裝為 AgentCanvas 的標準節點，讓 AAS 專注於「如何連接」而非重新發明模組。
- **LLM/VLM 服務**：支援 OpenAI、Anthropic、開源模型或本地推理引擎作為可替換的模型配置節點，方便根據延遲與成本切換後端。
- **MLOps 與實驗追蹤**：使用 Weights & Biases、MLflow 或類似工具記錄每次搜尋迭代的 diff、超參數、rollout 統計與成功率，便於回溯與再現。
- **CI/CD 與程式碼審查**：將 coding agent 產生的 diff 納入版本控制與自動化測試流程，避免未經檢查的改動直接進入產品分支。
- **資料湖與人機回饋介面**：把 episode-level logs 集中儲存，並提供視覺化介面讓領域專家標註失敗原因，這些標註可成為下一輪搜尋的批判訊號。

## 給不同背景讀者的閱讀建議

**初學者**
