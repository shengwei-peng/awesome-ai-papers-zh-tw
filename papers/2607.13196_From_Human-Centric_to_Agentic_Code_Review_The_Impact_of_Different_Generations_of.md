# 從以人為中心的程式碼審查到代理式程式碼審查：不同世代的生成式人工智慧技術對審查品質的影響

**原文標題：** From Human-Centric to Agentic Code Review: The Impact of Different Generations of Generative AI Technology on Review Quality  
**作者：** Suzhen Zhong、Shayan Noei、Bram Adams 等 4 位作者  
**發布日期：** 2026-07-14  
**HF 連結：** [https://huggingface.co/papers/2607.13196](https://huggingface.co/papers/2607.13196)  
**arXiv：** [https://arxiv.org/abs/2607.13196](https://arxiv.org/abs/2607.13196)

## ⚡ TL;DR

程式碼審查負擔沉重，但生成式AI參與後對效率與品質的影響仍缺乏實證。
研究分析207個GitHub專案102萬筆拉取請求，以審查者互動序列識別三種AI採用與協作模式。
AI代理發起或多代理參與在漸進與快速採用下加速決策，但效率提升未改善審查品質，人機協作為效率主因。

## 摘要翻譯

程式碼審查（code review）有助於在程式碼整合（code integration）前維護軟體品質（software quality），但也對人類審查者造成相當大的工作負擔。隨著生成式人工智慧（generative artificial intelligence）成為軟體開發的一部分，程式碼審查（code review）正從以人為中心的審查（human-centric review）流程，轉向由大型語言模型（large language model, LLM）審查者、AI 代理（AI agent）審查者與人類審查者共同參與的 AI 支援的審查流程。然而，目前仍缺乏實證證據來了解此轉變如何影響審查效率（review efficiency）與審查品質（review quality）。本研究分析 207 個 GitHub 專案中的 102 萬筆已審查拉取請求（pull request），這些專案橫跨三個程式碼審查（code review）時代：以人為中心的審查（human-centric review）、LLM 輔助審查（LLM-assisted review），以及代理式程式碼審查（agentic code review）。本研究識別出三種 AI 審查者採用模式：漸進式 AI 採用（Gradual AI Adoption）、快速 LLM 採用（Rapid LLM Adoption），以及快速 AI 代理採用（Rapid AI Agent Adoption）。進一步將拉取請求（pull request）的審查討論建模為審查者互動序列（reviewer interaction sequences），以描述人類、LLM 與 AI 代理（AI agent）審查者在審查過程中的協作模式（collaboration patterns）。研究結果顯示，在漸進式 AI 採用（Gradual AI Adoption）與快速 AI 代理採用（Rapid AI Agent Adoption）下，涉及 AI 代理（AI agent）的協作模式（collaboration patterns）——特別是由 AI 代理（AI agent）發起的審查或涉及多個 AI 代理（AI agent）的審查——與更快速的審查決策相關。然而，這些效率提升並未轉化為更好的審查品質（review quality）。研究亦發現，審查活動（review activity）與拉取請求類型（pull request type）在各個時代中仍然重要，而一旦有 LLM 與 AI 代理（AI agent）審查者參與，人機協作（Human-AI collaboration）模式即成為解釋審查效率（review efficiency）的最強因素。這些發現為設計能提升效率且不削弱審查品質（review quality）的 AI 支援的程式碼審查（code review）流程提供了實證指引。

### 核心貢獻（3～5點）
- 建構橫跨三個程式碼審查時代（以人為中心的審查、LLM 輔助審查、代理式程式碼審查）的大規模實證資料集，涵蓋 207 個 GitHub 專案與 102 萬筆已審查拉取請求。
- 識別出三種 AI 審查者採用模式：漸進式 AI 採用、快速 LLM 採用，以及快速 AI 代理採用。
- 將拉取請求的審查討論建模為審查者互動序列，以刻畫人類、LLM 與 AI 代理審查者之間的協作模式。
- 發現涉及 AI 代理的協作模式可加速審查決策，但效率提升並未轉化為更好的審查品質。
- 揭示一旦 LLM 與 AI 代理審查者參與，人機協作模式即成為解釋審查效率的最強因素。

### 適合對象
本論文適合軟體工程研究者、程式碼審查流程設計者、AI 輔助開發工具開發者，以及希望了解生成式人工智慧與 AI 代理如何影響程式碼審查效率與品質的實務專案經理與開發團隊成員閱讀。

## 深度分析

#### 方法論解析

本研究採用大規模實證分析，核心資料為 207 個 GitHub 專案中超過 102 萬筆已完成審查的拉取請求（Pull Request, PR），時間橫跨 2022 年 5 月至 2026 年 2 月，涵蓋人類審查者（Human Reviewer）、大型語言模型審查者（Large Language Model, LLM Reviewer）與 AI 代理審查者（AI Agent Reviewer）三種角色。方法論可拆解為以下五個環節：

1. **專案篩選與資料蒐集**  
   作者透過 GitHub 進階搜尋鎖定持續活躍、且至少擁有 100 顆星標（stars）的開源專案，確保樣本在生成式人工智慧（Generative AI）出現前後皆有足夠的審查活動（Review Activity）。篩選條件強調「連續審查活動」，目的在於觀察同一專案從以人為中心的審查（Human-Centric Review）、LLM 輔助審查（LLM-Assisted Review）到代理式程式碼審查（Agentic Code Review）的轉變過程，而非僅比較不同專案。

2. **審查者角色識別與時代劃分**  
   研究將每則審查意見歸類為人類、LLM 或 AI 代理所產生。雖然文中未詳述分類規則，但可推測其結合帳號名稱、機器人標籤（bot labels）、工具特徵（例如 `github-actions`、`coderabbit` 等）以及自然語言回饋（Natural-Language Feedback）的產生模式進行標註。在此基礎上，每個專案被切分為三個時代：pre-LLM 時代、LLM 時代與 agent 時代，並依各專案實際導入時間建立轉移軌跡。

3. **AI 採用實務分群（Adoption Practice Clustering）**  
   作者將每個專案的生成式 AI 採用時間序列進行分群，識別出三種典型實務：
   - **漸進式 AI 採用（Gradual AI Adoption）**：AI 審查者比例緩慢上升，人機協作（Human-AI Collaboration）逐步深化。
   - **快速 LLM 採用（Rapid LLM Adoption）**：在 LLM 工具出現後迅速提高 LLM 審查比例。
   - **快速 AI 代理採用（Rapid AI Agent Adoption）**：直接大規模導入具自主執行能力的 AI 代理審查者。  
   此分群讓研究能比較不同導入策略對審查效率（Review Efficiency）與審查品質（Review Quality）的差異影響。

4. **審查者互動序列建模（Reviewer Interaction Sequences）**  
   研究將單一 PR 內的審查討論視為一連串審查者互動事件，記錄人類、LLM 與 AI 代理的出現順序與組合，從中歸納出多種協作模式（Collaboration Patterns），例如：僅人類參與、由 AI 代理發起審查、多個 AI 代理同時參與、人類回應 AI 回饋等。這種序列化表示能捕捉「誰先發言、誰接續回應」的動態結構，而非僅計算各類審查者數量。

5. **品質與效率指標及解釋性模型**  
   - **審查效率**：以 PR 從建立到獲得審查決策（approval/merge/close）所需的時間衡量。
   - **審查品質**：採用審查異味（Review Smells）作為代理指標，例如指派不適當審查者、單次審查過多程式碼變更等已知會降低軟體品質（Software Quality）的現象。
   - **解釋性模型**：建立邏輯迴歸（Logistic Regression）等解釋性模型，評估協作模式、拉取請求類型（Pull Request Type）、審查活動強度等傳統因子對審查品質與效率的相對解釋力。

整體而言，本研究的方法論結合了巨觀的專案層級採用軌跡分析與微觀的 PR 層級互動序列分析，並透過解釋性統計模型橋接兩者，試圖回答「不同世代生成式 AI 技術如何改變程式碼審查」這一問題。

---

#### 實驗數據解讀

本研究圍繞三個研究問題（Research Questions, RQs）展開，實驗結果可從以下面向解讀：

**RQ1：常見的 AI 採用實務及其與審查品質的關聯**

- **快速 LLM 採用（Rapid LLM Adoption）** 與審查異味盛行率的顯著上升有關。這暗示在缺乏充分流程調整的情況下，倉促引入 LLM 審查者可能導致審查負擔轉移、回饋品質參差不齊，或讓開發者過度依賴自動化回饋而忽略深度審查。
- **漸進式 AI 採用（Gradual AI Adoption）** 與 **快速 AI 代理採用（Rapid AI Agent Adoption）** 在 agent 時代顯著提升了審查效率。這顯示無論是逐步磨合還是快速部署具備自主驗證能力的 AI 代理，皆可能縮短決策時間，但原因可能不同：前者來自人機協作成熟，後者來自 AI 代理能自動執行開發工具（Development Tools）與上下文檢索。

**RQ2：人機協作模式對審查品質的影響**

- 在 agent 時代，由 AI 代理發起的審查，或涉及多個 AI 代理的協作模式，在漸進式 AI 採用與快速 AI 代理採用中皆與更快的審查決策相關。這代表 AI 代理適合擔任「初篩」或「並行檢查」角色，能加速問題發現與回饋產生。
- 然而，這些效率提升並未轉化為更好的審查品質。相較於純人類審查，大多數涉及 LLM 或 AI 代理的協作模式呈現出更高的審查品質風險。這是一項關鍵警示：**自動化帶來的速度優勢可能伴隨著遺漏複雜缺陷、產生低價值評論或引入不一致標準的風險**。
- 沒有任何單一人機協作模式能同時在效率與品質上穩定勝過純人類審查。這意味著目前 AI 審查者尚未達到「全面替代」人類審查者的水準，而應被定位為輔助與加速工具。

**RQ3：人機協作模式與傳統因子的相對重要性**

- 傳統因子如審查活動強度與拉取請求類型（例如缺陷修復、功能新增）在三個時代中始終顯著，說明程式碼變更本質與社群參與度仍是審查結果的基礎。
- 一旦 LLM 與 AI 代理審查者加入，**人機協作模式成為解釋審查效率的最強因子**。這顯示「誰參與、以何種順序互動」對審查速度的重要性已超越單純的修補程式特性（Patch Characteristics）或專案規模。

綜合來看，實驗結果描繪出一幅「效率與品質權衡」的圖像：生成式 AI 確實能緩解審查瓶頸，但若流程設計不當，特別是快速導入 LLM 而未建立人機協作規範，反而可能損害審查品質。

#### 與現有研究的比較

**相較於傳統程式碼審查研究**

過去研究多聚焦於人類審查者的工作負載、修補程式大小對審查時間的影響，以及審查異味對軟體品質的負面效應。本研究將這些傳統因子納入模型，但進一步指出：當 AI 審查者進入流程後，**協作模式的解釋力凌駕於傳統因子**，這是對經典審查理論的重要補充。

**相較於 LLM 輔助審查的既有發現**

先前研究發現 LLM 輔助審查可能增加審查時間，本研究則區分了「LLM 時代」與「agent 時代」，並發現效率影響取決於採用實務與協作模式。例如，快速 LLM 採用與品質風險上升相關，而 AI 代理參與則可能加速決策。這說明將「生成式 AI」視為單一技術會掩蓋不同世代工具間的差異。

**相較於代理式程式碼審查的先驅探索**

目前針對 AI 代理（AI Agent）參與程式碼審查的實證研究仍相對稀少。本研究以超過百萬筆 PR 的大規模資料，首次系統性地比較人類、LLM 與 AI 代理三種審查者角色的互動模式，並提出「agent 發起」與「多 agent 協作」等具體模式，為後續設計代理式審查流程提供實證基礎。

**主要限制**

1. **觀察性研究，無法建立因果關係**：專案選擇採用何種 AI 審查策略可能與其規模、文化、程式碼複雜度等混淆因子相關，研究僅能呈現關聯性。
2. **審查者角色分類的準確性**：若分類規則依賴帳號名稱或工具特徵，可能誤判某些偽裝成人類的 AI 帳號，或遺漏未標註的 LLM 輔助回饋。
3. **品質代理指標的侷限**：審查異味雖與軟體品質相關，但並不等同於實際缺陷密度或後期維護成本。
4. **樣本代表性**：研究僅包含開源專案，且設有 stars 門檻，結果能否推廣至企業內部、閉源或小型專案仍需驗證。
5. **時代邊界的定義**：各專案進入 LLM 或 agent 時代的時間點可能受工具導入時間、社群慣例影響，若定義方式不一致，可能影響跨專案比較。

#### 可重現性評估

從提供的摘要與上下文來看，**本文並未明確提及是否釋出開源程式碼、資料集或模型權重**。由於本研究屬於大規模資料分析而非訓練深度學習模型，「模型權重」並不適用；真正影響可重現性的關鍵在於：

- **原始 PR 資料清單**：207 個專案名稱、102 萬筆 PR 的識別碼與擷取時間範圍。
- **審查者角色標註規則與結果**：如何區分人類、LLM 與 AI 代理的具體啟發式方法（heuristics）與標註資料。
- **互動序列定義**：協作模式的萃取演算法、狀態編碼與序列長度處理方式。
- **統計模型規格**：邏輯迴歸的變數選擇、控制變數、時代與專案層級效應的處理方式。

GitHub 資料雖為公開，但要在百萬筆規模上重現相同的專案篩選、角色分類與序列建模，仍需要作者釋出完整的複現套件（replication package）。若缺乏上述資源，其他研究者難以驗證分群結果、重跑迴歸或進行敏感性分析。建議作者未來提供：

1. 匿名化後的 PR 中繼資料與互動序列資料集；
2. 資料清理、角色標註與序列萃取的程式碼；
3. 迴歸模型與視覺化腳本；
4. 詳細的附錄說明分類規則與穩健性檢驗結果。

#### 未來研究方向

基於本研究的發現與限制，以下幾個方向值得後續深入探索：

1. **因果推論與實驗設計**  
   採用準實驗方法（例如差異中的差異，Difference-in-Differences）或隨機對照試驗（Randomized Controlled Trial, RCT），比較同一專案在導入 AI 審查者前後的品質變化，以釐清效率提升是否真正來自 AI，而非專案成熟度或程式碼生成量增加的伴隨效應。

2. **更細緻的品質指標**  
   除了審查異味，未來可納入合併後缺陷密度、回滾率、技術債累積速度、安全性漏洞（Security Vulnerabilities）等長期指標，評估 AI 審查者對軟體品質的真實影響。

3. **工具層級與廠商差異分析**  
   本研究將 LLM 與 AI 代理視為角色類別，未來可進一步區分特定工具（例如 GitHub Copilot、CodeRabbit、Amazon CodeGuru、自訂 agent），探討不同工具在回饋品質、上下文檢索能力與開發工具整合深度上的差異。

4. **人機協作流程設計**  
   研究顯示協作模式對效率影響重大，未來可設計並評估不同觸發規則，例如「AI 代理僅在修補程式大小超過閾值時介入」、「人類審查者必須對 AI 高風險評論進行複核」等混合式工作流程，尋求效率與品質的最佳平衡。

5. **多 AI 代理協調機制**  
   涉及多個 AI 代理的模式雖能加速決策，但也可能產生重複或衝突回饋。未來可研究代理間的任務分工、共識機制與衝突消解策略，以提升多代理協作的品質。

6. **人類審查者的認知負荷與信任**  
   從心理與社會技術系統角度，探討開發者對 AI 回饋的信任程度、認知負荷變化，以及過度依賴 AI 是否導致「審查惰性」（review complacency）。

7. **成本、能耗與規模化議題**  
   AI 代理執行開發工具與多次上下文檢索會帶來運算成本與能耗。未來研究可量化不同協作模式的成本效益，協助專案在效率、品質與永續性之間取捨。

8. **跨領域與閉源環境驗證**  
   將研究擴展至企業內部專案、安全關鍵系統或不同程式語言生態系，檢驗本研究結論的外部效度，並發展適合不同情境的代理式審查最佳實務。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？為什麼程式碼審查會成為軟體開發的瓶頸？**

A：這篇論文聚焦於生成式人工智慧快速滲透軟體開發後，程式碼審查從以人為中心轉向人機協作所帶來的影響。隨著 AI 生成程式碼的比例激增，例如 Google 指出新程式碼中有 75% 來自 AI 生成，拉取請求的數量與複雜度都大幅上升，使得原本就耗費人力的審查流程成為程式碼整合前的關鍵瓶頸。傳統上，程式碼審查仰賴人工審查者逐一檢視變更、提供回饋並確認品質，但當程式碼產出速度遠超過人工審查能量時，審查延遲與審查者負擔便會同步惡化。因此，理解 LLM 審查者與 AI 代理審查者如何參與審查、是否真能提升效率與品質，成為當前軟體工程研究的重要課題。

**Q2：現有研究為什麼無法充分解釋 AI 對程式碼審查的影響？**

A：現有文獻大多僅探討傳統人工審查或早期 LLM 輔助審查，對於 AI 代理審查者自主擷取專案上下文、執行開發工具並驗證發現後才產出回饋的差異，仍缺乏系統性的實證比較。許多研究只關注單一技術階段，例如 LLM 是否能生成自然語言回饋，卻較少追蹤專案如何隨時間從以人為中心、LLM 輔助到代理式審查逐步演進。此外，過去較少將拉取請求中的審查者互動序列化，以捕捉人類、LLM 與 AI 代理之間的協作模式。因此，本研究試圖填補這些缺口，提供跨時代、大規模且以協作模式為核心的實證證據。

**Q3：為什麼區分「LLM 輔助審查」與「代理式程式碼審查」很重要？**

A：LLM 輔助審查主要將大型語言模型當作回饋生成工具，其能力受限於模型本身所具備的知識與提示內容；相對地，代理式程式碼審查中的 AI 代理能主動檢索專案上下文、執行開發工具並驗證問題，具備更高的自主性與行動能力。這兩種技術在參與深度、資訊來源與對審查流程的干預程度上都有本質差異，因此對審查效率與品質的影響也可能截然不同。若將兩者混為一談，可能會掩蓋 AI 代理在特定協作模式下加速決策的優勢，也可能忽略 LLM 參與時潛在的品質風險。本研究正是透過區分這三個時代，才能更精確地辨識不同生成式 AI 技術世代的實際貢獻與限制。

**Q4：這篇論文的核心研究方法為何？**

A：本研究分析了來自 207 個 GitHub 開源專案、共計 102 萬筆拉取請求的審查資料，這些專案的審查實踐橫跨了前 LLM 時代、LLM 時代與代理時代。研究首先依據各專案採用生成式 AI 審查者的時間序列，將其聚類為三種 AI 採用實踐：漸進式 AI 採用、快速 LLM 採用與快速 AI 代理採用。接著，作者將每個拉取請求的審查討論建模為審查者互動序列，以刻畫人類、LLM 與 AI 代理在審查過程中的協作方式。最後，透過比較不同時代與協作模式下的審查效率與審查異味，並建立解釋性邏輯迴歸模型，來評估哪些因素最能解釋審查品質問題。

**Q5：將拉取請求審查討論建模為「審查者互動序列」有何創新之處？**

A：傳統的程式碼審查研究通常只關注單一審查者角色或整體統計指標，難以捕捉同一拉取請求中多種審查者先後發言、回應與協作的動態過程。本研究將審查討論視為一連串的互動事件，藉此識別出例如「由 AI 代理發起審查」或「多個 AI 代理同時參與」等具體的人機協作模式。這種序列化方法能夠同時納入參與者類型、發言順序與互動結構，從而揭示不同協作模式對審查效率與品質的差異化影響。此創新不僅讓研究能更細緻地比較人機協作樣態，也為後續設計 AI 支援的審查流程提供了可操作的實證基礎。

**Q6：作者為何選擇將 AI 採用實踐分為「漸進式 AI 採用」、「快速 LLM 採用」與「快速 AI 代理採用」三種？**

A：這三種分類反映了真實開源專案在導入生成式 AI 審查者時的不同節奏與策略選擇，有助於揭示採用方式本身對審查成果的調節作用。漸進式 AI 採用代表專案逐步引入 LLM 與 AI 代理，讓團隊有時間適應與調整流程；快速 LLM 採用則顯示專案在 LLM 技術出現後迅速跟進，但可能尚未充分整合代理能力；快速 AI 代理採用則代表專案較快進入代理式審查階段。透過這種分類，研究能夠比較不同採用路徑在效率與品質上的權衡，例如快速 LLM 採用是否會帶來較高的審查異味風險，而漸進式或快速代理採用是否更有助於維持效率與品質的平衡。

**Q7：本研究使用了什麼樣的資料集與評估對象？**

A：研究資料集涵蓋 207 個活躍的 GitHub 開源專案，這些專案在 2022 年 5 月至 2026 年 2 月期間具有持續的審查活動，並且至少擁有 100 顆星標，確保其具備一定的社群規模與審查慣例。在這些專案中，作者收集了超過 102 萬筆經過審查的拉取請求，橫跨前 LLM、LLM 與代理三個時代。評估對象包括審查效率指標，例如審查決策所需時間，以及審查品質指標，例如審查異味的發生率。這樣大規模且跨時代的資料設計，使研究結果比一般小樣本或單一時點的研究更具外部效度與實務參考價值。

**Q8：研究在效率與品質方面有哪些關鍵發現？**

A：研究發現，在漸進式 AI 採用與快速 AI 代理採用的專案中，由 AI 代理發起或涉及多個 AI 代理的協作模式與更快的審查決策顯著相關，顯示 AI 代理確實能加速部分審查流程。然而，這些效率提升並未轉化為更好的審查品質，多數涉及 LLM 或 AI 代理的協作模式相較於純人工審查，反而呈現出顯著更高的審查品質風險。此外，快速 LLM 採用與審查異味盛行率的顯著上升有關，暗示過快導入 LLM 技術可能會對審查品質造成負面影響。整體而言，研究結果凸顯了效率與品質之間的緊張關係，提醒開發團隊不應僅以速度作為評估 AI 審查成效的唯一標準。

**Q9：解釋性模型揭示了哪些影響審查品質的重要因素？**

A：解釋性邏輯迴歸模型顯示，一旦 LLM 與 AI 代理審查者加入審查流程，人機協作模式便成為解釋審查效率的最強因素，其影響力甚至超過傳統的拉取請求特性。與此同時，審查活動強度與拉取請求類型在三個時代中始終保持重要，說明這些傳統因素並未因 AI 參與而失效。然而，研究也發現沒有任何單一人機協作模式能同時在效率與品質上穩定優於純人工審查，這意味著協作模式的設計需要根據專案目標進行權衡。這些發現強調，未來的 AI 審查工具不僅要提升自動化程度，更應謹慎設計人機互動方式，以避免犧牲審查品質。

**Q10：這些發現如何指導實務上的程式碼審查流程設計？**

A：研究結果建議開發團隊在導入 AI 審查者時，應根據專案特性選擇合適的採用節奏與協作模式，而非盲目追求全面自動化。對於重視審查速度的專案，可以考慮讓 AI 代理在審查初期主動發起檢查，或安排多個 AI 代理分工協作，以縮短決策時間。但對於重視品質的專案，則應保留充足的人工監督與覆核機制，特別是在快速 LLM 採用的情境下，更需留意審查異味增加的風險。整體而言，最有效的 AI 支援審查流程應將人機協作模式視為核心設計變數，並持續監控效率與品質兩項指標。

**Q11：在設計 AI 審查工具或產品時，應該考慮哪些要點？**

A：首先，產品設計者應區分 LLM 與 AI 代理的不同能力邊界，避免將兩者視為可互相替代的同質化工具，因為它們對審查效率與品質的影響並不一致。其次，工具應提供可配置的協作模式，讓團隊能根據拉取請求類型、審查緊急程度與品質要求，決定是否由 AI 代理發起審查、需要多少人類審查者覆核，或是否引入多個 AI 代理。此外，產品應內建審查異味偵測與品質監控儀表板，協助團隊及早發現 AI 參與可能帶來的品質退化。最後，設計者應重視漸進式導入與使用者適應，因為研究顯示漸進式 AI 採用在維持效率與品質平衡方面表現較佳。

**Q12：這項研究對軟體工程領域可能帶來什麼樣的廣泛影響？**

A：這項研究為生成式 AI 時代的程式碼審查提供了大規模、跨時代的實證基礎，有助於學界與業界重新審視人機協作在軟體品質保證中的角色。它提醒研究者與實務者，AI 技術的導入並非單純的「加速工具」，而是會改變審查互動結構、決策流程與品質風險分佈的系統性變革。此研究也為後續探討 AI 代理自主性、多代理協作以及人類監督機制等議題奠定了方法論與資料基礎。隨著 AI 生成程式碼持續增加，這類研究將成為設計更穩健、可持續的軟體開發流程不可或缺的參考。

**Q13：這項研究有哪些已承認的限制？**

A：雖然研究涵蓋了 102 萬筆拉取請求，但資料來源僅限於 GitHub 上的開源專案，因此研究結果是否能直接推廣到企業內部專案、私有程式碼庫或不同開發文化仍需谨慎看待。此外，研究主要依賴可觀察的審查互動序列與審查異味指標，對於審查者主觀經驗、AI 生成回饋的語義品質以及未被記錄的線下討論，則無法完整捕捉。再者，由於生成式 AI 技術仍在快速演進，研究期間內的 LLM 與 AI 代理能力可能與未來版本有顯著差異，這也限制了研究結果的長期適用性。這些限制意味著後續研究需要結合質性方法與更多樣本的專案類型來進一步驗證與延伸。

**Q14：在哪些情況或失敗情境下，AI 參與審查可能無法帶來幫助？**

A：當專案採用快速 LLM 採用策略卻缺乏充分的人工監督時，審查異味的盛行率可能顯著上升，顯示過度依賴 LLM 反而可能損害審查品質。此外，研究發現沒有任何單一人機協作模式能同時在效率與品質上穩定超越純人工審查，這意味著在某些對品質高度敏感的拉取請求中，完全交由 AI 主導可能並不合適。特別是當拉取請求涉及複雜的架構變更、安全性議題或需要大量領域知識時，AI 代理可能因無法充分理解隱含上下文而產生誤導性回饋。因此，AI 參與審查的成效高度取決於任務特性、協作模式設計以及人類審查者的介入程度。

**Q15：這項研究指出了哪些未來研究方向？**

A：未來研究可以進一步探索如何設計能同時提升效率與品質的人機協作模式，例如結合 AI 代理的主動檢查與人類審查者的策略性覆核。另一個方向是發展更細緻的審查品質指標，不僅偵測審查異味，也評估 AI 生成回饋的正確性、可操作性與對開發者學習的幫助。此外，隨著多代理系統日益成熟，研究多個 AI 代理之間的分工、衝突與協調機制，將有助於理解代理式審查的極限與最佳實踐。最後，未來也可針對企業內部專案進行縱貫研究，以驗證本研究在開源情境下的發現是否適用於更具隱私性與治理要求的開發環境。

## 實務應用指南

### 適用場景

1. **大型開源專案分流審查負擔**  
   當拉取請求（Pull Request）數量龐大、人類審查者成為瓶頸時，可導入 LLM 或 AI 代理協助初篩，縮短審查決策時間。

2. **企業內部開發團隊導入生成式 AI 輔助審查**  
   適合希望從「以人為中心的審查」逐步過渡到「LLM 輔助審查」或「代理式程式碼審查」的團隊，並以實證資料評估成效。

3. **審查流程轉型與人機協作設計**  
   用於重新設計程式碼審查流程，明確人類、LLM、AI 代理各自的角色與協作模式。

4. **審查品質與效率的持續監控**  
   適合已導入 AI 審查工具、但希望建立指標體系來追蹤審查效率與審查異味（review smells）是否惡化的組織。

5. **CI/CD 管線中的自動化審查代理**  
   在持續整合流程中嵌入 AI 代理，自動檢查程式碼變更、擷取專案上下文、執行開發工具並產生自然語言回饋。

### 實作前置條件

- **資料準備**
  - 拉取請求元資料：標題、描述、建立／合併／關閉時間、作者、審查者身分。
  - 審查討論資料：review comments、timeline events、commit diffs。
  - 審查者標記：區分人類、LLM 帳號、AI 代理帳號（可透過帳號名稱、App 標籤或 bot 標記辨識）。
  - 專案上下文：issue 連結、文件、測試結果、靜態分析報告。
  - 品質指標：合併結果、審查異味標記、後續缺陷或 revert 紀錄。

- **運算資源**
  - 可呼叫 LLM API（如 OpenAI、Anthropic）或自行部署開源模型的運算環境。
  - 儲存與處理百萬級 PR 資料的資料倉儲與查詢能力。
  - 執行序列模式挖掘與統計建模的運算資源（一般 CPU 叢集即可）。

- **技能需求**
  - 熟悉 GitHub/GitLab API 與事件串流。
  - 具備資料清理、序列建模、分群與邏輯迴歸等統計分析能力。
  - 了解 LLM 提示工程、AI 代理編排與工具呼叫。
  - 具備程式碼審查實務經驗，能判讀審查異味與品質指標。

---

### 實作步驟建議

1. **劃分審查時代與標記審查者**  
   依據專案歷史，將時間軸切分為「以人為中心的審查」、「LLM 輔助審查」、「代理式程式碼審查」三個時代，並標記每則評論來自人類、LLM 或 AI 代理。

2. **蒐集與清理拉取請求資料**  
   透過 GitHub API、GraphQL 或 GHArchive 取得 PR 討論串、時間軸與程式碼差異，建立可重複使用的資料集。

3. **辨識 AI 採用模式**  
   對每個專案繪製 AI 審查者參與比例的時間序列，利用分群方法辨識「漸進式 AI 採用」、「快速 LLM 採用」、「快速 AI 代理採用」等模式。

4. **建立審查者互動序列**  
   將每個拉取請求的審查討論轉換為人類（H）、LLM（L）、AI 代理（A）的互動序列，並抽取常見協作模式（例如：A 發起、多 A 參與、人機交替等）。

5. **定義效率與品質指標**  
   - 效率：審查決策時間（從建立到合併／關閉）。
   - 品質：審查異味發生率、不適當審查者指派、過大修補程式、後續缺陷密度等。

6. **建立解釋模型**  
   使用邏輯迴歸或其他解釋性模型，比較傳統因素（拉取請求類型、審查活動量）與人機協作模式對審查品質的影響。

7. **部署、監控與迭代**  
   將 AI 代理整合至實際審查流程，持續追蹤效率與品質指標，並依據實證結果調整協作模式與採用策略。

### 潛在風險與注意事項

- **效率提升不等於品質提升**  
  研究發現 AI 代理參與可加速決策，但多數涉及 LLM 或 AI 代理的協作模式與較高的審查品質風險相關，必須同步監控品質指標。

- **快速 LLM 採用可能增加審查異味**  
  「快速 LLM 採用」與審查異味顯著增加有關，建議採取「漸進式 AI 採用」並保留人類最終把關。

- **AI 代理發起或多代理參與的品質風險**  
  雖然這類模式在部分採用情境下效率較高，但應設定明確的觸發條件與人類覆核機制。

- **審查者身分標記錯誤**  
  若將 LLM 或 AI 代理誤標為人類，會嚴重影響序列分析與模型結果，需建立可靠的帳號標記規則。

- **過度自動化削弱人類學習與責任歸屬**  
  自動回饋過多可能使開發者依賴 AI，降低人類審查者的參與度與程式碼理解，應明確劃分責任邊界。

### 與其他技術的整合建議

- **版本控制與協作平台**  
  透過 GitHub/GitLab API 與 Webhook，在 PR 建立或更新時自動觸發 AI 代理審查。

- **靜態分析與測試工具**  
  將靜態分析器、單元測試、程式碼覆蓋率工具與 AI 代理串接，讓代理在產生自然語言回饋前取得更多專案上下文。

- **Issue 追蹤與知識庫**  
  連接 issue tracker、技術文件與知識庫，協助 AI 代理理解變更背景並減少無關評論。

- **監控與商業智慧平台**  
  將審查效率與品質指標匯入 BI 或 observability 平台，建立儀表板以持續追蹤不同協作模式的表現。

- **AI 代理編排框架**  
  使用 LangChain、AutoGen 或類似框架管理多代理協作流程，並控制代理間的互動順序與權限。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先掌握本文的核心概念：三個審查時代、三種 AI 採用模式，以及「效率提升不一定代表品質提升」這項關鍵發現。可先略過統計模型細節，聚焦於適用場景與實作步驟。

- **AI 工程師**  
  請重點關注審查者互動序列的建模方式、人類／LLM／AI 代理的身分標記方法，以及 AI 代理與開發工具的整合。特別留意效率與品質之間的權衡，避免只優化速度。

- **研究人員**  
  建議深入閱讀研究方法，包括資料集建構、三個研究問題的設計、分群方法、序列模式抽取，以及解釋型邏輯迴歸模型。可進一步思考如何提升因果推論強度並複製研究結果。

- **產品經理**  
  請聚焦於三種 AI 採用模式的實務意涵與風險：「漸進式 AI 採用」較為穩健，「快速 LLM 採用」可能帶來品質問題。可運用本文發現規劃導入策略、設定人機協作規範，並向管理階層說明為何需要同時監控效率與品質。
