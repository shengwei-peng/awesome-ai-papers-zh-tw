## ⚡ TL;DR

編碼代理生成網頁應用逾七成不符需求，現行方法難以自動部署並透過瀏覽器驗證修復。
本文提出TDDev框架，透過測試驅動開發將需求轉為驗收測試、模擬瀏覽器驗證並產出結構化修復報告。
TDD提升生成品質34至48個百分點，協定取決於模型風格，錯配效益全失Token成本激增25倍。

## 摘要翻譯

編碼代理（Coding Agent）能夠根據自然語言描述（Natural-language Description）生成網頁應用程式，然而近期一項基準測試（Benchmark）研究顯示，生成的應用程式在超過 70% 的案例中無法滿足功能需求（Functional Requirement）。核心難題在於，網頁正確性（Web Correctness）無法從原始碼檔案（Source File）或終端機輸出（Terminal Output）加以評估：應用程式必須部署（Deployment），並透過模擬瀏覽器互動（Simulated Browser Interaction）進行驗證，且必須將失敗轉譯為可執行的修復訊號（Actionable Repair Signal）——這些步驟是現有代理在無人為中介（Human Mediation）時所無法完成的。本文提出 TDDev，一個透過三個階段將此閉環（Closed Loop）自動化的框架：（1）在撰寫任何程式碼之前，將高階需求（High-level Requirement）轉換為結構化驗收測試（Structured Acceptance Test）；（2）部署應用程式並透過瀏覽器互動模擬（Browser-based Interaction Simulation）進行驗證；（3）將瀏覽器觀測失敗（Browser-observed Failure）轉譯為供編碼代理使用的結構化修復報告（Structured Repair Report）。在 TDDev 的支援下，我們針對網頁應用程式生成進行首項控制實證研究，探討測試驅動開發（Test-driven Development, TDD）策略，並比較四種開發協定（Development Protocol），橫跨兩個編碼代理、兩個骨幹模型（Backbone Model）與兩個基準測試。相較於無 TDD 基線（No-TDD Baseline），TDD 機制可穩定提升生成品質（Generation Quality）達 34 至 48 百分點（Percentage Point）。核心發現是，最佳協定取決於模型的生成風格（Generation Style）：採用整體式（應用程式建構）（Holistic）風格建構應用程式的模型最能從代理式強制執行（Agentic Enforcement）中獲益，而採用保守式（程式碼擴充）（Conservative）風格擴充程式碼的模型則受益於增量式強制執行（Incremental Enforcement）。若協定與生成風格不匹配（Mismatch），將完全抵消 TDD 的效益，同時使 Token 成本（Token Cost）最高可達原本的 25 倍。使用者研究證實，TDDev 將人工開發者介入（Manual Developer Intervention）降至零，使工作負載從持續進行的提示工程（Prompt Engineering），轉移至自主且回饋

## 深度分析

#### 方法論解析

TDDev 的核心任務是將 high-level requirement（高階需求）𝑇₀ 轉化為可部署且符合 functional requirement（功能需求）的 full-stack web application（全端網頁應用程式）。形式化上，給定 𝑇₀，coding agent（編碼代理）產出 App = Agent(𝑇₀)，並以 acceptance suite 𝐶(𝑇₀) 作為正確性判準。與傳統程式碼生成任務不同，web correctness（網頁正確性）無法僅從 source file（原始碼檔案）或 terminal output（終端機輸出）靜態驗證，必須經過 deployment（部署）與 browser-based interaction simulation（瀏覽器互動模擬）才能確認。

為此，TDDev 設計了三階段 closed loop（閉環）：

1. **Requirement concretization（需求具體化）**：在撰寫任何程式碼前，先將 natural-language description（自然語言描述）轉譯為 structured acceptance test（結構化驗收測試）。這些測試並非單元測試，而是可操作瀏覽器的具體互動腳本，包含導航、輸入、點擊與預期畫面結果。
2. **Interactive validation（互動式驗證）**：將應用程式部署後，透過 simulated browser interaction（模擬瀏覽器互動）執行上述測試，例如表單提交、按鈕點擊與跨頁導航。此步驟捕捉動態行為與視覺狀態，而非僅比對靜態輸出。
3. **Failure translation（失效轉譯）**：當 browser-observed failure（瀏覽器觀測失敗）發生時，系統將視覺化、情境化的錯誤經驗轉譯為 structured repair report（結構化修復報告），作為 actionable repair signal（可執行的修復訊號）回饋給 coding agent。

在協定層面，研究比較了四種 development protocol（開發協定），核心差異在於測試強制執行的時機與粒度。關鍵發現是 generation style（生成風格）與協定的配適性：holistic（整體式）建構的模型傾向一次性產出完整架構，適合搭配 agentic enforcement（代理式強制執行），由 multi-agent（多代理）架構在宏觀層級把關；conservative（保守式）擴充的模型則偏好逐步修改現有程式碼，適合 incremental enforcement（增量式強制執行），逐項通過測試以避免過度改動。這種配對邏輯使 Test-driven development（TDD，測試驅動開發）從單一方法論轉化為可適配的工程框架。

#### 實驗數據解讀

本研究進行了首個針對網頁應用生成的 TDD 策略控制實驗，橫跨兩種 coding agent、兩種 backbone model（骨幹模型）與兩組 benchmark（基準測試）。數據顯示，相較於 no-TDD baseline（無 TDD 基線），具備 TDD 基礎設施的 generation quality（生成品質）穩定提升 34–48 percentage point（百分點）。這項增益在不同模型與代理組合間皆一致出現，顯示瀏覽器層級的回饋確實能有效縮減 runnable（可執行）與 shippable（可交付）之間的落差。

然而，實驗的核心洞見不在於「TDD 是否有用」，而在於「何種協定對何種模型有用」。當 development protocol 與 generation style 發生 mismatch（不匹配）時，TDD 的品質增益將完全消失，同時 token cost（Token 成本）最高可膨脹至 25 倍。這意味著強行以增量測試約束整體式模型，或放任保守式模型在缺乏逐步回饋下迭代，都會導致無效探索與大量無謂的權杖消耗。反之，配對正確時，系統能在成本可控下收斂。

使用者研究進一步驗證，TDDev 可將 manual developer intervention（人工開發者介入）降至零。工作負載從持續的 prompt engineering（提示工程）轉移至自主的 feedback-driven refinement（回饋驅動優化），顯著改變了人機協作的分工模式。

#### 與現有研究的比較

既有研究在強化 coding agent 時，主要依賴編譯器、測試腳本或終端機產出的結構化文字作為回饋，例如程式碼倉儲層級的除錯、multi-agent 軟體流程或 test-first 生成。這些方法對傳統軟體專案有效，卻無法直接遷移至 full-stack web application 開發，因為網頁應用程式的正確性必須在部署後透過瀏覽器互動才能顯現。TDDev 填補了這項關鍵缺口，將反饋來源從 terminal output 拓展至 browser-observed failure，並建立自動化的 failure translation 機制。

相較於僅生成前端 User Interface（UI，使用者介面）程式碼的相關工作（如早期 CNN-based 原型設計或 Multi-modal Large Language Model（MLLM，多模態大型語言模型）為基礎的視覺生成），TDDev 處理的是涵蓋前後端的 full-stack web application，且以 functional requirement 而非僅視覺相似度作為評估標準。這使其更貼近實際 software engineering（軟體工程）場景。

本研究的限制在於，目前實驗仍屬控制環境下的 benchmark 評測，真實世界的 high-level requirement 往往更為模糊且迭代頻繁；此外，雖然正確配對下能顯著提升品質，25 倍的 token cost 懲罰顯示成本對協定選擇極為敏感，而 generation style 的判定目前仍須先驗知識或試探，尚未完全自動化。

#### 可重現性評估

作者承諾釋出 TDDev 框架、所有實驗資料與 evaluation fixtures（評估固定裝置），這對 reproducibility（可重現性）是正面訊號。然而，從提供的文本脈絡觀察，本文採用 ACM 會議論文模板，其中會議名稱、DOI 與部分後續章節仍為占位符或截斷狀態，暗示目前版本可能為 preprint（預印本）或投稿階段稿件。在正式出版並公開原始碼倉儲前，實際可取得性仍有變數。建議後續讀者關注作者是否提供容器化部署腳本、backbone model 的確切版本標籤，以及 benchmark 資料集的完整互動規格，這些都是確保外部團隊能完整重現 34–48 percentage point 增益的關鍵細節。

#### 未來研究方向

1. **動態協定選擇**：目前研究揭示 generation style 與 development protocol 的配適性，但未深入探討如何於執行期自動偵測模型風格並動態切換協定。未來可訓練輕量分類器或利用試探性生成（pilot generation）來預測最佳協定，避免 mismatch 導致的成本爆炸。
2. **多模態回饋強化**：當前的 failure translation 主要基於瀏覽器觀測行為，未來可整合 Multi-modal Large Language Model（MLLM，多模態大型語言模型）直接比對畫面截圖與預期視覺狀態，提升對排版錯誤、樣式偏移等細微缺陷的感知能力。
3. **成本最佳化**：即使協定配對正確，反覆 deployment 與瀏覽器模擬仍具開銷。可研究測試優先排序（test prioritization）與差異化部署策略，減少不必要的 token cost 與運算資源。
4. **需求澄清閉環**：當 requirement concretization 無法將過於模糊的 natural-language description 轉為明確測試時，系統應主動發起需求澄清（requirement clarification），而非強行生成。這將使 TDDev 從單向需求接收進化為互動式需求工程（interactive requirements engineering）。
5. **擴展至分散式架構**：當前聚焦單一 full-stack web application，未來可探索 microservices（微服務）與分散式網頁系統的 TDD 自動化，處理跨服務互動與資料一致性驗證等更複雜的挑戰。

## 論文問答

**Q1：TDDev 旨在解決當前編碼代理在網頁應用程式生成中的核心問題是什麼？**
A：當前編碼代理雖能根據自然語言描述產出可執行的網頁應用程式原型，但近期基準測試顯示，超過七成的生成結果無法滿足功能需求，凸顯了「可執行」與「可交付」之間的巨大鴻溝。TDDev 旨在解決這個核心問題，透過自動化的測試驅動開發閉環，將高階需求轉化為可驗證的驗收標準，並在部署後持續驗證與修復。這使得編碼代理不再僅能產出語法正確的程式碼，而是能生成真正符合使用者預期、可上線運作的全端應用程式。

**Q2：為何現有的編碼代理與 TDD 方法無法有效驗證網頁應用程式的正確性？**
A：現有的編碼代理與 TDD 方法大多依賴編譯器輸出、終端機日誌或靜態原始碼來判斷正確性，這種回饋機制對於傳統軟體開發或許足夠，但網頁應用程式的正確性必須透過實際部署後的瀏覽器互動才能驗證。網頁錯誤往往表現為導航中斷、狀態未更新或視覺呈現異常等「體驗型」失敗，而非明確的編譯錯誤訊息，現有代理無法從終端機輸出中捕捉這類問題。因此，缺乏瀏覽器層級的互動模擬與失敗轉譯能力，是現有方法無法跨越可執行到可交付門檻的根本原因。

**Q3：縮小「可執行」到「可交付」的差距對於編碼代理的實務部署為何至關重要？**
A：全球每天有超過二十五萬個新網站上線，網頁應用程式的經濟規模與需求極其龐大，若編碼代理只能產出需要人工反覆除錯的原型，將嚴重限制其商業價值與實用性。縮小可執行與可交付之間的差距，意味著能將開發者從繁瑣的手動驗證與提示工程中解放出來，轉而專注於更高層次的設計與創新。TDDev 透過將人工介入降為零，實現了從需求到可部署應用程式的全自動化流程，這對於提升自動程式設計的產業落地至關重要。

**Q4：TDDev 框架的三個核心階段為何，它們如何形成自動化閉環？**
A：TDDev 框架包含三個核心階段：需求具體化、互動式驗證與失敗轉譯。首先，系統在撰寫任何程式碼之前，先將高階自然語言需求轉換為結構化的驗收測試；接著，應用程式被自動部署，並透過模擬瀏覽器互動來執行這些測試；最後，觀測到的失敗被轉譯為結構化修復報告，回饋給編碼代理進行修正。這三個階段形成了一個無需人為中介的閉環，讓代理能夠根據瀏覽器層級的真實回饋持續迭代優化程式碼。

**Q5：相較於既有的 TDD-for-agent 方法，TDDev 的關鍵創新體現在何處？**
A：過往應用於編碼代理的 TDD 方法主要仰賴編譯器錯誤、測試腳本文字輸出或終端機日誌等結構化文字回饋，這些訊號對代理而言是直接可讀的。然而，TDDev 面對的是網頁應用程式特有的多模態挑戰：錯誤並非以文字日誌呈現，而是體現在瀏覽器中的行為與視覺結果。其關鍵創新在於建立了瀏覽器互動模擬機制，並將觀測到的體驗型失敗精確轉譯為編碼代理能夠理解並據以行動的結構化修復訊號，從而突破了傳統 TDD 僅能處理顯式錯誤訊號的限制。

**Q6：TDDev 為何選擇採用多代理架構，而非由單一代理執行所有任務？**
A：TDDev 採用多代理架構，是因為全端網頁應用程式的生成涉及截然不同的專業領域，包括測試規格制定、部署環境編排、瀏覽器互動模擬以及程式碼修復。將這些職責分配給專門化的代理，能讓每個模組專注於其核心能力，提升整體系統的可靠性與並行處理效率。此外，多代理設計也為比較不同的開發協定與執行策略提供了彈性，使系統能夠針對不同骨幹模型的生成風格，選擇最適合的測試強制執行方式。

**Q7：作者採用了什麼樣的實驗設計與基準測試來評估 TDDev？**
A：作者設計了一項控制變因嚴謹的實證研究，橫跨兩種編碼代理、兩種骨幹模型以及兩個網頁應用程式基準測試集，並比較了四種不同的 TDD 開發協定。這樣的實驗設計能夠有效隔離 TDD 策略本身的效果，避免單一模型或資料集造成的偏差。透過在多樣化的組合設定下進行系統性評估，研究得以深入探討不同測試執行策略與模型生成風格之間的交互作用，確保研究發現的普遍性與穩健性。

**Q8：實驗的主要量化結果顯示 TDD 對生成品質有何影響？**
A：實驗結果顯示，導入 TDD 基礎設施後，生成品質相較於無 TDD 基線穩定提升了 34 至 48 個百分點，證明測試驅動開發對網頁應用程式生成具有顯著助益。然而，研究也發現這些改善並非自動發生，而是高度依賴開發協定與模型生成風格的匹配程度。一旦協定與風格不匹配，TDD 的效益將完全消失，且 Token 成本可能暴增最高達 25 倍，凸顯了策略選擇在經濟性與效能上的關鍵影響。

**Q9：四種開發協定的比較揭示了哪些關於 TDD 策略與模型行為交互作用的深層發現？**
A：四種開發協定的比較揭示了模型生成風格與測試執行策略之間深刻的交互作用：對於傾向一次性完整建構系統的整體式模型，代理式強制執行能發揮最大效益；而對於習慣逐步小幅擴充程式碼的保守式模型，增量式強制執行則更為有效。這項發現挑戰了 TDD 策略一體適用的假設，指出必須根據底層模型的行為特徵動態調整驗證與修復的節奏。此消融實驗不僅量化了不同協定的優劣，更為後續設計適應性多代理系統提供了重要的實證依據。

**Q10：在哪些實務開發場景中，整合 TDDev 能發揮最大效益？**
A：TDDev 最適合整合於低程式碼或無程式碼平台，讓非技術背景的使用者僅透過自然語言描述就能獲得可部署的網頁應用程式，無需理解底層實作細節。在快速原型開發的情境中，開發團隊也能利用 TDDev 大幅縮短從需求到可運作示範的週期，將心力集中於架構設計與使用者體驗而非手動除錯。此外，任何需要將高階需求自動轉化為功能完整且經過瀏覽器層級驗證之全端應用程式的企業流程，都是 TDDev 能發揮關鍵價值的場景。

**Q11：將 TDDev 商業化部署時，需要考量哪些成本與效率上的產品化議題？**
A：從產品化角度來看，TDDev 雖能顯著提升功能正確性，但若未謹慎選擇開發協定，Token 消耗可能激增 25 倍，對商業化部署的成本結構構成重大挑戰。因此，產品團隊必須建立動態協定選擇機制，根據當前骨幹模型的生成風格自動切換至最適策略，以平衡品質與成本。另一方面，TDDev 將傳統上由資深工程師執行的持續提示工程與手動驗證工作，轉化為自主的回饋驅動優化流程，長期來看有助於降低人力成本並提升交付速度。

**Q12：TDDev 可能對自動程式設計與多代理系統領域帶來什麼樣的深遠影響？**
A：TDDev 對自動程式設計領域的深遠影響在於，它確立了「瀏覽器即真相」的驗證典範，將動態互動行為而非靜態程式碼分析視為網頁應用程式正確性的最終裁判。這推動了多代理系統研究的發展，證明專業化代理分工在複雜軟體生命週期中的必要性。同時，協定與模型風格匹配的原則，也為其他涉及多模態生成與複雜環境驗證的任務——如行動應用程式開發或具身智慧系統——提供了可遷移的方法論啟示。

**Q13：TDDev 目前存在哪些作者已承認的根本性限制？**
A：TDDev 目前仍有一些根本限制，例如它假設高階需求最終能被轉譯為具體的驗收測試，但對於高度模糊、矛盾或不斷演變的使用者需求，現階段框架缺乏主動釐清或協商的能力。此外，整個閉環的有效性仍受制於底層編碼代理理解結構化修復報告並產出正確修正程式碼的能力，若代理本身的推理能力有限，回饋驅動優化將遭遇瓶頸。目前框架也主要聚焦於功能需求的驗證，對於效能、安全性、無障礙性等非功能需求的自動化測試與修復尚未涵蓋。

**Q14：在什麼樣的條件下，TDDev 會失效甚至導致效能不升反降？**
A：TDDev 的效益會在開發協定與模型生成風格嚴重不匹配時完全失效，例如對整體式建構的模型強制採用增量式執行，不僅無法提升品質，還會導致 Token 成本巨幅攀升。當瀏覽器互動模擬無法準確捕捉複雜的使用者操作流程——例如涉及多步驟狀態管理或非同步即時更新——失敗轉譯模組可能產生模糊或誤導性的修復訊號。此外，若應用程式依賴外部服務或動態資料來源，而模擬環境未能完善重現這些依賴，也可能造成假性的測試失敗，進而導向錯誤的修復方向。

**Q15：未來延伸 TDDev 能力最有潛力的研究方向為何？**
A：未來最具潛力的延伸方向包括將效能、安全性與無障礙性等非功能測試整合進 TDD 閉環，使生成結果更符合生產環境的嚴苛標準。另一個重要方向是發展能夠處理模糊或不完備需求的互動式釐清代理，讓系統在需求階段就能主動與使用者對話以消除歧義。此外，設計能夠根據模型即時行為自動偵測並切換最適協定的自適應機制，將有助於進一步壓低成本、提升效率，並讓 TDDev 能無縫適配不斷推陳出新的各類骨幹模型。

## 實務應用指南

### 適用場景

1. **新創團隊快速驗證產品概念**：創辦人僅以自然語言描述電商平台或社群網站的高階需求，透過 TDDev 在數小時內產出可部署、可互動的最小可行產品（MVP），取代傳統數週的手動開發，並確保功能需求從第一天就被結構化驗收測試所錨定。
2. **企業內部工具自動化**：將散落在文件中的功能需求（如報表後台、審批流程系統）自動轉譯為結構化驗收測試，再由多代理閉環生成可交付的全端網頁應用程式，降低內部 IT 積壓，並減少業務方與工程方來回確認的人為中介。
3. **程式設計教育與自學輔助**：學習者以自然語言描述作業規格後，系統即生成對應的驗收測試與參考實作，並透過瀏覽器互動模擬即時回饋錯誤，將教學場景從「語法正確」提升到「網頁正確性」的層次。
4. **遺留系統的功能擴充**：針對既有網頁應用程式新增模組時，利用 TDDev 的增量式強制執行協定，確保新舊程式碼整合後仍通過瀏覽器層級的端對端驗證，避免回歸錯誤，並將瀏覽器觀測失敗轉譯為可執行的修復訊號。
5. **設計稿到可交付原型的轉換**：結合 UI 設計稿與功能敘述，自動產出結構化驗收測試並驅動程式碼生成，彌補現有工具僅產出「可執行的」但功能缺漏的靜態頁面，真正達到「可交付的」品質。

### 實作前置條件

- **資料層面**：需準備高階需求文件（PRD 或使用者故事）、預期的瀏覽器互動腳本範本，以及用於評測的基準測試資料集；若為既有系統擴充，則需提供現有原始碼檔案與相依性設定。
- **運算層面**：具備容器化部署環境（如 Docker/Kubernetes）以自動化啟動應用程式；瀏覽器自動化基礎設施（如 Playwright 或 Selenium Grid）用於模擬瀏覽器互動；足夠的骨幹模型 API 配額，因閉環迭代可能消耗大量 Token。
- **技術能力**：團隊需熟悉全端網頁開發（前後端框架、資料庫）、DevOps 管線建置、提示工程，以及多代理系統的編排。若使用保守式擴充協定，需額外具備程式碼差異分析與區域性重構的能力。

### 實作步驟建議

1. **需求具體化與驗收測試生成**：在撰寫任何程式碼前，先將自然語言描述轉換為結構化驗收測試（如「使用者點擊結帳按鈕後應導向付款頁面」），並確保每項測試都包含具體的瀏覽器操作序列與預期畫面斷言。
2. **匹配開發協定與骨幹模型生成風格**：評估所選模型的慣性生成模式。若模型傾向一次性整體式建構（holistic），採用代理式強制執行（agentic enforcement）；若模型傾向保守式小幅修改（conservative），則採用增量式強制執行（incremental enforcement），避免不匹配導致 Token 成本暴增。
3. **建置瀏覽器互動模擬與部署管線**：搭建自動化部署環境，使應用程式生成後可立即啟動，並透過無頭瀏覽器執行點擊、表單提交、頁面導航等模擬操作，取代僅檢視原始碼檔案或終端機輸出的傳統驗證。
4. **實作失敗轉譯模組**：當瀏覽器觀測失敗發生時（如導航中斷、狀態未更新），將畫面差異與互動軌跡轉譯為結構化修復報告，明確指出「哪個 DOM 元素未如預期運作」與「預期行為為何」，供編碼代理進行可執行的修復。
5. **多代理閉環編排**：設計測試代理、部署代理與編碼代理的協作流程，確保每次迭代都遵循「生成→部署→驗證→修復」的閉環，並設定最大迭代次數與早期終止條件以控制成本。
6. **人機協作閘道與最終驗收**：雖然 TDDev 可將人工開發者介入降至零，仍建議在首次導入時保留人工閘道，用於審查結構化驗收測試是否真實反映業務意圖，避免測試本身幻覺導致方向偏離。

### 潛在風險與注意事項

- **協定與模型風格不匹配**：這是最昂貴的錯誤。若將增量式強制執行套用於整體式模型，或反之，不僅 TDD 效益完全消失，Token 成本可能飆升至 25 倍。導入前務必以小規模基準測試評估模型行為。
- **瀏覽器模擬的脆弱性**：自動化測試常因動態產生的 CSS 選擇器或載入延遲而誤判。建議採用語意化定位策略（如 role-based selectors）並加入明確等待條件，而非依賴絕對 XPath。
- **測試案例的幻覺**：編碼代理生成的結構化驗收測試可能過度推論需求，導致測試本身不符合使用者真實意圖。應在閉環啟動前由領域專家抽樣驗證測試品質。
- **部署環境漂移**：生成程式碼的相依版本（Node.js、Python 套件）與部署環境不一致將導致驗證失敗。建議將容器映像檔與相依鎖定檔（lock files）納入生成範圍，確保可重現性。
- **累積性成本與延遲**：每次閉環迭代都涉及模型呼叫、部署與瀏覽器模擬，在大型專案中可能產生顯著延遲與費用。建議實作快取機制（如通過測試的程式碼片段快取）與分層測試策略（單元測試先行、瀏覽器測試後行）。

### 與其他技術的整合建議

- **CI/CD 管線整合**：將 TDDev 嵌入 GitHub Actions 或 GitLab CI，使每次需求變更自動觸發「驗收測試生成→應用程式建置→瀏覽器驗證」流程，實現需求即程式碼（Requirements as Code）。
- **設計工具銜接**：串接 Figma 或 Sketch 的外掛程式，將設計稿中的元件規格與互動說明自動轉為高階需求輸入，縮短從設計到可交付原型的路徑。
- **低程式碼平台互補**：對於標準化後台（如 CRUD 管理介面），可先以低程式碼平台產出基礎架構，再透過 TDDev 針對客製化業務邏輯進行測試驅動的擴充，兼顧開發速度與功能正確性。
- **可觀測性工具**：整合瀏覽器 Session Replay 工具（如 LogRocket 或 OpenReplay），將多代理互動過程中的瀏覽器觀測失敗錄影留存，作為後續微調失敗轉譯模組的訓練資料。
- **向量資料庫與需求管理**：將歷史需求與對應的結構化驗收測試存入向量資料庫，當新專案啟動時透過 RAG（Retrieval-Augmented Generation）檢索相似案例，提升需求具體化的準確度與一致性。

### 給不同背景讀者的閱讀建議

- **初學者**：請先聚焦「為何網頁正確性無法從原始碼檔案或終端機輸出判斷」這一核心概念。本文的價值在於將傳統「寫完程式再測試」的習慣，翻轉為「先寫瀏覽器驗收測試再生成程式碼」，理解這個閉環邏輯後，再逐步了解多代理如何分工。
- **AI 工程師**：重點關注多代理架構中的「失敗轉譯」機制與開發協定的選擇策略。本文的實證結果指出，骨幹模型的生成風格（整體式 vs. 保守式）直接決定應採用代理式或增量式強制執行，這是將學術成果轉化為穩定產品的關鍵工程決策。
- **研究人員**：請深入檢視本文的控制實驗設計——四種開發協定、兩種編碼代理、兩種骨幹模型與兩種基準測試的交叉比較。特別注意「協定與生成風格不匹配時 TDD 效益完全消失」這一發現，它為後續自適應協定選擇或模型微調研究提供了明確的假設與驗證基礎。
- **產品經理**：請將閱讀重心放在使用者研究結果與成本效益分析。TDDev 可將人工開發者介入降至零，並將工作負載從持續的提示工程轉移至自主的回饋驅動優化；同時留意 Token 成本在錯誤配置下可能暴增 25 倍，這意味著協定選擇不僅是技術問題，更是直接影響產品經濟模型的商業決策。
