# 執行與否：分析基於大型語言模型之程式修復中程式碼執行的成本效益

**原文標題：** To Run or Not to Run: Analyzing the Cost-Effectiveness of Code Execution in LLM-Based Program Repair  
**作者：** Zhihao Lin、Junhua Zhu、Mingyi Zhou 等 8 位作者  
**發布日期：** 2026-06-25  
**HF 連結：** [https://huggingface.co/papers/2606.26978](https://huggingface.co/papers/2606.26978)  
**arXiv：** [https://arxiv.org/abs/2606.26978](https://arxiv.org/abs/2606.26978)

## ⚡ TL;DR

探討LLM程式修復智慧體中，頻繁執行程式碼是否值得其高昂成本。
透過分析七千多筆軌跡與三千次對照實驗，量化執行行為對修復成效的影響。
發現限制執行幾乎不降低解決率，卻大幅節省開銷，應權衡成本效益而非預設啟用。

## 摘要翻譯

基於大型語言模型（LLM-based）的程式修復（program repair）智慧體（agents）日益採用「生成-執行-修正（generate-run-revise）」範式（paradigm），透過迭代式執行測試以評估並改良修補程式（patches）。這種基於執行（execution-based）的方法（approach）已成為最先進（state-of-the-art, SOTA）系統中的標準實務。然而，執行（execution）可能耗時且昂貴，但其對這些智慧體的影響仍有待深入探討。本文針對基於大型語言模型之程式修復中的執行行為（execution behavior），進行一項兩階段實證研究。為了大規模刻畫執行行為，我們首先分析來自 SWE-bench 排行榜（leaderboard）提交結果（submissions）的 7,745 筆智慧體軌跡（agent traces）。其次，我們在四種執行範式（execution paradigms）下，針對 200 個 SWE-bench 實例與三個智慧體——Claude Code、Codex 與開源（open-source）的 OpenCode——評估 3,000 次端到端（end-to-end）修復嘗試（repair attempts），以進行效能與成本的細粒度（fine-grained）比較（comparison）。我們的分析揭示三項關鍵觀察：（1）所有受分析的智慧體與模型均會使用程式碼執行（code execution），平均每項任務進行 8.8 次測試執行（test runs）。執行行為在不同智慧體與模型間差異甚大，頻率範圍為每項任務 2 至 19 次，且後期執行（late-stage executions）的成功率（success rates）始終高於早期執行。（2）執行限制（execution restrictions）對修復成功影響甚微：在採用最先進（SOTA）模型的商業智慧體（commercial agents）上，禁止執行（Prohibited）與無限制執行（Unrestricted）之間的解決率（resolve-rate）差距僅 1.25 個百分點（percentage points），且未達統計顯著（statistically significant），而禁止執行可節省大量 Token 成本（token cost）與實際時間成本（wall-clock cost）。（3）執行效益（execution benefit）呈現集中而非均勻分布。這些模式顯示，現有智慧體不加區別地（indiscriminately）執行程式碼，在執行效益有限的實例上仍付出其成本。因此，執行應被視為一項具有明確成本效益權衡（cost-benefit tradeoff）的資源，而非預設功能（default capability）。

### 核心貢獻（3～5點）
- 大規模執行行為刻畫：透過分析 7,745 筆 SWE-bench 排行榜（leaderboard）智慧體軌跡（agent traces），發現每項任務平均 8.8 次測試執行（test runs），跨智慧體頻率差異顯著（2 至 19 次），且後期執行（late-stage executions）的成功率（success rates）顯著高於早期。
- 四種執行範式（execution paradigms）的細粒度（fine-grained）比較：針對 Claude Code、Codex 與 OpenCode 進行 3,000 次端到端（end-to-end）修復嘗試（repair attempts），發現執行限制（execution restrictions）對修復成功影響甚微（禁止執行 Prohibited 與無限制執行 Unrestricted 的解決率 resolve-rate 差距僅 1.25 百分點 percentage points，未達統計顯著 statistically significant），但可大幅節省 Token 成本（token cost）與實際時間成本（wall-clock cost）。
- 執行效益（execution benefit）的集中性：執行效益呈現集中而非均勻分布，顯示現有智慧體不加區別地（indiscriminately）使用執行，在效益有限的實例上仍付出高昂成本。
- 成本效益權衡（cost-benefit tradeoff）的明確化：主張程式碼執行（code execution）應被視為需顯式權衡成本的資源，而非無條件啟用的預設功能（default capability）。

### 適合對象
從事自動化程式修復（APR）、軟體工程與基於大型語言模型（LLM-based）智慧體研究的學者與工程師；正在開發程式碼智慧體（code agents）或軟體開發輔助工具，且需評估執行成本與延遲（latency）的實務開發者與系統架構師；以及關注大型語言模型系統成本效益（cost-effectiveness）與資源最佳化的研究團隊。

## 深度分析

#### 方法論解析

本研究採用兩階段（two-stage）實證設計，旨在將 code execution（程式碼執行）從 LLM-based agents（基於大型語言模型的智慧體）的複雜決策流程中獨立出來，作為單一 controlled variable（控制變因）進行隔離測量。不同於過往研究將 execution-based approach（基於執行的方法）視為隱含且必要的預設元件，本文主張應將 execution access（執行存取權限）視為可調度的資源，並透過固定 agent scaffold（智慧體腳手架）、僅變更執行權限的方式，精確量測其邊際價值。

第一階段為大規模的 execution behavior（執行行為）分析。作者蒐集並解析來自 SWE-bench leaderboard（SWE-bench 排行榜）的 7,745 筆 agent traces（智慧體軌跡），涵蓋四個知名 code agents（程式碼智慧體）、十二種 LLMs 與 SWE-bench Lite / Verified 兩大 benchmark datasets（基準測試資料集）。透過量化 test runs（測試執行）的頻率、timing distribution（時間分布）與 test outcomes（測試結果），建立當前 generate-run-revise paradigm（生成-執行-修正範式）的運作輪廓。

第二階段為 end-to-end repair attempts（端到端修復嘗試）的控制實驗。研究選定三個代表性智慧體：commercial agents（商業智慧體）Claude Code（搭載 Claude-Sonnet-4.5）、Codex CLI（搭載 GPT-5.2-x high），以及 open-source（開源）的 OpenCode（搭載 Qwen2.5-Coder-32B）。在 200 個 SWE-bench 實例（各取 Lite 與 Verified 前 100 筆）上，設計四種漸進式的 execution paradigms（執行範式），從完全 Prohibited（禁止執行）到完全 Unrestricted（無限制執行），共執行 3,000 次修復嘗試。研究以三個研究問題貫穿：
- **RQ1**：code agents 如何進行 code execution？（頻率、時機、success rates（成功率））
- **RQ2**：code execution 對效能的影響？（resolve-rate（解決率）、token cost（Token 成本）、wall-clock cost（實際時間成本））
- **RQ3**：在何種條件下 execution 能帶來效益？（分析穩定結果實例，探討 bug reproduction（錯誤重現）、fault localization（缺陷定位）與 execution feedback（執行回饋）的實質貢獻）

統計檢定採用 McNemar's test，以判斷不同 execution restrictions（執行限制）下的 resolve-rate 差異是否達到 statistically significant（統計顯著）。

#### 實驗數據解讀

**RQ1：執行行為的普及性與階段性差異**
數據顯示，所有受測的 agent-model 組合均會使用 code execution，平均每次任務進行 8.8 次 test runs，但不同組合間差異極大，範圍從 2 次至 19 次。值得注意的是，late-stage executions（晚期執行，對話後段 66–100%）的 success rates 顯著高於早期，例如 OpenHands 搭配 Claude-3.5-Sonnet 的成功率從早期 42% 提升至晚期 72%，整體平均達 57.9%。這暗示在 iterative workflow（迭代式工作流程）中，智慧體隨著對任務的理解加深，能夠執行更具針對性的 unit tests（單元測試），但同時也意味著前期執行可能消耗大量資源卻僅獲得較低回報。

**RQ2：執行限制對修復成效的邊際影響微弱**
核心發現指出，execution restrictions 對於 SOTA（最先進的）商業模型的修復成功率影響極為有限。Prohibited 與 Unrestricted 之間的 resolve-rate gap（解決率差距）僅 1.25 percentage points（百分點），且未達統計顯著（𝑝 > 0.05）。具體而言，Claude Code 在無執行權限下仍達 63% 的 resolve-rate，相較於無限制執行的 64% 僅下降 1 個百分點，卻節省 56% 的 token cost 與 48% 的 wall-clock cost。為排除資料洩漏的解釋，作者以訓練截止日早於 SWE-bench Verified 的 Qwen2.5-Coder-32B 進行複製實驗，結果顯示 OpenCode 在兩種模式下 resolve-rate 均為 10%，但 Prohibited 模式可減少 3 倍的 token 消耗。這項證據強烈表明，對於多數受測的 bugs，agents 支付了 execution 的 overhead（額外負擔），卻未獲得相應的效能提升。

**RQ3：執行效益的集中性與驗證落差**
進一步分析穩定結果（Pass→Pass 與 Fail→Fail）後，研究識別出兩項關鍵因素。首先，bug reproduction execution 對 fault localization 的幫助有限：雖然 55% 的 Claude Code 成功案例使用錯誤重現，但定位準確度在兩種模式下均維持 95% 以上，且僅 48.8% 的重現執行產生可操作的回饋。其次，execution feedback 經常無法導正錯誤：54–66% 的商業智慧體案例無論有無 execution access 都在單次編輯內完成；而在失敗案例中，81–100% 通過了智慧體自行執行的驗證，卻未通過官方的 SWE-bench 評估。這揭示了 agent-chosen tests（智慧體自選測試）與 ground-truth validation（地面真實驗證）之間存在顯著落差。總結而言，execution benefit（執行效益）並非均勻分布，而是 concentrated（集中）於特定實例；然而當前 agents 傾向於 indiscriminately（不加區別地）使用執行，導致成本效益嚴重失衡。

#### 與現有研究的比較

相較於過往聚焦於 model architectures（模型架構）、prompting strategies（提示策略）、search algorithms（搜尋演算法）或 benchmark performance（基準測試效能）的文獻，本文首次將 code execution 提升為可獨立操弄的核心變因，而非必要但隱含的流程元件。這項視角轉換對於理解 LLM-based program repair（基於大型語言模型的程式修復）的成本結構至關重要。

與 Agentless 的對比尤具啟發性。Agentless 以 localization-repair-validation pipeline（定位-修復-驗證流程）取代 agent loop（智慧體迴圈），同時移除了 multi-turn loop（多輪迴圈）與 execution access，因此其結果無法分離 execution 本身的邊際貢獻。本文採取更為 fine-grained（細粒度）的立場：保留 agent loop 的價值，但質疑其中 iterative execution（迭代式執行）的必要性。這種「控制變因隔離」的方法論嚴謹性，顯著優於 Agentless 的「全有或全無」設計。

然而，本研究亦存在若干限制。首先，受限於預算，端到端實驗僅涵蓋 200 個實例（各資料集前 100 筆），樣本規模相對有限，可能影響結果的泛化性。其次，四種 execution paradigms 的具體操作細節在提供的摘要中未完全展開，讀者難以得知漸進權限的確切設計。第三，研究聚焦於 Python 的 SWE-bench 資料集，對於其他語言或任務類型的適用性仍需驗證。最後，儘管作者以 open-source model 排除資料洩漏疑慮，商業模型（如 GPT-5.2-x high、Claude-Sonnet-4.5）仍可能存在訓練資料中的基準洩漏風險，這是採用專有系統進行實證研究的普遍挑戰。

#### 可重現性評估

在資料層面，第一階段使用的 7,745 筆 agent traces 來自公開的 leaderboard submissions（排行榜提交結果），具備高度可取得性；SWE-bench Lite 與 Verified 亦為公開的 benchmark datasets。在模型與工具層面，open-source 的 OpenCode 與 Qwen2.5-Coder-32B 為公開資源，有利於重現部分實驗結果。然而，兩個 commercial agents（Claude Code 與 Codex CLI）及其背後的 proprietary models 為閉源系統，其 model weights（模型權重）、內部提示細節與推論機制未公開，限制了實驗的完全重現性。

此外，研究強調 per-repository environment setup（逐程式庫環境設定）與維護 Docker image（Docker 映像檔）是一項重複性工程負擔，這意味著重現研究需具備相應的基礎建設與運算資源，以處理繁複的 dependencies（相依套件）與 runtime（執行時期）配置。根據提供的上下文，作者並未明確說明是否釋出實驗腳本、分析工具或原始碼，因此原始碼層面的可重現性仍有待確認。

#### 未來研究方向

基於本文「execution benefit 集中而非均勻」的核心發現，未來研究可朝以下方向展開：

第一，**選擇性執行策略（Selective Execution）**：開發能依據任務特性動態決定「何時執行」的智慧型策略，將 code execution 視為具明確 cost-benefit tradeoff（成本效益權衡）的資源，而非預設能力。這需要設計基於實例難度、錯誤類型或回饋預期效益的動態執行預算機制，避免在單次修復中 indiscriminately 消耗過多 test runs。

第二，**驗證對齊與回饋品質提升**：針對 agent-chosen tests 與 ground-truth validation 之間的顯著落差，未來可研究如何縮小兩者差距，例如透過更穩健的 test suite（測試套件）篩選、整合官方驗證回饋，或設計能自動偵測並修正偽陽性驗證結果的機制，以提升 execution feedback 的可操作性。

第三，**環境設定成本最佳化**：鑒於 per-repository environment setup 與 Docker image 維護構成顯著的 deployment breadth（部署廣度）瓶頸，未來可探索輕量化的 runtime 環境、通用容器化方案或依賴靜態分析的替代驗證途徑，以降低 execution 的 latency（延遲）與 overhead。

第四，**跨語言與跨任務驗證**：將研究擴展至 SWE-bench 以外的 benchmark 與非 Python 語言，驗證「執行效益集中」與「執行限制影響微弱」等現象是否普遍存在於其他 automated program repair (APR)（自動化程式修復（APR））場景，從而建立更具泛化性的 cost-effectiveness（成本效益）模型。

## 論文問答

**Q1：這篇論文旨在解決什麼核心問題？**
A：這篇論文聚焦於基於大型語言模型的程式碼智慧體在自動化程式修復（APR）任務中，程式碼執行的成本效益問題。雖然「生成-執行-修正」的迭代範式已成為最先進系統的標準做法，但執行測試所帶來的時間延遲、Token 成本與逐程式庫環境設定等額外負擔相當可觀，學界卻尚未系統性地探討其對智慧體成效的實際貢獻。因此，本研究試圖回答一個根本問題：在程式修復過程中，程式碼執行究竟有多重要，其效益是否足以正當化它所耗費的龐大資源。

**Q2：現有方法或過往研究為何無法充分解答上述問題？**
A：過往研究大多將程式碼執行視為智慧體流程中必要但隱含的元件，主要關注模型架構、提示策略或搜尋演算法的改進，卻缺乏對執行行為的量化影響進行系統性調查。雖然 Agentless 這類工作嘗試避免迭代執行，但它同時移除了多輪迴圈與執行存取權限，導致無法單獨隔離「執行」這個變因所帶來的邊際效益。由於缺乏將執行作為單一控制變因的嚴謹對照實驗，社群對於執行在智慧體迴圈中的實際價值仍僅有有限的理解。

**Q3：為何探討程式碼執行的成本效益對程式修復領域至關重要？**
A：隨著程式碼智慧體日益部署於真實世界與大規模場景，執行所隱含的資源消耗變得不容忽視，包括產生執行指令與解析冗長回饋的 Token 成本、等待編譯與測試結果的實際時間成本，以及維護各目標程式庫專屬 Docker 映像檔的持續工程負擔。若智慧體不加區別地在所有實例上反覆執行測試，即使在其幾乎無法提供額外效益的情況下仍支付高昂代價，將導致整體部署廣度與可行性受到嚴重限制。因此，釐清執行何時真正有助於修復成功，並將其視為需明確權衡的成本效益資源，是推動該領域從追求基準測試效能邁向實務應用的關鍵。

**Q4：本研究採用的核心方法論為何？**
A：本研究設計了一個兩階段的實證研究架構，以全面刻畫並隔離程式碼執行的影響。第一階段分析來自 SWE-bench 排行榜提交結果的 7,745 筆公開智慧體軌跡，涵蓋四種執行導向的智慧體與十二種不同的大型語言模型，以描繪大規模的執行行為特徵。第二階段則針對三種智慧體（Claude Code、Codex 與開源的 OpenCode）進行 3,000 次端到端修復嘗試，並在固定智慧體腳手架的前提下，僅變更四種執行範式，從而實現對執行邊際價值的精細控制與細粒度比較。

**Q5：與 Agentless 等先前研究相比，本研究的關鍵創新之處為何？**
A：本研究首次將程式碼執行單獨隔離為一個受控變因，在維持智慧體迴圈與多輪互動架構不變的情況下，僅系統性地調整執行存取權限。相較之下，Agentless 同時移除了迭代迴圈與執行能力，使其實驗結果無法區分「缺乏多輪對話」與「缺乏執行回饋」各自造成的影響。這種更細粒度的實驗設計讓研究者能夠精確測量執行本身對修復成功率與效率的因果效應，而非僅能觀察到兩種設計差異的混合結果。

**Q6：實驗設計中的四種執行範式是如何規劃的，其設計考量為何？**
A：研究團隊設計了四種從完全禁止到無限制執行的漸進式權限設定，以模擬不同程度的執行存取權限對智慧體表現的影響。其中明確包含「禁止執行」（Prohibited）與「無限制執行」（Unrestricted）兩種極端條件，並在中間設置漸進的過渡等級，從而允許研究者觀察隨著執行回饋增加，效能與成本如何變化。這種設計的關鍵在於僅變動執行權限這單一維度，而保持底層模型、提示策略與智慧體架構完全一致，確保任何觀察到的差異都可歸因於執行本身及其所產生的執行回饋。

**Q7：實驗使用了哪些基準測試與資料集，其規模為何？**
A：研究涵蓋了 SWE-bench Lite 與 SWE-bench Verified 兩個廣泛使用的程式修復基準測試。在第一階段的大規模軌跡分析中，研究團隊檢視了 7,745 筆公開的智慧體軌跡；而在第二階段的受控實驗中，受限於預算，則從上述兩個資料集中各選取前 100 個實例，總計在 200 個實例上執行了 3,000 次端到端修復嘗試。這樣的規模雖非涵蓋全部資料，但已足以對三種不同性質的智慧體（商業與開源）進行具有統計檢定力與細粒度比較的評估。

**Q8：限制程式碼執行對修復成功率與成本的主要影響為何？**
A：實驗結果顯示，執行限制對修復成功的影響微乎其微：在搭載最先進模型的商業智慧體上，禁止執行與無限制執行之間的解決率差距僅有 1.25 個百分點，且經 McNemar 檢定後不具統計顯著性。然而，禁止執行卻能帶來可觀的成本節省，例如 Claude Code 在無執行存取的情況下節省了 56% 的 Token 成本與 48% 的實際時間成本，而開源的 OpenCode 更減少了三倍以上的 Token 消耗。這些數據明確指出，當前智慧體在許多任務上支付了執行的高昂代價，卻未獲得相應的效能回報。

**Q9：細部分析揭示了執行回饋在何種條件下真正有益？**
A：深入分析發現，執行的效益並非均勻分布，而是高度集中在特定實例上，顯示當前智慧體確實存在不加區別地使用執行的問題。具體而言，錯誤重現執行對缺陷定位的幫助有限，僅有 48.8% 的重現執行能產生可操作的回饋；同時，54% 至 66% 的商業智慧體成功案例僅需單次編輯即可完成修復，與是否具備執行權限無關。更令人意外的是，81% 至 100% 的失敗案例雖通過了智慧體自行執行的驗證測試，卻在官方 SWE-bench 評估中失敗，凸顯智慧體自選測試與地面真實驗證之間存在顯著落差。

**Q10：實務上，商業程式碼智慧體的開發者應如何重新思考程式碼執行的角色？**
A：根據研究發現，開發者應將程式碼執行視為一項需要明確成本效益權衡的資源，而非預設必須具備的能力。智慧體不應在每次迭代中不加區別地執行測試，而應建立決策機制，評估當前修復階段與問題特性是否值得投入執行成本。這種典範轉移有助於在維持相近解決率的前提下，大幅降低 Token 成本與實際時間成本，使大規模部署更具經濟可行性與工程可擴展性。

**Q11：在真實世界大規模部署 LLM 修復智慧體時，應考量哪些實務因素？**
A：部署時必須將逐程式庫環境設定的隱性成本納入總體評估，因為維護每個目標程式庫專屬的 Docker 映像檔與相依套件是一項隨部署廣度線性增長的持續工程稅負。此外，執行測試套件可能耗費數分鐘到數小時的延遲，在需要快速回應的開發流程中會形成瓶頸，因此需權衡執行回饋的即時價值與其造成的等待成本。研究結果建議，產品團隊應優先投資於「選擇性執行」策略，讓智慧體僅在預期能顯著提升修復品質的關鍵時刻才啟動執行環境。

**Q12：這項研究可能如何影響未來程式修復智慧體的基準測試與評估方式？**
A：本研究揭示了僅以解決率作為唯一指標的不足，因為不同執行範式在幾乎相同的解決率下可能伴隨數倍差的資源消耗，凸顯成本效益應成為未來基準測試的核心維度之一。此外，智慧體自選測試與官方評估之間的系統性落差也提示，未來的評測標準應設計機制來偵測並懲罰過度擬合智慧體自身驗證流程的行為。整體而言，評估框架應從單純追求效能最大化，轉向同時衡量成功率、Token 成本、實際時間成本與執行次數的多目標優化典範。

**Q13：本研究在實驗範圍上有哪些已知的限制？**
A：由於預算限制，第二階段的受控實驗僅針對 SWE-bench Lite 與 Verified 的前 100 個實例進行，未能涵蓋整個資料集的所有多樣性，這可能影響結果在極端複雜或特定領域錯誤上的泛化性。此外，實驗主要聚焦於三種特定智慧體與其對應的大型語言模型組合，雖然已包含商業與開源代表，但仍無法完全推廣到所有現有或未來的模型架構。這些限制意味著，在執行極為關鍵的特定錯誤類型或不同語言生態系中，執行的邊際價值可能會有所不同，需要更多後續研究來驗證。

**Q14：在哪些類型的失敗案例或情境中，程式碼執行仍顯示出有限或無效益？**
A：研究發現，在僅需單次編輯即可修復的簡單案例中，無論是否允許執行，智慧體都能完成修復，顯示執行在這些情境下是多餘的資源浪費。同時，許多失敗案例呈現「智慧體驗證通過但官方評估失敗」的模式，表示執行回饋不僅未能導向正確修補程式，反而可能因為測試選擇不當而強化了錯誤的方向。此外，錯誤重現執行雖被頻繁使用，卻只有不到半數能產生可操作的定位資訊，說明在資訊不足或測試設計不良的條件下，執行本身難以轉化為有效的修復指導。

**Q15：這項工作為未來優化程式修復智慧體中的執行策略指出了哪些研究方向？**
A：未來研究可聚焦於開發動態的「選擇性執行」演算法，讓智慧體能根據當前對話狀態、問題複雜度與預期資訊增益，自主決定是否投入執行成本。另一個重要方向是縮小智慧體自選測試與地面真實驗證之間的落差，例如透過更強大的測試生成技術或將官方測試資訊更有效地整合至智慧體迴圈中。最後，鑑於研究發現後期執行的成功率顯著高於前期，探索如何將執行資源集中於修復流程的後段、並在前期以靜態分析或模型內部知識取代部分執行，將是提升整體成本效益的關鍵途徑。

## 實務應用指南

### 適用場景

1. **企業內部自動化程式修復管線**：當組織每日需處理大量內部程式庫的缺陷單時，可參考本文發現，對商業智慧體限制早期執行，僅保留最終驗證階段的執行權限，以降低 Token 成本與實際時間成本。
2. **資源受限的私有部署或邊緣環境**：在無法負擔逐程式庫 Docker 映像檔維護與長時間測試套件執行的場景下，採用「禁止執行」或限制執行範式，搭配靜態分析取代部分執行回饋。
3. **開源專案持續整合／持續部署（CI/CD）**：將智慧體嵌入 CI/CD 流程時，避免每次提交都觸發完整的生成-執行-修正迴圈，改為先以無執行模式產生候選修補程式，僅對高信心度修補進行測試執行。
4. **大型單體程式碼庫的初步缺陷分類**：在缺陷定位階段，利用本文觀察「執行對定位準確率影響有限」的結論，先在不執行程式碼的情況下產生定位與修復草案，減少環境設定開銷。
5. **教育或程式碼輔助工具**：在需要即時回應的互動式場景中，限制智慧體的反覆測試執行次數，避免學生或使用者等待過久，同時維持可接受的修復成功率。

### 實作前置條件

- **資料**：具備標準測試套件的缺陷資料集（如 SWE-bench Lite/Verified 格式）或內部累積的錯誤報告與智慧體軌跡；至少 100 筆以上實例以進行統計顯著檢定。
- **運算**：商業 LLM API（如 Claude Code、Codex）或開源模型推理端點（如 Qwen2.5-Coder-32B）；可執行容器化測試的環境（Docker）；以及用於對照實驗的無執行隔離環境。
- **技術能力**：熟悉 Python 專案結構與測試框架（pytest、unittest）；具備 Docker 映像檔維護與相依套件管理能力；能設計提示策略並分析智慧體軌跡；具備基礎統計分析能力（如 McNemar 檢定）以評估不同執行範式間的顯著性差異。

### 實作步驟建議

1. **建立無執行基線**：先將現有智慧體設定為「禁止執行」模式，測量其解決率、Token 成本與實際時間成本，作為對照基準。
2. **蒐集並分析智慧體軌跡**：記錄現有智慧體在無限制執行下的完整軌跡，統計每項任務的測試執行次數、執行階段分佈（早期 vs 晚期）與成功率，識別執行是否被不加區別地使用。
3. **設計分階段執行策略**：根據本文「晚期執行成功率顯著高於早期」的發現，限制對話前 50–60% 回合的執行存取權限，僅允許後期驗證；或設定執行預算（如每任務最多 3 次）。
4. **建立成本監控與效益閘道**：為每次執行記錄 Token 消耗與延遲，並設定條件式閘道——例如僅當修補程式涉及多檔案變更或信心分數低於閾值時，才觸發執行回饋。
5. **對齊智慧體驗證與官方測試**：針對「81–100% 失敗案例通過智慧體自我驗證但官方測試失敗」的落差，確保最終輸出一律經過與 SWE-bench 同等級的客觀測試套件驗證，而非僅依賴智慧體自行挑選的測試。
6. **漸進式部署與 A/B 測試**：先在非關鍵程式庫或 Lite 子集上比較「限制執行」與「無限制執行」的解決率差距，確認落在 1–2 個百分點內且統計不顯著後，再擴大至正式環境。

### 潛在風險與注意事項

- **不加區別地執行導致成本膨脹**：許多智慧體預設會反覆執行測試，即使對簡單錯誤也平均觸發 8.8 次測試執行。應設定硬性執行上限，並監控逐程式庫環境設定的工程稅。
- **智慧體自我驗證與地面真實值脫節**：研究顯示絕大多數失敗案例通過了智慧體自己執行的驗證，卻未通過官方評估。切勿以智慧體自行挑選的測試結果作為最終品質保證。
- **商業模型與開源模型的行為差異**：Claude Code 與 Codex 在禁止執行下仍保有高解決率，但開源 OpenCode 的基線較低。若使用開源模型，貿然移除執行可能導致效能斷崖，需先進行內部驗證。
- **晚期執行的隱性依賴**：雖然限制早期執行可省成本，但某些複雜缺陷仍需執行回饋來修正錯誤。建議保留「緊急執行」機制，允許智慧體在偵測到執行階段錯誤或編譯失敗時申請額外執行權限。
- **資料外洩與安全性**：在禁止執行模式下，智慧體可能更依賴訓練資料中的模式匹配。若目標程式庫包含敏感程式碼，應評估模型記憶風險，並優先使用訓練截止時間早於專案建立時間的模型。

### 與其他技術的整合建議

- **靜態分析與缺陷定位工具**：由於研究顯示執行對定位準確率提升有限（95% 以上 regardless of execution），可整合 Language Server Protocol（LSP）或靜態分析器（如 pylint、mypy）來取代早期的錯誤重現執行，提供低成本回饋。
- **檢索增強生成（RAG）**：在無執行模式下，智慧體更依賴程式碼理解。透過 RAG 注入相關函式定義與歷史修復紀錄，可彌補缺乏執行回饋的資訊缺口。
- **CI/CD 管線分層測試**：將智慧體產出的候選修補程式先送入輕量級煙霧測試（smoke test），僅通過後再執行完整測試套件，避免在明顯錯誤的修補上浪費長時間測試執行。
- **可觀測性平台**：整合 Prometheus/Grafana 或 LangSmith，追蹤每個任務的執行次數、Token 成本與解決率，建立執行效益的儀表板，持續優化成本效益權衡。
- **正式驗證與符號執行**：對於安全性關鍵修補，執行回饋可能不足以發現邊界案例。可將智慧體輸出銜接至符號執行或模糊測試工具，作為執行回饋的高階補充。

### 給不同背景讀者的閱讀建議

- **初學者**：請先聚焦論文的核心訊息——「執行程式碼並非越多越好」。理解生成-執行-修正範式中潛藏的 Token 成本與實際時間成本，並認識到在許多情況下，智慧體即使不執行程式碼也能達到相近的修復成功率。建議從第三節（RQ1）的執行行為描述與第四節（RQ2）的量化比較開始讀起。
- **AI 工程師**：請重點關注實驗設計的四種執行範式（禁止、限制、分階段、無限制）與智慧體軌跡分析方法。論文提供了具體的實作線索，例如如何固定智慧體骨架、僅變更執行存取權限來進行對照實驗，以及如何建立選擇性執行閘道。建議深入閱讀 RQ2 與 RQ3 的方法論與失敗案例分析。
- **研究人員**：本文首次將程式碼執行隔離為單一控制變因，填補了過往文獻將執行視為隱含必要條件的空白。建議關注其統計方法（McNemar 檢定）、資料集取樣策略，以及「執行效益集中而非均勻」這一發現所帶來的研究機會——例如設計自適應執行決策演算法，或探討為何商業模型在無執行下仍維持高解決率。
- **產品經理**：請將本文視為一份 ROI 分析報告。關鍵數字是：限制執行可節省 56% Token 與 48% 實際時間，而解決率僅下降約 1.25 個百分點且統計不顯著。建議據此評估在生產環境中導入「執行預算」或「分階段執行」策略的商業價值，並將執行視為需明確成本效益權衡的資源，而非預設啟用的能力。
