## 摘要翻譯

即使是一篇經過仔細校對的論文，仍可能在證明或所列假設中留下小缺口。我們介紹 PaperFormalizer，一個基於 Lean 的代理式流程管線，協助作者找出並補上其論文中的此類缺口，並將每篇論文轉化為通過 Lean 驗證的版本。從 LaTeX 原始碼開始，PaperFormalizer 將論文轉錄為陳述的依賴圖，審核每個自然語言陳述的忠實性、歧義性與正確性，接著在 Lean 中針對 Mathlib、選用的領域函式庫以及作者的個人工具組進行形式化與證明。只有作者知道一個陳述的真正意涵，以及如何最佳地修補結果中的形式化缺口。因此，當陳述存在多種解讀時，流程管線會停下並詢問作者；以自然語言與 TeX 符號呈現每項修補，作為作者可接受、拒絕或重新導向的提案；並將任何可能改變論文主張的決定留給作者。輸出為論文的註解版本與修訂版本、一份變更報告，以及 Lean 程式碼，其中每個宣告皆連結到其所形式化的陳述。隨著更多論文被形式化，作者的工具組也會持續成長；作者可分享其已驗證論文，使後續研究者能復用其 Lean 程式碼。透過讓已驗證論文的產出變得可行，PaperFormalizer 旨在使奠基於數學證明的研究更加健全。PaperFormalizer 運行於程式設計代理（Claude Code 或 Codex）之中，可於 https://github.com/Jiyuan-Tan/PaperFormalizer 取得。使用者所分享、附帶 Lean 程式碼的論文可於 https://paperformalizer.org 取得。

## 深度分析

#### 方法論解析

PaperFormalizer 提出了一套以 Lean 證明助手為基礎、結合大型語言模型代理 (LLM agent) 的「作者在迴圈中」(Author-in-the-Loop) 自動形式化 (Autoformalization) 流程管線 (Agentic Pipeline)。其核心設計理念是：自然語言 (Natural Language) 數學陳述具有內在歧義性 (Ambiguity)，且錯誤的修補方式可能改變作者原意，因此機器無法單獨完成從非形式化論文到形式化證明的轉換，必須由作者介入關鍵決策。

整個流程管線分為兩個主要階段，共六個子步驟：

**階段一：自然語言審核 (Natural Language Review)**

1. **轉錄 (Transcription)**：第一個代理讀取 LaTeX 原始碼，將論文轉換為一個「陳述依賴圖」(Dependency Graph of Statements)，其中節點代表論文中的各個陳述 (Statement)，邊則表示陳述之間的邏輯依賴關係。這一步驟將線性的論文結構轉化為可分析的圖結構，便於後續審核。

2. **審核 (Review)**：第二個審核代理 (Reviewer Agent) 對每個節點進行三方面的檢查——忠實性 (Faithfulness)、歧義性 (Ambiguity) 與正確性 (Correctness)。對於發現的問題，代理會提出修補方案 (Repairs)；當陳述存在多種合理解讀時，代理會停下來詢問作者，並以自然語言與 TeX 符號呈現每個修補提案 (Proposal)，由作者決定接受、拒絕或重新導向。

3. **規劃 (Planning)**：作者根據審核結果決定每個陳述的處理方式——復用 (Reuse) 既有形式化結果、重新形式化、或保持引用形式。

**階段二：自動形式化 (Autoformalization)**

4. **腳手架搭建 (Scaffolding)**：將審核通過的陳述轉化為 Lean 中的形式化宣告 (Declaration)，並進行忠實性稽核，確保形式化語句與自然語言陳述語意一致。

5. **證明填充 (Proof Filling)**：在 Lean 中填入完整證明，並進行細粒度的忠實性稽核，確保證明步驟對應論文的論證邏輯。

6. **連結 (Linking)**：建立 Lean 宣告與論文陳述之間的雙向連結，使每段形式化程式碼都能追溯到原始論文中的對應位置。

此設計的關鍵創新在於「雙層審核」機制：先在自然語言層面審核並修補，再在形式化層面審核並證明。這種分層策略降低了直接從自然語言跳到形式化時的錯誤率，因為許多歧義與錯誤可在自然語言階段就被發現並解決。此外，系統支援「個人工具組」(Author's Toolkit) 的累積——隨著作者形式化更多論文，可復用的 Lean 程式碼會持續增長，使後續論文的驗證成本遞減。

#### 實驗數據解讀

論文作者將 PaperFormalizer 應用於他們自己的三篇論文進行驗證。雖然完整實驗數據需參考第 5 節與相關表格，但從摘要與引言中可提取以下關鍵量化結果：

- **第一篇論文**：7 個結果中有 5 個需要某種形式的修訂，修訂比例約為 71%。
- **第二篇論文**：29 個結果中有 15 個需要修訂，修訂比例約為 52%。
- **修訂品質**：對於每個需要修訂的結果，流程管線提出的修補方案「大致保留了主要結果的陳述」(largely preserve the statement of the main results)。

這些數據揭示了幾個重要意涵：

首先，即使經過多輪校對 (Proofreading) 的論文，仍有超過半數的結果存在需要修補的缺口 (Gap)，這凸顯了形式化驗證的價值——它能捕捉到人眼容易忽略的邊界情況 (Boundary Case)、遺漏的正則性條件 (Regularity Condition) 或隱含假設 (Assumption)。

其次，修訂比例在不同論文中差異顯著（52% vs 71%），這可能反映論文的數學複雜度、領域特性或作者校對程度的差異。遺憾的是，論文中未提供第三篇論文的具體數據，也未說明選擇標準，因此難以全面評估系統在不同類型數學論文上的表現。

第三，「大致保留主要結果」這一定性描述雖然正面，但缺乏嚴格的量化指標來衡量修補方案與作者原意的一致程度。例如，未說明有多少修補被作者接受、拒絕或修改，也未提供修補前後定理陳述的差異分析。

整體而言，現有實驗數據呈現的是「概念驗證」(Proof of Concept) 階段的結果，證明了系統的可行性，但尚不足以進行統計推論或與其他方法進行嚴格的基準比較 (Benchmark Comparison)。

#### 與現有研究的比較

PaperFormalizer 明確定位於現有自動形式化研究光譜的中間位置，介於「純自然語言審核」與「全自動形式化」兩類系統之間：

**與自然語言審核系統的比較**：OSVerify [3] 與 Rethlas-OSV 專注於審核解答或論文的數學內容（自然語言層面），僅將審核發現傳遞給人類專家。這類系統擅長發現錯誤，但無法產生可執行的形式化證明。PaperFormalizer 將自然語言審核作為第一階段，但進一步將審核通過的陳述形式化為 Lean 程式碼，提供了端到端 (End-to-End) 的解決方案。

**與全自動形式化系統的比較**：Rethlas、Archon [4]、LeanMarathon [5] 與 LeanFlow [6] 等系統致力於自動將非形式化論證或整篇論文形式化為 Lean 4 程式碼。這些系統追求最大化自動化程度，但論文作者指出，當陳述存在歧義或結果不正確時，機器無法獨立判斷正確的解讀或修補方式。PaperFormalizer 的核心差異化在於「作者在迴圈中」設計——系統在關鍵決策點停下來詢問作者，而非自行猜測。

**PaperFormalizer 的獨特優勢**：

1. **雙階段架構**：先在自然語言層面解決歧義與錯誤，再進行形式化，降低了形式化階段的語意偏差風險。
2. **作者決策權**：所有可能改變論文主張的決策都留給作者，確保形式化結果忠於作者原意。
3. **個人工具組的累積效應**：隨著形式化論文數量增加，復用率提升，使後續論文的驗證成本遞減。
4. **雙向連結**：Lean 宣告與論文陳述之間的雙向追溯，便於讀者理解形式化與原文的對應關係。

**現有方法的限制**：

1. **實驗規模有限**：僅在三篇作者自己的論文中測試，未涵蓋不同領域、不同複雜度的論文。
2. **依賴閉源模型**：系統運行於 Claude Code 或 Codex 等閉源程式設計代理 (Coding Agent) 之上，無法控制底層模型的行為。
3. **缺乏量化評估指標**：未定義形式化忠實度、證明完成率等可量化的評估標準。
4. **Lean 特定性**：目前僅支援 Lean 與 Mathlib 生態系，無法直接應用於 Coq、Isabelle 等其他證明助手 (Proof Assistant)。

#### 可重現性評估

PaperFormalizer 在可重現性方面展現了良好的開放性：

**程式碼可用性**：系統已在 GitHub 公開（https://github.com/Jiyuan-Tan/PaperFormalizer），採用開源授權，研究者可自由取用、修改與部署。

**執行環境**：系統設計為在 Claude Code 或 Codex 等程式設計代理環境中運行，這意味著使用者需要具備相應的 API 存取權限。雖然這降低了純本機執行的可能性，但反映了當前 LLM 代理系統的典型部署模式。

**共享平台**：論文提供了 https://paperformalizer.org 作為使用者共享已驗證論文及其 Lean 程式碼的儲存庫 (Repository)，這為社群復用 (Reuse) 提供了基礎設施，有助於建立「驗證論文的網路效應」。

**依賴項**：系統依賴 Lean 4、Mathlib 以及可選的領域函式庫 (Domain Library)，這些都是成熟的開源專案，安裝與使用有完善的文檔支援。

**可重現性的限制**：

1. **底層模型不透明**：由於依賴閉源的 Claude 或 GPT 系列模型，相同的輸入可能因模型版本更新而產生不同輸出，影響實驗的可重現性。
2. **缺乏標準化測試集**：論文中未提供標準化的基準測試資料集 (Benchmark Dataset)，其他研究者難以在相同條件下比較不同方法的效能。
3. **作者介入的主觀性**：系統的「作者在迴圈中」設計意味著結果依賴於特定作者的判斷，這使得跨論文的比較缺乏統一的「標準答案」。
4. **實驗細節不完整**：論文中提及的「第 5 節與表格」在所提供的文本中未完整呈現，讀者需查閱完整論文才能獲取詳細的實驗設定與結果。

#### 未來研究方向

基於 PaperFormalizer 的當前設計與實驗結果，可識別出以下值得探索的研究方向：

**1. 擴大實驗規模與多樣性**

應定義並實作可量化的評估指標，例如：

代理會為每個陳述決定是復用 Mathlib、領域函式庫或作者工具組中的既有結果，還是從頭形式化。審查此規劃，特別注意被標記為「復用」的項目是否真的語義一致。

**步驟六：執行 Stage II 證明填充與連結（Proof Filling & Linking）**
代理自動產生 Lean 證明，並進行細粒度的忠實性審核。每個 Lean 宣告會被連結回論文中對應的陳述。此階段可能耗時較長（從數小時到數天，取決於論文規模），建議設定較長的代理執行逾時。

**步驟七：產出與發布**
取得三項產出：註解且修訂的論文、變更報告、以及與陳述連結的 Lean 程式碼。若希望與後續研究者共享，可將 Lean 程式碼上傳至 paperformalizer.org，並在論文中加入引用資訊。

### 潛在風險與注意事項

**風險一：修補方案改變原意**
系統提出的「最小修改」修補可能在邏輯上正確，但放棄了作者最在意的結論強度。**緩解方式**：在 Stage I 審核時，明確標記哪些結論是「不可妥協」的核心結果，要求代理為這些陳述提供保留原意的替代修補。

**風險二：LaTeX 巨集導致轉錄錯誤**
自定義的 `\newcommand`、領域特定的符號套件（如 `\usepackage{stmaryrd}`）可能被轉錄代理誤判。**緩解方式**：在執行前先將關鍵巨集展開為標準 LaTeX，或在轉錄後手動核對依賴圖中的陳述文字。

**風險三：Mathlib 命名空間漂移**
Lean 生態快速演進，Mathlib 中的名稱與 API 可能與論文寫作時不同。**緩解方式**：鎖定 Lean 工具鏈版本（透過 `lean-toolchain` 檔案），並在變更報告中記錄所使用的 Mathlib commit。

**風險四：作者工具組的「技術債」累積**
隨著形式化論文增加，個人工具組可能累積未充分審查的輔助引理。**緩解方式**：定期對工具組中的宣告進行回顧，標記哪些是「已驗證用於多篇論文」的核心元件。

**風險五：審核代理的假陽性與假陰性**
自然語言審核可能漏掉真正的錯誤，或將正確的陳述誤判為有問題。**緩解方式**：不要將 PaperFormalizer 視為最終裁決，而是作為「找出值得仔細檢查之處」的工具；對於系統未標記的陳述，仍需作者自行判斷。

**風險六：時間投入超出預期**
雖然比手動形式化快，但完整跑完一篇 30 個結果的論文仍可能耗時數週。**緩解方式**：採用漸進式策略，先形式化核心定理，附錄或次要引理留待後續版本。

### 與其他技術的整合建議

**與 arXiv 整合**：可將 arXiv e-print ID 作為輸入直接觸發流程，並在產出階段自動產生對應的 arXiv 註解版本（透過 overleaf 或自建 LaTeX 編譯流程）。

**與 GitHub Actions 整合**：將 Lean 編譯與忠實性審核包裝成 CI 工作流程，每次論文更新時自動驗證 Lean 程式碼仍可編譯，避免形式化版本與論文版本脫鉤。

**與 Mathlib 社群整合**：當形式化過程中發現 Mathlib 缺少的通用引理時，可將其貢獻回 Mathlib（遵循貢獻指南），使作者工具組與社群資源互相滋養。

**與文獻管理工具整合**：搭配 Zotero 或類似工具管理「已驗證論文」清單，在撰寫新論文時自動標記哪些引用已有可復用的 Lean 程式碼。

**與版本控制整合**：將 Lean 程式碼、修訂論文、變更報告放在同一個 Git 儲存庫的不同目錄，使用 git tag 標記每個論文的「已驗證版本」，方便日後追溯。

**與 LLM 評估管線整合**：若機構內部已有 AI 審稿系統，可將 PaperFormalizer 的審核階段作為其中一個專門的「數學健全性檢查」模組，與其他維度（寫作品質、實驗設計等）的檢查並行運作。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）與第 3 節（Stage I 的作者互動機制），理解「為什麼需要作者在迴圈中」這個核心設計理念，再瀏覽圖 1 的工作流程圖。實作上可從一篇自己寫過的小型技術報告開始，親身體驗「歧義性詢問」與「修補提案」的互動方式，無需急於理解 Lean 程式碼細節。

**給 AI 工程師**：重點閱讀第 2 節（Pipeline Design）與第 4 節（個人工具組的回饋迴圈），理解代理之間的分工介面、忠實性審核的細粒度設計、以及如何讓 LLM 與形式化系統（Lean）形成可靠的雙向校驗。若要二次開發，應特別關注代理提示詞的設計與 Stage I/II 之間的狀態傳遞格式。

**給研究者**：重點閱讀第 1 節末段的「Intended use」與第 5 節（實驗結果，特別是 5/7 與 15/29 的修訂比例），評估 PaperFormalizer 對自身研究流程的實質助益。建議將其視為「投稿前的最後一輪校對」，而非取代領域專家的審稿；對於高度領域特定或涉及新定義的論文，仍需作者深度參與。

**給產品經理**：重點閱讀摘要、「Intended use」段落與第 4 節的共享機制，理解 PaperFormalizer 的目標使用者（想強化自身論文的作者）、核心價值主張（讓已驗證論文變得實用可行）以及生態系設計（個人工具組 + 共享平台 paperformalizer.org）。若考慮商業化或機構導入，應評估 Lean 專業人才的稀缺性、單篇論文的處理成本，以及「修訂報告」作為可審計產出的潛在價值。
