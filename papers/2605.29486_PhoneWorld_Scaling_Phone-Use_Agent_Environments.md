## 摘要翻譯

手機使用智慧體（phone-use agents）的一大核心瓶頸在於，涵蓋真實行動行為且可控制、可複現（controllable, reproducible）的環境難以大規模建構。現有的行動智慧體評估基準測試（evaluation benchmarks）雖在評估方面取得重要進展，但其本身並未提供可擴展的方式來建構大量新的手機使用環境（phone-use environments）。我們提出 PhoneWorld，一個可重複使用的管線（reusable pipeline），能將真實 GUI 軌跡（GUI trajectories）與螢幕截圖（screenshots）轉換為可控制的手機使用環境（controllable phone-use environments）、可執行任務（executable tasks）、自動驗證器（automatic verifiers）與訓練展開（training rollouts）。有別於逐一手動建構行動評估基準測試，PhoneWorld 利用真實軌跡還原哪些畫面具關鍵性、畫面之間如何連結、哪些互動屬於狀態變更互動（state-changing interactions），以及哪些使用者目標（user goals）可進行自動驗證（automatic verification）。根據這些訊號，該管線建構出以唯讀應用程式內容（read-only app content）與可變狀態（mutable state）為後盾的可執行模擬 Android 應用程式（mock Android apps），再從相同的環境中衍生出可執行任務、基於規則的驗證器（rule-based verifiers）與訓練展開。在目前實作版本中，PhoneWorld 涵蓋 16 個領域（domains）共 34 個應用程式，包含搜尋、瀏覽、購物、訂位、媒體與社交互動等常見的消費者行動行為（consumer mobile behaviors）。在固定訓練預算（fixed training budget）下，於基於 AndroidWorld 的基線（baseline）中，將輔助語料庫（auxiliary corpus）的 10K 步驟替換為廣泛的 PhoneWorld 監督訊號（supervision），能同時提升四項評估基準測試的表現：HYMobileBench 提升 17.7 分、AndroidControl 提升 6.0 分、AndroidWorld 提升 14.7 分，以及 PhoneWorld 提升 52.5 分。我們接著探討兩個額外的擴展問題：增加 PhoneWorld 監督訊號的數量能顯著提升 PhoneWorld 的表現，且在固定的 PhoneWorld 預算下，擴展應用程式覆蓋範圍（app coverage）能帶來更大的增益。整體而言，PhoneWorld 將焦點從一次建構一個行動評估基準測試轉移至擴展手機使用環境本身的供給。

### 核心貢獻（3～5點）
- 提出 PhoneWorld，一個可重複使用的自動化管線（reusable pipeline），能將真實 GUI 軌跡與螢幕截圖轉換為大規模、可控制且可複現的手機使用環境（controllable phone-use environments）。
- 從真實軌跡自動還原關鍵畫面、導覽連結、狀態變更互動（state-changing interactions）與可驗證的使用者目標（user goals），並據此建構以唯讀應用程式內容（read-only app content）與可變狀態（mutable state）為後盾的模擬 Android 應用程式（mock Android apps）。
- 從相同環境同步衍生可執行任務（executable tasks）、自動驗證器（automatic verifiers）與訓練展開（training rollouts），形成完整的智慧體訓練與評估生態。
- 在固定訓練預算（fixed training budget）下，以 PhoneWorld 監督訊號（supervision）替換現有輔助語料庫（auxiliary corpus），可同時提升 HYMobileBench、AndroidControl、AndroidWorld 與 PhoneWorld 四項評估基準測試（evaluation benchmarks）的表現。
- 驗證增加監督訊號量與擴展應用程式覆蓋範圍（app coverage）均可帶來顯著效能增益，展現環境規模化（scaling）的價值。

### 適合對象
從事手機 GUI 智慧體、多模態智慧體（multimodal agents）、自動化行動介面操作，以及需要大規模可控制環境進行強化學習或模仿學習的研究者與開發者；亦適合關注評估基準測試（evaluation benchmarks）建構與資料管線（pipeline）設計的學術界與產業界人士。

## 深度分析

#### 方法論解析

PhoneWorld 的核心貢獻在於提出一套可重複使用的管線（reusable pipeline），將真實的 GUI 軌跡（GUI trajectories）與螢幕截圖（screenshots）轉換為可控制的手機使用環境（controllable phone-use environments）、可執行任務（executable tasks）、自動驗證器（automatic verifiers）以及訓練展開（training rollouts）。與傳統僅將軌跡視為模仿學習示範的做法不同，PhoneWorld 將真實使用軌跡（usage traces）視為環境建構的導引訊號，從中恢復應用程式的結構性知識，進而實現環境供給（environment supply）的規模化。

具體而言，該管線分為五個階段（對應圖 1）：

第一階段為真實應用頁面與軌跡擷取（Real App Pages and Traces）。研究團隊從真實應用程式中收集具代表性的螢幕截圖（screenshots）與手動探索的使用軌跡（usage traces），作為後續結構恢復的基礎資料。

第二階段為應用程式結構恢復（App Structure Recovery）。系統將螢幕截圖分類為不同的頁面類型（page types），並從軌跡中擷取各頁面的造訪頻率以及頁面轉移圖（transition graph）。此步驟識別出哪些畫面是核心的、導覽流程（navigation flows）如何在畫面間移動，以及哪些互動屬於狀態變更互動（state-changing interactions）。

第三階段為模擬應用規格建構（App Mock Specification）。恢復後的結構被轉換為頁面層級的產品需求文件（PRD）、可重複使用的 UI 元件、唯讀應用程式內容（read-only app content）層，以及可變狀態（mutable state）的資料綱要（schema）。這種設計確保模擬環境同時具備靜態內容的真實性與動態狀態的可操作性。

第四階段為自主應用程式建構（Autonomous App Construction）。一個程式編寫智慧體（coding agent）依據規格反覆實作、編譯、測試與修正模擬 Android 應用程式（mock Android apps），隨後經過人類稽核（human audit）。此階段產出可執行、可重置（resettable）且可檢視（inspectable）的模擬應用。

第五階段為任務合成與驗證環境（Environment for Task Synthesis and Verification）。在可執行的模擬環境上，系統衍生出可執行任務（executable tasks）、基於規則的驗證器（rule-based verifiers），並支援智慧體在模擬器（emulator）上進行 rollout，產生成功的訓練展開（training rollouts）供監督式微調（SFT）使用，同時也作為評估基準測試（evaluation benchmarks）的基礎。

此方法論的關鍵創新在於：同一套環境同時服務於評估與訓練。由於環境是模擬且可重置的，它不僅能進行程式化驗證（programmatic verification），還能被反覆執行以採集成功的訓練軌跡，從而將環境供給從評估工具擴展為訓練資料來源。此外，透過唯讀應用程式內容（read-only app content）與可變狀態（mutable state）的分離設計，PhoneWorld 在保持真實介面視覺外觀的同時，確保了互動狀態的可控性與可驗證性。

#### 實驗數據解讀

本研究圍繞三個擴展性問題（scaling questions）組織實驗，結果一致指向「環境供給是手機使用智慧體（phone-use agents）發展的關鍵瓶頸」。

第一個問題探討在固定訓練預算（fixed training budget）下，以 PhoneWorld 的監督訊號（supervision）部分取代輔助語料庫（auxiliary corpus）——即 AndroidWorld 的訓練資料——是否能提升基線（baseline）表現。實驗顯示，僅以 PhoneWorld 的 10K steps 取代原有輔助語料庫中的 10K steps，即可同時提升所有四項評估基準測試（evaluation benchmarks）的表現：HYMobileBench 提升 17.7 分、AndroidControl 提升 6.0 分、AndroidWorld 提升 14.7 分，而 PhoneWorld 本身提升 52.5 分。這項結果極具意義，因為它表明 PhoneWorld 的監督訊號不僅對自身環境有效，還能泛化至其他獨立的評估基準，顯示其捕捉了通用且可遷移的手機操作知識，而非僅是過擬合（overfitting）至特定模擬環境的表徵。

第二個實驗為全量取代對照（full-replacement control）：將整個輔助 AndroidWorld 語料庫全數替換為 PhoneWorld 監督訊號。結果顯示，此舉能強力提升 PhoneWorld 上的表現，但並未在匹配預算（matched-budget）設定下達到最全面的最佳效果。這說明 PhoneWorld 的監督訊號雖然強大，但與 AndroidWorld 資料具有互補性（complementary），而非單純的替代關係。最佳策略可能是混合使用真實應用軌跡（AndroidWorld）與模擬環境軌跡（PhoneWorld），以兼顧真實性與多樣性。

第三與第四個問題分別探討監督訊號數量與應用程式覆蓋範圍（app coverage）的擴展效應。研究發現，增加 PhoneWorld 監督訊號的量能顯著提升表現；而在固定 PhoneWorld 預算下，擴展應用程式覆蓋範圍（即納入更多 apps）能帶來更大的增益。這暗示在資源受限時，廣度（覆蓋更多領域/domains）可能比單一應用中的深度監督更具擴展效益，也呼應了本文主張——規模化的關鍵在於環境數量與類別的擴張。

整體而言，實驗數據強力支持本文核心論點：手機使用智慧體的進展不僅依賴更強大的模型，更依賴可擴展的手機使用環境（phone-use environments）供給方式。數據也顯示，即使只替換少量訓練步數，來自 34 個應用程式橫跨 16 個領域（domains）的廣泛監督訊號，就能在完全不同的測試分佈上帶來顯著增益。

#### 與現有研究的比較

現有手機智慧體研究主要沿兩條軸線發展：一是評估基準的建構，二是環境的可擴展建構。

在評估基準方面，AndroidWorld (Rawles et al., 2025) 確立了在真實 Android 應用程式中進行可複現（reproducible）線上評估的典範，具備程式化的任務初始化、成功檢查與重置邏輯。MobileWorld (Kong et al., 2025) 進一步推向長程、跨應用且更真實的手機任務。Android Agent Arena (Chai et al., 2025) 則提供基於關鍵狀態的任務驗證（essential-state-based task verification）之動態線上評估。MobileBench-OL (Wu et al., 2026a) 強調真實應用互動與實務執行能力。這些工作的重要性在於使嚴謹的線上評估成為可能，但它們的共同前提是「環境已經建置完成」，其焦點在於評估方法論。

PhoneWorld 的定位與上述工作形成鮮明對比：它並非僅是另一個評估基準，而是一套可重複使用的環境建構管線（pipeline），專注於解決「如何大規模建構新的手機使用環境」這一本質問題，特別是針對主流消費者行動行為（consumer mobile behaviors）所涉及的消費者面向應用程式。這使得 PhoneWorld 能同時支援評估與訓練，而現有基準大多僅聚焦評估。

在可擴展環境建構的相關研究中，InfiniteWeb (Zhang et al., 2026b) 等工作針對網頁環境提出自動化生成方法。PhoneWorld 則填補了行動應用領域的空白，並提出以真實 GUI 軌跡驅動的結構恢復與模擬應用程式自動建構流程，將真實軌跡的使用從「模仿對象」提升為「環境建構導引」。

然而，PhoneWorld 仍存在若干限制。首先，現行流程依賴人類稽核（human audit）確保模擬 Android 應用程式（mock Android apps）的品質，這在擴展至數百或數千個應用程式時可能成為瓶頸。其次，模擬應用程式基於唯讀應用程式內容（read-only app content）與可變狀態（mutable state）的設計，雖確保了可控性，但可能無法完全重現真實應用程式中所有複雜的動態行為（如即時伺服器互動、個人化推薦演算法、第三方登入流程）。第三，目前的基於規則的驗證器（rule-based verifiers）雖然可靠，但其設計需要針對不同應用程式定義規則，在極大規模擴展時可能面臨覆蓋率與維護成本的挑戰。

#### 可重現性評估

就本文提供的內容而言，PhoneWorld 的管線（pipeline）被描述為「AI 驅動、人類稽核（human-audited）」的流程，涵蓋從 GUI 軌跡（GUI trajectories）到模擬應用程式建構的完整鏈路。然而，在提供的摘要與內文脈絡中，作者並未明確宣告是否開放原始碼（open-source code）、釋出資料集（datasets）或公開模型權重（model weights）。

從方法論設計來看，PhoneWorld 具備良好的可重現性（reproducible）潛力：模擬 Android 應用程式（mock Android apps）本質上是可重置（resettable）且可檢視（inspectable）的，這消除了真實應用程式因版本更新或伺服器異動導致的不可複現問題。若未來作者釋出模擬應用程式的建構規格（PRD）、自動產生的程式碼、唯讀種子資料（read-only seed data）以及可變狀態（mutable state）的 SQLite 綱要，其他研究者將能完整重現這 34 個應用程式橫跨 16 個領域（domains）的環境。

目前可確認的是，PhoneWorld 在概念層面已將「可重現性」內建於設計核心：透過以模擬取代真實應用程式，環境狀態完全受控，這比依賴動態 Google Play 應用程式的評估方式更易複現。但要實際驗證與延伸此研究，社群仍需等待具體的開源釋出，特別是自主應用程式建構階段所使用的 coding agent 提示詞、人類稽核準則，以及規則驗證器（rule-based verifiers）的邏輯定義與任務敘述模板。

#### 未來研究方向

基於 PhoneWorld 的架構與實驗發現，以下幾個方向值得後續深入研究：

第一，降低人類稽核（human audit）成本。當前流程在第四階段仍需人類介入審查模擬 Android 應用程式（mock Android apps）。未來可探索更強大的程式編寫智慧體（coding agents）或自動化測試框架，以實現近乎全自動的環境建構，從而將規模從現行的 34 個應用程式擴展至數百甚至數千個應用程式，真正實現環境供給（environment supply）的規模化。

第二，深化跨應用長程任務。現有 PhoneWorld 實例涵蓋 16 個領域（domains），但任務可能仍多集中於單一應用內。借鑑 MobileWorld 的長程跨應用任務設定，未來可在 PhoneWorld 的可控制環境上設計更複雜的多應用協作流程，並研究手機使用智慧體（phone-use agents）在這類組合式任務中的規劃與推理能力。

第三，動態環境更新機制。真實應用程式持續演進，而模擬應用程式基於靜態的唯讀應用程式內容（read-only app content）。未來可研究如何透過持續學習或自動化差異偵測，將真實應用程式的更新同步至模擬環境，維持環境與真實世界的一致性，避免模擬環境隨時間漂移而過時。

第四，超越監督式微調（SFT）的訓練範式。本文展示 PhoneWorld 可產生訓練展開（training rollouts）供 SFT 使用。由於環境可重置且具備自動驗證器（automatic verifiers），它非常適合作為強化學習（Reinforcement Learning, RL）或線上探索（online exploration）的訓練場域。未來可探索以環境回饋驅動的 RL 訓練，進一步提升手機使用智慧體在觸控驅動介面（touch-driven interfaces）上的穩健性與探索效率。

第五，驗證機制的自動化擴展。目前的基於規則的驗證器（rule-based verifiers）與程式化驗證器（programmatic verifiers）依賴人工設計規則。未來可研究以大型語言模型（Large Language Models, LLMs）或學習式驗證器自動從使用軌跡（usage traces）與使用者目標（user goals）中推導驗證邏輯，降低任務設計的人力成本，並提升自動驗證器（automatic verifiers）的泛化能力。

第六，跨平台擴展。PhoneWorld 目前聚焦於 Android 平台。將此管線擴展至 iOS 或其他觸控驅動介面（touch-driven interfaces）平台，將有助於建立更通用的手機使用環境生態系，並探討不同平台間的知識遷移與模型泛化問題。

## 論文問答

**Q1：PhoneWorld 旨在解決的核心問題是什麼？**
A：PhoneWorld 旨在解決的核心瓶頸在於，如何大規模建構既可控又可複現、同時涵蓋真實手機使用行為的環境。真實的行動應用程式經常更新、難以重置，且要將其轉化為可複現的評估與訓練環境成本高昂，這使得手機使用智慧體的發展受到環境供給的嚴重限制。現有的評估基準雖然在可靠度上有所進展，但並未提供一種可擴展的方式來持續產出大量新的手機使用環境，因此 PhoneWorld 將重點放在環境本身的規模化建構上。

**Q2：現有的行動智慧體評估基準為何無法解決環境規模化的問題？**
A：現有的行動智慧體評估基準，例如 AndroidWorld、MobileWorld 與 Android Agent Arena，主要貢獻在於提供嚴謹的線上評估機制，但這些方法聚焦於「環境已建置完成後」的評估階段。它們本身並未提供一套可重複使用的流程，來系統性地產出針對主流消費者應用程式的大量新環境。由於這些基準通常需要針對單一應用程式手工打造，面對數量龐大且不斷變化的真實 App 時，這種做法難以擴展，無法滿足手機使用智慧體對於多樣化、可重置環境的需求。

**Q3：為什麼擴展手機使用環境的供給對於推動該領域進展至關重要？**
A：擴展手機使用環境的供給對於推動手機使用智慧體的進展至關重要，因為這類智慧體必須處理視覺豐富、有狀態且以觸控驅動的介面，而非僅透過 API 操作。與基於 API 的智慧體不同，手機使用智慧體需要在眾多不同應用程式中執行長程任務，這要求訓練與評估環境必須具備足夠的廣度與可複現性。若缺乏可規模化建構環境的方法，研究人員將持續受限於少數可手動維護的應用程式，進而阻礙模型能力與泛化性的提升。

**Q4：PhoneWorld 的核心方法與管線包含哪些主要步驟？**
A：PhoneWorld 的核心是一套可重複使用的 AI 驅動管線，能將真實的 GUI 軌跡與螢幕截圖轉化為可控制的手機使用環境、可執行任務、自動驗證器以及訓練展開。該流程首先從真實使用軌跡中恢復優先級化的螢幕清單、畫面轉移圖以及會改變環境狀態的互動操作；接著利用代表性的螢幕截圖建構可執行的模擬 Android 應用程式，以唯讀應用程式內容為基礎，並搭配可變狀態的資料庫架構。最後，系統從這些模擬環境中衍生出可執行任務、基於規則的驗證器以及成功的訓練軌跡，使環境同時服務於評估與監督式學習。

**Q5：相較於傳統基準建構方式，PhoneWorld 的關鍵創新是什麼？**
A：PhoneWorld 的關鍵創新在於它並非僅將真實軌跡視為模仿的示範，而是將其作為環境建構的指導訊號，從中發現哪些畫面是核心、畫面之間如何連結、哪些互動會改變狀態，以及哪些使用者目標適合自動驗證。這種方法將研究焦點從「一次手工打造一個行動基準測試」轉移到「規模化供應手機使用環境本身」。更重要的是，支援程式化評估的同一套環境也可以被重置、重新執行，並採集成功的訓練展開作為模型的監督訊號，實現評估與訓練資料生成的緊密整合。

**Q6：PhoneWorld 為何選擇以「唯讀內容＋可變狀態」的模擬 Android 應用程式作為環境基礎，而非直接使用真實 App？**
A：PhoneWorld 選擇建構模擬 Android 應用程式而非直接使用真實 App，是因為真實應用程式難以重置、頻繁變動，且要使其具備可複現性所費不貲。透過以真實 GUI 軌跡與螢幕截圖為基礎的模擬應用，環境既能保持與真實消費者行動行為的貼近性，同時又具備可重置、可檢視與可重複使用的特性。此外，將唯讀應用程式內容與可變狀態分離的設計，使得系統能夠自動驗證任務完成與否，並穩定地產出用於訓練的軌跡資料。

**Q7：實驗部分使用了哪些評估基準來驗證 PhoneWorld 的效用？**
A：本研究的實驗在 HYMobileBench、AndroidControl、AndroidWorld 以及 PhoneWorld 自身這四個評估基準測試上進行驗證。這些基準涵蓋了從基礎控制到長程複雜任務的不同面向，能夠全面衡量手機使用智慧體的表現。實驗採用基於 AndroidWorld 的強大基線模型，並透過替換其輔助語料庫中的部分訓練步數，來檢驗 PhoneWorld 監督訊號的效用。

**Q8：將 AndroidWorld 輔助語料替換為 PhoneWorld 監督訊號後，取得了哪些關鍵成果？**
A：在固定訓練預算下，將輔助 AndroidWorld 語料庫中的 10K 步替換為來自 PhoneWorld 的廣泛監督訊號後，所有四項評估基準同時獲得提升：HYMobileBench 進步 17.7 分、AndroidControl 進步 6.0 分、AndroidWorld 進步 14.7 分，而 PhoneWorld 本身進步 52.5 分。完全替換的對照實驗則顯示，PhoneWorld 的監督訊號雖然強大，但與 AndroidWorld 資料具有互補性，全數替換並未在匹配預算下達到最全面的表現。這些結果一致表明，PhoneWorld 提供的跨應用程式覆蓋範圍能夠顯著增強智慧體的泛化能力。

**Q9：關於監督量與應用程式覆蓋範圍的擴展性研究揭示了什麼？**
A：論文進一步探討了兩個擴展性問題：增加 PhoneWorld 監督訊號的數量，以及擴大應用程式覆蓋範圍。實驗發現，增加 PhoneWorld 監督量確實能顯著提升 PhoneWorld 基準上的表現；而在固定 PhoneWorld 預算下，擴展 App 覆蓋範圍則能帶來更大的增益。這顯示應用程式覆蓋範圍是更強的擴展訊號，意味著讓智慧體接觸更多樣的消費者應用程式領域，比單純增加特定 App 的訓練量更具效益。

**Q10：PhoneWorld 在實務上可以應用於哪些具體場景？**
A：PhoneWorld 可部署於需要快速為新消費者應用程式建構訓練與評估環境的場景，無需針對每個 App 手工打造基準測試。例如，智慧體開發團隊可以利用這套管線，自動生成涵蓋搜尋、購物、訂位、媒體與社交互動等 16 個領域的可執行環境。這使得企業能夠持續為不斷推陳出新的行動應用生態系統，提供穩定且可複現的訓練資料與評估平台。

**Q11：若要在產業環境中產品化部署 PhoneWorld，需要考量哪些因素？**
A：在產業環境中部署 PhoneWorld 時，必須考量自動化建構後仍需要人工稽核，以確保模擬 Android 應用程式的品質與正確性。產品團隊需要仔細設計唯讀種子資料與可寫入 SQLite 狀態之間的平衡，才能在維持介面真實感的同時確保環境可重置。此外，由於真實應用程式頻繁更新，管線需要定期重新執行並同步最新的 GUI 軌跡與螢幕截圖，才能讓模擬環境持續反映實際的消費者行動行為。

**Q12：PhoneWorld 可能對行動智慧體研究領域帶來什麼樣的深遠影響？**
A：PhoneWorld 有望改變行動智慧體研究的生態，將研究重心從「建構個別評估基準」轉向「建構可規模化供應環境的基礎建設」。透過降低產出新手機使用環境的成本，它不僅能加速訓練資料的生成，也能讓更多研究團隊在嚴謹且多樣的應用程式上進行評估。這可能使行動智慧體的開發更加民主化，讓資源較少的團隊也能取得過去只有大型機構才能維護的大量真實應用環境。

**Q13：作者在本論文中承認了哪些限制？**
A：論文坦承目前的 PhoneWorld 實例僅涵蓋 34 個應用程式與 16 個領域，雖然已具相當規模，但相較於數百萬計的真實 App 仍屬有限。模擬應用程式雖然能重現主要介面與導覽流程，但無法完全複製真實後端系統的複雜度與所有邊緣情況。此外，現階段的管線在應用程式建構階段仍需要人類參與稽核，這在一定程度上限制了完全自動化與無限擴展的可能性。

**Q14：在哪些類型的應用程式或任務上，PhoneWorld 可能會遭遇困難或失敗？**
A：PhoneWorld 在處理需要複雜即時後端互動或外部服務認證的應用程式時可能面臨挑戰，因為模擬環境難以忠實重現這類動態依賴。對於高度動態的內容，例如即時串流或即時多人互動，唯讀種子資料加上可變狀態的設計可能無法充分捕捉其即時變化的特性。此外，若任務成功與否取決於特定真實世界帳號狀態的跨應用程式互動，現有的基於規則驗證器可能難以準確判定任務完成狀態。

**Q15：根據論文內容，PhoneWorld 未來可以朝哪些方向進一步發展？**
A：未來研究可將 PhoneWorld 的應用程式覆蓋範圍從目前的 34 個擴展至數百甚至數千個，並進一步提升整體管線的自動化程度。強化編碼智慧體的能力以減少或消除人工稽核的需求，將是實現完全自主規模化的關鍵。另一個有潛力的方向是將 PhoneWorld 與持續更新的真實 GUI 軌跡串流整合，使模擬環境能夠隨著真實行動生態系統的演進而自我更新，從而建立長期可持續的手機使用環境供給機制。

## 實務應用指南

### 適用場景

1. **電商與 OTA 的自動化客服與回歸測試**：建立可重置的購物、訂房、訂票模擬環境，用於訓練手機客服智慧體處理下單、退換貨、行程修改等流程，或作為 App 改版前的自動化回歸測試沙盒。
2. **金融與支付 App 的合規與安全驗證**：將轉帳、繳費、申貸等真實操作流程轉為可控模擬環境，在不含敏感資料的條件下，驗證智慧體是否能正確完成任務並通過基於關鍵狀態的程式化驗證。
3. **內容與社群平台的審核與推薦測試**：模擬媒體消費、貼文互動、搜尋瀏覽等消費者行動行為，提供大規模且可複現的環境，以訓練或評估內容審核、輿情監控與推薦排序相關的多模態智慧體。
4. **企業內部行動應用的 RPA 訓練**：針對內部 ERP、CRM 或差勤系統的行動版，收集員工操作軌跡後建構模擬 App，讓 RPA 智慧體在可變狀態環境中反覆學習，避免直接在正式系統上操作。
5. **手機系統與輔助功能的無障礙驗證**：利用跨領域的模擬 App 覆蓋（如搜尋、購物、社交），建立多樣化畫面與互動流程，測試語音控制、螢幕閱讀器等輔助技術在不同情境下的穩定性。

### 實作前置條件

**資料需求**：真實 GUI 軌跡（包含螢幕截圖與對應的操作序列，如點擊座標與輸入內容）、探索式使用軌跡（exploratory-use episodes）、目標 App 的頁面結構參考文件，以及用於建構唯讀內容層的種子資料（read-only seed data）。

**運算資源**：Android 模擬器叢集（可採用自架 Emulator 或雲端裝置農場）、LLM API 配額（供頁面分類、轉移圖恢復與 Coding Agent 生成程式碼使用）、GPU 叢集（若計畫利用收集到的 rollout 進行多模態模型監督式微調）。

**技能需求**：具備 Android 開發基礎（理解 Activity、Fragment、SQLite 與編譯流程）、多模態模型訓練與資料處理經驗、軌跡清洗與頁面標註能力，以及 LLM Agent 的 Prompt Engineering 與除錯能力。

### 實作步驟建議

1. **軌跡收集與去識別化**：在目標 App 上執行探索式操作並錄製螢幕截圖與操作軌跡，同步移除或替換軌跡中的個人識別資訊（PII）與敏感內容。
2. **頁面結構恢復**：利用多模態模型或人工標註將截圖分類為頁面類型（如 P0/P1/P2 優先級），並從軌跡中恢復頁面轉移圖（transition graph）與狀態變更互動清單。
3. **撰寫模擬規格（PRD）**：為每個頁面產生詳細產品需求文件，定義全域與跨 App 可重用的 UI 元件模板，並設計唯讀內容 schema 與可變狀態（如 SQLite）的資料結構。
4. **自動化建構模擬 App**：啟動 Coding Agent，依據 PRD 迭代生成 Android 程式碼、編譯、安裝至模擬器，並執行自我檢查清單（self-review checklist）；優先實作高頻 P0 頁面以確保核心流程可運行。
5. **人工稽核與視覺對齊**：逐頁比對真實 App 與模擬 App 的畫面佈局與互動回饋，修正 UI 細節與狀態邏輯錯誤，確保模擬環境足以支撐後續的智慧體訓練。
6. **任務合成與驗證器開發**：從恢復的使用者目標中衍生可執行任務描述，並為每項任務建立基於規則或程式化的自動驗證器，明確定義任務完成的關鍵狀態指標。
7. **訓練與評估循環**：在模擬環境中執行智慧體 rollout，收集成功軌跡作為 SFT 監督資料；在固定訓練預算下，將 PhoneWorld 資料與現有輔助語料庫（如 AndroidWorld）混合，並於 HYMobileBench、AndroidControl 等基準上驗證成效。

### 潛在風險與注意事項

1. **模擬與真實差距（Sim-to-Real Gap）**：模擬 App 的視覺渲染、動畫時序或 API 回應可能與真實 App 存在差異，導致智慧體在真機環境泛化失敗。建議保留最小規模的真實 App 對照組，定期執行跨環境校準測試。
2. **版權與資料合規**：真實 App 的截圖、商標與內容可能涉及版權，種子資料應使用自行產生、開源授權或已去識別化的資料，避免直接複製受版權保護的商業內容作為唯讀內容層。
3. **狀態空間爆炸與維護成本**：過度追求頁面覆蓋率可能導致狀態組合過多、驗證器規則難以維護。建議採用優先級化策略，先聚焦高頻核心頁面（P0），再逐步擴充邊緣頁面（P1/P2）。
4. **LLM 生成程式碼的可靠性**：Coding Agent 可能產生無法編譯或含有邏輯漏洞的程式碼，必須建立「生成→編譯→測試→回饋」的自動化迴圈，並設置人工稽核閘道作為最後防線。
5. **驗證模糊地帶**：部分使用者目標（如「瀏覽感興趣的內容」）難以用規則自動驗證。任務設計階段應將目標轉譯為具體、可程式化檢查的關鍵狀態（例如「點擊了特定類別且停留超過 N 秒」）。

### 與其他技術的整合建議

1. **嵌入 CI/CD 管線**：將 PhoneWorld 模擬環境與自動驗證器整合至 Jenkins、GitLab CI 或 GitHub Actions，作為手機 App 每次發版前的自動化回歸測試與智慧體相容性驗證環節。
2. **結合雲端裝置農場**：透過 Firebase Test Lab、AWS Device Farm 或自架 Emulator 叢集大規模並行執行模擬 App，加速訓練 rollout 的收集與多裝置基準測試。
3. **對接多模態模型訓練框架**：將 PhoneWorld 產生的 SFT 資料直接餵入 LLaVA、Qwen-VL 等視覺語言模型訓練管線；實證顯示與 AndroidWorld 輔助語料混合使用可在固定預算下達到最佳泛化表現。
4. **搭配 RAG 知識庫維護**：將頁面 PRD、可重用 UI 元件規格與跨 App 互動文件向量化存入知識庫，供後續擴充新 App 時檢索重用，降低每次從零建構模擬環境的成本。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從圖 1 的管線全貌與「適用場景」開始，理解 PhoneWorld 並非單純的測試工具，而是一套「把真實手機畫面變成訓練場」的工廠；接著對照論文中的 34 個 App 範例，思考自己日常使用的 App 有哪些頁面可以被模擬，不必深入程式碼細節，重點是掌握「軌跡→結構→模擬→任務」的四階段邏輯。

**AI 工程師**：請重點閱讀第 2 節的環境建構細節與實驗章節的資料混合策略。論文證明將 PhoneWorld 監督訊號與 AndroidWorld 輔助語料庫搭配使用，在固定訓練預算下效果最佳；實作時應特別關注模擬 App 的狀態可變性與驗證器的程式化實作，這兩點直接影響 SFT 資料的品質與評估可信度。
