## ⚡ TL;DR

現有多智慧體編程系統受限於順序執行或缺乏協調，導致單一智慧體常放棄困難任務。
本文提出 AgentRoom，基於 CRDT 共享檔案系統，以 MCP 工具協調檔案宣告與廣播。
實驗顯示雙智慧體 AgentRoom 比單獨執行更少放棄任務，品質亦優於平行合併基線。

## 摘要翻譯

並發多智慧體編程（Concurrent Multi-Agent Coding）可望實現跨模組分工（Division of Labor）、透過冗餘達成的穩健性（Robustness through Redundancy），以及以多檔案專案（Multi-File Projects）為自然粒度（Natural Granularity）進行平行探索（Parallel Exploration）。即時協作編輯協定（Realtime Collaborative Editing Protocol）透過無衝突複製資料類型（Conflict-free Replicated Data Types, CRDT）為人類團隊解決這項協調（Coordination）問題；然而，這些系統底層的大型語言模型（LLM）卻是逐個詞元生成（Generate One Token at a Time），現有的多智慧體編程系統也承襲了這種序列限制（Serial Limit）：它們要不是透過階段交接（Phase Handoffs）依序安排智慧體，就是匯集未經協調的獨立樣本（Independent Samples）。此外，單一智慧體常以單檔雛形即退出（One-File Stub-and-Exit）的方式，放棄（Abandonment）高達一半的困難任務。AgentRoom 是一個適用於並發編程智慧體的即時協作編輯協定（Realtime Collaborative Editing Protocol）。其執行階層（Runtime Layer）運作於以 CRDT 合併的共享檔案系統（CRDT-merged Shared Filesystem）之上，將檔案層級宣告（佔用）（File-level Claim）、狀態（Status）與廣播（Broadcast）公開為 MCP 工具（MCP Tools）。五個前沿編程 CLI 模型（Frontier Coding-CLI Models）執行了四項後端編程任務（Backend Coding Tasks），並於 Python DevBench 與 Rust+axum 中進行跨語言檢查（Cross-Language Checks）。對於 CLI 穩定模型（CLI-stable Models），使用兩個智慧體的 AgentRoom 相較於單獨（Solo）放棄的任務更少，且執行間的變異更小。在對等運算（Matched-Compute）條件下，一項正向的平均 LLM 評審（LLM-judge）對比顯示 AgentRoom 優於平行合併（Parallel-merge）。另一項對比——套件探測（bundle probe）——則讓完整的 AgentRoom 優於每一個部分條件：這是一種排序關係，而非百分比差距。承擔負荷的是協調（Coordination），而非平行處理或 CRDT 合併（CRDT-merge）本身。

### 核心貢獻（3～5點）
- 提出 AgentRoom：一個適用於並發編程智慧體的即時協作編輯協定（Realtime Collaborative Editing Protocol），其執行階層（Runtime Layer）運作於以 CRDT 合併的共享檔案系統（CRDT-merged Shared Filesystem）之上，並將檔案層級宣告（佔用）（File-level Claim）、狀態（Status）與廣播（Broadcast）公開為 MCP 工具（MCP Tools）。
- 突破現有多智慧體編程系統的序列限制（Serial Limit），不再僅依賴階段交接（Phase Handoffs）或無協調的獨立樣本（Independent Samples），讓智慧體能在多檔案專案（Multi-File Projects）的自然粒度（Natural Granularity）下分工與平行探索（Parallel Exploration）。
- 透過五個前沿編程 CLI 模型（Frontier Coding-CLI Models）與四項後端編程任務（Backend Coding Tasks）的跨語言檢查（Cross-Language Checks），證明在 CLI 穩定模型（CLI-stable Models）下，雙智慧體 AgentRoom 比單獨（Solo）基線更少放棄（Abandonment）困難任務，且執行間變異更小。
- 在對等運算（Matched-Compute）條件下，以 LLM 評審（LLM-judge）與套件探測（bundle probe）證明完整 AgentRoom 優於平行合併（Parallel-merge）及各部分條件，並指出協調（Coordination）才是承擔負荷的關鍵，而非平行處理或 CRDT 合併（CRDT-merge）。

### 適合對象
從事多智慧體系統、LLM 程式生成、協同編輯協定與後端軟體工程的研究者與工程師；特別適合關注如何讓多個大型語言模型在共享工作空間（Shared Workspace）中有效分工、降低任務放棄率並提升程式碼生成穩健性的讀者。

## 深度分析

#### 方法論解析

AgentRoom 的核心貢獻在於把「即時協作編輯協定（Realtime Collaborative Editing Protocol）」從人類團隊場景遷移到多智慧體編程（Concurrent Multi-Agent Coding）場景，並且把協調層（coordination layer）與 CRDT 合併層（CRDT-merge layer）明確分離。整體架構可視為一個以 CRDT 為後盾（CRDT-backed）的共享工作空間（Shared Workspace），上面疊加一個由 MCP 工具（MCP Tools）暴露的狀態管理室（State-Management Room）。

**共享工作空間與 CRDT 基底。**  
底層採用 pycrdt（Yrs 的 Python 移植版）實作以 CRDT 合併的共享檔案系統（CRDT-merged Shared Filesystem）。所有智慧體（agents）在同一個 workspace 中執行，任一智慧體寫入的檔案會在 ∆ = 2 秒內以字元級（character-level）合併對其他智慧體可見。系統額外加入大括號／括號平衡的簡易檢查，以降低合併後語法立即崩潰的機率。這裡的 CRDT 滿足強最終一致性（Strong Eventual Consistency, SEC），確保並發編輯不會造成資料遺失；但作者也明確指出 SEC 只保證位元組層級（byte-level）的合併，不保證語意相容（semantic compatibility）。例如兩個智慧體在同一位移插入不相容的函式簽名，合併後兩段文字都會保留，但下游編譯或測試會失敗。

**協調介面：以 MCP 工具暴露的房間語義。**  
AgentRoom 把協調狀態封裝成一個執行階段物件（Runtime Object），並透過 MCP server 提供五個工具：

- `room_claim(path)`：檔案層級宣告（File-level Claim），以原子方式取得檔案所有權；若已被其他智慧體佔用則回傳 CONFLICT。
- `room_release(path)`：釋放（release）已佔用的檔案。
- `room_state()`：查詢房間狀態，回傳活躍宣告集合與近期廣播日誌視窗。
- `room_broadcast(msg)`：向僅附加廣播日誌（Append-only Broadcast Log）寫入訊息。
- `room_read()`：讀取房間狀態與共享檔案內容。

這組工具把「誰正在改哪個檔案」從自然語言對話中抽離出來，轉成狀態管理層強制執行的結構化資訊。這是 AgentRoom 與純聊天式多智慧體協調（chat-only multi-agent coordination）的關鍵區別：宣告語義（Claim Semantics）在狀態層強制執行，而非依賴智慧體自行解析文字。

**諮詢式鎖（Advisory Locking）與碰撞率模型。**  
`room_claim` 提供的是 Chubby 風格的諮詢式鎖（advisory lock）：鎖在 prompt 層強制，而非作業系統核心層。若智慧體未宣告就寫入，CRDT 仍會保留其位元組，但房間日誌會記錄違規，讓其他智慧體有機會進行跨智慧體除錯（cross-agent bug-fix pattern）。作者給出碰撞率（collision rate）公式：

\[
p_{\text{collision}}(N, K_t) = 1 - \prod_{k=0}^{N-1}\left(1 - \frac{k}{K_t}\right)
\]

在 N=2、K_t≈5 的運作點，碰撞機率約 20%。這說明僅有 CRDT 合併層仍會產生大量語意衝突；`room_claim` 以 O(1) 的單次編輯成本把碰撞率壓到接近零，從而讓協調層（coordination layer）承擔主要負載，而非平行度（parallelism）或 CRDT 合併本身。

**資訊論動機。**  
附錄 A.2 提供一個資訊論直覺：把 patch 視為對評分項目（rubric-coverage）空間的隨機變數，當宣告機制避免聯合熵（joint entropy）崩塌時，每步的聯合資訊量可接近隨智慧體數 N 線性成長。這只是動機而非形式證明，作者也謹慎地將其對應到 bundle component probe 的質性解讀。

#### 實驗數據解讀

實驗設計圍繞「對等運算（matched-compute）」原則：智慧體本身不變，只改變組合與協調方式。評估使用五個前沿編程 CLI 模型（frontier coding-CLI models），在四個後端編程任務（backend coding tasks）上進行，並以 Python DevBench 與 Rust+axum 做跨語言檢查（cross-language checks）。

**主要條件。**  
圖 1 的 T4 六條件協調消融實驗（T4 Six-Condition Coordination Ablation）包含：

- Solo：單獨（單一智慧體）基線。
- ChatDev：順序式階段交接（phase handoffs），設計→實作→審查。
- Parallel-merge / Parallel Solo：無協調的平行獨立樣本（independent samples），最後合併。
- Shared noMCP：有共享檔案系統但無 MCP 協調。
- AgentRoom（+collab）：完整協作條件。

**放棄率（Abandonment）的顯著改善。**  
最強的統計結果是「單檔雛形即退出（one-file stub-and-exit）」失效模式（failure mode）被大幅抑制。Solo 條件下，智慧體遇到困難任務時常只產生一個原始碼骨架（source skeleton）就提前退出（abandonment）。跨全部 12 個 model×task 分層，Cochran-Mantel-Haenszel（CMH）估計顯示 Solo 的放棄機率是 AgentRoom 的 13.7 倍（95% CI [3.9, 48]，p < 10⁻⁵，Tarone 同質性檢定 p=0.92）。而且每個有事件的分層，Solo 的放棄勝算比都大於 1。這說明兩個智慧體在 AgentRoom 中並行工作時，彼此的存在降低了「判定任務過難而放棄」的機率，可能是因為廣播日誌與共享進度提供了社會化／監督促進效果，也可能是因為檔案佔用機制讓智慧體更傾向完成自己負責的模組。

**連續型 LLM-judge 品質分數。**  
在對等運算下，AgentRoom 對 parallel-merge 的平均品質優勢為 +0.213（Welch p=0.003），且兩個評審模型都是 Sonnet，並採用結構上對偏見免疫（structurally bias-immune）的評分方式。這個正向平均對比把 AgentRoom 置於 parallel-merge 之上，但作者並未宣稱全面碾壓，而是強調「協調，而非平行度或 CRDT 合併，承擔了負載」。

**Bundle probe：協調層的質性貢獻。**  
附錄 B.13 的基質消融（substrate-only bundle probe）比較了 shared-only、prompt-only 與完整 AgentRoom，觀察到的順序為 shared-only < prompt-only < AgentRoom，其中最大的躍升出現在 MCP 協調層。然而由於 n=7，該步驟的信賴區間跨過零，因此只能質性解讀。這與資訊論動機一致：單純共享檔案或單純提示協作都不足以產生穩定增益，必須有結構化的檔案層級宣告與廣播機制。

**限制與細節。**  
- 樣本數在不同條件間差異大（n=6、12、32、11、7、14），部分對比的檢定力有限。  
- 結果主要來自 CLI-stable models；非穩定模型可能受工具呼叫失敗率影響。  
- Rust+axum 與 Python DevBench 的跨語言檢查雖然增加外部效度，但任務數量仍偏少。  
- LLM-judge 雖然採用結構化設計，仍屬自動評分，可能遺漏執行期語意錯誤。

#### 與現有研究的比較

**相對於順序式多智慧體系統（ChatDev-style）。**  
現有多智慧體編程系統大多採用順序輪替（sequential turn-taking）：設計→實作→審查，每個智慧體等待前一個完成。這種編排式交接（orchestrated handoffs）與角色預先分配（role pre-assignment）雖然降低了衝突，但也把 LLM 的生成過程鎖死在單一序列中，無法發揮多檔案專案（multi-file projects）的自然粒度（natural granularity）優勢。AgentRoom 透過顯式協調（explicit coordination）讓智慧體同時編輯不同檔案，從而實現分工（division of labor）與平行探索（parallel exploration）。

**相對於隱式 CRDT 協調（CodeCRDT）。**  
Pugachev (2025) 的 CodeCRDT 探索了隱式協調（implicit coordination）與角色預先分配（outliner / implementer），結果呈現混合成效：21% 加速與 39% 減慢並存。AgentRoom 與其不同之處在於：不使用預設角色，也不依賴編排交接，而是提供一個開放的房間與諮詢式協定（advisory protocol）。這讓智慧體能根據任務動態決定誰負責哪個檔案，而非被鎖定在大綱撰寫者（outliner）與實作者（implementer）的固定分工。

**相對於平行獨立樣本（parallel-merge / Parallel Solo）。**  
許多現代編程代理透過獨立採樣多條軌跡再合併結果來提升穩健性（robustness through redundancy）。這種方法雖然能透過冗餘（redundancy）降低單次失敗機率，但智慧體之間沒有協調，容易產生重複勞動與合併衝突。AgentRoom 在對等運算下對 parallel-merge 取得 +0.213 的平均品質優勢，顯示「協調後的並發」優於「無協調的並行」。

**相對於單獨智慧體（Solo）。**  
Solo 基線的「單檔雛形即退出」失效模式在多檔案後端任務中相當嚴重。AgentRoom 透過兩個智慧體的互相監督與檔案佔用機制，把放棄機率壓到極低。這凸顯了多智慧體協作在複雜任務中的價值，不只是加速，更是完成率（completion rate）的提升。

**尚未解決的問題。**  
- AgentRoom 目前仍依賴智慧體自願遵守 `room_claim` 規則；惡意或過於積極的智慧體可能未宣告就寫入。  
- CRDT 僅處理字元級合併，對語意衝突（如函式簽名不相容、型別不一致）無能為力。  
- 實驗規模集中在 N=2；當 N 增加時，碰撞率公式顯示衝突機率會快速上升，需要更強的協調策略。

#### 可重現性評估

從目前提供的全文脈絡來看，**論文尚未明確釋出開源程式碼、資料集或模型權重**。文中提到使用的技術元件大多為現有開源專案：

- pycrdt / Yrs：Y.js 的 Rust 核心移植，已開源。  
- Automerge：另一個 CRDT 實作，已開源。  
- MCP（Model Context Protocol）：Anthropic 提出的開放協定。  

然而，AgentRoom 本身的 runtime layer、MCP server 實作、提示詞模板（prompt templates）、評分 rubric、LLM-judge 腳本、以及實驗所用的後端任務具體版本，都**未在摘要與第一章中提及公開連結**。由於這是一篇 preprint，後續可能會釋出程式碼，但目前無法直接重現。

**可重現性的具體缺口：**

1. **程式碼：** 沒有提供 AgentRoom 系統實作的 repository 或套件名稱。  
2. **資料集：** Python DevBench 與 Rust+axum 任務的確切題目、測試案例、環境設定未詳列。  
3. **模型權重：** 使用的是商業 API 模型（Sonnet 等），權重不公開，但這在 LLM 研究中屬常態；重現時需使用相同 API 版本與參數。  
4. **實驗日誌：** 未說明是否公開原始對話軌跡、CRDT 合併紀錄、廣播日誌，這些對於理解協調動態至關重要。  
5. **隨機種子與抽樣：** 未說明每個條件的確切執行次數分配與隨機控制方式。

若要提升可重現性，建議作者釋出一個 Docker 化的實驗環境，包含 AgentRoom MCP server、任務定義、評分腳本與範例軌跡。

#### 未來研究方向

**1. 語意級 CRDT 與結構感知合併。**  
目前的 CRDT 只保證位元組層級合併。未來可探索語法樹級（AST-level）或型別級的 CRDT，讓並發編輯在函式簽名、資料結構、介面定義等層面也能自動合併或至少標記衝突，降低下游編譯失敗率。

**2. 動態角色與自適應分工。**  
AgentRoom 不預先分配角色，但未來可研究智慧體如何根據任務難度、檔案依賴圖、即時測試回饋，動態協商誰負責哪個模組。這可結合程式分析（program analysis）與圖神經網路來預測最佳分工。

**3. 擴展到 N > 2 的智慧體規模。**  
碰撞率公式顯示，當 N 增加時，檔案層級宣告的競爭會加劇。未來需要研究階層式宣告（目錄層級、模組層級）、子任務拍賣機制、或基於依賴圖的排程，以維持協調效率。

**4. 人機協作與可解釋協調。**  
AgentRoom 的廣播日誌與宣告狀態對人類開發者而言是高度可視化的。未來可將其整合進 IDE（如 VS Code），讓人類與多個 AI 智慧體在同一個共享工作空間中協作，並即時審查智慧體的協調決策。

**5. 容錯與惡意智慧體。**  
目前 `room_claim` 是諮詢式鎖，未強制執行。未來可研究如何在不犧牲靈活性的前提下，加入沙箱、回滾機制、或共識協定，以處理工具呼叫失敗、無限迴圈、或互相干擾的智慧體。

**6. 更廣泛的任務與語言覆蓋。**  
目前評估集中在後端編程任務與 Python/Rust。未來可擴展到前端開發、全端專案、資料科學 pipeline、基礎設施即程式碼（Infrastructure-as-Code）等場景，並納入更多程式語言與框架。

**7. 形式化協調理論。**  
附錄 A.2 的資訊論動機可進一步發展為形式化證明，探討在特定依賴結構與宣告策略下，協調並發編輯的資訊增益上界與下界，並據此設計最優協調協定。

**8. 與現有軟體工程流程整合。**  
將 AgentRoom 與版本控制（Git）、持續整合（CI）、程式碼審查（code review）流程結合，讓智慧體的協調日誌成為可審計的開發歷史，而不只是執行階段的暫態狀態。

## 論文問答

**Q1：並發多智慧體編程要解決的核心問題是什麼？**
A：核心問題在於如何讓多個大型語言模型智慧體在同一個多檔案專案上同時工作，而不會因為缺乏協調而互相衝突或重複勞動。現有系統大多繼承了 LLM 逐個詞元生成的序列限制，智慧體只能透過設計→實作→審查等階段交接，或完全獨立取樣後再合併，無法真正發揮並行探索與分工的潛力。AgentRoom 正是要回答：在對等運算的前提下，顯式協調的 CRDT 共享工作空間能否同時勝過順序式與隱式 CRDT 協調這兩種替代方案。

**Q2：現有的多智慧體編碼系統為什麼無法有效並發？**
A：現有系統主要採用順序輪轉，每個智慧體必須等待前一個完成才能接手，這把本可並行的計算資源浪費在等待上。另一種極端是讓多個智慧體獨立執行、最後再合併結果，但彼此沒有協調，容易產生重複或無法語意相容的程式碼。此外，單一智慧體在面對困難任務時常出現「單檔雛形即退出」的失效模式，只產生一個原始碼骨架就提前結束，現有方法無法透過同伴互動來抑制這種行為。

**Q3：為什麼即時協作編輯協定對多智慧體編程很重要？**
A：多檔案後端專案的自然粒度就是檔案與模組，而人類團隊已經透過 CRDT 等即時協作協定解決了類似的協調問題，這為智慧體提供了可借鏡的範式。如果智慧體能即時看到彼此的編輯、宣告對檔案的佔用並交換意圖，就能在保持並行優勢的同時避免語意衝突。這種協調不僅能提升完成率，也能降低執行間的變異，讓多智慧體系統從「取樣更多」進階到「協同更好」。

**Q4：AgentRoom 的核心架構由哪些元件組成？**
A：AgentRoom 由三個緊密整合的元件構成：一個以 CRDT 合併的共享檔案系統、一個執行階段協調介面，以及透過 MCP 工具與之互動的多個並發智慧體。共享檔案系統讓任何智慧體寫入的檔案能立即被其他智慧體看見，並在字元層級自動合併並發編輯；協調介面則以 MCP 工具形式提供檔案層級宣告、廣播、狀態查詢與讀取功能，讓智慧體能明確協調誰正在修改哪個檔案。

**Q5：AgentRoom 的關鍵創新是什麼？**
A：關鍵創新在於把「顯式協調」疊加到 CRDT 共享工作空間之上，而不是單純依賴 CRDT 的自動合併來隱式協調。它透過 `room_claim` 等 MCP 工具在狀態管理層強制檔案佔用語義，使智慧體能以諮詢式鎖定的方式避免語意碰撞，這與僅靠聊天或角色預先分配的做法有本質區別。實驗也顯示，真正承擔效能負載的是協調層，而非單純的並行度或 CRDT 合併本身。

**Q6：為什麼 AgentRoom 選擇使用 MCP 工具來暴露協調原語？**
A：MCP 工具讓協調原語成為智慧體可以明確呼叫的外部動作，而不是期望智慧體從聊天文字中推斷出誰佔用了哪個檔案，這大幅降低了誤解與衝突的機率。透過 `room_claim`、`room_broadcast`、`room_state` 等工具，系統能在執行階段物件中維護原子性的檔案宣告、僅附加廣播日誌與同儕狀態，形成可驗證的協調層。這種設計也讓 AgentRoom 能與各種命令列程式設計模型對接，無需修改模型內部結構。

**Q7：實驗使用了哪些模型與任務來評估 AgentRoom？**
A：研究使用了五個前沿的命令列程式設計模型，並在 Python DevBench 與 Rust+axum 後端任務上進行跨語言檢驗，總共涵蓋四個後端編程任務。這些任務具有多檔案、模組化的特性，適合測試智慧體之間的分工與協調能力。透過跨語言與多模型的設計，作者能更穩健地比較 AgentRoom 與單獨、平行合併、ChatDev 風格等條件。

**Q8：AgentRoom 在放棄率與品質上的主要實驗結果是什麼？**
A：在 CLI 穩定模型中，兩個智慧體的 AgentRoom 比單獨智慧體放棄更少的任務，且執行間變異更小；綜合所有 12 個模型×任務分層後，Cochran-Mantel-Haenszel 估計顯示單獨智慧體的放棄機率是 AgentRoom 的 13.7 倍。在對等運算條件下，AgentRoom 對平行合併條件取得了 +0.213 的 LLM-judge 綜合品質優勢，且 Welch 檢定達到顯著水準。這些結果顯示協調能夠有效抑制單一智慧體的「單檔雛形即退出」失效模式。

**Q9：T4 六條件協調消融實驗揭示了什麼？**
A：消融實驗比較了 ChatDev、Parallel Solo、Solo、Shared noMCP、AgentRoom 與平行合併等條件，結果顯示完整的 AgentRoom 條件表現最佳，而僅有並行但無協調的平行合併與順序交接的 ChatDev 風格都低於單一智慧體基線。進一步的 bundle probe 指出 shared-only < prompt-only < AgentRoom 的品質順序，且最大的提升來自 MCP 協調層。這說明單靠共享檔案系統或提示設計並不足夠，MCP 協調工具才是效能提升的主要來源。

**Q10：AgentRoom 最適合應用在哪些實務場景？**
A：AgentRoom 特別適合需要多個模組同時開發的後端專案，例如需要同時設計 API、資料庫模型、業務邏輯與測試的 Web 後端系統。在這些場景中，智慧體可以分別佔用不同檔案、透過廣播溝通介面約定，並在 CRDT 的保護下即時合併彼此的編輯。這種協作方式也能用於需要冗餘與平行探索的任務，例如同時產生多種實作策略並在共享空間中整合最佳方案。

**Q11：若將 AgentRoom 產品化，需要考慮哪些工程與設計因素？**
A：產品化時必須確保 MCP 伺服器與 CRDT 後端能夠穩定擴展到更多智慧體與更大型的程式碼庫，因為檔案宣告與廣播日誌會隨著智慧體數量增加而複雜化。同時需要設計良好的衝突偵測與修復機制，雖然 `room_claim` 能在合作前提下避免碰撞，但若有智慧體未宣告就寫入，系統仍需能記錄並協助修復。此外，廣播訊息的資訊密度與上下文視窗管理也會影響智慧體理解彼此意圖的效率，需要適當的摘要與檢索機制。

**Q12：AgentRoom 對多智慧體編程領域可能帶來什麼影響？**
A：AgentRoom 示範了把「協調」視為一等公民的重要性，提醒研究者不應只追求更多智慧體或更多樣本，而應設計能讓智慧體即時協同的協定與工具。它也可能推動 CRDT、MCP 與多智慧體系統的進一步整合，催生類似「智慧體專用的 Git + Slack」這樣的基礎設施。長遠來看，這種顯式協調框架有助於提升自動化軟體工程的可靠性與可解釋性，讓多智慧體團隊更像可預測的工程協作單位。

**Q13：作者承認 AgentRoom 有哪些主要限制？**
A：雖然 CRDT 能保證強最終一致性並避免資料遺失，但它只保證位元組層級的合併，不保證語意相容，例如兩個智慧體在同個字元偏移處插入不相容的函式簽名仍會導致編譯失敗。此外，`room_claim` 是諮詢式鎖定而非核心層強制，若智慧體不遵守協定，衝突仍可能發生，只是會被記錄下來供後續修復。實驗規模也相對有限，僅涵蓋四個後端任務與少數模型，尚不足以推論到所有程式設計領域。

**Q14：AgentRoom 在哪些情況下可能仍然失敗？**
A：當智慧體對任務的理解嚴重分歧，或廣播訊息無法有效傳達設計意圖時，協調可能流於形式，導致檔案雖然被宣告卻仍產生語意不一致的程式碼。如果智慧體頻繁地在未宣告的情況下寫入共享檔案，碰撞率會上升，後續的除錯與修復成本也會增加。此外，對於需要深度序列推理的單一演算法問題，並發協調的優勢可能不明顯，甚至因為溝通開銷而不如單獨智慧體集中解題。

**Q15：未來可以朝哪些方向擴展 AgentRoom？**
A：未來可以探索更強大的語意層協調，例如讓智慧體在宣告檔案的同時也宣告介面契約或型別約束，以降低 CRDT 合併後語意衝突的機率。也可以研究如何動態調整智慧體數量與角色，讓系統根據任務難度與模組結構自動決定最佳分工。另一個方向是將 AgentRoom 的協調原語整合到更廣泛的開發工具鏈中，例如結合版本控制、持續整合與人機協作介面，形成真正可部署的智慧體團隊開發環境。

## 實務應用指南

### 適用場景

1. **多檔案後端功能開發**  
   當需求涉及 API、資料庫模型、業務邏輯與測試檔案等多檔案協作時，可讓兩個以上編程智慧體透過 AgentRoom 同時認領不同模組，減少單一智慧體「單檔雛形即退出」的放棄行為。

2. **跨語言移植或 SDK 開發**  
   例如將 Python 服務改寫為 Rust + axum，或同步維護多語言客戶端。不同智慧體可各自負責一種語言的檔案，透過 room_broadcast 同步介面變更，降低跨語言檢查時的遺漏。

3. **緊急修復衝刺（Bug-fix Sprint）**  
   在生產事故場景下，可同時派出多個智慧體平行探索不同修補路徑，利用 CRDT 合併與廣播日誌保留所有嘗試，再由測試與 LLM judge 篩選最佳修補。

4. **大規模重構**  
   當需要改動大量檔案（如統一錯誤處理、更新依賴介面）時，可將檔案集合拆分給不同智慧體，透過檔案層級宣告避免同時編輯同一檔案，降低衝突與編譯失敗率。

5. **快速原型與平行方案探索**  
   在設計初期讓多個智慧體同時實作同一需求的不同變體，利用共享工作空間即時觀察彼此進度，最後合併或挑選最穩定的實作。

### 實作前置條件

**資料準備**
- 可執行的程式碼倉儲與明確的任務描述（含驗收標準或 rubric）。
- 完整的測試套件與編譯／執行腳本，作為智慧體判斷進度的依據。
- 廣播日誌格式與狀態結構的規範，例如 JSON Lines 訊息與檔案佔用狀態。

**運算資源**
- 至少可同時執行兩個編程 CLI 模型的運算環境（本機或雲端 API）。
- 一台可運行 CRDT 共享檔案系統與 MCP server 的節點，建議使用 pycrdt／Yrs 作為後端。
- 足夠的 token 預算；雖然 AgentRoom 在對等運算下表現較佳，但仍需為廣播與狀態查詢預留額外呼叫成本。

**技術能力**
- 熟悉 MCP 工具設計與 prompt engineering，能將 room_claim、room_release、room_state、room_broadcast、room_read 包裝成智慧體可理解的介面。
- 具備 CRDT 基礎知識，理解強最終一致性（SEC）保證的是位元層級合併，而非語意相容性。
- 能建置 CI／測試管線，用於自動驗證合併後的程式碼是否可編譯、可通過測試。

---

### 實作步驟建議

1. **建立 CRDT 共享檔案系統**  
   選定 pycrdt 或 Yrs，部署一個所有智慧體可同時讀寫的共享工作空間，設定字元層級合併的延遲參數（例如 ∆ = 2 秒）。

2. **封裝 MCP 協調工具**  
   在共享檔案系統之上實作 MCP server，暴露五個核心工具：room_claim、room_release、room_state、room_broadcast、room_read，並在狀態管理層強制檔案佔用語意。

3. **設計協作型 prompt**  
   在智慧體的系統提示中明確告知：執行編輯前應先呼叫 room_claim，完成後釋放；需要跨檔案溝通時使用 room_broadcast；並定期查詢 room_state 了解同伴進度。

4. **加入語意保護機制**  
   除了 CRDT 合併外，額外實作括號／大括號平衡檢查，並在每次寫入後執行編譯或測試，若失敗則透過廣播觸發跨智慧體修復。

5. **執行並行運行**  
   啟動 N=2（或更多）智慧體，讓它們在相同任務上同時工作。記錄每個步驟的 claim、release、broadcast 與檔案變更，以便後續除錯。

6. **驗證與評分**  
   使用測試套件與 LLM judge（建議採用結構上不易偏誤的評分方式）對最終產出評分，並與單獨智慧體、平行合併、ChatDev 風格順序執行等基線比較。

7. **迭代調校**  
   根據碰撞率、放棄率與執行變異度調整廣播日誌視窗長度、claim 逾時時間與 prompt 中的協作策略。

### 潛在風險與注意事項

- **諮詢式鎖定的弱保證**  
  room_claim 是諮詢式（advisory）而非核心層強制鎖定，若智慧體未先宣告就直接寫入，CRDT 仍會合併位元，但可能產生語意衝突（例如同一行出現兩個不相容的函式簽名）。建議在狀態管理層記錄違規並於 prompt 中強調協定紀律。

- **CRDT 不保證語意正確**  
  強最終一致性只確保並發編輯不遺失位元，不保證程式可編譯或測試通過。每次合併後都應執行編譯與測試，作為品質閘門。

- **廣播日誌膨脹**  
  append-only broadcast log 若無視窗限制，可能讓智慧體上下文過長。建議實作滑動視窗（如最近 τ 秒內的訊息）或摘要機制。

- **死鎖與佔用不放**  
  智慧體可能因異常退出而未釋放 claim。應設計逾時自動釋放與心跳機制，避免其他智慧體無限期等待。

- **成本與變異度**  
  雖然 AgentRoom 在對等運算下優於平行合併，但協調呼叫會增加 token 與延遲。建議先在小規模任務上驗證效益，再擴大到完整專案。

- **安全性**  
  共享工作空間讓所有智慧體可讀寫彼此檔案，應部署於沙箱環境，避免智慧體意外覆蓋關鍵設定或洩漏敏感資訊。

---

### 與其他技術的整合建議

- **版本控制（Git）**  
  將 AgentRoom 的共享工作空間視為一個高頻暫存區，智慧體完成階段性任務後再提交到 Git。可在每次 release 後自動產生 commit，保留協作歷史。

- **CI／CD 管線**  
  在每次 CRDT 合併或 claim 釋放後觸發自動化測試、lint 與型別檢查，並將結果廣播回房間，讓智慧體即時知道是否引入錯誤。

- **現有多智慧體框架**  
  可將 AgentRoom 作為底層狀態管理室，上層仍使用 LangGraph、AutoGen 或自訂 orchestrator 來決定要啟動哪些智慧體與任務拆分策略。

- **評測基準**  
  與 Python DevBench、SWE-bench 或自訂 Rust + axum 測試集整合，作為判斷任務是否完成的客觀標準，減少對 LLM judge 的單一依賴。

- **IDE 與開發工具**  
  可將 MCP server 包裝成 VS Code 或 JetBrains 外掛，讓人類開發者也能即時觀察智慧體的協作過程，並在必要時介入。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於圖 2 與圖 3，理解「共享工作空間＋檔案宣告＋廣播」這三個核心概念，並把 AgentRoom 想像成「給程式寫作者的即時 Google Docs」。不必急著讀形式化模型，先從實作 MCP 工具與跑一個兩智慧體的簡單後端任務開始。

**AI 工程師**  
重點閱讀第 2.1 與第 2.2 節，掌握 CRDT 合併的限制與諮詢式鎖定的設計權衡。實作時請特別注意狀態管理層的 claim 原子性、廣播日誌視窗與自動釋放機制，這些是從論文原型走到穩定產品的關鍵。

**研究人員**  
建議深入分析 CMH 估計與對等運算比較的實驗設計，特別是「協調而非平行或 CRDT 合併承擔主要負載」這項結論。可進一步探索不同 N、不同任務難度與不同協作協定變體對資訊聯合增益的影響。

**產品經理**  
請優先關注圖 1 與放棄率數據：AgentRoom 能顯著降低智慧體放棄任務的機率，並減少執行結果的變異度。評估導入時，應把重點放在「哪些多檔案任務最常因單一智慧體放棄而卡關」，並規劃與現有 CI／Git 流程的銜接，而非一次性取代整個開發流程。
