## ⚡ TL;DR

多代理系統的執行階段狀態分散於對話、工具、記憶體等側通道，難以稽核與重現。
OpenRath 將 Session 提升為一級執行階段值，使其具備可分支、可檢視、可重播特性。
論文展示程式模型、架構與證據協定，驗證受控執行階段特性，廣泛量化比較留待後續。

## 摘要翻譯

現代代理系統往往面臨分散的執行階段狀態問題：對話轉錄、工具效果、記憶體事件、工作區配置、分支來源與重播證據皆被分散記錄，導致難以檢視或重現。OpenRath 透過類似 PyTorch 的程式設計模型來解決此問題，適用於多代理、多會話系統。此類比聚焦於中央一級執行階段抽象所扮演的角色，而非張量計算。其核心抽象為 Session（會話），即在代理與工作流之間傳遞的執行階段值。Session 具備可分支的、可檢視的、可重播的、後端感知的與可組合的特性。其記錄對話區塊、沙箱配置、譜系元資料、Token 使用量、待處理工作與工具證據，同時界定記憶體互動進入執行階段記錄的位置。由於此狀態由同一個用於程式執行的值所承載，分岔、合併與重播因此成為明確的執行階段操作，而非從外部軌跡重建的狀態。OpenRath 進一步定義 Sandbox（沙箱）、Tool（工具）、Agent（代理）、Memory（記憶體）、Workflow（工作流）與 Selector（選擇器），其中選擇器將控制流轉化為執行階段路由決策。本報告呈現程式設計模型、架構、已稽核的里程碑與證據協定。其主張僅限於受控的執行階段特性，至於廣泛的量化比較、線上提供者品質、可選後端可用性與記憶體品質，則留待後續評估。其核心論點為：Session 為代理系統提供一級執行階段值，以實現可稽核的組合。

### 核心貢獻（3～5點）
- 提出以 Session 作為一級執行階段值的程式設計模型，將分散的執行階段狀態（對話轉錄、工具效果、記憶體事件、工作區配置、分支來源、重播證據）統一承載於單一可傳遞的值中，使分岔、合併與重播成為明確的執行階段操作。
- 定義 Session 的五大特性——可分支的、可檢視的、可重播的、後端感知的、可組合的——並界定其記錄內容（對話區塊、沙箱配置、譜系元資料、Token 使用量、待處理工作、工具證據）及記憶體互動的進入點。
- 引入 Sandbox、Tool、Agent、Memory、Workflow 與 Selector 等配套抽象，其中 Selector 將控制流轉化為執行階段路由決策，支援多代理、多會話系統的模組化組合。
- 提出證據協定與已稽核的里程碑機制，確保 Session 的執行階段記錄具備可追溯性與可驗證性，實現可稽核的組合此一系統設計目標。
- 明確界定研究範圍：主張僅限於受控的執行階段特性，量化比較、線上提供者品質、可選後端可用性與記憶體品質則留待後續評估，展現嚴謹的學術誠信。

### 適合對象
從事多代理系統、大語言模型應用框架或 AI 代理執行階段基礎設施研究的工程師與研究者；關注代理系統可重現性、可稽核性與狀態管理問題的架構設計師；以及對以會話為中心的程式設計模型感興趣的學術界人士。亦適合需要理解代理系統中執行階段狀態如何從分散記錄走向統一抽象的實務開發者。

## 深度分析

#### 方法論解析

OpenRath 的方法論核心在於重新定義多代理系統（multi-agent systems）中的「執行階段狀態邊界」（state boundary），將其從分散的側通道（side channels）整合為一個一級執行階段值（first-class runtime value）。論文首先精確地指出一個被既有系統忽略的問題——**隱藏執行階段狀態問題**（hidden-runtime-state problem）：在長程代理執行中，雖然最終輸出可能正確，但產生該輸出的執行階段狀態已被碎片化地記錄在訊息列表、控制器日誌、沙箱（sandbox）元資料、追蹤系統（tracing system）的跨度（spans）、以及記憶體（memory）服務的不同位置，使得稽核（audit）、分支（branch）、合併（merge）與重播（replay）變得困難。

**PyTorch 類比的深層意涵**

論文採用 PyTorch 啟發的程式設計模型（programming model），但明確聲明這是**架構性類比**而非張量（tensor）計算的類比。其映射關係如下：

| PyTorch 概念 | OpenRath 對應 | 功能對等性 |
|---|---|---|
| Tensor（張量） | Session（會話） | 流動的核心值 |
| Module/Layer（模組/層） | Agent（代理） | 可重用的轉換 |
| nn.Sequential / 容器 | Workflow（工作流） | 組合式容器 |
| `tensor.to(device)` | `session.to(backend)` | 顯式配置（placement） |
| Parameters（參數） | Memory（記憶體） | 持久化狀態平面 |

這個類比的關鍵洞察在於：**PyTorch 的成功不僅在於自動微分，而在於它把「流動的值」與「可重用的轉換」之間的介面統一為 `forward(x) -> y` 契約**。OpenRath 將同樣的契約應用於代理系統，定義 `forward(session) -> session`，使得所有轉換都保持 Session → Session 的形狀，從而允許代理無縫地嵌套進工作流，而無需引入額外的執行階段狀態格式。

**Session 作為一級執行階段值**

Session 不僅僅是聊天歷史，而是承載以下證據的執行階段值：
1. **對話區塊**（conversation chunks）——具備角色來源（role provenance）的訊息單位
2. **沙箱配置**（sandbox placement）——工作區位置資訊
3. **譜系元資料**（lineage metadata）——分支來源（branch provenance）與衍生關係
4. **Token 使用量**（token usage）——資源消耗追蹤
5. **待處理工作**（pending work）——未完成的任務狀態
6. **工具證據**（tool evidence）——工具執行的證據記錄
7. **記憶體邊界記錄**——定義記憶體擷取（memory recall）與記憶體提交（memory commit）事件進入執行階段記錄的位置

Session 的五個核心特性——**可分支的**（branchable）、**可檢視的**（inspectable）、**可重播的**（replayable）、**後端感知的**（backend-aware）、**可組合的**（composable）——共同支撐了「可稽核的組合」（auditable composition）這個設計目標。

**三種執行階段記錄的讀者區分**

論文提出一個重要的區分框架，說明為何 Session 不能被圖執行階段（graph runtime）的節點狀態或追蹤系統的跨度所取代：

| 記錄類型 | 寫給誰 | 主要內容 |
|---|---|---|
| 圖檢查點（Graph checkpoint） | 排程器（scheduler） | 控制在流程中的位置 |
| 追蹤跨度（Trace span） | 觀察者（observer） | 執行期間被觀察到的事件 |
| Session（OpenRath） | 代理程式本身 | 代理分岔、合併、交接、重播的即時值 |

這個區分揭示了 Session 的獨特價值：**它是寫給代理程式本身的值**，因此分岔-合併（fork-merge）、交接（handoff）與重播（replay）成為一級操作，而非從外部日誌重建的狀態。

**物件詞彙與後端感知邊界**

OpenRath 定義了七個核心物件：Session、Sandbox、Tool、Agent、Memory、Workflow、Selector。其中 **Selector** 是特別值得注意的設計——它將控制流（control flow）轉化為**執行階段路由決策**（runtime-routed decisions），這意味著路由邏輯本身也是 Session 的一部分，而非外部控制器決定。

**後端感知邊界**（backend-aware boundaries）是另一個關鍵設計：OpenRath 明確分離執行階段狀態與執行工具的後端、持久化記憶體的後端。這使得本地執行、可選的 OpenSandbox 配置、MCP 風格的工具、以及記憶體服務都能在同一個以 Session 為中心的模型中參與，因為它們的證據封包（evidence packets）會被驗證。

**證據協定**（evidence protocol）作為稽核基礎

雖然具體細節在提供的文本中未完全展開，但論文提到「證據協定」是 Session 可稽核性的基礎設施。這暗示 OpenRath 不僅記錄「發生了什麼」，還定義了「如何驗證記錄是否完整、未被竄改」的協定層。

#### 與現有研究的比較

**生態系統定位的精確性**

OpenRath 採取了一種「互補而非取代」的定位策略，這在論文中被反覆強調。它明確聲明：「OpenRath 既不是圖執行階段、追蹤系統、MCP 伺服器、沙箱提供者或基準測試框架的通用替代品，也不是它們中任何一個的薄包裝層。」這種定位顯示作者對生態系統的成熟理解——避免重複造輪子，而是填補一個被忽視的抽象層。

**與主要競爭系統的對比**

| 系統 | 主要抽象 | 與 OpenRath 的關係 |
|---|---|---|
| **AutoGen** [3] | 對話驅動的多代理框架 | OpenRath 可作為其執行階段狀態層 |
| **LangGraph** [4] | 圖執行階段 | OpenRath 補充其節點狀態的不足 |
| **OpenAI Agents SDK** [5] | 代理編排 | OpenRath 提供更結構化的狀態管理 |
| **MCP** [6, 7] | 工具/資料協定 | OpenRath 消費 MCP 工具並記錄其證據 |

**相對於現有工作的改進**

1. **狀態統一性**：現有系統通常將執行階段狀態分散在多個層（訊息列表、控制器日誌、沙箱元資料），OpenRath 將其統一為 Session 物件
2. **分岔-合併作為一級操作**：在現有系統中，分岔通常需要重建狀態；在 OpenRath 中，分岔是 Session 的原生操作
3. **後端感知**：現有系統通常將後端視為透明細節；OpenRath 將後端配置提升為 Session 的一級屬性
4. **證據協定**：現有系統通常缺乏結構化的證據記錄；OpenRath 將證據作為 Session 的核心組成部分

**相對於現有工作的限制**

1. **採用門檻**：開發者需要學習 Session 物件模型，而非僅使用訊息列表
2. **生態系統成熟度**：作為新提出的系統，缺乏豐富的工具、整合與社群支援
3. **實證基礎**：如前所述，缺乏廣泛的量化比較
4. **範圍侷限**：刻意避開了圖執行階段、追蹤系統等成熟領域，限制了其獨立使用的場景

**PyTorch 類比的雙刃劍**

這個類比既是優勢也是潛在的弱點。優勢在於它借用了一個已被廣泛理解的框架來解釋新概念；弱點在於它可能誤導讀者期待類似的自動微分或 GPU 加速能力，而這些並非 OpenRath 的範疇。論文對此有明確的免責聲明，但讀者在解讀時仍需謹慎。

#### 未來研究方向

**論文自身指出的後續方向**

論文摘要明確列出了四個留待後續評估的方向：
1. **廣泛的量化比較**——與 AutoGen、LangGraph、OpenAI Agents SDK 等系統的端到端對比
2. **線上提供者品質**——使用真實 LLM 提供者（如 GPT-4、Claude、Gemini）的評估
3. **可選後端可用性**——OpenSandbox、MCP 等可選後端的實際整合效果
4. **記憶體品質**——記憶體擷取與提交的準確性、效率、一致性評估

**論文未明確提及但值得探索的方向**

1. **形式化語義**——為 Session 的分岔-合併操作提供形式化語義（例如基於進程代數或類型理論），使得正確性可被機械化驗證
2. **分散式 Session**——當代理系統跨越多台機器時，Session 如何保持一致性？這涉及分散式狀態同步、衝突解決等問題
3. **Session 的隱私與安全**——Session 包含豐富的執行階段證據，但也可能包含敏感資訊。如何在保護隱私的同時維持可稽核性？
4. **與形式化驗證的整合**——Session 的證據協定是否可以與形式化驗證工具（如 Coq、Lean、TLA+）整合，使得代理行為可被形式化證明？
5. **Session 的壓縮策略**——長程代理執行會產生巨大的 Session。如何在保留關鍵證據的同時壓縮 Session？這涉及證據保留策略與壓縮演算法的設計
6. **跨 Session 的學習**——多個 Session 之間是否可以共享學習成果？這涉及元學習（meta-learning）與遷移學習（transfer learning）在代理系統中的應用
7. **人機協作介面**——Session 的可檢視性如何轉化為有效的人機協作介面？稽核者如何利用 Session 來理解、介入、甚至修正代理行為？
8. **Session 的經濟學**——在多代理市場中，Session 是否可以成為計費、結算的基礎單位？這涉及代理經濟學與資源分配的設計

**對程式設計模型本身的擴展**

1. **更豐富的 Selector 語義**——目前的 Selector 將控制流轉化為執行階段路由決策，但更複雜的路由策略（如基於強化學習的路由）如何整合？
2. **動態 Workflow**——Workflow 目前被描述為組合式容器，但能否支援動態重組？例如根據 Session 狀態自動調整工作流結構
3. **跨後端的統一介面**——目前分離了執行後端與記憶體後端，但更廣泛的後端（如不同的 LLM 提供者、不同的向量資料庫）如何統一介面？

**對學術界的影響**

OpenRath 的提出可能會引發以下學術討論：
1. **執行階段狀態的本質**——什麼是代理系統的「正確」執行階段狀態？Session 是否是最佳答案？
2. **抽象層的必要性**——是否真的需要一個獨立的執行階段狀態層？還是現有抽象已足夠？
3. **可稽核性 vs. 效率**——豐富的證據記錄會帶來效能開銷，如何在可稽核性與效率間取得平衡？

這些問題的探討將有助於推動代理系統從「能跑」走向「可被信任地跑」，這也是 OpenRath 核心主張的最終價值所在。

## 論文問答

**Q1：OpenRath 所定義的「隱藏執行階段狀態問題」（hidden-runtime-state problem）具體指的是什麼？**
A：此問題指的是現代代理系統中，執行階段狀態被分散記錄於多個側通道（side channels）之中，包括對話記錄、工具效果、記憶體事件、工作區配置、分支來源與重播證據等。這些資訊雖然各自存在，卻難以被統一檢視或重現，使得最終輸出雖然正確，卻無法追溯其生成過程。OpenRath 將此現象識別為一個結構性問題，而非單純的日誌缺失，並主張應從執行階段狀態的邊界（state boundary）著手重新設計。

**Q2：為什麼現有的代理系統無法有效回答稽核（audit）相關的問題？**
A：現有系統通常以訊息列表（message list）作為對話表面的主要記錄形式，但這類記錄並未暴露角色來源（role provenance）、被放棄的分支、工具配置、工作區效果、記憶體擷取或提交事件，以及被壓縮（compression）所丟棄的證據。當模型、提供者、工作區或提示詞改變後，缺乏譜系（lineage）、工具證據、沙箱元資料與使用量記錄的最終答案便難以被稽核。此外，圖形執行階段的節點狀態與追蹤系統的跨度（spans）雖然記錄了控制流位置或觀察事件，但這些記錄是為排程器或觀察者所設計，並非代理程式本身用於分岔、合併、交接與重播的程式值。

**Q3：為了解決這個問題如此重要？它對代理系統的長遠發展有何意義？**
A：隨著代理應用日益複雜並趨向多代理、多會話的分散式運作，執行階段狀態的碎片化將成為可擴展性的瓶頸。若無法在程式執行的同時保留可檢視、可分支、可重播的狀態，則系統在規模化時將難以維持可稽核性（auditability）。OpenRath 的核心論點是：將執行階段狀態置於程式自然流動的位置，比將其放在側通道更利於多代理系統的可檢視性，這對建立可信賴、可重現的代理基礎設施至關重要。

**Q4：OpenRath 的核心方法是什麼？什麼是 Session 抽象？**
A：OpenRath 的核心方法是將 Session 提升為代理系統中的一級執行階段值（first-class runtime value），這是一個可在代理與工作流之間傳遞的執行階段物件。Session 具備可分支（branchable）、可檢視（inspectable）、可重播（replayable）、後端感知（backend-aware）與可組合（composable）五大特性，並記錄對話區塊、沙箱配置、譜系元資料、Token 使用量、待處理工作、工具證據以及記憶體互動的進入點。由於此狀態由執行階段中實際流動的值所承載，分岔、合併與重播便成為明確的執行階段操作，而非從外部追蹤重建的狀態。

**Q5：OpenRath 的關鍵創新為何？為何選擇 PyTorch 類比的程式設計模型？**
A：關鍵創新在於採用類似 PyTorch 的程式設計模型，但僅借用其架構介面而非張量計算的數學語意。在 PyTorch 中，中央值流經可重用模組，模組透過統一的前向映射（forward mapping）對外暴露介面，配置透過類似 tensor.to(device) 的操作明確化，持久化的模組狀態則由參數（parameters）表示。OpenRath 將此模式適配至代理執行階段：Session 扮演流動值的角色、Agent 類似層的可重用轉換、Workflow 是組合式容器，皆遵循 forward(session) → session 的契約，而配置則表達為 session.to(backend)，記憶體則被視為代理綁定的持久化狀態平面，而非隱藏的提示文字。

**Q6：OpenRath 的物件詞彙（object vocabulary）包含哪些核心元件？它們的設計選擇考量為何？**
A：OpenRath 定義了七個核心元件：Session、Sandbox、Tool、Agent、Memory、Workflow 與 Selector，每個元件皆維持 Session → Session 的形狀以支援組合。其中 Selector 將控制流（control flow）轉化為執行階段路由決策（runtime-routed decisions），這是一項重要的設計選擇，使控制流本身成為可被執行階段管理的資源。另一關鍵設計是後端感知的邊界劃分：執行階段狀態與執行工具的後端、持久化記憶體的後端分離，使本地執行、OpenSandbox 配置、MCP 風格的工具與記憶體服務能在同一個以會話為中心的模型中參與，這種分離讓證據封包（evidence packets）能被驗證。

**Q7：OpenRath 採用何種基準或評估方式來驗證其主張？**
A：根據摘要所述，OpenRath 的主張僅限於受控的執行階段特性（controlled runtime properties），並未進行廣泛的量化比較。論文中呈現的是程式設計模型、架構、已稽核的里程碑（audited milestones）以及證據協定（evidence protocol），作為支撐其設計論點的證據。具體的量化基準測試、線上提供者品質、選用後端的可用性以及記憶體品質等面向，則被明確留給後續的評估工作。

**Q8：OpenRath 提出的關鍵結果或核心主張為何？**
A：OpenRath 的核心主張是：代理系統需要一個一級的執行階段狀態，而 Session 是該狀態的候選實作。論文中以表格形式對比三種執行階段記錄——圖形檢查點（為排程器而寫）、追蹤跨度（為觀察者而寫）與 Session（為代理程式本身而寫），強調 Session 是代理程式用於分岔、合併、交接與重播的即時值。論文的四項技術貢獻包括：以會話為中心的執行階段資料流、類似 PyTorch 的物件詞彙、工具與記憶體的後端感知邊界，以及證據協定，這些共同支撐了「可稽核的組合」（auditable composition）此一設計目標。

**Q9：論文中是否有消融研究（ablation studies）或比較分析？**
A：根據摘要的明確說明，廣泛的量化比較被刻意留給後續評估，因此本報告中並未呈現傳統意義上的消融研究或基準比較。論文的論證方式偏向架構性與概念性，透過展示三種執行階段記錄的差異、Session 的特性清單以及元件間的互動關係來支持其設計論點。這種做法反映了該工作作為「設計報告」而非「實證研究」的定位，其價值在於提出新的執行階段抽象，而非立即證明其在所有情境下優於既有方案。

**Q10：OpenRath 最適合應用於哪些實際場景？**
A：OpenRath 特別適合需要長時程、多分支、可稽核的代理執行場景，例如需要測試多種解法並比較結果的複雜規劃任務、需要追蹤工具修改了哪些檔案以及哪些記憶體項目被擷取或提交的程式開發代理，以及需要在壓縮後仍保留證據鏈的長對話系統。在多代理協作中，當工作需要在角色、工具、記憶體儲存、沙箱、分支與恢復執行之間分散時，Session 作為統一的執行階段值能顯著降低狀態管理的複雜度。

**Q11：從產品化的角度，OpenRath 解決了哪些重要的工程考量？**
A：從產品角度，OpenRath 解決了狀態可檢視性、可重現性與可稽核性三大工程痛點，使開發者能在最終答案之外，追溯到分支來源、工具證據、沙箱元資料與 Token 使用量等細節。其後端感知的設計讓本地執行、OpenSandbox、MCP 工具與記憶體服務能在同一模型下整合，降低了多供應商環境下的整合成本。此外，Selector 將控制流轉化為執行階段路由決策，使產品能靈活地根據執行階段狀態動態決定下一步行為，這對需要動態決策的應用至關重要。

**Q12：OpenRath 對代理系統領域的更廣泛影響為何？**
A：OpenRath 對領域的影響在於重新定位了執行階段狀態應放置的位置——從側通道移至程式自然流動的值之中，這可能影響未來代理框架的設計方向。它與 AutoGen、LangGraph、OpenAI Agents SDK 及 MCP 等系統形成互補而非競爭的關係，定位於「連接性」的角色：圖形執行階段負責排程、追蹤系統負責觀察跨度、MCP 負責暴露工具、沙箱負責執行命令，而 OpenRath 則讓這些效果成為一個可分支、可檢視、可重播的統一狀態物件。這種分層定位有助於避免各層各自發明不相容的代理狀態表示法。

**Q13：OpenRath 在論文中明確承認的限制為何？**
A：論文明確承認其主張僅限於受控的執行階段特性，並未涵蓋廣泛的量化比較、線上提供者的品質、選用後端的可用性以及記憶體品質等面向。這意味著 Session 抽象的實用性、效能與品質尚未在真實的大規模部署中得到驗證。此外，論文的論證主要基於架構性推理而非實證數據，因此讀者在評估其實際效益時需考量這些尚未被驗證的面向。

**Q14：OpenRath 可能面臨哪些失敗案例或邊界情境？**
A：在極高頻率的狀態更新場景下，Session 作為承載所有執行階段資訊的一級值，可能面臨序列化與傳遞的效能瓶頸。當多個代理同時對同一 Session 進行分岔與合併時，衝突解決策略的設計可能成為複雜的邊界情境。此外，若後端服務（如記憶體或沙箱）本身不穩定或回傳不一致的證據，Session 的證據協定能否正確處理這些異常情況，仍有待驗證。在需要極低延遲的即時互動場景中，攜帶完整譜系與證據的 Session 可能增加不可忽略的開銷。

**Q15：OpenRath 論文中暗示的未來研究方向為何？**
A：論文明確將廣泛的量化比較、線上提供者品質評估、選用後端的可用性驗證以及記憶體品質測量列為後續工作，這些將是驗證 Session 抽象實用性的關鍵步驟。此外，如何將 Session 與現有的圖形執行階段、追蹤系統、MCP 伺服器、沙箱提供者及基準測試框架進行更深入的整合，是值得探索的生態系統方向。記憶體作為代理綁定的持久化狀態平面，其品質、擷取效率與一致性也是未來研究的重要議題，這些方向的進展將決定 OpenRath 能否從設計提案走向廣泛採用的基礎設施。

## 實務應用指南

### 適用場景

**1. 長時程研究型代理（Long-Horizon Research Agent）**
當代理需要規劃、嘗試多條推理路徑、呼叫工具並最終收斂到答案時，OpenRath 的可分支會話（branchable session）允許系統同時維護多條探索分支，每條分支保留獨立的對話區塊、工具證據與譜系元資料。最終可由稽核者檢視「哪條分支產生了最終結果」，而非僅看到一段被壓縮過的訊息歷史。

**2. 程式碼生成與沙箱執行代理（Coding Agent with Sandbox）**
代理在沙箱中編輯檔案、執行測試、迭代修正時，OpenRath 的後端感知（backend-aware）邊界可將工作區配置（workspace placement）與工具證據（tool evidence）寫入同一個會話物件。當模型、提供者或提示詞變更時，仍可從會話重播（replay）整段執行，驗證當時的程式碼狀態與工具輸出。

**3. 多代理客戶服務與責任轉移（Multi-Agent Customer Support with Handoff）**
在需要將案件從分流代理轉交給專業代理、再升級給人類審核的場景中，會話物件可作為轉交的「案件卷宗」，攜帶角色來源（role provenance）、待處理工作（pending work）與記憶體事件（memory events）。Selector 將控制流轉為執行階段路由決策（runtime-routed decisions），使升級路徑本身成為可稽核的執行階段記錄。

**4. 法遵與稽核工作流（Compliance & Audit Workflow）**
在金融、醫療或法律場域，每一個代理決策都需附帶證據。OpenRath 的證據協定（evidence protocol）將工具呼叫、記憶體擷取（memory recall）與記憶體提交（memory commit）統一記錄於會話，使稽核員可重建「為什麼代理給出這個答案」，而不需從分散的側通道（side channels）拼湊。

**5. 生產環境代理的可重播除錯（Replayable Production Debugging）**
當線上代理出現異常行為時，工程師可從會話物件重播整段執行，包含上下文壓縮（context compression）前後的差異、已捨棄的證據、以及分支來源（branch provenance）。這比傳統的日誌系統更能支援根因分析，因為狀態邊界（state boundary）與程式執行流一致。

### 實作前置條件

**資料前置條件**
- 對話紀錄：需具備結構化的訊息流（角色、內容、時間戳），以便會話物件能以對話區塊（conversation chunks）形式記錄。
- 工具執行軌跡：每次工具呼叫需附帶輸入、輸出、執行環境資訊，否則工具證據無法寫入會話。
- 記憶體儲存：若使用記憶體抽象（Memory），需準備可持久化的鍵值或向量儲存後端。
- 譜系資訊：每個會話分支需有明確的父會話識別碼與建立原因，否則譜系元資料將不完整。

**計算前置條件**
- Python 3.10 以上執行環境（async/await 支援）。
- 可選的沙箱後端：本地子行程、容器化環境，或整合 OpenSandbox 等外部沙箱提供者。
- 可選的線上提供者（live-provider）：用於實際模型呼叫；本框架的受控執行階段屬性不依賴特定提供者。
- 標準的序列化儲存（如 JSON、Pickle、SQLite）以支援會話持久化與重播。

**技能前置條件**
- 熟悉 Python 物件導向設計與非同步程式設計模式。
- 理解代理設計模式（ReAct、Plan-and-Execute、Multi-Agent Handoff）。
- 具備基本的分散式系統概念：分支、合併、版本控制語意。
- 對 PyTorch 的 `Module` / `forward()` / `to(device)` 介面有概念性理解（僅作類比，非必要）。

### 實作步驟建議

**步驟一：定義會話物件的最小欄位集**
從一個最小可行會話開始，包含：對話區塊列表、沙箱配置、譜系父識別碼、Token 使用量、待處理工作佇列、工具證據列表、記憶體邊界記錄。避免一開始就設計過於複雜的巢狀結構，先驗證 `forward(session) -> session` 的契約是否能在最小場景中運作。

**步驟二：實作 Agent 與 Workflow 的統一介面**
讓所有 Agent 與 Workflow 遵循 `forward(session) -> session` 契約。這是 PyTorch 類比的核心：如同 `nn.Module` 統一了層的介面，OpenRath 統一了代理的介面。Workflow 作為組合式容器（workflow container），內部可巢狀其他 Agent 或 Workflow，但對外仍暴露相同的會話轉會話介面。

**步驟三：引入 Selector 將控制流路由化**
將傳統的 `if/else` 決策改寫為 Selector，使控制流本身成為執行階段路由決策（runtime-routed decisions）。這樣做的價值在於：路由依據（例如「該升級給人類嗎？」）會被記錄在會話中，事後可稽核「為什麼走這條路徑」。

**步驟四：分離後端與執行階段狀態**
明確區分「執行階段狀態」（會話物件本身）與「執行後端」（沙箱、模型提供者、工具伺服器）。使用 `session.to(backend)` 語意表達配置切換，但會話內容不應被後端細節污染。這樣本地執行、OpenSandbox、MCP 風格工具都能在同一會話模型下運作。

**步驟五：設計證據協定**
為工具呼叫、記憶體擷取、記憶體提交定義統一的證據封包格式。每筆證據需包含：時間戳、來源代理、輸入雜湊、輸出雜湊、所屬會話分支。這是稽核性的基礎——沒有統一的證據格式，稽核就退回到從側通道拼湊。

**步驟六：實作分岔、合併、重播操作**
在會話物件上提供一級的 `fork()`、`merge()`、`replay()` 操作。這些操作不應從外部控制器日誌重建，而應直接作用於會話物件本身。實作時需注意：分岔是廉價的（複製引用），合併需明確的衝突解決策略，重播需能區分「確定性重播」與「非確定性重播」。

**步驟七：建立已稽核的里程碑（Audited Milestones）**
為每個開發階段設定可驗證的里程碑，例如：「會話物件可序列化並跨程序還原」、「分岔後兩個分支的譜系可追溯」、「重播後 Token 使用量與原始執行一致」。每個里程碑都需有對應的稽核測試，而非僅有功能測試。

**步驟八：規劃受控執行階段屬性的評估邊界**
明確區分本系統聲稱的「受控執行階段屬性」（分支、合併、重播、檢視的正確性）與「未聲稱的屬性」（模型品質、記憶體品質、線上提供者表現）。前者可在隔離環境中驗證，後者需留待後續評估。

### 潛在風險與注意事項

**風險一：會話物件膨脹導致記憶體耗盡**
長時程代理的會話可能累積大量對話區塊、工具證據與譜系記錄。緩解方式：設計明確的壓縮策略，但壓縮本身必須是可稽核的——需記錄哪些證據被捨棄，而非靜默丟棄。

**風險二：分岔與合併的語意模糊**
不同分支可能對同一狀態做出衝突的修改。緩解方式：在合併前明確定義衝突解決策略（例如「最後寫入者勝出」、「人工仲裁」），並將衝突本身記錄為會話的一部分。

**風險三：重播的非確定性陷阱**
若代理呼叫外部 API 或讀取即時狀態，重播結果可能與原始執行不同。緩解方式：將非確定性來源明確標記，並在重播時允許「凍結外部輸入」模式，或在證據中記錄所有外部依賴。

**風險四：後端切換破壞會話完整性**
若 `session.to(backend)` 切換後，某些工具證據因後端差異而無法重現。緩解方式：證據封包應包含後端識別碼，重播時若後端不一致應明確警告，而非靜默產生不同結果。

**風險五：將 Session 誤用為通用資料儲存**
Session 是執行階段值（first-class runtime value），不是資料庫。緩解方式：明確區分「會話內的暫存狀態」與「持久化儲存」，避免將所有業務資料塞入會話導致序列化成本失控。

**風險六：Selector 路由邏輯過於隱晦**
若 Selector 的決策依據散落在程式碼各處，稽核性將受損。緩解方式：Selector 的輸入（會話狀態）與輸出（路由決策）都應寫入會話，使路由本身成為可追溯的執行階段記錄。

### 與其他技術的整合建議

**與 LangGraph 的整合**
LangGraph 提供圖執行階段（graph runtime）與檢查點（checkpoint）機制，負責「排程器」角色。OpenRath 的 Session 可作為圖節點之間傳遞的值，使 LangGraph 排程的執行具備分支、合併、重播能力。整合點：將 LangGraph 的狀態物件包裝為 OpenRath Session，或在圖節點內部使用 Session 作為局部執行階段值。

**與 AutoGen 的整合**
AutoGen 強調多代理對話模式。OpenRath 可作為其底層的執行階段狀態層，使 AutoGen 的群組聊天、代理轉交具備完整的譜系與工具證據記錄。整合點：將 AutoGen 的群組聊天管理器輸出對接至 OpenRath 的會話記錄。

**與 OpenAI Agents SDK 的整合**
OpenAI Agents SDK 提供追蹤（tracing）與工具呼叫抽象。OpenRath 的 Session 可作為追蹤 span 的承載值，使追蹤資料不僅是觀察者記錄，而是代理程式本身可操作的執行階段物件。整合點：在 SDK 的 hook 中將 span 資料寫入 Session。

**與 MCP（Model Context Protocol）的整合**
MCP 標準化工具與資料來源。OpenRath 的 Tool 抽象可作為 MCP 客戶端的包裝，使工具呼叫的證據（輸入、輸出、延遲、錯誤）自動寫入會話。整合點：將 MCP 工具呼叫包裝為 OpenRath Tool，並在呼叫前後更新會話的工具證據欄位。

**與沙箱提供者的整合**
無論是本地子行程、Docker 容器，或 OpenSandbox 等外部沙箱，都可透過 `session.to(backend)` 語意接入。整合點：定義統一的沙箱介面，使會話的工作區配置（workspace placement）與沙箱後端解耦。

**與持久化儲存的整合**
Session 需可序列化以支援跨程序、跨機器的恢復執行（resumed execution）。整合點：使用標準序列化格式（JSON、Pickle、Protocol Buffers）並搭配版本控制欄位，使舊版會話可在新版系統中降級讀取。

**與評估框架的整合**
本框架的聲明限於受控執行階段屬性，廣泛的定量比較、線上提供者品質、記憶體品質留待後續評估。整合點：將 Session 作為評估的輸入物件，使評估框架能重播特定會話並比較不同後端、不同提示詞下的執行差異。

### 給不同背景讀者的閱讀建議

**給初學者**
若你剛接觸代理系統，建議先閱讀第 1.1 節（問題框架）與第 1.2 節（中心主張），理解「為什麼執行階段狀態會碎片化」這個問題。接著跳過技術細節，直接看表 1（三種執行階段記錄、三種讀者），這個表格能幫助你直觀理解 Session 與圖檢查點、追蹤 span 的差異。PyTorch 類比的部分若不熟悉深度學習框架，可先略過，重點放在「為什麼需要一個一級執行階段值」這個概念。

**給 AI 工程師**
重點閱讀第 1.2 節的 PyTorch 類比與第 1.3 節的生態定位。理解 Session 如何對應到 `nn.Module` 的 `forward()` 介面，以及 `session.to(backend)` 如何對應到 `tensor.to(device)`。接著閱讀程式設計模型章節，掌握 Agent、Workflow、Tool、Memory、Selector 的職責劃分。實作時特別注意 `forward(session) -> session` 契約的強制性——這是組合性的基礎。最後檢視證據協定章節，確保你的工具呼叫與記憶體操作都能產生可稽核的證據封包。

**給研究者**
本論文的中心命題是「多代理系統需要一級執行階段狀態」，這是一個架構性主張而非經驗性主張。建議從兩個角度評估：(1) 將 Session 與現有的執行階段抽象（如圖狀態、追蹤 span）進行形式化比較，檢視其表達能力邊界；(2) 設計實驗驗證「當執行階段狀態與程式執行流一致時，稽核成本是否顯著降低」。注意論文的自我邊界：作者明確聲明廣泛的定量比較、線上提供者品質、記憶體品質不在本次範圍，這是誠實的研究聲明，後續工作可在此基礎上擴展。

**給產品經理**
本框架解決的核心問題是「代理決策的可解釋性與可稽核性」，這在企業級代理部署中至關重要。建議關注三個面向：(1) 適用場景——長時程代理、需要責任轉移的多代理系統、法遵工作流；(2) 整合成本——Session 可與現有圖執行階段、追蹤系統、MCP 工具共存，無需替換現有架構；(3) 評估邊界——本框架保證的是「執行階段狀態的可追溯性」，而非「代理決策的正確性」，後者仍需獨立的評估體系。在產品規劃中，應將「稽核性」作為與「品質」並列的獨立維度，而非附屬於品質之下。
