# Repo0：設計驅動的從零到完整程式碼生成（Design-Driven Zero-to-All Code Generation）

## ⚡ TL;DR

現有方法多假設程式庫架構已預先給定，難以從自然語言需求直接生成完整軟體專案。
本文提出 Repo0，以雙向有向無環圖維護架構狀態，依模組性指標演化元件邊界，收斂後再生成程式碼。
Repo0 在六個真實專案的功能覆蓋率與通過率均最佳，較最強基線最高提升 20 與 29 個百分點。

## 摘要翻譯

大型語言模型智慧體（Large Language Model Agents）在程式碼生成（Code Generation）方面已取得顯著進展，然而多數現有系統皆假設程式庫架構（Repository Architecture）已預先定義。此假設在從零到完整程式碼生成（Zero-to-All Code Generation）中並不成立：智慧體必須直接依據自然語言需求（Natural-Language Requirements）建構完整軟體專案（Software Project），並在整個開發過程中維持模組化的程式庫架構。我們提出 Repo0，一個用於從零到完整程式碼生成的持續性結構演化框架（Continuous Structural Evolution Framework）。Repo0 維護一個明確的架構狀態（Architectural State），並以雙向有向無環圖（Dual-Directed-Acyclic-Graph, Dual-DAG）加以具現化，包含需求層級有向無環圖（Requirement-level DAG）、元件層級有向無環圖（Component-level DAG），以及兩者之間的對齊關係（Alignment Relation）。從自然語言需求出發，它透過模組性指標（Modularity Metrics）所引導的結構性動作（Structural Actions），迭代演化元件邊界（Component Boundaries），直至結構收斂（Structural Convergence）；隨後由收斂後的架構引導測試驅動開發（Test-Driven Development）的程式碼生成。我們使用 GPT-5 mini 與 DeepSeek V3.2，在 RepoCraft 的六個真實世界程式庫上評估 Repo0。Repo0 在所有設定下均取得最高的功能覆蓋率（Functionality Coverage）與通過率（Pass Rate）。與最強的程式庫規劃基線（Repository-Planning Baseline）RPG 相比，Repo0 的功能覆蓋率提升最高達 20.08 個百分點，通過率提升最高達 29.74 個百分點。消融研究（Ablation）與結構演化分析（Structural-Evolution Analyses）進一步證實了 Dual-DAG 架構狀態、模組性引導的結構演化，以及明確結構收斂的重要性。

### 核心貢獻（3～5點）
- 提出 Repo0 框架，以持續性結構演化（Continuous Structural Evolution）取代傳統的靜態程式庫架構規劃（Static Repository-Architecture Planning），解決從零到完整程式碼生成中無法預設架構的挑戰。
- 設計 Dual-DAG 架構狀態，透過需求層級與元件層級有向無環圖及其對齊關係（Alignment Relation），顯式追蹤並演化程式庫架構。
- 以模組性指標（Modularity Metrics；如內聚性 Cohesion、耦合性 Coupling）引導結構性動作（Structural Actions；如拆分 Split、合併 Merge、修訂 Revise），迭代優化元件邊界（Component Boundaries）直至結構收斂。
- 在 RepoCraft 真實世界資料集上驗證，使用 GPT-5 mini 與 DeepSeek V3.2 均取得最佳功能覆蓋率與通過率，顯著優於 RPG 基線。
- 透過消融研究與結構演化分析，證實 Dual-DAG 架構狀態、模組性引導演化與明確結構收斂對生成品質的關鍵貢獻。

### 適合對象
軟體工程智慧體（Software Engineering Agents）與程式庫生成（Repository Generation）領域的研究者、從事大型語言模型（Large Language Models）程式碼生成應用的開發者，以及關注自動化軟體設計與模組化架構演化的學術與產業界人士。

## 深度分析

#### 方法論解析

Repo0 的核心貢獻在於將 zero-to-all code generation（從零到完整程式碼生成）重新定義為一個 **continuous structural evolution（持續性結構演化）** 問題，而非傳統的一次性規劃後執行。其方法論可從以下幾個層次理解：

##### 1. 雙層架構狀態：Dual-DAG（雙向有向無環圖）

Repo0 維護一個明確的 **architectural state（架構狀態）**，具體化為 Dual-DAG，包含：

- **Requirement-level DAG（需求層級有向無環圖）**：捕捉自然語言需求之間的功能依賴與層次分解關係，例如「使用者註冊」依賴「資料庫連線」。
- **Component-level DAG（元件層級有向無環圖）**：對應到實作層面的模組、套件、檔案及其相依關係。
- **Alignment relation（對齊關係）**：連結需求節點與實作元件節點，確保「設計」與「實作」之間的可追溯性。

這種分離至關重要，因為它讓系統能夠獨立診斷「需求是否完整」與「實作結構是否良好」，並透過對齊關係發現兩者之間的落差。

##### 2. 模組性引導的結構動作

Repo0 不採用固定的初始藍圖，而是讓智慧體在開發過程中反覆執行 **structural actions（結構性動作）**，包括：

- **Split（拆分）**：當某個元件出現 **low cohesion（低內聚）** 時，將其拆成多個職責更單一的元件。
- **Merge（合併）**：當多個元件之間出現 **high coupling（高耦合）** 或功能重疊時，將其合併。
- **Revise（修訂）**：當測試失敗或需求覆蓋不足時，調整元件邊界或相依結構。
- **Add / Delete（新增／刪除）**：根據需求覆蓋率與冗餘分析，補充遺漏的需求結構或移除不必要的元件。

這些動作由 **modularity metrics（模組性指標）** 引導，主要包含：

- **Cohesion（內聚性）**：越高越好，衡量同一元件內部功能相關程度。
- **Coupling（耦合性）**：越低越好，衡量元件之間的相依緊密程度。
- **Information hiding（資訊隱藏）**：評估元件內部實作細節是否過度暴露。

透過這些指標，Repo0 將軟體工程原則轉化為可量化的最佳化目標，使 LLM agent（大型語言模型智慧體）的決策具備明確依據。

##### 3. 持續回饋的演化迴圈

Repo0 的運作流程形成一個連續決策迴圈：

1. 從自然語言需求出發，建立初始的 Dual-DAG。
2. 智慧體觀察目前架構狀態，進行推理並選擇結構性動作。
3. 執行動作後，透過 **validation / execution feedback（驗證／執行回饋）**（如測試結果、靜態分析、覆蓋率檢查）評估結構品質。
4. 反覆調整直到達成 **structural convergence（結構收斂）**，即架構狀態不再顯著變動。
5. 收斂後的 Dual-DAG 再引導 **test-driven development（測試驅動開發，TDD）** 式的程式碼生成。

這個流程的關鍵在於「先收斂架構、再生成程式碼」，避免傳統方法在架構尚未穩定前就大量產出程式碼，導致後期重構成本高昂。

##### 4. 設計驅動的程式碼生成

與一般 end-to-end 程式碼生成不同，Repo0 強調 **design-driven generation（設計驅動生成）**。收斂後的 component-level DAG 會被轉換為具體的檔案結構、介面定義與相依規範，再交由 LLM 進行逐檔案實作。這種方式讓生成的程式碼從一開始就具備清晰的模組邊界，降低跨檔案協調失敗的風險。

#### 實驗數據解讀

Repo0 在 **RepoCraft** 資料集的六個真實世界程式庫上進行評估，並使用 **GPT-5 mini** 與 **DeepSeek V3.2** 兩種 backbone model（骨幹模型）進行對照。評估指標主要為：

- **Functionality Coverage（功能覆蓋率）**：衡量生成專案實現了多少比例的需求功能。
- **Pass Rate（通過率）**：衡量測試案例通過的比例。

##### 1. 整體表現

Repo0 在所有設定下均達到最高的 Functionality Coverage 與 Pass Rate，顯示其方法具有跨模型的穩健性。無論是使用 GPT-5 mini 或 DeepSeek V3.2，Dual-DAG 與結構演化機制都能有效提升生成品質。

##### 2. 與 RPG 的比較

與目前最強的 repository-planning baseline（程式庫規劃基線）**RPG** 相比，Repo0 的提升幅度相當顯著：

- Functionality Coverage 提升 **4.55–20.08 percentage points（百分點）**
- Pass Rate 提升 **7.61–29.74 percentage points（百分點）**

這代表 Repo0 不僅能生成更多功能，而且生成的功能更正確、更穩定。Pass Rate 的大幅提升尤其重要，因為它反映了生成程式碼的可執行性與正確性，而不僅是「看起來有實作」。

##### 3. 消融研究的意涵

論文進行的 ablation（消融研究）顯示：

- **Dual-DAG architectural state（Dual-DAG 架構狀態）** 是必要組件：若缺少需求層與元件層的明確分離與對齊，智慧體難以判斷結構問題的根源。
- **Modularity-guided structural evolution（模組性引導的結構演化）** 顯著改善品質：單純隨機或無約束的結構變動無法帶來相同效果。
- **Explicit structural convergence（明確的結構收斂）** 有助於穩定生成：在架構穩定後才進入 TDD 階段，可避免反覆重構造成的錯誤累積。

##### 4. 結構演化分析的啟示

進一步的 structural-evolution analyses（結構演化分析）指出：

- 由 cohesion（內聚性）與 coupling（耦合性）引導的演化能持續改善程式庫品質。
- 相對地，**unconstrained evolution（無約束演化）** 反而可能導致結構震盪或品質下降，證明 modularity metrics 不僅是啟發式指標，更是穩定收斂的關鍵。

#### 與現有研究的比較

##### 1. 相對於傳統程式碼生成方法

大多數現有 LLM-based code generation 方法假設 **repository architecture（程式庫架構）** 已經存在或部分給定，例如 GitHub issue resolution、函式補全、或基於現有檔案的編輯任務。Repo0 則挑戰更困難的設定：從純自然語言需求開始，同時推論功能與架構。

##### 2. 相對於 NL2Repo-Bench 等方法

NL2Repo-Bench 等研究透過提供 golden architecture（黃金架構）作為輸入來迴避設計問題。雖然這能簡化任務，但不符合真實開發情境——在實務中，架構往往是在迭代中逐漸浮現的。Repo0 的價值在於不需要預先給定完美藍圖。

##### 3. 相對於多智慧體規劃系統

部分研究採用 multi-agent systems（多智慧體系統），讓不同角色（如規劃者、程式設計師、測試員）分工協作。Repo0 則採用單一智慧體進行連續決策，並透過明確的 Dual-DAG 狀態與模組性指標來引導演化。這種設計減少了多智慧體之間的協調成本，並讓決策過程更具可解釋性。

##### 4. 相對於 RPG 等圖式規劃方法

RPG 等圖式規劃方法雖然引入了 repository planning（程式庫規劃），但仍將圖結構視為 **one-shot fixed graph（一次性固定圖）**。Repo0 的關鍵改進在於將圖視為 **continuously evolving artifact（持續演化的產物）**，並根據執行與驗證回饋動態調整。

##### 5. 限制與潛在弱點

儘管 Repo0 表現優異，仍有以下限制值得注意：

- **評估規模有限**：僅在六個真實世界程式庫上測試，難以推論到更大規模或更複雜的企業級專案。
- **收斂條件未完全揭露**：structural convergence 的判定標準（如閾值、最大迭代次數）在摘要中未詳細說明，可能影響不同任務的適用性。
- **模組性指標的計算成本**：cohesion 與 coupling 的量化可能需要靜態分析或執行環境支援，對於動態語言或高度依賴框架的專案可能較難精確計算。
- **對 backbone model 的依賴**：實驗使用 GPT-5 mini 與 DeepSeek V3.2，這些模型的內部機制與能力邊界會直接影響結構演化的品質。

#### 可重現性評估

##### 1. 開放資源

根據論文資訊，Repo0 的 **code and data（程式碼與資料）** 已公開於 GitHub：

> https://github.com/cslsolow/Repo0

這對於重現研究結果、進行後續比較與社群驗證非常重要。

##### 2. 資料集可取得性

實驗使用 **RepoCraft** 資料集。若該資料集同樣公開，則研究者可取得與論文相同的六個真實世界程式庫進行測試。然而，若 RepoCraft 包含私有或受限授權的程式碼，則可能影響部分使用者的重現能力。

##### 3. 模型可取得性

Repo0 依賴 **GPT-5 mini** 與 **DeepSeek V3.2** 作為 backbone model。這些屬於 closed-weight API model（閉源權重 API 模型），研究者需具備：

- 相應的 API 存取權限
- 足夠的運算預算（因結構演化涉及多次 LLM 呼叫與測試執行）
- 對 API 版本與溫度參數的精確控制，以確保結果可重現

由於 LLM 輸出具有隨機性，即使使用相同提示與資料，不同時間點的 API 回應可能略有差異，這是當前 LLM agent 研究普遍面臨的可重現性挑戰。

##### 4. 執行環境需求

Repo0 需要能夠執行生成程式碼並收集 **validation / execution feedback（驗證／執行回饋）** 的環境，包括：

- 各種程式語言的執行環境（如 Python、Node.js 等）
- 測試框架（如 pytest、Jest 等）
- 靜態分析工具以計算 cohesion 與 coupling

這些環境若未完整記錄於重現說明文件中，可能導致重現困難。

##### 5. 整體可重現性評估

整體而言，Repo0 的可重現性處於 **中等偏上** 水準：

- ✅ 原始碼與資料已公開
- ✅ 評估指標（Functionality Coverage、Pass Rate）相對客觀
- ⚠️ 依賴閉源 API model，存在成本與隨機性問題
- ⚠️ 執行環境與收斂條件需更詳細文件化

建議作者未來提供 Docker 映像檔、詳細的環境設定步驟、以及固定隨機種子的設定，以進一步提升可重現性。

#### 未來研究方向

Repo0 為 zero-to-all code generation 開啟了多條值得探索的研究路徑：

##### 1. 擴大評估規模與多樣性

未來可在更多程式語言、更大規模、以及不同領域（如 Web 後端、嵌入式系統、資料科學管線）的專案上驗證 Repo0 的泛化能力。特別是針對企業級單體式系統與微服務架構的生成，仍是開放挑戰。

##### 2. 更豐富的模組性指標

目前主要使用 cohesion、coupling 與 information hiding。未來可引入：

- **Cyclomatic complexity（循環複雜度）**
- **Interface stability（介面穩定性）**
- **Separation of concerns（關注點分離）**
- **Architectural technical debt（架構技術債）** 指標

這些指標可讓結構演化更貼近真實軟體工程實務。

##### 3. 與人類開發者的協作

Repo0 目前為全自動流程。未來可發展為 **human-in-the-loop（人機協作）** 模式，讓開發者在關鍵設計決策點（如元件拆分、需求優先順序）介入，結合人類領域知識與 LLM 的生成能力。

##### 4. 多智慧體與角色分工

雖然 Repo0 採用單一智慧體，但未來可探索將 Dual-DAG 的維護、結構動作選擇、程式碼生成、測試驗證等職責分配給不同專業化智慧體，並研究其協調機制。

##### 5. 動態與演化式需求

真實軟體開發中，需求會隨時間變動。未來可將 Repo0 擴展至 **incremental requirement update（增量需求更新）** 情境，讓 Dual-DAG 能夠持續適應新增、修改或刪除的需求。

##### 6. 收斂性與理論保證

目前 structural convergence 主要基於經驗觀察。未來可從理論上分析：

- 在何種條件下結構演化保證收斂？
- 不同模組性指標是否會導致局部最佳化？
- 如何避免結構震盪（structural oscillation）？

##### 7. 與 IDE 與開發工具整合

將 Repo0 整合至 VS Code、Cursor、GitHub Copilot 等開發環境中，可讓開發者從需求文件直接生成可執行的專案骨架，並在開發過程中持續獲得架構建議。

##### 8. 安全性與可維護性評估

除了 Functionality Coverage 與 Pass Rate，未來應納入：

- **Security vulnerability（安全漏洞）** 檢測
- **Code maintainability（程式碼可維護性）**
- **Long-term evolution cost（長期演化成本）**

這將使 zero-to-all code generation 不僅「能跑」，更能「長期健康地運作」。

## 論文問答

**Q1：什麼是「從零到完整程式碼生成」（Zero-to-All Code Generation），它與現有的程式碼生成任務有何不同？**

A：從零到完整程式碼生成是指智慧體必須在沒有預先定義程式庫架構的情況下，直接根據自然語言需求建構出整個軟體專案的任務。與現有大多數程式碼生成方法不同，後者通常假設程式庫架構已經部分或完全給定，智慧體只需在既有架構上完成程式碼補全或修改。這項任務更具挑戰性，因為智慧體必須同時推導出軟體的功能需求與其模組化架構，並在開發過程中持續維護良好的設計原則。

**Q2：現有方法為何在從零到完整程式碼生成中表現不佳？其核心瓶頸是什麼？**

A：現有方法的主要問題在於它們將軟體設計視為靜態的一次性規劃產物，而非持續演化的過程。這些方法通常在初始階段產生一份固定的架構藍圖，然後在後續開發中嚴格執行，無法根據實際生成與驗證過程中浮現的複雜度進行調整。核心瓶頸在於，真實軟體開發中元件的內聚性、耦合關係與實作細節往往只有在程式碼逐漸成形後才會變得清晰，因此缺乏持續結構演化的機制會導致元件邊界不一致、依賴結構脆弱以及跨檔案協調不良。

**Q3：為何在開發過程中持續維護程式庫的模組性如此重要？**

A：良好的模組性是軟體工程的核心原則，包含高內聚、低耦合與適當的資訊隱藏，這些原則能確保程式碼易於理解、維護與擴展。在從零到完整程式碼生成中，若缺乏明確的架構引導，智慧體容易產生功能重疊、內部細節洩漏或過度糾纏的依賴關係，進而降低整體程式庫品質。持續維護模組性不僅能提升生成程式碼的結構合理性，也能為後續的測試驅動開發與功能驗證奠定穩固基礎。

**Q4：Repo0 中的 Dual-DAG 架構狀態是什麼？它如何表達程式庫結構？**

A：Dual-DAG 是 Repo0 提出的雙向有向無環圖架構狀態，由需求層級 DAG、元件層級 DAG 以及兩者之間的對齊關係所組成。需求層級 DAG 捕捉功能需求之間的依賴與層次關係，而元件層級 DAG 則對應到實作層面的模組與其相依結構。透過明確維護這兩層圖結構及其對齊關係，Repo0 能夠在需求變更或實作回饋出現時，有系統地調整元件邊界與對應關係，避免需求與實作脫節。

**Q5：Repo0 中的結構性動作有哪些？模組性指標如何引導這些動作？**

A：Repo0 主要使用三種結構性動作：拆分（Split）、合併（Merge）與修訂（Revise），分別用於處理低內聚、高耦合與測試失敗等問題。模組性指標如內聚性與耦合性會持續評估當前 Dual-DAG 的品質，當某個元件出現低內聚時會觸發拆分，當多個元件之間存在高耦合或功能重疊時則觸發合併。這種以指標為導向的決策機制讓結構演化不再是憑直覺進行，而是有明確的量化依據與收斂條件。

**Q6：Repo0 的整體運作流程為何？它如何實現持續性結構演化？**

A：Repo0 從自然語言需求出發，首先建立初始的 Dual-DAG 架構狀態，然後進入反覆的結構演化迴圈。在每次迭代中，智慧體觀察當前架構狀態、執行推理並選擇適當的結構性動作，同時利用驗證與執行回饋來精煉架構，直到達成結構收斂。收斂後的穩定架構會進一步引導測試驅動開發的程式碼生成階段，確保最終產出的程式碼與經過充分演化的設計保持一致。

**Q7：Repo0 使用了哪些基準資料集與模型進行評估？**

A：Repo0 在 RepoCraft 資料集中的六個真實世界程式庫上進行評估，該資料集專門用於測試從需求生成完整程式庫的能力。實驗採用了兩種不同的大型語言模型作為骨幹，分別是 GPT-5 mini 與 DeepSeek V3.2，以驗證方法的泛化性與模型無關性。評估指標主要包括功能覆蓋率（Functionality Coverage）與通過率（Pass Rate），用於衡量生成程式庫是否完整實現需求並通過測試。

**Q8：Repo0 的主要實驗結果為何？與基線方法相比表現如何？**

A：Repo0 在所有設定下均達到最高的功能覆蓋率與通過率，顯示其在從零到完整程式碼生成任務上的優越性。與最強的程式庫規劃基線 RPG 相比，Repo0 的功能覆蓋率提升了 4.55 至 20.08 個百分點，通過率則提升了 7.61 至 29.74 個百分點。這些結果橫跨六個不同程式庫與兩種模型，顯示 Repo0 的設計驅動結構演化方法具有穩定且顯著的效能優勢。

**Q9：消融研究與結構演化分析揭示了哪些重要發現？**

A：消融研究結果顯示，Dual-DAG 架構狀態、模組性引導的結構演化以及明確的結構收斂機制都對最終效能有重要貢獻，移除任一組件都會導致效能下降。結構演化分析進一步指出，以內聚性與耦合性為導向的演化能顯著提升程式庫品質，而缺乏約束的隨意演化則無法帶來相同效益。這些分析共同證明了 Repo0 各項設計選擇的合理性，也強調了持續結構演化相較於一次性靜態規劃的關鍵價值。

**Q10：Repo0 可以應用在哪些實務場景中？**

A：Repo0 特別適合用於新創專案或原型開發，開發者只需提供自然語言需求描述，系統便能自動生成具備良好模組化結構的完整程式庫。此外，它也適用於教學場景，幫助學生理解如何從需求推導出合理的軟體架構。對於需要快速將產品構想轉化為可執行程式碼的企業團隊而言，Repo0 能夠大幅縮短初期設計與開發的時間成本。

**Q11：在實際部署 Repo0 時，有哪些產品層面的考量？**

A：首先，由於結構演化涉及多次迭代與模型呼叫，部署時需要評估運算成本與回應時間之間的平衡，特別是在互動式開發環境中。其次，為了確保生成結果符合組織的編碼規範與架構風格，可能需要加入額外的規則約束或後處理機制。最後，開發者應保留對最終架構與程式碼的審查與編輯能力，將 Repo0 定位為輔助設計與開發的智慧工具，而非完全自動化的黑箱系統。

**Q12：Repo0 對軟體工程智慧體領域可能帶來什麼影響？**

A：Repo0 將研究焦點從單純的程式碼合成轉向設計驅動的完整程式庫生成，強調架構設計在自動化軟體開發中的核心地位。這種持續結構演化的範式可能啟發後續研究在更多軟體工程任務中引入顯式的架構狀態與回饋機制，例如系統重構、遺留程式碼現代化或需求變更管理。長遠而言，Repo0 有助於推動軟體工程智慧體從「程式碼完成工具」朝向「具備設計思維的開發夥伴」發展。

**Q13：Repo0 目前存在哪些限制？**

A：Repo0 目前主要針對 RepoCraft 中的六個真實世界程式庫進行評估，樣本規模與領域多樣性仍相對有限，未來需要更大規模的驗證來確認其泛化能力。此外，結構演化過程依賴模組性指標的準確計算，而這些指標在面對高度動態或語意複雜的需求時可能無法完全捕捉設計品質。最後，Repo0 的效能仍受制於底層語言模型的能力，當模型對特定領域或程式語言的理解不足時，演化過程可能產生次佳決策。

**Q14：在哪些失敗案例中 Repo0 可能會遇到困難？**

A：當自然語言需求本身模糊、不完整或彼此矛盾時，Repo0 可能難以建立穩定的初始 Dual-DAG，導致後續結構演化偏離正確方向。另外，若需求涉及高度創新或非常規的架構設計，單純依賴內聚性與耦合性等傳統模組性指標可能不足以引導出最佳結構。在某些情況下，執行回饋可能無法及時揭示深層的設計缺陷，使得問題累積到後期才浮現，增加修復成本。

**Q15：Repo0 啟發了哪些未來研究方向？**

A：未來研究可以探索更豐富的架構品質指標，例如可擴展性、可測試性與安全性，以擴展 Repo0 的設計目標。另一個方向是將持續結構演化的概念應用於既有程式庫的重構與維護，而不僅限於從零開始生成。此外，結合人機協作機制，讓開發者能夠在演化過程中介入並提供高層設計意圖，也是提升實用性的重要研究課題。

## 實務應用指南

### 適用場景

1. **新創產品 MVP 從需求到可運行程式庫**  
   當團隊只有自然語言撰寫的產品需求文件（PRD），卻沒有現成程式庫架構時，可使用 Repo0 持續演化出 Dual-DAG 架構狀態，再生成可測試、可執行的初始程式碼基底。

2. **企業內部工具或自動化腳本專案**  
   針對資料處理流程、報表生成、內部 API 整合等需求，Repo0 可在無預設元件邊界的情況下，依內聚性與耦合性指標反覆調整元件邊界，避免產出單一巨大模組。

3. **開源專案快速雛形與社群貢獻起點**  
   開源維護者可把 issue 或功能規格餵給 Repo0，讓它從零生成具模組化結構的 repository，作為後續社群協作的基礎版本。

4. **教學與程式設計課程的輔助示範**  
   教師可展示如何從自然語言需求演化成元件層級 DAG，幫助學生理解高內聚、低耦合、資訊隱藏等軟體工程原則。

5. **遺留系統重構前的「理想架構」對照生成**  
   雖然 Repo0 主要用於從零生成，但其 Dual-DAG 與模組性指標也可作為重構目標：先從需求重新生成理想結構，再與現有程式庫比對差距。

### 實作步驟建議

1. **需求結構化與初始 Dual-DAG 建立**  
   將自然語言需求拆解為功能項目，建立需求層級 DAG；再由 LLM 智慧體產出對應的初始元件層級 DAG 與對齊關係。

2. **定義模組性指標與門檻**  
   選擇適合專案的內聚性（cohesion）與耦合性（coupling）計算方式，設定收斂條件，例如：「連續兩輪無 Split / Merge / Revise 動作」或「耦合性低於門檻且內聚性高於門檻」。

3. **執行結構性動作迴圈**  
   讓智慧體觀察目前 Dual-DAG，依據指標決定 Split、Merge 或 Revise，並更新需求層級 DAG、元件層級 DAG 與對齊關係，直到達成結構收斂。

4. **以收斂架構引導測試驅動開發**  
   結構收斂後，將元件 DAG 轉為檔案與套件結構，先產生測試案例，再依測試回饋生成實作程式碼，反覆驗證直到通過率穩定。

5. **持續整合與人工審查**  
   將生成結果納入版本控制，執行靜態分析、單元測試與程式碼審查；若發現新需求或測試失敗，回到結構演化階段重新調整 Dual-DAG。

### 潛在風險與注意事項

| 風險 | 說明與因應 |
|---|---|
| **過度擬合模組性指標** | 智慧體可能為了數字好看而過度拆分，導致元件過細。應輔以功能覆蓋率與通過率共同評估，並保留人工覆核權限。 |
| **需求變動造成結構震盪** | 自然語言需求若頻繁變動，Dual-DAG 可能難以收斂。建議先凍結核心需求，再進入結構收斂階段。 |
| **LLM 幻覺導致錯誤相依** | 元件層級 DAG 的邊可能反映 LLM 的推測而非實際程式碼相依。應以靜態分析或實際執行結果驗證相依關係。 |
| **收斂條件過鬆或過嚴** | 條件太鬆會留下低內聚 / 高耦合結構；太嚴則浪費運算。建議從論文設定出發，再依專案規模調整。 |
| **測試案例不足影響生成品質** | Repo0 後半段依賴測試驅動開發，若測試覆蓋不完整，生成的程式碼可能通過測試卻未滿足真實需求。 |

### 與其他技術的整合建議

- **與現有 CI/CD 管線整合**  
  將結構收斂後的程式庫直接推入 GitHub Actions / GitLab CI，自動執行 pytest、linter 與相依掃描，把驗證 / 執行回饋送回 Repo0 進行下一輪結構修訂。

- **與需求管理工具整合**  
  將 Jira、Notion 或 Linear 中的需求項目自動匯出為需求層級 DAG 的節點，需求變更時觸發 Dual-DAG 重新對齊與結構演化。

- **與現有程式庫共存的漸進式導入**  
  對於已有程式碼的專案，可先用 Repo0 針對「新模組」生成理想 Dual-DAG，再透過 adapter 或 facade 模式與舊系統銜接，降低全盤重寫風險。

- **與多智慧體框架整合**  
  可將 Repo0 的規劃 / 精煉智慧體作為「架構師角色」，與其他負責編碼、測試、文件的智慧體協作，形成更完整的軟體工程智慧體團隊。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦圖 1 與圖 2 的概念對照：傳統方法是一次性固定圖，Repo0 則像「會不斷修正藍圖的建築師」。理解 Dual-DAG 就是「需求圖」與「元件圖」互相對照，再記住高內聚、低耦合、資訊隱藏三個設計目標即可。

**AI 工程師**  
重點關注結構性動作（Split / Merge / Revise）的提示工程、模組性指標的計算方式，以及結構收斂條件如何影響 LLM 呼叫次數與生成品質。實作時建議把 Dual-DAG 以結構化格式（如 JSON / YAML）儲存，方便追蹤每輪演化。

**研究人員**  
可深入分析 Dual-DAG 對齊關係的數學性質、不同模組性指標對收斂速度與最終通過率的影響，並探索將此方法擴展至非 DAG 架構（如微服務拓撲、循環相依場景）的可能性。

**產品經理**  
本論文的核心價值在於「把軟體設計從一次性規劃變成持續演化」，這意味著需求不必等到完美才能開工，但必須建立明確的結構收斂與測試驗收機制。導入時應預留反覆調整架構的時間與運算預算。
