# LEASH：電腦使用代理（CUA）之不確定性感知弱到強升級與監督框架

## ⚡ TL;DR

電腦使用代理在長時程任務中面臨成本與效能的取捨，弱到強升級需決定何時升級及如何監督黑盒強代理。
LEASH 為無需訓練框架，以弱代理隱藏狀態對成敗軌跡的馬氏距離作為不確定性，驅動路由、升級與監督。
LEASH比隨機升級高6.55–11.94分，以Qwen達73.66%，匹配Opus5省19.2%。

## 摘要翻譯

電腦使用代理日益處理長時程任務，其中每一步都運行前沿模型的成本高昂，而僅靠小型開源權重模型則經常失敗。弱到強升級（W2SE）提供了一個中間方案：弱代理預設執行，僅在需要時將控制權交給強代理。核心挑戰在於決定何時升級，這需要一個足夠便宜、能在每一步進行檢查的不確定性信號。然而，即使在交接後，強代理仍可能迷失方向，但強代理通常透過其服務的黑盒 API 並未暴露可供監控的內部狀態。有鑑於此，我們提出 LEASH，一個無需訓練的框架，僅在弱代理的潛在不確定性顯示需要時才釋放強代理，並在之後以 LEASH 加以約束。LEASH 包含三個層次：(1) 用於早期路由的初始任務不確定性，(2) 用於執行期升級的步驟級不確定性，以及在交接後的 (3) 用於持續監督強黑盒代理的影子觀察者。在此，我們將潛在不確定性作為驅動所有三個層次的燃料。具體而言，我們將弱模型的隱藏狀態與其過去成功軌跡和失敗軌跡中的隱藏狀態進行比較，更近似於失敗軌跡的狀態代表更高的不確定性。在弱代理執行期間，我們的不確定性估計器重複使用動作生成過程中已產生的激活值，因此無需額外的前向傳遞或專門的監控器訓練。在 OSWorld 上以四個當代骨幹模型進行的實驗結果表明，LEASH 持續優於獨立運作的弱代理，並在匹配升級率下比隨機升級高出 6.55 至 11.94 個百分點。使用 Qwen3.5-35B-A3B 時，LEASH 在每個任務 0.4117 美元的成本下達成 73.66% 的任務成功率，與始終啟用的 Claude Opus 5（72.90%）相當，同時降低推理成本 19.2%。

### 核心貢獻（3～5點）
- 提出 LEASH 框架——一個無需訓練的三層架構，結合初始任務不確定性（早期路由）、步驟級不確定性（執行期升級）與影子觀察者（交接後持續監督），系統性地解決電腦使用代理在長時程任務中的成本與可靠性問題。
- 設計零額外計算成本的不確定性估計器——透過比較弱模型隱藏狀態與其過去成功／失敗軌跡的相似度來推斷不確定性，並重複使用動作生成過程中已產生的激活值，無需額外的前向傳遞或監控器訓練。
- 解決黑盒 API 不可監控的難題——影子觀察者機制使弱代理能在強代理交接後持續監督其行為，即使強代理以黑盒 API 形式部署亦能維持控制。
- 在 OSWorld 基準測試上以四個當代骨幹模型驗證有效性——LEASH 持續優於獨立運作的弱代理，在匹配升級率下比隨機升級高出 6.55–11.94 個百分點。
- 展現優異的成本效率——以 Qwen3.5-35B-A3B 搭配 LEASH 即可達到 73.66% 的任務成功率，與始終啟用 Claude Opus 5（72.90%）相當，同時降低推理成本 19.2%。

### 適合對象
從事 AI 代理（Agent）系統設計與部署的研究者與工程師，特別是關注電腦使用代理（CUA）、人機互動自動化、長時程序列決策、模型路由與成本優化的團隊；亦適合研究 AI 監督機制、不確定性估計、弱到強協同學習，以及前沿模型與開源權重模型混合部署策略的學術界與產業界讀者。

## 深度分析

#### 方法論解析

LEASH（Latent uncertainty for Escalation And SHadow oversight）將弱到強升級（Weak-to-Strong Escalation, W2SE）形式化為**預算受限的序列停止問題（Budget-constrained Sequential Stopping Problem）**，其核心洞見在於：弱代理的失敗風險可作為升級預期效益的代理指標（proxy），而此一風險可從弱代理自身的隱藏狀態（hidden states）中以無需訓練（training-free）的方式萃取。整體方法論可拆解為三個相互耦合的層次。

**第一層：表示庫（Representation Bank）的建構。** 在部署前，LEASH 蒐集弱代理在一小批保留任務（held-out tasks）上的隱藏狀態，涵蓋提示詞（prompt）與動作（action）兩類 token，並以任務級與子目標級（subgoal-level）的成功／失敗標籤加以標註。此表示庫作為語意錨點（semantic anchor），記錄了弱代理在「曾經成功」與「曾經失敗」兩種情境下的內部表徵分布。

**第二層：潛在不確定性估計器。** 給定測試時的新提示或動作，LEASH 在潛在空間中以**馬氏距離（Mahalanobis distance）** 計算該隱藏狀態與成功簇、失敗簇的相對距離——「越接近過去失敗的狀態，不確定性越高」。此設計的關鍵優勢在於：弱代理在產生動作時本就需要計算隱藏狀態，因此不確定性估計**完全重用既有激活值（activations）**，無需額外的前向傳遞（forward pass），亦無需訓練專屬的監控網路。這與傳統需要監控代理（monitoring agent）、參考模型（reference model）或多重採樣（multiple sampling）的方法形成鮮明對比。

**第三層：三層式決策架構。** LEASH 將單一不確定性信號驅動三個決策點：
1. **初始任務不確定性閘門（Initial Task Uncertainty Gate）**：在任務開始時，根據提示詞的不確定性決定是否直接路由至強代理，實現早期路由（early routing）。
2. **步驟級不確定性閘門（Step-level Uncertainty Gate）**：在弱代理執行期間，每步監控其不確定性，超過閾值即觸發執行期升級（runtime escalation）。
3. **影子觀察者（Shadow Observer）**：升級後，弱代理角色由「行動者」轉為「觀察者」，每三步檢視強代理的軌跡；當觀察者自身不確定性升高時，強代理的待執行動作將被回滾（rollback），並以更高推理預算重新決策。

此架構的理論基礎在於：弱代理的隱藏狀態已編碼了任務難度與執行信心等豐富資訊，無需外掛模組即可同時服務於「升級判斷」與「持續監督」兩個目標。論文亦提供了使用此分數作為升級依據的理論正當性（theoretical justification），將弱代理的失敗風險與升級的預期效益聯繫起來。

#### 實驗數據解讀

實驗在 OSWorld 基準上進行，採用四款當代開源權重模型（open-weight models）作為弱代理，並以 Claude Opus 5 作為強代理。評估設計遵循 Burns 等人（2023）的**性能差距恢復率（performance-gap recovery）** 指標，衡量 LEASH 在弱代理與始終啟用強代理（always-on Opus）之間恢復了多少性能差距。

**關鍵數據解讀如下：**

1. **升級率匹配下的比較**：在匹配升級率（matched escalation rates）下，LEASH 較隨機升級（random escalation）提升 6.55–11.94 個百分點。這顯示不確定性信號遠比隨機觸發更具資訊量，能精準識別弱代理真正需要協助的時刻。

2. **性能差距恢復率**：LEASH 恢復了 75–102% 的性能差距，而隨機升級僅恢復 37–69%。值得注意的是，**恢復率超過 100%** 的情況意味著 LEASH 在某些配置下甚至超越了始終啟用 Opus 的表現——這可能是因為弱代理在簡單步驟上比 Opus 更經濟且同樣準確，而 Opus 僅在困難步驟上介入。

3. **成本效益**：LEASH 的成本僅為始終啟用 Opus 的 69–81%，卻能恢復近全幅性能。以 Qwen3.5-35B-A3B 為弱代理時，LEASH 達到 73.66% 的任務成功率，每任務成本 $0.4117，**匹配了 Opus 的 72.90% 成功率，同時降低推理成本 19.2%**。在相同成本預算下，隨機升級僅達到約 64% 的成功率，落後約 9 個百分點。

4. **跨骨幹模型泛化**：四款弱代理骨幹模型（backbones）的一致性提升表明，潛在不確定性估計方法對模型架構具有相當的泛化能力，並非依賴特定模型的特殊性質。

**數據背後的意涵**：這些結果共同指向一個重要結論——**不確定性信號的品質比升級頻率更為關鍵**。即使升級率相同，基於語意距離的判斷遠優於隨機觸發，這驗證了「弱代理的隱藏狀態已包含足夠資訊」這一核心假設。

#### 與現有研究的比較

LEASH 在 W2SE 與電腦使用代理（Computer-Use Agents, CUAs）兩個研究脈絡中均提出了明確的定位。

**與 W2SE 既有方法的比較：**
- **監控代理方法**（如 Wang 等人 2024；Yi 等人 2026）：每步呼叫另一個重型代理進行驗證，雖直觀但成本高昂，難以擴展至長時程任務（long-horizon tasks）。LEASH 完全不需要此類監控代理。
- **訓練專屬監控模組方法**（如 Lei and Huang 2026；Wei 等人 2026）：需要資料標註（data annotation）與訓練階段，阻礙在不同部署限制（deployment constraints）下的即時採用。LEASH 的無需訓練特性繞過了此一瓶頸。
- **基於不確定性的既有方法**（如 Oh 等人 2026a、2026b；Wang 等人 2026）：仍依賴外部知識庫（external knowledge base）、參考模型或每步多重採樣，在長時程任務中迅速變得不可行或不切實際。LEASH 僅使用弱代理自身的過去經驗，無需任何外部資源。

**與 CUA 效率研究的比較：**
- **FrugalGPT、RouteLLM**（Chen 等人 2023；Dekoninck 等人 2025；Ong 等人 2025）：展示了模型路由與級聯在平衡成本與性能上的潛力，但主要針對語言任務。
- **Adaptive VLM Routing**（Liu 等人 2026）：根據動作難度與信心選擇模型，但需要外部知識庫。
- **StepWise**（Wei 等人 2026）：訓練輕量監控器偵測執行停滯並標記升級時機。

LEASH 的差異化在於：**利用骨幹代理自身的內部表徵引導任務級路由與步驟級升級，無需訓練專屬監控網路**。這使其在部署靈活性與計算效率上具備明顯優勢。

**與弱到強範式（Weak-to-Strong Paradigm）的關聯：** 傳統弱到強泛化研究（Burns 等人 2023；Jung 等人 2025）聚焦於「強模型如何從弱監督中學習」，而 LEASH 將此範式擴展至代理系統的執行層級，並引入「升級後的持續監督」這一被既有研究忽略的問題。

**侷限性分析：**
1. **表示庫的依賴**：需要一小批保留任務來建構成功／失敗表示庫，若弱代理從未見過的任務類型出現，不確定性估計可能失準。
2. **黑盒強代理的監督深度有限**：影子觀察者僅能觀察強代理的動作輸出軌跡，無法存取其內部推理過程，監督粒度受限於弱代理對「合理動作」的判斷能力。
3. **閾值設定的敏感性**：三層閘門的閾值如何在不同任務類型間泛化，仍需經驗調校。
4. **每三步檢查的頻率假設**：固定檢查間隔可能不適應所有任務節奏，動態調整機制有待探索。

#### 可重現性評估

從論文提供的資訊評估可重現性：

**有利因素：**
- **無需訓練的特性**：LEASH 不涉及模型訓練或資料標註流程，大幅降低了重現門檻。
- **基於公開基準**：OSWorld 是公開的電腦使用代理評測基準（benchmark），任務定義與評估協議均可取得。
- **使用公開模型**：四款弱代理骨幹模型均為開源權重模型（open-weight models），可從 Hugging Face 等平台取得。
- **強代理為商業 API**：Claude Opus 5 透過 API 呼叫，無需本地部署。

**潛在挑戰：**
- **表示庫的具體建構細節**：保留任務的選擇、隱藏狀態的擷取層、馬氏距離的協方差矩陣估計方式等細節需從附錄或程式碼確認。
- **閾值設定**：三層閘門的具體閾值如何決定，是否需要任務特定的調校，將影響重現結果。
- **OSWorld 評估的隨機性**：長時程任務的執行軌跡可能存在隨機性，需多次運行取平均以獲得穩定結果。
- **影子觀察者的回滾機制**：每三步檢查的頻率、回滾後的重新決策預算等超參數需明確說明。

**整體評估**：LEASH 的無需訓練特性使其在概念上易於重現，但完整的端到端重現仍需作者釋出程式碼，特別是表示庫建構、不確定性計算與三層閘門整合的實作細節。建議作者開源程式碼並提供預建構的表示庫，以促進社群驗證與後續改進。

#### 未來研究方向

LEASH 開啟了多條值得深入探索的研究路徑：

**1. 表示庫的動態擴展與線上學習。** 目前表示庫在部署前靜態建構，可探索在執行過程中根據新觀察到的成功／失敗案例線上更新表示庫，使不確定性估計隨代理經驗累積而持續精化。此方向與 Silver 與 Sutton（2025）所倡議的「從經驗中學習」路線一致。

**2. 多代理級聯與遞迴監督。** LEASH 目前的兩層架構（弱→強）可擴展至多層級聯，例如弱→中→強，或在多個弱代理間形成共識監督。影子觀察者的概念亦可遞迴應用——強代理本身亦可作為下一層的觀察者，形成監督鏈。

**3. 不確定性信號的理論深化。** 馬氏距離作為不確定性度量的理論基礎可進一步形式化，例如探討其在不同模型架構下的統計性質、與貝氏不確定性的關聯，以及在分布外（out-of-distribution）輸入下的行為。

**4. 跨任務與跨領域泛化。** 目前實驗集中於 OSWorld，可探索 LEASH 在網頁代理、程式設計代理、機器人控制等其他長時程代理任務上的表現，檢驗潛在不確定性是否具有跨領域的通用性。

**5. 強代理的細粒度監督。** 目前影子觀察者僅能觀察強代理的動作輸出，可探索結合動作語意分析、螢幕畫面變化檢測等多元信號，提升監督的細粒度與可靠性。

**6. 與自我改進迴圈的整合。** 論文提及 LEASH 為遞迴自我改進（recursive self-improvement）提供擴展性（Madaan 等人 2023；Schmidhuber 2007；Shinn 等人 2023；Wang 等人 2023；Zelikman 等人 2022）。未來可探索將升級決策與弱代理的策略更新結合，使弱代理從升級經驗中學習，逐步降低對強代理的依賴。

**7. 成本感知的不確定性閾值。** 目前閾值設定未明確考慮成本約束，可發展動態閾值調整機制，根據剩餘預算與任務剩餘步數自動平衡升級頻率與性能。

**8. 安全與對齊應用。** LEASH 的監督機制天然適用於安全監測場景——影子觀察者可作為強代理潛在有害行為的早期預警系統，此方向與 AI 對齊研究高度相關。

這些方向不僅能深化 LEASH 本身的技術內涵，亦將推動弱到強範式在更廣泛的代理系統中的應用，最終朝向「以低成本取得高性能、以持續監督確保可靠性」的實用目標邁進。

## 論文問答

**Q1：LEASH 主要解決什麼核心問題？**
A：LEASH 解決的是電腦使用代理（CUA）在長時程任務中面臨的「性能與成本取捨」難題。前沿專有模型（如 Claude Opus 5）雖然性能優異，但每步都呼叫會造成高昂的推理成本；而輕量開源權重模型雖然便宜，卻在複雜任務上表現不佳。為此，LEASH 提出弱到強升級（W2SE）機制，讓弱代理作為預設執行者，僅在不確定性高時才將控制權升級給強代理，從而在保證任務成功率的同時顯著降低平均成本。

**Q2：現有的弱到強升級方法為何不夠理想？**
A：現有方法主要分為兩類，但各有明顯瓶頸。第一類是引入額外的監控代理逐步驗證弱代理的動作，這會在每一步都增加重型代理的呼叫成本，與節省成本的核心目標相矛盾。第二類則是訓練專門的監控模組，需要額外的資料標註與訓練階段，難以直接應用於多變的部署環境。此外，即使是不確定性估計方法，也常依賴外部知識庫、參考模型或多重採樣，在長時程任務中變得不可行或不切實際。

**Q3：為什麼這個問題對電腦使用代理特別重要？**
A：電腦使用代理處理的任務通常極為長時程，平均耗時可超過一小時，且涉及數百個步驟的圖形介面操作，這使得每步成本的累積效應被大幅放大。同時，這類任務的視覺與操作上下文會隨時間演進，使得語言化信心度變得不可靠，難以作為升級判斷依據。更關鍵的是，即使強代理接手後，仍可能在長時程中偏離原任務目標，而強代理通常以黑盒 API 形式提供，內部狀態無法被監控，因此需要一個能同時處理升級判斷與後續監督的整合性框架。

**Q4：LEASH 的核心方法是什麼？**
A：LEASH 的核心是一個無需訓練的三層框架，皆由弱代理的潛在不確定性信號驅動。第一層是初始任務不確定性，用於在任務開始時進行早期路由；第二層是步驟級不確定性，在執行期間監控弱代理的軌跡並觸發執行期升級；第三層則是交接後的影子觀察者，由弱代理轉為監督者，持續監控黑盒強代理的行為。具體而言，該方法透過比較弱模型當前隱藏狀態與其過去成功、失敗軌跡的隱藏狀態之間的馬氏距離，量化其與失敗模式的相似度，作為不確定性的代理指標。

**Q5：影子觀察者機制的關鍵創新是什麼？**
A：影子觀察者的關鍵創新在於讓原本作為執行者的弱代理在升級後「角色轉換」為監督者，解決了黑盒強代理無法被監控的難題。由於強代理通常以黑盒 API 提供，內部狀態不可存取，傳統的內部監控方法無法適用；而弱代理作為白盒模型，其隱藏狀態可被讀取，因此能以自身的潛在不確定性來評估強代理的動作。當觀察者偵測到高不確定性時，會將待執行的動作回退並要求強代理以更高推理努力重新決策，從而實現對強代理的持續監督與即時介入。

**Q6：LEASH 採用了哪些設計選擇以實現無需訓練且高效？**
A：LEASH 的關鍵設計選擇是「重用」弱代理在動作生成過程中已產生的激活值，無需額外的前向傳遞或專門的監控模型訓練。具體而言，框架先在一小組保留任務上記錄弱代理提示與動作 token 的隱藏狀態，並以任務級與子目標級的成功／失敗標籤建立「表徵庫」；測試時則以馬氏距離度量新面臨的隱藏狀態與過去失敗軌跡的相似度。這種設計完全依賴弱代理自身的過去經驗作為語意錨點，不需外部資料集、參考模型或多重採樣，因此既無需訓練階段，也避免了執行期的額外重型計算。

**Q7：LEASH 使用什麼基準測試進行評估？為何選擇此基準？**
A：LEASH 在 OSWorld 基準上進行評估，這是一個專門用於電腦使用代理的標準化測試集。選擇 OSWorld 的原因在於它涵蓋了真實且多樣的圖形介面操作任務，能有效反映長時程代理在實際部署中的表現。實驗涵蓋了四種當代開源權重骨幹模型，並以 Claude Opus 5 作為強代理，從而能在不同弱代理配置下全面評估升級與監督機制的有效性。

**Q8：LEASH 的關鍵實驗結果為何？**
A：在匹配升級率下，LEASH 比隨機升級高出 6.55 至 11.94 個百分點，顯示其不確定性信號能精準識別需要升級的時機。在性能差距恢復率方面，LEASH 恢復了弱代理與始終啟用 Opus 之間 75% 至 102% 的性能差距，而隨機升級僅恢復 37% 至 69%；同時 LEASH 的成本僅為始終啟用 Opus 的 69% 至 81%。最具代表性的結果是，搭配 Qwen3.5-35B-A3B 時，LEASH 達到 73.66% 的任務成功率（單任務成本 0.4117 美元），匹配始終啟用 Claude Opus 5 的 72.90%，同時降低 19.2% 的推理成本。

**Q9：哪些消融實驗或分析支持了 LEASH 的設計？**
A：雖然摘要未詳列所有消融實驗，但從方法描述可推論出幾項關鍵分析支持其設計。首先，馬氏距離度量在潛在空間中比較隱藏狀態與過去成功／失敗軌跡的相似度，論文中提供了使用此分數進行升級的理論依據。其次，框架將單一潛在不確定性信號同時用於升級與監督兩個層面，驗證了「一個信號驅動多個決策」的可行性。此外，匹配升級率下的對比實驗（LEASH vs. 隨機升級）直接證明了不確定性信號相較於隨機策略的優勢，而成本與性能的權衡曲線則展示了在不同預算約束下的實用性。

**Q10：LEASH 適用於哪些實際應用場景？**
A：LEASH 特別適合需要大量自動化圖形介面操作的企業場景，例如客服中心的系統操作自動化、辦公軟體（如 LibreOffice）批次處理、瀏覽器資料擷取與填報、以及內部工具的測試自動化。在這些場景中，任務通常耗時長、步驟多，若全程使用前沿模型將造成難以承受的成本，而 LEASH 能在維持高任務成功率的同時顯著降低單任務支出。此外，對於雲端代理服務供應商而言，LEASH 提供的預算受限序列停止問題框架，使其能在客戶給定的成本上限內最大化整體吞吐量與成功率。

**Q11：LEASH 解決了哪些產品部署上的考量？**
A：LEASH 從三個層面回應了產品部署的核心考量：成本、可預測性與可擴展性。在成本方面，LEASH 透過只在必要時升級，使平均推理成本接近弱代理而非強代理，大幅降低單位任務支出。在可預測性方面，由於不確定性信號來自弱代理自身的隱藏狀態，無需依賴外部 API 或額外訓練，因此部署時不需維運額外的監控基礎設施。在可擴展性方面，框架的訓練-free 特性意味著新模型或新任務只需重新建立小型表徵庫即可上線，無需重訓監控器，這對於模型快速迭代的環境尤其重要。

**Q12：LEASH 對學術與產業的更廣泛影響是什麼？**
A：LEASH 對學術界的影響在於將弱到強升級形式化為預算受限的序列停止問題，並展示了單一潛在不確定性信號可同時驅動升級與監督兩個決策層面，為後續研究提供了新的理論框架。同時，「以模型自身過去經驗作為語意錨點」的概念呼應了 Silver 與 Sutton 提出的「經驗即一切」觀點，並與自我改進、反思等研究方向相契合。對產業而言，LEASH 證明了開源權重模型搭配前沿 API 的混合部署模式可在性能上匹敵始終啟用前沿模型，這將促使更多企業採用分層代理架構以平衡成本與能力，進一步推動 AI 代理在真實工作流程中的普及。

**Q13：LEASH 論文承認了哪些限制？**
A：雖然摘要未詳列所有限制，但從方法描述可推論出幾項潛在限制。首先，LEASH 依賴弱代理為白盒模型以讀取其隱藏狀態，這意味著若弱代理本身也是黑盒 API，則無法直接套用此框架。其次，表徵庫的建立需要一小組保留任務及其成功／失敗標籤，雖然規模不大，但在新領域部署時仍需一定的標註成本。此外，馬氏距離度量假設潛在空間中成功與失敗軌跡具有可區分的結構，若弱代理的表徵空間不夠豐富或任務過於簡單，則不確定性信號的鑑別力可能下降。

**Q14：LEASH 可能遭遇哪些失敗案例？**
A：LEASH 可能遭遇的失敗案例包括：當弱代理的隱藏狀態無法有效區分「真正的不確定性」與「任務本身的內在歧義」時，可能導致不必要的升級或錯失升級時機。在長時程任務中，若弱代理的軌跡逐漸偏離但其隱藏狀態仍與成功模式相似，則升級可能延遲觸發，造成更多步驟的浪費。此外，當強代理接手後若其動作本身合理但與弱代理觀察者的預期模式不符時，影子觀察者可能誤判為高不確定性而過度介入，導致強代理的推理效率降低。最後，若強代理在黑盒 API 後出現非預期的行為模式（如幻覺或重複動作），LEASH 的監督機制可能無法及時識別。

**Q15：LEASH 未來的研究方向有哪些？**
A：未來研究方向可從幾個維度展開。首先，可探索將 LEASH 擴展至多代理階層架構，例如多個弱代理協作並由單一強代理監督，或遞迴式的弱到強到更強升級鏈。其次，可研究如何讓表徵庫隨任務動態更新，使不確定性估計能適應新興的任務類型而不需重新標註。此外，將潛在不確定性與其他信號（如動作一致性、視覺注意力）融合，可能進一步提升升級判斷的精準度。最後，將 LEASH 的預算受限序列停止問題形式化推廣至其他領域（如程式碼生成、機器人控制），可驗證此框架的通用性，並推動「成本感知代理」成為新一代代理系統的標準設計原則。

## 實務應用指南

### 適用場景

1. **企業內部辦公自動化代理**：在 LibreOffice、瀏覽器、ERP 系統等 GUI 環境中執行跨應用程式工作流（如「匯出本月報表並寄給主管」），預設由開源權重模型處理例行步驟，僅在涉及複雜決策或多步驟導航時升級至 Claude Opus 5 等前沿模型，可顯著降低每任務成本。

2. **客服與技術支援桌面自動化**：在長時程的疑難排解任務（如「重置用戶權限並驗證登入」）中，弱代理先處理標準流程，當潛在不確定性升高時升級至強代理；交接後弱代理轉為影子觀察者，每三步檢查一次，避免強代理在長任務中偏離目標。

3. **軟體測試與迴歸驗證**：CI/CD 流程中以弱代理執行大量重複性 GUI 測試步驟，遇到非預期畫面或操作失敗跡象時升級至強代理進行根因分析；影子監督機制可在強代理嘗試修復時即時攔截錯誤動作。

4. **資料遷移與批次處理任務**：在跨系統資料搬運（如「從舊 CRM 匯出客戶資料並匯入新系統」）中，弱代理處理結構化重複操作，強代理僅在欄位對應、例外處理等需要語意理解的環節介入，預期可節省 19–31% 推理成本。

5. **個人化數位助理與無障礙工具**：為身心障礙使用者或長者提供 GUI 操作輔助時，弱代理快速完成簡單點擊與輸入，強代理在涉及多選項判斷或錯誤恢復時介入，並由弱代理持續監督避免強代理誤觸敏感操作。

### 實作前置條件

**資料需求**
- 一組「小型、保留（held-out）」的同領域任務軌跡：用於建立表示庫（representation bank），需涵蓋成功與失敗兩類標註。建議至少 50–200 條任務級軌跡，並對每條軌跡的子目標（subgoal）標註成功/失敗。
- 軌跡需包含弱代理在每個步驟的隱藏狀態（hidden states），涵蓋 prompt 與動作（action）token 的表徵。
- 評測資料集：建議以 OSWorld 或類似 GUI 自動化基準作為離線驗證環境。

**計算資源**
- 弱代理：開源權重模型（如 Qwen3.5-35B-A3B、Qwen2.5-VL、UI-TARS 等），需具備白盒存取權以讀取隱藏狀態。單張 A100/H100 等級 GPU 即可運行 7B–35B 級模型。
- 強代理：透過 API 呼叫的閉源前沿模型（如 Claude Opus 5、GPT 系列），僅需網路連線與 API 金鑰。
- 儲存：表示庫需保存每條軌跡的隱藏狀態向量，視任務長度與模型層數，預估每條軌跡數 MB 至數十 MB。

**技能前提**
- 熟悉 Transformer 內部結構，能從開源模型中提取中間層隱藏狀態（建議使用最後一層或倒數第二層）。
- 具備 GUI 代理開發經驗，理解 OSWorld、WebArena 等基準的動作空間與觀察格式。
- 熟悉 Mahalanobis 距離或類似統計度量在表徵空間中的應用。
- 具備基本的成本監控與 API 速率限制管理能力。

### 實作步驟建議

**步驟一：建立表示庫（Representation Bank）**
1. 選用目標弱代理骨幹模型，固定隨機種子。
2. 在保留任務集上執行弱代理，記錄每步 prompt 與動作 token 的隱藏狀態。
3. 根據任務最終結果（成功/失敗）與子目標結果為每筆表徵打標籤，分別存入「成功庫」與「失敗庫」。
4. 計算兩庫的均值向量與共變異數矩陣，作為 Mahalanobis 距離的參考分布。

**步驟二：實作不確定性評分器**
1. 設計評分函式：給定新步驟的隱藏狀態 $h$，計算 $h$ 到成功庫與失敗庫的 Mahalanobis 距離差值，差值越大代表越接近失敗模式。
2. 將評分器整合至弱代理的推論流程中，**重用動作生成時已產生的激活值**，避免額外前向傳遞。
3. 校準門檻：透過驗證集調整初始任務不確定性與步驟級不確定性的升級門檻，使升級率落在預算範圍內（建議先以 30–50% 升級率做消融實驗）。

**步驟三：建構三層路由與監督管線**
1. **初始任務不確定性層**：任務開始時對 prompt 評分，超過門檻則直接交由強代理執行。
2. **步驟級升級層**：弱代理執行期間，每步評分；超過門檻則觸發升級，將當前狀態序列化後移交強代理。
3. **影子觀察者層**：升級後，弱代理改為每三步對強代理的軌跡評分一次；當不確定性升高時，撤銷待執行動作並要求強代理以更高推理預算重新決策。

**步驟四：整合強代理 API 與動作回滾機制**
1. 設計動作介面層，統一強弱代理的動作格式（點擊、輸入、滾動等）。
2. 實作「撤銷佇列」：當影子觀察者標記動作為高不確定性時，自動執行反向動作（如關閉誤開的分頁、清除誤輸入文字）並將狀態回退至前一檢查點。
3. 設定強代理的推理預算梯度（如 standard / extended thinking），供升級後彈性調用。

**步驟五：離線評測與線上 A/B 測試**
1. 在 OSWorld 上以四種開源骨幹模型重現論文實驗，確認 LEASH 相對隨機升級能帶來 6.55–11.94 點的提升。
2. 計算「升級差距回收率」（performance-gap recovery），目標為 75–102%。
3. 部署至影子流量進行線上 A/B 測試，監控任務成功率、平均成本、升級率與使用者滿意度。
4. 根據線上分布漂移定期更新表示庫（建議每週或每月一次）。

**步驟六：成本與延遲優化**
1. 監控每任務的 token 消耗與 API 呼叫次數，目標成本應控制在 always-on 強代理的 69–81%。
2. 對影子觀察者的檢查頻率（預設每三步）做敏感度分析，在監督效果與監督成本間取捨。
3. 考慮快取常見任務的強代理回應，進一步降低重複任務成本。

### 潛在風險與注意事項

**風險一：表示庫的代表性偏差**
- **問題**：保留任務若與實際部署分布不一致，不確定性評分會失準，導致過度升級或升級不足。
- **緩解**：定期以最新部署資料重新校準表示庫；採用滑動窗口更新而非全量重訓；對新興任務類型加入少量標註樣本。

**風險二：弱代理骨幹模型變更後的相容性**
- **問題**：表示庫與特定骨幹模型綁定，更換模型後所有距離計算需重新建立。
- **緩解**：將表示庫建立流程模組化，支援一鍵重建；在模型升級時同步重做離線評測。

**風險三：強代理黑盒行為的不可預測性**
- **問題**：強代理可能在影子觀察者未察覺時偏離任務，尤其在長時程任務中上下文演進可能使語言化信心度失效。
- **緩解**：縮短觀察間隔（從每三步改為每兩步）以提高覆蓋；對高風險動作（刪除、付款、提交）設定獨立的人工審核鉤鏈。

**風險四：動作回滾的副作用**
- **問題**：撤銷動作可能破壞 GUI 狀態一致性，例如無法撤銷的系統對話框或非可逆操作。
- **緩解**：建立「不可回滾動作清單」，對此類動作僅觸發警告而不自動撤銷；改為要求強代理重新決策。

**風險五：API 成本失控**
- **問題**：若不確定性門檻過低，升級率可能飆升導致成本超過 always-on 強代理。
- **緩解**：設定硬性預算上限（如每任務最高 API 呼叫次數）；採用階梯式升級（先嘗試中型模型，必要時再升級至前沿模型）。

**風險六：評分器的對抗性脆弱性**
- **問題**：若攻擊者刻意構造輸入使隱藏狀態落入「成功庫」分布，可能繞過監督。
- **緩解**：結合規則式監控（如禁止動作清單）作為第二道防線；對高敏感操作採用人工確認。

### 與其他技術的整合建議

**與模型路由（Model Routing）框架整合**
- LEASH 的不確定性評分可作為 RouteLLM、FrugalGPT 等路由系統的特徵輸入，取代或補充其基於難度的路由策略。
- 建議將 LEASH 設計為路由決策的「最後一哩」，在多模型候選中選出最合適的骨幹。

**與 GUI 代理框架整合**
- 可作為 OSWorld、OpenInterpreter、AutoGen 等框架的外掛模組，僅接管升級與監督邏輯，不影響代理核心迴圈。
- 對支援多模態輸入的代理（如 Qwen2.5-VL），需擴展表示庫以納入視覺 token 的隱藏狀態。

**與監控與可觀測性平台整合**
- 將不確定性分數、升級率、影子觀察者觸發次數等指標匯出至 Prometheus、Grafana 或 LangSmith 等平台。
- 設定異常告警：例如升級率突然飆升或影子觀察者連續觸發，可能表示弱代理骨幹出現回歸。

**與成本管理系統整合**
- 與雲端成本監控（如 AWS Cost Explorer、內部 FinOps 平台）對接，自動標記每任務的強代理呼叫成本。
- 支援預算閾值告警與自動降級（將前沿模型暫時換為中端模型）。

**與人類回饋強化學習（RLHF）管線整合**
- 影子觀察者標記的高不確定性步驟可作為偏好資料，用於未來微調弱代理。
- 形成「LEASH 監督 → 資料收集 → 弱代理改進 → 升級率下降」的自我改善迴圈。

**與多代理協作框架整合**
- 在多代理系統中，LEASH 可作為「升級協調者」，決定哪些子任務需升級至更強代理，避免每個代理各自呼叫前沿模型造成成本浪費。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）了解「為什麼需要弱到強升級」以及 LEASH 想解決的核心問題（成本 vs. 可靠性的取捨），再跳讀第 2 節（Related Work）認識 GUI 代理與模型路由的脈絡。技術細節可先略過，重點掌握「弱代理預設執行、不確定性高時升級、升級後弱代理轉為監督者」這個三層架構的概念圖（Figure 2）。

**給 AI 工程師**：重點閱讀第 3 節（Method）關於 Mahalanobis 距離評分、表示庫建構、以及「重用動作生成的激活值避免額外前向傳遞」的實作巧思。實作時可直接參考第 4 節（Experiments）的骨幹模型選擇（Qwen3.5-35B-A3B、UI-TARS 等）與超參數設定，並以 OSWorld 作為標準化驗證環境。建議優先實作步驟級升級層，再逐步加入初始路由與影子監督。

**給研究者**：第 3 節中將 W2SE 形式化為「預算受限的序列停止問題」並以失敗風險作為升級預期效益的代理指標，是本文的理論核心，值得仔細推導。表示庫與 Mahalanobis 評分的設計可進一步延伸至其他領域（如程式碼生成、機器人控制）的弱到強升級。建議探索的方向包括：多模態表徵的擴展、表示庫的線上更新機制、以及與過程獎勵模型（PRM）的結合。

**給產品經理**：重點關注第 4 節的實驗結果與成本數據：LEASH 在匹配升級率下比隨機升級提升 6.55–11.94 點、回收 75–102% 的升級差距、成本僅為 always-on 強代理的 69–81%。以 Qwen3.5-35B-A3B 為例，每任務成本 $0.4117 即可達到 73.66% 成功率，與 always-on Claude Opus 5 相當但省 19.2%。這些數字可直接用於 ROI 評估與產品定價決策。部署時建議先以內部工具試點，累積 3–6 個月資料後再評估對外服務的可行性。
