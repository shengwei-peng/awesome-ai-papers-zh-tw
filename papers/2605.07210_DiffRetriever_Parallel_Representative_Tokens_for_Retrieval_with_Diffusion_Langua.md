# DiffRetriever：用於檢索的平行代表性標記（基於擴散語言模型）

## ⚡ TL;DR

現有LLM檢索器受限於單一表示或自回歸序列生成成本，未善用擴散語言模型的遮蔽位置預測介面。
DiffRetriever於提示後附加K個遮蔽位置，單次雙向傳遞並行產生多表示，支援稠密與稀疏檢索。
BEIR-7上超越PromptReps等基線，多標記擴散版顯著優於單標記，延遲不隨K成長。

## 摘要翻譯

PromptReps 顯示，自回歸語言模型（Autoregressive Language Models）可直接作為檢索器（Retriever）使用，透過提示（Prompt）其生成查詢（Query）或段落（Passage）的稠密表示（Dense Representations）與稀疏表示（Sparse Representations）。將此延伸至多個代表性標記（Representative Tokens）時，自回歸模型效率不佳，因為標記必須依序生成（Sequential Generation），且先前的多標記（Multi-token）變體相較於單標記解碼（Single-token Decoding）並未帶來穩定的提升。我們證明瓶頸在於序列生成，而非多標記概念本身。DiffRetriever 是一個用於擴散語言模型（Diffusion Language Models, DLMs）的代表性標記檢索器：其在提示中附加 K 個遮蔽位置（Masked Positions），並在單次雙向前向傳遞（Bidirectional Forward Pass）中讀取全部 K 個位置。在域內評估（In-domain Evaluation）與域外評估（Out-of-domain Evaluation）中，多標記 DiffRetriever 在我們所測試的每個擴散骨幹網路（Backbone）上皆大幅優於單標記版本，而自回歸多標記則表現持平或下降，且其延遲（Latency）成本隨 K 增長，而擴散模型則無此隨 K 增長的延遲成本。經監督式微調（Supervised Fine-Tuning, SFT）後，基於 Dream 的 DiffRetriever 是我們比較中最強的 BEIR-7 檢索器，優於 PromptReps、相同擴散骨幹上的編碼器風格（Encoder-style）DiffEmbed 基線，以及對比式微調（Contrastive Fine-Tuning）的單向量檢索（Single-vector Retrieval）模型 RepLLaMA。在凍結基礎模型（Frozen Base Model）上的每查詢最佳化（Per-query Oracle）於相同固定預算（Fixed Budget）下超越對比式微調，指出自適應預算選擇（Adaptive Budget Selection）可作為未來研究方向。程式碼公開於 https://github.com/ielab/diffretriever。

### 核心貢獻（3～5點）
- **釐清瓶頸所在**：指出 PromptReps 多標記變體效能不佳的根本原因在於自回歸模型的序列生成限制，而非多標記概念本身的缺陷。
- **提出平行檢索架構**：設計 DiffRetriever，於提示中附加 K 個遮蔽位置，並透過單次雙向前向傳遞同時讀取所有 K 個代表性標記，徹底免除序列生成的延遲負擔。
- **全面實驗驗證**：在多個擴散語言模型骨幹上證實多標記 DiffRetriever 一致且大幅優於單標記版本，且其延遲不隨 K 增長，與自回歸多標記形成鮮明對比。
- **刷新 BEIR-7 基準**：經監督式微調後，基於 Dream 的 DiffRetriever 超越 PromptReps、DiffEmbed 及 RepLLaMA 等強基線，成為該基準上表現最佳的檢索器。
- **開啟新研究方向**：揭示在凍結基礎模型上進行每查詢最佳化即可超越對比式微調，凸顯自適應預算選擇作為後續研究方向的潛力。

### 適合對象
從事資訊檢索、神經表示學習、擴散語言模型應用及高效推論研究的學者與工程師；尤其適合關注檢索系統中效率與品質的權衡、雙向注意力（Bidirectional Attention）機制、以及非自回歸生成模型於下游任務應用之研究人員，亦適合對比學習與稠密／稀疏表示（Multi-representation Retrieval）領域的實務開發者參考。

## 深度分析

#### 方法論解析

DiffRetriever 的核心方法論建立在對擴散語言模型（Diffusion Language Models, DLMs）介面特性的精準利用之上。傳統自回歸語言模型（Autoregressive Language Models）受限於由左至右（left-to-right）的序列生成（sequential generation）特性，每個標記必須依序產出；而 DLMs（如 Dream、LLaDA）採用遮蔽位置預測（masked-position prediction）介面，預先配置多個遮蔽位置（masked positions），透過雙向注意力（bidirectional attention）進行聯合預測。

**檢索提示設計（Retrieval Prompt Design）**

DiffRetriever 對查詢（query）與段落（passage）採用對稱的提示（prompt）格式。以查詢為例，提示結構為：「[Query] The words are "[MASK]₁ [MASK]₂ … [MASK]_{Kq}"」，後接固定的後綴標記 [EOT] [EOS]。段落端則使用類似的格式，但將 [Query] 替換為 [Passage]，並配置 Kp 個遮蔽位置。這種設計的關鍵在於：所有 K 個遮蔽位置在單次前向傳遞（forward pass）中被同時讀取，產生 K 個隱藏狀態（hidden states）作為稠密表示（dense representations），以及 K 個下一標記對數機率向量（next-token logit vectors）作為稀疏表示（sparse representations）。

**評分機制（Scoring Mechanism）**

DiffRetriever 採用混合評分策略，整合兩種訊號：

1. **稠密評分（Dense Score）**：採用 ColBERT 風格的 MaxSim（最大相似度）機制，計算每個查詢表示與每個段落表示之間的最大相似度，再進行總和。這實現了細粒度的晚期交互（late interaction），允許查詢與段落之間的標記級匹配。

2. **稀疏評分（Sparse Score）**：對遮蔽位置的對數機率向量進行最大池化（max-pooled），產生類似詞彙權重的稀疏表示。

3. **混合評分（Hybrid Score）**：將稠密與稀疏評分進行插值（interpolation），用於最終排序。

**與 PromptReps 的根本差異**

PromptReps 在自回歸骨幹上生成檢索表示時，必須依序解碼（sequential decoding）每個標記，因此牆鐘時間編碼成本（wall-clock encoding cost）隨生成數量線性增長。DiffRetriever 則預先配置 K 個遮蔽位置，從單次前向傳遞中平行讀取，延遲（latency）幾乎不隨 K 增加而上升。這一介面差異是本文論證的核心：多表示檢索（multi-representation retrieval）本身並非無效，而是自回歸介面不適合高效產生多個表示。

**單標記 vs. 多標記設定**

當 K=1 時，DiffRetriever 退化为單表示設定；當 K>1 時則進入多表示設定。值得注意的是，即使在 K=1 的情況下，DiffRetriever 仍優於同骨幹的 DiffEmbed 基線，這證明了直接使用遮蔽位置預測介面的價值，而非僅僅是多表示帶來的增益。

#### 實驗數據解讀

**整體效能表現**

根據摘要與正文描述，DiffRetriever 在多個評測基準上展現出顯著優勢：

- **域內評估（In-domain Evaluation）**：在 MS MARCO dev 上表現優異
- **域外評估（Out-of-domain Evaluation）**：在 TREC DL 19/20 與 BEIR-7 上均取得最佳聚合效能
- **微調後表現**：經監督式微調（Supervised Fine-Tuning, SFT）後，基於 Dream 骨幹的 DiffRetriever 成為其比較範圍內最強的 BEIR-7 檢索器

**關鍵實驗發現**

1. **多標記增益的一致性**：在所有測試的擴散骨幹上，多標記 DiffRetriever 均實質性地優於單標記版本。這與自回歸多標記設定形成鮮明對比——後者在多數情況下表現持平或下降，同時承受隨 K 線性增長的延遲成本。

2. **介面決定的效能差距**：即使在零樣本（zero-shot）與微調（fine-tuned）評估中，僅使用單一遮蔽位置的 DiffRetriever 已優於同骨幹的 DiffEmbed。這表明效能差距主要來自介面選擇，而非僅僅是模型規模或訓練資料的差異。

3. **每查詢最佳化（Per-query Oracle）分析**：在凍結基礎模型（frozen base model）上，為每筆查詢選擇最佳遮蔽標記數量所獲得的效能，超過了在相同固定預算（fixed budget）下的對比式微調（contrastive fine-tuning）。這一發現具有重要意義：它暗示自適應預算選擇（adaptive budget selection）可能比均勻增加表示數量更為有效。

4. **消融分析（Ablation）**：研究分離了多遮蔽位置表示與 ColBERT 風格 MaxSim 評分的各自貢獻。結果顯示：即使僅進行平均池化（mean-pooled），多表示仍帶來增益；而 MaxSim 評分進一步提升效能。

**遮蔽標記數量的影響**

研究發現，從訓練資料中得出的最佳 K 值能夠良好地遷移至不同資料集。然而，每查詢分析顯示，根據查詢特性動態選擇 K 值可獲得顯著增益。簡單特徵如查詢長度與熵（entropy）與此變異相關，這為自適應遮蔽位置預測提供了實證基礎。

#### 與現有研究的比較

**與 PromptReps 的比較**

PromptReps（Zhuang et al., 2024）是本文最直接的對比對象。兩者皆採用提示式方法讓語言模型生成檢索表示，但 PromptReps 在自回歸骨幹上運作，必須依序解碼。PromptReps 曾探索多表示變體，但未發現可靠的效能增益。本文論證這並非多表示概念本身的問題，而是自回歸介面的限制。DiffRetriever 在相同的多表示概念下，透過 DLM 介面實現了穩定的效能提升，且無額外的延遲成本。

**與 DiffEmbed 的比較**

DiffEmbed（Zhang et al., 2025a）將 DLM 視為類似 BERT 的編碼器，產生單一平均池化向量。DiffRetriever 直接利用遮蔽位置預測介面，即使在 K=1 時也已優於 DiffEmbed。這凸顯了「使用模型被訓練執行的介面」這一原則的重要性。

**與 RepLLaMA 的比較**

RepLLaMA（Ma et al., 2024）是經對比式微調的單向量檢索模型，代表了 LLM 檢索的主流範式。DiffRetriever 在微調後於 BEIR-7 上超越 RepLLaMA，顯示多表示 + 晚期交互的策略在 DLM 上能夠超越強大的單向量對比學習基線。

**與 ColBERT 的比較**

ColBERT（Khattab and Zaharia, 2020; Santhanam et al., 2022b）是基於 BERT 的多表示檢索經典方法，證明了細粒度匹配相較單表示的優勢。DiffRetriever 將此理念移植至 LLM 規模的檢索，但透過 DLM 介面避免了自回歸多表示的效率問題。

**與其他 DLM 檢索方法的比較**

- **pplx-embed**（Eslami et al., 2026）：同樣將 DLM 視為編碼器，產生單一向量，未利用遮蔽位置預測介面。
- **DiffuRank**（Liu et al., 2026）：使用擴散似然（diffusion likelihood）對第一階段檢索的候選進行重排序（reranking），而非作為第一階段檢索器。

**局限性（Limitations）**

1. **骨幹依賴性**：效能依賴於 DLM 的品質，目前可用的高品質 DLM 數量有限。
2. **固定預算的次優性**：每查詢最佳化分析顯示，固定 K 值並非最優，自適應機制尚未實現。
3. **比較範圍**：摘要聲稱「在我們的比較範圍內」最強，未必涵蓋所有可能的檢索方法。
4. **訓練成本**：雖然推論效率高，但 SFT 仍需標準的對比學習訓練流程。

## 論文問答

**Q1：現有的自回歸 LLM 檢索器在多表示設定下為何無法穩定提升檢索效能？**
A：自回歸語言模型（如 PromptReps）必須依序由左至右生成代表性標記，每多生成一個標記就需要額外一次前向傳遞，因此延遲成本隨標記數 K 線性成長。更關鍵的是，先前研究（如 Zhuang et al., 2024）嘗試多標記變體時，發現相較於單標記解碼並未帶來可靠的效能提升，這使得「多表示檢索對 LLM 是否有用」成為一個開放問題。本文的核心論點是：瓶頸在於自回歸的序列生成介面，而非多表示這個想法本身——因為 ColBERT 等 BERT 式模型已證實多表示能帶來實質效益。

**Q2：擴散語言模型（DLMs）與自回歸語言模型在檢索應用上的根本差異是什麼？**
A：自回歸語言模型嚴格由左至右逐標記生成，每個標記的產生都依賴前一個標記的結果，因此多個檢索表示必須序列化產出。相對地，擴散語言模型（如 Dream、LLaDA）採用遮蔽位置預測介面，預先配置多個遮蔽位置後，可在單一雙向注意力前向傳遞中聯合預測所有位置。這種平行預測能力使得 K 個代表性標記的編碼成本幾乎與單一標記相同，為多表示檢索提供了天然的效率優勢。

**Q3：為什麼現有的 DLM 檢索方法（如 DiffEmbed）未能充分利用 DLM 的特性？**
A：現有方法如 DiffEmbed 和 pplx-embed 將 DLM 視為類似 BERT 的編碼器，僅從雙向隱藏狀態中產生單一平均池化向量進行相似度評分。這種做法完全繞過了 DLM 訓練時所執行的遮蔽位置預測任務，等於把 DLM 降級為通用編碼器使用。本文實驗顯示，即使僅使用單一遮蔽位置，DiffRetriever 仍優於相同骨幹網路上的 DiffEmbed，證明直接利用遮蔽位置預測介面本身就具有價值，更遑論多表示帶來的進一步增益。

**Q4：DiffRetriever 的核心機制是什麼？它如何利用遮蔽位置預測介面？**
A：DiffRetriever 對每個查詢或段落套用檢索提示，並在提示末尾附加 K 個遮蔽位置（K=1 為單表示，K>1 為多表示）。這些遮蔽位置在單一雙向前向傳遞中被聯合預測，每個位置同時產生一個隱藏狀態（用於稠密檢索）和一個下一標記的 logits 向量（用於稀疏檢索）。由於所有 K 個位置共享同一次前向傳遞的計算，編碼成本不會隨 K 線性增加，這正是相較於自回歸多標記檢索的關鍵效率優勢。

**Q5：DiffRetriever 如何同時支援稠密、稀疏和混合檢索？**
A：對於稠密檢索，DiffRetriever 從 K 個遮蔽位置取出 K 個隱藏狀態向量，並透過 ColBERT 風格的 MaxSim 進行查詢與段落間的細粒度匹配。對於稀疏檢索，它從相同 K 個位置取出 K 個 logits 向量並進行最大池化（max-pooling），得到類似詞彙權重的稀疏表示。最後，系統將稠密分數與稀疏分數進行混合插值以產生最終排序，使 DiffRetriever 能靈活適應不同檢索需求。

**Q6：為什麼選擇 ColBERT 風格的 MaxSim 評分？這種設計選擇帶來什麼優勢？**
A：ColBERT 風格的 MaxSim 透過查詢與段落標記間的最大相似度匹配實現細粒度互動，比單向量平均池化更能捕捉局部語義對齊。本文消融研究也證實，即使僅使用平均池化，多表示本身已能帶來增益，而 MaxSim 評分則進一步強化了效果。這種設計借鑑了 ColBERT 在 BERT 式模型上已被驗證的成功經驗，同時結合 DLM 的平行預測優勢，使 LLM 檢索器首次能以低成本享受延遲互動的好處。

**Q7：DiffRetriever 在哪些基準測試集上進行了評估？**
A：本文在域內評估使用了 MS MARCO dev 和 TREC DL 19/20 兩個資料集，並在域外評估採用 BEIR-7 基準測試集，涵蓋多個不同領域的檢索任務以驗證泛化能力。這樣的評估設計同時兼顧了訓練分布內的效能與跨領域的遷移能力，是現代資訊檢索研究的標準做法。透過在這三類測試集上的系統性比較，能全面反映 DiffRetriever 相對於既有方法的優勢與穩健性。

**Q8：DiffRetriever 的關鍵實驗結果是什麼？它與哪些基線比較？**
A：在零樣本與微調後的評估中，DiffRetriever 在所有測試的擴散骨幹網路上，多標記設定都大幅優於單標記設定，而自回歸多標記則持平或下降且付出隨 K 線性成長的延遲代價。經監督式微調後，基於 Dream 的 DiffRetriever 在 BEIR-7 上成為其比較中最強的檢索器，超越了 PromptReps、相同擴散骨幹上的 DiffEmbed 基線，以及對比式微調的單向量 RepLLaMA。這些結果證明了 DLM 介面與多表示策略的雙重價值。

**Q9：消融研究揭示了哪些關於多表示和 MaxSim 評分貢獻的洞見？**
A：消融實驗將多表示的效益與 MaxSim 評分的效益分離檢驗，結果顯示即使僅使用平均池化，多表示本身仍能帶來效能提升，而 MaxSim 評分則在此基礎上再增添額外增益。這意味著兩種機制各自獨立貢獻價值，組合使用時效果最佳。此外，研究還發現從訓練資料得出的最佳遮蔽標記數能良好地遷移到其他資料集，但每筆查詢的最佳標記數存在顯著差異，這為自適應預算選擇提供了實證基礎。

**Q10：DiffRetriever 在實際產品部署中可能面臨哪些考量？**
A：在實際部署中，DiffRetriever 的主要優勢在於編碼成本不隨表示數 K 線性成長，這對於需要大規模索引的場景特別有利，因為段落索引可以一次性以高 K 值編碼。然而，部署時仍需考量擴散語言模型本身的推論成本（目前仍高於成熟的編碼器模型）、索引儲存空間（K 個向量會增加儲存需求），以及混合評分中稠密與稀疏權重的調校。對於延遲敏感的即時查詢應用，DiffRetriever 的單次前向傳遞特性使其比自回歸多標記方案更具競爭力。

**Q11：DiffRetriever 對於不同規模的擴散語言模型骨幹網路的適用性如何？**
A：本文在多個擴散骨幹網路上測試 DiffRetriever，結果顯示多標記設定在所有測試骨幹上都帶來實質改善，顯示該方法對骨幹規模具有一定的通用性。雖然論文未深入探討極小或極大模型的行為邊界，但 DLM 的遮蔽位置預測介面是這類模型的共同特徵，原則上 DiffRetriever 可應用於任何支援此介面的擴散語言模型。隨著 DLM 生態（如 Dream、LLaDA 等）持續發展，DiffRetriever 的適用範圍也將隨之擴大。

**Q12：DiffRetriever 對資訊檢索領域的更廣泛影響是什麼？**
A：DiffRetriever 的核心貢獻在於揭示了「介面決定 LLM 檢索成敗」這項洞見，挑戰了過去認為多表示對 LLM 檢索無效的結論。這促使研究者重新審視自回歸架構在檢索任務上的根本限制，並為基於新興架構（如擴散模型）的檢索方法開闢了道路。同時，論文中關於自適應預算選擇的發現（每查詢最佳標記數差異顯著）也指出了未來個人化檢索的潛力，可能影響下一代檢索系統的設計典範。

**Q13：DiffRetriever 的主要限制是什麼？**
A：本文坦誠指出的一項主要限制是：雖然固定預算的 DiffRetriever 已很強大，但在凍結基礎模型上的每查詢最佳化（oracle）效能竟超越對比式微調，這意味著固定 K 值並非最優策略。此外，DiffRetriever 依賴擴散語言模型作為骨幹，而目前高效、可部署的 DLM 選項仍不如自回歸模型成熟，這在短期內可能限制其工業落地。論文中也未深入探討極長查詢或極短段落的極端案例，這些都是值得未來研究的方向。

**Q14：在哪些情境下 DiffRetriever 可能表現不佳？**
A：當查詢極短（如單字查詢）或資訊密度極低時，K 個遮蔽位置可能產生冗餘表示，反而稀釋語義訊號。此外，若擴散語言模型骨幹在特定領域（如高度專業的醫學或法律文本）未經充分預訓練，遮蔽位置預測的品質可能下降，進而影響檢索效能。對於需要極低延遲的邊緣部署場景，雖然 DiffRetriever 比自回歸多標記更高效，但 DLM 本身的雙向注意力計算成本仍可能成為瓶頸。

**Q15：未來的研究方向有哪些？特別是關於自適應預算選擇？**
A：本文最明確指出的未來方向是自適應預算選擇——根據每筆查詢的特性動態決定 K 值，而非使用固定預算。論文發現簡單特徵如查詢長度與熵值與最佳 K 值具有相關性，這為實作輕量級預測器提供了線索。更宏觀地，未來工作可探索將 DiffRetriever 與其他 DLM 檢索方法（如 DiffuRank 的重排序）結合、應用於更大規模的 DLM 骨幹，以及將此平行表示策略推廣到生成式檢索或文件摘要等任務。

## 實務應用指南

### 適用場景

**1. 大規模企業知識庫與技術文件搜尋**
企業內部累積大量技術文件、API 文件、產品手冊時，傳統關鍵字搜尋難以處理同義詞與長語意查詢。DiffRetriever 的多表示稠密+稀疏混合評分能同時捕捉精確詞彙匹配（透過稀疏 logits）與語意相似度（透過 MaxSim），特別適合工程師以自然語言查詢「如何在 Kubernetes 中設定 HPA 自動擴縮」這類需要語意理解的問題。

**2. 客服與工單檢索系統**
客服系統需要在數十萬筆歷史工單中找出與當前問題最相關的解決方案。DiffRetriever 在 BEIR-7 上展現的域外泛化能力（out-of-domain evaluation）使其特別適合處理新產品線、新政策帶來的新領域查詢，無需為每個新領域重新訓練。

**3. 法律與醫療專業文件檢索**
法律判決書、醫學文獻等專業領域文件具有長上下文、專業術語密集的特性。DiffRetriever 的多標記表示能對長段落做更細粒度的匹配（ColBERT-style MaxSim），比單向量編碼更能區分不同段落對查詢的不同相關程度。

**4. 程式碼與技術問答平台（如 Stack Overflow 風格）**
程式碼問答常涉及精確的 API 名稱、錯誤訊息字串，稀疏表示能精準匹配這些字面元素；同時語意稠密表示能處理「如何非同步執行」這類概念性查詢。混合評分對此特別有效。

**5. 多語言或跨語言文件檢索管線**
雖然本文主要在英文 BEIR-7 上評估，但 DLM 骨幹（如 Dream、LLaDA）原生支援多語言。可作為跨語言檢索的第一階段檢索器，搭配 reranker 提升品質。

### 實作前置條件

**資料需求**
- **訓練資料**：若要進行監督式微調，需要類似 MS MARCO 的（查詢, 正例段落, 負例段落）三元組資料。論文中使用對比式微調目標。
- **領域語料**：用於建立段落索引的目標領域文件集合（建議至少數萬至數百萬段落）。
- **評測資料**：BEIR-7 子集（如 FiQA、Scifact、HotpotQA 等）作為域外泛化能力的驗證基準。

**計算資源需求**
- **GPU**：建議至少一張 A100 80GB 或 H100 用於微調 7B 級 DLM 骨幹；推論階段單張 A6000 即可處理中等規模批次。
- **記憶體**：多標記設定（K=8 或更大）會增加 hidden state 儲存成本，索引 100 萬段落約需數十 GB 記憶體。
- **儲存**：段落索引需儲存每個段落 K 個稠密向量與稀疏 logits，預估為單向量索引的 K 倍。

**技能前提**
- 熟悉 Hugging Face Transformers 與 PyTorch 訓練流程。
- 理解 ColBERT 與 MaxSim 評分機制。
- 具備資訊檢索基礎（nDCG、MRR、BM25 等概念）。
- 對擴散語言模型的遮蔽位置預測介面有基本認識。

### 實作步驟建議

**步驟 1：環境與骨幹模型準備**
從 `github.com/ielab/diffretriever` 取得官方程式碼，安裝依賴（PyTorch、Transformers、ColBERT 索引工具如 PLAID 或 FAISS）。選擇 DLM 骨幹（Dream-Base/7B 或 LLaDA-8B），確認模型權重可取得。

**步驟 2：設計檢索提示模板**
依照論文中 Figure 2 的格式設計 prompt：
- 查詢端：`[Query] The words are " [MASK]₁ [MASK]₂ ... [MASK]_Kq " [EOT] [EOS]`
- 段落端：`[Passage] The words are " [MASK]₁ [MASK]₂ ... [MASK]_Kp " [EOT] [EOS]`
- 決定 Kq 與 Kp 的初始值（論文實驗顯示 K=4 至 K=8 通常是良好起點）。

**步驟 3：零樣本基線評估**
先用凍結的基礎模型（frozen base model）跑 BEIR-7 子集，確認多標記設定相對於單標記與 DiffEmbed 編碼式基線的提升幅度。這一步能驗證 pipeline 正確性，並決定是否需要微調。

**步驟 4：監督式對比微調**
若零樣本效果不敷需求，使用 MS MARCO 訓練集進行對比式微調：
- 採 hard negative mining 提升訓練訊號品質。
- 採用混合損失：稠密 MaxSim 損失 + 稀疏 logits 的 KL/BM25 風格損失。
- 監控 in-domain（MS MARCO dev）與 out-of-domain（BEIR-7）指標，避免過擬合。

**步驟 5：段落索引建置**
使用微調後模型對所有段落做一次前向傳遞，提取 K 個 MASK 位置的 hidden states（稠密）與 logits（稀疏）。使用 ColBERT 風格的 PLAID 索引儲存稠密向量，稀疏 logits 可用倒排索引或 SPLADE 風格工具。

**步驟 6：查詢端推論與混合評分**
對每筆查詢做單次前向傳遞取得 Kq 個表示，計算：
- 稠密分數：對所有候選段落做 MaxSim（每個查詢向量取與段落所有向量最大相似度的總和）。
- 稀疏分數：對 logits 做 max-pooling 後的詞彙權重與段落稀疏表示做內積。
- 混合分數：依驗證集調整稠密/稀疏權重（如 α·dense + (1-α)·sparse）。

**步驟 7：上線與監控**
部署為第一階段檢索器，搭配 cross-encoder reranker 提升 top-K 品質。監控延遲（DLM 的並行解碼優勢使 K 增加時延遲幾乎不變）、召回率與使用者點擊回饋。

### 潛在風險與注意事項

**風險 1：DLM 骨幹的生態系尚不成熟**
相較於成熟的 BERT/LLaMA 生態，Dream、LLaDA 等 DLM 的社群資源、預訓練變體、量化支援仍較少。緩解：密切追蹤 Hugging Face 上的 DLM 模型更新，準備 fallback 至 RepLLaMA 等成熟方案。

**風險 2：多標記預算 K 的選擇影響成本與效果**
K 過大會增加索引儲存與 MaxSim 計算成本；K 過小則失去多表示優勢。論文的 per-query oracle 顯示最佳 K 因查詢而異。緩解：先以訓練集驗證最佳 K，再依查詢長度或熵等特徵做簡單啟發式調整（adaptive budget selection 是論文指出的未來工作）。

**風險 3：微調資料偏置導致域外表現下降**
論文中 frozen base model 的 per-query oracle 在固定預算下超越對比式微調，暗示微調可能犧牲泛化換取 in-domain 表現。緩解：保留 frozen 版本作為 fallback；微調時加入 BEIR-7 風格的多領域資料做混合訓練。

**風險 4：稀疏 logits 的詞彙表覆蓋問題**
稀疏表示依賤模型詞彙表，若目標領域有大量專有名詞未被充分預訓練覆蓋，稀疏分數會失靈。緩解：監控稀疏評分的詞彙命中率，必要時以領域語料做持續預訓練（continual pretraining）。

**風險 5：長段落截斷導致表示不完整**
DLM 對輸入長度仍有上限（通常 2048 或 4096 tokens），長段落可能被截斷而失去關鍵內容。緩解：採用滑動視窗或階層式編碼（先切段再聚合）。

### 與其他技術的整合建議

**與 BM25 的整合**
DiffRetriever 的稀疏 logits 已具備詞彙匹配能力，可作為 BM25 的神經化替代或互補。實務上可採「BM25 召回 → DiffRetriever 重排」的兩階段管線，或以 hybrid score 統一評分。

**與 Cross-Encoder Reranker 的整合**
DiffRetriever 定位為第一階段檢索器，輸出 top-100 至 top-1000 候選段落。建議搭配如 monoT5、BGE-reranker 等 cross-encoder 做第二階段精排，能在 BEIR-7 上再提升 5-15 個 nDCG 點。

**與 ColBERT v2 / PLAID 的整合**
DiffRetriever 的多表示稠密檢索與 ColBERT 概念相通，可直接使用 ColBERT v2 的 PLAID 索引結構儲存 K 個 MASK 位置的 hidden states，降低工程重複成本。

**與 RAG 系統的整合**
作為 RAG（Retrieval-Augmented Generation）的檢索端，DiffRetriever 提供高品質段落給 LLM 生成器。特別適合搭配 DLM 生成器（如 Dream），形成端到端的擴散架構 RAG 系統。

**與向量資料庫的整合**
稠密向量部分可匯出至 Milvus、Qdrant、Weaviate 等向量資料庫；稀疏 logits 部分可整合至 Elasticsearch 倒排索引或 SPLADE 風格工具。建議以統一 API 封裝混合評分邏輯。

**與現有 LLM 推論服務的整合**
若組織已有 vLLM、TGI 等 LLM 推論服務，需確認其對 DLM 的支援程度。DLM 的並行解碼特性使其在 batch 推論時吞吐量可能優於自回歸模型，但需要框架層支援。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「為什麼需要檢索」與「BM25 vs. 向量檢索」的差異，再讀本文。重點掌握 Figure 2 的概念圖——理解「在 prompt 末尾加 MASK 標記，讓模型預測這些位置的表示」這個核心想法即可，不必深入數學細節。可先跑官方 Colab notebook 體驗零樣本效果，再決定是否深入。

**給 AI 工程師**：直接關注第 3 節 Method 與程式碼實作。特別注意：(1) K 值的選擇對延遲與效果的權衡；(2) 混合評分中稠密/稀疏權重的調參；(3) PLAID 索引的建置成本。建議在自有領域資料上做小規模 A/B 測試，比較 DiffRetriever 與現有 RepLLaMA 等單向量方案的 top-10 召回率。

**給研究者**：本文最值得深究的洞見是「多表示檢索在自回歸模型上失敗，是因為介面不對而非概念不對」。這對 DLM 時代的檢索研究有方法論啟發。建議延伸閱讀：(1) PromptReps 原論文以理解多表示失敗的原因；(2) ColBERT 系列以理解 MaxSim 的理論基礎；(3) Dream/LLaDA 論文以理解 DLM 的訓練目標。論文中 per-query oracle 超越微調的觀察，是 adaptive computation 與 retrieval 結合的有趣未來方向。

**給產品經理**：核心訊息是「擴散語言模型為檢索帶來新的成本-效果平衡點」。多標記檢索在自回歸模型上會線性增加延遲，但在 DLM 上幾乎免費，這對需要大規模多表示檢索的產品（如企業搜尋、客服系統）是重要利基。建議評估自家檢索系統的延遲瓶頸與 top-K 召回率痛點，若現有方案在多表示檢索上有興趣但被成本卡住，DiffRetriever 值得 POC 驗證。短期內生態系尚不成熟，建議以研究合作或小規模試點方式導入，而非全面替換現有系統。
