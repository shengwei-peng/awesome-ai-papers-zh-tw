## 摘要翻譯

我們提出 Miles v0.1，一套全端（full-stack）、生產級（production-level）的前沿規模後訓練（frontier post-training）系統。Miles 承襲 slime 的簡潔設計（clean design），並以單一原則貫穿強化學習（Reinforcement Learning, RL）訓練迴圈（training loop）的每個階段：各元件都應可驗證、簡潔且可客製化（verified, clean, and customizable）。Miles 以正確性（accuracy）、效率（efficiency）、可靠性（reliability）與可擴展性（scalability）為首要目標（first-class goals），旨在讓研究人員與企業都能輕易採用前沿規模強化學習。本報告以端到端（end-to-end）方式介紹整個系統：基於 SGLang 建構的 Rollout 引擎（rollout engines）、可選擇兩種訓練後端（training backend，NVIDIA Megatron-LM 與 PyTorch FSDP）的訓練器（trainer），以及適用於不同部署拓撲（deployment topologies）的三種權重同步傳輸機制（weight-synchronization transports）。除了全參數強化學習（full-parameter RL），Miles 亦支援 LoRA 強化學習（LoRA RL）、同策略蒸餾（on-policy distillation）、監督式微調（Supervised Fine-Tuning, SFT），以及真實同策略 Rollout-訓練對齊（true-on-policy rollout-training alignment），並將相同架構擴展至擴散模型（diffusion models）。最後，我們以一項端到端案例研究（end-to-end case study）作結：在 64 顆 NVIDIA GB300 GPU 上，針對 GLM-5.2 744B-A40B 模型於終端機程式設計任務（terminal-use coding tasks）執行全非同步智能代理強化學習（fully asynchronous agentic RL），前 30 個測量步驟（first 30 measured steps）的中位數步驟時間（median step time）為 263 秒。Miles 已於 https://github.com/radixark/miles 開源（open-sourced），專案網站（project website）為 https://miles.radixark.com。

### 核心貢獻（3～5點）
- 提出全端、生產級的前沿規模後訓練系統 Miles v0.1，以「可驗證、簡潔且可客製化」為核心設計原則，並將正確性、效率、可靠性與可擴展性列為首要目標。
- 建構靈活的 RL 訓練架構：採用 SGLang Rollout 引擎、支援 NVIDIA Megatron-LM 與 PyTorch FSDP 雙訓練後端，並提供三種權重同步傳輸機制以適應不同部署拓撲。
- 支援多樣化的後訓練範式，包括全參數 RL、LoRA RL、同策略蒸餾、監督式微調、真實同策略 Rollout-訓練對齊（TITO），並將架構擴展至擴散模型。
- 透過端到端案例研究驗證系統能力：在 64 顆 NVIDIA GB300 GPU 上，針對 GLM-5.2 744B-A40B 模型執行全非同步智能代理強化學習，前 30 個測量步驟的中位數步驟時間為 263 秒。
- 將 Miles 開源釋出，降低研究人員與企業採用前沿規模 RL 後訓練的門檻。

### 適合對象
本論文最適合從事大型語言模型後訓練、強化學習基礎建設與生產級訓練系統開發的研究人員與工程師閱讀；對於希望將前沿規模 RL 訓練落地於實際應用的企業技術團隊，以及關注 SGLang、Megatron-LM、FSDP、權重同步與 Agentic RL 系統設計的讀者，亦具高度參考價值。

## 深度分析

#### 方法論解析

Miles v0.1 的核心方法論是將「前沿規模後訓練（frontier post-training）」視為一個全端（full-stack）系統工程問題，而非單純的演算法改進。整個系統圍繞一個強化學習（RL）訓練迴圈（RL training loop）展開，並將正確性（accuracy）、效率（efficiency）、可靠性（reliability）與可擴展性（scalability）列為首要目標（first-class goals）。其設計原則可歸納為：每個元件都應該是「可驗證、簡潔且可客製化（verified, clean, and customizable）」。

##### 1. 三階段非同步 RL 迴圈

Miles 將訓練流程明確劃分為三個階段：

- **Rollout（軌跡生成）**：由 SGLang 引擎 fleet 負責根據當前策略（policy）生成軌跡（trajectory）。在智能代理強化學習（agentic RL）場景中，一個 rollout session 會與隔離環境（isolated environment）進行多輪（multiple turns）互動，模型可呼叫工具（tools），環境則回傳觀察與獎勵（reward）。
- **Training（訓練）**：訓練器（trainer）使用 NVIDIA Megatron-LM 或 PyTorch FSDP（Fully Sharded Data Parallel）作為訓練後端（training backend），消耗已完成的軌跡群組（trajectory group），計算 RL loss（如 GRPO、GSPO、PPO 等），並更新策略權重。
- **Weight update（權重更新）**：每完成一次訓練步驟，系統透過權重同步（weight synchronization）將新權重傳回 rollout 引擎，盡量不打斷正在進行中的生成。

為了避免「生成—等待—訓練—等待」的鎖步（lockstep）模式造成氣泡（bubbles）與閒置時間（idle time），Miles 提供**全非同步（fully asynchronous）模式**：rollout 引擎持續生成軌跡，同時 trainer 在另一批資料上進行運算，兩者可平行推進。這是提升端到端硬體利用率（end-to-end hardware utilization）的關鍵。

##### 2. 以 Trajectory Group 為資料單元

Miles 特別強調「軌跡群組（trajectory group）」的概念：同一提示（prompt）產生的多條軌跡必須被一起生成、一起緩衝、一起丟棄或一起消費。這是因為 GRPO 等目標需要將單條軌跡與同組其他軌跡進行相對評分。這種設計讓系統在排程與記憶體管理上以群組為單位，避免部分軌跡遺失導致梯度估計偏差。

##### 3. 吞吐量優化：Affinity Routing

在多輪 agentic RL 中，每一輪幾乎都會重複使用前幾輪的上下文。若 SGLang router 將下一輪請求導向不同引擎，新引擎就必須重新預填充（prefill）整段歷史，嚴重降低 rollout 吞吐量。Miles 採用 SGLang 的 key-based routing，對同一 session 的所有請求附加穩定的 routing key，確保：

- **Session-aware routing**：同一多輪 episode 的請求都送到持有其 KV cache 的引擎。
- **DP-rank-aware routing**：在啟用 DP attention 時，進一步將請求綁定到特定的資料平行（data-parallel）rank。

這種 cache-preserving binding 稱為 affinity，能讓每輪只需預填充新產生的後綴，是維持長對話軌跡生成效率的關鍵。

##### 4. 正確性與數值一致性：TITO 與 Exact Token IDs

Miles 將 rollout 引擎與訓練器之間的數值差距（numerical gap）視為可能「使目標失效（invalidate the objective）」的風險。為此，系統強調：

- **精確 Token ID（exact token ids）**：訓練器看到的是模型實際採樣出的 token，而非近似或重新生成的 token。
- **True-on-policy rollout-training alignment（TITO）**：透過 TITO session 確保 rollout 與訓練階段的策略一致，包含陳舊度（staleness）、取樣策略（sampling policy）與重播資料（replay data）的控制。
- **Expert routing replay**：對於混合專家模型（MoE），確保 rollout 與訓練時的專家路由一致，避免梯度與實際採樣行為脫鉤。

##### 5. 訓練後端與記憶體效率

Trainer 支援兩種後端：

- **NVIDIA Megatron-LM**：適合超大規模模型與 NVIDIA 生態系的最佳化。
- **PyTorch FSDP**：提供較高的彈性與社群相容性。

此外，Miles 支援低精度食譜（low-precision recipes）、記憶體效率最佳化，並可將最佳化器（optimizer）狀態卸載（offload）到 CPU 或 NVMe，以降低 GPU 記憶體壓力。

##### 6. 權重同步傳輸機制

針對不同部署拓撲（deployment topologies），Miles 提供三種權重同步傳輸機制（weight-synchronization transports）：

- **NCCL broadcast**：適合標準多 GPU / 多節點叢集。
- **P2P RDMA**：適合需要跨節點低延遲傳輸的場景。
- **CUDA IPC**：當 rollout 引擎與 trainer 共置（colocated）於同一節點時，可利用行程間通訊加速。

##### 7. 擴展後訓練範式

除了全參數強化學習（full-parameter RL），Miles 還支援：

- **LoRA RL**：僅更新低秩適應（Low-Rank Adaptation）參數，降低記憶體與通訊成本。
- **On-policy distillation（同策略蒸餾）**：在生成資料仍接近當前策略時進行知識蒸餾。
- **Supervised fine-tuning（SFT，監督式微調）**：作為 RL 前的基礎或交替階段。
- **擴散模型（diffusion models）後訓練**：將相同架構延伸至非自迴歸生成模型。

##### 8. 驗證覆蓋與程式碼品質

Miles 從兩個軸線定義「能否執行」：

- **Day-0 model support**：開箱即用的模型家族支援。
- **Multi-vendor hardware**：跨硬體廠商的可移植性。

程式碼組織上強調可驗證、簡潔且可客製化，讓研究人員與企業能根據需求修改特定元件，而不必重寫整個系統。

#### 實驗數據解讀

本報告的端到端案例研究（end-to-end case study）聚焦於：

- **模型**：GLM-5.2 744B-A40B（推測為總參數 744B、激活參數約 40B 的混合專家模型，MoE）。
- **任務**：終端機程式設計任務（terminal-use coding tasks），屬於多輪 agentic RL 場景。
- **硬體**：64 張 NVIDIA GB300 GPU。
- **關鍵指標**：前 30 個測量步驟（first 30 measured steps）的中位數步驟時間（median step time）為 **263 秒**（約 4.38 分鐘）。

##### 1. 指標意義

「中位數步驟時間」衡量的是從一個訓練步驟開始到下一個步驟開始之間的牆上時間，涵蓋了 rollout 生成、資料緩衝、trainer 計算、權重同步（weight synchronization）與任何排程延遲。263 秒對於一個 744B 級別的 MoE 模型、在多輪 agentic 環境中進行全非同步 RL 來說，顯示系統能夠維持相對穩定的端到端節奏，而非被最慢軌跡或權重傳輸拖垮。

##### 2. 數據限制

然而，報告中提供的實驗數據相當有限：

- 僅報告 **30 個步驟**，無法判斷長期穩定性、收斂行為或訓練動態。
- 未提供任何**任務正確率**（如 pass@1）、獎勵曲線、KL 散度、梯度規模或模型品質指標，因此無法評估 RL 目標是否真正學到更好的程式設計能力。
- 測量來自**單一配置**（one configuration），缺乏對不同批次大小、軌跡數量、精度格式或權重同步傳輸機制的消融實驗（ablation）。
- 未說明 263 秒中各階段（rollout / training / weight sync）的佔比，難以判斷瓶頸所在。

總體而言，這組數據主要證明 Miles 能在前沿規模硬體上「跑起來」且步驟時間穩定，但尚不足以證明其訓練效率或最終模型效能優於其他系統。

#### 與現有研究的比較

##### 1. 相對於 slime 與 SGLang

Miles 明確承襲 slime 的簡潔設計（clean design），但將其擴展為生產級（production-level）全端系統。SGLang 提供快速的推論引擎與 agentic 工作負載最佳化，Miles 則在其上加入 RL 訓練器、權重同步、軌跡群組管理與 TITO 對齊，將「快速推論」轉化為「高通量 RL 訓練」。

##### 2. 相對於其他 RL 後訓練框架

目前社群已有 OpenRLHF、TRL、veRL 等開源 RL 框架。Miles 的差異化在於：

- **雙訓練後端**：同時支援 Megatron-LM 與 PyTorch FSDP，讓使用者根據規模與生態系選擇。
- **三種權重同步傳輸機制**：針對不同部署拓撲提供 NCCL broadcast、P2P RDMA、CUDA IPC。
- **全非同步 agentic RL**：明確處理多輪、工具使用、外部環境的複雜 rollout，而非僅限單輪短生成。
- **TITO 與 exact token ids**：強調 rollout 與訓練之間的數值一致性，這在 MoE 與大規模模型中尤為關鍵。
- **擴散模型支援**：將架構延伸至 diffusion models，超越傳統 LLM RL 框架的範疇。

##### 3. 主要限制

報告本身也坦承若干限制：

- 部分**精度格式（precision formats）**仍處於早期階段，可能影響低精度訓練的穩定性與效能。
- 某些**權重傳輸路徑（weight-transfer paths）**僅覆蓋特定模型家族（model families），尚未達到通用。
- 測量結果來自單一配置，缺乏廣泛的硬體與模型消融。
- 未詳細說明多廠商硬體（multi-vendor hardware）的實際驗證範圍與效能數據。

#### 可重現性評估

##### 1. 開源釋出

Miles 已開源（open-sourced）於 GitHub（https://github.com/radixark/miles），並設有專案網站（https://miles.radixark.com）。原始碼可用性對於重現系統行為、理解實作細節與進行二次開發至關重要。

##### 2. 資料與模型權重

報告**未提及**使用的終端機程式設計任務資料集名稱，也未說明 GLM-5.2 744B-A40B 的模型權重是否公開。若該模型與資料集均為內部或商業資源，則端到端案例研究難以被外部研究者完全重現。

##### 3. 硬體門檻

案例研究使用 64 張 NVIDIA GB300 GPU，這屬於前沿級運算資源，絕大多數學術實驗室與中小型企業難以取得。因此，雖然程式碼開源，但大規模實驗的可重現性主要取決於讀者能否取得同等級硬體。

##### 4. 文件與驗證覆蓋

報告提到「day-0 model support」與「multi-vendor hardware」兩個驗證軸線，但尚未提供詳細的支援清單或自動化測試結果。若未來能釋出完整的模型支援矩陣、單元測試與基準腳本，將大幅提升可重現性與社群信任度。

#### 未來研究方向

基於 Miles v0.1 的設計與目前揭露的數據，以下幾個方向值得後續探索：

1. **長期訓練動態與收斂性研究**：在數百至數千步規模上測量獎勵、KL 散度、pass@1 等指標，驗證全非异步排程是否會因權重陳舊度（staleness）影響收斂。

2. **精度格式與記憶體最佳化**：完成 FP8、BF16/FP16 混合精度等食譜的驗證，並量化其對步驟時間與模型品質的影響。

3. **權重同步機制的系統性比較**：針對 NCCL broadcast、P2P RDMA、CUDA IPC 進行消融，分析在不同節點拓撲與模型大小下的延遲與吞吐量。

4. **跨硬體廠商驗證**：將 multi-vendor hardware 支援從設計目標轉化為可量測的基準，例如在非 NVIDIA GPU 或異質叢集上運行相同工作負載。

5. **LoRA RL 與全參數 RL 的效能對比**：評估 LoRA RL 在程式設計任務上的效果，以及其對記憶體、通訊與最終模型能力的權衡。

6. **擴散模型後訓練**：將 TITO 與 RL 目標應用於文字到圖像或影片生成，探索 diffusion models 的 reward modeling 與策略最佳化。

7. **動態排程與自適應軌跡長度**：針對 agentic 任務中軌跡長度差異大的問題，設計能動態平衡 rollout 與 training 負載的排程器。

8. **開放資料集與模型基準**：釋出可公開取得的 terminal-use coding tasks 子集與對應評估腳本，降低社群重現門檻。

9. **容錯與可靠性機制**：在大規模非同步系統中，單一引擎或環境失敗不應拖垮整個訓練任務，未來可加強檢查點、重試與彈性擴展能力。

10. **多模態與更複雜工具環境**：將 Miles 的 agentic RL 能力延伸至視覺、網頁瀏覽、資料庫操作等更豐富的外部環境。

## 論文問答

**Q1：Miles v0.1 主要想解決什麼問題？**
A：Miles v0.1 旨在解決前沿規模（frontier-scale）語言模型後訓練（post-training）所面臨的系統層級挑戰，特別是強化學習（RL）訓練迴圈在生成軌跡、更新策略與同步權重過程中的複雜性。傳統的生成後更新迴圈已無法應對現今多輪、使用工具、與外部環境互動的 agentic RL 場景，這些場景需要同時處理延遲敏感的 rollout 與吞吐量導向的訓練。Miles 的目標是提供一個生產級、全端且可擴展的系統，讓研究人員與企業都能夠進行大規模 RL 後訓練。

**Q2：現有方法為何難以應對前沿規模的 RL 後訓練？**
A：現有系統通常難以同時兼顧 rollout 的延遲需求與訓練的吞吐量需求，導致管線中出現大量氣泡（bubbles）與閒置時間，進而降低端到端硬體利用率。此外，rollout 引擎與訓練器之間的數值差距（numerical gap）可能大到足以讓 RL 目標失效，因為訓練器看到的軌跡可能與策略實際採樣的內容不一致。現有方法也缺乏對多輪 agentic 互動、兆參數 MoE 模型以及多種部署拓撲的完整支援，因此難以達到生產級的可靠性與可擴展性。

**Q3：為何生產級的後訓練系統對當前 AI 發展如此重要？**
A：後訓練是將預訓練語言模型轉化為實用系統的關鍵階段，而生產級系統能確保這個過程在正確性、效率、可靠性與可擴展性上都達到可部署的標準。隨著模型規模成長到兆參數等級，且 rollout 變得越來越長、越來越複雜，只有穩定的系統才能持續產生高品質的訓練資料與模型更新。Miles 讓前沿規模 RL 變得可及，不僅能加速研究進展，也讓企業能將 RL 後訓練整合到實際產品與服務中。

**Q4：Miles v0.1 的核心方法與整體架構是什麼？**
A：Miles 的核心架構由三個主要階段組成：rollout、training 與 weight update，形成一個持續運作的 RL 訓練迴圈。在 rollout 階段，SGLang 引擎負責生成軌跡，並透過 SGLang router 維持快取親和性（affinity）；在 training 階段，訓練器可選擇 NVIDIA Megatron-LM 或 PyTorch FSDP 作為後端，計算 GRPO、GSPO、PPO 等 RL 損失並更新策略。最後在 weight update 階段，系統透過 NCCL broadcast、P2P RDMA 或 CUDA IPC 將新權重同步回 rollout 引擎，並支援非同步模式以重疊生成與訓練。

**Q5：Miles 的關鍵創新有哪些？**
A：Miles 的關鍵創新之一是將每個訓練迴圈階段都圍繞「可驗證、簡潔且可客製化」的原則設計，並將正確性、效率、可靠性與可擴展性列為首要目標。另一項創新是支援 fully asynchronous agentic RL，讓 rollout 引擎在訓練器更新權重的同時持續生成軌跡，大幅減少硬體閒置。此外，Miles 還提出 true-on-policy rollout-training alignment（TITO）機制，確保訓練時使用的 token 與 rollout 引擎實際採樣的 token 完全一致，避免數值差距導致梯度錯誤。

**Q6：Miles 做了哪些設計選擇來同時確保正確性與效率？**
A：為了確保正確性，Miles 採用精確 token ID（exact token ids）記錄軌跡，並透過 TITO session 與 rollout routing replay 保持 rollout 與訓練之間的一致性，包括專家路由（expert routing）的完全一致。為了提升效率，Miles 使用 SGLang 的 key-based routing 實現 session-aware 與 DP-rank-aware 的 affinity，讓多輪 agentic rollout 能重複使用 KV cache，避免每次重新 prefill 完整歷史。同時，權重同步提供三種傳輸機制以適應不同部署拓撲，並可將最佳化器卸載至 CPU 或 NVMe，進一步提升記憶體效率。

**Q7：論文中進行了哪些實驗或測量？**
A：論文提供了一個端到端案例研究，使用 GLM-5.2 744B-A40B 模型在終端機程式設計任務上進行全非同步 agentic RL，部署於 64 張 NVIDIA GB300 GPU 上。該研究測量了前 30 個步驟的中位數步驟時間（median step time），結果為 263 秒。雖然論文也提及 Miles 支援多種後端、傳輸機制與訓練範式，但明確指出部分測量來自單一配置而非多種配置的廣泛比較。

**Q8：案例研究的主要結果是什麼？**
A：案例研究顯示，Miles 能夠在 64 張 NVIDIA GB300 GPU 上成功執行具有 744B 總參數與 40B 啟動參數的 GLM-5.2 模型的全非同步 agentic RL，前 30 個測量步驟的中位數步驟時間為 263 秒。這個結果證明了 Miles 在前沿規模模型上實現生產級 RL 訓練的可行性，並展現了其在硬體利用率與訓練吞吐量方面的實際表現。該案例也驗證了 Miles 在處理多輪、工具使用與外部環境互動等複雜 agentic 場景時的系統穩定性。

**Q9：論文是否提到消融研究或不同配置的比較？**
A：論文並未詳細呈現傳統意義上的消融研究，而是強調 Miles 在設計上支援多種後端與傳輸機制的靈活性，例如訓練器可選擇 Megatron-LM 或 FSDP，權重同步可選擇 NCCL broadcast、P2P RDMA 或 CUDA IPC。作者也坦承部分測量結果僅來自單一配置，而非經過多種設定的廣泛比較。因此，未來仍需要更多系統性的實驗來評估不同後端、傳輸機制與精度格式對端到端效能與正確性的影響。

**Q10：Miles 適用於哪些實際應用場景？**
A：Miles 特別適合需要大規模 RL 後訓練的應用，例如程式碼生成、數學推理、工具使用與多輪對話代理等 agentic 任務。由於它支援監督式微調（SFT）、全參數 RL、LoRA RL、同策略蒸餾（on-policy distillation）與真實同策略對齊（TITO），因此能夠覆蓋從初步對齊到進階強化的完整後訓練流程。此外，Miles 將架構延伸至擴散模型，也使其可應用於影像、影片或其他生成式模型的後訓練場景。

**Q11：Miles 的設計反映了哪些產品化考量？**
A：Miles 強調「生產級」設計，將可靠性、可維護性與可客製性視為核心，並以「可驗證、簡潔且可客製化」作為組織程式碼與系統模組的原則。系統支援多種訓練後端與權重同步傳輸機制，讓企業能根據自身硬體拓撲與模型家族選擇最適配置。此外，Miles 開源於 GitHub 並設有專案網站，降低了研究人員與工程團隊的採用門檻，有助於社群協作與實際部署。

**Q12：Miles 對 RL 後訓練領域可能帶來什麼影響？**
A：Miles 透過提供開源、全端且生產級的後訓練系統，有望降低前沿規模 RL 研究的進入門檻，讓更多研究機構與企業能夠複製與擴展相關工作。它在正確性與效率上的設計原則，特別是 TITO 與非同步調度，可能成為未來 RL 訓練系統的參考標準。此外，Miles 將相同架構延伸至擴散模型，也有助於推動 RL 後訓練在更多模態與應用領域的發展。

**Q13：Miles 承認了哪些限制？**
A：論文明確指出 Miles 仍存在一些限制，包括部分精度格式仍處於早期階段，可能尚未在所有後端與模型家族上達到最佳穩定性。此外，某些權重傳輸路徑僅涵蓋特定模型家族，限制了其在所有架構上的通用性。作者也坦承部分測量結果來自單一配置，因此尚無法全面代表系統在所有設定下的表現。

**Q14：Miles 在哪些情況下可能會失敗或表現不佳？**
A：如果部署的模型家族不在 Miles 目前支援的權重傳輸路徑範圍內，則可能無法正確完成權重同步，導致訓練中斷或數值不一致。在精度格式尚未成熟的配置下，也可能出現數值不穩定或損失發散的問題。此外，若使用者選擇的後端、傳輸機制與硬體拓撲之間搭配不當，例如共置節點未使用 CUDA IPC 而改用較慢的傳輸方式，則可能無法發揮 Miles 的最佳效能。

**Q15：Miles 未來有哪些可能的發展方向？**
A：未來 Miles 可能會擴展對更多精度格式的完整支援，並增加權重傳輸路徑以覆蓋更廣泛的模型家族。系統性的消融研究與多配置比較也有助於進一步驗證不同後端、傳輸機制與調度策略對端到端效能的影響。此外，隨著 agentic RL 與多模態後訓練的發展，Miles 可能會持續強化其在更長軌跡、更複雜環境以及擴散模型上的支援能力。

## 實務應用指南

### 適用場景

1. **大規模程式設計 Agent 的後訓練**  
   適合需要讓模型在終端機或 IDE 外掛中執行多輪工具呼叫（例如執行測試、讀取檔案、提交 patch）的場景。Miles 的全非同步 Agentic RL 與 SGLang 的 KV cache affinity 路由，能讓模型在長對話軌跡中保持高吞吐量，並透過 GRPO/GSPO 等目標持續優化策略。

2. **企業級客服或流程自動化 Agent**  
   當模型需要與外部 API、資料庫或沙箱環境互動，且每次對話可能長達數十輪時，可利用 Miles 的隔離環境、軌跡群組（trajectory group）取樣與權重同步機制，進行穩定的 on-policy 訓練，避免 rollout 與 trainer 之間的數值差距導致目標失效。

3. **兆參數 MoE 模型的領域適應**  
   針對法律、醫療、金融等領域的 GLM、Mixtral 或類似 MoE 架構，Miles 支援 Megatron-LM 與 FSDP 雙後端，並提供 LoRA RL、全參數 RL 與 SFT 的彈性組合，讓企業在有限記憶體預算下完成大模型後訓練。

4. **擴散模型的強化學習對齊**  
   Miles 將同樣的 RL 迴圈架構延伸至擴散模型，適合需要把文字到圖像／影片生成模型對齊到人類偏好或自訂獎勵函數的產品，例如廣告素材生成、設計輔助工具。

5. **真實同策略（TITO）的模型對齊與蒸餾**  
   適合對「rollout 與訓練必須完全一致」有嚴格要求的場景，例如安全對齊、模型能力蒸餾，或需要精確 token ids 與專家路由一致性的高風險應用。

### 實作前置條件

**資料與環境**
- 高品質提示資料集：每筆資料應能產生可評分的軌跡群組，並具備穩定的 reward / preference label。
- 可重現的隔離環境：每個 Agentic rollout 都需要沙箱化執行環境（container、VM 或受限 process），確保動作執行安全且 reward 計算一致。
- 獎勵函數與評估基準：需預先定義 reward、單元測試、人工偏好或自動評分器，並建立離線評估 pipeline。

**運算資源**
- 至少具備多節點 NVIDIA GPU 叢集（建議 H100/GB200/GB300 等級），並具備 NVLink 與 RDMA 網路以支援 NCCL broadcast 或 P2P RDMA 權重同步。
- 足夠的 CPU 記憶體與 NVMe 空間，用於 optimizer state offloading、replay buffer 與 checkpoint 儲存。
- 若使用全參數 RL，需確認模型家族與精度格式已受 Miles day-0 支援；若資源有限，建議先從 LoRA RL 開始。

**技術能力**
- 熟悉 PyTorch 分散式訓練，至少理解 FSDP 或 Megatron-LM 其一。
- 具備 SGLang 或類似 vLLM 推論框架的部署與調校經驗。
- 理解 RL 目標（GRPO、PPO）與 on-policy / off-policy 差異。
- 具備 NCCL、CUDA IPC、RDMA 等底層通訊除錯能力。

---

### 實作步驟建議

1. **確認模型與硬體覆蓋範圍**  
   先查閱 Miles 的 day-0 模型支援清單與多廠商硬體矩陣，確認目標模型家族、精度格式（FP8/BF16 等）與權重傳輸路徑可用。

2. **建立可評估的 Rollout 環境**  
   將業務任務封裝成沙箱化環境，定義 observation、action 與 reward。先以固定策略進行小規模 rollout，驗證環境穩定性與 reward 分布。

3. **選擇訓練後端與同步傳輸**  
   - 兆參數 MoE 或需要極致擴展性：選 NVIDIA Megatron-LM。  
   - 較小模型或已熟悉 PyTorch 生態：選 PyTorch FSDP。  
   - rollout 與 trainer 共置時使用 CUDA IPC；跨節點優先考慮 P2P RDMA；標準叢集使用 NCCL broadcast。

4. **從 SFT 或 LoRA RL 開始熱啟動**  
   先用監督式微調建立基礎能力，再切換到 LoRA RL 降低記憶體與通訊成本，最後視需求升級為全參數 RL。

5. **啟用 TITO 驗證數值一致性**  
   在關鍵實驗中啟用 true-on-policy rollout-training alignment，比對 rollout 引擎與 trainer 的 exact token ids 與專家路由，確保梯度來自真實策略。

6. **逐步開啟全非异步模式**  
   先以同步模式確認端到端正確性，再啟用全非异步 Agentic RL，監控中位數步驟時間、權重陳舊度（staleness）與硬體利用率。

7. **持續監控與迭代**  
   追蹤 reward hacking、KL 發散、訓練損失與離線評估指標，定期 checkpoint，並保留可回滾的模型版本。

### 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **Rollout 與 Trainer 數值不一致** | 推論與訓練使用不同 kernel 或精度，導致 token 機率或專家路由不一致，使 RL 目標失效。 | 啟用 TITO session、驗證 exact token ids、使用相同精度格式與 sampling policy。 |
| **KV cache 親和性喪失** | 路由器將同一 session 的不同輪次導向不同引擎，造成重複 prefill、吞吐量崩潰。 | 使用 SGLang key-based routing 的 session-aware / DP-rank-aware affinity。 |
| **權重陳舊度過高** | 全非异步模式下 trainer 與 rollout 並行，策略更新與生成策略版本差距過大。 | 設定 staleness 上限、監控 on-policy 比率、必要時降回半同步。 |
| **記憶體與通訊瓶頸** | 大模型全參數 RL 容易 OOM，權重同步也可能佔滿網路頻寬。 | 採用 LoRA RL、optimizer offloading 至 CPU/NVMe、選擇合適的 weight-synchronization transport。 |
| **Reward hacking 與環境安全** | Agent 可能找到捷徑騙取 reward，或在沙箱外執行危險動作。 | 設計多維度 reward、加入單元測試與人工審核、強化沙箱隔離與網路限制。 |
| **模型家族與精度支援限制** | 部分精度格式或權重傳輸路徑仍處早期階段，某些模型家族可能未完整支援。 | 參考 Miles 官方 day-0 支援清單，先在目標模型上跑小規模驗證。 |

### 與其他技術的整合建議

- **容器編排與 MLOps 平台**：透過 Kubernetes + Slurm 管理 SGLang engine fleet 與 trainer 節點，將 Miles 納入現有的實驗追蹤（MLflow、Weights & Biases）與模型註冊中心。
- **資料湖與特徵平台**：將 prompt 資料集、軌跡 replay 資料與 reward 標籤統一儲存於物件儲存或資料湖，支援版本控制與離線分析。
- **現有推論服務**：若產品已使用 SGLang 或 vLLM 提供線上推理，可共用同一套 SGLang router 與 engine 部署，降低額外基礎建設成本。
- **CI/CD 與評估管線**：將離線評估、單元測試與 safety guardrails 整合進訓練後的模型閘道，確保每次權重更新都經過自動化驗證。
- **可觀測性工具**：對 rollout 延遲、KV cache 命中率、訓練步驟時間、權重同步頻寬與 staleness 建立儀表板，快速定位端到端瓶頸。

### 給不同背景讀者的閱讀建議

**給初學者**  
建議先從本文件的「適用場景」與 glossary 開始，理解 prompt、trajectory、rollout、policy 等基本名詞，再搭配 Miles 官方網站的入門範例，建立「生成 → 訓練 → 權重同步」的整體概念，不必一開始就深入 NCCL 或 Megatron-LM 細節。

**給 AI 工程師**  
請重點閱讀第 2 至 4 節的 rollout 調度、trainer 後端選擇與權重同步機制，並參考 GLM-5.2 案例研究的配置參數。實作時優先處理 SGLang router affinity、精度格式一致性與非同步調度，這三項通常決定系統能否穩定運行。

**給研究人員**  
建議聚焦第 3 節的 RL 目標（GRPO、GSPO、PPO）、第 5 節的 LoRA RL / on-policy distillation / TITO，以及第 6 節擴散模型延伸。Miles 的價值在於把前沿演算法以可驗證、可重現的方式落地，適合用來驗證新的後訓練假設。

**給產品經理**  
請把重點放在「適用場景」與「實作前置條件」，評估業務問題是否適合用 Miles 解決、需要多少 GPU 與資料預算，以及預期達成的 latency 與步驟時間。與工程團隊討論時，可優先確認模型家族支援、reward 設計與沙箱安全策略。
