## ⚡ TL;DR

企業AI代理訓練受限於隱私法規，現有合成方法難兼顧結構有效性與分布保真度。
本文提出透過模擬合成（STS），讓LLM代理透過策略強制API生成資料，並設計通用填充器（GP）。
GP在十個環境中達到0.88平均邊緣保真度與100%約束滿足率，且無需資料庫架構。

## 摘要翻譯

工具呼叫代理 (Tool-calling agents) 已成為企業 AI (Enterprise AI) 的核心技術，但由於企業系統、資料與資料庫架構 (Database schemas) 受到商業與法律限制，其大規模訓練與評估仍嚴重受限。表格資料合成 (Tabular data synthesis) 提供了一種自然的替代方案，但其效能受到結構有效性 (Structural validity) 與架構可用性的根本限制；而程序式合成 (Procedure-based synthesis) 方法則呈現相反的弱點，通常因缺乏逐領域編寫 (per-domain authoring) 而難以達到分布保真度 (Distributional fidelity)。我們提出**透過模擬合成 (Synthesis Through Simulation, STS)**，一種**無架構 (Schema-free)** 的資料合成範式，由大語言模型代理 (LLM agent) 在模擬企業環境 (Simulated enterprise environments) 中，透過對策略強制 API (Policy-enforcing APIs) 執行操作來生成資料。由於資料是透過定義了有效性的同一環境生成，STS 在構造上保證結構有效性，同時將有效性強制執行 (Validity enforcement) 與分布建模 (Distribution modeling) 解耦 (Decoupling)，使兩者得以獨立處理。**通用填充器 (Generalist Populator, GP)**，即 STS 的領域無關 (Domain-agnostic) 代理，解決了分布保真度與合成可擴展性 (Synthesis scalability) 的其餘挑戰：GP 在*無資料庫架構存取權限*的情況下，於全部十個環境中達到平均 **0.88** 的邊緣保真度 (Marginal fidelity) 與 **100%** 的約束滿足率 (Constraint satisfaction)，然而統計型表格資料生成器 (Statistical tabular data generators) 因必要的種子資料需求而無法應用於其中七個環境；具架構權限代理 (Schema-privileged agents) 則因脆弱任務組合 (Brittle task composition)，在航空環境的緊耦合工作流程 (Tightly coupled workflows) 中，於 82% 的軌跡 (Trajectory) 中失敗。我們於 https://github.com/SAP/synthesis-through-simulation 開源完整框架、全十個環境及生成的資料集。

### 核心貢獻（4點）
- 提出 **STS 範式**：一種無架構的資料合成方法，透過讓大語言模型代理在模擬企業環境中對策略強制 API 執行動作來生成資料，於構造上保證結構有效性，並將有效性強制執行與分布建模解耦，使兩者可獨立優化。
- 提出 **通用填充器 (GP)**：STS 的領域無關代理，無需存取資料庫架構，即可在多個企業環境中兼顧分布保真度與合成可擴展性。
- **實驗驗證優勢**：GP 於全部十個環境中達到平均 0.88 的邊緣保真度與 100% 的約束滿足率；相較之下，統計型表格資料生成器因種子資料需求而無法適用於七個環境，具架構權限代理則在航空環境的緊耦合工作流程中於 82% 的軌跡失敗。
- **開源釋出**：公開完整框架、十個模擬企業環境及對應生成資料集，供後續研究與產業應用使用。

### 適合對象
從事企業 AI、工具呼叫代理、表格資料合成、大語言模型代理訓練與評估之研究者與工程師；特別適合關注資料隱私與合規要求、合成資料品質、代理系統設計，以及欲在缺乏真實企業資料情境下進行模型開發與基準測試的學術界與產業界人士。

## 深度分析

#### 方法論解析

本文提出之核心方法論可從三個層次進行拆解：**問題分解、範式設計、代理架構**。

**問題分解的三軸框架**

作者將企業資料合成（enterprise data synthesis）問題分解為三個正交軸：(1) 結構有效性（structural validity），即生成資料是否符合業務邏輯與關聯式約束；(2) 分布保真度（distributional fidelity），即生成資料的特徵值分布是否與真實資料的經驗分布（empirical distribution）吻合；(3) 合成可擴展性（synthesis scalability），即方法能否在不付出大量逐環境編寫（per-environment authoring）成本的前提下推廣至新領域。此分解的關鍵洞察在於：現有方法之所以失敗，是因為它們試圖在同一個機制中同時解決這三個問題，導致顧此失彼。例如統計型表格資料生成器（如 CTGAN、TabDDPM、GReaT）擅長分布保真度但無法強制結構有效性；程序式合成（procedure-based synthesis）能保證結構有效性但缺乏分布保真度且需要大量人工編寫約束編碼（constraint encodings）與工作流程腳本（workflow scripts）。

**STS 範式的設計原理**

透過模擬合成（Synthesis Through Simulation, STS）的核心設計原理極為精煉：**既然企業生產系統（production enterprise systems）的 API 層（API layer）已經強制執行所有業務邏輯，那麼讓代理透過這些策略強制 API（policy-enforcing APIs）來生成資料，結構有效性便由建構本身保證**。此原理的數學形式化體現於轉移函數 Ψ 的定義：當工具呼叫 a=(t,x) 滿足前置條件 ϕ_t(d,x)=1 時，狀態才會被更新；否則狀態保持不變。這意味著任何被 API 接受的軌跡（trajectory）必然產生一致的資料庫快照（database snapshots），從根本上消除了結構無效資料的可能性。

此設計的另一深層意涵在於**解耦（decoupling）**：將有效性強制執行（validity enforcement）完全委派給 API 層後，代理可專注於分布真實性的建模，無需同時學習「什麼是有效的」與「什麼是典型的」。這與程序式合成形成鮮明對比——後者將兩者編碼在同一組規則中，導致每新增一個領域都需重新編寫約束與抽樣規則（sampling rules）。

**通用填充器（Generalist Populator, GP）的設計**

GP 是 STS 範式的具體實作，其最引人注目的特性是**零編寫（zero-authoring）**：僅需存取原始工具註冊表（tool registry），即函數簽章與描述，便能在十個不同企業環境中運作，無需存取底層資料庫架構（database schemas）、手寫意圖庫、抽樣器或任何逐環境配置。這與具架構權限代理（schema-privileged agents）形成對比——後者雖擁有完整資訊，卻在航空環境的緊耦合工作流程（tightly coupled workflows）中因脆弱任務組合（brittle task composition）而於 82% 的軌跡上失敗。

GP 的運作機制可推測為：代理觀察工具描述，自主推斷呼叫順序與參數值，透過 API 的接受/拒絕回饋作為隱式獎勵信號，逐步學習如何產生既有效又具分布真實性的資料。此設計巧妙避開了冷啟動問題（cold-start problem）——統計型生成器在七個環境中因缺乏必要種子資料而無法適用，而 GP 完全不需要預填充資料庫（pre-populated database）作為起點。

**形式化定義的嚴謹性**

作者將企業環境定義為四元組 E=(D,T,Ψ,V)，其中 D 為資料庫狀態空間、T 為帶有輸入架構 σ_t 與前置條件 ϕ_t 的型別化工具註冊表、Ψ 為轉移函數、V 為 M 個程式化業務規則檢查的驗證套件。此形式化不僅清晰，且自然地將「工具註冊表是環境唯一介面」這一設計約束編碼進定義中——底層資料庫架構不可存取，這正是 STS「無架構（schema-free）」特性的形式化體現。

#### 實驗數據解讀

**核心量化結果**

GP 在十個企業環境中達成 **0.88 平均邊緣保真度（marginal fidelity）** 與 **100% 約束滿足率（constraint satisfaction）**，且無需存取資料庫架構。此結果的解讀需從兩個維度進行：

首先，**100% 約束滿足率**驗證了 STS 範式的核心承諾——結構有效性由建構本身保證。這並非統計意義上的近似達成，而是確定性結果：任何被 API 接受的軌跡必然通過所有業務規則檢查。此數據的對照組尤其值得注意：統計型合成器在七個環境中因必要種子資料需求而**完全不適用**；具架構權限代理在航空環境中於 82% 的軌跡上失敗。這凸顯了 STS 在結構有效性維度上的絕對優勢。

其次，**0.88 平均邊緣保真度**衡量的是生成資料的單變量分布與目標分布的吻合程度。在五個環境中此指標高於 0.93，顯示 GP 在多數環境中能產生統計上可信的資料。然而需注意，邊緣保真度僅捕捉單欄位分布，未直接衡量跨欄位關聯或時序一致性，這是後續可深入探討的面向。

**對照實驗的設計意涵**

作者明確區分了三類對手：(1) 統計型合成器（CTGAN、TabDDPM、GReaT），代表分布保真度導向的方法；(2) 程序式合成（IRG、Kamino），代表結構有效性導向的方法；(3) 環境合成系統（EnvScaler、ScaleEnv），代表代理軌跡導向的方法。表 1 的六軸比較（輸出類型、結構有效性、分布保真度、參考分布感知、零編寫、無架構）顯示 STS 是唯一在所有軸上皆滿足（✓）的系統，而其他系統至少在兩到三個軸上呈現部分（∼）或不滿足（×）。

**驗證套件的角色**

驗證套件 V={r_1,...,r_M} 中的 M 個程式化業務規則檢查提供了獨立的約束滿足度量測。與 τ-bench 使用 LLM 評判器（LLM judge）進行事後驗證不同，STS 的驗證是程式化的、可重現的、不受 LLM 偏誤影響的。這是方法論上的重要差異——τ-bench 的「通過」取決於評判模型的判斷，而 STS 的「通過」取決於確定性的規則評估。

**實驗結果的侷限性**

需坦誠指出，論文中未詳細披露：(1) 十個環境的具體領域組成；(2) 邊緣保真度的計算方法（KL 散度？Wasserstein 距離？）；(3) GP 使用的基礎 LLM 模型及其規模；(4) 軌跡長度分布與生成成本。這些資訊的缺乏使得結果的獨立驗證與跨研究比較存在困難。

#### 與現有研究的比較

**定位於三大文獻脈絡**

本文明確將自身定位於三個文獻脈絡的交匯處：(1) 表格資料合成（CTGAN、TabDDPM、GReaT、SDV）；(2) 代理式資料與環境合成（APIGen-MT、DiaFORGE、ASTRA、EnvScaler、ScaleEnv）；(3) 工具呼叫代理基準（AgentBench、WebArena、SWE-bench、τ-bench、TED、ReAct、Toolformer、ToolLLM）。此定位揭示了 STS 的獨特貢獻：**它是首個將「生成企業資料庫快照」作為主要交付物的系統**，而非生成代理訓練軌跡或評估代理能力。

**相較於統計型合成器的改進**

CTGAN、TabDDPM、GReaT 等方法的核心限制在於：(1) 將記錄視為獨立，無法強制關聯式約束（relational constraints）；(2) 需要大量預填充訓練語料庫（training corpus），在企業部署中因隱私法規（privacy regulations）與合規要求（compliance requirements）而無法取得種子資料；(3) 無法處理動態、依賴當前資料庫狀態的業務邏輯。SDV 雖透過條件化子表合成於父表外鍵來處理參考完整性，但仍無法強制需在寫入時對即時資料庫狀態進行檢查的程序性約束。STS 透過 API 層生成繞過了所有這些限制。

**相較於程序式合成的改進**

IRG 與 Kamino 等程序式方法雖能處理靜態宣告式約束（功能相依、拒絕約束等），但這些靜態約束編碼本質上不同於依賴當前資料庫狀態的動態 API 強制業務邏輯。更關鍵的是，程序式方法需要大量逐環境編寫——約束編碼、工作流程腳本、抽樣規則——其人力成本（human effort cost）隨環境數量線性增長，無法規模化。STS 的零編寫特性徹底消除了此瓶頸。

**相較於環境合成系統的改進**

EnvScaler 與 ScaleEnv 雖能從種子規格程式化擴展工具互動環境，但其目標是生成代理訓練軌跡而非企業資料庫快照，且未在寫入時強制 API 層業務規則。STS 則將「已填充的資料庫快照」視為主要交付物，這是根本性的範式轉變。

**相較於 τ-bench 的差異**

τ-bench 與 STS 共享企業領域焦點與策略約束設定，但兩者在本質上不同：τ-bench 使用事後 LLM 評判器驗證最終狀態是否符合自然語言策略，而 STS 在 API 層以程式化方式強制執行約束；τ-bench 的交付物是代理的通過/失敗分數，而 STS 的交付物是已填充的資料庫快照本身。此差異使 STS 更適合用於代理訓練資料生成，而 τ-bench 更適合用於代理能力評估。

**現有方法的侷限性**

儘管 STS 展現顯著優勢，仍存在以下侷限：(1) 邊緣保真度 0.88 雖高，但未達統計型合成器在有充足種子資料時的水準；(2) 對 API 設計品質的依賴——若 API 本身存在漏洞或不一致，STS 無法自動修正；(3) 對 LLM 代理能力的依賴——若基礎模型推理能力不足，代理可能無法有效探索工具組合空間；(4) 缺乏對時序一致性與跨記錄關聯的明確評估指標。

#### 可重現性評估

**開源承諾的完整性**

作者明確聲明開源釋出**完整框架、所有十個環境、以及生成的資料集**，並提供 GitHub 連結（https://github.com/SAP/synthesis-through-simulation）。此開源承諾涵蓋了可重現性的三大支柱：程式碼、測試環境、與資料產出。

**可重現性的優勢面向**

從正面來看：(1) 十個企業環境的釋出使研究者能在相同基準上比較不同方法；(2) 完整框架的開源允許研究者修改 GP 的內部機制並測試變體；(3) 生成資料集的釋出使下游任務（如代理訓練）的重現成為可能；(4) SAP 的企業背景為環境的真實性提供了一定程度的可信度保證。

**可重現性的潛在障礙**

從負面來看，以下資訊的缺失可能影響完全重現：(1) **基礎 LLM 模型未明確指定**——論文中未清楚說明 GP 使用哪個具體 LLM（GPT-4？Claude？開源模型？），不同模型的代理能力差異可能導致結果顯著不同；(2) **超參數與提示工程細節**——代理的系統提示、溫度參數、最大軌跡長度等設定未在論文中充分披露；(3) **評估指標的計算細節**——邊緣保真度的具體計算方式（如使用哪個統計距離、如何處理類別型與數值型欄位）未明確說明；(4) **隨機性控制**——未說明是否使用固定隨機種子，多次執行的結果穩定性如何。

**與領域標準的對比**

相較於許多僅釋出程式碼或僅釋出資料的論文，STS 同時釋出兩者的做法值得肯定。然而，相較於如 τ-bench 等提供完整評估協議與基準分數的基準測試，STS 在評估標準化方面仍有進步空間。建議未來工作補充：(1) 標準化的評估腳本與指標計算程式碼；(2) 多個 LLM 後端的基準結果；(3) 統計顯著性檢驗與信賴區間。

#### 未來研究方向

**多維度保真度的形式化與評估**

當前邊緣保真度僅捕捉單欄位分布，未涵蓋跨欄位關聯、時序一致性、與罕見事件分布。未來研究可發展：(1) **聯合分布保真度指標**，衡量多欄位聯合分布的吻合程度；(2) **時序保真度指標**，評估生成資料庫快照隨時間演化的合理性；(3) **長尾分布保真度**，特別關注罕見但重要的業務事件（如糾紛、例外審批）。此方向需要新的統計距離度量與評估協議。

**代理能力的理論分析**

GP 的零編寫特性引發一個根本性問題：**給定僅有工具描述，代理能否在多項式時間內學會產生有效軌跡？** 此問題的形式化分析可能揭示：(1) 哪些類型的 API 設計有利於代理學習；(2) 工具描述的資訊量下界；(3) 代理探索策略的樣本複雜度。此方向將連接理論計算機科學與代理學習理論。

**API 設計原則的逆向工程**

既然 STS 的有效性依賴於 API 層的約束強制，未來研究可探索：(1) **API 設計模式對合成品質的影響**——哪些 API 設計原則（如原子性、冪等性、明確的錯誤回饋）能最大化代理學習效率；(2) **API 演化對既有合成資料集的影響**——當 API 變更時，如何更新已生成的資料集；(3) **從日誌自動推導 API 規範**——能否從企業系統的實際使用日誌中自動建構 STS 所需的模擬環境。

**與真實企業系統的整合驗證**

當前評估基於模擬環境，未來研究應在真實企業系統的脫敏環境中驗證 STS 的實用性。具體方向包括：(1) **領域專家評估**——邀請企業領域專家評估生成資料的真實性；(2) **下游任務驗證**——使用生成資料訓練的代理在真實系統上的表現是否接近使用真實資料訓練的代理；(3) **隱私攻擊抵抗性**——生成資料是否洩漏原始訓練資料的資訊（成員推斷攻擊、屬性推斷攻擊）。

**多代理協作與分工**

當前 GP 是單一代理，未來可探索：(1) **專家代理組合**——不同代理負責不同類型的資料生成（如一個負責員工資料，另一個負責交易資料），透過協調機制確保全局一致性；(2) **代理-人類協作**——在敏感決策點引入人類專家審核，平衡自動化與控制；(3) **代理自我改進**——代理透過生成-評估-調整的循環持續優化其分布建模能力。

**因果與反事實資料生成**

企業決策需要反事實推斷能力（如「若當初批准此貸款，違約率會如何？」）。未來可探索將因果推斷整合至 STS：(1) 在 API 層引入因果操作（如乾預、反事實查詢）；(2) 訓練代理產生符合因果結構的資料快照；(3) 評估生成資料在因果模型學習中的效用。此方向將連接因果推斷、因果發現、與資料合成的文獻。

**跨領域遷移與少樣本適應**

雖然 GP 已展現零編寫特性，但其在全新領域的表現仍待系統評估。未來研究方向：(1) **領域相似性度量**——哪些領域特性（如 API 複雜度、業務規則密度）預測 GP 的表現；(2) **少樣本適應機制**——當提供少量範例軌跡時，GP 能否進一步提升表現；(3) **持續學習**——隨著新領域的加入，GP 的能力如何累積與演化。

**倫理與治理框架**

隨著合成企業資料的廣泛使用，倫理與治理問題日益重要：(1) **資料真實性與誤用風險**——高度真實的合成資料可能被用於社會工程攻擊或詐欺；(2) **偏見放大**——若訓練代理的 LLM 本身存在偏見，生成資料可能放大此偏見；(3) **合規認證**——如何認證合成資料符合特定法規要求（如 GDPR、HIPAA）。此方向需要跨學科合作，連接技術、法律、與倫理學。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於企業 AI 中一個被嚴重低估的瓶頸：如何大規模地訓練與評估工具呼叫代理（tool-calling agents）。由於企業生產系統中的資料庫與資料庫架構（database schemas）受到隱私法規與合規要求的嚴格限制，無法直接匯出真實資料用於代理訓練，因此研究團隊需要尋找能產生「真實且連貫」的企業資料替代方案。論文的目標是建立一個能同時保證結構有效性（structural validity）、分布保真度（distributional fidelity）與合成可擴展性（synthesis scalability）的資料合成方法，以支援企業級代理的開發與評估。

**Q2：為什麼現有的表格資料合成方法（統計型與程序式）在企業場景中會失敗？**
A：統計型表格資料生成器（如 CTGAN、TabDDPM、GReaT）雖然能優化分布保真度，但它們將每一筆紀錄視為獨立個體，無法強制執行跨資料表的關聯式約束（relational constraints），且需要大量預填充訓練語料庫才能運作，在企業部署中會面臨冷啟動問題（cold-start problem）。程序式合成（procedure-based synthesis）雖然能透過編碼業務規則來保證結構有效性，卻無法處理分布保真度，且每新增一個企業領域都需要大量逐環境編寫（per-environment authoring）的工作，包括約束編碼、工作流程腳本與抽樣規則，人力成本隨環境數量線性成長，難以規模化。

**Q3：為什麼這個問題對企業 AI 的發展至關重要？**
A：企業 AI 代理若要在真實生產環境中可靠運作，必須在大量預填充資料庫快照（pre-populated database snapshots）上進行訓練與測試，以避免代理在執行任務時遇到無效狀態。然而，企業生產系統中的敏感資料（sensitive data）涉及個人與機密資訊，受隱私法規約束而無法直接用於訓練；資料庫架構本身也常編碼了企業不願公開的專有領域模型。因此，能否合成出在結構上有效、在分布上真實、且無需逐環境手工編寫的企業資料，直接決定了企業 AI 代理能否突破當前訓練與評估的規模限制。

**Q4：STS（Synthesis Through Simulation）的核心方法是什麼？**
A：STS 是一種「無架構」（schema-free）的資料合成範式，其核心思想是讓大語言模型代理透過執行操作來產生資料，這些操作會作用於模擬企業環境中具有策略強制 API（policy-enforcing APIs）的系統。由於資料是透過同一個定義「什麼是有效」的強制執行層所產生，任何被 API 接受的軌跡（trajectory）都會自動產生一個連貫的資料庫快照，因此結構有效性是由建構本身所保證的。這種設計同時將有效性強制執行（validity enforcement）與分布建模（distribution modeling）解耦（decoupling），讓兩者可以獨立地被處理與優化。

**Q5：STS 與 Generalist Populator（GP）的關鍵創新點為何？**
A：STS 的關鍵創新在於將「有效性」這個問題從資料生成流程中抽離出來，交由環境的 API 層負責，從而讓代理能專注於分布真實性的建模。GP 作為 STS 的領域無關代理（domain-agnostic agent），僅需要原始工具註冊表（raw tool registry）即可運作，無需存取底層資料庫架構、手工編寫的意圖庫、抽樣器或任何逐環境配置。這種「零編寫」（zero-authoring）的設計大幅降低了跨領域部署的成本，使合成方法能真正實現可擴展性。

**Q6：STS 在設計上做了哪些關鍵的取捨？**
A：STS 選擇將結構有效性的責任完全委託給 API 層，而非在代理內部維護一套約束系統，這個取捨換來的是代理可以更輕量化、跨領域可移植性更高。另一個關鍵取捨是放棄對資料庫架構的直接存取，僅透過工具簽章與描述來引導代理行為，這雖然限制了代理對底層資料模型的精確掌握，卻換來了對企業專有架構的零依賴性，使方法能適用於隱私敏感的場景。此外，STS 將資料庫快照本身視為主要交付物，而非代理的通過/失敗分數，這與 τ-bench 等以評分為導向的基準測試形成鮮明對比。

**Q7：論文中使用了哪些基準測試環境來評估 STS？**
A：論文中構建並開源了十個模擬企業環境，涵蓋人力資源、客戶關係管理、訂單管理、航空業務等典型企業領域，這些環境都具備完整的策略強制 API 與業務邏輯強制執行機制。為了進行公平比較，論文還將 STS 與統計型表格資料生成器、具架構權限代理（schema-privileged agents）以及 τ-bench 等基準測試進行對照，特別是在航空環境的緊耦合工作流程（tightly coupled workflows）上測試了代理的穩健性。這十個環境連同完整框架與生成資料集都已開源於 GitHub，方便後續研究重現與擴展。

**Q8：GP 在十個環境上的關鍵實驗結果為何？**
A：GP 在所有十個環境中達到了 100% 的約束滿足率（constraint satisfaction）與平均 0.88 的邊緣保真度（marginal fidelity），其中五個環境的邊緣保真度更超過 0.93，且全程無需存取資料庫架構。相較之下，統計型合成器在七個環境中因缺乏必要的種子資料而無法適用；具架構權限代理在航空環境的緊耦合工作流程上則有 82% 的軌跡失敗，顯示其任務組合（task composition）過於脆弱。這些結果證明了 GP 在無架構、零編寫的設定下，仍能在結構有效性與分布真實性兩個軸上同時達到優異表現。

**Q9：論文中進行了哪些消融實驗來驗證設計選擇？**
A：雖然提供的全文片段未完整列出所有消融實驗細節，但從方法論描述可推論，論文透過比較 GP 與具架構權限代理的表現，驗證了「無架構」設計並未犧牲太多性能，反而在緊耦合工作流程中展現更佳的穩健性。此外，論文將 STS 與統計型合成器在需要種子資料的環境中進行對比，凸顯了 GP 在冷啟動場景下的優勢；同時與程序式合成方法相比，則展示了零編寫設計在跨領域可擴展性上的明顯效益。這些對比實驗共同支撐了「解耦有效性強制執行與分布建模」這一核心設計原則的合理性。

**Q10：STS 在實際企業場景中能支援哪些應用？**
A：STS 可直接應用於企業 AI 代理的大規模訓練資料生成，幫助企業在不洩露敏感資料的前提下，建立足夠多樣化且連貫的預填充資料庫快照，用於微調與評估工具呼叫代理。在代理人測試與回歸驗證方面，企業可利用 STS 快速產生符合業務規則的測試案例，特別是在航空、人力資源等具有複雜關聯式約束的領域。此外，STS 也能用於企業內部的模擬沙盒，讓新代理在投入生產前先於模擬環境中進行安全試驗，降低上線風險。

**Q11：將 STS 整合到企業產品時需要考量哪些實務因素？**
A：產品化 STS 時首先需要考量的是模擬企業環境的建置成本，雖然 GP 本身是零編寫的，但每個領域仍需建構一套完整的策略強制 API 與驗證套件，這部分需要領域專家與工程師共同投入。其次是 API 設計的品質，因為 GP 完全依賴工具簽章與描述來引導行為，工具命名、參數說明與錯誤訊息的清晰度會直接影響合成資料的分布真實性。最後還需考量運算成本與生成速度，由於 GP 透過多輪軌跡產生資料，相較於傳統統計型合成器在單筆紀錄上的開銷更高，需要在品質與效率間取得平衡。

**Q12：STS 對企業 AI 與資料合成領域的更廣泛影響為何？**
A：STS 提出了一個新的資料合成範式，將「透過環境執行來產生資料」這一理念形式化，挑戰了傳統「先有資料庫架構再合成資料」的思維。這種範式不僅適用於企業資料，也可能影響到其他需要結構有效性的領域，例如合成醫療記錄、金融交易資料或政府公文等。更深遠的影響在於，STS 將資料合成從「靜態約束編碼」轉向「動態 API 強制執行」，這與現代企業系統朝向 API 化、服務化架構發展的趨勢高度契合，為未來的可組合企業 AI 奠定了基礎。

**Q13：STS 存在哪些已知的限制？**
A：STS 的首要限制在於其效能高度依賴模擬企業環境中 API 的設計品質與業務邏輯覆蓋範圍，若 API 無法完整表達真實系統的約束，則合成資料的結構有效性也會受到影響。其次，GP 雖然是領域無關的，但其表現仍受底層大語言模型能力所限，在極度複雜的緊耦合工作流程中可能需要更長的推理鏈或更強的模型才能維持穩定。此外，論文中也坦承邊緣保真度的衡量僅針對單變量分布，對於多變量聯合分布與時序相關性的真實性仍需進一步驗證。

**Q14：STS 在哪些情境下可能會失敗？**
A：當模擬環境的 API 無法完整捕捉真實企業系統的副作用或非功能性約束（例如效能、併發、一致性層級）時，STS 生成的資料雖然在結構上有效，卻可能無法反映真實系統的運行特性。在極度長鏈的工作流程中，GP 可能因為累積錯誤而偏離目標分布，特別是當工具呼叫的回饋訊息不夠明確時，代理容易陷入重複或無效的操作循環。此外，若企業領域中存在大量需要領域專家判斷的「軟性約束」（例如合理性、文化契合度），純粹依賴 API 強制執行可能無法完全捕捉這些細緻的業務邏輯。

**Q15：STS 未來可以朝哪些方向發展？**
A：未來研究可朝多個方向延伸：首先，可以探索將 STS 與強化學習結合，讓 GP 透過環境回饋持續優化其分布建模能力，進一步提升邊緣保真度與聯合分布真實性。其次，可以研究如何將 STS 擴展到多代理協作場景，讓多個 GP 同時操作同一環境，產生更複雜且具有時序關聯的企業資料。此外，將 STS 與差分隱私或聯邦學習等隱私保護技術結合，可在保證結構有效性的同時提供更強的隱私保證，這對於高度監管的產業（如金融、醫療）尤其重要。最後，建立標準化的企業環境基準測試套件，將有助於社群共同推進這個領域的研究。

## 實務應用指南

### 適用場景

**1. 企業內部工具呼叫代理的訓練資料生成**
企業在部署內部 AI 助理（例如 HR 系統、ERP、CRM 的對話式介面）時，常因隱私法規無法將真實資料匯出用於模型微調。STS 可在模擬環境中產生結構有效且分布逼真的合成資料，供監督式微調（SFT）與強化學習（RL）階段使用，特別適合需要大量多輪工具呼叫軌跡的場景。

**2. 隱私合規受限產業的測試資料建置**
金融、醫療、政府等受 GDPR、HIPAA、PCI-DSS 等法規約束的產業，難以取得真實客戶資料進行系統整合測試（SI testing）、迴歸測試或 UAT。透過 STS 模擬企業 API，可在不接觸真實個資的前提下，產出符合業務邏輯的預填充資料庫快照，作為測試環境的種子資料。

**3. 新業務流程的沙盒驗證與概念驗證（POC）**
當企業導入新模組（例如新的請假規則、報銷流程、訂單處理工作流）時，可先用 STS 快速生成具備合理分布的歷史資料，讓開發團隊在接近真實的環境中驗證 API 設計、效能瓶頸與邊界情境，縮短從設計到上線的週期。

**4. 工具呼叫代理的基準測試與能力評估**
研究團隊或產品團隊需要評估自家代理在「緊耦合工作流程」下的表現時，可利用 STS 產出多樣化的任務軌跡與資料庫狀態，作為評測基準（類似 τ-bench 的擴充），並可程式化檢查最終狀態是否符合業務規則。

**5. 跨部門系統遷移與資料模擬**
企業進行 SAP S/4HANA、Oracle Fusion 等大型系統升級或遷移時，常需要大量具代表性的測試資料。STS 可針對目標系統的 API 介面生成模擬資料，協助遷移團隊驗證資料完整性、流程正確性與下游報表輸出。

### 實作前置條件

**資料前置條件**
- **目標企業系統的 API 規格文件**：包含工具名稱、輸入參數結構、回傳格式與錯誤碼定義（即論文中所稱的「raw tool registry」）。
- **業務規則說明文件**：用於設計 API 的前置條件（precondition）與驗證套件（validation suite），例如「請假天數不得超過剩餘假期」、「訂單金額必須對應有效客戶」。
- **可選的參考分布資訊**：若希望合成資料更貼近真實分布，可提供少量匿名化的統計摘要（如部門人數比例、訂單金額區間分布），但並非必要。
- **種子資料（seed data）**：僅在需要參考特定實體（例如特定部門、特定客戶）時才需要；論文中 GP 在無種子的情況下仍可運作。

**運算資源前置條件**
- **LLM 推論環境**：建議使用支援函式呼叫（function calling）的商用模型（如 GPT-4o、Claude 3.5 Sonnet）或開源模型（如 Qwen2.5、Llama 3.1 的指令微調版本），並具備足夠的 context window（建議 ≥ 32K tokens）以容納多輪軌跡。
- **容器化執行環境**：Docker / Kubernetes 用於部署模擬企業環境與 API 服務。
- **狀態持久化層**：可使用 SQLite、PostgreSQL 或記憶體資料庫作為模擬環境的狀態儲存。
- **平行運算能力**：為加速大規模資料生成，建議配置多節點推論叢集或使用 vLLM、TGI 等高效推論框架。

**技能前置條件**
- **LLM 代理開發經驗**：熟悉 ReAct、Toolformer 等代理框架，能設計 prompt 與工具呼叫迴圈。
- **企業系統整合知識**：理解 RESTful API、OpenAPI 規格、狀態機與交易一致性概念。
- **Python 程式設計能力**：論文的開源框架以 Python 實作，需熟悉 asyncio、pydantic 等函式庫。
- **業務流程分析能力**：能將業務規則轉化為 API 前置條件與驗證腳本。
- **（選用）分散式系統經驗**：若需大規模平行化生成，則需具備任務排程與分散式協調的知識。

### 實作步驟建議

**步驟一：界定合成目標與評估指標**
明確要合成的資料類型（資料庫快照、軌跡、或兩者）、目標分布特性與必須滿足的業務約束。建議沿用論文的三大軸線：結構有效性、分布保真度、合成可擴展性，並設定可量化的驗收標準（例如 VPR ≥ 0.95、邊緣保真度 ≥ 0.85）。

**步驟二：建置或取得模擬企業環境**
從論文的 GitHub 儲存庫（https://github.com/SAP/synthesis-through-simulation）取得十個參考環境作為起點，或自行建置符合 `E = (D, T, Ψ, V)` 形式的環境：
- 定義資料庫狀態空間 `D`（資料表結構與初始狀態）。
- 實作工具註冊表 `T`，每個工具包含輸入結構 `σ` 與前置條件 `ϕ`。
- 實作轉移函數 `Ψ`，確保違反前置條件時狀態不變。
- 撰寫驗證套件 `V`，涵蓋所有必須強制執行的業務規則。

**步驟三：準備工具註冊表供 GP 使用**
僅需將 API 的函式簽章與自然語言描述暴露給 GP，**不要**洩漏底層資料庫架構。建議遵循 OpenAPI 3.0 規範輸出工具清單，並為每個工具撰寫清楚、具體的描述（包含參數語意、回傳值意義、常見錯誤情境）。

**步驟四：配置 GP 代理與推論設定**
- 選擇具備強健函式呼叫能力的基礎模型。
- 設定代理的系統提示詞，明確告知「僅能透過 API 操作環境」、「不得繞過業務規則」。
- 配置重試機制、軌跡長度上限與單步驗證邏輯。
- 啟用結構化輸出（structured output）以提升參數解析正確率。

**步驟五：執行批次資料生成**
- 定義生成任務的多樣性策略（例如不同起點狀態、不同目標分布）。
- 採用平行化推論與環境實例化以提升吞吐量。
- 記錄每條軌跡的工具呼叫序列、中間狀態與最終狀態，便於後續審計與除錯。

**步驟六：執行驗證與品質評估**
- 對每筆生成的資料庫快照執行驗證套件 `V`，計算 VPR。
- 計算邊緣保真度（marginal fidelity）與聯合分布指標，與參考分布比對。
- 對失敗案例進行根因分析（前置條件錯誤、參數解析錯誤、邏輯繞過等）。

**步驟七：整合至下游應用**
將通過驗證的資料匯出至目標系統（測試環境、訓練 pipeline、評測框架），並建立持續監控機制，定期重新生成以反映業務規則變更。

### 潛在風險與注意事項

**風險一：LLM 繞過業務規則的「聰明捷徑」**
代理可能嘗試以非預期順序呼叫工具，或選擇看似滿足但實際違反精神的參數組合（例如將請假日期設於過去以規避餘額檢查）。
**緩解措施**：在 API 層強制實作嚴格的前置條件檢查（即使代理嘗試繞過，狀態仍不會被修改）；並在驗證套件中加入「語意層級」的反作弊檢查。

**風險二：合成資料的分布偏差與代表性不足**
LLM 傾向產生「典型」或「常見」的組合，可能忽略罕見但重要的邊界情境（例如特殊例外流程、極端金額）。
**緩解措施**：在 prompt 中明確要求覆蓋率；引入分布採樣策略（如重要性抽樣）；定期比對合成資料與匿名化統計摘要的差異。

**風險三：API 設計不完善導致合成失敗**
若工具的前置條件定義不清或互相矛盾，GP 將難以產生有效軌跡，特別是在「緊耦合工作流程」中（如航空業的訂位、付款、出票順序）。
**緩解措施**：借鏡論文中「schema-privileged agents 在航空環境失敗 82%」的教訓，採用模組化、循序漸進的 API 設計；為每個工具提供清楚的「成功路徑」範例。

**風險四：成本與延遲的可擴展性瓶頸**
每筆資料生成需多次 LLM 推論呼叫，累積成本與時間在大規模部署時可能成為瓶頸。
**緩解措施**：使用較小的開源模型搭配領域微調；採用快取機制重用成功的軌跡片段；對簡單任務使用規則式生成器作為 fallback。

**風險五：資料洩漏與隱私殘留**
雖然不直接使用真實資料，但 LLM 的預訓練知識可能「洩漏」出真實企業的內部術語或結構。
**緩解措施**：在 prompt 中明確禁止引用預訓練知識中的具體實體；對輸出進行敏感詞過濾；採用企業內部部署的私有模型。

**風險六：驗證套件本身的完整性**
驗證套件 `V` 若未涵蓋所有業務規則，合成資料可能在「未檢查」的面向上失效。
**緩解措施**：邀請領域專家共同審查驗證套件；採用形式化方法（如斷言式編碼）補強；定期以紅隊演練測試驗證套件的覆蓋率。

### 與其他技術的整合建議

**與傳統統計型表格合成器（CTGAN、TabDDPM、GReaT）的互補整合**
統計型合成器在「有大量種子資料且僅需邊緣分布」時表現優異。建議採用混合策略：先用 STS 在無種子環境中建立初始資料庫，再用統計型合成器在已驗證的快照上進行分布微調；反之，亦可先用統計型合成器產生邊緣分布參考，再引導 GP 貼近該分布。

**與程序式合成框架（Kamino、IRG）的整合**
程序式合成擅長處理靜態宣告式約束，但難以處理動態 API 強制規則。可將程序式合成作為「約束編碼層」，將其輸出作為 STS 環境中 API 前置條件的輸入，達到雙重保障。

**與代理訓練框架（APIGen-MT、DiaFORGE、ASTRA）的整合**
這些框架專注於產生多輪對話軌跡。STS 可作為其上游的「環境填充器」，先產出結構有效的資料庫快照，再由這些框架產生對話軌跡，形成「環境 + 軌跡」的完整訓練資料 pipeline。

**與代理評測基準（τ-bench、AgentBench、WebArena）的整合**
τ-bench 採用 LLM judge 進行後驗證，STS 則採程式化強制。可將 STS 產生的資料庫快照作為 τ-bench 評測的起點狀態，提供更一致、可重現的測試基準；亦可將 τ-bench 的自然語言政策轉化為 STS 的 API 前置條件。

**與企業既有系統（SAP、Oracle、Salesforce）的整合**
透過各系統的標準 API（如 SAP BAPI、Oracle REST API、Salesforce Apex REST）建置模擬環境，並將 STS 生成的資料透過 ETL 流程載入測試實例；同時可逆向利用：將生產系統的 API 規格直接轉化為 STS 的工具註冊表。

**與 MLOps 與資料治理平台的整合**
將 STS 整合至 Feature Store 或 Data Catalog，使合成資料可被追蹤、版本化與審計；並透過 CI/CD pipeline 自動化驗證套件執行，確保每次業務規則變更後合成資料仍符合規範。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節的問題動機，理解「為什麼企業資料合成這麼困難」——核心在於真實企業系統的「有效性」不是單筆資料的屬性，而是跨記錄、跨時間、由 API 強制執行的關聯性。接著跳過數學形式化，直接看第 4 節以後的實驗結果，體會 STS 在十個環境中達到 100% 約束滿足的意義。最後造訪 GitHub 儲存庫，實際跑跑看官方提供的範例環境，從「動手做」中建立直覺。

**給 AI 工程師**：應聚焦於第 3 節的問題形式化（`E = (D, T, Ψ, V)`）與 GP 的代理設計細節，理解「為什麼僅給工具註冊表就能運作」。建議仔細閱讀 GP 的 prompt 策略、軌跡管理與錯誤恢復機制，並嘗試將 GP 移植到自家企業的 API 環境中，評估在真實業務流程下的表現。同時關注論文中提到的「schema-privileged agents 在航空環境失敗 82%」案例，反思自家代理設計是否也有類似的脆弱性。

**給研究者**：本論文在問題分解上具有方法論貢獻——將企業資料合成拆解為結構有效性、分布保真度、可擴展性三個獨立軸線，並證明可透過 API 層強制執行來「解耦」這些軸線。建議從這個視角出發，探索：(1) 是否能進一步形式化證明 API 強制執行的完備性；(2) GP 在更複雜的多代理環境或長期規劃任務中的表現；(3) 與主動學習、貝氏最佳化結合以提升分布保真度的可能性。此外，論文的開源框架提供了絕佳的實驗平台，可作為後續研究的基準線。

**給產品經理**：應將此技術視為「企業 AI 民主化的加速器」——它解決了企業導入工具呼叫代理時最棘手的「資料冷啟動」問題。建議評估：(1) 貴公司有哪些業務流程受限於隱私法規而無法產出訓練資料；(2) 採用 STS 後，從概念驗證到上線的時間可縮短多少；(3) 與傳統手寫測試資料相比，STS 的成本與覆蓋率優勢為何。在向高層提案時，可強調「100% 約束滿足」與「零環境編寫成本」這兩個最具說服力的數字，並以論文中十個環境的開源成果作為可信度佐證。
