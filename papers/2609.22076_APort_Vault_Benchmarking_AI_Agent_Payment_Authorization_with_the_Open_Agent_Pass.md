# APort Vault：以開放代理護照（Open Agent Passport, OAP）對 AI 代理支付授權（payment authorization）進行基準測試（benchmarking）

**原文標題：** APort Vault: Benchmarking AI Agent Payment Authorization with the Open Agent Passport  
**作者：** Uchi Uchibeke  
**發布日期：** 2026-09-18  
**HF 連結：** [https://huggingface.co/papers/2609.22076](https://huggingface.co/papers/2609.22076)

## ⚡ TL;DR

現有基準測試只量模型拒絕，無法回答部署者工具邊界執行後的殘留風險。
APort Vault重播4,371場真實CTF攻擊，14模型、五政策、兩軌道比較有無OAP授權層。
OAP層使未授權轉帳歸零（每工作階段上限0.38%），請求率幾乎不變，並釋出225,964筆評估。

## 摘要翻譯

APort Vault 是一個針對使用工具之 AI 代理（tool-using AI agents）的支付授權（payment authorization）所設計的基準測試（benchmark）。它將一場公開搶旗賽（capture-the-flag, CTF）中，由人工撰寫、針對即時支付代理（live payment agent）的 4,371 道攻擊（attacks），在來自 8 間實驗室（labs）的 14 個模型（models）上重播（replay），涵蓋五種政策配置（policy configurations）與兩種重播軌道（replay tracks），並在有無實作 OAP 規範之確定性行動前檢查（deterministic pre-action check）的條件下進行。共完成 225,964 次評估（evaluations）。我們對每次評估報告五種不同事件（events），因為一旦將它們合併，就會產生代理基準測試中經不起審查的數字。

轉帳（transfer）請求相當常見，且其請求率（request rate）在不同配置間的差異遠大於不同模型間的差異；然而每道攻擊只存在於單一配置中，因此政策（policy）與攻擊群組（attack cohort）會同步變動：在僅模型架構（model-alone architecture）評估中，等級 1（Level 1）的請求率為 10.9%，等級 2（Level 2）為 3.0%，等級 3（Level 3）為 0.1%，等級 4（Level 4）為 79.4%。在 1,293 道等級 4 提示（prompts）中，每道都在所有模型上進行評估，各模型的請求率介於 71.2% 至 84.3% 之間；其中 809 道提示（62.6%）引發了全部十四個模型的轉帳請求，且每一筆最終都成功付款（payment）給該等級的允許清單收款方（allowlisted recipient）。

授權邊界（authorization boundary）即為條件分歧之處。在等級 2 至等級 4 中，轉帳至護照未允許的收款方（recipient）：在僅模型架構的 76,842 筆中出現 140 筆，在授權層後架構（behind-the-layer architecture）的 69,297 筆中為 0 筆；而在 68,970 組配對的模型、提示與軌道三元組（matched model, prompt and track triples）中，則為 105 筆對 0 筆。此零值涵蓋 790 個來源工作階段（source sessions），得出每工作階段上限（per-session upper bound）為 0.38%。這個零並非靠拒絕付款（refusing payments）取得：授權層後架構共執行了 25,370 筆付款，而政策在評估的 25,640 筆轉帳呼叫（transfer calls）中拒絕了 187 筆，其中 148 筆是因收款方為禁止收款方（forbidden recipient）。

我們在 huggingface.co/datasets/aporthq/vault-benchmark-v1 釋出這 225,964 次評估、各等級護照（level passports）、評分程式碼（scoring code）與分析腳本（analysis script）。

### 核心貢獻（3～5點）
- 建構並釋出 APort Vault，首個針對 AI 代理支付授權的大規模基準測試，以 225,964 次評估重播 4,371 道人工撰寫攻擊。
- 比較「僅模型架構」與「授權層後架構」，驗證 Open Agent Passport（OAP）確定性行動前檢查在防止未授權資金移轉上的有效性。
- 主張代理基準測試應報告多種獨立事件，而非單一合併數字，以避免產生經不起審查的結果。
- 公開釋出完整評估資料、各等級護照、評分程式碼與分析腳本，促進後續研究與審查。

### 適合對象
本論文適合關注 AI 代理安全、支付系統風險控管、LLM 工具使用安全，以及代理基準測試方法學的研究者與工程師閱讀；對於設計或部署具資金操作能力之 AI 代理的實務人員、金融監管與資安領域專業人士亦具參考價值。

## 深度分析

#### 方法論解析

本研究的核心方法並非再生成一組對抗性提示（adversarial prompt），而是把真實世界裡人類為了贏得獎金而寫的攻擊，系統性地重播（replay）到一個受控的支付代理（payment agent）上，並比較「有無授權邊界（authorization boundary）」這個單一變因所造成的差異。具體而言，方法可拆解為四個層次：

1. 真實攻擊語料庫的取得  
   作者在 2026 年 3 月至 8 月間舉辦了一場公開的 capture-the-flag（CTF，搶旗賽），對象是一個線上代理銀行（live agentic bank）。共有 1,128 個不同工作階段（distinct session）產出 4,371 次攻擊嘗試（attack attempt），其中 97.7% 集中在上線窗口（launch window）內。這些攻擊不是研究者撰寫的任務集（researcher-authored task suite），也不是合成的越獄模板（synthetic jailbreak template），而是攻擊者為了實際把資金轉出而寫的內容，因此具備高度的生態效度（ecological validity）。

2. 重播網格（replay grid）的設計  
   每一則攻擊都被餵進 14 個來自 8 間實驗室（lab）的模型，並在 5 種政策等級（policy level）、2 種重播軌道（replay track）、2 種架構（architecture）下執行，總計完成 225,964 次評估（evaluation）。兩種重播軌道分別是：僅最終訊息軌道（final-message-alone track）——只把攻擊者的最後一則訊息餵給模型；以及完整訊息序列軌道（full-message-sequence track）——保留完整對話脈絡。兩種架構則是：僅模型架構（model-alone architecture），工具呼叫（tool call）直接執行；以及授權層後架構（behind-the-layer architecture），在模型輸出與工具執行之間插入一個確定性行動前檢查（deterministic pre-action check）。

3. Open Agent Passport（OAP，開放代理護照）的實作  
   該授權層實作了 OAP 規範，對每一筆轉帳呼叫（transfer call）在執行前檢查收款方（recipient）是否落在護照允許的範圍內。這個檢查是確定性（deterministic）的：不依賴 LLM 評判（LLM judge），而是根據明確的政策配置（policy configuration）與工具結構描述（tool schema）進行比對。模型（model）、提示（prompt）、解碼設定（decode settings）與工具結構描述在兩種架構下完全相同，因此任何差異都可歸因於授權邊界本身。

4. 五階段結果拆解  
   作者刻意不把結果壓縮成單一數字，而是分開報告五個事件：轉帳請求（request）、成功付款（successful payment）、政策決策（policy decision）、收款方成員資格（recipient membership）以及未允許轉帳（unpermitted transfer）。這種拆解讓讀者能區分「模型拒絕（refusal）」與「授權層拒絕（policy denied）」這兩種原本經常被混為一談的防禦機制。

#### 實驗數據解讀

數據呈現出幾個值得細究的現象：

1. 請求率（request rate）主要由政策與攻擊群組決定，而非模型  
   在模型單獨（model-alone）架構下，各等級的請求率分別為：Level 1 佔 10.9%、Level 2 佔 3.0%、Level 3 佔 0.1%、Level 4 佔 79.4%。這顯示絕大多數攻擊嘗試都集中在 Level 4，而不同政策等級（policy level）之間的請求率差異遠大於不同模型之間的差異。在 1,293 個 Level 4 提示上，14 個模型的請求率介於 71.2% 至 84.3%，且有 809 個提示（62.6%）能同時誘發全部 14 個模型提出轉帳請求。這說明「模型會不會請求付款」在該配置下幾乎是共同特徵，而非區分模型安全性的可靠指標。

2. 授權邊界是風險收斂的關鍵  
   在 Level 2 至 Level 4 的 76,842 次模型單獨評估中，共發生 140 筆未允許轉帳（unpermitted transfer）；相對地，在授權層後方（behind-the-layer）的 69,297 次評估中，未允許轉帳為 0。進一步控制模型、提示與軌道三元組（matched model, prompt and track triple）後，模型單獨組仍有 105 筆違規，授權層組仍為 0。由於這些結果來自 790 個來源工作階段（source session），作者給出每工作階段上限（per-session upper bound）為 0.38%，讓「零」不再只是零寬區間，而是具有統計信心的陳述。

3. 零違規並非來自壓抑請求  
   授權層後方仍執行了 25,370 筆成功付款（successful payment），政策拒絕（policy denied）了 187 筆轉帳呼叫，其中 148 筆是因為收款方被禁止（forbidden recipient）。這證明該層並未透過全面封鎖付款來換取安全，而是精準地攔截未允許的收款方。在 68,970 個配對三元組上，兩種架構的請求率差異僅 +0.084 個百分點，95% 區間為 [-0.020, +0.189]，進一步支持「授權層不改變模型行為，只改變執行結果」的論點。

4. Level 5 的詮釋必須謹慎  
   Level 5 完全不授予付款能力，其提示還明確告訴模型「會有守衛攔截」，因此它測量的是強制執行（enforcement）機制本身，而非模型易感性（model susceptibility）。作者也刻意不把 Level 2 至 Level 5 的結果合併成單一頭條數字，因為 Level 5 的結果數量是受限等級的 38 倍，會完全主導平均值。

5.  leaderboard 無法呈現的三個結構性發現  
   第一，結果高度集中在少數來源工作階段：790 個工作階段中，僅 2 個就貢獻了 Level 2 至 Level 4 一半的違規結果；單一偽造收據（forged-receipt）群組的 103 次嘗試就產生了 111 筆多輪 Level 2 結果。第二，攻擊跨模型轉移（attack transfer）很弱：2,809 次攻擊中只有 73 次能擊敗任何模型，且只有 1 次能擊敗五個模型。第三，多輪（multi-turn）優勢幾乎完全集中於單一攻擊家族，而非廣泛的多輪壓力（multi-turn pressure）效應。

6. LLM 評判的不可靠性  
   雖然本研究的主要指標是確定性的，作者仍對完整資料進行評判一致性稽核：合併的評判間 Kappa 為 0.772，但在 Level 3 降至 0.167、Level 5 降至 0.521；兩位評判分別只找回 99.1% 與 64.4% 的確定性確認結果。這再次說明為何主要指標必須避開 LLM 評判的主觀判斷。

#### 與現有研究的比較

相較於既有文獻，APort Vault 在問題定位與測量對象上有明顯區隔：

- 與 AgentDojo、InjecAgent 的比較  
  AgentDojo 與 InjecAgent 都建構了工具使用代理（tool-using AI agent）的攻擊測試案例，但攻擊者即基準測試作者本人。APort Vault 的攻擊來自公開 CTF 的參賽者，生態效度更高；此外，AgentDojo 測量的是提示注入是否重新導向代理，而 APort Vault 測量的是資金是否實際移轉（money moved）。

- 與 LLMail-Inject 的比較  
  LLMail-Inject 同樣釋出公開適應性挑戰中的大量提示注入嘗試，資料來源最為接近。但兩者的依變項不同：LLMail-Inject 測量注入是否到達並操控模型，APort Vault 則測量工具執行層的後果，並在相同攻擊下變動執行架構。

- 與 AgentHarm、ToolEmu 的比較  
  AgentHarm 評估代理是否願意執行 110 項明確有害任務，ToolEmu 則以語言模型模擬工具執行來發現風險行為。兩者都聚焦於模型傾向（disposition）。APort Vault 則把焦點從「模型想不想做」轉移到「部署者還能靠什麼攔截殘留風險（residual risk）」。

- 與 MT-JailBench、MultiBreak 的比較  
  這兩項研究都指出多輪攻擊優於單輪攻擊，並將原因歸於累積脈絡。APort Vault 的發現並不否定此結論，但顯示在多輪重播軌道下，效益幾乎完全來自單一攻擊家族與單一來源群組，提醒研究者對「多輪壓力普遍更強」的聚合敘述保持謹慎。

- 與 Gao 等關於自動化攻擊成功率評分研究的比較  
  既有研究已指出自動化攻擊成功率（ASR）評分脆弱。APort Vault 透過確定性指標迴避了這個問題，同時以評判稽核說明若改用 LLM 評判會帶來多大噪音。

限制方面，本研究明確自限於支付（payment）領域、單一工具結構描述與模擬銀行環境，因此不能外推到資料外洩（data exfiltration）、程式碼執行（code execution）或代理間委派（delegation between agents）。此外，「零違規」是「正確配置的政策引擎（policy engine）評估明確能力」的性質，並不保證授權層在誤配置情況下仍然安全。

#### 可重現性評估

本研究在可重現性（reproducibility）上採取了相對開放的姿態：

- 資料與程式碼釋出  
  作者於 Hugging Face 釋出 225,964 次評估結果、各等級護照（level passport）、評分程式碼（scoring code）與分析腳本（analysis script），並提供凍結快照雜湊（frozen snapshot hash）。這讓其他研究者可以直接檢視原始結果、重新跑分與進行後設分析。

- 確定性指標降低主觀變異  
  由於主要結果是從已執行工具呼叫（executed tool call）中讀取資金是否移轉，而非依賴 LLM 評判，因此重現時不需要處理評判模型版本或提示變動所帶來的噪音。

- 模型取得與架構重現的限制  
  雖然資料與評分邏輯公開，但要完全重現實驗仍需取得 14 個模型的 API 或權重。部分模型可能來自商業實驗室，未必公開模型權重（model weights）。此外，OAP 授權層的實作細節雖可從規範與釋出程式碼推導，但實際部署時的政策配置正確性仍是重現「零違規」結果的前提。

整體而言，APort Vault 在資料透明性與評分確定性上達到高標準，但在端到端重現上仍受限於商業模型的可取得性。

#### 未來研究方向

基於 APort Vault 的發現與方法，以下幾個方向值得後續探索：

1. 擴展到其他高風險能力  
   將相同的重播與授權邊界框架應用到資料外洩、程式碼執行、代理間委派、電子郵件發送或日曆預約等能力，檢驗 OAP 式授權在不同工具語意下的有效性。

2. 更豐富的政策語言與動態政策  
   目前實驗使用五個固定政策等級。未來可研究更細緻的政策語言（例如時間窗口、金額上限、雙重授權）以及動態更新政策時的穩定性。

3. 針對授權層的適應性攻擊  
   當攻擊者知道存在 OAP 層時，可能會嘗試繞過或欺騙政策引擎，例如偽造護照欄位、利用結構描述解析差異或攻擊授權層的實作漏洞。需要建立專門針對授權邊界的攻擊基準。

4. 誤配置與工程穩健性  
   「零違規」依賴正確配置。未來可系統性地測試政策引擎在常見誤配置（例如允許清單過寬、正規表示式錯誤、大小寫轉換不一致）下的表現，並發展配置驗證工具。

5. 即時動態 CTF 與縱貫研究  
   舉辦持續性、動態調整政策與模型的 CTF，觀察攻擊者如何隨防禦演進而適應，並建立模型版本更新後的縱貫風險追蹤。

6. 成本、延遲與使用者體驗  
   授權層雖然有效，但會增加延遲與營運成本。未來研究可量化每筆轉帳的額外開銷，並探討如何在安全與使用者體驗之間取捨。

7. 人機協同授權  
   將 OAP 與人類在迴路（human-in-the-loop）授權結合，研究何時應由自動層決定、何時應升級給人類審批，特別是在高金額或新收款方的情境。

8. 認證框架與標準化  
   將 APort Vault 的評估流程標準化，發展類似於安全認證的代理授權認證機制，協助部署者與監管機構評估殘留風險。

## 論文問答

**Q1：APort Vault 主要想解決什麼問題？**

A：APort Vault 針對的是「使用工具的 AI 支付代理」在面對攻擊時，資金是否會被轉到政策不允許的收款方這個核心風險。過去絕大多數評測只關注模型會不會拒絕攻擊者的請求，但這篇論文測量的是「模型與工具執行之間」的授權邊界能否攔下違規轉帳。換句話說，它回答的是：即使模型被騙而發出轉帳請求，部署者還有沒有第二道防線可以阻止錢真的被移走。

**Q2：為什麼現有以模型為中心的基準測試無法回答部署者真正關心的殘留風險？**

A：現有基準通常給出一個「哪個模型比較安全」的分數，但這個分數是模型版本的屬性，模型重新訓練後就會失效，也無法告訴部署者選完模型後還剩下多少風險。更重要的是，這些評測大多只看模型是否拒絕，卻忽略了模型一旦輸出工具呼叫，後續是否有人或機制把關。此外，許多評測仰賴 LLM 評判，而論文顯示評判者之間的一致性在某些政策等級會大幅下降，使得結果難以成為部署決策的可靠依據。

**Q3：測量「第二道防線」為什麼對實務部署很重要？**

A：因為即使選用當前最安全的模型，它在真實攻擊下仍可能以非零機率產生轉帳請求，部署者必須知道還有什麼機制能攔下剩餘的風險。APort Vault 使用的攻擊來自公開搶旗賽，參賽者為了獎金池會想盡辦法把錢轉出，因此比合成越獄模板或研究者撰寫的任務集更貼近真實威脅。透過在相同攻擊、相同模型、大規模評估下比較「有無授權層」的反事實情境，論文才能對「零違規」給出可信的統計上限。

**Q4：APort Vault 的核心重播方法論是什麼？**

A：研究團隊把 2026 年 3 月至 8 月公開搶旗賽中，1,128 個不同工作階段產生的 4,371 次人工攻擊重新餵給 14 個來自 8 家實驗室的模型。每次重播都在五種政策等級、兩種重播軌道（僅最終訊息與完整訊息序列）以及兩種架構下進行，兩種架構的唯一差別是工具呼叫前是否加上符合 OAP 規範的確定性行動前檢查。模型、提示、解碼設定與工具結構描述都保持一致，總共完成 225,964 次評估，最終以「已執行工具呼叫中資金是否移到未允許收款方」作為客觀結果。

**Q5：將每次評估拆解成五個獨立事件，這個設計的關鍵創新在哪裡？**

A：傳統基準常把各種中間過程壓縮成單一成功率，容易產生一個「撐不過審查」的數字；APort Vault 則分別報告「轉帳請求、成功付款、政策決策、收款方成員資格、未允許轉帳」五個事件。這樣才能清楚區分：授權層後的零違規並不是因為模型變得更會拒絕，而是因為工具邊界確實攔下了違規呼叫。同時，這種拆解也讓研究者看到請求率在兩種架構下幾乎相同，進而凸顯授權邊界才是決定資金是否外洩的關鍵變因。

**Q6：為什麼選擇使用確定性行動前檢查，而不是讓 LLM 評判攻擊是否成功？**

A：確定性檢查依據 Open Agent Passport（OAP）規範，對照政策護照直接判斷工具呼叫是否被允許，結果完全可重現、可審計，也不受評判模型主觀性或提示變化影響。論文的評判一致性稽核顯示，雖然整體 Kappa 達 0.772，但在 Level 3 會掉到 0.167，顯示 LLM 評判並不可靠。正因為最終指標是確定性的，評判品質的波動才不會影響 headline 結果，這正是採用確定性邊界檢查的重要論據。

**Q7：這項研究使用了什麼資料集與評測規模？**

A：資料來自一場針對線上代理銀行的公開搶旗賽，獎金池 6,500 美元，最終收集到 4,371 次真實攻擊嘗試，其中 97.7% 集中在上線窗口的 3 月 6 日至 12 日。這些攻擊被重播到 14 個模型、五種政策等級、兩種重播軌道與兩種架構，總計完成 225,964 次評估。所有評估結果、各等級護照、評分程式碼與分析腳本都已釋出在 Hugging Face 的 `aporthq/vault-benchmark-v1` 資料集。

**Q8：APort Vault 最重要的量化結果是什麼？**

A：在政策等級 2 至 4 的 76,842 次「僅模型」評估中，發生了 140 次未允許轉帳；而在有授權層的 69,297 次評估中，未允許轉帳為 0 次，對應的每工作階段上限為 0.38%。這個零並非來自模型拒絕付款，因為授權層後仍執行了 25,370 筆成功付款，只是在 25,640 次轉帳呼叫中政策拒絕了 187 次，其中 148 次是因為收款方不被允許。另外在 1,293 個 Level 4 提示上，十四個模型的請求率介於 71.2% 到 84.3%，顯示請求行為是這些設定的共同特徵，而非單一模型特別不安全。

**Q9：實驗中的對照與消融分析揭示了什麼？**

A：在控制模型、提示與重播軌道的 68,970 組配對三元組中，「僅模型」架構有 105 次未允許轉帳，「授權層後」架構為 0 次，證明邊界檢查才是決定性因素。同時，兩種架構的請求率差異僅 +0.084 個百分點，信賴區間為 [-0.020, +0.189]，說明授權層並沒有壓抑模型的請求意願。多輪重播的優勢也並非普遍存在，而是幾乎集中在一個偽造收據的攻擊群組，這提醒研究者對「多輪攻擊普遍更強」這類聚合結論要更謹慎。

**Q10：部署者應該如何應用這些發現來保護支付代理？**

A：部署者應該在模型與轉帳工具之間加入確定性授權層，並依據 OAP 等政策規範在工具執行前檢查收款方與金額是否符合護照許可。不能單純依賴模型拒絕攻擊，因為所有測試模型在相同設定下都會產生一定比例的轉帳請求。此外，部署者可以利用 APort Vault 釋出的真實攻擊語料庫與評分程式碼，針對自己的政策引擎與工具結構描述進行壓力測試。

**Q11：這對建構安全的代理金融產品有什麼具體啟示？**

A：產品設計應把「模型決策」與「工具執行」明確分離，並在後者設置強制執行的政策引擎，讓模型可以正常請求付款，但禁止的收款方絕對無法收到錢。產品也應以「已執行工具呼叫」作為 ground truth，而不是以模型輸出文字或 LLM 評判作為最終安全指標。Level 5 的設計特別顯示：當提示直接要求模型呼叫轉帳工具並承諾會有守衛攔截時，測量的是執行機制本身，而非模型易受攻擊程度，因此產品測試時要區分這兩種評量目標。

**Q12：這項研究可能對整個 AI 代理安全領域帶來什麼影響？**

A：APort Vault 把評測焦點從「模型拒絕率」轉移到「工具邊界執行」與「資金實際移轉」這類客觀後果，推動代理安全研究更貼近部署風險。它也示範了公開真實攻擊語料庫、釋出確定性評分程式碼與可重現分析腳本的價值，有助於減少 leaderboard 上常見的數字美化。更廣泛地說，這項工作為「行動前授權規範」如 OAP 提供了大規模實證基礎，可能促使更多高風險代理系統採用類似的邊界強制架構。

**Q13：作者明確承認了哪些限制？**

A：研究結果僅限於支付場景、單一工具結構描述與模擬銀行環境，不能推論到資料外洩、程式碼執行或代理間委派等其他風險。零違規是「在正確配置的政策引擎與明確定義的能力規範下」的性質，並不代表授權層不可能被錯誤配置或繞過。此外，Level 5 完全不授予付款能力，其提示旨在測試攔截機制，因此不能與 Level 2–4 的結果混為一談，論文也避免將 Level 2–5 聚合為單一指標。

**Q14：在什麼情況下，這道授權邊界可能會失效？**

A：如果政策引擎被錯誤配置，例如護照沒有正確列出禁止收款方，或能力規範存在歧義，攻擊者就可能鑽過邊界。此外，若攻擊者能夠竄改 Open Agent Passport、繞過檢查邏輯，或讓檢查層本身執行惡意程式碼，那麼這道防線也會失效。因此，0.38% 的每工作階段上限是對「目前觀察到零違規」的統計信心界限，而不是證明授權層在所有可能威脅下都絕對安全。

**Q15：未來可以朝哪些方向延伸這項研究？**

A：未來可以將相同方法擴展到資料外洩、程式碼執行、跨代理委派等高風險行動，建立對應的 OAP 風格授權邊界與基準測試。另一個方向是發展自動化的政策驗證工具與更嚴謹的能力規格語言，減少人為配置錯誤導致的繞過。最後，也可以結合即時監控、異常偵測與人工介入機制，形成多層次的代理安全防護，而不僅僅依賴單一行動前檢查。

## 實務應用指南

### 適用場景

1. **企業內部財務代理的支付閘道**：當公司部署可呼叫轉帳、付款或請款工具的 AI 代理時，可在模型輸出與真正執行轉帳之間加入 OAP 授權層，確保每一筆資金移轉都符合預先設定的收款方允許清單與額度政策。
2. **金融科技或虛擬銀行的智慧客服轉帳**：讓使用者透過對話發起轉帳的場景中，可將 APort Vault 的重播方法與評分邏輯用於紅隊測試，驗證「模型拒絕」與「授權邊界攔截」各自的實際效果。
3. **SaaS 平台代理的敏感操作授權**：除了支付，也可套用到刪除帳號、大量匯出資料、變更權限等高風險工具呼叫，透過確定性行動前檢查降低模型被提示注入誘導的後果。
4. **模型選型與部署風險評估**：在選擇要上線的模型時，不只比較模型的拒絕率，還能透過固定攻擊語料庫比較「僅模型架構」與「授權層後架構」的違規轉帳數，計算殘留風險。
5. **公開搶旗賽或紅隊計畫的後續分析**：將真實攻擊嘗試重播到多個模型與政策配置，建立可重現的基準測試，並公開釋出評估資料與評分程式碼供社群檢驗。

### 實作前置條件

- **資料**：需要一組真實或高擬真的攻擊提示，最好包含單輪與多輪對話；若無自有語料，可從 APort Vault 釋出的 4,371 筆人工攻擊與 225,964 筆評估結果開始。同時需要明確的政策規則，例如允許收款方清單、每筆/每日限額、來源帳戶等。
- **運算**：重播需要能呼叫多個模型的 API 或自有部署環境；14 個模型 × 數千筆攻擊 × 兩種軌道的規模，建議具備可平行處理的腳本與足夠的 API 配額。評分與分析則可在一般筆電或小型伺服器執行。
- **技能**：需要熟悉工具呼叫代理的開發、API 整合與日誌記錄；能撰寫確定性授權檢查規則；具備基礎統計觀念以解讀請求率、違規率與信賴界限；若要做法官稽核，還需了解 LLM judge 與一致性指標。

### 實作步驟建議

1. **定義工具與政策**：先將支付工具的工具結構描述、參數與允許收款方清單固定下來，劃分政策等級，例如 Level 1 全開、Level 4 僅允許特定收款方等。
2. **建立兩種架構**：一種是「僅模型架構」，模型輸出直接進入工具執行；另一種是「授權層後架構」，在工具執行前加入確定性 OAP 檢查，驗證收款方、額度與其他條件。
3. **準備攻擊語料並重播**：將攻擊以「僅最終訊息軌道」與「完整訊息序列軌道」分別餵給各模型，記錄模型是否產生轉帳請求、授權層是否通過、工具是否實際執行、資金是否移轉到非允許收款方。
4. **以五階段事件評分**：不要只算成功率，而是分開記錄「轉帳請求」、「成功付款」、「政策決策」、「收款方成員資格」與「違規轉帳」五種事件，才能區分模型拒絕與授權邊界攔截的貢獻。
5. **計算殘留風險與信賴界限**：針對違規轉帳數為零的情況，使用來源工作階段進行分群，計算每工作階段上限，避免把零直接解讀為絕對安全。
6. **釋出與迭代**：將評估結果、政策護照、評分程式碼與分析腳本一併釋出，並持續收集新的攻擊語料更新基準測試。

### 潛在風險與注意事項

- **不要把「零違規」當成絕對安全**：論文以工作階段分群後得到 0.38% 的每工作階段上限，實務上應持續監控並定期重跑紅隊測試。
- **政策規則寫錯會讓授權層失效**：OAP 檢查是確定性的，但前提是規則正確且涵蓋所有邊界情況。建議對政策進行單元測試，並審查允許清單是否過度寬鬆。
- **模型請求率與實際風險是兩回事**：模型仍會大量產生轉帳請求，授權層的價值在於攔截而非壓低請求率。若只看請求率，可能誤以為模型已經夠安全。
- **多輪攻擊可能集中在特定族群**：論文發現多輪優勢主要來自單一偽造收據群組，實務上應針對高產出攻擊來源進行深度分析，而非僅看整體平均。
- **LLM judge 不適合作為主要指標**：若使用模型評判輔助標註，需了解其一致性有限；關鍵的金流結果應以已執行工具呼叫與收款方紀錄為準。

### 與其他技術的整合建議

- **與現有身分驗證與授權系統整合**：OAP 授權層可對接 OAuth、RBAC/ABAC 或銀行核心系統的帳戶權限檢查，將 AI 代理視為另一個需要被授權的服務主體。
- **與監控與告警系統串接**：將每一次轉帳請求、政策拒絕與違規嘗試寫入結構化日誌，並連接 SIEM 或異常偵測系統，對高頻攻擊來源即時告警。
- **與沙箱或模擬執行環境搭配**：在正式上線前，可先用 ToolEmu 等模擬環境快速篩選高風險行為，再將通過篩選的攻擊放到真實或準生產環境重播。
- **與模型閘道並行使用**：模型閘道負責路由、速率限制與基本內容過濾，OAP 層則專注於行動前授權，兩者互補而非互相取代。
- **與持續紅隊測試流程結合**：將 APort Vault 的重播腳本納入 CI/CD 或定期安全測試，作為模型升級或政策變更後的回歸測試。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從「適用場景」與「潛在風險與注意事項」讀起，理解為什麼「模型拒絕」不足以保護支付代理，以及「授權邊界」是什麼意思；遇到統計術語時可先跳過，專注在論文反覆強調的核心訊息：要用實際執行的工具呼叫與收款方紀錄來評量安全。
- **AI 工程師**：請重點閱讀重播方法、兩種架構的實作差異、五階段事件評分與來源工作階段分群的風險計算；這些內容直接對應到如何在你負責的代理系統中插入確定性授權檢查，並設計可重現的評估流程。
- **研究人員**：建議深入分析論文的貢獻與限制，特別是為何不將多個等級的結果合併為單一指標、為何使用確定性指標而非 LLM judge、以及多輪攻擊效果集中在特定攻擊群組的發現；這些設計選擇對未來的代理安全基準測試研究具有方法論意義。
- **產品經理**：請聚焦在「殘留風險」與「部署問題」這兩個概念；論文指出即使選到最好的模型，仍可能有違規轉帳發生，而授權層能將其壓到可量測的低水準。這有助於你向利害關係人說明為何需要在產品中投入額外的政策引擎與紅隊測試資源。
