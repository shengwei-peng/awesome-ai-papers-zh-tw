# 先理解，再修復：用於軟體問題解決的問答導向儲存庫知識獲取

**原文標題：** Know Before Fix: QA-Driven Repository Knowledge Acquisition for Software Issue Resolution

**發布日期：** 2026-07-13

## ⚡ TL;DR

現有 LLM 程式設計代理因儲存庫理解不足而產生事實性錯誤，且修復導向的探索未能彌補知識缺口。
本文提出 ACQUIRE，以問答驅動的兩階段框架，將儲存庫知識獲取與修補生成解耦。
於 SWE-bench Verified，ACQUIRE Pass@1 最高提升 4.4 百分點。

## 摘要翻譯

基於 LLM 的程式設計代理（LLM-based coding agents）在自動化軟體問題解決（Software Issue Resolution）方面已取得顯著進展，但仍極易因儲存庫理解（repository understanding）不足而產生事實性錯誤（factual errors）。近期方法試圖透過修復前儲存庫探索（pre-repair repository exploration）來緩解此限制；然而，其修復導向策略（fix-driven strategies）在探索儲存庫時並未識別代理的知識缺口（knowledge gaps），往往產生不精確的上下文（imprecise context），無法彌補潛在的理解不足（understanding deficit）。本文提出 ACQUIRE，一個用於軟體問題解決的問答導向框架（QA-driven framework）。如同經驗豐富的開發者在嘗試修復前會先理解陌生的程式碼，ACQUIRE 在修復前明確地獲取儲存庫知識。此框架為兩階段框架（two-stage framework），將知識獲取（knowledge acquisition）與修補程式生成（patch generation）解耦：在第一階段，提問者（Questioner）與回答者（Answerer）協作以獲取結構化儲存庫知識（structured repository knowledge），其中提問者提出針對性問題（targeted questions），回答者則透過自主探索（autonomous exploration）產生基於證據的答案（evidence-grounded answers）；在第二階段，解決器（Resolver）利用所產生的問答知識（QA knowledge）來生成有依據的修補程式（informed patches）。透過將隱性知識缺口（implicit knowledge gaps）轉化為明確且事實可靠的理解（factually reliable understanding），ACQUIRE 能夠加快知識密集的修復階段（knowledge-intensive repair stages），並使問題解決更為準確。在 SWE-bench Verified 上的實驗顯示，ACQUIRE 始終優於具代表性的修復前方法，僅需適度的額外成本與時間，即可將 Pass@1 最高提升 4.4 個百分點。

### 核心貢獻（3～5點）
- 提出 ACQUIRE，一個問答導向的兩階段框架，將儲存庫知識獲取與修補程式生成解耦，使代理在生成修補前先建立對程式碼庫的可靠理解。
- 設計提問者（Questioner）與回答者（Answerer）協作機制，透過針對性問題與基於證據的答案，將隱性知識缺口轉化為明確、可驗證的結構化儲存庫知識。
- 引入解決器（Resolver），善用第一階段產出的問答知識生成有依據的修補程式，提升知識密集修復階段的準確度。
- 在 SWE-bench Verified 上進行實驗，證明 ACQUIRE 相較於具代表性的修復前方法能穩定提升 Pass@1，最高達 4.4 個百分點，且僅需適度的額外成本與時間。

### 適合對象
本論文適合對自動化軟體工程、基於大型語言模型的程式設計代理、自動化程式修補（APR）以及儲存庫理解有興趣的研究人員與實務工作者。特別是關注如何減少 LLM 在程式碼生成過程中的事實性錯誤、提升代理對大型程式碼庫結構與語義理解，以及設計更有效的前置探索策略以輔助軟體問題解決的讀者。

## 深度分析

#### 方法論解析

ACQUIRE 的核心設計是將**儲存庫理解（repository understanding）**與**修補程式生成（patch generation）**解耦為兩個明確階段，並以**問答導向的儲存庫知識獲取（QA-driven repository knowledge acquisition）**作為銜接兩階段的中介知識表徵。整體流程可對應資深開發者在面對陌生程式碼時，先透過提問建立理解，再動手修改的習慣。

**第一階段：問題導向的知識獲取（Question-Driven Knowledge Acquisition）**

此階段由兩個專責**代理（agent）**協作完成：

1. **提問者（Questioner）**：接收**問題描述（issue description）**後，將其分解為一組針對性問題（targeted questions）。這些問題並非隨意產生，而是依循一套**類別導向的問題分類法（category-guided question taxonomy）**，涵蓋互補的知識維度，例如圖 1 所示的「機制與行為（Mechanism & Behavior）」、「設計與使用方式（Design & Usage）」與「環境（Environment）」等。透過這種結構化模板，Questioner 能將原本隱性的**知識缺口（knowledge gaps）**轉化為可回答、可驗證的具體問題。
2. **回答者（Answerer）**：針對每一個問題進行**自主探索（autonomous exploration）**，在儲存庫中搜尋相關程式碼、文件、相依關係與執行跡證，並產生**基於證據的答案（evidence-grounded answers）**。最終輸出為一組結構化的**問答知識（QA knowledge）**，也就是以 QA pair 形式組織的**結構化儲存庫知識（structured repository knowledge）**。

這個階段的關鍵在於「先問再修」：不是直接根據問題關鍵字去定位可疑程式碼，而是先確認代理需要哪些**跨模組相依關係（cross-module dependencies）**、**隱式 API 契約（implicit API contracts）**或**資料流細節（data-flow details）**才能正確理解問題根源。

**第二階段：知識引導的修復（Knowledge-Informed Repair）**

此階段由**解決器（Resolver）**負責。Resolver 不再僅憑問題描述與原始程式碼上下文進行推理，而是將第一階段產出的 QA knowledge 一併納入提示（prompt），作為生成**有依據的修補程式（informed patches）**的基礎。由於這些知識已經過探索與證據支撐，Resolver 能減少因理解不足而導致的**事實性錯誤（factual errors）**，並加速原本**知識密集的修復階段（knowledge-intensive repair stages）**。

從方法論角度來看，ACQUIRE 的貢獻在於把「探索」從「修復導向策略（fix-driven strategies）」轉變為「理解導向策略」：探索的目標不是立刻找出可修改的位置，而是補足代理對儲存庫的事實理解。這種設計降低了後續修補階段因上下文不精確而產生的試誤成本，也讓錯誤更易於追溯——若修補失敗，可檢查是 Questioner 的問題設計不佳、Answerer 的答案有誤，還是 Resolver 的生成策略出了問題。

#### 實驗數據解讀

論文在 **SWE-bench Verified** 上進行評估，這是一個包含 500 個真實 GitHub issue 的基準資料集。主要評估指標為 **Pass@1**，即單次嘗試通過率，衡量代理在第一次生成的修補程式中能否通過所有相關測試。

根據摘要與引言，ACQUIRE 的主要實驗結果可歸納如下：

- **相較於基礎修復代理（base repair agent），Pass@1 最高提升 4.4 個百分點**。這表示在部分設定下，QA-driven 的知識獲取能顯著轉化為正確修補的機率提升。
- **相較於代表性的修復前探索方法（representative pre-repair methods），ACQUIRE 在兩種不同骨幹 LLM 上均一致表現更佳**。這說明其增益並非僅來自於特定模型的特性，而是方法架構本身具有跨模型穩定性。
- **額外成本與時間僅為適度增加（modest additional cost and time）**。雖然兩階段流程會引入額外的 token 消耗與執行步驟，但相較於知識不足導致反覆試誤所耗費的資源，這些前置成本被證明是划算的。

這些數據的實質意義在於：過去研究常將失敗歸因於 LLM 推理能力不足，但 ACQUIRE 的結果顯示，只要先補足**儲存庫理解（repository understanding）**，即使不更換更強大的模型，也能有效降低**事實性錯誤（factual errors）**。此外，「成本適度」這一點很重要，因為它意味著該方法在實務部署上具有可行性，不至於因前置探索過度昂貴而抵消修復效益。

不過，由於目前可取得的上下文未提供完整的數字表格，我們無法進一步分析不同問題類型、不同知識維度或不同模型規模下的細部表現。例如，4.4 個百分點的提升是否主要來自於複雜跨模組問題、是否在某些類別的問題上效果較弱、以及 token 成本與執行時間的具體比例，都值得在完整論文中進一步檢視。

#### 與現有研究的比較

現有自動化軟體問題解決（software issue resolution）方法大致可分為兩類，而 ACQUIRE 與兩者都有明確區隔：

**1. 直接修復導向方法**

許多 LLM-based coding agents 直接根據問題描述進行**基於關鍵字的定位（keyword-based localization）**與修補生成。這類方法的缺點在於：當問題涉及**跨模組相依關係（cross-module dependencies）**或**隱式 API 契約（implicit API contracts）**時，代理容易因缺乏背景知識而產生幻覺或違反未明文規定的使用規範。ACQUIRE 透過前置的 QA 知識獲取，先把這些隱性知識缺口顯性化，再進行修補，從根本上減少這類失敗。

**2. 修復前儲存庫探索方法（pre-repair repository exploration）**

近年來的研究嘗試在修補前先探索儲存庫，例如 LingmaAgent 透過連結問題關鍵字與程式碼實體，產生**結構化摘要（structural summaries）**以提供更廣泛的**程式碼庫上下文（codebase context）**。然而，這些方法本質上仍是**修復導向策略（fix-driven strategies）**：它們根據問題關鍵字或被動地擴展上下文，卻沒有明確辨識代理「還不懂什麼」。結果常取得**不精確的上下文（imprecise context）**，不僅無法彌補**理解不足（understanding deficit）**，有時甚至強化錯誤假設。

相較之下，ACQUIRE 的差異化優勢在於：

- **明確的知識缺口建模**：透過 Questioner 將問題拆解為針對性問題，主動指出需要哪些知識。
- **證據導向的回答**：Answerer 的回答必須基於實際探索證據，提升**事實可靠的理解（factually reliable understanding）**。
- **階段解耦**：知識獲取與修補生成分離，使兩個階段可獨立優化，也便於錯誤分析與除錯。

**限制與潛在弱點**

儘管 ACQUIRE 在概念上具有優勢，仍存在一些值得注意的限制：

- **問題品質依賴性**：若 Questioner 提出的問題不夠全面或偏離核心，後續 Answerer 與 Resolver 都難以彌補。
- **答案錯誤的傳播**：Answerer 雖強調證據，但仍可能產生錯誤詮釋；這些錯誤會直接進入 Resolver 的輸入，導致「有依據但錯誤」的修補。
- **分類法的覆蓋範圍**：目前的類別導向問題分類法可能無法涵蓋所有類型的儲存庫知識，對於特定領域（如嵌入式系統、分散式系統）可能需要擴展。
- **對簡單問題的額外開銷**：對於僅需關鍵字定位即可解決的簡單 bug，QA 階段可能帶來不必要的成本。
- **骨幹模型依賴**：雖然實驗顯示跨兩種 LLM 均有效，但極小或能力較弱的模型可能難以勝任 Questioner 的問題分解或 Answerer 的證據整合。

#### 可重現性評估

從目前可取得的上下文來看，論文並未明確說明是否公開原始碼、提示模板、實驗設定或模型權重。因此，在**可重現性（reproducibility）**方面的評估如下：

- **資料集**：SWE-bench Verified 是公開基準，任何研究者皆可取得，這部分沒有障礙。
- **方法實作**：雖然圖 1 提供了高階架構，但 Questioner 的具體提示設計、Answerer 的探索工具組合、類別導向問題分類法的完整清單、以及 Resolver 如何將 QA knowledge 融入提示等細節，仍需依賴論文正文或釋出的程式碼才能完整重現。
- **模型與成本**：實驗使用兩種骨幹 LLM，但模型版本、取樣參數、token 計算方式與執行時間測量方法若未公開，將影響結果的比較與再現。
- **再現難度**：由於 ACQUIRE 涉及多個代理協作與多輪工具呼叫，即使方法描述清楚，實作上的工程細節（如探索終止條件、錯誤處理、快取機制）也會顯著影響效能與成本。

綜合而言，ACQUIRE 的可重現性目前處於「概念清楚、細節待確認」的狀態。若作者能釋出原始碼與實驗腳本，將大幅提升社群驗證與後續改進的可能性。

#### 未來研究方向

基於 ACQUIRE 的架構與現有侷限，未來研究可朝以下方向延伸：

1. **動態知識精煉與多輪問答**
   目前的兩階段設計可擴展為迭代式流程：Resolver 在修補過程中若發現新的知識缺口，可回頭要求 Questioner 提出新問題，形成「探索—修補—再探索」的迴路，而非一次性知識獲取。

2. **自適應問題分類法**
   針對不同類型的儲存庫或問題領域，自動學習或調整問題類別，例如對於資料庫相關問題強化 schema 與 transaction 語義，對於前端框架問題強化生命週期與事件處理。

3. **答案正確性的自動驗證**
   引入靜態分析、符號執行或測試生成機制，自動檢查 Answerer 產生的答案是否與程式碼實際行為一致，降低錯誤知識傳播至 Resolver 的風險。

4. **與測試生成技術整合**
   將 QA knowledge 同時用於修補生成與測試案例生成，使代理不僅能產生正確 patch，還能主動驗證 patch 是否涵蓋問題情境。

5. **輕量化與成本最佳化**
   研究如何在保持效能的前提下，減少 Questioner 與 Answerer 的呼叫次數，例如透過檢索增強生成（Retrieval-Augmented Generation, RAG）預先篩選相關程式碼，或讓小模型負責問題分解、大模型負責答案生成。

6. **跨儲存庫知識遷移**
   探索是否能將某個儲存庫中學到的 QA knowledge 模式遷移到相似專案，以減少面對新程式碼庫時的冷啟動成本。

7. **人機協作與可解釋性**
   讓開發者能檢視、編輯或補充 Questioner 產生的問題與 Answerer 的答案，將 ACQUIRE 從全自動代理轉變為可解釋的輔助工具，提升實務採用意願。

8. **超越 Pass@1 的評估指標**
   除了單次嘗試通過率，未來可引入修補品質、可讀性、安全性、對既有 API 契約的遵守程度，以及知識獲取階段對最終錯誤類型的影響分析，建立更全面的評估框架。

## 論文問答

**Q1：基於 LLM 的程式設計代理在軟體問題解決中面臨什麼核心挑戰？**

A：這類代理經常因為對儲存庫理解不足而產生事實性錯誤，即使具備強大的推理能力也難以彌補。問題描述通常只包含外部症狀，卻缺乏跨模組相依關係、隱式 API 契約與資料流細節等儲存庫內部知識。因此，代理容易退化成基於關鍵字的淺層定位，無法正確追蹤故障根源。

**Q2：現有的修復前儲存庫探索方法為何無法有效解決上述問題？**

A：現有方法多採用修復導向策略，在探索儲存庫時並未先識別代理的知識缺口，只是根據問題關鍵字或結構化摘要擴大上下文。這種方式取得的上下文往往不精確，甚至會加深代理對程式碼庫的誤解。結果是，它們無法真正彌補理解不足，只是把更多雜訊餵給後續的修補生成階段。

**Q3：為什麼儲存庫理解對軟體問題解決特別重要？**

A：正確的修補需要掌握問題描述中未明載的內部知識，例如模組邊界間的互動與未明文規定的 API 使用規範。缺乏這些知識時，代理不僅容易失敗，還會付出極高的成本：知識不足的嘗試可能消耗成功解析四倍以上的 token 成本與近兩倍的執行步驟。因此，補強儲存庫理解是提升自動化問題解決效率與正確性的關鍵。

**Q4：ACQUIRE 的核心方法架構是什麼？**

A：ACQUIRE 是一個兩階段框架，它將知識獲取與修補程式生成明確解耦。第一階段由提問者與回答者協作，透過問答形式獲取結構化儲存庫知識；第二階段再由解決器利用這些問答知識生成有依據的修補。這種設計讓代理在動手修改程式碼之前，先建立對程式碼庫的明確理解。

**Q5：相較於先前方法，ACQUIRE 的關鍵創新是什麼？**

A：ACQUIRE 的關鍵創新在於將隱性知識缺口轉化為顯性、結構化的問答知識，而非直接以產生修補為目標進行探索。它模仿資深開發者面對陌生程式碼時會先提出診斷性問題、建立理解後再行修復的工作方式。透過這種問答導向的知識獲取，代理能夠在修復開始前確認自己缺乏哪些儲存庫知識，並以證據為基礎加以補足。

**Q6：提問者與回答者的設計選擇各自扮演什麼角色？**

A：提問者負責將問題描述分解為多個互補知識維度上的針對性問題，例如機制行為、設計用法與環境設定等；回答者則針對每個問題自主探索儲存庫，並產出基於證據的答案。兩者協作形成的問答知識集，不僅結構化且經過探索驗證，能夠為後續解決器提供事實可靠的理解基礎。

**Q7：本研究使用什麼基準來評估 ACQUIRE？**

A：實驗採用 SWE-bench Verified 作為主要評估基準，該資料集包含 500 個真實的 GitHub 問題。這些問題來自真實世界的開源儲存庫，能夠嚴格檢驗自動化問題解決方法在實際場景下的修補正確性。選用此基準也有助於與現有代表性的預修復方法進行公平比較。

**Q8：ACQUIRE 的主要實驗結果為何？**

A：在 SWE-bench Verified 上，ACQUIRE 相較於基礎修復代理最高可將 Pass@1 提升 4.4 個百分點。它在兩個不同的骨幹大型語言模型上，都一致優於代表性的修復前探索方法。更重要的是，這些效能增益僅伴隨適度的額外成本與時間開銷，顯示其具備實用價值。

**Q9：本研究是否進行消融研究或與其他方法比較？**

A：文中將 ACQUIRE 與多種代表性的修復前方法進行比較，例如透過關鍵字連結程式碼實體並建立結構化摘要的 LingmaAgent。實驗橫跨兩個骨幹模型，以驗證問答導向知識獲取策略的穩定性與泛用性。這些比較結果顯示，單純擴大上下文不如先識別並填補知識缺口來得有效。

**Q10：ACQUIRE 最適合應用在哪些實務場景？**

A：ACQUIRE 特別適合處理跨越多個模組、需要深入理解程式碼庫的知識密集型錯誤。當問題描述不完整、涉及隱式 API 契約，或開發者對該儲存庫並不熟悉時，這種先理解後修復的機制能顯著降低錯誤風險。它也適合整合到企業內部的大型程式碼庫維護流程中，協助工程師快速建立正確的上下文。

**Q11：在實際產品化部署 ACQUIRE 時，需要考量哪些因素？**

A：首先需權衡額外的 token 成本與執行時間，以及修補正確率提升所帶來的整體效益。其次，提問者產出的問題品質與覆蓋度會直接影響後續修復成效，因此需要持續監控與最佳化。最後，與現有開發工具鏈和程式設計代理工作流的整合方式，也會決定其在實際產品中的採用難度。

**Q12：這項研究對整個領域可能帶來什麼影響？**

A：本研究首次將儲存庫層級的問答機制整合進軟體問題解決流程，開啟了一個新的研究方向。它證明「先獲取知識、再生成修補」的解耦設計，能夠有效提升自動化程式設計代理的可靠性。未來這種架構可能影響更多程式設計代理的設計典範，促使社群更重視理解階段而非僅追求修補生成速度。

**Q13：ACQUIRE 有哪些已承認的限制？**

A：ACQUIRE 的成效高度依賴提問者能否正確識別關鍵的知識缺口，若問題方向偏離，後續回答與修補也會受到影響。此外，回答者的自主探索能力決定了答案的證據品質，探索失準可能導致錯誤的理解基礎。雖然額外成本被描述為適度，但對於需要極低延遲或高頻呼叫的場景，仍可能構成採用障礙。

**Q14：ACQUIRE 仍可能遇到哪些失敗案例？**

A：當問題所需知識超出儲存庫內部範圍，例如外部協定或第三方服務行為時，ACQUIRE 可能無法自行補足。若問題症狀模糊或涉及多個交錯的故障根源，提問者可能產出不相關的問題，導致後續修補偏離重點。另外，只要回答者檢索到錯誤證據，解決器仍可能基於這些錯誤資訊生成不正確的修補。

**Q15：未來有哪些值得探索的研究方向？**

A：未來可進一步強化提問者的診斷能力，使其能夠根據初步答案動態調整後續問題，形成互動式知識獲取。另一個方向是讓代理在必要時主動向人類開發者請求澄清，以處理極度模糊的問題描述。此外，將這種問答導向的知識獲取框架擴展到程式碼審查、重構或測試生成等其他軟體工程任務，也具有很大的應用潛力。

## 適用場景

1. **企業內部大型程式碼庫的維護工單處理**  
   當開發團隊面對數百萬行程式碼、模組邊界複雜的私有儲存庫時，ACQUIRE 可在生成修補前，先由 Questioner 針對工單提出「某 API 的隱式契約為何」「資料流如何跨模組傳遞」等問題，再由 Answerer 自主探索並產生基於證據的問答知識，降低因儲存庫理解不足導致的事實性錯誤。

2. **開源專案 issue 自動化修復（如 SWE-bench 類任務）**  
   對於來自 GitHub 的問題描述，ACQUIRE 適合處理需要跨檔案追蹤故障根源、理解隱式 API 契約的知識密集型案例，能提升 Pass@1，並減少基於關鍵字定位造成的誤判。

3. **新進開發者或外包團隊的入門修復輔助**  
   當人員對程式碼庫不熟悉時，可先執行第一階段問答導向的儲存庫知識獲取，將隱性知識缺口轉為結構化問答，作為後續人工修復或 Resolver 自動生成修補的參考。

4. **遺留系統重構前的影響範圍分析**  
   在動手修改老舊模組前，利用 Questioner 提出設計與使用方式、環境相依等問題，Answerer 回傳證據導向答案，幫助團隊建立事實可靠的理解，避免破壞跨模組相依關係。

5. **CI/CD 中的智慧化缺陷預檢與上下文補強**  
   將 ACQUIRE 嵌入持續整合流程，在測試失敗或靜態分析報告觸發後，先執行知識獲取階段，為後續自動修復代理或審查工具提供精確的程式碼庫上下文。

## 實作前置條件

### 資料條件
- **可存取的完整儲存庫**：需有原始碼、相依設定、測試檔案與版本歷史；若為私有專案，需額外處理授權與機敏資料脫敏。
- **問題描述與結構化模板**：每個 issue 需包含現象、重現步驟、預期與實際結果；建議預先將 GitHub issue 轉換為 ACQUIRE 可讀取的結構化模板。
- **領域詞彙與知識分類**：需定義 Questioner 使用的問題分類法（如機制與行為、設計與使用方式、環境等），並可依專案特性擴充。

### 運算條件
- **大型語言模型 API 或本地部署**：Questioner、Answerer、Resolver 各需呼叫 LLM；Answerer 還需反覆執行檔案搜尋、符號定位與程式碼閱讀工具。
- **工具執行環境**：需支援程式碼搜尋（grep、LSP、AST 解析）、測試執行與沙箱環境，以便 Answerer 進行自主探索並驗證答案。
- **成本與延遲預算**：雖然論文顯示額外成本與時間適中，但仍需預留比純修復導向代理更多的 token 成本與執行步驟。

### 技能條件
- **熟悉 LLM 代理設計與提示工程**：能設計 Questioner 的提問策略與 Answerer 的探索動作空間。
- **具備軟體工程除錯經驗**：能判斷問答品質、設計知識分類法，並驗證 Resolver 產出的修補。
- **基礎 MLOps / DevOps 能力**：能將多代理流程部署為可重複執行的服務，並監控 token 消耗與執行步驟。

## 實作步驟建議

1. **建立結構化問題輸入**  
   將原始 issue 描述轉換為固定模板，擷取關鍵資訊（錯誤現象、涉及模組、重現指令），作為 Questioner 的輸入。

2. **設計知識分類法與提問策略**  
   依專案特性定義互補的知識維度（例如：機制與行為、設計與使用方式、環境設定），並撰寫提示詞讓 Questioner 針對每個維度產生針對性問題。

3. **建置 Answerer 的自主探索工具箱**  
   整合程式碼搜尋、LSP 跳轉、AST 查詢、測試執行與文件檢索等工具，使 Answerer 能針對每個問題在儲存庫中尋找證據，並產生基於證據的答案。

4. **執行第一階段：問答導向的儲存庫知識獲取**  
   讓 Questioner 與 Answerer 協作產出 QA knowledge set；每個答案需標註來源檔案、程式碼片段與推理鏈，以便後續追蹤與人工審查。

5. **執行第二階段：知識引導的修補生成**  
   將結構化問答知識餵給 Resolver，生成有依據的修補程式；此處可保留原始 issue 描述作為高階目標，但讓 Resolver 優先參考 QA 知識。

6. **驗證、迭代與回饋**  
   對 Resolver 產出的 patch 執行回歸測試；若失敗，可將錯誤資訊回饋至 Questioner，補充新的知識缺口並重新執行知識獲取。

7. **產品化部署**  
   將兩階段流程封裝為 API 或 CI 外掛，加入成本與步驟上限、逾時機制、答案來源稽核與人工覆核閘門。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **問答品質不穩定** | Questioner 可能提出過於籠統或偏離核心的問題，Answerer 也可能給出錯誤或片面的答案。 | 引入知識分類法與範例提示，並對答案進行來源標註與一致性檢查；必要時加入人工審查。 |
| **成本與延遲上升** | 兩階段流程會增加 token 成本與執行步驟，可能不適合需要即時回應的場景。 | 設定問題數量上限、探索深度上限與快取機制；對簡單 issue 可跳過知識獲取階段。 |
| **過度依賴問答知識** | Resolver 可能忽略原始 issue 描述，或將不完整的 QA 知識當作唯一依據。 | 在 Resolver 提示中同時保留 issue 描述與 QA 知識，並要求它標註每個修改所依據的證據。 |
| **工具呼叫失敗或環境差異** | Answerer 自主探索時可能遇到編譯失敗、測試無法執行或權限不足。 | 使用容器化沙箱與標準化環境，並對工具呼叫結果進行錯誤處理與重試。 |
| **知識分類法遷移困難** | 為某專案設計的分類法可能無法直接套用至其他程式語言或架構。 | 將分類法設計為可設定檔，並在每個新專案導入前進行小規模試驗與調整。 |

## 與其他技術的整合建議

- **與現有 IDE / 編輯器整合**  
  可將 ACQUIRE 的 Questioner 與 Answerer 包裝為 VS Code / JetBrains 外掛，讓開發者在撰寫修補前先取得結構化儲存庫知識，並在側邊欄顯示 QA 知識與來源連結。

- **與檢索增強生成（RAG）系統整合**  
  將 Answerer 探索過程中產生的 QA 對儲存至向量資料庫，後續類似 issue 可直接檢索相關問答知識，減少重複探索成本。

- **與傳統靜態分析 / 符號執行工具整合**  
  在 Answerer 的工具箱中接入靜態分析器（如 CodeQL、pyright）與 LSP，提升跨模組相依關係與資料流細節的準確性。

- **與 CI/CD 及 issue 追蹤系統整合**  
  將 ACQUIRE 部署為 GitHub Actions / GitLab CI 工作，在 issue 被標記為 `bug` 或測試失敗時自動觸發，並將 QA 知識與修補建議回寫至 issue 討論串。

- **與現有修復導向代理整合**  
  ACQUIRE 可作為前置模組，為其他 fix-driven strategies（如 LingmaAgent）提供更精確的程式碼庫上下文，形成「先理解、後修復」的混合管線。

## 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦論文的圖一與兩階段流程，理解「為什麼要先問問題再修 bug」這個核心概念；不必一開始就深入提示工程，重點是體會「把隱性知識缺口變成顯性問答」如何幫助程式設計代理減少事實性錯誤。

**AI 工程師**：請仔細研究 Questioner、Answerer、Resolver 三個角色的分工與協作介面，特別是 Questioner 的知識分類法與 Answerer 的自主探索動作設計；實作時應優先處理答案的來源標註、探索成本控制，以及 Resolver 如何有效利用 QA 知識。

**研究人員**：本文的貢獻在於將儲存庫層級問答整合進軟體問題解決流程，並以實驗證明其優於修復導向的探索方法；可進一步探討問題分類法的最佳化、多輪問答的收斂條件、問答知識對不同規模模型的影響，以及與其他知識獲取範式（如主動學習、規劃式探索）的結合。

**產品經理**：請將 ACQUIRE 視為一種「降低自動修復錯誤率、提升可解釋性」的解決方案；評估導入時需權衡額外成本與時間對開發流程的影響，並優先應用於知識密集型、跨模組問題較多的維護場景，同時規劃人工覆核與知識沉澱機制。
