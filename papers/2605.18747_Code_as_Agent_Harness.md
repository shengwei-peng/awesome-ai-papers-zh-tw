## 摘要翻譯

近期，大型語言模型（Large Language Models, LLMs）在理解與生成程式碼方面展現出強大能力，涵蓋從競技程式設計（competitive programming）到儲存庫層級軟體工程（repository-level software engineering）等領域。在新興的智慧體系統（agentic systems）中，程式碼不再僅僅是目標輸出，而是日益成為智慧體推理、行動、環境建模（environment modeling）與基於執行的驗證（execution-based verification）之運作基底（operational substrate）。我們透過智慧體框架（agent harness）的視角來詮釋這一轉變，並提出「程式碼作為智慧體框架（code as agent harness）」：一個將程式碼置於智慧體基礎設施（agent infrastructure）核心的統一觀點。為了系統性地研究這一視角，我們圍繞三個相互連結的層次來組織本綜述。首先，我們探討框架介面（harness interface），在此層次中，程式碼將智慧體連結至推理、行動與環境建模。其次，我們審視框架機制（harness mechanisms）：包括用於長程執行（long-horizon execution）的規劃、記憶與工具使用，以及使框架具備可靠性與適應性的回饋驅動控制（feedback-driven control）與最佳化（optimization）。第三，我們討論如何將框架從單智慧體系統擴展至多智慧體設定（multi-agent settings），其中共享程式

## 深度分析

#### 方法論解析

本文提出「程式碼作為智慧體框架（Code as Agent Harness）」之核心方法論，並非傳統意義上的演算法或模型架構，而是一個統一的概念性框架（conceptual framework）與分類學（taxonomy），旨在重新定位程式碼（code）在智慧體系統（agentic systems）中的角色。作者首先區分三個相互耦合的要素：模型內部能力（model-internal capabilities）、系統提供的框架基礎設施（system-provided harness infrastructure），以及智慧體主動生成的程式碼產物（agent-initiated code artifacts）。有別於既有研究將程式碼視為大型語言模型（LLMs）的最終輸出產物，本文主張程式碼應作為可執行（executable）、可檢視（inspectable）、具狀態（stateful）的運作基底（operational substrate）。

在此基礎上，作者建構三層次的分析架構。第一層為框架介面（Harness Interface），探討程式碼如何連結推理（reasoning）、行動（action）與環境建模（environment modeling）。在推理面，程式輔助推理（program-aided reasoning）將中介推理（intermediate reasoning）外部化為可執行的計算步驟，並透過執行追蹤（execution traces）與執行期回饋（runtime feedback）進行驗證；在行動面，程式碼轉行動（code to actions）機制將高層意圖轉譯為可執行策略（executable policies），服務於具身智慧體（embodied agents）與 GUI/OS 自動化（GUI/OS automation）；在環境建模面，程式狀態、儲存庫與測試回饋（test feedback）構成結構化的環境表徵。

第二層為框架機制（Harness Mechanisms），處理長程執行（long-horizon execution）中的規劃（planning）、記憶（memory）、工具使用（tool use）與回饋驅動控制（feedback-driven control）。規劃包含執行前分解（pre-run decomposition）與執行期調整（runtime adjustment）；記憶區分為工作記憶（working memory）與長期記憶（long-term memory），並涵蓋線性／結構化（linear/structural）的經驗組織形式；工具使用則涉及工具搜尋與選擇（tool search & selection）以及動態的工具建立（tool creation）；控制機制透過執行期錯誤回饋（runtime error feedback）、靜態分析（static analysis）與紅隊演練（red-teaming）實現自我修復與穩健性。

第三層為擴展框架（Scaling the Harness），將視角從單一智慧體延伸至多智慧體設定（multi-agent settings）。此處強調共享程式碼產物（shared code artifacts）——如共享儲存庫（shared repo）、測試案例與執行狀態——如何支援多智慧體協調（multi-agent coordination）。作者進一步提出智慧體角色分類（agent role taxonomy），包括 Manager、Planner、Coder、Reviewer、Tester 等，並區分集中式（centralized）、精簡式（streamlined）、協作式（collaborative）與分散式（distributed）等多種協作架構，以及對抗性辯論（adversarial debate）等驗證機制。

#### 實驗數據解讀

必須首先指出，本文本質為回顧性綜論（survey / position paper），而非提出新模型並進行量化驗證的實證研究。因此，文中並未呈現傳統意義上的實驗數據、基準測試（benchmarks）結果或模型權重（model weights）。其「數據」主要體現為對現有系統與應用領域的系統性歸納，以及圖一所示之 Taxonomy of Code as Agent Harness。

從方法論的觀點來看，本文的「實驗」可理解為一種概念驗證（proof-of-concept）的後設分析：作者援引 Claude Code、Codex、LangChain 與企業級智慧體平台等代表性系統，作為支撐三層框架的經驗證據。這些系統在程式編寫助理（coding assistants）、科學發現（scientific discovery）、個人化（personalization）、DevOps 與企業工作流程（enterprise workflows）等領域的實踐，被重新詮釋為「程式碼作為智慧體框架」的具體例證。例如，Claude Code 與 Codex 展現了智慧體主動生成並迭代程式碼產物的過程；LangChain 則體現了工具使用與記憶機制的系統化整合。

由於缺乏量化指標（如 pass@k、任務成功率或人類偏好分數），本文的說服力主要來自其分類學的解釋力與涵蓋範圍。讀者無法從文中取得某一特定方法在某一基準上的優劣比較，而應將此綜論視為一張「統一路徑圖（unified roadmap）」，其價值在於為後續的實證研究提供問題意識與分類依據。這也意味著，文中提出的多項主張——例如回饋驅動控制能提升長程執行的可靠性——仍待未來研究透過控制實驗加以驗證。

#### 與現有研究的比較

相較於既有文獻，本文的最大貢獻在於視角轉移（paradigm shift）。過去關於 LLMs 與程式碼的研究，主要聚焦於程式合成（program synthesis）、程式理解（program understanding）與競技程式設計（competitive programming），將程式碼視為最終任務產出（target artifact）。即便在智慧體領域，既有對於 agent harness 的討論（如相關文獻 [13]–[23]）也多著重於系統層面的基礎設施——例如沙盒（sandboxes）、API 銜接、權限邊界與執行迴圈——而較少將「智慧體主動生成並持續演化的程式碼產物」置於分析的核心。

本文明確區分「系統提供的框架基礎設施」與「智慧體主動生成的程式碼產物」，並以後者作為組織中心（organizing center）。這使得本文能夠統合以往分散的研究脈絡：程式輔助推理（如 PAL、PoT）不再只是提升數學推理準確率的技巧，而是框架介面中「外部化推理（externalize inference）」的具體表現；機器人領域的程式化策略生成不再只是動作規劃，而是「程式碼轉行動」的體現；軟體工程中的測試驅動開發與 PR 工作流程（PR workflow）則成為多智慧體協調中的共享驗證機制。

然而，本文作為高層次綜論，其局限性在於技術細節的顆粒度較粗。例如，對於框架機制中的記憶（memory）如何具體實作（是基於檢索增強生成 RAG、還是基於可微分記憶網路？）、規劃（planning）在面對指數級搜尋空間時的剪枝策略、以及多智慧體間共享狀態（shared state）的一致性協議等，文中僅點出問題而未深入比較各技術路線的優劣。此外，「程式碼作為框架」的定義邊界在實作中可能趨於模糊：當系統基礎設施（如 LangChain 的 expression language）本身即由程式碼構成時，區分「系統提供」與「智慧體主動生成」的界線需要更精細的操作型定義。

#### 可重現性評估

就可重現性（reproducibility）而言，本文屬於概念性綜論，並未釋出開源程式碼、資料集或模型權重。其重現性主要仰賴概念框架的清晰度與分類學的邏輯一致性，而非實驗流程的標準化。從提供的上下文觀之，作者並未宣稱提供可執行的參考實作，而是邀請研究社群以「程式碼作為智慧體框架」的透鏡重新審視現有系統。

對於希望驗證或延伸此框架的研究者，可重現性路徑包含以下幾點：首先，圖一的分類學（taxonomy）具有明確的層次結構，研究者可以據此對現有或新開發的智慧體系統進行編碼（coding）與定位。其次，文中援引的系統（如 Claude Code、Codex、LangChain）多為公開可取得或已有詳細技術報告的商業／開源平台，研究者可以透過操作這些平台來復現作者所描述的現象（例如觀察智慧體如何透過執行期回饋迭代程式碼）。然而，由於缺乏標準化的評估協議，不同研究者對於「某一系統是否體現了 harness mechanisms 中的特定機制」可能產生詮釋上的分歧。

值得指出的是，本文提出的開放挑戰——如無迴歸的框架改進（regression-free harness improvement）與不完整回饋下的驗證（verification under incomplete feedback）——本身即暗示了可重現性的難題：若智慧體框架持續自我修改，則傳統的固定基準測試可能不足以捕捉其動態行為。因此，本文的可重現性不僅是技術實作的問題，更涉及評估方法論的重新設計。

#### 未來研究方向

基於本文所勾勒的框架與開放挑戰，未來研究可沿以下方向深化：

第一，**超越最終任務成功率的評估（evaluation beyond final task success）**。現有基準多採二元式的任務完成指標，未來需發展針對中介推理品質、框架穩健性與長期狀態一致性的細粒度評估指標，特別是衡量執行期調整（runtime adjustment）與規劃修正的過程獎勵（process rewards）。

第二，**不完整回饋下的驗證（verification under incomplete feedback）**。在真實環境中，智慧體往往無法取得完整的執行追蹤或測試覆蓋。未來研究可探索結合靜態分析（static analysis）、形式化驗證（formal verification）與機率性程式分析，以在部分可觀測的環境中建立可信度（confidence）估計機制。

第三，**無迴歸的框架改進（regression-free harness improvement）**。當智慧體動態建立工具（tool creation）或修改共享儲存庫（shared repo）時，如何確保新產生的程式碼產物不會破壞既有能力，類似於軟體工程中的迴歸測試（regression testing），將是框架工程（harness engineering）的關鍵課題。這可能涉及版本控制、差異化測試生成與能力保留約束（capability-preserving constraints）的整合。

第四，**多智慧體間一致的共享狀態（consistent shared state across multiple agents）**。隨著框架從單一智慧體擴展至多智慧體設定，共享程式碼產物的同步與衝突解決機制成為瓶頸。未來可借鏡分散式系統中的共識演算法（consensus protocols）與交易記憶體（transactional memory），設計適用於智慧體協作的狀態一致性模型。

第五，**安全關鍵行動的人類監督（human oversight for safety-critical actions）**。在 DevOps、企業工作流程或科學發現（scientific discovery）等場景中，智慧體可能觸發具有高風險的執行行為。未來需設計人類參與式執行（human-in-the-loop execution）的介面與中斷機制，並研究如何在保留人類監督的同時，不過度削弱長程執行的自主性。

第六，**擴展至多模態環境（extensions to multimodal environments）**。當前框架雖已涵蓋具身智慧體與 GUI/OS 自動化，但程式碼作為框架如何與視覺基礎定位（visual grounding）、功能可供性定位（affordance grounding）及連續的物理動態深度整合，仍是未開拓的領域。未來可探索以程式碼為中介，統合視覺、語言與動作的多模態表示學習。

最後，一個跨領域的後設方向是建立「框架描述語言（harness description language）」的標準化，使得不同研究團隊能夠以統一語法定義智慧體角色、記憶結構與工具介面，從而提升整個領域的可重現性與可比較性。

## 論文問答

**Q1：「程式碼作為智慧體框架」這一視角旨在解決什麼根本問題？**
A：傳統觀點往往將程式碼僅視為大型語言模型最終產出的目標產物，忽略了它在智慧體系統中作為運作基底的潛力。這種狹隘的視角無法解釋智慧體如何透過可執行的程式在長程執行中進行推理、行動與維持狀態。本文主張，唯有將程式碼視為智慧體框架基礎設施本身，才能為可檢視、可驗證且具持續互動能力的 AI 系統提供統一的運作基底。

**Q2：現有的方法或調查為何無法充分支援長期運作的智慧體系統？**
A：現有的調查通常聚焦於程式碼生成這項最終產出，或將模型推理視為純粹的內部過程，忽略了長程執行所需的系統層級基礎設施。這些方法經常將推理、行動與環境建模切割為彼此脫節的元件，導致智慧體難以利用執行期回饋來動態修正行為。因此，這類做法在長期任務中缺乏可靠性，因為它們沒有建立一個由程式碼產物媒介模型與外部世界之間的封閉迴路機制。

**Q3：為何將程式碼置於智慧體框架的核心，而非僅作為輸出，具有重要性？**
A：將程式碼置於框架核心，能將其轉化為可執行、可檢視且具狀態的媒介，從而銜接模型的內部能力與真實世界的行動。這種轉變使智慧體得以將中介推理外部化為可執行步驟，透過執行追蹤驗證進度，並在跨步驟的任務中維持持續的記憶與狀態。如此一來，它真正解決了自主性的瓶頸：問題不僅在於基礎模型的推理能力，更在於連接模型輸出與長期行動及持久狀態的系統可靠性。

**Q4：本文的核心方法論貢獻是什麼？**
A：本文提出了一個統一的三層分類架構——框架介面、框架機制與規模化擴展——以系統性地刻畫程式碼如何作為智慧體基礎設施運作。此架構將文獻組織為三個層次：首先探討程式碼如何作為推理與行動的介面，其次檢視其如何支撐規劃與記憶等機制，最後討論其如何擴展至多智慧體協調。透過聚焦於智慧體主動生成的程式碼產物，而非僅限於系統預先提供的基礎設施，本文為理解可執行的智慧體系統提供了連貫的理論透鏡。

**Q5：「程式碼作為智慧體框架」這一視角的關鍵創新為何？**
A：其關鍵創新在於重新概念化程式碼的角色，將其從被動的目標產物轉變為智慧體在任務迴圈中主動創建、執行、觀察與修正的動態運作基底。不同於僅預先定義工具與 API 的靜態框架工程，此視角強調智慧體動態生成的互動式程式碼物件，例如暫時性工具、迴歸測試與可執行工作流程。這種觀點將推理、行動與環境建模統一於單一可執行媒介之下，從而實現封閉迴路的適應與驗證。

**Q6：在設計這三層框架時，有哪些關鍵的設計選擇？**
A：第一層將程式碼設計為連接模型輸出與推理、行動及環境表示的框架介面，確保所有互動皆可程式化且可檢視。第二層將程式碼嵌入框架機制之中，涵蓋規劃、記憶、工具使用與回饋驅動控制，以支援超越單步生成的長期可靠性。第三層則將這些程式碼產物擴展為共享且持久的物件，使多智慧體能透過共享儲存庫與執行狀態進行協調、審查與驗證。

**Q7：本文回顧了哪些具代表性的方法與應用領域來支撐其框架？**
A：本文涵蓋了競技程式設計、儲存庫層級軟體工程、機器人控制、GUI/OS 自動化與科學發現等多元領域，回顧了程式輔助推理、可執行策略與執行期回饋系統等方法。文中以 Claude Code、Codex、LangChain 及企業級智慧體平台等代表性系統為例，說明程式碼產物在實務中的運作方式。這些案例為三層分類架構提供了實證基礎，展示程式碼如何在不同環境中介接推理、行動與狀態。

**Q8：從這項調查的綜合分析中，可以得出哪些關鍵發現或洞察？**

## 實務應用指南

### 適用場景

1. **企業級儲存庫維護與 DevOps 自動化**：將程式碼同時作為操作標的與框架介面，讓智慧體在共享儲存庫中執行重構、撰寫回歸測試、並透過執行期回饋驗證變更，實現 Repository-level software engineering 的自主化。
2. **跨系統企業工作流程編排**：利用智慧體產生的可執行腳本作為行動策略，串接不同 SaaS 的 行動 API，並以程式狀態與執行追蹤作為環境建模基礎，實現長程執行的業務流程自動化。
3. **科學發現與實驗室自動化**：在假說驗證迴圈中，以程式碼外部化中介推理與資料分析步驟，透過模擬迴圈與實驗室自動化設備執行，並用測試回饋與模擬器回饋修正實驗設計。
4. **多智慧體協作程式開發**：讓 Planner、Coder、Reviewer、Tester 等角色透過共享程式碼產物（如暫存工具、DSL、PR 工作流程）進行協作，利用對抗性辯論與基於執行的驗證確保產出品質。

### 實作前置條件

- **資料**：結構化環境狀態（DOM 狀態、儲存庫狀態、機器人感測資料）、API 規格與工具描述、歷史執行追蹤與測試回饋資料、長期記憶所需的偏好記憶或使用者狀態紀錄。
- **運算**：具備沙箱隔離的程式碼執行環境（支援執行期回饋與靜態分析）、LLM 推論基礎設施（支援多輪工具使用與長上下文）、向量資料庫或圖資料庫作為工作記憶與長期記憶儲存。
- **技能**：軟體工程能力（程式合成、程式理解、測試設計）、提示工程與代理迴路設計、API 與權限邊界管理、安全關鍵行動的人類監督機制設計。

### 實作步驟建議

1. **定義框架介面**：選定程式碼作為推理、行動與環境建模的共同基底。設計外部化推理的輸出格式（如結構化程式碼區塊），並定義行動 API 與環境狀態的程式化表示（例如將 GUI 狀態轉為可操作的程式物件）。
2. **建置安全執行沙箱**：部署具備網路隔離與權限邊界的執行環境，使智慧體產生的程式碼可安全執行，並能回傳執行期錯誤回饋、執行追蹤與程式狀態變化。
3. **實作框架機制**：導入執行前分解的規劃器、管理工作記憶與長期記憶的狀態儲存、以及工具搜尋與工具建立模組。確保智慧體能依據執行期回饋進行執行期調整。
4. **封閉驗證迴路**：建立基於執行的驗證管線，將回歸測試、靜態分析與執行期回饋整合至代理迴路，實現回饋驅動控制。對於關鍵步驟，插入人類參與式執行節點。
5. **擴展至多智慧體與多模態**：從單一智慧體搜尋過渡至多智慧體協調架構（集中式、協作式或分散式），透過共享儲存庫與共享狀態實現多角色協作，並逐步擴展至視覺基礎定位與多模態環境。

### 潛在風險與注意事項

- **沙箱逃逸與惡意程式碼**：智慧體可能產生具破壞性的程式碼。務必實作嚴格的沙箱隔離、最小權限原則，並對檔案系統與網路呼叫進行細粒度控管。
- **不完整回饋導致的錯誤驗證**：執行成功不代表語意正確。應結合靜態分析、紅隊演練與對抗性辯論，避免智慧體利用回饋漏洞產生假性通過的程式碼。
- **狀態不一致與迴歸**：多智慧體共享狀態時，可能因並發修改導致狀態分歧。需建立版本控制、鎖定機制與無迴歸的框架改進流程，確保更新提示或工具時不損害既有能力。
- **安全關鍵行動的人類監督缺口**：在部署至生產環境或實體機器人前，必須設計明確的人類監督閘門，避免不可逆的危險行動被自動執行。
- **長程執行中的記憶漂移**：隨著執行步驟增加，工作記憶可能累積錯誤。應定期將關鍵狀態外部化至長期記憶，並透過摘要與檢索機制維持上下文一致性。

### 與其他技術的整合建議

- **與現有 CI/CD 管線整合**：將智慧體產生的程式碼變更與回歸測試嵌入既有的持續整合流程，利用現有測試回饋作為框架驗證訊號，實現無迴歸的框架改進。
- **與 IDE 及 LSP 生態系整合**：透過語言伺服器協定將程式編寫助理嵌入開發環境，使程式碼編輯、靜態分析與儲存庫狀態查詢無縫銜接，強化情境感知能力。
- **與 RAG 與知識圖譜整合**：將長期記憶與技能庫儲存於向量資料庫或知識圖譜，支援工具搜尋與偏好記憶的精準檢索，提升跨任務的適應性策略。
- **與可觀測性平台整合**：接入 OpenTelemetry 或類似監控系統，將執行追蹤、環境狀態與智慧體決策紀錄統一收集，便於後續除錯、審計與框架最佳化。
- **與傳統符號驗證工具整合**：對於高風險或需要數學嚴謹性的任務，將 LLM 產生的程式碼交由形式化驗證器或 SMT 求解器檢查，彌補神經網路在精確推理上的不足。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從「程式碼作為推理與行動的介面」這一核心概念入手，先理解為何將思考過程寫成可執行程式碼能提升智慧體的可靠性。可從簡單的程式編寫助理或自動化腳本生成開始實作，無需一次掌握多智慧體或複雜的沙箱設計。
- **AI 工程師**：請聚焦於框架機制層的實作細節，特別是沙箱安全設計、執行期回饋迴路、工具建立與記憶管理。本文對於如何將無狀態的大型語言模型轉化為具備長期狀態與執行驗證能力的智慧體提供了具體的系統架構參考。
- **研究人員**：建議深入探討開放挑戰章節，特別是超越最終任務成功率的評估方法、不完整回饋下的驗證理論、多智慧體共享狀態的一致性，以及擴展至多模態環境的框架設計。這些問題正是目前智慧體系統從原型走向嚴謹科學的關鍵瓶頸。
- **產品經理**：請將閱讀重點放在適用場景與風險章節，評估程式碼作為智慧體框架在貴組織的 DevOps、企業工作流程或科學發現場景中的投資報酬率。同時需審慎規劃人類監督機制與安全邊界，確保自主執行不會逾越業務風險容忍度。
