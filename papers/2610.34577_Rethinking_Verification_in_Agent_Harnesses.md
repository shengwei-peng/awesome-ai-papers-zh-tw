本論文提出一個系統性的驗證設計框架，將代理框架 (agent harnesses) 中的驗證機制視為測試階段擴展 (test-time scaling) 的核心軸向。研究團隊圍繞三個核心設計問題展開：(1) 何時介入 (when to intervene)、(2) 由誰檢查工作 (who checks the work)、(3) 檢查如何導致修正 (how checking leads to revision)。

**四層框架的設計邏輯：**

- **L0 初始指令 (Initial instructions)**：在代理執行任務前，於系統提示 (system prompt) 中嵌入驗證相關指引，引導代理在工作中進行自我檢查。這屬於被動式設計，成本最低但效果有限。

- **L1 執行階段提醒 (Execution-time reminders)**：在代理執行過程中注入回合中途提醒 (mid-turn reminders)，促使代理在工作中持續進行自我驗證。這種設計試圖在不大幅增加成本的情況下提升代理的內在檢查意識。

- **L2 完成閘門 (Completion gates)**：在代理宣告完成後，重新開啟其工作進行自我檢查，包含拒絕式設計 (rejection-based designs) 等變體。這種設計讓代理有機會重新審視自身輸出，但成本顯著上升。

- **L3 獨立審查 (Independent review)**：引入獨立的審查者 (critic) 模型來檢查代理的工作，並將發現回傳給代理進行修正。這是本論文最為推薦的設計，透過分離「執行者」與「檢查者」的角色來提升驗證品質。

**17 種設計的變體維度：**

研究在四層框架內變化多個維度，包括訊息角色 (message role)、介入時機 (intervention timing)、審查者上下文 (critic context) 與審查策略 (review strategy)。在 L3 層級中，研究進一步區分為基於變更的審查 (changes-based review) 與基於軌跡的審查 (trajectory-based review)，並探討是否需要視覺檢查 (visual inspection)。

**獨立審查的擴展機制：**

研究透過兩種方式擴展 L3 獨立審查：(1) 增加額外審查輪次 (additional review rounds)，讓審查者反覆檢查；(2) 引入多個獨立審查者 (independent critics)，透過多角度檢查提升品質。這些擴展機制構成了測試階段擴展的具體實現方式。

#### 實驗數據解讀

**實驗設置：**

研究在兩個程式設計基準上進行評估：Terminal-Bench (TB) 與 SWE-bench Verified (SWE)，並引入內部的 VisualBench（包含 18 個視覺與互動任務）進行專家評估。實驗採用七個前沿程式設計模型 (frontier coding models)，包括 Qwen3.7-Max、Qwen3.8-Max、GLM-5.2、DeepSeek V4-Pro、DeepSeek V4-Flash、Kimi-K2.7-Code 與 MiniMax-M2.5。

**主要實驗結果：**

| 設計層級 | TB 增益 | SWE 增益 | 成本倍數 (TB) | 成本倍數 (SWE) |
|---------|---------|----------|---------------|----------------|
| L0 初始指令 | 模型相依的微小增益 | 模型相依的微小增益 | 0.90–1.00× | 0.90–1.00× |
| L1 執行階段提醒 | 模型相依的微小增益 | 模型相依的微小增益 | 0.75–0.93× | 0.75–0.93× |
| L2 完成閘門 | 較大增益 | 較大增益 | 1.60–1.76× | 1.48–1.56× |
| L3 獨立審查 | +5.9–9.5 百分點 | +3.9–6.6 百分點 | 1.13–1.25× | 1.00–1.04× |

**關鍵發現的解讀：**

1. **L0 與 L1 的成本效益**：值得注意的是，L1 執行階段提醒實際上能降低輸出 token 使用量 (0.75–0.93×)，這可能是因為提醒促使代理更早完成任務。然而，平均增益相當有限且高度模型相依 (model-dependent)，意味著這些設計並非通用解決方案。

2. **L2 的成本陷阱**：完成閘門雖然能產生較大增益，但成本顯著增加（最高達 1.76×）。這反映了拒絕式設計的固有缺陷——需要多次重新生成，導致計算資源消耗不成比例。

3. **L3 的最佳權衡**：獨立審查在 TB 上提升 5.9–9.5 百分點、在 SWE 上提升 3.9–6.6 百分點，而成本僅增加 1.00–1.25×。這個準確率–成本權衡 (accuracy–cost tradeoff) 遠優於 L2，證明了分離執行與檢查角色的有效性。

4. **VisualBench 的專家評估**：在視覺與互動產物評估中，所有四種 L3 獨立審查設計的淨偏好 (net preferences) 達 +13.2 至 +23.8 點，超越所有評估的 L0–L2 設計。這顯示獨立審查在需要主觀品質判斷的任務上同樣有效。

5. **擴展機制的邊際效益**：額外審查輪次或多個獨立審查者可在 TB 上額外提升最多 3.5 百分點的平均準確率，證明了測試階段擴展在驗證層面的可行性。

**變體設計的細部發現：**

- 基於變更的審查 (changes-based review) 在有或無視覺檢查需求下都優於基於軌跡的審查 (trajectory-based review)，這暗示聚焦於具體修改點比審查整體軌跡更有效。
- 審查者上下文的設計對最終效果有顯著影響，這為未來的微調提供了具體方向。

**步驟一：建立基準 (Baseline)**
先以單一代理、無驗證設計的方式在目標任務集上跑一輪，記錄準確率、平均輸出 token 數與單任務成本，作為後續比較的基準線。

**步驟二：選擇驗證層級**
依任務特性挑選起點：
- 成本敏感、任務簡單 → 從 L0（初始指令）或 L1（執行階段提醒）開始
- 重視品質、可接受較高成本 → 直接採用 L3（獨立審查）
- 需嚴格把關（如金融、醫療）→ 採用 L3 + 多輪審查或多 critic

**步驟三：設計 critic prompt**
根據論文 findings，採用「基於變更 (changes-based)」的審查策略優於「基於軌跡 (trajectory-based)」，且應要求 critic 進行視覺檢查（若任務涉及 UI）。critic 應接收：任務目標、代理最終輸出、執行證據（如測試結果、截圖）。

**步驟四：實作審查迴圈**
讓 critic 產出結構化 findings（問題清單、嚴重程度、建議修正），再將 findings 回傳給代理進行 revision。設定最大 revision 輪數（論文顯示額外輪次可再提升最多 3.5 百分點）。

**步驟五：成本監控與動態調整**
為每個任務追蹤 token 使用量與準確率。當 critic 判定「無重大問題」時提早結束；當 revision 連續多輪無改善時停止，避免成本無限增長。

**步驟六：跨模型校準**
在 2–3 個不同模型上測試所選設計，因為 L0/L1 的增益具高度模型相依性。針對弱模型加重審查，強模型可簡化。

**步驟七：建立持續評估機制**
將驗證設計版本化，定期在新任務子集上重新評估，避免設計隨模型更新而失效。

### 潛在風險與注意事項

**風險一：成本失控**
L2 完成閘門（特別是 rejection-based 設計）成本可達基準的 1.48–1.76 倍。若未設定 token 上限或最大重試次數，單一任務可能耗盡預算。
**緩解**：為每個任務設定硬性 token 預算與最大 revision 輪數；當 critic 連續兩輪未發現新問題時提早結束。

**風險二：critic 與代理同質偏誤**
若 critic 與代理使用相同模型，可能共享盲點，導致審查失效。
**緩解**：盡量使用不同模型家族作為 critic；若必須同模型，採用不同 temperature 或不同 prompt 視角。

**風險三：revision 反而破壞正確輸出**
代理在收到 critic 意見後可能「過度修正」，把原本正確的實作改壞。
**緩解**：要求 critic 標註問題嚴重程度，僅針對高嚴重性問題進行 revision；保留原始輸出作為 fallback。

**風險四：視覺/互動評估的主觀性**
VisualBench 仰賴專家盲測，難以自動化擴展。
**緩解**：建立結構化評分 rubric；對關鍵任務保留人工抽樣審查。

**風險五：模型更新導致設計失效**
前沿模型更新後，原本有效的驗證設計可能不再必要或反而有害。
**緩解**：建立定期 A/B 測試機制；將驗證設計視為可配置參數而非硬編碼。

**風險六：context window 爆炸**
長時程任務的軌跡可能超出 critic 的 context window。
**緩解**：僅傳遞最終輸出與關鍵變更摘要，而非完整軌跡；採用 changes-based 而非 trajectory-based 審查。

### 與其他技術的整合建議

**與 RAG 系統整合**
可將 critic 的 findings 存入向量資料庫，作為後續相似任務的先驗知識，減少重複審查成本。

**與 RLHF / DPO 整合**
蒐集 critic 標記為「高嚴重性問題」的案例作為偏好資料，用於微調代理本身，使其逐步內化審查能力，降低長期對 critic 的依賴。

**與監控與可觀測性平台整合**
將驗證設計的決策（為何觸發 revision、critic 發現了什麼）寫入 trace，串接 OpenTelemetry 或 LangSmith 等工具，方便除錯與成本歸因。

**與多代理框架整合**
在 AutoGen、CrewAI 等多代理框架中，將 critic 視為一個獨立角色 (role)，與 worker agent 解耦，便於獨立升級與替換。

**與傳統靜態分析工具整合**
critic 的 prompt 中可注入傳統工具的輸出（如 linter、SAST），讓 LLM 審查聚焦於語意與設計層次的問題，避免重複低階檢查。

**與預算控管系統整合**
將驗證成本納入任務預算 API，呼叫方可在下單時指定「成本上限」與「最低品質分數」，由系統自動選擇驗證層級。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節（Introduction）與第 4 層框架（L0–L3）的概念說明，理解「驗證」在代理系統中的角色與四種介入時機的差異。接著跳到實驗結論段，記住一個核心 takeaway：獨立審查 (L3) 是目前最具 CP 值的驗證設計。技術細節可先略過，著重於理解「為什麼需要 critic」與「何時該介入」。

**給 AI 工程師**：重點閱讀第 3–4 節的設計變因（訊息角色、介入時機、critic context、審查策略）與第 5 節的實驗結果表，特別是不同模型在 L0–L3 上的成本/準確率數字。建議直接以論文的 17 種設計為起點，在自己的任務集上重現 L3 + changes-based review 的配置，再依模型特性微調 prompt。

**給研究者**：第 2 節（Related Work）提供了完整的驗證研究譜系（learned verifiers、self-correction、tool-assisted verification），可作為文獻回顧的入口。第 6 節的消融實驗（額外審查輪次、多 critic）與 VisualBench 的專家評估方法是值得延伸的研究方向，特別是「為何 changes-based 優於 trajectory-based」背後的機制仍待深入探討。

**給產品經理**：聚焦於第 1 節的問題框架（何時介入、由誰檢查、如何修正）與結論段的實務建議。關鍵決策點在於：成本可承受範圍、任務失敗的代價、可接受的延遲。對高風險任務（如涉及金錢、安全、使用者體驗）優先採用 L3；對低風險、高量任務可僅用 L0/L1。建議將驗證設計視為可向客戶收費的「品質保證層」，而非純粹的成本中心。
