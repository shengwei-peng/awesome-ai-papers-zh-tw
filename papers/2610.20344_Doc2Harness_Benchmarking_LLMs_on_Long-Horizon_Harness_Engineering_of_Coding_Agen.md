## 摘要翻譯

由大型語言模型 (LLMs) 驅動的代理日益被部署於長時程任務中，其中它們會使用工具並修改實際工作區。其表現優劣不僅取決於模型本身，同時也取決於模型周圍的 harness。現有基準在固定 harness 下衡量下游任務的成功率，卻未探討 harness 工程本身。我們提出 Doc2Harness，一個直接評估長時程 harness 工程的兩階段基準。在 Stage 1 中，於固定建構器 harness 內運作的建構模型接收一份僅含介面的合約骨架，以及一份整合十二個前沿 harness 行為的開發文件，並在隔離容器中建構出完整的候選 harness。在 Stage 2 中，凍結的候選 harness 在與建構環境分離的容器中執行，每個測試案例使用一個容器，並由腳本化模擬模型端到端驅動。我們透過四個可觀察通道對每個測試案例評分，分別為模型請求、磁碟檔案、行程退出碼以及命令輸出；陽性對照用以排除虛假通過。在十九個前沿模型中，每個模型以三次獨立建構於 328 個測試案例上進行評估，GPT-6 Astra 達到最高的通過率 53.05%，而最弱的模型為 27.44%，差距約二十六個百分點。即便最強的模型仍於近半數的測試案例中失敗，且失敗集中於橫切功能如何劃分至各模組的方式。據我們所知，Doc2Harness 提供了首個用於衡量長時程 harness 工程的確定性基準。

### 核心貢獻（3～5點）
- 提出 **Doc2Harness**，據稱為首個直接衡量長時程 harness 工程的**確定性基準**，填補現有基準僅評測固定 harness 下游任務表現的研究缺口。
- 設計**兩階段評測架構**：Stage 1 由建構模型依據僅含介面的合約骨架與整合十二個前沿 harness 行為的開發文件，於隔離容器中產出候選 harness；Stage 2 則將凍結的候選 harness 部署於獨立容器，由腳本化模擬模型端到端驅動。
- 建立以**四個可觀察通道**（模型請求、磁碟檔案、行程退出碼、命令輸出）為基礎的評分機制，並透過**陽性對照**排除虛假通過，確保評估結果具備實質意義。
- 針對 19 個前沿模型進行大規模實驗（每模型 3 次獨立建構、328 個測試案例），揭示 GPT-6 Astra 以 53.05% 通過率領先、最弱模型僅 27.44%，差距約 26 個百分點，且最強模型仍有近半失敗。
- 診斷出失敗模式集中於**橫切功能**在模組間的劃分方式，為未來 harness 工程研究指明關鍵改進方向。

### 適合對象
- **AI 代理與 LLM 研究者**：關注代理執行框架設計、模型能力評測及長時程任務表現的研究人員。
- **基準測試設計者**：從事 AI 評測方法論、確定性基準與陽性對照實驗設計的學者與工程師。
- **軟體工程自動化研究者**：探討程式碼代理、自動化開發流程及 SWE 任務評估的專業人士。
- **harness 工程實務工作者**：實際建構、修改或維護 LLM 代理執行框架的工程團隊與技術負責人。

## 深度分析

#### 方法論解析

Doc2Harness 提出了一套兩階段評估框架，專門用於衡量大型語言模型 (LLMs) 在「harness 工程」這項長時程任務 (long-horizon tasks) 上的能力。其方法論的核心洞見在於：程式碼代理 (coding agents) 的實際表現不僅取決於底層模型，更取決於圍繞模型的執行框架 (harness)，而現有基準 (benchmark) 從未直接評估建構 harness 本身的能力。

**Stage 1：建構階段 (Construction)**

此階段採用「建構模型 (build model) + 固定建構器 harness (builder harness, 採用 OpenCode)」的組合。輸入包含兩個關鍵元件：

1. **開發文件 (development document)**：此文件經過精心設計，從十二個前沿 harness 的使用者文件中合併、消歧後重寫而成，目的是降低模型對參數化知識 (parametric knowledge) 的依賴——因為這些前沿 harness 僅在過去幾年出現且更新頻率高，模型較不可能在訓練語料中見過完整內容，從而迫使模型展現真正的泛化 (generalization) 能力。

2. **合約骨架 (contract skeleton)**：源自 mini-swe-agent (Yang et al., 2024)，但已移除所有內部實作，僅保留介面宣告。這種「僅含介面的合約 (interface-only contract)」設計迫使模型從零開始實作，而非僅修改既有程式碼。

建構流程中包含一個關鍵的「合約檢查 (contract check)」機制：驗證交付物是否能編譯與安裝、所需命令是否齊全、是否仍有佔位符存根 (placeholder stubs)、三個合約介面是否到位。此檢查僅驗證形式而非行為，通過後即將交付物「凍結 (frozen)」為候選 harness (candidate harness)，不再修改；失敗則退回給建構者繼續修訂（在配額內）。此設計確保每個被評分的候選 harness 代表模型主動宣告完成的狀態，而非時間限制到期時的狀態。

**Stage 2：評估階段 (Evaluation)**

此階段將凍結的候選 harness 移入與建構環境隔離的容器中，每個測試案例 (test case) 一個容器，並由腳本化模擬模型 (scripted mock model) 端到端驅動。這種「黑箱 (black box)」測試方法刻意避免直接檢查 harness 內部實作，而是觀察其外部行為。

評估透過四個可觀察通道 (observable channels) 進行：
- **模型請求 (requests sent to the model)**：harness 發送給模型的請求序列
- **磁碟檔案 (files on disk)**：執行後留下的檔案系統狀態
- **行程退出碼 (process exit code)**：執行程序的退出狀態
- **命令輸出 (command output)**：命令列的標準輸出

此四通道設計的精妙之處在於：harness 內部同一功能可能有多種實作方式，但無論採用何種實作，只要這四個可觀察通道的行為正確即視為通過。這解決了傳統單元測試 (unit tests) 在評估 harness 時的局限性——單元測試透過固定介面觀察行為，但 harness 的同一特徵可在內部以多種方式實現。

**陽性對照 (Positive Controls) 機制**

為排除「虛假通過 (vacuous passes)」——即測試案例通過但實際上待測功能從未執行的情況——Doc2Harness 引入陽性對照設計。陽性對照驗證觀察前提條件是否滿足；若陽性對照失敗，則該測試案例記為 FAIL，無論其自身狀態為何。這是借鑑生物醫學實驗設計的概念，確保評估結果反映真實的功能正確性而非測試設計的漏洞。

**輸入設計的深層考量**

兩種輸入（開發文件與合約骨架）的設計共同體現一個重要原則：減少模型對既有參數化知識的依賴。開發文件透過合併十二個前沿 harness 的行為並重新表述，創造出模型在訓練階段不太可能完整見過的內容；合約骨架則僅保留介面，迫使模型進行實作而非記憶。這使得 Doc2Harness 成為一個真正衡量泛化能力而非記憶能力的基準。

#### 實驗數據解讀

**整體表現分布**

實驗評估了 19 個前沿模型 (frontier models)，每個模型建構 3 個獨立的候選 harness，在 328 個測試案例上進行評分。結果顯示：

- **最強模型 GPT-6 Astra** 的通過率 (pass rate) 達到 53.05%
- **最弱模型** 的通過率僅為 27.44%
- 兩者差距約 **26 個百分點**

這個數據揭示了幾個重要訊息：

1. **基準未飽和 (unsaturated)**：最強模型仍無法通過近半數測試案例，說明 Doc2Harness 對當前最先進的模型仍具挑戰性，並非已被解決的問題。

2. **基準具區辨力 (discriminative)**：26 個百分點的差距證明此基準能有效區分不同能力層級的模型，而非所有模型都聚集在相近分數。

3. **長時程任務的固有難度**：即使是最強模型，過半的失敗率凸顯了 harness 工程作為長時程任務的複雜性——這類任務需要模型在長時間跨度內維持一致的設計決策、處理跨模組依賴、管理複雜的狀態。

**跨類別排名變動**

論文報告「模型在六個主要類別間的排名變動可達十六個位置」，這是一個極為重要的發現。它意味著：

- 沒有任何單一模型在所有類別中都表現優異
- 模型能力具有**類別特異性 (category-specific)**：某些模型可能在工具執行類別表現出色，但在會話狀態管理類別表現不佳
- 這對實際部署具有重要意涵：選擇模型時需考慮具體應用場景，而非僅看整體排名

**失敗模式分析**

論文指出「失敗集中在跨模組橫切功能 (cross-cutting functionality) 的拆分方式上」。這是一個深具啟發性的觀察：

- **橫切功能 (cross-cutting functionality)** 是指那些影響多個模組的功能，例如日誌記錄、權限檢查、錯誤處理、會話狀態管理等
- 這些功能在軟體工程中本就難以模組化，因為它們「橫切」於多個關注點
- 模型在建構 harness 時，若將橫切功能分散到過多模組，會導致：
  - 模組間耦合度增加
  - 介面不一致
  - 測試案例難以通過（因為四個可觀察通道的行為依賴於橫切功能的正確協調）

這暗示當前 LLM 在**軟體架構設計 (software architecture design)** 層面仍有明顯不足——它們可能擅長實作單一功能，但難以做出良好的模組化決策。

**評估方法的穩健性**

每個模型建構 3 個獨立候選 harness 的設計值得注意。這提供了：

1. **統計穩健性**：減少單次建構的隨機性影響
2. **穩定性評估**：可觀察同一模型不同建構之間的表現變異
3. **真實能力反映**：3 次建構的平均更能反映模型的「典型」表現而非「最佳」表現

#### 與現有研究的比較

**與 SWE 基準的比較**

Doc2Harness 明確區別於 SWE-bench Pro (Deng et al., 2026)、NL2Repo-Bench (Ding et al., 2026) 和 Commit0 (Zhao et al., 2025) 等現有 SWE 基準。關鍵差異在於：

| 面向 | 既有 SWE 基準 | Doc2Harness |
|------|--------------|-------------|
| 評估對象 | 模型在固定 harness 下的下游任務表現 | 模型建構 harness 本身的能力 |
| 評估標準 | 任務專屬的單元測試 | 四個可觀察通道的行為 |
| 評估方式 | 透過固定介面觀察 | 黑箱驅動 |
| 泛化要求 | 中等（成熟開源專案） | 高（harness 更新頻繁） |

**兩個關鍵差異點**

論文明確指出傳統 SWE 基準不適用於評估 harness 的兩個原因：

1. **單一特徵的多種實作**：harness 內部同一特徵可以有多種實作方式，而單元測試透過固定介面觀察行為，這種「介面固定性」不適用於 harness 評估。

2. **harness 無法獨立完成下游任務**：harness 的正確性必須透過驅動模型來評估，因為它本身不執行下游任務。這正是 Doc2Harness 採用「模擬模型驅動」設計的原因。

**與遞迴自我改進研究的關聯**

論文將此研究置於「遞迴自我改進 (recursive self-improvement)」的脈絡中——即代理修改自身基礎設施以提升能力的過程。Mei et al. (2025) 的研究指出 harness 決定了模型能力有多少能傳遞到環境，而 Doc2Harness 則提供了衡量這種「傳遞效率」上游能力的方法。

**改進與侷限性**

**改進**：
- 首次提供衡量長時程 harness 工程的確定性基準 (deterministic benchmark)
- 透過陽性對照排除虛假通過，提升評估準確性
- 透過合併十二個前沿 harness 的開發文件，降低對訓練語料的依賴

**侷限性**：
1. **模擬模型的限制**：使用腳本化模擬模型驅動候選 harness，雖然確保了確定性，但無法完全模擬真實 LLM 的複雜行為模式。某些在真實模型驅動下會出現的問題可能無法被測試案例捕獲。

2. **測試案例覆蓋範圍**：328 個測試案例雖然不少，但對於完整評估 harness 功能而言可能仍有缺口。特別是對於罕見的邊緣情況或新興功能，可能缺乏對應的測試案例。

3. **建構器 harness 的固定性**：使用 OpenCode 作為固定建構器 harness，這意味著評估結果反映的是「在 OpenCode 環境下建構 harness 的能力」，而非通用的 harness 建構能力。不同建構環境可能會產生不同的結果。

4. **開發文件的時效性**：開發文件是基於十二個前沿 harness 的當前狀態合併而成，但這些 harness 持續演進，基準可能隨時間失去部分挑戰性或代表性。

5. **缺乏人類專家對照**：雖然評估了 19 個模型，但未與人類專家建構的 harness 進行比較，這使得難以判斷 53.05% 的通過率在絕對意義上代表什麼水平。

#### 可重現性評估

**正面因素**

1. **確定性設計**：Doc2Harness 明確宣稱為「確定性基準 (deterministic benchmark)」，這是可重現性的重要基礎。模擬模型使用預設腳本，測試案例的輸入輸出均可預期。

2. **容器化隔離**：每個測試案例在獨立容器中執行，這消除了環境變異對結果的影響。

3. **標準化輸入**：開發文件和合約骨架是固定的輸入，任何研究者使用相同的模型和環境應能獲得相同的結果。

4. **多通道觀察**：四個可觀察通道提供了透明的評估依據，研究者可獨立驗證評分結果。

**潛在挑戰**

1. **模型版本依賴**：評估涉及 19 個前沿模型，這些模型的版本可能隨時間變化。若要重現特定模型的結果，需要確保使用完全相同的模型版本（包括任何 fine-tuning 或更新）。

2. **建構環境重現**：雖然使用 OpenCode 作為建構器 harness，但完整的建構環境（包括所有依賴、配置）需要精確重現才能獲得一致結果。

3. **測試案例的獲取**：328 個測試案例的具體內容、陽性對照的設計、評分規則的細節，需要從論文或補充材料中完整獲取。

4. **模型 API 變動**：前沿模型通常透過 API 存取，API 的變動（定價、速率限制、輸出格式）可能影響實驗結果。

**建議**

論文中未明確提及程式碼、資料集或模型權重是否開源。從可重現性角度，建議作者：

1. 開源完整的測試案例集與陽性對照設計
2. 提供建構環境的 Docker 映像或詳細配置
3. 釋出評分程式碼，特別是四通道觀察的具體實作
4. 提供開發文件與合約骨架的完整版本
5. 記錄每個模型評估時的具體版本與 API 設定

若這些資源可得，Doc2Harness 將成為一個高度可重現的基準；若缺乏，則其作為「確定性基準」的宣稱將受到質疑。

#### 未來研究方向

**1. 基準擴展與演進**

- **測試案例擴充**：隨著 harness 功能演進，持續新增測試案例，特別是針對新興功能（如多模態互動、協作代理）的測試。
- **類別細化**：將六大類別進一步細分，例如將「工具執行」拆分為「工具發現」、「工具調用」、「工具錯誤處理」等子類別，以提供更精細的能力剖面。
- **難度分層**：設計不同難度等級的測試案例，使基準能評估從基礎到進階的完整能力光譜。

**2. 評估方法改進**

- **混合驅動模型**：結合腳本化模擬模型與有限度的真實模型互動，以更真實地評估 harness 在實際使用中的表現。
- **人類專家對照**：引入人類專家建構的 harness 作為基準，量化模型表現與人類水平的差距。
- **長期穩定性追蹤**：對同一模型在不同時間點進行評估，追蹤模型能力隨版本更新的演變。

**3. 失敗模式深入分析**

- **橫切功能專項研究**：既然失敗集中在橫切功能的模組化拆分，可設計專門評估此能力的子基準。
- **架構決策分析**：研究模型在模組化、介面設計、依賴管理等方面的決策模式，探討是否存在系統性的偏差。
- **錯誤傳播研究**：分析早期設計決策如何影響後續實作，建立「錯誤傳播鏈」的概念框架。

**4. 與遞迴自我改進的整合**

- **迭代改進評估**：不僅評估單次建構，還評估模型在多次迭代中改進 harness 的能力——這更接近真實的遞迴自我改進場景。
- **改進效率指標**：衡量模型從失敗中學習並改進的速度與效果。
- **自我評估能力**：研究模型是否能準確評估自身 harness 的品質，這是遞迴自我改進的關鍵能力。

**5. 跨領域應用**

- **其他類型代理的 harness**：將方法論擴展到非程式碼代理，如研究代理、創意代理、客服代理等的 harness 評估。
- **多代理系統**：評估建構支援多代理協作的 harness 的能力，這是當前代理研究的熱點方向。
- **領域專屬 harness**：針對特定領域（如金融、醫療、法律）的專屬 harness 評估。

**6. 理論基礎建立**

- **harness 工程的理論框架**：建立 harness 工程的理論基礎，包括形式化的正確性定義、複雜度度量、品質指標。
- **泛化能力的理論分析**：研究為何 harness 工程需要更強的泛化能力，以及如何從理論上理解模型在此任務上的表現差異。
- **與軟體工程的連結**：將 harness 工程置於更廣泛的軟體工程理論框架中，借鑑既有的軟體品質模型（如 ISO 25010）來評估 harness。

**7. 工具與基礎設施**

- **互動式評估環境**：開發支援互動式探索的評估環境，讓研究者能深入理解模型行為。
- **視覺化分析工具**：建立視覺化工具，展示模型建構的 harness 架構、模組依賴、失敗分布等。
- **基準演進平台**：建立持續演進的基準平台，類似於 SWE-bench 的演進模式，確保基準的時效性與挑戰性。

這些研究方向不僅能深化對 Doc2Harness 本身的理解，更能推動整個「代理基礎設施評估」領域的發展，最終促進更強大、更可靠的 LLM 驅動代理系統的建構。

## 論文問答

**Q1：Doc2Harness 主要解決什麼核心問題？為何 harness 工程在當前 LLM 代理部署中如此關鍵？**

A：Doc2Harness 旨在直接評估 LLM 在「長時程 harness 工程」上的能力，也就是衡量模型能否從一份開發文件與介面骨架出發，獨立建構出一個完整的代理執行框架。隨著 LLM 驅動的程式碼代理被部署到日益複雜的環境中，harness 本身承擔了互動迴圈、工具執行、上下文管理、權限控管、會話狀態、失敗恢復與結果驗證等關鍵職能，決定了模型能力有多少能真正觸及環境。換言之，harness 的品質直接決定了代理在真實工作空間中的實際表現，因此如何衡量與改進 harness 工程能力成為一個迫切但被既有基準忽略的研究缺口。

**Q2：為何既有的 SWE 基準（如 SWE-bench Pro、NL2Repo-Bench、Commit0）無法直接用於評估 harness 工程？**

A：這些 SWE 基準仰賴任務隨附的單元測試來判定輸出是否可接受，但 harness 的特性使其無法沿用此一評估方式。首先，harness 中的單一功能可在內部以多種方式實現，而單元測試只能透過固定介面觀察行為，難以窮舉所有合法實作。其次，harness 本身並不獨立完成下游任務，其正確性必須由模型實際驅動後才能評估，無法像一般函式庫那樣單獨驗證。再加上既有 SWE 基準的開源儲存庫多為成熟專案，可能早已大量出現在訓練語料中，無法有效衡量泛化能力，而 harness 出現時間短、更新頻率高，反而更適合作為泛化壓力測試的載體。

**Q3：什麼是「遞迴自我改進」，它如何驅動了 Doc2Harness 的研究動機？**

A：遞迴自我改進指的是代理不僅執行任務，還會修改自身運作所依賴的基礎設施——亦即修改自己的 harness——並在下一輪任務中使用改進後的版本，逐步提升自身能力。由於人類已難以對代理的每一步進行監督，這種自我改進路徑被視為通往更強代理能力的關鍵機制。然而，遞迴自我改進能否成功，取決於模型是否能將此流程泛化到未曾見過的 harness 設計上，而這正是 Doc2Harness 想直接測量的能力：模型能否在長時程、多步驟的情境下，獨立產出一個可運作、可被評估的 harness。

**Q4：Doc2Harness 的兩階段設計具體包含哪些步驟？為何需要分為兩個階段而非單一評估？**

A：Stage 1 是建構階段：受測的建構模型在固定的建構器 harness（OpenCode）中運作，接收開發文件與僅含介面的合約骨架，於隔離容器中產出完整的候選 harness，並透過合約檢查（驗證可編譯安裝、必要命令齊備、無佔位符、三個合約介面到位）後凍結成品。Stage 2 是評估階段：凍結的候選 harness 被移至與建構環境隔離的容器中，由腳本化模擬模型依預設腳本驅動，逐一執行數百個測試案例。分為兩階段的關鍵原因在於：建構與評估必須解耦，否則模型可能在評估階段「作弊式地」調整行為；同時，凍結後的黑箱評估才能真實反映 harness 在未知情境下的穩健性與可重用性。

**Q5：Doc2Harness 透過哪四個可觀察通道來判定測試案例的通過與否？為何選擇這四個通道？**

A：四個可觀察通道分別是：發送給模型的請求、磁碟上的檔案、行程退出碼、以及命令輸出。這四個通道之所以被選中，是因為它們共同覆蓋了 harness 行為的所有可外部觀察面向：模型請求反映 harness 對 LLM 的呼叫模式與提示工程品質；磁碟檔案反映 harness 對工作空間狀態的讀寫與持久化行為；行程退出碼反映生命週期管理與錯誤處理；命令輸出則反映使用者可見的最終結果。透過同時觀察這四個通道，評估者能在不檢視內部實作的前提下，全方位驗證 harness 是否真的執行了預期行為，而非僅僅產出表面正確的輸出。

**Q6：什麼是「虛假通過」（vacuous pass）？Doc2Harness 如何透過陽性對照來排除此一風險？**

A：虛假通過指的是測試案例表面上通過，但實際上被測功能從未真正執行——例如測試斷言某檔案存在，而 harness 因錯誤而從未運行，導致檔案根本未被建立或刪除，斷言卻誤判為通過。為了排除這種風險，Doc2Harness 引入了陽性對照機制：在套用正式斷言之前，先驗證「觀察前置條件」是否成立，例如確認模型請求確實被發出、檔案系統確實被讀寫過。若陽性對照失敗，無論後續斷言結果為何，該測試案例一律記錄為 FAIL。這種設計確保了通過率反映的是 harness 的實質功能性，而非測試基礎設施的偶然狀態。

**Q7：在 19 個前沿模型的實驗中，Doc2Harness 揭示了哪些主要結果？模型間的差距有多大？**

A：實驗結果顯示 GPT-6 Astra 以 53.05% 的通過率奪冠，而最弱的模型僅達 27.44%，兩者差距約為 26 個百分點，證明該基準既能區辨模型差異也尚未飽和。更值得注意的是，即使是最強模型也幾乎有近半數的測試案例失敗，顯示長時程 harness 工程對當前前沿模型仍是極具挑戰性的任務。此外，模型在六個主要類別中的排名最多可移動 16 個位置，意味著不同模型在不同 harness 功能面向上的強弱分佈並不一致，整體排名無法完全代表單一維度的能力。

**Q8：Doc2Harness 的測試套件包含 328 個測試案例，這些案例如何設計以涵蓋廣泛情境？**

A：測試套件涵蓋了從基本工具呼叫、檔案操作、會話狀態管理，到複雜的失敗恢復與多步驟工作流程等多種情境，每個測試案例都在獨立的隔離容器中執行，以避免狀態洩漏與交叉污染。每個案例由腳本化模擬模型依預設腳本驅動候選 harness，確保評估過程的確定性與可重現性。此外，部分案例配備陽性對照，以驗證觀察前置條件是否真正成立。這種「廣度優先」且「確定性驅動」的測試設計，使 Doc2Harness 能系統性地揭露模型在不同功能面向上的細粒度差異。

**Q9：對評分後的候選 harness 原始碼進行分析後，作者發現了哪些與通過率相關的結構性規律？**

A：分析顯示，通過率較高的候選 harness 傾向於將橫切功能（例如權限控管、會話狀態、錯誤恢復）集中在較少的模組中，而非分散到多處。這種「集中化」設計降低了模組間的耦合與介面不一致的風險，使 harness 在面對新情境時更容易維持行為一致性。反之，失敗案例多呈現橫切功能被切割到多個模組、導致責任歸屬不清與互動模式難以預測的現象。這項發現為未來的 harness 工程提供了具體的設計準則：模組化應以功能內聚性為優先，而非單純追求功能分散。

**Q10：Doc2Harness 的研究成果可應用於哪些實際場景？哪些團隊最能從中受益？**

A：Doc2Harness 最直接的應用場景是評估與比較不同 LLM 在建構代理基礎設施時的能力，這對從事 AI 代理框架開發的團隊（如程式碼代理、自動化工作流程代理的供應商）尤其重要。其次，企業在部署內部程式碼代理時，可藉由此基準判斷哪個底層模型更適合承擔 harness 維護與演進的工作。此外，研究遞迴自我改進與代理自我演化機制的學術團隊，也能以此基準作為衡量「模型能否改進自身基礎設施」的標準化工具。

**Q11：產品團隊在部署程式碼代理時，應如何將 harness 工程納入考量？**

A：產品團隊應意識到，模型的底層能力僅是代理表現的一部分，harness 的設計品質同樣關鍵——甚至在某些情境下，harness 的好壞決定了模型能力能否被有效釋放。在選型階段，團隊可參考 Doc2Harness 等基準的結果，挑選在 harness 工程上表現較強的模型作為底層。在營運階段，則應將 harness 視為一級資產進行版本控管與持續改進，而非視為模型附屬的固定外殼。此外，團隊也應建立類似陽性對照的監控機制，確保代理行為的「通過」反映實質功能，而非測試或觀察管道的虛假訊號。

**Q12：Doc2Harness 對 LLM 代理評估領域的更廣泛影響是什麼？**

A：Doc2Harness 將評估對象從「模型在固定 harness 下的下游任務表現」轉向「模型建構 harness 本身的能力」，這是一個典範轉移：它把基礎設施的設計能力納入可衡量範疇，使研究社群能更嚴謹地討論「代理能力」一詞的真正意涵。同時，作為一個確定性基準，它為未來相關研究提供了可重現、可比較的共同基礎，有助於加速 harness 工程領域的標準化。此外，它也凸顯了「泛化」在 AI 代理研究中的核心地位——唯有在模型未曾大量見過的任務上進行評估，才能真正衡量其能力上限。

**Q13：Doc2Harness 存在哪些已知的限制？**

A：Doc2Harness 的限制之一在於其評估仍受限於開發文件所涵蓋的行為範圍——雖然文件整合自十二個前沿 harness，但任何未在文件中描述的功能都無法被測試。其次，腳本化模擬模型雖然提供了確定性，卻無法完全模擬真實 LLM 驅動時可能出現的隨機性與多樣性回應，因此通過率可能無法完全反映 harness 在真實代理環境中的表現。此外，328 個測試案例雖已具相當規模，但對於覆蓋所有可能的邊界情境仍有不足，特別是在跨模組互動的複雜情境下。

**Q14：失敗案例主要聚集在哪些類型的問題上？「橫切功能切割」具體造成了什麼困難？**

A：失敗案例明顯聚集在「橫切功能如何被切割到不同模組」這個議題上，例如權限檢查、會話狀態追蹤、錯誤恢復邏輯等橫切關注點（cross-cutting concerns）若被分散到多個模組，往往導致介面不一致、責任歸屬模糊、以及互動順序難以預測等問題。具體而言，當一個橫切功能被切割時，harness 容易在不同模組間產生重複或矛盾的實作，使得測試案例在特定情境下無法正確觸發預期行為。這也解釋了為何通過率最高的候選 harness 傾向於將橫切功能集中在少數模組——這是一種在測量中被驗證的設計啟示。

**Q15：基於 Doc2Harness 的發現，未來有哪些值得探索的研究方向？**

A：未來可探索的方向包括：將 Doc2Harness 擴展至多輪遞迴自我改進情境，衡量模型能否在多輪迭代中持續改進自身 harness；研究如何透過提示工程或訓練資料設計，引導模型產出橫切功能集中的 harness 結構；以及將評估對象從「單一模型建構 harness」擴展到「多模型協作建構 harness」，探索集體智慧在基礎設施設計中的角色。此外，將 Doc2Harness 與真實 LLM 驅動的評估相結合，檢驗腳本化模擬模型結果與真實情境下表現的相關性，也是建立更全面評估生態的重要下一步。

## 實務應用指南

### 適用場景

1. **企業內部 coding agent 框架選型評估**：當組織需要在多個 LLM 之間挑選作為內部程式碼代理的核心時，可直接以 Doc2Harness 對候選模型進行三輪獨立建構，根據通過率與橫切功能模組化程度，決定哪個模型最適合承擔長期維護代理基礎設施的工作。

2. **遞迴自我改進 (recursive self-improvement) 研究**：研究團隊若要驗證「代理修改自身 harness 後能力提升」的假設，可將 Doc2Harness 的 Stage 1 輸出作為下一輪 Stage 1 的輸入，反覆觀察通過率隨迭代次數的變化趨勢。

3. **模型泛化能力壓力測試**：由於開發文件是從十二個前沿 harness 合併改寫而成、合約骨架已移除所有內部實作，Doc2Harness 適合用於檢驗模型在「未見過的程式碼基礎設施」上的泛化表現，特別是針對訓練語料中較少出現的近年新興專案。

4. **代理框架教學與教材開發**：教育機構可將 Doc2Harness 的 328 個測試案例作為教材，讓學生分析高分與低分候選 harness 的原始碼差異，理解「互動迴圈、工具執行、會話狀態、失敗恢復、結果驗證」等元件如何正確拆分。

5. **第三方模型評估平台的基準整合**：模型評估平台（如排行榜服務）可將 Doc2Harness 納入定期評測排程，由於其為確定性基準 (deterministic benchmark)，可在版本更新時提供穩定的比較基準。

### 實作前置條件

**資料準備**
- 開發文件：需從至少十二個前沿 harness 的使用者文件合併、改寫並消歧後產出，建議保留版本控制以便日後更新。
- 合約骨架：以 mini-swe-agent 為基礎，僅保留三個介面，所有內部實作皆須移除。
- 測試案例集：涵蓋多種情境的數百個測試案例，並為關鍵案例設計陽性對照 (positive controls)。
- 預設腳本：為模擬模型 (mock model) 撰寫對應每個測試案例的回應腳本。

**運算資源**
- 隔離容器環境：每個 Stage 1 建構與每個 Stage 2 測試案例皆需獨立容器，建議使用 Docker 或 Kubernetes 編排。
- LLM API 存取：需具備十九個前沿模型（或其子集）的 API 配額，每個模型需執行三次獨立建構。
- 磁碟與日誌儲存：需保存每輪建構的原始碼、四個可觀察通道 (observable channels) 的輸出，以便事後分析。

**技能要求**
- 軟體工程能力：熟悉 Python、容器化、CI/CD 流程。
- 測試設計能力：能設計可區分「真實通過」與「虛假通過」的陽性對照。
- LLM 評估經驗：理解模型行為差異、提示工程、評估偏差來源。
- 基礎設施維運：能管理大量並行容器、處理超時與資源回收。

### 實作步驟建議

1. **建立評估管線骨架**：先實作 Stage 2 的驅動框架——將凍結的候選 harness 與模擬模型組合成「驅動 harness」，並實作四個可觀察通道的收集器（模型請求、磁碟檔案、行程退出碼、命令輸出）。此步驟不依賴任何特定模型，可先以一個已知可用的最小 harness 驗證管線正確性。

2. **撰寫開發文件與合約骨架**：從十二個前沿 harness 的文件中萃取行為描述，合併重複條目並消歧後形成單一開發文件；同時從 mini-swe-agent 蒸餾出僅含介面的合約骨架。建議邀請領域專家審閱，確保文件語意清晰、無歧義。

3. **設計測試案例與陽性對照**：為每個功能點設計至少一個測試案例，並對關鍵行為加入陽性對照——陽性對照失敗時，無論測試案例本身狀態為何，皆記錄為 FAIL，以排除虛假通過 (vacuous passes)。

4. **整合建構器 harness**：選擇固定的建構器 harness（論文中使用 OpenCode），將其與待測模型組合成 builder，並實作合約檢查邏輯（編譯安裝、必要命令存在、無佔位符、三個介面到位）。

5. **執行三輪獨立建構**：對每個受測模型執行三次獨立 Stage 1 建構，每次皆在獨立容器中完成，並以提交 (submission) 作為建構結束的訊號，避免以逾時作為結束條件。

6. **執行 Stage 2 評測**：將每個凍結的候選 harness 移至獨立的 Stage 2 容器，逐一執行 328 個測試案例，收集四個通道的觀察值並依陽性對照與斷言決定 PASS 或 FAIL。

7. **彙整通過率與排名**：計算每個模型三次建構的平均通過率，並依六大類別分別排名，觀察排名在不同類別間的位移幅度（論文中觀察到最高達十六個名次的變動）。

8. **分析失敗模式**：對低分候選 harness 的原始碼進行剖析，重點關注橫切功能 (cross-cutting functionality) 在模組間的拆分方式——論文發現高分候選 harness 傾向將橫切功能集中在較少模組中。

### 潛在風險與注意事項

- **虛假通過風險**：若未設計完善的陽性對照，測試案例可能在「功能從未實際執行」的情況下通過。緩解方式：為每個關鍵行為路徑設計獨立的陽性對照，並在陽性對照失敗時強制將測試案例記錄為 FAIL。

- **容器隔離洩漏**：若 Stage 1 與 Stage 2 容器未完全隔離，建構環境的狀態可能影響評測結果。緩解方式：使用獨立的容器映像、網路命名空間與檔案系統掛載，並在每次評測後銷毀容器。

- **模型版本漂移**：受測模型在評測期間可能更新版本，導致結果不可重現。緩解方式：固定模型版本快照、記錄 API 回應的模型 ID，並在報告中標註評測日期。

- **評估偏差**：開發文件源自十二個特定 harness，可能對某些模型的訓練分布有利。緩解方式：定期輪換來源 harness、加入「未見過」的行為描述，並觀察排名穩定性。

- **資源耗盡攻擊**：惡意或低品質模型可能產出極大的候選 harness，導致容器資源耗盡。緩解方式：設定建構階段的資源上限（CPU、記憶體、磁碟、時間），並在超限時自動終止。

- **橫切功能拆分不當**：論文指出失敗案例集中於橫切功能在模組間的拆分方式。緩解方式：在分析階段特別檢視權限、會話狀態、失敗恢復等橫切關注點的模組歸屬。

- **模擬模型腳本脆弱性**：Stage 2 的模擬模型依賴預設腳本，若腳本與候選 harness 的介面契約不符，整個評測可能失效。緩解方式：在 Stage 2 開始前先執行介面相容性檢查，並為腳本撰寫單元測試。

### 與其他技術的整合建議

- **與 SWE-bench 系列基準互補**：SWE-bench Pro、NL2Repo-Bench、Commit0 等基準使用任務專屬的單元測試評估下游任務成功；Doc2Harness 則評估 harness 本身的建構能力。建議在模型評估流程中同時運行兩類基準，以全面了解模型在「執行任務」與「建構執行環境」兩個維度上的表現。

- **與持續整合 (CI) 系統整合**：可將 Doc2Harness 整合至 CI 管線，每次模型版本更新時自動觸發三輪建構與評測，並將通過率趨勢圖整合至儀表板。

- **與模型評估平台整合**：Hugging Face Leaderboard、OpenCompass 等平台可將 Doc2Harness 作為「代理基礎設施開發」類別的子基準，並提供原始碼下載供研究者分析。

- **與遞迴自我改進框架整合**：可將 Doc2Harness 的 Stage 1 輸出作為下一輪的輸入，與 STOP、META-RISE 等遞迴自我改進框架結合，觀察通過率隨迭代次數的變化。

- **與可觀察性工具整合**：將四個可觀察通道的輸出導入 OpenTelemetry 或類似的可觀察性平台，以便跨模型、跨測試案例進行時序分析與異常偵測。

- **與靜態分析工具整合**：對候選 harness 的原始碼執行靜態分析（如模組耦合度、循環複雜度），並與通過率進行相關性分析，驗證「橫切功能集中於較少模組」這個觀察。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「為什麼 harness 本身值得被評估」這個核心問題；接著閱讀第 2.1 節的兩階段流程圖，建立對 Stage 1 建構與 Stage 2 評測的直觀認識。實作術語（如容器、模擬模型、陽性對照）可暫時略過細節，專注於「輸入是什麼、輸出是什麼、如何計分」這個主軸。

**給 AI 工程師**：重點閱讀第 2 節的任務描述與第 3 節的實驗設計，特別關注四個可觀察通道的設計動機、陽性對照如何排除虛假通過、以及合約檢查如何區分「形式正確」與「行為正確」。實作時可先以一個小型 LLM 與簡化版開發文件建立端到端管線，再逐步擴展至完整規模。

**給研究者**：第 4 節的實驗結果與分析是核心，特別是「高分候選 harness 傾向將橫切功能集中在較少模組」這個發現，以及「模型排名在不同類別間位移最高達十六個名次」這個現象。建議進一步分析失敗案例的原始碼，並考慮將 Doc2Harness 應用於遞迴自我改進、跨模型遷移學習等研究方向。

**給產品經理**：重點關注通過率的絕對值與相對差距——最強模型僅達 53.05%，最弱模型為 27.44%，這意味著即使是最先進的模型，在長時程 harness 工程上仍有近半失敗率。在產品規劃上，應將「模型建構 harness 的能力」視為一項需要持續追蹤的能力指標，而非一次性評估；同時，橫切功能拆分的失敗模式提示我們，產品化的代理框架應提供清晰的模組化範本，以降低模型建構的難度。
