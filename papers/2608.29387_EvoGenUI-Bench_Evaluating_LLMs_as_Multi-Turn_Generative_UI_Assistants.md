# EvoGenUI-Bench：評估大型語言模型（LLM）作為多輪生成式 UI 助理

**原文標題：** EvoGenUI-Bench: Evaluating LLMs as Multi-Turn Generative UI Assistants

**發布日期：** 2026-08-29

## ⚡ TL;DR

現有生成式UI評估多針對單次輸出，忽略多輪對話中可執行介面的持續維護。
提出EvoGenUI-Bench，以150項跨三情境的五輪任務與瀏覽器執行，結合多證據評估。
最強模型單輪通過率74.9%，五輪完成率僅37.3%，工具任務APR僅52.4%，分類揭示失效機制。

## 摘要翻譯

大型語言模型（LLM）能夠生成互動式網頁介面，但可靠的生成式 UI（Generative UI）需要在使用者請求（User request）不斷演變的過程中維護可執行產物（Executable artifact）。我們提出 EvoGenUI-Bench，一個用於多輪介面維護（Multi-turn interface maintenance）的基準測試（Benchmark），包含 150 個五輪任務（Five-turn task）與 750 個輪次（Turn），涵蓋三種情境（Scenario）：資訊呈現（Information presentation）、可執行互動（Executable interaction），以及工具接地外部狀態（Tool-grounded external state）。我們在瀏覽器中執行生成的產物，並使用截圖（Screenshot）、原始碼與 DOM 證據（Source and DOM evidence）、操作者軌跡（Actor traces），以及執行階段日誌（Runtime logs）進行評估。除了輪次層級成功率（Turn-level success）與對話片段層級成功率（Episode-level success）之外，我們以相鄰通過保留率（Adjacent Pass Retention, APR）衡量跨輪保留（Cross-turn retention）。在八個模型（Model）中，即使最強的模型達到 74.9% 的輪次通過率（Turn Pass），仍僅完成 37.3% 的五輪對話片段（Five-turn episode）；在工具接地任務上，APR 更進一步下降至 52.4%。診斷分析（Diagnostic analysis）顯示，呈現失敗（Presentation failures）主要集中於資訊架構（Information architecture），互動失敗（Interaction failures）在於衍生狀態傳播（Derived-state propagation）與功能可見性綁定（Affordance binding），而工具接地失敗（Tool-grounded failures）則額外涉及外部狀態接地（External-state grounding）與需求分解（Requirement decomposition）。這些結果重新建構了生成式 UI 的評估框架，從評斷孤立輸出，轉變為測試在產物演進（Artifact evolution）過程中，介面行為（Interface behavior）、衍生狀態（Derived state）、外部狀態（External state），以及助理聲稱（Assistant claims）是否保持同步（Synchronized）。

### 核心貢獻（3～5點）
- 提出 EvoGenUI-Bench，首個針對多輪生成式 UI 介面維護的基準測試，包含 150 個五輪任務與 750 個輪次，涵蓋資訊呈現、可執行互動與工具接地外部狀態三大情境。
- 建立結合瀏覽器執行、截圖、原始碼與 DOM 證據、操作者軌跡及執行階段日誌的多源證據評估流程。
- 提出輪次層級成功率、對話片段層級成功率，以及相鄰通過保留率（APR）等指標，以衡量跨輪保留能力。
- 透過診斷分析識別各類失敗模式：呈現失敗集中於資訊架構，互動失敗源於衍生狀態傳播與功能可見性綁定，工具接地失敗則涉及外部狀態接地與需求分解。
- 重新建構生成式 UI 的評估視角，強調應檢驗產物演進過程中介面行為、衍生狀態、外部狀態與助理聲稱是否持續同步。

### 適合對象
本論文適合對生成式 UI、多輪對話系統、LLM 代理（agent）評估，以及人機互動（HCI）研究有興趣的研究者與工程師；特別適合希望了解如何設計多輪基準測試、評估互動式網頁介面可執行性，以及診斷 LLM 在長期對話中狀態維護能力的讀者。

## 深度分析

#### 方法論解析

**EvoGenUI-Bench** 的核心是將生成式 UI（Generative UI）的評估從「單次生成」轉移到「多輪介面維護（multi-turn interface maintenance）」。傳統上，模型只需根據單一提示產出一個可執行的網頁介面；而在本基準測試中，模型必須在長達五輪的對話中持續更新同一個可執行產物（executable artifact），同時滿足當前請求（current request）、保留仍然有效的需求（still-valid requirements），並維持介面行為（interface behavior）、可見狀態（visible state）與助理聲稱（assistant claims）之間的同步。

**任務設計與情境分類**
本基準測試包含 150 個五輪任務（five-turn task），共 750 輪（turn）。每個任務以一個初始的介面生成請求開場，隨後接續四個對同一產物的累積修訂請求。這些任務被劃分為三大情境（scenario）：
- **資訊呈現（information presentation）**：評估模型如何組織、排版與呈現密集資訊，重點在於資訊架構（information architecture）與可讀性。
- **可執行互動（executable interaction）**：評估帶有本地狀態的互動式介面，例如表單（form）、儀表板（dashboard）或小型應用程式（mini-application），關注互動行為與狀態傳播。
- **工具接地外部狀態（tool-grounded external state）**：評估介面如何透過工具呼叫與外部真實狀態連結，例如天氣、預算或地圖資料，強調外部狀態接地（external-state grounding）與需求分解（requirement decomposition）。

**執行與證據導向的評估流程**
本研究並非僅對模型輸出的原始碼進行靜態檢查，而是建立了一套瀏覽器執行（browser execution）管線：首先嘗試建置並執行生成的產物，無法建置或執行的樣本直接計為失敗；可執行的產物則透過多表面證據組合（multi-surface evidence bundle）進行評分，包括：
- **截圖（screenshot）**：驗證視覺呈現與版面配置。
- **原始碼證據（source code evidence）**：檢查 HTML、CSS、JavaScript 的結構與語義。
- **DOM 證據（DOM evidence）**：分析文件物件模型（Document Object Model）的節點層級與屬性。
- **操作者軌跡（actor traces）**：由自動化操作者與介面互動，驗證互動行為是否正確。
- **執行階段日誌（runtime logs）**：捕捉主控台錯誤、工具呼叫結果與狀態變化。

基於這些證據，每個輪次從三個維度評分：**呈現（Presentation）**、**執行（Execution）** 與**對齊（Alignment）**。其中對齊特別檢驗生成的介面是否與助理在對話歷史（conversation history）中的描述一致。

**評估指標**
本基準測試提出三個層級的指標：
- **輪次通過率（Turn Pass）**：單一輪次是否通過所有評分維度。
- **對話片段完成率（Episode Completion Rate / TP@5）**：整個五輪對話片段（five-turn episode）是否全部通過。
- **相鄰通過保留率（Adjacent Pass Retention, APR）**：在上一輪通過的前提下，下一輪也通過的比例，用以衡量跨輪保留（cross-turn retention）與迴歸風險。

**診斷分類法**
作者進一步建立一套人工驗證的診斷分類法（diagnostic taxonomy），將失敗歸因於：資訊架構、衍生狀態傳播（derived-state propagation）、功能可見性綁定（affordance binding）、外部狀態接地與需求分解等機制，使分析不僅停留在「成功或失敗」，而能指出模型維護介面時的具體脆弱環節。

---

#### 實驗數據解讀

論文評估了八個模型（eight models），結果呈現出鮮明的層級落差：

- **輪次通過率（Turn Pass）**：最強模型達到 **74.9%**。這表示在單一輪次中，現今的大型語言模型（LLM）已能相對可靠地生成或修改一個可執行的網頁介面。
- **對話片段完成率（TP@5）**：最強模型卻僅完成 **37.3%** 的五輪對話片段（five-turn episode）。換言之，即使單輪表現不錯，能夠在連續五輪中都不出錯的機率卻不到四成。
- **相鄰通過保留率（APR）**：在工具接地外部狀態（tool-grounded external state）任務上，APR 進一步降至 **52.4%**。這意味著即便上一輪通過，下一輪仍有近一半機率失敗。

這三個數字共同說明：**單輪成功率會顯著高估生成式 UI 助理的實用可靠性**。真正的挑戰不在於「能否生成一個看起來對的介面」，而在於「當產物演進（artifact evolution）時，介面行為、衍生狀態（derived state）、外部狀態（external state）與助理聲稱（assistant claims）能否持續同步」。

**不同情境的失敗焦點**
診斷分析顯示，三類情境的失敗機制有明顯差異：
- **資訊呈現（information presentation）**：失敗主要集中在資訊架構（information architecture），例如資訊分群不當、層級混亂、視覺過於擁擠或修訂後可讀性下降。
- **可執行互動（executable interaction）**：失敗主要來自衍生狀態傳播（derived-state propagation）與功能可見性綁定（affordance binding）。例如使用者修改輸入後，相依的計算結果未更新；或按鈕、滑桿等控制項未正確連結到對應的行為。
- **工具接地外部狀態（tool-grounded external state）**：除了上述問題外，還額外出現外部狀態接地（external-state grounding）與需求分解（requirement decomposition）的失敗。例如工具呼叫結果未正確渲染、外部資料與介面狀態不同步，或複雜請求未被拆成可執行的子步驟。

**整體意涵**
實驗結果重新框定了生成式 UI 的評估重點：不應只判斷孤立輸出（isolated output）的視覺或語法正確性，而應測試產物在演進過程中，其行為、狀態與對話脈絡是否保持一致。對於開發實際助理系統而言，這意味著需要更強的長期記憶、差異化編輯能力、執行後自我驗證機制，以及對工具返回狀態的持續追蹤。

#### 與現有研究的比較

**與生成式 UI 基準測試的差異**
現有的生成式 UI 研究多聚焦於單次生成品質，例如視覺逼真度（visual fidelity）、可執行的前端生成（executable frontend generation）、多檔案網站生成，或 MiniAppBench 所強調的原則導向、互動密集的小型應用程式評估。這些工作雖然檢驗了模型產出互動式網頁介面的能力，但本質上仍將每個任務視為獨立的生成片段（generation episode），而非持續演進的持久介面。EvoGenUI-Bench 的獨特之處在於把「介面維護（interface maintenance）」本身當成評估對象：每次修訂都必須在保留先前有效需求的同時加入新需求。

**與迭代式開發研究的差異**
近期研究如 FronTalk、SlopCodeBench 與 MultiChallenge 也開始關注需求演進下的生成問題。FronTalk 強調多輪前端開發中特徵被遺忘或覆蓋的現象；SlopCodeBench 指出迭代擴展程式碼會造成結構退化；MultiChallenge 則記錄真實多輪指令遵循的失敗。EvoGenUI-Bench 延伸這條研究軸線，但進一步將生成的介面同時視為**助理輸出**與**互動層（interaction layer）**。因此，模型不只要產出正確的程式碼，還要確保該程式碼在瀏覽器中執行後，其行為與狀態能與對話歷史及外部真實狀態保持一致。

**與互動式代理基準測試的差異**
WebArena、VisualWebArena、OSWorld、AgentBench 等互動式代理（interactive agent）基準測試評估模型在預先存在的網站或作業系統環境中操作的能力。在這些設定中，環境提供介面，代理負責行動。EvoGenUI-Bench 則反轉這個關係：模型本身生成並持續修訂介面，環境僅負責執行與驗證。這種「建構即執行」的設定更貼近真正的生成式 UI 助理，但也帶來更複雜的一致性要求。

**與工具使用基準測試的差異**
ToolLLM 與 Berkeley Function Calling Leaderboard 等工具使用（tool use）評測主要檢驗模型選擇與呼叫工具的能力。EvoGenUI-Bench 則要求模型將工具取得的資料轉化為介面狀態，並在後續輪次中維持與外部狀態的同步。這比單純的工具呼叫更進一步，涉及資料接地、狀態傳播與視覺呈現的整合。

**主要貢獻與限制**
本研究的貢獻在於提出首個以「可執行產物演進」為核心的多輪基準測試，並結合視覺、原始碼、DOM、操作者軌跡與執行階段日誌等多種證據進行評估，同時引入 APR 作為跨輪保留指標。然而，其限制也應被正視：
- 任務長度固定為五輪，真實對話可能更長或更短，且使用者可能會撤回、修改或提出矛盾需求。
- 僅涵蓋網頁介面（HTML/CSS/JavaScript），未涉及行動應用程式、桌面應用程式或特定前端框架。
- 自動化評估雖然客觀，但可能無法完全捕捉主觀設計品質、無障礙性或品牌一致性。
- 工具接地情境可能受限於特定的外部 API 或模擬狀態，對於真實世界動態 API 的泛化能力仍需驗證。
- 評估聚焦於模型輸出，尚未納入真人使用者的互動動態、澄清行為與認知負荷。

#### 可重現性評估

**開放資源**
論文提供了程式碼倉儲：https://github.com/MAPS-research/EvoGenUI-Bench，這是提升可重現性（reproducibility）的重要基礎。若倉儲內包含完整的任務提示、評分腳本、瀏覽器自動化設定、操作者軌跡（actor traces）生成邏輯與診斷分類標註，則其他研究者能夠相對容易地複製主要實驗。

**資料集與模型權重**
- **資料集**：150 個五輪任務與 750 輪的對話內容是評估的核心。若作者完整釋出這些任務的初始請求、修訂序列與預期行為規格，將大幅提升可重現性。
- **模型權重**：本基準測試評估的是現成的大型語言模型（LLM），多數為透過 API 存取的專有模型，因此不涉及釋出模型權重。重現時需使用相同模型版本、溫度參數（temperature）與提示模板（prompt template），作者應在論文或倉儲中清楚記載這些設定。
- **評估管線**：瀏覽器執行、截圖、DOM 解析、執行階段日誌收集與操作者軌跡需要依賴 Playwright 或 Selenium 等自動化工具。若提供容器化環境（如 Docker）與相依套件清單，可有效降低環境差異造成的重現誤差。

**潛在挑戰**
- 專有模型 API 可能隨時間更新，導致相同提示產生不同結果；建議作者釋出原始模型輸出與種子設定，以便進行確定性比較。
- 瀏覽器渲染與工具呼叫可能受網路狀態、字型與作業系統影響，需要標準化的執行環境。
- 診斷分類法若有人工標註成分，應公開標註指引與一致性數據，才能讓後續研究進行公平比較。

**建議**
為達到高度可重現性，建議作者釋出：完整任務語料、黃金標註（gold annotations）、評分腳本、容器化執行環境、模型 API 設定與原始輸出紀錄。如此一來，EvoGenUI-Bench 才能成為生成式 UI 領域長期使用的標準評估平台。

#### 未來研究方向

**1. 更長期的產物演進與開放式對話**
未來研究可將五輪任務擴展到更長的對話片段（episode），甚至開放式、無固定長度的互動。同時可引入使用者模擬器（user simulator）來產生更自然、包含撤回、修正與矛盾需求的請求，測試模型在真實動態環境下的維護能力。

**2. 記憶與差異化編輯機制**
針對跨輪保留（cross-turn retention）低下的問題，可探索專為生成式 UI 設計的記憶架構，例如顯式需求記憶、版本控制、差異化程式碼編輯（diff-based editing），以及基於對話歷史的需求追蹤機制，以減少遺忘與迴歸。

**3. 執行後自我驗證與自動修復**
模型可在輸出後利用瀏覽器執行（browser execution）結果進行自我驗證，檢查截圖、DOM 與執行階段日誌，並自動修復錯誤。這類「生成—執行—驗證—修復」迴圈可顯著提升對話片段完成率（episode completion rate）。

**4. 多模態與混合主動式互動**
除了文字請求，未來可納入草圖、語音、螢幕標註或指向式輸入，並研究混合主動式（mixed-initiative）協作：助理不僅被動修改介面，也能主動提出設計建議、衝突警告或替代方案。

**5. 真實外部狀態與動態工具整合**
工具接地外部狀態（tool-grounded external state）任務可進一步擴展到真實、動態、具認證機制的 API，並研究如何建立穩定的狀態同步機制，例如使用反應式框架（reactive framework）或狀態機（state machine）來維持介面與外部狀態的一致性。

**6. 以人為本的評估**
自動化指標之外，未來應進行真人使用者研究，測量可用性、信任度、認知負荷與任務完成效率。特別是當介面在多輪後變得複雜時，使用者對「介面是否仍符合預期」的主觀感受至關重要。

**7. 領域專用與無障礙基準測試**
可針對特定領域（如資料視覺化、醫療儀表板、電子商務表單）建立專用基準，並加入無障礙（accessibility）、國際化與設計系統（design system）遵循等評估維度。

**8. 模組化代理架構**
將單一 LLM 擴展為多代理（multi-agent）系統，例如分離規劃器（planner）、程式碼生成器（coder）、視覺檢查器（visual critic）與測試執行者（test executor），可能改善需求分解（requirement decomposition）與長期維護表現。

**9. 對抗性與邊界案例測試**
設計刻意模糊、矛盾或極端累積的請求，測試模型的穩健性與錯誤恢復能力，例如要求刪除不存在功能、反覆切換主題，或在多輪後要求回復到早期版本。

**10. 與現代開發工具鏈整合**
未來助理可與版本控制、元件庫、設計系統及現代前端框架（如 React、Vue、Svelte）整合，使生成的產物不僅可執行，也具備可維護性與工程實務上的可用性。

## 論文問答

**Q1：EvoGenUI-Bench 主要想解決什麼問題？**

A：EvoGenUI-Bench 旨在解決大型語言模型在「多輪介面維護」上的可靠性問題。雖然現今 LLM 已能生成互動式網頁介面，但真正的生成式 UI 助理必須在對話過程中持續維護一個可執行產物，並隨著使用者請求演進而不斷更新。此基準測試評估模型是否能在每一輪中正確實作當前請求，同時保留仍然有效的需求、對話歷史與介面行為。

**Q2：現有的方法或基準測試為何無法充分捕捉這個問題？**

A：現有基準大多將「產物建構」與「任務執行」分開處理，模型要麼開發介面、要麼在預先定義的環境中操作，缺乏對持續演進介面的整體評估。此外，許多評估採用單次生成（single-shot）方式，無法反映使用者在真實對話中反覆修改需求的累積效應。這導致模型容易出現遺忘或覆蓋先前功能、對話狀態不一致等問題，而這些正是多輪生成式 UI 助理的核心挑戰。

**Q3：為什麼多輪介面維護對生成式 UI 助理如此重要？**

A：在實際應用中，使用者很少一次提出完整介面需求，而是透過多輪對話逐步添加、修改或精煉功能。每一輪更新都必須在回應當前請求的同時，維持先前功能的可執行性與可見狀態的一致性。若無法做到這點，助理產出的介面將難以成為可信賴的互動層，也會損害使用者對生成式 UI 系統的信心。

**Q4：EvoGenUI-Bench 的核心方法是什麼？**

A：該基準包含 150 個五輪任務，共 750 輪，涵蓋資訊呈現、可執行互動與工具接地外部狀態三大情境。對於每一個請求，系統會嘗試在瀏覽器中建立並執行生成的介面產物，並透過截圖、原始碼與 DOM 證據、操作者軌跡以及執行階段日誌進行綜合評估。這種瀏覽器執行與多源證據結合的方式，能夠更真實地檢驗介面行為與狀態是否正確。

**Q5：EvoGenUI-Bench 的關鍵創新有哪些？**

A：首先，它將生成式 UI 的評估從「判斷單一輸出」重新框架為「檢驗產物演進過程中行為、狀態與助理聲稱是否保持同步」。其次，它提出相鄰通過保留率（APR）這項跨輪保留指標，用於衡量前一輪通過後下一輪仍能通過的比率。最後，它整合了視覺、行為、原始碼與執行階段等多層面證據，並同時評估輪次層級、對話片段層級與轉換層級的可靠性。

**Q6：作者在設計上做了哪些重要選擇？**

A：作者選擇五輪對話片段作為基本單元，以在任務複雜度與評估可行性之間取得平衡。他們將任務劃分為三大情境套件，分別對應不同的失敗機制：資訊架構、衍生狀態傳播與功能可見性綁定、以及外部狀態接地與需求分解。此外，他們堅持在真實瀏覽器中執行產物，並結合自動化操作者軌跡與多種證據來源，以提升評估的客觀性與涵蓋面。

**Q7：實驗中使用了哪些基準情境？**

A：實驗涵蓋三種情境：資訊呈現情境評估模型如何組織密集資訊；可執行互動情境評估具有本地狀態的互動介面；工具接地外部狀態情境則評估透過工具與外部執行階段狀態連結的介面。每個任務都以初始介面生成請求開始，隨後對同一個介面進行四次連續修訂，形成完整的五輪對話片段。

**Q8：實驗的主要結果是什麼？**

A：在八個受測模型中，即使表現最佳的模型也僅達到 74.9% 的輪次通過率，而五輪對話片段的完整完成率只有 37.3%。在工具接地任務上，相鄰通過保留率（APR）更進一步下降至 52.4%。這些結果顯示，模型在單一輪次中表現尚可，但要在長期對話中持續維持介面可靠性仍有顯著落差。

**Q9：診斷分析揭示了哪些失敗模式？**

A：診斷分析顯示，呈現失敗主要集中在資訊架構設計不當；互動失敗則多與衍生狀態傳播錯誤以及功能可見性綁定失誤有關；工具接地失敗除此之外，還涉及外部狀態接地不準確以及需求分解能力不足。這些發現幫助研究者區分不同類型的介面維護失敗，並針對性地改進模型能力。

**Q10：這項研究可應用於哪些實務場景？**

A：此研究可應用於需要反覆迭代的任務導向互動介面，例如旅遊規劃器、儀表板、表單、比較視圖與小型應用程式。在這些場景中，使用者會持續新增功能、調整版面或連接外部資料，而介面必須保持一致與可執行。此外，任何將 LLM 作為互動層的產品，如生產力工具、資料視覺化平台或工作流程應用，都能從中受益。

**Q11：對產品開發有哪些重要啟示？**

A：產品開發者應建立機制來驗證每次修訂不會破壞先前功能，例如自動化迴歸測試或狀態一致性檢查。系統應明確維護對話歷史與仍然有效的需求，避免模型在新增功能時遺忘舊有約束。對於工具接地功能，更需要強化外部狀態同步，並清楚地向使用者傳達當前介面狀態與助理聲稱。

**Q12：這項研究對整個領域可能產生什麼影響？**

A：此研究促使學界與業界將研究焦點從令人驚豔的單次生成展示，轉向可靠的多輪維護能力。它提供了一個標準化的基準測試，讓不同模型能在相同條件下比較介面維護表現。同時，它所識別出的具體失敗機制，也為未來的模型架構、訓練資料與系統設計提供了明確的改進方向。

**Q13：作者承認了哪些限制？**

A：作者指出，目前基準採用五輪對話片段，可能無法完全涵蓋更長、更複雜的真實對話情境。此外，研究主要聚焦於網頁介面，尚未涵蓋原生應用程式或其他平台。自動化評估雖然客觀，但可能無法捕捉所有使用者體驗層面的細微差異，例如美學偏好或互動流暢度。

**Q14：研究特別強調了哪些失敗案例？**

A：研究發現模型在新增功能時經常遺失或覆蓋先前功能，導致介面行為與對話歷史不一致。在互動情境中，模型難以正確傳播衍生狀態，並將功能可見性正確綁定到介面元素上。在工具接地情境中，模型則容易在外部狀態接地與需求分解上出錯，使得介面無法準確反映外部真實狀態。

**Q15：未來可以朝哪些方向發展？**

A：未來研究可擴展到更長的對話片段、更多樣化的介面類型，以及更豐富的工具整合情境。提升模型對需求與狀態的顯式追蹤能力，將是改善跨輪保留率的關鍵。此外，發展自動修復機制、引入人機協作驗證，以及設計更強大的多輪訓練資料，都是值得探索的方向。

## 實務應用指南

### 適用場景

**1. 企業內部儀表板與報表產生器**
業務團隊可透過對話逐步調整儀表板：從「顯示本季銷售數據」開始，接著追加「按區域分組」「加入趨勢圖」「串接即時庫存 API」「切換深色模式」。系統必須在每一輪保留前序的篩選條件與視覺設定，而非每次重新生成獨立頁面。

**2. 低程式碼／無程式碼應用開發平台**
產品經理或公民開發者以自然語言迭代建構小型應用，例如活動報名表、工單追蹤器或預約系統。隨著需求演進，助理需持續維護可執行的前端產物，確保表單欄位、互動狀態與外部資料源保持同步。

**3. 旅遊／財務／健康等個人規劃助理**
如論文圖一所示的行程規劃器，使用者會陸續加入預算、天氣、地圖與主題切換等功能。這類應用要求介面在多次修訂後，仍能正確呈現資訊架構並維護衍生狀態（例如總花費、天數統計）。

**4. 客服或銷售支援的動態介面**
第一線人員可依對話脈絡即時生成客製化介面，例如產品比較表、報價試算表或退換貨表單。多輪對話中，助理必須避免覆蓋已確認的客戶資訊，並讓介面行為與助理聲稱保持一致。

**5. 教育與培訓互動教材**
教師可逐步建構互動式學習單，從基礎題目開始，陸續加入提示、計分邏輯、即時回饋與協作功能。每一輪更新都需確保學習流程與狀態傳播正確無誤。

### 實作前置條件

**資料準備**
- 具代表性的多輪對話歷史資料集，包含初始請求與後續修訂指令。
- 每個任務需附帶可驗證的評估準則，涵蓋視覺呈現、可執行互動與外部狀態同步。
- 若涉及工具接地外部狀態，需準備穩定的 API、模擬環境或沙箱資料。

**運算資源**
- 可執行瀏覽器實例的環境（如 Playwright、Selenium 或 Puppeteer），用於自動化截圖與 DOM 擷取。
- 足夠的 GPU／TPU 或 API 配額以支援八個模型規模的推論與反覆測試。
- 日誌儲存與軌跡回放基礎設施，便於診斷衍生狀態傳播與功能可見性綁定問題。

**技能需求**
- 前端工程能力：HTML、CSS、JavaScript／TypeScript 與現代框架（React、Vue、Svelte 等）。
- LLM 提示工程與多輪對話管理經驗。
- 自動化測試與評估管線設計能力，能整合截圖比對、DOM 檢查、操作者軌跡與執行階段日誌。
- 對資訊架構、互動設計與狀態管理有基本認識，以便分類失敗模式。

### 實作步驟建議

**步驟一：定義任務情境與評估維度**
參照論文的三種情境，將產品需求歸類為「資訊呈現」「可執行互動」或「工具接地外部狀態」。為每個任務設計五輪對話片段，確保每一輪都會對同一可執行產物進行累積修訂。

**步驟二：建立瀏覽器執行與證據蒐集管線**
讓模型生成的原始碼在隔離瀏覽器中執行，並同時收集截圖、DOM 證據、原始碼證據、操作者軌跡與執行階段日誌。這五種證據構成評估的客觀基礎。

**步驟三：設計三層指標**
- 輪次通過率（Turn Pass）：單一輪次是否滿足當前請求並保留仍然有效的需求。
- 對話片段完成率（TP@5）：五輪任務是否全部通過。
- 相鄰通過保留率（APR）：前一轮通過的前提下，下一輪也通過的比例，用以衡量跨輪保留能力。

**步驟四：導入診斷分類機制**
針對失敗案例建立分類法：資訊架構問題、衍生狀態傳播問題、功能可見性綁定問題、外部狀態接地問題與需求分解問題。這有助於定位模型與系統的弱點。

**步驟五：迭代改善模型與介面維護策略**
根據診斷結果調整提示策略，例如加入對話歷史摘要、狀態差異比對或自我檢查步驟。同時考慮引入結構化輸出、版本控制與自動回歸測試，以提升多輪介面維護的穩定性。

### 潛在風險與注意事項

**風險一：輪次通過率高但對話片段完成率低**
論文顯示最強模型輪次通過率達 74.9%，但五輪對話片段完成率僅 37.3%。這表示單次表現無法代表長期可靠性。建議將 TP@5 與 APR 列為產品上線前的必要門檻，而非只看單輪成功率。

**風險二：工具接地任務的跨輪保留特別脆弱**
工具接地外部狀態情境的 APR 僅 52.4%，常見於外部 API 回應與介面狀態不同步。建議為外部狀態建立明確的快取與重新整理策略，並在助理回應中清楚標示資料來源與更新時間。

**風險三：衍生狀態傳播錯誤導致使用者困惑**
例如預算總額未隨行程調整而更新。建議在每次修訂後自動執行一組狀態一致性檢查，確認所有衍生數值與可見狀態符合對話歷史。

**風險四：功能可見性綁定失效**
按鈕或輸入框看似存在但無法正確觸發行為。建議透過操作者軌跡進行端到端互動測試，而非僅仰賴靜態截圖或原始碼檢查。

**風險五：需求分解不當造成部分遺漏**
當使用者一次提出多個請求時，模型可能只實作其中一部分。建議在提示中要求模型先列出待實作項目，並在回應中逐項確認完成狀態。

### 與其他技術的整合建議

**與設計系統（Design System）整合**
將元件庫與樣式規範納入模型上下文，可減少資訊架構失敗並確保視覺一致性。例如要求模型優先使用既有的卡片、表格、表單與導航元件。

**與版本控制系統整合**
每一輪生成的可執行產物都應視為一次提交（commit），便於回溯、比較差異與進行回歸測試。這對於測量相鄰通過保留率與定位退化原因至關重要。

**與自動化測試框架整合**
將論文提出的五種證據蒐集機制封裝為 CI／CD 管線中的測試步驟，例如截圖比對測試、DOM 斷言、互動軌跡錄製與日誌檢查。

**與 Retrieval-Augmented Generation（RAG）整合**
對於長對話歷史，可將仍然有效的需求抽取並儲存於向量資料庫，讓模型在每一輪快速檢索相關上下文，降低遺忘或覆蓋舊需求的風險。

**與外部工具與 API 管理平台整合**
工具接地任務需統一的 API 呼叫、錯誤處理與狀態同步機制。建議透過工具編排層管理外部狀態，而非讓模型直接生成任意網路請求。
