## ⚡ TL;DR

現有基準測試建構費力且易性能飽和，難以區分最先進模型能力。
本文提出全自主的基準測試代理，自動化完成從查詢分析到品質控管的建構流程。
該系統生成十五項跨領域高品質基準測試，並揭示現有模型在特定領域推理的局限。

## 摘要翻譯

基準測試（Benchmarks）透過提供標準化且明確的衡量指標（standardized and explicit measures），對於評估與推進大型語言模型（Large Language Models, LLMs）及多模態大型語言模型（Multimodal Large Language Models, MLLMs）至關重要。然而，基準測試的建構過程勞力密集且難以重複利用，引發了對其永續性（sustainability）與可擴展性（scalability）的疑慮。此外，現有的基準測試在發布後經常迅速達到性能飽和（performance saturation），導致對最先進模型（state-of-the-art models）的鑑別力（discrimination）不足。為因應這些挑戰，我們提出了基準測試代理（Benchmark Agent），這是一個專為基準測試建構所設計的全自主（fully autonomous）代理系統（agentic system）。我們的框架統籌了完整的基準測試建構流程（benchmark construction pipeline），從使用者查詢分析（user query analysis）、子任務設計（subtask design）到資料標註（data annotation）與品質控管（quality control）。為了評估基準測試代理，我們實作該系統以建構 15 個具代表性的基準測試，涵蓋多樣的評估情境（evaluation scenarios），包括文字理解（text understanding）、多模態理解（multimodal understanding）及特定領域推理（domain-specific reasoning）。廣泛的實驗，包括人工評估（human evaluation）、LLM 作為評判者（LLM-as-a-judge）的評估，以及一致性檢查（consistency checks），顯示基準測試代理能夠在極少人為介入的情況下生成高品質的基準測試樣本（benchmark samples）。更重要的是，透過持續評估（continual evaluation），我們觀察到若干具啟發性的發現，包括現有模型在某些特定領域推理任務上表現不佳。我們相信快速演進的基準測試能為研究社群帶來重大貢獻。預覽版本與程式碼將於示範頁面（demo page）及程式碼儲存庫（code repository）公開釋出。

### 核心貢獻（3～5點）
- 提出基準測試代理，一個全自主代理系統，能統籌從使用者查詢分析、子任務設計到資料標註與品質控管的完整基準測試建構流程。
- 實際建構 15 個涵蓋文字理解、多模態理解及特定領域推理等多樣評估情境的代表性基準測試，驗證系統的實用性。
- 透過人工評估、LLM 作為評判者與一致性檢查等多面向驗證，證明系統能在極少人為介入下生成高品質基準測試樣本。
- 藉由持續評估發現，現有最先進模型在特定領域推理任務上仍存在明顯瓶頸，顯示快速演進基準測試的必要性。
- 相較於傳統基準測試易於性能飽和且建構成本高昂，本框架具備顯著的永續性與可擴展性。

### 適合對象
從事大型語言模型與多模態模型評估、基準測試設計的研究者，以及需要自動化建構領域專屬評測資料集的工程師與研究團隊。

## 深度分析

#### 方法論解析

本文提出之 Benchmark Agent（基準測試代理）為首個針對基準測試（Benchmark）建構任務設計之全自主（Fully Autonomous）代理系統（Agentic System）。有別於傳統依賴大量人力介入之基準測試建構流程（Benchmark Construction Pipeline），該系統透過雙元件架構實現從使用者查詢分析（User Query Analysis）、子任務設計（Subtask Design）、資料標註（Data Annotation）至品質控管（Quality Control）之端到端自動化。

其核心設計靈感源自腦—小腦（Brain-Cerebellum）階層式架構，由兩大模組緊密耦合而成：

1. **Benchmark Planner（基準測試規劃器）**：作為高層決策模組，負責將抽象之人類評估需求轉譯為具體可行之基準測試規格。其輸出涵蓋子任務劃分（Subtask Division）、資料配置（Data Configuration）及整體轉換方案（Transformation Schemes），扮演類似「大腦」之策略規劃角色。
2. **Benchmark Executor（基準測試執行器）**：作為執行模組，負責將規劃器產出之規格轉化為標準化、可執行之基準測試樣本（Benchmark Sample），並處理實際之資料生成與格式標準化，功能類比「小腦」之運動協調。

兩者透過迭代式自洽工作流程（Iterative, Self-Consistent Workflow）持續交互：Planner 根據 Executor 回傳之實際資料條件與執行限制調整高層策略，Executor 則依據更新後之規格進行樣本生成，形成閉迴路優化。此設計有效橋接高層評估需求與真實世界資料條件，解決基準測試建構作為長期任務（Long-Horizon Task）所面臨之規劃—執行落差。

該框架具備三項顯著特徵：

- **使用者導向客製化（User-oriented Customization）**：不同於 MMLU、GSM8K 等通用基準測試採用廣泛且統一之評估協議，Benchmark Agent 可依特定使用者需求調整任務格式（Task Format）、相關領域（Domain）及評估標準（Evaluation Criteria），實現個人化評估任務。
- **低人力成本之高品質輸出**：透過標準化與自動化關鍵建構階段，建立可重複使用（Reusable）之流程，顯著降低重複性人工投入。
- **跨模態泛化能力**：系統已驗證可產出涵蓋文字理解（Text Understanding）、多模態理解（Multimodal Understanding）、特定領域推理（Domain-Specific Reasoning）等 15 種代表性評估情境之基準測試，橫跨數學推理（Mathematical Reasoning）、藝術理解（Art Understanding）、醫學理解（Medical Understanding）、基於音訊的推理（Audio-based Reasoning）、圖像—音訊—文字理解（Image-Audio-Text Understanding）、一般理解（General Comprehension）、程式碼理解（Code Understanding）及多語言音訊理解（Multilingual Audio Understanding）等多元模態（Modality）。

#### 實驗數據解讀

為驗證 Benchmark Agent 之有效性，作者實作並產出 15 項代表性基準測試，並透過三重驗證機制進行品質評估：

1. **人工評估（Human Evaluation）**：作為品質驗證之黃金標準，確認生成樣本之語意正確性、選項合理性及難度適切性。
2. **LLM 作為評判者（LLM-as-a-Judge）**：利用大型語言模型（LLMs）自動評測生成樣本之品質與判別力，作為可擴展之自動化評估手段。
3. **一致性檢查（Consistency Check）**：檢驗樣本內部邏輯自洽性與跨樣本標準一致性，確保基準測試之信度。

實驗結果顯示，Benchmark Agent 可在極少人力介入（Minimal Human Involvement）下生成高品質基準測試樣本。更重要的是，透過持續評估（Continual Evaluation），研究團隊觀察到現有最先進模型（State-of-the-Art Models）在特定領域推理任務上仍存在顯著瓶頸，顯示自動生成之客製化基準測試能有效揭露通用基準測試未能捕捉之模型弱點。

此外，圖 2 之統計分析揭示了現有基準測試之性能飽和（Performance Saturation）現象：以 Qwen 與 Qwen-VL 系列模型為例，其在 MMLU、AI2D、MMLU-Pro、MMMU、GSM8K、MATH、MathVision、Arena-Hard、OSWorld 等基準測試上，準確率於短時間內迅速突破 80%。此現象導致最先進模型間之鑑別力（Discrimination）顯著不足，凸顯傳統靜態基準測試之侷限，亦反襯出 Benchmark Agent 所倡議之「快速演進基準測試」之必要性。

#### 與現有研究的比較

現有基準測試之建構模式多為人力驅動（Human-Driven），如 MMLU、GSM8K、MMMU 等經典基準測試，其開發需投入大量資源於任務設計、資料收集與清洗、人工標註及人類偏好對齊。此類流程通常針對個別基準測試量身打造，每項新基準幾乎從頭開始建構，造成重複性人工投入、緩慢之迭代週期，並對基準測試生態之永續性（Sustainability）與可擴展性（Scalability）構成嚴峻挑戰。

相較之下，Benchmark Agent 之貢獻與差異化優勢如下：

- **從靜態到動態**：傳統基準測試發布後迅速面臨性能飽和，而 Benchmark Agent 透過全自主流程，能依據模型能力演進持續產出新型評估任務，維持評估之鑑別力。
- **從通用到客製**：現有基準測試多採廣泛且統一之評估協議，難以滿足特定領域或細粒度能力之評估需求；Benchmark Agent 則支援使用者導向客製化，填補此缺口。
- **從孤立到可複用**：傳統流程難以重複使用，而 Benchmark Agent 將基準測試建構流程標準化，形成可重複調用之自動化管線。

然而，本研究仍存在若干侷限。首先，系統作為代理系統（Agentic System），其生成與評判品質高度依賴底層大型語言模型之能力，可能繼承骨幹模型之知識截止（Knowledge Cutoff）、偏見（Bias）及幻覺（Hallucination）問題。其次，對於醫學理解（Medical Understanding）等高風險特定領域，完全無人監督之自動生成是否具備足夠之信度與效度，仍需更嚴謹之跨領域專家驗證。最後，品質控管機制雖已導入自動化檢查，但在極端複雜之多模態推理情境下，自動化品質控管之上限仍有待探索。

#### 可重現性評估

就開源與可重現性（Reproducibility）而言，作者於文中承諾預覽版本與程式碼將公開於示範頁面（Demo Page）與程式碼儲存庫（Code Repository）。然而，由於本文目前為預印本（Preprint）階段，實際釋出之完整性與即時性仍需視後續官方發布狀況而定。

值得注意者，Benchmark Agent 並非傳統意義上之預訓練模型，而是一個框架（Framework）或系統，其運作必然依賴底層大型語言模型（LLMs）或多模態大型語言模型（MLLMs）作為骨幹。因此，其可重現性不僅取決於生成管線程式碼之開源，更受下列因素影響：

- **骨幹模型版本**：若系統呼叫 GPT-4、Claude 或 Gemini 等商業 API，不同版本之模型行為差異將直接影響生成基準測試之內容與品質，實驗之嚴格可重現性面臨挑戰。
- **提示工程（Prompt Engineering）細節**：Planner 與 Executor 之迭代邏輯、提示模板（Prompt Template）及參數設定（如 Temperature、Sampling Strategy）需完整揭露，方能確保其他研究者複現相同流程。
- **品質控管閾值**：自動化品質控管之具體規則與通過標準若未詳盡記載，將降低跨實驗室比較之可信度。

建議作者除釋出核心程式碼外，一併提供配置檔案（Configuration Files）、完整提示模板、所使用 API 之確切版本紀錄，以及 15 項已生成基準測試之資料集快照（Dataset Snapshot），以最大化研究之可重現性與社群貢獻度。

#### 未來研究方向

基於 Benchmark Agent 之架構與實驗發現，未來研究可沿以下數個方向深化與拓展：

1. **動態基準測試演進（Dynamic Benchmark Evolution）**：建立與模型能力同步進化之自動化機制，當既有基準測試之模型表現達到預設飽和閾值時，自動觸發 Benchmark Agent 生成更高難度或全新評估維度之任務，形成持續評估（Continual Evaluation）之閉迴路。
2. **多代理協作架構（Multi-Agent Collaboration）**：擴展現有雙元件設計，引入專責於特定模態（如音訊、影像、程式碼）之領域代理（Domain Agent），以及獨立之對抗性驗證代理（Adversarial Verification Agent），透過多代理辯證進一步提升基準測試之難度與多樣性。
3. **高風險領域之人機協作（Human-in-the-Loop）**：針對醫學理解、法律推理等高風險特定領域推理任務，設計輕量級專家回饋機制，於關鍵節點介入校準，兼顧自動化效率與安全性。
4. **對抗性基準測試生成（Adversarial Benchmark Generation）**：使 Benchmark Agent 不僅被動回應使用者查詢，更能主動探測模型弱點，生成針對性對抗樣本，以壓力測試（Stress Test）方式評估模型之穩健性。
5. **跨語言與文化適應**：現有多語言音訊理解僅為起點，未來可擴展至更多低資源語言（Low-Resource Languages）及具文化特異性之推理任務，評估模型之全球公平性與文化敏感度。
6. **減輕骨幹模型偏見（Backbone Bias Mitigation）**：開發去偏（Debiasing）與知識外掛（Knowledge Plug-in）技術，降低 Benchmark Agent 因依賴特定 LLM 而產生之知識同質化與觀點偏頗，確保生成基準測試之客觀性與廣泛適用性。

## 論文問答

**Q1：當前基準測試建構面臨哪些核心挑戰，這些挑戰如何影響大型語言模型的評估生態系？**
A：現有基準測試的建構過程高度依賴人力，導致勞力密集且難以重複利用，進而引發永續性與可擴展性的嚴重疑慮。此外，現有基準測試在發布後往往迅速達到性能飽和，使得最先進模型之間缺乏足夠的鑑別力。這些問題共同阻礙了研究社群對大型語言模型與多模態大型語言模型進行有效且持續的評估，迫使研究者不斷投入大量資源從頭開發新基準。

**Q2：為何現有人工主導的基準測試流程難以持續，且其產出的基準測試會迅速失去對最先進模型的鑑別力？**
A：傳統的基準測試建構流程主要由人類主導，需要投入大量心力於任務設計、資料收集與清理、人工標註以及人類偏好對齊等環節。這些流程通常為個別基準測試量身打造，導致每個新基準幾乎都必須從頭開始建構，造成重複的人力耗費與緩慢的迭代週期。更重要的是，這種模式無法快速回應模型能力的快速演進，使得基準測試在短時間內就失去區分模型差異的能力，如 Qwen 系列模型在多項基準上迅速突破八成正確率所示。

**Q3：在模型能力快速演進的背景下，開發全自主基準測試建構系統為何具有關鍵性的研究價值？**
A：基準測試是評估與推進大型語言模型及多模態大型語言模型的根本工具，能提供標準化且明確的性能衡量指標。然而，若建構過程無法永續且具備規模化能力，研究社群將難以持續追蹤模型進展並發現其新興限制。因此，開發全自主的基準測試代理系統對於維持評估體系的活力、降低人力成本，以及確保模型評估能與技術發展同步演進至關重要。

**Q4：Benchmark Agent 的雙組件架構如何運作，Benchmark Planner 與 Benchmark Executor 各自扮演什麼角色？**
A：Benchmark Agent 採用受大腦與小腦階層式架構啟發的雙組件設計，包含 Benchmark Planner 與 Benchmark Executor 兩大核心模組。Benchmark Planner 作為高階決策模組，負責將人類的評估需求轉譯為具體可行的基準測試規格，涵蓋子任務劃分、資料配置與整體轉換方案。Benchmark Executor 則作為操作模組，將這些規格轉換為標準化且可執行的基準測試，兩者緊密耦合以建立迭代且自我一致的工作流程。

**Q5：相較於傳統基準測試建構方法，Benchmark Agent 在「使用者導向客製化」與「成本效益」方面帶來哪些突破性創新？**
A：與現有主要評估通用能力的基準測試不同，Benchmark Agent 聚焦於客製化與個人化的評估任務，能夠針對特定使用者需求調整任務格式、相關領域與評估標準。此系統標準化並自動化了基準測試建構的關鍵階段，建立了可重複使用的流程管線，從而大幅降低了人力勞動成本。透過這種方式，研究者在極少人力介入的情況下，即可獲得符合特定評估目標的高品質基準測試樣本。

**Q6：作者為何選擇以大腦與小腦的階層式架構作為 Benchmark Agent 的設計藍本，這種設計如何解決長期任務的挑戰？**
A：由於基準測試建構屬於長期任務，對於簡單的大型語言模型代理系統構成重大挑戰，作者因此借鏡大腦與小腦的階層式架構來設計系統。這種雙組件設計透過高階規劃與低階執行的分離，有效橋接了高層次的評估查詢與真實世界的資料條件及實際執行限制。如此一來，Benchmark Planner 能專注於策略性的規格制定，而 Benchmark Executor 則負責操作層面的實現，確保整體流程既具策略性又可行。

**Q7：研究團隊如何驗證 Benchmark Agent 的跨領域泛化能力，其生成的 15 個基準測試涵蓋了哪些評估情境？**

## 實務應用指南

### 適用場景

1. **企業內部模型選型與垂直領域驗證**：金融、醫療或法律機構需評估大型語言模型在內部文件理解、法規遵循或專業術語推理的表現，但公開基準測試無法覆蓋其私有領域知識。Benchmark Agent 可依據內部語料自動生成客製化測試集，作為採購或微調前的盡職調查工具。
2. **多模態產品迭代測試**：智慧車載、具身智慧（Embodied AI）或智慧硬體團隊需持續驗證模型在「圖像-音訊-文字」混合輸入下的表現。透過全自主代理系統，團隊可針對真實感知場景（如車內對話結合路況影像）動態產生評估樣本，追蹤模型退化或進步。
3. **教育科技與適性學習平台**：針對數學推理、程式碼理解或藝術人文等科目，平台可依學生程度或課綱變化，自動生成個人化評量題目與難度分級。當學生能力或模型輔助水準提升時，系統自動更新題庫以避免性能飽和。
4. **模型安全與紅隊測試（Red Teaming）**：資安或 AI 倫理團隊可利用此框架自動化生成針對特定攻擊面向（如越獄提示、偏見誘導、虛假資訊傳播）的評估樣本，並隨模型防禦機制演進持續擴充測試維度。
5. **開源社群與研究機構的持續性評測**：當現有基準測試（如 MMLU、GSM8K）趨近飽和、鑑別力下降時，研究者可利用 Benchmark Agent 快速建立新一代動態基準，維持對最先進模型的區分能力，並降低重複人工建構的成本。

### 實作前置條件

- **資料**：須具備與評估目標相關的原始語料或媒體檔案（如 PDF、醫學影像、音訊、程式碼庫）。若為封閉領域，建議準備領域知識庫或專家撰寫的參考答案作為品質錨點（Gold Reference）。
- **運算**：需能呼叫高效能大型語言模型 API（如 GPT-4、Claude 3.5 或同等開源模型）作為 Benchmark Planner 與 Benchmark Executor 的推理後端；另需具備儲存與向量檢索基礎設施，以支援資料檢索與品質控管階段的語義比對。
- **技能**：團隊需具備提示工程（Prompt Engineering）與代理系統（Agentic Workflow）設計經驗，並至少有一名熟悉目標領域的主題專家（SME）負責驗證自動生成樣本的語義正確性與難度分佈。

### 實作步驟建議

1. **需求拆解與查詢結構化**：將使用者的高層評估需求（例如「評測模型對胸腔 X 光報告與病歷摘要的聯合推理能力」）轉化為結構化查詢，明確定義模態、領域、難度區間與輸出格式（選擇題、開放問答、多輪對話等）。
2. **規格生成（Planner 階段）**：讓 Benchmark Planner 根據查詢產生子任務設計、資料配置與整體轉換方案。此階段應人工審視產出的規格書（Specification），確認子任務間互斥且涵蓋完整，避免維度過度重疊。
3. **資料準備與前處理**：依規格書收集或清理原始資料，建立資料來源索引。若涉及多模態理解，需統一前處理流程（如音訊轉譯、影像 OCR、影片關鍵幀抽取），確保輸入格式符合 Executor 預期。
4. **自動化樣本生成（Executor 階段）**：由 Benchmark Executor 依規格執行資料標註、題目生成、選項設計與正確答案推導。建議採批次（Batch）處理並保留中繼結果（Intermediate Artifacts），以便後續追蹤與除錯。
5. **多層品質控管**：先以規則式檢查（格式、語法、選項長度平衡）篩選，再以 LLM-as-a-judge 進行語義一致性與難度校驗，最後抽樣進行人工評估，建立黃金標準（Gold Standard）並校正自動評判器的偏差。
6. **基準測試發布與持續迭代**：將通過品管的樣本匯入既有評測框架（如 lm-evaluation-harness 或自研平台），對目標模型執行首次評測。根據模型表現分佈與飽和度，自動或半自動觸發 Planner 重新生成更高難度或新面向的測試集，形成持續評估迴路。

### 潛在風險與注意事項

- **品質漂移（Quality Drift）**：全自主系統在多輪迭代中可能累積錯誤，導致題目語意模糊或答案錯誤。建議建立 Human-in-the-Loop 回饋機制，對每個新批次保留至少 5–10% 的人工覆核比例，並將專家修正意見反饋至 Planner 的提示範本。
- **資料污染（Data Contamination）**：若原始語料來自公開網路，模型可能在預訓練階段已見過類似內容。應實作 n-gram 重疊檢測與嵌入相似度篩選，並優先使用經過改寫的私有資料源，以確保評估效度。
- **評估維度過度擴散**：自動化生成容易產生大量相似子任務，反而降低評測效率與可解釋性。應在 Planner 階段引入覆蓋率與多樣性指標（如語義嵌入分散度）作為約束條件，確保子任務設計精簡且具代表性。
- **成本控管**：大規模呼叫大型語言模型 API 進行生成與評判可能產生高額費用。建議對 Executor 採用階層式模型策略（複雜推理與品質控管使用強模型，格式轉換與簡單標註使用輕量模型）。
- **領域倫理與版權**：醫療、法律等領域資料可能涉及隱私或版權限制。生成過程須確保去識別化（De-identification），並在發布前進行合規審查，避免衍生資料集觸法。

### 與其他技術的整合建議

- **與 MLOps / LLMOps 管線整合**：將 Benchmark Agent 嵌入 CI/CD 流程，在模型微調或部署後自動觸發領域基準測試，作為部署閘道（Deployment Gate）機制。可透過 Airflow、Prefect 或自研排程器編排 Planner→Executor→Evaluator 的工作流。
- **與向量資料庫及 RAG 架構結合**：利用現有企業知識庫作為資料來源，讓 Executor 在生成題目時透過檢索增強生成（RAG）取得相關上下文，確保題目貼近實際業務場景；同時利用檢索結果驗證生成內容的事實性。
- **與現有評測框架對接**：輸出格式建議相容於 EleutherAI lm-evaluation-harness、OpenCompass 或 Hugging Face Evaluate，降低社群與企業採用門檻。可透過轉接器（Adapter）將自動生成樣本轉為標準 JSONL 或 YAML 設定檔。
- **與模型監控（Observability）平台連動**：將基準測試結果即時寫入 Grafana、Weights & Biases 或 LangSmith，追蹤模型在特定維度（如醫學理解、程式碼理解）的長期趨勢，並在性能飽和時自動觸發新基準生成任務，形成閉環監控。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦於論文的圖一與第一章（Introduction），理解「為何現有基準測試會快速飽和」以及「全自主基準測試建構流程」的核心概念。無需深入技術細節，重點掌握 Benchmark Agent 能解決什麼問題，以及它與傳統人工出題在永續性與可擴展性上的差異。
- **AI 工程師**：請詳讀方法論中 Benchmark Planner 與 Benchmark Executor 的雙元件設計，以及品質控管機制。特別關注論文如何處理多模態資料流與 LLM-as-a-judge 的實作細節，這些是將論文落地為產品時的關鍵工程挑戰。
- **研究人員**：建議深入分析實驗章節中 15 個代表性基準測試的設計邏輯與持續評估結果。論文揭示的「特定領域推理任務仍為當前模型弱點」是極具價值的研究線索，可進一步探討動態基準（Dynamic Benchmarking）與模型能力邊界的理論關係。
- **產品經理**：請將閱讀重點放在「使用者導向客製化」與「高品質、低人力成本」這兩大特性上。評估此技術是否適用於你所在的產業場景，並思考如何將「持續演進的基準測試」包裝為產品差異化功能、合規驗證服務或模型選型顧問方案。
