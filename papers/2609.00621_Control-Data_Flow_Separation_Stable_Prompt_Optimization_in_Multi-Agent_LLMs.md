# 控制-資料流分離：多智慧體大型語言模型中的穩定提示最佳化

**原文標題：** Control-Data Flow Separation: Stable Prompt Optimization in Multi-Agent LLMs

## ⚡ TL;DR

多智慧體提示同時承載任務內容與執行協定，提示最佳化易破壞協定導致管線崩潰。
提出控制-資料流分離，將執行控制轉為型別化驗證物件，任務語言保留為可最佳化資料流。
在推理、評論生成與保險評級任務中達成100%最終協定有效性，並持續提升任務表現。

## 摘要翻譯

提示最佳化（Prompt Optimization）能夠改善多智慧體大型語言模型（Multi-Agent LLMs）系統，但被最佳化的提示（Prompt）通常扮演兩個相互交織的角色：生成任務相關內容（Task-Relevant Content），以及指定底層程式碼所依賴的執行關鍵協定（Execution-Critical Protocols），例如訊息路由（Message Routing）、輸出格式化（Output Formatting）與終止訊號（Termination Signals）。因此，一個旨在改善內容生成的提示編輯可能會無意間破壞協定，並導致整個智慧體管線（Agent Pipeline）失效。我們的核心觀察是，這兩個角色具有不同的表示形式：執行關鍵協定通常是結構化的（Structured），而任務相關內容通常以非結構化語言（Unstructured Language）呈現。基於此，我們提出控制-資料流分離（Control-Data Flow Separation），其中執行關鍵的控制被表示為型別化且經驗證的程式物件（Typed, Validated Program Objects），而任務相關語言則保留為智慧體通訊中可最佳化的資料流。此設計使最佳化器（Optimizer）得以改善多智慧體行為，同時避免路由與格式化介面暴露於提示飄移（Prompt Drift）。在合成推理（Synthetic Reasoning）、協作評論生成（Collaborative Review Generation）與保險評級工作流程（Insurance Rating Workflows）上，我們的框架於實證中達到 100% 的最終協定有效性（Eventual Protocol Validity），同時持續提升任務效能。

### 核心貢獻（3～5點）
- 指出提示（Prompt）在多智慧體大型語言模型中同時承擔「生成任務相關內容」與「指定執行關鍵協定」的雙重角色，並說明兩者因表示形式不同（結構化 vs. 非結構化語言）而適合分離。
- 提出控制-資料流分離（Control-Data Flow Separation）框架，將執行關鍵控制表示為型別化且經驗證的程式物件（Typed, Validated Program Objects），使任務相關語言保留為可最佳化的資料流。
- 透過將訊息路由、輸出格式化與終止訊號等協定抽離至控制通道，避免提示最佳化過程中的提示飄移（Prompt Drift）破壞系統執行。
- 在合成推理、協作評論生成與保險評級工作流程三項任務上達到 100% 的最終協定有效性（Eventual Protocol Validity），同時持續提升任務效能。

### 適合對象
從事基於語言模型的多智慧體系統（Language-Model-Based Multi-Agent Systems）研究或開發的學者與工程師，特別是關注提示最佳化、智慧體管線穩定性，以及生產環境中多智慧體系統可靠部署的讀者。

## 深度分析

#### 方法論解析

本研究的核心貢獻在於提出 **control-data flow separation（控制-資料流分離）**，用於解決多智慧體大型語言模型（multi-agent LLMs，多智慧體大型語言模型）在進行 **prompt optimization（提示最佳化）** 時的協定脆弱性問題。以下從問題形式化、脆弱性來源到設計原則逐步拆解。

##### 1. 多智慧體系統的形式化模型

論文將一個基於語言模型的多智慧體系統（language-model-based multi-agent systems，基於語言模型的多智慧體系統）建模為一組智慧體（agent，智慧體）\( \mathcal{A}=\{1,\dots,N\} \) 與一個程式 **controller（控制器）** 之間的互動。每個智慧體 \(i\) 由一組 **prompt（提示）** \(p_i\) 參數化，並固定使用某個基礎大型語言模型（base LLM，基礎大型語言模型）\(f_\theta\)。系統在離散步驟 \(t=1,2,\dots\) 中運行：

\[
y_{i_t t}=f_\theta(p_{i_t},\text{context}_{i_t t})
\]

其中 controller 根據目前狀態選擇要啟動的智慧體 \(i_t\)，建構上下文（context）後查詢 LLM，再將輸出 \(y_{i_t t}\) 解析為執行動作，例如更新訊息、轉交下一個智慧體、或發出 **termination signals（終止訊號）**。最終產生可觀察結果 \(\hat y\)，並與目標 \(y^*\) 比較以計算任務層級損失 \(L(\hat y,y^*)\)。

**Prompt optimization（提示最佳化）** 的目標即為：

\[
\min_{\{p_i\}_{i=1}^N}\mathbb{E}_{(x,y^*)\sim\mathcal{D}}\left[L\left(\hat y(x;\{p_i\}),y^*\right)\right]
\]

這類方法（如 **TextGrad（TextGrad 提示最佳化方法）**、**DSPy（DSPy 提示最佳化框架）** 的 teleprompter（提示器））將提示視為可編輯的文字參數，根據任務回饋反覆修改。

##### 2. 協定脆弱性（Protocol Fragility）的來源

在現有多智慧體系統中，單一智慧體輸出 \(y_{it}\) 通常同時承載兩種功能：

- **Task-relevant content（任務相關內容）**：如論證、評論、分析、解釋等，屬於 **unstructured language（非結構化語言）**，供其他智慧體與最佳化器閱讀。
- **Execution-critical protocols（執行關鍵協定）**：如 **message routing（訊息路由）**、**output formatting（輸出格式化）**、**stop signals（停止訊號）**、終止條件等，屬於 **structured（結構化）** 資訊，供 controller 解析以驅動 **agent pipeline（智慧體管線）**。

這兩種角色被糾纏在同一個文字欄位中，導致 **prompt drift（提示飄移）** 的風險：當最佳化器為了改進任務內容而修改提示時，可能連帶改變輸出中的格式或路由指令，造成 **message parsing（訊息解析）** 失敗、訊息被送往不存在的 **routing targets（路由目標）**，甚至使整個 **execution trace（執行追蹤）** 崩潰。論文在評論生成管線中觀察到，樸素的提示最佳化會使可用輸出（usable output，可用輸出）在最佳化過程中跌至零。

##### 3. 控制-資料流分離的設計

論文的關鍵觀察是：上述兩種角色具有不同的自然表示與消費者。基於此，提出將每個智慧體輸出拆分為兩個通道：

\[
y_{it}=(c_{it}, m_{it})
\]

- **Control channel（控制通道）** \(c_{it}\)：為 **typed, validated program objects（型別化且經驗證的程式物件）**，由 **schema（綱要）** 約束並在執行期進行 **runtime validation（執行期驗證）**。它包含執行關鍵資訊，例如下一個智慧體 ID、是否終止、輸出格式標記等，僅供 controller 消費，**不可被智慧體或 prompt optimizer（提示最佳化器）編輯**。
- **Data channel（資料通道）** \(m_{it}\)：為自由形式的文字訊息，承載任務相關資料（task-relevant data，任務相關資料），供其他智慧體閱讀與最佳化器修改，是端到端提示最佳化的操作表面。

這樣的設計確保：

1. **程式安全性（program-safety property）**：所有程式層級決策（路由、終止、狀態更新）僅依賴經驗證的控制通道；資料通道的內容不會影響執行協定。
2. **最佳化穩定性**：prompt optimizer 只能在資料通道對應的提示區域進行編輯，控制通道的 schema 與解析邏輯保持固定，從而避免提示飄移破壞管線。
3. **表達能力保留**：智慧體仍可使用豐富的自然語言溝通，互動圖仍可隨智慧體決策動態變化，只是這些決策必須透過結構化控制物件表達。

##### 4. 實作層面：cdsep

論文將此框架實作為 Python 函式庫 **cdsep（cdsep Python 函式庫）**。從文中 Listing 3 的說明來看，該函式庫支援以少於 40 行 Python 程式碼建構完整的多智慧體管線。控制通道通常以 Pydantic 或 dataclass 等型別化物件實現，並在每次 LLM 輸出後進行 schema 驗證；若解析失敗，可透過重試或後備機制確保最終產生合法控制物件，從而達到 **eventual protocol validity（最終協定有效性）**。

#### 實驗數據解讀

論文在四個情境下進行評估，並輔以跨 LLM 家族的穩健性研究。以下整理實驗設計、指標與結果意涵。

##### 1. 評估任務與設定

| 任務 | 性質 | 觀察重點 |
|---|---|---|
| **BBH single-agent reasoning（BBH 單一智慧體推理）** | 合成推理（synthetic reasoning，合成推理）任務 | 即使在單一智慧體場景，分離設計仍能維持協定有效性 |
| **MARG collaborative review generation（MARG 協作評論生成）** | 多智慧體協作生成 | 測量內容品質與跨模型穩健性 |
| **Synthetic insurance underwriting（合成保險核保）** | 結構化決策流程 | 驗證在需要嚴格格式與評級的業務流程中的穩定性 |
| **Industry-verified insurance rating workflows（業界驗證的保險評級工作流程）** | 真實產業場景 | 驗證框架在實務應用中的可行性 |

此外，論文在 MARG 上進行三大家族 LLM（OpenAI、Anthropic、Google）的穩健性研究，顯示此問題並非特定模型造成，而是多智慧體架構本身的結構性問題。

##### 2. 關鍵指標

- **Protocol validity（協定有效性）**：衡量 LLM 輸出是否能被 controller 正確解析為合法控制物件，即管線是否持續運行。
- **Eventual protocol validity（最終協定有效性）**：強調在最佳化過程中，系統最終能達到 100% 合法協定，不會因提示飄移而永久崩潰。
- **Task performance（任務表現）**：依任務而異。在 MARG 評論生成中，使用 **Jaccard（Jaccard 相似度指標）** 衡量生成評論與目標評論集合的重疊程度。

##### 3. 主要結果與意涵

- **100% eventual protocol validity**：在四個設定中，control-data flow separation 框架都能維持最終協定有效性。這代表無論 prompt optimizer 如何探索提示空間，控制通道始終受到 schema 與 runtime validation 保護，不會出現整個 agent pipeline 崩潰的災難性失敗。
- **MARG 評論生成的 Jaccard 從 31.0 提升至 44.4**：相較於 **naive prompt optimization（樸素提示最佳化）**（如 TextGrad）有時會讓系統完全崩潰，分離框架不僅維持穩定，還顯著提升內容品質。
- **優於 DSPy 的 teleprompter**：在相同 base LLM 下，本方法在 MARG 上優於 **BootstrapFewShot（BootstrapFewShot 提示器）** 與 **MIPROv2（MIPROv2 提示器）**。這顯示現有強大的提示最佳化器在多智慧體環境中會受到協定脆弱性的限制；將控制與資料分離後，最佳化器才能專注於改進內容與協作品質。
- **跨模型穩健性**：在 OpenAI、Anthropic、Google 三大家族模型上，分離設計都能維持協定有效性，說明此方法具有模型無關性（model-agnostic），問題根源在於「控制與資料糾纏」的架構設計，而非特定 LLM 的格式遵循能力。

##### 4. 結果的深層解讀

這些數據支持一個重要論點：**多智慧體系統的提示最佳化不能僅視為文字層級的最佳化問題**。當輸出同時承載控制語義時，提示空間中存在大量「災難性區域」——輕微的用詞改變就可能讓整個系統失效。Control-data flow separation 透過將控制語義從最佳化表面移除，把一個高維且不穩定的聯合最佳化問題，轉換為相對穩定的「內容提示最佳化 + 固定控制介面」問題。這不僅提升了任務表現，更重要的是讓最佳化過程變得可預測、可部署。

#### 與現有研究的比較

##### 1. 相對於現有提示最佳化方法

現有 **prompt optimization（提示最佳化）** 方法如 **TextGrad（TextGrad 提示最佳化方法）**、**DSPy（DSPy 提示最佳化框架）** 的 BootstrapFewShot 與 MIPROv2，通常將提示視為可編輯文字，並假設修改提示只會影響任務品質。這在單一智慧體問答或簡單任務中大致成立，但在多智慧體系統中，提示輸出還必須被 controller 解析為執行動作。本研究指出，這些方法在 multi-agent LLMs（多智慧體大型語言模型）中會遭遇協定脆弱性，甚至導致可用輸出歸零。

本框架並非要取代這些最佳化器，而是提供一個安全殼層：讓任何 optimizer（最佳化器）只能在資料通道上操作，從而釋放其內容最佳化能力，同時避免破壞執行協定。

##### 2. 相對於結構化生成與約束解碼

近年來有許多研究致力於讓 LLM 輸出符合特定 schema（綱要），例如 JSON mode、Outlines、Sainz et al. (2024) 等。這些方法確保輸出格式合法，但多數應用於單輪工具呼叫或固定輸出格式。本研究的差異在於：

- 將結構化輸出明確區分為 **control channel（控制通道）** 與 **data channel（資料通道）**；
- 控制通道專門承載執行關鍵協定（如 message routing、termination signals），並對 prompt optimizer 封閉；
- 資料通道保留為自由文字，成為最佳化目標。

換言之，本研究不僅要求「輸出合法」，更進一步要求「控制語義不可被提示最佳化漂移」。

##### 3. 與軟體工程原則的關聯

Control-data flow separation 本質上是軟體工程中 **separation of concerns（關注點分離）** 原則在 LLM 系統中的具體化。類比於網路中的控制平面（control plane）與資料平面（data plane），或作業系統中的核心態與使用者態，本研究將「執行控制」與「任務內容」分離。論文的貢獻在於將這個原則形式化、程式化，並針對 Python 控制的多智慧體 LLM 系統提供可執行的實作。

##### 4. 限制與未解決的問題

儘管設計優雅，本研究仍存在若干限制：

- **Schema 設計仍需人工定義**：控制通道的 schema 必須由開發者預先設計，無法自動從任務描述中推導。這在複雜開放式多智慧體系統中可能耗費大量工程心力。
- **僅保證語法/結構有效性**：100% protocol validity 指的是控制物件能通過 schema 驗證，但並不保證路由或終止決策在語意上正確。LLM 仍可能選擇錯誤的下一個智慧體或過早終止。
- **限制智慧體的創新能力**：由於控制通道固定且不可編輯，智慧體無法提出新的互動模式或動態調整管線結構，只能在既有 schema 內運作。
- **評估範圍有限**：雖然涵蓋推理、評論生成與保險評級，但尚未在更開放、更長程的任務（如軟體工程多智慧體協作）中驗證。
- **重試機制可能帶來成本與延遲**：為達到 eventual protocol validity，系統可能在控制物件無效時重試，增加 API 呼叫次數與回應時間。

##### 1. 開源程式碼

並以 Python 函式庫 **cdsep（cdsep Python 函式庫）** 形式釋出。根據文中描述，使用該函式庫可在少於 40 行 Python 程式碼內建構完整的多智慧體管線，這對於重現與後續研究非常友善。

##### 2. 資料集與模型權重

- **BBH（Big-Bench Hard）**：為公開基準，可自由取得。
- **MARG**：若為論文自行提出的評論生成基準，需確認倉庫是否釋出資料與評估腳本；目前提供的片段未明確說明。
- **Insurance underwriting**：包含合成資料與業界驗證資料。合成部分理論上可公開，但業界驗證資料可能涉及隱私或商業機密，未必能完全釋出。
- **模型權重**：本研究使用商業 API 模型（OpenAI、Anthropic、Google），無需下載模型權重，但重現需要相應 API 金鑰與預算。

##### 3. 重現的潛在挑戰

- API 版本與模型行為會隨時間變化，若論文未詳細記錄模型版本、溫度參數、重試次數上限等，未來重現可能出現差異。
- 控制通道的 schema 與驗證邏輯是重現關鍵，需要倉庫提供完整範例與文件。
- 產業驗證資料的不可取得性，可能使外部研究者無法完全複製保險評級工作流程的實驗。

整體而言，本研究在程式碼開放性上表現良好，但資料透明度與實驗超參數文件仍有強化空間。

#### 未來研究方向

基於 control-data flow separation（控制-資料流分離）框架，可延伸出以下研究方向：

1. **自動化 Schema 推導與學習**  
   目前控制通道的 schema 需人工設計。未來可研究如何從任務描述、範例軌跡或自然語言規格中自動推導控制 schema，甚至讓 LLM 在開發階段協助設計並驗證 schema 的完備性。

2. **語意層級的協定正確性保證**  
   現有框架保證控制物件的語法有效性，但未保證路由、終止等決策的語意正確性。可結合形式化方法（formal methods）、模型檢查（model checking）或符號執行，對控制流程進行更高階的驗證。

3. **控制策略與資料提示的聯合最佳化**  
   在固定 schema 下，可進一步研究如何安全地最佳化控制策略（例如學習路由函數）與資料提示，並在最佳化過程中維持不變式（invariant）與安全性約束。

4. **更豐富的控制語言**  
   目前的控制通道主要處理離散路由與終止訊號。未來可擴展至支援條件分支、迴圈、異常處理、子任務委派等更複雜的控制結構，使框架適用於更長程、更動態的多智慧體任務。

   將 cdsep 整合至 AutoGen、LangGraph、CrewAI、DSPy 等框架，讓現有開發者能無縫採用控制-資料流分離，並比較不同框架下的適用性。

## 論文問答

### 背景與動機

**Q1：這篇論文主要想解決什麼問題？**

A：論文指出，在多智慧體大型語言模型系統中，單一提示往往同時承擔兩種角色：一是生成任務相關內容，二是指定執行關鍵協定，例如訊息路由、輸出格式化與終止訊號。由於這兩種角色糾纏在同一個文字輸出中，提示最佳化器為了改進內容品質而做的修改，可能無意間破壞協定，導致整個智慧體管線崩潰。這種問題不只是答案品質下降，而是會造成執行追蹤中斷、訊息解析錯誤，甚至程式直接當機。

**Q2：現有的提示最佳化方法為何在多智慧體情境中變得脆弱？**

A：現有方法通常把提示視為可任意編輯的文字參數，並假設修改提示只會影響生成內容的品質。然而，在多智慧體系統裡，智慧體的輸出同時被控制器用來決定下一步要路由給哪個智慧體、是否停止互動，以及更新哪些中繼狀態。因此，樸素提示最佳化可能改變輸出格式或路由目標，使控制器無法正確解析，最終讓可用輸出降為零。

**Q3：為什麼「協定脆弱性」是一個必須正視的問題，而非只是理論上的擔憂？**

A：作者以協作評論生成任務為例，發現樸素提示最佳化會在最佳化過程中破壞格式指令，使系統可用輸出完全崩潰。這種失敗不是漸進式品質下滑，而是執行層級的災難：訊息可能被傳送到不存在的智慧體，或導致程式終止。對於需要穩定執行的應用場景，例如保險評級或軟體工程管線，這類崩潰會直接影響生產可靠性與使用者信任。

### 方法與創新

**Q4：什麼是「控制-資料流分離」？**

A：控制-資料流分離是論文提出的核心設計原則，主張將每個智慧體的輸出拆成兩個通道：控制通道與資料通道。控制通道是型別化且經驗證的程式物件，專門承載執行關鍵資訊，例如路由目標與終止訊號，並由控制器在執行期驗證其是否符合綱要。資料通道則是自由形式的文字，供其他智慧體與提示最佳化器閱讀與最佳化，從而避免提示飄移影響到底層執行協定。

**Q5：這個框架的關鍵設計選擇有哪些？**

A：首先，控制通道被設計為不可由智慧體或提示最佳化器直接編輯的結構化物件，確保執行決策始終基於經過驗證的欄位。其次，資料通道保留為非結構化語言，讓提示最佳化器能夠在這個表面上進行端對端最佳化，改進智慧體間的協調與內容品質。第三，整個分離機制透過 Python 函式庫 cdsep 實作，並在執行期對控制物件進行綱要驗證，使分離原則在實務中可強制執行。

**Q6：控制-資料流分離如何在保證安全性的同時，保留多智慧體系統的表達能力？**

A：該設計允許智慧體繼續交換豐富的自然語言訊息，也允許提示最佳化器根據任務層級回饋改進提示，同時互動圖仍然可以依賴智慧體的決策動態變化。差別在於，路由目標、輸出格式與終止訊號等執行關鍵資訊，現在是透過型別化且經驗證的程式物件來傳遞，而不是依賴脆弱的自然語言慣例。因此，系統既能維持語言模型的靈活性，又能避免提示編輯意外破壞執行協定。

## 實務應用指南

### 適用場景

1. **協作文件審閱與評論生成**  
   多個審閱智慧體依序對論文、合約或程式碼提出批評與改進建議。控制通道負責決定下一位審閱者、是否進入下一輪，以及終止條件；資料通道則承載具體評論內容。透過分離，可避免提示最佳化改寫「請輸出 JSON 並指定 next_agent」等格式指令，導致管線崩潰。

2. **保險核保與風險評級工作流程**  
   不同智慧體分別負責資料萃取、風險判斷、費率計算與核保決策。控制通道可定義為結構化的動作綱要（如 `action: approve / reject / escalate`、下一個處理單位），資料通道則保存理賠說明、風險理由與客戶溝通文字。這能確保監管所需的決策軌跡與路由邏輯不會因提示調整而飄移。

3. **軟體開發多智慧體管線**  
   例如需求分析 → 程式碼生成 → 測試 → 審查的迴圈。控制通道決定要將程式碼送往測試智慧體或審查智慧體、是否重新生成，以及何時結束；資料通道則是程式碼、測試報告與審查意見。分離後，提示最佳化可專注於提升程式碼品質，而不會破壞「把輸出傳給誰」的執行協定。

4. **客戶服務對話路由與摘要**  
   第一線智慧體理解客戶問題後，控制通道輸出結構化的路由決策（如轉接部門、優先等級、是否結案），資料通道則是給客戶的回覆與對話摘要。這讓客服系統在持續最佳化回覆語氣與內容時，不會讓轉接規則被自然語言覆蓋。

5. **醫療多專家會診決策支援**  
   各專科智慧體針對病歷提出見解，控制通道規範發言順序、是否啟動額外檢查、以及最終建議類型；資料通道則是臨床推理與建議說明。由於醫療場景對可追溯性與協定正確性要求極高，控制-資料流分離能降低提示調整帶來的執行風險。

### 實作前置條件

- **資料準備**
  - 現有管線的執行日誌與失敗案例，特別是因格式錯誤、路由錯誤或終止訊號遺失造成的崩潰。
  - 訓練與評估用的任務樣本，以及對應的目標輸出 \(y^*\)。

  - 提示最佳化所需的反覆運算預算：每次最佳化步驟都要執行完整多智慧體管線並評估損失。
  - 執行期驗證與測試環境，能夠快速重現協定失效情境。

- **技能與團隊**
  - 熟悉 Python 與多智慧體框架（如 DSPy、LangChain、AutoGen 或自訂控制器）。
  - 具備綱要設計能力，能使用 Pydantic、JSON Schema 或類似工具定義控制通道。
  - 了解提示工程與至少一種提示最佳化方法（如 TextGrad、DSPy BootstrapFewShot、MIPROv2）。
  - 有軟體工程測試觀念，能為控制通道撰寫單元測試與回退邏輯。

### 實作步驟建議

1. **拆解現有管線，識別控制與資料**  
   檢視每個智慧體的輸出，標記哪些部分被控制器解析（路由目標、動作、終止訊號、輸出格式），哪些部分只是給其他智慧體或人類閱讀的任務相關內容。

2. **設計控制通道綱要**  
   為每個智慧體定義型別化且經驗證的程式物件，例如 Pydantic model 或 JSON Schema。欄位應只包含執行決策所需資訊，並在執行期驗證其有效性。

3. **重構資料通道提示**  
   將原本混在提示中的格式與路由指令移除，改為強調任務內容、角色與溝通目標。資料通道應保留自然語言的彈性，成為提示最佳化的主要表面。

4. **實作控制器與驗證層**  
   讓控制器只讀取控制通道來決定下一步；資料通道僅用於顯示、記錄或傳遞給其他智慧體。加入執行期驗證與錯誤處理，例如控制物件解析失敗時觸發重試或回退。

5. **引入提示最佳化，但僅限資料通道**  
   使用 TextGrad、DSPy 或其他提示最佳化器調整資料通道提示與少樣本示例，但禁止其修改控制通道綱要或相關提示片段。

6. **建立協定有效性評估**  
   除了任務層級指標（如 Jaccard、準確率），還要追蹤「協定有效性」：每次執行是否成功產生合法控制物件、是否正確路由、是否正確終止。

7. **部署、監控與持續迭代**  
   在生產環境中記錄控制通道與資料通道的完整軌跡，設定協定失效警報，並定期用新樣本重新最佳化資料通道。

### 潛在風險與注意事項

- **過度分離導致語境遺失**  
  若控制通道完全不含任務語境，控制器可能做出錯誤決策。建議讓控制器同時可觀察資料通道作為參考，但**不**以資料通道作為唯一決策依據。

- **綱要過於僵化**  
  控制通道欄位設計太細會增加維護成本，太粗則無法有效防止飄移。應從最關鍵的執行決策開始，逐步精煉綱要。

- **智慧體在資料通道中「偷渡」控制指令**  
  即使控制通道被鎖定，資料通道中的自然語言仍可能包含類似「請轉交給 X」的內容。控制器應忽略資料通道中的路由暗示，並在提示中明確告知智慧體「路由決策僅由控制通道處理」。

- **驗證與重試帶來延遲**  
  執行期驗證、解析失敗重試會增加延遲與成本。建議設定重試上限，並對高風險控制動作設計快速回退路徑。

- **錯誤的安全感**  
  控制-資料流分離能防止「提示飄移破壞協定」，但無法保證任務內容正確或模型不產生幻覺。仍需搭配事實查核、人工審查與完整評估。

### 與其他技術的整合建議

- **與 DSPy / LangChain / AutoGen 整合**  
  可將控制通道實作為 DSPy 的 `Signature` 輸出型別、LangChain 的結構化輸出解析器，或 AutoGen 的 `ConversableAgent` 終止條件。資料通道則維持為自由文字訊息，讓現有提示最佳化器繼續運作。

- **與型別驗證工具整合**  
  使用 Pydantic、JSON Schema 或 `instructor` 等函式庫，強制 LLM 輸出符合控制通道綱要，並在解析失敗時提供明確錯誤訊息。

- **與可觀測性平台整合**  
  將控制通道與資料通道分別記錄到追蹤系統（如 LangSmith、Weights & Biases、OpenTelemetry），方便區分「任務品質問題」與「協定執行問題」。

- **與 CI/CD 整合**  
  把協定有效性測試納入持續整合流程：每次修改提示或綱要時，自動執行一組涵蓋正常與邊界案例的管線測試，確保不會引入新的執行追蹤錯誤。

- **與現有 API 閘道整合**  
  在 LLM 呼叫前後加入控制通道驗證層，作為 API 閘道的中介軟體，讓舊有系統無需大幅改動即可獲得協定保護。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先理解「為什麼提示最佳化會讓多智慧體系統壞掉」：想像一個智慧體本來要說「我同意」，但最佳化後卻說「我同意，請交給審查者 B」，導致程式解析錯誤。接著把重點放在「控制通道」與「資料通道」的區別，並跟著論文中的 `cdsep` 範例動手跑一次，比對有無分離時的差異。

- **AI 工程師**  
  請聚焦第 2、3 節的系統模型與分離設計，思考如何將現有管線重構成控制-資料分離架構。特別注意執行期驗證、錯誤回退，以及如何在提示最佳化器中鎖定控制通道。論文中的 MARG 與保險評級實驗可作為重構時的對照藍圖。

- **研究人員**  
  本文的核心貢獻在於將軟體工程中的控制-資料分離原則形式化到多智慧體提示最佳化，並提出「最終協定有效性」這項安全性質。建議深入閱讀形式化定義與實驗設計，評估該框架能否推廣到其他最佳化方法（如強化學習、可微分提示）或更複雜的互動圖式。

- **產品經理**  
  這篇論文提供了一個降低多智慧體系統維運風險的設計原則。閱讀時請關注「 naive prompt optimization 會讓可用輸出歸零」的實證結果，以及分離後在任務表現與協定有效性上的雙贏。評估導入時，可優先選擇路由/終止邏輯複雜、且提示需要持續迭代的產品場景作為試點。
