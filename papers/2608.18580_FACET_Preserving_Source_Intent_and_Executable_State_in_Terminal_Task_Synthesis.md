# FACET（可執行任務的細粒度代理式建構）：在終端機任務合成中保留來源意圖與可執行狀態

## ⚡ TL;DR

終端機任務合成常遺失來源資訊，且指令、環境、解答與驗證器彼此不一致。
提出 FACET 框架，先重建情境與工作流程，再建構並修復容器環境，以共享可執行狀態生成並對齊工件。
合成出具密集可執行檢核的複雜任務，並在多種模型規模微調後提升 Terminal-Bench 2.1。

## 摘要翻譯

訓練終端機代理（Terminal Agents）需要可規模化的可執行監督（Executable Supervision），然而，高品質終端機任務的合成（Terminal Task Synthesis）仍然具有挑戰性。每個任務結合了指令（Instruction）、初始化環境（Initialized Environment）、參考解答（Reference Solution）與可執行驗證器（Executable Verifier）；若這些工件（artifacts）源於不一致的假設，產生的任務可能無解或遭到錯誤評估。與此同時，多階段合成（Multi-Stage Synthesis）可能會捨棄原始來源中所編碼的目標、相依關係（Dependencies）、狀態轉換（State Transitions）與程序性約束（Procedural Constraints）。我們提出 FACET（Fine-grained Agentic Construction of Executable Tasks，可執行任務的細粒度代理式建構），一個同時因應資訊保存（Information Preservation）與跨工件一致性（Cross-Artifact Consistency）的框架。FACET 將相關的代理技能重建為連貫且資訊豐富的情境，並在生成最終任務工件之前建構並修復執行環境。產生的容器狀態（Container State）可作為指令、解答與驗證器的共享基礎（Shared Grounding），而基於執行的驗證（Execution-Based Validation）與針對性修復（Targeted Repair）則能修正特定工件的失敗，且避免不必要地重新生成仍有效的元件。FACET 可產生具有密集可執行檢查的複雜終端機任務，而從這些任務中收集的成功軌跡則提供了有效且資料效率高的監督（Data-Efficient Supervision）。對多種規模的模型進行微調（Fine-Tuning），皆能一致提升在 Terminal-Bench 2.1 上的表現，而對替代生成方案的分析也支持了基於環境的建構（Environment-Grounded Construction）對於任務有效性（Task Validity）與解答與驗證器對齊（Solution-Verifier Alignment）的重要性。這些結果確立了來源意圖（Source Intent）保存與共享可執行狀態（Executable State）基礎作為可擴展終端機任務合成的關鍵原則。

### 核心貢獻（3～5點）
- 提出 FACET 框架，同時解決終端機任務合成中的資訊保存與跨工件一致性問題。
- 透過基於環境的建構與容器狀態共享基礎，確保指令、參考解答與可執行驗證器之間的一致性。
- 採用基於執行的驗證與針對性修復機制，僅修復失敗工件而保留仍有效的元件。
- 生成具密集可執行檢查的複雜終端機任務，並提供資料效率高的可執行監督。
- 在多種模型規模上驗證微調效果，並確立來源意圖保存與共享可執行狀態基礎為可擴展終端機任務合成的關鍵設計原則。

### 適合對象
本論文適合研究大型語言模型代理、終端機代理訓練、命令列工具（Command-Line Tools）自動化、合成終端機資料流程（Synthetic Terminal-Data Pipelines）以及可執行驗證機制建構的研究人員與工程師。對於關注後訓練（Post-Training）微調、長期工作流程（Long-Horizon Workflows）、代理基準測試設計，以及可規模化監督訊號建構的讀者亦具高度參考價值。

## 深度分析

#### 方法論解析

FACET（Fine-grained Agentic Construction of Executable Tasks，可執行任務的細粒度代理式建構）將終端機任務合成（Terminal Task Synthesis）重新定義為一個「以可執行狀態（Executable State）為中心」的多階段建構問題，而非傳統的「先產生文字敘述、再補足環境」的生成流程。其核心目標是同時滿足兩項原則：**來源意圖（Source Intent）保存**與**跨工件一致性（Cross-Artifact Consistency）**。

##### 1. 問題形式化與任務束結構

論文將一個終端機任務定義為五元組：

\[
T=(I, E, S, V, M)
\]

其中：

- \(I\) 為 Instruction（指令）：描述使用者目標與期望行為；
- \(E\) 為 Environment Specification（環境規格）：包含容器、相依套件、檔案、服務等初始狀態；
- \(S\) 為 Reference Solution（參考解答）：可執行的解題軌跡或腳本；
- \(V\) 為 Executable Verifier（可執行驗證器）：在執行後檢查最終狀態是否正確；
- \(M\) 為 Runtime Metadata（執行期後設資料）：記錄建構與驗證過程的輔助資訊。

任務被接受的條件為：

\[
A(T)=B(E)\land \neg\nu_V(e_0)\land (e_T\neq \bot)\land \nu_V(e_T)
\]

這表示：環境必須能成功建構（\(B(E)\)）、初始狀態必須是非平凡的（\(\neg\nu_V(e_0)\)）、參考解答必須能成功執行（\(e_T\neq\bot\)）、且最終狀態必須通過驗證器（\(\nu_V(e_T)\)）。這個形式化強調終端機任務不是獨立的文字工件，而是**緊密耦合的可執行系統**。

##### 2. 資訊來源取得與技能理解

FACET 的輸入是大量異質的 Agent Skills（代理技能），來源包括 OpenClaw、ClawHub 與 GitHub 等公開儲存庫。處理流程分為四階段：

1. **收集與過濾**：移除包含不安全指令、需要私有資源、或無法重現的技能記錄；
2. **技能理解（Skill Understanding）**：將每個技能正規化為結構化記錄，包含描述、所需工具、輸入輸出、程序步驟與來源出處；
3. **情境抽取（Scenario Extraction）**：由抽取代理為每個技能推論可能的使用情境、初始狀態與目標狀態；
4. **情境–技能儲存庫建構**：將相似情境聚類，形成候選對 \(p_c=(c, X_c)\)，再經由模型評審（Judge）判斷該情境與技能組合是否相關、互補、無冗餘且可執行，最終保留合格的情境–技能對集合 \(P\)。

這個階段的關鍵在於：FACET 不直接把單一技能當作孤立模板，而是先重建「技能之間的關聯情境」，從而保留原始來源中的相依關係（Dependencies）、狀態轉換（State Transitions）與程序性約束（Procedural Constraints）。

##### 3. 情境重建與參考建構

對於每個情境–技能對 \(p_c\)，FACET 不直接生成最終任務，而是先進行**代理式情境重建（Agentic Scenario Reconstruction）**。該階段將來源技能還原為一個資訊豐富的組合情境，並從五個互補維度描述：

- **Skill Analysis（技能分析）**：識別每個技能的能力、工具、輸入輸出契約（Input–Output Contracts）、前置條件與可觀察效應；
- **Scenario Exploration（情境探索）**：提出具體的應用場景，使選定技能能共同服務於同一使用者目標；
- **Association and Fitting（關聯與組裝）**：決定技能之間的資料流與執行順序；
- **Workflow Planning（流程規劃）**：建立長期工作流程（Long-Horizon Workflows）的步驟順序；
- **Constraint Encoding（約束編碼）**：捕捉中間狀態、環境假設與程序性限制。

接著，這五維表示 \(D_c\) 被轉換為完整自然語言描述 \(C_c\)，再進一步產生對齊的參考工件：

\[
p_c \xrightarrow{\text{agentic reconstruction}} D_c \xrightarrow{\text{scenario synthesis}} C_c \xrightarrow{\text{reference building}} (R_S, R_I)
\]

其中 \(R_S\) 為解答參考，\(R_I\) 為指令參考。這種「先重建、後生成」的設計避免了過早壓縮來源資訊，使最終任務能保留原始技能中的複雜結構。

##### 4. 環境實現與共享基礎

在產生最終工件之前，FACET 先**建構並修復執行環境**。具體而言：

- 根據 \(E\) 初始化 Container State（容器狀態）\(e_0=\text{Init}(E)\)；
- 安裝相依套件、建立檔案與目錄、設定服務、匯入資料；
- 在環境建構失敗時進行診斷與修復，直到 \(B(E)\) 成立。

這個「已實現的容器狀態」被暴露為**共享基礎（Shared Grounding）**：後續的 Instruction（指令）、Reference Solution（參考解答）與 Executable Verifier（可執行驗證器）都針對同一組真實檔案、Schema、服務與執行期狀態生成。這是 FACET 與傳統 Multi-Stage Synthesis（多階段合成）的根本差異——後者往往僅透過文字規格傳遞資訊，容易導致指令引用不存在的檔案、解答假設錯誤的相依版本、或驗證器檢查無法達成的狀態。

##### 5. 基於執行的驗證與針對性修復

最後，FACET 進行 Execution-Based Validation（基於執行的驗證）：

1. 檢查環境是否成功建構；
2. 檢查初始狀態是否非平凡（驗證器不應在初始狀態就通過）；
3. 執行 Reference Solution（參考解答），確認不會失敗；
4. 在最終狀態執行 Executable Verifier（可執行驗證器），確認是否通過。

若某一工件失敗，FACET 進行 Targeted Repair（針對性修復）：只修改失效的特定工件（例如僅修復驗證器或僅調整環境），而保留已經有效的部分。這種精細化修復避免了「一旦出錯就全部重產」所造成的計算浪費，也減少了有效資訊在反覆生成中被稀釋的風險。

#### 實驗數據解讀

論文在 Terminal-Bench 2.1（Terminal-Bench 2.1）上進行評估，並透過 Fine-Tuning（微調）多個尺度的語言模型（Language Models）來驗證所生成資料的監督效果。雖然完整數據表格未在提供的片段中出現，但從摘要與引言可歸納出以下實驗發現與詮釋：

##### 1. 多尺度模型一致提升

FACET 產生的成功軌跡作為可執行監督（Executable Supervision），在多個模型尺度上進行 Fine-Tuning（微調）後，於 Terminal-Bench 2.1 上均獲得穩定改善。這顯示：

- 生成的任務具有足夠的**多樣性與難度分佈**，能覆蓋不同能力層級的模型；
- 成功軌跡並非「捷徑式」的淺層解答，而是包含真實的長期工作流程（Long-Horizon Workflows）與狀態轉換（State Transitions），因此對大、小模型都有訓練價值；
- 資料效率（Data Efficiency）高：相較於僅仰賴文字敘述或簡單技能模板生成的資料，FACET 能以較少的可執行樣本達到可觀的性能提升。

##### 2. 任務有效性與解答–驗證器對齊

論文透過對比不同生成方案，強調 Environment-Grounded Construction（基於環境的建構）對兩項指標的影響：

- **Task Validity（任務有效性）**：即任務束 \(T\) 滿足 \(A(T)\) 的比例。FACET 由於先實現環境再生成工件，顯著降低了「環境建構失敗」、「解答無法執行」、「驗證器過嚴或過鬆」等失效模式。
- **Solution-Verifier Alignment（解答與驗證器對齊）**：即 Reference Solution（參考解答）達成的最終狀態，確實能被 Executable Verifier（可執行驗證器）認定為正確。共享容器狀態（Container State）作為 Shared Grounding（共享基礎），使解答與驗證器針對同一組真實檔案與狀態進行定義，從而減少語義漂移。

##### 3. 密集可執行檢查的價值

FACET 強調產生「具有密集可執行檢查」的複雜終端機任務。這意味著每個任務不僅有單一最終檢查點，還可能包含多個中間狀態驗證。這類密集檢查對於訓練終端機代理（Terminal Agents）特別重要，因為代理必須學會：

- 正確操作命令列工具（Command-Line Tools）；
- 處理相依關係（Dependencies）與環境變化；
- 從執行失敗（Execution Failures）中恢復；
- 遵循程序性約束（Procedural Constraints）。

##### 4. 替代生成方案的分析意涵

論文比較了數種變體生成策略，結果支持以下設計選擇：

- **直接將技能翻譯為任務描述**會遺失跨技能相依與中間狀態，導致任務過於淺層；
- **先產生文字工件再補環境**容易出現跨工件不一致，降低 Task Validity（任務有效性）；
- **無針對性修復的全量重產**會浪費計算並破壞已對齊的工件；
- **以容器狀態為共享基礎**是確保 Solution-Verifier Alignment（解答與驗證器對齊）的關鍵。

#### 與現有研究的比較

##### 1. 既有合成終端機資料流程的侷限

近年來，Synthetic Terminal-Data Pipelines（合成終端機資料流程）已成為擴展終端機代理訓練資料的重要方向。相關工作依賴：

- Domain Specifications（領域規格）與 Skill Taxonomies（技能分類法）；
- Reusable Repositories（可重複使用儲存庫）；
- Terminal Recordings（終端機錄製記錄）；
- 社群問答資料；
- Procedurally Generated Task Signatures（程序化生成的任務特徵）。

這些方法確實能提升資料量與多樣性，但普遍存在兩個問題：

1. **資訊壓縮**：多階段生成會逐步丟失原始來源中的目標、相依關係、狀態轉換與程序性約束；
2. **工件漂移**：Instruction（指令）、Initialized Environment（初始化環境）、Reference Solution（參考解答）與 Executable Verifier（可執行驗證器）各自獨立生成，容易基於不一致的假設。

##### 2. Harbor Framework 的任務束觀點

Harbor Framework（Harbor Framework）已指出終端機任務是一個緊密耦合的工件束，但主要提供概念框架，未必強制要求所有工件都基於同一已實現的執行狀態。FACET 則進一步將此觀點操作化：它把 Container State（容器狀態）作為 Shared Grounding（共享基礎），使 Harbor 所定義的任務束真正具備可執行性與內部一致性。

##### 3. FACET 的改進

相較於既有研究，FACET 的主要貢獻在於：

| 面向 | 既有方法 | FACET |
|---|---|---|
| 技能使用方式 | 將技能視為孤立模板 | 透過 Agentic Scenario Reconstruction 重建技能間的組合情境 |
| 環境建構時機 | 通常在文字工件生成後補建 | 在產生最終工件前先實現並修復環境 |
| 跨工件一致性 | 仰賴文字規格傳遞 | 以 Container State（容器狀態）作為 Shared Grounding（共享基礎） |
| 修復機制 | 常採全量重產 | 採用 Targeted Repair（針對性修復），保留已有效工件 |
| 監督品質 | 數量多但可能不一致 | 強調 Task Validity（任務有效性）與 Solution-Verifier Alignment（解答與驗證器對齊） |

##### 4. 限制與潛在風險

儘管 FACET 在概念與實驗上均有顯著進展，仍存在以下限制：

- **來源品質依賴**：若原始技能記錄本身不完整、過時或含有隱含假設，情境重建與修復可能無法完全補救；
- **評審模型誤差**：情境–技能儲存庫的篩選仰賴模型評審（Judge），其誤判會直接影響後續所有階段；
- **計算成本**：反覆建構容器、執行解答與驗證器、進行 Targeted Repair（針對性修復）需要大量計算資源；
- **覆蓋範圍**：目前主要基於公開技能儲存庫，對於需要私有 API、特定硬體或長期執行服務的任務覆蓋有限；
- **長期工作流程挑戰**：雖然 FACET 能處理 Long-Horizon Workflows（長期工作流程），但極長或需要多容器協調的任務可能超出單一容器狀態的表達能力。

#### 可重現性評估

可重現性（Reproducibility）是終端機任務合成研究的核心挑戰之一，因為任務有效性高度依賴精確的環境狀態。FACET 的設計在理論上有利於重現，但實際可重現性取決於作者是否釋出以下關鍵資源：

##### 1. 已釋出或可利用的資源

- **技能來源**：OpenClaw、ClawHub 與 GitHub 為公開儲存庫，原則上可重新收集；
- **評估基準**：Terminal-Bench 2.1（Terminal-Bench 2.1）為公開基準，可用於驗證 Fine-Tuning（微調）效果；
- **容器技術**：採用 Container State（容器狀態）作為 Shared Grounding（共享基礎），若使用 Docker 等標準容器格式，環境再現性較高。

##### 2. 仍需釋出以確保重現的工件

- **71K 有效技能集合與結構化記錄**：雖然來源公開，但過濾、正規化與去重流程需要詳細說明；
- **情境–技能儲存庫 \(P\)**：包含候選對與 Judge 決策，是重建階段的關鍵輸入；
- **Agentic Scenario Reconstruction 的提示詞與模型設定**：五維表示 \(D_c\) 的具體模組與轉換規則；
- **環境建構與修復腳本**：包括相依安裝、服務啟動、錯誤診斷與 Targeted Repair（針對性修復）邏輯；
- **生成的任務束 \(T\)**：包含 Instruction（指令）、Environment Specification（環境規格）、Reference Solution（參考解答）、Executable Verifier（可執行驗證器）與 Runtime Metadata（執行期後設資料）；
- **Fine-Tuning（微調）所用的成功軌跡與模型權重**：以便驗證 Post-Training（後訓練）效果。

##### 3. 可重現性評級

- **方法層面**：由於 FACET 明確定義了任務束結構與接受準則 \(A(T)\)，並以容器狀態為中心進行驗證，方法本身具有高度可重現潛力；
- **實作層面**：若作者釋出完整程式碼、容器映像檔與生成任務，可重現性為**高**；若僅釋出論文與部分提示詞，則為**中等**，因為細節（如 Judge 提示、修復策略）難以完全復原；
- **資料層面**：由於涉及 71K 技能與大量模型生成內容，若未釋出中間資料，其他研究者難以完全複製相同分佈。

建議作者遵循「程式碼、資料、模型權重、容器映像檔」四位一體的釋出策略，以最大化研究影響力與可驗證性。

#### 未來研究方向

FACET 為可擴展的終端機任務合成奠定了重要基礎，但仍有多個值得延伸的方向：

##### 1. 強化修復策略

目前的 Targeted Repair（針對性修復）主要依賴模型評審與啟發式規則。未來可引入強化學習（Reinforcement Learning）或神經符號修復器，讓系統從過往修復經驗中學習，進一步提升修復成功率並降低計算成本。

##### 2. 多代理協作的情境重建

FACET 已使用單一抽取代理與評審模型。未來可探索多代理系統（Multi-Agent Systems），讓不同代理分別負責技能分析、情境探索、相依檢查與衝突解決，從而處理更複雜的跨領域組合。

##### 3. 動態與長期執行環境

目前 FACET 以單一 Container State（容器狀態）為主。未來可擴展至需要多容器、網路服務、資料庫或長時間執行程序的任務，並研究如何在此類動態環境中維持 Shared Grounding（共享基礎）。

##### 4. 難度與課程控制

FACET 產生的任務難度由來源技能與情境組合決定。未來可加入主動式難度調控與課程學習（Curriculum Learning）機制，根據代理當前能力動態生成適當難度的任務，提升訓練效率。

##### 5. 與後訓練範式深度整合

FACET 的成功軌跡可作為 Executable Supervision（可執行監督）。未來可進一步將其與 RLHF、DPO、Process Reward Models 等 Post-Training（後訓練）方法結合，利用執行軌跡中的中間狀態作為細粒度獎勵訊號。

##### 6. 開放評估工具與基準擴展

建議建構標準化的終端機任務合成評估工具，統一測量 Task Validity（任務有效性）、Solution-Verifier Alignment（解答與驗證器對齊）、資訊保存度與資料效率，並將 Terminal-Bench（Terminal-Bench）等基準擴展至更多任務家族與真實應用場景。

##### 7. 人機協作品質保證

儘管自動化合成能大規模產生資料，但對於高風險或高度專業的終端機任務，仍可引入 Human-in-the-Loop（人機協作）機制，讓領域專家審查情境重建結果與驗證器設計，以確保來源意圖（Source Intent）不被扭曲。

總結而言，FACET 透過「來源意圖保存」與「共享可執行狀態基礎」兩大設計原則，為終端機任務合成提供了一個更為嚴謹與可擴展的框架。未來研究可在修復自動化、多代理重建、動態環境與後訓練整合等方向持續推進，進一步釋放可執行監督（Executable Supervision）在訓練通用終端機代理（Terminal Agents）上的潛力。

## 論文問答

**Q1：什麼是終端機任務合成，為何可執行監督對訓練終端機代理如此重要？**

A：終端機任務合成是指自動產生一組緊密耦合的工件，包括使用者指令、初始化環境、參考解答與可執行驗證器，以構成一個可在真實終端機中執行與評估的完整任務。與僅產生文字或程式碼的靜態資料不同，這類任務要求代理必須與不斷變化的可執行狀態互動，例如操作檔案、安裝相依套件、呼叫命令列工具並從執行失敗中恢復。因此，可執行監督能讓語言模型在真實的狀態轉換中學習，而不只是模仿表面合理的文字輸出，這對發展長期工作流程與代理能力至關重要。

**Q2：現有的合成終端機資料流程為何無法保證高品質任務？**

A：現有方法雖然能從領域規格、技能分類法、可重複使用儲存庫、終端機錄製記錄或社群問答等多元來源大規模產生任務，但來源數量與多樣性的增加並不等同於任務品質的提升。由於終端機任務的各個工件高度相依，只要指令、環境、解答或驗證器之間出現不一致，整個任務就可能變得無法解決或被錯誤評估。此外，單純透過文字規格在生成階段之間傳遞資訊，無法確保所有工件都奠基於同一個已實現的執行狀態，因而容易產生參照未實現檔案或測試不可達狀態的問題。

**Q3：多階段合成過程中，來源意圖與任務工件為何容易流失或漂移？**

A：在多階段合成中，豐富的原始素材所包含的能力、相依關係、中間狀態、輸入輸出契約與程序性約束，會在連續的生成階段被逐步壓縮成簡化的任務描述，導致資訊保存不足。同時，各個工件在獨立生成時可能基於不同的假設，例如指令提到某個檔案但環境中並未建立，或解答假設了與驗證器不同的資料綱要。這種跨工件一致性缺失會使任務雖然在文字上看似合理，卻在實際執行時無法完成或無法被正確驗證。

**Q4：FACET 的核心工作流程包含哪些主要階段？**

A：FACET 首先從公開的技能套件中收集並過濾代理技能，將每個技能正規化為包含描述、所需工具、輸入輸出、程序步驟與來源出處的結構化記錄。接著，它進行情境重建，從相關技能中恢復連貫的使用者情境、跨技能相依關係、中間狀態與解答工作流程，並轉換為五個互補維度的情境表示與自然語言描述。最後，FACET 在產生最終任務工件之前先建構並修復執行環境，使容器狀態成為指令、解答與驗證器共享的基礎，並透過基於執行的驗證與針對性修復來修正特定工件的失敗。

**Q5：什麼是「代理式情境重建」，為何 FACET 要將其設計為五個互補維度？**

A：代理式情境重建是指 FACET 不直接將採樣到的技能翻譯成任務描述，而是先透過多個模組逐步恢復技能背後的完整應用情境，包括技能分析、情境探索、關聯與流程整合等。設計成五個互補維度是為了避免在生成早期就將豐富的來源資訊壓縮成淺薄描述，從而保留原始素材中的目標、相依關係、狀態轉換與程序性約束。這種做法能產生資訊密集且結構完整的複合情境，使後續產生的參考解答與指令更能反映來源意圖，而非僅使用每個技能最表面的能力。

**Q6：FACET 如何透過「基於可執行狀態的建構」確保跨工件一致性？**

A：FACET 在產生指令、解答與驗證器之前，會先將環境規格具體化為可執行的容器狀態，並把這個已實現的狀態暴露為共享基礎介面。這使得所有工件都能針對相同的檔案、綱要、服務、相依套件與執行時狀態來生成，從根本上降低了解答與驗證器之間的對齊誤差。相較於僅傳遞文字規格的傳統做法，這種環境導向的建構範式將終端機任務合成從獨立生成合理工件，轉變為建構一個整體一致且可執行的任務。

**Q7：FACET 的實驗使用了什麼基準測試與模型規模，主要結果為何？**

A：論文使用 Terminal-Bench 2.1 作為主要評估基準，並在多個模型規模上進行微調實驗。結果顯示，無論模型大小為何，使用 FACET 產生的任務資料進行微調都能一致地提升終端機任務表現。這說明 FACET 所產生的複雜終端機任務與密集可執行檢查，確實能提供資料效率高且有效的監督訊號。

**Q8：消融研究與替代生成方案的分析揭示了哪些關鍵設計原則？**

A：論文比較了不同的生成設計，結果支持「基於環境的建構」對於任務有效性與解答—驗證器對齊的重要性。相較於直接從技能產生任務描述或在無共享執行狀態下獨立生成各工件，FACET 先實現環境再生成工件的做法顯著減少了無效任務與驗證失配。此外，執行導向的驗證與針對性修復能只重新生成失敗的工件，避免不必要地捨棄已經正確的元件，進一步提升合成效率與資料品質。

**Q9：FACET 產生的成功軌跡在監督訊號方面具有什麼特性？**

A：FACET 產生的任務包含大量可執行檢查，因此從這些任務中收集到的成功軌跡能夠提供密集且可驗證的監督訊號。由於每個步驟都對應到真實的狀態轉換與驗證器回饋，模型可以從中學習正確的工具使用順序、錯誤恢復策略與長期工作流程規劃。實驗結果也顯示，這些軌跡在後訓練階段具有資料效率高的優勢，即使資料量有限也能帶來穩定的性能提升。

**Q10：FACET 產生的資料可應用於哪些實際場景？**

A：FACET 產生的可執行任務與軌跡可直接用於後訓練終端機代理，特別是在需要操作檔案系統、安裝相依套件、執行命令列工具與完成長期工作流程的場景。這些資料也適用於自動化軟體開發、DevOps 維運、雲端環境設定、資料處理管線建置等需要真實執行回饋的領域。由於任務具備可執行驗證器，它們不僅能作為訓練資料，也能作為評估代理能力的標準化測試案例。

**Q11：在產品化或部署 FACET 生成的任務時，需要考慮哪些因素？**

A：首先必須確保所有技能與相依資源都是公開且安全的，論文已過濾掉包含不安全指令、需要私有網站存取或依賴非公開資源的技能。其次，容器環境的可重現性與建構穩定性至關重要，因為任何環境建構失敗都會直接導致任務無效。此外，驗證器的設計需要仔細審查，以避免過度寬鬆或過度嚴格的檢查，並確保驗證結果與參考解答及使用者目標一致。

**Q12：FACET 對終端機代理與可執行任務合成領域可能帶來什麼影響？**

A：FACET 確立了「保存來源意圖」與「共享可執行狀態基礎」作為可擴展終端機任務合成的兩大核心原則。它將研究焦點從單純擴增來源多樣性，轉移到如何維持任務工件之間的一致性與可執行性。這種典範轉移有助於產生更高品質的訓練與評估資料，進而推動終端機代理在真實世界長期工作流程中的可靠性與自主性。

**Q13：FACET 有哪些已承認的限制？**

A：FACET 的品質在很大程度上取決於輸入技能套件的品質與覆蓋範圍，若原始技能描述不完整或過時，重建後的情境也可能出現偏差。雖然有模型評判器篩選情境—技能配對，但它仍可能接受某些在理論上合理、實際上卻難以執行的工作流程。此外，針對性修復雖然能修正許多工件層級的失敗，但並不保證能修復所有複雜的環境或相依問題，且目前方法主要聚焦於終端機環境。

**Q14：FACET 在哪些情況下可能產生無效或錯誤評估的任務？**

A：當環境規格無法正確建構時，例如缺少特定版本的相依套件或作業系統層級的差異，任務可能在初始化階段就失敗。若驗證器測試的是參考解答無法達到的狀態，則會出現解答與驗證器不對齊的問題。另外，若指令描述過於模糊或與實際環境狀態不符，代理可能執行出與預期不同的工作流程，卻仍無法通過驗證，導致錯誤評估。

**Q15：未來研究可以從哪些方向延伸 FACET 的框架？**

A：未來可以將 FACET 的環境導向建構原則擴展到圖形使用者介面或網頁代理，讓共享可執行狀態的概念應用於更廣泛的互動環境。另一方面，可以結合線上執行回饋與更強大的形式化驗證或定理證明技術，以進一步提升修復能力與任務正確性。此外，探索開放式任務生成與動態情境演化，也有助於產生更接近真實世界、需要持續適應的代理監督資料。

## 實務應用指南

### 適用場景

1. **大規模終端機代理訓練資料生成**  
   當團隊需要為 Terminal-Bench 等基準測試或內部代理訓練產生大量可執行、可驗證的終端機任務時，FACET 可將分散的代理技能重建成連貫場景，並確保指令、參考解答與可執行驗證器三者對齊。

2. **企業內部開發者工具與 DevOps 自動化訓練**  
   適用於需要讓代理學習操作命令列工具、安裝相依關係、處理檔案系統與長期工作流程的場景，例如自動化部署腳本生成、容器環境設定、CI/CD 故障排除等。

3. **可執行監督資料合成**  
   在後訓練階段需要「可執行監督」來微調語言模型時，FACET 能產出帶有密集執行檢查的任務，並從成功軌跡中收集資料效率高的監督訊號。

4. **技能庫與可重複使用儲存庫的再利用**  
   當組織已累積大量 OpenClaw、ClawHub 或 GitHub 上的技能套件，卻難以將其轉為結構化訓練任務時，FACET 可透過場景重建與環境修復，把異質技能轉換為一致的可執行任務。

5. **代理能力評估與基準測試建置**  
   適合研究團隊或評測平台用來建構複雜終端機任務，確保任務具備非平凡的初始狀態、可執行的參考解答，以及能正確評估最終狀態的可執行驗證器。

### 實作前置條件

**資料條件**

- 可取得公開或內部技能套件，例如 OpenClaw、ClawHub、GitHub 上的命令列技能記錄。
- 每個技能至少需包含描述、所需工具、輸入輸出、程序步驟與來源出處，以便進行結構化正規化。
- 需具備可執行的容器化環境規格，例如 Dockerfile、初始化腳本、相依套件清單等。

**運算條件**

- 足夠的容器執行資源以反覆建構與修復環境，因為 FACET 的核心在於「基於環境的建構」，需要多次執行 Init(E)、Run(S, e₀) 與驗證器 ν_V(e_T)。
- 可呼叫語言模型的 API 或本地推論資源，用於場景重建、自然語言描述生成、參考指令與解答生成，以及模型評審（judge）。
- 建議具備平行化執行與快取機制，以處理數萬筆技能的場景提取與驗證流程。

**技能與流程條件**

- 團隊需熟悉終端機任務合成流程，包含環境初始化、參考解答執行、可執行驗證器設計。
- 需具備判斷技能是否安全、可執行、無重複且不依賴非公開資源的能力。
- 建議已有基準測試或評估框架（如 Terminal-Bench）作為最終任務有效性的驗證標準。

### 實作步驟建議

1. **技能收集與清理**  
   從 OpenClaw、ClawHub、GitHub 等來源收集技能套件，移除包含不安全指令、需要私有網站存取、依賴非公開資源，以及不可讀、無法操作或重複的記錄。將保留技能正規化為結構化記錄。

2. **場景提取與技能配對**  
   對每個技能使用提取代理識別可能應用場景、使用者目標、初始狀態與期望最終狀態。將場景假設嵌入向量空間，檢索相似假設以找出可組合的相關技能群組，並由模型評審篩選出相關、互補、無冗餘且可執行的場景–技能配對。

3. **代理式場景重建**  
   針對每個通過篩選的場景–技能配對，進行五維度重建：技能分析、場景探索、技能關聯與流程設計、中間狀態與程序性約束確認，最後產出完整的自然語言場景描述 C 與對齊的參考指令 R_I、參考解答 R_S。

4. **環境實現與修復**  
   根據場景描述建構容器化環境 E，執行初始化 Init(E) 得到 e₀，並驗證環境是否成功建構 B(E)。接著執行參考解答 Run(S, e₀) 得到 e_T，確認不為失敗 ⊥。若環境或解答執行失敗，則針對性地修復，而非重新生成已有效的工件。

5. **可執行驗證器生成與對齊**  
   在已實現的容器狀態上生成可執行驗證器 V，確保驗證器測試的是參考解答能夠達成的真實最終狀態，並滿足 ν_V(e₀) 為假、ν_V(e_T) 為真的接受條件。

6. **執行導向驗證與迭代修復**  
   對每個任務執行完整驗證：B(E) ∧ ¬ν_V(e₀) ∧ (e_T ≠ ⊥) ∧ ν_V(e_T)。針對特定工件層級的失敗（如指令引用不存在的檔案、解答假設錯誤的相依關係、驗證器測試不可達狀態）進行針對性修復，保留已有效組件。

7. **成功軌跡收集與微調**  
   從通過驗證的任務中收集成功執行軌跡，作為可執行監督資料。使用這些資料對不同規模的語言模型進行微調，並在 Terminal-Bench 2.1 等基準測試上評估效能提升。

8. **產品化部署**  
   將驗證過的任務 bundle T = (I, E, S, V, M) 納入訓練資料管線或評測平台，建立版本控制、持續驗證與監控機制，確保隨著基礎環境或技能庫更新，任務仍保持有效。

### 潛在風險與注意事項

- **來源意圖流失**  
  若過早將技能壓縮成簡化任務描述，會遺失跨技能相依關係、中間狀態與程序性約束。應透過 FACET 的代理式場景重建階段保留五維度資訊，避免只使用技能最表層能力。

- **跨工件不一致**  
  指令、環境、參考解答與驗證器若各自獨立生成，容易出現指令引用不存在檔案、解答假設錯誤 schema、驗證器測試無法達成狀態等問題。必須以「共享可執行狀態」為基礎生成所有工件。

- **環境建構失敗與不可重現**  
  相依套件版本、網路資源可用性或作業系統差異可能導致環境無法建構。建議將環境規格容器化、鎖定版本，並在隔離環境中重複執行 Init(E) 以確認可重現性。

- **驗證器過於寬鬆或嚴格**  
  驗證器若只檢查最終輸出文字，可能忽略狀態轉換；若檢查過多內部狀態，則可能拒絕正確但實作不同的解答。應讓驗證器在參考解答實際產生的容器狀態上設計，並驗證 ¬ν_V(e₀) 與 ν_V(e_T)。

- **安全與惡意技能**  
  技能來源可能包含不安全指令。收集階段必須嚴格過濾，並在隔離容器中執行所有環境建構與解答執行，避免對主機系統造成影響。

- **過度修復導致資料流失**  
  針對性修復應只修改失效工件，避免為了修復單一問題而重新生成整個任務，否則可能破壞原本已對齊的組件。

### 與其他技術的整合建議

- **與現有訓練框架整合**  
  可將 FACET 產生的任務 bundle 直接餵入 RLHF、DPO 或軌跡監督式微調流程，作為可執行監督資料來源。成功軌跡特別適合用於提升終端機代理的長期工作流程能力。

- **與容器編排平台整合**  
  將環境建構與驗證流程部署於 Kubernetes、Docker Swarm 或雲端容器服務上，以平行化處理大規模任務合成，並利用快照與快取加速重複修復。

- **與向量資料庫與檢索系統整合**  
  場景提取階段產生的場景假設可儲存於向量資料庫，支援基於語義相似度的技能檢索與組合推薦，提升場景–技能配對的品質與多樣性。

- **與評測基準整合**  
  將 FACET 任務匯入 Terminal-Bench 2.1 或自訂基準測試，作為模型能力評估資料集。由於任務已通過執行導向驗證，可減少基準測試中的無效題目。

- **與 MLOps / 資料品質監控整合**  
  建立自動化管線定期重新執行 B(E) 與 ν_V(e_T)，監控因外部相依更新而導致的任務失效，並觸發針對性修復或汰除。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於「為什麼終端機任務很難合成」這個直覺：一個任務不只是文字指令，還包含環境、解答與驗證器，任何一環出錯都會讓整題作廢。理解 FACET 的核心概念——先重建場景、再實現環境、最後生成工件——之後再回頭看公式與管線細節會更容易。

**AI 工程師**  
本論文提供了一個可落地的多階段管線，建議重點閱讀場景重建、環境修復與執行導向驗證的實作細節，並思考如何將其整合進現有的資料生成與微調基礎設施。特別注意「共享可執行狀態」如何解決你過去在生成指令–解答–測試對時遇到的不一致問題。

**研究人員**  
論文的核心貢獻在於提出「來源意圖保存」與「共享可執行狀態基礎」兩個原則，並以 Terminal-Bench 2.1 驗證其對任務有效性與解答–驗證器對齊的影響。建議深入分析替代生成方案的比較實驗，並思考這些原則能否推廣到其他需要環境互動的代理任務合成領域。

**產品經理**  
本技術適合需要大規模、可驗證終端機訓練資料的產品場景。閱讀時請關注適用場景、實作前置條件與潛在風險，評估導入成本時需同時考慮容器運算資源、技能庫品質與持續驗證機制，並將 FACET 定位為提升資料品質與模型後訓練效果的基礎建設。
