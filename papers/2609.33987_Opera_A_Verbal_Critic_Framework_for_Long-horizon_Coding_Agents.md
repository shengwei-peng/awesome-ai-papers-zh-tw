## 摘要翻譯

長程程式碼代理需要及時的修正，然而當回饋誤判進行中的工作或未能處理根本問題時，回饋可能無效甚至有害。現有的批評器著重於評估軌跡並產生回饋，但很少追蹤回饋交付後的情況。我們提出 Opera，一個語言式批評框架，將每次修正視為持續性備註，並追蹤至所診斷的問題獲得解決為止。Opera 透過週期性觸發與事件驅動觸發決定審查時機，使用類型化運算子診斷問題，在交付前對照可見證據審核回饋，並追蹤代理後續的行動，以區分表面順從與實際解決度。作為測試時批評器，Opera 在 Terminal-Bench 2.1、SWE-Bench Pro 子集與 DeepSWE v1.1 上，分別將四個策略模型的非批評代理解決率提升最多 12.4、15.0 與 8.9 個百分點，並在所有三個基準測試中於競爭性批評基線中達到最高的平均解決率，且當策略模型自我批評時亦能提升其表現。除推論外，Opera 引導的推演序列提供近似同策略的訓練資料：在這些推演序列上微調 Qwen3.5-9B 可在無批評器推論的情況下，將其在保留 SWE-Bench Pro 倉庫上的解決率提升 10.2 個百分點，與使用更強模型推演序列進行微調的效果相當，同時在切換執行框架時（即從 OpenHands 切換至 Terminus-2——後者會大幅降低效能——）仍能保持其表現。程式碼已開源於：https://github.com/dongyuanjushi/Opera。

### 核心貢獻（3～5點）
- 提出 Opera 語言式批評框架，將每次修正視為持續性備註，並追蹤至所診斷的問題獲得解決為止，藉由週期性觸發與事件驅動觸發決定審查時機，並以類型化運算子進行診斷。
- 設計回饋審核機制，在交付前對照可見證據審核回饋，並追蹤代理後續行動以區分表面順從與實際解決度。
- 在 Terminal-Bench 2.1、SWE-Bench Pro 子集與 DeepSWE v1.1 三項基準測試上，於四個策略模型中皆達到最高的平均解決率，並證明策略模型自我批評時亦能受益。
- 證明 Opera 引導的推演序列可作為近似同策略訓練資料，微調 Qwen3.5-9B 後在保留 SWE-Bench Pro 倉庫上提升 10.2 個百分點，效果與使用更強模型蒸餾相當，且在切換執行框架時仍具穩健性。

### 適合對象
從事長程程式碼代理、LLM 代理自我反思與回饋機制研究的學者與工程師；關注程式碼生成代理評測基準（Terminal-Bench、SWE-Bench Pro、DeepSWE）的實務研究者；以及希望將批評式回饋整合至代理執行框架（如 OpenHands、Terminus-2）的 AI 應用開發者。

## 深度分析

#### 方法論解析

Opera 的核心設計理念是將「批評」（criticism）重新定義為**持續性備註管理**（persistent note management），而非傳統的單次評分或一次性回饋生成。這種設計直接回應了長程程式碼代理（long-horizon coding agents）面臨的三個根本性挑戰。

**1. 混合審查排程（Hybrid Review Scheduling）**

傳統批評器面臨一個權衡困境：純週期性觸發（periodic triggers）反應過慢，代理可能在下次審查前重複失敗指令多次；純事件驅動觸發（event-driven triggers）雖反應迅速，但容易遺漏「靜默失敗」（silent failures），例如代理自信地編輯錯誤檔案而未觸發任何錯誤事件。

Opera 採用**雙軌觸發機制**：
- **固定間隔審查**：每 k 個回合（turns）進行一次例行審查
- **事件驅動審查**：針對五種特定事件立即觸發，包含 Idle（無進展）、Repeat（重複動作）、Error（動作或工具失敗）、Test（測試執行）、Submission（最終補丁提交）

此設計的關鍵洞見在於：審查頻率應與**問題可偵測性**匹配，而非僅與時間掛勾。當代理明顯卡住時，無需等待週期性審查；當代理看似順利執行時，仍需週期性檢查以捕捉靜默失敗。

**2. 運算子批評器（Operator Critic）與審核機制（Audit）**

針對「回饋是否正當」這個挑戰，Opera 引入**類型化運算子**（typed operators）來結構化診斷過程。每個診斷必須包含三個要素：
- **證據**（evidence）：指向執行軌跡（execution traces）中的具體片段
- **修正方向**（corrective direction）：建議的下一步動作
- **解決標準**（resolution criterion）：固定的判定條件，確保解決度（resolution）對照原始問題而非最新指引

這與 SWE-PRM 等僅生成自然語言回饋的方法形成對比。Opera 的運算子批評器將診斷形式化，使後續追蹤變得可驗證。

**審核機制**則在回饋送達代理前進行篩選，過濾掉基於不完整證據的誤判。這直接回應了 RuVerBench 所揭示的 LLM 評判器（LLM judges）雜訊問題——即使在驗證明確條件時，LLM 評判仍可能出錯。

**3. 遵循度與解決度的分離追蹤**

這是 Opera 最具原創性的設計。傳統批評器僅檢查代理是否「聽從」回饋，但 Opera 區分兩個獨立維度：
- **遵循度**（adherence）：代理是否嘗試了建議的動作
- **解決度**（resolution）：底層問題是否真正被解決

這種分離揭示了「表面順從」（mere compliance）的陷阱——代理可能執行建議動作但未觸及根本問題。發現備註（finding note）會持續追蹤每個問題直到證據支持其解決，然後關閉；若未解決，則進入「精化」（refine）階段，產生新的指引。

**4. 與代理的互動介面**

Opera 僅透過執行軌跡和自然語言回饋與代理互動，不修改代理權重或內部狀態。這種「外掛式」設計使其能無縫整合至現有執行框架（harness），如 OpenHands、Terminus-2、Mini-swe-agent。

#### 實驗數據解讀

**1. 基準測試覆蓋**

實驗在三個互補的基準測試上進行：
- **Terminal-Bench 2.1**（100 tasks，OpenHands）：涵蓋終端操作與系統層級任務
- **SWE-Bench Pro 子集**（89 tasks，Terminus-2）：聚焦倉庫層級程式碼修復
- **DeepSWE v1.1**（113 tasks，Mini-swe-agent）：軟體工程任務的另一變體

使用三種不同執行框架（harness）增加了實驗的生態效度，避免單一框架的偏誤。

**2. 核心效能提升**

Opera 在三個基準上分別帶來最高 **12.4、15.0、8.9 百分點**（percentage points）的解決率（resolve rate）提升，且在四種策略模型（policy models）上均呈現一致改善。圖表顯示：
- DeepSeek-V4-Flash 在 SWE-Bench Pro 上提升 +11.0 pp
- Qwen3.8-27B 在 Terminal-Bench 2.1 上提升 +4.1 pp
- Muse-glimmer-30B 在 DeepSWE v1.1 上提升 +8.9 pp

值得注意的是，Opera 在**策略模型自我批評**（policy critiques itself）的設定下仍能改善效能，這打破了「批評器必須比策略模型更強」的隱含假設。

**3. 基準線比較**

Opera 在所有三個基準上達成最高平均解決率，超越四個競爭性批評基準線。這些基準線涵蓋了不同的批評策略：週期性軌跡評審（SWE-PRM 類型）、基於規則的評分、簡單的自我反思等。Opera 的優勢來自於其混合觸發與持續追蹤機制，而非單純的更強 LLM。

**4. 訓練資料價值**

最具實務影響力的結果在於**訓練資料生成**：
- 以 Opera 引導的學生推演序列（rollouts）作為微調（fine-tuning）資料
- Qwen3.5-9B 在保留（held-out）SWE-Bench Pro 倉庫上提升 **+10.2 pp**
- **匹配從更強模型蒸餾（distillation）的效果**，但無需在推論時使用批評器

這項結果揭示了 Opera 引導的軌跡具有「近似同策略」（approximately on-policy）的特性——它包含學生自身的動作加上針對其錯誤的精準診斷，這正是傳統從強模型蒸餾所缺乏的。

**5. 跨執行框架的穩健性**

微調後的模型在從 OpenHands 切換至 Terminus-2 時**保留了效能**，而後者通常會顯著降低效能。這暗示 Opera 引導的訓練資料教會了模型更通用的修復策略，而非過度擬合特定執行框架的動作模式。

#### 與現有研究的比較

**1. 與反思類方法的關係**

Self-Refine、Reflexion、CRITIC 等早期方法奠定了迭代自我回饋的基礎，但它們將批評視為**單次事件**。Opera 將其延伸為**持續性狀態管理**，這是概念上的重要躍進。

**2. 與 SWE-PRM 的關鍵差異**

SWE-PRM 採用固定間隔審查並提供分類法引導的回饋，但缺乏：
- 事件驅動觸發
- 回饋送達前的審核
- 解決度的持續追蹤

Opera 的混合排程解決了 SWE-PRM 在快速失敗偵測上的不足，而審核機制則緩解了 LLM 評判雜訊問題。

**3. 與 Agentic Rubrics 的互補性**

Agentic Rubrics 為每個倉庫建構專屬評分標準，但 RuVerBench 揭示了 LLM 驗證此類標準時的雜訊。Opera 不依賴預建評分標準，而是從執行軌跡中動態推導證據，這在概念上更為穩健。

**4. 與測試時計算擴展方法的定位**

SWE-Search（蒙地卡羅樹搜尋）、S*（平行採樣與精化）等方法將額外推論計算分配給**探索與選擇**。Opera 則將計算分配給**診斷與修正**，這是互補而非競爭的維度。兩者結合可能產生更強的系統。

**5. 局限性**

- **計算成本**：每次審查需要額外的 LLM 呼叫，混合排程增加了總推論成本
- **運算子設計的覆蓋性**：類型化運算子是否能涵蓋所有失敗模式尚待驗證
- **解決標準的形式化**：對於複雜任務，固定解決標準本身可能難以定義
- **跨語言泛化**：實驗集中在 Python 倉庫，其他語言的表現未經測試

#### 可重現性評估

**1. 程式碼可用性**

論文明確聲明程式碼開源於 `https://github.com/dongyuanjushi/Opera`，這是積極的可重現性指標。然而，僅有程式碼並不足夠——批評框架的效果高度依賴提示工程（prompt engineering）與審查排程的具體參數。

**2. 資料集與基準**

三個基準測試（Terminal-Bench 2.1、SWE-Bench Pro、DeepSWE v1.1）均為公開基準，但 SWE-Bench Pro 子集的具體選取標準需要檢查。保留（held-out）SWE-Bench Pro 倉庫的劃分方式對訓練資料實驗的可重現性至關重要。

**3. 模型權重**

- 策略模型（Qwen、Muse、GPT、Claude、DeepSeek）均為公開或可透過 API 取得的模型
- Qwen3.5-9B 的微調權重未明確聲明是否釋出，這限制了訓練資料實驗的直接驗證
- 批評器模型本身可以是任意 LLM，這增加了靈活性但也增加了結果變異性

**4. 評估協議**

解決率（resolve rate）的計算方式需要明確——是基於測試通過率、代理自我報告，還是外部驗證？論文中未充分說明的細節可能影響結果的可比較性。

**5. 整體評估**

可重現性處於中等偏上水準。程式碼公開是良好起點，但完整的可重現性需要：精確的提示模板、審查間隔 k 的設定、所有隨機種子的報告、以及微調權重的釋出。

#### 未來研究方向

**1. 運算子理論的形式化**

目前的類型化運算子是啟發式設計的。未來可探索：
- 從失敗軌跡中**自動學習**運算子類型
- 建立運算子之間的**因果依賴圖**，使批評器能預測連鎖失敗
- 將運算子與形式化語意（如程式不變式）對接，提升解決標準的可驗證性

**2. 多批評器協作**

單一批評器可能存在盲點。可研究：
- **異質批評器整合**：結合規則型、神經型、符號型批評器
- **批評器辯論**：讓多個批評器對同一診斷進行辯論，提升穩健性
- **批評器路由**：根據任務類型動態選擇最適批評器

**3. 與測試時計算擴展的深度整合**

Opera 與 SWE-Search、S* 等方法在計算分配上是互補的。未來可探索：
- **樹搜尋中的節點批評**：在蒙地卡羅樹搜尋的每個節點應用 Opera 風格的持續追蹤
- **平行採樣的診斷融合**：當多條軌跡產生衝突時，使用 Opera 的審核機制選擇最可信的回饋

**4. 從批評到教學的演進**

Opera 引導的軌跡已展現訓練資料價值。未來可探索：
- **課程式批評**：隨著代理能力提升，逐漸增加批評的抽象層級
- **反事實批評**：不僅診斷「發生了什麼錯」，更推演「若代理採取不同動作會如何」
- **元學習批評**：讓批評器本身從多任務經驗中學習何時介入最有效

**5. 跨領域泛化**

Opera 目前專注於程式碼修復，但其持續性備註概念可泛化至：
- **長程對話代理**：追蹤對話中的未解決問題
- **機器人控制**：診斷並追蹤操作失敗
- **科學發現代理**：監督假設生成與實驗驗證的循環

**6. 理論分析**

目前缺乏對「批評介入時機最優策略」的理論分析。可探索：
- 在何種條件下，週期性與事件驅動觸發的組合最優
- 審核機制的誤拒率（false rejection rate）與延遲成本之間的權衡
- 持續性追蹤對長程任務複雜度的理論加速效果

**7. 人機協作批評**

最終，批評器的設計可融入人類專家知識：
- 允許人類在關鍵節點**接管批評**
- 從人類批評中**蒸餾**出自動化規則
- 建立**可解釋的批評日誌**，使代理決策對人類透明

## 論文問答

**Q1：Opera 主要解決什麼核心問題？**
A：Opera 針對的是長程程式碼代理（long-horizon coding agents）在執行複雜任務時缺乏及時且有效回饋的問題。這類代理在長時間執行中容易重複無效動作、冗餘探索，甚至在任務尚未真正完成時就回報完成。雖然引入批評器（critic）看似自然解法，但批評器必須在不完整證據下判斷未完成的工作，這使得「真正的錯誤」與「合理的中間步驟」之間界線模糊，因此需要更精緻的批評機制。

**Q2：現有的批評方法為什麼會失敗或甚至有害？**
A：現有方法如 Self-Refine、Reflexion、CRITIC、SWE-PRM 等雖然提供了回饋與反思的基礎，但它們通常只關注如何產生回饋，而忽略回饋「之後」發生了什麼事。具體而言有三個挑戰：①介入時機不當——純週期性回饋可能太遲，而純事件驅動則會忽略靜默失敗；②回饋可能誤判——看似合理的診斷可能誤解部分證據，反而打斷原本會成功的工作；③無法區分表面順從與真正解決——代理可能照做建議但底層問題依然存在。

**Q3：為什麼這個問題在實務上很重要？**
A：長程程式碼代理已被廣泛應用於倉庫層級任務（repository-level tasks），涵蓋程式碼探索、編輯與測試等環節。若批評器無法準確介入，不僅浪費額外的推論成本，還可能讓代理偏離正確方向，導致整體任務失敗率上升。在軟體工程自動化日益普及的今天，提升這類代理的可靠性與效率，對於實際部署與商業應用具有關鍵意義。

**Q4：Opera 的核心方法是什麼？**
A：Opera 的核心方法是將每一次修正視為一條「持續性備註」（persistent note），從問題被發現開始就一直追蹤，直到有證據顯示問題已解決。這個備註包含三個要素：診斷出的問題、當前指引，以及固定的解決標準。透過這樣的設計，批評器能在多輪審查中持續追蹤自己先前的回饋，並以原始問題（而非最新指引）作為解決與否的判斷依據。

**Q5：Opera 的關鍵創新點為何？**
A：Opera 的關鍵創新在於它把「批評」重新定位為一種「介入後管理」的工作，而不僅僅是單次回饋的生成。具體而言，它結合了週期性與事件驅動的混合審查排程（hybrid review scheduling），並透過運算子批評器（operator critic）將每個問題連結到證據、修正方向與解決標準，再以審核機制（audit）在交付前回饋前把關，最後以發現備註（finding note）分別追蹤遵循度（adherence）與解決度（resolution）。

**Q6：Opera 在設計上做了哪些重要取捨？**
A：Opera 選擇以純語言（verbal）方式與代理互動，僅透過執行軌跡（execution traces）與自然語言回饋溝通，因此無需修改代理權重，可無縫接入現有執行框架（harness）。此外，它刻意區分「遵循」與「解決」——代理可能表面上採納建議但未真正解決問題，這種區分讓批評器能更精準地決定何時關閉或精煉一條備註。另一個重要設計是允許批評器「保持沉默」，當沒有觸發條件或無新問題時不發出回饋，避免過度干擾。

**Q7：Opera 在哪些基準測試上進行評估？**
A：Opera 在三個程式碼代理基準測試上進行評估：Terminal-Bench 2.1（89 個任務，使用 Terminus-2 框架）、SWE-Bench Pro 的 100 個任務子集（使用 OpenHands 框架），以及 DeepSWE v1.1（113 個任務，使用 Mini-swe-agent 框架）。同時測試了四種不同的策略模型（policy models），涵蓋 Qwen、Muse、GPT、Claude、DeepSeek 等不同規模與家族，以驗證框架的泛用性。

**Q8：Opera 的主要實驗結果為何？**
A：在測試時批評（test-time critic）情境下，Opera 將非批評代理的解決率（resolve rate）在 Terminal-Bench 2.1、SWE-Bench Pro 子集與 DeepSWE v1.1 上分別提升最多 12.4、15.0 與 8.9 百分點（percentage points），並在三個基準上皆取得所有競爭批評基線中最高的平均解決率。值得注意的是，即使策略模型自我批評（self-critique），Opera 仍能帶來改善。在訓練方面，以 Opera 引導的推演序列微調 Qwen3.5-9B，在保留的 SWE-Bench Pro 倉庫上提升 10.2 百分點，表現媲美以更強模型蒸餾（distillation）的結果。

**Q9：Opera 有進行哪些消融實驗或深入分析？**
A：雖然摘要未完整列出所有消融細節，但從框架設計可推論關鍵消融面向包括：混合審查排程（僅週期 vs. 僅事件驅動 vs. 混合）、審核機制的必要性（有無 audit 對回饋品質的影響）、以及遵循度與解決度分離追蹤的價值。此外，實驗也展示了切換執行框架（從 OpenHands 換到 Terminus-2）時，Opera 仍能維持效能，而其他方法則會顯著退化，顯示其框架無關的穩健性。

**Q10：Opera 適合哪些實際應用場景？**
A：Opera 特別適合需要長時間、多步驟程式碼操作的場景，例如自動化 bug 修復、大規模程式碼重構、跨檔案功能開發，以及需要反覆測試與除錯的軟體工程任務。由於它以純語言介面運作且不需修改代理權重，企業可在不重新訓練內部模型的情況下，將 Opera 整合到現有的程式碼代理管線中，立即獲得回饋品質的提升。

**Q11：在產品化部署 Opera 時需要考量哪些因素？**
A：產品化時首先需考量額外的推論成本——Opera 引入了一個批評模型與審查機制，會增加每次任務的計算開支。其次是延遲問題，混合審查排程雖然有效，但事件驅動審查可能在關鍵時刻增加回應時間。此外，需評估批評模型本身的選擇（強模型帶來高品質但成本高，弱模型則需仰賴審核機制把關），以及如何在不同執行框架間無縫整合。

**Q12：Opera 對程式碼代理領域的影響為何？**
A：Opera 重新定義了「批評」在代理系統中的角色，從單次回饋轉為持續性介入管理，這個觀點對整個領域具有方法論上的啟發性。它同時展示了批評框架不僅能改善測試時表現，還能產生高品質的同策略訓練資料（on-policy training data），這對資源有限、無法取得強模型蒸餾資料的研究團隊尤其重要。這種「批評即資料」的概念可能會推動更多結合測試時與訓練時優化的研究。

**Q13：Opera 存在哪些已知的限制？**
A：Opera 的限制包括：①仍依賴 LLM 評判器（LLM judges）進行診斷與審核，而 LLM 評判器本身存在雜訊；②額外的批評模型帶來顯著的推論成本開銷；③對於需要極快速反應的場景，事件驅動審查可能仍不夠即時；④框架假設代理能透過自然語言回饋調整行為，但若代理本身理解力不足，再好的批評也無用。

**Q14：Opera 在哪些情況下可能會失敗？**
A：Opera 可能失敗的情境包括：當批評模型本身能力不足時，審核機制也難以完全把關，可能產生誤導性回饋；當代理執行的任務證據極度模糊或缺失時，運算子批評器可能無法正確診斷；當問題的本質需要領域專家知識（如特定框架的隱性慣例）時，通用批評模型可能無法察覺。此外，若代理反覆在「表面順從」與「真正解決」間遊走，發現備註可能會無限精煉而無法關閉。

**Q15：Opera 未來可能的研究方向為何？**
A：未來方向可能包括：①將持續性備註的概念擴展到非程式碼領域的長程代理任務；②研究更高效的審核機制，例如結合符號驗證或輕量分類器以降低 LLM 評判成本；③探索批評器與代理的聯合訓練，讓代理能內化批評訊號；④將 Opera 與測試時擴展（test-time scaling）方法如樹搜尋、平行採樣結合；⑤研究如何讓批評器從失敗案例中持續學習，提升診斷品質。

## 實務應用指南

### 適用場景

1. **企業內部程式碼維護代理**：在大型 monorepo 中，代理需要長時間探索、修改並驗證多個檔案。Opera 的持續性備註機制能避免代理在錯誤的檔案上反覆編輯，特別適合 legacy 系統重構、跨模組 bug 修復等需要數十至數百步操作的任務。

2. **CI/CD 自動化修復流程**：將 Opera 整合進 CI pipeline，當測試失敗時自動啟動長程代理進行修復。事件驅動觸發（測試失敗、重複動作）能即時介入，週期性觸發則防止代理陷入無聲失敗（例如修改了錯誤的函式但未觸發錯誤）。

3. **開源專案的 issue triage 與初步修復**：對於 SWE-Bench 類型的真實 GitHub issue，代理需要理解 issue 描述、定位程式碼、撰寫 patch 並通過測試。Opera 的運算子批評器（Search、View、Edit、Test、Submit）能針對每個階段提供精準回饋。

4. **程式教學與程式碼審查輔助**：將 Opera 作為「教練」角色，引導學生或初級工程師的程式碼生成過程。審核機制能過濾掉誤導性建議，遵循度與解決度分離追蹤則能區分「照做但沒解決」與「真正修復」。

5. **模型微調的資料生成管線**：利用 Opera 引導的 rollouts 產生近似同策略（on-policy）的訓練資料，比從更強模型蒸餾更貼近學生模型自身的行為分布，適合用於持續改進小型開源模型（如 Qwen3.5-9B）。

### 實作前置條件

**資料需求**
- 至少一個程式碼代理執行框架（OpenHands、Terminus-2 或 Mini-swe-agent）的部署環境
- 評估基準的測試案例（Terminal-Bench 2.1、SWE-Bench Pro 子集、DeepSWE v1.1，或自有的倉庫層級任務集）
- 用於微調的「保留測試集」——必須與訓練任務的倉庫完全分離，避免資料洩漏

**運算資源**
- 推論階段：需要同時運行策略模型與批評模型。論文中四種策略模型（Qwen、Muse、GPT、Claude、DeepSeek 系列）皆可搭配，建議使用 API 服務以降低部署成本
- 微調階段：Qwen3.5-9B 等 9B 級別模型在單機多 GPU（如 4×A100/H100）即可完成 LoRA 或全參數微調
- 批評模型可選用與策略模型相同或更強的模型；論文中批評模型可與策略模型相同（self-critique）仍有效

**技能門檻**
- 熟悉 LLM agent 框架的執行軌跡（execution trace）格式
- 具備 prompt engineering 經驗，特別是設計結構化輸出（typed operators、resolution criteria）
- 若要重現微調實驗，需了解 SFT/DPO 等微調流程與評估 harness 切換的注意事項

### 實作步驟建議

**步驟一：建立執行軌跡收集管線**
整合 OpenHands、Terminus-2 或 Mini-swe-agent，記錄每個 turn 的動作、工具輸出、檔案變更與測試結果。Opera 僅透過執行軌跡與自然語言回饋與代理互動，無需修改代理權重。

**步驟二：實作混合審查排程器**
- 設定固定週期 `k`（論文中未明確給出單一最佳值，建議從 5–10 turns 開始調參）
- 實作五種事件觸發：Idle（無進展）、Repeat（重複動作）、Error（工具失敗）、Test（測試執行）、Submission（最終提交）
- 確保排程器支援「保持沉默」選項——無觸發時不發送回饋

**步驟三：部署運算子批評器**
設計 prompt 使批評器輸出結構化診斷，包含：
- 問題描述（claim）
- 可見證據（visible evidence）
- 修正方向（corrective direction）
- 解決標準（resolution criterion）
- 對應的 typed operator（Search / View / Edit / Test / Submit）

**步驟四：加入審核機制**
在批評器輸出後、實際送達代理前，加入一層審核（可為規則式或 LLM 式），過濾掉與可見證據矛盾的診斷。論文中特別強調 LLM 評判器存在雜訊，審核是必要的品質控制。

**步驟五：建立持續性備註系統**
為每個診斷問題建立 finding note，追蹤兩個獨立維度：
- **Adherence**：代理是否嘗試了建議的動作
- **Resolution**：底層問題是否真正解決
備註狀態分為 Resolved（關閉）、Unresolved（精煉回饋）、No issue（繼續執行）。

**步驟六：評估與基準比較**
在 Terminal-Bench 2.1、SWE-Bench Pro、DeepSWE v1.1 上比較有無 Opera 的解決率。論文中 Opera 在三個基準上皆達到最高的平均解決率，並優於四個競爭性批評基準。

**步驟七（選用）：產生微調資料**
收集 Opera 引導下的學生模型 rollouts（包含成功與失敗軌跡），用於微調小型模型。論文中 Qwen3.5-9B 在保留的 SWE-Bench Pro 倉庫上提升 10.2 個百分點，且在切換 harness 時（OpenHands → Terminus-2）效能不會顯著下降。

### 潛在風險與注意事項

**風險一：批評器誤判導致任務偏移**
- **現象**：批評器對部分證據做出過度診斷，使原本會成功的代理偏離正確路徑
- **緩解**：審核機制必須嚴格檢查「claim 是否由可見證據支持」；保留「保持沉默」選項；對 self-critique 場景特別小心，因為模型對自身錯誤的判斷可能存在系統性偏差

**風險二：審查頻率與成本的權衡**
- **現象**：過於頻繁的審查會大幅增加 token 成本與延遲；過於稀疏則失去即時介入的價值
- **緩解**：採用混合排程（週期 + 事件），事件觸發僅在必要時啟動；對長任務使用較大的 `k`，對短任務使用較小的 `k`

**風險三：遵循度與解決度的混淆**
- **現象**：代理可能執行了建議動作但未真正解決問題（mere compliance）
- **緩解**：在 finding note 中明確分離兩個維度；解決標準必須在診斷時就固定，避免被最新的回饋覆蓋；定期審查已「遵循」但未「解決」的備註

**風險四：微調資料的偏誤**
- **現象**：Opera 引導的 rollouts 帶有批評器的偏見，可能將這些偏見傳遞給學生模型
- **緩解**：保留一部分無批評器的 rollouts 作為對照；評估微調後模型在切換 harness 後的效能（論文中這是 Opera 資料的優勢——比強模型蒸餾更能跨 harness 泛化）

**風險五：基準與真實任務的落差**
- **現象**：Terminal-Bench 2.1 等基準的任務特性可能與企業實際程式碼庫差異甚大
- **緩解**：在自有程式碼庫上建立小型評估集；持續監控代理在生產環境中的「無聲失敗」率

### 與其他技術的整合建議

**與 Self-Refine / Reflexion 的整合**
Self-Refine 與 Reflexion 屬於「單次反思」機制，Opera 可作為它們的升級版——將每次反思升級為持續性備註，並加入審核與追蹤。建議將 Self-Refine 的迭代精煉邏輯包裝成 Opera 的一個 typed operator。

**與 SWE-PRM 的整合**
SWE-PRM 採用固定週期審查，Opera 的混合排程可作為其增強：在週期審查之間加入事件觸發，並加入審核機制過濾 PRM 的雜訊輸出。

**與 Agentic Rubrics 的整合**
Agentic Rubrics 提供倉庫特定的評分標準，Opera 可將這些標準作為「解決標準」嵌入 finding note，使解決度判斷更具體、可驗證。

**與 Tree of Thoughts / SWE-Search 的整合**
若使用樹搜尋框架，Opera 可作為節點選擇的「品質過濾器」——對每個候選軌跡套用批評器，僅保留通過審核的分支。

**與 CI/CD 系統的整合**
將 Opera 包裝成 webhook 服務：當 CI 失敗時觸發代理，代理的執行軌跡即時送入 Opera 批評器，回饋透過 issue comment 或 PR review 形式送回。

**與模型監控平台的整合**
將 finding note 的狀態（Resolved / Unresolved / Refined）匯出至監控儀表板，追蹤代理在生產環境中的「批評介入率」與「解決率」，作為模型版本的健康指標。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題描述與第 3 節的框架總覽（Figure 2），理解「為什麼需要批評器」以及「持續性備註」這個核心比喻。實作上可從 Mini-swe-agent + 單一策略模型開始，跳過微調部分，專注於體驗混合排程與審核機制如何影響代理行為。

**給 AI 工程師**：重點關注第 3.1–3.3 節的具體機制設計，特別是 typed operators 的設計、審核規則的實作方式、以及 finding note 的狀態機。實作時建議先複製論文的 prompt template，在自有基準上重現解決率提升，再針對特定領域調整 operator 類型與解決標準的措辭。

**給研究者**：第 2 節的相關工作分類（批評器、測試時縮放）提供了清晰的定位——Opera 的貢獻在於將批評視為「後續可追蹤的介入」而非「單次評分」。建議深入分析審核機制對 LLM 評判器雜訊的緩解效果，以及 Opera-guided rollouts 為何比強模型蒸餾更具跨 harness 泛化能力，這兩個問題都值得延伸研究。

**給產品經理**：Opera 的核心價值主張是「讓長程代理更可靠且更便宜」——透過及時且精準的介入提升解決率，同時 Opera-guided rollouts 提供了一條不依賴昂貴強模型蒸餾的模型改進路徑。評估導入價值時，建議關注三個指標：解決率提升、單任務平均成本（token 消耗）、以及切換執行框架時的效能穩定性（後兩項是 Opera 相較於蒸餾的差異化優勢）。
