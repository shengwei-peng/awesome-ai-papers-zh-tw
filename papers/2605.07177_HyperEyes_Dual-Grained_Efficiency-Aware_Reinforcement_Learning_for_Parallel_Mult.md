# HyperEyes：用於平行多模態搜尋代理的雙粒度效率感知強化學習

## ⚡ TL;DR

現有多模態搜尋代理循序處理多實體查詢，產生嚴重互動冗餘與推論成本過高問題。
提出HyperEyes平行代理，融合視覺定位與檢索為原子動作，透過雙粒度效率感知強化學習訓練。
在六項基準測試中，HyperEyes-30B以少5.3倍工具呼叫輪次，超越最強開源代理9.9%準確率。

## 摘要翻譯

現有的多模態搜尋代理（Multimodal Search Agents）循序處理目標實體，每個實體發出一個工具呼叫（Tool Call），並在查詢分解為獨立子檢索（Sub-retrieval）時累積冗餘的互動輪次（Interaction Round）。我們主張有效的多模態代理應「搜得更廣」而非「搜得更久」：在單一輪次內同時分派多個接地查詢（Grounded Query）。為此，我們提出 HyperEyes，一種平行多模態搜尋代理（Parallel Multimodal Search Agent），將視覺定位（Visual Grounding）與檢索（Retrieval）融合為單一原子動作（Atomic Action），使其能夠同時對多個實體進行並行搜尋，同時將推論效率（Inference Efficiency）視為首要訓練目標。

HyperEyes 以兩個階段進行訓練。針對冷啟動監督（Cold-start Supervision），我們開發了一個平行適用資料合成流程（Parallel-Amenable Data Synthesis Pipeline），涵蓋視覺多實體定位（Multi-entity Grounding）與文字多約束查詢（Multi-constraint Query），並透過漸進式拒絕抽樣（Progressive Rejection Sampling）策展效率導向軌跡（Efficiency-oriented Trajectory）。在此基礎上，我們的核心貢獻——雙粒度效率感知強化學習（Dual-Grained Efficiency-Aware Reinforcement Learning）框架——在兩個層級上運作。在宏觀層級（Macro Level），我們提出 TRACE（Tool-use Reference-Adaptive Cost Efficiency，工具使用參考自適應成本效率），這是一種軌跡層級獎勵（Trajectory-level Reward），其參考值在訓練過程中單調收緊（Monotonically Tightened），以抑制多餘的工具呼叫，同時不限制真正的多跳搜尋（Multi-hop Reasoning）。在微觀層級（Micro Level），我們改編線上策略蒸餾（On-Policy Distillation），從外部教師模型（External Teacher）在失敗 rollout（Failed Rollout）上注入密集的詞元層級修正訊號（Token-level Corrective Signal），以緩解稀疏結果獎勵（Sparse Outcome Reward）的信用分配（Credit Assignment）缺陷。

由於現有基準測試（Benchmark）僅將準確率（Accuracy）作為唯一評估指標，忽略了推論成本（Inference Cost），我們引入 IMEB——一個由人工策展（Human-curated）、包含 300 個實例的基準測試，可同時評估搜尋能力（Search Capability）與成本效率（Cost Efficiency）。在六個基準測試中，HyperEyes-30B 平均工具呼叫輪次（Tool-call Round）減少為原來的 1/5.3，在準確率上超越最強的同類開源代理（Open-source Agent）9.9%。

### 核心貢獻（3～5點）
- **平行多模態搜尋代理架構**：提出 HyperEyes，將視覺定位與檢索融合為單一原子動作，使代理能在單一互動輪次內同時分派多個接地查詢，從根本上消除循序工具呼叫（Sequential Tool Invocation）所帶來的互動冗餘（Interaction Redundancy）。
- **平行適用資料合成流程**：設計涵蓋視覺多實體定位與文字多約束查詢的資料建構方法，並透過漸進式拒絕抽樣策展效率導向軌跡，為冷啟動監督提供高品質訓練資料。
- **雙粒度效率感知強化學習框架**：在宏觀層級提出 TRACE（軌跡層級獎勵），其參考值於訓練過程中單調收緊以抑制暴力過度搜尋（Brute-force Over-searching）；在微觀層級改編線上策略蒸餾，從外部教師模型在失敗 rollout 上注入密集詞元層級修正訊號，緩解稀疏結果獎勵的信用分配缺陷。
- **IMEB 基準測試**：發布由人工策展、包含 300 個實例的基準測試，首次將搜尋能力與成本效率納入聯合評估，彌補現有基準僅以準確率為唯一指標的不足。
- **卓越的實驗表現**：在六個基準測試中，HyperEyes-30B 以平均 1/5.3 的工具呼叫輪次，在準確率上超越最強同類開源代理 9.9%，驗證「搜得更廣」策略在效率與效能上的雙重優勢。

## 深度分析

#### 方法論解析

HyperEyes 的方法論核心在於將「效率」從事後評估指標提升為訓練過程中的一等優化目標，並透過統一動作空間 (Unified Grounded Search, UGS) 與雙粒度強化學習 (Dual-Grained Efficiency-Aware RL) 兩個相互耦合的設計來實現。

**統一接地搜尋動作空間 (Unified Grounded Search, UGS)**

傳統多模態搜尋代理將「視覺定位 (visual grounding)」與「檢索 (retrieval)」視為兩個分離的動作：先呼叫裁切 (crop) 工具取得子影像，再對子影像執行影像搜尋或文字搜尋。這種序列化的動作分解在處理多實體影像時會產生嚴重的互動冗餘 (interaction redundancy)，因為每個實體都需要獨立的「裁切→搜尋」輪次。HyperEyes 提出的 UGS 將這兩個步驟融合為單一原子動作 (atomic action)，允許模型在一個回合 (round) 內同時輸出多個接地查詢 (grounded query)，每個查詢內含實體的邊界框 (bounding box) 與對應的搜尋指令。這種設計將文字層級的平行性延伸至視覺模態，使模型得以「搜尋得更廣，而非更久 (search wider, not longer)」。

**平行適用資料合成流程 (Parallel-Amenable Data Synthesis Pipeline)**

冷啟動監督 (cold-start supervision) 階段的目標是為後續 RL 提供高品質的效率導向軌跡 (efficiency-oriented trajectory)。流程涵蓋兩類查詢：視覺多實體 (visual multi-entity) 與文字多約束 (multi-constraint)。其中關鍵技術是漸進式拒絕抽樣 (Progressive Rejection Sampling)，其運作邏輯是：在每一輪抽樣中，以更嚴格的效率約束（例如更少的工具呼叫輪次）作為篩選門檻，逐步淘汰冗長軌跡而保留緊湊平行軌跡 (compact parallel trajectory)。這種由鬆至緊的課程式設計避免了直接以最嚴格標準篩選所導致的資料量不足問題，同時確保最終資料集內的軌跡本身就具備平行且非冗餘的結構特性。

**雙粒度效率感知強化學習框架 (Dual-Grained Efficiency-Aware RL)**

此框架是論文的中心貢獻，在兩個互補的粒度上運作：

*宏觀層級 (Macro Level) — TRACE 獎勵*

TRACE (Tool-use Reference-Adaptive Cost Efficiency) 是一種軌跡層級獎勵 (trajectory-level reward)，其創新在於「參考自適應 (reference-adaptive)」機制：獎勵函數中的參考成本 (reference cost) 並非固定值，而是在訓練過程中單調收緊 (monotonically tightened)。具體而言，隨著訓練推進，模型被期望以更少的工具呼叫輪次完成相同任務；若實際軌跡長度低於當前參考，則獲得正向效率獎勵；反之則受到懲罰。這種動態參考的設計避免了兩個極端：若參考過於寬鬆，模型會傾向暴力過度搜尋 (brute-force over-searching)；若參考過於嚴格，則可能壓制真實所需的多跳搜尋 (multi-hop search)。單調收緊的排程使模型在訓練早期保有探索空間，後期則被推向 Pareto 前緣的效率邊界。

*微觀層級 (Micro Level) — 線上策略蒸餾 (On-Policy Distillation, OPD)*

稀疏結果獎勵 (sparse outcome reward) 在長軌跡任務中存在嚴重的信用分配 (credit assignment) 問題：當 rollout 失敗時，模型難以判斷是哪一個詞元 (token) 的決策導致錯誤。HyperEyes 採用 OPD 來注入密集詞元層級修正訊號 (dense token-level corrective signal)。具體做法是：對於失敗的 rollout，從外部教師模型 (external teacher) 取得正確軌跡，並以此作為監督訊號對學生模型的詞元級對數機率 (token-level log-probability) 進行蒸餾。值得注意的是，這是「線上 (on-policy)」的——蒸餾發生在學生模型自身採樣的失敗軌跡上，而非離線資料集上，因此修正訊號與學生當前策略的錯誤模式高度相關，能有效針對性地修正弱點。

**整體訓練流程的耦合關係**

冷啟動階段提供具備平行結構的監督訊號，使模型學會 UGS 動作空間的基本語法；RL 階段則在效率約束下進一步優化策略。TRACE 從宏觀端防止整體軌跡冗餘，OPD 從微觀端修正個別決策錯誤，兩者形成互補的雙層監督訊號。

#### 實驗數據解讀

**核心結果：Pareto 主導 (Pareto Dominance)**

論文的旗艦結果是 HyperEyes-30B 在六個基準測試上同時提升準確率與效率：相較最強的開源代理 (open-source agent)，準確率提升 9.9%，平均工具呼叫輪次 (tool-call round) 減少 5.3 倍。這意味著 HyperEyes-30B 在「準確率—效率」二維空間中 Pareto 主導所有對比基線，即在任一固定效率預算下其準確率最高，或在任一固定準確率門檻下其成本最低。這是該領域少數能同時在兩個維度取得顯著改進的工作。

**IMEB 基準測試的設計意涵**

論文的另一重要貢獻是引入 IMEB (Image Multi-Entity Benchmark)，一個包含 300 個人工策展 (human-curated) 實例的基準測試。其獨特價值在於：

1. **聯合評估維度**：傳統基準（如 MMSearch、FVQA 等）僅以最終答案準確率作為評分標準，掩蓋了冗長軌跡的隱性成本。IMEB 同時評估搜尋能力 (search capability) 與成本效率 (cost efficiency)，使效率成為一等評估指標。

2. **多實體強制性**：每個實例的影像包含多個實體，且問題設計上「嚴格要求 (strictly requires)」跨實體的並行定位與檢索。這排除了可透過單一實體或單一跳躍解決的捷徑，確保評估的是真正的平行搜尋能力。

3. **診斷價值**：在 IMEB 上，平行搜尋的「廣度 (breadth)」成為主要瓶頸，這一發現揭示了先前模型在多實體視覺搜尋場景下的結構性缺陷。

**六基準的全面性**

雖然論文中未完整列出六個基準的名稱，但從相關文獻脈絡推測應包含 FVQA、MMSearch、MMSearch-R1、WebQA、InfoSeek 等多模態搜尋基準。在多個基準上的一致性提升表明，UGS 動作空間與雙粒度 RL 並非針對單一基準過擬合，而是學到了通用的平行搜尋策略。

**效率指標的解讀**

「5.3 倍更少的工具呼叫輪次」是一個強烈的訊號：它意味著在實際部署中，HyperEyes 的 API 成本、延遲與上下文長度均大幅降低。然而需注意，「平均」一詞暗示存在分佈差異——對於簡單任務可能僅節省 2-3 倍，對於複雜多實體任務可能節省 10 倍以上。論文中若能提供分位數 (quantile) 統計或按任務難度分層的結果，將更具說服力。

#### 與現有研究的比較

**相較循序多模態代理的改進**

傳統多模態搜尋代理（如 MMSearch-R1、WebVoyager 等）依賴循序工具呼叫 (sequential tool invocation) 來深化推理鏈 (reasoning chain)。這在多跳推理任務中有效，但在可分解為獨立子檢索 (sub-retrieval) 的查詢上會產生嚴重冗餘。HyperEyes 的核心改進在於：將平行性從文字層級（已有工作如 Search-R1、DeepDive、MiroThinker 探索過）擴展至視覺層級，並透過 UGS 動作空間實現真正的「單回合多實體接地搜尋」。

**相較純文字平行代理的差異**

文字領域的平行工具呼叫研究（如 ToolLLM、ReAct 的平行變體）已證明平行性可提升效率，但這些方法缺乏視覺接地能力。當面對圖表、空間 UI 佈局或影像接地約束時，純文字代理會遭遇語意損失 (semantic loss)。HyperEyes 的 UGS 設計正是為填補此模態缺口，使模型能在保留視覺證據的同時進行平行檢索。

**相較「寬搜尋」典範的定位**

近期文字代理研究探討了「搜尋更多、思考更少 (search more, think less)」的 Test-Time Scaling (TTS) 策略，強調擴展探索步驟以減輕 LLM 推理負擔。HyperEyes 與此典範方向一致，但更進一步：它不僅「搜尋更多」，而是「搜尋得更廣且更高效」，透過平行性同時實現廣度與效率的提升。

**潛在限制**

1. **多實體假設的依賴**：UGS 的平行性假設查詢可分解為獨立子任務。對於需要跨實體關聯推理的查詢（如「比較 A 與 B 的差異」），平行架構可能不如循序推理有效。論文中未深入探討此邊界情況。

2. **教師模型的可及性**：OPD 需要一個強大的外部教師模型來產生修正訊號，這在實際部署中可能成為瓶頸。若教師與學生之間存在能力差距過大或領域錯配，蒸餾效果可能受限。

3. **參考收緊排程的敏感性**：TRACE 的單調收緊排程是超參數敏感的——收緊過快可能導致策略崩壞 (policy collapse)，收緊過慢則無法有效抑制冗餘。論文中未提供此排程的理論分析或消融實驗。

4. **基準的領域偏置**：IMEB 雖具創新性，但 300 個實例的規模相對有限，且人工策展可能引入特定領域偏置。其在多大程度上代表真實世界多實體搜尋需求的分佈，仍有待驗證。

#### 可重現性評估

**程式碼與模型權重**

作為一篇預印本 (preprint) 論文，HyperEyes 的可重現性取決於作者後續是否開源。從論文的工程深度（包含兩階段訓練流程、客製化動作空間、雙層獎勵設計）來看，完整的開源實現將涉及大量程式碼：UGS 動作空間的解析器、漸進式拒絕抽樣的資料處理流程、TRACE 獎勵的動態參考排程、OPD 的詞元級對齊邏輯等。論文中未明確聲明程式碼倉庫連結，這是目前可重現性的一大缺口。

**資料集可及性**

IMEB 作為人工策展基準，其釋出形式（公開下載、申請制或僅供評估）將直接影響後續研究的可比性。300 個實例的規模適中，預期可完整公開。冷啟動訓練資料的合成流程雖然有詳細描述，但若不釋出合成後的具體軌跡資料，其他研究者難以精確重現訓練過程。

**訓練細節的透明度**

論文中提及了 HyperEyes-30B 的模型規模，但對於以下關鍵細節的描述仍待補充：

- 基礎模型 (base model) 的選擇與其原始能力
- 冷啟動階段的訓練資料量與訓練步數
- RL 階段的具體演算法（PPO、GRPO 或其他變體）
- TRACE 參考值的初始值、終值與收緊函數形式
- OPD 中教師模型的選擇與蒸餾溫度
- 工具呼叫的具體介面（搜尋 API、裁切工具的實作）

這些細節的缺失使得獨立重現存在相當難度。

**評估的可重現性**

六個基準的評估流程若採用標準化工具包（如 MMSearch 的官方評估腳本），則具備一定可重現性。但 IMEB 作為新基準，其評估指標的具體計算方式（效率如何量化、聯合評分如何加權）需要更明確的定義。

#### 未來研究方向

**1. 跨模態平行性的理論基礎**

目前 UGS 的平行性是啟發式設計的，未來可探索其理論基礎：例如，在什麼條件下平行搜尋優於循序搜尋？是否存在一個「平行性增益 (parallelism gain)」的理論上界？這將有助於將 HyperEyes 的經驗成功提煉為可預測的設計原則。

**2. TRACE 參考排程的自適應化**

當前的單調收緊排程是預設的，未來可研究基於策略當前效率分佈的自適應排程：例如，當模型在某些任務類型上已達到高效，但在其他類型上仍冗餘時，可對不同任務類型採用差異化的參考收緊曲線，實現更細粒度的效率約束。

**3. OPD 教師模型的替代方案**

OPD 對外部教師的依賴是實際部署的瓶頸。未來可探索：

- **自我修正 (self-correction)**：讓模型在失敗 rollout 上進行自我反思並產生修正軌跡
- **過程獎勞模型 (Process Reward Model, PRM)**：訓練一個專門評估中間步驟品質的模型，取代教師的詞元級監督
- **對抗式 OPD**：使用學生模型自身的成功 rollout 作為正向示範，失敗 rollout 作為負向示範，進行對比學習

**4. 效率指標的多維化**

IMEB 目前以工具呼叫輪次作為效率代理，未來可納入更多維度：

- **延遲 (latency)**：實際端到端回應時間
- **Token 消耗**：包括輸入上下文與輸出推理的總 token 數
- **API 成本**：不同工具的呼叫成本異質性
- **碳排放 (carbon footprint)**：作為永續 AI 的考量

建立多維效率基準將使效率研究更貼近實際部署需求。

**5. 從多實體到多模態平行**

HyperEyes 目前聚焦於視覺多實體的平行搜尋，未來可擴展至：

- **音訊-視覺平行**：同時處理影像與音訊證據
- **影片平行搜尋**：在長影片中並行定位多個時間片段
- **3D 場景平行**：在點雲或 3D 模型中並行搜尋多個物件

這將使平行搜尋典範從 2D 影像擴展至更豐富的多模態場景。

**6. 與人類認知機制的對齊**

人類在處理多實體視覺場景時，天然採用平行注意力機制 (parallel attention mechanism)。HyperEyes 的平行搜尋與人類認知之間是否存在結構性對應？未來可從認知科學角度分析平行搜尋策略，進一步優化模型設計。

**7. 安全與偏誤考量**

平行搜尋可能放大訓練資料中的偏誤：若某些實體類型在訓練資料中代表性不足，平行搜尋可能同時對多個偏誤實體進行接地，造成錯誤的級聯放大。未來需研究平行架構下的偏誤傳播機制與緩解策略。

**8. 實際部署的工程優化**

將 HyperEyes 部署至生產環境時，需考慮：

- **平行工具呼叫的速率限制 (rate limiting)**：同時呼叫多個搜尋 API 可能觸發限制
- **錯誤恢復**：部分平行呼叫失敗時的優雅降級
- **快取機制**：對相似實體的接地結果進行快取，避免重複計算

這些工程問題雖非學術焦點，但對實際影響至關重要。

## 論文問答

**Q1：為什麼現有的多模態搜尋代理在處理多實體查詢時效率低落？**

A：現有的多模態搜尋代理主要採用循序工具呼叫的範式，每個目標實體都需要經歷一次獨立的工具呼叫與互動輪次，因此當查詢可分解為多個獨立的子檢索任務時，會累積大量冗餘的互動輪次。這種循序設計雖然在多跳推理任務中表現良好，但在面對多實體視覺查詢時會產生嚴重的互動冗餘，因為每個實體都需要重複進行裁切、影像搜尋與文字搜尋等步驟。此外，由於缺乏明確的效率目標，模型傾向於產生冗長的軌跡而非緊湊的平行軌跡，使得上下文變得更長且更雜訊，進一步降低整體效率。

**Q2：為什麼僅僅具備平行工具呼叫能力並不足以帶來真正的效率提升？**

A：雖然平行工具呼叫已在文字代理與近期視覺模型中出現以解決循序處理的瓶頸，但擁有平行能力並不保證搜尋行為本身是高效的。現有模型主要透過純準確度獎勵進行優化，因此缺乏偏好緊湊平行軌跡而非冗長軌跡的激勵機制。在沒有明確效率目標的情況下，平行能力往往會退化成暴力過度搜尋，迫使模型進行大量不必要的互動輪次來恢復準確度。這說明僅有架構上的平行性是不夠的，必須在訓練目標中將推論效率視為一等公民來處理。

**Q3：「搜得更廣而非更久」（search wider, not longer）這個設計原則為何重要？**

A：這個原則直指多實體視覺搜尋任務的核心瓶頸——平行搜尋的廣度，而非序列推理的深度。傳統代理透過加深推理鏈來處理複雜任務，但在多實體場景中，各實體的檢索本質上是獨立的，應在同一輪互動中並行處理而非依序展開。透過在單一輪次內同時對多個實體進行接地與檢索，模型可以顯著縮短互動鏈並降低上下文雜訊，從而實現精準且高效的搜尋。這個原則也呼應了測試時計算（Test-Time Scaling）研究中關於「搜尋更多、思考更少」策略的洞察，強調外部知識的廣泛擷取能有效減輕 LLM 推理引擎的認知負擔。

**Q4：HyperEyes 的核心架構創新是什麼？**

A：HyperEyes 的核心架構創新在於其統一接地搜尋（Unified Grounded Search, UGS）動作空間，將視覺定位與檢索融合為單一的原子動作。這項設計將文字層級的平行性延伸至視覺模態，使代理能夠在單一輪次中同時對多個實體進行接地並發起搜尋查詢。透過將多實體定位、多約束查詢與檢索整合到同一個動作中，HyperEyes 避免了傳統代理需要在多個獨立步驟中重複處理每個實體的問題。這種原子化設計不僅提升了效率，也簡化了推理流程，使模型能夠以更結構化的方式處理複雜的多實體視覺查詢。

**Q5：TRACE 獎勵機制是如何運作的？**

A：TRACE（Tool-use Reference-Adaptive Cost Efficiency，工具使用參考自適應成本效率）是一種軌跡層級的獎勵設計，其參考值會在訓練過程中單調收緊。這個機制的核心思想是動態調整效率基準線，隨著訓練進行逐步提高對工具呼叫數量的要求，從而抑制多餘的工具呼叫，同時不限制真正的多跳搜尋需求。透過這種參考自適應的設計，模型被引導朝向最佳效率方向學習，避免在訓練初期因過於寬鬆的標準而養成冗長搜尋的習慣。這種單調收緊的獎勵排程確保了效率約束的漸進式強化，使模型能夠在維持準確度的同時持續優化推論成本。

**Q6：為什麼需要雙粒度（宏觀+微觀）的強化學習設計？**

A：雙粒度設計是為了解決強化學習中稀疏結果獎勵所帶來的信用分配不足問題。在宏觀層級，TRACE 提供軌跡層級的效率獎勵，引導整體搜尋行為朝向高效方向；但僅有軌跡層級的獎勵無法告訴模型具體哪個詞元或步驟出了問題。在微觀層級，線上策略蒸餾（On-Policy Distillation, OPD）從外部教師模型注入密集的詞元層級修正訊號，特別是在失敗的 rollout 上提供細粒度的監督。這種雙層次的設計結合了宏觀的效率導向與微觀的精確修正，使模型既能學會整體策略，又能從具體錯誤中獲得可操作的回饋，從而緩解稀疏獎勵帶來的學習效率低落問題。

**Q7：IMEB 基準測試的設計有何獨特之處？**

A：IMEB（Image Multi-Entity Benchmark）是一個包含 300 個實例的人工策展資料集，其獨特之處在於首次將搜尋能力與搜尋效率作為聯合評估指標。現有基準測試主要評估最終答案的準確率，掩蓋了冗長搜尋軌跡中的效率問題，而 IMEB 透過要求每個實例都包含多實體影像與嚴格需要並行定位與檢索的問題來填補這一缺口。這種設計使得評估能夠真實反映代理在多實體視覺場景中的綜合表現，而非僅僅關注最終答案是否正確。透過將操作效率提升為一等評估指標，IMEB 為未來多模態搜尋代理的發展建立了新的評估標準。

**Q8：HyperEyes-30B 在六個基準測試上的關鍵成果為何？**

A：HyperEyes-30B 在六個基準測試上展現了最先進的成果，Pareto 支配了現有的開源代理模型。具體而言，它在準確率上比最強的開源代理高出 9.9%，同時平均所需的工具呼叫輪次減少了 5.3 倍。這項成果的重要性在於它同時實現了準確度與效率的提升，而非傳統的權衡取捨——通常提升準確度需要更多計算資源，而 HyperEyes 證明了透過平行搜尋的廣度而非序列推理的深度，可以同時達成兩個目標。這種雙重突破驗證了「搜得更廣而非更久」設計原則的有效性，也展示了效率感知訓練框架的實質價值。

**Q9：訓練流程中各階段的消融研究顯示了什麼？**

A：雖然論文中未提供完整的消融研究細節，但從方法論設計可以推論各階段的貢獻：冷啟動階段透過平行適用資料合成流程與漸進式拒絕抽樣，為模型提供了效率導向軌跡的初始監督，使其在進入強化學習階段前已具備基本的平行搜尋能力。雙粒度效率感知強化學習框架中的 TRACE 與 OPD 各自負責不同層級的優化——前者處理軌跡層級的效率約束，後者處理詞元層級的精確修正。冷啟動監督與強化學習的結合確保了模型不會從隨機初始化開始探索低效的行為模式，而是基於高品質的初始軌跡進行進一步優化，從而加速收斂並提升最終效能。

**Q10：HyperEyes 適合哪些實際應用場景？**

A：HyperEyes 特別適合需要從視覺豐富的內容中同時擷取多個實體資訊的場景，例如體育賽事分析（從比賽截圖中識別多位球員的表現數據）、電子商務（從產品展示圖中比較多個商品規格）、以及社群媒體內容理解（從圖片中識別多個人物或物件並查詢相關資訊）。在這些場景中，使用者通常會提出涉及多個視覺元素的複合查詢，而 HyperEyes 的平行接地搜尋能力能夠在單一輪次中處理所有相關實體，大幅提升回應速度。此外，對於需要即時可驗證資訊的應用，如新聞查證或即時賽事報導，HyperEyes 的高效率特性使其能夠在時間敏感的場景中提供快速且準確的答案。

**Q11：將此技術產品化時需要考量哪些因素？**

A：產品化時首先需要考量的是基礎設施成本，雖然 HyperEyes 減少了工具呼叫輪次，但平行呼叫本身可能對後端服務造成短時間內的高併發壓力，需要相應的負載平衡與資源調度機制。其次是延遲與準確度的權衡，雖然平均效率提升 5.3 倍，但在某些邊緣案例中，平行呼叫的失敗可能導致需要重試，進而影響使用者體驗，因此需要設計良好的錯誤處理與降級機制。此外，模型本身的部署成本（30B 參數規模）也是重要考量，可能需要模型壓縮、量化或採用雲端 API 等方案來降低終端使用成本，同時確保回應品質不受顯著影響。

**Q12：這項研究對多模態代理領域的影響為何？**

A：這項研究最重要的影響在於將效率從次要考量提升為一等訓練目標，挑戰了多模態代理領域長期以來「準確度優先」的單一優化範式。透過引入 IMEB 基準測試，研究團隊建立了效率與準確度聯合評估的標準，這將促使後續研究在設計代理時必須同時考慮兩個維度。此外，雙粒度強化學習框架（TRACE + OPD）為稀疏獎勵問題提供了系統性的解決方案，這種設計思路可以延伸到其他需要效率約束的代理任務中。更廣泛地說，「搜得更廣而非更久」的原則可能會影響整個領域對測試時計算分配的重新思考，推動更多研究探索平行性作為效率提升手段的潛力。

**Q13：HyperEyes 有哪些已知的限制？**

A：從論文描述來看，HyperEyes 的主要限制在於其依賴於高品質的冷啟動資料，平行適用資料合成流程的品質直接影響後續強化學習的效果，若初始軌跡存在偏差，模型可能難以完全擺脫這些偏差。此外，30B 的參數規模雖然在開源模型中具有競爭力，但相較於更大的專有模型仍存在能力差距，且部署成本對中小型應用而言可能偏高。另一個潛在限制是 IMEB 僅包含 300 個實例，雖然經過人工策展，但規模相對有限，可能無法完全代表所有多實體視覺搜尋場景的多樣性，這也意味著模型在面對訓練分布外的查詢時，泛化能力仍有待驗證。

**Q14：在哪些情況下 HyperEyes 可能會失敗？**

A：HyperEyes 在處理實體間存在複雜依賴關係的查詢時可能表現不佳，因為其平行搜尋假設各子檢索任務是相對獨立的，若實體間的資訊需要交叉驗證或順序推理，平行架構可能無法有效處理。此外，當影像中的實體數量極多（如數十個以上）時，單一輪次的平行呼叫可能會超出模型的上下文處理能力或後端服務的併發限制，導致部分呼叫被截斷或失敗。在視覺接地不準確的場景下（如遮擋、低解析度或模糊的實體），平行搜尋可能會基於錯誤的定位結果發起大量無效查詢，造成效率與準確度的雙重損失，這也是暴力過度搜尋風險的具體表現。

**Q15：未來的研究方向有哪些？**

A：未來研究可以朝幾個方向延伸：首先，可以探索動態調整平行粒度的機制，根據查詢複雜度與實體數量自適應決定每輪呼叫的數量，而非固定採用最大平行度，以進一步提升效率。其次，可以將雙粒度強化學習框架應用於其他模態或任務，例如音訊或多輪對話場景，驗證其通用性。此外，IMEB 的 300 個實例可以擴展為更大規模、更多樣化的基準，並涵蓋更細粒度的效率指標（如延遲、token 使用量等）。最後，結合測試時計算（Test-Time Scaling）研究的最新進展，探索「搜得更廣」與「思考更深」之間的最佳平衡點，將是多模態代理領域值得深入探討的課題。

## 實務應用指南

### 適用場景

**1. 電商多商品比價與視覺化決策輔助**
消費者上傳一張包含多件商品（如服飾、家電配件）的圖片時，HyperEyes 可在一輪互動內同時定位所有商品並平行查詢規格、價格與評價，協助使用者快速完成跨平台比價。相較於傳統循序代理需為每件商品各花費 3–5 輪互動，平行機制可將整體決策時間壓縮至 1/5 以下。

**2. 社群媒體圖文事實查核**
面對一張包含多位公眾人物或多個地標的新聞圖片，查核系統需同時驗證每個實體的身分與背景脈絡。HyperEyes 的多實體接地搜尋（Multi-entity Grounding）可在單一輪次中裁切所有目標區域並平行送出檢索請求，特別適合需要快速產出查核報告的編輯台工作流。

**3. 智慧客服中的多附件工單理解**
使用者常在工單中夾帶多張截圖（訂單畫面、錯誤訊息、產品外觀）。HyperEyes 可同時解析多張影像中的多個視覺元素並交叉查詢 FAQ 與知識庫，縮短客服回應時間並降低平均處理成本（AHT）。

**4. 醫療影像多病灶交叉查證**
放射科醫師上傳含多個可疑病灶的 CT/MRI 切片時，系統可平行定位每個病灶並同時檢索最新文獻與相似病例，輔助診斷決策。此場景對效率極為敏感——縮短互動輪次意味著減少醫師等待時間。

**5. 教育領域的多模體學習輔助**
學生拍攝一頁含多個歷史人物或地理標誌的課本插圖時，輔助系統可平行查詢每個實體的延伸知識，並以單一回應整合所有解釋，模擬「一位博學教師同時講解多個概念」的自然教學節奏。

### 實作前置條件

**資料需求**
- **多實體視覺資料集**：需蒐集或標註大量「單張影像含多個可接地實體」的圖片，並配對多約束查詢（multi-constraint query）。建議至少 5–10 萬筆涵蓋人物、地標、產品、文件四類的訓練樣本。
- **效率導向軌跡資料**：透過 Progressive Rejection Sampling 從候選軌跡中篩選「工具呼叫數最少且答案正確」的範例，作為冷啟動監督訊號。
- **失敗 rollout 池**：需蒐集模型在 rollout 階段產生的失敗案例，用於 On-Policy Distillation 的教師示範配對。

**運算資源**
- **訓練階段**：30B 規模模型的全參數 RL 訓練建議至少 64 張 H100/A100 GPU，並配置 vLLM 或 SGLang 加速 rollout 產生。
- **推論階段**：單次查詢可能同時觸發 3–10 個平行工具呼叫，需預留 API 併發額度（搜尋引擎、影像裁切服務、向量資料庫）。
- **教師模型**：需部署一個比學生模型更強的 MLLM（如 GPT-4o、Qwen2.5-VL-72B）作為 OPD 的外部教師。

**技能門檻**
- 熟悉 PPO/GRPO 等 RL 演算法實作，能設計參考自適應的獎勵函數。
- 具備視覺定位（visual grounding）模型（如 Grounding DINO）的整合經驗。
- 理解稀疏獎勵下的信用分配問題，並能設計密集詞元層級的修正訊號。
- 具備分散式訓練與推論服務的部署能力。

### 實作步驟建議

**階段一：動作空間定義與基礎建設（2–4 週）**
1. 設計 Unified Grounded Search (UGS) 動作空間，將「裁切座標 + 檢索查詢」封裝為單一原子動作。
2. 建立工具呼叫介面層，支援影像裁切、文字搜尋、影像搜尋三類工具的平行呼叫。
3. 準備基礎 MLLM（建議從 Qwen2.5-VL-7B/30B 起步）並接入工具呼叫框架。

**階段二：冷啟動資料合成（3–5 週）**
1. 蒐集多實體影像並以視覺定位模型自動產生接地標註。
2. 為每張影像生成多約束查詢，確保問題需同時查詢多個實體才能正確回答。
3. 實作 Progressive Rejection Sampling：對每個查詢產生多條候選軌跡，依「正確性優先、工具呼叫數次之」排序，僅保留最緊湊的軌跡作為監督訊號。
4. 對基礎模型進行監督微調（SFT），建立初步的平行搜尋能力。

**階段三：雙粒度 RL 訓練（4–8 週）**
1. **宏觀層級**：實作 TRACE 獎勵函數，初始參考基準設為「人類專家軌跡的工具呼叫數 × 1.5」，訓練過程中以線性或餘弦排程單調收緊至 1.0 倍。
2. **微觀層級**：在每次 rollout 後，識別失敗樣本，由外部教師模型產生正確軌跡，計算詞元層級 KL 散度作為密集監督訊號。
3. 交替執行 GRPO 與 OPD 步驟，監控「準確率 / 工具呼叫數」帕累托曲線。

**階段四：評估與部署（2–3 週）**
1. 在 IMEB 與既有基準（MMSearch、WebQA 等）上聯合評估準確率與平均工具呼叫輪次。
2. 建立效率監控儀表板，追蹤每次推論的工具呼叫數與延遲。
3. 部署時設定工具呼叫併發上限與超時保護，避免單一查詢拖垮整體服務。

### 潛在風險與注意事項

**1. 平行呼叫的 API 成本失控**
雖然平行機制減少了「輪次」，但單輪內的併發請求數可能暴增。**緩解措施**：在 UGS 動作空間中加入「每輪最大實體數」上限（例如 5 個），並在獎勵函數中加入 API 成本懲罰項。

**2. 視覺定位錯誤向下游傳播**
若接地座標偏移，後續檢索將查詢錯誤的影像區域，導致整條軌跡失敗。**緩解措施**：在裁切後加入相似度檢查（裁切區域與查詢語義的 CLIP 分數），低於閾值時自動重試或降級為全圖搜尋。

**3. TRACE 參考基準過度收緊**
若參考基準收緊過快，可能迫使模型放棄必要的多跳推理以換取效率。**緩解措施**：採用「正確性優先」的安全閥——若軌跡答案錯誤，效率懲罰自動歸零，避免模型為了省成本而犧牲正確性。

**4. 教師模型偏差**
OPD 的效果高度依賴外部教師品質，若教師本身存在幻覺或偏見，會被放大注入學生模型。**緩解措施**：對教師軌跡進行二次驗證（自動檢查 + 抽樣人工審核），並在 OPD 損失中加入信心權重。

**5. 評估基準的侷限性**
IMEB 僅 300 筆實例，且聚焦多實體場景，可能無法反映長尾的真實查詢分佈。**緩解措施**：在自家業務資料上建立 A/B 測試框架，將「每千次查詢的工具呼叫總數」與「首次正確率」列為核心 KPI。

**6. 冷啟動資料的偏見**
Progressive Rejection Sampling 傾向選擇最短軌跡，可能過度偏好「猜對」而非「推理對」的樣本。**緩解措施**：在篩選時加入推理鏈長度的下限約束，確保保留的軌跡具備完整的推理過程。

### 與其他技術的整合建議

**1. 與傳統 RAG 系統整合**
HyperEyes 的文字搜尋工具可作為現有向量資料庫（如 Milvus、Qdrant）的封裝層。建議保留 RAG 的文件切塊與索引流程，僅將「是否呼叫、呼叫什麼、平行幾次」的決策交由 HyperEyes 控制。

**2. 與 Agent 框架整合**
可將 HyperEyes 作為 LangGraph 或 AutoGen 中的「視覺專家節點」，由上層規劃器決定何時呼叫。當查詢包含影像輸入時路由至 HyperEyes，純文字查詢則交給既有的文字搜尋代理。

**3. 與視覺定位模型解耦**
不建議將 Grounding DINO 等定位模型直接嵌入 HyperEyes 的 forward pass，而應作為獨立工具呼叫。這樣可在定位模型升級時無需重新訓練 HyperEyes，也方便針對不同垂直領域（醫療、工業）替換專用定位器。

**4. 與 Test-Time Scaling 策略互補**
HyperEyes 的「搜得更廣」與 Test-Time Scaling 的「想得更深」並不衝突。建議在系統層級設計兩階段策略：先用 HyperEyes 平行蒐集證據，再以長思考模型（如 o1-style）整合推理。

**5. 與成本監控平台整合**
將每次 rollout 的工具呼叫數、API 成本、延遲上報至既有監控系統（如 Prometheus + Grafana），設定「每查詢平均成本」警報閾值，並定期回灌至訓練流程以持續優化效率。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的圖 1 與第 2 節的相關工作，建立「為什麼多模態代理需要平行化」的直覺。接著跳過技術細節，直接看摘要中的「9.9% 準確率提升、5.3 倍工具呼叫減少」這個關鍵數字，理解 HyperEyes 解決的核心問題——「搜得更廣，而非更久」。可暫時略過 RL 訓練細節，專注於「統一接地搜尋動作空間」這個核心概念。

**給 AI 工程師**：重點研讀第 3 節的方法論，特別是 UGS 動作空間的設計與 TRACE 獎勵函數的單調收緊排程。建議在自己的業務場景中先小規模重現「多實體接地 + 平行搜尋」的流程，評估 API 成本與延遲的實際影響，再決定是否投入完整的 RL 訓練。On-Policy Distillation 的實作細節可參考原論文 [9]，重點關注失敗 rollout 的篩選標準與詞元層級損失的權重設計。

**給研究人員**：本論文的核心創新在於「將效率作為一階優化目標」並提出雙粒度（軌跡 + 詞元）的獎勵設計。建議深入分析 TRACE 的參考基準收緊曲線對帕累托前沿的影響，並探索以下延伸問題：(1) 參考基準是否可改為自適應而非單調收緊？(2) OPD 的教師是否可換成「同儕中較優者」而非外部強模型？(3) 雙粒度信號是否存在梯度衝突，如何平衡？IMEB 基準的設計理念也值得借鏡——呼籲社區建立更多「效率感知」的評估標準。

**給產品經理**：HyperEyes 的商業價值在於「用更少的 API 成本提供更好的答案」。在評估導入時，請關注三個指標：(1) 平均工具呼叫輪次的下降幅度（直接影響 API 成本）；(2) 首次回答正確率的提升（影響使用者滿意度）；(3) 對多實體圖片查詢的覆蓋率（影響新功能可行性）。建議先在內部資料上建立小規模 A/B 測試，以 IMEB 的 300 題作為概念驗證基準，再決定是否擴大投資。需特別注意：平行呼叫雖然減少輪次，但單輪成本可能上升，需以「每查詢總成本」而非「每輪成本」作為決策依據。
