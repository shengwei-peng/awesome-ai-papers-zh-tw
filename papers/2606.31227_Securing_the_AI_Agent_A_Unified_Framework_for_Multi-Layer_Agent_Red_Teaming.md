## 摘要翻譯

開源 AI 基礎設施——從模型服務引擎（model serving engines）、代理平台（agent platforms），到模型上下文協定（Model Context Protocol, MCP）生態系統與語言模型（language models）本身——的快速發展，已讓現有安全工具難以跟上。我們提出 AI-Infra-Guard，一個開源框架，該框架以一項核心觀察為主軸來組織 AI 紅隊演練（AI red teaming）：AI 代理（AI Agent）的攻擊面（attack surface）呈現分層特性（基礎設施層、協定/工具層、代理行為層與模型層），且沒有任何單一偵測典範（detection paradigm）能適用於所有層。因此，本框架為每一層配對最適合的典範：從涵蓋 75+ 個 AI 元件與 1,400+ 條漏洞規則的確定性規則匹配（deterministic rule matching），到由大型語言模型（LLM）驅動的 MCP 伺服器（MCP servers）與代理技能套件（agent-skill packages）代理式稽核（agentic auditing），再到多輪（multi-turn）黑箱（black-box）代理紅隊演練，乃至具備 26+ 種攻擊運算子（attack operators）、橫跨 16 個資料集（datasets）的越獄攻擊框架（jailbreak harness）。據我們所知，這是唯一涵蓋上述所有層面的開源框架，包括針對日益用於擴充 AI 代理能力的代理技能（agent skills）進行供應鏈稽核（supply-chain auditing）。我們將 AI-Infra-Guard 以開源形式釋出，使層-典範匹配（layer-paradigm matching）成為代理安全的實務基礎，並作為社群共同建構的共享基礎。

### 核心貢獻（3～5點）
- 提出 AI-Infra-Guard，據作者所知為首個涵蓋 AI 代理完整分層攻擊面的開源統一紅隊演練框架。
- 建立層-典範匹配原則，針對基礎設施層、協定/工具層、代理行為層與模型層分別配置最適偵測方法論。
- 實作四層對應的稽核能力：基礎設施規則掃描（75+ AI 元件、1,400+ 漏洞規則）、LLM 驅動的 MCP 伺服器與代理技能套件稽核、多輪黑箱代理紅隊演練，以及大規模越獄攻擊框架（26+ 攻擊運算子、16 個資料集）。
- 將供應鏈稽核延伸至代理技能（agent skills），填補 AI 軟體供應鏈中快速成長卻缺乏防護的環節。
- 以開源形式釋出框架，為學術界與產業界提供可擴展的代理安全研究與實務基礎。

### 適合對象
資安研究人員、AI/ML 工程師、紅隊測試人員、開源 AI 基礎設施維護者，以及關注 AI 代理供應鏈安全、MCP 生態系統風險與多層攻擊面治理的企業安全團隊與政策制定者。

## 深度分析

#### 方法論解析

本研究提出 **AI-Infra-Guard** 作為一個開源的多層代理紅隊演練（Multi-Layer Agent Red Teaming）框架，其核心方法論為 **層-典範匹配原則（Layer-Paradigm Matching Principle）**。該原則主張：AI 代理（AI Agent）的攻擊面（Attack Surface）並非單一平面，而是依據風險性質與可取得證據的差異，劃分為四個異質層級；每一層必須配對最適合的偵測典範（Detection Paradigm），才能同時兼顧覆蓋率、精確度與可解釋性。

四層架構與對應典範如下：

1. **基礎設施層（Infrastructure Layer）**：針對模型服務引擎（Model Serving Engines）如 Ollama、vLLM、llama.cpp，以及代理平台（Agent Platforms）如 Dify、LangFlow、Flowise，還有 MLflow、Kubeflow、Ray 等機器學習基礎設施。此層的風險多為網路暴露、未授權存取、API 金鑰外洩、版本已知漏洞等，證據形式為可觀測的指紋（Fingerprint）、Banner、設定檔與版本字串。因此採用 **確定性規則匹配（Deterministic Rule Matching）**，涵蓋 75+ 個 AI 元件（AI Components）與 1,400+ 條漏洞規則（Vulnerability Rules）。為處理 AI 元件常見的非語意化版本慣例（如 build identifier、dev tag、release candidate、rolling latest tag），框架內建版本正規化（Version Normalization）與指紋匹配語言（Fingerprint Matching Language），使傳統軟體組成分析（SCA）工具失效的版本比對問題得以解決。

2. **協定/工具層（Protocol/Tool Layer）**：聚焦 **模型上下文協定（Model Context Protocol, MCP）** 伺服器（MCP Servers）與相關工具。此層的弱點包括命令注入（Command Injection）、過度權限、混淆副手問題（Confused Deputy）以及工具濫用（Tool Abuse），這些缺陷往往無法以正規表示式或特徵碼（Signature）完整表達。因此採用 **LLM 驅動的領域稽核員（LLM as a Domain Auditor）**，透過 **代理式框架（Agentic Harness）** 對 MCP 伺服器與代理技能套件（Agent-Skill Packages）進行語意層級的安全分析。此處引入 **Prompt-as-Rule（提示即規則）** 的概念，將稽核邏輯以自然語言提示編寫，並輔以上下文管理（Context Management）與模型路由（Model Routing），依任務難度與成本把請求導向不同的大型語言模型（Large Language Model, LLM）。同時，框架也處理靜態分析（Static Analysis）與動態執行（Dynamic Execution）的取捨，並設計防護機制以避免 **保護掃描器免受自身輸入影響（Defending the Scanner Against Its Own Inputs）**。

3. **代理行為層（Agent Behavior Layer）**：此層的弱點只有在執行期（Runtime）才能顯現，例如目標劫持（Goal Hijacking）、系統提示詞洩漏（System Prompt Leakage）、多輪對話中的工具濫用等。由於攻擊者僅能透過自然語言對話介面與代理互動，框架採用 **多輪黑箱代理紅隊演練（Multi-Turn Black-Box Agent Red Teaming）**。透過設計對抗式多輪對話（Adversarial Dialogue），逐步升級攻擊強度（Escalation）並控制評估成本（Cost Control）。研究將風險分為四大風險家族（Four Risk Families），並為每個家族設計對應的攻擊載荷（Payloads），以系統化地評估代理在真實互動情境下的行為安全性。

4. **模型層（Model Layer）**：針對語言模型（Language Models）本身的對齊（Alignment）問題，框架提供 **越獄攻擊框架（Jailbreak Harness）**，整合 26+ 種攻擊運算子（Attack Operators）與 16 個資料集（Datasets）。此層將越獄成功率視為關於模型對齊的統計問題，透過三種角色——攻擊者、目標模型與評判模型（Judge）——以及攻擊函式庫、目標資料集與評判機制三種要素，將攻擊成功（Attack Success）轉換為可跨模型、跨資料集比較的指標。

除了分層方法論，本研究亦試圖建立 **AI 代理安全評估理論（Theory of AI Agent Security Assessment）**，提出安全異質性（Security Heterogeneity）、證據類別（Evidence Classes）、證據充分性（Evidence Sufficiency）、分層攻擊面（Layered Attack Surface）與層適應性評估（Layer-Adaptive Assessment）等概念，強調不同層級的「發現」需要不同種類與強度的證據支撐。例如，基礎設施層的發現可由版本比對與設定檔直接證明；而模型層的越獄則需統計上的多次抽樣與評判模型共同確認。

在工程實作上，AI-Infra-Guard 採用 **集中式伺服器-代理部署（Centralized Server-Agent Deployment）**，並透過基於技能（Skill-Based）的分散式架構與可擴充外掛系統（Extensible Plugin System）整合生態系統。這使得評估流程可以模組化擴展，並支援 **通用評估流程（Common Assessment Workflow）** 貫穿四層，最終將各層結果統一為 **結構化發現（Structured Findings）**。

#### 實驗數據解讀

由於目前可取得的上下文主要為論文摘要、章節大綱與引言，完整的實驗表格、精確度/召回率曲線與統計檢定結果尚未公開，因此本節僅能針對已揭露的規模性指標與設計意涵進行解讀。

1. **規模性指標的意義**：框架宣稱涵蓋 75+ 個 AI 元件與 1,400+ 條漏洞規則，這代表基礎設施掃描（Infrastructure Scanning）層具備相當廣泛的開源 AI 基礎設施覆蓋率，超越傳統漏洞資料庫對新興 AI 元件的收錄速度。同時，越獄攻擊框架具備 26+ 種攻擊運算子與 16 個資料集，顯示模型層評估在攻擊變異度與測試場景多樣性上達到一定規模。這些數字本身並非效能指標，而是「可評估範圍」的代理指標（Proxy）。

2. **精確度分層（Precision Stratification）**：基礎設施層的規則並非單一信賴等級，而是依據比對強度進行分層。例如，精確版本比對與已知 CVE 的規則屬於高信心發現；僅依賴 Banner 或指紋推測的規則則屬於較低信心、需要人工確認的發現。這種分層有助於降低誤報（False Positive），並讓使用者優先處理高信賴度的風險。

3. **代理技能掃描（Agent Skills Scanning）的評估**：論文提到針對代理技能（Agent Skills）進行供應鏈稽核（Supply-Chain Auditing），並設有技能檢測基準（Benchmarking Skill Detection）。這是過去較少被系統化研究的領域。理想上，該基準應報告對惡意或脆弱技能成品（Skill Artifact）的偵測率、誤報率與分析時間，但具體數值仍需等待全文釋出。

4. **越獄成功率的跨資料集可比性**：模型層將攻擊成功（Attack Success）設計為可比較的衡量指標，這意味著框架可能採用統一的評判模型（Judge）對 16 個資料集進行標準化評分，從而讓不同模型、不同攻擊運算子之間的 ASR（Attack Success Rate）具備橫向比較意義。然而，評判模型本身的偏差（Judge Bias）與閾值選擇會顯著影響結果，論文應進一步說明評判模型的校準方式。

5. **成本控制的實驗意涵**：黑箱多輪測試與 LLM 稽核都涉及 API 呼叫成本。論文強調成本控管（Cost Control），暗示實驗設計中可能記錄了每次評估的 Token 消耗、回合數與發現數量之間的權衡。對於實務部署而言，「單位成本發現數」將是比純粹攻擊成功率更重要的效率指標。

6. **資料解讀的限制**：目前缺乏量化比較，例如與現有掃描器（Nuclei、OWASP ZAP）或越獄基準（HarmBench、AdvBench）的對照實驗，也缺乏誤報率、召回率、F1 分數等傳統資安指標。因此，現有數字主要說明框架的「廣度」，其「深度」與「準確度」仍需更多實證數據支持。

#### 與現有研究的比較

AI-Infra-Guard 的定位介於傳統網路安全工具與新興 AI 安全研究之間，試圖彌補兩者之間的缺口。

1. **相較於傳統資安工具**：傳統軟體組成分析（SCA）工具與網頁掃描器（Web Scanners）主要針對已知 CVE、注入漏洞與腳本攻擊設計。然而，AI 基礎設施具有三項特性使其難以被傳統工具覆蓋：(1) 元件過於新穎，既有指紋資料庫與漏洞資料庫缺乏簽章；(2) 版本慣例不規則，語意化版本比對邏輯失效；(3) 威脅模型轉移，最高風險不再是傳統注入，而是未授權運算存取、API 金鑰外洩、提示注入（Prompt Injection）與工具濫用。AI-Infra-Guard 透過自建的 AI 元件指紋庫、版本正規化與 AI 專屬漏洞規則，直接回應這些限制。

2. **相較於單一層級的 AI 紅隊演練**：現有研究多聚焦於單一層級，例如越獄攻擊基準（Jailbreak Benchmarks）專注模型層、MCP 安全工具專注協定/工具層、網路掃描器專注基礎設施層。本框架的獨特之處在於將四層整合於單一開源框架，並特別強調 **代理技能供應鏈稽核（Supply-Chain Auditing of Agent Skills）**，這是過去較少被系統化處理的攻擊面。

3. **相較於其他 LLM 驅動的安全稽核工具**：近年已有研究嘗試以 LLM 進行程式碼審查或漏洞發掘。AI-Infra-Guard 的差異在於將 LLM 定位為「領域稽核員」，並透過代理式框架、上下文管理與模型路由提升稽核的可靠性與成本效益。此外，透過 **Prompt-as-Rule** 的設計，稽核邏輯可以像傳統規則一樣被版本控制與社群共享。

4. **主要改進**：
   - 提出系統化的四層攻擊面分類與對應評估典範；
   - 將確定性規則、LLM 語意稽核、多輪行為紅隊與統計式越獄評估整合於同一工作流程；
   - 強調證據類別與證據充分性，使不同層級的發現具備可解釋的評估標準；
   - 提供可擴充外掛系統，降低社群貢獻新元件、新規則與新攻擊運算子的門檻。

5. **限制與潛在弱點**：
   - **LLM 稽核的隨機性與成本**：LLM 輸出具有機率性，可能產生誤報或遺漏語意複雜的弱點；同時大規模稽核成本高昂。
   - **規則維護負擔**：基礎設施層的 1,400+ 條規則需要持續更新以跟上快速演進的開源 AI 生態。
   - **黑箱測試的內部狀態不可見**：代理行為層僅能透過對話介面觀察輸出，無法直接檢視代理內部規劃（Planning）與記憶狀態，可能遺漏某些內部決策鏈漏洞。
   - **越獄評判模型的偏差**：統一評判模型可能對特定攻擊風格或語言產生系統性偏差，影響跨資料集可比性。
   - **完整性無法保證**：與所有紅隊工具一樣，框架只能證明存在弱點，無法證明系統完全安全。

#### 可重現性評估

可重現性（Reproducibility）是安全研究能否被社群採納與驗證的關鍵。AI-Infra-Guard 以開源形式釋出，具備良好的可重現性基礎，但仍需檢視以下面向：

1. **程式碼與規則的開放程度**：框架釋出原始碼、75+ 個 AI 元件的指紋、1,400+ 條漏洞規則、26+ 種越獄攻擊運算子與 16 個資料集的使用方式，這些都是重現評估結果的核心素材。若能進一步提供規則的編寫指南與版本控制歷史，將有助於社群審查與貢獻。

2. **LLM 稽核的再現挑戰**：代理式框架與 Prompt-as-Rule 的輸出高度依賴所使用的 LLM 版本、溫度參數（Temperature）、提示詞模板與上下文長度。論文應詳細記載：(a) 預設使用的模型名稱與版本（例如 GPT-4、Claude、Llama 等）；(b) 模型路由策略；(c) 提示詞完整內容；(d) 輸出解析與結構化發現的後處理邏輯。缺少這些資訊，不同研究者可能得到顯著不同的結果。

3. **資料集與模型權重**：越獄評估使用的 16 個資料集若為公開資料集（如 AdvBench、HarmBench、MT-Bench 等），則資料可取得性較高。若包含自製資料集，則需公開標註與授權資訊。至於模型權重，由於框架主要針對 API 模型或開源模型進行黑箱/白箱測試，通常不需要釋出目標模型權重；但若框架內建專屬的評判模型（Judge Model），則應釋出該模型權重或訓練資料，以確保評分標準可重現。

4. **目標環境與測試設定的再現**：基礎設施掃描與 MCP 伺服器稽核需要特定的目標環境（例如特定版本的 Ollama、Dify、MCP server）。論文應提供 Docker Compose、Vagrant 或 Terraform 等環境設定檔，以及預期輸出範例，讓其他研究者能夠重現相同的發現。

5. **評估腳本與 CI 流程**：為提升可重現性，建議框架提供端到端評估腳本、單元測試與持續整合（CI）流程，自動驗證規則解析、LLM 輸出結構化與越獄評分邏輯是否穩定。

6. **整體評估**：AI-Infra-Guard 在「開放原始碼」與「模組化設計」上已具備高可重現性潛力，但由於涉及 LLM 與黑箱目標，完全精確的位元級再現（Bit-Exact Reproduction）可能難以達成。未來若能建立標準化的評估配置檔（如 YAML/JSON 格式的掃描計畫與模型設定），將大幅提升跨研究團隊的比較能力。

#### 未來研究方向

AI-Infra-Guard 為多層代理紅隊演練建立了一個實用的基礎，但仍有多個值得延伸的研究方向：

1. **跨層攻擊鏈（Cross-Layer Attack Chaining）**：目前四層評估雖然整合於同一框架，但各層之間的發現仍可能獨立呈現。未來可研究如何自動將基礎設施層的暴露、協定/工具層的漏洞、代理行為層的目標劫持與模型層的越獄串聯成完整攻擊鏈，並評估其複合風險。

2. **自動化規則與提示生成（Automated Rule & Prompt Generation）**：利用 LLM 自動從元件更新日誌、原始碼變更與 CVE 描述中生成新的漏洞規則與 Prompt-as-Rule，以降低人工維護 1,400+ 條規則的負擔，並加速對新興 AI 元件的覆蓋。

3. **即時執行期監控與自適應紅隊（Runtime Monitoring & Adaptive Red Teaming）**：將目前的離線評估擴展為持續監控系統，並根據代理執行時的行為回饋動態調整攻擊策略，實現「即時紅隊演練」。

4. **標準化代理紅隊基準（Standardized Agent Red Teaming Benchmarks）**：建立涵蓋多輪對話、工具使用、記憶體操作與多代理協作的標準化測試集，並定義超越攻擊成功率（ASR）的綜合指標，例如任務完成度下降幅度、攻擊隱蔽性、評估成本與發現嚴重性加權分數。

5. **供應鏈完整性與最小權限（Supply-Chain Integrity & Least Privilege）**：除了偵測弱點，未來可研究代理技能（Agent Skills）與 MCP 伺服器的簽章驗證、沙箱執行（Sandboxed Execution）、工具權限最小化與動態授權機制，從防禦端降低攻擊面。

6. **專用小型稽核與評判模型（Specialized Small Models for Auditing & Judging）**：目前 LLM 稽核與越獄評判依賴大型通用模型，成本高昂。未來可針對 AI 安全領域微調較小的專用模型，以提升速度、降低成本並減少對商業 API 的依賴。

7. **多模態與多代理擴展（Multi-Modal & Multi-Agent Extensions）**：隨著 AI 代理開始處理圖像、音訊與程式碼執行，攻擊面將擴展至多模態輸入與多代理協作場景。未來可將框架擴展至視覺提示注入、多代理共謀攻擊（Collusion Attacks）等新型威脅。

8. **防禦導向的對齊強化（Defense-Oriented Alignment Hardening）**：將紅隊發現反向回饋至安全微調（Safety Fine-Tuning）、對齊訓練與系統提示強化，形成「發現—修復—驗證」的閉環流程，並評估修復後模型的攻擊抵抗力提升幅度。

9. **成本效益最佳化（Cost-Effectiveness Optimization）**：研究如何在有限的評估預算下，透過主動學習（Active Learning）或強化學習選擇最具潛力的攻擊運算子與對話策略，以最大化單位成本發現的弱點數量。

10. **社群驅動的威脅情報共享（Community-Driven Threat Intelligence）**：建立開放的規則、攻擊運算子與發現資料庫，並設計聲譽機制與自動驗證流程，讓 AI-Infra-Guard 成為 AI 安全社群協作的共享基礎設施。

## 論文問答

**Q1 [背景與動機]：近兩年出現了哪一類新型的網路暴露軟體，使得傳統資安工具難以應對？**

A：近兩年快速興起的是開源 AI 基礎設施，包括模型服務引擎（如 Ollama、vLLM、llama.cpp）、代理平台（如 Dify、LangFlow、Flowise）、工作流程引擎（如 ComfyUI）、機器學習基礎設施（如 MLflow、Kubeflow、Ray），以及實作模型上下文協定（MCP）的伺服器。這些元件經常由個人或小型團隊部署，並直接暴露於不受信任的網路中，卻缺乏對應的安全防護工具。由於它們出現的時間太短、版本號不規則，且威脅模型已從傳統注入漏洞轉向未授權運算存取、API 金鑰外洩、提示注入與工具濫用，因此傳統掃描器難以有效偵測其風險。

**Q2 [背景與動機]：為何傳統的漏洞資料庫與軟體組成分析工具無法有效覆蓋這些 AI 元件？**

A：第一，這些 AI 元件太新，既有的指紋辨識與漏洞資料庫在設計時尚未包含它們，因此缺乏對應的特徵碼。第二，它們常使用不規則的版本命名方式，例如建置編號、開發標籤、發布候選版或滾動式 latest 標籤，這會擊敗依賴語意化版本比較的軟體組成分析工具。第三，最關鍵的是威脅模型已經改變，最高風險不再是傳統的注入與腳本漏洞，而是未授權存取昂貴運算資源、設定錯誤導致的憑證洩漏、提示注入劫持代理目標，以及模型安全對齊被對抗提示侵蝕等問題。

**Q3 [背景與動機]：為什麼作者認為「單一偵測典範」無法解決 AI 代理的安全問題？**

A：因為 AI 代理的攻擊面是高度分層的，橫跨基礎設施層、協定/工具層、代理行為層與模型層，每一層的風險性質與所需證據都不同。基礎設施層的未授權存取可以透過確定性規則證明，但模型層的越獄無法用正規表示式判斷；MCP 伺服器的語意缺陷也無法單靠原始碼靜態特徵碼完整捕捉。因此必須針對每一層選擇最適合的偵測典範，才能建立有效的評估流程。

**Q4 [方法與創新]：AI-Infra-Guard 的核心方法是什麼？它如何對應到四個攻擊面分層？**

A：核心方法是「層-典範匹配原則」（layer-paradigm matching principle），即為每一層攻擊面配對最適合的偵測典範。在基礎設施層，使用確定性規則匹配，涵蓋 75 個以上 AI 元件與 1,400 條以上漏洞規則；在協定/工具層，使用由 LLM 驅動的代理式稽核來審查 MCP 伺服器與代理技能套件；在代理行為層，採用多輪黑箱紅隊演練；在模型層，則使用包含 26 種以上攻擊運算子、橫跨 16 個資料集的越獄攻擊框架。這種分層設計讓不同性質的弱點都能被適當的證據形式所捕捉。

**Q5 [方法與創新]：本文聲稱的主要創新之一——對代理技能（agent skills）進行供應鏈稽核——為何重要？**

A：代理技能是擴展 AI 代理能力的外掛或套件，已成為 AI 軟體供應鏈中新的攻擊面，但過去缺乏針對這一層的開源安全稽核工具。AI-Infra-Guard 透過代理式技能分析管線與受控語意安全分析，能夠在技能成品被整合進代理之前發現潛在風險。據作者所知，這是首個開源框架同時涵蓋基礎設施、MCP 協定、代理行為、模型對齊以及代理技能供應鏈的完整紅隊演練方案。

**Q6 [方法與創新]：為什麼基礎設施層使用確定性規則，而 MCP 伺服器與代理技能卻需要 LLM 驅動的稽核？**

A：基礎設施層的弱點多為設定錯誤、未授權介面或已知漏洞，這些問題可以透過精確的指紋辨識與規則比對產生低誤報的證據，因此適合確定性規則。相對地，MCP 伺服器與代理技能的缺陷往往是語意層面的，例如命令注入、權限提升或混淆副手問題，這些弱點無法用單純的特徵碼或正規表示式表達。LLM 作為領域稽核員，能夠理解程式碼與工具描述中的語意風險，並透過 Prompt-as-Rule 與代理式框架產出結構化發現。

**Q7 [實驗與結果]：基礎設施掃描層的規模與設計優勢為何？**

A：基礎設施掃描層涵蓋超過 75 個開源 AI 元件與 1,400 條漏洞規則，並透過匹配引擎進行指紋辨識與規則比對。其設計採用精確度分層（precision stratification）來區分不同可信度的發現，並對結果進行評分，以降低誤報並優先處理高風險項目。由於規則是確定性的，這一層能夠提供可驗證、可重現的證據，特別適合快速盤點大規模部署的 AI 基礎設施。

**Q8 [實驗與結果]：MCP 伺服器稽核如何將 LLM 的自由文字輸出轉化為可操作的結構化發現？**

A：MCP 伺服器稽核使用代理式框架（agentic harness）讓 LLM 扮演領域稽核員，主動探索 MCP 伺服器的工具、參數與執行語境。系統透過上下文管理與模型路由控制稽核過程，並將 LLM 產生的自由文字分析轉換為結構化發現，例如弱點類型、影響範圍與利用條件。為了提升可靠性，設計上還包含防止掃描器被自身輸入污染、靜態與動態分析互補，以及工程化措施來穩定 LLM 稽核結果。

**Q9 [實驗與結果]：代理紅隊演練與越獄評估層分別如何衡量風險，並使用哪些評估資源？**

A：代理紅隊演練採用多輪黑箱對話，因為許多代理行為弱點只有在執行時期、透過連續互動才會顯現，並針對四類風險家族設計攻擊載荷，同時控制成本與對話輪數。越獄評估層則將模型對齊視為統計問題，使用 26 種以上攻擊運算子與 16 個資料集，透過可比的攻擊成功率來衡量不同模型的安全對齊程度。兩者都強調可驗證、可重複且具成本效益的測試，讓組織能夠量化代理與模型的實際風險。

**Q10 [應用與影響]：企業或研究團隊可以如何在實務中部署 AI-Infra-Guard？**

A：首先，可使用基礎設施掃描盤點內部部署的模型服務引擎、代理平台與 ML 流程工具，找出未授權存取或設定錯誤。其次，在引入第三方 MCP 伺服器或代理技能套件之前，可透過 LLM 驅動的稽核與技能掃描進行供應鏈安全檢查。最後，針對已上線的 AI 代理與模型，可定期執行多輪黑箱紅隊演練與越獄評估，以持續監控行為層與模型層的對齊狀態。

**Q11 [應用與影響]：AI-Infra-Guard 的系統架構與擴充性設計如何支援實際產品整合？**

A：系統採用集中式伺服器-代理部署架構，便於在分散式環境中大規模執行掃描與稽核任務。同時，它支援基於技能（skill-based）的分發與生態系統整合，並提供可擴充的外掛系統，讓社群能夠新增元件指紋、漏洞規則、攻擊運算子或評估資料集。這些設計使 AI-Infra-Guard 能夠嵌入 CI/CD 流程或持續監控系統，隨著 AI 生態系快速演進而擴展。

**Q12 [應用與影響]：將 AI-Infra-Guard 開源釋出對 AI 安全領域可能帶來什麼影響？**

A：開源釋出讓「層-典範匹配」從理論原則轉化為可實際運作的安全基礎，降低研究人員與安全團隊進行多層代理紅隊演練的門檻。它提供了一個統一的共享基礎，讓社群能夠共同擴充規則、資料集與偵測能力，避免每個團隊重複造輪子。隨著 AI 基礎設施的成長速度持續超越傳統安全工具，這樣的開源框架有助於建立跨層評估的標準與最佳實踐。

**Q13 [限制與未來]：作者可能承認哪些方法上的限制？**

A：確定性規則雖然精確，但對於尚未被收錄指紋的全新 AI 元件或零日弱點可能無法偵測。LLM 驅動的稽核雖具語意理解能力，但仍可能出現幻覺、不一致或成本高昂的問題，需要額外的工程化措施來確保可靠性。黑箱紅隊演練與越獄評估本質上是基於統計與抽樣的測試，無法保證發現所有弱點，也無法證明模型在所有對抗輸入下都安全。

**Q14 [限制與未來]：在哪些情況下，層-典範匹配原則可能不足以發現真實風險？**

A：當攻擊橫跨多層並形成複合式攻擊鏈時，例如先利用基礎設施層的未授權存取，再透過 MCP 工具層的語意漏洞，最終誘導代理行為層執行惡意操作，單層獨立評估可能難以捕捉整體風險。此外，若 MCP 伺服器在強化沙箱中執行，靜態或動態稽核可能無法觀察到真實的運行時行為；而對話輪數或成本限制也可能使多輪紅隊演練無法觸發深層的行為弱點。這些情況顯示，未來需要更強的跨層關聯分析與更長期的互動測試能力。

**Q15 [限制與未來]：未來可以朝哪些方向延伸 AI-Infra-Guard？**

A：未來可以持續擴充 AI 元件指紋庫與漏洞規則，以跟上快速演變的開源 AI 生態。另一方面，可進一步提升 LLM 稽核員的可靠性、降低成本，並發展自動化修復建議與風險緩解流程。此外，跨層關聯分析、複合攻擊鏈偵測，以及建立更多社群共享的基準測試與資料集，都是讓這個統一框架更具實用價值的重要方向。

## 適用場景

1. **企業內部 AI 基礎設施盤點與風險健檢**  
   當組織內部已部署 Ollama、vLLM、Dify、ComfyUI、MLflow、Kubeflow、Ray 等開源 AI 元件，卻不清楚哪些服務暴露於外網、版本是否存在已知弱點、API 金鑰是否外洩時，可使用 AI-Infra-Guard 的基礎設施掃描層進行快速盤點，產出元件清單與風險分數。

2. **MCP 伺服器與工具的上架前安全稽核**  
   在將第三方或內部開發的 MCP 伺服器、代理技能套件（agent-skill packages）正式接入代理平台前，透過 LLM 驅動的 MCP Server Auditing 與 Agent Skills Scanning，自動檢查命令注入、權限過大、機敏資料外洩、供應鏈污染等無法用傳統特徵碼表達的缺陷。

3. **AI 代理產品的多輪紅隊演練**  
   針對已上線的客服代理、程式輔助代理、資料分析代理等，使用 AI Agent Red Teaming 進行黑箱多輪對話測試，驗證代理是否會在持續引導下洩漏系統提示、濫用工具、繞過授權或執行非預期操作。

4. **模型選型與對齊性評估**  
   在導入新基座模型或微調模型前，利用 Jailbreak Evaluation 層的 26+ 攻擊運算子與 16 個資料集，對不同模型進行可比較的越獄成功率測試，作為模型上線或採購的客觀安全指標。

5. **AI 軟體供應鏈持續監控**  
   將 AI-Infra-Guard 整合至 CI/CD 或資安營運流程，對新引入的 AI 元件、MCP 工具、代理技能進行自動化掃描，建立從基礎設施、協定/工具、代理行為到模型層的縱深監控。

## 實作前置條件

- **資料準備**
  - 目標環境的網路可達性清單（IP、埠號、網域名稱）。
  - 待測 MCP 伺服器或代理技能套件的原始碼、設定檔、套件描述（如 `package.json`、`pyproject.toml`、README）。
  - 待測 AI 代理的對話介面（API endpoint、認證方式、速率限制）。
  - 越獄評估所需的目標模型 API 金鑰與存取配額。

- **運算資源**
  - 基礎設施掃描：一般伺服器或筆電即可，視掃描範圍調整執行緒數。
  - MCP 與技能稽核：需可呼叫外部 LLM（如 OpenAI、Anthropic、本地 vLLM），建議預留足夠 token 配額與快取空間。
  - 代理紅隊演練：需能持續呼叫目標代理 API，並記錄多輪對話；建議設定成本上限與執行時間上限。
  - 越獄評估：需同時執行攻擊模型、目標模型與評判模型（judge），建議具備 GPU 或足夠的商業 API 配額。

- **技能與人員**
  - 熟悉 Python 與命令列操作，能閱讀與修改 YAML/JSON 規則。
  - 具備基礎網路安全知識（HTTP、API、常見設定弱點）。
  - 理解 LLM 提示工程與代理運作原理，以便解讀 LLM 稽核結果。
  - 具備紅隊測試倫理與授權流程認知，避免在未授權環境執行測試。

## 實作步驟建議

1. **環境部署與權限確認**  
   從開源專案取得 AI-Infra-Guard，依文件完成 centralized server-agent 部署或本機安裝。確認已獲得目標環境書面授權，並劃定測試範圍與緊急聯絡窗口。

2. **建立資產清單**  
   使用基礎設施掃描層對目標網段進行被動與主動探測，識別 75+ AI 元件的指紋，建立包含元件名稱、版本、暴露面、認證狀態的資產清單。

3. **執行基礎設施弱點掃描**  
   針對清單中的元件套用 1,400+ 漏洞規則，特別關注未授權存取、API 金鑰外洩、預設憑證、過時版本等高風險項目；依精確度分層（precision stratification）優先處理高置信度發現。

4. **MCP 伺服器與代理技能稽核**  
   將待測 MCP 伺服器與技能套件接入 agentic harness，設定領域稽核員角色與模型路由策略。執行靜態與動態分析，將 LLM 輸出的自由文字轉為結構化發現，並人工複核高風險項目。

5. **代理行為層紅隊測試**  
   針對目標代理設計多輪對話劇本，涵蓋提示洩漏、工具濫用、權限繞過、目標劫持等四大風險家族。設定每輪成本與對話長度上限，記錄完整對話軌跡與成功條件。

6. **模型層越獄評估**  
   選定目標模型與 16 個資料集中的相關子集，套用 26+ 攻擊運算子產生變體提示。透過 judge 模型判定攻擊成功與否，計算 ASR（Attack Success Rate）並與其他模型比較。

7. **整合發現與持續改善**  
   將四層結果彙整為統一風險報告，標註證據類別與充分性。把掃描流程接入 CI/CD 或排程任務，並依新出現的 AI 元件、MCP 工具與攻擊手法持續更新規則與提示。

## 潛在風險與注意事項

- **誤報與誤判**  
  基礎設施規則可能因非標準版本命名（如 `b7824`、`2.3.dev`、`latest`）產生誤判，應參考版本正規化（version normalization）機制並人工確認。LLM 稽核與越獄評判也可能出現假陽性，建議保留原始對話或程式碼片段作為證據。

- **掃描器被惡意輸入污染**  
  MCP 與技能稽核過程中，掃描器本身會處理不可信程式碼與提示。應在隔離容器或沙箱中執行動態分析，限制網路 outbound，並對 LLM 輸出進行輸入驗證與結構化約束。

- **成本與速率限制失控**  
  多輪紅隊與越獄評估可能消耗大量 API 配額。務必設定單次評估成本上限、並行數上限與超時機制，並在離峰時段執行大規模測試。

- **法律與倫理風險**  
  未經授權掃描他人系統可能觸法。所有測試應在書面授權範圍內進行，對涉及武器、惡意程式、個資等敏感主題的越獄資料集應進行內部審查與去識別化處理。

- **模型對齊評估的侷限**  
  越獄成功率受 judge 模型、溫度參數、資料集選擇影響，單一數字不足以代表模型安全性。建議固定實驗設定並進行跨模型、跨時間的比較，而非僅看絕對 ASR。

## 與其他技術的整合建議

- **CI/CD 與軟體供應鏈安全**  
  將 Agent Skills Scanning 與 MCP Server Auditing 接入 GitHub Actions、GitLab CI 或 Tekton，在 PR 階段掃描新引入的 AI 技能與工具；並與 SBOM 工具（如 Syft、Grype）互補，填補傳統 SCA 對 AI 元件版本比對與行為弱點的不足。

- **漏洞與資產管理系統**  
  基礎設施掃描結果可透過標準化 JSON/SARIF 匯出，匯入 Jira、ServiceNow、DefectDojo 或自製資安儀表板，實現弱點追蹤與修復生命週期管理。

- **LLM 閘道與可觀測性平台**  
  將 AI Agent Red Teaming 與越獄評估發現轉為 LLM 防火牆（如 Lakera、Prompt Security、自研閘道）的阻擋規則或警示特徵；並與 Langfuse、LangSmith、OpenTelemetry 等可觀測工具整合，強化線上代理行為監控。

- **威脅情資與社群規則共享**  
  利用 AI-Infra-Guard 的可擴充外掛系統（extensible plugin system），持續同步社群新增的 AI 元件指紋、漏洞規則與攻擊運算子，形成組織內部與開源社群的雙向回饋迴路。

## 給不同背景讀者的閱讀建議

- **初學者**  
  建議先從第 1、3 章與第 5 章「基礎設施掃描」入手，理解 AI 攻擊面為何分層、以及規則匹配如何運作；接著實際部署工具掃描一個測試用的 Ollama 或 Dify 環境，再回頭閱讀第 4 章的理論概念，會更容易掌握「層-典範匹配」的核心思想。

- **研究人員**  
  第 4 章「邁向 AI 代理安全評估理論」與第 9 章「LLM 越獄評估」最值得深入，其中對安全異質性、證據類別、證據充分性與攻擊成功可比較性的討論，提供了進一步發展評估方法論的基礎；附錄中的攻擊運算子清單與偵測模式也可作為後續研究的實證起點。

- **產品經理**  
  建議優先閱讀摘要、第 1 章引言、第 3 章系統概述與第 11 章討論，掌握「為何需要分層防禦」與「各層分別解決什麼商業風險」；接著將第 8 章代理紅隊演練與第 9 章越獄評估轉化為產品上線前的安全閘道與合規報告，並參考「適用場景」規劃優先導入的客戶情境。
