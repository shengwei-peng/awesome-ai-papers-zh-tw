## 摘要翻譯

編碼代理（Coding Agents）可透過發現、清理與連接相關資料來回答資料湖（Data Lake）上的分析問題。然而，它們在每個問題後便捨棄這些工作，並為下一個問題從頭重做。工具演化（Tool Evolution）會跨任務自動建構並精煉可重複使用的工具，與這種重複性天然契合。由於資料湖問題的真實標籤（Ground-Truth Labels）需要專家先解答才能獲得，我們考慮非監督設定（Unsupervised Setting）。我們提出 TEAL（Tool Evolution for Analytics over data Lakes，資料湖分析的工具演化），它在沒有標籤的情況下，為給定的 Worker 代理（Worker Agent）演化一個工具函式庫（Tool Library）與使用技能（Usage Skills）。兩個代理從互補的證據中提出工具：Explorer 代理從資料湖本身提出，Critic 代理從 Worker 軌跡（Worker Trajectories）提出。一項被提出的變更只有在 Worker 於重跑（Rerun）時採用該工具（Tool Adoption）且不增加額外步數，且任何變更後的答案皆有軌跡證據（Trajectory Evidence）支持時，才會被保留。我們也介紹 TEAL-Q，當真實問題（Real Questions）不可得時，它會為工具演化生成合成問題（Synthetic Questions）。我們在 KramaBench 與 LakeQA 上，以四個 Worker 大語言模型（Worker LLMs）在步數預算（Step Budget）下進行評估，步數預算限制了 Worker 每題可採取的步數上限。在 10 或 15 步的嚴格預算下，TEAL 在兩個基準測試上都提升了所有 Worker 的表現，使 Sonnet-5 在 15 步時於 KramaBench 提升 9.3 分、於 LakeQA 提升 21.7 分。更嚴格的預算也會為演化產生更好的回饋訊號（Feedback Signal）。例如，Sonnet-5 在 20 步演化的 LakeQA 函式庫，於 30 步原樣部署時可得 68.3 分，高於基準（59.6）以及直接在 30 步演化的函式庫（64.2）。此外，在合成問題上演化的函式庫表現與在真實問題上演化的函式庫相當。這些結果顯示，有用的工具可在沒有標籤的情況下被演化，並期能啟發未來在非監督代理演化（Unsupervised Agent Evolution）中關於演化什麼以及如何取得回饋的研究。

### 核心貢獻（3～5點）
- 提出 TEAL 方法，在無真實標籤的非監督設定下，自動為 Worker 代理演化可重複使用的工具函式庫與使用技能，解決編碼代理跨任務重複勞動的浪費問題。
- 設計 Explorer 與 Critic 雙代理互補機制，分別從資料湖本身與 Worker 軌跡中提出工具候選，並以「重跑採用、不增步數、軌跡證據支持」三重條件嚴格篩選變更。
- 提出 TEAL-Q 合成問題生成方法，在真實問題不可得時仍可驅動工具演化，且實驗證明其效果與真實問題相當。
- 實驗驗證：在嚴格步數預算（10 或 15 步）下 TEAL 全面提升表現（Sonnet-5 於 15 步在 KramaBench +9.3 分、LakeQA +21.7 分），且更緊的預算能產生更佳的演化回饋訊號。

### 適合對象
從事資料湖分析、自動化資料整合、LLM 代理系統設計與工具學習（Tool Learning）研究的學者與工程師；以及對非監督式代理自我演化、自我演化本體（Self-Evolving Ontology）、合成資料驅動訓練等方向感興趣的研究者。亦適合關注如何降低資料分析系統中專家標註成本與提升代理可重用性之實務團隊參考。

## 深度分析

#### 方法論解析

TEAL（Tool Evolution for Analytics over data Lakes）的核心設計理念在於解決編碼代理（coding agents）在資料湖分析任務中重複勞動的問題。傳統的編碼代理在處理每個分析問題時，會從頭開始進行資料探索、清理與連接（join），即使面對的是同一個資料湖中的相似任務。這種「每次重來」的模式在步數預算（step budget）受限的情況下尤其致命，因為代理可能在尚未完成資料準備階段時就已耗盡步數。

**雙通道工具提案機制**

TEAL 採用兩個互補的代理來提案工具，這是整個框架最具巧思的設計：

1. **Explorer 代理**：從資料湖本身出發，不接觸任何問題或軌跡，模擬領域專家預先準備資料湖的過程。它會建立由預計算資料產物（precomputed data artifacts）支援的工具，例如目錄（catalog）、索引（index）以及清理過的表格。這類工具的本質是「將昂貴的一次性探索轉化為可重複呼叫的介面」，與資料庫系統中維護目錄與索引的設計哲學一致。

2. **Critic 代理**：從 Worker 代理的軌跡（trajectories）中尋找浪費步數或犯錯的位置，據此建立或修改工具。這類工具直接針對代理在實際任務中遇到的瓶頸，具有高度的針對性。

3. **Skill Writer 代理**：在每次工具變更後更新使用技能（usage skills），告訴 Worker 何時以及如何呼叫每個工具。這相當於在工具層之上提供一層「元指引」，避免代理面對陌生工具時無所適從。

**無標籤重跑驗證機制**

這是 TEAL 最關鍵的創新點。在資料湖分析任務中，取得真實標籤（ground-truth labels）需要專家親自完成探索、清理與連接的完整流程，成本極高。TEAL 提出了一套無需標籤的驗證流程：

- 提議的變更必須在重跑（rerun）時被 Worker 採用
- Worker 必須在不多花步數的情況下完成任務
- 若答案改變，必須有軌跡證據（trajectory evidence）支持新答案優於舊答案

這個設計巧妙地避開了「工具執行無錯誤即保留」的陷阱——因為一個工具可能執行流暢卻讀取了錯誤粒度（granularity）的表格、在解析時丟棄列、或以未對齊的鍵進行連接。重跑驗證透過觀察 Worker 是否主動採用新工具，以及新答案是否有軌跡支撐，來過濾這類「靜默錯誤」。

**TEAL-Q 合成問題生成**

當真實使用者問題稀缺時，TEAL-Q 從少量種子問題出發，先從相關檔案叢集中草擬問題，再透過多輪修訂強化問題，加入多表格連接等資料處理與推理需求，同時確保問題可回答。這使得 TEAL 能在缺乏真實問題的冷啟動場景下仍可運作。

**整體運作流程**

TEAL 的運作可分為離線演化與測試部署兩個階段。離線階段，Explorer 與 Critic 持續提案工具，Skill Writer 更新技能，每個變更都經過重跑驗證；測試階段，工具函式庫（tool library）被凍結並提供給 Worker 回答新問題。這種「演化—凍結—部署」的分離設計，使得演化過程可以消耗大量計算資源，而部署階段則保持輕量。

#### 實驗數據解讀

**基準測試與模型配置**

實驗在 KramaBench（Lai et al., 2026）與 LakeQA（Wang et al., 2026）兩個基準上進行，使用四種 Worker 大語言模型（Worker LLM）骨幹：Gemini-3.8-Flash、Gemini-3.1-Pro、Sonnet-5 與 Opus-4.8，並在不同的步數預算下進行評估。

**緊預算下的全面提升**

最顯著的結果出現在 10 步與 15 步的緊預算設定下：TEAL 在兩個基準上都提升了所有 Worker 的準確率。以 Sonnet-5 在 15 步預算下的表現為例，TEAL 在 KramaBench 上帶來 9.3 點的提升，在 LakeQA 上帶來 21.7 點的提升。這說明 TEAL 的價值在步數受限時最為突出——當代理沒有餘裕從頭探索時，預先演化好的工具能直接跳過耗時的準備步驟。

**與執行式工具演化的比較**

TEAL 同時優於 Li et al.（2026）提出的執行式工具演化方法。這驗證了 TEAL 的重跑驗證機制相較於單純「執行無錯誤即保留」的標準更為可靠，因為後者會保留那些執行流暢但語意錯誤的工具。

**緊預算演化的遷移性**

一個反直覺但極具實用價值的發現是：在更緊的預算下演化的函式庫，遷移到更寬鬆預算時表現反而更好。Sonnet-5 在 LakeQA 上以 20 步預算演化的函式庫，在 30 步部署時得分 68.3，不僅高於基線（59.6），也高於直接在 30 步下演化的函式庫（64.2）。這暗示緊預算提供了更強的演化回饋訊號（feedback signal）——當步數受限時，代理的失敗模式更為集中且明確，使 Critic 代理能更精準地識別需要工具介入的瓶頸。

**合成問題的有效性**

以 TEAL-Q 生成的 50 個合成問題進行演化，效果與使用真實問題相當。這大幅降低了 TEAL 的部署門檻，特別是在新資料湖缺乏歷史問題記錄的場景下。

**跨框架遷移**

在 OpenHands 框架下演化的函式庫可不經修改地遷移至 Google ADK、Codex CLI 與 Prime Agent，最高帶來 16.3 點的提升。這證明 TEAL 演化出的工具具有框架無關性，其價值在於工具本身的語意與功能，而非與特定代理架構的耦合。

**無監督驗證的可靠性**

TEAL 的無監督重跑驗證與使用真實標籤的oracle 驗證表現相當。這是論文最有力的實證之一：它證明了在缺乏標籤的情況下，純粹基於軌跡證據的驗證已足以篩選出具實用價值的工具。

#### 與現有研究的比較

**與資料庫系統的關係**

TEAL 的設計哲學與傳統資料庫系統高度一致：資料庫透過維護目錄、索引與視圖（view）來避免重複掃描原始資料，TEAL 則透過演化可重複使用的工具來避免代理重複進行探索與清理。然而，TEAL 並非取代資料庫系統，而是為缺乏預先建立目錄的資料湖提供自動化的「目錄建構」能力。

**與 EvoOntology 的比較**

EvoOntology（Chong et al., 2026）同樣讓代理建構資料湖之上的資源層，但其精煉過程依賴保留標籤的驗證分數提升。TEAL 的關鍵差異在於完全擺脫對標籤的依賴，這在資料湖分析場景中具有重要意義，因為標籤獲取成本極高。

**與 DataCOPE 的比較**

DataCOPE（Qiu et al., 2026）同樣在無標籤設定下發現技能，但其技能是程序性指引（procedural guidance），而非由持久產物支援的可呼叫工具。TEAL 的工具則具備實際的執行能力，能直接讀取預計算的目錄或索引，這使得工具的價值不僅在於指引，更在於實際的計算節省。

**與程式碼工具生成器的比較**

現有的程式碼工具生成器（如 Li et al., 2026；Wang et al., 2024b）通常為單一任務生成工具，缺乏跨任務的累積設計。TEAL 的工具函式庫則明確以「跨任務可重用」為目標，這使得演化過程中的每個工具決策都需考慮其在未來任務中的潛在價值。

**與監督式工具生成器的比較**

監督式工具生成器（Cai et al., 2024）依賴標籤驗證，在資料湖場景中成本過高。TEAL 的無監督驗證機制是其相對此類方法的核心優勢。

**限制與不足**

儘管 TEAL 表現優異，仍存在若干限制。首先，重跑驗證依賴 Worker 軌跡的穩定性，若 Worker 本身行為高度隨機，驗證訊號可能不夠可靠。其次，TEAL 的工具演化是離線的，無法在測試階段即時適應新出現的資料模式。第三，Explorer 與 Critic 的提案可能存在冗餘或衝突，目前缺乏明確的衝突解決機制。最後，雖然 TEAL-Q 生成的合成問題效果不錯，但合成問題與真實使用者問題的分布差異仍可能影響演化出的工具在真實場景中的適用性。

#### 可重現性評估

從論文提供的資訊來看，可重現性評估需要考量以下幾個面向：

**程式碼開源**

論文未明確聲明程式碼是否開源，但考慮到作者隸屬於 Google 且標註了實習身份，程式碼有可能隨論文發表一同釋出。TEAL 的核心元件（Explorer、Critic、Skill Writer、重跑驗證邏輯、TEAL-Q）若以模組化方式實作，則重現的工程難度中等。

**資料集可及性**

KramaBench 與 LakeQA 兩個基準測試均為公開資源（Lai et al., 2026；Wang et al., 2026），可從原始論文取得。資料湖的具體內容與結構需依據基準測試的設定進行配置。

**模型權重**

實驗使用的四種 Worker 模型（Gemini-3.8-Flash、Gemini-3.1-Pro、Sonnet-5、Opus-4.8）均為可透過 API 存取的商業模型，重現實驗需要相應的 API 存取權限與計算資源。

**超參數與設定**

論文提及步數預算（10、15、20、30 步）作為關鍵變數，但其他超參數（如 Explorer 與 Critic 的提案頻率、重跑驗證的接受閾值、TEAL-Q 的修訂輪數等）的具體設定未在提供的文本中詳細說明，這可能影響重現的精確度。

**跨框架遷移的驗證**

論文聲稱函式庫可從 OpenHands 遷移至 Google ADK、Codex CLI 與 Prime Agent，但這些框架的具體介面差異與遷移所需的適配工作在論文中未充分描述，這增加了獨立重現跨框架實驗的難度。

**整體可重現性判斷**

在現有資訊下，TEAL 的核心方法論可重現性中等偏上。基準測試與模型 API 均可取得，但完整的程式碼釋出、詳細的超參數設定以及跨框架適配細節仍需進一步確認。

#### 未來研究方向

**線上演化機制**

目前 TEAL 的演化是離線進行的，工具函式庫在測試階段被凍結。一個自然的方向是引入線上演化，使代理在處理新問題時能動態發現並新增工具，同時透過某種形式的回饋機制來驗證新工具的價值。這需要解決線上設定下的計算開銷與驗證延遲問題。

**更豐富的回饋訊號**

目前重跑驗證主要依賴「Worker 是否採用工具」與「答案是否有軌跡支持」兩個訊號。未來可探索更細粒度的回饋，例如工具呼叫的時機是否恰當、工具輸出是否被正確解讀、以及工具組合使用時的相容性等。

**多代理協作演化**

TEAL 目前只有 Explorer 與 Critic 兩個提案代理，且兩者獨立運作。未來可引入更複雜的多代理協作機制，例如讓代理之間互相評估提案品質，或透過辯論機制來篩選工具。

**工具泛化與遷移學習**

雖然 TEAL 證明了函式庫可在不同代理框架間遷移，但工具是否能跨資料湖遷移仍是開放問題。例如，在某個資料湖上演化出的「州別詐欺報告彙總」工具，能否應用於結構相似的另一個資料湖？這涉及工具抽象層次的設計。

**與人類專家的協作**

TEAL 完全自動化，但在實際部署中，人類專家的領域知識可能進一步提升工具品質。未來可探索人機協作的演化模式，例如讓專家對 Critic 的提案進行優先級排序，或對 Explorer 的探索方向進行引導。

**理論分析**

目前 TEAL 的有效性主要透過實驗驗證，缺乏理論層面的分析。例如，何時演化會收斂？演化函式庫的大小是否存在最優值？步數預算與演化效果之間的函數關係是什麼？這些問題的理論回答將有助於指導 TEAL 的實際部署。

**安全與可靠性**

自動演化的工具可能引入安全風險，例如執行任意程式碼或洩漏敏感資料。未來需要研究工具演化的安全邊界，例如透過沙箱執行、權限限制或形式化驗證來確保演化過程的安全性。

**長期記憶與經驗累積**

TEAL 的演化是針對特定資料湖的，未考慮跨資料湖的經驗累積。一個更宏觀的願景是建立代理的「長期記憶」，使其在處理多個資料湖的過程中累積通用的工具設計模式與領域知識，這將是通往更通用代理的重要一步。

## 論文問答

**Q1：為什麼資料湖分析中的編碼代理需要工具演化？**
A：編碼代理在回答資料湖問題時，需要進行資料探索、清理與整合等大量重複性工作，但每次問題結束後這些工作成果（如解析器、結構檢查、連接腳本）都會被丟棄。當下一個類似問題出現時，代理必須從頭重做相同的探索與清理，這在嚴格的步數預算下往往會失敗。工具演化能將這些重複步驟封裝成可重複呼叫的工具，並附帶使用技能，讓代理以單次呼叫取代逐步探索，從而緩解重複勞動的問題。

**Q2：現有的工具生成方法為何無法直接應用於資料湖分析？**
A：現有方法存在兩個主要瓶頸：第一，目錄與本體格式儲存的是描述性元資料，而非用於清理與查詢的可執行工具；第二，程式碼工具生成器只為當前任務建立工具，而非能在多個問題中持續發揮效益的產物。更關鍵的是，監督式工具生成器與自我演化本體仰賴真實標籤來驗證工具品質，但在資料湖分析中取得標籤成本極高，因為驗證單一答案需要專家人工探索、清理並連接底層資料集，這使得監督式方法在實務上難以規模化。

**Q3：為什麼僅以「執行無錯誤」作為工具驗證標準在資料湖中不可靠？**
A：一個工具即使執行成功，仍可能存在邏輯錯誤：在錯誤的表格粒度上讀取資料、在解析過程中遺漏列、或以未對齊的鍵進行表格連接。這些錯誤不會觸發執行階段錯誤，但會產生錯誤的答案。因此 TEAL 採用重跑驗證機制，要求 Worker 在更新後的工具函式庫下重跑問題，且必須採用新工具、不增加步數，且任何答案變更都必須由軌跡證據支持新答案優於舊答案，從而避免單純依賴執行成功所帶來的誤判風險。

**Q4：TEAL 框架的核心設計理念是什麼？**
A：TEAL 的核心設計是讓兩個代理從互補的證據來源提出工具變更：Explorer 代理從資料湖本身出發，不看任何問題或軌跡，建立領域專家會為資料湖準備的工具，例如由預計算目錄或清理過的表格支援的搜尋與查找工具；Critic 代理則檢視 Worker 在訓練問題上的軌跡，找出 Worker 浪費步驟或犯錯的地方，並據此建立或修訂工具。Skill Writer 代理則更新使用技能以反映每項已實作的變更，使工具函式庫與引導文件保持同步。

**Q5：TEAL 如何在沒有真實標籤的情況下驗證工具變更？**
A：TEAL 採用重跑驗證階段：對於每個被提出的工具變更，TEAL 會在促使該變更的問題上以更新後的工具函式庫重跑 Worker。變更只有在三個條件同時滿足時才會被保留：Worker 確實採用了變更的工具、Worker 仍能在不增加步數的情況下完成任務、且若答案改變，軌跡證據支持新答案優於舊答案。這種設計巧妙地將「工具是否有用」轉化為可觀察的行為證據，避免了對真實標籤的依賴。

**Q6：TEAL-Q 合成問題生成機制如何運作？**
A：當資料湖缺乏真實使用者問題時，TEAL-Q 能以少量種子問題作為示範來生成可用於工具演化的問題。其流程分為兩階段：首先從一組相關檔案叢集中草擬問題，接著透過多輪修訂來強化問題，加入資料處理與推理需求（例如多表格連接），同時確保問題可被回答。這使得即使在沒有真實問題的冷啟動情境下，仍能進行有意義的工具演化，並讓演化出的函式庫在真實問題上表現相當。

**Q7：TEAL 在哪些基準測試上進行評估，使用了哪些 Worker 模型？**
A：TEAL 在 KramaBench 與 LakeQA 兩個資料湖分析基準測試上進行評估，並使用四種 Worker 大語言模型作為骨幹：Gemini-3.8-Flash、Gemini-3.1-Pro、Sonnet-5 與 Opus-4.8。評估在不同的步數預算下進行，步數預算限制了 Worker 每個問題所能採取的最大步數，以模擬真實環境中資源受限的情境，並測試 TEAL 在不同模型與不同嚴苛程度下的泛化能力。

**Q8：TEAL 在緊縮步數預算下的主要實驗結果為何？**
A：在 10 步與 15 步的緊縮預算下，TEAL 在兩個基準測試上都提升了所有 Worker 的準確率。以 Sonnet-5 在 15 步預算下的表現為例，其在 KramaBench 上提升 9.3 點，在 LakeQA 上提升 21.7 點，且優於僅以執行成功作為驗證的工具演化方法。這顯示 TEAL 在資源受限的情境下特別有價值，因為它將重複的探索與清理工作封裝為可重用的工具，讓 Worker 能將有限的步數預算花在真正的分析推理上。

**Q9：步數預算的選擇如何影響工具演化的效果？**
A：一個關鍵發現是：在更緊縮的預算下演化的工具函式庫能轉移到更寬鬆的預算。例如，Sonnet-5 在 LakeQA 上以 20 步預算演化的函式庫，在 30 步預算下部署時得分 68.3，高於基線（59.6）以及直接在 30 步下演化的函式庫（64.2）。這表明更緊縮的預算能提供更好的回饋訊號，因為在嚴格限制下 Worker 更容易暴露其瓶頸，從而讓 Critic 代理能更精準地識別需要工具支援的步驟。

**Q10：TEAL 在實際部署中如何支援跨平台遷移？**
A：TEAL 演化的工具函式庫具有跨環境的可移植性：在 OpenHands 框架中演化的函式庫可不經修改地遷移至 Google ADK、Codex CLI 與 Prime Agent 等其他代理框架，並提升準確率達 16.3 點。這意味著企業可以在其偏好的代理基礎設施上部署 TEAL 演化的工具，而無需重新演化，這對於多平台環境下的實務部署具有重要意義，也降低了工具資產被鎖定在特定框架的風險。

**Q11：TEAL 對資料工程實務有何潛在影響？**
A：TEAL 將資料庫系統中目錄、索引、視圖等概念延伸到編碼代理領域，使代理能像資料庫系統一樣避免重複掃描原始資料。對資料工程師而言，這代表可以將耗時的探索與清理工作自動化，並隨著時間累積可重用的工具資產。此外，TEAL-Q 降低了對真實問題的依賴，使新資料湖在缺乏歷史查詢記錄時仍能受益於工具演化，這對於企業資料資產的長期治理具有實務價值。

**Q12：TEAL 的非監督特性對產品化有何意義？**
A：由於 TEAL 不需要真實標籤，它大幅降低了在企業環境中部署的門檻，因為企業通常不會有標註過的分析問題資料集。其重跑驗證機制也避免了對人類專家持續介入的需求，使得工具演化可以離線批次執行。此外，合成問題與真實問題在演化效果上表現相當，這意味著產品可以在缺乏真實使用資料的冷啟動階段使用 TEAL-Q 來啟動工具演化，縮短價值實現的時間。

**Q13：TEAL 的主要限制為何？**
A：TEAL 的限制之一在於其重跑驗證機制仰賴軌跡證據來判斷答案變更的合理性，這在某些情況下可能無法完全取代真實標籤的精確性。此外，TEAL 假設 Worker 代理在演化過程中是固定的，這意味著若更換底層模型，可能需要重新演化工具函式庫。雖然函式庫可跨框架遷移，但跨模型的遷移性尚未在論文中充分探討，這是產品化時需要考量的因素。

**Q14：TEAL 在哪些情境下可能會失敗？**
A：當資料湖中的資料品質極差或結構高度異質時，Explorer 代理可能難以建立可靠的目錄或查找工具。此外，若 Worker 的軌跡本身充滿錯誤（例如選擇錯誤的檔案粒度），Critic 代理可能會基於這些錯誤軌跡提出不當的工具變更。雖然重跑驗證能過濾部分此類問題，但對於需要深層領域知識才能判斷的複雜分析問題，純粹的軌跡證據可能不足以支持正確的答案變更，這是 TEAL 仍需人類專家介入的環節。

**Q15：TEAL 未來的研究方向為何？**
A：論文指出未來工作應探索「演化什麼」與「如何取得回饋」這兩個核心問題。具體方向包括：將工具演化擴展到更廣泛的代理任務（不限於資料湖分析）、研究更精緻的回饋訊號設計（例如結合人類偏好或弱監督訊號）、以及探索跨模型、跨領域的工具函式庫遷移性。此外，如何讓演化出的工具函式庫能持續適應資料湖的動態變化（例如新增檔案或結構改變），也是值得探索的方向，這將使 TEAL 從一次性離線演化邁向持續線上學習。

## 實務應用指南

### 適用場景

1. **政府開放資料分析平台**：城市或國家級開放資料入口網站通常累積數千份異質 CSV/JSON 檔案（人口、犯罪、交通、健保等），缺乏統一目錄。導入 TEAL 後，Explorer 代理可預先建立「依主題／年份／地理粒度」的搜尋工具與清理後的產物表，讓市民或分析師用自然語言提問（例如「哪個都會區佔該州詐欺檢舉比例最高」），無需手動翻找檔案。

2. **企業內部資料湖問答系統**：金融、電商、零售業的內部資料湖常混合交易紀錄、客戶檔案、第三方報表。TEAL 可在離線階段讓 Critic 代理觀察分析師（或先前的 Worker）軌跡，找出反覆出現的解析、連接、聚合瓶頸，自動產出可重用的工具（例如「跨報表統一幣別與日期格式」「客戶 ID 模糊匹配合併」），部署後供 BI 團隊或合規稽核人員查詢。

3. **學術研究資料整合**：社會科學、生命科學領域的研究者常需橫跨多個公開資料集（普查、健保、基因資料庫）做交叉分析。TEAL-Q 可在缺乏真實提問時，從檔案叢集自動合成研究問題（如「某基因表現量與社經指標的相關性」），並演化出對應的整合工具，協助研究助理快速產出可重現的分析流程。

4. **SaaS 客戶成功與資料 onboarding**：B2B SaaS 廠商在新客戶導入時，客戶的原始資料格式各異。TEAL 可在試運行階段讓 Worker 嘗試回答典型 onboarding 問題（如「本月活躍用戶數」「流失率」），由 Critic 觀察失敗軌跡並演化出該客戶專屬的清理與彙總工具，縮短上線時間。

5. **邊緣運算與離線分析代理**：在無法即時呼叫雲端 LLM 的場景（如現場稽核、災後調查），可先用 TEAL 在雲端離線演化出精簡的工具函式庫，再部署到邊緣裝置，讓小型 Worker 模型在嚴格步數預算下也能完成資料探索。

### 實作前置條件

**資料面**
- 一個具代表性的資料湖快照（檔案系統層級即可，無需預先建立 catalog 或 schema），規模建議從數百到數萬個檔案起步，以驗證工具泛化性。
- 一組「種子問題」用於 TEAL-Q 合成或 Critic 軌跡收集；即使只有 5–10 題真實問題也能啟動流程。
- 評估用的 hold-out 問題集（建議 ≥ 50 題）以量測演化後函式庫的實際效益。

**運算面**
- 至少一個具備 bash shell 與檔案編輯器介面的 coding agent 框架（論文中使用 OpenHands，亦可換成 Google ADK、Codex CLI、Prime Agent）。
- 三類 LLM 角色：Worker（執行問答）、Explorer 與 Critic（提議工具）、Skill Writer（更新使用技能）。可使用同一個底層模型分飾多角，但建議 Explorer/Critic 使用較強模型（如 Sonnet-5、Opus-4.8 等），Worker 可使用較小模型以節省成本。
- 足夠的磁碟空間儲存預計算產物（catalog、清理後表格、索引），以及可重現的執行環境（容器化建議）。

**技能面**
- 熟悉 LLM agent 框架的 tool/skill 註冊機制，理解 trajectory 紀錄格式。
- 具備資料工程基礎：能撰寫與審核 Python/pandas 腳本、SQL 查詢、檔案 I/O。
- 具備基本的 prompt engineering 能力，特別是設計 Explorer 與 Critic 的工具提議 prompt。
- 建議配置一位領域專家擔任「軌跡審閱者」，定期抽樣檢查被採納的工具是否真的合理（即使沒有 ground-truth 標籤）。

### 實作步驟建議

1. **界定範圍與基線**：選定一個資料湖子集與一組 Worker 候選模型，先在無工具狀態下用 10/15/20/30 步預算各跑一輪 hold-out 問題，記錄準確率、平均步數、失敗模式，作為後續比較的基準線。

2. **建立 Explorer 通道**：讓 Explorer 代理在不看任何問題與軌跡的情況下巡覽資料湖，產出「領域專家會準備的工具」——例如檔案搜尋、依 metadata 篩選、預先清理並儲存為 parquet 的高頻使用表格。建議將產物版本化（hash + 時間戳），方便後續重跑驗證。

3. **收集 Worker 軌跡**：用步數預算偏緊的設定（例如 10 或 15 步）讓 Worker 在訓練問題上作答，完整記錄每一步的指令、輸出、錯誤。偏緊預算能放大失敗訊號，是論文中觀察到的關鍵經驗法則。

4. **建立 Critic 通道**：將軌跡餵給 Critic 代理，要求它找出「重複發生」「耗費多步」「容易出錯」的模式，並提議新工具或修訂既有工具（例如把 5 步手動解析濃縮成單一 `parse_state_csv(path)` 呼叫）。

5. **Skill Writer 更新使用技能**：每當工具集合改動，讓 Skill Writer 重寫對應的 usage skill（簡短的自然語言說明 + 呼叫範例），確保 Worker 在新問題上知道何時該用哪個工具。

6. **重跑驗證（rerun verification）**：對每個被提議的改動，在「觸發該改動的問題」上重跑 Worker，採納條件為三項皆成立：(a) Worker 真的呼叫了新/修訂的工具；(b) 完成步數未增加；(c) 若答案改變，新答案必須有軌跡證據支持（例如引用了正確的表格列、計算式可重現）。任一條件不符則退回該改動。

7. **（選擇性）合成問題補強**：若真實問題不足，啟動 TEAL-Q：先以少量種子問題為示範，從檔案叢集草擬問題，經多輪修訂加入多表連接、聚合、推理需求，並驗證可作答。論文中 50 題合成問題已能達到接近真實問題的演化效果。

8. **跨預算與跨框架遷移**：先在緊預算下演化函式庫，再凍結部署到較寬鬆預算的環境；同樣地，在 OpenHands 演化的函式庫可直接匯入 Google ADK、Codex CLI、Prime Agent，無需重新訓練。

9. **建立監控與退場機制**：上線後持續收集新軌跡，定期（例如每週）讓 Critic 重新審視並提議新工具；同時保留「無工具 baseline」與「前一版函式庫」以便 A/B 測試，發現退化時可一鍵回退。

10. **量化評估與報告**：以論文中 KramaBench、LakeQA 為範本，產出「模型 × 預算 × 函式庫版本」三維準確率表，並附上工具採用率、平均步數變化、答案變更率等診斷指標，向利害關係人溝通效益。

### 潛在風險與注意事項

- **「執行成功 ≠ 邏輯正確」的陷阱**：未經驗證的工具可能乾淨執行卻讀錯表格粒度、解析時丟列、用未對齊的鍵做連接。務必啟用 rerun verification 的「軌跡證據支持」條件，並由領域專家定期抽樣審閱，不要只靠 runtime error 來把關。

- **過度擬合到訓練問題**：Critic 容易針對訓練軌跡中的特定錯誤「過度修正」，導致工具在 hold-out 問題上反而失效。務必保留獨立的 hold-out 集做驗證，並限制單次演化的改動幅度（可採滾動式小批次更新）。

- **預計算產物的一致性與新鮮度**：Explorer 產出的 catalog、清理後表格若與原始檔案不同步，會在資料更新後產生靜默錯誤。建議建立產物版本控制與失效偵測（hash 比對、檔案 mtime 監控），並在 Worker 軌跡中暴露產物版本以便除錯。

- **步數預算選擇的雙刃效應**：過緊的預算雖然提供更好的演化回饋，但 Worker 在演化階段本身可能大量失敗，導致 Critic 看到的軌跡樣本偏差。建議同時跑兩個預算（例如 10 步與 20 步）並比較演化結果。

- **合成問題的偏誤**：TEAL-Q 生成的問題可能過度集中在容易回答的檔案叢集，無法代表真實使用者多樣性。應在合成階段刻意引入多表連接、跨主題推理等需求，並定期用真實問題抽測。

- **跨框架遷移的介面相容性**：不同 agent 框架的工具呼叫格式、錯誤回傳結構、檔案路徑慣例不同。建議在工具層做一層薄包裝（adapter），讓同一份函式庫可在多框架間重用，避免重複演化。

- **成本與延遲**：Explorer 巡覽大型資料湖、Critic 反覆審視長軌跡都會消耗大量 token。建議對資料湖做分區處理、對軌跡做摘要後再餵給 Critic，並設置單次演化的預算上限。

- **安全與資料外洩**：工具若允許任意 bash 呼叫，可能被 prompt injection 誘導執行危險指令。務必在沙箱環境執行、限制檔案系統存取範圍、對輸出做敏感資料遮罩。

---

### 與其他技術的整合建議

- **與傳統資料庫系統整合**：將 TEAL 演化的工具包裝成 SQL 函數或 stored procedure，讓 BI 工具（Tableau、Looker、Power BI）也能呼叫；同時把 Explorer 產出的 catalog 同步到資料湖的 metastore（Glue、Hive Metastore），形成「LLM 工具 + 傳統目錄」的雙軌架構。

- **與 RAG 與語意搜尋整合**：Explorer 的檔案搜尋工具可改為呼叫既有的向量索引（Vertex AI Search、Elasticsearch、pgvector），讓工具同時支援關鍵字與語意查詢；Critic 則可從 RAG 檢索結果的引用段落中萃取證據，補強 rerun verification。

- **與 workflow orchestration 整合**：把 TEAL 的離線演化流程包裝成 Airflow、Dagster 或 Prefect 的排程任務，定期重跑；上線後的工具呼叫則可透過 API gateway 統一收費、限流、稽核。

- **與 MLOps / AgentOps 整合**：將 Worker 軌跡、工具版本、評估指標接入既有的 experiment tracking 系統（MLflow、W&B），方便跨模型、跨預算做比較；同時把工具函式庫納入 model registry，與模型版本綁定部署。

- **與本體與語意層整合**：若組織已採用語意層（dbt semantic layer、LookML、Ontology），可讓 TEAL 從既有本體讀取欄位定義與業務術語，產出與之對齊的工具與 skill，減少「同一概念多種說法」的歧義。

- **與人類專家回饋整合**：在 rerun verification 之外，開放一個輕量介面讓領域專家對「答案變更」做標註（接受/退回/修正），把這些標註回流到 Critic 的 prompt 或 fine-tuning 資料，逐步從純非監督走向弱監督。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節的「分析師提問詐欺檢舉比例」範例，建立「coding agent 在資料湖上重複做相同清理工作」的直覺；接著看圖 1（若有）的系統總覽，了解 Explorer、Critic、Worker 三者如何分工；最後跳到實驗結果的「緊預算下每個模型都進步」這張表，感受 TEAL 的實際效益，再回頭讀方法細節。

**給 AI 工程師**：重點放在第 3 節的方法細節，特別是 rerun verification 的三條件（工具被採用、步數不增、答案變更有證據）如何實作為程式碼；以及 TEAL-Q 的合成問題修訂流程如何寫成 prompt pipeline。實作時建議先用論文的 KramaBench 或 LakeQA 子集重現 10 步預算的實驗，再逐步替換成自家資料湖。

**給研究者**：第 4 節的消融實驗（緊預算 vs 寬預算、合成 vs 真實問題、跨框架遷移）是本文最值得深挖的部分，特別是「緊預算提供更好回饋訊號」這個反直覺發現；可進一步探索的方向包括：不同資料湖結構下的演化效率、Critic 的偏差分析、與 self-evolving ontology（EvoOntology）的理論比較，以及在多輪對話或多人協作場景下的延伸。

**給產品經理**：把 TEAL 視為「讓 AI 員工越用越聰明的內部機制」而非單一功能；關鍵決策點在於 (1) 願意投入多少離線運算來演化工具、(2) 接受多大的答案變動率、(3) 如何向使用者溝通「AI 正在學習你的資料」。建議先以單一高頻使用場景（例如客服資料查詢）做 POC，量化「平均完成步數下降」「人工介入率下降」等商業指標，再評估擴張到全資料湖的 ROI。
