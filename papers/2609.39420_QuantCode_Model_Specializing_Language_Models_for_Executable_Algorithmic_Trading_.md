## 摘要翻譯

大型語言模型（Large Language Models, LLM）雖是強大的通用程式碼生成器，但可執行的演算法交易（executable algorithmic trading）仍是一個極具挑戰性的專精化目標：模型必須將自然語言策略規格（natural-language strategy specification）轉譯為適用於專門交易框架（trading framework）的正確程式邏輯（program logic），在歷史資料（historical data）上執行、產生交易，並對需求保持語意忠實度（semantic faithfulness）。本研究探討兩種在此情境下專精化語言模型（specialized language model）的互補機制（complementary mechanisms）：在演算法交易框架程式碼（algorithmic-trading framework code）上進行持續預訓練（continued pretraining），以及針對代理驗證的需求到程式碼配對（agent-validated request-to-code pairs）進行監督式微調（Supervised Fine-Tuning, SFT）。評測以 QuantCode-Bench 基準測試為核心，這是我們提出的 400 題 Backtrader 策略生成（Backtrader strategy generation）基準測試，並輔以一個倉庫級 SWE-bench 式評測軌道（repository-level SWE-bench-like track）。持續預訓練使 Qwen3.5-397B-A17B 在單輪設定（single-turn setting）下的評審通過率（Judge Pass）從 41.5% 提升至 47.5%，並使 Qwen3.6-35B-A3B 從 27.8% 提升至 33.0%。在持續預訓練後應用 SFT，對 Qwen3.6-35B-A3B 帶來更顯著的提升，達到 58.2% 的 Judge Pass 與 83.5% 的成功回測率（successful backtests）；在代理式評估（agentic evaluation）中，首輪成功率（first-turn success）從 22.3% 提升至 58.3%，最多 10 輪後最終成功率（final success after up to 10 turns）從 47.5% 提升至 79.5%。單獨持續預訓練雖可提升代理式評估的首輪成功率，卻使經最多 10 輪修復後的最終成功率從 47.5% 降至 32.5%，此現象與指令遵循能力退化一致；而 SFT 則同時改善兩者。我們亦發現一種能力保留失效（capability-retention failure）：領域專精化會損害符合解析器的結構化工具呼叫（parser-conformant structured tool calling），而針對性恢復型監督式微調（targeted recovery SFT）能恢復工具呼叫格式（tool-call formatting），但無法恢復基礎檢查點（base checkpoint）的倉庫級代理表現（repository-level agent performance）。結果顯示，面向框架的預訓練（framework-oriented pretraining）、經驗證的監督式微調（validated SFT），以及明確的能力保留評估，能夠有效處理領域特定可執行程式碼生成中的不同失效模式。

### 核心貢獻（3～5點）
- 提出 QuantCode 模型，結合持續預訓練與監督式微調（SFT），使 LLM 專精於可執行的 Backtrader 演算法交易策略生成。
- 建立 QuantCode-Bench：400 題 Backtrader 策略生成基準測試，並設計倉庫級 SWE-bench 式評測軌道，涵蓋單輪與多輪代理式評估。
- 發現持續預訓練可提升單輪生成表現，但可能損害指令遵循與多輪修復能力；後續 SFT 可同時提升首輪與最終成功率。
- 識別能力保留失效：領域專精化會退化結構化工具呼叫格式，並驗證針對性恢復型 SFT 可恢復格式但無法完全恢復倉庫級代理表現。
- 驗證面向框架的預訓練、經驗證的 SFT 與明確的能力保留評估可各司其職，解決領域特定可執行程式碼生成的不同失效模式。

### 適合對象
對演算法交易、程式碼生成、領域適應與能力保留有興趣的研究者與工程師；特別適合從事金融量化策略自動化、LLM 專精化、代理式程式碼生成，以及軟體工程基準測試的讀者。

## 深度分析

#### 方法論解析

本研究的核心目標是將通用大型語言模型（LLM）專精化為能夠生成**可執行的演算法交易程式碼（executable algorithmic trading code）**的模型。與一般程式碼生成不同，此任務要求模型把自然語言策略規格（natural-language strategy specification）轉譯成特定交易框架（trading framework）——此處為 Backtrader——可執行的策略程式碼，並在歷史資料（historical data）上完成回測、產生交易訊號，且語意忠實度（semantic faithfulness）必須與使用者需求一致。為此，作者提出兩個互補機制（complementary mechanisms）：**持續預訓練（continued pretraining）**與**監督式微調（SFT）**，並在 QuantCode-Bench 基準測試（QuantCode-Bench）上進行單輪（single-turn）與多輪代理式評估（agentic evaluation）。

**持續預訓練（continued pretraining）**的訓練資料鎖定演算法交易框架程式碼（algorithmic-trading framework code）與相關儲存庫，目的在於提升模型對領域 API、生命週期方法（如 Backtrader 的 `__init__`、`next`、`notify_order`）、指標組合、訂單處理與框架慣例的熟悉度。這個階段並不直接學習「自然語言需求 → 程式碼」的對應，而是讓模型吸收領域程式碼的分布與語法模式，因此可視為**面向框架的預訓練（framework-oriented pretraining）**。

**監督式微調（SFT）**則使用**代理驗證的需求到程式碼配對（agent-validated request-to-code pairs）**，直接學習如何將真實使用者需求對應到符合框架規範的策略實作。這些配對並非單純人工標註，而是經過執行管線驗證：程式碼必須語法正確、能在回測環境初始化、成功執行、至少產生一筆交易，並通過 LLM 語意評審（semantic judge）。因此 SFT 的目標是強化**指令到程式碼的對齊（instruction-to-code alignment）**。

實驗設計採用可比的序列訓練血統（sequential training lineages）：Qwen3.6-35B-A3B 從基礎檢查點（base checkpoint）出發，依序經過持續預訓練與 SFT；Qwen3.5-397B-A17B 則比較其基礎檢查點與領域預訓練後檢查點。這樣的設計讓研究者能區分兩個階段各自貢獻的能力變化。

評估分為三個層次。第一層是 **QuantCode-Bench** 的 400 題 Backtrader 策略生成任務，採用分段式執行管線：語法正確 → 成功回測 → 產生交易 → LLM 語意評審通過。第二層是**代理式評估（agentic evaluation）**，模型最多可進行 10 輪（multi-turn）修正，根據結構化工具回饋（如執行錯誤、評審意見）迭代修補程式碼。第三層是**倉庫級 SWE-bench 式評測軌道（repository-level SWE-bench-like track）**，要求模型在真實演算法交易儲存庫中閱讀 issue、生成 patch、執行測試並根據工具回饋修復，測試領域能力是否能從單一策略檔案轉移到長程軟體工程任務。

此外，作者特別關注**能力保留失效（capability-retention failure）**：領域專精化可能損害模型原本具備的結構化工具呼叫（structured tool calling）格式。為此，他們評估權重合併（weight merging）與針對性恢復型監督式微調（targeted recovery SFT）兩種恢復策略，區分「解析器可解析的格式恢復」與「下游工具使用品質恢復」。

#### 實驗數據解讀

實驗結果清楚顯示持續預訓練與 SFT 各自作用於不同的失效環節。

在**單輪設定（single-turn setting）**下，持續預訓練對**評審通過率（Judge Pass）**帶來穩定但中等的提升：Qwen3.5-397B-A17B 從 41.5% 提升至 47.5%，Qwen3.6-35B-A3B 從 27.8% 提升至 33.0%。這說明讓模型多看演算法交易框架程式碼，確實能改善其對 Backtrader API 與領域慣例的掌握，使生成程式碼更貼近可執行的領域實作。然而，這種提升僅限於「程式碼看起來像正確的策略」，並未顯著改善需求語意對齊。

相較之下，在持續預訓練後接續 SFT，對 Qwen3.6-35B-A3B 產生更大幅度的進步：**Judge Pass 達到 58.2%**，**成功回測率（successful backtests）達到 83.5%**。這表示 SFT 不僅提升語意忠實度，也同時改善執行可行性與交易產生率。原因在於 SFT 的每個樣本都是經過執行管線驗證的「需求 → 程式碼」映射，模型因此學會如何把自然語言中的進場條件、出場條件、部位規模、停損邏輯與時間限制轉譯成正確的 Backtrader 實作。

在**代理式評估（agentic evaluation）**中，這種差異更加明顯。SFT 模型首輪成功率（first-turn success）從 22.3% 躍升至 58.3%，最多 10 輪後最終成功率（final success after up to 10 turns）從 47.5% 提升至 79.5%。這顯示 SFT 同時強化了初始生成品質與在回饋下持續修正的能力。

值得注意的是，單獨的持續預訓練在代理式評估中呈現矛盾現象：它提升了首輪成功率，卻把最多 10 輪後的最終成功率從基礎檢查點的 47.5% 降低到 32.5%。作者將此解釋為**指令遵循能力（instruction following）退化**：持續預訓練讓模型更熟悉領域程式碼分布，卻可能削弱其處理對話式回饋與遵循高階指令的能力。SFT 則能同時修復這個問題，顯示兩個階段確實互補——一個補強領域知識，一個補強對齊與互動能力。

另一個關鍵發現是**能力保留失效（capability-retention failure）**：領域專精化後，模型輸出的結構化工具呼叫格式不再符合解析器要求。透過權重合併或針對性恢復型 SFT，可以恢復**符合解析器的結構化工具呼叫（parser-conformant structured tool calling）**格式，但卻無法恢復基礎檢查點原本的**倉庫級代理表現（repository-level agent performance）**。這意味著工具呼叫格式的恢復只是表面，深層的工具使用推理與長程規劃能力在領域專精化過程中受到了更難逆轉的影響，也凸顯 QuantCode-Bench 本身並未直接測量這項能力。

至於倉庫級 SWE-bench 式軌道的具體數據，摘要與已披露內文並未提供詳細數字，因此難以判斷領域專精化對長程軟體工程任務的實際影響幅度。

#### 與現有研究的比較

本研究在幾個層面上與現有文獻形成對照。

在**領域適應預訓練（domain-adaptive pretraining）**與**以程式碼為中心的預訓練（code-centric pretraining）**方面，Code Llama、StarCoder2、DeepSeek-Coder 等模型證明語料組成對程式能力有顯著影響，但它們通常專精於廣泛的程式語言或儲存庫層級分布。本研究則進一步縮小目標分布，聚焦演算法交易框架的原始碼與使用模式，強調的不只是「會寫 Python」，而是「能在特定框架上執行並產生正確交易行為」。

在**程式碼生成評測**方面，傳統基準如 HumanEval、MBPP 主要關注語法正確性、單元測試通過率或 pass@k。QuantCode-Bench 則引入分段式執行管線，把評估從「能否編譯」推進到「能否執行回測」、「能否產生交易」以及「是否符合語意需求」。這與強調行為正確性（behavioral correctness）的軟體工程評測方向一致，但更聚焦金融領域的語意忠實度。

在**長程代理式工程**方面，近期技術報告如 GLM-5 與 Qwen3 都強調從靜態編碼轉向長期代理任務。本研究的倉庫級 SWE-bench 式軌道呼應此趨勢，但將其應用於演算法交易儲存庫，測試領域專精化是否能轉移到真實程式碼庫的 issue 修復。

本研究的主要貢獻在於**在同一模型血統中區分持續預訓練與 SFT 的效應**。許多先前研究只探討其中一種專精化方式，或將兩者混為一談。本文清楚展示：持續預訓練改善領域程式碼熟悉度，但可能損害指令遵循；SFT 改善需求對齊與代理表現；兩者結合才能達到最佳效果。此外，對能力保留失效的討論也填補了既有程式碼專精化研究較少觸及的部署面向。

然而，本研究也存在若干限制。首先，評測僅針對 Backtrader 單一交易框架，未能驗證對 Zipline、QuantConnect LEAN、vectorbt 等其他框架的泛化能力。其次，LLM 語意評審（semantic judge）本身可能帶有偏誤或對複雜策略的判斷不一致。第三，SFT 資料雖經代理驗證，但每個樣本仍是靜態的最終程式碼，未包含多輪修正軌跡，因此無法直接學習迭代修復策略。最後，領域專精化對通用能力的負面影響——特別是倉庫級代理表現——顯示專精化與能力保留之間的權衡仍需更深入探討。

#### 可重現性評估

根據目前提供的摘要與前兩節內文，本研究尚未明確說明原始碼、資料集或模型權重的釋出方式。要讓其他研究者能夠重現這些結果，至少需要以下幾項資產：

1. **QuantCode-Bench 的完整任務與執行管線**：包含 400 題自然語言策略規格、Backtrader 回測環境設定、歷史資料來源、語法檢查與交易產生判定邏輯。
2. **LLM 語意評審（semantic judge）的提示詞與評分標準**：由於 Judge Pass 是核心指標，評審用的提示詞、模型版本與評分規則必須公開，才能確保不同研究間的可比性。
3. **持續預訓練語料**：演算法交易框架程式碼與相關儲存庫的來源、篩選方式、去重與 token 化流程，以及訓練超參數（學習率、步數、批次大小等）。
4. **SFT 資料集**：代理驗證的需求到程式碼配對，包含原始需求、最終通過驗證的程式碼，以及驗證過程中使用的代理設定。
5. **訓練後的檢查點**：基礎檢查點、持續預訓練檢查點、SFT 檢查點，以及恢復型 SFT 檢查點，並附帶模型授權與使用條款。
6. **代理式評估與倉庫級評測的實作細節**：工具呼叫格式、回饋機制、最多 10 輪的停止條件，以及 SWE-bench 式軌道的儲存庫選擇與測試執行方式。

在這些資訊尚未公開前，本研究的重現性主要限於概念層面與部分數據趨勢的參照。若作者後續釋出上述資產，將大幅提升本工作在領域專精化 LLM 研究中的影響力與可驗證性。

#### 未來研究方向

基於本研究的發現，以下幾個方向值得進一步探索：

1. **多框架泛化**：將專精化方法擴展到 Zipline、QuantConnect LEAN、vectorbt、 pandas-ta 等其他演算法交易框架，測試模型是否能跨框架轉移領域知識，或需要為每個框架獨立訓練。
2. **強化學習與執行回饋**：目前 SFT 使用靜態的代理驗證配對。未來可引入強化學習（RL）或直接偏好最佳化（DPO），以回測結果、交易品質指標與語意評審分數作為獎勵訊號，直接優化可執行策略的生成。
3. **迭代修復軌跡學習**：將多輪代理式評估中的成功與失敗軌跡納入訓練，讓模型學習如何根據工具回饋進行針對性修復，而不只是模仿最終正確答案。
4. **能力保留與災難性遺忘緩解**：研究如何在領域專精化過程中保留通用代理能力與結構化工具呼叫品質，例如透過多工混合訓練、彈性權重鞏固（elastic weight consolidation）、LoRA 轉接器或權重合併策略。
5. **更嚴謹的語意評審**：開發更穩健的 LLM 評審機制，結合人工驗證、對抗性測試與細粒度評分維度（如進場條件正確性、出場條件正確性、部位規模邏輯），降低評審偏誤。
6. **真實交易與風險指標**：將評估從回測成功延伸到真實交易成本、滑價（slippage）、夏普比率、最大回撤等風險調整後指標，讓生成的策略不僅可執行，更具實務價值。
7. **倉庫級任務擴充與公開**：建立並釋出更大規模的演算法交易 SWE-bench 式資料集，涵蓋更多真實儲存庫、issue 類型與測試案例，作為長程領域軟體工程能力的標準評測。
8. **領域預訓練與 SFT 的規模法則**：系統性研究領域語料大小、SFT 樣本數量與模型規模對 Judge Pass、成功回測率與能力保留的影響，以指導未來的資料收集與訓練預算分配。
9. **跨語言策略規格**：探討模型是否能處理中文、日文、德文等非英文的自然語言策略規格，並維持相同的可執行生成品質。

## 論文問答

**Q1：可執行的演算法交易程式碼生成相比一般程式碼生成，挑戰為何更為嚴峻？**
A：演算法交易要求模型將自然語言策略規格轉譯為特定交易框架（如 Backtrader）的正確程式邏輯，這不僅涉及語法正確性，還必須處理指標計算、進出場條件、部位規模、停損邏輯與風險管理規則等多種語意細節。模型必須熟悉框架的生命週期方法、資料依賴關係、訂單處理機制與執行語意，否則程式可能在執行階段初始化失敗、無法產生交易，或實作出與需求不符的策略。相較於一般 Python 程式設計，這種領域專精化失敗無法僅靠通用程式能力彌補，因為錯誤往往只在回測執行時才會顯現。

**Q2：為何僅靠文本相似度或編譯正確性不足以評估交易策略程式碼？**
A：交易策略程式碼是一種可執行產物，其正確性取決於執行階段行為、狀態轉換以及與使用者意圖的語意對齊，而非僅是語法或表面文字。一份程式碼可能完全通過編譯，卻因為指標資料依賴錯誤而永遠無法觸發進場條件；也可能成功執行並產生交易，但實際上實作的是另一種策略。因此 QuantCode-Bench 採用分階段可執行管線，結合 LLM 語意評審，才能同時檢驗語法、執行、交易產生與語意忠實度。

**Q3：為何不能僅依賴通用大型語言模型，而需要針對演算法交易領域進行專精化？**
A：通用大型語言模型雖然具備廣泛的程式生成能力，但對於特定框架的慣例、抽象層級與執行語意可能缺乏深入理解，導致在 Backtrader 等專業框架上出現系統性失敗。演算法交易策略涉及許多領域特定概念，例如 K 棒狀態管理、指標串接、訂單追蹤與回測生命週期，這些知識無法單靠通用預訓練資料充分覆蓋。透過持續預訓練與監督式微調進行領域專精化，能夠讓模型學習框架原始碼型態與需求到程式碼的對應關係，從而提升可執行策略的生成品質。

**Q4：本研究提出的兩種互補機制各是什麼，分別針對哪些能力？**
A：第一種機制是面向框架的持續預訓練，讓基礎模型接觸演算法交易框架程式碼與使用模式，主要提升模型對領域 API、生命週期方法與框架慣例的熟悉度。第二種機制是監督式微調，使用經過代理驗證的需求到程式碼配對作為訓練資料，直接優化自然語言請求與可執行程式碼之間的對齊。這兩種機制相輔相成：持續預訓練教會模型「領域程式碼長什麼樣子」，而 SFT 則教會模型「如何根據使用者需求產出正確實作」。

**Q5：QuantCode 模型的核心創新為何？**
A：QuantCode 模型的核心創新在於結合了框架導向的持續預訓練與執行環境驗證的監督式微調，並以行為導向的 QuantCode-Bench 作為統一評測基準。不同於僅追求文本或語法正確性的程式生成研究，本研究強調程式必須能夠在 Backtrader 框架中執行、產生交易，並且語意上忠實於原始策略規格。此外，研究還納入倉庫級 SWE-bench 式評測軌道與能力保留分析，從多個層面檢驗領域專精化對模型整體能力的影響。

**Q6：為何持續預訓練與 SFT 在本研究中不能被視為可互相替代的方法？**
A：持續預訓練雖然能提升模型對領域程式碼分佈的熟悉度，但它並未直接優化從自然語言請求到正確程式碼的映射關係，因此對於指令遵循與語意對齊的幫助有限。相對地，SFT 雖然能提供直接的需求到程式碼對應範例，但這些示範是靜態目標，並未包含多輪修復的軌跡，因此無法完全取代預訓練所建立的領域知識基礎。實驗結果也顯示，單獨進行持續預訓練會提升首輪代理成功率，卻會降低最終修復成功率，這進一步證明兩者針對的是不同的失敗模式。

**Q7：QuantCode-Bench 如何設計以評估生成的 Backtrader 策略？**
A：QuantCode-Bench 包含 400 個以自然語言描述的交易策略任務，並透過分階段可執行管線評估生成結果。評測流程依序檢驗程式碼語法正確性、是否能在回測環境成功初始化與執行、是否至少產生一筆交易，以及是否通過 LLM 語意評審以確認與原始需求一致。該基準同時支援單輪設定與多輪代理式設定，後者允許模型根據結構化工具回饋在最多 10 輪內修復程式碼，從而更全面地評估模型的迭代改進能力。

**Q8：實驗中的關鍵量化結果有哪些？**
A：在單輪 Judge Pass 指標上，持續預訓練將 Qwen3.5-397B-A17B 從 41.5% 提升至 47.5%，將 Qwen3.6-35B-A3B 從 27.8% 提升至 33.0%。接續進行 SFT 後，Qwen3.6-35B-A3B 的 Judge Pass 大幅躍升至 58.2%，成功回測率達到 83.5%。在代理式評估中，SFT 模型首輪成功率從 22.3% 提升至 58.3%，最多 10 輪後的最終成功率從 47.5% 提升至 79.5%，顯示 SFT 對於可執行策略生成與迭代修復都有顯著助益。

**Q9：代理式評估揭示了持續預訓練與 SFT 的哪些不同影響？**
A：代理式評估顯示，持續預訓練雖然能提升首輪成功率，但卻會降低最終修復成功率，從基礎檢查點的 47.5% 下降至 32.5%，這顯示單純的領域預訓練可能損害了模型處理對話回饋與遵循指令的能力。相反地，SFT 不僅顯著提升首輪成功率，也同時改善最終成功率，代表它能同時強化初始生成品質與迭代修復能力。這項發現凸顯了在領域專精化過程中，必須同時關注單輪生成表現與多輪互動中的行為穩定性。

**Q10：QuantCode 模型在實際演算法交易開發中可應用於哪些場景？**
A：QuantCode 模型可協助量化交易團隊將自然語言策略構想快速轉換為可在 Backtrader 等框架執行的原型程式碼，縮短從策略設計到回測驗證的開發週期。對於需要頻繁迭代策略的基金或個人交易者，該模型能根據語意規格自動生成包含進出場條件、部位規模與風控邏輯的完整策略檔案。此外，在倉庫級維護情境中，模型也能協助修復既有交易程式碼庫中的問題，並根據測試回饋進行多輪修正。

**Q11：從能力保留失效的發現中，部署 QuantCode 模型時應考量哪些因素？**
A：研究發現領域專精化可能導致結構化工具呼叫格式退化，這對於需要與代理互動的部署環境是重要風險，因為解析器無法正確解析的輸出會中斷整個工作流程。雖然針對性恢復型 SFT 能夠修復工具呼叫的格式正確性，但無法完全恢復基礎檢查點在倉庫級代理任務上的表現，顯示某些能力的損失具有持續性。因此實際部署時，除了評估領域任務表現，也應建立明確的能力保留評測機制，並考慮採用權重合併或專屬恢復訓練等策略來維持通用代理能力。

**Q12：這項研究對 AI 輔助軟體工程領域可能帶來哪些更廣泛的影響？**
A：本研究強調了在專業領域中，程式碼正確性必須以可執行行為與語意忠實度來衡量，而非僅依賴語法或文本相似度，這對其他領域的 AI 輔助開發也具有參考價值。研究提出的分階段訓練管線與行為導向評測方法，可應用於其他需要框架專精化的軟體工程任務，例如資料科學管線、嵌入式系統或雲端基礎設施程式碼生成。此外，能力保留失效的發現提醒研究社群，在追求領域性能提升時，必須同時監控與維護模型的通用互動能力。

**Q13：本研究在資料與評測方面承認哪些限制？**
A：本研究的 SFT 資料雖然經過代理驗證，但每個示範仍是靜態的需求到程式碼配對，並未包含多輪修復的完整軌跡，因此可能無法充分訓練模型處理複雜迭代回饋的能力。QuantCode-Bench 目前聚焦於 Backtrader 框架，雖然這是 Python 演算法交易的主流工具之一，但結果是否能直接推廣到其他交易框架仍需進一步驗證。此外，倉庫級 SWE-bench 式評測軌道的規模與多樣性也可能有限，未來需要擴充更多真實程式碼庫與問題類型。

**Q14：能力保留失效為何是本研究的重要發現？**
A：能力保留失效顯示，針對 QuantCode-Bench 的領域專精化雖然提升了交易策略生成能力，卻同時損害了模型輸出符合解析器的結構化工具呼叫能力，這種退化會直接影響代理式系統的穩定性。更重要的是，即使透過針對性恢復型 SFT 修復了工具呼叫格式，模型在倉庫級代理任務上的表現仍未能回到基礎檢查點水準，顯示某些通用能力的損失難以簡單恢復。這項發現凸顯了在開發領域專精化模型時，必須將能力保留評估納入核心訓練與部署流程，而非僅關注目標領域的性能提升。

**Q15：未來研究可朝哪些方向改進領域專精化的可執行程式碼生成？**
A：未來研究可以探索結合強化學習或線上執行回饋的訓練方法，讓模型在生成程式碼後能根據實際回測結果進行更細緻的策略調整。另一個方向是擴充訓練資料，納入多輪修復軌跡與跨框架的程式碼範例，以同時提升初始生成品質與迭代修復能力。此外，發展更完善的能力保留訓練技術，例如更先進的權重合併方法或持續學習策略，將有助於在提升領域專精化的同時，維持模型在通用代理與倉庫級軟體工程任務上的表現。

## 實務應用指南

### 適用場景

1. **自然語言量化策略原型開發**  
   交易團隊可將以自然語言撰寫的策略規格（例如「當 20 日移動平均線突破 60 日移動平均線且 RSI < 70 時進場」）直接轉換為可執行的 Backtrader 策略程式碼，縮短從想法到回測的週期。

2. **既有演算法交易程式碼庫的維護與擴充**  
   適用於倉庫級（repository-level）任務，例如根據 GitHub issue 修復既有交易策略的 bug、重構過時 API 用法，或將舊版策略遷移至新版 Backtrader 框架。

3. **量化知識的結構化沉澱**  
   基金或自營交易團隊可將資深交易員的經驗法則轉為需求到程式碼配對，透過監督式微調（SFT）建立組織內部的策略生成助手，降低關鍵知識流失風險。

4. **多因子與複雜進出場邏輯自動化**  
   針對涉及多個技術指標、部位規模、停損停利、時間約束與風控規則的策略，模型可協助組裝正確的程式邏輯與狀態管理，減少人工實作時的遺漏。

5. **回測與執行框架的現代化遷移**  
   協助將傳統交易平台（如 MetaTrader、TradeStation）或自研回測腳本轉譯為 Python/Backtrader 生態系，並透過執行導向評測驗證語意忠實度。

**資料準備**
- 演算法交易框架程式碼語料：Backtrader 原始碼、官方範例、社群策略、文件與教學。
- 自然語言策略規格資料集：400 題以上涵蓋不同指標與邏輯的任務描述，並對應可執行的參考實作。
- 經代理驗證的需求到程式碼配對：需透過執行環境驗證語法正確性、回測成功性、交易產生與語意評審通過。
- 歷史資料：用於回測驗證的股票、期貨或加密貨幣歷史資料，並確保資料授權合規。

**運算資源**
- 基礎模型：建議使用 Qwen3.6-35B-A3B 或 Qwen3.5-397B-A17B 等 MoE 模型作為起點。
- 持續預訓練與 SFT：需配備多張高記憶體 GPU（如 A100/H100）與分散式訓練框架。
- 推論與評測基礎設施：需能批次執行生成程式碼、進行沙箱回測、執行 LLM 語意評審。

**技能組合**
- 熟悉大型語言模型訓練流程（持續預訓練、SFT、LoRA/全參數微調）。
- 具備 Backtrader 與 Python 量化交易實作經驗。
- 能設計執行導向評測管線與 LLM-based 語意評審 prompt。
- 具備 MLOps 與模型部署監控能力。

### 實作步驟建議

1. **建構領域預訓練語料庫**  
   收集 Backtrader 框架原始碼、策略範例、文件與真實倉庫程式碼，並進行去識別化與品質篩選。

2. **執行面向框架的持續預訓練**  
   在基礎檢查點上繼續預訓練，使模型熟悉交易框架的 API、生命週期方法、指標計算與訂單處理慣例。

3. **產生並驗證 SFT 訓練資料**  
   使用代理程式將自然語言策略規格轉為程式碼，並透過「語法 → 執行 → 產生交易 → 語意評審」四階段篩選，保留通過驗證的需求到程式碼配對。

4. **執行監督式微調**  
   在持續預訓練後的檢查點上進行 SFT，直接優化使用者請求到框架符合程式碼的對齊。

5. **建立執行導向評測管線**  
   參考 QuantCode-Bench 設計，依序檢驗：語法正確性、回測初始化成功、成功回測率、交易產生、Judge Pass（語意評審通過率）。

6. **進行代理式多輪評估**  
   讓模型接收結構化工具回饋並在最多 10 輪內修復，追蹤首輪成功率與最終成功率。

7. **評估並恢復能力保留**  
   檢查領域專精化是否造成結構化工具呼叫格式退化；若發生能力保留失效，可執行針對性恢復型 SFT 或權重合併。

8. **部署與持續監控**  
   將模型整合至內部策略開發平台，並持續監控生成程式碼的執行成功率、語意忠實度與工具呼叫解析成功率。

### 潛在風險與注意事項

- **持續預訓練可能損害指令遵循能力**  
  研究顯示，僅做持續預訓練會提升首輪代理成功率，但降低最多 10 輪後的最終成功率。建議務必接上 SFT 以恢復對話與修復能力。

- **結構化工具呼叫格式退化**  
  領域專精化可能破壞符合解析器的結構化工具呼叫。需在評測中加入 parser-conformant tool calling 檢查，並準備針對性恢復型 SFT。

- **過度擬合特定框架或 API 版本**  
  若訓練資料過度集中於 Backtrader，模型可能難以泛化到其他交易框架。建議保留部分多框架資料或明確限定應用範圍。

- **語意評審無法捕捉所有金融邏輯錯誤**  
  LLM-based Judge 可能遺漏細微的風控或部位計算錯誤。建議搭配單元測試、財務邏輯斷言與人工抽樣複核。

- **執行環境安全與相依性**  
  自動執行生成程式碼存在資安風險，應在沙箱環境中運行，並嚴格控管網路與檔案系統權限。

- **回測與實盤表現落差**  
  成功回測不代表實盤獲利。生成程式碼僅能作為研究原型，上線前仍需經過完整的盤前驗證與風控審查。

### 與其他技術的整合建議

- **與市場資料管線整合**  
  將模型輸出的策略程式碼直接對接歷史資料餵送系統（如 Bloomberg、Polygon、CCXT 或內部資料湖），實現自動化回測。

- **與風控與下單系統整合**  
  在策略生成後串接部位限制、停損檢查與訂單路由模組，確保生成程式碼不會繞過既有風控閘門。

- **與版本控制及 CI/CD 整合**  
  將生成的策略程式碼提交至 Git，並透過持續整合管線自動執行 QuantCode-Bench 風格的評測，確保每次變更都通過執行與語意檢驗。

- **與 IDE / 編輯器外掛整合**  
  開發 VS Code 或 Jupyter 擴充功能，讓交易員在編寫自然語言規格後，一鍵生成、執行與視覺化回測結果。

- **與 LLM 代理框架整合**  
  結合支援結構化工具呼叫的代理框架（如 LangChain、AutoGen、OpenAI Agents SDK），讓模型在多輪互動中接收回饋並修復程式碼。

- **與倉庫級軟體工程工具整合**  
  對於 SWE-bench 式任務，可串接程式碼檢索、靜態分析與單元測試工具，提升在真實交易程式碼庫上的修補能力。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦「為什麼需要專精化語言模型」這個核心問題：一般 LLM 雖然會寫 Python，但不一定懂 Backtrader 的框架慣例與執行語意。本文展示透過持續預訓練與 SFT，可以讓模型學會把自然語言策略規格變成真正可執行、會交易、且符合需求的程式碼。閱讀時可略過訓練細節，重點看適用場景與潛在風險。

**AI 工程師**  
本研究的重點在於兩階段訓練的交互作用：持續預訓練提升框架熟悉度，SFT 提升指令到程式碼的對齊，但領域專精化會帶來能力保留失效。建議仔細研究資料建構、驗證管線、QuantCode-Bench 的評測階段，以及恢復型 SFT 與權重合併的實驗設計，這些對實際落地極具參考價值。

**研究人員**  
本文的貢獻在於將「可執行的領域特定程式碼生成」拆解為多個層次的能力，並透過行為導向評測驗證。值得關注的議題包括：持續預訓練與 SFT 的互補性、代理式多輪修復中的能力退化現象、結構化工具呼叫的能力保留問題，以及倉庫級 SWE-bench 式任務的擴展性。

**產品經理**  
這篇論文描繪了一個可落地的「自然語言到交易策略」產品路徑。建議關注適用場景、成功指標（Judge Pass、成功回測率、首輪與最終成功率）、能力保留失效帶來的維運風險，以及與現有資料、風控、下單系統的整合點。特別注意：回測成功不等於實盤獲利，產品定位應放在「加速原型開發」而非「自動賺錢」。
