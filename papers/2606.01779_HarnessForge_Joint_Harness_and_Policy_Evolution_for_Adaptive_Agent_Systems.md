# HarnessForge：適應性智慧體系統的執行架構–策略共同演化

## ⚡ TL;DR

現有LLM智慧體系統僅單獨調整外部架構或內部策略，缺乏全系統層級的聯合適應與相容性優化。
提出HarnessForge框架，聯合錯誤引導架構調整與條件化策略對齊，實現架構與策略共同演化。
在五項跨領域基準中，較最強單一基線提升達12.0%，證明架構策略共演能顯著增強智慧體效能。

## 摘要翻譯

LLM 智慧體（LLM agents）日益被期許能在異質任務情境（heterogeneous task regimes）中運作，而這些情境需要不同的執行範式（execution paradigms）。這對固定式智慧體系統（fixed agent systems）構成挑戰，並凸顯了超越孤立元件更新（isolated component updates）之系統層級元適應（system-level meta-adaptation）的必要性。儘管現有研究已針對外部執行架構（external harness）進行調整，或對底層推理策略（reasoning policies）進行訓練，但全系統適應（full-system adaptation）仍缺乏充分的刻畫。結構與執行之間的適應空間（adaptation space）鮮少被明確界定，且外部執行架構與內部推理器（internal reasoner）之間的相容性也未被聯合優化。我們提出 HarnessForge，一個用於演化 LLM 智慧體系統的元適應框架（meta-adaptive framework）。HarnessForge 將智慧體系統形式化為一個執行架構–策略配對（harness–policy pair），藉此定義一個穩定的適應空間，將執行架構層級的執行結構（execution structure）與策略層級的推理行為（reasoning behavior）加以區隔。接著，它透過錯誤引導的執行架構調整（fault-guided harness tailoring）與執行架構條件化策略對齊（harness-conditioned policy alignment），進行執行架構–策略共同演化（harness–policy co-evolution）。橫跨多領域的五項基準測試（benchmarks）實驗顯示，HarnessForge 能持續提升 Qwen3-4B 與 Qwen3-8B 骨幹模型（backbones）的表現，優於純執行架構（harness-only）與純策略（policy-only）基線，相較最強基線（strongest baseline）提升最高達 12.0%，並達成良好的 rollout–效率權衡（rollout–efficiency tradeoffs）。這證明了執行架構–策略共同演化的有效性，以及執行架構與推理策略之間的可執行相容性（executable compatibility）對於智慧體系統適應（agent-system adaptation）至關重要。程式碼可於 https://github.com/mingju-c/HarnessForge 取得。

### 核心貢獻（3～5點）
- 提出 HarnessForge 元適應框架（meta-adaptive framework），將 LLM 智慧體系統形式化為「執行架構–策略配對」（harness–policy pair），建立穩定且明確的適應空間（adaptation space）。
- 透過「錯誤引導的執行架構調整」（fault-guided harness tailoring）與「執行架構條件化策略對齊」（harness-conditioned policy alignment），實現執行架構與策略的聯合共同演化（harness–policy co-evolution）。
- 在跨領域五項基準測試（benchmarks）中驗證，相較最強基線提升最高達 12.0%，並達成優異的 rollout–效率權衡（rollout–efficiency tradeoffs）。
- 證明執行架構與推理策略間的「可執行相容性」（executable compatibility）是全系統適應（full-system adaptation）的關鍵因素。

### 適合對象
從事 LLM 智慧體系統、元適應（meta-adaptation）機制、智慧體執行架構（harness）設計，以及大型語言模型推理策略（reasoning policy）聯合優化之相關研究者與工程師。

## 深度分析

#### 方法論解析

HarnessForge 的核心貢獻在於將智慧體系統（agent system）的適應目標（adaptation target）從傳統的「孤立元件更新（isolated component update）」提升至「系統層級元適應（system-level meta-adaptation）」。論文首先將 LLM 智慧體（LLM agent）形式化為一個耦合的（coupled）執行架構–策略配對（harness–policy pair）：

\[
G = (H, R_\delta), \quad H = (P, A, M), \quad R_\delta = R_{\theta_0} + \delta
\]

其中，執行架構（harness）\(H\) 由規劃結構（planning structure）\(P\)、行動結構（action structure）\(A\) 與記憶結構（memory structure）\(M\) 組成，定義了外部執行介面；而策略（policy）\(R_\delta\) 則以骨幹模型（backbone）\(R_{\theta_0}\) 加上可學習的 adapter \(\delta\) 構成，代表內部推理器（internal reasoner）在特定執行架構誘導的執行範式（harness-induced execution paradigm）下的行為。這種形式化明確區分了「外部執行結構（external execution structure）」與「內部推理行為」，從而建立了一個穩定且可解釋的適應空間（adaptation space）。

HarnessForge 的元適應框架（meta-adaptive framework）採用輪次式的共同演化（harness–policy co-evolution），每一輪演化（evolutionary round）包含以下三個協調階段：

1. **錯誤引導的執行架構調整（fault-guided harness tailoring）**：  
   系統先對當前的執行架構–策略配對進行 rollout 診斷（rollout diagnostics），收集智慧體軌跡（agentic trajectory）中的失敗訊號。隨後，元智慧體（meta-agent）依序執行錯誤定位（fault location, \(\mathbb{L}_\omega\)）、潛在改進識別（latent improvement, \(\mathbb{R}_\omega\)）與新架構生成（harness generation, \(\Gamma_\omega\)），針對規劃、行動與記憶模組進行結構性調整，產生多個候選執行架構（harness candidate）。

2. **執行架構條件化策略對齊（harness-conditioned policy alignment）**：  
   針對每個候選架構，系統從該架構下收集的軌跡中篩選高品質資料，用以訓練一個條件化於該架構的策略 adapter。這確保內部策略（internal policy）能精確執行該架構所暴露的規劃、行動與記憶介面，從而縮小相容性差距（compatibility gap），提升可執行相容性（executable compatibility）。

3. **Pareto 選擇與存檔**：  
   透過多目標篩選機制（考量任務表現與 rollout–效率權衡（rollout–efficiency tradeoff）），從眾多候選配對中選出優勝組合進入下一輪，並存入 scaffold archive \(\mathcal{Z}(r)\)。此機制確保演化過程不會為了追求單一指標而無限制增加推理步數或工具呼叫次數。

整體而言，HarnessForge 並非單純地「先搜尋架構、再訓練模型」或反之，而是將兩者視為不可分割的優化單元，透過診斷–調整–對齊的閉環，逐步逼近最適的系統層級配置。

#### 實驗數據解讀

論文在五個涵蓋異質任務情境（heterogeneous task regime）的基準測試（benchmark）上進行評估，領域橫跨多步驟工具使用（multi-step tool use）、檢索密集型推理（retrieval-heavy reasoning）、網頁互動（web interaction）等，並選用 Qwen3-4B 與 Qwen3-8B 作為骨幹模型（backbone）。實驗設計同時納入僅調整執行架構（harness-only）與僅調整策略（policy-only）的強基線，以驗證共同演化的必要性。

數據顯示，HarnessForge 在兩個骨幹模型上均帶來穩定且顯著的提升：相較於最強的單側面基線，**平均提升 3.56%，最高可達 12.0%**。這項結果具有多層意涵：

首先，它強烈驗證了「共同演化」假設。無論是單純搜尋外部執行結構（external execution structure）或單獨訓練內部執行行為（internal execution behavior），都無法達到系統最適；當執行架構與推理策略（reasoning policy）被視為獨立物件時，兩者之間的結構–執行耦合關係會被忽略，導致次優解。

其次，HarnessForge 在取得效能增益的同時，維持了**有利的 rollout–效率權衡（rollout–efficiency tradeoff）**。這表示其提升並非來自無限制地增加推理步數或延遲，而是來自更精準的架構–策略匹配。對於資源受限環境（resource-constrained setting）中的部署而言，這是一項關鍵的實務優勢。

最後，實驗橫跨兩種不同規模的骨幹模型（4B 與 8B），且趨勢一致，說明 harness–policy co-evolution 的效益具有跨模型規模的穩健性，並非僅在特定容量模型上才成立的偶然現象。

#### 與現有研究的比較

現有文獻大致可分為兩條軸線：**搜尋式方法（search-style method）**與**訓練式方法（training-style method）**。

搜尋式方法如 ADAS、AFlow、AgentSquare、MaAS、AutoHarness、Meta-Harness 與 MermaidFlow 等，將執行架構（harness）視為首要最佳化目標，自動化地設計工作流程（workflow）、執行圖（execution graph）、角色分配（role assignment）或記憶管理機制。這些方法確實減少了人工工程，但它們將模型端的執行者視為黑盒子，假設任何產生的外部執行結構都能被骨幹模型（backbone）正確執行，從而**隱含地忽略了可執行相容性（executable compatibility）**。一個更具表現力的規劃結構或行動介面，若內部推理器（internal reasoner）無法可靠地遵循，反而會導致失效。

訓練式方法如 Search-R1、ToolRL、ToRL、GiGPO、TreeRL、ARPO、Planner-R1 與 Memory-R1 等，則透過強化學習（reinforcement learning）、監督式學習（supervised learning）或偏好學習（preference learning）來調整模型策略（model policy）。這些方法改善了模型的內部推理能力，但通常運作於固定的互動範式（interaction paradigm）或預設執行架構之下。其根本限制在於：**一個更強的推理策略（reasoning policy）仍可能被不適當的規劃結構、行動空間或控制訊號所束縛**。

HarnessForge 的關鍵突破在於將適應目標（adaptation target）從「單一元件」轉移到「耦合配對」。透過錯誤引導的執行架構調整（fault-guided harness tailoring）與執行架構條件化策略對齊（harness-conditioned policy alignment）的協調，它首次在框架層級明確地縮小了相容性差距（compatibility gap），並以實證證明：在異質任務情境（heterogeneous task regime）中，架構與策略的聯合適應顯著優於任何單側面的極限。

然而，本研究也存在若干限制。首先，共同演化的運算成本高於單一側面調整：元智慧體（meta-agent）的診斷與生成、以及每輪針對多個候選架構進行策略 adapter 訓練，都需要可觀的推論與訓練資源。其次，目前的適應空間主要圍繞規劃–行動–記憶三大模組，對於更複雜的動態多智慧體協作或即時環境回饋的支援程度，仍有待後續驗證。

#### 可重現性評估

論文作者已於 GitHub 釋出原始碼（https://github.com/mingju-c/HarnessForge），這為可重現性奠定了基礎。實驗所使用的骨幹模型 Qwen3-4B 與 Qwen3-8B 均為公開權重模型，降低了模型取得的門檻。

不過，完整的可重現性仍面臨幾項挑戰。第一，元適應框架（meta-adaptive framework）的核心——元智慧體（meta-agent）——其提示設計（prompt design）、錯誤定位邏輯（fault location logic）與架構生成規則（harness generation rules）的細節，若未在論文或程式碼中完整揭露，將難以精確復現。第二，五個基準測試（benchmark）的資料處理流程、軌跡篩選標準以及訓練超參數，需要更詳盡的文件化。第三，共同演化涉及多輪次（multiple evolutionary rounds）的迭代訓練與推論，其隨機性與計算資源需求可能使小型實驗室難以完全複製。

建議作者未來提供預訓練好的策略 adapter 權重、演化過程中產生的 scaffold archive，以及各輪次 harness–policy pair 的具體配置，以進一步降低重現門檻，並促進社群在此基礎上進行消融研究（ablation study）。

---

#### 未來研究方向

1. **擴展適應空間（adaptation space）**：目前 HarnessForge 的執行架構（harness）主要分解為規劃（planning）、行動（action）與記憶（memory）三元件。未來可探索更細緻或更高階的結構原語，例如動態角色分配（dynamic role assignment）、多智慧體協議（multi-agent protocols）或環境回饋迴路（environment feedback loops），以處理更複雜的異質任務情境（heterogeneous task regime）。

2. **相容性預測與快速適配**：現行框架需透過實際 rollout 來驗證配對成效。未來可發展相容性預測模型，在不必完整執行的情況下，評估某一執行架構–策略配對（harness–policy pair）的潛在可執行相容性（executable compatibility），從而大幅降低演化成本，實現更高效的元適應（meta-adaptation）。

3. **跨骨幹遷移（cross-backbone transfer）**：當前的策略對齊（policy alignment）是針對特定骨幹模型（backbone）進行的。研究如何將為 Qwen3 系列優化的執行架構遷移至其他模型架構（如 Llama 或 GPT 系列），並保持其結構性支援（structural support）的有效性，是極具實務價值的方向。

4. **持續性元適應（continual meta-adaptation）**：目前的演化以離散輪次（discrete evolutionary rounds）進行。未來可朝向連續學習或線上適應（online adaptation）發展，使智慧體系統（agent system）能在部署後根據新興的任務分佈自動調整其執行架構與策略，而非僅限於預訓練階段的批次最佳化。

5. **理論分析**：現有成果多為實證性質。未來可從理論上刻劃「執行架構誘導的執行範式（harness-induced execution paradigm）」與「模型內部推理動力學」之間的匹配條件，為全系統適應（full-system adaptation）提供可證明的收斂保證或樣本複雜度上界，從而將 HarnessForge 的經驗性成功轉化為可預測的設計原則。

## 論文問答

**Q1：HarnessForge 旨在解決現有 LLM 智慧體系統在面對異質任務情境時的什麼核心問題？**
A：現有固定式智慧體系統難以應對需要不同執行範式的異質任務情境，例如多步驟工具使用、檢索密集型推理與網頁互動等。傳統方法往往將外部執行架構與內部推理策略視為靜態或孤立更新的元件，導致系統層級的元適應能力不足。HarnessForge 針對此問題，提出將智慧體系統重新定義為可共同演化的執行架構–策略配對，以實現全系統適應而非僅限於局部元件調整。

**Q2：為何單獨優化外部執行架構或內部推理策略的現有方法，不足以實現有效的智慧體系統適應？**
A：單獨優化外部執行架構雖能提供更豐富的規劃、行動或記憶結構，但若內部推理器無法可靠執行這些架構誘導的執行範式，則效能仍會受限。反之，僅強化內部策略而忽略外部架構，則模型可能受困於不適當的狀態空間、行動空間或控制訊號。這種相容性差距使得元件層級的觀點無法捕捉系統真正的瓶頸，因為完整的 LLM 智慧體系統本質上是一個耦合的執行架構–策略配對。

**Q3：在資源受限環境中，執行架構與推理策略之間的可執行相容性為何特別重要？**
A：在資源受限環境中，模型能力有限，外部執行架構必須提供足夠的結構性支援以彌補骨幹模型的不足，而內部策略則必須學習如何在該架構所定義的介面中有效執行。若兩者缺乏可執行相容性，即使架構設計精良或策略單獨強化，智慧體仍難以完成複雜任務。因此，將兩者視為耦合單元進行聯合優化，是實現高效能且具 rollout–效率權衡優勢之智慧體系統的關鍵。

**Q4：HarnessForge 的核心方法如何具體實現執行架構與策略的共同演化？**
A：HarnessForge 首先將智慧體系統形式化為一個執行架構–策略配對，其中執行架構由規劃、行動與記憶三個執行層元件組成，而策略則代表內部推理器的行為。在每一輪演化中，系統先透過 rollout 診斷執行失敗，利用元智慧體進行錯誤引導的執行架構調整；隨後，從篩選後的軌跡中訓練執行架構條件化策略對齊模組，使推理器適應調整後的架構。最後，框架透過帕雷托選擇機制挑選出效能與效率兼具的配對，進入下一輪演化。

**Q5：相較於先前將元件視為獨立優化目標的研究，HarnessForge 在適應目標的設定上有何關鍵創新？**
A：HarnessForge 的關鍵創新在於將「耦合的執行架構與內部策略」確立為明確的基本優化單元，而非將兩者視為可分離的獨立物件。這種重新定義建立了一個穩定的適應空間，能夠清楚區分架構層級的執行結構與策略層級的推理行為，從而讓系統層級的元適應有明確的操作對象。透過這種配對層級的觀點，框架得以直接優化兩者之間的可執行相容性，填補過往存在於結構與執行之間的適應空白。

**Q6：HarnessForge 為何選擇採用「錯誤引導」進行架構調整，並以「執行架構條件化」方式訓練策略對齊模組？**
A：採用錯誤引導的執行架構調整，是因為 rollout 過程中的實際失敗診斷能夠精確定位規劃、行動或記憶模組中的結構性缺陷，使架構修改更具針對性，避免盲目搜尋工作流程空間。而使用執行架構條件化的策略對齊，則能確保訓練出的 adapter 不是通用的單一策略，而是能夠與特定架構介面緊密配合的專門化推理行為。這兩項設計相輔相成，確保每一輪演化中架構的變更都能被策略準確理解與執行，逐步提升配對層級的相容性。

**Q7：HarnessForge 在哪些類型的基準測試上進行評估，這些測試如何驗證其跨領域適應能力？**
A：實驗橫跨五個來自不同領域的基準測試，涵蓋多步驟工具使用、檢索密集型推理、網頁互動等異質任務情境，以驗證框架在面對截然不同執行範式時的泛化能力。這些多樣化的測試環境要求智慧體必須具備不同的規劃深度、工具呼叫邏輯與記憶管理策略，因此能有效檢驗 HarnessForge 是否能自動發展出適合各任務情境的執行架構–策略配對。透過在這些領域上進行系統性評估，研究證明了該框架具備跨域適應的穩健性，而非僅針對單一任務類型過擬合。

**Q8：HarnessForge 在實驗中相較於純架構優化與純策略訓練的基線，取得了哪些關鍵量化成果？**
A：在 Qwen3-4B 與 Qwen3-8B 兩個骨幹模型上，HarnessForge 平均比最強的單一優化基線提升 3.56%，最高可達 12.0% 的效能增益。這些結果明確顯示，無論是僅調整外部執行架構或僅訓練內部推理策略，其上限均低於兩者聯合演化的系統層級方法。此外，框架在達成效能提升的同時，仍維持了有利的 rollout–效率權衡，顯示共同演化不僅帶來準確度優勢，也具備實際部署所需的計算效率。

**Q9：從 HarnessForge 與 harness-only、policy-only 基線的比較中，可以得出什麼關於「共同演化」必要性的實證結論？**
A：實驗結果表明，單獨演化外部執行架構或內部策略均無法達到 HarnessForge 的效能水準，這直接證明了執行架構–策略共同演化的必要性。當架構與策略分開優化時，兩者之間的相容性差距會成為效能瓶頸，導致更強的架構設計無法被現有策略充分利用，或更強的策略受困於不適配的架構介面。因此，唯有將兩者視為耦合配對進行聯合優化，才能顯著提升智慧體系統的整體表現，並確保架構的可執行性與策略的推理能力相互匹配。

**Q10：在實際部署中，HarnessForge 最適合應用於哪些需要適應性智慧體系統的場景？**
A：HarnessForge 特別適合部署在任務類型高度異質且執行範式差異顯著的環境，例如同時需要多步驟工具使用、複雜檢索推理與動態網頁互動的企業級自動化平台。在這些場景中，傳統固定式智慧體系統往往需耗費大量人力手動設計與調整工作流程，而 HarnessForge 能自動透過多輪演化產生與當前任務情境匹配的架構與策略配對。這種能力使其在需要快速適應新任務領域、且難以預先定義單一最佳執行結構的實際應用中，具備顯著的維護與擴展優勢。

**Q11：若將 HarnessForge 整合至商業化產品，在系統設計與營運層面需要考量哪些因素？**
A：產品化時需考量演化過程所需的 rollout 與訓練成本，因為多輪的共同演化會消耗額外的運算資源與時間，必須在離線演化與線上服務之間建立明確的階段區隔。此外，執行架構的可解釋性與版本管理亦至關重要，因為自動生成的規劃、行動與記憶結構需要能被工程師審計與除錯，以確保系統穩定與安全。最後，由於框架涉及元智慧體進行錯誤診斷與架構生成，產品團隊需建立適當的監控機制，避免自動調整過程中產生不符合業務邏輯的執行路徑。

**Q12：HarnessForge 對 LLM 智慧體領域的研究與發展可能帶來哪些深遠影響？**
A：HarnessForge 將研究視角從傳統的元件層級優化推進至系統層級的配對演化，為 LLM 智慧體的設計提供了新的理論框架與方法論基礎。透過確立「執行架構–策略配對」為基本優化單元，這項工作促使學界與業界重新審視外部結構與內部模型之間的互動關係，可能啟發更多關於可執行相容性的理論研究。長遠而言，這種共同演化的範式有助於發展出能夠自我診斷、自我重構並持續適應新環境的元適應智慧體系統，推動通用型智慧體的實現。

**Q13：HarnessForge 的框架設計存在哪些潛在的限制或約束條件？**
A：HarnessForge 目前主要驗證於 Qwen3-4B 與 Qwen3-8B 兩個規模相對較小的骨幹模型，其在更大參數量模型或不同模型家族上的泛化性仍需進一步驗證。此外，框架依賴元智慧體進行錯誤診斷與架構生成，若診斷結果存在偏差，可能導致後續調整方向錯誤，進而影響演化效率與最終效能。演化過程涉及多輪 rollout 與訓練，對於需要即時適應的場景而言，時間與計算成本可能構成實際部署的瓶頸。

**Q14：在什麼樣的情況下，HarnessForge 的共同演化機制可能遭遇失敗或效能瓶頸？**
A：若任務分佈過於分散或演化初期的執行架構–策略配對品質過差，錯誤引導的診斷可能難以收斂至有效的結構改進，導致演化過程在次優區域徘徊。當架構調整的幅度與策略對齊的速度不匹配時，例如架構發生劇烈變化而策略 adapter 無法及時適應，兩者間的相容性差距反而可能擴大。此外，若 rollout 診斷未能準確定位失敗根因，元智慧體可能對錯誤的模組進行無效修改，浪費運算資源並延遲收斂。

**Q15：基於 HarnessForge 的基礎，未來研究可以朝哪些方向進一步拓展？**
A：未來研究可探索將共同演化框架擴展至更大規模的骨幹模型，如數十億或千億參數等級的 LLM，以驗證其在強大基礎能力下的適應行為與上限。另一個方向是發展即時或線上的執行架構–策略共同演化機制，使智慧體能在部署環境中根據即時回饋動態調整，而非僅限於離線的多輪演化。此外，將此配對層級的適應觀點延伸至多智慧體系統，讓多個智慧體的協作架構與個別策略能夠聯合演化，亦是極具潛力的研究前沿。

## 實務應用指南

### 適用場景

1. **企業級多工具自動化流程**：例如財務月結需串接 ERP、報表系統與電子郵件，任務步驟與工具呼叫順序會隨法規或內部規範改變，HarnessForge 可同時調整外部工作流程（harness）與模型呼叫工具的策略，避免「流程已更新但模型仍照舊執行」的相容性斷裂。
2. **動態檢索增強型客服智慧體**：面對檢索密集型推理與開放式網頁互動並存的異質查詢，系統需動態決定何時觸發 RAG、何時瀏覽網頁。HarnessForge 能將檢索與瀏覽模組視為 harness 中的記憶與行動元件，並透過共同演化讓推理策略適配不斷變化的檢索時機。
3. **資源受限邊緣裝置上的適應性代理**：在僅能部署 Qwen3-4B 等輕量骨幹的場景中，固定 harness 往往過度複雜或過於簡陋。HarnessForge 可針對有限模型能力量身打造結構性支援（structural support），讓輕量策略也能可靠執行調整後的規劃與記憶結構。
4. **異質任務調度平台**：如單一智慧體需輪流處理資料分析（多步驟工具使用）、程式碼生成與網頁操作。傳統固定系統難以切換執行範式，HarnessForge 則透過 harness–policy co-evolution 為不同任務情境產出專屬的執行架構–策略配對。
5. **持續演化的研究助理**：當研究領域擴展時，助理需具備新任務分解、文獻回顧與實驗設計能力。HarnessForge 的演化輪次可逐步擴充規劃結構（planning）與記憶管理（memory），並同步對齊推理策略，實現系統層級的終身適應。

### 實作前置條件

- **資料**：需準備涵蓋目標任務分佈 𝑫 的智慧體軌跡（agentic trajectories），且必須同時包含成功與失敗案例，以供 fault-guided harness tailoring 進行診斷；另需建立 scaffold archive 𝒵(𝒓) 以記錄每輪 harness 變更歷程。
- **運算**：至少需配備可高效推理 Qwen3-4B 或 Qwen3-8B 的 GPU（如 NVIDIA A100 等級）；每輪演化涉及多次 rollout 與策略對齊訓練，建議保留足夠的運算預算，並為 meta-agent 的診斷流程配置獨立推理資源。
- **技能**：團隊需熟悉 LLM 外部執行結構設計（如 workflow、ReAct、tool-use procedure）、強化學習或偏好學習（用於 harness-conditioned policy alignment），以及 Python agent 框架（如 AutoGen、LangGraph）；同時需具備將錯誤日誌對應至 harness 元件（planning、action、memory）的除錯能力。

### 實作步驟建議

1. **定義初始執行架構–策略配對**：從基礎 harness 𝑯₀ = (𝑷, 𝑨, 𝑴) 與骨幹模型策略 𝑹₀ 出發，明確規劃（planning）、行動（action）、記憶（memory）三層的初始介面與控制訊號。
2. **建立診斷與歸檔機制**：部署 meta-agent 對當前配對進行 rollout 診斷，記錄錯誤位置 𝕃𝝎、潛在改進點 ℝ𝝎，並將結果寫入 scaffold archive，形成可追溯的演化資料。
3. **執行錯誤引導的架構調整（Harness Tailoring）**：依據診斷結果，針對 replan failure、tool call error 或記憶遺漏等故障類型，調整對應 harness 元件，產生候選 harness 族群。
4. **進行架構條件化策略對齊（Policy Alignment）**：為每個調整後的 harness 訓練專屬 adapter 𝜹，使更新後的策略 𝑹𝜹 = 𝑹𝜽₀ + 𝜹 能準確執行新架構誘導的執行範式，確保可執行相容性。
5. **配對選擇與多目標篩選**：以 Pareto selection 同時權衡成功率、步驟數（result steps）與延遲（delay），從候選配對中選出下一代的勝出 harness–policy pair。
6. **迭代演化與產品化**：重複上述流程數個演化輪次（evolutionary round），直到效能收斂；最終將勝出的配對封裝為具穩定 API 的 agent 服務，並保留 harness 編輯介面以供後續人工介入。

### 潛在風險與注意事項

- **相容性差距擴大**：若僅調整 harness 卻未同步更新 policy，將導致「架構過於複雜、推理器無法執行」的相容性差距（compatibility gap）。每輪必須強制執行 co-evolution，禁止單獨優化單側。
- **演化輪次成本爆炸**：每輪需產生大量 rollout 並訓練多組 adapter，運算成本可能指數增長。建議設定嚴格的資源預算上限，並優先採用輕量級 meta-agent 進行故障定位。
- **過度擬合特定任務分佈**：harness 可能過度特化於訓練任務分佈 𝑫，導致跨領域泛化能力下降。需保留獨立驗證集監測異質任務情境的表現，必要時引入正則化機制限制 harness 複雜度。
- **延遲與效能權衡**：更細緻的 harness（如多層 replanning 或複雜記憶管理）雖可提升成功率，卻會增加步驟延遲。產品上線前須明確延遲上限（latency budget），避免為了追求準確度而犧牲使用者體驗。

### 與其他技術的整合建議

- **現有 Agent 框架**：可將 HarnessForge 作為 AutoGen、MetaGPT 或 LangGraph 的上層元適應層，負責動態調整這些框架內的工作流程、角色分配與執行圖，而非從頭重建底層。
- **RAG 與記憶系統**：將向量檢索與摘要模組視為 harness 中的記憶元件 𝑴，利用 fault-guided tailoring 優化「何時檢索、如何更新記憶」的規則，並透過 policy alignment 讓模型學會依據檢索結果調整推理深度。
- **模型微調管線**：將 harness-conditioned adapter 的訓練整合進現有的 SFT、DPO 或 RLHF 管線，視為「架構感知」的額外訓練階段；adapter 的輕量特性也便於與 LoRA 等參數高效微調技術結合。
- **監控與可觀測性平台**：將每輪演化的 scaffold archive 𝒵(𝒓)、診斷日誌與 Pareto 前沿對接至 Langfuse、Weights & Biases 或自研監控系統，追蹤 harness 變更對生產環境指標的長期影響。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先理解「外部執行架構（harness）」與「內部推理策略（policy）」的區別，將 HarnessForge 想像成「同時改良工作說明書與員工技能」的雙軌訓練；可先從單一任務的 ReAct 範例開始，觀察調整 prompt 結構與微調模型行為的交互影響。
- **AI 工程師**：重點關注論文中的實作細節，特別是 fault-guided harness tailoring 的診斷邏輯與 harness-conditioned adapter 的訓練流程；建議直接參考官方程式碼，從 Qwen3-4B 基線開始復現，並嘗試將現有產品的固定 workflow 改寫為可編輯的 harness 元件。
- **研究人員**：請深入分析 co-evolution 的適應空間定義與 Pareto selection 的理論特性，思考如何將此框架擴展至多智慧體系統或更複雜的 credit assignment 場景；論文對「可執行相容性（executable compatibility）」的強調為 agent 系統設計提供了新的優化目標，值得進一步形式化。
- **產品經理**：將本文視為「讓 agent 產品具備自我演化能力」的架構參考，重點評估適用場景中的 ROI；需注意 co-evolution 需要持續的運算與資料投入，建議優先應用於高價值且任務異質性強的業務線，並規劃明確的效能–延遲商業權衡指標。
