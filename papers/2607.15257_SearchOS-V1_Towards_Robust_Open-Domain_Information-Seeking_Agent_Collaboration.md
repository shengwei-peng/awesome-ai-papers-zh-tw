## ⚡ TL;DR

開放領域資訊搜尋代理在長程互動中易遺漏進度、重複搜尋與陷入死胡同。
SearchOS將搜尋狀態外顯為關聯式綱要、證據圖與覆蓋地圖，並以管線平行排程與中介軟體協調多代理。

## 摘要翻譯

近期在工具整合式大型語言模型（Tool-Integrated Large Language Models）方面的進展，使網路搜尋成為資訊搜尋代理（information-seeking agents）的核心能力。然而，隨著互動歷史（interaction histories）增長，代理越來越難以追蹤任務進度。當搜尋嘗試未能取得有用的證據時，現有的單代理與多代理系統（multi-agent systems）可能陷入重複迴圈（repetitive loops），浪費搜尋預算，進而損害最終輸出（final output）的品質與完整性。我們提出 SearchOS，一個系統層級的多代理框架，將脆弱且隱含的搜尋進度（implicit search progress）轉化為明確、持續且共享的狀態（explicit, persistent, and shared state）。首先，我們將開放領域資訊搜尋（open-domain information seeking）形式化為具有有根據引用（grounded citations）的關聯式綱要填補（relational schema completion）任務，其中代理發現實體（entities）、跨越多個連結資料表（linked tables）填入屬性（attributes），並將每個數值錨定（anchor）至來源證據（source evidence）。接著，我們設計了搜尋導向情境管理（Search-Oriented Context Management, SOCM），將持續演化的狀態外顯化（externalize）為前沿任務（Frontier Task）、證據圖譜（Evidence Graph）、覆蓋地圖（Coverage Map）與失敗記憶（Failure Memory）。基於 SOCM，SearchOS 採用管線平行排程機制（pipeline-parallel scheduling mechanism），讓子代理的執行互相重疊，並持續將針對未解決覆蓋缺口的任務填入釋出的執行槽位（execution slots），以提升利用率與吞吐量。為了排程與控制搜尋代理的執行，SearchOS 引入了搜尋工具中介軟體框架（Search Tool Middleware Harness），攔截模型與工具互動（model and tool interactions）以記錄有根據的證據（grounded evidence），並應對執行停滯（execution stalls）或預算耗盡（budget exhaustion）；同時提供一個包含策略技能（strategy skills）與存取技能（access skills）的可重複使用階層式技能系統（reusable hierarchical skill system），以擴充代理的搜尋流程，並避免在不同執行間重複出現失敗的搜尋模式。在 WideSearch 與 GISA 上，SearchOS 在所有指標（metrics）上均領先所評估的單代理與多代理基線（baselines），為穩健的資訊搜尋協作奠定基礎。

### 核心貢獻（3～5點）
- 將開放領域資訊搜尋形式化為具備有根據引用的關聯式綱要填補任務，使搜尋進度可透過實體、屬性與來源證據進行結構化追蹤。
- 提出搜尋導向情境管理（SOCM），透過前沿任務、證據圖譜、覆蓋地圖與失敗記憶，將隱含的搜尋進度轉化為明確、持續且共享的狀態。
- 設計管線平行排程機制，讓子代理執行互相重疊，並持續將未解決缺口填入釋出槽位，以提升整體利用率與吞吐量。
- 引入搜尋工具中介軟體框架與可重複使用的階層式技能系統，以記錄有根據的證據、應對執行停滯與預算耗盡，並避免跨執行重複失敗模式。
- 在 WideSearch 與 GISA 基準上，於所有評估指標均領先現有單代理與多代理基線。

### 適合對象
從事資訊檢索、大型語言模型代理系統、多代理協作與開放領域問答研究的研究人員與工程師，特別是關注長程搜尋任務之狀態管理、排程效率與引用品質的讀者。

## 深度分析

#### 方法論解析

SearchOS 將開放領域資訊搜尋（open-domain information seeking）重新定義為「關聯式綱要填補（relational schema completion）搭配有根據的引用（grounded citations）」。給定自然語言查詢 q，系統會建立一個關聯式搜尋綱要（relational search schema）S = {T_m}, R，其中每張資料表 T_m 包含屬性（attributes）A_m 與主鍵（primary keys）P_m，而 R 則記錄資料表間的外鍵（foreign keys）關係。任務目標 T = (q, S) 因此從開放式請求（open-ended request）轉化為具體搜尋目標（concrete search target）：系統必須同時發現實體（discover entities）、填入屬性（populate attributes）、並為每個數值維護引用矩陣（citation matrix），將其錨定（anchor）到來源 URL 與錨定摘錄（anchored excerpt）。這種關聯式塑模（relational modeling）與正規化原則（normalization principles）的應用，能減少冗餘與衝突主張（conflicting claims），並讓進度可衡量（progress measurable）。

為了解決傳統代理將計畫、進度、證據與失敗視為短暫對話內容的問題，SearchOS 提出 Search-Oriented Context Management（SOCM，搜尋導向情境管理），把執行狀態外顯化（externalize execution state）為四個持續且共享的結構：

1. **Frontier Task（前沿任務）**：以優先順序排程的工作 DAG，代表當前最優先處理的搜尋目標。  
2. **Evidence Graph（證據圖譜）**：綱要綁定的證據圖，記錄來源、主張、實體與屬性之間的關係。  
3. **Coverage Map（覆蓋地圖）**：多綱要填補狀態，標示哪些實體/屬性已完成、進行中或待處理，形成明確缺口（explicit gaps）。  
4. **Failure Memory（失敗記憶）**：記錄無效查詢、無法存取的網站、不可用的技能與失敗案例，避免重複失敗模式並用於技能學習。

中央協調器（central orchestrator）負責將綱要分解為以覆蓋缺口為導向的任務，並協調探索代理（explore agent）、搜尋代理（search agent）與撰寫代理（writer agent）。不同於傳統多代理系統採用同步批次派發，SearchOS 使用管線平行排程（pipeline-parallel scheduling）：多個子任務同時進行，每當執行槽位（execution slots）被釋出，便立即填入針對未解決覆蓋缺口的新任務。這種設計借鏡 GPU 訓練中的 pipeline parallelism，能降低落後任務造成的閒置時間並提升搜尋吞吐量（throughput）。

為了讓執行控制不依賴代理自行記得呼叫，SearchOS 引入 Search Tool Middleware Harness（搜尋工具中介軟體框架）。該框架透過 Pre-LLM Call Wrapper 與 Post Tool Call Wrapper 攔截模型與工具互動（model and tool interactions），並提供：

- **Context Middleware（情境中介）**：註冊與管理代理情境，注入相關狀態。  
- **Sensor Middleware（感測中介）**：監控進度，在執行停滯（execution stalls）或預算耗盡（budget exhaustion）時進行行為介入（behavioral intervention）。  
- **Evidence Extraction Middleware（證據萃取中介）**：從工具回傳中提取並錨定有根據的證據（grounded evidence），維護引用與來源出處（provenance）。

透過中介層，預算執行、重複或停滯軌跡偵測、證據處理等全局不變量被移出代理提示詞，使代理能專注於局部搜尋決策。

此外，SearchOS 設計了可重複使用的階層式技能系統（reusable hierarchical skill system），分為：

- **Strategy Skills（策略技能）**：決定如何搜尋、搜尋什麼，例如查詢規劃與來源選擇。  
- **Access Skills（存取技能）**：針對特定網站或資料來源，描述如何到達並萃取資訊。

技能庫（skill library）透過 Registry/Router 根據任務與來源路由，執行 `skill_<name>()`。Skill Builder 則分析失敗案例（bad cases）、模擬、驗證，並從失敗中生成可跨執行（across runs）與跨工作階段（across sessions）重用的技能，從而避免重複無效搜尋模式。

整體流程可概括為：使用者問題 → 建立關聯式綱要 → 分解為覆蓋導向任務 → 管線平行派發代理 → 中介層攔截並更新 Evidence Graph、Coverage Map 與 Failure Memory → 撰寫代理綜合發現並產出帶引用的結構化報告。

#### 實驗數據解讀

論文在 WideSearch 與 GISA 兩個基準上進行評估，採用的指標（metrics）包括項目層級 F1（item-level F1）與集合層級 F1（set F1）。根據摘要與引言，SearchOS 在這兩個基準的所有評估指標上均領先所比較的單代理與多代理基線（baselines）：

- **WideSearch**：item-level F1 達到 **80.3**。  
- **GISA**：set F1 達到 **76.5**，較最強基線高出 **13.4** 分。

這些數據顯示 SearchOS 的穩健性（robustness）主要體現在需要多實體、多屬性、多表關聯的複雜任務上。GISA 上高達 13.4 分的領先幅度，強烈暗示傳統單代理或簡單多代理系統在長程任務中容易遺漏（omissions）資訊、重複收集（redundant collection）或陷入重複迴圈（repetitive loops），而 SearchOS 透過 Coverage Map 與 Failure Memory 有效抑制了這些問題。

WideSearch 的 80.3 item-level F1 雖然表現良好，但仍留有約兩成改進空間。這部分可能來自：檢索失敗、來源品質不佳、綱要與問題不匹配、錨定摘錄萃取錯誤，或是實體發現（entity discovery）不完整。由於目前提供的文本未包含詳細的消融實驗（ablation study）或錯誤分析，我們無法判斷各模組的個別貢獻比例。

需要謹慎解讀的是：實驗僅涵蓋兩個基準，且未報告延遲、吞吐量、成本或引用品質等指標。儘管論文強調管線平行排程能提升利用率與吞吐量，但若缺乏實際的執行時間或搜尋預算（search budget）使用效率數據，則難以量化其系統層級效益。此外，76.5 的 set F1 雖然相對領先，但絕對值顯示在開放領域資訊搜尋中，完整且正確地填滿複雜綱要仍具挑戰性。

#### 與現有研究的比較

SearchOS 的定位介於工具整合大型語言模型（Tool-Integrated LLMs）與通用多代理協作框架之間，但針對開放領域資訊搜尋做了系統級的專用設計。

相較於 ReAct、WebGPT 等早期單代理搜尋方法，SearchOS 不再依賴對話歷史（interaction histories）隱含地追蹤進度，而是將進度外顯化為 Coverage Map 與 Evidence Graph。這解決了「證據埋沒在上下文」與「代理遺忘已建立事實」的問題。相較於 AutoGen、MetaGPT 等通用多代理系統，SearchOS 增加了搜尋專用的 SOCM、Search Tool Middleware Harness、管線平行排程與階層式技能系統，能更有效避免平行工作者（parallel workers）之間的重複工作（duplicate effort）與執行槽位閒置。

與近期將長程資訊搜尋視為表格填補（table-completion）的研究（如 Lan et al., 2026）相比，SearchOS 的差異在於：它將表格填補進一步形式化為關聯式綱要填補，並引入引用矩陣、管線執行、失敗記憶與可重用技能，使過程不僅可驗證，也可持續學習與擴展。

主要優勢包括：

- **統一且可驗證的目標**：每個數值都有 grounded citations，便於驗證與除錯。  
- **持續共享狀態**：Frontier Task、Evidence Graph、Coverage Map、Failure Memory 讓多代理協作有共同基礎。  
- **高資源利用率**：pipeline-parallel scheduling 減少等待慢任務的閒置。  
- **執行層級保障**：中介層將預算、停滯偵測、證據錨定等責任從代理提示詞中分離。  
- **跨任務學習**：階層式技能系統保留有效搜尋與存取模式（effective search and access patterns）。

然而，SearchOS 也存在若干限制。首先，關聯式綱要需要預先或動態建立，對於高度開放、難以結構化的問題，綱要設計本身可能成為瓶頸。其次，中介層與管線排程增加了系統複雜度與潛在延遲，中央協調器在大量代理與資料表下可能成為瓶頸。Failure Memory 若累積過多雜訊，反而可能誤導後續決策。此外，系統高度依賴外部搜尋 API 與 LLM 的品質與成本，這些因素在不同執行環境中可能導致效能波動。

#### 可重現性評估

根據目前提供的文本，論文並未提及原始碼、資料集、模型權重或實驗設定的公開連結，因此可重現性（reproducibility）仍屬未知。WideSearch 與 GISA 若為現有公開基準，則評估資料本身可能可取得；但 SearchOS 的核心貢獻——包括 SOCM 實作、Search Tool Middleware Harness、技能庫與管線排程邏輯——若未釋出，則其他研究者難以完整重現其結果。

為提升可重現性，作者應考慮公開：

- 完整原始碼與容器化執行環境。  
- 關聯式搜尋綱要（relational search schema）的範例與產生方式。  
- Search Tool Middleware Harness 的實作細節，包括 Pre/Post Tool Call Wrapper。  
- 技能庫（skill library）的內容、註冊/路由機制與 Skill Builder 流程。  
- 使用的 LLM 版本、搜尋 API、提示詞模板與超參數。  
- 評估腳本、執行軌跡（orchestration trace）與成本紀錄。

此外，由於系統依賴專有 LLM 與搜尋 API，即使釋出程式碼，不同時間點的模型版本、API 回傳內容與網頁變化都可能影響結果重現。建議作者提供去識別化的執行記錄與固定種子設定，以降低變異性。

#### 未來研究方向

SearchOS 為穩健的資訊搜尋代理協作（robust information-seeking agent collaboration）開闢了多條後續研究路徑：

1. **自動綱要推導與動態演化**：目前仍須建立關聯式綱要，未來可研究如何讓 LLM 自動從問題中推導綱要，並在搜尋過程中動態新增資料表、屬性或關係。

2. **不確定性量化與衝突解決**：引入對每個數值與來源的信心分數，並設計機制調和證據（reconcile evidence）中的衝突主張，例如多數決、來源權重或人類驗證。

3. **人在迴路驗證**：在 Coverage Map 上視覺化未覆蓋缺口，讓使用者能確認、修正或補充資訊，提升最終輸出（final output）的可靠性。

4. **多模態證據整合**：將圖片、表格、PDF 等非文字來源納入 Evidence Graph 與 citation matrix，擴展至更豐富的資訊來源。

5. **分散式與容錯部署**：將中央協調器與中介層擴展為分散式架構，提升容錯能力與大規模代理排程的穩定性。

6. **動態預算分配**：根據 Coverage Map 的缺口重要性與預期資訊增益，動態調整各子任務的搜尋預算，避免預算耗盡在無價值路徑上。

7. **強化式技能學習**：讓 Skill Builder 不僅從失敗案例歸納，也能透過強化學習或模仿學習持續精進策略技能與存取技能。

8. **引用品質與可解釋性指標**：除了 F1，進一步評估 citation precision/recall、來源多樣性、錨定摘錄的準確性，並提供為何選擇某來源的解釋。

9. **跨語言與跨領域適應**：測試 SearchOS 在不同語言、專業領域與低資源網站上的泛化能力，並發展對應的 access skills。

10. **即時與串流資訊整合**：讓系統能處理不斷更新的網頁內容與新聞串流，維護 Evidence Graph 的時效性與正確性。

## 論文問答

**【背景與動機】**

**Q1：SearchOS 要解決的核心問題是什麼？**
A：現有工具整合型大型語言模型雖然具備網頁搜尋能力，但隨著互動歷史增長，代理難以追蹤任務進度，導致證據埋沒在對話脈絡中。當搜尋嘗試無法取得有效證據時，單一或多代理系統容易陷入重複迴圈，浪費搜尋預算並降低最終答案的完整性與品質。SearchOS 透過將脆弱且隱含的搜尋進度轉化為明確、持續且共享的狀態，來解決這些可靠性問題。

**Q2：為何現有的單代理與多代理系統在長程開放領域任務上會失敗？**
A：單一代理在搜尋路徑無效時，可能一再發出相似的查詢或持續探索同一條死路，造成預算浪費。多代理雖然能平行工作，但可能重複努力、對目標欄位產生歧見，或因等待最慢任務而讓執行槽位閒置。這些失敗源於傳統代理把計畫、進度、證據與失敗都視為短暫的對話內容，而非由系統維護的結構化狀態。

**Q3：為什麼將搜尋進度外顯化並持續保存很重要？**
A：外顯化後，系統能清楚知道哪些實體與屬性已被涵蓋、哪些仍是缺口，並能追蹤每個數值的來源與錨定摘錄。這讓進度變得可衡量，也讓多個代理能圍繞明確缺口協作，避免重複收集與遺漏。此外，系統可以在執行停滯或預算耗盡時主動介入，並跨工作階段保留有效的搜尋與存取模式。

**【方法與創新】**

**Q4：SearchOS 如何形式化開放領域資訊搜尋任務？**
A：SearchOS 將資訊搜尋視為「關聯式綱要填補」任務，並要求每個數值都附帶有根據的引用。系統會根據自然語言請求建立包含多個資料表、主鍵與外鍵關係的關聯式搜尋綱要，並在填補實體列與屬性時維護引用矩陣。這種形式化把開放式請求轉換成具體的搜尋目標，使進度能以實體與屬性層級進行衡量與驗證。

**Q5：什麼是 Search-Oriented Context Management（SOCM），它包含哪些核心元件？**
A：SOCM 是 SearchOS 用來將執行狀態外顯化並在所有代理之間共享的機制。它由 Frontier Task、Evidence Graph、Coverage Map 與 Failure Memory 四個核心結構組成，分別記錄當前優先任務、來源與數值間的證據關係、綱要填補狀態，以及無效的搜尋嘗試。中央協調器依據這些共享狀態將綱要分解為以覆蓋缺口為導向的子任務，並協調探索、搜尋與撰寫代理。

**Q6：SearchOS 的管線平行排程與 Search Tool Middleware Harness 各自扮演什麼角色？**
A：管線平行排程讓不同子任務能夠同時進行，並在執行槽位釋出後立即指派給尚未解決的綱要缺口，從而減少因慢速任務造成的閒置時間並提升搜尋吞吐量。Search Tool Middleware Harness 則攔截模型與工具的互動，負責注入相關狀態、擷取與錨定證據、執行預算控管，以及偵測重複或停滯的軌跡。兩者結合使代理能專注於局部搜尋決策，而系統層級則維持全局執行不變性。

**【實驗與結果】**

**Q7：SearchOS 在哪些基準上進行評估？**
A：論文在 WideSearch 與 GISA 兩個基準上評估 SearchOS。WideSearch 側重於需要大量事實收集的開放領域搜尋任務，而 GISA 則用於檢驗代理在結構化資訊尋求與引用上的表現。這兩個基準能夠同時檢驗系統的覆蓋完整性、引用正確性與整體答案品質。

**Q8：SearchOS 取得了哪些關鍵實驗結果？**
A：SearchOS 在所有評估的單代理與多代理基線中領先所有回報的 F1 指標。它在 WideSearch 上達到 80.3 的項目層級 F1，在 GISA 上達到 76.5 的集合層級 F1，後者比最強基線高出 13.4 分。這些結果顯示，將搜尋狀態外顯化並採用管線平行協作能顯著提升長程資訊搜尋的穩健性與正確性。

**Q9：從結果可以推論出哪些設計選擇的貢獻？（消融研究）**
A：雖然提供的摘要與內文未詳細列出各元件的獨立消融數據，但整體領先基線的幅度暗示了多項設計的協同效應。關聯式綱要填補提供了可衡量的目標，SOCM 減少了重複搜尋與遺漏，管線排程提升了執行效率，中介軟體則防止預算浪費與停滯。未來若能針對 Frontier Task、Failure Memory 與技能庫進行逐項消融，將能更精確量化每個元件的邊際貢獻。

**【應用與影響】**

**Q10：SearchOS 最適合應用在哪些實務場景？**
A：SearchOS 特別適合需要長期、多步驟且結構化輸出的資訊搜尋場景，例如學術文獻回顧、市場情報收集、競品比較分析、事實查核與具引用來源的調查報告。在這些場景中，系統必須發現大量實體、填補多個屬性，並調和不同來源的衝突主張。透過明確的綱要與共享狀態，SearchOS 能夠產生可驗證且組織良好的最終輸出。

**Q11：部署 SearchOS 時需要考慮哪些產品化議題？**
A：產品化時必須設計符合任務需求的關聯式綱要，並確保中介軟體能穩定攔截模型與工具的互動。此外，需要控管搜尋預算、評估來源可靠性、維護引用品質，並管理並行代理的執行槽位與衝突。Failure Memory 與階層式技能庫也需要持續更新，才能隨著時間累積有效的搜尋與存取模式。

**Q12：SearchOS 對資訊搜尋代理領域可能帶來什麼影響？**
A：SearchOS 將研究焦點從單純增強語言模型的搜尋能力，轉向建構具備系統級狀態管理的「代理作業系統」。這種外顯化進度、證據與失敗的設計典範，可望成為未來多代理協作的參考架構。同時，它強調有根據的引用與結構化輸出，有助於提升自動化資訊搜尋在真實應用中的可信度與可解釋性。

**【限制與未來方向】**

**Q13：目前工作有哪些已承認或隱含的限制？**
A：摘要與內文並未明確列舉限制，但從設計可推知若干隱含挑戰：系統需要預先或自動建立合適的關聯式綱要，對於高度動態或語意模糊的任務可能不易設計。證據圖與覆蓋地圖的規模隨任務增長，可能帶來儲存與推理開銷。此外，技能庫的覆蓋範圍與來源品質也會直接影響最終答案的完整性。

**Q14：SearchOS 仍可能出現哪些失敗案例？**
A：當任務的實際資訊結構與預設綱要不符時，系統可能無法正確發現實體或填入屬性。若網路來源不可用、被封鎖或內容品質低落，則即使有多個代理也難以取得可靠證據。此外，預算在填補所有缺口前耗盡、衝突主張無法有效調和，或技能庫缺少特定網站的存取策略，都可能導致輸出不完整或錯誤。

**Q15：SearchOS 未來可以朝哪些方向發展？**
A：未來可研究如何自動或動態地推導搜尋綱要，減少對人工設計綱要的依賴。系統也可透過線上學習持續精進策略技能與存取技能，並擴展至多模態證據，例如圖片、表格與影片。更進一步，可強化衝突解決機制、引入使用者互動式澄清，以及支援跨工作階段的個人化與分散式規模化執行。

## 實務應用指南

### 適用場景

1. **競爭情報與市場研究**  
   針對「某產業所有主要廠商近三年的營收、產品線、併購事件與專利佈局」這類開放式問題，SearchOS 可將每家廠商視為一筆實體列、各年度財務與事件視為屬性，並透過 Coverage Map 追蹤哪些廠商還缺少資料，避免研究員或單一代理反覆搜尋同一間公司。

2. **盡職調查 / KYC（認識你的客戶）**  
   在法遵或投資前調查中，需要彙整企業的註冊資本、董事名單、關係企業、訴訟與新聞。SearchOS 的關聯式綱要可將公司、人物、法律案件設為不同資料表，並以主鍵–外鍵關係串連；Evidence Graph 則確保每項結論都有錨定摘錄與來源 URL，方便稽核。

3. **科學文獻與臨床證據綜述**  
   針對「某療法對多種適應症的臨床試驗結果」進行長程搜尋時，可將試驗、適應症、療法、結果指標設為綱要，系統自動發現試驗實體、填入屬性，並把每個數值錨定到 PubMed 或臨床試驗註冊頁面，減少遺漏與衝突主張。

4. **企業內部知識庫補全**  
   當組織已有部分產品規格、客戶合約或技術文件，但分散在不同系統時，SearchOS 可將內部資料表與外部網路搜尋結合，把缺口（例如某產品的認證文件、某客戶的聯絡窗口）轉為 Frontier Task，由不同代理平行補完。

5. **供應鏈風險監控**  
   追蹤多層供應商的工廠位置、產能、天災影響與 ESG 爭議。透過 Failure Memory 記錄「某網站無法存取」或「某查詢詞找不到結果」的經驗，系統可在下一次執行時自動繞過無效路徑，避免重複浪費搜尋預算。

### 實作前置條件

**資料準備**
- 明確的使用者問題與預期輸出格式（報告、表格、API 回傳）。
- 關聯式搜尋綱要：至少包含資料表、屬性、主鍵、外鍵關係，以及每個屬性的資料型別與可接受來源類型。
- 搜尋與瀏覽工具：網路搜尋 API、網頁擷取服務、內部文件檢索引擎。
- 來源白名單 / 黑名單與引用品質規範，用於判斷證據是否可信。

**運算資源**
- LLM 推論端點（可為私有部署或第三方 API），建議具備函式呼叫與長上下文能力。
- 可儲存結構化狀態的後端：關聯式資料庫或圖資料庫（用於 Evidence Graph）、快取層（Coverage Map、Failure Memory）。
- 可平行執行多個代理的執行環境，並支援執行槽位動態分配。
- 中介軟體攔截層：能在模型呼叫前後與工具呼叫前後注入邏輯。

**技能與團隊**
- 熟悉關聯式資料庫設計與正規化原則。
- 具備代理協作與提示工程經驗。
- 能開發與維護網頁存取技能（處理分頁、登入、反爬蟲、API 速率限制）。
- 具備評估與品管能力：能定義 F1、覆蓋率、引用正確性等指標。

### 實作步驟建議

1. **從問題到綱要**  
   與領域專家一起把開放式請求轉成關聯式搜尋綱要。先從 1–2 張核心資料表開始，確認主鍵與必填屬性，再逐步加入外鍵關係。

2. **建立 Search-Oriented Context Management（SOCM）狀態儲存**  
   實作 Frontier Task（優先任務 DAG）、Evidence Graph（來源–數值關係）、Coverage Map（已填 / 未填狀態）、Failure Memory（無效查詢與不可存取網站）。這四項必須能被所有代理讀寫，而非存在個別對話歷史中。

3. **部署 Search Tool Middleware Harness**  
   在模型呼叫前包裝上下文、在工具呼叫後擷取與錨定證據、監控搜尋預算、偵測重複或停滯軌跡。讓代理專注於本地決策，系統負責維持全域不變量。

4. **設計代理角色與管線平行排程**  
   定義 explore、search、writer 等角色，並讓中央協調器根據 Coverage Map 的缺口持續填滿釋出的執行槽位。避免批次同步等待，減少 straggler 造成的閒置。

5. **建立階層式技能庫**  
   將「如何搜尋」抽象為策略技能（例如關鍵字改寫、實體發現、比較分析），將「如何到達特定網站並擷取」封裝為存取技能（例如某財經網站、某政府公開資料平台）。技能應可註冊、路由與版本管理。

6. **小規模試點與迭代**  
   選 10–50 個代表性查詢進行試跑，觀察 Coverage Map 的填補率、Failure Memory 是否有效避免重複錯誤、引用是否正確。根據結果調整綱要、提示與技能。

7. **產品化與持續監控**  
   加入評估儀表板、預算告警、人工覆核流程，並讓 Failure Memory 與成功軌跡持續回流，自動精簡或新增技能。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **綱要過度僵化** | 開放領域資訊本質上會出現預期外的實體與屬性，固定綱要可能遺漏重要資訊。 | 設計綱要擴充機制：允許代理在發現新類別時提出新增欄位或資料表，並經人工或規則審核。 |
| **來源可靠性與虛假引用** | 模型可能產生看似合理但無法驗證的引用，或從低可信度網站擷取資訊。 | 強制每個數值必須對應到錨定摘錄與 URL；建立來源評分與白名單；對關鍵數值進行交叉驗證。 |
| **搜尋預算爆增** | 長程任務容易因重複查詢或無效分支而耗盡預算。 | Middleware Harness 必須強制預算上限；Failure Memory 記錄無效查詢；Coverage Map 避免重複填補已確認的屬性。 |
| **存取技能失效** | 目標網站改版、登入流程改變或反爬蟲機制升級會讓既有技能失效。 | 將存取技能模組化並定期回歸測試；保留備用擷取方式（例如官方 API、RSS、網頁快取）。 |
| **平行代理間的衝突** | 多個代理可能同時修改同一筆實體，造成覆蓋或引用不一致。 | 在 SOCM 中加入樂觀鎖或屬性級鎖定；writer 代理負責最終彙整與衝突調和。 |
| **法遵與隱私** | 搜尋與儲存外部或內部資料可能涉及個資、版權或 robots.txt 限制。 | 在設計階段納入法務審查；對敏感來源設存取限制；記錄所有工具呼叫以滿足稽核需求。 |

### 與其他技術的整合建議

- **RAG（檢索增強生成）系統**：SearchOS 可視為「主動式、長程、多步驟」的 RAG 延伸。可將現有向量資料庫作為 Evidence Graph 的內部來源之一，並讓 Middleware Harness 統一處理內部檢索與外部網路搜尋的證據擷取。
- **知識圖譜（Knowledge Graph）**：Evidence Graph 可與現有 KG 對齊，把新發現的實體與關係匯入企業知識庫；反之，KG 也可作為綱要設計與實體發現的種子。
- **CRM / ERP / BI 工具**：將 Coverage Map 與填補結果透過 API 餵入現有報表或儀表板，讓業務使用者直接看到「哪些客戶資料還缺證明文件」或「哪些供應商資訊待驗證」。
- **Workflow / BPM 平台**：把 SearchOS 當成需要「資料補全」的任務節點。當流程觸發條件時，呼叫 SearchOS 進行開放領域搜尋，完成後再將結構化結果寫回流程。
- **LLMOps / 可觀測性平台**：將 orchestration trace、Coverage Map 變化、Failure Memory 與預算使用情形匯出到現有監控系統，協助維運團隊追蹤長程任務的健康度。

### 給不同背景讀者的閱讀建議

**給初學者**  
先聚焦論文想解決的問題：當 AI 代理上網搜尋很久之後，會忘記自己找過什麼、重複搜尋同一個關鍵字、最後答案也沒有出處。把 SearchOS 想像成一張「會自動補充、每格都有引用來源的 Excel 表格」——系統隨時知道哪些格子還沒填、誰正在填、以及之前哪些搜尋是浪費時間的。理解了這個畫面，再回頭看 Frontier Task、Evidence Graph 與 Coverage Map 會更直覺。

**給 AI 工程師**  
請把重點放在 Search Tool Middleware Harness、SOCM 與管線平行排程的實作細節。這篇論文的核心貢獻不是「讓 LLM 更會搜尋」，而是把狀態從對話歷史中抽出來變成系統級結構，並透過中介軟體維持不變量。建議從如何攔截模型與工具呼叫、如何設計可共用的狀態儲存、以及如何動態分配執行槽位開始實作，再逐步加入階層式技能庫與 Failure Memory。

**給研究人員**  
值得深入的是「關聯式綱要填補」這個形式化框架，以及它如何將開放領域資訊搜尋轉為可衡量、可驗證的目標。進一步可探討管線平行排程在代理協作中的理論效益、Failure Memory 對搜尋軌跡的長期影響、以及引用矩陣與證據圖譜在減少幻覺與衝突主張上的作用。實驗部分在 WideSearch 與 GISA 上的表現也可作為後續基準設計的參考。

**給產品經理**  
這篇論文提供的是一個可產品化的「開放領域研究自動化」架構。閱讀時請優先對照你的應用場景：哪些決策需要結構化證據？哪些資料來源可信？使用者願意為了更高完整性付出多少搜尋成本？同時要留意風險——綱要設計不良會限制產出、來源品質會影響信任、預算控制則直接關係 ROI。建議從一個明確、可驗證的業務指標（例如 KYC 案件完成率、研究報告產出時間）開始試點。
