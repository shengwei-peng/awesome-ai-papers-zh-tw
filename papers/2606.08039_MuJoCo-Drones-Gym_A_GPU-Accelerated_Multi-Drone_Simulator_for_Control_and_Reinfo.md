## 摘要翻譯

機器人模擬器是現代空中機器人學研究的基石，既是開發新控制演算法的工具，也是訓練強化學習（RL）策略的資料來源。然而，現有的四旋翼飛行器學習環境往往必須在物理逼真度、多智能體支援，以及現代深度強化學習流程所需的吞吐量之間做出取捨。本文提出 MuJoCo-Drones-Gym，這是一個基於 MuJoCo 物理引擎的開源且相容 Gymnasium 的多無人機環境。MuJoCo-Drones-Gym 支援任意數量的 Bitcraze Crazyflie 2.x 微型四旋翼，並提供模組化 API 以選擇（i）物理模型（剛體 MuJoCo 模型、顯式 Python 動力學，或地面效應、槳葉阻力與機間下洗氣流的任意子集）、（ii）動作介面（單馬達轉速、總歸一化推力、速度設定點或 PID 路徑點指令），以及（iii）觀測空間（運動學狀態向量、RGB / 深度 / 分割相機，或鄰域鄰接資訊）。PettingZoo ParallelEnv 包裝器可實現即插即用多智能體強化學習，而七個任務環境——懸停、速度追蹤、多機懸停、路徑點導航、編隊飛行、閘門競速，以及一個通用多智能體模板——則展示此介面的廣度。我們描述環境設計、底層物理與四旋翼飛行器動力學，並透過與 gym-pybullet-drones 專案相對應的控制與學習範例說明其應用，同時利用 MuJoCo 改良的接觸處理、渲染與可平行化性。

### 核心貢獻（3～5點）
- 基於 MuJoCo 物理引擎建構開源且相容 Gymnasium 的多無人機學習環境，可支援任意數量的 Bitcraze Crazyflie 2.x 微型四旋翼，並具備優於現有方案之接觸處理、渲染與可平行化性。
- 提供高度模組化 API，允許使用者彈性組合物理模型（剛體 MuJoCo、顯式 Python 動力學及進階氣動效應）、多層級動作介面（單馬達轉速至 PID 路徑點指令）與多模態觀測空間（狀態向量、RGB / 深度 / 分割相機及鄰域鄰接資訊）。
- 內建 PettingZoo ParallelEnv 包裝器，實現即插即用多智能體強化學習，無需額外橋接即可相容於現有多智能體 RL 流程。
- 提供七個涵蓋單機與多機任務的標準化環境（懸停、速度追蹤、多機懸停、路徑點導航、編隊飛行、閘門競速與通用多智能體模板），完整展示介面的廣度與通用性。

### 適合對象
從事空中機器人學、無人機控制與強化學習研究的學者與工程師，特別是需要高物理逼真度、多智能體協同支援，以及高吞吐量深度強化學習訓練流程的研究人員與開發者。

## 深度分析

#### 方法論解析

MuJoCo-Drones-Gym 的核心方法論在於將 gym-pybullet-drones 的設計理念（design philosophy）——輕量級、純 Python、可透過 pip 安裝——移植至 MuJoCo 物理引擎（physics engine），並透過模組化架構與 GPU 向量化（GPU vectorization）擴充其功能邊界。其方法論可從動力學建模、物理模式、軟體架構與硬體加速四個層次拆解。

在動力學層次，環境採用完整的剛體（rigid-body）狀態向量 x = [p, q, v, ω]ᵀ，其中 p 為世界座標位置，q 為符合 MuJoCo 慣例的 [w, x, y, z] 四元數（quaternion），v 與 ω 分別為線速度與角速度。控制輸入為四顆馬達的轉速 n（單位為 RPM，經換算後為 rad/s）。馬達模型（motor model）採用推力與反作用力矩與轉速成二次關係的經典假設，並針對 X 型配置（CF2X、RACE 級別）與十字型配置（CF2P）分別推導不同的滾轉／俯仰力矩分配矩陣。此處的關鍵技術選擇在於旋翼施力並非直接修改關節速度，而是透過 MuJoCo 的 xfrc（external force）機制施加於機體，這保留了 MuJoCo 內部隱式積分器（implicit integrator）的數值穩定性，同時允許研究者切換至顯式積分備援（explicit-integration fallback）以進行教學或除錯。

物理逼真度（physical fidelity）的調控是另一方法論亮點。環境提供六種物理模式（physics modes）：純 MuJoCo（pure MuJoCo）、含地面效應（ground effect）、含槳葉阻力（blade drag）、含機間下洗氣流（inter-drone downwash）、全組合（all-combined），以及顯式 Python 動力學（explicit Python dynamics）。三種空氣動力學效應（aerodynamic effects）可獨立開關：地面效應採用 Shi 等人的經驗模型，以旋翼半徑與離地高度之比修正推力；槳葉阻力採用 Forster 的速度比例模型，並以馬達轉速總和縮放；機間下洗氣流則引入 Dynamic Systems Lab（DSL）的 Zhou 模型。這種「可組合物理」的設計讓研究者能夠在控制理論測試平台（control-theory test-bed）所需的簡化模型，與深度強化學習流程（deep RL pipelines）所需的高逼真度模型之間無縫切換，而無需重寫環境核心。

在動作與觀測空間（action / observation space）的設計上，作者採用四層漸進式抽象：最底層為單馬達轉速（per-motor RPMs）；第二層為總歸一化推力（collective normalized thrust）搭配姿態力矩；第三層為速度設定點（velocity setpoints）；最頂層為 PID 路徑點指令（PID waypoint commands）。後兩者依賴內建的串級 PID 控制器堆疊（cascaded PID stack）（PIDControl / DSLPIDControl）作為內環（inner loop）。觀測端則提供運動學狀態向量（kinematic state vectors）、RGB / 深度 / 分割相機（RGB / depth / segmentation cameras），以及鄰域鄰接資訊（neighbourhood adjacency information）。這種模組化 API（modular API）確保了單一程式碼路徑即可支援從低階控制到高階感知的多樣化研究需求。

軟體架構方面，基底類別繼承自 Gymnasium 標準，並透過 PettingZoo ParallelEnv 包裝器（ParallelEnv wrapper）實現即插即用多智能體強化學習（drop-in multi-agent RL）。額外的可組合包裝器（composable wrappers）包含 Dryden 湍流與陣風場（Dryden-turbulence-plus-gust wind field）、六類程序生成障礙物（procedural obstacles）（森林／城市／室內／隨機／閘門／自定義），以及依據每回合指標（per-episode metrics）自動調整難度的自動課程（automatic curriculum）。這些包裝器不僅擴展了任務複雜度，也為領域隨機化（domain randomization）與穩健性驗證提供了標準化介面。

最具方法論突破的是 GPU 向量化後端。MJXVectorAviary 利用 MJX（MuJoCo 的 XLA 編譯 GPU 後端，XLA-compiled GPU back end）與 JAX 框架，透過 jax.vmap/jit 呼叫 在單一加速器（single accelerator）上執行數千個環境的批次模擬（batched simulation）。為了相容既有基於 NumPy 的強化學習函式庫（如 Stable-Baselines3），作者進一步提供 MJXVecEnvGymWrapper，將 MJX 的裝置陣列（device array）轉換為 Gymnasium VectorEnv 介面。這解決了傳統多無人機模擬器在吞吐量（throughput）與函式庫生態系之間的兼容性矛盾。

#### 實驗數據解讀

由於提供的文本摘錄在方法論（Section 3.1.3）後中斷，第 4 節與第 5 節的完整實驗數據與表 7（Table 7）並未呈現，因此以下分析側重於實驗設計邏輯、作者宣稱的效能指標，以及從方法論推導出的預期實驗意涵。

作者建構了七個任務環境（task environments）作為介面廣度的展示：懸停（Hover）、速度追蹤（Velocity Tracking）、多機懸停（Multi-Drone Hover）、路徑點導航（Waypoint Navigation）、編隊飛行（Formation Flight）、閘門競速（Gate Racing），以及通用多智能體模板（Generic Multi-Agent Template）。這涵蓋了單機穩態控制、動態追蹤、多機協同、競速避障與多智能體強化學習（Multi-Agent RL, MARL）等典型應用場景。圖 1 的 PID 懸停（pid hover）實驗顯示，在 z = 1 m 處，串級 PID 控制器堆疊（cascaded PID stack）可穩定控制 Bitcraze Crazyflie 2.x，這驗證了系統識別參數（system-identified parameters）與 MuJoCo 動力學的匹配度，也確認了離屏渲染器（offscreen renderer）與追蹤相機模式（track camera mode）的可用性。

在效能宣稱方面，作者指出底層 PyBullet 引擎在相同硬體上「比 MuJoCo 更慢且更不準確」，並強調 MuJoCo 在接觸處理（contact handling）、渲染（rendering）與可平行化性（parallelizability）上的優勢。這暗示第 5 節的正面交鋒（head-to-head comparison）應包含以下量化指標：模擬步驟吞吐量（sample throughput, steps/sec）、牆上時鐘訓練時間（wall-clock training time）、接觸穩定性（contact stability）與能量守恆誤差。若 MuJoCo 的隱式積分器確實在剛體碰撞與地面接觸中表現更穩定，則在閘門競速（Gate Racing）或程序生成障礙物（procedural obstacles）任務中，應能觀察到較低的數值發散率與較一致的回合終止條件。

MJX 後端（MJX back end）的實驗價值在於其對深度強化學習流程（deep RL pipelines）的影響。作者宣稱可於單一加速器（single accelerator）上批次模擬數千環境，這直接對應現代策略梯度方法（如 PPO、SAC）的環境互動瓶頸。預期實驗數據應顯示，相較於 PyBullet 的序列模擬或僅支援 CPU 向量化（vectorization）的方案，MJXVectorAviary 可達數量級的加速。然而，值得關注的是記憶體佔用與編譯開銷：jax.jit 的首次編譯時間（compilation time）在快速迭代實驗中可能構成隱性成本，而數千平行環境的狀態同步機制是否會在多機下洗氣流（inter-drone downwash）等耦合物理中引入數值誤差，亦需進一步檢驗。

此外，自動課程（automatic curriculum）與擾動包裝器（disturbance wrappers）的實驗應展示策略穩健性（robustness）的漸進提升。作者提到課程難度依據每回合指標（per-episode metrics）縮放，這暗示學習曲線（learning curves）應呈現非單調但長期上升的回報（return），而非傳統固定難度下的快速飽和。遺憾的是，由於缺乏完整的第 4 節內容，目前無法評估這些機制在具體任務上的收斂速度與最終策略品質。

#### 與現有研究的比較

MuJoCo-Drones-Gym 在無人機模擬器光譜中明確定位為 gym-pybullet-drones [1] 的現代化繼承者，並試圖填補「輕量級安裝、純 Python、Gymnasium 標準（community standard）」與「高物理逼真度（physical fidelity）、高吞吐量（throughput）、原生多智能體支援（multi-agent support）」之間的缺口。

相較於 gym-pybullet-drones，本工作保留了其作為比較基線（comparison baseline）的核心優勢——Python 優先、可 pip 安裝、以 Bitcraze Crazyflie 2.x 為中心——但進行了四項關鍵升級：物理引擎從 PyBullet 遷移至 MuJoCo，以獲得更精確的接觸處理（contact handling）與更快的模擬速度；API 從舊版 OpenAI Gym 升級至 Gymnasium 與 PettingZoo ParallelEnv 包裝器（ParallelEnv wrapper），符合現代社群標準（community standard）；新增基於 MJX 的 GPU 向量化（GPU vectorization），解決了 PyBullet 缺乏第一類 GPU 批次模擬（batched simulation）能力的問題；並擴充了空氣動力學模型與任務模板。這使得原先在 gym-pybullet-drones 上開發的基線控制器（baseline controller）與強化學習（RL）策略能夠以最小修改成本移植，同時享受後端效能提升。

與 safe-control-gym [11] 相比，後者雖同樣基於 PyBullet 且聚焦 Crazyflie，但其物理模型較為簡化，且未提供第一類多智能體或 GPU 向量化介面。CrazySwarm2 則專注於 ROS2 韌體迴路（firmware-in-the-loop）與真機整合，屬於硬體部署工具鏈，而非針對大規模強化學習的輕量基準。

Flightmare [12] 採用 Unity 進行渲染並搭配自定動力學引擎，雖具備高品質視覺，但安裝較重，且缺乏原生多智能體 API。MuJoCo-Drones-Gym 則以 MuJoCo 內建離屏渲染器（offscreen renderer）達成視覺觀測（RGB / 深度 / 分割相機），在保持輕量的同時，透過經廣泛驗證的物理引擎確保動力學可信度。

與 OmniDrones [13] 的比較最能凸顯本工作的定位差異。OmniDrones 基於 NVIDIA Isaac Sim / Isaac Lab，確實能提供極高的 GPU 吞吐量，但其緊密綁定專有 GPU 驅動程式與封閉生態系，限制了部署平台的廣泛性。MuJoCo-Drones-Gym 採用純 JAX / MJX 流程，透過 XLA 編譯 GPU 後端（XLA-compiled GPU back end）實現加速，不僅支援更廣泛的硬體與作業系統配置，也維持了開源標準的互通性。然而，這也意味著在絕對渲染品質與極大規模（數萬級）平行模擬上，OmniDrones 可能仍具優勢；MuJoCo-Drones-Gym 選擇的是在「開源彈性」與「吞吐量」之間取得平衡。

整體而言，MuJoCo-Drones-Gym 並非追求最高物理擬真（如 Gazebo 搭配 CFD）或最高 GPU 規模（如 Isaac Sim），而是精準佔據了「輕量級、開源、標準 API、高吞吐量多無人機強化學習」的利基（niche）。

#### 可重現性評估

本工作在可重現性（reproducibility）方面具備多項顯著優勢。首先，作者明確將專案開源 [7]，並採用 vendored 方式內嵌 Crazyflie 2.x 網格資源（meshes）於 multi_drone_mujoco/assets/cf2/ 目錄，使用者無需額外克隆完整的 MuJoCo Menagerie [9] 即可安裝。資源路徑亦可透過 MJ_DRONES_CF2_ASSETS 環境變數覆寫，這對於需要替換機型或進行外觀領域隨機化（domain randomization）的研究者十分友善。

動力學參數的透明度同樣值得肯定。環境直接採用 Forster [8] 的系統識別參數（system-identified parameters）作為 CF2X、CF2P 與 RACE 級別機型的預設值，這些參數來自已發表的實驗文獻，降低了「黑箱調參」的風險。六種物理模式（physics modes）與四種動作介面（action interface）的列舉式定義（Physics enum、action type enum）也確保了實驗條件可被精確復現。

在軟體生態相容性上，Gymnasium 與 PettingZoo 作為現今強化學習領域的社群標準（community standard），確保了與 Stable-Baselines3、RLlib 等主流函式庫的互通性。特別是 MJXVecEnvGymWrapper 的設計，彌合了 JAX 的裝置陣列與 NumPy 為基礎的強化學習流程之間的資料格式鴻溝，這對於希望利用 GPU 向量化（GPU vectorization）卻不願重寫訓練腳本的研究者至關重要。

然而，摘錄文本亦留下若干可重現性缺口。例如，作者雖提及與 gym-pybullet-drones 的範例鏡像對照，但未在提供的段落中詳述強化學習訓練的超參數（hyperparameters）、隨機種子（random seeds）協議、MJX 後端的 GPU 記憶體需求，或是否釋出預訓練權重（model weights）。此外，自動課程（automatic curriculum）的難度縮放函數形式、Dryden 風場的湍流強度預設值，以及程序生成障礙物（procedural obstacles）的隨機性邏輯，若能於附錄或程式碼文件中進一步文件化，將更有助於跨實驗室的嚴格復現。儘管如此，作為模擬器論文，其核心可重現產物——環境本身——已透過開源釋出與標準化 API 獲得充分保障。

#### 未來研究方向

基於 MuJoCo-Drones-Gym 的現有架構，未來研究可沿以下方向深化：

**物理與動力學擴充**：當前 MJX 後端（MJX back end）雖已支援大規模批次模擬（batched simulation），但 MJX 與原生 MuJoCo 在接觸模型與約束求解器上仍存在功能差距。未來可推動 MJX 的完整功能對齊，或整合更細緻的旋翼空氣動力學（如槳葉揮舞、渦環狀態、風切變），以進一步提升物理逼真度（physical fidelity）。此外，機型庫可擴展至傾轉旋翼、共軸雙槳或更大載重的無人機，超越現有的 Crazyflie 2.x 與 RACE 級別。

**模擬到現實（Sim-to-Real）遷移**：雖然環境已具備系統識別參數（system-identified parameters），但目前摘錄未提及與真機的系統性對齊實驗。未來可建立與 Bitcraze Crazyflie 硬體的直接橋接（類似 CrazySwarm2 的 ROS2 韌體迴路），並將領域隨機化（domain randomization）包裝器擴展為自動分佈學習（如基於現實誤差回饋調整隨機化範圍），以降低模擬到現實的表現落差。

**視覺強化學習（Vision-Based RL）**：環境已支援 RGB / 深度 / 分割相機（RGB / depth / segmentation cameras），但摘錄中未展示以像素為輸入的策略學習基準。未來可建構標準化的視覺觀測基準任務（例如以原始影像進行閘門競速或動態避障），並整合基於 NeRF 或 3D Gaussian Splatting 的程序場景，以縮小模擬影像與真實影像的分佈差異。

**多智能體強化學習（MARL）深化**：現有的 PettingZoo ParallelEnv 包裝器（ParallelEnv wrapper）提供了基礎的多智能體介面，但未來可進一步支援集中訓練分散執行（CTDE）架構、顯式通訊圖（communication graphs）與異質機群（heterogeneous swarms）。這將使環境能夠評估需要機間協調的複雜任務，如協同運輸或動態圍捕。

**自動課程與獎勵塑形**：目前的自動課程（automatic curriculum）依據每回合指標（per-episode metrics）線性縮放難度。未來可結合學習獎勵塑形（learned reward shaping）或目標生成網路（goal generation networks），讓課程不僅調整障礙密度與風速，更能主動生成對當前策略最具資訊量的初始狀態與目標配置。

**數位孿生（Digital Twin）整合**：在保留輕量級強化學習介面的同時，建立可選的 ROS2 橋接層，使 MuJoCo-Drones-Gym 能同時作為離線策略訓練平台與線上硬體監控的數位孿生體，這將大幅提升其在空中機器人學（aerial robotics）研究中的實用價值。

## 論文問答

**Q1：現有的四旋翼強化學習環境在物理逼真度、多智能體支援與模擬吞吐量之間，存在什麼樣的根本性權衡問題？**
A：現有模擬器往往難以同時兼顧高物理逼真度、多機協作支援，以及現代深度強化學習流程所需的高吞吐量。以 gym-pybullet-drones 為代表的廣泛使用環境雖然功能完整，但其底層 PyBullet 引擎在相同硬體上已比 MuJoCo 更慢且精確度較低，並且缺乏原生的 GPU 向量化能力。這種權衡使得研究人員在進行大規模平行訓練或需要精確接觸動力學的多機任務時，必須在模擬品質與訓練效率之間做出妥協。

**Q2：為何 gym-pybullet-drones 等現有模擬器無法滿足現代多智能體強化學習與控制研究的全部需求？**
A：gym-pybullet-drones 的底層 PyBullet 引擎不僅在速度與精確度上落後於 MuJoCo，更缺乏第一級的 GPU 向量化支援，難以利用現代加速器進行大規模批次模擬。此外，其 API 僅部分相容於已取代 OpenAI Gym 成為社群標準的 Gymnasium 與 PettingZoo 規範，導致整合現代 RL 函式庫時存在摩擦。這些限制使其在面對需要高平行度、精確接觸處理與標準化多智能體介面的研究時顯得力不從心。

**Q3：開發一個兼具高物理逼真度、多智能體支援與 GPU 加速的輕量級四旋翼模擬器，對空中機器人學研究有何重要性？**
A：機器人模擬器是現代空中機器人學研究的核心基石，既是新控制演算法的開發載具，也是訓練強化學習策略的資料來源。一個能同時提供精確物理、多機協作與大規模 GPU 平行訓練的開源環境，可顯著降低從模擬到真實（sim-to-real）遷移的門檻，並加速控制理論與深度 RL 的迭代研究。MuJoCo-Drones-Gym 正是在此背景下誕生，旨在填補輕量級、純 Python 且符合最新社群標準的多無人機模擬缺口。

**Q4：MuJoCo-Drones-Gym 的核心設計理念與技術架構是什麼？**
A：本論文提出的 MuJoCo-Drones-Gym 是一個建構於 MuJoCo 物理引擎之上的開源多無人機學習環境，完整相容 Gymnasium API 並透過 PettingZoo ParallelEnv 包裝器原生支援多智能體強化學習。其核心架構採用模組化設計，允許使用者自由組合六種物理模式、四種動作介面與多種觀測空間，並針對 Bitcraze Crazyflie 2.x 等機型提供系統識別參數與串級 PID 控制器。此外，透過 MuJoCo 的 MJX GPU 後端，系統能夠在單一加速器上利用 JAX 的 vmap/jit 機制批次模擬數千個環境，實現前所未有的訓練吞吐量。

**Q5：相較於現有模擬器，MuJoCo-Drones-Gym 的主要創新貢獻有哪些？**
A：其主要創新包括六種可選物理模式（涵蓋地面效應、槳葉阻力與機間下洗氣流）與基於 xfrc 的旋翼施力模型，讓使用者能在物理精確度與計算效率間彈性權衡。其次，內建 PettingZoo ParallelEnv 包裝器與 MJX 向量化後端，首次在輕量級純 Python 套件中同時提供標準化多智能體介面與 GPU 批次模擬能力。最後，七個即開即用的任務環境、可組合的擾動包裝器（風場、障礙物、自動課程）以及針對 MuJoCo 動力學調校的串級 PID 堆疊，大幅擴展了介面的廣度與易用性。

**Q6：在物理模型、動作介面與觀測空間的設計上，作者為何採用模組化與可組合的策略？**

## 實務應用指南

### 適用場景

**1. 大規模多機強化學習訓練與編隊驗證**  
若研究目標為開發十架以上微型無人機的協同策略（如分散式編隊、圍捕或協同搬運），可利用 `MultiAgentAviary` 與 PettingZoo `ParallelEnv` 包裝器，搭配 MJX GPU 向量化後端，在單張加速器上同時模擬數千個平行環境，顯著縮短 MARL 訓練週期。內建的 `FormationAviary` 與 `MultiHoverAviary` 可直接作為任務基線。

**2. 敏捷飛行與閘門競速的模擬到實機（Sim-to-Real）移植**  
針對 250g 競速機型或 Crazyflie 2.x 的自主穿越任務，`RaceAviary` 提供程序生成的閘門與障礙賽道。開發者可先以高更新頻率在 MuJoCo 中訓練視覺或狀態輸入的 RL 策略，再透過系統識別參數與網域隨機化（Domain Randomization）縮小模擬與真實動力學的差距，最終部署至實機。

**3. 強健控制器在擾動環境中的前置驗證**  
在將幾何控制器或串級 PID 部署到真實戶外場域前，可先啟用 Dryden 湍流與陣風場包裝器，並疊加 `FOREST` / `URBAN` 程序生成障礙物，驗證無人機在側風、陣風與狹窄空間中的抗擾能力。自動課程包裝器能根據每回合指標動態調整風速與障礙密度，逐步提升控制器強健性。

**4. 機載邊緣運算之輕量策略開發**  
由於本模擬器以純 Python 設計、支援 Gymnasium API，且內建 Crazyflie 2.x 的剛體與馬達模型，非常適合為資源受限的奈米無人機開發輕量觀測空間（如僅使用運動學狀態向量或鄰域鄰接資訊）與低維度動作介面（如速度設定點或歸一化總推力），後續再透過 ONNX 轉換至機載韌體。

**5. 自動化課程學習與工業巡檢任務原型**  
利用 `FlyThroughAviary` 與自動課程包裝器，可依據無人機在回合中的追蹤誤差或碰撞率，動態調整路徑點密度與環境難度。此流程適合快速迭代管線巡檢、倉儲盤點等需重複路徑規劃的商業場景原型。

### 實作前置條件

**資料需求**  
- 若目標為 Sim-to-Real，需準備目標機型的系統識別參數（質量、慣性張量、馬達推力係數、力矩係數、槳葉半徑等）。MuJoCo-Drones-Gym 已內建 Crazyflie 2.x（CF2X / CF2P）與 250g RACE 級別的識別參數；若使用自訂機型，需提供 URDF / MJCF 網格與對應動力學係數。  
- 視覺任務需額外準備閘門或障礙物紋理資料（可复用模擬器內建程序生成資源）。

**運算需求**  
- **基礎開發**：具備 AVX 指令集的現代 CPU、16 GB 以上記憶體、支援 OpenGL 的顯示卡（用於離屏渲染與視覺化）。  
- **大規模 RL 訓練**：NVIDIA GPU（建議 Compute Capability 7.0+，記憶體 8 GB 以上）以執行 MJX 的 XLA 編譯 GPU 後端；CPU 向量化作為備援方案。  
- **儲存空間**：預留 5–10 GB 用於 MuJoCo、JAX、網格資產與訓練記錄檔。

**技能需求**  
- 熟悉 Python 3.9+ 與物件導向設計，具備 Gymnasium / PettingZoo API 基礎。  
- 強化學習實作經驗（了解 PPO、SAC 等演算法與 Stable-Baselines3 或 RLlib 框架）。  
- 基礎控制理論（PID 調參、狀態空間表示法），以便理解內建控制器與動作介面的對應關係。  
- 若使用 MJX 後端，需了解 JAX 的函數轉換（`jit`、`vmap`）與不可變陣列語義。

### 實作步驟建議

**步驟一：環境安裝與基線驗證**  
透過 `pip install` 安裝套件後，優先執行 `examples/pid.py` 中的懸停範例，確認 MuJoCo 渲染器、Crazyflie 網格資產與 `MJ_DRONES_CF2_ASSETS` 路徑設定無誤。此步驟可驗證純 MuJoCo 物理模式與 `BaseAviary` 的基本迴路。

**步驟二：選定機型與物理模式**  
依據目標硬體選擇 `DroneModel.CF2X`、`CF2P` 或 `RACE`，並在 `Physics` 列舉中設定動力學保真度。若追求最高吞吐量且暫不考慮空氣動力學細節，可先使用 `Physics.PYB`（顯式 Python 動力學）或純 MuJoCo 模式；若需驗證近地飛行或機間干擾，則啟用地面效應、槳葉阻力與機間下洗氣流的全組合模式。

**步驟三：單機任務原型開發**  
從 `HoverAviary` 或 `VelocityAviary` 開始，選定動作介面（建議初學者先使用 `ActionType.VEL` 速度設定點，由內建串級 PID 處理低階馬達控制）。確認觀測空間（運動學狀態、RGB/深度相機或鄰域資訊）與獎勵函數符合任務需求後，再接入 Stable-Baselines3 或自訂 RL 演算法。

**步驟四：GPU 向量化擴展**  
將單環境訓練腳本遷移至 `MJXVectorAviary`，透過 `jax.vmap` / `jit` 將批次模擬平行化。若使用 NumPy 為主的 RL 函式庫，可透過 `MJXVecEnvGymWrapper` 包裝為 `GymnasiumVectorEnv`，維持與既有訓練流程的相容性。

**步驟五：疊加擾動與課程學習**  
在訓練中期引入 `WindFieldWrapper`（Dryden 湍流）與 `ObstaclesWrapper`，並啟用自動課程包裝器動態調整風速與障礙難度。此階段建議記錄每回合指標（追蹤誤差、能量消耗、碰撞次數）作為課程調整依據。

**步驟六：多智能體擴展（如適用）**  
將環境包裝為 PettingZoo `ParallelEnv`，使用 MAPPO、QMIX 等演算法進行多機訓練。利用 `neighbourhood adjacency` 觀測空間降低通訊假設，驗證分散式策略的可擴展性。

**步驟七：Sim-to-Real 匯出與驗證**  
將訓練完成的策略匯出為 ONNX 格式，並在真實 Crazyflie（透過 CrazySwarm2）或自訂飛控上進行軌跡比對。若發現顯著差距，可返回步驟二調整網域隨機化參數（如質量誤差 ±10%、推力係數誤差 ±15%），重新執行步驟四至六。

### 潛在風險與注意事項

**1. 模擬與真實動力學差距（Sim-to-Real Gap）**  
MuJoCo 的接觸處理雖優於 PyBullet，但微型無人機的槳葉彈性、電池壓降與馬達延遲仍難以完全建模。**緩解措施**：啟用全部空氣動力學模式（含機間下洗氣流），並在訓練後期加入顯著網域隨機化；同時保留 `Physics.PYB` 顯式積分備援模式作為真實動力學的對照組。

**2. MJX GPU 後端的功能限制**  
MJX 目前對部分 MuJoCo 進階接觸參數（如特定類型的約束求解細節）支援有限，且大規模向量化的記憶體消耗隨無人機數量線性增長。**緩解措施**：在需要精細碰撞（如閘門競速中槳葉擦撞）的場景，先以 CPU 版 MuJoCo 驗證物理正確性，再決定是否遷移至 MJX；並監控 JAX 裝置記憶體使用量。

**3. 動作介面與真實飛控不匹配**  
若使用 `ActionType.RPM` 直接輸出馬達轉速，真實 Crazyflie 的韌體可能採用不同控制架構（如速率環與姿態環分離）。**緩解措施**：優先採用 `ActionType.VEL` 或 `ActionType.PID` 路徑點指令，讓模擬器內建的 `DSLPIDControl` 作為內環，實機部署時也保留相同 PID 增益結構，降低介面轉換風險。

**4. 視覺渲染的效能瓶頸**  
啟用 RGB / 深度 / 分割相機時，MuJoCo 的離屏渲染器在單執行緒下可能無法餵飽現代 GPU 的 RL 訓練吞吐量。**緩解措施**：視覺任務建議採用獨立渲染執行緒或預先產生紋理，並評估是否將影像編碼器（Encoder）與策略網路分開訓練，以減少模擬器與訓練管線的耦合。

**5. API 版本與依賴衝突**  
Gymnasium、PettingZoo 與 JAX 生態系更新頻繁，可能發生 API 不相容。**緩解措施**：使用專案提供的 `requirements.txt` 或 `pyproject.toml` 鎖定版本，並在虛擬環境（venv / conda）中隔離開發。

### 與其他技術的整合建議

**1. ROS2 / CrazySwarm2 橋接**  
雖然 MuJoCo-Drones-Gym 本身為純 Python，但可透過 `rclpy` 建立輕量橋接節點，將模擬器的觀測（位置、速度）發布為 ROS2 Topic，並將指令（速度設定點或姿態指令）訂閱回模擬器。此架構可無縫銜接 CrazySwarm2 的真實機隊控制流程，實現「相同 Python 介面，模擬與實機一鍵切換」。

**2. Stable-Baselines3 與 RLlib**  
對於習慣 NumPy 生態的團隊，直接使用 `MJXVecEnvGymWrapper` 將 MJX 向量環境轉為 `GymnasiumVectorEnv`，即可餵入 SB3 的 PPO / SAC 進行訓練。若需要更進階的分散式訓練，可將 PettingZoo 包裝後的環境接入 RLlib 的 `ParallelPettingZooEnv`。

**3. 實驗追蹤與超參數調校**  
建議整合 Weights & Biases 或 TensorBoard，記錄不同物理模式（純 MuJoCo vs. 全組合）下的學習曲線、能量效率與碰撞率。自動課程包裝器的難度係數應作為獨立指標追蹤，以便分析策略強健性的成長軌跡。

**4. 模型部署與邊緣推論**  
訓練完成的策略可透過 JAX 的 `jax2tf` 轉換為 TensorFlow SavedModel，再進一步匯出為 ONNX，最終部署至 Crazyflie 的 STM32 微控制器（需量化）或機載 Raspberry Pi / Jetson（直接推論）。若使用 JAX 全生態，也可直接在邊緣裝置執行精簡後的 JAX 模型。

**5. 與高階渲染或數位孿生平台互補**  
若專案需要照片級真實感渲染（Photorealistic Rendering）或與 CAD 環境互動，可將 MuJoCo-Drones-Gym 作為「動力學與 RL 訓練後端」，透過 API 將狀態同步至 NVIDIA Isaac Sim / Omniverse 或 Unity Flightmare 進行視覺呈現，而非直接替代它們。

### 給不同背景讀者的閱讀建議

**給初學者**  
建議從 `examples/pid.py` 與 `examples/learn.py` 開始，先理解 `BaseAviary` 的 `reset()` 與 `step()` 流程，並嘗試在 `HoverAviary` 中調整 `ActionType.VEL` 的目標高度。暫時跳過 MJX 與空氣動力學細節，專注於熟悉 Gymnasium 的觀測與獎勵設計，待能穩定執行單機懸停後，再進入多機與 RL 範例。

**給 AI 工程師**  
重點閱讀第 3.4 節（觀測與動作空間設計）、第 3.5 節（包裝器機制）與第 3.6 節（MJX GPU 向量化）。請特別關注 `MJXVecEnvGymWrapper` 如何將 JAX 陣列轉換為 NumPy，以及不同 `ActionType` 對策略網路輸出層維度的影響。這些細節直接決定了你能否將現有 SB3 或自訂訓練管線無痛遷移至此環境。

**給研究人員**  
請深入檢視第 3.1 節的動力學推導、第 3.2 節的六種物理模式，以及附錄中的系統識別參數來源。若你的研究涉及 Sim-to-Real，需仔細比較 MuJoCo 與 PyBullet 在接觸處理與剛體積分上的差異（第 5 節）。對於多智能體研究，PettingZoo `ParallelEnv` 的實作細節與鄰域鄰接資訊的圖結構設計值得作為方法論章節引用。

**給產品經理**  
請聚焦第 4 節的七個任務環境與第 5 節的效能比較表。評估 MuJoCo-Drones-Gym 是否適合你的產品路線圖時，關鍵在於：它是否能在單一加速器上提供足夠的訓練吞吐量（相較於 gym-pybullet-drones 的顯著提升）、是否支援目標機型（Crazyflie 或 250g 競速機），以及其輕量安裝特性是否能縮短研究到原型（Research-to-Prototype）的週期。物理逼真度的模組化設計也意味著團隊可根據專案時程彈性取捨模擬精度與開發速度。
