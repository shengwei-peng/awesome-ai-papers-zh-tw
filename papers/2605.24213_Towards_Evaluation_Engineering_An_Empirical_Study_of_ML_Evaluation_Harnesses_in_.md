## ⚡ TL;DR

本研究分析57個評估套具，建立五階段模型，並大規模分類GitHubIssue的根本原因。
未實作功能、文件缺口與缺輸入驗證為主因，問題多集中規格階段，確立評估工程獨立領域地位。

## 摘要翻譯

評估套具（evaluation harnesses）是透過管理模型呼叫（model invocation）、資料載入（data loading）、指標計算（metric computation）與結果報告（result reporting）來編排（orchestrate）模型評估的軟體系統。儘管其在機器學習（machine learning, ML）基礎設施中扮演關鍵角色，其運作挑戰（operational challenges）與工程議題（engineering concerns）迄今仍少有探討。我們提出一項針對 57 個評估套具的實證研究（empirical study），推導出五階段套具模型（five-stage harness model），並依工作流程階段（workflow stage）與根本原因（root cause）將 16,560 個 Issue 予以分類。多數套具的運作挑戰集中於規格階段（Specification stage）（佔 Issue 的 41.4%），此階段涉及套具與外部模型（external models）、資料集（datasets）及評分裁判（scoring judges）之整合。運作挑戰最頻繁的三項根本原因為未實作功能（unimplemented features）（24.3%）、文件缺口（documentation gaps）（20.3%）與缺少輸入驗證（missing input validation）（17.2%），三者合計佔已分類 Issue 的 61.7%，涵蓋既有功能中的缺陷（defects in existing functionality）以及阻礙預期工作流程的能力缺口（capability gaps）。根本原因亦隨工作流程階段而異：環境不相容（environment incompatibility）與外部相依性損壞（external dependency breakage）佔供應問題（provisioning issues）的 36.2%，而演算法錯誤（algorithmic error）（25.9%）與驗證缺口（validation gap）（22.5%）則主導評估問題（assessment issues）。綜合以上貢獻，本研究為將評估工程（Evaluation Engineering, EvalEng）視為一項獨立的軟體工程（software engineering, SE）議題奠定了實證基礎。

### 核心貢獻（3～5點）
- 建立五階段套具模型（five-stage harness model）與工作流程階段導向的根本原因分類架構，並對 16,560 個 Issue 進行大規模分類，提供評估套具運作挑戰的系統性實證基礎。
- 發現多數運作挑戰集中於規格階段（Specification stage）（41.4%），且前三項根本原因——未實作功能（unimplemented features）、文件缺口（documentation gaps）與缺少輸入驗證（missing input validation）——合計佔比高達 61.7%，同時涵蓋既有功能缺陷與阻礙預期工作流程的能力缺口（capability gaps）。
- 揭示根本原因隨工作流程階段而異：供應問題（provisioning issues）多源於環境不相容（environment incompatibility）與外部相依性損壞（external dependency breakage），而評估問題（assessment issues）則主要由演算法錯誤（algorithmic error）與驗證缺口（validation gap）所主導。
- 確立評估工程（Evaluation Engineering, EvalEng）為一項獨立且值得深入研究的軟體工程（software engineering, SE）議題，銜接機器學習基礎設施與傳統軟體工程實踐。

### 適合對象
從事機器學習基礎設施、評估套具（evaluation harnesses）或基準測試（benchmark）開發之軟體工程師與研究人員；關注評分正確性（scoring correctness）、結果完整性（result integrity）及評估工作流程可靠度之評估工程師；以及研究軟體缺陷分類、開源專案維運與實證軟體工程方法之學者。

## 深度分析

#### 方法論解析

本研究採用混合式方法論（mixed-methods methodology），結合質性工作流程萃取與量化大規模議題分類，形成四階段研究架構。第一階段為**評估套具（evaluation harnesses）**之識別：作者透過精選來源（curated sources）與基於關鍵字的 GitHub 搜尋（keyword-based GitHub search），篩選出 57 個橫跨不同機器學習（ML）領域的開源評估套具，確保樣本涵蓋多樣的評估情境（diverse evaluation scenarios）。第二階段為工作流程模型之萃取：研究團隊針對套具文件與本地執行（local execution）紀錄，採用迭代式開放卡片分類法（iterative open card sorting），並以持續比較（constant comparison）反覆檢視資料，直至達到理論飽和（theoretical saturation）。此過程產出階層式工作流程模型（hierarchical workflow model），包含 5 個工作流程階段（workflow stages）、9 個步驟（steps）與 34 項具體實作策略（strategies），從環境設定（environment setup）一路涵蓋至結果報告（result reporting）。

第三階段為大規模 GitHub Issue 探勘（large-scale GitHub issue mining）：團隊自 57 個套具中挖掘 19,638 筆 GitHub Issue 報告（GitHub issue reports），內容涵蓋錯誤報告（bug reports）、功能請求（feature requests）與使用問題（usage questions）。第四階段則是大規模分類：研究人員先以人工建立共識標籤，再訓練 LLM-based 分類器（LLM-based classifiers）進行自動標註，並以 Cohen's κ > 0.87 的標準驗證人機一致性。分類維度包含兩軸：一是將議題對應至五階段套具模型（five-stage harness model）中的特定工作流程階段；二是歸因至根本原因分類法（root cause taxonomy）中的 10 項類別，同時涵蓋軟體缺陷（software defects）與能力缺口（capability gaps）。

此方法論的優勢在於以質性扎根確保模型的領域適切性，再以 LLM 擴充規模至近兩萬筆議題，兼顧理論深度與統計廣度。然而，潛在限制在於樣本僅涵蓋公開於 GitHub 之開源專案，未包含企業內部閉源之商業評估基礎設施；此外，Issue 報告的品質與完整度取決於使用者回報意願，可能存在沉默失效（silent failures）未被記錄的系統性偏差。

#### 實驗數據解讀

在 19,638 筆挖掘出的議題中，最終有 16,560 筆完成分類。數據顯示，**規格階段（Specification stage）**是運作挑戰（operational challenges）最為集中的環節，佔全部議題的 41.4%。此階段涉及外部模型（external models）、資料集（datasets）與評分裁判（scoring judges）的整合，本質上是一種高風險的邊界操作。細部拆解發現：在模型準備（model preparation）議題中，與遠端模型 API 整合相關的問題（如認證失敗、端點變更與速率限制）佔了 48.5%；而在輸入準備（input preparation）議題中，離線基準測試資料（offline benchmark data）的載入與存取問題（如資料可用性變更、格式不匹配與前置處理失敗）更高達 76.4%。這顯示評估套具並非自給自足的軟體系統，其可靠性高度繫於外部生態系統的波動。

根本原因（root causes）的分布則揭示了一項與直覺相悖的現象：評估套具的主要工程負擔並不在於指標計算（metric computation）的演算法正確性，而在於操作化（operationalization）的摩擦。未實作功能（unimplemented features，24.3%）、文件缺口（documentation gaps，20.3%）與缺少輸入驗證（missing input validation，17.2%）三者合計佔 61.7%，遠高於評分錯誤（scoring errors，8.3%）。這意味著開發者與使用者耗費最多心力在「讓套具跑起來」而非「確保評分數學正確」。

進一步觀察各階段的失效組成（failure composition），可發現明顯的階段特異性：在供應問題（provisioning issues）中，環境不相容（environment incompatibility）與外部相依性損壞（external dependency breakage）合計佔 36.2%，反映環境配置與相依性管理（dependency management）是評估工程（EvalEng）的基礎痛點；而在評估問題（assessment issues）中，演算法錯誤（algorithmic error，25.9%）與驗證缺口（validation gap，22.5%）則佔據主導，顯示一旦進入實際評分階段，計算正確性與輸入驗證便成為核心風險。

最後，研究亦揭露工程採用缺口（engineering adoption gaps）：僅 22.8% 的套具提供不確性量化（uncertainty quantification），而僅 8.8% 具備迴歸警示（regression alerting）能力。這表明當前評估套具普遍停留在「能執行單次評估」的工具層次，尚未全面進化為具備生產環境監控意識的可靠軟體基礎設施（software infrastructure）。

#### 與現有研究的比較

既有文獻多從方法論視角（methodological perspectives）探討 ML 評估，聚焦於應計算何種指標、應測試何種能力，或基準測試設計（benchmark design）中的汙染、標註錯誤與可重現性等議題。這些研究回答的是「what to evaluate」，但將執行評估的軟體基礎設施視為透明媒介（transparent medium），並未將其當作軟體產品（software products）進行系統性檢視。相較之下，本文明確提出**評估工程（EvalEng）**作為軟體工程（SE）的獨立關懷領域，將研究焦點從「評估什麼」轉移至「如何可靠地操作化評估」。

與 HELM、LMEval、BigCodeEval 等專案相關文獻不同，本文並非提出新的基準測試（benchmark）或評分指標，而是將這些專案背後的評估套具視為研究客體，分析其運作工作流程（operational workflows）與使用者摩擦。這種「後設基礎設施」（meta-infrastructure）視角補足了驗證不對稱（verification asymmetry）文獻的缺口：過去研究強調可靠的驗證基礎設施是 ML 進步的前提，卻未深入探討該基礎設施本身的工程脆弱性。

本研究的限制在於其橫斷面（cross-sectional）特性：議題數據反映的是特定時間點的狀態，未能捕捉評估套具隨版本演進的縱向動態。此外，GitHub Issue 報告作為資料來源，雖能反映使用者遭遇的顯性問題，卻難以捕捉設計層面的深層缺陷（如架構債務）或組織內部的流程失敗。相較於傳統軟體工程領域對建置系統（build systems）或持續整合／持續部署（CI/CD）的長期實證研究，EvalEng 仍處於奠基階段，亟需更多縱向與質性深度訪談的互補研究。

#### 可重現性評估

根據本文提供之脈絡，研究主要依賴公開可取得之資料來源（57 個開源評估套具及其 GitHub Issue 報告），理論上具備高度可重現性（reproducibility）之潛力。然而，文中並未明確提及是否釋出複製套件（replication package），包含議題資料集、LLM-based 分類器之提示詞（prompts）、人工標註準則或分類程式碼。由於分類過程涉及 LLM 校準與人類共識標籤（human consensus labels），若缺乏公開之標註指南與模型參數設定，其他研究者難以完全複製其 16,560 筆議題的分類結果。

工作流程模型之萃取雖採用標準的開放式卡片分類法（open card sorting）與持續比較，但具體的編碼手冊（codebook）與原始卡片資料亦未在節錄中交代。對於一門新興領域（EvalEng）而言，建立可重複使用的公開資料集與自動化分類工具，將是推動社群接納的關鍵。建議後續研究釋出經去識別化處理之 Issue 語料庫與分類標籤，並提供容器化（containerized）的環境以重現本地執行（local execution）之分析流程，從而降低後續研究者進入此領域的門檻。

#### 未來研究方向

基於本文所建立之實證基礎，未來研究可沿以下數個方向深化評估工程（EvalEng）領域：

1. **自動化相依性健康監測**：由於外部相依性損壞（external dependency breakage）與環境不相容（environment incompatibility）是供應問題（provisioning issues）的主因，可發展針對評估套具的相依性管理（dependency management）工具，自動偵測遠端 API 端點變更、資料集版本漂移（dataset version drift）與評分裁判模型之更新。

2. **輸入驗證與文件之形式化驗證**：鑑於缺少輸入驗證（missing input validation）與文件缺口（documentation gaps）合計佔近四成議題，未來可探索文件驅動開發（documentation-driven development）或自動化文件驗證框架，確保組態驅動的評估工作流程（configuration-driven evaluation workflows）之每項參數皆有明確的結構化規格與執行期檢查。

3. **生產導向能力之標準化**：目前不確性量化（uncertainty quantification）與迴歸警示（regression alerting）的採用率極低。後續研究可制定 EvalEng 之成熟度模型，將結果完整性（result integrity）、評分正確性（scoring correctness）監控與跨版本效能退化偵測納入最佳實踐，並設計對應的開源工具鏈。

4. **跨領域與縱向比較研究**：本文樣本橫跨多個 ML 領域，但未深入分析自然語言處理（NLP）、電腦視覺（CV）或強化學習（RL）之間的差異。未來可針對特定領域進行分層分析，並以縱向研究（longitudinal study）追蹤同一套具在不同版本週期中的議題演化，識別技術債務（technical debt）的累積模式。

5. **評分裁判之信任與安全性**：隨著越來越多套具依賴外部模型作為評分裁判（scoring judges），其潛在的偏誤、對抗性攻擊與 API 供應商鎖定（vendor lock-in）問題尚未被充分探討。未來可發展裁判模型之校準、可解釋性與替代性評分機制，以強化評估結果的穩健性。

6. **開發者體驗（Developer Experience, DX）與人為因素**：除了技術性根本原因，亦可透過使用者訪談與可用性測試，深入理解套具開發者與使用者在操作化（operationalization）過程中的認知負荷與決策行為，從而設計更符合人體工學的評估套具介面與錯誤訊息。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文指出，儘管評估套具（evaluation harnesses）在機器學習基礎設施中扮演著編排模型呼叫、資料載入、指標計算與結果報告的關鍵角色，但其運作挑戰與工程議題至今仍未受到軟體工程學界的足夠重視。現有的研究多從方法論視角探討該評估什麼能力或使用什麼指標，卻忽略了當評估被操作化（operationalized）為實際軟體系統時所引發的軟體工程難題。因此，本文旨在填補這項缺口，將評估套具視為軟體產品進行實證研究，並提出「評估工程（EvalEng）」作為一個獨立的軟體工程關注領域。

**Q2：為何現有的機器學習評估研究無法有效解決實務上的痛點？**
A：現有文獻主要聚焦於基準測試設計、衡量指標選擇以及模型能力測試等方法論問題，探討的是「該評估什麼」，而非「如何可靠地執行評估」。這些研究通常將執行評估的軟體基礎設施視為透明的媒介，未能深入檢視套具在實際運作中遭遇的相依性管理、評分正確性、結果完整性與環境設定等工程挑戰。由於缺乏對操作化過程中軟體工程議題的系統性理解，開發者與使用者往往只能面對支離破碎的文件、未實作的功能與頻繁的外部相依性損壞，而無法從現有方法論研究獲得實質的工程指引。

**Q3：為何將評估套具視為軟體產品進行研究具有重要性？**
A：人工智慧的進步在很大程度上依賴於「驗證不對稱性」，即驗證解方案遠比生成解方案容易，而這種不對稱性使得機器學習的發展速度直接繫於評估基礎設施的可靠性。無論是偵測基準測試資料污染、確保結果可重現，或是處理框架不相容與標註錯誤等問題，其最終能否被解決都取決於評估套具的軟體工程品質。若忽視評估套具作為軟體產品的工程屬性，將導致研究社群難以建立穩定、可重複且可擴展的評估流程，進而阻礙模型進展的衡量與比較。

**Q4：本研究採用的核心方法論為何？**
A：本研究採用四階段方法論，結合質性工作流程萃取與大規模 GitHub Issue 探勘。首先，研究者透過精選來源與基於關鍵字的 GitHub 搜尋確立 57 個評估套具；接著運用迭代式開放卡片分類法與本地執行，從文件與實際操作中萃取出一套階層式工作流程模型。最後，研究團隊探勘 19,638 筆 GitHub Issue 報告，並使用經人工共識標註校準（κ > 0.87）的 LLM 分類器，將這些議題大規模映射至工作流程階段與根本原因類別，以兼顧質性深度與量化廣度。

**Q5：相較於既有文獻，本研究的主要創新貢獻是什麼？**
A：本研究首次系統性地將評估套具視為軟體產品進行實證分析，並明確提出「評估工程（EvalEng）」作為一個有別於傳統機器學習方法論的獨立軟體工程領域。研究不僅建構了包含五階段、九步驟與三十四項策略的運作工作流程模型，更從 16,560 筆已分類的 GitHub Issue 中歸納出涵蓋軟體缺陷與能力缺口的根本原因分類法。這些貢獻將過去分散且隱性的評估操作經驗，轉化為可分析、可比較且可指導工程實踐的系統性知識。

**Q6：作者為何選擇分析 GitHub Issue 並採用 LLM 分類器作為主要研究手段？**
A：GitHub Issue 報告包含了錯誤報告、功能請求與使用問題，能真實反映開發者與使用者在實際運作評估套具時遭遇的摩擦與痛點，是萃取運作挑戰的豐富質性資料來源。然而，人工分析近兩萬筆議題在規模上並不可行，因此作者採用 LLM 分類器進行大規模自動標註，並透過與人工共識標籤校準以確保高一致性（κ > 0.87）。這種設計選擇使得研究能夠在維持分類品質的同時，對橫跨 57 個套具的營運挑戰進行量化統計與階段映射。

**Q7：本研究的資料範圍與分析對象涵蓋哪些層面？**
A：本研究的對象包含從精選來源與 GitHub 搜尋中篩選出的 57 個開源評估套具，並從中探勘了 19,638 筆 GitHub Issue 報告。在質性分析方面，研究透過開放式卡片分類與持續比較，歸納出包含五個工作流程階段、九個步驟與三十四項具體實作策略的運作模型。在量化分析方面，則針對 16,560 筆已分類議題，建立包含十個類別的根本原因分類法，並統計各類問題在不同階段的分布與盛行率。

**Q8：研究中最關鍵的實證發現為何？**
A：研究發現，評估套具的運作挑戰主要集中在規格階段（Specification stage），該階段佔了所有議題的 41.4%，顯示整合外部模型、資料集與評分裁判是當前最大的工程負擔。在根本原因方面，未實作功能（24.3%）、文件缺口（20.3%）與缺少輸入驗證（17.2%）三者合計佔了 61.7%，遠高於演算法錯誤或評分錯誤（僅 8.3%）。這項結果明確指出，評估套具的主要工程難題並非來自指標計算本身的正確性，而是來自操作化過程中的整合、可用性與功能完整性缺口。

**Q9：不同工作流程階段的根本原因分布有何差異，這揭示了什麼意涵？**
A：研究顯示，各階段的失效組成（failure composition）具有顯著差異：在供應階段（Provisioning），環境不相容與外部相依性損壞合計佔了 36.2%，凸顯環境設定與資源配置的高度脆弱性。相對地，在評估階段（Assessment），演算法錯誤（25.9%）與驗證缺口（22.5%）則佔據主導地位，反映指標計算與結果驗證的複雜性。這種階段性的分布差異意謂著改善評估套具可靠性不能採取一體適用的策略，而必須針對不同階段設計專屬的工程實踐與測試機制。

**Q10：這些研究發現對哪些實務情境具有立即的指導意義？**
A：對於評估套具開發者而言，研究結果明確指出應優先強化規格階段的外部整合能力，例如改善遠端模型 API 的認證機制、端點穩定性，以及離線基準測試資料的格式相容性。對於使用者來說，當遭遇運作挑戰時，可依據根本原因分類法快速定位問題是出自文件缺口、未實作功能或是輸入驗證不足，從而縮短除錯時間。對於企業與研究機構，這些發現也提醒在導入開源評估套具時，必須預留額外工程資源處理操作化過程中的整合與維護成本，而非僅關注評估指標的理論正確性。

**Q11：目前多數評估套具在生產導向能力方面存在哪些不足？**
A：研究發現，評估套具對於生產環境所需能力的採用極不均衡，僅有 22.8% 的套具會對分數進行不確定性量化（uncertainty quantification），而提供迴歸警示（regression alerting）以偵測多次執行間分數退化者更只有 8.8%。這些工程採用缺口（engineering adoption gaps）顯示現今多數評估套具仍偏向研究原型，缺乏持續監控、穩定性保證與統計嚴謹性。若評估結果無法伴隨信賴區間或自動化警示，將難以在實際產品開發流程中作為可靠的決策依據。

**Q12：這項研究可能對機器學習與軟體工程領域帶來哪些深遠影響？**
A：本研究為「評估工程（EvalEng）」奠定了實證基礎，促使學界與業界將焦點從「該評估什麼」轉向「如何工程化地執行評估」，這類似於過去數十年間 DevOps 運動如何將部署與維運轉變為獨立的工程學科。透過建立統一的工作流程模型與根本原因分類法，研究為後續的套具測試技術、自動化驗證工具與評估即服務（Evaluation-as-a-Service）平台的發展提供了理論架構。長遠來看，這將有助於提升整個人工智慧生態系統的評估可靠性，使模型比較與進展追蹤建立在更穩固的軟體工程基礎之上。

**Q13：本研究在方法論上可能存在哪些限制？**
A：由於研究資料主要來自開源社群的 GitHub Issue 報告，這可能產生倖存者偏差，因為只有活躍且公開的專案才會被納入分析，而內部專有的評估系統則未被涵蓋。此外，Issue 的內容通常由遇到問題的使用者主動回報，這意味著某些沉默型失效（silent failures）或未被使用者察覺的缺陷可能會在資料中代表性不足。雖然 LLM 分類器已透過高一致性（κ > 0.87）的人工標註進行校準，但自動分類仍可能遺漏部分細微的語境脈絡，特別是在處理跨階段的複合性問題時。

**Q14：這項研究的根本原因分類法可能無法完全涵蓋哪些類型的評估失效？**
A：本研究的根本原因分類法主要聚焦於操作化過程中的軟體工程挑戰，例如整合失敗、文件缺口與輸入驗證不足，而非基準測試方法論本身的根本缺陷，例如指標設計是否真正反映模型能力。某些隱蔽的品質問題，如基準測試資料污染或標註錯誤，若未被使用者察覺並回報為 GitHub Issue，則不會出現在研究的議題資料集中。因此，對於那些源自評估設計哲學或資料品質、但尚未在套具操作層面爆發的失效模式，本研究的分析框架可能較難直接捕捉。

**Q15：這項研究指出了哪些未來的研究方向？**
A：基於所發現的工程採用缺口，未來研究可聚焦於開發自動化的套具測試技術，例如針對外部相依性損壞與環境不相容的持續整合（CI）管線，以及標準化的模型與資料集介面以降低整合成本。另一個重要方向是將不確定性量化與迴歸警示等生產導向能力內建為評估套具的核心功能，而非可有可無的附加元件。此外，由於本研究僅涵蓋開源套具，未來亦需深入調查企業內部專有評估基礎設施的工程實踐，以建立更完整的評估工程知識體系。

## 實務應用指南

### 適用場景

1. **企業級大型語言模型驗收平台**：需統一評估多家供應商（如 OpenAI、Anthropic 或本地開源模型）的 API 與權重，管理多版本資料集與評分裁判模型，並以組態驅動的評估工作流程自動化執行。
2. **MLOps 管線中的回歸偵測閘道**：在持續整合／持續部署（CI/CD）中嵌入評估套具，於模型上線前自動執行基準測試，偵測分數退化並觸發警示。
3. **多模態研究再現性基礎設施**：學術團隊建立標準化評估套具，統一編排影像、音訊、文字等資料載入與指標計算，確保外部研究者能重現論文結果。
4. **第三方模型採購驗證**：金融或醫療產業在導入外部模型前，利用標準化套具驗證供應商宣稱的效能數據，降低操作化風險。
5. **開源模型社群排行榜營運**：如 HELM 或 LMEval 生態系，需處理大規模外部相依性與多樣的評估情境，並對社群回報的 GitHub Issue 報告進行系統性根因分析。

### 實作前置條件

- **資料**：結構化基準測試資料集（含黃金標準標籤）、模型輸出範本、評分裁判模型（judge model）或規則型評分器、歷史評分結果作為迴歸基線。
- **運算**：具 GPU／TPU 的執行節點（視模型規模而定）、隔離的容器化環境（Docker／Kubernetes）以管理相依性，以及穩定的外部模型 API 配額。
- **技能**：熟悉 Python 與主流機器學習框架（PyTorch／TensorFlow）、軟體工程實務（版本控制、CI/CD、相依性管理），以及評估指標的統計基礎與不確定性量化方法。

### 實作步驟建議

1. **工作流程解構（Specification）**：依據本文提出的五階段套具模型，將評估流程拆解為規格、供應、執行、評估、報告。優先定義外部模型、資料集與評分裁判的介面抽象層，隔離供應商差異。
2. **環境供應與相依性凍結（Provisioning）**：建立可重現的執行環境（如 requirements.lock、Docker image），鎖定外部套件版本；針對環境不相容與外部相依性損壞預留隔離與降級機制。
3. **防禦式輸入驗證**：在資料載入與模型呼叫階段導入嚴格的輸入驗證，處理格式不符、前處理失敗、端點變更與認證失效，降低運作挑戰。
4. **指標計算與不確定性量化（Assessment）**：實作指標計算模組時同步建立單元測試與交叉驗證；導入不確定性量化與分數迴歸警示，補足目前業界採用率偏低的能力缺口。
5. **文件化與錯誤處理**：建立操作手冊與疑難排解指南，填補文件缺口；針對未實作功能提供清晰的錯誤訊息與替代方案，減少使用者摩擦。

### 潛在風險與注意事項

- **規格階段整合風險**：外部模型 API（認證失敗、端點變更、速率限制）與離線資料集（資料可用性變更、格式不符）集中了 41.4% 的議題。建議實作 Adapter 模式隔離外部變動，並對 API 回應與資料格式進行語意版本控管。
- **相依性漂移**：環境不相容與外部相依性損壞佔供應問題的 36.2%。應避免直接依賴最新版套件，採用鎖定檔與定期回歸測試，並在容器層級快取已知良好的環境快照。
- **演算法錯誤與驗證缺口**：評估階段中演算法錯誤（25.9%）與驗證缺口（22.5%）為主因。任何新指標上線前，需以已知輸入進行手工驗算（sanity check），並建立黃金標準測試集防止指標計算偏差。
- **文件缺口與隱性假設**：20.3% 的問題源於文件缺口。需明確記錄前處理步驟、隨機種子設定、硬體需求與預期執行時間，避免再現性危機與使用者因隱性假設而產生的誤用。

### 與其他技術的整合建議

- **MLOps 平台**：將評估套具整合至 Kubeflow、MLflow 或自研 CI/CD 管線，透過組態驅動觸發評估工作流程，並將結果報告寫入實驗追蹤系統，實現結果完整性管理。
- **資料版本控制**：搭配 DVC 或 Git LFS 管理基準測試資料集版本，確保規格階段載入的資料與原始論文或上一版模型一致，避免資料污染（contamination）。
- **監控與可觀測性**：串接 Prometheus／Grafana 追蹤 API 速率限制、執行時間與資源使用率；將評分結果與不確定性區間匯入監控儀表板，作為模型部署閘道。
- **大型語言模型服務框架**：若評估涉及 LLM，可透過 LiteLLM、vLLM 或 TGI 的統一介面進行模型呼叫，減少因供應商 API 差異導致的整合負擔與軟體缺陷。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從 RQ1（五階段套具模型）與 RQ3（階段與根本原因對應）入手，先理解評估套具的完整生命週期與常見陷阱。實作時可選擇 LMEval 或 HELM 等成熟開源專案進行改裝，而非從零建構，並特別留意文件缺口與缺少輸入驗證這兩類高頻問題。
- **AI 工程師**：重點閱讀 RQ2（根本原因分類法）與第 7 節工程意涵。關注規格階段的抽象層設計、輸入驗證機制，以及如何在 CI/CD 中導入不確定性量化與迴歸警示，以提升套具可靠性與生產就緒度。
- **研究者**：建議深入方法論與效度威脅章節，評估本文提出的階層式工作流程模型與根本原因分類法是否適用於您的研究領域。可將評估工程（EvalEng）視為獨立於方法論視角的軟體工程研究主題，探討其與軟體可靠性、經驗軟體工程的連結。
- **產品經理**：聚焦摘要與討論章節，掌握「41.4% 的問題集中在規格階段」與「文件缺口佔 20.3%」這兩項關鍵數據。在規劃評估基礎建設時，優先配置工程資源於外部整合與文件化，而非僅追求指標計算的複雜度，以有效降低運作挑戰與維護成本。
