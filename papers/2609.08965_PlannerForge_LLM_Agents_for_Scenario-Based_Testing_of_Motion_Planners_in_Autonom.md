# PlannerForge：用於自動駕駛運動規劃器基於情境測試的 LLM 代理框架

**原文標題：** PlannerForge: LLM Agents for Scenario-Based Testing of Motion Planners in Autonomous Driving  
**作者：** Yuan Gao、Sebastian Müller、Mattia Piccinini 等 8 位作者  
**發布日期：** 2026-09-08  
**HF 連結：** [https://huggingface.co/papers/2609.08965](https://huggingface.co/papers/2609.08965)

## ⚡ TL;DR

自動駕駛情境測試流程分散且手動，缺乏統一整合。
提出PlannerForge，以LLM代理整合情境生成、檢索、修改、測試與增強。
開源20–35B模型在多數任務媲美商業API，成本調校使成功率自50.4%升至70.2%。

## 摘要翻譯

確保自動駕駛（Autonomous Driving）的安全性是一項關鍵挑戰。基於情境的測試（Scenario-based Testing）是驗證自動駕駛系統（Autonomous Driving Systems, ADSs）的系統化流程，但目前仍屬片段化的模組化流程（Modular Pipeline），情境生成（Scenario Generation）、情境檢索（Scenario Retrieval）、情境修改（Scenario Modification）、ADS 執行（ADS Execution）與結果分析（Results Analysis）等階段由不同工具分別執行，彼此間缺乏互動。大型語言模型（Large Language Model, LLM）代理（Agents）雖已在 ADS 的感知、規劃與控制（Perception, Planning, and Control）等子系統中展現潛力，然而先前研究尚未以統一的 LLM 代理（LLM-agent）框架涵蓋 ADS 完整的基於情境測試流程。本研究提出 PlannerForge，一個擴展基於情境測試所有階段（從情境生成到 ADS 評估（ADS Assessment））並新增兩個經 LLM 強化階段（ADS 增強（ADS Enhancement）與 ADS 基準測試（ADS Benchmarking））的 LLM 代理框架。我們以 10 個現成的大型語言模型（Off-the-shelf LLMs），在 5 種提示條件（Prompt Conditions）下對所有任務（生成（Generation）、選擇（Selection）、修改（Modification）、模組路由（Module Routing）、規劃器測試（Planner Testing）與增強（Enhancement））評估 PlannerForge。各任務最佳分數（Best-per-task Scores）介於 0.88 至 1.00 之間，開源 20–35B 後端模型（Open-source 20–35B Backends）在多數任務上可與商業 API（Commercial APIs）匹敵；其中 Qwen3.6:35B 在五項任務中的三項達到與商業 API 相當的表現。將各模組端到端串聯（End-to-end Chaining）後，可保留 83% / 78% 的種子查詢（Seed Queries）（商業 API / 開源模型）。在自然語言生成（Natural-language Generation）方面，PlannerForge 優於 Scenario Factory 2.0（Finkeldei 等人，2025），在 200 個情境中分別產生 193 個與 144 個可執行（Executable）情境，且請求的城市、道路與車輛屬性（City, Road and Vehicle Attributes）實現率（Attribute Realization Rate）達 92–96%。在排名第一選擇（Rank 1 Selection）任務中，PlannerForge 優於 BM25（Robertson 與 Zaragoza，2009）（92.0% 對 67.5%）；在物理上有效的編輯（Physically Valid Edits）任務中，優於 From-Words-to-Collisions（Gao 等人，2025）（≥94% 對 31%）。當 N=400 時，成本調校（Cost-tuning）將規劃器成功率（Planner Success Rate）從 50.4% 提升至 70.2%，並將碰撞率（Collision Rate）從 19.0% 降至 8.4%，且無須進行領域特定微調（Domain-specific Fine-tuning）。

### 核心貢獻（3～5點）
- 提出 PlannerForge，首個以統一 LLM 代理框架涵蓋 ADS 完整基於情境測試生命週期（從情境生成到 ADS 評估），並新增 ADS 增強與 ADS 基準測試兩個 LLM 強化階段。
- 在六項核心任務（生成、選擇、修改、模組路由、規劃器測試、增強）上進行系統化評估，最佳分數達 0.88–1.00，且開源 20–35B 模型在多數任務可與商業 API 匹敵。
- 端到端串聯各模組後仍保留 83%（商業 API）/ 78%（開源模型）的種子查詢，顯示框架在完整流程中的穩定性。
- 在多項對照實驗中超越既有基線：自然語言生成優於 Scenario Factory 2.0、排名第一選擇優於 BM25、物理上有效的編輯優於 From-Words-to-Collisions。
- 透過成本調校（無須領域特定微調）將規劃器成功率從 50.4% 提升至 70.2%，並將碰撞率從 19.0% 降至 8.4%。

### 適合對象
適合自動駕駛驗證、運動規劃、LLM 代理應用，以及情境基礎安全測試領域的研究人員與工程師；特別是關注如何以統一 LLM 框架整合情境生成、檢索、修改、評估、增強與基準測試，並希望以開源模型降低對商業 API 依賴的讀者。

## 深度分析

#### 方法論解析

##### 整體定位與生命週期
PlannerForge 是一個以對話機器人（chatbot）為介面的 LLM-agent（大型語言模型代理）框架，目標是將傳統上高度碎片化的 scenario-based testing（基於情境的測試）流程整合為單一、可互動的端到端（end-to-end）管線。相較於過去研究多聚焦於單一階段（如 scenario generation（情境生成）），PlannerForge 覆蓋了 Riedmaier 等人提出的六個經典階段——Scenario Source（情境來源）、Scenario Generation（情境生成）、Scenario Database（情境資料庫）、Scenario Selection（情境選擇）、Test Execution（測試執行）、ADS Assessment（ADS 評估）——並額外加入兩個 LLM 時代的階段：ADS Enhancement（ADS 增強）與 ADS Benchmarking（ADS 基準測試）。整個流程圍繞 motion planners（運動規劃器）進行，因為規劃器是 ADS（自動駕駛系統）的核心決策模組，其行為對複雜且 safety-critical situations（安全關鍵情境）特別敏感。

##### 問題形式化
作者將 LLM 驅動的基於情境測試形式化為一連串「自然語言 → 結構化輸出」的決策過程：

- 令 \(U\) 為自然語言語句空間、\(S\) 為開源二維運動規劃模擬器產出的情境空間、\(D \subseteq S\) 為 curated database（精選資料庫）、\(\Theta\) 為 motion-planner configurations（運動規劃器組態）、\(H\) 為對話歷史、\(O\) 為執行結果、\(Y\) 為自然語言分析。
- 在第 \(t\) 輪對話中，代理觀察到的輸入為  
  \[
  x_t = (u_t, s_t, \theta_t, h_t)
  \]
  其中 \(u_t \in U\) 為使用者語句、\(s_t \in S\) 為當前情境、\(\theta_t \in \Theta\) 為規劃器組態、\(h_t \in H\) 為歷史。
- 對話起始時，系統透過 Generation 或 Selection 產生初始情境 \(s_0\)：
  \[
  f_{\text{gen}}: U \to S \quad \text{或} \quad f_{\text{sel}}: U \times D \to D
  \]
- 後續輪次則由 Module Router（模組路由器）根據使用者語句 \(u_t\) 與對話歷史 \(h_t\) 決定下一個階段，例如進入 Modification（情境修改）、Planner Testing（規劃器測試）或 Enhancement（規劃器增強）。

這種形式化的價值在於把原本各自獨立的工具（GUI 編輯器、資料庫篩選器、批次執行腳本）統一為一個以語言為介面的狀態機，使整個測試生命週期（lifecycle）能夠被單一 LLM-agent 協調。

##### 六大核心模組

1. **Generation（情境生成）**  
   將自然語言描述轉換為可在模擬器中執行的結構化情境。PlannerForge 使用 OpenStreetMap（OSM）作為真實地圖來源，讓 LLM 根據城市、道路與車輛屬性生成對應的測試情境。此模組不僅要產生語意正確的描述，還必須確保輸出對模擬器可執行（executable）。

2. **Selection（情境選擇 / 檢索）**  
   從 curated open-source scenario database（精選開源情境資料庫）中檢索與使用者意圖（user intent）最相關的情境。不同於傳統 hand-crafted database filters（手工設計的資料庫篩選器），此模組利用 LLM 理解語意，進行語意匹配與排序。

3. **Modification（情境修改）**  
   對既有情境進行 traffic object and behavior changes（交通物件與行為變更），例如新增車輛、改變速度、調整軌跡等。關鍵挑戰在於修改後仍須保持 physical validity（物理有效性），避免車輛重疊、違反運動學或超出道路邊界。

4. **Module Routing（模組路由）**  
   作為對話系統的調度中心，根據使用者語句與歷史決定應該啟動哪個下游模組。這相當於把使用者的測試意圖對應到 scenario-based testing pipeline（基於情境的測試流程）中的正確階段。

5. **Planner Testing（規劃器測試）**  
   在模擬器中執行目標 motion planner（運動規劃器），收集執行結果 \(O\)，並進行 results analysis（結果分析）。此模組支援 unified multi-planner interface（統一多規劃器介面），可對不同規劃器進行比較。

6. **Enhancement（規劃器增強）**  
   根據測試結果自動調整 planner cost weights（規劃器成本權重），以提升 planner success rate（規劃器成功率）並降低 collision rate（碰撞率）。這是傳統測試流程中較少被自動化的環節，PlannerForge 透過 LLM 將測試回饋轉化為規劃器組態的最佳化建議。

7. **Benchmarking（基準測試）**  
   雖然在問題形式化中未獨立列出，但論文將 ADS Benchmarking 視為強化階段，讓使用者在相同情境下比較多個規劃器，實現 cross-planner comparisons（跨規劃器比較）。

##### 對話式介面與端到端串聯
PlannerForge 以 chatbot-oriented interface（對話導向介面）包裝上述技術複雜度。使用者可以用自然語言逐步提出需求，例如「在慕尼黑市區生成一個行人突然穿越馬路的情境」、「把車速提高 20%」、「測試規劃器 A 並與規劃器 B 比較」、「根據碰撞結果調整成本權重」。Module Router 會把這些語句路由到對應模組，並將各模組輸出串聯成連貫的測試會話。這種 end-to-end chaining（端到端串聯）是 PlannerForge 與既有工具最大的差異：傳統流程需要人工在不同工具間搬移檔案，而 PlannerForge 讓 LLM-agent 自動銜接各階段。

##### 提示設計
論文評估了五種 prompt conditions（提示條件），雖然具體細節未在提供的摘要中詳列，但可推測涵蓋 zero-shot（零樣本）、few-shot（少樣本）、chain-of-thought（思維鏈）、tool-augmented（工具增強）與 structured-output（結構化輸出）等設定。透過系統性比較不同提示條件，作者證明 off-the-shelf LLMs（現成大型語言模型）在無需 domain-specific fine-tuning（領域特定微調）的情況下即可勝任大部分任務。

#### 實驗數據解讀

##### 評估設置
論文使用 10 個 off-the-shelf LLMs，包含五個 commercial APIs（商業 API）與五個 open-source models（開源模型），規模落在 20–35B 之間，涵蓋 reasoning（推理）與 non-reasoning（非推理）模型。評估任務包括 Generation、Selection、Modification、Module Routing、Planner Testing 與 Enhancement，並在五種提示條件下進行。

##### 各任務結果

| **Generation（屬性實現）** | city, road and vehicle attributes（城市、道路與車輛屬性） | 92–96% | — | attribute realization rate（屬性實現率）高，表示模型能穩定地把使用者指定的地理與交通屬性映射到情境中。 |
| **Selection（情境選擇）** | rank 1 selection（排名第一選擇正確率） | 92.0% | BM25：67.5% | LLM 的語意理解明顯優於傳統詞彙檢索，能捕捉同義詞與隱含意圖。 |

##### 商業模型 vs. 開源模型
實驗的一項重要發現是 open-source 20–35B backends（開源 20–35B 後端模型）在大多數任務上可與 commercial APIs 匹敵。特別是 Qwen3.6:35B 在五項核心任務中有三項追平商業 API。這對學術界與產業界具有雙重意義：

1. **成本與可及性**：無需依賴付費 API 即可建構高品質測試代理。
2. **資料隱私**：可在本地部署模型，避免將敏感測試資料傳送至第三方。

然而，commercial APIs 在端到端 retention 上仍略勝一籌（83% vs. 78%），顯示在複雜多輪對話與錯誤累積場景下，商業模型仍具穩定性優勢。

##### 無領域微調的意義
所有實驗均未進行 domain-specific fine-tuning，這強調了 PlannerForge 的通用性與可遷移性。最佳分數達 0.88–1.00 說明現成 LLM 已具備足夠的常識推理、空間理解與結構化輸出能力，能夠直接應用於自動駕駛測試領域。

#### 與現有研究的比較

##### 相對於傳統基於情境的測試
傳統方法遵循 Pegasus、SAKURA 等產業倡議所建立的六階段分類法，但各階段通常由獨立工具執行：scenario generation 使用 GUI editors（圖形使用者介面編輯器）或腳本、scenario selection 依賴 hand-crafted database filters、modification 多為 ad-hoc scenario modification（臨時性情境修改）、cross-planner comparisons 需要 batch runs（批次執行）與 offline aggregation（離線彙整）。PlannerForge 的貢獻在於將這些碎片整合為 unified framework（統一框架），並以自然語言作為單一操作介面。

##### 相對於 LLM 驅動的情境生成
過去 LLM 在 ADS 中的應用多集中於 perception（感知）、planning（規劃）與 control（控制）等子系統，或僅用於 scenario generation，例如 ChatScene、Chat2Scenario、Text2Scenario、LCTGen 等。PlannerForge 超越了單一生成階段，將 generation、selection、modification、execution、assessment、enhancement 與 benchmarking 串接為完整生命週期。這使其不僅能「產生情境」，更能「根據測試結果改進規劃器」。

##### 相對於特定基線的改進
- **Scenario Factory 2.0**：在 natural-language generation（自然語言生成）任務上，PlannerForge 產生 193 個可執行情境，相較於基線的 144 個，提升約 34%。這顯示 PlannerForge 在語言到模擬器輸出的轉換上更為穩健。
- **BM25**：在 rank 1 selection 上，PlannerForge 達 92.0%，遠高於 BM25 的 67.5%。這證明語意檢索相較於詞彙匹配更能理解使用者意圖。
- **From-Words-to-Collisions**：在 physically valid edits 上，PlannerForge 達 ≥94%，而基線僅 31%。這凸顯 LLM 在維持物理一致性上的優勢，對 safety-critical testing 尤為重要。

##### 相對於 ADS Enhancement 研究
LanguageAgent 等研究已將 LLM 用作 planner 或 controller，但較少將 LLM 用於「根據測試結果自動調整規劃器成本權重」。PlannerForge 的 Enhancement 模組填補了這一缺口，將測試與最佳化形成閉環。

##### 限制
儘管成果顯著，論文仍存在若干限制：

1. **模擬器維度**：目前使用二維運動規劃模擬器，尚未涵蓋高擬真三維模擬器（如 CARLA）中的感知與感測器雜訊。
2. **領域泛化**：雖然未進行領域微調是優勢，但也意味模型可能產生幻覺（hallucination），特別是在極少見的 edge cases（邊角案例）上。
3. **評估規模**：部分實驗（如 N=400 的成本調校）規模仍屬中等，尚未驗證於大規模、多城市、多規劃器的長期測試。
4. **安全保證**：PlannerForge 提供的是統計層面的成功率與碰撞率改善，而非形式化安全保證，無法直接取代 ISO 21448 SOTIF 等標準所需的完整驗證流程。
5. **對話複雜度**：chatbot 介面雖然降低門檻，但對於高度專業的測試工程師而言，可能仍需更細緻的結構化控制選項。

#### 可重現性評估

##### 開放資源
論文已提供 code and data（程式碼與資料）於 GitHub：`https://github.com/TUM-AVS/PlannerForge`。這是正向訊號，顯示作者有意支援研究社群重現結果。

##### 模擬器與資料
- 情境生成使用 OpenStreetMap（OSM）作為地圖來源，OSM 為公開資料，可自由取得。
- 情境檢索使用 curated open-source scenario database（精選開源情境資料庫），若該資料庫亦隨程式碼釋出，則重現性高。
- 模擬器為 open-source 2D motion-planning simulator（開源二維運動規劃模擬器），若為 CommonRoad 等常見平台，則環境建置相對容易。

##### 模型可及性
- 開源模型（如 Qwen3.6:35B）權重可公開下載，有利於重現開源模型實驗。
- 商業 API（如 GPT-4 系列）需要付費訂閱與 API 金鑰，可能增加重現成本，但論文已證明開源模型可達相近效果，因此研究者可用開源模型進行近似重現。

##### 可重現性挑戰
1. **隨機性與溫度設定**：LLM 輸出具有隨機性，若論文未詳細記載 temperature、sampling seed、top-p 等參數，重現結果可能略有波動。
2. **提示模板**：五種 prompt conditions 的具體模板若未完整公開，重現時難以完全對齊。
3. **模擬器版本與相依套件**：不同版本的模擬器、地圖解析器或規劃器可能導致 executability 指標差異。
4. **硬體需求**：20–35B 模型需要較大 GPU 記憶體，對部分研究團隊可能造成門檻。

整體而言，PlannerForge 的可重現性處於中上水準：核心程式碼與資料已公開，且使用開源模型即可復現主要結論，但細節參數與環境設定仍需論文正式版本進一步補充。

8. **人機協作與可解釋性**  
   強化 chatbot 的解釋能力，讓使用者能理解為何某個情境被選擇、為何某次測試失敗、以及成本權重如何被調整，提升測試工程師對 LLM 決策的信任。

9. **線上學習與持續驗證**  
   將 PlannerForge 從離線測試工具擴展為持續驗證系統，隨著規劃器版本更新自動回歸測試，並從新發現的失敗案例中學習生成新情境。

10. **跨領域遷移**  
    將此統一 LLM-agent 框架應用於機器人、無人機、智慧交通系統等其他安全關鍵領域，驗證其通用性與可擴展性。

## 論文問答

**Q1：PlannerForge 旨在解決自動駕駛領域中的什麼核心問題？**

A：PlannerForge 主要解決現有基於情境的測試流程高度片段化的問題。在傳統做法中，情境生成、檢索、修改、ADS 執行與結果分析等階段往往由彼此獨立的工具分開處理，缺乏有效的整合與互動。這種模組化流程導致測試過程繁瑣、難以自動化，也無法根據使用者的測試意圖靈活調整。PlannerForge 透過單一對話式 LLM 代理框架，將整個測試生命週期串接起來，從而提升測試的系統性與效率。

**Q2：為什麼現有方法無法充分支援自動駕駛的情境測試？**

A：現有方法大多只聚焦於情境生成這單一階段，而忽略了檢索、修改、執行與分析等其他關鍵環節。傳統流程依賴圖形介面編輯器、手工設計的資料庫篩選器、臨時性情境修改，以及僵硬的手寫腳本來執行測試。此外，規劃器成本權重通常需要人工調校，跨規劃器比較也需要額外撰寫批次執行腳本並離線彙整結果。這些瓶頸使得現有方法難以形成一個統一、自動化且以使用者意圖為導向的測試流程。

**Q3：統一的基於情境測試框架對自動駕駛為何重要？**

A：隨著自動駕駛系統朝向 SAE 第四級發展，嚴謹的驗證變得至關重要，但在真實世界中測試罕見邊角案例的成本極高且危險。基於模擬的情境測試能夠系統化地評估自動駕駛系統在各種運作條件與安全關鍵情境下的表現。一個統一的框架不僅能降低測試成本，還能讓研究人員與工程師以自然語言驅動整個測試流程，加速發現規劃器的弱點並進行迭代改進。

**Q4：PlannerForge 的核心方法是什麼？**

A：PlannerForge 是一個由大型語言模型驅動的代理框架，將所有情境測試階段整合到單一對話式管線中。它在傳統的六個階段之上，額外加入了 ADS 增強與 ADS 基準測試這兩個 LLM 時代的強化階段。整個流程被形式化為一連串從自然語言到結構化輸出的決策，並由模組路由器根據使用者提示與對話歷史決定下一步該呼叫哪個模組。這種設計讓使用者能透過聊天介面完成從情境生成到規劃器比較的完整工作流。

**Q5：PlannerForge 的主要創新之處有哪些？**

A：PlannerForge 是首個將情境測試完整生命週期統一於單一 LLM 代理框架的系統，並額外納入規劃器增強與跨規劃器基準測試功能。它提供了一個統一的多規劃器介面，讓不同運動規劃器能在相同生成或修改後的情境下進行比較評估。此外，研究結果顯示，未經領域特定微調的現成 LLM 就能在多項任務上達到接近甚至媲美商業 API 的表現，這對開源模型的應用具有重要意義。

**Q6：PlannerForge 在設計上做了哪些關鍵選擇？**

A：設計上採用對話式介面來抽象化背後的技術複雜度，讓非專家使用者也能以自然語言操作整個測試流程。框架特別針對運動規劃器進行設計，因為規劃器是自動駕駛系統的核心決策模組，其行為對複雜安全關鍵情境特別敏感。在資料來源方面，PlannerForge 結合了 OpenStreetMap 的真實地圖生成、開源情境資料庫檢索，以及透過交通物件與行為變異進行情境修改，形成一個可擴展且貼近真實世界的測試平台。

**Q7：實驗中使用了哪些基準與對照方法？**

A：實驗在自然語言生成任務上與 Scenario Factory 2.0 比較，在情境選擇任務上與經典詞彙檢索方法 BM25 比較，在情境修改任務上則與 From-Words-to-Collisions 比較物理有效性。作者評估了十個現成的大型語言模型，包含五個商業 API 與五個開源模型，並在五種提示條件下進行測試。此外，實驗也涵蓋了端到端串聯、屬性實現率，以及規劃器成本調校等多項分析。

**Q8：PlannerForge 的關鍵實驗結果是什麼？**

A：各任務最佳分數介於 0.88 到 1.00 之間，顯示現成 LLM 在大多數任務上表現優異。開源 20–35B 後端模型在多數任務上能與商業 API 匹敵，其中 Qwen3.6:35B 在五項任務中有三項達到與商業 API 相當的水準。端到端串聯能保留 83% 的商業模型種子查詢與 78% 的開源模型種子查詢。與基線相比，PlannerForge 在可執行情境生成上達到 193 對 144 的表現，排名第一選擇準確率為 92.0% 對 BM25 的 67.5%，物理有效編輯率則達到至少 94% 對 31%。

**Q9：實驗中有哪些消融研究或深入分析？**

A：研究在五種提示條件下評估模型，以了解不同提示設計對各任務表現的影響。作者也系統性地比較了商業 API 與開源模型在生成、選擇、修改、模組路由、規劃器測試與增強等任務上的差異。端到端串聯實驗則量化了管線中資訊遺失的程度，結果顯示商業模型保留率較高。此外，研究也分析了城市、道路與車輛屬性的實現率，發現請求屬性有 92% 至 96% 能被實際滿足。

**Q10：PlannerForge 有哪些實際應用場景？**

A：自動駕駛開發團隊可以利用 PlannerForge，從自然語言描述自動生成各種安全關鍵測試情境，例如壅塞路口、行人突然穿越或惡劣天氣條件。研究人員則能透過統一介面，在相同情境下比較不同運動規劃器的表現，從而進行客觀的基準測試。安全工程師也可以從現有資料庫中檢索相關情境，並根據特定測試需求進行修改，以驗證系統在罕見邊角案例下的穩健性。

**Q11：部署 PlannerForge 時需要考慮哪些產品化因素？**

A：首先需要在商業 API 的成本與開源模型的可取得性之間做出權衡，因為兩者在多數任務上表現相近。其次，框架必須與現有的模擬環境與多種運動規劃器順利整合，這涉及資料格式、API 介面與執行效率等工程挑戰。此外，對話式介面必須能穩定理解多樣化的使用者意圖，同時確保生成與修改後的情境在物理上合理且可執行，才能安全地用於實際驗證流程。

**Q12：PlannerForge 可能對自動駕駛領域帶來什麼影響？**

A：PlannerForge 有望大幅減少情境測試中繁瑣的人工操作與工具切換成本，使驗證流程更加自動化與標準化。由於開源模型已能在多項任務上媲美商業 API，這將降低先進測試技術的取得門檻，讓更多研究團隊與中小型企業受益。長遠來看，這類統一框架有助於加速 SAE 第四級自動駕駛系統的安全驗證，推動產業朝更可靠、更可解釋的方向發展。

**Q13：論文承認了哪些限制？**

A：PlannerForge 目前主要聚焦於運動規劃器，尚未涵蓋感知與控制等完整自動駕駛系統模組。雖然單一模組表現良好，但端到端串聯時仍會損失部分種子查詢，顯示管線整合仍有改進空間。此外，由於使用的是現成大型語言模型，其表現可能受到模型版本更新、提示設計變化以及特定領域知識不足等因素影響。

**Q14：PlannerForge 可能存在哪些失敗案例？**

A：端到端串聯僅能保留約 83% 的商業模型查詢與 78% 的開源模型查詢，表示部分使用者意圖在模組間傳遞時可能遺失或扭曲。雖然屬性實現率達到 92% 至 96%，但仍有少數生成情境無法完全滿足請求的城市、道路或車輛屬性。此外，情境修改的物理有效性雖然顯著優於基線，但並非百分之百，某些編輯仍可能產生不符合物理規則或無法在模擬器中執行的結果。

**Q15：未來有哪些可能的研究方向？**

A：未來可以將框架擴展到完整的自動駕駛系統，包含感知、預測與控制模組的協同測試。針對特定領域資料進行微調，或許能進一步提升生成、修改與分析任務的準確度與一致性。另外，也可以加入更多真實世界資料、強化對抗性情境生成，以及建立更完整的開放基準，讓 PlannerForge 這類工具能更接近實際道路測試的需求。

## 實務應用指南

### 適用場景

1. **自駕車運動規劃器的開發與回歸測試**  
   當團隊開發新的運動規劃器或修改成本函數時，可用 PlannerForge 快速生成大量結構化情境，並在每次程式碼變更後自動執行回歸測試，確認規劃器在常見與邊角案例上的表現是否退化。

2. **安全關鍵邊角案例的生成與驗證**  
   針對真實世界中難以複現的危險情境（如行人突然穿越、對向車違規超車），工程師可用自然語言描述需求，由框架自動生成對應模擬情境，並檢驗規劃器是否能安全處理。

3. **多規劃器競品比較與基準測試**  
   在需要比較自家規劃器與開源或第三方規劃器時，可利用統一介面在同一批生成與修改後的情境上執行測試，並自動產出碰撞率、成功率等可比較指標。

4. **事故報告重建與對應情境再現**  
   收到真實事故報告或模擬日誌後，可透過自然語言輸入事故描述，由框架協助重建近似情境，並測試不同規劃器在類似條件下的反應，以支援根因分析。

5. **規劃器成本權重的自動調校**  
   當規劃器在特定情境族群表現不佳時，可利用 Enhancement 模組自動調整成本權重，例如降低碰撞風險或提升行車舒適性，無需人工反覆試誤。

### 實作步驟建議

1. **環境建置與模擬器整合**

2. **資料準備與情境資料庫建置**  
   下載並清理目標區域的 OSM 資料，建立初始情境資料庫。若已有歷史測試情境或事故案例，可一併匯入以提升檢索與修改任務的覆蓋率。

3. **LLM 後端選型與提示工程**  
   依預算與延遲需求選擇商用 API 或開源 20–35B 模型。針對 Generation、Selection、Modification、Module Routing、Enhancement 五項任務分別設計提示樣板，並用少量驗證集評估正確率與可執行率。

4. **模組逐一驗證**  
   先獨立測試 Generation、Selection、Modification 等模組，確認輸出符合物理可行性與屬性要求。論文顯示物理有效編輯率可達 94% 以上，建議團隊以此為最低門檻。

5. **端到端串聯與對話介面部署**  
   將各模組透過 Module Router 串接，並提供聊天機器人式介面。測試從自然語言需求到情境生成、規劃器執行、結果分析的完整流程，確認商業模型可保留約 83%、開源模型約 78% 的種子查詢意圖。

6. **持續監控與迭代**  
   建立測試結果儀表板，追蹤成功率、碰撞率與屬性實現率。定期根據失敗案例更新提示樣板與情境資料庫，並利用 Enhancement 模組自動調校規劃器成本權重。

### 潛在風險與注意事項

- **LLM 幻覺導致不可行情境**  
  即使最佳模型也可能生成無法在模擬器中執行的情境。建議在執行前加入語法與物理可行性檢查，並將失敗案例回饋至提示工程流程。

- **模擬與真實世界的差距（Sim-to-Real Gap）**  
  模擬中通過不代表實車安全。應將 PlannerForge 視為篩選與回歸工具，最終仍需在封閉場域或受控環境進行實車驗證。

- **成本與延遲**  
  端到端流程涉及多次 LLM 呼叫與模擬執行，大規模測試時成本可能快速累積。建議先以小批量驗證效果，再逐步擴充，並對非關鍵任務選用開源模型降低成本。

- **安全與責任歸屬**  
  自動生成的危險情境可能涉及倫理與法律議題。應建立審查機制，確保測試目的明確，並記錄生成參數與執行結果以備追溯。

- **過度依賴特定 LLM 後端**  
  不同模型在任務間表現差異大，建議保留後端切換能力，避免被單一供應商或模型版本綁死。

---

### 與其他技術的整合建議

- **持續整合／持續部署（CI/CD）管線**  
  將 PlannerForge 嵌入規劃器開發的 CI/CD 流程，每次提交後自動執行一組核心情境測試，並在退化時發出告警。

- **資料湖與情境資料庫**  
  將生成與修改後的情境儲存至結構化資料庫，並與現有資料湖整合，支援長期趨勢分析與跨版本比較。

- **現有模擬平台**  
  若團隊已使用 CARLA、SUMO 或其他自駕模擬器，可透過標準化介面將 PlannerForge 作為上層情境管理與測試編排層，而非取代既有模擬基礎建設。

- **MLOps 與模型註冊表**  
  將不同規劃器版本與對應測試結果關聯至模型註冊表，便於追蹤哪一版規劃器在哪些情境族群表現最佳。

- **需求管理與事故追蹤系統**  
  將自然語言測試需求與功能安全需求、事故報告連結，確保每個生成情境都有明確的驗證目標與可追溯來源。

---

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從摘要與適用場景讀起，理解「為什麼要用 LLM 做情境測試」以及 PlannerForge 能解決什麼問題。技術細節如模組路由與成本權重調校可暫時略過，重點放在整體流程與實際應用價值。

**AI 工程師**  
應聚焦於問題形式化、模組設計與提示工程實驗，特別注意論文中五種提示條件與十種 LLM 後端的比較結果。實作時可優先參考開源 20–35B 模型的表現，評估是否能在不微調的情況下達到商用 API 水準。

**研究人員**  
建議深入閱讀相關工作與評估指標，關注 PlannerForge 如何將傳統六階段情境測試流程擴展為包含 ADS Enhancement 與 Benchmarking 的完整生命週期。未來研究可探索更強大的開源模型、多模態輸入，或將框架延伸至感知與控制子系統。

**產品經理**  
重點閱讀適用場景、潛在風險與整合建議，評估導入 PlannerForge 所需的資料、運算與人力成本。論文中的量化結果（如成功率提升與碰撞率下降）可作為與安全團隊和客戶溝通時的效益依據。
