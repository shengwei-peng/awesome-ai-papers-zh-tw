## ⚡ TL;DR

程式設計智慧體轉向長期自主執行，Token效率成為擴展遞迴自我改進的關鍵挑戰。
本文提出SoL-Pi，以遞迴自我改進啟發的自動研究迴圈，在框架層發現可遷移的效率機制。
EdgeBench中SoL-Pi與Pi相當，Token流量減44.7–49%、API成本減約三成。

## 摘要翻譯

隨著程式設計智慧體（coding agents）從監督式程式碼補全（supervised code completion）走向無人值守、全天候探索，其工作也從孤立的預測擴展為由推理、工具使用（tool use）與回饋（feedback）所構成的長期軌跡（long trajectories）。因此，Token 效率（token efficiency）對於擴展遞迴自我改進（recursive self-improvement, RSI）變得日益重要。我們在框架層（harness layer）採取受 RSI 啟發的方法，在數量與多樣性皆持續增加的環境（environments）中擴展自動研究迴圈（auto-research loops），以進行框架推展（harness rollouts）。在此規模下，此過程產生可重複使用的改進（reusable improvements），能夠遷移至其開發情境之外，使自動化框架發現（automated harness discovery）朝向生產級成果（production-level outcomes）邁進。四項機制經篩選後留存並構成 SoL-Pi，涵蓋動作執行（action execution）、上下文壓縮（context compaction）、觀察處理（observation handling）與委派閱讀（delegated reading）。在 EdgeBench 的 51 項任務評測中，SoL-Pi 在 GPT-5.6 Sol 與 Opus 5 上達到與 Pi 相當的效能，同時將記錄到的 Token 流量（token traffic）減少 44.7–49.0%，API 成本（API cost）降低約三分之一。換句話說，相較於原生 Codex（native Codex）框架與 Claude Code 框架（Claude Code harnesses），估計每小時可節省 8.75–13.50 美元；相較於 Pi，則可節省 4.36–5.71 美元。

### 核心貢獻（3～5點）
- 在智慧體框架層（harness layer）引入受遞迴自我改進（RSI）啟發的自動研究迴圈，透過大規模、多樣化的環境推展（harness rollouts）發現可重複使用的效率改進。
- 提出並驗證四項核心機制：動作執行（action execution）、上下文壓縮（context compaction）、觀察處理（observation handling）與委派閱讀（delegated reading），共同構成 SoL-Pi。
- 在 EdgeBench 的 51 項任務上，SoL-Pi 於 GPT-5.6 Sol 與 Opus 5 模型中達到與 Pi 相當的效能，同時顯著降低 Token 流量（44.7–49.0%）與 API 成本（約三分之一）。
- 展示自動化框架發現（automated harness discovery）能產生可遷移至開發情境之外的生產級成果（production-level outcomes），為無人值守的程式設計智慧體提供可擴展的遞迴自我改進路徑。

### 適合對象
本論文適合從事大型語言模型智慧體、程式設計智慧體（coding agents）、自主研究系統、遞迴自我改進（RSI）以及模型部署與服務效率最佳化的研究人員與工程師閱讀；對於希望在不重新訓練模型的前提下，透過框架層級最佳化降低 API 成本並提升代理程式效率的實務開發者亦具高度參考價值。

## 深度分析

#### 方法論解析

SoL-Pi 的核心貢獻在於把「框架層級最佳化（Harness-level optimization）」視為一個可規模化的遞迴自我改進（Recursive Self-Improvement, RSI）搜尋問題，而不是單純的人工調校。論文將整個流程命名為 SoL-Pi：擴展自動研究迴圈（SoL-Pi: Scaling Auto-Research Loop），其本質是讓一個研究 AI（research AI）反覆觀察基礎框架（base harness）的執行軌跡（execution traces），提出候選變更（candidate changes），並在獨立的研究環境（research environments）中驗證，最終篩選出可重複使用的改進（reusable improvements）。

整個方法論可拆解為三個層次：

1. **搜尋原則層：廣度與深度（breadth and depth）、獨立驗證（Independent validation）、可規模化協調（Scalable orchestration）**
   - 廣度與深度透過「廣至深漏斗（broad-to-deep funnel）」實現：外層先探索大量機制假設，內層再針對入選方向進行反覆實作與淬煉。
   - 獨立驗證要求保留任務（held-out tasks）的證據必須在候選機制被凍結（freeze）後才評估，且結果絕不回傳給搜尋迴圈，避免過度擬合（overfit）搜尋環境。
   - 可規模化協調則透過隔離的搜尋譜系（isolated search lineages）達成：每個實驗都是一次性、可丟棄的共享技能模板（shared skill template）實例，失敗不會污染其他分支。

2. **流程層：Oracle Analysis → 方向提案 → 獨立開發 → 凍結 → 保留驗證（held-out validation）**
   - 在投放預算前，Oracle Analysis 先檢視既有開發軌跡，找出基礎框架中可避免的開銷。
   - 研究 AI 從六個提案家族（proposal families）——context、progress、tools、delegation、prompt and policy、improvement and evaluation——產出 152 個方向。
   - 每個方向進入獨立的自動研究迴圈，採用 Ralph Loop 進行迭代實作：實作者（implementer）根據明確完成條件精煉候選，再由獨立審查者（reviewer）檢查，未通過則修訂。
   - 評估前，能力指標（capability metrics）、可接受容差（tolerances）與效率指標（efficiency metrics）即被固定，且與最佳化 AI 嚴格隔離，防止其操弄驗收標準。
   - 候選機制必須通過兩道閘門：所有能力指標維持在預設容差內，且至少改善一項預先宣告的效率指標。通過後，再以帕雷托非支配（nondominated）方式篩選。

3. **機制層：四大被保留機制**
   - 搜尋最終篩選出四項機制，分別對應動作執行（action execution）、上下文壓縮（context compaction）、觀察處理（observation handling）與委派閱讀（delegated reading）。
   - 雖然論文摘要與方法段落未詳述每項機制的具體演算法，但從名稱與提案家族可推論：
     - **動作執行** 可能涉及減少重複或冗餘的工具使用（tool use）、合併連續動作、或更精準的終止（termination）與恢復（recovery）決策。
     - **上下文壓縮** 對應 context 家族，應是在不遺失關鍵資訊的前提下，對智慧體迴圈（agent loop）中的對話歷史進行摘要或截斷。
     - **觀察處理** 可能類似 ObservationPack 的概念，重新界定觀察邊界（observation boundary），避免把過大或過於稀疏的觀察塞入提示。
     - **委派閱讀** 屬於 delegation 家族，應是讓專門模組或較便宜的模型（cheaper models）先讀取長文件或長軌跡，再由主模型消費精簡後的結果。

這種設計的關鍵在於把「框架發現（automated harness discovery）」從單一任務調參，提升為跨環境、跨模型的可遷移效率改進搜尋。透過將開發回饋與保留評估（held-out evaluation）物理隔離，SoL-Pi 試圖解決過去演化後的框架（evolved harnesses）容易過度擬合開發任務的問題。

#### 實驗數據解讀

論文在 EdgeBench 這個包含 51 項任務的基準上進行最終驗證，並比較兩種模型：GPT-5.6 Sol 與 Opus 5。主要結果可歸納為三點：

1. **能力維持不變**
   - SoL-Pi 在兩種模型上皆達到與 Pi 相當的表現。這點至關重要：它證明框架層級最佳化並未以犧牲任務完成率為代價。若能力顯著下降，則 Token 效率（token efficiency）的提升將失去實用意義。

2. **Token 流量（token traffic）降低 44.7–49.0%**
   - 這代表在整個長期範圍（long horizons）執行過程中，模型與環境之間傳輸的 Token 總量幾乎減半。對於需要長時間運作的程式設計智慧體（coding agents）或軟體工程智慧體（software engineering agents）而言，這直接轉化為更低的延遲與更高的吞吐量。

3. **API 成本（API cost）降低約三分之一，並換算為可觀的時薪節省**
   - 相較於原生 Codex（native Codex）與 Claude Code 框架（Claude Code harnesses），每小時可節省 8.75–13.50 美元。
   - 相較於已經最佳化的 Pi 框架，每小時仍可節省 4.36–5.71 美元。
   - 這說明即使與強基線相比，SoL-Pi 發現的機制仍具有顯著的邊際效益。

從數據解讀的角度，有幾個值得注意的細節：

- **能力與效率的權衡被明確量化**：論文不是只報告單一指標，而是同時報告能力（與 Pi 相當）與效率（Token 與成本），並透過預先固定的容差來確保兩者兼顧。這符合多目標最佳化的精神。
- **跨模型一致性**：GPT-5.6 Sol 與 Opus 5 都呈現類似的降幅，暗示這些機制具有某種程度的模型無關性（model-agnostic），而非僅針對單一模型提示工程（prompt engineering）的結果。
- **成本節省的實務意義**：以每小時節省約 5–10 美元估算，若一個自主研究或軟體工程智慧體每天運行數小時，長期累積的營運成本差異將非常可觀。這也呼應了論文開頭的主張：Token 效率已成為長期範圍代理程式的首要系統考量（first-order systems concern）。

不過，摘要與內文並未提供標準差、個別任務的分布、或不同機制對總降幅的貢獻比例。若未來能補充這些數據，將有助於判斷哪些機制是「大贏家」，哪些只是邊際貢獻。

#### 與現有研究的比較

SoL-Pi 在相關文獻中的定位相當明確：它補充了模型層級與基礎設施層級的效率研究，並在「框架層級最佳化」這個相對未被充分探索的領域推進了一步。

| 研究方向 | 代表工作 | 與 SoL-Pi 的關係 |
|---|---|---|
| 降低每 Token 成本 | 更快的注意力核心（attention kernels）、服務基礎設施（serving infrastructure）、量化（quantization） | 這些方法與 SoL-Pi 正交。SoL-Pi 不修改模型權重或推理核心，而是減少實際需要的 Token 數量，因此可與上述技術疊加。 |
| 使用較便宜的模型 | 模型路由、級聯推理 | SoL-Pi 的委派閱讀（delegated reading）可能內含類似思想，但重點在於框架機制設計，而非模型選擇。 |
| 自動化框架發現 | Meta-Harness | Meta-Harness 搜尋可執行的框架程式（executable harness programs），並評估其遷移到保留資料集與模型的能力。SoL-Pi 與其相似，但更強調「廣至深漏斗」與「隔離搜尋譜系」來避免過度擬合。 |
| 遞迴框架自我改進 | Recursive Harness Self-Improvement（RHI） | RHI 針對單一任務迭代改進提示層級規格（prompt-level specifications）。SoL-Pi 則追求跨任務、跨環境的可遷移效率改進，規模與目標均不同。 |
| 過度擬合風險 | 近期研究指出演化後的框架在保留任務上僅有邊際增益 | SoL-Pi 透過獨立驗證與凍結機制直接回應此批評，試圖把開發回饋與最終評估分開。 |

SoL-Pi 的主要改進包括：

- **規模化**：約 150 個方向、500 個可執行環境、3,000 次以上執行、60,000 次以上的智慧體—環境互動。這樣的規模遠超一般人工調校可達成的範圍。
- **可遷移性**：透過保留驗證與隔離設計，強調發現的改進能超越開發環境，朝向生產級成果（production-level outcomes）。
- **系統性**：把能力與效率指標、容差、驗收閘門全部預先固定，避免最佳化 AI 操弄指標。

然而，其限制也同樣明顯：

- **領域侷限**：實驗集中在 EdgeBench 的程式設計任務。觀察處理、上下文壓縮等機制在開放式網頁瀏覽、多模態互動或科學實驗等領域是否同樣有效，仍需驗證。
- **機制細節不足**：摘要與方法段落僅列出四項機制的名稱，未說明其具體實作、超參數或失敗案例。這使得外部研究者難以判斷其通用性。
- **評估基準單一**：雖然 EdgeBench 包含 51 項任務，但仍屬於同一類型基準。若僅在此基準上驗證，難以完全排除對 EdgeBench 特定任務分布的隱性過度擬合。
- **RSI 的安全與對齊風險**：論文強調 RSI 的價值在於搜尋過程，但當 AI 最佳化器（AI optimizer）能夠修改框架的提示、工具使用與終止條件時，也可能引入未預期的行為或目標偏移（goal misgeneralization）。這方面在摘要與方法中著墨不多。

從方法論描述來看，SoL-Pi 的設計原則與流程已經相當詳細，具備「概念上可重現」的基礎：研究者可以依照廣至深漏斗、Ralph Loop、Oracle Analysis 與雙閘門驗收等步驟重建系統。然而，若缺乏具體的機制實作細節與原始軌跡，外部團隊要完全重現 44.7–49.0% 的 Token 降幅將面臨相當挑戰。

- 至少部分匿名化後的執行軌跡，以供社群分析失敗模式（failure modes）。
- 完整的成本計算方式，包括模型定價、重試次數與失敗執行的攤提。

#### 未來研究方向

SoL-Pi 開啟了幾條值得後續探索的研究路線：

1. **跨領域遷移驗證**
   將 SoL-Pi 發現的機制應用到非程式設計領域，例如自主研究（autonomous research）、自我演化的個人助理（self-evolving personal assistants）、科學實驗代理或網頁代理。這能檢驗「觀察處理」與「上下文壓縮」等機制是否為通用原則，還是僅適用於程式碼生成任務。

2. **線上適應與終身學習**
   目前 SoL-Pi 的搜尋是在一批固定環境中完成，然後將機制凍結後部署。未來可研究如何在生產環境中持續收集執行軌跡，並以較低成本進行線上微調或週期性再搜尋，使框架隨使用場景演化。

3. **結合模型層級與框架層級最佳化**
   SoL-Pi 已證明框架層級最佳化可與模型壓縮（model compression）、量化、注意力核心加速等技術正交。下一步可建立聯合最佳化框架，同時決定「使用什麼模型」與「如何設計 harness」，以達到全域最優的延遲—成本—能力權衡。

4. **多目標帕雷托前沿分析**
   目前採用預先固定的能力容差與效率指標。未來可放寬為動態多目標搜尋，繪製完整的帕雷托前沿，讓使用者根據應用場景選擇不同能力—效率取捨點。

5. **RSI 的安全、對齊與可解釋性**
   當 AI 最佳化器能修改智慧體框架的提示與決策邏輯時，必須建立更嚴謹的審查機制。未來可研究如何讓自動研究迴圈在提升效率的同時，維持對齊性（alignment）、避免目標偏移，並產生人類可理解的改進說明。

6. **更豐富的評估指標**
   除了 Token 流量與 API 成本，未來可納入延遲、能源消耗、人類審查成本、錯誤可修復性等指標，使框架評估更貼近真實生產環境。

7. **開放基準與社群驅動的框架發現**
   建立類似「HarnessBench」的公開平台，讓不同研究團隊提交環境與任務，並以標準化協議比較各種自動化框架發現方法。這將加速可重複使用的改進累積，並降低單一研究過度擬合特定基準的風險。

總結而言，SoL-Pi 把「框架層級最佳化」從手工藝轉變為可規模化的自動研究流程，並在保持能力的同時顯著降低 Token 與成本。其設計原則——廣度與深度、獨立驗證、可規模化協調——為未來的遞迴自我改進研究提供了重要的方法論參考，但其在領域泛化、機制透明度與可重現性方面仍有進一步深化的空間。

## 論文問答

**Q1：SoL-Pi 主要想解決什麼問題？**

A：SoL-Pi 主要解決程式設計智慧體從監督式程式碼補全走向長期、無人值守探索時所面臨的 Token 效率問題。當智慧體的運作範圍擴展到包含推理、工具使用與回饋的長軌跡時，任務層級的 Token 消耗會迅速成為首要系統考量。不同於過去聚焦於降低每個 Token 成本或壓縮模型的做法，SoL-Pi 選擇在智慧體框架層進行最佳化，以減少實際執行過程中不必要的 Token 流量。

**Q2：現有方法為何無法有效解決這個問題？**

A：現有的效率提升方法多半著眼於注意力核心加速、量化壓縮、服務基礎設施或改用較便宜的模型，這些都屬於基礎設施層或模型層的最佳化，並未處理智慧體框架本身如何使用 Token。然而，智慧體框架中的工具使用、上下文管理、驗證、委派、恢復與終止機制彼此緊密耦合，局部改進很可能在後續階段引發失效或把成本轉移到後面。此外，過去研究發現演化後的框架容易對搜尋任務過度擬合，在保留任務上僅能取得邊際增益，因此需要更嚴謹的驗證設計。

**Q3：為什麼 Token 效率對遞迴自我改進特別重要？**

A：遞迴自我改進需要在大量且多樣的環境中反覆執行自動研究迴圈，每次推展都會產生龐大的 Token 流量，若效率不佳，整體成本將難以負擔。提升 Token 效率意味著在固定預算下可以執行更多迭代、探索更廣泛的假設，從而加速發現可重複使用的改進。因此，Token 效率不僅是成本問題，更是決定遞迴自我改進能否規模化的關鍵系統因素。

**Q4：SoL-Pi 的核心方法是什麼？**

A：SoL-Pi 採用受遞迴自我改進啟發的方法，在智慧體框架層進行自動化搜尋與改進：由研究 AI 觀察基礎框架的執行軌跡，提出候選變更，並在研究環境中測試其效果。整個流程被組織成「廣至深漏斗」，從大量假設出發，再對有潛力的方向進行獨立、深入的開發與驗證。最終篩選出四項核心機制：動作執行、上下文壓縮、觀察處理與委派閱讀，並整合為 SoL-Pi 系統。

**Q5：SoL-Pi 的關鍵創新與設計原則是什麼？**

A：SoL-Pi 的設計由三項原則指導：廣度與深度、獨立驗證，以及可擴展協調。廣度確保假設覆蓋率，深度則反覆實作、審查與強化候選機制；獨立驗證要求保留證據必須在候選凍結後才評估，且結果絕不回傳到搜尋迴圈；可擴展協調則透過隔離的搜尋譜系，讓漏斗能橫向擴展到更多想法與環境，而不會互相污染。這些原則共同解決了過去自動化框架改進中常見的過度擬合問題。

**Q6：為什麼要將開發回饋與保留驗證嚴格分離？**

A：嚴格分離是為了避免保留驗證的失敗被當成修補線索，導致候選機制逐漸變成針對特定任務的解決方案。SoL-Pi 規定在候選凍結後才進行保留驗證，且驗證結果永遠不回饋到搜尋迴圈，這樣才能確保發現的改進具有跨環境遷移能力。這種設計類似機器學習中測試集不可參與訓練的原則，是評估可遷移效率改進的關鍵保障。

**Q7：論文使用了什麼評測基準，為什麼選擇它？**

A：論文使用包含 51 項任務的 EdgeBench 作為最終評估基準。EdgeBench 在整個搜尋過程中與開發環境完全隔離，確保最終結果能真實反映機制的泛化能力，而非對搜尋任務的過度擬合。論文在 EdgeBench 上比較 SoL-Pi 與 Pi 基線，並分別測試 GPT-5.6 Sol 與 Opus 5 兩種模型。

**Q8：SoL-Pi 取得了哪些關鍵實驗結果？**

A：在 EdgeBench 上，SoL-Pi 在維持與 Pi 相當表現的同時，將記錄的 Token 流量降低 44.7% 至 49.0%，API 成本也減少約三分之一。相較於原生 Codex 與 Claude Code 框架，估計每小時可節省 8.75 至 13.50 美元；相較於 Pi，每小時仍可節省 4.36 至 5.71 美元。這些成果顯示，即使不進行額外的模型訓練，僅透過框架層級最佳化就能帶來顯著的成本效益。

**Q9：論文是否進行了機制層級的分析或消融研究？**

A：論文說明每項機制都必須通過兩道篩選閘門：所有能力指標必須落在預設容許範圍內，且至少有一項預先宣告的效率指標獲得改善。在通過閘門的候選中，系統會保留在宣告指標下非被支配的結果，確保不會為了單一指標犧牲其他重要面向。雖然摘要與方法段落明確列出四項存活機制，但關於個別機制對最終增益的貢獻比例，目前提供的全文片段尚未揭露更細緻的消融數據。

**Q10：哪些實際應用場景最能受惠於 SoL-Pi？**

A：SoL-Pi 特別適合需要長期運作的自主研究系統、軟體工程智慧體、自我演化的個人助理，以及任何 Token 成本會隨時間累積的智慧體部署。對於 24 小時運行的生產級程式設計智慧體而言，每小時節省的成本在長期營運下會非常可觀。因此，商業化的智慧體平台、雲端編碼助理與自動化研究管線都是潛在的高價值應用場景。

**Q11：在產品化部署 SoL-Pi 時需要考慮哪些因素？**

A：產品團隊必須注意智慧體框架內各元件的緊密耦合性，任何改動都需要經過完整的整合測試，以避免局部最佳化引發下游失效。廣至深漏斗需要穩健的協調基礎設施，才能同時管理數百個隔離的搜尋譜系與數萬次智慧體環境互動。此外，開發環境與保留驗證環境必須嚴格分離，否則將喪失對可遷移性的保證，進而影響生產部署的可靠性。

**Q12：SoL-Pi 對整個領域可能帶來什麼影響？**

A：SoL-Pi 指出遞迴自我改進的長遠價值，可能不在於單一系統的自我修改，而在於能夠跨大量公開環境擴展搜尋流程，以發現可重複使用的改進。它為智慧體效率研究開闢了一條與模型訓練和基礎設施最佳化互補的新方向。透過證明框架層級的改進可以泛化到未見任務，SoL-Pi 讓自動化框架發現更接近生產級成果的目標。

**Q13：論文承認了哪些限制？**

A：論文指出智慧體框架最佳化本身極具挑戰性，因為工具使用、上下文管理、驗證與終止等機制緊密交織，局部改動容易產生意想不到的副作用。整個搜尋流程需要在約 500 個可執行環境中進行超過 60,000 次智慧體環境互動，代表運算資源與協調成本相當高。此外，152 個提出方向中僅有四項機制最終存活，顯示多數假設並未轉化為有效改進，也暗示目前對哪些改進具有可遷移性仍缺乏完整理論理解。

**Q14：SoL-Pi 可能面臨哪些失效案例？**

A：一種常見失效是候選變更在開發環境中降低 Token 消耗，卻因改變智慧體行為模式而導致後續階段失敗或把成本轉移到後面。另一種風險是候選機制雖通過開發驗證，卻在保留任務上表現不佳，顯示其對搜尋環境過度擬合。此外，若能力指標、容許範圍與效率指標未與最佳化代理嚴格隔離，研究 AI 可能會鑽研評估標準，產生看似符合條件但實際無用的改進。

**Q15：未來可以朝哪些方向延伸這項研究？**

A：未來可以將廣至深漏斗擴展到更多元的環境類型與智慧體架構，例如多模態智慧體或需要長期記憶的系統。結合框架層、模型層與基礎設施層的最佳化，有機會進一步放大效率增益。另一個方向是讓自動研究迴圈本身更自動化，例如自動整合存活機制、自動調整超參數，並在發現衝突時自行協調，從而減少人類工程師在迴圈中的介入。

## 實務應用指南

### 適用場景

1. **全天候軟體工程智慧體**  
   當程式設計智慧體需要長時間自主執行（例如整晚進行程式碼重構、測試與文件更新），SoL-Pi 可透過上下文壓縮、觀察處理與委派閱讀，降低長期執行累積的 Token 流量與 API 成本，同時維持完成率。

2. **企業內部自動化研究助理**  
   在金融、法律或生醫領域，自主研究智慧體需反覆檢索、閱讀長文件並產出報告。SoL-Pi 的框架層級最佳化能減少重複觀察與冗餘動作，讓研究迴圈在大量文件環境中仍具成本效益。

3. **多租戶客服與個人助理平台**  
   自我演化的個人助理若同時服務大量用戶，Token 開銷會隨對話長度快速上升。將 SoL-Pi 機制嵌入智慧體框架，可在不重新訓練模型的情況下，顯著降低每位用戶的邊際 API 成本。

4. **CI/CD 中的自動化程式碼審查與修復 Agent**  
   在持續整合管線中，Agent 需反覆執行測試、讀取日誌、修改程式碼。SoL-Pi 的動作執行與觀察處理機制可減少無效迴圈與過大觀察輸入，加速修復流程並降低雲端 API 帳單。

5. **多智慧體協作平台**  
   當多個 Agent 透過委派分工完成複雜任務時，SoL-Pi 的委派閱讀與上下文壓縮能避免資訊在 Agent 間重複傳遞，提升整體 Token 效率與通訊清晰度。

### 實作前置條件

**資料準備**
- 可穩定執行的**基礎框架**（base harness）與其完整執行軌跡（execution traces）。
- 一組**研究環境**（development environments）用於候選改進實驗，以及嚴格隔離的**保留任務**（held-out tasks）用於最終驗證。
- 預先定義且凍結的**能力指標**（capability metrics）與**效率指標**（efficiency metrics），例如完成率、正確性、Token 流量、API 成本。

**運算資源**
- 足夠的 API 預算以支撐大規模自動研究迴圈（論文規模約 152 個方向、500 個環境、3,000 次以上執行）。
- 可平行執行多個**隔離搜尋譜系**（isolated search lineages）的運算與編排資源。
- 軌跡儲存與分析基礎設施，用於 Oracle Analysis 與後續機制評估。

**技能需求**
- 熟悉智慧體框架（agent harness）與智慧體迴圈設計。
- 具備提示工程、工具使用、上下文管理與觀察邊界調整經驗。
- 能建立獨立評估管線並防止驗證資訊回流搜尋迴圈。
- 具備基礎的模型 API 成本分析與實驗追蹤能力。

### 實作步驟建議

1. **固定評估協議**  
   在開始搜尋前，先確定能力指標、可接受誤差範圍與效率指標，並將這些規則鎖定，不讓 AI 最佳化器接觸或修改。

2. **建立基礎框架與收集執行軌跡**  
   讓現有智慧體框架在代表性任務上運行，記錄完整執行軌跡，作為 Oracle Analysis 與後續假設生成的素材。

3. **執行 Oracle Analysis 並建立假設池**  
   分析軌跡中重複動作、上下文膨脹、過大觀察與稀疏診斷訊號等開銷來源，產出 100–200 個候選改進方向，涵蓋上下文、工具、委派、提示與政策等面向。

4. **啟動隔離的自動研究迴圈**  
   為每個有潛力的方向建立獨立、可拋棄的搜尋譜系。每個譜系包含：提出變更 → 實作 → 固定實驗 → 檢視結果 → 保留、修訂或丟棄。

5. **加入實作與審查迴圈**  
   在單一譜系內使用 implementer–reviewer 機制：實作者將候選機制做到明確完成標準，再由獨立審查者檢查；審查未通過則修訂，避免帶有缺陷的機制進入評估。

6. **套用雙閘門篩選與非支配排序**  
   候選機制必須同時滿足：所有能力指標在預設容差內，且至少改善一項效率指標。通過者再以非支配排序（nondominated selection）挑選最佳組合。

7. **整合機制並調校超參數**  
   將篩選出的機制（動作執行、上下文壓縮、觀察處理、委派閱讀）整合為單一 SoL-Pi 框架，並在不影響能力的前提下調校實作細節與超參數。

8. **進行保留任務驗證**  
   在完全凍結框架與驗收規則後，於保留任務（如 EdgeBench）執行最終評估。驗證結果無論好壞都不得回流搜尋迴圈。

9. **部署、監控與週期性再搜尋**  
   上線後持續監控 Token 流量、API 成本與完成率，並定期累積新軌跡以啟動下一輪自動研究迴圈。

### 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **過度擬合研究環境** | 改進只在開發任務有效，保留任務無感或變差。 | 嚴格區分開發環境與保留任務；保留驗證結果不回饋搜尋。 |
| **指標作弊** | AI 最佳化器利用評估規則漏洞，例如把成本轉移到後期階段。 | 能力與效率指標在搜尋前凍結；採用多項指標與非支配排序。 |
| **下游能力衰退** | 局部效率改進導致驗證、恢復或終止機制失效。 | 每個機制都需通過完整能力指標檢查，並由獨立審查者把關。 |
| **譜系間交叉污染** | 多個平行實驗共用狀態或程式碼，導致失敗擴散。 | 每個搜尋譜系使用隔離、可拋棄的實例與獨立環境。 |
| **搜尋本身成本過高** | 自動研究迴圈消耗大量 API 預算，未必划算。 | 先以小型假設池與精簡環境試跑，驗證 ROI 後再擴大規模。 |
| **驗證資訊洩漏** | 開發過程中意外使用到保留任務資料。 | 建立明確的資料隔離政策與自動化檢查，確保保留任務在凍結前不被檢視。 |

### 與其他技術的整合建議

- **與模型層最佳化互補**  
  SoL-Pi 屬於框架層級最佳化，可與量化、模型壓縮、更快注意力核心或較便宜的模型搭配，形成「模型 + 框架」雙軸降本策略。

- **嵌入現有 Agent 開發框架**  
  可將四項核心機制以中介軟體形式接入 LangChain、AutoGen、Claude Code 或 Codex CLI，作為智慧體迴圈前的觀察過濾與動作調度層。

- **結合可觀測性工具**  
  將 Token 流量、動作次數、上下文長度與觀察大小即時輸出到監控儀表板，作為下一輪自動研究迴圈的輸入。

- **與人類審查流程銜接**  
  在生產環境中，SoL-Pi 發現的機制可先於影子模式（shadow mode）運行，比對原框架輸出，確認無誤後再全面上線。

- **支援多模型後端**  
  論文顯示 SoL-Pi 在 GPT-5.6 Sol 與 Opus 5 上均有效。建議將機制設計為模型無關（model-agnostic），以便在不同 API 供應商間切換與比較成本。
