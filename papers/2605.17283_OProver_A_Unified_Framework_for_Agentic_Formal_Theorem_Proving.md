**原文標題：** OProver: A Unified Framework for Agentic Formal Theorem Proving

## ⚡ TL;DR

現有形式化證明器僅在推論時使用檢索與編譯器回饋，導致訓練與推論不一致，且缺乏修復歷程資料。
提出OProver，結合檢索與回饋多輪修復，並透過迭代訓練與OProofs資料集共同演化證明策略。
OProver-32B於五項基準獲三項最佳與兩項次佳，整體表現超越先前所有開放權重證明器。

## 摘要翻譯

近期形式化定理證明（formal theorem proving）的進展受益於大規模證明生成（large-scale proof generation）與驗證器感知訓練（verifier-aware training），但智能體證明（agentic proving）鮮少整合進證明器訓練中，僅於推論階段運用。我們提出 OProver，一個適用於 Lean 4 的智能體形式化定理證明（agentic formal theorem proving）統一框架，其中失敗的證明嘗試會利用檢索出的編譯器驗證證明（compiler verified proofs）與 Lean 編譯器回饋（Lean compiler feedback）進行迭代修正。OProver 的訓練先經持續預訓練（continued pretraining），再接續迭代後訓練（iterative post-training）：每次迭代執行智能體證明，將新驗證的證明索引至 OProofs 與檢索記憶體（retrieval memory），使用修復軌跡（repair trajectories）作為監督式微調（Supervised Fine-Tuning, SFT）資料，並將未解決的困難案例（unresolved hard cases）用於強化學習（Reinforcement Learning, RL）。OProofs 由公開 Lean 資源、大規模證明合成（large-scale proof synthesis）與智能體證明軌跡（agentic proving traces）建構而成，包含 177 萬筆敘述（statements）、686 萬筆編譯器驗證證明（compiler-verified proofs），以及包含檢索上下文（retrieved context）、失敗嘗試（failed attempts）、回饋（feedback）與修復（repairs）的序列化軌跡（serialized trajectories）。在五項基準測試（benchmarks）中，OProver-32B 於 MiniF2F（93.3%）、ProverBench（58.2%）與 PutnamBench（11.3%）取得最佳 Pass@32，並在 MathOlympiad（22.8%）與 ProofNet（33.2%）排名第二，獲得比以往任何開放權重完整證明證明器（open-weight whole-proof prover）更多的最佳名次。

### 核心貢獻（3～5點）
- 提出 OProver 統一框架，將智能體證明能力深度整合至證明器訓練流程，透過檢索已驗證證明與編譯器回饋迭代修正失敗嘗試，突破傳統僅於推論階段使用智能體的局限。
- 設計持續預訓練結合迭代後訓練的兩階段訓練範式：每次迭代執行智能體證明、索引新驗證證明至檢索記憶體、以修復軌跡進行監督式微調，並針對未解決困難案例執行強化學習。
- 建構大規模 Lean 形式化證明資料集 OProofs，收錄 177 萬筆敘述、686 萬筆編譯器驗證證明，以及包含檢索上下文、失敗嘗試、回饋與修復的序列化軌跡。
- 在五項基準測試中取得領先成績：於 MiniF2F、ProverBench、PutnamBench 獲得最佳 Pass@32，總體最佳名次數量超越以往任何開放權重完整證明證明器。

### 適合對象
從事形式化數學、自動定理證明、大型語言模型推理與智能體系統研究的學者與工程師；特別適合關注 Lean 4 證明自動化、驗證器感知訓練，以及開源權重證明器開發的進階讀者。

## 深度分析

#### 方法論解析

OProver 的核心貢獻在於建立一個 unified framework（統一框架），將過往僅作為 test-time heuristics（測試時啟發法）的 retrieval（檢索）與 compiler feedback（編譯器回饋）內化為 proving policy（證明策略）的一部分，從而解決 train-inference mismatch（訓練-推論不匹配）的結構性問題。具體而言，該框架由三大相互作用的元件構成：

首先是 OProofs Construction（OProofs 建構）。不同於過往 formal corpora（形式化語料庫）僅保存 end products of proving（證明的最終產物），OProofs 額外記錄了 proof construction（證明建構）過程中的 failed attempts（失敗嘗試）、retrieved context（檢索上下文）、compiler diagnostics（編譯器診斷資訊）以及 subsequent repairs（後續修復）。其資料來源包含三大類：public Lean resources（公開 Lean 資源）、large-scale proof synthesis（大規模證明合成）所產生並經 Lean 4 compiler（Lean 4 編譯器）驗證的證明，以及 OProver 自身 agentic proving traces（智能體證明軌跡）。最終資料集包含 1.77M 條 Lean statements（Lean 敘述）與 6.86M 條 compiler verified proofs（編譯器驗證證明），並以 serialized trajectories（序列化軌跡）保存多輪互動歷史。

其次是 OProver Agentic Proving（OProver 智能體證明）。此元件將定理證明形式化為 bounded multi-round refinement process（有界多輪精煉過程）。在第 t 輪，proving policy（證明策略）π 的輸入狀態為 X_t = (s, R_t, p_{t-1}, f_{t-1})，其中 s 為 target theorem statement（目標定理敘述），R_t 為自 retrieval memory（檢索記憶體）M 中查詢取得的 top-k compiler verified proofs（前 k 個編譯器驗證證明），p_{t-1} 為上一輪的 proof attempt（證明嘗試），f_{t-1} 則為 Lean 4 compiler（Lean 4 編譯器）V 回傳的 compiler feedback（編譯器回饋）。策略根據此狀態生成新的 proof attempt，若驗證失敗則進入下一輪 feedback-conditioned refinement（回饋條件化精煉）；若成功則將該證明加回 retrieval memory，形成動態擴充的記憶機制。

第三是 OProver Agentic Training（OProver 智能體訓練）。訓練分為兩階段：第一階段為 continued pretraining（持續預訓練），在 OProofs 上執行以獲得 domain-adapted basemodel OProver-Base；第二階段為 iterative post-training（迭代後訓練），形成 prover 與 corpus 的 co-evolution（協同演化）。每一迭代中，當前 prover 執行 agentic proving（智能體證明）產生 rollouts；成功的 verified proofs（驗證證明）被索引至 retrieval memory，而 repair trajectories（修復軌跡）則作為 SFT（Supervised Fine-Tuning，監督式微調）資料；未能解決的 unresolved hard cases（未解決的困難案例）則保留給 RL（Reinforcement Learning，強化學習）作為下一輪的策略最佳化信號。此設計讓 data、training procedure 與 proving policy 在單一框架內共同演化。

#### 實驗數據解讀

論文採用 Pass@32（給定 32 次嘗試至少成功一次的比例）作為主要評估指標，橫跨五個代表性 benchmarks（基準測試集）。OProver-32B 的表現如下：在 MiniF2F 達到 93.3%、ProverBench 達到 58.2%、PutnamBench 達到 11.3%，此三項皆為最佳成績；在 MathOlympiad 達到 22.8%、ProofNet 達到 33.2%，位列第二。就 open-weight whole-proof provers（開放權重完整證明證明器）而言，OProver 取得最多 top placements。

數據解讀上，MiniF2F 的 93.3% 已非常接近該基準的效能天花板，顯示框架在高中奧林匹亞難度的形式化證明上具備極高穩定性。ProverBench 的 58.2% 則代表在更廣泛的數學命題上，檢索與回饋驅動的修復機制能有效處理多樣化問題。最值得關注的是 PutnamBench 的 11.3%：Putnam 數學競賽題目屬於大學數學競賽中的最高難度，過往自動證明系統在此基準上的成功率極低，雙位數的突破顯示 agentic self-correction（智能體自我修正）與檢索增強對於深層數學推理具有實質助益。MathOlympiad 與 ProofNet 的第二名次則暗示，在極端依賴特定領域知識或長程邏輯鏈的題型上，仍有精進空間。

#### 與現有研究的比較

相較於既有文獻，OProver 的差異化定位相當明確。過往如 Yang et al. (2023)、Jiang et al. (2022)、Wu et al. (2025) 等研究雖已引入 retrieval、compiler feedback 與 iterative repair（迭代修復），但這些能力多被視為 inference-time augmentation（推論時增強），疊加於固定的 fixed prover（固定證明器）之上。換言之，prover 在訓練階段僅見過 finalized proofs（最終證明），推論時卻突然面對 compiler diagnostics（編譯器診斷資訊）與檢索訊號，造成嚴重的 train-inference mismatch（訓練-推論不匹配）。

OProver 從根本上改變此範式：透過將 retrieval-grounded refinement（基於檢索的精煉）與 feedback-conditioned refinement（回饋條件化精煉）納入政策學習，使模型在訓練時即學會如何利用 compiler feedback 與 retrieved context 進行自我修正。資料層面上，現有 formal corpora（形式化語料庫）與 proof-synthesis datasets（證明合成資料集）僅保留 end products of proving（證明的最終產物），缺乏 multi-round interaction histories（多輪互動歷史）；OProofs 則首次大規模保存包含失敗與修復的完整軌跡，填補了 agentic self-correction（智能體自我修正）所需的監督信號缺口。

然而，OProver 仍存在若干限制。首先，框架目前僅針對 Lean 4（Lean 4）設計，其 unified framework 能否遷移至 Coq 或 Isabelle 等系統尚待驗證。其次，whole-proof generation（完整證明生成）的範式在面對極長證明時可能遭遇上下文長度與錯誤傳播的瓶頸，而論文未明確與 tree-search-based provers（基於樹搜尋的證明器）進行直接比較。最後，co-evolution pipeline（協同演化流程）涉及大規模編譯器驗證與多輪迭代，其計算成本與碳足跡顯著高於單遍訓練方法。

#### 可重現性評估

從研究再現的角度觀察，OProver 的方法論描述具備相當的完整性：三大 pipeline（OProofs Construction、Agentic Proving、Agentic Training）的輸入輸出關係、state 定義、以及 iterative post-training（迭代後訓練）的循環邏輯均有清楚交代。論文將 OProver-32B 定位為 open-weight whole-proof prover（開放權重完整證明證明器），間接暗示模型權重可能對外釋出，有利於社群驗證。

不過，在提供的文本範圍內，作者並未明確承諾釋出原始碼、OProofs 的完整下載連結、retrieval memory 的索引方式，或是 SFT 與 RL 階段的詳細超參數與硬體配置。大規模 proof synthesis（證明合成）與 Lean 4 verification（Lean 4 驗證）所需的基礎建設（如分散式編譯驗證環境）門檻極高，若缺乏開源實作，其他研究團隊難以完全重現從 continued pretraining（持續預訓練）到 co-evolution（協同演化）的完整流程。此外，serialized trajectories（序列化軌跡）中的 failed attempts（失敗嘗試）與 compiler feedback 的具體編碼方式（例如錯誤訊息是否經過清洗或截斷）未見詳述，這些細節對於嚴格重現至關重要。

#### 未來研究方向

基於 OProver 的架構與實驗結果，以下幾個方向值得後續探索：

第一，跨系統通用化。當前框架深度整合 Lean 4（Lean 4）的生態，未來可將 co-evolution pipeline（協同演化流程）擴展至 Coq、Isabelle/HOL 或其他形式化系統，驗證其作為通用 agentic formal theorem proving（智能體形式化定理證明）範式的可遷移性。

第二，學習式檢索機制。現行 retrieval memory（檢索記憶體）似乎依賴靜態或啟發式檢索，後續可引入專門訓練的 dense retriever，使 retrieved context（檢索上下文）能更精準地對齊當前證明狀態，進一步提升 retrieval-grounded refinement（基於檢索的精煉）的效率。

第三，層次化與模組化證明。將 OProver 的 whole-proof generation（完整證明生成）與 subgoal decomposition（子目標分解）或 hierarchical planning（層次化規劃）結合，透過「證明草圖→子目標→完整證明」的階段式生成，緩解長證明中的錯誤累積問題。

第四，強化學習演算法深化。目前 RL（Reinforcement Learning，強化學習）僅用於 unresolved hard cases（未解決的困難案例），可進一步探索更具樣本效率的演算法變體（如基於 MCTS 的 RL 或 DPO），並設計更細緻的 reward shaping（獎勵塑形）以反映證明結構的局部正確性。

第五，非形式化與形式化雙向增強。強化 autoformalization（自動形式化）與 informal math reasoning（非形式化數學推理）的互動，例如利用大型語言模型將自然語言證明提示轉化為形式化 sketch，再由 OProver 完成細節驗證，可大幅擴充 OProofs 的覆蓋範圍。

第六，推論效率與成本最佳化。multi-round refinement loop（多輪精煉迴圈）頻繁呼叫 Lean 4 compiler（Lean 4 編譯器）成本高昂，未來可發展輕量級的 feedback simulator（回饋模擬器）或學習式錯誤預測模組，以減少實際編譯次數，加速推論。

## 論文問答

**[Background & Motivation]**

**Q1：OProver 主要想解決形式化定理證明領域中的什麼核心問題？**
A：OProver 主要解決現有形式化定理證明系統中普遍存在的「訓練-推論不匹配」問題。過往的方法雖然會在推論階段引入檢索或編譯器回饋，但這些能力僅作為測試時啟發法或推論時增強，而非證明器本身學習到的策略。這導致模型在訓練時只接觸最終驗證成功的證明，卻未學習如何根據檢索上下文與編譯器診斷資訊進行多輪精煉與證明修復，因此在部署時面對需要迭代修正的真實分布表現不佳。

**Q2：為何現有的形式化語料庫無法有效支援智能體形式化定理證明？**
A：現有的公開形式化語料庫與證明合成資料集大多只保留證明的最終產物，也就是經過編譯器驗證的最終證明。這些語料庫普遍遺漏了失敗嘗試、檢索上下文以及驅動證明修復的編譯器診斷資訊。由於缺乏記錄多輪互動歷史的序列化軌跡，模型無法從中學習智能體自我修正的能力，這正是推動 OProver 建構 OProofs 資料集的關鍵動機。

**Q3：將智能體證明能力整合進訓練流程，而非僅作為推論時的附加模組，為何至關重要？**
A：將檢索、編譯器回饋與迭代修復整合進訓練過程，能夠從根本上消除訓練分布與推論分布之間的落差。若智能體證明能力僅在推論時附加於固定證明器之上，模型從未在訓練階段優化過使用這些訊號的策略，導致其在面對需要基於檢索的精煉與回饋條件化精煉的任務時缺乏穩健性。透過端到端訓練證明策略，OProver 使模型能將檢索記憶體與 Lean 編譯器回饋視為策略的一部分，從而顯著提升形式化定理證明的整體效能。

**[Method & Innovation]**

**Q4：OProver 的核心方法論如何將定理證明形式化為可學習的策略？**
A：OProver 將定理證明形式化為一個有界限的多輪精煉迴圈，由證明策略 𝜋、檢索記憶體 𝑀 與 Lean 4 編譯器 𝑉 三個互動元件構成。在每一輪中，策略會根據目標定理、檢索到的已驗證證明、前一次的失敗嘗試以及編譯器回饋來產生新的證明草稿。若編譯器驗證失敗，系統會將診斷資訊返回給策略進行回饋條件化精煉；一旦成功，該證明便會被加回檢索記憶體，供後續證明檢索使用。

**Q5：相較於過往的 Lean 資料集，OProofs 的關鍵創新與獨特價值是什麼？**
A：OProofs 與過往 Lean 資料集最大的不同在於，它不僅收錄最終的編譯器驗證證明，更完整保存了序列化的證明建構軌跡。這些軌跡包含了檢索上下文、失敗嘗試、Lean 編譯器回饋以及後續的修復過程，提供了過去形式化語料庫所缺乏的監督訊號。該資料集透過整合公開 Lean 資源、大規模證明合成與智能體證明軌跡三種互補來源，形成一個能同時支援持續預訓練與迭代後訓練的動態語料庫。

**Q6：OProver 的迭代後訓練管道如何具體促成證明器與語料庫的共同演化？**
A：OProver 的迭代後訓練形成了一個證明器與語料庫共同演化的閉環：每一輪迭代中，當前證明器會執行智能體證明並產出新的驗證證明與修復軌跡。新驗證的證明會被索引到檢索記憶體與 OProofs 中，而修復軌跡則作為監督式微調的訓練資料，未解決的困難案例則保留給強化學習提供策略優化訊號。這種設計使得資料、訓練流程與證明策略能夠在單一框架內持續協同進化，而非像傳統方法那樣讓模型與資料靜止不變。

**[Experiments & Results]**

**Q7：OProver-32B 在五個基準測試上的關鍵實驗結果為何？**
A：OProver-32B 在五個形式化定理證明基準測試上取得了領先的成績，其中在 MiniF2F 達到 Pass@32 93.3%、ProverBench 58.2%、PutnamBench 11.3%，均為最佳表現。同時，它在 MathOlympiad 與 ProofNet 上分別取得 22.8% 與 33.2%，排名第二。這些結果顯示 OProver 在開放權重完整證明證明器中獲得了比以往任何系統都更多的頂尖名次，驗證了將智能體能力整合進訓練框架的有效性。

**Q8：為何 Pass@32 是評估 OProver 特別合適的指標？**
A：Pass@32 衡量的是在給定 32 次嘗試機會中，至少能成功產生一個正確證明的比例，這對於評估 OProver 這類具備迭代修正能力的系統特別重要。由於 OProver 本質上是一個多輪精煉迴圈，單次生成指標無法充分反映其透過檢索與編譯器回饋逐步修復證明的優勢。該指標因此能夠捕捉智能體證明在有限嘗試次數內的探索與修正潛力，證明其在實際應用中具備更高的容錯性與成功率。

**Q9：OProver-32B 與先前開放權重的完整證明證明器相比，展現了什麼樣的規模與效能關係？**
A：OProver-32B 採用 320 億參數的模型規模，在現有開放權重完整證明證明器中展現了最強的整體競爭力。相較於過往僅依賴單遍生成或 Best-of-N 完整證明生成的開源系統，OProver 透過智能體形式化定理證明框架與迭代後訓練，在相同權重開放下取得了更均衡且優異的跨基準表現。這說明當模型具備足夠容量時，將檢索與回饋機制內化為學習策略，能夠比單純擴大生成樣本數更有效地提升形式化推理能力。

**[Applications & Impact]**

**Q10：OProver 的統一框架在學術基準之外，有哪些潛在的實際應用場景？**
A：OProver 的統一框架可應用於需要高度可靠性的驗證軟體開發流程，例如作業系統核心、編譯器或密碼學協定的形式化驗證。在這些場景中，工程師經常需要反覆與編譯器互動以修復證明漏洞，而 OProver 能自動執行這種基於編譯器回饋的證明修復，顯著降低人工介入的成本。此外，它也能作為數學研究者的互動式助手，協助將非形式化的數學直覺轉化為經過機械驗證的嚴格證明。

**Q11：若要將 OProver 產品化為互動式定理證明輔助工具，需要考量哪些系統與工程因素？**
A：在實際產品化部署 OProver 時，必須考量檢索記憶體的即時索引與維護成本，因為隨著驗證證明數量增加，記憶體規模與檢索效率將直接影響推論延遲。此外，多輪精煉迴圈需要與 Lean 4 編譯器緊密整合，每一輪都涉及編譯驗證，這對系統的計算資源與回應時間提出了較高要求。因此，在設計互動式定理證明輔助產品時，需要權衡迭代深度、檢索品質與使用者體驗，並可能需要建立快取機制或近似檢索來加速回饋迴路。

**Q12：OProver 的成功可能對機器推理與 AI 數學領域帶來什麼樣的深遠影響？**
A：OProver 為機器推理領域樹立了新的典範，證明形式化定理證明不應僅止於最終證明的生成，而應將失敗與修復的歷程視為核心學習訊號。這種將智能體自我修正內化為策略的方法，有望啟發其他形式化系統如 Coq 或 Isabelle 發展出類似的訓練框架。更廣泛地說，它縮短了機器輔助數學與實際軟體驗證之間的距離，顯示出大型語言模型在嚴格形式系統中透過環境回饋持續改進的可行性。

**[Limitations & Future]**

**Q13：OProver 目前有哪些已知的限制與不足之處？**
A：儘管 OProver 在多項基準上表現突出，其在 PutnamBench 等極具挑戰性的競賽題目上成功率仍僅有 11.3%，顯示對於需要高度原創數學洞察的難題仍有明顯局限。此外，該框架目前專注於 Lean 4 生態系，其檢索記憶體與編譯器回饋機制高度依賴 Lean 的型別系統與錯誤訊息格式，遷移至其他證明輔助工具需要額外工程。同時，迭代式的多輪驗證流程相較於單遍生成會消耗更多計算資源，這在資源受限的環境中可能構成實用瓶頸。

**Q14：在哪些類型的失敗案例中，OProver 的智能體精煉迴圈可能難以收斂？**
A：OProver 的智能體精煉迴圈可能在檢索記憶體缺乏相關引理或相似證明結構的極冷門領域中難以收斂。當目標定理需要跨越多個抽象層次的長程依賴，而編譯器回饋僅提供局部型別錯誤時，模型可能陷入重複修正表面語法卻無法觸及核心邏輯缺陷的循環。此外，若定理的證明需要突破性的構造或全新的數學引理，單純基於既有已驗證證明的檢索與局部修復策略，往往難以產生足夠的創新性來解決問題。

**Q15：未來研究可以從哪些方向進一步擴展 OProver 的共同演化管道？**
A：未來研究可將 OProver 的共同演化管道擴展至 Lean 4 以外的形式化系統，例如 Coq 或 Isabelle，以驗證此框架的通用性。另一方面，結合非形式化數學推理與自然語言解釋，或許能讓模型在形式化證明之前先進行高層次規劃，從而改善對極困難案例的處理能力。此外，透過更先進的語義檢索技術、更大規模的模型容量，以及自動化的大規模證明生成來持續擴充 OProofs，都有望進一步推動開放權重完整證明證明器邁向更高的效能天花板。

## 實務應用指南

### 適用場景

1. **大型形式化數學專案之證明自動化**  
   適用於需要將大量數學定理轉譯為 Lean 4 並完成機械驗證的研究機構或開源社群（如 Mathlib 擴展計畫）。OProver 的多輪精煉迴圈可協助數學家從草稿狀態逐步收斂至編譯器驗證證明，降低互動式證明的人工負擔。

2. **關鍵演算法與軟體系統的形式化驗證**  
   在需要高可靠度的領域（如密碼學協定、分散式系統共識演算法、作業系統核心模組），可利用 OProver 將規格敘述轉為形式化命題，並透過基於檢索的精煉與回饋條件化精煉，自動生成經 Lean 4 可信核心確認的型別正確證明。

3. **智慧數學教育與互動式解題平台**  
   將 OProver 部署為後端智能體，學生輸入證明嘗試後，系統可即時回傳 Lean 編譯器回饋與檢索自 OProofs 的相似參考證明，引導學生進行證明修復。此場景特別適合奧林匹亞數學培訓或高等數學線上課程。

4. **自然語言數學文獻的自動形式化與知識庫建構**  
   出版社或學術資料庫可運用 OProver 的資料回流機制，將自動形式化後的命題投入智能體證明軌跡收集，持續擴充 OProofs 規模，形成「自動形式化 → 證明合成 → 人工校驗 → 索引回流」的知識庫生產線。

5. **開源數學庫的證明補全與維護**  
   針對既有 Lean 4 專案中遺留的 `sorry`（待補證明）或 Mathlib 升級導致的證明失效，可利用 OProver 的檢索記憶體查詢歷史驗證證明，並以修復軌跡作為監督式微調資料，自動化完成證明補全與遷移。

### 實作前置條件

**資料準備**
- 領域語料：至少需準備百萬級 Lean 4 程式碼與數學敘述作為持續預訓練基底，並搭配公開 Lean 資源（如 Mathlib）與原始非形式化數學文本作為自動形式化來源。
- 檢索記憶體：需建構可擴展的向量資料庫或符號檢索系統，用於儲存並即時查詢已驗證證明，且需支援每輪迭代後動態索引新增的成功證明。
- 軌跡資料：必須能序列化並儲存多輪互動歷史，包含檢索上下文、失敗嘗試、編譯器診斷資訊與後續修復內容。

**運算資源**
- 預訓練與後訓練：需具備百卡級以上高端 GPU（如 A100/H100）叢集，以支援 32B 參數模型的持續預訓練與多輪迭代後訓練（含監督式微調與強化學習）。
- 編譯器驗證叢集：需部署可平行化處理的 Lean 4 編譯器農場，因為智能體證明過程中每輪嘗試都需即時編譯驗證，延遲將直接影響推論吞吐量與訓練採樣效率。

**技術能力**
- 團隊需熟悉 Lean 4 語法、依賴型別理論與形式化數學工作流程；同時需具備大型語言模型分散式訓練、檢索增強生成（RAG）系統工程、以及強化學習（如 PPO/GRPO）實作經驗。

### 實作步驟建議

**步驟一：建構領域專屬 OProofs 語料與檢索記憶體**  
從公開 Lean 資源與內部非形式化文件出發，執行去重、過濾、自動形式化，並透過大規模證明合成產生初始編譯器驗證證明。將這些證明索引至檢索記憶體，作為後續檢索上下文與預訓練資料來源。

**步驟二：執行持續預訓練取得領域基座模型**  
在通用基座模型上進行一次性持續預訓練，使用 OProofs 中的 Lean 程式碼與數學內容，產出領域適配的 `OProver-Base`。此階段目標是讓模型熟悉 Lean 4 語法結構與數學證明風格。

**步驟三：部署智能體證明推論環境**  
建置 Target theorem → 檢索記憶體查詢（top-k 已驗證證明）→ 證明策略生成 → Lean 4 編譯器驗證 → 回饋條件化精煉 的多輪精煉迴圈。確保編譯器回饋能完整傳遞給策略模型，且成功證明可即時寫回檢索記憶體。

**步驟四：啟動迭代後訓練與資料共演化迴圈**  
每輪迭代執行：(1) 使用當前模型進行智能體證明採樣；(2) 將新產生的驗證證明索引至檢索記憶體並擴充 OProofs；(3) 以修復軌跡作為監督式微調資料進行 SFT；(4) 將未解決的困難案例保留為強化學習訓練訊號。重複此循環直至驗證通過率收斂。

**步驟五：產品化介面與人機協作整合**  
封裝證明策略為 API 或 IDE 外掛，提供「生成—驗證—建議修復」的互動介面。針對企業場景，需加入人工審核閘道，讓領域專家確認自動生成證明後再納入正式程式碼庫。

### 潛在風險與注意事項

**訓練-推論分布不匹配（Train-Inference Mismatch）**  
若僅在推論階段才引入檢索與編譯器回饋，模型在訓練時未見過失敗嘗試與修復分布，容易在部署後產生幻覺或無效證明。**緩解方式**：嚴格遵循論文的迭代後訓練流程，確保修復軌跡與強化學習訊號確實來自模型自身產出的智能體證明軌跡，而非僅使用第三方靜態語料。

**檢索記憶體品質與覆蓋率不足**  
若初始 OProofs 規模過小或領域偏移嚴重，檢索出的已驗證證明可能與目標定理無關，導致策略模型被誤導。**緩解方式**：在冷啟動階段優先確保語料涵蓋目標領域的基礎引理（lemmas），並在每次迭代後主動監控檢索命中率與證明重用率。

**編譯器驗證延遲與系統瓶頸**  
Lean 4 編譯器在面對大型專案時可能產生顯著延遲，若推論過程中每輪嘗試都需同步等待驗證，將嚴重拖慢採樣與使用者體驗。**緩解方式**：採用非同步驗證佇列與編譯器快取機制；在訓練階段可預先批次驗證，推論階段則設定超時與最大回合數上限。

**強化學習訓練不穩定**  
以未解決的困難案例作為強化學習訊號時，獎勵稀疏且方差大，容易導致策略崩潰。**緩解方式**：設計細粒度獎勵函數（如編譯器錯誤數量減少、證明長度縮短），並搭配穩定的 RL 演算法（如經過驗證的 PPO 變體）與梯度裁剪。

**Lean 4 版本更新導致證明失效**  
形式化證明對語言版本與函式庫 API 高度敏感，Mathlib 升級可能使既有驗證證明與模型輸出失效。**緩解方式**：將檢索記憶體與 OProofs 綁定特定 Lean 4 與 Mathlib 版本快照；建立自動化 CI 管線定期重驗既有證明，並觸發模型微調以適應新版語法。

### 與其他技術的整合建議

**與現有 Lean 4 開發工具鏈整合**  
將 OProver 封裝為 VS Code Lean 4 擴充功能或 Language Server Protocol（LSP）後端，讓使用者在編輯器內直接觸發「證明建議」與「錯誤修復」指令，並把檢索記憶體查詢結果以 inline hint 形式呈現。

**與企業 CI/CD 及程式碼審查系統整合**  
在軟體驗證場景中，可將 OProver 嵌入 GitHub/GitLab CI 流程：當開發者提交包含形式化規格的 Pull Request 時，自動觸發智能體證明嘗試，並將生成的完整證明與編譯器驗證報告附加為審查評論，供維護者確認。

**與檢索增強生成（RAG）基礎建設整合**  
若組織已具備向量資料庫（如 Milvus、Pinecone）與 Embedding 服務，可直接將 OProofs 的已驗證證明視為專屬知識庫，利用現有 RAG 管線實現 top-k 檢索，僅需額外開發 Lean 4 專用的符號相似度計算或重排序（reranking）模組。

**與教育平台及學習管理系統（LMS）整合**  
針對數學教育場景，將 OProver 的多輪精煉迴圈包裝為「逐步提示」API，限制每回合僅揭露部分回饋（如只顯示錯誤型別不直接給出修復後證明），避免學生過度依賴自動生成，同時記錄學生的失敗嘗試與修復軌跡作為學習分析資料。
