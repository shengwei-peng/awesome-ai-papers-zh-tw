# LongHorizon-Harness：提升長程智慧體在真實世界任務上的能力

## ⚡ TL;DR

現有智慧體框架將執行、狀態與評估混於不斷增長的上下文中，導致錯誤累積且任務狀態難以追蹤。
本文提出 LongHorizon-Harness，以MEA迴圈外移任務狀態，並用環境驗證的事實更新。
實驗顯示WeaveBench、Terminal-Bench與OSWorld的表現均顯著提升。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）智慧體（agent）日益承擔需要持續推理、工具使用（tool use），並在眾多相互依賴的步驟中持續修正的長程任務（long-horizon tasks）。然而，現有的智慧體框架（agent harnesses）將任務執行（task execution）、任務狀態（task state）與完成度評估（completion assessment）全部維護在不斷增長的上下文（context）中，導致狀態難以追蹤，並使錯誤的自我評估傳播到後續決策。我們將長程執行（long-horizon execution）重新定義為任務狀態管理問題，並提出 LongHorizon-Harness，該框架在執行過程之外明確維護任務狀態，且僅以經環境獨立驗證的事實更新狀態。其管理-執行-稽核（Manage-Execute-Audit, MEA）迴圈由管理器（manager）維護任務狀態並決定下一個子任務，再由全新上下文執行器（fresh-context executor）執行該子任務，最後由唯讀稽核器（read-only auditor）在下一輪開始前驗證產生的環境狀態。輕量級 AgentAdapter 支援可互換的模型後端（model backend）與工具框架後端（harness backend），無需修改其原生智慧體迴圈（native agent loops）。LongHorizon-Harness 使 Qwen 3.7-Plus 在 WeaveBench 上從 51.8% 提升至 80.7%，在 Terminal-Bench 2.1 上從 69.7% 提升至 77.2%，並在 OSWorld 2.0 上從 2.8% 提升至 8.3%。它亦使 Claude Opus 4.7 在 OSWorld 2.0 子集（subset）上從 20.0% 提升至 34.3%，展現出在模型、工具框架與互動領域間的一致提升。

### 核心貢獻（3～5點）
- 將長程執行重新定義為任務狀態管理問題，把任務狀態外化於執行過程之外，並僅以環境獨立驗證的事實更新，避免錯誤自我評估累積傳播。
- 提出管理-執行-稽核（MEA）迴圈：管理器規劃子任務、全新上下文執行器執行、唯讀稽核器驗證環境狀態，實現狀態追蹤與動作執行的分離。
- 設計輕量級 AgentAdapter，支援模型後端與工具框架後端無縫互換，無需修改原生智慧體迴圈。
- 在 WeaveBench、Terminal-Bench 2.1、OSWorld 2.0 等多項基準測試上，對 Qwen 3.7-Plus 與 Claude Opus 4.7 均帶來顯著且一致的效能提升。

### 適合對象
適合從事長程智慧體、大型語言模型工具使用、自主任務執行框架、電腦使用（computer use）與多模態互動（multimodal interaction）等領域的研究人員與工程師，特別是關注基準測試評估、上下文管理，以及跨模型／跨框架整合的讀者。

## 深度分析

#### 方法論解析

##### 核心問題重構：從單一軌跡到任務狀態（task state）管理
LongHorizon-Harness 把長程執行（long-horizon execution）重新定義為一連串「經獨立稽核的任務狀態轉換」。傳統智慧體工具框架（agent harness）把任務執行（task execution）、任務狀態維護與完成度評估（completion assessment）全部塞進同一個不斷增長的上下文（context）中，導致三個結構性問題：(i) 執行與狀態共用 context，歷史越長越難追蹤；(ii) 執行者同時兼任裁判，錯誤的自我評估會被寫入任務狀態並成為後續決策的前提；(iii) 早期錯誤與目標偏移（goal drift）會沿著軌跡（trajectory）累積放大。LongHorizon-Harness 的解法是將任務狀態外顯化為獨立紀錄，只允許「從環境獨立驗證過的事實」更新它，並由管理器（manager）根據當前狀態與原始目標推導下一個子任務。

##### Manage-Execute-Audit（MEA）迴圈詳解
每一輪 MEA 迴圈（MEA loop）包含三個解耦角色：

1. **管理器（manager）**：讀取當前任務狀態 \(S_i\)，產生一份子任務合約 \(c_i\)。合約明確定義子目標、驗收準則（acceptance criteria）、邊界限制與相關先驗證據。必要時可走 ask route 向使用者詢問資訊或取得授權。這相當於把「要什麼」與「怎麼判斷完成」先寫成規格，再交給執行者。

2. **執行器（executor）**：在全新、有預算限制的新鮮上下文（fresh context）中只執行這一個子任務，並修改環境。由於 context 不攜帶過往執行歷史，執行器不會被之前失敗或偏離目標的對話污染，也避免上下文退化（context rot）。子任務完成後，執行器的互動歷史會被丟棄，只有精簡、已驗證的任務狀態會跨輪保留。

3. **稽核器（auditor）**：以唯讀（read-only）方式獨立檢查執行後的環境，判斷哪些條件已滿足、哪些產出物（artifacts）已產生、哪些事實已被發現，並產出稽核報告 \(v_i\)。稽核器不修改環境，因此不會陷入執行者的確認偏誤，也讓完成度評估與執行動作解耦。

管理器根據 \(v_i\) 更新任務狀態後，再進入下一輪。整個長程任務因此變成「狀態 → 合約 → 執行 → 稽核 → 狀態」的離散轉換序列，而非一條連續增長的對話軌跡。

##### AgentAdapter 與後端互換性
LongHorizon-Harness 透過輕量的 AgentAdapter 與現有智慧體工具框架（如 Claude Code、Codex CLI、OpenClaw、Hermes Agent）對接，保留其原生智慧體迴圈（native agent loops），同時支援模型後端（model backend）與工具框架後端（harness backend）的互換。這意味著 manager、executor、auditor 三個角色可以分別選用不同模型或框架，例如 executor 用擅長編碼的模型、auditor 用擅長檢視的模型，而不需要改動底層系統。

##### 設計動機與對應挑戰
- **對抗累積錯誤（compounding errors）**：每輪只承認稽核器驗證過的事實，錯誤不會被寫入長期狀態繼續傳播。
- **對抗上下文退化（context rot）**：執行歷史不會累積，跨輪資訊以精簡狀態呈現。
- **對抗任務狀態遺失（task-state loss）**：任務狀態被外顯化並由管理器專責維護，成為決策的單一真實來源。

不過，這套方法也仰賴稽核器能正確觀察環境、驗收準則能被明確定義，且子任務之間的相依性與邊界能被準確刻畫。若環境回饋不完整或合約規格模糊，獨立稽核的價值會下降。

#### 實驗數據解讀

##### 基準測試（benchmark）與指標
論文在三個近期長程基準測試上驗證：

| 基準測試 | 領域 | 主要指標 |
|---|---|---|
| WeaveBench | 跨介面協調 | PassRate |
| Terminal-Bench 2.1 | 命令列任務 | 推測為通過率 / 完成率 |
| OSWorld 2.0 | 桌面圖形介面工作流 | binary completion |

這三個基準分別涵蓋了跨 API / CLI / GUI 的長程互動，能檢驗框架在不同互動領域的泛化性。

##### 量化結果與效應量
以 Qwen 3.7-Plus 為模型後端時：

- **WeaveBench**：PassRate 從 51.8% 提升至 80.7%，進步 28.9 個百分點。這不僅大幅超越自身基線，也高於官方最強結果 41.2%（Claude Opus 4.7 + Claude Code），幾乎是後者的兩倍。
- **Terminal-Bench 2.1**：從 69.7% 提升至 77.2%，進步 7.5 個百分點。
- **OSWorld 2.0（完整測試）**：binary completion 從 2.8% 提升至 8.3%，絕對進步 5.5 個百分點，但相對成長約 3 倍。

以 Claude Opus 4.7 在 OSWorld 2.0 的 34 題子集（subset）上測試，則從 20.0% 提升至 34.3%，進步 14.3 個百分點。

##### 跨領域與跨模型一致性
數據呈現幾個值得注意的現象：

1. **WeaveBench 的增益最大**：這類跨介面協調任務通常涉及多個工具、多個檔案與多步驟依賴，最容易出現目標偏移與狀態遺失。外顯任務狀態與獨立稽核正好對症下藥。

2. **Terminal-Bench 增益相對溫和**：命令列任務的輸出通常較為確定，基線工具框架已能透過終端機回饋維持一定狀態，因此 MEA 迴圈的邊際效益較小，但仍達到 7.5 個百分點的穩定提升。

3. **OSWorld 絕對值仍低**：即使相對成長顯著，完整測試的 binary completion 僅 8.3%，顯示桌面 GUI 長程任務仍是極大挑戰。子集測試中 Claude Opus 4.7 達到 34.3%，可能反映子集難度較低或該模型在視覺推理上的優勢。

4. **跨模型一致改善**：無論是 Qwen 3.7-Plus 或 Claude Opus 4.7，引入 LongHorizon-Harness 後都提升，說明增益主要來自框架設計，而非單純換用更強模型。

##### 絕對表現與剩餘挑戰
雖然相對進步顯著，但 OSWorld 2.0 等真實桌面環境的絕對成功率仍遠低於實用門檻。此外，論文未報告成本、延遲、每輪平均呼叫次數等實務指標，這些會影響在真實長程任務（動輒數小時）中的可部署性。

#### 與現有研究的比較

##### 相對於傳統 agent harness
現有智慧體工具框架如 Claude Code、Codex CLI、OpenClaw 已支援規劃（planning）、任務分解（task decomposition）、工具使用（tool use）與隔離 context 的子代理（subagents）。然而，它們普遍存在兩個結構限制：(i) 執行與任務狀態共用同一個增長中的 context；(ii) 執行者同時負責判斷完成與否。LongHorizon-Harness 透過外顯任務狀態、fresh-context executor 與 read-only auditor，把這兩個耦合點解開，從系統層面降低錯誤傳播與自我評估偏誤。

##### 與驗證／稽核相關研究的關聯
過去已有研究探討讓模型檢查自身輸出或環境狀態以提升正確性（Zheng et al., 2023; Zhuge et al., 2024）。LongHorizon-Harness 把這類驗證機制系統化為 MEA 迴圈的一環，並與任務狀態管理結合：稽核不再只是「額外檢查」，而是決定下一輪狀態與子任務的正式閘道。

##### 主要貢獻與限制
**主要貢獻**：
- 將長程執行重新框架為任務狀態管理問題；
- 提出可插拔後端的 MEA 架構；
- 在多個基準與模型上展示一致且顯著的增益。

**限制**：
- 稽核器的正確性仍受限於模型能力與環境可觀察性。若環境狀態難以唯讀檢查（例如需要理解複雜視覺布局或隱含業務邏輯），稽核可能失準。
- 子任務合約的品質高度影響結果，但如何自動產生高品質合約仍具挑戰。
- 每輪丟棄 executor context 雖然減少污染，但也可能丟失對後續子任務有用的微觀細節。
- 論文未討論運算成本、延遲與人機協作時的授權流程細節。

#### 可重現性評估

##### 程式碼與資料開放性
根據提供的摘要與引言，論文並未明確說明是否釋出原始碼、提示模板（prompts）或任務狀態的結構化格式。三個基準測試（WeaveBench、Terminal-Bench 2.1、OSWorld 2.0）本身是公開資料集，但 LongHorizon-Harness 的實作細節（manager 的合約生成邏輯、auditor 的唯讀工具組、AgentAdapter 的介面規格）若未公開，將大幅限制外部重現。

##### 模型與硬體需求
實驗同時使用開源模型 Qwen 3.7-Plus 與專有模型 Claude Opus 4.7。Qwen 系列權重可取得，但 Claude Opus 4.7 與 GPT 系列需透過 API 呼叫，增加重現成本與不可控因素。此外，OSWorld 2.0 等桌面環境需要虛擬機或容器化基礎設施，硬體與授權門檻不低。

##### 評估協議透明度
論文提到在「matched model backends and evaluation protocols」下進行比較，但未提供完整的超參數、每題嘗試次數、時間限制、稽核失敗時的重試策略等細節。若要達到可重現性，作者至少需要釋出：(i) 核心框架程式碼；(ii) 三個角色使用的提示與工具定義；(iii) 狀態更新與合約生成的演算法細節；(iv) 完整的執行日誌或至少統計摘要。

#### 未來研究方向

##### 技術強化
- **更強大的稽核器（auditor）**：引入多模態感知、主動驗證（active verification）或形式化規格檢查，讓 auditor 能處理更複雜的 GUI 狀態與隱含業務邏輯。
- **自適應子任務粒度**：讓管理器（manager）根據任務難度與當前狀態不確定性動態調整子任務大小，避免過細導致開銷過大，或過粗導致稽核困難。
- **錯誤復原與重新規劃**：當稽核報告顯示子任務未達驗收準則時，設計自動回滾（rollback）或修復子任務機制，而非僅更新狀態。
- **狀態更新的不確定性建模**：讓任務狀態攜帶置信度或替代假設，提升在模糊環境下的穩健性。

##### 應用擴展
- **更長的任務完成時程（task-completion horizon）**：將 MEA 迴圈擴展到數小時甚至數天的軟體工程或科學發現任務，並結合持久化記憶體與跨會話狀態恢復。
- **人機協作**：強化 ask route，讓管理器在需要授權、價值判斷或資訊不足時，以結構化方式向人類提問，而非中斷整個流程。
- **安全與對齊**：研究如何防止執行器或外部環境操縱任務狀態，並確保稽核器的判斷與人類意圖一致。

##### 評估與方法論
- **成本—效益分析**：建立包含 API 呼叫次數、延遲、token 消耗與成功率的綜合指標，評估 LongHorizon-Harness 在真實部署場景的經濟可行性。
- **元件消融研究**：進一步區分「外顯任務狀態」、「fresh-context executor」與「read-only auditor」各自的邊際貢獻，並在不同模型組合上進行系統性比較。
- **形式化驗證**：探索任務狀態轉換是否可納入形式化框架，以提供某些類型任務的完成保證。

## 論文問答

**Q1：長程任務執行目前面臨哪些核心挑戰？**
A：目前長程任務執行主要面臨三大挑戰：累積錯誤與目標偏移、上下文退化，以及任務狀態遺失。累積錯誤與目標偏移是指早期步驟的錯誤會沿著執行軌跡不斷放大，使智慧體逐漸偏離原始目標；上下文退化則是隨著互動歷史增長，關鍵資訊越來越難以被檢索與利用，導致效能急遽下降。任務狀態遺失則代表智慧體難以持續維護一份準確且最新的任務狀態，而這份狀態對於協調多個相互依賴的步驟至關重要。

**Q2：現有智慧體工具框架在長程執行上有哪些結構性限制？**
A：現有框架存在兩個主要結構性限制：第一，任務執行與任務狀態管理共享同一份不斷增長的上下文，導致狀態越來越難追蹤；第二，任務執行與完成度評估仍然緊密耦合，智慧體在執行子任務的同時也自行判斷是否完成。這種設計使得錯誤的自我評估容易被記錄為任務狀態的一部分，並成為後續決策的前提，進而造成錯誤傳播。隨著軌跡變長，這些問題會相互加劇，顯著降低長程任務的成功率。

**Q3：為何將長程執行重新定義為任務狀態管理問題很重要？**
A：將長程執行重新定義為任務狀態管理問題，可以把焦點從「產生一條連續的動作軌跡」轉移到「維護一份準確、經過驗證的任務狀態」。這種觀點強調任務狀態應該獨立於執行過程之外，並且只根據環境中獨立驗證過的事實來更新。如此一來，後續子任務的規劃便能建立在可靠的基礎上，減少錯誤累積與目標偏移的風險。

**Q4：LongHorizon-Harness 的核心 MEA 迴圈如何運作？**
A：LongHorizon-Harness 採用「管理—執行—稽核」（Manage-Execute-Audit, MEA）三階段迴圈來處理長程任務。首先，管理器讀取當前任務狀態，並根據原始目標定義下一個子任務的合約，包括目標、驗收標準、邊界限制與相關先驗證據；接著，全新上下文執行器在乾淨且受預算限制的上下文中執行該子任務，並修改環境。最後，唯讀稽核器獨立檢查環境變化，產出稽核報告，管理器再依據報告更新任務狀態並進入下一輪，執行器的互動歷史則會被丟棄。

**Q5：為何要將任務狀態維護在執行上下文之外，並只以獨立驗證的事實更新？**
A：將任務狀態維護在執行上下文之外，可以避免不斷增長的執行歷史干擾狀態追蹤，從而減緩上下文退化的問題。同時，只允許透過獨立稽核器從環境中驗證的事實來更新狀態，能夠防止智慧體產生幻覺或錯誤的自我評估被寫入任務狀態。這樣的設計確保每一輪決策都建立在客觀、可檢驗的環境事實上，而非執行器的主觀宣稱。

**Q6：AgentAdapter 的設計目的與優勢是什麼？**
A：AgentAdapter 是一個輕量轉接層，目的是讓 LongHorizon-Harness 能夠在不修改現有智慧體原生迴圈的前提下，支援多種模型後端與工具框架後端的互換。這意味著無論底層使用 Claude Code、Codex CLI、OpenClaw 或 Hermes Agent 等框架，還是 Claude Opus、GPT、Qwen 等模型，都可以透過統一介面接入 MEA 迴圈。這種設計大幅提升了框架的通用性與可移植性，也讓研究人員與工程師能更容易地在不同系統間進行比較與部署。

**Q7：論文在哪些基準測試上評估 LongHorizon-Harness？**
A：論文選用了 WeaveBench、Terminal-Bench 2.1 與 OSWorld 2.0 三個近期提出的長程基準測試。WeaveBench 側重跨介面協調任務，OSWorld 2.0 聚焦桌面工作流程，而 Terminal-Bench 2.1 則涵蓋具挑戰性的命令列任務。這三個基準測試共同覆蓋了圖形介面、終端機與跨介面互動等多樣場景，能夠較全面地檢驗框架在不同互動領域的表現。

**Q8：LongHorizon-Harness 帶來哪些關鍵性能提升？**
A：在 WeaveBench 上，LongHorizon-Harness 將 Qwen 3.7-Plus 的 PassRate 從 51.8% 提升至 80.7%，顯著超越 Claude Opus 4.7 搭配 Claude Code 官方報告的 41.2%；在 Terminal-Bench 2.1 上，Qwen 3.7-Plus 的表現從 69.7% 提升至 77.2%。在 OSWorld 2.0 完整基準上，Qwen 3.7-Plus 的二元完成率從 2.8% 提升至 8.3%，而在 34 題子集上，Claude Opus 4.7 的表現也從 20.0% 提升至 34.3%。這些結果顯示框架在不同模型、不同工具框架與不同互動領域都能帶來一致且顯著的進步。

**Q9：論文是否有提供消融實驗或各元件貢獻分析？**
A：根據目前提供的全文內容，論文並未詳細列出個別元件的消融實驗結果，而是透過整體設計的合理性與最終性能提升來說明 MEA 迴圈的有效性。從設計邏輯來看，管理器、全新上下文執行器與唯讀稽核器三者各司其職，分別負責狀態維護與子任務規劃、無干擾執行，以及獨立驗證，彼此相輔相成。未來研究可以進一步拆解這三個角色的個別貢獻，例如比較有無稽核器、是否使用全新上下文，或管理器更新策略的差異。

**Q10：哪些真實應用場景最能受惠於 LongHorizon-Harness？**
A：LongHorizon-Harness 特別適合需要多步驟、長時間執行且環境狀態可驗證的場景，例如軟體工程中的大型專案開發、資料分析與科學運算管線、IT 維運自動化，以及桌面端的複雜工作流程。在這些應用中，任務通常包含許多相互依賴的步驟，且每一步的結果都可以透過檔案系統、程式輸出或介面狀態進行檢查。透過 MEA 迴圈，系統能夠持續追蹤已完成的子任務與待處理項目，降低因錯誤累積而導致整體失敗的風險。

**Q11：在產品化時需要考慮哪些系統層面因素？**
A：產品化時首先需要確保 AgentAdapter 能夠穩定對接目標模型後端與工具框架後端，並維持原生智慧體迴圈的完整性。其次，唯讀稽核器的呼叫頻率與範圍會直接影響延遲與成本，因此需要在驗證完整性與系統開銷之間取得平衡。此外，執行器的上下文預算、使用者授權路線的安全性、稽核工具的唯讀隔離，以及失敗時的重試與回退機制，都是實際部署時必須仔細設計的環節。

**Q12：這項研究對智慧體領域可能產生什麼影響？**
A：這項研究提出了一種將長程執行明確建模為任務狀態管理問題的典範，並透過獨立稽核來確保狀態更新的可靠性，這可能成為未來長程智慧體工具框架設計的重要參考模式。它同時展示了在模型層之外，透過更好的系統架構與狀態管理也能顯著提升長程任務成功率。這種模型無關的改進路徑有助於推動整個領域從單純擴大模型規模，轉向更精緻的執行與驗證機制。

**Q13：作者承認哪些限制？**
A：儘管 LongHorizon-Harness 帶來顯著相對提升，但在 OSWorld 2.0 完整基準上的絕對表現仍僅有 8.3%，顯示這類開放式桌面任務依然極具挑戰性。此外，稽核器雖然能獨立檢查環境，但其觀察能力仍受限於可用工具與驗收標準的清晰度，管理器的規劃品質也仍然依賴底層語言模型的推理能力。MEA 迴圈的多輪結構也會帶來額外的計算與時間開銷，這在資源受限的場景中需要審慎評估。

**Q14：在什麼情況下 MEA 迴圈可能失敗？**
A：當子任務的驗收標準過於模糊或難以透過現有唯讀工具客觀檢驗時，稽核器可能無法準確判斷執行結果，導致任務狀態更新錯誤。如果環境觀察不完整，或管理器誤解了稽核報告，也可能使後續子任務規劃偏離正確方向。此外，對於需要大量連續上下文理解或細微互動技巧的任務，頻繁重置執行器上下文可能會削弱其對任務整體脈絡的掌握，進而影響執行品質。

**Q15：未來研究方向有哪些？**
A：未來可以進一步研究如何自動生成更精確且可驗證的子任務驗收標準，並根據任務難度與環境回饋動態調整子任務粒度。另一個方向是讓系統從稽核失敗中學習，例如自動修正常見的執行錯誤或改進管理器的狀態更新策略。此外，降低 MEA 迴圈的延遲與成本、擴展至多智慧體協作場景，以及在不同領域進行更細緻的消融實驗與泛化性分析，也都是值得深入探索的課題。

## 實務應用指南

### 適用場景

1. **跨系統自動化流程（RPA 升級）**  
   例如財務月結：智慧體需登入 ERP、下載報表、開啟 Excel 核對、產出摘要並寄送郵件。LongHorizon-Harness 的 MEA 迴圈可把「下載完成」「欄位一致」「郵件已寄」等事實寫入任務狀態，避免中間步驟的幻覺導致後續動作建立在錯誤前提上。

2. **軟體開發與維運（DevOps / SRE）**  
   長時間的除錯或部署流程，例如「調查生產環境異常 → 查日誌 → 下載追蹤檔 → 修改設定 → 驗證服務恢復」。執行器每次在全新上下文中處理單一子任務，稽核器再獨立檢查環境變化，適合需要高可靠性的維運場景。

3. **科學實驗與資料分析管線**  
   多步驟實驗如「下載資料集 → 清洗 → 訓練模型 → 評估 → 產生報告」。管理器依據經稽核的任務狀態決定下一步，確保實驗軌跡可被追蹤與重現，減少因上下文退化而遺漏關鍵參數。

4. **桌面與作業系統自動化**  
   例如協助使用者完成簡報製作：開啟簡報軟體、搜尋圖片、插入圖表、調整排版、匯出 PDF。唯讀稽核器可檢查畫面或檔案系統狀態，確認每一步確實完成後才更新任務狀態。

5. **客服與業務流程代理**  
   處理需要多輪確認的複雜申訴或訂單修改：先確認客戶身分、查詢訂單、執行退款或換貨、寄送確認信。任務狀態與執行上下文分離，可讓不同模型後端輪流擔任管理器、執行器或稽核器。

### 實作前置條件

- **資料準備**  
  - 明確的任務目標與可驗收的完成條件。  
  - 環境可觀測的狀態來源：螢幕截圖、CLI 輸出、API 回傳值、檔案系統狀態、資料庫查詢結果等。  
  - 每個子任務的輸入、輸出與邊界定義，便於管理器產生子任務合約。

- **運算資源**  
  - 可呼叫的模型後端（如 Qwen 3.7-Plus、Claude Opus 4.7、GPT 系列），建議管理器與稽核器使用較強模型，執行器可依成本彈性選擇。  
  - 執行環境需支援沙箱化或容器化，確保每輪執行器可在乾淨上下文中運作，且不影響主環境。  
  - 足夠的呼叫預算：長程任務會經歷多輪 MEA，需評估 token 與 API 成本。

- **技能與團隊配置**  
  - 熟悉提示工程與智慧體工具框架（如 Claude Code、Codex CLI、OpenClaw）的工程師。  
  - 具備環境自動化經驗（CLI/GUI 自動化、API 整合、容器管理）。  
  - 至少一名成員負責設計稽核邏輯與任務狀態結構，確保狀態更新只來自獨立驗證的事實。

---

### 實作步驟建議

1. **拆解任務並定義任務狀態結構**  
   將長程任務拆成可獨立驗收的子任務，並設計任務狀態格式（例如 JSON/YAML），記錄「已完成動作」「待滿足需求」「已發現環境事實」「產出物清單」。

2. **設計子任務合約（Subtask Contract）**  
   管理器每輪輸出一份合約，包含子目標、驗收條件、邊界限制與相關先前任務狀態證據，讓執行器只需專注於單一任務。

3. **實作全新上下文執行器**  
   透過 AgentAdapter 掛接現有工具框架後端，確保每輪執行時只載入當前子任務合約與必要工具，執行結束後丟棄該輪互動歷史。

4. **建立唯讀稽核機制**  
   稽核器使用唯讀工具觀察環境，產出稽核報告：哪些條件已滿足、哪些未滿足、環境發生哪些變化。此報告是更新任務狀態的唯一依據。

5. **封閉 MEA 迴圈**  
   管理器讀取任務狀態 → 產生子任務合約 → 執行器執行 → 稽核器驗證 → 管理器依稽核結果更新任務狀態 → 進入下一輪，直到任務完成或需要使用者授權。

6. **整合現有後端與持續迭代**  
   利用 AgentAdapter 支援不同模型與工具框架後端，先在小型任務子集驗證，再逐步擴大到完整長程任務，並根據稽核失敗案例調整合約與驗收條件。

---

### 潛在風險與注意事項

- **稽核器本身也可能出錯**  
  若稽核器誤判環境狀態，錯誤仍會寫入任務狀態。建議對關鍵步驟設計多重稽核（例如同時檢查檔案存在與內容雜湊），並保留稽核日誌供人工複查。

- **子任務切分過細或過粗**  
  切分太細會增加回合數與成本；切分太粗則失去狀態管理的意義。應以「可獨立驗收」為原則，並在執行中動態調整粒度。

- **環境狀態不可觀測**  
  若某些完成條件無法透過唯讀工具驗證，則無法納入任務狀態。需預先補足觀測能力，例如增加 API 端點、日誌欄位或畫面截圖。

- **執行器在全新上下文中遺漏隱含脈絡**  
  雖然全新上下文可減少干擾，但也可能讓執行器忽略長期依賴。管理器應在合約中明確列出相關先前任務狀態與證據。

- **成本與延遲膨脹**  
  每輪 MEA 都涉及多次模型呼叫。建議設定預算上限、回合數上限，並在管理器中加入「詢問使用者」路徑，避免無謂探索。

---

### 與其他技術的整合建議

- **現有智慧體工具框架**  
  透過 AgentAdapter 掛接 Claude Code、Codex CLI、OpenClaw 或 Hermes Agent，保留其原生智慧體迴圈與工具生態，只需在外層加上 MEA 狀態管理。

- **可觀測性平台**  
  將任務狀態、稽核報告與每輪合約匯出至 OpenTelemetry、LangSmith 或自架追蹤系統，便於除錯、審計與持續改善。

- **知識庫與向量檢索**  
  對於需要參考大量文件的長程任務，可將任務狀態中的「已發現事實」同步寫入向量資料庫，供後續子任務檢索，但應以稽核後的事實為優先。

- **CI/CD 與自動化測試**  
  把 LongHorizon-Harness 嵌入 CI/CD 管線執行回歸測試或部署任務，並用稽核報告作為閘道條件，只有通過驗證才進入下一階段。

- **多模型策略（Model Routing）**  
  管理器與稽核器可配置較強模型以確保決策品質，執行器可依子任務難度動態選擇模型，透過 AgentAdapter 統一介面切換。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦於「管理-執行-稽核迴圈」的直覺：把長任務想像成一份不斷被核對的待辦清單，管理器決定下一步、執行器動手做、稽核器檢查結果，只有被確認過的事實才會寫回清單。理解這個流程後，再回頭看任務狀態與 AgentAdapter 的設計細節。

- **AI 工程師**  
  請重點閱讀方法章節與 AgentAdapter 的實作方式，評估如何將現有智慧體工具框架改寫為 MEA 架構。特別注意全新上下文執行器的狀態隔離、稽核器的唯讀約束，以及如何設計可驗收的子任務合約。

- **研究人員**  
  本文的核心貢獻在於將長程執行重新定義為「任務狀態管理問題」，並強調獨立驗證的事實才能更新狀態。建議關注其與現有規劃、反思、自我修正方法的差異，以及在不同基準測試（WeaveBench、OSWorld 2.0、Terminal-Bench 2.1）上的實證設計與限制。

- **產品經理**  
  本文提供了一個提升長任務完成率的系統性方案，適用於需要高可靠性的企業流程自動化。閱讀時請對照自身產品場景，評估哪些任務具備可觀測的環境狀態、是否值得投入多模型與多輪稽核的成本，以及 AgentAdapter 如何降低與現有後端整合的門檻。
