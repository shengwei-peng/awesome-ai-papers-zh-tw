## 摘要翻譯

大語言模型代理（LLM agents）經常在多輪互動（multi-turn interactions）中運作，其中使用者的意圖在執行前會發生變化。我們研究意圖漂移（intent drift）：即使用者意圖中被取代的部分（superseded parts）持續影響最終答案（final answer）或工具動作（tool action）的失敗模式。我們提出 IntentFlux，這是一個可執行基準測試（executable benchmark），可將可驗證的任務轉換為具有受控意圖變化的對話，同時保留其原始評分器（grader）。在 627 個案例的校準（calibration）中，當對話包含更多被取代（superseded）和已撤銷（withdrawn）的資訊時，平均任務分數（mean task score）從 0.476 下降至 0.384。在八個模型中，當相同的最終任務必須從演進式對話（evolving dialogue）中恢復，而非在單輪（single-turn）中直接給定時，完全正確解決方案的比率顯著較低。我們進一步提出 StateForge，它在生成前明確維護活躍需求（active requirements）。在 General-Test 上，它將平均任務分數從 0.367 提升至 0.467。提供真實最終狀態（ground-truth final state）可進一步提升效能，但仍無法恢復單輪效能，這表明狀態估計（state estimation）誤差僅能解釋部分差距。這些結果確立了意圖漂移作為一種可量測的多輪失敗模式（multi-turn failure mode），以及明確的狀態維護（state maintenance）作為部分緩解方法。

### 核心貢獻（3～5點）
- **定義並量化意圖漂移問題**：系統性地提出「意圖漂移」作為大語言模型代理在多輪互動中可量測的失敗模式，即被取代的意圖持續影響最終答案或工具動作。
- **建構 IntentFlux 可執行基準測試**：將可驗證任務轉換為具受控意圖變化的對話，並保留原始評分器；在 627 案例校準中證實對話中過時資訊越多，平均任務分數顯著下降（0.476 → 0.384）。
- **跨模型實驗驗證多輪效能落差**：在八個模型上證實，從演進式對話中恢復最終任務的完全正確率，顯著低於單輪直接給定任務的表現。
- **提出 StateForge 緩解方法**：透過在生成前明確維護活躍需求，在 General-Test 上將平均任務分數從 0.367 提升至 0.467，證實顯式狀態維護能部分緩解意圖漂移。
- **剖析剩餘效能差距的成因**：即使提供真實最終狀態，仍無法完全恢復單輪效能，顯示狀態估計誤差僅能解釋部分差距，揭示未來研究方向。

### 適合對象
- 研究大語言模型代理可靠性與多輪對話系統的學者與工程師
- 從事 AI 代理框架（如 Deep Agents、OpenHarness）設計與評估的研究人員
- 關注工具增強型語言模型（tool-augmented LLM）實際部署中錯誤累積問題的業界實務者
- 對基準測試設計、可執行評測方法論感興趣的 NLP 研究者
- 需要理解使用者意圖動態變化下系統行為的對話式 AI 產品設計者

## 深度分析

#### 方法論解析

本論文提出兩個互補的核心組件：**IntentFlux 基準測試**與 **StateForge 狀態維護框架**，用以系統性地測量並修復大語言模型代理（LLM agents）在多輪互動（multi-turn interactions）中的意圖漂移（intent drift）問題。

**IntentFlux 的建構邏輯**

IntentFlux 的設計哲學在於「保留來源驗證器（source verifier）但改變對話結構」。其運作流程為：將可執行的來源任務（source task）轉換為受控的多輪對話，其中使用者意圖透過三種原子操作進行演進：

- **ADD(g)**：將新目標 $g$ 加入意圖狀態 $G_t$，形成 $G_{t+1} = G_t \cup \{g\}$
- **DELETE(g)**：從狀態中移除目標 $g$，形成 $G_{t+1} = G_t \setminus \{g\}$
- **REPLACE(g, g')**：以新目標 $g'$ 取代舊目標 $g$，形成 $G_{t+1} = (G_t \setminus \{g\}) \cup \{g'\}$

此設計的關鍵在於：編輯序列 $E = (e_1, \ldots, e_K)$ 由預先定義的 oracle 套用，最終產生已知的活躍意圖 $G^\star$，而來源任務評分器（source-task grader）則用以評估代理輸出。這種「已知最終意圖 + 可控編輯歷史」的雙重特性，使研究者能夠精確測量過時資訊（stale information）對最終輸出的影響程度。

**過時資訊的兩種注入機制**

IntentFlux 透過兩種方式刻意引入過時資訊：

1. **變體（Variant）**：指某個活躍意圖項目的「合理替代值」，在後續對話中被目標值所取代。例如使用者先提及「用 Python 實作」，後改為「用 JavaScript 實作」。變體的存在使得模型若未正確追蹤編輯，可能輸出基於 Python 的錯誤解答。

2. **誘餌（Decoy）**：指使用者後續撤銷的合理約束條件。IntentFlux 僅保留那些「若被遵守會改變來源任務評分器判定結果」的誘餌，這個篩選條件至關重要——它確保誘餌的影響是可測量的，而非無害的雜訊。

**StateForge 的架構設計**

StateForge 採用「狀態維護與任務求解分離」的模組化設計。其核心思想是：在生成最終答案之前，先由一個模型驅動的追蹤器（tracker）將已取代的意圖項目及其衍生的結論從對話歷史中移除，僅將活躍狀態（active state）提供給基礎代理（base agent）。

此架構的關鍵優勢在於：
- **可解釋性**：活躍需求（active requirements）以結構化形式呈現，便於除錯與審計
- **可替換性**：追蹤器可獨立升級或蒸餾（distillation），無需重新訓練整個代理
- **錯誤分解**：可區分「狀態估計錯誤」與「基於正確狀態的推理錯誤」

**兩條互補的部署路徑**

論文進一步提出兩種將 StateForge 行為內化（internalize）至代理的策略：

1. **模組化路徑**：維持外部追蹤器，使用**在策略蒸餾（On-Policy Distillation, OPD）**訓練小型追蹤器。具體而言，9B 參數的追蹤器在統計上與 122B 參數的參考模型無顯著差異，而 2B 追蹤器可透過 OPD 從 0.266 提升至 0.445 的表現。

2. **內化路徑**：透過**思考蒸餾（thinking distillation）**將狀態折疊（state-folding）行為直接融入 35B 的獨立代理，使其 General-Test 分數從 0.296 提升至 0.461，無需外部框架即可運作。

#### 實驗數據解讀

**校準階段的意圖漂移量化**

在 627 個來源任務的校準集（calibration pool）上，平均任務分數（mean task score）從簡易條件（easy condition）的 **0.476** 下降至困難條件（hard condition）的 **0.384**，相對降幅達 **19.3%**。這個數字揭示了一個重要現象：即使對話結構本身合理，僅僅因為意圖的演進就會造成顯著的效能損失。

**跨模型的一致性驗證**

為排除校準模型的特殊性，論文評估了八個近期的大語言模型。結果顯示：在每個難度等級下，演進式對話條件的表現都低於單輪條件。這種跨模型的一致性表明，意圖漂移是**結構性的多輪失敗模式（multi-turn failure mode）**，而非特定模型的弱點。

**長度匹配對照組的關鍵證據**

長度匹配對照組（length-matched control）的設計極具說服力：它在不引入意圖修訂的情況下，僅增加對話長度，得到的分數為 **0.734**，接近單輪條件的 **0.778**，且遠高於對應的漂移分數 **0.469**。這個對照實驗排除了「多輪本身導致效能下降」的簡單解釋，證實效能損失確實源自**意圖的演進**，而非對話長度的增加。

**即時工具使用環境的延伸驗證**

在即時工具使用環境（live tool-use environment）中，與乾淨條件（clean condition）相比，隱藏最終意圖的明確重述會使部分給分分數（partial-credit score）下降 **0.103**。這個結果將意圖漂移效應從靜態最終答案任務擴展至動態工具呼叫場景，顯示其普遍性。

**外部框架的局限性**

兩種歷史管理框架的表現令人警覺：
- **Deep Agents**（滾動式摘要，rolling summarization）：General-Test 分數為 **0.354**
- **OpenHarness**（兩階段壓縮，two-phase compaction）：General-Test 分數為 **0.392**
- **裸模型（bare model）多輪執行**：**0.367**

這三個數字形成一個關鍵發現：**單純的對話壓縮無法可靠恢復損失的效能**。即使歷史被壓縮，生成器仍需判斷哪些保留資訊仍然有效——這正是 StateForge 要解決的核心問題。

**StateForge 的效能分解**

StateForge 將 General-Test 分數從 **0.367** 提升至 **0.467**，相對改善約 **27.2%**。更精細的分解實驗揭示：
- **估計狀態**：0.467（StateForge 預測的活躍狀態）
- **真實最終狀態（ground-truth final state）**：**0.549**
- **單輪乾淨條件**：**0.778**

這個三元組極具診斷價值：從 0.467 到 0.549 的差距代表**狀態估計錯誤（state estimation errors）**造成的損失；從 0.549 到 0.778 的差距則代表**即使給定完美狀態，在保留對話歷史下仍存在的殘餘錯誤**。這意味著狀態估計只是問題的一部分，代理在接收到正確狀態後仍會受到對話歷史的某種干擾。

**小型追蹤器的可行性**

9B 追蹤器與 122B 參考模型在統計上無顯著差異，這為部署成本提供了重要洞見：狀態維護任務可以用相對小的模型勝任。透過 OPD，2B 追蹤器從 0.266 提升至 0.445，雖然仍低於 9B 版本，但證明了**知識蒸餾在狀態維護任務上的有效性**。

#### 與現有研究的比較

**與分片指令設定（Sharded-instruction settings）的關係**

Laban 等人（2025）的研究顯示模型在任務資訊逐步揭露時會「迷失」。IntentFlux 與此設定的關鍵區別在於：分片指令設定僅測量資訊遺失，而 IntentFlux 透過**已知的最終意圖**與**可控的編輯歷史**，能夠區分「遺失」與「使用過時資訊」這兩種不同的失敗模式。這是一個重要的細粒度區分，因為兩者需要不同的修復策略。

**與演進式意圖評估（Evolving-intent evaluations）的關係**

Tack 等人（2026）將可驗證任務轉換為揭示/修訂/切換互動，Jia 等人（2026）的 EvolIF 透過主題約束的增刪改來演進意圖，Zou 等人（2026）的 InterruptBench 研究長期網頁導航中的修訂與撤回。這些設定測量代理是否最終遵循演進中的任務，但**無法區分過時意圖持續影響答案所導致的失敗與其他多輪錯誤**。IntentFlux 透過變體與誘餌的設計填補了這個測量缺口。

**與長期記憶研究的關係**

Uddin 等人（2026）懲罰使用失效記憶的行為，Patel（2026）訓練代理偏好當前值而非被取代值。IntentFlux 與這些工作的互補性在於：它專注於**開放式任務需求及其依賴關係**，並在可執行設定中運作，而非僅處理簡單的鍵值記憶。

**與長上下文方法的關係**

Liu 等人（2023）、Jiang 等人（2023）、Lee 等人（2024）、Zhang 等人（2025）等長上下文方法透過壓縮或檢索來管理增長的歷史。然而，這些方法**未必明確解析哪些先前意圖仍然活躍**。StateForge 的創新在於：在生成答案之前，先將編輯歷史折疊為活躍需求狀態，這是一種「語意級」的歷史管理，而非單純的「token 級」壓縮。

**與信念追蹤的關係**

Kim 與 Schuster（2023）、Zhu 等人（2024）的實體與信念追蹤工作與 StateForge 在精神上相似，但 StateForge 運作於**開放式任務需求及其依賴關係**，且在可執行設定中驗證，這擴展了傳統信念追蹤的範疇。

**與學習中間推理的研究的關係**

Hsieh 等人（2023）、Mukherjee 等人（2023）、Guan 等人（2024）的推理蒸餾工作，以及 Agarwal 等人（2023）的在策略蒸餾（OPD），為 StateForge 的兩條部署路徑提供了方法論基礎。IntentFlux 的貢獻在於將這些通用技術**適配至可執行的過時意圖失敗場景**，並以此監督狀態維護行為。

**StateForge 的局限性**

儘管 StateForge 帶來顯著改善，但以下局限性值得注意：
1. **模組化路徑的系統複雜度**：需要維護獨立的追蹤器，增加部署與除錯成本
2. **殘餘錯誤的存在**：即使給定真實最終狀態，0.549 仍低於單輪的 0.778，顯示對話歷史本身對代理有某種干擾效應
3. **內化路徑的規模需求**：35B 代理才能達到接近模組化版本的表現，對資源受限的部署場景構成挑戰

#### 可重現性評估

**基準測試的可重現性要素**

IntentFlux 的設計本身有利於重現：
- **來源任務的可驗證性**：每個任務都附帶原始評分器，確保評估標準的客觀性
- **編輯序列的確定性**：給定初始意圖 $G_0$ 與編輯序列 $E$，最終意圖 $G^\star$ 由 oracle 唯一確定
- **變體與誘餌的篩選標準明確**：誘餌僅在「遵守會改變評分器判定」時保留，這個標準可程式化驗證

**實驗設計的可重現性**

論文的實驗設計包含多項可重現的對照：
- **長度匹配對照組**：排除對話長度的混淆效應
- **跨模型評估**：八個模型的結果提供穩定性證據
- **乾淨條件基準**：單輪條件作為效能上限的參考點
- **真實最終狀態注入實驗**：分離狀態估計錯誤與推理錯誤

**潛在的可重現性挑戰**

然而，以下因素可能影響完全重現：
1. **模型版本敏感性**：八個模型的具體版本與檢查點未在提供的文本中明確列出，不同時間點的模型快照可能產生不同結果
2. **評分器的執行環境**：來源任務評分器可能在特定環境（如特定版本的 Python 直譯器、函式庫）下產生不同判定
3. **對話生成的隨機性**：若對話生成涉及隨機採樣（如溫度參數），則相同來源任務可能產生不同的對話實例
4. **StateForge 追蹤器的訓練資料**：OPD 訓練所需的具體資料組成與訓練超參數需要詳細記錄

**開放性建議**

基於論文的貢獻性質，建議作者公開：
- IntentFlux 的完整基準資料集（含所有來源任務、編輯序列、變體、誘餌）
- StateForge 的參考實作與訓練程式碼
- 評估管線（含評分器執行環境配置）
- 預訓練的追蹤器權重（9B 與 2B 版本）
- 內化路徑的 35B 代理權重

這些資源的釋出將使社群能夠驗證論文結論、進行消融實驗，並將 IntentFlux 與 StateForge 應用於新的場景。

#### 未來研究方向

**1. 殘餘錯誤的根因分析**

從 0.549（真實最終狀態）到 0.778（單輪）的差距代表一個尚未解釋的現象：即使代理接收到完美的活躍狀態，保留的對話歷史仍會干擾其表現。這個殘餘錯誤的根因值得深入探究，可能涉及：
- 對話歷史中的語言模式對模型的隱式偏置
- 代理在生成過程中「回憶」過時資訊的機制
- 注意力機制對歷史位置的偏好

未來工作可透過控制歷史內容的實驗（例如僅保留最終狀態、完全清空歷史）來分離這些效應。

**2. 跨領域的 IntentFlux 擴展**

當前的 IntentFlux 主要基於可執行的程式碼或邏輯任務。未來可擴展至：
- **開放式對話任務**：如創意寫作、諮詢對話，其中「正確答案」的定義更為模糊
- **多模態場景**：結合視覺、語音的意圖演進
- **長期任務**：跨越多個對話 session 的意圖漂移

**3. 狀態維護的理論基礎**

目前 StateForge 的設計主要基於經驗觀察。理論層面的問題包括：
- 狀態維護任務的計算複雜度上界為何？
- 追蹤器所需的最小模型容量與任務難度的關係？
- 是否存在「狀態維護不可學習」的任務類型？

**4. 與規劃與推理的整合**

StateForge 將狀態維護與任務求解分離，但兩者可能存在更深的耦合。未來可探索：
- 聯合訓練狀態追蹤器與任務求解器
- 將狀態折疊行為融入代理的規劃過程
- 開發能夠「自我追蹤」活躍需求的代理架構

**5. 評估方法的標準化**

IntentFlux 提供了測量意圖漂移的標準化方法，但仍有改進空間：
- 開發更細粒度的失敗分類（如「部分使用過時資訊」vs「完全忽略新資訊」）
- 設計人類評估協議以驗證自動化評分的有效性
- 建立跨基準的意圖漂移測量標準

**6. 安全性與隱私考量**

意圖漂移不僅是效能問題，也涉及安全性：
- 攻擊者可能刻意注入誘餌以操縱代理行為
- 過時資訊可能洩漏敏感的使用者資料
- 狀態維護機制本身可能成為攻擊面

未來工作應探討 IntentFlux 與 StateForge 在對抗性設定下的穩健性。

**7. 與人類認知的對齊**

人類在使用過程中經常改變主意，且能靈活追蹤「哪些資訊仍然有效」。未來可借鑑人類認知科學的研究（如工作記憶理論、情境模型），設計更符合人類直覺的狀態維護機制，並透過使用者研究驗證 StateForge 類代理在實際互動中的表現。

**8. 工業部署的實務考量**

從研究到部署的轉化需要解決：
- 追蹤器的延遲成本對即時互動的影響
- 狀態維護失敗的監控與恢復機制
- 使用者對「代理記得我說過什麼」的期望管理

這些實務問題將決定 StateForge 類方法在真實產品中的可行性。

## 論文問答

**Q1：什麼是「意圖漂移」（intent drift），為什麼它是 LLM 代理的一個重要問題？**
A：意圖漂移指的是在使用者多輪互動過程中，原本已被取代或撤銷的意圖片段，仍然持續影響代理最終輸出的答案或工具動作的失敗模式。這個問題之所以重要，是因為真實世界的使用者往往不會一次性給出完整且最終的規格，而是會逐步揭露、修正、甚至撤回先前的需求。當代理無法正確辨識哪些需求仍然「活躍」時，它就可能依據過時資訊做出錯誤的行動，例如使用已被替換的參數值或遵守已被撤銷的約束條件。這種錯誤在涉及工具呼叫或可執行程式碼的場景中尤其危險，因為一個錯誤的參數可能導致不可逆的後果。

**Q2：現有的多輪評估方法為何無法有效捕捉意圖漂移問題？**
A：現有的分片指令設定（sharded-instruction settings）雖然能測試模型在資訊逐步揭露時是否會遺漏任務內容，但無法區分「遺漏」與「使用了過時資訊」這兩種本質不同的失敗模式。較新的演進式意圖評估雖然加入了參數揭示、修訂與任務切換等元素，但它們通常只測量代理最終是否遵循了演進後的任務，而無法隔離出「被取代意圖持續影響答案」這個特定失敗機制。要直接研究此問題，必須具備已知的最終意圖，以及其錯誤使用會改變任務結果的過時資訊——這正是 IntentFlux 試圖填補的研究缺口。

**Q3：為什麼在意圖漂移成為可測量的失敗模式後，學術界與產業界都應該重視這個問題？**
A：從學術角度來看，意圖漂移代表了一種先前未被充分形式化的多輪失敗類型，建立可量化的基準能讓後續研究有共同的比較基礎。從產業角度來看，任何部署 LLM 代理於真實使用者互動的系統——例如客服機器人、程式助理或自動化工作流程——都必然會面臨使用者中途改變心意的情境。若代理無法正確處理這些變更，不僅會降低使用者信任，更可能在關鍵任務中產生嚴重錯誤。因此，將意圖漂移從一個模糊的「對話失敗」轉化為可測量、可修復的工程問題，對於 LLM 代理的可靠部署至關重要。

**Q4：IntentFlux 這個基準測試的核心設計理念是什麼？它如何運作？**
A：IntentFlux 的核心設計理念是將可驗證的「來源任務」轉換為受控制的多輪對話，同時保留原始評分器以確保任務結果可被客觀判定。它透過引入「意圖狀態」的概念，將任務表示為一組原子化的自然語言目標，並透過 ADD、DELETE、REPLACE 三種編輯操作來模擬使用者意圖的演變。這種設計讓研究者能精確控制哪些資訊被引入、何時被取代或撤銷，從而將「過時意圖的影響」這個變因從其他多輪錯誤中隔離出來。此外，IntentFlux 透過「變體」（variant）與「誘餌」（decoy）兩種機制引入過時資訊，前者是後續被替換的替代值，後者則是後續被撤銷的約束條件，且誘餌僅在遵守它會改變評分結果時才被保留。

**Q5：StateForge 方法的核心創新是什麼？它如何解決意圖漂移問題？**
A：StateForge 的核心創新在於將「意圖狀態維護」與「下游任務求解」明確分離，由一個模型驅動的追蹤器在生成答案前先移除已被取代的意圖項目及其衍生的結論，再將「活躍狀態」提供給基礎代理。這種「先摺疊（fold）後生成」的設計哲學，與單純壓縮對話歷史的方法（如滾動摘要或兩階段壓縮）形成對比——後者只是縮減資訊量，但並未解決「哪些保留資訊仍然有效」的問題。StateForge 的關鍵洞見是：對話歷史的長度本身並非主要瓶頸，代理能否正確判斷每段資訊的活躍狀態才是，因此需要一個專門的模組來處理這個狀態估計任務。

**Q6：IntentFlux 在設計變體與誘餌時做了哪些關鍵選擇？這些選擇為何重要？**
A：IntentFlux 在設計變體時選擇使用「看似合理的替代值」，例如在程式任務中以另一種實作語言作為替代，這使得變體在語境中具有可信度，從而增加代理誤用它的機率。在誘餌的設計上，則採用了嚴格的篩選標準——只有當「遵守誘餌會改變來源任務評分器的判定結果」時，該誘餌才會被保留。這種設計避免了無效誘餌（即無論是否遵守都不影響結果）造成的假陽性問題，確保了基準測試的區辨力。這些選擇共同保證了 IntentFlux 能夠精確測量「過時資訊被錯誤使用」這個特定失敗模式，而非泛泛的多輪對話錯誤。

**Q7：本研究使用了哪些基準測試與資料集？主要的實驗結果為何？**
A：本研究使用了三個主要的評估設定：627 個來源任務組成的校準集、125 個任務的 General-Test 固定測試集，以及一個即時工具使用環境。在校準實驗中，平均任務分數從簡易條件的 0.476 下降到困難條件的 0.384，呈現 19.3% 的相對降幅。在跨模型評估中，八個近期 LLM 在演進式對話條件下的表現都顯著低於單輪直接給定任務的條件。值得注意的是，長度匹配對照組（無意圖修訂）得分為 0.734，接近單輪條件的 0.778，遠高於對應的漂移分數 0.469，證明了「額外的對話輪次」本身並非表現下降的原因。

**Q8：StateForge 與其他方法（如 Deep Agents、OpenHarness）的比較結果如何？**
A：在 General-Test 上，Deep Agents（使用滾動式摘要）得分為 0.354，OpenHarness（使用兩階段壓縮）得分為 0.392，而裸模型的多輪執行得分為 0.367——這顯示單純的對話壓縮並無法可靠地恢復因意圖漂移而損失的表現。相較之下，StateForge 將平均任務分數從 0.367 提升至 0.467，展現了明確的狀態維護機制的價值。更進一步地，若將估計的狀態替換為真實最終意圖（ground-truth final state），表現可進一步提升至 0.549，但仍低於單輪乾淨條件的 0.778，這說明狀態估計錯誤雖然是重要的因素，卻只能解釋部分剩餘的表現差距。

**Q9：本研究的消融實驗揭示了哪些關於狀態維護的洞見？**
A：消融實驗揭示了兩個重要的洞見。首先，狀態估計是狀態摺疊（state folding）中的實質組成部分——當提供真實最終狀態時，表現顯著提升，證明了狀態估計錯誤確實會影響最終結果。其次，即使給定完美的狀態資訊，表現仍無法完全恢復到單輪水準，這意味著除了狀態估計之外，殘留的對話歷史仍會對代理產生干擾。此外，研究還發現 9B 的追蹤器在統計上與 122B 的參考模型無顯著差異，透過 on-policy 蒸餾（OPD）可將 2B 追蹤器從 0.266 提升至 0.445，這顯示狀態維護任務可以有效地蒸餾到較小的模型中。

**Q10：在哪些實際應用場景中，意圖漂移問題會特別關鍵？**
A：意圖漂移問題在許多實際應用場景中都至關重要，尤其是在涉及多步驟、可執行操作的代理任務中。例如，在程式開發助理中，使用者可能先要求用 Python 實作，後來改為 JavaScript，若代理仍以 Python 撰寫就會產生錯誤；在資料分析代理中，使用者可能先指定某個欄位作為分組依據，後來改用另一個欄位，若代理未更新理解就會產生錯誤的彙總結果。在客服或銷售場景中，使用者可能先表達購買意願但後來撤回，若代理仍推薦相關產品就會造成困擾。在自動化工作流程中，參數的變更若未被正確追蹤，可能導致整個流程執行錯誤並產生不可逆的副作用。

**Q11：從產品部署的角度來看，本研究對 LLM 代理系統的設計有何啟示？**
A：本研究對產品設計的啟示可以從兩個互補的路徑來看。第一個是模組化路徑：使用較小的可訓練追蹤器來專門維護活躍狀態，再將其提供給基礎代理，這種設計在效能與成本之間取得了良好平衡——9B 追蹤器已能達到 122B 參考模型的水準。第二個是內化路徑：透過思維蒸餾（thinking distillation）將狀態摺疊行為直接內化到基礎代理中，使其成為獨立運作的單一模型，這對於資源受限或需要簡化架構的部署場景特別有用。產品設計者應根據延遲、成本與維護性的權衡，在這兩種路徑之間做出選擇，並意識到單純的對話壓縮並不足以解決意圖漂移問題。

**Q12：本研究對 LLM 代理研究領域的更廣泛影響是什麼？**
A：本研究對領域的更廣泛影響在於將「意圖漂移」從一個模糊的對話失敗現象，提升為一個可形式化、可測量、可修復的工程問題。透過 IntentFlux 基準測試，後續研究有了一個共同的評估平台，可以比較不同方法在處理演進式意圖時的表現。透過 StateForge 的「狀態維護與任務求解分離」設計理念，本研究為處理多輪對話中的狀態追蹤問題提供了一個新的範式。此外，研究中關於「狀態估計只能解釋部分表現差距」的發現，點出了未來需要進一步探索的方向——例如對話歷史中殘留資訊的干擾機制，以及如何讓代理更有效地忽略無關的歷史片段。

**Q13：本研究承認哪些限制？**
A：本研究承認幾項重要的限制。首先，即使提供真實最終狀態，表現仍無法完全恢復到單輪水準，這說明除了狀態估計之外，還有其他因素導致多輪表現低於單輪，例如對話歷史中殘留資訊的干擾或上下文視窗的稀釋效應。其次，IntentFlux 的設計雖然控制了意圖變更，但對話的自然性可能受限於受控制的編輯序列，未必能完全反映真實使用者行為的多樣性。此外，StateForge 的有效性依賴於追蹤器模型的品質，雖然 9B 模型已能達到 122B 的水準，但在更複雜的任務或更長的對話中，狀態估計的準確性可能會下降。

**Q14：在哪些情況下，現有方法（包括 StateForge）仍然會失敗？**
A：現有方法在幾種情況下仍可能失敗。第一，當意圖變更非常細微或隱含時（例如使用者說「也許換個方式做」但未明確指出要替換什麼），追蹤器可能無法正確識別需要被取代的項目。第二，當對話歷史非常長且包含大量相互依賴的意圖項目時，狀態估計的錯誤可能會累積並放大。第三，當使用者意圖本身存在內部矛盾或模糊性時，即使正確追蹤了所有變更，最終的活躍狀態仍可能無法被明確判定。最後，在涉及複雜工具呼叫鏈的場景中，某一輪的意圖變更可能影響後續多個步驟的參數，這種「漣漪效應」對狀態維護系統來說是特別具有挑戰性的情境。

**Q15：本研究指出了哪些未來研究方向？**
A：本研究指出了幾個值得探索的未來方向。首先是如何讓代理更有效地處理隱含或模糊的意圖變更，這可能需要結合更強的對話理解能力與不確定性推理。其次是探索對話歷史中殘留資訊干擾的機制——為何在給定完美狀態後表現仍低於單輪，這個問題的解答可能需要新的注意力機制或上下文處理架構。第三個方向是將狀態維護能力擴展到更複雜的任務類型，例如涉及多代理協作或長期記憶的場景。最後，如何在不使用外部追蹤器的情況下，讓基礎代理本身具備更強的「狀態摺疊」能力，仍是一個開放的問題，本研究中的思維蒸餾實驗只是這個方向的初步嘗試。

## 實務應用指南

### 適用場景

**1. 客戶服務與訂單管理代理**
在使用者反覆修改訂單規格的情境中（例如先訂購 A 款外套、後改為 B 款、接著要求加購配件、最後又撤回配件需求），傳統代理常因「意圖漂移」而送出錯誤的訂單組合。導入 IntentFlux 風格的對話設計與 StateForge 式的狀態維護機制，可讓代理在每一輪生成前回顧「活躍需求清單」，避免將已撤銷的配件或已被取代的款式混入最終訂單。

**2. 程式開發輔助代理（Cursor、Copilot Workspace 等）**
開發者常在多輪對話中改變需求：「先用 Python 寫，改成 TypeScript」「加入 JWT 驗證，但先不要做 rate limiting」「把資料庫從 PostgreSQL 換成 SQLite」。這些被取代的語言、函式庫、限制條件若殘留在代理的脈絡中，會導致最終程式碼混用舊規格。StateForge 的顯式狀態折疊（state-folding）行為可在生成程式碼前先過濾掉過時約束。

**3. 旅遊與行程規劃代理**
使用者常見的修訂模式：「先去東京，改成京都」「要商務艙，後來改經濟艙」「取消博物館行程」。若代理未追蹤哪些需求仍活躍，可能輸出包含已取消景點或舊艙等的行程單。IntentFlux 的「變體」與「誘餌」概念正好對應此類修訂與撤回。

**4. 企業內部流程自動化（IT、工單、HR 助理）**
員工提交工單時常會補充、修正或撤回先前描述的問題（例如「我的筆電無法開機」→「其實是螢幕壞了」→「抱歉，是投影機沒訊號」）。代理若未正確折疊狀態，可能會同時派遣多個無關技師或遺漏真正的問題。

**5. 資料分析與 BI 對話代理**
分析師在探索資料時會反覆調整查詢條件：「先看 2023 年資料，改成 2024 年」「排除北美地區，後來又加回來」「改用日活躍使用者而非月活躍」。意圖漂移會導致最終報表混入舊的時間區間或錯誤的指標定義。

### 實作前置條件

**資料準備**
- 一批具備「可驗證評分器」的來源任務（verifiable tasks），例如程式碼任務的單元測試、SQL 任務的執行結果比對、訂單任務的結構化輸出驗證。IntentFlux 的設計前提是「保留原始評分器」，因此每個任務都必須有可程式化判定的正確答案。
- 對話編輯腳本（edit scripts）：定義每個任務的初始意圖集 $G_0$、編輯序列 $E=(e_1,\dots,e_K)$ 與最終活躍意圖 $G^\star$。需要領域專家或 LLM 輔助生成「合理的變體值」與「合理的誘餌約束」，並以「服從誘餌是否會改變評分器結果」作為篩選條件。
- 長度匹配對照組（length-matched control）：相同輪數但不含意圖修訂的對話，用於分離「多輪本身」與「意圖漂移」造成的效能損失。

**運算資源**
- 基準評估：8 個近期 LLM 的多輪推理，每個任務約需數十至數百 token 的生成；627 個校準任務 × 多個難度等級 × 多個模型，整體評估建議至少數百 GPU-hours 等級的算力。
- StateForge 訓練：on-policy distillation（OPD）需要教師模型（122B 等級）為學生模型（2B–9B 等級）產生 rollouts；thinking distillation 則需在 35B 等級的代理上進行監督微調。建議配備 8×A100/H100 以上的訓練環境。
- 線上部署：tracker 模型可獨立部署為小型服務（單張消費級 GPU 即可運行 9B 等級模型），與基礎代理解耦。

**技能門檻**
- 熟悉多輪對話系統的設計模式（訊息歷史管理、上下文壓縮、檢索增強）。
- 具備 prompt engineering 與結構化輸出（JSON schema）能力，因為 StateForge 的 tracker 需要輸出明確的「活躍需求清單」。
- 對 verifiable task 評分管線（sandbox 執行、斷言比對）有實務經驗。
- 若要重現論文的 OPD 與 thinking distillation，則需熟悉 SFT/DPO/RLHF 流程與分散式訓練框架（DeepSpeed、FSDP、vLLM 等）。

### 實作步驟建議

**步驟 1：盤點現有代理的「意圖漂移」風險**
先以 IntentFlux 的精神自建小型診斷集：挑選 50–100 個真實業務任務，請領域專家為每個任務設計 2–3 輪的修訂腳本（含至少一個變體與一個誘餌），並保留原始評分器。在現有代理上跑這批任務，記錄「單輪分數」與「多輪分數」的差距，作為基準線。

**步驟 2：建立「活躍需求清單」的資料結構**
定義一個結構化物件（例如 JSON schema），欄位包含 `active_requirements`、`withdrawn_constraints`、`replaced_values`、`dependencies`。每個需求項目應有唯一 ID、原始措辭、來源輪次、目前狀態（active/superseded/withdrawn）。這是 StateForge 風格設計的核心抽象。

**步驟 3：實作 tracker 模組**
以一個獨立的 LLM（或小型專門模型）擔任 tracker，輸入為完整對話歷史，輸出為更新後的活躍需求清單。關鍵設計：
- 在每一輪使用者訊息後、代理生成前，先呼叫 tracker 更新狀態。
- tracker 的 prompt 應明確指示「移除已被取代的值」「移除已被撤回的約束」「保留仍活躍的需求」。
- 將 tracker 輸出作為系統提示的一部分注入基礎代理，而非取代對話歷史。

**步驟 4：以 OPD 蒸餾小型 tracker**
若大型 tracker（122B）成本過高，可採 on-policy distillation：讓學生模型（2B–9B）對自己的輸出產生 rollouts，由教師模型給予回饋，再以這些訊號微調學生。論文中 2B tracker 從 0.266 提升至 0.445 的結果顯示此路徑可行。

**步驟 5：評估並決定模組化 vs 內化路徑**
- **模組化路徑**：保留外部 tracker，優點是更新狀態邏輯時不需重訓基礎代理，且 9B tracker 與 122B 參考模型效能統計上無顯著差異。
- **內化路徑**：以 thinking distillation 把狀態折疊行為直接蒸餾進基礎代理（35B），論文中分數從 0.296 提升至 0.461，且無需外部框架。
- 建議先採模組化路徑快速驗證，再視成本與維運考量決定是否內化。

**步驟 6：建立持續監控**
部署後持續收集「最終狀態估計錯誤率」與「任務分數」指標。注意論文的發現：即使提供真實最終狀態，分數仍低於單輪（0.549 vs 0.778），代表狀態估計只是部分原因，其餘差距來自「保留對話歷史本身對生成的干擾」。

### 潛在風險與注意事項

**1. 過度折疊（over-folding）導致遺失有效資訊**
tracker 可能過度激進地刪除看似「被取代」的需求，但實際上使用者只是補充而非替換（例如「用 Python 寫」後接「也要 TypeScript 版本」是 ADD 而非 REPLACE）。緩解方式：在 tracker 的 prompt 中明確區分 ADD/DELETE/REPLACE 三種編輯類型，並要求 tracker 對每個動作附上信心分數，低信心時改為保留而非刪除。

**2. 誘餌（decoy）設計的領域依賴性**
論文的誘餌篩選條件是「服從誘餌會改變評分器結果」，這在可驗證任務中容易判定，但在開放式生成任務（如創意寫作、開放問答）中難以自動化。緩解方式：對開放式任務改採「人類標註 + LLM 評審」雙軌制，或限制 StateForge 僅用於有明確驗收標準的子任務。

**3. tracker 與基礎代理的版本漂移**
若基礎代理升級（例如從 GPT-4 換到 GPT-5），tracker 的 prompt 與蒸餾資料可能不再適用。緩解方式：將 tracker 與基礎代理視為耦合系統，建立聯合回歸測試；每次基礎代理變更後，重跑 IntentFlux 風格的診斷集。

**4. 對話歷史完全丟棄的副作用**
論文的「真實最終狀態注入」實驗顯示，即使狀態完美，仍有約 0.23 的分數差距（0.778 − 0.549），代表對話歷史本身仍會干擾生成。緩解方式：不要完全丟棄對話歷史，而是讓基礎代理在「活躍需求清單」與「原始對話」兩者間取捨；可在 prompt 中明確指示「以活躍需求清單為準，對話歷史僅供參考」。

**5. 壓縮不等於狀態折疊**
論文中 Deep Agents（滾動式摘要）與 OpenHarness（兩階段壓縮）在 General-Test 上僅得 0.354 與 0.392，甚至低於裸模型。代表單純壓縮對話歷史無法解決意圖漂移。緩解方式：避免將「壓縮框架」誤用為「狀態維護」；兩者應分層設計，壓縮負責控制 token 成本，狀態折疊負責語意正確性。

**6. 評估管線的偽陽性**
若評分器只看最終輸出，可能誤判「代理其實理解了正確意圖但表達方式不同」的情況。緩解方式：採用 partial-credit scoring（部分給分），並對最終輸出做語意相似度比對，而非嚴格的字串匹配。

### 與其他技術的整合建議

**1. 與長上下文管理技術整合**
StateForge 不取代長上下文方法，而是互補：長上下文方法（壓縮、檢索、滑動窗口）負責控制 token 成本與注意力分散，StateForge 負責語意層級的「哪些資訊仍有效」。建議架構為：對話歷史 → 長上下文壓縮 → tracker 折疊 → 活躍需求清單 + 壓縮後歷史 → 基礎代理。

**2. 與 RAG（檢索增強生成）整合**
在使用者反覆修改需求的情境中，RAG 檢索到的舊文件可能與當前需求衝突。建議在 RAG 檢索後、生成前插入 tracker 步驟：tracker 根據活躍需求清單對檢索結果做「時效性過濾」，標記或移除已被取代的條目。

**3. 與 function calling / tool use 整合**
工具呼叫的參數最容易受意圖漂移影響（例如使用者改了日期但代理仍用舊日期呼叫 API）。建議在每次 tool call 前，由 tracker 輸出的活躍需求清單作為參數解析的「權威來源」，而非直接從對話歷史抽取。

**4. 與 RLHF / DPO 對齊流程整合**
若基礎代理經過 RLHF 對齊，tracker 也應納入對齊範圍：訓練資料應包含「錯誤折疊」的負樣本（例如刪除仍活躍的需求、保留已撤回的約束），讓 tracker 學會正確的折疊行為。

**5. 與多代理架構整合**
在多代理系統中（例如 planner-executor-critic），可將 tracker 設計為獨立的前置代理，所有下游代理共享同一份活躍需求清單，避免每個代理各自解讀對話歷史而產生不一致。

**6. 與日誌與可觀測性系統整合**
tracker 的每一次狀態更新都應寫入結構化日誌（包含被刪除的需求、刪除原因、信心分數），便於事後審計與除錯。這在企業合規場景（例如金融、醫療）中尤其重要。

### 給不同背景讀者的閱讀建議

**給初學者**
這篇論文的核心訊息其實很直觀：當使用者反覆改變心意時，AI 代理容易「記得太多舊東西」而做錯事。建議先讀摘要與第 1 節的動機段落，理解「意圖漂移」這個失敗模式在日常對話中其實隨處可見（例如你自己跟 Siri 或客服聊天時也遇過）。然後跳到第 3 節看 IntentFlux 如何把這個現象變成可量化的實驗，最後讀第 1 節後半段的 StateForge 介紹，理解「在生成前先整理一份活躍需求清單」這個簡單但有效的解法。數學公式與蒸餾細節可以先略過，掌握概念即可。

**給 AI 工程師**
重點放在第 3 節的「演進意圖狀態」形式化（ADD/DELETE/REPLACE 三種編輯）與第 4 節的 StateForge 架構。工程師最關心的應該是：tracker 模組如何與現有代理管線整合、prompt 怎麼寫、活躍需求清單的資料結構如何設計。論文中 9B tracker 與 122B 參考模型效能相當的結論，對於成本敏感的產品是重要訊號——你不需要部署超大模型就能拿到狀態維護的好處。建議直接動手實作一個最小可行版本：先在內部代理上加一個 tracker 步驟，用 50 個真實任務驗證，再決定是否投入 OPD 蒸餾。

**給研究者**
論文的價值在於把一個常被忽略的失敗模式（意圖漂移）從「感覺上存在」變成「可測量、可隔離、可部分修復」。第 4 節的「真實最終狀態注入」實驗（0.549 vs 0.778）是特別值得深思的發現：即使狀態估計完美，仍有顯著差距，這暗示對話歷史本身對生成有某種「殘留干擾」，是未來工作的開放問題。建議關注三個延伸方向：(1) 如何形式化定義「殘留干擾」並設計針對性實驗；(2) thinking distillation 為何能內化狀態折疊行為，其機制是什麼；(3) IntentFlux 的「誘餌篩選條件」能否推廣到開放式任務。論文的相關工作段落（第 2 節）也提供了豐富的延伸閱讀線索。

**給產品經理**
這篇論文回答了一個產品上常被低估的問題：「為什麼我們的 AI 代理在 demo 時表現很好，實際使用者用起來卻常常出錯？」答案是：demo 通常是單輪乾淨對話，實際使用者會反覆修改、撤回、補充需求，而代理沒有設計來處理這種「演進中的意圖」。產品上的意涵是：(1) 不要只看單輪 benchmark 評估供應商，必須要求多輪、含修訂的評估；(2) 若代理支援多輪任務，應明確詢問供應商「如何處理使用者中途改變心意」；(3) StateForge 式的顯式狀態維護是值得投資的能力，即使只能修復部分差距（從 0.367 到 0.467），對使用者體驗也是顯著提升。建議把 IntentFlux 風格的診斷集列為代理採購的標準評估項目之一。
