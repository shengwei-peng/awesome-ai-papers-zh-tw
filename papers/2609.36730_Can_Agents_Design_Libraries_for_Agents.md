# 智慧體能為其他智慧體設計函式庫嗎？

**原文標題：** Can Agents Design Libraries for Agents?

**發布日期：** 2026-09-29

## ⚡ TL;DR

智慧體常重複實作而非重複使用程式碼，且缺乏評估其函式庫對下游智慧體可用性的方法。
本文提出兩階段基準，讓智慧體依開放規格設計函式庫，再由下游智慧體使用，並以正確性與簡潔性評分。
十一項任務中智慧體重現生產級抽象，下游卻常因介面僵化重複實作；以智慧體為優先指引提升分數與簡潔性。

## 摘要翻譯

智慧體（agent）越來越常在其他智慧體撰寫的程式碼之上進行開發，卻傾向重新實作（reimplement）而非重複使用（reuse），使後續智慧體必須處理的程式碼庫（codebase）不斷膨脹。為了衡量智慧體為其他智慧體設計函式庫（library）的能力，我們提出函式庫設計基準測試（LibraryDesignBench），這是一個兩階段基準測試（two-phase benchmark）：智慧體根據一份定義必要能力（required capabilities）與潛在使用案例（potential use cases）、但不預先規定設計的非規範性規格書（non-prescriptive specification），實作全功能函式庫（full-featured library）。我們透過三個來自不同模型家族（model families）的使用者智慧體（user agents）所撰寫程式的正確性（correctness）與簡潔性（simplicity）來評估該函式庫。此基準測試涵蓋四種語言中 15 個函式庫設計任務（library-design tasks）的 242 道專家驗證的程式設計問題（expert-validated programming problems）。在 15 個任務中有 11 個，作為設計者的智慧體重現了人類撰寫的生產級函式庫（human-written production library）的抽象層。下游智慧體（downstream agents）同樣會採用（adopt）智慧體與人類撰寫的函式庫，但卻未充分利用（underuse）這些函式庫，反而重新實作函式庫已提供的能力。我們的失敗分析發現，下游智慧體撰寫額外程式碼，主要是因為智慧體撰寫的函式庫過於僵化（rigid）或難以使用（hard to use），而非因為缺少的能力（missing capabilities）。我們也嘗試給予設計者更多規範式指引（prescriptive guidance）且以智慧體為優先的指引（agent-first guidance），並讓他們使用子智慧體（subagents）測試自己的函式庫；這提升了下游分數，並產生更簡潔的程式。函式庫設計基準測試提供了一個測試平台（testbed），用於評估面向使用者智慧體的函式庫設計實務，並提供可改善下游重複使用（downstream reuse）的初始設計基線（design baseline）。

### 核心貢獻（3～5點）
- 提出 LibraryDesignBench，一個兩階段基準測試，用於評估智慧體為其他智慧體設計函式庫的能力。
- 建構大規模評估資源：涵蓋四種語言、15 個函式庫設計任務、242 道專家驗證的下游程式設計問題，並使用三個不同模型家族的使用者智慧體進行評測。
- 發現在 15 個任務中有 11 個，智慧體設計者能重現人類生產級函式庫的抽象層；但下游智慧體雖會採用這些函式庫，卻經常未充分利用，反而重新實作已提供的功能。
- 透過失敗分析指出，下游智慧體撰寫額外程式碼的主因是函式庫過於僵化或難以使用，而非缺少必要能力。
- 驗證給予設計者更規範式且以智慧體為優先的指引，並以子智慧體測試函式庫，可提升下游分數與程式簡潔性，為後續研究提供初始設計基線。

### 適合對象
本論文適合對人工智慧智慧體、自動化軟體工程、函式庫與 API 設計，以及多智慧體協作程式碼生態系感興趣的研究人員與工程師；特別是關注如何讓智慧體產出更易被其他智慧體重複使用、維護與擴展之高品質程式碼的讀者。

## 深度分析

#### 方法論解析

**兩階段評估架構**

LibraryDesignBench（函式庫設計基準測試）採用兩階段基準測試（two-phase benchmark），分為 Design Phase（設計階段）與 Evaluation Phase（評估階段）。在 Design Phase 中，受評估的智慧體（agent under evaluation）πθ 根據一份非規範性規格書（non-prescriptive specification）I 實作全功能函式庫（full-featured library）L；這份規格書僅列出 required capabilities（必要能力）與 potential use cases（潛在使用案例），卻不預先指定 interfaces and abstractions（介面與抽象層）。在 Evaluation Phase 中，來自不同 model families（模型家族）的能力較弱使用者智慧體（less capable user agents）πu 使用 L 解決 downstream programming problems（下游程式設計問題）。最終分數取決於 downstream programs（下游程式）的 correctness（正確性）與 simplicity（簡潔性）。這種「以真實使用觀察來評估」的方法論，是本文與僅用 correctness tests（正確性測試）或 static metrics（靜態指標）評分的核心區別。

**任務與規格書設計**

整個 benchmark 包含 15 個 library-design tasks（函式庫設計任務），涵蓋四種程式語言，並對應 242 道 expert-validated programming problems（專家驗證的程式設計問題）。每個任務都對照一個真實的 production library（生產級函式庫），例如 Rust 的 CLI（命令列介面）任務對照 clap crate。規格書會提供 2–3 個 visible problems（可見問題）作為使用範例，這些範例同時保留在計分題目中，類似於可見測試案例。設計智慧體還必須使用語言專屬 package manager（套件管理員）打包函式庫，確保下游智慧體能夠安裝與引用。這種設計強迫設計者從使用情境出發，而非僅滿足單元測試。

**評分指標：正確性與簡潔性**

Correctness 以 tests passed（通過測試數）相對於 reference tests（參考測試）的比例衡量。Simplicity 則透過四項靜態指標的 capped reference-to-program ratios（封頂參考程式比率）平均而得，包括 LOC（程式碼行數）、Cyclomatic complexity（循環複雜度）、Cognitive complexity（認知複雜度）與 Halstead complexity（Halstead 複雜度）。ratio 以 reference solutions（參考解決方案）相對於 downstream programs 的數值計算，並封頂於 1，避免過度壓縮可讀性。最終 library score（函式庫分數）綜合所有下游問題與 implementer（實作者）表現，反映該函式庫在真實使用中的價值。

**對照實驗：LibraryUseBench（函式庫使用基準測試）**

為了分離「函式庫設計」與「函式庫使用」兩種效應，作者將 L 固定為 production library，並評估 8 個模型作為 implementers，稱為 LibraryUseBench。結果顯示，即使使用 human-written production library（人類撰寫的生產級函式庫），下游智慧體的 simplicity 也僅達 61.5，最佳模型 Opus 5.5 為 66.9。這說明最終分數不僅取決於函式庫設計，也受限於下游智慧體能否善用函式庫。

**介入策略：以智慧體為優先的設計指引**

作者進一步測試更 prescriptive guidance（規範式指引）的變體：讓設計智慧體先 sketch consumer programs（草擬使用者程式）、提供 runnable usage examples（可執行使用範例），並以 subagents（子智慧體）測試設計。這種 agent-first guidance（以智慧體為優先的指引）使 downstream scores 提升約 2.3 分，simplicity 提高 6.8%，並減少與 production library 的 exported-name overlap（匯出名稱重疊），顯示針對智慧體使用習慣調整設計流程具有潛力。

#### 實驗數據解讀

**設計智慧體能重現生產級抽象**

在 15 個任務中，有 11 個任務的 agent-designed libraries（智慧體設計的函式庫）重現了 production-library abstractions（生產級函式庫抽象層）。這表示當前 frontier models 能從非規範性規格書與少數可見範例中，推論出符合慣例的 API design（API 設計）。Opus 5.5 在完整兩階段評估中取得最高 library score 48.9，較 production library 基線高出 2.3 分，顯示頂尖設計智慧體在某些情境下能超越人類生產級函式庫對下游智慧體的幫助。

**下游智慧體採用但未充分利用**

實驗發現，downstream agents（下游智慧體）對 agent-written 與 human-written 函式庫的採用率相近，但普遍存在 underuse（未充分利用）現象：它們會 reimplement（重新實作）函式庫已提供的功能。這導致 downstream programs 比 reference solutions 更長、更複雜。換句話說，函式庫本身通常是正確的，但使用者智慧體未能有效 leverage（利用）其抽象。

**失敗根因：僵化與難用介面**

作者對 excess-code（額外程式碼）案例進行 audit，發現 64% 歸因於 rigid（僵化）或 hard-to-use（難以使用）的介面，僅 14% 歸因於 missing capabilities（缺少的能力）。這是本文最重要的實證發現：對於 agent-oriented（面向智慧體）的函式庫設計，瓶頸不在功能完整性，而在於介面是否符合智慧體的使用模式。智慧體傾向於使用直觀、命名清晰、組合彈性高的 API；一旦介面需要額外樣板碼或隱含約定，它們寧可自行實作。

**實作者效應顯著**

LibraryUseBench 的結果進一步指出，即使固定使用最佳函式庫，不同 implementer 的表現差異仍大。這意味 library score 同時是「設計品質」與「使用能力」的綜合指標。未來在比較不同設計智慧體時，應控制或報告 implementer 的貢獻，以免將使用困難誤判為設計缺陷。

**介入策略的效果與極限**

agent-first guidance 讓設計智慧體從消費者視角出發，結果使 downstream scores 提升、程式更簡潔。然而，即便加入 subagent 測試與可執行範例，GPT-6 Astra 的表現仍略遜於 production library。這暗示：單純改進提示策略仍有天花板，可能需要更深層的訓練或迭代設計機制，才能穩定達到人類工程師的設計水準。

#### 與現有研究的比較

**相對於規範式介面評分**

既有研究（Ding et al., 2026; Zhao et al., 2025; Liu et al., 2025; Peng et al., 2026; Gautam et al., 2025）多以規格書中的 signatures（簽名）或 constructs（結構）來評分，但這種方式預先規定了設計，無法衡量開放式的 library design。本文的非規範性規格書與下游使用評估，填補了「設計品質」與「介面正確性」之間的空白。

**相對於智慧體驗證與靜態指標**

Agentic validation（智慧體驗證）（Ehrenberg et al., 2026）與 static metrics 主要評估實作是否正確或程式碼規模，但無法反映 usability（易用性）。本文透過真實 downstream agents 的使用結果來評分，是唯一能同時捕捉 correctness 與 simplicity 的 faithful（忠實）方法。

**相對於人工審查**

human review（人工審查）衡量的是人類偏好，而非 agent 的需求。LibraryDesignBench 直接觀察 agent 的行為，使評估更貼近未來由智慧體主導的軟體工程生態。

**主要貢獻與限制**

主要貢獻包括：(1) 提出以真實使用為核心的兩階段基準；(2) 區分設計與使用效應的 LibraryUseBench；(3) 透過失敗分析指出 usability 是關鍵瓶頸；(4) 驗證 agent-first guidance 的有效性。

限制包括：(1) 規模有限：15 個任務、242 道問題，難以涵蓋所有函式庫類型；(2) simplicity 指標雖可量化，但無法完全捕捉語意可讀性、錯誤訊息品質或文件完整性；(3) 評估結果依賴所選 model families，若換用更強或不同的使用者智慧體，分數可能改變；(4) visible problems 同時出現在設計與測試中，可能導致設計者 overfit（過度擬合）；(5) 未進行人類與智慧體的 A/B 易用性實驗，對「agent 需要什麼」的推論仍屬間接；(6) 使用商業 API 模型，weights（權重）不公開，長期可重現性受限。

#### 可重現性評估

**開放資源**

作者已將程式碼與資料釋出於 GitHub：https://github.com/SprocketLab/librarydesignbench。這包含 15 個 library-design tasks、242 個 downstream programming problems、規格書、reference solutions、評分腳本與執行環境，對可重現性非常有利。

**資料集與任務**

所有 expert-validated programming problems 與對應的 reference solutions 均已公開，研究社群可直接使用或擴充。任務涵蓋四種語言，並以真實 production library 作為對照，具備良好的外部參照。

**模型與權重**

本研究使用的模型多為商業 API，例如 Opus 5.5、GPT-5.6 Luna、GPT-6 Astra、DeepSeek v4.1F、GLM 5.3 Flash 與 Codex。這些模型的 weights 並未公開，且 API 行為可能隨時間漂移。因此，雖然評估流程與資料可重現，但要完全複製原始分數，需要取得相同版本的模型存取權，並在相近時間點執行。建議未來研究在論文中詳細記錄 API 版本、溫度參數與呼叫時間戳，以提升可重現性。

**執行環境**

設計智慧體必須將函式庫打包成可安裝的套件，這項要求確保了評估的實用性，但也增加了環境依賴。公開的 repository 若包含容器化設定（如 Docker），將進一步降低重現門檻。

#### 未來研究方向

**擴充 benchmark 覆蓋率**

未來可將 LibraryDesignBench 擴展到更多程式語言、應用領域（如機器學習、網頁開發、系統程式、資料處理）以及更複雜的 library-design tasks，特別是包含狀態管理、非同步流程或長期執行階段行為的函式庫。

**發展 agent-first 設計原則**

需要系統化總結哪些 API 模式、命名慣例與抽象層對智慧體最友善，並建立相應的設計模式與 anti-patterns。可進一步發展自動化的 usability 評分模型，以減少對大量 downstream agents 呼叫的依賴。

**迭代式與多智慧體共同設計**

目前僅使用 subagents 進行測試；未來可讓 subagents 參與 co-design（共同設計），透過反覆回饋調整介面。這可視為一種針對函式庫設計的 meta-optimization（後設最佳化），目標是最大化 downstream reuse（下游重複使用）。

**更細緻的易用性指標**

除了 LOC、Cyclomatic complexity、Cognitive complexity 與 Halstead complexity，未來可加入動態執行軌跡、智慧體花費的 token/turn 數、錯誤訊息理解難度，以及與慣用用法（idiomatic usage）的語意相似度，以建構更全面的 usability 指標。

**針對函式庫設計的訓練與微調**

可收集大規模的 library-design 資料，對模型進行 supervised fine-tuning（監督式微調）或 reinforcement learning（強化學習），讓模型學會在設計階段預測下游智慧體的需求，而不僅是模仿 production library。

**多智慧體生態系統研究**

函式庫設計並非一次性事件，而是持續演化。未來可研究智慧體如何設計、維護、版本化與淘汰函式庫，以及不同智慧體設計的函式庫之間的兼容性、網路效應與社群採用動態。

**人機協作設計工具**

探討在哪些環節引入人類工程師能最有效提升設計品質，例如抽象層審查、命名把關或邊界案例確認，並開發互動式 library-design 輔助工具。

**新穎抽象與創造力評估**

目前智慧體多數重現 production-library abstractions。未來可設計任務，鼓勵智慧體發明全新抽象，並評估其創造力、泛化能力與對下游任務的長期價值。

**穩健性與異常使用情境**

研究函式庫在面對 out-of-distribution（分布外）需求、對抗性輸入或部分規格遺漏時的表現，並設計能主動提供清晰錯誤訊息與遷移指引的 robust（穩健）函式庫。

## 論文問答

## 背景與動機

**Q1：這篇論文試圖解決什麼核心問題？為什麼「智慧體為智慧體設計函式庫」變得重要？**
A：隨著 AI 智慧體越來越常基於其他智慧體撰寫的程式碼進行開發，它們傾向於重新實作而非重複使用既有功能，導致程式碼庫不斷膨脹。這篇論文關注的核心問題是：智慧體能否設計出其他智慧體也能有效利用的函式庫、框架或 SDK。如果函式庫設計不良，未來的智慧體在正確性與程式碼量上都會受影響，進而增加人類介入修復的成本。

**Q2：為什麼傳統的單元測試或人類審查無法充分評估智慧體設計的函式庫？**
A：傳統正確性測試只能確認函式庫本身是否正確，無法衡量它對使用者的幫助程度；若依照規格書檢查介面簽名，又會預先規範設計，失去評估「設計能力」的意義。智慧體驗證與靜態指標只能評分實作品質，而非易用性；人類審查則反映人類偏好，未必符合智慧體使用者的需求。因此，這些方法都無法忠實地衡量一個函式庫對下游智慧體的價值。

**Q3：為什麼「觀察下游智慧體實際使用函式庫」被視為最忠實的評估方式？**
A：函式庫的價值最終體現在使用者能否用它寫出更正確、更簡潔的程式，而這只有在真實使用情境中才能顯現。無論介面多麼符合規格或人類主觀認為優雅，若下游智慧體無法理解或難以呼叫，就無法發揮應有效益。因此，透過讓不同能力的使用者智慧體解決下游問題，才能同時捕捉正確性與簡潔性，反映函式庫真正的設計品質。

## 方法與創新

**Q4：LibraryDesignBench 的兩階段流程與評分方式是什麼？**
A：LibraryDesignBench 分為「設計階段」與「評估階段」：設計階段讓受評估智慧體依據非規範性規格書實作完整函式庫，規格只定義必要能力與潛在使用案例，不指定介面或抽象層；評估階段則讓三個來自不同模型家族的能力較弱使用者智慧體，使用該函式庫解決下游程式設計問題。最終分數根據下游程式的正確性（通過測試數）與簡潔性（相對於使用生產級函式庫的參考解答）來計算，後者綜合程式碼行數、循環複雜度、認知複雜度與 Halstead 複雜度。

**Q5：這個基準測試的關鍵創新是什麼？它與傳統函式庫評估有何不同？**
A：關鍵創新在於使用「非規範性規格書」並透過下游智慧體的真實使用來評分，而非僅檢查函式庫是否通過測試或介面是否符合預設簽名。傳統評估往往預先規定 API 長相，這會限制設計者的創意，也無法反映實際使用體驗；LibraryDesignBench 則讓智慧體自由決定抽象與介面，並以其他智慧體能否輕鬆採用為最終標準。這種方法把焦點從「函式庫是否正確」轉移到「函式庫是否對未來使用者有用」。

**Q6：為什麼選擇同時衡量正確性與簡潔性，並使用四種靜態複雜度指標？為何要讓三個不同模型家族的使用者智慧體參與評估？**
A：正確性確保函式庫能完成任務，簡潔性則反映函式庫是否真正減少重複實作與認知負擔；兩者結合才能衡量函式庫對下游開發的綜合價值。使用程式碼行數、循環複雜度、認知複雜度與 Halstead 複雜度，可以從不同面向捕捉程式大小與結構複雜度，避免單一指標偏頗。讓三個不同模型家族的使用者智慧體參與，則能評估函式庫設計對多樣化使用者的泛用性，降低單一模型特性造成的偶然結果。

## 實驗與結果

**Q7：這個基準測試涵蓋哪些任務、語言與問題？能否舉一個具體例子？**
A：LibraryDesignBench 包含 15 個函式庫設計任務，橫跨四種程式語言，並有 242 個經專家驗證的下游程式設計問題。舉例來說，其中一個 Rust 任務要求設計名為 clirs 的命令列介面解析 crate，規格書說明需要支援子命令、旗標、選項、型別值、引數數量、跨引數關係與自動生成說明等，但不規定 API 長相。評估階段則讓下游智慧體使用 clirs 實作如 site-plan 等 13 個 CLI 工具，並與使用生產級 clap 函式庫的參考解答比較簡潔性。

**Q8：實驗的主要結果是什麼？智慧體設計的函式庫與人類撰寫的生產級函式庫相比表現如何？**
A：在設計者端，Opus 5.5 取得最高總分 48.9，甚至比人類撰寫的生產級函式庫高出 2.3 分；在 15 個任務中，有 11 個任務的智慧體設計者能重現生產級函式庫的主要抽象。然而，下游智慧體即使面對人類撰寫的函式庫，簡潔性也僅達 61.5，顯示使用者端仍有很大進步空間。整體而言，智慧體已能設計出接近人類水準的抽象，但下游智慧體尚未充分利用這些函式庫。

**Q9：失敗分析與介入實驗揭示了哪些關鍵問題？哪些改進方法有效？**
A：失敗分析發現，64% 的過多程式碼案例源於函式庫介面僵化或難以使用，僅 14% 是因為缺少功能，說明問題主要在設計易用性而非功能完整性。在 LibraryUseBench 中，即使固定使用生產級函式庫，不同實作者表現差異顯著，Opus 5.5 最佳為 66.9，而 GPT-5.6 Luna 在更高推理努力下主要提升正確性，在更規範式提示下主要提升函式庫使用。進一步給設計者「以智慧體為優先」的規範式指引，包括先繪製消費者 API 草圖、提供可執行使用範例，並以子智慧體測試設計，可提升總分約 2.3 分，其中簡潔性提升 6.8%。

## 應用與影響

**Q10：在實務上，LibraryDesignBench 可以如何應用？**
A：開發者可用它來比較不同模型設計函式庫的能力，從中挑選更適合擔任「函式庫設計者」的智慧體。函式庫作者也能藉由這個平台檢驗自己的 API 對 AI 使用者是否夠直覺，並在釋出前發現僵化或難用的介面。此外，研究團隊可將其作為長期測試平台，持續追蹤智慧體在軟體工程任務中從「重新實作」走向「重複使用」的進展。

**Q11：這些發現對開發智慧體程式設計工具有什麼產品層面的啟示？**
A：產品設計應把「智慧體使用者」視為一類特殊使用者，提供更具主見、更直覺的 API，而非僅追求功能完整。為智慧體設計函式庫時，應附上可執行的使用範例、清晰的消費者程式草圖，並在內部用子智慧體進行測試，以確保介面不會造成下游困擾。這些做法能減少下游智慧體重新實作既有功能的傾向，從而降低程式碼膨脹與後續維護成本。

**Q12：這項研究對整個軟體工程與 AI 領域可能帶來什麼影響？**
A：它把軟體工程的核心問題從「人類為人類設計函式庫」擴展到「智慧體為智慧體設計函式庫」，凸顯未來程式碼生態系將由 AI 使用者共同塑造。這也提醒我們，優秀的函式庫不只在於正確與強大，更在於能否被其他自主系統理解與採用。長遠來看，這可能催生專門針對智慧體使用習慣的設計原則、文件格式與自動化測試工具，改變開源社群與企業內部的程式碼治理方式。

## 限制與未來方向

**Q13：這項研究有哪些已承認的限制？**
A：目前基準僅涵蓋 15 個任務與四種語言，雖然已具規模，但仍無法代表所有領域的函式庫設計情境。簡潔性指標雖然綜合多種靜態複雜度，但終究是靜態度量，可能無法完全捕捉可讀性或語義上的簡潔。此外，評估使用的下游智慧體來自特定模型家族，未來仍需驗證這些結論對更廣泛、更新模型的泛用性。

**Q14：論文指出哪些典型的失敗案例？這些案例說明了什麼？**
A：典型失敗包括下游智慧體在函式庫已提供某功能時仍自行重新實作，以及因介面僵化而繞過函式庫寫出更長、更複雜的程式。例如，某些智慧體撰寫的函式庫雖然功能齊全，但引數順序、命名或組合方式不符合使用者智慧體的預期，導致使用率偏低。這些案例說明，功能完整性只是門檻，真正的瓶頸在於介面是否彈性、直覺，以及是否能引導使用者智慧體正確採用。

**Q15：未來可以朝哪些方向延伸這項研究？**
A：未來可以擴充更多語言、領域與更大規模的函式庫設計任務，並引入動態執行時指標或人機協作評估來補強靜態簡潔性分數。另一方向是開發自動化的「智慧體優先」設計輔助工具，例如自動生成使用範例、偵測僵化介面，或讓設計者與子智慧體反覆迭代。最終，也可將這類評估整合進智慧體的訓練流程，直接優化「設計出能被其他智慧體重複使用的函式庫」這一目標。

## 實務應用指南

### 適用場景

**企業內部 AI 程式碼生成平台**：當組織部署多個智慧體協作開發時，可由一個較強的設計智慧體先建立內部 SDK、工具函式庫或框架，再由下游智慧體重複使用，避免每個智慧體都重新實作相同能力，降低程式碼庫膨脹。

**多智慧體協作軟體開發**：在需要不同模型家族分工的場景中，上游智慧體負責函式庫設計，下游智慧體負責應用程式開發。此模式適用於需要穩定介面與抽象層的大型專案，例如命令列工具 crate、資料處理框架或測試工具。

**自動化框架與 CLI 工具生成**：若產品需要快速產生客製化 CLI 解析器、配置管理函式庫或領域特定語言（DSL）工具，可採用本文的兩階段基準測試流程，先讓智慧體設計函式庫，再驗證其他智慧體能否用它寫出簡潔正確的程式。

**遺留系統現代化**：將舊有程式碼包裝成新函式庫時，可由智慧體根據非規範性規格書設計新介面，再透過下游智慧體驗證新介面是否比直接操作舊程式碼更簡單，作為重構成效的客觀指標。

**開源 AI 輔助開發工具評測**：對於開發 AI 程式設計助手或模型評測平台的團隊，LibraryDesignBench 提供了一個測試平台，可系統性比較不同模型設計函式庫、並觀察下游重複使用行為。

---

### 實作前置條件

**資料準備**：需要一份非規範性規格書，明確列出必要能力與潛在使用案例，但不預先指定介面與抽象層。同時需要專家驗證的下游程式設計問題、參考解答、參考測試，以及對應的人類撰寫生產級函式庫作為對照基準。

**運算資源**：需要能夠呼叫多個模型家族 API 的權限，例如 GPT、DeepSeek、GLM 等不同來源的智慧體。此外需要可執行測試的隔離環境，用於驗證函式庫正確性與下游程式通過測試數。

**技能需求**：團隊成員需具備軟體工程背景，熟悉 API 設計與至少一種目標語言（如 Rust、Python 等）。同時需要理解靜態指標，例如程式碼行數、循環複雜度、認知複雜度與 Halstead 複雜度，並能進行失敗分析與迭代優化。

---

### 實作步驟建議

1. **撰寫非規範性規格書**：定義函式庫必須支援的必要能力，列舉兩到三個可見的下游使用案例，但刻意不規範介面名稱、結構體設計或抽象層細節，讓設計智慧體自行決定。

2. **執行設計階段**：讓受評估的智慧體根據規格書實作全功能函式庫，並使用語言專屬套件管理工具打包，確保下游智慧體可以順利安裝與引用。

3. **建立評估題目集**：準備數十到數百道專家驗證的下游程式設計問題，涵蓋不同難度與使用情境。每道題目都需有以生產級函式庫撰寫的參考解答，作為簡潔性比較基準。

4. **部署下游使用者智慧體**：選用三個以上不同模型家族、能力較弱的使用者智慧體，讓它們使用設計好的函式庫解決下游問題，觀察其採用與未充分利用行為。

5. **評估正確性與簡潔性**：記錄每個下游程式通過測試數，並計算相對於參考解答的簡潔性分數，綜合程式碼行數、循環複雜度、認知複雜度與 Halstead 複雜度。

6. **進行失敗分析**：針對下游智慧體寫出額外程式碼的案例進行審查，區分是介面僵化或難以使用，還是缺少的能力所導致，並將結果回饋給設計階段。

7. **加入以智慧體為優先的規範式指引**：要求設計智慧體先撰寫消費者視角的 API 草圖、提供可執行的使用範例，並強調主要使用者是其他智慧體而非人類工程師。

8. **使用子智慧體測試函式庫**：在設計階段就讓子智慧體試用初版函式庫，及早發現介面問題，避免進入評估階段後才發現下游重複實作。

---

### 潛在風險與注意事項

**介面僵化導致下游重複實作**：根據論文失敗分析，64% 的額外程式碼案例來自僵化或難以使用的介面，而非缺少的能力。設計時應保留彈性，避免過度嚴格的參數順序或隱藏必要功能。

**下游智慧體未充分利用函式庫**：即使使用生產級函式庫，下游智慧體仍傾向重新實作已有功能。建議在提示中加入強制使用函式庫的指引，並提供完整可執行的使用範例。

**過度依賴正確性測試**：僅驗證函式庫是否正確無法衡量其對下游智慧體的價值。必須同時觀察下游程式是否更簡潔，才能真實評估函式庫設計品質。

**不同模型家族行為差異大**：同一個函式庫對不同使用者智慧體的友善程度可能不同。評估時應涵蓋多個模型家族，避免以單一模型表現推論整體可用性。

**規格書過度規範會限制設計創意**：若規格書預先指定太多介面細節，將無法測量智慧體真正的函式庫設計能力。應在「足夠指引」與「保留設計空間」之間取得平衡。

---

### 與其他技術的整合建議

**整合 CI/CD 管線**：將兩階段基準測試嵌入持續整合流程，每次函式庫變更後自動觸發設計階段與評估階段，並產出正確性與簡潔性報告。

**結合靜態分析工具**：將程式碼行數、循環複雜度、認知複雜度與 Halstead 複雜度等靜態指標整合至分析腳本，自動比較下游程式與參考解答的差異。

**與 IDE 或編輯器外掛整合**：在開發環境中提示智慧體或開發者目前可用的函式庫能力，減少未充分利用與重新實作的情況。

**搭配文件與範例生成工具**：利用智慧體自動產生使用文件與可執行範例，並將其作為規範式指引的一部分餵給下游使用者智慧體。

**連接模型評測平台**：將 LibraryDesignBench 的函式庫分數與現有模型評測平台對接，作為比較不同模型在軟體工程任務上表現的補充指標。

---

### 給不同背景讀者的閱讀建議

**初學者**：這篇論文探討的是「AI 如何幫 AI 設計更好用的工具」，你可以把它想像成一個老師傅打造工具箱、學徒再用工具箱做東西的過程。建議先從圖一與摘要讀起，理解兩階段基準測試的概念，不必急著深入複雜度指標或模型細節。

**AI 工程師**：本文提供了一個可落地的評估框架，重點在於如何透過下游智慧體的真實使用來衡量函式庫品質。建議仔細閱讀設計階段的提示設計、失敗分析分類，以及以智慧體為優先的規範式指引，這些都能直接應用在你目前建構的多智慧體開發流程中。

**研究人員**：LibraryDesignBench 的核心貢獻是將函式庫評估從「正確性」擴展到「下游使用成效」，並提供 242 道專家驗證題目作為研究基礎。建議關注其評量指標設計、簡潔性公式，以及為何介面僵化比缺少能力更常導致失敗，這些都是未來可延伸的研究方向。

**產品經理**：如果你的產品涉及讓 AI 自動產生或維護程式碼，這篇論文提醒了一個關鍵風險：AI 寫的函式庫可能正確但難用，導致後續 AI 或工程師花更多時間重新實作。建議聚焦在適用場景與潛在風險章節，評估是否該在產品中引入類似的兩階段品質驗證機制。
