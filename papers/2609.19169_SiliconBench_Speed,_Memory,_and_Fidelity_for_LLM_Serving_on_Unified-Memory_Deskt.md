## ⚡ TL;DR

現有本地LLM推論評測只重速度，忽略統一記憶體桌面的記憶體餘量與輸出保真度。
本文提出SiliconBench，從速度、記憶體、保真度評估九個Apple Silicon引擎。
僅三引擎過三門檻；vllm-metal並發吞吐翻倍，Thunderbolt RDMA張量並行勝TCP。

## 摘要翻譯

統一記憶體桌面系統（Unified-Memory Desktops）上的並發本地大型語言模型（LLM）推論服務（Concurrent Local LLM Serving）必須保留記憶體餘量（Memory Headroom）與輸出保真度（Output Fidelity），而這正是僅考量速度的排名（Speed-Only Rankings）所忽略的。我們提出 SiliconBench，從速度（Speed）、記憶體（Memory）與保真度（Fidelity）三個面向，評估九個 Apple Silicon 推論引擎（Serving Engines）。我們在 Qwen3、Qwen3.5 與 Gemma 4 上評估對話（Chat）與 Agent 推論服務（Agent Serving），並使用分類任務（Classification Task）對照 NVIDIA 參考實作（NVIDIA Reference）檢驗品質迴歸（Quality Regressions）。DGX Spark 提供互補的推論效能參考基準。三項設計準則（Desiderata）引導結果解讀：推論架構成熟度（Serving Architecture Readiness）、記憶體紀律（Memory Discipline），以及多節點擴展（Multi-Node Scaling）。在 Qwen3-0.6B 上，僅 vllm-metal 在兩項工作負載中，於並行度（Concurrency）從 1 提升至 16 時將吞吐量（Throughput）提高逾兩倍；CUDA vLLM 與 SGLang 在相同提示詞上展現更強的並行度（Concurrency）擴展性。明確記憶體預算（Explicit Memory Budgets）並不能保證記憶體餘量（Memory Headroom）：有兩套推論軟體堆疊（Inference Stacks）雖然記憶體使用量逼近實體容量（Physical Capacity）、吞吐量（Throughput）下滑，仍完成所有請求。較新的模型架構（Model Architectures）所獲得的引擎支援（Engine Support）較為有限，其受評估實作與保真度參考（Fidelity Reference）相符。僅有三套推論軟體堆疊同時滿足完成率（Completion）、保真度（Fidelity）與模型覆蓋率門檻（Model-Coverage Gate）。在更大的密集模型（Dense Models）與混合專家模型（MoE Models）上的比較，凸顯了在進行中的生成（Ongoing Generation）過程中排程提示詞處理（Scheduling Prompt Processing）的重要性：vllm-metal 的打包式預填—解碼路徑（Packed Prefill-Decode Path）在並發負載（Concurrent Load）下，能維持比 omlx 更低的首 token 延遲（First-Token Latency）。在受測的雙機配置（Two-Machine Configurations）中，透過 Thunderbolt RDMA 的張量並行（Tensor Parallelism）具擴展性，而透過 TCP 的流水線並行（Pipeline Parallelism）則出現衰退。我們釋出基準測試程式碼、每次執行結果（Per-Run Results）與維護日誌（Maintenance Journals），並透過結合有界 Agent 修復（Bounded Agent Fixes）與人工審查（Human Review）的流程加以支援。

### 核心貢獻（3～5點）
- 提出 SiliconBench 評估框架，從速度（Speed）、記憶體（Memory）、保真度（Fidelity）三個面向系統評估 Apple Silicon 上的九個推論引擎（Serving Engines）。
- 在 Qwen3、Qwen3.5、Gemma 4 上評估對話（Chat）與 Agent 推論服務（Agent Serving），並以分類任務（Classification Task）對照 NVIDIA 參考實作（NVIDIA Reference）檢驗品質迴歸（Quality Regressions）。
- 揭示並行度（Concurrency）擴展、記憶體紀律（Memory Discipline）與模型支援的實務差異：僅少數推論軟體堆疊（Inference Stacks）同時滿足完成率（Completion）、保真度（Fidelity）與模型覆蓋率門檻（Model-Coverage Gate）。
- 驗證多節點擴展（Multi-Node Scaling）特性：在雙機配置（Two-Machine Configurations）中，Thunderbolt RDMA 上的張量並行（Tensor Parallelism）具擴展性，而 TCP 上的流水線並行（Pipeline Parallelism）則衰退。
- 公開釋出基準測試程式碼、每次執行結果（Per-Run Results）與維護日誌（Maintenance Journals），並說明結合有界 Agent 修復（Bounded Agent Fixes）與人工審查（Human Review）的可重現流程。

### 適合對象
對本地 LLM 推論服務、Apple Silicon / 統一記憶體桌面系統（Unified-Memory Desktops）效能評測、推論引擎（Serving Engines）開發與多節點擴展（Multi-Node Scaling）感興趣的研究人員與系統工程師；亦適合需要選擇本地部署方案或建構可重現基準測試流程的開發者與進階使用者。

## 深度分析

#### 方法論解析

SiliconBench 的核心方法論可概括為「在同一個統一記憶體桌面系統（Unified-Memory Desktops）上，同時評量推論速度（Speed）、記憶體使用（Memory）與輸出保真度（Output Fidelity）」。這三個維度分別對應到本文提出的三大設計準則（Desiderata）：推論架構成熟度（Serving Architecture Readiness, D1）、記憶體紀律（Memory Discipline, D2）與多節點擴展（Multi-Node Scaling, D3）。

**評測對象與引擎分類。** 論文選定九個活躍開發的 Apple Silicon 推論引擎（Serving Engines）：llama.cpp、Ollama、mlx_lm、vllm-metal、vllm-mlx、omlx、sglang、hf_transformers、mistral.rs。Table 1 從四個技術特徵區分這些堆疊：提示詞批次處理（Prompt Batching）、KV 快取配置（KV-Cache Layout）、預填 / 解碼（Prefill/Decode）是否合併執行，以及記憶體策略（Memory Policy）。這樣的分類讓後續結果不只是「誰比較快」，而能連結到具體的系統設計選擇，例如 vllm-metal 採用打包 token（Packed Tokens）、分頁式（Paged）KV 快取與同一 pass（Same Pass）的 Prefill/Decode，而 mlx_lm、vllm-mlx、omlx、sglang、mistral.rs 多採用填充批次（Padded Batch）或單一提示詞（One Prompt）並將兩階段分開執行（Separate Passes）。

**工作負載與並行設計。** 為了模擬真實本地使用情境，SiliconBench 設計了兩類工作負載：對話（Chat）與 Agent 推論服務（Agent Serving）。後者特別重要，因為單一程式設計 Agent（Coding Agent）可能同時發出 4 到 16 個同時請求（Simultaneous Requests），這會對連續批次處理（Continuous Batching）與記憶體管理造成顯著壓力。實驗從並行度（Concurrency）1 掃描到 16，觀察吞吐量（Throughput）、延遲（Latency）、記憶體使用（Memory Use）與完成率（Completion）的變化。

**模型選擇策略。** 選用 Qwen3-0.6B 作為共同基線，因為它夠小，能讓所有引擎都跑得起來；再以 Qwen3.5-0.8B 與 Gemma-4-E4B-it 檢驗新模型架構（Model Architectures）的引擎支援（Engine Support）狀況。此外，論文在附錄中補充更大型的密集模型（Dense Models）與混合專家模型（MoE Models）實驗，以及多機配置（Two-Machine Configurations）測試。

**保真度評量方法。** 不同於一般速度排行榜僅比較吞吐量，SiliconBench 使用一個分類任務（Classification Task）來檢查品質迴歸（Quality Regressions）。具體做法是將各引擎在 Apple Silicon 上的輸出與 NVIDIA 參考實作（NVIDIA Reference）——以 NVIDIA A100 執行的結果——進行任務層級分數（Task-Level Scores）比對。這種設計把「輸出是否正確」轉化為可量化的保真度門檻（Fidelity Gate），避免引擎為了加速而犧牲答案品質。

**記憶體測量與門檻。** 由於 Apple Silicon 的 RAM 與 macOS 及前景應用程式（Foreground Applications）共享，SiliconBench 不只看絕對記憶體用量，更關注記憶體餘量（Memory Headroom）。實驗觀察當記憶體使用接近實體容量（Physical Capacity）時，吞吐量是否下降、請求是否失敗，從而評估引擎的記憶體紀律（D2）。同時設立完成率、保真度與模型覆蓋率（Model-Coverage Gate）三個通過條件，篩選出真正可用的堆疊。

**多節點擴展方法。** 針對單機記憶體無法容納的大型模型，論文測試雙機配置下的張量並行（Tensor Parallelism, TP）與流水線並行（Pipeline Parallelism, PP）。特別比較透過 Thunderbolt RDMA 的 TP 與透過 TCP 的 PP，以評估不同互連與平行策略在統一記憶體桌面上的表現。

**維護與可重複性流程。** 為了應對推論引擎快速迭代帶來的適配問題，SiliconBench 提出「有界 Agent 修復（Bounded Agent Fixes）+ 人工審查（Human Review）」的維護流程。當依賴失敗或模板錯誤發生時，由 Agent 在限定範圍內提出適配修正，再由研究人員審核後重新產生官方結果。每次發布都包含每次執行結果（Per-Run Results）與維護日誌（Maintenance Journals），讓結果可追溯。

#### 實驗數據解讀

**速度與並行擴展：vllm-metal 在 Apple Silicon 上展現較佳的並行擴展性。** 在 Qwen3-0.6B 上，vllm-metal 是唯一一個在對話與 Agent 兩種工作負載中，都能將吞吐量從並行度 1 到 16 提升超過兩倍的堆疊。這與其技術選擇密切相關：打包式預填—解碼路徑（Packed Prefill-Decode Path）讓新進入的提示詞處理（Prompt Processing）能與進行中的生成（Ongoing Generation）共享同一 pass，減少 GPU 空閒；分頁式 KV 快取（Paged KV Cache）則降低記憶體碎片，支援更有效的連續批次處理。相對地，採用分開 pass（Separate Passes）與連續配置（Contiguous per Batch / per Request）的引擎，在並發負載（Concurrent Load）下容易出現首 token 延遲（First-Token Latency）上升或吞吐量停滯。

**CUDA 參考凸顯 Metal 後端成熟度差距。** 在相同提示詞上，CUDA vLLM 與 SGLang 展現出更強的並行擴展。這說明目前 Apple Silicon 的推論引擎在核心調度、記憶體管理與核心生成工具鏈上，仍落後於 CUDA 生態系。DGX Spark 作為互補的參考平台，提供了「若核心與排程成熟後可達到的性能上限」。

**對話排名無法代表 Agent 情境。** 論文指出，單純的對話吞吐量排名會遮蔽並發 Agent 推論服務的差異。Agent 工作負載通常包含更長、更多樣的提示詞，對 Prefill 階段的排程壓力更大。因此，僅用 Chat 結果挑選引擎，可能會低估在真實 Agent 使用情境下的延遲與失敗風險。

**記憶體紀律：明確上限不等於保留餘量。** 實驗發現，即使某些引擎設定了明確記憶體預算（Explicit Memory Budgets），仍可能讓記憶體使用逼近實體容量，導致吞吐量下降。有兩個堆疊雖然完成所有請求，但記憶體幾乎用滿，這對 macOS 與前景應用程式是警訊。這顯示 D2 不只是「會不會當機」，而是「在高負載下是否仍保留足夠記憶體餘量給作業系統與使用者」。換句話說，記憶體策略（Memory Policy）的宣告與實際執行之間存在落差，需要更細緻的測量與反饋機制。

**完成率、保真度與模型覆蓋率的三重門檻。** 只有三個 Apple Silicon 堆疊同時通過完成率、保真度與模型覆蓋率三個門檻。這強調了速度並非唯一指標：一個引擎可能很快，但若無法支援新模型架構，或在分類任務上相對 NVIDIA 參考實作產出品質迴歸，就不適合推薦。值得注意的是，雖然 Qwen3.5 與 Gemma 4 的引擎支援較窄，但已評估的實作在保真度上都能匹配參考，顯示問題主要在「能不能跑」，而非「跑了會不會變爛」。

**大型模型與 Prefill/Decode 排程。** 在更大型的密集模型與 MoE 模型上，vllm-metal 的打包式 Prefill/Decode 路徑在並發負載下仍保持比 omlx 更低的首 token 延遲。這再次驗證：對於本地並發服務，能否在 decode 進行中穿插處理新請求的 prefill，是決定使用者體驗的關鍵。omlx 採用單一提示詞與分開 pass，在高並行下容易讓新請求等待，形成隊列延遲。

**多節點擴展：TP over Thunderbolt RDMA 可行，PP over TCP 倒退。** 雙機實驗顯示，透過 Thunderbolt RDMA 的張量並行能夠擴展，而透過 TCP 的流水線並行則出現性能倒退。這有幾層意義：第一，Thunderbolt 提供的頻寬與延遲足以支撐 TP 所需的 all-reduce 通訊；第二，PP 的氣泡（pipeline bubble）與 TCP 的傳輸延遲疊加後，抵消了平行化的好處；第三，對於統一記憶體桌面系統，選擇正確的平行策略與互連技術，比單純增加機器數量更重要。

#### 與現有研究的比較

**相較於現有消費級 / Apple Silicon 基準測試。** 過去研究如 Rajesh et al.、Barrios、Benazir and Lin 主要比較少數堆疊的吞吐量，缺乏並發負載、記憶體餘量與輸出品質的綜合評量。Zhang and Huang 聚焦 CPU–GPU 執行權衡，Vegasena 探討客製化 Metal 核心對長上下文 KV attention 的影響，Chen et al. 研究跨 Mac Studio 的混合專家並行，Stuhlmann et al. 則擴展到多種加速器家族。SiliconBench 的差異在於：同時覆蓋九個 Apple Silicon 引擎、以 DGX Spark 作為 CUDA 參考、並將速度、記憶體與保真度綁定在同一個審計框架中。

**相較於資料中心推論系統研究。** 連續批次處理（Continuous Batching）、分頁式 KV 快取（Paged KV Cache）、區塊化預填（Chunked Prefill）與前綴共享（Prefix Sharing）等技術已在 CUDA 資料中心加速器上成為標準。SiliconBench 將這些技術的「就緒程度」移植到 Apple Silicon 進行檢驗，發現 Metal 後端在核心生成工具鏈（如 Triton、TileLang）與新注意力架構支援上仍較不成熟。

**相較於分散式推論研究。** Petals 與 Prima.cpp 等研究探索協作式 GPU 服務與異質家庭叢集，但多聚焦於架構設計而非系統性比較。SiliconBench 在固定工作負載下比較三種多節點系統，並明確區分 TP/PP 與 Thunderbolt RDMA/TCP 的組合影響，為本地多機部署提供實證依據。

**相較於輸出飄移與動態基準研究。** He and Thinking Machines Lab、Yuan et al.、Khatchadourian and Franco、Anthropic 等研究指出核心非確定性、混合精度與跨提供者差異會造成 LLM 輸出飄移。SiliconBench 採用分類任務與 NVIDIA 參考實作來操作化保真度，但僅用單一任務類型，對創意生成、程式碼正確性或長上下文忠實度的覆蓋仍有限。White et al.、Jain et al.、Zhang et al. 則透過定期更新提示詞來對抗基準過時；SiliconBench 選擇固定提示詞、但透過維護 Agent 與社群 PR 持續更新框架適配器，並公開維護日誌，形成另一種可重複性策略。

**主要限制。** 第一，研究以 Apple Silicon 為主，雖有 DGX Spark 作為參考，但對 Intel/AMD 內顯、Qualcomm 等統一記憶體平台的代表性不足。第二，macOS 的記憶體壓縮與 swap 機制使「實際可用餘量」難以精確量測。第三，引擎版本快速迭代，結果可能隨版本更新而變化。第四，保真度僅用分類任務，未能涵蓋所有輸出品質面向。第五，多節點實驗僅到雙機，更大規模叢集的行為仍需驗證。

#### 可重現性評估

**開源釋出與透明度。** SiliconBench 釋出了基準測試程式碼、每次執行結果與維護日誌，這在推論引擎快速演進的領域中尤為重要。維護日誌記錄了早期執行中遇到的依賴失敗與模板錯誤，讓其他研究者能追溯結果產生過程，也凸顯了持續軟體驗證的必要性。

**模型權重與資料集可取得性。** 評估使用的 Qwen3、Qwen3.5 與 Gemma 4 均可在 HuggingFace 上取得，且 mlx-community Hub 提供大量 Apple Silicon 轉換模型。這降低了重現門檻。然而，論文未明確說明分類任務所使用的資料集名稱與前處理流程，若該資料集非公開，則會成為可重現性的潛在缺口。

**引擎與環境版本。** 九個受測引擎皆為開源專案，理論上可取得對應版本。但由於推論框架更新頻繁，若官方釋出未鎖定確切的 commit hash、Python 套件版本與 macOS 版本，重現結果可能出現差異。維護日誌雖有幫助，但仍建議未來版本加入完整的軟體物料清單（SBOM）與容器化或虛擬化環境描述。

**維護流程的優缺點。** 「有界 Agent 修復 + 人工審查」的流程在自動化與品質控制之間取得平衡：Agent 能快速產生適配器修正，人工審查則避免未經控制的漂移。但此流程仍帶有一定主觀性，不同審查者對「可接受修正」的標準可能不同。未來可進一步將審查準則與回歸測試自動化，減少人為變異。

**整體可重現性評價。** 在程式碼、模型權重與原始數據公開方面，SiliconBench 達到高水準；但在資料集細節、環境鎖定與跨平台泛化上仍有改進空間。對於一個以「持續維護」為核心設計的基準測試而言，這樣的透明度已經優於多數一次性評測。

#### 未來研究方向

**擴展模型與任務覆蓋。** 未來可納入更大型的密集模型（Dense Models）與混合專家模型（MoE Models），例如數十億到數百億參數的模型，以測試單機與多機記憶體極限。此外，除了分類任務，也應加入程式碼生成（如 HumanEval）、指令遵循、長上下文檢索（needle-in-haystack）與多模態任務，讓保真度評量更貼近真實使用情境。

**強化記憶體紀律機制。** 可研究作業系統感知的動態記憶體預算（Dynamic Memory Budgets），根據 macOS 回報的記憶體壓力（Memory Pressure）即時調整 KV 快取大小或批次數量。也可探討記憶體壓縮、swap 與統一記憶體頻寬爭用對推論效能的量化影響，建立「使用者可感知餘量」的指標。

**提升 Metal 推論生態成熟度。** 目前 Metal 在核心生成工具鏈（如 Triton、TileLang for Metal）上仍落後 CUDA。未來研究可聚焦於：為 Apple Silicon 實作區塊化預填（Chunked Prefill）、前綴共享（Prefix Sharing）、推測解碼（Speculative Decoding）與更高效注意力核心，縮小與 CUDA vLLM / SGLang 的並行擴展差距。

**多節點與異質叢集擴展。** 除了 Thunderbolt RDMA，可評估 Ethernet、WiFi、InfiniBand 等不同互連下的張量並行與流水線並行表現。也可研究混合平行策略（TP + PP）、專家平行（Expert Parallelism）與異質裝置（Apple Silicon + NVIDIA + CPU）協作，為家庭或小型工作室叢集提供最佳實務。

**能量、溫度與前景應用干擾。** 統一記憶體桌面系統通常有功耗與散熱限制，未來可加入每 token 功耗（Watts per Token）與熱節流（Thermal Throttling）測量。同時，直接測量推論服務對前景應用程式（如瀏覽器、IDE）的延遲影響，將比單純記憶體餘量更能反映使用者體驗。

**自動化維護與社群協作。** 可將維護 Agent 與持續整合（CI）系統結合，自動偵測引擎更新後的適配器失效、執行回歸測試並產生維護日誌。同時建立統一的本地推論 API 標準，降低為九個引擎各自撰寫適配器的負擔，讓社群能更容易貢獻新引擎與新模型。

**長上下文與量化影響。** 未來可評估不同上下文長度下的 KV 快取管理策略，以及 4-bit / 8-bit 量化對速度、記憶體與保真度的權衡。特別是在統一記憶體頻寬有限的情況下，量化與 KV 快取壓縮可能是提升可服務模型大小的關鍵。

## 論文問答

**Q1：SiliconBench 主要想解決什麼問題？**
A：SiliconBench 針對的是在統一記憶體桌面系統上進行並發本地 LLM 推論服務時，現有評測過度偏重速度而忽略記憶體餘量與輸出保真度的問題。Apple Silicon 這類平台的 GPU 與 CPU 共享同一池 LPDDR 記憶體，推論引擎必須與 macOS 及前景應用程式競爭記憶體，單純的吞吐量排名無法反映系統整體可用性。此外，單一請求的速度也無法代表程式設計 Agent 同時發出 4 到 16 個請求時的實際表現，因此需要同時評量速度、記憶體與輸出品質。

**Q2：為什麼「僅考量速度的排名」不足以評估本地推論引擎？**
A：速度排名無法顯示引擎在耗盡記憶體後對整台電腦的影響，當可用記憶體接近實體容量時，系統會產生記憶體壓力，導致推論與前景應用程式同時變慢甚至請求失敗。其次，單一請求的吞吐量無法衡量引擎在並發負載下是否具備連續批次處理與記憶體紀律，缺乏這些能力的堆疊可能在多請求情境下崩潰或效能驟降。最後，速度排名也忽略了輸出保真度，不同引擎可能產生與 NVIDIA 參考實作不一致的結果，進而影響任務層級分數。

**Q3：為什麼統一記憶體桌面系統成為本地 LLM 推論的重要平台？**
A：Apple Silicon 與 NVIDIA DGX Spark 等統一記憶體桌面系統使用 CPU 與 GPU 共享的低功耗 DDR 記憶體，容量已可達 512GB，過去這只見於資料中心加速器。Mac 生態系統對本地 LLM 的需求龐大，例如 Ollama、llama.cpp、LM Studio 每年有數十萬次 Mac 安裝，mlx_lm 每月在 PyPI 也有大量下載。然而，正因為記憶體由作業系統、前景應用程式與推論引擎共用，如何在高效推論的同時保留足夠記憶體餘量，成為評估引擎的關鍵課題。

**Q4：SiliconBench 的核心評估方法包含哪些要素？**
A：SiliconBench 同時從速度、記憶體與保真度三個視角，評估九個 Apple Silicon 推論引擎在對話與 Agent 兩種工作負載下的表現。速度方面測量吞吐量與延遲，記憶體方面追蹤使用量與請求完成率，保真度方面則以分類任務比對各引擎輸出與 NVIDIA A100 參考實作的差異。此外，研究還在 DGX Spark 上執行互補的 CUDA 參考軌道，以便透過共享引擎家族進行跨平台比較。

**Q5：相較於現有基準，SiliconBench 的關鍵創新是什麼？**
A：SiliconBench 首次將並發擴展性、記憶體使用與任務層級保真度整合在同一個 Apple Silicon 推論引擎評測中，並提出推論架構成熟度、記憶體紀律與多節點擴展三大設計準則來解讀結果。它還引入結合有界 Agent 修復與人工審查的維護流程，以應對推論軟體堆疊快速更新所帶來的適配器失效與範本錯誤。所有基準程式碼、每次執行結果與維護日誌均對外釋出，強調可重現與持續驗證。

**Q6：SiliconBench 在實驗設計上做了哪些重要選擇？**
A：研究選擇 Qwen3-0.6B 作為共同基線模型，並以 Qwen3.5-0.8B 與 Gemma-4-E4B-it 測試新架構支援度，同時在更大型的密集模型與混合專家模型上進行補充實驗。並行度從 1 提升到 16，以模擬程式設計 Agent 發出的同時請求；記憶體策略則依據提示詞批次處理、KV 快取配置與預填／解碼是否同一 pass 進行分類。為了檢驗品質迴歸，研究使用固定提示詞與分類任務，並將各引擎結果與 NVIDIA 參考實作比對。

**Q7：SiliconBench 使用了哪些基準工作負載與模型？**
A：主要工作負載包括對話型與 Agent 型兩種推論服務情境，並透過分類任務量化輸出保真度。模型方面以 Qwen3-0.6B 為主軸，另評估 Qwen3.5-0.8B 與 Gemma-4-E4B-it 等較新架構，並在附錄中補充更大型的密集模型與 MoE 模型實驗。DGX Spark 軌道則在相同模型與提示詞上執行 CUDA vLLM 與 SGLang 等引擎，作為 Apple Silicon 結果的對照參考。

**Q8：SiliconBench 有哪些關鍵實驗結果？**
A：在 Qwen3-0.6B 上，vllm-metal 是唯一能將對話與 Agent 兩種工作負載的吞吐量從並行度 1 到 16 都提升超過兩倍的 Apple Silicon 引擎。CUDA vLLM 與 SGLang 在相同提示詞下展現更強的並發擴展性，顯示 Metal 後端在排程與記憶體管理上仍有追趕空間。最終只有三個 Apple Silicon 堆疊同時通過完成率、保真度與模型覆蓋率三大門檻；此外，明確記憶體預算並不保證記憶體餘量，有引擎雖完成所有請求，但記憶體使用已逼近實體容量且吞吐量下滑。

**Q9：在大型模型與多節點實驗中觀察到什麼現象？**
A：在較大的密集模型與混合專家模型上，研究發現將提示詞處理排程與進行中的生成階段並行執行非常重要；vllm-metal 的打包式預填—解碼路徑在並發負載下，能維持比 omlx 更低的首 token 延遲。在多節點雙機配置中，透過 Thunderbolt RDMA 的張量並行能夠有效擴展，但透過 TCP 的流水線並行則出現效能迴歸。這些結果凸顯了記憶體紀律與通訊後端對統一記憶體桌面系統擴展性的影響。

**Q10：SiliconBench 的評測結果對實際應用場景有何意義？**
A：對於使用程式設計 Agent 的開發者而言，結果顯示並非所有引擎都能穩定處理 4 到 16 個同時請求，選擇支援連續批次處理與分頁式 KV 快取的引擎較為穩妥。對於一般使用者，研究提醒即使某引擎吞吐量高，也可能快速耗盡記憶體，導致瀏覽器、IDE 或 macOS 本身變慢。因此，在挑選本地 LLM 推論方案時，應同時考量速度、記憶體餘量與輸出品質，而非只看單一排行榜。

**Q11：從產品設計角度，開發者應如何根據 SiliconBench 選擇或改進推論引擎？**
A：產品開發者應優先採用具備連續批次處理、分頁式 KV 快取與明確記憶體上限的引擎，以在並發負載下兼顧吞吐量與記憶體紀律。同時需要建立持續的適配器維護機制，因為推論框架與模型更新頻繁，容易出現相依性失敗或範本錯誤。最後，若目標是服務超過單機記憶體容量的模型，應評估基於高速互連的張量並行方案，而非單純依賴 TCP 的流水線並行。

**Q12：SiliconBench 對學術界與產業界可能帶來什麼影響？**
A：SiliconBench 為 Apple Silicon 上的本地 LLM 推論提供了第一個同時涵蓋速度、記憶體與保真度的系統性評測，有助於研究人員識別現有引擎的架構缺口。對產業界而言，公開的基準程式碼、每次執行結果與維護日誌可作為選型與優化的依據，也能促進引擎開發者針對記憶體管理與新模型支援進行改進。整體而言，它推動了本地推論評測從單純比速度，轉向更全面、更貼近實際使用情境的評估典範。

**Q13：這項研究有哪些已承認的限制？**
A：研究的主要焦點放在 Apple Silicon，雖然有 DGX Spark 作為 CUDA 參考，但其他統一記憶體平台或 x86 桌面系統的覆蓋有限。早期執行中出現了相依性失敗與範本錯誤，顯示推論基準測試需要持續的軟體驗證，結果也會隨引擎版本與適配器狀態而變動。此外，較新的模型架構目前只有較少的引擎支援，這限制了對最新模型家族的比較廣度。

**Q14：SiliconBench 觀察到哪些具體的失敗或退化案例？**
A：部分引擎因缺乏連續批次處理或嚴謹的記憶體管理，在並發負載下會顯著變慢甚至請求失敗。即使設定了明確記憶體上限，某些堆疊仍會讓記憶體使用逼近實體容量，雖然完成所有請求，但吞吐量已經下降且系統餘量不足。在多節點實驗中，透過 TCP 的流水線並行出現效能迴歸；而早期測試中也有五次執行因相依性問題或範本錯誤而需要修復。

**Q15：未來可以朝哪些方向延伸 SiliconBench？**
A：未來可擴充更多模型架構與推論引擎，特別是加強 Metal 核心開發工具對新注意力架構的支援，以縮短 Apple Silicon 與 CUDA 在模型覆蓋率上的差距。記憶體評估也可進一步納入更細緻的餘量指標與自動化壓力測試，幫助使用者預判前景應用程式是否會受影響。此外，多節點擴展可測試更大規模叢集與更高速互連，同時持續優化結合有界 Agent 修復與人工審查的維護流程，以提升基準的長期可持續性。

## 實務應用指南

### 適用場景

1. **本機程式設計 Agent 叢集**  
   開發團隊在 Mac Studio 或 Mac Pro 上同時執行 4–16 個程式設計 Agent，每個 Agent 都對本地 LLM 發出請求。此時需要的不只是單一請求速度，而是高並行下的吞吐量與記憶體餘量，避免 IDE、瀏覽器與 macOS 被擠壓。

2. **隱私優先的企業內部對話助理**  
   法務、醫療或金融單位在統一記憶體桌面（Apple Silicon 或 DGX Spark）上部署內部聊天機器人，要求資料不離機。需要同時評估速度、記憶體佔用，以及相對 NVIDIA 參考實作的輸出保真度，確保回答品質不因本地引擎而下降。

3. **邊緣多節點大型模型服務**  
   當單機統一記憶體無法容納大型 Dense 或 MoE 模型時，使用兩台以上 Mac 透過 Thunderbolt RDMA 做張量並行（Tensor Parallelism），把推理分散到多機，同時監控記憶體紀律與首 token 延遲。

4. **模型上線前的品質閘道**  
   在 MLOps CI 流程中，把 SiliconBench 的分類任務與保真度門檻當作迴歸測試：每次更新推論引擎或量化設定後，自動比對 NVIDIA 參考實作，確保新任務層級分數沒有品質迴歸。

5. **教育或研究用的本地小模型評測平台**  
   研究者或學生在資源有限的 Apple Silicon 筆電上，針對 Qwen3-0.6B、Qwen3.5-0.8B 或 Gemma-4-E4B-it 等輕量模型，快速比較九種引擎的實際表現，並學習連續批次處理、KV 快取配置與記憶體預算的影響。

### 實作前置條件

- **硬體**：至少一台 Apple Silicon Mac（建議 32 GB 以上統一記憶體），若要進行多節點擴展則需兩台以上支援 Thunderbolt 的機器；可選配 DGX Spark 作為 CUDA 參考軌。
- **軟體**：macOS、Python 3.10+、Docker（部分引擎需要）、Git、Homebrew；準備好至少一個要測試的引擎，例如 `vllm-metal`、`ollama`、`mlx_lm`、`omlx`、`sglang`、`llama.cpp`、`mistral.rs` 等。
- **模型與資料**：從 Hugging Face `mlx-community` 或官方倉庫取得 Qwen3、Qwen3.5、Gemma 4 等模型的 MLX 或 HF 格式；準備對話與 Agent 兩類提示詞，以及用於保真度檢驗的分類任務與標準答案。
- **參考基準**：若要做輸出保真度比對，需先取得 NVIDIA 參考實作（如 A100 或 DGX Spark 上的 CUDA vLLM / SGLang）在同一模型與提示詞下的輸出。
- **技能**：熟悉 Python 指令列、基本 shell 腳本、Docker 操作；了解 LLM 推論的 prefill/decode 概念、KV 快取、連續批次處理；具備閱讀維護日誌與排查 adapter 錯誤的能力。

---

### 實作步驟建議

1. **定義工作負載與成功指標**  
   決定要測的是對話（chat）還是 Agent 推論服務，並設定並行度範圍（建議 1、2、4、8、16）。同時定義「完成率」、「吞吐量」、「記憶體餘量」、「首 token 延遲」與「分類任務正確率」等門檻。

2. **依據引擎特性做初選**  
   參考 Table 1 的提示詞批次處理、KV 快取配置、prefill/decode 方式與記憶體策略。例如需要高並行與記憶體紀律時，優先考慮支援打包 token（packed tokens）、分頁式 KV 快取與同一 pass 的 `vllm-metal`。

3. **設定記憶體預算並執行並行掃描**  
   為每個引擎設定明確記憶體上限（explicit cap），從並行度 1 跑到 16，記錄吞吐量、延遲、完成率與實際記憶體佔用。特別注意記憶體接近實體容量時，吞吐量是否衰退或請求失敗。

4. **進行保真度檢驗**  
   在相同溫度與抽樣參數下，讓各引擎與 NVIDIA 參考實作執行同一批分類任務，比對任務層級分數。設定保真度門檻，淘汰輸出品質明顯下降的組合。

5. **檢查模型覆蓋率**  
   確認目標模型（尤其是 Qwen3.5、Gemma 4 等新架構）是否被選定引擎支援。新模型架構的引擎支援通常較窄，需預留轉換或 adapter 開發時間。

6. **執行多節點擴展測試（如需要）**  
   對於單機放不下的模型，測試張量並行（Tensor Parallelism）與流水線並行（Pipeline Parallelism）。根據論文結果，優先使用 Thunderbolt RDMA 的張量並行，避免使用 TCP 的流水線並行。

7. **建立維護與持續驗證流程**  
   採用「有界 Agent 修復 + 人工審查」的維護日誌機制：由 Agent 在限定範圍內提出 adapter 修正，研究人員審查後重新產生官方結果，並公開每次執行結果與維護日誌。

8. **部署與監控**  
   選出通過完成率、保真度與模型覆蓋率三大門檻的引擎後，以 OpenAI 相容 API 形式部署，並持續監控 macOS 記憶體壓力與前景應用程式反應。

### 潛在風險與注意事項

- **明確記憶體預算不保證餘量**：即使設定了 explicit cap，某些引擎在並發負載下仍會把記憶體用到接近實體容量，導致 macOS 記憶體壓力升高、吞吐量衰退，甚至影響前景應用程式。建議預留 20–30% 實體記憶體給系統與其他程式。
- **並發下的品質迴歸**：高並行不一定只影響速度，某些批次處理或量化路徑可能改變輸出分布。務必用分類任務持續比對 NVIDIA 參考實作，設立保真度門檻。
- **新模型支援不完整**：Qwen3.5、Gemma 4 等較新架構在 Apple Silicon 上的 Metal kernel 支援可能落後於 CUDA，需確認引擎版本與模型轉換狀態。
- **Adapter 與模板錯誤**：論文提到早期執行曾出現依賴失敗與模板錯誤。正式上線前應跑完整端到端測試，並保留維護日誌以便回溯。
- **多節點擴展方式選錯**：流水線並行透過 TCP 可能反而衰退；若要做跨機擴展，應優先評估 Thunderbolt RDMA 的張量並行。
- **過度優化單一指標**：只追求吞吐量可能犧牲記憶體餘量或保真度。建議以完成率、保真度、模型覆蓋率三大門檻先篩選，再比較速度。

---

### 與其他技術的整合建議

- **API 閘道與負載平衡**：將 `vllm-metal`、`ollama` 等支援 OpenAI 相容 API 的引擎置於反向代理（如 Nginx、Traefik）後方，讓程式設計 Agent 或聊天前端無縫切換底層引擎。
- **IDE 與 Agent 工具鏈**：透過標準 HTTP API 把本地 LLM 接到 Continue、Cline、LangChain、AutoGen 等 Agent 框架，並設定並行請求上限以避免壓垮單機。
- **模型倉庫與轉換**：使用 Hugging Face `mlx-community` 的預轉換模型，或自行用 `mlx_lm` 轉換新模型；在 CI 中自動下載並驗證 checksum。
- **評測框架**：把 SiliconBench 的分類任務與提示詞整合進 `lm-evaluation-harness` 或自訂 pytest 流程，作為每次引擎升級的迴歸測試。
- **監控與可觀測性**：透過 macOS `memory_pressure`、Activity Monitor 或自訂腳本收集統一記憶體使用率；對多節點場景則監控 Thunderbolt 網路延遲與 RDMA 頻寬。
- **混合雲備援**：對於 Apple Silicon 無法支援的模型或並行度，可設定 fallback 到 DGX Spark 或雲端 CUDA vLLM，確保服務不中斷。

---

### 給不同背景讀者的閱讀建議

- **初學者**：先從論文引言、詞彙表與 Table 1 開始，理解「速度、記憶體、保真度」為何同樣重要，並認識九種引擎在提示詞批次處理與記憶體策略上的基本差異，不必急著深入 kernel 細節。

- **AI 工程師**：重點閱讀第 3 節三大設計準則與第 6 節測量結果，特別關注 `vllm-metal` 的打包式預填—解碼路徑、並行度 1→16 的吞吐量變化、記憶體紀律實測，以及 Thunderbolt RDMA 張量並行的多節點配置。

- **研究人員**：聚焦方法論、分類任務的保真度設計、維護日誌與有界 Agent 修復流程，思考如何將 SiliconBench 擴展到更多模型架構、更長上下文或異質硬體叢集，並檢視論文對輸出漂移與 benchmark 過時問題的處理。

- **產品經理**：掌握三大門檻（完成率、保真度、模型覆蓋率）與最終只有三個堆疊通過審核的結論，據此評估技術選型對使用者體驗、硬體成本與記憶體餘量的影響，並把「保留前景應用程式可用記憶體」當作產品規格的一部分。
