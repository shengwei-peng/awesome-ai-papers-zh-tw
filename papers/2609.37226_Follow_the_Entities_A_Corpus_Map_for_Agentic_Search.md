## 摘要翻譯

在大型文件集合（corpus）上回答問題與完成任務，通常需要連結分散於多篇文件（documents）中的證據；例如，某專案的核准記錄於一份文件、其需求載於另一份文件，而最新狀態則出現在第三份文件中。近期的 LLM 代理（LLM agents）透過反覆搜尋整個語料庫（corpus）來處理此問題，而非僅閱讀一組固定的前 k 篇文件（top-k documents）。然而，當語料庫僅以扁平化文件集合（flat collection of files）的形式呈現時，一份相關文件無法顯示它與其他文件的關聯，因此代理必須針對每個查詢（query）重新發現這些關係，經常遺漏互補證據（complementary evidence），同時消耗大量額外 Token。為此，我們提出 CorpusMap，一種以語料庫中反覆出現的實體（recurring entities）為中心來組織語料庫的導航層（navigation layer）；這些實體可從文件本身辨識，並能將單一文件連結到來自不同來源的多份其他文件。具體而言，CorpusMap 將每個反覆出現的實體表示為一個實體頁面（Entity Page），該頁面彙整關於此實體的資訊，並連結到所有提及它的文件，形成實體–文件圖（entity-document graph），讓代理能夠沿著圖形遍歷，以收集原本互不相連的證據。此外，由於 CorpusMap 是透過跨文件指稱消解（mention resolution）來離線建構（offline construction），其連結可跨查詢共享（shared across queries），而無需在推論時間（inference time）反覆重新發現。我們使用 7 種不同的模型與 3 個基準資料集（benchmark datasets），結果顯示 CorpusMap 相較於原始語料庫代理式搜尋（raw-corpus agentic search），在提升證據發現（evidence discovery）與答案品質（answer quality）的同時，平均消耗更少的 Token，並進一步優於 4 種替代的導航層，顯示實體可作為導航大型文件集合的有效錨點。

### 核心貢獻（3～5點）
- 提出 CorpusMap，一種以反覆出現實體為中心的語料庫導航層，將語料庫組織為可遍歷的實體–文件圖。
- 透過離線建構與跨文件指稱消解，使實體連結能跨查詢共享，避免在推論時間重複發現關係。
- 在 7 種模型與 3 個基準資料集上驗證，CorpusMap 能同時提升證據發現與答案品質，並降低 Token 消耗。
- 相較於 4 種替代導航層，CorpusMap 表現更優，顯示實體是導航大型文件集合的有效錨點。

### 適合對象
從事檢索增強生成（RAG）、LLM 代理與多文件問答系統研究與開發的學術研究者與工程師，特別是關注如何提升跨文件證據發現效率、降低推論成本，以及設計語料庫層級導航結構的讀者。

## 深度分析

#### 方法論解析

本研究提出的 **CorpusMap（語料庫地圖）** 並非另一個檢索器（retriever），而是一個疊加在原始語料庫之上的**導航層（navigation layer）**。其核心設計理念是：大型文件集合中的問題答案，往往分散在多份文件內，而這些文件之間的關聯性通常透過「反覆出現的實體（recurring entities）」——例如人名、專案名稱、產品名稱、部門、客戶等——隱性地連結在一起。CorpusMap 把這些實體抽取出來，轉換成可查詢、可遍歷的節點，從而讓 **LLM 代理（LLM agents）** 在回答問題時，能夠沿著**實體–文件路徑（entity-document path）**主動發掘**互補證據（complementary evidence）**，而不是每次都在**扁平化文件集合（flat collection of files）**中重新摸索。

##### 離線建構流程

CorpusMap 的建構完全在**離線建構（offline construction）**階段完成，主要包含四個步驟：

1. **實體提及偵測（Entity Mention Detection）**  
   對每份文件進行分析，找出其中提及的實體。這一步並不一定需要 LLM，可以使用命名實體辨識（NER）、名詞片語抽取、規則樣式或輕量級嵌入模型來完成。由於強調「可離線、可增量、無需 LLM」，推測作者採用的是較輕量且可解釋的抽取方式，而非昂貴的生成式摘要。

2. **跨文件指稱消解（Cross-document Mention Resolution / Coreference）**  
   將不同文件中指稱同一對象的提及合併為同一個實體。例如，某份郵件中的 “Project Atlas”、某份狀態報告中的 “Atlas migration”、以及會議紀錄中的 “the Atlas project” 都應被解析為同一個實體。這是整個方法成敗的關鍵：若消解錯誤，後續的實體頁面會混入無關文件，或遺漏關鍵文件。

3. **實體頁面生成（Entity Page Generation）**  
   每個被解析出來的實體會對應到一個 **Entity Page（實體頁面）**。該頁面彙整了所有提及此實體的文件片段，並且保留**來源文件（source documents）**的歸屬資訊。換言之，Entity Page 不是無來源的摘要，而是帶有出處標註的聚合檢視。這讓代理在後續推理時，可以追溯每個事實的原始出處，降低幻覺風險。

4. **實體–文件圖組裝（Entity-Document Graph Construction）**  
   最終形成一個二分圖（bipartite graph）：一側是實體節點，另一側是文件節點；若某文件提及某實體，則兩者之間存在一條邊。這個 **entity-document graph（實體–文件圖）** 就是 CorpusMap 的導航骨幹。

##### 查詢時導航機制

在推論階段，當使用者給出一個 **Query（查詢）** 時，代理的運作方式與傳統 **agentic search（代理式搜尋）** 不同：

- **起點**：代理首先辨識 Query 中明確或隱含提到的實體，然後直接打開對應的 Entity Page。
- **沿著實體–文件路徑走訪**：Entity Page 會列出所有提及該實體的文件。代理可以選擇打開最相關的文件；在閱讀文件後，又可發現文件中提到的其他實體，再跳轉到這些實體的 Entity Page，形成「實體 → 文件 → 實體 → 文件」的走訪路徑。
- **保留原始文件存取權**：CorpusMap 是「 additive layer（疊加層）」，並未取代原始語料庫。代理仍然可以隨時回到原始文件進行細讀，確保不會因為聚合而遺失細節。

這種設計的關鍵優勢在於「關係被預先計算並跨查詢共享」。傳統 **raw-corpus agentic search（原始語料庫代理式搜尋）** 每次都要透過多次 **tool call（工具呼叫）** 與搜尋來重新發現「哪些文件講到同一個專案」；CorpusMap 則把這些關係在離線階段固定下來，查詢時直接複用，從而減少重複檢索與重複閱讀。

##### 設計上的幾個重要選擇

- **以實體為錨點（entity as anchor）**：實體是跨文件最穩定、最容易自動識別的連接點。相較於主題、事件或時間軸，實體的邊界較明確，也較容易透過無監督或輕量監督方法抽取。
- **離線計算、線上複用**：這讓 **inference time（推論時間）** 的 **token consumption（Token 消耗量）** 大幅下降，因為代理不需要反覆搜尋與重新發現關係。
- **來源歸屬（source attribution）**：Entity Page 中的每個事實都連回原始文件，這對企業場景中的可解釋性與可信度非常重要。
- **可增量更新**：隨著語料庫新增或修改文件，可以只對受影響的實體進行局部更新，而不需要全量重建。

#### 實驗數據解讀

本研究在三個 **benchmark datasets（基準資料集）**——EnterpriseRAG-Bench、WixQA 與 HERB——上，使用七種不同的 LLM 進行評估。雖然摘要中未詳細說明每個模型的名稱與每個資料集的題目數量，但從結果趨勢可以歸納出以下重點。

##### 評估指標

作者主要報告兩類指標：

1. **Answer quality（答案品質）**：衡量最終答案是否正確、完整。雖然具體是採用 F1、Exact Match（EM）、還是 LLM-as-judge 並未在提供的片段中詳述，但從「6.4 到 11.7 點的提升」來看，應該是某種百分制或標準化分數。
2. **Evidence discovery（證據發現）**：衡量代理是否成功找到回答問題所需的黃金文件集合。這對於多文件問答任務特別重要，因為若遺漏關鍵文件，即使生成模型再強也難以回答正確。
3. **Token consumption（Token 消耗量）**：特別是 input tokens，用來衡量代理在檢索與推理過程中的成本與效率。

##### 主要結果

- 與 **raw-corpus agentic search（原始語料庫代理式搜尋）** 相比，CorpusMap 在整體答案品質上提升了 **6.4 至 11.7 點**。
- 同時，平均 input tokens 減少了 **34% 至 57%**。
- 在 **evidence discovery（證據發現）** 上也有改善，表示 CorpusMap 確實幫助代理找到更多原本會被遺漏的互補證據。
- CorpusMap 也優於四種替代的導航層設計，包括 **LLM Wiki** 與 **Corpus2Skill**。

##### 結果意義

這組數據傳達了兩個同等重要的訊息：

1. **結構化導航能提升答案品質**：單純給代理「完整語料庫存取權」並不足以解決多文件證據整合問題。當語料庫以實體為中心被組織後，代理更容易發現分散的證據，從而提升答案正確性與完整性。
2. **更好的結構也能降低成本**：傳統觀念常認為，提升檢索品質需要更多迭代、更多工具呼叫、更多 tokens；但 CorpusMap 顯示，若把跨文件關係預先結構化，反而可以減少重複搜尋，達到「品質更高、成本更低」的雙贏。

##### 需要注意的細節

由於目前僅能看到摘要與引言，以下細節仍有待完整論文釐清：

- **品質分數的絕對值與變異數**：6.4–11.7 點的提升在不同模型與資料集上是否一致？是否存在某些模型對 CorpusMap 特別敏感？
- **Token 減少的來源**：是來自較少的搜尋步驟、較少的重複閱讀，還是 Entity Page 本身比多次搜尋結果更精簡？
- **錯誤分析**：CorpusMap 在哪些類型的問題上幫助最大？在哪些問題上可能反而因為實體消解錯誤而表現變差？

#### 與現有研究的比較

##### 相較於傳統 RAG 與 GraphRAG

傳統 **retrieval-augmented generation (RAG)（檢索增強生成）** 通常根據 Query 的語義相似度，檢索出 **top-k documents（前 k 篇文件）** 後直接生成答案。這種方式在證據集中於單一文件時效果很好，但當答案需要整合多份文件時，容易遺漏關鍵文件。

近年來的 **GraphRAG** 與 **HippoRAG** 等圖形化 RAG 方法，雖然也會抽取實體與關係並建立圖，但它們的圖主要用於「改進檢索器內部的選擇」，最終仍把固定的一組段落或摘要餵給生成器。換言之，生成器無法主動在圖上導航，也無法在檢索遺漏時自行補救。CorpusMap 的差異在於：**把 entity-document graph（實體–文件圖）直接暴露給 LLM 代理**，讓代理能夠在推論過程中動態走訪、修正與擴展證據集合。

##### 相較於原始語料庫代理式搜尋

現有的 **agentic search（代理式搜尋）** 已經讓代理能透過多次 **tool call（工具呼叫）** 主動搜尋完整語料庫，不再受限於初始檢索結果。然而，由於語料庫對代理而言仍是一個 **flat collection of files（扁平化文件集合）**，代理必須自行透過關鍵字猜測、閱讀、推理來重建文件間關係。這不僅耗費大量 tokens，也容易在每次查詢時重複發現相同的關聯。CorpusMap 把這些關係預先結構化並跨查詢共享，從根本上改變了代理與語料庫的互動方式。

##### 相較於 LLM Wiki 與 Corpus2Skill

作者特別提到 CorpusMap 優於四種替代導航層，其中包括：

- **LLM Wiki**：這類方法通常使用 LLM 自動生成類似維基百科的條目。雖然能提供高可讀性的摘要，但生成過程可能產生幻覺、失去來源歸屬，且建構成本高昂。CorpusMap 則強調來源歸屬，並可在不使用 LLM 的情況下建構。
- **Corpus2Skill**：這類方法可能以「技能」或「任務」為中心組織語料庫。相較之下，CorpusMap 以「實體」為中心，更貼近文件自然生成的結構，也更容易自動維護。

##### 限制與潛在弱點

儘管 CorpusMap 的設計很有吸引力，仍存在以下限制：

1. **過度依賴實體**：若問題的關鍵連結不是實體共現，而是時間順序、因果關係、主題相似性或隱含語境，CorpusMap 可能無法提供有效導航。
2. **指稱消解錯誤會被放大**：跨文件 **mention resolution（指稱消解）** 一旦出錯，錯誤的 Entity Page 會把代理導向不相關文件，且這些錯誤在離線階段就已固定。
3. **熱門實體的頁面過大**：對於在大量文件中出現的實體（如公司名稱、執行長姓名），Entity Page 可能非常長，反而增加閱讀負擔。如何對 Entity Page 進行分層或摘要，是實際部署時需要考慮的問題。
4. **僅有實體–文件邊**：目前的圖是二分圖，缺少實體與實體之間的關係邊（例如「A 是 B 的經理」、「X 專案依賴 Y 專案」）。這些關係對某些複雜推理任務可能同樣重要。

##### 程式碼與資料集公開狀況

從目前提供的片段來看，作者並未在摘要或引言中提供開源程式碼、資料集或模型權重的連結。論文標示為 Preprint，因此尚無法確定最終版本是否會釋出：

- **資料集**：EnterpriseRAG-Bench、WixQA、HERB 三個 **benchmark datasets（基準資料集）** 的可取得性不一。WixQA 可能較容易公開取得；EnterpriseRAG-Bench 與 HERB 若來自企業內部或包含敏感文件，則可能無法完全公開，這會限制外部驗證。
- **模型權重**：實驗使用七種不同模型，很可能包含 GPT-4、Claude、Gemini 等專有 API 模型。這些模型的權重不公開，且 API 行為可能隨時間變化，影響長期可重現性。

##### 再現難度

即使資料與程式碼部分公開，要完全重現仍有挑戰：

- **離線建構的參數與閾值**：實體抽取與消解過程中涉及許多超參數（如相似度閾值、共指距離、頁面大小限制），這些細節對結果影響很大。
- **代理導航策略**：代理如何決定下一步要打開哪個 Entity Page 或文件？是貪婪、啟發式，還是有學習機制？不同的策略會顯著影響 evidence discovery 與 token consumption。
- **API 版本與提示詞**：若使用專有模型，提示詞（prompt）與 API 版本會影響結果，而這些細節通常難以完全固定。

總體而言，本研究的概念與方法描述相對清楚，但要達到嚴格的可重現性，仍需作者釋出完整的建構流程、代理策略程式碼與評估腳本。

#### 未來研究方向

基於 CorpusMap 的設計與限制，可以延伸出以下幾個值得探索的方向：

1. **引入實體間關係邊**  
   目前的圖僅連結實體與文件。未來可進一步抽取實體之間的關係（例如「負責人」、「依賴」、「隸屬於」），形成更豐富的知識圖譜，讓代理能進行更深層的多跳推理（multi-hop reasoning）。

2. **學習式導航策略**  
   目前代理沿著實體–文件路徑的走訪策略可能是基於啟發式規則。未來可以透過強化學習或模仿學習，訓練代理學會在 Entity Page 與文件之間做出更精準的選擇，進一步提升效率與準確率。

3. **動態與增量維護**  
   雖然作者提到 CorpusMap 可增量更新，但具體如何處理實體合併、分裂、廢棄與版本控制，仍是實際部署中的開放問題。特別是在企業環境中，文件持續新增與修改，如何保持 Entity Page 的即時性與一致性值得深入研究。

4. **分層與可縮放的 Entity Page**  
   對於熱門實體，Entity Page 可能過於龐大。未來可研究如何自動生成多層次摘要、依據查詢動態篩選相關片段，或結合向量索引讓代理只讀取最相關的部分。

5. **與生成式摘要的結合**  
   CorpusMap 目前強調不使用 LLM 建構，以保持來源歸屬與低成本。但未來可以探索「輕量抽取式骨幹 + 選擇性 LLM 增強摘要」的混合架構，在需要時為代理提供更高階的語義整合。

6. **多模態與跨語言實體**  
   企業語料庫中常包含表格、圖片、簡報、聊天記錄等非文字內容。如何將這些多模態資訊納入 Entity Page，以及如何处理跨語言的同一實體，都是實用且具挑戰性的方向。

7. **使用者回饋與個人化導航**  
   不同使用者對同一實體的關注點不同。未來可讓 CorpusMap 根據使用者角色、歷史查詢與回饋，動態調整 Entity Page 的呈現順序與導航建議。

8. **開源實作與標準化評估**  
   建立開源的 CorpusMap 實作框架，並在更多公開資料集上進行標準化評估，將有助於社群驗證、比較與改進這類實體中心導航方法。

總結來說，CorpusMap 提出了一個從「改進搜尋演算法」轉向「改進語料庫結構」的重要視角。透過把反覆出現的實體轉化為可重複使用的導航錨點，它不僅提升了多文件問答的答案品質，也顯著降低了代理的 Token 消耗，為未來的企業級知識問答系統提供了一個兼具效率與可解釋性的設計範式。

## 論文問答

**Q1：這篇論文試圖解決什麼核心問題？**

A：論文聚焦於「如何在大型語料庫中回答需要跨文件串連證據的複雜問題」。現實中，一個問題的答案往往分散在多份文件裡，例如專案核准信、需求規格與最新狀態更新分別存在不同系統；這些文件彼此之間的關係通常不會在單一文件內明確寫出，而且整個語料庫可能包含數十萬份雜亂的檔案。因此，真正的挑戰不只是理解個別文件內容，還要在茫茫文件海中「找到」並「連結」這些互補證據。

**Q2：傳統 RAG 與原始語料庫代理式搜尋為何不足以應對這個挑戰？**

A：傳統檢索增強生成（RAG）通常只根據查詢召回前 k 篇文件，一旦關鍵證據未被初始檢索命中，模型就無從得知。代理式搜尋雖然能透過多輪工具呼叫反覆搜尋完整語料庫，但語料庫對代理而言仍是一堆扁平化的文件，文件之間的關係必須在每次查詢時重新推論與發現。這不僅容易遺漏需要跨文件才能拼湊出的互補證據，也會讓代理反覆閱讀相同內容，造成大量額外的 token 消耗。

**Q3：為什麼作者主張應該建立「持續存在的導航層」，而非僅僅改進搜尋演算法？**

A：因為文件之間的關係（例如哪些文件都提到同一個專案）在大多數查詢下是穩定不變的，沒有必要每次推論時都重新發現。如果能在離線階段把這些跨文件結構顯式地建構出來，查詢時就能重複使用，既提升效率也減少遺漏。此外，導航層是在原始語料庫之上增加一層結構，並不取代原始文件，所以代理仍然可以回到完整語料庫進行細部查證。

**Q4：CorpusMap 的核心方法是什麼？**

A：CorpusMap 是一種以實體為中心的語料庫導航層，它會在離線階段辨識每份文件中的實體提及，並把跨文件指稱同一個實體的 mention 解析、合併為同一個實體。每個解析後的實體會被表示成一個「實體頁面」（Entity Page），頁面中彙整了不同文件對該實體的陳述，並標註來源，同時連結到所有提及該實體的文件。這些實體頁面與文件之間的連結形成了一張可遍歷的實體–文件圖，供代理在查詢時沿著實體路徑尋找證據。

**Q5：相較於 GraphRAG 等圖形化 RAG 方法，CorpusMap 的關鍵創新在哪裡？**

A：GraphRAG 這類方法雖然也會抽取實體與關係，但主要是把圖結構用在「檢索器」內部，最後仍把固定的一組段落或摘要送給生成模型。CorpusMap 則把實體–文件圖直接「暴露」給代理，讓代理能主動沿著連結在圖中移動，從一份文件跳到另一份相關文件。這種設計讓代理有機會發現檢索器原本可能遺漏的跨文件證據，而不是只能被動接受一次檢索的結果。

**Q6：作者為什麼選擇「實體」作為語料庫導航的錨點？**

A：因為文件本來就是圍繞著人、專案、產品等共同實體產生的，實體能自然地把單一文件連結到許多其他相關文件。更重要的是，這些實體可以只從語料庫本身辨識出來，不需要依賴特定查詢，因此導航層可以完全離線建構。這種查詢無關、可重複使用的特性，使實體成為穩定且有效的導航錨點。

**Q7：論文在哪些基準資料集上驗證 CorpusMap？**

A：作者使用了 EnterpriseRAG-Bench、WixQA 與 HERB 三個基準資料集，這些資料集都包含需要跨越多份文件才能回答的複雜企業情境問題。它們涵蓋了不同領域與文件來源，例如專案追蹤、電子郵件、會議紀錄與營運文件等，能夠測試證據發現與答案品質。透過在這三個資料集上進行實驗，作者得以證明 CorpusMap 的效益具有跨領域的穩定性。

**Q8：CorpusMap 相較於原始語料庫代理式搜尋帶來哪些關鍵量化結果？**

A：在七個不同的模型上，CorpusMap 相較於原始語料庫代理式搜尋，整體答案品質提升了 6.4 到 11.7 分，同時平均輸入 token 使用量減少了 34% 到 57%。這表示 CorpusMap 不僅讓代理找到更多正確證據，也讓搜尋過程更有效率。這些結果顯示，改善語料庫的組織方式能同時提升效能與成本效益。

**Q9：論文是否比較了其他導航層或進行消融實驗？結果如何？**

A：是的，作者將 CorpusMap 與四種替代導航層進行比較，包括 LLM Wiki 與 Corpus2Skill 等，結果顯示 CorpusMap 在證據發現與答案品質上均優於這些方法。此外，論文也指出 CorpusMap 可以在不使用 LLM 的情況下建構，並且能隨著語料庫增長進行增量更新。這些特性讓它在實際部署環境中更具可行性與擴展性。

**Q10：能否舉一個 CorpusMap 在實務中運作的具體例子？**

A：論文圖 2 展示了一個企業場景：使用者詢問「Atlas 遷移為何延遲？」，代理首先從查詢中辨識出「Project Atlas」這個實體，並透過實體頁面找到 Q3 狀態報告、部署紀錄與相關郵件。接著，代理沿著「J. Chen」這位負責人的實體頁面，發現他在 11 月 6 日的 standup 紀錄中因基礎設施審查被卡住。最後，代理把這些分散在不同文件中的資訊拼湊起來，得出「Atlas 延遲是因為負責人 J. Chen 的基礎設施審查受阻」的答案。

**Q11：從產品化與部署的角度，CorpusMap 有哪些優勢？**

A：CorpusMap 在離線階段預先建構，查詢時只需重複使用已建立好的實體–文件連結，因此能顯著降低推論階段的 token 成本與延遲。它還支援增量更新，當語料庫新增或修改文件時，不需要從頭重建整張地圖。此外，CorpusMap 不需要依賴 LLM 來建構，這讓它在成本、速度與可擴展性上更適合大型企業環境。

**Q12：這項研究對代理式搜尋領域可能帶來什麼影響？**

A：這項研究把焦點從「如何讓代理搜得更好」轉移到「如何讓語料庫本身更容易被導航」，開啟了語料庫組織與代理設計並重的研究方向。它證明了實體可以作為穩定且可重複使用的導航錨點，讓代理在大型文件集合中更有效地發現跨文件證據。這種思路可能影響未來企業知識管理、智慧助理與企業搜尋產品的設計。

**Q13：CorpusMap 有哪些潛在限制或依賴條件？**

A：CorpusMap 的效果高度依賴實體提及辨識與指稱消解的準確度，如果系統錯誤地把兩個不同實體合併，或漏掉某個重要實體，代理就可能沿著錯誤的路徑搜尋。此外，它主要捕捉以實體為中心的關係，對於不依賴具名實體的隱含關係或抽象主題連結可能較弱。離線建構雖然節省推論成本，但也需要額外的預處理與儲存開銷。

**Q14：在哪些情況下 CorpusMap 可能表現不佳或失敗？**

A：當問題的答案取決於非實體性的隱含脈絡，例如某種情緒趨勢、時間序列中的細微變化，或文件之間的因果關係沒有透過共同實體表達時，CorpusMap 的導航路徑可能無法觸及關鍵證據。如果語料庫中充滿指稱模糊、縮寫或代名詞，指稱消解錯誤也會導致實體頁面資訊不完整或連結錯誤。另外，對於非常罕見、只出現在一兩份文件中的實體，實體頁面能帶來的跨文件連結效益也會相對有限。

**Q15：未來可以朝哪些方向延伸或改進 CorpusMap？**

A：未來可以進一步豐富實體頁面中的關係類型，例如加入時間軸、事件順序或因果關係，讓代理能進行更複雜的推理。也可以結合動態更新機制與使用者回饋，讓語料庫地圖隨著新文件與新查詢持續演化。此外，將 CorpusMap 與查詢導向的檢索策略混合使用，或許能在保持跨文件導航優勢的同時，進一步提升對特定問題的適應性。

## 實務應用指南

### 適用場景

1. **企業內部知識問答**  
   當員工詢問「Project Atlas 為何延遲？」時，答案可能分散在電子郵件、專案追蹤系統、會議紀錄與法務合約中。CorpusMap 可透過實體頁面把「Project Atlas」「J. Chen」「Acme MSA」等相關文件串起，讓代理直接沿著實體–文件路徑找到互補證據，而不必反覆搜尋整個語料庫。

2. **客戶支援與故障排查**  
   客服代理需要整合產品手冊、內部維運日誌、工單與聊天頻道中的資訊。以產品名稱、事件編號或客戶名稱作為實體錨點，CorpusMap 能幫助代理快速定位跨系統的相關文件，減少遺漏關鍵線索。

3. **法規遵循與合約審查**  
   合規查詢常需比對法條、內部政策、合約條款與審計報告。透過離線建構的實體–文件圖，代理可以從某份合約中的供應商名稱，連結到採購紀錄、風險評估與最新往來郵件，提升證據發現的完整性。

4. **研發與技術文件導航**  
   大型軟體專案的設計文件、API 文件、Issue Tracker 與程式碼註解往往彼此引用。CorpusMap 能把模組、服務名稱、負責人等實體彙整成實體頁面，協助工程師代理追蹤需求從設計到實作的完整脈絡。

5. **醫療或學術文獻綜合**  
   在需要整合多篇論文、病歷或臨床試驗報告的場景中，以疾病、藥物、患者編號或研究機構為實體，可建立跨文件的連結，輔助研究代理彙整分散的證據。

### 實作前置條件

- **資料條件**  
  需要可存取的大型文件集合，且文件間存在反覆出現的實體（如人名、專案、產品、組織）。文件格式應能抽取純文字，例如 PDF、Word、電子郵件、Markdown 或 HTML。若語料庫已具備資料夾或應用程式邊界（engineering/、legal/、operations/），可進一步輔助實體指稱消解。

- **運算資源**  
  離線建構 CorpusMap 需要執行實體辨識、指稱消解與實體頁面生成。雖然論文指出可不用 LLM 完成，但實務上建議至少具備可批次執行的 NLP 管線或小型語言模型 API；查詢階段則需要可呼叫工具的大型語言模型（LLM）代理。

- **技術能力**  
  團隊需熟悉文件解析、資訊抽取、圖資料庫或向量資料庫操作，以及 LLM 代理的工具呼叫（tool call）設計。若要走輕量路線，也需具備規則式或傳統 NLP 的實體連結能力。

- **領域知識**  
  需要有人協助定義「哪些實體類型對業務最有價值」，例如專案名稱、客戶名稱、產品代號等，並提供少量標註資料以驗證指稱消解品質。

### 實作步驟建議

1. **語料庫盤點與清理**  
   先將各來源文件統一解析為結構化文字，記錄來源應用程式、資料夾路徑與時間戳，並移除明顯無法使用的格式或重複內容。

2. **定義實體類型與抽取規則**  
   根據業務場景決定要抽取哪些反覆出現的實體（如人員、專案、產品、組織、事件編號）。可混合使用命名實體辨識模型、正規表示式與內部詞典。

3. **執行跨文件指稱消解**  
   將不同文件中提及同一實體的指稱合併。初期可用字串匹配或規則，進階則可引入嵌入相似度或小型語言模型判斷。此步驟是離線建構的核心，直接影響實體–文件圖的品質。

4. **生成實體頁面與連結**  
   為每個消解後的實體建立實體頁面，彙整各文件對該實體的陳述並標註來源文件，同時建立從實體頁面指向所有來源文件的連結。

5. **設計代理導航工具**  
   讓 LLM 代理能夠透過 tool call 開啟文件、查看文件中提到的實體清單、跳轉到實體頁面，再從實體頁面選擇其他相關文件。確保原始文件與實體頁面都可被代理讀取。

6. **建立增量更新機制**  
   當語料庫新增或修改文件時，只重新處理變動的文件與受影響的實體頁面，避免每次全量重建。可搭配排程或事件驅動的更新流程。

7. **評估與迭代**  
   使用真實查詢評估證據發現率與答案品質，同時監控 Token 消耗量。根據錯誤案例回頭修正實體抽取範圍或指稱消解規則。

### 潛在風險與注意事項

- **指稱消解錯誤**  
  若把兩個不同實體誤判為同一個（例如兩位同名員工），代理會拿到錯誤的互補證據。建議保留置信度分數，對高風險合併加入人工確認或顯示多個候選實體。

- **實體頁面過於龐大**  
  熱門實體可能被大量文件提及，導致實體頁面過長。可對來源文件排序、摘要或分群，避免代理被資訊淹沒。

- **過度依賴實體連結**  
  CorpusMap 是導航層而非取代原始語料庫。代理仍應保留直接搜尋全語料庫的能力，以處理未被實體涵蓋的查詢。

- **隱私與權限問題**  
  實體頁面可能彙整了來自不同權限層級的文件內容。需確保代理只能存取使用者有權限閱讀的來源文件，並在實體頁面中遵守最小權限原則。

- **維護成本被低估**  
  離線建構雖可跨查詢共享連結，但語料庫持續成長時，指稱消解與實體頁面更新仍需監控。建議從小範圍試點開始，再逐步擴大覆蓋範圍。

### 與其他技術的整合建議

- **與 RAG 系統整合**  
  CorpusMap 不取代傳統 RAG，而是作為其導航層。可先以向量檢索找到初始文件，再讓代理利用實體–文件圖擴展到相關文件，彌補單次檢索的遺漏。

- **與 GraphRAG / 知識圖譜整合**  
  若已建置知識圖譜，可將 CorpusMap 的實體頁面視為「文件導向的實體節點」，補充圖譜中缺少的原始文件連結與來源歸因。

- **與企業搜尋引擎整合**  
  將實體頁面與實體–文件連結匯入現有搜尋索引，讓使用者在搜尋結果中看到「相關實體」與「相關文件」面板，提升人機協作效率。

- **與 LLM 代理框架整合**  
  無論使用 LangChain、Semantic Kernel 或其他框架，都可將「開啟實體頁面」「列出文件中的實體」「追蹤實體–文件路徑」設計為標準工具呼叫。

- **與資料治理平台整合**  
  將 CorpusMap 的更新流程接入資料目錄或 ETL 管線，確保新增文件時自動更新實體連結與來源歸因。

### 給不同背景讀者的閱讀建議

**初學者**  
這篇論文提出了一種讓 AI 代理更有效率地「逛」大量文件的方法：先把文件裡反覆出現的人、專案、產品等實體找出來並連結在一起，形成一張地圖；之後代理回答問題時，就可以沿著這張地圖找證據，而不必每次都從頭搜尋整個語料庫。建議先從圖 2 的範例開始理解「離線建構」與「查詢時重複使用」這兩個核心概念，再回頭看實驗結果。

**AI 工程師**  
本文的價值在於把「語料庫組織」與「代理搜尋」分開處理：透過離線的實體指稱消解建立可重複使用的實體–文件圖，並在推論時間以 tool call 方式讓代理沿圖導航。建議重點關注實體頁面的設計、增量更新機制，以及與現有 RAG / 代理框架整合時的工具介面定義，這些是落地時最關鍵的工程決策。

**研究人員**  
論文將多文件問答重新框定為「語料庫導航問題」，並驗證了以實體為錨點的導航層在證據發現與答案品質上的優勢。可進一步探索的問題包括：更複雜的實體關係（如事件時序、因果關係）是否應納入導航層、指稱消解錯誤對下游問答的影響，以及 CorpusMap 在動態語料庫中的理論保證。

**產品經理**  
這項技術適合證據分散在多個系統、且查詢主題圍繞特定人事物的大型文件集合。它的商業價值在於「一次建構、多次查詢」：雖然前期需要投入離線建構成本，但能顯著降低每次查詢的 Token 消耗量並提升答案品質。評估導入時，建議優先選擇查詢頻率高、跨文件證據明確的場景做為試點，並把增量維護成本納入總體擁有成本估算。
