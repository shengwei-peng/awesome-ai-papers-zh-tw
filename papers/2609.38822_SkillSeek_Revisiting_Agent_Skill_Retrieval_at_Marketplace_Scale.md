## 摘要翻譯

Anthropic 的代理技能（Agent Skills）將可重複使用的程序性知識（procedural knowledge）封裝為 SKILL.md 目錄形式，供 LLM 代理（LLM agent）使用，而開源彙整（open-source aggregation）的技能數量已突破 230,000 項，使得「選擇（selection）」而非「編寫（authoring）」成為瓶頸。文獻中既有的做法將選擇外包給代理本身：透過 LLM 媒介檢索迴圈（LLM-mediated retrieval loop），在代理的決策迴圈（decision loop）內重寫查詢並優化候選，每項任務皆需支付 LLM token 成本。我們提出 SkillSeek，一個基於標準 IR 方法（standard IR recipe）建構的開源兩階段技能檢索器（two-stage retriever）——由 BGE-base 雙編碼器（bi-encoder）饋入小型交叉編碼器（cross-encoder），並透過模型上下文協議（MCP）對外提供。於涵蓋候選池（pool）、骨幹網路（backbone）與方法的 4×11 網格搜索（grid search）實驗中，於 89 項任務的 SkillsBench 基準上，SkillSeek 與 Liu 等人（2026b）的 LLM 媒介迴圈達到實質對等的表現，且幾乎不增加額外成本：僅 BM25 即在四種設定中的三種達到或超過其優化迴圈（refined loop）的通過率（pass rate），小型交叉編碼器則在第四種設定上補足剩餘差距。第一階段召回上限（first-stage recall ceiling）解釋了此現象，每次試驗花費（per-trial spend）從 51.30 美元（USD）降至 27.54 美元（與無技能基線（no-skill baseline）相差不到 0.5 美元）。在我們測試的 SkillsBench 任務與 OpenHands 代理框架（agent harness）下，這使標準 IR 方法成為代理技能檢索的強預設選擇（strong default），而 LLM 媒介替代方案則自然適用於確定性方法（deterministic methods）力有未逮的情境。

### 核心貢獻（3～5點）
- **釐清瓶頸轉移**：當開源技能彙整規模突破 230,000 項時，代理技能使用的工作瓶頸已從「編寫技能」轉移至「選擇技能」，凸顯技能檢索（skill retrieval）作為獨立研究問題的重要性。
- **提出 SkillSeek 系統**：設計並開源一套基於標準 IR 方法的兩階段技能檢索器，以 BGE-base 雙編碼器進行第一階段粗排，再以小型交叉編碼器重排序器（cross-encoder reranker）進行精排，並透過 MCP 伺服器（MCP server）對外提供服務，便於與既有代理框架整合。
- **實證對等且大幅節省成本**：在 SkillsBench 89 項任務的 4×11 網格實驗中，SkillSeek 與 Liu 等人（2026b）的 LLM 媒介迴圈達到實質對等的通過率，但每次試驗花費從 51.30 美元降至 27.54 美元，與無技能基線僅相差不到 0.5 美元。
- **解釋效能天花板機制**：透過分析指出第一階段召回上限（first-stage recall ceiling）是決定整體效能的關鍵瓶頸，單純 BM25 即可在多數設定下追平 LLM 媒介優化迴圈，僅需小型交叉編碼器補足剩餘差距。
- **確立方法定位**：主張在當前 SkillsBench 任務與 OpenHands 框架設定下，標準 IR 方法應作為代理技能檢索的強預設選擇（strong default），而 LLM 媒介方法則保留作為確定性方法不足時的自然替代方案。

### 適合對象
- **從事 LLM 代理（LLM agent）系統設計的研究者與工程師**：尤其關注如何讓代理有效運用日益龐大技能庫的實務工作者。
- **資訊檢索（IR）領域學者**：對檢索增強生成（RAG）、雙編碼器（bi-encoder）與交叉編碼器重排序（cross-encoder reranking）等技術在代理場景中的應用感興趣者。
- **代理框架與工具生態開發者**：正在建構或整合 MCP 伺服器、技能發布平台（marketplace / distribution platforms）者，可參考本研究的兩階段檢索器架構與成本效益分析。
- **AI 基礎設施成本優化決策者**：關注 LLM 推理成本（token cost）、上下文窗口（context window）管理與 Token 膨脹（token inflation）等議題的技術主管。
- **學術會議 AACL-IJCNLP 2026 與 NLP / IR 相關會議的與會者**：本論文將於該會議發表，適合關注自然語言處理前沿方法的學術界讀者。

## 深度分析

#### 方法論解析

SkillSeek 的方法論核心在於回歸資訊檢索 (Information Retrieval, IR) 領域的「標準食譜」(standard IR recipe)，並將其包裝為可透過模型上下文協議 (Model Context Protocol, MCP) 暴露給 LLM 代理 (LLM agent) 使用的服務。其架構可拆解為三個關鍵設計決策：

**第一階段：雙編碼器粗排 (Bi-encoder First-stage Retrieval)**

SkillSeek 採用 BGE-base 作為雙編碼器 (bi-encoder)，將技能池 (skill pool) 中的每個 SKILL.md 元數據條目 (metadata entry) 預先編碼為稠密嵌入 (dense embedding)。在查詢階段，使用者任務描述同樣被編碼為向量，透過餘弦相似度從候選池 (pool) 中取出前 20 名 (top-20) 候選技能。此階段的設計哲學是「漸進式載入」(progressive loading) 機制的延伸——只取元數據層級的資訊進行比對，避免在第一階段就消耗大量計算資源於完整技能內容。

**第二階段：交叉編碼器精排 (Cross-encoder Reranking)**

取出的 top-20 候選被送入小型交叉編碼器重排序器 (cross-encoder reranker) 進行精排，最終輸出 top-5 給代理。論文中測試了兩個變體：預設的 bge-reranker-v2-m3 與 Qwen3-Reranker-0.6B。交叉編碼器的優勢在於能同時編碼查詢與文檔，捕捉雙編碼器遺漏的細粒度語義互動，但代價是計算成本較高，因此僅應用於少量候選。

**MCP 介接層**

SkillSeek 透過 MCP 伺服器 (MCP server) 暴露檢索介面，使代理能在不改動自身決策迴圈 (decision loop) 的前提下調用檢索服務。這是與 Liu 等人 (2026b) 的 liu_refined 方法最關鍵的架構差異：後者將檢索邏輯嵌入代理的決策迴圈中，每次任務都需支付 LLM 查詢重寫 (query rewrite) 與迭代優化 (iterative refinement) 的 token 成本；而 SkillSeek 的檢索路徑完全確定性 (deterministic)，零 LLM 調用。

**方法論的關鍵洞察**

作者提出「第一階段召回上限」(first-stage recall ceiling) 來解釋為何簡單方法即可匹敵複雜方法：當正確技能未被雙編碼器或 BM25 召回時，無論第二階段如何精排或 LLM 如何重寫查詢，都無法在靜態檢索框架內補救。Liu 等人的 LLM 媒介迴圈 (LLM-mediated loop) 的真正價值在於「跨技能合成」(cross-skill synthesis)——例如 Terminal-Bench 2.0 案例中，代理將兩個部分相關技能合併為新技能。這種合成能力是確定性方法 (deterministic methods) 結構上無法提供的，但論文的實證結果顯示，此優勢在 SkillsBench 的 89 個任務中極少觸發。

#### 實驗數據解讀

**實驗設計**

論文在 4×11 的網格搜索 (grid search) 上進行評估，涵蓋兩個技能池（192 技能精選集與 34K 技能市場規模集）、多個骨幹網路 (backbone) 模型，以及 11 種方法變體。評測基準為 SkillsBench 的 89 個任務，透過 OpenHands 代理框架 (agent harness) 執行，以 pytest 驗證器回傳 {0, 1} 的獎勵計算通過率 (pass rate)。

**核心數據解讀**

1. **BM25 的意外強健性**：在四個 (池, 骨幹網路) 設定中的三個，純 BM25 的通過率即達到或超過 Liu 等人的 liu_refined 優化迴圈 (refined loop)。這挑戰了文獻中「必須使用稠密嵌入或 LLM 媒介方法」的隱含假設。

2. **SkillSeek 在第四設定的補位**：在 34K 池搭配 Qwen3.5-397B-A17B 的設定中，BM25 略遜於 liu_refined，但 SkillSeek 的 Qwen3-Reranker-0.6B 變體以 0.442 的通過率追平 liu_refined；預設的 bge-reranker-v2-m3 變體則相對無技能基線 (no-skill baseline) 提升 +5.7%，而 liu_refined 為 +9.0%。

3. **成本結構的根本差異**：
   - 無技能基線：$27.41
   - liu_hybrid（代理內混合檢索）：$39.43（+44%）
   - liu_refined（額外精煉代理）：$51.30（+87%）
   - SkillSeek：$27.54（+0.5%，幾乎與基線持平）

4. **Token 膨脹 (Token inflation) 的非單調性 (non-monotonic lift)**：Li 等人 (2026) 報告的數據顯示，1 個相關技能提升 +17.8%，2-3 個提升 +18.6%，但 4 個以上反而下降至 +5.9%。這意味著檢索器的精確率 (precision) 比召回率 (recall) 更關鍵——錯誤技能的負面效應超過正確技能的正向效應。

**第一階段召回上限的實證支持**

若 BM25 與雙編碼器在第一階段即遺漏正確技能，則無論第二階段使用交叉編碼器或 LLM 重排都無法補救。Liu 等人的 LLM 媒介迴圈透過查詢重寫與迭代探索試圖突破此上限，但實證顯示此機制在 SkillsBench 任務上極少產生實質收益——BM25 與 SkillSeek 的表現差異主要來自精排階段，而非來自 LLM 媒介的查詢優化。

**統計顯著性疑慮**

需注意論文中「觀察到平價」(observed parity) 的措辭較為謹慎。89 個任務的樣本規模下，幾個百分點的差異可能落在信賴區間內。論文的網格搜索雖然系統化，但未明確報告信賴區間或假設檢定結果，這是解讀時需保留的空間。

#### 與現有研究的比較

**與 Liu 等人 (2026b) 的定位差異**

Liu 等人的方法代表「將選擇外包給代理」(outsource selection to the agent) 的文獻主流立場，其 liu_hybrid 在代理決策迴圈內執行混合檢索 (hybrid retrieval)，liu_refined 則在任務代理前加入獨立的精煉代理。SkillSeek 的定位是「確定性檢索的對照組」(deterministic-retrieval point of comparison)，兩者共享 BM25 + 稠密嵌入的第一階段，但在重排序器 (reranker) 設計上分道揚鑣：Liu 等人使用 LLM 代理，SkillSeek 使用交叉編碼器。

**與 Zheng 等人 (2026) 的互補性**

Zheng 等人在約 80K 技能的 SkillsBench 衍生池上研究相同的路由問題，發現隱藏技能主體會損失 37-44 點路由準確率，並提出 1.2B 參數的「主體感知」(body-aware) 檢索-重排管線達到 74.0% Hit@1。兩篇工作的關鍵差異有三：(1) Zheng 等人微調自己的編碼器與重排序器，SkillSeek 則是免訓練 (training-free) 且使用現成模型；(2) Zheng 等人未與 LLM 媒介檢索迴圈比較；(3) Zheng 等人未報告 token 或貨幣成本，而這正是 SkillSeek 貢獻的核心軸線。兩者形成互補：Zheng 等人證明主體感知能提升路由準確率，SkillSeek 則證明在標準 IR 食譜下，確定性方法已能在成本效益上匹敵 LLM 媒介方法。

**與 Li 等人 (2026) SkillsBench 的關聯**

Li 等人提出的 SkillsBench 是本論文的評測基準，其報告的「精選技能 +16.2% 平均提升」與「4 技能以上退化至 +5.9%」的非單調性發現，直接支撐了 SkillSeek 對精確率優先的論證。

**與 Han 等人 (2026) 的 SWE 技能發現**

Han 等人發現 49 個公開 SWE 技能中有 39 個對通過率無影響，僅 7 個產生有意義的領域特定增益。這進一步印證了「技能選擇比技能數量更重要」的觀點，與 SkillSeek 的論證方向一致。

**方法論的侷限性**

1. **合成能力的結構性缺失**：Liu 等人在 Terminal-Bench 2.0 案例中展示的跨技能合成能力，是 SkillSeek 確定性框架無法提供的。論文明確承認此點，將 LLM 媒介方法定位為「確定性方法不足時的自然選擇」。

2. **評測範圍的侷限**：實驗僅在 SkillsBench 的 89 個任務與 OpenHands 框架上進行。不同任務領域（如程式設計、數學推理、網頁操作）可能呈現不同的檢索難度分佈。

3. **骨幹網路選擇的代表性**：論文中測試的骨幹網路集中於 Qwen 系列與 Claude 系列，未涵蓋更廣泛的開源模型。

#### 可重現性評估

**程式碼與資料的開放性**

論文明確聲明開源 SkillSeek，包括「重現論文中每個數字的腳本」(scripts that regenerate every number in this paper)，並提供 GitHub 倉庫連結：https://github.com/guanqun-yang/SkillSeek。這是高度負責任的可重現性承諾。

**模型權重的可用性**

SkillSeek 使用的所有模型均為現成 (off-the-shelf) 的公開模型：BGE-base 雙編碼器、bge-reranker-v2-m3 與 Qwen3-Reranker-0.6B 交叉編碼器重排序器。這些模型在 Hugging Face 上均可直接下載，無需自行訓練或微調。

**基準與框架**

評測使用 SkillsBench（公開基準）與 OpenHands（開源代理框架），兩者均有完整的任務定義與執行環境。

**可重現性的潛在障礙**

1. **API 成本的可變性**：論文中報告的美元成本依賴於特定時間點的 LLM API 計價，未來計價變動可能影響絕對數字，但相對比例（SkillSeek 接近基線、liu_refined 接近兩倍）應保持穩定。

2. **34K 技能池的來源**：論文中使用的 34K 技能市場規模池來自 Liu 等人 (2026b) 的爬取 (crawl)，需確認該資料集的公開可用性與版本一致性。

3. **網格搜索的計算資源**：4×11 的網格搜索涉及大量任務執行，完整重現需要相當的計算預算。

**整體評估**

可重現性評估為「優秀」：程式碼、模型、基準、框架均為公開，論文提供了具體的倉庫連結與重現腳本。主要的不確定性在於外部資料集（34K 技能池）的可獲取性與 API 成本的時效性。

#### 未來研究方向

**1. 第一階段召回上限的突破機制**

論文揭示了確定性方法的結構性瓶頸在於第一階段召回。未來研究可探索：(a) 將 LLM 查詢重寫作為「離線索引增強」(offline index augmentation) 而非「線上檢索迴圈」，即預先生成多個查詢變體並建立索引；(b) 結合 Zheng 等人 (2026) 的主體感知方法，將技能主體資訊融入第一階段編碼；(c) 階層式索引 (hierarchical indexing)，先以元數據粗篩，再以主體細篩。

**2. 跨技能合成的確定性近似**

Liu 等人展示的跨技能合成能力是確定性方法的核心缺口。未來可研究：(a) 基於技能依賴圖 (skill dependency graph) 的預組合技能包；(b) 使用小型 LLM 在檢索階段進行「軟合成」(soft synthesis)，即輸出多技能的混合表示而非單一技能；(c) 將合成操作從檢索階段移至執行階段，由代理在讀取多個技能後自行組合，但檢索階段僅負責精準的單技能召回。

**3. 動態技能池的增量索引**

當前實驗使用靜態技能池，但實際市場規模的技能池持續增長（從 47K 到 238K 的爬取記錄）。未來需研究：(a) 增量索引更新 (incremental index update) 的效率；(b) 技能版本控制對檢索一致性的影響；(c) 技能淘汰 (skill deprecation) 機制。

**4. 領域自適應的檢索策略**

SkillsBench 的 89 個任務涵蓋不同領域（程式設計、檔案操作、資料處理等）。未來可研究：(a) 不同領域對 BM25 與稠密檢索的相對偏好；(b) 領域自適應的混合權重 (hybrid weight) 學習；(c) 元學習 (meta-learning) 框架，讓檢索器根據任務類型自動調整策略。

**5. 成本感知的檢索評估**

論文的核心貢獻在於將「成本」納入評估軸線，但目前僅以美元計價。未來可發展更細緻的成本模型：(a) 區分「檢索成本」與「執行成本」；(b) 考慮延遲 (latency) 對代理效能的影響；(c) 在延遲、準確率、成本三維 Pareto 前線上進行系統性分析。

**6. 技能品質的預檢機制**

Han 等人發現 49 個 SWE 技能中 39 個對通過率無影響。若能在檢索階段預先過濾低品質技能，可進一步提升精確率。未來可研究：(a) 基於歷史使用數據的技能品質評分；(b) 技能內容的靜態分析（如測試覆蓋率、文件完整性）；(c) 技能間冗餘度的自動偵測。

**7. 與代理框架的深度整合**

當前 SkillSeek 透過 MCP 暴露，未來可探索更深的整合：(a) 代理主動提供「技能使用反饋」(skill usage feedback) 給檢索器以優化排序；(b) 檢索器根據代理的中間狀態 (intermediate state) 動態調整候選；(c) 多代理協作下的技能共享與檢索快取 (retrieval cache)。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**

A：這篇論文聚焦於「代理技能檢索」（agent skill retrieval）在市場規模下的選擇瓶頸。隨著 Anthropic 推出 Agent Skills 機制並以 SKILL.md 目錄封裝可重複使用的程序性知識，開源彙整的技能數量已突破 23 萬筆，使得「選擇合適技能」取代「撰寫新技能」成為主要瓶頸。論文的出發點是：當技能池膨脹到這種規模時，代理必須具備精準挑選少量相關技能的能力，而非將整個池載入上下文或仰賴人工策展。

**Q2：為什麼現有的 LLM 媒介檢索方法存在不足？**

A：現有文獻的主流做法（以 Liu 等人 2026b 為代表）是將選擇外包給代理本身，由 LLM 在決策迴圈內重寫查詢、迭代精煉候選技能。這種設計雖然在「需要合成新技能」的場景下表現出色（例如將兩個部分相關技能合併為新技能），但代價是每個任務都要支付 LLM token 成本。論文的關鍵觀察是：在 SkillsBench 的 89 個任務中，這種合成優勢其實很少真正派上用場——BM25 在四個設定中的三個就已達到或超過該方法的通過率，意味著昂貴的 LLM 媒介迴圈在多數情境下是過度設計。

**Q3：為什麼這個問題對整個領域很重要？**

A：技能檢索的效率直接決定了 LLM 代理在真實部署中的經濟可行性與可擴展性。論文指出，即使只有 192 個技能，將整個池載入上下文也會讓通過率回到無技能基線，同時 token 成本膨脹 59%；而策展子集也並非萬靈丹，因為技能帶來的提升呈非單調特性（1 個技能 +17.8%、2-3 個 +18.6%、4 個以上反而降至 +5.9%）。這意味著檢索器必須在「精準」與「成本」之間取得平衡，而這正是 SkillSeek 想為整個領域重新校準的預設起點。

**Q4：SkillSeek 的核心方法是什麼？**

A：SkillSeek 採用經典的兩階段資訊檢索（IR）流程：第一階段使用 BGE-base 雙編碼器（bi-encoder）從技能池中粗排取出前 20 名候選，第二階段再以小型交叉編碼器（cross-encoder）對這些候選進行重排序，最終挑出前 5 名交給代理。整個系統透過模型上下文協議（MCP）暴露給代理，使其能像呼叫一般工具一樣使用檢索功能，而檢索迴圈中完全沒有 LLM 介入，是一個確定性、可重現的管線。

**Q5：SkillSeek 的關鍵創新點為何？**

A：論文的關鍵創新在於「實證貢獻」而非架構新奇——它證明了標準 IR 食譜在代理技能檢索任務上已足以匹敵 LLM 媒介迴圈。具體而言，SkillSeek 在 4×11 的（技能池、骨幹網路、方法）網格實驗中，於 34K 池搭配 Qwen3.5 的設定下，其 Qwen3-Reranker-0.6B 變體達到與 liu_refined 相同的 0.442 通過率，而預設的 bge-reranker-v2-m3 變體甚至比無技能基線提升 +5.7%。這個發現挑戰了「必須用 LLM 做檢索」的預設，直指第一階段召回上限才是瓶頸。

**Q6：SkillSeek 在設計上做了哪些關鍵選擇？**

A：SkillSeek 刻意採用「開箱即用、無需訓練」的元件組合：雙編碼器與交叉編碼器都是現成模型，不針對技能檢索任務做微調，這與 Zheng 等人（2026）需要自訓 1.2B 參數管線的做法形成對比。此外，整個系統可在 CPU 上執行、零 LLM token 消耗，並透過 MCP 標準協議整合，使部署摩擦降到最低。這些設計選擇共同傳達一個訊息：對於大多數代理技能檢索場景，簡單、便宜、確定性的方法就應該是預設起點。

**Q7：實驗採用了哪些基準測試與評估設定？**

A：實驗在 SkillsBench 的 89 個任務上進行，並使用 OpenHands 代理框架作為執行環境，透過 pytest 驗證器回傳 0 到 1 之間的評分作為獎勵。技能池涵蓋兩個規模：192 個技能的精選集與 34,000 個技能的市場規模集；骨幹網路則橫跨多種 LLM 配置。評估同時記錄通過率與單次試驗的美元花費，以便在準確率與成本兩個軸上做帕累托比較。

**Q8：實驗最重要的結果是什麼？**

A：最重要的結果是 SkillSeek 在通過率上與 Liu 等人的 LLM 媒介迴圈達到「觀察平價」，但成本結構截然不同：liu_refined 的單次試驗花費為 51.30 美元，liu_hybrid 為 39.43 美元，而 SkillSeek 僅 27.54 美元，與無技能基線的 27.41 美元相差不到 50 美分。換言之，SkillSeek 用幾乎可忽略的額外成本換來了與昂貴 LLM 迴圈相當的通過率，這對生產環境的成本敏感部署具有直接意義。

**Q9：論文中做了哪些消融或對照實驗？**

A：論文的消融設計是一個 4×11 的網格，系統性地變動技能池（192 vs. 34K）、骨幹 LLM、以及檢索方法（BM25、liu_hybrid、liu_refined、SkillSeek 等）。其中一個關鍵消融觀察是：純 BM25 在四個（池、骨幹）設定中的三個就已達到或超過 liu_refined 的通過率，僅在第四個設定（34K 池搭配 Qwen3.5-397B-A17B）落後，而 SkillSeek 的小型交叉編碼器恰好補上這個差距。這組消融清楚說明了瓶頸在第一階段召回率，而非第二階段的精排。

**Q10：SkillSeek 適合哪些實際應用場景？**

A：SkillSeek 特別適合成本敏感、規模龐大的代理部署，例如企業內部知識庫助手、客服自動化、程式碼助理等需要從數萬筆技能中挑選相關程序的場景。由於它完全在 CPU 上運行且不消耗 LLM token，對於需要高吞吐量、低延遲的線上服務尤其友善。此外，當技能池快速成長（例如從數千筆擴張到數萬筆）時，標準 IR 食譜的可擴展性遠優於每次任務都要呼叫 LLM 的代理迴圈。

**Q11：在產品化部署上需要考量哪些因素？**

A：產品化時應考量三個面向：第一，SkillSeek 透過 MCP 暴露，可無縫接入現有代理框架，無需修改代理核心邏輯；第二，由於是確定性方法，行為可預測、可除錯，便於建立監控與 A/B 測試；第三，雖然預設元件已足夠，但若遇到特定領域的長尾技能，仍可考慮針對性微調編碼器以提升召回率。整體而言，SkillSeek 的設計哲學是「先求有、再求好」，讓團隊能以最低成本驗證技能檢索的價值，再決定是否投入更複雜的方案。

**Q12：這項研究對整個領域會產生什麼影響？**

A：這項研究最重要的影響是「重新定位預設值」：它告訴研究界與工程界，在代理技能檢索任務上，標準 IR 食譜應該是預設起點，而非直接跳到 LLM 媒介方案。這不僅能降低部署成本，也能促使大家更仔細思考「LLM 媒介迴圈究竟在哪些場景真正必要」。長遠來看，這可能推動學界更系統地比較確定性與 LLM 媒介方法，並發展出更精準的「何時該用哪種方法」的決策框架。

**Q13：論文自身承認了哪些限制？**

A：論文坦誠其結論是在 SkillsBench 任務與 OpenHands 框架下得出的，因此未必能直接外推到所有代理場景。此外，雖然 SkillSeek 在通過率上與 LLM 媒介迴圈達到「觀察平價」，但樣本數與統計顯著性仍有討論空間。論文也明確指出，與 Liu 等人的方法共享相同的稀疏加稠密第一階段，但在重排序階段分道揚鑣，這意味著兩者其實可以互補而非完全替代。

**Q14：在哪些失敗案例中 LLM 媒介迴圈仍具優勢？**

A：Liu 等人文件化了一個 Terminal-Bench 2.0 的張量平行案例：代理先檢索到兩個部分相關的技能（torch-tensor-parallel 與 pytorch-research），再合成一個新技能，融合第一個的權重分片與第二個的自訂 autograd.Function 模式。當正確的技能確實存在於池中、但「沒有任何單一技能足以獨立解決任務」時，LLM 媒介迴圈的合成能力是靜態檢索器無法複製的。這正是論文所說的「確定性方法力有未逮」的場景。

**Q15：未來有哪些值得探索的研究方向？**

A：未來方向可分為三條路線：第一，結合 Zheng 等人（2026）所發現的「技能主體內容決定路由成敗」現象，發展主體感知的檢索管線，但需控制訓練成本；第二，設計混合式架構，平時使用確定性檢索，僅在偵測到「需要合成」訊號時才啟動 LLM 媒介迴圈，以兼顧成本與能力；第三，建立更全面的基準測試，涵蓋更多技能池規模與領域，並系統性地量化「合成需求」的發生頻率，以便為不同場景推薦最合適的方法組合。

## 實務應用指南

### 適用場景

**1. 企業內部代理技能市集（Internal Skill Marketplace）**
當企業累積數千至數萬份 SKILL.md 形式的內部程序知識（例如：合約審查流程、報表生成 SOP、客服回覆模板）時，SkillSeek 的兩階段檢索器可直接掛載在內部代理框架上，讓員工代理在執行任務時自動載入最相關的技能，而無需為每次任務支付 LLM 媒介檢索的額外成本。

**2. 開源技能彙整平台的預設檢索後端**
針對 Holzbauer 等人 (2026) 報告的 238,180 規模公開技能池，SkillSeek 可作為 SkillsHub、SkillsMP 等發布平台的預設搜尋引擎。論文已驗證在 34K 規模下，BM25 與 SkillSeek 變體即可達到與 LLM 媒介迴圈相當的通過率，特別適合不想為每次查詢付出數十美元的平台營運者。

**3. CI/CD 與 DevOps 代理的技能路由**
在終端機自動化、CI 修復、雲端資源配置等場景中，代理需要從大量腳本與設定模板中挑選正確的執行路徑。SkillSeek 的 CPU 友善特性（Qwen3-Reranker-0.6B 與 bge-reranker-v2-m3 皆可在 CPU 運行）使其適合部署在邊緣或成本敏感的自動化環境。

**4. 客服與文件處理代理的精準技能載入**
當代理需要從數百份標準作業程序中挑選最相關的一份時，論文中「載入 192 份技能反而使通過率回到無技能基線」的發現尤為關鍵。SkillSeek 的 top-5 精排機制可避免上下文視窗被不相關技能污染，特別適合需要嚴格控制 token 成本的客服系統。

**5. 多模型骨幹網路的公平比較基準**
若團隊正在評估不同 LLM 骨幹網路（如 Qwen3.5、Claude Opus 4.6 等）在技能增強下的表現，SkillSeek 提供了一個確定性、低成本的標準化檢索層，使跨模型比較不再受到檢索策略變動的混淆。

### 實作前置條件

**資料準備**
- 一組結構化的 SKILL.md 目錄集合，每個目錄需包含元數據條目（啟動時載入，約 30 tokens）與完整技能本體（按需載入）。論文中使用的兩個規模為 192 與 34,000 份技能。
- 評估用的任務集：建議採用 SkillsBench 的 89 個任務作為基準，並準備對應的 pytest 驗證腳本作為獎勵函數。
- 若需重現論文數字，需取得 OpenHands 代理框架的執行環境與任務定義檔。

**運算資源**
- 雙編碼器階段：BGE-base 規模的嵌入模型可在單張消費級 GPU（如 RTX 4090）或 CPU 上運行；34K 規模的索引建置通常在數分鐘內可完成。
- 交叉編碼器重排序：Qwen3-Reranker-0.6B 與 bge-reranker-v2-m3 皆支援 CPU 推理，這是 SkillSeek 能將每次試驗花費壓在 $27.54（接近無技能基線 $27.41）的關鍵。
- 完整管線無需任何 LLM API 呼叫，這與 Liu 等人 (2026b) 的 liu_refined 需在每次任務支付 LLM 成本形成對比。

**技能前提**
- 熟悉資訊檢索（IR）基本概念：雙編碼器、交叉編碼器、BM25、top-k 檢索、倒數排名融合。
- 了解 MCP（Model Context Protocol）通訊協定，因為 SkillSeek 透過 MCP 伺服器對外暴露檢索介面。
- 具備 Python 與向量資料庫（如 FAISS、Qdrant）的操作經驗。
- 若要部署在生產環境，需理解代理框架（如 OpenHands）的工具呼叫機制。

### 實作步驟建議

**步驟一：技能池的建立與索引**
將所有 SKILL.md 目錄收集至統一目錄，使用 BGE-base 對每份技能的元數據條目（而非完整本體）進行嵌入，建立稠密向量索引；同時為元數據條目建立 BM25 倒排索引。論文中第一階段召回上限是決定最終通過率的瓶頸，因此元數據條目的品質至關重要。

**步驟二：兩階段檢索管線的組裝**
第一階段以 BM25 與 BGE-base 雙編碼器並行檢索，透過倒數排名融合合併結果，取 top-20 候選；第二階段以小型交叉編碼器（建議先嘗試 bge-reranker-v2-m3 作為預設，必要時切換至 Qwen3-Reranker-0.6B）對 top-20 重排序，輸出 top-5 給代理。

**步驟三：MCP 伺服器封裝**
將上述管線封裝為 MCP 伺服器，使代理可透過標準化的工具呼叫介面請求技能。論文中 SkillSeek 的設計正是以此方式整合進 OpenHands 框架，無需修改代理核心程式碼。

**步驟四：基準評估與網格搜索**
在 SkillsBench 的 89 個任務上，針對 (技能池, 骨幹網路, 檢索方法) 三個維度進行 4×11 網格評估。建議至少測試 192 與 34K 兩個池規模，以及 Qwen3.5-397B-A17B 等代表性骨幹網路，以判斷在自身場景下 BM25 是否已足夠，或需要啟用 SkillSeek 的完整兩階段管線。

**步驟五：成本與通過率的雙軸監控**
部署後持續追蹤每次試驗的美元花費與任務通過率。論文的關鍵發現是：當 SkillSeek 達到與 liu_refined 相同的通過率時，每次試驗花費從 $51.30 降至 $27.54，差距僅來自重排序器的 CPU 推理成本，幾乎可忽略。

**步驟六：保留 LLM 媒介迴圈作為備援**
針對論文中提及的「合成型任務」（例如 Liu 等人在 Terminal-Bench 2.0 案例中需要合併兩個技能的權重分片與 autograd 模式），應保留 LLM 媒介迴圈作為備援路徑。實務上可設計一個啟發式規則：當 SkillSeek 的 top-5 信心分數低於某閾值時，自動切換至 LLM 媒介模式。

### 潛在風險與注意事項

**風險一：第一階段召回上限的瓶頸**
論文明確指出「第一階段召回上限解釋了這個模式」，若 BM25 + BGE-base 的 top-20 未能涵蓋真正相關的技能，後續重排序也無法挽回。緩解方式：定期審查失敗案例的 top-20 列表，必要時擴大候選數量或加入領域特定的同義詞擴展。

**風險二：技能數量增加時的效益遞減**
Li 等人 (2026) 與 Jiang 等人 (2026) 報告「加入技能的提升是非單調的」：1 個相關技能提升 +17.8%，2 至 3 個提升 +18.6%，但 4 個以上反而退化至 +5.9%。緩解方式：嚴格控制 top-k 數量（論文中使用 top-5），並監控代理上下文視窗的實際使用率。

**風險三：載入全部技能池的隱性成本**
即使現代 LLM 擁有足夠大的上下文視窗，論文的附錄 F 顯示載入 192 份技能已使通過率回到無技能基線，同時 token 成本膨脹 59%。緩解方式：絕對不要將整個技能池載入代理上下文，務必透過檢索器篩選。

**風險四：合成型任務的處理能力不足**
當任務需要合併多個技能的部分內容時，確定性檢索器無法產生論文中 Liu 等人展示的「合併權重分片與 autograd 模式」這類新技能。緩解方式：保留 LLM 媒介迴圈作為備援，或在技能設計階段就預先合併常見的組合模式。

**風險五：評估基準的代表性偏差**
論文結果基於 SkillsBench 的 89 個任務與 OpenHands 框架，在其他領域（如醫療、法律、創意寫作）的泛化性尚未驗證。緩解方式：在自家任務集上進行小規模 A/B 測試，特別關注失敗案例的分布是否與 SkillsBench 一致。

**風險六：交叉編碼器的選擇影響有限**
論文中 Qwen3-Reranker-0.6B 與 bge-reranker-v2-m3 在 34K / Qwen3.5 設定下表現不同（前者與 liu_refined 持平於 0.442，後者提升 +5.7%），選擇哪一個需依場景測試。緩解方式：建立自動化的重排序器選擇機制，根據任務類型動態切換。

---

### 與其他技術的整合建議

**與 RAG（檢索增強生成）的整合**
SkillSeek 的兩階段檢索架構與 RAG 的雙編碼器 + 重排序器模式高度一致，可直接複用現有的向量資料庫（如 FAISS、Qdrant、Milvus）與 BM25 索引基礎設施。差異在於 SkillSeek 檢索的對象是結構化的 SKILL.md 程序知識，而非非結構化的文件段落。

**與函數呼叫（Function Calling）的整合**
當代理透過函數呼叫請求 SkillSeek 的 MCP 伺服器時，可將檢索結果包裝為結構化的工具描述，使代理能明確知道每個技能的觸發條件與預期輸出。論文中 SkillSeek 透過 MCP 暴露介面的設計正是為了無縫接入現有的代理工具呼叫流程。

**與 CLAUDE.md 持久化指令的整合**
CLAUDE.md 這類持久化專案指令適合承載「永遠載入」的核心技能，而 SkillSeek 適合承載「按需載入」的情境技能。建議將兩者分工：CLAUDE.md 存放團隊規範、安全守則等通用知識，SkillSeek 處理任務特定的程序知識。

**與子代理（Sub-agents）的整合**
對於複雜的多步驟任務，可在子代理層級部署 SkillSeek，使每個子代理只載入與其子任務相關的技能，避免主代理的上下文視窗被污染。論文中 Liu 等人的 LLM 媒介迴圈本質上也是一種子代理模式，但成本較高。

**與 Liu 等人 (2026b) 的混合檢索整合**
SkillSeek 與 liu_hybrid 共享 BM25 + 稠密嵌入的第一階段，差異僅在第二階段。實務上可設計一個開關：預設使用 SkillSeek 的交叉編碼器重排序，當信心分數不足時切換至 liu_refined 的 LLM 媒介精煉，兼顧成本與合成能力。

**與 Zheng 等人 (2026) 的體感感知檢索對比**
Zheng 等人報告隱藏技能本體會損失 37 至 44 點路由準確率，並提出 1.2B 規模的體感感知檢索重排序管線達到 74.0% Hit@1。SkillSeek 的訓練免費、現成模型策略與其形成對照，適合無法承擔自訂模型訓練成本的團隊；若團隊有能力微調，Zheng 等人的方法在路由準確率上可能更優。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的圖 1，理解「任務 → 檢索 → 代理 → 驗證」的基本迴圈，以及 SkillSeek 與 LLM 媒介迴圈在「零 LLM 呼叫」與「3 至 10 次 LLM 呼叫」之間的成本差異。接著閱讀第 2 節的相關工作，了解技能檢索問題的脈絡。實作上可先從 192 份技能的 BM25 基準開始，體會「簡單方法有時已足夠」的核心訊息。

**給 AI 工程師**：重點閱讀第 4 節的實驗設計，特別是 4×11 網格（4 個池與骨幹網路組合 × 11 種方法）的評估方式，以及表 6 的成本拆解（$39.43 vs $27.41 vs $51.30 vs $27.54）。工程實作上，建議直接參考論文的 GitHub 倉庫（https://github.com/guanqun-yang/SkillSeek）取得可重現的腳本，並將 MCP 伺服器封裝模式套用到自家的代理框架中。

**給研究者**：論文的關鍵洞見在於「第一階段召回上限解釋了 LLM 媒介迴圈優勢不大的原因」，這對資訊檢索與代理系統的交叉領域有方法論上的啟發。建議延伸閱讀 Li 等人 (2026) 關於非單調提升的發現，以及 Zheng 等人 (2026) 關於體感感知檢索的工作，思考在何種任務特性下確定性方法會失效，進而設計新的混合策略。

**給產品經理**：核心訊息是「在 SkillsBench 與 OpenHands 的測試條件下，標準 IR 方法已足夠作為預設，無需為每次任務支付 LLM 媒介檢索的額外成本」。這對產品的單位經濟有直接影響：若每月執行數萬次技能增強任務，從 liu_refined 遷移至 SkillSeek 可節省數萬美元的 LLM API 費用。但同時需注意，論文的結論限定於特定基準與框架，在自家產品上線前應進行小規模驗證，特別是針對需要合併多個技能的部分內容的合成型任務。
