## ⚡ TL;DR

現有實驗追蹤工具只能監控，即時調整訓練仍須撰寫訓練器專屬程式碼。
Interactive Training 2 透過共享協定公開可調設定與動作，於安全控制點套用請求。
已在五個NLP與強化學習流程中驗證，為可稽核的人機協同訓練提供可重複使用的基礎。

## 摘要翻譯

實驗追蹤器（Experiment Tracker）能夠顯示訓練進度，但若要變更正在執行的訓練，通常仍需要針對該訓練器撰寫專屬程式碼。我們提出 Interactive Training 2，一個透過共享協定（Shared Protocol）來引導訓練的開源控制平面（Control Plane）。訓練應用程式宣告其所公開的設定與動作，人類與自動化控制器（Controller）透過相同介面提交請求（Request），而訓練迴圈（Training Loop）會在安全的控制點（Control Point）驗證並套用這些請求。客製化的 Aim 工作空間（Aim Workspace）結合了即時指標（Live Metric）與控制項，並提供依時序記錄的請求與執行結果（Execution Result）。我們在五個自然語言處理（NLP）與強化學習（Reinforcement Learning）的工作流程中展示本系統。釋出的程式碼與追蹤紀錄為可稽核的人類與大型語言模型代理（LLM Agent）引導式訓練提供了可重複使用的基礎。

### 核心貢獻（3～5點）
- 提出 Interactive Training 2，一個開源的可稽核控制平面（Auditable Control Plane），透過共享協定統一人類與自動化控制器對即時模型訓練（Live Model Training）的操作介面。
- 讓訓練應用程式能夠宣告其所公開的設定與動作，並由訓練迴圈在安全的控制點驗證與套用請求。
- 客製化 Aim 工作空間，將即時指標、控制項與依時序記錄的請求和執行結果整合於單一介面。
- 在五個自然語言處理與強化學習的工作流程中驗證系統，並釋出可重複使用的程式碼與追蹤紀錄。

### 適合對象
從事機器學習系統、模型訓練基礎建設、實驗管理工具開發的研究人員與工程師；特別是對即時訓練控制、人機協作調參、自動化代理引導訓練，以及訓練過程可稽核性有興趣的讀者。

## 深度分析

#### 方法論解析

##### 1. 整體架構：從被動監控到主動控制
Interactive Training 2（以下簡稱 IT2）的核心貢獻在於把「觀察訓練」與「操控訓練」整合到同一個共享協定（Shared Protocol）中。傳統 Experiment Tracker（實驗追蹤器）如 Weights & Biases、TensorBoard 或 Aim 主要提供 Live Metric（即時指標）視覺化，但若要改變 Learning Rate（學習率）、觸發 Checkpoint（檢查點）儲存或停止訓練，研究者通常必須撰寫 Callback（回呼函式）或針對特定 Trainer 的程式碼。IT2 把這些控制需求抽象為一個 Control Plane（控制平面），讓 Training Loop（訓練迴圈）本身宣告可調項目與可執行動作，而人類、腳本、啟發式規則或 LLM Agent（大型語言模型代理）都透過相同介面提交 Request（請求）。

##### 2. 註冊機制：Knob 與 Action
Training Application（訓練應用程式）透過 Python API（Python API）呼叫 `register_knob` 註冊 Typed Setting（型別化設定），也就是 Knob（調節鈕）。每個 Knob 綁定名稱、資料型別、可選範圍與步進大小、自然語言描述，以及對應的 getter 與 setter。這樣的設計讓控制項具備型別安全：例如 AdamW（Loshchilov and Hutter, 2019）的 Learning Rate、資料來源取樣權重、Muon（Jordan et al., 2024）動量或 RL 的課程難度，都可以被統一表示，而不必把任務相關邏輯塞進訓練會話。

除了設定項，應用程式還可註冊 Structured Action（結構化動作），例如 `set_knob`、`evaluate`、`save_checkpoint`、`load_checkpoint`、`pause`、`stop`，或領域專屬動作如凍結語言模型嵌入層。HTTP API 與 LLM Agent 看到的是同一份已註冊動作清單，這消除了「人類介面」與「自動化介面」不一致的問題。

##### 3. 控制點與安全套用
IT2 的關鍵設計原則是「Training Loop 仍擁有控制權」。Request 可隨時抵達，但只有在 Control Point（控制點）才會被逐一套用。每次呼叫 `session.step(metrics)` 時，系統會：

1. 記錄新指標並快照初始設定組態；
2. 依排程執行附掛的 Controller（控制器）；
3. 從單一動作佇列中取出 Human（人類）與自動化 Request；
4. 執行對應處理器、箝制設定值，並為每個 Request 記錄 Execution Result（執行結果）；
5. 在暫停狀態下持續處理 resume 與 stop 類 Request。

`session.pump()` 則可在訓練閒置時處理 Pending Request 而不記錄訓練指標。回傳的 `StepControl` 物件會告訴整合層是否應停止、評估、存取 Checkpoint、重置模組或更新設定。這個 Control Point 保證當呼叫返回時，所有被接受的變更已經在下一步驟前生效，從而避免非同步修改模型狀態所帶來的競態條件。

##### 4. Journal：可稽核的時序日誌
IT2 的 Auditability（可稽核性）來自 Journal（日誌）。每個 Request 會與其來源、結果、周圍訓練脈絡一起被記錄。在 Round（回合）內，Metric、Request、Result、Checkpoint 與 Controller 決策共享一份有序 Journal；跨 Round 時，系統會產生新的模型與 Optimizer（優化器），並把上一 Round 的 JSONL Journal、設定、分數與反思傳入下一個 Plan（計畫）。這讓研究者能夠重建「誰請求了什麼動作、請求內容為何、是否成功、前後發生了什麼事」，而不必在分散的 Console Log（終端機日誌）中拼湊。

##### 5. Aim Workspace：觀察、控制與審查的統一介面
IT2 客製化 Aim Workspace（Aim 工作空間），將 Live Metric（即時指標）、Controls（控制項）與 chronological record（依時序記錄）結合。研究者可以檢視 Validation Loss（驗證損失）曲線、提交 Learning Rate 調整、觀察 Request 何時被套用，並在 Journal 中看到 Request → Result → Saved Checkpoint 的完整鏈路。這種「觀察—控制—審查」三位一體的介面，是傳統實驗追蹤器所缺乏的。

#### 實驗數據解讀

##### 1. 實驗設計：五個異質工作流
論文在五個涵蓋 NLP（自然語言處理）與 Reinforcement Learning（強化學習）的工作流上展示 IT2，包括 Callback 整合、Optimizer Wrapper（優化器包裝器）、直接 PyTorch 訓練迴圈與 RL 迴圈。Table 1（雖然完整數值未在提供的上下文中列出）總結了每個工作流如何整合 TrainingSession、暴露了哪些 Knob 與 Action，以及 Journal 中記錄了哪些 Score（分數）。

##### 2. 結果的性質：功能性與概念性驗證
由於論文重點是提出 Control Plane 而非追求 State-of-the-Art（最先进水平）性能，其「實驗數據」更多是質性與功能性展示：

- **Setting Change 的即時生效**：例如 BERT 微調範例中，研究者把 Learning Rate 從 3×10⁻⁵ 降至 2×10⁻⁵，系統在 Control Point 套用後，Validation Loss 軌跡隨之改變，並在 Journal 中留下完整記錄。
- **Best-so-far（目前最佳）Round Score**：每個 Round 結束後，系統會記錄最佳分數，作為下一 Round Plan 的輸入。這對 LLM Agent 進行長期規劃特別重要。
- **Request → Result → Checkpoint 鏈路**：圖 1 顯示一個 Request 從計畫、控制、指標變化到儲存 Checkpoint 的完整流程，證明系統能把決策與結果連結起來。

##### 3. 指標解讀
- **Validation Loss**：用來衡量 Setting Change 是否帶來預期效果。若 Learning Rate 下調後 Validation Loss 持續下降，表示控制有效。
- **Round Score**：以 Goal（目標）Metric（如最佳驗證損失）為基礎，評估整個 Round 的表現。這不僅是模型性能指標，也是 Controller 決策品質的間接指標。
- **Audit Trail 完整性**：雖然不是傳統 ML 指標，但「能否重建每個 Request 的前後脈絡」是 IT2 宣稱 Auditable Control Plane（可稽核控制平面）的核心衡量標準。

##### 4. 實驗的侷限
提供的上下文未包含量化比較，例如與純人工調參或現有 Callback 方案相比，IT2 在收斂速度、最終性能或開發時間上的具體提升。因此，目前只能確認系統「可行」且「通用」，但尚無法評估其「多有效」。

#### 與現有研究的比較

##### 1. 相對於傳統 Experiment Tracker
Weights & Biases、TensorBoard、Aim、MLflow 等工具專注於 Monitoring（監控）與 Logging（日誌記錄），提供豐富的 Live Metric 視覺化與實驗比較功能。然而，它們通常不具備「回寫」訓練狀態的能力。IT2 的進步在於把監控層延伸為控制層：同一個 Aim Workspace 既能看指標，也能下指令，並把指令結果記錄回同一條 Journal。

##### 2. 相對於超參數調整與 AutoML
Optuna、Ray Tune、Hyperband 等工具能在訓練前或訓練中調整 Hyperparameter（超參數），但它們通常以「啟動新 Trial（試驗）」為主要模式，而非在單一 Live Model Training（即時模型訓練）過程中動態修改。IT2 則允許在單一執行中持續 Steering（引導），並支援人類即時介入，這對探索性研究更為重要。

##### 3. 相對於現有互動式訓練研究
Zhang et al.（2022）與 Walsh et al.（2025）等研究已指出研究者會根據即時行為調整訓練，但相關工具仍然碎片化。IT2 提供了一個統一的 Shared Protocol（共享協定），讓不同 Controller 透過相同介面與訓練互動，並以 Journal 記錄所有互動。這比「每個實驗寫專屬 Callback」更具可移植性與可重複性。

##### 4. 相對於 LLM Agent for Science
近期有許多研究讓 LLM Agent 自動設計實驗、撰寫程式碼或調整參數。IT2 的獨特之處在於為 LLM Agent 提供了一個「型別化、可驗證、可稽核」的動作空間：Agent 只能看到與使用已註冊的 Knob 與 Action，而 Training Loop 會在 Control Point 驗證並箝制其請求，降低 Agent 誤操作風險。

##### 5. 限制與未解決問題
- **整合成本**：訓練程式仍需呼叫 `register_knob`、`session.step` 等 API，對於已高度封裝的 Trainer（如 Hugging Face Trainer）需要額外包裝。
- **Control Point 選擇負擔**：應用程式開發者必須決定何時呼叫 Control Point，過於頻繁可能影響效能，過於稀疏則降低互動即時性。
- **安全性與信任**：雖然系統可隱藏危險動作不讓 LLM Agent 看到，但對於惡意或錯誤的人類 Request，目前僅依賴型別檢查與範圍箝制，缺乏更細緻的存取控制或沙箱機制。
- **分散式訓練**：論文未討論多節點、多 GPU 情境下的 Request 同步與一致性問題。
- **量化評估不足**：缺乏對系統開銷、Controller 決策品質與最終模型性能的系統性量化比較。

#### 可重現性評估

##### 1. 開源釋出
論文已將程式碼釋出於 `github.com/yuntian-group/interactive-training`，並提供互動式展示 `interactivetraining.ai/live`。此外，系統執行過程中產生的 traces（執行軌跡）也一併釋出，這對理解 Request 如何被處理、Journal 如何記錄非常有幫助。

##### 2. 資料集與模型權重
上下文未明確說明使用的 Dataset（資料集）與 Model Weights（模型權重）。從 BERT 微調範例推測，可能使用公開資料集（如 GLUE）與公開預訓練權重。若果真如此，則資料與模型取得相對容易；但論文應在文件中清楚列出資料集版本、預處理流程與權重來源，以避免重現時因版本差異導致結果不一致。

##### 3. 環境與依賴
目前提供的資訊未包含完整的相依性清單、Python 版本、CUDA 版本或硬體規格。對於一個需要與 PyTorch、Aim 及可能多個 RL 框架整合的系統，建議提供：
- `requirements.txt` 或 `pyproject.toml`；
- Docker Image 或 Dockerfile；
- 硬體需求與預期執行時間；
- CI 測試與最小可執行範例。

##### 4. Journal 與 Trace 的價值
釋出的 traces 本身就是一種「可重現的敘事」：研究者可以重播 JSONL Journal，觀察每個 Request 的來源、內容與結果。這對稽核與除錯極有價值，但若要重現完整訓練，仍須搭配原始程式碼與隨機種子設定。

##### 5. 綜合評價
IT2 在「開放性」上表現良好：核心系統開源、展示可用、軌跡可下載。但在傳統 ML 可重現性標準（資料、環境、超參數、隨機種子、硬體）上，論文提供的細節仍顯不足。若後續版本能補充完整實驗設定與自動化重現腳本，將大幅提升其可重現性。

#### 未來研究方向

##### 1. 分散式與多節點控制平面
目前的設計似乎針對單一 Training Session。未來可擴展至 Distributed Training（分散式訓練）情境，處理多 Worker 之間的 Request 廣播、Checkpoint 一致性與全域 Control Point 同步問題。

##### 2. 細緻化存取控制與安全沙箱
針對 LLM Agent 或多人協作場景，可引入 Role-based Access Control（角色型存取控制）、動作審批流程、以及 Request 影響範圍預估（例如「此動作將覆蓋目前 Checkpoint」），進一步降低誤操作風險。

##### 3. Controller 效能基準測試
建立標準化的 Benchmark（基準測試），比較不同 Controller（人類、啟發式規則、LLM Agent）在固定任務上的 Steering 效率、最終模型性能與 Journal 品質。這將幫助社群客觀評估自動化訓練引導的價值。

##### 4. 與更多深度學習框架整合
目前展示以 PyTorch 為主，未來可擴展至 JAX、TensorFlow、以及更高階框架如 Hugging Face Transformers、Lightning、Accelerate，降低整合門檻。

##### 5. 智慧型 Control Point 選擇
研究如何根據訓練狀態動態調整 Control Point 頻率。例如，在損失劇烈震盪時提高檢查頻率，在穩定訓練時降低頻率，以平衡互動性與計算開銷。

##### 6. 可重播與可逆訓練
基於 Journal 與 Checkpoint，可發展「時間旅行」功能：讓研究者回到某個 Request 之前的狀態、比較不同 Steering 決策的分支結果，甚至自動化 A/B 測試不同控制策略。

##### 7. 模型手術與結構化動作擴展
除了調整 Hyperparameter 與存取 Checkpoint，未來可支援更細緻的 Model Surgery（模型手術）動作，例如動態新增或移除層、切換 Optimizer、合併 LoRA Adapter 等，並確保這些動作同樣經過型別驗證與稽核。

##### 8. 標準化 Audit Format
推動 Journal 格式成為社群標準，使其能與 MLflow、WandB、Aim 等現有工具互換，並支援長期儲存、法規稽核與自動化報告生成。

##### 9. 人機協作介面
改善 Aim Workspace 的協作功能，例如多人同時觀察與下指令時的衝突解決、自然語言指令轉換為 Typed Request、以及基於 Journal 的自動摘要與決策建議。

##### 10. 與 MLOps 管線整合
將 IT2 嵌入持續訓練（Continuous Training）與 CI/CD 管線，使其不僅服務於研究探索，也能在生產環境中支援人類審核過的自動化模型更新與緊急停機。

## 論文問答

**Q1：Interactive Training 2 旨在解決什麼核心問題？**
A：Interactive Training 2 主要解決即時模型訓練過程中缺乏通用控制介面的問題。現有的實驗追蹤器雖然能夠顯示訓練進度和即時指標，但研究人員若想根據觀察結果調整學習率、重新平衡資料或儲存檢查點，通常必須撰寫針對特定訓練框架的回呼函式或自訂邏輯。這種碎片化的工具生態使得人類和自動化控制器難以跨不同訓練工作流程進行一致且可重複的介入，因此本系統提出一個共享協定來統一監控、控制與日誌記錄機制。

**Q2：為什麼現有的實驗追蹤器無法滿足即時訓練導引的需求？**
A：現有的實驗追蹤器主要專注於視覺化訓練狀態和記錄指標，但它們通常不提供通用的方式來執行控制決策。研究人員雖然可以觀察到驗證損失上升或不穩定的現象，但要實際降低學習率或暫停訓練，仍須針對特定訓練器撰寫專屬程式碼。這種觀察與行動之間的斷層導致每次實驗都需要重建監控、控制和日誌記錄機制，增加了重複性工作並限制了自動化代理的廣泛應用。

**Q3：可稽核的人類與代理導引訓練為何重要？**
A：可稽核性讓研究人員能夠重建每個動作請求的來源、內容、執行結果以及周圍的訓練脈絡，這對於理解模型行為和除錯至關重要。在機器學習研究中，許多關鍵決策是在訓練過程中動態做出的，若缺乏完整的日誌記錄，將難以追溯某個設定變更是否真正帶來預期效果。此外，當大型語言模型代理或其他自動控制器參與決策時，完整的稽核軌跡有助於評估代理行為、確保實驗可重現，並為未來改進控制策略提供依據。

**Q4：共享控制協定的核心運作方式為何？**
A：共享控制協定的核心在於訓練應用程式透過 Python API 註冊型別化設定與結構化動作，而人類、腳本、啟發式規則或 LLM 代理都透過相同介面提交請求。訓練迴圈在安全的控制點檢查佇列中的請求，驗證其有效性後才套用變更，並記錄執行結果再繼續下一個訓練步驟。這種設計確保所有控制器無論是自動或人為，都使用一致的請求格式和處理流程，從而實現跨不同訓練框架的統一控制。

**Q5：控制平面的「可稽核性」體現在哪些方面？**
A：可稽核性體現在系統能夠依時序記錄每個請求的來源、內容、是否成功套用，以及請求前後的訓練脈絡，包括指標、評估結果和檢查點。客製化的 Aim 工作空間將即時指標、控制項和事件日誌整合在同一介面中，使得研究人員可以輕易追蹤從決策到執行的完整鏈路。這種設計不僅讓人類能夠理解訓練過程中的關鍵轉折，也讓自動化控制器的決策過程變得透明且可檢視。

**Q6：為什麼由訓練迴圈決定請求的套用時機？**
A：由訓練迴圈決定控制點是為了確保設定變更和動作請求不會在訓練過程中造成不一致或危險狀態，例如在梯度更新中途改變學習率。訓練應用程式最清楚哪些時點是安全的，因此由它宣告控制點並在該處驗證、夾取值並套用請求，可以避免外部控制器對訓練內部狀態做出不當假設。這種設計也讓訓練程式碼保留對模型更新的最終控制權，同時仍允許外部代理靈活地提出調整建議。

**Q7：論文在哪些工作流程上展示了系統？**
A：論文展示了五個涵蓋自然語言處理和強化學習的工作流程，包括使用 BERT 的語言模型微調、以及涉及回呼函式、優化器包裝器和直接 PyTorch 訓練迴圈的案例。這些工作流程展示了共享協定能夠適應不同的訓練架構，從高階框架整合到低階手動迴圈都能使用相同的控制機制。透過這些多樣化的示範，作者證明了該系統具有足夠的通用性，可以支援不同領域和實作風格的即時訓練導引。

**Q9：五個工作流程如何與 TrainingSession 整合？**
A：每個工作流程都會根據自身需求註冊不同的調節鈕和動作，例如學習率、來源取樣權重、動量或課程難度，並在適當的控制點呼叫 session.step() 或 session.pump()。這些整合方式包括回呼函式、優化器包裝器，以及直接在 PyTorch 或強化學習迴圈中嵌入控制點，顯示出協定的靈活性。無論採用何種整合方式，TrainingSession 都負責統一處理請求佇列、驗證、套用和記錄，讓訓練程式碼無需重複實作控制邏輯。

**Q10：研究人員在實務中如何使用這個系統？**
A：研究人員可以在 Aim 工作空間中觀察即時指標，當發現驗證損失不再下降或訓練變得不穩定時，立即透過相同介面降低學習率、請求評估或儲存檢查點。他們也可以撰寫腳本或啟發式規則，在特定條件下自動提交請求，甚至讓 LLM 代理根據訓練日誌和目前狀態提出調整建議。由於所有請求都經過相同的共享協定處理並記錄在日誌中，研究人員可以輕易比較不同控制策略的效果，並在後續實驗中重現成功的介入模式。

**Q11：Aim 工作空間如何支援使用者的觀察與控制需求？**
A：Aim 工作空間將即時指標視覺化、控制項和依時序排列的事件日誌整合在同一介面中，讓研究人員無需在多個工具之間切換。使用者可以直接在圖表旁邊看到控制項，並在提交請求後立即追蹤其處理狀態和最終結果。這種整合設計大幅降低了觀察與行動之間的摩擦，並透過日誌將每個決策與對應的訓練事件連結起來，提升了整體工作流程的透明度和效率。

**Q12：這項研究對機器學習領域可能產生什麼廣泛影響？**
A：這項研究為人類與自動化代理共同參與模型訓練提供了一個可重複使用的基礎設施，有助於推動互動式機器學習和自動化機器學習的發展。透過統一的控制平面，不同研究團隊可以更容易地比較和共享控制策略，而不必為每個實驗重建專屬工具。此外，可稽核的日誌記錄也為研究訓練動態、代理決策行為和可重現性提供了寶貴的資料基礎，可能促進更多關於人機協作訓練的研究。

**Q13：目前系統有哪些已知的限制？**
A：雖然論文沒有明確列出所有限制，但從設計上可以看出，系統的有效性取決於訓練應用程式正確註冊調節鈕和動作，並在適當位置呼叫控制點，這需要開發者額外投入整合工作。此外，目前系統主要處理單一訓練程序內的請求，對於分散式訓練或多節點同步控制的支援程度尚不明確。另外，雖然訓練迴圈保留了最終控制權，但如何設計良好的控制點頻率和驗證規則，仍然需要領域知識和實驗經驗。

**Q14：自動化控制器可能出現哪些失敗案例？**
A：自動化控制器可能會在訓練尚未穩定時過早調整學習率，導致模型收斂到次優解，或者頻繁請求評估和儲存檢查點而產生不必要的計算開銷。LLM 代理雖然能根據自然語言描述提出建議，但可能誤解當前訓練狀態或提出不適合該任務的設定變更，因此訓練迴圈的驗證機制和隱藏危險動作的功能就顯得格外重要。此外，若控制器的決策邏輯存在偏誤，長期累積的錯誤介入可能會被記錄下來，但已經對訓練結果造成不可逆的影響。

**Q15：未來研究可以朝哪些方向發展？**
A：未來研究可以擴展共享協定以支援更複雜的分散式訓練場景，並開發更智慧的預設控制點和驗證規則來降低整合門檻。另一個方向是設計更強大的 LLM 代理，使其能夠根據長期的日誌資料和領域知識做出更穩健的決策，同時保持可解釋性和可稽核性。此外，將這個控制平面與更廣泛的實驗管理平台和模型註冊系統整合，也有助於建立從實驗設計到部署的完整人機協作訓練生態系。

## 實務應用指南

### 適用場景

1. **大規模語言模型微調時的動態超參數調整**  
   在長時間的 BERT 或 LLM 微調過程中，研究人員可透過 Aim 工作空間觀察即時指標（如驗證損失），並在即時模型訓練進行中安全地降低學習率、調整資料取樣權重，或觸發評估與檢查點儲存，而無需中斷訓練迴圈或修改訓練程式碼。

2. **強化學習課程學習（Curriculum Learning）的即時難度控制**  
   強化學習訓練可將「課程難度」註冊為調節鈕，控制器（人類、啟發式規則或 LLM 代理）依據目前最佳分數與即時指標，在控制點提交難度調整請求，讓環境難度隨訓練狀態逐步提升。

3. **多實驗並行的自動化 early stopping 與檢查點管理**  
   當同時執行多組實驗時，自動化控制器可統一透過共享協定監控各實驗日誌，並在驗證損失不再改善時自動請求停止、載入最佳檢查點或重新初始化模組，減少人工巡檢成本。

4. **人機協作的生成式模型訓練調校**  
   生成式模型訓練過程中，領域專家可在 Aim 工作空間中觀察生成品質指標，手動請求變更優化器參數（如 Muon 動量）或凍結特定層，並透過日誌追蹤每項決策的原因與結果，建立可稽核的調校歷程。

5. **LLM 代理驅動的自主超參數探索**  
   將 Interactive Training 2 的控制介面開放給 LLM 代理，讓代理根據每回合的指標、設定與反思摘要自動規劃下一回合的設定變更，適合用於需要反覆試驗的模型開發流程。

### 實作前置條件

**資料與運算**
- 可執行 PyTorch 訓練迴圈的運算環境（GPU 叢集、雲端 VM 或本地工作站）。
- 能夠儲存訓練日誌、檢查點與 JSONL 格式回合日誌的儲存空間。
- 若使用 Aim 工作空間進行視覺化，需能執行 Aim 伺服器並讓訓練節點與使用者瀏覽器皆可存取。

**技術能力**
- 熟悉 Python 與 PyTorch，能夠修改訓練迴圈以插入 `session.step()` 或 `session.pump()` 控制點。
- 理解訓練應用程式中 getter/setter 的設計，能將現有超參數封裝為型別化調節鈕。
- 具備 REST API 或 HTTP 客戶端操作經驗，以便透過共享協定提交請求。
- 若希望整合 LLM 代理，需熟悉提示工程與自動化控制器的基本設計。

### 實作步驟建議

1. **安裝與環境準備**  
   從 `github.com/yuntian-group/interactive-training` 取得原始碼，安裝相依套件，並在本機或遠端啟動 Aim 工作空間與訓練會話服務。

2. **識別可控制項目**  
   檢視現有訓練腳本，列出可在執行期安全變更的設定（如學習率、取樣權重、動量）與動作（如 evaluate、save_checkpoint、load_checkpoint、pause、stop）。

3. **註冊調節鈕與動作**  
   使用 Python API 的 `register_knob` 將每個設定註冊為型別化調節鈕，指定資料型別、範圍、步進大小與自然語言描述；同時註冊對應的結構化動作與目標分數（goal）。

4. **插入控制點**  
   在訓練迴圈中選擇安全時機（如每個 step 或每 N 個 step 結束後）呼叫 `session.step(metrics)`，讓系統有機會檢查佇列請求、執行設定變更並記錄結果。閒置時可呼叫 `session.pump()` 處理暫停、恢復等請求。

5. **連接控制器**  
   設定人類使用者透過 Aim 工作空間提交請求，或撰寫腳本／LLM 代理透過相同 HTTP API 傳送請求。確保所有控制器使用相同的請求格式與動作清單。

6. **驗證與測試**  
   先以小規模實驗測試每個調節鈕與動作，確認數值會被正確截斷（clamp）、動作會在控制點生效、日誌能正確記錄請求來源與執行結果。

7. **部署到生產級訓練**  
   將系統整合至正式訓練流程，設定自動化控制器排程（如每 100 steps 執行一次），並定期匯出 JSONL 日誌以進行離線稽核與回合間反思。

### 潛在風險與注意事項

- **控制點選擇不當導致狀態不一致**  
  若在梯度更新中途套用設定變更，可能導致數值不穩定。應將控制點設在 step 邊界、epoch 結束或評估完成後，並由訓練迴圈決定何時安全套用。

- **過度頻繁的請求干擾訓練穩定性**  
  自動控制器（尤其是 LLM 代理）可能過度調整參數。建議設定最小調整間隔、數值變動上限，並在日誌中標記異常頻繁的請求。

- **危險動作被意外觸發**  
  對於 `load_checkpoint`、`reset_module` 或 `stop` 等影響較大的動作，應在應用程式層隱藏或額外驗證，避免 LLM 代理或未授權使用者誤用。

- **日誌遺失影響可稽核性**  
  可稽核控制平面的核心在於完整記錄。務必將 JSONL 日誌持久化至可靠儲存，並在回合結束時攜帶配置、分數與反思摘要至下一回合。

- **多控制器競爭同一佇列**  
  當人類與多個自動控制器同時操作時，可能產生衝突請求。建議實作請求優先順序或鎖定機制，並在日誌中保留每個請求的來源與時間戳記。

### 與其他技術的整合建議

- **實驗追蹤器（如 Weights & Biases、TensorBoard）**  
  Interactive Training 2 並非要取代現有實驗追蹤器，而是補強其「只能看、不能改」的限制。可將即時指標同時寫入原有追蹤器與 Aim 工作空間，讓研究人員保留既有視覺化習慣。

- **排程與 workflow 系統（如 Kubernetes、Airflow、Slurm）**  
  將訓練會話作為長期執行服務部署在叢集中，控制器則以獨立任務形式執行。回合結束後的反思摘要可用於觸發下一個 workflow 任務。

- **LLM 代理框架（如 LangChain、AutoGPT）**  
  將註冊的動作清單與目前訓練狀態包裝成工具（tool），讓 LLM 代理根據日誌與指標自動產生請求。建議先在人機協作模式下運作，再逐步放寬自動化程度。

- **MLOps 平台與模型註冊表**  
  將 `save_checkpoint` 動作與模型版本管理系統串接，使每次儲存的檢查點自動註冊版本、附帶當下設定與日誌連結，強化模型血緣追蹤。

- **警報與監控系統（如 Prometheus、Grafana）**  
  從日誌中抽取關鍵事件（如請求失敗、異常頻繁的設定變更）並轉換為監控指標，搭配告警機制讓維運人員即時介入。

| Controller | 控制器 | 提交請求的人類、腳本、啟發式規則或 LLM 代理 |

| Typed Setting | 型別化設定 | 具有明確資料型別的可調訓練設定 |
