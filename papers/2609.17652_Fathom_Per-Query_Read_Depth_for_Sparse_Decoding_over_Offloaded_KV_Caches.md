# Fathom：針對卸載式 KV 快取上稀疏解碼的逐查詢讀取深度

**原文標題：** Fathom: Per-Query Read Depth for Sparse Decoding over Offloaded KV Caches

**發布日期：** 2026-09-15

## ⚡ TL;DR

解決卸載式 KV 快取在長上下文稀疏解碼時，逐 token 掃描所有鍵所造成的互連頻寬瓶頸。
提出 Fathom，讓每個查詢依通道重要性以反向注水法，動態決定 4-bit 鍵快取各通道的讀取深度。
在百萬 token 長上下文下，GPU 時間較 136-bit 掃描快 1.67 倍，並以更少位元達到更低注意力誤差。

## 摘要翻譯

當智慧代理會話（Agentic Sessions）的長度達到一百萬個 token（One Million Tokens），且同時有多個會話駐留時，KV 快取（KV Cache）以及用於對其排序的索引都存放在主機記憶體（Host Memory）中，而為了執行 Top-k 解碼步驟（Top-k Decoding）而對所有 n 個鍵（keys）進行排序的掃描（scan），便成為限制解碼速度的傳輸量瓶頸。我們提出 Fathom（Fathom），一種逐查詢鍵掃描方法，讓每個查詢（query）決定讀取各鍵通道（Channel）的位元數。4-bit K 快取（4-bit K Cache）以通道優先（Channel-Major）方式儲存為位元平面（Bit Planes），因此前 t 個位元平面的前綴（Prefix）即為該通道的 t-bit 量化器（Quantizer）；查詢則依據其通道的變異數加權重要性（Variance-Weighted Importance），透過反向注水法（Reverse Water-Filling）來分配位元預算（Bit Budget）。在 Qwen3-8B（Qwen3-8B）處理一百萬個 token 時，每個解碼步驟（Decode Step）在 GPU 時間（GPU Time）上的速度為 Double Sparsity（Double Sparsity）、Loki（Loki）與 SparQ r=32（SparQ）之 136-bit 掃描（136-bit Scans）的 1.67 倍；在與 SparQ 68-bit 讀取（68-bit Read）（r=16）相同的 GPU 時間下，Fathom 在七組模型與上下文（Context）設定中的六組上，讀取位元組數減少 18%，且注意力誤差（Attention Error）更低。在 RULER 風格任務（RULER-Style Tasks）上，每個逐 token 掃描都與精確 Top-k 解碼（Exact Top-k Decoding）一致；在真實程式設計代理會話（Coding-Agent Sessions）上，Fathom 僅以 92 bit（92 bits）即可達到與最準確的 136-bit 掃描相同的步驟一致性（Step Agreement）。儲存的內容即為量化服務堆疊（Quantized Serving Stack）已持有的 4-bit K 快取副本；當索引常駐於 GPU 記憶體（GPU memory）時，本方法並不會更快。

### 核心貢獻（3～5點）
- 提出逐查詢鍵掃描 Fathom：每個查詢依據自身通道的重要性，動態決定讀取 4-bit K 快取各通道的位元數，突破傳統固定深度掃描的限制。
- 以通道優先位元平面儲存與反向注水法配置位元預算：前 t 個位元平面即為 t-bit 量化器，並按變異數加權重要性分配位元，兼顧速度與準確度。
- 在 Qwen3-8B 一百萬個 token 情境下，每個解碼步驟的 GPU 時間較 Double Sparsity、Loki 與 SparQ r=32 的 136-bit 掃描快 1.67 倍；與 SparQ 68-bit 讀取耗時相同時，Fathom 在七組設定中的六組讀取位元組數減少 18% 且注意力誤差更低。
- 在 RULER 風格任務上，每個逐 token 掃描皆與精確 Top-k 解碼一致；在真實程式設計代理會話中，僅以 92 bit 即可達到最準確 136-bit 掃描的步驟一致性。
- 儲存內容即為量化服務堆疊已持有的 4-bit K 快取副本，無需額外資料結構；但當索引常駐於 GPU 記憶體時，本方法不會更快。

### 適合對象
適合對長上下文大型語言模型推論系統、KV 快取量化與卸載、稀疏注意力及代理應用有興趣的研究者與系統工程師；特別是正在建構或優化百萬級 token 量化服務堆疊，並需在記憶體頻寬受限環境下提升解碼效率的從業人員。

## 深度分析

#### 方法論解析

##### 問題設定與核心動機
Fathom 針對的是**Offloaded KV Caches（卸載式 KV 快取）**下的**Sparse Decoding（稀疏解碼）**。當**Agentic Sessions（智慧代理會話）**長度達到一百萬個 **token**，且多個會話同時常駐於伺服器時，整個 **KV Cache（KV 快取）**與其索引無法放進 GPU 高頻寬記憶體（HBM），只能存放在 **Host Memory（主機記憶體）**或更慢的儲存層。此時，解碼步驟的瓶頸不再是 GPU 運算，而是**Interconnect（互連）**頻寬：每個 **Decode Step（解碼步驟）**都需要掃描全部 n 個鍵來找出 **Top-k Sparse Attention（Top-k 稀疏注意力）**的候選者。因此，降低掃描所需的位元數，就等於直接降低延遲。

##### 固定深度掃描的局限
現有方法如 **Loki**、**Double Sparsity**、**SparQ** 與 **Thumbnail Scans（縮圖掃描）**都屬於「固定深度」掃描：
- Loki 讀取前 r 個 **Principal-Component Coordinates（主成分座標）**；
- Double Sparsity 讀取離線選定的 c 個 **Channel（通道）**；
- SparQ 讀取查詢選定的 r 個通道的 **Full Depth（完整深度）**；
- Thumbnail 則是所有通道都讀 2 bit。

這些方法的共同限制是：對於每個通道，讀取深度都相同，無法根據當前 **Query（查詢）**的實際需求調整。

##### Fathom 的兩大設計支柱
Fathom 讓「**Per-Query Read Depth（逐查詢讀取深度）**」成為可能，核心建立在兩個觀察上：

1. **量化誤差（Quantization Error）**隨位元數指數下降。  
   對於通道 j，若已讀取深度為 t_j，則再多讀 1 bit 所減少的剩餘分數誤差，正比於 g_j · 4^{-t_j}，其中 g_j 是該通道對此查詢 **Score Variance（分數變異數）**的貢獻。  
   這意味著：重要通道的第 1 bit 遠比第 4 bit 有價值，而重要通道的第 4 bit 可能還不如次要通道的第 1 bit。因此，按「**Marginal Value（邊際價值）**」遞減順序分配位元，即為 **Reverse Water-Filling（反向注水法）**，且有 **Closed Form（閉式解）**。

2. **Bit Planes（位元平面）**的 **Channel-Major（通道優先）**儲存。  
   4-bit K 快取若按通道優先、位元切分的方式存放，則某個通道的前 t 個位元平面，就恰好等於該通道的 t-bit mid-rise **Quantizer（量化器）**，且使用相同的 **Block Scale（區塊縮放）**。  
   因此，讀取前 t 個平面是「精確的較低精度量化」，不需要額外維護一份低解析度副本。

##### 多解析度索引的運作方式
Fathom 把現有量化服務堆疊已經持有的 4-bit K 快取，轉換成一個「多解析度索引」：
- 每個查詢根據自己的 q 向量，計算各通道的變異數加權重要性（Variance-Weighted Importance）。
- 在給定的 **Bit Budget（位元預算）**下，用反向注水法決定每個通道應讀取的深度 t_j。
- 由於位元平面是連續的前綴（**Prefix**），GPU 可以按通道順序讀取所需位元數，無需隨機存取。

這樣一來，同樣的 4-bit K 快取既能作為服務用的量化表示，也能作為稀疏解碼的近似索引，幾乎不增加儲存成本。

##### 通道基底選擇規則
Fathom 還提出一個「基底規則」來決定要對哪些表示做位元平面分解：
- 對於使用 **QK-norm（QK 正規化）**的模型（如 **Qwen3-8B**），直接使用原始 **Channel（通道）**即可。
- 對於未使用 QK-norm 的模型（如 **Llama-3.1**、**Qwen2.5**），則先對鍵做 **Karhunen–Loève Transform（KLT）**，再對 KLT 係數做位元平面儲存。

這個規則讓 Fathom 能夠適應不同模型的統計特性，而不需要像 Loki 那樣強制進入 PCA 基底。

#### 實驗數據解讀

##### 主要效能結果
論文在 **Qwen3-8B** 上進行了一百萬 token 長度的測試，結果顯示：
- 與 **136-bit Scans（136-bit 掃描）**的 Loki、Double Sparsity、SparQ r=32 相比，Fathom 的解碼步驟在 GPU 時間上快 **1.67×**。
- 與 **SparQ** 的 **68-bit Read（68-bit 讀取）**（r=16）相比，在相同 GPU 時間下，Fathom 少讀 **18%** 的位元組，且在七個模型與上下文設定中的六個，達到更低的 **Attention Error（注意力誤差）**。

這說明當索引位於主機記憶體時，Fathom 不僅節省頻寬，還能把頻寬節省轉化為實際的時間收益。

##### 位元組節省與等誤差比較
在七個模型與上下文設定（最長至 128k token）上，Fathom 相較於 Double Sparsity 的 136-bit 掃描，達到 **1.8–2.9×** 的等誤差位元組節省。這表示：若要達到與 Double Sparsity 相同的近似誤差，Fathom 只需要讀取約三分之一到二分之一的位元組。這對於頻寬受限的卸載式場景是決定性的優勢。

##### 下游任務表現
- **RULER-Style Tasks（RULER 風格任務）**：在 32k 與 128k 長度下，Fathom 的每個 per-token 掃描都與 **Exact Top-k Decoding（精確 Top-k 解碼）**達到一致。這表示 Fathom 的近似排序沒有損害最終的 top-k 選擇品質。
- **Coding-Agent Sessions（程式設計代理會話）**：在真實的程式開發代理會話中，Fathom 僅用 **92 bits** 就達到了最準確的 136-bit 掃描方法的 **Step Agreement（步驟一致性）**。這驗證了方法在真實長上下文互動場景中的實用性。

##### 不同硬體情境的差異
論文也誠實地指出：當索引已經常駐於 GPU HBM 時，Fathom 並不會更快。這是因為 HBM 頻寬遠高於 PCIe，此時每個位元組的算術開銷成為瓶頸，單純減少位元組無法轉化為時間收益。這個區分非常重要：Fathom 是為「卸載式 KV 快取」這個特定瓶頸設計的，而不是萬能加速器。

#### 與現有研究的比較

##### 相對於 Loki
Loki 將鍵旋轉到 PCA 基底，並讀取前 r 個主成分座標。論文發現，即使使用 fp16 精度，Loki 在 Qwen3-8B 的後期層仍會遺失某些方向，顯示其表示是「秩受限（rank-limited）」的。Fathom 不強制進入單一低秩基底，而是根據當前查詢動態決定每個原始通道或 KLT 通道的讀取深度，因此能保留更多方向資訊。

##### 相對於 Double Sparsity
Double Sparsity 維護一份離線選定的 label cache，讀取固定 c 個通道的 4-bit 表示。它是 Qwen3 模型上最強的離線基線，但通道選擇是靜態的。Fathom 的動態、逐查詢位元分配能夠在相同或更低的位元預算下達到更低誤差，因為它把位元花在「對當前查詢最有價值」的地方。

##### 相對於 SparQ
SparQ 讓查詢選擇 |q_j| 最大的 r 個通道，並以完整深度讀取。這相當於「選對通道，但每個通道都讀一樣多」。Fathom 進一步細化：不僅選通道，還決定每個通道讀多少 bit。因此，在相同 GPU 時間下，Fathom 可以讀更少位元組卻得到更低誤差。

##### 相對於 Thumbnail 與 Landmark 方法
Thumbnail 對所有通道讀取 2-bit，屬於均勻低解析度；Landmark 方法則是減少掃描的鍵數量。Fathom 與它們正交：Fathom 減少的是「每個鍵的位元數」，並且是非均勻、自適應的。它可以與頁面、區塊或地標等減少掃描範圍的技術進一步結合。

##### 主要限制
1. **情境依賴性**：只有在 KV 快取與索引位於主機記憶體或更慢層級時，Fathom 才能轉化為時間收益。若索引已在 HBM，則無加速效果。
2. **儲存格式要求**：需要 4-bit K 快取以通道優先的位元平面方式存放。現有量化服務堆疊可能使用不同的資料佈局，轉換需要工程成本。
3. **只掃描 K 快取**：方法聚焦於鍵的掃描，選出 top-k 後仍需讀取對應的 value。若 value 也卸載，則 value 讀取仍可能是瓶頸。
4. **每查詢開銷**：反向注水法雖有閉式解，但仍需為每個查詢計算通道重要性並決定深度。在極高批次或極短上下文下，這部分開銷可能相對顯著。

#### 未來研究方向

##### 1. 擴展至 Value 快取與完整 KV 索引
Fathom 目前只針對 K 快取做可變深度掃描。未來可研究如何對 V 快取也建立多解析度索引，或設計聯合的 KV 掃描預算分配，以進一步降低卸載式場景下的總頻寬。

##### 2. 動態位元預算與層級自適應
論文提到可使用「每層校準一次的選擇性預算」。未來可探索完全動態的預算分配：根據當前層的重要性、查詢難度、或生成階段（起草 vs. 驗證）即時調整總位元預算。

##### 3. 與分頁、地標、推測解碼的結合
Fathom 減少每個鍵的位元數，而頁面（Pages）、區塊（Blocks）、地標（Landmarks）等方法減少掃描的鍵數。兩者結合可望達到更大加速。此外，與 **Speculative Decoding（推測解碼）**結合，可讓草稿模型也使用稀疏鍵掃描。

##### 4. 硬體協同設計
位元平面的通道優先儲存對記憶體控制器與 DMA 不友善。未來可設計專用的解壓縮單元或記憶體佈局，使 HBM 內的索引也能從可變深度讀取中受益，突破目前「HBM 無加速」的限制。

##### 5. 理論誤差界限與最佳化
反向注水法在此是啟發式但有效的。未來可建立更嚴格的理論框架，證明在給定預算下，該分配方式對 top-k 選擇誤差或注意力輸出誤差的最優性或近似比。

##### 6. 跨架構與多模態延伸
可將 Fathom 應用於 **Mixture-of-Experts（MoE）**模型、視覺語言模型（VLM）的長序列場景，或狀態空間模型（SSM）中的類似鍵值結構，檢驗其泛化能力。

##### 7. 訓練感知量化與索引聯合學習
目前的位元平面來自後訓練量化。未來可在訓練或微調階段，聯合學習量化器、位元平面順序與通道重要性，使稀疏掃描與模型目標更緊密對齊。

## 論文問答

**【背景與動機】**

**Q1：在長上下文稀疏解碼中，當 KV 快取被卸載到主機記憶體時，主要的效能瓶頸是什麼？**
A：當智慧代理會話（agentic sessions）延伸到數十萬甚至一百萬個 token，且多個會話同時常駐時，KV 快取與其索引無法全部放進 GPU 記憶體，而必須存放在主機記憶體或更慢的儲存層。此時，為了執行 Top-k 稀疏注意力，系統必須對所有 n 個鍵進行一次掃描以排序注意力分數，這股跨互連（interconnect）的資料流會成為解碼步驟的主要瓶頸。相較之下，真正被選中的勝出列（winner rows）資料量僅約 200MB 且不隨上下文長度成長，因此瓶頸在於「掃描所有鍵」而非「讀取 top-k 鍵」。

**Q2：現有的逐 token 掃描方法為什麼無法有效降低掃描流量？**
A：現有方法如 Loki、Double Sparsity、SparQ 與縮圖掃描（thumbnail scans）都預先固定每個鍵或每個通道的讀取深度，例如 Loki 固定讀取 r 個主成分座標、Double Sparsity 固定讀取 c 個離線選定的通道、SparQ 固定讀取查詢自選的 r 個通道的完整深度。這些方法對所有被觸及的通道使用相同位元數，忽略了不同查詢下各通道的邊際價值差異。結果是它們會在某些通道上浪費位元（第四個位元的價值很低），卻又在其他通道上分配不足（第一個位元的價值很高），無法達到同預算下的最小注意力誤差。

**Q3：為什麼降低掃描流量對實際生產環境如此重要？**
A：解碼本質上是頻寬受限（bandwidth-bound）的運算，每個生成 token 都會讀取模型權重，並在長上下文時讀取整個 KV 快取。當 KV 快取被卸載後，快取讀取取代權重讀取成為每步成本的主導項，且其大小與上下文長度線性成長。減少每次掃描傳輸的位元數，能直接縮短 GPU 等待資料的時間，並讓單一伺服器同時服務更多長會話，對部署成本與延遲都有顯著影響。

**【方法與創新】**

**Q4：Fathom 的核心方法是什麼？**
A：Fathom 提出逐查詢讀取深度（per-query read depth）的鍵掃描機制，讓每個查詢自行決定要讀取每個鍵通道的多少位元。它把 4-bit K 快取以通道優先（channel-major）方式儲存成位元平面（bit planes），因此讀取某通道的前 t 個平面就等於取得該通道的 t-bit 量化器（quantizer），且與原始區塊縮放（block scale）完全一致。接著，查詢根據各通道對分數變異的貢獻，以反向注水法（reverse water-filling）分配有限的位元預算（bit budget），把更多位元花在邊際價值高的通道上。

**Q5：是哪兩個關鍵觀察讓逐查詢讀取深度成為可能？**
A：第一個觀察是量化誤差每增加一位元約下降四倍，因此通道 j 再多讀一個位元的邊際價值與 \(g_j 4^{-t_j}\) 成正比，其中 \(g_j\) 是該通道對此查詢分數變異數的貢獻；這意味著重要通道的第一個位元遠比第四個位元有價值，而次要通道的第一個位元甚至可能比重要通道的第四個位元更有價值。第二個觀察是，只要把 4-bit K 快取按通道優先儲存為位元平面，那麼讀取前 t 個平面就天然構成精確的 t-bit 中升量化器，不需要額外維護低精度副本。這兩點結合後，原本的 4-bit K 快取就變成一個多解析度索引（multi-resolution index），每個查詢可以按需讀取不同深度。

**Q6：Fathom 在通道基底與預算分配上做了哪些設計選擇？**
A：Fathom 針對不同模型選擇不同的通道表示：對於使用 QK-norm（如 Qwen3）的模型直接使用原始通道，對其他模型（如 Llama-3.1、Qwen2.5）則使用鍵的卡亨南–洛夫轉換（Karhunen–Loève transform, KLT）平面。它還提供一個可選的每層預算（per-layer budget），只需校準一次即可在後續推論中重複使用。反向注水法的位元分配具有閉式解（closed form），因此雖然是逐查詢決策，卻不會帶來昂貴的額外計算開銷。

**【實驗與結果】**

**Q7：論文在哪些基準與設定上評估 Fathom？**
A：實驗涵蓋 7 種模型與上下文設定，最長達 128k token，並在 RULER 風格長上下文任務（32k 與 128k）以及真實程式設計代理會話（coding-agent sessions）上進行評估。對照方法包括 Loki、Double Sparsity、SparQ、2-bit 縮圖掃描與區塊地標索引（block-landmark index）。實驗同時測量了方法所針對的「索引存放在主機記憶體」情境，以及它並不擅長的「索引存放在 GPU 高頻寬記憶體（HBM）」情境。

**Q8：Fathom 的關鍵量化結果有哪些？**
A：在 Qwen3-8B 一百萬 token 的設定下，Fathom 的解碼步驟在 GPU 時間上比 Double Sparsity、Loki 與 SparQ r=32 的 136-bit 掃描快 1.67 倍，且準確度相當或更好。在與 SparQ 68-bit 讀取（r=16）相同的 GPU 時間內，Fathom 能少讀 18% 的位元組，並在 7 個模型與上下文設定中的 6 個達到更低的注意力誤差。在 RULER 風格任務上，所有逐 token 掃描方法都與精確 Top-k 解碼表現一致；在真實程式設計代理會話中，Fathom 僅用 92 bit 就達到最準確 136-bit 掃描的步驟一致性（step agreement）。

**Q9：論文提供了哪些消融實驗與分析？**
A：消融實驗包括通道基底選擇（原始通道 vs. KLT 平面）、每層預算校準、以及讓每個查詢頭各自選擇通道的 SparQ 強化變體。論文也指出 Loki 在 Qwen3-8B 上存在秩限制（rank-limited）問題：即使使用 fp16 座標，32 個主成分座標仍會遺漏後層的方向資訊。此外，§7 針對索引位於 GPU HBM 的情況進行了每位元組算術量分析，解釋為何 Fathom 在該情境下無法加速。

**【應用與影響】**

**Q10：Fathom 在哪些實際場景中能發揮最大效益？**
A：Fathom 專為「KV 快取與掃描索引都存放在主機記憶體」的稀疏解碼情境設計，這正是長時間智慧代理會話與大量並行會話共存的生產環境。當上下文長度達到數十萬到一百萬 token，掃描流量主導跨互連傳輸時，節省的位元組會直接轉化為 GPU 時間縮短。由於它只需要量化服務堆疊已經持有的 4-bit K 快取，因此部署時無需額外維護一份專用索引副本。

**Q11：在產品化部署時需要考慮哪些因素？**
A：首先，必須確保 K 快取以通道優先的位元平面形式儲存，這樣才能支援前綴讀取並構成多解析度索引；對已採用 4-bit KV 量化的服務堆疊而言，這項改動相對輕量。其次，若索引能完全放進 GPU HBM，則 Fathom 不會帶來加速，因此系統應根據記憶體配置選擇是否啟用。最後，雖然逐查詢的位元分配會增加少量計算，但相較於長上下文下的 PCIe 傳輸成本，這部分開銷幾乎可以忽略。

**Q12：Fathom 可能對長上下文大型語言模型服務領域帶來什麼影響？**
A：Fathom 將稀疏注意力索引的設計從「固定深度近似掃描」推進到「逐查詢自適應多解析度索引」，證明按通道重要性動態分配位元可以同時打敗均勻深度的方法在位元組與準確度上的表現。它也展示了量化位元平面可以同時扮演儲存格式與搜尋索引的角色，模糊了 KV 快取與近似索引之間的界線。這可能啟發後續研究進一步探索學習式通道重要性估計、跨層預算分配，以及與頁面／區塊／地標剪枝方法的結合。

**【限制與未來方向】**

**Q13：論文承認了哪些主要限制？**
A：Fathom 在索引位於 GPU 高頻寬記憶體（HBM）時不會更快，因為 HBM 頻寬充裕，改變了每位元組的算術成本權衡。它假設底層服務堆疊已經持有 4-bit K 快取，若沒有這份量化副本，儲存優勢將不復存在。此外，該方法針對 Top-k 稀疏注意力設計，對於需要稠密注意力或極短上下文的工作負載並無幫助。

**Q14：Fathom 在哪些情況下可能出現準確度下降或失效？**
A：如果對查詢各通道的變異數加權重要性估計不準，位元預算可能會被錯誤地分配到邊際價值低的通道，導致注意力誤差上升。對於未使用 QK-norm 而需依賴 KLT 基底的模型，若校準資料與實際分佈漂移，基底不匹配也可能影響排序品質。在位元預算極度緊縮時，多解析度近似仍可能遺漏後層中細微的分數差異，進而影響 top-k 選擇。

**Q15：這項工作指出了哪些未來研究方向？**
A：未來可以將逐查詢讀取深度的概念擴展到 V 快取或聯合 QK 量化，以進一步壓縮跨互連流量。結合 Fathom 與頁面、區塊或地標層級的剪枝，有機會在掃描範圍與每鍵位元數上同時取得更大節省。另一個方向是設計線上學習或跨層適應的通道重要性估計機制，並針對 GPU HBM、主機記憶體與遠端儲存等異質記憶體層級進行聯合最佳化。

## 實務應用指南

### 適用場景

1. **百萬級 token 的程式設計代理會話**  
   當 coding agent 一次會話累積數十萬到一百萬個 token，且同一伺服器同時駐留數十到數百個會話時，KV 快取必須卸載到主機記憶體。Fathom 可將逐 token 鍵掃描的位元數從 136 bit 降到約 92 bit，在 PCIe 頻寬受限的場景顯著縮短解碼步驟。

2. **長文件問答與法律／醫療文本分析**  
   需要反覆查閱長篇上下文（如合約、病歷、論文）的應用，多數 token 為靜態快取內容。Fathom 的逐查詢讀取深度能減少每次生成新 token 時對整份 KV 快取的掃描流量。

3. **量化推論服務堆疊中的稀疏注意力**  
   已部署 4-bit KV 量化、分組查詢注意力（GQA）與 top-k 稀疏注意力的服務，只要 K 快取已以通道優先位元平面存放，即可直接將 Fathom 作為掃描索引，無需額外儲存副本。

4. **多租戶 LLM 推論叢集**  
   當 GPU 記憶體被模型權重與多個會話瓜分，KV 快取被迫放在主機記憶體或 CXL 記憶體池時，Fathom 針對「掃描流量是瓶頸」的硬體條件設計，能降低每步的跨互連資料量。

5. **檢索增強生成（RAG）的長上下文合併**  
   若檢索回來的多篇文件被拼成極長上下文，且大部分內容在多次解碼中重複使用，Fathom 可減少對這些已快取鍵的重複掃描成本。

### 實作前置條件

**資料條件**
- 具代表性的校準資料：需覆蓋實際查詢分佈，用於計算每層通道重要性與設定每層位元預算。
- 驗證資料：RULER 風格長上下文任務、真實 coding-agent 會話紀錄，或下游任務，用於確認稀疏解碼與精確 top-k 解碼的步驟一致性。

**運算條件**
- KV 快取與掃描索引實際存放在主機記憶體（或更慢層級），並透過 PCIe／NVLink／CXL 與 GPU 互連。
- 已具備 4-bit K 快取，且能以通道優先位元平面方式儲存。
- GPU 有足夠算力執行逐查詢反向注水法與 top-k 排序，且這部分開銷小於節省下來的記憶體傳輸時間。

**技術能力**
- 能修改 KV 快取管理器與注意力後端（如 vLLM、SGLang、TensorRT-LLM 等）的資料佈局與掃描核。
- 熟悉 CUDA／Triton 核心開發、量化區塊縮放、GQA、top-k 稀疏注意力。
- 能進行端到端效能剖析，區分「掃描流量瓶頸」與「winner rows 讀取瓶頸」。

---

### 實作步驟建議

1. **確認瓶頸在掃描流量**  
   先剖析現有解碼步驟：測量 dense attention、winner rows 讀取、以及現有掃描（如 SparQ r=16/32）各自的 GPU 時間與跨互連位元數。只有在掃描位元數佔主導且索引卸載時，Fathom 才會加速。

2. **將 4-bit K 快取改為通道優先位元平面佈局**  
   讓每個通道的 4 個位元連續存放。如此讀取前 t 個位元平面即等價於該通道的 t-bit 中點量化器，且可沿用原本的區塊縮放，不需要額外低精度副本。

3. **選擇通道表示方式**  
   若模型使用 QK-norm（如 Qwen3），可直接使用原始通道；若是 Llama-3.1 或 Qwen2.5 等模型，則需離線計算鍵的 Karhunen–Loève 轉換（KLT）並儲存轉換基底，讓位元平面對應到 KLT 通道。

4. **校準每層位元預算**  
   用校準資料計算每層、每個 KV 頭的通道變異數加權重要性，並以反向注水法決定預算。目標是在達到與 136-bit 掃描相當的注意力誤差或步驟一致性前提下，盡量降低平均讀取位元數（論文顯示約 92 bit 可達標）。

5. **實作 Fathom 掃描核**  
   對每個查詢，依據 `g_j · 4^{-t_j}` 的邊際價值遞增分配位元，直到用盡該層預算。核函式需支援每通道不同讀取深度，並將讀出的位元平面還原為近似注意力分數。

6. **整合稀疏 top-k 流程**  
   使用 Fathom 的近似分數對所有鍵排序，選出每查詢頭的 top-k；接著只把這些 winner rows 的完整鍵值對讀回 GPU，計算精確注意力輸出。

7. **端到端驗證**  
   在 RULER 風格任務上確認與精確 top-k 解碼的步驟一致性；在 coding-agent 會話上測量步驟一致性與下游指標；同時監控實際讀取位元數與 GPU 時間。

8. **上線與持續監控**  
   部署後追蹤每層注意力誤差、掃描位元數、解碼延遲。若輸入分佈漂移，可重新校準每層預算或設定動態預算上限。

### 潛在風險與注意事項

- **只在索引卸載時有效**  
  若 KV 快取與掃描索引已可放進 GPU HBM，Fathom 不會更快；論文 §7 的每位元組運算分析說明了原因。部署前務必確認硬體條件。

- **位元平面佈局增加系統複雜度**  
  通道優先位元平面可能與現有 page/block 管理器的張量佈局衝突，需調整記憶體配置與頁面排程邏輯。

- **校準分佈與線上分佈不一致**  
  若實際查詢的通道重要性與校準資料差異大，預算分配會失效。建議保留 fallback 機制，在誤差超過門檻時切回完整掃描或 dense attention。

- **每查詢反向注水法的開銷**  
  雖然有閉式解，但仍需排序或選擇通道。若預算極小或通道數極多，計算開銷可能侵蝕傳輸節省。建議在核心內做微基準測試。

- **低預算下的 late-layer 方向遺失**  
  如同 Loki 在 Qwen3-8B 後層會遺失某些方向，Fathom 若預算過低也可能出現類似問題。需透過 RULER 與真實會話驗證，避免只追求位元數而犧牲準確度。

- **不減少 winner rows 讀取**  
  Fathom 只降低掃描階段流量。若 top-k 選中的 winner rows 數量很大或其值快取也在主機記憶體，則整體加速會被稀釋。

- **GQA 群組選擇策略**  
  論文採用 SparQ 的群組內對 `|q|` 求和後選通道。若改為每個查詢頭各自選通道再取聯集，會增加讀取量，需審慎評估。

### 與其他技術的整合建議

- **與量化服務堆疊整合**  
  Fathom 可直接使用現有 4-bit K 快取，無需額外儲存。建議以自訂 attention backend plugin 形式嵌入 vLLM、SGLang 或 TensorRT-LLM，替換掃描核但保留頁面調度與 KV 量化管線。

- **與 GQA、KV 量化並用**  
  Fathom 專注於 K 快取掃描；V 快取與模型權重仍沿用原有量化與 GQA 設定。這三者可疊加，進一步降低長上下文解碼頻寬。

- **與 H₂O / StreamingLLM 等驅逐策略並用**  
  可採用統一協議：保留前 4 個與最近 32 個 token，其餘 `k−36` 個名額由 Fathom 近似分數決定。這樣既能控制快取大小，又能維持稀疏注意力品質。

- **與推測解碼（Speculative Decoding）並用**  
  Fathom 降低每個 decode step 的延遲，推測解碼減少所需步數，兩者互補。但需注意草稿模型與目標模型的 KV 快取佈局是否一致。

- **與分層記憶體／CXL 整合**  
  當 KV 快取放在 CXL 記憶體池或 NVMe 分層時，掃描流量瓶頸更明顯，Fathom 的效益會進一步放大。但需確保位元平面存取模式對該層記憶體友善。

### 給不同背景讀者的閱讀建議

**初學者**  
把重點放在問題動機與直覺：長上下文讓 KV 快取太大而必須放到主機記憶體，每次生成 token 都要掃描所有鍵，Fathom 的想法是「重要的通道多讀幾位元、不重要的通道少讀幾位元」，就像看縮圖時對重要區域放大、對背景縮小。技術細節可先略過反向注水法與位元平面，理解它只改掃描、不改 winner 的精確計算即可。

**AI 工程師**  
請聚焦 §3 的位元平面佈局、反向注水法閉式解，以及 §4 的實驗協議。實作時要特別注意：通道優先位元平面是否與現有 KV cache manager 相容、每層預算如何在校準資料上決定、以及 §7 對 HBM 駐留情況的分析——這會直接決定你的服務是否適合導入 Fathom。

**研究人員**  
核心貢獻在於「前綴位元平面即精確 t-bit 量化器」與「逐查詢反向注水法」這兩個觀察的結合。建議細讀與 Loki、Double Sparsity、SparQ 的比較（§2、§5、§6），以及 §3.5 針對 QK-norm 與 KLT 的基底選擇規則。論文對 HBM 情況的負面結果也值得一讀，因為它界定了方法的適用範圍。

**產品經理**  
這是一項「硬體條件限定」的效能優化：只有在 KV 快取卸載到主機記憶體、且掃描流量是瓶頸時，才能用更低的位元數達到與現有 136-bit 掃描相近的準確度。適合長上下文代理、多租戶量化推論等場景；若你的部署已將 KV 完全放進 GPU HBM，則不應優先投資此技術。評估時請同時看位元節省、GPU 時間與下游任務一致性三個指標。
