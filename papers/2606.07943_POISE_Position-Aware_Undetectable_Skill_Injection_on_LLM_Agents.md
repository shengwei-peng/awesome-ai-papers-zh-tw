## ⚡ TL;DR

技能污染攻擊面臨可靠性與隱匿性的權衡，YAML注入易被檢查，內文注入則易遭代理懷疑。
本文提出POISE，於結構可行的單一位置嵌入指令，並以上下文感知生成器融入鄰近步驟。
在Skill-Inject上達成89.3%攻擊成功率，僅5.6%變體新增高風險警報，突破靜態防禦。

## 摘要翻譯

代理技能（Agent Skills）提供了一種輕量機制以擴充通用代理，但其開放格式使其暴露於技能污染攻擊（Skill-Poisoning Attack）之下。一種具實務危險性的注入必須保持不可見：若執行酬載（Payload）導致使用者的合法任務失敗，所產生的失敗訊號將引發對該技能的檢查。因此，我們以攻擊成功率（Attack Success Rate, ASR）來評估攻擊，該指標要求注入的酬載必須執行，且使用者的任務在同一試驗中仍須通過其驗證器（Verifier）。在此視角下，先前的技能污染攻擊面臨可靠性—隱匿性權衡（Reliability–Stealth Trade-off）：YAML 前置區塊（YAML Header）注入能可靠地被載入，但易於被檢查；而更具隱匿性的內文注入（Body Injection）將明確的惡意命令置於技能本文中，可靠性卻較低，因為脫離上下文的命令（Out-of-Context Commands）會引起代理自身的懷疑。我們提出 POISE，一種位置感知（Position-Aware）攻擊，將觸發器（Trigger）壓縮為單一、看似良性的內文指令（Body Instruction），將其置於可行的位置，並使用上下文感知生成器（Context-Aware Generator）將其與鄰近的設定或前置步驟融合。在 Skill-Inject 基準上，針對 codex+gpt-5.2，POISE 達到 89.3% 的攻擊成功率，較隨機放置內文基線（Random-Body Baseline）高出 28.0 點，較純 YAML 基線（YAML-Only Baseline）高出 2.6 點，同時保留了內文放置（Body Placement）的隱匿優勢（Stealth Advantage）。此隱匿性即為決定性差距（Decisive Margin）：由於合法技能本文自然需要特權工具操作（Privileged Tool Operations），LLM 掃描器（LLM Scanners）表現得高度敏感（Hyper-Sensitive），在四位評判（Four Judges）與兩個基準（Both Benchmarks）上平均錯誤標記了 74.6% 的乾淨技能（Clean Skill）。POISE 融入這些誤報（False Alarms）之中，僅使 5.6% 的受污染變體（Poisoned Variant）相較其乾淨基線（Clean Baseline）新增高風險警報（High-Risk Alert），使當前的靜態防禦（Static Defenses）失效。

### 核心貢獻（3～5點）
- **提出新穎的攻擊評估視角**：以攻擊成功率（ASR）作為核心指標，要求注入酬載執行且使用者任務同時通過驗證器，揭示先前技能污染攻擊在可靠性與隱匿性之間的根本權衡。
- **設計 POISE 位置感知攻擊方法**：將觸發器壓縮為單一、看似良性的內文指令，並透過上下文感知生成器將其融入鄰近的設定或前置步驟，兼顧可靠性與隱匿性。
- **展現優異的攻擊效能**：在 Skill-Inject 基準上針對 codex+gpt-5.2 達到 89.3% ASR，較隨機內文基線高出 28.0 點，較純 YAML 基線高出 2.6 點。
- **揭示靜態防禦的結構性盲點**：實證 LLM 掃描器因合法技能本文本就涉及特權工具操作而高度敏感，平均誤報 74.6% 的乾淨技能；POISE 僅使 5.6% 的受污染變體新增高風險警報，使現有靜態防禦形同失效。

### 適合對象
本研究最適合關注大語言模型代理（LLM Agents）安全性的研究人員與工程師，特別是從事代理系統攻防研究、AI 供應鏈安全、紅隊演練（Red Teaming）、以及防禦機制設計的學者與業界從業者；同時亦適合關注 AI 可信賴性、第三方套件風險管理與自動化工作流程安全性的政策制定者與產品安全團隊閱讀。

## 深度分析

#### 方法論解析

POISE（Position-aware One-Instruction Skill Injection for Silent Execution）的核心設計理念在於解決技能污染攻擊中長期存在的「可靠性—隱匿性權衡」（reliability–stealth trade-off）。論文將此權衡形式化為兩個失敗閘門：可見性閘門（visible command-bearing content 越多，越容易被靜態掃描器或人工審查發現）與操作相關性閘門（指令若放置位置不當，可能根本不會被代理讀取或執行）。

**三角色分離架構**

POISE 將攻擊構造拆分為三個獨立角色，這種模組化設計是方法論上的重要決策：

1. **結構規則（Structural Rules）**：負責選擇「局部可允許錨點」（locally admissible anchor）。這裡的「位置感知」（position-aware）並非語義層面的理解，而是結構層面的相容性——例如選擇編號步驟（numbered position）或設定步驟（setup position），這些位置在技能本文的格式規約中天然具有指令承載能力。結構規則不依賴語義內容判斷，因此具備跨技能的泛化性。

2. **上下文感知生成器（Context-Aware Generator）**：將承載攻擊的指令（attack-bearing instruction）改寫為與鄰近程序步驟語氣、術語、風格一致的局部本文（local prose）。這是 POISE 與「無上下文隨機內文基線」（context-free random-body baseline）的根本差異——後者僅隨機選擇位置插入指令，容易產生「脫離上下文指令」（out-of-context commands），進而觸發代理自身的懷疑機制。

3. **捆綁輔助腳本（bundled auxiliary script）**：實際的受限動作（bounded action）由隨技能套件一同安裝的腳本執行，而非直接在 SKILL.md 中以自然語言描述完整攻擊流程。這大幅壓縮了「可見的承載命令內容」（visible command-bearing footprint），因為 SKILL.md 中僅出現一行看似無害的指令（如「執行 setup.sh 以初始化環境」），真正的惡意邏輯被封裝在二進位或腳本檔案中。

**攻擊目標的形式化**

論文將攻擊目標實例化為三個危害類別（harm categories）：exfil（憑證或資料外洩設定）、cfg（組態篡改）、sys（系統狀態探測，作為特權 shell 行為的受限代理）。每個類別使用一個固定的「金絲雀腳本」（canary script）跨所有任務執行，金絲雀執行後僅在驗證類別特定的沙箱證據（sandbox evidence）後才寫入成功標記。這種「後置條件驗證」（postcondition-validated）的設計避免了單純以網路回應或檔案存在作為成功指標的脆弱性。

**攻擊成功率（ASR）的雙重條件**

POISE 定義的 ASR 是一個嚴格的複合指標：同一試驗（single trial）中，金絲雀動作必須完成後置條件驗證，且使用者任務必須通過其任務驗證器（task verifier）。這比僅要求「代理執行了某個動作」更接近實際威脅情境——若攻擊導致使用者任務失敗，失敗訊號（failure signal）會引發對技能的檢查（inspection），從而暴露注入。

**無軌跡回饋的設計哲學**

值得強調的是，POISE 在構造階段不使用軌跡回饋（trajectory feedback）或個別代理重新定向（per-agent retargeting）。每個內文編輯（body edit）僅構造一次，然後在四種代理—模型配置（agent–model configuration）上不修改地重播（replay）。這與 SkillJect（Jia et al. 2026）使用的軌跡驅動精化（trace-driven refinement）形成對比，後者雖然可能達到更高 ASR，但需要針對每個代理調整，泛化性與實用部署成本較高。

#### 實驗數據解讀

**主要 ASR 結果**

在 Skill-Inject 基準的合格池（eligible pool）上，以 codex+gpt-5.2 為代理—模型配置，POISE 達到 89.3% ASR。相較之下：

- 無上下文隨機內文基線（context-free random-body baseline）：61.3% ASR，差距為 28.0 個百分點。
- 純 YAML 基線（YAML-only baseline）：86.7% ASR，差距為 2.6 個百分點。

這組數據揭示了 POISE 的核心主張：它達到了 YAML 級別的可靠性，但避開了 YAML 前置區塊（YAML frontmatter）的可見性暴露。換言之，POISE 在「可靠性—隱匿性權衡曲線」上推進了前沿，而非僅優化單一維度。

**跨配置轉移性**

同一內文編輯在四種代理—模型配置上無需重新定向，即達到 86.7–90.7% ASR 的區間。這顯示 POISE 的結構規則與上下文感知生成器產生的指令具有跨架構穩定性，不依賴特定模型的弱點或偏好的措辭。

**靜態防禦的有效性評估**

這是論文最具說服力的實驗結果之一。論文評估了四位評判（four judges，即四種 LLM 掃描器）在兩個基準上的表現：

- 乾淨技能（clean skill）的誤報率（false-positive rate）平均為 74.6%。這意味著現有 LLM 掃描器對合法技能本文中常見的「特權工具操作」（privileged tool operations）過度敏感，幾乎每四個合法技能就會被錯誤標記為高風險。
- POISE 產生的受污染變體（poisoned variant）相較其乾淨基線（clean baseline），平均僅有 5.6% 產生新的高風險警報（high-risk alert）。

這組數據的深層含義是：POISE 的攻擊並非「躲避掃描器」，而是「融入掃描器已有的雜訊中」。由於掃描器對乾淨技能的誤報已達 74.6%，POISE 注入的指令所引發的額外警報相對於基線噪音而言幾乎不可區辨。這對靜態防禦（static defenses）的有效性提出了根本性質疑——單純降低警報閾值會產生更多誤報，而提高閾值則會讓 POISE 類攻擊完全隱形。

**實驗設計的嚴謹性**

所有實驗在隔離的 Docker 沙箱中執行，使用研究者控制的端點與夾具（fixtures）。exfil 金絲雀雖發出有限的 HTTP 請求嘗試，但網路回應或傳遞不計入評分。這種「受限代理」（bounded surrogate）設計既保留了攻擊的代表性，又控制了實際危害範圍，符合負責任的漏洞研究倫理。

#### 與現有研究的比較

**與 Skill-Inject（Schmotz et al. 2026）的關係**

Skill-Inject 建立了技能檔案作為注入向量，並研究了上下文式、位置式與腳本式攻擊。POISE 與其共享威脅模型與部分評測基礎設施，但 POISE 明確將攻擊構造約束為「單一指令、單一位置」，這是對 Skill-Inject 中「多步驟內文污染」（multi-step body poisoning）的精煉與極端化。Skill-Inject 的多步驟方法雖然可能達到類似 ASR，但會擴大可見的承載命令足跡（visible command-bearing footprint），降低隱匿性。

**與 SkillJect（Jia et al. 2026）的對比**

SkillJect 使用軌跡驅動精化來優化隱匿的注入技能，屬於「自適應攻擊」（adaptive attack）。POISE 明確放棄軌跡回饋，採用「一次構造、跨配置重播」的策略。這代表兩種不同的研究哲學：SkillJect 追求在特定代理上的極致性能，POISE 追求在未知代理上的穩健泛化。從實用攻擊者角度，POISE 的方法更接近真實供應鏈場景——攻擊者無法事先觀察目標代理的執行軌跡。

**與 SkillAttack（Duan et al. 2026）的區分**

SkillAttack 對良性技能進行紅隊測試但不修改它們，屬於「非破壞性探測」。POISE 則是「破壞性注入」，直接修改技能套件。兩者互補：SkillAttack 揭示哪些合法技能容易被誤用，POISE 展示如何構造難以偵測的惡意變體。

**與 Qu et al.（2026）的定位**

Qu et al. 研究技能生態中嵌入的惡意邏輯，POISE 則聚焦於單一技能的單一指令注入。POISE 的貢獻在於回答一個更精細的問題：「最少需要多少可見的承載命令內容，才能實現可靠且保留任務的執行？」

**與 YAML 注入攻擊的比較**

YAML 前置區塊注入（Zhang, Lazuka, and Murag 2025）具有預載入（preloaded）與可靠的優勢，但「顯而易見」（conspicuous）——任何審查者打開 SKILL.md 都會立即看到 YAML 中的可疑指令。POISE 的隱匿優勢（stealth advantage）正是相對於此：內文放置（body placement）天然處於合法程序步驟的語境中，需要更深的語義分析才能識別。

**限制與未涵蓋面向**

POISE 的方法論有幾個值得注意的限制：

1. **依賴捆綁腳本**：受限動作必須由輔助腳本執行，這要求攻擊者能將腳本打包進技能套件。在某些受限的技能生態中，腳本可能被沙箱禁止或需要額外權限。
2. **結構規則的覆蓋範圍**：結構規則選擇「編號位置」或「設定位置」，但並非所有技能本文都具有清晰的編號結構。對於高度敘事性或非結構化的技能本文，POISE 的適用性可能下降。
3. **上下文感知生成器的品質**：論文中未詳細說明生成器的具體實現（是基於 LLM 的改寫、模板填充，還是其他機制），這影響了方法的透明度與可重現性。
4. **金絲雀動作的代表性**：三個危害類別（exfil、cfg、sys）作為「受限代理」是否充分代表真實攻擊者的能力，值得進一步驗證。

#### 可重現性評估

**程式碼與資料的可用性**

從提供的全文脈絡中，論文未明確聲明程式碼、資料集或模型權重是否開源。arXiv 預印本（arXiv:2606.07943v2）通常會附帶補充材料聲明，但目前可見的內容中僅提及「實作細節見附錄 G」（implementation details appear in Appendix G），這暗示存在技術細節但未承諾公開發布。

**可重現性的關鍵要素評估**

1. **方法論描述的充分性**：POISE 的三角色分離架構（結構規則、上下文感知生成器、捆綁腳本）在論文中描述清晰，但「上下文感知生成器」的具體演算法未在主文中展開。若該生成器是基於 LLM 的提示工程，則其行為可能隨基礎模型版本而變化；若基於規則模板，則可重現性較高。

2. **評測基準的可用性**：Skill-Inject 基準由 Schmotz et al.（2026）提出，假設其已公開，則 POISE 的實驗可在該基準上重現。但論文中提及「兩個基準」（both benchmarks），第二個基準的名稱未在提供的脈絡中明確，可能需要查閱完整論文。

3. **代理—模型配置**：codex+gpt-5.2 及其他三種配置涉及商業 API，其行為可能隨服務版本更新而變化，這對長期可重現性構成挑戰。

4. **金絲雀腳本與沙箱設定**：Docker 沙箱、研究者控制的端點與夾具的具體配置對重現至關重要，但論文中僅以「見附錄 G」帶過。

5. **四位評判（four judges）的身份**：論文未明確列出四種 LLM 掃描器的具體名稱或版本，這使得靜態防禦評估難以獨立驗證。

**可重現性風險**

整體而言，POISE 的可重現性處於中等水準。方法論框架清晰，但關鍵實作細節（生成器、沙箱、評判）依賴附錄，而附錄內容在提供的脈絡中不可見。對於安全研究社群，建議作者在正式發表時附帶開源程式碼與基準配置，以利獨立驗證。

#### 未來研究方向

**1. 動態與自適應防禦機制**

POISE 的結果顯示靜態防禦（static defenses）在面對融入雜訊的攻擊時幾乎失效。直接的研究方向是探索動態防禦——例如在代理執行技能步驟時監控工具呼叫的異常模式，或在沙箱中實際執行技能指令並比對預期行為。這類「執行時驗證」（runtime verification）可能比靜態掃描更有效，但也帶來效能成本。

**2. 結構感知防禦的可行性**

既然 POISE 利用「結構可允許錨點」（locally admissible anchor）來放置攻擊，反向思考是訓練防禦模型識別「結構上可允許但語義上可疑」的指令。這需要大量標註資料，且可能面與 POISE 生成器相同的對抗演化問題。

**3. 跨語言與跨文化的技能污染**

POISE 的實驗主要在英文技能本文上進行。中文、日文、阿拉伯文等語言的技能本文可能具有不同的結構規約與語境特徵，POISE 的結構規則與上下文感知生成器是否同樣有效，是值得探索的問題。

**4. 多模態技能套件的攻擊面**

當前 POISE 假設技能套件僅包含 SKILL.md 與文字腳本。隨著多模態代理的發展，技能套件可能包含圖片、音訊、影片等資產。攻擊者可將惡意指令編碼在圖片的隱寫術（steganography）中，或利用視覺模型的 OCR 弱點，這是 POISE 未涵蓋的攻擊面。

**5. 聯邦與分散式技能生態的信任機制**

POISE 假設攻擊者控制單一第三方技能套件。在實際生態中，技能可能來自多個來源並相互引用。探索「技能供應鏈的信任傳遞」（trust propagation across skill supply chains）是重要的系統性研究方向，例如透過加密簽章、聲譽系統或去中心化驗證機制。

**6. 對 POISE 的對抗性評估**

既然 POISE 達到 89.3% ASR，下一個問題是：是否存在「POISE 增強版」能突破 95% ASR？例如結合軌跡回饋（向 SkillJect 靠攏）或利用代理的特定弱點。同時，也應探索「POISE 變體」——例如將攻擊分散到多個技能套件中，或利用技能的版本更新機制。

**7. 經濟與激勵分析**

技能污染攻擊的防禦需要成本（審查、沙箱執行、掃描）。POISE 的結果暗示現有防禦的成本效益比不佳。未來研究可從經濟學角度分析：何種防禦投資組合能最大化降低攻擊成功率，同時控制誤報成本？

**8. 形式化驗證技能安全性**

長期方向是對技能本文進行形式化驗證（formal verification），證明其所有可能的執行路徑都不會違反安全策略。這在理論上可徹底消除 POISE 類攻擊，但在實務上面臨技能本文自然語言的模糊性與代理行為的不確定性挑戰。

**9. 人機協作審查介面**

既然 LLM 掃描器的誤報率達 74.6%，純自動化防禦不可行。未來可探索「人機協作審查介面」（human-in-the-loop review interface），讓 LLM 標記可疑區段，人類審查者聚焦於高風險片段，從而提高審查效率。

**10. POISE 在真實部署中的縱向研究**

目前 POISE 的評測在受控沙箱中進行。縱向研究（longitudinal study）追蹤真實技能生態中 POISE 類攻擊的出現頻率、攻擊者使用的具體技術、以及防禦方的應對演化，將有助於理解攻擊與防禦的實際動態。

## 論文問答

**Q1：POISE 究竟要解決什麼核心問題？**
A：POISE 處理的是 LLM 代理面臨的「技能污染攻擊」（skill-poisoning attack）問題，特別是攻擊者透過第三方技能套件（skill package）注入惡意指令的供應鏈威脅。論文的關鍵觀察是：實務上危險的攻擊必須「隱形」——若執行酬載導致使用者任務失敗，失敗訊號會引發對該技能的檢查，因此攻擊必須在使用者任務仍通過驗證器的同一試驗中完成金絲雀動作（canary action）。POISE 試圖在「可靠性—隱匿性權衡」（reliability–stealth trade-off）曲線上找到一個受限但實務重要的操作點，使單一指令即可同時達成攻擊成功與任務保留。

**Q2：為何現有的技能污染攻擊方法會失敗？**
A：現有方法大致分為兩類，但都無法同時兼顧可靠性與隱匿性。YAML 前置區塊（YAML frontmatter）注入雖然會被代理預載、執行可靠，但因其結構化、可預測的特性極易被人工或自動掃描器檢查出來；相對地，將明確惡意命令直接放入技能本文（body）的內文注入雖然較隱蔽，但因命令脫離上下文（out-of-context commands）容易引起代理自身的懷疑，導致執行可靠性下降。這種「可靠但顯眼 vs. 隱蔽但不可靠」的二元困境，正是 POISE 想要突破的核心限制。

**Q3：為什麼這個問題在實務上至關重要？**
A：已安裝的技能對代理而言是「可重複使用的程序性授權」（reusable procedural authority），其本文指定工具如何排序執行，捆綁腳本則提供可執行支援，這使得受污染套件能在合法工作流程內部，從同一通道呈現攻擊者選定的命令，而非作為與使用者任務競爭的獨立請求。此外，由於技能套件通常來自第三方來源，受污染技能構成一條從供應鏈內部操控工具使用的攻擊路徑，其威脅等級遠高於短暫的檢索段落注入，因此研究如何在受限的可見攻擊內容下達成可靠且任務保留的執行，具有迫切的實務意義。

**Q4：POISE 的核心方法是什麼？**
A：POISE（Position-aware One-Instruction Skill Injection for Silent Execution）是一種位置感知攻擊，將觸發器壓縮為單一、看起來良性的內文指令，並放置於結構上可行的編號或設定位置。具體而言，它由三個角色組成：結構規則（structural rules）負責選擇局部可允許的錨點（locally admissible anchor），上下文感知生成器（context-aware generator）將指令融合於鄰近的設定或前置步驟，而捆綁的輔助腳本（auxiliary script）則實作受限的金絲雀動作。這種設計使攻擊承載的可見命令內容降至最低，同時透過結構相容性與上下文融合維持執行可靠性。

**Q5：POISE 的關鍵創新點為何？**
A：POISE 的關鍵創新在於將「位置感知」與「單一指令」兩個概念結合，挑戰了「可見攻擊內容越多越可靠」或「越少越隱蔽」的傳統假設。它證明了只要選擇結構上相容的錨點並透過上下文感知生成器使指令與鄰近程序自然融合，單一指令即可同時達到 YAML 級別的可靠性（89.3% ASR）並保留內文放置的隱匿優勢。更重要的是，整個構造過程無需軌跡回饋（trajectory feedback）或個別代理重新定向（per-agent retargeting），每個內文編輯只需構造一次即可在所有四種代理—模型配置上重播，這大幅降低了攻擊的工程成本。

**Q6：POISE 在設計上做了哪些關鍵取捨？**
A：POISE 在設計上做了幾項重要取捨：首先是將攻擊承載的可見內容嚴格限制為「單一指令」，以最小化審查表面（review surface）；其次是將實際的受限動作委派給捆綁的輔助腳本執行，使 SKILL.md 中的命令本身保持簡短且語義模糊。再者，它採用三個固定的傷害類別（exfil、cfg、sys）並共用同一個金絲雀腳本，透過後置條件驗證（postcondition validation）而非網路回應來評分，以避免依賴外部網路並提升可重現性。這些設計共同使 POISE 能在一個受限但實務重要的操作點上達成可靠性與隱匿性的平衡。

**Q7：POISE 使用哪些基準與模型配置進行評測？**
A：POISE 的主要評測在 Skill-Inject 基準上以 codex+gpt-5.2 代理—模型配置進行，並在四種代理—模型配置上測試內文編輯的可轉移性。為了評估靜態防禦的有效性，論文使用了四位 LLM 評判（four judges）對兩個基準（both benchmarks）上的乾淨技能與受污染變體進行掃描，計算高風險警報（high-risk alert）的差異。這種多配置、多評判的設計使結果能同時反映攻擊的跨模型泛化能力與對當前靜態防禦的繞過效果。

**Q8：POISE 的關鍵實驗結果為何？**
A：在 Skill-Inject 基準上以 codex+gpt-5.2 評測時，POISE 達到 89.3% 的攻擊成功率（ASR），較無上下文的隨機內文基線高出 28.0 個百分點，並較純 YAML 基線高出 2.6 個百分點，同時保留了內文放置的隱匿優勢。跨四種代理—模型配置的轉移實驗顯示，POISE 的內文編輯無需重新定向即可達到 86.7%–90.7% 的 ASR，展現出極佳的可轉移性。在靜態防禦評測方面，POISE 僅使 5.6% 的受污染變體相較其乾淨基線新增高風險警報，而 LLM 掃描器對乾淨技能的誤報率平均高達 74.6%，凸顯了當前靜態防禦在「高度敏感」狀態下的無效性。

**Q9：POISE 進行了哪些消融實驗來驗證各元件的貢獻？**
A：論文的消融設計主要透過三個基線的對比來驗證各元件的貢獻：無上下文的隨機內文基線（context-free random-body baseline）證明了「位置感知」與「上下文融合」的必要性，因為隨機放置的指令因脫離上下文而執行率僅 61.3%；純 YAML 基線（YAML-only baseline）則證明了 POISE 在不放棄隱匿優勢的前提下仍能達到 YAML 級別的可靠性。此外，與多步驟內文污染（multi-step body poisoning）的對比顯示，單一指令版本在維持 ASR 的同時大幅縮小了可見命令足跡，這驗證了「單一指令」設計在隱匿性上的關鍵作用。

**Q10：POISE 的研究成果適用於哪些實務場景？**
A：POISE 的研究成果直接適用於任何依賴第三方技能套件的 LLM 代理部署場景，包括開源技能市集、企業內部代理平台以及個人開發者從外部來源安裝技能的場景。在這些場景中，使用者通常無法逐一審查每個技能的完整內容，POISE 證明了即使經過仔細檢視，單一融合良好的指令仍可能逃過偵測，這對技能審核流程與供應鏈安全實務具有重要啟示。此外，其評測方法論（後置條件驗證 ASR 加上配對靜態發現差異）也可被防禦方採用，作為評估自身掃描器誤報率與攻擊繞過率的標準化框架。

**Q11：POISE 對產品與防禦設計有何具體啟示？**
A：POISE 揭示了一個對產品設計極為重要的警訊：當前 LLM 掃描器對乾淨技能的平均誤報率高達 74.6%，這意味著任何試圖以「更敏感」來提升偵測率的策略都會立即癱瘓正常使用流程，因此單純提高敏感度並非可行方向。產品設計者應意識到，技能本文中合法的特權工具操作（privileged tool operations）會自然觸發警報，這使得「融合於誤報之中」成為攻擊者的隱身策略。具體而言，防禦系統需要從靜態分析轉向結合執行時監控、軌跡異常偵測與多模態驗證的縱深防禦，而非僅依賴 LLM 評判的單一靜態掃描。

**Q12：POISE 對代理安全研究領域有何整體影響？**
A：POISE 將技能檔案攻擊的「可靠性—偵測前沿」（reliability–detection frontier）向前推進，證明了在受限的可見攻擊內容下仍可達成任務保留的可靠執行，這迫使研究者重新思考「最小可見攻擊足跡」的概念。其方法論貢獻——特別是後置條件驗證 ASR 與配對靜態發現差異的評測框架——為未來攻擊與防禦研究提供了更嚴謹的比較基準。更深遠的影響在於，POISE 凸顯了當前靜態防禦在面對上下文融合攻擊時的根本侷限，可能促使整個領域從「特徵匹配」轉向「語義推理」與「執行時驗證」等新一代防禦範式。

**Q13：POISE 自身存在哪些已承認的限制？**
A：POISE 在論文中坦承了若干限制：首先，單一指令的約束雖然提升了隱匿性，但也限制了攻擊者可承載的動作複雜度，僅能委派給捆綁腳本的「受限動作」（bounded action）；其次，整個構造過程不使用軌跡回饋或個別代理重新定向，雖然提升了可轉移性，但代價是無法針對特定代理的弱點進行優化。再者，攻擊的傷害類別僅限於三種（exfil、cfg、sys），且使用固定的單一金絲雀腳本，可能無法涵蓋所有實務攻擊場景；最後，所有實驗在隔離的 Docker 沙箱中執行，雖然提升了可重現性，但與真實部署環境的網路與系統條件仍存在差距。

**Q14：POISE 在哪些情況下可能會失敗？**
A：POISE 的失敗模式可從幾個面向分析：若結構規則無法在目標技能中找到局部可允許的錨點（例如技能本文完全沒有編號步驟或設定段落），則攻擊將無處可放置；若上下文感知生成器產生的指令與鄰近程序的融合度不足，仍可能被代理識別為脫離上下文而拒絕執行。此外，若使用者的任務本身極為敏感或代理被配置為對所有特權操作進行強制確認，則即使指令融合良好，攻擊仍可能在執行階段被攔截。最後，若未來防禦方引入執行時軌跡監控或跨技能一致性檢查，POISE 的靜態構造特性可能使其更容易被這類動態防禦識別。

**Q15：POISE 之後有哪些值得探索的未來方向？**
A：POISE 開啟了多條值得探索的研究路線：在攻擊端，可研究多指令但仍維持低可見足跡的進階變體，或結合軌跡回饋進行針對性優化（但需權衡工程成本）；在防禦端，最迫切的方向是開發能區分「合法特權操作」與「惡意特權操作」的語義推理式掃描器，以及結合執行時監控的縱深防禦架構。更宏觀地看，未來研究應探索「技能生態系統」層面的安全機制，例如技能簽章、來源驗證與聲譽系統，以從供應鏈源頭降低受污染技能進入代理環境的機率，這也是 POISE 論文所暗示但未深入探討的長期解決方向。

## 實務應用指南

### 適用場景

以下場景均以**防禦方與紅隊演練**為出發點，目的是評估並強化代理系統對技能污染攻擊的抵抗力，而非協助實際攻擊部署。

1. **企業內部代理平台的紅隊演練**：金融、醫療、法律等高度受監管產業的內部 AI 代理平台，可採用 POISE 的方法論作為紅隊測試案例，驗證自家代理在面對「單一指令、上下文融合」型攻擊時是否會在不觸發任務失敗的前提下執行惡意動作。

2. **第三方技能市集的安全審核管線**：類似 Hugging Face、GitHub Marketplace 的技能分發平台，可將 POISE 揭示的「位置感知 + 上下文融合」模式納入審核啟發式，識別那些刻意將可疑指令藏在編號步驟或前置設定中的套件。

3. **代理框架供應商的防禦基準測試**：提供 agent runtime 的廠商（如 Anthropic、OpenAI Agents SDK 的下游框架）可將 POISE 的攻擊構造方式作為基準測試集，量化自家靜態掃描器、行為監控、軌跡審查模組的偵測率與誤報率。

4. **學術與產業界的攻防基準研究**：資安研究社群可將 POISE 與 Skill-Inject、SkillJect 等既有攻擊並列比較，推動「可靠性—隱匿性」前沿曲線的標準化評測。

5. **漏洞獎勵計畫的測試案例庫**：企業或開源代理生態系（如 MCP、Claude Skills 相容系統）運營的漏洞獎勵計畫，可收錄 POISE 風格的測試樣本，作為外部研究員提交報告時的參考基準。

### 實作前置條件

**資料前置條件**
- **基準資料集**：需取得或重建 Skill-Inject 基準（含合法技能本體、使用者任務、任務驗證器），以及至少一個對照基準（論文中提及「兩個基準」但未在摘要中具名）。
- **乾淨技能語料庫**：用於建立「clean baseline」以計算「新增高風險警報率」，建議至少蒐集數十至數百個真實世界的 SKILL.md 樣本。
- **金絲雀腳本與沙盒環境**：需準備三類（exfil、cfg、sys）的受限腳本，並具備 honey-tagged 憑證、固定狀態探測點、可驗證的後置條件檢查器。
- **任務驗證器集合**：每個使用者任務都需有可程式化檢查的通過條件，否則無法計算「同一試驗中任務仍通過」的 ASR。

**運算前置條件**
- **模型 API 配額**：需能呼叫 codex、gpt-5.2 等前沿模型，且具備足夠的 context window 來容納完整技能檔案。
- **隔離沙盒**：所有實驗必須在隔離的 Docker 環境中執行，避免金絲雀動作（特別是 exfil 類）影響真實系統。
- **四位 LLM 評判**：需準備四款獨立的 LLM 掃描器作為靜態防禦評測的評判。

**技能前置條件**
- 熟悉 LLM agent 架構（tool use、function calling、code execution sandbox）。
- 理解 prompt injection 攻防基本概念與既有分類法（Zhan et al. 2024、Schmotz et al. 2026）。
- 具備 prompt engineering 與結構化文件（YAML frontmatter、Markdown）處理能力。
- 對靜態分析、誤報率、paired difference 評測設計有基本認識。

### 實作步驟建議

以下步驟描述如何**重現並應用 POISE 的方法論於防禦評測**，而非提供攻擊部署教學。

**步驟一：建立評測骨架**
- 將 Skill-Inject 基準載入隔離沙盒，確認每筆任務都有可程式化驗證器。
- 為每個技能建立「clean baseline」快照：原始 SKILL.md、原始輔助腳本、四位評判的掃描結果。

**步驟二：構造對照組**
- 實作「context-free random-body baseline」：在技能本文中隨機位置插入一條攻擊指令。
- 實作「YAML-only baseline」：將攻擊指令置於 YAML frontmatter。
- 兩者皆需使用相同的金絲雀腳本與後置條件檢查。

**步驟三：構造 POISE 變體**
- 套用結構規則：掃描技能本文，識別編號步驟或前置設定段落作為「局部可允許錨點」。
- 使用上下文感知生成器：將攻擊指令改寫為與鄰近步驟語意相容的單一指令（例如偽裝成「驗證環境設定」的 setup 步驟）。
- 將受限動作委派給捆綁的輔助腳本，避免在指令本文中暴露具體命令。

**步驟四：執行 ASR 評測**
- 對每個變體在四種代理—模型配置上各執行一次完整試驗。
- 記錄兩個獨立布林值：金絲雀後置條件是否成立、任務驗證器是否通過。
- ASR = 兩者同時為真的比例。

**步驟五：執行靜態防禦評測**
- 將每個變體送交四位 LLM 掃描器，記錄高風險警報清單。
- 計算「paired difference」：對每個技能，比較其 clean baseline 警報集與變體警報集，計算新增警報率。
- 同時計算 clean skill 的誤報率作為對照。

**步驟六：分析與報告**
- 比較 POISE 與兩個基線的 ASR 差距。
- 比較 POISE 與 YAML-only 的新增警報率差距。
- 重點關注「可靠性—隱匿性前沿」的位移，而非單一指標。

### 潛在風險與注意事項

**雙重用途風險（Dual-Use Risk）**
POISE 是一個明確的攻擊構造方法。將其方法論對外公開時，必須確保僅用於：(a) 取得授權的紅隊演練、(b) 防禦基準測試、(c) 學術研究。任何未經授權的實際部署皆違反多國資安法規與該論文之倫理聲明。

**沙盒逃逸風險**
exfil 類金絲雀腳本會嘗試發出 HTTP 請求。必須確保：(a) 沙盒網路完全隔離或僅指向研究者控制的接收端、(b) honey-tagged 憑證不含任何真實資料、(c) 接收端僅記錄 metadata 而不儲存 payload。

**評測偏差風險**
- **模型版本漂移**：codex、gpt-5.2 等模型版本更新可能改變 ASR 數字，需固定模型版本並記錄評測日期。
- **基準污染**：若評測用的技能本體已進入模型訓練資料，結果可能失真；應使用模型未見過的私有技能集做交叉驗證。
- **評判同質化**：四位 LLM 評判若底層模型相近，可能共享盲點；建議至少包含一款非 OpenAI 家族的評判。

**誤報陷阱**
論文揭示 LLM 掃描器對合法技能的平均誤報率高達 74.6%。這意味著：
- 不能單純以「警報數量」作為防禦有效性指標。
- 必須採用 paired difference 設計，區分「clean baseline 已有的警報」與「新增警報」。
- 高誤報率會導致審查者疲勞，反而降低對真實攻擊的警覺。

**單一指令的脆弱性**
POISE 的設計前提是「單一指令」。若防禦方加入「跨步驟一致性檢查」或「指令數量上限啟發式」，可能直接瓦解此攻擊；但同時也可能提高對合法多步驟技能的誤報。

**軌跡回饋的缺失**
POISE 不使用軌跡回饋或個別代理重新定向，這是其「一次構造、跨配置重播」的優勢，但也意味著針對特定代理的客製化變體可能達到更高 ASR。防禦方應假設攻擊者會進一步客製化。

### 與其他技術的整合建議

**與既有 prompt injection 防禦整合**
- **行為監控層**：在 agent runtime 中加入「任務無關動作偵測器」，當代理執行與當前任務語意無關的腳本呼叫時觸發警報。POISE 的金絲雀動作通常與使用者任務無關，這是關鍵訊號。
- **指令密度分析**：將 POISE 的「單一指令」特性反過來利用——對技能本文中的命令承載指令做密度統計，過高或過低皆為可疑訊號。
- **跨來源信任鏈**：將技能套件視為類似 npm 或 PyPI 的供應鏈節點，引入套件簽章、來源驗證、依賴圖譜分析。

**與 SIEM/SOAR 整合**
- 將 POISE 評測中發現的「新增高風險警報」模式編碼為 SIEM 規則，例如：「同一技能在 clean baseline 與變體間的警報差集超過閾值」。
- 將 ASR 評測結果作為 threat intelligence feed，定期更新內部代理的風險評分。

**與程式碼審查流程整合**
- 對第三方技能套件實施類似開源軟體的 code review：審查 SKILL.md 的指令結構、輔助腳本的執行權限、YAML frontmatter 的可疑欄位。
- 將 POISE 的「位置感知」邏輯編碼為 linter 規則，標記那些刻意嵌入編號步驟或前置設定的可疑指令。

**與紅隊自動化平台整合**
- 將 POISE 的三階段構造（結構規則 → 上下文生成 → 腳本委派）封裝為可重複使用的 red team toolkit。
- 與既有 prompt injection 基準（如 BIPIA、AgentBench）並列，形成完整的代理安全評測套件。

**與學術基準整合**
- 將 POISE 與 Skill-Inject、SkillJect、SkillAttack 等並列為「技能污染攻擊家族」的標準成員。
- 推動「可靠性—隱匿性前沿曲線」成為該領域的標準評測圖表。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「為什麼單一指令、上下文融合的攻擊比隨機插入更難被偵測」這個核心直覺。接著跳到第 3 節了解三階段構造（結構規則、上下文生成、腳本委派）的高階概念。技術細節（附錄中的 prompt 模板、腳本實作）可暫時略過，重點是建立「攻擊表面 = 可見內容 + 操作相關性 × 上下文相容性」這個心智模型。

**給 AI 工程師**：應重點研讀第 3 節的威脅模型與三階段構造，理解 POISE 為何選擇「單一指令」而非「多指令分散」。在自家代理系統中，應實作：(1) 技能載入時的結構化解析（區分 YAML 與 body）、(2) 指令與任務語意的相關性檢查、(3) 輔助腳本的權限沙箱化。論文中揭示的 74.6% 誤報率是關鍵警訊——純 LLM 靜態掃描不足以作為唯一防禦層。

**給研究人員**：應將 POISE 視為「可靠性—隱匿性前沿」上的一個新操作點，並與 SkillJect 的軌跡驅動方法、SkillAttack 的非修改式紅隊方法進行三角比較。值得追問的研究問題包括：(1) 若防禦方加入「跨步驟一致性檢查」，POISE 的 ASR 會下降多少？(2) 「單一指令」是否為最優操作點，還是存在更小的攻擊承載形式？(3) 上下文感知生成器是否可被對抗性地反向工程，導致掃描器對特定融合模式產生盲點？

**給產品經理**：應理解 POISE 揭示的商業風險：第三方技能市集是供應鏈攻擊的高風險節點。在產品決策上，應考慮：(1) 是否對第三方技能實施類似行動應用商店的審核機制、(2) 是否向使用者揭露技能的權限範圍、(3) 是否提供「技能隔離執行」的能力，讓使用者任務與技能副作用在不同的沙盒中執行。論文中 89.3% ASR 與 5.6% 新增警報率的組合，意味著「使用者幾乎不會察覺攻擊發生」——這是產品層級必須正視的 UX 與信任風險。
