## ⚡ TL;DR

訓練 API 呼叫代理需要大量高品質軌跡，但傳統方法依賴完整實作環境與可執行 API，造成可擴展性瓶頸。
本文提出 ESAT，僅以 API 規格為輸入，利用 LLM 即時模擬環境回饋，生成任務、軌跡並過濾低品質樣本。
在 AppWorld 與 OfficeBench 上，合成資料微調顯著提升效能，證明 LLM 模擬 API 實用且可擴展。

## 摘要翻譯

訓練 API 呼叫大型語言模型代理（API-calling LLM agents）需要大量高品質軌跡（trajectories）。然而，大規模收集此類資料通常需要完整實作環境（fully implemented environments）、可執行 API（executable APIs），以及真實且預先填充的後端資料庫（pre-populated backend databases），這對可擴展性（scalability）造成重大瓶頸。為克服此問題，我們提出一種無環境合成資料生成（Environment-free Synthetic Data Generation）方法，將大型語言模型（LLM）作為動態即時（on-the-fly）的數位世界模型（digital world models）加以運用。僅給定 API 規格（API specifications），本方法即可生成模擬代理（agent）與有狀態環境（stateful environment）互動的軌跡。具體而言，大型語言模型首先生成多樣化且可利用所提供 API 解決的任務；教師代理（teacher agent）接著迭代地解決每個任務，同時模擬器大型語言模型（LLM simulator）根據任務情境（task context）與模擬歷史（simulation history）生成一致的合成 API 回應（synthetic API responses）。最後，大型語言模型評判器（LLM judge）對軌跡進行過濾，以確保最終資料集的品質。本研究在具挑戰性的 AppWorld 與 OfficeBench 評測基準（benchmarks）上評估所提方法，這些基準同時包含資訊檢索任務（information-retrieval tasks）與狀態改變任務（state-changing tasks）。使用本研究的合成資料（synthetic data）進行微調（fine-tuning）可帶來顯著的效能提升（performance gains），顯示針對 API 呼叫代理的有效監督訊號（supervision）無需任何可執行環境（executable environment）即可生成。本研究結果確立基於大型語言模型的 API 模擬（LLM-based API simulation）為一個實用且可擴展（scalable）的解決方案，可用於訓練橫跨多樣化 API 生態系統（API ecosystems）的代理。

### 核心貢獻（3～5點）
- 指出大規模收集高品質代理軌跡需仰賴完整實作環境與後端資料庫，形成可擴展性瓶頸（scalability bottleneck）。
- 提出無環境合成資料生成方法，僅憑 API 規格即可將大型語言模型作為動態即時的數位世界模型，生成代理與有狀態環境互動的軌跡。
- 設計三階段流程：任務合成（Task Synthesis）、軌跡合成（Trajectory Synthesis，由教師代理與模擬器 LLM 協作完成）、軌跡過濾（Trajectory Filtering，由 LLM 評判器執行）。
- 在 AppWorld 與 OfficeBench（涵蓋資訊檢索與狀態改變任務）上驗證，以合成資料微調可顯著提升模型效能。
- 確立基於大型語言模型的 API 模擬是訓練跨多樣化 API 生態系統代理的實用且可擴展方案。

### 適合對象
對 API 呼叫代理、大型語言模型代理、合成資料生成、指令微調與代理軌跡資料建構有興趣的研究者與工程師；特別是希望在缺乏可執行環境與後端資料庫的情況下，仍能大規模生成高品質訓練資料的實務工作者。

## 深度分析

#### 方法論解析

本研究提出 **ESAT（Environment-Free Synthetic Agentic Trajectory generation pipeline，無環境代理軌跡生成流程）**，其核心假設是：現代 **大型語言模型（LLM）** 在大量世界知識（world knowledge）上預訓練後，能夠充當動態的**數位世界模型（digital world models）**。只要給定 **API 規格（API specifications）**、任務指令與互動歷史，LLM 即可即時合成逼真的 **API 回應（API responses）**，模擬真實環境的狀態變化，而無需實際執行任何 API 或建置後端資料庫。

ESAT 分為三個階段：

1. **任務合成（Task Synthesis）**  
   由一個 **任務生成器 LLM（Task Generator LLM）** 根據 API 規格產生多樣且可解的任務。接著，一個 **LLM 評判器（LLM Judge）** 過濾掉無效或不可解的任務，確保後續合成的 **軌跡（trajectories）** 具有合理的起點。

2. **軌跡合成（Trajectory Synthesis）**  
   這是 ESAT 的核心。一個 **教師代理（Teacher Agent）** 負責逐步解題，並對一個 **API 模擬器 LLM（API Simulator LLM）** 發出 API 呼叫。模擬器根據「任務情境（task context）」與「模擬歷史（simulation history）」即時生成合成回應，包含讀取與寫入操作的結果。由於整個過程完全在模擬中進行，因此能產生多步互動（multi-step interaction）的完整 **代理軌跡（agentic trajectories）**，涵蓋使用者指令、交錯的讀寫 API 呼叫、執行結果與最終回應。

3. **軌跡過濾（Trajectory Filtering）**  
   最後，一個 **軌跡評判 LLM（Trajectory Judge LLM）** 對生成的軌跡進行品質評估，篩選出正確、完整且冗餘度低的樣本，形成高品質的 **軌跡資料集（trajectory dataset）** 用於監督式微調（supervised fine-tuning, SFT）。

方法論上的關鍵創新在於「情境感知」的 API 模擬。不同於早期僅靠 LLM 隱含對話連貫性生成假回應的做法，ESAT 的模擬器明確利用長上下文能力追蹤先前互動與狀態變化，從而降低狀態飄移（state drift）與幻覺識別碼（hallucinated identifiers）的風險。這使得合成資料能同時支援 **資訊檢索任務（information-retrieval tasks）** 與 **狀態改變任務（state-changing tasks）**，後者對狀態追蹤（state tracking）的要求更高。

然而，此方法也高度仰賴 API 規格的完整性與 LLM 對該領域的世界知識。若 API 規格過於簡略或涉及專業領域知識缺口，模擬器可能產生不一致的底層狀態（underlying states），進而影響教師代理的解題品質與最終資料集的可信度。

#### 實驗數據解讀

研究在兩個具有挑戰性的多應用基準上進行驗證：**AppWorld** 與 **OfficeBench**。這兩個基準皆包含複雜的多步 **資訊檢索** 與 **狀態改變** 任務，適合用來檢驗合成資料是否能培養代理的穩健 API 使用、狀態追蹤與錯誤復原（error recovery）能力。

實驗涵蓋參數規模從 **1.7B 到 27B** 的模型，並以 **監督式微調（SFT）** 方式在 ESAT 生成的資料上訓練。主要發現包括：

- **顯著效能提升**：相較於對應的基礎模型，經 ESAT 資料微調後的模型在 AppWorld 上最高提升 **50.5%**，在 OfficeBench 上最高提升 **60.5%**。這顯示即使完全沒有真實環境執行，合成軌跡仍能提供有效的監督訊號。
- **超越真實環境訓練資料**：在 AppWorld 上，官方提供了一組從真實環境收集的訓練任務軌跡。實驗結果顯示，僅使用 ESAT 合成資料訓練的模型，表現優於使用這些真實環境軌跡訓練的模型。這是本文最具說服力的結果之一，暗示 LLM 模擬器產生的回饋在某些情境下甚至比真實環境資料更適合訓練（可能因為真實資料品質不穩定、錯誤樣本較多，或 ESAT 能產生更多樣化、經過評判篩選的高品質軌跡）。

從數據意涵來看，這些結果支持了「LLM 可作為 API 模擬器」的核心假設。但需注意幾點詮釋：

- 效能提升的絕對值與基礎模型本身能力密切相關；對較小模型而言，50.5% 的相對提升可能來自於基線極低，因此不代表已達可部署水準。
- OfficeBench 的 60.5% 提升顯示該方法在辦公軟體 API 生態中特別有效，可能因為這類 API 的狀態轉換較符合 LLM 已內化的世界知識。
- 由於提供的上下文未詳細說明評估指標（例如是否採用任務成功率、部分完成率或 API 呼叫正確率），我們無法進一步拆解各指標的貢獻。理想情況下，應同時檢視「最終任務成功率」與「中間步驟正確率」，以判斷模型是學會了真正推理，還是僅記憶了常見模式。

#### 與現有研究的比較

本研究可定位於「LLM 驅動的合成資料生成」與「API 模擬」兩條研究線的交會處。

**相較於需要完整實作環境的方法**  
過去許多研究（如 Qin et al., 2024；Zeng et al., 2024；Liu et al., 2024 等）透過在真實 API 端點或完整沙箱中執行工具呼叫來生成軌跡。這類方法雖然能確保資料的真實性（grounding），但面臨嚴重的 **可擴展性瓶頸（scalability bottleneck）**：每當要擴展到新的 API 生態系統，就必須重新建置後端基礎設施，並取得多樣的 **預先填充後端資料庫（pre-populated backend databases）** 與 **底層狀態配置（underlying state configurations）**。ESAT 將問題簡化為「規格問題」，只需 API 規格即可生成資料，大幅降低了進入門檻。

**相較於早期以 LLM 作為 API 模擬器的方法**  
ToolAlpaca、ToolACE 與 Nemotron 等研究也嘗試用 LLM 模擬 API 回應，但它們主要依賴 LLM 隱含的對話連貫性，容易在長軌跡中出現 **狀態飄移（state drift）** 與 **幻覺識別碼（hallucinated identifiers）**。ESAT 的改進在於引入明確的「情境感知」機制：模擬器會參考任務情境與完整模擬歷史來生成回應，並透過教師代理與評判 LLM 進行多輪篩選，從而提升長軌跡的一致性與品質。

**主要優勢總結**

- **無環境（environment-free）**：無需可執行 API、後端資料庫或真實部署服務。
- **可跨領域擴展**：只要具備 API 規格，即可快速遷移到不同 API 生態系統。
- **長軌跡一致性**：利用長上下文能力維持多輪互動中的狀態連貫。
- **品質控制機制**：透過任務過濾與軌跡評判，提升資料集整體品質。

**限制與潛在弱點**

- **世界知識依賴**：模擬品質受限於 LLM 對該 API 領域的先驗知識；對冷門或新興 API，可能出現事實性錯誤。
- **無真實接地（no grounding）**：合成回應未經真實執行驗證，錯誤可能累積並被教師代理學習。
- **評判器偏誤**：LLM Judge 可能與模擬器或教師代理共享類似偏誤，導致低品質軌跡未被有效過濾。
- **長上下文成本與限制**：隨著軌跡增長，模擬器所需的上下文長度增加，可能提高推理成本並觸及上下文長度上限。
- **API 規格品質敏感**：若規格文件不完整或語意模糊，生成任務與回應的品質會下降。

#### 未來研究方向

基於 ESAT 的框架與其限制，未來研究可朝以下方向延伸：

1. **強化狀態一致性機制**  
   可引入外部結構化記憶體（如鍵值資料庫、狀態圖或符號追蹤器）輔助 LLM 模擬器，降低長軌跡中的狀態飄移，特別是針對需要精確數值運算或複雜交易歷史的任務。

2. **混合式模擬與真實執行**  
   開發「模擬為主、真實執行為輔」的混合流程：先以 ESAT 大規模生成候選軌跡，再對關鍵狀態改變步驟進行少量真實 API 驗證，以兼顧擴展性與資料真實性。

3. **自動化 API 規格驗證與補全**  
   研究如何從文件、程式碼或現有日誌中自動萃取並補全 API 規格，減少對人工撰寫規格的依賴，進一步提升跨領域遷移能力。

4. **多代理協作模擬**  
   將單一教師代理擴展為多代理系統，模擬使用者、代理與多個後端服務之間的互動，以生成更貼近真實應用場景的軌跡。

5. **自我改進與對抗性過濾**  
   讓模擬器、教師代理與評判器進行迭代對抗或協作優化，例如透過困難樣本採礦（hard negative mining）生成更具挑戰性的錯誤復原與邊界案例。

6. **規模化法則與資料效率分析**  
   系統性研究 ESAT 生成資料量、模型規模與下游任務表現之間的關係，找出不同 API 領域中的最佳資料合成策略與成本效益平衡點。

7. **安全性與幻覺評估**  
   建立專門評估合成 API 模擬安全性的基準，檢視模擬器是否會生成危險、偏誤或誤導性的回應，並發展相應的緩解技術。

8. **擴展至 API 設計與自動化測試**  
   除了訓練代理，ESAT 的模擬能力也可用於在 API 正式上線前進行行為模擬與壓力測試，成為 API 開發流程中的輔助工具。

## 論文問答

**Q1：訓練 API 呼叫代理需要什麼樣的資料，為何難以取得？**
A：訓練 API 呼叫大型語言模型代理需要大量高品質軌跡，這些軌跡必須捕捉完整的多步互動過程，包括使用者指令、交錯的讀取與寫入 API 呼叫、執行結果以及最終回應。相較於標準指令微調資料，這類多步軌跡更難以大規模收集，因為它們必須教會代理穩健的 API 使用、準確的狀態追蹤以及有效的錯誤復原能力。傳統上，這類資料需要依賴完整實作環境、可執行 API 以及預先填充的後端資料庫，因此收集成本高昂且難以擴展。

**Q2：現有的合成資料生成方法存在什麼瓶頸？**
A：現有方法通常假設能夠使用完整實作環境與可執行 API，並在真實後端資料庫上執行工具呼叫以確保軌跡的真實性。這種緊密耦合使得資料合成與環境建設綁在一起，每當要為新的 API 生態系統生成資料時，就必須先工程化對應的基礎設施，並費力地取得多樣的底層狀態配置來填充環境。因此，這種對功能性環境的依賴嚴重限制了方法擴展到新 API 領域的速度與廣度。

**Q3：為何將資料生成與可執行環境解耦很重要？**
A：將資料生成與可執行環境解耦可以把代理軌跡合成轉化為輕量級的規格問題，只需 API 規格即可產生訓練資料。這不僅消除了建置與填充後端資料庫所帶來的基礎設施瓶頸，也讓合成資料能夠無縫擴展到多樣的 API 生態系統。對於快速演進的 API 服務而言，這種無環境合成資料生成方式能大幅降低資料收集門檻，加速代理的開發與迭代。

**Q4：ESAT 流程包含哪三個階段？**
A：ESAT 流程首先進行任務合成，由任務生成器大型語言模型根據 API 規格產生多樣且真實的任務，並由評判器過濾掉無效任務。接著進入核心的軌跡合成階段，教師代理與 API 模擬器大型語言模型互動，教師代理迭代地發出 API 呼叫，而模擬器則根據任務情境與模擬歷史即時生成連貫的合成 API 回應。最後是軌跡過濾階段，由軌跡評判大型語言模型評估軌跡的正確性、完整性與冗餘性，剔除次優樣本以確保高品質的軌跡資料集。

**Q5：相較於早期使用大型語言模型模擬 API 回應的方法，ESAT 的模擬器有何關鍵創新？**
A：ESAT 的 API 模擬器大型語言模型是一種情境感知的動態數位世界模型，它會利用任務情境、輸入引數以及先前互動歷史來生成環境回饋。這種設計讓模擬器能夠在長序列的多步互動中維持狀態一致性，避免早期方法僅依賴隱式對話連貫性而容易出現的狀態飄移與幻覺識別碼問題。透過即時追蹤模擬歷史與狀態變化，該模擬器可以產生更真實、更連貫的有狀態環境互動軌跡。

**Q6：為何 ESAT 選擇讓教師代理與模擬器互動，而非直接由大型語言模型生成完整軌跡？**
A：讓教師代理與模擬器互動能夠更真實地模擬代理與有狀態環境之間的動態回饋迴路，因為每次 API 呼叫都會根據當前模擬狀態產生對應的回應，從而迫使教師代理進行即時推理與錯誤處理。直接生成完整軌跡容易忽略中間狀態變化與環境回饋的因果關係，導致軌跡缺乏真實的多步互動特性。此外，這種互動式設計也便於後續由軌跡評判大型語言模型針對正確性與完整性進行過濾，確保最終資料集更適合用於監督式微調。

**Q7：論文在哪些基準上進行評估，這些基準涵蓋哪些任務類型？**
A：論文在 AppWorld 與 OfficeBench 兩個具有挑戰性的多應用基準上進行評估，這兩個基準都包含複雜的多步資訊檢索任務與狀態改變任務。AppWorld 提供官方訓練任務，可用來比較合成資料與真實環境收集資料的訓練效果；OfficeBench 則進一步驗證方法在不同 API 生態系統上的泛化能力。這些基準能夠測試代理在長程互動中進行狀態追蹤、規劃與執行複雜使用者指令的能力。

**Q8：ESAT 合成資料對模型效能帶來哪些關鍵提升？**
A：實驗結果顯示，在參數規模從 1.7B 到 27B 的模型上進行監督式微調後，使用 ESAT 合成資料的模型相較於基礎模型都有顯著效能提升，在 AppWorld 上最高可達 50.5%，在 OfficeBench 上最高可達 60.5%。這些結果顯示，即使沒有任何可執行環境，基於大型語言模型的 API 模擬也能產生有效的監督訊號。更重要的是，這證明了無環境合成資料生成可以作為訓練 API 呼叫代理的實用且可擴展的解決方案。

**Q9：與 AppWorld 官方真實環境訓練資料相比，ESAT 合成資料表現如何？**
A：在 AppWorld 基準上，使用 ESAT 合成資料微調的模型表現優於使用官方訓練任務軌跡所訓練的模型，而這些官方軌跡是從真實 AppWorld 環境中收集而來。這項結果相當引人注目，因為它表明僅憑 API 規格所生成的合成軌跡，不僅能夠媲美、甚至能超越真實環境資料的訓練效果。這也進一步支持了論文的核心主張：現代大型語言模型具備足夠的世界知識，可以作為動態數位世界模型來替代真實環境進行資料合成。

**Q10：ESAT 在哪些實際應用場景中最具價值？**
A：ESAT 特別適合於 API 生態系統快速演變或難以建置完整測試環境的場景，例如新創服務、企業內部私有 API 或尚未正式上線的 API 規格。在這些情境中，工程團隊往往無法立即取得可執行 API 與預先填充的後端資料庫，而 ESAT 只需 API 規格就能開始生成訓練資料。此外，對於需要大量多樣化狀態配置來覆蓋邊界案例的應用，無環境合成資料生成也能大幅降低資料準備成本。

**Q11：在實際產品化過程中，使用 ESAT 需要考量哪些因素？**
A：產品化時首先需要確保 API 規格的品質與完整性，因為模擬器的輸出完全依賴這些規格來推論合理的輸入引數、輸出格式與狀態變化。其次，必須建立有效的軌跡過濾與驗證機制，因為大型語言模型模擬仍可能產生幻覺識別碼或狀態不一致的軌跡，需要額外的評判器或單元測試來把關。最後，在部署到真實環境前，建議將合成資料訓練的模型與少量真實環境資料進行對齊或驗證，以降低模擬與現實之間的落差。

**Q12：這項研究可能對代理訓練與資料合成領域帶來什麼影響？**
A：這項研究確立了基於大型語言模型的 API 模擬作為一種實用且可擴展的訓練資料來源，可能改變未來 API 呼叫代理的開發流程。它將資料合成的關注重點從「如何建置真實環境」轉向「如何設計高品質的 API 規格與評判機制」，從而降低新領域代理開發的門檻。長遠來看，這種無環境合成資料生成方法可能促進更多元 API 生態系統上的代理訓練，加速通用型代理的發展。

**Q13：論文可能承認或暗示哪些限制？**
A：雖然論文強調 ESAT 的優勢，但從方法設計可以推知，合成資料的品質高度依賴所使用大型語言模型的世界知識與推理能力，若模型對特定 API 領域不熟悉，模擬結果可能不夠準確。此外，由於沒有真實環境執行，某些涉及複雜業務邏輯、數值計算或外部即時資料的任務可能難以被精確模擬。這些限制意味著 ESAT 目前最適合作為資料擴增與早期開發工具，而非完全取代所有真實環境驗證。

**Q14：ESAT 可能出現哪些失敗案例？**
A：一個常見的失敗案例是模擬器在長序列互動中產生狀態飄移，例如遺漏先前寫入 API 呼叫所造成的狀態變化，導致後續回應與先前互動歷史不一致。另一個潛在問題是幻覺識別碼，例如模擬器生成看似合理但實際上不存在於狀態中的交易編號或物件 ID，這會讓教師代理做出錯誤推論。此外，若 API 規格描述模糊或缺少邊界條件，任務生成器可能產生無效任務，即使經過評判器過濾仍可能殘留品質不佳的樣本。

**Q15：未來研究可以朝哪些方向延伸這項工作？**
A：未來研究可以探索如何將 ESAT 與輕量級的形式化驗證或符號執行結合，以減少大型語言模型模擬中的狀態飄移與幻覺問題。另一個方向是發展更強大的軌跡評判器，結合執行追蹤與單元測試來自動檢測合成軌跡中的邏輯錯誤。此外，也可以研究如何將無環境合成資料生成擴展到更廣泛的代理互動場景，例如多代理協作、具身智慧或需要與真實世界感測器互動的應用。

## 實務應用指南

### 適用場景

1. **企業內部 API 自動化代理訓練**  
   大型企業通常擁有數百個內部 API（如 HR、財務、CRM），但建立完整的測試沙箱與預先填充的後端資料庫成本高昂。ESAT 可直接從 API 規格生成高品質軌跡，讓企業在無需完整實作環境的情況下，訓練能處理請假、報銷、客戶查詢等任務的 API 呼叫代理。

2. **新產品或新 API 的早期代理開發**  
   在後端服務尚未完全建置前，產品團隊即可利用 API 規格文件（如 OpenAPI/Swagger）生成合成互動資料，提前訓練與驗證代理的行為。這能縮短從規格到可運作代理的開發週期，特別適合新創或敏捷團隊。

3. **跨領域 API 生態系的快速擴展**  
   當需要支援新的 API 生態系統（如金融開放銀行、醫療資訊交換、IoT 裝置管理）時，傳統方法需為每個領域建置專屬環境。ESAT 將資料生成簡化為規格問題，使團隊能快速為多樣化 API 生成訓練軌跡。

4. **複雜多步工作流程自動化**  
   適用於需要交錯讀取與寫入 API 呼叫的場景，例如「查詢庫存 → 建立訂單 → 更新客戶狀態 → 發送通知」。API 模擬器 LLM 能維持狀態一致性，生成包含狀態追蹤與錯誤復原的長軌跡。

5. **客服與任務導向對話系統**  
   可為虛擬助理生成涵蓋真實後端互動的訓練資料，例如處理帳戶查詢、預約修改、退款申請等狀態改變任務，無需連接真實的生產環境。

### 實作前置條件

**資料準備**
- 完整且正確的 API 規格文件（建議使用 OpenAPI/Swagger 格式）。
- API 的輸入引數、輸出結構、錯誤碼與業務邏輯說明。
- 領域知識文件，用於引導任務生成器產出符合真實使用情境的任務指令。
- 少量人工撰寫的任務範例（可選，但有助於提升任務品質與多樣性）。

**運算資源**
- 可呼叫的強大 LLM API（如 GPT-4、Claude 3.5 Sonnet 等級），用於任務生成器、教師代理、API 模擬器與評判器。
- 用於監督式微調（SFT）的運算資源（如 1.7B 至 27B 參數模型的 GPU/TPU）。
- 軌跡儲存與版本控制系統，便於後續過濾與迭代。

**技能需求**
- 熟悉 API 設計與 RESTful/JSON 規格。
- 具備提示工程（prompt engineering）能力，能設計任務生成、模擬與評判的提示。
- 了解 LLM 微調流程與評估指標（如成功率、狀態一致性）。
- 具備基礎的資料品質分析能力，能識別無效任務與狀態飄移問題。

---

### 實作步驟建議

**步驟一：API 規格整理與標準化**  
將所有目標 API 的規格統一為結構化格式，確保包含端點、方法、參數、回傳結構、錯誤情境與業務規則。規格越完整，模擬器生成的回應越一致。

**步驟二：任務合成（Task Synthesis）**  
使用任務生成器 LLM 根據 API 規格生成多樣化的有效任務。任務應涵蓋資訊檢索與狀態改變兩大類型，並包含不同複雜度與錯誤復原情境。接著以評判 LLM 過濾無效任務。

**步驟三：軌跡合成（Trajectory Synthesis）**  
為每個有效任務配對教師代理與 API 模擬器 LLM。教師代理根據任務指令逐步發出 API 呼叫，模擬器則依據任務情境與模擬歷史即時生成合成 API 回應，形成完整的多步互動軌跡。

**步驟四：軌跡過濾（Trajectory Filtering）**  
利用軌跡評判 LLM 評估每條軌跡的正確性、完整性與冗餘度，剔除次優樣本。可額外加入規則式檢查（如輸出格式驗證、狀態變化一致性）作為輔助。

**步驟五：監督式微調（SFT）**  
將過濾後的高品質軌跡資料集用於微調目標語言模型。建議從小規模實驗開始，觀察模型在驗證集上的表現，再擴大資料規模。

**步驟六：評估與迭代**  
在真實或部分可執行的環境中評估微調後的模型。針對失敗案例分析是否源於任務設計、模擬器不一致或過濾不足，並迭代改進提示與流程。

### 潛在風險與注意事項

**狀態飄移與幻覺識別碼**  
在長軌跡中，API 模擬器 LLM 可能遺忘先前的狀態變化，或生成不存在識別碼。建議在提示中強制要求模擬器追蹤關鍵狀態變數，並定期以規則式檢查驗證識別碼一致性。

**任務品質不穩定**  
自動生成的任務可能包含語意模糊、無法執行或超出 API 能力的項目。應透過多輪評判與少樣本範例（few-shot examples）提升任務有效性，並保留人工抽樣審查機制。

**領域正確性不足**  
對於金融、醫療等高風險領域，LLM 模擬的業務邏輯可能與真實系統不符。建議將 ESAT 資料與真實環境執行的小規模驗證資料結合，或引入領域專家設計的約束規則。

**過度依賴 LLM 評判器**  
評判 LLM 本身可能遺漏細微錯誤。可輔以單元測試、語法檢查與執行追蹤（execution trace）比對，建立多層次的品質控管。

**資料分布偏差**  
自動生成的任務可能過度集中在某些 API 或情境。應監控資料集中 API 呼叫頻率、任務長度與任務類型的分布，確保訓練資料涵蓋足夠多樣性。

### 與其他技術的整合建議

**與真實執行環境搭配驗證**  
雖然 ESAT 無需完整環境，但建議保留一小部分可在真實環境執行的驗證軌跡，用於校準模擬器品質並偵測狀態飄移。

**結合 RAG 強化 API 文件理解**  
將 API 規格文件納入檢索增強生成（RAG）系統，使任務生成器與模擬器能動態查詢最新文件，特別適合規格頻繁更新的場景。

**與 RLHF / DPO 整合**  
在 ESAT 生成的軌跡基礎上，可進一步使用人類回饋強化學習（RLHF）或直接偏好最佳化（DPO）來優化代理的推理風格與錯誤處理策略。

**嵌入 CI/CD 與 MLOps 流程**  
將任務生成、軌跡合成、過濾與微調流程自動化，並與模型版本控制、A/B 測試整合，使合成資料生成成為持續改善代理能力的一環。

**搭配可觀測性工具**  
在實際部署時，結合追蹤（tracing）與日誌分析工具，持續收集真實互動資料，並回饋至 ESAT 流程以生成更符合實際分布的訓練資料。

### 給不同背景讀者的閱讀建議

**給初學者**  
這篇論文提出了一種不需要真實環境就能訓練 API 代理的方法。你可以先聚焦在「為什麼需要合成資料」以及 ESAT 的三個階段（任務合成、軌跡合成、軌跡過濾），理解大型語言模型如何同時扮演「出題老師」、「模擬環境」和「批改助教」的角色，不必一開始就深入技術細節。

**給 AI 工程師**  
建議重點閱讀軌跡合成與 API 模擬器的設計，特別是如何利用長上下文維持狀態一致性，以及評判 LLM 的過濾策略。實作時請特別注意提示工程的設計、模擬器在長軌跡中的狀態飄移問題，並思考如何將論文方法落地為可重複執行的資料生成管線。

**給研究人員**  
本文的核心貢獻在於將 LLM 視為動態數位世界模型，並驗證無環境合成資料對代理訓練的有效性。建議關注其與傳統可執行環境方法的比較、評估指標的設計，以及長軌跡狀態一致性的理論限制，這些都是未來可延伸的研究方向。

**給產品經理**  
這項技術能顯著降低訓練 API 代理的基礎設施成本，並加速新 API 生態系的支援。閱讀時請著重評估它對你所在產品的適用場景、潛在風險（特別是狀態改變任務的正確性），以及需要投入的資料與運算資源，以便判斷是否值得納入產品路線圖。
