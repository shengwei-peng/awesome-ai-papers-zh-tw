# 新增是機器，刪除才是人類：衡量與緩解大型語言模型程式碼編輯中的刪除迴避

## ⚡ TL;DR

大型語言模型在程式碼修復中傾向保留應刪除的程式碼，導致可維護性下降。
論文提出 CanItDelete 基準與診斷階梯，並於後訓練階段教導刪除。
實驗顯示模型刪除召回率偏低，而刪除後訓練能顯著提升程式碼編輯表現。

## 摘要翻譯

大型語言模型（large language models, LLMs）日益撰寫與修復生產環境程式碼（production code），但越來越多證據顯示，它們那些通過測試的修補程式（test-passing patches）反而讓程式碼庫（codebase）更難維護。我們找出一個具體根源：刪除迴避（deletion avoidance），亦即系統性地傾向保留預期編輯所要求移除的程式碼。橫跨官方 SWE-bench Verified 排行榜（leaderboard）上的五個領先模型，對照開發者修補程式（developer patch）的刪除召回率（deletion recall），即使在五個模型都能解決的任務中，最高也僅達 71.7%；模型雖能在超過 92% 的必要刪除（required deletion）中定位（localization）到正確檔案，卻僅在不到 52% 的案例中刪除確切行（exact line）。相對地，29.0% 的通過測試修補程式會以防護條件 / 後備邏輯（guard / fallback）包裹目標程式碼（targeted code），我們將這種模式稱為 Guard-and-Go。這類修補程式之所以通過，是因為原始測試很少檢查刪除：當我們為 34 個 SWE-bench Verified 任務加裝測試（retrofit tests），只要目標程式碼仍然存在即會失敗，四個涵蓋封閉權重（closed weights）與開放權重（open weights）的前沿模型（frontier models）表現便從 63.2% 降至 41.9%。由於真實修復混合了刪除與新增，我們建構了 CanItDelete，一個從真實提交（real commits）中挖掘出 200 個任務的基準（benchmark），這些任務的完整所需編輯（full required edit）皆為刪除。即使沒有新增性修改（additive work），最佳模型仍每五個任務就失敗一個，而較小的開放模型（smaller open models）則降至 18.0%。接著我們以四個累加提示（cumulative prompts）對 GPT-5.6 Sol 進行消融；成功率（success rate）幾無變化，直到我們提供確切行，這幾乎消除了不完整刪除（incomplete deletion），但成功率僅提升至 80.5%，因為模型接著會刪除範圍超出指定區段（beyond the spans），或反而新增程式碼。最後，透過一項先導研究（pilot study），我們展示了一個可能的解決方案：在後訓練（post-training）階段教導刪除，能減少刪除迴避並改善更廣泛的程式碼編輯表現（code-editing performance），顯示這種行為是訓練不足（undertrained），而非無法達成。

### 核心貢獻（3～5點）
- 發現並量化大型語言模型程式碼編輯中的刪除迴避現象，指出模型傾向以 Guard-and-Go 模式保留應刪除的程式碼。
- 揭示現有測試對刪除行為的檢驗不足，透過加裝測試使前沿模型通過率顯著下降，凸顯維護性風險。
- 提出 CanItDelete 基準，收錄 200 個純刪除的真實提交任務，專門評估模型在無新增性修改時的刪除能力。
- 透過提示消融實驗，說明僅提供確切行雖能減少不完整刪除，卻會引發超出指定區段刪除或無謂新增等新問題。
- 以先導研究證明在後訓練階段教導刪除可減少刪除迴避，並提升整體程式碼編輯表現，暗示此行為源於訓練不足而非能力上限。

### 適合對象
本論文適合軟體工程、AI 輔助程式設計、程式碼智慧代理與自動化程式修復領域的研究者與工程師，亦適合關注大型語言模型生成程式碼可維護性、希望提升自動化修復品質以達可合併（merge-ready）水準的開源專案維護者與開發者。

## 深度分析

#### 方法論解析

本研究的核心方法論可拆解為三個層次：**刪除迴避（deletion avoidance）的現象刻畫**、**純刪除基準 CanItDelete 的建構**，以及**診斷式提示階梯（diagnostic ladder）與後訓練（post-training）介入**。

首先，作者將「刪除迴避」操作化為可量化的指標。他們以 SWE-bench Verified 官方排行榜上五個前沿模型（frontier models）——GLM-4.6、GPT-5、Kimi-K2、Opus-4.5 與 Salesforce SAGE——的 OpenHands 提交為分析對象，並固定腳手架（scaffold）以隔離模型本身行為差異。針對每一題，他們比對模型修補程式（patch）與開發者修補程式（developer patch），找出後者從非測試 Python 檔案中移除、且未在同一所在函式（enclosing function）/類別（class）/模組（module）內復原的程式碼位置，稱為**參考刪除（reference deletion）**。評估指標包含：

- **刪除召回率（deletion recall）**：模型刪除位置與參考刪除位置的交集比例，衡量「該刪的是否真的刪了」。
- **刪除精確率（deletion precision）**：模型刪除中有多少比例對應到參考位置，衡量「是否誤刪」。
- **三層定位檢查**：針對每一個必要刪除（required deletion），檢查模型是否修改了正確檔案、是否觸及所在函式/類別/模組，以及是否移除確切行（exact line）。

其次，為了排除「新增性修改（additive work）」對刪除能力的干擾，作者提出 **CanItDelete** 基準。該基準從真實提交（real commits）中挖掘 200 個任務，其**完整所需編輯（full required edit）**僅包含刪除，並以**編輯前檔案（pre-edit file）**完整呈現。評分採用**確定性（deterministic）**且**考慮出現次數的評估器（occurrence-aware evaluator）**，能精確判斷目標程式碼（targeted code）是否被完整移除，而不會因語意等價但文字不同而誤判。

第三，作者設計了一套**累加提示（cumulative prompts）**的診斷階梯，用於定位刪除失敗的來源。以 GPT-5.6 Sol 為對象，逐步加入：（1）明確的刪除指令；（2）區域指標（region pointer）；（3）精確的程式碼區段（spans）需移除。這種設計能區分「找不到位置」、「知道位置但不敢刪」、「刪過頭」等不同失敗模式。

最後，作者進行一項**先導研究（pilot study）**：在 7B 模型的程式碼後訓練資料中，僅加入佔總 token 0.7% 的 12.8k 個刪除範例，觀察刪除迴避是否可透過訓練改善。這驗證了「刪除能力並非不可達，而是訓練不足（undertrained）」的假說。

#### 實驗數據解讀

##### 1. SWE-bench Verified 上的刪除迴避

即使模型已通過測試，其修補程式仍大量保留開發者移除的程式碼。在五個模型共同解決的 197 題中，**刪除召回率（deletion recall）**最高僅達 Opus-4.5 的 71.7%，最低為 Kimi-K2 的 65.2%。換言之，通過測試的修補程式（test-passing patches）仍遺留約 28%–35% 的必要刪除。

更細緻的定位數據顯示，模型並非找不到目標：它們在超過 92% 的情況下修改了包含必要刪除的檔案，並在 68.1%–74.4% 的情況下觸及正確的所在函式/類別/模組。然而，真正移除確切行（exact line）的比例僅 44.6%–51.6%。這說明問題不在**定位（localization）**，而在**執行刪除的決策**。

##### 2. Guard-and-Go：刪除迴避的主要形式

模型最常見的替代策略是 **Guard-and-Go**：保留原本應刪除的邏輯，但在外層加上防護條件（guard）或後備邏輯（fallback），使其在特定條件下不被執行。這類修補佔所有通過測試修補的 **29.0%**。這種做法能通過測試，是因為原始測試很少檢查「某段程式碼是否已不存在」。當作者針對 34 個以刪除為主的任務（deletion-heavy tasks）**加裝測試（retrofit tests）**，要求若經驗證的刪除目標（validated deletion target）仍存在則測試失敗，四個前沿模型的解決率（resolution rate）從 63.2% 驟降至 41.9%，86 個原本通過的嘗試中有 29 個失敗。這證明現有排行榜分數可能高估了真正的維護品質。

##### 3. CanItDelete：純刪除情境下的表現

在排除新增性修改後，CanItDelete 的結果顯示刪除仍是顯著弱點。12 個模型的成功率（success rate）從 79.0% 到 18.0% 不等，最佳模型仍有約五分之一任務失敗，較小的開放模型（smaller open models）甚至僅 18.0%。失敗模式中，**不完整刪除（incomplete deletion）**主導了 12 個模型中的 10 個，再次確認模型傾向於「少刪」而非「多刪」。

##### 4. 診斷階梯：提示無法根本解決問題

對 GPT-5.6 Sol 的消融顯示，單純給予明確刪除指令或區域指標，對成功率幫助有限；只有提供**精確 spans** 時，不完整刪除才幾乎消失。但即便如此，成功率僅提升至 80.5%，因為模型開始出現兩種新錯誤：**刪除超出指定區段（beyond the spans）**與**新增程式碼而非刪除**。這呼應了作者「模型缺乏的是控制，而非能力」的論點——給定明確邊界後，模型能刪，但無法穩定地「只刪該刪的」。

##### 5. 後訓練教導刪除：訓練不足假說的證據

在先導研究中，僅以 0.7% 的後訓練 token 加入刪除範例，就使 7B 模型在 CanItDelete 上的刪除迴避降低 13.9 個百分點，且效益轉移到未針對性訓練的基準：SWE-bench Verified 提升 5.3 百分點，CanItEdit 提升 1.4 百分點。這強烈暗示目前程式碼後訓練資料中刪除範例不足，刪除行為是**訓練不足（undertrained）**而非不可學習。

#### 與現有研究的比較

本研究與現有文獻的關係可從三個面向理解：**基準設計**、**現象刻畫**與**改善途徑**。

在基準設計上，SWE-bench Verified 是當前軟體工程領域最具代表性的排行榜，但其評分僅檢查測試是否通過，不檢查修補程式是否與開發者修補一致。這導致模型可以透過 Guard-and-Go 等繞過策略取得高分。相較之下，CanItEdit 等編輯基準雖關注程式碼編輯（code editing）能力，但仍混合新增與刪除。CanItDelete 的貢獻在於**將刪除孤立出來**，並使用考慮出現次數的評估器，使測量更精確。這類「分解式基準」與過去將程式碼修復視為整體任務的研究形成互補。

在現象刻畫上，過去研究已指出代理產生的修復（agent-authored fixes）被拒率高、AI 產生的貢獻（AI-generated contributions）被部分專案拒絕，以及維護者（maintainer）認為通過測試的修補過於冗長（verbosity）且不符合專案慣例（repository conventions）。本研究進一步將這些維護性問題追溯到具體機制：**刪除迴避**。這比單純說「模型寫太多」更具解釋力，也提供了可量化的診斷指標。

在改善途徑上，過去許多研究聚焦於擴大模型規模、改進檢索或強化工具使用，而本研究指出**資料層面的偏斜**可能是主因。這與近期強調「資料品質與組成」的後訓練研究一致，但本研究首次針對「刪除」這一特定編輯動作進行系統性介入，並證明小量刪除資料即可帶來跨基準遷移效益。

**限制方面**，本研究主要分析 Python 程式碼與 SWE-bench 生態，其他語言或企業內部程式碼庫（codebase）的刪除行為可能不同。此外，先導研究僅在單一 7B 規模進行，尚無法確定更大模型是否會出現規模效應或收益遞減。最後，作者也承認開發者修補並非唯一正確解，因此刪除召回率僅是行為參考，而非絕對正確性判準。

#### 可重現性評估

本研究在可重現性（reproducibility）上的表現呈現「測量透明但資源尚未完全開放」的狀態。

**已公開或可推導的資訊**包括：

- 明確列出五個分析的 OpenHands 提交版本、模型名稱與選取程序（附錄 A.1 表 5）。
- 詳細定義參考刪除、刪除召回率、刪除精確率與三層定位檢查的計算方式。
- 使用標準統計方法（Mann–Whitney U 檢定、Cliff’s δ、Holm 校正 p 值）比較解決與未解決任務。
- CanItDelete 基準、測量程式碼與資料集承諾在論文接受後釋出，並已於匿名審查期間提供。

**仍有限制的部分**包括：

- 部分前沿模型為**封閉權重（closed weights）**，如 GPT-5、Opus-4.5 等，研究者與第三方無法直接取得權重，只能透過 API 復現。
- 雖然腳手架固定為 OpenHands，但不同模型提交可能使用不同提示或工具呼叫版本，完全復現需依賴官方提交快照。
- 後訓練實驗的 12.8k 刪除範例與 7B 模型細節尚未於摘要中完整揭露，需等待論文附錄或釋出資料。

整體而言，本研究在方法描述上足夠詳細，使其他研究者能夠在取得資料後重建主要實驗；但由於涉及商業模型與尚未公開的訓練資料，完全獨立復現仍有一定門檻。

#### 未來研究方向

基於本研究的發現，未來可朝以下方向延伸：

1. **多語言與跨領域的 CanItDelete 擴展**：目前聚焦 Python，未來可建構 Java、C++、JavaScript 等語言的純刪除基準，檢驗刪除迴避是否為跨語言普遍現象。

2. **Guard-and-Go 自動偵測與懲罰**：開發靜態或動態分析工具，自動識別「用條件包裹應刪除邏輯」的模式，並將其納入基準評分，使排行榜更能反映可維護性（maintainability）。

3. **維護導向的評估指標**：除了測試通過與刪除召回率，未來可引入程式碼複雜度、技術債權重、維護者偏好預測等指標，衡量修補程式是否真正**可合併（merge-ready）**。

4. **刪除資料的系統性增強**：研究如何大規模從版本控制歷史中挖掘高品質刪除範例，並設計資料篩選策略，避免引入錯誤或過時的刪除模式。

5. **強化學習與人類回饋的刪除獎勵**：將刪除完整性與邊界正確性納入獎勵函數，透過強化學習或人類回饋強化學習（RLHF）訓練模型更精準地控制刪除範圍。

6. **智慧代理（agent）層級的刪除規劃**：改進腳手架（scaffold）的規劃模組，使代理在動手編輯前先明確標記「應刪區段」與「應保留區段」，降低 Guard-and-Go 的發生率。

7. **人機協作的刪除確認機制**：設計互動式系統，讓模型在面對高風險刪除時主動請求人類確認，並從中學習刪除決策的邊界。

8. **刪除與新增的平衡訓練**：探討後訓練資料中新增與刪除範例的最佳比例，以及這種比例如何影響模型在混合編輯任務上的表現。

9. **可解釋性研究**：分析模型在面對刪除決策時的注意力與激活模式，理解為何模型傾向於保留程式碼，並據此設計針對性架構改進。

10. **規模化先導研究**：將後訓練教導刪除的實驗擴展到更大模型（如 30B、70B）與更多訓練資料，驗證效益是否隨規模遞增，並評估對通用程式碼編輯表現（code-editing performance）的長期影響。

## 論文問答

**Q1：什麼是「刪除迴避」（deletion avoidance），為什麼它會成為大型語言模型程式碼編輯的隱憂？**  
A：刪除迴避是指大型語言模型在進行程式碼修復時，系統性地保留那些按照開發者修補程式應該被移除的程式碼的傾向。這種行為會讓模型產生的修補雖然能通過既有測試，卻讓程式碼庫變得更加冗長、難以維護，甚至違反專案慣例。由於現行基準多以測試通過與否作為唯一標準，刪除迴避因此成為一種難以被察覺但影響深遠的品質缺陷。

**Q2：現有的 SWE-bench Verified 等基準為何無法有效發現刪除迴避問題？**  
A：SWE-bench Verified 主要檢驗修補程式是否能讓測試通過，卻不會比對模型輸出與開發者修補程式在程式碼結構上的差異。原始測試很少會主動檢查「某段程式碼是否已經被移除」，因此模型可以用 Guard-and-Go 等方式繞過刪除需求，仍然獲得正確的評分。換句話說，測試通過並不能保證模型真正執行了開發者預期的減法式修改。

**Q3：為什麼「會刪除」對生產環境程式碼的可維護性與可合併性如此重要？**  
A：在真實的開源專案中，維護者拒絕 AI 產生貢獻的常見理由包括過度冗長與偏離專案慣例，而這些問題往往源自於模型沒有確實刪除過時邏輯。保留無用程式碼會增加未來閱讀、除錯與重構的成本，也會讓修補程式離「可合併」的標準更遠。因此，刪除不僅是語法層面的操作，更是決定程式碼長期健康度的關鍵維護行為。

**Q4：作者群採用了什麼核心方法來衡量模型在真實倉庫修復中的刪除迴避程度？**  
A：他們以開發者修補程式作為行為參考，計算「刪除召回率」（deletion recall），也就是模型正確移除的必要刪除佔開發者全部刪除的比例。為了區分定位與執行，他們進一步在三個層級檢查每一次必要刪除：是否修改了正確檔案、是否觸及所在函式或類別、以及是否刪除了確切行。研究固定了 OpenHands 腳手架，並只分析五個模型結果一致的任務，以降低腳手架與任務難度帶來的干擾。

**Q5：CanItDelete 這個新基準與 SWE-bench Verified 相比有何不同？它的設計考量是什麼？**  
A：CanItDelete 是從真實提交中挖掘出的 200 個任務，這些任務的完整所需編輯「僅有刪除」，從而排除了新增性修改所帶來的混淆因素。它使用確定性且考慮出現次數的評估器，在完整的編輯前檔案上判斷模型是否完整移除了所有目標程式碼。這樣的設計讓研究者能夠單獨檢驗模型的刪除能力，而不必擔心搜尋、新增或重組程式碼等其他因素掩蓋刪除失敗的事實。

**Q6：什麼是 Guard-and-Go？為什麼它被視為刪除迴避的主要表現形式？**  
A：Guard-and-Go 是指模型保留開發者原本要移除的邏輯，並在外層加上防護條件或後備邏輯來繞過執行的策略。在通過測試的修補中，這種模式佔了 29.0%，顯示模型傾向用「包裹」而非「刪除」來處理過時程式碼。由於這類修補能通過測試，卻讓程式碼庫累積無用或誤導性的邏輯，因此被視為刪除迴避最具代表性的表現。

**Q7：在 SWE-bench Verified 上的實驗揭示了哪些關於刪除召回率的關鍵數據？**  
A：在五個前沿模型都能解決的 197 個任務中，刪除召回率最高也只有 71.7%，最低則為 65.2%，顯示即使測試通過，仍有相當比例的必要刪除被保留。模型雖然能在超過 92% 的情況下找到包含必要刪除的檔案，卻只有不到 52% 的機會刪除確切行。整體而言，通過測試的修補仍會留下 28.3% 至 34.8% 的開發者刪除未處理。

**Q8：當研究者加裝檢查刪除是否完成的測試後，模型表現出現了什麼變化？**  
A：研究者在 34 個以刪除為主的 SWE-bench Verified 任務上加裝了「若目標程式碼仍存在則失敗」的測試，結果四個前沿模型的解決率從 63.2% 驟降至 41.9%。在 86 個原本通過的嘗試中，有 29 個因為保留目標程式碼而失敗。這個實驗清楚顯示，單靠原始測試會大幅高估模型真正完成刪除的能力。

**Q9：針對 GPT-5.6 Sol 的累加提示消融實驗得出了什麼結論？**  
A：研究者逐步給予明確刪除指示、區域指標，以及最後的確切程式碼區段，結果只有在提供確切區段後，不完整刪除才幾乎被消除。然而，即使給出確切區段，成功率也只達到 80.5%，因為模型開始出現刪除超出指定區段或額外新增程式碼等新錯誤。這說明模型並非完全缺乏刪除能力，而是缺乏對刪除邊界的精細控制。

**Q10：刪除迴避對現實中的程式碼代理與自動化開發工具有什麼實務影響？**  
A：在真實 GitHub 倉庫中，已有 46.4% 的代理產生修復被拒絕，部分專案甚至直接拒絕 AI 產生的貢獻，原因之一就是修補過於冗長且不符合專案慣例。如果編碼代理持續使用 Guard-and-Go 來規避刪除，將導致更多通過測試卻無法被維護者合併的拉取請求。因此，產品團隊不能僅以測試通過率作為代理品質指標，還需要評估其輸出是否真正精簡且符合維護標準。

**Q11：從產品設計角度，應該如何防範或偵測 Guard-and-Go 這類刪除迴避行為？**  
A：開發團隊可以在測試中加入針對刪除目標的斷言，確保過時邏輯一旦被保留就會觸發測試失敗。程式碼審查工具也可以主動標記「新增條件包裹既有邏輯」的修補模式，提醒審查者檢查是否應直接刪除。此外，代理的獎勵函式應納入修補簡潔度與對開發者修補結構的相似度，以降低模型用新增代替刪除的誘因。

**Q12：這項研究可能對整個程式碼編輯與軟體工程基準領域帶來什麼更廣泛的影響？**  
A：本研究首次系統性地量化了刪除迴避，並提出 CanItDelete 與診斷梯子等工具，讓社群能夠更精確地評估模型的減法編輯能力。它也證明刪除能力可以透過後訓練資料強化而提升，暗示目前模型在刪除上的弱點主要是訓練不足，而非能力不可及。這將促使未來的基準設計與訓練資料策展更重視「刪除」這個長期被忽視的維護面向。

**Q13：這篇論文承認了哪些主要限制？**  
A：後訓練刪除教學的先導研究僅在單一 7B 規模模型上進行，尚未驗證在不同規模與架構上的效果。CanItDelete 目前聚焦於 Python 且僅包含純刪除任務，尚未涵蓋多語言或同時涉及新增與刪除的複雜情境。此外，為了控制變因，研究固定了 OpenHands 腳手架，因此不同模型在工具呼叫與定位策略上的差異可能沒有被完全探討。

**Q14：即使在給予確切刪除區段的情況下，模型仍會出現哪些失敗案例？**  
A：當提示明確指出要刪除的程式碼區段後，不完整刪除雖然大幅減少，但模型卻開始刪除超出指定區段的內容，或在應該只做減法時額外新增程式碼。這顯示問題不在於模型無法理解刪除指令，而在於它難以精準控制刪除邊界。換句話說，刪除失敗同時存在兩種極端：邊界不明時刪太少，邊界給定後又可能刪太多。

**Q15：根據這項研究，未來有哪些值得探索的方向？**  
A：未來可以將刪除範例納入不同規模模型的後訓練資料，並觀察其泛化到 SWE-bench Verified 與 CanItEdit 等混合任務的效果。研究者也可以設計更貼近維護者判斷的評估指標，例如修補簡潔度、慣例符合度與長期可維護性。最後，將 CanItDelete 擴展到 Python 以外的語言，並納入同時需要新增與刪除的真實修復情境，將有助於更全面地理解與改善模型的刪除行為。

## 實務應用指南

## 適用場景

1. **自動化重構與廢棄程式碼清理**  
   當團隊需要移除已棄用的函式、過時的相容性邏輯或重複實作時，可將刪除任務獨立抽出，像 CanItDelete 一樣要求模型「只刪、不補」，避免模型為了通過測試而用 Guard-and-Go 把舊邏輯包在防護條件裡。

2. **以刪除為主的缺陷修復代理**  
   許多真實 bug 的開發者修補程式（developer patch）其實是減法修復，例如移除錯誤的預設值、多餘的狀態轉換或無效的例外處理。這類場景適合在代理的提示中明確要求刪除，並搭配會因「目標程式碼仍存在」而失敗的加裝測試（retrofit tests）。

3. **程式碼審查與合併前閘道**  
   在 CI/CD 或 pull request 審查流程中，針對刪除型修改額外執行刪除召回率檢查：比對模型 patch 與參考刪除位置，確保通過測試的修補沒有遺留應刪除的確切行（exact line），降低維護者（maintainer）拒收 AI 產出貢獻的機率。

4. **模型後訓練資料策展**  
   若組織自行微調程式碼模型，可從真實提交（real commits）中挖掘「完整所需編輯即為刪除」的樣本，加入後訓練（post-training）混合資料。論文顯示僅佔 token 0.7% 的刪除範例即可提升 CanItDelete 與 SWE-bench Verified 表現。

5. **基準測試與模型選型**  
   在評估不同 frontier / open weights 模型時，除了整體解決率，可額外採用 CanItDelete 這類純刪除基準與診斷階梯（diagnostic ladder），區分「找不到位置」「定位到檔案/函式卻沒刪到行」「刪過頭」等不同失效模式。

## 實作前置條件

- **資料**：可取得程式碼庫（codebase）的 git 歷史、開發者修補程式，以及能執行的測試套件；最好有標註過的刪除型提交，或能自動篩選「完整所需編輯為刪除」的 commit。
- **運算**：若僅做推論與評估，需足夠的 GPU/TPU 或 API 額度執行 frontier 模型；若要進行後訓練，需支援 7B 以上模型的微調資源，並能處理約 12.8K 刪除樣本。
- **技能**：熟悉 Python 程式碼結構、單元測試與靜態分析工具；具備提示工程（prompt engineering）經驗；後訓練路線則需要資料工程與分散式訓練能力。
- **工具**：建議具備 OpenHands 或類似的程式碼代理腳手架（scaffold），以便固定工具呼叫與定位行為，減少不同框架帶來的變異。

---

## 實作步驟建議

1. **建立刪除敏感的真實任務集**  
   從內部專案挑選開發者 patch 以刪除為主的 issue，仿照 CanItDelete 製作「編輯前檔案（pre-edit file）＋純刪除答案」的任務，並使用考慮出現次數的確定性評估器（occurrence-aware deterministic evaluator）判斷是否完整刪除。

2. **加裝刪除檢查測試**  
   對這些任務額外撰寫會因「刪除目標仍存在」而失敗的測試，模擬論文 retrofit tests 的做法，避免 Guard-and-Go 型 patch 僥倖通過原有測試。

3. **設計累加提示（cumulative prompts）診斷階梯**  
   先給基礎提示，再逐步加入「明確刪除指令」「所在函式/類別/模組指標」「確切刪除區段（spans）」，觀察模型在哪一層開始改善，以判斷問題是定位、執行還是控制邊界。

4. **導入刪除召回率指標**  
   在評估腳本中計算 deletion recall 與 precision，並細分三個層級：是否修改到正確檔案、是否改到所在作用域、是否移除確切行，作為持續監控儀表板。

5. **後訓練補強刪除能力（選用）**  
   若提示與評估仍不足，從真實提交挖掘刪除樣本，佔後訓練混合資料約 0.5%–1% token，微調開放權重模型，並驗證增益是否轉移到 SWE-bench Verified 等通用基準。

6. **整合到審查與部署流程**  
   將上述評估與提示模板封裝成 CI 閘道或程式碼審查機器人，對於標記為 deletion-heavy 的 pull request 自動執行刪除召回率檢查與加裝測試。

## 潛在風險與注意事項

- **Guard-and-Go 難以被既有測試發現**  
   模型傾向用條件或後備邏輯包裹目標程式碼，使可維護性（maintainability）下降卻仍通過測試。必須額外設計刪除敏感測試，不能只看整體 test-passing patches。

- **過度刪除（刪過頭）**  
   一旦給出確切 spans，模型可能刪除超出指定區段，或在應純刪除時新增程式碼。建議在評估器中同時檢查「多刪」與「多增」，並要求 patch 最小化變更。

- **定位與執行混淆**  
   論文發現模型常已找到正確檔案與所在函式/類別/模組，卻沒刪到確切行。因此失敗不一定來自搜尋能力不足，而是編輯控制不精，需針對性地加強 span-level 編輯訓練。

- **資料污染與過擬合**  
   若後訓練樣本來自與評估任務相同的專案，可能產生資料洩漏。應以時間或 commit 切分訓練/測試，並在無關基準上驗證泛化能力。

- **規模與維護成本**  
   手動標註 200 筆等級的 CanItDelete 任務與加裝測試需要工程師時間；建議先從高頻、高風險的刪除型 issue 開始試點，再逐步擴大覆蓋率。

---

## 與其他技術的整合建議

- **CI/CD 閘道**：將 CanItDelete 風格的刪除召回率檢查與加裝測試嵌入合併前管線，作為除了單元測試通過之外的第二道品質門檻。
- **靜態分析工具**：結合 dead-code detection、linter 與型別檢查，先標記可能可刪除的程式碼區段，再交由 LLM 產出刪除 patch，降低定位難度。
- **RAG / 專案慣例檢索**：在提示中檢索專案慣例（repository conventions）與相似歷史提交，讓模型知道何時該刪、何時該保留向後相容邏輯。
- **程式碼代理腳手架**：固定使用 OpenHands 等框架，統一工具呼叫與檔案編輯介面，避免不同 scaffold 造成刪除行為差異，便於公平比較模型。
- **人機協作審查**：對於高風險刪除，讓模型產出候選 patch 後由維護者做最終確認，特別是涉及公開 API 或資料遷移的場景。

## 給不同背景讀者的閱讀建議

**初學者**：建議先從「適用場景」與「潛在風險」兩節讀起，理解 LLM 寫程式碼時為什麼會「寧可加條件也不刪除」，以及這對程式碼可維護性的影響；技術名詞可對照文末詞彙表，不必急著深入後訓練細節。

**AI 工程師**：重點閱讀「實作步驟建議」與「整合建議」，特別是累加提示診斷階梯、deletion recall 指標計算，以及如何將 CanItDelete 評估器與既有 CI/CD 結合；可進一步參考論文附錄的指標與統計方法。

**研究人員**：建議深入論文的方法論與實驗設計，包括參考刪除（reference deletion）的定義、三層級定位分析、CanItDelete 的採礦與評估方式，以及後訓練僅用 0.7% token 即帶來顯著提升的發現，這些都提供了可複製的研究路徑。

**產品經理**：請聚焦「適用場景」與「潛在風險」，評估導入刪除敏感檢查對維護者接受度、合併品質與長期技術債的影響；後訓練路線可視為中長期投資，短期可先透過加裝測試與審查閘道降低風險。
