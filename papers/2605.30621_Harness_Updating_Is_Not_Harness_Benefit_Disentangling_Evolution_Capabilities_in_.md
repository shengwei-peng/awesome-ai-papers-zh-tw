# 框架更新能力（Harness-Updating）並非框架受益能力（Harness-Benefit）：釐清自我演化大型語言模型代理（Self-Evolving LLM Agents）中的演化能力

## ⚡ TL;DR

探討LLM代理框架自我演化中，模型基礎能力是否預測其演化能力。
將演化能力拆為框架更新與框架受益兩項，跨七個模型與三個基準實驗分析。
發現更新能力與基礎能力無關，但受益能力呈非單調，中階受益最大，弱模型因啟用與遵循失敗受益最少。

## 摘要翻譯

大型語言模型代理（LLM Agents）日益被部署為圍繞可編輯外部框架（Harness）——包含提示詞（Prompt）、技能（Skill）、記憶（Memory）與工具（Tool）——所建構的系統，能在不更動模型參數的情況下影響任務執行。框架自我演化（Harness Self-Evolution）透過根據執行證據（Execution Evidence）更新這些框架，來調適此類代理。然而，模型在任務解決方面的基礎能力（Base Capability）是否能預測其在框架自我演化方面的能力，仍不明確：哪些模型能產生有用的框架更新，哪些模型又能真正從中受益？我們分析兩種框架自我演化能力：(i) 框架更新能力（Harness-Updating），即根據執行證據產生有用且持久框架更新的能力；(ii) 框架受益能力（Harness-Benefit），即在任務解決過程中從更新後框架受益的能力。我們的分析揭示兩項發現。首先，框架更新能力在基礎能力上呈現平坦趨勢：來自不同能力等級（Capability Tier）的模型所產生的框架更新，所帶來的效益驚人地相似；即使是 Qwen3.5-9B 的更新，其效益也與 Claude Opus 4.6 相當。其次，框架受益能力在基礎能力上呈現非單調性：弱能力模型（Weak-Tier Model）從更新後框架中受益甚微，中等能力模型（Mid-Tier Model）受益最多，而強能力模型（Strong-Tier Model）的受益程度則低於中等能力模型。我們將弱能力等級的低效益追溯至兩種失敗模式（Failure Mode）：弱能力模型可能無法啟用相關的框架工件（Harness Artifact），或是啟用了框架工件卻無法忠實遵循。這些發現建議將能力預算（Capability Budget）投入於任務解決代理（Task-Solving Agent）而非演化器（Evolver），並在代理訓練（Agent Training）中著重於框架調用（Harness Invocation）與長時程指令遵循（Long-Horizon Instruction Following）。我們的原始碼已公開於 https://github.com/A-EVO-Lab/a-evolve/tree/release/harness-evolution。

### 核心貢獻（3～5點）
- **拆解框架自我演化的兩種獨立能力**：明確區分「框架更新能力」（從執行證據產生有用持久框架更新）與「框架受益能力」（在任務解決中從更新框架受益），為後續研究建立可分析的雙軸框架。
- **揭示框架更新能力與基礎能力無關**：不同能力等級的模型所產生的框架更新帶來的效益驚人地相似，即使是 Qwen3.5-9B 的更新亦不遜於 Claude Opus 4.6，顯示「誰來更新框架」並非關鍵瓶頸。
- **揭示框架受益能力呈非單調性**：弱能力模型受益甚微、中等能力模型受益最多、強能力模型受益反而較少，挑戰「模型越強越能善用框架」的直覺假設。
- **診斷弱能力模型的兩種失敗模式**：框架啟用失敗（Harness Activation Failure，無法載入相關框架工件）與框架遵循失敗（Harness Adherence Failure，載入卻無法忠實執行），為弱模型無法受益提供具體機制解釋。
- **提出實務配置建議**：能力預算應優先投入任務解決代理而非演化器，並應在代理訓練中強化框架調用與長時程指令遵循能力。

### 適合對象
- 研究自我演化代理（Self-Evolving Agent）、代理式系統（Agentic System）與大型語言模型代理的學者與工程師。
- 從事代理訓練（Agent Training）、代理框架（Agent Harness）設計與部署時環境（Deployment-Time Environment）優化的實務工作者。
- 對模型診斷（Model Diagnosis）、能力預算分配、推理（Reasoning）與任務解決（Task Solving）能力分層議題感興趣的人工智慧研究者。
- 需評估在凍結的大型語言模型（Frozen LLM）外圍投入編輯元件所帶來效益的產品決策者與技術主管。

## 深度分析

#### 方法論解析

本文提出一個關鍵的概念性解耦框架，將「框架自我演化」（harness self-evolution）系統中的模型能力拆解為兩個獨立維度：**框架更新能力**（harness-updating）與**框架受益能力**（harness-benefit）。這個解耦是本文最重要的方法論貢獻，因為它打破了過往研究將「端到端效能增益」視為單一指標的慣例。

**框架演化系統的結構設計**

如圖 1 所示，作者將代理式系統（agentic system）抽象為兩個角色：凍結的大型語言模型（frozen LLM）作為任務解決代理（task-solving agent），以及另一個大型語言模型作為演化器（evolver）。任務解決代理透過外部框架（harness）——包含提示詞（prompts）、技能（skills）、記憶（memories）、工具（tools）等可編輯工件（artifacts）——與外部環境互動。演化器則從執行證據（execution evidence，包含失敗、回饋、軌跡、成功程序等）中產生持久的框架更新。這種「雙模型」設計使得兩個能力可以被獨立測量：固定任務解決代理、變動演化器，可測量框架更新能力；固定演化器、變動任務解決代理，則可測量框架受益能力。

**實驗設計的因子化策略**

作者採用因子化（factorial）實驗設計，在三個代理基準（agentic benchmarks）上配對七個大型語言模型（涵蓋開源與閉源、不同能力等級）作為代理與演化器。這種設計的精妙之處在於：透過交叉配對，可以分離出每個能力對端到端效能的獨立貢獻。例如，若固定 Claude Opus 4.6 為任務解決代理，分別用 Qwen3.5-9B 與 Claude Opus 4.6 作為演化器，兩者產生的下游增益若相近，則證明框架更新能力對基礎能力（base capability）並不敏感。

**失敗模式的診斷方法**

針對弱能力模型（weak-tier models）受益最低的現象，作者提出兩個失敗模式作為解釋：（1）**框架啟用失敗**（harness activation failure）——模型未能載入相關框架工件；（2）**框架遵循失敗**（harness adherence failure）——模型載入框架但無法在長時程任務（long-horizon task）中忠實遵循。這個診斷框架將「弱模型為何受益低」從單純的「能力不足」細化為可操作的訓練目標。

#### 實驗數據解讀

**框架更新能力的平坦性**

第一個核心發現是：框架更新能力在基礎能力上呈現平坦（flat）特性。具體而言，跨能力等級的模型作為演化器時，所產生的框架更新帶來的下游增益差異極小——在任何基準上，演化器之間的差距最多僅 3.1 個百分點。這個數據極為關鍵，因為它意味著即使使用 Qwen3.5-9B 這類相對小型的開源模型作為演化器，其產生的框架更新仍能與 Claude Opus 4.6 的更新帶來相當的任務增益。這直接挑戰了「演化器越強、框架越好」的直覺假設。

**框架受益能力的非單調性**

第二個核心發現揭示了非單調（non-monotonic）關係：中等能力模型（mid-tier models，例如 GPT-OSS-120B）從更新框架中受益最多；強能力模型（strong-tier models，例如 Claude Opus 4.6）因接近效能天花板（performance ceiling）而受益較少；而弱能力模型（如 Qwen3-32B）雖然理論上有最大的提升空間，實際上受益最少。這種倒 U 型曲線（inverted-U curve）是本文最具實務意涵的發現。

**弱模型的雙重失敗機制**

針對弱模型的低受益現象，作者提供了量化證據：Qwen3-32B 的框架載入率僅約 25%，而強模型約為 96%，呈現約四倍的差距。更嚴重的是，即使框架被載入，弱模型在長時程軌跡中的指令遵循（instruction following）衰減速度比強模型陡峭四倍以上。這兩個數據點精確定位了弱模型失敗的兩個階段——「是否載入」與「載入後是否遵循」——為後續訓練提供了明確的優化方向。

**實驗設計的內部效度**

值得肯定的是，作者透過固定其中一個角色、變動另一個角色的方式，確保了因果歸因的清晰度。例如，當比較不同演化器時固定任務解決代理，反之亦然。這種控制變項的策略避免了混淆變項（confounding variables）對結論的污染，使得「框架更新能力平坦」與「框架受益能力非單調」這兩個結論具有較高的內部效度。

#### 與現有研究的比較

**相較於過往自演化代理研究的突破**

過往的自演化代理方法（如 Madaan et al., 2023 的 SELF-REFINE；Wu et al., 2025；Agrawal et al., 2026；Xia et al., 2026；Lin et al., 2026b）多聚焦於「如何讓框架自我演化」，並以端到端任務效能作為唯一評估指標。本文則將視角從「方法設計」轉向「能力分析」，提出兩個關鍵問題：哪些模型能產生有用的框架更新？哪些模型能從中受益？這種從「how」到「who」的轉變填補了過往文獻中對「演化器與代理能力不對稱性」的認識空白。

**與框架工程（harness engineering）研究的互補**

過往的框架工程研究（如 Yao et al., 2022；Qin et al., 2024；Li et al., 2026b；Liu et al., 2026）側重於框架的表示形式——提示詞、工具、記憶、技能、程式碼等——並探討如何設計這些工件。本文則將焦點從「框架裝什麼」轉向「模型如何與框架互動」，揭示了框架設計與模型能力之間的耦合關係。具體而言，本文指出即使框架設計良好，若任務解決代理無法啟用或遵循框架，演化效益仍會流失。

**本文的侷限性**

儘管貢獻明確，本文仍有幾項侷限值得注意：（1）實驗僅在三個代理基準上進行，跨領域的泛化性仍待驗證；（2）七個模型的樣本量雖然涵蓋了不同等級，但對於「能力等級」的劃分依據未充分說明，可能存在主觀性；（3）失敗模式的診斷主要基於載入率與遵循衰減率，缺乏對失敗機制的更深層因果分析；（4）框架更新能力的平坦性是否在更複雜的框架類型（例如多模態工具鏈）下仍成立，仍屬未知。

#### 可重現性評估

**程式碼與資料的開放性**

作者明確表示原始碼已公開於 GitHub（https://github.com/A-EVO-Lab/a-evolve/tree/release/harness-evolution），這對於可重現性是重要的第一步。從論文結構判斷，該程式碼庫應包含完整的實驗流程、模型配對配置、基準評測腳本等。

**可重現性的潛在挑戰**

然而，完整重現本文結果仍面臨若干挑戰：（1）閉源模型（如 Claude Opus 4.6）的 API 行為可能隨版本更新而變化，導致結果不一致；（2）三個代理基準的具體名稱與版本在提供的文本中未完全揭示，重現者需從程式碼庫推斷；（3）框架更新的「持久性」如何在不同實驗中標準化，需仰賴程式碼中的具體實作細節；（4）模型診斷（model diagnosis）的量化指標（如載入率、遵循衰減率）的計算方式需從程式碼中提取。

**模型權重與資料可用性**

對於開源模型（如 Qwen3.5-9B、Qwen3-32B、GPT-OSS-120B），模型權重可直接取得；對於閉源模型，僅能透過 API 存取。基準資料集的可取得性則需視具體選擇而定——若使用公開基準（如 SWE-bench、HumanEval 等變體），則資料可重現；若為自建基準，則需仰賴作者釋出。

#### 未來研究方向

**框架啟用作為一階訓練目標**

本文最直接的延伸是將「框架調用」（harness invocation）從隱性行為提升為顯性的訓練目標。可以設計專門的監督式微調（supervised fine-tuning）資料，教導模型在特定任務情境下主動載入相關技能或記憶；或是透過強化學習（reinforcement learning）以「框架載入成功率」作為獎勵訊號。這與傳統的指令遵循訓練不同，因為它要求模型不僅理解指令，還要主動檢索與運用外部工件。

**長時程指令遵循的專項強化**

針對框架遵循失敗，未來研究可探索：（1）位置編碼（positional encoding）或注意力機制（attention mechanism）的改進，以延緩長時程中的指令遺忘；（2）將框架內容編碼為更結構化的形式（例如帶有優先級標記的技能清單），降低遵循負擔；（3）設計「框架遵循率」作為代理訓練的專項評測指標，類似於長上下文理解（long-context understanding）領域的評測體系。

**演化器與代理的異質配對策略**

本文發現框架更新能力平坦，但未深入探討「演化器—代理」配對是否存在最佳組合。例如，是否存在某些演化器對特定類型的任務解決代理特別有效？未來可研究基於任務特性或代理弱點的演化器選擇機制，甚至設計「演化器路由」（evolver routing）系統。

**框架演化能力的基準化**

目前缺乏專門評測「框架演化能力」的基準。本文提出的兩個能力維度可作為新基準的設計基礎：框架更新能力基準可測量模型從執行證據中提煉可重用程序的品質；框架受益能力基準可測量模型對外部框架的啟用率與遵循率。這類基準將有助於系統性地追蹤模型在代理式系統中的演化能力進展。

**多模態與多代理框架的擴展**

本文聚焦於文字型代理框架，未來可將分析擴展至多模態框架（包含視覺、音訊工件）以及多代理框架（多個代理共享或競爭框架）。在多代理情境下，框架更新能力與受益能力的解耦可能呈現更複雜的動態，例如某代理產生的框架更新可能被另一代理誤用或忽略，這將是值得探索的理論方向。

**框架演化的理論模型建構**

最後，本文以實驗觀察為主，未來可嘗試建立框架演化的理論模型。例如，將框架視為共享的外部記憶，演化器與代理視為讀寫雙方，則可借用分散式系統中的快取一致性（cache coherence）理論來分析框架更新的傳播效率與失效模式。這種理論化將有助於預測不同模型組合下的演化效益，並指導更系統化的系統設計。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文聚焦於「框架自我演化」（harness self-evolution）這一新興領域中一個尚未被釐清的核心問題：模型的基礎任務解決能力（base capability）究竟能否預測其在框架自我演化中的表現。具體而言，論文試圖回答兩個實務問題——哪些模型能從執行證據中產生有用的框架更新（harness updates），以及哪些模型能真正從這些更新後的框架中受益。由於現有自我演化代理方法多以端到端（end-to-end）方式評估，無法區分「演化器」（evolver）與「任務解決代理」（task-solving agent）各自的貢獻，因此這個問題長期被遮蔽。

**Q2：為什麼現有的端到端評估方式不足以回答這些問題？**
A：現有方法僅以最終任務分數衡量自我演化系統的整體效益，但這個總分其實混合了兩個獨立來源：演化器所產生框架更新的品質，以及任務解決代理實際運用這些更新的能力。當總分提升時，研究者無法判斷改善究竟來自更好的更新內容，還是來自代理更善於使用更新後的框架。這種混淆使得模型選擇、能力預算分配與訓練目標設計都缺乏明確依據，也讓不同自我演化方法之間的比較失去解析度。

**Q3：釐清這兩種能力為何對整個領域很重要？**
A：若無法區分「框架更新能力」與「框架受益能力」，研究社群與實務團隊在設計自我演化系統時容易誤將資源投入錯誤的位置。論文的發現顯示，演化器的能力差距對最終表現影響極小，反而是任務解決代理的能力才是關鍵變數；這對模型選用、預算配置與訓練策略都有深遠影響。此外，理解弱模型為何無法受益（涉及框架啟用與框架遵循兩種失敗模式），能指引未來代理訓練應強化哪些具體技能，進而推動整個領域朝更穩健的方向發展。

**Q4：論文提出了哪兩個核心能力概念？**
A：論文定義了兩個可分離的能力維度：「框架更新能力」（harness-updating）指模型作為演化器時，從執行證據中產生有用且持久框架更新的能力；「框架受益能力」（harness-benefit）則指模型作為任務解決代理時，能在任務執行過程中實際受惠於更新後框架的能力。這兩個能力分別對應自我演化系統中的兩個角色——前者負責「寫入」，後者負責「讀取並使用」——並可透過固定其中一個角色、變動另一個角色的實驗設計加以獨立測量。

**Q5：論文最關鍵的創新之處為何？**
A：論文的關鍵創新在於將原本被視為單一現象的「自我演化效益」拆解為兩個可獨立量測的能力，並透過系統性的角色互換實驗（cross-role experiments）揭示兩者與基礎能力之間存在截然不同的關係。這種「解耦」（disentanglement）的研究視角突破了過去端到端評估的盲點，使研究者得以觀察到「框架更新能力對基礎能力幾乎不敏感」與「框架受益能力對基礎能力呈非單調關係」這兩個反直覺的現象，進而提出具體的設計準則。

**Q6：論文採用了哪些關鍵的實驗設計選擇？**
A：論文採用「角色配對」（role pairing）的實驗設計：將七個橫跨不同能力等級與開源／閉源家族的模型，分別擔任演化器與任務解決代理，在三個具代表性的代理基準上進行全面配對實驗。這種設計讓研究者能在控制單一變數的條件下，獨立觀察每個角色對最終表現的貢獻。此外，論文還針對弱模型進行深入的個案分析（case study），透過載入率與遵循率等指標診斷失敗根源，使結論不僅是現象描述，更具備機制層級的解釋力。

**Q7：論文使用了哪些基準與模型來驗證其發現？**
A：實驗涵蓋三個具代表性的代理基準（agentic benchmarks），橫跨不同任務特性以確保結論的泛化性。模型方面則選用七個大型語言模型，涵蓋開源與閉源家族，並刻意跨越弱、中、強三個能力等級（capability tier），其中包括 Qwen3.5-9B、Qwen3-32B、GPT-OSS-120B 與 Claude Opus 4.6 等具代表性的模型。這種「多基準 × 多模型 × 多等級」的設計使論文得以在異質環境中檢驗其核心論點的穩健性。

**Q8：論文最重要的兩個實驗發現為何？**
A：第一個關鍵發現是「框架更新能力對基礎能力幾乎不敏感」（flat in base capability）：無論演化器的能力高低，其產生的框架更新所帶來的效益差異極小——例如 Qwen3.5-9B 演化器所產生的更新，其下游效益竟可媲美 Claude Opus 4.6。第二個關鍵發現是「框架受益能力對基礎能力呈非單調關係」（non-monotonic）：中等能力模型（如 GPT-OSS-120B）受益最多，強模型因接近效能天花板而受益較少，弱模型則因兩種失敗模式而受益最少，呈現倒 U 形曲線。

**Q9：論文如何透過消融與個案研究支持其論點？**
A：論文透過兩類補充分析強化其結論：一是針對弱模型的失敗模式進行深入的個案研究，量化「框架啟用失敗」（harness activation failure，例如 Qwen3-32B 的載入率僅約 25%，遠低於強模型的約 96%）與「框架遵循失敗」（harness adherence failure，弱模型在長時程軌跡中的遵循衰減速度比強模型陡峭四倍以上）；二是量化不同演化器之間的效益差距，證實該差距在任何基準上都不超過 3.1 個百分點，從經驗上支持「將能力預算投入演化器報酬遞減」的設計建議。

**Q10：這項研究適用於哪些實際部署情境？**
A：對於在部署時環境（deployment-time environment）中運作的代理式系統特別有價值，例如任務分布會隨時間漂移的客服代理、需要持續吸收新工具的軟體操作代理，以及在邊緣案例（edge cases）出現後必須調整流程的長時程任務代理。在這些情境中，框架自我演化是維持系統效能的關鍵機制，而本研究的發現能幫助工程團隊判斷應將有限的模型能力預算配置於演化器還是任務解決代理，從而做出更經濟的部署決策。

**Q11：這項研究對產品設計與工程實務有何具體啟示？**
A：產品層面有三項明確指引：第一，能力預算應優先配置給任務解決代理而非演化器，因為後者的能力差距對最終表現影響有限；第二，框架調用（harness invocation）應被視為代理訓練中的「一等公民技能」，特別是針對弱模型需補強其載入框架的能力；第三，長時程指令遵循（long-horizon instruction following）是另一關鍵訓練目標，因為即使框架成功載入，弱模型仍可能在軌跡中段失去遵循。這些指引可直接轉化為模型選型、訓練資料設計與評估指標制定的具體行動。

**Q12：這項研究對整個自我演化代理領域有何長遠影響？**
A：本研究將「自我演化效益」從一個模糊的端到端概念，轉化為兩個可獨立量測、可分別優化的能力維度，為未來研究提供了更精細的分析框架。它促使後續工作必須明確區分「誰負責產生更新」與「誰負責使用更新」，並在報告成果時分別評估兩者的貢獻。同時，研究所揭示的「演化器報酬遞減」現象，可能會引導資源從開發更強的演化模型，轉向強化任務解決代理的框架調用與長時程遵循能力，進而重塑整個領域的研發優先順序。

**Q13：論文承認哪些研究限制？**
A：論文的實驗範圍受限於七個模型與三個代理基準，雖然橫跨不同能力等級與開源／閉源家族，但樣本規模仍屬有限，可能無法完全代表整個模型生態。此外，框架的具體形式（提示詞、技能、記憶、工具等）在不同基準中可能有所差異，論文的結論是否對所有類型的框架工件（harness artifact）皆成立，仍有待更廣泛的驗證。最後，論文主要關注效益的量化，對於框架更新內容的品質（例如可讀性、可組合性、安全性）等質性面向著墨較少。

**Q14：論文識別出哪些具體的失敗案例？**
A：論文清楚指出弱模型存在兩種失敗模式：第一種是「框架啟用失敗」，表現為模型在任務解決過程中根本未載入相關的框架工件，例如 Qwen3-32B 的載入率僅約 25%，意味著大量潛在可用的更新內容被閒置；第二種是「框架遵循失敗」，表現為模型雖然成功載入框架，但在長時程任務的後段逐漸偏離框架指引，導致執行結果不正確。這兩種失敗模式解釋了為何弱模型雖有最大的進步空間，卻實際受益最少。

**Q15：論文提出了哪些未來研究方向？**
A：基於其發現，論文暗示數個值得探索的方向：首先是開發專門強化「框架調用」能力的訓練方法，使弱模型能更可靠地載入並使用框架工件；其次是設計針對長時程指令遵循的訓練策略，以對抗弱模型在軌跡中段出現的遵循衰減；再者是探索框架表示形式（representation）對兩種能力的影響，例如更結構化或更簡潔的框架是否有助於弱模型遵循；最後則是將此分析框架擴展至多代理協作、多模態代理等更複雜的場景，檢驗「框架更新」與「框架受益」的分離現象是否依然成立。

## 實務應用指南

### 適用場景

1. **企業內部客服與 IT 維運代理**：在大型組織中，客服或 IT 維運任務常隨產品線更新、季節性事件而漂移。透過框架自我演化，系統可從工單解決軌跡中自動萃取可重用的技能（例如「重置 VPN 的標準步驟」），並寫入技能庫供後續任務調用，無需人工撰寫維運手冊。

2. **軟體工程中的程式碼審查與重構助手**：在程式碼審查代理中，框架可包含風格指南、安全檢核清單、重構範例等工件。代理在審查過程中累積新的檢核規則或重構模式，演化器將其沉澱為可重用的技能，使後續審查更貼近團隊實際慣例。

3. **資料分析與商業智慧代理**：分析代理在處理 SQL 查詢、儀表板生成時，可將成功的查詢範本、欄位對應規則、視覺化偏好沉澱為記憶或技能。隨著任務進行，框架會自動演化為更貼近該組織資料語意的版本。

4. **多步驟研究與報告撰寫代理**：在長時程研究任務中，代理可將文獻檢索策略、引用格式、章節結構等經驗沉澱為提示詞或技能，使後續報告品質穩定提升，特別適合顧問公司、學術機構、新聞媒體。

5. **嵌入式裝置或邊緣 AI 的工具呼叫代理**：在資源受限的部署環境中，無法頻繁更新模型權重，但可透過框架演化讓代理學會更有效率地呼叫工具、組合 API，特別適合 IoT 閘道器、工業控制、智慧家居等場景。

### 實作前置條件

**資料面**
- 任務軌跡資料：需蒐集代理在真實任務中的完整軌跡，包含觀察、動作、工具呼叫、最終成敗與回饋。建議至少數百至數千筆具代表性的成功與失敗案例。
- 任務分布文件：清楚記錄任務類型、難度分布、邊緣案例，作為評估框架演化效果的基準。
- 既有框架工件：若已有提示詞、技能、記憶、工具等工件，需整理成可被演化器讀寫的結構化格式（例如技能以 Markdown + 函式簽名儲存）。

**運算面**
- 推理算力：需同時部署任務解決代理與演化器兩個角色。演化器可使用較小模型（例如 Qwen3.5-9B 等級），任務解決代理則依任務難度選擇合適等級。
- 儲存空間：框架工件會隨時間累積，需規劃版本控制與去重機制，避免技能庫無限膨脹。
- 評估管線：需建立可重現的基準測試，以便量化框架演化前後的任務表現差異。

**技能面**
- 具備 LLM 代理開發經驗，理解提示詞工程、工具呼叫、ReAct 等基本模式。
- 熟悉結構化輸出與函式呼叫，能設計讓演化器可靠地寫入框架的介面。
- 具備基本的錯誤分析能力，能區分框架啟用失敗與框架遵循失敗兩種弱模型典型問題。

### 實作步驟建議

**步驟一：盤點現有框架並建立基準**
盤點目前代理使用的提示詞、技能、記憶、工具清單，並在不啟動演化的情況下，於代表性任務上量測基礎能力分數，作為後續比較的基準線。

**步驟二：設計演化迴圈**
定義「執行 → 診斷 → 更新 → 再執行」的閉環。執行階段由任務解決代理完成任務並留下軌跡；診斷階段由演化器分析成功與失敗案例；更新階段由演化器將新發現寫入框架；再執行階段以更新後的框架重跑任務以驗證效果。

**步驟三：選擇合適的演化器**
根據本文發現，框架更新能力在不同能力等級間差異極小（最多約 3.1 個百分點）。因此演化器可選用成本較低的中小型模型（例如 Qwen3.5-9B 等級），不必為了演化器升級到旗艦模型。把能力預算留給任務解決代理。

**步驟四：選擇任務解決代理的等級**
本文顯示中等能力模型（例如 GPT-OSS-120B 等級）從框架演化中受益最多。強模型已接近效能天花板，邊際效益低；弱模型則因框架啟用失敗與框架遵循失敗而受益有限。建議優先採用中等能力模型作為任務解決代理。

**步驟五：監控框架啟用率與遵循率**
為任務解決代理建立兩項關鍵指標：框架啟用率（代理是否在需要時載入相關技能）與框架遵循率（代理是否在長時程軌跡中持續遵守框架指示）。若啟用率偏低（例如低於 50%），需在代理訓練中加入框架調用能力；若遵循率隨軌跡長度快速下降，則需強化長時程指令遵循能力。

**步驟六：建立版本化與回滾機制**
框架工件應納入版本控制，每次演化產生新版本時保留前一版本。當新版本在評估管線中表現不如前一版時，自動回滾，避免框架漂移導致系統退化。

**步驟七：迭代評估與預算分配**
定期以基準測試量測框架演化帶來的增益，並將結果回饋到模型選擇決策。若發現任務解決代理是瓶頸，投資於升級代理或針對性訓練；若發現演化器是瓶頸，則優先檢查演化器的診斷品質與寫入介面，而非直接升級模型。

### 潛在風險與注意事項

**風險一：弱模型無法啟用框架**
弱能力模型可能根本不會載入相關技能或記憶，導致框架演化完全無效。緩解方式：在代理訓練中將框架調用列為一等公民技能，例如在系統提示中明確指示「遇到 X 類任務時必須先查詢技能庫」，並透過合成資料訓練模型養成此習慣。

**風險二：弱模型無法遵循框架**
即使框架被載入，弱模型可能在長時程任務中逐漸偏離框架指示。緩解方式：縮短單次任務的步驟數、在關鍵節點插入框架重讀機制、或將長任務拆解為多個子任務並在每個子任務開頭重新載入框架。

**風險三：框架工件累積過多導致上下文膨脹**
隨著演化進行，技能庫可能膨脹到超出模型上下文長度。緩解方式：定期對技能進行摘要、合併、去重；採用檢索式技能載入而非全量載入；設定技能數量上限並淘汰低頻技能。

**風險四：演化器產生低品質或有害更新**
演化器可能從失敗案例中學到錯誤的啟發式，或將個案經驗過度泛化。緩解方式：在更新寫入前加入驗證步驟（例如以小型評估集測試新框架），並設置人工審核節點處理高風險工件。

**風險五：強模型邊際效益低造成投資浪費**
若直接採用旗艦模型作為任務解決代理，框架演化的邊際效益有限。緩解方式：依據本文發現，採用中等能力模型搭配框架演化，往往比單獨使用強模型更具成本效益。

**風險六：評估管線與真實分布脫節**
若基準測試無法反映真實任務分布，框架演化的效果可能被高估或低估。緩解方式：定期以真實任務樣本更新評估集，並追蹤線上表現指標。

### 與其他技術的整合建議

**與 RAG（檢索增強生成）整合**
框架中的技能與記憶本質上是結構化的檢索物件。可將技能庫視為一種特殊的 RAG 知識庫，但比一般 RAG 更具程序性（包含可執行步驟）。建議沿用現有 RAG 的檢索基礎設施，但為技能加入觸發條件標籤，使代理能在正確情境下自動載入。

**與版本控制與 CI/CD 整合**
框架工件應如同程式碼一般納入 Git 版本控制，並建立 CI 管線：每次框架更新自動觸發評估測試，通過後才合併至主分支。這能避免框架漂移並提供完整的演化歷史。

**與監控與可觀測性平台整合**
將框架啟用率、遵循率、任務成功率等指標接入既有的監控平台（例如 Prometheus、Grafana），並設定告警閾值。當指標異常時，可快速定位是演化器、任務解決代理或框架本身的問題。

**與多代理架構整合**
在多代理系統中，可將演化器設計為獨立的元代理，定期巡覽各任務代理的軌跡並更新共享框架庫。這種集中式演化能避免每個代理各自演化造成的不一致。

**與模型微調管線整合**
當發現弱模型在框架啟用或遵循上有系統性缺陷時，可將相關軌跡整理成微調資料，針對性訓練模型。這與本文建議的「將框架調用與長時程指令遵循列為代理訓練目標」一致。

---

### 給不同背景讀者的閱讀建議

**給初學者**：本文的核心訊息很直觀：與其砸錢升級負責「寫教材」的演化器，不如把資源放在負責「用教材」的任務解決代理上。建議先理解「框架」是什麼（提示詞、技能、記憶、工具的集合），再讀圖 2 的兩個發現，理解為什麼中等模型反而受益最多。

**給 AI 工程師**：重點關注「框架啟用失敗」與「框架遵循失敗」這兩個失敗模式，這直接影響你在實作時要監控哪些指標。建議在系統中加入框架啟用率與遵循率的儀表板，並在代理訓練資料中強化框架調用行為。演化器可選用成本較低的中小型模型，把預算留給任務解決代理。

**給研究者**：本文最有意思的發現是「框架更新能力在不同能力等級間幾乎平坦」，這挑戰了直覺上「強模型必然產生更好更新」的假設。建議延伸思考：為什麼框架更新對模型能力不敏感？是因為更新任務本身較簡單，還是因為現有評估指標無法捕捉更新品質的細微差異？另外，「框架受益能力非單調」也值得深入研究，特別是弱模型的兩種失敗模式是否可透過特定訓練方法緩解。

**給產品經理**：這篇論文對資源配置有明確指引：把能力預算投資在任務解決代理而非演化器；選擇中等能力模型搭配框架演化，往往比單獨使用旗艦模型更具成本效益。在產品規劃上，應將框架演化視為「讓中等模型變強」的槓桿，而非「讓強模型更強」的工具。同時需注意，弱模型用戶可能看不到框架演化的價值，需在產品設計中考慮模型等級與功能開放的對應關係。
