## 摘要翻譯

近期的智慧體（agent）基準測試（benchmark）越來越將評估奠基於可執行環境，從程式碼修復（code repair）、網頁導航（web navigation）、應用程式 API（app APIs）到函式呼叫（function calling）也不例外。然而，要完成程式碼之外、具實質影響力的工作，僅產生看似合理的回應或有效的工具呼叫並不足夠：智慧體必須在多輪互動（multi-turn interaction）中蒐集遺漏資訊、遵循領域政策（domain policies）、協調相互依賴的工具，並實現正確且無連帶效應（collateral effects）的持久狀態轉換（persistent state transition）。本文提出 Thinkingbox，一個用於工具—智慧體—使用者互動（tool-agent-user interaction）的沙盒（sandbox），提供隔離的 MCP 相容工具工作階段（MCP-compatible tool sessions）、完整的執行軌跡（execution traces），以及依據終端後端狀態（terminal backend state）進行的結果評估（outcome evaluation）。建構於此沙盒之上的 Thinkingbox-bench 包含橫跨多種情境的 507 個受政策約束的工作流程（policy-conditioned workflows），涵蓋零售（retail）、款待業（hospitality）、汽車保險（auto insurance）、新銀行內部 IT 支援（neobank internal IT support），以及顧問公司 IT／HR 支援（consulting IT/HR support）等領域。每次嘗試都會由任務專屬的可執行檢查（executable checks）進行評估，這些檢查接受有效軌跡（valid trajectories），同時拒絕錯誤效應（wrong effects）、遺漏效應（missing effects）或額外效應（extra effects）；特定任務還會額外檢查最終回應（final response）的必要屬性（required properties）。橫跨專有模型（proprietary models）與開源權重模型（open-weight models），最佳模型達到 65.36% 的 pass@1，但 pass@20 僅為 25.25%。此外，許多失敗的嘗試顯示出正常終止與有效的狀態改變動作，顯示回應或工具呼叫層級的訊號並非端對端（end-to-end）任務完成的明確代理指標（proxies）。Thinkingbox-bench 揭示了偶爾找到成功軌跡與可靠完成具狀態商業任務之間存在巨大落差。我們公開釋出 Thinkingbox 與 Thinkingbox-bench：https://github.com/microsoft/thinkingbox

### 核心貢獻（3～5點）
- 提出 Thinkingbox 沙盒（sandbox）：支援工具—智慧體—使用者互動（tool-agent-user interaction），提供隔離的 MCP 相容工具工作階段（MCP-compatible tool sessions）、完整執行軌跡（execution traces），並能依據終端後端狀態（terminal backend state）進行結果評估（outcome evaluation）。
- 建構 Thinkingbox-bench 基準：收錄 507 個受政策約束的工作流程（policy-conditioned workflows），涵蓋零售、款待業、汽車保險、新銀行內部 IT 支援與顧問公司 IT／HR 支援等真實商業情境。
- 設計可執行檢查（executable checks）評估機制：接受有效軌跡（valid trajectories），並拒絕錯誤、遺漏或額外效應（wrong / missing / extra effects），部分任務另檢核最終回應（final response）的必要屬性。
- 揭示可靠性差距（reliability gap）：最強模型 pass@1 達 65.36%，pass@20 僅 25.25%，且回應／工具呼叫層級訊號無法作為端對端任務完成的代理指標。

### 適合對象
從事大型語言模型智慧體（LLM agents）研究與開發的學者與工程師，特別是關注企業流程自動化、工具使用評測、可執行基準測試設計，以及需要評估智慧體在多輪互動中遵循政策與正確改變後端狀態的研究者與產品團隊。

## 深度分析

#### 方法論解析

Thinkingbox 的核心貢獻在於把「agent（智慧體）能否完成工作」從「產生合理回應或合法 function call（函式呼叫）」提升到「是否正確驅動終端後端狀態轉換」。作者將每個任務形式化為  
\[
x=(b_0,g,T,U,C)
\]  
其中 \(b_0\) 為 initial backend state（初始後端狀態）、\(g\) 為 user goal（使用者目標）、\(T\) 為 domain tools（領域工具）集合、\(U\) 為 simulated user policy（模擬使用者政策）、\(C=\{c_i\}_{i=1}^m\) 則是一組隱藏的 executable checks（可執行檢查）。這個 formulation 把商業流程視為一個 induced POMDP（誘發的部分可觀察馬可夫決策過程）：agent 在每一輪只能觀察到 dialogue history（對話歷史）與 tool observations（工具觀察），然後選擇發送 user-facing message（面向使用者的訊息）或執行 tool action（工具動作）\((\tau_t,p_t)\)；後者會在 isolated backend session（隔離的後端工作階段）中實際改變狀態。

整個互動由 orchestrator（編排器）統一驅動，形成一個可重複的 loop（迴圈）：simulated user（模擬使用者）依據政策與目標提出需求或追問；LLM agent（大型語言模型智慧體）決定要詢問、呼叫工具或回覆；domain tools（領域工具）透過 MCP-compatible tool sessions（MCP 相容工具工作階段）執行；side-effect extractor（副作用擷取器）記錄 persistent state transition（持久狀態轉換）；最後 executable judges（可執行評判器）根據 \(C\) 評分。MCP 相容的設計讓每個任務世界都能被獨立實例化、重置與隔離，避免 cross-task contamination（跨任務污染），也讓同一套 runtime（執行環境）能同時服務 inference（推論）、leaderboard evaluation（排行榜評估）與 failure analysis（失敗分析）。

評估設計是方法論的關鍵。不同於傳統只看最終答案或 tool-call trace（工具呼叫軌跡）是否合法，Thinkingbox 採用 outcome evaluation（結果評估）：每個任務都有針對 terminal backend state（終端後端狀態）的檢查，能夠接受多條 valid trajectories（有效軌跡），但會拒絕 wrong effects（錯誤效應）、missing effects（遺漏效應）與 extra effects（額外效應）。此外，30 個任務還對 final response（最終回應）套用 binary rubrics（二元評分標準），檢核 required disclosures（必要揭露事項）、confidentiality（機密性）與 consistency（一致性）。這種設計特別適合 stateful business workflows（具狀態的商業工作流程），因為它把「工作完成與否」轉換成可執行的狀態斷言，而不是簡化成單一文字答案。

#### 實驗數據解讀

Thinkingbox-bench 包含 507 個 policy-conditioned workflows（受政策約束的工作流程），橫跨 retail / e-commerce（零售／電子商務）、travel and hospitality（旅遊與款待）、auto insurance（汽車保險）、neobank internal IT support（新銀行內部 IT 支援）與 consulting IT / HR support（顧問公司 IT／HR 支援）五個領域。作者對 12 個 proprietary models（專有模型）與 open-weight models（開源權重模型）進行測試，每個任務重複 20 次，並報告 pass@1（單次嘗試通過率）、pass@20（二十次嘗試中至少一次通過率）與 pass^20（all-20 success，全部 20 次成功比例）。

最強模型的表現為 pass@1 65.36%、pass@20 91.12%、pass^20 僅 25.25%。這組數字揭示了明顯的 reliability gap（可靠性差距）：幾乎所有任務都可在 20 次嘗試內找到成功軌跡，但同一模型卻很難每次都穩定複製該成功。換句話說，discoverability（可發現性）高，但 dependable repetition（可倚賴的重複性）低。這也說明 response-level（回應層級）或 tool-call-level（工具呼叫層級）的訊號並非 end-to-end task completion（端到端任務完成）的可靠代理；許多失敗軌跡其實會「乾淨地結束」並產生看似合法的 state-changing actions（狀態改變動作），卻在終端狀態上出現錯誤、遺漏或多餘的副作用。

從失敗模式來看，常見問題包括：呼叫正確 API 但選錯 entity（實體）、在未收集 required confirmation（必要確認）前就更新紀錄、產生流暢的使用者訊息但 backend（後端）未真正改變，以及執行違反 domain policies（領域政策）的連帶操作。evaluator ablations（評估器消融）進一步顯示，僅檢查工具呼叫是否流暢會高估模型能力，唯有同時檢查 terminal backend state、side effects（副作用）與 final response，才能區分「會用工具」與「真正完成工作」。

#### 與現有研究的比較

現有 executable benchmarks（可執行基準測試）大多聚焦於 code repair（程式碼修復）、web navigation（網頁導航）、app APIs（應用程式 API）或 function calling（函式呼叫），其成功準則相對容易規格化與執行，但較少處理多輪、具狀態且帶有政策約束的商業流程。在 stateful conversational tools（具狀態對話工具）領域，ToolSandbox、τ-bench 與 τ2-bench 已經引入狀態檢查與重複可靠性，但 Thinkingbox 進一步提供跨五個商業領域的 common runtime（通用執行環境），並以 task-specific executable checks（任務專屬可執行檢查）偵測 collateral effects（連帶效應／附帶影響）。

AppWorld 的 state-based tests（基於狀態的測試）允許替代解並檢測連帶變化，Thinkingbox 與其互補之處在於強調 policy-conditioned user interaction（受政策約束的使用者互動）、MCP 相容工具會話與完整 execution traces（執行軌跡）。WorkArena++、CRMArena 與 CRMArena-Pro 聚焦企業軟體流程與多輪專業互動，AgentDojo 則關注工具輸出不可信時的安全性；Thinkingbox 的差異化在於把評估重心放在 terminal backend state 與可重複的可靠性指標。至於 MCP-Bench、MCPMark 與 MCP-Atlas 等 MCP 相關基準，Thinkingbox 提供的是經過人工審查的 policy-conditioned workflows，並結合 outcome evaluation 與 failure analysis，而非僅測試工具發現或 CRUD 操作。

然而，Thinkingbox 也有其限制。首先，五個領域雖具代表性，但仍無法涵蓋所有企業場景；其次，simulated user（模擬使用者）的政策與真實人類的變異性之間存在差距；第三，task-specific evaluators 需要大量人工工程，維護與擴充成本不低；第四，20 次重複試驗雖能衡量可靠性，卻也帶來顯著的運算與 API 成本；最後，MCP-centric（以 MCP 為中心）的設計可能不易直接遷移到非 MCP 的企業系統。

#### 可重現性評估

作者已將 Thinkingbox 與 Thinkingbox-bench 一併釋出於 GitHub（https://github.com/microsoft/thinkingbox），這對可重現性是一大加分。釋出內容理應包含 sandbox（沙盒）、orchestrator、task worlds（任務世界）、domain tools 與 executable judges，讓其他研究者能複製 leaderboard evaluation 與 failure analysis。

不過，完整重現仍取決於幾項條件：每個任務後端必須能以 isolated backend sessions 啟動與重置；MCP-compatible tool sessions 需要穩定的伺服器實作；proprietary models 的重現性受限於 API 版本、temperature（溫度）與隨機種子；open-weight models 雖可取得權重，但仍需一致的推論框架與硬體。此外，simulated user policy 若包含隨機性，也必須提供 deterministic seeds（確定性種子）才能讓不同實驗間的軌跡可比較。建議未來釋出時進一步提供 containerized backends（容器化後端）、pinned dependencies（固定版本依賴）、完整 prompts（提示詞）與版本化的 task checks，以降低重現門檻。

#### 未來研究方向

Thinkingbox-bench 所揭示的 reliability gap 為後續研究開闢了多條路徑。第一，方法論上可發展專為穩定性設計的 agent 架構，例如結合 explicit planning（顯式規劃）、self-verification（自我驗證）、rollback（回滾）機制與長期 memory（記憶），以縮小 pass@20 與 pass^20 之間的落差。第二，可探索自動化或半自動化產生 executable checks 的技術，降低 task-specific evaluator 的維護成本。第三，將 Thinkingbox 作為訓練環境，透過 curriculum learning（課程學習）或 reinforcement learning from executable feedback（來自可執行回饋的強化學習）提升模型在 stateful business workflows 上的可靠性。

第四，擴展領域至 healthcare（醫療）、legal（法律）、supply chain（供應鏈）或政府服務，並引入真實使用者研究以驗證 simulated user 的效度。第五，研究 multi-agent coordination（多智慧體協調）與 human-in-the-loop（人機協作）在長期商業流程中的角色。第六，針對政策變異與 adversarial users（對抗性使用者）進行 robustness（穩健性）測試，確保 agent 不會因使用者誘導而違反 domain policies。最後，推動企業工作流程基準的標準化，讓 reliability-oriented metrics（面向可靠性的指標）如 pass^20 成為評估實用 agent 的常規標竿。

## 論文問答

**Q1：Thinkingbox 試圖解決什麼樣的評測缺口？**

A：現有許多智慧體基準測試聚焦於程式碼修復、網頁導航或函式呼叫，這些任務的成功標準相對容易定義為「語法正確」或「可執行」。然而，真實的商業工作流程——例如處理退款、修改訂房或更新保險理賠——是具狀態、多輪且受政策約束的，成功與否取決於終端後端狀態是否正確轉換，而非僅看回應是否合理。Thinkingbox 正是為了填補這個缺口而設計，提供一個可重複使用的沙盒，讓工具、智慧體與模擬使用者在隔離環境中互動，並以可執行檢查驗證最終結果與副作用。

**Q2：為什麼僅憑回應或工具呼叫的正確性，不足以判斷智慧體完成任務？**

A：智慧體可能產生流暢且看似正確的最終回應，同時卻未真正改變後端狀態，或對錯誤的實體進行更新。即使工具呼叫本身語法有效且可執行，也可能發生遺漏效應、額外效應，或違反領域政策的連帶效應。因此，Thinkingbox 強調必須檢查終端後端狀態與對話內容，才能區分「看起來完成」與「真正完成」。

**Q3：在具狀態的商業任務中，「可靠性」為何比「偶爾成功」更重要？**

A：商業任務通常具有不可逆或高影響的副作用，例如錯誤退款或保險理賠狀態被誤改，一次失誤就可能造成實質損失。實驗顯示最強模型在 20 次嘗試中至少成功一次的比例高達 91.12%，但全部 20 次都成功的比例僅 25.25%，顯示成功軌跡雖可發現，卻難以穩定重現。這個發現—可靠性差距——說明評測必須納入重複試驗，才能判斷智慧體是否適合部署於具後果的企業場景。

**Q4：Thinkingbox 的核心架構與運作流程是什麼？**

A：Thinkingbox 是一個可重複使用的沙盒，協調模擬使用者、大型語言模型智慧體、隔離的 MCP 相容工具工作階段、副作用擷取器與可執行評判器。每個任務被定義為初始後端狀態、使用者目標、可用領域工具、模擬使用者政策與一組隱藏的可執行檢查。在多輪互動結束後，系統會檢查終端後端狀態、連帶效應，以及部分任務的最終回應，以判定智慧體是否真正達成目標。

**Q5：Thinkingbox 相較於現有可執行基準，主要創新在哪裡？**

A：它的核心創新在於將「政策約束的多輪對話」、「具狀態工具使用」與「終端狀態結果評估」整合到同一個沙盒中。不同於只檢查工具呼叫是否合法的基準，Thinkingbox 接受多條有效軌跡，同時拒絕錯誤、遺漏或額外的持久狀態轉換。此外，它還對最終回應進行二元評分標準檢核，涵蓋必要揭露事項、機密性與一致性，確保智慧體不只會用工具，也能可靠地完成工作並正確溝通。

**Q6：為什麼 Thinkingbox 要採用隔離的 MCP 相容後端工作階段？**

A：隔離的後端工作階段能確保每個任務在獨立環境中執行，避免任務之間的狀態互相污染，從而提升實驗的可重複性與排行榜評估的公平性。採用 MCP 相容工具工作階段則讓不同領域的工具能以標準化方式暴露給智慧體，降低整合成本。完整的執行軌跡也便於後續進行失敗分析，讓研究者能追蹤智慧體在哪一步偏離了正確狀態轉換。

**Q7：Thinkingbox-bench 涵蓋哪些領域與任務特性？**

A：Thinkingbox-bench 包含 507 個受政策約束的工作流程，橫跨零售／電子商務、旅遊與款待、汽車保險、新銀行內部 IT 支援，以及顧問公司 IT／HR 支援等五個領域。這些任務強調多步驟交易、政策條件下的更新、使用者澄清、紀錄查詢，以及不可逆或高影響的副作用。每個任務都會對終端後端狀態進行可執行檢查，其中 30 個任務還會額外檢查最終回應的必要揭露、機密性與一致性。

**Q8：實驗中的關鍵結果是什麼？反映了什麼問題？**

A：研究團隊評估了 12 個專有與開源權重模型，每個任務重複 20 次，最強模型達到 65.36% 的 pass@1，並在 91.12% 的任務中至少成功一次。然而，全部 20 次嘗試都成功的比例僅有 25.25%，顯示智慧體雖能找到成功軌跡，卻無法穩定重現。這個發現凸顯了「可發現性」與「可靠性」之間的巨大落差，也說明單次通過率並不足以衡量智慧體在具狀態商業任務上的實用價值。

**Q9：作者進行了哪些失敗模式與評估器的分析？**

A：作者進行失敗分析，發現許多未通過的嘗試其實以「乾淨」的方式終止，並且包含看似有效的狀態改變動作，但最終狀態仍不符合任務要求。他們也透過評估器消融實驗，區分「流暢的工具使用」與「可靠的工作完成」，證明僅檢查工具呼叫或對話流暢度會高估智慧體表現。這些分析進一步強調，必須同時檢查錯誤效應、遺漏效應與額外效應，才能準確評估智慧體是否達成目標。

**Q10：Thinkingbox 可應用於哪些實際商業場景？**

A：Thinkingbox 適合評估任何需要改變後端狀態的企業協助流程，例如電商平台的訂單修改與退款、旅館的訂房變更、保險公司的理賠狀態更新，以及新銀行或顧問公司的內部 IT／HR 支援工單處理。這些場景都需要智慧體在與使用者多輪對話中收集遺漏資訊、遵循領域政策、協調相依工具，並產生正確的持久狀態轉換。透過 Thinkingbox，企業可以在部署前測試智慧體是否會造成非預期的連帶效應。

**Q11：若要在產品中部署這類智慧體，Thinkingbox 的設計帶來哪些啟示？**

A：產品團隊應建立隔離的沙盒環境，讓智慧體在不影响真實系統的情況下進行端到端測試。評估指標不能只看單次通過率，而應納入重複試驗的可靠性指標，例如 all-20 success，以確保智慧體在多次執行下仍穩定。此外，最終回應的二元評分標準——包括必要揭露事項、機密性與一致性——提醒產品設計者，智慧體不僅要正確操作工具，還必須以安全且一致的方式與使用者溝通。

**Q12：這項研究對整個智慧體評測領域可能產生什麼影響？**

A：Thinkingbox 將智慧體評測的焦點從「單次工具呼叫是否正確」推進到「多輪狀態任務是否可靠完成」，為後續研究提供了一個可重複使用的互動底層。它公開釋出的沙盒與基準能促進學界與業界在具狀態商業工作流程上的比較與創新。長遠來看，這有助於發展出更穩健的多輪規劃、政策遵循與副作用避免技術，推動智慧體從實驗室走向真實企業應用。

**Q13：Thinkingbox-bench 目前有哪些可能的限制？**

A：雖然論文未詳細列出所有限制，但從設計可推知，507 個任務雖經人工審查，仍無法涵蓋真實世界中所有企業流程的複雜度與變異性。模擬使用者的行為雖能測試政策遵循，但可能無法完全捕捉真人使用者的不可預測性與邊緣案例。此外，目前評估領域集中於五個商業場景，未來若要驗證更廣泛的通用性，仍需擴展到更多產業與更動態的後端系統。

**Q14：從實驗結果看，智慧體最常見的失敗案例是什麼？**

A：許多失敗發生在智慧體已經「乾淨」終止且執行了看似有效的狀態改變動作之後，例如更新了錯誤的紀錄、遺漏必要的確認步驟，或產生了額外的未授權副作用。部分智慧體的最終回應雖然流暢，卻與實際執行結果不一致，甚至洩漏了應受保護的敏感資訊。這些案例顯示，智慧體在狀態追蹤、政策落地與回應一致性方面仍有顯著提升空間。

**Q15：未來可以如何延伸 Thinkingbox 與相關研究？**

A：未來可以將 Thinkingbox 擴展到更多產業領域，並與真實或半真實的 MCP 伺服器整合，以測試智慧體在更動態環境中的表現。研究者可發展專門提升可靠性而非僅提升可發現性的訓練方法，例如透過強化學習讓智慧體學會自我修正與避免連帶效應。此外，結合更強大的驗證機制、更真實的使用者模型，以及跨重試的一致性分析，將有助於縮小發現性與可靠性之間的差距，讓智慧體真正適用於高風險的商業工作流程。

## 實務應用指南

### 適用場景

1. **客戶服務與交易處理**  
   將 Thinkingbox 用於零售、電子商務或旅遊款待業的退換貨、訂單修改、預訂變更等具狀態流程。智慧體必須在多輪對話中確認使用者身分、查詢紀錄、執行退款或改單，並避免連帶影響其他訂單狀態。

2. **保險理賠與核保輔助**  
   應用於汽車保險等場景，讓智慧體根據領域政策收集事故資訊、更新理賠狀態、安排查勘，同時確保最終回應包含必要揭露事項且不洩漏機密資料。

3. **企業內部 IT／HR 服務台**  
   在新銀行、顧問公司或大型企業中，處理帳號開通、權限申請、設備報修、請假或薪資查詢。透過隔離的後端工作階段，驗證智慧體是否正確更新工單狀態，而非僅產生看似合理的回覆。

4. **跨系統業務流程自動化**  
   當單一任務需要協調多個後端系統（例如 CRM、ERP、財務系統）時，Thinkingbox 可作為可重複執行的驗證沙盒，確認智慧體在多次嘗試下都能穩定達成正確的持久狀態轉換。

5. **Agent 上線前的可靠性評測**  
   在正式部署前，利用 Thinkingbox-bench 的 507 個政策約束工作流程與可執行檢查，對專有或開源權重模型進行 pass@1／pass@20 評估，找出「偶爾成功但無法穩定重現」的任務。

### 實作前置條件

- **領域資料與政策文件**  
  需要清晰的業務流程說明、API 規格、資料庫綱要、領域政策（如退款規則、保密要求），以及可轉換為隱藏可執行檢查的期望終端後端狀態。

- **可隔離的後端環境**  
  每個任務需要能獨立重設的後端工作階段，支援 MCP 相容工具呼叫，並能記錄完整執行軌跡與副作用。

- **運算與模型資源**  
  需準備 LLM 推理端點（專有模型 API 或開源權重模型推論環境）、沙盒執行節點，以及足夠資源執行 20 次重複試驗以評估可靠性差距。

- **技術能力**  
  團隊應具備 LLM 智慧體開發、函式呼叫與 MCP 整合、後端服務開發、可執行評判器設計，以及將業務政策轉為二元評分標準的能力。

### 實作步驟建議

1. **將業務流程建模為任務世界**  
   依據論文中的 \(x=(b_0, g, T, U, C)\) 框架，定義初始後端狀態、使用者目標、可用領域工具、模擬使用者政策與隱藏可執行檢查。

2. **建置或改裝領域後端與 MCP 工具**  
   把現有 CRM、ERP、ITSM 等 API 包裝成 MCP 相容工具，確保每次試驗都在隔離的後端工作階段中執行，並能重設狀態。

3. **設計模擬使用者與對話政策**  
   根據真實客服或內部支援對話，建立會主動補充資訊、糾正錯誤或要求確認的模擬使用者，避免智慧體只在過度配合的環境中表現良好。

4. **開發可執行評判器**  
   針對每個任務撰寫檢查終端後端狀態、副作用與最終回應的程式化裁判，特別要檢測遺漏效應、額外效應與錯誤效應。

5. **整合智慧體與編排器**  
   讓 LLM 智慧體在 Thinkingbox 編排循環中運行，支援多輪工具—智慧體—使用者互動，並記錄完整執行軌跡供後續分析。

6. **執行重複試驗與可靠性分析**  
   對每個任務執行多次嘗試，計算 pass@1、pass@20 與 all-20 success，優先處理 pass@20 高但 all-20 低的任務，這些正是「可發現但不可靠」的關鍵缺口。

7. **強化與部署**  
   針對失敗模式加入護欄、人工確認、工具呼叫前檢查與回退機制，並將 Thinkingbox-bench 納入 CI/CD，作為上線前的回歸測試。

### 潛在風險與注意事項

- **pass@20 高不代表真正可靠**  
  論文顯示最強模型 pass@20 可達 91.12%，但 all-20 僅 25.25%。產品決策應以多次穩定成功率為主，而非單次最佳表現。

- **連帶效應難以察覺**  
  智慧體可能完成主要任務，卻同時產生額外效應（如誤改其他客戶資料）。必須透過終端後端狀態檢查與副作用比對來捕捉。

- **模擬使用者與真實使用者落差**  
  模擬使用者的回應模式若過於規律，會高估智慧體表現。建議定期用真實對話資料校準，並保留人工在環確認。

- **不可逆或高風險操作**  
  對於退款、理賠撥付、權限變更等動作，應設計人工核准閘門，或在沙盒中先驗證再於生產環境以唯讀或延遲執行方式上線。

- **評判器過於嚴格或寬鬆**  
  可執行檢查必須接受不同有效軌跡，同時拒絕錯誤狀態。建議與領域專家共同審查二元評分標準，避免過度擬合特定解法。

- **資料機密與隱私**  
  即使使用沙盒，也應避免在評估資料中放入真實個資，並對最終回應進行機密性檢查，防止智慧體洩漏敏感資訊。

### 與其他技術的整合建議

- **現有企業系統 API**  
  透過 MCP 包裝層將 CRM、ERP、HR 系統、ITSM 或保險核心系統的 API 接入 Thinkingbox，讓智慧體在隔離工作階段中呼叫真實介面的模擬版本。

- **RAG 與政策知識庫**  
  將領域政策文件、標準作業程序與常見問答以檢索增強生成方式提供給智慧體，協助其在多輪互動中遵循政策約束。

- **可觀測性與日誌平台**  
  把執行軌跡、工具呼叫、後端狀態變化與評判結果匯出至現有監控系統，支援即時異常偵測與事後稽核。

- **人工在環與審批流程**  
  對高影響工具呼叫加入外部審批閘門，讓 Thinkingbox 不僅是評測環境，也成為人機協作的工作流程編排層。

- **CI/CD 與模型選型**  
  將 Thinkingbox-bench 納入持續整合管線，作為模型升級或提示詞變更前的回歸測試，並比較專有模型與開源權重模型的可靠性差距。
