Lembas 的核心設計理念是將影片檢索增強生成（Video Retrieval-Augmented Generation, Video RAG）重新詮釋為一個**符元分配問題（Token Allocation Problem）**，而非傳統的「檢索後全量處理」流程。這一框架的提出反映了一個關鍵觀察：現有方法在選擇「哪些證據（evidence）」該被處理後，卻忽略了「每個證據該分配多少符元（token）」這個維度的重要性。

**問題建模層面**，Lembas 將每個檢索到的項目（幀 frames 或字幕 subtitles）視為一個具有獨立效用函數的資源消費者，並在共享預算（shared budget）下進行最佳化。其效用函數設計融合了三個關鍵要素：

1. **查詢相關性（Query Relevance）**：衡量該項目與使用者問題的語意匹配程度。
2. **符元邊際效益遞減（Diminishing Returns）**：透過實驗驗證，作者發現下游準確率隨符元數量呈現**凹函數（concave function）**形式的飽和曲線，因此採用**飽和有理函數（saturating rational function）**來建模單一項目內部的符元邊際價值遞減現象。
3. **冗餘感知（Redundancy Awareness）**：當多個相似項目同時獲得符元時，新項目的邊際價值會進一步降低，這反映了「資訊重複」的問題。

**最佳化演算法層面**，由於項目間的符元分配相互依賴（interdependent），組合空間呈指數級爆炸。Lembas 採用**反覆注水演算法（Iterative Water-Filling Algorithm）**來求解此問題。該演算法的關鍵設計在於：

- 將多變數耦合問題分解為一系列**閉式解子問題（closed-form subproblems）**。
- 在每次迭代中，先更新「多樣性感知相關性（diversity-aware relevance）」，再求解注水子問題。
- 具備**可證明的收斂性保證（provable convergence guarantee）**，在 ℓ 次迭代後可達到 O(1/ℓ) 的目標函數間隙（objective gap），這在實務上提供了理論可靠性。

**多輪對話機制（Multi-turn Conversations）**是 Lembas 的另一個重要設計亮點。傳統方法在多輪對話中難以有效復用先前已處理的證據，因為不同查詢可能需要不同的符元數量。Lembas 透過兩個關鍵機制解決此問題：

- **查詢無關的符元排序（Query-independent Token Ranking）**：使後續輪次能夠僅預填（prefill）快取中缺失的符元，大幅降低重複計算成本。
- **注意力精煉（Attention Refinement）**：利用視覺語言模型（Vision-Language Models, VLMs）對快取證據的注意力（attention）來細化相關性，無需額外的 VLM 呼叫即可更新證據評估。

**實作層面**，Lembas 採用**注意力剪枝（attention-based pruning）**來實現具體的符元數量控制，這是一種與模型無關的後處理技術，能夠與各種現有的 RAG 系統無縫整合，體現了其「即插即用（plug-and-play）」的設計哲學。

#### 與現有研究的比較

Lembas 在影片 RAG 領域的定位具有獨特性。從**方法論演進**的角度來看，現有研究可分為三個主要流派：

**第一類：基於嵌入的 RAG（Embedding-based RAG）** 與 **基於圖的 RAG（Graph-based RAG）**——這些方法專注於「檢索什麼（what to retrieve）」，透過語意相似度（semantic similarity）或實體-事件圖譜來選擇證據，但對每個檢索項目採用統一的符元成本。Lembas 的差異化在於它關注「分配多少符元（how many tokens）」，並作為這些檢索器的下游模組運作。

**第二類：幀選擇方法（Frame Selection Methods）**——包括基於檢索啟發式（retrieval heuristics）、學習式策略（learned policies）和代理式搜尋（agentic search）的方法。這些方法決定「處理哪些幀」，但通常對選中的幀採用固定或統一的符元數量。

**第三類：符元壓縮方法（Token Compression Methods）**——透過符元合併（token merging）或剪枝（pruning）來減少視覺冗餘（visual redundancy），但缺乏對「符元邊際價值」的明確建模。

Lembas 的核心優勢在於**統一框架**：它將幀選擇、符元壓縮和符元分配整合到一個最佳化問題中，並提供了理論收斂性保證。相比之下：

- **QuoTA** 採用相關性比例分配（relevance-proportional allocation），但缺乏冗餘感知。
- **AdaAlloc** 使用離散解析度層級（discrete resolution tiers），但受限於預定義規則。
- **代理式預算規劃（Agentic Budget Planning）** 雖然靈活，但缺乏最佳化保證且計算成本較高。

**限制與不足**：

1. **依賴上游檢索器**：Lembas 假設上游 RAG 系統已提供相關的幀和字幕，若檢索階段遺漏關鍵證據，後續的符元分配無法補救。
2. **效用函數的擬合成本**：飽和有理函數的擬合需要對每個項目進行預測，這增加了額外的計算開銷（雖然相對於 VLM 推論成本而言較小）。
3. **多輪對話的注意力精煉假設**：該機制假設 VLM 的注意力能夠可靠反映證據相關性，但對於某些模型或任務類型可能不成立。
4. **基準測試的局限性**：評測主要集中在英文基準（MLVU、LongVideoBench、Video-MME），對於其他語言或文化背景的影片泛化能力有待驗證。

### 實作步驟建議

**階段一：建立基線檢索管線**
1. 整合現有影片 RAG 系統（如基於 CLIP 的幀檢索、字幕向量檢索）
2. 確認能為每個查詢回傳 Top-K 候選幀與字幕片段
3. 評估基線在目標資料集（如 MLVU、LongVideoBench）上的準確率與成本

**階段二：訓練效用模型**
1. 在不同符元數（例如 32、64、128、256 tokens/frame）下評估 VLM 準確率
2. 以凹函數（rational function）擬合每個項目的「符元數—效用」曲線
3. 結合查詢相關性與冗餘感知，定義每個項目的邊際價值函數

**階段三：實作 Token Allocator**
1. 將影片 RAG 形式化為共享預算下的最佳化問題
2. 實作反覆注水演算法（iterative water-filling），每輪更新 diversity-aware 相關性並解閉合解
3. 驗證收斂性（目標函數差距 ≤ ε）並設定迭代上限

**階段四：整合注意力剪枝**
1. 根據分配結果，使用 attention-based pruning 將每幀壓縮至目標符元數
2. 確保剪枝後的視覺符元仍保留關鍵區域的細節

**階段五：支援多輪對話**
1. 實作 query-independent token ranking，使符元排序與查詢解耦
2. 設計增量 prefill 機制，僅補齊快取中缺少的符元
3. 利用 VLM 對快取證據的 attention 精煉後續輪次的相關性

**階段六：部署與監控**
1. 將 Lembas 封裝為 plug-and-play 模組，介接既有 RAG 與 VLM
2. 建立成本與準確率的儀表板，持續追蹤 trade-off
3. 收集失敗案例，定期重訓效用模型

### 潛在風險與注意事項

**風險一：效用模型擬合不準**
- **現象**：凹函數假設在某些項目上不成立（例如二元答案問題只需 1 個關鍵幀）
- **緩解**：保留離散解析度層級作為 fallback，並對低相關性項目設定符元下限

**風險二：注水演算法陷入局部解**
- **現象**：雖然連續鬆弛有全域最佳解，但離散化後可能偏離
- **緩解**：以 O(1/ℓ) 收斂保證設定迭代上限，並在實務上加入隨機重啟

**風險三：多輪 KV-cache 失效**
- **現象**：不同輪次的符元分配差異大，導致快取命中率低
- **緩解**：採用 query-independent token ranking，並設計「最大預填 + 增量補齊」策略

**風險四：字幕與視覺證據權重失衡**
- **現象**：某些查詢主要依賴字幕，某些則依賴視覺細節
- **緩解**：在效用函數中加入模態權重，並允許依查詢類型動態調整

**風險五：評估基準偏誤**
- **現象**：在 MLVU 上提升 7.2 個百分點，但實際業務資料分布不同
- **緩解**：在自家資料上做 A/B 測試，並以「每千次查詢成本」與「準確率」雙指標評估

### 與其他技術的整合建議

**與現有 RAG 系統整合**
Lembas 是 plug-and-play 模組，可直接接在 CLIP-based 幀檢索、字幕向量檢索或 graph-based RAG（如 VideoRAG、VideoAgent）之後，無需修改上游檢索邏輯。建議保留原有 Top-K 檢索作為候選池，再由 Lembas 決定每個項目的符元預算。

**與 VLM 推論引擎整合**
可與 vLLM、SGLang 等高效推論框架搭配。建議將 attention-based pruning 實作為自訂的 token processor，並利用其 KV-cache 管理機制支援多輪復用。

**與影片前處理管線整合**
搭配場景偵測（scene detection）、關鍵幀抽取（keyframe extraction）可減少候選池大小；搭配 ASR 品質過濾可提升字幕證據的效用。

**與成本監控系統整合**
透過 OpenRouter 等 API 計價標準，將「每千次查詢成本」納入監控指標。建議設定成本上限自動觸發預算縮減機制。

**與多模態快取系統整合**
若已部署向量資料庫（如 Milvus、Qdrant），可將 Lembas 的 token ranking 結果預先寫入，作為下一輪的快速檢索索引。
