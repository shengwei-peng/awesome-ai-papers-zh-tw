## 摘要翻譯

終端代理透過在終端中執行命令，解決軟體工程與科學研究中的任務。透過強化學習 (RL) 訓練它們需要多樣化且可驗證的環境，但這些環境目前仍主要由人類研究人員設計，因此其供應的增長僅能隨研究人員的工作速度推進。我們提出 AutoEnvScaling，將環境設計視為一項終端任務，並利用代理來自動化資料飛輪。提議者代理根據正在訓練的求解者的軌跡建構新的 RL 環境，而求解者的新軌跡則引導下一輪。透過將環境生成轉化為終端任務，相較於僅提示詞生成，AutoEnvScaling 將有效環境率最多提升 25 倍，同時將每個有效環境成本降低最多 75%。我們展示了在 GPT-5.6-sol 生成的 AutoEnvScaling 環境上訓練 Qwen3.5-35B-A3B，可使其 Terminal-Bench 2.1 分數比匹配的 Tmax 基準提升 4.3 分。AutoEnvScaling 更宏大的目標是實現遞迴自我改進 (RSI)：透過使環境生成與求解皆成為終端任務，讓單一模型在兩個角色中共同演化。結果顯示，Qwen3.6-35B-A3B 同時扮演兩個角色，在 Terminal-Bench 2.1 上提升 12.2 分，並將其 Terminal-Bench 4.0 分數從 1.6 提升至 3.2。該流水線亦可跨代理式任務領域進行泛化，為軟體工程、電腦使用、專業工作及 GPU 核心程式設計生成環境。總體而言，這些結果展示了朝向代理自主建構訓練環境、降低對人類依賴這條路徑的可能性，並朝 RSI 邁出了核心一步。

### 核心貢獻（3～5點）
- **方法創新**：提出 AutoEnvScaling，將環境設計視為終端任務，由提議者代理根據求解者的軌跡自動化建構 RL 訓練環境，使資料飛輪得以自我驅動。
- **效率提升**：相較於僅提示詞生成，AutoEnvScaling 將有效環境率最多提升 25 倍，並將每個有效環境成本降低最多 75%。
- **訓練成效驗證**：在 GPT-5.6-sol 生成的 AutoEnvScaling 環境上訓練 Qwen3.5-35B-A3B，使其 Terminal-Bench 2.1 分數較匹配的 Tmax 基準提升 4.3 分。
- **遞迴自我改進 (RSI) 實證**：Qwen3.6-35B-A3B 同時扮演提議者與求解者雙角色，於 Terminal-Bench 2.1 提升 12.2 分，並將 Terminal-Bench 4.0 分數從 1.6 提升至 3.2。
- **跨領域泛化**：該流水線可推廣至軟體工程、電腦使用、專業工作及 GPU 核心程式設計等代理式任務領域，展現廣泛適用性。

### 適合對象
從事強化學習、終端代理、自動化環境生成及遞迴自我改進研究的 AI 研究者與工程師；關注代理能力擴展、訓練資料自動化與自主 AI 系統發展的學術界與產業界從業者；以及對 Terminal-Bench 等代理基準測試感興趣的 LLM 應用研究者。

## 深度分析

#### 方法論解析

AutoEnvScaling 的核心洞見在於將「環境設計」本身重新定位為一個終端任務 (terminal task)，而非傳統上由人類研究者執行的離線流程。這種重新定位帶來三個層面的方法論突破：

**1. 雙代理閉環架構**

系統由兩個角色構成：提議者代理 (proposer agent) 與求解者 (solver)。提議者在沙盒 (sandbox) 中運作，配備程式碼工具框架 (coding harness)、求解者軌跡 (solver rollouts)、工作區 (workspace) 與網路存取 (web access)，能夠建構完整的 Harbor 訓練環境——包含指令、執行環境、參考解答與測試。提議者可啟動子沙盒 (child sandboxes) 來建構與測試任務，這種遞迴沙盒設計模擬了人類研究者「先寫原型、再驗證」的迭代流程。

**2. 求解者引導的資料飛輪 (data flywheel)**

與靜態環境池不同，AutoEnvScaling 的訓練池會隨求解者能力演進而動態調整。每個新環境在被納入訓練池前，必須通過兩道關卡：驗證 (validation) 與校準 (calibration)。校準步驟尤為關鍵——它確保新環境對當前求解者具有適當的難度（既非太簡單也非太困難），這呼應了課程學習 (curriculum learning) 與無監督環境設計 (unsupervised environment design) 的理論基礎。求解者完成新一輪訓練後產生新軌跡，這些軌跡反過來指引提議者下一輪的環境建構方向，形成自我強化的循環。

**3. 遞迴自我改進 (RSI) 的實現路徑**

論文的第三個貢獻在於展示單一策略可同時擔任兩個角色。Qwen3.6-35B-A3B 同時作為提議者與求解者，透過權重訓練 (weights) 而非僅工具框架優化 (harness optimization) 來更新提議者能力。這種設計的關鍵在於穩定性：若提議者產生過於困難的環境，求解者將無法從中學習；若過於簡單，則無訓練訊號。論文聲稱訓練提議者能維持此迴圈穩定，使兩角色共同演化 (co-evolve)。

**與既有方法的本質差異**

從 Table 1 的分類可看出，AutoEnvScaling 是唯一同時具備「外部提議者 + 自身提議者 + 工具框架優化 + 權重訓練」四個特性的方法。Endless Terminals、TermiGen、Tmax 等流水線合成方法僅使用提示詞 (prompt) 與人類定義的策略；AutoData 雖使用工具框架但僅生成問答資料而非完整環境；SPADE 雖訓練共享模型但僅限於 Gym 風格環境。AutoEnvScaling 的獨特之處在於將「建構完整可執行環境」這一高度複雜的任務交由代理自主完成。

#### 實驗數據解讀

**1. 環境生成效率指標**

相較於僅提示詞生成 (prompt-only generation)，AutoEnvScaling 將有效環境率 (valid-environment rate) 提升最高 25 倍，並將每個有效環境成本 (cost per valid environment) 降低最高 75%。這兩個指標的數量級改善具有重要意涵：它意味著代理不僅能產生更多可用環境，且每個環境的邊際成本大幅下降。這對於年支出據報超過 10 億美元的 RL 環境產業投資具有直接經濟影響。

**2. 跨模型泛化能力**

實驗橫跨八個前沿模型進行比較，包括 GPT-5.6-sol 與 Claude Opus 5 作為提議者，Qwen3.5-9B 與 Qwen3.5-35B-A3B 作為求解者。這種跨模型設計驗證了方法不依賴特定模型的特性。值得注意的是，GPT-5.6-sol 與 Claude Opus 5 設計的環境能為 Qwen 系列模型帶來最高 7.4 點（9B）與 4.3 點（35B-A3B）的 Terminal-Bench 2.1 提升，顯示強模型設計的環境對弱模型同樣有效。

**3. 求解者回饋的必要性**

論文明確指出「沒有求解者回饋時增益會縮小」，這是一個關鍵的消融實驗結論。它驗證了資料飛wheel的核心假設：環境生成必須與求解者當前能力耦合，否則會退化为靜態池的流水線合成方法。

**4. 遞迴自我改進的量化成果**

Qwen3.6-35B-A3B 同時擔任兩角色時，在 Terminal-Bench 2.1 上相較冷啟動 (Cold-Start) 檢查點提升 12.2 點，並將 Terminal-Bench 4.0 從 1.6 提升至 3.2（翻倍）。Terminal-Bench 4.0 的提升尤具意義，因為該基準通常代表更困難、未充分探索的任務，顯示 RSI 不僅在已知任務上有效，還能拓展能力邊界。

**5. 領域泛化性**

方法在軟體工程、電腦使用、專業工作、GPU 核心程式設計四個領域均能生成環境，證明其不僅限於特定任務類型。GPU 核心程式設計的納入尤其值得注意，因為這是一個需要深度專業知識且傳統上高度依賴人類專家的領域。

#### 與現有研究的比較

**定位優勢**

AutoEnvScaling 在環境生成方法譜系中佔據獨特位置。相較於 Endless Terminals [8]、TermiGen [67]、Tmax [13] 等流水線合成方法，它擺脫了預定義流水線 (pre-defined pipeline) 的束縛；相較於 Terminal-World [5]、RST [20]、Environment Evolution [7]、Terminal-Uni [49]、T1 [54] 等反饋驅動方法，它將反饋使用方式從人工設計改為代理自主決策；相較於 AutoData [17] 與 EnvHarness [12] 等代理式方法，它能建構全新環境而非僅修改現有環境或生成 QA 資料；相較於 SPADE [23] 等自我對弈方法，它不限於 Gym 風格環境且支援更廣泛的代理式任務領域。

**理論基礎的銜接**

方法論上，AutoEnvScaling 與課程學習 [3, 6]、無監督環境設計 [34]、提議者-求解者自我對弈 [22, 51, 65] 等理論框架深度銜接。Self-Challenging agents [66] 與 SSR [48] 等近期工作也探索了代理自主生成任務，但 AutoEnvScaling 的差異在於：(1) 環境是完整的 Harbor 任務而非簡單的程式碼注入；(2) 提議者本身透過 RL 訓練而非僅提示詞工程；(3) 求解者回饋直接驅動下一輪環境設計。

**侷限性與未解問題**

儘管成果顯著，仍有幾項侷限值得關注。首先，論文中 25 倍有效環境率提升與 75% 成本降低是「最高」值而非平均值，實際分佈與統計顯著性需進一步檢視。其次，RSI 實驗僅展示單一模型（Qwen3.6-35B-A3B）的結果，不同規模模型是否能維持迴圈穩定性仍未知。再者，雖然方法聲稱支援四個領域，但各領域的環境品質與訓練效果是否均衡，論文中未提供細粒度分析。最後，遞迴自我改進的長期穩定性——例如經過數十輪後是否會出現環境品質退化或模式崩潰——是 RSI 路線的核心風險，論文未充分探討。

#### 未來研究方向

**1. RSI 穩定性與長期演化**

最關鍵的後續研究方向是 RSI 迴圈的長期穩定性。當前提議者與求解者共同演化僅展示有限輪次的結果，未來工作應探討：(a) 數十至數百輪後是否出現環境品質退化；(b) 提議者是否會過度擬合求解者弱點而產生「對抗性」環境；(c) 引入多樣性機制（如環境熵獎勵）是否能緩解模式崩潰。

**2. 提議者架構的多樣化**

當前提議者是單一代理，未來可探索：(a) 多提議者集成，不同提議者專精不同領域或難度區間；(b) 階層式提議者，高層提議者決定領域分佈，低層提議者執行具體建構；(c) 提議者與人類研究者的協作模式，人類提供高層指引而代理處理細節。

**3. 跨模態環境生成**

目前環境主要限於命令列與程式碼任務，未來可擴展至：(a) 視覺-語言環境，涵蓋 GUI 操作與多模態推理；(b) 機器人與具身環境，雖然這需要更複雜的模擬器整合；(c) 多代理環境，其中環境本身涉及多個互動代理。

**4. 環境品質的理論分析**

目前缺乏對「什麼構成高品質訓練環境」的理論理解。未來工作可：(a) 建立環境複雜度、可學習性、新穎性等形式化指標；(b) 分析環境分佈對最終策略泛化能力的影響；(c) 借鑒資訊理論與 PAC 學習框架量化環境資訊含量。

**5. 安全與對齊考量**

RSI 路線引發重要的安全問題：若代理能自主設計訓練環境，是否可能在過程中產生有害環境或繞過人類監督？未來工作應：(a) 設計環境審核機制，確保自動生成的環境符合安全規範；(b) 研究提議者的價值對齊，確保其設計目標與人類意圖一致；(c) 建立「停止開關」以在環境品質異常時介入。

**6. 效率與可持續性**

雖然每個有效環境成本降低 75%，但 RSI 路線的總計算成本仍可能很高。未來應：(a) 探索提議者蒸餾，將大型提議者能力壓縮至小型模型；(b) 研究環境重用機制，避免重複生成相似環境；(c) 結合主動學習，主動識別最需要新環境的求解者能力缺口。

**7. 從環境生成到資料生成**

AutoEnvScaling 的核心思想——「將生成任務本身作為代理任務」——可推廣至更廣泛的資料生成場景，包括：(a) 監督式微調資料的自動生成；(b) 偏好資料的合成；(c) 工具使用軌跡的自動化建構。這可能催生一個統一的自演化訓練生態系統。

## 論文問答

**Q1：AutoEnvScaling 這篇論文要解決的核心問題是什麼？為什麼這個問題在當前 AI 代理研究中特別重要？**
A：這篇論文要解決的核心問題是「訓練環境供給瓶頸」——目前強化學習（RL）訓練終端代理所需的環境幾乎全部由人類研究者設計，導致供給速度受限於人力。這個問題之所以重要，是因為終端代理已廣泛應用於軟體工程、科學研究、資料分析與網路安全等領域，而 RL 已成為提升代理能力的主要方法；當代理能力提升後，原本有用的環境會失去訓練價值，研究者必須不斷重新診斷代理弱點並設計新環境，形成一個高度依賴人力的循環。論文中提到，業界每年在 RL 環境上的投入據報導已超過 10 億美元，凸顯此瓶頸已成為產業級別的關鍵問題。

**Q2：現有的環境生成方法（如流水線合成、反饋驅動方法、代理式方法、自我對弈）各自有什麼根本性的限制？**
A：這四類方法共同的限制是「研究者預先固定了環境生成的方式」。具體而言，流水線合成（如 Tmax、Endless Terminals）透過預定義的領域分類法或固定生成步驟來擴展環境，但這些環境池在訓練前就已固定，無法隨代理進步而調整；反饋驅動方法（如 Terminal-World、SETA、RST）雖然加入了反饋迴圈，但如何使用反饋仍由人工設計，缺乏自主性；代理式方法（如 AutoData、EnvHarness）雖將工作交給編碼代理，但前者僅生成問答資料、後者僅修改既有環境包裝，皆無法從零建構新環境；自我對弈方法（如 SPADE）雖讓提議者隨求解者進步而生成更難任務，但提議者仍透過固定流水線生成任務，本質上仍是流水線合成的延伸。

**Q3：為什麼「將環境設計視為終端任務」這個觀點轉換如此關鍵？它如何改變整個研究範式？**
A：這個觀點轉換之所以關鍵，是因為它讓環境設計變成了終端代理「天生擅長的事」——寫程式、除錯、執行指令——而非需要特殊工具鏈或人工介入的獨立流程。透過讓提議者代理在沙盒中讀取求解者軌跡、決定要建構什麼、撰寫並測試完整環境，整個研究人員的工作流程被端到端地自動化。這不僅消除了人類瓶頸，更開啟了「遞迴自我改進（RSI）」的可能性：同一個模型可以同時擔任提議者與求解者，設計自己的訓練環境並從中學習，形成真正的共同演化閉環。

**Q4：AutoEnvScaling 的核心方法架構是什麼？提議者代理與求解者代理如何互動形成資料飛輪？**
A：AutoEnvScaling 的核心架構包含兩個角色：提議者代理（proposer）與求解者代理（solver）。提議者代理在配備編碼工具框架、求解者軌跡、工作區與網路存取的沙盒中運作，能啟動子沙盒來建構並測試任務，最終產出完整的 Harbor 訓練環境（包含指令、執行環境、參考解答與測試）。每個環境在進入訓練池前都會被驗證並依當前求解者能力校準難度；求解者接著在通過的環境上以驗證器獎勵進行 RL 訓練，其新產生的軌跡又會引導下一輪環境生成，形成一個不斷演化的資料飛輪。

**Q5：AutoEnvScaling 與既有方法相比，最關鍵的創新點是什麼？**
A：最關鍵的創新點在於「提議者本身也會學習」——如表 1 所示，AutoEnvScaling 是唯一同時支援外部與自身提議者來源、且提議者可透過工具框架與權重訓練兩種方式進行優化的方法。具體而言，提議者不僅能透過工具框架優化（如 SPADE 般使用記憶體）來改進，還能透過權重訓練真正進化；資料來源涵蓋語料庫、軌跡、記憶體與網路存取，遠比既有方法豐富。這意味著提議者會隨著求解者進步而調整其環境生成策略，使訓練池真正隨代理能力動態演化，而非預先生成後固定使用。

**Q6：在設計 AutoEnvScaling 時，有哪些重要的設計選擇？為什麼選擇將環境設計轉為終端任務而非其他形式？**
A：最重要的設計選擇是「讓提議者代理在沙盒中端到端執行研究人員的工作流程」，而非預先定義生成步驟或固定反饋使用方式。這樣的選擇是因為終端代理天生擅長寫程式、除錯與執行指令，而環境設計本質上就是這些操作的組合；將其包裝為終端任務後，代理可靈活決定要建構什麼、如何測試、如何根據失敗除錯。此外，設計中還包含「環境校準」機制——每個環境都會依當前求解者的通過率調整難度，確保訓練池中的環境對求解者而言既非太簡單也非太難，這是動態課程學習的具體實現。

**Q7：AutoEnvScaling 在實驗中使用了哪些基準測試？為什麼選擇這些特定的評估方式？**
A：實驗主要使用 Terminal-Bench 2.1 與 Terminal-Bench 4.0 作為評估基準。Terminal-Bench 2.1 是較成熟的終端代理基準，能穩定衡量代理在命令列環境中的綜合能力；Terminal-Bench 4.0 則是更具挑戰性的版本，用於驗證方法的泛化效果。選擇這些基準是因為它們直接對應終端代理的核心能力，且能與 Tmax 等既有方法的基準線進行公平比較。此外，論文中也展示該流程可泛化至軟體工程、電腦使用、專業工作與 GPU 核心程式設計等代理式任務領域，顯示其不僅限於單一基準。

**Q8：AutoEnvScaling 的關鍵實驗結果有哪些？這些數字具體說明了什麼？**
A：關鍵結果包含三個層面：第一，相較於僅提示詞生成，有效環境率提升最高達 25 倍，每個有效環境成本降低最高達 75%；第二，使用 GPT-5.6-sol 與 Claude Opus 5 設計的環境訓練 Qwen3.5-9B 與 Qwen3.5-35B-A3B，在 Terminal-Bench 2.1 上分別提升最高 7.4 與 4.3 分，超越靜態 Tmax 環境池；第三，當 Qwen3.6-35B-A3B 同時擔任提議者與求解者時，Terminal-Bench 2.1 提升 12.2 分（相較於冷啟動檢查點），Terminal-Bench 4.0 從 1.6 提升至 3.2。這些數字說明：(1) 提議者代理的設計大幅提升環境生成效率；(2) 求解者引導的環境比靜態池更能提升代理能力；(3) 單一模型可同時勝任兩個角色並實現遞迴自我改進。

**Q9：論文中進行了哪些消融實驗？這些消融揭示了哪些關鍵設計的必要性？**
A：論文中明確提到一個關鍵消融：「沒有求解者反饋時，效能提升會縮小」。這揭示了求解者軌跡作為提議者輸入的重要性——若提議者無法讀取求解者的失敗模式與弱點，就無法針對性地設計能填補能力空缺的環境。此外，論文中也區分了「外部提議者」（如 GPT-5.6-sol）與「自身提議者」（如 Qwen3.6-35B-A3B 同時擔任兩種角色）的設定，並比較了工具框架優化與權重訓練兩種提議者更新方式，這些比較顯示權重訓練（即真正訓練提議者）是實現穩定遞迴自我改進的關鍵。

**Q10：AutoEnvScaling 在實際應用上有哪些具體場景？哪些產業或研究領域會最先受益？**
A：實際應用場景相當廣泛：(1) 軟體工程領域——代理可自動產生程式碼修復、重構、測試案例等訓練環境；(2) 電腦使用領域——可生成 GUI 操作、檔案管理等工作流環境；(3) 專業工作領域——如資料分析、報告生成等辦公自動化任務；(4) GPU 核心程式設計——可建構高效能計算的優化任務。最先受益的會是高度依賴 RL 訓練的 AI 公司（特別是程式碼助手、自動化代理開發商）、雲端運算供應商（因 GPU 核心程式設計環境可自動化生成），以及學術研究中需要大量客製化環境的團隊。

**Q11：從產品化角度來看，AutoEnvScaling 帶來哪些實質的成本與效率優勢？**
A：從產品化角度，AutoEnvScaling 帶來三項實質優勢：(1) 成本降低——每個有效環境成本最高降低 75%，這對每年在 RL 環境上投入數億至數十億美元的公司而言意義重大；(2) 環境品質提升——有效環境率提升最高 25 倍意味著同樣的運算資源可產生更多可用訓練資料；(3) 持續改進能力——資料飛輪使訓練池隨代理進步動態調整，無需人工重新診斷弱點並設計環境，長期運維成本大幅降低。這些優勢使企業能以更低的前期投入建立可自我改進的代理訓練流程。

**Q12：AutoEnvScaling 對整個 AI 代理研究領域會產生什麼長遠影響？**
A：長遠影響主要體現在三個層面：(1) 降低研究門檻——過去只有大型實驗室能負擔環境建構成本，未來中小團隊也能透過代理自動產生高品質訓練環境；(2) 加速 RSI 研究——AutoEnvScaling 證明了單一模型可同時擔任提議者與求解者並穩定共同演化，為遞迴自我改進提供了具體實證路徑；(3) 改變研究範式——從「人類設計環境、代理學習」轉向「代理設計環境、代理學習」，這可能成為未來代理訓練的標準範式，並促使更多研究聚焦於代理的元學習與自我演化能力。

**Q13：AutoEnvScaling 存在哪些已承認的限制？**
A：論文中承認的限制主要包含：(1) 提議者代理本身的品質會限制環境品質——若提議者能力不足，產生的環境可能無法有效訓練求解者；(2) 自身提議者設定（即同一模型同時擔任兩種角色）需要仔細穩定化，否則可能出現提議者與求解者能力不匹配的問題；(3) 雖然方法泛化至多個領域，但每個領域的環境品質仍受該領域基準成熟度影響——例如 Terminal-Bench 4.0 雖有提升但絕對分數仍偏低（從 1.6 到 3.2），顯示在更困難的基準上仍有改進空間。

**Q14：AutoEnvScaling 在哪些情況下可能會失敗？有哪些潛在的失敗模式？**
A：潛在的失敗模式包括：(1) 提議者陷入「局部最優」——若提議者過度依賴求解者當前軌跡，可能只生成求解者已會的環境變體，無法真正拓展能力邊界；(2) 環境校準失靈——若求解者能力快速變化，校準過的環境可能迅速過時或過難，導致訓練訊號品質下降；(3) 自身提議者設定下的「能力鎖定」——若提議者與求解者共享權重，可能出現兩者共同陷入某種風格而無法突破；(4) 領域泛化失敗——在軟體工程等成熟領域表現良好，但在缺乏明確驗證標準的新興領域，環境品質可能難以保證。

**Q15：基於 AutoEnvScaling 的成果，未來有哪些值得探索的研究方向？**
A：未來值得探索的方向包含：(1) 更強的 RSI 機制——目前單一模型的共同演化已實現 12.2 分提升，未來可探索多模型協作式 RSI 或更長期的演化穩定性；(2) 跨領域遷移——將 AutoEnvScaling 從終端任務擴展至機器人、對話代理、多模態代理等更廣泛的代理類型；(3) 提議者品質評估——建立專門衡量「環境設計能力」的基準，使提議者訓練更可衡量；(4) 安全性與對齊——當代理能自主設計訓練環境時，如何確保生成的環境不會引入偏誤、安全漏洞或不良行為，是至關重要的研究方向；(5) 理論分析——理解資料飛輪的收斂性、穩定性與樣本效率，將有助於將此方法從經驗成果轉化為可預測的工程實踐。

### 實作前置條件

**資料前置條件**
- **種子任務集（Seed Tasks）**：至少數百到數千個具備「指令、執行環境、參考解法、驗證測試」四要素的可驗證任務（Harbor 格式），可從既有基準（Terminal-Bench、Tmax）匯入或從內部程式碼倉庫重構。
- **求解者軌跡資料庫**：儲存求解者每次 rollouts 的完整記錄，包含指令序列、輸出、耗時、錯誤訊息，這是 proposer 判斷「下一輪該建什麼」的關鍵輸入。
- **領域知識文件**：API 文件、技術規範、coding style guide 等，供 proposer 在沙盒中透過 web access 查閱。

**運算前置條件**
- **沙盒基礎設施**：可隔離執行程式碼的容器環境（Docker/Podman），並支援「子沙盒」（child sandboxes）以平行測試候選任務。
- **前沿模型 API 配額**：作為 proposer 的 GPT-5.6-sol、Claude Opus 5 等模型需要足夠的 token 配額；論文顯示 proposer 階段成本可佔整體訓練成本相當比例。
- **RL 訓練框架**：支援 verifier reward 的 RL 框架（如 verl、OpenRLHF、Tunix），以及分散式訓練所需的 GPU 叢集（Qwen3.5-35B-A3B 等 MoE 模型通常需要 8×H100 等級的節點）。
- **可擴展的任務儲存與版本控制**：每輪產生的環境需可追溯、可回滾，並標記其對應的求解者版本。

**技能前置條件**
- **RL 與 LLM 訓練經驗**：熟悉 PPO/GRPO 等演算法、reward shaping、KL 約束。
- **代理工程能力**：能搭建 terminal agent 的工具呼叫迴圈、處理 sandbox 隔離與資源限制。
- **軟體工程能力**：熟悉容器化、CI/CD、測試自動化，因為 proposer 本身就是在做「寫程式並除錯」的工作。
- **評估設計能力**：能設計 verifier 來區分任務通過/失敗，並校準任務難度（避免過難或過易）。

### 實作步驟建議

**步驟一：建立最小可行環境生成管線（MVP Pipeline）**
- 從 Terminal-Bench 2.1 或 Tmax 匯入約 100 個種子任務作為 cold-start 訓練集。
- 部署一個 baseline solver（例如 Qwen3.5-9B + 標準 terminal harness）。
- 收集 solver 在這些任務上的 rollouts，建立軌跡資料庫。

**步驟二：搭建 proposer 沙盒與工具框架**
- 為 proposer 配備：sandbox 執行權限、coding harness（檔案編輯、shell 執行、測試執行）、web access（用於查文件）、子沙盒啟動能力。
- 採用 Harbor 框架的任務格式（instruction + environment + reference solution + tests）作為產出標準。
- 設定 proposer 的 system prompt，明確「讀 rollouts → 診斷弱點 → 設計任務 → 寫程式碼 → 跑測試 → 驗證」的端到端工作流程。

**步驟三：實作驗證與難度校準機制**
- 每個 proposer 產出的候選環境必須通過「雙重驗證」：(1) reference solution 能通過測試；(2) 當前 solver 在該環境上通過率落在目標區間（論文建議約 30%–70%，避免過難或過易）。
- 計算 valid-environment rate 與 cost per valid environment 兩個關鍵指標，作為 proposer 改進的依據。

**步驟四：啟動資料飛輪（Data Flywheel）**
- 訓練一輪 solver → 收集新 rollouts → proposer 根據新 rollouts 產生下一批環境 → 合併新舊環境訓練下一輪 solver。
- 每輪保留「環境版本 ↔ solver 版本」的對應關係，便於 ablation 與回溯。

**步驟五：導入 proposer 自我改進機制**
- **Harness 優化**：固定 proposer 權重，僅透過 prompt 迭代、工具配置調整來提升 proposer 表現（門檻較低，建議先做）。
- **權重訓練**：當 harness 優化遇到瓶頸，再訓練 proposer 的權重（論文顯示 Qwen3.6-35B-A3B 同時擔任 proposer 與 solver 可達 12.2 點提升）。
- 注意 RSI 的穩定性風險，需設定 KL 約束與環境品質下限。

**步驟六：推廣至多個代理式任務領域**
- 將同一 proposer 框架套用至軟體工程、電腦使用、專業工作、GPU kernel 等領域，僅替換領域特定的工具與種子任務。
- 建立跨領域的環境品質基準，確保 proposer 不會在某一領域過擬合。

**步驟七：建立監控與治理機制**
- 監控 proposer 產出環境的多樣性（避免模式崩塌）、難度分布漂移、成本趨勢。
- 設定人類審查抽樣比例（例如 5%–10% 的新環境需人工 review），兼顧自動化與品質保證。

---

### 潛在風險與注意事項

**風險一：模式崩塌（Mode Collapse）與環境多樣性下降**
- *現象*：proposer 傾向產生與現有環境相似的任務，導致訓練分布過窄，solver 過擬合特定模式。
- *緩解*：(1) 在 proposer reward 中加入「與既有環境的相似度懲罰項」；(2) 定期從外部基準（如 Terminal-Bench）注入多樣性種子；(3) 監控任務 embedding 的 t-SNE 分布，確保覆蓋率。

**風險二：驗證器漏洞（Verifier Hacking）**
- *現象*：proposer 可能學會產出「solver 容易僥倖通過但實際無訓練價值」的環境（例如測試過於寬鬆）。
- *緩解*：(1) 採用多樣化測試類型（unit test、property-based test、oracle check）；(2) 對每個新環境跑 reference solution 與多個 baseline solver，交叉驗證；(3) 定期人工 audit。

**風險三：RSI 訓練不穩定**
- *現象*：proposer 與 solver 共同訓練時，可能出現「環境品質下降 → solver 退化 → proposer 更難判斷弱點」的負向循環。
- *緩解*：(1) 設定 proposer 與 solver 的更新頻率錯開（例如每 2 輪 solver 更新才更新 1 次 proposer）；(2) 保留 frozen 的「品質錨點」環境集，定期回測；(3) 嚴格的 KL 約束與 reward clipping。

**風險四：成本失控**
- *現象*：proposer 階段的 API 成本（GPT-5.6-sol 等前沿模型）可能遠超訓練本身。
- *緩解*：(1) 設定每輪環境生成的預算上限；(2) 採用 cascade 策略：先用便宜模型產生候選，再用前沿模型驗證；(3) 監控 cost per valid environment，目標維持在論文的 75% 降幅水準。

**風險五：領域遷移失敗**
- *現象*：在軟體工程有效的 proposer 設定未必適用於 GPU kernel 或專業工作。
- *緩解*：(1) 每個領域保留獨立的 proposer prompt 與工具配置；(2) 領域特定的 verifier 設計；(3) 小規模 pilot 驗證後再擴展。

**風險六：對人類研究人員的依賴仍存在**
- *現象*：雖然 proposer 自動化了環境生成，但 reward 設計、verifier 標準、評估指標仍需人類定義。
- *緩解*：明確劃分「自動化邊界」與「人類介入邊界」，將人類精力集中在高層次的目標設定與品質把關，而非逐個任務設計。

### 與其他技術的整合建議

**與既有 RL 訓練框架整合**
- AutoEnvScaling 的環境產出可直接餵入 verl、OpenRLHF、Tunix 等支援 verifier reward 的 RL 框架，無需修改訓練主迴圈。
- 建議將「環境生成」封裝為獨立的 microservice，透過佇列（如 RabbitMQ、Celery）與訓練 pipeline 解耦，方便水平擴展 proposer 沙盒。

**與程式碼代理框架整合**
- 終端代理的底層可採用 OpenHands、SWE-Agent、Aider 等開源框架，AutoEnvScaling 只需在其之上加入「proposer 模式」即可。
- 若企業已有自製代理，可將 proposer 視為「同一 agent 的另一個 system prompt 切換」，降低維護成本。

**與 MLOps / LLMOps 平台整合**
- 將環境版本、solver 版本、rollouts、reward 曲線全部納入 MLflow 或 Weights & Biases 的追蹤，方便跨輪次比較。
- 環境本身可存入物件儲存（如 S3、MinIO），並用 DVC 或 Git LFS 進行版本控管。

**與人類回饋機制（RLHF / RLAIF）整合**
- 雖然 AutoEnvScaling 主要靠 verifier reward，但對於難以自動驗證的任務（如「程式碼可讀性」），可加入 AI Feedback 或人類標註作為輔助 reward。
- proposer 本身也可接受人類偏好資料微調，提升其設計品質。

**與知識庫與企業內部系統整合**
- proposer 的 web access 可指向企業內部 Confluence、Notion、API 文件站，而非開放網路，提升任務的領域貼合度。
- 與 issue tracker（Jira、Linear）整合，讓 proposer 自動從歷史 ticket 萃取任務候選。

**與評估基準整合**
- 持續在 Terminal-Bench 2.1/4.0 等公開基準上回測，避免「過擬合自家環境分布」而失去泛化能力。
- 建立內部評估集（held-out tasks），模擬真實部署環境的分布。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「強化學習需要大量可驗證的環境」這個核心痛點，再把 AutoEnvScaling 想成「讓 AI 自己出題目給自己做」的概念。可以跳過技術細節，專注在 §1 的問題動機、Figure 2 的資料飛輪示意、以及「遞迴自我改進」這個願景，理解為何這項研究被視為朝向 AGI 的一步。

**給 AI 工程師**：重點閱讀 §1 後半段的 proposer 架構（sandbox + coding harness + web access + child sandboxes）、Table 1 的方法比較、以及實驗章節中 valid-environment rate 與 cost per valid environment 的數據。實作時可先從「prompt-only baseline」做起，再逐步加入 solver rollouts 與 harness 優化，最後才考慮 proposer 權重訓練。

**給研究者**：重點關注 §2 的相關工作分類（pipeline synthesis / feedback-driven / agentic / self-play）、RSI 的穩定性分析、以及 proposer 與 solver 共同訓練時的 KL 約束與更新頻率設計。論文的 ablation 與跨領域泛化實驗是值得深入挖掘的方向，特別是「為何 GPT-5.6-sol 設計的環境能讓 Qwen3.5-35B-A3B 提升 4.3 點」這個跨模型知識遷移現象。

**給產品經理**：把 AutoEnvScaling 視為「降低 RL 訓練資料成本」的基礎設施投資。關鍵商業指標是：(1) 每個有效環境的成本下降幅度（論文達 75%）；(2) 訓練出的代理在真實任務上的表現提升（Terminal-Bench 4.0 從 1.6 提升到 3.2）；(3) 跨領域可擴展性（同一套框架支援軟體工程、GPU kernel 等）。在評估導入時，應優先考慮「內部已有大量程式碼軌跡與任務資料」的場景，因為這是 AutoEnvScaling 發揮槓桿效應最大的地方。
