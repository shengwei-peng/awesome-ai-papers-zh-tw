# SkillSpec：意圖遮罩式規格推理以確保代理技能正確性

**原文標題：** SkillSpec: Intent-Masked Specification Reasoning for Agent Skill Correctness  
**作者：** Yizhuo Zhang、Bo Kang、Yi Yang 等 6 位作者

## ⚡ TL;DR

本文解決代理技能中語義不一致與意圖衝突等難以偵測的靜默缺陷問題。
提出 SkillSpec，以 Hoare 風格規格推理結合意圖遮罩與沙箱驗證，檢查技能正確性。
在 515 個真實技能中發現 763 個已確認缺陷，精確率達 61.2%，顯示規格推理可有效把關品質。

## 摘要翻譯

自主代理系統（Autonomous Agent Systems）日益依賴可複用技能抽象（Reusable Skill Abstractions）來整合經驗知識與領域專業知識。這些工件通常將自由格式指令（Free-Form Instructions）與異質資源（Heterogeneous Resources）封裝在一起。然而，確保其正確性仍具挑戰性。其失效模式超越了傳統程式碼缺陷（Conventional Code Defects），延伸至諸如意圖衝突（Intent Conflicts）等細微的語義不一致（Semantic Inconsistencies），這些衝突會以被底層模型（Underlying Model）掩蓋的靜默失敗（Silent Failures）形式呈現。此外，技能正確性（Skill Correctness）必須以意圖中的任務邊界（Task Boundaries）與泛化性（Generalizability）為基礎。我們提出 SkillSpec，一個 Hoare 風格框架（Hoare-Style Framework），將技能正確性表述為規格推理問題（Specification Reasoning Problem）。它將異質技能儲存庫（Heterogeneous Skill Repository）轉換為統一圖形表示（Unified Graph Representation），對齊描述、指令與程式碼工件（Code Artifacts）。對各節點，SkillSpec 從周圍的宣告意圖（Declared Intent）推導出 ExpectSpec，並在部分揭露的意圖（Partially Disclosed Intent）下從編碼行為（Encoded Behavior）推論出 FactSpecs。意圖遮罩（Intent Mask）調控對整體視圖（Holistic View）、血緣視圖（Lineage View）、鄰域視圖（Neighborhood View）與局部視圖（Local View）的存取，以平衡過量上下文（Excessive Context）所引入的偏差，並避免上下文不足（Insufficient Context）所導致的無據推論。SkillSpec 對這些視圖進行聯合推理以標記候選缺陷（Candidate Defects），並在隔離沙箱（Isolated Sandbox）中自動驗證這些缺陷。在取自 SkillsBench 與熱門下載儲存庫的 515 個真實世界技能上，SkillSpec 識別出 763 個人工確認缺陷（Manually Confirmed Defects），橫跨 239 個技能，達到 61.2% 的精確率（Precision）。跨多個模型家族（Model Families）的節點層級分析（Node-Level Analysis）顯示，規格推理（Specification Reasoning）對於程式碼節點（Code Nodes）一致可靠，而純文字節點（Plain-Text Nodes）仍是主要瓶頸。大多數缺陷發生於宣告意圖與實作之間的邊界（Boundaries between Declared Intent and Implementation），顯示明確規格（Explicit Specifications）可為真實世界代理生態系統（Agent Ecosystems）中的技能品質保證（Skill Quality Assurance）提供實務基礎。

### 核心貢獻（3～5點）
- 提出 SkillSpec，一個 Hoare 風格框架，將代理技能正確性轉化為規格推理問題，並以統一圖形表示對齊描述、指令與程式碼工件。
- 設計雙軌規格推導機制：從宣告意圖導出 ExpectSpec，並在部分揭露意圖下從編碼行為推論 FactSpecs。
- 引入意圖遮罩機制，調控整體、血緣、鄰域與局部四種視圖，以平衡過量上下文與上下文不足之間的推論偏差。
- 在 515 個真實世界技能上進行大規模評估，識別出 763 個人工確認缺陷，並發現大多數缺陷集中於宣告意圖與實作之間的邊界。
- 透過跨模型家族的節點層級分析，指出程式碼節點的規格推理較為可靠，而純文字節點仍是主要瓶頸。

### 適合對象
從事自主代理系統、大型語言模型工具使用、可複用技能抽象與代理生態系統品質保證的研究人員與工程師；特別適合關注技能規格驗證、語義一致性檢測，以及希望建立自動化技能品質管線的開發者與維運團隊。

## 深度分析

#### 方法論解析

##### 核心問題設定：將技能正確性視為規格一致性問題
SkillSpec 把代理技能（Agent Skill）視為一種「可執行工件（Executable Artifact）」，其正確性並非僅取決於程式碼能否執行，而是取決於「宣告意圖（Declared Intent）」與「編碼行為（Encoded Behavior）」之間的一致性。作者借鑑 Hoare 風格框架（Hoare-Style Framework）的精神，把每個技能節點的語義拆成兩類規格：

- **ExpectSpec**：從完整宣告意圖導出的預期規格，代表「這個步驟應該做什麼」。
- **FactSpecs**：在部分揭露的意圖（Partially Disclosed Intent）下，從實作工件推導出的事實規格，代表「這個步驟實際上做了什麼」。

當 ExpectSpec 與 FactSpecs 出現不一致時，即視為潛在的候選缺陷（Candidate Defects）。這種做法把傳統上針對程式碼的 Hoare 三元組概念，擴展到同時涵蓋自然語言指令（Natural-Language Instructions）與異質程式碼工件（Code Artifacts）的代理技能場景。

##### 異質工件的統一圖形表示（Unified Graph Representation）
為了處理挑戰 C1（異質工件與離散約束），SkillSpec 首先將整個異質技能儲存庫（Heterogeneous Skill Repository）轉換為統一圖形表示：

1. **SKILL.md 解析**：將半結構化的技能描述檔案（SKILL.md）映射為工作流圖（Workflow Graph），其中節點可能對應步驟說明、參數、前置條件等純文字節點（Plain-Text Nodes）。
2. **程式碼解析**：將腳本轉換為源於具體語法樹（Concrete Syntax Tree）的語言無關中間表示（Language-Agnostic Intermediate Representation, IR），形成程式碼節點（Code Nodes）。
3. **雙向節點綁定（Bidirectional Node Binding）**：把描述層的宣告意圖與程式碼層的編碼行為對齊，讓後續的規格推理能夠在圖上跨語言、跨模態地進行。

這種圖形化統一表示是後續所有規格推理的基礎，也是 SkillSpec 與傳統僅針對單一程式碼檔案進行靜態分析的最大差異之一。

##### 意圖遮罩（Intent Mask）與多視圖 FactSpecs
挑戰 C2 指出：意圖揭露粒度（Intent Disclosure Granularity）會同時帶來兩種風險：

- **過量上下文（Excessive Context）**：若模型在推導事實規格時看到完整意圖，容易產生確認偏誤，把實作「腦補」成符合預期的樣子，掩蓋真正的實作證據。
- **上下文不足（Insufficient Context）**：若完全沒有高階意圖，模型又可能對行為邊界做出不合理的推論。

為此，SkillSpec 提出 **意圖遮罩（Intent Mask）**，在推導 FactSpecs 時刻意遮蔽部分意圖資訊，並組合四種視圖：

| 視圖 | 說明 | 作用 |
|---|---|---|
| 整體視圖（Holistic View） | 整個技能儲存庫的全域脈絡 | 提供任務邊界（Task Boundaries）與泛化性（Generalizability）資訊 |
| 血緣視圖（Lineage View） | 沿技能譜系上下游的脈絡 | 捕捉步驟間的因果與資料流關係 |
| 鄰域視圖（Neighborhood View） | 圖中鄰近節點的脈絡 | 平衡局部細節與周邊語義 |
| 局部視圖（Local View） | 單一節點本身 | 聚焦具體實作證據，避免被外部意圖污染 |

透過對這四種視圖分別推導 FactSpecs，SkillSpec 能夠在多種意圖揭露粒度下進行比較，降低單一視角帶來的偏誤。

##### 聯合規格推理與候選缺陷標記
在取得 ExpectSpec 與多視圖 FactSpecs 後，SkillSpec 進行聯合推理：

- 比較「預期應該發生的行為」與「在不同意圖粒度下實際推導出的行為」。
- 當多視圖 FactSpecs 彼此不一致，或與 ExpectSpec 產生衝突時，標記為候選缺陷。
- 特別關注宣告意圖與實作之間的邊界（Boundaries between Declared Intent and Implementation），因為實驗顯示大多數缺陷都發生在這裡。

這裡的推理本質上是一種「語義不一致檢測」，涵蓋了描述漂移（Description Drift）、意圖衝突（Intent Conflicts）等傳統程式分析難以捕捉的問題。

##### 隔離沙箱（Isolated Sandbox）動態驗證
靜態標記的候選缺陷仍需執行層級證據。SkillSpec 採用隔離沙箱進行自動驗證：

- 使用暖容器（Warm Container）重複利用環境，降低驗證成本。
- 每次執行分配全新的工作空間（Fresh Workspace）與代理上下文（Agent Context），避免狀態污染。
- 對程式碼層級的主張執行最小探針（Minimal Probes）。
- 對工作流層級的主張建構情境進行佐證（Scenario Corroboration）。
- 保留執行時證據（Runtime Evidence）與軌跡（Trajectory），供後續人工確認與除錯。

這種「靜態推理 + 動態驗證」的雙階段設計，是 SkillSpec 能夠在真實代理生態系統（Agent Ecosystems）中達到實用精確率（Precision）的關鍵。

#### 實驗數據解讀

##### 資料集與規模
論文評估使用了兩個來源：

- **SkillsBench**：一個針對代理技能的基準集（Benchmark）。
- **SkillsTop**：從 skills.sh 下載量最高的技能中收集的集合。

最終共評估 **515 個真實世界技能（Real-World Skills）**，這些技能來自廣泛使用的代理技能生態系統，具有代表性。

##### 主要結果
SkillSpec 在這 515 個技能中：

- 識別出 **239 個技能** 含有缺陷，佔總數的 **46.4%**。
- 共標記 **763 個經人工確認的缺陷（Manually Confirmed Defects）**。
- 在沙箱驗證後達到 **61.2% 的精確率（Precision）**。

這幾個數字傳達了幾個重要訊息：

1. **缺陷非常普遍**：近半數的熱門技能都含有可被識別的缺陷，顯示代理技能品質保證（Skill Quality Assurance）是一個真實且急迫的問題。
2. **精確率具實用價值但仍有進步空間**：61.2% 的 Precision 表示每三個候選缺陷中約有兩個是真實缺陷，對於自動化篩選工具而言已具可用性，但仍會產生可觀的假陽性（False Positives）。
3. **缺陷密度高**：763 個確認缺陷分散在 239 個技能中，平均每個有缺陷的技能約含 3.2 個缺陷，顯示問題往往不是單點錯誤，而是結構性的語義不一致。

##### 節點層級分析（Node-Level Analysis）
論文進一步比較不同模型家族（Model Families）在節點層級的表現，發現：

- **程式碼節點（Code Nodes）**：規格推理始終可靠。這符合直覺，因為程式碼具有明確語法與執行語義，模型較容易從中推導出穩定的 FactSpecs。
- **純文字節點（Plain-Text Nodes）**：仍是主要瓶頸。自然語言指令的模糊性、隱含前提與自由格式（Free-Form Instructions）使得 ExpectSpec 與 FactSpecs 的對齊困難。

這項發現對未來研究具有指導意義：提升純文字節點的規格抽取與對齊能力，是改善整體 Precision 與 Recall 的關鍵。

##### 缺陷分佈與根本原因
實驗指出，大多數缺陷發生在「宣告意圖與實作之間的邊界」。這與論文的核心論點一致：

- 傳統程式碼缺陷（Conventional Code Defects）如語法錯誤、型別錯誤等，通常會在執行時期失敗（Runtime Failures）或測試階段暴露。
- 代理技能的缺陷更多是語義不一致（Semantic Inconsistencies），例如 SKILL.md 描述的功能與腳本實際行為不符，或不同步驟的意圖互相衝突。這些問題會被基礎模型（Foundation Model）的內在能力（Intrinsic Capabilities）掩蓋，形成靜默失敗（Silent Failures）。

因此，單靠執行觀察無法發現這些缺陷，必須透過明確規格（Explicit Specifications）進行對照檢查。

##### 未呈現但值得關注的指標
論文摘要與內文未明確提及：

- **召回率（Recall）**：我們不知道有多少真實缺陷未被 SkillSpec 發現。
- **執行成本與延遲**：雖然提到使用暖容器降低成本，但未給出具體數字。
- **不同模型家族間的精確率差異**：僅說明「跨模型家族有效」，未提供詳細比較表。

這些資訊的缺失使得我們難以全面評估 SkillSpec 在實際部署中的經濟性與覆蓋率。

#### 與現有研究的比較

##### 相對於傳統軟體驗證
傳統軟體的正確性主要透過以下機制保障：

- **型別系統（Type Systems）**
- **單元測試與整合測試**
- **執行時期監控與 Runtime Failures**

這些方法對於代理技能有明顯局限：

1. **自然語言指令無法被型別系統檢查**：自由格式指令（Free-Form Instructions）不具備形式化語法，傳統型別檢查無法適用。
2. **測試無法覆蓋語義漂移**：即使技能在特定輸入下執行成功，仍可能與 SKILL.md 的宣告意圖不一致，形成靜默失敗。
3. **執行成功不等於正確**：基礎模型可能憑藉其內在能力補償了技能中的錯誤，讓使用者誤以為技能沒問題。

SkillSpec 透過規格推理（Specification Reasoning）把驗證焦點從「是否執行成功」轉移到「行為是否符合宣告意圖」，填補了上述空白。

##### 相對於現有代理技能研究
現有代理技能研究多聚焦於：

- **能力增強（Capability Enhancement）**
- **安全性（Safety）**
- **基準測試（Benchmarks）**

但針對「技能缺陷（Skill Defects）」的系統性研究相對不足。SkillSpec 是少數同時整合以下兩者的框架：

- **靜態缺陷檢測**：透過圖形化統一表示與規格推理，在執行前發現語義不一致。
- **動態沙箱驗證**：在真實環境中執行最小探針，確認候選缺陷是否確實存在。

這種「靜態 + 動態」的組合，使其不同於純粹的靜態分析工具，也不同於僅依賴執行觀察的測試方法。

##### 相對於其他規格推理工作
近年已有研究將 Hoare 風格推理擴展到自然語言指令與大規模系統驗證。SkillSpec 的獨特之處在於：

1. **專注於代理技能場景**：把 SKILL.md、自然語言指令、腳本、資料等多種異質資源統一建模。
2. **引入意圖遮罩機制**：透過控制意圖揭露粒度，解決規格推導中的偏誤問題。
3. **強調任務邊界與泛化性**：不只看單一執行是否成功，而是檢查技能是否在其宣稱的任務邊界（Task Boundaries）內正確運作，並具備合理的泛化性（Generalizability）。

##### 主要限制
儘管有上述貢獻，SkillSpec 仍存在明顯限制：

1. **純文字節點是瓶頸**：自然語言規格抽取與對齊的可靠性不足，限制了整體表現。
2. **精確率仍有提升空間**：61.2% 的 Precision 意味著開發者仍需花費時間過濾假陽性。
3. **召回率未知**：無法判斷 SkillSpec 是否遺漏了大量真實缺陷。
4. **驗證成本**：雖然使用暖容器與最小探針，但對 515 個技能執行沙箱驗證仍可能耗費可觀的計算資源。
5. **依賴基礎模型能力**：ExpectSpec 與 FactSpecs 的推導都仰賴 LLM，因此模型本身的幻覺（Hallucination）與推理錯誤會直接影響結果。

#### 可重現性評估

##### 開放資源現況
根據目前提供的論文內容，**未明確提及原始碼、資料集或模型權重的公開釋出**。論文描述了方法架構與實驗結果，但沒有提供：

- GitHub 或其他程式碼倉庫連結。
- 515 個評估技能的完整清單與標註。
- 沙箱驗證環境的具體配置檔案。
- 用於推導 ExpectSpec 與 FactSpecs 的提示詞（Prompts）細節。

##### 對可重現性的影響
這對可重現性（Reproducibility）造成以下挑戰：

1. **方法實作細節不透明**：意圖遮罩的具體遮蔽策略、多視圖 FactSpecs 的組合方式、候選缺陷的評分機制等，都缺乏足夠細節讓他人復現。
2. **資料取得困難**：雖然 skills.sh 與 SkillsBench 是公開資源，但論文未說明如何從中篩選出 515 個技能，也未釋出人工確認的缺陷標註。
3. **沙箱環境難以重建**：暖容器、最小探針、情境建構等動態驗證步驟需要特定基礎設施，若無公開配置，其他研究者難以重複實驗。
4. **模型依賴性難以評估**：論文提到跨模型家族有效，但未說明使用了哪些具體模型版本與參數設定。

##### 建議的改進
若要提升可重現性，作者可考慮釋出：

- 完整的原始碼與相依套件清單。
- 評估資料集與人工標註（或至少釋出技能 ID 與缺陷位置）。
- 沙箱驗證的 Docker 映像檔或配置腳本。
- 主要實驗的提示詞範本與模型版本資訊。

在這些資源公開之前，SkillSpec 的結果較難被獨立驗證或作為後續研究的基準比較。

#### 未來研究方向

##### 1. 強化純文字節點的規格抽取
由於純文字節點（Plain-Text Nodes）是主要瓶頸，未來可探索：

- 更結構化的自然語言理解技術，例如從 SKILL.md 自動抽取前置條件、後置條件與不變量。
- 結合領域本體（Domain Ontology）或技能模板，降低自由格式指令的歧義性。
- 使用對比學習或微調專門的規格抽取模型，提升 ExpectSpec 的穩定性。

##### 2. 意圖遮罩策略的最佳化
目前的意圖遮罩（Intent Mask）採用四種固定視圖，未來可研究：

- 自適應遮罩：根據節點類型、技能複雜度或模型能力動態調整遮蔽範圍。
- 可學習的遮罩：透過訓練資料學習最適合的意圖揭露粒度。
- 多輪對話式規格澄清：讓模型在發現歧義時主動詢問，而非單向推論。

##### 3. 從缺陷檢測到缺陷修復
SkillSpec 目前僅標記候選缺陷，下一步可發展為自動修復框架：

- 根據 ExpectSpec 與 FactSpecs 的差異，生成修補建議。
- 區分 SKILL.md 描述錯誤、程式碼實作錯誤、或兩者皆錯，並對症下藥。
- 結合人機協同（Human-in-the-Loop）審查，提升修復的可信度。

##### 4. 跨技能與跨儲存庫的泛化性分析
論文已強調任務邊界（Task Boundaries）與泛化性（Generalizability）的重要性，未來可進一步：

- 建立技能泛化性測試集，評估技能在宣稱邊界外的行為。
- 研究技能之間的組合正確性：當多個技能串接使用時，意圖是否衝突。
- 發展技能版本差異分析，追蹤規格隨時間的漂移。

##### 5. 降低成本與提升擴展性
沙箱驗證雖有效但昂貴，未來可研究：

- 更輕量的靜態過濾器，減少需要進入沙箱的候選數量。
- 基於執行軌跡（Trajectory）的選擇性重驗證，避免重複執行。
- 將部分驗證任務卸載到較小模型，僅保留高風險案例給強大模型。

##### 6. 與形式化驗證的結合
雖然代理技能難以完全形式化，但對於程式碼節點（Code Nodes）可探索：

- 將 IR 轉換為形式化語言，進行部分自動化證明。
- 對關鍵不變量使用 SMT 求解器或符號執行輔助驗證。
- 建立「輕量形式化規格」與自然語言規格的混合驗證流程。

##### 7. 多代理與動態環境中的技能正確性
目前的 SkillSpec 主要針對單一技能的靜態儲存庫，未來可擴展至：

- 多代理協作場景下的技能互動正確性。
- 動態環境中技能行為的持續監控與規格更新。
- 線上學習與適應過程中的技能品質退化偵測。

這些方向都有助於把 SkillSpec 從一個研究原型，轉化為可部署於真實代理生態系統（Agent Ecosystems）中的品質保證基礎設施。

## 論文問答

**Q1：SkillSpec 主要想解決什麼問題？**
A：SkillSpec 針對的是自主代理系統中「可複用技能抽象」的正確性保證問題。這些技能通常把自由格式指令與異質資源（如程式碼、資料、設定檔）打包在一起，因此其缺陷不僅是傳統程式碼錯誤，更常出現語義不一致、意圖衝突、描述漂移等會被底層基礎模型掩蓋的靜默失敗。由於技能的正確性必須奠基於宣告意圖、任務邊界與泛化性，現有的型別系統或單元測試難以直接適用，因此需要新的規格推理方法來自動化檢測這類缺陷。

**Q2：為什麼傳統軟體驗證方法難以發現代理技能中的缺陷？**
A：傳統軟體的行為主要由程式碼決定性定義，可透過型別檢查、測試與執行時期失敗來偵錯；然而代理技能大量依賴非結構化的自然語言指令，其語義容許超出傳統程式碼缺陷的錯誤型態。當基礎模型具備強大的內在能力時，它可能在執行過程中自動補足或掩蓋技能中的不一致，使得單靠觀察執行結果無法判斷技能是否正確。因此，必須將觀察到的行為對照技能的宣告意圖與一般性要求，才能辨識出真正的語義缺陷。

**Q3：確保技能正確性為什麼對代理生態系統很重要？**
A：技能已經成為代理生態系統中的第一級軟體工件，數個月內就有超過二十萬個技能被釋出，並被廣泛重複使用與分發。一旦某個技能存在意圖衝突或邊界描述不實等問題，就會隨著複用傳播到不同的任務與代理中，造成難以追蹤的系統性風險。因此，建立以明確規格為基礎的技能品質保證機制，是讓大規模代理生態系統能夠安全、可靠運作的關鍵基礎。

**Q4：SkillSpec 的核心方法論是什麼？**
A：SkillSpec 將技能正確性重新定義為一個 Hoare 風格的規格推理問題：每個技能都隱含「應該做什麼」與「實際做了什麼」兩種規格，正確性取決於兩者是否一致。它首先把異質技能儲存庫轉換成統一圖形表示，將 SKILL.md 中的描述對齊到工作流圖節點，並把程式碼工件解析成語言無關的中間表示。對每個節點，SkillSpec 從周圍的宣告意圖導出 ExpectSpec，同時在部分揭露意圖的條件下從實作推導 FactSpecs，再透過多視角聯合推理標記候選缺陷，最後在隔離沙箱中動態驗證。

**Q5：「意圖遮罩式規格推理」的關鍵創新在哪裡？**
A：關鍵創新在於引入「意圖遮罩」機制，以調控模型在推導 FactSpecs 時能看到的意圖範圍，避免過量上下文造成「照本宣科」的偏差，也避免上下文不足導致缺乏依據的推論。透過組合整體視圖、血緣視圖、鄰域視圖與局部視圖四個層級，SkillSpec 能夠在不同粒度下分別檢視宣告意圖與編碼行為。這種多視角對照讓系統更容易發生意圖與實作不一致的邊界上偵測到語義缺陷，而不是只依賴單一、完整的提示。

**Q6：SkillSpec 在設計上做了哪些重要選擇？**
A：首先，它採用統一圖形表示來綁定半結構化的 SKILL.md 描述與程式碼工件，並使用源於具體語法樹的語言無關中間表示，以處理異質程式碼資源。其次，它設計了四層意圖遮罩來精細控制意圖揭露粒度，在推導 FactSpecs 時平衡偏差與推論依據。最後，它的沙箱驗證採用可重複使用的暖容器，但為每次執行分配全新的工作空間與代理上下文，並針對程式碼層級宣稱執行最小探針、針對工作流層級建構情境進行佐證，以保留可審查的執行證據。

**Q7：實驗使用了哪些資料集與基準？**
A：實驗評估了 515 個真實世界技能，這些技能來自 SkillsBench 基準集以及從 skills.sh 下載量最高的 SkillsTop 集合。作者在收集時先鎖定 skills.sh 上安裝次數超過 1,000 的技能，從約 88 萬個技能中篩出 7,577 個熱門技能，再從中選取具有代表性的樣本進行分析。這樣的選取方式確保了實驗結果能反映實際被廣泛採用的代理技能品質現況。

**Q8：SkillSpec 取得了哪些關鍵實驗結果？**
A：在 515 個技能中，SkillSpec 識別出 239 個技能含有缺陷，佔比 46.4%，並經人工確認得到 763 個真實缺陷，沙箱驗證後的精確率達到 61.2%。節點層級分析顯示，規格推理對於程式碼節點相當穩定可靠，但純文字節點仍是主要瓶頸，容易因自然語言語義模糊而產生不準確的規格。絕大多數缺陷發生在宣告意圖與實作之間的邊界，證明了明確規格對於技能品質保證具有實質價值。

**Q9：實驗中有哪些消融或敏感性洞見？**
A：跨多個模型家族的節點層級分析一致顯示，程式碼節點的規格推理結果較為穩健，而純文字節點的表現則隨模型與語義複雜度波動較大，這凸顯了自然語言規格抽取仍是待強化的環節。意圖遮罩的設計有效地在過量與不足上下文之間取得平衡，若完全揭露意圖，FactSpecs 容易偏向 ExpectSpec，降低缺陷偵測力。沙箱驗證則進一步過濾掉靜態推理產生的假陽性，是達到實用精確率不可或缺的步驟。

**Q10：SkillSpec 可應用在哪些實務場景？**
A：技能市集與代理平台可在技能上架前整合 SkillSpec，對開發者提交的技能進行自動化品質審查，降低有缺陷技能被廣泛分發的風險。企業內部的持續整合／持續部署流程也能將其納入，作為技能版本更新時的靜態檢查與動態回歸測試工具。對於個別開發者而言，SkillSpec 可以協助及早發現 SKILL.md 描述與程式碼實作之間的漂移，減少後續除錯成本。

**Q11：在產品化過程中需要考慮哪些因素？**
A：首先必須權衡驗證成本與覆蓋率，因為每次沙箱執行與多視角規格推理都會消耗模型呼叫與運算資源，雖然暖容器可攤提部分開銷，但仍需為每次執行準備乾淨的工作空間與代理上下文。其次，純文字節點的瓶頸意味著產品中可能需要引入人機協作機制，讓人工審查專注於高風險的自然語言規格衝突。最後，SkillSpec 需要與技能註冊表、版本控制系統以及代理執行環境緊密整合，才能發揮持續品質監控的效果。

**Q12：這項研究對整個領域可能帶來什麼影響？**
A：SkillSpec 把傳統程式分析與 Hoare 風格驗證的思想擴展到包含自然語言指令的代理工件，為軟體工程與大型語言模型代理研究之間搭起橋樑。它證明了透過明確規格與多視角對照，可以在真實世界技能中大規模、自動化地發現語義缺陷。這將促使未來的技能開發者更重視 SKILL.md 等宣告意圖文件的品質，並推動建立標準化的技能規格語言與品質認證機制。

**Q13：SkillSpec 有哪些已承認的限制？**
A：純文字節點的規格抽取仍不夠穩定，是整體效能的主要瓶頸，限制了對自由格式指令缺陷的召回率與精確率。61.2% 的精確率雖然具有實用價值，但仍代表有近四成的候選缺陷需要人工再次確認，無法完全免除人工審查。此外，目前的方法主要針對單一技能的靜態與動態驗證，尚未涵蓋多個技能組合使用時的交互作用，也無法處理惡意或故意誤導的宣告意圖。

**Q14：典型的失敗案例有哪些？**
A：當 SKILL.md 中的宣告意圖本身含糊或過於籠統時，ExpectSpec 會變得難以定義，而 FactSpecs 也可能因為意圖遮罩導致過度寬鬆的解釋。對於高度隱含在自然語言步驟中的行為，例如依賴常識或上下文推論的指令，規格推理可能無法完整捕捉其預期效果。沙箱驗證也可能因為測試情境不夠具代表性，而無法重現某些需要特定外部狀態或長期互動才會觸發的工作流層級缺陷。

**Q15：未來可以朝哪些方向延伸？**
A：未來可以針對純文字節點開發更強大的語義解析器，或結合檢索增強生成技術來提升自然語言規格的抽取品質。也可以探索更細緻或動態調整的意圖遮罩策略，並將驗證範圍從單一技能擴展到多技能組合與執行時期監控。最後，建立開放的技能缺陷基準與標準化規格語言，將有助於社群持續改善代理技能的品質保證方法。

## 實務應用指南

### 適用場景

1. **技能市集（Skill Marketplace）上架前品質閘門**  
   在 skills.sh 等公開或企業內部技能市集，作者上傳 SKILL.md、自然語言指令與程式碼工件後，SkillSpec 可作為自動化審查工具，於上架前偵測描述漂移、意圖衝突與實作不一致，降低使用者遇到靜默失敗的風險。

2. **企業內部代理技能 CI/CD 管線**  
   當團隊持續迭代大量可複用技能抽象時，可將 SkillSpec 整合至持續整合流程，每次提交後自動產生 ExpectSpec 與 FactSpecs，並在隔離沙箱中驗證候選缺陷，避免有問題的技能版本進入正式環境。

3. **遺留技能盤點與汰換評估**  
   對於已累積數千個技能的組織，SkillSpec 能以統一圖形表示梳理異質技能儲存庫，標示出宣告意圖與編碼行為之間的邊界缺陷，協助決定哪些技能需要重構、棄用或補強文件。

4. **多作者技能註冊中心治理**  
   在由不同團隊貢獻技能的代理生態系統中，SkillSpec 提供客觀的規格一致性檢查機制，減少因自由格式指令詮釋差異造成的語義不一致，並作為跨團隊品質保證的共同語言。

5. **高風險領域的技能安全與合規審查**  
   針對金融、醫療或法律等場景的技能，SkillSpec 可強化任務邊界與泛化性檢查，確認技能不會在預期範圍外執行，並透過沙箱動態驗證降低基礎模型內在能力掩蓋缺陷的可能性。

### 實作前置條件

**資料準備**
- 可存取完整的技能儲存庫，包含 SKILL.md、自然語言指令、程式碼工件、資源檔案與相依性清單。
- 技能內容需具備一定程度的結構化資訊，例如步驟描述、輸入輸出說明與程式碼對應關係，以便建立統一圖形表示。
- 建議準備已人工標註缺陷的驗證集，用於校正意圖遮罩與評估精確率。

**運算資源**
- 大型語言模型推論能力：建議支援多個模型家族，以便進行節點層級分析與交叉驗證。
- 圖形資料庫或向量儲存：用於儲存技能節點、血緣關係、鄰域關係與規格推論結果。
- 隔離沙箱環境：需支援容器化執行、暖啟動容器重複利用，並能為每次驗證分配乾淨的工作空間與代理上下文。

**團隊能力**
- 熟悉 Hoare 風格規格推理與程式分析基礎。
- 具備將異質資源轉換為語言無關中間表示的經驗。
- 能設計與維護 LLM 提示工程流程，並具備沙箱安全與成本控管經驗。

---

### 實作步驟建議

1. **盤點與正規化技能資產**  
   收集所有 SKILL.md 與程式碼工件，解析半結構化描述並將其轉換為工作流程圖；同時將不同語言的程式碼轉為語言無關中間表示，建立宣告意圖與編碼行為的雙向節點綁定。

2. **建立統一圖形表示**  
   將每個技能視為一張圖，節點涵蓋純文字節點與程式碼節點，邊則代表血緣、鄰近呼叫與整體工作流程關係，為後續規格推理提供結構化基礎。

3. **設定意圖遮罩與多視圖策略**  
   針對每個節點配置整體視圖、血緣視圖、鄰域視圖與局部視圖的可見範圍，平衡過量上下文造成的偏差與上下文不足導致的推論缺乏依據。

4. **產生 ExpectSpec 與 FactSpecs**  
   從完整宣告意圖導出 ExpectSpec，並在部分揭露的意圖下從實作工件推導 FactSpecs。建議對程式碼節點與純文字節點採用差異化提示策略，因為純文字節點是目前主要瓶頸。

5. **執行規格一致性推理**  
   聯合比對 ExpectSpec 與多視圖 FactSpecs，標記候選缺陷，特別關注宣告意圖與實作之間的邊界，因為大多數缺陷發生於此處。

6. **沙箱動態驗證**  
   對每個候選缺陷在隔離沙箱中執行最小探針測試或建構情境進行佐證，保留執行軌跡與運行證據，並將驗證結果回饋至缺陷排序機制。

7. **人工審查與分級**  
   由領域專家審查經沙箱確認的候選缺陷，依嚴重程度分級，並決定是否阻擋發布、要求修正或僅記錄追蹤。

8. **持續監控與回饋迴路**  
   將審查結果重新餵入模型與規則調校流程，定期重新生成規格以偵測描述漂移，並隨技能迭代更新圖形表示與遮罩設定。

### 潛在風險與注意事項

- **純文字節點的推理瓶頸**  
  論文顯示規格推理對程式碼節點較為可靠，但純文字節點容易產生雜訊。建議對純文字節點加強人工覆核，或結合文件模板與結構化欄位降低歧義。

- **LLM 推論幻覺與不穩定性**  
  ExpectSpec 與 FactSpecs 皆由模型生成，可能出現過度推論。可透過多模型家族投票、意圖遮罩對照與沙箱驗證來提升信心。

- **上下文過量與不足的權衡**  
  過多宣告意圖會使 FactSpec 偏向預期行為，掩蓋真實缺陷；過少則導致推論缺乏依據。需依技能複雜度動態調整四層視圖的揭露比例。

- **沙箱環境的真實度限制**  
  沙箱無法完全模擬所有外部相依與網路狀態，部分缺陷可能在驗證時未被觸發。建議搭配代表性測試資料與模糊測試提升覆蓋率。

- **成本與延遲**  
  對大型技能儲存庫進行全量規格推理與沙箱驗證成本高昂。可先對高風險或高下載量技能優先執行，並利用暖容器與快取機制降低開銷。

- **過度依賴自動化結果**  
  論文精確率為 61.2%，表示仍有相當比例誤報。SkillSpec 應作為輔助工具，而非取代人工審查與傳統測試。

### 與其他技術的整合建議

- **CI/CD 與版本控制**  
  在 Git 提交或合併請求階段觸發 SkillSpec 檢查，將候選缺陷報告附加至程式碼審查流程，並設定品質閘門阻擋高嚴重度問題。

- **技能註冊中心與市集平台**  
  將 SkillSpec 嵌入上架流程，作為技能發布前的必要檢查項目，並向使用者公開品質分數或驗證標章。

- **IDE 與開發者工具**  
  為技能作者提供即時規格一致性提示，例如在編輯 SKILL.md 或程式碼時，即時顯示 ExpectSpec 與 FactSpecs 的差異。

- **現有測試框架**  
  SkillSpec 不應取代單元測試或整合測試，而應與之互補：靜態規格推理負責語義不一致，動態沙箱驗證補強執行證據，傳統測試則確保功能正確性。

- **LLM 可觀測性平台**  
  將 SkillSpec 的執行軌跡、規格推論結果與沙箱驗證紀錄匯入可觀測性系統，協助維運團隊追蹤技能在生產環境中的行為偏差。

- **文件與知識管理系統**  
  把產出的 ExpectSpec 與 FactSpecs 匯出為結構化文件，作為技能使用說明、維護手冊與教育訓練素材。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於論文的動機與核心概念：把技能視為可執行工件，其正確性取決於宣告意圖與編碼行為是否一致。理解「靜默失敗」「描述漂移」「意圖衝突」等關鍵詞後，再閱讀適用場景與實作步驟，即可掌握 SkillSpec 能解決什麼問題。

**AI 工程師**  
應深入研讀統一圖形表示的建構方式、語言無關中間表示的設計、意圖遮罩的四層視圖機制，以及 ExpectSpec 與 FactSpecs 的生成與比對流程。沙箱驗證的實作細節與成本優化策略也是落地時的關鍵。

**研究人員**  
可關注本研究如何將 Hoare 風格規格推理擴展到自然語言指令與異質代理工件，並分析多視圖推理在程式碼節點與純文字節點上的差異表現。未來可進一步探索提升純文字節點精確率、降低 LLM 推論成本，以及將方法推廣至更廣泛的代理生態系統。

**產品經理**  
重點在於評估商業價值與導入成本：61.2% 的精確率代表需要人工審查環節，因此 SkillSpec 最適合作為品質閘門與輔助審查工具，而非全自動把關。建議優先導入高風險、高使用量或多人協作的技能場景，並將其定位為提升技能品質保證與使用者信任度的基礎建設。
