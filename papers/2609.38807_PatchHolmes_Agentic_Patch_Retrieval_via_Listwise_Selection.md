# PatchHolmes：透過列表式選擇的代理式補丁檢索

**原文標題：** PatchHolmes: Agentic Patch Retrieval via Listwise Selection

## ⚡ TL;DR

解決漏洞補丁檢索問題，因60-63% CVE缺乏修補連結，傳統逐點評分難以處理長差異。
PatchHolmes兩階段系統先以混合檢索產生Top-100候選，再由代理列表式比較選出最佳提交。
Recall@1超越Favia 25.34%與IRCoT 31.40%，無需微調即可運行於凍結模型。

## 摘要翻譯

補丁檢索（Patch Retrieval，即尋找修復已知漏洞之提交的工作）是漏洞管理（Vulnerability Management）工作流程的基礎，然而主要公告資料庫（Advisory Database）中 60% 至 63% 的 CVE 缺乏補丁連結。我們提出 PatchHolmes，一個兩階段補丁檢索（Two-Phase Patch Retrieval）系統，將混合式第一階段檢索器（Hybrid First-Stage Retriever）與代理式（Agentic）第二階段檢查迴圈（Inspection Loop）相結合。不同於逐點式先前工作（Pointwise Prior Work）獨立評分每個候選，第二階段代理以 Top-100 列表式（Top-100 Listwise）讀取候選：它一次看到完整的候選名單，並透過四個預算受限的工具（Budgeted Tools）選擇性地讀取 3 至 10 個提交，最終選出單一最佳提交。在 GitHubAD 上，PatchHolmes 在 Recall@1 上領先逐點式二元分類器（Binary Classifier）Favia 25.34 個百分點，並領先檢索加思維鏈（Retrieve-and-CoT）基準 IRCoT 31.40 個百分點，每個 CVE 僅需一次代理對話（Agent Conversation），而 Favia 需要十次；在候選集合（Candidate Set）相同的情況下，相較於直接採用檢索器的首選候選，代理使 Recall@1 額外提升 27.32 個百分點；而同一代理原封不動地遷移至 PatchFinder_top10 後，將 Recall@1 從 PatchFinder 自身的首選（24.28%）提升至 39.86%。在 Qwen 系列內更換 LLM 主幹（LLM Backbone）僅使 Recall@1 變動不到 1 個百分點，而第二個模型系列（gpt-oss）仍遠高於無代理基準（No-Agent Floor），因此增益來自列表式代理迴圈（Listwise Agent Loop）；整個系統以凍結的開放權重模型（Frozen Open-Weight Model），於本地 Git 儲存庫（Local Git Repository）上運行，無需微調（Fine-tuning）或外部搜尋 API（External Search API）。

### 核心貢獻（3～5點）
- 提出 **PatchHolmes** 兩階段補丁檢索系統，結合混合式第一階段檢索器與代理式第二階段檢查迴圈，有效解決公告資料庫中 60%–63% CVE 缺乏補丁連結的缺失連結問題（Missing-Link Problem）。
- 引入 **列表式選擇（Listwise Selection）** 機制，使代理能一次檢視完整 Top-100 候選名單（Top-k Shortlist），並透過四個預算受限的工具選擇性深入讀取 3 至 10 個提交，突破傳統逐點評分（Pointwise Scoring）獨立判斷的限制。
- 在 GitHubAD 資料集上，Recall@1 顯著超越逐點式基準 Favia（+25.34%）與檢索加思維鏈基準 IRCoT（+31.40%），且每個 CVE 僅需一次代理對話，運算效率大幅提升。
- 證明列表式代理迴圈的增益具備 **跨模型與跨檢索器的可遷移性**：在 Qwen 系列內更換 LLM 主幹影響小於 1%，且同一代理無修改地遷移至 PatchFinder_top10 即可將 Recall@1 由 24.28% 提升至 39.86%。
- 系統完全基於 **凍結的開放權重模型（Frozen Open-Weight Model）** 與本地 Git 儲存庫運行，無需微調或付費外部搜尋 API（Paid External Search API），具備高度實用部署性與擴展性（Scaling）。

### 適合對象
本論文最適合以下讀者閱讀：(1) 從事軟體漏洞管理、漏洞揭露（Vulnerability Disclosure）與安全性公告（Security Advisory）維護的研究者與實務工程師；(2) 關注開源軟體（OSS）安全、軟體供應鏈掃描器（Supply-Chain Scanner）與 SBOM 元資料整理（Metadata Curation）的研究人員；(3) 對大型語言模型（LLM）代理式（Agentic）推理、檢索增強生成（RAG）與思維鏈（CoT）機制感興趣的自然語言處理與資訊檢索領域學者；(4) 負責 CVE 補丁對應（Patch Mapping）、受影響版本範圍追蹤（Affected-Version-Range Tracker）與漏洞評估（Vulnerability Assessment）的資安分析師與維護者。

## 深度分析

#### 方法論解析

PatchHolmes 採用「兩階段串接」(two-phase pipeline) 架構，將補丁檢索 (patch retrieval) 任務拆解為「候選召回」與「精細選擇」兩個子問題，並以「列表式選擇」(listwise selection) 作為核心設計哲學，與傳統逐點評分 (pointwise scoring) 形成根本性區別。

**第一階段：混合式檢索器 (Hybrid First-Stage Retriever)**

第一階段的目標是從大型 Git 儲存庫中高效召回可能包含漏洞修復的候選提交。系統採用三個互補的信號源進行融合：

1. **BM25 詞彙檢索**：基於 CVE 描述與提交訊息 (commit message)、差異內容 (diff)、保留時間 (reserve)、發布時間 (publish) 等欄位進行稀疏檢索。BM25 擅長捕捉精確的詞彙匹配，對於 CVE 描述中提及的具體函式名稱、錯誤類型等關鍵詞特別有效。
2. **密集向量檢索 (Dense FAISS)**：使用 Qwen3-Embedding-8B 作為編碼器，將 CVE 描述與候選提交映射到同一向量空間，透過 FAISS 進行近似最近鄰搜尋。密集檢索能捕捉語意相似性，緩解 CVE 描述與修復提交之間詞彙不重疊的問題（例如 CVE 描述提到「buffer overflow」，而修復提交訊息寫「out-of-bounds read」）。
3. **倒數排名融合 (Reciprocal Rank Fusion, RRF, k=60)**：將 BM25 與密集檢索的排名結果以 RRF 公式融合，產生最終的 top-100 候選名單。RRF 是一種無需訓練的排名融合方法，對個別檢索器的分數尺度不敏感。

**第二階段：代理式檢查迴圈 (Agentic Inspection Loop)**

第二階段是 PatchHolmes 的核心創新。系統使用 OpenHands SDK 建構一個多輪代理 (multi-turn agent)，配備四個預算受限的工具 (budgeted tools)：

| 工具名稱 | 功能 | 預算 |
|---------|------|------|
| `list_candidates` | 一次性列出全部 100 個候選的單行摘要 (one-line manifest) | 1 次呼叫 |
| `read_commit` | 讀取單一提交的訊息、檔案列表與差異渲染 (8K 預算) | 多次呼叫 |
| `read_file_diff` | 讀取單一檔案的完整差異 (16K 預算) | 多次呼叫 |
| `submit_answer` | 提交最終選擇的提交識別碼與推理依據 | 1 次呼叫 |

代理的最大迭代次數設定為 15 次，但實驗中實際僅讀取 3 至 10 個候選提交即完成決策，體現出極高的選擇效率。

**列表式選擇 vs. 逐點評分的本質差異**

傳統方法（如 Favia）對每個候選獨立進行二元分類 (binary classifier)，輸出「是/否」標籤與信心分數 (confidence score)。當多個候選同時被標記為「是」時，最終的 rank-1 選擇退化为依賴候選順序 (candidate order) 的平手決勝 (tie-break)，而非基於內容的比較。

PatchHolmes 的列表式代理則不同：代理在 `list_candidates` 工具中一次性看到全部 100 個候選的摘要，並可根據先前工具呼叫的觀察結果 (observation) 動態調整下一步行動。這種「觀察→行動→觀察」的閉環 (closed-loop) 設計，使代理能夠：
- 比較候選之間的相對優劣，而非獨立評分
- 根據已讀內容調整後續讀取策略（例如跳過明顯不相關的提交）
- 在長差異中進行預算受限的分塊讀取，突破 BERT 類編碼器 512 token 的視窗限制

以 CVE-2015-9251（jQuery 跨網站指令碼攻擊，XSS）為例：Favia 對全部 10 個候選給出相同的「是」標籤與信心度 5，最終依序選擇了不相關的重構提交 (refactor) e7b3bc4；而 PatchHolmes 的代理依第一階段排名順序讀取 5 個提交（1, 2, 9, 4, 3），識別出 b078a62 添加了 `ajaxPrefilter` 邏輯以阻止 `text/javascript` 回應的自動執行，正是該漏洞的修復。

#### 實驗數據解讀

**主要效能指標**

在 GitHubAD 資料集（8,401 個 CVE）上的實驗結果顯示 PatchHolmes 在 Recall@1 上取得顯著提升：

| 比較對象 | Recall@1 提升幅度 | 對話成本 |
|---------|------------------|---------|
| vs. Favia（逐點二元分類器） | +25.34% | 1 次代理對話 vs. 10 次獨立呼叫 |
| vs. IRCoT（檢索加思維鏈） | +31.40% | — |
| vs. 第一階段檢索器 top-1 | +27.32% | 候選集相同 |
| PatchFinder top-1 → PatchHolmes | 24.28% → 39.86% | 代理無修改遷移 |

**關鍵消融實驗 (Ablation Insights)**

1. **代理迴圈的獨立貢獻**：在固定第一階段候選集的前提下，代理本身帶來 27.32% 的 Recall@1 提升。這意味著效能增益主要來自第二階段的列表式選擇機制，而非第一階段檢索器的改進。

2. **跨候選集的遷移能力**：將同一代理（未經修改）應用於 PatchFinder_top10 的候選集，Recall@1 從 PatchFinder 自身的 24.28% 提升至 39.86%（+15.58 個百分點）。這證明代理的列表式選擇能力具有候選集無關的泛化性。

3. **骨幹模型穩健性**：在 Qwen 系列內部切換不同規模的 LLM 骨幹 (LLM backbone)，Recall@1 變化幅度小於 1%。進一步換用 gpt-oss 模型家族，效能仍遠高於「無代理基準」(no-agent floor)。這強烈暗示效能增益源自列表式代理迴圈 (listwise agent loop) 本身的設計，而非特定模型的特性。

**實驗設計的嚴謹性**

- **控制變量**：第一階段候選集在比較中保持一致，確保效能差異歸因於第二階段。
- **成本對比**：PatchHolmes 每個 CVE 僅需 1 次代理對話，而 Favia 需要 10 次獨立 LLM 呼叫，實際上 PatchHolmes 在取得更高準確率的同時降低了 API 呼叫成本。
- **真實世界約束**：整個系統運行於凍結的開放權重模型 (frozen open-weight model) 之上，無需微調 (fine-tuning)，無需付費外部搜尋 API (paid external search API)，僅依賴本地 Git 儲存庫 (local Git repository)。

#### 與現有研究的比較

**相對於傳統補丁檢索方法（Tan et al., 2021; Dunlap et al., 2024; Li et al., 2024; Zheng et al., 2026）**

傳統方法存在兩個根本性限制：
1. **開放迴圈 (open-loop)**：靜態特徵堆疊對每個候選評分一次即輸出最終排名，無法根據觀察結果調整查詢、無法深入檢查候選、無法回退重試。
2. **前 LLM 時代編碼器**：512 token 的 BERT 類上下文視窗無法容納平均約 15,000 token 的提交差異，大部分差異在評分前即被截斷。

PatchHolmes 的代理式第二階段從根本上解決了這兩個問題：多輪代理可基於工具觀察結果精煉查詢，工具介導的分塊差異渲染使代理能夠在預算內讀取長提交。

**相對於通用領域閉環檢索器（Trivedi et al., 2023; Jiang et al., 2023; Asai et al., 2023; Jin et al., 2025a）**

通用領域方法（如 IRCoT）交替進行檢索與推理，但缺乏任務專屬的工具設計。它們針對開放網路多跳問答 (multi-hop QA) 調校，每一跳共享詞彙量較大；而補丁檢索是封閉世界設定 (closed-world setting)，CVE 描述與修復提交之間詞彙重疊度低。IRCoT 在本實驗設定下僅達到 28.55% Recall@1，遠遜於 PatchHolmes。

**相對於 Favia（Storhaug et al., 2026）**

Favia 用 LLM 取代傳統微調評分器，對 10 個預篩選候選各輸出一個「是/否」標籤與信心分數。其結構性缺陷在於逐點設計：10 次呼叫彼此獨立，當多個候選同時獲得「是」時，rank-1 選擇缺乏聯合信號進行平手決勝。PatchHolmes 的列表式設計直接消除了這一缺陷。

**現有方法的局限性**

儘管 PatchHolmes 表現優異，仍存在以下侷限：
1. **計算成本**：雖然每個 CVE 僅需 1 次代理對話，但代理內部的多輪迭代與長差異讀取仍消耗大量 token，實際推理成本可能高於簡單的逐點評分。
2. **代理失敗模式**：當代理在 15 次迭代內未呼叫 `submit_answer` 時的行為未明確說明；代理可能陷入反覆讀取同一提交或無法收斂。
3. **資料集偏誤**：實驗僅在 GitHubAD 上進行，未驗證在其他漏洞資料庫（如 NVD）上的泛化能力。
4. **大型儲存庫可擴展性**：49% 的 CVE 涉及超過 5,000 個提交的儲存庫，雖然第一階段檢索可處理，但代理在如此大規模候選池中的選擇效率有待進一步驗證。

#### 可重現性評估

PatchHolmes 在可重現性方面展現出極高的透明度，這在當前 LLM 研究中尤為難得：

**模型權重 (Model Weights)**
- 第一階段密集檢索器使用 Qwen3-Embedding-8B，屬於開放權重模型 (open-weight model)，可從 Hugging Face 等平台公開取得。
- 第二階段代理的 LLM 骨幹在 Qwen 系列內可靈活切換，且實驗表明骨幹選擇對 Recall@1 影響小於 1%，降低了對特定模型的依賴。
- gpt-oss 作為第二模型家族的驗證，進一步證明系統不鎖定特定供應商。

**程式碼與框架**
- 代理迴圈基於 OpenHands SDK 構建，該 SDK 本身為開源專案，研究社群可完整審視其工具呼叫與觀察處理的實作細節。
- 雖然論文中未明確提及程式碼倉庫 URL，但基於 AACL-IJCNLP 2026 的接收狀態與「預印本」(preprint) 標註，預計作者將在會後釋出程式碼。

**資料集 (Datasets)**
- GitHubAD 資料集包含 8,401 個 CVE，來源為 GitHub Advisory Database，屬於公開可取得的漏洞資料。
- 評估指標 Recall@1 為標準資訊檢索度量，無需自定義評測腳本。

**基礎設施需求**
- 系統運行於本地 Git 儲存庫，無需外部搜尋 API，這大幅降低了重現門檻。
- 無需微調 (fine-tuning) 即可運行，避免了訓練資料準備與超參數調校的負擔。
- 凍結模型 (frozen model) 的使用意味著無需 GPU 訓練資源，僅需推理算力。

**可重現性的潛在障礙**
- 代理的最大迭代次數（15 次）與各工具的 token 預算（8K、16K）為超參數，其選擇依據未充分披露。
- RRF 融合參數 k=60 的設定缺乏消融實驗。
- 第一階段 BM25 與密集檢索的具體欄位權重未明確說明。

#### 未來研究方向

**1. 代理架構的最佳化**

當前代理的最大迭代次數固定為 15 次，但實驗中實際僅使用 3 至 10 次即完成決策。未來可探索：
- 自適應迭代預算：根據 CVE 複雜度動態調整最大迭代次數。
- 早停機制 (early stopping)：當代理對當前最佳候選的信心度超過閾值時提前終止。
- 工具呼叫策略學習：透過強化學習或模仿學習，讓代理學會更高效的讀取順序。

**2. 多代理協作 (Multi-Agent Collaboration)**

單一代理需同時負責「規劃讀取順序」與「評估候選內容」兩個任務。未來可探索：
- 規劃代理與評估代理的分離：前者負責決定讀取哪些提交，後者負責內容比對。
- 辯論式架構：讓兩個獨立代理對同一 CVE 提出候選，透過辯論機制收斂至最終答案。

**3. 跨儲存庫遷移學習**

當前系統在每個 CVE 上獨立運行，未利用跨 CVE 的共享知識。未來方向包括：
- 從歷史 CVE-提交對中學習常見的漏洞模式與修復模式。
- 建構漏洞類型（如緩衝區溢位、XSS、SQL 注入）的原型 (prototype)，輔助代理進行零樣本 (zero-shot) 推理。

**4. 差異理解增強**

當前代理透過 `read_commit` 與 `read_file_diff` 讀取原始差異文字，未來可整合：
- 程式碼語意分析：抽象語法樹 (AST) 層級的差異比對，識別控制流變化。
- 變數依賴追蹤：追蹤漏洞相關變數在修復前後的傳播路徑。
- 測試案例關聯：將 CVE 描述與提交中的測試程式碼進行關聯。

**5. 效率與成本的權衡**

雖然 PatchHolmes 避免了付費 API，但本地推理仍需算力投入。未來可探索：
- 候選預篩選強化：在第一階段即將候選集從 100 縮減至更小規模，降低代理工作量。
- 增量式差異摘要：對長差異進行預摘要，使代理在更少 token 內獲取關鍵資訊。
- 蒸餾小型代理：將大型代理的決策能力蒸餾至小型模型，降低推理成本。

**6. 評估基準的擴展**

當前評估僅限於 GitHubAD，未來應在更多資料集上驗證：
- NVD 資料集：驗證跨漏洞資料庫的泛化能力。
- 跨語言評估：涵蓋非英語 CVE 描述與多語言程式碼庫。
- 時序泛化：訓練與測試 CVE 的時間分佈差異對效能的影響。

**7. 與漏洞管理流程的整合**

PatchHolmes 目前僅輸出「最佳提交」與推理依據，未來可探索：
- 自動化安全性公告生成：基於修復提交自動產生 CVE 描述與修補建議。
- 受影響版本範圍推斷：從修復提交推斷漏洞的引入版本與受影響版本範圍。
- 與 SBOM 工具整合：將補丁對應結果饋入軟體物料清單 (Software Bill of Materials) 驅動的供應鏈掃描器 (supply-chain scanner)。

**8. 安全與可信度考量**

代理自主讀取與評估提交的設計引發新的安全問題：
- 提示注入 (prompt injection) 風險：惡意提交訊息可能誘導代理選擇錯誤候選。
- 對抗性攻擊：攻擊者可構造看似相關但實際無關的提交，誘使代理誤判。
- 決策可解釋性：代理的推理依據需對安全分析師透明，以支援人工審核。

## 論文問答

**Q1：什麼是補丁檢索（Patch Retrieval），為什麼它在漏洞管理中扮演關鍵角色？**
A：補丁檢索是指在給定的程式碼儲存庫中，找出能修復某個已知漏洞（CVE）的具體提交（commit）的任務。這個任務是漏洞管理工作流程的基礎，因為每個被揭露的軟體漏洞都需要對應到上游儲存庫中實際修復它的提交，才能進一步用於安全性公告、CVSS 評分、受影響版本範圍追蹤以及 SBOM 驅動的供應鏈掃描器等下游應用。然而，目前 GitHub 漏洞資料庫與 NVD 中有 60% 到 63% 的 CVE 缺少補丁連結，而人工對應無法規模化，NVD 本身也面臨維護者積壓導致元資料整理延遲的問題，因此自動化的補丁檢索系統對於處理日益龐大的漏洞揭露量至關重要。

**Q2：為什麼現有的補丁檢索方法（pointwise scoring）會失敗？**
A：現有的傳統補丁檢索方法採用開放迴圈（open-loop）的設計，對每個候選提交獨立評分一次後直接輸出最終排名，無法在頂部結果錯誤時修正查詢、深入檢查候選或回退重試。更嚴重的是，這些方法依賴 BERT 類的編碼器，其 512 token 的上下文視窗根本容納不下平均約 15,000 token 的提交差異（diff），導致大部分差異內容在評分前就被截斷。此外，CVE 描述通常描述安全症狀（如「緩衝區溢位」），而修復提交的訊息則描述底層記憶體存取錯誤（如「越界讀取」），兩者共享詞彙極少，使得詞彙檢索器難以匹配。Favia 的 pointwise 設計在 CVE-2015-9251 上對 10 個候選都給出「yes」信心度 5，最終依候選順序而非內容選出錯誤的提交，正是這種獨立評分缺乏聯合信號的典型失敗案例。

**Q3：補丁檢索任務本身有哪些內在的困難特性？**
A：補丁檢索任務面臨三個根本性的內在困難。首先，語料庫規模龐大，49% 的 CVE 是針對擁有超過 5,000 個提交的儲存庫所提出的，這使得候選空間極為廣大。其次，差異內容非常長，在 8,401 筆 CVE 的 GitHubAD 資料集中，平均提交差異約為 15,000 token，遠超 BERT 等前 LLM 編碼器的 512 token 視窗。第三，CVE 描述與修復提交訊息之間共享詞彙極少，因為前者描述安全症狀而後者描述底層技術細節，導致純詞彙檢索無法有效匹配。這三個特性意味著第一階段檢索器雖然能將正確提交放入前 100 名，但真正的瓶頸在於第二階段選擇器——如何從這 100 個候選中準確識別出真正的修復提交。

**Q4：PatchHolmes 的核心方法是什麼？它採用什麼樣的兩階段架構？**
A：PatchHolmes 採用兩階段補丁檢索架構：第一階段是混合式檢索器，第二階段是代理式檢查迴圈。第一階段結合 BM25+時間、訊息、差異、保留、發布等欄位，以及使用 Qwen3-Embedding-8B 的稠密 FAISS 檢索，透過 RRF（k=60）融合產生前 100 名候選集合。第二階段則是一個基於 OpenHands SDK 的代理迴圈（最大迭代次數 15），配備四個預算受限的工具：list_candidates（一次顯示 100 筆單行清單）、read_commit（訊息、檔案、8K 差異渲染）、read_file_diff（單檔 16K 差異）以及 submit_answer（提交最佳提交與推理）。代理會根據每次工具觀察的結果來決定下一步行動，從 100 個候選中選擇性地讀取 3 到 10 個提交，最終提交一個最佳提交。

**Q5：PatchHolmes 的關鍵創新是什麼？為什麼「列表式選擇」（listwise selection）比「逐點評分」（pointwise scoring）更有效？**
A：PatchHolmes 的關鍵創新在於採用列表式選擇（listwise selection）取代傳統的逐點評分（pointwise scoring）。在逐點評分中，每個候選被獨立評分，當多個候選都獲得高分時，最終的排名只能依賴候選順序等外部信號來打破平手，無法進行聯合比較。列表式選擇則讓代理同時看到完整的候選清單，能夠比較候選之間的相對優劣，並透過四個預算受限的工具選擇性地深入檢查最有希望的提交。這種設計在 CVE-2015-9251 案例中展現了明顯優勢：Favia 對 10 個候選都給出相同的「yes」信心度，最終依順序選出錯誤的重構提交；而 PatchHolmes 的代理依第一階段排名順序讀取 5 個提交（1、2、9、4、3），識別出第 9 個提交 b078a62 才是真正的修復，因為它新增了阻斷 text/javascript 回應自動執行的 ajaxPrefilter。

**Q6：PatchHolmes 在設計上做了哪些關鍵選擇，以兼顧效能與成本？**
A：PatchHolmes 在設計上做了多項兼顧效能與成本的關鍵選擇。首先，整個系統運行在凍結的開放權重模型（frozen open-weight model）之上，無需微調或付費外部搜尋 API，這使得成本不會隨 CVE 數量線性成長。其次，每個 CVE 僅需一次代理對話，相較於 Favia 的 10 次獨立呼叫，大幅降低了推理成本。第三，代理配備四個預算受限的工具，限制了單次提交的讀取量（如 read_commit 限制為 8K、read_file_diff 限制為 16K），避免無限制的上下文消耗。第四，代理被設計為從 100 個候選中選擇性地讀取 3 到 10 個提交，而非全部讀取，進一步控制了計算成本。最後，整個系統在本地 Git 儲存庫上運行，無需外部搜尋 API，符合大規模漏洞管理的成本約束。

**Q7：PatchHolmes 在哪些基準資料集上進行評估？主要比較對象有哪些？**
A：PatchHolmes 主要在 GitHubAD 資料集上進行評估，該資料集包含 8,401 筆 CVE，是補丁檢索領域的重要基準。主要比較對象包括三類：傳統逐點評分方法 Favia（一個將微調評分器替換為 LLM 的二元分類器）、通用領域閉迴圈檢索器 IRCoT（檢索加思維鏈基準），以及另一個檢索基準 PatchFinder（特別是其 top-10 變體 PatchFinder_top10）。此外，作者還將 PatchHolmes 的代理模組遷移至 PatchFinder_top10 框架，評估代理在不同第一階段檢索器上的泛化能力。實驗還包括在 Qwen 模型家族內更換不同大小的骨幹模型，以及引入第二個模型家族 gpt-oss 來驗證列表式代理迴圈的增益是否來自架構而非特定模型。

**Q8：PatchHolmes 的關鍵實驗結果為何？**
A：PatchHolmes 在 GitHubAD 上取得了顯著的成果：相較於逐點二元分類器 Favia，Recall@1 提升了 25.34 個百分點；相較於檢索加思維鏈基準 IRCoT，Recall@1 提升了 31.40 個百分點，而每個 CVE 僅需一次代理對話（Favia 需要 10 次）。在候選集合完全相同的情況下，代理相較於直接取檢索器第一名帶來了 27.32% 的 Recall@1 增益，證明了第二階段代理的價值。當將同一個代理（未經修改）遷移至 PatchFinder_top10 時，Recall@1 從 PatchFinder 自身的第一名選擇（24.28%）提升至 39.86%，展現了強大的跨系統遷移能力。在 Qwen 模型家族內更換骨幹模型時，Recall@1 變化小於 1%，而第二個模型家族 gpt-oss 也遠高於無代理基準，證明增益來自列表式代理迴圈本身而非特定模型。

**Q9：PatchHolmes 進行了哪些消融實驗來驗證各元件的貢獻？**
A：PatchHolmes 透過多項消融實驗驗證各元件的貢獻。第一項消融比較了「代理選擇」與「直接取檢索器第一名」的差異，結果顯示代理帶來 27.32% 的 Recall@1 增益，證明第二階段代理確實提供了實質價值。第二項消融將同一個代理模組遷移至 PatchFinder_top10 框架，Recall@1 從 24.28% 提升至 39.86%，證明代理並非依賴特定的第一階段檢索器，而是具有通用性。第三項消融在 Qwen 模型家族內更換不同大小的骨幹模型，Recall@1 變化小於 1%，證明效能不依賴於特定模型大小。第四項消融引入第二個模型家族 gpt-oss，結果仍遠高於無代理基準，進一步證明增益來自列表式代理迴圈架構本身，而非特定模型或模型家族。

**Q10：PatchHolmes 在實際漏洞管理工作流程中可以應用於哪些場景？**
A：PatchHolmes 在實際漏洞管理工作流程中有多項重要應用場景。首先，它可用於自動補丁連結補完，解決 GitHub 漏洞資料庫與 NVD 中 60% 到 63% CVE 缺少補丁連結的問題，大幅減少安全性公告中缺失的修補資訊。其次，它可整合至 SBOM 驅動的供應鏈掃描器，自動找出漏洞對應的修復提交，幫助組織判斷其使用的開源軟體版本是否受影響。第三，它可用於受影響版本範圍追蹤，透過找出修復提交來精確界定漏洞影響的版本區間。第四，它可輔助 CVSS 評分流程，提供修復細節作為評分依據。最後，由於 PatchHolmes 運行在本地 Git 儲存庫上且無需外部 API，企業可在內部部署以處理敏感的私有儲存庫漏洞。

**Q11：從產品化的角度來看，PatchHolmes 有哪些重要的設計考量？**
A：從產品化角度來看，PatchHolmes 有多項重要的設計考量。第一，成本可控性：系統運行在凍結的開放權重模型上，無需微調或付費外部搜尋 API，這使得處理成本不會隨 CVE 數量線性成長，適合大規模部署。第二，部署簡便性：整個系統在本地 Git 儲存庫上運行，企業可在內部基礎設施上部署，無需將程式碼或漏洞資訊傳送至外部服務，保護了智慧財產與隱私。第三，無需每個儲存庫微調：傳統方法需要針對每個儲存庫進行微調，而 PatchHolmes 的凍結模型設計省去了這項繁重工作。第四，可解釋性：代理最終會提交一個最佳提交並附帶推理過程，使用者能理解為何選擇該提交。第五，效率：每個 CVE 僅需一次代理對話，相較於 Favia 的 10 次呼叫，推理成本大幅降低。

**Q12：PatchHolmes 對漏洞管理與資安研究領域可能產生哪些影響？**
A：PatchHolmes 對漏洞管理與資安研究領域可能產生多項深遠影響。在實務層面，它能大幅加速 CVE 補丁連結的補完工作，緩解 NVD 維護者積壓的問題，使安全性公告能更快、更完整地提供修補資訊。在研究層面，它提出的列表式選擇（listwise selection）框架為補丁檢索乃至其他檢索任務提供了新範式，證明了代理式閉迴圈設計相較於開放迴圈評分器的優勢。在產業層面，由於其無需微調、無需付費 API 的特性，使得中小型企業與開源社群也能部署先進的補丁檢索能力，縮小了資源落差。在標準制定層面，PatchHolmes 的成功可能促使漏洞資料庫（如 NVD、GitHub Advisory Database）考慮整合類似的自動化工具，提升元資料整理的效率與品質。

**Q13：PatchHolmes 存在哪些已知的限制？**
A：PatchHolmes 存在幾項已知的限制。第一，雖然代理從 100 個候選中選擇性讀取 3 到 10 個提交，但對於某些極為困難的案例，可能需要讀取更多提交才能找到正確答案，而目前的設計限制了讀取數量。第二，代理的效能雖然在 Qwen 家族內更換模型時變化小於 1%，但對於某些極端困難的 CVE（如描述極為模糊或修復極為隱晦的情況），仍可能失敗。第三，雖然系統無需付費外部 API，但仍需要足夠的本地運算資源來運行 LLM，對於資源極為有限的環境可能構成部署障礙。第四，代理的推理過程雖然提供了一定可解釋性，但其決策仍依賴 LLM 的內部判斷，可能存在難以預測的失敗模式。第五，目前的評估主要集中在 GitHubAD 資料集，對於其他類型的漏洞資料庫或私有儲存庫的泛化能力仍需進一步驗證。

**Q14：PatchHolmes 在哪些情況下可能會失敗？**
A：PatchHolmes 在幾種情況下可能會失敗。第一，當 CVE 描述極為模糊或缺乏關鍵技術細節時，代理可能難以從候選清單中識別出真正的修復提交，因為缺乏足夠的線索進行匹配。第二，當修復提交涉及大規模重構或多個不相關變更時，代理可能難以判斷哪些變更才是真正的安全修復。第三，當多個候選提交都涉及類似的程式碼區域時，代理可能難以區分哪一個才是真正的修復，特別是當修復涉及細微的邏輯變更時。第四，對於某些冷門或文件極少的儲存庫，代理可能缺乏足夠的背景知識來理解 CVE 描述與提交之間的語意關聯。第五，當第一階段檢索器的 top-100 中根本沒有包含正確提交時，無論代理多麼聰明都無法找到答案，這凸顯了第一階段檢索器品質的重要性。

**Q15：PatchHolmes 未來有哪些可能的發展方向？**
A：PatchHolmes 未來有多項可能的發展方向。第一，擴展第一階段檢索器的能力，例如整合更多檢索信號（如程式碼結構相似度、符號執行結果）或採用更大規模的稠密檢索模型，以提高 top-100 的召回率。第二，豐富代理的工具集，例如加入靜態分析、動態測試或符號執行工具，讓代理不僅能讀取差異，還能實際執行程式碼來驗證修復假設。第三，引入多代理協作機制，例如讓不同代理從不同角度分析候選，再透過投票或討論機制選出最終答案。第四，擴展到其他漏洞相關任務，如漏洞嚴重性評估、漏洞利用程式碼生成、受影響版本範圍預測等。第五，結合人類專家的反饋進行線上學習或強化學習，讓系統能從錯誤中持續改進。第六，針對特定領域（如核心系統、嵌入式系統、機器學習模型）進行專門化，以處理不同類型漏洞的特殊挑戰。

## 實務應用指南

### 適用場景

1. **漏洞公告資料庫補完**：NVD 與 GitHub Advisory Database 中約 60%–63% 的 CVE 缺少補丁連結，安全研究團隊可將 PatchHolmes 部署為批次補完管線，每日掃描新增 CVE 並自動回填 commit 識別碼，緩解維護者積壓問題。

2. **SBOM 驅動的供應鏈風險評估**：在 SBOM 掃描器（如 Snyk、Dependency-Track）下游接入 PatchHolmes，當掃描器回報某個 OSS 套件存在 CVE 時，自動定位上游修復 commit，產出可驗證的修補證據，協助企業判斷是否需要升級或套用 backport。

3. **CVE 積壓清理服務**：商業漏洞情報廠商（如 VulnCheck、Risk Based Security）可將 PatchHolmes 整合進自家平台，作為「補丁連結補完」API 對外收費，特別針對揭露多年仍未修補的長尾 CVE（如 CVE-2013-1814 案例）。

4. **內部紅隊與弱點管理平台**：企業內部 SOC 或弱點管理平台（如 Tenable、Qualys）可將 PatchHolmes 作為「CVE-to-commit 對映引擎」，讓分析師在收到 CVE 告警時直接看到修復程式碼片段，加速 triage 決策。

5. **OSS 維護者的漏洞回應自動化**：大型開源專案（如 Kubernetes、Linux kernel）的維護團隊可反向使用 PatchHolmes，自動比對外部揭露的 CVE 與自家 commit 歷史，確認是否已有修復、是否需要新增安全性公告。

### 實作前置條件

**資料需求**
- 目標儲存庫的完整 Git 歷史（本地 clone），需包含 commit message、檔案 diff、作者與時間戳記。
- CVE 描述資料集（建議從 GitHub Advisory Database 或 NVD JSON Feed 取得），每筆至少包含 CVE ID、描述、受影響套件與儲存庫座標。
- 評估用金標準資料集（GitHubAD 8,401 筆 CVE，或自建標註）以驗證 Recall@1。

**運算資源**
- 一張具備 ≥24GB VRAM 的 GPU（如 A100 40GB、L40S、RTX 4090），用於承載 Qwen3-Embedding-8B（密集檢索）與 Qwen3 系列 LLM（代理推理）。
- 至少 64GB 系統記憶體與 1TB SSD，用於建置 BM25 索引與 FAISS 向量索引。
- 若使用 gpt-oss 系列模型，需額外確認其推論框架（如 vLLM、SGLang）的相容性。

**技能門檻**
- 熟悉倒排索引（BM25）、向量檢索（FAISS）與 Reciprocal Rank Fusion（RRF, k=60）混合檢索管線。
- 具備 LLM Agent 開發經驗，建議使用 OpenHands SDK 或類似框架，能定義工具（tool schema）並管理多輪對話。
- 理解 Git 內部結構（packfile、commit graph），能從本地儲存庫萃取 diff 並做分塊渲染。
- 基本的提示工程（prompt engineering）能力，特別是設計 list_candidates 的單行 manifest 格式。

### 實作步驟建議

**步驟一：建置 Phase 1 混合檢索器**
1. 對目標儲存庫的所有 commit 萃取四個欄位：message、diff、reserve date、publish date。
2. 以 BM25 分別對 message 與 diff 建立倒排索引；同時使用 Qwen3-Embedding-8B 對 message+diff 拼接文本編碼為向量，存入 FAISS 索引。
3. 設定三路召回（BM25-msg、BM25-diff、Dense FAISS），以 RRF（k=60）融合並產出 Top-100 候選名單。
4. 驗證金標準 commit 是否落在 Top-100 內（目標 MRR@100 應高於 0.5）。

**步驟二：設計 Phase 2 代理工具組**
1. 實作四個預算受限工具：
   - `list_candidates`：回傳 100 筆候選的單行 manifest（hash、message 摘要、檔案數）。
   - `read_commit`：回傳 commit message、檔案清單與 8K token 預算的 diff 渲染。
   - `read_file_diff`：針對單一檔案提供 16K token 預算的完整 diff。
   - `submit_answer`：提交最終 `<commit_hash, reasoning>` 並終止對話。
2. 設定代理最大迭代次數（建議 max_iter=15），並實作觀察-動作迴圈（observation → next action）。
3. 設計 system prompt，明確指示代理「列表式比較」而非「逐點評分」，並提供 CVE 描述與候選清單。

**步驟三：選擇 LLM 主幹並凍結**
1. 預設採用 Qwen3 系列（如 Qwen3-8B、Qwen3-14B），論文顯示同家族內切換 Recall@1 變動 <1%。
2. 若需更高穩健性，可改用 gpt-oss 系列驗證跨家族泛化能力。
3. 嚴格凍結模型權重，不進行任何微調，以維持可重現性與部署成本可控。

**步驟四：批次執行與評估**
1. 對每筆 CVE 啟動一次代理對話（one conversation per CVE），記錄工具呼叫序列與最終答案。
2. 計算 Recall@1、Recall@5、Recall@10，並與 Favia、IRCoT、PatchFinder_top10 比較。
3. 統計平均工具呼叫次數（論文觀察為 3–10 次）與單 CVE 端對端延遲，作為成本估算依據。

**步驟五：產品化封裝**
1. 將 Phase 1 與 Phase 2 包裝為 REST API（`POST /v1/patch_retrieval`，body 為 CVE 描述與 repo 路徑）。
2. 加入結果快取層（Redis），對相同 CVE 描述直接回傳歷史答案。
3. 串接監控（Prometheus + Grafana），追蹤 Recall、延遲、token 用量與代理迭代次數分佈。

### 潛在風險與注意事項

**風險一：代理陷入無效迴圈或 token 預算超支**
- **現象**：代理反覆呼叫 `read_commit` 卻未提交答案，或單次對話消耗過多 token。
- **緩解**：強制設定 max_iter=15 與單 CVE token 上限；當代理連續 3 次未取得新資訊時，自動觸發 `submit_answer` 並要求其基於目前觀察做最佳猜測。

**風險二：長 diff 截斷導致錯失關鍵修復線索**
- **現象**：平均 15K token 的 diff 超過 `read_commit` 的 8K 預算，代理可能看不到真正的修復片段。
- **緩解**：實作智慧分塊（依檔案或 hunks 切分），並讓代理透過 `read_file_diff` 針對可疑檔案深入；同時在 `list_candidates` 的 manifest 中標註 diff 大小，引導代理優先檢視中等長度的 commit。

**風險三：點對點評分幻覺與平手決勝失效**
- **現象**：如同 Favia 在 CVE-2015-9251 的案例，代理可能對多個候選給出相似信心而無法決勝。
- **緩解**：在 system prompt 中明確禁止「給每個候選打分數」，改要求「比較並指出唯一最佳者」；若代理回報平手，強制其再讀一次差異化檔案。

**風險四：儲存庫規模造成的索引成本**
- **現象**：49% 的 CVE 對應儲存庫超過 5,000 commits，全庫嵌入成本高昂。
- **緩解**：採用增量索引（僅索引最近 N 個 commit 或符合 CVE 時間窗口的 commit）；使用 FAISS IVF 或 HNSW 加速向量檢索；對超大 monorepo 改採儲存庫切片策略。

**風險五：缺乏金標準時的評估偏差**
- **現象**：自建評估集可能標註不全，導致 Recall@1 被低估。
- **緩解**：以 GitHubAD 8,401 筆作為基準，並對自家資料集做人工抽樣驗證；同時報告 Recall@10 而非僅 Recall@1，以緩解標註雜訊。

**風險六：LLM 主幹版本漂移**
- **現象**：升級 Qwen3 至新版後，代理行為可能改變。
- **緩解**：固定模型版本與 checkpoint hash；在 CI 中加入回歸測試（固定 CVE 子集，監控 Recall@1 變動 <1%）。

### 與其他技術的整合建議

1. **與漏洞掃描器整合**：在 Snyk、Dependabot、Trivy 的輸出下游接入 PatchHolmes API，將「CVE 告警」轉為「修復 commit + diff 摘要」，可直接嵌入掃描報告的「Remediation」段落。

2. **與 SBOM 工具整合**：與 CycloneDX、SPDX 格式的 SBOM 對接，當 SBOM 標記某元件存在 CVE 時，自動查詢 PatchHolmes 並回填 `<vulnerability><patches><commit>` 欄位，提升 SBOM 的可執行性。

3. **與 CI/CD 整合**：在 GitHub Actions 或 GitLab CI 中加入 `patch-link-check` job，當 PR 修復某 CVE 時，自動驗證 commit message 是否包含 CVE ID，並呼叫 PatchHolmes 反向確認該 commit 確實修復該 CVE。

4. **與知識圖譜整合**：將 PatchHolmes 輸出餵入漏洞知識圖譜（如 OSV.dev、VulnDB），建立「CVE ↔ commit ↔ 檔案 ↔ 函式」的多層映射，支援更細粒度的影響範圍分析。

5. **與 RAG 系統整合**：在企業內部安全知識庫（如基於 LangChain 或 LlamaIndex 的 RAG）中，將 PatchHolmes 的 `read_commit` 結果作為檢索增強來源，讓分析師能用自然語言查詢「CVE-XXXX 的修復涉及哪些函式」。

6. **與事件回應平台整合**：與 TheHive、Tines 等 SOAR 平台串接，當高嚴重性 CVE 告警觸發時，自動呼叫 PatchHolmes 取得修復 commit，並在 playbook 中產生「套用修補」或「建立 backport branch」的工作項目。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的 Figure 1 與 CVE-2015-9251 範例，直觀理解「為什麼逐點評分會失敗」與「列表式選擇為什麼有效」，再回頭看術語；Phase 1 的 BM25 + Dense + RRF 是經典混合檢索套路，可參考 Elasticsearch 官方文件補強背景；Phase 2 的代理部分先理解「工具呼叫迴圈」的概念即可，細節可留待實作時再深究。

**給 AI 工程師**：重點關注 Phase 2 的四個工具設計與預算分配（8K / 16K token）、OpenHands SDK 的整合方式、以及 system prompt 如何引導代理做列表式比較；建議直接複製論文的工具 schema 與 prompt 模板，在自家儲存庫上跑通端對端流程，再針對長 diff 與大型 monorepo 場景做優化；同時關注代理迭代次數與 token 用量的監控，這是產品化的關鍵成本指標。

**給研究者**：本文的核心貢獻在於「listwise selection」對「pointwise scoring」的經驗性勝出，以及「frozen open-weight model + local Git」的可重現設定；建議從消融實驗切入，特別是「同候選集合下代理 vs. 取 Top-1」帶來的 27.32% Recall@1 增益，以及跨 LLM 家族（Qwen vs. gpt-oss）的穩定性驗證；可進一步探索的方向包括：不同代理框架（ReAct、Reflexion）的比較、工具預算的理論最優分配、以及將此範式遷移至其他「長文檔 + 短查詢」的檢索任務（如法律判決檢索、學術論文對應）。

**給產品經理**：PatchHolmes 解決的是一個高 ROI 的真實痛點——60%–63% 的 CVE 缺少補丁連結，且 NVD 本身有人力積壓；產品的核心價值主張是「在本地、可重現、無需付費 API 的條件下，自動補完 CVE-to-commit 對映」；商業模式可考慮 SaaS（按 CVE 計費）、私有部署（授權給大型企業 SOC）、或資料服務（向漏洞情報廠商提供補丁連結補完 API）；關鍵風險是 LLM 推理成本與代理延遲，建議在 MVP 階段先以 Recall@10 為主打指標（容錯更高），再逐步推廣到 Recall@1 的高精度場景。
