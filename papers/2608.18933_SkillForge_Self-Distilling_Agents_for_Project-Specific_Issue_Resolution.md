# SkillForge：專案特定問題解決的自蒸餾智能體

**原文標題：** SkillForge: Self-Distilling Agents for Project-Specific Issue Resolution  
**作者：** Silin Chen、Han Li、Xiaodong Gu 等 5 位作者  
**發布日期：** 2026-08-19

## ⚡ TL;DR

現有智能體缺乏專案特定知識，且受限於歷史軌跡或高昂的測試時探索成本。
SkillForge 重寫測試覆蓋核心功能以合成議題，並蒸餾出實體導向的雙層技能。
在 SWE-bench 兩基準上，SkillForge 提升開源與閉源模型的議題修復率。

---

## 摘要翻譯

基於大型語言模型（Large Language Model, LLM）的智能體在自動化軟體問題解決（Automated Software Issue Resolution）方面展現出卓越的能力，然而它們在解決特定儲存庫（repository）中的問題時經常遭遇困難，原因在於缺乏專案特定知識（Project-specific Knowledge）。現有的自我演化方法（Self-evolving Approaches）從儲存庫歷史（Repository History）或線上修復軌跡（Online Repair Trajectories）中獲取這類知識，但它們若非依賴可取得的問題解決訊號（Issue-resolution Signals），就是每個問題都需付出可觀的測試時探索成本（Test-time Exploration Cost）。在本文中，我們提出 SkillForge，一個自蒸餾框架（Self-distillation Framework），能主動從儲存庫本身獲取專案特定知識。SkillForge 不等待真實問題暴露出專案特定知識缺口，而是透過重新實作（Re-implementation）儲存庫中受測試覆蓋的核心功能（Test-covered Core Functionalities）來合成專案特定問題（Synthetic Issues）。透過解決這些合成問題，SkillForge 將可複用的專案特定知識蒸餾為實體導向技能（Entity-grounded Skills），並與相關儲存庫實體（Repository Entities）建立關聯，供後續問題解決之用。使用開源模型（Open-source Models）與閉源模型（Closed-source Models）進行的大量實驗顯示，SkillForge 相較於強大的基線（Baselines）方法，能持續提升問題解決效能。這些結果顯示，在解決真實問題之前主動獲取專案特定知識，能顯著改善下游軟體問題解決（Downstream Software Issue Resolution）。

### 核心貢獻（3～5點）
- 提出 SkillForge，一個能主動從儲存庫本身獲取專案特定知識的自蒸餾框架，無需依賴真實歷史問題或昂貴的線上探索。
- 透過重新實作受測試覆蓋的核心功能來合成專案特定問題，使模型能在接觸真實議題前即學習儲存庫內部慣例與 API 合約。
- 將解決合成問題所獲得的知識蒸餾為實體導向技能，並與相關儲存庫實體建立關聯，形成可複用的長期知識。
- 在開源模型與閉源模型上均顯示相較於強基線方法能持續提升問題解決效能，驗證主動學習專案知識對下游議題修復的效益。

### 適合對象
本論文最適合對自動化軟體工程、LLM 智能體、自動化程式修復（APR）以及知識蒸餾有興趣的研究人員與工程師閱讀；特別是正在開發儲存庫專屬 AI 程式設計輔助工具、希望解決 LLM 在特定專案上冷啟動問題，或關注如何以低成本方式讓智能體持續自我演化的讀者。

## 深度分析

#### 方法論解析

SkillForge 的核心設計可視為一個「主動式自蒸餾（self-distillation）」迴路，將傳統「等真實 issue 發生後才學習」的典範，轉換為「從儲存庫（repository）本身提煉專案特定知識（project-specific knowledge）」的典範。整體流程可對應圖 1 的四個階段：Project-Specific Issue Synthesis、Issue Resolution Attempt、Skill Distillation、Skill Adaptation。

##### 1. 專案特定合成問題生成（Project-Specific Issue Synthesis）

SkillForge 不等待真實 issue，而是主動從當前儲存庫快照（repository snapshot）中製造「可執行且行為有依據」的合成問題（synthetic issues）。其步驟如下：

- **選取測試覆蓋的核心功能（test-covered core functionalities）**：以現有測試作為錨點，挑選已被測試驗證的程式功能。這確保後續生成的合成問題具備可驗證的 fail-to-pass 測試訊號。
- **追蹤執行軌跡（execution traces）**：針對選定的功能，透過執行追蹤找出共同實現該功能的程式區段，包括跨檔案、跨模組的協調程式碼。
- **受限脈絡下的重新實作（re-implementation under constrained context）**：在保留原始語意的前提下，以不同方式改寫這些協調區段，製造出「看似真實」的缺陷實例。由於改寫範圍受原始執行路徑與測試約束，所生成的問題具備以下特性：
  - 可執行（executable）；
  - 有對應的 fail-to-pass 測試作為驗證標準；
  - 與專案結構、API 合約（API contracts）、隱式執行路徑（implicit execution paths）緊密相關。

這一步是 SkillForge 與傳統資料增強的關鍵差異：合成問題並非隨機注入 bug，而是基於專案內部真實協作邏輯所產生，因此能夠暴露專案特定的慣例與陷阱。

##### 2. 問題解決嘗試（Issue Resolution Attempt）

生成合成問題後，SkillForge 呼叫基礎 SWE agent（例如 Mini-SWE-Agent）嘗試修復。此階段會產生完整的 agent trajectories，包括搜尋（search）、編輯（edit）、測試（test）、生成 patch 等行動序列。無論成功或失敗，這些軌跡都蘊含可蒸餾的知識：
- **成功軌跡**：提供「如何正確修改特定實體」的正面範例；
- **失敗軌跡**：提供「哪些修改會違反專案慣例」的負面教訓與診斷反思。

##### 3. 技能蒸餾（Skill Distillation）

SkillForge 將軌跡中的經驗蒸餾為兩層互補的技能庫（dual-level skill repository）：

- **全域診斷技能集（Global Diagnostic Skill Set, M_ext）**：捕捉可重複使用的專案層級知識，例如：
  - 各實體（entity）的角色與職責；
  - 診斷與導航的推理劇本（reasoning playbooks）；
  - 相關 API 的組合與使用模式。
  這類技能屬於「全域／結構性」知識，適合在解題初期作為宏觀引導。

- **局部介入技能集（Local Intervention Skill Set, M_int）**：記錄與特定儲存庫實體（repository entities，如類別、函式、檔案）綁定的微觀指導，例如：
  - 針對某函式的修改建議；
  - 應避免的常見錯誤（pitfall-avoidance lessons）；
  - 與該實體相關的 API 使用注意事項。
  這類技能屬於「局部／特定性」知識，適合在 agent 接觸到對應實體時即時注入。

透過將軌跡抽象為 entity-grounded skills，SkillForge 把一次性解題經驗轉換為可重複檢索、可累積的專案特定知識。

##### 4. 技能適應（Skill Adaptation）

在下游真實 issue resolution 時，SkillForge 採用兩階段檢索與注入策略：

- **Macro Initialization（宏觀初始化）**：在 agent 開始解題前，先檢索與當前 issue 相關的 M_ext，作為初始專案特定上下文（initial project-specific context）。這相當於讓 agent 在動手前先獲得「專案導覽手冊」。
- **Micro JIT Injection（微觀即時注入）**：在 agent 與儲存庫互動過程中，每當存取特定 API 或實體時，即時檢索並注入對應的 M_int。這種 just-in-time guidance 讓 agent 在需要時才獲得局部建議，避免上下文過載，並確保建議與當前操作高度相關。

整體而言，SkillForge 的方法論可概括為「以合成問題為媒介、以軌跡為原料、以實體為錨點、以雙層技能為表徵」的主動知識累積框架。

#### 實驗數據解讀

論文在兩個主流 benchmark 上進行評估：SWE-bench Verified 與 SWE-bench Pro，並分別使用開源模型 DeepSeek-V3.2 與閉源模型 GPT-5-mini 作為底層 LLM。基礎 agent 為 Mini-SWE-Agent。

##### 1. 主要結果

| Benchmark | 模型 | Mini-SWE-Agent | SkillForge | 絕對提升 |
|---|---|---|---|---|
| SWE-bench Verified | DeepSeek-V3.2 | 66.4% | 72.2% | +5.8% |
| SWE-bench Verified | GPT-5-mini | 55.0% | 60.6% | +5.6% |
| SWE-bench Pro | DeepSeek-V3.2 | — | — | +5.8% |
| SWE-bench Pro | GPT-5-mini | — | — | +4.1% |

註：論文摘要與引言中對 SWE-bench Pro 的絕對 Pass@1 數值未完整列出，但明確報告相對於 Mini-SWE-Agent 的提升幅度。

##### 2. 結果意涵

- **穩定的跨模型提升**：無論是開源模型（DeepSeek-V3.2）或閉源模型（GPT-5-mini），SkillForge 都能帶來約 4–6 個百分點的 Pass@1 提升。這顯示專案特定知識的預先獲取對不同模型皆有互補效果，並非僅對特定模型有效。
- **跨難度 benchmark 的泛化**：SWE-bench Verified 與 SWE-bench Pro 的問題難度與分佈不同，SkillForge 在兩者上均持續改善，表示其技能庫具備一定的泛化能力。
- **超越歷史驅動與線上方法**：論文指出 SkillForge 在所有評估的 history-driven 與 online project-specific knowledge acquisition baselines 中表現最佳。這驗證了「主動從儲存庫本身學習」相較於「依賴歷史 issue」或「測試時高成本探索」的優勢。

##### 3. 潛在的解讀角度

- **冷啟動問題（cold-start problem）的緩解**：提升幅度雖非巨幅，但在已經相當強的基線（如 DeepSeek-V3.2 在 Verified 上已達 66.4%）上仍能穩定進步，顯示專案特定知識確實能填補通用 agent 的知識缺口。
- **成本與效益的權衡**：雖然實驗未詳細報告 token 與時間成本，但 SkillForge 的知識獲取發生在「issue 到達之前」，可攤提（amortize）到後續多個 issue 上，相較於 online 方法的 per-issue 探索成本更具規模經濟。

#### 與現有研究的比較

##### 1. 相對於歷史驅動方法（History-Driven Methods）

代表性方法包括 EvoCoder 與 SWE-Exp，其共同特點是從 historical issues、commits 或 agent trajectories 中蒸餾知識。SkillForge 的差異在於：

- **不依賴歷史 issue-resolution signals**：對於新專案、長尾元件（long-tail components）或尚未被歷史軌跡觸及的 API 組合，歷史方法缺乏學習訊號；SkillForge 則可從當前儲存庫主動生成。
- **覆蓋率可控**：透過測試覆蓋導向的合成，SkillForge 能針對性地暴露核心功能與邊界行為，而非受限於過去 issue 的分佈。

##### 2. 相對於線上探索方法（Online Methods）

代表性方法如 SWE-Exp 的 online 變體，在測試階段針對每個目標 issue 生成額外軌跡以精煉 agent。SkillForge 的優勢包括：

- **降低 per-issue test-time exploration cost**：線上方法需為每個 issue 支付額外的 trajectory、token 與時間成本；SkillForge 將大部分知識獲取前置，後續僅需輕量檢索與注入。
- **知識可累積與重用**：線上方法獲得的指導通常僅對當前 issue 有效；SkillForge 將經驗蒸餾為可重複使用的 skills，形成長期資產。

##### 3. 相對於一般 SWE agents（如 SWE-agent、OpenHands）

這些 agent 本質上是通用儲存庫探索器（generic repository explorer），缺乏專案特定知識。SkillForge 透過 Macro Initialization 與 Micro JIT Injection，為其提供結構化、實體導向的專案先驗，從而減少重複試錯。

##### 4. 限制與潛在弱點

- **測試覆蓋率的依賴**：合成問題的品質與範圍受限於現有測試。若專案測試稀疏或品質不佳，則難以生成有意義的合成 issue。
- **合成問題與真實 issue 的分佈差異**：雖然合成問題基於真實執行路徑，但其缺陷模式可能與人類回報的 issue 不完全一致，存在領域偏移（domain shift）風險。
- **技能蒸餾的品質**：從成功與失敗軌跡中自動萃取 skills，可能引入雜訊或過度擬合特定合成案例。如何驗證技能的可靠性仍具挑戰。
- **計算前置成本**：雖然 per-issue 成本降低，但初始合成與自蒸餾需要額外計算資源，對於極大型儲存庫可能成本可觀。
- **實體粒度的選擇**：entity-grounded skills 的粒度（函式、類別、檔案、模組）會影響檢索效果，論文未深入探討不同粒度的影響。

#### 可重現性評估

##### 1. 開放資源

論文明確指出原始碼與資料已公開於 GitHub：

> https://github.com/cslsolow/SkillForge

這為可重現性（reproducibility）奠定良好基礎。研究者原則上可取得：
- SkillForge 的實作程式碼；
- 用於實驗的資料或資料生成流程；
- 部分設定與腳本。

##### 2. 潛在重現障礙

- **模型權重與 API 存取**：實驗使用 DeepSeek-V3.2（開源模型）與 GPT-5-mini（閉源模型）。前者權重可取得，後者需 OpenAI API 存取權限與費用。
- **計算資源**：合成問題生成、軌跡收集、技能蒸餾與下游評估均涉及大量 LLM 呼叫，重現完整實驗需要可觀的 GPU 或 API 預算。
- **SWE-bench 環境**：執行 SWE-bench Verified 與 SWE-bench Pro 需要正確配置 Docker、測試環境與執行權限，部分專案依賴特定版本的外部套件。
- **超參數與提示設計**：論文未在提供的摘要與引言中詳述提示模板（prompt templates）、技能檢索閾值、合成問題數量等關鍵超參數，這些細節將影響重現精度。
- **隨機性與種子**：LLM-based agent 的輸出具有隨機性，若論文未提供種子與多次執行結果，重現時可能出現變異。

##### 3. 可重現性建議

為提升可重現性，建議作者補充：
- 詳細的超參數設定與提示模板；
- 每個 benchmark 的完整執行日誌與成本統計；
- 多次執行的標準差或區間估計；
- 明確的環境設定檔（如 Dockerfile、requirements.txt）。

#### 未來研究方向

##### 1. 擴展合成問題的覆蓋範圍

目前 SkillForge 以 test-covered core functionalities 為起點。未來可探索：
- **無測試區域的主動探索**：結合靜態分析、符號執行或模糊測試（fuzzing）生成測試，擴展至未被測試覆蓋的長尾元件。
- **更真實的缺陷模式**：引入從真實 bug 資料庫（如 Bug2Commit、ManySStuBs4J）學到的缺陷分佈，使合成問題更接近人類引入的錯誤。

##### 2. 技能庫的動態演化與版本控制

- **技能更新機制**：隨著儲存庫演進，舊 skills 可能失效。可設計基於測試回歸或版本差異的技能失效偵測與更新機制。
- **跨版本遷移**：研究 skills 在不同版本間的遷移學習，減少每次釋出後重新蒸餾的成本。

##### 3. 多儲存庫與跨專案遷移

- **通用專案知識與特定知識的分離**：將 skills 拆解為「跨專案通用」與「專案特定」兩層，促進知識在相似專案間遷移。
- **聯邦式技能學習**：在多個儲存庫上聯合蒸餾 skills，建立可共享的軟體工程知識庫。

##### 4. 與檢索增強生成（RAG）的深度融合

- **更精細的檢索器**：訓練專門的 dense retriever 或 cross-encoder，提升 M_ext 與 M_int 的檢索準確率。
- **動態技能組合**：根據 issue 描述與當前 agent 狀態，動態決定要注入哪些 skills，而非僅依賴實體匹配。

##### 5. 多智能體協作與技能驗證

- **專家化 agent**：讓不同 agent 分別負責診斷、修復、測試與技能驗證，透過多智能體協作提升技能品質。
- **自動化技能驗證**：建立獨立驗證機制，確保蒸餾出的 skills 確實能提升後續 issue resolution，並過濾雜訊。

##### 6. 理論與可解釋性分析

- **知識增益量化**：發展指標衡量 skills 對 agent 決策的實際貢獻，例如 ablation study 中區分 M_ext 與 M_int 的個別效益。
- **錯誤模式分析**：深入分析 SkillForge 仍失敗的案例，找出專案特定知識無法覆蓋的瓶頸（如需求理解、外部依賴、非功能性需求）。

##### 7. 成本效益最佳化

- **選擇性蒸餾**：根據儲存庫規模與 issue 到達頻率，決定是否執行完整 SkillForge 流程，或僅針對高風險模組進行蒸餾。
- **輕量化技能表示**：探索將 skills 壓縮為更緊湊的表示（如向量或結構化規則），降低檢索與注入開銷。

整體而言，SkillForge 為「主動獲取專案特定知識」開闢了一條有潛力的路徑，未來研究可在覆蓋範圍、技能演化、跨專案遷移與成本效益等面向進一步深化。

## 論文問答

**Q1：SkillForge 主要想解決什麼問題？**

A：SkillForge 旨在解決 LLM 軟體工程智能體在面對特定儲存庫時的「冷啟動」問題，也就是智能體因缺乏專案特定知識而必須從頭摸索儲存庫結構與慣例的困境。由於真實專案存在隱式執行路徑、API 合約與模組間的耦合關係，沒有先驗知識的代理往往會反覆落入相同的專案特定陷阱。這種情況使得即使基礎模型能力很強，也只能退化成通用的儲存庫探索器，顯著降低問題修復的效率與正確率。

**Q2：現有的自我演化方法為何不足以解決這個問題？**

A：現有方法主要分為歷史驅動與線上探索兩類，但兩者都屬於被動式學習。歷史驅動方法如 EvoCoder 與 SWE-Exp 受限於過去 issue、commit 與軌跡的豐富度與覆蓋率，對於未被歷史軌跡觸及的長尾元件幾乎無法提供學習訊號。線上方法雖然降低對歷史的依賴，卻需要在每個目標 issue 的測試階段付出大量的軌跡、token 與時間成本，而且指導知識只有在 issue 出現後才能取得。

**Q3：為什麼專案特定知識對自動化議題修復如此重要？**

A：因為正確的修補程式不只要修復表面錯誤，還必須維護儲存庫特定的 API 合約、命名慣例與模組間的隱式依賴關係。缺乏這些知識的智能體在診斷與修改時會不斷進行重複的試錯，導致時間浪費與錯誤累積。相對地，一旦掌握可重複使用的專案特定知識，智能體就能像熟悉專案的開發者一樣，快速定位問題並提出符合專案風格的修補。

**Q4：SkillForge 的核心方法流程是什麼？**

A：SkillForge 是一個自蒸餾框架，它主動從當前儲存庫本身合成專案特定的合成問題，而非等待真實 issue 出現。具體而言，它從被測試覆蓋的核心功能出發，追蹤執行路徑以找出協同實現同一功能的程式區段，並在受限制的上下文下重新實作這些區段，從而產生可執行且由測試驗證行為的合成問題。接著讓 SWE 智能體解決這些合成問題，再從成功與失敗的軌跡中蒸餾出可重複使用的實體導向技能。

**Q5：SkillForge 的雙層技能庫各自扮演什麼角色？**

A：SkillForge 將蒸餾出的知識組織為全局診斷技能集（M_ext）與局部介入技能集（M_int）兩個互補層級。M_ext 負責捕捉專案層級的可重用知識，例如實體角色、推理劇本與相關 API 組合，用於在解題前進行宏觀初始化。M_int 則記錄與特定儲存庫實體綁定的修改指引與避坑經驗，並在智能體存取對應實體時以即時注入（JIT）方式提供微觀指導。

**Q6：與先前方法相比，SkillForge 的關鍵創新在哪裡？**

A：SkillForge 最大的創新在於將「被動等待歷史軌跡」轉變為「主動從儲存庫本身蒸餾專案知識」，在真實 issue 到來前就完成了知識準備。它不需要依賴可用的歷史問題解決訊號，也避免了線上方法對每個目標 issue 都進行昂貴測試時探索的開銷。此外，透過將技能與儲存庫實體緊密關聯，SkillForge 能夠在智能體實際互動程式碼的當下提供高度相關的指引。

**Q7：實驗使用了哪些基準與模型？**

A：論文使用 SWE-bench Verified 與 SWE-bench Pro 兩個具有代表性的軟體問題修復基準進行評估。模型方面同時採用開源模型 DeepSeek-V3.2 與閉源模型 GPT-5-mini，以驗證方法的通用性。底層智能體則以 Mini-SWE-Agent 為基礎，並與多個歷史驅動與線上專案知識獲取基線進行比較。

**Q8：SkillForge 取得了哪些主要量化結果？**

A：在 SWE-bench Verified 上，SkillForge 分別達到 DeepSeek-V3.2 72.2% 與 GPT-5-mini 60.6% 的 Pass@1，相較 Mini-SWE-Agent 分別提升 5.8 與 5.6 個百分點。在更具挑戰性的 SWE-bench Pro 上，也分別進步 5.8 與 4.1 個百分點。整體而言，SkillForge 在兩個基準與兩種模型上均穩定優於所有評估的強基線方法。

**Q9：這些結果對 SkillForge 的設計選擇有何啟示？**

A：實驗結果顯示，主動在真實 issue 出現前獲取專案特定知識，能顯著改善下游軟體問題解決的表現。全局診斷技能提供了專案層級的宏觀先驗，減少智能體在儲存庫中盲目探索的時間；局部介入技能則透過即時注入降低反覆試錯的成本。雙層設計與實體導向的檢索機制相輔相成，說明知識的組織形式與使用時機同樣重要。

**Q10：SkillForge 在哪些實際場景中最具價值？**

A：SkillForge 特別適合歷史 issue 稀少或全新的專有儲存庫，因為這些場景下歷史驅動方法難以取得足夠學習訊號。它也能作為 CI/CD 流程中的預備步驟，在真實錯誤回報湧入前先為智能體建立專案知識庫。此外，對於需要快速讓自動化修復工具上線的企業團隊，SkillForge 可顯著縮短智能體熟悉專案的時間。

**Q11：部署 SkillForge 時需要考慮哪些產品工程問題？**

A：首先必須評估合成問題生成與技能蒸餾所需的一次性計算成本，並設計有效的排程與資源配置策略。其次，技能庫的儲存、索引與檢索效率會直接影響下游 issue 解決的延遲，需要隨著程式碼演進持續更新。最後，還需建立品質監控機制，避免錯誤或過時的技能被注入智能體，反而干擾修復決策。

**Q12：SkillForge 可能對軟體工程智能體領域帶來什麼影響？**

A：SkillForge 推動了從「被動反應式學習」到「主動預備式學習」的典範轉移，強調在面對真實任務前先建立專案記憶。它示範了如何將解題軌跡轉化為結構化、可檢索且與程式實體綁定的技能，為未來的 SWE 智能體提供了一種新的知識表示方式。長遠來看，這類自蒸餾機制可能成為自動化軟體維護系統的標準前置處理流程。

**Q13：SkillForge 有哪些可預見的限制？**

A：SkillForge 高度依賴現有測試對核心功能的覆蓋，未被測試觸及的程式區域難以生成有意義的合成問題。合成問題的品質與多樣性也受限於重新實作時的約束條件，可能無法完整模擬真實 issue 的分佈。此外，蒸餾出的技能品質根本上仍受制於底層 SWE 智能體解決合成問題的能力，若智能體在合成階段表現不佳，後續技能也會受到污染。

**Q14：SkillForge 可能在哪些情況下失效或表現不佳？**

A：當真實 issue 涉及測試未覆蓋的長尾元件或邊緣使用情境時，SkillForge 因缺乏對應合成經驗而難以提供有效指引。如果儲存庫在技能蒸餾後發生大幅重構，已儲存的實體導向技能可能變得過時甚至誤導智能體。另外，若合成問題過於簡單或與真實缺陷分佈差異過大，蒸餾出的知識可能無法遷移到下游任務。

**Q15：未來可以朝哪些方向延伸 SkillForge？**

A：未來可以結合 SkillForge 與歷史驅動方法，讓主動蒸餾的知識與真實修復軌跡互補，進一步提升覆蓋率。也可以研究增量式技能更新機制，使技能庫能隨著程式碼變動自動演化，避免知識陳舊。此外，探索跨專案技能遷移、更強大的合成問題生成策略，以及在更多模型與應用領域上的評估，都是值得深入的方向。

## 實務應用指南

### 適用場景

1. **新團隊接手大型或遺留專案**  
   當團隊剛接手一個缺乏完整歷史問題（historical issues）與修復軌跡（agent trajectories）的儲存庫（repository）時，SkillForge 能主動從現有測試覆蓋的核心功能（test-covered core functionalities）合成問題，快速累積專案特定知識（project-specific knowledge），縮短冷啟動（cold-start）時間。

2. **新產品或快速迭代專案的真實 issue 尚未累積**  
   對於上線初期、真實缺陷樣本稀少的產品，SkillForge 可在真實問題到來前，先透過重新實作（re-implementation）產生合成問題（synthetic issues），讓軟體工程智能體（SWE agents）預先學習 API 合約（API contracts）與隱式執行路徑（implicit execution paths）。

3. **企業內部共用框架或平台團隊**  
   當多個產品線共用自訂框架、內部 API 或特定編碼慣例時，SkillForge 可將這些重複出現的專案級知識蒸餾（knowledge distillation）為實體導向技能（entity-grounded skills），供不同專案的下游軟體問題解決（downstream software issue resolution）重複使用。

4. **CI/CD 中的預防性品質閘道**  
   在持續整合流程中，SkillForge 可作為上線前的自動化環節：定期針對核心功能生成合成問題並驗證修復能力，同時更新技能庫，讓後續真實 issue 的修復更快、更準。

5. **長尾元件或低活躍模組的知識補強**  
   對於歷史軌跡較少觸及的長尾元件（long-tail components），SkillForge 可透過覆蓋率導向的程式碼重寫補強學習訊號，避免智能體在這些區域重複落入相同的專案特定陷阱。

### 實作前置條件

**資料條件**
- 可執行的儲存庫快照，包含穩定的測試套件與足夠的測試覆蓋率。
- 能夠產生執行追蹤（execution traces），以識別協同實作同一功能的程式碼區段。
- 具備 fail-to-pass 測試機制，讓合成問題可被客觀驗證。

**運算條件**
- 可呼叫的大型語言模型（LLM）API，建議同時評估開源模型（open-source models）與閉源模型（closed-source models）。
- 執行 SWE agents（如 Mini-SWE-Agent）的容器化環境，包含檔案系統、測試執行與修補程式（patches）驗證能力。
- 技能儲存與檢索基礎設施，例如向量資料庫或圖資料庫，用於儲存雙層技能集（M_ext 與 M_int）並建立與儲存庫實體（repository entities）的對應。

**技能條件**
- 熟悉軟體工程智能體（software engineering agents）的運作流程，包括搜尋、編輯、測試與提交修補程式。
- 具備測試覆蓋率分析、程式碼重寫提示工程（prompt engineering）與軌跡分析能力。
- 能夠設計與維護檢索增強（RAG）流程，將技能適時注入智能體上下文。

---

### 實作步驟建議

1. **盤點與選取核心功能**  
   使用測試覆蓋率工具找出被現有測試涵蓋、行為穩定的核心功能，優先選取跨多個儲存庫實體協作、且蘊含專案特定慣例的區域。

2. **生成可執行的合成問題**  
   根據執行追蹤識別共同實作同一功能的程式碼區段，在受限上下文下對這些區段進行重新實作，產生行為錯誤但可編譯、可測試的合成問題，並確保對應的 fail-to-pass 測試能正確觸發。

3. **自動化解決合成問題並收集軌跡**  
   部署 SWE agent 對每個合成問題進行修復嘗試，無論成功或失敗都完整記錄智能體軌跡（agent trajectories），作為後續知識蒸餾的素材。

4. **蒸餾雙層技能庫**  
   從軌跡中萃取：
   - **全局診斷技能集（M_ext）**：專案級診斷與導航知識，例如實體角色、推理劇本與相關 API。
   - **局部介入技能集（M_int）**：針對特定實體的修改指引與避坑經驗，包含成功修復經驗與失敗反思。

5. **建立技能儲存與索引**  
   將技能以實體導向技能的形式存入技能庫，並為每個技能標註相關的儲存庫實體、測試案例與適用情境，支援後續檢索與即時注入。

6. **在下游問題解決中啟用技能**  
   - **Macro Initialization**：在處理新 issue 前，先檢索並注入相關的 M_ext 作為初始專案上下文。
   - **Micro JIT Injection**：當智能體在解題過程中存取特定 API、類別或函式時，即時注入對應的 M_int 指引。

7. **持續迭代與維護**  
   隨著真實 issue 的解決，不斷比對、更新與淘汰過時技能；定期重新生成合成問題，以涵蓋新加入的核心功能與程式碼變更。

---

### 潛在風險與注意事項

- **合成問題與真實問題分布不一致**  
  若重新實作產生的合成問題過度偏離真實缺陷模式，蒸餾出的技能可能無法有效遷移。建議透過執行追蹤與測試約束來保持行為真實性，並在真實 issue 基準上定期驗證。

- **技能幻覺或過時**  
  大型語言模型在蒸餾軌跡時可能產生錯誤或過時的指導。應為技能加上版本標註、來源軌跡與置信度，並結合人工抽樣審查。

- **成本與延遲**  
  合成問題生成與自動修復需要大量 token、時間與計算資源。建議設定預算上限、優先處理高覆蓋高風險模組，並將技能庫建置視為一次性或週期性投資。

- **授權與資料安全**  
  重新實作與軌跡記錄可能涉及授權程式碼或敏感業務邏輯。需確認儲存庫授權條款，並對技能庫與軌跡資料實施存取控制。

- **過度擬合合成問題**  
  智能體可能學會應對合成問題的特定模式，卻在真實 issue 上表現下滑。應保留獨立的真實 issue 驗證集，並監控線上修復成功率。

### 與其他技術的整合建議

- **與 Issue Tracking 系統整合**  
  將 SkillForge 接入 Jira、GitHub Issues 或 GitLab Issues，在問題分類（triage）後自動觸發相關技能檢索，並將修復結果回寫至工單。

- **與 CI/CD 管線整合**  
  在 Pull Request 階段觸發 SkillForge：針對變更範圍生成合成問題、驗證既有技能是否仍然有效，並在合併前更新技能庫。

- **與 RAG 與向量資料庫整合**  
  將 M_ext 與 M_int 視為專案知識來源，與現有文件、程式碼嵌入共同建立統一檢索層，強化智能體的上下文理解。

- **與 IDE 或編輯器插件整合**  
  在開發者瀏覽或修改特定儲存庫實體時，即時彈出對應的局部介入技能（M_int），作為程式碼提示或潛在陷阱警告。

- **與可觀測性工具整合**  
  將線上異常、錯誤日誌或測試失敗模式轉化為新的合成問題輸入，持續擴充技能庫並貼近實際運行情境。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦「冷啟動問題」與「合成資料」這兩個核心概念，把 SkillForge 理解為「讓 AI 在正式修 bug 之前，先透過自己出題、自己解題來讀懂這個專案的慣例」，再回頭對照論文中的流程圖與實驗結果。

- **AI 工程師**：請重點閱讀雙層技能庫的設計——全局診斷技能集（M_ext）與局部介入技能集（M_int）如何被檢索、如何進行 Just-in-Time 注入，以及合成問題生成與軌跡蒸餾的提示工程細節，這些是落地時最需要調校的環節。

- **研究人員**：可從主動學習、自我對弈（self-play）、知識蒸餾與長期記憶的角度延伸本工作，特別值得探討的是合成問題分布與真實 issue 分布的對齊、技能庫的可解釋性，以及在不同規模儲存庫上的泛化邊界。

- **產品經理**：請把關注點放在商業價值與成本權衡：SkillForge 能縮短新專案導入時間、降低每個 issue 的測試時探索成本（test-time exploration cost），但評估 ROI 時必須同時納入合成階段的一次性投入與後續節省的人力與時間。
