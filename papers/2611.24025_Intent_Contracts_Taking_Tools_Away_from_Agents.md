論文設計三種介面進行對比實驗：

1. **盲審查 (REVIEW)**：模擬 Claude Code 自動模式 (Auto Mode) 的推理盲權限分類器 (Reasoning-blind Permission Classifier) 資訊邊界 (Information Boundary)。規劃器提出完整 shell 指令，審查者僅接收使用者原始訊息與指令本身，看不到規劃器的推理說明。

2. **意圖可見審查 (REVIEW+INTENT)**：在盲審查基礎上加入兩個差異——程式碼驗證規劃器的逐字引用 (Verbatim Quotation)，並讓審查者看見目標 (Goal) 與引用欄位。審查者仍只能核准或拒絕整個指令。

3. **合約執行 (CONTRACT)**：規劃器不持有任何環境工具，僅能提交包含目標（最多 100 字）、使用者逐字引用、允許的輸出主機、寫入前綴與錯誤政策的合約。程式碼驗證引用、範圍與目標格式後，由可信模型撰寫至多一個工具呼叫，僅執行授權部分。

**由程式碼強制保證的不變量 (Invariants)**

論文區分兩類性質：介面結構保證的性質（取決於派發程式碼正確性）與模型行為相關的結果（取決於特定模型配置）。前者包含三項關鍵不變量：

- **可信模型撰寫所有執行呼叫**：在合約執行模式下，規劃器寫的任何文字都不會被傳遞給工具，徹底切斷規劃器對具體指令內容的直接影響。
- **已記錄合約先於每次呼叫**：合約日誌構成規劃器對執行影響的完整記錄，且在執行前寫入。
- **可信端決定執行範圍**：可信模型可選擇只執行使用者授權的部分，而非被迫接受整個指令或拒絕整個指令。

此設計的關鍵洞見在於：規劃任務可能比檢查一個提議步驟更困難，因此讓強模型負責規劃、小模型負責檢查。但「部分執行」(Partial Execution) 能力是合約介面相對於審查介面的根本優勢——審查者只能二元決策（核准/拒絕整個指令），而合約模式允許可信模型裁剪指令範圍。

**威脅模型與信任假設**

論文採用 AI 控制領域的標準威脅模型：可信模型被假設為「嘗試遵循使用者而非必然正確」，可犯錯；驗證與派發程式碼則被假設為「強信任」，因為介面性質依賴其正確實作。實驗僅評估合作型模型與良性過度執行 (Benign Over-reach)，不涉及對抗性規劃器 (Adversarial Planners)。

#### 實驗數據解讀

1. **目標與物件命名一致性**：在合約模式下，每個被改變的物件都會在產生該改變的合約目標中被命名。相比之下，在審查模式下，規劃器在指令中命名物件，卻很少在目標中命名。這項結果驗證了合約機制的「規劃器影響可追溯性」——透過強制目標欄位包含物件名稱，建立起清晰的責任鏈。

2. **良性過度執行處理**：當規劃器加入使用者從未要求的工作時，合約模式在使用者任務上達成 27/30 的成功率，而意圖可見審查僅 16/30。差距約 37 個百分點，反映出審查者只能拒絕整個指令的限制——若指令包含額外工作，審查者要嘛全部放行（造成過度執行），要嘛全部拒絕（任務失敗）；合約模式則可裁剪至僅執行授權部分。

**關鍵失敗模式分析**

40-49% 的錯誤目標命中率揭示一個根本限制：此錯誤源於規劃器對模糊指涉 (Ambiguous Reference) 的物件選擇，而任何本文使用的可信模型都無法看見環境來驗證此選擇。指示執行者在不確定時拒絕，並未改變此錯誤率。

此結果的深層意涵在於：合約介面改變的是「誰撰寫指令」與「誰決定執行範圍」，但無法改變「規劃器對模糊語言的詮釋」。當使用者說「重啟那個服務」時，無論由誰撰寫 systemctl 指令，目標服務的選擇仍取決於規劃器的語言理解，而這是當前模型無法可靠完成的任務。

**測量方法的創新**

論文提出一項與基準測試工具日誌時間對齊的程式化測量：判斷每個被改變的物件是否在產生該改變的合約中被命名。此測量繞過了自然語言意圖 (Natural-language Intent) 評估的模糊性，直接檢查「規劃器聲明的目標」與「實際影響的物件」之間的對應關係。

AmPermBench 本身使用模糊 DevOps 請求與程式化任務結果來檢驗授權問題。本文將此基準擴展為三種介面的對比框架，並新增「目標-物件命名一致性」測量與「部分執行 vs 整指令核准」的小型任務區分。

A：隨著大型語言模型代理在 DevOps 等真實場景中獲得更多工具存取權與自主性，模糊的自然語言請求可能導致未授權的行動，即使代理本身意圖良善。這種「良性過度執行」（benign over-reach）會在使用者與代理之間形成一道授權鴻溝，使得使用者難以預測或控制代理的實際行為。因此，建立一套能夠在執行前捕捉並驗證意圖的機制，對於安全部署工具型代理是不可或缺的基礎建設。

**Q4：這篇論文提出的核心方法是什麼？**
A：論文提出「意圖合約」（Intent Contracts），這是一種授權介面，其核心設計是讓規劃模型完全不持有任何環境工具。在每一步中，規劃器提交一份簡短的已記錄合約，內容包含目標、對使用者的逐字引用以及範圍欄位；接著由程式碼驗證合約格式，再由一個小型可信模型根據使用者原話檢查授權範圍，並由該可信模型親自撰寫工具呼叫。這種設計讓規劃器只能「描述」一步行動，而無法直接控制執行內容。

**Q5：相較於既有方法，此研究的關鍵創新為何？**
A：最關鍵的創新在於徹底將工具從規劃器手中移除，並由可信模型撰寫每一個被執行的呼叫。在審查式設計下，規劃器撰寫的指令一經核准便原封不動地執行；而在意圖合約下，規劃器最多只能用 100 字描述意圖，且不能包含任何指令行，這使得可信模型可以決定「執行多少」而非僅僅「核准與否」。這種從二元核准到部分執行的轉變，是本文最具突破性的設計變革。

**Q6：合約結構中有哪些重要的設計選擇？**
A：合約的設計刻意保持精簡但資訊密集：目標欄位（最多 100 字）需明確指出物件、預期變更以及與使用者請求的關聯；逐字引用欄位要求規劃器必須引用使用者原話；範圍欄位則包含允許的外部主機、寫入路徑前綴以及錯誤處理策略。此外，程式碼會自動驗證引用的真實性、範圍的合理性以及目標的格式，這些設計共同確保規劃器對執行的所有影響都會在執行前被完整記錄。

**Q7：實驗使用了哪些基準測試與模型？**
A：實驗採用 AmPermBench 基準測試中的三個任務族，這些任務族專門設計用於檢驗模糊 DevOps 請求下的授權問題。規劃模型使用 gpt-6.1-terra，可信模型則使用較小的 GLM-5.3-Flash，這樣的組合反映了「強模型規劃、弱模型檢查」的分工理念。

**Q8：實驗中最關鍵的結果為何？**
A：實驗揭示了三項關鍵發現：第一，在意圖合約下，每一個被變更的物件都會在產生該變更的合約目標中被明確命名；而在審查條件下，規劃器傾向在指令中提及物件，卻很少在目標中提及。第二，當規劃器加入使用者從未要求的工作時，意圖合約在 30 次執行中有 27 次能完成使用者的任務，而意圖可見審查者僅有 16 次。第三，意圖合約並未減少未授權行為的發生率，與盲審查幾乎無法區分，且在 40-49% 的狀態變更執行中擊中了錯誤的目標。

**Q9：三種介面條件在哪些屬性上有所不同？**
A：三種介面在五個關鍵屬性上有所區別：執行呼叫的撰寫者（規劃器或可信模型）、規劃器文字是否對可信模型可見、可信模型能決定的範圍（整個指令或步驟的任何部分）、每個呼叫前是否有記錄意圖、以及可信模型是否能看見環境。這些差異並非由模型行為決定，而是由派發程式碼的資訊流所固定，因此只要程式碼正確，這些屬性就能穩定成立。

**Q10：哪些實際情境最能受惠於這種方法？**
A：凡是涉及模糊自然語言請求的 DevOps 場景都特別適合採用此方法，例如「重啟服務」、「清理舊任務」、「更新設定檔」等。使用者通常只希望授權部分動作，而非整個指令的執行，而意圖合約允許可信模型只執行被授權的部分，從而避免代理因詮釋過度而造成非預期的破壞。這對於需要嚴格控制變更範圍的生產環境尤其重要。

**Q11：在產品化部署時應考量哪些因素？**
A：產品化時必須考量三個關鍵因素：首先，可信模型本身必須足夠可靠，因為所有執行的呼叫都由它撰寫；其次，驗證與派發程式碼的正確性至關重要，因為論文中強調的許多屬性都依賴於程式碼的正確實作；最後，規劃器與可信模型的角色提示需要謹慎設計，以確保兩者能有效協作。這些因素共同決定了系統在真實環境中的安全性與可用性。

**Q12：這項研究對 AI 控制領域的更廣泛影響為何？**
A：本研究對 AI 控制領域的貢獻在於提出了一種新的分工範式：強模型負責規劃、弱模型負責檢查，並將自然語言意圖視為「待驗證的聲明」而非可信資訊。這種觀點挑戰了傳統上對代理意圖聲明的信任，並提供了一個完整的執行前記錄機制，使得規劃器對執行的所有影響都能被追溯與審查。這對於建立可審計、可問責的代理系統具有深遠的意義。

**Q13：這項方法有哪些已明確承認的限制？**
A：論文坦誠地指出多項重要限制：意圖合約並未減少未授權行為的發生率，與盲審查在這方面幾乎無法區分；在 40-49% 的狀態變更執行中，可信模型無法察覺規劃器對模糊指涉選擇了錯誤的物件，因為它看不到環境；即使指示執行者在不確定時拒絕執行，也無法改變這個錯誤。此外，實驗僅評估了良性過度執行情境，並未涵蓋對抗性規劃器的威脅模型。

**Q14：主要的失敗案例是什麼？**
A：最主要的失敗案例發生在規劃器對模糊指涉選擇錯誤物件時。由於可信模型無法看見環境，它無法判斷規劃器所選的物件是否真的是使用者所指的那一個，這導致在 40-49% 的狀態變更執行中擊中了錯誤的目標。這個錯誤源於規劃器對自然語言的詮釋，而非可信模型或驗證機制的疏失，因此即使加入「不確定時拒絕」的指示也無法緩解。

**Q15：這項工作提出了哪些值得探索的未來方向？**
A：未來可探索的方向包括：在對抗性規劃器的威脅模型下評估此方法的穩健性；研究如何讓可信模型獲得有限的環境感知能力以驗證物件選擇；探討部分執行機制與其他安全機制的結合可能性；以及深入研究如何更好地處理自然語言中的模糊指涉問題。此外，論文中作為基準的「無人閱讀的意圖聲明」條件也值得進一步研究，以釐清意圖記錄本身是否具有獨立的安全價值。

### 潛在風險與注意事項

- **合約無法降低未授權行為的發生率**：論文明確指出，合約在「未授權動作」指標上與盲審查無統計差異。實作者不應將意圖合約視為安全升級，而應理解它改變的是「發生未授權行為時的可解釋性與可部分撤銷性」。

- **模糊指涉仍是規劃器的選擇問題**：當使用者說「重啟那台出問題的服務」時，選錯目標物件的機率在論文中達 40–49%，且「告訴執行器在拿不準時拒絕」並未改變這個錯誤率，因為可信模型看不到環境狀態。實作者應將此視為規劃器品質問題，而非介面問題。

- **驗證與派發程式碼是可信基礎**：所有「由介面保證的性質」都依賴驗證與派發程式碼的正確實作。任何繞過驗證（例如規劃器把指令藏在目標欄位裡）或派發漏洞（例如把規劃器文字誤傳給工具）都會瓦解整個介面的安全保證。

- **逐字引用的欺騙風險**：規劃器可能在引用欄位放入真實的逐字引用，但目標欄位卻描述與引用無關的動作。論文的意圖可見審查者會被指示「真實引用不足以證明授權」，實作時必須把這個判斷邏輯明確寫進可信模型的指令中。

- **部分執行的副作用**：當可信模型只執行指令的一部分時，可能產生半完成狀態（例如只刪除部分檔案）。實作者應設計錯誤處理策略與補償機制，並在合約的 `error_policy` 欄位中明確約定。

- **評測侷限性**：論文僅以一對模型、一組指令評估良性過度執行，並未涵蓋對抗性規劃器。實作者不應將結果外推到惡意代理情境。

### 與其他技術的整合建議

- **與 Claude Code 自動模式互補**：Claude Code 的自動模式刻意將代理的散文從權限分類器輸入中移除，意圖合約則反過來保留簡短的目標聲明。兩者可整合為「自動模式 + 意圖合約日誌」，既降低提示注入風險，又保留可審計的規劃理由。

- **與 AI Control 框架結合**：可信模型的角色定義（假設會嘗試遵循使用者而非保證正確）與 AI Control 文獻一致，可直接套用現有的「不可信強模型 + 可信弱模型」控制協定與評估方法。

- **與傳統權限管理系統（IAM / RBAC）整合**：合約中的 `egress_hosts` 與 `write_prefixes` 欄位可對接企業 IAM 政策，讓可信模型在寫工具呼叫時自動套用最小權限原則。

- **與審計與可觀測性平台整合**：每筆合約都是結構化紀錄，可直接送入 SIEM 或審計日誌系統，作為「誰、在什麼意圖下、執行了什麼動作」的證據鏈。

- **與提示注入防護整合**：意圖合約可作為提示注入的一道防線——即使規劃器被注入攻擊而想執行惡意動作，它仍須透過合約提交目標，而可信模型只依據原始使用者訊息判斷授權，使注入內容難以直接生效。

**給初學者**：建議先讀第 1 節與第 2.1 節，理解「為什麼要把工具從規劃器拿走」這個核心動機，再看圖 1 與表 1 的介面對照。實作上可從「禁止規劃器直接呼叫工具、強制它先寫一段目標文字」這個最小版本開始體驗，不必一次到位所有欄位。

**給 AI 工程師**：重點放在第 2.2 節的「由介面保證的性質」與表 1，這些是程式碼層面的契約，與模型無關。實作時應把驗證與派發程式碼視為可信計算基礎（trusted computing base），並為其撰寫完整的單元測試，因為所有安全論點都依賴它的正確性。同時關注第 3 節的實驗數據，特別是 27/30 vs 16/30 的對比，理解「部分執行」相對於「整指令核准」的工程價值。

**給研究者**：論文的價值在於把「介面設計」與「模型表現」清楚分離——前者是程式碼性質，後者是配置觀察。建議延伸方向包括：（1）對抗性規劃器下的合約表現、（2）多步驟合約的組合授權問題、（3）可信模型本身的可錯性如何影響整體安全邊界、（4）將 AmPermBench 擴展到非 DevOps 領域的模糊指涉情境。

**給產品經理**：理解這個介面的核心價值主張是「可解釋性與可部分撤銷性」，而非「更高的安全性」。當代理做出超出使用者授權的動作時，意圖合約能讓事後調查清楚看到「代理說它想做什麼 vs 使用者實際說了什麼」，並允許只執行被授權的部分。對產品而言，這意味著更短的除錯時間、更清楚的責任歸屬，以及在受監管產業中更易通過稽核；但不應將其宣傳為「更安全的代理」。
