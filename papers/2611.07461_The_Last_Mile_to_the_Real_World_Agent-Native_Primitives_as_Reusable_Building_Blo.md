本文提出了一套系統性的方法論來解決 LLM 代理在真實世界任務中「最後一里」(Last Mile to the Real World) 的瓶頸問題。其核心論點是：現有方法將資源（如工具、API、程式碼、證明）置於可觸及範圍內，但將「應用資源的能力」留給呼叫者（caller），導致每個框架（harness）都必須重新建構這種能力，造成能力無法跨任務累積、學習成果隨任務結束而消失、結果難以驗證等問題。

**核心概念：代理原生原語（Agent-Native Primitives）**

作者將傳統的可重用軟體元件、時序延伸選項（temporally extended options）以及契約式設計（design by contract）概念延伸至基於 LLM 的單元。每個原語由兩個關鍵部分組成：

1. **資源本體（Resource）**：可以是工具、API、程式碼、證明、文件等被動的工件（passive artifacts）。
2. **駐留式大語言模型（Resident LLM）**：賦予資源自然語言介面，使其能在情境中（in context）應用於每個請求，並與其他原語溝通需求。

這種設計使被動工件轉變為能彼此對話的主動參與者（active participants），且原語的介面讓框架能在不閱讀資源的情況下找到並呼叫它。

**HEELO 框架的三個機制**

HEELO 並非僅僅是原語的集合，而是一個圍繞演化中原語函式庫建構任務專屬框架的工程框架，包含三個關鍵機制：

1. **函式庫選擇與組合（Library Selection and Composition）**：透過介面或原語自身的相關性評估來尋找候選原語，並將任務所需的少數原語組合成任務專屬圖（task-specific graph），使每個結果與訊息能傳遞給其消費者。

2. **基於證據的執行與改進（Evidence-Based Execution and Improvement）**：以多輪方式執行圖，根據任務環境中的證據驗證結果，並將每次失敗追溯到其所牽涉的原語，使修訂僅重做相關工作而保留其餘部分。

3. **驗證與發布（Validation and Publishing）**：在任務之間改進函式庫，一旦測試、編譯器或開發執行等證據確認後，即納入新的或改進的原語。

**八個原語家族**

作者將 HEELO 實例化為八個原語家族，每個家族針對一類真實世界任務：

| 原語家族 | 應用領域 | 規模 |
|---------|---------|------|
| 工具原語（Tool Primitives） | LLM 工具使用 | 25,519 個（含 16,464 個包裝即時 API） |
| 程式碼原語（Code Primitives） | 程式碼儲存庫建構 | 1,424 個（每個都通過其攜帶的測試驗證） |
| 數學原語（Math Primitives） | 形式化定理證明 | 82 個（Lean 工件可編譯） |
| 知識原語（Knowledge Primitives） | 知識密集型任務 | — |
| 代理原語（Agent Primitives） | 多代理系統 | — |
| 開發原語（Dev-Primitives） | 軟體工程 | — |
| 導航原語（Navigation Primitives） | 大型資訊空間 | — |
| 框架原語（Harness Primitives） | 代理框架 | — |

此外，作者還引入了 522 個程式碼儲存庫重建任務的基準測試，源自七個領域的真實 Python 專案。

**方法論的理論基礎**

作者引用了 companion studies 的結果，證明了兩個關鍵性質：
- 需求驅動的啟動（need-driven activation）保持在任務需求範圍內，無論函式庫如何增長。
- 識別了何時每任務組合（per-task composition）優於最佳固定框架。

這為方法論提供了理論支撐，避免了函式庫膨脹導致的效率問題。

#### 與現有研究的比較

**定位**

本文定位於解決 LLM 代理領域的一個根本性缺口：現有方法在「讓資源可被觸及」方面已取得重要進展，但在「讓資源被正確應用」方面仍有不足。作者將此問題命名為「真實世界的最後一里」，並提出將應用能力從呼叫者遷移至資源本身的系統性解決方案。

**相較於現有方法的優勢**

1. **vs. 工具學習（Tool Learning）**：工具學習專注於讓代理學會呼叫工具，但將工具的應用邏輯留給呼叫者。代理原生原語則將應用邏輯封裝在工具內部，使工具成為主動參與者。

2. **vs. 檢索與記憶（Retrieval and Memory）**：這些方法改善了資訊的可及性，但對於如何將檢索到的內容應用於特定情境仍依賴呼叫者。知識原語則將這種應用能力內建於原語中。

3. **vs. 技能庫與程式碼庫（Skill/Code Libraries）**：傳統函式庫是被動的，需要呼叫者理解如何使用。代理原生原語透過駐留式 LLM 提供了自然語言介面，使呼叫者無需深入理解即可使用。

4. **vs. 多代理框架、工作流搜尋、框架生成器（Multi-agent Frameworks, Workflow Search, Harness Generators）**：這些方法試圖從外部建構更好的框架，但每個任務仍需重新建構能力。HEELO 則透過演化原語函式庫實現能力的跨任務累積。

5. **vs. 單一代理（Monolithic Agent）**：單一代理將所有能力集中於一個模型，難以擴展且難以驗證。HEELO 的模組化設計使每個原語可獨立驗證、改進與重用。

**改進幅度**

從實驗數據看，HEELO 在多個基準測試上帶來了 10–20 點的提升，這在 LLM 代理領域是顯著的。特別是在 heelo.dev 的 46 個真實世界任務上，完成率從約 20% 提升至 76–85%，這表明方法論在實務環境中的有效性。

**限制與不足**

1. **建構成本**：雖然每任務組合成本僅為一次代理嘗試的 2.7–4.3%，但建構 25,519 個工具原語、1,424 個程式碼原語等需要大量前期投入。

2. **原語品質依賴**：原語的品質直接影響系統表現。雖然有驗證機制，但如何確保原語在面對新任務時的泛化能力仍是挑戰。

3. **領域覆蓋**：雖然有八個原語家族，但對於某些特殊領域（如醫療、法律），可能需要額外的原語開發。

4. **MCP 依賴**：heelo.dev 平台的實驗依賴 MCP 伺服器，這要求任務環境支援 MCP 協議。

5. **基準測試的時效性**：論文中提到的 GPT-5.6、Claude Opus 5 等模型版本可能隨時間演進，基準測試的難度也可能調整。

## 實務應用指南

### 適用場景

1. **企業內部 API 工具自動化**：將公司內部散落的 SaaS API（如 CRM、ERP、票務系統）包裝成 Tool Primitives，讓代理能依業務情境自動串接。論文顯示 Tool Primitives 在 ToolBench 將通過率從 55.8% 提升至 75.1%，並在 τ 2-Bench 航空領域任務上以最高 7.7 倍低成本超越 GPT-5.4。

2. **程式碼儲存庫重構與遷移**：針對遺留系統的現代化、套件升級、跨語言移植等任務，使用 Code Primitives 將每個重構動作封裝為可驗證的單元。論文實例中 Code Primitives 在程式碼遞送上比 Claude Code 多 56.2%，並以 GPT-OSS-20B 適應與診斷維持 95.1% 遞送率同時降本 24.0%。

3. **軟體工程任務自動化（CI/CD、測試、除錯）**：以 Dev-Primitives 處理 Terminal-Bench 類的終端機任務，例如建置失敗排查、依賴衝突解決、容器化部署。論文報告在 Terminal-Bench 4.0 將 Codex 的 37.3% 提升至 55.5%，DevOps-Gym 四階段平均成功率也顯著提升。

4. **大型資訊空間的導航與研究**：當任務需要從海量文件、網頁、知識庫中找出並串接證據時，使用 Navigation Primitives。論文在 GAIA-Text-103 將準確率從 45.6% 提升至 58.3%，且主動式導航在證據周圍資訊膨脹 16 倍時仍能維持 1.23 倍成長。

5. **多代理協作與知識密集問答**：以 Agent Primitives 與 Knowledge Primitives 處理需要多角色協商或長篇文件推理的任務，例如盡職調查、技術審查、合規檢核。論文顯示 Agent Primitives 在 Qwen3-8B 上比最強多代理系統多 7.5 分且少 3–4 倍 token，Knowledge Primitives 在 GPT-5.6 Luna 上平均領先 Hybrid RAG 14.3 分。

### 實作前置條件

**資料準備**
- 任務的驗收標準（acceptance criteria）與可執行測試案例，這是 HEELO「證據驅動修訂」機制的基礎。
- 目標資源的結構化描述：API 的 OpenAPI 規格、程式碼儲存庫的測試套件、知識庫的文件切分與引用關係。
- 失敗案例日誌：用於訓練「失敗追溯到原語」的診斷能力。

**運算資源**
- 至少一個骨幹模型（backbone）的 API 存取權限，例如 GPT-5.6、Claude Opus 5 或開源替代方案（Qwen3-8B、GPT-OSS-20B）。
- 原語駐留式 LLM 的推理預算：每個原語內含一個小型 LLM，數千個原語同時運行時需要批次推理或邊緣部署。
- 任務專屬圖（task-specific graph）的執行環境：支援回合式執行、訊息傳遞與狀態保存。

**技能要求**
- 框架工程（harness engineering）能力：理解如何將模型、工具、記憶、評估組裝為可重現的執行環境。
- 提示工程與評估設計：為每個原語家族設計介面契約、輸入輸出 schema 與失敗模式分類。
- 軟體工程實務：版本控制、CI/CD、測試自動化，這是「驗證與發布」機制能落地的關鍵。
- 領域知識：依任務選擇原語家族時，需理解該領域的「最後一里」瓶頸（例如航空訂位的政策約束、形式化證明的條件匹配）。

### 實作步驟建議

**步驟一：盤點現有資源並分類**
盤點組織內所有可被代理使用的資源（API、程式碼、文件、知識庫），依論文八大原語家族分類。優先處理「最後一里」瓶頸最明顯的家族，例如客服場景優先 Tool Primitives，研發團隊優先 Dev-Primitives。

**步驟二：建立原語函式庫骨架**
為每個資源建立最小可行原語：定義自然語言介面、駐留式 LLM 的角色與約束、輸入輸出 schema、驗證證據的來源。論文實例中 Tool Primitives 達 25,519 個、Code Primitives 達 1,424 個，可循序漸進從數十個開始。

**步驟三：實作 HEELO 三大機制**
1. 函式庫選擇與組合：建立原語檢索機制（透過介面或原語自身的相關性評估），並組合為任務專屬圖。
2. 證據驅動執行與改進：以回合方式執行任務專屬圖，從環境收集證據（測試輸出、編譯結果、開發日誌），失敗時追溯到涉及的原語並僅重做其工作。
3. 驗證與發布：原語改進後需通過驗證（測試、編譯、開發執行）才能進入函式庫。

**步驟四：建立 MCP 伺服器對外介面**
仿照論文 heelo.dev 平台，透過 Model Context Protocol（MCP）伺服器將 HEELO 函式庫開放給既有代理（Claude Code、Codex 等），讓它們在不重建能力的情況下獲得原語支援。論文實例顯示此整合讓 Claude Opus 5.5 從 9/46 提升至 39/46，GPT-6.1 Sol 從 9/46 提升至 35/46。

**步驟五：建立評估管線與持續改進**
部署與論文同等規模的評估管線（涵蓋 20+ 基準測試），持續監控各原語家族的效益、成本與失敗模式。論文強調「任務決定哪些原語運行」，因此評估需支援按任務切分的成本效益分析。

**步驟六：迭代演化函式庫**
依任務表現決定新原語的納入或既有原語的改版。論文強調「需求驅動啟動」讓函式庫增長時單次任務的啟動成本仍受任務需求限制，因此需設計原語的懶載入與快取機制。

### 潛在風險與注意事項

**風險一：原語膨脹導致檢索成本失控**
當原語數量達到數萬級時，每個任務的檢索與組合成本可能成為瓶頸。緩解方式：採用論文證實的「需求驅動啟動」設計，讓原語按任務需求懶載入；建立原語分層索引（家族 → 類別 → 實例）。

**風險二：證據驗證的可靠性**
若任務環境缺乏可靠的驗收證據（例如測試覆蓋不足、API 回傳不確定），「證據驅動修訂」機制可能誤判失敗原因。緩解方式：為每個原語設計多重證據來源（測試 + 編譯 + 開發日誌），並設置人工審查閘門處理低信心案例。

**風險三：駐留式 LLM 的成本與延遲**
每個原語內含一個 LLM，數千原語同時運行會造成成本與延遲問題。緩解方式：使用小型開源模型（如 Qwen3-8B、GPT-OSS-20B）作為駐留 LLM，僅在關鍵原語使用大型模型；採用批次推理與結果快取。

**風險四：原語介面演化的相容性**
當原語改版時，依賴其介面的任務專屬圖可能失效。緩解方式：採用語意化版本控制，保留舊版介面一段時間；建立介面變更的影響分析工具。

**風險五：單一代理思維的慣性**
團隊可能傾向把所有能力塞進一個大型代理，而非設計為原語組合。緩解方式：以論文的「單一代理 vs. 原語組合」對比實驗作為內部教育素材；從小規模原語組合開始展示效益。

**風險六：MCP 整合的安全邊界**
透過 MCP 對外開放原語時，需考慮權限控管、資料外洩與濫用風險。緩解方式：實施原語級的存取控制、稽核日誌與速率限制。

### 與其他技術的整合建議

**與 RAG 系統整合**：Knowledge Primitives 可作為 RAG 的進化版，不只檢索文件還主動應用文件。建議將現有 RAG 管線的檢索器封裝為 Navigation Primitives，將文件內容的應用邏輯封裝為 Knowledge Primitives，兩者透過任務專屬圖組合。

**與 CI/CD 整合**：Dev-Primitives 與 Harness Primitives 可直接嵌入 CI/CD 管線，作為自動化測試、程式碼審查、部署驗證的代理單元。論文顯示 Harness Primitives 在 SWE-bench Verified 與 Terminal-Bench 2.0 上以 2.7%–4.3% 的組合成本超越 mini-SWE-agent 種子框架 7.5–12.2 分。

**與多代理框架整合**：Agent Primitives 可作為 LangGraph、AutoGen、CrewAI 等框架的底層單元，取代其內建的工具呼叫機制。論文顯示 Agent Primitives 在 Qwen3-8B 上比最強多代理系統多 7.5 分且少 3–4 倍 token。

**與形式化驗證整合**：Math Primitives 可與 Lean、Coq 等證明助手整合，用於需要形式化保證的場景（合規驗證、安全關鍵系統）。論文實例中 82 個 Math Primitives 的 Lean 工件皆可編譯。

**與企業 SSO 與權限系統整合**：透過 MCP 伺服器對外提供原語時，整合企業 SSO（如 Okta、Azure AD）與細粒度權限系統，確保代理只能呼叫授權範圍內的原語。

**與監控與可觀測性平台整合**：將原語的執行軌跡、證據收集、失敗追溯過程整合至 Langfuse、Phoenix 等可觀測性平台，方便除錯與成本分析。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「真實世界的最後一里」這個核心問題——為什麼代理能取得資源卻仍無法完成任務。接著閱讀「代理原生原語」的定義，體會「能力應隨資源同行」這個設計哲學。實作上可從單一原語家族（例如 Tool Primitives）的小規模實驗開始，無需一次建構完整 HEELO 框架。

**給 AI 工程師**：重點閱讀 HEELO 的三大機制（函式庫選擇與組合、證據驅動執行與改進、驗證與發布）以及八大原語家族的實作細節。特別關注「任務專屬圖」的設計模式與「失敗追溯到原語」的診斷邏輯，這是將論文方法落地為產品的關鍵工程決策。建議參考論文中 MCP 伺服器的整合方式，將 HEELO 作為現有代理（Claude Code、Codex）的外掛而非取代品。

**給研究者**：論文的價值在於將八個看似獨立的研究方向（工具使用、程式碼生成、形式化證明、知識密集任務、多代理、軟體工程、資訊導航、框架工程）統一在一個框架下。建議深入分析「需求驅動啟動」的理論基礎、「任務決定哪些原語運行」的經驗規律，以及「原語內部增益」的消融實驗設計。同時關注 522 個程式碼重構任務的新基準測試，這是該領域的重要資源。

**給產品經理**：核心訊息是「代理的瓶頸不在於模型能力，而在於資源與能力的分離」。產品決策上應優先投資「原語函式庫」而非更大的模型；評估代理產品時，應關注「最後一里」指標（任務完成率、成本、延遲）而非單純的模型基準分數。論文中 heelo.dev 平台的 46 個真實世界任務（Claude Opus 5.5 從 9 提升至 39、GPT-6.1 Sol 從 9 提升至 35）是評估商業價值的具體參考。建議將原語視為可累積的組織資產，而非每次任務重建的成本。
