## ⚡ TL;DR

AI 生成數學激增，但驗證與維護形式化成果成為瓶頸。
本文提出 Lean Pool，由 AI 代理匯集、維護並最佳化形式化數學專案。
目前已收錄 211 個專案、逾三百萬行程式碼，並促成證明簡化與編譯加速。

## 摘要翻譯

Lean Pool 是一個形式化數學（formalized mathematics）儲存庫（repository），由 AI 代理（智能體）（AI agents）擴增（grown）、維護（maintained）與最佳化（optimized）。

### 核心貢獻（3～5點）
- 提出由 AI 代理（AI agents）主動維護的形式化數學（formalized mathematics）檔案庫（archive）架構。
- 透過 AI 自動化處理儲存庫（repository）的擴增（growth）、維護（maintenance）與最佳化（optimization）。
- 降低形式化數學函式庫（library）持續更新所需的人力成本與技術門檻。
- 為研究級數學（research-level mathematics）成果提供可長期保存、驗證與重用的動態檔案庫（living archive）。

### 適合對象
本論文適合從事形式化數學、互動式定理證明器（theorem prover）研究、數學函式庫（math library）維護，以及對生成式 AI（Generative AI）輔助數學知識管理有興趣的研究人員與開發者閱讀。

## 深度分析

#### 方法論解析

Lean Pool 的核心方法論並非從零打造一個新的數學函式庫（library），而是建立一個**動態檔案庫（living archive）**，將已經完成的**形式化專案（formalization project）**匯集（pool）到同一個 **Lean**／**Mathlib** 環境中，並由 **AI 代理（AI agent）**持續進行維護（maintenance）與最佳化（optimize）。整個流程可拆解為三個支柱：成長（growth）、維護與最佳化。

在**成長**階段，Lean Pool 透過兩種方式擴增內容：一是由 AI 代理自動發現符合 **Apache-2.0 授權條款（Apache-2.0 license）**或 **MIT 授權條款（MIT license）**的既有形式化專案並將其納入池（pooling）；二是接受人類貢獻者（contributor）直接提交自己的專案。被納入的專案必須是「嚴謹完整的形式化（serious complete formalization）」，針對**具名的已知結果（named known result）**，且不得包含 `sorry` 或 `admit`，也不能引入超出 `Classical.choice`、`propext`、`Quot.sound` 之外的公理。這些**入庫規則（admission rules）**構成第一道品質閘門，確保檔案庫內的證明至少具備機械可檢驗的正確性。

在**維護**階段，Lean Pool 面對的最大挑戰是 Mathlib 與 Lean 版本不斷演進所帶來的相容性（compatible）問題。作者設計了一個依賴更新工作流程（dependency-update workflow）：當新的 Lean／Mathlib 版本釋出時，AI 代理會執行**升級 Lean 版本（bumping the Lean version）**，自動修復因 API 變動而產生的錯誤（resolve errors）。此外，每日排程工作會搜尋新舊形式化專案、檢視開放的**拉取請求（Pull Request, PR）**、處理維護者議題、最佳化現有專案，並在 Zulip 發布**每日專案公告（daily project announcements）**。

**品質保證**採用三層架構：第一層是 **Lean kernel（Lean 核心）**，以型別論為基礎保證**證明正確性（correctness of proofs）**；第二層是嚴格的 **linter（程式碼檢查器）**，檢查程式碼風格、禁用 `set_option`、未檢查宣告與資源限制繞過機制；第三層是 **LLM review（大型語言模型審查）**，用於檢查**定義（definition）**與**定理敘述（theorem statement）**的品質。值得注意的是，LLM 並不負責驗證證明細節，而是輔助確保高階數學介面的可讀性與一致性。

在**最佳化**方面，AI 代理會定期掃描**程式碼庫（codebase）**，針對編譯時間（compilation time）與 **RAM 使用量（RAM usage）**的**熱點（hotspot）**進行重構，以提升**簡潔性（conciseness）**與**編譯速度（compilation speed）**。這種以資源效率為目標的持續重構，在傳統由人類維護的數學函式庫中較為少見。

最後，Lean Pool 強調**歸屬（attribution）**與**來源（provenance）**：每個專案都附有一張專案卡片，記錄作者、上游來源、證明來源（人工撰寫、AI 生成或混合）以及主要結果的非形式化敘述。這種設計試圖在 AI 大量參與的環境中，區分「提交者」與「原作者」，避免形式化成果被誤歸屬。

整體而言，Lean Pool 的方法論是一種「彙整＋維護＋最佳化」的混合模式，其創新之處在於把 AI 代理放在持續整合（Continuous Integration, CI）與版本遷移的第一線，而非僅將 AI 視為一次性生成工具。然而，從提供的文本來看，AI 代理的具體架構、提示詞（prompt）、模型選擇、錯誤修復策略與 LLM 審查的評分標準都未詳細說明，這使得方法論在可複製性與可評估性上仍有明顯缺口。

#### 實驗數據解讀

論文提供的統計數據（statistics）顯示，Lean Pool 目前包含 211 個**匯集專案（pooled project）**，總計約 3,228,485 行 Lean **程式碼行數（lines of code）**，共有 18 位貢獻者，且 **Lean 版本（Lean version）**已被升級六次。從規模來看，平均每個專案約 15,000 行 Lean 程式碼，已達到相當可觀的體量，顯示 Lean Pool 確實能夠快速聚合大量研究級數學的形式化成果。

然而，這些數字需要謹慎解讀。首先，**程式碼行數（lines of code）**並不等同於數學內容的豐富度或定理數量；AI 生成的證明往往較為冗長，可能會顯著膨脹行數。其次，論文未提供每個專案的定理數、證明長度分布、原始提交日期或領域分類，因此難以判斷這 211 個專案是否涵蓋均衡的數學領域，抑或集中在某些特定主題。

關於**版本升級（version bump）**的成效，六次成功的 Lean／Mathlib 升級確實是 Lean Pool 方法論有效性的重要證據。由於 Mathlib 更新頻繁且經常破壞既有 API，能夠在升級後維持整個檔案庫的建置（build）成功，代表 AI 代理在**修復錯誤（resolve errors）**與恢復**相容性（compatible）**方面具備實用價值。但文本並未提供每次升級所修復的錯誤數量、花費時間、人工介入比例，也沒有說明是否出現過升級失敗或專案被移除的案例。缺乏這些細節，我們無法評估 AI 維護的穩健性與成本。

在**最佳化（optimize）**方面，論文聲稱已接受可帶來全庫範圍證明縮短與編譯加速的變更，但提供的文本中並未列出具體的**編譯時間（compilation time）**或 **RAM 使用量（RAM usage）**前後對比。同樣地，關於 **LLM review（大型語言模型審查）**的成效，也沒有給出誤報率、漏報率或與人工審查的一致性數據。這些缺失使得「AI 維護優於傳統人工維護」的論點仍停留在定性描述階段。

另一個值得注意的數據點是論文提到「初始自動化後的後續修復（follow-up repairs after initial automation）」以及「大型審查的資源需求（resource demands of large reviews）」。這暗示 AI 代理的第一輪輸出並非完全可靠，仍需要二次修正，且隨著檔案庫規模擴大，審查與最佳化的計算成本會持續上升。這些都是實際營運中不可忽視的隱性成本。

此外，論文引用了一項 **LeanEval** 稽核，聲稱檔案庫中的數學已被後續研究級形式化所重用。這是關於**證明重用（reuse proofs）**價值的重要外部驗證，但由於 LeanEval 的詳細數據未在提供的文本中展開，我們無法判斷重用的頻率、深度與影響範圍。

總結來說，現有數據足以證明 Lean Pool 在規模與持續運作上的可行性，但距離嚴格的科學評估仍有距離。未來若能補充每次升級的錯誤統計、最佳化的效能對比、LLM 審查的準確率，以及與純人工維護模式的對照實驗，將大幅提升結果的說服力。

#### 與現有研究的比較

Lean Pool 在生態系中的定位介於傳統數學函式庫、預印本平臺與 AI 定理證明系統之間，最適合與以下幾類現有工作進行比較。

首先，與 **Mathlib** 相比，Mathlib 是 Lean 的**標準數學函式庫（standard math library）**，採用嚴格的人工審查（strict human review），以線性速率（linear rate）穩定成長，品質高但擴展速度受限。Lean Pool 則採用較為寬鬆的聚合模式：它不重新發明這些數學內容，而是把外部已完成的專案納入共同環境，並由 AI 代理負責後續維護。兩者關係應是互補而非競爭：Mathlib 提供基礎設施與嚴謹的核心內容，Lean Pool 則作為容納更多研究級數學（research-level mathematics）的「衛星檔案庫」。但這也帶來風險：Lean Pool 中的專案可能與 Mathlib 的介面設計不一致，導致可重用性（reuse）不如直接貢獻到 Mathlib。

其次，與 **arXiv** 相比，arXiv 是數學論文的預印本（preprint）平臺，強調快速分享與最小阻力（minimal friction），但不保證內容正確性。Lean Pool 的願景正是成為 arXiv 的**形式化對應物（formal analogue）**：每篇新論文除了 PDF 版本外，還附帶一個經過機械驗證並持續維護的形式化版本。相較於靜態的 GitHub 儲存庫（repository），Lean Pool 的優勢在於主動維護跨版本相容性；但相較於 arXiv 的同行審查與社群監督，Lean Pool 目前依賴 linter 與 LLM 審查，其品質把關機制仍較弱。

第三，與近期以生成與證明為導向的 AI 數學系統（例如 AlphaProof、LeanDojo 等）相比，Lean Pool 的 AI 應用場景截然不同。這些系統聚焦於自動產生**數學證明（mathematical proof）**或發現新定理，而 Lean Pool 的 AI 代理主要負責**形式化數學（formalized mathematics）**的策展、版本遷移、程式碼重構與資源最佳化。換句話說，Lean Pool 把 AI 當作「圖書館員與維修工」，而非「數學家」。這是一個較少被討論但同樣重要的研究方向，因為隨著 AI 生成證明的數量暴增，**驗證瓶頸（verification bottleneck）**與後續維護將成為關鍵挑戰。

第四，與一般的套件註冊中心（如 Lean 的 Reservoir、npm、PyPI）相比，Lean Pool 增加了專案卡片、來源標註、**闡述（Exposition）**文件與主動版本升級等機制。這些設計更貼近學術文獻的需求，特別是在歸屬與可理解性方面。然而，一般套件管理工具通常提供版本約束與依賴解析，Lean Pool 目前則傾向於把所有專案綁定到單一最新 Mathlib 版本，這在專案數量持續增加時可能會造成維護負擔。

Lean Pool 的主要貢獻在於提出並實踐了一個「AI 維護的檔案庫（AI-maintained archive）」概念，結合了開源授權（open-source license）合規、歸屬保存、自動化 CI 檢查與持續最佳化。其限制則包括：與 Mathlib 的整合深度不足、LLM 審查的可靠性尚未驗證、AI 自動發現專案時可能面臨授權與來源爭議，以及缺乏類似學術同行審查的品質保證層級。

#### 可重現性評估

Lean Pool 在可重現性（reproducibility）方面具備良好的基礎，因為它本質上就是一個開放原始碼（open source）專案。論文提供了索引網站、**闡述（Exposition）**網站與 Zulip 討論頻道的連結，且所有匯集專案都必須採用 **Apache-2.0 授權條款**或 **MIT 授權條款**。這意味著其他研究者可以下載整個**程式碼庫（codebase）**，檢視每個**匯集專案（pooled project）**的證明、執行 `lake build` 進行驗證，並在相同環境下重現編譯結果。

然而，可重現性仍有幾個明顯的缺口。第一，雖然形式化內容本身開放，但維護這些內容的 **AI 代理（AI agent）**的實作細節——包括使用的模型、提示詞、自動化腳本、每日工作排程與**持續整合（Continuous Integration, CI）**配置——在提供的文本中幾乎沒有說明。如果這些工具未一併開源，那麼「AI 如何維護 Lean Pool」這個核心貢獻將難以被他人複製或驗證。

第二，**LLM review（大型語言模型審查）**所使用的大型語言模型（Large Language Model, LLM）若為商業 API（例如 OpenAI GPT 系列或 Anthropic Claude），其模型權重（model weights）通常不公開，且 API 行為可能隨時間變化。即使公開提示詞，不同時間呼叫同一模型也可能產生不同結果，這會影響審查結果的可重現性。若論文能採用開源權重的模型（如 Llama、Mistral）並固定版本，將有助於提升可重現性。

第三，整個檔案庫包含超過三百萬行 Lean 程式碼，編譯所需的 **RAM 使用量**與時間可能相當可觀。雖然 CI 環境可以重現，但一般個人電腦可能難以在合理時間內完成完整建置，這對小型研究團隊或審稿者構成實際障礙。若能提供容器化環境（如 Docker image）、預編譯的快取（cache）或模組化建置指令，將大幅降低重現門檻。

第四，論文本身的人類撰寫部分僅有一頁，其餘幾乎全由 AI 生成。這雖然呼應了論文主題，但也可能導致某些技術細節、附錄內容與實驗記錄不夠完整或一致。例如，文中提到機械檢查細節在附錄 B、貢獻者列表在附錄 C.1，但這些附錄內容未在提供的文本中出現，影響了外部審查的完整性。

第五，目前未見論文提及釋出標籤（release tag）、DOI、Zenodo 典藏或標準化的 artifact 評估流程。對於一個以「檔案庫（archive）」自居的專案，長期保存與版本快照機制同樣重要。若能提供固定版本的快照與對應的 artifact 說明文件，將使 Lean Pool 更符合學術界對可重現性的期待。

總體而言，Lean Pool 在「內容開放」層面表現良好，但在「方法開放」與「環境可重現」層面仍有改進空間。建議未來完整開源維護代理的程式碼與提示詞、固定 LLM 版本或採用開源權重模型、提供容器化建置環境，並釋出帶有 DOI 的穩定快照。

#### 未來研究方向

Lean Pool 的出現開啟了多條值得深入探索的研究路徑，以下從技術、評估、生態與社會四個層面提出可能的後續方向。

在**技術層面**，首先可以發展更強大的自動化定理發現與補全機制。目前 Lean Pool 主要收錄已完成的**形式化專案（formalization project）**，未來可讓 AI 代理主動識別數學文獻中的 gaps，並嘗試將這些結果形式化後填補到 Mathlib 或 Lean Pool 中，從單純的「維護者」轉變為「擴展者」。其次，可以研究如何將 Lean Pool 中的大量證明作為訓練資料，提升專用於數學的 AI 模型在定理證明與形式化輔助上的表現。第三，針對大規模程式碼庫的**編譯速度（compilation speed）**與 **RAM 使用量（RAM usage）**，可以開發增量編譯、模組化依賴分析與智慧快取策略，以降低持續整合（CI）成本。

在**評估層面**，亟需建立系統性的指標來衡量 AI 維護的成效。例如：AI 代理在每次 **升級 Lean 版本（bumping the Lean version）**時修復的錯誤數與所需時間、LLM 審查相較於人工審查的準確率與誤報率、最佳化前後的編譯時間與記憶體對比，以及專案被後續研究**證明重用（reuse proofs）**的頻率。這些量化數據不僅能驗證 Lean Pool 的價值，也能為其他 AI 維護系統提供基準（benchmark）。

在**生態整合層面**，Lean Pool 可以進一步與 **arXiv** 建立雙向連結：自動從 arXiv 摘要中識別已形式化的論文，並在論文頁面標註對應的 Lean Pool 專案；同時，Lean Pool 的專案卡片也可直接引用 arXiv ID 與 DOI。此外，可以建立標準化的專案中繼資料格式、支援語義搜尋（semantic search）與定理層級的引用追蹤，使形式化成果更容易被數學家發現與使用。

在**人機協作與社會層面**，未來需要設計更完善的人類-AI 協同審查機制。例如，讓 LLM 先進行初步審查，再由領域專家進行重點複核；建立貢獻者聲譽系統；以及針對 AI 生成證明的歸屬與責任問題制定明確規範。特別是當 AI 代理自動發現並匯入外部專案時，授權條款（license）相容性、原作者同意與**來源（provenance）**追蹤都將成為重要的研究與治理議題。

最後，在**長期保存層面**，Lean Pool 可以借鏡數位典藏領域的做法，定期產生不可變快照（immutable snapshot）、賦予 DOI，並將其備份至 Zenodo 等長期典藏平臺。這不僅能確保形式化數學的持久可取得性，也能讓 Lean Pool 真正成為數學文獻的正式對應物（formal analogue），而不僅僅是一個活躍的 GitHub 儲存庫（repository）。

## 論文問答

**Q1：Lean Pool 試圖解決什麼問題？**
A：Lean Pool 試圖解決研究級數學形式化成果難以長期保存與維護的問題。隨著生成式 AI 能快速產出數學論證，驗證已成為新的瓶頸，而 Lean 雖然是主要的證明驗證語言，其標準函式庫 Mathlib 的成長速度卻受嚴格人工審查限制，無法涵蓋大量研究級數學。Lean Pool 因此建立一個由 AI 代理維護的動態檔案庫，讓已完成的形式化專案能持續相容於不斷演進的 Lean/Mathlib 生態系，並供後續研究重複使用。

**Q2：現有方法（如 Mathlib）為何無法滿足需求？**
A：Mathlib 作為 Lean 的標準數學函式庫，雖然提供了大量基礎定義與定理，但缺乏許多研究級數學所需的內容。更重要的是，Mathlib 採用嚴格的人工審查流程，使其成長速度趨於線性，難以跟上 AI 生成證明與形式化專案的爆發速度。這種瓶頸使得許多獨立完成的形式化專案無法被有效整合、維護與重複利用，最終可能隨著 Lean/Mathlib 版本更新而失效。

**Q3：為何維護形式化數學如此重要？**
A：形式化數學的價值不僅在於當下驗證證明的正確性，更在於能成為後續研究的基礎。當 Lean 與 Mathlib 不斷演進時，舊有的形式化專案若無人維護，將因版本不相容而無法被新研究引用或匯入。因此，持續維護形式化成果能確保數學文獻中的定理、假設與證明可被長期檢索、檢視與重複使用，進而支持數學知識的累積與傳播。

**Q4：Lean Pool 的核心方法是什麼？**
A：Lean Pool 的核心方法是建立一個由 AI 代理與人類協作維護的集中式形式化數學檔案庫。它透過「匯集」機制將符合資格的獨立形式化專案整合到共同的 Lean/Mathlib 環境中，並由 AI 代理負責版本升級、錯誤修復、程式碼最佳化與持續整合檢查。Lean 核心保證證明正確性，而嚴格的 linter 與 LLM 審查則確保定義與定理敘述的品質，形成一個可持續運作的維護流程。

**Q5：Lean Pool 的關鍵創新有哪些？**
A：Lean Pool 的關鍵創新在於將 AI 代理大規模引入形式化數學的維護與最佳化流程，而不僅僅是證明生成。它結合了自動化的版本升級、程式碼簡潔化、編譯速度與記憶體使用最佳化，並透過 LLM 審查補足傳統 linter 無法涵蓋的語意品質檢查。此外，它提出了一種類似 arXiv 的「形式化對應物」願景，讓數學論文與其形式化版本並存，並在文獻引用與形式化依賴之間建立對應關係。

**Q6：Lean Pool 在設計上做了哪些重要選擇？**
A：Lean Pool 在設計上強調品質控管、授權合規與歸屬保存。被匯集的專案必須是嚴謹完整的形式化、不得含有 `sorry` 或 `admit`、只能使用限定的公理，並且必須採用 Apache-2.0 或 MIT 開源授權。每個專案都需要一張卡片記錄作者、上游來源、證明來源與主要結果，以確保即使由 AI 代理或維護者匯入，原始貢獻仍能被正確歸屬。

**Q7：Lean Pool 目前的規模與統計數據為何？**
A：根據論文所述，Lean Pool 目前已匯集 211 個專案，包含超過 320 萬行 Lean 程式碼，並有 18 位貢獻者參與。Lean 版本至今已升級六次，顯示檔案庫持續跟進 Lean/Mathlib 的演進。這些數據顯示 Lean Pool 已具備相當規模，並且能夠透過自動化流程管理大量形式化專案的生命週期。

**Q8：Lean Pool 在維護與最佳化方面取得了哪些關鍵成果？**
A：Lean Pool 的歷史建置紀錄顯示，AI 代理輔助的版本升級能夠修復因 Mathlib 更新而產生的相容性錯誤，使舊專案重新可編譯。此外，已接受的變更展示了整個程式碼庫層級的證明縮短、編譯速度提升與記憶體使用降低。這些成果說明代理輔助維護不僅能恢復相容性，還能持續改善形式化程式碼的品質與效能。

**Q9：Lean Pool 是否提供關於其有效性的證據或比較分析？**
A：雖然論文未以傳統消融實驗呈現，但提供了多項證據支持其有效性，包括歷史建置紀錄、已接受的程式碼最佳化變更，以及獨立的 LeanEval 審計顯示檔案庫中的數學確實被後續研究級形式化所重用。這些紀錄也揭示了自動化後續修復、大規模審查的資源需求，以及可重用介面與編譯成本之間的權衡。整體而言，這些證據共同描繪出 AI 維護在實際運作中的成效與挑戰。

**Q10：Lean Pool 有哪些實際應用場景？**
A：Lean Pool 可應用於數學研究者發表新定理時同步釋出經過驗證的形式化版本，讓讀者能立即檢查證明並引用相關定理。它也適合保存由 AI 生成的數學論證所伴隨的形式化證明，例如 OpenAI 的相關工作所示。此外，後續研究可以直接匯入 Lean Pool 中的定理，建立在已被驗證的結果之上，減少重複形式化的成本。

**Q11：Lean Pool 在運營與產品層面有哪些考量？**
A：Lean Pool 在運營上採用每日自動化作業，包括搜尋新形式化專案、檢查開放 PR、處理維護議題、最佳化現有專案，以及在 Zulip 發布每日公告。它提供三種文件形式：傳統索引、闡述性文件與每日公告，以協助使用者發現與理解內容。這些設計顯示 Lean Pool 不僅是技術原型，更是一個試圖降低使用阻力、促進社群參與的長期運營產品。

**Q12：Lean Pool 對形式化數學與 AI 領域可能帶來什麼影響？**
A：Lean Pool 提出了一種新的典範，讓 AI 代理承擔形式化數學中繁瑣但必要的維護工作，從而讓人類研究者與貢獻者能專注於創造性任務。它有潛力成為 arXiv 的形式化對應物，改變數學論文發表與知識累積的方式。長遠來看，這種模式可能加速研究級數學的形式化普及，並促進 AI 生成數學與人類數學社群之間的信任與協作。

**Q13：Lean Pool 承認哪些限制？**
A：論文坦承人類撰寫部分僅有一頁，其餘幾乎由 AI 生成，這在某種程度上反映了該專案本身對 AI 代理的依賴。此外，Lean Pool 的運作紀錄顯示自動化流程仍需後續人工修復，而大規模 LLM 審查也消耗可觀的運算資源。這些限制提醒我們，AI 維護雖然能顯著提升效率，但目前仍無法完全取代人類監督與判斷。

**Q14：Lean Pool 在實際運作中遇到哪些失敗案例或挑戰？**
A：根據論文記錄，AI 代理在初步自動化後仍需進行後續修復，顯示自動維護並非總能一次到位。大規模 LLM 審查也帶來顯著的資源需求，包括時間與運算成本。此外，在設計可重用介面與控制編譯成本之間存在權衡，某些為了提升可重用性的設計可能會增加整體編譯負擔，這是維護大型形式化檔案庫時必須持續面對的挑戰。

**Q15：Lean Pool 未來的發展方向為何？**
A：Lean Pool 的願景是成為類似 arXiv 的形式化數學共享平台，讓大多數新數學論文在發表時都伴隨經過維護的形式化版本。未來可能進一步擴大 AI 代理在發現、匯集、審查與最佳化方面的自動化程度，同時改善文件與檢索機制以提升可用性。隨著形式化技術變得更加容易，Lean Pool 也有機會與更多數學期刊、預印本平台整合，成為數學知識生態系中不可或缺的一環。

## 實務應用指南

### 適用場景

1. **研究機構的形式化數學資產庫**  
   數學系、理論資訊科學實驗室或 AI for Math 團隊可將內部已完成的 Lean 形式化專案匯集為單一動態檔案庫，避免每個專案各自維護 Mathlib 版本，並讓後續研究能重複使用已驗證的定理。

2. **AI 生成證明的驗證與典藏**  
   當生成式 AI 產出大量數學論證時，可將其轉為 Lean 形式化後納入檔案庫。Lean 核心確保證明正確性，LLM 審查與嚴格 Linter 則把關定義與定理敘述品質，降低人工逐行檢查的負擔。

3. **企業關鍵演算法的正確性基線**  
   密碼學、分散式系統、金融模型等領域可將核心引理與協議性質以 Lean 形式化，並透過 AI 維護的檔案庫持續追蹤 Mathlib 升級，確保證明在函式庫演進後仍保持相容。

4. **線上課程與開放教材的維護**  
   大學可將課程中的證明轉為 Lean 形式化教材，利用自動化排程進行版本升級與程式碼簡化，讓教材隨著 Mathlib 更新而保持可編譯，並透過 Exposition 與索引供學生查閱。

5. **arXiv 的形式化對應物**  
   學術社群可要求或鼓勵作者在 arXiv 發表論文時，同步提交經維護的 Lean 形式化到檔案庫，使文獻引用與形式化匯入形成對應的知識圖譜。

### 實作前置條件

**資料前提**
- 已完成且嚴謹完整的形式化專案：不得包含 `sorry`、`admit`、未經允許的 axiom，也不得使用 `set_option` 或繞過資源限制的機制。
- 專案必須採用 Apache-2.0 或 MIT 授權條款，並附帶專案卡片：作者、上游來源、證明來源（人工／AI／混合）、主要結果與非正式敘述。
- 需有清晰的歸屬與授權鏈，避免後續授權污染。

**運算前提**
- 持續整合（CI）環境：需支援大型 Mathlib 依賴專案的編譯，具備足夠 RAM 與 CPU 核心。
- 儲存空間：用於保存多版本原始碼、編譯快取與歷史建置紀錄。
- LLM API 或本地模型：供 LLM 審查定義與定理敘述使用。
- 自動化排程基礎設施：每日搜尋、版本升級、最佳化與公告任務。

**技能前提**
- 熟悉 Lean 語言與 Mathlib 生態。
- 具備 CI/CD、Linter 設定與 GitHub 拉取請求（PR）流程經驗。
- 能設計 AI 代理（智能體）的工作流程，包括提示工程、錯誤修復迴圈與程式碼最佳化。
- 了解開源授權條款與學術歸屬規範。

### 實作步驟建議

1. **定義收錄範圍與品質閘門**  
   明確只收錄具名的已知結果、允許的 axiom 集合、禁止的程式碼模式，以及專案卡片必填欄位。

2. **建立統一的 Lean 儲存庫與 CI 管線**  
   設定單一儲存庫，鎖定 Lean 版本，配置嚴格的 Linter、編譯時間與 RAM 監控，並啟用快取以加速建置。

3. **設計匯集（pooling）流程**  
   支援人工貢獻與 AI 代理發現外部專案兩種途徑。匯集時需升級 Lean 版本、調整程式碼以通過 CI、補齊專案卡片，並確認授權條款。

4. **部署自動化檢查**  
   除了 Lean 核心的證明正確性驗證，還要檢查無 `sorry`/`admit`、無未經授權 axiom、無資源限制繞過，並執行風格與效能 Linter。

5. **引入 LLM 審查**  
   針對定義與定理敘述進行自動化審查，檢查命名一致性、假設完整性、與 Mathlib 慣例的相容性，並將審查結果附加到 PR。

6. **建立週期性維護作業**  
   排程每日或每週任務：偵測 Mathlib 新版本、自動升級 Lean 版本、修復編譯錯誤、縮短證明、降低編譯時間與 RAM 使用量。

7. **建構文件與發現機制**  
   維護傳統索引、闡述（Exposition）頁面，並在 Zulip 等管道發布每日專案公告，讓使用者能搜尋、理解並引用結果。

8. **設立人工監督與修復迴圈**  
   AI 代理完成初步升級或最佳化後，保留人工複審閘門；記錄後續修復案例，作為改進代理提示與工具的依據。

9. **持續度量與迭代**  
   追蹤匯集專案數量、程式碼行數、編譯時間、RAM 使用量、版本升級成功率與後續研究重用次數，並據此調整流程。

### 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **授權污染** | 匯集外部專案時可能混入非 Apache-2.0/MIT 授權條款的程式碼。 | 在匯集前強制檢查授權條款與來源，並要求專案卡片記載上游來源。 |
| **定理敘述錯誤** | Lean 核心只驗證證明，不保證定理敘述符合數學原意。 | 對定義與定理敘述進行 LLM 審查，並保留人工專家複審。 |
| **Mathlib 版本頻繁變動** | 每次升級都可能導致大量專案編譯失敗。 | 採用漸進式版本升級、建立修復劇本、保留可回滾的歷史建置。 |
| **資源爆炸** | 大型形式化專案可能耗盡 CI 的 RAM 或編譯時間。 | 設定嚴格的資源上限、監控熱點、定期最佳化高成本證明。 |
| **歸屬與貢獻混淆** | AI 代理與人類協作時，難以區分實際勞動比例。 | 透過專案卡片與 Git 紀錄保留上游作者、提交者與證明來源標籤。 |
| **過度依賴 AI 維護** | 代理可能產生看似合理但實際錯誤的修復。 | 維持人類最終把關機制，並建立審計日誌記錄每次代理修改。 |

### 與其他技術的整合建議

- **與 arXiv 及學術引用系統連結**  
  在 Exposition 頁面與專案卡片中嵌入 arXiv ID 與 DOI，並提供可引用的 BibTeX，使文獻引用與形式化匯入形成對應關係。

- **與 GitHub PR 流程整合**  
  將 Linter、LLM 審查、編譯測試與資源監控設為 PR 的強制檢查項目，確保只有通過全部閘門的變更才能合併。

- **與即時通訊平台整合**  
  透過 Zulip 機器人自動發布每日專案公告、版本升級狀態與最佳化成果，提升社群參與度與透明度。

- **與 Mathlib 上游同步**  
  建立自動化偵測機制，在 Mathlib 發布新版本後觸發升級流程，並將修復經驗回饋給上游社群。

- **與開發環境整合**  
  支援 VS Code Lean 擴充功能，讓使用者能直接瀏覽、匯入與驗證檔案庫中的定理。

- **與企業 CI/CD 管線整合**  
  將 Lean Pool 作為形式化驗證的依賴庫，企業專案在每次建置時引用經維護的版本，確保關鍵性質持續有效。
