## 摘要翻譯

LLM 作為評判者（LLM-as-a-judge）已成為自動化評估（automated evaluation）的標準做法，但它面臨高昂成本、顯著延遲與不透明決策等問題——這些限制削弱了其可擴展性與可靠性。我們提出一個簡單且高效的替代方案：程式蒸餾（program distillation）。我們不再於評估階段提示 LLM，而是將其決策邏輯蒸餾為一個程式委員會（committee of programs），由這些程式直接對候選樣本（candidate）評分。這些程式化評判者（programmatic judges）具備透明性，可檢視且可編輯，並消除每樣本 API 成本（per-sample API costs）。基於此概念，我們提出 PAJAMA，此系統將程式合成為評判者、將其決策聚合為聯合裁決（joint verdict），並納入後備機制（fallback mechanism），選擇性地將低信心案例（low-confidence cases）升級並交由 LLM 處理。橫跨五個資料集（datasets）與四個模型家族（model families），我們證明程式化評判者能達到與 130 億參數規模的 LLM 評判者（13B-size LLM judge）相當的表現。當使用程式輸出作為路由訊號（routing signals）時，PAJAMA 同時提升了準確率（accuracy）與吞吐量（throughput），並推進了帕雷托前沿（Pareto frontier）。除了評估之外，程式化評判者還能產生低成本且有效的獎勵訊號（reward signals）：在 RewardBench 上，從程式裁決（verdicts）蒸餾而來的獎勵模型（reward model）優於以專有 LLM（proprietary LLM）標籤（labels）訓練的獎勵模型，且 API 成本降低兩個數量級（orders of magnitude）。

### 核心貢獻（3～5點）
- 提出「程式蒸餾」方法，將 LLM 評判者的決策邏輯轉換為可執行、可檢視、可編輯的程式化評判者，以解決傳統 LLM-as-a-judge 的高成本、高延遲與不透明性問題。
- 設計並實作 PAJAMA 系統，結合程式合成、聯合裁決聚合與選擇性升級後備機制，兼顧評估準確率與運算效率。
- 在五個資料集與四個模型家族上驗證，程式化評判者可達到與 130 億參數規模 LLM 評判者相當的表現。
- 展示以程式輸出作為路由訊號時，PAJAMA 能同時提升準確率與吞吐量，推進準確率—吞吐量的帕雷托前沿。
- 證明程式化評判者所產生的獎勵訊號可用於訓練獎勵模型，在 RewardBench 上以遠低於專有 LLM 標籤的 API 成本達到更優表現。

### 適合對象
本論文適合從事大型語言模型評估、自動化評測方法、獎勵模型訓練與強化學習對齊研究的學者與工程師；特別是關注 LLM-as-a-judge 的成本、延遲、可解釋性與可擴展性，並希望以輕量、透明且可編輯的程式化方案取代或輔助專有 LLM 評估流程的讀者。

## 深度分析

#### 方法論解析

##### 核心典範：程式蒸餾（program distillation）

本文提出的 PAJAMA（Program-As-a-Judge Automated Model Assessment）系統，核心在於將傳統 LLM-as-a-judge（LLM 作為評判者）典範中的「每次評估都呼叫模型推論」，轉換為「一次性合成可執行程式，之後在本機重複執行」。這個過程稱為程式蒸餾（program distillation）：LLM 不再直接對每個候選樣本（candidate）給出裁決（verdict），而是被提示生成一段 Python 評判函式（Python judging function），把其內隱的評判邏輯（judging logic）編碼成明確的程式碼。此函式會根據評估量規（evaluation rubric）抽取可解釋特徵（interpretable features）——例如語義漂移（semantic drift）透過詞頻向量餘弦相似度（TF-vector cosine similarity）衡量、語篇段落間的主題一致性（topic consistency）、對矛盾（contradiction）與截斷（truncation）的明確懲罰項（explicit penalties）——最後組合成加權分數（weighted score）。

這樣的轉換帶來三項立即優勢：

1. **成本結構改變**：API 成本（API cost）從與資料集大小成正比，降為與生成的程式數量成正比。程式一旦合成即可儲存並在本機執行（local execution），後續每個樣本不再產生 per-sample API costs（每樣本 API 成本）。
2. **延遲與吞吐量（latency / throughput）**：程式執行速度遠低於模型推論，可達數十倍加速。
3. **透明性與可編輯性（transparency / editable）**：評判邏輯以程式碼呈現，研究者可以逐行檢視、修改、注入領域知識（domain knowledge），甚至朝形式化可驗證（formally verifiable）方向發展。

##### PAJAMA 的三項設計挑戰與對應機制

單一程式化評判者（programmatic judge）難以泛化（generalization）到所有輸入；多個程式容易產生重複邏輯；不同評估量規產生的分數尺度不一且帶雜訊。針對這三點，PAJAMA 設計了三個模組：

1. **多樣化評估量規驅動的合成（diverse rubric-driven synthesis）**  
   系統先整理一組可表達為程式碼的評估量規，再讓 LLM 針對每條量規生成不同的 Python 評判函式。這相當於建立一個程式委員會（committee of programs），每個成員代表不同的決策規則，從而降低單一邏輯的盲點。

2. **校準與聚合（calibration & aggregation）**  
   各程式輸出的原始分數因量規不同而尺度各異，因此需要校準。接著透過類似弱監督（weak supervision）中標籤函式（labeling function）聚合的機制，將多個程式評判器的裁決整合為聯合裁決（joint verdict）。這一步解決了「 noisy scores at different scales」的問題，並把程式間的衝突轉化為穩定的共同判決。

3. **信心感知的後備機制（confidence-aware fallback mechanism）**  
   對於委員會意見分歧或整體信心分數（confidence）過低的低信心案例（low-confidence cases），系統執行選擇性升級（selective escalation），將其遞交給 LLM 評判者（LLM judge）處理。這形成一個混合評估系統：簡單樣本由程式快速處理，困難樣本才動用昂貴模型，兼顧準確率（accuracy）與吞吐量（throughput）。

##### 工作流程

如圖 2 所示，給定查詢 q 與兩個候選回應 r^(1)、r^(2)，PAJAMA 首先讓多個程式化評判者產生初始評分；接著對輸出進行校準與選擇，再聚合為最終偏好；不確定的案例則透過路由訊號（routing signals）升級至 LLM 評判者，產生最終偏好。這個設計把「模型推論」當作稀有資源來使用，而「程式執行」則作為大規模篩選與評分的主力。

#### 實驗數據解讀

##### 基準比較：獨立程式評判者已可媲美 130 億參數 LLM

作者在 5 個偏好資料集（datasets）、橫跨 4 個模型家族（model families）上驗證。關鍵發現是：獨立運作的程式化評判者（programmatic judges）在準確率上能夠匹配 OLMo-2-13B-Instruct 這個 130 億參數規模的 LLM 評判者（13B-size LLM judge），同時執行速度快上 **47.25×**。這顯示對於許多偏好判斷任務，評判邏輯確實可以被蒸餾成輕量、可解釋的程式，而不需要每次都啟動大型語言模型。

##### 混合系統：推進準確率–吞吐量帕雷托前沿（accuracy–throughput Pareto frontier）

當把程式輸出作為路由訊號，並結合較小的 LLM 時，PAJAMA 在準確率與吞吐量的權衡上明顯優於單純使用 LLM：

- 搭配 OLMo-2-7B-Instruct：準確率提升 **+5.0%**，吞吐量提升 **2.9×**。
- 搭配 Qwen2.5-3B-Instruct：準確率提升 **+2.6%**，吞吐量提升 **2.2×**。

這些數據說明後備機制（fallback mechanism）有效地把「容易判斷」的樣本交給程式，把資源集中在真正需要模型語義能力的樣本上。結果不是單純犧牲準確率換速度，而是同時改善兩者，真正推進了帕雷托前沿（Pareto frontier）。

##### RewardBench：低成本高品質的獎勵訊號（reward signals）

在 RewardBench（獎勵模型評測基準）上，作者進一步展示程式化評判者的應用價值：用程式裁決（verdicts）所產生的標籤（labels）訓練獎勵模型（reward model），其表現優於使用專有 LLM（proprietary LLM）偏好標籤訓練的獎勵模型，且 API 成本（API cost）降低 **50×**，在評估階段甚至不需要任何專有模型呼叫。這對獎勵模型蒸餾（reward model distillation）與強化學習（reinforcement learning）後訓練管線具有重要意義——它提供了一種便宜、可解釋、且品質不遜於昂貴專有模型的獎勵訊號來源。

##### 對風格偏誤（stylistic biases）的穩健性

實驗也顯示程式化評判對 LLM 評判常見的系統性偏誤（systemic bias）——例如偏好冗長（verbosity）、豐富格式（rich formatting）或情緒化語言（emotionally charged language）——較不敏感。此外，若搭配 coding agent 進行迭代式程式校準，穩健性還可進一步提升。這點凸顯了「把評判邏輯編碼化」在對抗風格偏誤上的潛力。

#### 與現有研究的比較

##### 相對於 LLM-as-a-judge（LLM 作為評判者）

現有自動化評估（automated evaluation）主流是反覆呼叫 LLM 進行成對偏好標註（pairwise preference labeling）、評分量規準則（rubric criteria）或提供強化學習回饋。這雖然方便，但存在四大問題：

- **推論成本（Inference Cost）**：擴展到百萬級樣本時，專有模型 API 支出（API spending）高昂；開放權重部署（open-weight deployments）也需大量 GPU 需求（GPU demand）。
- **不透明邏輯（Opaque Logic）**：即使 LLM 提供理由說明（justification），其決策過程（decision process）仍難以驗證，可能受幻覺（hallucination）影響。
- **系統性偏誤（Systemic Bias）**：對冗長、格式、情緒化語言等風格偏誤敏感。
- **重新推論成本（Re-inference Tax）**：修改單一評分準則就必須對整個資料集重新推論。

PAJAMA 透過程式蒸餾（program distillation）把「每次推論」變成「一次性投資（one-time investment）」加「本機執行」，從根本上改變成本結構；同時提供可檢視（inspectable）、可編輯的評判邏輯，並降低風格偏誤。

##### 相對於弱監督（weak supervision）

弱監督領域長期使用標籤函式（labeling functions）從啟發式規則、領域知識或預訓練模型產生雜訊標籤，再聚合為機率性標籤決策。PAJAMA 借鑑此框架，但將其應用場景從「建立分類資料集」轉移到「模型評估」：把每個程式化評判者視為一個標籤函式，透過校準與聚合產生聯合裁決（joint verdict）。差異在於 PAJAMA 的標籤函式是由 LLM 自動從評估量規合成，而非手工設計，擴展性更強。

##### 相對於 LLM 路由策略（routing strategies）

現有路由策略多在多個 LLM 之間選擇適合的模型，分為依賴啟發式的 model-free 方法（如最近鄰查找）與需要額外訓練分類器的 model-based 方法。前者受限於啟發式強度，後者則增加推論延遲與標註成本。PAJAMA 提出的是「程式→LLM」的單向升級路由：利用程式委員會內部訊號作為路由訊號（routing signals），只把不確定樣本升級給 LLM。這是一種無需額外監督、低延遲的後備機制（fallback mechanism），與傳統在多個 LLM 間選擇的路由邏輯互補。

##### 限制與待釐清之處

儘管優勢明顯，PAJAMA 仍有幾項限制：

- **合成品質依賴 LLM 能力**：若 LLM 無法把複雜語義判斷正確轉譯為程式，則程式評判者會遺失細微差別。
- **評估量規覆蓋率**：系統表現受限於 curated rubrics 是否涵蓋任務所需的各種判斷維度。
- **校準與聚合的穩定性**：在不同資料集上，校準方法與聚合模型可能需要調整。
- **後備門檻的權衡**：信心門檻過低會犧牲準確率，過高則失去成本優勢，最佳值可能隨任務而異。
- **泛化到更複雜任務**：目前實驗集中在偏好資料集與 RewardBench，對於需要深層常識、因果推理或開放式生成的評估，程式化方法的能力邊界尚待驗證。

#### 可重現性評估

##### 開源釋出狀況

根據論文第 1 頁腳註，作者已釋出原始碼（source code）、專案頁面與展示系統，連結為 `https://sprocketlab.github.io/PAJAMA/`。這為可重現性奠定良好基礎。若程式碼包含合成提示（synthesis prompt）、評估量規（evaluation rubric）範本、校準與聚合邏輯、以及後備機制的門檻設定，則其他研究者應能在公開資料集上復現主要結果。

##### 資料集與模型權重

實驗使用的五個偏好資料集與 RewardBench（獎勵模型評測基準）均為公開資料集，模型家族包含 OLMo-2 與 Qwen2.5 等開放權重模型（open-weight deployments），這些權重可公開取得。因此基準實驗的硬體與資料門檻相對較低。

##### 需要注意的重現變因

- **LLM 合成器的不確定性**：程式化評判者由 LLM 生成，不同模型版本、溫度參數或提示設計會產生不同程式，進而影響結果。論文需清楚說明使用的合成模型與取樣參數。
- **專有 LLM 標籤**：RewardBench 實驗中與專有 LLM（proprietary LLM）標籤比較時，若該模型為商業 API，則其輸出可能隨時間變化，重現時需記錄 API 版本與呼叫時間。
- **程式執行環境**：Python 評判函式可能依賴特定套件版本（如 scikit-learn、NLTK、transformers），環境差異可能影響特徵計算與執行速度。

整體而言，PAJAMA 的可重現性屬於中上水準：核心程式碼與資料公開，但「LLM 生成程式」這一步本身帶有隨機性與模型依賴性，建議作者提供生成的程式委員會（committee of programs）快照，以便其他研究者直接比較。

#### 未來研究方向

1. **自動化評估量規發掘**  
   目前 PAJAMA 依賴人工整理或 curated 的評估量規。未來可研究如何讓 LLM 自動從任務描述、錯誤案例或人類回饋中發掘新的評估量規，進一步降低人工設計成本。

2. **形式化驗證與可解釋性增強**  
   程式化評判者具備可解釋性（interpretability），可進一步引入靜態分析、單元測試或形式化驗證（formally verifiable）技術，確保評判函式不會對特定類型輸入產生系統性錯誤。

3. **跨領域與跨語言泛化**  
   當前實驗主要聚焦英文偏好資料集。未來可探討程式化評判者在多語言、程式碼生成、數學推理、長文件摘要等領域的泛化能力，並研究領域適應（domain adaptation）策略。

4. **線上校準與人類回饋迴路**  
   將 PAJAMA 與人類回饋結合，讓系統在部署過程中持續校準程式評判者、更新權重，並動態調整後備門檻，形成自我改進的評估管線。

5. **與小型 LLM 評判者的協同**  
   除了「程式→大型 LLM」的兩層架構，未來可研究「程式→小型 LLM→大型 LLM」的多層路由，讓不同成本與能力的模型各司其職，進一步推進帕雷托前沿（Pareto frontier）。

6. **獎勵模型蒸餾的深入分析**  
   RewardBench 結果已顯示程式標籤可訓練出高品質獎勵模型（reward model）。未來可探討程式標籤與人類標籤、專有 LLM 標籤的混合比例、錯誤模式差異，以及對強化學習（reinforcement learning）收斂性的影響。

7. **對抗穩健性與偏誤審計**  
   雖然程式化評判者對風格偏誤（stylistic biases）較不敏感，但仍可能對其他結構化特徵產生偏誤。未來可建立系統化的偏誤審計工具，並結合對抗樣本測試來提升穩健性。

8. **蒸餾到神經評判模型**  
   最終可將程式委員會的聯合裁決進一步蒸餾成輕量神經網路，兼具程式透明性與神經網路的語義泛化能力，形成「程式監督 → 神經模型」的兩階段蒸餾。

## 論文問答

**Q1：LLM-as-a-judge 目前面臨哪些主要限制，使得其難以大規模部署？**
A：論文指出 LLM 評判者存在四大核心問題：推論成本高昂、決策邏輯不透明、系統性偏誤，以及重新推論成本。當評估規模達到數百萬樣本時，無論是呼叫專有 API 還是部署開放權重模型，都會產生可觀的 API 支出、延遲與 GPU 需求。此外，LLM 的內部決策過程難以驗證，容易受冗長、豐富格式或情緒化語言等風格偏誤影響；而每次修改評分準則都必須對整個資料集重新推論，造成浪費。

**Q2：為什麼這些限制在 LLM-as-a-judge 越來越普及的同時，變得越來越難以忽視？**
A：隨著 LLM 評判者被廣泛用於成對偏好標註、獎勵模型蒸餾與強化學習回饋等關鍵流程，評估已成為現代機器學習管線的核心元件。當評估頻率與資料量急遽增加時，每樣本都呼叫 LLM 的成本與延遲會被快速放大，讓系統難以擴展。同時，若評估結果不透明或帶有偏誤，將直接影響後續模型訓練與部署的可靠性，使得研究者與工程師迫切需要更經濟、可解釋且可信的自動化評估方案。

**Q3：可擴展且可靠的自動化評估為何重要？**
A：高品質的自動化評估是決定模型能否持續改進的關鍵，因為它提供了偏好標籤、獎勵訊號與策略回饋。若評估本身成本過高，團隊就無法頻繁地對大量候選樣本進行篩選與迭代；若評估結果不穩定或難以理解，則會讓整個訓練管線建立在不可靠的訊號之上。因此，降低評估成本並提升透明度，不僅能加速實驗週期，也能增強對模型行為的掌控與信任。

**Q4：什麼是程式蒸餾（program distillation），它與傳統 LLM-as-a-judge 的根本差異為何？**
A：程式蒸餾是指讓 LLM 在合成階段一次性地生成其評判邏輯，並將這些邏輯轉換為可執行的 Python 評判函式，之後直接在本地執行這些程式來對候選樣本評分。不同於傳統方式需要對每個樣本反覆呼叫 LLM，程式蒸餾把評估從「基於模型的推論」轉變為「合成程式執行」。這使得 API 成本只與生成的程式數量相關，而非資料集大小，同時帶來更低的延遲與更高的可解釋性。

**Q5：PAJAMA 系統包含哪三個核心元件，各自解決什麼問題？**
A：PAJAMA 的第一個元件是經過精心設計、可表達為程式碼的評估量規，用於引導 LLM 合成多樣化的評判函式，避免邏輯過於單一。第二個元件是建模步驟，負責校準各程式評判器的輸出，並將彼此衝突的裁決聚合為一個聯合判決。第三個元件是信心感知的後備機制，會把低信心案例選擇性升級給 LLM 評判者，從而同時兼顧速度與準確率。

**Q6：為什麼 PAJAMA 選擇使用「程式委員會」而非單一程式來進行評估？**
A：單一程式評判器往往難以泛化到所有輸入，且單純合成的多個程式容易產生重複的邏輯。此外，來自不同評分量規的程式會使用不同的分數尺度，並帶有各自的雜訊。透過組成一個程式委員會，PAJAMA 能夠結合多樣化的決策規則，並利用校準與聚合來解決衝突，從而提升整體評估的穩健性與準確率。

**Q7：論文在哪些資料集與模型家族上驗證了 PAJAMA？**
A：研究團隊在五個偏好資料集與四個模型家族上進行實驗，涵蓋不同規模與架構的開放權重模型，例如 OLMo-2-13B-Instruct、OLMo-2-7B-Instruct 與 Qwen2.5-3B-Instruct。此外，他們也在 RewardBench 上測試程式化評判者所產生的獎勵訊號品質。這樣的跨資料集與跨模型設計，有助於證明方法在不同情境下的通用性與穩定性。

**Q8：PAJAMA 的主要實驗結果有哪些？**
A：獨立的程式化評判者能夠達到與 OLMo-2-13B 評判者相當的準確率，同時執行速度快上 47.25 倍。當作為路由訊號與較小的 LLM 搭配時，PAJAMA 能推進準確率與吞吐量的帕雷托前沿：例如搭配 OLMo-2-7B 可提升 5.0% 準確率並達到 2.9 倍吞吐量，搭配 Qwen2.5-3B 則提升 2.6% 準確率並達到 2.2 倍吞吐量。在 RewardBench 上，以程式化評判者標籤蒸餾出的獎勵模型，表現優於以專有 LLM 標籤訓練的模型，且 API 成本降低約兩個數量級。

**Q9：論文進行了哪些消融或穩健性分析？**
A：作者發現程式化評估對帶有偏誤的樣本具有較強的穩健性，較不容易受到風格偏誤影響。進一步地，將程式化評判與能夠迭代校準程式的 coding agent 結合，可以進一步提升其穩健性。這些分析顯示，透過適當的校準與持續優化，程式評判器不僅能維持高效率，也能在品質上接近甚至超越部分 LLM 評判者。

**Q10：哪些實際應用場景最能從 PAJAMA 受益？**
A：PAJAMA 特別適合需要大規模、低延遲評估的場景，例如每日處理數百萬筆對話的偏好標註管線、獎勵模型訓練、強化學習回饋迴路，以及模型上線後的持續監控。在這些情境中，每筆樣本都呼叫專有 LLM 會迅速累積驚人的 API 支出，而程式化評判者能以極低成本提供穩定訊號。透過後備機制，系統還能在高價值的邊界案例上保留 LLM 的判斷能力，達成成本與品質的平衡。

**Q11：在產品化部署 PAJAMA 時，需要考慮哪些工程與維護問題？**
A：首先必須建立一套高品質且涵蓋關鍵維度的評分量規，因為程式的品質高度依賴於這些準則的設計。其次需要持續校準各程式的輸出尺度，並根據業務需求調整後備機制的信心門檻，以決定多少比例的樣本要交回 LLM。最後，由於程式是可檢視且可編輯的，團隊應建立版本控制與審查流程，讓領域專家能夠注入知識、修正錯誤，並確保評估邏輯隨產品演進而更新。

**Q12：這項研究可能對自動化評估與弱監督領域帶來什麼影響？**
A：PAJAMA 提出了一種新的評估典範，將評判邏輯從黑箱模型中蒸餾出來，轉變為透明、可執行且可編輯的程式。這不僅降低了大規模評估的門檻，也讓弱監督技術從傳統的分類標籤任務擴展到模型評估與獎勵訊號生成。長遠來看，這種方法可能促使更多研究者與工程師將評估視為可設計、可驗證的系統元件，而非單純依賴昂貴且不透明的 LLM 呼叫。

**Q13：論文承認 PAJAMA 有哪些限制？**
A：作者指出，單一程式難以泛化，且自動合成的程式容易出現邏輯重複或分數尺度不一致的問題。此外，整個流程仍依賴 LLM 進行程式合成與低信心案例的後備判斷，因此若 LLM 在合成階段產生錯誤邏輯，後續評估也會受到影響。評估量規的設計品質同樣是關鍵瓶頸，若量規無法涵蓋任務所需的細微判斷，程式評判器就可能遺漏重要維度。

**Q14：在哪些情況下 PAJAMA 可能會失敗或表現不佳？**
A：當輸入屬於評分量規未涵蓋的新穎領域，或需要深厚世界知識與常識推理才能判斷的模糊案例時，程式評判器可能難以做出正確裁決。若對手刻意產生能欺騙簡單特徵的對抗樣本，例如透過表面上的主題一致性掩蓋邏輯矛盾，也可能讓程式誤判。此外，當多個程式評判器對某樣本意見分歧且信心分數都很低時，即使交給 LLM 後備，仍可能面臨整體不確定性過高的風險。

**Q15：未來可以朝哪些方向進一步發展這項工作？**
A：未來研究可以探索更強大的程式合成與自動校準方法，例如讓 coding agent 自動發現並修正評估量規，或結合形式化驗證技術來確保程式邏輯的正確性。另一個方向是擴展程式化評估的適用範圍，從成對偏好與獎勵訊號延伸到更複雜的開放式生成任務與多維度評分。最後，降低後備機制對 LLM 的依賴比例、提升程式委員會的整體信心，將是進一步降低成本與延遲的重要課題。

## 實務應用指南

### 適用場景

1. **大規模內容品質篩選**  
   當每日需要評估數十萬至上百萬則使用者生成內容（如客服對話、論壇回覆、教育平台作文）時，可透過程式化評判者對每個候選樣本進行本地打分，僅將低信心案例升級給 LLM 評判者，顯著降低 API 成本與延遲。

2. **RLHF 與獎勵模型訓練的成對偏好標註**  
   在強化學習或獎勵模型蒸餾流程中，需要大量成對偏好標籤。可先由程式委員會產生高品質偽標籤，再蒸餾成獎勵模型；論文顯示，在 RewardBench 上這種方式能以低兩個數量級的 API 成本達到優於專有 LLM 標籤的表現。

3. **搜尋與推薦結果的排序評估**  
   針對檢索結果、商品推薦或問答系統的多個候選答案，可用明確的評估量規（如相關性、主題一致性、資訊完整性）合成多個 Python 評判函式，快速產生可解釋的排序訊號。

4. **程式碼審查與技術文件評分**  
   將「可讀性」「邏輯一致性」「是否包含必要測試」等準則編碼為可執行程式，自動評估程式碼補全、Pull Request 或技術文件草稿，並讓工程師直接檢視與編輯評判邏輯。

5. **動態評分準則的快速上線**  
   當業務規則頻繁變動（如新增一條合規檢查、調整品牌語調標準），只需修改或重新合成對應的評判函式，無需對整個資料集重新呼叫 LLM，避免重新推論成本。

### 實作前置條件

- **資料準備**  
  - 一批具代表性的候選樣本與對應的查詢（query/response pair）。  
  - 人類或 LLM 產生的參考標籤，用於校準與驗證程式化評判者的準確率。  
  - 明確的評估量規 / 評分準則，最好已拆解為可觀察、可量化的特徵（如語義漂移、主題一致性、截斷、矛盾）。

- **運算資源**  
  - 執行 Python 評判函式的本地環境（CPU 即可，視吞吐量需求可橫向擴展）。  
  - 用於一次性程式合成的 LLM API 配額（建議使用能力較強的模型以提升初始程式品質）。  
  - 若採用 PAJAMA 的後備機制，需保留少量專有 LLM 或開放權重模型的推論配額，僅處理低信心案例。

- **技術能力**  
  - 熟悉 Python 與基礎自然語言處理工具（如 scikit-learn、spaCy、sentence-transformers）。  
  - 具備提示工程經驗，能將評估量規轉寫為「合成提示」。  
  - 了解弱監督、標籤聚合與基礎機率校準概念，以便實作聯合裁決與信心分數。

### 實作步驟建議

1. **定義與拆解評估量規**  
   將業務目標轉為 5–15 條獨立準則，每條準則對應一個可解釋特徵。例如「邏輯連貫性」可拆成「語篇段落間的主題一致性」與「前後句的語義漂移」。

2. **設計合成提示並產生評判函式**  
   對每條準則撰寫結構化合成提示，要求 LLM 輸出 Python 評判函式。提示中應指定輸入格式、輸出分數範圍、禁止行為（如不得直接呼叫外部 LLM），並要求函式內註解說明權重與懲罰項。

3. **建立程式委員會並執行本地評分**  
   將所有產生的程式化評判者組成委員會，對候選樣本批次執行。此時會得到多組不同尺度的分數與裁決。

4. **校準與聚合**  
   使用標籤資料對各程式的輸出進行校準（例如 Platt scaling 或 isotonic regression），解決不同程式分數尺度不一致的問題；再以多數決、加權投票或學習得到的聚合模型產生聯合裁決與信心分數。

5. **設定信心門檻與後備機制**  
   根據驗證集決定信心分數門檻。高信心樣本直接採用程式裁決；低信心案例選擇性升級給 LLM 評判者。透過調整門檻，在準確率與吞吐量之間取得所需的帕雷托前沿。

6. **迭代優化與領域知識注入**  
   定期抽樣檢視錯誤案例，並以編碼代理或人工方式修正評判函式。可加入領域知識（如專有名詞表、禁止用語清單）以提升穩健性，特別是針對帶有風格偏誤的樣本。

7. **部署與監控**  
   將程式委員會封裝為評估服務，整合至 CI/CD 或 MLOps 管線；持續監控程式執行成功率、後備比例、與人類標籤的一致性，並在準確率下降時觸發再合成。

### 潛在風險與注意事項

- **程式脆弱性與泛化不足**  
  單一評判函式容易在分佈外樣本上失效。建議始終使用多樣化的程式委員會，並透過校準與聚合降低單點失誤。

- **重複邏輯與低覆蓋率**  
  若合成提示過於相似，LLM 可能產出功能重複的程式。可在提示中要求不同特徵提取策略（詞頻向量、語義嵌入、規則比對），並以多樣性採樣增加委員會覆蓋面。

- **分數尺度不一致與雜訊**  
  不同程式可能輸出 0–1、1–5 或任意實數。未經校準直接聚合會扭曲聯合裁決，因此校準步驟不可省略。

- **過度依賴後備機制**  
  若信心門檻設得太低，大量樣本仍會送交 LLM，抵銷成本優勢。應以驗證集上的成本—準確率曲線選擇門檻，並監控實際後備比例。

- **評估量規本身的偏誤**  
  程式只會反映設計者寫入的規則。若量規隱含對冗長、豐富格式或情緒化語言的偏好，仍會產生系統性偏誤。建議定期與人類標籤比對，並進行偏誤審計。

- **生成程式碼的安全性**  
  由 LLM 產生的 Python 程式可能包含危險呼叫或資源耗盡迴圈。務必於沙箱環境中執行，限制網路與檔案系統權限，並對執行時間設上限。

### 與其他技術的整合建議

- **與現有 LLM 評判者並行部署**  
  初期可將 PAJAMA 視為影子系統，與現有 LLM-as-a-judge 同時運行，比對兩者的一致性與成本差異，再逐步擴大程式化評判者的採用比例。

- **嵌入 RLHF 與獎勵模型蒸餾管線**  
  將程式化評判者產生的標籤作為弱監督訊號，訓練輕量獎勵模型；在 RewardBench 等基準上，這種做法已展現低成本高效益的優勢。

- **串接 MLOps 評估與 CI/CD**  
  把評判函式納入模型發布前的自動化評估閘道，對新版本模型進行大規模回歸測試；由於本地執行成本低，適合每次程式碼合併都觸發完整評估。

- **結合可觀測性工具**  
  記錄每個樣本的程式輸出、信心分數、後備標記與最終裁決，並以視覺化儀表板追蹤。當後備比例或錯誤率異常時，可快速定位是哪些評判函式需要更新。

- **與編碼代理協作迭代**  
  將錯誤案例自動餵給編碼代理，請其根據失敗模式修改評判函式，形成「合成 → 執行 → 診斷 → 修正」的閉環，進一步提升長期穩健性。

### 給不同背景讀者的閱讀建議

- **AI 工程師**  
  請特別關注程式合成提示的設計、程式委員會的多樣性、輸出校準方法，以及後備機制的信心門檻設定；這些是決定系統能否在實際產品中同時達成高準確率與高吞吐量的關鍵，並可參考論文附錄或開源程式碼進行復現。

- **研究人員**  
  本文的貢獻在於將弱監督與程式合成引入評估領域，建議深入分析聯合裁決的建模方式、與傳統 LLM 評判者的偏誤比較，以及 RewardBench 上獎勵模型蒸餾的實驗設計；未來可探索更複雜的聚合模型、主動學習選樣，或形式化驗證評判函式的可能性。

- **產品經理**  
  重點閱讀成本、延遲與準確率的權衡數據，以及後備機制帶來的靈活性；思考如何將 PAJAMA 包裝為內部評估基礎建設，並向利害關係人說明其相較於全 LLM 評判在 API 支出、可解釋性與規則可編輯性上的商業價值。
