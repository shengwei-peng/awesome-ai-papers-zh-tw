## ⚡ TL;DR

現有基準僅評測單次LLM生成，無法評估智慧體流程、核心對核心優化及未見配置泛化。
提出AgentKernelArena，以196項任務評測智慧體在隔離環境中的GPU核心優化與泛化。
生產級智慧體達高正確率與6.89倍加速，但PyTorch轉HIP在未見配置上因形狀假設導致正確性下降。

## 摘要翻譯

GPU 核心優化（GPU kernel optimization）對於高效率的深度學習系統（deep learning systems）日益關鍵，但撰寫高效能核心仍需要大量的低階專業知識（low-level expertise）。近期的 AI 編碼智慧體（AI coding agents）能夠反覆讀取程式碼、呼叫編譯器（compilers）與效能分析器（profilers），並迭代式精進（iteratively refine）實作，然而現有的核心基準測試僅評估單次大型語言模型（large language model, LLM）呼叫，而非完整智慧體工作流程（full agent workflows），且皆未同時納入核心對核心優化（kernel-to-kernel optimization）與未見配置泛化測試（unseen-configuration generalization testing）。我們提出 AgentKernelArena，一個用於衡量 AI 編碼智慧體在 GPU 核心優化上的表現的開源基準測試（open-source benchmark）。該基準測試包含 196 項任務，涵蓋 HIP-to-HIP 優化（HIP-to-HIP optimization）、Triton-to-Triton 優化（Triton-to-Triton optimization）與 PyTorch-to-HIP 轉譯（PyTorch-to-HIP translation），並在隔離工作區（isolated workspaces）中，透過閘控編譯（gated compilation）、正確性檢查（correctness checks）與效能檢查（performance checks）、集中式評分（centralized scoring），以及一項未見配置泛化協定（generalization protocol），來評估完整智慧體工作流程；此協定可測試優化結果是否能轉移至智慧體未見過的輸入配置（input configurations）。橫跨 Cursor Agent、Claude Code 與 Codex Agent 等生產級智慧體（production agents），我們發現在大多數任務類別中，編譯成功率近乎完美，且具備高正確率（high correctness rates）；其中最佳配置於 PyTorch-to-HIP、HIP-to-HIP 與 Triton-to-Triton 任務的平均加速比（mean speedups）分別最高達 6.89 倍、6.69 倍與 2.13 倍。我們的未見配置評估顯示，HIP-to-HIP 與 Triton-to-Triton 優化大多能轉移至未見過的輸入形狀（input shapes），而 PyTorch-to-HIP 則出現顯著的正確性下降（correctness drops），顯示從頭生成核心的智慧體經常寫死形狀特定假設（shape-specific assumptions）。AgentKernelArena 設計為模組化可擴充框架（modular, extensible framework），以針對智慧體、任務與硬體目標（hardware targets），對智慧體驅動的 GPU 核心優化進行嚴謹評估。

### 核心貢獻（3～5點）
- 提出 AgentKernelArena 開源基準測試框架，首次針對 GPU 核心優化場景評估完整智慧體工作流程（含多輪工具呼叫與迭代精進），彌補現有基準僅測試單次 LLM 生成之不足。
- 設計涵蓋 196 項任務的多元任務集，包含 HIP-to-HIP 優化、Triton-to-Triton 優化與 PyTorch-to-HIP 轉譯三大類別，並建立閘控編譯、正確性檢查與效能檢查之評測管線。
- 引入未見配置泛化協定，系統性檢驗智慧體產出之核心是否能泛化至未曾見過的輸入形狀與配置，填補泛化能力評估缺口。
- 實證評估 Cursor Agent、Claude Code 與 Codex Agent 等生產級智慧體，發現其在多數任務中可達近乎完美的編譯成功率與高正確率，最佳配置平均加速比達 6.89 倍（PyTorch-to-HIP）、6.69 倍（HIP-to-HIP）與 2.13 倍（Triton-to-Triton）。
- 發現 PyTorch-to-HIP 轉譯任務存在顯著正確性下降，揭示從頭生成核心的智慧體傾向寫死形狀特定假設，而 HIP-to-HIP 與 Triton-to-Triton 優化則具備較佳之未見輸入形狀泛化能力。

### 適合對象
本論文適合深度學習系統效能工程師、GPU 核心優化研究者、AI 編碼智慧體開發者，以及從事編譯器自動優化與異質硬體程式設計模型研究的學術與產業界人士閱讀。

## 深度分析

#### 方法論解析

本研究的方法論核心在於將評測對象從傳統的單次 LLM 呼叫（single LLM calls）或輕量迭代提示，轉移至完整智慧體工作流程（full agent workflows）的端到端評估。AgentKernelArena 建立了一個沙箱工作區（sandboxed workspace），讓 AI 編碼智慧體（AI coding agents）在具備完整 shell 存取權限的隔離工作區（isolated workspaces）內，自主執行多輪開發迴圈（multi-turn development loops）：讀取程式碼、呼叫編譯器（compilers）與效能分析器（profilers）、根據回饋迭代式精進（iteratively refine）核心實作，直至達到可設定的超時限制。

評測管線採用嚴格的編譯→正確性→效能閘控管線（compile→correctness→performance gating pipeline）。執行流程分為四階段：(1) 時間戳記隔離的工作區設置（workspace setup）與基準測量（baseline measurement），編譯原始核心並分析效能；(2) 啟動智慧體進行自主優化（agent execution）；(3) 集中式評分（centralized scoring），由框架統一對智慧體修改後的核心執行閘控編譯（gated compilation）、正確性檢查（correctness checks）與效能檢查（performance checks）。唯有編譯成功才會進入正確性驗證，正確性通過後才會執行效能分析，這種設計避免了「正確性作弊」或將無法編譯的程式碼納入統計，並透過算術平均各測試案例的加速比來計算最終效能增益。

任務設計涵蓋 196 個取自真實世界深度學習系統（deep learning systems）GPU 工作負載的任務，分為三大類別：HIP-to-HIP 優化（HIP-to-HIP optimization）、Triton-to-Triton 優化（Triton-to-Triton optimization），以及 PyTorch-to-HIP 轉譯（PyTorch-to-HIP translation）。前兩者屬於核心對核心優化（kernel-to-kernel optimization），要求智慧體在既有低階實作上進一步榨取效能；後者則是從高階程式設計模型（programming models）生成底層 HIP 核心，其錯誤模式與優化空間截然不同。

最具方法論價值的是未見配置泛化測試（unseen-configuration generalization testing）協定。不同於既有基準僅在智慧體優化過程中可見的輸入配置（input configurations）上驗證，本研究額外設計了一套未見輸入形狀（unseen input shapes）的泛化協定（generalization protocol），檢驗智慧體產出的優化是否僅過擬合於可見測試案例，抑或真正具備跨配置轉移能力。此外，框架可選擇性地附加領域特定備忘單，如 GPU 架構指南與 HIP/Triton 最佳實作文件，以降低異質智慧體架構（heterogeneous agent architectures）之間因先備知識不對稱造成的評測偏差。

#### 實驗數據解讀

實驗針對 Cursor Agent、Claude Code 與 Codex Agent 等生產級智慧體（production agents）進行評測。整體而言，所有受測智慧體在編譯階段均呈現接近完美的通過率，顯示當前大型語言模型（large language model, LLM）在語法生成與編譯器回饋理解上已相當成熟。正確性方面，多數任務類別維持高正確率（high correctness rates），但在未見配置下出現顯著分化。

平均加速比（mean speedups）呈現明顯的任務類別層級：PyTorch-to-HIP 轉譯達到最高 6.89x，HIP-to-HIP 優化達 6.69x，而 Triton-to-Triton 優化僅達 2.13x。這組數據透露了深層的效能生態訊息：PyTorch-to-HIP 的高加速比反映了從高階 PyTorch 實作轉譯至底層 HIP 時，存在巨大的低階專業知識（low-level expertise）紅利空間——基準實作本身留有大量記憶體階層（memory hierarchies）、平行執行模型（parallel execution models）與低階排程行為（low-level scheduling behavior）的優化餘地；HIP-to-HIP 的 6.69x 則顯示即便在已具備一定優化程度的低階核心上，智慧體仍能透過指令選擇（instruction selection）、矩陣乘法單元（matrix-multiply units）與張量加速硬體（tensor acceleration hardware）等架構特定功能（architecture-specific features）的調度進一步突破瓶頸（bottleneck）。相對地，Triton-to-Triton 的 2.13x 天花板較低，可能暗示 Triton 編譯器已將多數顯而易見的優化（如記憶體合併存取或自動向量化）內建完成，智慧體能介入的空間主要限於演算法層級或排程策略的微調，這也意味著 Triton 生態的效能瓶頸已從人工核心調校轉移至編譯器自動化能力。

泛化協定的結果則揭示了更關鍵的品質差異。HIP-to-HIP 與 Triton-to-Triton 的優化成果在未見輸入形狀上大致成功轉移，顯示核心對核心優化傾向產生具備泛化能力的改進（例如調整執行緒區塊配置或記憶體配置策略）。然而，PyTorch-to-HIP 在未見配置上出現嚴重的正確性下降（correctness drops），這明確指出智慧體在從頭生成核心時，經常引入形狀特定假設（shape-specific assumptions）——例如將區塊大小、迴圈邊界或共享記憶體配置硬編碼為優化過程中觀察到的特定數值。這種過擬合行為在單一配置評測中無法被偵測，卻在部署預算（deployment budgets）與推論成本（inference costs）敏感的生產環境中構成重大風險，因為真實深度學習系統的輸入形狀往往具有動態變異性。

#### 與現有研究的比較

相較於 HumanEval、MBPP 等僅評估單次 Python 函式功能正確性（functional correctness）的基準，或 SWE-bench 等針對儲存庫層級修補程式（repository-level patches）與多環境智慧體任務（multi-environment agentic tasks）的通用軟體工程評測，AgentKernelArena 首次針對 GPU 核心優化這一效能關鍵領域，建立了支援工具使用智慧體迴圈（tool-using agent loop）的專屬競技場。

在核心基準測試家族中，KernelBench、TritonBench、ROCmBench、robust-kbench 與 MultiKernelBench 等現有工作主要評估從規格說明（specification）生成核心的單次或輕量迭代 LLM 生成能力，缺乏完整智慧體工作流程評測，也未涵蓋核心對核心優化情境。robust-kbench 雖透過 LLM-based verifiers 防範正確性作弊，但仍屬於靜態生成評測。AgentKernelArena 的貢獻在於：(i) 將評測粒度提升至多輪、多工具呼叫的自主開發迴圈；(ii) 引入 HIP-to-HIP 與 Triton-to-Triton 的優化任務，更貼近人類工程師實際維護與調校既有核心的工作流；(iii) 首創未見配置泛化測試，揭露既有基準無法捕捉的形狀過擬合問題。

對於 QiMeng-Kernel、AutoTriton、TritonForge、AdaExplore 與 GEAK 等 LLM-driven kernel optimization systems，過往各自採用不同的評測協定，難以進行跨系統比較。AgentKernelArena 提供標準化的競技場，使這些系統可作為新的智慧體條目接入，有助於社群建立公平的效能共識。

然而，本研究亦存在若干侷限。首先，196 個任務的規模雖具代表性，但相較於動輒數千題的通用程式設計基準仍屬精緻型評測。其次，任務明顯偏向 HIP 生態系（考量作者所屬機構為 AMD），對於 CUDA 或 SYCL 等其他程式設計模型與硬體目標（hardware targets）的覆蓋有限。第三，泛化協定目前僅聚焦於輸入形狀的變化，尚未涵蓋資料型別、硬體世代或張量配置等更廣義的輸入配置遷移。最後，生產級智慧體的閉源與版本漂移特性，使得長期可重現性面臨挑戰。

#### 可重現性評估

AgentKernelArena 作為開源基準測試（open-source benchmark），採用模組化可擴充框架（modular, extensible framework）設計，允許透過設定檔新增智慧體、任務與硬體目標，這對社群貢獻極為有利。隔離工作區與集中式評分機制從架構上杜絕了狀態污染與評分偏差，是確保可重現性的堅實基礎。

不過，可重現性仍存在隱憂。由於評測對象為商業化的生產級智慧體（如 Cursor Agent、Claude Code、Codex Agent），其底層 LLM 版本、系統提示與工具鏈行為可能隨供應商更新而變動，論文未明確說明是否鎖定特定模型版本。此外，GPU 驅動程式、ROCm 版本與編譯器版本對核心效能數據具有決定性影響，若未完整記錄這些底層軟體堆疊資訊，不同實驗室之間的絕對加速比比較將存在雜訊。幸運的是，框架的相對比較設計（統一基準與統一評分指令）可在一定程度上抵銷這類系統性偏差。由於本研究屬於基準測試框架而非模型訓練工作，不涉及模型權重（model weights）釋出問題，其開源程式碼與任務資料集即為主要可重現性資產。

#### 未來研究方向

基於 AgentKernelArena 所揭示的現象，未來研究可沿以下方向深化：

第一，**動態形狀與廣義泛化協定**。當前的未見配置泛化測試主要針對靜態輸入形狀。未來應擴展至動態形狀、不同資料型別（如 FP8、BF16）及跨硬體後端（hardware backends）遷移，以模擬真實深度學習系統中常見的彈性推論需求。

第二，**解決 PyTorch-to-HIP 的形狀特定假設問題**。研究可探索符號執行、編譯器輔助驗證或形狀斷言生成等技術，強迫智慧體在從頭生成核心時維持配置無關的不變性，從而縮小可見與未見配置之間的正確性差距。

第三，**領域專屬智慧體架構**。目前評測使用通用 AI 編碼智慧體。未來可針對 GPU 核心優化設計專屬智慧體，例如整合檢索增強生成動態查詢架構特定功能文件，或將效能分析器的回饋直接嵌入智慧體的觀察空間進行強化學習微調。

第四，**多目標優化與部署導向評測**。現行評測以加速比為主要指標，未來可納入記憶體用量、功耗、編譯時間與推論成本等多維度指標，建立更符合部署預算限制的帕累托前沿評估。

第五，**擴充任務規模與程式設計模型**。將任務庫擴展至 CUDA、OpenCL、SYCL 乃至 DSL（如 TVM、MLIR），並增加分散式或多核心協同優化任務，使 AgentKernelArena 成為跨硬體目標的通用評測標準。

第六，**自動化基準策展**。利用 LLM 自動從開源 GPU 核心儲存庫挖掘高價值優化情境，並自動生成對應的測試與泛化配置，降低人工設計 196 個任務的維護負擔，並持續追蹤新硬體架構特定功能所帶來的優化機會。

## 論文問答

**Q1：為何 GPU 核心優化在現代深度學習系統中如此重要，且傳統上這項工作面臨哪些挑戰？**
A：隨著深度學習模型規模持續擴大，推論成本已成為部署預算的主要部分，而 GPU 核心優化正是決定整體系統效能的關鍵瓶頸。傳統上，撰寫高效能 GPU 核心需要深厚的低階專業知識，開發者必須深入理解記憶體階層、平行執行模型、指令選擇，以及各種架構特定功能如矩陣乘法單元與張量加速硬體。這種對高度專業化人力與時間的依賴，使得效能優化難以規模化，也限制了深度學習系統在實際應用中的成本效益與部署效率。

**Q2：現有的程式碼生成與核心基準測試為何無法充分評估 AI 編碼智慧體在 GPU 核心優化上的能力？**
A：現有的基準測試如 HumanEval 與 SWE-bench 主要針對通用軟體工程或單次 Python 函式生成，並未涵蓋效能導向的 GPU 程式設計場景。即使是專門的核心基準測試如 KernelBench 與 TritonBench，也僅評估單次 LLM 呼叫或輕量迭代提示下的核心生成，缺乏完整的工具使用智慧體迴圈，也沒有核心對核心優化的設定。更重要的是，這些現有測試都未檢驗智慧體產出的優化是否能泛化到未見過的輸入配置，因此無法揭露智慧體是否僅對可見測試案例過度擬合。

**Q3：本文提出的 AgentKernelArena 主要為了解決現有評測框架的哪些關鍵缺口？**
A：AgentKernelArena 旨在填補現有基準測試無法評估完整智慧體工作流程的缺口，特別是針對那些能夠自主編譯、測試、分析並迭代精進的多輪開發迴圈。此框架同時引入了核心對核心優化任務，包括 HIP-to-HIP、Triton-to-Triton 以及 PyTorch-to-HIP 轉譯，超越了僅從規格說明生成核心的單一模式。最關鍵的是，它建立了首個系統性的未見配置泛化協定，能夠檢驗智慧體優化後的核心在面對從未觀察過的輸入形狀時，是否仍能保持正確性與效能提升。

**Q4：AgentKernelArena 的核心評測流程為何，與傳統單次模型生成評測有何不同？**
A：AgentKernelArena 採用以智慧體為中心的評測方式，每個智慧體在獨立的沙箱工作區中運作，擁有完整的 shell 存取權限，可自主執行編譯、正確性驗證與效能分析長達設定的逾時時間。評測流程嚴格遵循編譯→正確性→效能的閘控管線，只有通過編譯才能進入正確性檢查，只有正確性通過才會進行效能剖析，確保速度比的計算建立在正確且可執行的程式碼之上。這與傳統僅評分孤立 LLM 輸出的方式截然不同，因為它完整模擬了人類工程師撰寫、編譯、測試、分析的迭代開發循環，並透過集中式評分機制實現跨異質智慧體架構的公平比較。

**Q5：AgentKernelArena 在任務設計與工作區隔離方面採取了哪些關鍵設計選擇？**
A：基準測試包含 196 個取自真實世界 GPU 工作負載的任務，涵蓋 HIP-to-HIP 優化、Triton-to-Triton 優化與 PyTorch-to-HIP 轉譯三大類別，確保評測結果能直接對應到生產環境中的實際需求。每次任務執行都會建立一個帶時間戳記的隔離工作區，內含完整的任務原始檔、評測腳本與建構基礎設施，智慧體無法存取其他任務、先前執行結果或其他智慧體的輸出。這種設計不僅防止了共享狀態汙染與資訊外洩，也確保了實驗的可重現性，並支援在多張 GPU 上進行大規模平行評測。

**Q6：何謂「未見配置泛化協定」，其在 AgentKernelArena 中扮演什麼角色？**
A：未見配置泛化協定是 AgentKernelArena 的一項關鍵創新，它系統性地測試智慧體優化後的 GPU 核心是否能轉移至智慧體在優化過程中從未觀察過的輸入形狀與配置。此協定透過在智慧體可見的開發配置之外，額外引入未見輸入配置進行正確性與效能驗證，從而揭露智慧體是否僅對已知測試案例過度擬合，或是真正產生了具備泛化能力的優化策略。這項機制對於評估 AI 編碼智慧體的實用價值至關重要，因為在真實部署環境中，核心經常需要處理各種動態且無法事先窮舉的輸入尺寸。

**Q7：實驗中評測了哪些生產級 AI 編碼智慧體，整體表現如何？**
A：實驗評測了 Cursor Agent、Claude Code 與 OpenAI Codex Agent 等主流生產級智慧體，結果顯示這些智慧體在多數任務類別上達到了近乎完美的編譯成功率與高正確率。在效能方面，最強配置在 PyTorch-to-HIP 任務上達到最高 6.89 倍的平均加速比，在 HIP-to-HIP 任務上達到 6.69 倍，而在 Triton-to-Triton 任務上則達到 2.13 倍。這些結果顯示現代 AI 編碼智慧體已具備相當強大的 GPU 核心優化潛力，能夠在完整的工具使用迴圈中產出顯著快於基準實作的高效能核心。

**Q8：在未見配置泛化測試中，不同任務類別呈現出什麼樣的差異性結果？**
A：實驗結果顯示，HIP-to-HIP 與 Triton-to-Triton 的優化成果大多能順利泛化到未見過的輸入形狀，顯示智慧體在現有核心基礎上進行改進時，較能保留對不同配置的適應能力。然而，PyTorch-to-HIP 轉譯任務在面對未見配置時出現了顯著的正確性下降，這表明當智慧體需要從頭生成核心時，經常會將特定輸入形狀的假設硬編碼到程式碼中。這項發現凸顯了從高階框架轉譯到低階核心的挑戰，也說明未見配置泛化協定成功揭露了現有智慧體在處理動態輸入尺寸時的脆弱性。

**Q9：實驗結果如何說明智慧體在「從頭生成核心」與「優化現有核心」兩種情境下的能力差異？**
A：實驗數據顯示，智慧體在進行 HIP-to-HIP 與 Triton-to-Triton 等核心對核心優化時，不僅能達到顯著加速，其成果也能穩定泛化至未見配置，反映出在既有程式碼基礎上改進相對容易控制。相對地，PyTorch-to-HIP 這類需要從高階描述轉譯並從頭建構低階核心的任務，雖然在可見配置上能達到最高加速比，卻在未見配置上出現嚴重的正確性衰退。這項差異暗示智慧體在從頭生成核心時，傾向於過度依賴開發過程中觀察到的特定輸入維度資訊，導致產出的程式碼缺乏對動態形狀的魯棒性。

**Q10：AgentKernelArena 的模組化設計如何促進其在學術界與產業界的實際應用？**
A：AgentKernelArena 採用模組化可擴充框架設計，允許使用者透過設定檔輕鬆新增不同的智慧體、任務類型與硬體目標，大幅降低了社群進行大規模基準測試的門檻。由於其任務取自真實的生產級機器學習程式碼庫與開源 GPU 核心儲存庫，評測結果能直接反映智慧體在實際部署場景中的效能表現。這種設計使得無論是學術研究者開發新的核心優化演算法，或是硬體廠商驗證 AI 智慧體在自家架構上的程式生成能力，都能利用此框架進行標準化且可重現的評估。

**Q11：對於現有的 LLM 驅動核心優化系統（如 AutoTriton、TritonForge 等），AgentKernelArena 提供了什麼樣的價值？**
A：目前各類 LLM 驅動的核心優化系統如 QiMeng-Kernel、AutoTriton、TritonForge、AdaExplore 與 GEAK 等，各自採用不同的評估協定，導致跨系統比較極為困難。AgentKernelArena 提供了一個標準化的競技場，讓這些系統能夠以統一的智慧體身份接入，並在相同的編譯、正確性與效能閘控管線下接受評測。這不僅促進了研究社群的公平比較，也為這些系統的開發者提供了一個嚴謹的測試平台，有助於識別其方法在真實多輪開發迴圈與未見配置泛化上的優勢與不足。

**Q12：AgentKernelArena 的評測結果對於企業部署 AI 編碼智慧體進行 GPU 核心開發有何實務啟示？**
A：評測結果顯示，企業在部署 AI 編碼智慧體進行 GPU 核心開發時，應優先將其應用於現有核心的迭代優化場景，因為這類任務在正確性與泛化能力上表現較為穩健。對於需要從 PyTorch 等高階框架轉譯為 HIP 等低階核心的任務，則必須建立額外的驗證機制，特別是針對未見輸入形狀的壓力測試，以避免智慧體將特定形狀假設硬編碼到生產程式碼中。此外，企業可利用此框架的集中式評分與隔離工作區設計，建立內部的標準化評測流程，確保不同智慧體產出的核心在整合至產品前都經過嚴格的編譯、正確性與效能把關。

**Q13：本文是否指出 AgentKernelArena 或受測智慧體存在哪些已知的限制？**
A：本文明確指出，雖然智慧體在多數任務上表現優異，但在 PyTorch-to-HIP 轉譯任務中，面對未見輸入配置時出現了顯著的正確性下降，這是現階段智慧體從頭生成核心時的一項重要限制。此現象根源於智慧體傾向將開發過程中觀察到的輸入形狀資訊硬編碼到核心中，導致其缺乏對動態維度的魯棒處理能力。此外，雖然框架本身設計為可擴充，但目前的 196 個任務主要聚焦於 HIP 與 Triton 生態系，對於其他 GPU 程式設計模型或更廣泛硬體後端的覆蓋仍有待社群未來持續擴展。

**Q14：為何 PyTorch-to-HIP 任務在未見配置上會出現顯著的正確性下降，這對未來智慧體設計有何警示？**
A：PyTorch-to-HIP 任務在未見配置上出現正確性大幅下降，主要是因為智慧體在從高階描述生成低階核心時，經常會針對開發階段可見的特定輸入形狀做出隱含假設，並將這些假設直接寫死於程式碼邏輯或記憶體配置中。這種「形狀特定假設」的過度擬合行為，使得核心在遭遇稍微不同的張量維度時便無法正確執行，暴露出智慧體在理解泛化程式設計原則上的不足。對未來智慧體設計而言，這警示開發者必須強化智慧體對於動態形狀處理與參數化程式設計的認知，或透過在提示中明確要求形狀無關的實作來減少此類硬編碼風險。

**Q15：AgentKernelArena 在未來可以朝哪些方向擴展，以持續推動 AI 核心優化領域的發展？**
A：未來 AgentKernelArena 可透過其模組化架構持續擴充，納入更多元的 GPU 硬體目標、程式設計模型如 CUDA 或 SYCL，以及更多取自新興深度學習工作負載的任務。框架也可整合更進階的泛化測試協定，例如針對不同資料型別、記憶體限制或批次大小的未見配置進行壓力測試，進一步提升對智慧體魯棒性的評估深度。此外，隨著 AI 編碼智慧體的能力持續演進，此框架亦可作為評測多智慧體協作、長期迭代維護與跨儲存庫核心遷移等更複雜場景的基礎平台，持續為學術與產業研究提供嚴謹的標準化評測依據。

## 實務應用指南

### 適用場景

1. **AI 晶片與硬體廠商評估編碼智慧體**：GPU 硬體團隊（如 AMD、NVIDIA 或新創晶片公司）可利用 AgentKernelArena 建立標準化戰場，系統性比較 Claude Code、Cursor Agent、Codex Agent 等生產級智慧體在自家硬體目標上的核心優化能力與平均加速比，作為採購或技術合作依據。
2. **深度學習框架團隊自動化運算子效能提升**：PyTorch、JAX 或 TensorFlow 等框架維護者可將 PyTorch-to-HIP 轉譯任務整合至內部流程，評估 AI 編碼智慧體能否自動將高階運算子轉譯並優化為高效底層核心，縮短新運算子的開發週期。
3. **企業內部 GPU 效能工程與程式碼現代化**：擁有大量既有 CUDA/HIP/Triton 程式碼庫的企業（如雲端服務供應商、推薦系統團隊）可透過 HIP-to-HIP 與 Triton-to-Triton 優化任務，評估導入智慧體進行批次重構與效能調校的可行性與投資報酬率。
4. **ML 平台與 MLOps 基礎設施商建立效能閘控**：可將 AgentKernelArena 的編譯→正確性→效能閘控管線嵌入持續整合（CI）系統，對任何進入生產環境的 GPU 核心自動執行多輪智慧體優化嘗試與未見配置泛化測試，防止效能迴歸。
5. **學術研究機構開發新一代智慧體架構**：研究者可在模組化可擴充框架上快速接入新提出的異質智慧體架構（例如具備反思機制或強化學習回饋的工具使用智慧體迴圈），以 196 項真實任務驗證其在低階專業知識領域的泛化能力。

### 實作前置條件

- **運算資源**：具備目標 GPU（如 AMD Instinct 系列對應 ROCm/HIP 環境）的運算節點；若評測 Triton 任務則需確保相容之張量加速硬體。建議配置多 GPU 以支援平行評測，並以容器化技術建立隔離工作區。
- **軟體與工具鏈**：ROCm/HIP SDK、Triton、PyTorch 開發環境、Docker/Podman，以及 AgentKernelArena 原始碼與相依套件。智慧體端需具備呼叫編譯器與效能分析器的完整 Shell 權限。
- **資料準備**：除框架內建任務外，若需評估內部程式碼，須準備現有 GPU 核心原始碼、對應的輸入配置（包含可見與未見輸入形狀）、參考實作（Ground Truth）與數值容差規格。
- **技能需求**：團隊需具備 GPU 程式設計模型（HIP/CUDA、Triton）實務經驗、Python 與 Shell 腳本開發能力，以及 LLM API（OpenAI、Anthropic 等）整合與提示詞工程經驗。
- **授權與成本**：生產級智慧體（Cursor Agent、Claude Code、Codex Agent）的 API 金鑰或企業授權；預留足夠預算以支應多輪開發迴圈中大量 Token 消耗與 GPU 運算時數。

### 實作步驟建議

1. **環境建置與沙箱隔離**：部署具時間戳記的沙箱工作區，確保每次評測任務執行皆在獨立目錄中進行，防止共享狀態汙染。安裝 AgentKernelArena 並驗證基線編譯與效能分析流程。
2. **任務選定與領域擴充**：從 196 項內建任務中選取目標類別（如 PyTorch-to-HIP 轉譯），或依模組化設計新增企業內部核心任務。針對目標硬體後端配置對應的 cheatsheets（GPU 架構指南、HIP/Triton 最佳實踐文件）。
3. **智慧體接入與提示詞配置**：將目標 AI 編碼智慧體透過設定檔接入框架，統一提示詞模板（包含任務類型、原始檔案路徑、目標函式、編譯/測試/分析指令）。設定最大迭代次數與超時參數。
4. **基準測試執行**：執行完整管線——先進行基線測量（編譯原始核心並分析效能），再啟動智慧體進行多輪迭代，最後由集中式評分模組依序執行閘控編譯、正確性檢查與效能檢查。
5. **未見配置泛化驗證**：執行泛化協定，將智慧體在可見輸入配置上優化後的核心，於未見輸入形狀下重新驗證正確性與加速比。比對兩者差異，識別形狀特定假設。
6. **結果分析與產品化**：彙整集中式評分結果，針對泛化測試失敗案例進行根因分析（如硬編碼區塊大小）。將通過驗證的高效能核心經人工複審後，合併至正式產品程式碼庫。

### 潛在風險與注意事項

- **過度擬合可見配置**：智慧體在多輪迭代中可能針對測試輸入形狀寫死假設，導致未見配置正確性下降。**因應措施**：嚴格分離可見與未見資料集，將泛化測試設為部署前的強制閘門，禁止僅以可見配置加速比作為驗收標準。
- **編譯與正確性作弊**：智慧體可能產生僅通過特定測資但邏輯錯誤的程式碼。**因應措施**：正確性檢查需涵蓋邊界條件、數值精度與多組隨機輸入，必要時引入 LLM-based 驗證器或魯棒性篩選器。
- **資源消耗與成本失控**：完整智慧體工作流程涉及大量 API 呼叫與 GPU 編譯/分析時間。**因應措施**：設定嚴格的超時與迭代上限，啟用平行多 GPU 評測縮短總時長，並建立每日/每週預算上限。
- **隔離性失效與資安風險**：若沙箱未妥善隔離，智慧體可能讀取其他任務答案、環境變數或敏感憑證。**因應措施**：每次執行建立全新隔離工作區，限制網路存取（僅允許必要編譯器與 API 端點），並在評測後徹底清理。
- **硬體與工具鏈快速演進**：HIP 與 Triton 的最佳實踐隨架構世代快速變化，過時的 cheatsheets 會導致智慧體產生無效或低效能指令。**因應措施**：建立定期審查機制，隨硬體後端更新同步修訂架構指南與編譯器版本。

### 與其他技術的整合建議

- **CI/CD 管線整合**：將 AgentKernelArena 嵌入 GitHub/GitLab CI，對任何修改 GPU 核心的 Pull Request 自動觸發評測。將「編譯成功＋正確性通過＋未見配置泛化通過」作為合併前的效能閘控條件。
- **與現有基準測試形成互補層級**：搭配 KernelBench（單次生成）與 TritonBench（Triton 專項）等現有基準，建立「單次 LLM 呼叫 → 多輪智慧體優化 → 未見配置泛化驗證」的三層評測體系，全面覆蓋從程式碼生成到產品落地的品質需求。
- **IDE 與人機協作開發環境**：在 VS Code 或 Cursor 等編輯器中整合 AgentKernelArena 的評測腳本，讓工程師一鍵觸發智慧體優化，並於側邊欄即時查看編譯錯誤、正確性比對結果與效能提升數據。
- **監控與實驗追蹤系統**：將每次評測的加速比、正確率、泛化分數寫入 MLflow、Weights & Biases 或時序資料庫，搭配儀表板追蹤不同智慧體版本與基礎模型迭代間的長期趨勢。
- **自動化程式碼審查輔助**：將泛化測試中偵測到的形狀特定假設標記為程式碼異味，透過 bot 自動在程式碼審查平台留言，提醒維護者該核心可能存在未見輸入形狀的風險。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從論文的「Benchmark Design」與「Task Selection」章節入手，先理解 GPU 核心優化的基本挑戰與三種任務類型（HIP-to-HIP、Triton-to-Triton、PyTorch-to-HIP），再觀察實驗結果中智慧體的成功與失敗案例，無需深入技術細節即可建立對 AI 編碼智慧體能力邊界的直覺。
- **AI 工程師**：重點閱讀「Agent-centric evaluation」與「unseen-configuration generalization protocol」部分，關注如何將生產級智慧體（Cursor、Claude Code、Codex）接入沙箱工作區，以及提示詞設計、cheatsheets 配置與多輪工具呼叫迴圈的實作細節，這些內容可直接應用於內部智慧體評測框架的建置。
- **研究人員**：深入分析泛化協定的設計邏輯與實驗發現，特別是 PyTorch-to-HIP 任務在未見輸入形狀上的正確性下降現象，可作為未來研究「如何減少智慧體形狀過擬合」或「增強低階程式碼泛化能力」的切入點；框架的模組化設計也便於擴充新的硬體目標與評分指標。
- **產品經理**：聚焦「適用場景」與實驗數據中的平均加速比（最高達 6.89x），評估導入 AI 編碼智慧體進行 GPU 核心優化的投資報酬率；同時留意「未見配置泛化測試」所揭示的風險，在規劃產品路線圖時預留人工複審與安全驗證的緩衝期，避免將尚無法泛化的智慧體產出直接部署至生產環境。
