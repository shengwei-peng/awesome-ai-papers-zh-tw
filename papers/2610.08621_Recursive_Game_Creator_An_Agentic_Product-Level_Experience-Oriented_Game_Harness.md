## 摘要翻譯

近期遊戲設計代理在生成可玩遊戲（playable game）方面已取得顯著進展。然而，程式正確性（program correctness）並不能保證玩家擁有愉快的體驗。我們提出遞迴遊戲創建器（Recursive Game Creator），這是一個體驗導向框架（experience-oriented harness），旨在將代理式遊戲開發（agentic game development）從初步的遊戲原型（game prototype）推進到引人入勝的遊戲。遞迴遊戲創建器圍繞四個組件組織遞迴開發：設計師（Designer）、建構師（Builder）、玩家（Player）與審查者（Reviewer）。設計師將使用者指令與審查者的回饋轉化為詳細的計畫。建構師將這些計畫轉化為候選遊戲。程式原生玩家（coding-native player）透過程式化介面（programmatic interface）建立並執行可重複使用策略（reusable policy），以有效率地蒐集多樣化的遊戲過程軌跡（gameplay trajectory），緩解由基於 GUI 的慢速收集所導致的評估偏差（evaluation bias）。審查者使用精心設計的基於軌跡的指標（trajectory-based metrics）來推導玩家偏好（player preferences），並整合視覺證據（visual evidence）與明確的文字偏好（textual preferences），根據遊戲特定標準（game-specific criteria）評估遊戲。最後，審查者接受較佳版本，並為下一輪提供改進審查（improvement review），從而閉合遞迴迴圈（recursive loop）。我們的方法在 GameCraft-Bench 上達到 77.89 的最先進（state-of-the-art）整體表現。在 GameASG-Bench 上，其嚴格任務成功率（strict task success rate）達到 53.2%，較同模型基準提升 34.1%，並在所有比較方法中取得最高的平均執行時檢查通過率（mean runtime-check pass rate）93.4%。使用者研究（user study）顯示更長的遊玩時間（playtime）與更高的評分（rating）。程式碼即將釋出。

### 核心貢獻（3～5點）
- 提出體驗導向框架（Experience-Oriented Harness），將代理式遊戲開發從「程式正確性導向」推進至「產品級玩家體驗導向」，填補可玩性與趣味性之間的鴻溝
- 設計四組件遞迴開發架構（設計師 Designer、建構師 Builder、玩家 Player、審查者 Reviewer），形成自我回饋的遞迴迴圈（recursive loop），實現迭代式精煉
- 引入程式原生玩家（Coding-Native Player），透過程式化介面（programmatic interface）高效蒐集多樣化遊戲過程軌跡（gameplay trajectory），有效緩解 GUI 收集所帶來的評估偏差（evaluation bias）
- 在 GameCraft-Bench（77.89）與 GameASG-Bench（嚴格任務成功率 53.2%、平均執行時檢查通過率 93.4%）兩項基準上取得最先進（state-of-the-art）表現，並透過使用者研究驗證實際遊玩體驗的提升（更長的遊玩時間與更高的評分）

### 適合對象
從事 AI 代理（AI Agent）、自動化遊戲開發、創意計算與程式合成（program synthesis）的研究者與工程師；對大型語言模型驅動的代理系統、遊戲 AI 評測基準（benchmark）、AI 生成內容品質評估感興趣的學術界與產業界人士；以及關注人機互動（HCI）、玩家體驗（player experience）評估與代理式工作流程（agentic workflow）設計的研究人員。

## 深度分析

#### 方法論解析

Recursive Game Creator（遞迴遊戲創建器）的核心設計理念在於將「程式正確性」與「玩家體驗品質」解耦，並透過四個角色化組件構成的遞迴迴圈（recursive loop）來持續提升遊戲品質。整體架構模擬真實遊戲工作室（game studio）的分工模式，由 Designer（設計師）、Builder（建構師）、Player（玩家）、Reviewer（審查者）四個組件協同運作。

**Designer（設計師）組件**負責將使用者指令與 Reviewer 的回饋轉化為結構化的設計圖（design graph）。此設計圖涵蓋四大面向：遊戲機制（gameplay mechanism）、故事線（storyline）、回饋系統（feedback system）與視覺素材需求（visual asset requirements）。這種結構化設計有助於後續 Builder 進行模組化實作，也讓 Reviewer 能針對特定面向進行診斷。

**Builder（建構師）組件**扮演實作角色，呼叫外部工具（external tools）來實作遊戲後端（game backend）、組織視聽素材（audiovisual asset），並進行專案管理（project management）。此組件本質上是程式編碼代理（coding agent），負責將抽象設計轉化為可執行的程式碼。

**Coding-Native Player（程式原生玩家）**是本系統最具創新性的組件。相較於傳統 GUI 代理（GUI agent）透過螢幕截圖（screenshot）進行視覺解讀（visual interpretation）並逐幀決策的做法，Coding-Native Player 透過程式化介面（programmatic interface）直接存取遊戲狀態（game state）、合法動作（legal actions）與進度訊號（progress signals）。其核心優勢包含四點：

1. **高頻率控制（high-frequency control）**：避免視覺模型推論的延遲（latency），可進行密集且快速的遊戲互動。
2. **高效的軌跡收集（efficient trajectory collection）**：分離快速的遊戲控制與策略建構，大幅提升 rollout 效率。
3. **多樣化能力模擬（diverse capability simulation）**：可建構不同策略與能力層級的可重複使用策略（reusable policy），模擬不同水準的玩家行為。
4. **可重現結果（reproducible results）**：策略以程式碼形式儲存，可被一致地重複執行。

此設計有效緩解了基於 GUI 的收集（GUI-based collection）所帶來的評估偏差（evaluation bias），因為 GUI 代理受限於視覺模型的細粒度（fine-grained）解讀能力與單步決策延遲，難以進行大規模且多樣化的遊戲測試。

**Experience-Oriented Reviewer（體驗導向審查者）**是另一個關鍵創新。此組件結合兩類評估依據：來自軌跡的結構化指標（trajectory-based metrics）與來自螢幕截圖的視覺證據（visual evidence）。其評估框架包含三個層次：

- **通用指標**：遊玩時間（playtime）、成功率（success rate）等跨遊戲類型的標準。
- **遊戲特定標準（game-specific criteria）**：由 Reviewer 主動推斷適合個別遊戲的分析準則。例如，賽車遊戲重視「回應式轉向」，視覺小說重視「有意義的故事線與連貫對話」。
- **遊戲特定診斷（game-specific diagnosis）**：難度評估（difficulty assessment）、邊角錯誤發現（corner-bug discovery）、遊戲內時間記錄（time-in-game recording）等。

Reviewer 將推斷的玩家偏好（player preferences）以結構化文字表達，包含期望體驗、支援觀察與修訂優先順序。同時，使用者也可在遊玩過程中提供明確的文字偏好（textual preferences），使系統能同時兼顧客觀品質與主觀品味。

**遞迴迴圈（recursive loop）的運作機制**為：策略執行產生軌跡 → 軌跡與視覺分析產生體驗與偏好回饋 → Designer 將回饋轉化為新計畫 → Builder 實作新候選版本 → 進入下一輪測試。Reviewer 在每輪結束時接受較佳版本，並提供改進審查（improvement review）作為下一輪精煉（next-round refinement）的依據。此閉環設計使系統能從粗糙的遊戲原型（game prototype）逐步演化為產品級遊戲（product-level game）。

#### 實驗數據解讀

**GameCraft-Bench 評測結果**：系統在整體表現上達到 77.89 分的最先進（state-of-the-art）水準。經過三輪精煉後，總分從 72.70 提升至 77.89，增幅為 +5.19 分，且每個回報的評分類別皆有改善。這顯示遞迴機制確實能持續提升遊戲品質，而非僅在初始版本就達到上限。三輪的設定暗示作者在效率與效果間取得平衡——更多輪次可能帶來邊際效益遞減。

**GameASG-Bench 評測結果**：嚴格任務成功率（strict task success rate）達到 53.2%，相較於同模型基線提升了 34.1 個百分點（從約 19.1% 提升至 53.2%，雖然原文以「9.47 to 25/47 tasks」表述，換算約為 19.1% 至 53.2%）。平均執行時檢查通過率（mean runtime-check pass rate）達到 93.4%，為所有比較方法中最高。這兩個指標的意義在於：成功率反映遊戲能否完整滿足任務規格，執行時檢查通過率反映遊戲在運行時的穩定性與功能性。93.4% 的高通過率顯示 Builder 產出的程式碼品質可靠，遞迴機制有效減少了功能性缺陷。

**使用者研究（user study）結果**：相較於基線，系統產出的遊戲獲得更長的遊玩時間（playtime）與更高的評分（rating）。此結果特別重要，因為它直接驗證了「體驗導向」設計的有效性——若僅追求程式正確性，無法解釋玩家願意花更多時間遊玩的事實。遊玩時間作為代理指標，反映了遊戲的吸引力與沉浸感。

**基準比較定位**：在 GameCraft-Bench 與 GameASG-Bench 兩個基準上皆達到最高整體分數，確立了其在代理式遊戲開發（agentic game development）領域的領先地位。值得注意的是，兩個基準的評測面向可能互補：GameCraft-Bench 側重互動式產出物的品質，GameASG-Bench 側重任務規格的達成率。

**實驗設計的侷限**：原文未詳細說明每輪精煉的具體時間成本、token 消耗或單一遊戲的開發週期。此外，使用者研究的樣本規模、人口統計與統計顯著性檢定皆未在提供的文本中揭露，這限制了對「更長遊玩時間與更高評分」結論的強度評估。

#### 與現有研究的比較

**與 GUI 代理遊戲測試方法的比較**：相較於 Huang et al. (2026) 與 Zhang et al. (2026a) 等使用 GUI 代理進行遊戲測試的工作，本系統的 Coding-Native Player 透過程式化介面繞過了視覺解讀的瓶頸。GUI 代理受限於每次動作都需要視覺模型推論，導致延遲高且難以進行大規模 rollout；而 Coding-Native Player 將策略建構與遊戲控制分離，可進行高頻率且多樣化的測試。這是本工作在方法論上的根本差異。

**與迭代式遊戲開發代理的比較**：與 Yan et al. (2026) 的 Harness-of-Harness 與 Hu et al. (2026) 的迭代式工作相比，本系統的特點在於「體驗導向」的 Reviewer 設計。Harness-of-Harness 強調持久性開發與獨立評估，但未明確將玩家體驗作為核心優化目標；本系統則透過軌跡指標、視覺證據與遊戲特定標準的結合，直接針對玩家體驗進行診斷與改進。

**與並行工作的關係**：Wu et al. (2026) 的 RSIGame 探索遞迴自我改進於代理式遊戲開發，與本工作方向相近，但 RSIGame 主要依賴迭代評估回饋進行精煉，而本系統更強調體驗導向的多層次評估框架與 Coding-Native Player 的策略多樣性。

**與通用軟體代理系統的比較**：相較於 MetaGPT（Hong et al., 2024）與 ChatDev（Qian et al., 2024）等通用多代理框架，本系統的領域特化程度更高。GameGPT（Chen et al., 2025a）雖將角色協作應用於遊戲開發，但未明確處理「從原型到產品」的體驗提升問題。AutoUE（Yin et al., 2026）與 OpenGame（Jiang et al., 2026）分別針對 Unreal Engine 與可重複使用專案範本，但同樣缺乏體驗導向的評估機制。

**與程式碼生成應用的關聯**：本工作借鑑了 Code2Video（Chen et al., 2025b）、VideoAgent（Liang et al., 2026）、VideoCoCo（Li et al., 2026）等將程式碼生成應用於影片創作的工作，以及 Code as Policies（Liang et al., 2023）、ProgPrompt（Singh et al., 2022）、Voyager（Wang et al., 2023）、Eureka（Ma et al., 2024）等將程式碼作為機器人策略表達方式的工作。這些工作共同啟發了「以可執行程式碼作為遊戲測試策略」的設計理念。

**現有工作的侷限與本工作的改進**：

1. **程式正確性不等於體驗品質**：現有工作多專注於產生可執行的遊戲，但未系統性地處理體驗問題。本工作透過體驗導向審查者明確回應此缺口。
2. **GUI 代理的效率瓶頸**：現有遊戲測試多依賴 GUI 代理，本工作以 Coding-Native Player 解決效率與多樣性問題。
3. **缺乏偏好整合機制**：現有工作多未考慮玩家主觀偏好，本工作允許使用者提供文字偏好，並由 Reviewer 推斷隱含偏好。
4. **單輪生成的限制**：現有工作多為單輪生成，本工作的遞迴機制支援多輪持續改進。

**本工作的侷限**：

1. **依賴程式化介面的可用性**：Coding-Native Player 需要遊戲暴露結構化的狀態與事件介面，對於高度視覺化或介面封閉的遊戲可能不適用。
2. **Reviewer 的評估標準依賴 LLM 推斷**：遊戲特定標準由 Reviewer 主動推斷，可能存在推論偏差或不完整性。
3. **遞迴次數的選擇**：三輪精煉的設定缺乏理論依據，更多或更少輪次的影響未充分探討。
4. **計算成本**：多輪精煉涉及多次 Builder 實作與 Player rollout，整體計算成本可能較高。

**評測協議**：GameCraft-Bench 與 GameASG-Bench 應有標準化的評測協議，但本工作的具體評測設定（如溫度、隨機種子、評估次數）未在文本中詳細說明。使用者研究的協議（參與者招募條件、遊玩環境、評分量表）同樣未揭露。

**可重現性改善建議**：

1. 儘速釋出程式碼與設定檔，使外部研究者能復現實驗結果。
2. 明確說明使用的基礎模型及其版本。
3. 提供詳細的評測協議文件，包括提示模板、評估腳本與評分標準。
4. 公開使用者研究的完整協議與資料（經適當匿名化處理）。
5. 釋出遞迴過程中產生的中間版本與軌跡資料，便於深入分析。

**與領域標準的比較**：在代理式遊戲開發領域，程式碼與基準的公開程度參差不齊。GameDevBench、GameCraft-Bench、GameXpertBench（Chi et al., 2026; Luo et al., 2026; Chen et al., 2026）等基準的釋出提升了領域的可重現性，但具體方法的程式碼釋出仍待加強。本工作承諾釋出程式碼，符合領域趨勢，但時程未明確。

#### 未來研究方向

**1. 擴展 Coding-Native Player 的適用範圍**

現有設計假設遊戲暴露程式化介面，但許多商業遊戲或高度視覺化的遊戲可能缺乏此類介面。未來可探索混合方法：結合程式化介面的高效控制與視覺模型的細粒度理解，在介面不可用時自動回退至視覺模式。此外，可研究自動介面生成技術，使 Builder 在實作遊戲時自動產生可供 Player 存取的標準化介面。

**2. 強化 Reviewer 的評估能力**

目前 Reviewer 的遊戲特定標準依賴 LLM 推斷，可能不夠全面或存在偏差。未來方向包括：

- **人類專家知識整合**：將遊戲設計領域專家的評估標準編碼為結構化知識庫，輔助 Reviewer 的推斷。
- **多模態深度融合**：現有設計將軌跡指標與視覺證據分開處理，未來可探索更緊密的多模態融合機制，例如將軌跡事件與螢幕截圖在時序上對齊進行聯合分析。
- **因果分析能力**：從「觀察到問題」深化為「理解問題成因」，使改進建議更具針對性。

**3. 遞迴策略的最佳化**

三輪精煉的設定缺乏理論基礎。未來可研究：

- **自適應輪數**：根據遊戲類型、初始品質或改進幅度動態決定停止條件。
- **早停機制**：當 Reviewer 判斷品質已收斂或改進幅度低於閾值時自動停止。
- **分支探索**：不僅進行單一路徑的遞迴精煉，還可探索多個設計分支並選擇最佳者。

**4. 偏好學習與個人化**

目前偏好整合主要透過使用者提供的文字偏好與 Reviewer 推斷的隱含偏好。未來可探索：

- **長期偏好建模**：從使用者的多輪互動中學習穩定的偏好模式。
- **隱式偏好訊號**：從遊玩行為（如重試次數、關卡選擇、遊玩時長分布）推斷偏好，減少對明確文字輸入的依賴。
- **偏好對齊評估**：建立專門的基準衡量系統產出與玩家偏好的對齊程度。

**5. 計算效率與成本最佳化**

多輪精煉涉及大量的 LLM 呼叫與遊戲執行，計算成本可能成為實際部署的瓶頸。未來方向包括：

- **增量式精煉**：僅修改需要改進的部分，而非每輪從頭生成。
- **快取與重用**：跨遊戲類型重用設計模式、策略模板與評估標準。
- **輕量級模型分工**：將不同任務分配給不同規模的模型，平衡成本與品質。

**6. 從單一遊戲到遊戲系列**

現有系統聚焦於單一遊戲的開發，未來可探索：

- **系列化開發**：在統一的世界觀或機制下開發多個相關遊戲。
- **模組化設計**：使 Builder 產出的程式碼更具模組化與可重用性，降低後續遊戲的開發成本。
- **跨遊戲遷移學習**：將一個遊戲的設計經驗遷移至相關類型。

**7. 與人類開發者的協作模式**

目前系統以全自動方式運作，未來可探索人機協作：

- **設計師在環（designer-in-the-loop）**：讓人類設計師在關鍵決策點介入，例如確認設計方向或調整評估標準。
- **可解釋性增強**：使 Reviewer 的診斷與建議更易被人類理解與審核。
- **教學應用**：將系統作為遊戲設計教學工具，幫助學習者理解迭代改進的過程。

**8. 更廣泛的評測與基準建設**

現有基準（GameCraft-Bench、GameASG-Bench）雖提供了量化指標，但對「體驗品質」的衡量仍不完整。未來可建立：

- **體驗品質專項基準**：專門衡量遊戲的吸引力、沉浸感、情感回應等體驗面向。
- **長期遊玩評估**：衡量遊戲在多次遊玩或長期使用後的吸引力維持能力。
- **跨文化評估**：考慮不同文化背景下的玩家偏好差異。

**9. 安全性與倫理考量**

隨著代理式遊戲開發能力的提升，需關注：

- **內容安全**：確保生成的遊戲內容符合適當的年齡分級與內容標準。
- **偏見審查**：檢測並緩解 Reviewer 在評估標準上的潛在偏見。
- **智慧財產權**：處理生成遊戲中可能涉及版權的視覺或音樂素材。

這些方向不僅能推動 Recursive Game Creator 本身的演進，也將對整個代理式遊戲開發領域產生深遠影響，從「能執行的遊戲」邁向「真正令人享受的遊戲」。

## 論文問答

**Q1：為什麼「程式正確執行」不足以代表「遊戲好玩」？這個問題在代理式遊戲開發中為何特別關鍵？**

A：程式正確性僅代表遊戲能夠被執行與運行，但無法保證玩家在實際遊玩過程中能獲得愉悅的體驗。一款遊戲的好玩與否取決於引人入勝的機制設計、適當的難度曲線、一致性的視覺與敘事呈現，以及對玩家操作的回應式回饋等多個面向。在代理式遊戲開發中，由於程式編碼代理（Coding Agent）擅長的是程式碼生成與推理，而非細粒度的視覺遊戲狀態解讀，因此更容易產生出「能跑但不好玩」的遊戲原型。這使得從可執行原型進化到產品級遊戲（Product-Level Game）成為一個尚未被妥善解決的核心挑戰。

**Q2：現有的代理式遊戲開發方法在「體驗導向」這方面有哪些具體不足？**

A：現有方法多依賴 GUI 代理（GUI Agent）來進行遊戲測試，透過螢幕截圖與視覺解讀來驅動遊戲互動，但這種方式存在多項限制。首先，截圖驅動的測試容易遺漏透過程式化介面（Programmatic Interface）才能取得的結構化狀態、合法動作、事件與進度訊號。其次，每個動作都需要視覺解讀與模型決策，造成明顯的延遲，限制了高頻率、細粒度的遊戲推演（Rollout）。此外，這些方法通常缺乏針對個別遊戲特性的診斷能力，無法區分賽車遊戲需要靈敏的操控、而視覺小說需要連貫的對話與故事線等差異化需求。

**Q3：為何「重複的遊戲測試（Playtesting）」對於產品級遊戲的開發至關重要？**

A：產品級遊戲的開發本質上是一個需要不斷試錯與調整的過程，僅憑單次的程式生成無法揭示玩家在長時間遊玩中才會遭遇的問題，例如難度失衡、邊角錯誤（Corner-Bug）或敘事斷裂等。透過反覆的遊戲測試，開發者能夠蒐集多樣化的遊戲過程軌跡（Gameplay Trajectory），進而分析玩家的實際行為模式與體驗感受。這種以體驗為核心的反饋迴圈，正是將粗糙原型進化為具備完整體驗品質的產品級遊戲所不可或缺的環節。

**Q4：遞迴遊戲創建器（Recursive Game Creator）的核心架構是如何設計的？四個組件各自扮演什麼角色？**

A：遞迴遊戲創建器採用模擬真實遊戲工作室（Game Studio）的角色分工，將系統劃分為設計師（Designer）、建構師（Builder）、玩家（Player）與審查者（Reviewer）四個組件。設計師負責將使用者指令與審查者的回饋轉化為詳盡的設計圖（Design Graph），涵蓋遊戲機制、故事線、回饋系統與視覺素材需求。建構師則呼叫適當的外部工具，將設計圖實作為候選遊戲，負責遊戲後端、視聽素材組織與專案管理。玩家組件透過程式化介面建立並執行可重複使用的策略（Reusable Policy），以高效蒐集多樣化的遊戲過程軌跡。審查者則結合軌跡指標、視覺證據與文字偏好，進行遊戲特定診斷並提供改進審查（Improvement Review），形成遞迴迴圈（Recursive Loop）。

**Q5：「程式原生玩家（Coding-Native Player）」相較於傳統 GUI 代理有何關鍵創新？**

A：程式原生玩家的核心創新在於繞過視覺解讀層，直接透過程式化介面與遊戲互動，從而實現高頻率控制（High-Frequency Control）與高效的軌跡蒐集。傳統 GUI 代理需要為每個動作進行截圖、視覺理解與模型決策，不僅延遲高，也難以進行密集且可重現的測試。相對地，程式原生玩家能夠建構具有不同策略與能力等級的可重複使用策略，模擬多樣化的玩家能力（Diverse Capability Simulation），並產生可重現的結果（Reproducible Results）。這種設計將快速的遊戲控制與策略建構、視覺評估分離開來，同時保留了直接暴露的狀態與事件資訊供後續分析，有效緩解了 GUI 收集所帶來的評估偏差（Evaluation Bias）。

**Q6：體驗導向審查者（Experience-Oriented Reviewer）如何兼顧「通用標準」與「遊戲特定標準」？**

A：體驗導向審查者採用雙層次的評估策略，底層為通用標準，包含遊玩時間（Playtime）、成功率與執行時檢查等跨遊戲類型皆適用的指標；上層則為遊戲特定標準（Game-Specific Criteria），由審查者主動推斷每款遊戲應著重的面向。例如，賽車遊戲重視靈敏的操控反應，而視覺小說則重視有意義的故事線與連貫的對話。審查者會將推斷出的偏好以結構化文字表達，涵蓋期望的體驗描述、支援性觀察與修訂優先順序。同時，使用者也能在遊玩過程中提供明確的文字偏好（Textual Preferences），這些輸入共同引導下一輪的設計計畫，使精煉過程能同時兼顧遊戲品質與玩家品味。

**Q7：實驗使用了哪些評測基準？這些基準各自側重於什麼樣的能力？**

A：研究使用了兩個主要的評測基準：GameCraft-Bench 與 GameASG-Bench。GameCraft-Bench 評估引擎驅動的開發與互動式產出物的整體品質，涵蓋多個類別的綜合評分。GameASG-Bench 則側重於任務成功率與執行時檢查通過率，能夠衡量代理在具體遊戲開發任務上的完成度與程式穩健性。這兩個基準互補，前者關注整體體驗品質的提升幅度，後者關注特定任務的達成率與執行可靠性，共同驗證了遞迴遊戲創建器在不同面向上的表現。

**Q8：遞迴遊戲創建器在兩個基準上的關鍵成果為何？這些數字代表什麼意義？**

A：在 GameCraft-Bench 上，遞迴遊戲創建器達到了 77.89 的最先進（State-of-the-Art）整體表現，經過三輪精煉後，總分從 72.70 提升至 77.89（+5.19），且每個回報的類別皆有進步，證明了遞迴迴圈能持續改善遊戲品質。在 GameASG-Bench 上，嚴格任務成功率（Strict Task Success Rate）達到 53.2%，相較於同模型基線提升了 34.1%，並在所有比較方法中取得了最高的平均執行時檢查通過率（Mean Runtime-Check Pass Rate）93.4%。這些數據顯示，該方法不僅能讓更多任務被成功完成，也能讓產出的遊戲在實際執行時更加穩定可靠。

**Q9：除了基準測試之外，是否有進行消融研究（Ablation Study）或使用者研究（User Study）來驗證各組件的貢獻？**

A：是的，研究中包含了使用者研究來驗證遞迴遊戲創建器的實際效果。結果顯示，相較於基線方法，使用者對遞迴遊戲創建器所產出的遊戲展現出更長的遊玩時間（Playtime）與更高的評分（Rating），這直接證明了體驗導向設計對玩家滿意度的正面影響。雖然論文中未明確呈現完整的消融研究數據，但從三輪精煉中每個類別皆有提升的結果，可以間接推論出設計師、建構師、玩家與審查者四個組件在遞迴迴圈中各自扮演了不可或缺的角色。

**Q10：遞迴遊戲創建器在實際應用上適用於哪些場景？**

A：遞迴遊戲創建器特別適用於從粗糙遊戲原型進化為產品級遊戲的開發流程，無論是獨立開發者快速驗證遊戲概念，或是工作室進行概念驗證階段皆能受益。其支援使用者導向的客製化能力，使得玩家可以透過文字偏好引導遊戲朝特定方向演化，例如調整難度、改變敘事風格或強化特定機制。此外，由於程式原生玩家能高效蒐集多樣化軌跡，該系統也適合用於遊戲平衡性測試、自動化品質保證（QA）以及大規模遊戲設計探索等場景。

**Q11：從產品化的角度來看，這個系統需要考量哪些實際部署因素？**

A：從產品化角度來看，系統需要考量多項實際部署因素。首先，程式原生玩家仰賴遊戲提供結構化的程式化介面，這對於許多現有遊戲引擎並非原生支援，需要建構師組件額外處理介面暴露的問題。其次，視覺素材的生成與管理涉及外部工具的整合成本與版權議題，在實際部署時需要建立素材庫與授權機制。此外，遞迴迴圈的多輪迭代會消耗大量運算資源，如何在品質提升與成本控制之間取得平衡，是商業化應用時必須正視的課題。

**Q12：這項研究對代理式遊戲開發領域的長遠影響為何？**

A：這項研究將代理式遊戲開發從「能跑的程式」推進到「好玩的遊戲」，重新定義了該領域的目標與評估標準。透過引入體驗導向的設計理念與程式原生的測試方法，研究為後續工作提供了一個可參考的多組件遞迴框架範式。更重要的是，使用者偏好的整合機制開啟了「人機協作遊戲開發」的可能性，讓 AI 不僅是工具，更能成為理解並回應玩家品味的創作夥伴，這對遊戲產業的未來發展具有深遠的啟發意義。

**Q13：論文中有哪些被明確承認的限制？**

A：雖然論文並未以獨立章節詳列所有限制，但從內容中可以推論出幾項被間接承認的挑戰。首先，系統的效能高度依賴遊戲能夠提供結構化的程式化介面，對於介面封閉或狀態不透明的遊戲，程式原生玩家的優勢將無法完全發揮。其次，視覺素材的品質仍受限於外部工具的能力，審查者雖然能評估視覺呈現，但實際素材的生成仍仰賴其他系統。此外，遞迴迴圈的收斂性並未在論文中深入探討，多輪迭代是否能持續帶來顯著改善，或在某些情況下會陷入局部最優，仍是需要進一步驗證的問題。

**Q14：在什麼樣的情況下，這個系統可能會失敗或表現不佳？**

A：系統可能在幾種情境下表現不佳：當遊戲類型極度仰賴細緻的視覺表現（如高品質 3D 動作遊戲）時，僅憑截圖評估可能無法捕捉到關鍵的體驗問題。當使用者的偏好與審查者推斷的遊戲特定標準產生衝突時，系統可能難以有效整合兩種訊號源。當遊戲的程式化介面設計不良或狀態暴露不完整時，程式原生玩家將退回到近似 GUI 代理的低效模式。此外，對於需要多人互動或社群驅動體驗的遊戲類型，單一玩家的軌跡分析將無法反映真實的社交動態。

**Q15：基於這項研究，未來有哪些值得探索的方向？**

A：未來值得探索的方向包括：將遞迴迴圈擴展至支援多人遊戲測試，引入多代理模擬以反映真實的社交遊玩體驗；結合強化學習或偏好學習技術，讓審查者能更精準地建模玩家品味；探索跨遊戲類型的遷移學習，使系統能將一個遊戲類型的診斷經驗應用到新類型；以及研究遞迴迴圈的理論收斂性，了解在何種條件下迭代能保證品質持續提升。此外，將系統與現有遊戲引擎（如 Unity、Unreal）深度整合，降低介面暴露的工程門檻，也是推動實際落地的關鍵方向。

## 實務應用指南

### 適用場景

1. **獨立遊戲工作室的快速原型迭代**：小型團隊可利用此框架在數小時內將文字構想轉化為可玩的遊戲雛型，並透過自動化的「程式原生玩家」進行大量試玩，縮短從概念驗證到可展示版本（MVP）的時間。

2. **教育訓練用的客製化遊戲生成**：教師或教育科技業者可輸入教學目標（例如「訓練學生認識化學元素週期表」），由 Designer 規劃遊戲機制、Builder 實作、Player 模擬不同學習程度的學生行為、Reviewer 評估教材契合度，產出符合學習目標的小型遊戲。

3. **遊戲大賽或黑客松的 AI 輔助開發**：參賽者在限定時間內可借助框架快速生成多版本遊戲，並透過 Reviewer 的體驗導向回饋找出最佳版本，提升作品品質與獲獎機會。

4. **遊戲 UX 研究中的 A/B 測試自動化**：研究人員可讓框架同時生成多個機制變體（例如不同難度曲線的跳躍遊戲），由 Coding-Native Player 模擬新手、中階、專家三種玩家策略，量化比較各版本的留存率與挫折點。

5. **企業內部訓練模擬器開發**：用於員工訓練（例如客服情境模擬、產線操作演練）的遊戲化教材，可透過框架快速產出符合特定業務流程的互動內容，並依據受訓者偏好持續優化。

### 實作前置條件

**資料需求**
- 目標遊戲類型的範例程式碼庫（建議至少 5–10 個同類型開源遊戲專案作為參考素材）
- 視覺素材庫（角色、場景、UI 套件），可使用開源資源如 Kenney、OpenGameArt
- 遊戲特定評估標準的範本（針對不同類型如競速、視覺小說、平台跳躍等準備 rubric）
- 玩家偏好資料集（可從既有玩家評論、Steam 評論或自建問卷取得）

**運算資源**
- 大型語言模型 API 存取權（建議使用 GPT-4 等級以上模型作為 Designer 與 Reviewer）
- 程式碼執行沙箱環境（支援 Python、JavaScript 等語言的隔離執行）
- 螢幕截圖與視覺評估用的視覺語言模型（VLM）
- 平行運算能力以同時執行多個 Player 策略（建議至少 8–16 個並行 worker）

**技能門檻**
- 熟悉 LLM 代理框架（如 LangChain、AutoGen 或自建 agent loop）
- 具備遊戲引擎基礎知識（Unity、Godot、Phaser 等至少一種）
- 程式設計能力（Python 為主，需能撰寫策略程式與 API 介接）
- 提示工程（Prompt Engineering）經驗，特別是結構化輸出與多輪對話管理
- 基本的遊戲設計素養（理解 MDA 框架、玩家體驗要素）

---

### 實作步驟建議

**階段一：建立基礎架構（2–4 週）**
1. 搭建四角色通訊協議：定義 Designer、Builder、Player、Reviewer 之間的訊息格式（建議使用 JSON Schema 規範輸入輸出）。
2. 實作 Builder 的工具呼叫層：整合程式碼生成、檔案管理、外部素材 API（如圖像生成、語音合成）。
3. 建立遊戲執行沙箱：支援常見遊戲框架的啟動、暫停、重置與狀態快照。

**階段二：實作 Coding-Native Player（3–4 週）**
1. 為目標遊戲類型定義「程式化介面」：暴露遊戲狀態、合法動作、事件觸發等結構化資訊。
2. 設計策略模板庫：包含隨機遊玩、目標導向、風險規避、激進進攻等多種策略原型。
3. 實作軌跡收集器：記錄每回合的狀態序列、動作、獎勵與終止條件，輸出標準化格式（如 JSONL）。
4. 加入多樣化能力模擬：根據玩家等級調整反應時間、決策品質等參數。

**階段三：實作 Experience-Oriented Reviewer（3–4 週）**
1. 建立通用評估指標：遊玩時間、成功率、崩潰次數、重玩率等。
2. 設計遊戲特定 rubric 自動推導機制：讓 Reviewer 根據遊戲類型自動產生對應的評估維度（例如競速遊戲的「操控響應度」、視覺小說的「劇情連貫性」）。
3. 整合視覺評估：串接 VLM 對螢幕截圖進行美學、UI 一致性、視覺回饋清晰度的評分。
4. 實作偏好整合介面：允許使用者輸入文字偏好，並與 Reviewer 推斷的隱式偏好合併。

**階段四：建立遞迴迴圈（2–3 週）**
1. 設計版本管理機制：保留每一輪的遊戲版本、評估結果與改進建議。
2. 實作「接受/拒絕」決策邏輯：根據 Reviewer 評分決定是否採用新版本。
3. 設定終止條件：達到目標分數、預算上限或最大迭代輪數時停止。
4. 加入早停機制：當連續多輪無顯著改善時自動結束。

**階段五：評測與優化（持續進行）**
1. 在 GameCraft-Bench 與 GameASG-Bench 上驗證效能。
2. 進行使用者研究：邀請目標玩家進行實際遊玩並收集滿意度資料。
3. 根據回饋調整 rubric 權重與策略多樣性。

---

### 潛在風險與注意事項

**風險一：評估偏差導致「過度最佳化」**
- **現象**：Reviewer 偏好某些特定風格，導致所有遊戲趨向同質化。
- **緩解**：在 Reviewer 中加入多樣性獎勵項，並定期以人類玩家評分進行校正。

**風險二：程式原生介面設計不當**
- **現象**：遊戲未暴露足夠的結構化狀態，導致 Player 無法有效測試。
- **緩解**：在 Builder 階段強制要求實作標準化的 debug API（狀態查詢、動作注入、事件訂閱）。

**風險三：迭代成本過高**
- **現象**：每輪迭代需重新編譯、執行遊戲，累積時間與 API 成本驚人。
- **緩解**：使用增量編譯、快取機制，並設定每輪的時間預算上限（例如 15 分鐘）。

**風險四：視覺評估不可靠**
- **現象**：VLM 對遊戲美學的判斷與人類觀感有落差，可能誤導 Reviewer。
- **緩解**：將視覺評估權重控制在總分的 20–30%，並以人類評分作為定期校準基準。

**風險五：玩家偏好被過度解讀**
- **現象**：使用者輸入的少量文字偏好被過度放大，導致遊戲失去設計主軸。
- **緩解**：設定偏好影響力的上限（例如不超過整體評分的 15%），並保留 Designer 的設計自主權。

**風險六：邊角錯誤難以被軌跡捕捉**
- **現象**：某些罕見路徑的 bug 不會在常規策略中被觸發。
- **緩解**：在策略庫中加入「壓力測試」策略（隨機動作、極端輸入），並結合符號執行或模糊測試技術。

---

### 與其他技術的整合建議

**與遊戲引擎整合**
- Unity：透過 Unity Test Framework 暴露狀態介面，使用 Addressable 系統管理素材。
- Godot：利用 GDScript 的 `@tool` 模式實作 debug API，整合 GUT 測試框架。
- 網頁遊戲（Phaser/PixiJS）：直接在瀏覽器中注入測試 hook，使用 Puppeteer 輔助截圖。

**與版本控制整合**
- 使用 Git 自動管理每輪迭代的版本，標記評分與改進建議。
- 整合 CI/CD 流程：每次 Builder 提交後自動觸發 Player 試玩與 Reviewer 評估。

**與專案管理工具整合**
- 將 Reviewer 的改進建議自動轉為 Jira/Linear 的任務項目。
- 在 Notion 或 Confluence 中自動生成迭代日誌，包含評分趨勢圖表。

**與人類協作流程整合**
- 在關鍵決策點（如「是否採用新版本」）保留人類審核環節。
- 提供 Web UI 讓設計師即時查看軌跡回放、調整偏好權重。

**與其他代理框架整合**
- 可將四角色包裝為 MCP（Model Context Protocol）工具，供其他代理系統呼叫。
- 與 AutoGen、LangGraph 等框架結合，實現更複雜的多代理協作。

**與素材生成 AI 整合**
- 串接 Stable Diffusion、Midjourney 等圖像生成 API 自動產出視覺素材。
- 使用 ElevenLabs 或類似服務生成 NPC 語音與音效。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節的「四角色分工」比喻，理解 Designer-Builder-Player-Reviewer 的遞迴迴圈概念即可，不必深入技術細節。可將本文視為「AI 輔助遊戲開發的可能性展示」，重點體會「程式可執行 ≠ 體驗良好」這個核心觀點。

**給 AI 工程師**：重點關注 Coding-Native Player 的設計取捨——為何選擇程式化介面而非 GUI 代理，以及如何設計可重用的策略模板。實作時可先從單一遊戲類型（如平台跳躍）切入，驗證四角色通訊協議與軌跡收集的可行性，再逐步擴展到其他類型。建議參考 Voyager 與 Eureka 等「以程式碼表達行為」的工作。

**給研究者**：本文的核心貢獻在於「體驗導向評估」與「程式原生測試」的結合。可深入分析 Reviewer 的 rubric 自動推導機制、軌跡指標的設計原理，以及遞迴迴圈的收斂性保證。建議與 RSIGame、GameCraft-Bench 等並列工作進行比較研究，特別是評估方法論的差異。

**給產品經理**：理解此框架的價值在於「將遊戲開發從單次生成轉為持續優化的流程」。在實際導入時，建議先定義明確的「體驗 KPI」（如新手 5 分鐘留存率、首次失敗後重玩率），再讓框架圍繞這些指標迭代。同時需注意成本控制——每輪迭代的 API 與運算成本應納入專案預算。
