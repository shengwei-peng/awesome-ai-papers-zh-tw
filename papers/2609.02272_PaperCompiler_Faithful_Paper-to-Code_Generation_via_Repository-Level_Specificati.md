# PaperCompiler：透過儲存庫層級規格編譯達成忠實的論文轉程式碼生成

**原文標題：** PaperCompiler: Faithful Paper-to-Code Generation via Repository-Level Specification Compilation  
**作者：** Yunhao Liu、Hong Phuc Pham、Jaehong Yoon  
**發布日期：** 2026-09-02  
**HF 連結：** [https://huggingface.co/papers/2609.02272](https://huggingface.co/papers/2609.02272)  
**arXiv：** [https://arxiv.org/abs/2609.02272](https://arxiv.org/abs/2609.02272)

## ⚡ TL;DR

論文轉程式碼時，自由格式中間產出易導致方法退化與儲存庫不一致。
提出 PaperCompiler，將論文證據編譯為明確的儲存庫層級實作規格。
在 Paper2CodeBench 上，參考保真度相對提升 13.8%，嚴重批評降至 6.1%。

---

## 摘要翻譯

忠實地將研究論文轉換為儲存庫層級（repository-level）實作仍具挑戰性，因為論文通常以高層次描述方法，並將實作假設隱含未明，同時要求生成的儲存庫必須保留方法邏輯、評估協定與跨檔案一致性。儘管論文轉程式碼生成（paper-to-code generation）智能體近期有所進展，其中間產出（intermediate outputs）常以自由格式摘要（free-form summaries）或規劃呈現，下游編碼智能體（downstream coding agents）可能忽略、重新詮釋或壓縮這些內容，導致演算法退化（algorithm degradation）與儲存庫結構不一致。為解決這些挑戰，我們提出 PaperCompiler，一個將論文導向證據（paper-grounded evidence）編譯為明確儲存庫層級實作規格的論文轉程式碼生成框架。PaperCompiler 將實作相關證據進行論文接地（Paper Grounding），同時保留來源出處（source provenance），並區分論文支援（paper-supported）、推論得出（inferred）、外部委派（externally delegated）與未解決（unresolved）等資訊類別。產生的規格納入非退化需求（non-degradation requirements）、所有權分配（ownership assignments）、跨檔案依賴（cross-file dependencies）與檔案層級約束（file-level constraints）。儲存庫生成在這些編譯後的規格下進行，同時保留對論文未固定的局部工程選擇之彈性。PaperCompiler 在 Paper2CodeBench 上優於強力基線，在基於參考的保真度（reference-based fidelity）上達到 13.8% 的相對改善幅度（從 3.64 提升至 4.15），並減少高嚴重度評估批評（high-severity evaluator critiques）（從 13.2% 降至 6.1%）。

### 核心貢獻（3～5點）
- 提出 PaperCompiler 框架，透過規格編譯（specification compilation）將論文導向證據轉化為明確的儲存庫層級實作規格，避免下游編碼智能體忽略或扭曲方法細節。
- 建立四類資訊區分機制（論文支援、推論得出、外部委派、未解決），並保留來源出處，提升規格的可追溯性與透明度。
- 在規格中編碼非退化需求、所有權分配、跨檔案依賴與檔案層級約束，確保方法邏輯與儲存庫結構的一致性。
- 在 Paper2CodeBench 上達成顯著改善：基於參考的保真度從 3.64 提升至 4.15（相對改善 13.8%），高嚴重度評估批評從 13.2% 降至 6.1%。

### 適合對象
從事論文轉程式碼生成、自動化軟體工程、大型語言模型（LLMs）應用與可重現性（Reproducibility）研究的學者與工程師；特別適合關注如何將研究論文忠實轉換為可執行程式碼、並需維護跨檔案一致性與方法保真度的研究人員。

## 深度分析

#### 方法論解析

PaperCompiler 的核心貢獻在於將「論文轉程式碼生成（paper-to-code generation）」視為一個**規格編譯（specification compilation）**問題，而非單純的序列化文字生成任務。傳統作法常把論文內容轉成自由格式摘要（free-form summaries）或推理軌跡（reasoning traces），下游編碼智能體（downstream coding agents）在解讀時容易遺失、簡化或重新詮釋關鍵細節。PaperCompiler 則透過三階段流程，把論文導向證據（paper-grounded evidence）編譯成具有**來源出處（source provenance）**、**所有權分配（ownership assignments）**與**跨檔案依賴（cross-file dependencies）**的持續性規格（persistent specifications），再於這些規格的約束下進行儲存庫層級（repository-level）生成。

##### 三階段流程

1. **Paper Grounding（論文接地）**  
   此階段從論文中萃取與實作相關的證據，並建立一份**實作藍圖（implementation blueprint）**。重點不在於直接產出程式碼，而在於辨識哪些敘述對應到實作需求，同時保留支援性來源證據（supporting source evidence），例如演算法步驟、數學式、表格超參數、評估慣例（evaluation conventions）等。PaperCompiler 在此會對資訊進行分類：
   - **論文支援（paper-supported）**：論文明確記載的細節；
   - **推論得出（inferred）**：基於論文脈絡或領域慣例合理補全的內容；
   - **外部委派（externally delegated）**：交由外部函式庫、官方程式碼（official code）或相關論文譜系（paper lineage）處理的部分；
   - **未解決（unresolved）**：證據不足、需要標記出來的缺口。  
   這種分類讓後續階段能清楚區分「必須嚴格保留的方法關鍵語意（method-critical semantics）」與「可彈性處理的工程決策」。

2. **Specification Compilation（規格編譯）**  
   在取得接地證據後，PaperCompiler 將其協調為明確的**實作需求（implementation requirements）**，並進一步組織成儲存庫層級結構。此階段產出：
   - **非退化需求（non-degradation requirements）**：防止方法邏輯被簡化或扭曲的約束，例如「必須枚舉所有合法分割」而非「僅回傳第一個分割」；
   - **所有權分配（ownership assignments）**：每個需求對應到哪個儲存庫元件（檔案、類別、函式）負責實作；
   - **跨檔案依賴（cross-file dependencies）**：釐清資料前處理（data preprocessing）、模型初始化（model initialization）、訓練流程與評估流程之間的生產者–消費者關係；
   - **檔案層級約束（file-level constraints）**與**本地化檔案規格（localized file specifications）**：針對個別檔案的輸入輸出介面、呼叫順序與不變條件。  
   這些規格是結構化且持續存在的，能避免自由格式中間產出（intermediate outputs）被下游忽略或壓縮。

3. **Constraint-Guided Repository Generation（約束引導儲存庫生成）**  
   最後階段在已編譯規格的約束下生成實際檔案。由於規格已明確指定介面與跨檔案一致性要求，編碼智能體只需在未被論文固定的局部工程選擇上保留彈性，例如變數命名、輔助函式拆分、錯誤處理風格等。這種「全局嚴格、局部彈性」的設計有助於同時維持**方法保真度**與**程式碼可讀性**。

##### 案例說明：Universal Neural Functionals

圖 2 以 *Universal Neural Functionals* 為例，說明規格編譯如何避免**演算法退化（algorithm degradation）**。該方法要求對索引集合進行所有合法分割（partition），並為每個分割建立一個基底元素，最後以完整的分割導出基底集（full partition-derived basis set）建構網路層。PaperCoder 的中間規劃以自由格式摘要呈現，下游生成時將「枚舉所有分割」壓縮成「只取第一個分割或單一基底」，導致方法層級偏差（method-level deviations）。相對地，PaperCompiler 將「必須產生完整基底集」編譯為明確的檔案層級約束，並把該需求的所有權指派給負責建構層的模組，從而保留原始演算法語意。

#### 實驗數據解讀

論文在 **Paper2CodeBench** 與 **Paper2Code-Extra（P2C-Ex）** 共 90 篇論文上進行評估，並與 PaperCoder、AutoP2C、AutoReproduce 等強基線（baselines）比較。評估指標可大致分為兩類：一類是不依賴參考實作的**參考無關評估（reference-free evaluation）**，另一類是與作者實作比對的**基於參考的保真度（reference-based fidelity）**；此外還有評估者對生成結果的錯誤嚴重度分析。

##### 主要量化結果

| 評估情境 | PaperCompiler 之前 | PaperCompiler | 相對改善幅度（relative improvement） |
|---|---|---|---|
| Reference-free evaluation（參考無關評估） | 4.562 | 4.777 | +4.7% |
| P2C-Ex | 4.535 | 4.728 | +4.3% |
| Reference-based fidelity（基於參考的保真度） | 3.647 | 4.152 | +13.8% |
| High-severity failure rate（高嚴重度失敗率） | 13.2% | 6.1% | 下降超過一半 |

##### 結果意涵

1. **基於參考的保真度提升最為顯著**  
   相較於參考無關評估僅有約 4–5% 的進步，reference-based fidelity 從 3.647 提升到 4.152，相對改善達 13.8%。這顯示 PaperCompiler 的優勢主要體現在「貼近作者實作細節」上，而非僅讓儲存庫看起來更完整。規格編譯把論文特定方法學約束（paper-specific methodological constraints）明確寫入檔案規格，使生成結果在演算法細節、資料前處理與評估協定上更接近真實實作。

2. **高嚴重度評估批評（high-severity evaluator critiques）大幅下降**  
   高嚴重度失敗率從 13.2% 降至 6.1%，幾乎減半。這表示演算法退化、跨檔案不一致（cross-file inconsistencies）與核心方法遺漏等嚴重錯誤顯著減少，與 PaperCompiler 強調的非退化需求與跨檔案依賴管理直接呼應。

3. **參考無關評估的改善相對溫和**  
   4.7% 與 4.3% 的進步雖然穩定，但幅度較小，可能原因包括：參考無關評分較偏重表面完整性（檔案結構、可執行性、文件），而這些面向基線已具一定水準；或者該指標對方法內部細節的敏感度不如 reference-based fidelity。這也暗示未來需要設計更能捕捉「方法保真度」的參考無關指標。

#### 與現有研究的比較

##### 通用軟體工程智能體（General-purpose software-engineering agents）

現有多智能體軟體工程（multi-agent SWE）系統，例如 SWE-agent、OpenHands、Agentless，主要處理既有儲存庫的缺陷修復或功能修改。它們假設儲存庫結構與介面已經存在，並未針對論文特定方法學約束進行設計。因此，這類系統在論文轉程式碼任務中常出現**論文接地不足（insufficient paper grounding）**的問題，無法有效恢復資料前處理、模型初始化與評估慣例等隱含細節。

##### 現有論文轉程式碼系統

PaperCoder 將流程分為規劃、分析、編碼三階段；AutoP2C 引入多模態證據（multimodal evidence）與除錯機制；AutoReproduce 則利用論文譜系與執行回饋進行迭代修正。這些系統雖然強化了論文分析與知識萃取，但階段間傳遞的資訊多為自由格式計畫或摘要，缺乏：
- 明確所有權（explicit ownership）：未清楚標示哪個元件負責實現哪個需求；
- 非退化約束：未將「不得簡化方法」寫成可檢查的規則；
- 跨檔案一致性機制：難以確保不同檔案對同一需求的詮釋一致。  

PaperCompiler 透過規格編譯彌補上述缺口，把論文需求轉化為具有來源連結證據（source-linked evidence）的結構化規格。

##### PaperCompiler 的優勢與限制

**優勢：**
- 明確區分論文支援、推論得出、外部委派與未解決資訊，提升透明度；
- 以持續性規格貫穿生成流程，降低下游重新詮釋造成的資訊流失；
- 透過所有權分配與跨檔案依賴管理，減少跨檔案不一致；
- 在參考基準上取得顯著保真度提升，並大幅降低高嚴重度錯誤。

**限制：**
- 規格編譯本身仍依賴大型語言模型（large language models, LLMs），若論文敘述模糊或演算法步驟不完整，接地階段可能產生錯誤或過度推論；
- 對於高度領域專屬的實作慣例，系統可能需要額外的外部知識或人類介入；
- 規格編譯會帶來額外計算與延遲成本，對於需要快速生成的場景可能構成挑戰；
- 評估仍部分仰賴 LLM 評估者，可能存在評分偏誤或對細微方法差異不敏感的問題。

#### 可重現性評估

就本文所提供的前印本（preprint）內容而言，作者尚未明確說明是否釋出原始碼、提示詞模板、規格編譯器的實作細節或模型權重（model weights）。這對可重現性（reproducibility）構成一定不確定性：

- **資料集**：Paper2CodeBench 與 P2C-Ex 為既有公開評測基準，原則上可取得；但 PaperCompiler 實際使用的論文子集、前處理設定與評估腳本是否公開，仍待確認。
- **程式碼與規格**：若未釋出規格編譯階段的結構化輸出格式與生成管線，其他研究者難以驗證「規格編譯」本身對最終結果的貢獻，也難以進行公平比較。
- **模型權重**：論文未提及是否訓練專屬模型，若僅使用現成 LLM API，則結果對模型版本、溫度參數與提示詞高度敏感，需要詳細記錄才能重現。

建議作者後續釋出：
1. 完整管線程式碼，包含 Paper Grounding、Specification Compilation 與 Constraint-Guided Repository Generation 三階段；
2. 規格格式（schema）與範例，讓社群能理解非退化需求與所有權分配的具體表示；
3. 使用的提示詞、LLM 版本與推論參數；
4. 自動化評估腳本與人工評估準則，以便進行獨立驗證。

#### 未來研究方向

1. **整合執行回饋與測試驅動精煉**  
   可結合 AutoReproduce 的路線，在 Constraint-Guided Repository Generation 後加入單元測試與執行回饋，自動檢驗非退化需求是否被違反，並迭代修正規格與程式碼。

2. **多模態證據的深度融合**  
   參考 AutoP2C，將論文中的圖表、演算法虛擬碼、數學式與正文一同納入 Paper Grounding，提升對複雜方法細節的萃取能力。

3. **領域專屬規格語言的設計**  
   目前規格可能以自然語言或半結構化格式呈現，未來可發展更形式化的領域特定語言（domain-specific language），讓非退化需求與跨檔案依賴能被自動驗證。

4. **不確定性量化與人類參與迴路**  
   針對未解決（unresolved）資訊，可設計主動式澄清機制，讓系統向使用者或作者確認關鍵實作假設，並將不確定性納入規格與最終評估。

5. **規格編譯器的可解釋性與除錯工具**  
   開發視覺化工具，展示每個實作需求如何從論文哪一段落推導、指派給哪個檔案、與哪些檔案相依，協助研究者理解與修正生成結果。

6. **從論文譜系與官方程式碼中進行檢索增強**  
   對於外部委派資訊，可進一步利用論文譜系、相關 GitHub 儲存庫與技術文件進行檢索增強生成（retrieval-augmented generation），減少推論錯誤。

7. **輕量化與開源化**  
   將規格編譯知識蒸餾到較小模型，或建立開源規格資料集，降低使用門檻並促進可重現性。

8. **跨語言與跨領域擴展**  
   目前評估集中於機器學習論文，未來可探索 PaperCompiler 在電腦視覺、自然語言處理、系統研究乃至非英文論文上的適用性與調整需求。

## 論文問答

**Q1：PaperCompiler 主要想解決什麼問題？**
A：PaperCompiler 旨在解決將機器學習研究論文忠實轉換為儲存庫層級可執行程式碼的難題。論文通常以高階方式描述方法，並將資料前處理、模型初始化與評估慣例等實作關鍵細節隱含在字裡行間，導致自動生成系統難以完整復現方法邏輯。此外，生成的程式碼儲存庫必須同時保留方法語意、評估協定與跨檔案一致性，這使得論文轉程式碼生成成為一項極具挑戰性的任務。

**Q2：現有的論文轉程式碼智能體為何會失敗？**
A：現有系統如 PaperCoder、AutoP2C 與 AutoReproduce 雖然強化了論文分析與重現流程，但它們在不同階段之間常以自由格式計畫、摘要或推理軌跡傳遞資訊。這類中間產出無法明確地將實作需求綁定到負責實現的儲存庫元件，因此下游編碼智能體容易忽略、重新詮釋或壓縮關鍵細節。結果就是方法邏輯被簡化或扭曲，產生演算法退化與跨檔案不一致的問題。

**Q3：為什麼保留方法關鍵語意與跨檔案一致性如此重要？**
A：研究論文的可重現性與實務應用高度依賴程式碼能否準確反映作者提出的方法，任何方法層級偏差都可能削弱論文宣稱的科學貢獻。跨檔案一致性則確保資料流、模型介面與評估流程能正確協同運作，避免單一檔案正確但整體儲存庫無法執行的情況。因此，論文轉程式碼系統不能僅產生語法正確的片段，而必須在整個儲存庫層級維持方法邏輯與結構的一致性。

**Q4：PaperCompiler 的三個核心階段各自負責什麼？**
A：PaperCompiler 的第一階段是「論文接地」（Paper Grounding），負責從論文中萃取出與實作相關的證據，並建構保留來源出處的實作藍圖。第二階段是「規格編譯」（Specification Compilation），將接地後的證據整理為明確的實作需求，並組織成儲存庫層級的所有權分配、跨檔案依賴與本地化檔案規格，同時加入防止方法退化的約束。第三階段是「約束引導的儲存庫生成」（Constraint-Guided Repository Generation），在這些編譯後的規格下產生各檔案程式碼，並維持介面與跨檔案一致性。

**Q5：「規格編譯」與傳統自由格式計畫有何不同？**
A：規格編譯將論文導向證據轉換為持續性、結構化的實作規格，並明確標示每項需求應由哪個儲存庫元件負責實現。相較於自由格式摘要，這些規格會區分論文支援、推論得出、外部委派與未解決等資訊類別，並保留來源連結證據。這種明確所有權與非退化需求的設計，使下游生成階段難以任意簡化或重新詮釋論文方法。

**Q6：PaperCompiler 如何在忠於論文的同時保留工程彈性？**
A：PaperCompiler 將論文明確規定或強烈暗示的實作需求編碼為硬性約束，確保方法關鍵語意不會在生成過程中退化。然而，對於論文未固定的局部工程選擇，例如變數命名、輔助函式拆分或部分實作細節，生成階段仍保有一定彈性。這種設計讓系統既能避免演算法退化，又不會過度限制合理的程式設計決策。

**Q7：論文使用了哪些評測基準與基線方法？**
A：實驗在 Paper2CodeBench 的 90 篇論文以及 Paper2Code-Extra（P2C-Ex）上進行評估。比較的基線方法包括 PaperCoder、AutoP2C 與 AutoReproduce 等現有論文轉程式碼或論文重現系統。這些基準與基線涵蓋了不同難度與參考實作可得性的情境，能夠全面檢驗 PaperCompiler 的效能。

**Q8：PaperCompiler 的主要量化結果是什麼？**
A：在基於參考實作的保真度評估中，PaperCompiler 將分數從 3.647 提升至 4.152，相對改善幅度達 13.8%。在無參考評估與 P2C-Ex 上，也分別取得 4.562→4.777（4.7%）與 4.535→4.728（4.3%）的進步。此外，高嚴重度評估批評的比率從 13.2% 下降至 6.1%，顯示生成結果在方法正確性與儲存庫品質上都有顯著提升。

**Q9：圖 2 的 Universal Neural Functionals 案例說明了什麼？**
A：該案例顯示論文要求為每個有效分割建立一個基底元素，並由完整的分割導出基底集合來建構網路層。PaperCoder 由於使用自由格式計畫，遺失了「完整分割」這項關鍵需求，最終只保留單一基底，造成演算法退化。相對地，PaperCompiler 透過結構化規格保留了完整的分割建構規則，正確生成所有分割對應的基底元素。

**Q10：PaperCompiler 在哪些實務場景中最具價值？**
A：當論文作者未釋出官方程式碼，或釋出的程式碼不完整時，PaperCompiler 能協助研究者快速建立可執行的參考實作。它也適用於需要大規模重現文獻方法的自動化流程，例如系統性評比、可重現性挑戰或教學用途。透過降低手動重現的負擔，該工具有助於加速研究驗證與方法採用。

**Q11：部署 PaperCompiler 時需要考慮哪些產品化議題？**
A：首先，系統會標示未解決或推論得出的資訊，因此實際部署時應保留人工審查與確認機制。其次，生成結果需要與版本控制、持續整合與授權管理流程整合，以確保程式碼可維護且符合開源規範。最後，應建立執行回饋與自動測試機制，以驗證生成儲存庫是否真正符合論文描述。

**Q12：PaperCompiler 可能對機器學習可重現性領域帶來什麼影響？**
A：PaperCompiler 透過提升論文轉程式碼的保真度，能顯著降低研究社群在重現他人工作時的門檻與錯誤率。它有潛力成為可重現性管線中的標準化工具，使更多研究方法能被快速驗證、比較與應用。長期而言，這類技術有助於縮小論文描述與實際程式碼之間的落差，促進更透明的科學研究。

**Q13：PaperCompiler 有哪些已知的限制？**
A：其效能仍受限於論文本身的清晰度與資訊完整性，若論文對關鍵細節隻字未提，系統只能將其標示為未解決或推論得出。此外，目前的評估指標雖能量化參考保真度，但未必能完整捕捉所有語意層面的偏差。對於極度模糊或自相矛盾的論文描述，PaperCompiler 也無法憑空產生正確的實作決策。

**Q14：PaperCompiler 仍可能出現哪些失敗案例？**
A：當論文遺漏重要超參數或前處理步驟時，即使規格編譯正確，生成結果仍可能與作者實作存在差異。若跨檔案依賴被錯誤指定，可能導致介面不一致或執行階段錯誤。此外，外部函式庫版本更新或 API 變動，也可能使原本正確的生成程式碼在實際執行時產生非預期行為。

**Q15：未來可以朝哪些方向改進 PaperCompiler？**
A：未來可進一步結合執行回饋與自動化測試，讓規格編譯與程式碼生成形成更緊密的迭代迴路。也可以整合論文譜系與多模態證據，以填補單篇論文未明言的隱含知識。此外，引入人機協作機制，讓研究者能互動式地解決未解決細節，將有助於提升生成結果的可信度與實用性。

## 實務應用指南

## 適用場景

1. **學術論文重現與可重現性驗證**  
   當研究者取得一篇機器學習論文但官方程式碼遺失、不完整或尚未釋出時，可使用 PaperCompiler 將論文方法轉換為儲存庫層級的參考實作，並透過論文導向證據與來源出處追蹤每項實作決策的依據。

2. **企業內部方法落地與原型開發**  
   研發團隊閱讀到適合業務場景的演算法後，可利用 PaperCompiler 快速產出結構化的實作藍圖與檔案規格，縮短從論文到可執行程式碼的距離，特別適合需要保留論文特定方法學約束的專案。

3. **教學與論文導向程式碼教材生成**  
   教育工作者可將 PaperCompiler 產出的規格與對應程式碼作為教材，讓學生清楚看到「論文敘述 → 實作需求 → 檔案所有權分配 → 程式碼」的對應關係，強化對方法細節的理解。

4. **自動化基準測試與方法比較**  
   在 Paper2CodeBench 這類評測基準中，PaperCompiler 可協助大規模產生多篇論文的實作，並透過非退化需求與跨檔案一致性檢查，降低演算法退化與方法層級偏差。

5. **開源貢獻與社群重現專案**  
   開源維護者可使用 PaperCompiler 為熱門論文產生初始儲存庫骨架與檔案層級約束，再交由社群補強工程細節，確保核心方法邏輯不被後續改寫所弱化。

## 實作前置條件

- **資料需求**  
  - 目標論文的全文 PDF 或可用文字內容（含演算法、數學式、實驗設定、評估慣例）。  
  - 若論文引用外部資料集或相依套件，需準備對應的下載路徑、授權資訊與前處理說明。  
  - 建議準備官方程式碼或參考實作（若有），用於驗證基於參考的保真度。

- **運算需求**  
  - 具備可呼叫大型語言模型（LLMs）的 API 金鑰或本地 GPU/TPU 推論環境。  
  - 儲存庫生成階段需要足夠的上下文視窗與多次迭代，建議使用支援長上下文與多輪對話的模型。  
  - 執行與測試生成程式碼需配備適當的運算資源（CPU/GPU、記憶體、磁碟空間）。

- **技能需求**  
  - 熟悉論文領域的機器學習方法與評估協定，能判斷論文支援、推論得出、外部委派與未解決資訊的差異。  
  - 具備軟體工程能力，能審查跨檔案依賴、介面設計與檔案層級約束。  
  - 了解版本控制、持續整合與單元測試，以便在約束導向的儲存庫生成後進行驗證。

## 實作步驟建議

1. **論文接地（Paper Grounding）**  
   將論文全文輸入 PaperCompiler，萃取實作關鍵細節，例如資料前處理、模型初始化、損失函數、訓練流程與評估慣例。此階段會產生實作藍圖，並保留支援性來源證據與來源出處。

2. **證據分類與補全**  
   將萃取出的資訊標記為論文支援、推論得出、外部委派或未解決。對於未解決項目，決定是否透過論文譜系、外部文件或實驗反饋來補強。

3. **規格編譯（Specification Compilation）**  
   將分類後的證據轉換為明確的實作需求，並建立所有權分配、跨檔案依賴與檔案層級約束。特別要加入非退化需求，防止下游編碼智能體簡化或扭曲方法邏輯。

4. **約束導向儲存庫生成（Constraint-Guided Repository Generation）**  
   依據編譯後的規格產生各檔案程式碼，同時保留論文未規定的局部工程選擇彈性。生成過程中持續檢查介面一致性與跨檔案依賴。

5. **驗證與迭代修正**  
   執行生成的儲存庫，比對論文敘述與參考實作，評估基於參考的保真度。針對高嚴重度評估批評進行根因分析，並回到規格編譯階段修正。

6. **文件化與釋出**  
   將規格、來源連結證據與程式碼一併釋出，讓後續使用者能追蹤每項實作決策的論文依據，提升可重現性。

## 潛在風險與注意事項

- **演算法退化**  
  若規格未明確規範方法關鍵語意，下游編碼智能體可能為了簡化實作而忽略核心步驟。建議在規格中明確寫入非退化需求，並透過單元測試驗證關鍵行為。

- **跨檔案不一致**  
  多檔案儲存庫容易出現介面錯配或資料流不一致。應在規格編譯階段完整列出跨檔案依賴，並在生成後進行整合測試。

- **過度推論**  
  系統可能將推論得出的資訊誤當作論文支援。實務上應保留清楚的標記與來源出處，並由領域專家審查未解決與推論項目。

- **外部資源變動**  
  外部委派的套件版本或資料集格式可能改變。建議鎖定版本、記錄環境設定，並在規格中註明相依關係。

- **評估協定偏差**  
  論文常隱含評估慣例，若規格未涵蓋，可能導致實驗結果無法與論文比較。應將評估流程視為獨立的實作需求並分配所有權。

## 與其他技術的整合建議

- **多智能體軟體工程框架**  
  可將 PaperCompiler 視為專門的論文智能體，負責產生結構化規格，再交由通用軟體工程智能體（如 SWE-agent、OpenHands、Agentless）執行檔案生成、除錯與驗證。

- **檢索增強生成（RAG）與論文譜系**  
  結合論文譜系檢索與外部知識庫，可補強未解決資訊，提升推論得出項目的可靠性，類似 AutoReproduce 的做法。

- **多模態證據萃取**  
  對於包含複雜圖表、演算法流程圖或數學式的論文，可整合 AutoP2C 風格的多模態證據模組，強化論文接地階段的資訊完整性。

- **持續整合／持續部署（CI/CD）**  
  將 PaperCompiler 產出的規格與測試需求納入 CI/CD 流程，自動檢查每次修改是否違反非退化需求或跨檔案依賴。

- **版本控制與規格管理**  
  使用 Git 與文件化規格倉儲同步管理，讓實作需求、所有權分配與程式碼變更歷史相互對應，便於協作與審查。

## 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦於圖 1 與圖 2 的對照，理解「自由格式摘要」與「結構化規格」的差異，再跟著 PaperCompiler 的三階段流程走一遍，重點觀察論文敘述如何被轉換成具體的檔案規格與程式碼，不必一開始就深入每個技術細節。

- **AI 工程師**  
  請特別關注規格編譯階段的設計：如何將論文導向證據分類為論文支援、推論得出、外部委派與未解決，以及如何透過非退化需求與所有權分配避免下游編碼智能體的演算法退化，這是將 PaperCompiler 落地到實際開發流程的關鍵。

- **研究人員**  
  建議從可重現性與方法保真度的角度評估本文，思考 PaperCompiler 如何減少方法層級偏差與跨檔案不一致，並可進一步探討規格編譯是否能擴展到論文重現以外的研究自動化任務，例如自動化文獻比較或方法改進。

- **產品經理**  
  可將本文視為一種降低論文技術落地風險的框架，重點理解它如何縮短「論文 → 產品原型」的週期、減少高嚴重度評估批評，以及與現有軟體工程智能體整合的可能性，從而評估在研發流程中導入的投資報酬率。
