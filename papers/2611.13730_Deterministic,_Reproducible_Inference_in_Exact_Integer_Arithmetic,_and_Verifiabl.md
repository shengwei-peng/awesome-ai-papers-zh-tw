tritify 的核心方法論建立在「將浮點從執行時路徑中徹底移除」這一根本性設計原則之上。論文的技術架構可分為三個層次：離線量化階段、執行時整數路徑、以及驗證雙胞胎 (verification twin)。

**離線量化階段**：權重 (weights) 與 epsilon 量化參數 (eps quantization) 在離線時一次性轉換為定點整數 (fixed-point integers)。此階段允許使用浮點運算，因為它不影響執行時的可重現性。值得注意的是，整數編碼後的 GLM-4.5-Air 模型達到 427 GB，這意味著每個參數平均佔用約 4 bytes 的整數表示空間。

**執行時整數路徑 (forward_int)**：這是 tritify 最具創新性的部分。所有元素級資料路徑——矩陣乘法累積 (matrix-multiply accumulation)、再量化 (requantization)、殘差連接 (residual addition)、正規化 (normalization) 與注意力縮放 (attention scales)——皆以精確整數算術執行。具體而言：

1. **動態激活量化**：激活值以每張量 (per-tensor) 動態量化，無需校正階段 (calibration-free)，這與傳統量化方法（如 GPTQ、AWQ）需要校準資料集形成對比。
2. **整數逆均方根 (inverse-RMS)**：正規化層中的逆 RMS 計算採用整數 isqrt 演算法，完全避開 sqrt、frexp 與平台超越函數 (transcendental functions)。
3. **查表非線性 (lookup-table nonlinearities)**：GELU 與 softmax-exp 等非線性函數以整數查表實現，確保跨平台位元一致性。
4. **純整數簿記 (integer bookkeeping)**：當兩個張量相加時選擇共同縮放因子 (common scale) 的標量運算亦為整數。

**驗證雙胞胎 (forward_ref)**：每個操作同時提供整數路徑與浮點參照路徑，並設置一個閘門 (gate) 拒絕任何超出容忍度的偏差。這種「自我驗證」設計哲學貫穿整個系統。

**工程架構**：論文提出「凍結通用引擎 + 家族外掛」(frozen generic engine plus per-family plugins) 的架構，使可重現性屬性可重複使用於不同模型家族。

**與可重現浮點方案的比較**：論文承認可重現浮點是可達成的，例如 ReproBLAS 透過固定歸約順序 (reduction-pinned BLAS) 實現。然而，此類方案：(1) 有性能成本；(2) 非標準推理堆疊的預設行為；(3) 僅固定求和順序，無法使整個異質模型的推理位元相同。tritify 的整數路徑從根本上消除了 IEEE-754 加法非結合性 (non-associativity) 與超越函數平台差異的根源問題。

### 潛在風險與注意事項

**風險一：分散式部署增加延遲**
分散式推理的本質是「換容量而非換速度」。跨機網路通訊會增加延遲，對即時性要求高的應用（如即時翻譯、互動對話）需評估是否可接受。緩解方式：將通訊密集的層（如注意力）放在同一機器，僅將專家權重分散。

**風險二：不保證機密性**
tritify 提供的是「可驗證」而非「可保密」。驗證預言機需要存取權重才能重新計算，因此權重本身仍是公開或半公開的。若需要隱私保護，需另行整合同態加密或安全多方計算。緩解方式：將 tritify 視為「誠實執行驗證層」，與現有的加密通訊層疊加使用。

**風險三：浮點中間值不相等**
整數路徑的最終決策與浮點參照一致，但中間張量的浮點表示不會位元相等。若下游系統依賴中間值的精確位元（如某些除錯工具或特徵監控），會出現差異。緩解方式：明確區分「決策層級驗證」與「中間值層級驗證」，僅在需要時比對中間值。

**風險四：對不誠實伺服器的保護尚未完成**
論文明確指出「將誠實執行一致性提升為對不誠實伺服器的保證」屬於未來工作。目前的驗證機制假設伺服器會誠實執行計算，僅驗證「執行結果是否正確」，無法防範伺服器主動造假（如預先計算答案跳過推理）。緩解方式：等待論文中提到的後續工作，或自行整合零知識證明層。

**風險五：模型架構覆蓋範圍有限**
目前驗證的模型類別為 decoder-only LM、MoE decoder、Segment Anything 2.1。編碼器模型、擴散模型、強化學習策略網路等尚未驗證。緩解方式：先在小型子任務上驗證目標模型的位元一致性，再決定是否全面採用。

**風險六：量化誤差累積**
雖然論文聲稱「無保真度斷崖」，但極深層數（如 16 層以上）的誤差仍需逐層監控。緩解方式：建立 per-layer fidelity 儀表板，對每層輸出的雜湊與浮點參照比對，設定自動告警閾值。

### 與其他技術的整合建議

**與 vLLM、TGI、TensorRT-LLM 等推理框架整合**
tritify 並非要取代這些高效能推理框架，而是提供「確定性層」。建議架構：使用 tritify 作為驗證基準與離線量化工具，主線推理仍用高效能框架，僅在關鍵決策點（如最終 token 選擇）用 tritify 驗證。對於需要位元一致性的場景，則直接以 tritify 為推理引擎。

**與 Kubernetes / 分散式運算平台整合**
將 tritify 的分散式推理封裝為 Kubernetes Operator，自動處理模型分片、節點選擇、網路配置。整合 Prometheus 監控各分片的 SHA-256 一致性，整合 OpenTelemetry 追蹤跨機推理的延遲分布。

**與零知識證明（ZKP）系統整合**
這是論文中標記為「未來工作」的方向。技術路線：將 tritify 的整數運算電路化，使用 Halo2 或 Plonky2 等 ZKP 框架產生推理證明，讓驗證者無需重新執行即可確認結果正確性。預期整合後可實現真正的「對不誠實伺服器的保證」。

**與 MLOps / 模型版本管理整合**
將 tritify 產生的 SHA-256 作為模型版本的一部分存入模型註冊表（Model Registry，如 MLflow）。每次模型更新自動產生新基準 SHA-256，並在 CI/CD 流程中驗證新版本與舊版本在相同輸入下的決策差異。

**與學術重現性平台整合**
論文與程式碼可整合到 Papers with Code、HuggingFace Model Hub 等平台，讓每個模型卡附帶 tritify 重現指令與基準 SHA-256，推動 ML 研究的可重現性標準。

**與邊緣運算框架整合**
在邊緣裝置（手機、嵌入式系統、IoT 裝置）上部署 tritify 的輕量版本，利用其無需 CUDA/GPU 的特性降低硬體需求。與 ONNX Runtime、TFLite 等邊緣框架並存，根據場景選擇確定性優先或速度優先。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節（Introduction），重點理解「為什麼浮點推理不可重現」這個核心問題——IEEE-754 加法不具結合性、平台數學函式庫對超越函數的捨入規則不同。接著看第 2 節的三個明確聲明，了解 tritify 宣稱做到什麼、不宣稱做到什麼。技術細節可暫時跳過，重點是建立「位元級可重現性」這個概念框架。

**給 AI 工程師**：直接進入第 3 節以後的技術章節，仔細研究整數算術的實作細節——動態 per-tensor 量化、整數 isqrt、查找表實作 GELU/softmax。特別關注「凍結的通用引擎 + 家族外掛」這個架構設計，這是將 tritify 擴展到新模型類別的關鍵。實作時建議從小型模型（如 OLMoE-1B-7B）開始驗證，再逐步擴展到生產規模。

**給研究者**：重點關注方法論的嚴謹性——論文明確區分三個獨立聲明並逐一驗證，這在 ML 系統論文中相當罕見。仔細審視「per-layer fidelity through sixteen layers」的實驗設計，理解如何測量保真度斷崖。對「可驗證分散式推理」的理論意涵感興趣的讀者，可思考其與可驗證計算（Verifiable Computing）、委託計算（Delegated Computation）理論的關聯。

**給產品經理**：聚焦於商業價值的轉譯——tritify 開啟了「雲端容量 + 本地可驗證」的第三種部署選項，打破「全本地（私有但受限）vs 全雲端（強大但需盲信）」的二元市場。理解論文中明確標記的限制：不保證速度提升、不保證機密性、對不誠實伺服器的保護是未來工作。評估導入時機時，優先考慮合規需求強、結果需第三方驗證、模型規模超出單機容量的場景。
