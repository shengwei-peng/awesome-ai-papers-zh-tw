## ⚡ TL;DR

靜態程式碼基準會洩漏至訓練資料，且終將被更強代理飽和。

1,500回合賽事顯示GPT-5.5修復率98.3%最強，難度隨編寫能力提升。

## 摘要翻譯

靜態程式碼基準（Static Benchmark）在發布時即已固定。隨著時間推移，其任務會洩漏至訓練資料（Training Data）中，且更強的代理最終會使其達到飽和（Saturation）。我們主張基準應致力於自擴展：其任務與驗證標準（Oracle）於評測時（Evaluation Time）建立，因此不存在預先可洩漏的內容，且其難度由參與代理決定，而非在發布時固定。我們提出 SWE-Duel，這是一個由兩個程式碼代理（Coding Agents）透過鏡像紅藍對抗回合（Mirrored Adversarial Turn）相互評估的競技場。在每個回合中，紅方代理（Red Agent）在三個上下文隔離會話（Context-Isolated Session）中處理一個真實的程式碼儲存庫（Repository）。其提出並實作一項新功能，並為其撰寫功能測試（Feature Test），接著在該功能中嵌入一個細微的漏洞，並附上密封式觸發漏洞測試（Sealed Bug-Triggering Test）。最終的拉取請求（Pull Request, PR）僅在以下條件成立時才會被接受：(1) 通過功能測試與程式碼儲存庫的既有測試，且恰好在漏洞測試上失敗；以及 (2) 同一代理的一個全新會話能夠在盲測情況下修復該漏洞，此條件用以排除無法解決的任務。接著藍方代理（Blue Agent）審查該拉取請求，但不會被告知存在漏洞。其僅在修訂版本（Revision）通過所有三套測試時獲勝，之後兩個代理交換角色。我們在五種程式語言的 15 個程式碼儲存庫上，針對 11 個模型外殼參與者（Model-Harness Participant）進行了 1,500 回合的錦標賽（Tournament）。領先者各以不同方式勝出。GPT-5.5 搭配 Codex CLI 排名第一，為最強的解題器（Solver），在其所審查的缺陷（Defect）中修復了 98.3%。Claude Opus 4.8 搭配 mini-swe-agent 排名第二，為最強的任務編寫者，紅方勝率（Red Win Rate）為 27.3%。最後，在同一個模型系列中，最新版本所撰寫的任務擊敗固定參考解題器（Fixed-Reference Solver）的比例遠高於舊版本（42.9% 對比 4.0%），這初步證明了任務難度（Task Difficulty）隨任務編寫能力（Task Authoring Capability）同步擴展。

### 核心貢獻（3～5點）
- 提出自擴展競技場（Self-Scaling Arena）概念，解決靜態基準（Static Benchmark）的資料洩漏（Leakage）與飽和（Saturation）問題，使基準難度隨參與代理能力動態調整
- 設計 SWE-Duel 對抗式競技場（Adversarial Arena），透過鏡像紅藍對抗回合（Mirrored Adversarial Turn）讓兩個程式碼代理（Coding Agents）以紅方（Red Agent）與藍方（Blue Agent）角色相互評估
- 引入雙重驗證機制：任務須同時通過功能測試（Feature Test）、既有測試與密封式觸發漏洞測試（Sealed Bug-Triggering Test），且須能被同代理於盲測下修復，確保任務可解且難度適中
- 進行大規模實驗驗證：在 15 個程式碼儲存庫（Repository）、5 種程式語言上進行 1,500 回合錦標賽（Tournament），涵蓋 11 個模型外殼參與者（Model-Harness Participant），包含 GPT-5.5 與 Claude Opus 4.8 等前沿模型（Frontier Model）
- 證明任務難度（Task Difficulty）與任務編寫能力（Task Authoring Capability）成正比：同一模型系列中，最新版本所撰寫的任務擊敗固定參考解題器（Fixed-Reference Solver）的比例（42.9%）遠高於舊版本（4.0%）

### 適合對象
從事大型語言模型（LLM, Large Language Model）評測、程式碼代理（Coding Agents）研究、自動化軟體工程的學者與工程師；對基準設計、對抗式評測協定（Evaluation Protocol）、AI 安全與紅隊測試（Red Teaming）感興趣的研究人員；以及關注前沿模型（Frontier Model）能力評估與資料洩漏（Leakage）問題的業界實務工作者。

## 深度分析

#### 方法論解析

SWE-Duel 提出了一種根本性的基準測試範式轉移——從「靜態基準」轉向「自擴展競技場」(Self-Scaling Arena)。其方法論核心在於解決兩個長期困擾程式碼基準測試的問題：訓練資料洩漏 (Leakage) 與任務飽和 (Saturation)。

**核心機制：鏡像對抗回合 (Mirrored Adversarial Turn)**

整個系統建立在「紅藍對抗」(Red-Blue Adversarial) 的雙代理互評架構上。每個回合包含三個上下文隔離會話 (Context-Isolated Session)，確保代理在不同階段無法存取彼此的內部狀態：

1. **紅方代理 (Red Agent) 的任務編寫階段**：在真實程式碼儲存庫 (Repository) 上提出新功能、實作該功能並撰寫功能測試 (Feature Test)，接著植入一個細微的漏洞 (Bug)，並配套密封式觸發漏洞測試 (Sealed Bug-Triggering Test)。此處的「密封」設計至關重要——藍方代理無法看到這些測試，避免了「作弊式還原」(trivial revert) 的可能性。

2. **雙重閘門驗證 (Dual-Gate Validation)**：提交的拉取請求 (Pull Request, PR) 必須同時通過兩個條件：
   - **功能性閘門**：通過功能測試與儲存庫既有測試，但恰好失敗於漏洞測試
   - **可解性閘門**：同一代理在全新會話中能夠「盲目修復」(repair blind) 自身植入的漏洞，這排除了不可解任務

3. **藍方代理 (Blue Agent) 的審查階段**：在不獲知漏洞存在的情況下審查 PR，並提交修訂版本 (Revision)。藍方勝出的條件是其修訂版本同時通過三套測試套件：功能測試（功能保留）、漏洞測試（漏洞修復）、既有測試（無回歸）。

**自擴展性 (Self-Scaling Property) 的形式化保證**

此設計的精妙之處在於：所有任務內容（功能、漏洞、判準/驗證標準 Oracle）皆在評測時 (Evaluation Time) 動態生成，因此不存在預先可洩漏的內容。同時，任務難度由參與代理自身的任務編寫能力決定，而非由人類開發者歷史所設定的固定難度上限。這形成了一個自我強化的迴圈——更強的代理能編寫更難的任務，而這些任務又能更精準地測量下一代代理。

**覆蓋的軟體工程生命週期**

單一對決實際上同時評估了六項核心能力：需求規格化 (Requirement Specification)、功能實作 (Feature Implementation)、測試生成 (Test Generation)、程式碼審查 (Code Review)、缺陷定位 (Fault Localization) 與程式修復 (Program Repair)。這種「一對決多能力」的設計大幅提升了評估的資訊密度。

#### 實驗數據解讀

**錦標賽規模與設計**

實驗在 11 個模型-外殼參與者 (Model-Harness Participant) 之間進行，涵蓋 15 個跨五種程式語言的儲存庫，共產生 1,500 個回合。其中 10 位參與者進行完整循環賽 (Round Robin)，Gemini 3.1 Pro 作為後期加入者僅參與 5 場比賽。這種設計允許新模型以低成本加入既有排行榜。

**關鍵結果分析**

1. **解題能力冠軍**：GPT-5.5 搭配 Codex CLI 修復了 98.3% 的審查缺陷，展現出壓倒性的解題能力。這意味著當 GPT-5.5 處於藍方角色時，幾乎能識別並修復所有紅方植入的漏洞。

2. **任務編寫能力亞軍**：Claude Opus 4.8 搭配 mini-swe-agent 以 27.3% 的紅方勝率 (Red Win Rate) 排名第二。這是一個極具啟發性的指標——它說明 Claude Opus 4.8 能編寫出連對手都難以修復的困難任務，體現了「攻擊即防守」的對抗性優勢。

3. **代際難度追蹤證據**：在同一模型家族內，最新版本編寫的任務擊敗固定參考解題器 (Fixed-Reference Solver) 的比例為 42.9%，而舊版本僅為 4.0%。這個 10 倍以上的差距提供了初步證據：任務難度確實隨任務編寫能力 (Task Authoring Capability) 同步提升，這正是「自擴展」性質的經驗驗證。

**指標設計的深層意涵**

紅方勝率與藍方修復率是兩個互補但不等價的指標。一個代理可能在「解題」上極強（高藍方修復率），但在「編寫困難任務」上較弱（低紅方勝率），反之亦然。這種雙維度評估避免了單一指標帶來的盲點，也解釋了為何 GPT-5.5 與 Claude Opus 4.8 能以不同方式「贏得」錦標賽。

#### 與現有研究的比較

**與靜態基準的比較**

SWE-bench Verified 的失敗案例最具警示意義：OpenAI 已停止回報其在該基準上的結果，因為前沿模型能夠重現其標準修補程式 (Gold Patch)。這直接證明了靜態基準的「過期性」——一旦釋出便開始貶值。SWE-Duel 透過評測時生成任務從根本上繞過了這個問題。

**與持續更新基準的比較**

SWE-bench-Live 與 SWE-rebench 透過收集訓練截止時間 (Training Cutoff) 後的 GitHub 議題來延緩洩漏，但這些任務的難度仍受人類開發者日常問題所限制。SWE-Duel 的突破在於：任務難度不再受限於人類開發歷史，而是由代理自身的能力上限決定。

**與模型生成任務的比較**

BugPilot 雖然也收集代理產生的漏洞，但採用「先產生、後固定」的模式，本質上仍是靜態集合。SwingArena 雖然採用對抗式競技場 (Adversarial Arena) 設計，但任務池仍來自固定的 GitHub 議題，僅在評測時生成驗證標準。SWE-Duel 是首個同時在「任務」與「判準」兩個維度都實現評測時生成的系統。

**與任務擾動方法的比較**

DyCodeEval 等方法透過擾動原始任務來避免精確記憶化，但保留了原始任務與解答。這種方法僅能防禦「死記硬背」式攻擊，無法防禦「理解後推導」式攻擊。SWE-Duel 由於任務本身是全新的，不存在被推導的基礎。

**現有侷限性**

1. **可解性閘門的偏差**：要求紅方代理能自我修復漏洞，這可能系統性地偏向「對紅方代理而言較容易但對其他代理較困難」的任務，而非真正困難的任務。
2. **儲存庫選擇偏差**：15 個儲存庫的代表性有限，可能無法完全反映真實軟體開發的多樣性。
3. **對抗動態的單一性**：紅藍雙方僅有「編寫漏洞」與「修復漏洞」兩種角色，未涵蓋更廣泛的對抗場景（如效能對抗、安全對抗）。

#### 可重現性評估

SWE-Duel 在可重現性方面展現了明確的承諾：

1. **開放競技場工具包**：作者釋出了 SWE-Duel 的開源工具包，使社群能從零開始舉辦自己的錦標賽，或將新代理加入既有排行榜。這大幅降低了後續研究的進入門檻。

2. **完整的錦標賽資料**：1,500 回合的完整記錄應包含所有任務、漏洞、測試與結果，這些資料本身就是寶貴的研究資源。

3. **多模型覆蓋**：實驗涵蓋了前沿專有模型 (GPT-5.5、Claude Opus 4.8、Gemini 3.1 Pro) 與開放權重模型 (DeepSeek V4 Pro)，並搭配三種不同的代理外殼 (Agent Harness)，提供了豐富的跨配置比較資料。

**侷限性**

1. **前沿模型的權重不可獲取**：GPT-5.5、Claude Opus 4.8 等專有模型無法本地重現，限制了對模型行為的深入分析。
2. **任務的隨機性**：由於任務在評測時生成，無法精確重現特定回合的完整狀態，這對除錯與案例研究構成挑戰。
3. **儲存庫環境依賴**：實驗依賴特定版本的儲存庫與依賴項，環境配置的長期維護是個潛在問題。

#### 未來研究方向

**1. 多代理對抗拓撲擴展**

當前設計僅限於雙代理對抗。未來可探索多代理場景，例如「紅方聯盟」對「藍方聯盟」，或引入「白方代理」作為公正的測試生成者。這將更貼近真實軟體開發中的多方協作與利益衝突。

**2. 對抗維度的多樣化**

現有設計聚焦於「功能性正確性」對抗。可擴展至：
- **效能對抗**：紅方編寫功能正確但效能低落的實作
- **安全對抗**：紅方植入安全漏洞而非功能性漏洞
- **可維護性對抗**：紅方編寫功能正確但難以維護的程式碼

**3. 自擴展性的理論分析**

目前「自擴展」性質僅有初步經驗證證據（42.9% vs. 4.0%）。未來需要：
- 形式化定義「自擴展性」並證明其理論邊界
- 分析「可解性閘門」對難度上限的約束機制
- 研究是否存在「任務編寫能力飽和」現象

**4. 跨領域遷移**

SWE-Duel 目前專注於程式碼任務。其「評測時生成任務與判準」的核心思想可遷移至：
- 數學推理基準（代理互相設計證明題）
- 對話系統評測（代理互相設計對話場景）
- 機器學習模型評測（代理互相設計資料集）

**5. 人機協作評測**

將人類開發者引入對抗迴圈，例如「人類紅方 vs. 代理藍方」或「代理紅方 vs. 人類藍方」，可評估代理在真實人機協作場景中的表現，並研究人類與代理在任務編寫能力上的差異。

**6. 長期演化研究**

追蹤同一基準在多代模型上的表現，繪製「任務難度-模型能力」共同演化曲線。這將為 AGI 進展的測量提供全新的方法論基礎。

**7. 漏洞植入策略的理論化**

紅方代理的漏洞植入目前是黑盒過程。未來可研究：
- 不同漏洞類型（語法、邏輯、邊界條件、並發）的相對難度
- 漏洞植入策略的可學習性
- 漏洞植入與修復之間的「資訊不對稱」量化

## 論文問答

**Q1：靜態程式碼基準測試面臨的核心問題是什麼？為什麼這個問題會隨時間惡化？**
A：靜態基準測試在發布時即被固定，其任務內容與標準答案會隨著時間逐漸洩漏到模型的訓練資料中，因為大型語言模型持續從公開材料學習。更嚴重的是，當更強的代理出現時，這些固定的任務集會被「飽和」——也就是說，代理的能力會超越基準測試所能測量的範圍。這意味著從基準發布的那一刻起，它就開始失去區分前沿模型能力的能力，使得基準測試失去長期可信的評測信號，這也是 OpenAI 近期停止回報 SWE-bench Verified 結果的主因。

**Q2：現有的解決方案（如 SWE-bench-Live、SWE-rebench、BugPilot、SwingArena）為何仍無法達到「自擴展」的要求？**
A：SWE-bench-Live 與 SWE-rebench 透過持續從 GitHub 收集新任務來緩解資料洩漏問題，但其任務難度仍受限於人類開發者日常面對的議題，無法隨代理能力提升而提高。BugPilot 雖然收集代理實作功能時意外引入的漏洞，但這些任務仍是預先生成的固定集合，無法在評測時動態生成。SwingArena 雖然採用對抗式競技場的形式，但任務仍來自固定的人類撰寫 GitHub 議題池，僅在評測時生成驗證標準，因此這些方法都無法同時滿足「任務在評測時生成」與「難度由參與者決定」這兩個自擴展的核心條件。

**Q3：為什麼「自擴展」這個特性對於程式碼代理的長期評測如此重要？**
A：自擴展特性確保基準測試能持續提供有意義的區分信號，因為任務難度會隨著代理能力的提升而自動調整，避免被飽和的命運。此外，由於所有任務與判準都是在評測時才生成，這些具體內容不可能事先存在於訓練資料中，從根本上解決了資料洩漏問題。這種設計讓基準測試從「一次性發布的靜態工具」轉變為「能與領域共同演化的動態評測生態系」，對於維持前沿模型評測的可信度與時效性至關重要。

**Q4：SWE-Duel 的「鏡像對抗回合」具體是如何運作的？紅方與藍方代理各自扮演什麼角色？**
A：在每個回合中，紅方代理在一個真實的程式碼儲存庫上工作，跨越三個上下文隔離的會話，依序完成提議新功能、實作功能並撰寫功能測試、嵌入細微漏洞並附上密封式觸發漏洞測試等任務。接著藍方代理在不被告知漏洞存在的情況下審查這個拉取請求，並提交修訂版本；只有當修訂版本同時通過功能測試、漏洞測試與現有回歸測試時，藍方才算獲勝。雙方在下一回合交換角色，這種鏡像設計讓每個代理同時被評估為解題者與任務編寫者兩個維度，全面剖析其在軟體工程生命週期中的表現。

**Q5：拉取請求的「准入條件」為何設計得如此嚴格？這背後的關鍵創新是什麼？**
A：拉取請求必須同時通過功能測試與儲存庫的現有測試，但必須恰好失敗於漏洞測試，這個看似矛盾的條件確保了任務既非平凡也非不可能。關鍵創新在於「自我修復閘門」——紅方代理必須在全新的會話中盲目修復自己植入的漏洞，這個機制排除了無法解決的任務，避免了藍方代理面對不可能的挑戰。這種雙重驗證機制讓 SWE-Duel 能同時保證任務的可解性與鑑別度，是其自擴展特性的核心保障，也避免了「紅方設計出自己也解不開的任務」這種退化情形。

**Q6：為什麼紅方代理需要使用三個上下文隔離的會話？這種設計選擇帶來什麼好處？**
A：三個上下文隔離的會話分別用於功能提案、功能實作與測試撰寫、以及漏洞嵌入，這種設計防止了代理在單一長上下文中產生「自我洩漏」——也就是避免代理在後續會話中記得自己植入漏洞的位置或方式。這個設計也模擬了真實軟體工程中不同角色（如產品經理、開發者、測試者）的協作流程，讓評測更貼近實際工作情境。更重要的是，這種隔離讓自我修復閘門成為真正有意義的測試，因為修復代理面對的是與植入代理完全不同的資訊環境，無法依賴記憶作弊。

**Q7：SWE-Duel 的錦標賽是如何設置的？參與者與評測規模為何？**
A：錦標賽共有 11 個模型外殼參與者，每個參與者配對一個前沿的專有或開放權重模型（如 GPT-5.5、Claude Opus 4.8、DeepSeek V4 Pro、Gemini 3.1 Pro）與三種代理外殼之一。評測在 15 個涵蓋五種程式語言的程式碼儲存庫上進行，其中 10 位參與者進行完整的循環賽，Gemini 3.1 Pro 作為遲到加入者僅進行 5 場比賽，總共產生 50 場比賽與 1,500 個回合。這種大規模、多語言、多模型的設計確保了結果的穩健性與泛化性，也展示了 SWE-Duel 框架的廣泛適用性。

**Q8：錦標賽的關鍵結果是什麼？不同領導者展現了什麼不同的「獲勝方式」？**
A：GPT-5.5 搭配 Codex CLI 排名第一，是最強的解題器，修復了 98.3% 它所審查的缺陷；Claude Opus 4.8 搭配 mini-swe-agent 排名第二，是最強的任務編寫者，紅方勝率達 27.3%。這顯示了不同模型在「解題」與「出題」這兩個維度上具有截然不同的優勢——有些模型善於發現並修復他人埋藏的問題，有些則善於設計出能難倒對手的任務。這種「不同維度的冠軍」現象揭示了程式碼代理能力的多面向性，單一指標無法完整捕捉，也暗示未來基準測試應採用多維度評估。

**Q9：有什麼初步證據顯示任務難度會隨任務編寫能力而擴展？**
A：在同一個模型家族中，新版本所撰寫的任務擊敗固定參考解題器的比例（42.9%）遠高於舊版本（4.0%），這提供了任務難度追蹤編寫能力的初步證據。這個結果意味著當代理的編寫能力提升時，它能設計出更難以被解決的任務，從而自動提升基準測試的鑑別度。這種「自我調整難度」的特性正是自擴展基準測試的核心承諾，也是 SWE-Duel 與傳統靜態基準測試最根本的差異，證明了「代理互相評估」這條路徑的可行性。

**Q10：SWE-Duel 在實際應用上能支援哪些場景？**
A：SWE-Duel 可用於持續監控前沿程式碼代理的真實能力，因為其自擴展特性確保評測不會因資料洩漏或飽和而失效，能長期提供有意義的比較基準。企業可利用此框架評估內部部署的程式碼助理，因為它能反映代理在完整軟體工程生命週期中的表現，包括需求規格、功能實作、測試生成、程式碼審查、缺陷定位與程式修復等多個環節。此外，社群可透過開放的競技場工具包啟動自己的錦標賽或將新代理加入現有排行榜，促進基準測試生態系的多元化發展。

**Q11：從產品角度來看，這個研究對 AI 程式碼工具的開發有何啟示？**
A：產品開發者應意識到「解題能力」與「任務編寫能力」是兩個獨立的維度，單一基準測試無法完整評估代理的綜合表現，這意味著產品定位需要根據目標使用場景選擇合適的代理。例如，程式碼審查工具可能更看重解題能力，而自動化測試生成工具則可能更看重任務編寫能力。此外，由於 SWE-Duel 涵蓋了完整的軟體工程生命週期，產品設計應考慮如何讓代理在多個環節中協作，而非僅僅優化單一任務的表現，這也呼應了業界對「AI 軟體工程師」而非「AI 程式碼片段產生器」的期待。

**Q12：SWE-Duel 對程式碼代理研究領域的更廣泛影響是什麼？**
A：SWE-Duel 重新定義了基準測試的角色，從「靜態測量工具」轉變為「動態演化生態系」，這可能激發更多關於自擴展評測方法的研究。在方法論上，它展示了對抗式設計在程式碼代理評測中的威力，可能影響後續基準測試的設計範式，鼓勵研究者採用「代理互相評估」的思路。更深遠地，這種「代理互相評估」的思路可能擴展到其他 AI 領域，如數學推理、科學發現等，推動整個 AI 評測文化從「人類設計任務測 AI」轉向「AI 設計任務測 AI」。

**Q13：SWE-Duel 存在哪些已承認的限制？**
A：雖然 SWE-Duel 解決了資料洩漏與難度飽和問題，但其評測結果仍受限於所選的 15 個程式碼儲存庫與五種程式語言，可能無法完全代表所有軟體開發場景，例如嵌入式系統或特定領域框架。此外，紅方代理的「自我修復閘門」雖然排除了無法解決的任務，但這個機制本身也限制了任務難度的上限——若紅方無法修復自己植入的漏洞，任務就不會被採用，因此任務難度被紅方自身能力所約束。最後，錦標賽僅進行了 1,500 回合，對於統計穩定性而言仍屬中等規模，更大規模的評測可能揭示更細微的能力差異。

**Q14：SWE-Duel 可能會出現哪些失敗案例或邊緣情況？**
A：一個潛在的失敗案例是紅方代理可能學會「對抗性自我修復」——也就是設計出自己能在新會話中修復、但對手幾乎無法修復的特定漏洞模式，這會降低基準測試的鑑別度並偏向特定解題風格。另一個邊緣情況是當藍方代理透過簡單地還原程式碼儲存庫到原始版本來「解決」問題，但這在 SWE-Duel 中被功能保留機制所防範，因為還原會移除已實作的功能而無法通過功能測試。還有一個潛在問題是若所有參與代理的能力趨於一致，紅藍雙方勝率可能收斂到 50%，使得排名失去區分意義，這也是自擴展基準測試需要持續引入新參與者的原因。

**Q15：SWE-Duel 的未來發展方向有哪些？**
A：未來可擴展到更多程式語言與程式碼儲存庫類型，特別是那些在當前錦標賽中代表性不足的領域，如嵌入式系統、遊戲開發或科學計算，以提升評測的生態代表性。此外，可探索多代理協作場景，讓紅藍雙方各自組隊，考驗代理在團隊動態中的表現，這也更貼近真實軟體開發的協作模式。另一個有趣方向是將 SWE-Duel 的自擴展理念應用於其他 AI 能力評測，如多模態理解、複雜推理或機器人控制等，建立跨領域的自擴展評測生態系，從根本上改變 AI 評測的文化與方法論。

## 實務應用指南

### 適用場景

**1. 企業內部程式碼代理模型的縱向評測**
企業研發團隊可將 SWE-Duel 部署為內部 CI 流程的一部分，定期對自家程式碼代理（如內部微調模型或第三方 API）進行對抗式評測。透過紅藍回合自動產生「難度隨模型演進」的測試案例，避免傳統 SWE-bench 類基準因資料洩漏而失效的問題，並可作為模型升級前的把關機制。

**2. 程式碼審查（Code Review）模型的訓練資料生成器**
傳統程式碼審查訓練資料需仰賴人工標註或從開源專案挖掘，品質與多樣性受限。SWE-Duel 的紅方代理可自動產生「含有微妙缺陷的新功能 PR」，藍方代理的修訂版本則可作為「正確修復」的對照樣本，雙方互補形成高品質的監督式訓練資料，特別適合訓練 fault localization 與 patch generation 模型。

**3. AI 程式設計競賽與黑客松平台**
平台營運商可基於 SWE-Duel 架構舉辦「AI vs AI」對抗賽，觀眾可即時觀看兩個代理在真實儲存庫上互相攻防。相較於靜態題目庫，此模式提供無限且難度自適應的競賽內容，並可作為模型發表會、技術年會的展示環節。

**4. 程式碼代理的紅隊演練（Red Teaming）與安全性測試**
資安團隊可將 SWE-Duel 作為「對代理本身發動攻擊」的工具：紅方代理刻意植入各類漏洞（邏輯錯誤、邊界條件、資源洩漏等），用以測試藍方代理是否能識別並修復。這比單純的靜態漏洞資料庫更能反映代理在真實 PR 審查流程中的表現。

**5. 學術研究中代理架構與規劃能力的縱向比較**
研究人員可利用 SWE-Duel 的「任務難度隨編寫能力成長」特性，比較不同代理架構（如 ReAct、Reflexion、Tree-of-Thought）在「自我編寫任務難度」上的差異，探究代理的元認知（meta-cognition）能力如何影響其作為出題者的上限。

### 實作前置條件

**資料前置條件**
- **基準儲存庫集合**：至少需準備 10–20 個具備完整測試套件、活躍維護的開源儲存庫，覆蓋 3 種以上程式語言（論文使用 15 個儲存庫、5 種語言）。每個儲存庫需具備可容器化的環境（Dockerfile 或等效設定）。
- **既有測試套件**：每個儲存庫需有可獨立執行的回歸測試，作為「無回歸」判定的基準。
- **訓練截止時間錨點**：若需評估「任務難度隨編寫能力成長」的縱向效果，需準備同一模型家族的多個版本快照。

**計算前置條件**
- **LLM API 配額**：每場對戰需執行 3 個上下文隔離會話（紅方提案、紅方自修、藍方審查），1,500 回合的錦標賽估計需數百萬至數千萬 token 的 API 額度。
- **容器執行環境**：每個會話需在隔離的容器中執行，避免上下文污染與檔案系統衝突；建議使用 Kubernetes 或 Docker Compose 編排。
- **平行運算能力**：錦標賽需支援多場對戰同時進行；建議至少 50–100 個並行容器槽位。
- **持久化儲存**：每回合的程式碼狀態、測試結果、PR 內容需結構化儲存以便後續分析。

**技能前置條件**
- **LLM 代理開發經驗**：熟悉 prompt engineering、tool use、function calling 與代理迴圈設計。
- **DevOps 與 CI/CD**：能撰寫 Dockerfile、設定 GitHub Actions 或等效 CI 流程、處理測試隔離。
- **測試框架知識**：理解 pytest、JUnit、Go test 等主流框架的執行與結果解析。
- **統計分析能力**：能處理 Elo 等級分、勝率、信賴區間等錦標賽指標。
- **基礎設施工程**：熟悉容器編排、資源配額、任務排程系統。

### 實作步驟建議

**步驟 1：建立儲存庫沙箱與測試執行層**
挑選 15 個符合條件的開源儲存庫，為每個撰寫 `Dockerfile` 與 `run_tests.sh` 腳本，確保既有測試套件可在容器內穩定執行。將每個儲存庫標記為「乾淨基準狀態」，作為後續判定「無回歸」的對照組。

**步驟 2：實作紅方代理的三會話流程**
- 會話 A（功能提案與實作）：給定儲存庫，提示代理提出新功能、實作程式碼並撰寫功能測試。
- 會話 B（漏洞植入）：在隔離上下文中，提示代理在已實作的功能中植入微妙缺陷，並撰寫能觸發該缺陷的測試。
- 會話 C（自我修復閘道）：在全新會話中，要求同一代理僅憑 PR 內容修復缺陷。此步驟為「可解性過濾器」，剔除過於刁鑽或無法修復的任務。

**步驟 3：實作 PR 驗收邏輯**
對紅方提交的 PR 執行三項確定性檢查：(1) 功能測試通過；(2) 既有回歸測試通過；(3) 漏洞觸發測試失敗。三者皆成立才進入下一階段，否則該回合作廢並重新抽樣。

**步驟 4：實作藍方代理的審查流程**
藍方代理僅看到 PR 與功能測試（看不到漏洞測試），需提交修訂版本。執行三項檢查：(1) 功能測試通過（功能保留）；(2) 漏洞測試通過（漏洞修復）；(3) 既有測試通過（無回歸）。三者皆通過則藍方勝，否則紅方勝。

**步驟 5：實作錦標賽排程與 Elo 評分系統**
採用循環賽（round-robin）排程，每對參與者進行固定場數對戰。整合 Elo 或 Glicko 評分系統，根據勝率動態更新排名。支援「晚加入者」機制（論文中的 Gemini 3.1 Pro 即以此方式加入）。

**步驟 6：建立觀測與分析儀表板**
記錄每回合的詳細指標：紅方勝率、藍方修復率、任務編寫耗時、漏洞類型分布、修復耗時等。提供模型 × 外殼（harness）的二維熱力圖，揭示不同組合的強項（如 GPT-5.5 + Codex CLI 為最強解題器，Claude Opus 4.8 + mini-swe-agent 為最強編題者）。

**步驟 7：縱向難度追蹤實驗**
若要驗證「任務難度隨編寫能力成長」，固定一個解題器（如某版本的 Claude），讓不同版本（舊版 vs 新版）的代理作為紅方編寫任務，統計固定解題器的失敗率。論文中此差距為 42.9% vs 4.0%，可作為基準預期值。

**步驟 8：開源工具包釋出與社群營運**
將上述元件打包為可重現的 arena toolkit，提供 CLI 介面讓社群新增自有的代理參與者，並建立公開排行榜與定期錦標賽機制。

### 潛在風險與注意事項

**風險 1：自我修復閘道限制了任務難度上限**
紅方代理必須能在新會話中修復自己植入的漏洞，這雖然排除了不可解任務，但也意味著「紅方能編寫的最難任務」上限被紅方自身能力所限制。**緩解方式**：放寬閘道條件（例如允許紅方使用更強的解題器作為修復者），或引入「異質修復者」機制。

**風險 2：紅方代理可能產生「過於明顯」的漏洞**
若紅方代理傾向植入易被發現的漏洞（如語法錯誤、明顯邏輯反轉），則藍方勝率會虛高，無法反映真實審查能力。**緩解方式**：在 prompt 中明確要求「微妙且非顯而易見的缺陷」，並對漏洞類型分布進行監控；若某類漏洞占比過高則調整 prompt。

**風險 3：藍方代理可能透過「重置整個 PR」繞過漏洞**
若藍方代理直接拒絕整個 PR，雖然會通過漏洞測試（因為漏洞不存在了），但會失敗於功能測試（功能也消失了）。**緩解方式**：論文的設計已透過「功能保留」檢查防堵此策略；實作時需嚴格驗證三項測試皆執行於藍方提交的最終狀態。

**風險 4：計算成本與時間成本極高**
1,500 回合的錦標賽需大量 API 呼叫與容器執行時間，單次完整錦標賽可能耗時數天至數週。**緩解方式**：採用抽樣錦標賽（subset tournament）、早期停止（early stopping）規則，或在開發階段使用較小模型作為煙霧測試。

**風險 5：外殼（harness）差異可能混淆模型能力評估**
論文明確指出「模型 × 外殼」是評測單元，單獨比較模型會忽略外殼影響。**緩解方式**：固定外殼後再比較模型，或在報告中明確標註外殼資訊；避免跨外殼直接比較模型排名。

**風險 6：儲存庫選擇偏差**
若選用的 15 個儲存庫偏向特定領域或難度，會影響錦標賽結果的泛化性。**緩解方式**：採用分層抽樣（依語言、領域、規模），並定期輪換儲存庫集合。

**風險 7：評測結果的可重現性**
LLM 的非確定性與版本更新可能導致相同配置下結果波動。**緩解方式**：固定 temperature、記錄模型版本快照、多次重複實驗取平均，並在報告中提供信賴區間。

### 與其他技術的整合建議

**與 SWE-bench 系列基準互補使用**
SWE-Duel 不應取代 SWE-bench / SWE-bench-Live / SWE-rebench，而應作為「動態層」與之並存：靜態基準用於跨模型絕對能力比較，SWE-Duel 用於縱向追蹤與難度自適應評測。建議在模型發表時同時報告兩類基準的結果。

**與 CI/CD 系統整合**
將 SWE-Duel 的紅方代理包裝為 GitHub App 或 GitLab CI 組件，在每次 PR 提交時自動產生「對抗式測試案例」，作為傳統單元測試的補充。這能在真實開發流程中持續驗證代理的審查能力。

**與程式碼審查工具（如 CodeRabbit、SonarQube）整合**
SWE-Duel 產出的「含缺陷 PR」資料集可作為靜態分析工具的基準測試集，評估其漏洞偵測率；反之，靜態分析工具的輸出也可作為藍方代理的輔助輸入，提升其審查表現。

**與代理框架（如 LangChain、AutoGen、CrewAI）整合**
SWE-Duel 的三會話架構可作為代理框架的標準化測試場，框架開發者可透過 SWE-Duel 排行榜展示其框架在不同模型上的加成效果。建議將 SWE-Duel 的代理介面抽象為標準協議（如 OpenAI function calling 格式），降低整合門檻。

**與版本控制系統深度整合**
紅方代理的「提案 → 實作 → 植入漏洞」流程可對應到 Git 的三個獨立分支（feature、buggy、fixed），藍方代理則在 PR 層級運作。建議將 SWE-Duel 的狀態管理與 Git 物件模型對齊，方便除錯與審計。

**與模型評測平台（如 Hugging Face OpenLLM Leaderboard）整合**
SWE-Duel 的 Elo 評分可作為程式碼代理專屬排行榜的底層評分機制，與現有的通用 LLM 排行榜互補。建議提供標準化的 JSON 輸出格式，方便第三方平台直接消費。

### 給不同背景讀者的閱讀建議

**給初學者**
建議先閱讀第 1 節的「問題動機」與「紅藍回合示意圖」，理解「為什麼靜態基準會失效」以及「對抗式評測的基本直覺」。跳過技術細節，專注於「紅方編題、藍方解題」這個核心比喻。可將 SWE-Duel 想像成一場「AI 之間的程式設計對抗賽」，其中較強的 AI 能設計出讓對手失敗的題目，這個直覺有助於理解後續所有設計選擇。

**給 AI 工程師**
重點閱讀第 1 節的「評測協定」與第 2 節的「相關工作比較」，特別注意三會話架構的設計理由（為何要上下文隔離？為何需要自我修復閘道？）。實作時直接參考論文中提到的開源 arena toolkit，並仔細研究「PR 驗收邏輯」的三項確定性檢查——這是整個系統正確性的基石。建議先以小規模（如 3 個儲存庫、3 個參與者）做端到端驗證，再逐步擴展。

**給研究人員**
重點關注三個層面：(1)「自我修復閘道」如何形式化為任務難度的上界約束，這是理論上的有趣問題；(2)「任務難度隨編寫能力成長」的縱向實驗設計（42.9% vs 4.0% 的差距），可作為未來研究「代理元認知能力」的起點；(3) 與 BugPilot、SwingArena 的比較，思考「完全自擴展 vs 部分自擴展」的權衡。論文的錦標賽規模（1,500 回合）也為統計顯著性提供了良好基礎，可進一步分析 Elo 評分的收斂性與信賴區間。

**給產品經理**
SWE-Duel 的核心商業價值在於「解決基準洩漏問題」——這直接影響 AI 程式設計產品的可信度與長期競爭力。建議從「客戶案例」角度思考：若您的產品依賴第三方 LLM 的程式碼能力，SWE-Duel 可作為「客觀的第三方驗證機制」，幫助您在模型選型時避開「已被飽和的基準」陷阱。此外，「紅方編題、藍方解題」的對抗式設計可作為產品差異化賣點（例如「我們的代理能編寫出讓 GPT-5.5 失敗的任務」），用於市場宣傳與技術品牌建立。實作上，建議先以內部評測形式試運行 3–6 個月，累積資料後再考慮對外發布排行榜。
