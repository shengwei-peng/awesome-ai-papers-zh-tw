## ⚡ TL;DR

靜態程式碼基準會洩漏至訓練資料並遭強代理飽和，無法長期提供有效評測。
本文提出 SWE-Duel 自擴展競技場，紅藍代理以鏡像對抗回合互評，紅方植入漏洞、藍方審查修復。
1,500 回合賽事中，GPT-5.5 修復率達 98.3% 居首，新版模型所編任務難度遠超舊版。

## 摘要翻譯

靜態程式碼基準在發布時即固定不變。隨著時間推移，其任務會洩漏至訓練資料中，而更強的代理最終會將其完全攻克。我們主張基準測試應反過來以自擴展為目標：其任務與判準（oracles）於評測時生成，因此沒有任何內容會提前存在而遭到洩漏，且其難度由參與代理決定，而非在發布時固定。我們介紹 SWE-Duel，這是一個由兩個程式碼代理（coding agents）透過鏡像紅藍對抗回合相互評測的競技場。在每個回合中，紅方代理（Red agent）在三個上下文隔離的工作階段（context-isolated sessions）中處理真實的程式碼儲存庫（repository）。其提出並實作一項新功能並附帶功能測試（feature tests），接著在該功能中植入一個細微漏洞（bug），同時附上密封的漏洞觸發測試（sealed bug-triggering tests）。最終的拉取請求（PR, Pull Request）只有在以下條件成立時才會被接受：（1）通過功能測試與程式碼儲存庫既有的測試，且恰好未通過漏洞測試，且（2）同一代理的全新工作階段（fresh session）能在不知情的狀態下修復該漏洞，藉此排除不可解任務（unsolvable tasks）。接著藍方代理（Blue agent）在未被告知存在漏洞的情況下審查該拉取請求（PR）。藍方代理僅在其修訂版本（revision）通過全部三組測試套件（test suites）時獲勝，之後雙方代理互換角色。我們在五種程式語言的 15 個程式碼儲存庫上，針對 11 個模型-框架參與者（model-harness participants）進行 1,500 回合的錦標賽（tournament）。領先者以不同方式取勝。GPT-5.5 搭配 Codex CLI 排名第一，為最強的解題者，於所審查的缺陷（defects）中達 98.3% 修復率。Claude Opus 4.8 搭配 mini-swe-agent 排名第二，為最強的任務編寫者，紅方勝率（Red win rate）達 27.3%。最後，在同一模型系列中，最新版本所撰寫的任務擊敗固定參考解答器（reference solver）的比例遠高於舊版本（42.9% 對比 4.0%），此結果初步顯示任務難度會隨任務編寫能力（task authoring capability）同步提升。

### 核心貢獻（3～5點）
- 提出「自擴展競技場」（Self-Scaling Arena）概念，主張基準測試的任務與判準應於評測時動態生成，避免內容提前洩漏至訓練資料，且難度由參與代理決定而非發布時固定。
- 設計 SWE-Duel 對抗式評測機制，透過鏡像紅藍對抗回合讓兩個程式碼代理相互評測：紅方代理負責提出任務並植入漏洞，藍方代理負責審查並修復，雙方角色互換。
- 建立嚴格的任務接受條件，須同時通過功能測試、既有測試，且恰好未通過密封的漏洞觸發測試，並透過全新工作階段的盲修測試排除不可解任務，確保任務品質。
- 透過 1,500 回合的錦標賽實驗，驗證不同模型-框架組合的解題能力與任務編寫能力，並初步證實任務難度會隨任務編寫能力同步提升。

### 適合對象
從事大型語言模型（LLMs）評測研究、程式碼代理（coding agents）開發、自動化軟體工程（AI for SE）以及基準測試設計的研究人員與工程師；亦適合關注前沿模型（frontier models）能力對比、對抗式評測協議（adversarial evaluation protocol）設計，以及訓練資料污染（data contamination）問題的學術界與產業界讀者。

## 深度分析

#### 方法論解析

SWE-Duel 提出了一種名為「自擴展競技場」（Self-Scaling Arena）的全新評測範式，其核心設計理念是讓基準測試本身隨著被評測代理的能力而動態演進，而非在發布時即固定難度與內容。

**紅藍對抗回合（Red-Blue Turns）的核心機制**

整個評測協議圍繞「鏡像對抗回合」（Mirrored Adversarial Turns）展開。在每一回合中，紅方代理（Red Agent）與藍方代理（Blue Agent）扮演互補且對立的角色，並在下一回合互換角色。這種設計確保了雙方都同時被評測為「解題者」與「任務編寫者」，從而獲得更全面的能力剖面。

**紅方代理的三階段上下文隔離工作流程**

紅方代理的工作被刻意拆分為三個上下文隔離的工作階段（Context-Isolated Sessions），這是該方法論中最精巧的設計之一：

1. **功能設計階段**：紅方代理在第一個工作階段中提出一個新功能（New Feature），並為其實作相應的功能測試套件（Feature Test Suite）。此階段的輸出是一個完整的功能實作加上對應的測試。

2. **漏洞植入階段**：在第二個工作階段中，紅方代理在已實作的功能中嵌入一個細微的漏洞（Embedded Bug），並同時撰寫密封的漏洞觸發測試（Sealed Bug-Triggering Tests）。這個階段的關鍵在於「密封」二字——這些測試對藍方代理完全不可見，僅用於評測時的驗證。

3. **自修復門檻階段（Self-Repair Gate）**：在第三個全新工作階段中，紅方代理必須能夠在「盲目」狀態下（即不被告知漏洞存在）修復自己植入的漏洞。這一步驟至關重要，因為它排除了不可解任務（Unsolvable Tasks），確保只有紅方代理自己能修復的任務才會進入正式對戰。

**拉取請求（PR）的雙重准入條件**

紅方提交的 PR 必須同時滿足兩個條件才能進入對戰：

- **條件一**：PR 必須通過功能測試與儲存庫既有的回歸測試（Regression Tests），但必須恰好失敗於漏洞觸發測試。這驗證了漏洞確實存在且功能未被破壞。
- **條件二**：如前所述，紅方代理必須能在全新工作階段中修復該漏洞。

**藍方代理的審查機制**

藍方代理在不知漏洞存在的情況下審查 PR，並提交修訂版本（Revision）。藍方獲勝的條件是其修訂版本必須同時通過三個測試套件：功能測試套件（功能保留）、漏洞觸發測試套件（漏洞修復）、既有回歸測試套件（無回歸破壞）。任一測試套件失敗即代表紅方獲勝。

**污染抵抗設計的精妙之處**

圖 2 所展示的污染抵抗機制（Contamination-Resistant Evaluation）是該方法的另一個關鍵創新。由於紅方代理實作了新功能並嵌入了漏洞，藍方代理無法簡單地將儲存庫還原至原始版本來「修復」漏洞——因為這樣做會同時移除已實作的功能。功能保留由功能測試套件確定性驗證，漏洞移除由漏洞觸發測試套件確定性驗證，回歸破壞由既有測試套件確定性驗證。這種三層驗證結構使得藍方代理必須進行真正的程式碼理解與修復，而非投機取巧。

**單一回合涵蓋的軟體工程生命週期**

值得注意的是，單一對戰回合實際上評測了軟體工程的多個面向：需求規格制定（紅方提出功能）、功能實作、測試生成、程式碼審查（藍方審查）、故障定位（藍方找出漏洞）、程式修復（藍方修復）。這種「一魚多吃」的設計使得評測效率極高。

#### 實驗數據解讀

**錦標賽規模與結構**

SWE-Duel 的實驗設計規模相當可觀：11 個模型-框架參與者（Model-Harness Participants）在 15 個程式碼儲存庫（涵蓋五種程式語言）中進行了 1,500 回合的對戰。其中 10 位參與者進行完整的循環賽（Round Robin），Gemini 3.1 Pro 作為遲到加入者（Late Entrant）僅進行 5 場比賽，共產生 50 場匹配。這種設計不僅評測了主流參與者，還展示了系統對新參與者的快速整合能力。

**領先者的雙重評測維度**

實驗結果揭示了一個重要的方法論洞見：最強的「解題者」與最強的「任務編寫者」並非同一人。

- **GPT-5.5 搭配 Codex CLI** 排名第一作為最強解題者，修復了 98.3% 的缺陷。這意味著當它作為藍方代理審查 PR 時，幾乎總能成功識別並修復紅方植入的漏洞。
- **Claude Opus 4.8 搭配 mini-swe-agent** 排名第二作為最強任務編寫者，紅方勝率達 27.3%。這意味著當它作為紅方代理設計任務時，其植入的漏洞有超過四分之一的機率能成功騙過對手。

這種「解題能力」與「出題能力」的分離，暗示了程式碼代理可能存在不同的能力維度，而非單一的綜合能力指標。

**同模型家族內的版本演進證據**

最具說服力的證據來自同模型家族內的比較：同一家族中最新版本編寫的任務擊敗固定參考解答器（Reference Solver）的比例為 42.9%，而舊版本僅為 4.0%。這超過十倍的差距提供了「任務難度隨任務編寫能力而擴展」的初步實證證據。這正是「自擴展」特性的核心驗證——當編寫者變強時，其編寫的任務也自動變得更難。

**遲到加入者的評測效率**

Gemini 3.1 Pro 作為遲到加入者僅需 5 場比賽即可被排名，這顯示了 SWE-Duel 的評測效率。相較於傳統基準需要完整評測所有任務，自擴展競技場可以快速整合新參與者，這對於快速演進的模型市場尤為重要。

**行為剖面的多樣性**

實驗揭示了不同模型與框架組合呈現出截然不同的行為剖面（Behavioral Profiles）。這暗示了模型能力與框架設計之間存在複雜的交互作用，單純比較模型分數可能會忽略框架帶來的差異。

#### 與現有研究的比較

**與靜態基準的比較：SWE-bench Verified**

SWE-bench Verified（Jimenez et al., 2024）是目前最知名的程式碼基準之一，但 OpenAI 已停止回報其在該基準上的結果，因為前沿模型（Frontier Models）能夠重現其黃金補丁（Gold Patches）。SWE-Duel 從根本上解決了這個問題：因為任務在評測時才生成，不存在可供重現的「黃金補丁」。

**與持續更新基準的比較：SWE-bench-Live 與 SWE-rebench**

SWE-bench-Live（Zhang et al., 2025）與 SWE-rebench（Badertdinov et al., 2025）透過持續收集 GitHub 上的新任務來維持時間上的新鮮度。然而，這些基準的任務難度仍然受限於人類開發者日常面對的問題。SWE-Duel 的突破在於：任務難度不再由人類問題的分佈決定，而是由參與代理的編寫能力決定，因此可以無限擴展。

**與任務擾動方法的比較**

Guan 等人（2026a）與 DyCodeEval（Chen et al., 2025）提出擾動任務以避免精確記憶化，但保留了原始任務與解答。SWE-Duel 更進一步：連原始任務都不存在，因為任務本身就是在評測時由代理生成的。

**與 BugPilot 的比較**

BugPilot（Sonwane et al., 2025）收集代理在實作新功能時無意引入的漏洞，但這些任務是預先生成的固定集合。SWE-Duel 則刻意讓代理植入漏洞，並透過自修復門檻確保任務的可解性，這是一個更可控的設計。

**與 SwingArena 的比較**

SwingArena（Xu et al., 2026）將大型語言模型配對為補丁提交者（Patch Submitters）與測試撰寫審查者（Test-Writing Reviewers），是最接近 SWE-Duel 的對抗式競技場。然而，SwingArena 仍然從固定的 GitHub 議題池中抽取任務，僅在評測時生成判準（Oracles）。SWE-Duel 則連任務本身都在評測時生成，這是根本性的差異。

**SWE-Duel 的局限性**

儘管 SWE-Duel 解決了許多現有基準的問題，但仍存在以下局限：

1. **任務分佈的偏斜**：由於任務由代理生成，其分佈可能與真實軟體工程任務的分佈有所不同。代理傾向於生成它們能夠解決的任務，這可能導致任務偏離人類開發者實際面對的問題類型。

2. **自修復門檻的偏誤**：自修復門檻要求紅方代理能修復自己植入的漏洞，但這並不保證任務對所有代理都可解。某些漏洞可能對特定代理特別困難。

3. **評測成本**：1,500 回合的錦標賽需要大量的 API 呼叫與計算資源，這對於資源有限的研究者來說可能是個障礙。

4. **語言覆蓋**：雖然涵蓋五種程式語言，但相較於真實世界的程式語言多樣性仍有差距。

5. **儲存庫選擇偏誤**：15 個儲存庫可能無法代表所有類型的軟體專案。

#### 可重現性評估

SWE-Duel 在可重現性方面表現出色，這從論文中明確引用的三個資源即可看出：

1. **開放競技場工具包（Minn, 2026c）**：作者提供了完整的開源工具包，使社群能夠從零開始建立自己的錦標賽。這降低了進入門檻，並促進了研究的可重現性。

2. **現有排行榜（Minn, 2026b）**：社群可以將新代理加入現有排行榜，這意味著評測結果可以持續累積與比較。

3. **錦標賽資料（Minn, 2026a）**：1,500 回合的完整錦標賽資料可供分析，這對於深入研究代理行為非常有價值。

**模型權重與訓練資料的可用性**

論文中使用的模型包括 GPT-5.5、Claude Opus 4.8、DeepSeek V4 Pro、Gemini 3.1 Pro 等，其中部分為專有模型（如 GPT-5.5、Claude Opus 4.8），部分為開放權重模型（如 DeepSeek V4 Pro）。對於專有模型，雖然無法獲得權重，但可以透過 API 進行評測，這在實務上是可行的替代方案。

**框架的可重現性**

論文中使用了三種代理框架（harness），包括 Codex CLI 與 mini-swe-agent 等。這些框架的程式碼通常是開源的，這進一步增強了可重現性。

**儲存庫的選擇**

15 個儲存庫涵蓋五種程式語言，這些儲存庫的選擇標準與其代表性需要在論文中更詳細地說明，以確保其他研究者能夠選擇類似的儲存庫進行比較。

#### 未來研究方向

**1. 擴展參與者規模與多樣性**

目前的錦標賽僅有 11 位參與者，未來可以擴展到數十甚至數百位參與者。更大的參與者池將產生更穩定的排名，並揭示更多樣化的行為剖面。此外，可以考慮引入專門設計的「對抗型代理」，這些代理經過優化以編寫極難被發現的漏洞，從而推動解題能力的上限。

**2. 跨領域任務生成**

目前 SWE-Duel 專注於程式碼任務，但「自擴展競技場」的概念可以應用於其他領域，例如數學證明、科學實驗設計、創意寫作等。這將考驗該範式的通用性。

**3. 多代理協作評測**

SWE-Duel 目前是雙代理對抗，未來可以擴展為多代理協作場景。例如，三個代理共同開發一個功能，其中一個代理嘗試植入漏洞，另外兩個代理嘗試識別並修復。這將更貼近真實的軟體開發團隊動態。

**4. 任務難度的細粒度校準**

雖然實驗顯示任務難度隨編寫能力擴展，但目前缺乏對難度的細粒度控制。未來可以研究如何讓代理生成特定難度等級的任務，例如「僅有 10% 機率被解出的任務」，這對於訓練與評測都很有價值。

**5. 自修復門檻的改進**

目前的自修復門檻僅要求紅方代理能修復自己植入的漏洞，但這可能過於寬鬆或過於嚴格。未來可以研究更精細的可解性驗證機制，例如要求多個不同的代理都能修復該漏洞。

**6. 漏洞類型的多樣化**

目前的漏洞是「細微的」，但未來可以研究不同類型的漏洞，例如安全性漏洞、性能瓶頸、可維護性問題等。這將使評測更全面。

**7. 與人類開發者的比較**

雖然 SWE-Duel 評測的是代理之間的相對能力，但未來可以引入人類開發者作為基準，驗證代理生成的任務是否與人類面對的真實任務具有相似的難度分佈。

**8. 長期演化研究**

SWE-Duel 的自擴展特性使其成為研究模型能力長期演化的理想工具。未來可以追蹤同一模型家族在數代之間的表現變化，這將為模型能力的演化提供獨特的視角。

**9. 經濟可行性與成本效益分析**

1,500 回合的錦標賽需要大量資源，未來需要研究如何在保持評測品質的前提下降低成本，例如透過抽樣策略或更高效的對戰設計。

**10. 與強化學習的結合**

SWE-Duel 的對抗性質使其成為強化學習的理想環境。代理可以透過與其他代理對戰來改進自己的編寫與解題能力，這將開啟「代理自我訓練」的新範式。

總結而言，SWE-Duel 提出了程式碼代理評測的一個根本性轉變：從「靜態基準」轉向「自擴展競技場」。這個轉變不僅解決了訓練資料洩漏的問題，更重要的是讓基準能夠隨著代理能力的提升而自動提升難度。這種設計哲學可能會影響未來所有 AI 代理評測的發展方向。

## 論文問答

**Q1：靜態程式碼基準測試為何會隨時間失效？SWE-Duel 試圖解決的核心問題是什麼？**
A：靜態程式碼基準（如 SWE-bench Verified）在發布後即固定不變，其任務與參考解答會隨著時間逐漸滲入大型語言模型的訓練語料中，導致模型能直接「記憶」而非「推理」出答案；同時，更強的代理最終會將固定任務集完全攻克，使基準失去鑑別力。SWE-Duel 試圖解決的核心問題正是這個「洩漏與飽和」的雙重困境——它主張基準應該是「自擴展」的，任務與判準都在評測時即時生成，使內容根本沒有機會事先洩漏，且難度由參賽代理自身的編寫能力決定，而非在發布時凍結。

**Q2：現有的持續更新基準（如 SWE-bench-Live、SWE-rebench）為何仍不足以解決問題？**
A：SWE-bench-Live 與 SWE-rebench 透過持續從 GitHub 收集訓練截止後的新任務來延緩洩漏問題，但其任務難度仍受限於人類開發者日常遭遇的議題分布，屬於「較新但未必更難」的更新。換言之，這類基準的難度天花板由人類開發活動決定，無法隨著代理能力提升而自動提高；SWE-Duel 則透過讓代理本身擔任任務編寫者，使難度能隨參賽者的編寫能力同步上升，突破了人類議題分布的難度上限。

**Q3：為什麼「自擴展」特性對程式碼代理的長期評測至關重要？**
A：隨著大型語言模型每隔數月就推出能力更強的新一代，固定難度的基準很快就會被「打滿分」，失去區分領先模型與追趕模型的能力；而自擴展基準能讓難度隨代理能力同步攀升，使評測結果在多年後仍具備鑑別度。此外，由於任務在評測時才生成，模型無法事先針對特定題目進行微調或記憶，這讓基準能持續提供可信賴的進步訊號，避免業界陷入「在基準上分數提高但實際能力未提升」的虛假進步陷阱。

**Q4：SWE-Duel 的紅藍對抗回合（Red-Blue Turns）具體是如何運作的？**
A：在每一回合中，紅方代理在真實儲存庫上跨三個上下文隔離的工作階段運作，依序提出新功能、實作該功能並撰寫功能測試，最後植入細微漏洞並附上密封的漏洞觸發測試；其提交的拉取請求必須通過功能測試與既有回歸測試、同時恰好在漏洞測試上失敗，且紅方代理必須在全新工作階段中能盲修自己的漏洞，以排除不可解任務。接著藍方代理在不獲知漏洞存在的情況下審查該拉取請求，只有當其修訂版本同時通過功能測試、回歸測試與漏洞測試三套測試時才算獲勝，雙方在下一回合交換角色，形成鏡像對抗結構。

**Q5：SWE-Duel 防止「直接還原」作弊的設計機制是什麼？**
A：由於紅方代理植入的漏洞與新功能共存於同一個拉取請求中，藍方代理若想透過單純還原儲存庫到原始版本來移除漏洞，會連帶把新功能一起刪除，導致無法通過功能測試。這種設計迫使藍方必須真正進行除錯與程式修復，而非走捷徑；功能測試套件決定性地驗證功能保留、漏洞測試套件決定性地驗證漏洞修復、回歸測試套件驗證沒有破壞既有行為，三者缺一不可，使「作弊式解法」在結構上被排除。

**Q6：「自我修復閘門」（self-repair gate）在 SWE-Duel 中扮演什麼關鍵角色？**
A：自我修復閘門要求紅方代理在全新的工作階段中、且不被告知漏洞位置的情況下，能修復自己植入的漏洞，這個機制確保只有「可解的」任務才會進入正式對戰。這個設計巧妙地劃定了任務難度的上限——若紅方代理自己都無法修復，那麼藍方代理也幾乎不可能修好，因此這類任務會被自動剔除，避免浪費評測資源並防止「無解任務」污染排行榜；同時它也鼓勵紅方代理植入「自己修得了但別人修起來更困難」的細微漏洞，使整個競技場的任務品質保持在合理區間。

**Q7：SWE-Duel 的錦標賽規模與參賽者組成為何？**
A：研究團隊舉辦了一場涵蓋 11 個「模型-框架」參與者的錦標賽，在 15 個跨五種程式語言的真實儲存庫上進行，總共產生 50 場對戰與 1,500 個回合；其中 10 位參與者進行完整的循環賽，Gemini 3.1 Pro 作為遲到加入的參賽者僅出賽 5 場即可被排名。這種大規模且異質的設計使結果能區分出不同模型與框架組合的行為特徵，而非僅僅反映單一模型的原始能力。

**Q8：錦標賽中最具代表性的結果是什麼？不同領導者各自展現了什麼樣的強項？**
A：GPT-5.5 搭配 Codex CLI 排名第一，展現了最強的解題能力，能修復其審查的 98.3% 缺陷；Claude Opus 4.8 搭配 mini-swe-agent 排名第二，則展現了最強的任務編寫能力，紅方勝率高達 27.3%。這顯示「解題強」與「編寫強」是兩種不同的能力剖面——前者考驗除錯與修復的技術深度，後者考驗設計微妙漏洞與對手難以察覺的創造力，兩者並非完全正相關，這對未來挑選代理組合具有重要啟示。

**Q9：SWE-Duel 如何初步證明「任務難度會隨編寫能力提升」？**
A：研究團隊在單一模型家族內進行了對比實驗，發現由該家族最新版本所編寫的任務擊敗固定參考解答器的比例為 42.9%，遠高於由較舊版本所編寫任務的 4.0%。這個懸殊的差距提供了初步證據，說明當編寫代理的能力提升時，其產出的任務對其他代理而言確實更具挑戰性，驗證了「自擴展」假說在實務上是可行的——這也是 SWE-Duel 與傳統靜態基準最關鍵的差異所在。

**Q10：SWE-Duel 在實際軟體工程生命週期中涵蓋了哪些能力面向？**
A：單一場 SWE-Duel 對戰即涵蓋了需求規格制定（紅方提出新功能）、功能實作（紅方撰寫程式碼）、測試生成（紅方撰寫功能與漏洞測試）、程式碼審查（藍方檢視拉取請求）、故障定位（藍方找出隱藏漏洞）與程式修復（藍方提交修訂版本）等六大軟體工程核心活動。這種全方位評測特性使 SWE-Duel 比僅測試單一面向（如純解題或純測試生成）的基準更貼近真實開發情境，也更能反映代理在端到端工作流程中的實用價值。

**Q11：SWE-Duel 對企業挑選程式碼代理有何實務啟示？**
A：企業不應僅憑單一基準分數挑選代理，而應根據自身需求權衡「解題能力」與「任務編寫能力」——若團隊需要的是可靠的除錯與修復助手，則應參考 GPT-5.5 這類高解題率的組合；若團隊需要的是能設計測試案例、找出程式碼細節缺陷的審查者，則 Claude Opus 4.8 這類高紅方勝率的組合可能更合適。此外，由於 SWE-Duel 涵蓋五種程式語言與多種框架，企業可依據自身技術棧選擇對應表現優異的代理組合。

**Q12：SWE-Duel 對程式碼代理研究領域的長期影響為何？**
A：SWE-Duel 的開源競技場工具包讓社群能從零開始舉辦自己的錦標賽或將新代理加入既有排行榜，這種開放性有望催生持續運作的「活基準」生態系；更重要的是，「自擴展」概念可能擴散到程式碼以外的其他代理評測領域（如數學、寫作、規劃），形成新一代評測範式。長期來看，這種設計能讓學術界與工業界不再陷入「發布新基準 → 一年內被攻克 → 再發布更難基準」的循環，而是建立一個能與模型共同演化的評測基礎設施。

**Q13：SWE-Duel 目前存在哪些已知的限制？**
A：首先，自我修復閘門雖然排除了不可解任務，但紅方代理仍可能在「自己修得了但對手也修得了」的區間植入漏洞，導致部分任務過於容易而無法有效區分參賽者；其次，紅藍雙方都使用同一組代理時，可能存在「風格偏誤」——熟悉自身編寫風格的代理在審查時可能佔有結構性優勢；最後，雖然涵蓋五種語言與 15 個儲存庫，但對於超大型企業級 monorepo 或高度領域特定的程式碼庫（如嵌入式系統、遊戲引擎），SWE-Duel 的代表性仍待驗證。

**Q14：SWE-Duel 可能出現哪些失敗案例或邊界情況？**
A：一個潛在的失敗模式是紅方代理植入「過於細微」的漏洞，導致藍方代理即使未真正理解程式碼也能透過隨機修改碰巧修復，反而獎勵了非真正的除錯能力；另一個邊界情況是當紅方代理無法在全新工作階段中修復自己植入的漏洞時，整個任務會被丟棄，這可能造成評測資源浪費，特別是當參賽代理的自我修復能力較弱時。此外，若藍方代理選擇「拒絕審查」或提交空修訂版本，雖然會輸掉該回合，但這種保守策略可能在某些情境下反而是理性的，這也凸顯了 SWE-Duel 目前缺乏對「放棄」行為的更細緻評分機制。

**Q15：SWE-Duel 未來可以朝哪些方向延伸？**
A：短期可考慮引入「不對稱資訊」變體，例如讓藍方代理能選擇查看部分歷史提交或要求紅方提供更多上下文，以模擬真實企業中常見的部分資訊審查情境；中期可將評測範圍從「單一拉取請求」擴展到「多代理協作開發」，讓多個代理共同完成一個大型功能並互相審查；長期則可探索跨領域的自擴展競技場，例如結合程式碼、數學證明與自然語言規格的綜合任務，使評測能更全面地衡量通用人工智慧的工程能力，並真正實現「基準與模型共同演化」的願景。

### 適用場景

**1. 企業內部程式碼代理的持續評測**
大型軟體組織可在內部部署 SWE-Duel 風格的競技場，用於評估自家研發或採購的程式碼代理。相較於 SWE-bench 等靜態基準，自擴展特性意味著評測題目永遠不會「過時」或被代理背誦，特別適合用於季度性的代理能力盤點與採購決策。

**2. AI 程式碼助手供應商的差異化定位**
程式碼助手廠商可利用 SWE-Duel 區分自家產品的「解題強項」與「任務編寫強項」。論文中 GPT-5.5 與 Claude Opus 4.8 分別在兩個維度領先，顯示此架構能揭露單一排行榜無法呈現的能力剖面，對產品定位與行銷敘事極具價值。

**3. CI/CD 流程中的回歸防護層**
將 SWE-Duel 的紅方機制整合進 CI/CD，可在每次合併請求（PR）時自動生成「對抗性測試」並驗證代理是否能修復。這對於開源專案維護者特別有用，可在合併前自動產生比人類審查者更刁鑽的測試案例。

**4. 程式碼修復模型的合成訓練資料生成**
訓練資料枯竭是程式碼模型的主要瓶頸。SWE-Duel 在評測時動態產生「漏洞—觸發測試—修復」三元組，可作為高品質合成資料來源，用於微調專門的 fault localization 或 program repair 模型。

**5. 學術研究中的代理能力縱向追蹤**
研究機構可長期運行 SWE-Duel 錦標賽，追蹤同一模型家族（如 Claude Opus 4.5 → 4.6 → 4.8）在「編寫任務難度」上的演進。論文已展示新版本編寫的任務擊敗固定參考解答器的比例（42.9% vs 4.0%），這對研究模型世代間的能力躍遷極具參考價值。

### 實作前置條件

**資料需求**
- 至少 10–20 個乾淨、可建置、可測試的開源儲存庫，覆蓋 3 種以上程式語言（論文使用 15 個儲存庫、5 種語言）。每個儲存庫需具備完整的測試套件與可重現的建置流程（Docker 化環境最理想）。
- 每個儲存庫的 baseline 狀態（HEAD commit、依賴鎖定檔、建置指令）必須可重現，否則「回歸測試」會產生偽陽性。
- 預先定義的「特徵邊界」：儲存庫需有清楚的模組化結構，避免紅方代理植入的漏洞跨越多個檔案而難以定位。

**運算資源**
- 每場對戰需 6 個獨立的工作階段（紅方 3 個、藍方 1 個、自我修復 1 個、評測 1 個），且彼此上下文隔離。建議每場對戰預留 8–16 vCPU、32 GB RAM 的容器環境。
- 1,500 回合的完整錦標賽若以 GPT-5.5 等前沿模型執行，單回合 API 成本約 5–20 美元，整體預算需 7,500–30,000 美元（不含儲存庫建置時間）。
- 需具備任務排程與隔離機制（Kubernetes、Docker Compose 或雲端 batch job），避免不同回合互相干擾。

**技能門檻**
- 熟悉至少一種代理框架（mini-swe-agent、Codex CLI、Aider 或自製 harness），並能將其包裝為可程式化呼叫的介面。
- 具備靜態分析與測試自動化經驗，能撰寫「PR 准入閘」邏輯（驗證功能測試通過、回歸測試通過、漏洞測試失敗）。
- 了解 LLM 評測的統計方法（ELO、Glicko、布蘭德計分），因為 SWE-Duel 的排名需透過多場對戰累積。

### 實作步驟建議

**步驟一：建立儲存庫語料庫**
挑選 15 個左右活躍但穩定的開源專案，優先選擇測試覆蓋率 > 60%、單一語言佔比 > 80% 的儲存庫。為每個儲存庫產製 Docker 映像，記錄建置時間、測試執行時間、依賴大小等中繼資料，作為後續難度分層依據。

**步驟二：實作紅方代理管線**
將紅方流程拆分為三個上下文隔離的工作階段：(a) 提案與實作新功能並產生功能測試；(b) 在新功能中植入細微漏洞並產生漏洞觸發測試；(c) 在全新工作階段中自我修復漏洞。每個階段需有獨立的 prompt 模板與輸出解析器，並強制使用不同的 system prompt 以避免上下文洩漏。

**步驟三：建立 PR 准入閘**
實作確定性的驗證邏輯：(1) 執行功能測試套件，全部通過；(2) 執行儲存庫既有測試套件，全部通過；(3) 執行漏洞觸發測試套件，全部失敗；(4) 啟動紅方的全新工作階段，要求其修復漏洞，若無法修復則拒絕此 PR。這個閘是 SWE-Duel 防止「不可解任務」混入錦標賽的核心。

**步驟四：實作藍方代理管線**
藍方僅接收 PR 描述與程式碼差異，無法看到漏洞測試套件。藍方提交修訂版本後，執行三套測試：功能測試（驗證未刪除新功能）、回歸測試（驗證未破壞既有功能）、漏洞測試（驗證漏洞已修復）。三者皆通過才算藍方獲勝。

**步驟五：建構錦標賽排程與計分系統**
採用循環賽制，每對 (模型, 框架) 組合互相對戰。計分可採用 ELO 或布蘭德計分，並分別追蹤「紅方勝率」（任務編寫能力）與「藍方修復率」（解題能力）。論文中 GPT-5.5 的 98.3% 修復率與 Claude Opus 4.8 的 27.3% 紅方勝率顯示兩個維度應獨立排名。

**步驟六：部署開源工具包並建立排行榜**
論文已釋出 arena toolkit（Minn, 2026c），建議直接基於其擴充。對外提供 CLI 介面讓社群提交新代理，並以 GitHub Actions 自動驗證提交者的代理是否符合協議（不會偷看漏洞測試）。

### 潛在風險與注意事項

**風險一：紅方代理產生「假漏洞」**
紅方可能植入過於明顯的漏洞（例如語法錯誤、變數未定義），導致藍方只需一輪 grep 即可修復，無法真正區分能力差異。**緩解方式**：在漏洞測試中加入「漏洞隱蔽性」指標，例如要求漏洞必須通過 lint、型別檢查，且至少跨越 2 個檔案。

**風險二：藍方代理透過「刪除功能」規避漏洞**
若藍方直接還原儲存庫到原始狀態，漏洞自然消失但功能也消失。論文的設計已透過功能測試套件防堵此問題，但實作時需確保功能測試足夠嚴格，能捕捉到「刪除整個功能模組」這類粗糙行為。

**風險三：自我修復閘產生偏差**
紅方在「全新工作階段」中修復自己的漏洞，這個閘會偏向「紅方能解的題目」。若紅方能力較弱，可能會拒絕所有難度合理的任務，導致錦標賽題目過於簡單。**緩解方式**：允許紅方在自我修復階段使用「提示增強」（例如明確告知「這是你剛才植入的漏洞」），僅作為閘的最低標準。

**風險四：上下文隔離洩漏導致評測失效**
若三個紅方工作階段共用底層快取、容器檔案系統或 API 金鑰日誌，可能造成跨階段資訊洩漏。**緩解方式**：使用獨立的容器、獨立的 API key、獨立的隨機種子，並在每次工作階段結束後銷毀所有中介產物。

**風險五：API 成本失控**
1,500 回合的錦標賽若全部使用前沿模型，成本可能超過 3 萬美元。**緩解方式**：採用兩階段篩選——先用開源模型（如 DeepSeek V4 Pro）進行大規模預賽，再以專有模型進行決賽；或限制每個儲存庫的回合數。

**風險六：評測結果難以跨研究比較**
不同實驗室的儲存庫選擇、提示詞、框架版本都會影響結果。**緩解方式**：固定基準儲存庫清單與框架版本，僅允許替換模型權重；並釋出完整的回合日誌供他人重現。

### 與其他技術的整合建議

**與 SWE-bench / SWE-bench-Live 互補**
SWE-Duel 不應取代 SWE-bench，而應作為其「動態補充」。建議在 CI 流程中同時執行兩者：SWE-bench 提供可比較的歷史基準點，SWE-Duel 提供對抗前沿模型的即時訊號。

**與靜態分析工具整合**
紅方植入漏洞後，可先用 SonarQube、CodeQL 等工具掃描，過濾掉會被靜態分析直接抓出的「低品質漏洞」，迫使紅方設計更細微的缺陷。這能提升整體錦標賽的難度下限。

**與 RLHF / 偏好學習整合**
藍方的修訂版本與紅方的原始 PR 構成天然的「偏好對」，可用於訓練 reward model。建議將 SWE-Duel 的回合日誌轉換為 DPO 或 RLHF 訓練資料，特別是「藍方成功修復」vs「藍方失敗」的對比樣本。

**與程式碼搜尋引擎整合**
紅方在設計漏洞時，可呼叫程式碼搜尋引擎（如 Sourcegraph）確認漏洞模式在訓練語料中不常見，避免代理透過記憶修復。這能進一步提升評測的污染抵抗力。

**與企業內部知識庫整合**
在企業場景中，可將內部程式碼風格指南、API 設計規範注入紅方與藍方的 system prompt，使評測更貼近真實工作場景。例如紅方需遵循內部命名規約植入漏洞，藍方需在修復時同時遵守規範。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節的「紅藍回合」比喻，理解「對抗式評測」的核心概念即可，無需深究技術細節。重點是體會「基準測試會過時」這個直覺——就像考試題目被洩露後就失去鑑別度一樣，SWE-Duel 透過「考試當場出題」來解決這個問題。

**給 AI 工程師**：重點閱讀第 1 節的紅方管線設計（特別是三個上下文隔離工作階段的拆分）與第 2 節對 BugPilot、SwingArena 的比較。實作時可先從 mini-swe-agent 開始，這是論文中表現最佳的開源框架之一。建議在自己的小型儲存庫（5–10 個）上先跑 50 回合驗證管線，再擴展到完整錦標賽。

**給研究者**：第 2 節的相關工作分類（靜態基準、持續更新基準、模型生成基準）提供了完整的基準測試演化地圖。特別值得關注的是「任務難度隨編寫能力提升」這個假設——論文以 42.9% vs 4.0% 的數據初步驗證，但這是否會飽和？是否存在理論上限？這些都是值得追問的開放問題。

**給產品經理**：核心訊息是「單一排行榜無法呈現代理全貌」。GPT-5.5 是最強解題者但未必是最強任務編寫者，這對採購決策意味著：若團隊需要「能解決困難 bug 的助手」，應選 GPT-5.5；若需要「能產生高品質測試案例的工具」，Claude Opus 4.8 可能更適合。建議將 SWE-Duel 的雙維度排名納入採購評估表，而非僅看單一準確率。
