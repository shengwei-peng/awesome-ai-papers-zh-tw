## ⚡ TL;DR

研究想法規格常因方法細節不足，導致實作時出現無依據假設與錯誤實作。
本文提出 IdeaAMBIG 基準，評估規格可編碼性、缺陷定位與澄清行動生成。
實驗顯示缺陷定位是主要瓶頸，提供正確解決方案可大幅提升可編碼率。

## 摘要翻譯

研究想法可能新穎、連貫且科學上合理，但其提出的方法仍可能規格不足，難以忠實實作（Faithful Implementation）。我們研究面向實作的（Implementation-Facing）研究方法規格（Method Specifications）之可編碼性（Codification Readiness），定義為規格是否提供足夠的方法性資訊，使稱職實作者（Competent Implementer）或編碼代理（Coding Agent）能在沒有無依據假設（Unsupported Assumptions）的情況下建構出預期的方法。我們從論文、程式碼庫、GitHub Issues 討論串與可複現性產物中，建構有證據基礎的規格（Evidence-Grounded Specifications）及其有依據的解決方案（Supported Resolutions）。我們提出 IdeaAMBIG，一個包含 660 筆有證據基礎實例的基準測試：163 筆來自可複現性報告（Reproducibility Reports）與 GitHub Issues 的真實世界缺口，以及 497 筆注入可編碼參考規格（Codification-Ready References）中的受控合成缺口（Controlled Synthetic Gaps）。IdeaAMBIG 評估三項能力：可編碼性評估（Codification-Readiness Assessment）、缺陷定位（Defect Localization），以及澄清行動生成（Clarification Action Generation）。缺陷定位僅接收規格，而澄清行動生成則額外接收已標註的缺陷。在 13 個大型語言模型（LLMs）上的評估顯示，最佳模型在真實世界實例上達到 9.6% 的宏觀缺陷恢復率（Macro Defect Recovery Rate），但若給定缺陷，宏觀澄清行動成功率（Macro Clarification Action Success Rate）則達到 80.6%。在一項神諭研究（Oracle Study）中，提供黃金標準解決方案（Gold Resolution）可將下游可編碼率（Downstream Codification-Ready Rate）從 14% 提升至 98%。在所有受評估模型中，缺陷定位是主要瓶頸；一旦提供缺陷，澄清行動的表現則明顯較佳。

### 核心貢獻（3～5點）
- 提出可編碼性（Codification Readiness）概念，用於衡量研究方法規格是否足以讓稱職實作者或編碼代理在無無依據假設下忠實實作。
- 建構 IdeaAMBIG 基準測試，包含 660 筆有證據基礎的實例，結合 163 筆真實世界缺口與 497 筆受控合成缺口。
- 設計三項評估能力：可編碼性評估、缺陷定位與澄清行動生成，並揭示缺陷定位是當前大型語言模型的主要瓶頸。
- 透過神諭研究證明，提供黃金標準解決方案可將下游可編碼率從 14% 大幅提升至 98%，凸顯缺口識別與解決的關鍵性。

### 適合對象
本論文適合對自動化科學研究、AI 研究代理（Research Agents）、研究方法規格化、軟體可複現性，以及大型語言模型在協助研究想法轉化為可執行程式碼之能力與限制感興趣的研究人員與實作者。特別推薦給關注如何提升研究想法實作品質、降低可複現性失敗（Reproducibility Failures）風險的讀者。

## 深度分析

#### 方法論解析

本研究的核心在於形式化「可編碼性（codification readiness）」這一概念：一個面向實作的研究方法規格（method specification）必須讓稱職實作者（competent implementer）或編碼代理（coding agent）能夠在沒有無依據假設（unsupported assumptions）的情況下，建構出忠實實作（faithful implementation）。若兩位稱職實作者可能因規格遺漏而做出實質不同的方法定義選擇（method-defining choices），則該規格屬於未就緒（NOT_READY）。這個定義把焦點從「想法是否新穎或可行」轉移到「方法是否已被充分規格化」，補上了研究代理（research agents）從構想到執行之間的關鍵缺口。

為了評估這個能力，作者建構了 IdeaAMBIG（IdeaAMBIG）基準測試，包含 660 個有證據基礎的規格（evidence-grounded specifications）實例，分為兩大來源：

1. **真實世界缺口（real-world gaps）**：共 163 筆，來自 GitHub Issues（GitHub Issues）與可複現性報告（reproducibility reports）。這些是實作者真正遭遇、且有已驗證解決方案的規格缺口。
2. **受控合成缺口（controlled synthetic gaps）**：共 497 筆，從可編碼參考規格（codification-ready references）中精確注入單一實作關鍵缺口而產生，提供明確的反事實目標。

每個實例都包含目標缺陷（target defect）、有依據的解決方案（supported resolution），以及第一層（Level-1）3 類、第二層（Level-2）10 類的標籤。真實缺口的建構流程包括：從公開程式庫與再現報告中收集已解決的議題、過濾與分類、抽取可編碼參考規格、再由大型語言模型（LLMs）協助提取缺口與解決方案。合成缺口的建構則更為嚴謹：只選用來自已被獨立驗證成功再現的論文與程式碼，從中抽取可編碼參考規格，再自動生成並注入單一候選缺陷，確保每個合成實例都只有一個實作關鍵缺口。

IdeaAMBIG 設計了三項循序漸進的評估任務：

- **可編碼性評估（codification-readiness assessment）**：僅輸入規格 x，判斷其是否 READY 或 NOT_READY。
- **缺陷定位（defect localization）**：輸入欠規格的 x，但不給任何缺陷提示，要求模型找出規格缺口的位置與類型。
- **澄清行動生成（clarification action generation）**：輸入 x 加上已標註的缺陷（annotated defect），要求模型產生能夠釐清該缺口的問題或行動。

這三項任務的設計重點在於把「發現阻塞點」與「知道阻塞點後如何處理」分開評估，從而精確定位模型能力的瓶頸。

#### 實驗數據解讀

作者在 13 個 LLMs 上進行評估，結果呈現出非常鮮明的對比：

- 在真實世界實例上，最佳模型的**宏觀缺陷恢復率（Macro Defect Recovery Rate）**僅有 **9.6%**。
- 但在已給定標註缺陷的條件下，最佳模型的**宏觀澄清行動成功率（Macro Clarification Action Success Rate）**高達 **80.6%**。
- 在**神諭研究（oracle study）**中，若直接提供黃金標準解決方案（gold resolution），下游可編碼率（downstream codification-ready rate）從 **14%** 大幅提升至 **98%**。

這組數據傳達了幾個重要訊息。首先，**缺陷定位（defect localization）是當前 LLMs 的主要瓶頸**：模型很難僅從規格文字中主動發現「哪裡遺漏了會改變方法行為的關鍵資訊」。其次，一旦缺陷被指出，模型生成有用澄清問題的能力相對成熟，這表示「提問」本身比「發現該問什麼」容易得多。最後，神諭研究顯示，只要能正確補齊缺失資訊，規格幾乎可以確保轉換為可編碼狀態，這強調了「在編碼前先釐清規格缺口」的巨大下游價值。

值得注意的是，真實世界實例的難度遠高於受控合成缺口。真實缺口往往夾雜大量背景脈絡、隱含假設與不相關的實作細節，而合成缺口則是單一、乾淨、有明確反事實目標的擾動。這也解釋了為何模型在真實數據上的缺陷恢復率如此低。此外，宏觀指標（macro metrics）對類別不平衡較為穩健，因此 9.6% 並非極端嚴苛的計算方式所致，而是真實反映了模型在跨類別平均表現上的不足。

從應用角度來看，這些結果暗示：現階段若要將 LLM 整合進自動化研究流程，較務實的設計是讓模型在編碼前主動標示「不確定之處」，再由人類或其他驗證機制協助定位缺陷，而非完全放手讓模型自行填補無依據假設。

#### 與現有研究的比較

IdeaAMBIG 在研究自動化（automated research）的評估光譜中佔據了一個獨特位置。現有研究大致可分為兩端：

- **上游想法品質評估（upstream idea quality）**：例如評估新穎性（novelty）、可行性（feasibility）、多樣性（diversity）等，這類工作關注「想法本身好不好」。
- **下游計畫與產物驗證（downstream plans and artifacts）**：例如實驗設計、科學程式碼生成、論文與程式碼一致性檢查等，這類工作假設方法已經被充分規格化。

IdeaAMBIG 則專注於兩者之間的「規格缺口」，評估方法規格是否足以支撐忠實實作。這與 SciConvBench 等對話式規格釐清基準不同：SciConvBench 強調多輪對話中逐步釐清需求，而 IdeaAMBIG 則把問題拆解為「能否判斷規格就緒」、「能否獨立定位缺陷」、「能否在已知缺陷下產生澄清行動」三個單項能力，更適合診斷模型在規格化階段的具體弱點。

與 LimitGen 等人為擾動的局限性基準相比，IdeaAMBIG 的受控合成缺口（controlled synthetic gaps）同樣採用精確擾動，但聚焦的是「會直接改變方法行為的未解決選擇」，而非一般性的研究限制。與論文—程式碼一致性（paper–code consistency）檢測相比，IdeaAMBIG 是在實作發生前介入，目標是預防可複現性失敗（reproducibility failures），而非事後發現已產生物件之間的差異。

本研究的優勢包括：結合真實與合成數據、所有缺口與解決方案皆有論文或程式碼證據支持、採用單一缺陷實例（single-defect instances）以便精確歸因、並透過人類盲審與獨立重標註確保標籤可靠性。

然而，IdeaAMBIG 也存在一些限制。首先，單一缺陷的假設雖然有助於分析，但真實規格往往同時存在多個互相牽連的缺口。其次，真實數據主要來自機器學習領域的 GitHub Issues 與可複現性報告，領域覆蓋仍有限。第三，合成缺口的生成依賴 LLM 提取候選缺陷，若提取過程本身有偏誤，可能影響合成實例的代表性。最後，澄清行動的評估目前以語義正確性為主，未必能完全保證依該澄清實作後的程式碼行為與原始意圖一致。

#### 可重現性評估

從提供的內容來看，IdeaAMBIG 的數據來源具有高度透明性：真實缺口來自公開的 GitHub Issues 與可複現性報告，合成缺口的參考規格則來自已驗證成功再現的論文與程式碼。這種「有證據基礎」的建構方式讓其他研究者可以追溯每個實例的原始出處，並獨立驗證缺口與解決方案是否合理。

此外，作者進行了人類研究、盲審與獨立重標註，以確認標籤的可靠性與工作流程的可信度。可編碼參考規格（codification-ready references）的篩選標準也相當嚴格，要求參考來源必須包含可運行程式碼與已報告結果，這降低了因參考本身不正確而導致的標籤雜訊。

不過，在提供的上下文中，並未明確說明是否會公開完整的資料集、缺口注入與評估程式碼、或模型權重。若作者後續釋出這些資源，則本研究的可重現性將非常高；反之，其他團隊若要複製整個流程，仍需自行重建從議題抽取、參考規格驗證、到合成缺口注入的完整管線，難度與工時都相當可觀。因此，建議後續發表時應詳細說明資料釋出範圍與授權條款，以強化社群的再現能力。

#### 未來研究方向

IdeaAMBIG 為「研究想法規格化」這個新興議題奠定了評估基礎，未來可沿以下方向延伸：

1. **多缺陷與組合式缺口（multi-defect / compositional gaps）**：放寬單一缺陷實例的限制，研究模型如何同時定位並處理多個互相牽連的規格缺口。
2. **互動式澄清迴路（interactive clarification loops）**：將單輪的澄清行動生成擴展為多輪對話，讓模型能根據人類回饋逐步收斂到可編碼規格。
3. **可執行驗證（executable verification）**：不僅評估澄清問題的語義正確性，更進一步將補齊後的規格交給編碼代理實作，以實際執行結果驗證忠實實作程度。
4. **領域擴展（domain expansion）**：將評估範圍從機器學習擴大到其他科學領域，例如計算生物學、化學模擬或社會科學實驗設計。
5. **專門化模型訓練（specialized model training）**：利用 IdeaAMBIG 作為訓練資料，微調專門用於規格缺口檢測與澄清的模型，並觀察其泛化到真實議題的能力。
6. **不確定性感知與主動學習（uncertainty-aware detection）**：讓模型在無法確定時明確表達不確定，並主動選擇最有資訊價值的澄清問題，降低無依據假設的風險。
7. **對抗式與動態基準生成（adversarial / dynamic benchmark generation）**：自動生成更困難、更隱蔽的規格缺口，以持續推動模型進步。
8. **人機協作規格精煉（human-AI collaborative specification refinement）**：設計讓研究人員與 AI 共同撰寫與審查方法規格的工作流程，並評估其對最終研究品質的影響。

總體而言，IdeaAMBIG 揭示了一個過去被忽視但至關重要的問題：即使研究想法本身合理，若其方法規格存在缺口，自動化執行仍可能產生「看起來能跑、實際上跑錯方法」的結果。未來的研究代理若要真正可靠，必須在編碼前具備發現、定位並釐清這些實作關鍵缺口的能力。

## 論文問答

**Q1：IdeaAMBIG 旨在解決什麼核心問題？**

A：IdeaAMBIG 聚焦於研究想法規格（Research-Idea Specifications）在「可編碼性」（Codification Readiness）上的關鍵缺口，也就是一個研究想法雖然新穎、合理且科學上可行，但其方法規格可能仍不足以讓稱職實作者（Competent Implementer）或編碼代理（Coding Agent）進行忠實實作（Faithful Implementation）。當核心方法中的方法定義選擇（Method-Defining Choices）被省略、模糊或內部不一致時，下游代理可能會默默引入無依據假設（Unsupported Assumptions），導致產出看似能運作但實際上實作了錯誤方法的程式碼。這個問題直接影響研究自動化管線的可靠性，因為從想法生成到實驗執行之間的規格橋梁若斷裂，將造成可複現性失敗（Reproducibility Failures）。

**Q2：為什麼現有的評估方法無法捕捉這個問題？**

A：現有的科學研究評估大多集中於上游想法品質（Upstream Idea Quality），例如新穎性、可行性與多樣性，或是下游計畫與產物（Downstream Plans and Artifacts），例如生成的程式碼與實驗結果，但卻預設連接這兩者的研究方法規格已經足夠明確。這些評估忽略了規格本身可能存在的實作關鍵缺口（Implementation-Critical Gaps），使得模型即使能產出高品質想法或執行計畫，也無法保證實作與原意一致。IdeaAMBIG 正是要填補這個評估空白，透過證據基礎的規格（Evidence-Grounded Specifications）來檢驗模型是否能識別規格缺口、定位缺陷並產生有效的澄清行動。

**Q3：為什麼可編碼性對研究自動化如此重要？**

A：可編碼性決定了一個研究想法是否能被轉換為與原意一致的實驗原型（Experimental Prototype），而不需要實作者自行猜測關鍵設計選擇。在大型語言模型（LLMs）與研究代理（Research Agents）日益整合科學工作流程的背景下，若規格在編碼前就緒度不足，自動化系統將面臨兩難：要么主動尋求澄清，要么默默做出無依據假設。後者尤其危險，因為它可能產生表面成功但方法錯誤的結果，進一步放大可複現性危機，因此可編碼性評估是確保研究自動化可信度的關鍵環節。

**Q4：IdeaAMBIG 的核心方法論是什麼？**

A：IdeaAMBIG 建構了一個包含 660 個單一缺陷實例（Single-Defect Instances）的基準測試，其中 163 個來自真實世界的 GitHub Issues 與可複現性報告（Reproducibility Reports），497 個則是透過在可編碼參考規格（Codification-Ready References）中注入受控合成缺口（Controlled Synthetic Gaps）所產生。每個實例都包含目標缺陷、有依據的解決方案（Supported Resolutions），以及來自 3 個 Level-1 和 10 個 Level-2 類別的標註。這種設計讓研究者能夠精確評估模型在三項漸進能力上的表現：可編碼性評估（Codification-Readiness Assessment）、缺陷定位（Defect Localization），以及澄清行動生成（Clarification Action Generation）。

**Q5：與現有基準相比，IdeaAMBIG 的關鍵創新是什麼？**

A：IdeaAMBIG 的關鍵創新在於它首次將研究想法規格的「實作就緒度」（Implementation Readiness）獨立出來作為評估對象，而非僅評估想法品質或最終產物。它結合了真實世界缺口與受控合成缺口的雙重設計，前者確保生態效度與實務相關性，後者提供精確的反事實目標以利嚴謹評估。此外，它將缺陷定位與澄清行動生成分開評估，這種分離設計能夠精確識別模型能力的瓶頸所在，特別是模型是否能在沒有提示的情況下主動發現規格中的實作關鍵缺口。

**Q6：在建構基準時有哪些主要設計選擇？**

A：首先，作者選擇從已獨立驗證成功複現或執行的論文中抽取可編碼參考規格，確保參考規格本身確實足以被忠實實作。其次，真實世界缺口來自 GitHub Issues 與 TMLR 可複現性報告等實際情境，並經過人工分類與分解以確保每個實例只包含單一缺陷。最後，合成缺口透過大型語言模型在參考規格中精確注入單一實作關鍵細節的變更，並由人工驗證其有效性與工作流程合理性，從而兼顧規模化與標註可靠性。

**Q7：IdeaAMBIG 使用了哪些資料集與評估任務？**

A：IdeaAMBIG 包含兩大資料來源：一是真實世界缺口，來自 2017 至 2025 年間的 ML Reproducibility Challenge 報告、GitHub Issues 以及與論文連結的程式碼庫；二是合成缺口，來自已確認可複現的 AI 研究者執行研究論文與想法。評估任務分為三項：任務一只給定規格並要求判斷是否可編碼；任務二僅給定規格並要求定位缺陷；任務三則在給定規格與標註缺陷後，要求產生能夠釐清缺口的澄清問題或行動。這三項任務形成由淺入深的評估管線，能夠分離不同層次的模型能力。

**Q8：實驗中的關鍵結果是什麼？**

A：在 13 個大型語言模型中，最強模型在真實世界實例上的宏觀缺陷恢復率（Macro Defect Recovery Rate）僅達 9.6%，顯示缺陷定位是當前模型最嚴重的瓶頸。然而，當給定標註缺陷後，最強模型的宏觀澄清行動成功率（Macro Clarification Action Success Rate）達到 80.6%，顯示模型在知道問題所在後，通常能夠提出有用的澄清問題。此外，在神諭研究（Oracle Study）中，提供黃金標準解決方案（Gold Resolution）後，下游可編碼率（Downstream Codification-Ready Rate）從 14% 大幅提升至 98%，凸顯了正確澄清資訊對實作就緒度的關鍵價值。

**Q9：作者進行了哪些消融研究或深入分析？**

A：作者透過比較真實世界缺口與受控合成缺口，驗證了合成實例能夠保留自然發生缺口的有效性與工作流程合理性。人類研究、盲審與獨立重新標註進一步確認了兩個子集都包含可解決且實作關鍵的缺口，並且標籤具有高度可靠性。此外，透過將缺陷定位與澄清行動生成分開評估，作者能夠精確量化模型在「發現問題」與「解決問題」上的能力差距，並證明即使是最強大的模型，在沒有缺陷提示的情況下也難以主動發現規格中的實作關鍵缺口。

**Q10：IdeaAMBIG 有哪些實際應用場景？**

A：IdeaAMBIG 可直接應用於研究代理的開發與評估，特別是在自動化科學工作流程中負責將研究想法轉換為程式碼的環節。它也能幫助研究者在撰寫論文或技術文件時，預先檢視自己的方法規格是否存在實作關鍵缺口，從而減少後續可複現性問題。此外，對於開源專案維護者與程式碼庫貢獻者而言，這個基準可用來訓練模型自動識別 issue 中的規格模糊之處，並提出具體的澄清問題以加速問題解決。

**Q11：從產品與工程角度來看，這項工作帶來哪些考量？**

A：在產品層面，IdeaAMBIG 提醒開發者不能僅以「程式碼能否執行」或「結果是否好看」來評估研究自動化系統，而必須檢驗系統是否實作了研究者真正意圖的方法。工程上，這意味著研究代理需要內建可編碼性檢查機制，在進入編碼階段前先評估規格是否就緒，並在發現缺口時主動暫停並尋求澄清。此外，由於缺陷定位是主要瓶頸，產品設計上可能需要結合人機協作介面，讓模型在無法確定時能夠向人類研究者提出具體問題，而非默默做出無依據假設。

**Q12：這項工作對整個領域可能產生什麼影響？**

A：IdeaAMBIG 為研究自動化領域建立了一個新的評估維度，將學界與業界的注意力從單純的想法生成與程式碼生成，轉移到兩者之間的規格橋梁品質。這有助於推動更可靠的研究代理設計，減少因規格不清導致的可複現性失敗，並提升科學研究自動化的整體可信度。長遠來看，這項工作也可能影響學術寫作與同行評審的標準，促使研究者更仔細地規格化其核心方法，從而讓研究結果更容易被驗證與延伸。

**Q13：作者承認了哪些限制？**

A：作者指出 IdeaAMBIG 目前專注於單一缺陷實例，而真實世界中的規格缺口可能同時包含多個相互關聯的問題，這是基準設計上為了評估可控性所做的簡化。此外，雖然合成缺口經過驗證，但它們畢竟是人為注入的，可能無法完全涵蓋自然發生缺口的所有複雜性與語境細節。最後，基準主要聚焦於方法規格的實作就緒度，並未涵蓋所有可能影響研究成功的因素，例如資料品質、計算資源限制或實驗設計的整體合理性。

**Q14：有哪些失敗案例或特別困難的實例？**

A：最困難的實例通常是那些需要深入領域知識才能判斷方法定義選擇是否缺失的情況，例如混合專家模型（MoE）中「啟動參數數量」（Activated Parameter Count）的計算方式是否包含閘門（Gate）參數。另一類困難實例涉及隱含在論文或程式碼中的慣例，若模型未具備相關背景知識，便難以察覺規格中省略了關鍵細節。此外，即使是最強模型在真實世界實例上的缺陷恢復率也僅有 9.6%，顯示仍有大量實例需要更強大的推理能力或更豐富的領域上下文才能正確定位。

**Q15：未來有哪些研究方向？**

A：未來研究可以擴展 IdeaAMBIG 至多缺陷實例，以更接近真實世界中複雜規格缺口的樣貌。另一個方向是開發能夠主動進行多輪澄清的研究代理，讓模型不僅能提出單次問題，還能根據回答持續追問直到規格達到可編碼狀態。此外，將可編碼性評估整合到端到端的研究自動化管線中，並結合人類回饋進行強化學習，也是提升研究代理可靠性的重要方向，最終目標是讓自動化系統能夠在實作前自主發現並解決規格缺口。

## 實務應用指南

### 適用場景

1. **AI 研究代理的規格審查閘道**  
   在自動化研究流程中，將 IdeaAMBIG 的三項任務（可編碼性評估、缺陷定位、澄清行動生成）嵌入研究代理的「構想→實作」轉換點，於生成程式碼前先檢查方法規格是否已達可編碼狀態，避免編碼代理帶著無依據假設實作出錯誤方法。

2. **學術論文與開源程式碼的複現性預檢**  
   期刊、會議或開源維護者可在論文接收或合併程式碼前，使用 IdeaAMBIG 的評估框架檢視「研究想法規格」是否遺漏方法定義選擇，例如訓練細節、超參數設定或資料前處理步驟，降低後續可複現性失敗的機率。

3. **企業內部 AI 方法轉移與工程交接**  
   當研究團隊將新方法移交給工程團隊實作產品化時，可用此框架檢查方法規格的實作就緒度，找出模糊或缺失的實作關鍵缺口，並產出具體澄清問題作為交接文件。

4. **大型語言模型能力評測與選型**  
   模型開發者可採用 IdeaAMBIG 的 660 筆實例作為評測集，比較不同 LLM 在「僅給規格就要找出缺陷」與「給定缺陷後產生澄清行動」的表現，作為選擇研究代理核心模型的依據。

5. **教學與研究訓練**  
   在研究生或工程師的實作方法學課程中，使用受控合成缺口與真實 GitHub Issues 作為教材，訓練學員辨識規格缺口、提出有依據的解決方案，並理解無依據假設如何導致可複現性失敗。

### 實作前置條件

**資料需求**
- 取得 IdeaAMBIG 資料集（660 筆實例，含真實缺口與受控合成缺口）以及對應的黃金標準解決方案與 Level-1 / Level-2 標籤。
- 若應用於自有領域，需準備「可編碼參考規格」作為對照基準，例如已成功複現的論文方法描述、可執行程式碼、GitHub Issues 與可複現性報告。
- 建議建立領域詞表與方法定義選擇清單，以便將通用框架對應到特定任務（如 MoE 的 top-k 閘門、Dense FFN 的參數匹配方式）。

**運算需求**
- 執行三項評估任務本身主要為推論工作：中等規模 LLM（如 7B–70B）即可進行可編碼性評估與澄清行動生成。
- 缺陷定位任務對模型能力要求較高，建議使用最強可取得模型（如 GPT-4o、Claude 3.5/4、DeepSeek-V4-Pro 等級）作為主要評測模型。
- 若要大規模自動化審查大量規格，需準備具備足夠 API 配額或本地 GPU 叢集的推論環境。

**技能需求**
- 熟悉研究論文與程式碼對照閱讀，能判斷方法規格中的實作關鍵缺口。
- 具備提示工程經驗，能設計零樣本或少樣本提示，引導模型輸出「READY / NOT_READY」、缺陷位置與澄清問題。
- 了解評估指標設計，特別是 Macro Defect Recovery Rate 與 Macro Clarification Action Success Rate 的計算方式。
- 若進行領域遷移，需要領域專家協助標註「有依據的解決方案」，確保標籤具證據基礎。

### 實作步驟建議

1. **定義評估對象與範圍**  
   選定要審查的研究想法規格，例如論文的方法章節、AI 研究代理產生的方法描述，或內部技術文件。明確核心方法與方法定義選擇的邊界。

2. **建立可編碼參考規格**  
   從已成功複現的論文、可執行程式碼與再現報告中，萃取出「若照此規格實作，兩位稱職實作者會得到相同方法」的參考版本，作為判斷缺口的黃金基準。

3. **執行可編碼性評估（Task 1）**  
   將規格輸入模型，要求判斷 READY / NOT_READY。若為 NOT_READY，再進入後續步驟；若為 READY，仍需抽樣人工複核，因為模型可能遺漏隱性缺口。

4. **執行缺陷定位（Task 2）**  
   僅提供規格，不給缺陷提示，要求模型指出具體缺失、模糊或不一致的方法定義選擇。此步驟是主要瓶頸，建議使用最強模型並結合人工驗證。

5. **執行澄清行動生成（Task 3）**  
   在模型或人工標註出缺陷後，要求模型產生具體的澄清問題或所需資訊（例如「請問 MoE 的參數匹配是否包含閘門參數？」）。確認澄清行動能導向有依據的解決方案。

6. **收集解答並更新規格**  
   將澄清問題回饋給原始作者、論文作者或領域專家，取得證據支持的解答後，更新方法規格，並重新執行 Task 1 確認已達可編碼狀態。

7. **整合至 CI/CD 或研究代理流程**  
   將上述步驟包裝為自動化檢查節點，例如在研究代理產生方法描述後、呼叫編碼代理前執行；或在論文投稿系統中作為可複現性預檢工具。

8. **持續監控與迭代**  
   收集模型預測與人工判斷的差異，擴充自有領域的受控合成缺口資料，定期重新校準評估提示與模型選型。

### 潛在風險與注意事項

- **缺陷定位仍是瓶頸**：論文顯示即使最強模型在真實實例上的 Macro Defect Recovery Rate 僅約 9.6%，不可單獨依賴自動定位，必須保留人工複核機制。
- **模型可能過度自信地標為 READY**：模型傾向忽略隱性方法定義選擇，建議對 READY 預測進行抽樣審查，並要求模型列出所有做過的假設。
- **澄清問題可能過於籠統**：若問題不夠具體，無法取得有依據的解決方案。應要求模型參照規格中的確切段落或變數名稱來定位問題。
- **領域遷移時標籤品質下降**：IdeaAMBIG 的實例主要來自機器學習領域，應用於其他學科時需重新建立證據基礎的標註流程，避免直接套用。
- **過度依賴自動化可能抑制創意**：此框架聚焦「能否忠實實作」，而非評估想法的新穎性或科學價值，應與上游想法品質評估搭配使用。
- **隱私與授權問題**：使用 GitHub Issues、可複現性報告或論文內容建立自有資料集時，需確認授權條款與資料使用規範。

### 與其他技術的整合建議

- **研究代理（Research Agents）**：將 IdeaAMBIG 作為方法規格審查模組，置於「想法生成」與「實驗執行 / 編碼代理」之間，形成帶有閘道的流水線。
- **程式碼生成工具（Code Generation）**：在呼叫編碼代理前，先確認規格已達可編碼狀態；若未就緒，則將澄清問題作為額外上下文餵給編碼代理，提升下游可編碼率。
- **論文—程式碼一致性檢查（Paper–Code Consistency）**：IdeaAMBIG 處理實作前的規格缺口，可與後置的論文—程式碼一致性檢測工具串接，形成從規格到產物的完整驗證鏈。
- **科學批判與同行審查輔助**：與 LimitGen、SciConvBench 等科學批判基準互補，IdeaAMBIG 專注於未解決的方法定義選擇，適合嵌入審查輔助系統。
- **知識庫與檢索增強生成（RAG）**：將論文、程式碼、Issue 線索與可複現性報告建入向量資料庫，讓模型在定位缺陷時能檢索相關證據，提升有依據解決方案的品質。
- **持續整合 / 持續部署（CI/CD）**：在開源專案或企業內部方法庫中，將規格審查設為合併前檢查項目，確保新方法文件達到實作就緒度。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從圖 1 的三項任務與「可編碼性」概念入手，理解「想法很好」與「能夠被正確實作出來」是兩回事；接著閱讀真實 GitHub Issues 範例，觀察一個小細節（例如 scheduler 是否套用）如何導致不同實作結果，最後再回頭看論文的正式定義與評估指標。

**AI 工程師**  
重點關注實作步驟與整合建議，特別是缺陷定位任務的瓶頸與澄清行動生成的高成功率；思考如何將這三項任務包裝成 API 或中介層，並與現有的編碼代理、RAG 系統與 CI/CD 流程結合，同時預留人工複核的 fallback 機制。

**研究人員**  
建議深入閱讀資料建構方式（真實缺口 vs. 受控合成缺口）、標註流程與人類研究驗證，評估此框架是否適用於自身領域；同時注意論文對「可編碼性」與「想法品質」的區分，避免將實作就緒度誤認為科學價值評估。

**產品經理**  
聚焦適用場景與潛在風險，評估將 IdeaAMBIG 引入團隊後能減少哪些成本（例如重複實作、可複現性失敗、研究—工程交接摩擦）；同時理解此技術目前仍無法全自動運作，需規劃人工審查與領域專家參與的資源配置。
