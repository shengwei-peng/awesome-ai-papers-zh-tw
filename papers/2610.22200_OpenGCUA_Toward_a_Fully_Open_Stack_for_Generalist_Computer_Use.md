## ⚡ TL;DR

前沿電腦使用代理如GPT-6 Astra為封閉系統，限制了通用電腦使用代理的系統性研究。
本文提出OpenGCUA開放技術棧，核心採用程式碼執行與框架至模型決策轉移設計。
在OSWorld-v2上八款模型平均得分提升19.6分，步數減少53%，真實裝置測試亦驗證效率差異。

## 摘要翻譯

電腦使用領域已到達一個轉折點：焦點正從僅限 GUI 的互動，擴展到能透過視覺與程式化介面（visual and programmatic interfaces）在使用者電腦上完成任務的系統。我們將通用電腦使用代理（Generalist Computer-Use Agent, GCUA）定義為一個系統，其中模型自行決定如何跨視覺與程式化介面進行觀察、動作與工作組織。然而，前沿實作（frontier implementations），例如 GPT-6 Astra 的電腦使用系統，仍大多為封閉系統，限制了對其設計進行系統性研究（systematic study）。我們推出開放通用電腦使用代理（Open Generalist CUA, OpenGCUA），這是一個與社群（community）共同開發並開放 GCUA 完整技術棧（full stack）的持續進行的專案（ongoing project）。本報告呈現 OpenGCUA 的首次發布（first release）。

程式碼執行（code execution）是我們代理設計（agent design）的核心功能：它讓中間結果（intermediate results）決定後續操作，並使模型能將其既有的程式設計能力（programming capabilities）直接應用於電腦互動（computer interaction）。我們亦提出框架至模型決策轉移（harness-to-model decision transfer），將選定的觀察與任務狀態決策（task-state decisions）從固定的框架規則（harness rules）移轉至模型。在 OSWorld-v2 上，我們的完整配置（full configuration）在全部八個受評測模型（含 GPT-6 Astra 與 Claude Opus 5）上皆提升了任務得分（task score），相較於批次式僅 GUI 執行（batched GUI-only execution），平均部分得分（mean partial score）提高 +19.6 點，每任務報告步數（reported steps per task）平均減少 53.0%。

我們釋出實作（implementation）與提示詞（prompts）、八個模型的評測軌跡（evaluation trajectories），以及真實裝置框架（real-device harness）與跨裝置軟體開發套件（cross-device SDK）的初步版本（preliminary versions）。該框架處理了基準未能完整涵蓋的真實裝置挑戰（real-device challenges），而軟體開發套件則提供跨電腦、行動裝置與瀏覽器的通用程式介面（common programming interface）。在我們的真實裝置框架下的四個真實 macOS 任務（real macOS tasks）中，選定的 Qwen3.8-Max 執行的報告推理詞元（reported reasoning tokens）數為 GPT-6 Astra 的 19.4 倍，凸顯了模型在真實裝置執行效率（real-device execution efficiency）上的顯著差異。

### 核心貢獻（3～5點）
- **提出 GCUA 系統定義與 OpenGCUA 開放技術棧**：將通用電腦使用代理定義為由模型自主決定如何跨視覺與程式化介面進行觀察、動作與工作組織的系統，並以開放原始碼形式釋出完整技術棧，促進社群對前沿設計的系統性研究。
- **以程式碼執行為核心的代理設計**：讓中間結果驅動後續操作，使模型能直接運用既有程式設計能力於電腦互動，突破僅依賴 GUI 操作的限制。
- **提出框架至模型決策轉移機制**：將選定的觀察與任務狀態決策從固定框架規則移轉至模型，提升代理的自主性與適應能力。
- **在 OSWorld-v2 上驗證顯著效能提升**：完整配置於八個受評測模型（含 GPT-6 Astra 與 Claude Opus 5）皆提升任務得分，平均部分得分提高 +19.6 點，每任務報告步數平均減少 53.0%。
- **釋出真實裝置框架與跨裝置 SDK 初步版本**：處理基準未能完整涵蓋的真實裝置挑戰，並提供跨電腦、行動裝置與瀏覽器的通用程式介面，為真實環境部署奠定基礎。

### 適合對象
本論文最適合從事電腦使用代理（Computer-Use Agent, CUA）、大型語言模型代理設計、自動化與人機互動研究的學者與工程師閱讀；亦適合關注開源人工智慧系統、代理評測基準（如 OSWorld-v2）、以及真實裝置部署挑戰的產業研發人員與研究生參考。

## 深度分析

#### 方法論解析

OpenGCUA 的方法論核心在於重新定義電腦使用代理（Computer-Use Agent, CUA）的範疇，並提出兩項關鍵設計原則：**程式碼執行（Code Execution）** 與 **框架至模型決策轉移（Harness-to-Model Decision Transfer）**。此方法論的設計動機來自於對前沿封閉系統（如 GPT-6 Astra）的觀察——這些系統已從純 GUI 操作演進為結合視覺與程式化介面的混合架構。

**1. 通用電腦使用代理（GCUA）的形式化定義**

論文中將 GCUA 定義為「能透過視覺互動與程式化存取完成多元電腦任務的代理系統，其中模型依任務需求決定如何觀察、執行與組織工作」。此定義包含三個核心決策權：
- **觀察決策（What to observe）**：模型決定當前步驟應取得螢幕截圖、AX tree（Accessibility Tree，無障礙存取樹），或無需新觀察。
- **行動決策（How to act）**：模型輸出一個統一程式，跨越 GUI、AX tree、CLI（Command Line Interface）與 API。
- **組織決策（How to organize）**：模型管理計畫、進度與上下文保留。

此三層決策架構使 GCUA 與傳統 GUI-only CUA 形成本質區別——後者將上述決策固化於框架規則中，而 GCUA 將決策權下放至模型本身。

**2. 程式碼執行機制**

程式碼執行是 OpenGCUA 代理設計的核心功能。實作上採用 Python runtime 結合 PyAutoGUI 與 bash() 呼叫，使模型能在一個輸出中混合 GUI 操作與 shell 指令。此設計的關鍵優勢在於：
- **中間結果驅動後續操作**：程式碼執行產生的中間結果（如檔案內容、API 回應）可直接作為後續步驟的輸入，無需經過截圖辨識的循環。
- **複用模型既有程式設計能力**：模型無需學習新的動作空間格式，直接運用其程式設計能力處理電腦互動。
- **批次化操作**：多個 GUI 動作可在一個程式碼區塊中批次執行，減少與環境的往返次數。

論文中列舉了代表性的程式碼執行模式，包括檔案系統操作、批次 GUI 動作、API 呼叫與 shell 指令的組合等。同時也明確指出 **僅視覺回饋（Visual-Only Feedback）** 的限制——當任務需要精確讀取文字、處理結構化資料或進行複雜計算時，純視覺介面會產生不必要的誤差與步驟。

**3. 框架至模型決策轉移機制**

此機制將部分原本由固定框架規則處理的決策（如觀察選擇、任務狀態判斷）轉移至模型。論文中提出具體的轉移模式：
- **觀察選擇轉移**：模型決定何時需要新截圖、何時可沿用既有資訊。
- **任務狀態決策轉移**：模型判斷任務是否完成、是否需要重試、是否陷入迴圈。

此設計的理論基礎在於：模型對任務語意有更深的理解，固定規則難以處理所有邊角情況；將決策權交給模型可提升整體效率與穩健性。

**4. 真實裝置框架（Real-Device Harness）的五層式架構**

針對真實裝置部署，論文提出五層式架構以回應基準測試無法捕捉的挑戰（如背景視窗、使用者干擾、共享控制）。雖然具體細節需參考完整論文，但此架構顯然涵蓋從裝置互動層到模型介面層的完整堆疊，處理真實環境中的非確定性。

**5. 跨裝置 SDK（Cross-Device SDK）**

提供電腦、行動裝置與瀏覽器之間的通用程式介面，使代理程式能以統一方式處理跨裝置任務。此 SDK 的設計理念是將裝置異質性抽象化，讓模型專注於任務邏輯而非介面差異。

#### 實驗數據解讀

論文的實驗設計分為兩大部分：基準測試（OSWorld-v2）與真實裝置初步實驗（macOS）。

**1. OSWorld-v2 基準測試結果**

在 OSWorld-v2 上評測了八款模型，包含前沿封閉模型（GPT-6 Astra、Claude Opus 5）與開源模型（Qwen3.8-Max 等）。完整配置（Full Configuration）相對於批次僅 GUI 執行（Batched GUI-Only Execution）基線的關鍵結果：
- **平均部分得分（Mean Partial Score）提升 +19.6 點**：此為跨八款模型的平均改善，顯示程式碼執行與決策轉移的組合對不同模型均有穩健效益。
- **每任務報告步數（Reported Steps per Task）平均減少 53.0%**：效率提升顯著，意味著代理以更少步驟完成任務。

此結果的解讀重點在於：+19.6 點的改善並非來自單一模型的偶然表現，而是跨模型的系統性增益，驗證了程式碼執行與決策轉移作為通用設計原則的有效性。53.0% 的步數減少則凸顯了效率作為一等公民指標（Efficiency as a First-Class Metric）的實證基礎——純 GUI 操作的循環成本在基準測試中已造成顯著浪費。

**2. 消融實驗（Ablation）**

論文進行了兩項關鍵消融實驗：
- **程式碼執行消融實驗（Code-Execution Ablation）**：驗證移除程式碼執行後效能下降的程度。
- **框架至模型決策轉移消融實驗（Harness-to-Model Decision Transfer Ablation）**：驗證決策轉移機制的獨立貢獻。

雖然具體數值需參考完整論文，但此設計表明兩項機制各自貢獻獨立價值，且組合使用時產生綜效。

**3. CUA 與 GCUA 的對比**

論文區分三種配置：
- **CUA**：傳統 GUI-only 代理。
- **GUI+CLI 混合型 CUA（GUI+CLI Hybrid CUA）**：結合 GUI 與 CLI 但仍受限於固定動作空間。
- **GCUA**：完整配置，含程式碼執行與決策轉移。

此對比實驗驗證了 GCUA 相較於 GUI+CLI 混合型 CUA 的進一步優勢，說明僅加入 CLI 並不足夠，必須讓模型擁有統一的程式輸出能力。

**4. 真實 macOS 任務初步結果**

在四個真實 macOS 任務下，Qwen3.8-Max 使用的報告推理詞元（Reported Reasoning Tokens）為 GPT-6 Astra 的 **19.4 倍**。此數據揭示了兩個重要現象：
- **模型間效率差異巨大**：前沿模型在推理效率上仍有顯著優勢，開源模型需在精簡推理方面持續優化。
- **基準測試無法完全反映真實效率**：真實裝置環境下的推理成本是基準測試中難以觀察的維度。

**5. 「金錢與時間能買多少任務表現？」實驗**

此實驗探討資源投入（推理預算、嘗試次數）與任務表現的關係，暗示單純增加計算資源並非萬靈丹，系統設計的改善才是根本。

#### 與現有研究的比較

**1. 相對於 GUI-only CUA 的定位**

傳統 CUA 研究（如 Qin et al., 2025; Lu et al., 2026）專注於截圖觀察與滑鼠鍵盤動作的閉環。OpenGCUA 的貢獻在於明確指出此範式的不足：當任務涉及檔案操作、結構化資料處理或多步驟邏輯時，純 GUI 介面會產生不必要的步數與誤差。論文的 **轉向程式碼執行的路線翻轉（The Route Flip to Code Execution）** 概念標誌了典範轉移。

**2. 相對於前沿封閉系統**

GPT-6 Astra 的電腦使用系統被視為代表性 GCUA，但其模型權重、完整提示設定、真實裝置框架、裝置控制 SDK 與執行軌跡均未公開。OpenGCUA 的核心定位差異在於：
- **可重現性**：釋出實作、提示詞與評測軌跡。
- **設計透明度**：明確區分程式碼執行與決策轉移兩項機制。
- **社群協作**：作為持續進行的專案（Ongoing Project），邀請社群共同發展。

然而，必須承認 OpenGCUA 目前 **尚未包含訓練好的模型**，這是與封閉前沿系統最大的差距。

**3. 相對於 Qwen-UI-Agent**

作者的前作 Qwen-UI-Agent 透過統一 GUI 與 CLI 動作空間與批次動作探索了類似方向。在 OpenGCUA 的框架中，GUI+CLI 混合型 CUA 被定位為 GCUA 的特殊案例——這顯示研究的演進脈絡：從動作空間統一到程式碼執行，再到決策權轉移。

**4. 局限性**

- **模型未釋出**：首次發布僅含設計、軌跡與初步框架，無法直接用於部署。
- **真實裝置實驗規模小**：僅四個 macOS 任務，統計意義有限。
- **跨裝置 SDK 為初步版本**：跨裝置任務的實證驗證尚不充分。
- **效率指標的定義**：報告步數與推理詞元是代理回報的數值，未必完全反映實際計算成本。

#### 可重現性評估

OpenGCUA 在可重現性方面展現了明確的承諾，但首次發布的覆蓋範圍有限：

**1. 已釋出資源**
- **實作程式碼（Implementation）**：代理框架的程式碼已開源釋出。
- **提示詞（Prompts）**：完整的提示設定可供檢視與修改。
- **評測軌跡（Evaluation Trajectories）**：八款模型在 OSWorld-v2 上的執行軌跡均已釋出，這是極具價值的研究資源，使社群能進行軌跡分析與後續研究。

**2. 初步版本資源**
- **真實裝置框架（Real-Device Harness）**：初步版本釋出，但標示為「preliminary」，穩定性與覆蓋範圍有待驗證。
- **跨裝置 SDK（Cross-Device SDK）**：初步版本，跨裝置任務的支援尚不完整。

**3. 未釋出資源**
- **模型權重**：首次發布明確表示「GCUA model is not included in this release」，這是最大的可重現性缺口。沒有模型，框架的實際效能無法被獨立驗證。
- **真實裝置評測基準**：尚無系統化的真實裝置評測環境釋出。

**4. 可重現性評等**

整體而言，OpenGCUA 在「設計可重現性」方面表現優異——任何研究者均可重現其代理設計與消融實驗。但在「端到端可重現性」方面受限於模型未釋出。論文的路線圖（Roadmap）明確規劃了從設計驗證到模型發布（From Design Validation to Model Release）的路徑，預期後續版本將補齊此缺口。

#### 未來研究方向

OpenGCUA 開啟了多個值得深入探索的研究方向：

**1. 模型訓練與開源模型優化**

最直接的方向是訓練並釋出 GCUA 模型。論文中 Qwen3.8-Max 在真實裝置上使用 19.4 倍於 GPT-6 Astra 的推理詞元，凸顯了開源模型在精簡推理方面的巨大改進空間。未來研究可探討：
- 如何在訓練階段內化程式碼執行模式，減少運行時推理負擔。
- 如何讓開源模型學會有效的觀察選擇策略，避免不必要的截圖。
- 蒸餾（Distillation）前沿模型的決策模式至開源模型。

**2. 真實裝置評測基準的建立**

論文中明確指出基準測試與真實機器之間的差距（The Gap Between Benchmarks and Real Machines）。未來應發展：
- 系統化的 macOS 真實裝置評測環境。
- 涵蓋背景視窗、使用者干擾、共享控制的測試場景。
- 真實裝置效率指標的標準化（如推理詞元、實際計算時間、電力消耗）。

**3. 跨裝置任務的理論與實作**

跨裝置 SDK 開啟了跨裝置任務的研究空間，例如「在電腦上編輯文件後於手機上預覽」。未來研究可探討：
- 跨裝置任務的形式化定義與評測。
- 跨裝置狀態同步與一致性保證。
- 跨裝置任務規劃（Task Planning）的演算法。

**4. 框架至模型決策轉移的理論基礎**

此機制目前以經驗方式呈現，未來可發展：
- 哪些決策適合轉移至模型、哪些應保留於框架的理論原則。
- 決策轉移對模型可解釋性（Interpretability）的影響。
- 決策轉移與模型能力（Capability）之間的相依關係——能力較弱的模型可能無法承擔更多決策權。

**5. 效率優化的系統層面研究**

論文中「效率作為一等公民指標」的主張值得深入：
- 程式碼執行與決策轉移之外的其他效率優化途徑（如快取、預測執行、平行化）。
- 效率與任務表現之間的權衡（Trade-off）。
- 不同模型在效率維度上的特徵分析。

**6. 安全與共享控制**

真實裝置部署引入了 GUI-only 基準測試中不存在的安全挑戰：
- 代理動作的權限邊界。
- 使用者干擾下的狀態恢復。
- 敏感操作（如刪除檔案、付款）的確認機制。

**7. 程式碼執行模式的系統性研究**

論文中列舉了代表性的程式碼執行模式，但缺乏系統性的分類與分析。未來可建立程式碼執行模式的分類學，並研究不同模式對不同任務類型的適用性。

OpenGCUA 的核心價值不僅在於其當前成果，更在於其作為 **持續進行的開源專案（Ongoing Project）** 所開啟的研究議程。論文的路線圖明確規劃了從設計驗證到模型發布、從基準測試到真實裝置評測、從單一裝置到跨裝置的演進路徑，為整個電腦使用代理研究社群提供了清晰的協作框架。

## 論文問答

**Q1：為什麼作者認為電腦使用代理研究正處於一個「轉折點」？**

A：作者認為電腦使用代理研究正處於轉折點，是因為研究焦點正從僅限於 GUI 的互動模式，擴展到能透過視覺與程式化介面完成使用者電腦上任務的系統。這種轉變的核心在於 GPT-6 Astra 等前沿系統開始強調結合 GUI 操作、shell 命令、無障礙樹存取等多種介面，並由 OpenAI 明確推薦使用程式碼執行方式來撰寫 GUI 操作並與程式化操作結合。問題的本質已從「模型操作 GUI 介面的能力有多好」轉變為「系統透過任何有效手段在使用者的真實電腦上完成工作的能力有多好」，這標誌著研究範式的根本性變化。

**Q2：現有的 GUI-only 電腦使用代理有哪些根本性的限制？**

A：現有的 GUI-only 電腦使用代理僅依賴螢幕截圖觀察和滑鼠鍵盤動作，這種限制使得它們無法利用模型既有的程式設計能力來處理任務。僅憑視覺回饋，模型難以處理需要精確文字操作、批次處理或複雜邏輯判斷的任務，因為這些操作在 GUI 中往往需要大量步驟且容易出錯。此外，GUI-only 代理在面對需要存取無障礙樹、shell 命令或應用程式 API 的場景時顯得力不從心，這些程式化介面往往能提供更直接、更可靠的互動方式。

**Q3：為什麼需要將前沿系統（如 GPT-6 Astra）的技術棧開放出來？**

A：將前沿系統的技術棧開放出來是必要的，因為 GPT-6 Astra 等系統的模型權重、完整提示設定、真實裝置框架、裝置控制 SDK 和執行軌跡均未公開，這嚴重限制了社群重現系統行為、比較替代設計的能力。封閉性使得研究者無法系統性地研究設計選擇和執行機制如何影響任務完成度和成本，特別是在真實裝置條件下的表現。OpenGCUA 透過開放完整技術棧，包括實作程式碼、提示詞、八款模型的評測軌跡、真實裝置框架和跨裝置 SDK，使社群能進行系統性的設計驗證和改進。

**Q4：OpenGCUA 的「程式碼執行」設計核心是什麼？它如何不同於傳統的 GUI 操作？**

A：OpenGCUA 的「程式碼執行」設計核心在於讓模型能夠在 Python 執行環境中撰寫程式，將 GUI 操作（如 PyAutoGUI）與 bash 命令等程式化操作組合成單一的模型輸出。這種設計讓中間結果能夠決定後續操作，例如模型可以執行程式碼讀取檔案內容、處理資料後再根據結果進行下一步 GUI 操作，從而實現傳統 GUI-only 代理難以達成的複雜工作流程。透過這種方式，模型可以直接運用其既有的程式設計能力來處理電腦互動任務，大幅提升效率與可靠性。

**Q5：什麼是「框架至模型決策轉移」（Harness-to-Model Decision Transfer）？為什麼這是一個重要的設計選擇？**

A：「框架至模型決策轉移」是 OpenGCUA 提出的一種設計原則，將原本由固定框架規則決定的觀察選擇和任務狀態判斷（例如何時擷取螢幕截圖、何時存取無障礙樹、何時更新任務進度）轉移給模型自行決定。這種設計選擇的重要性在於，傳統的固定框架規則難以適應多樣化的任務需求，而模型本身具備更強的任務理解能力，能根據當前任務狀態做出更合適的觀察和組織決策。透過讓模型掌控這些決策，代理能更靈活地處理不同類型的任務，並減少不必要的觀察動作所帶來的效率損耗。

**Q6：真實裝置框架的五層式架構是如何設計來回應真實裝置挑戰的？**

A：真實裝置框架採用五層式架構來系統性地回應真實裝置部署中的各種挑戰，包括共享控制、背景視窗互動、動態演進的使用者請求等基準測試無法完全捕捉的問題。這種分層設計將不同的功能關注點分離，使每一層都能專注於解決特定類別的真實裝置問題，例如裝置控制、狀態管理、錯誤恢復等。透過這種架構，框架能夠在使用者的真實電腦上穩定運行，並支援需要長期執行、跨應用程式協作的複雜任務，這是基準測試環境中通常不會出現的需求。

**Q7：OpenGCUA 在 OSWorld-v2 基準測試上的主要成果是什麼？**

A：在 OSWorld-v2 基準測試上，OpenGCUA 的完整配置在所有八款評測模型（包括 GPT-6 Astra 和 Claude Opus 5）上都提升了任務得分，平均部分得分提升了 +19.6 點。更值得注意的是，相較於批次僅 GUI 執行的基線方法，每任務的報告步數平均減少了 53.0%，這顯示出程式碼執行和決策轉移設計不僅提升了任務表現，也大幅提升了執行效率。這些結果證明了 OpenGCUA 的代理設計選擇具有跨模型的通用性，能為不同的前沿模型帶來一致的改進。

**Q8：程式碼執行消融實驗和框架至模型決策轉移消融實驗分別揭示了什麼？**

A：程式碼執行消融實驗透過比較啟用與停用程式碼執行的配置，揭示了程式碼執行對於任務完成的關鍵貢獻，證明讓模型運用其程式設計能力直接處理電腦互動能帶來實質的效能提升。框架至模型決策轉移消融實驗則驗證了將觀察選擇和任務狀態決策從固定框架規則轉移給模型能進一步改善表現，顯示模型在這些決策上比固定規則更為有效。這兩個消融實驗共同證明了 OpenGCUA 的兩個核心設計選擇——程式碼執行和決策轉移——都是促成最終效能改進的必要組成部分，而非冗餘設計。

**Q9：不同模型在真實裝置執行效率上的差異有多大？這意味著什麼？**

A：在四個真實 macOS 任務中，選定的 Qwen3.8-Max 執行所使用的報告推理詞元數是 GPT-6 Astra 的 19.4 倍，這顯示出不同模型在真實裝置執行效率上存在巨大差異。這種差異意味著，即使模型在基準測試上表現相近，在真實裝置上的實際部署成本和回應時間可能截然不同，對於產品化部署具有重要意義。這也凸顯了為何作者主張將效率作為「一等公民指標」——單純的任務成功率無法反映真實使用情境下的成本與使用者體驗。

**Q10：OpenGCUA 的跨裝置 SDK 如何支援跨電腦、行動裝置與瀏覽器的任務？**

A：OpenGCUA 的跨裝置 SDK 提供了一個通用的程式介面，讓代理程式能夠以統一的方式存取電腦、瀏覽器和行動裝置，從而支援跨越多種裝置的任務。這種設計使得開發者無需為每種裝置類型編寫獨立的控制邏輯，而是透過同一套 API 來協調不同裝置上的操作，大幅簡化了跨裝置任務的開發。對於需要在多個裝置間協調工作的場景（例如在電腦上處理文件後透過手機分享），這種統一介面提供了重要的基礎設施支援。

**Q11：將效率作為「一等公民指標」對實際產品部署有何影響？**

A：將效率作為「一等公民指標」對實際產品部署有深遠影響，因為它迫使設計者在追求任務成功率的同時，也必須考量執行成本、回應時間和資源消耗。在真實裝置上，使用者對延遲敏感且執行成本直接影響商業可行性，因此僅追求高任務得分而忽略效率的系統難以實際部署。OpenGCUA 透過程式碼執行、簡潔的模型推理和框架最佳化來系統性改善效率，這種設計哲學對於將電腦使用代理從研究原型推向實際產品至關重要。

**Q12：OpenGCUA 開源釋出的內容對學術界和工業界有何價值？**

A：OpenGCUA 開源釋出的內容對學術界和工業界都具有重要價值：學術界可以透過釋出的實作、提示詞和八款模型的評測軌跡進行可重現的研究，系統性地分析程式碼執行和決策轉移模式的效果；工業界則可以借鑑真實裝置框架和跨裝置 SDK 的設計，加速從基準測試到實際部署的轉換過程。特別是評測軌跡的釋出，使研究者能深入分析前沿模型的行為模式，這在過去因封閉性而無法實現。這種全面的開放策略有助於推動整個電腦使用代理領域的協作發展。

**Q13：當前 OpenGCUA 首次發布版本有哪些尚未涵蓋的部分？**

A：當前 OpenGCUA 首次發布版本尚未包含經過訓練的模型，這是專案路線圖中明確標示的後續工作重點。雖然釋出了代理設計、評測軌跡、真實裝置框架的初步版本和跨裝置 SDK，但完整的模型訓練、發布以及更全面的真實裝置評測環境（特別是在 macOS 上的基準測試）仍在開發中。此外，真實裝置框架和跨裝置 SDK 目前都是初步版本，需要在實際部署中持續改進和完善，以處理更廣泛的真實使用情境。

**Q14：從基準測試到真實裝置部署時，會遇到哪些基準測試無法捕捉的挑戰？**

A：從基準測試到真實裝置部署時，會遇到多項基準測試無法捕捉的挑戰，包括共享控制（使用者可能在代理執行任務時同時操作電腦）、與背景視窗的互動（任務可能受到非焦點應用程式的影響）、以及動態演進的使用者請求（任務需求可能在執行過程中改變）。此外，真實裝置上的硬體差異、系統設定多樣性、網路狀態波動等因素也會影響代理表現，這些都是標準化基準測試環境中通常不會出現的變數，需要框架層級的特殊設計來處理。

**Q15：OpenGCUA 專案的未來路線圖是什麼？社群如何參與？**

A：OpenGCUA 專案的未來路線圖從設計驗證階段逐步推進到模型發布階段，後續將釋出經過訓練的統一電腦與瀏覽器使用模型，並持續發展真實裝置評測環境，特別是針對 macOS 的基準測試。研究優先事項包括系統性改善 GCUA 執行效率、開發更全面的真實裝置評測方法，以及探索更廣泛的系統層級改進。社群可以透過貢獻程式碼、改進框架設計、分享評測結果、報告真實裝置使用案例等方式參與專案，共同推動通用電腦使用代理技術的開放發展。

## 實務應用指南

### 適用場景

**1. 企業內部桌面流程自動化**
針對 ERP、CRM、舊版內部系統等缺乏 API 的桌面應用，部署 OpenGCUA 代理執行重複性操作（如報表匯出、資料登錄、跨系統對帳）。由於採用程式碼執行與 GUI+CLI 混合操作，可在單一輸出中組合滑鼠點擊與 shell 指令，特別適合需要批次處理大量視窗操作的場景。

**2. 跨裝置任務編排（電腦、手機、瀏覽器）**
透過 OpenGCUA 提供的跨裝置 SDK，構建同時操作 macOS 桌面、Android 手機與瀏覽器的代理。例如：從手機截圖辨識發票 → 在桌面 Excel 整理 → 透過瀏覽器上傳至會計系統。SDK 提供統一程式介面，使代理程式無需為每個平台重寫控制邏輯。

**3. 軟體回歸測試與 UI 自動化**
將 OpenGCUA 整合至 CI/CD 流程，取代傳統基於座標的脆弱腳本。代理可根據視覺回饋動態調整操作路徑，並透過 AX tree 取得語意資訊，在應用程式介面變更時仍具備一定韌性。論文報告的 53.0% 步數縮減代表測試時間與 API 成本可同步下降。

**4. 個人數位助理與無障礙輔助**
為身心障礙者或高齡使用者部署代理，協助操作複雜軟體（如報稅系統、政府網站）。真實裝置框架支援共享控制與背景視窗互動，符合實際使用情境。

**5. 開發者工具與程式設計輔助**
代理可在 IDE、終端機、瀏覽器之間切換，協助完成從需求閱讀、程式碼搜尋、測試執行到 PR 提交的完整工作流。程式碼執行機制讓模型直接運用既有程式設計能力處理中間結果。

### 實作步驟建議

**步驟一：釐清代理邊界與決策權配置**
依據論文「框架至模型決策轉移」原則，明確劃分哪些觀察與任務狀態決策由框架處理、哪些交給模型。建議從保守配置開始（框架主導），再逐步將決策權轉移給模型，並以 OSWorld-v2 或自建基準量化每次調整的影響。

**步驟二：建置程式碼執行環境**
部署 Python runtime，整合 PyAutoGUI 與 bash 呼叫能力。確保沙箱具備足夠權限執行 GUI 操作（螢幕擷取、輸入模擬）但限制檔案系統與網路存取。論文中此設計使中間結果能決定後續動作，是效率提升的關鍵。

**步驟三：選擇並整合模型**
從論文中評測的 8 個模型出發，依任務特性選擇。需注意：Qwen3.8-Max 在真實 macOS 任務中使用 19.4 倍於 GPT-6 Astra 的推理詞元，效率差異顯著，選型時應同時考量品質與成本。

**步驟四：實作跨裝置 SDK 介面**
若需跨裝置操作，先定義 SDK 的統一抽象層（觀察、動作、狀態查詢），再為每個平台實作適配器（macOS、Windows、Android、瀏覽器）。論文將 SDK 與框架分離，便於獨立演進。

**步驟五：部署真實裝置框架並處理邊界情況**
實作五層式架構，特別關注共享控制、背景視窗、動態請求等基準測試無法完全捕捉的挑戰。建議先在內部團隊裝置試運行，蒐集失敗案例後再擴大部署。

**步驟六：建立效率監控儀表板**
將「效率作為一等公民指標」落實為系統設計：追蹤每任務報告步數、推理詞元數、API 成本、完成時間。設定警報閾值，當代理步數異常飆高時觸發人工審查。

**步驟七：迭代與社群貢獻**
將自建任務集、評測結果、框架改進回饋至 OpenGCUA 社群。論文明確將此定位為「持續進行中的專案」，單一組織難以覆蓋所有設計空間。

### 潛在風險與注意事項

**風險一：程式碼執行的安全邊界**
代理可執行任意 Python 與 bash，若沙箱配置不當，可能誤刪檔案或外洩資料。
*緩解措施*：採用最小權限原則，限制可寫入的目錄、網路出口白名單、敏感指令黑名單（如 `rm -rf`、`curl` 至外部網域）。所有執行程式碼應保留稽核日誌。

**風險二：真實裝置的非預期互動**
背景視窗、系統通知、其他使用者操作可能干擾代理，導致任務失敗或誤觸發動作。
*緩解措施*：實作專注模式（隱藏通知、鎖定輸入焦點）、定期截圖比對預期狀態、設置人工接管熱鍵。

**風險三：模型效率差異導致成本失控**
不同模型的推理詞元消耗差異可達 19.4 倍，若未監控，單月 API 費用可能遠超預期。
*緩解措施*：設定每任務詞元預算上限、優先選用效率較高的模型、對簡單子任務使用較小模型。

**風險四：基準測試與真實效能落差**
OSWorld-v2 改善 +19.6 點不代表真實裝置有相同幅度提升；基準無法完全捕捉共享控制、動態請求等挑戰。
*緩解措施*：在內部真實裝置上建立小型但具代表性的任務集，作為上線前的最終驗證。

**風險五：框架至模型決策轉移的權衡**
將過多決策交給模型可能降低穩定性；保留過多則失去彈性。
*緩解措施*：以消融實驗方法（論文 3.3.5 節）逐項評估每個轉移決策的效益與風險，建立組織內部的決策權配置指南。

**風險六：封閉模型依賴**
目前最佳表現仰賴 GPT-6 Astra 等封閉模型，模型政策變更或價格調整會直接影響系統。
*緩解措施*：維持多模型支援、追蹤 OpenGCUA 自身的模型訓練進度（論文路線圖將模型發布列為後續目標）。

### 與其他技術的整合建議

**與 RPA 平台整合**
OpenGCUA 可作為傳統 RPA（UiPath、Automation Anywhere）的補強層，處理需要視覺理解與動態決策的例外流程。建議以 RPA 處理結構化主流程，遇到無法定位元素時呼叫 OpenGCUA 代理。

**與 LLM 應用框架整合**
可整合 LangChain、AutoGen 等框架的代理編排能力，將 OpenGCUA 作為「電腦操作工具」註冊至現有代理。程式碼執行機制使其能與其他工具（搜尋、資料庫查詢）無縫組合。

**與測試自動化平台整合**
將 OpenGCUA 代理包裝為 Selenium、Playwright 的替代或補充，特別適用於桌面應用與混合 Web+Native 場景。53.0% 的步數縮減可直接轉化為 CI/CD 執行時間節省。

**與可觀測性系統整合**
將代理軌跡（截圖、動作、推理詞元）匯入既有日誌平台（如 Datadog、Elastic），建立任務級別的可追蹤性。論文中釋出的評測軌跡格式可作為整合參考。

**與裝置管理（MDM）整合**
企業部署時，需將真實裝置框架納入 MDM 政策，統一管理代理的權限、更新與稽核。跨裝置 SDK 的統一介面有助於在 MDM 框架內標準化代理行為。

### 給不同背景讀者的閱讀建議

**給初學者**
建議先閱讀第 2 章「通用電腦使用代理：定義與定位」，理解 GCUA 與傳統 GUI 代理的差異；再讀第 3.1 節「GUI 與 CLI 上的程式碼執行」，透過具體範例感受「中間結果決定後續動作」的設計理念。實作上可先在 OSWorld-v2 跑通論文的基準配置，再逐步替換為自有任務。

**給 AI 工程師**
重點研讀第 3 章「代理設計」，特別是 3.2 節「框架至模型決策轉移」的機制與消融實驗（3.3.5），理解哪些決策適合留在框架、哪些應交給模型。第 3.3.6 節「金錢與時間能買多少任務表現」對成本敏感的工程團隊尤為重要。實作時建議直接採用論文釋出的提示詞與評測軌跡作為起點。

**給研究者**
第 2.3 節「為何是現在：轉向程式碼執行的路線翻轉」與第 5 章「路線圖」提供了領域發展的脈絡與未來方向。建議關注「效率作為一等公民指標」此一主張（2.4 節），以及程式碼執行消融實驗（3.3.4）所揭示的設計空間。論文將模型發布列為後續工作，是值得追蹤的開源模型進展。

**給產品經理**
應聚焦第 1 章的問題轉變（從「模型如何操作 GUI」到「系統如何完成電腦上的工作」）與第 4 章「真實裝置通用電腦使用代理」，理解基準測試與真實部署的落差。第 4.3.3 節的初步真實裝置結果與案例研究（4.3.4）有助於評估技術成熟度與導入時程。建議將效率指標（步數、推理詞元）納入產品 KPI，而僅追求任務完成率。
