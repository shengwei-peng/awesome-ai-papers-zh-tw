## 摘要翻譯

代理系統使用大型語言模型（LLMs）來執行具體任務。先前的研究往往零碎地借用作業系統中的排程、快取或隔離等抽象概念，因此其所建構的機制缺乏共同基礎，且對代理系統兩種形式——工作流（Workflows）與代理（Agents）——的共享視角有限。我們建構一個能同時提供兩者的抽象機器。

我們將 LLM 視為預言機（Oracle），並以一條指令擴充雙堆疊下推自動機，該指令將整個堆疊作為查詢交給預言機，並將答案附加至同一堆疊。因此，該機器執行兩種計算：預言機的計算，以及我們稱之為 Priestess 的圖靈完備計算。程式僅對其附加內容的堆疊會自回歸地增長，正如代理的上下文一般。兩個對稱破缺——儲存中的 S 與轉移中的 T——使 Priestess 程式成為預言機所執行程式的作業系統，並使代理與工作流成為任務程式的兩種配置。

對於內部自回歸的預言機，在特定條件下，兩種計算會在每次回答結束時同步，並透過該同步我們對快取建模並分析排程。沒有任何對所有預言機皆成立的保證能固定兩種計算之間傳遞的內容，但此類保證確實能固定其邊界本身。

建構 V 將該機器適配至馮·紐曼電腦。為證明其可實現，我們提出 ArchNights——一個擴充的 RISC-V ISA 與一個 Linux 風格作業系統，於設計上實作該機器。ArchNights-SE 在 gem5 上作為電腦系統執行，當其將 LLM 作為預言機執行時即成為代理系統，並將開源。

代理系統屆時便能如電腦系統一樣被設計。隨著基礎的奠定與統一視角的建立，未來的研究便能共享不變量與界，且各附其條件。

### 核心貢獻（3～5點）
- 提出一個統一的抽象機器模型，將 LLM 視為預言機，並以雙堆疊下推自動機加上一條指令擴充之，使預言機計算與圖靈完備計算（Priestess）得以在同一框架中並存。
- 透過儲存中的對稱破缺 S 與轉移中的對稱破缺 T，將代理（Agent）與工作流（Workflow）統一詮釋為任務程式的兩種配置，並使 Priestess 程式扮演預言機所執行程式之作業系統的角色。
- 對內部自回歸的預言機，建立兩種計算於每次回答結束時同步的條件，並以此同步機制對快取建模、對排程進行分析，同時釐清跨越兩種計算之內容的邊界保證。
- 提出建構 V，將抽象機器適配至馮·紐曼電腦；並以 ArchNights（一個擴充的 RISC-V ISA 與 Linux 風格作業系統）及其 gem5 實作 ArchNights-SE 證明該機器可實現，開源後可供社群重現與延伸。
- 為代理系統提供一個奠基於電腦系統設計典範的統一視角，使後續研究得以共享不變量與界，並各自附帶成立條件。

### 適合對象
本論文最適合以下讀者閱讀：從事代理系統（agentic systems）與大型語言模型應用研究的學者與工程師，特別是關注代理框架（agent harness）、工作流引擎（workflow engine）、代理作業系統（agent OS）等基礎設施設計者；對形式化演算、圖靈機模型、計算理論有興趣的理論電腦科學研究者；以及從事 RISC-V ISA 擴充、gem5 模擬器實作、系統軟體設計的電腦系統與架構研究者。此外，對於希望理解「代理系統如何能如電腦系統一樣被嚴格設計」此一願景的讀者，本論文亦提供了具體的理論與實作藍圖。

## 深度分析

#### 方法論解析

本論文提出一個稱為 Oracle 2-PDA（O-2-PDA）的抽象機器，作為分析代理系統（agentic systems）的理論基礎。其方法論核心可拆解為四個層次：

**1. 相對化（Relativization）作為分離手段**

作者將大型語言模型（LLM）視為計算理論中的預言機（Oracle），並將其與其餘計算分離為黑盒。此一相對化步驟使 LLM 與外部程式的互動本身成為一台機器，從而將「模型即電腦」的隱喻形式化。相對化的關鍵在於：對於預言機的內部運作不做任何假設，僅規範其輸入輸出介面，這使得理論結論對任何具備該介面的預言機皆成立——無論是 LLM、人類，或未來的某種系統。

**2. 單一指令的設計哲學**

O-2-PDA 在標準雙堆疊下推自動機（two-stack pushdown automaton）的基礎上，僅新增一條指令 `oracles`：將整個堆疊 s 的內容交給預言機，並將答案附加至同一堆疊。此設計的精妙之處在於：

- **雙堆疊的圖靈完備性**：兩條堆疊使機器本身具備圖靈完備性，無需預言機即可表達任意可計算函數。
- **自回歸形式（autoregressive form）的湧現**：當程式僅對堆疊執行附加（append）操作時，預言機所見的歷史從一次呼叫到下一次呼叫以「查詢、答案、工具結果、查詢」的順序自回歸地增長——這正是 LLM 上下文的本質結構。作者強調此形式屬於「互動」而非「模型」，這是一個重要的概念區分。

**3. 兩次對稱破缺（symmetry breaking）**

O-2-PDA 本身在「O 堆疊」與「P 堆疊」之間是對稱的——兩者僅是顏色標籤，無結構性差異。作者透過兩次破缺賦予機器作業系統的層級：

- **儲存對稱破缺 S（storage breaking）**：決定預言機在何處可找到「程式」。在 O 堆疊上，預言機可找到可執行的程式；在 P 堆疊上，預言機僅能找到資料。此破缺類似於記憶體頁面的權限位元（permission bits），區分可執行頁與資料頁。
- **轉移對稱破缺 T（transition breaking）**：決定誰選擇下一個轉移。新增的 O 模式使機器反覆查詢同一個 O 堆疊並附加每次的答案，從而將預言機置於控制迴圈的中心。

兩次破缺共同使 Priestess 程式成為預言機所執行程式的作業系統，並自然產生兩種任務程式配置：Agent（預言機動態決定下一步）與 Workflow（預定義程式碼路徑）。

**4. 同步（synchronization）與邊界**

對於內部自回歸的預言機，兩種計算在每次答案結束時於特定條件下同步。此同步機制被用於建模快取（caching）與排程（scheduling）。作者特別指出：沒有任何對所有預言機皆成立的保證能固定兩種計算之間流動的具體內容，但這樣的保證能固定邊界本身。這是一個深刻的觀察——不變量（invariants）與界（bounds）應作用於邊界，而非內容。

**5. 建構 V：從抽象機器到馮·紐曼電腦**

建構 V 將 O-2-PDA 適配至馮·紐曼電腦（von Neumann computer），透過 ArchNights（一個擴充的 RISC-V ISA）與 Linux 風格的作業系統實現。ArchNights-SE 在 gem5 模擬器上作為電腦系統運行，當其將 LLM 作為預言機執行時，即成為代理系統。

#### 實驗數據解讀

本論文屬於理論基礎性質的工作，其「實驗」主要體現在兩個層面：

**1. 形式化驗證**

論文的實證內容並非傳統意義上的基準測試（benchmark），而是：
- 證明 O-2-PDA 的圖靈完備性（透過雙堆疊 PDA 的已知結果）
- 證明兩次對稱破缺產生預期的作業系統層級結構
- 證明自回歸形式在「僅附加」條件下自然湧現

這些屬於數學證明而非實驗數據，因此論文中沒有傳統的精確率、召回率、F1 等指標。

**2. ArchNights-SE 的系統實作驗證**

論文中提及 ArchNights-SE 在 gem5 上作為電腦系統運行，並在執行 LLM 作為預言機時成為代理系統。然而，從所提供的全文脈絡來看，具體的系統層級實驗數據（例如：指令週期數、快取命中率、排程延遲、吞吐量等）並未在引用的章節中呈現。這暗示該工作的實證部分可能：
- 仍在進行中（論文聲明 ArchNights 將開源）
- 屬於附錄或後續工作
- 或作者選擇將實作驗證留待未來工作

**3. 概念性實驗：對既有問題的重新框架**

論文將「快取」與「排程」等概念統一在一個框架下，這本身就是一種概念性實驗。具體而言：
- 對於 Agent，快取是程式保留並重用的上下文
- 對於 Workflow，快取是模型的注意力狀態（即 KV 快取）
- O-2-PDA 框架將兩者統一為「兩次呼叫之間共享前綴的區間」

雖然沒有量化數據，但此統一本身具有重要的理論價值。

**4. 限制與不足**

- **預言機假設的強度**：論文的結論依賴於「內部自回歸預言機」的假設。對於不具備此性質的預言機（例如：非自回歸模型、檢索增強系統），同步保證可能不成立。

- **與現代 LLM 架構的距離**：論文中對預言機的抽象雖然優雅，但現代 LLM 的特性（如：思維鏈、工具使用格式、系統提示）如何在 O-2-PDA 中精確表達，仍需進一步闡明。
- **效能分析的缺失**：作為一個圖靈機層級的抽象，O-2-PDA 對實際代理系統的效能預測能力尚未展示。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼這個問題在當前代理系統研究中特別重要？**

A：這篇論文要解決的核心問題是代理系統（agentic systems）缺乏統一的理論基礎，使得 Workflows 與 Agents 兩種形式各自發展、難以共享不變量與界。隨著大型語言模型成為開放式任務的實用執行器，代理系統迅速增多，但研究被兩朵雲所遮蔽：基礎（foundations）與統一（unification）。這個問題之所以重要，是因為若沒有共同基礎，每個新問題都需要新的類比才能被提出，導致機制之間難以陳述與驗證，快取的兩種觀點（程式的上下文 vs. 模型的 KV 快取）就是典型例子。

**Q2：現有方法（形式化演算與作業系統類比）為何無法提供令人滿意的統一基礎？**

A：現有方法分為兩類：形式化演算（如 λA、ZipperGen、LLMbda、智能演算）定義語言並證明其能力界限，但未說明什麼使一個部分成為另一部分的作業系統；結構性設計（如 AIOS、AgentOS、AOS、Quine）則透過與作業系統的類比建構系統，但類比的理論僅延伸到類比之處。兩類方法都產生了實際成果（如代理配置的 lint、經驗證的解譯器、運行中的執行環境），但它們建立在不同類比之上，缺乏共同語言來陳述與檢查機制，因此無法形成可共享的基礎。

**Q3：論文所說的「兩朵雲」分別指什麼？論文如何試圖同時驅散這兩朵雲？**

A：第一朵雲是基礎問題，形式化與結構性兩條路線各自發展，卻沒有共同的論述基礎；第二朵雲是統一問題，Workflows 與 Agents 的研究通常從其中一種形式出發，具體機制在一種形式中建構後便與另一種形式分開研究。論文透過建構一個抽象機器（Oracle 2-PDA）同時提供兩種形式來驅散這兩朵雲：藉由一條指令連接預言機與圖靈完備機器，再以兩次對稱破缺使其中一部分成為另一部分的作業系統，從而讓 Workflow 與 Agent 成為同一任務程式的兩種擺放方式。

**Q4：論文的核心理論構造 Oracle 2-PDA 是什麼？它如何運作？**

A：Oracle 2-PDA 是一個雙堆疊下推自動機，擴充了一條稱為 `oracles` 的指令，該指令將整個堆疊內容交給預言機（Oracle），並將答案附加回同一個堆疊。其計算因此分為兩部分：預言機內部的計算，以及圖靈完備的其餘計算（稱為 Priestess）。兩個堆疊使機器具備圖靈完備性，並讓兩種角色各有自己的堆疊（O 堆疊與 P 堆疊）；當程式只對堆疊進行附加時，預言機所見的歷史會以自迴歸方式增長，正如模型的上下文一般。

**Q5：兩次對稱破缺（S 與 T）分別是什麼？為何它們對建構作業系統層級關係至關重要？**

A：儲存對稱破缺 S 決定預言機在哪裡能找到程式：在 O 堆疊（Oracle 堆疊）上預言機可找到程式，在 P 堆疊（Priestess 堆疊）上預言機只會看到資料。轉移對稱破缺 T 決定誰選擇下一個轉移，它加入一個 O 模式，使機器反覆查詢同一個 Oracle 堆疊並附加每次的答案。兩次破缺共同使 Priestess 程式成為預言機所執行程式的作業系統，並讓 Agent 與 Workflow 成為同一任務程式的兩種擺放方式，從而將作業系統與被管理程式的關係形式化。

**Q6：什麼是 Priestess？它與 Oracle 的關係為何？**

A：Priestess 是 Oracle 2-PDA 中圖靈完備的那部分計算，也就是負責查詢預言機的其餘機器。它與 Oracle 的關係是分工的：Oracle 負責產生答案，Priestess 負責管理堆疊、執行轉移、並決定何時呼叫 Oracle。經過兩次對稱破缺後，Priestess 程式成為 Oracle 所執行程式的作業系統，這種關係使得代理系統能像電腦系統一樣被設計，每個設計選擇都能從電腦系統的理論或經驗出發加以論證。

**Q7：論文提出了哪些實作或評估方式來驗證理論構造？**

A：論文提出 ArchNights 作為擴充的 RISC-V ISA 與 Linux 風格的作業系統，透過設計實作該機器；其中 ArchNights-SE 在 gem5 模擬器上作為電腦系統運行，並在運行 LLM 作為 Oracle 時成為代理系統。論文並非以傳統基準測試為主，而是以「可實現性」（realizability）作為驗證目標，證明抽象機器能夠被實作為真實的計算系統，並將開源釋出供社群使用與擴充。

**Q8：ArchNights-SE 在 gem5 上的關鍵結果是什麼？**

A：ArchNights-SE 的關鍵結果是證明建構 V 能成功將抽象機器適配至馮·紐曼電腦，具體展現為一個擴充的 RISC-V ISA 與 Linux 風格作業系統。它在 gem5 上作為電腦系統運行，並在搭載 LLM 作為 Oracle 時轉變為代理系統，顯示同一個系統能同時服務兩種角色。這項實作證明了理論構造不僅是紙上設計，而是可被工程化、可被社群檢驗與延伸的實體系統。

**Q9：論文進行了哪些分析或消融式研究來支撐其論點？**

A：論文分析了在內部自迴歸預言機（internally autoregressive Oracles）下，兩種計算如何在每次答案結束時於特定條件下同步，並透過這種同步來模型化快取與分析排程。論文也區分了「對所有預言機都成立的保證」與「對特定預言機成立的保證」，指出前者雖無法固定跨計算的具體內容，但能固定邊界本身。這種條件式的分析取代了傳統的消融實驗，提供了理論上的清晰邊界。

**Q10：此模型如何應用於代理系統中的快取問題？**

A：透過同步分析，論文模型化了快取：程式的快取（保留並重用的上下文）與模型的快取（KV 快取、注意力狀態）這兩種觀點，在統一機器中對應到同一個區間，即兩次共享前綴的呼叫之間。自迴歸形式的堆疊增長正反映了模型上下文的增長方式，因此兩種快取觀點得以在同一框架下被陳述與比較，解決了過去兩者各說各話的問題。

**Q11：此模型如何應用於排程問題？**

A：同樣透過同步分析，排程也被模型化：無論是 Agent 形式中決定工具呼叫執行時如何處理任務狀態，還是 Workflow 形式中根據執行時間決定保留或預取哪些步驟前綴，兩者都針對同一區間。統一機器使得排程決策能以共享的不變量與界來推理，避免過去兩種形式各自發展出重複卻不相容的排程機制。

**Q12：這項研究對代理系統設計的實務影響是什麼？**

A：實務上，代理系統可以像電腦系統一樣被設計：每個設計選擇都能從電腦系統的理論（如作業系統、編譯器、計算理論）或經驗出發加以論證，而非僅憑類比或臨時的工程權宜。ArchNights 提供了具體的平台，讓研究者能在統一的 ISA 與作業系統上實驗 Workflow 與 Agent 的組合，並以開源方式讓社群共享不變量、界與條件，從而提升整個領域的可驗證性與可累積性。

**Q13：論文承認的限制有哪些？**

A：論文承認，對所有預言機都成立的保證無法固定跨計算的具體內容（即哪些資料會在 Oracle 與 Priestess 之間流動），但這樣的保證確實能固定邊界本身。這意味著模型在普遍性上有所取捨：放棄對內容的強保證以換取對邊界的強保證。此外，兩種計算的同步僅在內部自迴歸預言機的特定條件下成立，對不滿足條件的預言機，快取與排程的分析可能不適用。

**Q14：此模型可能遭遇的失敗案例或邊界情況為何？**

A：當預言機不具備內部自迴�性，或不滿足同步所需的特定條件時，兩種計算無法在每次答案結束時正確同步，導致快取與排程的分析失效。此外，若預言機的語意無法被明確定義（例如人類的回答若無可解析的語意），則模型無法將其納入 Oracle 角色，這也是論文強調「只要能為人類的詞語定義語意，人與模型在此機器上同質」的原因。

**Q15：論文為未來工作指出了哪些方向？**

A：論文指出，有了統一的基礎與視角，未來工作可以共享不變量與界，每個不變量與界都附帶其成立條件，從而讓代理系統研究從零散類比走向可累積的科學。具體方向包括：在 ArchNights 上實驗更多 Workflow 與 Agent 的組合、探索不同預言機下的同步條件、將更多電腦系統概念（如行程隔離、記憶體管理）形式化地引入代理系統設計，以及透過開源釋出讓社群共同驗證與擴充這套框架。

## 實務應用指南

### 適用場景

1. **統一代理框架設計**：建構同時支援工作流與代理模式的單一系統，避免兩種形式各自維護重複的快取、排程與隔離機制；可將現有 n8n、Dify、Coze 等工作流引擎的節點實作為 Priestess 程式，節點內的代理呼叫實作為 Oracle 查詢。
2. **多代理協作平台**：在需要多個 LLM 代理同時運作的場景（如程式碼審查、客服分流、研究助理），透過 Priestess 統一管理代理間的上下文共享、KV 快取與資源分配，利用同步點實作跨代理的排程。
3. **安全敏感的代理應用**：在金融、醫療或法律場景中，採用 Quine 風格的 POSIX 行程隔離，確保模型輸出與人類輸入之間的明確安全邊界，並透過形式化演算（λA、LLMbda）驗證關鍵不變量。
4. **可驗證的代理系統**：需要對代理行為進行形式化驗證的場景（如符合法規要求的 AI 系統），利用 AgentSpec 等規則語言在執行時間強制語意，並以 Calculus of Intelligence 等演算證明在特定條件下的界。
5. **邊緣裝置上的代理部署**：在資源受限的裝置上，利用 ArchNights 的 RISC-V 擴充實現輕量級代理系統，透過 ISA 層級的支援降低軟體堆疊開銷，並以 gem5 模擬器進行早期驗證。

### 實作前置條件

**資料需求**：
- 目標 LLM 的 API 或本地部署權重（支援串流輸出以便觀察自回歸形式）
- 領域任務的範例對話與工具呼叫日誌，用於設計 Oracle 查詢格式
- 既有代理框架的程式碼（如 Claude Code、Codex、Pi Agent、DeepSeek Harness）作為參考實作
- 目標工作流的節點定義與編排規格

**運算資源**：
- gem5 模擬器執行 ArchNights-SE 的開發環境（建議 64GB 以上 RAM）
- 至少一張具備足夠 VRAM 的 GPU 用於本地 LLM 推論
- RISC-V 交叉編譯工具鏈（GCC/LLVM 的 RISC-V 後端）
- 足夠的磁碟空間儲存模擬追蹤與日誌

**技能需求**：
- 計算理論基礎：圖靈機、下推自動機、可計算性
- 作業系統概念：行程隔離、系統呼叫、記憶體管理
- RISC-V 指令集架構知識
- LLM 推論管線理解：KV 快取、注意力狀態、串流解碼
- 形式化方法經驗（call-by-push-value、λ 演算）為加分項

### 實作步驟建議

1. **理解抽象機器模型**：先在紙上或小型模擬中實作 O-2-PDA，確認「Oracle 查詢」指令的語意——將整個堆疊內容交給 Oracle，並將回答附加至同一堆疊；驗證雙堆疊賦予的圖靈完備性。
2. **定義雙對稱破缺**：實作儲存破缺 S（決定 Oracle 在哪個堆疊可找到程式）與轉移破缺 T（決定誰選擇下一個轉移），這是將 Priestess 提升為作業系統的關鍵步驟。
3. **設計 Oracle 介面**：將目標 LLM 包裝為 Oracle，定義查詢與回答的解析語意，確保自回歸形式成立（程式僅附加、不修改堆疊）；實作串流解析器以支援內部自回歸 Oracle。
4. **建構 ArchNights ISA 擴充**：在 RISC-V 基礎上新增支援 O-2-PDA 指令的擴充，定義暫存器、堆疊與 Oracle 呼叫的硬體介面；確保與既有 RISC-V 工具鏈相容。
5. **實作 ArchNights-SE 核心**：在 gem5 上實作 Linux 風格的作業系統，提供行程隔離、系統呼叫與 Oracle 註冊機制；保留 POSIX 介面以利移植。
6. **整合 LLM 作為 Oracle**：將 LLM 推論引擎接入 ArchNights-SE，驗證同步條件（內部自回歸 Oracle 在每次回答結束時與 Priestess 同步）；實作同步點的快取與排程鉤子。
7. **建構快取與排程層**：利用同步點實作跨 Oracle 與 Priestess 的統一快取，統一處理上下文快取與 KV 快取；設計排程器處理多代理場景的優先順序與資源分配。
8. **形式化驗證**：使用 λA 或 LLMbda 等演算為關鍵元件提供語意，在 CI/CD 流程中證明特定條件下的不變量與界。
9. **效能基準測試**：在 gem5 上量測抽象機器的執行時間與記憶體開銷，與原生代理框架比較，識別最佳化機會。

### 潛在風險與注意事項

- **Oracle 黑盒特性**：論文明言「沒有任何對所有 Oracle 都成立的保證能固定跨兩個計算的內容」，因此不能假設 LLM 會遵守特定語意；必須設計容錯機制處理 Oracle 的任意輸出，包括提示注入攻擊。
- **同步條件脆弱**：內部自回歸 Oracle 的同步僅在特定條件下成立，若 LLM 採用非自回歸解碼、批次處理或串流中斷，同步點可能錯位，導致快取與排程失效。
- **自回歸形式假設**：若程式修改而非僅附加堆疊，Oracle 看到的歷史就不再是線性增長，可能破壞整個抽象的合理性；需在編譯器或執行時間強制此不變量。
- **效能開銷**：雙堆疊與 Oracle 呼叫的抽象可能引入顯著的執行時間與記憶體開銷，需仔細評估在生產環境的可行性；gem5 模擬速度遠低於真實硬體，開發與除錯週期可能拉長。
- **安全邊界依賴保證**：論文中安全邊界由「保證」定義，但保證本身依賴 Oracle 的行為；若 Oracle 被提示注入攻破壞，邊界即失效；需設計多層防禦機制。
- **RISC-V 生態成熟度**：相較 x86 與 ARM，RISC-V 的工具鏈與系統軟體生態仍在發展，可能遇到相容性問題；硬體支援有限，需依賴模擬器驗證。
- **抽象洩漏風險**：當 Oracle 的實際行為與抽象機器的假設不符時（例如 LLM 產生幻覺或違反語意），抽象可能「洩漏」導致系統行為不可預測；需設計監控與降級機制。

### 與其他技術的整合建議

- **與既有代理框架整合**：可將 Claude Code、Codex、Pi Agent、DeepSeek Harness 等框架的執行模型映射至 O-2-PDA，將其工具呼叫與上下文管理視為 Oracle 查詢，逐步遷移至 ArchNights-SE；保留既有 API 以降低遷移成本。
- **與工作流引擎整合**：n8n、Dify、Coze 等工作流引擎的節點可實作為 Priestess 程式，節點內的代理呼叫則實作為 Oracle 查詢；利用統一視角消除兩種形式間的重複實作。
- **與 Linux 整合**：ArchNights-SE 設計為 Linux 風格作業系統，可作為 Linux 的延伸或獨立發行版，保留既有系統呼叫介面以利移植；參考 Quine 的設計，將代理實作為 POSIX 行程。
- **與 RISC-V 工具鏈整合**：利用 GCC/LLVM 的 RISC-V 後端擴充 ArchNights 指令，確保編譯器支援新指令的程式碼生成；參與上游社群以利長期維護。
- **與形式化工具整合**：將 λA、ZipperGen、LLMbda、Calculus of Intelligence 等演算的語意檢查器整合至 CI/CD 流程，在部署前驗證代理程式的關鍵不變量；使用 AgentSpec 在執行時間強制規則。
- **與 KV 快取系統整合**：論文中指出 KV 快取與上下文快取是同一現象的兩面，可設計統一介面同時管理兩者，避免重複實作；參考 FMOS 的虛擬化條件設計介面保證。
- **與 AIOS、AgentOS、AOS 整合**：這些系統各自從作業系統類比出發，可將其抽象映射至 O-2-PDA，評估在統一框架下的相容性與效能差異。

### 給不同背景讀者的閱讀建議

**給初學者**：建議從第 1 節「Introduction」開始，理解代理系統的兩種形式（工作流與代理）為何難以統一，以及「兩朵雲」（基礎與統一）如何阻礙研究進展。接著閱讀第 1.2 節的「一條指令、兩個對稱破缺」以掌握核心直覺，暫時跳過形式化細節，重點在於理解「Oracle + 雙堆疊」如何自然產生自回歸形式，以及為何這與代理的上下文增長相似。

**給 AI 工程師**：應聚焦於第 2、3 節的抽象機器定義，理解 O-2-PDA 的指令語意、雙堆疊的角色分工，以及儲存破缺 S 與轉移破缺 T 如何將 Priestess 提升為作業系統。接著閱讀第 6 節的 ArchNights 設計，思考如何將現有代理框架映射至此抽象，並評估在生產環境中實作的可行性與效能取捨；附錄 A 的術語定義有助於與團隊建立共同語言。

**給研究者**：應仔細研讀第 3 節的對稱破缺構造、第 4 節的同步條件分析，以及第 5 節對「無 Oracle 通用保證」的討論。這些是論文最具原創性的理論貢獻，也是後續研究可延伸的方向，例如放寬同步條件、探索其他可計算性模型、或證明特定 Oracle 類別下的新不變量；附錄中的形式化細節值得仔細推敲，並與 λA、LLMbda 等既有演算比較。

**給產品經理**：建議先讀摘要與第 1 節，掌握論文要解決的問題（兩朵雲）與提出的方案（統一抽象機器 + ArchNights）。重點關注第 6 節的 ArchNights-SE 實作計畫，評估其作為開源基礎設施的成熟時程與對現有產品的潛在影響；可將此論文視為「代理系統的作業系統理論」的起點，思考自家產品在快取、排程、安全邊界等面向是否可受益於統一框架，以及何時值得投入資源進行概念驗證。
