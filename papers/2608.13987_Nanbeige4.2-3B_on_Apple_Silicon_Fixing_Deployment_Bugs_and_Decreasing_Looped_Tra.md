## 摘要翻譯

Nanbeige4.2-3B 是一款 30 億參數的 agentic model（智慧體模型），採用 Looped Transformer（LT，迴圈式 Transformer）架構，重複使用同一層堆疊進行第二次 forward pass（前向傳播），在不增加額外參數的情況下提升 effective depth（有效深度）。我們在 Apple Silicon（蘋果晶片）上以 MPS（Metal Performance Shaders）後端進行評估，發現五個獨立的 bug（錯誤）導致釋出的 checkpoint（檢查點）無法透過 Hugging Face transformers out of the box（開箱即用）（包括一個 silently-zeroed（靜默歸零）的 RoPE buffer（RoPE 緩衝區），以及對已移除的 transformers cache APIs（快取 API）的呼叫）。此外，我們指出即使修復這些錯誤，仍不足以執行 agentic tasks（智慧體任務），因為 LT 為達成 parameter efficiency（參數效率）所採用的層重複使用策略會使 peak attention memory（峰值注意力記憶體）實際上翻倍。因此，我們提出一種 chunked-prefill strategy（分塊預填充策略），以緩解隨之而來的記憶體容量懲罰，在 32 GB shared memory（共享記憶體）上，將可允許的 context width（上下文寬度）延長為原本的 2.7 倍。然而，即使記憶體開銷已降低，我們發現仍需額外修補才能讓 Nanbeige4.2-3B 正常運作；待 system prompt（系統提示詞）與 MPS 原生記憶體錯誤皆獲解決後，才得以在標準 MCP（Model Context Protocol，模型上下文協定）與 tool-calling（工具呼叫）基準測試上進行可靠評估。在 MCPMark 的部分資料中，除錯後的模型最多可完成 30% 的真實 agentic tasks（智慧體任務）（原本為 0%），而在 BFCL（Berkeley Function Calling Leaderboard，函式呼叫評測榜單）上，single tool calls（單一工具呼叫）表現近乎完美（然而多數 multi-tool tests（多工具測試）仍失敗）。我們釋出修補後的 checkpoint（檢查點）、system prompt（系統提示詞）最佳化工具與評估框架，詳見 https://github.com/johnhalloran321/Nanbeige4.2-3B-mps-fix。

### 核心貢獻（3～5點）
- 修復五個獨立 bug，使 Nanbeige4.2-3B 的 checkpoint（檢查點）能透過 Hugging Face transformers 在 MPS 上開箱即用。
- 提出 chunked-prefill strategy（分塊預填充策略），降低 LT 層重複使用造成的 peak attention memory（峰值注意力記憶體）翻倍問題，於 32 GB shared memory（共享記憶體）上將 context width（上下文寬度）延長為原本的 2.7 倍。
- 修補 system prompt（系統提示詞）與 MPS 原生記憶體錯誤，讓模型可在 MCP 與 tool-calling（工具呼叫）基準上可靠評估。
- 在 MCPMark 子集上達成最多 30% 真實智慧體任務完成率（原為 0%），並在 BFCL 的 single tool calls（單一工具呼叫）上接近完美，但 multi-tool tests（多工具測試）仍多數失敗。
- 釋出修補後的 checkpoint（檢查點）、system prompt（系統提示詞）最佳化工具與評估框架。

### 適合對象
對在蘋果晶片 / MPS 上部署小型語言模型、迴圈式 Transformer 記憶體最佳化、智慧體與工具呼叫評測感興趣的研究者與工程師；特別是需處理開箱即用部署問題、RoPE / KV cache 相容性，以及邊緣裝置記憶體限制的實務開發者。

## 深度分析

#### 方法論解析

本研究並非提出全新的模型架構，而是針對 **Nanbeige4.2-3B** 這個以 **Looped Transformer（LT，迴圈式 Transformer）** 為核心的 3B 參數智慧體模型，進行一連串「部署導向」的除錯與記憶體最佳化。整體方法論可拆解為四個層次：**初始部署錯誤修復**、**LT 記憶體瓶頸緩解**、**系統提示詞（system prompt）行為修正**，以及 **MPS（Metal Performance Shaders）** 原生記憶體問題的處理。

首先，作者透過在 Apple Silicon 上直接載入官方檢查點（checkpoint），獨立確認了五個導致模型無法開箱即用（out of the box）運作的錯誤：

1. **RoPE buffer（RoPE 緩衝區）靜默歸零（silently-zeroed）**：這是最關鍵的錯誤。`inv_freq` 緩衝區在載入時被設為全零，且由於 `persistent=False` 與 meta-device 載入機制的交互作用，直到第一次前向傳播（forward pass）前都未被重新填充。這使得 **RoPE（Rotary Position Embedding，旋轉位置編碼）** 完全喪失位置資訊（positional information），模型雖能生成流暢文字，卻對語詞順序（token order）毫無概念。這類錯誤不會拋出例外，極難察覺。
2. **RoPE 組態分派 KeyError（鍵值錯誤）**：自訂建模程式碼對 RoPE 型別的 dispatch 邏輯有誤，對部分合法組態值會在模型建構階段就引發 `KeyError: 'type'`，這並非 MPS 專屬問題。
3. **Cache API sentinel 不匹配**：直接呼叫 `forward()` 並使用預設 `past_key_values=None` 時，會呼叫目前 transformers 版本中已移除的 `DynamicCache.from_legacy_cache(...)`，導致 `AttributeError`。
4. **Position-IDs 重新裁剪**：在 MPS 上執行 `generate()` 時，自訂注意力程式碼對 `position_ids` 的處理會引發 `mps.matmul` 維度不一致的 Metal assertion，造成無法捕捉的 SIGABRT 崩潰，此問題在 CPU 上不會重現。
5. **Tied-weights 鍵格式不相容**：權重綁定的鍵命名慣例與 transformers 的 `save_pretrained()` 不相容，即使模型能跑也無法重新序列化。

這五項修復採用 **sibling-file monkeypatching（同目錄檔案 monkeypatching）** 的方式完成，優點是不會修改已快取的 transformers 套件檔案，便於追蹤與重現。然而，修復後模型在智慧體任務（agentic tasks）上仍不可行，原因在於 LT 的層重複使用策略：雖然參數量維持 3B，卻在單次前向傳播中將同一組 L 層執行兩次，導致峰值注意力記憶體（peak attention memory）加倍。對於需要長推理軌跡（reasoning traces）的智慧體任務，這在 32 GiB 共享記憶體（shared memory）的 Apple Silicon 上會迅速造成記憶體不足（OOM，out-of-memory）。

為此，作者提出 **chunked-prefill strategy（分塊預填充策略）**：不再一次性對整段提示計算完整的 `(prompt_len × prompt_len)` 注意力分數，而是將提示切成固定大小（預設 256 tokens）的區塊，逐塊前向傳播並遞增地擴展 **DynamicCache**，最後再將剩餘部分交給 `generate()` 進行解碼。這種做法將原本每個迴圈都需重複配置的完整二次方注意力張量，轉換為多次較小規模的 KV cache 累積運算，從而降低記憶體峰值。

即便如此，模型仍暴露出兩個額外缺陷：其一，Nanbeige4.2-3B 內建的工具使用系統提示詞（tool-use system prompt）會在呼叫者傳入任何 system message 時被「替換」而非「合併（merged）」，導致工具呼叫能力被靜默關閉；其二，MPS 發生 OOM 後，服務程序（serving process）的可用記憶體預算（memory budget）會被永久劣化，直到在 MCPMark 評測中才浮現。最終，作者必須同時處理這五項初始錯誤、分塊預填充演算法、系統提示詞修正與 MPS 專屬 OOM 修復，才能實現可複現評估（reproducible evaluation）。

#### 實驗數據解讀

本研究的實驗結果主要分為兩大類：**記憶體與上下文長度能力**，以及**智慧體與工具呼叫基準測試表現**。

在記憶體方面，作者報告在 32 GiB 共享記憶體的 Apple Silicon 上，chunked-prefill 能將可允許的上下文寬度（context width）延伸約 **2.7 倍**。這是一個顯著的系統層級改進，因為它直接決定了模型能否處理包含長篇系統提示、工具描述與多輪對話歷史的 agentic tasks。值得注意的是，這個數字並非來自參數量減少或量化，而是來自對 LT 注意力記憶體峰值的重新調度，顯示推論階段的演算法設計與模型架構同等重要。

在智慧體評測方面，數據呈現強烈的對比：

- **MCPMark（Model Context Protocol 評測基準）子集**：原始檢查點完全無法完成任何真實智慧體任務（0%），而除錯後的模型可完成高達 **30%**。從相對進步來看這是巨大的躍升，證明前述錯誤確實嚴重掩蓋了模型的真實能力；但從絕對表現來看，30% 仍屬偏低，顯示 Nanbeige4.2-3B 在複雜、多步驟的智慧體場景中仍有明顯局限。
- **BFCL（Berkeley Function Calling Leaderboard）**：模型在單一工具呼叫（single tool calls）上表現接近完美，但在多工具測試（multi-tool tests）中卻失敗了大多數案例。這項結果具有重要意涵：模型對工具 schema 的理解與單步函式呼叫格式掌握良好，這可能來自其訓練資料中豐富的工具使用範例；然而一旦需要規劃、組合或依序呼叫多個工具時，其推理與長程狀態追蹤能力便不足。

綜合來看，實驗數據描繪出一個「被錯誤埋沒的潛力模型」：修復後確實能執行部分 agentic tasks，但 LT 架構帶來的記憶體壓力與多步推理瓶頸，使其難以與官方模型卡（model card）所宣稱的、相較於 Qwen3.5-4B / Qwen3.5-9B 的競爭力完全對應。

#### 與現有研究的比較

本研究在定位上介於「模型部署工程」與「架構分析」之間，與以下幾類現有研究形成對比：

首先，相較於原始 **Looped Transformer（LT）** 研究（Bae et al., 2026）強調的參數效率（parameter efficiency）與有效深度（effective depth）提升，本論文揭示了 LT 在實際邊緣部署中的隱藏成本：雖然預訓練時參數量較少，但推論時的峰值注意力記憶體會加倍。這補充了既有文獻對 LT 的評估視角——過往多聚焦於模型品質與參數規模的權衡，較少討論在統一記憶體架構（如 Apple Silicon）上的可行性。

其次，與官方模型卡宣稱的 Qwen3.5-4B / Qwen3.5-9B 比較結果相比，本研究指出這些數字在 MPS 上無法直接重現，因為原始檢查點本身就無法正常運作。這凸顯了「模型能力」與「模型可部署性」之間的落差：一個在紙面上表現優異的模型，若無法在終端裝置上正確載入，其實際價值將大打折扣。

再者，與其他針對小型語言模型（SLM，small language model）的部署研究相比，本論文特別強調「靜默正確性錯誤」（如 RoPE buffer 被靜默歸零）而非單純的效能崩潰。這類錯誤比明顯的例外更危險，因為它會讓使用者誤以為模型正常運作，實際上卻輸出位置不一致的結果。此外，作者也罕見地處理了 system prompt 被替換而非合併的語義層級問題，以及 MPS OOM 後記憶體預算永久劣化的系統層級問題。

然而，本研究也存在若干限制：

- **通用性有限**：實驗主要針對 Apple Silicon / MPS 環境，雖然部分錯誤（如 RoPE config dispatch、cache API 不匹配）並非 MPS 專屬，但記憶體最佳化與 OOM 修復的結論未必直接適用於 CUDA 或其他後端。
- **未與其他記憶體節省技術比較**：例如未探討 **FlashAttention**、量化（quantization）、KV cache 壓縮或投機解碼（speculative decoding）與 LT 的結合效果。
- **絕對表現仍偏低**：即使經過完整修復，MCPMark 上 30% 的成功率與 BFCL 多工具測試的多數失敗，顯示模型在智慧體能力上仍有顯著提升空間。
- **chunked-prefill 的時間成本**：雖然降低記憶體峰值，但將預填充階段拆成多次前向傳播，可能增加延遲，論文中對延遲—吞吐量權衡的討論較少。

#### 可重現性評估

本研究在可重現性（reproducibility）方面的表現相當扎實，主要體現在以下幾點：

- **開源釋出完整**：作者釋出了修補後的檢查點、系統提示詞最佳化器（system prompt optimizer）以及評測腳本，存放於 GitHub 倉庫 `johnhalloran/Nanbeige4.2-3B-mps-fix`。
- **修復方式透明**：所有修復均透過 sibling-file monkeypatching 實作，並提供完整 diff 與重現腳本，位於倉庫的 `patch/` 目錄中。這種做法避免了修改 transformers 函式庫內部檔案，降低了環境相依性。
- **錯誤定位精確**：論文 Table 1 詳列每個錯誤在未修改 `modeling_nanbeige.py` 中的行號、觸發條件與錯誤訊息或症狀，並標明使用 `transformers==5.8.1`。這對於希望追蹤問題根源的研究者極具價值。
- **硬體與環境說明清楚**：實驗在 Apple Silicon、32 GiB 共享記憶體上進行，使用 bf16（bfloat16）格式，這些資訊有助於他人複現記憶體相關結果。

不過，可重現性仍有幾個潛在弱點：

- **transformers 版本鎖定**：論文明確使用 `transformers==5.8.1`，但未來 transformers 版本更新可能再次破壞相容性，而修補檢查點的長期維護狀況尚不明朗。
- **MPS OOM 修復細節不足**：摘要與內文提到存在 MPS 專屬 OOM 修復，但 excerpt 中未詳細說明其具體機制，需依賴倉庫程式碼才能完整理解。
- **評測子集定義不明**：MCPMark 上報告的是「子集」結果，但未清楚說明選取子集的標準與完整資料集上的表現，可能影響結果的泛化解讀。
- **尚未經同儕審查**：此為 arXiv 預印本，未經正式同儕審查，部分結論與數據仍需社群進一步驗證。

#### 未來研究方向

基於本研究的發現，未來可從以下幾個方向延伸：

1. **跨後端與跨架構的 chunked-prefill 泛化**：將分塊預填充策略擴展至其他採用權重共享或迴圈層的架構，並在 CUDA、CPU 等後端驗證其效果，建立更通用的記憶體—效能權衡框架。
2. **結合記憶體高效注意力機制**：將 FlashAttention、記憶體高效注意力（memory-efficient attention）或 KV cache 量化與 LT 結合，進一步降低二次方注意力成本，使長上下文智慧體任務在邊緣裝置上更可行。
3. **自動化靜默錯誤檢測**：針對 remote-code checkpoint 開發靜態分析或執行時斷言工具，自動偵測 RoPE buffer 歸零、system prompt 被覆蓋、cache API 不相容等靜默錯誤，提升開源模型生態的可靠性。
4. **強化多工具推理能力**：針對 BFCL 多工具測試的失敗模式，設計專門的多步規劃與工具組合微調資料，或改進 system prompt 合併策略，以提升模型在複雜 agentic tasks 上的成功率。
5. **MPS 與統一記憶體的服務化研究**：深入探討 MPS 記憶體分配器在 OOM 後的行為，設計具備記憶體預算恢復與彈性排程的邊緣推論服務框架，讓 Apple Silicon 能更穩定地承載長上下文模型。
6. **更廣泛的基準測試**：在完整 MCPMark、SWE-bench、WebArena 等更多智慧體與工具使用基準上進行評估，並與同參數量級的非迴圈模型進行控制變因比較，以釐清 LT 在 agentic 場景中的真實優劣。
7. **延遲—吞吐量權衡分析**：系統性量化 chunked-prefill 在不同區塊大小、序列長度與硬體配置下的延遲與記憶體節省，為生產環境中的參數調校提供指引。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**

A：這篇論文聚焦於讓 Nanbeige4.2-3B 這個 3B 參數的迴圈式 Transformer（Looped Transformer，LT）智慧體模型，能夠在 Apple Silicon 的 MPS 後端上穩定且可複現地執行。作者發現官方釋出的檢查點無法開箱即用，會因為五個獨立的部署錯誤而載入失敗或靜默產生錯誤輸出。此外，即使修復了這些錯誤，LT 架構為了參數效率而重複使用層所導致的雙倍峰值注意力記憶體，仍然會讓智慧體任務所需的長上下文無法在 32 GiB 共享記憶體上運行。

**Q2：為什麼現有的直接使用 Hugging Face transformers 載入方式會失敗？**

A：直接使用 `AutoModelForCausalLM.from_pretrained(..., device="mps")` 會遇到五個彼此獨立的錯誤，包括 RoPE 緩衝區被靜默歸零、RoPE 設定分派出現 KeyError、呼叫已被移除的 cache API、MPS 上 position_ids 重新裁剪引發的硬崩潰，以及 tied-weights 鍵格式導致無法重新序列化。其中 RoPE 緩衝區歸零是最具欺騙性的問題，因為它不會拋出例外，只會讓模型在完全沒有位置資訊的情況下產生流暢但語意不連貫的輸出。這些錯誤分別發生在模型載入、第一次前向傳播、直接呼叫 forward、generate 階段以及 save_pretrained，因此單一修補無法讓模型正常運作。

**Q3：解決這個問題為什麼對邊緣裝置上的智慧體應用很重要？**

A：小型語言模型（SLM）在 Apple Silicon 等統一記憶體架構上本地執行，被視為保護隱私、降低延遲與減少雲端成本的重要方向。如果一個號稱擅長智慧體任務的模型連載入都會失敗，或在長推理軌跡中因記憶體不足而無法運行，將嚴重阻礙學術界與產業界對其能力的評估與部署。本研究透過系統性修補與記憶體最佳化，讓 Nanbeige4.2-3B 終於能在標準 MCP 與工具呼叫基準上進行可複現的評估，填補了釋出檢查點與實際可用性之間的落差。

**Q4：作者提出的核心方法是什麼？**

A：作者採取兩階段策略：首先透過同級檔案 monkeypatch 的方式修復五個初始部署錯誤，讓模型能在 MPS 上正確載入與執行；接著引入分塊預填充（chunked-prefill）策略，把原本一次處理完整提示的單次前向傳播，拆成多個固定長度的區塊，並在區塊之間遞增地建立 Key-Value cache。這種做法避免了迴圈式 Transformer 在每次迴圈都重新計算完整 quadratic 注意力分數所帶來的雙倍記憶體峰值。最後，作者還補上了系統提示詞合併與 MPS 記憶體不足的修復，才讓模型真正適用於智慧體任務。

**Q5：分塊預填充策略如何降低迴圈式 Transformer 的記憶體開銷？**

A：在傳統的預填充階段，模型會對整段提示計算一次 prompt_len × prompt_len 的注意力分數，而迴圈式 Transformer 因為把同一組層執行兩次，相當於讓這個二次方的記憶體峰值再翻倍。分塊預填充則是將提示切成例如 256 個 token 的區塊，逐塊前向傳播並把產生的鍵值存入 DynamicCache，這樣每一個區塊只需要處理當前區塊與已累積 cache 的注意力，而非整段提示的完整平方張量。透過這種方式，作者成功在 32 GiB 共享記憶體上把可允許的上下文寬度延伸了約 2.7 倍，讓原本無法執行的長智慧體軌跡得以運行。

**Q6：除了初始五個錯誤與分塊預填充，作者還發現並修復了哪些關鍵問題？**

A：作者發現 Nanbeige4.2-3B 內建了一個訓練時學到的工具使用系統提示詞，但只要呼叫者傳入任何 system message，這個提示詞就會被「替換」而非「合併」，導致模型失去工具呼叫能力。此外，在 MCPMark 評估過程中，MPS 發生記憶體不足（OOM）後，服務程序可用的記憶體預算會被永久劣化，即使後續請求理論上應該夠用也會再爆 OOM。修復這兩個問題後，模型才終於能在真實的智慧體與工具使用基準上穩定評估。

**Q7：論文在哪些基準上進行了評估，結果如何？**

A：作者主要在 MCPMark 與 BFCL（Berkeley Function Calling Leaderboard）兩個基準上進行測試。在 MCPMark 的子集合上，經過完整修補的模型能完成高達 30% 的真實智慧體任務，而原始未修補檢查點的完成率為 0%。在 BFCL 上，模型對單一工具呼叫幾乎達到完美表現，但在需要連續或並行規劃的多工具測試中仍然失敗居多，顯示其智慧體推理與多步工具編排能力仍有明顯瓶頸。

**Q8：分塊預填充在記憶體與上下文長度上帶來了什麼具體改善？**

A：在未使用分塊預填充的情況下，迴圈式 Transformer 的雙倍峰值注意力記憶體會讓 32 GiB 共享記憶體很快耗盡，無法支撐智慧體任務所需的長上下文。採用分塊預填充後，作者測得可允許的上下文寬度提升了約 2.7 倍，這對於需要長推理軌跡與多次工具呼叫的 ReAct 風格智慧體至關重要。值得注意的是，這項改善並未減少模型參數量，而是透過改變預填充演算法來降低啟動階段的記憶體峰值。

**Q9：如果只修復前五個部署錯誤，模型是否就能執行智慧體任務？**

A：不行，因為前五個錯誤只解決了載入與執行的正確性問題，並未處理迴圈式 Transformer 的記憶體開銷。修復後的模型雖然能產生正確帶有位置資訊的輸出，但在面對智慧體任務的長提示時，仍會因為雙倍注意力記憶體而很快記憶體不足。因此作者必須進一步引入分塊預填充、系統提示詞合併以及 MPS OOM 修復，才能讓模型在 MCPMark 與 BFCL 上進行可靠評估。

**Q10：這些修補對於實際在 Apple Silicon 上部署智慧體應用有什麼意義？**

A：這些修補讓開發者可以在 Mac 等 Apple Silicon 裝置上本地執行一個 3B 參數的智慧體模型，並透過 MCP 與外部工具互動，無需依賴雲端 API。對於重視資料隱私、需要離線運行或希望降低推理成本的應用場景，例如個人知識管理、本地程式碼助手與自動化辦公流程，這具有相當大的實用價值。不過，要真正產品化，仍需注意記憶體管理、系統提示詞設計與多工具規劃能力等限制。

**Q11：在產品化過程中，開發者應該特別注意哪些設計考量？**

A：首先，任何傳入的 system message 都必須與模型內建的工具使用系統提示詞合併，而不是直接覆蓋，否則會喪失工具呼叫能力。其次，由於 Apple Silicon 的共享記憶體沒有類似 CUDA 的分頁機制，開發者需要監控記憶體預算、設定合理的分塊大小，並在發生 OOM 後考慮重啟服務程序以避免記憶體預算被永久劣化。最後，分塊預填充雖然降低記憶體峰值，但會增加預填充延遲，因此需要根據應用對延遲與吞吐量的需求進行權衡。

**Q12：這項研究對整個語言模型領域可能帶來什麼影響？**

A：這項研究凸顯了「釋出檢查點」與「真實可部署性」之間經常被忽略的落差，特別是對於使用 `trust_remote_code=True` 的自訂模型架構。它也提醒研究者，參數效率並不等同於推理效率，迴圈式 Transformer 等架構雖然能節省參數，卻可能以記憶體與計算為代價。此外，本研究釋出的修補檢查點、系統提示詞最佳化器與評估工具，為後續在邊緣裝置上評估與改進智慧體模型提供了可複現的基礎。

**Q13：作者承認了哪些主要限制？**

A：首先，即使經過完整修補，模型在 MCPMark 上也只能完成 30% 的任務，顯示其智慧體能力仍有很大進步空間。其次，模型在 BFCL 的多工具測試中表現不佳，說明多步推理與工具編排並非單靠部署修復就能解決。最後，本研究的許多修復與測試是針對 Apple Silicon 與 MPS 後端，雖然部分錯誤也會影響其他裝置，但記憶體行為與 OOM 修復具有平台特定性。

**Q14：在哪些情況下，修補後的模型仍然會失敗？**

A：當任務需要同時規劃與呼叫多個工具時，模型在 BFCL 的多工具測試中仍然會失敗，顯示其高階推理與工具協調能力有限。如果沒有正確合併系統提示詞，模型會遺失訓練時內建的工具使用行為，導致無法產生正確的工具呼叫。此外，在極長上下文或記憶體壓力過大的情況下，即使使用分塊預填充，MPS 仍可能發生 OOM，若未處理則會永久降低後續請求的可用記憶體預算。

**Q15：未來可以朝哪些方向繼續改進？**

A：未來可以將這套修復與分塊預填充策略推廣到其他迴圈式 Transformer 模型，並進一步最佳化區塊大小以在記憶體、延遲與吞吐量之間取得更好平衡。另一方面，可以針對多工具規劃與長軌跡推理進行模型層級的改進，例如改進工具使用系統提示詞的設計或加入專門的多步推理訓練。最後，也可以探索更硬體感知的排程與記憶體管理機制，讓類似的 SLM 在不同邊緣平台上都能穩定且高效地執行智慧體任務。

## 實作步驟建議

### 步驟 1：驗證官方檢查點的錯誤
先以未修改檢查點在 MPS 上執行最小範例，確認五個初始 bug（RoPE buffer 靜默歸零、RoPE config KeyError、DynamicCache API 不存在、position_ids 重裁切、tied-weights 儲存錯誤）。這一步能建立除錯基線。

### 步驟 2：套用修補檢查點
切換到 `johnhalloran/Nanbeige4.2-3B-mps-fix`，透過 sibling-file monkeypatch 載入，避免修改 transformers 套件原始檔。載入後立即檢查 `inv_freq` 緩衝區是否非零、是否能正常 `forward()` 與 `save_pretrained()`。

### 步驟 3：啟用分塊預填充策略
對於超過 256 token 的提示詞，使用論文提供的 `_chunked_prefill_generate()`，以 `chunk_size=256` 逐步建立 `DynamicCache`，再交給 `generate()` 解碼。這可將 32 GiB 機器上的可用上下文寬度提升約 2.7 倍。

### 步驟 4：修正系統提示詞合併邏輯
當呼叫者提供自訂 system message 時，必須與模型內建的 tool-use system prompt **合併**（merge），而非直接取代。可使用論文釋出的 system prompt optimizer，確保工具呼叫能力不會被靜默關閉。

### 步驟 5：處理 MPS OOM 與記憶體預算
在長推理軌跡（reasoning traces）或多輪工具呼叫場景，監控 MPS 記憶體。若發生 OOM，建議重啟服務程序（而非僅清除 cache），因為 MPS 可能永久降低後續可用記憶體預算。

### 步驟 6：在標準基準上驗證
依序執行 BFCL（單一工具呼叫應接近完美）與 MCPMark（預期約 30% 真實智慧體任務完成率）。記錄多工具測試（multi-tool tests）失敗案例，作為產品功能邊界。

### 步驟 7：部署到產品雛型
將模型包裝為 MCP 伺服器或本地 API，設定最大上下文長度、chunk size、重試與程序重啟機制，並對使用者提示詞長度做硬性限制。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **RoPE 位置資訊遺失** | 官方檢查點的 `inv_freq` 緩衝區被靜默歸零，模型生成流暢但語詞順序錯亂。 | 載入後檢查 buffer，使用修補檢查點。 |
| **自訂 system prompt 覆蓋工具提示** | 任何外部 system message 會直接取代內建 tool-use system prompt，導致工具呼叫能力歸零。 | 使用合併邏輯或 system prompt optimizer。 |
| **MPS OOM 後記憶體預算永久下降** | 一旦觸發 OOM，同一服務程序後續可用記憶體可能減少，造成不穩定。 | 以獨立程序/容器執行，OOM 後自動重啟。 |
| **LT 雙倍峰值注意力記憶體** | 迴圈式 Transformer 雖節省參數，但預填充時需兩次完整 quadratic attention。 | 啟用分塊預填充，限制單次提示長度。 |
| **多工具任務表現弱** | BFCL 多工具測試多數失敗，不適合複雜多步規劃場景。 | 產品設計上限制為單一工具呼叫或人工拆分子任務。 |
| **transformers 版本相依** | 論文使用 `transformers==5.8.1`，新版 API 可能再次不相容。 | 鎖定版本，升級前重新跑完整回歸測試。 |

## 與其他技術的整合建議

- **MCP 伺服器**：將修補後的 Nanbeige4.2-3B 作為 MCP 用戶端背後的 LLM，但建議只暴露單一工具呼叫端點；對於需要連續多工具的工作流，可在外層用狀態機拆成多次單工具呼叫。
- **LangChain / LlamaIndex**：可將模型包裝為自訂 LLM 元件，但需自訂 `generate()` 流程以插入分塊預填充與 system prompt 合併；不要直接套用預設的 `HuggingFacePipeline`。
- **本地 RAG**：短上下文摘要與單次檢索適合；長文件重排序（reranking）或大量檢索結果餵入時，需先截斷至安全上下文長度，否則 MPS OOM 風險劇增。
- **監控與可觀測性**：整合 `pytorch-mps` 記憶體統計與程序健康檢查，當 MPS 記憶體高於門檻時主動重啟服務，避免 OOM 後的隱性降級。
- **量化與推論框架**：未來可評估與 `llama.cpp`、`mlx-lm` 等 Apple Silicon 原生後端整合，但需注意 LT 層重複使用邏輯是否被正確支援；在 transformers 生態驗證穩定前，不建議貿然轉換格式。

## 給不同背景讀者的閱讀建議

**初學者**：這篇論文同時是「模型部署除錯」的實戰教材。建議先跟著修補檢查點跑通第一個 `model.generate()`，再回頭對照五個 bug 的表格，理解為什麼「沒報錯」比「報錯」更危險；不必一開始就深入 Looped Transformer 的數學，先把「系統提示詞被覆蓋」與「MPS OOM」兩個產品級問題記住即可。

**AI 工程師**：重點放在實作細節：sibling-file monkeypatch 的維護性、分塊預填充與 `DynamicCache` 的互動、MPS 記憶體預算在 OOM 後的持久性影響。建議直接下載 artifact，把 `_chunked_prefill_generate()` 整合進你現有的 serving 框架，並為 system prompt 合併寫單元測試。

**研究人員**：關注 Looped Transformer 的「參數效率 vs. 記憶體開銷」權衡，以及這篇論文揭示的「開箱即用性」對學術宣稱的影響。可延伸研究：在更大統一記憶體或不同硬體（如 Intel/AMD iGPU）上，chunked prefill 對 LT 的通用性；或設計不 doubling peak attention memory 的迴圈架構變體。

**產品經理**：把這篇論文視為風險清單：一個宣稱強大的 agentic 模型，可能因五個獨立 bug、system prompt 被覆蓋、MPS OOM 而在產品中完全無法使用。評估是否值得投入 Mac 本機部署時，請以「單一工具呼叫接近完美、多工具任務多數失敗」作為功能邊界，並把 32 GiB 記憶體與程序重啟機制列為必要產品規格。
