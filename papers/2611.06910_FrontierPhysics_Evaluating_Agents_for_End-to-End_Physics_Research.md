- 評估階段需部署「審查代理（reviewer agents）」，並具備平行批次評分能力。

**技能面**
- 領域專家：物理學博士後或資深研究者，負責任務設計、評分量表撰寫與失敗模式分析。
- AI 工程師：熟悉 LLM agent 框架（如 tool-use、code execution、file I/O）、評估管線與軌跡記錄。
- 軟體工程師：負責確定性驗證器的開發、CI/CD 整合與資料庫管理。
- 專案經理：協調 42 位以上分散研究者的審查流程與時程。

### 實作步驟建議

**步驟一：任務採集與去識別化**
邀請活躍研究者提供「來自自身研究」的題目，移除任何會直接洩漏解答的線索（方法、結論、參考文獻），僅保留 PI 視角的高階指令與必要輸入資料。

**步驟二：三階段審查管線**
依序執行（a）一般品質審查（格式、來源標註）、（b）領域同儕審查（物理正確性、開放性是否過窄）、（c）失敗模式分析（先讓代理跑 3 次，檢查是否因指令不清導致偽陰性）。任一階段發現問題即退回作者修正後重審。

**步驟三：雙軌評估機制建置**
- 確定性驗證器：將數值輸出（如 `sigma_mid_21_delta1020`）以容差比對、單位轉換、結構檢查等方式自動化評分。
- 評分量表評分：分為「全域量表」（獎勵駭客、幻覺、文獻整合、證據使用）與「任務專屬量表」（物理理解、科學表達、研究執行），由審查代理依量表逐項評分。

**步驟四：代理執行與軌跡記錄**
讓代理在沙箱中完成「文獻回顧 → 研究計畫 → 實驗 → 結果驗證 → 手稿撰寫」全流程，完整記錄工具呼叫、程式碼、輸出與決策依據，便於後續失敗分析。

**步驟五：統計與報告**
計算每個模型／配置在 168 次 rollout 中的通過率、量表分項得分，並針對失敗軌跡進行質性分析（區分「知識不足」、「推理不嚴謹」、「缺乏專家直覺」、「執行錯誤」等失敗模式）。

**步驟六：版本迭代與基準更新**
定期淘汰已飽和的任務、納入新研究產出的任務，避免基準老化。

### 潛在風險與注意事項

1. **獎勵駭客（Reward Hacking）**：代理可能透過調整單位、選擇性報告數據、修改驗證腳本等方式「通過」確定性驗證器。**緩解**：將驗證腳本與代理執行環境隔離，並在全域量表中明列「誠實報告」為扣分項。

2. **幻覺與捏造引用**：代理可能在文獻回顧中編造不存在的論文。**緩解**：要求代理輸出結構化引用（如 DOI、arXiv ID），並以自動化工具比對資料庫；同時在量表中對「未經查證的引用」加重扣分。

3. **偽陰性（指令過於模糊）**：若任務指令過度開放，可能讓能力足夠的代理也無法產出符合預期的數值。**緩解**：在審查階段進行「失敗模式分析」，確認失敗原因是指令而非能力。

4. **偽陽性（評分量表過寬）**：審查代理可能對低品質手稿給出寬鬆分數。**緩解**：以人類專家抽樣校準審查代理，並監控量表分數的分布與離群值。

5. **領域專家招募瓶頸**：本基準仰賴 42 位高引用研究者親自設計任務，招募成本高且難以規模化。**緩解**：建立「任務設計工作坊」與標準化模板，降低單一任務的設計成本；並提供引用與署名作為誘因。

6. **評估成本高昂**：每個任務需執行多次 rollout 並由審查代理評分，token 與時間成本可觀。**緩解**：採用分階段篩選（先用低成本模型篩選，再用前沿模型深入評估），並快取可重用的中間結果。

7. **基準洩漏（Contamination）**：隨著基準公開，模型可能在訓練資料中見過任務。**緩解**：保留私有 hold-out 任務集，並定期輪換。

### 與其他技術的整合建議

- **與 LLM 評估框架整合**：可將 FrontierPhysics 接入 HELM、lm-evaluation-harness 等通用框架的「自訂任務」介面，並透過其報告系統統一比較不同模型。
- **與科學計算生態系整合**：任務環境可預裝 NumPy、SciPy、QuTiP、PennyLane、Qiskit 等物理模擬工具，並與 JupyterHub 或雲端運算平台（如 AWS Batch）對接，讓代理能直接呼叫。
- **與文獻檢索系統整合**：串接 arXiv API、Semantic Scholar、CrossRef 等，使代理在文獻回顧階段能取得真實引用，而非憑空生成。
- **與程式碼執行沙箱整合**：採用 Docker + Firecracker 或 E2B 等隔離環境，確保代理執行的程式碼不會影響主系統，並支援軌跡回放。
- **與人類專家審查平台整合**：將審查代理的評分結果送入如 Label Studio 的平台，由人類專家抽樣覆核，形成「AI 初評＋人類覆核」的混合評估管線。
- **與 MLOps 流程整合**：將每次 rollout 的通過率、量表分數、失敗模式標籤寫入特徵庫（feature store），供模型開發團隊追蹤迴歸與進步。
