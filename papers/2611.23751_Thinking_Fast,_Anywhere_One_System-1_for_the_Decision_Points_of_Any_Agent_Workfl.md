A：AnyS1 將雙系統代理從「為單一工作流程手工打造」解放出來，使其成為任何代理都能使用的通用基礎設施，大幅降低了採用門檻。它也推動了「以技能為中心」的代理生態系發展，讓技能庫不僅是給大型模型閱讀的提示，更成為可編譯、可優化決策的程式化資產。從產業角度來看，AnyS1 顯著降低了生產環境中代理的推論成本，有助於讓高頻、長程的代理應用在經濟上變得可行。

**Q13：AnyS1 存在哪些已知的限制？**

A：AnyS1 的設計僅適用於「選項可列舉」的決策，對於需要開放式生成、創意發想或複雜推理的步驟，仍須仰賴 System-2。此外，AnyS1 的效果高度仰賴公開技能的品質與結構清晰度，若技能本身缺乏明確的程序性結構，挖掘出來的決策點品質也會受限。最後，雖然 AnyS1 支援零樣本閾值遷移，但在某些極端分布外（out-of-distribution）的領域，仍可能需要重新校準以達到最佳表現。

**Q14：AnyS1 在哪些情境下可能會失效？**

A：當決策的選項集合無法事先列舉（例如需要從開放語意空間中挑選答案）時，AnyS1 的指針型架構便無法適用，只能交由 System-2 處理。此外，若技能的撰寫風格不一致或語意模糊，可能導致挖掘出的決策點品質不佳，進而使 System-1 的信心值失準。另一個潛在風險是，當 System-1 的信心被錯誤地校準為「高」時，可能會在應該回退的關鍵節點上堅持錯誤判斷，造成難以察覺的連鎖錯誤。

**Q15：AnyS1 開啟了哪些值得探索的未來研究方向？**

A：未來可將 AnyS1 擴展到更複雜的決策類型，例如多選項排序、條件式分支組合，或結合多模態資訊（圖像、表格）的決策點。此外，也可探索讓 System-1 在執行階段從 System-2 的回退修正中進行線上學習，使信心校準能隨時間持續優化。更宏觀地看，AnyS1 的「技能即程式」理念可進一步與技能合成、策展（curation）結合，催生出能自我演化決策能力的大型代理生態系。

**階段三：System-1 模型訓練（離線，約 1 週）**

**階段四：信心閾值校準（部署前）**
1. **AnyS1_warm 路徑**：在目標工作流程上執行少量未標註開發任務，根據任務成功率與成本權衡調整閾值。

### 潛在風險與注意事項

**1. 訓練資料偏誤風險**
Any-DP 的品質高度依賴「真實容器執行」而非 LLM 幻想狀態。論文實驗顯示，使用 LLM 生成的狀態會使模型在保留觀察上的表現下降 18.8 個百分點。實務上若無法提供完整執行環境，應至少以「人類示範軌跡」或「真實日誌回放」取代純合成資料。

**2. 信心校準漂移**
System-1 的信心分佈可能隨部署環境、輸入分佈漂移而失準。若未定期重新校準，閾值可能導致過度樂觀（過多錯誤採用）或過度保守（成本節省效果不彰）。建議部署後每週以小型標註集監控 ECE，並在漂移超過閾值時觸發重新校準。

**3. 級聯錯誤風險**
若 System-1 在早期決策點犯錯，後續步驟可能在錯誤狀態上繼續執行，導致整個任務失敗。論文中特別強調「calibration and confidence gating prevent cascading search failures」，因此信心閾值的設定寧可偏保守，也不要為了追求高採用率而犧牲可靠性。

**4. 列舉決策覆蓋率天花板**
AnyS1 的成本節省上限由工作流程中「可列舉決策」所佔比例決定。若工作流程以開放式生成為主（例如創意寫作、開放問答），AnyS1 的效益將極為有限。部署前應先分析目標工作流程的決策類型分佈，確認列舉決策佔比足以支撐預期效益。

**5. 跨模型家族遷移的隱性成本**
雖然論文宣稱 AnyS1 在 DeepSeek-V4.1-Flash 與 GPT-6 Sol 兩種 System-2 上皆有效，但不同模型家族的提示工程、token 化方式、輸出格式可能影響 System-1 的輸入編碼。建議在更換 System-2 時重新評估 System-1 的輸入預處理流程。

**6. 技能文件品質依賴**
若底層 SKILL.md 本身含糊、矛盾或缺乏明確選項，挖掘出的決策點品質將大打折扣。在導入前應對技能文件進行品質審查，必要時進行重寫或補充。

### 與其他技術的整合建議

**1. 與 RAG（Retrieval-Augmented Generation）整合**
AnyS1 處理「列舉決策」，RAG 處理「事實查詢」。兩者可互補：當 System-1 判斷需要特定領域知識時，自動觸發 RAG 查詢，再將結果回傳給 System-2 進行開放生成。建議將 RAG 視為 AnyS1 工作流程中的「確定性步驟」之一。

**2. 與 Function Calling / Tool Use 整合**
AnyS1 的「確定性步驟」可直接呼叫既有 API 或工具；「列舉決策」可作為工具選擇的前置分類器。例如在多工具代理中，先用 System-1 判斷「該用哪個工具」，再執行對應的 function call，可降低每次工具選擇的延遲。

**3. 與多代理編排框架（LangGraph、AutoGen、CrewAI）整合**
AnyS1 可作為單一代理內部的「快速決策層」，與多代理編排正交。具體做法：在每個代理節點內部，將其決策邏輯拆分為「AnyS1 處理的列舉決策」與「LLM 處理的開放決策」，無需改變外部編排結構。

**4. 與模型蒸餾技術整合**
若組織已有大型模型的蒸餾經驗，可將 AnyS1 的 4B System-1 視為「針對列舉決策的特化蒸餾」，與通用蒸餾模型並行部署。針對特定垂直領域，可進一步在 Any-DP 基礎上以領域資料進行領域適配（domain adaptation）。

**5. 與可觀測性平台整合**
建議將 System-1 採用率、回退率、信心分佈等指標接入既有可觀測性平台（如 LangSmith、Phoenix、Datadog LLM Observability），以便即時發現漂移與異常。

**6. 與 CI/CD 流程整合**
AnyS1 的閾值校準與模型版本管理應納入 CI/CD：每次 System-1 模型更新時，自動執行保留基準測試，確認任務成功率不退化且成本效益符合預期。
