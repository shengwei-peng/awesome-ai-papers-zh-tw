# Hi-Q：用於多跳問答的階層式證據引導查詢細化

**原文標題：** Hi-Q: Hierarchical Evidence-guided Query Refinement for Multi-Hop Question Answering

**發布日期：** 2026-08-31

## ⚡ TL;DR

多跳問答中查詢與語料粒度不匹配，難以找到可檢索的推理單元。
Hi-Q 以證據條件化機制階層細化查詢，僅擴展未解析節點並保留依賴關係。
在三個基準上超越 IRCoT 與 PropRAG，全語料庫平均達 52.3 EM 與 64.0 F1。

## 摘要翻譯

多跳問答（Question Answering, QA）的一個核心瓶頸在於，問題表達的粒度通常與語料庫中證據可被檢索的粒度不同。現有方法透過在語料庫上施加固定圖結構、迭代地重新表述查詢，或在語料庫上執行生成的程式來處理這種不匹配，但這些策略並未明確判斷查詢單元何時已獲證據支持、何時應進一步細化。我們將此瓶頸形式化為可檢索粒度發現（retrievable granularity discovery），並提出 Hi-Q，一個用於階層式查詢細化（hierarchical query refinement）的證據條件化框架（evidence-conditioned framework）。在每個查詢節點（query node），解析運算子（resolution operator）會檢驗已檢索的證據是否支持當前的查詢單元；已解析節點（resolved nodes）則終止擴展，而未解析節點（unresolved nodes）則由保留依賴關係的二元運算子（dependency-preserving binary operator）進行擴展，並由語義覆蓋驗證器（semantic coverage verifier）檢查。因此，Hi-Q 會逐步生成一棵查詢樹（query tree），其拓撲由語料庫支持訊號（corpus support signals）決定，而非固定的分解模板或預先建構的圖。我們在三個多跳問答基準上評估 Hi-Q，主要採用全語料庫檢索（full-corpus retrieval）設定，其中相依證據必須在開放領域干擾項（open-domain distractors）中找出，而非僅限於小型註釋資料池。在該設定下，Hi-Q 在三個基準上的平均值達到 52.3 完全匹配（Exact Match, EM）與 64.0 F1 分數（F1 score），相較於迭代式檢索（Iterative Retrieval）基線 IRCoT，在相同平均上領先 15.1 EM / 18.2 F1；並在 MuSiQue-full 上相較於圖檢索增強生成（Graph Retrieval Augmented Generation）基線 PropRAG 領先 11.5 EM / 12.0 F1，且無需進行全語料庫圖建構（corpus-wide graph construction）。在前人研究所使用的受限支持/干擾項設定（supporting/distractor setting）中，Hi-Q 同樣取得最佳表現，平均達到 57.9 EM 與 69.3 F1，分別領先 PropRAG 5.6 EM / 3.9 F1 與 IRCoT 13.7 EM / 15.8 F1。專案頁面詳見 https://hi-q-project.github.io/。

### 核心貢獻（3～5點）
- 將多跳 QA 的核心瓶頸形式化為「可檢索粒度發現（retrievable granularity discovery）」，並提出證據條件化框架 Hi-Q，以階層式查詢細化動態橋接問題粒度與語料庫證據粒度。
- 設計解析運算子（resolution operator）與語義覆蓋驗證器（semantic coverage verifier），明確判斷查詢單元是否已獲證據支持，並僅對未解析節點進行保留依賴關係的擴展。
- 以語料庫支持訊號（corpus support signals）動態生成查詢樹（query tree）拓撲，無需預先建構全語料庫圖（corpus-wide graph construction）或依賴固定分解模板。
- 在全語料庫檢索（full-corpus retrieval）與前人使用的支持/干擾項設定（supporting/distractor setting）下，均顯著超越迭代檢索基線 IRCoT 與圖檢索 RAG 基線 PropRAG。

### 適合對象
本論文適合研究多跳問答（Multi-hop QA）、檢索增強生成（Retrieval-Augmented Generation, RAG）、迭代式檢索（Iterative Retrieval）與圖檢索（Graph Retrieval）的學者與工程師，特別是關注開放領域設定下證據檢索、查詢細化（query refinement）與邏輯分解（logical decomposition）機制的研究者。

## 深度分析

#### 方法論解析

Hi-Q（Hierarchical Evidence-guided Query Refinement，階層式證據引導查詢細化）將 multi-hop QA（多跳問答）的核心瓶頸重新定義為 **retrievable granularity discovery（可檢索粒度發現）**：對於一個給定的語料庫（corpus），必須找出「哪一個層級的查詢單元（query unit）既能被可靠檢索，又能被正確回答」。這個定義把焦點從單純的邏輯分解（logical decomposition）轉移到「語料庫支持訊號（corpus support signals）」上，強調查詢的粒度必須與文件中可檢索的證據粒度對齊。

為此，Hi-Q 建立了一棵線上生長的 **query tree（查詢樹）**，樹中的每個節點都是一個查詢單元，而樹的拓撲（topology）並非來自預設模板或預建圖譜，而是由以下三個耦合機制動態決定：

1. **Resolution operator（解析運算子）**：在每個 query node（查詢節點）上，該運算子會檢視目前檢索到的證據，判斷當前查詢單元是否已經被充分支持。若支持足夠，該節點成為 **resolved node（已解析節點）** 並終止擴展；若支持不足，則標記為 **unresolved node（未解析節點）**，進入下一階段細化。這是一種 **evidence-conditioned framework（證據條件化框架）** 的體現，作者進一步指出此決策可視為對 unresolved support（未解決支持度）的成本敏感閾值（cost-sensitive threshold）。

2. **Dependency-preserving binary operator（保留依賴關係的二元運算子）**：對於未解析節點，Hi-Q 不會任意拆解，而是將其擴展為兩個子查詢，並確保前置條件（prerequisite）子查詢先被解決，其結果再傳遞給依賴它的下游子查詢。這樣可以避免傳統 iterative retrieval（迭代式檢索）中「中間查詢未經檢驗就繼續傳播」的錯誤放大問題。

3. **Semantic coverage verifier（語義覆蓋驗證器）**：每次二元拆分後，驗證器會檢查兩個子查詢的語義合起來是否仍完整覆蓋父節點的意圖，防止 **over-decomposition（過度分解）** 導致語境約束遺失，也避免拆分後的子查詢過於粗粒度而產生檢索干擾。

這三個機制分別對應圖 1 所示的三種粒度失敗模式：(a) single retrieval（單次檢索）因查詢過粗而無法串起完整證據鏈；(b) Graph RAG（圖檢索增強生成）因預建圖譜的粒度固定且與查詢無關，容易淪為表面種子對齊；(c) iterative retrieval（迭代式檢索）雖能改寫查詢，但缺乏對每個中間查詢是否可檢索的明確檢驗，導致錯誤傳播。Hi-Q 透過「先檢驗、再細化、保留依賴」的順序，把查詢從 coarse-grained（粗粒度）逐步收斂到 fine-grained（細粒度），但只對真正需要細化的節點動刀。

值得注意的是，Hi-Q 並不預先假設最佳檢索粒度，而是透過檢索與回答回饋動態發現。這使得它與 Graph RAG 有本質區別：後者把粒度決策搬到語料庫側並離線完成，而 Hi-Q 在查詢側線上建構 query tree，無需 **corpus-wide graph construction（全語料庫圖建構）**。

#### 實驗數據解讀

論文在兩種設定下評估 Hi-Q，並以 **EM（Exact Match，完全匹配）** 與 **F1 score（F1 分數）** 為主要指標：

1. **Full-corpus retrieval（全語料庫檢索）**：這是較貼近真實開放領域的設定，相關證據必須從整個語料庫中找出，並伴隨大量 open-domain distractors（開放領域干擾項）。在此設定下，Hi-Q 在三個 multi-hop QA 基準測試（包含 MuSiQue-full）上平均達到 **52.3 EM / 64.0 F1**。
   - 相較於 iterative retrieval baseline IRCoT（迭代檢索基線），平均領先 **15.1 EM / 18.2 F1**。
   - 相較於 graph-based RAG baseline PropRAG（圖檢索 RAG 基線），在 MuSiQue-full 上領先 **11.5 EM / 12.0 F1**。

2. **Supporting/distractor setting（支持/干擾項設定）**：這是前人工作常用的受限設定，干擾項較少。Hi-Q 在此設定下平均達到 **57.9 EM / 69.3 F1**。
   - 相較於 PropRAG 領先 **5.6 EM / 3.9 F1**。
   - 相較於 IRCoT 領先 **13.7 EM / 15.8 F1**。

這些數字有幾層意義：

- **對 iterative retrieval 的壓倒性優勢**（full-corpus 領先 15 EM 以上）顯示，單純讓 LLM 根據中間發現不斷改寫查詢是不夠的；若沒有明確的「當前查詢是否已被證據支持」檢驗，錯誤會在後續檢索中被放大。Hi-Q 的 resolution operator 正是針對這個問題。

- **對 Graph RAG 的顯著領先**（MuSiQue-full 領先 11.5 EM）說明，預建圖譜雖然能提供語料庫結構，但其固定粒度並不保證與每個問題的證據需求對齊。Hi-Q 的 query tree 由 corpus support signals 決定，因此能適應不同問題的粒度需求。

- **兩種設定間的差距**（full-corpus 約 52.3/64.0，restricted 約 57.9/69.3）反映了 open-domain distractors 對多跳系統的影響。Hi-Q 在兩種設定下都取得最佳表現，顯示其對干擾項具有一定魯棒性，但 full-corpus 的絕對數值仍顯示這類任務仍有很大進步空間。

- 作者還提到一個 **cost-matched configuration（成本匹配配置）**：在相同 LLM 呼叫次數下，Hi-Q 比 iterative retrieval 更便宜且更準確。這點對實際部署很重要，因為多跳系統往往伴隨高昂的 LLM 推理成本。

- 此外，論文透過 trigger diagnostics（觸發診斷）、ablations（消融實驗）、reader 與 embedding substitutions（閱讀器與嵌入模型替換）來驗證 unresolved-support signal 的有效性，這表示 Hi-Q 的優勢不僅來自某個特定元件，而是來自整體 evidence-conditioned 的設計。

#### 與現有研究的比較

Hi-Q 的定位可從與四類相關研究的對比中看出：

1. **Standard RAG（標準檢索增強生成）**：傳統 RAG 把 query 和 corpus 都視為固定，查詢即使用者輸入的 surface form（表面形式），語料庫則是扁平段落。這在問題與證據粒度相近時有效，但在 multi-hop QA 中，單一 coarse-grained 查詢往往只匹配到孤立的表面詞彙，無法串起完整推理鏈。Hi-Q 透過階層式細化彌補這個粒度落差。

2. **Graph RAG（如 PropRAG、HippoRAG、GraphRAG、RAPTOR）**：這類方法把粒度決策搬到語料庫側，透過預建圖譜或命題層級結構來檢索。優點是能利用全局結構，缺點是結構固定且 query-agnostic（與查詢無關），並需承擔 corpus-wide pre-computation cost（全語料庫預計算成本）。Hi-Q 反其道而行，在查詢側線上建構 dependency-ordered query tree，不預建圖譜，因此粒度由當前問題與語料庫支持訊號共同決定。

3. **Iterative Retrieval（如 IRCoT、ReAct、Self-Ask）**：這類方法確實會根據中間發現改寫查詢，但它們沒有明確測試「剛才發出的查詢是否可檢索」。一個邏輯上合理的中間查詢可能與語料庫中的原子事實不對齊，一旦選錯 bridge entity 或遺漏約束，後續查詢會放大錯誤。Hi-Q 的 resolution operator 把細化條件化於證據支持度，並透過 dependency-preserving binary operator 讓下游查詢扎根於已解決的前置事實。

4. **Query Decomposition（如 Least-to-Most prompting、Decomposed Prompting、TRQA）**：這類方法在還沒看到證據前就產生所有子查詢，屬於「先分解、後檢索」。Hi-Q 則是「邊檢索、邊決定是否分解」，只有在證據支持不足時才擴展節點，因此能避免不必要的分解，也能防止過早承諾錯誤的分解結構。

相較於 **code-executing agent（程式執行型智慧體）**，Hi-Q 不需要生成並執行結構化程式，這降低了執行環境的複雜度，但也意味著它無法直接利用程式語言的組合能力來處理需要算術或資料庫操作的子任務。

**限制方面**，Hi-Q 仍有以下值得注意之處：

- **對 LLM 的依賴**：resolution operator、binary operator 與 semantic coverage verifier 都仰賴 LLM 的判斷。若 LLM 對「證據是否支持查詢」的判斷失準，整棵 query tree 可能朝錯誤方向生長。
- **二元拆分的表達力**：雖然二元分解能保留依賴關係，但某些推理結構可能本質上是 n-ary（多元）或需要更複雜的拓撲，強制二元拆分可能不是最自然的形式。
- **閾值與成本權衡**：resolution operator 涉及 unresolved support 的閾值設定，這個閾值需要在「過早終止導致遺漏證據」與「過度分解導致成本飆升」之間取捨。
- **缺乏全局語料庫結構**：雖然這讓 Hi-Q 免於預建圖譜，但也意味著它無法利用 corpus-wide 的實體關係來引導檢索，對於需要大量背景知識的問題可能處於劣勢。
- **延遲問題**：query tree 的線上生長會增加檢索與 LLM 呼叫次數，雖然作者提到 cost-matched 配置仍有優勢，但在延遲敏感的應用中仍需優化。

#### 可重現性評估

從論文目前提供的資訊來看，可重現性有以下幾個面向：

- **資料集可取得性**：三個 multi-hop QA 基準測試（包含 MuSiQue-full）均為公開資料集，因此資料層面的重現沒有障礙。
- **模型與訓練**：論文強調 Hi-Q 無需 task-specific fine-tuning（任務特定微調），主要使用現成的 LLM 與 retriever（檢索器）。這降低了重現門檻，因為不需要取得或訓練專屬模型權重。
- **專案頁面**：論文提供專案頁面網址 `https://hi-q-project.github.io/`，但摘要與引言中並未明確說明是否已釋出原始碼、提示詞（prompts）、超參數、評估腳本或模型檢查點（model checkpoints）。

因此，目前可重現性處於「中等」狀態：研究問題、方法論與實驗設定已描述得相當清楚，但要完全重現，仍需作者釋出以下項目：

1. Hi-Q 的完整實作程式碼，包含 query tree 的建構邏輯。
2. resolution operator、dependency-preserving binary operator 與 semantic coverage verifier 的詳細 prompts。
3. unresolved support 的閾值設定與成本計算方式。
4. 使用的 LLM 版本、retriever、reader 與 embedding model（嵌入模型）的具體配置。
5. 資料分割與評估腳本，特別是 full-corpus retrieval 與 supporting/distractor setting 的確切設定。

若這些資源能在專案頁面釋出，Hi-Q 的可重現性將大幅提升；反之，其他研究者可能需要根據論文描述自行推測實作細節，容易在 prompts 與閾值上產生偏差。

#### 未來研究方向

Hi-Q 的設計開啟了幾個值得後續探索的方向：

1. **自適應分解元數（adaptive arity decomposition）**：目前 Hi-Q 使用二元運算子擴展未解析節點。未來可研究如何根據問題結構自動決定拆分成兩個、三個或更多子查詢，以處理更複雜的推理拓撲。

2. **學習型解析閾值（learned resolution thresholds）**：目前的 unresolved support 決策依賴閾值，未來可透過少量標註資料或強化學習來學習最佳閾值，讓系統在不同領域或不同難度的問題上自動調整。

3. **與輕量級語料庫圖譜的混合（hybrid with lightweight corpus graphs）**：Hi-Q 完全放棄預建圖譜雖然簡潔，但若能結合輕量、線上建構的局部圖譜，或許能在保留 query-adaptive 優勢的同時，利用部分全局結構來提升檢索效率。

4. **長文件與網頁規模檢索（long-document and web-scale retrieval）**：目前的評估集中在段落級語料庫。將 Hi-Q 擴展到長文件或多跳網頁檢索，需要更強大的段落定位與摘要機制。

5. **效率與延遲優化**：query tree 的線上生長會帶來多次 LLM 呼叫與檢索。未來可研究節點剪枝（pruning）、快取（caching）、平行擴展（parallel expansion）等技術，以降低延遲與成本。

6. **不確定性量化與人機協作（uncertainty quantification and human-in-the-loop）**：當 resolution operator 對證據支持度不確定時，可引入不確定性估計，並在必要時請求人類確認，進一步降低錯誤傳播風險。

7. **跨語言與多模態多跳問答（cross-lingual and multi-modal multi-hop QA）**：Hi-Q 的框架原則上可應用於其他語言或結合圖像、表格等多模態證據，但需重新設計 semantic coverage verifier 以處理不同模態間的語義對齊。

8. **理論分析**：未來可對 query tree 的複雜度、錯誤傳播上界與檢索召回率進行理論分析，為 Hi-Q 類方法提供更堅實的保證。

## 論文問答

**Q1：Hi-Q 想要解決的多跳問答核心瓶頸是什麼？**
A：Hi-Q 將核心瓶頸定義為「可檢索粒度發現」（retrievable granularity discovery），也就是問題的邏輯表達粒度與語料庫中可檢索證據的粒度經常不一致。多跳問題通常以單一句子的粗粒度形式呈現，但所需事實卻分散在多篇文件的細粒度段落中，導致檢索時難以一次命中完整推理鏈。因此，關鍵挑戰不只是邏輯分解問題，而是如何找出在給定語料庫中「既能被檢索、又能被回答」的適當粒度。

**Q2：現有的單次檢索、圖檢索 RAG 與迭代檢索各自為何會失敗？**
A：單次檢索會因為粗粒度查詢同時糾結多個推理條件，導致檢索結果只匹配表面詞彙而遺漏完整證據鏈。圖檢索 RAG 雖然引入語料庫結構，但其預先建構的圖是查詢無關的固定粒度，可能把推理簡化為種子節點的表面對齊。迭代檢索雖然會隨時間改寫查詢，但它不會明確檢驗當前查詢是否已有證據支持，因此早期錯誤的中間查詢會一路傳播到後續步驟。

**Q3：為什麼發現可檢索粒度對多跳問答如此重要？**
A：如果查詢太粗，會把多個推理面向混在一起，造成檢索干擾；如果查詢太細，又可能遺失上下文限制，導致過度分解。找到對齊語料庫的粒度能讓每個子查詢都對應到可檢索的事實單元，從而提升檢索精準度與答案正確率。這也是 Hi-Q 與單純邏輯分解方法的根本差異：它不預先假設最佳分解方式，而是透過檢索與回答回饋動態發現。

**Q4：Hi-Q 的核心框架由哪些元件組成？**
A：Hi-Q 是一個證據條件化的階層式查詢細化框架，會在執行過程中長出一棵查詢樹。每個查詢節點都會由解析運算子（resolution operator）檢驗已檢索證據是否足以支持該查詢單元；若不足，則由保留依賴關係的二元運算子進行擴展，並透過語義覆蓋驗證器確認拆分後的子查詢仍保留父節點意圖。整棵樹的拓撲因此由語料庫支持訊號決定，而非固定的分解模板或預建圖結構。

**Q5：Hi-Q 的「失敗感知粒度控制」機制如何運作？**
A：該機制透過解析運算子對每個查詢節點進行證據支持測試，若證據已足夠，節點就標記為已解析並終止擴展，避免對已可回答的查詢過度分解。若證據支持不足，則該節點被視為未解析，才會進一步細化，因此粗查詢會被適當拆解，而已有支持的查詢不會被無謂展開。作者進一步指出，這個決策可以視為對未解析支持訊號的成本敏感閾值操作。

**Q6：Hi-Q 如何透過保留依賴關係的階層式細化來防止錯誤傳播？**
A：二元擴展運算子會優先解析前置子查詢，再將其結果傳遞給下游相依子查詢，從而減少檢索不足與錯誤放大。語義覆蓋驗證器則確保每次二元拆分都保留父節點的語義意圖，避免為了細化而遺失關鍵條件。由於只有未解析節點才會被擴展，錯誤的中間查詢不會像傳統迭代檢索那樣無條件進入下一輪檢索。

**Q7：論文在哪些資料集與設定下評估 Hi-Q？**
A：論文在三個多跳問答基準上進行評估，並特別強調「全語料庫檢索」設定，也就是在開放領域干擾項中尋找相依證據，而非只在少量標註的支持文件池中檢索。其中也包含 MuSiQue-full 這類具有挑戰性的資料集。此外，作者也在前人常用的支持／干擾項設定下進行比較，以驗證方法在不同場景的穩健性。

**Q8：Hi-Q 在實驗中取得了哪些關鍵量化結果？**
A：在全語料庫檢索設定下，Hi-Q 在三個基準上的平均達到 52.3 EM 與 64.0 F1，分別領先 IRCoT 15.1 EM／18.2 F1，並在 MuSiQue-full 上領先 PropRAG 11.5 EM／12.0 F1。在支持／干擾項設定下，Hi-Q 平均達到 57.9 EM 與 69.3 F1，領先 PropRAG 5.6 EM／3.9 F1，並領先 IRCoT 13.7 EM／15.8 F1。這些結果顯示 Hi-Q 在兩種設定下都無需預建全語料庫圖即可取得最佳表現。

**Q9：論文提供了哪些消融實驗或診斷分析來支持設計選擇？**
A：作者透過觸發診斷、消融實驗以及更換閱讀器與嵌入模型的實驗，驗證未解析支持訊號的有效性。他們也設計了成本對等的配置，證明在相同 LLM 呼叫次數下，Hi-Q 不僅比迭代檢索更準確，而且成本更低。這些分析強調了解析運算子與語義覆蓋驗證器對整體效能的貢獻，並顯示框架對不同底層模型的適應性。

**Q10：Hi-Q 適合應用在哪些實務場景？**
A：Hi-Q 適用於任何需要在大量開放領域文件中進行多步推理的問答場景，例如企業知識庫查詢、法律判例與法條交叉檢索、醫學文獻綜合分析等。在這些場景中，答案所需的證據往往分散於多篇文件，且問題表面形式與文件粒度不一致。Hi-Q 的動態細化能力能夠根據實際語料庫調整查詢粒度，從而提升檢索與回答的可靠性。

**Q11：在產品化部署 Hi-Q 時需要考慮哪些因素？**
A：Hi-Q 無需進行全語料庫圖建構，能顯著降低預處理與維護成本，這對大型企業知識庫特別有利。然而，查詢樹的動態生長會帶來額外的 LLM 呼叫與檢索延遲，因此需要根據應用場景平衡準確度與成本。此外，由於解析運算子、擴展運算子與驗證器都是模組化設計，產品團隊可以根據需求替換不同的嵌入模型或閱讀器。

**Q12：Hi-Q 對多跳問答與 RAG 領域可能帶來什麼影響？**
A：Hi-Q 將研究焦點從固定的邏輯分解或預建知識圖，轉移到以證據為條件的線上查詢細化，提供了一種新的檢索增強生成典範。它證明了透過檢索回饋動態發現可檢索粒度，可以在無需昂貴預處理的情況下超越圖檢索與迭代檢索基線。這可能啟發更多結合檢索感知推理與成本敏感控制的後續研究。

**Q13：Hi-Q 目前有哪些主要限制？**
A：Hi-Q 的表現仍然受制於底層檢索器與閱讀器的品質，若相關證據根本未被檢索到，解析運算子也難以做出正確判斷。其二元擴展假設雖然簡潔，但未必適合所有推理拓撲，例如某些問題可能需要三元或更複雜的拆分。此外，語義覆蓋驗證器與解析運算子都依賴 LLM，可能產生誤判並增加計算開銷。

**Q14：Hi-Q 在哪些情況下可能會失敗？**
A：當語料庫中缺少回答問題所需的關鍵事實時，無論查詢如何細化都無法得到正確答案。若解析運算子錯誤地將證據不足判斷為已支持，或將已有支持的節點過度細化，都會導致後續錯誤。此外，對於語意模糊或需要常識推理而非事實檢索的問題，Hi-Q 的證據條件化設計可能無法有效引導查詢細化。

**Q15：未來可以從哪些方向延伸 Hi-Q？**
A：未來可以探索自適應的分支因子，讓查詢節點依據問題複雜度進行二元或多元拆分，而不局限於二元運算子。另一個方向是將 Hi-Q 與結構化知識圖或程式執行代理結合，以處理需要數值運算或關係推理的問題。此外，透過學習方式自動調整解析閾值，並將框架擴展到多模態或長文件場景，也是值得深入研究的路徑。

## 實務應用指南

### 適用場景

1. **法律與合規多層次檢索**  
   例如查詢「某判決中被告公司註冊地所在縣市的環保罰則上限」，需要從判決書找出公司、再查公司登記資料、再對應地方環保法規。Hi-Q 的階層式查詢細化可在每個節點檢驗證據是否已足夠，避免一次丟出過於粗粒度的問題。

2. **企業知識庫根因分析**  
   例如「型號 X 在 2023 年 Q2 於亞太區發生電池過熱的供應商批次」，需串連客訴紀錄、維修單、產品規格書與供應鏈資料。透過保留依賴關係的二元運算子，可先解析「型號 X 的電池供應商」再追蹤「批次」，降低中間錯誤傳播。

3. **醫學文獻綜合問答**  
   例如「針對 EGFR T790M 突變的第三代標靶藥在亞洲族群中的無惡化存活期中位數」，問題橫跨基因變異、藥物、臨床試驗與族群統計。Hi-Q 可在全語料庫檢索設定下，於開放領域干擾項中逐步收斂到可檢索粒度。

4. **金融盡職調查與關係人追蹤**  
   例如「某上市公司董事長近親控制的公司在過去兩年受過的證券監理處分」，需跨財報、股東名冊、新聞與監管公告進行多跳推理。解析運算子能判斷「關係人」是否已證據充分，再決定是否細化「處分紀錄」。

5. **技術文件與程式碼溯源**  
   例如「導致某 API 逾時的最近一次相依套件更新版本」，需串連需求文件、設計文件、程式碼提交紀錄與 Issue 追蹤。語義覆蓋驗證器可確保每次二元分解仍保留上層查詢意圖，避免過度拆解後遺失上下文。

### 實作前置條件

**資料條件**
- 已切分（chunked）的非結構化語料庫，例如文件、網頁、紀錄等。
- 建議同時具備密集向量索引與詞彙索引，以支援混合檢索（dense + sparse）。
- 不需要預先建構全語料庫知識圖譜，但若有領域標註的多跳問答對，可用於驗證與調參。

**運算條件**
- 向量資料庫與嵌入模型（embedding model）用於首次檢索。
- 大型語言模型（LLM）API 或本地部署模型，供解析運算子、二元運算子、語義覆蓋驗證器與最終答案生成使用。
- 成本會隨查詢樹深度與節點數增加，需預留 LLM 呼叫預算與延遲評估。

**技能條件**
- 熟悉 RAG 管線、檢索器（retriever）與重排器（reranker）設定。
- 具備提示工程（prompt engineering）與多跳問答評估經驗（EM / F1）。
- 能使用 Python 整合向量資料庫、LLM API 與流程編排工具。

---

### 實作步驟建議

1. **定義可檢索單位並建立索引**  
   根據領域特性決定文件切分粒度，建立密集向量與詞彙混合索引。此處的「可檢索單位」即 Hi-Q 後續要發現的粒度基礎。

2. **實作解析運算子（Resolution Operator）**  
   針對每個查詢節點，檢索 Top-K 段落後，由 LLM 判斷證據是否已足以回答該查詢單元。設定成本敏感的解析閾值，決定該節點終止或繼續細化。

3. **實作保留依賴關係的二元運算子**  
   對於未解析節點，將其拆解為兩個子查詢，並確保前置子查詢先被解析、結果寫入歷史後，再進行依賴子查詢的檢索。

4. **加入語義覆蓋驗證器**  
   每次分解後，驗證兩個子查詢的語義合取是否仍覆蓋父節點意圖，避免過度拆解導致上下文遺失。

5. **建構查詢樹編排器**  
   以 BFS 或 DFS 方式動態生長查詢樹，維護已解析節點的歷史證據，並將葉節點答案向上傳播至根節點。

6. **整合答案生成器（Reader / Generator）**  
   根節點彙整所有已解析子問題的證據，由 LLM 生成最終答案。

7. **在全語料庫檢索設定下評估與調校**  
   使用多跳問答基準測試，調整解析閾值、Top-K、提示詞與嵌入模型；特別關注開放領域干擾項中的 EM / F1 表現。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **早期錯誤分解傳播** | 若第一個子查詢選錯實體，後續檢索會放大錯誤。 | 強化語義覆蓋驗證器、引入多候選分解與回溯機制。 |
| **過度拆解導致語意遺失** | 查詢過細可能失去父節點的上下文限制。 | 二元運算子強制保留依賴關係，並以覆蓋驗證器把關。 |
| **成本隨樹深度爆炸** | 每個未解析節點都會觸發檢索與多次 LLM 呼叫。 | 設定最大深度、快取已解析節點結果、使用成本敏感閾值。 |
| **檢索器品質成為瓶頸** | 若首輪檢索遺漏關鍵段落，解析運算子會誤判。 | 採用混合檢索、重排器、領域適配嵌入模型。 |
| **LLM 在運算子中產生幻覺** | 解析或驗證判斷可能不穩定。 | 使用自我一致性（self-consistency）投票、專用輕量判斷模型、或人機協作驗證。 |
| **延遲過高** | 多跳推理與多次 LLM 呼叫會拉長回應時間。 | 平行化獨立子查詢、非同步檢索、串流回傳中間結果。 |

### 與其他技術的整合建議

- **作為現有 RAG 管線的查詢細化層**  
  在傳統單次檢索前加入 Hi-Q，將原始問題轉換為依賴有序的查詢樹，再對每個節點呼叫既有檢索器與生成器。

- **與 Graph RAG 互補**  
  若企業已有預建知識圖譜，可讓 Hi-Q 的線上查詢樹決定圖中 traversal 的順序與終止條件，避免固定圖結構的粒度不匹配。

- **嵌入 Agent 框架作為規劃模組**  
  在 ReAct、Self-Ask 等 Agent 中，以 Hi-Q 取代固定迭代式查詢改寫，讓每次下一步檢索都基於「證據是否已支持當前查詢單元」的明確訊號。

- **與企業文件平台串接**  
  將文件擷取、權限控管、版本管理視為前置管線，Hi-Q 僅讀取使用者有權限的索引內容，並記錄每個答案對應的來源節點以供稽核。

- **整合可觀測性工具**  
  記錄查詢樹拓撲、每個節點的解析結果、LLM 呼叫次數與檢索來源，便於後續除錯、成本分析與持續優化。

### 給不同背景讀者的閱讀建議

**初學者**  
建議從圖 1 的三種粒度失敗模式開始：單次檢索、圖檢索增強生成與迭代式檢索各自的問題。重點理解「解析運算子」就像一個「夠不夠了？繼續拆？」的開關，幫助系統決定何時停止細化。

**AI 工程師**  
請聚焦解析運算子的提示設計、語義覆蓋驗證器的實作細節，以及保留依賴關係的二元運算子如何維護歷史與傳播答案。同時參考論文中的成本對等配置，了解如何在相同 LLM 呼叫次數下超越迭代式基線。

**研究人員**  
核心貢獻在於將多跳 RAG 重新定義為「可檢索粒度發現」問題。建議深入閱讀消融實驗、觸發診斷（trigger diagnostics）、讀者模型與嵌入模型替換實驗，並比較圖檢索、迭代檢索與程式執行 Agent 基線的差異。

**產品經理**  
關注適用場景、全語料庫檢索與支持/干擾項設定的商業意義，以及「無需全語料庫圖建構」如何降低前期基礎建設成本。評估時請同時看準確率（EM / F1）與每次查詢的 LLM 成本，以決定導入範圍與優先級。
