## ⚡ TL;DR

邊緣-雲端協作在長時程代理執行中產生軌跡層級效應，但現有研究僅著重於查詢層級的路由決策，缺乏系統性理解。
本文提出 EC2-Bench 基準，從任務效能、資源使用與隱私暴露三面向評估長時程代理的邊緣-雲端協作。
研究發現協作在效能、資源與隱私間取得最佳平衡；邊緣能力增強時，效能差距縮小但隱私差異仍大，策略轉向邊緣主導。

## 摘要翻譯

邊緣-雲端協作結合了邊緣端執行較低的推論開銷與較佳的資料局部性，以及雲端託管模型更強大的能力。然而，隨著 LLM 代理日益在長時程情境中運作，雲端參與會在整個執行過程中交錯進行，而非對每個查詢進行一次性決策。此種交錯參與引入了軌跡層級效應，但此效應目前仍理解不足。為了解決此差距，我們提出 EC2-Bench，一個用於評估長時程代理執行中邊緣-雲端協作的基準測試。它提供了可執行的數位工作區代理任務，以及涵蓋任務效能、資源使用和隱私暴露的統一評估框架。利用此基準測試，我們對邊緣-雲端協作的多種形式進行實證研究。我們的研究揭示了三項發現。首先，與純邊緣執行和純雲端執行相比，協作在任務效能、資源使用和隱私暴露之間取得了理想的平衡。其次，隨著邊緣模型變得更強大，協作執行趨近於純雲端效能，各策略之間的效能差異縮小，而隱私暴露仍高度取決於策略。第三，更強的邊緣能力將偏好的協作方式從外部控制的雲端參與和直接雲端執行，轉向更多的邊緣控制協作。進一步的分析識別出雲端呼叫決策和指令遵循是有效協作的重要邊緣端能力。這些發現為長時程代理執行中的邊緣-雲端協作提供了系統性的理解，並為設計能有效與雲端模型協作的未來邊緣代理提供了洞見。程式碼與資源可於 https://github.com/OpenBMB/EC2-Bench 取得。

### 核心貢獻（3～5點）
- 提出 EC2-Bench 基準測試，提供可執行的數位工作區代理任務與統一評估框架，涵蓋任務效能、資源使用與隱私暴露三大面向。
- 透過實證研究揭示邊緣-雲端協作相較於純邊緣執行與純雲端執行，能在效能、資源與隱私間取得更佳平衡。
- 分析邊緣模型能力提升對協作策略的影響：效能差異縮小但隱私暴露仍高度策略依賴，且偏好策略由外部控制的雲端參與轉向邊緣控制協作。
- 識別出雲端呼叫決策與指令遵循為有效協作的關鍵邊緣端能力，為未來邊緣代理設計提供實務洞見。

### 適合對象
從事 LLM 代理系統、邊緣運算、模型路由（model routing）與人機協作（human-AI collaboration）研究的學者與工程師；以及關注隱私保護、資源效率與代理式工作流程（agentic workflow）部署實務的業界研發人員。

## 深度分析

#### 方法論解析

本論文提出 EC2-Bench（Edge-Cloud Collaborative Agent Benchmark），這是一個專門用於評估長時程代理執行（long-horizon agent execution）中邊緣-雲端協作（edge-cloud collaboration）的基準測試框架。其方法論設計具有以下幾個核心特色：

**1. 三維評估框架的設計理念**

EC2-Bench 採用三維度聯合評估的方式來衡量邊緣-雲端協作系統，這與傳統僅關注任務準確度的評估方式有本質區別：

- **任務效能（Task Performance）**：衡量代理完成數位工作區任務的成功率與品質
- **資源使用（Resource Usage）**：量化推論過程中的計算開銷（computational overhead）與記憶體消耗
- **隱私暴露（Privacy Exposure）**：評估雲端參與過程中敏感資訊（sensitive information）離開本地環境（local environment）的程度

這種三維設計反映了邊緣-雲端協作的核心張力：邊緣端執行具有較低的推論開銷（inference overhead）與較高的資料局部性（data locality），但能力受限；雲端託管模型（cloud-hosted model）能力強大但會引入隱私風險（privacy risk）與資源成本。

**2. 軌跡層級（Trajectory-Level）的協作建模**

論文最關鍵的方法論貢獻在於將協作從「查詢層級（query level）」提升至「軌跡層級（trajectory level）」。在長時程代理執行中，邊緣與雲端模型可以在多步驟任務（multi-step task）的不同執行步驟（execution step）交錯參與（interleaved participation），而非一次性決定（one-shot decision）。這種設計捕捉了軌跡層級依賴（trajectory-level dependency）：雲端參與決策（cloud participation decision）會影響後續執行步驟（subsequent execution step），並累積資源成本（resource cost）。

**3. 協作策略的系統化分類**

研究將協作策略沿兩個維度進行分類：
- **雲端參與的時機控制**：由外部路由器/規則控制器決定，或由邊緣代理自主決定雲端呼叫（cloud invocation）
- **功能角色分配**：雲端模型可擔任執行、規劃（planning）或指導（guidance）等不同角色

**4. 邊緣能力（Edge Capability）作為實驗變數**

研究設計了不同邊緣能力區間（capability regime）的實驗，模擬邊緣模型從弱到強的演進過程，這使得研究能夠回答協作策略如何隨邊緣能力演進而調整。

**5. 三個研究問題的層次化設計**

- **RQ1**：邊緣-雲端協作在長時程代理執行中是否仍然有效？
- **RQ2**：邊緣能力提升如何影響協作執行？
- **RQ3**：協作應如何隨邊緣能力進步而演進？

這三個問題形成了從「是否有效」到「如何演進」的層次化邏輯鏈。

---

#### 實驗數據解讀

論文透過 EC2-Bench 進行系統性實證研究（empirical study），揭示了三個核心發現，每一個都對邊緣-雲端協作的設計具有重要啟示：

**發現一：協作在長時程代理中仍具效能-資源-隱私的平衡優勢**

實驗結果顯示，邊緣-雲端協作在任務效能、資源使用與隱私暴露三個維度上，相較於純邊緣執行（edge-only execution）與純雲端執行（cloud-only execution）達到了更佳的平衡。具體而言：
- 相較於純邊緣執行，部分雲端參與能顯著提升任務效能
- 相較於純雲端執行，協作模式大幅降低雲端資源使用與隱私暴露

這意味著協作並非簡單的「能力換隱私」取捨（trade-off），而是能夠在多個維度上同時取得改善。

**發現二：邊緣能力提升使效能收斂，但隱私差異持續存在**

隨著邊緣模型變強，協作執行的任務效能逐漸逼近純雲端執行的水準，不同協作策略之間的效能差異（performance difference）也大幅縮小。然而，**隱私暴露的策略依賴性（strategy-dependent）依然顯著**。這個發現極為重要：當效能收斂時，隱私成為區分協作策略優劣的關鍵指標。這意味著未來的協作設計不能僅以效能為唯一標準，必須將隱私作為獨立且持續重要的設計目標。

**發現三：協作策略偏好隨邊緣能力轉變**

研究發現協作策略的最佳選擇隨邊緣能力而變化：
- **弱邊緣模型**：受益於外部路由（external routing）與直接雲端執行（direct cloud execution），因為邊緣模型本身難以做出可靠的雲端呼叫決策
- **強邊緣模型**：受益於邊緣主導協作（edge-controlled collaboration）與雲端諮詢（cloud advisory），因為邊緣模型已具備足夠的元認知能力（meta-cognitive ability）來判斷何時需要雲端協助

**進一步分析：邊緣端關鍵能力**

論文進一步識別出兩個對有效協作至關重要的邊緣端能力（edge-side ability）：
1. **雲端呼叫決策（cloud-invocation decision-making）**：邊緣模型能否準確判斷何時需要呼叫雲端
2. **指令遵循（instruction following）**：邊緣模型能否正確執行雲端提供的指導

這兩個能力是支撐「邊緣主導協作」模式的基礎，也是未來邊緣模型優化的重要方向。

#### 與現有研究的比較

**1. 相較於一次性路由/升級方法（One-Shot Routing/Escalation）**

傳統的邊緣-雲端 LLM 協作系統（如 Chen et al., 2023; Ong et al., 2024）將協作視為每個查詢的一次性協調流程，透過路由（routing）或升級（escalation）決策來選擇邊緣或雲端模型。本論文的關鍵改進在於：

- **從查詢層級到軌跡層級**：傳統方法在查詢層級（query level）做決策，本論文則在軌跡層級（trajectory level）分析協作效果
- **從單一決策到交錯參與**：傳統方法通常一次性決定整個查詢的執行位置，本論文則允許邊緣與雲端在多步驟任務中交錯參與
- **從二元選擇到功能角色分配**：傳統方法主要關注「在哪裡執行」，本論文進一步探討雲端可擔任執行、規劃或指導等不同角色

**2. 相較於現有邊緣-雲端評估基準**

- **LLMSwitchBench（Liu et al., 2025）**：專注於智慧家庭查詢的邊緣-雲端路由評估，場景較為受限
- **M4A1（Yuan et al., 2026b）**：將裝置-雲端評估擴展至多模態、多任務、多輪對話，但仍聚焦於個別推論請求的執行位置

EC2-Bench 的獨特價值在於：
- 專注於**長時程代理執行**而非單輪查詢
- 將**隱私暴露**作為獨立評估維度
- 涵蓋**軌跡層級效應**而非僅查詢層級效能

**3. 相較於通用 LLM 路由基準**

通用 LLM 路由基準（如 Huang et al., 2025; Lu et al., 2025）抽象化邊緣-雲端設定，主要評估異質模型池的路由品質與成本-效能取捨（cost-performance trade-off）。EC2-Bench 則保留了邊緣-雲端的具體部署語意，更貼近實際系統部署情境。

**4. 論文的侷限性**

- **任務範圍**：雖然涵蓋數位工作區代理任務，但可能未完全代表所有長時程代理場景（如實體機器人控制、複雜科學研究等）
- **模型範圍**：實驗所使用的邊緣與雲端模型組合可能無法完全代表所有可能的部署配置
- **隱私量化方式**：隱私暴露的量化方式可能需要更細緻的定義，例如區分不同類型的敏感資訊
- **動態環境**：實際部署中的網路延遲、頻寬限制等動態因素可能未被充分模擬

#### 可重現性評估

**1. 開源資源的可用性**

論文明確聲明程式碼與資源已開源（open-source）於 GitHub（https://github.com/OpenBMB/EC2-Bench），這為研究的可重現性提供了良好基礎。OpenBMB 作為開源社群，過往也釋出了多個 LLM 相關工具與基準測試，具有一定的可信度。

**2. 可重現性的優勢**

- **基準測試框架**：EC2-Bench 提供了統一的執行與評估環境，降低了不同研究間比較的障礙
- **三維評估指標**：明確的任務效能、資源使用、隱私暴露指標定義有助於結果的標準化比較
- **協作策略的系統化分類**：使得後續研究可以在統一的策略空間中進行比較

**3. 可重現性的潛在挑戰**

- **模型依賴性**：實驗結果可能依賴於特定的邊緣與雲端模型版本，模型更新可能導致結果變化
- **硬體差異**：邊緣裝置（edge device）的硬體特性（如記憶體限制、計算資源）會影響資源使用指標，但不同硬體平台間的結果可能不一致
- **任務執行環境**：數位工作區任務的執行可能受到作業系統、軟體版本等環境因素影響
- **隱私暴露的測量**：如何標準化測量隱私暴露仍是一個開放問題，不同的測量方法可能導致不同的結論

**4. 改進建議**

為了進一步提升可重現性，未來工作可以考慮：
- 提供標準化的硬體參考配置
- 釋出基準測試的容器化映像（containerized image）
- 公開實驗的詳細日誌與中間結果

**2. 隱私保護的協作機制**

鑑於隱私暴露在邊緣能力提升後仍具策略依賴性，未來可以研究：
- 差分隱私（differential privacy）技術在邊緣-雲端協作中的應用

- 敏感資訊的自動偵測與遮罩機制
- 本地化推理（local inference）與雲端推理的混合隱私保護策略

**3. 自適應協作策略**

論文的第三個發現指出最佳協作策略隨邊緣能力而變。未來可以探索：
- 動態調整協作策略的自適應系統
- 基於邊緣模型能力評估的策略選擇機制
- 在代理執行過程中即時切換協作模式的彈性架構

**4. 多模態與多代理擴展**

- 將 EC2-Bench 擴展至多模態代理任務（如視覺-語言代理）
- 研究多代理系統（multi-agent system）中的邊緣-雲端協作，其中多個邊緣代理可能同時與雲端互動
- 探索代理間協作（agent-to-agent collaboration）與邊緣-雲端協作的交叉議題

**5. 軌跡層級的理論分析**

論文以實證研究為主，未來可以發展：
- 軌跡層級協作的理論模型，分析協作的效能下界與上界
- 雲端呼叫次數與任務效能之間的理論關係
- 隱私-效能取捨（privacy-performance trade-off）的形式化分析

**6. 實際部署考量**

- 網路不穩定對協作效能的影響
- 邊緣裝置的能源效率（energy efficiency）考量
- 雲端服務的成本模型與定價策略對協作設計的影響
- 延遲敏感場景下的協作最佳化

**7. 評估方法的演進**

- 開發更細緻的隱私暴露量化指標
- 設計更能反映真實使用者體驗的任務效能指標
- 建立跨基準測試的標準化評估協議
- 探索代理執行的長期效應評估（如跨任務的學習與適應）

這些研究方向不僅能深化對邊緣-雲端協作的理解，也將推動邊緣代理（edge agent）技術在實際應用中的落地，使 LLM 代理能夠在保護隱私、控制成本的同時，充分發揮雲端模型的能力優勢。

## 論文問答

**Q1：為什麼邊緣-雲端協作在長時程 LLM 代理執行中變得越來越重要？**
A：隨著 LLM 應用從單次提示-回應互動轉向目標導向的代理執行，代理需要在軟體開發、資料分析、資訊檢索與工作場所自動化等場景中進行多步驟的迭代互動與工具使用。然而，邊緣裝置受限於計算資源與記憶體限制，僅能部署小型 LLM（通常 ≤10B 參數），這類模型在推理、規劃與工具使用等高需求任務上表現不佳。純雲端執行雖然能取得較強能力，卻會帶來較高的推論開銷、較差的資料局部性，以及敏感資訊外洩的隱私風險。因此，邊緣-雲端協作成為兼顧效率與能力的關鍵範式，透過讓輕量邊緣模型與雲端前沿模型互補，實現更可靠的長時程代理執行。

**Q2：現有的邊緣-雲端 LLM 系統在處理長時程代理任務時有哪些不足？**
A：現有系統大多將協作視為針對單一查詢的一次性協調流程，主要透過路由或升級決策來決定每個查詢由邊緣或雲端模型處理。然而，在長時程代理執行中，邊緣與雲端的參與會沿著軌跡交錯進行，雲端參與決策會影響後續執行步驟、累積資源成本，並決定有多少敏感資訊離開本地環境。這種軌跡層級依賴性使得查詢層級的獨立路由分析無法捕捉真實的協作動態。此外，過去的評估資源（如 LLMSwitchBench、M4A1）主要聚焦於單回合推論的路由品質，缺少對代理式執行中多步驟軌跡的系統性評估框架。

**Q3：為什麼「軌跡層級效應」是理解邊緣-雲端協作的關鍵？**
A：在長時程代理執行中，雲端參與並非一次性決定，而是會在軌跡的不同點交錯發生，這使得每次雲端呼叫都會對後續執行步驟產生影響。例如，雲端模型在某步驟提供的回應會成為邊緣模型下一輪決策的上下文，進而影響其是否再次呼叫雲端。這種累積效應不僅會沿軌跡累積資源成本，也會決定代理在執行過程中將多少潛在敏感的工作區資訊暴露給雲端。因此，僅在查詢層級分析路由或升級決策的準確度，無法反映協作策略在整體軌跡上的真實表現，必須從軌跡層級進行系統性的實證分析。

**Q4：EC2-Bench 的核心設計理念是什麼？**
A：EC2-Bench 的核心設計理念在於提供一個統一的實證基礎，使研究者能夠在一致的環境下系統性地比較不同的邊緣-雲端協作策略。其設計結合了多樣化的真實世界數位工作區代理任務，以及一個涵蓋任務效能、資源使用與隱私暴露三個維度的統一執行與評估環境。這種設計使研究者能夠同時回答三個關鍵研究問題：協作在長時程代理中是否仍然有效、邊緣能力提升如何影響協作執行，以及協作策略應如何隨邊緣能力演進。透過這樣的基準測試，EC2-Bench 填補了過去評估資源僅聚焦於單回合路由的不足。

**Q5：EC2-Bench 如何統一評估三個維度（任務效能、資源使用、隱私暴露）？**
A：EC2-Bench 在任務效能維度上評估代理完成數位工作區任務的成功率與品質，確保協作策略的實際效用；在資源使用維度上衡量雲端推論的計算與通訊成本，反映協作對系統負擔的影響；在隱私暴露維度上則量化代理執行過程中離開本地環境的敏感資訊量，凸顯協作策略對使用者隱私的潛在風險。這三個維度的聯合考量使研究者能夠辨識出在效能、成本與隱私之間取得最佳平衡的協作配置，而非僅追求單一指標的極優化。這種多維度評估框架對於設計實用的邊緣代理系統至關重要。

**Q6：EC2-Bench 在協作策略設計上有哪些獨特考量？**
A：EC2-Bench 涵蓋了多樣化的協作策略，包括由外部控制器或路由器動態決定雲端參與時機的策略，以及由邊緣代理自行決定何時呼叫雲端的邊緣主導策略。此外，EC2-Bench 也探討了邊緣與雲端模型在執行過程中的不同功能角色劃分，例如執行、規劃或提供指導等互補分工。這種策略多樣性使研究者能夠系統性地比較不同協調機制在各種邊緣能力水準下的表現，進而找出最適合特定部署情境的協作模式。

**Q7：EC2-Bench 採用了哪些基準測試任務來評估代理執行？**
A：EC2-Bench 提供了多樣化的可執行數位工作區代理任務，這些任務反映了真實世界中代理需要處理的工作流程，包括軟體開發、資料分析、資訊檢索與工作場所自動化等場景。這些任務具有長時程特性，需要代理進行迭代互動與工具使用，而非僅是單回合的問答。透過這種任務設計，EC2-Bench 能夠有效評估協作策略在多步驟軌跡中的真實表現，並揭示不同策略在軌跡層級效應下的差異。

**Q8：實證研究揭示了哪些關於邊緣-雲端協作的核心發現？**
A：研究揭示了三項核心發現。首先，邊緣-雲端協作在長時程代理中仍然有效：部分雲端參與能夠在任務效能上超越純邊緣執行，同時在資源使用與隱私暴露上遠低於純雲端執行，達成三者間的有利平衡。其次，當邊緣模型變得更強時，協作執行的效能會趨近純雲端執行，且不同協作策略之間的效能差異會顯著縮小，但隱私暴露的差異仍然顯著。最後，協作策略的相對優劣會隨邊緣能力而改變：較弱的邊緣模型從外部路由與直接雲端執行中獲益較多，而較強的邊緣模型則從邊緣主導的呼叫與雲端諮詢中獲益較多。

**Q9：邊緣模型能力的提升如何影響不同協作策略的相對表現？**
A：當邊緣模型能力較弱時，協作策略之間的效能差異較大，此時由外部控制器主導的路由策略或直接雲端執行策略能顯著提升任務效能，因為邊緣模型難以獨立完成複雜任務。隨著邊緣模型能力提升，不同協作策略在任務效能上的差異逐漸縮小，因為更強的邊緣模型本身就能處理更多任務，雲端參與的邊際效益降低。然而，即使在邊緣能力較強的情境下，不同策略在隱私暴露上的差異仍然顯著，這凸顯了隱私作為協作策略區分指標的重要性，即使在效能趨同時仍不可忽視。

**Q10：EC2-Bench 的研究成果對實際邊緣代理部署有何指導意義？**
A：研究成果為實際邊緣代理部署提供了明確的策略選擇指引：在邊緣模型能力有限時，應優先考慮外部路由或直接雲端執行等策略，以確保任務完成的可靠性；在邊緣模型能力較強時，則應採用邊緣主導的呼叫與雲端諮詢策略，以在維持高效能的同時降低隱私暴露。此外，研究強調了雲端呼叫決策與指令遵循作為關鍵邊緣端能力的重要性，這意味著未來的邊緣模型訓練應同時優化獨立能力與協作能力。這些發現有助於系統設計者在效能、成本與隱私之間做出更明智的取捨。

**Q11：在設計邊緣代理產品時，應如何根據邊緣能力選擇合適的協作策略？**
A：產品設計者應根據目標裝置的邊緣能力等級來選擇協作策略。對於搭載較弱邊緣模型的入門級裝置，採用外部控制的雲端參與策略可以確保使用者獲得可靠的代理體驗，但需注意隱私暴露的累積風險。對於搭載較強邊緣模型的高階裝置，則應設計邊緣主導的協作模式，讓邊緣代理自主決定何時需要雲端協助，這不僅能降低延遲與成本，也能減少不必要的工作區資訊外洩。此外，產品應提供透明的隱私設定，讓使用者能根據自身需求調整協作策略。

**Q12：這項研究對邊緣 AI 與代理技術領域的長期影響是什麼？**
A：這項研究的長期影響在於將邊緣-雲端協作的分析從查詢層級提升到軌跡層級，為未來研究建立了更全面的分析框架。它強調了隱私暴露作為協作策略關鍵區分指標的重要性，這將促使後續研究在設計協作系統時更重視隱私保護。此外，研究凸顯了雲端呼叫決策與指令遵循作為邊緣端關鍵能力的角色，這將影響未來邊緣模型的訓練目標，使其不僅追求獨立執行的強健性，也追求與雲端模型協作的有效性。整體而言，這項研究推動了邊緣代理從「單機執行」走向「協作智慧」的典範轉移。

**Q13：EC2-Bench 在任務覆蓋面與模型多樣性方面有哪些已知限制？**
A：EC2-Bench 的任務主要聚焦於數位工作區代理場景，雖然涵蓋了軟體開發、資料分析、資訊檢索與工作場所自動化等類型，但可能無法完全代表所有長時程代理應用，例如實體機器人控制或多模態感知任務。此外，評估中所使用的邊緣與雲端模型組合雖然多樣，但隨著模型技術快速演進，未來可能需要持續更新模型池以反映最新的能力水準。這些限制意味著研究結論在推廣到其他代理場景時需要謹慎，並可能需要針對特定領域進行補充評估。

**Q14：在哪些情境下，邊緣-雲端協作可能無法達到預期效果？**
A：當邊緣模型的雲端呼叫決策能力不足時，即使雲端模型能力強大，協作也可能無法有效運作，因為邊緣模型可能在不適當的時機呼叫雲端，或無法正確整合雲端回應。此外，在網路連線不穩定或頻寬受限的邊緣部署環境中，頻繁的雲端呼叫可能導致嚴重的延遲與可用性問題，使協作策略的實際表現低於預期。另一個失敗情境是當任務涉及高度敏感的資訊時，即使協作策略在效能上表現優異，隱私暴露的累積仍可能超出組織或使用者的可接受範圍。

**Q15：未來研究可以從哪些方向進一步深化邊緣-雲端協作的理解？**
A：未來研究可以從多個方向深化此一主題。首先，可以探索更細粒度的協作機制，例如讓邊緣與雲端模型在單一執行步驟內進行更緊密的互動，而非僅在步驟層級切換。其次，可以研究如何透過專門的訓練方法提升邊緣模型的雲端呼叫決策與指令遵循能力，使其成為更有效的協作夥伴。此外，未來工作也可以將 EC2-Bench 擴展到多模態代理任務、跨裝置協作場景，或納入更複雜的隱私保護機制（如聯邦學習或差分隱私），以更全面地評估邊緣-雲端協作在真實世界部署中的可行性。

## 實務應用指南

### 適用場景

1. **企業內部數位工作區自動化**：員工在本地裝置處理含有客戶資料、財務報表等敏感資訊的工作流程，僅在邊緣模型無法勝任的複雜推理或規劃任務時呼叫雲端前沿模型，兼顧生產力與資料合規。

2. **行動裝置上的個人助理應用**：智慧型手機、平板上的個人助理需處理行事曆、郵件、聯絡人等隱私資料，採用邊緣-雲端協作可讓日常查詢在本地完成，僅在需要深度研究或多步驟規劃時才將部分內容送往雲端。

3. **離線優先的遠端工作場景**：在網路不穩定的工地、偏遠地區或航空環境中，邊緣代理作為主力執行者，雲端僅在恢復連線時針對關鍵決策點提供建議，確保業務持續運作。

4. **邊緣 IoT 裝置的智慧控制**：工業感測器網路、智慧建築系統中，邊緣代理即時處理控制迴圈，雲端模型僅在異常診斷、預測性維護等需要深度分析的場景介入。

5. **個人開發者的編碼助手整合**：本地 IDE 中的程式碼助理以邊緣模型處理自動完成、簡單重構等任務，雲端模型僅在被明確邀請時介入處理複雜架構設計或跨檔案除錯。

### 實作前置條件

**資料面**
- 任務類型盤點：需明確區分哪些工作流程屬於長時程代理執行（多步驟、需工具使用），哪些屬於單次查詢
- 隱私分級標註：對工作區中的檔案、欄位、API 回傳資料進行敏感度分級，作為雲端呼叫的過濾依據
- 軌跡紀錄基礎設施：需具備完整記錄代理每一步決策、工具呼叫、模型切換點的能力

**運算面**
- 邊緣裝置：建議至少配備可推論 ≤10B 參數模型的 NPU/GPU（如 Apple Silicon、Qualcomm Hexagon、高階 NVIDIA Jetson）
- 邊緣模型：選用具備基本指令遵循與工具使用能力的小型 LLM（如 Qwen2.5-7B、Llama-3.1-8B 等開源模型）
- 雲端模型 API：存取前沿 LLM 的推論端點（如 GPT-4、Claude、Gemini 等）
- 網路條件評估：對目標部署環境的延遲、頻寬、可用性進行基準測試

**技能面**
- 熟悉代理框架（Claude Code、OpenClaw、LangGraph 等）的部署與客製化
- 具備模型路由、串接（cascading）策略的設計能力
- 了解 EC2-Bench 評估框架的使用方法以進行策略驗證
- 基本的隱私工程素養，包括資料脫敏、最小化揭露原則

### 實作步驟建議

**步驟一：建立基線評估**
使用 EC2-Bench 在目標任務上分別測量「純邊緣執行」與「純雲端執行」三個維度的表現——任務效能、資源使用、隱私暴露。這組數據將作為後續所有協作策略比較的基準。

**步驟二：盤點邊緣能力等級**
依據邊緣模型在 EC2-Bench 上的表現，將其歸入「弱邊緣」或「強邊緣」等級。論文的關鍵發現指出：邊緣能力越強，越傾向採用邊緣主導的協作模式（如邊緣控制雲端呼叫、雲端僅提供建議），而非外部路由或直接雲端執行。

**步驟三：選擇協作策略**
依據邊緣能力選擇對應策略：
- **弱邊緣階段**：優先採用外部控制的雲端參與（路由器決定何時呼叫雲端）或直接雲端執行，以確保任務完成度
- **強邊緣階段**：轉向邊緣主導協作，由邊緣代理自行判斷何時需要雲端協助，並讓雲端扮演顧問角色而非執行者

**步驟四：優化邊緣端兩項關鍵能力**
論文明確指出「雲端呼叫決策」與「指令遵循」是有效協作的關鍵邊緣能力。實作上應：
- 訓練或提示邊緣模型準確判斷「此步驟是否超出自身能力」
- 強化邊緣模型對雲端回傳建議的解析與執行能力

**步驟五：建立隱私防護層**
即使在強邊緣階段，不同協作策略的隱私暴露差異仍然顯著。應在雲端呼叫前對傳輸內容進行脫敏、摘要或選擇性揭露，並在 EC2-Bench 的隱私評估維度上持續監控。

**步驟六：迭代驗證與策略調整**
隨著邊緣模型版本更新或新任務加入，定期重跑 EC2-Bench 評估，檢視當前協作策略是否仍為最優組合。論文發現協作策略的偏好會隨邊緣能力提升而轉移，需動態調整。

### 潛在風險與注意事項

**風險一：軌跡層級的隱私累積洩漏**
即使單次雲端呼叫揭露的資訊有限，長時程代理執行中的多次呼叫可能累積出可推斷敏感全貌的資訊量。
*緩解措施*：設計隱私預算（privacy budget）機制，限制單一軌跡中可送往雲端的累計資訊量；對重複出現的敏感實體進行追蹤與遮罩。

**風險二：雲端呼叫決策錯誤導致的成本失控**
邊緣模型若過度依賴雲端，會造成雲端費用與延遲飆升；若過度保守，則任務效能下降。
*緩解措施*：設定雲端呼叫比例上限與單次軌跡成本上限；對邊緣模型的呼叫決策進行信心度校準。

**風險三：邊緣模型能力誤判**
若低估邊緣模型能力而一律採用外部路由，會錯失強邊緣階段的效率優勢；若高估則會造成任務失敗。
*緩解措施*：以 EC2-Bench 為基準定期重新評估邊緣模型能力邊界，避免憑經驗判斷。

**風險四：策略轉換期的效能震盪**
從「外部控制」轉向「邊緣主導」協作時，邊緣模型需要時間學習何時該呼叫雲端，過渡期可能出現任務效能暫時下降。
*緩解措施*：採用漸進式策略轉換，例如先在低風險任務上試行新策略，再逐步擴大範圍。

**風險五：雲端回應的指令遵循落差**
雲端模型提供的建議若未被邊緣模型正確解析與執行，會造成協作失效。
*緩解措施*：規範雲端輸出的格式（如結構化 JSON、明確動作清單），並對邊緣模型的解析能力進行專項測試。

### 與其他技術的整合建議

**與企業身分與存取管理（IAM）整合**
將雲端呼叫權限與企業 SSO、角色權限系統掛鉤，確保只有經授權的使用者工作流程才能觸發雲端資源，並保留完整的呼叫稽核日誌。

**與監控與可觀測性平台整合**
將 EC2-Bench 的三維評估（任務效能、資源使用、隱私暴露）整合至現有 APM 或 LLM 監控平台，設定自動化告警閾值，例如當隱私暴露指標超過基線時觸發通知。

**與代理框架整合**
EC2-Bench 設計為可評估各種代理框架，實務上可將其評估邏輯嵌入 Claude Code、OpenClaw 等框架的 CI/CD 流程中，作為協作策略變更前的回歸測試關卡。

**與資料脫敏與 DLP 系統整合**
在邊緣代理與雲端 API 之間部署資料外洩防護（DLP）層，自動過濾信用卡號、身分證字號等敏感欄位，與企業既有的資料分類政策保持一致。

**與模型版本管理系統整合**
當邊緣模型或雲端模型版本更新時，自動觸發 EC2-Bench 評估管線，確保新版本組合下的協作策略仍維持在三維度最佳平衡點。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與「適用場景」段落，建立對「為什麼邊緣不能單獨完成所有任務」與「為什麼雲端不能單獨完成所有任務」的直覺理解。接著閱讀「實作步驟建議」中的步驟一至步驟三，掌握協作策略選擇的基本邏輯。論文中具體的 EC2-Bench 設計細節可暫時略過，待實際動手時再回頭查閱。

**給 AI 工程師**：重點閱讀「實作步驟建議」與「潛在風險與注意事項」，特別關注「雲端呼叫決策」與「指令遵循」這兩項邊緣能力的工程化方法。建議直接 clone EC2-Bench 程式碼庫，在自己的目標任務上重現論文的評估流程，並將三維評估整合進既有的模型評估管線中，以數據驅動協作策略的選擇。

**給研究者**：論文的價值在於將邊緣-雲端協作從「查詢層級的路由問題」提升為「軌跡層級的策略問題」，並提出 EC2-Bench 作為標準化評估基礎。建議深入閱讀「Related Work」與論文中關於協作策略分類、邊緣能力分級的論述，並思考如何擴展 EC2-Bench 至多模態代理、多代理協作等場景，或探索更細粒度的隱私暴露量化指標。

**給產品經理**：重點理解三項核心發現的商業意涵：（1）邊緣-雲端協作是兼顧效能、成本、隱私的務實解；（2）隨著邊端模型持續進步，產品策略應從「雲端為主」逐步轉向「邊緣為主、雲端為輔」；（3）即使效能趨同，隱私仍是策略差異化的關鍵維度。建議將「隱私暴露」納入產品 KPI，並在產品路線圖中預留協作策略動態調整的彈性。
