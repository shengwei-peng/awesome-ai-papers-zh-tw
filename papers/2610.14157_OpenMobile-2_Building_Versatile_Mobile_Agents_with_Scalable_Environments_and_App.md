## 摘要翻譯

我們推出 OpenMobile-2——一個具備完全開放訓練環境與配方的接近前沿水準行動代理。我們提出三項關鍵進展：(1) 具備模擬商業應用程式的多元環境：我們建構了 MobileGym++，內含 35 個高擬真度、功能豐富的商業風格應用程式，支援跨應用程式工作流程，同時保留完整的可控性以進行重置與驗證。結合 Android 模擬器中新配置的應用程式，形成一個橫跨超過 110 個應用程式的多元訓練場域。(2) 大規模開放訓練資料：在此基礎上，我們彙整了近 12K 筆行動互動軌跡用於監督式微調，以及目前規模最大的行動代理可驗證強化學習訓練資料開放集合，涵蓋超過 2K 個具備自動獎勵的可執行任務。(3) 混合 GUI 與應用程式原生工具使用：我們探索了一種實驗性的行動裝置使用設定，其中應用程式將選定功能以應用程式原生工具的形式，與其 GUI 並行提供，使代理能夠在單一任務中交錯執行 GUI 動作與工具呼叫。我們在 MobileGym++ 中實作了此設定，於 50 多個應用程式中提供超過 300 個經嚴謹界定的工具。此外，我們推出 MobileGym++ Bench，用於複雜的長時程商業行動場景，在共享任務套件上同時支援僅 GUI 評估與混合 GUI 與工具評估。OpenMobile-2 在多項既有基準測試上展現競爭力，包括 AndroidWorld (79.9) 與 MobileWorld (50.4)，同時在將能力遷移至真實裝置的行動裝置使用方面，展現令人期待的成果，將 SPA-Bench 效能從 31.9 幾近翻倍至 59.6。所有資源可於 https://os-copilot.github.io/OpenMobile2-Home/ 取得。

### 核心貢獻（3～5點）
- **建構 MobileGym++ 環境**：內含 35 個高擬真度商業風格應用程式，結合 Android 模擬器中新配置的應用程式，形成橫跨 110+ 應用程式的多元訓練場域，並保留完整可控性以支援重置與驗證。
- **大規模開放訓練資料**：彙整近 12K 筆行動互動軌跡用於監督式微調，並發布目前規模最大的行動代理可驗證強化學習訓練資料開放集合，涵蓋超過 2K 個具備自動獎勵的可執行任務。
- **混合 GUI 與應用程式原生工具使用**：探索實驗性行動裝置使用設定，於 50+ 應用程式中提供超過 300 個經嚴謹界定的工具，使代理能在單一任務中交錯執行 GUI 動作與工具呼叫。
- **推出 MobileGym++ Bench**：針對複雜長時程商業行動場景，在共享任務套件上同時支援僅 GUI 評估與混合 GUI 與工具評估。
- **卓越的基準測試表現與真實裝置遷移能力**：在 AndroidWorld (79.9)、MobileWorld (50.4) 等基準測試上展現競爭力，並將 SPA-Bench 效能從 31.9 幾近翻倍至 59.6。

### 適合對象
本論文適合從事行動代理、視覺語言模型、強化學習及人機互動研究的學者與工程師閱讀，特別是關注開放模型訓練、可控模擬環境建構、GUI 自動化與工具增強代理等議題的研究團隊。此外，對於希望將行動代理技術部署至真實裝置的產業從業者，亦具高度參考價值。

## 深度分析

#### 方法論解析

OpenMobile-2 的方法論核心在於解決行動代理（mobile agent）訓練中的三大瓶頸：環境多樣性不足、訓練資料規模受限、以及 GUI 互動效率低落。整體方法可拆解為三個相互支撐的技術支柱。

**一、MobileGym++ 環境架構**

MobileGym++ 建立在 MobileGym 的模擬框架之上，採用「功能性重新實作」（functional re-implementation）策略來重現商業應用程式。與直接抓取真實商業 App 不同，此方法透過重建 App 的核心功能邏輯與內部狀態（internal state），在保留高擬真度（high-fidelity）互動體驗的同時，實現了乾淨重置（clean reset）與程式化驗證（programmatic verification）。具體而言，環境包含三個層次：

1. **35 個商業風格應用程式**：涵蓋跨應用程式工作流程（cross-app workflow），例如健身 App 中的 `search_course` 工具，允許代理在 GUI 動作與結構化呼叫之間切換。
2. **Android 模擬器中的新配置 App**：與模擬 App 互補，提供更真實的系統層互動。
3. **總計 110+ 應用程式的訓練場域**：透過模擬與模擬器的混合架構，兼顧可擴展性與擬真度。

此設計的關鍵洞察在於：傳統基於真實 App 的環境難以平行化（parallelization）且重置成本高昂，而純模擬環境則缺乏商業工作流程的深度。MobileGym++ 透過「可控模擬」填補了這道鴻溝。

**二、訓練資料規模化策略**

資料管線分為兩個階段：

- **監督式微調（SFT）階段**：蒐集近 12K 條行動互動軌跡（trajectory），涵蓋多樣化的任務、應用程式與環境。這些軌跡作為模仿學習的標籤，使模型學習基本的 GUI 操作模式。
- **強化學習（RL）階段**：構建超過 2K 個可執行任務（executable task），每個任務配備可靠的驗證器（verifier）以提供自動獎勵（automatic reward）。這是目前最大的開源行動代理 RL 訓練資料集。

值得注意的是，RL 資料的「可驗證性」是設計核心——透過環境內建的狀態檢查機制，代理的行為可被自動評分，無需人工標註，這大幅降低了訓練成本並提升了資料利用效率。

**三、混合 GUI 與應用程式原生工具使用（Hybrid GUI-Tool Use）**

此為本文最具實驗性的貢獻。MobileGym++ 在 50+ 個應用程式中暴露超過 300 個應用程式原生工具（app-native tool），允許代理在同一任務中交錯使用 GUI 動作與工具呼叫（tool call）。此設計反映了電腦使用（computer use）領域的新興趨勢：通用但低效的 GUI 互動正與高效但功能受限的結構化介面（structured interface）互補。

技術實作上，每個工具都經過「仔細範圍界定」（carefully scoped），確保其功能邊界清晰，避免代理產生歧義行為。代理的動作空間被擴展為 `A = A_GUI ∪ A_tool`，並透過統一的動作表示學習何時該使用 GUI、何時該呼叫工具。

**四、MobileGym++ Bench 評估套件**

包含 215 個長時程（long-horizon）跨應用程式任務，每個任務皆具備持久化使用者狀態（persistent user state）與程式化驗證。關鍵設計在於：每個任務可同時以 GUI-only 或混合 GUI-tool 模式求解，使得兩種代理可在同一任務套件（task suite）上直接比較。

#### 實驗數據解讀

**一、基準測試效能**

| 基準測試 | OpenMobile-2 效能 | 關鍵意義 |
|---------|------------------|---------|
| AndroidWorld | 79.9 | 在標準化行動代理基準上展現競爭力 |
| MobileWorld | 50.4 | 在更具挑戰性的長時程任務上表現穩健 |
| SPA-Bench | 59.6（從 31.9 提升）| 真實裝置遷移能力近乎翻倍 |

**二、數據解讀的深層意涵**

1. **AndroidWorld 79.9 分的定位**：此分數顯示 OpenMobile-2 已接近前沿（near-frontier）水準，但需注意 AndroidWorld 主要涵蓋系統工具與開源 App，無法完全反映商業場景的複雜度。

2. **MobileWorld 50.4 分的挑戰**：MobileWorld 涉及更複雜的跨應用程式工作流程，50.4 分意味著代理在長時程規劃與狀態追蹤上仍有顯著改進空間——這正是混合工具使用試圖解決的痛點。

3. **SPA-Bench 從 31.9 躍升至 59.6**：此增幅最為戲劇性，顯示從模擬環境到真實裝置（real-device）的遷移（transfer）能力大幅提升。這暗示 MobileGym++ 的模擬保真度足以讓訓練出的策略泛化至真實世界。

**三、消融實驗的隱含訊息**

雖然完整消融數據未在提供的文本中呈現，但摘要與引言暗示了兩個關鍵發現：

- **應用程式多樣性的重要性**：擴展 App 覆蓋範圍（從少數開源 App 到 110+ 商業風格 App）對代理泛化能力有顯著貢獻。
- **混合 GUI-tool 的互補效益**：在長時程任務中，工具呼叫可作為 GUI 動作的加速器，減少操作步驟並降低錯誤率。

#### 與現有研究的比較

**一、相對於現有開源行動代理的優勢**

| 比較維度 | 現有開源工作 | OpenMobile-2 |
|---------|-------------|--------------|
| 環境規模 | 少數開源 App + 系統工具 | 110+ 商業風格 App |
| 訓練資料 | 軌跡規模有限，RL 資料稀缺 | 12K SFT + 2K+ RL 任務 |
| 互動模式 | 純 GUI | GUI + 300+ 應用程式原生工具 |
| 重置與驗證 | 困難且成本高 | 完全可控且自動化 |

**二、相對於閉源/專有系統的差距**

OpenMobile-2 雖在 AndroidWorld 上達到 79.9，但與最先進的閉源系統（如基於 GPT-4o 或 Claude 的代理管線）相比，在以下方面仍有差距：

1. **螢幕解析精度**：閉源系統常依賴外部 OCR 與版面分析模組，而 OpenMobile-2 採用端到端視覺語言模型（vision-language model），在細粒度 UI 元素定位上可能略遜。
2. **規劃能力**：長時程任務的成功率（MobileWorld 50.4）顯示規劃與記憶機制仍需強化。
3. **商業 App 覆蓋深度**：35 個商業風格 App 雖是重大進步，但相較於真實商業生態的數百萬 App，覆蓋率仍有限。

**三、方法論定位**

OpenMobile-2 在「環境擴展性」（environment scaling）維度上做出了獨特貢獻。現有工作如 AndroidWorld（Rawles et al., 2025）依賴真實 App 導致重置困難；MobileGym（Wu et al., 2026a）雖提供模擬但 App 數量有限；其他模擬環境（Liu et al., 2026b）則缺乏商業工作流程。OpenMobile-2 透過「功能性重新實作」策略，在擬真度、可控性與規模之間取得了最佳平衡點。

**四、限制與未解決問題**

1. **模擬差距（Sim-to-Real Gap）**：儘管 SPA-Bench 表現優異，但功能性重新實作仍可能與真實 App 在視覺呈現、邊緣案例行為上存在差異。
2. **工具設計的人工成本**：300+ 工具的範圍界定需要大量人工設計，未來需探索自動化工具發現機制。
3. **任務複雜度的上限**：215 個長時程任務雖具代表性，但相較於真實使用者的多樣需求，覆蓋面仍有限。

#### 可重現性評估

**一、開源資源的完整性**

根據摘要聲明「All resources are available at https://os-copilot.github.io/OpenMobile2-Home/」，OpenMobile-2 提供了完整的開放技術堆疊（open stack），包含：

1. **環境程式碼**：MobileGym++ 的模擬框架與 35 個商業風格 App 的功能性重新實作。
2. **訓練資料**：12K SFT 軌跡與 2K+ RL 任務的完整釋出。
3. **訓練配方（training recipe）**：包含模型架構、訓練超參數、資料處理流程等。
4. **評估套件**：MobileGym++ Bench 的 215 個任務及其驗證器。

**二、可重現性優勢**

- **無需真實商業 App 授權**：由於採用功能性重新實作，研究者可在不違反授權條款的前提下重現實驗。
- **確定性環境**：模擬環境的隨機性可控，使得實驗結果可重現。
- **標準化評估**：MobileGym++ Bench 提供統一的評估介面，便於跨研究比較。

**三、潛在的可重現性挑戰**

1. **Android 模擬器配置**：部分任務依賴 Android 模擬器中的真實 App，其行為可能隨 Android 版本、裝置型號而異。
2. **視覺語言模型的版本依賴**：若訓練配方未明確指定基礎模型（如 Qwen-VL、InternVL 等）的具體版本，結果可能難以精確重現。
3. **工具呼叫的介面穩定性**：300+ 工具的 API 設計若在釋出後變動，將影響下游研究的相容性。

**四、整體評估**

OpenMobile-2 的可重現性在開源行動代理領域屬於頂尖水準。其「全開放」策略（環境、資料、配方、評估套件）為社群提供了寶貴的基礎設施，有望加速該領域的研究迭代。

#### 未來研究方向

**一、環境擴展的下一階段**

1. **自動化 App 重建**：當前 35 個商業風格 App 仰賴人工功能性重新實作，未來可探索利用大型語言模型從 App 截圖、API 文件或使用者錄影中自動重建模擬 App。
2. **動態環境演化**：現有環境的 App 狀態相對靜態，可引入時間維度（如通知、背景更新）以模擬更真實的使用情境。
3. **多裝置生態系統**：將環境從單一智慧型手機擴展至手錶、平板、桌面與 IoT 裝置，模擬跨裝置工作流程。

**二、訓練方法的深化**

1. **RL 演算法的適配**：現有 RL 訓練資料規模（2K+ 任務）相較於電腦使用領域仍偏小，可探索更高效的 RL 演算法（如基於偏好學習、過程獎勵模型）以提升樣本效率。
2. **自我對抗訓練**：讓代理在環境中自我產生困難任務並學習解決，可能突破當前效能瓶頸。
3. **多模態獎勵設計**：除任務完成度外，可引入使用者體驗指標（如操作步驟數、錯誤率）作為輔助獎勵。

**三、混合 GUI-Tool 框架的演進**

1. **工具自動發現**：代理應能從 GUI 互動中自動推導出可工具化的操作，而非依賴預定義的 300+ 工具。
2. **工具組合推理**：探索代理如何學習將多個工具組合成更高階的工作流程原語。
3. **GUI 與工具的無縫切換**：當工具呼叫失敗時，代理應能優雅地降級至 GUI 動作，反之亦然。

**四、評估基準的演進**

1. **真實使用者需求的代表性**：當前基準（AndroidWorld、MobileWorld、SPA-Bench）雖具價值，但未必完全反映真實使用者的任務分布。可透過大規模使用者研究來校準基準設計。
2. **安全性與隱私評估**：行動代理涉及敏感操作（如支付、個人資料），需建立專門的安全性評估框架。
3. **長期使用者體驗**：除任務成功率外，應評估代理的長期使用體驗（如學習使用者偏好、減少重複詢問）。

**五、跨領域應用**

1. **無障礙輔助**：OpenMobile-2 的技術可應用於協助視障或運動障礙使用者操作智慧型手機。
2. **企業自動化**：將行動代理整合至企業流程自動化平台，處理跨 App 的業務流程。
3. **教育與培訓**：作為智慧型教學助手，引導使用者學習複雜 App 的操作。

**六、理論基礎的探索**

1. **代理能力的理論上限**：在給定的環境複雜度下，視覺語言模型架構的行動代理能達到何種理論上限？
2. **環境多樣性與泛化能力的量化關係**：如何系統性地設計環境以最大化代理的泛化能力？
3. **GUI 與結構化介面的形式化統一**：是否存在統一的數學框架來描述 GUI 動作與工具呼叫的互補關係？

OpenMobile-2 為行動代理研究提供了堅實的基礎設施，其真正的價值將在後續研究中被充分釋放——透過在這個開放平台上進行系統性實驗，社群有望在未來幾年內將行動代理的效能推向新的高度。

## 論文問答

**Q1：OpenMobile-2 主要解決的核心問題是什麼？**
A：OpenMobile-2 致力於解決開放社群在訓練行動代理時所面臨的「互動經驗不足」問題。現有的開放行動代理模型在效能上明顯落後於閉源系統，主要原因是缺乏大規模、高品質且可重置的訓練環境與互動軌跡資料。該論文透過建構可擴展的環境、開放的訓練資料以及完整的訓練配方，將環境擴展（environment scaling）落實為具體實踐，使開放社群能夠訓練出接近前沿水準的行動代理。

**Q2：為何現有的開放原始碼行動代理環境不足以支援大規模訓練？**
A：現有的開放環境（如 Android 模擬器中的開源應用程式與系統工具）雖然提供真實的互動，但第三方應用程式通常缺乏可靠的 reset 機制，且完整的 Android 堆疊難以大規模平行化以支援強化學習的 rollout。此外，模擬式環境雖然提供高效率的重置與平行化能力，但應用程式數量稀少且功能深度不足，無法捕捉商業工作流程中豐富的互動經驗。這些限制使得應用程式覆蓋範圍成為擴展互動經驗的主要瓶頸。

**Q3：為什麼「擴展互動經驗」對於行動代理的發展如此重要？**
A：行動代理的能力高度依賴於跨多樣任務、應用程式與環境所收集的大規模互動經驗，這些經驗通常以軌跡的形式呈現。獨立蒐集這類資料成本高昂，而高品質的互動資料大多為專有資源，導致開放社群在訓練資源上處於劣勢。透過擴展互動經驗，模型不僅能學習更廣泛的 GUI 操作模式，還能提升對新應用程式與未知工作流程的泛化能力，這對於實現真正實用的行動代理至關重要。

**Q4：OpenMobile-2 的核心方法論是什麼？**
A：OpenMobile-2 的核心方法論建立在三大支柱之上：首先是 MobileGym++ 環境，內含 35 個高擬真度的商業風格應用程式功能性重新實作，搭配 Android 模擬器中新配置的應用程式，形成涵蓋 110 個以上應用程式的多樣化訓練場域。其次是規模化的開放訓練資料，包含近 12K 條用於監督式微調的軌跡，以及超過 2K 個配備自動獎勵的可執行強化學習任務。最後是混合 GUI 與應用程式原生工具使用的統一框架，使代理能在同一任務中交錯使用 GUI 動作與工具呼叫。

**Q5：MobileGym++ 相較於既有環境的關鍵創新為何？**
A：MobileGym++ 的關鍵創新在於兼顧了「高擬真度」與「完全可控性」這兩個看似矛盾的特性。它透過功能性重新實作 35 個商業應用程式，不僅保留了豐富的內部狀態與跨應用程式工作流程，還能支援乾淨的重置與任務結果的程式化驗證。這種設計讓研究人員能夠在模擬環境中重現真實的商業場景，同時享有模擬環境帶來的高效率平行化與可重置優勢，從而克服了現有開放環境在應用程式覆蓋範圍與可控性之間的取捨困境。

**Q6：在混合 GUI 與應用程式原生工具使用的設計上，OpenMobile-2 做出了哪些關鍵選擇？**
A：OpenMobile-2 選擇將工具整合為「應用程式本身所暴露的功能」，而非外部附加的系統層介面或 MCP 伺服器，這使得工具呼叫與 GUI 操作能夠在同一任務中無縫交錯執行。在 MobileGym++ 中，超過 300 個經過嚴格範圍界定的工具分散於 50 多個應用程式中，例如健身應用程式中的 search_course 功能。此外，MobileGym++ Bench 採用「每個任務皆可使用或不使用工具來完成」的設計原則，使 GUI 專用代理與混合代理能在相同的長時程任務套件上進行公平比較。

**Q7：OpenMobile-2 在哪些基準測試上進行了評估？**
A：OpenMobile-2 在多個已建立的行動代理基準測試上進行了評估，包括 AndroidWorld（79.9 分）與 MobileWorld（50.4 分），這兩個基準測試涵蓋了多樣化的行動裝置使用情境。此外，論文還引入了 MobileGym++ Bench，這是一個包含 215 個長時程跨應用程式任務的基準測試，支援持久化使用者狀態與程式化驗證，並允許 GUI 專用與混合 GUI 工具代理在同一任務套件上進行評估。

**Q8：OpenMobile-2 的關鍵實驗結果為何？**
A：OpenMobile-2 在已建立的基準測試上取得了具競爭力的表現，在 AndroidWorld 上達到 79.9 分、在 MobileWorld 上達到 50.4 分。更引人注目的是其在真實裝置設定上的遷移能力，SPA-Bench 的效能從 31.9 分幾乎翻倍提升至 59.6 分，超越了強勁的開放原始碼基準模型。這些結果顯示出 OpenMobile-2 不僅在模擬環境中表現優異，還能有效地將所學遷移至真實裝置的行動使用情境。

**Q9：消融研究揭示了哪些關鍵發現？**
A：消融研究凸顯了兩個關鍵發現：第一，擴展應用程式的多樣性對於提升代理的泛化能力至關重要，這驗證了 MobileGym++ 中 110 個以上應用程式設計的合理性；第二，混合 GUI 與應用程式原生工具使用展現了互補效益，說明結合通用但效率較低的 GUI 互動與高效但功能受限的結構化介面，能夠為行動代理帶來顯著的效能提升。這些發現為未來環境設計與代理訓練策略提供了明確的方向指引。

**Q10：OpenMobile-2 的實際應用情境有哪些？**
A：OpenMobile-2 可應用於多種實際的行動裝置自動化情境，包括跨應用程式的工作流程自動化，例如從電子郵件中擷取資訊並自動填入行事曆或待辦事項清單。在電子商務領域，代理能夠在多個購物應用程式之間比較價格並完成下單流程。此外，透過混合 GUI 與工具使用的能力，OpenMobile-2 也能在需要高效結構化操作的場景（如資料查詢、批次處理）中發揮作用，同時保留處理非標準介面的彈性。

**Q11：從產品化的角度來看，OpenMobile-2 帶來了哪些考量？**
A：從產品化角度來看，OpenMobile-2 的開放性大幅降低了企業開發行動代理的技術門檻，使中小型團隊也能基於完整的訓練配方打造客製化代理。然而，部署至真實裝置時仍需考量隱私、安全性與使用者授權等議題，特別是當代理需要存取敏感應用程式（如銀行、醫療）時。此外，混合 GUI 與工具使用的設計也意味著產品需要維護應用程式工具的版本相容性，這對長期維運提出了新的挑戰。

**Q12：OpenMobile-2 對行動代理研究領域的影響為何？**
A：OpenMobile-2 對領域的影響主要體現在三個層面：環境層面上，它證明了商業風格應用程式的功能性重新實作是擴展互動經驗的可行路徑；資料層面上，近 12K 條軌跡與 2K 個可驗證強化學習任務的釋出，填補了開放社群在訓練資源上的關鍵缺口；方法論層面上，混合 GUI 與應用程式原生工具使用的統一框架為未來研究樹立了新典範。這些貢獻共同推動了開放原始碼行動代理從「追隨者」向「競爭者」的轉變。

**Q13：OpenMobile-2 存在哪些已承認的限制？**
A：OpenMobile-2 的限制主要來自於模擬環境與真實裝置之間的差距，儘管 MobileGym++ 提供了高擬真度的商業風格應用程式，但功能性重新實作仍無法完全捕捉真實商業應用程式的所有邊緣情況與版本更新。此外，雖然 SPA-Bench 的效能從 31.9 提升至 59.6，但與閉源前沿模型相比仍有差距，顯示出在真實裝置上的泛化仍有改善空間。最後，300 多個工具的範圍界定需要大量人工設計，這在擴展至更多應用程式時將成為瓶頸。

**Q14：OpenMobile-2 可能遭遇哪些失敗案例？**
A：OpenMobile-2 可能在以下情境中遭遇失敗：當遇到訓練環境中未涵蓋的新應用程式或新版本介面變更時，代理的泛化能力可能不足；在需要精確視覺理解（如複雜圖表辨識、手寫文字識別）的任務中，基於視覺語言模型的代理可能產生錯誤；此外，當應用程式的 GUI 結構發生非預期變化（如彈出式廣告、系統更新提示）時，代理可能會偏離預期的工作流程。在混合 GUI 與工具使用方面，若工具的範圍界定不夠完整，代理可能會過度依賴 GUI 而忽略更高效的工具呼叫路徑。

**Q15：OpenMobile-2 的未來研究方向為何？**
A：未來研究方向可從幾個維度展開：在環境層面，可探索自動化或半自動化的應用程式功能性重新實作流程，以降低擴展至更多應用程式的成本；在方法論層面，可進一步研究 GUI 動作與工具呼叫之間的動態決策機制，使代理能根據任務特性自適應地選擇最有效的互動方式；在評估層面，可建構更貼近真實裝置使用情境的基準測試，涵蓋更多長時程、多步驟的複雜任務。此外，跨平台擴展（從 Android 延伸至 iOS）以及多模態輸入（語音、影像）的整合，也是值得探索的重要方向。

## 實務應用指南

### 適用場景

1. **企業內部流程自動化**：將員工日常需要在多個 App 之間切換的操作（例如從 CRM 複製客戶資料、貼到通訊軟體發送訊息、接著在記帳 App 建立發票）整合為單一自然語言指令，特別適合需要跨 App 資料搬運的業務場景。

2. **客服與個人助理 App 整合**：第三方開發者可在自家 App 中嵌入 OpenMobile-2 驅動的助理模組，讓使用者用口語指令完成「查詢我的訂單並退款」這類長時程任務，無需逐層點選 UI。

3. **App 開發階段的 UI/UX 測試**：QA 團隊可利用 MobileGym++ 的可控環境與可重置特性，對新版本 App 進行大規模迴歸測試，特別是跨 App 工作流程的整合測試。

4. **無障礙輔助工具**：為視障或行動不便的使用者提供可自然語言控制的行動裝置操作介面，混合 GUI 與工具呼叫的模式可在效率與覆蓋率間取得平衡。

5. **App 廠商主動暴露原生工具**：參考 MobileGym++ 的設計，App 開發者可主動將高頻功能（如 `search_course`、`add_to_cart`）以結構化介面形式開放給代理呼叫，兼顧使用者體驗與自動化效率。

### 實作前置條件

**資料需求**
- 至少需要一份目標領域的 App 截圖與操作軌跡資料集（建議數千筆以上），可從 MobileGym++ 釋出的 12K 軌跡起步，再以自身 App 資料補強。
- 對 RL 階段，需要為每個任務撰寫可程式化驗證的檢查函式（verifier），這是 MobileGym++ 2K+ 可執行任務的核心設計。

**運算資源**
- 監督式微調（SFT）階段：建議 8 張以上 A100/H100 等級 GPU，視基礎模型大小而定。
- 強化學習階段：需要可平行化的環境池（MobileGym++ 的模擬框架支援此特性），rollout 階段建議配置 32+ 個 Android 模擬器或模擬環境實例。
- 評估階段：MobileGym++ Bench 含 215 個長時程任務，完整評估需預留數小時 GPU 時間。

**技能門檻**
- 熟悉視覺語言模型（VLM）的微調流程（LoRA 或全參數微調）。
- 具備 Android 模擬器操作經驗，理解 App 生命週期與狀態管理。
- 能撰寫任務驗證腳本（Python 為主），熟悉 ADB 或 App 內部狀態檢查 API。
- 對 GUI 動作空間（tap、swipe、type）與結構化工具呼叫的混合設計有概念。

### 實作步驟建議

1. **環境建置**：先部署 MobileGym++ 模擬框架，安裝 35 個商業風格 App 與 Android 模擬器中的輔助 App，確認 reset 機制與 verifier 可正常運作。建議從官方提供的 Docker 映像檔開始以節省環境配置時間。

2. **資料準備**：以 MobileGym++ 釋出的 12K 軌跡進行初步 SFT；若目標領域特殊（例如金融、醫療），再以自身蒐集的軌跡進行領域適應。RL 階段則從 2K+ 可驗證任務中篩選與目標場景相符的子集。

3. **基礎模型選擇與微調**：選擇合適的開源視覺語言模型作為起點，採用 SFT 訓練 GUI 動作預測能力。建議先在 AndroidWorld 等公開基準上驗證基本能力，再進入 RL 階段。

4. **強化學習訓練**：在 MobileGym++ 的可控環境中執行 RL，利用 verifier 提供自動獎勵訊號。關鍵在於環境的乾淨重置與平行化能力，這正是 MobileGym++ 相較於真機環境的優勢。

5. **混合 GUI 與工具整合**：若目標 App 已暴露原生工具，修改動作空間使其同時支援 GUI 動作與工具呼叫；在 MobileGym++ Bench 上以「同一任務、兩種模式」對照評估，找出最佳混合策略。

6. **真機遷移與驗證**：在 SPA-Bench 等真機基準上測試遷移能力，根據結果決定是否需要額外的真機微調或領域適應資料。

7. **部署與監控**：將訓練好的模型封裝為服務，串接至目標 App 或助理產品；持續監控任務成功率與使用者回饋，建立再訓練的資料回流機制。

### 潛在風險與注意事項

- **模擬到真實的轉移落差**：MobileGym++ 的商業風格 App 是功能性重新實作而非真實商業 App，視覺與互動細節可能與真機有差異。緩解方式：在 SPA-Bench 等真機基準上做最終驗證，並準備少量真機微調資料。

- **任務驗證器的可靠性**：RL 訓練高度依賴 verifier 的正確性，若 verifier 設計不嚴謹，代理可能學會「作弊」通過驗證但實際未完成任務。緩解方式：採用多重狀態檢查、避免僅依賴單一 UI 元素判斷。

- **App 版本更新導致環境漂移**：模擬 App 升級或真實 App 更新介面後，原本訓練的軌跡可能失效。緩解方式：建立持續整合流程，定期重跑評估並更新訓練資料。

- **工具呼叫的權限與安全邊界**：app-native tool 雖然效率高，但若設計不當可能繞過使用者確認步驟（例如直接執行付款）。緩解方式：對敏感操作保留 GUI 確認步驟，或在工具層加入二次驗證。

- **長時程任務的錯誤累積**：跨 App 工作流程步數多，單步錯誤會連鎖放大。緩解方式：設計回退機制、加入中間狀態檢查點，並在評估中區分單步成功率與整體成功率。

- **資料偏誤與隱私**：12K 軌跡的分布可能偏向特定 App 類型或任務類型。緩解方式：分析訓練資料分布，對低資源場景主動擴增，並注意軌跡中是否含有個人隱私資料。

### 與其他技術的整合建議

- **與 RAG 系統整合**：將 OpenMobile-2 視為「動作執行層」，上層搭配 RAG 提供任務相關的領域知識（例如公司內部 SOP），可提升複雜任務的完成率。

- **與 MCP（Model Context Protocol）伺服器整合**：MobileGym++ 的 app-native tool 概念與 MCP 高度契合，可將既有 MCP 伺服器包裝為代理可呼叫的工具，擴展可自動化範圍。

- **與傳統 RPA 工具互補**：對於結構化、重複性高的流程，仍可由 RPA 處理；OpenMobile-2 適合處理需要視覺理解與彈性決策的非結構化任務，兩者可依場景分工。

- **與裝置管理平台（MDM）整合**：在企業場景中，可透過 MDM 統一部署代理所需的環境配置、權限與 App 工具白名單，確保合規與安全。

- **與監控與可觀測性工具整合**：將每次代理執行的軌跡、決策與結果送入日誌系統（如 LangSmith、自建監控），便於除錯、稽核與持續改進。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的整體介紹與圖 2，建立「環境—資料—模型—評估」四層架構的概念；接著到官方網站（os-copilot.github.io/OpenMobile2-Home/）實際操作展示影片，理解代理在螢幕上「看到什麼、做什麼」。先不必深入 RL 細節，重點是體會「混合 GUI 與工具」這個設計理念如何兼顧效率與覆蓋率。

**給 AI 工程師**：重點關注第 3 節的 MobileGym++ 環境設計與第 4 節的訓練資料建構流程，特別是 verifier 的設計模式與 SFT/RL 兩階段的銜接方式。實作上建議先復現 AndroidWorld 上的 79.9 分數作為基準，再嘗試將 MobileGym++ 的工具整合進自有 App 的動作空間，評估混合模式對延遲與成功率的影響。

**給研究者**：本論文的核心研究問題是「如何以可控環境擴展互動經驗」，建議深入分析 MobileGym++ 的 35 個商業風格 App 如何在「擬真度」與「可控性」間取捨，並比較其與 AndroidWorld、MobileWorld 等真機基準的任務分布差異。RL 階段的可驗證任務設計、混合 GUI-tool 的消融實驗，以及模擬到真機的遷移分析，都是值得延伸的研究方向。

**給產品經理**：重點理解 OpenMobile-2 能解決什麼問題、不能解決什麼問題。它適合處理「跨 App、需要視覺理解、任務描述自然語言化」的場景，但對延遲敏感、需嚴格合規審計、或涉及金流的核心流程，仍應保留人為確認。建議從內部工具或客服輔助等低風險場景試點，根據 MobileGym++ Bench 的 215 個長時程任務類型，挑選與自身產品痛點相符的子集驗證可行性，再評估是否擴大導入。
