# RealSWE：以真實使用者請求對編碼智慧體進行組合式評估

**原文標題：** RealSWE: A Compositional Evaluation of Coding Agents under Realistic User Requests  
**作者：** Gyuhyeong Kim、Hyojung Gwon、Jeonghyeon Kim 等 5 位作者  
**發布日期：** 2026-08-31  
**HF 連結：** [https://huggingface.co/papers/2608.27831](https://huggingface.co/papers/2608.27831)

## ⚡ TL;DR

現有 SWE-bench 基準與真實使用者請求在資訊量與語言風格上存在顯著落差。
論文提出 RealSWE，以 381 個多變體任務家族進行組合式評估，控制資訊組成與語言風格。
真實輸入使解決率平均下降 6.4 個百分點，期望行為與動機顯著影響效能，並提供實用建議。

## 摘要翻譯

編碼智慧體（coding agent）目前多以 SWE-bench 系列（SWE-bench family）基準進行評估，這些任務由經整理的 GitHub issue 建構而成：篇幅長、結構化且資訊豐富。然而，真實使用者請求（realistic user request）通常短得多，結構也較為鬆散。為了刻畫這種基準與現實差距（benchmark–reality gap），我們定義了一個六類別的資訊分類法（information taxonomy）與四個語言風格（linguistic style）維度，並將其應用於 SWE-chat 中的真實使用者提示（user prompt），以及 SWE-bench Verified 與 SWE-bench Pro 的問題陳述（problem statement）。我們發現，僅含問題陳述（單獨出現或僅附帶有限額外上下文）的請求佔真實提示的 88%，但在基準問題中僅佔 7%。此外，87% 的真實提示寫得較為隨意，而 94% 的基準問題則為正式風格。基於這些觀察，我們提出 RealSWE，包含 381 個衍生自 SWE-bench Verified 與 SWE-bench Pro 的多變體任務家族（multi-variant task family）。每個家族內的變體共享相同的底層任務與黃金修補檔（gold patch），僅在資訊組成（information composition）與語言風格上有所不同。我們以 RealSWE 評估七個當代大型語言模型（large language model, LLM），發現：（i）真實輸入平均使解決率（resolution rate）降低 6.4 個百分點（percentage point, pp），且可能改變模型排名（model ranking）。進一步的控制分析顯示：（ii）加入期望行為（Desired Behavior）與動機（Motivation）會顯著影響效能，而環境資訊（Environment Information）與重現步驟（Reproduction Steps）僅增加 token（詞元）數量，卻沒有可測量的效益；（iii）語言風格僅有微小且因模型而異的影響。這些發現為使用者與智慧體提供了具體可行的指引：明確陳述期望行為與動機——而大多數真實提示都忽略了這兩項資訊——能顯著提升大型語言模型的軟體工程效能（software engineering performance）。

### 核心貢獻（3～5點）
- 量化並刻畫真實使用者請求與 SWE-bench 系列基準題目之間的結構與資訊落差：真實提示多為簡短、隨意且資訊稀疏，而基準問題則多為長篇、正式且資訊豐富。
- 提出六類資訊分類法與四個語言風格維度，作為分析與重構使用者提示的系統性框架。
- 建構 RealSWE 評估基準，包含 381 個多變體任務家族，每個家族內的變體共享相同底層任務與黃金修補檔，僅在資訊組成與語言風格上有所差異。
- 透過控制實驗發現：納入期望行為與動機可顯著提升編碼智慧體效能，而環境資訊與重現步驟僅增加 token 數量卻無顯著助益；語言風格的影響則較小且因模型而異。
- 提供實務建議：使用者在向編碼智慧體提出請求時，應明確陳述期望行為與動機，以有效提升大型語言模型的軟體工程效能。

### 適合對象
本論文適合從事編碼智慧體、大型語言模型評估、軟體工程自動化以及人機協同程式設計的研究者與工程師閱讀；對於希望設計更貼近真實使用情境之基準、改善智慧體提示工程策略，或理解真實使用者請求如何影響模型效能的實務工作者亦具高度參考價值。

## 深度分析

#### 方法論解析

##### 1. 整體設計哲學：從「任務難度」轉向「溝通方式」
傳統 SWE-bench（常見的編碼智慧體評測基準）系列將評估重心放在底層軟體工程任務的難度、規模與可執行性，而 RealSWE（本論文提出的真實使用者請求評估基準）則把焦點轉移到「同一任務如何被表達」。其核心假設是：coding agent（編碼智慧體）在真實場景中接收到的 user prompt（使用者提示），與 benchmark（評測基準）中經過整理的 GitHub issue（GitHub 議題）在資訊組成（information composition）與語言風格（linguistic style）上存在系統性差異，而這種差異會顯著影響 resolution rate（解決率）。因此，RealSWE 並非要創造更難的任務，而是要建立一個能夠隔離並量化「溝通方式」效應的評估框架。

##### 2. 資訊分類法（information taxonomy）
論文針對兩大常見任務類型分別定義六類資訊欄位，構成 information taxonomy（資訊分類法）：

- Bug fix（錯誤修復）：
  - Problem Statement (P)（問題陳述）：Observed Failure（觀察到的失敗現象）。
  - Desired Behavior (D)（期望行為）：修復後應該呈現的正確行為。
  - Reproduction Steps (R)（重現步驟）：如何重現該 bug。
  - Environment Information (E)（環境資訊）：執行環境、版本、相依套件等。
  - Additional Information (A)（額外資訊）：例如 source URL（來源網址）、日期、參考連結等。

- Feature request（功能請求）：
  - Problem Statement (P)（問題陳述）：Requested Feature（請求的功能）。
  - Motivation (M)（動機）：為何需要此功能。
  - Additional Information (A)（額外資訊）。

此分類法的價值在於把一個完整的 GitHub issue 拆解成可獨立增減的欄位，使研究者能夠進行組合式評估（compositional evaluation），觀察每一類資訊對模型效能的邊際貢獻。

##### 3. 語言風格維度（linguistic style）
論文定義四個語言風格維度，並從 SWE-chat（真實開發者與編碼智慧體互動資料集）與 SWE-bench Verified（SWE-bench 的子集）、SWE-bench Pro（SWE-bench 的子集）中觀察到顯著差異：

- 正式度（formality）：casual（口語/隨意）vs. formal（正式）。
- 句法語氣（sentence mood）：imperative sentences（祈使句）vs. declarative sentences（陳述句）。
- 長度與簡潔度（length / conciseness）：真實 prompt 通常較短、較稀疏。
- 結構化程度（structural organization）：真實 prompt 較少分段、標題、清單等正式結構。

透過這兩個正交軸——「說了什麼」與「怎麼說」——論文得以獨立操縱資訊內容與語言風格，從而分離兩者對模型效能的影響。

##### 4. RealSWE 的建構流程
1. 從 SWE-bench Verified 與 SWE-bench Pro 中選出 381 個底層任務，每個任務保留相同的 gold patch（黃金修補檔）與可執行測試。
2. 將原始 problem statement（問題陳述）解析為上述資訊欄位。
3. 對每個任務產生 multi-variant task family（多變體任務家族）：透過包含或排除不同資訊欄位，並以風格轉換重寫，生成多種 prompt 變體。
4. 所有變體共享相同底層任務與正確答案，因此任何效能差異都可歸因於溝通方式，而非任務難度或儲存庫差異。

##### 5. 兩種釋出形式
- RealSWE-bench（圖表中亦標示為 RealSWE-bench）：固定評估集，其 prompt 分佈與 SWE-chat 中觀察到的真實分佈對齊，用於標準化比較。
- RealSWE-Framework：可配置框架，提供完整變體套件，支援 per-field ablations（逐欄位消融）、任意資訊組合與風格控制，適合機制研究與自訂實驗。

##### 6. 控制變因設計的優勢
這是方法論上最大的亮點：因為底層任務與 gold patch 固定，任何 resolution rate（解決率）變化都可歸因於 information composition（資訊組成）或 linguistic style（語言風格）。這種設計克服了過去研究中「任務、儲存庫、難度、溝通方式」混淆的問題，使 RealSWE 成為一個真正可用於因果推論的評估平台。

#### 實驗數據解讀

##### 1. 整體效能落差
圖 1 顯示七個當代 LLM（large language model，大型語言模型）在原始 SWE-bench 與 RealSWE-bench 上的解決率。所有模型在真實輸入下皆下降，平均下降 6.4 percentage points (pp)（百分點）。這驗證了 benchmark–reality gap（基準與現實差距）不僅存在，而且具有普遍性——無論模型強弱，都無法免疫於真實使用者請求的資訊稀疏與風格差異。

##### 2. 資訊價值高度不均
控制實驗發現不同資訊欄位對效能的貢獻差異極大：

- Desired Behavior（期望行為）：對 bug fix（錯誤修復）影響最大，帶來 +8 pp，相當於約 17% 的相對提升。這表示當使用者明確說明「應該如何正確運作」時，編碼智慧體能顯著降低需求推論錯誤。
- Motivation（動機）：對 feature request（功能請求）可提升高達 +7 pp。說明「為何需要此功能」有助於模型理解功能定位、使用情境與邊界條件。
- Reproduction Steps（重現步驟）與 Environment Information（環境資訊）：增加 token（詞元）數量但無顯著效益。可能原因包括：可執行測試已隱含重現邏輯，或模型能從儲存庫上下文推斷環境；在已有測試與程式碼上下文的情況下，這些欄位成為冗餘資訊。

這項發現對使用者極具實用價值：與其鉅細靡遺地描述環境與重現步驟，不如清楚陳述期望行為與動機。

##### 3. 語言風格影響有限
相較於資訊內容，linguistic style（語言風格）的改變僅產生 small, model-dependent effects（小且因模型而異的影響）。這暗示：對當前 LLM 而言，「說什麼」比「怎麼說」更重要；模型對口語化、祈使句等非正式表達已有一定容忍度。然而，這並不表示風格完全無關，而是其效應遠小於資訊欄位的有無。

##### 4. 模型排名變化與穩健性
RealSWE-bench 不僅降低整體解決率，也改變 model ranking（模型排名），並縮小強弱模型之間的差距。這表示頂尖模型在 information-sparse（資訊稀疏）、casual（口語化）的真實輸入下，其優勢被部分抵銷；換句話說，現有 leaderboard（排行榜）可能過度獎勵在完整 GitHub issue 上表現的模型，而低估對真實使用者請求的穩健性（robustness）。

##### 5. 真實分佈與基準的結構性差異
數據顯示：

- 僅含 problem statement（問題陳述）或少量額外上下文的 prompt 佔真實請求 88%，但在 SWE-bench Verified / Pro 中僅佔 7%。
- 87% 真實 prompt 為 casual（口語）風格，而 94% 基準題目為 formal（正式）風格。
- 51% 真實 prompt 使用 imperative sentences（祈使句），89% 基準題目使用 declarative sentences（陳述句）。

這些分佈差異正是 RealSWE-bench 設計的經驗基礎，也解釋了為何模型在真實輸入上表現較差。

#### 與現有研究的比較

##### 1. 與 SWE-bench 系列比較
SWE-bench 系列（包含 SWE-bench Verified、SWE-bench Pro）專注於擴充任務數量、程式語言、儲存庫與複雜度，但每個 executable task（可執行任務）通常只對應單一 canonical issue description（標準議題描述）。因此它們測量的是「任務難度」，而非「溝通方式」。RealSWE 填補了這一空白，透過 multi-variant task family（多變體任務家族）將同一任務以不同資訊與風格呈現，從而實現對溝通效應的精細測量。

##### 2. 與 CURSORBENCH 比較
CURSORBENCH 使用真實程式設計對話，具備高度真實性，但屬於 closed-source（閉源）基準，無法獨立檢驗或重複使用。此外，其任務、儲存庫、難度與溝通方式同時變化，難以分離各因素效應。RealSWE 則是 open-source（開源）且控制底層任務固定，能進行機制分析與受控比較。

##### 3. 與 SAVING SWE-BENCH 及其他啟發式變體比較
SAVING SWE-BENCH 嘗試將 GitHub issue 轉換為使用者風格輸入，但其轉換同時改變多個任務規格屬性，難以將效能變化歸因於特定資訊欄位或語言屬性。其他研究則透過截斷 problem statement（問題陳述）或注入 ambiguity（模糊性）來模擬真實輸入，但缺乏對真實使用者資料的系統性分析。RealSWE 的優勢在於以 SWE-chat 為經驗基礎，並採用組合式設計，可進行 per-field ablation（逐欄位消融）與任意 composition（組合）。

##### 4. 主要貢獻與限制
主要貢獻：
- 首次系統性量化真實使用者請求與基準題目在資訊與語言風格上的差異。
- 提供開源、可配置、控制變因的評估框架。
- 識別 Desired Behavior（期望行為）與 Motivation（動機）為高價值信號，並提供可操作的建議。

限制：
- 底層任務仍來自 SWE-bench，屬於經整理的 GitHub issue，可能無法完全代表真實世界中所有軟體工程任務。
- 語言風格轉換是基於觀察到的維度進行重寫，可能未涵蓋所有真實對話中的噪音，例如拼寫錯誤、程式碼片段、截圖或多輪上下文。
- 研究聚焦 bug fix（錯誤修復）與 feature request（功能請求），未涵蓋 refactoring（重構）、testing（測試）、documentation（文件）等請求類型。
- 真實分佈以 SWE-chat 為代表，可能偏向特定使用者群體、工具介面或產業領域。

#### 可重現性評估

##### 1. 開放資料與框架
論文明確表示將釋出 RealSWE-bench 與 RealSWE-Framework，屬於 open-source（開源）資源。由於其基於公開的 SWE-bench Verified 與 SWE-bench Pro，底層任務、gold patch（黃金修補檔）與可執行測試皆已公開，具備良好的可重現性基礎。

##### 2. 相依資源
- SWE-chat（真實開發者與編碼智慧體互動資料集）作為分佈統計與風格分析的依據，若該資料集公開，則分佈對齊過程可重現。
- 原始儲存庫與 commit（提交）/ pull request（拉取請求）來自 open-source GitHub repository（開源 GitHub 儲存庫），可透過 SWE-bench 官方管道取得。

##### 3. 模型權重與 API
實驗涵蓋七個模型：DeepSeek V4 Pro、DeepSeek V4 Flash、MiMo V2.5 Pro、MiMo V2.5、Claude Haiku 4.5、Qwen3.7 Plus、MiniMax M3。其中部分為 proprietary models（專有模型），僅能透過 API 存取；部分為 open-weight models（開放權重模型），可本地下載。雖然 exact reproducibility（完全重現）受 API 版本、取樣參數與溫度設定影響，但 RealSWE-Framework 提供標準化輸入，可大幅降低比較門檻。

##### 4. 再現難度
整體而言，RealSWE 的可重現性評價為高：任務固定、變體可配置、評估指標明確（resolution rate，解決率）。只要論文釋出變體生成程式碼與 RealSWE-bench 的具體 prompt，研究者即可在相同或不同模型上重複實驗，並進行自訂的 controlled ablations（控制消融）。

#### 未來研究方向

##### 1. 擴展資訊分類法與任務類型
目前 information taxonomy（資訊分類法）主要針對 bug fix（錯誤修復）與 feature request（功能請求）。未來可納入 refactoring（重構）、performance optimization（效能優化）、test generation（測試生成）、documentation（文件）等任務，並發展對應的資訊欄位，例如 performance target（效能目標）、test coverage requirement（測試覆蓋率要求）。

##### 2. 互動式與多輪對話評估
真實場景中，coding agent（編碼智慧體）可主動詢問 clarification（澄清）。未來可建構 multi-turn（多輪）版本的 RealSWE，評估模型在資訊不足時提出問題、整合答案並完成任務的能力。

##### 3. 主動資訊檢索與推論
既然 Desired Behavior（期望行為）與 Motivation（動機）如此重要，未來可研究如何讓 agent 自動從儲存庫、issue 歷史、文件或測試中推論這些信號，降低對使用者明確陳述的依賴。

##### 4. 訓練與資料增強
RealSWE-Framework 可成為 training data augmentation（訓練資料增強）工具：透過對同一任務生成多種資訊組合與風格變體，提升模型對真實使用者請求的穩健性（robustness）。

##### 5. 跨語言與文化差異
目前研究以英文為主。未來可探討不同語言、文化背景下的使用者請求風格，以及模型對非英語、混合語言或特定領域術語的處理能力。

##### 6. 解釋環境與重現步驟何時有用
實驗發現 Environment Information（環境資訊）與 Reproduction Steps（重現步驟）在現有設定下無顯著效益。未來可設計任務，使測試無法自動重現 bug（例如涉及特定硬體、外部服務或競態條件），進一步研究這些欄位的邊界條件與價值。

##### 7. 結合真實商業代理與工具使用
未來可在具備檔案瀏覽、執行 shell、網頁搜尋等工具的完整 agent 系統上評估 RealSWE，觀察工具使用是否能彌補資訊稀疏帶來的效能損失，並探討 software engineering performance（軟體工程效能）在更真實部署環境中的表現。

## 論文問答

**Q1：在編碼智慧體評估中，「基準與現實差距」指的是什麼？**
A：「基準與現實差距」指的是現有 SWE-bench 系列基準的輸入來自精心整理的 GitHub issue，通常篇幅長、結構完整且語氣正式，而真實使用者請求卻往往簡短、口語化且資訊稀疏。研究發現，僅含問題陳述或只有少量額外脈絡的提示佔真實使用者請求的 88%，但在 SWE-bench Verified 與 Pro 中只佔 7%。這種落差意味著排行榜上的高分解決率，可能無法直接反映智慧體在實際使用場景中的軟體工程效能。

**Q2：現有的真實導向基準（如 CURSORBENCH 或啟發式變體）為何不足以解決這個問題？**
A：CURSORBENCH 雖然使用真實程式設計對話，但屬於閉源資料集，無法供研究者獨立檢驗或重複使用；而開放的啟發式變體則常透過截斷問題陳述或注入模糊性來模擬真實輸入，缺乏對真實使用者資料的系統性分析。更重要的是，這些方法通常同時改變任務規格的多個屬性，使得效能變化難以歸因於特定資訊欄位或語言特徵。因此，它們雖然證實了差距存在，卻無法說明差距的成因或如何測量。

**Q3：為何要將「資訊組成」與「語言風格」分開研究？**
A：因為編碼智慧體的表現不僅取決於任務本身的難度，也深受任務「如何被描述」的影響；若將資訊內容與表達方式混為一談，就無法判斷效能下降是源自缺少關鍵線索，還是單純因為語氣不同。透過獨立操控這兩個軸向，研究者可以進行精確的消融實驗，找出哪些資訊欄位真正具有價值。這種拆解也為使用者提供了具體、可操作的改進建議，而不只是籠統地說「提示要寫清楚」。

**Q4：RealSWE 的核心方法是什麼？**
A：RealSWE 首先從 SWE-chat 這個真實開發者與編碼智慧體互動資料集中，歸納出六類資訊分類法與四個語言風格維度；接著從 SWE-bench Verified 與 Pro 中選出 381 個底層任務，為每個任務建立多變體任務家族。每個家族共享相同的底層任務與黃金修補檔，只在資訊組成與語言風格上有所不同。這種設計讓研究者能在固定任務難度的前提下，系統性地比較不同提示形式對模型表現的影響。

**Q5：相較於 SAVING SWE-bench，RealSWE 的關鍵創新在哪裡？**
A：SAVING SWE-bench 會同時改變任務規格的多個性質，難以將效能變化歸因到單一欄位；RealSWE 則把每個任務視為獨立可控的多變體家族，能單獨消融「期望行為」、「動機」、「重現步驟」或「環境資訊」等欄位。此外，RealSWE 的變體是根據 SWE-chat 中真實使用者請求的實證分布來設計，而非單純啟發式地截斷或加雜訊。它同時釋出了固定評測集 RealSWE-bench 與可設定框架 RealSWE-Framework，兼顧標準化比較與客製化研究需求。

**Q6：在建立多變體任務家族時，作者做了哪些重要設計選擇？**
A：作者刻意保持每個家族的底層任務與黃金修補檔不變，只讓提示在資訊組成與語言風格上產生差異，以確保任何效能變化都可歸因於提示本身。針對 bug-fix 與 feature-request 兩類任務，他們設計了不同的資訊欄位，例如 bug-fix 強調「期望行為」，feature-request 則強調「動機」。這種組合式設計不僅能進行單一欄位消融，也能任意組合多個欄位，從而模擬各種真實使用者可能給出的輸入形式。

**Q7：RealSWE 的主要實驗結果是什麼？**
A：研究評估了七個當代大型語言模型，發現相較於原始 SWE-bench 風格的題目，真實風格輸入平均讓解決率下降 6.4 個百分點，且所有模型在 RealSWE-bench 上都有所衰退。更有趣的是，真實輸入會改變模型之間的相對排名，顯示不同模型對稀疏或非正式提示的耐受度並不一致。這些結果凸顯了僅用傳統 SWE-bench 排行榜來比較編碼智慧體能力，可能會高估或扭曲模型在真實場景中的表現。

**Q8：控制實驗揭示了哪些資訊欄位真正影響效能？**
A：對於 bug-fix 任務，加入「期望行為」能顯著提升成功率約 8 個百分點，相當於 17% 的相對增益；相對地，「重現步驟」與「環境資訊」雖然增加了 token 數量，卻沒有帶來可測量的效益。對於 feature-request 任務，加入「動機」則可提升最多 7 個百分點。這說明並非所有資訊都同等重要，某些欄位是關鍵信號，而另一些欄位只是增加輸入長度。

**Q9：語言風格的改變對模型表現有何影響？**
A：研究發現語言風格的影響相對較小，且效果因模型而異；無論是正式或口語語氣、祈使句或陳述句，都沒有對所有模型產生一致且顯著的效能變化。這與資訊組成的強烈效應形成鮮明對比，顯示「提示說了什麼」比「怎麼說」更為關鍵。因此，使用者在撰寫提示時，應優先確保包含關鍵資訊欄位，而非過度糾結於語氣或句式。

**Q10：根據研究發現，終端使用者應如何撰寫提示以提升編碼智慧體的表現？**
A：使用者在回報 bug 時應明確說明「期望行為」，在提出功能請求時則應補充「動機」，因為這兩項資訊是研究發現最有價值的信號，但真實提示中卻經常缺失。研究指出，只有約 5% 的真實使用者提示會包含這類資訊，而明確補充後能顯著提升模型的軟體工程效能。換句話說，與其讓智慧體從稀疏描述中推測意圖，不如主動提供「希望發生什麼」以及「為什麼需要這個改變」。

**Q11：對於編碼智慧體產品的設計者，這項研究有哪些實務啟示？**
A：產品設計者可以在使用者介面中主動引導使用者補充「期望行為」或「動機」，例如在提交問題前彈出結構化欄位或追問問題。智慧體本身也應具備主動澄清的能力，當偵測到關鍵資訊缺失時，能向使用者詢問最具價值的問題，而非被動接受稀疏提示。這樣的設計不僅能提升實際解決率，也能縮小實驗室基準與真實使用場景之間的落差。

**Q12：這項研究對整個軟體工程與 AI 評估領域可能帶來什麼影響？**
A：RealSWE 將評估焦點從單純比較任務難度，擴展到「任務如何被溝通」這一維度，促使社群更重視提示品質與資訊完整性。它提供了一個開源且可設定的評估框架，讓後續研究能夠在標準化環境下探討不同溝通形式對編碼智慧體的影響。長遠來看，這有助於開發更能理解並處理規格不足、口語化使用者請求的下一代編碼智慧體。

**Q13：RealSWE 有哪些已承認的限制？**
A：RealSWE 的任務仍衍生自 SWE-bench Verified 與 Pro，因此其底層任務分布、程式語言與開源儲存庫範圍可能無法涵蓋所有真實軟體工程場景。研究主要聚焦於文字提示，尚未納入多輪對話、互動式澄清或多模態輸入等更豐富的互動形式。此外，用於匹配分布的 SWE-chat 資料集雖然規模龐大，但仍可能無法完全代表全球所有開發者的使用習慣與語言背景。

**Q14：目前仍有哪些失敗案例或尚未解答的問題？**
A：即使補充了關鍵資訊，部分模型仍然無法成功解決某些任務，顯示資訊完整性並非唯一的瓶頸。語言風格對不同模型產生不一致的影響，其背後機制仍待更深入的分析。另外，為何「重現步驟」與「環境資訊」在實驗中未帶來顯著效益，也值得進一步探討，例如是否因為模型已能從儲存庫或測試中推斷出相關資訊。

**Q15：未來研究可以朝哪些方向延伸？**
A：未來可以將 RealSWE 的組合式評估方法擴展到多輪互動與主動澄清場景，研究智慧體應如何提問才能最有效獲取關鍵資訊。也可以結合多模態輸入，例如截圖、日誌檔或程式執行影片，來模擬更真實的開發者工作流程。此外，將這套評估框架應用到程式碼審查、測試生成或重構等其他軟體工程任務，也有助於全面理解溝通形式對 AI 輔助軟體工程的影響。

## 實務應用指南

### 適用場景

1. **企業內部編碼智慧體上線前的真實壓力測試**  
   在將 Claude、DeepSeek、Qwen 等模型導入內部開發工具前，可用 RealSWE-Framework 把現有 SWE-bench 任務轉換成員工實際會輸入的簡短、口語化提示，評估模型在資訊稀疏情境下的解決率，避免上線後才發現「基準分數高、實際表現差」。

2. **客服／工單系統自動轉譯使用者回報**  
   當使用者透過 Slack、Jira 或 GitHub issue 回報「這個在空輸入時會 crash」這類片段資訊時，可依 RealSWE 的資訊分類法（問題陳述、期望行為、重現步驟、環境資訊、動機）自動補全結構化欄位，再餵給編碼智慧體，提升首次修復成功率。

3. **模型選型與採購決策**  
   不同模型對「資訊組成」與「語言風格」的敏感度不同，RealSWE 的多變體任務家族能區分出哪些模型在真實使用者請求下排名會變動，協助採購團隊選出最適合自身使用者語境的模型，而非只看原始 SWE-bench 排行榜。

4. **提示工程與 Agent 引導介面設計**  
   產品團隊可根據研究發現——對 bug 修復補上「期望行為」、對功能請求補上「動機」能顯著提升效能——在 UI 中設計引導式表單或自動追問機制，把使用者原本遺漏的關鍵資訊補齊。

5. **教育與訓練資料生成**  
   想訓練或微調專屬 coding agent 時，可用 RealSWE-Framework 產生同一底層任務的多種資訊組合與語言風格變體，作為多樣化訓練資料，強化模型對口語化、規格不足提示的穩健性。

### 實作前置條件

- **資料準備**
  - 至少能取得 SWE-bench Verified 或 Pro 的任務與黃金修補檔作為底層任務來源。
  - 若有自家使用者與編碼智慧體的互動紀錄（類似 SWE-chat），可用來校準「資訊組成」與「語言風格」的分布；若無，可直接採用 RealSWE-bench 的固定分布。
- **運算資源**
  - 可執行 SWE-bench 評測流程的 sandbox 環境（Docker／容器化測試）。
  - 足夠的 API 額度或 GPU 資源：381 個多變體任務家族 × 多種資訊組合，評估七個模型規模的實驗可能產生數千至上萬次呼叫。
- **技術與人員能力**
  - 熟悉 Python、Git、SWE-bench harness 與測試驗證流程。
  - 具備提示工程與基礎統計分析能力，能解讀「百分點差異」與控制變因。
  - 建議至少一名成員理解論文中的六類資訊分類法與四個語言風格維度，以確保變體生成符合研究定義。

---

### 實作步驟建議

1. **盤點與分類現有使用者提示**  
   收集內部真實使用者請求，依論文提出的資訊分類法標註每則提示包含哪些欄位（問題陳述、期望行為、重現步驟、環境資訊、動機、額外資訊），並判斷語言風格（正式／口語、陳述句／祈使句等），建立自身分布基線。

2. **對齊 RealSWE 的任務與分布**  
   從 SWE-bench Verified／Pro 中選出與內部場景相近的任務，使用 RealSWE-Framework 產生多變體任務家族。若無法取得內部分布，可直接採用 RealSWE-bench 的固定評估集，確保結果可與論文比較。

3. **設計控制實驗**  
   固定底層任務與黃金修補檔，僅改變單一資訊欄位或語言風格維度，例如：  
   - 僅問題陳述 vs. 問題陳述 + 期望行為  
   - 正式語言 vs. 口語化語言  
   這樣才能像論文一樣，分離出「期望行為」或「動機」的獨立貢獻。

4. **執行評測並記錄成本**  
   在 sandbox 中執行各變體，記錄解決率、token 用量、執行時間。特別注意「重現步驟」與「環境資訊」雖增加 token，但論文顯示未必提升效能，需驗證是否也出現在自身資料中。

5. **分析並轉化為產品規則**  
   根據結果建立提示模板：bug 修復模板強制要求「期望行為」，功能請求模板強制要求「動機」。同時標記對語言風格敏感的模型，作為未來選型依據。

6. **持續監控與迭代**  
   上線後持續收集真實互動，定期與 RealSWE 分布比對，當使用者輸入風格漂移時，重新校準變體生成策略。

---

### 潛在風險與注意事項

- **分布偏移風險**  
  RealSWE 是依 SWE-chat 的分布建構，若你的使用者族群（例如非英語母語、企業內部工具）語言習慣不同，直接套用固定評估集可能產生偏差。建議用內部資料重新校準。

- **變體生成改變語義**  
  在改寫語言風格或刪減資訊欄位時，可能不小心改變任務本身的難度或甚至答案。需人工抽樣檢查，確保黃金修補檔仍然適用。

- **過度推論小樣本差異**  
  某些資訊組合的樣本數可能較少，百分點差異未必顯著。建議搭配統計檢定或 bootstrap 信賴區間，避免把雜訊當成洞察。

- **成本與延遲**  
  多變體評測會快速消耗 API 預算與運算時間。可先從與業務最相關的任務子集（例如前端 bug、API 功能請求）開始，再擴大到完整評估。

- **隱私與資料安全**  
  若使用內部真實提示校準分布，需去識別化並避免將含有機敏程式碼的任務上傳至公共評測服務。

### 與其他技術的整合建議

- **CI／CD 品質閘門**  
  將 RealSWE-bench 納入模型更新或 prompt 改版前的自動化回歸測試，確保新版本在真實使用者請求下沒有退化。

- **RAG 與上下文檢索**  
  當使用者提示缺少「環境資訊」或「重現步驟」時，可串接程式碼檢索模組自動從儲存庫、README、requirements 中補齊，減少對使用者輸入完整度的依賴。

- **人機協作澄清機制**  
  結合 RealSWE 的資訊分類法設計主動澄清對話：當偵測到 bug 提示缺少期望行為，或功能請求缺少動機時，自動追問使用者，而非直接讓模型猜測。

- **可觀測性與回饋迴路**  
  在生產環境記錄每次請求的資訊欄位覆蓋率與最終是否解決，定期將這些資料餵回 RealSWE-Framework，形成「真實資料 → 分布校準 → 評測 → 產品改進」的閉環。

- **提示豐富層（Prompt Enrichment Layer）**  
  在進入編碼智慧體前，先由一個輕量模型或規則引擎將口語化輸入轉譯為結構化欄位，並依據 RealSWE 發現的高價值欄位進行補強。

---

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦論文的核心結論：對 bug 修復明確寫出「期望行為」、對功能請求說明「動機」，能顯著提升編碼智慧體的表現。接著看圖 1 與表 1，理解真實提示和 SWE-bench 題目的差距，不必一開始就深入變體生成細節。

- **AI 工程師**  
  重點閱讀 RealSWE-Framework 的設計與控制實驗方法，學習如何固定底層任務、只改變資訊組成與語言風格。實作時可參考論文的六類資訊分類法與四個語言風格維度，建立可重複的評測 pipeline。

- **研究人員**  
  本研究的價值在於將「基準與現實差距」拆解為可操作的變因。建議深入分析各資訊欄位的因果效應、語言風格的模型依賴性，以及多變體任務家族在評估穩健性上的方法學貢獻，可進一步延伸至互動式澄清或主動學習研究。

- **產品經理**  
  把論文當成設計依據：真實使用者通常只給問題陳述，但模型最需要的是期望行為與動機。建議從 UI／UX 角度思考如何透過表單、追問或範例提示，引導使用者補上這兩項關鍵資訊，同時用 RealSWE-bench 作為選型與上線前的驗收標準。
