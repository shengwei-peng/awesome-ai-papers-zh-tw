Wactorz 的方法論核心在於將三個原本分屬不同研究社群的典範融合為一個統一的執行環境：**Erland/OTP 的演員模型與監督樹**（Actor Model with Supervision Trees）、**執行階段程式碼生成的 LLM 代理**（Runtime Code-Generating LLM Agents），以及 **MQTT 發布/訂閱物聯網匯流排**（Pub/Sub IoT Bus）。這種融合並非僅是概念上的拼貼，而是針對「實體 AI」（Physical AI）場景中代理必須長期存活、容忍自身錯誤、並部署於感測器旁的低功耗邊緣節點（Edge Node）所設計的系統性回應。

**架構層次與角色分工**

系統採用單一 Python `asyncio` 行程搭配獨立的 Mosquitto 代理伺服器（Broker），所有協調皆透過 MQTT 主題（Topic）進行。每個代理皆為一個 `Actor`，具備收件匣（Inbox）、訊息迴圈（Message Loop）、每 10 秒發送一次的心跳（Heartbeat），以及一個鍵值對的 `persist()`/`recall()` 介面。狀態儲存採分層策略：結構化鍵值路由至 SQLite、訓練後模型（Trained Model）、numpy 陣列與張量（Tensors）路由至獨立的 Blob 檔案、其他 Python 物件則以 pickle 序列化。代理的身分以 `name@node` 格式定址，使兩台機器可各自運行同名代理，這是後續即時遷移（Live Migration）的基礎。

**代理生成流程**

當使用者以自然語言提出請求（例如「當 PC 攝影機偵測到人時打開辦公室燈」），`MainActor` 先進行意圖分類（Intent Routing），區分為直接驅動、Home Assistant 查詢、管線（Pipeline）或純聊天。管線請求會被路由至一個**每請求臨時生成**的 `PlannerAgent`，該代理輸出一份 JSON 規劃，並為每個步驟產出定義 `setup()`、`process()` 與 `handle_task()` 三個方法的 Python 原始碼。每個程式碼區塊隨即被編譯為一個 `DynamicAgent`，以「無重啟」（no restart）策略生成至運行中的系統。`InstallerAgent` 會在生成前 `pip install` 宣告的相依套件；不在白名單（Allow-list）上的套件則需操作員於儀表板（Dashboard）核准。此外，系統維護一份受信賴食譜目錄（Trusted Recipes），涵蓋時序收集、異常偵測、天氣、能源等常見需求，可在無需生成程式碼的情況下直接使用。

**基於主題的探索機制**

Wactorz 最具方法論創新性的設計在於「**以主題而非名稱進行探索**」（Discovery by Topic, Not by Name）。代理之間從不直接以名稱定址彼此，而是透過 MQTT 主題進行發布與訂閱。`TopicBus` 為每個主題註冊一份**合約**（Contract），記錄其生產者、消費者，以及一份實際承載的訊息樣本（Captured Sample）。當後續請求需要已存在的資料流（例如「計算攝影機看到的人數」），規劃者在撰寫程式碼前會先取得對應的合約與樣本，因此消費者讀取 `payload["person"]` 是因為生產者實際發送的欄位即為此，而非來自第二次 LLM 呼叫的猜測。此機制消除了多 LLM 管線中兩個代理對欄位名稱不一致的經典失敗模式，並使代理具備可替換性：只要主題與結構保持不變，重新命名或重新生成生產者後其消費者仍可正常運作。

**監督與自我修復**

由於程式碼由模型生成，錯誤被視為「預期」而非「例外」。系統採取多層防禦：生成程式碼通過一個**預執行驗證器**（Pre-execution Validator），阻擋 shell 執行、檔案刪除與 `eval`；一個**消毒器**（Sanitiser）修正 LLM 最常見的錯誤（將同步方法誤加 `await`）；`setup()`、`process()` 或 MQTT 訂閱回呼中的反覆執行階段錯誤會將程式碼與追蹤資訊（Traceback）回傳給 LLM 進行**就地修復**（In-place Repair），修復結果持久化至生成註冊表（Spawn Registry）；`process()` 呼叫則受逾時保護（Timeout-guarded）。在更高層級，`Supervisor` 採用 `ONE_FOR_ONE` 策略：當機的代理單獨重啟並重新載入其持久化狀態。重啟採用**退避**（Backoff）而非停止策略——連續當機後延遲會增長至數分鐘，最終可達一小時，因為代理所依賴的服務中斷通常會自行恢復，而被淘汰的代理會在有人注意到之前持續停機。`MonitorActor` 追蹤心跳與錯誤註冊表，重啟降級的代理，但刻意不重啟無法編譯的代理（此類代理會被重新規劃）。

**Wiring 檢視與系統可觀察性**

儀表板中的 **Wiring 檢視**（亦可透過 `GET /api/wiring` 取得）將代理與主題繪製為一張圖，可選擇依機器分組，並標記三類問題：代理發布但無人讀取的主題；訂閱者所訂主題無生產者且未觀察到任何訊息（感測器、Home Assistant 或腳本預期發布的根主題除外）；以及**欄位不匹配**（Field Mismatch），即代理宣告讀取的欄位在主題中並不存在。主題的實際承載內容以觀察到的為準，若無則回退至生產者宣告的內容。選取代理或主題會顯示其最後一筆承載內容。該檢視本身不保留狀態，僅在查詢時讀取主題註冊表。

**即時遷移與模型分發**

代理可在邊緣節點（如 Raspberry Pi）上生成，並透過 MQTT 匯流排在節點間即時遷移。訓練後的模型可在主機器上儲存一次，依版本提供給需要該模型的代理所在節點。此機制使資源受限的邊緣裝置無需重複儲存大型模型。

#### 實驗數據解讀

1. **從單一聊天請求建立攝影機到燈具的自動化**：使用者以自然語言請求「當 PC 攝影機偵測到人時打開辦公室燈」，`PlannerAgent` 將此意圖轉化為 JSON 規劃並生成對應的 `DynamicAgent`，無需人工介入即可完成端到端部署。

2. **新增第二個代理並觀察自我修復**：第二個代理透過主題自動連線（Auto-wired）至第一個代理，並刻意植入一個**除以零錯誤**（Division-by-Zero）。系統的監督機制偵測到錯誤後，將程式碼與追蹤資訊回傳給 LLM，LLM 完成就地修復，代理在**不遺失其計數狀態**的情況下恢復運行。此結果驗證了「狀態持久化」與「程式碼修復」兩個機制的正交性——修復的是程式碼，而非狀態。

3. **部署全新的 Raspberry Pi 節點並即時遷移代理**：在示範過程中部署一台全新的 Raspberry Pi，並將代理即時遷移至該節點，驗證了 `name@node` 定址機制與 MQTT 匯流排的跨節點協調能力。

**數據意涵**

- **$0.13 的模型使用成本**顯示 LLM 呼叫的經濟可行性：規劃、修復與遷移的整體成本極低，使該系統在實務部署中具備成本優勢。
- **四分鐘的端到端時間**涵蓋了從自然語言請求到跨節點部署的完整流程，相較於傳統的「人工撰寫規則、測試、部署」流程，時間成本降低數個數量級。
- **狀態在修復過程中不遺失**是關鍵的正確性指標：這意味著監督重啟與狀態持久化機制的解耦設計是成功的，代理的「身分」與「程式碼」可獨立演化。
- **除以零錯誤的自動修復**展示了 LLM 作為「程式設計師」與監督者作為「安全網」的協作模式——LLM 負責創造與修正，監督者負責維持存活。

然而，論文的實證部分存在明顯限制：僅有單一示範場景（攝影機到燈具）、單一錯誤類型（除以零）、單一遷移方向（主節點到 Raspberry Pi）。缺乏多場景、多錯誤類型、多節點拓撲的系統性基準測試，也未提供代理數量、訊息吞吐量、資源消耗（CPU、記憶體、網路頻寬）等量化指標。

#### 與現有研究的比較

**與 LLM 編排框架的比較**

Wactorz 明確將自身定位於與 AutoGen（Wu et al. 2023）、CrewAI 與 LangGraph（Chase 2022）的對比中。這些框架將多代理系統建模為**對話或圖**，在單一腳本內執行，並在任務完成時終止。Wactorz 的批評指出此生命週期模型不適合實體 AI：監看攝影機、電力表或門窗感測器的代理必須**持續運行**、容忍其未撰寫程式碼中的錯誤，且常需部署於具間歇性雲端存取的**低功耗裝置**上。Wactorz 的差異化在於：(1) 代理為**長駐**（Long-lived）而非任務終止；(2) 程式碼由 LLM 在執行階段生成；(3) 監督樹提供容錯；(4) MQTT 匯流排支援跨節點遷移。

**與邊緣自動化工具的比較**

Home Assistant 規則與 Node-RED 流程同為長駐系統，但屬於**靜態**系統：每條規則皆由人工撰寫。Wactorz 的差異在於將 LLM 引入規則生成環節，使非技術使用者可透過自然語言擴展系統。

**與物聯網探索機制的比較**

論文引用了作者早期的社會物聯網（Social IoT）研究（Kasnesis et al. 2017），該研究透過本體論（Ontology）與語意規則進行物件需求與服務的匹配。Wactorz 的**主題合約**（Topic Contract）機制則從**實際承載的訊息樣本**中學習，無需預先建立共享詞彙。這對於「其結構描述（Schema）在 LLM 撰寫之前不存在」的代理而言是必要的，因為本體論匹配需要預先定義的詞彙。

**與 Erlang/OTP 的關係**

Wactorz 的監督策略直接繼承自 Erlang/OTP 的 `ONE_FOR_ONE` 模式，但將「程式碼」從靜態的編譯產物轉變為 LLM 生成的執行階段產物，並將「狀態」從 Erlang 的行程狀態轉變為 SQLite 與 Blob 檔案中的持久化鍵值。這種轉變使監督重啟可跨越節點邊界（即時遷移），這在傳統 Erlang 叢集中雖可能但較為複雜。

**限制與不足**

論文坦誠列出多項限制：(1) 預執行驗證器僅阻擋已知危險模式，新型攻擊面（如提示注入導致生成惡意程式碼）尚未完整分析；(2) LLM 修復可能引入新錯誤，需多次迭代；(3) MQTT 本身缺乏端對端加密與強認證，安全模型需另行設計；(4) 邊緣節點的資源限制（CPU、記憶體、儲存）對代理數量與模型大小構成硬約束；(5) 缺乏對大規模部署（數百至數千代理）的效能評估。

#### 未來研究方向

**1. 安全性與信任模型**

當 LLM 成為「程式設計師」時，提示注入（Prompt Injection）攻擊面隨之擴大。攻擊者可透過污染輸入資料（攝影機畫面、感測器讀數）誘導 LLM 生成惡意程式碼。未來研究應探索：(a) 形式化驗證生成程式碼的安全性質；(b) 多代理投票或共識機制以偵測惡意行為；(c) 沙箱化執行環境（如 WebAssembly、微核心）以限制代理的系統呼叫權限。

**2. 規模化與效能**

論文僅展示單一示範場景，缺乏數百至數千代理同時運行的效能資料。未來研究應系統評估：(a) MQTT 主題數量與訊息吞吐量對監督者延遲的影響；(b) SQLite 與 Blob 儲存的可擴展性；(c) 邊緣節點的資源消耗（CPU、記憶體、網路頻寬、儲存 I/O）；(d) LLM 呼叫的並行化與批次化以降低成本。

**3. 修復品質與學習**

就地修復機制目前僅依賴單次 LLM 呼叫，可能產生震盪（修復引入新錯誤）或局部最優。未來方向包括：(a) 測試驅動修復（Test-driven Repair），由系統自動生成測試案例驗證修復正確性；(b) 修復歷史學習，使 LLM 從過去的修復中累積經驗；(c) 多代理辯論機制，由多個 LLM 對修復方案進行評審。

**4. 跨節點協調與遷移**

即時遷移目前展示於主節點到 Raspberry Pi 的單一方向，未來應探索：(a) 多對多遷移與負載平衡；(b) 代理群組（Agent Group）的原子遷移，維持主題合約的一致性；(c) 異質硬體（不同架構的邊緣節點）間的代理移植；(d) 網路分割（Network Partition）下的降級運作模式。

**5. 結構描述演化與版本管理**

當生產者被重新生成時，其訊息結構可能改變，導致消費者失敗。雖然主題合約機制降低了此風險，但缺乏結構描述演化的正式管理。未來研究應引入：(a) 結構描述版本控制與向下相容性檢查；(b) 自動消費者重生成機制；(c) 灰度遷移（Gray Migration）以逐步替換生產者。

**6. 與傳統自動化生態系的整合**

Wactorz 已展示與 Home Assistant 的整合，但與 Node-RED、工業自動化系統（如 OPC UA、Modbus）的整合尚未深入。未來應發展標準化的橋接代理，使 LLM 生成的代理可無縫嵌入既有自動化基礎設施。

**7. 形式化語意與驗證**

主題合約目前僅記錄欄位名稱與樣本，缺乏形式化語意。未來可引入：(a) JSON Schema 或 Protocol Buffers 作為結構描述；(b) 時序邏輯（Temporal Logic）驗證代理行為符合預期；(c) 模型檢查（Model Checking）以探索代理互動的狀態空間。

**8. 能源與永續性**

邊緣節點常受能源限制（如電池供電的感測器）。未來應研究：(a) 代理休眠與喚醒機制以節省能源；(b) LLM 呼叫的能源成本（推論本身消耗能源）；(c) 再生能源供應下的自適應運算策略。

**9. 人機協作與可解釋性**

當 LLM 生成代理後，使用者需理解其行為以建立信任。Wiring 檢視是良好起點，但未來應發展：(a) 自然語言解釋代理決策；(b) 視覺化除錯介面；(c) 使用者回饋機制以修正代理行為。

**10. 基準測試與標準化**

最迫切的需求之一是建立標準化基準，使不同代理框架可公平比較。基準應涵蓋：(a) 從自然語言到部署的端到端時間；(b) 容錯與自我修復成功率；(c) 跨節點遷移的狀態一致性；(d) 資源消耗與成本；(e) 安全性與隱私保護。

**Q10：Wactorz 最適合哪些實務應用場景？**

**Q11：Wactorz 與 Home Assistant、Node-RED 等邊緣自動化工具相比有何優勢？**
A：Home Assistant 與 Node-RED 都是長駐但靜態的工具——每一條規則都需要人類撰寫，無法適應使用者以自然語言提出的新需求。Wactorz 則讓 LLM 成為「程式設計師」，使用者只需用聊天描述意圖，系統就會即時生成對應的代理程式碼並部署。同時，Wactorz 保留了 Home Assistant/Node-RED 的長駐特性，並加上監督樹、自我修復、即時遷移等原本屬於 Erlang/OTP 強項的能力。這種「LLM 的彈性」加上「Erlang 的可靠性」組合，是現有邊緣自動化工具所欠缺的。

**Q12：Wactorz 對邊緣 AI 部署的產業意涵為何？**
A：Wactorz 證明了 LLM 代理可以在樹莓派等級的低功耗裝置上即時生成、監督與遷移，這對邊緣 AI 的產業化具有重要意義。企業不再需要為每個新感測器或新場景預先撰寫與部署程式，而是讓現場的邊緣節點透過聊天介面「自我編程」。訓練後的模型可在主機上儲存一次，依版本推送給需要它的節點使用，降低了模型管理與分發的複雜度。這也意味著，邊緣裝置的角色從「被動執行預載邏輯」轉變為「主動參與系統演化」。

**Q13：Wactorz 在論文中坦承的限制有哪些？**
A：論文明確指出，Wactorz 並非萬能：對於「程式碼無法編譯」的代理，MonitorActor 刻意不會重啟，而是交由操作者介入處理，因為反覆重試無助於解決語法錯誤。系統仰賴 Mosquitto 作為唯一外部元件，若 MQTT 代理本身故障，所有代理都會失去協調能力。此外，LLM 生成的程式碼雖然經過預執行驗證（阻擋 shell 執行、檔案刪除、`eval`）與常見錯誤修正，但無法保證完全沒有安全漏洞或邏輯缺陷，使用者仍須對代理行為保持監督。

**Q14：Wactorz 可能遭遇哪些失敗案例？**
A：典型的失敗案例包括：LLM 生成的程式碼通過驗證但仍含有邏輯錯誤（例如錯誤的條件判斷導致代理永遠不觸發）、代理依賴的外部服務（如 Home Assistant API）長時間離線導致指數退避最終仍無法恢復，以及兩個代理對同一主題的酬載結構理解不一致（雖然合約機制已大幅降低此風險）。此外，若使用者的自然語言請求本身含糊不清，PlannerAgent 可能生成出與預期行為偏差極大的代理，需要操作者透過 Wiring 檢視來發現並修正。

**Q15：Wactorz 未來的發展方向為何？**
A：從論文的延伸版本內容可推測，未來發展可能包括：更豐富的安全模型（目前僅阻擋 shell 執行、檔案刪除與 `eval`，但對更細粒度的資源限制仍待加強）、更完整的「手寫代理」函式庫 API（讓開發者無需透過 LLM 也能享受監督、持久化與遷移能力）、更成熟的模型版本管理（將訓練後模型依版本分發到不同節點），以及更強健的 MQTT 容錯機制。此外，如何讓多個邊緣節點在沒有穩定雲端連線時仍能協調代理生成與遷移，也是值得探索的方向。

### 潛在風險與注意事項

- **LLM 生成程式碼的可預測性**：即使有預執行驗證器，模型仍可能產生非預期行為。建議對關鍵代理採用「手寫 + 監督」模式，僅對探索性任務使用生成模式。

- **狀態遺失風險**：監督者採用 ONE_FOR_ONE 重啟策略，但若 SQLite 或 pickle 檔案損毀，狀態可能遺失。應定期備份狀態儲存目錄，並在遷移前驗證狀態完整性。

- **重啟退避（backoff）造成的長時間停機**：連續崩潰後重啟間隔會延長至分鐘甚至小時。對即時性要求高的場景，應設定外部告警並準備手動介入流程。

- **主題契約漂移**：當生產者被重新生成或更名時，消費者仍能繼續運作（前提是主題與欄位形狀不變），但若欄位變更，Wiring view 會標示欄位不符。建議在變更前主動通知所有下游代理。

- **模型檔案傳輸成本**：訓練後模型透過 blob 檔案傳送至邊緣節點，大型模型會消耗頻寬與時間。應評估是否在邊緣節點預載模型，或採用較小的蒸餾版本。

- **安全模型邊界**：Wactorz 的安全設計假設 MQTT broker 與 LLM API 是可信賴的。在不受信任的網路環境中，需額外加入 TLS、broker 認證與 API 金鑰輪替機制。

- **編譯失敗的代理不會自動重啟**：論文明確指出，程式碼無法編譯的代理會被刻意標記而不重啟，需操作員介入。應建立儀表板通知流程。
