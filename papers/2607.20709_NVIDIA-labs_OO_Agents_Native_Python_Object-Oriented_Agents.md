## 摘要翻譯

傳統的代理（agent）開發分散於提示模板（prompt templates）、工具結構描述（tool schemas）、回呼程式碼（callback code）與工作流程圖（workflow graphs）之間。我們提出 NVIDIA 物件導向智慧代理（NVIDIA Object-Oriented Agents, NOOA），一個模型無關（model-agnostic）的 Python 框架，用於建構可靠的 AI 代理。NOOA 採取更簡單的方法：代理就是一個 Python 物件（Python object）。其方法（methods）是模型可以採取的動作、欄位（fields）是它的狀態、文件字串（docstrings）是它的提示詞，而型別註解（type annotations）則是契約（contracts）。程式碼本體（code body）為「…」的方法，會在執行時期由 LLM 驅動的代理迴圈（LLM-driven agent loop）完成；一般本體的方法則仍是標準的確定性 Python（deterministic Python）。這使開發者與代理面對相同的介面，因此代理行為可以像其他軟體一樣被測試、追蹤、重構（refactored）與改進。

本文有三項貢獻。（1）我們提出以 Python 物件作為代理（agent-as-a-Python-object）的程式設計模型，以及其背後的設計原則。在 Python 已有現成抽象之處，我們直接採用。代理特有的能力——包括上下文（context）、事件（events）、狀態渲染（state rendering）、長期記憶（long-term memory），以及受驗證的 LLM 迴圈（validated LLM loops）——透過簡潔的 Python 風格 API 提供，使開發者與代理都能共享同一套熟悉的程式設計模型。（2）我們辨識出六個面向模型（model-facing）的概念，據我們所知，NOOA 是首個將它們整合在單一介面上的框架：型別化輸入／輸出（typed input/output）、對即時物件（live objects）採用傳參考（pass-by-reference）、程式碼即動作（code as action）、可程式化的迴圈工程（programmable loop engineering）、顯式物件狀態（explicit object state），以及供上下文與事件使用的模型可呼叫的 harness API（model-callable harness APIs）。我們發現研究社群已在若干概念上逐漸收斂——通常以實驗性或局部功能的形式出現——並透過比較促進更廣泛的採用。（3）我們證明現有模型能有效使用此介面，無論是在針對性的能力測試（capability tests），或是在代理基準測試（agentic benchmarks）與推理基準測試（reasoning benchmarks）上，例如 SWE-bench Verified、Terminal-Bench 2.0 與 ARC-AGI-3。

### 核心貢獻（3～5點）
- 提出以 Python 物件作為代理（agent-as-a-Python-object）的程式設計模型，直接採用 Python 既有抽象，並透過 Pythonic API 暴露上下文、事件、狀態渲染、長期記憶與受驗證的 LLM 迴圈等代理能力。
- 首次將六個面向模型（model-facing）的設計概念整合於單一介面：型別化輸入／輸出（typed input/output）、對即時物件傳參考（pass-by-reference over live objects）、程式碼即動作（code as action）、可程式化的迴圈工程（programmable loop engineering）、顯式物件狀態（explicit object state），以及模型可呼叫的 harness API（model-callable harness APIs）。
- 在針對性的能力測試與多項代理／推理基準測試（SWE-bench Verified、Terminal-Bench 2.0、ARC-AGI-3）上，驗證現有模型能有效使用 NOOA 介面。

### 適合對象
AI 代理開發者、軟體工程師、機器學習研究人員，以及希望以原生 Python 物件導向方式建構可測試、可追蹤、可重構且可靠之 AI 代理的實務工作者。

## 深度分析

#### 方法論解析

NOOA（NVIDIA Object-Oriented Agents）的核心方法論可以概括為 **Agent-as-a-Python-object（以 Python 物件作為代理）**：一個完整的代理（Agent）就是一個 Python 類別（class），其欄位（field）是狀態、方法（method）是能力、文件字串（docstring）是提示詞（prompt）、型別註解（type annotation）是契約（contract），而方法本體若為 `...`（ellipsis），則由執行時期（runtime）的 LLM 驅動迴圈來完成；若為一般 Python 程式碼，則維持確定性（deterministic）執行。這種設計把「代理開發」重新框定為「物件導向程式設計」，讓開發者與模型共用同一套介面。

##### 設計原則與對應能力

論文提出五項設計原則（P1–P5），每項原則都對應到一至多項 **model-facing（面向模型的）介面能力**：

1. **P1：Reuse Python abstractions（重用 Python 抽象）**  
   不另創領域專用語言（DSL），而是直接採用 Python 既有的類別、方法、asyncio、例外處理、控制流程。對應能力包括：
   - **Loop engineering（可程式化的迴圈工程）**：單一代理或多代理編排都使用普通 Python 控制流。
   - **Explicit object state（顯式物件狀態）**：持久狀態存在代理物件的欄位中，而非僅存在對話歷史裡。

2. **P2：Reframe agentic loops as method calls（將代理迴圈重構為方法呼叫）**  
   應用程式看到的不是無結構的文字交換，而是帶有型別輸入／輸出（typed input/output）的 Python 方法呼叫。對應能力為：
   - **Typed I/O（型別化輸入／輸出）**：方法簽名（signature）同時是呼叫介面與模型可見的契約。
   - **Pass-by-reference（傳參考）**：模型操作的是即時物件（live object），而非被序列化（serialize）進提示詞的文字。

3. **P3：Move deterministic work out of the agentic loop（把確定性工作移出代理迴圈）**  
   精確規則、算術、解析、狀態轉換應寫成普通方法；語義判斷、綜合、開放式任務才交給 LLM。程式碼本體的真實與否（`...` 與否）明確標示這條邊界。

4. **P4：Unlock the model’s existing Python knowledge（釋放模型既有的 Python 知識）**  
   模型透過撰寫 Python 程式碼來採取行動，即 **CodeAct（程式碼即動作）**。CodeAct 程式碼可使用普通迴圈、條件判斷、asyncio、資料庫客戶端、繪圖函式庫與任意 import，無需學習新的工具結構描述（tool schema）或 DSL。

5. **P5：Expose the harness as explicit APIs（將 harness 以顯式 API 暴露）**  
   代理特有的概念——結構化上下文（context）、上下文渲染（context rendering）、事件歷史（event history）——以 Pythonic API 提供給開發者與模型。對應能力為：
   - **Harness APIs（harness API）**：模型可呼叫以取得 context、事件等資訊。

##### 語法與執行模型

以論文中的 `SupportAgent` 為例：

- `class SupportAgent(Agent)`：代理本身是一個 Python 類別。
- `order_db: OrderDB`：物件狀態（object state）以欄位形式存在，對模型可見且可傳參考。
- `is_refund_eligible`：具有真實程式碼本體的確定性方法，可被模型呼叫，也可被單元測試。
- `classify`：標註 `@strategy(PredictStrategy())` 且本體為 `...`，代表單次 LLM 呼叫（single-shot Predict），回傳型別 `TicketKind` 會被執行時期驗證。
- `triage`：標註 `@strategy(CodeActStrategy())` 且本體為 `...`，代表迭代式 CodeAct（iterative CodeAct）迴圈；模型可檢視 `order`、呼叫 `is_refund_eligible()` 與 `classify()`，最終必須回傳符合 `Ticket` 型別的結果。

這裡的關鍵在於 **型別註解（type annotation）同時扮演三種角色**：對開發者是靜態型別提示、對執行時期是驗證契約、對模型是輸入輸出規格。文件字串（docstring）則同時是給人看的說明與給模型看的 prompt。這種「單一表面（single surface）」大幅減少了傳統框架中 prompt template、tool schema、callback、workflow graph 彼此脫節的問題。

##### Runtime harness 的職責

雖然語法看起來像普通 Python，但 NOOA 的 harness 在背後完成多項工作：

- **Context construction（上下文建構）**：將 `self` 的欄位、方法簽名、docstring、型別資訊與傳入的 live objects 組合成模型可理解的上下文。
- **State rendering（狀態渲染）**：對 live objects 產生有界預覽（bounded preview），避免把整個資料庫塞進提示詞。
- **Validated LLM loop（受驗證的 LLM 迴圈）**：在 CodeAct 中執行模型產生的程式碼、捕捉輸出與例外、把觀察結果（observation）餵回模型，直到產生符合回傳型別的結果。
- **Runtime validation（執行時期驗證）**：透過 Pydantic 等機制在方法回傳前驗證型別與約束條件（constraint）。

換句話說，NOOA 把「提示工程（prompt engineering）」轉化為「軟體工程（software engineering）」：代理行為可以被測試、追蹤（trace）、重構（refactor）、版本控制與最佳化。

#### 實驗數據解讀

由於提供的上下文未包含具體數字表格，本節先說明論文宣稱的實驗架構與基準測試（benchmark）意涵，再指出在缺乏詳細數據時應如何審慎解讀。

##### 評估的基準測試

論文提到三項代理與推理基準測試：

- **SWE-bench Verified**：真實 GitHub issue 的軟體工程代理基準，評估代理能否在既有程式碼庫中定位 bug、修改程式碼並通過測試。它考驗長期規劃、程式碼理解、工具使用與驗證能力。
- **Terminal-Bench 2.0**：終端機代理基準，評估代理在 shell／命令列環境中執行多步驟任務的能力，強調對檔案系統、程序與命令輸出的互動。
- **ARC-AGI-3**：抽象推理與程式合成基準，要求代理從少數範例中歸納出底層轉換規則並產生正確輸出，考驗泛化與組合推理。

若 NOOA 在這些基準上取得有效結果，代表當前模型確實能夠：

1. 理解以 Python 類別與方法呈現的介面；
2. 在 CodeAct 迴圈中撰寫並執行有效程式碼；
3. 利用 pass-by-reference 的 live objects 進行狀態查詢與操作；
4. 遵守型別契約並產生結構化輸出。

##### 應如何解讀「current models use this interface effectively」

論文摘要指出「current models use this interface effectively」，這是一個關於 **介面充分性（interface sufficiency）** 的宣稱，而非單純的 SOTA（state-of-the-art）分數競賽。其意義在於：即便 NOOA 的介面比一般 tool-calling 框架更「程式碼化」，現有 LLM 仍能駕馭它。這對設計者很重要，因為它降低了採用 CodeAct + OOP 介面的風險。

然而，在沒有具體數字的情況下，我們無法判斷：

- NOOA 相較於其他框架（如 smolagents、OpenAI Agents SDK、AutoGen）的絕對或相對表現；
- 使用的模型版本、取樣參數、pass@k 設定、成本與延遲；
- 在 SWE-bench 上是否使用額外檢索、測試篩選或人類介入；
- 失敗案例的分布（例如是介面理解失敗、程式碼執行失敗，還是驗證失敗）。

因此，目前只能說這些結果 **初步證明了 NOOA 介面的可行性與表達力**，但要評估其優越性，仍需等待完整實驗表格與對照組數據。

##### 能力測試（capability tests）的可能內容

除了端對端基準，論文也提到針對性的能力測試。合理推測這些測試會涵蓋：

- **Typed I/O 遵守度**：模型是否能在被要求時回傳符合 Pydantic 模型的物件。
- **Pass-by-reference 互動**：模型能否透過參考呼叫物件方法、讀取欄位，而非僅依賴文字描述。
- **狀態持久化**：多輪 CodeAct 中，物件欄位的修改是否能正確反映並被後續步驟使用。
- **確定性方法呼叫**：模型是否能正確選擇呼叫確定性方法，而非用 LLM 重新實作相同邏輯。
- **Harness API 使用**：模型是否能透過顯式 API 查詢 context 與事件歷史。

這些測試若通過，將強化「單一表面設計確實被模型理解」的論點。

#### 與現有研究的比較

NOOA 的定位並非提出全新的單一技術，而是把多個已在社群中浮現的概念整合到同一個物件導向表面。論文明確指出六項 **model-facing ideas（面向模型的概念）**：typed input/output、pass-by-reference over live objects、code as action、programmable loop engineering、explicit object state、以及 model-callable harness APIs for context and events。以下逐一與現有研究對照。

##### 1. Typed I/O（型別化輸入／輸出）

許多框架已使用型別註解來定義工具輸入輸出，例如 **PydanticAI**、**Marvin**、**Instructor** 與 **DSPy** 的 signature。這些系統通常把型別視為「模型輸出必須符合的結構描述」。NOOA 的差異在於：型別註解同時也是 **Python 方法簽名**，因此開發者呼叫代理方法時與呼叫普通函式無異，模型也能在 CodeAct 中直接以 Python 語法操作這些型別。

##### 2. Pass-by-reference over live objects（對即時物件傳參考）

傳統 agent 框架（如 **LangChain**、**CrewAI**、早期 **OpenAI function calling**）大多將輸入序列化為 JSON 或文字後送入 prompt。這種方式簡單，但會遺失物件內部狀態、方法與動態資訊。NOOA 讓模型直接面對 live objects，類似某些互動式程式設計環境（如 **Jupyter**、**IPython**）或 **smolagents** 的 code executor，但更進一步把物件繫結到代理的 `self` 狀態，使模型能持續參考同一物件實例。

##### 3. Code as action（程式碼即動作）

CodeAct 概念源自 Wang et al. 的 *Executable Code Actions Elicit Better LLM Agents*，後續 **smolagents**、**OpenAI Code Interpreter**、**CodeActAgent** 都採用模型寫程式碼再執行的範式。NOOA 的貢獻在於把 CodeAct 嵌入物件導向類別：模型寫的程式碼可以呼叫 `self` 上的其他方法、讀取欄位、使用任意 import，從而讓「程式碼即動作」與「物件狀態」無縫結合。

##### 4. Programmable loop engineering（可程式化的迴圈工程）

多數框架使用預設的 ReAct 或 planner-executor 迴圈，若要自訂流程，需學習 workflow graph（如 **LangGraph**）或特殊配置。NOOA 則讓迴圈工程回歸 Python：開發者可用普通 `for`、`while`、`asyncio.gather`、方法呼叫來編排多步驟或多代理流程。這與 **AutoGen** 的對話式編排或 **CrewAI** 的角色流程不同，更接近「用 Python 寫程式」而非「用 YAML／圖形介面設定流程」。

##### 5. Explicit object state（顯式物件狀態）

ReAct 與多數對話式代理把狀態隱含在對話歷史中；**MemGPT** 等則透過虛擬記憶管理來擴展上下文。NOOA 把狀態放在類別欄位，使狀態對模型可見、可讀取、可修改，也讓開發者能用普通 Python 追蹤狀態變化。這類設計在物件導向代理研究中較少見，但在軟體工程實踐中非常自然。

##### 6. Model-callable harness APIs（模型可呼叫的 harness API）

部分框架（如 **OpenAI Agents SDK**、**AutoGen**）提供 context 或 tracing API，但通常是給開發者使用。NOOA 將 context 與 events 暴露為模型也能呼叫的 Pythonic API，使代理能主動查詢自己的執行歷史與環境狀態，這對於自我反思（self-reflection）與錯誤修復很重要。

##### 優勢總結

相較於現有研究，NOOA 的主要優勢在於 **統一性（unification）**：它把 prompt、tool schema、state、workflow、validation 全部收斂到一個 Python class，減少了開發者與模型需要學習的多種抽象。這也帶來更好的可測試性、可追蹤性與重構性。

##### 限制

- **語言綁定**：目前僅適用 Python 生態系；若要在其他語言複製相同哲學，需要重新設計。
- **安全性**：CodeAct 執行模型產生的程式碼需要強固的沙箱（sandbox）；論文未詳述安全機制。
- **模型能力門檻**：雖然論文宣稱 current models 能有效使用，但較弱模型可能在撰寫正確 Python、理解 `self` 狀態與型別契約上表現不佳。
- **除錯複雜度**：當代理迴圈失敗時，錯誤可能同時來自模型生成的程式碼、harness 渲染或驗證邏輯，追蹤難度高於純文字對話。
- **狀態渲染挑戰**：對於大型物件或資料庫，如何產生有界且資訊豐富的預覽仍是開放問題。

#### 可重現性評估

可重現性（reproducibility）是評估任何代理框架的關鍵。根據提供的上下文，目前可做出以下判斷：

##### 程式碼與框架可用性

論文標註為「NVIDIA-labs OO Agents」，暗示可能來自 NVIDIA 的開源實驗室，但**提供的文本中並未給出 GitHub 儲存庫、套件安裝指令或官方文件連結**。若 NOOA 最終以開源 Python 套件形式釋出（例如 `pip install nooa`），則重現門檻會顯著降低；反之，若僅為內部原型，則社群難以驗證。

##### 資料集與基準

- **SWE-bench Verified**、**Terminal-Bench 2.0**、**ARC-AGI-3** 均為公開資料集，這部分沒有可用性問題。
- 但重現需要知道：使用的模型端點（endpoint）、API 版本、溫度（temperature）、top-p、最大迭代次數、pass@k 設定、以及是否使用額外檢索或測試篩選。

##### 模型權重

NOOA 標榜 **model-agnostic（模型無關）**，因此不依赖特定模型權重。重現時可選用任何支援程式碼生成與工具使用的 LLM（如 GPT-4、Claude、Llama、Qwen 等）。然而，不同模型的表現差異可能很大，論文需報告所使用的模型與設定，才能進行公平比較。

##### Harness 實作細節

NOOA 的可重現性高度依賴 harness 的具體實作，包括：

- 如何將 `self` 與 live objects 渲染給模型；
- CodeAct 程式碼執行環境（是否使用 Docker、restricted Python、IPython kernel）；
- 驗證與重試策略（例如 Pydantic 驗證失敗後如何反饋給模型）；

#### 未來研究方向

NOOA 的物件導向代理範式開啟了多個值得後續探索的方向：

##### 1. 多代理系統的物件導向編排

既然單一代理是 Python 物件，多代理系統可以透過「物件組合」來實現：一個代理的方法呼叫另一個代理的方法，或透過 `asyncio.gather` 並行執行多個代理。未來可研究如何在此基礎上設計型別安全的 handoff（交接）機制、代理間契約與共同狀態管理。

##### 2. 智慧化的狀態渲染與上下文壓縮

Pass-by-reference 的挑戰在於物件可能非常龐大。未來可發展自適應的 state rendering 技術：根據模型當前任務動態選擇要暴露的欄位、產生摘要（summary）、或使用 diff 表示變化，以在有限上下文長度內最大化資訊密度。

##### 3. 自動策略選擇與迴圈工程最佳化

目前開發者需手動為方法選擇 `PredictStrategy` 或 `CodeActStrategy`。未來可研究如何根據方法簽名、docstring、歷史表現或任務複雜度，自動選擇或混合策略，甚至讓模型在執行時期切換策略。

##### 4. 安全沙箱與最小權限執行

CodeAct 讓模型執行任意 Python，帶來顯著安全風險。未來需要標準化的沙箱方案，例如基於 capability-based 權限、細粒度檔案系統隔離、網路限制與資源配額，並將這些安全策略也表達為 Python 物件或裝飾器。

##### 5. 型別驅動的測試生成與形式驗證

由於 NOOA 的方法具有明確型別契約，可以自動生成單元測試、模糊測試（fuzzing）或甚至輕量級形式驗證，以確保代理在重構後仍維持行為正確性。這將進一步強化「代理開發即軟體工程」的願景。

##### 6. IDE 與開發者工具整合

NOOA 的設計非常適合整合到現代 IDE：例如視覺化哪些方法是 agentic、哪些欄位會被渲染給模型、自動補全 harness API、以及逐步執行 CodeAct 迴圈。這類工具可顯著降低開發與除錯門檻。

##### 7. 跨語言擴展

雖然 NOOA 根植於 Python，但其核心哲學——以語言原生抽象作為代理介面——可推廣至其他程式語言。未來可探索 TypeScript、Rust、Julia 等語言的等價設計，並研究不同語言訓練資料分布對 agent readiness 的影響。

##### 8. 更廣泛的評估與成本分析

未來應在更多基準（如 WebArena、OSWorld、GAIA）上評估 NOOA，並詳細報告延遲、token 消耗、API 成本與失敗模式。這有助於理解 CodeAct + OOP 介面在真實應用中的經濟性與可靠性。

## 論文問答

**Q1：NOOA 想要解決傳統代理開發中的什麼核心問題？**
A：傳統代理開發把原始碼拆散到提示模板、工具結構描述、回呼程式碼、工作流程圖與編排程式碼等多種不同工件中，導致開發者必須學習框架專屬的領域語言。NOOA 提出「代理即 Python 物件」的模型，把代理、動作、狀態、提示與契約統一成單一 Python 類別。這種做法讓代理開發回歸到熟悉的軟體工程實踐，也讓程式碼更容易測試、追蹤與重構。

**Q2：為什麼把代理原始碼分散在不同媒介會造成問題？**
A：當能力被拆成提示模板、結構描述與回呼時，開發者無法直接使用 Python 中已經成熟的型別、變數作用域、控制流程與物件狀態等抽象。這不僅提高了學習門檻，也讓行為難以像普通程式碼一樣進行單元測試、版本控制與重構。NOOA 透過直接採用 Python 既有的類別、方法、欄位、asyncio 與例外機制，消除了這種碎片化所帶來的摩擦。

**Q3：什麼是「代理就緒性」，NOOA 如何利用它？**
A：代理就緒性指的是語言模型能直接理解並使用開發介面的能力，而 LLM 的訓練資料中充斥著大量 Python 程式碼與常見函式庫。NOOA 讓代理本身就是原生 Python 物件，因此模型可以運用既有的 Python 知識來撰寫程式碼、呼叫方法與操作物件。這對人類開發者與自主編碼代理都同樣直覺，達到降低學習成本與提升模型可用性的雙重效益。

**Q4：請說明「以 Python 物件作為代理」的程式設計模型。**
A：在 NOOA 中，代理是一個繼承自 `Agent` 的 Python 類別，類別欄位代表模型可見的持久狀態，方法則代表代理能執行的動作。文件字串會被當成提示詞，型別註解則成為輸入輸出的契約；方法本體若為 `...`，執行時期會由 LLM 驅動的迴圈來完成，而普通本體則維持確定性 Python 行為。因此，同一個類別同時是原始碼、提示介面、型別契約、工具介面與狀態邊界。

**Q5：NOOA 結合了哪六個模型面向的介面能力？**
A：這六個能力分別是：型別化輸入／輸出、對即時物件的傳參考、程式碼即動作、可程式化的迴圈工程、顯式物件狀態，以及模型可呼叫的 harness API。根據論文說法，NOOA 是首個將這六項能力整合在單一表面的框架。這些能力對應到五項設計原則，讓開發者與模型共享同一套熟悉的 Python 介面。

**Q6：NOOA 如何在同一個類別中區分確定性程式碼與代理迴圈？**
A：區分方式完全體現在方法本體：具有真實程式碼本體的方法是普通 Python，例如 `is_refund_eligible` 會直接回傳布林值；而本體為 `...` 的方法則標記為代理方法，並透過 `@strategy(PredictStrategy())` 或 `@strategy(CodeActStrategy())` 指定執行策略。執行時期 harness 會對這些代理方法啟動受驗證的 LLM 迴圈，並在回傳前驗證型別與約束條件。

**Q7：論文在哪些基準測試上評估 NOOA？**
A：論文選用了 SWE-bench Verified、Terminal-Bench 2.0 與 ARC-AGI-3 這三個涵蓋不同面向的基準測試。SWE-bench Verified 評估軟體工程任務，Terminal-Bench 2.0 評估終端機操作能力，ARC-AGI-3 則評估抽象推理能力。此外，作者也進行了一系列針對介面能力的能力測試，以驗證當前模型能否有效使用 NOOA 的 Python 物件介面。

**Q8：針對性能力測試可能檢驗哪些項目？**
A：這些測試可能檢驗模型是否能正確解析型別化輸入、操作傳參考的即時物件、透過 CodeAct 撰寫並執行 Python 程式碼、呼叫 `self` 上的方法、使用 harness API 存取上下文與事件，以及回傳經過 Pydantic 驗證的結構化輸出。成功通過這些測試代表模型不僅能讀懂 Python 類別，還能在執行時期主動運用物件導向介面完成任務。

**Q9：論文是否提供消融研究或與其他框架的比較？**
A：雖然摘錄中未詳細列出數據表格，但論文明確提到會與十四個其他框架和 harness 進行比較，並對照六項模型面向能力。這些比較旨在說明社群已在部分實驗性功能上朝這些方向收斂，而 NOOA 首次將它們整合於單一表面。未來工作可能會進一步針對不同策略、模型規模與安全沙箱進行更深入的消融分析。

**Q10：`SupportAgent` 範例在實際客服場景中如何應用？**
A：`SupportAgent` 可以接收顧客訊息、照片與即時 `Order` 物件，先透過 `classify` 代理方法將問題分類為退款、損壞或其他，再呼叫確定性的 `is_refund_eligible` 檢查退款資格，最後回傳帶有優先級與摘要的 `Ticket`。由於輸入是即時物件而非序列化文字，它能直接與現有訂單資料庫與影像管線整合。整個類別可以像後端服務程式碼一樣進行單元測試、版本控制與部署。

**Q11：把代理程式視為普通軟體會帶來哪些產品與工程優勢？**
A：開發者可以使用標準的型別檢查、單元測試、程式碼審查、版本控制與重構工具來維護代理行為。確定性方法可以直接被測試，而代理方法的事件歷史則提供了可追蹤性。這種設計把提示工程重新納入軟體工程的規範之中，有助於提升系統的可靠性、可維護性與協作效率。

**Q12：NOOA 可能對未來的代理框架設計產生什麼影響？**
A：NOOA 示範了強大執行環境仍可提供簡潔 Python 程式設計模型的可能性，類似 PyTorch 對深度學習的影響。它可能促使更多框架放棄專屬 DSL，轉而採用宿主語言的原生物件導向抽象。這種收斂將同時造福人類開發者與自主編碼代理，使代理系統更容易被建構、理解與擴展。

**Q13：NOOA 目前有哪些主要限制？**
A：NOOA 相當依賴模型撰寫正確 Python 程式碼並遵守型別契約的能力，較弱的模型可能會頻繁失敗。此外，執行模型產生的程式碼需要安全的沙箱環境，以避免意外或惡意的副作用。對於需要長期規劃與多代理協作的複雜任務，仍須謹慎設計迴圈工程與狀態管理。

**Q14：在什麼情況下，Python 物件介面可能會失效？**
A：當模型幻覺出不存在的屬性或方法、對共享狀態進行未預期的修改，或誤解大型物件的有限預覽時，介面可能會出錯。長期任務中，錯誤會隨著步驟增加而累積，導致偏離目標。雖然型別驗證、確定性守衛與事件追蹤能減輕這些風險，但無法完全消除所有失敗模式。

**Q15：NOOA 與相關領域未來可能朝哪些方向發展？**
A：未來可以強化狀態渲染、長期記憶整合、多代理編排模式，以及更嚴格的安全沙箱與更廣泛的模型比較。作者也希望社群能更廣泛採用這六項模型面向能力，以推動介面標準化。另一個可能方向是將物件導向代理模型擴展到其他程式語言，同時保留開發者與模型共享同一套程式設計介面的核心精神。

## 實務應用指南

## 適用場景

1. **企業內部客服與工單分流系統**  
   將 NOOA 的 `SupportAgent` 模式應用於客服場景：模型讀取即時訂單物件（`Order`）、呼叫確定性退款規則（`is_refund_eligible`），並透過型別化回傳（`Ticket`）產生結構化工單。適合需要把業務規則與語意理解分離、且要求可追蹤與可重構的金融、電商與 SaaS 客服流程。

2. **軟體工程輔助代理（SWE-bench 類任務）**  
   利用 CodeAct 策略讓模型在代理方法中撰寫並執行 Python 程式碼，直接操作程式碼庫物件、測試框架與版本控制 API。適用於自動化 bug 修復、程式碼審查、重構與單元測試生成，特別是已有完整型別註解與 Pydantic 模型的 Python 專案。

3. **終端機與基礎設施維運代理（Terminal-Bench 類任務）**  
   把伺服器狀態、容器、日誌與監控指標封裝成即時 Python 物件，讓代理透過傳參考方式查詢與操作。適合雲端維運、自動化故障排查、批次指令執行與合規檢查，並可透過確定性方法鎖定危險操作。

4. **科學與資料分析工作流**  
   將資料框、圖表、實驗參數封裝為物件狀態，模型以 Python 程式碼即動作（CodeAct）方式進行探索性分析、視覺化與假設驗證。適合研究團隊需要反覆迭代、保留中間狀態、並能重現分析步驟的場景。

5. **抽象推理與規則合成（ARC-AGI-3 類任務）**  
   透過顯式物件狀態與受驗證的 LLM 迴圈，讓模型在結構化環境中嘗試多種程式轉換並驗證輸出。適合需要組合搜尋、程式合成與嚴格輸出約束的教育、遊戲 AI 與形式化推理應用。

## 實作步驟建議

1. **領域建模與契約設計**  
   將業務實體（如 `Order`、`Ticket`、`Image`）以 Pydantic 模型或 Python 類別定義，並加上型別註解與描述。這些型別同時是開發者介面、模型可見契約與執行時期驗證依據。

2. **拆分確定性與代理性邏輯**  
   把精確規則、計算、狀態轉換寫成帶有真實方法本體的 Python 方法；把需要語意判斷、合成或開放式決策的步驟標記為 `...` 主體，並選擇 `PredictStrategy` 或 `CodeActStrategy`。

3. **建立 Agent 類別並注入狀態**  
   繼承 `nooa.Agent`，將資料庫連線、記憶體、配置等持久狀態以欄位形式掛載。確保這些狀態對模型可見，但只暴露必要的預覽與操作介面。

4. **撰寫模型可見的文件字串與策略裝飾器**  
   在代理方法上使用 `@strategy(...)`，並在 docstring 中清楚描述目標、輸入語意、可呼叫方法與回傳格式。文件字串即提示詞，應像寫給新進工程師一樣具體。

5. **在本機進行能力測試與單元測試**  
   對確定性方法撰寫單元測試；對代理方法設計能力測試，檢查模型是否能正確呼叫方法、遵守型別契約、處理邊界輸入。NOOA 的優勢在於可用標準 Python 測試工具執行。

6. **整合追蹤、事件與長期記憶**  
   透過 harness API 管理上下文與事件歷史，將代理執行過程記錄下來，並視需求接入外部向量資料庫或日誌系統作為長期記憶。

7. **部署到生產並持續迭代**  
   將 Agent 類別視為一般服務元件進行版本控制、CI/CD、A/B 測試與效能監控。根據生產資料持續重構 docstring、型別契約與確定性方法。

## 潛在風險與注意事項

- **模型產生程式碼的安全性**  
  CodeAct 策略會執行模型寫出的 Python 程式碼，必須在沙箱、容器或權限受限的環境中運行，並對網路、檔案系統與敏感 API 進行白名單控管。

- **傳參考帶來的副作用**  
  模型可操作即時物件（live object），雖然提升表現力，但也可能意外修改共享狀態。建議對傳入物件提供唯讀視圖或複本，並在確定性方法中明確處理變異操作。

- **型別契約與實際模型行為的落差**  
  執行時期會驗證回傳型別，但模型仍可能產生語意正確卻不符合業務預期的結果。應搭配領域專家審查、回歸測試與人機協作審批機制。

- **過度依賴代理方法處理本應確定的邏輯**  
  若把可精確定義的規則也交給 LLM，會增加成本、延遲與不穩定性。應定期檢視代理方法，將成熟邏輯重構為確定性 Python 方法。

- **上下文長度與狀態渲染成本**  
  物件狀態與事件歷史可能迅速增長，導致提示過長。需設計狀態渲染策略，只暴露模型當前所需的摘要，並適時清理或歸檔事件歷史。

## 與其他技術的整合建議

- **現有 Python 生態系**  
  NOOA 直接採用 Python 類別、型別註解、`asyncio` 與 Pydantic，因此可無縫整合 FastAPI、SQLAlchemy、Pandas、NumPy、Matplotlib 等既有函式庫。建議將這些函式庫的包裝方法作為確定性工具提供給模型。

- **LLM 服務與推理平台**  
  由於 NOOA 是模型無關框架，可透過統一介面切換 OpenAI、Anthropic、NVIDIA NIM 或本地開源模型。建議在 harness 層抽象模型呼叫，以便依任務難度與成本動態選擇模型。

- **現有代理與編排框架**  
  若組織已使用 LangChain、LlamaIndex 或 CrewAI，可先將 NOOA 用於需要嚴格型別契約與可測試性的核心代理，再透過 API 呼叫或訊息佇列與既有工作流銜接，而非一次性全面遷移。

- **資料庫、向量儲存與快取**  
  將 `OrderDB` 等狀態物件背接真實資料庫，長期記憶可接向量資料庫（如 FAISS、Milvus、pgvector），事件歷史可寫入結構化日誌或 OLAP 系統供後續分析。

- **可觀測性與 MLOps 工具**  
  將 NOOA 的事件歷史與追蹤資料輸出為 OpenTelemetry 或結構化日誌，整合至現有的監控、警報與模型評估管線，實現代理行為的可追蹤性。

## 給不同背景讀者的閱讀建議

- **初學者**  
  建議從論文中的 `SupportAgent` 範例開始，先理解「代理就是一個 Python 物件」這個核心概念。重點觀察 `...` 主體與真實方法本體的區別，以及 Pydantic 模型如何同時扮演輸入/輸出契約與提示內容。不必一開始就深入 CodeAct 的沙箱安全議題，先學會用 `PredictStrategy` 做單次型別化預測，再逐步加入迴圈與狀態。

- **AI 工程師**  
  請聚焦於 NOOA 如何將提示工程轉化為軟體工程：docstring 即提示、型別註解即契約、單元測試即可驗證代理行為。實作時應特別關注確定性方法與代理方法的邊界劃分、傳參考物件的副作用控管，以及如何透過 harness API 管理上下文與事件歷史。這篇論文提供了一個可落地的重構與維運框架。

- **研究人員**  
  本論文提出六種模型面向介面能力的組合，包括型別化輸入/輸出、傳參考、程式碼即動作、可程式化迴圈工程、顯式物件狀態與模型可呼叫 harness API。建議從第 2、3、5、6 節切入，評估這些設計對模型能力表現、樣本效率與可解釋性的影響，並思考如何將其應用於程式合成、推理與多代理協同等研究方向。

- **產品經理**  
  本文的關鍵商業價值在於降低學習曲線與維運成本：開發者可用熟悉的 Python 物件導向方式建構代理，模型也能直接理解這些程式碼。建議關注「代理就緒性」與可追蹤性如何縮短上市時間、減少提示維護負擔，並評估哪些高風險決策場景適合先導入 NOOA，例如客服分流、資料分析或內部維運自動化。
