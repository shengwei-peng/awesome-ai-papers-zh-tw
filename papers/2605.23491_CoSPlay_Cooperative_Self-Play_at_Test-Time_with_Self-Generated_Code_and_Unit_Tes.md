## ⚡ TL;DR

現有方法依賴真值單元測試，且自生成測試易與錯誤程式碼虛假耦合，無法在無真值下共同提升兩者品質。
提出 CoSPlay，藉探索攻擊引導與執行矩陣雙向訊號，讓程式碼與測試在測試時協作對弈並共同演化。
實驗顯示 CoSPlay 大幅提升程式碼與測試品質，媲美真值訓練的強化學習模型，且具良好擴展性。

## 摘要翻譯

近期，可驗證獎勵強化學習（RLVR）與測試階段擴展（TTS）透過可執行驗證推動了大型語言模型（LLM）在程式碼生成上的進展。然而，真值單元測試（GT UT）仍是一大瓶頸：最先進的（SOTA）RLVR 方法需要它們來進行昂貴的訓練，而現有的 TTS 方法若沒有它們則會失去競爭力。這催生了免真值測試階段擴展（GT-free TTS），其中現有方法直接使用自生成單元測試（Self-Generated UTs）來精煉並選擇程式碼候選方案（Code Candidates）。然而，這類單元測試經常含有雜訊或與錯誤程式碼虛假耦合（Spuriously Coupled），且單元測試的品質反過來也難以在缺乏可靠程式碼的情況下獲得驗證。因此，核心挑戰在於同時提升兩者。為此，我們提出 CoSPlay，一個免真值、免訓練的框架，透過協作自我對弈（Cooperative Self-Play）同時提升程式碼與單元測試。它首先探索多樣的解決方案構想，並識別其潛在的失效模式，以產生具鑑別力的單元測試構想。接著，它利用來自程式碼-單元測試執行矩陣（Code-UT Execution Matrix）的雙向通過次數訊號（Pass-Count Signals）迭代地修剪或修正較弱的程式碼，並刷新或替換不可靠的單元測試，使兩個候選池共同演化（Co-Evolve）。最後，當多個程式碼在最高通過次數上持平時，它從最大的輸出共識叢集中選出最終程式碼，因為正確的程式碼在相同輸入上會達成一致，而錯誤的程式碼則會分歧。在四個具挑戰性的基準測試上的實驗顯示，CoSPlay 在 Qwen2.5-7B-Instruct 上將平均 BoN 從 22.1% 提升至 33.2%，並將單元測試準確率從 14.6% 提升至 78.3%，達到或超越了 RLVR 模型 CURE-7B 的水準。當應

## 深度分析

#### 方法論解析

CoSPlay（協作自我對弈）是一個免真值（GT-free）且免訓練（training-free）的三階段推論框架，旨在透過程式碼候選方案（code candidates）與自生成單元測試（self-generated UTs）的共同演化（co-evolution），解決無真值單元測試（GT UTs）情境下的程式碼生成瓶頸。其核心方法論可拆解為以下三個階段：

**第一階段：Exploration-Attack-Guided Code-UT Idea Generation（探索-攻擊導向的程式碼與單元測試構想生成）**
此階段的關鍵在於讓後續的單元測試（UT）具備判別性，而非僅產生通用輸入。首先進行 Solution exploration（解決方案探索）：針對問題描述 P，提示大型語言模型（LLM）產生一組高階演算法提示（high-level algorithmic hints）H；再從子集空間 Ω = {ω ⊆ H | |ω| ∈ {1,2}} 中，將每個子集展開為自然語言層級的詳細解決方案計畫（solution plans）S，藉此平衡解題多樣性與組合爆炸。隨後進行 Failure-oriented UT attack idea exploration（面向失敗的單元測試攻擊構想探索）：針對每個計畫 s ∈ S，要求 LLM 識別潛在失敗模式（potential failure modes）、隱藏邊界案例（hidden edge cases）與實作陷阱（implementation pitfalls），進而產生 UT attack idea pool A。這些攻擊構想直接對應各種解題策略的脆弱點，使得後續生成的 UTs 能針對性地檢驗合理候選方案（plausible candidates）的語意正確性。

**第二階段：Execution-Matrix-Driven Iterative Self-Play（執行矩陣驅動的迭代自我對弈）**
在池初始化（Pool Construction）階段，Code pool C 由 S 隨機排列後逐一生成 code candidates c_i。UT pool T 的輸入則來自兩個來源：Random source（隨機來源）直接依據題目產生有效輸入；Attack source（攻擊來源）則將 A 中的構想實例化為具體的有效輸入。針對每個輸入 x_j，論文要求 LLM 多次求解，若取樣輸出大多一致，則將共識答案設為預期輸出 y_j，形成 t_j = (x_j, y_j) 並加入 T。此機制已隱含弱共識過濾，試圖在無真值（GT-free）前提下建立初步的輸出錨點。

接著建構 Code-UT Execution Matrix（程式碼-單元測試執行矩陣）M_{|C|×|T|}，記錄每個 code candidate 在每個 UT 上的通過與否。由此衍生出雙向的 pass-count signals（通過次數訊號）：
- **程式碼端（Code-side）**：高支援度（high-support）的 UTs（即被部分程式碼通過、部分不通過的測試）提供可靠的細部修正（refinement）訊號。具體操作包括 Code Clean（程式碼清理），剪除零通過（zero pass）的弱勢程式碼；以及 Code Fix（程式碼修復），利用高品質 UTs 的失敗回饋修復未通過的候選方案。
- **單元測試端（UT-side）**：高支援度（high-support）的程式碼（即通過較多非瑣碎 UTs 的候選方案）則作為評判 UT 品質的證據。具體操作包括 UT Refresh（單元測試更新），重新生成（regenerate）與錯誤程式碼形成虛假耦合（spuriously coupled）的 UTs，以打破耦合；以及 UT Replace（單元測試替換），重新取樣（resample）零判別力（zero-discrimination）的瑣碎 UTs。

透過這些雙向訊號，兩個池子在迭代中互相評價、互相淨化，形成正向回饋迴路，逐步提升 code candidates 與 self-generated UTs 的整體品質。

**第三階段：Output-Consensus-Based Cluster Selection（基於輸出共識的叢集選擇）**
當迭代結束後，若仍有最高通過次數（highest pass count）相同的 BoN-tied codes（Best-of-N 平手程式碼），則進入最終歧義消解機制。系統產生隨機有效輸入（random valid inputs），收集各平手程式碼的輸出簽章（output signatures），並依據輸出相似度進行分群（clustering）。論文背後的統計直覺是：correct codes（正確程式碼）在任意有效輸入上應趨於一致（agree），而 wrong codes（錯誤程式碼）則傾向發散（diverge）。因此，選擇最大輸出共識叢集（largest output-consensus cluster）中的代表程式碼，可作為無真值（GT-free）情境下最可靠的最終選擇依據。

整體而言，CoSPlay 的方法論建立在一組內部品質評估原則之上：在缺乏 GT labels 的情況下，UT pass counts 估計測試可靠性，code pass counts 估計候選方案品質，而 output-consensus clusters 則估計最終選擇信心度。這三項訊號在理論與實證上均與真實品質相關，構成了 GT-free 程式碼生成的診斷基礎。

#### 實驗數據解讀

論文於四個具挑戰性的程式碼生成基準測試（benchmarks）上進行評估，核心數據呈現出顯著的推論階段效能增益：

- **基礎模型增益**：在 Qwen2.5-7B-Instruct 上，CoSPlay 將平均 Best-of-N（BoN）從 22.1% 提升至 33.2%，相對增幅達 50.2%。這顯示即使在免訓練（training-free）且免真值（GT-free）的嚴苛條件下，透過 test-time scaling（TTS）的共同演化仍能大幅釋放模型潛能。更值得注意的是，UT accuracy（單元測試準確率）從初始的 14.6% 躍升至 78.3%，意味著 Self-Play 機制能將 self-generated UTs 的雜訊率從 85.4% 壓低至 21.7%，幾乎完成對測試池的淨化。

- **與 RLVR 模型的比較**：CURE-7B 是一個經大規模 GT UTs 訓練的 SOTA（最先進的）RLVR（可驗證獎勵強化學習）模型。CoSPlay 在 Qwen2.5-7B-Instruct 上即可匹配或超越（match or surpass）CURE-7B，這項結果具有重大意義：它暗示昂貴的模型權重更新（model-weight updates）與人工策展真值測試，可能被推論階段的演算法創新所替代。此外，當將 CoSPlay 應用於 CURE-7B 時，BoN 再提升 5.7%，顯示此框架與現有 RLVR 微調模型並非互斥，而是可作為推論時的增強外掛（inference-time enhancer）。

- **擴展性與預算分析**：在可比的輸出 token 預算（comparable output-token budgets）下，CoSPlay 優於現有 GT-free TTS 基線方法（baselines）。更重要的是，其效能隨著預算增加（budget scales up）而持續上升，未出現明顯飽和，顯示出良好的推論擴展律（inference scaling law）。這對於追求以計算換效能（compute-for-performance）的應用場景極具吸引力。

- **跨骨幹泛化性**：實驗涵蓋 instruct 模型、RLVR-tuned 模型與 frontier-scale backbones（前沿規模骨幹模型），CoSPlay 均帶來一致的 BoN 提升。這證明其品質評估訊號（pass-count signals 與 output-consensus clusters）並非過度擬合於特定模型族，而是具備通用性的推論策略。

#### 與現有研究的比較

**相對於 RLVR 典範**
現有 SOTA RLVR 方法（如 CURE-7B）依賴大規模 GT UTs 進行訓練，而 GT UTs 的策展成本高昂且難以規模化（costly to scale）。Absolute-Zero 雖然嘗試 GT-free RLVR，但仍需進行模型權重更新（model-weight updates），且在實務上競爭力較弱。CoSPlay 完全在測試階段（test-time）運作，無需任何訓練或真值資料，從根本上迴避了 GT UTs 的瓶頸，提供了一個可規模化的推論策略（scalable inference strategy）。

**相對於現有 TTS 與重排序方法**
現有 GT-free TTS 方法通常直接以 self-generated UTs 對 code candidates 進行啟發式或數學重排序（heuristic or mathematical re-ranking）。這類方法的脆弱性（fragile）在於：生成的 UTs 可能包含錯誤預期輸出、無法區分合理候選方案（plausible candidates），或與錯誤程式碼形成虛假耦合（spuriously coupled）。CoSPlay 的創新在於將「程式碼品質驗證」與「UT 品質驗證」視為共同演化（co-evolution）問題，透過 Code-UT Execution Matrix（程式碼-單元測試執行矩陣）的雙向 pass-count signals（通過次數訊號）主動識別並剔除不可靠 UTs，同時修復錯誤程式碼，打破了「無可靠程式碼則無法驗證 UT，無可靠 UT 則無法驗證程式碼」的循環困境。

**相對於 PlanSearch**
PlanSearch 著重於自然語言層級的解決方案探索（solution exploration），CoSPlay 則將其擴展至「攻擊構想」生成，並進一步銜接可執行的迭代自我對弈（iterative self-play）迴路，形成從構想到驗證的完整閉環。

**限制（Limitations）**
儘管成效顯著，CoSPlay 仍存在若干限制。首先，初始 code candidates 與 self-generated UTs 的品質下限仍受限於基礎 LLM（大型語言模型）的能力；若模型過弱，初始 pool 可能充斥系統性偏誤，導致共同演化收斂至錯誤共識。其次，迭代執行與多次取樣意味著推論延遲與計算成本顯著高於單次生成（single-pass generation），雖然總成本低於 RLVR 的訓練開銷，但對於延遲敏感（latency-sensitive）的即時應用仍具挑戰。最後，方法高度依賴可執行環境與確定性輸出，對於涉及非確定性行為、外部 I/O 或長期狀態依賴的程式碼問題，執行矩陣的判斷可能失準。

#### 可重現性評估

從方法論層面觀察，CoSPlay 的演算法流程描述相對詳盡，包含三階段的操作邏輯、Code-UT Execution Matrix（程式碼-單元測試執行矩陣）的雙向訊號定義，以及 Output-Consensus-Based Cluster Selection（基於輸出共識的叢集選擇）機制，理論上具備可重現性（reproducibility）。然而，實際重現仍需多項關鍵細節：提示詞模板（prompt templates）、LLM 取樣溫度（sampling temperature）、迭代停止條件（stopping criteria）、UT 重新生成的具體觸發閾值，以及隨機有效輸入（random valid inputs）的生成策略。這些細節目前僅見於方法概述與圖示，尚未提供完整的偽代碼（pseudocode）或演算法方塊。

#### 未來研究方向

**與 RLVR 訓練管線整合**
未來可將 CoSPlay 在推論階段產生的高品質 self-generated UTs 與經過驗證的 code candidates，作為免真值（GT-free）的訓練資料回饋至模型微調，形成「推論-訓練」閉環。這可能催生出新一代無需人工策展測試資料的 RLVR（可驗證獎勵強化學習）方法。

**動態預算分配（Dynamic Budget Allocation）**
目前框架採用固定的迭代與取樣配置。未來可依據問題難度、初始 pool 的多樣性，或執行矩陣的收斂速度，自適應調整迭代次數與取樣數，避免在簡單問題上過度消耗輸出 token 預算（output-token budgets）。

**多語言與跨領域泛化**
將 Code-UT 共同演化（co-evolution）框架擴展至多種程式語言（multi-language），乃至其他可驗證的生成任務，如數學證明（mathematical proof）、形式化邏輯推導或化學分子設計，驗證其作為通用推論策略的邊界。

**引入形式化方法輔助**
結合符號執行（symbolic execution）、靜態分析（static analysis）或形式化驗證（formal verification），以自動化方式生成更具理論保證的攻擊性 UTs，降低對 LLM（大型語言模型）生成 UTs 的依賴，進一步提升 GT-free 情境下的可靠性上限。

**錯誤模式知識庫**
將 Exploration-Attack 階段產生的 failure modes 累積為結構化知識庫，用於指導未來相似問題的初始 UT 生成，提升冷啟動（cold-start）效率，並使模型能從歷史錯誤中系統性地學習。

## 論文問答

**Q1：CoSPlay 旨在解決 LLM 程式碼生成領域中的什麼核心問題？**
A：CoSPlay 旨在解決當前大型語言模型程式碼生成方法中，真值單元測試（GT UT）所造成的瓶頸問題。雖然可驗證獎勵強化學習（RLVR）需要耗費大量成本，使用大量真值單元測試進行訓練，而現有的測試階段擴展（TTS）方法在缺乏這些真值資料時又會失去競爭力，因此亟需免真值（GT-free）的替代方案。該研究指出，自生成的單元測試往往充斥雜訊，或與錯誤程式碼形成虛假耦合，導致程式碼品質與測試品質無法獨立驗證，形成互為因果的困境。

**Q2：為何現有的免真值測試階段擴展方法難以達成具競爭力的表現？**
A：現有的免真值測試階段擴展方法通常仰賴自生成的單元測試來精煉與篩選程式碼候選方案，但這樣的管線本質上相當脆弱。這些生成的單元測試可能包含錯誤的預期輸出、無法區分合理的候選方案，或者與有缺陷的程式碼產生虛假的一致性，進而導致篩選訊號不可靠。由於缺乏能夠聯合驗證並同時改善程式碼池與單元測試池的機制，這些方法難以打破瑕疵程式碼與錯誤測試之間相互污染的惡性循環。

**Q3：為何在免真值設定中，聯合改善程式碼與單元測試對程式碼生成至關重要？**
A：在免真值的設定中，程式碼候選方案的品質與單元測試的品質具有深度的相互依賴關係，因為可靠的程式碼是驗證單元測試的前提，而具有鑑別力的單元測試又是驗證程式碼的必要條件。若僅改善其中一方而另一方仍維持雜訊，評估訊號將持續不可靠，導致整個篩選過程崩潰。因此，建立一個能同時淨化兩個集合的共同演化機制，對於在沒有任何真值監督的情況下實現可擴展且具競爭力的程式碼生成至關重要。

**Q4：CoSPlay 框架的三個主要階段為何，它們之間如何銜接？**
A：CoSPlay 包含三個循序階段：探索—攻擊導向的程式碼與單元測試構想生成、執行矩陣驅動的迭代自我對弈，以及基於輸出共識的群集選擇。第一階段透過探索多樣的解題策略，並從其潛在失效模式中推導出針對性的單元測試構想，從而建立植基於特定解題假設的初始集合。第二階段建構程式碼—單元測試執行矩陣，利用雙向通過次數訊號迭代地修剪弱程式碼並更新不可靠的單元測試，使兩個集合共同演化；第三階段則針對仍處於最高通過次數平手狀態的程式碼，比較它們在隨機有效輸入上的輸出，並從最大的輸出共識群集中選出最終方案。

**Q5：CoSPlay 中合作自我對弈機制的關鍵創新是什麼？**
A：此合作自我對弈機制的核心創新在於利用程式碼—單元測試執行矩陣的雙向通過次數訊號，在無需任何訓練或真值資料的情況下，建立程式碼候選方案與單元測試之間的共同演化迴路。不同於以往將程式碼生成與測試生成視為獨立流程的做法，CoSPlay 讓高支持度的單元測試為程式碼的修剪與修復提供可靠的精煉訊號，同時讓高支持度的程式碼為判斷與替換不可靠的單元測試提供依據。這種相互評估機制打破了錯誤程式碼與瑕疵測試之間的虛假耦合，使兩個集合在推論過程中能夠持續地相互提升品質。

**Q6：CoSPlay 為何在解題探索時將提示子集大小限制為一或二，這對單元測試生成有何助益？**
A：在解題探索階段將提示子集大小限制為一或二，是為了在解題多樣性與組合爆炸之間取得平衡，確保解題計畫池在可管理的範圍內涵蓋不同的演算法方向。針對每個計畫，系統會分析其潛在失效模式、隱藏邊界案例與實作陷阱，從而產生針對性的單元測試攻擊構想，而非僅生成籠統膚淺的測試案例。這樣的設計確保初始單元測試池植基於特定解題假設，能夠透過鎖定各候選方案獨有的弱點來更有效區分合理的程式碼候選方案。

**Q7：CoSPlay 在哪些類型的基準上進行評估，並測試了哪些骨幹模型？**
A：CoSPlay 在四個具挑戰性的程式設計基準上進行評估，以驗證其有效性與泛化能力。實驗主要以 Qwen2.5-7B-Instruct 作為骨幹模型，並將框架應用於經過 RLVR 微調的 CURE-7B 模型以及多樣化的其他骨幹架構，以展示其廣泛的適用性。這些評估涵蓋了標準指示模型、RLVR 調校模型與前沿規模模型，並在可比的輸出標記預算下與現有基線方法進行公平比較。

**Q8：CoSPlay 取得了哪些最顯著的量化改進成果？**
A：在 Qwen2.5-7B-Instruct 上，CoSPlay 將平均 Best-of-N（BoN）表現從 22.1% 提升至 33.2%，並將單元測試準確率從 14.6% 大幅躍升至 78.3%。這些成果使其能夠匹配甚至超越使用大量真值單元測試訓練的強大 RLVR 模型 CURE-7B。此外，當 CoSPlay 應用於 CURE-7B 之上時，還能額外帶來 5.7% 的 BoN 提升，顯示其即使對於已經優化的模型仍具有互補的加值效果。

**Q9：論文提供了什麼證據來驗證 CoSPlay 內部品質評估訊號的可靠性？**
A：論文確立了三項內部品質評估原則：單元測試的通過次數可估計測試的可靠性，程式碼的通過次數可估計候選方案的品質，而輸出共識群集則可估計最終選擇的信心度。透過理論分析與自我對弈前後的對照研究，作者證明這些訊號與真實品質具有強烈的相關性，並能可靠地支撐共同演化過程。這些診斷工具為未來的免真值程式碼生成方法提供了實用的品質評估手段，使其得以在沒有真值標籤的情況下判斷樣本品質。

**Q10：相較於傳統 RLVR 或依賴真值的 TTS 方法，CoSPlay 在哪些實務場景中特別具有價值？**
A：相較於傳統的 RLVR 或依賴真值的 TTS 方法，CoSPlay 在真值單元測試稀少、昂貴或大規模取得不可行的實際開發環境中特別具有價值。由於它完全無需訓練且不要求更新模型權重，因此可以直接部署於現成的指示模型或 RLVR 微調模型之上，無需額外的微調基礎設施。這使其非常適合用於快速原型開發、競技程式設計平台，或是重視降低標註成本與運算開銷的企業級程式碼生成工具。

**Q11：將 CoSPlay 作為推論時間策略部署時，有哪些關鍵的產品層級優勢？**
A：作為純粹的推論時間策略，CoSPlay 避免了 RLVR 訓練管線中需要大量專家整理單元測試所帶來的龐大運算與資料成本。它透過迭代自我對弈與共識群集進行運作，這意味著只要增加標記預算就能向上擴展其效能，而無需重新訓練底層模型。此外，它與多樣化骨幹模型的相容性——從標準指示模型到前沿規模系統——使產品團隊能夠靈活地將其整合至不同的 LLM 供應商與版本之中。

**Q12：CoSPlay 可能如何影響程式碼生成與測試階段擴展領域的未來研究方向？**
A：CoSPlay 將研究視角從單純地增加採樣數量，轉向共同演化典範，使程式碼與測試在推論過程中相互增強。透過證明無需任何真值資料即可達成具競爭力的程式碼生成，它為軟體工程乃至其他領域中可擴展的自我監督驗證開闢了新路徑。其所建立的內部品質評估原則也為未來的免真值方法提供了診斷基礎，潛在可將合作自我對弈擴展至形式數學或科學模擬等其他需要可驗證推理的領域。

**Q13：CoSPlay 框架存在哪些固有的限制或運算權衡？**
A：CoSPlay 高度仰賴底層大型語言模型生成多樣且高品質的解題計畫，以及進行有意義的失效模式分析，因此其效能上限受限於骨幹模型的推理能力。迭代自我對弈過程需要多輪的程式碼執行、單元測試重新生成與矩陣計算，相較於單次生成方法會消耗更多的推論標記與延遲時間。此外，儘管該框架大幅提升了單元測試準確率，仍無法保證測試的絕對可靠性，且若初始計畫池缺乏足夠的多樣性以涵蓋問題的解空間，共同演化過程可能仍會陷入困境。

**Q14：在什麼條件下，CoSPlay 可能在共同演化後仍無法選出正確的程式碼？**
A：當多個錯誤的程式碼候選方案碰巧在已演化的單元測試以及用於共識群集的隨機有效輸入上產生完全相同的輸出時，可能會形成虛假共識，使系統無法察覺其缺陷。若初始探索階段未能捕捉到真正的解題策略，或是單元測試攻擊構想過於籠統，執行矩陣從一開始就可能缺乏鑑別力，導致自我對弈迴路停滯不前。此外，當最高通過次數層級包含許多不同但細微錯誤的實作，且它們在受測輸入上恰好一致時，輸出共識機制可能會誤將一大群錯誤行為視為可靠，而忽略了規模較小但正確的程式碼群集。

**Q15：CoSPlay 框架暗示了哪些未來的改進方向或擴展可能？**
A：未來研究可透過整合更結構化的程式分析或檢索增強技術來強化探索階段，以確保更廣泛地涵蓋解題策略與邊界案例。研究者亦可開發更精緻的共識機制或後設學習方法，在維持選擇準確度的同時進一步降低收斂所需的標記預算。最後，這種合作自我對弈典範或可從程式碼生成擴展至其他需要可驗證輸出的領域，例如定理證明、資料分析管線或代理工具使用，這些場景同樣面臨真值監督難以大規模取得的挑戰。

## 實務應用指南

### 適用場景

1. **企業內部自動化腳本與工具開發**：當團隊需要快速生成資料處理、報表自動化或 DevOps 腳本，卻缺乏官方維護的真值單元測試（GT UT）時，CoSPlay 可在測試階段透過自生成單元測試與程式碼候選方案的共同演化，直接產出附帶驗證信號的可執行程式碼。
2. **教育程式碼輔助與自動評測系統**：在程式設計教學或線上評測平台中，面對大量學生提交的習題，系統往往沒有針對每道題目的完整 GT UT。CoSPlay 能夠針對題目描述自動探索解題策略與攻擊構想，生成具鑑別力的單元測試，協助判斷學生程式碼的合理候選方案是否正確。
3. **遺留系統維護與重構**：針對缺乏文件與測試覆蓋率的舊有專案，工程師在重構或新增功能時，可利用 CoSPlay 根據問題描述與現有程式碼片段，自動產生高鑑別度的自生成單元測試，補足測試缺口並驗證重構後的程式碼候選方案。
4. **快速原型開發與 API 整合**：在新創或產品驗證階段，開發者需要快速串接第三方 API 或產生概念驗證（PoC）程式碼。CoSPlay 可在無須預先準備 GT 資料的情況下，透過協作自我對弈迭代打磨整合程式碼，並透過輸出共識聚類降低錯誤風險。
5. **競賽與面試輔助解題**：在競技程式設計或技術面試準備情境中，使用者經常只有題目敘述而無官方測試數據。CoSPlay 能夠模擬多種解題方向並針對潛在失效模式生成攻擊導向的單元測試，協助使用者找出最穩定的解法。

### 實作前置條件

- **模型與運算資源**：需具備可執行程式碼生成的大型語言模型（LLM），建議使用至少 7B 參數以上的指令模型（如 Qwen2.5-7B-Instruct 或同級模型）。由於需要大量採樣生成程式碼候選方案與單元測試，並多次執行迭代，建議配置具備充足 VRAM 的 GPU 或高效能 API 端點，並預留可擴展的輸出 token 預算。
- **資料需求**：僅需問題描述（Problem Description）與目標程式語言設定，**無需**任何真值單元測試（GT UT）或額外訓練資料。若企業內部有程式碼規範文件，可選擇性納入提示以提升生成品質。
- **執行環境**：必須建置安全的程式碼執行沙箱（如 Docker 容器或虛擬機），因為框架需要實際執行自生成程式碼與自生成單元測試以建構程式碼-單元測試執行矩陣。沙箱需支援目標語言的執行期環境，並具備網路隔離與資源限制。
- **技術能力**：實作團隊需熟悉單元測試概念、具備解析執行矩陣與通過次數訊號的程式能力，並能處理沙箱部署與錯誤日誌分析。若需整合現有工具鏈，則需具備 CI/CD 或 IDE 外掛的開發經驗。

### 實作步驟建議

1. **問題解析與策略探索**：針對給定的問題描述，提示 LLM 產出多組高階演算法提示（hints），涵蓋可能的資料結構、演算法策略與邊界案例。再將這些提示組合成大小為 1 至 2 的子集，擴展為詳細的自然語言解題計畫池，確保涵蓋多樣的合理候選方案方向。
2. **攻擊導向測試構想生成**：針對每個解題計畫，提示 LLM 識別潛在失效模式、隱藏邊界案例與實作陷阱，將其轉化為單元測試攻擊構想池。此步驟確保後續的自生成單元測試能針對特定解題假設進行鑑別，而非僅產生泛泛的隨機輸入。
3. **初始化程式碼與測試池**：根據解題計畫池生成初始程式碼候選方案池；同時結合隨機有效輸入與攻擊構想實例化，產生初始單元測試池。對於每個測試輸入，可多次採樣 LLM 的輸出，若多數結果一致則將其作為預期輸出，建立可執行的單元測試。
4. **建構執行矩陣與雙向篩選**：執行所有程式碼候選方案與單元測試的組合，建立通過／失敗的程式碼-單元測試執行矩陣。分析通過次數訊號：淘汰零通過或極低通過的弱程式碼；對於零鑑別度（幾乎全通或全敗）的單元測試，則予以刷新或替換。
5. **迭代共同演化**：重複執行矩陣分析、程式碼修復（利用高支持度的單元測試回饋修補失敗程式碼）、以及單元測試重新生成（針對仍存在的虛假耦合或漏洞）。讓程式碼池與單元測試池在固定迭代次數內或達到收斂條件前持續共同演化。
6. **輸出共識聚類選擇**：當迭代結束後，若仍有最高通過次數相同的程式碼候選方案（BoN-tied），則對這些程式碼餵入隨機有效輸入，收集其輸出簽名並進行聚類。選擇最大共識群集中的代表程式碼作為最終輸出，因為正確程式碼傾向在任意輸入上達成一致，而錯誤程式碼則容易發散。
7. **產品化封裝與監控**：將最終選定的程式碼、其通過的單元測試、執行矩陣的通過次數統計，以及共識聚類的信心分數一併輸出。建立日誌追蹤機制，記錄每次迭代的淘汰與修復歷程，供後續人工審查或系統優化使用。

### 潛在風險與注意事項

- **虛假耦合（Spurious Coupling）**：錯誤的程式碼候選方案與錯誤的單元測試可能互相驗證，形成穩定的虛假通過。必須透過迭代中的單元測試替換機制與多樣性採樣來打破耦合，並監控是否有特定程式碼-測試組合長期綁定。
- **執行安全風險**：自生成程式碼可能包含無限迴圈、惡意系統呼叫或資源耗盡攻擊。所有執行必須在嚴格隔離的沙箱中進行，設定 CPU、記憶體與執行時間上限，並禁止不必要的網路與檔案系統權限。
- **計算成本與延遲**：多次採樣、矩陣執行與迭代會顯著增加輸出 token 消耗與端對端延遲。建議設定明確的 token 預算上限、最大迭代次數與早期停止條件（例如當最高通過次數連續兩輪未改善即停止）。
- **無法收斂或低品質輸出**：若問題難度超出模型能力，或初始解題計畫過於單一，可能導致最終共識群集過小甚至無法產出可靠程式碼。此時應設計降級策略，例如回傳「信心不足」訊號並導入人工審查，而非強制輸出。
- **領域適配限制**：論文驗證主要基於競賽型程式設計任務，移植至特定框架（如前端 React、SQL 查詢、機器學習管線）時，需自行調整輸入驗證邏輯、執行環境與輸出比對方式，不能直接沿用純演算法題的執行矩陣設定。

### 與其他技術的整合建議

- **與檢索增強生成（RAG）整合**：將企業內部的程式碼規範、常用函式庫文件與內部 API 說明納入提示脈絡，使 CoSPlay 在探索解題計畫時能優先參考內部慣例，提升生成程式碼的實用性與可維護性。
- **與現有 CI/CD 管線整合**：將 CoSPlay 部署為缺乏測試覆蓋率的舊有專案之自動測試生成器，在 pre-commit 或 Pull Request 階段觸發，自動補充單元測試並驗證變更是否破壞現有共識。
- **與 RLVR 模型疊加使用**：如論文實驗所示，CoSPlay 作為免訓練的測試階段擴展（TTS）框架，可進一步提升已微調之 RLVR 模型效能。建議將其視為 inference-time 的增強層，在不重新訓練模型權重的情況下持續精進輸出品質。
- **與人機協作審查介面整合**：將執行矩陣的熱力圖、通過次數分佈與輸出共識聚類結果視覺化呈現給開發者，協助其快速定位高風險程式碼區段，而非直接自動部署至生產環境。
- **與靜態分析工具整合**：在初始化階段先以 Linter、型別檢查器或符號執行工具預篩程式碼候選方案，提前過濾語法錯誤與明顯型別不符的樣本，減少後續執行矩陣中的無效計算。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先掌握「程式碼與單元測試可以互相驗證」這個核心直覺，不必急於理解所有數學推導。可將閱讀重點放在圖 3 的三階段流程圖，以及論文中關於「為何錯誤程式碼會發散、正確程式碼會收斂」的直觀說明，這將幫助你快速建立對 CoSPlay 運作方式的整體認識。
- **AI 工程師**：請著重研讀第 2 節的方法論細節，特別是程式碼-單元測試執行矩陣的雙向訊號設計、程式碼修剪與單元測試刷新策略，以及輸出共識聚類的實作邏輯。實驗章節中的超參數設定（如採樣數量、迭代次數、子集空間大小）是復現與調校的關鍵參考。
- **研究人員**：建議深入分析第 3 節提出的內部品質評估原則與理論分析，思考通過次數訊號與真實品質之間的相關性。可進一步探索如何將此共同演化框架擴展至數學證明生成、形式化驗證或其他具備可執行獎勵訊號的生成任務。
- **產品經理**：請聚焦「免真值資料」與「免訓練」所帶來的商業價值與部署彈性，評估將 CoSPlay 導入內部開發工具鏈以降低測試維護成本的可行性。同時需審慎評估計算預算、端對端延遲與輸出品質之間的權衡，並規劃相應的使用者體驗與降級機制。
