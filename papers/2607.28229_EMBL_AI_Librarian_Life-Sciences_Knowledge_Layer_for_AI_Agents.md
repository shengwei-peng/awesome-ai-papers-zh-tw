## 摘要翻譯

網路正逐漸由 AI 代理（AI agents）而非人類存取。每個代理都需要知識，生命科學（life sciences）領域尤其如此，因為該領域的代理式流程正快速成長。文獻存取是滿足此需求的關鍵一環，而 Europe PMC 等資源已收錄超過 4000 萬筆索引記錄，並被廣泛用於滿足這項需求。然而，這些資源並非為 AI 代理（AI agents）設計：它們接受關鍵字與複雜查詢語法（query syntax），並回傳整篇論文，因此每個代理都必須學習語法、執行多次搜尋，並閱讀全文（full-text articles）以找到所需證據。我們提出 EMBL AI Librarian，這是一個為 AI 代理（AI agents）升級 Europe PMC 介面的知識層（knowledge layer）：代理以自然語言（natural language）提問，並獲得能回答問題的證據。單一大型語言模型（large language models, LLMs）協調（orchestration）整個知識檢索流程：它會規劃一組互補子查詢（complementary subqueries），交由即時 Europe PMC 搜尋引擎（search engine）執行，接著閱讀選出的論文並定位相關證據。我們在四個評測基準上評估 Librarian：文獻綜合（literature synthesis）、聲稱驗證（claim verification）、開放領域問答（open-domain question answering），以及下游生物學任務（downstream biology tasks），如實驗流程問題（protocol questions）與序列操作（sequence manipulation）。在 ScholarQABench 上，Librarian 在引用 F1（Citation F1）上較近期發表的強大基線提升超過 16 分。作為現有聲稱驗證（claim verification）管線的檢索層（retrieval layer）使用時，它提升了與專家共識（expert consensus）的一致性；而在開放式文獻問答評測基準 LitQA2 上，以 Librarian 為知識基礎的 GPT-5.4 代理，得分較使用網路搜尋（web search）時高出約 8 分。總體而言，我們的結果顯示，為生命科學（life sciences）領域的 AI 代理（AI agents）配備 Librarian 知識層（knowledge layer），能在多項任務上提升表現。我們已在 https://github.com/petroni-lab/librarian 公開釋出程式碼。

### 核心貢獻（3～5點）
- 提出 EMBL AI Librarian，一個專為生命科學 AI 代理設計的知識層，將 Europe PMC 升級為支援自然語言問答的介面。
- 以單一大型語言模型協調整個知識檢索流程：規劃互補子查詢、執行即時搜尋、閱讀論文並定位可引用證據。
- 在四個評測基準（文獻綜合、聲稱驗證、開放領域問答、下游生物學任務）上驗證 Librarian 的效益。
- 在 ScholarQABench 上引用 F1 提升超過 16 分；作為檢索層可提升與專家共識的一致性；LitQA2 上 GPT-5.4 使用 Librarian 較網路搜尋高出約 8 分。

### 適合對象
生命科學與生物醫學研究者、AI 代理與文獻檢索系統開發者、生物資訊學家，以及關注學術問答、科學聲稱驗證與 AI 代理基礎設施的研究人員與工程師。

## 深度分析

#### 方法論解析

##### 問題設定與介面設計
EMBL AI Librarian（以下簡稱 Librarian）的核心目標，是將原本為人類設計的 Europe PMC（歐洲 PubMed 中心，開放生命科學文獻搜尋引擎）升級為適合 AI agents（AI 代理）使用的 knowledge layer（知識層）。傳統上，Europe PMC 要求使用者輸入關鍵字與複雜 query syntax（查詢語法），並回傳整篇全文或摘要；AI agents 必須自行學習語法、發出多次 complementary searches（互補搜尋）、再讀完整篇文章才能擷取所需證據。Librarian 將這個流程抽象為一個自然語言介面：agent 以 natural language（自然語言）提問，系統回傳一組精簡、可引用的 evidence items（證據項目）。

每個 evidence item 包含三個元件：(1) 與問題直接相關的短文本片段（short text span）；(2) 可供引用的 paper metadata（文獻後設資料）；(3) 產生該證據的 Europe PMC query（查詢）。這種設計讓下游 agent 不必處理全文，也保留了檢索過程的透明性——任何人都可以回溯該證據是透過哪個子查詢找到的。

##### 三階段檢索與證據排序管線
根據論文第 2 節，Librarian 的檢索流程可分為三個階段：

1. **Recall-oriented retrieval（召回導向檢索）**  
   生命科學實體常有多種 aliases（別名），例如基因符號 TP53、蛋白質名稱 p53、疾病名稱 ALS 與 amyotrophic lateral sclerosis、MeSH terms（醫學主題詞）等。單一 Europe PMC 查詢很容易因為 surface form 不同而遺漏相關文獻。因此，單一 LLM controller（LLM 控制器）會先將自然語言問題拆解成多個互補的 subqueries（子查詢），同時使用 keyword queries（關鍵字查詢）與 fielded queries（欄位查詢），針對基因、蛋白質、物種、化學物質等結構化註釋進行檢索，以最大化召回率。

2. **文內證據定位與排序**  
   召回回來的文章不會整篇餵給下游模型。Librarian 會將選定的 papers（文獻）分解成 paragraphs（段落），再由 LLM 針對原始問題對每個候選段落進行 relevance scoring（相關性評分），找出真正包含答案的文本片段。

3. **Precision-oriented evidence selection（精確導向證據選擇）**  
   最後系統會過濾 false positives（偽陽性），回傳一個 compact、ranked 的 citable evidence（可引用證據）清單。整體流程從「盡量找全」逐步收斂到「只留最相關」。

##### 為何不使用密集向量索引
論文明確指出，雖然 dense vector database（密集向量資料庫）是常見的文獻檢索方案，Librarian 刻意避免自建索引，原因有四：

- **基礎建設成本高昂**：索引並伺服整個文獻庫需要數百 GB 的 embeddings（例如 OpenScholar 的資料儲存約 744 GB）。
- **LLM 能力提升壓縮密集檢索優勢**：近期研究顯示，能力良好的 LLM 搭配調校過的 BM25 骨幹與多查詢策略，在科學基準上已可媲美甚至超越密集檢索。
- **破壞結構化後設資料**：向量嵌入會 flatten 基因、蛋白質、物種、化學物質等欄位註釋，無法直接進行 fielded search（欄位搜尋）。
- **不可檢視性**：nearest-neighbour lookup（最近鄰搜尋）難以解釋，而 Europe PMC 的結構化 keyword query 可被檢查與除錯。

因此，Librarian 選擇「無索引」架構：直接呼叫 Europe PMC 的 live search engine（即時搜尋引擎），把索引與維護成本交還給 Europe PMC，同時保留結構化查詢與透明性。

##### LLM 協調器（Orchestrator）的角色
整個管線由單一 LLM（large language model，大型語言模型）協調，而非多個專家模組串接。這個 LLM orchestrator（LLM 協調器）同時負責：

- 理解自然語言問題；
- 規劃互補子查詢（包含別名擴展與欄位限制）；
- 解析 Europe PMC 回傳結果；
- 在段落層級進行證據評分與篩選。

由於 Librarian 是 model-agnostic（模型無關）的，只要換上更強的 LLM，整體效能就能隨之提升，無需重新設計管線。

##### 證據項目的結構與透明性
最終輸出的 evidence item 是「比整篇文章更細緻」的單位。它讓下游 agent 可以直接引用、比較與推理，而不必自行處理全文。同時，每個項目保留產生它的 Europe PMC query，使 retrieval（檢索）過程可被 inspect（檢視）——這對需要審計與驗證的生命科學應用尤為重要。

#### 實驗數據解讀

論文在四個互補情境中評估 Librarian：literature synthesis（文獻綜合）、claim verification（聲稱驗證）、open-domain question answering（開放領域問答）、以及 downstream biology tasks（下游生物學任務）。以下逐一解讀。

##### ScholarQABench：文獻綜合
在 literature synthesis 任務中，評估指標為 Citation F1（引用 F1），衡量生成摘要中引用文獻的精確度與召回率。Librarian 相較於近期強大的 agentic baselines（代理基線），平均提升超過 **16 個百分點**。這顯示：

- 多子查詢策略能有效擴大召回，避免遺漏關鍵文獻；
- 段落級證據篩選能過濾不相關全文，提升引用品質；
- 將「讀全文」的負擔從下游 agent 轉移到 Librarian，顯著改善最終綜合表現。

##### ProClaim：聲稱驗證
在 claim verification 任務中，Librarian 被用作 ProClaim 管線的 retrieval layer（檢索層）。結果顯示，與 expert consensus（專家共識）的 agreement（一致性）平均提升 **5 個百分點**。這說明：

- 更精準的證據擷取能直接改善科學聲稱的真偽判斷；
- 相較於原本使用的檢索方式，Librarian 提供的 citable evidence 更能代表專家所依據的文獻基礎。

##### LitQA2：開放領域問答
在 LitQA2 這個 open-form（開放式）文獻問答基準上，研究團隊讓 GPT-5.4 分別搭配 Librarian 與 web search（網路搜尋）進行比較。結果顯示，使用 Librarian 時準確率提升約 **8 個百分點**。這凸顯：

- 針對生命科學領域設計的專業檢索層，比一般網路搜尋更能提供可靠答案；
- 即使前端是強大的 frontier model（前沿模型），後端檢索品質仍是決定問答表現的關鍵瓶頸。

##### LAB-Bench：下游生物學任務
在 LAB-Bench 的生物學 workflow tasks（工作流程任務）中，Librarian 對兩種 frontier backbones（前沿骨幹模型）都帶來 macro accuracy（宏觀準確率）提升，最高達 **+4.2 分**；其中在 sequence manipulation（序列操作）子任務上，提升更高達 **+11.3 分**。這表示：

- 實驗流程問題與序列操作問題特別依賴精確的文獻證據；
- Librarian 能將技術細節（例如 protocol questions，實驗流程問題）從大量文獻中萃取出來，顯著降低模型幻覺風險。

##### 綜合解讀
四個設定、四個基準都呈現一致正向結果，顯示 Librarian 並非只在單一任務有效，而是具備通用性的 knowledge layer。值得注意的是，這些增益來自「檢索層」的改善，而非單純放大模型規模，呼應了近期研究強調的：高品質檢索證據對 agent 表現的貢獻可能超過模型本身擴展。

#### 與現有研究的比較

##### 相對於密集檢索系統
過去許多文獻問答系統（如基於 DPR、OpenScholar 的 pipeline）採用 dense retrieval（密集檢索）：將文獻切分成 passages（段落）、embed 成向量、再進行 nearest-neighbour search（最近鄰搜尋）。Librarian 的差異在於：

- **不維護自有索引**：降低基礎建設與更新成本；
- **保留欄位查詢能力**：可直接針對 gene symbols（基因符號）、protein names（蛋白質名稱）、organism（物種）、chemicals（化學物質）等結構化欄位檢索；
- **可解釋性更高**：每個證據都附帶產生它的 Europe PMC query，便於審計。

然而，密集檢索在語意相似性檢索上仍有優勢，特別是當使用者問題與文獻用詞差異較大時。Librarian 透過 LLM 生成多個互補子查詢來彌補這一點，但是否能完全取代密集檢索，仍取決於具體應用。

##### 相對於 BM25 + LLM 多查詢方法
近期研究顯示，BM25 搭配 LLM 生成的多個 keyword queries 已能在科學基準上挑戰密集檢索。Librarian 可視為這條路線的進一步延伸：它不僅生成關鍵字查詢，還結合 Europe PMC 的 fielded query syntax，並在召回後進行段落級證據評分與篩選。因此，Librarian 的貢獻不在於提出全新的檢索演算法，而在於將「檢索、解析、證據擷取」整合成一個 agent-first（代理優先）的知識層。

##### 相對於網路搜尋
與一般 web search（網路搜尋）相比，Librarian 專注於生命科學文獻，並直接連結到 Europe PMC 的 curated（經過整理）資料。這帶來兩個優勢：

- **來源可靠**：Europe PMC 收錄經過索引的 PubMed abstracts、全文與預印本，較不易受到低品質網頁內容干擾；
- **可引用性**：每個 evidence item 都附帶完整的 paper metadata，適合學術寫作與聲稱驗證。

不過，網路搜尋的覆蓋範圍更廣，能取得非學術來源（如新聞、資料庫、部落格），在某些開放式問題上仍具價值。

##### 創新貢獻與限制
**主要創新**：
1. 定義了生命科學領域的 agent-first knowledge layer 介面；
2. 提出無索引、直接串接 Europe PMC live search 的架構；
3. 以單一 model-agnostic LLM 協調整個檢索與證據擷取流程；
4. 在多個基準上展示一致且顯著的效能提升。

**主要限制**：
- **依賴 Europe PMC 覆蓋範圍**：若文獻未開放近用或未被 Europe PMC 索引，Librarian 無法取得；
- **即時 API 的穩定性與延遲**：所有檢索都透過 live search engine，可能受 rate limit（速率限制）與網路延遲影響；
- **查詢生成錯誤會傳播**：若 LLM 產生的 subqueries 不準確，後續證據品質會跟著下降；
- **單一 LLM 的幻覺風險**：雖然檢索過程透明，但 LLM 在評分段落相關性時仍可能出錯；
- **評估語言與領域限制**：目前基準以英文生命科學文獻為主，跨語言與跨領域泛化能力尚未驗證。

#### 可重現性評估

##### 開源釋出內容
論文明確表示已公開釋出：

- source code（原始碼）；
- prompts（提示詞）；
- runtime configuration（執行階段設定）；
- evaluation pipelines（評估流程）。

這對 reproducibility（可重現性）非常有利，因為其他研究者可以直接檢視提示詞設計與管線細節，而不必從論文推測實作細節。

##### 資料與 API 可取得性
Librarian 依賴的 Europe PMC 是公開服務，提供 website、API 與 bulk download（大量下載）。評估使用的基準——ScholarQABench、LitQA2、LAB-Bench、ProClaim——均為已發表的公開資料集。因此，資料取得門檻低，符合開放科學原則。

##### 模型與計算需求
Librarian 是 model-agnostic，理論上可使用任何 LLM。論文評估中使用了 GPT-5.4 等 frontier model。這帶來兩個再現議題：

- **商業 API 依賴**：若使用 GPT-5.4 等閉源模型，再現結果會受 API 版本、溫度參數、prompt 變動影響；
- **成本**：雖然 Librarian 不建索引，但多次 Europe PMC 查詢加上段落級 LLM 評分，仍會產生不可忽略的 API 費用。

研究者若改用開源 LLM（如 Llama、Qwen、Mistral）可降低成本，但效能可能與論文報告不同。

##### 再現風險
主要風險包括：

- Europe PMC API 行為或回傳格式隨時間改變；
- 商業 LLM API 的 non-determinism（非確定性）導致結果浮動；
- 部分基準的黃金標準或評分腳本更新。

整體而言，Librarian 的可重現性處於中上水準：程式碼與提示詞公開、資料公開、API 公開，但部分再現細節仍取決於外部服務的穩定性與版本。

#### 未來研究方向

##### 1. 多模態證據擷取
目前 Librarian 主要回傳文本片段，但生命科學文獻中的證據常存在於 figures（圖表）、tables（表格）與 supplementary data（補充資料）。未來可擴展至圖表理解與多模態 evidence item，讓 agent 能引用圖像中的實驗結果。

##### 2. 迭代式與互動式檢索
現有管線是一次性生成 subqueries 後進行證據評分。未來可引入 iterative retrieval（迭代檢索）：agent 根據初步證據提出追問，Librarian 動態調整查詢策略，形成多輪對話式的文獻探索。

##### 3. 不確定性量化與幻覺控制
LLM 在生成查詢與評分段落時可能過度自信。未來研究可加入 uncertainty calibration（不確定性校正）或 confidence score（信心分數），讓下游 agent 知道哪些證據較可靠，哪些需要額外驗證。

##### 4. 混合索引策略
雖然 Librarian 主張無索引，但在特定高頻查詢場景下，可考慮 hybrid indexing（混合索引）：對熱門文獻或領域建立輕量 dense cache，同時保留 Europe PMC 作為權威後盾，兼顧速度與透明性。

##### 5. 跨語言與跨領域擴展
目前聚焦英文生命科學文獻。未來可將相同架構應用於其他語言（如中文、德文、法文）的生物醫學資料庫，或擴展至化學、材料科學、氣候科學等需要嚴謹文獻證據的領域。

##### 6. 與生物資訊工具鏈深度整合
Librarian 目前主要作為檢索層。未來可與 bioinformatics tools（生物資訊工具）、實驗設計系統、lab automation（實驗室自動化）平台結合，讓 agent 在檢索文獻後直接執行序列分析、引子設計或 protocol optimization（實驗流程最佳化）。

##### 7. 使用者中心評估與倫理考量
除了自動化基準，未來需要更多 usability studies（可用性研究）與使用者研究，評估研究人員如何與 Librarian 互動、如何信任其回傳證據，以及如何避免過度依賴自動化檢索所帶來的 confirmation bias（確認偏誤）。

##### 8. 處理付費牆與非開放文獻
Europe PMC 雖然龐大，但仍有大量文獻受 paywall（付費牆）保護。未來可探索與出版商或機構 repository（機構典藏）整合，在合法授權範圍內擴大檢索覆蓋率。

## 論文問答

**Q1：為什麼現有的 Europe PMC 等文獻資源難以直接滿足 AI 代理的需求？**

A：Europe PMC 原本是為人類研究者設計的，其介面要求使用者輸入關鍵字與複雜的查詢語法，並且回傳的是整篇論文，而非精簡的證據片段。AI 代理若直接使用這類資源，必須自行學習語法、針對基因符號或疾病同義詞等別名發出多次互補搜尋，並在固定上下文視窗內閱讀全文，這會迅速耗盡 Token 預算。因此，現有資源雖然收錄了超過四千萬筆記錄，卻無法讓代理以自然語言提問並直接獲得可引用的答案。

**Q2：密集向量檢索為何在生命科學文獻場景中不是最佳解？**

A：密集檢索需要將大量文獻切塊並建立向量索引，整體基礎設施成本高昂，例如 OpenScholar 的資料儲存就高達約 744 GB。此外，隨著大型語言模型能力增強，由 BM25 等詞彙檢索搭配 LLM 產生多組查詢的策略，在科學基準上的表現已可媲美甚至超越密集檢索。更重要的是，向量嵌入會壓平結構化後設資料，使代理難以針對基因、蛋白質、化學物等明確欄位進行檢索，且最近鄰搜尋的過程不如欄位化關鍵字查詢來得可檢視與透明。

**Q3：為什麼為 AI 代理建立專屬的知識層在生命科學領域特別重要？**

A：生命科學文獻呈指數成長，研究人員面臨嚴重的資訊超載，而 AI 代理已深入日常研究流程，包括摘要多篇論文、執行生物資訊工具、排序生物標誌物候選以及生成可驗證假說。這些任務都必須以已發表的證據為基礎，但代理若無法高效取得可信文獻，就難以確保輸出品質。因此，一個能讓代理用自然語言提問、並回傳精簡可引用證據的共享知識層，對提升生命科學研究的可靠性與效率至關重要。

**Q4：EMBL AI Librarian 的核心運作流程包含哪些階段？**

A：Librarian 首先進行召回導向的檢索，由單一大型語言模型控制器針對自然語言問題產生多組互補的關鍵字與欄位化子查詢，並即時查詢 Europe PMC。接著系統從檢索到的論文中選出相關文獻，將其拆解為段落，並針對原始問題對候選證據進行評分。最後，它回傳一組經過排序、精簡且可引用的證據項目，每個項目都包含文字片段、論文後設資料以及產生該證據的 Europe PMC 查詢。

**Q5：Librarian 與傳統密集向量資料庫相比，最關鍵的設計差異是什麼？**

A：Librarian 不維護自己的向量索引，而是直接重複使用 Europe PMC 的即時、經過策展的欄位化搜尋基礎設施，因此無需承擔龐大的索引與儲存成本。它保留了密集檢索「自然語言輸入、回傳可引用片段」的優點，但同時具備關鍵字檢索的可檢視性與結構化欄位查詢能力。這種設計讓 Librarian 能夠隨著 Europe PMC 資料更新而即時取得最新文獻，並讓代理或使用者追溯每筆證據的來源查詢。

**Q6：為什麼 Librarian 採用單一 LLM 控制器來協調整個檢索流程？**

A：單一 LLM 控制器讓 Librarian 能夠統一處理查詢規劃、文獻檢索、段落拆解與證據評分，簡化系統架構並降低模組間溝通成本。由於該設計是模型無關的，任何更強大的大型語言模型都可以直接替換為引擎，使系統能隨著基礎模型進步而自動提升效能。此外，集中式協調也讓 Librarian 能根據原始問題動態調整子查詢策略與證據篩選標準，提升檢索的靈活性。

**Q7：作者使用了哪些基準來評估 Librarian 的表現？**

A：評估涵蓋四類任務，分別是文獻綜合、聲稱驗證、開放領域問答以及下游生物學任務。具體使用的基準包括 ScholarQABench、ProClaim 聲稱驗證管線、LitQA2 開放式文獻問答，以及 LAB-Bench 中的生物學工作流程任務。這些基準從引用品質、專家共識一致性、問答準確率到實驗流程與序列操作能力，全面檢驗 Librarian 作為知識層的價值。

**Q8：Librarian 在實驗中取得了哪些關鍵成果？**

A：在 ScholarQABench 上，Librarian 的平均引用 F1 比近期強大的基線模型提升超過 16 分。作為 ProClaim 聲稱驗證管線的檢索層時，它使結果與專家共識的一致性平均提升 5 分。在 LitQA2 上，搭載 Librarian 的 GPT-5.4 代理比使用網路搜尋的設定準確率高出約 8 分，而在 LAB-Bench 的生物序列操作任務上，宏觀準確率最高提升 11.3 分。

**Q9：從實驗結果可以觀察到哪些任務類型的增益特別明顯？**

A：文獻綜合任務的引用 F1 提升最為顯著，顯示 Librarian 回傳的精簡證據片段能幫助代理更準確地引用來源。在需要精確事實查核的聲稱驗證任務中，Librarian 也明顯拉近了模型輸出與專家共識的距離。此外，在實驗流程問題與生物序列操作等下游生物學任務上，Librarian 同樣帶來穩定進步，尤其在序列操作這類高專業性任務上進步最大。

**Q10：Librarian 在實際研究場景中可以如何被使用？**

A：研究人員可以將 Librarian 嵌入文獻綜合工具，讓代理自動彙整多篇論文並附上可驗證引用。它也能作為聲稱驗證系統的檢索層，協助快速判斷某個科學主張是否有已發表證據支持。此外，在設計實驗流程、進行分子選殖或序列操作時，Librarian 可為生物資訊代理提供即時、可信且可追溯的文獻依據。

**Q11：從產品化角度來看，Librarian 有哪些優勢？**

A：由於 Librarian 不自行建立向量索引，部署與維護成本遠低於傳統密集檢索系統，且能自動受益於 Europe PMC 的資料更新與策展品質。其模型無關架構讓產品可以靈活替換底層大型語言模型，並隨模型升級而提升效能。每筆證據都保留原始 Europe PMC 查詢，也讓產品具備良好的可解釋性與稽核能力，有助於建立使用者信任。

**Q12：Librarian 對生命科學領域更廣泛的影響可能是什麼？**

A：Librarian 示範了如何將既有的開放文獻基礎設施升級為代理優先的知識層，為其他領域的類似轉型提供參考。它有助於降低 AI 代理在生命科學研究中的幻覺風險，因為代理的推理能更穩固地錨定在可引用的發表證據上。長遠來看，這類知識層可能成為生命科學研究自動化的標準元件，促進更快速、透明且可重現的科學發現。

**Q13：Librarian 目前可能存在哪些限制？**

A：Librarian 的表現仍受制於底層 Europe PMC 的檢索結果品質與覆蓋範圍，若原始資料庫缺少相關文獻，系統也無法憑空產生證據。由於整個流程由單一 LLM 協調，模型本身的錯誤或偏誤可能影響子查詢生成、文獻選擇與證據評分的正確性。此外，對於需要跨多篇論文進行高度複雜綜合推理的問題，僅回傳精簡片段可能不足以支撐完整論證。

**Q14：哪些情況可能導致 Librarian 檢索失敗或表現不佳？**

A：當問題涉及非常新穎或跨領域的主題，而相關術語尚未穩定出現在 Europe PMC 的索引或註釋中時，召回率可能下降。若生物實體擁有過多別名或高度歧義名稱，LLM 產生的子查詢可能遺漏關鍵表面形式，導致遺漏重要文獻。此外，當所需答案分散在多篇論文的方法或圖表中，且無法被單一段落完整捕捉時，精簡證據片段的效用也會受限。

**Q15：未來可以朝哪些方向進一步發展 Librarian？**

A：未來可以結合多模態能力，讓 Librarian 不僅檢索文字，也能定位圖表與表格中的相關證據。系統也可以加入主動式查詢改寫與互動式澄清機制，在問題模糊時向使用者或代理確認意圖。此外，將 Librarian 擴展到更多語言、整合預印本與開放資料庫，並與生物資訊工具鏈更緊密結合，都是值得探索的發展方向。

## 實務應用指南

### 適用場景

1. **系統性文獻回顧與證據綜合**
   研究團隊在撰寫系統性回顧或藥物機轉綜述時，可透過 Librarian 以自然語言提問，例如「CRISPR-Cas9 在 iPSC 分化中的 off-target 效應有哪些證據？」，系統會自動規劃互補子查詢、檢索 Europe PMC，並回傳帶有引用來源的精簡證據片段，減少研究人員逐篇閱讀全文的負擔。

2. **生物醫學聲稱驗證**
   生技公司、監管事務或科學傳播團隊在審查產品宣稱或新聞稿時，可將 Librarian 作為檢索層嵌入 ProClaim 等聲稱驗證管線，自動比對公開文獻是否支持特定生物標誌物、療效或機制聲稱，並提升與專家共識的一致性。

3. **實驗室流程問答與序列操作輔助**
   實驗室可將 Librarian 整合至內部知識庫或 ELN（電子實驗筆記本），回答「如何設計 AAV 載體的 ITR 引物？」或「某蛋白質的常見突變如何影響功能？」等下游生物學任務，特別在序列操作類問題上可顯著提升準確率。

4. **假說生成與生物標誌物優先排序**
   藥物探索團隊在初期靶點發現階段，可利用 Librarian 快速彙整某疾病、基因或化合物相關的文獻證據，作為生成可驗證假說或排序候選生物標誌物的知識層。

5. **開放領域學術問答服務**
   大學圖書館、研究機構入口網站或學術搜尋引擎可將 Librarian 作為後端，讓使用者以自然語言查詢生命科學問題，並獲得可引用、可追蹤來源的答案，而非僅回傳整篇論文連結。

### 實作前置條件

**資料需求**
- 無需自建向量資料庫或全文索引，但須能穩定存取 Europe PMC 即時搜尋 API 與全文內容。
- 若應用於特定子領域（如某種癌症或模式生物），建議準備領域常見實體別名表（基因符號、蛋白質名稱、疾病同義詞、MeSH 詞彙），以輔助子查詢規劃。

**運算需求**
- 主要運算負載來自單一 LLM 協調器與 Europe PMC API 呼叫，無需大規模嵌入索引基礎設施。
- 需準備 LLM 推理端點（可為 OpenAI、Anthropic、開源模型或地端部署），並預留足夠的 Token 預算處理文獻片段評分與排序。
- 建議具備快取層與佇列機制，以管理 API 速率限制與重複查詢。

**技能需求**
- 熟悉 Python 與 REST API 整合。
- 具備提示工程（prompt engineering）經驗，能調整查詢規劃、證據評分與排序的提示。
- 了解生命科學文獻結構（摘要、方法、圖表、參考文獻）與基本生物資訊實體命名規則。
- 具備評估 RAG 或檢索增強系統的經驗，能使用 Citation F1、LitQA2 等指標進行驗證。

### 實作步驟建議

1. **環境建置與 API 接入**
   申請 Europe PMC API 存取權限，設定 LLM 服務憑證，並從 GitHub 取得 Librarian 原始碼、提示與執行設定。

2. **定義證據單元與輸出格式**
   決定下游代理需要的證據粒度（例如段落、句子或圖表說明），並設計輸出結構：文字片段、論文後設資料（標題、作者、DOI、PMID）以及產生該證據的 Europe PMC 查詢。

3. **實作查詢規劃模組**
   利用 LLM 將自然語言問題拆解為多個互補子查詢，涵蓋不同別名、物種限制與欄位（如基因、蛋白質、化學物質、疾病註釋），以提升召回率。

4. **串接即時檢索與文件篩選**
   透過 Europe PMC 即時搜尋執行子查詢，取得候選論文後，依相關性與可取得性（開放近用全文與否）篩選，避免處理過多全文。

5. **段落拆解與證據評分**
   將選定論文分解為段落，使用 LLM 對每個候選片段與原始問題的相關性進行評分，並過濾假陽性，回傳精簡、可引用的證據清單。

6. **建置代理介面與追蹤機制**
   提供自然語言查詢介面，並保留每筆證據對應的 Europe PMC 查詢語法，讓使用者或下游代理能夠檢查與驗證檢索過程。

7. **評估與迭代**
   在 ScholarQABench、LitQA2 或自製領域測試集上評估 Citation F1 與回答準確率，針對低召回或低精確度的問題類別調整子查詢策略與提示。

### 潛在風險與注意事項

- **幻覺與證據錯誤引用**
  LLM 在評分或摘要時可能產生未出現在原文的資訊。建議強制要求每個證據片段附上原始文字與 PMID，並讓下游系統只引用回傳的原始片段，而非由模型自由生成。

- **API 速率限制與延遲**
  Europe PMC 與 LLM API 皆有呼叫限制，高頻查詢可能導致延遲或中斷。應實作指數退避、快取與非同步佇列，並監控每次查詢的延遲與成本。

- **開放近用與版權限制**
  並非所有 Europe PMC 記錄都具備開放全文，部分僅提供摘要。若應用需要完整方法或圖表內容，需確認授權狀態，或將檢索範圍限制於開放近用全文。

- **實體別名覆蓋不足**
  基因符號、疾病同義詞或化學物質名稱若未在子查詢中充分展開，可能遺漏關鍵文獻。建議結合外部詞彙表（如 MeSH、HGNC）進行查詢擴展。

- **證據選擇偏差**
  LLM 在排序證據時可能偏好常見或近期文獻，忽略冷門但重要的研究。可引入多樣性排序或強制納入不同觀點的證據。

- **模型依賴與成本波動**
  雖然 Librarian 是模型無關架構，但不同 LLM 在查詢規劃與證據評分上的表現差異顯著。建議建立模型切換與 A/B 測試機制，並持續追蹤成本。

本文示範了一個具體的 AI 應用：讓電腦程式（AI 代理）用自然語言查詢生命科學文獻，並直接獲得可引用的答案片段。建議先理解 Europe PMC 是什麼、為什麼傳統關鍵字搜尋對 AI 不友善，再關注 Librarian 如何透過「問題拆解 → 多次搜尋 → 精選證據」三步驟解決這個問題，無需深入技術細節即可掌握其核心價值。

**AI 工程師**
重點閱讀系統架構與協調流程：單一 LLM 如何同時扮演查詢規劃器、檢索執行器與證據評分器；為何選擇不建立自有向量索引，而是直接呼叫 Europe PMC 即時搜尋；以及模型無關設計帶來的擴展性。可進一步研究提示設計、段落拆解策略、相關性評分方法，並思考如何將此模式遷移到其他領域的專業文獻資料庫。

**研究人員**
建議聚焦評估結果與適用任務：Librarian 在文獻綜合、聲稱驗證、開放領域問答與下游生物學任務上的表現，特別是 Citation F1 與 LitQA2 準確率的提升。可思考如何將此工具應用於自己的研究領域，例如系統性回顧、假說生成或實驗設計，同時注意開放近用限制與證據偏差的問題。

**產品經理**
本文提供了一個清晰的產品定位：為生命科學 AI 代理打造的「知識層」。建議從商業場景出發，評估哪些產品功能（如文獻問答、聲稱驗證、實驗輔助）最適合優先導入 Librarian；同時關注成本結構（LLM Token、API 呼叫）、合規性（引用來源透明、版權）以及與現有產品（ELN、LIMS、RAG 系統）的整合路徑。
