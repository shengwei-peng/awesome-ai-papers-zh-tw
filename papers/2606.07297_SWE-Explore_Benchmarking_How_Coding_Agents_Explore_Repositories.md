## ⚡ TL;DR

現有程式碼基準測試以二元通過率評估代理，無法區分探索與修補能力。
本文提出SWE-Explore基準，從成功軌跡中擷取行級標準答案，評估探索器的排序品質。
實驗顯示代理式探索器優於經典擷取，行級涵蓋率與排序效率為關鍵差異指標。

## 摘要翻譯

程式碼庫層級的程式碼基準測試（例如 SWE-bench）已大幅提升程式碼代理的能力。然而，這些基準測試通常將程式碼任務視為整體性的二元預測（binary prediction）問題（例如，已解決或未解決），忽略了諸如程式碼庫理解（repository understanding）、上下文擷取（context retrieval）、程式碼定位（code localization）和錯誤診斷（bug diagnosis）等細粒度的代理能力。在本文中，我們提出 SWE-Explore，這是一個用於獨立評估程式碼庫探索（repository exploration，程式碼代理的一項關鍵能力）的基準測試。給定一個程式碼庫和一個問題，SWE-Explore 要求探索器在固定的行數預算（line budget）下，回傳排序後的相關程式碼區域清單。SWE-Explore 涵蓋橫跨 10 種程式語言（programming languages）與 203 個開源程式碼庫（open-source repositories）的 848 個問題。針對每個實例，我們從成功解決相同問題的多條獨立代理軌跡（agent trajectories）中萃取出行級標準答案（ground truth），提煉出其解題路徑實際參考的特定程式碼區域。我們從涵蓋率（coverage）、排序（ranking）和上下文效率（context-efficiency）三個維度評估探索，表明這些指標緊密對應下游修復行為（repair behavior）。在廣泛的擷取方法（retrieval methods）、通用程式碼代理（general coding agents）和專用定位器（specialized localizers）中，我們發現代理式探索器（agentic explorer）在效能上明顯領先於經典擷取（classical retrieval）。雖然現代方法在檔案層級定位（file-level localization）上已表現強健，但行級涵蓋率（line-level coverage）與高效的排序仍是區分最先進（state-of-the-art）探索器的關鍵軸線。

### 核心貢獻（3～5點）
- **提出 SWE-Explore 基準測試**：專注於獨立評估程式碼代理的程式碼庫探索能力，彌補現有基準測試（如 SWE-bench）僅進行整體性二元預測而忽略細粒度能力的不足。
- **建構大規模多語言評估資料集**：涵蓋 10 種程式語言、203 個開源程式碼庫中的 848 個問題，提供具規模且多樣化的測試平台（testbed）。
- **設計基於成功軌跡的行級標準答案**：從多條獨立成功解決問題的代理軌跡中萃取出實際參考的程式碼區域，作為行級標準答案，確保評估依據具備實證基礎。
- **提出三維度評估框架**：以涵蓋率、排序與上下文效率三個維度直接評估探索品質（exploration quality），並驗證這些指標與下游修復行為高度相關。
- **揭示現有方法的關鍵差異化軸線**：實證發現代理式探索器明顯優於經典擷取方法；現代方法在檔案層級定位上已趨成熟，但行級涵蓋率與高效排序仍是區分最先進探索器的核心挑戰。

### 適合對象
- 研究軟體工程代理（software engineering agent）、自動化程式修復或 AI 程式碼生成的研究者與博士生。
- 從事資訊擷取（information retrieval）、搜尋代理（search agent）或上下文管理（context management）技術開發的學術與業界團隊。
- 關心大型語言模型在長時程專業任務（long-horizon professional task）中推理與規劃能力的研究人員。
- 建構或評估程式碼代理框架（如 SWE-agent、AutoCodeRover、OpenHands 等）的工程師與技術主管。
- 對多模態軟體問題（multimodal software issue）與多語言程式碼庫（multilingual repository）基準測試設計感興趣的學者。

## 深度分析

#### 方法論解析

SWE-Explore 的核心方法論在於將「程式碼庫探索」(repository exploration) 從端到端 (end-to-end) 的修復流程中抽離出來,建立一個獨立的、可量化的評估目標。這個方法論設計包含三個關鍵支柱:**任務形式化**、**標準答案建構**、以及**多維度評估框架**。

**任務形式化 (Task Formalization)**

論文將探索任務定義為一個「在固定行數預算 (line budget) 下的排序式上下文選擇問題」(ranked context selection under a fixed line budget)。給定一個 issue 描述與一個程式碼庫,explorer 必須輸出一個排序過的程式碼區域列表 (ranked list of code regions)。這個設計的精妙之處在於其「輸出格式的刻意簡化」——無論是稀疏擷取器 (sparse retrievers)、互動式代理 (interactive agents),還是長上下文選擇器 (long-context selectors),都被統一視為同一種「排序區域列表的生產者」(producers of ranked region lists)。這種抽象使得異質方法之間的比較變得公平且直接,避免了因為輸出格式差異而產生的評估偏差。

**標準答案建構 (Ground Truth Construction)**

SWE-Explore 最具方法論創新性的部分在於其「軌跡衍生標準答案」(trajectory-derived ground truth) 的建構方式。具體而言,對於每個 issue,作者收集多個「獨立成功解決該 issue 的代理軌跡」(independent agent trajectories that successfully solved the same issue),然後從這些軌跡中提煉出「解決路徑實際查閱的具體程式碼區域」。這種方法有三個重要意涵:

1. **避免人工標註的成本與偏見**:不同於 ContextBench [13] 需要人工標註黃金上下文 (gold contexts),SWE-Explore 透過軌跡聚合自動產生標準答案,大幅降低了標註成本。
2. **反映真實的探索需求**:標準答案來自於「成功解決」的軌跡,因此代表的是「實際被證明有用」的程式碼區域,而非理論上可能相關的區域。
3. **多軌跡共識機制**:透過聚合多個獨立軌跡,可以過濾掉單一代理的偶然行為,保留更具普遍性的探索模式。

**多維度評估框架 (Multi-Dimensional Evaluation Framework)**

論文提出沿三個維度評估探索品質:**涵蓋率 (coverage)**、**排序 (ranking)**、以及**上下文效率 (context-efficiency)**。這個三維框架的設計邏輯在於:一個優秀的 explorer 不僅要找到正確的程式碼區域(涵蓋率),還要在排序中將其前置(排序品質),並且在有限的行數預算內達成這些目標(效率)。這種設計避免了單一指標可能帶來的盲點——例如,一個 explorer 可能涵蓋了所有正確區域但將其埋在排序末尾,或反之。

**下游驗證協議 (Downstream Validation Protocol)**

為了驗證探索指標的外部效度 (external validity),論文設計了一個受控的下游協議:將每個 explorer 的輸出作為「唯一可見的程式碼庫上下文」餵給一個固定的程式碼代理,然後測量其產生的修補程式是否能通過原始測試套件。這個設計巧妙地將探索品質與修復行為連結起來,證明了「探索指標的提升確實對應到下游修復成功率的提升」。

#### 實驗數據解讀

雖然完整實驗數據未在提供的文本中,但從摘要與方法論描述可以推導出以下關鍵實驗發現與其意涵:

**探索者分層現象 (Explorer Tiering)**

實驗揭示了一個清晰的「代理式探索器 (agentic explorers) 顯著優於經典擷取 (classical retrieval)」的分層現象。這意味著傳統的資訊擷取方法(如 BM25、embedding-based retrieval)在面對複雜的程式碼庫探索任務時存在根本性限制——它們缺乏互動式推理能力,無法根據初步發現調整搜尋策略。相比之下,代理式方法能夠進行多輪推理、動態調整查詢,展現出更接近人類開發者的探索模式。

**檔案層級 vs. 行級表現差距**

論文指出「檔案層級定位 (file-level localization) 對現代方法而言已經相當成熟」,但「行級涵蓋率 (line-level coverage) 與高效排序 (efficient ranking) 仍是區分最先進探索器的關鍵軸線」。這個發現極具實務意涵:它意味著現有方法的瓶頸不在於「找到正確的檔案」,而在於「在檔案內精確定位到關鍵的程式碼行」,以及「在排序中將這些關鍵行前置」。這對實際應用有直接影響——即使 explorer 找到了正確檔案,如果無法精確指出需要修改的行,仍會浪費大量上下文預算在無關程式碼上。

**指標與修復行為的強相關性**

「沿著涵蓋率、排序、上下文效率維度的指標強烈追蹤下游修復行為」這項發現是 SWE-Explore 方法論效度的核心證據。它意味著這些指標不僅是理論上的測量,更是實際修復成功的預測因子。這種「指標-行為一致性」(metric-behavior alignment) 是評估基準設計的黃金標準。

**跨語言泛化性**

SWE-Explore 涵蓋 848 個 issues,橫跨 10 種程式語言與 203 個開源程式碼庫。這個規模與多樣性使得實驗結論具有較強的泛化性,不會僅限於特定語言或領域。10 種程式語言的覆蓋也意味著結論對 Python、Java、JavaScript、Go、Rust 等主流語言生態都適用。

**實驗設計的潛在侷限**

從提供的資訊來看,實驗可能存在以下值得關注的點:標準答案來自「成功軌跡」,這可能引入「survivorship bias」(存活者偏差)——只有被成功解決的 issue 才會被納入,而最困難的 issue 可能因為從未被成功解決而被排除。此外,「成功軌跡」本身可能反映的是特定代理的探索偏好,不同代理可能有不同的「正確探索路徑」。

#### 與現有研究的比較

SWE-Explore 在現有研究中佔據一個獨特且互補的位置。透過論文提供的 Table 1 比較框架,可以從六個設計維度進行定位:

**與 SWE-bench 系列的比較**

SWE-bench [11]、SWE-bench Verified [6]、SWE-bench Multilingual [30]、SWE-bench Pro [7] 都是「可執行基準 (execution-based benchmarks)」,以最終通過測試與否作為評估標準。SWE-Explore 與這些基準的關鍵差異在於:**SWE-Explore 不要求 explorer 寫出或驗證修補程式**,而是專注於探索階段。這種解耦使得評估更為輕量,也使得無法執行修補的方法(如純擷取器)能夠被納入比較。

**與 Loc-Bench 的比較**

Loc-Bench [5] 專注於定位,但缺乏多語言支援、軌跡衍生標準答案、聯合探索+修復評估,以及排序區域評估。SWE-Explore 在這些維度上都有所突破,特別是「軌跡衍生標準答案」這項設計,使得評估目標更貼近實際探索需求。

**與 ContextBench 的比較**

ContextBench [13] 引入了人工標註的黃金上下文並對代理軌跡進行評分,但缺乏行級標準答案與排序區域評估。SWE-Explore 的「軌跡衍生標準答案」方法避免了 ContextBench 的人工標註成本,同時提供了更精細的行級評估。

**與 SWE-ContextBench、SWE-Pruner 的比較**

SWE-ContextBench [37] 與 SWE-Pruner [26] 分別基準化上下文壓縮與經驗重用,但都不具備軌跡衍生標準答案。SWE-Explore 與這些基準形成互補——前者評估「找到正確上下文」,後者評估「有效管理已找到的上下文」。

**SWE-Explore 的獨特貢獻**

綜合來看,SWE-Explore 的獨特價值在於它是**第一個同時具備**以下特性的基準:(1) 可執行驗證,(2) 多語言覆蓋,(3) 行級標準答案,(4) 軌跡衍生標準答案,(5) 聯合探索+修復評估,(6) 排序區域評估。這種「六維全備」的設計使得它能夠同時服務於擷取研究、代理研究、以及上下文管理研究社群。

**相較於現有工作的改進**

1. **更精細的評估粒度**:從檔案級到行級的跨越,使得評估能夠捕捉到現有方法無法觀察的細節差異。
2. **更公平的比較框架**:統一輸出格式使得異質方法能夠在同一基準上比較。
3. **更強的外部效度驗證**:透過下游修復協議,證明了探索指標的實務價值。
4. **更低的標註成本**:軌跡衍生方法避免了昂貴的人工標註。

**潛在限制**

1. **標準答案的代理偏見**:軌跡衍生標準答案可能反映特定代理的探索偏好,不同代理可能對「正確探索路徑」有不同看法。
2. **存活者偏差**:只使用成功解決的 issue 可能無法代表完整的 issue 難度分布。
3. **行數預算的任意性**:固定的行數預算可能無法反映所有實際應用場景的需求。
4. **靜態快照的限制**:使用程式碼庫的靜態快照可能無法捕捉動態探索行為(如執行測試、查看 git history)。

#### 可重現性評估

從提供的文本資訊來評估 SWE-Explore 的可重現性:

**正面指標**

1. **明確的基準規模**:論文清楚說明了 848 個 issues、10 種程式語言、203 個開源程式碼庫,提供了具體的規模資訊。
2. **標準化的評估協議**:固定行數預算、排序區域列表輸出格式,這些都是可標準化的設計。
3. **公開的程式碼庫來源**:使用 203 個開源程式碼庫,這些都是公開可取得的。
4. **方法論透明度**:軌跡衍生標準答案的方法在論文中有所描述,理論上可以重現。

**需要進一步確認的面向**

1. **基準資料集的公開性**:論文未明確說明 SWE-Explore 基準資料集是否會公開釋出,以及釋出的形式(完整軌跡、僅標準答案、評估腳本等)。
2. **評估腳本的可取得性**:標準化的評估腳本對於重現實驗結果至關重要,但論文中未明確提及。
3. **預訓練模型權重**:SWE-Explore 是評估基準而非模型,本身不涉及模型權重,但其下游協議中使用的「固定程式碼代理」若為閉源模型,可能影響重現性。
4. **軌跡資料的來源**:成功軌跡的來源代理(如 SWE-agent、AutoCodeRover 等)若是閉源或需要特定 API 存取,可能限制標準答案的獨立重現。

**重現性風險評估**

整體而言,SWE-Explore 的重現性處於中等水準。基準設計本身具有可重現性,但完整的實驗重現可能受限於:(1) 軌跡資料的取得成本,(2) 下游協議中使用的程式碼代理的可取得性,(3) 評估基礎設施的複雜度。建議作者在最終版本中明確提供資料集、評估腳本、以及完整的實驗配置,以提升基準的實用價值。

#### 未來研究方向

基於 SWE-Explore 的設計與發現,以下是幾個值得探索的未來研究方向:

**1. 動態探索行為評估**

SWE-Explore 目前評估的是「最終輸出的排序列表」,但實際的探索過程是動態的、多輪的。未來可以探索如何評估「探索過程的品質」,例如:探索效率(找到正確區域所需的步驟數)、探索策略的合理性(是否避免了冗餘查詢)、以及探索的適應性(是否能根據初步發現調整策略)。

**2. 多代理軌跡融合的標準答案建構**

目前的標準答案來自多個獨立軌跡的聚合,但聚合方式可能影響標準答案的品質。未來可以探索更 sophisticated 的融合方法,例如:根據軌跡品質加權、識別軌跡間的共識與分歧、或使用軌跡間的一致性作為信心指標。

**3. 跨語言探索的遷移學習**

SWE-Explore 涵蓋 10 種程式語言,但不同語言的探索模式可能有所不同。未來可以探索:探索策略是否能跨語言遷移?某些語言(如動態語言 vs. 靜態語言)是否需要特殊的探索方法?語言特性如何影響探索難度?

**4. 探索與修復的聯合最佳化**

SWE-Explore 將探索與修復解耦評估,但實際應用中兩者是聯合最佳化的。未來可以探索:如何設計能夠在探索階段就考慮修復需求的代理?探索策略是否可以根據修復反饋動態調整?

**5. 大型程式碼庫的可擴展性**

SWE-Explore 的 203 個程式碼庫雖然規模可觀,但現代企業級程式碼庫可能更大、更複雜。未來可以探索:探索方法在百萬行級程式碼庫上的表現如何?是否需要層次化的探索策略(如先模組級、再檔案級、最後行級)?

**6. 探索品質與程式碼品質的關聯**

SWE-Explore 評估的是「找到正確程式碼」的能力,但未來可以探索探索品質與程式碼品質指標(如可維護性、可測試性)的關聯。例如:高品質的程式碼是否更容易被探索?探索品質能否作為程式碼品質的間接指標?

**7. 對抗性探索評估**

目前的標準答案來自「成功軌跡」,但這可能使評估過於「友善」。未來可以探索對抗性評估:設計刻意混淆探索的 issue(如多個相似檔案、誤導性的錯誤訊息),以測試 explorer 的魯棒性。

**8. 探索成本的可持續性**

SWE-Explore 評估了上下文效率,但未考慮計算成本。未來可以探索:探索品質與計算成本的權衡?是否存在「足夠好」的探索策略,能夠在低成本下達成高品質?

**9. 與人類開發者的比較**

SWE-Explore 的標準答案來自代理軌跡,但人類開發者的探索模式可能有所不同。未來可以探索:代理探索與人類探索的差異?人類的探索經驗能否用於改進代理?代理探索能否反過來增強人類開發者的效率?

## 論文問答

**Q1：為什麼現有的程式碼庫層級基準測試（如 SWE-bench）在評估程式碼代理時存在根本性的限制？**

A：現有的程式碼庫層級基準測試將整個修復流程簡化為單一的通過/失敗二元預測，這種做法雖然讓不同模型之間可以直接比較，卻掩蓋了成功背後的細部機制。一個二元分數無法揭示代理究竟是在閱讀相關程式碼、定位錯誤、生成修補程式，還是驗證修復等哪個環節成功或失敗。這種「端到端」的評估方式將探索、定位、修補程式合成等多種能力混雜在一起，使我們無法精確診斷代理的瓶頸所在，也阻礙了針對性的改進。

**Q2：SWE-Explore 想要解決的核心問題是什麼？**

A：SWE-Explore 旨在將「程式碼庫探索」這項關鍵能力從端到端的修復流程中抽離出來，作為一個獨立、可比較的評估目標。具體而言，它將探索任務形式化為：在給定問題與程式碼庫的情況下，要求探索器返回一個在固定行數預算下的相關程式碼區域排序清單。這種設計使得稀疏擷取器、互動式代理與長上下文選擇器都能以相同的輸出格式進行比較，無需實際撰寫或驗證修補程式。

**Q3：為什麼程式碼庫探索被視為程式碼代理的一項關鍵能力？**

A：一個真實的程式碼庫通常包含數千個檔案，要從中找出哪幾行具體的程式碼承載了某個問題的證據，是一項極具挑戰性的任務。即使是那些最終成功解決問題的代理，也必須先精準地定位到相關的程式碼片段才能進行後續修復。當代理失敗時，我們需要區分兩種截然不同的失敗模式：未能探索到相關程式碼，或是已取得足夠證據但無法合成正確修補程式，而後者已被現有的可執行基準測試所涵蓋，前者則長期處於被低估的狀態。

**Q4：SWE-Explore 如何將探索任務形式化？**

A：SWE-Explore 將探索任務定義為一個排序的、行級的上下文選擇任務：給定一個問題描述與一個程式碼庫，探索器需要返回一個排序的程式碼區域清單，並在固定的行數預算下進行評分。這種形式化設計刻意保持簡單，使不同類型的探索方法——無論是經典資訊擷取、互動式搜尋代理，還是長上下文選擇器——都能被視為同一種「排序區域清單的產生器」來比較。透過這種統一的介面，評估可以聚焦於探索行為本身，而不必涉及修補程式的撰寫或驗證。

**Q5：SWE-Explore 如何從代理軌跡中衍生出標準答案（ground truth）？**

A：SWE-Explore 提出了一種新穎的「軌跡基礎監督」方法，從獨立成功解決相同問題的代理軌跡中提煉出標準答案的程式碼區域。具體而言，對於每個實例，研究者分析那些成功解決該問題的代理在解題過程中實際查閱了哪些具體的程式碼區域，並以此作為該問題的標準答案。這種方法大幅減少了對人工標註的需求，同時確保了標準答案反映了真實有效的解題路徑，而非主觀猜測。

**Q6：SWE-Explore 在評估指標設計上有哪些關鍵選擇？**

A：SWE-Explore 從三個維度系統性地評估探索品質：涵蓋率（coverage）衡量探索器是否找到了所有相關的程式碼區域；排序（ranking）評估相關區域在輸出清單中的優先級；上下文效率（context-efficiency）則關注在有限行數預算下探索器能多快地浮現關鍵證據。此外，SWE-Explore 還配備了一個受控的下游驗證協議：將探索器的輸出作為唯一可見的程式碼庫上下文餵給一個固定的程式碼代理，藉此驗證探索指標與下游修復成功之間的關聯性。

**Q7：SWE-Explore 基準測試的規模與覆蓋範圍如何？**

A：SWE-Explore 涵蓋了 848 個問題實例，橫跨 10 種程式語言與 203 個開源程式碼庫，呈現出廣泛的多語言與多領域特性。這樣的規模與多樣性使得評估結果具有相當的代表性與泛化能力，避免了單一語言或單一領域可能帶來的偏差。相較於僅針對 Python 的 SWE-bench Verified 等基準測試，SWE-Explore 的多語言覆蓋更能反映真實世界中軟體開發的多樣性。

**Q8：SWE-Explore 的實驗揭示了哪些主要發現？**

A：實驗結果顯示，代理式探索器（agentic explorers）形成了一個明顯高於經典擷取方法的層級，證明了互動式、代理驅動的探索策略相較於傳統資訊擷取具有顯著優勢。同時，研究也發現現代方法在檔案層級定位上已經表現強勁，但行級涵蓋率與高效的排序仍是區分最先進探索器的關鍵軸線。這意味著未來的改進空間主要在於如何更精準地定位到具體的程式碼行，而非僅僅找到正確的檔案。

**Q9：SWE-Explore 如何驗證其探索指標能預測下游修復的成功率？**

A：SWE-Explore 設計了一個受控的下游協議：將每個探索器的輸出——且僅有該輸出——作為可用的程式碼庫上下文，提供給一個固定的程式碼代理，然後測量其生成的修補程式是否能通過原始的測試套件。這個協議並非要取代主要的基準測試，而是作為一種外部效度檢驗，確認探索指標所衡量的內容確實與下游成功驅動因素一致。透過這種方式，SWE-Explore 確保了其評估不僅是理論上的合理，更與實際的修復行為密切相關。

**Q10：SWE-Explore 在哪些實際應用場景中具有價值？**

A：在大型企業級程式碼庫的維護中，SWE-Explore 的探索能力評估能幫助團隊選擇最適合的代理工具來處理錯誤修復、功能新增等任務。對於開源專案的維護者而言，該基準測試提供了一個標準化的方式來評估不同代理在陌生程式碼庫中的導航能力。此外，在程式碼審查、安全漏洞排查等需要快速定位關鍵程式碼片段的場景中，SWE-Explore 所衡量的行級探索能力也具有直接的實務意義。

**Q11：SWE-Explore 如何影響程式碼代理產品的設計？**

A：透過揭示行級涵蓋率與排序效率是當前的主要瓶頸，SWE-Explore 為產品設計者指明了優化方向：應投資於更精細的上下文選擇機制，而非僅僅追求檔案層級的命中率。產品的架構設計可以借鑒 SWE-Explore 的下游驗證協議，將探索模組與修補合成模組解耦，以便獨立優化與評估各個環節。這種模組化思路也有助於在資源受限的環境中部署更高效的代理，因為可以根據行數預算動態調整探索深度。

**Q12：SWE-Explore 對自動化軟體工程領域的更廣泛影響是什麼？**

A：SWE-Explore 推動了代理能力評估從「整體二元判斷」向「細粒度、多維度」的範式轉移，這種分解式評估的思路將成為未來基準測試設計的重要參考。它促使研究者認識到，探索、定位、修補合成等是不同的能力維度，需要各自獨立的評估方法與改進策略。同時，軌跡基礎監督的方法也為其他領域的基準測試建構提供了新範式，特別是在難以進行大規模人工標註的場景中。

**Q13：SWE-Explore 存在哪些已知的局限性？**

A：由於標準答案源自成功代理的軌跡，可能存在「代理偏見」——即標準答案反映的是現有代理的解題模式，而非理論上最優的探索路徑。這意味著某些需要非傳統或創造性探索方式才能解決的問題，可能在評估中被低估。此外，軌跡基礎的標準答案也可能受到代理框架本身的限制，例如某些代理可能因為架構設計而傾向於探索特定類型的程式碼區域。

**Q14：哪些失敗案例或邊緣情況可能對 SWE-Explore 構成挑戰？**

A：對於需要跨多個檔案進行複雜關聯才能解決的問題，僅僅評估個別檔案內的行級涵蓋率可能不足以反映真實的探索難度。當問題描述模糊或需要領域專業知識才能理解時，探索器可能因為無法正確解讀問題而失敗，但這種失敗並非探索能力本身的問題。此外，對於需要動態執行、除錯資訊或測試結果才能定位的錯誤，靜態的程式碼探索可能無法提供完整的證據。

**Q15：SWE-Explore 開啟了哪些值得探索的未來研究方向？**

A：未來可以探索如何將 SWE-Explore 的評估框架擴展到多輪、互動式的探索場景，其中代理可以根據初步發現動態調整搜尋策略。另一個方向是結合靜態分析、動態執行資訊與語義理解，開發能更高效進行行級定位的混合式探索方法。此外，將 SWE-Explore 的軌跡基礎監督方法應用於其他軟體工程任務（如重構、測試生成）的評估，也是一個極具潛力的研究方向。

## 實務應用指南

### 適用場景

1. **企業內部程式碼庫的智慧除錯助手**：在大型 monorepo 或微服務架構中，當開發者回報 issue 時，團隊可使用 SWE-Explore 評估框架來挑選最適合的探索器（explorer），快速縮小「需要修改的程式碼行」範圍，縮短平均修復時間（MTTR）。

2. **程式碼代理（coding agent）研發團隊的模型選型與迭代**：在訓練或微調新的程式碼代理時，可將 SWE-Explore 作為離線評估指標，用來比較不同檢索方法、專用定位器與代理式探索器在「行級涵蓋率」與「上下文效率」上的差異，避免僅依賴端到端的解決率。

3. **程式碼審查（code review）與知識傳承工具**：將 SWE-Explore 的軌跡衍生標準答案（trajectory-grounded ground truth）方法應用於內部 PR 流程，自動標註「哪些行是新人最需要理解的關鍵脈絡」，作為 onboarding 教材或審查重點提示。

4. **AI 程式教育平台的學習路徑推薦**：教育平台可利用 SWE-Explore 的多語言覆蓋（10 種程式語言、203 個開源專案），根據學生正在學習的語言或框架，從基準資料集中挑選對應的 issue 與標準答案，產生結構化的練習題。

5. **開源專案維護者的工單分流系統**：對於擁有大量 issue 的開源專案（如 Kubernetes、React、Django），可將 SWE-Explore 評估出的高效探索器整合進 triage 機器人，自動將 issue 路由到熟悉相關模組的維護者，並附上「最可能需要檢查的程式碼區域」。

### 實作前置條件

**資料面**
- 至少一份完整的開源程式碼庫快照（建議支援 Git，能取得 commit hash 與檔案內容）。
- 對應的 issue 描述（標題 + 內文，建議保留原始 markdown 格式）。
- 一組「成功解決該 issue 的代理軌跡」，用於衍生行級標準答案；若無既有軌跡，需先執行至少一次端到端修復以產出資料。
- 評估用的測試套件（test suite），用於下游修復驗證協議。

**運算面**
- 能執行大型語言模型（LLM）推論的環境：建議配備至少一張 24GB 顯（如 A100 / H100），或使用雲端 API（OpenAI、Anthropic、本地 vLLM 部署皆可）。
- 向量資料庫（如 Milvus、Qdrant、FAISS）以支援語意檢索；若使用 BM25 等經典方法則只需 CPU。
- 程式碼索引工具（如 tree-sitter、lsif-tools）以加速檔案結構解析。
- 容器化環境（Docker）以重現 SWE-bench 風格的測試執行環境。

**技能面**
- 熟悉 Python 與命令列工具鏈（git、docker、pytest）。
- 具備資訊檢索（IR）基礎概念：TF-IDF、BM25、embedding、reranker。
- 了解 LLM agent 框架（如 LangChain、OpenHands、SWE-agent）的呼叫方式。
- 能閱讀並修改評估腳本（建議具備基本的軟體工程實務經驗）。

### 實作步驟建議

1. **釐清目標並選取評估軸**：先決定要優化「涵蓋率」、「排序品質」還是「上下文效率」。若產品場景重視「用最少行數找到答案」，優先看 context-efficiency；若重視「絕不放過關鍵證據」，優先看 coverage。

2. **準備基準資料集**：從 SWE-Explore 釋出的 848 個 instance 中，依目標語言與專案類型篩選子集；或依照論文的「軌跡衍生標準答案」流程，從自家成功軌跡中產出新的行級 ground truth。

3. **建立探索器介面**：實作一個統一的 `Explorer` 抽象介面，輸出為「排序過的程式碼區域清單（含檔案路徑與行號範圍）」，使 BM25、embedding 檢索器、LLM 搜尋代理與長上下文選擇器都能以同一格式被評分。

4. **執行評估並收集三類指標**：
   - **Coverage**：在固定行數預算下，標準答案行被涵蓋的比例。
   - **Ranking**：標準答案行在排序清單中出現的位置（可採 MRR、nDCG）。
   - **Context-efficiency**：達到特定涵蓋率所需的最少行數。

5. **執行下游修復驗證**：將探索器的輸出作為「唯一可見的程式碼上下文」餵給一個固定的程式碼代理，觀察其是否能通過原始測試套件。此步驟用來確認你選用的探索指標確實與實際修復成效正相關。

6. **建立基準線與迭代**：先以 BM25 + embedding reranker 作為基準，再逐步加入代理式探索器；每次變更都記錄三類指標與下游解決率，形成可比較的版本歷史。

7. **部署與監控**：將最佳探索器包裝成 API 或 CLI 工具，整合進 IDE 插件、CI 流程或 issue triage 系統；持續監控「探索耗時」、「行數預算使用率」與「下游修復成功率」。

### 潛在風險與注意事項

- **軌跡偏差（trajectory bias）**：標準答案來自「成功代理的軌跡」，但這不代表唯一正確路徑。若某個 issue 有多種合法解法，可能低估其他有效探索路徑。**緩解**：保留多條成功軌跡並取聯集，或加入人工抽樣驗證。

- **行級標註的雜訊**：代理在解決過程中可能「順便讀到」與修復無關的行，導致 ground truth 膨脹。**緩解**：設定最小停留時間或編輯距離門檻，過濾掉僅被快速掃過的行。

- **行數預算的選擇偏差**：不同預算下，探索器的相對排名可能翻轉（例如小預算下 BM25 勝出，大預算下 LLM 代理勝出）。**緩解**：報告多個預算點的結果，而非單一數字。

- **語言覆蓋不均**：SWE-Explore 雖涵蓋 10 種語言，但 Python 與 JavaScript 實例可能遠多於其他語言，導致跨語言泛化結論失真。**緩解**：分語言報告指標，並在自家應用中針對目標語言重新校準。

- **測試套件不可靠**：下游驗證依賴測試是否足夠嚴謹；若測試覆蓋不足，可能誤判探索器品質。**緩解**：搭配 mutation testing 或人工審查抽樣。

- **API 成本與延遲**：代理式探索器仰賴多次 LLM 呼叫，單次評估可能耗費數美元與數十秒。**緩解**：對小預算場景使用快取與早期停止；對生產環境設定嚴格的超時與成本上限。

- **資料洩漏與版本控管**：若評估用的 commit 與訓練資料重疊，會高估模型表現。**緩解**：嚴格鎖定 commit hash，並定期比對訓練集。

### 與其他技術的整合建議

- **與 RAG 系統整合**：將 SWE-Explore 的探索器視為程式碼領域的 retriever，與既有文件 RAG（如 LangChain、LlamaIndex）共用 embedding 與 reranker 基礎設施，降低重複投資。

- **與 CI/CD 流程整合**：在 pull request 階段自動執行探索器，輸出「本次變更可能影響的關鍵行」清單，輔助 reviewer 聚焦；可結合 GitHub Actions 或 GitLab CI。

- **與 issue tracker 整合**：透過 GitHub / GitLab API，在新 issue 建立時自動觸發探索器，將結果以 comment 或 label 形式回填，串接 triage 工作流。

- **與程式碼搜尋工具整合**：將 SWE-Explore 的評估結果作為 Sourcegraph、Code Search 等企業工具的「品質基準」，定期回測以偵測模型退化。

- **與監控與可觀測性平台整合**：把探索器的指標（涵蓋率、效率、下游成功率）匯入 Prometheus / Grafana，建立長期儀表板；異常下降時觸發告警。

- **與 agent 框架整合**：在 OpenHands、AutoCodeRover 等框架中，將「探索階段」與「修補階段」解耦，使探索器可獨立升級與替換，而不必重訓整個代理。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的動機圖（Figure 1）與貢獻列表，理解「為什麼需要把探索與修補分開評估」這個核心問題；接著跳到實驗章節的指標定義，試著用一個小型 Python 專案手動跑一次 BM25 探索器，親身體驗「行級標準答案」的概念，再回頭讀方法細節。

**給 AI 工程師**：重點放在第 3 節的評估協議與第 4 節的實驗設計，特別是「下游修復驗證」如何把探索指標與實際解決率連結；建議直接 clone 官方程式碼，把 `Explorer` 介面實作成可插拔模組，並用自家 codebase 的成功軌跡建立私有基準，作為選型依據。

**給研究者**：第 2 節的相關工作分類與第 5 節的限制討論是切入點；可進一步追蹤 ContextBench、SWE-ContextBench、Loc-Bench 等引用文獻，理解「軌跡衍生標準答案」相較於人工標註的取捨，並思考如何延伸到多模態 issue、長時程任務或 agentic context compression 等開放問題。

**給產品經理**：把 SWE-Explore 視為「衡量 AI 程式碼助手探索能力」的客觀尺規；在規劃產品時，可要求研發團隊以 SWE-Explore 指標作為驗收門檻（例如「在 500 行預算下涵蓋率 ≥ 80%」），並理解「行級涵蓋率」與「使用者感受到的修復速度」之間的對應關係，避免被單一解決率數字誤導。
