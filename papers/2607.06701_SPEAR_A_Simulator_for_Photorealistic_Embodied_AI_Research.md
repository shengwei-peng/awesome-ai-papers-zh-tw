## ⚡ TL;DR

現有照片級真實模擬器在通用性、可程式化與渲染速度上受限。
SPEAR 是 Python 函式庫，透過模組化外掛與 UE 反射系統連接，可動態呼叫逾一萬四千個 UE 函數。
能以每秒 73 幀將 1920x1080 美術影像直寫入 NumPy，並提供多種真實值影像模態與廣泛應用。

## 摘要翻譯

互動式模擬器（interactive simulator）已成為訓練具身智慧體（embodied agent）與生成合成視覺資料（synthetic visual data）的強大工具，但現有的照片級真實模擬器（photorealistic simulator）在通用性、可程式化能力（programmability）與渲染速度方面仍有不足。我們透過提出 SPEAR：照片級真實具身人工智慧研究模擬器（Simulator for Phototypical Embodied AI Research）來解決這些限制。SPEAR 的核心是一個 Python 函式庫（Python library），可透過模組化外掛架構（modular plugin architecture）連接並以程式化方式控制任何 Unreal Engine（UE）應用程式。SPEAR 將超過 14K 個相異的 UE 函數（UE function）暴露給 Python，使可程式化功能（programmable functionality）較現有基於 UE 的模擬器提升了一個數量級（order-of-magnitude）。此外，單一 SPEAR 執行個體能夠以每秒 73 幀（frames per second, FPS）的速度，將 1920×1080 的照片級真實美術影像（beauty image）直接渲染到使用者的 NumPy 陣列（NumPy array）中——比現有的 UE 外掛程式（plugin）快了一個數量級——同時還提供任何現有基於 UE 的模擬器所不具備的真實值影像模態（ground truth image modality），例如非漫射本徵影像分解（non-diffuse intrinsic image decomposition）、材質識別碼（material ID）與物理基礎著色參數（physically based shading parameter）。最後，SPEAR 引入了一個表達力豐富的高階程式設計模型（high-level programming model），讓使用者能夠指定工作項目（work item）之間具有任意資料相依性（data dependency）的複雜 UE 工作圖（complex graph of UE work），並在單一 UE 幀（single UE frame）內確定性執行（deterministic execution）這些工作圖。我們透過一系列多元的範例應用展示 SPEAR 的實用性：在多個真實場景 UE 專案（in-the-wild UE project）中控制具有不同動作空間（action space）的多個具身智慧體（例如人類角色（human character）、汽車（car）與機器人）；渲染照片級真實的城市規模環境（city-scale environment）；操控 UE 的程序化內容生成系統（procedural content generation system）；渲染細緻人臉（human face）的同步多視角影像（multi-view image）；與 MuJoCo 物理模擬器（MuJoCo physics simulator）協調互動式的協同模擬（co-simulation）；以及透過 AI 程式設計助理（AI coding assistant）以自然語言（natural language）進行場景編輯（scene editing）。

### 核心貢獻（3～5點）
- 提出 SPEAR，一個以 Python 函式庫為核心、透過模組化外掛架構控制任意 UE 應用程式的照片級真實具身人工智慧研究模擬器，大幅提升可程式化功能與通用性。
- 實現高效率渲染：單一執行個體可於 73 FPS 將 1920×1080 美術影像直接輸出至 NumPy 陣列，並提供多種現有 UE 模擬器缺乏的真實值影像模態。
- 引入高階程式設計模型，支援具任意資料相依性的複雜 UE 工作圖，並能在單一 UE 幀內完成確定性執行。
- 展示多元應用，包括多種具身智慧體控制、城市規模環境渲染、程序化內容生成、人臉多視角同步、MuJoCo 協同模擬，以及自然語言場景編輯。

### 適合對象
從事具身人工智慧、電腦視覺、機器人學、強化學習與模擬器開發的研究人員與工程師，特別是需要照片級真實合成資料、高自由度 UE 程式控制，以及跨物理引擎協同模擬的進階使用者。

## 深度分析

#### 方法論解析

SPEAR 的核心方法論可以概括為「直接綁定 Unreal Engine（UE，虛幻引擎）的執行期反射系統（runtime reflection system），而非手工包裝有限函數」。具體而言，SPEAR 由三個層次組成：底層的 C++ 外掛程式（plugin）與 UE 反射系統互動、中間層的 Python 函式庫（Python library）提供原生 Python 呼叫體驗、以及高階程式設計模型（high-level programming model）讓使用者以非同步、零複製（zero-copy）的方式編排複雜 UE 工作圖（complex graph of UE work）。

**1. 反射式 UE 控制介面**
傳統 UE 模擬器通常針對特定任務手工撰寫數百個 Python 介面（Python interface）函數，導致可程式化功能（programmable functionality）受限。SPEAR 則透過 C++ 外掛直接操作 UE 的反射系統，讓 Python 端能夠在執行期以字串為鍵來尋找類別（class）、呼叫函數（function）、讀寫物件變數（variable）。這種設計使 SPEAR 能夠暴露超過 14,000 個不重複的 UE 函數（UE function），涵蓋場景編輯（scene editing）、程序化內容生成系統（procedural content generation system）、材質與燈光、動畫藍圖等幾乎所有 UE 子系統，而程式碼規模卻維持在相對精簡的水準。

**2. Python 原生語義與非同步呼叫**
SPEAR 的高階程式設計模型讓使用者可以像呼叫原生 Python 函數一樣呼叫 UE 函數，並自動處理型別轉換。每個函數都提供同步與非同步（asynchronous）兩種版本：同步版本會等待 UE 執行完畢並回傳結果；非同步版本則回傳 future 物件，讓使用者在 UE 仍在運算時繼續執行 Python 程式，最後再統一取得結果。這對於需要連續發出多個渲染或物理查詢的具身人工智慧（embodied AI）訓練流程特別重要，可顯著攤平通訊延遲。

**3. 零複製 NumPy 陣列（NumPy array）傳輸**
現有 UE 外掛在將高解析度影像傳回 Python 時，常因多次記憶體複製與序列化而造成 20–35 倍的通訊開銷（communication overhead）。SPEAR 實作了共享記憶體機制，讓 UE 渲染的影像可以直接寫入使用者的 NumPy 陣列，無需額外複製。這是 SPEAR 能夠以 73 每秒幀數（frames per second，FPS）將 1920×1080 照片級真實（photorealistic）美術影像（beauty image）直接渲染到 NumPy 陣列的關鍵。

**4. 確定性工作圖執行**
SPEAR 允許使用者定義任意資料相依性（data dependency）的 UE 工作圖，並保證在單一 UE 幀（single UE frame）內確定性執行（deterministic execution）。這對於需要同步多視角影像（multi-view image）、協同模擬（co-simulation）或複雜感測器融合的實驗至關重要，因為它避免了傳統「發送命令→等待幀結束→再發送命令」所帶來的非確定性與效能損失。

**5. 模組化外掛架構（modular plugin architecture）**
不同於許多現有 UE 模擬器以單體式應用程式（monolithic application）或客製化分支（custom fork）形式發布，SPEAR 是一組可插入任何現有 UE 專案的模組化外掛。這意味著研究者可以將 SPEAR 掛載到未經修改的 Epic Games 範例專案（in-the-wild UE project），例如 CitySample、StackOBot、CropoutSample、GameAnimationSample，而無需維護自己的 UE 分支，也更容易整合第三方資產。

**6. 可客製化相機感測器**
SPEAR 提供一個可客製化相機感測器，除了美術影像外，還能輸出多種真實值影像模態（ground truth image modality），包括深度（depths）、表面法向量（surface normals）、實例與語義識別碼（instance and semantic IDs）、非漫射本徵影像分解（non-diffuse intrinsic image decomposition）、材質識別碼（material ID）與物理基礎著色參數（physically based shading parameter）。這些模態對應 Hypersim 資料集的格式，使 SPEAR 成為生成照片級真實合成資料集（photorealistic synthetic dataset）的強大工具。

#### 實驗數據解讀

論文透過兩大類實驗驗證 SPEAR：量化效能比較與多樣化應用展示。

**1. 可程式化功能與程式碼規模**
SPEAR 暴露超過 14,000 個不重複 UE 函數，相較於現有 UE 模擬器僅數百個函數，達到數量級（order-of-magnitude）的提升。同時，由於採用反射系統而非手工包裝，其程式碼規模相對精簡（論文以 Table 1 比較，雖然確切行數未在提供的上下文中列出，但強調「modest code footprint」）。這說明方法論在「功能覆蓋率」與「維護成本」之間取得了良好權衡：功能越多，通常需要越多包裝程式碼，但 SPEAR 透過反射機制將新增功能自動化。

**2. 渲染與傳輸效能**
在 1920×1080 解析度下，SPEAR 能將美術影像直接渲染到 NumPy 陣列並達到 73 FPS，比現有 UE 外掛快一個數量級。這個數字應從三個層面解讀：
- **絕對速度**：73 FPS 已接近或超過許多即時渲染（real-time rendering）應用的需求，足以支援強化學習（reinforcement learning）與感覺運動控制（sensorimotor control）等需要高頻互動的任務。
- **相對提升**：論文指出現有 UE 外掛在相同解析度下回傳影像到 Python 的速度，比獨立式 UE 應用程式（standalone UE application）直接渲染到視埠（viewport）慢 20–35 倍。SPEAR 將此差距縮小到可忽略的程度，意味著效能瓶頸從「Python-UE 通訊」轉移回「GPU 渲染本身」。
- **零複製的貢獻**：高效能不僅來自非同步呼叫，更來自共享記憶體設計。對於需要同時輸出多種真實值影像模態的應用，零複製能避免每種模態都產生一次昂貴的記憶體複製。

**3. 應用展示**
論文展示了六類應用，涵蓋不同動作空間（action space）的具身智慧體（embodied agent）：
- **人類角色（human character）與汽車（car）** 在 CitySample 城市規模環境（city-scale environment）中運行；
- **飛行機器人（flying robot）** 在 StackOBot 專案中控制；
- **資源收集遊戲（resource collecting game）** CropoutSample 中的多個代理；
- **跑酷技能（parkour skill）人類與四足機器人（quadruped robot）** 在 GameAnimationSample 中控制；
- 與 MuJoCo 物理模擬器（MuJoCo physics simulator）進行互動式協同模擬（co-simulation）；
- 透過 AI 程式設計助理（AI coding assistant）以自然語言（natural language）編輯場景。

這些展示的共同意義在於：SPEAR 並非針對單一任務設計，而是一個通用平台。它能夠控制多種不同動作空間的代理、操作 UE 的程序化內容生成系統、渲染同步多視角人臉影像，並與外部物理引擎整合。這驗證了「反射式通用介面」確實能轉化為實際研究生產力。

#### 與現有研究的比較

**1. 相較於其他 UE 模擬器**
現有 UE 模擬器如 AI2-THOR、UnrealCV、Habitat-Sim（雖然 Habitat 主要使用其他引擎，但也有 UE 版本相關工作）等，通常提供數百個手工設計的 Python 函數。這些介面雖然對特定任務（例如導航、物體操作）足夠，但難以擴展到城市規模環境、車輛模擬或程序化內容生成。SPEAR 透過反射系統將可程式化功能提升一個數量級，並以模組化外掛形式存在，無需客製化 UE 分支。

**2. 相較於 Unity / Panda3D / IsaacSim**
Unity 與 Panda3D 也常被用於具身人工智慧研究，但它們的渲染品質與商業級資產生態通常不及 UE。IsaacSim 雖然在物理模擬與機器人領域表現優異，但屬於封閉源碼商業平台，整合第三方資產與自訂渲染管線的彈性較低。SPEAR 選擇完全開放原始碼（open-source）的 UE，並保留其商業遊戲開發（commercial game development）等級的渲染能力，對於需要照片級真實合成資料集的研究特別有利。

**3. 相較於傳統合成資料生成工具**
Hypersim 等資料集雖然提供高品質真實值影像模態，但通常是離線渲染、難以互動。SPEAR 不僅能渲染 Hypersim 所包含的深度、法向量、實例/語義 ID、非漫射本徵影像分解等模態，還額外提供材質識別碼與物理基礎著色參數，並且以互動式模擬器（interactive simulator）的形式運行。這讓 SPEAR 同時具備「資料生成」與「代理訓練」兩種能力。

**4. 主要改進**
- **功能覆蓋**：14K+ UE 函數 vs. 數百個手工函數。
- **傳輸效率**：零複製 NumPy 傳輸，73 FPS @ 1080p。
- **整合彈性**：模組化外掛，可掛載到任何 UE 專案。
- **確定性執行**：支援單一 UE 幀內的複雜工作圖。
- **真實值模態**：提供現有 UE 模擬器不支援的材質與著色參數。

**5. 限制**
- **學習曲線**：由於暴露大量 UE 底層功能，使用者需要熟悉 UE 的類別與反射命名規則，對非 UE 使用者門檻較高。
- **效能依賴硬體**：73 FPS 的數據應是在高階 GPU 上測得，論文未在提供的片段中詳細說明硬體配置，低階硬體可能無法複製相同效能。
- **物理模擬仍以 UE 為主**：雖然可與 MuJoCo 協同模擬，但原生物理功能仍受限於 UE 的 PhysX/Chaos，對於需要高精度接觸模擬的靈巧操作（dexterous manipulation）可能仍需額外整合。
- **反射系統的邊界**：並非所有 UE 函數都對反射可見，某些底層引擎功能或第三方外掛可能仍需手工包裝。

#### 可重現性評估

**1. 程式碼與資源可用性**
SPEAR 作為一個模組化外掛與 Python 函式庫，理論上應以開放原始碼形式釋出，因為論文強調其基於完全開放原始碼的 UE，並且未使用客製化 UE 分支。然而，根據提供的上下文，並未明確給出 GitHub 儲存庫網址或釋出版本號。若原始碼確實公開，則可重現性極高：研究者只需安裝 UE、編譯 C++ 外掛、安裝 Python 套件，即可在 Epic Games 範例專案上執行。

**2. 資料集與模型權重**
SPEAR 本身並非訓練模型，因此不涉及模型權重（model weights）。它生成的是合成視覺資料（synthetic visual data），資料集可由使用者自行產生。論文提到其相機感測器可輸出與 Hypersim 相容的模態，因此若未來釋出預設場景與相機配置，將有助於產生可重複的基準資料集。

**3. 環境相依性**
- **UE 版本**：SPEAR 需要特定 UE 版本，若 UE 大版本更新導致反射 API 變動，可能需要維護。
- **作業系統**：UE 主要支援 Windows 與 Linux，macOS 支援有限，這會影響部分使用者的可重現性。
- **硬體需求**：照片級真實渲染需要高效能 GPU，且城市規模環境（如 CitySample）對記憶體與顯存需求極高。

**4. 文件與範例**
論文展示了多個範例應用，若能提供對應的 Python 腳本與設定檔（如圖 3 所示的 `config.yaml`），將大幅降低重現門檻。目前從片段可見 SPEAR 使用 YAML 配置與簡潔 Python API，這對可重現性是正面訊號。

**5. 綜合評估**
假設原始碼完整釋出，SPEAR 的可重現性屬於「中高」：核心技術（反射綁定、零複製傳輸）可在標準 UE 上重現；但部分展示（如 CitySample、人臉多視角渲染）依賴大型商業範例專案與高階硬體，可能無法被所有研究團隊輕易複製。

#### 未來研究方向

**1. 擴大反射覆蓋與自動化包裝**
未來可進一步減少對手工包裝的依賴，例如自動處理非反射可見的底層 API、支援 Blueprint 節點的動態發現、以及提供更完整的型別推論與錯誤提示，降低非 UE 專家使用者的門檻。

**2. 多 GPU 與分散式渲染**
目前 SPEAR 的效能數據集中在單一實例。對於城市規模環境與大規模強化學習訓練，未來可發展多 GPU 平行渲染、多程序環境批次（vectorized environments）與雲端分散式協同模擬，以進一步提升資料吞吐量。

**3. 與更多物理引擎整合**
雖然已展示與 MuJoCo 的協同模擬，但未來可深化與其他物理模擬器（如 Isaac Gym、Bullet、Drake）的整合，特別是針對靈巧操作與四足運動（quadruped locomotion）等需要高精度接觸動力學的任務。

**4. 標準化基準與資料集**
SPEAR 可成為新一代具身人工智慧基準平台。未來研究方向包括建立標準化的導航、操作、自動駕駛（autonomous driving）任務套件，並釋出對應的照片級真實合成資料集，供基礎模型（foundation model）訓練與評估使用。

**5. 與大型語言模型（LLM）代理結合**
論文已展示透過 AI 程式設計助理以自然語言編輯場景。未來可將此擴展為「語言驅動的具身智慧體」，讓 LLM 直接產生 SPEAR 控制程式碼，進行場景理解、任務規劃與程式化內容生成，推動可控式影片合成（controllable video synthesis）與互動式模擬的結合。

**6. 動態全域光照與神經渲染整合**
UE 的 Lumen、Nanite 等技術已提供高品質動態光照。未來可將 SPEAR 與神經輻射場（NeRF）、3D Gaussian Splatting 等神經渲染技術結合，支援三維與四維重建（3D and 4D reconstruction）、新視角合成與動態場景編輯。

**7. 領域隨機化（Domain Randomization）與 Sim-to-Real**
SPEAR 能夠程式化控制材質、燈光、相機參數與場景佈局，非常適合進行大規模領域隨機化。未來可發展自動化的隨機化管線，並驗證其在深度估計（depth estimation）、分割（segmentation）、機器人控制等任務上的 Sim-to-Real 遷移效果。

**8. ROS / 機器人中介軟體整合**
為了讓 SPEAR 更貼近真實機器人研究，未來可提供 ROS2 橋接器，讓 SPEAR 作為高保真模擬後端，與真實機器人軟體堆疊無縫整合。

## 論文問答

**Q1：SPEAR 主要想解決什麼問題？**

A：SPEAR 旨在解決現有照片級真實互動式模擬器在通用性、可程式化能力與渲染速度上的不足。具體而言，現有基於 Unreal Engine（UE）的模擬器通常只提供數百個手工包裝的 Python 函數，無法充分發揮 UE 強大的即時渲染與程序化內容生成能力。SPEAR 透過模組化外掛架構與直接操作 UE 執行期反射系統，讓研究者能以 Python 動態呼叫超過一萬四千個 UE 函數，並以每秒 73 幀的速度將 1920×1080 的照片級真實美術影像直接渲染到 NumPy 陣列中，大幅提升具身人工智慧研究的開發效率與資料品質。

**Q2：為什麼現有的 UE 模擬器無法滿足研究需求？**

A：現有 UE 模擬器主要有三項限制。第一，它們的 Python 介面通常是手工打造且功能有限，僅包含數百個函數，無法涵蓋 UE 龐大的原生功能。第二，這些模擬器在將高解析度影像等大量資料傳回 Python 時會產生嚴重的通訊開銷，例如回傳一張 1920×1080 影像可能比 UE 獨立應用程式直接渲染到視埠慢 20 到 35 倍。第三，多數模擬器以單體式應用程式或需要客製化 UE 分支的形式發布，難以整合到現有專案或引入第三方資產，限制了它們在真實場景 UE 專案中的可用性。

**Q3：照片級真實的具身人工智慧模擬器為何重要？**

**Q4：SPEAR 的核心技術方法是什麼？**

A：SPEAR 的核心技術洞察是直接透過全面的 C++ 介面與 UE 的執行期反射系統互動，使 Python 函式庫能夠在執行期以字串為鍵來動態尋找類別、呼叫函數與操作物件變數。這種方法無需為每個類別、函數或變數撰寫手工包裝程式碼，因此能在維持精簡程式碼量的同時，暴露超過 14,000 個獨特的 UE 函數。在此低階反射介面之上，SPEAR 進一步提供高階程式設計模型，讓使用者可以像呼叫原生 Python 函數一樣呼叫任何對反射系統可見的 UE 函數，並支援非同步變體與零複製的 NumPy 陣列傳輸。

**Q5：SPEAR 相較於現有模擬器的關鍵創新有哪些？**

   將 SPEAR 與 MuJoCo 物理模擬器進行互動式協同模擬，結合 AI 程式設計助理（如大型語言模型）以自然語言驅動 UE 場景編輯與程序化內容生成，加速原型設計與內容製作流程。

- **資料與資產**：取得 Unreal Engine 5.x 專案（建議使用 Epic Games 範例專案，如 CitySample、StackOBot、CropoutSample、GameAnimationSample），並確認資產授權允許研究與商業用途；準備場景、角色、材質與動作資源。
- **運算資源**：建議配備 NVIDIA RTX 30/40 系列以上 GPU、32 GB 以上系統記憶體、SSD 儲存空間（UE 專案與編譯結果通常數十 GB），以及支援 DirectX 12 的作業系統（Windows 為主，Linux 需額外驗證）。
- **軟體環境**：安裝 Unreal Engine 5.x、Visual Studio 2022 或對應 C++ 編譯工具、Python 3.8+、NumPy，並能編譯 UE C++ 外掛程式。
- **技能需求**：熟悉 Python 與 NumPy；具備 UE Blueprint 或 C++ 基礎以便理解反射系統與自訂函式庫；若需整合機器人流程，建議了解 ROS2、OpenAI Gymnasium 或強化學習框架。

## 實作步驟建議

1. **安裝與編譯 SPEAR 外掛**  
   將 SPEAR 以模組化外掛形式加入目標 UE 專案，編譯專案並確認 Python 函式庫可透過 `spear` 套件連線到獨立式 UE 應用程式。

2. **設定場景與感測器**  
   在 UE 編輯器中配置相機感測器、代理生成點與所需真實值渲染目標（深度、法向量、語義 ID、材質識別碼等），並在 `config.yaml` 中指定解析度與幀率。

3. **編寫 Python 控制程式**  
   使用 SPEAR 的高階程式設計模型，以原生 Python 函式呼叫方式操作 UE 物件；對於高頻影像傳輸，使用非同步變體與 NumPy 零拷貝機制，避免通訊開銷成為瓶頸。

4. **定義任務圖與確定性執行**  
   針對需要多步驟相依的場景（例如先移動相機、再取得深度、再觸發物理事件），建立複雜 UE 工作圖，並在單一 UE 幀內確定性執行，保證實驗可重現。

5. **資料生成或策略訓練**  
   將渲染結果直接寫入 HDF5、TFRecord 或 LMDB 等資料管線，或串接 PyTorch/TensorFlow 進行線上強化學習；定期驗證真實值與美術影像的時間同步性。

6. **部署與迭代**  
   在模擬中完成驗證後，可將策略遷移至真實機器人，或將合成資料與真實資料混合訓練；持續監控幀率與記憶體使用，必要時調整渲染品質與非同步粒度。

## 潛在風險與注意事項

- **效能與記憶體瓶頸**：雖然 SPEAR 可達 73 FPS（1920×1080），但城市規模場景、多相機同步或高解析度真實值輸出會快速消耗 GPU 記憶體與頻寬，建議逐步增加負載並監控 `nvidia-smi`。
- **UE 版本與外掛相容性**：SPEAR 依賴 UE 執行期反射系統，不同 UE 版本或自訂引擎分支可能導致編譯失敗或函數暴露不一致，應鎖定官方支援版本並避免使用過度修改的客製化分支。
- **反射系統的覆蓋限制**：並非所有 UE 函數都對反射可見，部分底層渲染或第三方 C++ 函式庫可能需要額外標記 `UFUNCTION()`/`UPROPERTY()` 或撰寫輕量包裝器。
- **確定性與可重現性**：雖然 SPEAR 支援單一 UE 幀內確定性執行，但物理模擬、隨機種子、非同步網路事件仍可能引入變異，建議固定種子並在相同硬體與驅動版本下執行。
- **資產授權與法規**：Epic Games 範例專案與 Marketplace 資產通常僅限 UE 相關用途，商業應用前需確認授權條款；生成的人臉或城市資料亦需注意隱私與肖像權議題。

## 與其他技術的整合建議

- **機器人作業系統（ROS2）**：可將 SPEAR 的觀測（影像、點雲、里程計）透過 ROS2 topic 發布，並將控制指令訂閱回 SPEAR，形成模擬到真實（sim-to-real）的橋接。
- **強化學習框架**：包裝 SPEAR 環境為 OpenAI Gymnasium 介面，搭配 Stable-Baselines3、RLlib 或自訂分散式訓練管線，利用非同步 API 提升取樣效率。
- **物理模擬器協同**：透過 SPEAR 的反射介面讀取/寫入物件姿態，與 MuJoCo 進行互動式協同模擬，讓 UE 負責視覺渲染、MuJoCo 負責高精度物理。
- **資料管線與基礎模型訓練**：將 SPEAR 輸出的美術影像與真實值直接匯入 HDF5、WebDataset 或雲端儲存，供大型視覺基礎模型、3D/4D 重建模型進行預訓練。
- **AI 程式設計助理**：串接 LLM API（如 OpenAI、Claude），讓產品或設計師以自然語言描述場景修改，再由 LLM 生成 SPEAR Python 腳本呼叫 UE 函數，實現自然語言場景編輯。

## 給不同背景讀者的閱讀建議

- **初學者**：建議從 SPEAR 官方範例與 Python API 文件開始，先學會如何啟動 UE 專案、生成簡單物件與取得相機影像，暫時不需要深入 C++ 反射系統；重點理解「SPEAR 把 UE 當成可程式化的照片級真實世界」這個核心概念。

- **AI 工程師**：請聚焦於高階程式設計模型、非同步變體與 NumPy 零拷貝機制，這些是將 SPEAR 從「能動」推到「能規模化訓練」的關鍵；同時留意感測器管線、幀率穩定性，以及如何將 SPEAR 包裝成 Gymnasium 環境。

- **研究人員**：建議深入閱讀 SPEAR 如何利用 UE 執行期反射系統暴露 14K 以上函數，以及真實值影像模態（非漫射本徵影像分解、材質識別碼、物理基礎著色參數）的技術細節；這些是設計新實驗、產生新資料集時最重要的貢獻。

- **產品經理**：請優先評估適用場景、授權成本與運算開支，並理解 SPEAR 相較於單體式模擬器的整合彈性；重點關注它能串接現有 UE 資產、支援多種具身智慧體與真實值輸出，這些特性對縮短資料生成與原型驗證週期具有明確商業價值。
