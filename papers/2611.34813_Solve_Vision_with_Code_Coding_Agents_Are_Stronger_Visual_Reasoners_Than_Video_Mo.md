# 以程式碼解決視覺：程式碼代理是比影片模型更強的視覺推理器

**原文標題：** Solve Vision with Code: Coding Agents Are Stronger Visual Reasoners Than Video Models  
**作者：** Dezhi Luo、Fengyuan Yu、Haotian Zhang 等 14 位作者  
**發布日期：** 2026-11-25

## ⚡ TL;DR

本研究探討影片生成模型是否優於程式碼代理作為視覺推理器。
讓程式碼代理接收首幀與提示，撰寫程式渲染答案影片進行評估。
結果顯示閉源代理得分達0.923，遠超最佳影片模型的0.670。

## 摘要翻譯

影片生成模型（Video generation model）越來越多地被評估為視覺推理器（Visual reasoner）：給定第一幀（First frame）和自然語言提示（Natural-language prompt），模型能否產生執行指定任務的影片？此範式被認為具有優勢，因為推理原生於視覺媒介（Visual medium），直接在幀中展開，而非透過語言或程式碼。然而，此原生路徑（Native route）是否實際上是視覺推理（Visual reasoning）更可靠的路徑，尚未在相同條件下與符號式替代方案（Symbolic alternative）進行測試。因此，我們將相同的任務，以相同的輸入、輸出規格和評估器，提交給兩種媒介：程式碼代理（Coding agent）並非進行像素去噪（Denoising pixels），而是撰寫程式來渲染答案影片，並由未修改的基於規則的評估器（Rule-based evaluator）進行評分。在 VBVR-Pro-Bench（Xu 等人，2026）上，這是一個包含 500 個任務實例、涵蓋五個認知類別（Cognitive categories）並擁有符號式標準答案（Symbolic ground truth）的套件，代理接收與影片模型相同的第一幀和提示，無法存取標準答案、元資料或生成模型，且每實例單次嘗試（One attempt per instance）。三個閉源模型代理（Closed-model agent，分別為 Codex 搭配 gpt-6-astra、Claude Code 搭配 Fable 5.1，以及 Gemini CLI 搭配 Gemini 3.1 Pro）得分分別為 0.923、0.894 和 0.893，每個都高出最佳影片模型（Best video model）0.22 以上。在 23 個可執行的開源權重模型（Open-weight model）中，表現最佳的 GLM-5 達到 0.572，高於除強化學習訓練模型（RL-trained model）外的所有影片模型。綜合而言，我們證明對於可從第一幀和提示計算出解答的任務，程式合成（Program synthesis）目前是比影片生成更實質可靠的視覺推理路線。我們進一步區分描繪式程式（Depictive program，其在影像中導航以還原可遷移方案（Transferable scheme））與命題式程式（Propositional program，其操作硬編碼值（Hard-coded value）），揭示視覺推理如何在代理撰寫的程式中展開，以及這對一般性推理（Reasoning in general）的本質所帶來的意涵。

### 核心貢獻（3～5點）
- **首次系統性對比兩種視覺推理範式**：在完全相同的輸入、輸出規格與評估器條件下，直接比較原生視覺推理（影片生成）與符號替代方案（程式合成路線），填補了該領域缺乏受控實證比較的空白。
- **提出「以程式碼解決視覺」範式**：證明程式碼代理透過撰寫程式並委派渲染（Delegate rendering）給標準 Python 影像函式庫，能在視覺推理任務上大幅超越影片模型，顛覆「推理必須原生於視覺媒介」的既有假設。
- **建立 VBVR-Pro-Bench 基準測試的全面評估**：在涵蓋五個認知類別（抽象、感知、空間性、轉換、知識）、共 500 個任務實例的套件上，評估三個閉源模型程式碼代理與 23 個開放權重模型，並與影片模型進行基準對照。
- **揭示代理程式中的推理結構**：區分描繪式程式（Depictive program，導航影像以還原可遷移機制）與命題式程式（Propositional program，操作硬編碼值），為理解視覺推理在程式合成中的展開方式提供新視角。
- **對一般性推理本質的理論意涵**：透過分析代理撰寫的程式如何從影像中提取函數，明確陳述程式合成路徑對推理本質（Nature of reasoning）的啟示，超越單純的基準測試結果。

### 適合對象
- 從事**多模態推理**與**視覺語言模型**研究的研究者，特別關注影片生成模型作為通用推理器的潛力與局限。
- **程式合成（Program synthesis）** 與**神經符號 AI** 領域的學者，探索以程式碼取代端對端生成的可能性。
- **AI 基準測試設計者**，對具備可驗證獎勵（Verifiable reward）與符號式標準答案的程序化生成任務感興趣者。
- **大型語言模型代理（LLM Agent）** 的開發者與實務工程師，特別是閉源模型程式碼代理（Closed-model coding agent）與開源權重模型（Open-weight model）的應用者。
- 對**推理本質**與**認知類別**（抽象、感知、空間性、轉換、知識）有理論興趣的 AI 哲學與認知科學研究者。

## 深度分析

#### 方法論解析

本論文提出一個核心方法論主張：對於可從第一幀與提示詞確定性計算出解答的視覺任務，**程式合成路徑（program-synthesis route）** 比 **原生影片生成路徑（native route）** 更可靠。方法論的核心設計在於「**受控的媒介變更（controlled change of medium）**」——即在保持所有其他評估條件不變的前提下，僅替換答案的呈現媒介。

**評估協議設計的嚴謹性**

作者設計了一個極為乾淨的對照實驗：

1. **輸入對等性**：程式碼代理接收與影片模型完全相同的第一幀（first frame）與自然語言提示詞（natural-language prompt），以及相同的容器規格（container specification），包含幀大小（frame size）、幀率（frame rate）、幀數（frame count）與時長（duration）。

2. **輸出對等性**：代理必須撰寫程式來渲染（rendering）答案影片，輸出由**未修改的官方評估器（unmodified evaluator）** 評分，與影片模型使用相同的基於規則的評估器（rule-based evaluator）。

3. **資訊隔離**：代理無權存取符號式標準答案（symbolic ground truth）、任務生成器（task generator）或任務元資料（task metadata），亦不得呼叫影像或影片生成模型。

4. **資源限制**：CPU 沙盒（CPU sandbox）環境、標準 Python 影像函式庫、30 分鐘牆鐘時間預算（wall-clock budget）、每實例單次嘗試（one attempt per instance）。

**沙盒與代理配置**

每個實例在全新的容器中執行，僅包含輸入與由執行框架（harness）產生的任務陳述。任務陳述結構對所有代理與實例一致，僅實例特定的輸出格式不同。代理以非特權使用者身分執行，網路存取僅限於模型 API 呼叫與套件安裝。透過事件日誌稽核確認無生成式模型被呼叫。

**代理選擇**

採用三款現成命令列程式碼工具：Codex（搭配 gpt-6-astra）、Claude Code（搭配 Fable 5.1）與 Gemini CLI（搭配 Gemini 3.1 Pro），皆以官方非互動模式執行，預設設定，不加入任何系統提示詞或技能修改。透過 OpenCode 框架評測 23 個可執行的開源權重模型（open-weight model）。

**程式分類法**

作者提出一個重要的分析框架，將代理撰寫的程式（agent-written program）區分為兩類：

- **描繪式程式（depictive program）**：通用程式，在執行時導航影像以還原可遷移方案（transferable scheme），可應用於同一任務族系（task family）的不同實例。
- **命題式程式（propositional program）**：將代理在工作階段中推導出的答案編碼為符號常數（hard-coded value），僅負責渲染，無法將解決能力遷移至其他實例。

此分類揭示了視覺推理在代理程式中的展開方式，並對推理的本質（nature of reasoning）提出啟示。

#### 實驗數據解讀

**主要效能結果**

在 VBVR-Pro-Bench 的 500 個實例上，三個閉源模型代理（closed-model coding agent）分別達到 **0.923、0.894 與 0.893** 的分數，皆領先最佳影片模型超過 0.22 分。最佳影片模型為經強化學習訓練（RL-trained）的版本，以評估器作為可驗證獎勵（verifiable reward），得分為 **0.670**。

在開源權重模型中，表現最佳的 **GLM-5** 達到 **0.572**，超越除 RL 訓練版本外的所有影片模型。DeepSeek R1 因不支援 Amazon Bedrock 上的工具呼叫而被排除。

**類別層級分析**

代理在五個認知類別（cognitive category）——抽象（abstraction）、感知（perception）、空間性（spatiality）、轉換（transformation）與知識（knowledge）——皆領先影片模型。值得注意的是，描繪式程式的比例在感知與轉換任務中最高，而命題式程式的比例在抽象與知識任務中最高，但兩種模式皆無法預測效能。

**效率分析**

作者將失敗區分為**交付失敗（delivery failure）** 與**內容失敗（content failure）**：

- 開源權重模型的低分主要由交付失敗驅動：模型從未呼叫工具、在執行程式碼前停止，或耗盡時間預算而僅交付少數影片。
- 除交付影片所需的最少工具呼叫外，工具呼叫數量本身並不預測分數。
- 三個閉源代理的分數跨度僅 0.030，但成本差距接近一個數量級，顯示**成本效益的顯著差異**。

**程式策略分析**

在 1,385 個閉源代理解決自身實例的程式中，描繪式與命題式程式的平衡隨任務類別而變化。這項分析揭示了代理如何在不同認知需求下採用不同的解決策略：對於需要從影像中提取結構的任務（感知、轉換），代理傾向撰寫通用、可重用的程式；對於需要特定知識或抽象推理的任務，代理傾向將推導結果硬編碼。

#### 與現有研究的比較

**定位**

本論文將**程式合成路徑（program-synthesis route）** 實例化於一個專為影片模型設計的基準測試上，並以其評估標準進行評測。相關工作包括 Gao 等人（2023）、Chen 等人（2023）、Surís 等人（2023）以及 Gupta 與 Kembhavi（2023）的研究，但這些工作多在不同的視覺推理基準上進行，未與影片模型在完全對等的條件下對照。

**相較於影片生成範式的改進**

1. **效能大幅提升**：閉源代理比最佳影片模型高出 0.22 分以上，這在基準測試中屬於巨大差距。
2. **可解釋性**：代理的程式碼提供透明的推理軌跡，而影片模型的內部去噪過程（denoising pixels）為黑盒。
3. **效率**：程式碼代理在 CPU 環境中執行，無需昂貴的 GPU 推論。

**限制與侷限性**

1. **任務範圍限制**：本方法僅適用於「解答可從第一幀與提示詞確定性計算」的任務。對於需要真實世界物理模擬、複雜場景理解或無法以程式表達的視覺現象，影片生成可能仍是唯一可行路徑。

2. **生成模型禁令**：代理被明確禁止呼叫影像或影片生成模型，這排除了混合方法的可能。實際應用中，結合程式合成與生成模型的混合架構可能更強大。

3. **基準測試偏誤**：VBVR-Pro-Bench 的任務為程序化生成（procedurally generated），其結構化特性可能有利於程式合成路徑。在更開放、更多樣化的視覺推理任務上，影片模型可能表現更佳。

4. **單次嘗試限制**：每實例僅一次嘗試，未考慮迭代改進的潛力。影片模型同樣僅一次嘗試，但程式碼代理的迭代能力可能未被充分利用。

5. **開源模型差距**：最佳開源模型 GLM-5（0.572）與閉源代理（最高 0.923）之間存在 0.35 分的巨大差距，顯示開源生態在程式碼代理能力上仍有顯著追趕空間。

6. **評估器依賴**：基於規則的評估器（rule-based evaluator）雖然提供客觀評分，但可能無法捕捉所有視覺推理的細微差異。

#### 可重現性評估

**程式碼與資料可用性**

論文提供了專屬網站 **SOLVE-VISION-WITH-CODE.COM**，暗示可能有相關資源釋出。然而，從全文脈絡判斷：

1. **基準測試**：VBVR-Pro-Bench 由 Xu 等人（2026）發布，屬於既有資源，本論文直接使用。

2. **評估管道**：作者聲明「所有結果皆由單一端到端管道產生」，但未明確說明該管道是否開源。

3. **代理程式**：1,385 個閉源代理解決實例的程式被分析與分類，但未明確說明是否公開。

4. **模型權重**：閉源模型（gpt-6-astra、Fable 5.1、Gemini 3.1 Pro）無權重可取得；開源模型透過 OpenCode 框架與 Amazon Bedrock 存取。

**可重現性挑戰**

1. **閉源模型不確定性**：閉源模型的版本與設定可能隨時間變化，導致結果難以精確重現。

2. **環境敏感性**：CPU 沙盒的具體配置、Python 版本、函式庫版本可能影響結果。

3. **評估器版本**：使用「未修改的官方評估器」，但官方評估器本身的版本演進可能影響分數。

4. **隨機性**：代理的單次嘗試可能受隨機因素影響，但作者未報告多次執行的標準差。

**整體評估**

可重現性處於中等水準。基準測試與評估器為公開資源，方法論描述詳盡，但完整的程式碼、管道與代理程式集合的釋出狀態尚不明確。建議作者明確釋出端到端管道與程式分類的標註資料，以促進後續研究的驗證與延伸。

#### 未來研究方向

**1. 混合架構探索**

結合程式合成與影片生成的混合方法值得深入研究。例如：代理可先撰寫程式骨架，再利用生成模型填補無法以程式表達的視覺細節；或代理可呼叫生成模型作為視覺感知工具，從影像中提取結構化資訊後再進行程式推理。

**2. 程式合成路徑的擴展**

將本方法應用於更複雜的視覺推理任務，例如：
- 需要多步驟物理模擬的任務
- 涉及真實世界場景理解的任務
- 需要常識知識整合的任務

**3. 描繪式與命題式程式的深入分析**

進一步研究兩種程式模式的觸發條件與轉換機制：
- 為何在感知與轉換任務中描繪式程式比例較高？
- 是否能設計提示詞或訓練方法，引導代理在更多任務上採用描繪式策略？
- 命題式程式是否反映代理在面對困難任務時的「退縮」行為？

**4. 開源模型的追趕**

GLM-5 與閉源代理之間的 0.35 分差距顯示開源生態的改進空間。未來工作可專注於：
- 針對程式碼代理的視覺推理微調
- 提升開源模型的工具呼叫可靠性
- 降低交付失敗率

**5. 成本效益最佳化**

三個閉源代理分數相近但成本差距一個數量級，提示未來研究應將**成本**納入視覺推理系統的評估指標。開發在效能與成本間取得最佳平衡的代理配置是重要方向。

**6. 推理本質的理論探討**

描繪式與命題式程式的區分為「推理的本質」提供了新的視角：
- 描繪式程式體現了「從特殊到一般」的歸納推理
- 命題式程式體現了「從一般到特殊」的演繹應用
- 兩者在不同認知類別中的分布差異，可能反映人類視覺推理的認知機制

**7. 評估器的改進**

雖然基於規則的評估器提供客觀性，但可能過於嚴格或過於寬鬆。未來可探索：
- 結合規則評估與神經評估的混合評估器
- 對推理過程（而非僅對輸出）的評估
- 對程式碼品質與可遷移性的元評估

**8. 安全性與可靠性**

程式碼代理在沙盒中執行，但生成的程式碼可能包含未預期的行為。未來應研究：
- 程式碼代理在視覺推理任務中的安全防護
- 對抗性輸入下的穩健性
- 錯誤程式的自動修復機制

**9. 跨模態遷移**

將程式合成路徑從影片推理遷移至其他視覺任務，例如：
- 靜態影像推理
- 3D 場景理解
- 互動式視覺環境（如遊戲、模擬器）

**10. 世界模型的新範式**

論文最後指出，這些結果「對世界模型中的視覺推理方法（無論是原生或透過程式碼）具有啟示」。未來可探索以程式碼為基礎的世界模型建構，其中視覺推理透過明確的程式合成而非隱式的像素生成來實現，這可能為人工通用智慧（AGI）中的視覺理解提供新路徑。

## 論文問答

**Q1：為什麼影片生成模型被視為視覺推理的潛在路徑？這種「原生視覺推理」範式的核心論點是什麼？**
A：影片生成模型之所以被視為視覺推理的潛在路徑，是因為它們能直接產出具有時間一致性的影片，被認為可以在「視覺媒介」中「原生」地展開推理過程，而無需透過語言或程式碼等中間符號層。這種範式的核心論點在於：當模型從第一幀與自然語言提示出發，透過像素去噪生成影片時，推理過程就直接內嵌於幀的演化之中，因此被視為更貼近人類視覺認知的「原生」形式。然而，這種論點預設了「在視覺媒介中展開」就等同於「更可靠」，但這個假設在本文之前從未與符號式替代方案在相同條件下進行過嚴格對比驗證。

**Q2：現有影片生成模型在視覺推理任務上的表現如何？它們面臨的根本困難是什麼？**
A：在 VBVR-Pro-Bench 上，即使是經過強化學習訓練、以基準測試評估器作為可驗證獎勵的最佳影片模型，也僅達到 0.670 的分數，距離基準測試上限仍有相當大的差距。這些模型面臨的根本困難在於：對於大多數 VBVR-Pro 任務，正確輸出其實是第一幀與提示的確定性函數，但影片模型必須在生成過程中以隱含方式「還原」這個函數，這對像素去噪機制而言極為困難。換言之，模型被迫在連續、高維的像素空間中學習離散、結構化的規則，而非以符號形式明確陳述解題邏輯，這正是其表現受限的結構性原因。

**Q3：為什麼作者認為需要將「程式合成」這條符號式替代路徑與原生影片生成進行受控比較？**
A：作者之所以強調「受控比較」，是因為過去影片模型與程式碼代理的比較往往在不同的輸入、輸出規格或評估器下進行，導致無法釐清表現差異究竟來自媒介本身的特性，還是來自評估條件的不一致。本文透過固定所有變因——相同的第一幀、相同的提示、相同的輸出容器規格、未修改的官方評估器——僅改變「答案的媒介」（從像素去噪改為程式合成），使兩者的比較成為真正的「受控媒介變更」實驗。這種設計使我們能夠隔離出「以程式碼明確陳述解題邏輯並委派渲染給直譯器」相較於「在像素空間隱含還原函數」的純粹優勢，從而對視覺推理的本質提出更精確的經驗性論斷。

**Q4：這篇論文的核心方法論是什麼？如何設計一個「受控的媒介變更」實驗？**
A：本文的核心方法論是「以程式碼代理取代影片模型，在完全相同的評估條件下回答 VBVR-Pro-Bench 的 500 個實例」。具體而言，每個程式碼代理接收與影片模型完全相同的第一幀、自然語言提示與容器規格（幀大小、幀率、幀數、時長），但其任務改為「撰寫一個能渲染出答案影片的程式」，並由未修改的官方評估器進行評分。這種設計的關鍵在於「控制變因」：禁止呼叫任何影像或影片生成模型、禁止存取標準答案或任務元資料、僅有一次嘗試機會、輸出未交付影片則計零分——這些規則與影片模型的評估規則完全對齊，確保了比較的公平性。

**Q5：程式碼代理在沙盒環境中的執行設定有哪些關鍵設計選擇？為何這些限制重要？**
A：沙盒環境的關鍵設計選擇包括：僅使用 CPU、預裝標準 Python 影像處理函式庫與字型、30 分鐘牆鐘時間預算、單次嘗試、禁止呼叫生成模型、僅允許變更提示所要求的內容、且動作必須在整個片段中展開。這些限制之所以重要，是因為它們確保了程式碼代理無法透過「走捷徑」來規避推理——例如禁止呼叫生成模型排除了「讓另一個模型代勞」的可能性，CPU 限制排除了依賴昂貴硬體的解法，而單次嘗試與時間預算則模擬了真實部署場景下的資源約束。此外，事件日誌與留存程式的稽核機制進一步保證了規則被確實遵守，使實驗結果具有可信度。

**Q6：「描繪式程式」與「命題式程式」的區分有何理論意義？這如何揭示視覺推理的本質？**
A：「描繪式程式」是代理在執行階段導航圖像以還原一個「可遷移方案」的通用程式，能應用於同一任務族系的不同實例；而「命題式程式」則將代理在工作階段中推導出的答案編碼為硬編碼的符號常數，僅渲染該特定實例，因此無法遷移。這種區分的理論意義在於：它揭示了「視覺推理」在程式碼代理中可能以兩種截然不同的方式實現——前者更接近「理解任務結構並推導通用解法」，後者則更接近「從圖像中抽取特定答案並寫死」。值得注意的是，這兩種模式的比例隨任務類別而異：感知與轉換任務中描繪式比例較高，而抽象與知識任務中命題式比例較高，但兩者皆無法單獨預測表現，顯示視覺推理的本質可能比單一模式更為多元。

**Q7：VBVR-Pro-Bench 的設計特點是什麼？為何它適合用來比較影片模型與程式碼代理？**
A：VBVR-Pro-Bench 是一個包含 500 個實例、橫跨 100 個任務族系的基準測試，每個族系有 5 個實例，並涵蓋抽象、感知、空間性、轉換、知識五個認知類別。其核心設計特點是「程序化生成任務」搭配「符號式標準答案」與「基於規則的評估器」，這意味著每個實例都有一個可由規則驗證的正確輸出，而非仰賴人類主觀判斷。這個基準之所以特別適合本文的比較，是因為它的任務結構允許「確定性函數」的存在——正確輸出可由第一幀與提示計算得出——這使得「以程式碼明確陳述該函數」成為一條可行的解題路徑，從而使影片模型與程式碼代理的對比具有實質意義。

**Q8：三個閉源模型代理與開源權重模型的具體表現如何？差距有多大？**
A：三個閉源模型代理——Codex（搭配 gpt-6-astra）、Claude Code（搭配 Fable 5.1）與 Gemini CLI（搭配 Gemini 3.1 Pro）——分別達到 0.923、0.894 與 0.893 的分數，皆領先最佳影片模型（0.670）超過 0.22。在 23 個可執行的開源權重模型中，表現最佳的 GLM-5 達到 0.572，超越了除強化學習訓練模型之外的所有影片模型。這個差距相當顯著：即使是表現最弱的閉源代理（0.893）也比最佳影片模型高出 0.223，而最佳閉源代理（0.923）則領先 0.253，顯示在這個基準上，程式合成路徑相較於原生影片生成具有壓倒性的可靠性優勢。

**Q9：不同認知類別（抽象、感知、空間性、轉換、知識）中，程式碼代理與影片模型的表現差異為何？**
A：根據本文的實驗結果，三個閉源模型代理在所有五個認知類別中皆領先影片模型，這意味著程式碼代理的優勢並非僅限於特定類型的任務，而是橫跨整個認知光譜都具有更可靠的表現。這種全面性的領先暗示：對於「可由第一幀與提示計算得出解的任務」，無論該任務涉及抽象規則推導、感知資訊抽取、空間關係操作、轉換程序執行或知識應用，符號式程式合成都比像素空間的隱含還原更為有效。這也意味著，影片模型在所有類別上的瓶頸並非源於特定能力（如空間推理或知識檢索）的不足，而是源於「在像素空間中學習確定性函數」這個根本性的表徵挑戰。

**Q10：這項研究對「世界模型」（world modeling）研究領域有何啟示？**
A：本文對世界模型研究的啟示在於：對於那些「解可由初始狀態與指令計算得出」的任務，程式合成可能比原生影片生成更接近可靠的「世界模型」建構路徑。傳統世界模型研究往往假設「在視覺媒介中模擬」是必要的，但本文顯示，當世界演化規則可被符號化時，透過程式碼明確陳述規則並委派渲染，能獲得遠高於像素模擬的可靠性。這促使研究者重新思考世界模型的定位：或許真正的「世界模型」不必是端到端的影片生成器，而可以是「能產出可執行程式以模擬世界演化」的系統，這為結合符號推理與視覺表徵的混合架構開啟了新方向。

**Q11：在實際產品應用中，程式碼代理相較於影片生成模型有哪些優勢與劣勢？**
A：程式碼代理在實際應用中的優勢包括：極高的可靠性（在結構化任務上分數遠超影片模型）、可解釋性（產出的是可讀程式而非黑箱像素）、可審查性（程式邏輯可被人工檢視與修改）、以及較低的硬體需求（CPU 沙盒即可執行）。然而，其劣勢同樣明顯：僅適用於「解可由初始狀態計算得出」的確定性任務，對於需要真實物理模擬、複雜流體動力學或無法符號化的視覺現象時，程式碼代理難以勝任；此外，撰寫程式所需的時間與 token 成本可能較高，且對於非結構化的創意內容生成，影片模型仍具優勢。因此，兩者更可能形成互補關係，而非完全替代。

**Q12：這項研究對 AI 推理研究的一般性啟示是什麼？「推理的本質」問題如何被重新框架？**
A：本文對 AI 推理研究的一般性啟示在於：「推理」未必需要在與輸入相同的表徵空間中進行——對於視覺輸入，推理可以透過符號程式碼在語言空間中完成，再將結果渲染回視覺空間。這重新框架了「推理的本質」問題：推理的關鍵不在於表徵媒介的同質性，而在於「能否明確陳述並執行解題所需的確定性函數」。當代理撰寫的程式碼能夠「導航圖像以還原可遷移方案」（描繪式）或「從圖像中抽取特定答案」（命題式）時，視覺推理便以這兩種模式在程式碼中展開，從而挑戰了「原生視覺推理必然優於符號式推理」的預設，並提示我們：未來的視覺推理系統或許應結合兩種路徑的優勢。

**Q13：這篇論文承認哪些研究限制？實驗設計有哪些需要謹慎解讀的地方？**
A：本文的研究限制主要在於：實驗僅在 VBVR-Pro-Bench 上進行，該基準的任務皆為「解可由第一幀與提示計算得出」的確定性函數，因此結論的適用範圍受限——對於需要真實物理模擬、開放式創造或無法符號化的視覺現象，程式碼代理的優勢未必成立。此外，影片模型的分數取自已發布的 VBVR-Pro 排行榜而未重新執行，這雖符合「受控比較」的精神（固定評估條件），但仍意味著影片模型的潛在進步未被納入。最後，閉源模型代理的具體運作機制（如內部提示工程、工具呼叫策略）並未完全公開，這使得結果的可重現性受限於商業產品的版本演進。

**Q14：程式碼代理在哪些類型的任務上可能會失敗？「命題式程式」的局限性意味著什麼？**
A：程式碼代理可能失敗的任務類型包括：需要真實物理模擬（如流體、軟體動力學）的任務、需要大規模真實世界資料的視覺常識任務、以及無法以確定性函數形式表達的開放式生成任務。「命題式程式」的局限性則更為深刻：由於這類程式將答案編碼為硬編碼的符號常數，僅適用於被寫死的那一個實例，因此即使代理「成功」解題，其解題能力也無法遷移至同一任務族系的其他實例。這意味著：在抽象與知識任務中，命題式比例較高的事實暗示，代理在這些類別上的成功可能更多來自「從圖像中抽取特定資訊」而非「理解任務結構」，這對「代理是否真正具備視覺推理能力」的詮釋提出了重要警示。

**Q15：未來研究方向有哪些？這項工作如何延伸至更廣泛的視覺推理問題？**
A：未來研究方向可從幾個層面延伸：首先，可將程式合成路徑推廣至更複雜的視覺推理任務，例如需要多步驟規劃、長程時間一致性或與物理世界互動的場景，以測試其極限；其次，可探索「混合架構」——結合影片模型的視覺表徵能力與程式碼代理的符號推理能力，例如由影片模型產生粗略視覺預測，再由程式碼代理進行精細化修正；第三，可深入研究如何提升「描繪式程式」的比例，使代理的解題能力更具遷移性與泛化性；最後，可將此範式應用於機器人、動畫製作、教育模擬等實際領域，探討「以程式碼解決視覺問題」在真實世界部署中的可行性與效益，從而推動視覺推理研究從基準測試走向實際應用。

2. **設定沙盒環境**：建立 CPU-only Python 容器，安裝標準影像函式庫與字型，設定 30 分鐘牆鐘時間預算與資源限制，禁用影像/影片生成模型呼叫。

3. **整合程式碼代理**：選用閉源代理（Codex + gpt-6-astra、Claude Code + Fable 5.1、Gemini CLI + Gemini 3.1 Pro）或透過 OpenCode 框架接入開源權重模型（如 GLM-5），以非互動模式執行，預先核准所有操作。

4. **準備任務輸入**：為每個實例生成標準化的任務聲明，包含第一幀路徑、提示詞、容器規格與三項約束（禁止生成模型、僅修改提示要求內容、動作須貫穿全片）。

5. **執行單次嘗試**：每個實例僅給予一次嘗試機會，不提供重試；記錄代理的事件日誌、工具呼叫次數、執行時間與 token 用量。

6. **評分與分析**：使用未修改的官方評估器對輸出影片計分；區分「遞送失敗」（未產出影片）與「內容失敗」（影片存在但評分低），並依五個認知類別（抽象、感知、空間性、轉換、知識）分析表現。

7. **分類程式策略**：將代理撰寫的程式分類為「描繪式」（執行時導航圖像以還原可遷移方案）與「命題式」（操作硬編碼值，僅適用單一實例），用於後續優化方向判斷。

### 潛在風險與注意事項

**遞送失敗風險**
- 開源權重模型常因未呼叫工具、過早停止或逾時而未產出影片，導致計零分
- **緩解措施**：設定最小工具呼叫次數門檻、優化代理的任務聲明以強調「必須執行並輸出影片」、預先測試模型的工具呼叫能力

**成本與效率落差**
- 三個閉源代理分數僅相差 0.030，但成本差距可達一個數量級
- **緩解措施**：建立成本-效益評估表，依任務類別選擇最具成本效益的代理；對大量批次任務優先採用開源權重模型

**泛化能力不足**
- 命題式程式僅適用單一實例，無法遷移至同任務族系的其他實例
- **緩解措施**：在提示中鼓勵代理撰寫描繪式程式；對命題式比例偏高的任務類別（抽象、知識）進行專項優化

**評估器偏誤**
- 強化學習訓練的影片模型以評估器作為可驗證獎勵，可能過擬合特定評估規則
- **緩解措施**：使用多樣化、未公開的測試實例驗證；定期審查評估器規則是否被代理或模型「走捷徑」

**安全與合規**
- 代理在沙盒中擁有網路存取與套件安裝權限，可能引入安全風險
- **緩解措施**：嚴格限制可安裝的套件白名單、記錄所有網路呼叫、對產出程式進行靜態掃描

### 與其他技術的整合建議

**與現有影片生成管線整合**：將程式碼代理作為「前處理」階段，用於產生結構化、可驗證的影片骨架，再交由影片生成模型進行風格化或照片寫實化渲染，兼顧邏輯正確性與視覺品質。

**與教育科技平台整合**：在 LMS（如 Moodle、Canvas）中嵌入代理 API，教師提供第一幀與提示即可批次生成練習題示範影片，並透過基於規則的評估器自動檢核學生作答影片。

**與資料視覺化工具整合**：將 Tableau、Power BI 的靜態圖表匯出為首幀，串接代理產出動畫版本，嵌入 Jupyter Notebook 或網頁報告中。

**與 CI/CD 流程整合**：將程式碼代理納入視覺回歸測試管線，對 UI 變更自動產出「預期動畫」影片並與實際錄製影片比對，偵測非預期的視覺行為。

**與模擬軟體整合**：在 Gazebo、Unity 等模擬環境中，將模擬快照作為首幀，代理撰寫程式渲染後處理動畫（如軌跡標註、向量場視覺化），用於成果展示。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「程式碼代理 vs. 影片模型」的核心對比——前者透過程式合成明確陳述答案函數，後者透過像素去噪隱式還原。接著閱讀第 2.1 節了解任務設定與沙盒機制，無需深究數據細節。重點掌握「對於可從首幀與提示計算出確定性答案的任務，程式合成目前遠比影片生成可靠」這個核心結論。

**給 AI 工程師**：應聚焦於第 2 節的方法論與第 3 節的實驗結果，特別注意沙盒設計（CPU-only、30 分鐘預算、禁用生成模型）、單次嘗試機制、以及「遞送失敗」與「內容失敗」的區分。實作時可參考論文的單一端到端管線設計，並針對開源權重模型的工具呼叫問題進行工程優化。建議進一步閱讀附錄中的程式分類分析，理解描繪式與命題式程式的工程意涵。

**給研究者**：本論文的核心貢獻在於「受控的媒介變更」實驗設計與「程式策略分類」（描繪式 vs. 命題式）。建議深入閱讀第 4 節的策略分析與附錄中的 1,385 個程式分類結果，思考以下問題：(1) 程式合成路徑的優勢是否可推廣至非確定性視覺任務？(2) 描繪式與命題式的比例與任務類別的關聯揭示了什麼視覺推理本質？(3) 此結果對世界模型（world model）研究的意涵為何？

**給產品經理**：核心訊息是：對於「可從圖片與文字計算出確定答案」的視覺任務，目前程式碼代理的可靠性（0.893–0.923）遠超影片模型（最高 0.670），且成本可控。產品決策上，若任務屬於結構化、可驗證類型（如教學動畫、資料視覺化、操作教學），應優先採用程式碼代理方案；若任務強調照片寫實性與時間一致性（如行銷影片、娛樂內容），則影片生成模型仍有其不可替代的價值。建議評估自家產品的視覺任務屬於哪一類，並據此規劃技術路線。
