## 摘要翻譯

電腦使用智慧體可透過圖形使用者介面（GUI）或程式化命令介面執行軟體任務，但現有評估往往將互動模態與任務、初始狀態、驗證器及允許動作之間的差異混為一談。我們提出了一個配對執行層基準測試，涵蓋 18 個應用程式與 12 個工作流程類別共 440 項桌面任務；其中，純螢幕 GUI 智慧體與技能中介 CLI 智慧體接收相同的目標、狀態與最終狀態驗證器，且僅限使用模態原生動作。在此控制情境中，最強的 GUI 智慧體達到 59.1% 的完全通過率，優於最強的原始技能 CLI 智慧體的 48.2%；然而，驗證器引導技能擴增將 CLI 成功率提升至 69.3%，顯示 CLI 的效能落差很大程度上源自技能覆蓋率不完整，而非僅歸因於模型本身的能力。這些

## 深度分析

#### 方法論解析

本研究的核心方法論創新在於建立一套配對執行層基準測試（matched execution-layer benchmark），以嚴格控制互動模態（interaction modality）以外的干擾變因。過往評測往往將互動模態與任務內容、初始狀態（initial state）、驗證器（verifier）設計及允許動作（permitted action）混為一談，導致無法區分模型能力與介面形式的差異。為此，作者設計了 440 道桌面任務（desktop task），橫跨 18 個應用程式（application）與 12 個工作流程類別（workflow category），並確保純螢幕 GUI 智慧體（screen-only GUI agent）與技能中介 CLI 智慧體（skill-mediated CLI agent）接收完全相同的目標、初始狀態與最終狀態驗證器（final-state verifier）。關鍵在於強制雙方僅能使用各自模態原生動作空間（modality-native action space）：GUI 端僅能透過螢幕截圖（screenshot）感知環境，並執行點擊（click）、拖曳（drag）、輸入（typing）、捲動（scroll）與鍵盤快捷鍵（keyboard shortcut）等操作；CLI 端則僅能透過程式化技能（programmatic skill）呼叫應用程式狀態（application state）的操作介面。

基準測試建置採用三階段管線：首先，從 OpenComputer 任務中篩選出具備 CLI-Anythings 技能層（skill layer）支援的應用程式，確保雙模態皆可行；其次，將原本偏向 GUI 導向的步驟式指令重寫為模態中立指令（modality-neutral instruction），僅描述期望的最終成果而非特定操作路徑；最後，人工篩選與驗證，降低介面偏誤。此外，研究設計了一項驗證器引導技能擴增（verifier-guided skill augmentation）機制：針對原始技能介面（skill interface）無法滿足的驗證器檢查點（verifier checkpoint），以終態需求為依據修補技能集（patched-skill set），藉此診斷技能覆蓋率（skill coverage）對 CLI 表現的影響程度。此設計將「技能層完備性」從「模型基礎能力」中分離，使執行瓶頸（execution bottleneck）的歸因更為精確。

#### 實驗數據解讀

實驗結果呈現三個層次的對比。首先，在原始設定下，最強大的純螢幕 GUI 智慧體（GPT-5.4）達到 59.1% 的完全通過率（full pass rate），顯著優於最強原始技能 CLI 智慧體（CodexGPT-5.5）的 48.2%。此差距乍看之下暗示 GUI 在桌面任務上具有先天優勢。然而，第二層數據顯示，原始技能層僅能滿足 37.6% 的驗證器檢查點，意味過半的失敗並非源於模型無法規劃或推理，而是技能介面根本不提供達成目標所需的操作路徑。第三層數據為關鍵反轉：在驗證器引導技能擴增後，CLI 智慧體的完全通過率躍升至 69.3%，超越 GUI 達 10 個百分點以上。作者謹慎地將此結果定位為「覆蓋率控制的診斷性上限」（coverage-controlled diagnostic upper bound），而非可立即部署的基線，因為修補過程使用了驗證器資訊，在實務上相當於事後補齊技能。

從工作流程類別細究，GUI 在應用程式介面直接暴露目標流程的任務中佔優；CLI 則在目標狀態可表徵為結構化產物（structured artifact）的場景中具有競爭力。值得注意的是，即便在修補技能後，試算表（spreadsheet）與網頁（web）工作流程仍存在模態特有挑戰，顯示除了技能缺失外，CLI 還面臨隱式預設重建（implicit-default reconstruction）與不可觀測的應用程式語義（unobservable application semantics）等深層問題。相對地，GUI 的執行瓶頸主要來自長程工作流程（long-horizon workflow）中的可靠基礎互動（grounded interaction），例如視覺元素定位失準、版面變化後的復原能力，以及多步驟操作中的錯誤累積。兩種模態呈現互補的失效模式（complementary failure modes），而非單純的優劣排序。

#### 與現有研究的比較

相較於既有文獻，本研究的定位在於「去混淆」（deconfound）模態效應。現有 GUI 智慧體研究雖已識別視覺基礎（perceptual grounding）與長動作鏈為主要失效模式，但這些評測完全基於可見應用程式介面（visible application interface），無法區分「任務難度」、「模型能力」與「GUI 模態成本」。另一方面，既有 CLI 智慧體研究常將命令列介面（CLI）等同於無限制的 shell 環境或任意程式碼執行，這實際上評測的是通用程式能力，而非特定於應用程式的技能層效能。本研究明確採用技能中介（skill-mediated）視角，將 CLI 限制在經過篩選的技能層內，從而與 GUI 進行同質的比較。

本研究的改進體現在三個層面：其一，建立可執行的最終狀態驗證器，使成功標準客觀且跨模態一致；其二，透過模態中立指令消除語言提示中的介面偏誤；其三，引入驗證器引導的技能診斷框架，量化技能覆蓋率對效能的邊際貢獻。然而，研究亦存在侷限：440 道任務雖涵蓋 18 個應用程式，但選取前提是必須具備 CLI-Anythings 支援，這可能系統性地排除那些難以封裝為程式化技能的應用程式，從而低估 CLI 在極端複雜或封閉軟體上的困難。此外，修補技能集的上限分析依賴人工介入與驗證器回饋，尚未自動化。

#### 可重現性評估

就提供的文本脈絡而言，本研究明確引用 OpenComputer 作為任務來源，並以 CLI-Anythings 作為技能層基礎，這為外部研究者提供了部分復現路徑。然而，文中並未明確說明 440 道任務的完整資料集、重寫後的模態中立指令、最終狀態驗證器程式碼，以及修補技能集（patched-skill set）的具體實作是否完全開源。沙盒桌面（sandboxed desktop）環境的確切配置（作業系統版本、應用程式版本、解析度設定等）亦未在節錄中詳述。若作者未釋出執行層的容器化環境與驗證器實作，其他團隊將難以精確復現 59.1% 與 48.2% 等絕對數值，僅能參照其方法論框架進行類似設計。建議後續發表時提供標準化評測套件，包含受控初始狀態的虛擬機映像檔與可執行的終態檢查腳本，以強化可重現性。

#### 未來研究方向

本研究為電腦使用智慧體（computer-use agent）的模態選擇提供了系統性證據，同時開啟數個值得深入的方向。第一，自動化技能層擴增：當前驗證器引導的技能修補依賴人工與驗證器回饋，未來可探索由大型語言模型自動生成對應程式化技能（programmatic skill），以提升技能覆蓋率（skill coverage）的可擴展性（scalability）。第二，混合模態智慧體（hybrid agent）：既然 GUI 與 CLI 呈現互補失效模式，設計能動態切換或同時使用螢幕感知與技能呼叫的架構，可能在長程工作流程中結合 GUI 的廣泛適用性與 CLI 的結構化效率。第三，隱式預設重建問題：CLI 智慧體在呼叫技能時常因應用程式的預設參數或隱藏狀態而偏離預期，需要更精細的應用程式語義觀測機制，例如結合應用程式內部狀態 API 或強化學習以校準隱藏變因。第四，長程可靠性：GUI 智慧體在多步驟操作中的錯誤累積問題可透過中間狀態驗證（intermediate-state verification）與分層規劃（hierarchical planning）緩解。最後，將此配對執行層協議（matched execution-layer protocol）擴展至網頁、行動裝置及企業級軟體，將有助於建立更通用的執行層評測生態系。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：本文旨在解決現有評估方式無法有效區分「互動模態本身」與「其他混淆變因」對電腦使用智慧體表現的影響。過去比較圖形使用者介面（GUI）與命令列介面（CLI）時，往往同時混雜了任務內容、初始狀態、驗證器設計以及允許動作的差異，導致無法精確識別真正的執行瓶頸。因此，作者主張必須建立一個嚴格控制的配對執行層基準測試，才能公正地比較兩種模態的優劣。

**Q2：為何現有的評估方法無法公平比較 GUI 與 CLI 智慧體？**
A：現有方法在比較純螢幕 GUI 智慧體與技能中介 CLI 智慧體時，未能控制任務目標、初始狀態與最終狀態驗證器等關鍵變因，使得觀察到的效能差異可能源自任務本身而非互動模態。舉例來說，某些測試可能讓 GUI 智慧體執行視覺導向的任務，卻讓 CLI 智慧體處理結構化資料操作，這種任務內容的不一致會嚴重偏誤比較結果。此外，現有基準測試通常允許不同模態使用不同的動作空間，進一步混淆了模態原生能力與外部工具支援程度的影響。

**Q3：將執行層模態效應與其他變因分離為何如此重要？**
A：這種隔離能幫助研究者準確定位智慧體失敗的根本原因，避免將任務設計的偏誤誤判為互動模態的限制。如果無法區分這些變因，我們就無法判斷 GUI 智慧體的失敗是來自視覺基礎互動的困難，還是任務本身不適合視覺操作；同理也無法判斷 CLI 智慧體的表現不佳是源於模型能力不足，還是技能層的覆蓋率缺口。這種精確的歸因對於指導未來的技術投資、系統架構選擇與產品開發優先順序具有關鍵的戰略意義。

**Q4：本文提出的核心方法是什麼？**
A：本文提出了一個包含 440 個桌面任務、橫跨 18 個應用程式與 12 個工作流程類別的配對執行層基準測試。在這個框架中，兩種互動模態的智慧體接收完全相同的模態中立指令、初始狀態與可執行的最終狀態驗證器，但各自只能使用其模態原生動作空間。例如，GUI 智慧體僅能透過點擊、拖曳、輸入與鍵盤快捷鍵操作沙盒桌面，而 CLI 智慧體則只能呼叫程式化技能介面，確保任何觀察到的效能差異都能歸因於互動模態本身的特性。

**Q5：這個基準測試設計的關鍵創新為何？**
A：關鍵創新在於三階段建構流程與嚴格的變因控制，這是首次在執行層上實現 GUI 與技能中介 CLI 的公平對照。研究團隊首先選擇同時支援視覺互動與 CLI-Anythings 技能層的應用程式，接著將原本偏向 GUI 的逐步指令重寫為僅描述目標結果的模態中立指令，最後透過人工篩選來減少介面偏誤。這種系統化的流程確保了任務集不會過度偏袒任一互動模態，使得比較結果具有高度的內部效度。

**Q6：為何作者選擇將智慧體限制在模態原生動作空間，而非允許任意動作？**
A：作者這樣做是為了真實反映兩種互動典範在實際部署時的根本差異，並將模態效應與通用程式碼執行能力分離。GUI 智慧體必須透過可見應用程式介面進行基礎互動，這模擬了人類直接操作電腦的方式；而 CLI 智慧體則依賴預先建構的技能介面來操作應用程式狀態，代表了透過程式化命令介面進行自動化的路徑。若允許任意動作，將無法區分模態本身的執行邏輯與模型的一般推理能力，從而破壞比較的控制性與實務意義。

**Q7：實驗的主要量化結果為何？**
A：在最強大的模型配置下，純螢幕 GUI 智慧體（GPT-5.4）達到了 59.1% 的完全通過率，而使用原始技能集的 CLI 智慧體（CodexGPT-5.5）僅達到 48.2%。然而，當引入驗證器引導技能擴增後，CLI 智慧體的成功率大幅提升至 69.3%，顯著超越 GUI 表現。這項結果強烈暗示，原始觀察到的 CLI 劣勢主要並非來自基礎模型能力的不足，而是技能介面的覆蓋率不完整所致。

**Q8：驗證器引導技能擴增實驗揭示了什麼關於 CLI 智慧體的洞見？**
A：該實驗揭示，原始技能集僅能滿足 37.6% 的驗證器檢查點，顯示技能覆蓋率是造成 CLI 執行瓶頸的關鍵因素。當研究人員根據驗證器觀察到的需求修補遺失的技能路徑後，CLI 智慧體能夠在原本失敗的任務上取得顯著進展，成功率從 48.2% 躍升至 69.3%。值得注意的是，作者將此結果視為覆蓋率控制的診斷性上限估計，而非現成可用的基線，因為修補過程依賴了驗證器資訊，在真實部署中無法直接複製。

**Q9：GUI 與 CLI 智慧體分別呈現出哪些互補的失敗模式？**
A：GUI 智慧體主要受限於視覺基礎互動的可靠性以及長程工作流程中的程序執行困難，例如在複雜多步驟操作中維持注意力與精確操作。相對地，CLI 智慧體的瓶頸則集中在技能覆蓋率缺口、隱式預設重建問題，以及部分無法透過技能層觀察到的應用程式語義。這些差異表明，GUI 將執行邏輯嵌入可見介面之中，而 CLI 則將執行邏輯外顯於建構的技能層，兩者面臨的根本挑戰截然不同。

**Q10：這些發現對實際部署桌面自動化系統有何指導意義？**
A：當目標應用程式的可見介面直接暴露所需工作流程時，GUI 智慧體通常是較穩健的選擇；反之，若目標狀態可以明確表示為結構化產物，則 CLI 智慧體在技能覆蓋率充足的前提下可能更具優勢。企業在導入自動化解決方案時，應先評估任務性質與現有技能層的對應程度，而非預設某一互動模態必然較優。此外，對於長期維運而言，持續擴充與驗證技能介面的完整性將是 CLI 路徑成功的關鍵投資。

**Q11：產品開發者在選擇互動模態時應考量哪些因素？**
A：開發者必須權衡可見應用程式介面的穩定性與技能層的可擴展性。GUI 智慧體雖然無需預先建構技能介面，但容易受到介面佈局變化與長程工作流程中錯誤累積的影響；CLI 智慧體則需要持續維護技能層以確保覆蓋率，但一旦技能完備，其在結構化操作上的精確度與可擴展性較高。因此，對於快速變動的消費級應用程式，GUI 可能更具彈性；而對於企業內部系統或具有穩定程式化介面的專業軟體，投資 CLI 技能層可能帶來更高的長期回報。

**Q12：這項研究對自主智慧體領域的廣泛影響為何？**
A：這項研究重新定義了 GUI 與 CLI 比較的框架，將其從單純的模型能力競賽轉化為「執行邏輯應嵌入可見介面抑或外顯技能層」的工程問題。透過建立嚴格控制的配對執行層基準測試，本文為後續研究提供了一個可複現的評估典範，有助於區分真正的模態限制與實驗設計瑕疵。這也提醒學界與業界，在宣稱某一互動模態優於另一模態之前，必須先確保任務內容、初始狀態與驗證標準的一致性。

**Q13：本文承認了哪些研究局限？**
A：作者承認驗證器引導技能擴增所達到的 69.3% 成功率是診斷性上限，而非現成可用的 CLI 基線，因為修補技能集的過程利用了驗證器資訊，在真實部署中無法直接複製。此外，儘管基準測試涵蓋了 18 個應用程式，但仍有部分工作流程類別（如試算表與網頁工作流程）在修補技能後仍存在模態特有的挑戰。最後，本研究聚焦於執行層的比較，並未深入探討規劃層或推理層的差異，這些層面可能也會影響兩種模態的整體表現。

**Q14：即使在處理技能覆蓋率後，哪些具體的失敗案例仍然存在？**
A：即使在技能覆蓋率缺口獲得修補後，CLI 智慧體在試算表與網頁工作流程中仍面臨持續的挑戰，顯示部分問題超越了單純的技能介面不完整。這些殘留的失敗案例可能源於應用程式語義無法透過現有技能層完整觀察，或是隱式預設重建導致狀態轉換與預期不符。對 GUI 智慧體而言，即使擁有完整的視覺資訊，在長程工作流程中仍會因視覺基礎互動的可靠性問題而失敗，這些程序執行上的困難無法僅透過增加技能數量來解決。

**Q15：這項研究指出了哪些未來的研究方向？**
A：未來研究可朝開發能動態擴充技能覆蓋率的自動化技能發現機制邁進，以降低 CLI 智慧體對人工維護技能層的依賴。對於 GUI 智慧體，研究者需要探索更強大的視覺基礎模型與錯誤恢復策略，以提升長程工作流程中的執行穩健性。此外，結合兩種模態優勢的混合式架構——例如利用 GUI 進行探索與驗證、同時透過 CLI 執行結構化批量操作——可能是突破現有執行瓶頸、邁向更通用電腦使用智慧體的重要路徑。

## 實務應用指南

### 適用場景

1. **企業級桌面流程自動化選型**：當組織需要自動化操作 LibreOffice、Audacity、Chrome 等傳統桌面應用程式時，可用此配對執行層方法評估應採用純螢幕 GUI 智慧體（模擬人類點擊與輸入）或技能中介 CLI 智慧體（透過程式化技能層操作），避免將任務難度與互動模態混為一談。
2. **跨模態自動化測試與 QA**：建立模態中立的任務描述與可執行終態驗證器，讓同一套測試案例能同時驗證 GUI 與 CLI 兩條自動化路徑的正確性，特別適用於需支援多種部署環境（有無 API、新舊版本介面）的企業軟體。
3. **低程式碼/無程式碼平台的路由決策**：在 Agentic 工作流程中，依據任務類型動態分流——視覺設計、網頁導航等長程工作流程導向 GUI；試算表公式批次處理、檔案後設資料修改等結構化產物導向 CLI，並以統一的終態驗證器確認結果。
4. **遺留系統現代化與技能層建構**：針對僅提供可見應用程式介面、缺乏穩定 API 的老舊系統，透過驗證器引導技能擴增的方式，有系統地將 GUI 操作反向工程為 CLI 技能層，逐步提升程式化自動化的覆蓋率。
5. **多模態智慧體的 Bottleneck 診斷**：當 AI 助理同時具備視覺感知與工具呼叫能力時，利用本文的對照協定定位失敗根源——究竟是視覺基礎互動與長程執行漂移（GUI 瓶頸），還是技能介面不完整與隱式預設重建錯誤（CLI 瓶頸）。

### 實作前置條件

- **資料需求**：模態中立指令（僅描述目標產出，不含 GUI 或 CLI 特定步驟）、標準化初始狀態（沙盒桌面快照或容器化環境模板）、可執行的終態驗證器（能自動檢查檔案內容、應用程式狀態或結構化產物的程式碼，而非人工判讀）。
- **運算資源**：支援截圖與輸入模擬的沙盒桌面環境（供 GUI 智慧體使用）、可執行 CLI 技能的隔離容器或虛擬機、以及足夠的 LLM 推理配額（需支援長程多輪互動，如 GPT-5.4 或 CodexGPT-5.5 等級模型）。
- **技能與人力前提**：具備視覺自動化框架（如 PyAutoGUI、Playwright 桌面版）經驗的工程師；熟悉目標應用程式內部狀態與 CLI-Anything 技能層格式的開發者；能撰寫模態中立任務規範並定義驗證器檢查點的領域專家。

### 實作步驟建議

1. **建立配對執行層協定**：鎖定任務目標、初始狀態與終態驗證器，使 GUI 與 CLI 智慧體接收完全一致的輸入。任務描述必須為模態中立指令，僅敘述期望的最終結果。
2. **劃分模態原生動作空間**：為 GUI 智慧體限定螢幕截圖、點擊、拖曳、輸入、捲動與鍵盤快捷鍵；為 CLI 智慧體限定技能層允許的程式化操作集合，禁止混用模態，確保比較的是互動模態而非動作自由度。
3. **開發可執行的終態驗證器**：針對每項桌面任務設計自動化檢查點（如 LibreOffice Calc 的儲存格數值、Audacity 的音軌名稱、draw.io 的圖表節點數量），作為客觀的任務完成判準。
4. **執行雙模態基準測試**：在涵蓋 18 個應用程式與 12 個工作流程類別的任務集上，分別運行純螢幕 GUI 智慧體與原始技能 CLI 智慧體，記錄完全通過率與各類別的表現分佈。
5. **診斷技能覆蓋率缺口**：分析 CLI 路徑的驗證器檢查點失敗案例，識別原始技能層未覆蓋的操作（如應用程式語義不可見、隱式預設重建錯誤），並執行驗證器引導技能擴增以估算可恢復的效能上限。
6. **依據工作流程特性部署最佳模態**：將視覺設計、網頁流程與長程介面導航任務配置給 GUI 路徑；將試算表、批次檔案操作與結構化產物任務配置給 CLI 路徑，並在智慧體編排層設計動態路由邏輯。

### 潛在風險與注意事項

- **混淆變因風險**：若任務描述、初始狀態或驗證器在兩模態間存在細微差異，會導致錯誤歸因。務必使用同一套模態中立指令，並鎖定沙盒環境的作業系統與應用程式版本。
- **技能層維護成本陷阱**：CLI 智慧體的效能高度依賴技能介面完整度。原始技能僅能滿足 37.6% 的驗證器檢查點，若缺乏持續擴增技能的工程資源，CLI 路徑的實際完全通過率可能長期停留在 48.2% 附近，遠低於 GUI 基線。
- **長程工作流程漂移**：GUI 智慧體在數十步以上的任務中，容易因視覺基礎錯誤（如按鈕座標偏移、介面佈局變化）而累積錯誤。建議在長任務中設置中間狀態檢查點與復原機制，避免單點失敗導致全盤重來。
- **過度擬合驗證器的誤解**：驗證器引導修補可將 CLI 成功率提升至 69.3%，但此為診斷上限而非開箱即用基線。實際產品部署時，不可假設能預先知悉所有驗證器需求來即時修補技能層。
- **應用程式語義不可見性**：部分應用程式狀態（如未存檔的暫時編輯、渲染管線內部參數）對 CLI 技能層不可見，需額外設計狀態查詢介面或回退至 GUI 進行確認。

### 與其他技術的整合建議

- **與 RPA 平台整合**：將 GUI 模態接入現有 RPA 的視覺錄製與排程流程，同時將 CLI 技能層封裝為 RESTful API，讓中央排程器依據任務類別與技能覆蓋率動態選擇執行模態。
- **與 LLM 編排框架整合**：透過 LangChain、AutoGen 或類似框架，將模態中立指令作為高階目標，由路由器（Router）根據當前技能層覆蓋狀態與任務特徵，決定派發至 GUI Agent 或 CLI Agent，並統一以終態驗證器回傳結果。
- **與 CI/CD 整合**：將沙盒桌面環境與終態驗證器容器化，納入持續整合管線，對桌面應用程式的自動化腳本進行回歸測試，確保 GUI 與 CLI 路徑在版本更新後仍維持預期通過率。
- **與知識庫整合**：針對 CLI 技能層建立操作語義知識庫，記錄每個技能對應的驗證器檢查點、隱式預設行為與失敗模式，支援未來自動化技能生成、缺口偵測與跨應用程式技能遷移。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦於「配對執行層」的核心概念——想像你要比較兩個人完成同一份考卷，必須給予相同的題目、相同的起點、相同的評分標準，只是允許使用的工具不同（滑鼠 vs 指令碼）。從圖 1 的概覽與第 3 節的基準建構流程開始，理解為何控制變因如此重要，再回頭看實驗數據會更容易上手。
- **AI 工程師**：請重點研讀第 3.2 節的基準建構管線與診斷分析章節。實務上最關鍵的收穫是「技能覆蓋率診斷方法」：如何透過驗證器檢查點反推 CLI 技能層的缺口，以及為何 GUI 的瓶頸在長程視覺基礎而非模型能力。這直接影響你在生產環境中選擇模態與設計 fallback 機制的決策。
- **研究人員**：本文的方法論貢獻在於分離「互動模態」與「任務內容」這兩個長期混淆的變因。建議深入分析互補失敗模式的分類（視覺基礎與長程執行 vs 技能覆蓋缺口與隱式預設重建），並思考如何將此配對協定擴展至多模態代理（同時具備 GUI 與 CLI 能力）或應用於其他執行層（如觸控、語音）。
- **產品經理**：請將注意力放在實驗結果的商業意涵：GUI 59.1% 與原始 CLI 48.2% 的落差，可透過技能擴增收斂至 CLI 69.3%，意味著「建構技能層」是 ROI 極高的工程投資，但僅適用於結構化工作流程。視覺設計與網頁流程仍應保留 GUI 路徑。建議以此數據作為與工程團隊討論自動化路線圖的依據。
