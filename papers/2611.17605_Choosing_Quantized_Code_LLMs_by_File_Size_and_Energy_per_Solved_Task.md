## ⚡ TL;DR

開發者為筆電挑選本地程式碼 LLM 時，需在正確性與能耗間取捨，常見「大模型低精度」法則未必划算。
作者測試 24 個 Qwen2.5-Coder GGUF 檔案，以每解決任務能耗建立依大小的選擇指南。
1 至 2 GB 時 q4_K_M 同居正確性與能耗前緣；3 GB 的 7B-q2_K 能耗翻倍卻無顯著增益。

## 深度分析

#### 方法論解析

本論文的核心方法論建立在「以檔案大小為索引、以每解決任務能耗（Energy per Solved Task）為統一計價單位」的雙軸決策框架上，試圖為本地部署程式碼大型語言模型（Code LLMs）的開發者提供實證驅動的選擇指南。

**研究設計的關鍵選擇**

作者刻意將「模型系列」（Qwen2.5-Coder-Instruct）與「提示策略」（zero-shot prompt）固定，僅在「模型規模」（0.5B、1.5B、3B、7B）與「量化配方」（fp16、q8_0、q6_K、q5_K_M、q4_K_M、q3_K_M、q2_K）兩個維度上進行系統性遍歷，共構成 24 個 GGUF 檔案。這種「控制變數、橫切比較」的設計避免了混淆變數，使每個檔案的能耗與正確性可被獨立歸因。

**能耗計量的多軌設計**

論文最值得注意的方法論嚴謹性在於其能耗計量採用多重會計（accounting）方式：
- **分軌計量（rails）**：分別量測 CPU、GPU、記憶體通道的功耗
- **整機計量（whole-system power）**：量測裝置整體功耗

這種設計使作者能驗證「7B-q2_K 較 3B-q4_K_M 需要 2.03 倍每解決任務能耗」這一關鍵結論在不同計量方式下的穩健性——分軌下為 2.03 倍，整機下為 1.66 至 1.81 倍。

**統計推論的嚴謹性**

對於核心的「錨定配對」（anchor pair，即 3B-q4_K_M 對 7B-q2_K），作者採用三層驗證：
1. **精確配對檢定（exact paired tests）**：在 542 個任務上做任務對任務的比較
2. **交替會話配對（alternating session pairs）**：在 HumanEval+ 上進行五組交替重複實驗，以控制時間漂移與系統狀態變數
3. **90% 信賴區間（90% CI）**：量化不確定性，明確指出 3B-q4_K_M 的最大可能落後僅 2.4 點

**「配方標籤不等於位元數」的重要洞察**

作者揭示了一個常被忽略的技術細節：Ollama 的配方標籤（recipe tag）並非純粹的位元數標示。以 0.5B-q3_K_M 為例，該檔案實際上「不包含任何三位元張量」，其有效每權重位元數（Effective Bits Per Weight, BPW）為 5.66。這是因為 k-quants 方案會在單一檔案中混合多種張量類型，部分張量維持較高精度。這項觀察對實務選擇至關重要——開發者若僅憑標籤推斷能耗，將產生嚴重誤判。

**證據標籤系統**

每個推薦都附帶「證據標籤」（evidence label），明確標示其依據來自：重複實驗、正確性檢定、還是點估計的能耗邊際。這種透明化的不確定性溝通，是方法論上的重要貢獻。

#### 實驗數據解讀

**核心數據矩陣**

論文的實驗結果以「檔案大小預算」為橫軸（0.5、1、2、4、8 GB），縱軸為每個預算下的最佳選擇：

| 預算 | 推薦檔案 | 關鍵數據 |
|------|---------|---------|
| 1 GB | 1.5B-q4_K_M | 同時位於正確性與能耗前緣 |
| 2 GB | 3B-q4_K_M | 同時位於正確性與能耗前緣 |
| 3 GB | 3B-q4_K_M（拒絕 7B-q2_K）| 7B-q2_K 需 2.03 倍能耗 |
| 8 GB | 7B-q6_K | 提供顯著正確性增益 |

**「較大模型法則」失效的關鍵證據**

這是全文最重要的實驗發現。在 3 GB 預算下，傳統經驗法則「較大模型在較低精度下傾向勝過較小模型在較高精度下」（larger-model rule）會推薦 7B-q2_K——因為它是唯一能塞進 3 GB 的 7B 檔案。然而實驗數據顯示：

- **正確性**：3B-q4_K_M 解決 366 個任務，7B-q2_K 解決 363 個，差距在統計上不顯著（90% CI 限制落後至多 2.4 點）
- **能耗**：7B-q2_K 需要 2.03 倍的每解決任務能耗（分軌計量），或 1.66 至 1.81 倍（整機計量）
- **穩健性**：在 HumanEval+ 的五組交替會話配對中，比率為 1.925 對 1.956，與主網格結果高度一致

這個結果挑戰了 Song 等人所報告的「3.5 有效 BPW 效能門檻」——7B-q2_K 的 3.16 BPW 低於該門檻，因此其失敗具有理論預期性，但本論文首次在程式碼任務上以能耗為成本函數量化了這個失敗的幅度。

**q4_K_M 的甜蜜點（sweet spot）**

從 1.5B 起，q4_K_M 與同尺寸最高精度版本之間的正確性差距始終小於 3 點（90% CI）。這印證了先前文獻中「四位元精度幾乎普遍最優」的觀察，並將其推廣到程式碼任務的能耗維度。

**0.5B 規模的特殊性**

0.5B 模型展現出與較大模型不同的行為：其配方標籤與實際張量組成的對應關係較弱（q4_K_M 檔案中僅 12/169 個張量為 q4_K，其餘為 q8_0）。這暗示在小模型上，量化對能耗的影響模式可能與大模型不同，但作者未深入分析此現象。

**能耗與通過率的解耦**

論文的隱含訊息是：在程式碼任務上，「更多參數」與「更高通過率」並非線性關係。當精度降至 q2_K 時，模型容量（capacity）的增加被噪訊注入所抵消，導致淨正確性幾乎無變化，但計算成本卻不成比例地增加——這是「能耗-正確性前緣」（energy-correctness frontier）上的一個凹點（concave point）。

#### 與現有研究的比較

**與 Cunha 等人 [2] 的關係**

Cunha 等人在 GREENS 2026 的工作測試了五個本地 LLM 在 HumanEval-X 與 MBPP+ 上的表現，採用 Intel Core i7-8700 與 CPU-only 推論。本論文承接其「模型選擇影響能耗」的核心論點，但有三項關鍵推進：

1. **硬體現代化**：從 Intel CPU 轉向 Apple Silicon GPU（fanless MacBook Air M2），反映本地推論的主流硬體轉移
2. **量化維度的細粒度遍歷**：Cunha 等人每個模型僅測一個量化檔案，本論文則對四個尺寸各測多個量化等級
3. **成本函數的統一化**：以「每解決任務能耗」取代「每 token 能耗」或「每工作負載能耗」，更貼近開發者的實際效用

**與 Alizadeh 等人 [3], [11] 的關係**

Alizadeh 等人的兩項研究在 Ollama 上測試 fp16、q8、q4 標籤，涵蓋 Qwen2.5-Coder 1.5B 與 7B，發現「量化大型模型優於全精度中型模型」。本論文與其結論一致（fp16 結果吻合），但有三項差異化貢獻：

1. **量化階梯的延伸**：從 q4 延伸至 q3_K_M 與 q2_K，揭示了「過度量化」的能耗懲罰
2. **計價單位的轉變**：從「每 token 能耗」轉為「每解決任務能耗」，將能耗與開發者效用直接掛鉤
3. **硬體差異**：Alizadeh 等人使用 NVIDIA A100 與一般筆記型 GPU，本論文使用無風扇 Apple 筆電，反映「永遠開機的程式碼助手」的真實部署場景

**與 Saad-Falcon 等人 [5] 的關係**

Saad-Falcon 等人提出「每焦耳準確率」（accuracy per joule）指標。本論文的「每解決任務能耗」與其精神一致，但更聚焦於「已驗證的程式碼正確性」而非一般語言任務的準確率，這對程式碼助手場景更具實務意義。

**與 Abkin 等人 [9] 的關係**

Abkin 等人在代理任務（agent tasks）上使用 bootstrap 區間報告「每驗證任務能耗」。本論文借鏡其統計方法（90% CI），但將其應用於靜態程式碼生成任務。

**文獻中的反向證據**

值得注意的是，兩項基於 Hugging Face Transformers 的研究 [12], [13] 報告「量化提高能耗」，與 Ollama 生態系的結果 [3], [11] 矛盾。本論文站在 Ollama 一側，並未深入探討此分歧——這可能與 llama.cpp 的記憶體映射策略、Metal GPU 的量化支援、或 Transformers 框架的執行階段有關，是一個值得追問的開放問題。

**本論文的主要限制**

1. **單一模型家族**：僅測試 Qwen2.5-Coder，結論對其他程式碼模型（如 CodeLlama、DeepSeek-Coder、StarCoder）的可推廣性未經驗證
2. **單一硬體平台**：僅在 MacBook Air M2 上測試，Apple Silicon 的統一記憶體架構可能使結果難以推廣至分離式 CPU/GPU 系統
3. **單一評測基準**：僅使用 EvalPlus（HumanEval+ 與 MBPP+），未涵蓋 LiveCodeBench、CodeContests 等更具實務複雜度的基準
4. **靜態分析缺失**：未分析量化對程式碼風格、安全性、可維護性的影響，僅以「通過/未通過」二元結果計價

#### 可重現性評估

**優於平均的開放性**

本論文在可重現性方面展現了高於領域平均水準的承諾：

1. **完整釋出物**：作者明確聲明釋出「每任務結果、功耗日誌與分析腳本」（per-task results, power logs and the analysis script），這三項是重現實驗的關鍵資產
2. **可再生定價清單**：24 個檔案的有效 BPW 與每解決任務能耗均附於論文中，且「釋出的腳本可重新生成每個測量數字」，這意味著即使硬體不同，開發者也能在自身機器上驗證相對排序
3. **標準化工具鏈**：使用 Ollama 與 llama.cpp 等主流工具，無自製推論引擎的黑箱風險

**可重現性的潛在障礙**

然而，仍有若干因素可能妨礙嚴格重現：

1. **硬體特定性**：MacBook Air M2 的功耗特性受晶片批次、macOS 版本、電池健康度等多重因素影響。論文中未說明量測時的系統狀態（電池是否接電、螢幕亮度、背景程序等）
2. **溫度效應**：無風扇設計意味著持續推論會導致熱節流（thermal throttling），這會系統性地影響能耗與延遲測量，但作者未討論此效應
3. **模型版本漂移**：Ollama 上的 GGUF 檔案可能隨時間更新，本論文未提供檔案的雜湊值或下載時間戳記
4. **隨機性控制**：論文中提到「五組交替會話配對」用於控制時間漂移，但未說明主要實驗是否採用固定隨機種子，或推論的確定性程度

**與「再生式科學」的距離**

論文的「再生式價格清單」（regenerable price list）概念值得讚賞——它將靜態的實驗結果轉化為可由開發者本地驗證的動態工具。這種「科學即軟體」（science-as-software）的方法論，若能擴展至更多模型家族與硬體平台，將對綠色軟體（green software）社群產生實質貢獻。

**資料與程式碼可用性評分**

基於上述分析，本論文在可重現性方面可評為「中等偏上」：
- ✅ 釋出原始資料與腳本
- ✅ 使用標準化工具鏈
- ✅ 提供可再生方法
- ⚠️ 硬體特定性高
- ⚠️ 隨機性與系統狀態控制細節不足

#### 未來研究方向

**1. 跨模型家族的泛化驗證**

本論文僅測試 Qwen2.5-Coder 一個模型家族。最直接的延伸是將相同方法論應用於：
- **DeepSeek-Coder-V2 / V3**：測試 MoE 架構對量化-能耗權衡的影響
- **CodeLlama / StarCoder2**：驗證「q4_K_M 甜蜜點」是否為架構無關的普遍現象
- **Phi-3 / Phi-4-mini**：探索小模型在極低精度下的能耗彈性

此方向可建立「量化-能耗-正確性」的三維曲面，而非當前的離散點估計。

**2. 跨硬體平台的能耗特性映射**

Apple Silicon 的統一記憶體架構使本論文結果難以直接推廣至：
- **分離式 GPU 系統**（NVIDIA RTX 系列）：量化對 VRAM 頻寬的影響模式不同
- **行動裝置**（手機、平板）：熱預算更為嚴苛，節流效應更顯著
- **邊緣裝置**（Raspberry Pi、Jetson Nano）：與 Husom 等人 [14] 的工作形成互補

建立「硬體-量化-能耗」的查表工具，將是綠色 AI 部署的實質基礎建設。

**3. 動態量化與自適應精度**

本論文測試的是靜態量化檔案。一個有趣的方向是：
- **執行時自適應精度**：根據任務難度動態選擇量化等級
- **混合精度推論**：在同一生成過程中對不同層使用不同精度
- **能耗感知解碼**：在正確性信心度高時提前停止，節省計算

這將把「選擇指南」從「事前決策」轉化為「執行時最佳化」。

**4. 程式碼品質的多維評估**

當前論文僅以「通過/未通過」二元結果計價。未來可納入：
- **程式碼風格一致性**（linting 違規數）
- **安全性弱點**（靜態分析結果）
- **可維護性指標**（循環複雜度、認知複雜度）
- **執行效率**（生成程式碼的執行時間與記憶體使用）

這將使「每解決任務能耗」擴展為「每品質調整後任務能耗」，更貼近工業部署的真實成本函數。

**5. 代理工作流的能耗建模**

本論文聚焦於單次程式碼生成。隨著程式碼代理（coding agents）興起，未來工作應探討：
- **多輪迭代的能耗累積**：錯誤修正迴圈如何放大模型選擇的影響
- **工具呼叫的能耗成本**：程式碼執行、測試執行、搜尋的能耗是否改變模型選擇的最優解
- **人機協作循環**：開發者介入點對整體能耗的影響

**6. 碳排放與電網時空異質性**

「能耗」僅是碳排放的代理變數。未來工作應整合：
- **電網碳強度**（grid carbon intensity）的時空變化
- **再生能源匹配**（renewable matching）的部署策略
- **生命週期評估**（LCA）：將模型訓練的隱含能耗攤提到每次推論

這將把「綠色軟體」從裝置層級提升至系統層級。

**7. 量化對模型行為的深層影響**

本論文發現 q2_K 在 7B 上「不付費」，但未深入分析原因。未來可探討：
- **注意力模式崩潰**：極低精度是否破壞長程依賴
- **詞彙分布偏移**：量化是否系統性地改變生成程式的 API 選擇
- **錯誤類型分析**：量化模型的失敗是語法錯誤、邏輯錯誤、還是 API 誤用

這將連結「綠色 AI」與「可解釋 AI」兩個社群。

**8. 基準測試的代表性反思**

EvalPlus 雖為標準基準，但其任務可能無法代表開發者的真實工作負載。未來應：
- 在企業級程式碼庫上進行縱向研究
- 比較「基準通過率」與「實際生產力提升」的相關性
- 建立「開發者效用函數」的標準化量測方法

這將使「每解決任務能耗」從學術指標轉化為產業決策依據。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼這個問題對開發者很重要？**
A：這篇論文要解決的核心問題是：在本地筆電上運行程式碼助手時，開發者該如何在眾多 GGUF 量化檔案中，依據檔案大小預算做出最佳選擇。這個問題之所以重要，是因為本地推論會將每次請求的能耗直接轉移到開發者的機器上，而開發者只需下載一個模型檔案，該檔案同時決定了模型規模與量化配方。一旦選錯檔案，不僅會浪費能源，還可能無法獲得顯著的正確性提升。論文將「每解決任務的能耗」（energy per solved task）視為開發者的真實成本，因為開發者最終關心的是能正常運作的程式碼，而非單純的模型大小或精度數字。

**Q2：現有的「較大模型在較低精度下通常勝過較小模型在較高精度下」的經驗法則，在什麼情況下會失效？**
A：根據本研究的實測結果，這個經驗法則在 3 GB 檔案大小預算時會失效。具體而言，當 7B-q2_K（有效 BPW 為 3.16，低於 Song 等人所報告的 3.5 BPW 效能門檻）作為唯一能放入 3 GB 預算的 7B 檔案時，它相較於 2 GB 的 3B-q4_K_M 並未帶來顯著的解題數提升（366 vs. 363），90% 信賴區間將 3B-q4_K_M 的差距限制在 2.4 點以內。然而 7B-q2_K 卻需要 2.03 倍的每解決任務能耗（整機功耗計量下為 1.66 至 1.81 倍）。這顯示在低於 BPW 門檻時，盲目套用「較大模型法則」會付出不成比例的能源代價，卻換不到對應的正確性收益。

**Q3：為什麼僅靠「每權重位元數」（BPW）或檔案大小標籤不足以做出明智的模型選擇？**
A：BPW 與檔案大小標籤無法反映 GGUF k-quant 配方的真實結構，因為一個標籤（如 q4_K_M）僅描述大多數張量的量化方式，檔案中其餘張量可能維持更高精度。例如 0.5B-q3_K_M 檔案實際上不含任何三位元張量，其有效 BPW 高達 5.66；而 0.5B-q6_K 檔案則混合了 q6_K 與 q8_0 張量。這意味著僅憑標籤名稱猜測精度會產生嚴重誤導，開發者必須依據實際量測的有效 BPW 與每解決任務能耗來做選擇，這也是本論文主張「以 Ollama 列出的檔案大小為索引、附上證據標籤的選擇指南」的核心理由。

**Q4：本研究提出的「選擇指南」（Selection Guide）採用什麼核心方法來索引與標註模型推薦？**
A：本研究提出的選擇指南以 Ollama 列出的檔案大小（0.5、1、2、4、8 GB）作為索引維度，在每個預算級距中選出在 542 個 EvalPlus 任務上解題數最多的檔案，並附上其每解決任務能耗與預算內的次優選項。每個推薦與每條比較規則都帶有「證據標籤」（evidence label），明確標示其依據來自重複實驗、正確性檢定或點估計的能耗差距。這種設計讓開發者能直接根據自身機器的儲存與記憶體預算快速決策，同時清楚理解每個推薦背後的證據強度，而非僅憑模糊的經驗法則。

**Q5：本研究在方法上的關鍵創新為何？為什麼「每解決任務的能耗」是比「每 token 能耗」更好的計量單位？**
A：本研究的關鍵創新在於將「每解決任務的能耗」作為模型選擇的核心價格指標，並透過精確配對檢定（exact paired tests）逐任務比較 24 個檔案。相較於既有文獻常用的「每 token 能耗」或「每工作負載能耗」，「每解決任務的能耗」直接對應開發者的實際產出價值——能通過測試的可執行程式碼。這避免了單純追求低能耗卻犧牲正確性的陷阱，也讓「能源前緣」（energy frontier）與「正確性前緣」（correctness frontier）的概念得以在同一指標下整合比較，使模型選擇從單一維度最佳化轉變為多目標的 Pareto 前緣分析。

**Q6：本研究在實驗設計上有哪些重要的取捨與選擇？為何選擇 fanless MacBook Air M2 與 Qwen2.5-Coder？**
A：本研究選擇無風扇 MacBook Air M2 作為測試平台，是為了模擬開發者在輕薄筆電上運行本地程式碼助手的真實情境，並避免主動散熱造成的功耗波動干擾量測。選擇 Qwen2.5-Coder-Instruct 是因為它是當前主流的開源程式碼模型家族，且 Ollama 為其提供完整的四種規模（0.5B、1.5B、3B、7B）與多種 k-quant 配方，便於系統性地跨規模與跨精度比較。此外，研究固定了程式碼家族與零樣本提示，僅變動模型規模與量化配方，從而隔離出檔案大小選擇對能耗與正確性的純粹影響，這是 Cunha 等人 [2] 啟發但更聚焦的設計選擇。

**Q7：本研究使用了哪些基準測試？為何選擇 EvalPlus 而非僅用 HumanEval？**
A：本研究主要使用 EvalPlus 的 542 個任務作為評測基準，並在關鍵的「錨點步驟」（3B-q4_K_M vs. 7B-q2_K 比較）中額外加入 HumanEval+ 的五組交替會話配對實驗。選擇 EvalPlus 是因為它擴展並強化了 HumanEval 與 MBPP 的測試案例，能更嚴格地區分看似通過但實際脆弱的解法，從而對量化造成的細微正確性損失更為敏感。HumanEval+ 的加入則用於驗證主要網格（main grid）結果在另一基準上的穩健性，兩者的能耗比率（1.925 vs. 1.956）高度一致，強化了結論的可推廣性。

**Q8：本研究最重要的實驗結果是什麼？「錨點步驟」揭示了哪些反直覺的發現？**
A：本研究最重要的發現是：在 3 GB 預算下，套用「較大模型法則」選擇 7B-q2_K 並不划算——它相較於 2 GB 的 3B-q4_K_M 並無顯著解題增益，卻需耗費 2.03 倍的每解決任務能耗（CPU/GPU/記憶體通道計量）或 1.66 至 1.81 倍的整機功耗。這個「錨點步驟」揭示了兩個反直覺的點：第一，當有效 BPW 低於 3.5 的效能門檻時，模型規模的紅利會被量化損失抵消；第二，開發者若僅看「能跑最大的模型」而忽略能耗代價，會在不自覺中為幾乎不存在的正確性提升付出雙倍能源成本。此外，從 1.5B 規模起，q4_K_M 相較於同規模最高精度的解題數差距均在 90% 信賴區間內小於 3 點，這為「四位元精度幾乎普遍最優」的經驗法則提供了新的實證支持。

**Q9：本研究是否進行了消融或穩健性測試？如何驗證主要結論在不同條件下仍成立？**
A：本研究透過多層次的穩健性測試驗證主要結論。首先，在「錨點步驟」中加入了五組交替會話配對實驗，模擬重複使用情境，得到的能耗比率（1.925）與主網格（1.956）高度吻合。其次，研究比較了兩種能耗計量方式——CPU/GPU/記憶體通道的分項計量與整機功耗計量——結果均顯示 7B-q2_K 的能耗劣勢在 1.66 至 2.03 倍之間，方向一致。此外，所有比較都附上 90% 信賴區間與精確配對檢定，避免僅以點估計下結論。雖然論文未明確以「消融研究」一詞呈現，但透過跨基準（EvalPlus 與 HumanEval+）、跨計量方式與跨重複會話的三重驗證，實質上構成了一組穩健性檢驗。

**Q10：本研究的選擇指南在哪些實際應用場景中能發揮最大價值？**
A：本研究的選擇指南對於在資源受限裝置（如輕薄筆電、小型工作站、邊緣裝置）上部署本地程式碼助手的個人開發者與小型團隊最具價值。具體場景包括：需要在無穩定網路或隱私敏感環境下運行離線程式碼補完的開發者、關注碳足跡並希望將綠色軟體原則落實到 AI 工具鏈中的永續發展團隊，以及為學生或新進工程師配置開發環境時需要在效能與能耗間取捨的教育機構。此外，該指南也適合用於企業內部政策制定，例如規範「推薦員工使用 2 GB 的 3B-q4_K_M 而非 3 GB 的 7B-q2_K」，以在不犧牲正確性的前提下降低組織整體的 AI 工具能耗。

**Q11：本研究對綠色軟體（Green Software）領域與永續 AI 政策有何產品與決策意涵？**
A：本研究對綠色軟體領域的核心意涵在於：將「每解決任務的能耗」從學術指標轉化為可直接操作的模型選擇依據，使開發者能在不下載更大模型、不付出更高能源成本的情況下，獲得幾乎等效的程式碼生成品質。這對永續 AI 政策的制定尤為重要，因為它提供了一個可重現、可審計的量化框架——論文中釋出的每任務結果、功耗日誌與分析腳本讓任何組織都能在自己的硬體上重新驗證推薦。在產品層面，Ollama 等本地模型分發平台可考慮將「每解決任務的能耗」或「能源前緣狀態」納入模型卡（model card），協助使用者做出更明智的下載決策。

**Q12：本研究的成果對程式碼 LLM 與量化技術的整體學術與產業生態有何影響？**
A：本研究的影響體現在三個層面：在學術上，它填補了「跨規模、跨量化配方、結合能耗與正確性」的系統性比較空白，並對「較大模型法則」與「四位元最優法則」兩條經驗法則提供了精細化的邊界條件（3.5 BPW 門檻、q4_K_M 在 1.5B 以上的穩健性）。在產業上，它為本地推論生態系提供了一個以檔案大小為索引的實用決策工具，挑戰了「越大越好」的行銷敘事。在永續發展上，它示範了如何將能耗量測從附帶指標提升為一等公民，與正確性並列為模型評測的核心維度，可能啟發後續研究將此方法擴展至其他模型家族（如 Llama、DeepSeek-Coder）與其他任務領域（如數學推理、對話生成）。

**Q13：本研究存在哪些已承認的限制？其結論的外部效度（external validity）如何？**
A：本研究承認的限制包括：僅測試單一模型家族（Qwen2.5-Coder-Instruct）、單一硬體平台（fanless MacBook Air M2）與單一推論執行環境（Ollama/llama.cpp），因此結論未必能直接外推至其他模型架構、GPU 加速情境或雲端部署。此外，評測僅涵蓋 542 個 EvalPlus 任題與 HumanEval+，對於真實軟體工程任務（如多檔案重構、長脈絡除錯）的代表性有限。能耗量測也未涵蓋閒置時的基礎功耗或模型載入階段的能耗，這些在頻繁切換模型的場景中可能成為不可忽略的開銷。

**Q14：本研究的選擇指南在哪些「失敗案例」或極端情境下可能不適用？**
A：本研究的選擇指南在以下情境可能不適用：第一，當開發者需要極高的單次解題成功率（例如安全關鍵程式碼生成）時，8 GB 的 7B-q6_K 雖能耗較高但提供顯著增益，此時「能源前緣」推薦應讓位於「正確性前緣」。第二，當硬體配備高效能獨立 GPU 時，量化對 GPU 推論速度的影響模式可能與 Apple Silicon 的統一記憶體架構不同，結論可能改變。第三，對於需要極低延遲的互動式編輯情境，每解決任務的能耗可能不如「首 token 延遲」或「吞吐量」重要。第四，當任務類型從函式層級補完擴展到需要長脈絡理解的代理式程式設計時，較大模型的注意力容量優勢可能重新超越量化損失。

**Q15：本研究的未來研究方向為何？作者釋出的資料與腳本如何促成後續研究？**
A：本研究的未來方向包括：將相同方法擴展至其他程式碼 LLM 家族（如 Llama 3、DeepSeek-Coder、Code Llama）以檢驗結論的普適性；納入更多元的工作負載（如 SWE-bench、RepoBench）以反映真實軟體工程任務；探索動態量化或混合精度策略在能源前緣上的表現；以及將能耗模型延伸至訓練階段，探討「訓練一次、推論多次」情境下的生命週期能耗。作者釋出的每任務結果、功耗日誌與分析腳本構成了一個可重現的基準，使後續研究者能在相同硬體上驗證新模型，或在不同硬體上重新繪製能源前緣，從而累積跨平台、跨模型的系統性證據，推動本地 AI 推論朝向更永續的方向發展。

## 實務應用指南

### 適用場景

1. **個人筆電上的離線程式碼助手**：開發者在無網路或低網速環境（如飛機、長途列車、偏鄉駐點）需要程式碼補完、錯誤診斷或函式生成時，可依筆電可用磁碟空間與電池續航，從論文的選擇指南直接挑選對應的 GGUF 檔案，避免反覆試誤。

2. **企業內部開發機的綠色 IT 政策落地**：資訊部門需為數十至數百台開發機統一部署本地 LLM 助手時，可依每台機器的 RAM/SSD 預算（1 GB、2 GB、4 GB、8 GB）批次推送對應的 Qwen2.5-Coder 量化檔，並以「每解決任務的能耗」作為 ESG 報表的量化指標。

3. **CI/CD 與程式碼審查的低成本自動化**：在自架 GitLab 或 Jenkins 環境中，將 1.5B-q4_K_M 或 3B-q4_K_M 作為 PR 自動審查、單元測試生成、靜態分析補充的本地模型，無需依賴雲端 API，可在隔離網路中運作並降低每張工單的推論成本。

4. **教育訓練與程式設計課程**：學校或訓練機構在資源有限的筆電教室（如 Chromebook、舊款 MacBook）部署統一的程式碼助手時，可依教室機型記憶體挑選 1 GB 或 2 GB 級距的檔案，確保全班同時使用仍流暢且不過熱。

5. **邊緣裝置與物聯網閘道器的程式碼生成**：在工業閘道器、路由器或小型 NUC 上執行輕量程式碼任務（如設定檔生成、log 解析腳本），可參考 0.5B 與 1.5B 級距的能耗與正確性資料，挑選在 ARM/x86_64 上仍可接受的量化方案。

### 實作前置條件

**資料面**
- 一份可重現的程式碼評測集（建議使用 EvalPlus 的 HumanEval+ 與 MBPP+ 共 542 題，或自建內部任務集以反映團隊的程式碼風格）。
- 每個候選 GGUF 檔案的「有效每權重位元數（BPW）」清單，因為 Ollama 標籤（如 q4_K_M）並不等於實際位元密度，0.5B-q3_K_M 實際為 5.66 BPW。
- 預先量測的功耗日誌：CPU、GPU、記憶體通道分項功耗，以及整機功耗（whole-system power），用於計算「每解決任務的能耗」。

**運算面**
- 一台與目標部署環境相近的基準機：論文使用無風扇 MacBook Air M2，若部署於 Windows/Linux 筆電或伺服器，需重新量測一次以校正能耗比率。
- llama.cpp 執行環境（GGUF 格式支援）與 Ollama CLI；若要走 CI/CD 整合，需準備可重啟的服務化腳本。
- 足夠的磁碟空間存放 24 個候選檔案（0.5B 至 7B 的 q2_K 至 q6_K 全套），並預留 RAM 給最大候選（7B-q6_K 約 8 GB）。

**技能面**
- 熟悉 GGUF k-quants 配方差異與 llama.cpp 啟動參數（如 `-ngl` GPU offload 層數、context size）。
- 能撰寫或修改 Bash/Python 腳本以批次執行評測、解析結果、計算配對樣本的信賴區間（90% CI）。
- 具備基礎的功耗量測知識（Intel RAPL、Apple powermetrics、或是外接 USB 功耗計），並理解 CPU/GPU/記憶體通道分項與整機功耗的差異。

### 實作步驟建議

1. **定義預算與目標任務集**：先盤點部署機器的可用磁碟或 RAM 預算（0.5/1/2/4/8 GB），並選定要評測的程式碼任務集（建議沿用 EvalPlus 以便與論文對齊）。

2. **下載並標註候選檔案**：從 Ollama 或 HuggingFace 取得 Qwen2.5-Coder-Instruct 在 0.5B、1.5B、3B、7B 四個尺寸下的所有量化檔（q2_K、q3_K_M、q4_K_M、q4_0、q5_K_M、q6_K、q8_0、fp16），並用 `gguf-info` 或論文釋出的腳本計算每個檔的「有效 BPW」。

3. **建立功耗量測管線**：在基準機上以固定取樣頻率（如 100 ms）記錄 CPU/GPU/記憶體分項功耗與整機功耗，並在每次任務推論前後打標，確保能對齊到單一任務的能耗。

4. **執行全網格評測**：每個檔案跑同一份任務集，記錄每題是否通過（pass/fail）、耗時、能耗；對關鍵對照組（如 3B-q4_K_M vs 7B-q2_K）額外執行 5 組交替會話配對，以驗證結果穩定性。

5. **計算「每解決任務的能耗」**：對每個檔案計算 `total_energy / solved_tasks`，並分別在「分項功耗」與「整機功耗」兩種計量下計算比率；同時計算通過率的 90% 信賴區間。

6. **產出選擇指南**：依檔案大小分級（1 GB、2 GB、3 GB、4 GB、8 GB）列出首選與次選，每個推薦附上證據標籤——「重複實驗確認」、「正確性顯著差異」、「僅能耗點估計差距」。

7. **部署與監控**：將首選檔案部署到目標機器，於 CI/CD 或開發環境中串接，並持續監控每千次推論的能耗與通過率，作為後續模型升級或回退的依據。

8. **釋出可重現資產**：將每題結果、功耗日誌、分析腳本公開（如同論文於附錄釋出），讓團隊成員能在不同機器上重現並校正。

### 潛在風險與注意事項

- **「較大模型法則」並非萬能**：論文顯示在 2 GB 至 3 GB 的交界，7B-q2_K（3.16 BPW）相較 3B-q4_K_M 並無顯著正確性增益（90% CI 差距上限僅 2.4 點），但能耗卻高出 1.66 至 2.03 倍。切勿僅憑「模型越大越好」直覺跳級。

- **量化標籤不等於實際位元密度**：Ollama 的 q4_K_M 在 0.5B 模型上僅覆蓋少數張量，實際 BPW 可能遠高於 4；選檔前務必以工具驗證有效 BPW，避免誤判精度。

- **整機功耗與分項功耗的解讀差異**：論文顯示 7B-q2_K 在 CPU/GPU/記憶體分項上是 3B-q4_K_M 的 2.03 倍能耗，但在整機功耗下縮減為 1.66 至 1.81 倍。對外報告時須註明採用哪一種計量，否則容易被質疑灌水或低估。

- **無風扇機型的熱節流效應**：MacBook Air M2 在長時間推論後可能降頻，導致後段任務耗時與能耗偏高；建議在評測前讓機器充分冷卻，或在腳本中加入冷卻間隔。

- **任務集偏誤**：EvalPlus 以 Python 函式為主，若團隊主力語言為 Java、Go、Rust，需自建對應任務集，否則通過率無法直接外推。

- **GPU offload 設定差異**：論文的能耗數據基於特定 `-ngl` 參數，若部署時改變 GPU offload 層數，能耗結構會大幅改變；建議在指南中明確標註推論設定。

- **冷啟動與快取效應**：首次載入模型檔的 I/O 與記憶體配置成本不應計入單題能耗，否則會高估小型檔案的每任務能耗。

### 與其他技術的整合建議

- **VS Code / JetBrains 插件**：透過 Continue、CodeGPT 或 Cody 等支援 Ollama API 的插件，將指南推薦的模型設為預設本地端點；可在插件設定中依使用者筆電規格自動切換 1 GB 或 2 GB 級距。

- **企業 SSO 與權限控管**：將模型檔案放置於內部 artifact registry（如 Artifactory、Harbor），透過 SSO 控制下載權限，並用 audit log 追蹤每位開發者的能耗貢獻。

- **能耗監控儀表板**：將每任務能耗資料匯入 Grafana 或 Prometheus，搭配工單系統（Jira、Linear）計算每張 ticket 的推論成本，作為 FinOps 與綠色 IT 的雙重指標。

- **CI/CD 中的程式碼審查**：在 GitHub Actions 或 GitLab CI 中加入本地 LLM 審查 stage，使用 1.5B-q4_K_M 作為預設模型，並依儲存庫大小自動切換至 3B-q4_K_M。

- **多模型路由**：在內部 API gateway（如 Kong、Envoy）後方部署多個量化模型，依任務難度路由——簡單補完走 0.5B，複雜重構走 3B-q4_K_M，並以「每解決任務的能耗」作為路由成本函數。

- **與靜態分析工具互補**：將 LLM 生成的修補建議與 SonarQube、Semgrep 的結果交叉比對，僅在靜態分析無法涵蓋的語意錯誤上呼叫較大的模型，進一步降低平均能耗。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與 Table II 的選擇指南，理解「檔案大小」與「每解決任務的能耗」兩個核心概念即可；不必急著理解 BPW 與 k-quants 的細節，只要記住「1 GB 選 1.5B-q4_K_M、2 GB 選 3B-q4_K_M、3 GB 不要為了貪大而跳 7B-q2_K」這個結論，就能在自己的筆電上立刻受惠。

**給 AI 工程師**：重點放在 RQ3 的錨點對照（3B-q4_K_M vs 7B-q2_K）與「分項功耗 vs 整機功耗」的計量差異，這是部署本地 LLM 時最常被忽略的成本面；建議在自己的目標機型上重跑一次論文釋出的腳本，並把結果與 CI/CD 的單元測試覆蓋率綁定，作為模型升級的決策依據。

**給研究者**：論文的價值在於把「正確性」與「能耗」放在同一個 Pareto 前緣上比較，並用配對樣本與 90% CI 取代點估計；可進一步延伸的方向包含：跨模型家族（Llama、DeepSeek-Coder）、跨硬體（Apple M 系列 vs Intel/AMD）、跨任務類型（重構 vs 生成 vs 測試寫作）的能耗—正確性前緣比較，以及把「每解決任務的能耗」標準化為綠色軟體的 benchmark。

**給產品經理**：這份論文提供了一個可直接放進產品決策的量化框架——「每 GB 預算能買到多少正確性、多少能耗成本」；建議在規劃本地 LLM 功能時，先以指南的 1 GB 與 2 GB 級距作為 MVP，觀察使用者付費意願與續航滿意度後，再決定是否升級至 8 GB 級距；同時把「每千次推論的能耗」列為對外溝通的綠色指標，有助於企業客戶的 ESG 採購偏好。
