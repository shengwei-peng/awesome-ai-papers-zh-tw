## 摘要翻譯

近期 GPU 核心優化代理將其所學保留於知識庫中，或作為蒸餾技能保存。核心基準測試對每次嘗試的實作評估正確性與速度，但未衡量保留經驗的復用價值。我們提出 MetaKernelBench，用以衡量：自某一核心領域特定語言 (DSL) 的嘗試中所蒸餾出的經驗，能否改善在另一 DSL 中對同一問題的新嘗試。其 74 個問題為六個家族中的融合子圖，每個以一對 CuTe DSL 與 TIRx 變體呈現，兩者僅在 DSL 上有所差異。代理首先單獨嘗試每個變體，並被指示將其所學蒸餾為自然語言技能，無論來源嘗試是否通過驗證，該技能皆會被轉移。該技能是同一模型在另一 DSL 中進行技能條件式嘗試時唯一的額外輸入。我們在匹配的每次嘗試預算下，將每次技能條件式嘗試與同一變體上的單獨嘗試進行比較，評分正確性與端到端執行時間。跨六個模型與兩個方向，相對於單獨嘗試的配對提升範圍從 -19% 至 +29%。四個模型在兩個方向皆有提升，但每個模型與方向中皆有 16% 至 45% 的問題出現退步。結果取決於來源嘗試相對於目標單獨嘗試的表現，而非僅取決於來源是否成功：當來源嘗試表現優於目標嘗試時，71% 的比較中有所改善；而當來源嘗試表現低於目標嘗試時，54% 的比較中出現退步。MetaKernelBench 透過衡量同一問題跨 DSL 核心知識轉移，補足實作品質指標。

### 核心貢獻（3～5點）
- 提出 MetaKernelBench，首個專門衡量「同一問題跨 DSL 核心知識轉移」效果的基準測試，補足既有實作品質指標僅評分單次嘗試正確性與速度的不足。
- 建構涵蓋六個家族、74 個融合子圖問題的測試集，每個問題皆以 CuTe DSL 與 TIRx 兩種變體配對呈現，兩者僅在 DSL 上不同，確保實驗可隔離語言因素。
- 設計「單獨嘗試 → 蒸餾自然語言技能 → 技能條件式嘗試」三階段實驗流程，並以「技能為唯一額外輸入」嚴格控制變因，使測量結果可歸因於知識轉移本身。
- 跨六個模型與兩個方向進行大規模實驗，揭示配對提升介於 -19% 至 +29%，並發現結果取決於來源嘗試相對於目標單獨嘗試的表現（優於時 71% 改善，低於時 54% 退步），而非僅取決於來源是否成功。

### 適合對象
從事 GPU 核心優化、LLM 代理程式碼生成、自動化機器學習編譯（AutoML/Compiler）、以及程式設計語言知識遷移研究的學者與工程師；亦適合關注 AI 代理長期經驗累積與復用機制的研究團隊與業界研發人員。

## 深度分析

#### 方法論解析

MetaKernelBench 提出了一個獨特的評測範式，將焦點從「單次實作的品質」轉向「保留經驗的復用價值」。其方法論核心在於建構一個嚴格控制變數的跨 DSL（Domain-Specific Language，領域特定語言）配對實驗框架。

**任務形式化設計**

每個問題 $p$ 包含三個 DSL 中立的組成部分：(1) 任務描述、(2) PyTorch 參考函式、(3) 固定工作負載下的輸入產生器。對於 DSL $d \in \mathcal{D} = \{\text{CuTe}, \text{TIRx}\}$，任務變體 $\tau_{p,d}$ 僅在共享規格之上加入 $d$ 及其軟體環境。這種設計確保配對變體之間僅 DSL 不同，計算語義、工作負載、硬體（單一 NVIDIA B200 GPU）與驗證規則均固定，從而將「跨 DSL 核心知識轉移」純化為唯一的研究變因。

**核心知識與技能的定義**

作者將「核心知識」（kernel knowledge）定義為問題層級、硬體層級與策略層級的原則，這些原則可獨立於特定 DSL 的語法與 API 表達，例如避免中間張量的物化（materialization of intermediate tensors）、重疊資料搬移與計算（computation overlap）、以及在 Eager PyTorch 與 DSL 核心之間劃分工作。「技能」（skill）則是代理以自然語言記錄其發現的載體（SKILL.md），但並不保證其正確性或對後續嘗試有用。

**配對轉移流程**

流程分為三階段：(1) 對每個變體進行單獨嘗試（solo attempt），代理使用驗證器回饋迭代優化並蒸餾（distill）發現為技能；(2) 將來源技能轉移至另一 DSL 的全新嘗試，僅技能作為額外輸入，來源實作與軌跡（trajectory）均被保留；(3) 在相同變體、相同預算（matched per-attempt budgets）下比較技能條件式嘗試與單獨嘗試，計算配對提升（paired lift）。

**關鍵設計選擇**

值得注意的設計包括：(a) 無論來源嘗試是否通過驗證，技能都會被轉移，使失敗嘗試的發現也能貢獻；(b) 禁止使用其他核心語言、編譯器、CUDA Graphs、參考函式呼叫及 DSL 函式庫匯入的核心，強制代理在受限環境中工作；(c) 採用旁路測試（bypass test）確保 DSL 步驟確實執行必要計算，避免代理以 Eager PyTorch 規避核心開發；(d) 端到端計時涵蓋 Python 派發、Eager 操作與 DSL 核心，反映真實部署情境。

此方法論的精妙之處在於：透過配對同一問題的兩個 DSL 變體，保留了使先前經驗相關的計算與硬體條件，同時改變了核心的表達方式。這避免了「同 DSL 重複問題」會讓 DSL 專屬配方直接套用的混淆，也避免了「換問題」會改變哪些發現仍相關的問題。

#### 實驗數據解讀

**整體提升幅度**

在六個模型與兩個方向（CuTe→TIRx 與 TIRx→CuTe）的單次嘗試比較中，配對提升範圍為 **−19% 至 +29%**。這個範圍揭示了跨 DSL 技能轉移的雙刃特性：技能既能顯著提升表現，也能造成實質退步。

**模型間異質性**

四個模型在兩個方向上均獲得正提升，但每個模型與方向都有 **16% 至 45% 的問題出現退步**。這意味著即使平均表現為正，技能轉移仍對相當比例的個別問題有害。這種異質性凸顯了技能轉移並非普遍有益的機制，而是高度依賴問題與模型的條件性現象。

**決定轉移成敗的關鍵因素**

最重要的發現是：轉移結果取決於來源嘗試相對於目標單獨嘗試的「站位」（standing），而非單純的來源成功與否。具體而言：
- 當來源站位高於目標單獨嘗試時，**71% 的比較獲得改善**
- 當來源站位低於目標單獨嘗試時，**54% 的比較出現退步**

這個非對稱性（71% vs 54%）暗示「好技能」比「壞技能」更容易傳遞正面價值，但負面技能的傷害效應仍不可忽視。

**失敗模式分析**

失敗分析揭示了模型規模與失敗類型的關聯：
- **較大模型**：主要被其所遵循的技能「誤導」（led astray），即接受了技能中不正確的結論並據此行動
- **兩個單獨通過率最低的模型**：主要在自身執行中失敗，而非被技能誤導

這暗示較大模型具有更強的技能遵循傾向，但也更容易被錯誤技能帶偏；較小模型則可能因能力限制而無法有效利用技能。

**技能內容與改善的關聯**

內容分析顯示，含有「不支援的結論並排除替代方案」的技能在受傷害的比較中比在受幫助的比較中更常見（適用於六個模型中的五個）。然而，與改善相關的其他技能內容則因模型而異，顯示沒有單一類型的「好技能」能跨模型通用。

#### 與現有研究的比較

**定位差異**

MetaKernelBench 與現有核心基準測試（如 KernelBench 系列）形成互補關係。傳統基準測試評量單次實作的正確性與加速比（speedup），而 MetaKernelBench 評量的是「保留經驗的復用價值」——這是現有基準完全未觸及但對實際部署至關重要的面向。

**相較於知識庫與技能蒸餾研究的改進**

近期 GPU 核心優化代理（如 Dong et al., 2026; Fu et al., 2026）已開始使用持久化知識庫（persistent knowledge bases）或將成功 rollout 蒸餾為技能。然而，這些工作缺乏對「技能是否真正有用」的系統性測量。MetaKernelBench 透過配對實驗設計填補了這一空白，使研究者能夠量化技能轉移的實際效益。

**相較於跨硬體與跨 DSL 基準的擴展**

Wen et al. (2026) 與 Younesian et al. (2026) 將評測擴展至其他硬體平台、核心 DSL 與未見輸入配置。MetaKernelBench 採取了不同但互補的方向：固定硬體與輸入配置，僅改變 DSL，從而隔離出「跨 DSL 知識轉移」這個特定維度。

**限制與不足**

1. **問題數量有限**：74 個問題分佈於六個家族，雖然足以進行統計分析，但可能無法涵蓋所有核心優化場景
2. **DSL 選擇有限**：僅涵蓋 CuTe DSL 與 TIRx 兩種 DSL，未涵蓋 Triton、CUDA C++ 等其他主流核心語言
3. **單一硬體平台**：僅在 NVIDIA B200 上測試，未涵蓋其他 GPU 架構
4. **預算設定**：40 分鐘預算可能限制了某些需要長時間探索的優化策略
5. **未測試泛化能力**：作者明確指出此設定不測試對新問題、新工作負載或新硬體的泛化能力

#### 可重現性評估

**程式碼與資料可用性**

根據論文提供的資訊，MetaKernelBench 的 74 個問題規格、CuTe DSL 與 TIRx 變體定義、驗證規則與評測流程應隨論文開源。然而，論文中未明確提及程式碼儲存庫連結或具體的開源協議。

**模型權重**

實驗涉及六個模型，但論文未列出具體的模型名稱或版本，這對完全重現實驗構成障礙。研究者需要根據論文中描述的模型特性（如「較大模型」與「兩個單獨通過率最低的模型」）推測具體模型。

**評測環境規格**

論文明確指定了硬體（單一 NVIDIA B200 GPU）、軟體環境（CuTe DSL 與 TIRx 的特定版本）、預算（每次嘗試 40 分鐘、10 次提交）與驗證規則，這些規格的明確性有利於重現。

**可重現性挑戰**

主要挑戰包括：(1) 代理的隨機性可能導致單次嘗試結果變異，需要多次重複以獲得穩定估計；(2) 技能蒸餾的自然語言輸出具有非確定性；(3) 不同模型 API 的差異可能影響實作細節。

#### 未來研究方向

**擴展 DSL 覆蓋**

未來工作可將 MetaKernelBench 擴展至更多核心 DSL（如 Triton、CUDA C++、HIP），建立更全面的跨 DSL 知識轉移評測框架。這將有助於理解不同 DSL 對之間的知識可遷移性差異。

**技能品質分析**

鑑於「不支援的結論並排除替代方案」的技能更常導致傷害，未來可研究自動化技能品質評估方法，例如在轉移前對技能進行驗證或篩選，僅保留高品質技能。

**多步驟轉移**

當前設定僅涉及單次技能轉移。未來可探索多步驟轉移鏈，即技能在多個問題或多次迭代中累積與精化，研究技能組合與演化的動態。

**技能結構化表示**

自然語言技能雖然靈活，但缺乏結構化語義。未來可探索將技能表示為結構化形式（如策略樹、條件規則），以提高轉移的可靠性與可解釋性。

**與人類專家知識對齊**

將代理蒸餾的技能與人類核心優化專家的知識進行對比分析，可揭示代理發現的獨特洞見與人類知識的差距，為人機協作的核心優化流程提供基礎。

**動態預算與早期停止**

鑑於轉移結果高度依賴來源站位，未來可設計自適應預算分配機制，根據來源嘗試的初步表現決定是否繼續技能轉移，以降低退步風險。

**泛化能力測試**

在當前固定問題設定之外，可設計變化的工作負載、輸入規模或硬體配置，測試技能轉移的泛化能力，補捉當前 MetaKernelBench 未涵蓋的維度。

## 論文問答

**Q1：MetaKernelBench 主要解決什麼樣的研究問題？**
A：MetaKernelBench 聚焦於一個先前未被系統性量化的問題：當 GPU 核心優化代理從一次嘗試中蒸餾出經驗後，這些保留的經驗是否真的能在不同領域特定語言（DSL）之間產生實質的復用價值。傳統的核心基準測試只評估單次嘗試所產生的實作在正確性與速度上的表現，卻完全忽略了代理所累積的「保留經驗」能否在後續任務中被有效利用。本文將此問題形式化為「同一問題跨 DSL 核心知識轉移」，並主張這是一個獨立於實作品質的評估維度。

**Q2：為什麼現有的核心基準測試無法衡量這件事？**
A：現有基準（如 KernelBench 系列）主要關注單一嘗試在固定 DSL 下的實作分數，無論是參考實作的加速比還是相對於參考的正確性，都只反映「該次提交」的表現。這類評分機制無法區分一個高分是來自於代理本身的優化能力，還是來自於它從先前任務中繼承了有用的經驗。此外，傳統基準通常只測試單一 DSL，無法觀察經驗在跨語言情境下的轉移效果，因此「保留經驗的復用價值」這個維度長期處於評估盲區。

**Q3：為什麼衡量「保留經驗的復用價值」對領域很重要？**
A：隨著 GPU 核心優化代理日益依賴持久化知識庫與蒸餾技能來加速收斂，理解這些機制是否真的帶來價值變得至關重要。若代理只是把錯誤或無用的結論寫入技能庫，反而可能在後續嘗試中誤導自己，造成退步。MetaKernelBench 提供了一種方法論，能讓研究者區分「代理本身的優化能力提升」與「經驗復用帶來的提升」，這對於設計更可靠的代理架構與避免錯誤累積具有實質意義。

**Q4：MetaKernelBench 的核心方法論是什麼？**
A：核心方法論是「配對變體 + 技能蒸餾 + 配對提升」三步驟。首先，每個問題都被表述為 CuTe DSL 與 TIRx 兩個變體，兩者共享相同的 DSL 中立規格、輸入、GPU 與驗證規則，僅 DSL 不同。接著，代理在「單獨嘗試」中對每個變體進行優化，並被要求將所學蒸餾成自然語言技能（SKILL.md），無論該次嘗試是否通過驗證。最後，僅將來源技能（不含實作或軌跡）作為額外輸入，提供給同一模型在另一 DSL 上的「技能條件式嘗試」，並以配對提升（paired lift）比較兩者的表現差異。

**Q5：本研究相較於過往工作的關鍵創新為何？**
A：關鍵創新在於將「知識轉移」本身作為一個可量化的評估維度，而非僅僅把技能視為代理內部的輔助機制。具體而言，本文設計了一個嚴謹的控制變因實驗：來源實作與軌跡都被刻意保留在目標嘗試之外，僅讓技能跨越 DSL 邊界，從而能純粹衡量「技能蒸餾與使用」的聯合效果。此外，無論來源嘗試成功或失敗，技能都會被轉移，這使得基準能夠捕捉失敗嘗試中可能仍具價值的發現，這是過往工作未曾系統性探討的設計。

**Q6：在設計上有哪些重要的選擇與取捨？**
A：設計上最重要的取捨是選擇「同一問題、跨 DSL」而非「同一 DSL、跨問題」或「跨硬體」。前者會讓 DSL 專屬配方原封不動地轉移，無法測試真正的知識轉移；後者則會改變哪些發現仍然相關，混淆變因。本文刻意固定語義、工作負載、硬體與驗證規則，僅改變 DSL，使計算與硬體條件保持一致，確保觀察到的差異純粹來自於技能轉移。此外，技能以自然語言形式記錄而非結構化資料，這是為了反映真實代理系統中技能的可讀性與可移植性。

**Q7：實驗中使用了哪些模型與基準設定？**
A：實驗涵蓋六個模型，並對兩個方向（CuTe DSL → TIRx 與 TIRx → CuTe DSL）都進行評估，總計 74 個融合子圖問題，橫跨六個家族。每個問題在單獨嘗試與技能條件式嘗試下都使用匹配的代理配置與每次嘗試預算，確保兩者僅在「是否加入技能」這一點上有所不同。評分涵蓋正確性（5 次提交中正確次數）與端到端執行時間的加速比，並以配對提升作為主要比較指標。

**Q8：實驗中最關鍵的結果是什麼？**
A：最關鍵的結果是配對提升在六個模型與兩個方向上呈現高度異質性，範圍從 -19% 到 +29%。雖然有四個模型在兩個方向上都有淨增益，但每個模型與方向都存在 16% 到 45% 的退步問題，顯示技能轉移並非普遍有益。更具洞察力的發現是：結果取決於來源嘗試相對於目標單獨嘗試的「站位」，而非單純的來源成功與否——當來源高於目標時，71% 的比較獲得改善；當來源低於目標時，54% 出現退步。

**Q9：除了主要結果外，有哪些消融或分析性研究？**
A：本文進行了內容分析、案例分析與失敗分析三類補充研究。內容分析顯示，在五個模型中，「帶有排除替代方案的未支持結論」在受傷害的比較中比在受幫助的比較中更常見。失敗分析則揭示一個有趣的模型規模效應：較大的模型主要被自己遵循的技能誤導，而兩個單獨通過率最低的模型則主要在自身執行中失敗，意味著技能對不同規模模型的影響機制不同。

**Q10：在實際應用場景中，MetaKernelBench 能如何被使用？**
A：在實際應用中，開發者可使用 MetaKernelBench 來診斷自家代理的技能蒸餾機制是否真的有效，特別是在多 DSL 環境下的代理系統中。例如，當一個團隊準備讓代理同時支援 CuTe DSL 與 TIRx 時，可以透過此基準量化技能庫是否帶來實質增益，或反而引入雜訊。這也有助於在部署前識別哪些問題類型最容易從技能轉移中受益，進而優化技能的篩選與管理策略。

**Q11：從產品化的角度來看，這項研究帶來哪些考量？**
A：產品化角度上，這項研究提醒我們：技能庫並非「越多越好」，錯誤或過於具體的技能可能造成系統性退步。產品設計時應考慮加入技能品質過濾、來源信心評估，以及在技能與目標問題不相關時主動略過的機制。此外，由於結果高度依賴來源相對於目標的站位，產品可能需要根據目標問題的難度動態調整技能的權重或選擇策略，而非無條件套用所有累積經驗。

**Q12：本研究對 GPU 核心優化領域的整體影響是什麼？**
A：本研究為領域引入了一個全新的評估範式，從「單次實作分數」擴展到「經驗復用價值」，促使研究者重新思考代理架構中持久化記憶的角色。它也凸顯了 DSL 多樣性作為評估維度的重要性，因為僅在單一 DSL 上表現良好的代理未必能跨語言泛化。長期而言，這可能推動領域發展出更精緻的技能蒸餾、篩選與轉移機制，使代理系統在多語言、多硬體環境下更加穩健。

**Q13：本文明確承認的限制有哪些？**
A：本文坦承 MetaKernelBench 並未測試對新問題、新工作負載或新硬體的泛化能力，因為它刻意固定了這些條件以純化變因。此外，基準僅涵蓋兩個 DSL（CuTe DSL 與 TIRx）與單一硬體（NVIDIA B200），因此結論的外推性受限。74 個問題雖然橫跨六個家族，但相對於真實世界中核心問題的多樣性，仍屬於有限樣本。

**Q14：失敗案例揭示了哪些具體問題？**
A：失敗案例顯示，較大模型容易被技能中未經支持的結論誤導，特別是當技能排除了某些替代方案時，模型傾向於直接遵循而不再探索。這種「過度信任技能」的現象可能源於較大模型對自然語言指示的服從性更強。相對地，較小模型則更多在自身執行層面失敗（例如無法正確實作 DSL 核心），顯示技能對它們而言並非主要瓶頸，而是基本能力本身。

**Q15：未來的研究方向有哪些？**
A：未來方向包括：擴展到更多 DSL 與硬體平台，以檢驗跨語言轉移的結論是否普適；研究技能品質的自動評估與篩選機制，特別是如何識別「帶有未支持結論」的技能；探索動態技能選擇策略，根據目標問題特性決定是否啟用特定技能；以及將評估擴展到新問題與新工作負載，測量真正的泛化能力，而非僅限於同一問題的跨 DSL 轉移。

## 實務應用指南

### 適用場景

1. **LLM 核心優化代理的選型與評估**：企業在建構或採購 GPU 核心自動優化系統時，可使用 MetaKernelBench 量化不同 LLM 在「跨 DSL 知識轉移」維度上的能力差異，補足傳統僅看單次實作正確性與加速比的不足，特別適合需要長期累積經驗的內部代理平台。

2. **核心 DSL 遷移專案的決策支援**：當團隊考慮從既有 DSL（如 TIRx）遷移至新 DSL（如 CuTe DSL）時，可利用本基準模擬「帶著舊 DSL 經驗在新 DSL 上重新嘗試」的情境，預估遷移後代理的實際表現落差，並據此規劃人力與訓練投入。

3. **技能蒸餾管線的品質稽核**：對於已部署「將成功 rollout 蒸餾為自然語言技能」機制的代理系統，可將 MetaKernelBench 作為回歸測試套件，定期檢查技能庫中新增技能的轉移效益，識別造成退步的「偽技能」（如錯誤排除替代方案的指引）。

4. **代理記憶體（persistent memory）機制的 A/B 測試**：在比較不同知識庫設計（如向量檢索、圖譜、純文字 SKILL.md）時，可固定模型與 DSL 配對，僅替換記憶體後端，透過配對提升幅度量化各機制對跨任務復用經驗的貢獻。

5. **學術研究中的知識轉移現象分析**：研究人員可利用本基準的 74 個問題與 6 個家族結構，控制計算與硬體條件不變，專注研究「技能內容—轉移成效」之間的因果關係，特別適合探討自然語言技能中哪些語意特徵（如否定式結論、量化指標）預測轉移成功。

### 實作前置條件

**資料需求**
- 74 個融合子圖問題的 DSL 中立規格（任務描述、PyTorch 參考函式、輸入產生器），需以可執行 Python 模組形式提供。
- 每個問題的 CuTe DSL 與 TIRx 兩個變體，僅 DSL 與其軟體環境不同，其餘（語義、工作負載、硬體、驗證規則）完全一致。
- 對應的 GPU 驗證器與 CPU 沙盒腳本，能在固定預算（如 40 分鐘、10 次提交）內回傳正確性（5/5 通過）與端到端加速比。
- 來源 DSL 的官方文件（用於匯入代理的檢索增強生成管線）。

**運算資源**
- 單一 NVIDIA B200 GPU 作為執行環境；端到端計時涵蓋 Python 派發、Eager PyTorch 與 DSL 核心。
- 足夠的 CPU 沙盒資源以支援 6 個模型 × 2 個方向 × 74 個問題 × 2 種嘗試（單獨 vs 技能條件式）的批次執行。
- 建議預留每個問題約 80 分鐘的代理執行時間（單獨與技能條件式各 40 分鐘），全基準完整跑完單一模型約需 200 小時以上。

**技能門檻**
- 熟悉至少一種核心 DSL（CuTe DSL 的 layout algebra 或 TIRx 的 storage layouts）以理解任務變體差異。
- 具備 LLM 代理工程經驗：能配置「單獨嘗試 → 技能蒸餾 → 技能條件式嘗試」三階段管線，並嚴格控制「僅技能為額外輸入」。
- 具備基準評估素養：理解配對設計（matched budgets）、配對提升（paired lift）計算方式，以及來源/目標嘗試相對位階的解讀方式。

### 實作步驟建議

1. **建構 DSL 中立規格層**：將 74 個問題抽象為 `task.py`，內含任務描述、`reference(*inputs)` 與 `make_inputs()`，確保兩個 DSL 變體共用同一檔案，僅在變體層注入 DSL 與其環境。

2. **實作配對變體與驗證契約**：為每個問題產出 `τ_p,CuTe` 與 `τ_p,TIRx` 兩個變體，固定工作負載、輸入產生器、bypass 測試規則與端到端計時邊界；明文禁止 CUDA Graphs、參考函式呼叫與外部核心庫匯入。

3. **設計單獨嘗試管線**：代理在無任何轉移知識下嘗試每個變體，接收 GPU 驗證器的正確性與加速比回饋；嘗試結束時，無論成功與否，皆指示代理將所學蒸餾為 `SKILL.md`（自然語言、無 DSL 語法/API 限制）。

4. **建立技能轉移機制**：將來源變體的 `SKILL.md` 作為唯一額外輸入注入目標變體的全新代理會話；嚴格隱藏來源實作與軌跡，確保「僅技能跨越 DSL 邊界」。

5. **執行配對比較**：在相同代理配置與每次嘗試預算下，計算每個問題的配對提升 =（技能條件式加速比 − 單獨加速比）／單獨加速比，並彙整至模型 × 方向矩陣。

6. **分析來源相對位階**：將每次比較按「來源嘗試相對於目標單獨嘗試的位階（上／下）」分箱，驗證「上階 71% 改善、下階 54% 退步」的模式是否在新模型上重現。

7. **內容與失敗分析**：對造成退步的技能進行質化編碼（如「否定式結論」「錯誤排除替代方案」），並區分「被技能誤導」與「自身執行失敗」兩類失敗模式，產出可行動的技能品質指標。

8. **產品化封裝**：將上述管線容器化，提供 CLI 介面指定模型、方向與問題子集；輸出標準化報告（JSON + Markdown），便於 CI 整合與跨版本回歸比較。

### 潛在風險與注意事項

- **技能內容污染**：若 `SKILL.md` 夾帶來源 DSL 的語法片段或 API 名稱，會繞過「僅 DSL 不同」的控制變因；應在管線中加入 DSL 關鍵字過濾與人工抽樣審查。
- **預算不匹配導致的偽提升**：技能條件式嘗試若獲得更多隱性資源（如更長推理時間），配對提升將無法歸因於技能本身；務必嚴格匹配每次嘗試的提交次數與時間上限。
- **bypass 測試繞過**：代理可能透過巧妙組合 Eager PyTorch 規避 DSL 核心呼叫；驗證器需主動注入「必須由 DSL 核心執行」的計算或資料搬移步驟，並在輸出張量上追溯依賴。
- **小樣本問題的家族偏差**：74 個問題分屬 6 家族，若某家族問題特性極端（如全部偏向資料搬移），模型平均提升可能被少數家族主導；報告應同時呈現家族層級的配對提升。
- **退步案例的歸因混淆**：當技能條件式嘗試失敗時，需區分「代理遵循了錯誤技能」與「代理未採用技能但自身執行失敗」；前者反映蒸餾品質，後者反映模型能力，兩者對系統改進的指引不同。
- **模型版本漂移**：基準結果對模型版本敏感（如同樣 GPT 系列小版本更新即可能改變蒸餾傾向），發布報告時須明確標註模型 checkpoint 與日期，避免跨期比較失真。
- **硬體單一性**：本基準僅在 B200 上驗證，轉移效益可能隨架構（如 Hopper、Blackwell 後續版本）改變；產品化時應保留硬體抽象層以便擴充。

---

### 與其他技術的整合建議

- **與 KernelBench 系列整合**：將 MetaKernelBench 作為 KernelBench 的「轉移維度」擴充層，保留原有單次實作評分，再附加跨 DSL 配對提升指標，形成「實作品質 × 經驗復用」的二維評估卡。
- **與代理框架（LangGraph、AutoGen）整合**：將「單獨嘗試 → 技能蒸餾 → 技能條件式嘗試」封裝為標準化的代理工作流模板，使現有核心優化代理可一鍵啟用轉移評估模式。
- **與向量知識庫整合**：在技能蒸餾後，將 `SKILL.md` 自動嵌入並存入向量庫，支援後續基於語意相似度的技能檢索；可在本基準上 A/B 測試「全文注入」與「檢索式注入」兩種模式。
- **與 CI/CD 整合**：將配對提升作為代理系統發布的品質閘門（quality gate），當新模型或新技能庫導致平均配對提升下降超過閾值時自動阻擋部署。
- **與可觀測性平台整合**：把每次嘗試的軌跡、驗證器回饋與技能內容串接至 OpenTelemetry 或類似平台，支援跨問題、跨模型的時序分析與異常偵測。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦第 1 節的問題動機與圖 1 的管線總覽，理解「為何需要衡量跨 DSL 知識轉移」以及「單獨嘗試與技能條件式嘗試的差異」；數字結果（−19% 到 +29%、71% 與 54%）可作為現象級結論記憶，暫不深入統計細節。

**AI 工程師**：應將重心放在第 2 節的任務形式化與實作步驟，特別是 bypass 測試、預算匹配與「僅技能為額外輸入」的控制變因設計；這些是將基準落地為內部評估平台的工程關鍵，也是診斷自家代理退步案例的檢查清單。

**研究者**：第 1 節末段的「來源相對位階決定轉移成敗」與內容／失敗分析是核心學術貢獻；建議進一步追問「技能中哪些語意特徵預測轉移成功」，並將本基準作為探討自然語言記憶體品質的受控實驗平台。

**產品經理**：應關注「四個模型雙向皆改善、但每個模型皆有 16%–45% 退步」這組數字，理解跨 DSL 知識轉移並非免費午餐；產品定位上可強調「經驗復用價值」作為差異化賣點，但須誠實溝通退步風險，並以本基準作為持續監控的承諾依據。
