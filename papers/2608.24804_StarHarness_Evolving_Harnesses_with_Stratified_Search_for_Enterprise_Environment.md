## ⚡ TL;DR

在工具繁多的企業環境中，固定模型權重難以彌補智慧體套具與環境之間的錯配。
本文提出StarHarness，依基線失敗分層任務並區分搜尋、選擇與保留集，固定模型權重以演化套具。
在三企業基準上，演化套具提升20–35百分點，泛化至保留任務並轉移至GPT、Qwen且減少偽陽診斷。

## 摘要翻譯

我們提出 StarHarness，一個在固定模型權重（model weights）的前提下，演化環境專屬（environment-specific）智慧體套具（agent harness）的框架。演化後的套具可包含提示詞與任務框架（prompt and task framing）、工具介面（tool interfaces）、技能（skills）、MCP 支援的提供者（MCP-backed providers）、子智慧體結構（subagent structure），以及智慧體迴圈配置（agent-loop configuration）。StarHarness 根據基線失敗行為（baseline failure behavior）對任務進行分層，以建構精簡的演化池（evolution pool）；將提案者可見的搜尋任務（proposer-visible search tasks）與提案者隱藏的選擇任務（proposer-hidden selection tasks）加以區分；並將部分任務保留為保留任務（held-out tasks），以評估泛化（generalization）能力。在 ITBench SRE、EnterpriseOps-Gym ITSM 與 AutomationBench Finance 上，套具演化在每個環境經過 4 至 12 個接受的變更（accepted changes）後，完整基準測試效能（full-benchmark performance）相較於預設套具（default harness）提升了 20 至 35 個百分點。這些提升在未納入演化的任務上仍然持續，且無需重新演化即可轉移至 GPT 與 Qwen 模型家族（GPT and Qwen model families）。追蹤分析（trace analysis）顯示，這些改善來自介面修復（interface repairs）、環境慣例（environment conventions），以及能壓縮搜尋空間的營運知識（operational knowledge）；在多個設定中，偽陽性診斷（false-positive diagnoses）更少且軌跡（trajectories）更短。因此，StarHarness 提供了一種實用的方法，可減少工具繁多的企業任務（tool-rich enterprise tasks）中持續存在的模型與環境不匹配（model-environment mismatch）問題。

### 核心貢獻（3～5點）
- 在固定模型權重的前提下，演化環境專屬的智慧體套具，可同時調整提示詞與任務框架、工具介面、技能、MCP 支援的提供者、子智慧體結構與智慧體迴圈配置。
- 提出分層式搜尋機制：依基線失敗行為對任務分層以建構精簡演化池，區分提案者可見的搜尋任務與提案者隱藏的選擇任務，並保留保留任務以評估泛化。
- 在 ITBench SRE、EnterpriseOps-Gym ITSM 與 AutomationBench Finance 三個企業基準測試上，相較預設套具提升 20–35 個百分點的完整基準測試效能。
- 證明演化所得套具在未參與演化的任務上仍具持續效益，且無需重新演化即可跨 GPT 與 Qwen 模型家族轉移。
- 透過追蹤分析揭示效能改善來源：介面修復、環境慣例與營運知識壓縮搜尋，並在多個設定中減少偽陽性診斷與縮短軌跡。

### 適合對象
本論文適合致力於在企業環境中開發與部署大型語言模型智慧體的研究者與工程師，特別是關注工具繁多的企業任務、模型與環境不匹配、提示詞與智慧體架構最佳化，以及跨模型泛化與轉移議題的讀者。

## 深度分析

#### 方法論解析

StarHarness 的核心貢獻在於將「套具（harness）」視為可最佳化的外部程式碼資產，而非僅僅調整模型權重（model weights）或提示詞（prompts）。具體而言，它把智慧體套具（agent harness）定義為圍繞固定語言模型的一組可執行鷹架，涵蓋提示詞與任務框架（prompt and task framing）、工具介面（tool interfaces）與工具綱要（tool schemas）、引數前處理、技能（skills）、MCP 支援的提供者（MCP-backed providers）、子智慧體結構（subagent structure）、脈絡管理、驗證邏輯以及完成邏輯等。這種視角讓「環境專屬的（environment-specific）」適應可以透過版本控制與程式碼審查來管理，而不必重新訓練或微調模型。

其最佳化目標可寫成：

\[
h^* = \arg\max_{h \in H} J(h; D_{\text{holdout}})
\]

其中 \(J\) 是在保留任務（held-out tasks）上的平均任務分數，\(H\) 為允許修改的套具空間。由於演化過程中無法接觸保留任務的結果，StarHarness 採用三層資料劃分來近似此目標：

1. **提案者可見的搜尋任務（proposer-visible search tasks）**：供提案者（proposer）閱讀追蹤（traces）並產生候選修補（patch）。
2. **提案者隱藏的選擇任務（proposer-hidden selection tasks）**：用於客觀評估候選修補，避免提案者直接針對這些任務過度擬合（overfitting）。
3. **保留任務（held-out tasks）**：僅在最終評估時使用，用來衡量泛化（generalization）。

這種劃分類似於機器學習中的訓練／驗證／測試分割，但套具層級的搜尋空間是離散且結構化的，因此需要額外的機制來控制搜尋成本。

為了進一步壓縮搜尋空間，StarHarness 採用**分層式搜尋（stratified search）**：首先依據基線失敗行為（baseline failure behavior）將任務分層，從而構建一個緊湊的演化池（evolution pool）。這意味著系統不會均勻地從所有任務中抽樣，而是優先納入能代表不同失敗模式的任務，例如介面錯誤、狀態相依性（state dependencies）誤判、或領域慣例（domain conventions）遺漏等。這種分層策略能讓少量任務子集（task subsets）即可覆蓋主要的錯誤型態，降低評估開銷。

演化迴圈本身採用**autoresearch pattern**：先測量基線、提出一個有範圍的單一介入、評估、僅在改善時保留，然後從新的 frontier 繼續。具體流程包含：

- **提案階段（proposal）**：提案者閱讀當前套具與搜尋任務的追蹤，產生候選修補。
- **驗證階段（validation）**：檢查修補範圍、匯入正確性，並執行單一任務的煙霧測試（smoke test）。
- **評估階段（evaluation）**：對通過驗證的候選，在隱藏選擇集上執行；若選擇集平均提升，則晉升為新的 frontier，並以驗證器通過率（verifier rate）作為平手時的輔助指標。

一個值得注意的設計是**單一任務翻轉閘門（single-task flip gate）**：在進入昂貴的完整選擇集評估前，先要求候選修補能翻轉（flip）提案者選定的一個失敗任務。這個快速篩選大幅減少了無效修補的評估成本。整個搜尋過程透過**持續性記憶分類帳（persistent memory ledger）**或**解題日誌（solution journal）**記錄修補、會話、評估產物、frontier 分數、每個任務結果、已接受假設與捨棄嘗試，支援樹狀搜尋與後續迭代。

從實作面來看，StarHarness 的優化器（optimizer）本身也是一個「編碼套具（coding harness）」，建構於 OhMyPi 之上；而被最佳化的對象則是 Stirrup 套具。這種「套具演化套具」的設計讓整個流程可自我指涉地迭代，同時保持模型權重與基準測試固定不變。

#### 實驗數據解讀

論文在三個互補的企業環境（enterprise environments）上進行評估：

1. **ITBench SRE**：40 個 Kubernetes 根本原因分析（root-cause analysis）情境，智慧體需檢視警報、事件、追蹤、指標與拓樸，並輸出結構化診斷。
2. **EnterpriseOps-Gym ITSM**：103 個 IT 服務管理（IT Service Management）工作流程，涵蓋事件、問題、變更、知識與使用者管理，最終狀態由 SQL 資料庫斷言（database assertions）驗證。
3. **AutomationBench Finance**：100 個橫跨 47 個模擬 SaaS 應用程式的財務工作流程（multi-application finance workflows），以程式化狀態檢查（programmatic state checks）評分。

實驗結果顯示，經過 4 到 12 個接受的變更（accepted changes）後，演化後的套具在完整基準測試效能（full-benchmark performance）上比預設套具（default harness）提升 20–35 個百分點。這個數字有幾層意義：

- **樣本效率**：相較於需要數百或數千次試誤的強化學習或提示詞搜尋，StarHarness 僅需個位數到十餘次成功修改即可達成顯著提升，顯示分層式搜尋確實有效壓縮了搜尋空間。
- **泛化能力**：提升不僅出現在演化時使用的任務上，也出現在保留任務（held-out tasks）上。這表示學到的修補並非單純記憶特定任務的解法，而是捕捉了環境層級的通用結構。
- **跨模型遷移**：演化後的套具無需重新演化即可在 GPT 與 Qwen 模型家族（GPT and Qwen model families）之間遷移。這點非常重要，因為它暗示套具層級的專業化與模型權重相對解耦，企業可以在一個模型上投資套具工程，再部署到其他模型。

追蹤分析（trace analysis）進一步將效能提升歸因於三類反覆出現的環境專業化：

1. **介面修復（interface repairs）**：修正工具介面或引數前處理，使智慧體能夠發出有效的工具呼叫。
2. **環境慣例（environment conventions）**：補充工具綱要（tool schemas）中未明載的領域慣例（domain conventions），例如特定欄位命名、狀態轉換順序或必填欄位。
3. **壓縮搜尋的營運知識（operational knowledge that compresses search）**：將領域經驗編碼為技能或子智慧體結構，減少智慧體在龐大工具介面（large tool surfaces）中的試誤。

這些改變也帶來行為層級的改善：偽陽性診斷（false-positive diagnoses）減少，軌跡（trajectories）縮短。這不僅提升正確率，也降低推論成本與延遲，對企業部署具有實務價值。

不過，論文對於「20–35 個百分點」的絕對基準水準著墨較少。若預設套具的基線正確率很低，20–35 個百分點的提升雖然顯著，但最終絕對效能可能仍未達生產可用門檻。此外，不同環境所需的接受變更數量不同（4–12 次），暗示某些企業環境的套具缺口較大，或搜尋空間更複雜。

#### 與現有研究的比較

StarHarness 定位於提示詞最佳化（prompt optimization）與智慧體架構方法（agent-architecture methods）之間的狹窄地帶。傳統提示詞最佳化主要搜尋提示詞與示範樣本，而智慧體架構方法則擴展到可執行模組（executable modules）與工作流程結構（workflow structure）。StarHarness 更進一步，將搜尋空間擴大到包含 MCP 支援的提供者、子智慧體結構、智慧體迴圈配置（agent-loop configuration）等可執行鷹架，但同時保持模型權重固定。

與 Meta-Harness 等近期系統相比，StarHarness 的評估協議更為嚴格。Meta-Harness 雖在文字分類與數學推理上使用保留集，但在 TerminalBench-2 上卻在同一 89 項任務上搜尋並報告最終效能，作者將其框定為「發現情境（discovery setting）」。相對地，StarHarness 採用任務層級分離、提案者隱藏選擇集與保留評估，能更清楚區分搜尋表現與泛化表現，回應了近期對更嚴格套具演化評估的呼籲。

相較於 WorkArena、Terminal-Bench 2.0 等基準，StarHarness 選擇的三個企業基準更強調具狀態後端（stateful backends）、龐大工具介面、跨步驟相依性（cross-step dependencies）與最終狀態需求（final-state requirements）。這些特性讓其方法更貼近真實企業服務管理與財務工作流程，而非單純的問答或命令列任務。

然而，StarHarness 也有其限制：

- **搜尋空間的複雜度**：雖然分層式搜尋壓縮了任務數量，但套具空間本身仍可能極大，且候選修補的語法與語意正確性需要依賴驗證器與煙霧測試。
- **對提案者能力的依賴**：提案者必須能從追蹤中診斷失敗並產生合理修補。若基線模型本身無法理解複雜的企業領域，提案品質可能受限。
- **環境專屬性與可維護性**：雖然論文強調套具變更是可測試、可回復的程式碼變更，但過度專精於特定環境的套具可能增加長期維護負擔，特別是當後端系統升級或工具綱要改變時。
- **未與權重更新方法直接比較**：論文未比較將相同領域知識透過微調或強化學習寫入模型權重的效果，因此無法斷言套具演化在所有情境下都是最佳策略。

#### 可重現性評估

從論文提供的資訊來看，可重現性（reproducibility）處於中等水準。方法章節提到 StarHarness 的優化器建構於 OhMyPi，而被演化的對象是 Stirrup 套具，後者由 Artificial Analysis 提供。這些都是具名的實作元件，但論文並未提供明確的開源連結、版本號或完整的程式碼倉儲資訊。

三個評估基準——ITBench SRE、EnterpriseOps-Gym ITSM、AutomationBench Finance——在文中均有引用，但同樣未說明是否公開可取得、授權條款或確切資料版本。對於企業環境基準而言，這尤其重要，因為它們通常涉及具狀態後端與模擬 SaaS 應用程式，重現整個執行環境的門檻較高。

模型權重（model weights）部分，由於 StarHarness 刻意保持其固定，因此只要使用相同的 GPT 或 Qwen 模型家族版本，原則上即可複製。但論文未詳細說明使用的具體模型版本、溫度（temperature）、最大步數、或呼叫 API 的設定，這些細節會影響追蹤與最終分數。

實驗結果的再現還面臨一個結構性挑戰：套具演化是隨機或半隨機的搜尋過程，即使使用相同的初始套具與任務集，不同執行可能產生不同的接受變更序列。論文雖提到確定性晉升規則，但未說明提案者的隨機種子、重複次數或誤差範圍。若要提升可重現性，建議未來工作補充：

- 完整的開源程式碼與相依套件清單。
- 基準環境的容器化或虛擬機映像。
- 每次實驗的隨機種子與多次執行的統計區間。
- 演化過程中所有接受與拒絕修補的完整日誌。

#### 未來研究方向

StarHarness 開啟了幾個值得後續探索的方向：

1. **多環境聯合演化**：目前論文針對單一企業環境分別演化套具。未來可研究如何讓單一套具同時適應多個環境，或透過遷移學習將一個環境學到的介面修復與慣例轉移到另一個相似環境，進一步降低每個新環境的演化成本。

2. **線上持續適應**：現有方法似乎是離線批次演化。在真實企業場景中，後端系統、工具綱要與業務規則會持續演變。研究如何讓套具在生產環境中偵測效能衰退並自動觸發局部演化，將大幅提升實用性。

3. **與模型權重更新的混合策略**：雖然 StarHarness 強調固定模型權重，但未來可探討套具演化與輕量級微調、提示詞調整或強化學習的互補性。例如，先以套具演化修復介面與慣例問題，再針對殘餘的推理錯誤進行模型層級更新。

4. **可解釋性與安全性**：隨著套具變得越來越複雜，理解每個接受變更為何有效、是否引入潛在風險變得重要。未來可發展自動化的影響分析與人類可讀的變更摘要，並將安全約束（例如禁止某些工具組合或狀態變更）納入演化目標。

5. **更嚴格的統計評估**：目前結果主要報告平均任務分數的提升。未來可加入跨多次獨立演化的變異數分析、不同分層策略的消融實驗，以及對保留任務與選擇任務之間效能差距的系統性研究，以量化過度擬合的風險。

6. **擴展到更多企業領域**：除了 SRE、ITSM 與財務流程，未來可將 StarHarness 應用於人力資源、供應鏈、客戶關係管理等領域，並建立跨領域的企業智慧體套具資料庫，促進領域慣例與營運知識的共享。

## 論文問答

【背景與動機】

**Q1：在工具繁多的企業任務中，智慧體面臨的核心挑戰是什麼？**
A：核心挑戰是模型與環境之間持續存在的不匹配（model-environment mismatch），因為企業後端通常具狀態、工具介面龐大，且跨步驟相依性與領域慣例往往未完整寫在工具綱要中。套具（harness）決定了智慧體如何解讀狀態、呼叫工具與滿足最終狀態檢查，因此設計不良會導致即使模型能力足夠也無法完成任務。這種不匹配在 IT 服務管理、網站可靠性工程與財務自動化等需要精確狀態變更的場景特別明顯。

**Q2：現有的提示詞最佳化或智慧體架構方法為何難以直接解決企業環境的問題？**
A：現有方法多聚焦於提示詞、示範樣本或部分可執行模組的搜尋，較少針對具狀態後端、大型工具介面與環境專屬慣例進行整體調整。許多系統會同時改變模型權重或政策，使得修改難以像普通程式碼一樣測試與回滾。相較之下，StarHarness 在固定模型權重的情況下，把提示詞、工具介面、技能、MCP 提供者、子智慧體結構與執行迴圈都納入可編輯範圍，直接修補模型與環境的介面落差。

**Q3：為什麼在演化套具時保持模型權重固定具有實務重要性？**
A：固定模型權重讓所有演化出來的修改都停留在可執行腳手架層，能夠像一般程式碼變更一樣進行版本控制、審查與復原。這對企業部署至關重要，因為重新訓練或微調大型語言模型成本高昂，且可能影響其他任務的表現。此外，外部化的套具修改更容易跨模型家族轉移，例如從 GPT 到 Qwen，而無需針對每個模型重新演化。

【方法與創新】

**Q4：StarHarness 所謂的「套具演化」具體涵蓋哪些搜尋空間？**
A：套具演化是指在外部迴圈中最佳化圍繞固定語言模型的可執行套具，搜尋空間包括提示詞與任務框架、工具定義與綱要、引數前處理、技能、MCP 支援的提供者、子智慧體結構、上下文管理、驗證邏輯與完成邏輯等。這些元件共同決定智慧體如何推理、採取行動與解讀外部狀態，因此比單純調整提示詞更能處理複雜的企業流程。StarHarness 透過 OhMyPi 編碼套具作為最佳化器，對目標 Stirrup 套具提出並套用修補。

**Q5：分層式搜尋與三種任務切分如何協助避免過度擬合？**
A：StarHarness 首先依據基線失敗行為將任務分層，建立緊湊的演化池；接著將任務分為提案者可見的搜尋任務、提案者隱藏的選擇任務，以及最終保留的評估任務。這種切分確保提案模型在搜尋時能觀察失敗軌跡以產生修補，但無法利用選擇集的分數來過度調整，而保留任務則提供真正的泛化指標。如此一來，套具的改進必須在看不見的任務上也能成立，才能被接受。

**Q6：演化迴圈中的「單一任務翻轉閘門」與確定性晉升規則有何作用？**
A：每個候選修補先經過提案者選定的單一任務測試，若無法翻轉該任務的結果，則直接拒絕並跳過昂貴的完整評估，從而節省計算資源。通過閘門的候選才會在隱藏選擇集上評估，並且只有在選擇集平均表現提升時才會被接受，必要時才以驗證器通過率作為打破平局的依據。這種 autoresearch 風格的迴圈搭配持久化記憶帳本，確保每次只從當前前沿進行一個有界干預，逐步累積穩定的改進。

【實驗與結果】

**Q7：論文使用了哪三個基準測試，它們各自評估什麼能力？**
A：ITBench SRE 包含 40 個 Kubernetes 根本原因分析情境，要求智慧體檢視警報、事件、追蹤、指標與拓樸後給出結構化診斷。EnterpriseOps-Gym ITSM 提供 103 個會改變狀態的 IT 服務管理工作流程，並以 SQL 資料庫斷言檢查 ServiceNow 的最終狀態。AutomationBench Finance 則包含 100 個橫跨 47 個模擬 SaaS 應用程式的財務工作流程，透過程式化狀態檢查評分，三者共同涵蓋營運遙測、狀態變更與多應用協作。

**Q8：實驗中的關鍵量化結果是什麼？**
A：在三個基準測試上，經過 4 到 12 個被接受的變更後，演化後的套具比預設套具在完整基準測試效能上提升 20 至 35 個百分點。更重要的是，這些增益在演化過程中完全未接觸的保留任務上依然存在，顯示改進並非過度擬合搜尋集。此外，演化後的套具無需重新演化即可在 GPT 與 Qwen 模型家族之間轉移，展現良好的模型遷移能力。

**Q9：追蹤分析揭示了哪些具體的改進機制？**
A：追蹤分析歸納出三種反覆出現的環境專門化形式：介面修復、環境慣例的學習，以及能壓縮搜尋空間的營運知識。這些改變使智慧體在若干設定中產生更少的偽陽性診斷，並縮短行動軌跡，代表不僅正確率提升，效率也有所改善。例如，修補工具介面或納入領域約束後，智慧體能更快收斂到正確的根本原因或工作流程終態。

【應用與影響】

**Q10：StarHarness 在實務上最適合應用在哪些企業場景？**
A：最適合的場景包括需要操作大量領域工具且對最終狀態有嚴格要求的企業流程，例如 IT 服務管理中的事件與變更單處理、網站可靠性工程中的故障診斷，以及財務部門跨多個 SaaS 應用程式的自動化對帳與報表流程。在這些場景中，工具綱要往往無法完整表達領域慣例與策略約束，透過套具演化可以補足這些缺失。由於不需要重新訓練模型，企業能針對每個環境快速迭代專屬套具。

**Q11：若要在產品中導入 StarHarness，需要哪些技術與流程考量？**
A：產品團隊需要建立一個可重複執行的基準測試與評估管線，並將目標套具設計為可被外部最佳化器讀取與修補的程式碼倉庫，例如論文中的 Stirrup 套具。最佳化器本身以 OhMyPi 編碼套具為基礎，負責提出候選修補、執行範圍檢查與單一任務煙霧測試，再於隱藏選擇集上評估。由於所有修改都是普通程式碼變更，團隊可以將其納入版本控制、程式碼審查與漸進式部署流程，降低上線風險。

**Q12：這項研究對企業智慧體領域可能帶來什麼長遠影響？**
A：StarHarness 提供了一種實用的方式，讓企業在不必承擔重新訓練模型成本的前提下，持續縮小模型與特定環境之間的落差。這有助於提升工具繁多企業任務的可靠性與可維護性，並讓同一套環境專屬最佳化能跨模型重複使用。長遠來看，這種「套具即程式碼」的演化範式可能成為企業部署大型語言模型智慧體的標準環節，類似現今的持續整合與測試文化。

【限制與未來】

**Q13：論文承認的方法限制有哪些？**
A：儘管分層式搜尋能建立緊湊的演化池，但它可能遺漏某些罕見或僅在保留集中出現的失敗模式，導致無法完全保證泛化。此外，每次候選都需執行基準評估，即使單一任務閘門能過濾部分無效提案，整體搜尋仍需要可觀的計算資源。目前評估也僅涵蓋三個企業領域，對於更廣泛的環境多樣性與更長期的線上漂移，方法的有效性仍需進一步驗證。

**Q14：在哪些情況下 StarHarness 可能無法修復智慧體的失敗？**
A：當失敗根源來自模型本身的能力限制，例如需要超出目前模型所能提供的複雜推理或世界知識時，單純調整套具無法解決問題。此外，若候選修補僅能通過單一任務翻轉閘門，卻在隱藏選擇集上造成平均表現下降或引發新的錯誤模式，則會被拒絕。某些任務可能涉及動態變化的環境狀態或安全策略，若這些變化無法在演化池中充分取樣，套具也難以學到穩定的對應規則。

**Q15：未來研究可以朝哪些方向延伸？**
A：未來可以將套具演化與輕量模型微調或適配器結合，同時探索外部套具與內部模型能力的聯合最佳化。另一方面，可發展更豐富的提案策略，例如讓多個提案者並行探索不同修改方向，或引入多目標準則同時考量正確率、延遲與成本。此外，線上持續適應與安全約束的整合也是重要方向，使套具能在生產環境中隨環境漂移自動更新，同時避免產生有害或違反政策的行為。

## 實務應用指南

### 適用場景

1. **企業 ITSM 狀態變更自動化**  
   在 ServiceNow 或類似平台中，智慧體需要執行開單、派工、變更請求、知識庫更新等會改變後端狀態的工作流程。StarHarness 可針對這類環境專屬的資料庫斷言與領域慣例，演化出正確的工具介面與任務框架。

2. **SRE 根本原因分析輔助**  
   面對 Kubernetes、雲端監控與營運遙測資料，智慧體必須從 alerts、metrics、traces、topology 中收斂診斷。透過分層式搜尋，StarHarness 能修復工具介面、減少偽陽性診斷，並縮短推理軌跡。

3. **跨應用程式財務流程自動化**  
   例如應付帳款、對帳、報表產出等橫跨多個 SaaS 或內部系統的流程，常因各系統的程式化狀態檢查與 API 慣例而失敗。演化後的套具可學會環境慣例，提升多應用程式財務工作流程的成功率。

4. **內部工具或舊系統的 API 適配**  
   當企業內部後端、遺留系統或 MCP 支援的提供者的工具綱要不完整時，可用 StarHarness 自動調整引數前處理、技能封裝與子智慧體結構，降低模型與環境不匹配。

5. **模型不變、僅調整互動層的部署情境**  
   若受限於合規、成本或延遲而無法微調模型權重，但希望提升智慧體在特定企業環境的表現，就適合採用套具演化而非模型訓練。

### 實作前置條件

- **資料與環境**
  - 可重複執行的目標基準測試或沙箱環境（如 ITBench、EnterpriseOps-Gym、AutomationBench 或企業自建的同構測試集）。
  - 基線套具的完整追蹤紀錄（trace），包含成功與失敗軌跡，以便依基線失敗行為進行分層。
  - 保留任務（held-out tasks）必須與搜尋任務、選擇任務分開，且演化過程中不可洩漏答案給提案者。

- **運算資源**
  - 能夠反覆呼叫 LLM API 的預算，因為每次提案、驗證與評估都會消耗 token。
  - 可並行執行多筆任務評估的運算節點，建議具備 CI 等級的執行環境。
  - 版本控制與構件儲存空間，用於保存每個候選修補、評分與記憶帳本。

- **技能與團隊**
  - 熟悉 Python 與智慧體套具程式碼（如 OhMyPi / Stirrup 或自研 harness）。
  - 具備提示詞工程、工具綱要設計、MCP 協定與子智慧體結構的實作經驗。
  - 至少一位熟悉目標企業領域（ITSM、SRE、財務流程）的營運或領域專家，以判斷演化結果是否合理。

---

### 實作步驟建議

1. **建立可量測的基線**  
   在預設套具上執行完整基準測試，記錄每筆任務的分數、軌跡、驗證器回饋與失敗模式。這是後續分層與泛化評估的依據。

2. **劃分任務集合**  
   將任務分為三組：提案者可見的搜尋任務、提案者隱藏的選擇任務，以及完全保留的 held-out tasks。分層時可依失敗模式（例如工具呼叫錯誤、狀態檢查失敗、偽陽性診斷）進行分層式取樣，確保演化池緊湊且具代表性。

3. **定義套具的編輯表面**  
   明確允許演化的範圍：提示詞與任務框架、工具介面與綱要、引數前處理、技能、MCP 支援的提供者、子智慧體結構、智慧體迴圈配置、驗證與結束邏輯等。同時列出禁止更動的項目（如模型權重、基準測試答案）。

4. **執行演化迴圈**  
   採用 autoresearch 模式：每次只提案一個有範圍的變更，先通過單一任務翻轉測試（flip test）與語法／匯入驗證，再於隱藏選擇集上評估；只有提升選擇集平均分數才晉升為新的 frontier。持續將修補、分數、失敗狀態寫入記憶帳本。

5. **泛化與模型遷移驗證**  
   在 held-out tasks 上評估最終套具，確認完整基準測試效能提升。接著在不重新演化的情況下，將套具套用至其他模型家族（如 GPT 與 Qwen），檢驗跨模型遷移能力。

6. **部署為一般程式碼變更**  
   將接受的變更視為普通程式碼修補，透過 PR/MR 審查、單元測試與回滾機制併入生產套具。持續監控實際軌跡，並定期重新執行保留任務以偵測環境漂移。

### 潛在風險與注意事項

- **對選擇集的過度擬合**  
  即使保留 held-out tasks，若選擇集過小或與真實分佈差異過大，仍可能學到只對選擇集有效的捷徑。建議選擇集涵蓋多種失敗模式，並以保留任務作為最終閘門。

- **提示詞膨脹與維護成本**  
  演化可能不斷追加提示詞與技能，導致套具臃腫、token 成本上升。應定期審查接受的變更，刪除無效或重複的規則，並將通用知識整理為可維護的技能模組。

- **工具綱要與環境慣例漂移**  
  企業後端 API、欄位語意或策略約束會隨時間改變。演化結果應納入版本控制，並與後端變更通知聯動，避免已修復的介面再次失效。

- **偽陽性診斷與副作用**  
  在 SRE 或 ITSM 場景中，錯誤的診斷或狀態變更可能觸發真實營運風險。建議在沙箱中充分驗證，並對狀態變更動作加上人工核准或影響範圍限制。

- **演化成本與收斂不確定性**  
  每次迭代都需執行多筆任務評估，成本可能快速累積。可先設定最大迭代次數與預算上限，並在連續數次未改善時提前停止。

### 與其他技術的整合建議

- **CI/CD 與版本控制**  
  將 StarHarness 的演化迴圈視為自動化實驗管線：每次接受的變更產生一個修補分支，經由標準程式碼審查、單元測試與基準測試閘道後才合併。

- **可觀測性與追蹤分析**  
  整合現有的追蹤系統（如 OpenTelemetry、LangSmith、自研 trace store），持續收集軌跡並回饋至分層式搜尋，讓介面修復與營運知識能夠被量化與重現。

- **MCP 提供者註冊中心**  
  若企業已採用 Model Context Protocol，可將演化後的技能與 MCP 支援的提供者統一註冊，讓不同智慧體共享環境專屬的適配層。

- **現有 ITSM / SRE / 財務系統**  
  針對 ServiceNow、Kubernetes、財務 SaaS 等系統，建議透過官方 API 或現有 RPA 連接器暴露工具，再由 StarHarness 調整智慧體套具的呼叫方式，而非取代既有後端。

- **安全與治理護欄**  
  結合權限控管、輸出過濾與人工迴路（human-in-the-loop），特別是對於會改變狀態的工具呼叫，確保演化後的套具不會繞過現有合規機制。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦於「適用場景」與「實作步驟建議」，理解 StarHarness 是一種「不修改模型權重、只調整智慧體周邊配置」的技術；遇到分層式搜尋或 MCP 等術語時，可先對照文末詞彙表，不必深究演算法細節，重點是知道它能解決哪些企業任務失敗。

- **AI 工程師**  
  請仔細閱讀方法章節與實作步驟，特別是搜尋任務、選擇任務與保留任務的分離設計，以及 autoresearch 演化迴圈的實作細節；這有助於你在自家 harness 上複現，並避免常見的過度擬合與提示詞膨脹問題。

- **研究人員**  
  本文的貢獻在於提出緊湊的失敗模式分層演化協定，並以任務層級分離與跨模型遷移實驗來衡量泛化；建議關注實驗設計、保留任務的設定，以及追蹤分析中歸納出的介面修復、環境慣例與營運知識三種學習形式。

- **產品經理**  
  重點看適用場景、風險與整合建議：StarHarness 能讓同一套模型在不同企業環境中表現更好，且變更可像程式碼一樣審查與回滾；但需預留評估預算、沙箱環境與領域專家參與，並注意狀態變更動作的安全與合規風險。
