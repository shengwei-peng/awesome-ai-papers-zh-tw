## 摘要翻譯

配備終端機存取能力的大型語言模型（LLMs）已展現出自動化軟體工程任務的強大能力。然而，現有代理在長時程工作流程上仍表現脆弱，因為它們必須反覆重建散佈於原始碼檔案、配置、測試、依賴項及執行期行為中的程式狀態，導致互動歷史日益增長、上下文爆炸及語義漂移。大型儲存庫更進一步增加了識別任務相關元件的難度。為解決這些挑戰，我們提出開發原語（Dev-Primitives，Development Primitives），這是一種模組化且可執行的抽象概念，能將儲存庫元件從被動的軟體構件轉變為軟體工程中的主動參與者。每個開發原語將一個儲存庫構件與一個駐留式大型語言模型配對，使該構件擁有一個奠基於自身實作與依賴關係的代理原生介面，進而實現自然語言推理、元件間通訊及局部自我修改。基於開發原語，我們提出 HERMES——一個透過模組化可執行開發原語進行軟體工程的框架工程方法，該方法透過依賴感知動態啟動機制及一個將執行證據映射回必須修訂之元件的錯誤診斷機制，在儲存庫規模下實例化這些原語。在四個軟體工程基準測試上的大量實驗表明，HERMES 平均比匹配基線框架高出 12.4%。此外，當搭配強大的啟動模型與診斷模型時，即使使用 Qwen3-8B 開發原語，HERMES 在所有四個基準測試上與同質化 GPT-5.6 Sol 配置的差距仍保持在 4.5% 以內，同時在 Terminal-Bench 4.0 上將推論成本降低 26.2%，凸顯了框架設計在軟體工程代理中的重要性。

### 核心貢獻（3～5點）
- 提出**開發原語（Dev-Primitives）**抽象概念，將儲存庫元件從被動的軟體構件轉變為具備代理原生介面的主動參與者，使其能進行自然語言推理、元件間通訊與局部自我修改。
- 提出 **HERMES 框架工程方法**，透過依賴感知動態啟動機制與錯誤診斷機制，在儲存庫規模下實例化開發原語，有效緩解長時程工作流程中的上下文爆炸與語義漂移問題。
- 在四個軟體工程基準測試上的實驗結果顯示，HERMES 平均比匹配基線框架高出 **12.4%**，驗證了框架設計的實質效益。
- 當搭配強大的啟動模型與診斷模型時，即使採用 Qwen3-8B 開發原語，HERMES 在所有四個基準測試上與同質化 GPT-5.6 Sol 配置的差距仍保持在 **4.5%** 以內，同時在 Terminal-Bench 4.0 上將推論成本降低 **26.2%**，證明異質模型配置亦能兼顧效能與效率。

### 適合對象
從事大型語言模型驅動之軟體工程代理研究的學者與研究生、自動化軟體修復與程式碼遷移工具的開發者、軟體儲存庫規模化維運的工程實務者，以及對代理架構設計、框架工程與模型異質配置策略感興趣的產業界研究者。

## 深度分析

#### 方法論解析

本論文提出了一套名為 HERMES（Harness Engineering framework for software engineeRing via Modular Executable Dev-PrimitiveS）的框架工程方法，核心創新在於將軟體儲存庫中的被動構件（passive artifacts）轉化為具備主動推理能力的「開發原語」（Dev-Primitives, Development Primitives）。以下從三個層次深入剖析其方法論。

**一、開發原語（Dev-Primitives）的設計理念**

傳統的軟體工程代理（software engineering agents）無論是流水線式方法（pipeline-based methods，如 Agentless、AutoCodeRover）還是代理式方法（agent-based methods，如 SWE-agent、OpenHands），都將整個儲存庫視為一個被動的程式碼集合，由單一或集中式的大型語言模型（LLM）透過終端機存取來反覆檢查、修改與執行。這種模式在長時程工作流程（long-horizon workflows）中會遭遇三個瓶頸：上下文爆炸（context explosion）、語義漂移（semantic drift）以及分散式程式狀態（distributed program state）的反覆重建。

Dev-Primites 的核心洞見在於：將「推理能力」綁定到「構件本身」，而非綁定到「任務角色」或「檔案層級的工作單元」。每個 Dev-Primitive 由兩個部分組成：(1) 一個儲存庫構件（repository artifact），例如某個原始碼檔案、配置檔、測試案例或執行期元件；(2) 一個駐留式大型語言模型（resident LLM），該模型讀取並理解其所屬構件的實作內容與依賴關係。這種設計使構件獲得一個「代理原生介面」（agent-native interface），能夠：

- 以自然語言方式被定址與詢問；
- 對自身的實作與依賴進行推理；
- 與其他 Dev-Primites 進行元件間通訊（inter-component communication），交換需求與約束；
- 進行局部自我修改（localized self-modification），在不離開其所屬構件語境的情況下調整實作。

這個抽象的關鍵在於「資訊所有權」（information ownership）的重新分配：元件特定的資訊與推理保留在擁有該資訊的構件中，避免了傳統代理中所有資訊都必須被塞入單一互動歷史的問題。

**二、HERMES 框架的兩大機制**

僅有 Dev-Primites 並不足以解決規模化問題。一個大型儲存庫可能包含數千個元件，若全部啟動將造成資源浪費。HERMES 因此引入兩個關鍵機制：

**(1) 依賴感知動態啟動機制（Dependency-Aware Dynamic Activation Mechanism）**

此機制負責決定哪些 Dev-Primites 應被實例化以處理當前任務。其運作流程為：

- **候選集定位**：根據任務描述（例如錯誤報告、功能需求），識別最可能實作相關行為的元件作為種子節點；
- **依賴展開**：沿著依賴關係（呼叫者、被呼叫者、配置檔、測試案例）向外擴展，納入可能需要同步修改的相關元件；
- **實例化與協商**：僅在這個候選集中實例化 Dev-Primites，這些原語在儲存庫執行前先修改其構件並交換需求。

這種設計避免了「全儲存庫啟動」的資源浪費，同時確保了修改的一致性——因為依賴鏈上的元件會主動溝通彼此的需求。

**(2) 錯誤診斷機制（Bug Diagnosis Mechanism）**

單一輪次的修改往往無法完全解決問題，而執行回報通常只告訴代理「儲存庫仍然失敗」，卻不指出哪個元件需要修改。錯誤診斷機制將執行證據（execution evidence，例如測試失敗訊息、堆疊追蹤、執行期錯誤）映射回應被修訂的元件，並僅重新啟動這些相關的原語，重複此過程直到儲存庫通過測試或修訂預算耗盡。

這個機制本質上是一個「閉環回饋系統」：執行→診斷→局部重啟動→再執行，將長時程任務分解為一系列較小的、範圍明確的修改迭代。

**三、與傳統範式的根本差異**

論文明確指出，現有系統與 Dev-Primites 的關鍵差異在於「推理能力所附著的單元」：

- 傳統多代理系統將工作分配給設計者預先指定的角色或集中協調的檔案層級任務，因此推理單元與資訊交換路徑是預先固定的；
- 既有原語系統封裝的是可重用的、與任務無關的行為（如技能、工具介面）；
- 上下文管理方法則將資訊保留在單一軌跡中。

Dev-Primitive 則是由其所擁有的構件所定義，因此原語集合是由儲存庫與需求所「歸納產生」（induced）的，而非由設計者預先指定。這是一個從「設計者中心」到「儲存庫中心」的範式轉移。

#### 實驗數據解讀

論文在四個軟體工程基準測試上評估 HERMES，涵蓋四種任務類型：議題解決（issue resolution）、全儲存庫重構（whole-repository refactoring）、終端機任務（terminal-based tasks）以及 DevOps 工作流程。以下從多個角度解讀實驗數據。

**一、整體效能提升**

在預設的 GPT-5.6 Sol 配置（中等推理強度）下，HERMES 在四個基準測試上平均比匹配基線框架（matched baseline harnesses）提升了 12.4 個百分點。這個數字在軟體工程代理領域是相當顯著的，因為現有基準測試的整體正確率通常在 30%–60% 區間，12.4 個百分點的提升意味著相對改進幅度可達 20%–40%。

**二、模型異質配置的經濟效益**

更具啟發性的結果是異質配置實驗：當啟動模型（activation model）與診斷模型（diagnosis model）使用較強的模型，而 Dev-Primites 使用較小的 Qwen3-8B 時，HERMES 在四個基準測試上仍保持在同質化 GPT-5.6 Sol 配置（homogeneous GPT-5.6 Sol configuration）的 4.5 個百分點以內，同時在 Terminal-Bench 4.0 上減少了 26.2% 的推論成本（inference cost）。

這個結果揭示了一個重要的系統設計原則：在軟體工程代理中，「框架設計」（harness design）的品質可能比「單一模型的絕對強度」更為關鍵。具體而言：

- 啟動與診斷是「決策密集型」任務，需要全域視野與精確判斷，適合使用較強的模型；
- Dev-Primites 的工作是「元件內部的局部推理與修改」，範圍較小，較小的模型即可勝任；
- 透過這種職責分工，整體系統可以在效能幾乎不損失的情況下大幅降低成本。

**三、為何 HERMES 能帶來這些改進？**

從方法論角度推測，12.4 個百分點的提升可能來自以下幾個因素的疊加效應：

1. **減少上下文負擔**：每個 Dev-Primitive 只關注其所屬構件，避免了將整個儲存庫塞入單一上下文的負擔；
2. **依賴一致性**：透過依賴感知啟動，修改一個元件時會自動考慮其呼叫者、被呼叫者、配置與測試，減少了「修改 A 破壞 B」的問題；
3. **精確的錯誤定位**：錯誤診斷機制將執行證據映射回具體元件，避免了盲目重試整個流程；
4. **自然語言通訊**：元件間以自然語言交換需求，比傳統的程式碼靜態分析更靈活，能處理語義層面的約束。

**四、實驗設計的侷限性**

雖然數據令人印象深刻，但需注意以下幾點：

- 論文中未詳細列出每個基準測試的具體數字，僅提供平均值，難以判斷提升是否在所有任務類型上均勻分布；
- 「匹配基線」的具體定義不明確——是同一模型在傳統代理框架下的表現，還是其他專門設計的基線？這會影響 12.4 個百分點的解讀；
- 26.2% 的成本降低僅在 Terminal-Bench 4.0 上報告，其他基準測試的成本效益未明確說明。

#### 與現有研究的比較

**一、定位於軟體工程代理演進譜系**

軟體工程代理的發展可分為三個階段：

1. **流水線式方法**（Agentless、AutoCodeRover）：預先定義控制流程，將軟體修復分解為故障定位（fault localization）、補丁生成（patch generation）、驗證（validation）等階段。優點是可預測、可解釋；缺點是流程僵化，難以處理需要多輪互動的複雜任務。

2. **通用代理式方法**（SWE-agent、OpenHands、CodeAct）：將 LLM 置於互動式執行環境中，透過通用動作迴圈（action loop）檢查、修改、執行。優點是靈活；缺點是在長時程任務中遭遇上下文爆炸與語義漂移。

3. **多代理/角色分工方法**（ChatDev、MetaGPT 等）：將工作分配給設計者預定義的角色或檔案層級的開發者，由中央協調者統籌。優點是分工明確；缺點是推理單元與通訊路徑是固定的，無法適應不同儲存庫的結構。

HERMES 的定位介於第二與第三階段之間，但有根本性差異：它的推理單元不是「設計者指定的角色」，而是「由儲存庫結構歸納產生的元件」。這使得 HERMES 能夠：

- 適應不同儲存庫的獨特結構（每個儲存庫的 Dev-Primites 集合都不同）；
- 自動處理元件間的依賴關係，無需設計者預先定義通訊路徑；
- 將元件特定的資訊保留在元件內部，避免上下文污染。

**二、與可重用模組化代理能力的比較**

另一條相關研究路線關注「可重用的代理能力」，例如 Jin 等人（2026a;b）以及 Li 等人（2026）的工作將推理程序、技能或工具介面封裝為可重用的模組。HERMES 與這條路線的差異在於：

- 可重用模組封裝的是「任務無關的行為」，可在不同任務間共享；
- Dev-Primites 封裝的是「特定構件的實作與依賴」，是任務相關且儲存庫特定的。

兩者實際上是互補的：可重用模組可作為 Dev-Primites 內部的推理工具，而 Dev-Primites 則為這些工具提供了「歸屬於哪個構件」的語境。

**三、與上下文管理方法的比較**

Liu 等人（2026）與 Wang 等人（2026a）的工作專注於在單一軌跡內管理上下文增長。HERMES 採取了不同的策略：不是「壓縮單一軌跡」，而是「將資訊分散到多個原語中」。這兩種策略可以結合使用——例如，在每個 Dev-Primitive 內部仍可使用上下文壓縮技術。

**四、優勢與侷限性**

**優勢：**
- 從「設計者中心」轉向「儲存庫中心」，更具適應性；
- 透過依賴感知啟動與錯誤診斷機制，有效處理長時程任務；
- 異質配置實驗顯示框架設計的重要性，提供了一條降低成本的可行路徑。

**侷限性：**
- **啟動成本**：依賴感知啟動機制本身需要一個「啟動模型」來識別候選元件，這增加了系統複雜度；
- **診斷準確性**：錯誤診斷機制的效果取決於將執行證據映射回元件的準確性，若映射錯誤可能導致錯誤的原語被重啟動；
- **元件邊界定義**：Dev-Primites 的「元件」邊界如何劃分？是按檔案、類別、函數還是其他粒度？論文中未明確討論；
- **通訊開銷**：元件間通訊雖然比集中式軌跡更結構化，但仍可能產生額外的協調成本；
- **評估範圍**：實驗僅在四個基準測試上進行，對於極大型或極小型儲存庫的表現尚待驗證。

#### 未來研究方向

**一、元件邊界的理論基礎**

目前 Dev-Primites 的「元件」概念較為模糊——可以是檔案、類別、函數或模組。未來研究可探討：

- 如何根據任務類型自動決定最適合的元件粒度？
- 不同粒度對效能、成本與可解釋性的影響為何？
- 是否存在一套理論框架來指導元件劃分？

**二、依賴感知啟動的演算法改進**

當前的依賴感知啟動機制可能面臨「依賴爆炸」問題——一個元件的依賴鏈可能延伸至數百個相關元件。未來方向包括：

- 引入依賴重要性評分，優先啟動高重要性元件；
- 結合靜態分析與動態執行資訊，更精確地預測哪些元件需要修改；
- 探索基於圖神經網路的方法來學習依賴傳播模式。

**三、錯誤診斷機制的增強**

錯誤診斷是 HERMES 的閉環核心，其準確性直接影響系統效能。未來可考慮：

- 結合符號執行（symbolic execution）與神經方法，提供更精確的故障定位；
- 引入因果推理（causal reasoning）來區分「症狀」與「根因」；
- 探索多輪診斷的累積學習，使系統能從過去的診斷錯誤中改進。

**四、與人類開發者的協作**

Dev-Primites 的「自然語言介面」為人機協作提供了新的可能：

- 人類開發者可作為「高階原語」，對其他原語下達意圖性指令；
- 原語可向人類解釋其修改決策，提升可解釋性；
- 在關鍵修改點引入人類審核，平衡自動化與可控性。

**五、跨儲存庫的遷移學習**

每個儲存庫的 Dev-Primites 集合都是獨特的，但不同儲存庫之間可能存在結構相似性（例如相似的框架、語言、架構模式）。未來可探索：

- 跨儲存庫的元學習（meta-learning），使啟動與診斷機制能快速適應新儲存庫；
- 建立「原語模式庫」，將常見的元件類型（如 API 端點、資料庫模型、測試套件）預先封裝。

**六、安全性與可靠性**

當元件具備自我修改能力時，安全邊界成為關鍵問題：

- 如何防止一個 Dev-Primitive 的修改破壞其他原語的依賴？
- 是否需要引入形式化驗證（formal verification）來確保修改的正確性？
- 在多輪修改中，如何避免「修改漂移」導致系統偏離原始意圖？

**七、評估基準的擴展**

現有實驗僅涵蓋四個基準測試，未來可考慮：

- 更大規模的儲存庫（如超過百萬行程式碼的系統）；
- 更長時程的任務（如跨越數週的軟體演進）；
- 更多元的領域（如嵌入式系統、科學計算、遊戲開發）；
- 與人類開發者的直接比較，評估 HERMES 在實際軟體工程流程中的效用。

**八、理論分析**

目前 HERMES 的設計主要基於經驗觀察，未來可從理論角度分析：

- 在什麼條件下，Dev-Primites 優於集中式代理？
- 啟動集合的大小與任務效能之間的理論關係；
- 錯誤診斷機制的收斂性分析——在給定診斷準確率下，系統需要多少輪才能解決問題？

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於大型語言模型（LLM）代理在執行長時程軟體工程任務時所面臨的根本性瓶頸。當任務需要持續與儲存庫互動時，相關的程式狀態會分散在原始碼檔案、設定檔、測試、依賴項與執行期行為之中，導致代理必須反覆重建這些分散的狀態。隨著互動歷史不斷累積，會引發上下文爆炸、語義漂移等問題，使得代理難以維持穩定的推理品質。論文的目標正是要從「框架設計」的角度重新思考軟體工程代理的運作方式。

**Q2：為何現有的流水線式方法與代理式方法在長時程任務上會失敗？**
A：流水線式方法（如 Agentless、AutoCodeRover）將軟體修復預先拆解為故障定位、補丁生成與驗證等階段，這種剛性控制流程難以適應執行過程中持續變動的儲存庫狀態。代理式方法（如 SWE-agent、OpenHands、CodeAct）雖然讓 LLM 在互動式環境中自由操作，但受限於僅能追加的歷史紀錄與被動的壓縮策略，無法根本解決狀態分散的問題。更關鍵的是，無論採用哪種典範，編輯一個檔案往往需要同步調整呼叫端、設定與測試，這種跨檔案的一致性負擔是純粹的歷史壓縮無法消除的，這也是為何全儲存庫遷移任務中僅有 5.4% 的代理執行能完成所有評估階段。

**Q3：為何「框架工程」（Harness Engineering）在軟體工程代理中如此重要？**
A：過去的研究多聚焦於提升模型本身的推理能力或訓練專門的軟體工程模型，卻較少系統性地探討如何設計包圍模型的執行框架。論文的實驗結果顯示，即使使用相同的底層模型，框架設計的差異就能帶來平均 12.4 個百分點的效能提升，這證明了框架本身是影響代理成敗的關鍵變數。一個良好的框架不僅管理上下文與動作，更應該從根本上改變代理與儲存庫元件互動的方式，這正是 HERMES 的核心論點。

**Q4：什麼是「開發原語」（Dev-Primitives），它如何運作？**
A：開發原語是一種模組化且可執行的抽象，將儲存庫中的每個元件（從原始碼檔案到設定檔）與一個駐留式 LLM 配對。這個駐留模型會讀取其所屬元件的實作內容與依賴關係，使該元件具備「代理原生介面」，能以自然語言被定址、推理自身實作、與其他原語通訊，甚至進行局部自我修改。這樣一來，原本被動的軟體構件就轉變為主動參與軟體工程流程的個體，元件專屬的資訊與推理能力得以保留在擁有它的元件之中。

**Q5：HERMES 框架中的兩個關鍵機制是什麼？它們如何互補？**
A：第一個機制是「依賴感知動態啟動」，它會先定位最可能實作目標行為的元件，再沿著依賴關係追溯到可能需要同步修改的呼叫端、設定與測試，僅實例化這個候選集合中的開發原語，避免在擁有數千個元件的大型儲存庫中浪費資源。第二個機制是「錯誤診斷機制」，由於單一輪次的修改往往無法一次解決問題，而執行結果通常只會回報「儲存庫仍然失敗」而非指出哪個元件需要修改，因此這個機制會將失敗回溯到涉及的元件，並僅重新啟動這些原語，循環直到儲存庫通過測試或預算耗盡。兩者結合形成「啟動—執行—診斷—再啟動」的閉環，使 HERMES 能以局部且精準的方式處理長時程任務。

**Q6：Dev-Primitives 與既有的模組化代理能力相比，核心創新在哪裡？**
A：既有研究將推理能力附加在設計者預先指定的角色或集中協調的檔案層級任務上，因此推理單元與資訊交換路徑都是事先固定的；也有研究將可重用的能力封裝為任務無關的行為模組。Dev-Primitives 的根本差異在於「推理單元是由其所擁有的構件所定義」，原語的集合是由儲存庫本身與任務需求所誘發（induced），而非由設計者預先指定。這意味著原語的邊界、它們之間的通訊路徑，以及它們能存取的資訊範圍，都會隨著任務與儲存庫的結構動態調整，這是一種更貼近軟體本質的模組化方式。

**Q7：HERMES 在哪些基準測試上進行了評估？這些基準涵蓋了哪些面向？**
A：HERMES 在四個軟體工程基準測試上進行了實驗，涵蓋了四種不同的任務類型：議題解決（issue resolution）、全儲存庫重構（whole-repository refactoring）、終端機基礎任務（terminal-based tasks）以及 DevOps 工作流程。這樣的設計能夠全面檢驗框架在不同互動深度與複雜度下的表現，從相對聚焦的單一議題修復，到需要跨多個檔案維持一致性的全儲存庫遷移與演進任務，皆在評估範圍內。

**Q8：HERMES 的主要實驗結果為何？**
A：在預設的 GPT-5.6 Sol 中等推理強度設定下，HERMES 在四個基準測試上平均比匹配的基線框架提升了 12.4 個百分點，展現出穩定且顯著的效能增益。這項結果說明，無論任務類型為何，HERMES 的框架設計都能帶來一致的改善，而非僅在特定類型的任務上有效。更值得注意的是，這樣的提升是在不更換底層模型的前提下達成的，凸顯了框架設計本身的價值。

**Q9：使用較小的 Qwen3-8B 模型作為開發原語時，HERMES 的表現如何？**
A：當搭配強大的啟動模型與診斷模型時，使用 Qwen3-8B 作為開發原語的 HERMES 在四個基準測試上仍能維持在同質化 GPT-5.6 Sol 配置 4.5 個百分點以內的差距，同時在 Terminal-Bench 4.0 上減少了 26.2% 的推論成本。這顯示 HERMES 的模組化設計允許在不同元件上靈活配置不同規模的模型，實現成本與效能的良好平衡，對於實際部署具有重要意義。

**Q10：HERMES 最能發揮價值的實務場景有哪些？**
A：HERMES 特別適合需要跨多個檔案、跨多個元件維持一致性的長時程任務，例如全儲存庫遷移、框架升級、大規模重構以及複雜的 DevOps 工作流程。在這些場景中，傳統代理容易因為狀態分散與上下文爆炸而失敗，而 HERMES 透過將推理能力下放給各個元件，能有效緩解這些問題。此外，對於元件數量龐大但僅有少數元件與當前任務相關的大型儲存庫，HERMES 的動態啟動機制也能避免無謂的資源浪費。

**Q11：在實際部署 HERMES 時，有哪些工程上的考量？**
A：首先，需要為每個儲存庫元件設計合適的駐留模型配置，這涉及模型規模、推理強度與成本的權衡，論文中展示的異質配置（強啟動/診斷模型搭配輕量原語）是一種可行方案。其次，動態啟動與錯誤診斷機制本身需要可靠的啟動模型與診斷模型支撐，這些模型的品質會直接影響框架的整體效能。最後，框架的迭代預算（revision budget）需要根據任務特性與成本限制進行調整，以避免無限循環或過早終止。

**Q12：HERMES 對軟體工程代理領域的整體影響為何？**
A：HERMES 的提出將研究焦點從「如何讓模型更會寫程式」轉向「如何設計包圍模型的執行框架」，這是一個重要的典範轉移。它證明了框架設計本身可以是效能瓶頸的解方，而非僅僅是模型能力的附屬品。此外，Dev-Primitives 的概念也為未來的可解釋性、可審計性與人機協作開啟了新方向——每個元件都能以自然語言解釋自身的行為與修改理由，這對於建立可信賴的軟體工程代理至關重要。

**Q13：這篇論文所承認的限制有哪些？**
A：雖然論文中並未明確列出所有限制，但從方法描述可推論出幾項挑戰：Dev-Primitives 的有效性高度依賴於啟動模型與診斷模型的品質，若這些模型判斷失準，可能導致錯誤的元件被啟動或錯誤的元件被診斷為問題根源。此外，將 LLM 附加到每個元件會帶來額外的運算成本，雖然異質配置能緩解此問題，但在極大規模的儲存庫中仍需謹慎設計啟動策略。

**Q14：在哪些情境下 HERMES 可能仍然會失敗？**
A：當任務需要跨越元件邊界進行深層語意推理，或當問題的根源並非單一元件而是元件間的互動契約時，HERMES 的局部自我修改機制可能不足以處理。此外，若儲存庫缺乏清晰的依賴關係結構（例如高度動態生成程式碼或反射機制），依賴感知動態啟動可能無法準確定位候選元件集合。最後，對於需要全新設計而非修改既有元件的任務，Dev-Primitives 的典範可能不太適用。

**Q15：基於這篇論文，未來的研究方向有哪些？**
A：未來可朝幾個方向延伸：首先，可以探索 Dev-Primitives 在不同軟體工程任務（如測試生成、效能優化、安全審查）上的應用與調適；其次，可以研究如何讓原語之間的通訊更結構化與可驗證，例如引入形式化契約或類型系統；再者，跨儲存庫的知識轉移也是值得探索的方向，讓一個專案中學習到的原語經驗能應用於其他專案；最後，如何將人類開發者更順暢地整合進這個框架，實現真正的人機協作軟體工程，也是重要的長期研究方向。

## 實務應用指南

### 適用場景

**1. 大型企業級儲存庫的議題修復（Issue Resolution at Scale）**
適用於擁有數千個原始碼檔案、複雜依賴關係的企業級專案（如金融核心系統、電信計費平台）。傳統 SWE-agent 在此類場景下常因上下文爆炸而失敗，HERMES 透過依賴感知動態啟動機制，只實例化與議題相關的元件，能有效處理分散於多檔案、多模組的修復任務。

**2. 全儲存庫遷移與重構（Whole-Repository Migration / Refactoring）**
當需要將整個專案從舊框架遷移至新框架（例如 AngularJS 升級至 Angular、Python 2 升級至 Python 3、Java 8 升級至 Java 17），或進行大規模架構重構時，HERMES 的元件間通訊機制可讓各模組主動協調介面契約變更，避免因單一檔案修改導致的連鎖錯誤。

**3. 終端機密集型 DevOps 工作流程（Terminal-Heavy DevOps Workflows）**
適用於 CI/CD 設定調整、容器化部署、雲端資源配置等需要持續與終端機互動的任務。在 Terminal-Bench 4.0 等基準測試中，HERMES 已驗證能以較低的推論成本完成此類任務，特別適合需要反覆執行指令並根據輸出調整的場景。

**4. 開源專案的長期維護與貢獻管理**
適用於開源社群中需要處理大量分散議題、跨貢獻者協作的場景。HERMES 的錯誤診斷機制可將執行失敗回溯至具體元件，讓維護者精準定位問題，而非面對冗長的執行日誌。

**5. 異質模型團隊的成本敏感型開發環境**
適用於希望兼顧效能與成本的組織：使用較小的 Qwen3-8B 模型作為元件駐留 LLM，僅在關鍵的啟動與診斷階段使用較強的 GPT-5.6 Sol 模型，可在維持接近頂級效能的同時降低 26.2% 的推論成本。

### 實作前置條件

**資料前置條件**
- 目標儲存庫的完整原始碼、組態檔、測試套件與依賴清單（requirements.txt、package.json、pom.xml 等）
- 儲存庫的依賴關係圖（可透過靜態分析工具如 `pydeps`、`dependency-cruiser` 預先生成）
- 歷史議題與修復紀錄（用於訓練或評估啟動模型與診斷模型的準確度）
- 終端機執行環境的沙箱化設定（Docker 容器或 VM 映像檔）

**計算前置條件**
- 至少一台具備 24GB 以上 VRAM 的 GPU（如 NVIDIA A5000 或以上），用於部署 Qwen3-8B 等中型模型
- 若需使用 GPT-5.6 Sol 等旗艦模型，需準備對應的 API 金鑰與足夠的 API 額度
- 高吞吐量的物件儲存（如 S3）以保存執行證據與診斷日誌
- 容器編排平台（Kubernetes 或 Docker Swarm）以支援多 Dev-Primitive 並行實例化

**技能前置條件**
- 熟悉 LLM 代理框架（如 LangChain、AutoGen、SWE-agent）的設計模式
- 具備靜態程式分析基礎，能解讀抽象語法樹（AST）與控制流圖
- 理解軟體工程中的依賴管理、版本控制（Git）與測試驅動開發（TDD）
- 具備分散式系統除錯經驗，能處理多代理並行執行的競態條件

### 實作步驟建議

**步驟一：儲存庫元件化盤點**
將目標儲存庫拆解為可獨立定址的元件（檔案、類別、模組、組態），為每個元件建立唯一識別碼與元資料（路徑、語言、依賴清單、介面契約）。此步驟是後續 Dev-Primitive 實例化的基礎。

**步驟二：建構依賴感知啟動模型**
訓練或微調一個輕量級啟動模型，輸入為議題描述（自然語言），輸出為候選元件集合及其依賴鏈。可採用檢索增強生成（RAG）結合儲存庫嵌入索引的方式，先以語意相似度篩選，再以靜態依賴圖擴展。

**步驟三：實作 Dev-Primitive 抽象層**
為每個元件包裝一個駐留式 LLM 介面，該介面具備四項能力：自然語言推理、元件間通訊、局部自我修改、執行證據回報。建議採用標準化的 JSON Schema 定義介面契約，方便跨語言元件互通。

**步驟四：整合動態啟動機制**
在代理主迴圈中，先呼叫啟動模型取得候選元件集合，再依據預算（例如最多啟動 N 個元件）實例化對應的 Dev-Primitive。實例化時應採用延遲載入策略，避免一次性載入所有元件造成記憶體爆炸。

**步驟五：實作錯誤診斷機制**
當儲存庫執行失敗時，收集執行證據（測試輸出、堆疊追蹤、日誌），並訓練一個診斷模型將失敗映射回應被修改的元件集合。此機制應支援多輪迭代，每次只重新啟動被診斷出的元件，而非全部重來。

**步驟六：建立評估管線**
在四類基準測試（議題解決、全儲存庫重構、終端機任務、DevOps 工作流程）上建立自動化評估管線，持續追蹤成功率、推論成本、修復時間等指標。建議採用 A/B 測試框架比較 HERMES 與基線框架的差異。

**步驟七：異質模型部署與成本優化**
根據預算與效能需求，選擇合適的模型組合策略：對成本敏感場景，可將元件駐留 LLM 替換為 Qwen3-8B 等中型模型，僅在啟動與診斷階段使用旗艦模型。透過監控推論 token 消耗驗證成本節省效果。

### 潛在風險與注意事項

**風險一：元件邊界界定不當**
若元件切割過細，會導致 Dev-Primitive 數量爆炸、互動成本飆升；若切割過粗，則失去局部推理的優勢。**緩解措施**：以單一職責原則（SRP）為指導，結合領域驅動設計（DDD）的聚合根概念，動態調整元件粒度。

**風險二：元件間通訊的語意漂移**
當多個 Dev-Primitive 透過自然語言交換需求時，可能因模型幻覺導致介面契約不一致。**緩解措施**：在通訊層加入結構化驗證（例如 JSON Schema 校驗）與版本控制機制，並對關鍵介面變更要求人工審核。

**風險三：啟動模型的召回率不足**
若啟動模型遺漏關鍵元件，會導致修復不完整。**緩解措施**：採用保守策略，寧可多啟動也不要遺漏；同時設置依賴鏈的深度上限（例如 3 層），避免無限擴展。

**風險四：診斷模型的誤判成本**
錯誤診斷會浪費寶貴的修訂預算在無關元件上。**緩解措施**：採用多模型投票機制，並保留「全部重啟」的 fallback 選項；同時記錄診斷歷史，用於後續模型微調。

**風險五：異質模型間的能力落差**
當元件駐留模型（如 Qwen3-8B）能力不足時，可能無法正確理解複雜議題。**緩解措施**：建立升級路徑（escalation path），當元件模型信心度低於閾值時，自動將任務升級至旗艦模型處理。

**風險六：執行沙箱的安全性**
Dev-Primitive 具有自我修改能力，若缺乏適當隔離，可能造成不可預期的副作用。**緩解措施**：採用強隔離的容器沙箱，限制網路存取與檔案系統寫入範圍，並對所有修改操作記錄 audit log。

### 與其他技術的整合建議

**與 SWE-agent / OpenHands 整合**
HERMES 並非取代現有代理框架，而是作為上層的編排層。可將 SWE-agent 的動作迴圈封裝為 HERMES 的「執行原語」，由 HERMES 負責元件啟動與診斷，SWE-agent 負責具體的程式碼編輯與指令執行。

**與 RAG 系統整合**
啟動模型的候選元件篩選可借助向量資料庫（如 Milvus、Weaviate）儲存的儲存庫嵌入索引。建議將原始碼以函式或類別為單位切塊，並保留足夠的上下文（如類別註解、相依函式簽名）以提升檢索品質。

**與 CI/CD 平台整合**
將 HERMES 的錯誤診斷機制與 GitHub Actions、GitLab CI 等平台整合，可在 PR 階段自動觸發元件級修復建議，並將診斷結果以註解形式回饋至程式碼審查流程。

**與監控與可觀測性系統整合**
將執行證據與診斷日誌匯入 Prometheus、Grafana 或 OpenTelemetry，建立儀表板追蹤元件啟動率、診斷準確率、修復成功率等關鍵指標。

**與版本控制系統整合**
HERMES 的自我修改操作應透過 Git 進行版本化，每次修改產生獨立 commit 並附上診斷依據，方便後續追溯與回滾。建議整合 `git bisect` 工具加速錯誤定位。

**與多代理協作框架整合**
HERMES 可作為 AutoGen、MetaGPT 等多代理框架中的「元件層」，由中央協調代理負責高層任務分解，HERMES 負責低層的元件級執行與診斷。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與引言的「Dev-Primitives 是什麼」段落，建立「讓程式碼元件自己會思考」的核心直覺。接著跳過數學與實驗細節，直接看圖 1（若有）與案例展示，理解一個議題如何被分解到多個元件並協作完成。重點掌握「元件 + 駐留 LLM = 主動參與者」這個類比，無需深入演算法細節。

**給 AI 工程師**：建議從方法論章節切入，特別關注動態啟動機制與錯誤診斷機制的具體實作。可將本文視為「多代理系統在軟體工程領域的工程化樣板」，重點學習如何將 LLM 能力綁定到具體的程式碼工件上、如何設計元件間通訊協定、以及如何在異質模型間做成本與效能的權衡。建議在閱讀時同步思考如何將此模式應用於自身專案。

**給研究者**：本文的核心貢獻在於「將推理能力綁定到工件而非任務」的範式轉移，建議從相關工作章節出發，比較 Dev-Primitives 與既有 primitives（如 tool-use primitives、skill primitives）的本質差異。可深入探討的開放問題包括：元件邊界的理論基礎、跨語言元件的語意對齊、診斷模型的可解釋性、以及在更大規模儲存庫（百萬行程式碼等級）下的可擴展性。

**給產品經理**：重點關注效能數字（12.4% 平均提升、26.2% 成本節省）與適用場景章節，理解 HERMES 解決的「長時程任務失敗率高」這個真實痛點。在評估導入價值時，應關注三個維度：任務類型是否屬於長時程且涉及多檔案修改、現有方案的失敗成本有多高、以及團隊是否能承受異質模型部署的運維複雜度。建議先在一個中等規模專案上進行概念驗證（PoC），再決定是否全面導入。
