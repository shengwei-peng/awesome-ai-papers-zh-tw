## ⚡ TL;DR

現有防護僅能攔截單一變更動作，無法確保客服代理遵循完整政策程序。
PolicyGuide 將政策編譯為工作流程圖，並在使用者回合邊界主動驗證、引導下一步。
τ²-bench 上 Pass⁴ 從 0.42 升至 0.62，電信進步最大，工作流程可跨模型遷移。

## 摘要翻譯

客戶服務 LLM 代理（LLM agents）在代表使用者行動時，必須遵循組織政策。合規失敗可能源於禁止行動（forbidden actions），例如授予不符合資格的變更；或是遺漏程序性要求（procedural requirements），例如身份識別（identification）或確認（confirmation）。執行時安全防護機制（runtime safeguards）可以介入高風險行動，但僅限單一行動的檢查無法引導代理完成多步驟程序。工作流程遵循系統支援規定的流程執行，但主要目標是完成工作流程，而非確保代理行為合規。PolicyGuide 則是將每個領域的政策編譯成工作流程圖（workflow graph），並在使用者回合邊界（user-turn boundaries）調用主動驗證器（proactive verifier）。驗證器根據持久化圖狀態（persisted graph state），協調待處理請求（open requests），並沿著符合政策的路徑（policy-compliant path）傳回步驟特定補救措施（step-specific remediation）。在 τ²-bench 的航空、零售與電信領域中，搭配 GPT-5.4 代理與驗證器，PolicyGuide 將平均 Pass⁴ 從 0.42 提升至 0.62，其中在電信領域（工作流程結構最完整的領域）提升幅度最大，從 0.19 提升至 0.61。相同的工作流程可套用至 Claude Sonnet 4.6 與 Gemini 2.5 Pro 代理。補充評估顯示，在對抗性使用者（adversarial users）情境下觀察到最低的攻擊成功率，並在作者設計的工作流程層級驗證（workflow-level validation）中展現最強的程序合規性。

### 核心貢獻（3～5點）
- 提出 PolicyGuide 框架，將政策合規從單一行動防護擴展至整個工作流程引導，解決多步驟程序中的遺漏與違規問題。
- 將自然語言政策（natural-language policies）編譯為工作流程圖，並在使用者回合邊界透過主動驗證器進行工作流程層級驗證。
- 利用持久化圖狀態協調待處理請求，提供步驟特定補救措施，使代理能持續沿著符合政策的路徑執行。
- 在 τ²-bench 的航空、零售與電信領域中顯著提升 Pass⁴，尤其在結構化程度最高的電信領域效果最為顯著。
- 工作流程可移轉至多種前沿模型（frontier models），並在對抗性使用者與工作流程層級驗證中展現強健的程序合規性。

### 適合對象
本論文適合對大型語言模型代理安全、企業政策合規、客戶服務自動化，以及多步驟工作流程驗證感興趣的研究人員與工程師。特別推薦給關注如何在實際部署中確保 LLM 代理遵循複雜組織政策、並希望從單點防護轉向整體流程引導的讀者。

## 深度分析

#### 方法論解析

PolicyGuide（政策引導框架）將「政策合規（policy-compliant）」重新定義為一個同時涉及**結果正確性**與**程序正確性**的雙軸問題。在客戶服務 LLM 代理（大型語言模型代理）的場景中，違規不僅來自於執行了禁止行動（forbidden actions），例如為不符合資格的使用者辦理變更；也可能來自於遺漏程序性要求（procedural requirements），例如未先完成身份識別（identification）、資格檢查（eligibility checks）或最終確認（confirmation）。傳統的執行時安全防護機制（runtime safeguards）多屬於行動防護機制（action guard），只在變更性工具呼叫（mutating tool call）發生當下進行 PASS/BLOCK 判斷，因此對於發生在突變動作之前的對話步驟或工具使用順序無從介入。PolicyGuide 的核心貢獻，便是把自然語言政策（natural-language policies）編譯成工作流程圖（workflow graph），並在使用者回合邊界（user-turn boundaries）啟動主動驗證器（proactive verifier），以持久化圖狀態（persisted graph state）持續追蹤整段對話的程序進度。

具體而言，PolicyGuide 的方法論可拆解為以下環節：

1. **政策編譯為工作流程圖**  
   每一條領域政策被轉換成一張有向圖，節點代表政策所要求的步驟（如：問候、身份識別、讀取紀錄、資格檢查、呈現方案、請求確認、執行變更、拒絕請求等），邊則代表步驟間的合法轉移與先後依賴。這種表示法能夠區分**扁平先決條件（flat prerequisites）**——可在最終動作前集中檢查——與**有序工作流程要求（ordered workflow requirements）**——必須按特定順序完成，且可能分散在多個使用者回合中。以電信領域的故障排除（troubleshooting）為例，其診斷–指示–驗證（diagnose–instruct–verify）順序便可被明確編碼為圖中的有序路徑。

2. **持久化圖狀態與多請求協調**  
   主動驗證器不只在單一回合運作，而是透過持久化圖狀態記錄目前所在節點、已完成節點與待處理請求（open requests）。當使用者同時提出多項請求時，驗證器能夠為每個請求維護各自的圖位置，並在使用者回合邊界進行協調，避免代理因為對話交錯而遺漏或錯置程序。

3. **使用者回合邊界的主動驗證**  
   與行動防護機制被動等待突變動作不同，PolicyGuide 在使用者回合結束、代理即將回應之前主動遍歷工作流程圖。它從持久化圖狀態的當前位置出發，檢查所有待處理請求，找出第一個未滿足的節點，並回傳針對該節點的步驟特定補救措施（step-specific remediation）。這種設計讓驗證發生在自然的對話斷點，既能即時導正代理，又避免中斷生成過程。

4. **步驟特定補救與突變攔截**  
   若代理在尚未完成必要步驟前便嘗試進行變更性工具呼叫，PolicyGuide 會攔截該呼叫並回傳未滿足步驟的補救指引，例如「請先完成身份識別」或「請先確認使用者資格」。只有在所有前置步驟都已具備充分依據（grounded）後，驗證器才會建議執行突變動作，從而引導代理沿著符合政策的路徑（policy-compliant path）完成任務。

5. **代理無關的外部覆蓋層**  
   PolicyGuide 並非內建於代理內部的工作流程控制器，而是作為外部覆蓋層（external overlay）運作。它將驗證器（verifier）與行動者（actor）分離，因此同一套工作流程圖可搭配不同的前沿模型（frontier model），如 GPT-5.4（GPT-5.4 前沿模型）、Claude Sonnet 4.6（Claude Sonnet 4.6 前沿模型）與 Gemini 2.5 Pro（Gemini 2.5 Pro 前沿模型）。這對於閉源權重（closed-weight）模型特別重要，因為領域特定微調（domain-specific fine-tuning）往往不可行，而外部安全層提供了一個無需重新訓練的整合點。

6. **與行動防護機制的互補定位**  
   PolicyGuide 並不取代傳統的行動防護機制，而是向上游延伸其保護範圍。行動防護機制仍可作為最後一道關卡，對變更性工具呼叫進行硬阻擋；PolicyGuide 則負責在對話進行中持續引導代理完成必要程序，減少走到最終阻擋的情況。

#### 實驗數據解讀

本研究在 τ²-bench（τ²-bench 政策遵循基準）的 Airline、Retail 與 Telecom 三個領域進行評估，採用的主要指標為 Pass⁴（Pass⁴ 四次取樣通過率指標），即每個任務取樣四次，只要有一次成功即計為通過。以下是對實驗結果的逐層解讀：

- **整體效能提升**  
  未受引導的基線（unguided）平均 Pass⁴ 為 0.42，加入 PolicyGuide 後提升至 0.62，相當於約 20 個百分點的絕對增益。這顯示單純依賴通用推理與行動迴圈（reasoning-and-acting loop）難以穩定遵循複雜政策，而程序層級的引導能顯著改善合規率。

- **領域差異：電信領域的最大增益**  
  Telecom 的 Pass⁴ 從 0.19 大幅提升至 0.61，增益高達 42 個百分點。這與該領域的政策結構高度一致：根據作者的政策分析，Telecom 的有序工作流程要求（ordered workflow requirements）佔比高達 54.0%，遠高於 Airline 的 4.7% 與 Retail 的 3.6%。當程序步驟必須依序完成、且中間可能沒有任何變更性工具呼叫可供行動防護機制攔截時，PolicyGuide 的跨回合主動驗證便顯得格外關鍵。

- **Retail 與 Airline 的相對表現**  
  Retail 的程序性要求（procedural requirements）接近 100%，但大多屬於可在最終動作前集中檢查的扁平先決條件；Airline 的程序性要求佔 67.4%，有序要求僅 4.7%。因此這兩個領域雖有進步，但幅度預期小於 Telecom。這也說明 PolicyGuide 的價值與「政策結構化程度」高度相關：政策越是有序、越依賴多步驟程序，引導效果越明顯。

- **診斷變體與 FlowAgent 基線**  
  作者在 Telecom 上額外比較了診斷性工作流程變體與一個匹配的 FlowAgent 工作流程控制器基線。雖然提供的上下文未詳述數字，但這類對比有助於區分「外部引導」與「內建工作流程控制」的差異：PolicyGuide 作為外部覆蓋層，既能達到相近或更好的程序遵循，又保留了對通用代理行為的防護角色。

- **跨代理遷移**  
  研究將同一套工作流程圖遷移至 Claude Sonnet 4.6 與 Gemini 2.5 Pro 代理上，結果顯示工作流程具有跨模型轉移性。這驗證了 PolicyGuide 的設計假設：程序知識應與行動模型解耦，從而避免為每個前沿模型（frontier model）重新設計內部控制器。

- **對抗性穩健性**  
  在 CRAFT（對抗性紅隊測試框架）紅隊測試中，PolicyGuide 達到觀察到的最低攻擊成功率。這意味著對抗性使用者（adversarial users）難以透過對話操弄誘導代理跳過必要步驟或執行違規動作，因為驗證器會在每次使用者回合後重新檢查程序狀態。

- **工作流程層級驗證**  
  除了 Pass⁴ 這類結果導向指標，作者還設計了一個 Telecom 追蹤稽核（trace audit），從工作流程層級驗證（workflow-level validation）的角度檢查每一步程序是否確實依序執行。PolicyGuide 在此獲得最強的程序合規表現，證明其不僅提升最終成功率，也真正改善了中間步驟的遵循度。

- **整體解讀**  
  儘管 0.62 的平均 Pass⁴ 已顯著優於基線，但仍有三成以上任務未能通過，顯示政策合規問題尚未完全解決。未來若能進一步降低圖編譯錯誤、提升驗證器對模糊語境的判斷，仍有進步空間。

#### 與現有研究的比較

PolicyGuide 的定位介於兩條既有研究路線之間：**執行時安全防護機制（runtime safeguards）**與**工作流程／標準作業程序代理（workflow/SOP agent）**。

- **與行動防護機制的比較**  
  傳統行動防護機制如 GuardAgent、Conseca、Progent 等多在變更性工具呼叫（mutating tool call）發生時進行局部檢查。PolicyGuard（Kang et al., 2026）是與 PolicyGuide 最接近的基線：它會讀取完整對話、針對每個突變動作維護一份檢查清單，並回傳 PASS/BLOCK 與補救訊息。然而 PolicyGuard 仍然是**動作觸發（action-triggered）**的：它只在代理試圖執行突變時才運作，無法持續追蹤代理在對話前期是否已偏離程序，也無法處理沒有突變動作的有序流程（如電信故障排除的 diagnose–instruct–verify）。PolicyGuide 透過持久化圖狀態與使用者回合邊界驗證，把防護範圍從「單一動作」擴展到「整段工作流程」。

- **與工作流程／SOP 代理的比較**  
  SOP-Agent 等研究將標準作業程序（SOP）編譯成決策圖，並在代理執行時限制每個節點可採取的動作。這類系統的設計目標是**忠實執行工作流程（faithful workflow execution）**，因此工作流程控制通常內建於代理執行環境中。相較之下，PolicyGuide 並不取代代理的推理與行動迴圈，而是作為外部覆蓋層對通用代理行為進行安全防護。這帶來兩項優勢：一是可跨代理重複使用，二是能夠防範代理偏離政策，而不只是協助代理完成預設流程。

- **綜合定位**  
  PolicyGuide 可視為「以工作流程狀態為基礎的執行時安全防護機制」。它吸收了工作流程系統的程序表達能力，同時保留了外部安全層的監控與介入能力。這種「驗證器與行動者分離」的架構，特別適合閉源權重（closed-weight）的前沿模型，因為它無需修改模型內部或進行領域特定微調（domain-specific fine-tuning）。

- **限制**  
  PolicyGuide 的效能高度依賴工作流程圖的品質。若政策編譯過程遺漏了例外情況、語境條件或新修訂條文，驗證器可能給出錯誤指引。此外，它目前仍是在每次使用者回合後進行驗證，對於需要即時中斷代理生成的場景可能不夠及時。對抗性評估雖顯示良好結果，但僅限於 CRAFT 框架所涵蓋的攻擊類型，面對更強大的自適應對手時仍需進一步驗證。

#### 可重現性評估

- **資料集與評估基準**  
  τ²-bench（τ²-bench 政策遵循基準）與其前身 τ-bench 是公開的政策遵循代理評估基準，提供自然語言政策、唯讀工具與變更性工具，以及 Airline、Retail、Telecom 等領域的任務。因此，評估所使用的任務與成功標準原則上可由其他研究者取得，具備一定的可重現性基礎。

- **程式碼與工作流程圖釋出狀況**  
  根據提供的上下文，文中並未明確說明 PolicyGuide 的原始碼、編譯後的工作流程圖或主動驗證器的提示詞（prompts）是否公開。若這些核心資產未釋出，其他研究者將難以精確重現 verifier 的行為與圖編譯結果，只能根據論文描述進行重新實作。

- **模型權重與 API 版本**  
  實驗使用 GPT-5.4、Claude Sonnet 4.6 與 Gemini 2.5 Pro 等閉源權重（closed-weight）模型。這些模型的權重不公開，且 API 行為可能隨版本更新而變化。即使使用相同模型名稱，不同時間點的 API 回應也可能導致 Pass⁴ 等指標出現波動，影響數值結果的精確再現。

- **政策編譯的人工成本**  
  將自然語言政策（natural-language policies）轉換為工作流程圖（workflow graph）可能涉及大量領域專家知識與人工判斷，尤其是區分扁平先決條件與有序工作流程要求、處理例外與語境條件。若編譯流程未自動化或未詳細記錄，則在新領域上複製 PolicyGuide 的成本會相當高。

- **綜合評估**  
  整體而言，本研究的可重現性屬於「部分可重現」：評估任務與指標公開，但核心系統實作、模型存取與圖編譯細節若未釋出，將限制獨立驗證。建議作者未來釋出 verifier 程式碼、圖結構定義與編譯腳本，以提升社群再現與擴展的可能性。

#### 未來研究方向

1. **自動化政策編譯**  
   目前工作流程圖（workflow graph）的建構可能依賴人工或半自動方式。未來可探索從自然語言政策（natural-language policies）直接抽取程序步驟與順序約束的方法，例如結合資訊抽取、語意解析與大型語言模型，降低領域遷移成本。

2. **動態圖更新與例外處理**  
   組織政策經常變動，且實務上充滿例外條款。研究如何讓 PolicyGuide 在政策更新時自動調整圖結構，或在執行時偵測並處理未預見的語境例外，將大幅提升實用性。

3. **與形式化驗證結合**  
   可將工作流程圖視為狀態機，並運用模型檢查（model checking）技術證明某些合規性質（例如「任何變更性工具呼叫前必須完成身份識別」），從理論上強化系統保證。

4. **統一安全層架構**  
   將 PolicyGuide 與現有的行動防護機制（action guard）、參數級最小權限控制（如 Progent）以及輸出過濾器整合為單一執行時安全防護機制（runtime safeguard）堆疊，並研究各層之間的優先順序與衝突解決策略。

5. **多請求排程與衝突偵測**  
   當使用者同時提出多個待處理請求（open requests）時，如何決定處理順序、偵測請求間衝突（例如一項變更可能使另一項變更不合法），是值得深入研究的問題。

6. **從失敗軌跡學習**  
   利用 τ²-bench 中未通過的軌跡，訓練或微調 verifier，使其能夠更精準地預測代理常見的偏離模式並給出更有效的步驟特定補救措施（step-specific remediation）。

7. **延遲與成本最佳化**  
   每次使用者回合都呼叫大型驗證器會增加延遲與 API 成本。未來可研究如何以較小模型執行圖遍歷，或設計快取與增量驗證機制，只在狀態可能改變時才進行完整檢查。

8. **更強大的對抗性評估**  
   除了 CRAFT（對抗性紅隊測試框架）之外，可針對提示注入（prompt injection）、社會工程攻擊、多回合誘導等設計更嚴苛的對抗性使用者（adversarial users）測試，並發展相應的防禦機制。

9. **多模態與跨通道擴展**  
   將 PolicyGuide 從純文字客服擴展至語音、表單、圖片等多元通道，並處理跨模態資訊（例如使用者上傳證件照片以完成身份識別）的程序合規問題。

10. **人機協作與可解釋性**  
    讓客服人員能夠理解 PolicyGuide 為何建議某個步驟、在必要時進行覆寫或回報錯誤，並將回饋納入圖結構更新，形成持續改善的閉環。

## 論文問答

**Q1：客戶服務 LLM 代理在政策遵循上面臨的核心問題是什麼？**  
A：客戶服務 LLM 代理必須在代表使用者行動時遵守組織政策，但違規可能來自兩種互補的失敗模式：一是執行了「禁止行動」，例如為不符合資格的使用者批准變更；二是忽略了「程序性要求」，例如未完成身份識別、資格檢查或最終確認。這些程序性缺失不僅可能導致原本被允許的動作缺乏依據，也可能間接產生被禁止的結果。因此，政策合規不僅是「選對動作」，還必須「依正確流程完成動作」。

**Q2：現有的行動防護機制與工作流程導向代理為何不足以解決上述問題？**  
A：傳統的執行時安全防護機制通常只在代理呼叫最終變更性工具時進行 PASS/BLOCK 判斷，因此當代理跳過前置程序步驟時，錯誤往往要到流程末端才會被發現，且僅能回傳阻擋而無法主動引導。另一方面，工作流程或標準作業程序代理雖能執行規定步驟，但其設計目標主要是「忠實完成流程」，而非作為外部安全機制來防範通用代理的違規行為。即便是較進階的 PolicyGuard，也仍局限於以變更性動作為觸發點，無法覆蓋動作之前的對話或工具使用偏差。

**Q3：為什麼程序性要求與有序工作流程在實務中特別重要？**  
A：作者對 τ²-bench 的政策分析顯示，程序性要求在三個領域都極為普遍：航空佔 67.4%、零售幾乎 100%、電信達 98.0%。其中，「有序工作流程要求」在電信領域特別集中，高達 54.0%，遠高於航空的 4.7% 與零售的 3.6%。這意味著在電信等領域，代理必須依序完成診斷、指示、驗證等步驟，單純在最終動作前檢查扁平先決條件無法確保合規。

**Q4：PolicyGuide 的核心方法是什麼？**  
A：PolicyGuide 會將每個領域的自然語言政策編譯成一張工作流程圖，並在使用者回合邊界啟動一個主動驗證器。該驗證器根據持久化的圖狀態，從目前節點開始遍歷整張圖，核對所有待處理請求，並針對第一個未滿足的步驟回傳步驟特定補救措施。透過這種方式，系統能在整段互動過程中持續追蹤代理是否走在符合政策的路徑上。

**Q5：PolicyGuide 相較於既有方法的最大創新是什麼？**  
A：PolicyGuide 的關鍵創新在於把「工作流程執行」與「行為安全防護」結合成一個外部、諮詢式的覆蓋層，而不是把流程控制內建到代理架構中。它透過持久化圖狀態跨越多個使用者回合追蹤進度，並能在代理嘗試過早執行變更性工具之前，就主動指出缺失步驟。這種設計讓同一套程序表示可以搭配不同前沿模型代理重複使用，兼具通用性與安全防護功能。

**Q6：為什麼 PolicyGuide 選擇在使用者回合邊界進行驗證，並將驗證器與執行者分離？**  
A：使用者回合邊界是對話中自然的介入點，此時系統可以統整所有待處理請求、重新評估圖狀態，並在代理進入下一步之前給出指引。將驗證器與代理執行者分離，則能讓 PolicyGuide 作為外部安全防護機制運作，無需修改或重新訓練閉源權重的 LLM。此外，這種分離使工作流程圖與驗證邏輯能跨 GPT-5.4、Claude Sonnet 4.6 與 Gemini 2.5 Pro 等不同代理轉移。

**Q7：論文在哪些基準、模型與指標上評估 PolicyGuide？**  
A：實驗主要在 τ²-bench 的航空、零售與電信三個領域進行，使用 GPT-5.4 作為代理與驗證器。主要評估指標為 Pass⁴，即四次取樣中通過政策的平均比例。此外，作者也將相同工作流程轉移到 Claude Sonnet 4.6 與 Gemini 2.5 Pro 代理上，驗證跨模型通用性。

**Q8：PolicyGuide 取得了哪些關鍵量化結果？**  
A：在 GPT-5.4 上，PolicyGuide 將三個領域的平均 Pass⁴ 從未受引導的 0.42 提升到 0.62，進步幅度達 20 個百分點。其中提升最顯著的是電信領域，從 0.19 大幅躍升至 0.61，這與電信政策具有最強的工作流程結構相符。這些結果顯示，當政策包含大量有序程序要求時，整體工作流程引導能帶來最大效益。

**Q9：除了主實驗，作者還進行了哪些補充分析與對照實驗？**  
A：作者設計了診斷式工作流程變體，並在電信領域與一個匹配的 FlowAgent 工作流程控制器基線進行比較。此外，他們使用 CRAFT 紅隊攻擊框架測試對抗性使用者的繞過能力，並透過作者自行設計的電信軌跡稽核來評估程序層級合規性。這些互補評估顯示 PolicyGuide 在對抗攻擊下具有最低觀察到的攻擊成功率，並在流程層級驗證中展現最強的程序合規。

**Q10：PolicyGuide 最適合應用在哪些實務場景？**  
A：PolicyGuide 特別適合需要嚴格遵循組織政策、且政策可表達為多步驟程序的客戶服務場景，例如航空訂票與改票、零售訂單修改與退換貨、電信帳號方案變更與故障排除。在這些領域中，代理必須同時避免違規動作並依序完成身份識別、資格檢查與確認等步驟。任何以自然語言政策規範代理行為的企業流程，都可以考慮引入這類外部工作流程安全防護層。

**Q11：若要在產品中部署 PolicyGuide，需要考慮哪些工程與設計議題？**  
A：首先，需要將自然語言政策準確地編譯成工作流程圖，這涉及政策解析、節點定義與轉換條件的設計，並需持續維護以因應政策更新。其次，系統必須可靠地持久化圖狀態，以支援多回合對話與多個待處理請求的同時追蹤。最後，由於它作為外部覆蓋層運作，產品團隊可以將其整合到現有 LLM 代理執行階段，而無需對閉源模型進行領域特定微調。

**Q12：PolicyGuide 對 LLM 代理安全與合規研究領域可能帶來什麼影響？**  
A：PolicyGuide 橋接了過去相對獨立的兩條研究路線——執行時安全防護與工作流程導向執行，提出了一種同時「守護」與「引導」的統一框架。它證明外部、主動、基於圖的驗證器能顯著提升政策合規率，並可跨不同前沿模型轉移。這為未來企業級代理系統提供了一個可擴展的合規基礎設施範式，降低了對閉源模型重新訓練的依賴。

**Q13：論文可能承認哪些限制？**  
A：PolicyGuide 的有效性取決於政策能否被正確且完整地編譯成工作流程圖，對於語意模糊或充滿例外的自然語言政策，圖形化過程可能面臨挑戰。此外，驗證器本身也是由 LLM 驅動，可能出現判斷錯誤或對圖狀態的誤解。目前評估集中在 τ²-bench 的三個領域，對於更開放、更少結構化的應用場景，方法是否同樣有效仍需進一步驗證。

**Q14：在哪些情況下 PolicyGuide 可能仍然失敗？**  
A：當使用者請求高度交錯、多個目標同時進行且彼此依賴時，驗證器可能難以正確協調待處理請求與圖路徑。如果工作流程圖與實際政策存在不一致，例如遺漏了某些例外條件，系統也可能引導代理走向錯誤方向。此外，精心設計的對抗性提示可能試圖混淆狀態追蹤或誘使驗證器產生錯誤的補救建議。

**Q15：未來研究可以朝哪些方向延伸 PolicyGuide？**  
A：未來可以擴展圖形表示以支援更豐富的政策語意，例如時間限制、例外處理、條件分支與動態授權。也可以結合線上學習或人類回饋，讓系統從實際違規案例中自動修正圖結構與驗證規則。此外，將 PolicyGuide 與細粒度的參數級防護或論證型安全檢查結合，可能進一步提升對複雜對抗攻擊的抵抗力。

## 實務應用指南

## 適用場景

1. **航空公司訂位與改票客服代理**  
   當使用者要求改航班、升等或退票時，代理必須先完成身份識別、資格檢查、費用說明與確認，才能執行變更性工具呼叫。PolicyGuide 可在每個使用者回合邊界檢查是否遺漏任何程序性要求，避免「先改後驗」的違規。

2. **電商零售訂單修改與退款代理**  
   退換貨政策通常包含多項扁平先決條件（訂單狀態、時間窗口、商品類別）以及確認步驟。PolicyGuide 能將這些政策編譯成工作流程圖，並在使用者每次輸入後主動提示代理補齊遺漏條件。

3. **電信故障排除與方案變更代理**  
   電信領域的故障排除常遵循「診斷–指示–驗證」的有序工作流程要求，且部分步驟沒有變更性工具呼叫可供行動防護機制攔截。PolicyGuide 的持久化圖狀態可追蹤代理在流程中的位置，確保不會跳過診斷或驗證。

4. **金融保險理賠或帳戶異動客服**  
   需要嚴格遵循 KYC、風險告知、雙重確認等程序的場景，PolicyGuide 可作為外部主動驗證器，在關鍵變更前強制完成所有必要步驟。

5. **企業內部 IT 服務台（ITSM）代理**  
   處理權限申請、設備報修或機密資料存取時，PolicyGuide 可確保代理依 SOP 收集資訊、取得主管核准並記錄審計軌跡。

## 實作前置條件

### 資料準備
- **自然語言政策文件**：組織現行的客服政策、SOP、合規條文，需能對應到「禁止行動」與「程序性要求」兩大類。
- **工具描述與分類**：清楚區分讀取工具與變更性工具呼叫，並標註每個工具對應的業務動作。
- **對話範例與失敗案例**：包含歷史對話記錄、常見違規模式（如跳過身份識別、未確認即修改），用於驗證圖形覆蓋率。
- **領域詞彙與實體對照表**：例如航班代碼、商品狀態、電信方案名稱，確保 verifier 能正確解析使用者意圖。

### 運算資源
- **前沿模型 API 配額**：代理與 PolicyGuide verifier 各需穩定的 LLM 呼叫配額；論文使用 GPT-5.4，實務上可依延遲與成本選用 Claude Sonnet 4.6 或 Gemini 2.5 Pro。
- **圖狀態儲存**：需可持久化的狀態儲存（如圖資料庫、Redis、PostgreSQL），用於保存每個對話的持久化圖狀態與待處理請求。
- **低延遲推論管線**：verifier 在每個使用者回合邊界執行，需控制在可接受的回應延遲內（通常數百毫秒至 1–2 秒）。

### 技能與團隊
- **政策分析師**：能將自然語言政策拆解為先決條件、有序步驟與禁止事項。
- **圖形建模與軟體工程師**：負責將政策編譯為工作流程圖，並設計狀態轉換邏輯。
- **LLM 代理工程師**：熟悉推理與行動迴路（ReAct）、工具呼叫格式與提示工程。
- **評估工程師**：能設計 Pass⁴、對抗性測試（如 CRAFT red-teaming）與工作流程層級驗證。

## 實作步驟建議

### 步驟 1：政策結構化與缺口分析
將自然語言政策轉換為結構化清單，標註：
- 哪些動作屬於禁止行動；
- 哪些屬於程序性要求；
- 哪些是扁平先決條件，哪些是有序工作流程要求。

可參考論文附錄做法，計算各領域中程序性要求的占比，優先處理高風險流程。

### 步驟 2：編譯工作流程圖
將結構化政策轉為工作流程圖：
- 節點代表必要步驟（身份識別、資格檢查、確認等）；
- 邊代表步驟間的合法順序；
- 每個節點標註完成條件與所需證據（例如「已讀取會員資料」、「使用者已口頭確認」）。

### 步驟 3：實作主動驗證器
在每個使用者回合邊界呼叫 verifier：
- 從持久化圖狀態載入當前位置；
- 解析使用者最新輸入，更新待處理請求；
- 沿著工作流程圖前進，找出第一個未滿足的節點；
- 回傳步驟特定補救措施給代理。

### 步驟 4：設計補救與引導提示
補救訊息應具體且可執行，例如：
> 「在執行變更性工具呼叫前，請先完成身份識別：向使用者索取帳號末四碼與出生日期。」

避免僅回傳 BLOCK，而是讓代理知道下一個符合政策的路徑。

### 步驟 5：整合狀態持久化
確保 verifier 與代理之間共享持久化圖狀態，支援：
- 多輪對話中的位置追蹤；
- 同時處理多個待處理請求；
- 對話中斷後可恢復。

### 步驟 6：端到端評估與迭代
- 使用 τ²-bench 或自建測試集評估 Pass⁴；
- 針對電信等高度結構化領域加強有序工作流程要求測試；
- 進行 CRAFT red-teaming 評估對抗性使用者攻擊；
- 執行作者設計的工作流程層級驗證，確認程序合規而不只是結果正確。

### 步驟 7：部署監控與持續維護
- 記錄每次 verifier 介入的原因與代理後續行動；
- 當政策更新時，同步更新工作流程圖與完成條件；
- 定期審查未覆蓋的邊緣案例，擴充圖形。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **圖形覆蓋不全** | 政策文件未窮舉所有例外情境，導致 verifier 無法辨識合法捷徑。 | 結合人工審查與歷史對話挖掘，定期擴充節點與邊；保留人工覆核通道。 |
| **過度嚴格造成使用者體驗下降** | 代理被強制執行過多步驟，對話變得冗長。 | 區分「必要」與「建議」步驟；允許使用者在知情下放棄非強制程序。 |
| **延遲與成本** | 每個使用者回合邊界都呼叫 verifier，增加延遲與 API 費用。 | 對簡單查詢使用快取或輕量規則前置過濾；僅在涉及變更性工具呼叫或複雜流程時啟用完整驗證。 |
| **代理過度依賴引導** | 代理可能學會只照 verifier 提示走，喪失彈性處理能力。 | 將 PolicyGuide 設計為「諮詢式」外部覆蓋層，而非強制控制代理架構；保留代理的推理與行動迴路自主權。 |
| **對抗性攻擊** | 使用者可能透過語義繞過或長上下文操縱，誘導代理跳過步驟。 | 定期進行 CRAFT red-teaming；將 verifier 的狀態判斷與對話內容分離，避免被使用者輸入直接污染。 |
| **跨模型行為差異** | 不同前沿模型對補救提示的理解與遵循程度不同。 | 在 Claude Sonnet 4.6、Gemini 2.5 Pro 等目標模型上進行 transfer 測試，調整提示與節點定義。 |

## 與其他技術的整合建議

- **現有執行時安全防護機制**：PolicyGuide 不取代行動防護機制，而是與之互補。建議將 PolicyGuide 置於使用者回合邊界，行動防護機制仍守在最終變更性工具呼叫，形成雙層防護。
- **CRM / 票務系統**：將 verifier 的持久化圖狀態與客服工單綁定，讓真人客服接手時能清楚看到已完成與待完成步驟。
- **工作流程引擎（Workflow Engine）**：若企業已有 BPMN 或 SOP 系統，可將其輸出作為 PolicyGuide 工作流程圖的輸入來源，降低政策編譯成本。
- **可觀測性平台**：將 verifier 的判斷、圖位置、補救措施寫入追蹤系統（如 OpenTelemetry），便於稽核與除錯。
- **RAG 與知識庫**：對於需要動態查詢政策細節的步驟，可讓 verifier 結合 RAG 檢索最新政策條文，再決定是否滿足節點條件。
- **微調與持續學習**：雖然閉源權重模型難以領域特定微調，但可將 PolicyGuide 產生的高品質合規軌跡作為未來開源模型或代理微調的訓練資料。

## 給不同背景讀者的閱讀建議

**初學者**：建議先從圖 2 的三種執行機制比較開始，理解「行動防護機制」與「PolicyGuide」的差別；接著閱讀適用場景與實作步驟，把 PolicyGuide 想像成一位「會記得整段對話進度的外部督導」，不需要立刻理解圖演算法細節。

**AI 工程師**：重點關注主動驗證器的實作架構、持久化圖狀態的設計，以及補救提示的生成邏輯；建議搭配 τ²-bench 的電信領域案例，實際 trace 一次「診斷–指示–驗證」流程，並思考如何將 verifier 嵌入現有的 ReAct 代理管線。

**研究人員**：論文的核心貢獻在於將「安全防護」與「工作流程執行」兩個問題統一為政策合規問題；建議深入分析政策拆解結果（程序性要求 vs. 有序工作流程要求）、Pass⁴ 的跨領域差異，以及 CRAFT 對抗性測試與工作流程層級驗證的設計。

**產品經理**：請聚焦於業務價值與落地風險：PolicyGuide 能顯著提升電信等結構化領域的通過率，但會增加延遲與對話長度；建議評估哪些高風險流程最適合優先導入，並規劃與現有客服系統、人工覆核機制的整合路徑。
