## 摘要翻譯

科學程式碼儲存庫（scientific code repositories）將數十年人類知識編碼於可執行模型（executable models）、方法（methods）與工具（tools）之中。然而，碎片化工具鏈（fragmented toolchains）、隱含領域慣例（implicit domain conventions）與專門正確性準則（specialized correctness criteria），使得這些知識難以轉化為可靠的學習經驗（reliable learning experience）——我們將此挑戰稱為科學經驗瓶頸（scientific experience bottleneck）。我們提出 ScienceIDE，這是一套將全球科學程式碼轉化為科學代理人（scientific agents）可程式化環境（programmable environments）的基礎設施（infrastructure）。在專家定義的科學案例（scientific cases）與驗收準則（acceptance criteria）引導下，代理人（agents）將儲存庫（repositories）轉化為可執行環境（executable environments），支援任務生成（task generation）、任務執行（task execution）與科學驗證（scientific verification）。這些環境為監督式微調（supervised fine-tuning, SFT）、強化學習（reinforcement learning, RL）與評估（evaluation）提供了共享基礎（shared foundation）。我們利用經驗證互動軌跡（verified interaction trajectories），訓練了 PhAI-IDE-72B、PhAI-IDE-9B 與 PhAI-IDE-4B。此模型家族（model family）在保留科學程式碼修復（held-out scientific-code repair），以及選定通用基準測試（selected general-purpose benchmarks）中的程式碼（code）、推理（reasoning）與知識（knowledge）方面均展現提升，顯示科學經驗能正向遷移（positive transfer）至更廣泛的能力（capabilities）。ScienceIDE 為代理人學習與科學實踐（scientific practice）的整合工作空間（integrated workspace）奠定基礎，使人類的科學軟體（scientific software）成為發展科學智慧（scientific intelligence）的共享底層（shared substrate）。

程式碼：https://github.com/aitofound/ScienceIDE

### 核心貢獻（3～5點）
- 提出 ScienceIDE 基礎設施，能將全球科學程式碼庫自動轉化為可執行、可程式化的科學代理人學習環境。
- 建立由專家定義科學案例與驗收準則引導的任務生成、執行與科學驗證流程。
- 利用經驗證互動軌跡訓練 PhAI-IDE 模型家族（72B／9B／4B），並在保留科學程式碼修復與通用基準測試上展現正向遷移。
- 為代理人學習與科學實踐整合工作空間奠定基礎，使科學軟體成為發展科學智慧的共享底層。

### 適合對象
適合對 AI 代理人、科學計算、程式碼大型語言模型、可驗證強化學習，以及希望將既有科學軟體轉化為可學習經驗的研究者與工程師閱讀。

## 深度分析

#### 方法論解析

ScienceIDE 的核心目標是將分散的科學程式碼庫（scientific codebase）轉換為代理人可學習環境（agent learnable environments），以緩解所謂的科學經驗瓶頸（scientific experience bottleneck）。整體流程可視為一條「科學經驗管線（scientific experience pipeline）」：從原始儲存庫（repository）出發，經由專家定義的科學案例（scientific cases）與驗收準則（acceptance criteria），逐步封裝成可執行環境（executable environments），再由環境專屬工廠（environment-specific factories）產生經驗證的任務，最終形成可供監督式微調（SFT）、強化學習（RL）與評估使用的軌跡資料。

**1. 從程式碼庫到科學模組（scientific module）**  
建構單位並非任意檔案群組，而是「擁有一致科學職責與可執行覆蓋率」的科學模組。AI 代理人（AI agents）首先檢視被固定的上游版本（pinned source）、授權、依賴與建構假設，執行官方測試（official tests）與範例，以觀察輸出格式、數值變異（numerical variability）、昂貴路徑與執行風險。接著代理人提出模組劃分，界定輸入輸出、演算法階段、擁有的實作路徑以及排除的職責；領域專家（domain experts）再審查並確認模組邊界。這種「專家—代理人協作」模式確保科學等價性（scientific equivalence）可被追蹤，而非僅是檔案層級的打包。

**2. 可執行環境的封裝**  
核准後的模組會與執行期（runtime）、科學驗證（scientific verification）機制一起封裝為環境。環境內含：可編輯的代理人工作空間（editable agent workspace）、經校準的檢查策略（calibrated checking policies）、私有驗證器（private verifier）以及參考輸出（reference outputs）。來源固定、依賴與觀察到的風險都附著於此可重複使用的執行期，從而將「能否執行」與「任務設計」解耦（decouple from task authoring）。

**3. 從官方測試到科學檢查（scientific checks）**  
驗證的基本單位是檢查（check）：固定輸入、可評分的輸出，以及對應的通過策略（pass policy）。通過策略有兩種形式：逐點策略（pointwise policy）比較每個評分值與參考值的絕對誤差是否在數值容差（numerical tolerances）內；聚合策略則評量整體分佈或趨勢。官方測試（official tests）即使沒有隨附參考答案，也可透過固定建構產生比較基準；若無官方來源，則需策展人同意成為自訂檢查。這種設計把隱含領域慣例（implicit domain conventions）轉化為可執行檢查（executable checks per environment）。

**4. 環境專屬工廠與任務生成**  
每個環境配備專屬工廠（factory），負責將任務配方（task recipes）與程式碼特定規則轉化為候選任務（candidate tasks）。任務需指定初始工作空間、交付物與驗證器。工廠產生的候選任務會經過驗證，確認其回合（episode）能支持評估、SFT 與 RL，才會被納入登錄檔（registry）。目前登錄檔包含 2,515 個修復任務（repair tasks）、295 個實作任務（implementation tasks）與 2 個加速任務（acceleration tasks）。

**5. 代理人互動與學習**  
一個回合（episode）是代理人與任務的單次互動，產出成品、互動軌跡（trajectory）與量測結果。通過的軌跡成為經驗證互動軌跡（verified interaction trajectories），進一步轉為分級軌跡（graded trajectories）與分級回饋（graded feedback）。這些資料透過通用介面（common interfaces）同時服務三種用途：SFT 資料、線上 RL 的可驗證獎勵（verifiable rewards），以及對保留環境或任務的評估。論文據此訓練了 PhAI-IDE-72B、PhAI-IDE-9B 與 PhAI-IDE-4B 三個模型，顯示科學經驗對程式推理（code reasoning）、一般推理與知識基準測試（knowledge benchmarks）具有正向遷移（positive transfer）。

#### 實驗數據解讀

由於提供的全文片段主要涵蓋方法論與部分結果，以下針對可取得的數據進行解讀，並指出其含義與限制。

**1. 登錄檔規模與任務分佈**  
目前 ScienceIDE 登錄檔（registry）收錄 2,515 個修復任務、295 個實作任務與僅 2 個加速任務。這顯示基礎設施在「修復」與「實作」兩類任務家族（task families）上已具備一定規模，但在將科學程式碼遷移至加速器（moving scientific codes to accelerators）這類長期科學工作（long-horizon scientific work）上仍處於非常早期的階段。加速任務數量稀少，可能反映兩個現實：其一，加速器移植涉及廠商工具鏈（vendor toolchain）與雙倍精度（double precision）等複雜決策，環境建構成本極高；其二，這正是論文所強調「瓶頸最尖銳、回報也最大」之處。

**2. 困難子集的預算耗盡率（budget exhaustion）**  
在困難子集（hard subset）上，任務平衡（task-balanced）後的預算耗盡率為 37.3%。這表示即使給予代理人完整操作預算，仍有超過三分之一的困難任務無法在限制內完成。該數字不宜直接視為失敗率，而應理解為：科學程式碼任務的長程規劃與多步驟執行仍具顯著挑戰。它同時也說明 ScienceIDE 作為評估平台能區分出不同難度，具備鑑別力。

**3. Fable/Astra 軌跡審查（trace review）的失敗模式**  
在 Fable/Astra trace review 中，大部分任務平衡的失敗源於參考慣例不匹配（reference-convention mismatches）。這是一個關鍵診斷：許多失敗並非科學計算本身錯誤，而是代理人輸出的格式、命名、單位或介面慣例與參考實作不一致。這凸顯了隱含領域慣例（implicit domain conventions）對科學驗證的影響，也暗示未來需要更強大的「慣例對齊」機制，例如透過範例驅動的輸出規範或自動慣例學習。

**4. PhAI-IDE 模型家族的遷移效果**  
論文指出，使用經驗證互動軌跡訓練的 PhAI-IDE-72B、PhAI-IDE-9B 與 PhAI-IDE-4B，在保留科學程式碼修復（held-out scientific-code repair）以及選定通用基準測試（selected general-purpose benchmarks）上均有提升。這支持了核心假設：科學程式碼經驗不僅能改善科學任務，也能促進更廣泛的程式推理與知識能力。然而，由於缺乏具體數值與對照基線，無法判斷提升幅度是否具統計顯著性，也無法區分是來自資料規模、任務難度還是模型規模效應。

#### 與現有研究的比較

**1. 相較於科學程式編寫與可再現性基準**  
現有科學程式編寫基準（scientific coding benchmarks）與可再現性基準（reproducibility benchmarks）主要用於評估代理人（evaluate agents），但通常不具備大規模產生與管理經驗的生產基礎設施（production infrastructure）。ScienceIDE 的差異在於：它把「評估」擴展為「持續學習的環境」，透過可執行儲存庫環境（executable repository environments）與環境專屬工廠，讓同一個環境能同時支持修復、實作、再現與加速等多種任務家族。

**2. 相較於一般程式碼代理基準（如 SWE-bench）**  
SWE-bench 等基準聚焦於真實 GitHub issue 的修復，驗證依賴現有測試；ScienceIDE 則進一步處理科學領域的特殊正確性準則（specialized correctness criteria），例如數值容差、物理守恒量、收斂性等。它將官方測試（official tests）與專家校準的通過策略結合，使「恢復科學結果（recover the science）」成為可執行契約（contract），而非僅是單元測試全過。

**3. 相較於加速器移植研究**  
過去將科學程式碼遷移至加速器（moving scientific codes to accelerators）多依賴手寫移植（hand-written port），並且常預設使用雙倍精度。ScienceIDE 提出把精度視為推導需求（derived requirement）而非預設（default），並讓驗證機制與任務編寫解耦，使任何任務——從注入缺陷（injecting a defect）到移植昂貴路徑（porting an expensive path）——都依「是否在容差範圍內（within tolerance）恢復科學結果」來評分。這是方法論上的重要改進。

**4. 主要限制**  
首先，專家策展成本高昂：每個科學模組都需要領域專家審查邊界、檢查策略與參考輸出，難以快速擴展到數萬個儲存庫。其次，加速任務僅 2 個，顯示最困難也最具價值的長期科學工作尚未被充分覆蓋。第三，參考慣例不匹配導致大量失敗，說明驗證器對輸出形式的敏感度可能過高，需要更穩健的科學等價定義。最後，目前釋出的內容主要為基礎設施程式碼，模型權重與完整資料集的可取得性尚不明確。

#### 可重現性評估

**1. 開放原始碼與基礎設施**  
論文提供 GitHub 倉庫（https://github.com/aitofound/ScienceIDE），並將 ScienceIDE 定位為開放基礎設施（open infrastructure）。登錄檔（registry）與命令列介面（CLI）可追蹤來源固定、依賴與出處（provenance），這對可再現性（reproducibility）是正面訊號。

**2. 環境封裝與依賴固定**  
每個環境都包含被固定的來源（pinned source）、依賴、觀察到的執行風險與私有驗證器。這種設計有助於降低異質工具鏈（heterogeneous toolchains）帶來的再現困難。然而，科學軟體（scientific software）常依賴特定編譯器（compilers）、數值函式庫、MPI、CUDA 等底層工具，實際建置仍可能面臨平台差異。

**3. 資料與模型權重**  
論文提到使用經驗證互動軌跡訓練 PhAI-IDE 模型家族，但並未明確說明訓練資料、模型權重或評估任務是否完全公開。若僅釋出環境建構工具而無預建環境與軌跡資料，其他研究者仍需耗費大量資源重新產生資料，可再現性會打折扣。

**4. 專家知識的再現門檻**  
即使程式碼開放，科學模組的審查、檢查策略校準與參考輸出確認仍需要領域專家知識。這使得「環境建構」本身成為可再現性的瓶頸，未來需要更多自動化或社群共筆機制來降低門檻。

#### 未來研究方向

**1. 擴大加速器與長期科學任務覆蓋率**  
目前加速任務僅 2 個，未來應優先針對 GPU、TPU、FPGA 等加速器移植建立更多環境，並設計多回合、長期科學工作（long-horizon scientific work）的評估協定，例如逐步將 CPU 雙倍精度核心改寫為混合精度加速器核心，同時維持數值容差。

**2. 自動化模組劃分與檢查校準**  
降低專家策展成本是規模化的關鍵。可研究如何讓 AI 代理人自動提出科學模組邊界、推薦觀察量與容差，並由專家僅做最終確認；同時發展從官方測試與文獻數值自動推導通過策略的方法。

**3. 慣例對齊與穩健驗證**  
針對參考慣例不匹配造成的失敗，未來可引入「慣例學習」模組：讓代理人從多個參考實作中歸納輸出格式、命名規則與單位慣例，或設計對慣例差異不敏感的科學等價驗證器。

**4. 多代理人協作與科學發現**  
ScienceIDE 目前聚焦於程式碼操作，但科學智慧（scientific intelligence）還包括提出有價值的問題（worthwhile questions）、設計介入（interventions）與從證據遷移教訓。未來可結合多代理人系統，讓一個代理人負責假設生成，另一個負責程式碼實作與驗證，形成探索導向工作（discovery-oriented work）的閉環。

**5. 課程式強化學習與模型蒸餾**  
利用已驗證軌跡設計由易到難的課程，可進一步提升強化學習（RL）效率；同時可將大模型（如 PhAI-IDE-72B）的科學經驗蒸餾到更小模型，推動科學智慧在邊緣或資源受限環境的應用。

**6. 社群驅動的開放科學生態**  
建立類似 Hugging Face 的科學環境共享平台，讓各領域研究者貢獻模組、檢查策略與任務，並以開放評估回饋持續擴充登錄檔，最終使全人類的科學軟體成為發展科學智慧的共享底層（shared substrate）。

## 論文問答

**Q1：什麼是「科學經驗瓶頸」，它為何是發展科學智慧的主要障礙？**
A：科學經驗瓶頸指的是科學程式碼庫中累積的數十年人類知識，難以自動轉化為代理人可學習的可靠經驗。這是因為科學儲存庫存在異質工具鏈、隱含領域慣例與專門正確性準則，使得可執行程式碼不一定能直接產生有意義的任務與可驗證的訓練訊號。若無法突破此瓶頸，語言模型與科學代理人便難以從真實科學軟體中學習，限制了科學智慧的規模化發展。

**Q2：現有的程式編寫基準與可再現性基準為何不足以解決科學智慧問題？**
A：現有基準多聚焦於評估代理人能否完成特定程式修復或再現任務，但缺乏將大量科學儲存庫系統性地轉為可訓練環境的生產基礎設施。它們通常只提供固定測試，卻未處理科學驗證所需的數值容差、物理量檢查與未明文慣例。因此，這些基準能評估能力，卻難以持續擴展經驗並支援監督式微調、強化學習與長期科學工作。

**Q3：為何科學程式碼庫是訓練科學代理人的潛在高價值資料來源，卻又難以直接使用？**
A：科學程式碼庫編碼了可執行的模型、方法與工具，蘊含豐富且經外部檢驗的訓練訊號，例如官方測試與數值模擬結果。然而，這些儲存庫的碎片化工具鏈與專門領域慣例，使得程式碼難以被穩定執行與重複驗證。此外，要將可執行程式碼轉化為帶有行為驗證、分級回饋與記錄互動的任務，需要大量領域專家介入與基礎設施支援。

**Q4：ScienceIDE 的核心技術流程是什麼？它如何將科學專業知識轉化為可重複使用的代理人經驗？**
A：ScienceIDE 的流程從釘選版本的科學儲存庫開始，由 AI 代理人檢視原始碼、依賴與建置假設，並與領域專家合作劃分科學模組與驗收準則。每個核准的模組會被封裝成可執行環境，包含可編輯的代理人工作空間、經校準的檢查策略與獨立的私有驗證器。環境專屬工廠再根據這些資產生成候選任務，經驗證後成為評估、監督式微調與強化學習的資料來源。

**Q5：什麼是「科學模組」，它與一般按檔案分組有何不同？為何這種劃分對環境品質至關重要？**
A：科學模組是圍繞一項連貫科學責任與可執行覆蓋範圍所定義的單元，而非僅將相關檔案放在一起。它明確標示輸入輸出、演算法階段、擁有的實作路徑與排除的責任範圍，使每個環境都有清晰的科學等價契約。這種劃分讓專家能針對科學邊界進行校準，也讓同一儲存庫中的共享求解器能支援多個模組而不混淆各自的驗收準則。

**Q6：ScienceIDE 在設計上如何確保科學驗證與任務編寫能夠獨立運作？這帶來什麼好處？**
A：ScienceIDE 將每個環境的驗證契約固定為可執行檢查，並與任務編寫解耦，因此無論任務是注入缺陷、實作新功能或移植昂貴路徑，都只需檢查結果是否在容差範圍內恢復科學結果。這種設計讓領域專家專注於定義科學邊界與驗收準則，而環境專屬工廠則可重複使用這些決策來大量生成不同任務家族。如此一來，專家心力不必耗費在每一個個別任務上，顯著提升了可擴展性。

**Q7：論文使用了哪些模型與資料來驗證 ScienceIDE 的訓練價值？**
A：作者利用經驗證互動軌跡訓練了 PhAI-IDE-72B、PhAI-IDE-9B 與 PhAI-IDE-4B 三個不同規模的模型家族。這些軌跡來自科學代理人與可執行環境的互動，並經過科學驗證與分級回饋，確保訓練訊號的可靠性。透過這種方式，模型能同時學習程式碼修復、實作與科學推理等多種長期科學工作所需的行為。

**Q8：ScienceIDE 訓練出的模型在實驗中表現如何？這些結果說明了什麼？**
A：PhAI-IDE 模型家族在保留的科學程式碼修復任務上取得進步，顯示其能將學習到的科學經驗遷移到未見過的程式碼問題。此外，模型在選定的通用程式、推理與知識基準測試上也有所提升，呈現出從科學經驗到更廣泛能力的正向遷移。這些結果初步證明，高品質的科學程式碼互動軌跡能夠增強語言模型的綜合能力，而不僅限於特定科學任務。

**Q9：在困難子集與軌跡審查中，作者觀察到哪些主要失敗模式？這對未來改進有何啟示？**
A：在困難子集上，任務平衡的預算耗盡率達到 37.3%，顯示長期科學工作對代理人而言仍具挑戰性。Fable/Astra 軌跡審查則發現，參考慣例不匹配是大部分任務平衡失敗的主因，意味著隱含領域慣例與參考實作不一致會嚴重影響驗證結果。這些發現指出，未來需要更精細地校準檢查策略、強化代理人對領域慣例的理解，並提升環境說明文件的完整性。

**Q10：ScienceIDE 可支援哪些實際科學任務類型？請舉例說明。**
A：ScienceIDE 目前登錄的任務家族包括 2,515 個修復任務、295 個實作任務與兩個加速任務，涵蓋從除錯到效能移植的多種科學工作。例如，修復任務會刻意注入缺陷，要求代理人恢復科學結果在容差範圍內；加速任務則挑戰代理人將科學程式碼遷移至加速器，同時維持數值正確性。由於同一環境可重複使用於不同任務家族，ScienceIDE 能成為科學實踐與代理人學習的整合工作空間。

**Q11：在實務上，領域專家與 AI 代理人在 ScienceIDE 中各自扮演什麼角色？這種分工有何優勢？**
A：領域專家負責定義科學責任、驗收準則與經校準的檢查策略，並審查模組邊界與科學等價契約；AI 代理人則協助檢視原始碼、建置環境、提出模組劃分與實作實驗轉接器。這種分工讓專家將心力集中於科學邊界與新目標，而重複性的環境建置與任務生成則由代理人與工廠自動化處理。結果是專家知識被轉化為可重複使用的可執行環境，能持續產生新的訓練與評估資料。

**Q12：ScienceIDE 對科學研究與人工智慧發展可能帶來哪些長遠影響？**
A：ScienceIDE 將人類累積的科學軟體轉化為共享底層，使科學程式碼庫成為發展科學智慧的共同基礎。透過開放登錄檔，研究人員可以在特定領域訓練與評估代理人，並將其應用回實際科學工作。長遠來看，這種整合工作空間有助於縮短科學發現週期，並促進可驗證、可重複的科學代理人能力持續演進。

**Q13：作者承認 ScienceIDE 目前有哪些主要限制？**
A：目前登錄的加速任務僅有兩個，顯示在將科學程式碼遷移至加速器這類高價值但困難的任務家族上，規模仍相當有限。此外，困難子集仍有顯著的預算耗盡率，且參考慣例不匹配導致大量失敗，反映環境校準與代理人理解仍有改進空間。整體而言，擴展到更多科學領域與任務類型仍需要持續的專家策展與基礎設施投入。

**Q14：哪些失敗案例特別凸顯科學經驗瓶頸的難度？**
A：在 Fable/Astra 軌跡審查中，參考慣例不匹配佔據了大部分任務平衡失敗，顯示即使結果數值正確，若不符合領域內隱含的輸出格式或命名慣例，仍會被判定為失敗。另一方面，困難子集中 37.3% 的任務在達到預算上限前未能完成，說明長期科學工作需要更強的規劃與工具使用能力。這些案例凸顯科學驗證不僅是程式正確性，更涉及領域慣例與長程決策的綜合挑戰。

**Q15：針對上述限制，作者與社群未來可以朝哪些方向改進 ScienceIDE？**
A：未來可以擴充登錄檔中的科學模組數量，特別是增加加速任務與跨領域任務家族，以涵蓋更廣泛的科學實踐。同時，應強化檢查策略的校準流程，讓參考慣例與數值容差更透明，並發展能自動偵測與適應隱含領域慣例的代理人。最終，ScienceIDE 可進一步整合為結合科學實作、代理人學習與同儕審查的開放平台，讓科學智慧在真實且不斷演化的科學軟體生態中持續成長。

## 適用場景

1. **科學軟體缺陷自動修復與回歸驗證**  
   將長期維護的數值模擬、計算化學、氣候或流體力學程式庫轉為可執行環境，自動注入缺陷並要求代理人在數值容差內恢復科學結果，用於產生大量經驗證的科學程式碼修復任務與回歸測試資料。

2. **跨加速器科學程式碼遷移與低精度驗證**  
   針對需要從 CPU 移植到 GPU、TPU 或國產 AI 晶片的科學程式碼，建立「恢復科學結果」為驗收準則的可執行檢查，讓代理人學習自動改寫昂貴計算路徑，並以專家校準的數值容差判斷雙倍精度是否為真正的推導需求。

3. **研究實驗室再現性與教學環境建置**  
   把論文附帶的儲存庫或實驗室內部科學軟體打包成版本化、可執行的儲存庫環境，提供學生與研究人員一致的執行介面、官方測試與科學驗證，降低異質工具鏈造成的再現性問題。

4. **科學 AI 代理人的持續學習與評估平台**  
   作為監督式微調（SFT）資料、強化學習（RL）可驗證獎勵與保留評估的共享基礎，支援科學代理人在真實程式碼、資料與模擬器中進行長期探索導向工作，並記錄分級軌跡以供迭代訓練。

5. **企業研發知識沉澱與方法審查**  
   將數十年累積的科學程式碼庫轉為代理人可學習環境，把隱含領域慣例與專門正確性準則固化為可執行檢查，協助新進工程師理解方法邊界，並自動化部分程式碼審查與方法驗證流程。

## 實作前置條件

### 資料與領域資產
- **版本化科學程式碼庫**：需有固定的上游版本、清晰的授權、完整的相依性與建置說明。
- **官方測試與範例**：單元測試、迴歸測試或隨軟體釋出的範例問題，作為科學檢查的基礎。
- **專家定義的科學案例**：包含模組職責、輸入輸出、演算法階段、排除範圍與數值容差。
- **參考輸出與驗收準則**：可來自已發表數值、收斂行為、守恆量，或經領域專家同意的自訂檢查。

### 運算資源
- **環境執行叢集**：足夠執行官方測試與代理人互動的容器或虛擬機資源，科學模擬通常需要 CPU/GPU 與較大記憶體。
- **代理人訓練資源**：若要走 PhAI-IDE 路線，需準備大型語言模型微調與強化學習所需 GPU（如 72B/9B/4B 規模對應的叢集）。
- **儲存與版本控制**：用於保存原始碼釘選、參考輸出、互動軌跡與分級回饋。

### 技能與團隊
- **領域專家**：負責劃分科學模組邊界、確認等價契約與校準通過策略。
- **AI/ML 工程師**：設計環境專屬工廠、代理人互動迴圈、SFT/RL 訓練流程。
- **基礎設施工程師**：負責容器化、CI/CD、登錄檔維護與可再現執行環境。
- **數值分析人員**：協助設定數值容差、判斷參考慣例不匹配與檢查偽陽性。

## 實作步驟建議

1. **選定目標儲存庫與科學模組**  
   釘選上游版本，盤點授權、相依性與建置假設。由代理人輔助檢視程式碼，再經領域專家審查，依「科學職責」與「可執行覆蓋率」劃分模組，而非僅按檔案群組。

2. **建立可執行環境**  
   將核准的模組打包成包含可編輯代理人工作區、執行期與官方測試的環境。使用容器化技術固定工具鏈，記錄建置風險與觀察到的數值變異。

3. **定義科學驗收契約**  
   把官方測試與範例對應到模組職責，決定保留、排除或標記為缺口。為每個檢查設定通過策略：點對點比較、收斂檢查或守恆量檢查，並明確數值容差與參考慣例。

4. **開發環境專屬任務工廠**  
   針對修復、實作、再現或加速等任務家族，設計能產生有效初始工作空間、交付物與驗證器的工廠。任務必須經過行為驗證，確保單一互動軌跡可同時支援評估、SFT 與 RL。

5. **產生並驗證互動軌跡**  
   讓代理人與任務互動，產出成品、軌跡與量測結果。透過私有驗證器與科學檢查進行分級，過濾無效任務，並保留成功與失敗軌跡作為學習資料。

6. **訓練與評估模型**  
   使用經驗證互動軌跡建立 SFT 資料，並以可驗證獎勵進行強化學習。務必保留部分環境或任務家族不參與訓練，用於測量對保留科學程式碼修復與通用基準測試的正向遷移。

7. **發布至登錄檔並持續迭代**  
   將環境、工廠與檢查策略註冊到開放或內部登錄檔，與科學實踐社群共享。隨著新模組、新任務家族與新參考慣例加入，定期重新校準檢查策略。

## 潛在風險與注意事項

| 風險 | 說明 | 建議緩解方式 |
|---|---|---|
| **參考慣例不匹配** | 代理人輸出在數學上正確，但與參考實作的格式、單位或慣例不同，導致任務平衡失敗率偏高。 | 在軌跡審查中區分「科學錯誤」與「慣例不匹配」，必要時放寬或標準化驗證器。 |
| **數值容差設定不當** | 容差過嚴會產生偽陰性，過鬆則讓錯誤解法過關。 | 以官方測試、收斂行為與專家知識共同校準，並對每個檢查記錄容差來源。 |
| **異質工具鏈導致不可再現** | 科學軟體常依賴特定編譯器、MPI、CUDA 版本或外部資料。 | 完整釘選原始碼、相依性與執行期映像檔，並在隔離環境中執行。 |
| **任務工廠產生無效任務** | 自動生成的缺陷或實作任務可能過於簡單、無解或與科學目標無關。 | 加入任務驗證階段，確保每個候選任務都能產生有意義的學習訊號。 |
| **獎勵駭入與驗證器過擬合** | 代理人可能找到繞過檢查的捷徑，而非真正修復科學問題。 | 使用多樣化檢查、保留測試與人類軌跡審查，避免單一驗證器被利用。 |
| **專家標註瓶頸** | 模組邊界與驗收準則需要大量領域專家時間。 | 讓專家專注於科學邊界與新目標，重複性的任務生成與檢查執行交由自動化流程處理。 |
| **授權與資料隱私** | 科學程式碼庫可能涉及開源授權衝突或敏感研究資料。 | 在打包環境前進行授權稽核，敏感資料使用私有登錄檔與存取控制。 |

## 與其他技術的整合建議

- **CI/CD 與版本控制**：將環境建置、官方測試與科學檢查納入 GitHub Actions、GitLab CI 或 Jenkins，確保每次原始碼釘選都能自動驗證可再現性。
- **容器與編排**：使用 Docker/Singularity 固定執行期，並以 Kubernetes 或 HPC 排程器（如 Slurm、PBS）管理大規模代理人互動與科學模擬。
- **LLM 代理人框架**：可將 ScienceIDE 的通用介面對接到 LangChain、AutoGPT、SWE-agent 或自研代理人迴圈，讓現有語言模型在科學環境中執行行動。
- **強化學習與微調基礎設施**：透過 Ray RLlib、OpenRLHF、TRL 或類似框架，把分級軌跡轉為 SFT 資料與可驗證獎勵，支援線上 RL 訓練。
- **實驗追蹤與 MLOps**：使用 Weights & Biases、MLflow 或自研系統記錄軌跡、獎勵、通過率與數值收斂行為，便於比較不同環境與模型變體。
- **資料與模型版本化**：搭配 DVC、Git LFS 管理參考輸出、預訓練檢查點與大型軌跡資料集。
- **現有程式碼智慧工具**：可與 GitHub Copilot、Codeium 或內部程式碼助手整合，讓科學環境成為這些工具的驗證後端，提供可執行的正確性回饋。

**初學者**：先聚焦「把科學程式碼變成可執行、可評分的學習環境」這個核心概念。不必一開始就理解 720 億參數模型的訓練細節，重點是認識科學經驗瓶頸、可驗證獎勵與任務工廠如何讓 AI 從真實程式碼中學習。

**AI 工程師**：請深入閱讀技術流程圖與環境建置章節，特別注意「驗證機制與任務編寫解耦」的設計、環境專屬工廠的實作方式，以及如何將互動軌跡同時轉為 SFT 資料與 RL 獎勵。這會直接影響你設計代理人迴圈與訓練管線的方式。

**研究人員**：建議從科學經驗瓶頸與正向遷移的論證切入，關注模組邊界、等價契約、數值容差校準與保留評估方法。這些是判斷該基礎設施能否真正產出可靠科學智慧、而非僅是另一個程式碼基準的關鍵。

**產品經理**：把重點放在適用場景、專家投入產出比與風險章節。理解為何需要領域專家定義驗收準則、為何要容器化與版本控制，以及如何把 ScienceIDE 嵌入現有的研發流程與 CI/CD，將有助於規劃落地路徑與商業價值。
