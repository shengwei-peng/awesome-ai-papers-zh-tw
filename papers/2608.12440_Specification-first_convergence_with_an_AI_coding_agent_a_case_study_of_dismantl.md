## 摘要翻譯

本文報告一項單一、全程記錄的大規模架構重構（large-scale architectural refactoring）案例研究，由 AI 編碼代理（AI coding agent）在規格優先協定（specification-first protocol）下執行，其生成之程式碼未經人工程式碼審查（human code review），亦無預先存在之測試預言（test oracle）可驗證目標行為。此任務——在一個大型且相互依賴的程式碼庫中拆除一項核心架構不變量（core architectural invariant）——經作者評估，透過漸進式重構（incremental refactoring）實際上不可行，傳統上這類變更往往須以重寫處理。在本文所述的協定下，代理成功完成了該任務。

該系統為一生產環境的 TypeScript 應用程式（TypeScript application），包含 717,725 行程式碼、橫跨 3,648 個檔案。此任務需要拆除一項核心生命週期不變量（core lifetime invariant）：即 UI 面板（UI panel）在 AI 請求（AI request）期間保持開啟之保證。目標行為為使串流生成（streaming generation）在面板關閉後仍能存活，並於重新開啟時重新附加至同一個即時串流（live stream），且不遺失、不重複。

協定流程為：由代理撰寫形式規格（formal specification），進行 14 個精煉循環（refinement cycles）以對照原始碼稽核該規格，接著進行原子式實作（atomic implementation），再透過編譯/測試回饋迴路（compile/test feedback loop），最後進行 17 個驗證循環（verification cycles）以對照凍結規格（frozen specification）稽核程式碼。在 31 個稽核回合（audit passes）中，於任何人執行程式前已修正 201 項缺陷（defects）。收斂準則（convergence criterion）為實證性：連續兩個驗證回合皆為零發現（zero findings）。

此變更涉及 189 個檔案（其中 31 個為新增）；若計入萃取階段（extraction phase），兩次提交（commits）共計 288 個檔案、34,770 新增行數（insertions）、16,422 刪除行數（deletions）。在首次及約三十個後續工作階段（sessions）中，軟體均按規格運作，未觀察到任何錯誤。耗時：三天；成本：2,430 美元。

完整的規格與原始工作階段日誌（以法文撰寫，超過 1,500 頁）已作為證據公開，可供檢視整個流程，並可提交給語言模型（language model）進行一致性檢查（consistency checking）。

### 核心貢獻（3～5點）
- 提出並驗證「規格優先收斂」（Specification-first convergence）協定，使 AI 編碼代理得以在無人工程式碼審查、無測試預言的情況下，完成傳統上需重寫才能處理的大規模架構重構。
- 成功拆除一個 717,725 行、3,648 個檔案的生產環境 TypeScript 應用程式中的核心生命週期不變量，讓串流生成能在 UI 面板關閉後存活並於重新開啟時無損重新附加。
- 以實證收斂準則（連續兩次驗證回合零發現）確保品質，在任何人執行程式前即透過 31 個稽核回合修正 201 項缺陷。
- 公開完整的形式規格與超過 1,500 頁法文原始工作階段日誌，作為可檢視、可提交語言模型進行一致性檢查的完整證據鏈。

### 適合對象
本論文最適合軟體工程研究者、代理式軟體工程（agentic software engineering）與 AI 輔助程式開發實務者、大型 TypeScript 或前端應用架構師，以及對大規模重構、形式規格驅動開發、無測試預言驗證方法感興趣的讀者。對於正在評估如何將 AI 編碼代理應用於複雜、高風險維護任務的技術主管與資深工程師，本文亦具高度參考價值。

## 深度分析

#### 方法論解析

本文提出的核心方法可稱為 **Specification-first convergence（規格優先收斂）**，其目標並非在程式碼生成後再進行 **human code review（人工程式碼審查）**，而是把品質閘門（quality gate）向上游移動：先讓 **AI coding agent（AI 編碼代理）** 針對真實程式碼寫出一份 **formal specification（形式規格）**，反覆稽核到規格與原始碼一致，再將規格凍結，作為後續實作與驗證的單一參照。

整個協定可拆解為以下階段：

1. **Extraction phase（萃取階段）**  
   在動手改程式之前，代理先從 717,725 行、3,648 個檔案的 TypeScript 應用程式中，萃取出與目標子系統相關的程式碼。這一步產生了額外的檔案變動，使得兩次 **commits（提交）** 總計觸及 288 個檔案。萃取的目的在於讓代理掌握實際的 **dependency graph（依賴圖）**，避免規格流於想像。

2. **規格撰寫與精煉（Formal specification + refinement cycles）**  
   代理針對「拆除 **core lifetime invariant（核心生命週期不變量）**」這個任務撰寫規格：原本系統保證 **UI panel（UI 面板）** 在整個 **AI request（AI 請求）** 期間必須保持開啟；目標行為則改為 **streaming generation（串流生成）** 必須能在面板關閉後繼續存活，並在重新開啟時 **reattach** 到同一條 **live stream（即時串流）**，且不能遺失或重複內容。  
   接著進行 14 個 **refinement cycles（精煉循環）**，也就是讓代理反覆把規格對照原始碼進行 **audit passes（稽核回合）**，找出規格與程式碼現況之間的落差、遺漏的隱含不變量、邊界條件等，並修正規格。這個階段的重要性在於：規格必須「扎根」於真實程式碼，而不是代理的幻覺。

3. **Frozen specification（凍結規格）**  
   當規格經過連續稽核不再產生發現時，規格被凍結。凍結意味著後續實作與驗證都必須以這份文件為準，不能因為實作困難就回頭改規格。這份外部文件成為代理自我檢查的客觀參照，也是本方法與一般「讓第二個代理來審查」做法的關鍵差異。

4. **Atomic implementation（原子式實作）**  
   代理根據凍結規格一次性產出所有程式碼變更，而非採用 **incremental refactoring（漸進式重構）**。作者認為這個任務若用漸進式重構幾乎不可行，因為核心不變量橫跨大量相依檔案，任何中間狀態都可能導致系統崩潰。原子式實作雖然風險較高，但配合後續驗證迴路，可避免「改到一半」的不一致狀態。

5. **Compile/test feedback loop（編譯/測試回饋迴路）**  
   程式碼生成後，先透過編譯器與既有測試套件檢查型別錯誤、語法錯誤與回歸問題。需要強調的是，這裡沒有 **test oracle（測試預言）** 能驗證新行為——因為「面板關閉後串流仍然存活」這個行為原本並不存在，舊測試不可能涵蓋它。編譯/測試迴路只能排除低階錯誤，無法證明目標行為正確。

6. **Verification cycles（驗證循環）**  
   實作完成後，進入 17 個 **verification cycles（驗證循環）**。此時啟動一個全新的代理工作階段（fresh session），讓它把生成的程式碼與凍結規格逐條比對，找出不符合規格的 **defects（缺陷）**。這裡的檢查者雖是同一個模型的全新會話，但關鍵在於它沒有參與實作，且手邊有凍結規格作為外部參照，因此能降低自我審查的偏誤。

7. **Convergence criterion（收斂準則）**  
   收斂標準是經驗性的：連續兩次 **verification passes（驗證回合）** 都達到 **zero findings（零發現）**。這比單次零發現更嚴格，可降低僥倖通過的機率。整個流程共 31 個稽核/驗證回合，修正了 201 個缺陷，才讓人類第一次執行程式。

此外，作者提到代理運作在一個約 250,000 字元的 system prompt 下，其中累積了數百條從過往失敗中歸納出的規則。這與 Davis 等人提出的 governance substrate 概念類似：透過不斷加長、加嚴的外部約束，來彌補模型本身在長程任務中的不穩定性。代理也被設計成「提出 patch」而非直接寫檔，這與 SWE-agent 的研究發現一致：編輯介面會顯著影響可靠性。

總結來說，這個方法論的創新不在於「讓 AI 寫更多程式碼」，而在於把「意圖」從「實作」中分離出來，並用一份凍結的規格作為雙方可共同檢視的客觀標準。這使得超大規模、跨檔案的架構變更有機會在沒有人工逐行審查的情況下收斂。

#### 實驗數據解讀

本研究的數據呈現出一個高強度、反覆收斂的過程，值得逐項剖析：

| 指標 | 數值 | 意義 |
|---|---|---|
| 程式碼規模 | 717,725 行 / 3,648 檔案 | 真實生產級 TypeScript 應用程式，非玩具範例 |
| 變更範圍 | 189 檔案（31 個新檔） | 直接與拆除生命週期不變量相關 |
| 含萃取階段總計 | 288 檔案、34,770 insertions、16,422 deletions | 淨增約 18,348 行，規模接近小型重寫 |
| 稽核/驗證回合 | 31 次（14 規格精煉 + 17 程式碼驗證） | 顯示規格與實作都經過多輪收斂 |
| 修正缺陷數 | 201 個 | 在人類執行程式前已排除 |
| 耗時 | 3 天 | 相較傳統重寫或大型重構顯著縮短 |
| 成本 | USD 2,430 | 以代理運算成本計算 |
| 後續觀察 | 首次與約 30 次後續工作階段均未發現 bug | 經驗性運作品質指標 |

首先，**201 個缺陷** 這個數字本身具有雙重意義。一方面，它說明若沒有嚴謹的稽核迴路，單靠 AI 一次性生成 189 個檔案的變更，品質會非常不穩定；另一方面，這 201 個缺陷全都在人類執行程式前被發現並修正，顯示規格優先協定確實能扮演強力的品質閘門。平均每次稽核回合發現約 6.5 個缺陷，但這個平均值會遮蔽收斂趨勢：合理推測前幾回合發現的缺陷遠多於後期，最終才趨近於零。

其次，**連續兩次 zero findings** 的收斂準則雖然嚴格，但仍屬於「程序性保證」而非「語意保證」。也就是說，它證明代理已經無法從凍結規格中找出程式碼的不一致，但並不保證規格本身完備，也不保證所有隱含不變量都被涵蓋。這是沒有 test oracle 時無可避免的局限。

第三，**成本與時間** 極具討論價值。以 2,430 美元、3 天完成一個橫跨 189 個檔案、涉及核心架構不變量的變更，無論是相較於人類團隊重寫，還是相較於長達數週的漸進重構，都顯得極具競爭力。然而，這個數字可能低估了前置準備成本：250,000 字元的 system prompt、萃取階段的設計、以及作者對系統的深入理解，都是長期累積的投資。若把這些攤提進去，單次任務的邊際成本雖低，但進入門檻並不低。

第四，**「未觀察到 bug」** 的聲稱需要謹慎解讀。作者報告首次執行與後續約 30 個工作階段都沒有發現錯誤，但這只是有限的手動/實際使用觀察，並非系統性測試覆蓋。對於串流生成這類涉及並行、生命週期與狀態重新附接的行為，邊界條件（例如網路中斷、快速開關面板、多個並行 AI request）未必在 30 次使用中被觸及。因此，這個數據支持「流程能收斂到可運作狀態」，但尚不足以宣稱「完全正確」。

最後，**變更規模** 值得注意。34,770 行新增與 16,422 行刪除的總量，已經接近許多專案所謂的「重寫」規模。作者卻將其定位為「重構」，這暗示規格優先方法可以把傳統上需要重寫的任務，轉化為可控的大型重構。這也是本文最具挑釁性的主張之一。

#### 與現有研究的比較

本文與當前 **agentic software engineering（代理式軟體工程）** 的主流研究處於互補位置，主要差異可從以下幾個軸線來看：

**1. 相對於 SWE-bench 與 SWE-bench Pro**  
SWE-bench 系列假設存在一個 **test oracle（測試預言）**：正確行為已經被人類寫成的測試所編碼，代理的任務是找到能通過測試的 patch。本文的任務完全不適用這個框架——目標行為「面板關閉後串流仍然存活」原本不存在，因此沒有現成測試可以滿足。SWE-bench Pro 報告即使使用統一 scaffold，目前系統解析率仍低於 45%，而本文則展示了一個沒有 oracle 時的替代路徑：先建立規格，再讓實作收斂到規格。

**2. 相對於 Loop engineering / Harness engineering**  
Addy Osmani 提出的 **loop engineering（迴路工程）** 以及 Anthropic、OpenAI 的相關實踐，強調建立外層系統來分配工作、檢查結果、記錄狀態。Anthropic 特別建議用「沒有記憶的第二個代理」來審查程式碼，以減少偏誤。本文的協定採用了類似精神，但做法不同：檢查者是同一個模型的 fresh session，真正的分離來自於「凍結規格」這個外部參照，而非檢查者的身份。這與研究發現「模型若沒有外部參照而僅是自我修訂，品質不會提升甚至會變差」的結論一致。

**3. 相對於 Review bottleneck 文獻**  
近期研究指出，AI 輔助開發雖然增加了 pull request 數量，卻使審查時間增加高達 91%，整體交付指標並未改善。本文直接回應這個 **review bottleneck（審查瓶頸）**：當變更跨數百個相依檔案時，人類審查者無法在 working memory 中掌握整個 dependency graph，因此傳統審查會失效。規格優先方法把審查對象從「生成後的程式碼」轉為「生成前的意圖」，試圖繞過這個瓶頸。

**4. 相對於 Davis 等人的 Governance Substrate**  
Davis 等人報告他們的治理底層在 12 週內累積到 116 萬行程式碼，包含文件、靜態與動態分析、工具鏈等。本文的 system prompt 約 25 萬字元，規模較小，但概念類似：都是把反覆觀察到的代理失敗轉化為持久的外部約束。兩者共同指向一個趨勢：讓 AI 代理可靠地處理複雜任務，關鍵不在於單次提示工程，而在於長期累積的治理結構。

**主要限制與批評空間：**

- **單一個案（n=1）**：本文是單一、刻意挑選的壓力測試，無法推論到其他領域或任務類型。  
- **沒有獨立人工程式碼審查**：雖然流程宣稱成功，但缺乏第三方人類審查來驗證是否真的沒有重大缺陷。  
- **規格的完備性無法被驗證**：如果規格本身遺漏了關鍵不變量，後續所有驗證都會跟著漏掉。  
- **原子式實作的風險**：一旦規格有誤，一次性大規模變更的 rollback 成本很高。  
- **語言與可及性**：規格與日誌為法文，雖然作者主張這是透明證據，但對多數研究者而言增加了理解門檻。

總體而言，本文不是要在 SWE-bench 上追求更高分數，而是要開拓一個「無 oracle 的大型架構變更」問題空間，並提出一個可行的程序性解決方案。

#### 可重現性評估

可重現性可分為三個層次來評估：**程序透明性**、**方法複製性**、**結果再現性**。

**程序透明性：高**  
作者公開了完整的 formal specification（形式規格）與 raw session logs（原始工作階段日誌），總計超過 1,500 頁法文。這在 AI 編碼代理研究中相當罕見，允許外部讀者檢視代理如何從規格精煉走到程式碼驗證，也允許把這些材料餵給另一個 **language model（語言模型）** 進行 **consistency checking（一致性檢查）**。對於質疑流程是否真如所述收斂的人，這些日誌提供了可檢視的證據。

**方法複製性：中**  
規格優先收斂的協定本身可以在其他程式碼庫上複製：只要建立萃取階段、讓代理撰寫規格、進行 refinement cycles、凍結規格、原子式實作、再進行 verification cycles，並以連續兩次 zero findings 為收斂準則即可。然而，本文並未公開實際的 system prompt、agent harness、工具鏈細節，也沒有說明如何設計 audit passes 的具體提示。因此，其他團隊可以複製概念，但難以精確複製同一套執行環境。

**結果再現性：低**  
由於目標系統是生產級 TypeScript 應用程式，原始碼極可能未開源，因此無法讓其他研究者重新執行同樣的重構任務。此外，商用 language model API 具有非確定性，即使使用相同提示，不同時間、不同溫度參數或不同模型版本都可能產生不同結果。日誌記錄的是一次特定軌跡，而非可重複的實驗。

#### 未來研究方向

本文開啟了多條值得後續探索的研究路線：

**1. 規格語言與工具鏈的標準化**  
目前規格以自然語言（法文）撰寫，雖然彈性高，但難以自動化檢查。未來可發展結構化的規格語言或領域特定語言（DSL），讓 frozen specification 能與程式碼進行更嚴謹的對照，甚至結合形式化方法。

**2. 從規格自動生成 Test oracle**  
既然本文任務沒有現成 test oracle，未來可研究如何從 formal specification 自動合成測試案例，把「規格優先」與「測試優先」橋接起來。這將彌補目前僅靠經驗觀察的品質保證缺口。

**3. 無 Oracle 重構基準的建立**  
可擴充 SWE-bench 類型的基準，加入「目標行為尚未存在、無現成測試」的任務，專門評估 specification-first 代理的表現。這需要設計新的評量指標，例如規格完備性、收斂回合數、人類驗收率等。

**4. 檢查者身份的系統性比較**  
本文使用 fresh session 的同一模型作為 checker。未來可比較：不同模型 checker、相同模型但不同 system prompt、人類 checker、以及結合靜態分析工具的 checker，以找出最可靠的審查配置。

**5. 缺陷分類與代理失敗模式分析**  
對 201 個 defects 進行分類（例如：狀態管理錯誤、生命週期遺漏、型別不一致、邊界條件遺漏等），可以幫助研究者理解 AI 代理在大型重構中最容易失敗的環節，並據此改進 system prompt 與工具鏈。

**6. 原子式 vs. 漸進式實作的比較**  
本文選擇 atomic implementation 是基於任務特性，但未提供與 incremental refactoring 的對照實驗。未來可在類似任務上比較兩種策略的收斂速度、缺陷數與最終品質。

**7. 人機協作的安全邊界**  
「沒有人工程式碼審查」在生產環境中極具爭議。未來研究可探討：哪些類型的變更可以安全地移除人類審查？哪些必須保留人類把關？如何設計分級治理機制？

**8. 多語言與跨文化規格研究**  
由於本文規格使用法文，未來可探討規格撰寫語言是否影響代理的理解與一致性檢查效果，並發展多語言規格標準。

**9. 長期維護與技術債追蹤**  
規格優先產出的大型變更，在後續維護中是否比傳統重構更容易理解與修改？凍結規格能否成為長期技術文件？這些都是軟體維護領域的重要問題。

**10. 成本—品質最適化**  
31 個 audit passes 與 201 個缺陷修正是否為必要？是否存在更少的回合數就能達到相同品質？透過更大規模實驗，可建立成本模型並優化代理工作流程。

總結來說，這篇論文不僅提供了一個引人注目的個案，更為「無 oracle、大規模、架構層級的 AI 代理軟體工程」奠定了方法論雛形。後續研究若能補強可重現性、建立標準化工具，並與形式化驗證及測試生成結合，將有機會把規格優先收斂從個案方法提升為可規模化的工程實踐。

## 論文問答

**Q1：這篇論文處理的核心問題是什麼？**
A：本研究處理的是一個大型生產級 TypeScript 程式碼庫中的核心架構不變量拆除問題，具體而言，是要讓 AI 串流生成能夠在 UI 面板關閉後繼續存活，並於重新開啟時重新連接到同一個即時串流。該系統規模達到 717,725 行程式碼、3,648 個檔案，而這次變更觸及了 189 個檔案。作者評估這類變更傳統上幾乎無法透過漸進式重構安全完成，通常只能選擇重寫整個系統。

**Q2：為什麼現有的 AI 編碼代理與人工程式碼審查方法無法有效處理此任務？**
A：現有的 AI 編碼代理雖然在孤立、自包含的任務上表現出色，但當單一變更跨越數百個相互依存的檔案並需要同時維護數十個隱含不變量時，人工程式碼審查會成為嚴重的瓶頸。相關研究顯示，AI 輔助開發雖然產出更多拉取請求，但審查時間可能增加高達 91%，因為沒有審查者能夠在短期工作記憶中完整掌握如此龐大的依賴圖。此外，這個任務沒有預先存在的測試預言，因為目標行為——面板關閉後生成仍然存活——在變更之前並不存在，所以傳統的 SWE-bench 式評估範式無法直接套用。

**Q3：這類架構重構為什麼重要？**
A：核心生命週期不變量的拆除直接影響使用者體驗與系統架構彈性，例如使用者可以關閉面板後重新開啟，而不遺失或重複生成內容。在生產環境中，這類需求經常出現，但傳統上因為風險過高而被迫擱置，或以成本高昂的重寫方式處理。能夠安全地進行此類大規模架構重構，意味著軟體維護成本可以顯著降低，同時保留既有系統的投資與領域知識。

**Q4：規格優先收斂協定的核心步驟是什麼？**
A：該協定首先由 AI 編碼代理撰寫形式規格，接著進行 14 個精煉循環，將規格與原始碼反覆稽核比對以確保規格符合現實系統。規格凍結後，代理進行原子式實作，並透過編譯與測試回饋迴路修正語法與執行期問題。最後進行 17 個驗證循環，將程式碼與凍結規格比對，直到連續兩次驗證回合都達到零發現，作為收斂準則。

**Q5：與現有方法相比，規格優先收斂的關鍵創新在哪裡？**
A：關鍵創新在於將控制點從事後審查轉移到事前規格：不是等程式碼產生後再檢查，而是先讓代理撰寫並精煉規格，再讓程式碼對齊這份凍結規格。這解決了沒有測試預言時無法判定正確性的問題，因為規格本身成為驗證的參照。此外，驗證時使用沒有先前記憶的新工作階段，避免代理被自己的推理過程偏誤，這與 Anthropic 建議由無記憶的第二代理進行審查的原則一致。

**Q6：為什麼選擇原子式實作與凍結規格，而不是漸進式重構？**
A：由於需要拆除的是核心架構不變量，任何中間狀態都可能破壞系統一致性，因此漸進式重構在作者評估中被視為實際上不可行。原子式實作確保變更一次性完成，避免長時間處於半完成狀態而引入不確定性。凍結規格則提供穩定的驗證基準，防止實作過程中規格漂移，使後續 17 個驗證循環能夠客觀判斷程式碼是否符合預期。

**Q7：實驗的規模與設定為何？**
A：實驗對象是一個包含 717,725 行程式碼、3,648 個檔案的生產級 TypeScript 應用程式。任務需要拆除「UI 面板在 AI 請求期間必須保持開啟」的核心生命週期不變量，目標是讓串流生成在面板關閉後存活並可重新連接。整個過程在沒有人工程式碼審查、也沒有預先存在測試預言的情況下進行，刻意選擇作為該方法論的壓力測試。

**Q8：研究的主要量化結果是什麼？**
A：最終變更觸及 189 個檔案，其中 31 個為新檔案；加上萃取階段，兩次提交共計 288 個檔案、34,770 行新增與 16,422 行刪除。在 31 個稽核回合中，代理在任何人執行程式前就修正了 201 個缺陷。整個過程耗時三天，成本約 2,430 美元，且在首次與後續約三十個工作階段中，軟體均按規格運作，未觀察到錯誤。

**Q9：在沒有測試預言的情況下，如何驗證正確性？**
A：正確性透過規格本身與反覆稽核來驗證：先讓規格與原始碼對齊，再讓程式碼與凍結規格對齊，收斂準則是連續兩次驗證回合達到零發現。雖然沒有預先存在的測試預言，但編譯與測試回饋迴路仍用於捕捉語法與執行期錯誤。此外，作者公布了 1,500 多頁的法文規格與原始對話日誌，供外部檢視並可提交給語言模型進行一致性檢查。

**Q10：這種方法適用於哪些實務場景？**
A：此方法適用於任何涉及大規模架構重構、且難以透過漸進式變更安全完成的場景，例如核心不變量拆除、協定升級或跨模組資料流重設計。它也適合沒有完整測試預言的遺留系統，因為規格可以成為新的驗證基準。對於需要保留既有投資、無法承受重寫風險的企業應用程式，這種規格優先協定特別具有價值。

**Q11：對工業實務與產品開發有何啟示？**
A：這項研究顯示，當變更規模超過人類審查的工作記憶負荷時，可以將品質控制轉移到規格層級與自動化驗證迴路。產品團隊可以投資於更長、更詳細的代理系統提示與規格文件，以減少對人工程式碼審查的依賴。然而，這也意味著團隊需要建立撰寫、凍結與稽核規格的能力，並接受原子式實作所帶來的整合風險管理挑戰。

**Q12：這項研究對代理式軟體工程領域可能產生什麼影響？**
A：本研究挑戰了「AI 編碼代理只能處理小型、孤立任務」的既有假設，證明在適當協定下，代理可以完成傳統上需要重寫的大規模架構變更。它將「迴路工程」的討論從可測試的小單位擴展到無法拆分的大規模變更，並提出以規格作為收斂參照的替代路徑。這可能促使學界與業界重新思考審查瓶頸的解決方案，並發展更嚴謹的規格驅動代理協定。

**Q13：這項研究有哪些主要限制？**
A：這是一個單一案例研究，樣本數為一，因此結果的普遍性與可重複性仍需更多研究驗證。所有規格與日誌均為法文，可能限制國際研究社群的直接檢視與複製。此外，雖然在約三十個後續工作階段中未觀察到錯誤，但這並不等同於形式驗證，無法保證在長期運作或邊緣情況下完全沒有缺陷。

**Q14：在什麼情況下這個方法可能失敗？**
A：如果規格本身存在系統性錯誤或遺漏關鍵不變量，後續所有實作與驗證都將建立在錯誤基礎上，因為凍結規格是唯一的正確性參照。當任務可以自然拆分為多個獨立小單位且已有測試預言時，原子式實作可能反而比漸進式重構更冒險。此外，若代理無法準確理解龐大依賴圖或規格過於複雜而難以稽核，收斂過程可能無法在合理時間與成本內完成。

**Q15：未來有哪些研究方向值得探索？**
A：未來可以發展多語言、可機器檢查的規格格式，降低規格錯誤與語言隔閡的風險。也可以研究如何將此方法與形式驗證或屬性測試結合，以提供更強的正確性保證。此外，跨多個案例與不同領域的重複實驗，將有助於確立規格優先收斂的適用範圍、成本模型與最佳實踐。

## 實務應用指南

### 適用場景

1. **拆除核心生命週期不變量**  
   例如即時串流應用中，原本假設「UI 面板開啟期間 AI 請求必須持續存在」，現在需要讓串流生成在面板關閉後繼續執行，並於重新開啟時無損重新接上。這類變更跨越數十到數百個檔案，且無現成測試預言可驗證新行為。

2. **無法漸進重構的跨模組架構調整**  
   當單一變更必須同時改動狀態管理、事件匯流排、API 契約與前端元件，且任何中間狀態都會導致系統崩潰時，可採用規格優先收斂，把整段變更視為一次原子式實作。

3. **遺留系統的大規模重構而非重寫**  
   對於數十萬行、缺乏完整測試覆蓋的 TypeScript/JavaScript 企業級應用，當業務無法承受重寫風險，但需要移除深植的架構不變量時，可用此方法在數天內完成高風險重構。

4. **新增行為無法用既有測試定義的場景**  
   例如引入全新的並發模型、離線續傳、多裝置同步，或改變錯誤重試語意。由於目標行為過去不存在，無法仰賴現有測試套件作為預言，必須先建立形式規格，再讓實作對齊規格。

5. **人工程式碼審查到達瓶頸的超大變更**  
   當單一 PR 涉及 100+ 檔案、依賴圖超出人類工作記憶體負荷，審查時間成指數增長時，可將品質閘門從「事後審查程式碼」轉移到「事前反覆稽核規格」。

### 實作前置條件

**資料與工具**
- 完整原始碼存取權，以及能產生模組/檔案依賴圖的工具（如 TypeScript compiler API、dependency-cruiser）。
- 可運作的編譯、測試與靜態分析管線（TypeScript、ESLint、單元測試框架），作為編譯/測試回饋迴路的基礎。
- 版本控制系統（Git）與獨立分支，確保原子式實作不會污染主線。
- 原始執行日誌與規格文件的長期保存空間，供後續一致性檢查與稽核。

**運算資源**
- 支援長上下文（數百萬 token 級）的語言模型 API，因為系統提示詞與程式碼脈絡可能達數十萬字元。
- 足夠執行數十次稽核回合的預算與速率限制；本案例 31 個稽核回合、201 個缺陷修正，耗資約 USD 2,430。
- 能反覆執行完整編譯與測試套件的 CI 環境或本地開發機。

**技能與組織條件**
- 至少一位資深工程師能判斷哪些不變量可被拆除、哪些必須保留，並在最終驗收時做出風險決策。
- 熟悉提示工程與代理編排，能設計系統提示詞、稽核規則與修補提案流程。
- 管理層接受「無人工程式碼審查」的風險輪廓，並願意以階段部署與可觀測性作為替代性品質閘門。

### 實作步驟建議

1. **建立代理控制框架**  
   設計長系統提示詞（可能達數十萬字元），將過往觀察到的代理失敗模式轉化為 durable rules。代理應以「提出修補提案」而非直接寫入檔案的方式工作，並使用全新工作階段擔任稽核者。

2. **萃取與範圍界定**  
   先進行萃取階段：從程式碼庫中找出與目標不變量相關的所有檔案、介面與隱含假設，建立依賴圖與影響範圍清單。此階段本身可視為一次小型規格優先收斂。

3. **由代理撰寫形式規格**  
   讓 AI 編碼代理根據目標行為撰寫正式規格文件，明確列出：要拆除的核心架構不變量、必須保留的新不變量、串流生成與 UI 面板的重新接合語意、錯誤處理與資源清理規則。

4. **規格精煉循環**  
   執行多次精煉循環（本案例 14 回合），讓代理將規格與真實原始碼逐一比對，找出規格與現實不一致之處並修正。直到規格能穩定通過稽核，再將其凍結為後續驗證基準。

5. **凍結規格並原子式實作**  
   規格凍結後，不再允許因實作困難而回頭修改規格。代理依據凍結規格產生完整程式碼變更，並透過編譯/測試回饋迴路修復語法錯誤與型別錯誤。

6. **驗證迴路對齊凍結規格**  
   啟動 17 次或更多驗證循環，由無記憶的新工作階段稽核程式碼是否完全符合凍結規格。每次發現缺陷就修正，再重新驗證。

7. **達到收斂準則**  
   收斂準則應設為「連續兩次驗證回合皆為零發現」。本案例在 31 次稽核回合、201 個缺陷修正後達成，才進入人類執行與驗收。

8. **分階段部署與可觀測性驗收**  
   雖然論文未經人工程式碼審查，但在生產環境仍建議使用功能旗標、金絲雀部署、詳細日誌與錯誤追蹤，觀察數個工作階段確認無異常後再全面上線。

### 潛在風險與注意事項

- **規格本身的缺陷會被放大**：若凍結規格寫錯，後續所有驗證都只會確認程式碼「錯得一致」。應在精煉循環中投入足夠時間，並由資深工程師審閱規格而非審閱程式碼。  
- **代理確認偏誤**：同一工作階段反覆檢查自己的輸出可能愈修愈偏。務必使用無記憶的新工作階段擔任稽核者，並以凍結規格作為外部參照。  
- **無測試預言的虛假安全感**：編譯通過與既有測試通過，並不保證新行為正確。零發現僅代表程式碼符合規格，不代表規格符合真實使用者需求。  
- **上下文長度與成本爆炸**：大型程式碼庫可能撐破模型上下文，需搭配萃取階段、分段稽核與依賴圖裁剪。  
- **原子式變更的整合風險**：數百檔案的一次性提交容易與主線衝突。建議在隔離分支進行，並在實作期間凍結相關模組的併入。  
- **過度依賴代理的組織風險**：此方法適合高風險、難以人工審查的任務，不應成為所有開發的常態；安全關鍵或法規嚴格領域仍須保留人工程式碼審查。  
- **單一案例研究的侷限**：本文僅報告一次成功經驗，尚未證明可重複於其他團隊、語言或領域，建議先以非關鍵重構試點。

### 與其他技術的整合建議

- **版本控制與 CI/CD**：將萃取階段與最終實作分為兩個提交，並在 CI 中強制執行編譯、型別檢查與靜態分析，作為編譯/測試回饋迴路的自動化底線。  
- **現有測試框架**：雖然無測試預言，仍應讓代理在實作後補充針對新不變量的單元測試與整合測試，並納入未來迴歸測試。  
- **程式碼分析工具**：整合 dependency-cruiser、TypeScript compiler API 或自訂靜態檢查，協助代理在稽核回合中驗證依賴圖與介面一致性。  
- **功能旗標與可觀測性**：搭配 LaunchDarkly、Sentry、Datadog 等工具，在生產環境以金絲雀方式驗證串流生成重新接合的行為。  
- **Loop engineering 實踐**：可與 Anthropic 提出的 loop engineering 並行：由外層系統管理工作單元、指派代理執行、再用第二個無記憶代理依凍結規格驗證。  
- **LLM 一致性檢查**：將規格、原始程式碼與工作階段日誌提交給獨立語言模型，自動檢查三者是否一致，作為額外的非執行式驗證層。

### 給不同背景讀者的閱讀建議

**初學者**  
這篇論文展示的是高階代理式軟體工程，不是入門教學。建議先具備 TypeScript、版本控制、單元測試與基本提示工程經驗後再閱讀；重點放在「為什麼要先寫規格」以及「為什麼稽核者要用新工作階段」，不必一開始就追求 189 個檔案的規模。

**AI 工程師**  
對你而言，最有價值的是規格優先協定的具體流程：形式規格、精煉循環、凍結規格、原子式實作、驗證迴路與零發現收斂準則。請特別留意系統提示詞的累積設計、修補提案機制，以及如何利用無記憶稽核者降低確認偏誤。

**研究人員**  
本文是單一、 fully instrumented 的案例研究，而非對照實驗。可關注其方法論貢獻：在無測試預言、無人工程式碼審查的條件下，如何以規格作為外部參照來收斂大規模重構。未來可複製此協定於不同語言與領域，並量化其可重複性、成本效益與缺陷逃逸率。

**產品經理**  
這代表一種新的成本與風險權衡：以數天時間與數千美元完成過去可能被評估為「只能重寫」的任務。但請注意，此方法目前適用於技術債極深、變更範圍極大且人工審查到達瓶頸的場景；不應視為取代所有開發流程，而應作為高風險重構的選項之一，並搭配分階段上線與嚴密監控。
