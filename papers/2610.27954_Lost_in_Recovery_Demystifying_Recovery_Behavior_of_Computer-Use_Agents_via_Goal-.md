本文提出 ReTrace 框架，系統性地研究電腦使用代理（Computer-Use Agents）的復原行為（Recovery Behavior）。其方法論設計具有高度的理論嚴謹性與實務可行性，以下從三個核心層面進行解析。

**1. 形式化定義：轉移一致性復原（Transition-Consistent Recovery）**

作者從預測狀態表示理論（Predictive State Representation Theory, Littman and Sutton, 2001）出發，將「狀態」定義為對未來行為的預測集合，而非單純的視覺相似度。這一形式化具有深遠意義：傳統的狀態比對方法（如像素比對、DOM 結構比對）容易忽略隱性狀態變化，例如檔案系統的隱性修改、登入狀態的切換、或應用程式的內部狀態機改變。轉移一致性復原的核心條件為：若從復原狀態（Recovered State）與目標狀態（Target State）執行相同的後續動作（Downstream Actions），必須產生相同結果（Identical Outcomes）。此定義將「復原成功」從表面相似性提升至行為等價性（Behavioral Equivalence），更貼近實際任務完成的本質。

**2. 三階段管線設計**

ReTrace 的運作流程分為三個相互銜接的階段：

- **階段 A：在策略軌跡展開（On-Policy Trajectory Rollout）**：此階段解決一個關鍵的前置問題——環境的隨機性。電腦使用環境中存在許多非確定性因素，如動畫過場、隨機化 UI 元素、網路延遲等。作者透過將每條成功軌跡重播 N 次，僅保留轉移一致的軌跡，從而建構一個確定性的資料集。這一步驟為後續評估提供了可靠的基準線，避免將環境隨機性誤判為復原失敗。

- **階段 B：透過擾動產生軌跡漂移（Trajectory Drift via Perturbation）**：從確定性軌跡中選取一個種子步驟（Seed Step）作為復原目標 S_k，然後透過受控錯誤注入（Controlled Error Injection）將代理誘導至錯誤狀態（Erroneous State）S_E。此設計的巧妙之處在於「受控」二字——錯誤並非隨機產生，而是經過設計以模擬真實代理可能犯下的錯誤類型，從而使評估具有生態效度（Ecological Validity）。

- **階段 C：目標導向動作回放（Goal-Oriented Action Replay）**：從錯誤狀態出發，要求代理產生復原動作以抵達 S_R，然後從 S_R 重播原始軌跡的剩餘動作（a_k...a_{T-1}），觀察是否能重現原始任務結果。此階段的評估指標為「任務結果是否一致」，而非「視覺是否相似」，這正是轉移一致性復原的操作化體現。

**3. 理論與實務的橋接**

ReTrace 的方法論設計展現了幾項重要特質。首先，它將抽象的理論概念（行為等價性）轉化為可操作的實驗協議，降低了理論與實務之間的落差。其次，框架的模組化設計允許研究者替換不同的錯誤注入策略、不同的代理模型、或不同的環境，從而支援跨平台、跨模型的比較研究。最後，目標導向動作回放的設計巧妙地將「復原品質」與「任務完成度」解耦，使研究者能夠獨立分析這兩個維度。

然而，方法論也存在若干隱含假設值得關注：(1) 假設存在確定性軌跡，但部分任務本質上具有不可消除的隨機性；(2) 假設錯誤注入能夠代表真實錯誤分布，但實際錯誤可能更為多樣；(3) 假設「重播相同動作產生相同結果」是合理的復原標準，但某些情境下代理可能需要產生替代動作序列才能完成任務。

#### 實驗數據解讀

雖然完整實驗數據需參閱正文後續章節，但從摘要與引言揭露的關鍵發現可進行以下解讀。

**1. 理想復原的效能提升（RQ1）**

實驗顯示，當代理被「神諭式」地返回到先前的完好狀態（Intact State）時，其任務完成率顯著優於單純的環境重置（Environment Reset）。此結果的深層意義在於：環境重置雖然消除了錯誤狀態，但也抹除了代理先前累積的正確進度；而理想復原則精準地保留了有效的工作成果。這意味著現有評估基準中採用的「重置後重來」策略可能系統性地低估了代理的真實能力，而復原機制才是釋放代理潛在任務完成能力（Latent Task Completion Capabilities）的關鍵槓桿。

**2. 當前代理的復原能力缺口（RQ2）**

研究發現現有電腦使用代理在錯誤條件下既缺乏復原傾向（tendency），也缺乏復原能力（capability）。此雙重缺口揭示了一個重要現象：當前代理的訓練目標主要聚焦於前向決策（Forward Decision），缺乏對「逆轉錯誤」這類反向推理能力的顯式訓練。更值得注意的是，當代理被賦予明確的基於模型的復原（Model-Based Recovery）機制後，復原成功率提升超過一個數量級（order of magnitude），這強烈暗示復原能力是潛在的（latent）而非完全缺失的——代理具備相關知識，但缺乏在錯誤情境下調用這些知識的機制。

**3. 端到端增益的條件性（RQ3）**

實驗結果呈現一個關鍵的二元性：準確的模型級復原能帶來可測量的端到端增益（End-to-End Gains），但弱復原（weak recovery）則可能主動偏離正確軌跡。此發現對實務部署具有重要意涵——復原機制並非「有總比沒有好」，錯誤的復原動作可能比不復原更糟糕。這凸顯了復原品質（recovery quality）作為獨立評估維度的重要性，也暗示未來的代理設計需要在「復原傾向」與「復原準確性」之間取得平衡。

**4. 跨平台與跨模型的一致性**

ReTrace 在 OSWorld（Xie et al., 2024）與 WindowsAgentArena（Bonatti et al., 2024）兩個基準上進行實驗，涵蓋封閉源與開放源電腦使用代理。這種跨平台、跨模型的實驗設計增強了結論的普適性，但也帶來一個值得關注的問題：不同作業系統環境下的錯誤模式可能存在系統性差異（例如 Windows 的權限模型 vs. Linux 的檔案系統語義），這可能影響復原策略的可遷移性。

#### 與現有研究的比較

**1. 與錯誤處理策略的比較**

現有文獻中的錯誤處理策略可分為三大類，ReTrace 對每一類都提出了批判性反思：

- **反思（Reflection）策略**（Chae et al., 2025a,b; Wu et al., 2025b; Wang et al., 2025a; Zhang et al., 2026a; Xue et al., 2026; Wang et al., 2026c）：此類方法透過文本回饋（Textual Feedback）或獎勵信號（Reward Signals）誘導代理產生自我反思行為，從錯誤狀態繼續前進。然而，如圖 1(A) 所示，反思策略面臨副作用（Side Effects）風險——某些錯誤一旦造成就無法僅透過「繼續前進」來彌補，例如已關閉的視窗（Window Closed）或已刪除的檔案。ReTrace 的復原策略則從根本上避免了此問題。

- **回溯（Rollback）策略**（Koh et al., 2024b; He et al., 2025; Hu et al., 2025; Zhang et al., 2026b）：此類方法依賴環境重置後的動作回放（Action Replay），或網頁環境的 API 基礎回溯（如瀏覽器上一頁）。ReTrace 明確指出此類方法的三大限制：(a) 環境重置在線上正式網站（Production Websites）與作業系統（Operating Systems）等專有設定（Proprietary Settings）中不可行；(b) 動作回放在長視野設定（Long-Horizon Settings）下計算成本過高；(c) API 回溯僅限於網頁環境，無法覆蓋桌面應用。

- **基於模型的復原（Model-Based Recovery）**：ReTrace 將此定位為「通用復原」（General-Purpose Recovery）的關鍵路徑，填補了現有研究的空白。相較於前述啟發式補救措施（Heuristic Remedies），基於模型的復原不依賴外部基礎設施，理論上可應用於任何環境。

**2. 與狀態表示理論的連結**

ReTrace 借鑑預測狀態表示理論（PSR），將狀態定義為「對未來行為的預測集合」。此理論連結具有方法論深度：傳統的電腦使用代理研究多採用視覺特徵或 DOM 結構作為狀態表示，但這些表示無法捕捉隱性狀態。PSR 的引入為評估「真正的復原」提供了理論基礎，也為未來設計更強大的狀態表示學習方法提供了啟示。

**3. 限制與不足**

儘管 ReTrace 在方法論上具有顯著優勢，但仍存在以下限制：

- **錯誤注入的代表性**：受控錯誤注入（Controlled Error Injection）雖然保證了實驗的可控性，但可能無法完全代表代理在真實部署中遭遇的錯誤分布。未來研究可考慮結合真實錯誤日誌進行驗證。

- **計算成本**：雖然 ReTrace 避免了完整動作回放，但其本身仍需多次軌跡展開與重播，計算成本不容忽視。對於超長視野任務，框架的可擴展性有待驗證。

- **代理自主性的邊界**：ReTrace 評估的是「代理能否自主產生復原動作」，但未深入探討代理應在何時觸發復原（觸發時機問題）。此問題與錯誤檢測（Error Detection）能力密切相關，是未來研究的重要方向。

**1. 錯誤檢測與復原觸發機制**

ReTrace 聚焦於「代理能否復原」，但未深入探討「代理何時應觸發復原」。未來研究可考慮：(a) 設計輕量級的錯誤檢測模組，使代理能即時識別錯誤狀態；(b) 探索不確定性估計（Uncertainty Estimation）作為復原觸發信號；(c) 研究錯誤嚴重程度的分級機制，以決定是否需要復原或僅需反思。

**2. 階層化復原策略**

當前 ReTrace 將復原視為單一動作，未來可探索階層化復原（Hierarchical Recovery）策略：(a) 將復原分解為「撤銷錯誤動作」與「重建正確狀態」兩個子任務；(b) 引入子代理（Sub-Agent）專門負責復原，主代理專注於前向任務；(c) 設計可重用的復原原語庫，提升復原效率。

**3. 復原能力的訓練方法**

實驗發現復原能力是潛在的而非缺失的，這暗示透過專門訓練可釋放此能力。未來研究方向包括：(a) 設計包含復原軌跡的訓練資料；(b) 探索強化學習中的「復原獎勵」設計；(c) 研究課程學習（Curriculum Learning）策略，從簡單錯誤逐步過渡到複雜錯誤。

**4. 跨環境復原的可遷移性**

不同作業系統、不同應用程式之間的錯誤模式存在差異。未來研究可探討：(a) 復原策略的跨平台遷移學習；(b) 通用復原原語的抽象化設計；(c) 元學習（Meta-Learning）方法使代理快速適應新環境的錯誤模式。

**5. 安全性與副作用考量**

復原機制本身可能引入新的安全風險，例如「過度復原」可能刪除使用者希望保留的資料。未來研究應考慮：(a) 設計可逆的復原操作；(b) 在復原前進行使用者確認；(c) 建立復原操作的審計日誌，增強可解釋性與可信度。

**6. 與人類協作的混合復原**

在某些高風險情境下，完全自主的復原可能並不可取。未來可探索人機協作復原模式：(a) 代理提出復原方案，人類確認後執行；(b) 代理在復原過程中即時報告進度；(c) 設計自然語言介面，使非技術使用者能理解與監督復原過程。

**7. 理論層面的深化**

ReTrace 的轉移一致性復原定義為復原研究提供了形式化基礎，但仍有許多理論問題值得探索：(a) 復原的計算複雜度下界；(b) 不同錯誤類型的復原難度分級；(c) 復原能力與任務完成能力之間的理論關聯。這些理論問題的解答將有助於設計更系統化的代理訓練與評估方法。

## 論文問答

**Q1：這篇論文主要解決什麼核心問題？**
A：這篇論文聚焦於電腦使用代理（Computer-Use Agents）在長視野設定（Long-Horizon Settings）下的脆弱性問題。當代理執行複雜的數位工作流程（Digital Workflows）時，早期的錯誤會累積並傳遞到後續步驟，且已執行的細粒度鍵盤與滑鼠操作（Fine-Grained Operations）可能產生未預期的副作用（Side Effects），例如代理在整理目錄時可能默默覆蓋使用者想保留的檔案。因此，如何讓代理從錯誤狀態（Erroneous State）自主復原到先前的完好狀態（Intact State），成為建構可靠代理的關鍵挑戰。

**Q2：為什麼現有的錯誤處理策略不足以解決這個問題？**
A：現有的錯誤處理策略（Error-Handling Strategies）大致可分為反思（Reflection）、回溯（Rollback）與復原（Recovery）三類，但各有明顯限制。反思策略從錯誤狀態繼續向前推進，容易產生副作用；回溯策略需要環境重置（Environment Reset）並執行動作回放（Action Replay），但在專有設定（Proprietary Settings）如線上正式網站（Production Websites）與作業系統（Operating Systems）中往往不可行；而基於 API 的回溯（API-Based Rollback）僅限於網頁環境（Web Environments），例如瀏覽器上一頁（Browser Back）功能，無法涵蓋桌面環境。這些啟發式補救措施（Heuristic Remedies）都無法提供通用復原（General-Purpose Recovery），使得基於模型的復原（Model-Based Recovery）成為亟需探索的方向。

**Q3：為什麼研究代理的復原行為如此重要？**
A：研究復原行為的重要性體現在三個層面：首先，理解代理是否能自主復原決定了其在真實場景中的可靠運作（Reliable Operation）程度；其次，論文發現理想的復原能解鎖模型的潛在任務完成能力（Latent Task Completion Capabilities），意味著許多看似失敗的任務其實可以透過正確的復原來完成；最後，系統性地研究復原行為有助於將其確立為電腦使用代理的基礎能力（Fundamental Capability），推動整個領域朝向更可靠的代理系統發展。

**Q4：ReTrace 框架的核心方法是什麼？**
A：ReTrace 的核心方法是目標導向動作回放（Goal-Oriented Action Replay），這是一個可擴展的評估框架（Evaluation Framework），用於系統性地研究電腦使用代理的復原行為。該方法首先透過同策略軌跡展開（On-Policy Trajectory Rollout）收集成功的軌跡，並將每個動作序列回放 N 次以建立轉移一致性資料集；接著透過擾動（Perturbation）將代理引入錯誤狀態；最後從復原狀態（Recovered State）回放剩餘動作，測試代理是否能重現原始任務結果。這種設計使得評估過程具有確定性與可重現性。

**Q5：論文最重要的理論創新是什麼？**
A：論文最重要的理論創新是將成功的復原形式化為轉移一致性復原（Transition-Consistent Recovery）：若從復原狀態與目標狀態（Target State）執行相同的後續動作（Downstream Actions）會產生相同結果（Identical Outcomes），則兩狀態被視為等價。這個定義靈感來自預測狀態表示理論，超越了單純的視覺相似性，透過行為等價性捕捉潛在的狀態變化。這種形式化使得復原評估能夠以可測量的方式進行，而非僅依賴主觀判斷。

**Q6：ReTrace 在設計上有哪些關鍵選擇？**
A：ReTrace 的關鍵設計選擇體現在三個層面：在資料收集階段，僅保留多次回放後結果一致的軌跡，確保環境轉移的確定性；在錯誤注入階段，採用受控錯誤注入（Controlled Error Injection）來產生可重現的錯誤狀態；在評估階段，則透過比較觀測結果來判斷復原是否成功。這些設計選擇共同確保了評估的嚴謹性，並使框架能夠應用於不同的代理模型與作業環境，包括封閉源碼與開放源碼的電腦使用代理。

**Q7：實驗使用了哪些基準測試？**
A：實驗將 ReTrace 實例化於兩個重要的基準測試：OSWorld 與 WindowsAgentArena，前者涵蓋 Linux 桌面環境，後者則針對 Windows 作業系統。這兩個基準測試共同覆蓋了主流的桌面作業系統場景，使研究結果具有廣泛的適用性。透過在這些基準上評估封閉源碼與開放源碼的電腦使用代理，論文得以全面檢視不同模型在復原行為上的表現差異。

**Q8：論文揭示了哪些關鍵實驗結果？**
A：論文揭示了三個關鍵發現：首先，理想復原（Ideal Recovery）——即將代理返回到神諭先驗狀態——能顯著提升任務表現，超越單純的環境重置，證實復原是解鎖代理潛在任務解決能力的關鍵槓桿；其次，當前的電腦使用代理既缺乏自主復原的傾向，也缺乏相應能力，使得這項潛在能力未被利用；最後，當代理配備明確的基於模型的復原機制時，復原成功率提升超過一個數量級，證實潛在復原能力（Latent Recovery Capabilities）確實存在，只是未被激發。

**Q9：實驗中如何驗證復原品質與任務成功的關係？**
A：論文透過端到端增益（End-to-End Gains）的測量來驗證兩者關係：準確的模型級復原能帶來可測量的任務完成率提升，而品質不佳的復原則可能主動偏離軌跡（derail the trajectory），導致任務失敗。這項消融研究證實了復原品質與下游任務成功之間存在直接的因果關係，強調了可靠復原機制對於整體代理表現的重要性。

**Q10：這項研究適用於哪些實際應用場景？**
A：這項研究適用於多個實際應用場景，包括文件編輯（Document Editing）、目錄整理（Directory Organization）、網站登入等日常數位工作流程。在這些場景中，使用者期望代理能可靠地完成任務，即使中途發生錯誤也能自主恢復。例如，當代理在編輯簡報時不小心關閉了某個視窗（Window Closed），理想的復原機制應能讓代理恢復到先前的完好狀態並繼續完成任務，而非從錯誤狀態繼續推進而產生副作用。

**Q11：在產品化部署時需要考慮哪些因素？**
A：產品化部署時需要考慮多項因素：首先，復原機制必須能在無法進行環境重置的專有設定中運作，這對線上正式網站與作業系統尤為重要；其次，復原的準確性至關重要，因為弱復原可能比不復原更糟糕，會主動偏離任務軌跡；最後，代理需要同時具備復原的傾向與能力，目前的代理雖然具備潛在復原能力，但缺乏自主觸發復原的傾向，這需要在產品設計中透過提示工程或訓練機制來引導。

**Q12：這項研究對整個領域有何影響？**
A：這項研究將復原確立為電腦使用代理的基礎能力（Fundamental Capability），為未來的研究提供了新的方向。它揭示了當前代理在復原行為上的不足，並提供了系統性的評估工具，使研究者能夠量化比較不同代理的復原能力。此外，論文強調了從「強化前向決策策略」轉向「結合可靠復原機制」的研究範式轉移，這可能影響未來代理架構的設計思路，推動整個領域朝向更可靠的代理系統發展。

**Q13：論文承認有哪些研究限制？**
A：論文的研究限制主要體現在兩個方面：首先，評估範圍目前僅限於 OSWorld 與 WindowsAgentArena 兩個基準測試，雖然涵蓋了主流桌面作業系統，但尚未擴展到行動環境或其他數位工作流程；其次，實驗中測試的代理模型數量有限，雖然涵蓋了封閉源碼與開放源碼的代表，但可能無法完全代表所有電腦使用代理的復原能力。這些限制為未來研究留下了擴展空間。

**Q14：論文中提到了哪些失敗案例？**
A：論文中提到的失敗案例主要體現為弱復原導致軌跡偏離：當代理嘗試進行復原但復原品質不佳時，不僅無法恢復到目標狀態，還可能將任務推向更糟糕的方向。這種現象說明了復原機制的雙刃劍特性——不準確的復原比不復原更具破壞性。此外，當前代理即使具備潛在復原能力，也缺乏自主觸發復原的傾向，導致在錯誤狀態下繼續推進而產生副作用，這也是一種隱性的失敗模式。

**Q15：未來的研究方向有哪些？**
A：未來研究方向可從幾個層面展開：在技術層面，可探索更有效的復原機制設計，包括如何讓代理自主識別需要復原的情境、如何生成準確的復原動作序列；在評估層面，可將 ReTrace 擴展到更多環境與任務類型，包括行動環境與更複雜的數位工作流程；在訓練層面，可研究如何透過強化學習或監督學習來激發代理的潛在復原能力；在應用層面，則可探索子代理（Sub-Agent）協作、記憶增強等機制來提升整體復原可靠性。這些方向共同指向建構真正可靠的電腦使用代理系統。

### 實作前置條件

- 成功的任務軌跡資料集：需蒐集代理在目標環境（如 OSWorld、WindowsAgentArena）中成功完成任務的完整動作序列，每條軌跡需具備確定性的環境轉移（即相同動作序列在多次執行下產生相同結果）。
- 環境狀態快照機制：需具備能夠擷取、儲存與比對螢幕畫面與底層狀態（例如 DOM、檔案系統、應用程式內部狀態）的工具。
- 錯誤注入策略庫：定義可控的錯誤類型（視窗關閉、誤刪檔案、輸入錯誤參數等），用於產生錯誤狀態。

**運算資源**
- 多代理並行執行環境：因需對每條軌跡進行 N 次回放以驗證轉移一致性，建議配置支援多 VM 或容器並行執行的基礎設施。
- 視覺語言模型推論資源：評估階段需呼叫目標電腦使用代理（閉源如 GPT-Computer-Use、Claude，或開源如 UI-TARS），需準備對應的 API 額度或本地 GPU 叢集。
- 儲存空間：每次回放的螢幕截圖與動作日誌會產生大量資料，建議預留 TB 等級的物件儲存。

**技能前提**
- 熟悉大型視覺語言模型（LVLM）的提示工程與動作空間設計。
- 具備作業系統自動化基礎（pyautogui、xdotool、Win32 API 等）。
- 理解強化學習中的軌跡回放與策略評估概念。
- 具備環境確定性控制能力（處理隨機化、時間敏感操作等）。

### 實作步驟建議

**步驟一：建立確定性的基準環境**
從 OSWorld 或 WindowsAgentArena 開始，配置可重現的虛擬機或容器環境。關閉或固定所有非確定性來源（隨機種子、系統時鐘、動畫效果），確保相同動作序列在多次執行下產生相同結果。

**步驟二：蒐集並篩選轉移一致的成功軌跡**
使用目標代理在基準任務上執行 rollout，蒐集成功軌跡。對每條成功軌跡進行 N 次回放（論文中建議 N ≥ 3），僅保留所有回放結果一致的軌跡，作為轉移一致資料集。

**步驟三：設計錯誤注入策略**
從每條保留軌跡中選取一個「種子步驟」k，將其後續動作定義為「目標導向動作」。在狀態 S_k 上注入可控錯誤（例如關閉特定視窗、刪除檔案、修改設定），產生錯誤狀態 S_E。

**步驟四：實作目標導向動作回放評估**
讓代理從錯誤狀態 S_E 嘗試生成復原動作序列，抵達候選復原狀態 S_R。接著從 S_R 與目標狀態 S_k 分別回放相同的目標導向動作 (a_k, ..., a_{T-1})，比對最終結果是否一致。若一致，則該復原動作滿足轉移一致性。

**步驟五：量化分析與基準比較**
計算復原成功率（Recovery Success Rate）、任務完成率（Task Success Rate）等指標。比較「理想復原」（直接回到 S_k）、「自主復原」（代理自行從 S_E 復原）與「無復原」（從 S_E 繼續執行）三種情境下的端到端表現差異。

**步驟六：將復原能力整合至代理的決策迴圈**
根據評估結果，設計提示或微調策略，使代理在偵測到錯誤狀態時主動觸發復原程序。可採用兩階段決策：先判斷當前狀態是否偏離預期軌跡，若是則進入復原模式，否則繼續前向執行。

**步驟七：建立持續評估與監控機制**
將 ReTrace 評估流程整合至 CI/CD 流程中，每次代理模型更新後自動執行復原能力回歸測試，確保新版本不會退化。

### 潛在風險與注意事項

**風險一：環境非確定性導致評估失真**
若基準環境中存在未受控的隨機性（例如系統通知、動畫時長、隨機化檔案命名），相同動作的回放結果可能不一致，導致轉移一致性判定錯誤。
**緩解措施**：在評估前對環境進行完整的確定性審查，固定所有隨機來源；對回放結果採用多數決或統計檢定。

**風險二：錯誤注入的代表性不足**
若注入的錯誤類型過於單一或過於人為，可能無法反映真實部署環境中的錯誤模式，導致評估結果過於樂觀或悲觀。
**緩解措施**：蒐集真實部署日誌中的錯誤模式，建立錯誤類型的分類體系，確保注入策略覆蓋常見與邊界案例。

**風險三：復原動作本身引入新錯誤**
代理在嘗試復原時可能產生新的副作用（例如為了關閉錯誤視窗而誤觸其他按鈕），形成「復原失敗的復原」遞迴問題。
**緩解措施**：設定復原動作的最大步數上限與中止條件；採用階層式復原策略，先嘗試低成本復原（單鍵 undo），再逐步升級至多步驟操作。

**風險四：評估成本過高**
每條軌跡需進行 N 次回放，且每個錯誤狀態需評估多次復原嘗試，整體運算成本可能遠超一般基準測試。
**緩解措施**：採用分層抽樣，僅對高風險任務類型進行完整評估；使用較小的 N 值進行初篩，再對候選軌跡進行精確驗證。

**風險五：視覺相似但行為不一致的狀態**
兩個螢幕畫面可能視覺上相似，但底層狀態（例如未儲存的緩衝區、隱藏的對話框）不同，導致後續動作產生不同結果。
**緩解措施**：這正是論文中「轉移一致性」概念的價值所在——不依賴視覺比對，而是透過行為等價性來判定狀態一致性。

**風險六：閉源代理的不可控性**
若使用閉源代理（如 GPT-Computer-Use、Claude Computer Use），其內部決策邏輯無法修改，僅能透過提示工程引導復原行為，效果可能受限。
**緩解措施**：在代理外部包裝一層「監督代理」（meta-agent），專門負責偵測錯誤狀態並觸發復原程序；或考慮使用支援 fine-tuning 的開源模型。

### 與其他技術的整合建議

**與反思機制（Reflection）的整合**
論文中區分了「反思」（從錯誤狀態繼續前進）與「復原」（回到完好狀態）。實務上可將兩者結合成階層式錯誤處理：先嘗試低成本反思修正，若失敗則升級至復原程序。可設計一個錯誤處理路由器，根據錯誤嚴重程度與可逆性自動選擇策略。

**與測試時回溯（Test-Time Rollback）的整合**
對於支援完整環境重置的場景（例如內部測試環境），可將 ReTrace 的轉移一致性評估作為「是否需要重置」的判斷依據：若代理能自主復原，則避免昂貴的環境重置；僅在自主復原失敗時才觸發回溯。

**與軌跡記憶與經驗回放系統的整合**
將成功的復原軌跡存入代理的長期記憶（例如類似 ReAct 的經驗庫），在未來遇到相似錯誤狀態時可直接參考先前的復原策略，提升復原效率。

**與多代理協作框架的整合**
在多代理系統中，可設置專門的「復原代理」（Recovery Agent）作為子代理（Sub-Agent），由主代理在偵測到錯誤時呼叫。復原代理專注於狀態恢復，主代理專注於任務前進，職責分離有助於提升整體可靠性。

**與監控與可觀測性平台的整合**
將 ReTrace 的評估指標（復原成功率、轉移一致性比率）整合至現有的 MLOps 儀表板中，作為代理可靠性的關鍵指標。當指標下降時觸發告警，並自動啟動回歸測試。

**與人類回饋強化學習（RLHF）的整合**
蒐集人類對代理復原行為的評分（例如「這個復原動作是否合理」），用於微調代理的復原策略，使其更貼近人類專家的錯誤處理模式。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的圖 1，直觀理解「反思」、「回溯」與「復原」三種錯誤處理策略的差異。接著閱讀第 2 節了解電腦使用代理的基本概念與發展脈絡。核心論點集中在第 1 節末尾的三個研究問題（RQ1-RQ3），這三個問題構成了整篇論文的骨架，理解它們有助於掌握後續章節的動機。

**給 AI 工程師**：重點閱讀第 3 節的 ReTrace 框架設計，特別是「轉移一致性復原」的數學形式化與「目標導向動作回放」的實作細節。第 4 節的「理想復原」實驗提供了具體的基準數據，可作為在自有環境中實作的參考。第 5 節揭示了當前代理的復原能力差距，這對評估自家系統的成熟度極具參考價值。

**給研究者**：第 3 節的形式化定義（受預測狀態表示理論啟發）是理論貢獻的核心，建議仔細推導。第 5 節與第 6 節的實驗設計（特別是錯誤注入的分類與轉移一致性的驗證方法）可作為後續研究的起點。此外，論文中揭示的「潛在能力未被利用」現象，與近期關於模型潛能激發（latent capability elicitation）的研究方向高度相關，值得深入探索。

**給產品經理**：重點關注第 1 節的問題動機與第 6 節的端到端增益數據。論文的核心理論點是：當前電腦使用代理的失敗，許多並非源於模型能力不足，而是缺乏有效的錯誤復原機制。這意味著在產品設計中，投資於「錯誤處理 UX」與「復原機制」可能比單純提升模型規模更具成本效益。圖 1 的三種策略對比可直接用於向利害關係人說明技術選型的權衡。
