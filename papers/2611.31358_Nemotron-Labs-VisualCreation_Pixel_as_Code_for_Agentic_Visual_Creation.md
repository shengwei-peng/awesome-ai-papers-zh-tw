A：Pixel as Code 的核心在於將所有視覺產物統一抽象為「離散表示 𝑐_r 與渲染器 R_r」的組合：生成器 G_r 產出表示，渲染器將其轉為可檢視的影像 Î。這種設計不要求所有表示共用詞彙或渲染器，而是透過「生成→渲染→檢視」的共同介面，使光柵影像的學習式視覺標記與 SVG、HTML/CSS、繪圖程式碼等顯式程式得以在同一系統中並存與互補。對於光柵路徑，分詞器的編碼器 E 與解碼器 D 分別提供表示與渲染；對於結構化路徑，則由對應的渲染後端（如瀏覽器引擎）負責執行與視覺化。

### 潛在風險與注意事項

**1. 視覺幻覺與事實錯誤**
光柵生成器可能產生視覺上合理但內容錯誤的影像（例如錯誤的數字、虛構的人物）。**緩解措施**：對關鍵內容（數據、姓名、日期）採用結構化路由產出可驗證的程式碼；視覺稽核階段加入事實性檢查；對高風險場景（醫療、法律、金融）保留人工審核環節。

**2. 結構化程式碼的可執行性風險**
生成的 HTML/CSS/JS 可能存在語法錯誤、跨瀏覽器相容性問題、依賴缺失。**緩解措施**：在沙箱環境中執行並渲染；採用「目標式修復」迴路自動修正常見錯誤；保留檢查點以便回退。

**3. 視覺評估模型的偏誤**
Super-VL 等視覺評估模型可能對特定風格、構圖產生系統性偏見，導致候選篩選結果不理想。**緩解措施**：建立多元化的評估資料集；定期以人類評估校準模型；對關鍵決策採用配對裁判（pairwise judge）而非絕對評分。

**4. 代理迴路的無限循環**
修復迴路可能因錯誤診斷而陷入無限迭代。**緩解措施**：設定最大迭代次數與時間預算；設計「升級」機制，當自動修復失敗時將任務升級給人類。

**5. 算力成本與延遲**
完整框架涉及多個 LLM 呼叫、視覺生成、渲染、評估，單次請求的延遲與成本可能較高。**緩解措施**：設計快取機制（相似需求複用結果）；採用早期退出策略（高品質候選直接通過）；對簡單需求使用較小的模型。

**6. 著作權與內容安全**
訓練資料可能包含受著作權保護的影像或程式碼。**緩解措施**：嚴格篩選訓練資料來源；對生成結果進行相似度檢測；建立內容審核機制過濾不當內容。

**7. 評估基準與真實需求的落差**
基準測試（GenEval2、Chart2Code 等）可能無法完全反映真實使用者的需求。**緩解措施**：建立內部評估集，邀請目標使用者進行 A/B 測試；持續收集生產環境的回饋資料。
