## ⚡ TL;DR

現有多智能體程式系統採通用規劃、編碼與除錯角色，難以處理競技程式設計的演算法專業知識。
MARS以檢索增強生成為基礎，組建演算法主題專家團隊，透過公開測試回饋接力生成C++17解答。
MARS達62.4%通過率，較直接提示提升14.4百分點，成本為CodeSIM三分之一。

## 摘要翻譯

大型語言模型（Large Language Models, LLM）擅長程式碼生成（code generation），但競技程式設計（competitive programming）凸顯出一個持續存在的失效模式（failure mode）：現有的多智能體管線（multi-agent pipeline）把工作分配給通用的規劃器（planner）、編碼器（coder）與除錯器（debugger）等角色，卻將演算法技術（algorithmic technique）的選擇完全交由骨幹模型（backbone model）獨自決定。我們提出 MARS（Multi-Agent Relay of Specialized LLMs，多專家 LLM 接力系統），這是一個純提示框架（prompt-only framework），其中每個智能體（agent）都是主題專家（topic specialist）——例如動態規劃（dynamic programming）、圖論（graphs）、字串（strings）、幾何（geometry）等——並以演算法理論語料庫（algorithm-theory corpus）上的檢索增強生成（Retrieval-Augmented Generation, RAG）為基礎。針對給定問題，檢索機制會選出一小組相關專家；啟動代理（starter）會撰寫初始的 C++17 解法，隨後每一輪會在沙盒（sandbox）中針對公開範例（public examples）執行候選解（candidate solution），由當前專家（active specialist）決定保留、修復或交接（keep, repair, or hand off）草稿，並將結構化封包（structured packet）轉發給下一位專家。最後再透過單一基礎設施修復階段（infrastructure-fixer pass）來正規化樣板程式碼（boilerplate）。在 CodeContests 測試分割（test split）上以 Gemma 4 進行評估，MARS 達到 0.624 ± 0.006 的通過率（pass rate），平均每項任務記錄 2.3 個管線階段（pipeline stage）（較直接提示（direct prompting）提升 14.4 個百分點），在大幅縮小與 CodeSIM（0.731）差距的同時，牆鐘成本（wall-clock cost）僅為 CodeSIM 的 1/3.3，且每項任務的 token 消耗量（per-task token spend）變異數（variance）顯著較小。原始碼（source code）已公開於 GitHub：https://github.com/fckand/mars。

### 核心貢獻（3～5點）
- 提出 MARS，一個純提示框架（prompt-only framework），以主題專家（topic specialist）接力取代通用的規劃器／編碼器／除錯器分工，解決現有多智能體管線將演算法技術選擇完全交由單一骨幹模型決定的問題。
- 結合檢索增強生成（RAG）與演算法理論語料庫（algorithm-theory corpus），使每位專家代理具備特定演算法領域的領域知識與演算法理論洞見。
- 設計「啟動代理（starter）→ 沙盒（sandbox）執行 → 保留／修復／交接（keep, repair, or hand off）→ 基礎設施修復階段（infrastructure-fixer pass）」的多智能體接力管線，並透過結構化封包（structured packet）在專家間傳遞問題特定上下文。
- 在 CodeContests 測試集上以 Gemma 4 達到 0.624 的通過率（pass rate），較直接提示（direct prompting）提升 14.4 個百分點，並以 3.3 倍更低的牆鐘成本（wall-clock cost）與更穩定的每項任務 token 消耗量縮小與 CodeSIM 的差距。

### 適合對象
從事競技程式設計、自動化程式碼生成、多智能體系統與檢索增強生成研究的學者與工程師；特別適合希望以純提示框架、在不重新訓練模型的前提下提升 LLM 解題能力與效率的研究者。

## 深度分析

#### 方法論解析

MARS（Multi-Agent Relay of Specialized LLMs，多專家 LLM 接力系統）的核心設計，是將傳統多智能體管線（multi-agent pipeline）中「規劃器（planner）—編碼器（coder）—除錯器（debugger）」的階段對齊分解（stage-aligned decomposition），替換成「主題對齊多智能體接力（topic-aligned multi-agent relay）」。具體而言，系統維護一個由十一個主題專家（topic specialist）組成的池子，每個專家對應單一演算法領域，例如動態規劃（dynamic programming）、圖論（graphs）、字串（strings）、幾何（geometry）等。每位專家並非僅靠角色扮演（persona）取得異質性，而是透過檢索增強生成（Retrieval-Augmented Generation, RAG）從各自的語料庫切片（corpus slice）取得演算法理論知識，再進行推理與程式生成。

**團隊組建：自我回報的主題能力（self-reported topical competence）**  
面對一道競技程式設計（competitive programming）題目時，所有可用專家會被詢問兩個問題：該題目是否落在其專長範圍內，以及該專家是否能啟動接力。每位專家會回傳 in-scope 旗標、relevance 旗標與信心分數（confidence score），並依據其專屬標籤（tag set）從共享的 cp-algorithms 演算法理論語料庫（algorithm-theory corpus）中檢索相關段落。系統根據分數篩選出最多三個最相關的專家，再透過額外的 can-start probe 選出啟動代理（starter）。

**接力流程：保留、修復或交接（keep, repair, or hand off）**  
啟動代理首先撰寫初始 C++17 候選解（candidate solution）。之後每一個接力步驟（relay step）包含兩次 LLM（Large Language Model，大型語言模型）呼叫：第一次根據當前程式碼、被指派的子任務、啟動合約（starter contract）、前序接力狀態的精簡摘要，以及檢索到的 RAG 上下文，生成新的程式草稿；接著在沙盒（sandbox）ExecEval 中對公開測試（public tests）執行草稿。第二次 LLM 呼叫則檢視執行報告，並決定採取三種行動之一：保留程式碼（keep-code）、修復程式碼（repair-code），或不做修改（no-change），同時決定下一個貢獻的專家。每次決策後，當前專家會將程式碼與結構化封包（structured packet）傳遞給下一位專家。

**終止條件與基礎設施修復（infrastructure-fixer）**  
接力會在以下情況停止：出現明確的停止訊號、已無未使用的入選專家、達到步驟上限（最多八步），或連續兩步無進展時重新路由、連續三步無進展時終止。接力結束後，程式碼會先被清理；若偵測到僅涉及樣板程式碼（boilerplate）層級的失敗——例如輸入輸出接線（I/O wiring）、標頭檔引用（includes）或型別寬度（type widths）——才會呼叫基礎設施修復器（infrastructure-fixer）進行最後正規化。

整體而言，MARS 是一個純提示框架（prompt-only framework）：沒有額外的微調、強化學習或人類回饋，所有改進來自於主題專業化、RAG 檢索 grounding，以及將公開測試執行結果作為每步的迴路內訊號（in-loop signal）。

#### 實驗數據解讀

論文在 CodeContests 測試分割（test split）的 165 道題目上進行評估，骨幹模型（backbone model）為指令微調版 Gemma 4，設定溫度（temperature）0.0、top-p 0.95、token 預算 4096；檢索使用 Jina Embeddings v2 對 cp-algorithms 語料庫編碼。

**主要結果**  
MARS 的通過率（pass rate）達到 0.624 ± 0.006，相較於直接提示（direct prompting）提升 14.4 個百分點，並大幅縮小與 CodeSIM（0.731）之間的差距。每項任務平均僅使用 2.3 個記錄的管線階段（pipeline stage），實際耗時（wall-clock cost）比 CodeSIM 低 3.3 倍，且每項任務的 token 消耗量（per-task token spend）標準差（standard deviation）約為 CodeSIM 的七分之一。

**對照基線的意義**  
論文設計了多個消融與對照系統：
- **Direct（直接提示）**：單一 LLM 呼叫，作為最弱基線。
- **Single-RAG**：只使用檢索到的最相關單一專家，顯示「有 RAG 但無接力」的效果。
- **Parallel ensemble（平行集成）**：合併各專家候選解，測試平行化而非接力的價值。
- **Base relay（基礎接力）**：移除公開測試自我檢查、子任務追蹤與基礎設施修復器，用來衡量這些機制的個別貢獻。

MARS 同時超越這些基線，說明動態組隊、執行回饋與樣板碼修復三者缺一不可。值得注意的是，MARS 的平均階段數僅 2.3，表示多數題目在一到兩位專家接力後即可收斂，這也解釋了為何它能以較低成本接近 CodeSIM 的表現。

**結果的兩面性**  
從正面看，MARS 證明對於競技程式設計這類需要深層演算法理論洞見（theoretical algorithmic insights）的任務，「主題專家 + 理論檢索 + 執行回饋」的組合優於通用角色分工。然而，它仍未超越 CodeSIM，暗示模擬驅動規劃（simulation-driven planning）與更激進的除錯搜尋仍能在絕對正確率上帶來額外收益；MARS 選擇的是一個在正確率、實際耗時與成本變異數（variance）之間更平衡的設計點。

#### 與現有研究的比較

**相較於通用多智能體系統（heterogeneous multi-agent systems）**  
現有研究常透過角色扮演、骨幹模型多樣性（backbone diversity）、去中心化協調（decentralized coordination）或能力描述來創造異質性。MARS 的差異在於將智能體的專長直接對齊到任務的主題結構，並以演算法理論語料庫為每位專家提供 grounding。這使得專家不僅「扮演」某個角色，而是能檢索到與題目相關的演算法知識。

**相較於程式碼檢索方法**  
REDCODER、DocPrompting、RepoCoder 等研究檢索的是程式碼、API 文件或程式庫內容，目標是降低實作層面（implementation surface）的錯誤。MARS 則針對每個專家檢索不同的演算法理論切片，補強的是「該用什麼演算法技術」這類高層知識，而非單純的程式碼片段。

**相較於動態組隊研究**  
過去有研究依任務條件式描述（task-conditional descriptions）招募專家、即時生成智能體與計畫、以非監督式重要性分數（unsupervised importance score）排序，或將 LLM 操作圖（graph of LLM operations）中的節點提示與智能體間邊（inter-agent edges）一起最佳化。MARS 採用的是自我回報主題能力機制：由專家自己判斷題目是否在其領域內，再組成小型團隊。這種做法簡潔，但也帶來自我評估可能過度自信的風險。

**相較於其他競技程式設計多智能體系統**  
AgentCoder 透過程式設計師、測試設計師與測試執行器三方迭代；MapCoder 串接檢索、規劃、編碼與除錯；CodeSIM 進一步引入模擬驅動規劃與除錯；Solvita 則發展相關分解。MARS 與它們最大的區別在於維持純提示框架，不依賴強化學習或人類回饋，並以確定性的公開測試執行作為回饋來源。

**主要限制**  
1. **語料庫覆蓋率**：cp-algorithms 雖然廣泛，但冷門或新興演算法主題可能缺乏對應專家或檢索內容。  
2. **自我評估誤差**：專家可能高估自身相關性，或對跨領域綜合題目判斷錯誤。  
3. **公開測試的侷限**：系統僅能見到公開範例（public examples），可能過擬合可見測資，無法保證在隱藏測試上的穩健性。  
4. **規模上限**：最多三名專家、八個步驟的預算，對於最困難的奧林匹亞級題目可能仍不足。  
5. **骨幹模型上限**：作為純提示系統，MARS 的最終表現受 Gemma 4 的推理與程式生成能力限制。  
6. **基礎設施修復器的範圍**：僅處理樣板碼層級問題，無法修復深層語意錯誤或演算法邏輯缺陷。

#### 可重現性評估

論文已將原始碼公開於 GitHub：https://github.com/fckand/mars，這是提升可重現性的重要基礎。評估所使用的 CodeContests 測試分割、cp-algorithms 演算法理論語料庫，以及 Gemma 4 與 Jina Embeddings v2 等模型權重，原則上均為公開資源；ExecEval 沙盒執行環境也在文獻中公開發表。

**有利因素**  
- 實驗設定明確：溫度 0.0、top-p 0.95、4096 token 預算，隨機性極低。  
- 所有對照系統（Direct、Single-RAG、Parallel ensemble、Base relay、CodeSIM）使用相同骨幹模型與主要超參數，比較基準一致。  
- 論文宣稱附錄 A、B 提供完整提示模板與端到端範例，附錄 C 提供 MARS 與各基線的虛擬碼（pseudocode），有助於復現管線邏輯。

**待確認因素**  
由於無法直接檢視倉庫內容，以下項目會影響實際可重現程度：倉庫是否包含預先建好的檢索索引、每位專家的標籤集合與主題描述、自我評估提示、接力 orchestration 程式碼、ExecEval 整合方式，以及基礎設施修復器的具體規則。若這些元件齊全，則重現門檻主要落在運算資源：雖然 MARS 比 CodeSIM 便宜，但每題仍需多次 Gemma 4 推論與沙盒執行，需要足夠的 GPU 或 API 配額。

整體而言，MARS 在可重現性方面具備良好潛力：公開資料、公開模型、公開程式碼與詳細附錄，使其成為競技程式設計多智能體研究中相對容易跟隨與擴展的工作。

#### 未來研究方向

1. **更精準的路由機制**  
   以學習式或經過校準（calibrated）的分類器取代純粹自我回報，並結合題目難度估計，可減少專家誤配與過度自信問題。

2. **混合檢索：理論 + 實作**  
   在現有演算法理論語料庫之外，加入高品質程式碼範例、測試案例與錯誤修復紀錄，讓專家同時掌握「該用什麼演算法」與「如何正確實作」。

3. **更強大的驗證訊號**  
   除了公開測試，可引入自動生成測資、符號執行（symbolic execution）或輕量級形式驗證，以彌補公開測資覆蓋不足的問題。

4. **自適應預算**  
   根據題目難度或中間執行表現動態調整專家人數與步驟上限，對簡單題目提前停止，對困難題目允許更深度的接力。

5. **骨幹模型多樣性與專家化**  
   為不同主題專家配置不同規模或經過專門微調的模型，或引入更強大的開源／商業骨幹模型，觀察是否能進一步縮小與 CodeSIM 的差距。

6. **與模擬驅動方法的結合**  
   在保留 MARS 低成本優勢的前提下，選擇性地整合 CodeSIM 式的模擬規劃與搜尋，形成「主題專家接力 + 模擬驗證」的混合架構。

7. **跨領域遷移**  
   將主題對齊接力框架應用到數學推理、科學發現或軟體工程等其他需要深層領域知識（domain knowledge）的任務。

8. **從歷史軌跡學習**  
   收集成功與失敗的接力軌跡，用以更新提示、擴充檢索語料庫，或精煉專家描述，實現持續改進。

9. **多語言程式生成**  
   目前 MARS 鎖定 C++17，未來可擴展至 Python、Java 等語言，並研究語言特性對專家設計與樣板碼修復的影響。

10. **更困難的評估基準**  
    在奧林匹亞級題目、IOI、Codeforces 高難度賽事或更嚴苛的隱藏測試上驗證，以檢驗系統在極端稀疏正確訊號下的穩健性。

## 論文問答

**Q1：競技程式設計中，現有大型語言模型面臨的核心困難是什麼？**

A：競技程式設計題目通常結合了深厚的演算法理論洞見與問題特定的上下文，正確性回饋非常稀疏，僅靠單一骨幹模型難以穩定選出合適的演算法技術。直接提示（direct prompting）往往把演算法策略的選擇全權交給模型本身，導致在需要動態規劃、圖論或幾何等專門知識時頻繁失敗。因此，如何將演算法領域知識有效地注入生成流程，是提升通過率的關鍵挑戰。

**Q2：現有的多智能體管線為何難以應對這類問題？**

A：現有方法大多採用階段對齊分解，例如規劃器、編碼器、除錯器等通用角色，但這些角色並不具備特定演算法主題的專業知識，演算法技術的選擇仍由骨幹模型單獨承擔。這種通用分工無法針對競技程式設計中多樣化的主題需求進行調適，也缺乏與演算法理論語料庫的緊密結合。結果是，系統雖然能產出語法正確的程式，卻常在核心策略上出錯。

**Q3：為什麼解決這個問題具有重要意義？**

A：競技程式設計被視為程式碼生成與深層推理能力的嚴格壓力測試，能在此領域穩定求解代表模型具備更強的演算法理解與問題拆解能力。此外，MARS 在提升通過率的同時顯著降低實際耗時與每項任務的 token 消耗變異數，對於需要可預測成本與低延遲的產品化應用極具價值。這也為其他需要領域專長的複雜任務，例如數學推理或科學發現，提供了可參考的多智能體設計範式。

**Q4：MARS 的核心方法架構是什麼？**

A：MARS 是一個純提示框架，內建多個主題專家代理，每個代理專精於單一演算法領域，並透過檢索增強生成（RAG）從對應的 cp-algorithms 語料庫切片中取得理論依據。面對題目時，所有代理先自我評估是否與題目主題匹配以及是否能啟動接力，從中挑選最多三名專家組成團隊。接著由啟動代理撰寫初始 C++17 解，後續每一回合都會在沙盒中執行公開測試，現用專家根據執行結果決定保留、修復或交接草稿，最後再由基礎設施修復階段正規化樣板程式碼。

**Q5：MARS 相較於先前多智能體系統的主要創新在哪裡？**

A：MARS 以「主題對齊多智能體接力」取代傳統的「階段對齊分解」，讓每個代理成為單一演算法主題的領域專家，而非通用的規劃或除錯角色。它將公開測試執行結果作為每一接力步驟的迴路內訊號，使專家能即時根據實際執行狀況修正或交接程式碼。此外，團隊組成並非預先固定，而是透過專家自我回報的主題能力動態形成，從而讓系統能針對每道題目調度最相關的演算法知識。

**Q6：MARS 有哪些關鍵設計選擇？**

A：系統選用 Gemma 4 作為骨幹模型，溫度設為 0.0、top-p 為 0.95，並將每次生成限制在 4096 個 token，以確保輸出穩定且可控。檢索部分使用 Jina Embeddings v2 對 cp-algorithms 語料庫進行編碼，每個專家只檢索與其主題標籤對應的語料庫切片。為了平衡效能與成本，接力最多包含三名不同專家與八個步驟，並設有無進展截止條件與基礎設施修復階段，僅在偵測到輸入輸出接線、型別寬度等樣板層級錯誤時才進行修正。

**Q7：MARS 在哪些實驗設定與基線上進行評估？**

A：實驗使用 CodeContests 測試分割中的 165 道題目，所有方法均以 Gemma 4 為骨幹模型進行公平比較。對照基線包括直接提示（Direct）、僅使用最相關專家的 Single-RAG、合併多名專家候選的 Parallel ensemble、移除公開測試自我檢查與基礎設施修復的 Base relay，以及較強的對照方法 CodeSIM。這樣的設計能夠清楚檢視主題專家、接力機制與基礎設施修復各自帶來的貢獻。

**Q8：MARS 的主要實驗結果是什麼？**

A：在 CodeContests 測試集上，MARS 達到 0.624 ± 0.006 的通過率，平均每項任務僅需 2.3 個管線階段，相較於直接提示提升了 14.4 個百分點。雖然仍略低於 CodeSIM 的 0.731，但 MARS 已大幅縮小差距，同時實際耗時僅為 CodeSIM 的三分之一左右。更重要的是，MARS 每項任務的 token 消耗標準差約為 CodeSIM 的七分之一，顯示其在成本可預測性上具有顯著優勢。

**Q9：消融實驗揭示了哪些組件的重要性？**

A：Base relay 去除了公開測試自我檢查、子任務追蹤與基礎設施修復，其表現低於完整 MARS，顯示這些機制對於穩定產出正確解不可或缺。Single-RAG 只使用一名最相關專家，無法處理需要跨主題協作的複雜題目；Parallel ensemble 雖然能合併多名專家意見，但缺乏接力過程中的迭代精進與錯誤修復。相較之下，MARS 的動態組隊加上逐步執行回饋，是提升通過率與控制成本的核心組合。

**Q10：MARS 可應用於哪些實務場景？**

A：MARS 可部署為競技程式設計的練習輔助工具，協助使用者根據題目主題自動生成帶有解釋的 C++17 解題程式。它也能應用於技術面試準備平台，針對動態規劃、圖論、字串等常見主題提供逐步引導與程式碼修正。由於其每項任務的 token 消耗變異數小，特別適合需要穩定計費與低延遲回應的商業 API 服務。

**Q11：若將 MARS 產品化，需要考慮哪些因素？**

A：首先必須建立安全的沙盒執行環境，以確保公開測試能在隔離狀態下正確且安全地運行。其次，cp-algorithms 等演算法理論語料庫需要持續維護與更新，並隨著新演算法主題擴充專家代理池。此外，雖然 MARS 是純提示框架，省去了微調成本，但仍需監控專家自我評估的準確性，並在延遲、token 預算與解題品質之間取得平衡。

**Q12：MARS 對多智能體與程式碼生成領域可能帶來什麼影響？**

A：MARS 證明了將智能體異質性與任務的主題結構對齊，並輔以檢索增強生成，能顯著優於通用角色分工的基線。這一設計思路可推廣至數學推理、科學計算、軟體工程等其他需要深厚領域知識的任務。未來的多智能體系統可能會更強調「領域專家＋動態組隊＋執行回饋」的架構，而非單純堆疊規劃、編碼、除錯等通用角色。

**Q13：MARS 目前有哪些已知的限制？**

A：本研究主要在 CodeContests 資料集與 Gemma 4 模型上進行評估，尚未驗證於其他模型或更具挑戰性的奧林匹亞級題目。系統依賴公開測試作為迴路內訊號，若公開測試覆蓋不足，可能無法發現隱藏邊界錯誤。此外，專家團隊規模與接力步數設有人工上限，自我回報的主題能力也可能偶爾誤判，這些都是目前設計上的限制。

**Q14：MARS 在哪些情況下可能失敗？**

A：當題目需要同時融合多種深層演算法技術，且無法被單一主題專家完整掌握時，接力可能難以收斂到正確解。若公開範例過於簡單而隱藏測試涵蓋極端案例，現用專家可能誤以為程式已正確而提前停止。此外，若專家對自身專長範圍過度自信或過度保守，可能導致錯誤的團隊組成，進而影響初始策略與後續修復方向。

**Q15：未來可以朝哪些方向改進 MARS？**

A：未來可擴充專家代理池，納入更多新興或複合主題，並結合更強大的骨幹模型以進一步提升單步生成品質。也可以引入隱藏測試回饋、獎勵模型或學習式團隊組成機制，讓系統能根據歷史表現自動挑選最適專家。此外，將 MARS 的主題接力架構與大規模搜尋、採樣或形式化驗證結合，並應用於定理證明、數學競賽等領域，是值得探索的後續方向。

## 實務應用指南

### 適用場景

1. **競技程式設計輔助與教育平臺**  
   將 MARS 嵌入解題訓練系統，讓學生在遇到動態規劃、圖論、字串、幾何等主題時，自動呼叫對應主題專家代理，產生可執行的 C++17 候選解並根據公開測試即時修正，作為示範或提示工具。

2. **企業內部演算法題庫自動化解題**  
   針對面試題庫、編碼測驗或內部競賽平臺，利用 MARS 的主題自評與接力機制，自動為每道題目組建最相關的小型專家團隊，降低人工分類與反覆調 prompt 的成本。

3. **程式競賽即時輔助系統**  
   在限時比賽或線上評測（Online Judge）環境中，MARS 可在僅使用公開測試的前提下快速迭代，適合做為「第一輪草稿產生器」，再由選手接手處理隱藏測資與邊界條件。

4. **演算法教學與知識檢索增強問答**  
   把 MARS 的 RAG 模組獨立出來，結合 cp-algorithms 等理論語料庫，提供「主題導向」的演算法解釋、範例程式與錯誤分析，強化學習者的理論基礎。

5. **低資源環境下的程式生成基線**  
   相較於需要大量取樣與複雜模擬的方法（如 CodeSIM），MARS 以較少管線階段與較低實際耗時達到可接受的通過率，適合在 GPU 預算或延遲敏感的產品中作為首選基線。

### 實作步驟建議

1. **建立主題專家池與語料庫切片**  
   將演算法理論語料庫依主題（動態規劃、圖論、字串、幾何等）切分，並為每個切片設計專家角色描述與標籤集合。

2. **建置 RAG 檢索層**  
   使用嵌入模型將每個語料庫切片與題目描述向量化，實作「每個專家只看自己主題切片」的檢索增強生成機制。

3. **設計自我評估提示**  
   讓每位主題專家針對新題目回答三個問題：是否在專業範圍內、是否與主題相關、是否有信心啟動接力，並回傳分數與 `can-start` 標記。

4. **組建小型專家團隊**  
   依分數選出最多三位專家，並從 `can-start` 標記為真的專家中挑選啟動代理，負責撰寫初始 C++17 候選解。

5. **實作接力迴路**  
   每一回合依序執行：(a) 現用專家根據當前程式碼、子任務與 RAG 上下文產生草稿；(b) 在沙盒中執行公開測試；(c) 專家決定保留、修復或交接給下一位專家；(d) 將結構化封包與程式碼傳遞下去。

6. **加入終止條件與基礎設施修復**  
   設定最多八步、最多三位不同專家、連續兩次無進展則重繞、三次無進展則停止的機制。接力結束後，由基礎設施修復階段檢查並修正 I/O 接線、標頭檔、型別寬度等樣板程式碼問題。

7. **評估與迭代**  
   在 CodeContests 或自有題庫上測量通過率、每題 token 消耗量、實際耗時與標準差，並根據失敗案例調整專家描述、檢索片段長度與終止條件。

### 潛在風險與注意事項

- **過度依賴公開測試導致隱藏測資表現不佳**  
  MARS 僅使用公開範例作為迴路內訊號，可能過擬合於公開案例。建議在產品中保留人工複審或額外單元測試階段，並明確標示為「草稿輔助」而非最終答案。

- **主題分類錯誤造成專家組隊失當**  
  若題目橫跨多個主題或自我評估不準，可能選錯專家。可加入第二層「元評審」模型或規則式後處理，檢查專家回覆的一致性與覆蓋率。

- **沙盒安全風險**  
  執行未經審查的 C++17 程式碼可能帶來資安威脅。務必使用隔離沙盒、限制執行時間與記憶體、禁止網路存取，並對編譯選項進行白名單控管。

- **Token 與延遲波動**  
  雖然 MARS 的每題 token 消耗標準差較小，但仍需監控個別題目的管線階段數。建議設定硬性預算上限與逾時中斷，避免少數難題拖垮整體服務。

- **純提示框架的可維護性**  
  所有專家行為仰賴提示模板，版本管理與 A/B 測試非常重要。建議將每個專家的系統提示、RAG 片段格式與結構化封包格式納入版本控制。

### 與其他技術的整合建議

- **與現有 Online Judge 系統整合**  
  將 MARS 的沙盒層對接至既有評測系統的編譯與執行 API，讓公開測試結果直接驅動接力流程，無需重新打造執行環境。

- **與傳統規劃—編碼—除錯管線互補**  
  MARS 可取代或強化現有管線中的「編碼器」角色，保留既有的規劃器與除錯器作為前後處理，形成「主題專家 + 通用角色」的混合架構。

- **與程式碼搜尋與文件檢索工具結合**  
  除了 cp-algorithms，也可擴充至公司內部程式碼庫、API 文件或歷史解題紀錄，讓專家代理同時具備理論與實作層面的參考資料。

- **與持續整合/持續部署（CI/CD）管線整合**  
  將 MARS 用於自動產生演算法題或迴歸測試的參考實作，並透過 CI 執行公開測試，作為程式碼合併前的快速驗證步驟。

- **與人機協作介面整合**  
  在 IDE 外掛或聊天機器人中暴露「目前由哪位專家處理」、「公開測試結果」、「交接原因」等結構化封包資訊，提升使用者信任度與可解釋性。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「適用場景」與「實作前置條件」讀起，理解 MARS 如何像一支「演算法專家接力隊」解決程式競賽題目。接著參考附錄中的端到端範例，觀察主題專家如何根據公開測試保留、修復或交接程式碼，再回頭閱讀方法細節。

**AI 工程師**  
重點關注第 3 節的方法實作：專家自我評估的提示設計、RAG 切片策略、結構化封包格式、接力終止條件與基礎設施修復階段。建議直接參考附錄 C 的虛擬碼與 GitHub 原始碼，評估如何將其移植到自有模型與沙盒環境。

**研究人員**  
請聚焦於 MARS 與現有多智能體系統的差異：主題對齊的異質專家、語料庫切片式 RAG、公開測試作為迴路內訊號，以及與 CodeSIM 等模擬驅動方法在通過率、實際耗時與 token 變異數上的權衡。可進一步探討專家組隊機制、自我評估校準與跨主題題目的泛化性。

**產品經理**  
本研究的核心價值在於以較低成本（3.3 倍低於 CodeSIM 的實際耗時、更穩定的每題 token 消耗）顯著提升通過率。建議評估將 MARS 作為競技程式設計輔助、面試題庫自動化解題或演算法教學工具的商業可行性，同時注意公開測試過擬合與安全沙盒等落地風險。
