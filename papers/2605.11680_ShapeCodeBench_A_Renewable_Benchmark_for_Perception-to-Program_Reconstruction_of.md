## 摘要翻譯

我們提出 ShapeCodeBench，一個用於感知到程式重建（perception-to-program reconstruction）的合成基準：給定一張渲染後的點陣圖（raster image），模型必須輸出一個可執行的繪圖程式（drawing program），由確定性評估器（deterministic evaluator）重新渲染並與目標進行比較。v1 領域特定語言（DSL）在 512 × 512 的黑白畫布上定義了四個基本元件（primitive），但每個實例皆由種子式隨機數產生器（seeded RNG）生成，因此可建立新的保留測試集（held-out set）以減少實例級污染（exact-instance contamination）。我們釋出一個凍結分割（frozen split）eval_v1，包含 150 個樣本，涵蓋簡單、中等與困難三個難度等級（difficulty tier），並以完全匹配（exact match）、像素準確率（pixel accuracy）、前景交並比（foreground IoU）、解析成功率（parse success）與執行成功率（execution success）進行評分。我們評估了空程式基線（empty-program floor）、一個經典電腦視覺啟發式（classical computer-vision heuristic），以及 Claude Opus 4.7（高強度與最大強度）與 GPT-5.5（中等強度與超高強度推理）的表現。該啟發式在簡單場景中具有競爭力，但當形狀重疊使連通元件（connected components）融合時即失效；最強的多模態模型（multimodal model）配置保留了大部分前景結構（foreground structure），但仍因微小的參數誤差（parameter errors）而無法達到完全匹配。最佳整體完全匹配仍然偏低，因此 ShapeCodeBench 距離基準飽和（benchmark saturation）仍有相當距離。基準程式碼、凍結資料集、執行產物（run artifacts）與論文原始檔案皆已釋出，以支援獨立複現（independent replication）與延伸。

### 核心貢獻（3～5點）
- 提出 ShapeCodeBench，一個專為「感知到程式重建」任務設計的可再生合成基準，採用種子式隨機數產生器生成實例，可隨時建立新的保留測試集以避免實例級污染。
- 釋出凍結的 eval_v1 分割（150 個樣本，涵蓋三個難度等級），並建立以確定性評估器為基礎的多指標評分體系（完全匹配、像素準確率、前景交並比、解析成功率、執行成功率）。
- 系統性地比較空程式基線、經典電腦視覺啟發式，以及 Claude Opus 4.7 與 GPT-5.5 在不同推理強度下的表現，揭示啟發式在重疊場景下的失效與前沿多模態模型在參數精度上的瓶頸。
- 證實 ShapeCodeBench 距離基準飽和仍有相當距離，為視覺程式歸納（visual program induction）與反向圖學（inverse graphics）研究提供具挑戰性的評測平台。
- 完整釋出基準程式碼、凍結資料集、執行產物與論文原始檔案，支援獨立複現與後續延伸研究。

### 適合對象
從事視覺語言模型（vision-language model）、視覺程式歸納、反向圖學、結構擷取（structure extraction）與符號向量生成（symbolic vector generation）等領域的研究者與工程師；以及關注基準設計、抗污染評測方法論、可重現人工智慧研究的學術界與產業界人士。對評估前沿多模態模型在精細視覺結構理解與程式合成能力上表現的研究團隊尤具參考價值。

## 深度分析

#### 方法論解析

ShapeCodeBench 的方法論核心在於建立一個「感知到程式重建」（perception-to-program reconstruction）的合成基準（synthetic benchmark），其設計哲學強調三個交會的設計壓力：確定性執行（deterministic execution）、基於渲染的評分（render-based scoring）、以及受控生成（controlled generation）。整體方法論可拆解為五個相互耦合的元件。

**領域特定語言（DSL）的極簡設計。** ShapeCodeBench 的 DSL 僅包含四個基本元件（primitives）：`filled_circle`、`circle`、`filled_square`、`square`，分別對應實心圓、空心圓、實心方塊、空心方塊。每個基本元件接受整數參數（位置、尺寸、線寬等），刻意排除浮點數與複雜控制流（如迴圈、條件分支）。這種極簡設計具有雙重意涵：一方面降低了語法解析失敗的雜訊，使評估能聚焦於「感知正確性」而非「程式碼生成正確性」；另一方面讓評估器只需使用安全的受限 Python 解析器（safe restricted Python parser）即可處理所有輸出，大幅降低任意程式碼執行的安全風險。畫布固定為 512×512 灰階，前景為黑色、背景為白色，這種黑白畫布（black-on-white canvas）的單色設計消除了色彩感知與紋理識別的變因。

**種子式生成器與難度分層。** 每個場景實例皆由種子式隨機數產生器（seeded RNG）生成，並透過顯式的難度控制參數調節形狀數量、尺寸、線寬、重疊程度與畫布裁切。生成器支援三個難度等級（difficulty tier）：easy、medium、hard，每個等級 50 個樣本，總計 150 個樣本構成凍結的 `eval_v1` 分割。這種「按軸分解」（axis-factorized）的設計繼承自 CLEVR 的診斷傳統，使研究者能將失敗模式歸因於特定的視覺因子（例如重疊、裁切、密集度），而非混雜的雜訊。

**確定性渲染管線。** 評估器使用與生成器相同的 Pillow 渲染管線重新渲染（re-render）模型輸出的程式碼，並與目標點陣圖（raster image）進行比對。這種「渲染即評分」的設計避免了文字差異導致的誤判：即使模型生成的程式碼在語法上與參考解不同，只要語意等價程式（semantically equivalent program）能渲染出相同的視覺結果，仍應獲得滿分。這與 TurtleBench 等基準的設計哲學一致，但 ShapeCodeBench 進一步將渲染管線完全確定化，確保跨平台、跨時間的評分一致性。

**五維評分指標體系。** ShapeCodeBench 採用五個互補的評分指標：完全匹配（exact match）、像素準確率（pixel accuracy）、前景交並比（foreground IoU）、解析成功率（parse success）、執行成功率（execution success）。其中完全匹配是最嚴格的指標，要求渲染結果與目標逐像素相同；前景交並比則容忍小幅度參數誤差（parameter errors），僅衡量前景區域的重疊程度；解析成功率與執行成功率則診斷模型輸出是否能被正確解析與執行。這種多層次的指標設計使研究者能區分「感知失敗」與「程式碼生成失敗」。

**可再生基準（renewable benchmark）的一等公民設計。** ShapeCodeBench 最具方法論創新性的設計在於將「基準刷新」（benchmark refresh）提升為一等公民的工作流程。由於生成器與評估器皆完全自動化，研究者可從新種子生成全新的保留測試集（held-out set）並自動評分，無需逐實例人工標註（per-instance human annotation）或人工評分（manual judging）。這不僅緩解了實例級污染（exact-instance contamination），更將基準的更新週期從「月」縮短到「分鐘」，使基準能跟上模型迭代的速度。

#### 實驗數據解讀

ShapeCodeBench 的實驗設計採用了「地板—天花板—前沿」三層次的基線策略：空程式基線（empty-program floor）作為性能下限、經典電腦視覺啟發式（classical computer-vision heuristic）作為非學習式對照、四種前沿多模態模型（frontier multimodal model）配置作為性能前沿。這種設計使實驗結果能從多個角度解讀。

**基準線的揭示性。** 空程式基線（即模型輸出空字串或無效程式）作為下限，量化了「完全失敗」時的像素準確率與前景交並比；經典電腦視覺啟發式（基於連通元件分析 connected components 與形狀擬合）則代表了「無深度學習」時代的最佳對策。這兩個基線的存在使多模態模型的相對性能有了明確的錨點。

**難度等級依賴的交叉現象（tier-dependent crossover）。** 實驗結果揭示了一個極具啟發性的模式：在 easy 等級，經典啟發式以 0.26 的完全匹配率領先所有多模態配置（最高僅 0.08）；但在 medium 與 hard 等級，啟發式完全崩潰，而 GPT-5.5 在超高強度（extra_high effort）下仍能維持最高 0.87 的前景交並比。這種交叉現象反映了兩種方法論的根本差異：啟發式透過分離連通元件（individuating separated connected components）能精確識別獨立形狀，但當形狀重疊（overlapping shapes）導致元件融合時便無能為力；多模態模型則透過整體感知保留了大部分前景結構（foreground structure）與空間結構（spatial structure），但因參數估計的小幅誤差而無法達到完全匹配。

**推理強度（reasoning effort）的溫和效應。** 實驗顯示推理強度的提升對性能有正向但溫和的影響：Claude Opus 4.7 在最大強度（max effort）下的前景交並比高於高強度（high effort）；GPT-5.5 在超高強度下亦優於中等強度（medium effort）。然而，這種提升未能跨越啟發式與多模態模型之間的完全匹配鴻溝，顯示推理強度的增加主要改善了「思考的深度」而非「感知的精度」。

**基準飽和度的明確證據。** 最佳整體完全匹配率僅 0.087（啟發式於 easy 等級），多模態模型中最高僅 0.027。這些數字明確證明 ShapeCodeBench 遠未飽和（far from saturated），仍有大量改進空間。值得注意的是，GPT-5.5 在超高強度下達到 0.87 的前景交並比，顯示其「幾乎正確」但「不完全正確」——這是一個典型的「最後一哩」問題，模型已掌握大致結構，僅在精確參數上失誤。

**失敗模式的診斷價值。** 前景交並比與完全匹配之間的巨大差距（0.87 vs 0.027）揭示了多模態模型的核心失敗模式：它們能正確識別「有幾個形狀」、「大致在哪裡」、「大致多大」，但難以精確輸出「圓心座標 (x, y) = (237, 412)、半徑 r = 47」這類整數參數。這種「結構正確、參數錯誤」的模式為未來研究提供了明確的改進方向。

#### 與現有研究的比較

ShapeCodeBench 在三條既有的研究脈絡中定位自身：視覺程式歸納（visual program induction）、合成診斷基準（synthetic diagnostic benchmarks）、以及多模態模型的圖像到程式碼評估。

**與視覺程式歸納的關係。** ShapeCodeBench 的概念祖先可追溯至 CSGNet [15]，後者從 2D 與 3D 形狀推導構造性實體幾何（CSG）程式。後續工作 [12, 9, 8, 4, 5] 將程式歸納擴展至透視場景、重複 3D 結構、參數基本元件與可重複使用的程式庫合成。然而，這些系統皆為「方法論優先」的展示，而非「基準優先」的現代多模態模型評估。ShapeCodeBench 採納了這些工作的 DSL 設計哲學，但將焦點從「展示某個系統能解決此問題」轉為「系統化評估前沿模型在此問題上的能力邊界」。

**與 CLEVR 傳統的關係。** CLEVR [6] 與 CLOSURE [1] 展示了精心分解的合成基準如何暴露推理失敗模式並減少虛假捷徑。ShapeCodeBench 繼承了這種「按軸分解」的診斷姿態，但有三個關鍵差異：(1) 任務從「視覺問答」轉為「程式生成」，輸出空間從離散答案擴展至結構化程式碼；(2) 評分從「答案正確性」轉為「渲染正確性」，更貼近程式語義；(3) 加入了可再生性（renewability）作為一等公民設計，這是 CLEVR 系列所欠缺的。

**與 TurtleBench 的關係。** TurtleBench [13] 是近期將視覺程式歸納復興為「基準優先」目標的代表，專注於 Turtle 繪圖語言。ShapeCodeBench 與 TurtleBench 共享「基準優先」的設計哲學，但 DSL 更簡單（4 個基本元件 vs Turtle 的多樣指令），畫布更小（512×512 vs Turtle 的更大畫布），且更強調可再生性。這種「更窄、更深、更可再生」的定位使 ShapeCodeBench 能更精確地診斷失敗模式，但也限制了其覆蓋的視覺概念範圍。

**與截圖到程式碼工作的關係。** 截圖轉 HTML（screenshot-to-HTML）[2, 16]、網頁結構擷取（structure extraction）、LaTeX 與樂譜識別 [14]、符號向量生成（symbolic vector generation）[10, 19] 等工作皆探討「圖像到程式碼」的同一根本問題。ShapeCodeBench 的差異在於其刻意將問題窄化至最簡單的視覺場景，使評估能完全自動化且確定化，避免了 HTML/CSS 等複雜語義中難以評分的灰色地帶。

**主要限制。** ShapeCodeBench 的極簡 DSL 雖帶來評估便利，但也限制了其外部效度：現實世界的圖像到程式碼任務涉及色彩、紋理、漸層、曲線、文字等豐富視覺元素，這些皆不在 ShapeCodeBench 的覆蓋範圍內。此外，作者坦承基準刷新「無法防止模型學習生成器的分布」（does not prevent models from learning the generator distribution），這是一個根本性的限制——若模型的訓練資料包含類似分布的合成資料，基準的診斷價值將被削弱。

#### 可重現性評估

ShapeCodeBench 在可重現性（reproducibility）方面展現了極高的成熟度，幾乎達到了該領域的最佳實踐標準。

**程式碼與資料的完整釋出。** 基準程式碼、凍結資料集、執行產物（run artifacts）與論文原始碼皆於 GitHub 公開（https://github.com/shivamk3r/shape-code-bench），並於 Zenodo 釋出存檔版本（DOI: 10.5281/zenodo.20132286）。這種「程式碼 + 資料 + 論文 + 存檔」的四重釋出模式，使獨立複現（independent replication）成為可能。

**逐樣本點陣圖雜湊值。** 為了確保跨平台的評估實例完全一致，作者釋出了每個樣本的點陣圖雜湊值（per-sample raster hashes）。這是一個細節但關鍵的設計：即使不同平台的 Pillow 版本或浮點精度有細微差異，雜湊值仍能驗證渲染結果是否完全一致。

**提供者無關的執行器（provider-agnostic runner）。** 執行器記錄了提示詞、模型配置、原始輸出、標準化預測、評分指標與逐樣本產物，使模型評估可審計且易於擴展。這種設計使新增模型（如未來的 GPT-6、Claude Opus 5）只需實作一個適配器介面，無需修改核心評估邏輯。

**凍結分割的明確性。** `eval_v1` 分割被明確凍結，包含 150 個樣本（每難度等級 50 個），並使用確定性種子。這使不同論文的結果可直接比較，避免了「在不同的測試集上比較」這一常見的可重現性陷阱。

**可重現性的潛在風險。** 儘管釋出程度極高，仍有兩個潛在風險：(1) 模型 API 的版本演進——Claude Opus 4.7 與 GPT-5.5 的 API 行為可能隨時間變化，使歷史結果難以重現；(2) 硬體與浮點精度差異——雖然點陣圖雜湊能驗證最終結果，但中間的模型推理過程可能因硬體而異。這些風險屬於整個領域的系統性問題，而非 ShapeCodeBench 特有的缺陷。

#### 未來研究方向

ShapeCodeBench 的設計與實驗結果揭示了多條值得探索的未來研究方向。

**DSL 的漸進式擴展。** 當前 DSL 僅有 4 個基本元件，未來可逐步加入三角形、橢圓、直線、弧線、多邊形等基本元件，並引入簡單的控制流（如 `for` 迴圈生成重複圖案）。這種擴展應保持「評估完全自動化」的原則，避免引入需要人工判定的語義元素。

**三維場景的延伸。** 將 DSL 從 2D 擴展至 3D（如立方體、球體、圓柱體）將大幅提升任務的複雜度與診斷價值，並與 CSGNet 等 3D 視覺程式歸納工作建立更直接的橋樑。然而，3D 渲染的確定性與跨平台一致性是技術挑戰。

**更多前沿模型的系統評估。** 當前僅評估了 Claude Opus 4.7 與 GPT-5.5 的四種配置，未來應納入更多模型（如 Gemini、Llama、Qwen-VL）以及開源視覺語言模型（vision-language model），以建立更全面的模型能力地圖。特別是開源模型的納入將使研究者能進行更深入的錯誤分析（如注意力視覺化、表示探測）。

**「最後一哩」參數精度的專項研究。** GPT-5.5 在超高強度下達到 0.87 前景交並比但僅 0.027 完全匹配的現象，揭示了「結構正確、參數錯誤」這一普遍失敗模式。未來研究可專門探討如何提升參數精度，例如：(1) 將參數預測分解為粗估計與精細化兩階段；(2) 引入符號回歸或數值優化作為後處理；(3) 設計專門的參數精度獎勵函式進行微調。

**生成器分布學習的對抗性評估。** 作者坦承基準刷新無法防止模型學習生成器的分布。未來可設計「對抗性基準」：每次評估時根據模型的歷史錯誤動態調整生成器的分布，使模型無法透過記憶訓練資料來作弊。這將把基準從「靜態測試集」演進為「動態對手」。

**與程式語言模型的整合。** 將 ShapeCodeBench 與程式碼大型語言模型的預訓練結合，探索「視覺預訓練是否能提升程式碼生成」或「程式碼預訓練是否能提升視覺感知」等跨模態遷移問題，將為多模態學習理論提供新的實驗平台。

**評分指標的精緻化。** 當前的完全匹配過於嚴格（容忍度為零），前景交並比過於寬鬆（容忍度為無限大）。未來可引入「參數層級的容忍度」，例如允許座標 ±2 像素的誤差、半徑 ±1 像素的誤差仍視為匹配，從而更精確地區分「感知正確但量化誤差」與「感知錯誤」。

**真實世界圖像的遷移評估。** 雖然 ShapeCodeBench 刻意使用合成圖像以確保評估確定性，但最終目標是評估真實世界圖像到程式碼的能力。未來可設計「合成到真實」的遷移評估：在 ShapeCodeBench 上預訓練或微調，於真實世界的圖標、Logo、UI 元素等場景上測試，量化合成訓練的遷移效益。

這些方向不僅能擴展 ShapeCodeBench 本身的覆蓋範圍，更能推動「感知到程式重建」這一研究主題從「基準評估」走向「能力建構」，最終實現真正能從圖像生成可執行程式碼的視覺語言模型。

## 論文問答

**Q1：什麼是「感知到程式重建」(perception-to-program reconstruction) 任務？為什麼這個任務對現代多模態模型很重要？**

A：感知到程式重建任務要求模型觀察一張渲染後的點陣圖像，並輸出一個可執行的繪圖程式，該程式經由確定性評估器重新渲染後與目標圖像比對。這個任務的重要性在於它測試模型是否能從視覺輸入中逆向推導出產生該圖像的符號化、結構化程式碼，而非僅僅進行像素級的擬合。對於現代多模態模型而言，這項任務考驗的不只是視覺感知能力，更包括將視覺資訊抽象化、量化為精確參數（如座標、半徑、邊長）並組合成語法正確的程式語句的能力。這也是從「看圖說話」邁向「看圖重建」的核心能力躍遷。

**Q2：現有的視覺程式歸納 (visual program induction) 與圖像轉程式碼基準存在哪些不足？ShapeCodeBench 如何回應這些不足？**

A：現有方法如 CSGNet 等雖然證明了圖像到程式問題的可行性，但多數並非以「基準優先」(benchmark-first) 的方式評估現代大型視覺語言模型；它們通常缺乏可再生性、確定性執行與基於渲染的評分三者的結合。許多基準仰賴人工標註或人工評分，難以快速刷新；也有些基準雖然自動化，但無法控制難度因子或避免實例級污染。ShapeCodeBench 透過種子式隨機數產生器 (seeded RNG) 自動生成場景，並以確定性 Pillow 流水線重新渲染評分，使得新保留測試集可隨時生成、評估可重現，同時保留 CLEVR 式的診斷性設計哲學。

**Q3：為什麼「可再生」(renewable) 基準設計對當前多模態模型評估特別重要？**

A：隨著大型模型在訓練過程中可能接觸到公開基準的資料，「實例級污染」(exact-instance contamination) 已成為評估可信度的嚴重威脅；可再生基準允許研究者從全新種子生成保留測試集，從根本上緩解此問題。此外，可再生設計改變了模型開發的回饋循環：研究者可在不委請新標註或人工評分的情況下，自動產生新實例並取得客觀分數，這對於快速迭代與迴歸測試至關重要。ShapeCodeBench 將基準刷新提升為一等公民工作流程，使基準本身能隨模型進步而持續保持鑑別力。

**Q4：ShapeCodeBench 的領域特定語言 (DSL) 設計有何特色？為何選擇僅有四個基本元件？**

A：ShapeCodeBench 的 DSL 僅包含四個基本元件：filled_circle、circle、filled_square、square，全部在 512×512 的黑白畫布上操作。這種極簡設計是刻意的窄化任務範疇，使失敗模式可被歸因於特定的視覺因子（如形狀數量、大小、筆畫寬度、重疊、畫布裁切），而非 DSL 本身的複雜度。透過限制基本元件數量，基準得以聚焦於「感知到程式」的核心挑戰——精確參數估計與結構化程式碼生成——而非語法記憶或元件辨識。同時，這也讓評估器的解析與渲染流程保持透明、可重現。

**Q5：ShapeCodeBench 的評估器如何運作？為何採用「基於渲染的評分」(render-based scoring) 而非文字比對？**

A：評估器使用安全的受限 Python 解析器 (safe restricted Python parser) 解析模型預測的程式，再透過與生成目標圖像相同的確定性 Pillow 流水線重新渲染，最後以像素級指標與目標比對。採用基於渲染的評分是因為語意等價的程式可能在文字上完全不同（例如不同的變數命名、順序或冗餘語句），但渲染結果一致；文字比對會對這些等價程式造成不公平的懲罰。這種設計也讓評估對模型輸出格式的小幅變化更具容忍度，更貼近實際的程式語意正確性。

**Q6：ShapeCodeBench 的三個難度等級（easy、medium、hard）是如何定義與控制的？**

A：三個難度等級透過種子式隨機數產生器中的明確難度控制參數來區分，這些參數涵蓋形狀數量、大小、筆畫寬度、重疊程度與畫布裁切等視覺因子。easy 等級通常包含較少且分離的形狀，medium 開始引入中等程度的重疊，hard 則涉及更多形狀、更密集的重疊與更極端的參數組合。這種受控的難度設計使研究者能診斷模型在不同視覺條件下的具體失敗模式，例如本文發現經典電腦視覺啟發式在 easy 等級領先，但在 medium 與 hard 上因重疊融合而崩潰。

**Q7：ShapeCodeBench 的主要評估指標有哪些？它們各自捕捉什麼樣的能力？**

A：ShapeCodeBench 使用五個主要指標：exact match（完全匹配，要求程式語意與參數完全一致）、pixel accuracy（像素準確率，衡量整體像素級相似度）、foreground IoU（前景交並比，聚焦於前景形狀區域的重疊程度）、parse success（解析成功率，衡量模型輸出是否能被解析器接受）與 execution success（執行成功率，衡量解析後的程式是否能成功執行）。這些指標互補：parse/execution success 反映基本的程式語法能力，pixel accuracy 與 foreground IoU 反映視覺重建品質，而 exact match 則是最嚴格的綜合指標，要求參數完全精確。

**Q8：ShapeCodeBench 上各模型的關鍵實驗結果為何？呈現什麼樣的「難度等級依賴交叉」現象？**

A：實驗顯示經典電腦視覺啟發式在 easy 等級的 exact match 上以 0.26 領先所有多模態配置（後者最高僅 0.08），但在 medium 與 hard 等級上崩潰，因為重疊形狀融合導致連通元件分析失效。GPT-5.5 在 extra_high 推理強度下達到最高的 foreground IoU（最高 0.87），在所有難度等級皆領先，並保留了大部分空間結構，但因小幅參數誤差而無法達成 exact match（最佳多模態 exact match 僅 0.027）。Claude Opus 4.7 在兩個推理強度下的 foreground IoU 都落後於啟發式。這種「啟發式在簡單場景領先、LLM 在複雜場景保留結構」的交叉現象，凸顯了兩類方法的不同失敗模式。

**Q9：推理強度 (reasoning effort) 對模型表現有何影響？是否能縮小啟發式與多模態模型之間的差距？**

A：推理強度的提升對表現有幫助但幅度有限：Claude Opus 4.7 在 max effort 下於 foreground IoU 上略優於 high effort，GPT-5.5 在 extra_high effort 下亦優於 medium effort。然而，這種提升並不足以縮小啟發式與多模態模型在 easy 等級 exact match 上的差距，也無法讓多模態模型在 medium/hard 等級超越啟發式的崩潰點。這顯示推理強度的增加主要改善了空間結構的保留，但對於精確參數估計的幫助有限，凸顯了「感知」與「精確程式碼生成」之間仍存在結構性鴻溝。

**Q10：ShapeCodeBench 的設計理念可應用於哪些實際場景？**

A：ShapeCodeBench 的窄化、可控與可再生設計理念可應用於許多需要從視覺輸入生成結構化程式碼的場景，例如設計工具中的「圖像轉 SVG」、UI 設計稿轉程式碼、CAD 草圖重建與技術插圖向量化等。這些場景都要求模型不僅理解視覺內容，還要產出可編輯、可參數化的符號化表示，而非僅僅是像素擬合。此外，ShapeCodeBench 的診斷式設計哲學（明確控制難度因子）也適用於其他需要細粒度錯誤分析的視覺理解任務，如醫學影像報告生成或科學圖表理解。

**Q11：ShapeCodeBench 對多模態模型的產品化部署有何啟示？**

A：從實驗結果可看出，當前前沿多模態模型在「精確參數估計」上仍有結構性不足——即使 GPT-5.5/extra_high 能保留 0.87 的前景 IoU，exact match 仍僅 0.027，這對需要精確重建的產品（如 CAD 重建、設計稿轉程式碼）是重大瓶頸。產品化部署時應考慮混合策略：在簡單、分離的場景中可採用經典電腦視覺啟發式（其 easy 等級表現優異），在複雜、重疊的場景中則輔以多模態模型以保留空間結構。此外，parse success 與 execution success 指標提醒我們，模型輸出的語法可靠性仍是工程化部署的基礎門檻。

**Q12：ShapeCodeBench 對視覺程式歸納與多模態評估領域的整體影響為何？**

A：ShapeCodeBench 透過同時滿足確定性執行、基於渲染的評分與可再生性三項設計壓力，為該領域提供了一個新的基準範式，鼓勵未來工作朝「基準優先、可刷新、可診斷」的方向發展。其釋出的程式碼、凍結資料集、執行產物與論文源也大幅降低了獨立複現的門檻，有助於建立可累積的科學對話。更重要的是，ShapeCodeBench 揭示了「感知」與「結構化程式碼生成」之間的鴻溝，為後續研究（如更好的參數估計、符號接地、神經符號混合方法）提供了明確的目標與診斷工具。

**Q13：ShapeCodeBench 存在哪些已承認的限制？**

A：作者明確承認的限制包括：DSL 僅有四個基本元件，過於簡化，無法代表真實世界的複雜繪圖任務；畫布固定為 512×512 黑白，限制了視覺多樣性；可再生設計雖緩解了實例級污染，但無法防止模型學習生成器的分布（即模型可能學會「模擬」生成器而非真正理解視覺內容）；評估指標中 exact match 過於嚴格，可能低估語意等價但參數不同的程式。此外，基準僅評估了兩個前沿模型與有限的推理強度配置，更廣泛的模型與配置比較仍有待未來工作。

**Q14：ShapeCodeBench 上觀察到的主要失敗模式有哪些？**

A：主要失敗模式可分為三類：第一，經典電腦視覺啟發式在重疊形狀融合時崩潰，因為連通元件分析無法區分融合後的形狀邊界；第二，多模態模型在精確參數估計上持續犯錯，即使空間結構大致正確，座標、半徑或邊長的小幅誤差仍導致 exact match 失敗；第三，模型輸出可能無法被解析器接受（parse success 失敗）或解析後無法執行（execution success 失敗），反映語法可靠性問題。這些失敗模式凸顯了不同方法的能力邊界，也為未來改進提供了具體方向。

**Q15：ShapeCodeBench 的未來發展方向為何？**

A：未來發展方向可能包括：擴充 DSL 以涵蓋更多基本元件（如三角形、橢圓、曲線、群組與迴圈），使其更貼近真實繪圖任務；引入彩色畫布與更複雜的視覺場景；增加更多模型與配置的評估以建立更全面的基準基準線；探索神經符號混合方法以結合經典電腦視覺的精確性與多模態模型的結構理解；以及將基準擴展到三維場景或時序繪圖任務。此外，作者也提到可進一步研究「模型學習生成器分布」的風險，並設計相應的對抗性評估方法。

## 實務應用指南

### 適用場景

1. **CAD 與向量圖重建工具的模型選型**：在工程設計領域，常需要將掃描的點陣圖（如手繪草圖、舊版 PDF 工程圖）反向重建為可編輯的向量格式。ShapeCodeBench 的「感知到程式重建」框架可直接用於評估不同視覺語言模型在「圖轉向量程式」任務上的表現，作為選型依據。

2. **教育科技中的幾何題目自動評分**：中小學幾何題常以點陣圖形式呈現圓與方塊的組合。將 ShapeCodeBench 的 DSL 擴充為教學版幾何描述語言，可讓學生作答的圖像自動轉為程式、比對標準答案，支援大規模自動化評分。

3. **UI 設計稿轉程式碼的前置研究**：雖然 ShapeCodeBench 的 DSL 僅有四個基本元件，但其「渲染式評分」與「確定性執行」機制可作為截圖轉 HTML/React 元件研究中的微型沙盒，用來隔離並診斷模型在「視覺感知 → 結構化程式碼」轉換上的失敗模式。

4. **機器人視覺中的符號場景理解**：在工業機器人或服務機器人場景中，常需將攝影機拍攝的符號標記（如地面標線、QR 碼變體）解析為可執行的繪圖指令。ShapeCodeBench 的合成場景可作為符號解析管線的回歸測試集。

5. **生成式 AI 的紅隊與安全評估**：ShapeCodeBench 的可再生特性（fresh held-out sets）讓安全研究人員能在不洩漏測試樣本的前提下，持續評測模型是否會在「圖生程式」任務中產生惡意或越權的程式碼。

### 實作前置條件

**資料需求**
- 凍結評估集 `eval_v1`（150 樣本，easy/medium/hard 各 50），可從 Zenodo DOI `10.5281/zenodo.20132286` 下載。
- 若需自建訓練或測試集，須具備 Python 3.10+ 環境與 Pillow 函式庫以執行場景生成器。
- 每個樣本需附帶：渲染後 PNG、對應 DSL 程式碼、種子值、難度等級標籤。

**運算資源**
- 渲染與評分階段僅需 CPU，單張 512×512 影像渲染時間 < 100 ms。
- 評估前沿多模態模型時，建議準備具備 ≥ 80GB VRAM 的 GPU（如 A100/H100）以容納 1M 上下文視窗；或使用對應 API（Anthropic、OpenAI）並預留足夠 token 額度。
- 批次評估 150 樣本 × 4 種推理強度設定，建議預留 4–8 小時 API 配額。

**技能門檻**
- 熟悉 Python AST 與受限解析器（restricted parser）設計，以確保模型輸出在沙箱中安全執行。
- 具備電腦視覺基礎（連通元件分析、輪廓偵測）以理解經典啟發式基準的運作原理。
- 熟悉多模態模型的 prompt 工程與推理強度參數調校。
- 具備基本的統計分析能力，能解讀 exact match、pixel accuracy、foreground IoU 等指標的差異。

### 實作步驟建議

1. **建立開發環境並取得基準**：複製 GitHub 倉庫 `shivamk3r/shape-code-bench`，安裝依賴（`pip install -r requirements.txt`），驗證 `eval_v1` 的 150 個樣本可正確載入並通過既有評估器。

2. **理解 DSL 與受限解析器**：閱讀 `dsl.py` 與 `parser.py`，確認四個基本元件（`filled_circle`、`circle`、`filled_square`、`square`）的參數語法（座標、半徑/邊長、線寬）。在沙箱中手動撰寫幾個範例程式，觀察渲染輸出。

3. **建立基準參考線**：先執行「空程式基線」與「經典 CV 啟發式」（如連通元件分離 + 形狀擬合），記錄其在三個難度等級的 exact match 與 foreground IoU。這些數字將作為後續模型比較的錨點。

4. **設計 prompt 模板**：根據論文中描述的 prompt 格式（含 DSL 語法說明、範例、輸出格式限制）撰寫 prompt 模板。建議加入「僅輸出程式碼，勿加解釋」的系統指令，以提升 parse success。

5. **批次評估多模態模型**：使用論文中釋出的 provider-agnostic runner，分別以 Claude Opus 4.7（high / max effort）與 GPT-5.5（medium / extra_high effort）對 150 樣本進行推論。務必保留原始輸出、normalized predictions 與每樣本產物，以便審計。

6. **計算五項指標**：對每個樣本計算 exact match、pixel accuracy、foreground IoU、parse success、execution success，並按難度等級分組彙整。論文中 GPT-5.5/extra_high 在 foreground IoU 達 0.87、exact match 僅 0.027 的落差，是診斷「感知正確但參數誤差」的關鍵指標。

7. **分析失敗模式**：將錯誤樣本依類型分類——參數誤差（半徑/座標偏移）、元件遺漏、重疊融合、語法錯誤——並比對不同推理強度設定的改善幅度。

8. **建立回歸測試流程**：利用 seeded RNG 設計一個 CI/CD 流程，每次模型更新時自動生成新的保留測試集（fresh held-out set），執行評估並比對指標變化，避免基準飽和後失去鑑別力。

9. **產出可審計的執行產物**：將每次評估的 prompts、模型設定、原始輸出、normalized predictions、metrics 與 per-sample artifacts 打包成結構化目錄，方便日後重現與第三方驗證。

### 潛在風險與注意事項

- **基準污染風險**：雖然 ShapeCodeBench 透過 seeded RNG 支援可再生，但若模型曾於訓練階段接觸過相同 DSL 語法，仍可能學會生成器分佈。建議每次重要評估都使用全新種子產生的保留測試集，而非反覆使用 `eval_v1`。

- **評估指標的語義陷阱**：render-based scoring 雖避免了文字差異懲罰，但 foreground IoU 高（0.87）不代表 exact match 高（0.027）。若產品決策僅看 IoU，可能誤判模型已「足夠好」；應同時關注 exact match 與參數誤差分佈。

- **受限解析器的安全性**：模型輸出會被傳入 Python 解析器執行，即便使用 restricted parser，仍須嚴格限制可呼叫的函式與屬性，避免模型產生 `__import__` 或檔案 I/O 等越權指令。建議在 Docker 沙箱或 gVisor 中執行評估。

- **推理強度的成本邊際效應**：論文中 max > high、extra_high > medium 的提升幅度有限，但 token 成本可能倍增。在生產環境部署前，應繪製「推理強度 vs. 指標 vs. 成本」曲線，找出甜蜜點。

- **DSL 過於簡化的泛化風險**：四個基本元件的 DSL 無法代表真實世界的複雜圖像（如漸層、曲線、文字）。若將 ShapeCodeBench 的結論直接外推至截圖轉 HTML 等任務，可能產生過度樂觀的預期。

- **經典 CV 啟發式的天花板**：在 easy 等級，啟發式以 0.26 exact match 領先所有多模態模型；若產品場景以「分離、形狀單純」為主，傳統管線可能比 LLM 更划算。應依場景特性選擇技術路線。

### 與其他技術的整合建議

- **與視覺程式歸納系統整合**：ShapeCodeBench 的 DSL 可作為 CSGNet [15]、LILO [5] 等視覺程式歸納系統的標準化評估介面。建議將這些系統包裝為可產生 ShapeCodeBench 相容輸出的適配層，統一比較。

- **與 MLOps 平台整合**：將 provider-agnostic runner 接入 MLflow 或 Weights & Biases，每次評估自動記錄指標、樣本產物與模型版本，支援 A/B 測試與回歸分析。

- **與合成資料生成管線整合**：ShapeCodeBench 的 seeded generator 可作為更大規模合成資料工廠的元件，例如擴充 DSL 加入三角形、橢圓、路徑，產生百萬級訓練樣本供視覺語言模型微調。

- **與紅隊評估框架整合**：將 ShapeCodeBench 的「圖生程式」任務接入如 HarmBench、AdvBench 等紅隊框架，評估模型在面對惡意視覺輸入時是否會產生有害程式碼。

- **與教育評分系統整合**：將 DSL 擴充為幾何描述語言後，可整合至 Moodle、Canvas 等 LMS 平台，作為幾何題自動評分引擎的核心。

- **與向量圖編輯器整合**：將 ShapeCodeBench 的渲染器與 Inkscape、Adobe Illustrator 的腳本介面對接，使模型輸出可直接匯入專業設計工具進行後製。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「給模型一張圖，讓它寫程式把圖畫回來」這個核心任務。跳過技術細節，專注於「為什麼這比單純的圖像分類更難」以及「為什麼需要可再生的基準」。可執行程式碼倉庫中的 `demo.ipynb`，親眼觀察模型在三個難度等級的表現差異，建立直觀感受。

**給 AI 工程師**：重點閱讀第 3 節（DSL、生成器、評估器設計）與第 4 節（實驗設定）。特別注意受限解析器的實作、render-based scoring 的設計取捨，以及 provider-agnostic runner 的架構。可將此基準整合至現有的模型評估 CI/CD 流程，作為視覺感知任務的回歸測試。論文中 GPT-5.5/extra_high 與 Claude Opus 4.7/max 的比較數據，可作為內部模型選型的參考起點。

**給研究者**：第 2 節的相關工作梳理了視覺程式歸納、合成診斷基準、可再生評估三條脈絡，是定位自身研究的重要參考。第 5 節的失敗模式分析（參數誤差、重疊融合、感知 vs. 程式發射的落差）提供了多個值得深挖的研究方向，例如：如何讓模型在前景 IoU 高的同時降低參數誤差？推理強度的邊際效益何時遞減？建議從「保留測試集的可再生性」切入，探討基準設計對抗污染的新機制。

**給產品經理**：ShapeCodeBench 的核心訊息是「前沿多模態模型在圖生程式任務上仍有巨大改進空間」——最佳 exact match 僅 0.087（啟發式）與 0.027（多模態）。這意味著任何宣稱「AI 可一鍵將設計稿轉為程式碼」的產品，都應對其準確度與可靠性抱持務實期待。建議將 ShapeCodeBench 作為內部技術盡職調查的微型沙盒，在投入大規模資源前，先用此基準驗證供應商模型的真實能力。同時注意「推理強度提升帶來的成本增加」與「傳統 CV 啟發式在簡單場景的競爭力」，這些都是產品定價與技術路線決策的關鍵輸入。
