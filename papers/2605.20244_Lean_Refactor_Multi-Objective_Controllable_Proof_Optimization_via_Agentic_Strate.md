## ⚡ TL;DR

現有方法難以同時縮短Lean證明長度、降低編譯成本並維持跨版本穩定，且每次模型更新都需重新微調。
提出LeanRefactor，以檢索增強代理框架與版本感知策略庫，在凍結LLM上實現多目標可控重構。
競賽證明壓縮逾七成、研究型程式碼庫逾二成，編譯時間最高降六成，且重構後證明更易零樣本遷移至未來版本。

## 深度分析

#### 方法論解析

Lean Refactor 是一個檢索增強（retrieval-augmented）代理框架（agentic framework），其核心設計理念在於將重構（refactoring）知識外化（externalize）至一個精選資料庫（curated database），從而讓凍結代理式大型語言模型（frozen agentic LLM）在推論階段（inference time）透過檢索（retrieval）而非微調（fine-tuning）來完成多目標（multi-objective）優化。整體方法圍繞三大設計選擇展開：

第一，**密集標註（densely annotated）的版本感知策略庫（strategy bank）**。不同於一般程式碼重構僅依賴雜訊–乾淨程式碼配對（noisy-clean code pairs）或重構軌跡（refactoring trajectories），Lean Refactor 建構了超過 9 千條多目標重構策略（multi-objective refactoring strategies）。每條策略均為可複用的重構模式（pattern），並攜帶結構化後設資料（metadata），明確記錄其支援的 Lean/Mathlib 版本（supported Lean/Mathlib versions）、預期編譯成本降低（expected compilation-cost reduction）幅度，以及適用情境與執行範例。這種設計直接回應了 Lean 程式碼庫（Lean repositories）脆弱的相容性（fragile compatibility）問題：當 Lean 與 Mathlib 以近週為週期發布新版本時，策略庫可透過版本標註進行過濾，避免模型因知識截止點（knowledge cutoff）而產生對過時策略（stale tactics）或已移除 API（removed APIs）的普遍幻覺（pervasive hallucination）。

第二，**多目標檢索與重排（multi-objective retrieve-and-rerank）**。在推論時，系統首先對目標證明進行語義接地（semantic grounding），透過依賴註解（dependency annotations）理解其與 Mathlib 及專案內引理的關聯。隨後，根據使用者指定的偏好（如證明長度 proof length、編譯成本 compilation cost、版本相容性 version compatibility 之間的權衡取捨 trade-offs），動態過濾並重排策略。此機制讓框架具備可控制（controllable）特性：使用者可在推論階段引入未見目標（unseen objectives），而無需重新訓練模型。這解決了標準預訓練（pretraining）、人類回饋強化學習（RLHF）或微調（fine-tuning）無法原則性平衡相互牴觸（in tension）目標的問題。

第三，**隨插即用（plug-and-play）的代理循環（agent loop）**。框架將檢索到的策略注入由凍結前沿大型語言模型（frozen frontier LLMs）實例化的三個模組——規劃者（planner）、重構者（refactorer）與除錯者（debugger）——組成的代理循環中。由於權重固定，該框架可無縫轉移至 Gemini、Claude 與 GPT 系列等不同骨幹模型，完全規避因模型頻繁更替（model churn）或 Lean 發布週期（release cycle）變動所導致的重複微調（repeated fine-tuning）成本。

#### 實驗數據解讀

論文在兩類性質迥異的資料上進行評估：競賽基準測試（competition benchmarks）與研究型程式碼庫（research repositories）。

在競賽數學領域，Lean Refactor 於 miniF2F、PutnamBench 與 Putnam2025 上達到超過 70% 的 Token 層級壓縮（token-level compression）。這顯示對於結構相對標準、依賴較少的競賽證明，檢索增強策略能大幅消除冗餘步驟（redundant steps）與不必要的重度自動化（heavy automation）。然而，研究型程式碼庫（如 PFR、PhysLean、Analysis、FLT）的壓縮率降至 20% 以上。此落差並非方法失效，而是反映了研究級證明更密集的跨檔案與 Mathlib 依賴網路：簡化這類證明需要理解更大的上下文，難度顯著高於競賽語料。

編譯成本（compilation cost）方面的成果尤具實務意義。框架不僅達到最高 60% 的編譯時間縮減（compilation-time reduction），一般情況下亦能穩定降低超過 30%。這驗證了圖 2 的核心觀察：證明長度（proof length）與編譯時間的 Pearson 相關係數僅約 0.1，代表「短證明」不等於「低成本證明」。先前研究將長度作為編譯成本的替代推論目標，本研究則透過策略庫中的預期編譯成本降低標註，實現對兩者的聯合優化。

版本穩健性（version-robust）實驗顯示，版本過濾檢索（version-filtered retrieval）能進一步提升目標 Lean 版本（target Lean version）上的壓縮表現。更具前瞻性的發現是，經重構的 miniF2F 證明（refactored miniF2F proofs）相較於未重構的對應版本（unrefactored counterparts），展現出更強的零樣本版本遷移（zero-shot version transfer）能力，能在更多未來 Lean 版本（future Lean releases）中通過型別檢查。這暗示良好的重構不僅是「壓縮」，更是透過消除對易變 API 的依賴來提升程式碼的向前相容性。

#### 與現有研究的比較

本研究與先前研究（prior work）的差異可從三個維度剖析。

**目標空間**：既有 LLM 驅動的自動證明器（LLM-powered provers）與重構工作多聚焦單一目標——通常是證明正確性或長度最小化——並透過強化學習（RL）或微調（fine-tuning）達成。然而，Lean 重構本質上多目標（natively multi-objective）：較繁重的策略（heavier tactics）可能縮短證明長度卻膨脹編譯成本（inflate compilation cost），而成本較低的證明（cheaper proofs）又可能拉長篇幅。Lean Refactor 首次在推論階段提供原則性的權衡取捨（trade-offs）機制，無需針對新目標重新訓練。

**版本對齊**：前沿大型語言模型（frontier LLMs）的知識截止點（knowledge cutoff）普遍早於近期 Mathlib 發布（圖 3），導致與 Lean 發布週期（release cycle）脫節（misaligned with）。現有代理框架（agentic frameworks）即便搭配網頁搜尋增強（web-search augmentation），也缺乏讓維護者（maintainer）將程式碼庫（codebase）版本與相容模型配對的原則性方法。Lean Refactor 透過策略庫的版本後設資料（metadata）與動態過濾，將版本相容性（version compatibility）轉化為可檢索、可驗證的訊號，這是其他基於訓練的流程（training-based pipelines）無法比擬的優勢——後者每次遇到新 LLM 版本發布（LLM releases）或函式庫版本（library versions）更新，都需重複微調（repeated fine-tuning）。

**資料與場景**：先前研究主要依賴社群彙整之競賽語料庫（community-aggregated competition corpora），如 NuminaMath 或 miniF2F，但競賽證明無法反映研究級證明（research-level proofs）的結構複雜度。本研究額外評估了 PFR、PhysLean 等研究型程式碼庫，填補了此空白。與 Claude Code 相比，Lean Refactor 在壓縮率與編譯成本降低上均勝出，且保持對多種骨幹模型的相容性。

**限制**：策略庫的覆蓋率與品質仍是瓶頸；對於極度依賴特定 Mathlib 內部結構的證明，若策略庫中缺乏對應版本的重構模式，檢索增強的效益會遞減。此外，框架目前假設策略庫由人工或半自動方式精選（curated），其維護成本在 Mathlib 高速演化下不容忽視。

#### 可重現性評估

論文明確釋出迄今最大規模的 Lean 重構資料集：超過 20 萬對長短證明配對（long-short proof pairs）以及 9 千條重構策略（refactoring strategies），每條均標註編譯成本降低與相容 Lean/Mathlib 版本。這對社群極具價值，因為配對重構資料（paired refactoring data）在 Lean 生態中向來稀缺。

在模型權重方面，由於 Lean Refactor 採用凍結大型語言模型（frozen LLMs）作為骨幹，研究者無需取得或釋出任何專有權重，僅需呼叫 Gemini、Claude 或 GPT 系列的公開 API 即可復現代理循環（agent loop）的行為。

然而，就完整可重現性而言，論文摘要與內文雖詳述框架設計與演算法虛擬碼（Algorithm 1），但未於提供的節錄中給出公開原始碼儲存庫連結、策略庫的具體授權條款，或自動化建置策略庫的完整工具鏈。實務上，若缺少釋出程式碼與精選資料庫（curated database）的定期同步機制，外部研究者將難以完全復現其在未來 Lean 版本上的版本穩健（version-robust）表現。因此，目前可重現性評級為「資料集部分釋出、方法論清晰、但完整系統實作待公開」。

#### 未來研究方向

基於 Lean Refactor 的架構與實驗結果，以下幾個方向值得深入探索：

**自動化策略庫演化**：當前策略庫需人工或半自動維護以跟上 Mathlib 發布週期（release cycle）。未來可發展自動化管線，從新版本的 Mathlib 提交紀錄中萃取重構模式，並自動驗證其版本相容性（version compatibility）與預期編譯成本降低（expected compilation-cost reduction），降低維護者（maintainer）負擔。

**跨證明輔助系統遷移**：雖然本框架針對 Lean 設計，但其檢索增強（retrieval-augmented）代理框架的核心概念——以外化的後設資料（metadata）彌補凍結 LLM 的知識截止點（knowledge cutoff）——可遷移至 Coq、Isabelle/HOL 等其他形式化驗證生態，解決類似的版本脆弱性問題。

**動態多目標偏好學習**：目前使用者需在推論階段明確指定權衡取捨（trade-offs）。未來可結合線上學習或少量使用者回饋，讓框架自動推斷特定程式碼庫或開發者偏好的多目標組合，甚至處理推論階段才出現的未見目標（unseen objectives）。

**編譯成本代理模型**：實際測量編譯成本（compilation cost）在推論時仍屬昂貴操作。可訓練輕量級代理模型（surrogate model）來預測策略應用後的編譯時間，從而加速多目標重排，使代理循環（agent loop）在計算上更具可擴展性。

**研究級程式碼庫的深層語義重構**：當前在研究型程式碼庫（research repositories）上的壓縮率仍有大幅提升空間。未來工作可強化跨檔案依賴的語義接地（semantic grounding），發展能夠重構引理網路（lemma networks）而非僅單一證明的全局優化策略，以處理更複雜的協作式機器驗證數學（collaborative, machine-verified mathematics）專案。

## 論文問答

**Q1：Lean Refactor 旨在解決 LLM 生成 Lean 證明的哪些核心挑戰？**
A：本研究指出三個根本瓶頸：首先，Lean 重構本質上是多目標的，證明長度、編譯成本與版本相容性往往相互牴觸，難以同時滿足。其次，Lean 與 Mathlib 的函式庫版本演進迅速，但前沿大型語言模型的知識截止點與之脫節，導致模型經常幻覺出過時策略或已移除的 API。第三，基於訓練的流程面臨模型頻繁更替與 Lean 發布週期的雙重壓力，每次推出新模型或新版本都需重複微調，擴展性極差。

**Q2：現有的微調或代理框架為何無法有效處理 Lean 證明重構？**
A：現有以強化學習或微調為基礎的方法主要將獎勵綁定在證明正確性上，導致模型對冗餘步驟與過度自動化不敏感，無法辨識可簡化的結構。這類方法缺乏在推論階段平衡證明長度與編譯成本等競爭目標的原則性機制。此外，建構於預訓練通用推理大型語言模型之上的代理框架，由於權重凍結且知識截止點固定，無法動態適應快速演進的 Mathlib API，因而難以在版本快速更迭的環境中維持可靠性。

**Q3：為何多目標優化對 Lean 證明重構具有關鍵的實務重要性？**
A：實證顯示證明長度與編譯時間僅存在微弱相關性，因為縮短證明可能反而呼叫更繁重的策略，進而膨脹編譯成本。研究型程式碼庫更高度依賴 Mathlib 與專案內部引理，形成複雜的依賴網路，單純追求長度壓縮可能破壞可維護性。因此，同時考量證明長度、編譯成本與版本相容性，才能產出既簡潔又高效、且能跨越不同 Lean 版本穩定運作的重構結果。

**Q4：Lean Refactor 的核心架構為何？它如何運用檢索增強技術？**
A：Lean Refactor 是一個隨插即用的檢索增強代理框架，其設計核心是將重構知識外化到一個精選且密集標註的策略庫中。該資料庫收錄了可重複使用的多目標重構策略，每筆資料都帶有後設資料，例如支援的 Lean/Mathlib 版本與預期編譯成本降低幅度。在推論階段，系統根據使用者指定的目標與版本限制，動態檢索並重新排序相關策略，再引導凍結代理式大型語言模型執行重構，無需對模型本身進行任何微調。

**Q5：Lean Refactor 如何在無需微調底層 LLM 的情況下，實現可控制的多目標重構？**
A：本框架將重構專業知識從模型權重中解耦，轉而儲存在經過策展、具備版本感知能力的策略庫內。系統在推論時依據使用者對證明長度、編譯成本與版本相容性的偏好，動態過濾並重新排序策略。接著，這些帶有明確執行指令與結構脈絡的策略被餵給凍結的大型語言模型，使其能夠按需朝不同目標進行最佳化，同時保持對 Gemini、Claude 或 GPT 系列等不同骨幹模型的相容性。

**Q6：策略庫與代理迴路的設計選擇背後有哪些關鍵考量？**
A：策略庫的每筆條目都密集標註了重構後設資料，包括經驗證的 Lean/Mathlib 版本相容性與預期編譯成本降低，這直接緩解了模型知識截止點與函式庫發布週期之間的脫節。在推論階段，系統透過依賴註解進行語意接地，以處理研究型證明中複雜的外部與內部引理網路。代理迴路則由規劃器、重構器與除錯器組成，且可由任何凍結的前沿大型語言模型實例化，確保整個框架能夠隨插即用於不同的模型供應商。

**Q7：Lean Refactor 在哪些基準測試與程式碼庫上進行評估？**
A：實驗涵蓋了數學競賽基準測試，包括 miniF2F、PutnamBench 與 Putnam2025，以及研究型程式碼庫如 PFR、PhysLean、Analysis 與 FLT。相較於競賽證明，這些研究型程式碼庫更大量依賴 Mathlib 與專案內部依賴，結構複雜度顯著更高。透過同時在標準化競賽題目與真實世界數學函式庫上驗證，作者得以全面評估框架在壓縮率與編譯效率上的表現。

**Q8：Lean Refactor 相較於先前研究與 Claude Code 達成了哪些關鍵量化成果？**
A：在競賽基準測試上，Lean Refactor 達到超過 70% 的 Token 層級壓縮，在研究型程式碼庫上則超過 20%，並且最高可縮減 60% 的編譯時間。此外，經重構的 miniF2F 證明在零樣本版本遷移至未來 Lean 版本時，表現出比未重構對應版本更強的穩健性。這些成果不僅顯著優於先前研究與 Claude Code，也證明了以後設資料驅動的檢索增強方法能同時兼顧長度與成本目標。

**Q9：版本過濾檢索對框架效能有何具體貢獻？**
A：版本過濾檢索會將策略庫限制在已明確驗證可用於使用者目標 Lean/Mathlib 工具鏈的條目，從而大幅減少對過時策略與不相容 API 的幻覺。實驗顯示，相較於未過濾的檢索，這種機制能進一步提升在目標 Lean 版本上的壓縮率。這證實了將代理模型扎根於版本特定策略，對於維持重構品質至關重要，尤其是在底層證明生態系持續超越大型語言模型訓練截止點的情況下。

**Q10：在哪些實務場景中，Lean Refactor 對 Lean 生態系使用者最具價值？**
A：對於需要跨越快速演進之 Lean 版本進行大規模升級的 Mathlib 等大型函式庫維護者而言，此工具能顯著降低手動重寫數千行證明碼的負擔。研究人員在處理依賴密集、編譯成本高昂的研究型程式碼庫時，也能藉此提升證明可讀性並加速協作。此外，競賽參與者與教育工作者可利用它將 LLM 生成的冗長證明精煉為簡潔、易於理解的形式，同時確保與最新工具鏈相容。

**Q11：Lean Refactor 的「隨插即用」特性體現在哪裡？為何這對產品化很重要？**
A：本框架將底層大型語言模型視為凍結的代理，無論使用 Gemini、Claude 或 GPT 系列模型，都不需要進行微調或架構修改。這項設計對產品化至關重要，因為它能隔離模型頻繁更替帶來的衝擊，讓使用者在不重新訓練管線或蒐集新配對資料的情況下，立即採用更新或更具成本效益的前沿模型。同時，這也降低了部署門檻，使組織能將 Lean Refactor 整合至現有偏好的模型後端，避免供應商綁定。

**Q12：Lean Refactor 可能對 LLM 驅動的形式化驗證與自動證明領域帶來哪些廣泛影響？**
A：Lean Refactor 證明了透過精選且富含後設資料的策略庫，可以有效引導凍結的大型語言模型，從而提供一種可擴展的替代方案，擺脫每當新模型或函式庫版本出現就需重複微調的昂貴循環。其多目標、可控制的重構典範將關注焦點從單純的正確性擴展到效率與可維護性，這對工業級形式化驗證尤為關鍵。這種方法也可能啟發其他形式語言與軟體工程領域建構類似的檢索增強代理框架，特別是那些同樣面臨版本脆弱性與競爭優化目標的場景。

**Q13：作者在資料稀缺性與模型覆蓋範圍方面承認了哪些根本限制？**
A：作者指出，相較於 Python 或 Java 等主流語言，Lean 的配對重構資料極為稀少，因為其程式碼庫規模較小，且現有語料庫缺乏重構軌跡或雜訊–乾淨程式碼配對。此外，前沿大型語言模型固有的知識截止點落差，意味著單一模型無法原生涵蓋所有歷史與未來的 Lean/Mathlib 版本。雖然 Lean Refactor 透過策略庫緩解了此問題，但策略庫本身仍需隨著新函式庫版本的發布持續策展與重新分析。

**Q14：哪些類型的證明或情境可能仍然是 Lean Refactor 難以有效處理的？**
A：相較於自成一格的競賽題目，那些具有極度密集且複雜依賴網路的研究級證明——例如高度仰賴專案內部引理與特定 Mathlib 內部實作的證明——帶來更大的挑戰。由於證明長度與編譯成本之間的相關性薄弱，若檢索到的策略無意間建議了更繁重的策略，則積極的長度壓縮有時反而可能增加編譯時間。此外，需要超出語法重構的語意變更，或依賴策略庫尚未收錄之全新 API 的尖端證明，仍可能發生重構失敗或品質下降。

**Q15：作者提出了哪些未來研究方向以延伸此項工作？**
A：作者建議擴充策略庫以涵蓋更多樣化與更前沿的 Lean/Mathlib 版本，潛在途徑包括從版本控制歷史中自動挖掘重構模式。他們也暗示可將即時編譯成本回饋等連續執行階段訊號更緊密地整合進代理迴路，以進一步精煉多目標權衡取捨。最後，將此檢索增強代理典範推廣至其他形式化驗證語言與軟體工程情境，是超越 Lean 領域、實現框架通用化的重要前景。

## 實務應用指南

### 適用場景

1. **大型 Lean/Mathlib 專案的持續維護**：當函式庫每週發布新版本、API 頻繁異動時，維護者可利用 Lean Refactor 自動壓縮累積的冗長證明，並透過版本過濾檢索確保重構後的證明與目標工具鏈相容，降低跨版本遷移成本。
2. **數學競賽與教育平台**：針對 LLM 產生的正確但冗長之競賽證明（如 miniF2F、Putnam），平台可將其作為後處理模組，在保持正確性的前提下壓縮 Token 長度、降低編譯成本，提升學生閱讀體驗與系統吞吐量。
3. **研究級形式化數學專案**：在 PFR、PhysLean、FLT 等依賴密集的研究型程式碼庫中，用於處理跨檔案引理網路複雜的重構需求，顯著縮減整體編譯時間，加速證明迭代。
4. **自動證明器的後處理管線**：作為隨插即用的精煉層，接在現有 LLM 驅動的自動證明器（如 ReProver、Goedel-Prover）之後，將「正確但粗糙」的初始證明轉化為簡潔、低成本且易維護的最終產出。
5. **CI/CD 版本遷移輔助**：整合至持續整合流程，自動偵測因 Lean/Mathlib 升級而失效的證明風格，並透過具備版本相容性標註的策略庫，產生可於未來版本零樣本遷移的重構建議。

### 實作前置條件

- **資料**：目標 Lean 程式碼庫的完整存取權限；若無內部重構軌跡，可從論文釋出之 200K 長短證明配對與 9K 重構策略起步，再針對組織內部語料擴充。策略庫需具備密集後設資料，包括支援的 Lean/Mathlib 版本與預期編譯成本降低幅度。
- **運算**：可執行目標 Lean/Mathlib 工具鏈的編譯環境（建議多核心 CPU 與充足記憶體，以批次測量實際編譯時間）；呼叫前沿 LLM API（Gemini、Claude、GPT 系列）的網路連線與預算。
- **技能**：熟悉 Lean 4 語法、Mathlib API 與證明結構；具備向量檢索系統（如 Milvus、Pinecone）建置經驗；能設計代理框架（ReAct / tool-use）與多目標控制邏輯，無需模型微調能力。

### 實作步驟建議

1. **建構版本感知策略庫**：以論文釋出資料為基底，針對內部程式碼庫挖掘重構模式。每筆策略必須標註適用語境（競賽或研究級）、預期編譯成本降低率，以及經驗證的 Lean/Mathlib 版本清單。
2. **部署語義檢索與多目標過濾器**：將策略庫嵌入向量資料庫，並依使用者偏好（證明長度優先、編譯成本優先或平衡）與目標版本號，建立動態過濾與重排管線。
3. **整合凍結代理式 LLM**：選定單一前沿 LLM（不進行微調），透過檢索增強方式為其規劃器（Planner）、重構器（Refactorer）與除錯器（Debugger）注入結構化上下文與明確執行指令（何時套用、如何套用、範例）。
4. **建立編譯成本回饋迴路**：在代理迴路中實際呼叫 Lean 編譯器測量重構前後的編譯時間，將真實訊號回傳至多目標控制器，避免僅以 Token 長度作為代理指標。
5. **目標版本驗證與漸進部署**：在特定 Lean/Mathlib 工具鏈上進行端到端驗證，確認重構後證明可通過型別檢查且編譯成本確實下降。先於 CI 管線或編輯器中以「建議模式」運行，維護者確認後再轉為自動化提交。

### 潛在風險與注意事項

- **函式庫版本快速迭代導致策略過時**：Lean/Mathlib 每週發布可能使策略中的過時策略或已移除 API 失效。緩解方式為建立策略庫的定期重新標註（re-profiling）機制，並在檢索時嚴格過濾與目標版本相容的策略。
- **多目標權衡難以預設**：縮短證明可能呼叫較繁重的策略而膨脹編譯成本。切勿在推論階段固定單一目標權重，應提供使用者可調的滑桿或組態檔，並以帕雷托前沿（Pareto frontier）呈現選項。
- **檢索品質決定上限**：若檢索系統未能召回適用於當前證明結構的策略，凍結 LLM 仍可能產生普遍幻覺。需確保目標證明的依賴註解完整，以強化語義 grounding。
- **編譯成本量測開銷**：批次測量編譯時間可能成為瓶頸。建議採用增量編譯快取與統計抽樣，而非每次重構都執行全量乾淨編譯。
- **研究級程式碼的上下文規模**：研究型程式碼庫的跨檔案依賴遠比競賽題複雜，代理的上下文視窗可能不足。應優先檢索並注入相關外部與內部引理定義，而非僅餵入待重構的單一證明區塊。

### 與其他技術的整合建議

- **CI/CD 管線（GitHub Actions / GitLab CI）**：將 Lean Refactor 作為提交前檢查或夜間批次作業，自動產生重構建議 PR。整合版本過濾檢索，使不同分支可綁定各自目標 Lean 版本。
- **編輯器外掛（VS Code Lean 擴充）**：透過 LSP 或自訂指令，讓使用者在編輯器中選取證明區塊，即時呼叫代理框架取得多目標重構建議，並預覽長度與預估編譯成本變化。
- **現有 LLM 自動證明器（如 ReProver、Goedel-Prover）**：作為後處理層接在證明生成管線之後。自動證明器負責「產生正確證明」，Lean Refactor 負責「精煉為可維護、低成本的證明」，形成互補。
- **向量資料庫與 MLOps 工具**：使用 Milvus、Pinecone 或 Weaviate 託管策略庫，並透過 MLflow 或自訂儀表板追蹤各策略在不同 Lean 版本上的實際編譯成本降低率，持續更新後設資料。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦於論文的圖一與圖四，理解 Lean Refactor 作為「多目標、版本穩健的證明壓縮工具」的核心定位。無需深入代理迴路的技術細節，但應認識到 Lean 證明除了「正確」還需要「好維護」，並熟悉 proof length、compilation cost 與 version compatibility 三個基本維度。
- **AI 工程師**：請重點閱讀第三節 Methods 與演算法虛擬碼，特別是「凍結 LLM + 檢索增強」的架構如何規避重複微調。關注策略庫的後設資料設計（版本標註、編譯成本預期）與多目標重排管線的實作細節，這是將論文轉化為可部署系統的關鍵。
- **研究人員**：建議深入探討第二節對 Lean 重構本質挑戰的分析，以及實驗中版本過濾檢索與零樣本版本遷移的結果。論文釋出的 200K 長短證明配對與 9K 策略可作為後續形式化數學、程式碼重構或多目標強化學習研究的基礎資源。
- **產品經理**：請將閱讀重心放在第一節的動機與貢獻聲明，以及實驗數據（70% 競賽壓縮率、60% 編譯時間縮減、支援 Gemini/Claude/GPT）。評估導入時，請注意本框架「隨插即用、無需微調」的特性可大幅降低模型頻繁更替的維運成本，但需預留策略庫持續維護與版本標註的人力。
