## ⚡ TL;DR

現有多代理系統以靜態分割組織計算，協調量隨資訊空間擴大而機械增長，與查詢實際需求脫節。
本文提出ANTMAN框架，以可修訂需求圖追蹤未解決需求與證據，作為執行期協調的控制狀態。
實驗顯示，16倍資訊空間增長下ANTMAN協調僅增1.23倍，遠優於基線15倍以上，並維持答案品質。

## 摘要翻譯

資訊搜尋代理（Information-Seeking Agent）日益在規模過大而無法窮盡處理的資訊空間（Information Space）中運作。然而許多多代理系統（Multi-Agent System）以可用空間的靜態分割（Static Partition）為核心組織計算，導致協調量隨資訊的切分方式而非查詢尚未滿足的需求成長。我們提出 ANTMAN，一個自適應協調框架（Adaptive Coordination Framework），將演進中的未解決資訊需求（Unresolved Requirement）視為執行期協調（Runtime Coordination）的單位。ANTMAN 維護一個可修訂的需求圖（Need Graph），追蹤未解決需求、累積證據（Accumulated Evidence）、先前嘗試（Prior Attempt）與搜尋進度（Search Progress），並利用此狀態在發現新證據時控制工作代理選擇（Worker Selection）、路由（Routing）與任務層級恢復（Task-Local Recovery）。透過將協調策略（Coordination Policy）與特定底層搜尋介面（Substrate-Specific Search Interface）分離，同一個需求條件式機制（Need-Conditioned Mechanism）可跨不同資訊空間運作。跨多文件問答（Multi-Document Question Answering）、受控的長上下文擴展（Long-Context Scaling），以及真實的結構化導航（Structured Navigation）等實驗顯示，ANTMAN 在各種設定下皆有效，包括將執行委派給規模顯著較小的工作代理模型（Smaller Worker Model）時。在可搜尋的上下文增加 16 倍的情況下，ANTMAN 的主動協調量（Active Coordination）僅增加 1.23 倍，相較之下分割驅動基線（Partition-Driven Baseline）則增加超過 15 倍，同時維持強健的答案品質（Answer Quality）。

### 核心貢獻（3～5點）
- 提出以「未解決資訊需求」為執行期協調單位的新範式，取代傳統以靜態分割為核心的設計，使協調量隨查詢需求而非資訊切分方式成長。
- 設計可修訂的需求圖（Need Graph），統一追蹤未解決需求、累積證據、先前嘗試與搜尋進度，作為驅動工作代理選擇、路由與任務層級恢復的可修訂狀態結構。
- 將協調策略與特定底層搜尋介面解耦，使同一需求條件式機制可跨異質資訊空間通用，提升框架的可移植性。
- 實證在 16 倍可搜尋上下文擴增下，ANTMAN 的主動協調量僅增 1.23 倍，相較分割驅動基線超過 15 倍的增幅，展現極佳的協調可擴展性。
- 驗證即使將執行委派給規模顯著較小的工作代理模型，ANTMAN 仍能在多文件問答、長上下文擴展與結構化導航等設定下維持強健的答案品質。

### 適合對象
從事多代理系統（Multi-Agent System）、長上下文理解、資訊檢索與問答系統研究的學者與工程師；以及對大型語言模型推論效率、協調機制設計與異質資訊空間導航策略感興趣的實務研究者。

## 深度分析

#### 方法論解析

ANTMAN 的核心方法論突破在於將多代理協調（multi-agent coordination）的組織單位從「輸入空間的靜態分割（static partition）」轉變為「動態演化的未解決資訊需求（unresolved information need）」。這個設計選擇具有深層的理論基礎，源自 Bates (1989) 對資訊搜尋行為的經典觀察：搜尋過程中新發現的證據會反過來改變搜尋者對問題的理解，並重新導引搜尋方向本身。

**Need Graph（需求圖）作為執行期控制狀態**

Need Graph 是整個框架的中樞資料結構，它是一個可修訂（revisable）的執行期狀態（runtime state），追蹤四類資訊：(1) 未解決需求（unresolved requirements）——目前尚未被滿足的資訊需求清單；(2) 累積證據（accumulated evidence）——已收集到的支援或反駁假設的資訊片段；(3) 先前嘗試（prior attempts）——過去的搜尋或推理嘗試記錄；(4) 搜尋進度（search progress）——整體搜尋過程的進展狀態。這個設計的關鍵在於 Need Graph 不是靜態的查詢分解結果，而是一個隨證據累積而持續更新的動態結構。當新證據到達時，圖中的需求可以被「解決（resolve）」、「精煉（refine）」或「新引入（introduce）」，從而重新導引後續的搜尋方向。

**需求條件式協調機制（Need-Conditioned Mechanism）**

ANTMAN 的協調策略（coordination policy）以當前的 Need Graph 狀態為條件，動態決定三件事：(1) 哪些需求應該被繼續追求；(2) 哪些工作代理（worker agent）應該被啟用；(3) 任務如何被路由（routing）到合適的代理或子空間。這種設計使得代理的啟動數量不再由資訊空間的分割數量決定，而是由查詢實際尚未滿足的需求決定。當資訊需求保持固定而資訊空間擴大時，ANTMAN 不會機械式地增加代理數量。

**任務層級恢復（Task-Local Recovery）**

當搜尋進展停滯時，ANTMAN 啟動任務層級的恢復機制，透過三種方式介入：(1) 重新框架化（reframing）未解決的需求；(2) 重新路由（rerouting）需求到不同的搜尋路徑；(3) 回退（fallback）到替代的解析路徑。這種恢復是在單一任務層級進行的，而非全域性的重新規劃，因此成本可控。

**協調策略與底層介面的分離**

ANTMAN 將協調策略與特定底層搜尋介面（substrate-specific search interface）解耦，使得同一套需求條件式協調機制可以在不同的資訊空間上運作——無論是扁平長上下文（flat long-context）、多文件集合（multi-document collection），還是結構化資料庫（structured repository）。這個抽象層次使得框架具有跨領域的可遷移性。

#### 實驗數據解讀

**核心效率指標：協調成長量解耦**

Figure 1 呈現了本文最具說服力的實驗結果。在資訊空間大小（information-space size）從 32K 增長到 512K（即 16 倍增長）的條件下，ANTMAN 的主動協調量（active coordination）僅增長 1.23 倍，而 LongAgent 增長 15.29 倍、CoA 增長 15.33 倍。對應的模型呼叫次數（model calls）方面，ANTMAN 從 22.83 增長到 33.10（1.21 倍），而 LongAgent 從 73.10 增長到 292.50（12.81 倍）。推論成本（inference cost）方面，ANTMAN 從 $0.077 增長到 $0.533（6.90 倍），而 LongAgent 從 $0.355 增長到 $1.397（14.22 倍）。值得注意的是，ANTMAN 在 512K 時僅使用 3.17 個工作代理，而 LongAgent 需要 290.50 個成員代理（member agent），差距接近兩個數量級。

**跨基準測試的答案品質**

在三個結構化導航（structured navigation）基準上，ANTMAN 優於最強的非基準專用基線：RepoProbe 提升 15.3%、SWE-QA-Pro 提升 18.4%、GAIA 提升 27.9%。這些結果顯示 Need Graph 不僅降低了協調成本，也提升了答案品質（answer quality），因為動態需求追蹤比靜態分割更能適應真實資訊需求的演變。

**小型工作代理的可遷移性**

當所有非協調器（orchestrator）元件改用 Qwen3-8B 這類較小的工作代理模型（smaller worker model）時，ANTMAN-H 保留了完整 ANTMAN 效能的 89.2%（RepoProbe）、93.5%（SWE-QA-Pro）和 98.3%（GAIA）。這個結果具有重要的實務意涵：Need Graph 的協調抽象使得框架對工作代理的容量要求降低，因為大部分推理負擔由協調器承擔，工作代理只需執行局部搜尋。

**證據位置敏感度的改善**

在 Early、Middle、Late 三種證據放置位置下，ANTMAN 的中間位置差距（middle-position gap）僅為 +0.015，而直接全上下文推論（direct full-context inference）為 -0.181。這意味著 ANTMAN 的選擇性協調機制大幅降低了對證據在上下文中位置的敏感性，這是長上下文模型（long-context model）的已知弱點。

**消融實驗的意涵**

將 Need Graph 替換為無圖的自適應重新規劃（graph-free adaptive replanning）會導致效能下降 23.82%（512K）和 16.67%（GAIA），證明 Need Graph 作為顯式狀態的價值超越了通用的自適應協調。這暗示 Need Graph 的結構化表示捕捉了某些單純的重新規劃無法表達的資訊——特別是需求的依賴關係、證據與需求的對應、以及嘗試歷史的累積。

#### 與現有研究的比較

Table 1 系統性地將 ANTMAN 與現有方法在六個維度上進行比較：大規模/結構化資訊空間處理、自適應/迭代資訊存取、多代理協作、顯式演化的需求/差距狀態、需求驅動的協調範圍、空間解耦的協調。

**與基於分割的多代理方法的比較**

LongAgent 和 CoA 是最直接的對照組。兩者都採用分割驅動（partition-driven）的設計：將輸入切分為固定大小的區塊並指派給各成員代理。這種設計的問題在於代理數量與分割數量耦合，而非與查詢需求耦合。ANTMAN 的優勢在於打破了這個耦合，使得協調量可以獨立於資訊空間大小進行調控。

**與自適應資訊搜尋方法的比較**

DPR、ChainRAG、ReAct、DRAGIN、KiRAG、SelfRACG、S2G-RAG 等方法雖然支援自適應/迭代資訊存取，但大多缺乏多代理協作（multi-agent collaboration）和顯式的需求狀態追蹤。S2G-RAG 是其中最接近的，具備顯式的需求/差距狀態，但其需求驅動的協調僅限於下一步檢索，而非整體的代理啟用範圍。ANTMAN 的獨特之處在於將需求狀態提升為控制整個代理群啟用與路由的核心。

**與其他多代理導航方法的比較**

OWL、C-3PO、MAIN-RAG、DyLAN 等多代理方法在協作機制上各有特點，但都缺乏完整的顯式需求狀態追蹤或空間解耦的協調。ANTMAN 是 Table 1 中唯一在所有六個維度上都具備完整能力（✓）的方法。

**限制與未涵蓋的面向**

ANTMAN 的方法論假設 Need Graph 能夠被有效建構與維護，這在某些場景下可能具有挑戰性：(1) 當資訊需求極為模糊或高度開放式時，需求的識別與追蹤本身可能成為瓶頸；(2) 協調器的設計複雜度可能隨著需求類型的多樣化而增加；(3) 雖然框架聲稱與底層介面解耦，但實際的跨領域遷移仍需要針對不同資訊空間設計對應的證據收集介面。此外，論文未深入討論 Need Graph 的規模管理問題——當未解決需求數量極大時，圖結構本身的維護成本是否會成為新的瓶頸。

#### 可重現性評估

**程式碼與模型權重**

本文為 arXiv 預印本（arXiv:2609.33326v1），截至目前處於審查中狀態。論文未明確聲明程式碼是否開源，也未提供模型權重（model weights）的釋出資訊。考慮到實驗涉及多個基準測試（RepoProbe、SWE-QA-Pro、GAIA）和多種基線方法（LongAgent、CoA、OWL 等）的比較，完整的可重現性需要作者釋出：(1) ANTMAN 的核心實作；(2) Need Graph 的建構與更新邏輯；(3) 協調器的提示工程（prompt engineering）細節；(4) 與各基線方法的公平比較配置。

**資料集可用性**

RepoProbe、SWE-QA-Pro 和 GAIA 應為公開或可取得的基準測試。GAIA 是已知的多代理與推理基準，RepoProbe 和 SWE-QA-Pro 從命名推測與程式碼倉庫導航相關，可能源自既有研究。實驗中使用的多文件問答（multi-document QA）資料集未在提供的文本中明確說明，需要查閱完整論文以確認。

**實驗配置的透明度**

Figure 1 提供了具體的數值（代理數量、呼叫次數、成本），這增強了結果的可驗證性。但完整的可重現性仍需以下資訊：(1) 協調器使用的具體模型及其版本；(2) 工作代理的模型配置；(3) 上下文視窗（context window）的處理方式；(4) 評估指標的計算細節。論文中提到的「Qwen3-8B」作為較小工作代理的選擇暗示了模型家族的具體性，這有助於部分重現。

**與現有實作的整合性**

ANTMAN 聲稱與底層介面解耦，這在理論上允許與現有的檢索系統、程式碼分析工具、網頁導航框架整合。但實際整合的工程細節未在論文中詳述，這對希望將 ANTMAN 應用於自訂資訊空間的研究者構成障礙。

#### 未來研究方向

**理論層面的深化**

ANTMAN 提出的「需求驅動協調」概念值得進一步的理論形式化。未來研究可以探索：(1) Need Graph 的計算複雜度上界，特別是在最壞情況下需求數量的增長行為；(2) 協調量與資訊空間大小的解耦條件——在什麼樣的問題結構下，這種解耦是可以保證的；(3) 與資訊理論（information theory）的連結，將「未解決需求」形式化為殘餘資訊量（residual information）的度量。

**跨領域應用擴展**

雖然論文展示了在多文件問答、長上下文、結構化導航三個場景的有效性，但 ANTMAN 的設計原則可以進一步應用於：(1) 科學文獻綜述（scientific literature review），其中資訊需求隨證據累積而高度演化；(2) 法律案件研究，需要在大量文件中追蹤多條論證線索；(3) 醫療診斷支援，其中資訊需求隨檢驗結果動態調整；(4) 程式碼除錯與重構，跨多個檔案與版本的依賴追蹤。

**Need Graph 的學習化**

目前的 Need Graph 似乎依賴於預定義的規則或提示工程來建構與更新。未來可以探索：(1) 將 Need Graph 的建構本身作為一個學習問題，使用強化學習（reinforcement learning）來優化需求的識別與追蹤策略；(2) 從人類資訊搜尋行為的大規模資料中學習需求演化的模式；(3) 將 Need Graph 與知識圖譜（knowledge graph）結合，利用結構化先驗知識來指導需求的分解與精煉。

**混合協調架構**

ANTMAN 的純需求驅動設計在某些場景下可能不是最優的。未來可以探索：(1) 需求驅動與分割驅動的混合架構，在某些子任務上使用靜態分割以利用其簡單性；(2) 分層協調（hierarchical coordination），在高層使用需求驅動、在低層使用分割驅動；(3) 根據問題特性動態選擇協調策略的元學習（meta-learning）機制。

**效率與可擴展性的進一步優化**

雖然 ANTMAN 已經展示了顯著的效率提升，但仍有優化空間：(1) Need Graph 的增量更新機制，避免每輪重新建構；(2) 工作代理的快取與重用，特別是在多輪搜尋中；(3) 協調器的輕量化，使得小型模型也能承擔協調角色；(4) 平行化策略的優化，使得多個需求的追蹤可以並行進行而不產生冗餘。

**評估方法的標準化**

目前缺乏統一的基準來評估「需求驅動協調」的有效性。未來可以：(1) 設計專門的基準測試，衡量系統在需求演化場景下的表現；(2) 開發標準化的指標來量化「協調效率」，即每單位協調量所獲得的資訊增益；(3) 建立跨領域的評估協議，使得不同資訊空間下的結果具有可比性。

## 論文問答

**Q1：ANTMAN 試圖解決的核心問題是什麼？**
A：ANTMAN 試圖解決的核心問題是「資訊空間規模」與「實際協調需求」之間的錯配。隨著現代資訊搜尋代理面對的資訊空間日益龐大且異質，傳統多代理系統以靜態分割為基礎的設計會讓代理數量隨資訊空間的切分數量線性成長，而非隨查詢真正未解決的需求成長。這種耦合使得在大型資訊空間中，協調成本會機械性地膨脹，卻未必帶來對應的答案品質提升。ANTMAN 因此主張應以「演化中的未解決需求」取代「輸入分割」作為執行期協調的單位。

**Q2：為何基於靜態分割的多代理方法（如 LongAgent、CoA）會在大型資訊空間中失效？**
A：基於靜態分割的方法將輸入切分為固定大小的區塊並指派給各成員代理，這使得代理數量直接綁定於資訊空間的分割數量，而非查詢的實際需求。當資訊空間擴大 16 倍時，LongAgent 的主動協調量成長 15.29 倍、CoA 成長 15.33 倍，遠超過實際查詢所需的協調量。這種設計不僅造成高昂的模型呼叫次數與推論成本，也暴露了「資訊空間組織方式」與「查詢需求」之間的根本錯配。換言之，當底層資訊需求保持固定時，擴大可搜尋上下文本身不應要求代理數量等比例增加。

**Q3：為什麼資訊需求的動態特性對多代理協調如此重要？**
A：經典資訊搜尋研究（如 Bates, 1989）早已指出，搜尋並非單純對固定查詢進行逐步精煉的過程；新遇到的證據會改變搜尋者對問題的理解，並重新導引搜尋方向。對資訊搜尋代理而言，新需求可能只在取得中間證據後才浮現，先前識別的需求也可能被解決或需要修正，而無生產力的搜尋方向則必須被放棄。因此，有效的協調不能僅依賴對查詢的初始分解，而需要一個明確、可修訂的表示方式，來記錄「隨證據累積仍尚未解決的事項」。這正是 ANTMAN 將動態需求狀態提升為一級協調單位的理論基礎。

**Q4：什麼是「需求圖（Need Graph）」，它在 ANTMAN 中扮演什麼角色？**
A：需求圖是 ANTMAN 維護的一個可修訂的執行期控制狀態，用以追蹤未解決需求、累積證據、先前嘗試與搜尋進度。它並非靜態的任務分解樹，而是會隨新證據浮現而持續演化的狀態結構：需求可能被解決、被精煉，或被新增。當前的需求圖決定哪些需求應被繼續追蹤、哪些工作代理應被啟用，並指導路由與任務層級恢復的進行。當進度停滯時，ANTMAN 會透過重新框定或重新路由未解決需求，或退回到替代的解決路徑，來執行任務層級恢復。

**Q5：ANTMAN 相較於既有方法最關鍵的創新是什麼？**
A：ANTMAN 最關鍵的創新在於將「未解決的資訊需求」而非「輸入分割」確立為執行期協調的單位，從而使協調量與資訊空間大小解耦。透過以需求圖作為顯式的執行期狀態，ANTAN 讓代理啟用、路由與恢復皆由尚未被滿足的需求所驅動，而非由資訊空間如何被切分所決定。這項設計帶來一個可量化的效益：在資訊空間擴大 16 倍時，ANTMAN 的主動協調量僅成長 1.23 倍，而分割驅動基線則成長超過 15 倍。換言之，ANTMAN 證明了「需求驅動的協調」能以近乎固定的協調成本處理大幅擴張的資訊空間。

**Q6：ANTMAN 如何實現「與底層資訊空間無關」的協調機制？**
A：ANTMAN 透過將協調策略與特定底層搜尋介面分離，來達成跨資訊空間的通用性。協調策略本身只依賴需求圖的狀態——未解決需求、累積證據、先前嘗試與搜尋進度——而不直接綁定於任何特定的檢索或搜尋介面。這種抽象使得同一套以需求為條件的協調機制，能夠在多文件問答的扁平長上下文、儲存庫程式碼導航（RepoProbe、SWE-QA-Pro）以及 GAIA 等異質結構化導航任務中運作，而無需為每種資訊空間重新設計協調邏輯。這也是為什麼 ANTMAN 能在三個互補的實驗設定中同時維持有效性的關鍵原因。

**Q7：ANTMAN 在哪些基準上進行評估？為何選擇這些基準？**
A：ANTMAN 在三類互補的設定下進行評估：多文件問答（用以測試需求驅動協調在標準資訊搜尋任務上能否維持答案品質）、受控的資訊空間擴展（從 32K 到 512K，用以測試主動協調是否能與無關的資訊空間成長解耦），以及真實的結構化導航（RepoProbe、SWE-QA-Pro、GAIA，用以測試同一協調抽象能否超越扁平的長上下文輸入）。這三類設定分別檢驗 ANTMAN 設計的不同面向：答案品質、擴展性與跨底層遷移能力。透過同時覆蓋「品質」、「規模」與「結構多樣性」三個維度，評估能夠驗證 ANTMAN 的設計選擇在各種壓力下是否仍具穩健性。

**Q8：ANTMAN 的關鍵量化結果為何？**
A：ANTMAN 的關鍵量化結果可從三個面向來看。第一，在擴展性上，當資訊空間擴大 16 倍時，ANTMAN 的主動協調量僅成長 1.23 倍、模型呼叫次數成長 1.21 倍、推論成本成長 6.90 倍，而 LongAgent 與 CoA 的對應數字皆超過 12 至 16 倍。第二，在答案品質上，ANTMAN 在 RepoProbe、SWE-QA-Pro 與 GAIA 上分別超越最強的非基準專用基線 15.3%、18.4% 與 27.9%。第三，在成本效益上，即便將所有非協調者元件委派給 Qwen3-8B 等較小的工作代理模型，ANTMAN-H 仍能保留 ANTMAN 完整效能的 89.2%、93.5% 與 98.3%，證明了顯著的成本下降空間。

**Q9：ANTMAN 的消融研究揭示了哪些關鍵設計的必要性？**
A：ANTMAN 的消融研究顯示，以無圖的自適應重規劃取代顯式的需求圖，會在 512K 設定下造成 23.82% 的效能下降，並在 GAIA 上造成 16.67% 的下降。這項結果證明了 ANTMAN 的效益並非來自泛用的「自適應協調」即可，而是必須仰賴一個明確、可修訂的「需求／缺口狀態」來驅動協調。此外，ANTMAN 在 Early、Middle、Late 三種證據位置擺放下，中段位置的效能落差僅 +0.015，而直接全上下文推論則為 −0.181，顯示選擇性協調能顯著降低對證據位置的敏感性。這些消融結果共同支持了「顯式需求狀態」與「選擇性協調」兩項核心設計的必要性。

**Q10：ANTMAN 在哪些實際應用場景中能帶來最大價值？**
A：ANTMAN 在需要於大型、異質且結構化資訊空間中進行多步推理的場景中價值最高，例如企業級多文件問答、大規模程式碼儲存庫導航、科學文獻綜述，以及客服系統在龐大知識庫中查找並整合證據。這些場景的共同特徵是：可搜尋的資訊量遠大於單一查詢真正需要動用的證據量，且證據可能散落於不同位置與結構中。ANTMAN 的需求驅動協調使系統能聚焦於尚未解決的部分，而非隨資訊空間擴大而線性膨脹，因此在成本與延遲敏感的生產環境中尤其具有吸引力。

**Q11：從產品化的角度，ANTMAN 帶來哪些重要的設計取捨？**
A：從產品化角度，ANTMAN 帶來三項關鍵取捨。第一是成本可預測性：主動協調量與資訊空間大小近乎解耦，使得推論成本在面對大型上下文時仍能維持在合理範圍，這對需要 SLA 保障的產品至關重要。第二是模型選用彈性：實驗顯示即便將執行委派給 8B 等較小的工作代理模型，ANTMAN-H 仍能保留絕大部分效能，這意味著產品可在品質與成本之間靈活調配。第三是對證據位置的穩健性：ANTMAN 對證據在上下文中的位置不敏感，這降低了系統在面對真實世界中資訊分布不均時的失效風險。

**Q12：ANTMAN 對多代理系統研究領域可能產生什麼更廣泛的影響？**
A：ANTMAN 對多代理系統研究領域的影響在於典範轉移：它挑戰了「以輸入分割為核心」的傳統多代理設計，主張應以「未解決需求」作為協調的原子單位。這種觀點與經典資訊搜尋理論（Bates, 1989）相互呼應，將搜尋視為一個動態、需求演化的過程，而非一次性的查詢分解。從更廣的視角來看，ANTMAN 示範了如何透過顯式的執行期狀態來達成「規模無關的協調」，這對未來設計可擴展、可解釋且成本可控的多代理系統具有方法論上的啟發。它也為「空間解耦協調」這一新興設計原則提供了具體的實證基礎。

**Q13：ANTMAN 目前存在哪些已知的限制？**
A：ANTMAN 的已知限制可從幾個面向來看。首先，雖然實驗涵蓋多文件問答、長上下文擴展與結構化導航三類設定，但這些基準仍屬特定範疇，對於其他類型的資訊空間（例如多模態、串流式或高度動態更新的資料源）的適用性尚未被驗證。其次，ANTMAN 的效能高度依賴需求圖的品質，而需求圖的建構與維護本身需要由協調者模型承擔，這對協調者模型的能力提出了額外要求。最後，論文中對「任務層級恢復」機制的觸發條件與收斂行為著墨較少，這使得在高度複雜或對抗性的搜尋環境中，恢復機制能否持續有效仍待進一步檢驗。

**Q14：ANTMAN 在哪些情境下可能會失效？**
A：ANTMAN 可能在以下幾種情境下失效。第一，當初始需求本身被錯誤或模糊地定義時，需求圖可能會繼承這些錯誤並在後續搜尋中持續誤導代理，因為整個協調流程都圍繞著這些需求展開。第二，當資訊空間中的相關證據極度分散、需要大量跨子空間整合時，需求圖可能會膨脹到難以管理的規模，反而使協調成本上升。第三，當底層工作代理模型的能力不足以執行被指派的子任務時，即便需求圖的規劃正確，實際執行仍可能失敗——雖然 ANTMAN-H 在 8B 模型上表現良好，但在更極端的模型縮減情境下，品質下降幅度仍可能超出可接受範圍。

**Q15：ANTMAN 開啟了哪些值得探索的未來研究方向？**
A：ANTMAN 開啟了多個值得探索的未來研究方向。第一，可以研究如何讓需求圖本身可被學習或自動精煉，而非完全依賴協調者模型的手工維護，以降低對協調者能力的依賴。第二，可以將需求驅動的協調原則擴展至多模態資訊空間，例如同時涵蓋文字、影像與表格的異質搜尋場景。第三，可以從理論上分析「需求驅動協調」的擴展性上界與下界，理解在何種資訊結構與查詢特性下，協調量能夠真正與資訊空間大小解耦。第四，則可探索 ANTMAN 與人類在環（human-in-the-loop）互動的結合，讓使用者能直接編輯需求圖，進一步提升系統的可解釋性與可控性。

## 實務應用指南

### 適用場景

1. **企業知識庫深度問答**：在跨部門、跨系統的大型企業知識庫（例如 Confluence、Notion、SharePoint 加上內部 Wiki）部署 ANTMAN，讓使用者以自然語言提問時，系統能動態追蹤尚未被滿足的子需求（例如「先確認 Q3 財報數字，再交叉比對 Q4 預測」），而非將整個知識庫靜態切塊後丟給數十個代理。

2. **程式碼倉庫探索與除錯**：在 GitHub Enterprise、GitLab 等大型 monorepo 中，讓 ANTMAN 擔任「需求驅動的程式碼導航員」。當開發者描述一個 bug 或 feature 需求時，Need Graph 會隨著證據（檔案內容、git log、測試結果）累積而動態調整，避免 LongAgent 式設計在 512K 規模下產生 290 個成員代理的災難。

3. **法律與合規文件審查**：處理數萬頁的合約、判例集、法規文本時，ANTMAN 可在「找出所有與資料保護相關的條款」「比對 GDPR 與本地法差異」等子需求上動態調度，避免一次性把所有文件塞進單一代理的上下文視窗。

4. **多模態研究助理**：在 arXiv、PubMed、內部研究報告組成的異質資訊空間中，ANTMAN 的「需求條件式機制」可跨文本、表格、圖表三種底層介面運作，同一套 Need Graph 控制邏輯無需為每種資料型態重寫。

5. **客戶支援與工單分派**：在大型客服系統中，ANTMAN 可作為「未解決需求追蹤器」，當客戶描述模糊問題時，系統動態判斷還缺哪些資訊（訂單編號、錯誤截圖、重現步驟），並選擇合適的工作代理（訂單查詢代理、知識庫代理、技術診斷代理）接力處理，而非預先為每個子領域各開一個代理。

### 實作前置條件

**資料面**
- 一個或多個「大型資訊空間」來源：文件集合、程式碼倉庫、結構化資料庫、API 端點集合。
- 每個資訊空間需具備可被抽象化的「搜尋介面」（例如 BM25、向量檢索、SQL 查詢、檔案系統遍歷、Git 操作），ANTMAN 的協調策略需與這些介面解耦。
- 評估用基準資料集：至少需要類似 GAIA、RepoProbe、SWE-QA-Pro 的子集，用以驗證答案品質與協調成長量。

**算力面**
- 一個足夠強的「協調者模型」（orchestrator），負責維護 Need Graph、決定 worker 啟用與路由；論文中使用大型模型作為協調者。
- 多個可被委派的工作代理模型；論文中實驗顯示 8B 等級的 Qwen3-8B 已可勝任 worker，關鍵在於協調者能否正確下指令。
- 預期推論成本隨資訊空間成長應接近線性以下，而非 LongAgent 的超線性膨脹（論文中 16× 空間僅帶來 1.23× 主動協調量）。

**技能面**
- 熟悉 LLM agent 框架（LangGraph、AutoGen、CrewAI 或自製 orchestrator-worker 架構）。
- 具備圖狀態管理（graph state management）能力，能設計可新增、解決、精煉節點的動態資料結構。
- 理解任務分解與子任務依賴關係，能將「未解決需求」形式化為可被 LLM 操作的結構化欄位。
- 具備評估管線設計能力，能同時量測「答案品質」與「協調效率」兩個維度。

### 實作步驟建議

**步驟一：定義 Need Graph 的資料結構**
從論文的描述出發，設計一個包含以下欄位的節點結構：未解決需求描述、累積證據列表、先前嘗試紀錄、搜尋進度狀態（pending / in-progress / resolved / abandoned）。Need Graph 本身應是可修訂的（revisable），允許新增節點、合併節點、標記節點為已解決。

**步驟二：實作協調者（Orchestrator）迴圈**
協調者的核心是一個 while-not-resolved 迴圈：讀取當前 Need Graph → 選擇要啟用的 worker → 將子需求與可用搜尋介面描述傳遞給 worker → 接收證據 → 更新 Need Graph。論文中強調「Need Graph 決定哪些需求應被追蹤、哪些 worker 應被啟用」，這是控制流的中心。

**步驟三：抽象化搜尋介面層**
建立一個 substrate adapter 層，將不同資訊空間的搜尋操作（檢索、SQL、檔案讀取、API 呼叫）包裝成統一的介面。ANTMAN 的關鍵設計選擇是「協調策略與特定底層介面解耦」，這讓同一套 Need Graph 控制邏輯可在多文件 QA、長上下文、結構化導航三種場景間移植。

**步驟四：實作任務層級恢復機制**
當某個 worker 回報「無進展」或 Need Graph 偵測到停滯時，觸發 task-local recovery：重新框定需求（reframing）、改路由（rerouting）、或回退到替代解析路徑（fallback）。這是 ANTMAN 區別於「純粹 graph-free 自適應重規劃」的關鍵，論文中報告移除此機制會在 512K 規模下損失 23.82% 效能。

**步驟五：建立評估管線**
同時量測兩個指標：(1) 答案品質（與基準答案比對），(2) 協調效率（active coordination、模型呼叫次數、推論成本）。論文的關鍵論點是「在 16× 資訊空間成長下，ANTMAN 的主動協調量僅成長 1.23×，而 LongAgent 成長 15.29×」，這個比例必須在自家資料上重現驗證。

**步驟六：迭代 worker 模型規模**
先以最強模型作為 worker 驗證正確性，再逐步換成 8B 等級模型。論文中 ANTMAN-H（用 Qwen3-8B 作為所有非協調者元件）在 RepoProbe、SWE-QA-Pro、GAIA 上分別保留 89.2%、93.5%、98.3% 的完整效能，這個比例可作為成本最佳化的目標線。

**步驟七：上線監控與 A/B 測試**
在生產環境中監控 Need Graph 的節點生命週期、worker 啟用頻率、恢復機制觸發率。與既有的單一代理或靜態分割方案做 A/B 測試，特別關注「證據位置敏感度」（早期、中期、晚期放置的差異），ANTMAN 在這項指標上僅有 +0.015 的中期位置差距，而直接全上下文推論為 −0.181。

### 潛在風險與注意事項

**風險一：Need Graph 膨脹失控**
若協調者未嚴格執行「解決」與「放棄」操作，Need Graph 可能無限增長，反而比靜態分割更耗資源。
**緩解**：設定節點數上限、定期 GC 已解決節點、對停滯節點強制標記 abandoned。

**風險二：協調者模型成為瓶頸**
所有 worker 啟用與路由都由協調者決定，若協調者模型不夠強，整體效能會被拖垮。
**緩解**：使用較大的模型作為協調者、較小的模型作為 worker（論文的 ANTMAN-H 模式）；為協調者設計專門的 prompt 與少量樣本。

**風險三：任務層級恢復機制設計不當**
恢復機制若過於激進，可能在已接近答案時重新框定需求，造成迴圈；若過於保守，則無法處理真正的死路。
**緩解**：設定恢復觸發條件（例如連續 N 次無新證據）、限制單一需求的恢復次數、記錄恢復歷史供日後分析。

**風險四：搜尋介面抽象過於粗糙**
若 substrate adapter 隱藏了底層空間的重要特性（例如程式碼倉庫的依賴關係），協調者可能下達無法執行的指令。
**緩解**：在 adapter 層保留「能力描述」與「限制說明」，讓協調者能據此判斷可行性。

**風險五：評估管線只量測答案品質而忽略協調成本**
若僅以答案正確性為指標，容易誤導團隊採用更複雜、更昂貴的方案。
**緩解**：將「每查詢推論成本」「主動協調量」列為一級指標，與品質指標並列。

**風險六：對小型資訊空間過度設計**
ANTMAN 的設計目標是「大型資訊空間」，在小型空間中，靜態分割或單一代理可能更簡單且足夠。
**緩解**：設定空間大小閾值，低於閾值時自動降級為簡單方案。

### 與其他技術的整合建議

**與 RAG 系統整合**
ANTMAN 可作為 RAG 的上層協調器：傳統 RAG 負責單次檢索與生成，ANTMAN 負責多輪、跨來源的資訊蒐集。論文中提及的 ChainRAG、KiRAG、S2G-RAG 等方法都具備部分「自適應資訊存取」能力，但缺乏明確的「演化中需求狀態」，可作為 ANTMAN 的單輪檢索後端。

**與程式碼代理整合**
在 SWE-bench 類任務中，ANTMAN 的 Need Graph 可與既有工具（如 Aider、Cursor、Claude Code 的工具呼叫層）對接：worker 代理呼叫檔案讀寫、grep、git 操作，ANTMAN 負責決定「下一步該探索哪個子需求」。論文中 RepoProbe 與 SWE-QA-Pro 的結果顯示此整合可行。

**與多代理框架整合**
ANTMAN 的 orchestrator-worker 模式可套用於 LangGraph（以 graph state 為中心）、AutoGen（以對話為中心）、CrewAI（以角色為中心）。關鍵是將 Need Graph 實作為框架的共享狀態物件，並讓協調者能讀寫該物件。

**與成本控制系統整合**
ANTMAN 的「主動協調量」指標可與雲端推論的成本監控系統對接，設定每查詢成本上限。當成本逼近上限時，協調者可主動收斂 Need Graph、跳過非關鍵子需求。

**與人類監督機制整合**
在敏感場景（法律、醫療、金融）中，可在 Need Graph 的關鍵節點插入「人類審核」閘門：當某個未解決需求涉及高風險判斷時，暫停 worker 啟用，等待人類輸入。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與第一節，理解「為什麼靜態分割會隨資訊空間膨脹」這個核心問題，再看 Figure 1 的視覺化對比（ANTMAN 的氣泡幾乎不變大，LongAgent 與 CoA 的氣泡暴增）。不必急著理解 Need Graph 的內部結構，先掌握「以未解決需求為單位，而非以輸入區塊為單位」這個設計哲學。

**給 AI 工程師**：直接跳到方法章節，仔細閱讀 Need Graph 的節點欄位定義、協調者迴圈的偽程式碼、以及任務層級恢復機制的觸發條件。特別注意論文中「移除 Need Graph 改用 graph-free 自適應重規劃會損失 23.82%」這個消融實驗，它證明了「明確的狀態表示」比「隱式的重規劃」更有效。實作時可先以 LangGraph 為原型，把 Need Graph 實作為 graph state。

**給研究者**：重點關注三個面向：(1) Need Graph 作為「執行期控制狀態」的理論定位，與經典資訊搜尋理論（Bates, 1989）的對應關係；(2) 跨底層移植性的實驗設計（多文件 QA、長上下文、結構化導航三種場景）；(3) 與較小 worker 模型（8B）協作時的效能保留率（89.2%–98.3%），這對未來「小模型當 worker、大模型當協調者」的分工研究有直接啟發。Table 1 的方法分類表也值得細讀，它清楚定位了 ANTMAN 在六個維度上的獨特組合。

**給產品經理**：把 ANTMAN 視為「讓 AI 助理處理大型資訊空間時不會隨資料量線性漲價」的工程方案。核心商業價值在於：當客戶的知識庫從 32K 成長到 512K 時，採用 ANTMAN 的成本僅成長約 7 倍，而採用 LongAgent 類方案的成本會成長 14 倍以上。對內可作為「為什麼我們的 AI 助理比競品便宜」的故事素材；對外可在客戶面對「資料越積越多怎麼辦」的疑慮時，提出明確的工程解方。
