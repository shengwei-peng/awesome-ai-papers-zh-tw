## 摘要翻譯

多步驟大型語言模型管線因檢索、推理與格式化步驟之間的交互作用而失效，因此僅提示最佳化可能忽略鏈式結構中的瓶頸。我們提出 FAPO（全自主提示最佳化），一個使 Claude Code 得以在標準化程式碼庫內最佳化大型語言模型管線的框架。FAPO 評估管線、檢視中間步驟、診斷故障、提出限定範圍變更，並反覆驗證變體以針對評分函數進行最佳化。它首先嘗試提示編輯，僅當提示最佳化顯得不足，且歸因識別出結構瓶頸時，才於限定範圍內變更鏈式結構。橫跨六項基準測試與三個任務模型，FAPO 在 18 項模型–基準測試比較中有 15 項勝過基準方法 GEPA。在 11 項模型–基準測試比較中，FAPO 以不重疊的平均值 ± 試驗標準差範圍勝出，且 FAPO-GEPA 平均增益為 +14.1 百分點。在提示優先搜尋升級為結構變更的六項 HoVer 與 IFBench 比較中，FAPO 六項全數勝出，平均增益達 +33.8 百分點。FAPO 亦提升資安任務的效能：在 CTIBench-RCM 這項資安 CVE 至 CWE 對應任務上，僅提示最佳化的 FAPO 在 GPT-5 上提升測試準確率 +4.0 百分點，在 Foundation-Sec-8B-Instruct 上提升 +7.1 百分點，在 Foundation-Sec-8B-Reasoning 上提升 +2.0 百分點。這些結果使 FAPO 成為通用型與資安導向任務皆適用的最先進管線最佳化技術。

### 核心貢獻（3～5點）
- 提出 FAPO 框架，使 Claude Code 能在標準化程式碼庫內全自主最佳化多步驟大型語言模型管線；透過評估、檢視中間步驟、診斷故障、提出限定範圍變更並反覆驗證變體，針對評分函數進行閉迴路最佳化。
- 設計「提示優先搜尋」策略：先嘗試提示編輯，僅當歸因識別出結構瓶頸且提示最佳化不足時，才於限定範圍內變更鏈式結構，有效解決單純提示最佳化無法觸及的結構瓶頸。
- 於六項基準測試與三個任務模型進行廣泛評估，在 18 項模型–基準測試比較中贏得 15 項，平均增益達 +14.1 百分點；在六項升級為結構變更的比較中平均增益更高達 +33.8 百分點，顯著優於基準方法 GEPA。
- 驗證 FAPO 在資安任務的成效：於 CTIBench-RCM 的 CVE 至 CWE 對應任務中，僅提示最佳化即顯著提升多個模型的測試準確率，確立其作為通用與資安導向任務皆適用的最先進管線最佳化技術。

### 適合對象
從事多步驟大型語言模型管線設計、自動化提示最佳化、AI 智慧體開發，以及關注資安威脅情報與漏洞分析應用的研究人員與工程師。

## 深度分析

#### 方法論解析

FAPO（Fully Autonomous Prompt Optimization，全自主提示最佳化）的核心假設是：多步驟大型語言模型管線（Multi-step LLM pipeline）的失效並非單一提示（Prompt）所能概括，而是檢索（Retrieval）、推理（Reasoning）、格式化（Formatting）等步驟交互作用後，錯誤經由下游元件（Downstream components）傳播所致。因此，傳統單輪提示調校（Single-turn prompt tuning）或僅針對最終輸出進行提示空間搜尋（Prompt space search）的做法，往往無法定位真正的結構瓶頸（Structural bottleneck）。

為此，FAPO 將管線視為可檢視管線（Inspectable pipeline），並以 Claude Code（Claude Code）作為驅動最佳化迴圈（Optimization loop）的智慧體（Agent），在標準化程式碼庫中執行以下五階段閉迴路搜尋（Closed-loop search）：

1. **任務工作空間初始化**：每個任務對應一個租戶工作空間（Tenant workspace），內含問題陳述（Problem statement）、評估準則（Evaluation criterion）、任務模型（Task model）設定、當前提示與允許變更範圍。租戶操作手冊（Tenant playbook）為最高層級政策文件，可覆寫 FAPO 本身的能力，確保防護欄（Guardrails）不被突破。
2. **執行與記錄**：共享評估引擎（Evaluation engine）透過 LangGraph（LangGraph）將管線表示為狀態圖（Stateful graph），執行訓練案例並記錄最終答案、評分函數（Score function）輸出，以及每個中間步驟（Intermediate steps）的輸入輸出與日誌。
3. **故障診斷與歸因（Attribution）**：證據報告將反覆出現的故障（Recurring failures）依照可能原因分群，例如缺少證據（Missing evidence）、不當棄權（Unsupported abstention）、答案冗長、輸出格式錯誤（Malformed output）或最終指令強度不足。此處的歸因機制是方法論的關鍵：不同於紅隊演練（Red-teaming）或越獄攻擊（Jailbreaking）文獻中常見的 Best-of-N（Best-of-N）策略——其目標是在固定查詢預算（Query budget）內找到至少一個成功的失效案例——FAPO 進行了目標轉移（Objective shift），旨在提升單一管線變體（Pipeline variant）在 N 個評估案例上的平均分數。這使得智慧體必須解釋反覆出現的故障，而非僅僅利用罕見的成功樣本。
4. **限定範圍變更（Scoped changes）**：Claude Code 首先嘗試提示編輯（Prompt edits）。只有在記錄的失效證據顯示提示最佳化不足以解決主導瓶頸，且租戶允許的範圍合約（Scope contract）明確授權時，才會進行結構變更（Structural changes），例如延長檢索鏈或引入確定性約束執行（Deterministic constraint enforcement）。
5. **安全審查與迭代**：獨立審查器檢查提案是否違反任務規則、是否導致資料洩漏或竄改評分器（Scorer）。僅當審查通過後，才會重新執行評估並進入下一輪。

在架構層面，FAPO 遵循四項設計原則：將共享測試器與任務分離；所有決策必須基於已記錄的證據；偏好最小有效變更；透過租戶隔離確保可擴展性與可重現性。這種「提示優先搜尋（Prompt-first search）、結構變更為後備」的漸進式策略，使 FAPO 能在不改變鏈式結構（Chain structure）的前提下先榨取提示層面的效能，並僅在必要時才承擔結構調整所帶來的複雜度與風險。

#### 實驗數據解讀

實驗橫跨六個基準測試（Benchmark）——HoVer（HoVer）、IFBench（IFBench）、LiveBench-Math（LiveBench-Math）、HotpotQA（HotpotQA）、Papillon（Papillon）、AIME（AIME）——與三個任務模型：GPT-4.1-mini（GPT-4.1-mini）、GPT-5.4-mini（GPT-5.4-mini）、Gemma3-12B（Gemma3-12B）。基線方法為 GEPA（GEPA），兩者從相同管線與初始提示出發。

整體而言，在 18 組模型–基準測試比較（Model-benchmark comparison）中，FAPO 贏得 15 組，平均增益（Mean gain）達 +14.1 百分點（Percentage points, pp）。其中有 11 組呈現不重疊的平均值 ± 試驗標準差範圍（Non-overlapping mean ± trial-standard-deviation ranges），代表統計上具顯著優勢。具體分項觀察如下：

* **結構變更的決定性影響**：在 HoVer 與 IFBench 這兩項需要多跳檢索與嚴格指令遵循的基準測試上，FAPO 的提示優先搜尋在發現未解決瓶頸後，升級為管線結構調整（如延長檢索鏈、加入確定性約束）。在這六組發生升級的比較中，FAPO 全數獲勝，平均增益高達 +33.8 pp（HoVer 從 GEPA 的 48.5% 提升至 83.8%；IFBench 從 48.5% 提升至 80.7%）。這顯示當任務本質涉及複雜證據鏈與格式約束時，僅調整提示無法克服結構瓶頸，而 FAPO 的歸因驅動結構變更恰好填補了這一缺口。
* **提示編輯的穩健性**：在僅允許提示編輯的比較中，FAPO 仍贏得 12 組中的 9 組，顯示其歸因導向的提示最佳化本身即優於 GEPA。
* **數學推理的邊界**：AIME 是唯一 GEPA 領先的基準測試（FAPO 落後 -3.0 pp）。這暗示對於需要深層數學推理的任務，管線結構或提示層面的調整可能觸及天花板，問題核心可能來自任務模型（Task model）本身的推理能力，而非管線設計。
* **資安領域的泛化**：在 CTIBench-RCM（CTIBench-RCM）這項 CVE 至 CWE 對應（CVE-to-CWE）的資安分類任務中，實驗受限於 Foundation-Sec 評估協議，僅進行提示編輯。結果顯示 FAPO 對 GPT-5（GPT-5）提升測試準確率（Test accuracy）+4.0 pp、對 Foundation-Sec-8B-Instruct（Foundation-Sec-8B-Instruct）提升 +7.1 pp、對 Foundation-Sec-8B-Reasoning（Foundation-Sec-8B-Reasoning）提升 +2.0 pp。這證明即使不更動鏈式結構，FAPO 的證據驅動提示最佳化亦能跨域遷移至資安威脅情報任務。

綜合來看，FAPO 的優勢高度集中在具有多步驟交互與嚴格格式要求的任務；對於純數學推理，其最佳化空間相對有限。

#### 與現有研究的比較

FAPO 在文獻光譜中的定位介於「模型能力評估」與「提示工程工具」之間，並透過目標轉移與架構設計做出區隔：

* **相對於越獄攻擊與紅隊演練文獻**：過去研究採用平行搜尋（Parallel search）、樹狀搜尋（Tree-based search）、啟發式搜尋（Heuristic search）或重複取樣，在目標上追求「找到至少一個成功失效案例」。FAPO 借用其閉迴路搜尋模式，但將目標轉為提升管線變體在大量案例上的平均分數。這項轉移使得歸因成為必要——智慧體必須解釋反覆出現的故障，而非僅利用單一成功樣本。此差異使 FAPO 更適用於生產環境中的可靠性提升，而非對抗性測試。
* **相對於評估套件**：HELM（HELM）、BIG-bench（BIG-bench）、AgentBench（AgentBench）等套件主要衡量模型行為與能力，而非針對固定可檢視管線的設計進行最佳化。FAPO 不僅評估，更主動診斷步驟層級故障（Step-level failures）並修改管線。
* **相對於提示程式設計系統**：DSPy（DSPy）最佳化 LLM 模組；GEPA（GEPA）最佳化管線內的提示。然而，兩者皆未設計用於檢查中間步驟輸出，並在標準程式碼工作空間中同時改變提示或鏈式結構。FAPO 的獨特之處在於具備「結構變更」能力，且透過 Claude Code 在真實程式碼庫中操作，而非僅在抽象層級調整參數。

**限制方面**，首先，AIME 的負增益顯示當任務瓶頸位於模型核心推理能力而非管線編排時，FAPO 的結構或提示調整可能無效甚至有害。其次，FAPO 高度依賴 Claude Code 這一專有工具，且最佳化迴圈由大型語言模型驅動，過程中存在非確定性，可能導致不同執行軌跡產生不同變體。第三，結構變更受限於租戶操作手冊定義的範圍，若租戶過度保守，則無法觸及關鍵結構瓶頸。最後，反覆評估與智慧體推理帶來的運算成本顯著高於單輪提示調校，對於查詢預算敏感的場景可能構成障礙。

#### 可重現性評估

FAPO 在可重現性（Reproducibility）上採取多層次設計：

* **開源釋出**：論文明確指出程式碼已公開於 `https://github.com/cisco-foundation-ai/fully-automated-prompt-optimization`，提供社群取得完整工具鏈的途徑。
* **標準化工作空間**：系統將共享執行階段（`src/hephaestus/`）與租戶工作空間（`tenants/<tenant_id>/`）嚴格分離。每個租戶內完整保存鏈結程式碼、提示與管線變體（Pipeline variant）、資料集轉換程式碼與 JSONL 快取、評分器、評估設定（Eval config）、測試案例、儲存設定與最佳化歷程。評估設定透過指定參數與選用變體來定義可重現的鏈結配置。
* **完整記錄**：所有中間步驟輸出、最終輸出、配置與變體歷史皆寫入租戶層級目錄，確保每次執行軌跡皆可回溯。

然而，可重現性仍面臨若干挑戰：

* **專有工具依賴**：Claude Code 為 Anthropic 的商業產品，未取得授權者無法完全複製最佳化迴圈中的智慧體行為。
* **商業模型漂移**：實驗使用 GPT-4.1-mini、GPT-5.4-mini、GPT-5 等商業 API，模型權重未公開，且遠端模型可能隨時間發生版本漂移，難以保證長期數值完全吻合。
* **智慧體非確定性**：儘管最終管線配置與評估設定可被記錄並重播，但由 Claude Code 驅動的變更提案過程本質上具有隨機性，不同執行可能產生不同的最佳化軌跡與最終變體。不過，只要最終配置與隨機種子固定，最終管線的測試準確率應可大致復現。

整體而言，FAPO 在「管線配置重現」層面設計嚴謹，但在「最佳化過程重現」層面受制於 LLM 智慧體的固有隨機性與商業工具限制。

#### 未來研究方向

基於 FAPO 的架構與實驗結果，以下幾個方向值得後續探索：

1. **自動升級決策的理論化**：目前 FAPO 採用啟發式判斷「提示最佳化是否不足」以決定是否升級至結構變更。未來可發展基於資訊理論或歸因置信度的量化指標，使從提示編輯到結構變更的升級決策更具可解釋性與最適性。
2. **跨租戶知識遷移**：當多個租戶工作空間處理相似任務時，能否將一個租戶中發現的故障模式與對應變更策略，透過元學習（Meta-learning）或案例檢索方式遷移至新租戶，以降低冷啟動成本。
3. **數學與深層推理任務的強化**：針對 AIME 等 FAPO 表現較弱的基準測試，可探索將外部工具（如計算器、形式驗證器、定理證明器）納入允許的結構變更範圍，或結合專用推理模組，突破純提示與管線編排的天花板。
4. **成本感知的最佳化**：當前閉迴路搜尋可能消耗大量查詢預算。未來可研究以輕量級模型執行故障歸因與變更提案，僅在驗證階段使用強大任務模型，或引入早期停止機制以提升效率。
5. **多模型同時最佳化**：現有框架針對單一任務模型進行最佳化。後續可擴展為尋找在 GPT、Gemma 等不同模型家族上皆穩健的通用管線變體，提升部署彈性。
6. **資安與關鍵任務的結構強化**：CTIBench-RCM 的實驗僅觸及提示層面。未來可在資安領域放寬結構變更限制，例如自動插入威脅情報檢索節點或弱點知識圖譜驗證步驟，以評估 FAPO 在高風險安全管線中的上限。

## 論文問答

**Q1：FAPO 旨在解決什麼核心問題？**

A：FAPO 主要解決多步驟大型語言模型管線在檢索、推理與格式化等步驟交互作用下產生故障的問題。傳統的單輪提示調校或僅針對最終提示進行最佳化，往往無法捕捉鏈式結構中上游錯誤向下游元件傳播的瓶頸。因此，FAPO 將管線視為可檢視的工作流程，透過記錄中間步驟輸出來定位故障根源，而非僅僅調整最後一個提示。

**Q2：現有的提示最佳化方法與評估套件為何無法有效解決此問題？**

A：現有許多提示空間搜尋方法（如越獄攻擊中的 Best-of-N 或樹狀搜尋）目標是在固定查詢預算下找到至少一個成功的對抗樣本，這種模式只會利用罕見的成功案例，而非解釋反覆出現的故障。此外，HELM、BIG-bench 與 AgentBench 等評估套件主要衡量模型本身的能力，而非針對固定且可檢視的管線設計進行最佳化。至於 DSPy 與 GEPA 等框架，雖然能最佳化模組或管線內的提示，但它們無法檢查步驟層級的故障，也不能在提示編輯不足時自動變更鏈式結構。

**Q3：為何最佳化多步驟 LLM 管線比僅最佳化最終提示更為重要？**

A：隨著多步驟 LLM 管線在資安、企業分析與知識工作中日益普及，工作流程的複雜度與 LLM 呼叫次數也隨之增加，使得錯誤可能在任何一個環節發生。若僅針對最終提示進行調校，將無法處理上游檢索遺漏或中間推理格式錯誤等結構性問題，這些問題會持續傳播並污染下游輸出。因此，唯有從管線層級進行診斷與最佳化，才能系統性地提升整體工作流程的平均準確率與可靠性。

**Q4：FAPO 的核心方法論是什麼？**

A：FAPO 將 LLM 管線視為可檢視的工作流程，並在標準化的程式碼庫與隔離的租戶工作空間中，由 Claude Code 驅動閉迴路最佳化循環。系統首先對當前管線執行訓練案例評估，記錄每個步驟的輸入、輸出與日誌，並產生證據報告將故障歸因為遺漏證據、格式錯誤或最終指令薄弱等類型。接著，Claude Code 根據歸因結果提出限定範圍的變更：先嘗試提示編輯，僅當記錄的故障證據顯示提示最佳化不足以解決結構瓶頸時，才會在租戶允許的範圍內修改鏈式結構，且每次變更都需通過安全審查後才會重新執行驗證。

**Q5：相較於 GEPA 等既有方法，FAPO 的關鍵創新為何？**

A：FAPO 的關鍵創新在於能夠自主檢查中間步驟輸出，將反覆出現的故障歸因至特定管線元件，並依據實證證據決定要編輯提示或修改鏈式結構。不同於僅能在管線內最佳化提示的 GEPA，FAPO 在歸因分析顯示提示編輯無法解決主要瓶頸時，可自動升級為結構變更——例如延伸檢索鏈或引入確定性約束執行機制。這種以證據為基礎、限定範圍的升級策略，使系統能系統性地提升管線平均分數，而非僅僅利用單一成功樣本。

**Q6：FAPO 的關鍵設計原則與架構選擇有哪些？**

A：FAPO 遵循四項設計原則：將共享評估引擎與任務特定工作空間分離、以記錄的中間證據作為最佳化決策依據、偏好最小且有效的變更（先提示後結構），以及對每項提案實施安全審查防護欄。架構上，它使用 LangGraph 將管線表示為狀態圖，並透過租戶工作空間隔離不同任務的提示、鏈變體、評分器與最佳化歷程，其中租戶 playbook 作為最高層級的政策文件可覆寫 FAPO 能力。這種設計確保了再現性、擴充性與跨租戶隔離，避免單一任務的假設影響其他任務。

**Q7：FAPO 在哪些基準測試與模型上進行了評估？**

A：FAPO 在六個通用基準測試上進行評估，包括 HoVer、IFBench、LiveBench-Math、HotpotQA、Papillon 與 AIME，並使用 GPT-4.1-mini、GPT-5.4-mini 與 Gemma3-12B 三種任務模型。此外，研究團隊也在資安領域的 CTIBench-RCM（CVE 至 CWE 分類任務）上進行測試，採用 GPT-5、Foundation-Sec-8B-Instruct 與 Foundation-Sec-8B-Reasoning 等模型。這些涵蓋問答、事實驗證、指令遵循、數學推理與網路安全的多元基準，能夠全面檢驗 FAPO 的泛化能力。

**Q8：相較於 GEPA 基線，FAPO 取得了哪些關鍵量化結果？**

A：在 18 組模型–基準測試比較中，FAPO 贏得 15 組，平均增益達到 +14.1 百分點。其中有 11 組比較的勝出幅度具有統計穩健性，呈現平均值與試驗標準差範圍不重疊的顯著領先。特別值得注意的是，在 HoVer 與 IFBench 的六組比較中，FAPO 從提示編輯升級為結構變更後全數獲勝，平均增益高達 +33.8 百分點，充分顯示當提示層級搜尋遇到未解決瓶頸時，結構最佳化能帶來巨大效益。

**Q9：FAPO 在資安任務上的表現如何？這對純提示最佳化有何啟示？**

A：在僅限提示編輯的 CTIBench-RCM 資安任務中，FAPO 分別為 GPT-5、Foundation-Sec-8B-Instruct 與 Foundation-Sec-8B-Reasoning 帶來 +4.0、+7.1 與 +2.0 百分點的測試準確率提升。這些結果顯示，即使不更動管線結構，FAPO 以證據為導向的提示最佳化依然能有效強化專業資安分類任務的表現。這也說明 FAPO 不僅適用於通用任務，同樣能作為資安聚焦管線的最佳化技術，達到領先水準。

**Q10：FAPO 可應用於哪些實務場景？**

A：FAPO 特別適合需要結合檢索、推理與格式化的企業分析、資安營運與複雜知識工作等多步驟 LLM 管線場景。舉例來說，組織可利用 FAPO 自動精煉威脅情報分類、多跳文件驗證或指令遵循代理人的管線，這些場景經常因中間步驟錯誤傳播而導致整體失效。由於 FAPO 在標準化程式碼庫中運作，並具備租戶隔離與防護欄機制，因此能安全整合至需要可重現與可稽核最佳化流程的生產環境。

**Q11：將 FAPO 整合到開發流程時，需考慮哪些產品與營運因素？**

A：整合 FAPO 時，必須為每個任務建立隔離的租戶工作空間，內含任務說明、評分規則、當前提示以及定義允許變更範圍的租戶 playbook。系統在每次變更前都會執行安全審查，確保提案不會洩漏資料、竄改評分器或違反任務規則，這對維護管線完整性至關重要。此外，由於所有變體、中間輸出與評估分數都記錄在租戶層級目錄中，開發團隊能完整掌握最佳化歷程，便於除錯、合規查核與版本回滾。

**Q12：FAPO 對 LLM 管線工程與提示最佳化領域可能帶來什麼廣泛影響？**

A：FAPO 將最佳化目標從尋找單一成功對抗提示，轉變為透過基於證據的歸因來提升管線平均分數，從而為自主管線精煉建立新典範。它彌補了模型評估套件與可程式化管線框架之間的落差，因為 FAPO 主動最佳化固定且可檢視的管線設計，而非僅僅評測模型能力。這種方法為研究與工程社群提供了可取得的工具，以利用 Claude Code 同時進行提示與結構層級的管線搜尋，有望加速更可靠 LLM 應用的開發。

**Q13：論文承認 FAPO 存在哪些限制？**

A：論文指出，FAPO 目前的實作仰賴 Claude Code 作為最佳化智慧體，這意味其成效與成本結構與該特定工具綁定。此外，該框架需要使用者提供結構良好的問題陳述、評估準則與標準化程式碼庫，這可能帶來可觀的前期工程投入。租戶 playbook 與防護欄也必須謹慎設計以避免不安全變更，這表示在定義最佳化邊界時，仍需要一定程度的人類監督。

**Q14：FAPO 是否存在失敗案例或表現較差的基準測試？**

A：是的，在六個通用基準測試中，AIME 是唯一一個 GEPA 領先 FAPO 的項目，這顯示某些數學推理任務對 FAPO 現有的歸因與編輯策略構成獨特挑戰。這暗示對於需要高度專業化推理鏈的問題類型，提示優先或結構感知最佳化未必總能立即帶來增益。深入分析這類失敗案例，有助於理解證據驅動管線修改的適用邊界，並精進針對抽象推理領域的歸因啟發式規則。

**Q15：這項工作為自主管線最佳化指出了哪些未來方向？**

A：未來研究可將 FAPO 擴展至支援更多基礎模型與最佳化智慧體，以降低對單一供應商的依賴。學界也可探索更精細的歸因機制，使其能診斷非相鄰管線步驟之間的微妙交互作用，而非僅限於局部瓶頸。最後，將自動化結構搜尋與生產環境回饋的持續學習迴路結合，可望實現即時自我改進的管線，使其能隨任務分布變化自動調適，而無需手動重新配置租戶設定。

## 實務應用指南

### 適用場景

1. **企業多跳知識檢索問答（Multi-hop RAG QA）**：適用於結合外部文件檢索、推理與格式化輸出的工作流程，例如法規查詢或技術文件問答。當錯誤可能在檢索、推理或格式化任一環節傳播時，FAPO 可透過歸因定位瓶頸，並優化提示或鏈式結構。
2. **資安威脅情報分類管線**：如 CTIBench-RCM 中的 CVE 至 CWE 對應任務。FAPO 可在僅允許提示編輯的防護欄下，反覆驗證管線變體以提升測試準確率，適合安全協定嚴格、不允許任意更動鏈式架構的環境。
3. **複雜指令遵循與合規文件生成**：類似 IFBench 的場景，需要管線同時處理多項約束條件。FAPO 先執行提示優先搜尋，僅在歸因顯示結構瓶頸時，才引入確定性約束執行步驟或延長檢索鏈。
4. **多步驟數據分析與報告生成**：結合程式碼執行與大型語言模型呼叫的分析管線。FAPO 的評估引擎可記錄中間步驟輸出，協助判斷錯誤來自資料檢索、程式碼邏輯或最終摘要提示。
5. **自主智慧體工作流程調校**：基於 LangGraph 建構的狀態圖管線。FAPO 利用 Claude Code 驅動最佳化迴圈，在租戶工作空間內反覆診斷步驟層級故障，並提出限定範圍變更。

### 實作前置條件

- **資料準備**：需備妥訓練案例、可重複執行的評估準則、問題陳述與評分函數。中間步驟的輸入輸出必須可被記錄，以便進行故障診斷與歸因。建議預先建立基線提示與初始鏈式結構。
- **運算資源**：需能呼叫 Claude Code 作為最佳化代理，同時具備任務模型（如 GPT-5、Gemma3-12B 或領域模型如 Foundation-Sec-8B-Instruct）的 API 配額。反覆評估會產生大量查詢，需預留足夠查詢預算與運算成本。
- **技術能力**：團隊需熟悉 Python、LangGraph 狀態圖設計與多步驟大型語言模型管線開發。此外，需具備設計評分函數、建立租戶工作空間隔離機制，以及撰寫租戶 playbook（含防護欄與允許變更範圍）的能力。

### 實作步驟建議

1. **建立標準化租戶工作空間**：為任務建立隔離的 `tenants/<tenant_id>/` 目錄，內含鏈結程式碼、提示變體、評分器、評估設定與租戶 playbook。playbook 為最高層級政策文件，需明確限定提示編輯與結構變更的允許範圍。
2. **將管線表達為可檢視狀態圖**：使用 LangGraph 建構管線，確保每一步的輸入、輸出與紀錄均可被評估引擎擷取。這是後續歸因與故障診斷的基礎。
3. **定義評估準則與評分函數**：建立可重現的評估設定（eval config），指定參數與變體選擇規則。評分函數應能反映最終答案品質，且不可在最佳化過程中被意外修改。
4. **執行基線評估與故障歸因**：以共享評估引擎執行初始管線，記錄最終答案、分數與中間步驟輸出。產生證據報告，將故障分類為缺少證據、不當棄答、輸出格式錯誤或最終指令薄弱等類型。
5. **啟動提示優先的閉迴路搜尋**：由 Claude Code 分析故障證據，先提出提示編輯。每次僅允許一項限定範圍變更，經獨立審查（safety review）確認未洩漏資料、未竄改評分器且符合任務規則後，才執行評估。
6. **有條件地升級至結構變更**：僅當記錄的故障證據顯示提示最佳化無法解決主導結構瓶頸，且租戶 playbook 允許時，才變更鏈式結構（如延長檢索鏈、新增確定性約束步驟或調整參數）。
7. **反覆驗證與版本紀錄**：每個通過審查的管線變體均需執行評估，比較平均分數與標準差。所有變體歷程、設定與分數應保留於租戶目錄，確保最佳化過程可重現。
8. **收斂判斷與產品化部署**：當分數收斂或查詢預算耗盡時，選擇最高分數的管線變體。將最終的評估設定與提示版本納入版本控制，作為生產環境部署的基準。

### 潛在風險與注意事項

- **過度擬合訓練案例**：FAPO 以訓練案例的平均分數為目標，可能過度擬合特定資料分布。建議保留獨立測試集，並在最佳化後驗證泛化表現。
- **歸因錯誤導致無效修改**：若中間步驟紀錄不完整，歸因可能誤判瓶頸位置（如將檢索錯誤歸因於推理提示）。需確保狀態圖的每一步均有充足日誌與證據支援。
- **查詢預算與成本失控**：閉迴路搜尋需多次呼叫任務模型與 Claude Code。應在租戶 playbook 中設定迭代次數上限與成本預算，並監控累計開銷。
- **防護欄與範圍蔓延**：若未嚴格執行審查機制，Claude Code 可能提出超出允許範圍的變更（如修改評分器邏輯）。必須透過獨立審查閘門（safety gate）攔截違規提案。
- **結構變更的副作用**：在 HoVer 或 IFBench 等基準測試中，結構變更雖可大幅提升分數，但可能增加延遲或破壞下游元件相容性。升級至結構變更前，應評估對延遲與維運成本的影響。
- **負向增益風險**：如 AIME 基準測試所示，並非所有任務都能從提示或結構變更中受益。若連續多輪分數未提升，應考慮提前終止並回復基線。

### 與其他技術的整合建議

- **與 DSPy 協作**：DSPy 適合模組化的提示程式設計與編譯，FAPO 則補充其缺乏的「管線結構變更」與「步驟層級故障歸因」能力。可將 DSPy 模組作為 LangGraph 節點嵌入 FAPO 租戶工作空間，由 FAPO 負責高層次的閉迴路最佳化。
- **整合現有 CI/CD 與 MLOps**：將租戶工作空間視為程式碼倉庫中的獨立專案，透過 Git 管理提示變體與評估設定。在持續整合流程中觸發 FAPO 評估引擎，自動比較新舊管線變體的平均準確率。
- **銜接可觀測性平台**：將 FAPO 產生的中間步驟輸出與證據報告導入 LangSmith、Langfuse 或內部追蹤系統，強化故障診斷的可視化，並累積跨任務的歸因知識庫。
- **強化現有資安工作流程**：對於 CTI 平台中的 CVE 至 CWE 對應任務，可在不改變既有資料流的前提下，以 FAPO 租戶隔離模式優化分類管線的提示，並將評分函數對接現有威脅情報評分標準。
- **與向量資料庫與檢索系統整合**：當 FAPO 判斷需要延長檢索鏈時，可直接調用現有向量資料庫（如 Pinecone、Milvus）或關鍵字檢索引擎，無需重建底層索引。

### 給不同背景讀者的閱讀建議

- **初學者**：請先聚焦圖 2 的最佳化迴路概念與「提示優先、結構次之」的核心策略。無需深入 LangGraph 狀態圖的實作細節，重點理解 FAPO 如何透過反覆測試與審查來提升管線表現即可。
