iPrefBench 的方法論核心在於建構一個能同時評估「推斷」(Infer) 與「詢問」(Ask) 兩種個人化能力的測試環境，其設計哲學體現了對真實人機協作場景的深度理解。

**雙軌資訊來源設計**

此基準測試最關鍵的創新在於明確區分兩種缺失資訊的來源：

- **可從歷史推斷 (History-Inferable)**：資訊存在於使用者過去 3,051 筆活動事件中，代理應主動從中提取。例如「預約我常去的餐廳」中的餐廳名稱，可從過去的訂位紀錄推斷。
- **僅能詢問 (Ask-Only)**：資訊僅存在於使用者當下意圖中，無法從歷史推測。例如「明天」的具體時間與人數，必須透過 `ask_user` 動作取得。

這種二元分類迫使代理必須發展「元認知」(Meta-cognition) 能力——判斷哪些資訊屬於哪一類，而非盲目詢問或過度推斷。

**一致性人設 (Coherent Persona) 的建構**

基準測試圍繞單一一致性人設展開，包含 3,051 筆跨 26 個應用程式的活動事件。這種設計避免了「冷啟動」(Cold-Start) 問題，確保所有推斷都有具體的歷史依據。人設的一致性使得評估標準更為客觀——每個「正確答案」都有明確的歷史佐證，而非評審者的主觀判斷。

**評估框架的雙軸設計**

iPrefBench 採用兩個正交的評估軸：

1. **個人化任務完成度 (Personalized Task Completion)**：分為「動作完成度」(Action Completion) 與「個人化分數」(Personalization Score)。前者衡量操作是否執行，後者衡量使用者相關決策是否符合實際意圖。
2. **使用者與代理互動 (User-Agent Interaction)**：借用 Grice 對話準則 (Grice's Maxims) 的精神，以召回率 (Recall) 與精確率 (Precision) 評估詢問品質——召回率衡量是否問到所有必要資訊，精確率衡量所問是否確實必要。

**挑戰性情境的刻意設計**

基準測試特別納入三類困難情境：當前指令覆蓋過去模式（如「這次試試新餐廳」）、近期行為顯示偏好改變、以及偏好選項不可用。這些情境模擬了真實世界中個人化偏好的動態特性，避免代理過度依賴靜態歷史模式。

#### 實驗數據解讀

**執行能力與個人化的巨大鴻溝**

七個前沿代理的實驗結果揭示了一個驚人的落差：Claude Opus 5 達到 91.6% 的動作完成度，但完整任務成功率僅 47.7%。這 44 個百分點的差距幾乎完全來自個人化層面的失敗。這意味著當代代理已具備成熟的「執行能力」(Execution Capability)，但「個人化能力」(Personalization Capability) 嚴重滯後。

**詢問不足是主要瓶頸**

在詢問行為方面，所有代理在僅能詢問資訊上的召回率最高僅 44.3%，顯示代理普遍傾向「沉默猜測」(Silent Guessing) 而非主動詢問。這與人類使用者的真實期望形成鮮明對比——使用者寧願被問，也不願代理做出錯誤假設。

**精確率與召回率的權衡**

精確率落在 60% 至 77% 區間，意味著代理所問的問題中，有相當比例並非真正必要。這暴露了一個根本性的權衡：增加詢問可提升召回率與任務成功率，但會降低精確率並增加使用者負擔。實驗中明確加入「澄清階段」(Clarification Phase) 的嘗試證實了此權衡——更多問題帶來更高成功率，卻犧牲了精確率。

**任務設計的區辨力**

基準測試的 130 個任務展現了良好的區辨力，能有效區分不同代理的個人化能力。這對於未來研究極具價值，因為它提供了細粒度的診斷工具，而非僅有單一總分。

**方法論優勢**

相較於同時提供歷史與互動但未區分資訊來源的基準 (如 Chen et al., 2026b,c)，iPrefBench 的「可推斷 vs. 僅能詢問」分類提供了更精確的診斷能力——能明確指出代理失敗是因為「該推斷卻沒推斷」還是「該詢問卻沒詢問」。

**現有限制**

然而，此基準也存在侷限性：

1. **單一人設**：僅基於一個一致性人設，可能無法涵蓋使用者群體的多樣性。

4. **模擬使用者限制**：模擬使用者無法完全重現真實使用者的語境、情緒與隱含偏好。

4. **無障礙輔助技術**：對於視障或行動不便的使用者，個人化代理若能正確推斷其偏好（如字級、常用聯絡人），可大幅減少互動成本。iPrefBench 的「recall/precision on ask-only」指標可直接應用於評估此類輔助代理的溝通效率。

5. **學術研究中的代理能力比較**：研究團隊在發表新代理模型時，可使用 iPrefBench 作為標準化基準，與 Claude Opus 5 等前沿模型比較，凸顯自家方法在「個人化」維度上的進展。

### 實作前置條件

**資料面**
- 需要建構一個「一致性人設」（coherent persona），包含至少數千筆跨應用程式的活動事件（iPrefBench 使用 3,051 筆、26 個 App）。資料必須內部一致，避免出現「使用者從不吃辣」但歷史中又有「點麻辣鍋」的矛盾。
- 每筆任務的「缺失資訊」必須事先標註為「可推斷」或「僅能詢問」兩類，並附上對應的歷史證據或預期答案。
- 需要準備一個可執行的 iOS 模擬環境（iPrefBench 是基於 iOSWorld 建構），或自建 Android/Web 等同類環境。

**運算面**
- 評估前沿代理（如 Claude Opus 5 等）需要 API 呼叫成本，每個任務可能涉及多輪互動，130 個任務 × 7 個代理的評估成本不容小覷。
- 模擬使用者（simulated user）需要另一個 LLM 來扮演，建議使用與主代理不同或更強的模型以避免評估偏差。

**技能面**
- 熟悉行動裝置 GUI 代理的動作空間設計（點擊、滑動、文字輸入、呼叫 `ask_user` 等）。
- 具備 LLM 評估（LLM-as-a-judge）的 prompt 工程能力，因為個人化分數需要 LLM 判斷代理選擇是否符合使用者意圖。
- 了解 Grice 對話準則（quantity、quality、relation、manner），以便設計「recall/precision on ask-only」這類互動品質指標。

### 實作步驟建議

**第一步：定義評估目標與指標體系**
先決定要衡量「動作完成度」與「個人化完成度」兩個獨立維度，而非只看單一成功率。參考 iPrefBench 的 rubric 設計，將每個任務拆解為「必要操作」與「使用者相依選擇」兩類評分項。

**第二步：建構人設與活動歷史**
從單一一致性人設出發，產生跨應用程式的活動事件。建議先聚焦 5–10 個高頻應用（如地圖、訊息、餐廳、音樂、外送），再擴展到 20+ 個。務必建立「人設規格書」記錄明確偏好（如「素食者」「過敏：花生」「常用支付：Apple Pay」），作為後續評分的 ground truth。

**第三步：設計未指定任務**
每個任務至少刻意省略 1–3 個使用者相依細節，並明確分類：
- **可推斷類**：省略的資訊必須能在歷史中找到明確證據（例如「訂我常去的餐廳」→ 歷史中有 5 次以上相同餐廳訂位）。
- **僅能詢問類**：省略的資訊在歷史中無從得知（例如「訂明天晚上」→ 沒有任何「明天晚上」的歷史模式）。
- **覆寫類**：當前指令與歷史偏好矛盾（例如「這次訂不一樣的餐廳」），測試代理是否能正確處理覆寫。

**第四步：實作環境與模擬使用者**
在 iOSWorld 或自建環境中實作 `ask_user` 動作介面。模擬使用者應能根據人設規格書回答問題，並對「過度詢問」設定容忍上限（例如最多回答 3 個問題）。

**第五步：執行評估並分析差距**
對每個代理計算：
- Action Completion（動作完成率）
- Personalization Score（個人化分數）
- Ask-Only Recall（必要詢問的召回率）
- Ask-Only Precision（詢問的精確率）

重點觀察「動作完成率高但個人化分數低」的落差，這正是 iPrefBench 揭示的核心問題。

**第六步：迭代改進代理策略**
根據評估結果調整代理的 prompt 或決策邏輯。例如：若 recall 低，可加入「主動詢問」階段；若 precision 低，可加入「先檢查歷史再決定是否詢問」的推理步驟。

### 潛在風險與注意事項

1. **「過度詢問」陷阱**：iPrefBench 顯示，強迫代理進入澄清階段可提高 recall，但會降低 precision，反而打擾使用者。**緩解方式**：在 prompt 中明確教導代理「先查歷史、無法確定再問」，並設定詢問數量上限。

2. **模擬使用者的偏差**：模擬使用者若用 LLM 扮演，其回答可能與真實使用者不一致（例如過於配合、過於簡短）。**緩解方式**：使用更強的模型扮演使用者、預先準備多樣化回答模板，並對回答風格做一致性檢查。

3. **人設一致性崩潰**：當活動事件數量增加（iPrefBench 用 3,051 筆），很容易產生內部矛盾。**緩解方式**：建立「人設規則引擎」，在生成活動時自動檢查是否違反已記錄的偏好。

4. **評估分數的 LLM 判官偏差**：個人化分數仰賴 LLM 判斷「代理選擇是否符合使用者意圖」，不同判官模型可能給出不同結果。**緩解方式**：使用多個判官模型取共識，或在關鍵任務上改為人工評估。

5. **環境可執行性的維護成本**：iOSWorld 等環境會隨作業系統更新而失效。**緩解方式**：鎖定特定 iOS 版本、容器化環境、並建立回歸測試。

6. **「幸運猜對」掩蓋真實能力**：代理可能靠猜測碰巧答對 ask-only 資訊，使表面分數虛高。**緩解方式**：將 ask-only 資訊的設計為「有多個合理答案但只有一個符合人設」，降低隨機命中率。

### 與其他技術的整合建議

1. **與 RAG（檢索增強生成）整合**：將「活動歷史」視為一個可檢索的知識庫，代理在決定「推斷 vs. 詢問」前，先用 RAG 檢索相關歷史事件。這能顯著提升 history-inferable 類任務的表現。

2. **與記憶系統（Memory）整合**：長期部署的個人化代理需要持久化使用者偏好。iPrefBench 的評估方法可作為「記憶系統品質」的監控指標，定期用 130 個任務抽樣測試，觀察個人化分數是否隨時間提升。

3. **與 RLHF / DPO 整合**：將 iPrefBench 的評估結果作為獎勵訊號，用於微調代理的「詢問策略」。例如：對「該問卻沒問」與「不該問卻問了」分別給予負獎勵。

4. **與多代理架構整合**：可設計「規劃代理」+「詢問代理」分工——規劃代理負責拆解任務、判斷哪些資訊可推斷；詢問代理負責生成精準的提問。這與 iPrefBench 揭示的「推斷/詢問」二元結構天然契合。

5. **與可解釋性工具整合**：在代理決定「詢問」時，輸出其推理過程（為何歷史中找不到、為何需要使用者確認），方便使用者判斷問題是否合理，也便於開發者除錯。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的 Introduction 與 Figure 1，理解「為什麼未指定任務對個人化代理很重要」這個核心問題。接著看「評估 7 個前沿代理」的段落，體會「動作完成 91.6% 但任務成功率僅 47.7%」這個驚人的落差，這就是整篇論文的價值所在。技術細節可以先跳過。

**給 AI 工程師**：重點研讀「評估指標設計」段落，特別是「action completion vs. personalization」的分離設計，以及「ask-only recall/precision」這兩個互動品質指標。這些指標可直接借用到自家代理的評估 pipeline 中。第 2 節 Related Work 也能幫助你快速掌握 CUA 基準測試的生態系。

**給研究者**：本論文最大的研究缺口在於「如何讓代理學會正確判斷何時該推斷、何時該詢問」。建議從「Explicitly adding a clarification phase can substantially increase the number of questions... but lower precision in turn」這段出發，思考如何設計兼顧 recall 與 precision 的方法（例如：先檢索歷史、計算信心分數、僅在低信心時詢問）。這是後續可發表的方向。

**給產品經理**：本論文揭示的核心 insight 是「使用者對代理的不滿，往往不是來自代理做錯事，而是來自代理做對了動作但做錯了選擇」。建議將「個人化完成度」列為產品 KPI，並思考：你的代理在「該問的時候不問」與「不該問的時候猛問」之間，目前偏哪一邊？iPrefBench 提供了一個量化此問題的工具。
