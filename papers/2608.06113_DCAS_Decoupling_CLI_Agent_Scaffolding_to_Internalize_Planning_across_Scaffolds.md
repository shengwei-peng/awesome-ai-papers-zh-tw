# DCAS：解耦 CLI 代理腳手架，使規劃能力跨腳手架內化

**原文標題：** DCAS: Decoupling CLI Agent Scaffolding to Internalize Planning across Scaffolds  
**作者：** Kishanthan Thangarajah、Boyuan Chen、Ahmed E. Hassan  
**發布日期：** 2026-08-06  
**HF 連結：** [https://huggingface.co/papers/2608.06113](https://huggingface.co/papers/2608.06113)  
**arXiv：** [https://arxiv.org/abs/2608.06113](https://arxiv.org/abs/2608.06113)

## ⚡ TL;DR

CLI 代理經 OpenHands 微調後，於非訓練腳手架上的效能明顯下滑。
本文提出 DCAS，在不修改腳手架下替換後端模型，支援跨腳手架評估與規劃感知軌跡收集。
實驗證實規劃品質為高槓桿因素，僅以單一腳手架少量規劃感知軌跡微調即可跨腳手架泛化。

## 摘要翻譯

基於 CLI 的軟體工程代理（CLI-based software-engineering agent）已迅速成熟，然而開放生態系統（open ecosystem）卻收斂至單一訓練環境（training environment）：用於微調（fine-tune）開源模型（open models）的軌跡資料集（trajectory datasets）幾乎全數在 OpenHands 下收集。在此資料上微調的模型於 OpenHands 中表現良好，但部署（deploy）於任何非訓練腳手架（non-training scaffold）時皆顯著下降。未經微調的基礎模型（base model）並未出現此分歧（divergence），顯示該差距（gap）係由微調所導致，且與訓練腳手架的慣例（convention）密切相關。我們認為，規劃結構（planning structure）是一項具關鍵支撐性的腳手架特定行為（scaffold-specific behavior），本文區分為兩種意義：顯式規劃（explicit planning），即在執行前產生、並作為一等公民產物（first-class artifact）的執行前計畫（pre-execution plan）；以及隱式規劃（implicit planning），即貫穿整個代理迴圈（agent loop）、形塑執行過程的結構慣例（structural convention）。在此假設下，縮小差距需要將規劃從固定的腳手架產物轉化為習得的模型能力（learned model capability）。我們提出解耦 CLI 代理腳手架（Decoupling CLI Agent Scaffolding, DCAS），這是一個後端替換攔截層（backend-substitution interception layer），可在不修改腳手架（scaffold）的情況下，於任何 CLI 腳手架與任何後端模型（backend model）之間路由（route）API 流量（API traffic），從而實現跨腳手架評估（cross-scaffold evaluation）與規劃感知軌跡收集（planning-aware trajectory collection）。運用 DCAS，一項對照的規劃來源介入（controlled plan-source intervention）證實規劃品質（planning quality）為高影響力元件（high-leverage component），其提升幅度超過我們觀察到的跨腳手架性能下降（cross-scaffold drop）。僅以 DCAS 在單一腳手架下收集的少量規劃感知軌跡（planning-aware trajectories）進行微調的模型，在非訓練腳手架上皆有穩定提升（gain），且規劃的兩種意義在訓練資料中經驗上可區分（empirically separable）。

### 核心貢獻（3～5點）
- 診斷微調誘發的跨腳手架性能下降：發現於 OpenHands 軌跡資料上微調的開源模型，部署於非訓練腳手架時顯著衰退，而基礎模型無此分歧，指出問題根源在於訓練腳手架的慣例綁定。
- 提出規劃結構假說：區分顯式規劃與隱式規劃兩種意義，主張規劃結構是腳手架特定的關鍵支撐行為，需轉化為習得的模型能力以縮小跨腳手架差距。
- 提出 DCAS 方法：設計後端替換攔截層，無需修改腳手架即可於任意 CLI 腳手架與後端模型間路由 API 流量，支援跨腳手架評估與規劃感知軌跡收集。
- 實證驗證規劃的影響力：透過對照的規劃來源介入證實規劃品質為高影響力元件；僅以少量規劃感知軌跡微調即可在非訓練腳手架上獲得穩定提升，且兩種規劃意義在訓練資料中經驗上可區分。

### 適合對象
從事大型語言模型代理、軟體工程自動化、開源模型微調與評估的研究人員與實務工作者（practitioner）；特別適合關注代理腳手架可移植性、跨框架評估方法，以及希望將規劃能力內化為模型能力而非依賴特定框架實作的機器學習（machine learning）工程師與開發者。

## 深度分析

#### 方法論解析

##### 1. 核心問題與假說
本文針對的現象是：開源社群的微調（fine-tuning）軌跡資料集（trajectory dataset）幾乎全數在 OpenHands 這一 CLI 腳手架（CLI scaffold）下收集，導致微調後的開源模型（open model）在 OpenHands 上表現優異，但部署到任何非訓練腳手架（non-training scaffold）時性能顯著下降；而未經微調的基礎模型（base model）並無此落差。作者據此推論，這種跨腳手架性能下降（cross-scaffold drop）並非模型能力不足，而是微調過程中「學會」了特定訓練腳手架（training scaffold）的規劃慣例。

為了精確定位問題，作者區分了兩種規劃（planning）概念：
- **顯式規劃（explicit planning）**：執行前產生一個獨立、可被觀察與評估的執行前計畫（pre-execution plan），例如 Claude Code 的 Plan Mode 或 OpenCode 的 Plan agent。
- **隱式規劃（implicit planning）**：不表現為單一計畫文件，而是滲透在代理迴圈（agent loop）每一回合的結構慣例（structural convention），包括工作如何分解、何時從探索轉入行動、工具呼叫（tool call）的順序、失敗後如何重新規劃等。

作者的核心假說是：微調在單一腳手架下會讓模型內化該腳手架特有的「顯式／隱式規劃混合比例」；若要在不同腳手架間泛化，必須把規劃從固定腳手架產物轉化為模型習得的能力（learned model capability）。

##### 2. DCAS 的設計理念
**DCAS（Decoupling CLI Agent Scaffolding，解耦 CLI 代理腳手架）** 是一個後端替換攔截層（backend-substitution interception layer）。其設計目標是讓任何 CLI 腳手架無需修改即可與任何後端模型（backend model）配對，從而：
1. 在保持目標腳手架完整慣例表面的前提下，進行跨腳手架評估（cross-scaffold evaluation）。
2. 在任何目標腳手架下收集規劃感知軌跡（planning-aware trajectory），包括那些原本與專有後端緊密綁定的腳手架（如 Claude Code）。
3. 讓微調資料能夠直接來自多樣腳手架，而無需改寫腳手架原始碼。

DCAS 的運作邏輯可理解為「API 流量（API traffic）中間人」：它攔截（intercept）腳手架發往其預設後端的請求，將之路由（route）到研究者指定的替代模型，再把回應轉回腳手架。由於腳手架只看到符合其預期格式的對話，因此腳手架的系統提示（system prompt）、工具模式（tool schema）、回合管理（turn management）等慣例都保持原樣；真正被替換的是產生回應的後端模型。這種解耦（decouple）方式比「修改腳手架以支援新模型」更乾淨，因為它避免了為了適配模型而順便改變腳手架行為，從而確保實驗中的腳手架變因純粹是腳手架本身。

##### 3. 規劃來源介入（plan-source intervention）
為了驗證規劃品質（planning quality）是否為高影響力元件（high-leverage component），作者設計了對照介入（controlled intervention）：固定執行模型與腳手架，只改變計畫的來源。這能夠在控制其他變因的情況下，孤立出規劃對解決率（resolution rate）的貢獻。可能的對比包括：
- 由模型自身產生計畫；
- 由人類或更強模型提供高品質計畫；
- 不提供顯式計畫，僅依賴腳手架隱式結構。

若高品質計畫帶來的提升超過跨腳手架性能下降，則說明規劃品質確實是關鍵支撐行為（load-bearing behavior）。

##### 4. 訓練資料的組成實驗
第二個研究問題透過比較兩種訓練資料來測試兩種規劃意涵：
- **僅含計畫（plan-only）**：訓練資料只包含顯式計畫，不含後續執行軌跡。若模型因此學會產生更好的執行前計畫，但執行結構未改善，則顯式規劃可被獨立內化。
- **計畫加執行（plan-and-execution）**：訓練資料同時包含計畫與完整代理迴圈執行。若模型在執行結構（隱式規劃）上表現更好，則隱式規劃也可被學習。

這種設計讓作者能夠經驗上區分（empirically separable）兩種規劃，並判斷微調資料應如何配比。

##### 5. 跨腳手架泛化驗證
第三個研究問題檢驗：在單一腳手架下，使用少量 DCAS 收集的規劃感知軌跡進行微調後，模型能否在未見過的非訓練腳手架上表現提升。若提升一致出現，則規劃已被內化為結構性技能，而非僅記憶特定腳手架的輸出格式。

#### 實驗數據解讀

##### 1. 基礎模型與微調模型的跨腳手架差異
引言指出，未經微調的基礎模型在不同腳手架上的表現差異遠小於微調後模型；只有在單一腳手架微調後，跨腳手架差距（spread）才急劇擴大。這項觀察具有重要方法論意義：
- 它排除了「某些腳手架本質上過難」的解釋，因為基礎模型能相對穩定地適應各腳手架。
- 它將因果指向微調過程：模型學到的不是通用解題能力，而是與訓練腳手架慣例耦合的條件反射。

對實務工作者（practitioner）而言，這意味著目前開源模型的高分數具有「腳手架依賴性」；若因成本（cost）、授權（licensing）、延遲（latency）或資料隱私限制（data-privacy constraint）而選用其他腳手架，微調模型的優勢可能迅速消失。

##### 2. RQ1：規劃品質的槓桿效應
雖然具體數值未在提供的摘要中列出，但作者宣稱規劃來源介入帶來的提升超過了觀察到的跨腳手架性能下降。若此結果成立，則可解讀為：
- **規劃是瓶頸**：在固定後端模型與腳手架下，執行能力並未耗盡，真正限制解決率的是計畫品質。
- **高品質計畫具有跨腳手架價值**：即使腳手架不同，好的執行前計畫仍能引導執行，這為後續「把規劃內化為模型能力」提供了動機。

此處的指標應包含解決率（resolution rate）與計畫遵循度（plan adherence）。若計畫遵循度高但解決率低，代表計畫本身有問題；若計畫好但遵循度低，則代表執行結構（隱式規劃）未能配合。

##### 3. RQ2：兩種規劃的經驗可分性
透過比較 plan-only 與 plan-and-execution 訓練，作者聲稱兩種規劃在訓練資料中可被區分。這暗示：
- **顯式規劃**主要影響模型產生前置計畫的能力，對執行過程中的工具序列影響較小。
- **隱式規劃**主要影響模型在代理迴圈中如何組織動作、處理觀察與調整策略。

若兩者確實可分，則未來的微調資料設計可以「按需配比」：針對缺乏顯式規畫階段的腳手架（如 mini-swe-agent），可強化隱式規劃軌跡；針對有 Plan Mode 的腳手架，則補充顯式計畫樣本。

##### 4. RQ3：少量規劃感知軌跡的泛化
作者報告，使用少量 DCAS 收集的規劃感知軌跡在單一腳手架下微調後，模型在多個非訓練腳手架上均有提升。這是本文最具實務價值的發現：
- **資料效率**：相較於動輒數萬條的單一腳手架軌跡，少量但規劃感知的跨腳手架資料即可帶來泛化。
- **技能轉移而非格式記憶**：若提升僅來自記憶，模型應在訓練腳手架上進步、在非訓練腳手架上退步；但結果是跨腳手架普遍進步，支持「規劃作為結構性技能」的假說。

不過，由於未見完整數據，仍需留意：提升是否在所有非訓練腳手架上都達到統計顯著？不同腳手架間的增益分佈是否均勻？這些細節將影響結論的強度。

#### 與現有研究的比較

##### 1. 單一腳手架訓練生態的侷限
現有公開軌跡資料集如 SWE-Gym、Nebius、SWE-Lego、CoderForge 皆在 OpenHands 下收集。這種收斂造成兩個問題：
- **評估偏差**：模型在 OpenHands 上的高分可能部分反映對該腳手架提示、工具命名與回合結構的過擬合（overfitting）。
- **部署風險**：實務上選擇腳手架的理由是成本、授權、延遲與隱私，而非訓練資料來源；當模型遷移到其他腳手架時性能下降，削弱了微調的實用價值。

DCAS 的貢獻在於打破這種單一腳手架壟斷，使研究者能夠系統性地比較同一後端模型在不同腳手架下的行為，並收集多樣化訓練資料。

##### 2. 與規劃相關研究的關係
Liu 等人先前在大量 CLI 代理軌跡中發現，計畫品質與計畫遵循度是解決率的主要驅動因素（primary driver）。本文在此基礎上進一步：
- 將「規劃」操作化為顯式與隱式兩個層次；
- 透過 DCAS 設計可控制的規劃來源介入，而非僅做相關性分析；
- 證明規劃能力可透過微調內化，並泛化到未見腳手架。

相較於傳統的 Plan-and-Solve、ReAct、Reflexion 等強調「讓模型在單一框架內做規劃」的研究，DCAS 更關注**規劃與腳手架慣例的分離**，這是代理系統可攜性（portability）的關鍵一步。

##### 3. 與腳手架設計研究的對比
Claude Code 與 OpenCode 將顯式規劃階段內建於腳手架；mini-swe-agent 則刻意極簡，無專屬規劃階段。過去研究多將這些設計視為腳手架特性，並比較其最終性能。DCAS 則提供了一個統一視角：無論腳手架是否暴露規劃階段，都可以把後端模型替換出來，並觀察模型在相同腳手架下因規劃訓練而產生的行為變化。這把腳手架研究從「哪個腳手架最好」轉向「腳手架教會了模型什麼」。

##### 4. 本文的侷限
儘管概念新穎，仍有幾點值得注意：
- **API 攔截的完整性**：DCAS 能否完整捕捉所有腳手架內部狀態（如 Claude Code 的私有上下文管理、工具呼叫協議）？若某些關鍵資訊未透過 API 流量暴露，則跨腳手架評估可能仍有殘留偏差。
- **後端模型能力下限**：實驗使用的模型規模為 32B，對於更小或更大的模型，規劃內化與泛化的效果可能不同。
- **任務範圍**：研究聚焦 SWE-bench Verified 類型的軟體工程任務，對於需要長期規劃或多檔案協調的更複雜任務，結論是否成立仍需驗證。
- **顯式與隱式的邊界**：雖然作者宣稱兩者可分，但在某些腳手架中，顯式計畫可能會被改寫或隱含於系統提示中，界線未必總是清晰。

#### 可重現性評估

##### 1. 開源釋出的潛力
DCAS 作為一個後端替換攔截層，理論上可以獨立開源為一個代理中間件。若作者釋出：
- DCAS 攔截與路由程式碼；
- 規劃感知軌跡資料集（planning-aware trajectory dataset）；
- 微調後的模型權重（model weights）；
- 跨腳手架評估腳本與設定檔；

則本研究的可重現性（reproducibility）將相當高，因為 SWE-bench Verified、OpenHands、OpenCode、mini-swe-agent 等皆為公開資源。

##### 2. 專有元件造成的限制
然而，研究涉及 Claude Code 這類閉源腳手架，以及可能使用的 Anthropic 或 OpenAI 專有模型。這會帶來以下重現障礙：
- **API 存取權限**：Claude Code 的後端替換可能需要逆向工程其內部 API，或依賴特定授權的企業 API；一般研究者未必能輕易複製。
- **成本與延遲**：跨腳手架評估需要多次呼叫大型語言模型，SWE-bench Verified 的完整評估成本高昂。
- **版本漂移**：腳手架與模型 API 持續更新，DCAS 的攔截邏輯需要隨之維護，否則重現結果會因版本差異而改變。

##### 3. 資料與模型權重
從提供的摘要與引言中，並未明確說明是否公開釋出資料與權重。若僅釋出方法論與部分實驗設定，則其他研究者雖可依照描述重建 DCAS，但難以完全複製訓練軌跡與模型檢查點。建議作者提供：
- 軌跡資料的元資料與範例，說明如何標註顯式計畫與隱式結構；
- 微調所用的超參數與資料配比；
- 各腳手架版本的確切 commit 或發行版本號。

##### 4. 評估環境
由於跨腳手架評估涉及多個異質系統，建議提供容器化（containerized）的評估環境，例如 Docker 映像檔，內含已配置好的 OpenHands、OpenCode、mini-swe-agent 與 DCAS 代理，以降低環境設定的門檻。

#### 未來研究方向

##### 1. 多腳手架聯合微調
本文已證明單一腳手架下的規劃感知軌跡可泛化到非訓練腳手架。下一步可探討**同時在多個腳手架下收集軌跡並聯合微調**，是否能進一步縮小跨腳手架差距，甚至達到「腳手架無關」的模型行為。這涉及資料配比、腳手架特定提示的去偏、以及如何避免多腳手架間的衝突。

##### 2. 主動式與選擇性軌跡收集
DCAS 使得在任何腳手架下收集資料成為可能，但未來可結合主動學習（active learning）或困難樣本採樣，優先收集那些最能補足模型規劃弱點的軌跡。例如，針對模型在特定腳手架上計畫遵循度低的任務，動態生成更多規劃感知訓練樣本。

##### 3. 強化學習與規劃內化
目前研究使用監督式微調（supervised fine-tuning）。未來可探索以強化學習（reinforcement learning）直接優化跨腳手架解決率，讓模型在執行過程中學習何時堅持計畫、何時重新規劃，從而更深入地內化隱式規劃。

##### 4. 規劃能力的可解釋性分析
顯式規劃相對容易解釋，但隱式規劃仍較為黑箱。未來研究可利用探針（probing）、注意力視覺化或因果介入方法，分析模型在代理迴圈各回合中如何編碼計畫、如何根據觀察調整結構，從而驗證隱式規劃確實被學習而非僅是表面格式模仿。

##### 5. 擴展至非 CLI 代理
DCAS 專注於 CLI 腳手架，但其解耦思想可擴展至 GUI 代理、API 代理或多模態代理。未來可設計類似的後端替換層，研究規劃在網頁操作、機器人控制或科學實驗代理中的跨腳手架轉移。

##### 6. 標準化規劃交換格式
若顯式規劃能成為一等公民產物（first-class artifact），社群可推動跨腳手架的規劃交換格式（如標準化的計畫結構、依賴關係與驗證點）。DCAS 可作為此標準的測試平台，評估不同腳手架對同一計畫的執行一致性。

##### 7. 成本效益與部署最佳化
跨腳手架評估與訓練涉及大量模型呼叫，未來可研究如何在保持規劃品質的前提下減少 token 消耗、降低延遲，並針對不同部署場景（邊緣裝置、私有雲、公有 API）選擇最適腳手架與模型組合。

##### 8. 動態腳手架適應
最終願景是讓模型在部署時能自動適應新腳手架的慣例，而無需重新微調。這可能需要結合少樣本提示（few-shot prompting）、元學習（meta-learning）或線上適應（online adaptation），使代理具備「讀懂腳手架規則並調整規劃風格」的能力。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文指出，開放生態系統中的 CLI 軟體工程代理幾乎都在 OpenHands 這單一腳手架下收集訓練軌跡，導致微調後的模型在 OpenHands 上表現很好，但部署到其他非訓練腳手架時性能明顯下降。更有趣的是，未經微調的基礎模型並沒有這種落差，因此問題根源不在模型能力，而在微調過程中學到的腳手架特定慣例。作者認為這個落差嚴重限制了模型在不同部署環境間的通用性與可攜性。

**Q2：為什麼這個問題在實務上很重要？**
A：實務工作者選擇 CLI 腳手架時，通常依據成本、授權、延遲與資料隱私等條件，而不是因為某個模型剛好在該腳手架上被微調過。如果模型只能在訓練時的腳手架上正常運作，那麼企業或研究人員就會被綁定在特定框架，無法靈活切換到更適合自身需求的腳手架。因此，讓模型學到可跨腳手架轉移的規劃能力，對開放生態系統的發展至關重要。

**Q3：現有的方法或資料集為什麼無法解決這個問題？**
A：現有的公開軌跡資料集幾乎都在單一腳手架下收集，並且把規劃與執行過程混雜在一起，難以分離出可轉移的規劃行為。此外，具備豐富規劃行為的腳手架通常與專有後端模型緊密耦合，無法輕易替換成其他模型進行對照實驗。目前也缺乏通用的基礎設施來進行跨腳手架評估，因此研究者難以系統性地診斷與縮小性能落差。

**Q4：DCAS 的核心機制是什麼？**
A：DCAS 是一個後端替換攔截層，能夠在不修改腳手架原始碼的前提下，攔截並重新路由腳手架與後端模型之間的 API 流量。這意味著任何 CLI 腳手架都可以搭配任何後端模型運作，讓研究者能在保持目標腳手架完整慣例介面的情況下，測試同一個模型在不同環境中的表現。透過這種解耦，DCAS 同時支援跨腳手架評估與規劃感知軌跡收集。

**Q5：DCAS 的關鍵創新在哪裡？**
A：DCAS 的關鍵創新在於把「腳手架」與「後端模型」這兩個原本緊密耦合的層次分開，讓腳手架的對話管理、工具結構與回合慣例得以保留，同時自由替換背後的語言模型。這不僅讓研究者能進行嚴謹的對照實驗，也讓規劃感知軌跡可以在原本無法觸及的專有風格腳手架下收集。換句話說，DCAS 把「部署環境」轉變成可觀察、可操控的實驗變因，而非固定的限制條件。

**Q6：論文為什麼要區分「顯式規劃」與「隱式規劃」？**
A：顯式規劃指的是執行前產生一個作為一等公民產物的計畫，例如 Claude Code 的 Plan Mode；隱式規劃則是腳手架在每一回合強加的結構慣例，例如工作如何分解、何時從探索轉向行動、工具呼叫如何排序等。兩種規劃都會因腳手架而異，而微調會讓模型學到訓練腳手架特有的混合形式。區分兩者有助於判斷哪一種規劃行為可以透過訓練內化為模型能力，並進一步分離它們在資料中的貢獻。

**Q7：論文設計了哪些研究問題與實驗來驗證假設？**
A：論文提出三個研究問題：RQ1 透過規劃來源介入，探討顯式規劃品質是否會影響任務性能；RQ2 比較「僅用計畫」與「計畫加執行」兩種訓練資料，測試兩種規劃意義分別能被學到什麼程度；RQ3 則檢驗學到的規劃能力能否泛化到模型在訓練時從未見過的腳手架。這三個問題層層遞進，從單一因素控制逐步推向跨腳手架轉移。

**Q8：實驗的主要結果是什麼？**
A：對照式的規劃來源介入顯示，規劃品質是一個高槓桿元件，其帶來的提升甚至超過觀察到的跨腳手架性能下降。此外，僅用少量在單一腳手架下透過 DCAS 收集的規劃感知軌跡進行微調，模型就能在多個非訓練腳手架上獲得一致進步。實驗也證明顯式規劃與隱式規劃在訓練資料中是經驗上可區分的，兩者對模型行為的影響可以被分開檢視。

**Q9：有哪些對照或消融實驗支持這些結論？**
A：在 RQ1 中，研究者固定執行模型與腳手架，只改變計畫的來源，從而孤立出規劃本身對性能的貢獻。在 RQ2 中，透過比較 plan-only 與 plan-and-execution 兩種訓練組合，能夠判斷模型學到的是顯式計畫結構、隱式執行慣例，還是兩者的混合。在 RQ3 中，則是在 OpenHands、Claude Code、OpenCode 與 mini-swe-agent 等結構差異明顯的腳手架上進行評估，以驗證學得能力的泛化性。

**Q10：DCAS 在實務上可以應用在哪些場景？**
A：企業可以在內部選擇符合成本、授權與隱私需求的 CLI 腳手架，同時部署同一個經過微調的開源模型，而不必受限於模型原本的訓練環境。研究團隊也能利用 DCAS 在目標腳手架下收集規劃感知軌跡，進行針對性的微調與評估。對於需要多腳手架並存的組織而言，DCAS 提供了一個統一的後端替換與資料收集基礎設施。

**Q11：在產品化或部署時需要考慮哪些因素？**
A：首先必須確保 API 攔截與路由不會破壞腳手架原有的工具呼叫格式、回合管理與錯誤處理邏輯。其次，額外的攔截層可能帶來延遲與除錯複雜度，需要在效能與彈性之間取捨。最後，當後端模型涉及外部服務時，還必須考量資料隱私、授權合規以及請求流量的安全控管。

**Q12：這項研究對整個領域可能帶來什麼影響？**
A：這項研究把焦點從「針對特定腳手架微調」轉向「把規劃內化為模型能力」，有助於發展出更通用、可攜的軟體工程代理。它也鼓勵未來的訓練資料集涵蓋更多樣的腳手架與規劃形式，而非持續集中在單一環境。長遠來看，DCAS 這類解耦基礎設施可能成為評估與比較不同 CLI 代理的標準工具。

**Q13：論文承認了哪些限制？**
A：研究目前只涵蓋四個腳手架，雖然它們在設計光譜上具有代表性，但仍無法涵蓋所有可能的 CLI 代理框架。此外，實驗中使用的 DCAS 規劃感知軌跡數量相對較小，規模效應仍有待進一步驗證。攔截層本身的實作與維護也需要隨著腳手架版本更新而持續調整。

**Q14：在什麼情況下，DCAS 訓練出的模型可能仍然失敗？**
A：如果目標腳手架的隱式規劃慣例與訓練資料中的任何腳手架都截然不同，模型可能難以正確推斷其回合結構與工具使用方式。極度簡化的腳手架，例如僅有 bash 互動、沒有結構化工具呼叫的 mini-swe-agent，會對轉移能力構成嚴峻考驗。此外，若任務高度依賴某個腳手架專有的工具行為或環境狀態，單靠規劃內化可能仍不足以彌補差距。

**Q15：未來可以朝哪些方向延伸這項研究？**
A：未來可以擴大規劃感知軌跡資料集的規模，並納入更多樣化的開源與商業腳手架，以進一步驗證泛化性。也可以發展自動化的規劃標註與課程學習方法，讓模型系統性地學習從顯式到隱式的各種規劃形式。除此之外，把 DCAS 的解耦思路延伸到 GUI 代理或 API 代理，並探索不同規劃訓練課程的組合，也是值得發展的方向。

## 實務應用指南

## 適用場景

**1. 多腳手架企業部署**
組織內部因團隊、授權或資料隱私限制而混用 OpenHands、Claude Code、OpenCode 等不同 CLI 腳手架時，可利用 DCAS 的後端替換攔截層，讓同一個微調後的後端模型在不同腳手架下維持穩定表現，避免「只在 OpenHands 上表現好、換到內部腳手架就大幅下降」的問題。

**2. 後端模型供應商遷移**
當企業需要從某一模型供應商切換到另一供應商（例如因成本、延遲或授權變更），DCAS 可在不修改現有腳手架的前提下重新路由 API 流量，並透過規劃感知軌跡收集快速產生新後端模型所需的微調資料，降低遷移成本。

**3. 專有腳手架的規劃感知資料收集**
部分功能強大的腳手架（如 Claude Code）原本緊密綁定專有後端模型。DCAS 能將其 API 流量攔截並導向其他開源模型，從而收集該腳手架下的顯式規劃與隱式規劃軌跡，供內部模型訓練使用。

**4. 腳手架選型與跨腳手架評估**
工程團隊在評估要採用哪個 CLI 腳手架時，可透過 DCAS 控制後端模型保持一致，單獨比較不同腳手架對解析率的影響，排除「模型差異」帶來的混淆因素。

**5. 以規劃為核心的訓練資料建構**
對於希望提升模型策略規劃能力的團隊，DCAS 支援在單一或多個腳手架下收集同時包含顯式規劃（執行前計畫）與隱式規劃（代理迴圈結構慣例）的軌跡資料集，用於訓練更具泛化能力的軟體工程代理。

## 實作前置條件

**資料條件**
- 可取得至少一個目標 CLI 腳手架的執行環境（OpenHands、OpenCode、mini-swe-agent 等）。
- 具備現有軌跡資料或能夠執行規劃感知軌跡收集的基礎設施。
- 若進行跨腳手架評估，需準備標準化評測集（如 SWE-bench Verified）與對應的實例執行環境。

**運算條件**
- 後端模型推理端點：可為商業 API 或自建推理服務（如 vLLM、TGI）。
- 微調運算資源：針對 32B 規模開源模型，需配備足夠 GPU 記憶體的叢集（例如多張 A100/H100）以執行監督式微調。
- 軌跡收集與評估需可並行執行多個代理實例，建議具備容器化排程能力（Kubernetes 或類似方案）。

**技能條件**
- 熟悉 CLI 代理的代理迴圈、工具呼叫格式與多輪對話結構。
- 具備 API 攔截與路由的開發經驗，能處理不同腳手架間的請求/回應格式轉換。
- 具備監督式微調與 SWE-bench 評測實作經驗。
- 能理解顯式規劃與隱式規劃的區別，並據此設計訓練資料。

## 實作步驟建議

**步驟一：部署 DCAS 後端替換攔截層**
在目標腳手架與後端模型之間部署 DCAS，設定 API 流量路由規則，使腳手架以為它正在與原廠後端通訊，實際上由 DCAS 轉發至指定模型。此階段不應修改腳手架本身。

**步驟二：驗證腳手架慣例表面完整性**
確認攔截後的腳手架仍保留完整慣例表面，包括工具綱要、對話結構、計畫階段觸發條件等。可透過少量 SWE-bench 實例比較攔截前後的行為一致性。

**步驟三：設計規劃感知軌跡收集策略**
決定要收集的規劃類型：若目標是顯式規劃，優先選用具有專用計畫階段的腳手架（如 OpenCode）；若目標是隱式規劃，則需記錄代理迴圈中每回合的決策結構。DCAS 應同時擷取計畫內容與執行軌跡。

**步驟四：執行對照規劃來源介入實驗**
在固定後端模型與腳手架下，進行規劃來源介入（例如使用人工計畫、模型計畫、無計畫），量化規劃品質對解析率的影響，確認規劃是否為高槓桿元件。

**步驟五：微調模型並分離兩種規劃訊號**
分別訓練「僅計畫」與「計畫加執行」兩種資料組合，觀察模型習得的是顯式規劃能力、隱式規劃慣例，還是單純記憶特定腳手架行為。

**步驟六：跨腳手架評估泛化能力**
將微調後的模型透過 DCAS 部署到訓練時未見過的腳手架，使用相同評測集比較解析率，驗證規劃能力是否真正內化為模型能力，而非腳手架特定記憶。

**步驟七：產品化部署與持續監控**
將 DCAS 整合至 CI/CD 或內部開發平台，持續監控不同腳手架下的解析率、延遲與成本，並定期回補規劃感知軌跡以迭代模型。

## 潛在風險與注意事項

**腳手架慣例錯配**
即使後端模型相同，不同腳手架的結構慣例仍可能導致效能下降。建議在微調資料中納入多個腳手架的規劃感知軌跡，而非僅依賴單一訓練腳手架。

**API 格式與狀態管理不相容**
部分腳手架對工具呼叫順序、錯誤處理或上下文長度有隱含假設。DCAS 需完整模擬原廠後端的行為，否則可能破壞代理迴圈。實作時應建立格式轉換測試與回歸驗證。

**過度擬合特定規劃風格**
若訓練資料過度集中於某一腳手架的計畫格式，模型可能學會「模仿格式」而非「學會規劃」。可透過混合多腳手架資料與計畫來源介入實驗來診斷並緩解。

**評估偏差與資料外洩**
使用 SWE-bench 進行跨腳手架評估時，需嚴格區分訓練與測試實例，避免軌跡收集過程中無意間洩漏測試集資訊。同時應報告多個隨機種子或切分的結果。

**攔截層引入的延遲與成本**
DCAS 作為中間層會增加額外網路跳躍與格式轉換開銷。在產品化部署時應評估延遲影響，必要時將 DCAS 與後端模型部署於同一區域或同一叢集內。

**資料隱私與授權風險**
攔截專有腳手架（如 Claude Code）的流量可能涉及服務條款限制。企業應先確認授權範圍，並在內部可控環境中執行，避免將敏感程式碼流經未經授權的第三方端點。

## 與其他技術的整合建議

**CI/CD 與程式碼審查流程**
將 DCAS 路由後的 CLI 代理整合至持續整合管線，讓同一模型在提交前自動於不同腳手架下執行測試，並將規劃品質與計畫遵循度納入審查指標。

**模型服務基礎設施**
DCAS 可與 vLLM、Text Generation Inference 或商業 API 閘道並置，透過統一的路由層動態切換後端模型，實現依成本、延遲或資料隱私限制的自動模型選擇。

**可觀測性與軌跡儲存**
將 DCAS 攔截到的規劃感知軌跡寫入資料湖或軌跡資料庫，結合追蹤工具（如 OpenTelemetry）分析顯式規劃與隱式規劃在實際執行中的表現，作為後續微調的資料來源。

**現有代理框架**
對於已使用 OpenHands 或 OpenCode 的團隊，DCAS 可作為無縫橋接層，無需重寫腳手架即可試驗新後端模型；對於自研腳手架，DCAS 提供標準化的 API 適配介面，降低整合新模型的工程負擔。

**資料標註與品質管線**
將 DCAS 收集的軌跡接入人工或自動標註流程，特別針對計畫品質與計畫遵循度進行評分，以建立高品質的規劃感知訓練資料集。

## 給不同背景讀者的閱讀建議

**給初學者**
建議先聚焦於論文的動機與核心概念：為什麼微調後的模型換個腳手架就變差、什麼是顯式規劃與隱式規劃，以及 DCAS 如何像「轉接頭」一樣讓不同 CLI 腳手架都能使用同一個後端模型。不必一開始就深入 API 攔截或微調細節，重點是理解「規劃應該成為模型能力，而非腳手架的固定產物」這一主張。

**給 AI 工程師**
請著重閱讀 DCAS 的後端替換攔截層設計、規劃來源介入實驗的實作方式，以及「僅計畫」與「計畫加執行」兩種訓練資料組合如何影響模型行為。這些內容直接關係到如何在自己的微調管線中複現跨腳手架泛化效果，並可借鏡其格式轉換與狀態管理經驗。

**給研究人員**
本論文的核心貢獻在於區分顯式規劃與隱式規劃，並以對照實驗驗證兩者在訓練資料中經驗上可區分。建議深入分析三個研究問題的設計、跨腳手架評估的控制變因，以及論文如何論證規劃品質是解析率的主要驅動因素。這些設計對於未來研究代理泛化與腳手架解耦具有參考價值。

**給產品經理**
本研究的最大商業意義在於打破「訓練腳手架等於部署腳手架」的限制，讓企業能依成本、授權、延遲與資料隱私選擇最適合的 CLI 腳手架，而不必受限於模型原本的訓練環境。閱讀時可關注跨腳手架性能下降的幅度、規劃感知微調所需的資料量，以及這些數據如何支撐投資內部模型微調與 DCAS 基礎設施的決策。
