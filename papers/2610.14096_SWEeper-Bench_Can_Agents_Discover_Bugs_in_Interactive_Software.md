# SWEeper-Bench：代理能否在互動式軟體中發現錯誤？

**原文標題：** SWEeper-Bench: Can Agents Discover Bugs in Interactive Software?  
**作者：** Yang Yao、Haozhe Chen、Bingyi Kang 等 5 位作者  
**發布日期：** 2026-10-08

## ⚡ TL;DR

現有基準假設錯誤已被發現，無法評估代理自主發現互動相依性錯誤的能力。
本文提出 SWEeper-Bench 基準，含 200 個真實網頁任務，以代理驗證器透過瀏覽器評判。
最佳前沿代理僅通過 59.0%，瓶頸在錯誤發現：觸及功能 75.4%，但僅 50.0% 能辨識錯誤。

## 摘要翻譯

程式碼代理（Coding Agent）越來越多地透過即興生成互動式軟體（Interactive Software）來與使用者互動，而非以文字回覆，然而此類軟體中的許多錯誤僅在多步互動（Multi-step Interaction）後才會顯現。如今，使用者必須自行發現這些錯誤並等待修復，使得開發迴圈既緩慢又昂貴。現有的基準測試（如 SWE-bench）通常假設錯誤已被識別，使得代理尋找互動相依性錯誤（Interaction-dependent Failure）的能力幾乎未被評估。我們提出 SWEeper-Bench，包含 200 個任務，這些任務基於 200 個廣泛使用的開源網頁應用程式（Open-source Web Application）中的真實錯誤修復（Bug Fix）所建構。每個任務僅向代理提供程式碼庫（Codebase）與一個開放式請求（Open-ended Request），例如「找出並修復 Focalboard 看板分享與成員管理的問題」。由於這些錯誤難以僅從程式碼中偵測，代理必須設計互動式測試來揭露它們。接著由代理式驗證器（Agentic Verifier）根據使用者在瀏覽器中會觀察到的內容來判斷每個修復。在 15 個前沿代理（Frontier Agent）中，表現最好的僅通過 59.0% 的任務。透過對代理軌跡（Trajectory）進行階段式分析（Stage-by-stage Analysis），我們發現最大的瓶頸（Bottleneck）在於識別錯誤行為（Buggy Behavior）：代理雖然經常觸及相關功能，但從未觸發錯誤或無法辨識錯誤。SWEeper-Bench 衡量代理在以下方向上的進展：自行完成此迴圈，交付無需等待使用者回饋即可正常運作的軟體。

### 核心貢獻（3～5點）
- 提出 SWEeper-Bench 基準測試，涵蓋 200 個源自真實開源網頁應用程式之錯誤修復的任務，專門評估代理在互動式軟體中主動發現錯誤的能力。
- 採用開放式請求設計，僅提供程式碼庫與自然語言指令，迫使代理必須自行設計互動式測試以揭露互動相依性錯誤，而非依賴預先標註的錯誤位置。
- 引入代理式驗證器機制，根據使用者在瀏覽器中實際觀察到的行為來判斷修復是否通過，更貼近真實使用情境。
- 透過對 15 個前沿代理的階段式軌跡分析，揭示當前代理的主要瓶頸在於「識別錯誤行為」而非「觸及相關功能」，為未來研究指明改進方向。
- 實證結果顯示最佳代理僅通過 59.0% 的任務，凸顯互動式軟體之錯誤發現與修復仍是一項極具挑戰性的任務。

### 適合對象
- 研究 AI 代理（Agent）、程式碼生成與軟體工程之學者與研究生
- 從事基準測試（Benchmark）設計與評估方法論的研究人員
- 開發程式碼代理、IDE 整合工具（如 Cursor、Claude Code、Codex）之工程團隊
- 關注 LLM 實際應用於真實軟體開發流程的產業從業者與技術決策者

## 深度分析

#### 方法論解析

SWEeper-Bench 的方法論核心在於重新定義「程式碼代理評測」的問題邊界——從「修復已知錯誤」轉向「發現未知錯誤」。這個轉變具有深層的方法論意涵。

**任務建構流程（Task Curation Pipeline）**

論文採用「真實錯誤修復回溯法」（Real Bug Fix Retrofitting）建構基準。每個任務源自一個已合併的拉取請求（Pull Request, PR），其中父提交（parent commit）為錯誤版本，合併修復為參考解答。這種設計避免了合成錯誤（synthetic bugs）的人為偏差，因為開發者實際修復的錯誤往往具有非平凡的邏輯複雜度。具體而言：

1. **單一應用程式單一任務原則**：200 個任務對應 200 個不同的開源網頁應用程式，中位數倉庫擁有 4.6k GitHub stars，確保任務的多樣性與真實代表性。
2. **錯誤選擇標準**：選擇「難以察覺但一旦看見即明顯」的錯誤——可透過正常使用重現，且任何使用者都會認同需要修復。這排除了主觀爭議性的設計缺陷。
3. **互動相依性過濾**：僅選取需要多步驟使用者互動才能顯現的錯誤，例如 Focalboard 的案例需要 9 個步驟跨越兩個帳號才能觸發。這確保了基準測試的區辨力（discriminative power）。

**代理輸入設計（Agent Input Design）**

代理僅接收三項資源：
- 完整的程式碼庫（codebase）
- 運行中的應用程式（含瀏覽器存取）
- 開放式請求（open-ended request），僅標示產品區域名稱

這種「最小資訊原則」刻意排除原始 issue、PR 描述、參考補丁、倉庫歷史與行為測試，迫使代理必須自主探索。開放式請求的設計（例如「Find and fix issues in Focalboard's board sharing and membership」）模擬了真實使用情境——使用者通常只會描述功能區域而非具體錯誤。

**代理式驗證器（Agentic Verifier）**

驗證機制是本基準最具創新性的元件。傳統 SWE-bench 使用隱藏單元測試（hidden unit tests）檢查內部狀態，但這會拒絕採用不同實作路徑的合法修復。SWEeper-Bench 改採「使用者可觀察行為」標準：

- 驗證器在沙盒（sandbox）中套用代理的補丁至全新應用程式副本
- 透過 Playwright/Chromium 執行預定義的行為測試
- 僅評判使用者介面中可觀察的結果

驗證器本身由 LLM 驅動（GPT-5.6 Luna 或 Claude Sonnet 5），搭配 Codex 或 Browser Use 工具。表 1 的驗證器準確性數據顯示：目標測試在錯誤版本上通過率為 0.2–0.8%，在參考修復上為 99.2–100.0%，證實驗證器具有高鑑別度與一致性。

**階段式軌跡分析（Stage-by-stage Trajectory Analysis）**

論文提出一個關鍵的診斷框架，將代理行為分解為兩個階段：
1. **到達特徵階段（Reaching the Feature）**：代理是否定位到包含錯誤的功能模組
2. **識別錯誤行為階段（Identifying the Buggy Behavior）**：代理是否觸發並辨識出失敗

這個分解揭示了瓶頸所在：75.4% 的軌跡到達了正確特徵，但僅 50.0% 識別出錯誤行為。這種「接近但未觸發」的失敗模式是互動式錯誤發現的核心挑戰。

#### 實驗數據解讀

**整體效能數據**

15 個前沿代理（frontier agents）中，最佳者僅通過 59.0% 的任務，9 個代理通過率低於 50%。這個數字在表面上似乎偏低，但需要放在正確的脈絡下理解：

- 當代理被給予詳細的錯誤描述（而非開放式請求）時，5 個測試代理的通過率約為 96%。這證明任務本身是可解的，瓶頸確實在於「發現」而非「修復」。
- 59.0% vs 96% 的差距（約 37 個百分點）量化了「發現成本」——這是從診斷修復到主動發現的代價。

**瓶頸的階段性分析**

軌跡分析揭示了兩個關鍵數據點：
- **75.4% 到達率**：代理具備足夠的程式碼理解與導航能力，能定位到相關功能模組
- **50.0% 識別率**：在已到達的軌跡中，僅約三分之二能成功觸發並辨識錯誤

這意味著即使代理「知道在哪裡找」，仍有約 25% 的軌跡完全失敗於發現階段。這指向一個具體的能力缺口：**互動式測試設計能力**。代理需要具備「假設驅動的探索行為」（hypothesis-driven exploration）——形成關於「可能出錯的地方」的假設，設計互動序列來驗證，並從觀察中辨識異常。

**瀏覽器使用率偏低**

論文指出代理「很少透過瀏覽器進行測試，除非被明確指示」。這是一個重要的行為觀察：代理傾向於靜態程式碼分析而非動態互動測試。這反映了當前 LLM 代理訓練資料中，程式碼理解任務遠多於互動式除錯任務的偏差。

**驗證器成本與可靠性**

表 1 顯示驗證器每次任務成本從 $0.160 到 $3.840 不等，差異約 24 倍。這反映了不同模型組合的取捨：
- GPT-5.6 Luna + Codex：$0.160，最經濟
- Claude Sonnet 5 + Browser Use：$3.840，最昂貴但達到 100.0% 的一致性

成本差異對大規模評測的可行性有實質影響。

**領域分佈的隱含資訊**

200 個任務分佈於 7 個領域（圖 4）：
- 內容與知識：40
- IT、安全與開發工具：35
- 協作與通訊：31
- 檔案、媒體與分享：29
- 金融與商業：28
- 個人與生活風格：22
- 商務與支付：15

這種分佈反映了真實開源生態的權重，但也意味著某些領域（如商務與支付）的統計檢驗力較低。

#### 與現有研究的比較

**與 SWE-bench 系列的定位差異**

SWE-bench（Jimenez et al., 2024）及其後續工作（Yang et al., 2025; Rashid et al., 2025; Deng et al., 2025; Zan et al., 2025; Zhang et al., 2025）共享一個基本假設：錯誤已被使用者報告並以 issue 形式提供。這些基準測量的是「診斷與修復」（diagnosis and repair）能力，而非「發現」（discovery）能力。

SWEeper-Bench 的關鍵創新在於**取消了錯誤描述的輸入**。這看似微小的改變，實際上重新定義了任務的認知需求：
- SWE-bench：閱讀錯誤描述 → 定位程式碼 → 修復
- SWEeper-Bench：理解功能區域 → 形成假設 → 設計互動測試 → 觸發錯誤 → 辨識錯誤 → 修復

後者增加了「假設生成」與「實驗設計」兩個認知階段，這對當前以靜態分析為主的代理是重大挑戰。

**驗證機制的改進**

SWE-bench 使用隱藏單元測試存在兩個問題：
1. **路徑依賴性**：測試可能拒絕功能正確但實作不同的修復
2. **內部狀態偏誤**：測試檢查內部變數而非使用者體驗

SWEeper-Bench 的代理式驗證器透過「使用者可觀察行為」標準解決了這兩個問題。任何能讓使用者在瀏覽器中觀察到正確行為的修復都會通過，這更接近真實的軟體品質標準。

**與互動式軟體生成研究的關聯**

論文引言中描述的場景——「助手為團隊活動建立小型應用程式並分享給二十位同事」——呼應了近期關於 LLM 生成完整應用程式的研究（如 GPT-Engineer、Devin 等）。SWEeper-Bench 為這類系統提供了首個系統性的品質評測框架。

**限制與未涵蓋面向**

1. **僅限網頁應用程式**：基準排除了行動應用、桌面應用、命令列工具等互動式軟體。這限制了結論的泛化性。
2. **僅限開源專案**：商業軟體中的錯誤模式可能不同，特別是涉及付費功能、權限管理的錯誤。
3. **單一錯誤假設**：每個任務評估一個目標錯誤，雖然代理可修復多個問題，但基準無法捕捉「錯誤叢集」（bug clusters）的發現能力。
4. **語言偏差**：200 個任務可能集中於 JavaScript/TypeScript 生態，未涵蓋 Python、Ruby 等後端語言的互動式錯誤。

#### 可重現性評估

**正面因素**

1. **任務來源透明**：每個任務源自真實的開源 PR，提交歷史可追溯
2. **驗證器規格明確**：表 1 提供了具體的模型組合與成本數據
3. **執行環境標準化**：使用 Playwright + Chromium + Node.js，跨平台可重現

**可重現性疑慮**

1. **驗證器的隨機性**：使用 LLM 作為驗證器引入了非確定性。雖然表 1 報告了三次執行的標準差（多在 ±0.3% 內），但代理本身的隨機性可能放大這個問題。
2. **應用程式狀態依賴**：許多網頁應用程式需要特定狀態（資料庫、檔案系統、外部服務）才能運行。論文未詳細說明如何處理這些依賴。
3. **瀏覽器版本敏感性**：不同版本的 Chromium 可能對前端行為的渲染有細微差異。
4. **代理版本綁定**：測試的 15 個代理是特定時間點的版本，隨著模型更新，結果可能無法直接比較。

**資料集與程式碼可用性**

論文未明確聲明資料集與程式碼的開源狀態，但基於學術慣例與 SWE-bench 的先例，預期會釋出：
- 200 個任務的定義檔案
- 沙盒環境配置
- 驗證器實作

**基準的長期維護**

互動式軟體的錯誤模式會隨技術演進而變化（例如 Web Components、Server-Side Rendering 的新錯誤類型）。基準需要持續更新才能保持相關性，這對長期可重現性是挑戰。

#### 未來研究方向

**1. 互動式測試生成的演算法改進**

最直接的改進方向是增強代理的「假設驅動探索」能力。可能的研究路徑包括：
- **基於風險的優先排序**：訓練代理優先測試高風險的程式碼路徑（如權限檢查、狀態轉換）
- **對抗性測試策略**：借鑑模糊測試（fuzzing）思想，自動生成邊界輸入
- **多代理協作**：一個代理生成假設，另一個代理執行測試，形成「假設-驗證」迴圈

**2. 錯誤發現的認知模型**

75.4% 到達率與 50.0% 識別率之間的差距，暗示需要更深入理解「錯誤辨識」的認知過程。未來研究可探索：
- 代理如何從「正常行為」中區辨「異常行為」
- 視覺化呈現（截圖、影片）是否能提升錯誤辨識準確率
- 代理是否能學習「錯誤的典型症狀」（如空白頁面、錯誤訊息、狀態不一致）

**3. 基準的擴展與多樣化**

- **跨平台覆蓋**：擴展至行動應用（React Native、Flutter）、桌面應用（Electron）、CLI 工具
- **錯誤類型多樣化**：當前基準可能偏向「功能性錯誤」，未涵蓋「效能錯誤」、「安全性錯誤」、「可訪問性錯誤」
- **多錯誤任務**：設計需要同時發現並修復多個相關錯誤的任務，更接近真實除錯情境

**4. 驗證器的理論基礎**

代理式驗證器雖然實用，但缺乏形式化保證。未來研究可：
- 形式化定義「使用者可觀察行為」的語義
- 結合符號執行（symbolic execution）與 LLM 推理的混合驗證
- 研究驗證器的對抗穩健性（adversarial robustness）

**5. 從發現到預防**

SWEeper-Bench 測量「發現後修復」，但終極目標是「預防錯誤發生」。可能的研究方向：
- 在程式碼生成階段引入錯誤預防機制
- 結合形式化驗證（formal verification）與 LLM 的混合方法
- 從歷史錯誤資料庫學習「錯誤模式」並在生成時主動避免

**6. 人機協作除錯**

當前基準假設代理獨立完成所有工作，但真實情境中，使用者可以提供回饋。未來可探索：
- 互動式基準：代理可向使用者詢問澄清問題
- 主動回報機制：代理識別可疑行為時主動詢問使用者確認
- 漸進式修復：代理先修復明確的錯誤，再針對模糊的錯誤尋求確認

**7. 經濟與可持續性分析**

驗證器成本差異達 24 倍，這對大規模部署有實質影響。未來研究應：
- 量化「發現成本」與「使用者等待成本」的經濟權衡
- 探索成本效益最佳的代理-驗證器組合
- 研究錯誤發現的投資回報率（ROI）模型

SWEeper-Bench 的真正貢獻不僅是 200 個任務，而是重新定義了問題：「代理能否在使用者之前發現錯誤？」這個問題的答案將決定未來軟體開發的人機分工模式。

## 論文問答

**Q1：SWEeper-Bench 試圖解決的核心問題是什麼？**
A：SWEeper-Bench 聚焦於互動式軟體中一類特別難處理的錯誤——這些錯誤只有在使用者完成特定的多步驟互動後才會顯現，例如共享的看板從未出現在協作者的側邊欄，或購物車中接受的優惠券在結帳時被拒絕。這類錯誤無法單純從程式碼靜態分析中察覺，必須實際操作軟體才能觸發。傳統上，這些錯誤仰賴使用者在真實使用情境中「親身踩到」後回報，使得開發迴圈變得緩慢且昂貴。

**Q2：為什麼現有的 SWE-bench 等基準測試無法有效評估「發現錯誤」的能力？**
A：SWE-bench 及其後繼基準測試的設計前提是「錯誤已經被使用者回報」，因此它們衡量的是診斷與修復能力，而非從零開始的探索與發現能力。此外，這些基準測試普遍使用隱藏單元測試來評分，這些測試檢查的是內部狀態而非使用者實際看到的行為，可能會拒絕採用不同實作方式的合法修復。SWEeper-Bench 正是為了補足這個缺口而設計。

**Q3：為什麼「主動發現錯誤」對未來的程式碼代理如此重要？**
A：隨著 Codex、Claude Code、Cursor 等程式碼代理越來越多地即時生成互動式軟體而非以文字回應，使用者可能在幾分鐘內就會收到一個包含註冊表單、共享行程表、預算追蹤器的小型應用程式。這類軟體通常沒有 QA 團隊把關，因此錯誤必須由代理在交付前自行發現並修復。SWEeper-Bench 推動代理從「等待使用者回饋」轉變為「自主閉合開發迴圈」，這是程式碼代理走向成熟的關鍵一步。

**Q4：SWEeper-Bench 的核心方法是什麼？**
A：SWEeper-Bench 收錄了 200 個任務，每個任務來自一個真實的開源網頁應用程式中已被修復的使用者可見錯誤。每個任務只提供給代理三項輸入：完整的程式碼庫、執行中的應用程式與瀏覽器、以及一個開放式請求（例如「找出並修復 Focalboard 看板分享與成員功能的問題」）。代理必須自行理解應用程式的使用方式、預測可能出錯之處，並設計互動式測試來暴露錯誤，最終產出修補程式碼。

**Q5：SWEeper-Bench 最關鍵的創新是什麼？**
A：SWEeper-Bench 最關鍵的創新在於採用「代理式驗證器」（agentic verifier）來評分，該驗證器透過 Playwright 控制 Chromium 瀏覽器，僅根據使用者實際觀察到的行為來判斷通過或失敗。這種設計避免了隱藏單元測試的兩個主要缺陷：它不檢查內部狀態，因此接受任何能產生正確使用者可見行為的實作方式；同時它真實模擬了使用者操作流程，能捕捉到互動相依性的錯誤。

**Q6：SWEeper-Bench 在任務設計上有哪些重要選擇？**
A：研究團隊刻意挑選「難以發現但一旦發現就很明顯」的錯誤——這些錯誤可透過正常使用重現，且任何使用者都會同意該行為需要修正。每個開源應用程式僅貢獻一個任務，確保了領域的多樣性，涵蓋內容與知識、IT 與開發工具、協作通訊、檔案與媒體分享、財務商業、個人生活風格、商務支付等七大領域。此外，代理永遠不會看到原始的 issue、拉取請求、參考修補、儲存庫歷史或行為測試，確保評估的公平性。

**Q7：SWEeper-Bench 這個基準測試涵蓋哪些內容？**
A：SWEeper-Bench 包含 200 個任務，橫跨 200 個不同的開源網頁應用程式，中位數儲存庫擁有 4.6k 個 GitHub stars。這些應用程式依領域分布為：內容與知識 40 個、IT 安全與開發工具 35 個、協作與通訊 31 個、檔案媒體與分享 29 個、財務與商業 28 個、個人與生活風格 22 個、商務與支付 15 個。知名的應用程式包括 Ghost、Outline、Uptime Kuma、NocoDB、Focalboard、Stirling-PDF、Memos、SiYuan 等。

**Q8：SWEeper-Bench 的主要實驗結果為何？**
A：研究團隊測試了 15 個前沿代理，結果令人警覺——表現最佳的代理僅通過 59.0% 的任務，且有 9 個代理通過率不到一半。然而，當研究團隊將開放式請求替換為詳細的錯誤描述時，所有測試的 5 個代理通過率都躍升至約 96%。這個鮮明的對比顯示，代理其實「會修這些錯誤」，瓶頸完全在於「找到錯誤」這一步。

**Q9：階段式分析揭示了哪些關於瓶頸的洞見？**
A：透過對代理軌跡的階段式分析，研究團隊發現代理在 75.4% 的軌跡中能成功到達包含錯誤的功能區域，但僅在 50.0% 的軌跡中真正識別出錯誤行為。換言之，最大的瓶頸並非「找不到程式碼位置」，而是「未能觸發失敗」或「未能辨識出失敗」。此外，代理很少主動透過瀏覽器進行測試，除非被明確指示這麼做，這凸顯了當前代理在互動式探索能力上的根本不足。

**Q10：SWEeper-Bench 涵蓋哪些實際應用場景？**
A：SWEeper-Bench 的任務反映了多元的真實互動情境，例如 Focalboard 的看板共享（共享後未出現在接收者側邊欄，需九個步驟跨兩個帳號才能重現）、SearXNG 的搜尋建議介面（包含 & 符號的查詢被錯誤地 HTML 跳脫）、以及電子商務結帳流程中的優惠券處理等。這些場景涵蓋了從團隊協作、知識管理到商務交易的各種互動式軟體使用模式。

**Q11：SWEeper-Bench 對產品開發實務有何影響？**
A：SWEeper-Bench 促使產品開發從「被動修復」轉向「主動發現並修復」的典範。對於依賴程式碼代理快速產出原型的團隊而言，這代表著更高的軟體品質保證——代理能在交付前自行掃蕩錯誤，而非讓使用者充當測試者。這也意味著開發迴圈的成本與時間將大幅縮短，因為不再需要等待使用者回報問題。

**Q12：SWEeper-Bench 對程式碼代理研究領域的整體影響是什麼？**
A：SWEeper-Bench 將程式碼代理的評估從「修復錯誤」推進到「發現錯誤」，這是衡量代理是否能真正閉合「建置—測試—修復」迴圈的關鍵一步。它促使研究者關注代理的探索策略、互動式測試設計與失敗辨識能力，而非僅僅是修補能力。這也為未來代理的設計提供了明確的改進方向：必須學會主動操作軟體、預測使用者行為、主動觸發潛在的失敗情境。

**Q13：SWEeper-Bench 有哪些已知的局限性？**
A：SWEeper-Bench 的局限性包括：僅涵蓋網頁應用程式，未涵蓋行動、桌面或命令列軟體；僅使用開源應用程式，可能無法代表商業軟體的複雜度；任務僅有 200 個，規模相對有限；驗證器的成本差異頗大，從每任務 0.16 美元到 3.84 美元不等，使用較強的驗證器會大幅增加評估開支。此外，所有任務都基於英文環境的開源專案，可能存在語言與文化偏誤。

**Q14：SWEeper-Bench 揭示了哪些典型的代理失敗案例？**
A：典型的失敗案例包括：代理雖然導航到了包含錯誤的功能頁面，但從未執行能觸發失敗的特定操作序列；代理雖然看到了異常輸出，但未能將其辨識為錯誤行為；以及代理傾向於僅進行靜態程式碼分析，而非透過瀏覽器實際操作應用程式。這些失敗凸顯了當前代理在「互動式推理」與「使用者視角模擬」上的根本弱點。

**Q15：基於 SWEeper-Bench 的洞見，未來的研究方向有哪些？**
A：未來研究方向包括：訓練代理更主動地透過瀏覽器進行互動式測試，而非僅依賴靜態分析；發展更好的「失敗辨識」能力，讓代理能從異常輸出中推斷出潛在錯誤；探索讓代理自主閉合「建置—測試—修復」完整迴圈的方法；以及將此框架擴展到網頁以外的互動式軟體領域。此外，降低驗證器成本、提升驗證效率也是實務上重要的研究方向。

## 實務應用指南

### 適用場景

1. **「氛圍編碼」(Vibe Coding) 自動化品管**：當開發者或非技術使用者透過 Codex、Claude Code、Cursor 等代理在數分鐘內產出小型互動式應用（如團隊活動報名系統、共享行程表）時，可將 SWEeper-Bench 風格的「探索式測試代理」嵌入流程，在交付前自動掃描並修復使用者會遇到的互動錯誤，避免錯誤被推到真實使用者面前。

2. **開源專案維護者的錯誤分流**：Focalboard、SearXNG、Uptime Kuma 等中型開源專案維護者，可利用此基準衍生的工具對 GitHub Issue 進行預篩選——代理先在沙盒中重現並嘗試修復，再把「已附帶可運行瀏覽器測試與修補提案」的工單轉給人類審核，縮短 triage 時間。

3. **企業內部工具（Internal Tools）的持續健檢**：公司內部低程式碼平台產生的儀表板、表單系統常因權限、狀態機、跨頁流程而藏有互動錯誤。可部署一個定期執行的 SWEeper-Bench 代理，針對每個內部應用產生「開放式請求 + 瀏覽器探勘」任務，產出 PR 等人類審核。

4. **程式碼代理的紅隊評估與選型**：企業在採購或自建程式碼代理時，可將 SWEeper-Bench 的 200 個任務作為選型基準，特別關注「發現率」（reach feature 與 identify buggy behavior 的差距）而非僅看最終通過率，以判斷代理是否具備真正的探索能力。

5. **瀏覽器自動化測試的合成資料生成**：QA 團隊可利用 SWEeper-Bench 的「代理式驗證器」工作流（Playwright + Chromium + 行為斷言）作為模板，從真實錯誤修復 PR 反向合成高擬真的端對端測試案例，補強既有 Cypress / Playwright 測試套件。

### 實作前置條件

**資料面**
- 一個或多個目標開源網頁應用的完整程式碼庫（建議優先選擇有完整 issue tracker、活躍 PR 審核流程、且能在容器中啟動的專案，例如 Focalboard、SearXNG、Memos）。
- 每個任務需具備：(a) 一個「錯誤版本」commit、(b) 一個「參考修復」PR、(c) 至少兩個可在瀏覽器中執行的行為測試（target test 與 preservation test）。
- 應用必須可在沙盒中以 headless 模式啟動並對外提供可訪問的 URL（多數 Node.js / Python / Go 網頁框架皆可，需預先撰寫 Dockerfile 與啟動腳本）。

**算力面**
- 代理本體：需能呼叫前沿 LLM（GPT-5.6、Claude Sonnet 5 等）並支援 function calling / tool use；單任務平均成本約 $0.16（純程式碼代理）至 $3.84（瀏覽器代理），200 任務完整評估預算約數百至上千美元。
- 驗證器：同樣需要前沿 LLM，加上可執行 Playwright 的容器（建議每任務 2 vCPU、4 GB RAM）。
- 沙盒：每個任務需獨立容器以避免狀態洩漏；建議使用 Docker + Kubernetes 或 Firecracker microVM。

**技能面**
- 熟悉 Playwright / Puppeteer 等瀏覽器自動化框架，能撰寫「行為斷言」而非傳統單元測試。
- 具備 LLM agent 開發經驗（tool use、軌跡記錄、階段式評估）。
- 了解 GitHub PR 工作流，能從 merged PR 反向萃取「錯誤版本」與「參考修復」。
- 基本的網頁應用除錯能力，能在瀏覽器中手動重現互動錯誤以驗證任務品質。

### 實作步驟建議

**階段一：任務策展（Task Curation）**
1. 從目標領域（如「內容與知識」、「IT 與開發工具」）挑選候選開源專案，優先選擇 GitHub stars ≥ 1k、近期有 merged bug fix PR 的專案。
2. 對每個 PR，手動在瀏覽器中重現錯誤，確認「任何使用者都會同意這需要修復」，並記錄重現所需的完整步驟序列。
3. 萃取「錯誤版本」parent commit 與「參考修復」diff，撰寫兩個行為測試：一個 target test（驗證錯誤已修復）、一個 preservation test（驗證未破壞既有行為）。
4. 撰寫開放式請求，僅描述產品區域名稱（例如「Find and fix issues in Focalboard's board sharing and membership」），不可洩漏錯誤細節。

**階段二：代理環境建置（Agent Setup）**
5. 為每個任務準備獨立沙盒，預先啟動應用並暴露 URL；提供代理完整的程式碼庫讀寫權限與瀏覽器工具（建議整合 Browser Use 或自建 Playwright MCP server）。
6. 設定代理的 system prompt，明確告知「僅透過使用者可觀察的行為判斷錯誤」，並提供檔案編輯、shell 執行、瀏覽器操作三類工具。
7. 實作軌跡記錄器，記錄每個階段的狀態：(a) 是否到達相關功能、(b) 是否觸發錯誤、(c) 是否識別錯誤行為、(d) 是否提出修補。

**階段三：代理式驗證器（Agentic Verifier）**
8. 在乾淨容器中套用代理產出的 patch，重新啟動應用。
9. 執行兩個行為測試，將每步的 DOM 快照、console log、截圖提供給驗證器 LLM。
10. 驗證器僅依據「使用者會看到什麼」判定 PASS / FAIL；對 target test 而言，錯誤版本應 0% 通過、修復版本應 100% 通過（參考 Table 1 的指標）。

**階段四：評估與分析（Evaluation）**
11. 對 15 個前沿代理執行完整 200 任務評估，計算通過率與平均成本。
12. 進行階段式分析：分離「到達功能」、「觸發錯誤」、「識別錯誤」、「提出修補」四個階段的通過率，定位瓶頸。
13. 對通過率低的代理，額外提供詳細錯誤描述重跑，計算「修復率」（已知錯誤下的通過率）以分離發現與修復能力。

**階段五：產品化（Productionization）**
14. 將評估流程包裝為 CI/CD 可呼叫的 API，支援單任務或批次模式。
15. 整合到企業內部工具鏈（如 Jira、Linear、GitHub Actions），讓代理產出的 PR 自動指派給人類審核者。
16. 建立儀表板監控「發現率 vs 修復率」隨模型版本變化的趨勢。

### 潛在風險與注意事項

**風險一：驗證器的偽陽性 / 偽陰性**
- 行為測試可能因時序問題（race condition）誤判；緩解方式：對每個任務跑三次取平均（參考 Table 1 的 ±0.3 標準差），並對失敗案例人工抽樣覆核。

**風險二：代理繞過真實互動、直接讀程式碼「猜」錯誤**
- 部分代理可能透過閱讀程式碼推測錯誤而未實際觸發；緩解方式：在軌跡分析中強制要求代理必須執行瀏覽器操作才算「識別錯誤」，並獎勵實際觸發失敗的軌跡。

**風險三：任務洩漏（Data Contamination）**
- 若 200 個任務的 PR 已在訓練資料中，代理可能「記住」而非「發現」錯誤；緩解方式：定期更新任務集、優先選擇近期 merged 的 PR，並在評估時遮蔽 PR 編號與 commit hash。

**風險四：成本失控**
- 瀏覽器代理單任務成本可達 $3.84，完整評估 15 個代理 × 200 任務成本極高；緩解方式：建立小子集（30–50 任務）作為快速煙霧測試，僅對通過煙霧測試的代理跑完整集。

**風險五：沙盒安全**
- 代理擁有 shell 執行權限，可能嘗試存取外部網路或破壞沙盒；緩解方式：嚴格限制 outbound network（論文已預設關閉）、使用唯讀根檔案系統、限制 CPU / 記憶體配額。

**風險六：開放式請求的模糊性**
- 過於模糊的請求可能讓代理花大量時間探索無關功能；緩解方式：在 prompt 中提供「產品區域」與「典型使用者流程」的輕量提示，但避免洩漏錯誤細節。

### 與其他技術的整合建議

**與 SWE-bench 系列整合**
- SWE-bench 測試「已知錯誤的修復能力」，SWEeper-Bench 測試「未知錯誤的發現能力」；建議在企業評估中同時跑兩者，以分離代理的「發現」與「修復」能力維度。

**與瀏覽器自動化框架整合**
- 將 Playwright / Puppwright 作為代理的標準工具介面；可參考 Browser Use 或自建 MCP server，讓代理能以自然語言操作瀏覽器。

**與 CI/CD 整合**
- 在 GitHub Actions 或 GitLab CI 中加入「SWEeper-style 預檢」步驟：每次 PR 合併前，自動對變更的程式碼區域產生開放式請求並執行代理，產出「潛在互動錯誤報告」。

**與錯誤追蹤系統整合**
- 將代理發現的錯誤自動建立 Jira / Linear / GitHub Issue，附帶重現步驟、截圖、修補 PR 草稿，供人類審核。

**與可觀測性平台整合**
- 把代理軌跡上傳至 LangSmith、Langfuse 或自建平台，視覺化「到達功能 → 觸發錯誤 → 識別錯誤 → 修補」四階段的流失率，定位瓶頸。

**與人類審核工作流整合**
- 採用「代理先修、人類後審」模式：代理產出 PR 後，由領域專家審核；審核通過的修補可作為新的訓練資料，形成持續改進迴圈。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節，理解「為什麼互動式軟體的錯誤特別難抓」這個核心問題；接著看 Figure 3 的任務執行流程圖，建立「代理 + 瀏覽器 + 驗證器」三件式的直覺；最後試著用 Playwright 手動重現 Figure 5 的 Focalboard 案例，體驗「九步驟才會出現的錯誤」是什麼感覺。

**給 AI 工程師**：重點研讀第 2.3 節的代理式驗證器設計與 Table 1 的驗證器準確性數據，這是將 LLM 整合進測試判定的關鍵；同時關注第 1 節末段的階段式分析（75.4% 到達功能 vs 50.0% 識別錯誤），這直接告訴你目前瓶頸在「識別」而非「修復」，應優先投資於強化代理的瀏覽器探索與失敗識別能力。

**給研究者**：第 2.1 節的任務策展方法論（從 merged PR 反向建構任務）是可遷移的研究方法；建議進一步分析「哪些類型的互動錯誤最容易被代理忽略」（例如跨帳號、跨頁面的狀態同步錯誤），並設計專門的子基準；也可探索「合成任務生成」以突破 200 個真實任務的規模限制。

**給產品經理**：核心訊息是「目前最好的代理也只能自己抓到 59% 的使用者會遇到的錯誤」——這意味著在可預見的未來，代理產出的互動式軟體仍需要人類使用者作為最後一環的測試者；產品設計上應保留「使用者回報錯誤」的管道，並考慮整合「代理自動修復」功能以縮短回饋迴圈；Figure 4 的七大領域分布可作為評估自家產品複雜度的參考。
