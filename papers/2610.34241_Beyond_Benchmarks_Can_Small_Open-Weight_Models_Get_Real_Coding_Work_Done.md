#### 實驗數據解讀

**觀察性資料：閘道器流量與除錯任務**

- **4,165 次編碼代理閘道器回合 (Coding-Agent Gateway Turns)**：這是作者自身會話的累積資料，反映真實使用情境下的流量規模
- **623 次除錯任務 (Debug Jobs)**：顯示在整合過程中，模型行為異常的頻率相當高（佔總回合約 15%）

**首字時間 (TTFT) 對比**

| 請求類型 | 首字時間中位數 (Median TTFT) |
|---------|---------------------------|
| 冷前綴請求 (Cold-Prefix Request) | 約 69.4 秒 |
| 高重用請求 (High-Reuse Request) | 2.8 秒 |

這個約 25 倍的差距揭示了**快取前綴重用 (Cached Prefix Reuse) 對編碼代理工作流的決定性影響**。編碼任務通常涉及穩定的系統提示詞、工具定義與專案上下文，若這些前綴能被有效快取，可大幅降低延遲。但作者特別標註這是「觀察性 (observational)」資料，並非受控實驗，因此因果推論需謹慎。

**第一項委派研究（45 次試驗）**

| 組別 | 通過率 |
|------|--------|
| 直接編碼 (Direct Coding) | 15/15 |
| 委派給量化 Qwen3-Coder 30B-A3B 工作模型 | 12/15（首次）、14/15（重複） |

**第二項委派研究（第二個 15 任務套件）**

這是數據中最具戲劇性的部分：

**部分可重現的面向**

- **使用的模型**：Qwen3-Coder 30B-A3B、Nemotron Cascade 2、Claude Opus 5.5 均為公開或可存取的模型

| 缺口 | 影響 |

**對領域的啟示**

## 論文問答

**Q1：為什麼「模型能跑」不足以代表「能完成編碼工作」？**
A：論文區分出四個層次的進展：已服務（checkpoint 載入並回應）、連貫文字、解析並執行工具呼叫、通過行為檢查的已驗證任務完成。這四個層次並非可互換的——一個端點可能滿足前三項卻在第四項失敗，因為工具語義、快取狀態、會話連續性等問題會在實際編碼代理工作流程中才浮現。論文的核心論點正是「模型產生文字」與「完成編碼工作」是截然不同的成功標準。

**Q2：現有的基準測試（如 SWE-bench）為何無法捕捉這些工程實務問題？**
A：SWE-bench 和 SWE-Lancer 激勵了檢查軟體成果而非孤立程式碼片段，但本文指出這些基準無法系統性地捕捉介面契約設計、快取連續性、工具語義保留等實際工程問題。論文的貢獻在於提供一個具體的回顧性敘述，涵蓋執行環境／配方限制、可計數的操作失敗、快取連續性，以及有界限的已驗證任務與委派經濟性研究。這些是工程旅程末端的案例研究，而非整體專案的總結。

**Q3：為什麼分散式推論最終被放棄，改為單節點服務？**
A：作者最初想像團隊成員跨筆電共享記憶體與算力來服務過大的模型，但實驗後發現重啟與權重傳輸嚴重拖慢分散式迭代速度。此外，模型特定的服務配方無法在執行環境間乾淨地遷移，相容的 API 也無法保留代理的工具語義。當分片聊天比分片編碼代理會話更可用時，單節點服務便逐漸成為預設，工程重心也轉向編碼客戶端整合與已驗證的編碼任務。

**Q4：本研究的核心方法論是什麼？**
A：論文採用「證據限定敘述」（evidence-qualified account）方法，記錄服務、代理協定、會話連續性、產物驗證和驗證在實務中的運作。證據來自作者自身的 4,165 個編碼代理閘道器回合、623 個除錯任務，以及三個獨立的委派研究（皆使用隱藏行為檢查與固定的 Claude Opus 5.5 父模型）。這些研究未匯集，也不對模型或執行環境進行排名，而是提供有界限、可審核的工程經驗記錄。

**Q5：關鍵創新或區分是什麼？**
A：論文提出四個進展層次的區分，並強調「工作程式碼」不等於「已驗證成果」——在委派工作流程中，工作者的產物還必須滿足介面契約、被父模型接受並套用，其隱藏檢查才算數。最具啟發性的發現來自事後診斷：36 個僅因移除參數名稱前綴底線而被拒絕的有效 JSON 產物中，有 19 個在原始隱藏行為檢查中通過，顯示介面契約的設計能在父模型審查開始前就拒絕功能正確的程式碼。

**Q6：為什麼選擇固定的 Claude Opus 5.5 作為父模型？**
A：固定 Claude Opus 5.5 父模型是為了隔離工作者模型的變數，使委派研究的結果可歸因於工作者而非父模型決策。這種設計讓直接編碼與委派編碼之間的比較更具解釋力，因為父模型的審查行為在所有試驗中保持一致。論文中明確指出，這些研究並非用來對模型或執行環境進行排名，而是用來檢視在固定父模型下不同工作者的表現差異。

**Q7：採用了哪些基準或任務套件來評估？**
A：研究採用兩個獨立的 15 任務套件，皆以 TypeScript 測試夾具為基礎，並以隱藏行為檢查進行評估。第一個套件包含 45 次試驗，第二個套件則在固定的產物契約下評估替換群組。這些任務套件是有界限的，不應被誤認為是端到端軟體專案的代表性評估，但能提供直接可計分的成果。

**Q8：關鍵的實驗結果是什麼？**
A：在 45 次試驗研究中，直接編碼通過 15/15，委派給量化的 Qwen3-Coder 30B-A3B 工作者通過 12/15 和 14/15。在第二個 15 任務套件中，替換群組的直接編碼達到 45/45，而 Nemotron Cascade 2 工作者僅 12/45（11 次工作者替換），Qwen3-Coder 工作者更達到 0/45。若將 16 個因訂閱限制而未發出任何模型呼叫即停止的會話計為失敗，數字變為 37/45 與 8/45。

**Q9：快取重用對效能有何影響？**
A：觀察性資料顯示，儲存的冷前綴請求首字時間（TTFT）中位數約為 69.4 秒，而高重用請求僅 2.8 秒，差距約 25 倍。這凸顯了會話連續性與穩定前綴在編碼代理工作流程中的關鍵作用——長會話依賴執行環境與代理／閘道器邊界之外的快取狀態。論文中將此列為工程層之一，強調「模型能跑」與「會話能持續」是不同層次的問題。

**Q10：實際應用場景為何？**
A：論文涵蓋三類實際部署：開發者筆電上的本地部署（使用 llama.cpp 或 MLX）、雲端 GPU 上的單節點服務（使用 vLLM 或 SGLang），以及與編碼客戶端（Cline、OpenCode、Claude Code、Kilo、Continue）的整合。目標是讓普通開發者筆電（而非清空其他應用程式的專用機器）能運行本地推論，並透過閘道器支援工具呼叫（編輯檔案、執行測試等）。

**Q11：產品設計上有何重要考量？**
A：介面契約的設計會在父模型審查開始前就拒絕功能正確的程式碼——36 個僅因參數重新命名而被拒絕的產物中，19 個在隱藏檢查中通過。這顯示產物驗證規則（JSON 格式、匯入、匯出、參數簽名）需要更細緻的設計，否則會浪費功能正確的工作者輸出。此外，訂閱限制導致 16 個會話在沒有任何模型呼叫的情況下停止，這也是產品層面的可靠性問題。

**Q12：對領域的影響為何？**
A：在兩個具有直接編碼組的研究中，直接編碼皆具有較低的 API 列表價格等效前沿成本（每次已驗證成功成本），這對開源模型的經濟可行性提出了具體的經驗性證據。論文也強調「已驗證成功」與「功能實作」是不同層次的進展，呼籲領域在評估編碼代理時應採用更嚴格的驗證標準。這些發現對開源權重模型在實際軟體工程中的定位有重要啟示。

**Q13：論文承認的限制為何？**
A：作者明確指出，這些研究未匯集，也不對模型或執行環境進行排名；樣本規模有限（45 次試驗與 15 任務套件），且 TypeScript 測試夾具不代表整體軟體專案。此外，事後診斷（19/36 通過隱藏檢查）並未建立任何研究在沒有該規則下的得分，因此不能反推原始研究的成功率上限。論文自定位為「回顧性經驗系統經驗報告」，而非控制良好的基準研究。

**Q14：主要的失敗案例有哪些？**
A：最顯著的失敗案例包括：16 個會話因訂閱限制在沒有任何模型呼叫的情況下停止；Qwen3-Coder 工作者在第二個套件中達到 0/45；以及介面契約拒絕了 36 個功能正確的產物（其中 19 個事後證實可通過隱藏檢查）。此外，工具呼叫格式、回合控制、上下文行為、快取重用等層面的差異，導致名義上相容的端點在實務中表現迥異。

**Q15：未來研究方向為何？**
A：未來方向包括：改進介面契約設計以避免拒絕功能正確的程式碼；探索分散式推論在更穩定的網路條件下的可行性；擴展至更廣泛的軟體工程任務（不限於 TypeScript 測試夾具）；以及建立更細緻的會話連續性與快取管理機制。論文也暗示需要更多研究來理解父模型審查與產物驗證之間的邊界，以及如何系統性地衡量「已驗證成功」的真實成本。

## 實務應用指南

### 適用場景

1. **個人開發者的本地編碼助手部署**：在配備 Apple Silicon Mac（如 M2/M3/M4）或單張消費級 GPU（16–24 GB VRAM）的工作站上，以 llama.cpp 或 MLX 服務 Qwen3-Coder 30B-A3B 等量化模型，搭配 Cline 或 Continue 等編碼客戶端，處理中等複雜度的 TypeScript/Python 改檔與除錯任務。

2. **中小型團隊的內部編碼代理閘道器**：在單一雲端 GPU 節點（vLLM 或 SGLang）部署開放權重模型作為後端，透過薄型閘道器統一對外暴露 OpenAI 相容 API，讓團隊成員在 Cline、OpenCode、Kilo、Claude Code 等不同客戶端間切換而不需重寫工具呼叫格式。

3. **分散式推論的概念驗證**：在兩台以上一般筆電間以 llama.cpp 的 RPC over Wi-Fi 機制分片載入單一模型，驗證「無專用互連下能否拼出更大模型」的可行性，適用於預算受限的學術或開源社群實驗。

4. **父模型 + 工作模型的委派式編碼工作流**：以 Claude Opus 5.5 等前沿模型作為父模型負責規劃與審查，將可明確切割的子任務（如產生單一函式實作）委派給本地 Qwen3-Coder 或 Nemotron Cascade 2 工作模型，透過產物契約（Artifact Contract）與隱藏行為檢查（Hidden Check）把關品質。

5. **編碼基準之外的工程驗證流程建置**：在 CI/CD 環境中為每一個編碼任務設計任務專屬的隱藏行為檢查（功能性 + 邊緣案例），用於評估任何候選模型或工作流，而非僅依賴 SWE-bench 等通用基準。

### 實作前置條件

**資料面**
- 目標儲存庫的程式碼與既有測試（建議至少具備可執行的單元測試套件，作為隱藏檢查的起點）。
- 任務套件定義：每個任務需有明確的函式簽名、輸入輸出契約、邊緣案例清單。
- 對照組資料：若要評估委派效益，需準備「直接由前沿模型完成」與「由工作模型完成」兩種產物，用於事後比對。

**運算面**
- 單節點服務：至少一張 24 GB VRAM 的消費級 GPU（如 RTX 3090/4090），或 32 GB 以上統一記憶體的 Apple Silicon Mac。
- 分散式推論實驗：兩台以上可透過 Wi-Fi 互連的筆電，合計可用記憶體需大於模型量化後大小。
- 雲端服務：單一 A100/H100 或同等級 GPU 即可承擔論文規模的 4,165 回合閘道流量。

**技能面**
- 熟悉至少一種推論引擎（vLLM、SGLang、llama.cpp、MLX）的部署與服務配方撰寫。
- 理解 OpenAI 相容 API、工具呼叫（tool call）JSON 格式與代理協定差異。
- 具備基本的快取前綴（cached prefix）與會話狀態管理概念。
- 能撰寫任務專屬的隱藏行為檢查腳本（TypeScript/Python 皆可）。
- 對模型量化（quantization）對產出品質的影響有基本認知。

### 實作步驟建議

**步驟一：建立單節點服務基線**
從雲端 GPU 上的 vLLM 或 SGLang 開始，選擇一個開放權重模型（例如 Qwen3-Coder 30B-A3B），撰寫可重現的服務配方（包含量化設定、parser/template、context 設定）。先以純聊天介面驗證「已服務（served）」與「連貫文本（coherent text）」兩個層級。

**步驟二：接入編碼客戶端與薄型閘道器**
在服務前部署一個薄型閘道器，統一處理工具呼叫格式轉換、回合控制與日誌。依序測試 Cline、OpenCode、Kilo、Continue、Claude Code 等客戶端，記錄每個客戶端的工具呼叫格式差異與相容性問題。論文中 4,165 回合的閘道日誌是這個階段的關鍵除錯資料來源。

**步驟三：建立會話連續性機制**
設計穩定前綴（stable prefixes）策略以最大化快取重用。論文觀察到冷前綴請求的首字時間中位數約 69.4 秒，而高重用請求僅 2.8 秒——這是 25 倍的差距，會直接影響開發者體感。需在閘道器層記錄會話親和性（session affinity），避免跨節點切換導致快取失效。

**步驟四：設計產物契約與行為驗證**
為每個編碼任務定義產物契約：單一 JSON 物件、必要的 imports/exports、參數簽名（含底線前綴等命名規則）。契約通過後再進入父模型審查與套用，最後由任務專屬的隱藏行為檢查把關。論文的事後診斷顯示，36 個僅因參數命名被拒的產物中有 19 個其實通過了隱藏檢查——契約設計本身就是一項工程決策。

**步驟五：執行委派研究並量化成本**
若要評估委派效益，固定父模型（論文中使用 Claude Opus 5.5），在 15–45 個任務的試驗套件上比較直接編碼與委派給工作模型的通過率，同時計算 API 列表價格等效的「每次已驗證成功成本」。論文結論是：在兩個有直接編碼對照組的研究中，直接編碼的成本均低於委派路徑。

**步驟六：建立除錯任務管線**
將 623 個除錯任務的經驗沉澱為可重複使用的診斷流程：先區分失敗發生在哪一層（已服務 / 連貫文本 / 工具呼叫解析 / 行為驗證），再針對該層除錯。論文圖 2 的四個成功層級是定位問題的標準框架。

### 潛在風險與注意事項

**風險一：相容 API 不等於代理相容**
即使模型提供 OpenAI 相容端點，工具呼叫格式、回合控制、上下文行為、快取重用策略仍可能與編碼客戶端預期不符。緩解：在導入新模型時，務必以薄型閘道器隔離差異，並在 4,165 回合規模的日誌中驗證穩定性，而非僅做單回合煙霧測試。

**風險二：冷前綴請求的 TTFT 災難**
69.4 秒的首字時間會讓開發者誤以為系統當機。緩解：設計會話親和性與前綴穩定化策略；對冷啟動任務考慮預熱；或在 UI 層提供明確的等待指示。

**風險三：產物契約過度嚴格**
論文事後診斷發現，19/36 個僅因參數命名被拒的產物其實功能正確。緩解：契約規則應有明確的「功能性影響」說明；對純命名差異考慮寬鬆模式或自動修正層。

**風險四：訂閱限制導致工作流中斷**
論文中 16 個會話在呼叫任何模型前就因訂閱限制停止，若計為失敗則直接編碼從 45/45 變為 37/45。緩解：為父模型準備備援方案；對工作模型採用本地部署以避免外部配額依賴。

**風險五：量化工作模型在委派任務中表現不穩**
Qwen3-Coder 工作模型在第二個 45 任務套件中通過率為 0/45，而 Nemotron Cascade 2 為 12/45（其中 11 個為工作模型替換）。緩解：不要假設「能聊天就能委派」；每個工作模型都需在目標任務套件上獨立驗證。

**風險六：將基準分數誤認為實戰能力**
SWE-bench 等基準的分數無法預測代理在真實儲存庫契約下的表現。緩解：以任務專屬的隱藏行為檢查作為最終驗證關卡，而非僅看基準排名。

### 與其他技術的整合建議

**與編碼客戶端整合**
Cline、OpenCode、Kilo、Continue、Claude Code 各有偏好的工具呼叫風格。建議在閘道器層維護一份「客戶端適配表」，將內部統一的工具呼叫格式轉譯為各客戶端期望的格式，避免每個客戶端單獨維護一份 prompt 模板。

**與 CI/CD 整合**
將任務專屬的隱藏行為檢查包裝為 CI 步驟，使任何模型產出的程式碼在合併前都經過同一套驗證。這也讓「每次已驗證成功成本」可以從 CI 日誌中自動計算。

**與雲端 GPU 服務整合**
單節點服務可部署於 RunPod、Vast.ai、Lambda Labs 等按時計費的雲端 GPU；論文觀察到的高重用請求 2.8 秒 TTFT 顯示，在穩定工作負載下雲端 GPU 的成本效益可優於訂閱制前沿 API。

**與本地部署整合**
對延遲敏感或資料敏感的場景，可在 Apple Silicon Mac 上以 MLX 或 llama.cpp 部署量化模型作為離線後端，雲端 GPU 作為線上後端，閘道器依任務特性路由。

**與監控與可觀測性整合**
論文的 4,165 回合與 623 除錯任務是寶貴的可觀測性資料。建議將閘道器日誌接入 OpenTelemetry 或類似的追蹤系統，按四個成功層級（已服務 / 連貫文本 / 工具呼叫 / 行為驗證）分類失敗，便於快速定位問題層。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的「四個成功層級」框架（圖 2），理解「模型能跑」與「編碼工作能完成」之間存在多個可失敗的邊界。接著看第 2 節的範圍說明，明白這是一份工程經驗報告而非模型排名。實作上先從單節點 llama.cpp/MLX 本地部署開始，跳過分散式推論與委派研究的章節。

**給 AI 工程師**：重點關注第 5–7 節的服務配方、快取前綴重用數據（69.4 秒 vs 2.8 秒 TTFT）與會話連續性設計。論文圖 1 的五個工程層是部署開放權重編碼代理的標準檢查清單。第 9 節的產物契約與事後診斷（19/36 命名問題產物其實通過驗證）對設計代理介面特別有啟發。

**給研究人員**：注意論文的「證據限定敘述」立場——三個委派研究未彙整、不排名模型或執行環境，每個研究的對照組與任務套件都不同。第 9.4 節的事後診斷示範了一種誠實面對契約設計偏差的方法。建議將此報告與 SWE-bench、SWE-Lancer 的工作對照閱讀，理解基準評測與實戰驗證的落差。

**給產品經理**：核心訊息是「基準分數不能預測實戰表現」，且「直接編碼在成本與通過率上可能都優於委派」。論文中 Qwen3-Coder 工作模型 0/45 的結果提醒：在向客戶承諾「用小型模型取代前沿 API」之前，必須在客戶的真實任務上做委派試驗，而非僅看模型發布時的基準數字。第 2 節明確區分了「工程工作」與「編碼任務評估」，有助於設定合理的產品時程預期。
