# CheckerBench：長時程代理（Long-Horizon Agents）能否合成靜態分析檢查器（Static-Analysis Checkers）？

**原文標題：** CheckerBench: Can Long-Horizon Agents Synthesize Static-Analysis Checkers?  
**作者：** Hang He、Li Wang、Hao Chen 等 12 位作者  
**發布日期：** 2026-10-06  
**HF 連結：** [https://huggingface.co/papers/2610.07557](https://huggingface.co/papers/2610.07557)

## ⚡ TL;DR

現有基準測試無法評估代理能否從零合成可重複使用的靜態分析檢查器。
作者提出 CheckerBench 與 CheckerLab，前者含 300 個 CVE 任務。
21 種配置平均 Pass@1 僅 32.30%，最佳 45.33%，顯示此任務仍極具挑戰。

---

## 摘要翻譯

靜態分析檢查器合成（Static-analysis checker synthesis）要求代理（agent）解讀缺陷規格（defect specification）、檢視儲存庫（repository）、實作分析器專屬邏輯（analyzer-specific logic），並透過反覆的編譯與分析回饋（feedback）來精煉檢查器。現有的程式碼代理（coding agents）基準測試（benchmarks）著重於諸如補丁生成（patch generation）或漏洞偵測（vulnerability detection）等任務，鮮少評估代理能否從頭到尾在儲存庫中開發出可用的檢查器。我們提出 CheckerBench，一個包含 300 個任務的可執行基準測試（executable benchmark），這些任務源自橫跨 167 個儲存庫、85 個 CWE 及五個語言生態系（language ecosystems）的 297 個 CVE。每個任務包含含有漏洞的版本（vulnerable revision）與修復後的版本（fixed revision）、鎖定的分析環境（pinned analysis environment），以及檢查器骨架（checker scaffold）。我們進一步提出 CheckerLab，一個通用評估框架，能獨立重建提交的檢查器，並量測漏洞與修復版本間的診斷對比度（diagnostic contrast）、補丁定位（patch localization）、誤報（false positives）與工具使用（tool use）。在 21 種模型-框架配置（model-harness configurations）及每種配置三次獨立重複下，平均 Pass@1 為 32.30%，最佳表現則達到 45.33%。這些結果顯示，對當前的程式碼代理而言，可靠且可重複使用的檢查器（reusable checker）開發仍是一項艱鉅的挑戰。

### 核心貢獻（3～5點）
- 提出 **CheckerBench**：一個包含 300 個任務的可執行基準測試，涵蓋 167 個儲存庫、297 個 CVE、85 個 CWE 及五個語言生態系
- 提出 **CheckerLab**：一個通用評估框架，能獨立重建提交的檢查器並量測四項關鍵指標（診斷對比度、補丁定位、誤報、工具使用）
- 系統性評估 21 種模型-框架配置 × 3 次獨立重複，揭示當前程式碼代理在長時程檢查器開發任務上的能力上限（平均 Pass@1 為 32.30%，最佳為 45.33%）
- 證實可靠且可重複使用的檢查器開發對當前程式碼代理仍具高度挑戰性

### 適合對象
從事靜態分析、程式碼代理（coding agents）、大型語言模型（LLMs）應用、軟體工程自動化及安全性研究的研究人員與工程師，特別是關注漏洞偵測、缺陷模式識別與代理式（agentic）程式碼生成領域者。

## 深度分析

#### 方法論解析

CheckerBench 的方法論核心在於將「長時程代理式靜態分析檢查器合成」(long-horizon agentic static-analysis checker synthesis) 從一個模糊的研究概念轉化為可系統化評量的工程任務。其方法論可從三個層面深入剖析：

**一、任務形式化 (Task Formalization)**

論文將檢查器合成任務形式化為一個四階段的代理工作流：(1) 詮釋缺陷規格 (defect specification)，即理解 CVE/CWE 所描述的漏洞模式；(2) 巡覽儲存庫並定位相關程式碼；(3) 實作分析器專屬的檢查器邏輯 (analyzer-specific logic)，需整合至建置系統 (build system)；(4) 透過反覆的編譯與分析反馈進行精煉。此形式化的關鍵在於它保留了真實軟體工程的「長時程」特性——代理必須在多個檔案間進行協調修改、處理編譯錯誤、理解分析器內部抽象，並在多次迭代中平衡偵測率與誤報率。

**二、基準建構管線 (Construction Pipeline)**

六階段管線設計是方法論的另一支柱：

1. **漏洞來源收集**：從 CVE 資料庫連結至修復提交 (fix commits)，恢復含有漏洞的版本 (vulnerable revision) 與修復後的版本 (fixed revision) 配對。
2. **可執行環境重建**：鎖定工具鏈與分析器版本，確保兩個版本皆可成功建置——這是「可執行基準測試」(executable benchmark) 的基礎。
3. **檢查器合成任務建構**：將修補差異 (patch) 與程式碼捆綁，加入建置/掃描步驟，形成代理可見的任務套件。
4. **獨立驗證器建構**：在隔離環境中重建提交的檢查器，檢查報告變化是否正確區分漏洞版本與修復版本。
5. **人為引導的軌跡收集**：審查失敗嘗試，修訂後重跑，最多三次後排除或通過。
6. **品質控制與分割建構**：驗證產物、去重任務，產出最終的驗證檢查器與軌跡。

此管線的工程價值在於其「可擴展性」(scalability)——相較於手策的檢查器範例，此管線可自動化地從 CVE 衍生新任務。

**三、評估框架 CheckerLab 的設計哲學**

CheckerLab 採用「獨立重複生成」(independent repeated generation) 與「凍結候選驗證」(frozen-candidate verification) 兩個關鍵機制。前者要求每個任務獨立執行多次以緩解隨機性；後者將提交的檢查器在凍結環境中重新建置並執行，避免代理在自身環境中「作弊」。評估面向涵蓋：(a) 診斷對比度 (diagnostic contrast)——檢查器能否區分漏洞版本與修復版本；(b) 補丁定位 (patch localization)——報告是否精確指向修補位置；(c) 殘留報告 (residual reports)——誤報控制；(d) 計算成本 (computational cost)——資源效率。這種多面向評估避免了單一指標的偏差。

#### 實驗數據解讀

**一、整體效能落差**

跨 21 種模型-框架配置 (model-harness configurations)、每配置三次獨立重複的實驗結果顯示：平均 Pass@1 僅 32.30%，最佳配置僅達 45.33%。此數據揭示的核心訊息是：**即使是最先進的程式碼代理，在需要跨檔案協調、理解分析器內部機制、並維持低誤報的長時程任務上，仍有超過一半的失敗率**。45.33% 的「最佳」成績意味著在 300 個任務中仍有約 164 個失敗，距離實用部署仍有顯著差距。

**二、Pass@1 的解讀**

Pass@1 衡量的是單次嘗試的成功率，這對實際應用至關重要——在 CI/CD (持續整合/持續部署) 管線中，檢查器開發通常沒有「多次重試」的奢侈。32.30% 的平均值意味著代理在三分之二的任務上首次嘗試即失敗，這對自動化靜態分析工具鏈的建構構成實質瓶頸。

**三、評估指標的互補性**

論文中提及的四個評估面向並非冗餘，而是捕捉檢查器品質的不同維度：
- **診斷對比度**不足表示檢查器無法區分漏洞與修復版本——這是基本功能的缺失；
- **補丁定位**不準確表示檢查器雖能偵測但報告位置錯誤——這會降低開發者信任度；
- **殘留報告**過多表示誤報率高——這會造成「警報疲勞」(alert fatigue)；
- **計算成本**過高則限制實務部署的可行性。

**四、跨配置差異的意涵**

21 種配置間的效能差距（從平均 32.30% 到最佳 45.33%，差距約 13 個百分點）暗示：(a) 不同模型架構對長時程任務的處理能力存在系統性差異；(b) 代理框架 (harness) 的設計——例如工具整合方式、迭代策略、上下文管理——對最終效能有顯著影響。然而，論文未深入剖析各配置的具體差異，這是數據解讀上的一個缺口。

#### 與現有研究的比較

**一、與 SWE-bench 系列基準的比較**

SWE-bench [32]、SWE-Gym [53]、R2E-Gym [31] 等基準聚焦於「補丁生成」(patch generation)——給定 issue，產生修復程式碼。CheckerBench 與之的根本差異在於：**SWE-bench 評估的是「修復一個 bug」，而 CheckerBench 評估的是「建構一個能偵測該類 bug 的可重複使用工具」**。前者是點對點的修復，後者是泛化性的檢查器開發。此外，SWE-bench 不要求代理理解分析器框架、不評估誤報率、不衡量檢查器的可重用性。

**二、與漏洞偵測基準的比較**

ReposVul [61]、VulEval [64]、JitVul [69] 等基準聚焦於漏洞偵測 (vulnerability detection)——判斷程式碼是否含有漏洞。CheckerBench 的定位更上游：不是「偵測漏洞」，而是「建構偵測器」。這是從「消費者」轉變為「生產者」的角色轉換，對代理的工程能力要求更高。

**三、與專用檢查器合成系統的比較**

RhoSynth [24] 從範例學習圖式程式碼品質規則；KNighter [67] 從 Linux 核心補丁合成 Clang Static Analyzer 檢查器；QLCoder [59] 透過工具使用合成 CodeQL 查詢；MoCQ [35] 與 CQLLM [60] 生成漏洞模式或 CodeQL 查詢。這些系統的共同特徵是**針對特定分析器或領域**，而 CheckerBench 提供跨五種語言生態系、跨多種分析器的統一評估協議。CheckerLab 的「獨立驗證」機制也比這些系統的自我評估更為嚴謹。

**四、CheckerBench 的獨特優勢**

從 Table 1 的系統性比較可看出，CheckerBench 是**唯一同時支援**：(a) 儲存庫上下文、(b) 可執行環境、(c) 多框架、(d) 長時程互動、(e) 檢查器合成、(f) 語意驗證、(g) 誤報評估的基準。這種「全特徵」設計填補了現有基準的關鍵空白。

**五、限制與不足**

儘管覆蓋面廣，CheckerBench 仍存在以下限制：
1. **任務來源偏差**：297 個 CVE 雖跨 167 個儲存庫，但 CVE 的分佈本身偏向已公開報告的漏洞，可能無法代表所有缺陷模式；
2. **分析器覆蓋有限**：雖跨五種語言生態系，但每種生態系的分析器選擇有限，未涵蓋所有主流靜態分析工具；
3. **「長時程」的定義模糊**：論文未明確界定何謂「長時程」——是迭代次數？時間長度？還是任務複雜度？
4. **缺乏人類基線**：未報告人類專家完成相同任務的效能與時間，難以判斷 32.30% 的「絕對」水準。

#### 可重現性評估

**一、基準的可重現性**

CheckerBench 強調「可執行基準測試」(executable benchmark)，每個任務包含：(a) 含有漏洞的版本與修復後的版本、(b) 鎖定的分析環境、(c) 檢查器骨架 (checker scaffold)。這種設計使任務本身可被獨立重現——任何研究者皆可下載任務套件、在相同環境中執行代理、並使用 CheckerLab 進行評估。

**二、評估框架的可重現性**

CheckerLab 的「凍結候選驗證」機制是確保評估可重現的關鍵：提交的檢查器在標準化環境中重新建置並執行，避免代理在自身環境中產生偏差結果。此外，獨立重複生成（每配置三次）提供了統計穩定性。

**三、潛在的可重現性挑戰**

儘管設計完善，仍有以下可重現性風險：
1. **環境依賴**：鎖定的工具鏈版本可能在不同主機上產生差異，特別是涉及原生編譯 (native compilation) 的 C/C++ 任務；
2. **隨機性管理**：LLM 的採樣溫度、代理框架的隨機決策皆可能影響結果，論文中三次重複是否足夠緩解變異值得商榷；
3. **基準演化**：CVE 資料庫持續更新，基準的「凍結」狀態如何維持？是否會隨時間出現資料漂移？

**四、開放性問題**

從提供的內容無法確認：(a) 基準資料集是否已公開發布；(b) CheckerLab 框架的程式碼是否開源；(c) 實驗中使用的 21 種模型-框架配置的具體清單與設定細節。論文中提及「300 verified checkers」與「300 pilot trajectories」，暗示有產出物可供檢視，但需查閱完整論文或附錄以確認開放程度。

#### 未來研究方向

**一、代理能力的縱深提升**

32.30% 的平均 Pass@1 揭示了多個可深化的研究方向：
1. **分析器感知訓練 (Analyzer-Aware Training)**：現有 LLM 的預訓練資料可能未充分涵蓋特定分析器（如 Clang Static Analyzer、CodeQL）的內部機制與 API。可探索針對性的微調或檢索增強生成 (RAG, Retrieval-Augmented Generation) 策略；
2. **多代理協作 (Multi-Agent Collaboration)**：將檢查器合成分解為「規格理解」、「程式碼定位」、「邏輯實作」、「測試驗證」等子任務，由專門化代理協作完成；
3. **記憶與技能累積 (Memory & Skill Accumulation)**：讓代理在跨任務間累積可重用的「技能」(skills)，例如特定分析器的常見模式。

**二、評估方法的演進**

1. **動態難度分級**：現有 300 個任務可能難度異質，可發展難度分級機制，使評估更具鑑別度；
2. **過程評估 (Process Evaluation)**：除最終結果外，評估代理的中間步驟——例如編譯錯誤恢復能力、迭代效率；
3. **人類基線建立**：招募靜態分析專家完成相同任務，建立人類基線以判斷代理的相對水準；
4. **長期演化追蹤**：將 CheckerBench 作為持續追蹤代理能力演化的「活基準」(living benchmark)。

**三、檢查器品質的多維強化**

1. **誤報率優化**：現有評估已包含誤報面向，但如何讓代理在合成階段即考慮誤報控制仍待探索；
2. **可解釋性 (Interpretability)**：檢查器不僅要偵測漏洞，還應產生可理解的報告——這對開發者信任至關重要；
3. **效能感知合成 (Performance-Aware Synthesis)**：將計算成本納入合成目標，使檢查器在大型程式碼庫上仍可高效執行。

**四、跨領域擴展**

1. **更多語言與分析器**：擴展至 Rust、Go、JavaScript 等語言，以及 Semgrep、SonarQube 等分析器；
2. **非 CVE 缺陷**：納入非安全相關的缺陷（如效能問題、可維護性問題），使檢查器合成任務更全面；
3. **領域專用檢查器**：探索針對特定領域（如嵌入式系統、密碼學程式庫）的檢查器合成基準。

**五、理論基礎的建立**

1. **長時程任務的形式化**：明確定義「長時程」的計算複雜度與資訊理論特性；
2. **失敗模式分析 (Failure Mode Analysis)**：系統性分類代理失敗的原因——是規格理解錯誤？程式碼定位失準？還是分析器整合失敗？
3. **可學習性理論**：探討檢查器合成任務的可學習性邊界——哪些類型的檢查器在原則上可被代理學習，哪些需要人類專家介入。

總結而言，CheckerBench 不僅是一個基準測試，更是將「代理式軟體工程」推向更深層次——從「修復 bug」到「建構工具」——的重要里程碑。其揭示的 32.30% 平均 Pass@1 既顯示了當前技術的不足，也為未來研究提供了清晰的改進方向。

## 論文問答

**Q1：什麼是「長時程代理式靜態分析檢查器合成」這個核心問題？為何它對程式碼代理而言特別困難？**
A：這個任務要求代理（agent）根據缺陷規格，導覽分析器基礎架構、實作檢查器邏輯、整合進建置系統，並透過編譯器與分析器的反饋進行迭代精煉，最終產出可重複使用的靜態分析檢查器。它之所以困難，是因為代理必須同時理解複雜的分析器框架、跨多個檔案進行協調修改，並確保最終的檢查器能夠編譯、偵測目標缺陷、且維持低誤報率。這是一個典型的「長時程」任務——單次嘗試往往無法成功，必須經過多輪規劃、實作、除錯的循環。

**Q2：現有的程式碼代理基準測試為何無法有效評估這項任務？**
A：現有基準測試大多不是「以檢查器為中心」的——儲存庫層級的基準（如 SWE-bench）著重於程式碼補全、補丁生成或功能實作，而漏洞基準（如 ReposVul、VulEval）則聚焦於偵測、分類或修復，而非可重複使用的檢查器合成。此外，現有基準提供的任務互動有限：它們通常評估獨立任務，或將工作流程拆解成預先定義的階段，無法讓代理進行迭代式規劃、實作與除錯。各基準在環境、工具介面與評估協議上的差異，也使得跨系統比較變得困難。

**Q3：為何這項研究對軟體工程領域具有重要性？**
A：靜態分析是偵測複雜程式缺陷的可擴展方法，但現有靜態分析器依賴人工設計的檢查器，需要大量專家投入來編碼缺陷模式與分析策略。若代理能自動化這項工作，將大幅降低專家負擔並提升漏洞覆蓋率。更重要的是，這類「將過去的漏洞轉化為可重複使用的檢查」的能力，能讓昨日的失敗守護明日的程式碼，對軟體供應鏈安全具有長遠價值。

**Q4：CheckerBench 的核心方法論是什麼？它如何建構基準？**
A：CheckerBench 採用一條可擴展的自動化建構管線，從 CVE 漏洞來源收集開始，連結 CVE 至修復 commit、恢復含有漏洞與修復後的版本對。接著重建可執行的分析環境（鎖定工具與分析器版本），然後打包成包含修補與程式碼、建置/掃描步驟的代理可見任務套件。整個管線還包含獨立的驗證器（重新建置、檢查報告變化）與人為引導的 rollout 收集，最終通過品質控制與去重以產出 300 個經驗證的任務。

**Q5：CheckerLab 這個統一評估框架的關鍵創新為何？**
A：CheckerLab 的關鍵創新在於「獨立重複生成」與「凍結候選驗證」機制——每個合成的檢查器會被獨立重建，並在含有漏洞與修復後的版本上執行，藉此評估診斷對比度、補丁定位、殘留報告與運算成本。這種設計避免了「代理自我評估」可能帶來的偏差，並提供細粒度的檢查器正確性測量。相較於僅衡量補丁層級正確性或測試套件結果的傳統指標，CheckerLab 還能捕捉漏洞覆蓋率、誤報控制與分析器相容性等檢查器專屬特性。

**Q6：在基準設計上有哪些關鍵的選擇？為何選擇 300 個任務、5 種語言生態系？**
A：300 個任務的規模橫跨 297 個 CVE、167 個儲存庫、85 個 CWE 與 5 種程式語言生態系，這樣的設計兼顧了任務多樣性與統計可信度。選擇多語言生態系是因為不同分析器（如 Clang Static Analyzer、CodeQL 等）有不同的規則編碼方式與缺陷模式，跨語言評估能檢驗代理的泛化能力。此外，每個任務都提供可重現的儲存庫、分析器專屬環境與可重複使用的技能，使代理能進行迭代開發而非單獨的程式碼生成。

**Q7：實驗中測試了哪些模型與代理框架配置？**
A：研究橫跨 21 種模型-框架（model-harness）配置，並對每種配置進行 3 次獨立重複。這種大規模、多配置的設計是為了系統性地評估不同 LLM 與代理框架組合在檢查器合成任務上的表現差異，並降低單次實驗的隨機性。具體的配置細節雖未在摘要中詳列，但涵蓋了當前主流的程式碼代理系統。

**Q8：實驗的關鍵結果為何？這些數字揭示了什麼？**
A：平均 Pass@1 僅為 32.30%，最佳配置也只有 45.33%，這顯示即使是表現最好的代理，仍有超過一半的機會無法成功合成可靠的檢查器。這意味著當前的程式碼代理在長時程、需要跨檔案協調、且涉及工具反饋的任務上仍有明顯不足。這個結果也凸顯了「能寫程式碼」與「能開發可重複使用的分析工具」之間存在巨大鴻溝。

**Q9：從結果中可以歸納出哪些關於代理能力的洞察？**
A：首先，代理在理解分析器框架的內部邏輯上仍有困難，這反映在需要多次迭代才能正確整合檢查器的任務上。其次，跨檔案協調修改對代理而言是高風險操作，容易引入編譯錯誤或破壞現有功能。再者，誤報控制是另一個瓶頸——即使代理能偵測到目標缺陷，往往難以避免對正常程式碼發出警報。這些洞察共同指向：長時程任務需要更強的規劃、記憶與工具使用能力。

**Q10：這項研究的實際應用場景為何？**
A：最主要的應用場景是自動化靜態分析器的擴展——企業與開源專案可利用此技術將歷史 CVE 快速轉化為可重複使用的檢查規則，從而強化軟體供應鏈安全。此外，安全研究團隊可用於快速原型化新的漏洞偵測規則；教育訓練中可作為程式碼代理能力的標準化測試場域；CI/CD 整合上則可讓開發流程自動產生專案專屬的靜態檢查。

**Q11：從產品化的角度，這項研究帶來哪些考量？**
A：產品化時必須考量運算成本——多次迭代的編譯與分析相當耗時，難以大規模部署於即時開發流程。此外，檢查器的可靠性需要獨立驗證（這正是 CheckerLab 的設計精神），不能僅依賴代理自我宣稱的成功。誤報率對開發者體驗影響極大，產品必須提供抑制機制與嚴重程度分級。最終，與現有分析器的整合介面、版本相容性與授權議題也都是商業化的關鍵考量。

**Q12：這項研究對程式碼代理與軟體工程領域的更廣泛影響為何？**
A：這項工作建立了一個新的「代理能力上限測試」——它衡量的是代理能否從零開始建構工具，而非僅僅修改或生成程式碼。這推動了領域從「程式碼生成」走向「工具合成」的典範轉移。同時，CheckerLab 的獨立驗證理念也為未來的代理評估樹立了新標準，強調可重現性與細粒度指標。長期來看，這類基準將引導研究社群投入長時程規劃、跨檔案推理與工具整合等核心挑戰。

**Q13：這項研究有哪些已承認的限制？**
A：首先，雖然涵蓋 5 種語言生態系，但相較於真實世界的程式語言多樣性仍屬有限，可能無法完全代表所有靜態分析場景。其次，基準中的任務源自真實 CVE，但 CVE 本身的代表性與偏誤（如某些 CWE 類型被過度報告）會影響基準的覆蓋平衡。此外，評估仰賴「診斷對比度」等代理指標，但這些指標與實際部署中開發者體驗的對應關係仍需進一步驗證。

**Q14：實驗中觀察到哪些典型的失敗案例？**
A：常見的失敗模式包括：代理無法正確理解分析器的 API 而產出無法編譯的程式碼；在跨檔案修改時破壞了建置系統的相依性；雖然能偵測到目標漏洞，但同時產生大量誤報使檢查器失去實用價值；以及在迭代精煉過程中陷入局部最優，無法透過進一步修改提升效能。這些失敗凸顯了「長時程」特性帶來的複合性挑戰——單一環節的失誤會導致整體任務失敗。

**Q15：未來的研究方向有哪些？**
A：未來可朝幾個方向延伸：一是擴大語言與分析器的覆蓋面，納入更多領域專屬的靜態分析框架；二是發展更好的代理記憶與規劃機制，以處理長時程任務中的狀態管理；三是探索人機協作模式，讓專家能在關鍵決策點介入以提升成功率；四是將檢查器合成與漏洞修復、測試生成等下游任務整合，形成完整的漏洞生命週期自動化；五是研究如何從成功與失敗的軌跡中提煉可遷移的技能，使代理能力能跨任務持續累積。

## 實務應用指南

### 適用場景

1. **企業安全團隊的自動化規則開發**：大型企業的 AppSec 團隊可利用 CheckerBench 訓練或評估內部代理，使其能根據 CVE 描述自動產生對應的 Semgrep、CodeQL 或 Clang Static Analyzer 規則，縮短從漏洞揭露到內部防護部署的時間差。

2. **開源專案維護者的客製化檢查器生成**：Linux kernel、FFmpeg、OpenSSL 等大型 C/C++ 專案的維護者，可借助類似流程為自家程式碼庫產生專屬的靜態分析檢查器，補強通用 SAST 工具難以覆蓋的專案特定缺陷模式。

3. **DevSecOps 流程中的自動化安全閘門**：在 CI/CD pipeline 中整合代理式檢查器合成模組，當新漏洞被揭露時，自動產生對應的檢查規則並部署至預提交 (pre-commit) 或合併請求 (merge request) 階段的掃描節點。

4. **安全研究機構的大規模 CVE 模式挖掘**：研究機構可利用 CheckerLab 的評估框架，系統性地比較不同 LLM 代理在跨語言、跨分析器環境下合成檢查器的能力，產出可發表的基準數據。

5. **程式碼審查工具的規則市集擴充**：商業程式碼審查平台（如 SonarQube、Snyk）可採用此流程，讓客戶透過自然語言缺陷描述自動生成專屬規則，豐富其規則市集並降低人工撰寫成本。

### 實作前置條件

**資料需求**
- CVE/CWE 對應資料庫（如 NVD、OSV、GitHub Advisory Database）
- 漏洞修補前後的程式碼版本（commit pair），需可重現建置
- 目標靜態分析器的原始碼與版本資訊（Clang Static Analyzer、CodeQL、Semgrep、Infer 等）
- 既有檢查器範例作為 few-shot 參考

**運算資源**
- LLM API 存取（GPT-4、Claude、DeepSeek 等模型，或自部署開源模型）
- 容器化環境（Docker/Podman）以重現「鎖定的分析環境」
- 每個任務約需數十分鐘至數小時的代理執行時間，300 個任務完整評估需可觀的 GPU/API 配額
- 至少數 TB 的儲存空間用於保存多版本儲存庫與分析結果

**技能門檻**
- 熟悉至少一種靜態分析器（推薦從 CodeQL 或 Clang Static Analyzer 入手）
- LLM 代理開發經驗（tool use、function calling、sandbox 設計）
- 軟體工程能力：Docker、CI/CD、版本控制、自動化測試
- 評估指標設計經驗：理解診斷對比度、補丁定位、誤報率等度量

### 實作步驟建議

**階段一：基準測試環境建置（2-4 週）**
1. 從 CheckerBench 公開資料中選取與目標領域相符的子集（例如聚焦 C/C++ 的記憶體安全缺陷）
2. 部署 CheckerLab 框架，配置獨立的「重建-驗證」管線，確保提交的檢查器在隔離環境中可重現
3. 建立模型-框架配置矩陣，初期建議至少測試 3 種模型 × 2 種代理框架的組合

**階段二：代理能力評估與基線建立（2-3 週）**
1. 對選定任務集執行三次獨立重複，記錄 Pass@1、診斷對比度、補丁定位準確率
2. 分析失敗模式：編譯失敗、誤報過高、無法定位漏洞、工具呼叫錯誤等
3. 依據論文結果（平均 32.30%、最佳 45.33%）設定合理的內部基線目標

**階段三：領域特化調校（4-8 週）**
1. 針對高頻失敗模式設計檢查器骨架（scaffold）改進，例如預載分析器 API 文件、加入常見缺陷模式範本
2. 引入檢查器範例庫作為 in-context 參考，提升代理對分析器特定邏輯的理解
3. 設計迭代精煉機制：當編譯或分析失敗時，提供結構化錯誤訊息而非原始輸出

**階段四：產品化整合（4-6 週）**
1. 將訓練後的代理包裝為 API 服務，輸入為 CVE 描述與儲存庫，輸出為可部署的檢查器檔案
2. 整合至企業 SAST 平台，建立規則版本管理與回滾機制
3. 設計人機協作介面：安全工程師審核代理產出的檢查器，並提供修正回饋以持續改進

**階段五：持續監控與改進**
1. 定期以新揭露的 CVE 更新評估集，追蹤代理效能漂移
2. 建立誤報回報管道，將人工標註的誤報案例納入訓練資料
3. 監控工具呼叫成本與執行時間，設定預算上限

### 潛在風險與注意事項

**風險一：誤報率過高導致開發者信任流失**
- 緩解：採用 CheckerLab 的「診斷對比度」指標作為必要條件，僅當檢查器在漏洞版本產生警報且在修復版本不產生警報時才視為有效；設定誤報率閾值（例如每千行程式碼不得超過 X 個警報）

**風險二：環境重現性問題導致評估失真**
- 緩解：嚴格使用容器化鎖定環境，避免「在我機器上可以跑」問題；對每個任務保存環境快照（Docker image hash、工具版本清單）

**風險三：代理產生「幻覺式」檢查器（語法正確但語意錯誤）**
- 緩解：建立獨立驗證管線（frozen-candidate verification），由 CheckerLab 自動重建並執行；對關鍵基礎設施採用人工審核雙重把關

**風險四：成本失控**
- 緩解：設定每任務的 token 與時間上限；採用較小模型處理初步篩選，僅對候選任務使用大型模型；監控 Pass@1 與成本的比值

**風險五：覆蓋率偏差**
- 緩解：論文顯示 32.30% 的平均通過率代表近七成任務失敗，部署前需明確界定適用範圍；避免將此技術用於零容忍場景（如醫療、航太控制系統）

**風險六：分析器版本綁定**
- 緩解：當底層分析器升級時，需重新評估既有檢查器的有效性；建立檢查器與分析器版本的對應表

### 與其他技術的整合建議

**與 SAST 工具整合**
- 將代理產出的檢查器以標準格式輸出（Semgrep YAML、CodeQL QL 檔案、Clang Checker .cpp 檔案），透過各工具的 CLI 直接載入
- 建立「規則生命週期管理」模組，統一管理代理產生、人工撰寫、第三方規則

**與 CI/CD Pipeline 整合**
- 在 GitHub Actions、GitLab CI、Jenkins 中加入「檢查器合成」階段：當新 CVE 影響專案依賴時，自動觸發代理產生對應規則
- 與現有掃描節點串接，新規則經審核後自動部署至 pre-merge 掃描

**與漏洞管理系統整合**
- 串接 DefectDojo、ThreadFix 等平台，將代理產出的檢查器與 CVE 編號關聯，便於追蹤漏洞覆蓋率
- 整合 SBOM（軟體物料清單）工具，當 SBOM 出現新漏洞時自動觸發規則合成

**與威脅情報平台整合**
- 對接 MISP、AlienVault OTX 等威脅情報源，自動擷取新 CVE 描述作為代理輸入
- 將代理產出的檢查器回饋至威脅情報平台，形成雙向資訊流

**與程式碼審查工具整合**
- 在 IDE 插件（如 VS Code、JetBrains）中嵌入輕量版代理，對開發者即將提交的程式碼即時產生專案特定檢查
- 與 SonarQube 規則引擎整合，擴展其自訂規則能力

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節了解「靜態分析檢查器合成」這個任務的本質——它不只是寫程式碼，而是要讓代理理解一個複雜的分析器框架並產出可重複使用的規則。接著重點看圖 1 的整體結果（平均 32.30% 通過率），體會這個問題的難度。技術細節可先跳過，專注於「為什麼這件事重要」與「它解決了什麼痛點」。

**給 AI 工程師**：重點關注第 3 節的任務建構管線與 CheckerLab 的評估設計，特別是「獨立重建-凍結候選驗證」機制如何避免過擬合。實作上可從論文的開源儲存庫著手，先重現小規模實驗（例如 30 個任務），再逐步擴展。建議設計自己的失敗模式分類法，並實驗不同的代理框架（如 LangChain、AutoGen、自建 loop）對結果的影響。

**給研究者**：第 4 節的實驗結果與消融研究是核心，特別是不同模型-框架配置間的效能差異。可進一步探索的方向包括：多代理協作（專門負責理解 CVE、專門負責編寫檢查器、專門負責除錯）、檢查器範例庫的檢索增強生成（RAG）、以及跨語言遷移學習。此外，論文中 32.30% 的平均通過率留下了大量改進空間，特別是在長時程規劃與工具呼叫效率方面。

**給產品經理**：這項技術目前處於「研究原型」階段，平均僅三分之一任務可成功，不建議直接用於生產環境的關鍵安全決策。但可作為內部工具的「輔助功能」試點，例如讓安全工程師從「從零撰寫規則」轉為「審核並修正代理產出的規則」，預期可節省 50-70% 的初始規則開發時間。關鍵決策點在於：選擇哪個靜態分析器作為目標（建議從團隊已熟悉的工具切入）、如何設計人機協作介面、以及如何衡量投資報酬率（建議追蹤「從 CVE 揭露到內部防護部署」的時間縮短幅度）。
