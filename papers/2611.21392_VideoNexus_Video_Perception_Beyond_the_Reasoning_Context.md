VideoNexus 的核心設計理念在於「解耦」(decoupling) 感知與推理兩個原本緊密耦合的過程。傳統的影片問答系統——無論是靜態擷取 (static ingestion) 還是耦合式代理 (coupled multimodal context)——都將原始像素 (raw pixels) 與推理軌跡 (reasoning trace) 放在同一個上下文中處理，導致視覺資訊隨著對話輪次不斷累積。VideoNexus 透過引入「感知子代理」(perception sub-agent) 機制，將視訊處理外包到獨立的、短暫存在的 (ephemeral) 上下文中執行。

**規劃器 (Planner) 的職責**：規劃器本身不接收視訊串流，僅以文字形式運作。它負責：(1) 根據當前問題與已收集的證據，決定下一步要檢查的時間區間；(2) 為每個感知呼叫選擇合適的取樣密度（每秒幀數 fps）；(3) 整合回傳的「發現」(Finding) 與「證據卡」(evidence card)；(4) 判斷何時停止搜尋並產出最終答案。這種設計讓規劃器的輸入始終維持在文字層級，避免視覺符元 (visual tokens) 隨推理過程膨脹。

**感知子代理的兩種呼叫模式**：
- **Overview（總覽）**：對整段影片進行粗略掃描，回傳一組候選時間區間供導航使用。在論文的圖 1 範例中，Overview 處理了 1,019 幀加完整音訊，消耗 159,576 符元，但僅回傳 608 符元的精簡摘要。
- **Inspect（檢查）**：針對特定區間進行細部觀察，可由規劃器指定較高的取樣密度。圖 1 範例中，Inspect 在 40:40–41:10 區間以 1 fps 取樣 30 幀，消耗 3,248 符元，回傳 374 符元的 Finding 加上 982 符元的證據卡。

**證據交換格式 (Evidence Exchange Format)**：每個 Finding 包含三個關鍵元素——絕對時間戳 (absolute time)、狀態標記 (status: ok 或不確定) 以及文字化的視覺觀察。對於需要視覺驗證的細節，系統會附加一張小型「證據卡」(evidence card)，通常為 6 幀的視覺摘要。這種設計讓規劃器能在不保留完整感知輸入的情況下，針對特定細節請求進一步驗證。

**取樣密度的彈性控制**：與 VideoSeek 等方法不同，VideoNexus 允許規劃器根據任務性質動態調整取樣率。粗略探索時可使用稀疏取樣 (sparse sampling)，而針對短暫事件或細節驗證時則提高密度。這解決了論文中指出的兩個關鍵問題：稀疏取樣可能遺漏關鍵細節 (decisive detail)，而每幀描述 (per-frame descriptions) 則會讓回傳報告的長度隨取樣量線性增長。

#### 實驗數據解讀

**LVBench 完整測試結果**：以 Gemini 3.8 Flash 作為共享骨幹模型 (backbone)，VideoNexus 在完整 LVBench 上達到 88.6% 準確率，顯著優於同骨幹的靜態擷取 (85.0%，差距 +3.6 點) 與 Gemini 內建代理式處理 (87.5%，差距 +1.1 點)。更值得注意的是成本效益——VideoNexus 僅消耗內建代理模式 44% 的 API 成本 (API cost)，這意味著在準確率提升的同時，運算成本降低超過一半。

**配對子集消融實驗 (Paired Subset Ablation)**：在控制其他變因的情況下，規劃器輸入量減少 32%，而準確率從 86.5% 提升至 89.0%。這個結果直接驗證了核心假設：解耦感知與推理不僅能降低上下文負擔，還能提升任務表現。可能的解釋是，當規劃器不再被大量視覺符元干擾時，其推理品質得以提升。

**跨骨幹模型遷移**：以 Kimi K3 作為共享骨幹模型，在 Video-GAIA 基準上，VideoNexus 比官方 ReAct 評測框架 (ReAct harness) 提升 8.5 點。這顯示該框架的設計並非依賴特定模型的特性，而是具有跨模型的泛化能力。

**與 VideoSeek 的比較**：在同骨幹條件下，VideoNexus 比 VideoSeek 重跑結果高出 7.2 點，且成本更低。然而論文中坦承，兩者的比較在音訊存取方面存在差異，這在補充材料中有進一步分析。VideoSeek 的全域掃描平均每幀回傳 28 符元，增加掃描預算會直接導致回傳報告變長，而 VideoNexus 的精簡證據交換格式則不受此限制。

#### 與現有研究的比較

**定位差異**：在影片代理 (video agent) 的光譜上，VideoNexus 佔據了一個獨特的位置。EVA 與 VideoTemp-o3 等方法採用學習式策略 (learned policy)，透過訓練獲得查詢驅動的觀察行為；而 VideoNexus 是無需訓練 (training-free) 的框架，僅依靠提示工程 (prompt engineering) 與架構設計達成類似效果。這使得 VideoNexus 更容易部署到新的骨幹模型上，但也將效能上限交由基礎模型的能力決定。

**與感知委派方法的比較**：VideoSeek 與 VideoXAgent 同樣將感知委派給獨立模型，但兩者仍維持「觀察大小隨取樣密度線性增長」的依賴關係。VideoNexus 的關鍵創新在於打破了這個依賴——透過結構化的證據卡與精簡的文字回傳，讓取樣密度與回傳資訊量解耦。

**與靜態擷取的比較**：靜態擷取將一小時的影片以 1 fps 取樣後，會產生數十萬個視覺符元，模型必須在這個龐大的多模態情境 (multimodal context) 中同時進行證據定位、感知與推理。VideoNexus 透過分散式處理，讓每個子任務在更小、更專注的上下文中執行，這與文字領域中「長上下文不等於有效使用」(access to long context does not ensure effective use) 的發現一致。

**限制與不足**：
1. **音訊差異的混淆變因**：與 VideoSeek 的比較中，音訊存取的差異未被完全控制，這可能部分解釋了效能差距。
2. **對規劃器模型的依賴**：框架效能高度依賴骨幹模型的推理與規劃能力，若模型在多步驟規劃上表現不佳，框架優勢可能無法顯現。
3. **證據卡的資訊損失**：將視覺資訊壓縮為 6 幀的證據卡必然伴隨資訊損失，對於需要極精細視覺細節的任務可能不夠充分。
4. **缺乏學習式適應**：與 EVA 等方法相比，無法透過訓練自動優化觀察策略。

客服通話錄影（含螢幕分享與音訊）需要快速定位「客戶在哪個時間點表達不滿」。VideoNexus 同時處理原生音視訊的能力，可結合語氣分析與畫面操作，產出精簡的 Findings 供主管檢視。

**4. 自動駕駛與行車記錄器的事件回溯**
長途行車記錄影片中，事故發生前的關鍵 30 秒往往散落在數小時的錄影中。VideoNexus 的規劃器可先以稀疏取樣掃描異常，發現候選區間後再密集檢查，兼顧效率與細節。

**5. 教育影片的智慧助教**
線上課程平台可部署 VideoNexus 風格的代理，讓學生針對長講座影片提問（如「教授在解釋量子糾纏時用了什麼比喻」），系統回傳帶時間戳的證據而非整段影片。

## 實作前置條件

**資料需求**
- 影片檔案需支援隨機時間區段讀取（seekable），建議使用 MP4/MKV 等容器格式

## 實作步驟建議

**步驟一：定義工具介面**
將 VideoNexus 的兩個核心工具封裝為標準介面：
- `overview(video_id, scan_budget)`：回傳候選時段清單（start, end, reason）
- `inspect_frames(video_id, start, end, fps)`：回傳 Finding（含絕對時間錨定的聲明與狀態）
兩者皆應限制回傳 token 數，避免上下文膨脹。

**步驟二：建立規劃器迴圈**
實作 ReAct 風格的主迴圈：規劃器讀取問題 → 呼叫 `overview` → 整合候選時段 → 呼叫 `inspect_frames` 取得 Finding → 判斷是否需要再次檢查或可作答。每一輪只將 Finding 與證據卡加入推理上下文，原始幀不保留。

**步驟三：設定取樣密度策略**
根據任務類型動態決定 fps：
- 廣域探索：0.1–0.5 fps（每 2–10 秒一幀）
- 局部驗證：1–4 fps（每秒 1–4 幀）
- 細節確認：最高可達原生幀率
規劃器應在呼叫 `inspect_frames` 時明確指定此參數。

**步驟四：設計證據卡格式**
統一 Finding 的 JSON 結構，例如：
```json
{
  "interval": [2445, 2460],
  "claims": [
    {"text": "角色在練習時跌倒", "status": "ok", "evidence_time": 2445},
    {"text": "將鐵條綁在手腕", "status": "ok", "evidence_time": 2455}
  ],
  "uncertainty": []
}
```
此格式讓規劃器能精準引用與交叉驗證。

**步驟五：建立評估管線**
在 LVBench 或自有資料集上重現論文的消融實驗：
- 比較「靜態擷取」vs「VideoNexus」在準確率、規劃器輸入 token、API 成本的差異
- 監控平均每題讀取幀數（論文報告為 621 幀/題）
- 記錄規劃器呼叫 `inspect_frames` 的次數分佈

**步驟六：迭代優化**
根據失敗案例分析規劃器的決策模式：是否過早停止？是否在錯誤區間反覆檢查？可加入反思步驟（reflection）或自我驗證機制。

## 潛在風險與注意事項

**風險一：規劃器陷入無效迴圈**
症狀：代理反覆檢查同一區間卻無法收斂。
緩解：設定最大呼叫次數上限；要求規劃器在每次呼叫前明確說明「為何需要再次檢查」；對重複區段加入懲罰機制。

**風險二：稀疏取樣錯失關鍵事件**
症狀：總覽階段以低 fps 掃描，遺漏短暫事件（如 2 秒內的閃光）。
緩解：對已知含快速事件的影片類型（運動、爆炸）預設較高的總覽 fps；允許規劃器在 Finding 中標記「不確定」以觸發再次檢查。

**風險三：音視訊對齊誤差**
症狀：Finding 引用時間與實際事件發生時間有偏差。
緩解：使用統一的時間基準（影片容器時間碼）；在證據卡中明確標示絕對秒數而非相對位置。

**風險四：API 成本失控**
症狀：規劃器過度呼叫 `inspect_frames` 導致成本飆升。
緩解：設定單題預算上限；對 `inspect_frames` 的輸入區間長度與 fps 設硬性上限；定期審查呼叫日誌。

**風險五：骨幹模型能力差異**
症狀：換用較弱模型時，規劃器的決策品質顯著下降。
緩解：在選用骨幹前先以小型基準測試規劃能力；對較弱模型可預先提供「檢查清單」式的提示範例。

**風險六：影片長度上限**
症狀：超過骨幹模型原生視訊長度上限（如 1 小時）的影片無法直接處理。
緩解：先以場景偵測切分影片為多個段落，再對每段獨立執行 VideoNexus，最後合併 Findings。

## 與其他技術的整合建議

**與 RAG 系統整合**
VideoNexus 的 Findings 可作為影片文件的「索引條目」寫入向量資料庫。對同一影片的多輪問答可共用先前累積的 Findings，避免重複感知呼叫。

**與影片搜尋引擎整合**
將 `overview` 的輸出（候選時段）與傳統影片搜尋（如 CLIP-based 語義搜尋）結合：先用搜尋縮小範圍，再用 VideoNexus 細部驗證，兼顧召回率與精確度。

**與多代理框架整合**
VideoNexus 的規劃器可作為 LangGraph、AutoGen 或 CrewAI 中的「影片專家」節點，與文字、程式碼、網頁等其他專家代理協作。

**與快取層整合**
對熱門影片預先執行 `overview` 並快取候選時段；對常見問題類型預先生成「檢查模板」，減少規劃器的推理負擔。

**與監控與可觀察性整合**
將每次呼叫的輸入 token、輸出 token、耗時、Findings 數量寫入日誌系統（如 LangSmith、OpenTelemetry），方便後續分析與成本歸屬。

**與人類審核整合**
在低信心度的 Finding 上標記「需人工確認」，將證據卡推送給審核員介面，支援一鍵跳轉到對應時間點。
