# 測試時的 AI4AI（AI 驅動 AI）：透過推論時輔助架構（harness）實現強到弱能力轉移

**原文標題：** AI4AI at Test-Time: Strong-to-Weak Capability Transfer via Harnesses  
**作者：** Cheng Qian、Wenting Zhao、Liangwei Yang 等 9 位作者  
**發布日期：** 2026-08-12

## ⚡ TL;DR

傳統蒸餾需重新訓練弱模型，本文探討能否在推論時直接轉移能力。
強模型利用少量驗證資料迭代設計推論輔助架構，無需更新弱模型參數。
目標模型平均分從0.49躍升至0.91，證明推論時輔助架構可免重新訓練轉移能力。

## 摘要翻譯

近期關於蒸餾（distillation）的研究通常透過教師強制（teacher forcing）、同策略蒸餾（on-policy distillation）及相關訓練時方法（training-time methods）更新後者（小型模型，smaller ones）的參數，以將大型模型（large models）的能力轉移至小型模型（smaller models）。本文探討這類轉移是否也能在測試時（test time）發生。我們研究強到弱鷹架輔助（strong-to-weak scaffolding）：較強的建構者模型（builder model）是否能建構推論時輔助架構（inference-time harness），幫助較弱的目標模型（target model）在無需任何參數更新（parameter updates）的情況下更可靠地解決任務。我們使用四個具代表性的心智理論（Theory-of-Mind, ToM）基準測試（benchmarks），每個建構者模型將 5% 的資料作為驗證集（validation set），在多輪過程中迭代式精煉（iteratively refine）其輔助架構，最終輔助架構（finalized harness）則在完整測試集（full test set）上進行評估。實證結果顯示，這種測試時能力轉移（test-time capability transfer）非常有效，平均目標模型表現（average target-model performance）從 0.49 大幅提升至 0.91，幾乎翻倍。我們的分析指出，這些增益主要來自於將不穩定的模型推理（unstable model reasoning）卸載（offloading）為確定性程式碼（deterministic code）、針對基準測試的路由（benchmark-specific routing），以及嚴格的答案格式強制（answer-format enforcement），而非來自鼓勵目標模型更廣泛地推理（reason more extensively）或更廣泛地取樣（sample more broadly）。我們進一步發現，建構者模型推理投入（builder-model reasoning effort）會單調地（monotonically）提升輔助架構品質；平台效應（platform effects）相對於建構者模型自身能力而言相對輕微；較弱的目標模型獲得最大的增益。這些結果顯示，推論時輔助架構設計（inference-time harness design）是傳統訓練時蒸餾（conventional training-time distillation）的重要互補方法（complement），使強模型（strong models）能夠在無需重新訓練（retraining）的情況下，將認知結構（cognitive structure）轉移至弱模型（weak models）。

### 核心貢獻（3～5點）
- 提出在測試時（test time）而非訓練時進行強到弱能力轉移，透過建構者模型（builder model）設計推論時輔助架構（harness），無需更新目標模型（target model）參數。
- 在四個心智理論（Theory-of-Mind, ToM）基準測試上驗證此方法，平均目標模型表現從 0.49 提升至 0.91，幾乎翻倍。
- 分析增益來源：主要來自將不穩定推理卸載為確定性程式碼、針對基準測試的路由與嚴格答案格式強制，而非增加目標模型推理廣度或取樣多樣性。
- 發現建構者模型推理投入與輔助架構品質呈單調正相關，平台效應相對輕微，且較弱的目標模型獲益最大。
- 主張推論時輔助架構設計可作為傳統訓練時蒸餾的重要互補方法，使強模型能在無需重新訓練的情況下將認知結構轉移至弱模型。

### 適合對象
對大型語言模型能力轉移、知識蒸餾、推論時擴展（test-time scaling）及 AI 輔助 AI（AI4AI）系統設計感興趣的研究人員與工程師；特別適合希望在不重新訓練或更新小模型參數的前提下，利用強模型提升弱模型任務表現的實務工作者與學術研究者。

## 深度分析

#### 方法論解析

本研究提出「強到弱鷹架輔助（strong-to-weak scaffolding）」作為一種新型的**測試時（test-time）** / **推論時（inference-time）能力轉移（capability transfer）** 典範。其核心問題是：能否不更新目標模型的參數，而由一個更強的**建構者模型（builder model）** 在推論階段為一個較弱的**目標模型（target model）** 設計外部輔助結構，使其任務表現顯著提升？

##### 1. 問題設定與形式化

與傳統**知識蒸餾（distillation）** 或**資料蒸餾（data distillation）** 不同，本研究假設目標模型的權重完全固定，禁止任何形式的**參數更新（parameter updates）** 或**重新訓練（retraining）**。能力轉移的媒介從「模型權重」轉移到「推論時輔助架構（harness）」。一個 harness 被定義為任何能夠圍繞目標模型運作的外部結構，包括：

- **任務路由（task routing）**：依據題目類型將輸入導向不同處理分支；
- **提示模板（prompt templates）**：設計系統提示、角色設定、解題框架；
- **確定性求解器（deterministic solvers）**：將部分推理步驟轉為可預測的程式碼或規則；
- **少樣本示範（few-shot exemplars）**：提供高品質的輸入—輸出範例；
- **驗證階段（verification passes）**：檢查答案一致性、格式與邏輯；
- **答案格式強制（answer-format enforcement）**：嚴格規範輸出格式以便解析與評分。

建構者模型僅能接觸到每個基準測試（benchmark）中 5% 的資料作為**驗證集（validation set）**，並在多次迭代中精煉 harness；最終 harness 則在完整**測試集（full test set）** 上評估。此設計確保 harness 必須學到可泛化的任務結構，而非記憶特定答案。

##### 2. 強到弱能力轉移的運作機制

本研究將「讓模型變得更強」與「讓任務變得更簡單」區分為兩條互補路徑。傳統蒸餾走的是第一條路：透過**教師強制（teacher forcing）**、**同策略蒸餾（on-policy distillation）** 與**密集回饋（dense feedback）** 讓學生模型內化行為。相對地，strong-to-weak scaffolding 走的是第二條路：透過 harness 降低目標模型所承受的**認知負荷（cognitive load）**，把不穩定的推理卸載到確定性程式碼、把複雜決策轉為**針對基準測試的路由（benchmark-specific routing）**，並以嚴格的格式控制減少輸出解析錯誤。

這種設計特別適合**心智理論（Theory-of-Mind, ToM）** 基準測試，因為這類任務具有明確的子類型結構（如高階信念遞迴、視角轉換、貝葉斯目標推論），可透過外部符號程序或分類路由來分解。

##### 3. 迭代式 harness 建構流程

方法流程可概括為：

1. **初始化**：建構者模型根據任務描述與少量驗證樣本，產生初始 harness；
2. **驗證評估**：將該 harness 套用於目標模型，在 5% 驗證集上取得表現；
3. **錯誤分析**：建構者模型檢視錯誤案例，診斷是推理失敗、格式錯誤、路由錯誤或認知負荷過高；
4. **迭代精煉（iteratively refine）**：根據診斷結果修改 harness，例如加入新的確定性求解器、調整提示模板、增加驗證階段；
5. **最終評估**：將定稿的**最終輔助架構（finalized harness）** 套用於完整測試集。

此流程類似於自動化的「提示工程 + 系統設計」，但由強模型擔任工程師，弱模型僅作為執行元件。

#### 實驗數據解讀

##### 1. 主要效應量（Effect Size）

研究在四個具代表性的 ToM 基準測試上進行實驗。以 **GPT-5.4-mini** 作為目標模型時，無 harness 的平均準確率為 0.49，加入最佳 harness 後提升至 0.91，絕對增益達 0.42，幾乎是原始表現的兩倍。更重要的是，「每一種建構者配置都帶來正向淨提升」，顯示這種能力轉移方式具有高度穩定性，而非依賴特定超參數或幸運抽樣。

##### 2. 增益來源：結構外部化而非更多推理

作者進行細緻的機制分析，發現表現提升主要來自：

- **將不穩定的模型推理卸載為確定性程式碼（offloading unstable model reasoning into deterministic code）**：例如把信念狀態的遞迴更新、機率計算或邏輯檢查寫成固定程式，減少語言模型在長鏈推理中的隨機錯誤。
- **針對基準測試的路由（benchmark-specific routing）**：依據題目子類型選擇對應的求解策略，避免讓弱模型自行判斷應採用何種推理框架。
- **嚴格的答案格式強制（strict answer-format enforcement）**：透過規範輸出格式（如強制 JSON、限定選項字母）降低後處理錯誤與模型「胡說」機率。

相對地，研究發現單純增加驗證資料量、鼓勵目標模型進行更廣泛推理，或擴大取樣多樣性，並非增益的主要來源。這點對實務設計非常重要：與其讓弱模型「更努力想」，不如為它「把路鋪好」。

##### 3. 不同基準測試的差異

- **BigToM**：最佳 harness 發現答案可透過結構化推理幾乎完全轉換為可編譯的規則與技能，顯示該基準測試具有較高的「可外部化」結構。
- **其他基準測試**：增益更多來自於真實降低推理負擔，而非捷徑（shortcut）。
- **殘留錯誤**：主要集中在最困難的子類型，特別是遞迴深度 ≥ 2 的高階 **Hi-ToM** 案例，以及貝葉斯目標推論（Bayesian goal-inference）子類型。這暗示 harness 雖強，仍無法完全彌補目標模型在極深層推理上的內部能力缺口。

##### 4. 建構者與目標模型的相依性

- **建構者模型推理投入（builder-model reasoning effort）**：研究發現隨著建構者投入更多推理資源（例如更長的思考鏈、更多迭代），harness 品質呈現**單調（monotonically）** 提升。這表示 harness 設計本身是一項需要認知資源的任務，強模型的內部推理能力會直接轉化為更好的外部結構。
- **平台效應（platform effects）**：相較於建構者模型自身能力，不同模型平台/供應商所造成的影響相對有限。這意味著方法的核心價值在於「誰來設計 harness」，而非「在哪個平台上執行」。
- **目標模型強度**：較弱的目標模型（GPT-5.4-mini）獲得的提升大於已經較強的目標模型（Gemini-3.5-flash）。這符合認知負荷理論：能力越低的模型，越能從外部結構化支援中受益。

#### 與現有研究的比較

##### 1. 與傳統訓練時蒸餾的對比

傳統**模型蒸餾（model distillation）**（Hinton et al., 2015; Hsieh et al., 2023）與**同策略蒸餾（on-policy distillation）**（Agarwal et al., 2024; Ouyang et al., 2022）皆透過更新學生模型權重來轉移能力，常伴隨**教師強制（teacher forcing）**、**推理解釋（rationales）**、**示範（demonstrations）** 與**獎勵訊號（reward signals）**。本研究則完全迴避**參數更新（parameter updates）**，將能力轉移發生在**推論時（inference-time）**。兩者可視為互補：蒸餾改變模型內部能力，harness 改變模型外部環境。

##### 2. 與提示工程與代理系統的關係

近年**代理系統（agentic systems）** 與工具使用框架（如 ReAct、ToolFormer、DSPy）也強調透過路由、記憶與工具來增強模型表現（Wei et al., 2022; Yao et al., 2022; Schick et al., 2023; Madaan et al., 2023）。本研究的貢獻在於：

- 將 harness 設計自動化，交由更強的建構者模型執行；
- 明確區分「強模型」與「弱模型」的角色，形成系統性的**強到弱能力轉移（strong-to-weak capability transfer）**；
- 透過大規模實證分析，量化 harness 各項機制對表現的貢獻，並指出認知負荷降低是關鍵機制。

相較於一般提示工程多聚焦於單一模型，本研究強調「為弱模型設計環境」，並以驗證集驅動迭代，更接近自動化機器學習（AutoML）中的 pipeline 搜尋。

##### 3. 與認知負荷理論的連結

作者引用 Sweller（1988）的認知負荷理論，指出小模型失敗未必只是內部能力不足，也可能是任務呈現方式（task presentation）造成過高負荷。這為 harness 設計提供了理論基礎：好的 harness 應該是「外部認知結構（cognitive structure）」，協助目標模型分配注意力、減少工作記憶負擔。

##### 4. 限制與潛在問題

- **領域侷限**：實驗僅聚焦於**心智理論（ToM）** 基準測試，雖然 ToM 具有挑戰性且結構豐富，但 harness 設計原則是否適用於數學推理、程式生成、多模態任務仍需驗證。
- **捷徑風險**：在 BigToM 上，harness 幾乎可將任務轉為規則化求解，這雖提升分數，但也引發「是否真正測量到目標模型的心智推理能力」的疑慮。若 harness 過度外部化，基準測試可能變成測量 harness 設計能力，而非目標模型能力。
- **建構者能力天花板**：對於遞迴深度 ≥ 2 的 Hi-ToM 與複雜貝葉斯推論，即使最佳 harness 仍有殘留錯誤，顯示外部結構無法完全彌補極端困難任務的內部能力缺口。
- **評估指標單一**：主要以準確率（accuracy）與宏觀平均（macro-average）為指標，對於 harness 的延遲、成本、可維護性、可解釋性等部署面向著墨較少。

#### 可重現性評估

本論文目前為 **Salesforce AI Research** 與**伊利諾大學厄巴納－香檳分校（University of Illinois Urbana-Champaign）** 研究人員發布的**預印本（preprint）**。根據提供的上下文，論文尚未提及是否公開：

- 原始程式碼；
- harness 產生與評估的完整 pipeline；
- 四個 ToM 基準測試的預處理版本；
- 目標模型與建構者模型的確切 API 版本與參數設定；
- 最終 harness 的具體內容與提示模板。

由於實驗涉及多個商業模型（如 GPT-5.4-mini、Gemini-3.5-flash，以及作為建構者的強模型），即使程式碼公開，其他研究者仍需取得相同模型存取權才能完全重現結果。此外，論文中部分模型名稱（如 GPT-5.4-mini）可能為筆誤或假設性命名，實際對應模型版本需以作者最終釋出為準。

在缺乏開源資源的情況下，本研究的可重現性目前評為「有限」。建議作者未來釋出：

1. 完整的 harness 建構與評估程式碼；
2. 驗證集與測試集的切分方式；
3. 所有提示模板與中間迭代版本；
4. 模型 API 版本、溫度參數、取樣設定等細節；
5. 成本與延遲數據，以便社群評估實用性。

#### 未來研究方向

##### 1. 跨領域與跨任務泛化

未來研究可將 strong-to-weak scaffolding 擴展至數學推理（如 GSM8K、MATH）、程式合成（如 HumanEval）、科學問答（如 GPQA）與多模態任務。關鍵問題是：哪些任務結構適合被外部化為確定性程式碼？哪些任務仍必須依賴模型內部推理？

##### 2. 自動化 harness 設計的元學習

目前 harness 由建構者模型透過迭代試誤產生。未來可發展「harness 設計的元學習（meta-learning for harness design）」，讓建構者模型從多個任務中學習如何設計通用型 harness，減少每個新任務所需的驗證資料與迭代次數。

##### 3. 與訓練時蒸餾的結合

本研究強調 harness 是傳統蒸餾的**互補（complement）**。未來可探討兩階段策略：先以 harness 提升弱模型推論表現，再將 harness 增強後的輸出作為訓練資料進行**資料蒸餾（data distillation）**，使弱模型最終能內化部分外部結構，達到「無 harness 也能表現良好」的目標。

##### 4. 動態與適應性 harness

現有 harness 在測試時多為靜態結構。未來可研究**動態 harness（dynamic harness）**，根據每筆輸入的難度即時調整路由深度、是否呼叫外部求解器、或是否啟用驗證階段，以在準確率與成本間取得更好權衡。

##### 5. 可解釋性與認知負荷量化

未來可發展系統性方法來量化 harness 降低了多少認知負荷，例如測量目標模型所需推理步驟、注意力分佈或工作記憶負擔。這將有助於區分「真實推理支援」與「基準測試捷徑（benchmark-specific shortcuts）」。

##### 6. 安全性與穩健性

當 harness 包含大量確定性程式碼與路由規則時，可能引入新的失敗模式，例如對抗樣本攻擊路由邏輯、格式強制導致資訊遺失、或過度依賴外部求解器而產生級聯錯誤。未來需研究 harness 的對抗穩健性與錯誤傳播分析。

##### 7. 開放式評估框架

建立標準化的 strong-to-weak scaffolding 評估框架，涵蓋不同強度的建構者模型、目標模型、任務領域與資源限制，將有助於比較不同 harness 設計方法，並推動該領域從工程技藝走向科學方法。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文挑戰了傳統知識蒸餾的基本前提，也就是「要縮小強模型與弱模型之間的能力差距，必須對弱模型進行額外訓練或參數更新」。作者提出一個互補問題：能力轉移是否可以在測試時／推論時發生，而不需要更動目標模型的權重。具體而言，他們研究「強到弱鷹架輔助」，讓較強的建構者模型為較弱的目標模型設計推論時輔助架構（harness），從而提升目標模型在心智理論（Theory-of-Mind, ToM）基準測試上的表現。

**Q2：現有的訓練時蒸餾方法有什麼不足，為什麼需要測試時的能力轉移？**
A：現有的訓練時蒸餾方法——例如教師強制、同策略蒸餾、資料蒸餾——都假設必須透過額外訓練讓學生模型內化教師的行為，這通常需要大量資料、運算資源，以及對目標模型參數的存取權限。然而，小模型表現不佳有時並非單純因為內部能力不足，而是因為任務呈現方式造成了過高的認知負荷。測試時輔助架構採取另一條路徑：不讓模型變得更強，而是讓任務對模型來說更容易解決，從而避開重新訓練的成本與限制。

**Q3：為什麼強到弱鷹架輔助在當前 AI 部署趨勢下特別重要？**
A：隨著模型部署從單一提示走向代理式系統，小型語言模型越來越常嵌入在包含解析、路由、工具選擇與驗證的複雜流程中，而非單獨使用。強到弱鷹架輔助提供了一種系統化的方式，讓強模型把認知結構轉移給弱模型，而無需重新訓練後者。這不僅能降低部署成本，也為評估建構者模型「設計可複用推論環境」的能力提供了新的研究場景。

**Q4：這篇論文提出的核心方法是什麼？**
A：核心方法是讓建構者模型在僅能看到 5% 資料作為驗證集的情況下，迭代式地精煉一個推論時輔助架構（harness），最終在完整測試集上評估該架構對固定目標模型的幫助。這個 harness 可以包含任務路由、提示模板、確定性求解器、少樣本示範、驗證流程以及答案格式強制等多種機制。整個過程中，目標模型不進行任何參數更新，建構者模型也無法接觸完整測試集，因此成功的 harness 必須學到可跨樣本遷移的任務結構，而非記住特定答案。

**Q5：相較於傳統蒸餾，這項研究最重要的創新點是什麼？**
A：最重要的創新在於將能力轉移的單位從「模型權重」轉移到「推論時輔助架構」，正式定義了「強到弱鷹架輔助」這個獨立的推論時能力轉移設定。這意味著強模型不是把知識灌進弱模型，而是把解題所需的認知結構、路由邏輯與格式控制外部化為程式或流程。這種 AI4AI（AI 驅動 AI）的觀點讓強模型扮演「鷹架工程師」的角色，開啟了有別於傳統訓練時蒸餾的能力轉移範式。

**Q6：作者在方法設計上做了哪些關鍵選擇？**
A：作者選擇以心智理論（ToM）基準測試作為實驗場域，因為這類任務對小模型來說困難，但同時具有可被外部結構利用的規律性，例如依子類型路由、分解中間狀態或進行符號求解。他們只讓建構者模型使用 5% 資料作為驗證集，並允許其迭代精煉 harness，以模擬真實部署中無法取得完整測試集的情境。此外，他們系統性地比較了建構者模型的推理投入、平台效應與不同目標模型，從而分離出 harness 設計本身的貢獻。

**Q7：實驗使用了哪些基準測試，為什麼選擇它們？**
A：實驗使用了四個具代表性的心智理論（ToM）基準測試，包括 BigToM 與 Hi-ToM 等。這些任務要求模型追蹤嵌套信念、視角轉換、隱藏資訊與貝葉斯目標推論，對小型模型構成嚴峻挑戰。同時，這些測試也具備明確的任務結構，使得外部輔助架構可以透過子類型路由、確定性程式碼與一致性檢查來分擔目標模型的推理負擔。

**Q8：這項研究最關鍵的實驗結果是什麼？**
A：最強的 harness 將 GPT-5.4-mini 在四個 ToM 基準測試上的平均準確率從 0.49 提升到 0.91，絕對增益高達 0.42，而且所有建構者配置都帶來正向的淨提升。進一步分析顯示，這些增益主要來自於將不穩定的模型推理卸載為確定性程式碼、針對基準測試的路由，以及嚴格的答案格式強制，而非單純讓目標模型做更廣泛的推理或取樣。此外，較弱的目標模型獲得的幫助更大，而建構者模型的推理投入與 harness 品質呈現單調遞增關係。

**Q9：作者進行了哪些消融或機制分析來解釋 harness 為何有效？**
A：作者發現，單純增加驗證資料量、擴大取樣範圍或要求目標模型產生更長推理，並不是提升的主要來源；真正的關鍵在於把推理結構外部化、使用確定性程式碼，以及強制答案格式。他們也發現平台效應相對於建構者模型本身的能力來說較為有限，說明 harness 品質主要取決於建構者模型的設計能力。殘留錯誤則集中在最困難的情境，例如 Hi-ToM 中遞迴深度至少為二的高階信念推理，以及貝葉斯目標推論的特定子類型。

**Q10：這項技術最適合應用在哪些實務場景？**
A：這項技術特別適合無法或不宜重新訓練目標模型的場景，例如邊緣裝置上的小型模型、成本敏感的 API 服務，或需要快速適應新任務的代理式系統。在這些情境中，強模型可以扮演「鷹架工程師」，自動為弱模型設計推論流程，而無需接觸其內部權重。這也適用於需要高可解釋性或模組化維護的產品，因為 harness 的邏輯通常以可讀的程式碼或提示模板形式存在。

**Q11：若要在產品中落地，需要考慮哪些工程與設計議題？**
A：首先需要考慮 harness 的延遲與複雜度，因為額外的路由、驗證與工具呼叫會增加推論時間與成本。其次，必須避免 harness 過度依賴特定基準測試的捷徑，導致在真實世界資料上泛化不良。最後，還需評估建構者模型本身的可靠性與可取得性，因為 harness 品質高度依賴其設計能力，且需要持續維護與版本控制。

**Q12：這項研究對整個 AI 領域可能帶來什麼影響？**
A：這項研究將 AI 社群的注意力從「如何訓練更強的單一模型」部分轉移到「如何設計更好的推論時系統架構」，並強化了 AI4AI 的趨勢。它顯示強模型不僅能生成資料或答案，還能設計可複用的認知結構來輔助其他模型，這可能改變我們評估與比較模型能力的方式。長遠來看，這有助於建立更模組化、可解釋且可重現的代理式系統，並與傳統訓練時蒸餾形成互補。

**Q13：這項研究有哪些已承認的限制？**
A：研究主要聚焦於心智理論（ToM）基準測試，因此其結論是否能推廣到數學、程式碼或多模態等其他領域仍需進一步驗證。此外，由於建構者模型只能使用 5% 的資料進行驗證，harness 可能會過度擬合這些少數樣本或利用特定測試的結構性捷徑。研究也受限於所選建構者模型與目標模型的能力範圍，不同模型族之間的轉移效果可能有所差異。

**Q14：即使在最佳 harness 下，哪些類型的錯誤仍然難以解決？**
A：殘留錯誤主要集中在最高難度的情境，例如 Hi-ToM 中遞迴深度達到二以上的高階信念推理，以及複雜的貝葉斯目標推論子類型。在 BigToM 上，部分最佳 harness 甚至發現答案可以透過結構化規則完全推導，這雖然帶來高分，卻也引發這些增益是否完全等同於「真正推理」的疑問。這些失敗模式顯示，當任務所需的內部推理深度超過外部結構能卸載的範圍時，harness 的效果會達到瓶頸。

**Q15：未來研究可以朝哪些方向延伸？**
A：未來可以將強到弱鷹架輔助擴展到 ToM 以外的領域，例如數學推理、程式合成或多模態任務，以檢驗其通用性。另一個方向是發展自動化的 harness 搜尋或元學習方法，讓建構者模型能夠在更少驗證資料與更少迭代下產生高品質輔助架構。此外，結合訓練時蒸餾與推論時 harness 設計，並探討推論時能力轉移的理論極限與泛化保證，也是值得深入探索的課題。

## 實務應用指南

### 適用場景

1. **企業內部知識問答（Small-Model + RAG）**  
   在目標模型為輕量版語言模型的前提下，由強模型設計 harness：依問題類型路由到檢索、計算或摘要分支，強制輸出引用格式與置信度標記，讓小模型在無需重新訓練的情況下穩定回答內部文件問題。

2. **醫療／法規文件初審**  
   小模型負責初步抽取與判讀，harness 將高風險判斷（劑量計算、法條衝突檢查）卸載為確定性規則或外部工具，並透過格式強制與一致性驗證降低漏判風險。

3. **教育輔導機器人**  
   依題型（數學、閱讀理解、心智理論式對話）進行基準測試 aware 路由，搭配 few-shot 提示模板與答案格式強制，使小模型能穩定引導學生推理而非直接給答案。

4. **客服意圖分類與回覆生成**  
   小模型執行意圖識別與草稿生成，harness 負責實體抽取、知識庫查詢、敏感詞檢查與最終 JSON 格式輸出，減少目標模型在不穩定推理上的負擔。

5. **邊緣裝置上的結構化推論**  
   在運算受限裝置部署小模型，由強模型預先設計 harness，將需要遞迴或機率推理的步驟轉為確定性程式碼，只把最適合語言模型處理的部分交給目標模型執行。

### 實作前置條件

**資料**
- 一份具有代表性的 **驗證集**（約佔整體資料 5%），包含輸入、正確答案與常見錯誤類型。
- 明確的輸入輸出規格、答案格式與評估指標（accuracy、F1、格式合規率等）。
- 領域知識文件或工具 API 規格，供 harness 進行確定性卸載。

**運算**
- 可呼叫的 **建構者模型（builder model）** API（能力顯著高於目標模型）。
- 已部署的 **目標模型（target model）** 推論環境（地端、邊緣或 API）。
- 可執行 harness 的程式環境（Python、容器、工具呼叫權限）。
- 評估 pipeline，能自動執行 harness、收集預測、計算指標並回傳錯誤案例。

**技能**
- Prompt engineering 與 few-shot 示範設計能力。
- Python 與工具整合能力（正規表示式、解析器、外部 API）。
- 評估指標設計與錯誤分析能力。
- 領域專家協作，以設計正確的確定性規則與驗證邏輯。

---

### 實作步驟建議

1. **定義任務與成功指標**  
   明確目標模型要解決的任務、可接受的延遲與正確率門檻，並決定 harness 的輸出格式。

2. **選擇 builder 與 target 模型**  
   builder 應明顯強於 target；target 選擇需考量部署成本與延遲。記錄平台與版本，避免平台效應干擾評估。

3. **建立小型驗證集與評估腳本**  
   從資料中抽取約 5% 作為驗證集，並建立自動化評估腳本，能輸出每題預測、正確與否與錯誤類型。

4. **設計初始 harness**  
   讓 builder 產生第一版 harness，包含：任務路由邏輯、提示模板、few-shot 示範、答案格式強制與基礎驗證。

5. **迭代式精煉（Iterative Refine）**  
   在驗證集上執行 harness，將錯誤案例與目前程式碼回饋給 builder，請其修改路由、提示或加入確定性檢查。重複數輪直到驗證集表現收斂。

6. **強化確定性卸載與格式控制**  
   針對不穩定的模型推理步驟，優先改由確定性程式碼、外部工具或符號求解處理；同時嚴格強制答案格式，避免解析失敗。

7. **在獨立測試集或影子環境評估**  
   使用未參與迭代的完整測試集或生產影子流量進行最終評估，確認 harness 沒有過度擬合驗證集。

8. **部署、監控與持續更新**  
   上線後監控格式錯誤率、殘差錯誤類型與延遲；定期用新資料讓 builder 重新精煉 harness，無需重新訓練目標模型。

### 潛在風險與注意事項

| 風險 | 說明 | 因應方式 |
|---|---|---|
| **過度擬合驗證集** | harness 針對 5% 資料調整，可能學到捷徑而非通用結構。 | 保留獨立測試集；進行錯誤類型分析；要求 builder 產生可解釋的路由規則。 |
| **Benchmark-specific shortcut** | harness 利用資料偏差而非真正提升推理能力。 | 設計對抗樣本與跨資料集驗證；將確定性規則與領域知識掛鉤。 |
| **格式強制過度嚴格** | 目標模型因格式要求而產生無效或迴避答案。 | 加入容錯解析與 fallback 流程；監控格式合規率與正確率同步變化。 |
| **建構者能力天花板** | builder 本身無法理解任務結構時，harness 品質受限。 | 選擇更強 builder 或增加 builder 推理投入；引入領域專家提示。 |
| **延遲與維護成本** | 多輪路由、工具呼叫與驗證會增加推論延遲與系統複雜度。 | 模組化設計；對延遲敏感路徑簡化 harness；使用快取與非同步檢查。 |
| **安全與幻覺風險** | harness 可能將錯誤輸出包裝成合規格式。 | 加入獨立驗證器與人在迴路（human-in-the-loop）機制；限制高風險決策自動化。 |
| **平台效應** | 不同模型供應商的輸出習性不同，harness 可能遷移困難。 | 將平台相關邏輯封裝為可替換模組；在 target 更換時重新評估。 |

### 與其他技術的整合建議

- **與 RAG（檢索增強生成）整合**：harness 可先判斷問題是否需要檢索，再決定呼叫向量資料庫或知識圖譜，並強制引用格式，讓小模型專注於摘要與生成。
- **與 Agent 框架整合**：將 harness 視為 agent 的協調層，負責任務分解、工具選擇與驗證迴圈，目標模型則作為其中一個輕量推理節點。
- **與訓練時蒸餾互補**：harness 用於快速部署與迭代；當資料與運算資源充足時，可將 harness 中驗證有效的結構（如示範、推理步驟）轉為訓練資料，進行傳統模型蒸餾。
- **與 LLMOps／MLOps 整合**：將 harness 版本化、納入 CI/CD 測試，並在每次更新 target 模型或 builder 模型時自動回歸測試。
- **與可觀測性工具整合**：記錄 harness 每個分支的呼叫次數、錯誤類型與延遲，作為後續精煉的依據。
- **與微服務架構整合**：將 harness 部署為獨立服務，target 模型與外部工具作為下游服務，便於擴展與降級。

### 給不同背景讀者的閱讀建議

**初學者**：先理解「強模型不重新訓練小模型，而是幫它設計推論流程」這個核心概念。重點閱讀論文的 Introduction 與「適用場景」相關段落，並把 harness 想像成「給小模型的考試作弊小抄＋檢查表」，不必一開始深入技術細節。

**AI 工程師**：請聚焦實作步驟與風險章節，特別注意「確定性卸載」、「格式強制」與「迭代式精煉」的實作細節。建議直接參考論文中的錯誤分析方式，設計自己的驗證集評估 pipeline，並將 harness 模組化以便維護。

**研究人員**：本研究提供了一個不同於傳統訓練時蒸餾的能力轉移設定。建議深入分析「強到弱鷹架輔助」與「認知負荷減輕」的因果機制，並思考如何將此框架擴展到 Theory-of-Mind 以外的推理任務，以及與參數更新方法的理論關係。

**產品經理**：本技術最適合「需要快速上線、運算成本敏感、但任務結構可被規則化」的應用。請評估你的場景是否有明確的輸入分類、可驗證的輸出格式與可用的外部工具；若有，harness 能在不重新訓練模型的情況下顯著提升小模型表現，縮短產品迭代週期。
