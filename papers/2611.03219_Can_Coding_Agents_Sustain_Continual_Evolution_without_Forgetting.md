- 每個資料集需能收集完整的執行軌跡（execution trajectory），包含代理的 prompt、工具呼叫、中間狀態與最終結果。
- 建議準備「保留集」（held-out set）以評估先前任務的效能是否退化。

**運算資源**
- 需具備執行基礎模型推理的 GPU 資源（論文中使用 DeepSeek-V4-Flash-0731 等模型）。
- 每輪演化需執行數百至數千次任務以收集足夠軌跡，整體實驗需支援多次完整迭代。
- 建議使用容器化環境（如 Docker）以重現各資料集的執行條件。

**技能前提**
- 熟悉 LLM 代理架構（prompt、工具呼叫、執行迴圈）的設計與除錯。
- 具備軟體工程基準測試（SWE-Bench 等）的環境建置經驗。
- 能閱讀並修改代理框架程式碼（Python 為主），並進行手動軌跡分析。
- 對持續學習（continual learning）與穩定性—可塑性權衡（stability–plasticity dilemma）有基本概念。

### 實作步驟建議

**步驟一：定義任務序列與演化方向**
參考論文中的六種持續演化方向，將欲處理的軟體工程任務排序成一個序列 𝒟 = (D₀, D₁, …, D_K)。每個方向代表一種任務類型轉換（例如「原始碼修復 → 測試生成」、「測試生成 → 功能新增」）。明確記錄每個方向的起點與終點資料集。

**步驟二：建立基準代理框架**
選用一個種子代理框架（如 Mini-SWE-Agent 或 NexAU₀），固定基礎模型 𝑀，僅演化代理框架 𝐻。在每個資料集上先量測未演化時的基準效能，作為後續比較的對照組。

**步驟三：選擇代理框架演化方法**
從兩種代表性方法中擇一：
- **AHE**：基於軌跡分析自動產生代理框架修改。
- **Meta-Harness**：以更高層次的元策略調整代理框架元件。
兩者皆需設定演化輪數、每輪的軌跡收集量與修改驗證機制。

**步驟四：執行第一階段演化**
在 D₀ 上執行多輪演化，每輪收集執行軌跡、套用演化方法 Ω、更新代理框架 𝐻ᵢ₊₁ = Ω(𝐻ᵢ, 𝒯ᵢ)，並記錄在 D₀ 上的效能變化。達到收斂或預期效能後停止。

**步驟五：執行第二階段演化並監測遺忘**
以第一階段產出的代理框架為起點，在 D₁ 上繼續演化。**關鍵**：每輪演化後，必須重新評估代理在 D₀ 上的效能，觀察是否出現災難性遺忘。建議繪製「迭代次數 vs. 來源任務效能」曲線（類似論文 Figure 1(a)）。

**步驟六：分析代理框架衝突**
收集至少數百條代理軌跡（論文使用 520 條以上），手動分析演化過程中引入的代理框架修改，並依三類衝突分類：
- **驗證衝突**（verification conflict）：產物閘門或測試條件改變導致先前任務通過的解被判為失敗。
- **工作流程衝突**（workflow conflict）：任務求解程序改變，破壞先前任務的執行路徑。
- **預算衝突**（budget conflict）：逾時或收斂條件調整，使先前任務在新規則下無法完成。

**步驟七：根據分析結果設計緩解機制**
針對識別出的衝突類型，設計對應的緩解策略，例如：保留驗證閘門的向後相容性、為不同任務類型維護獨立的程序模板、設定預算下限等。

**步驟八：建立持續評估管線**
將「演化—評估來源任務—分析衝突—調整」流程自動化，確保每次新任務演化後都能即時偵測遺忘現象，並將結果回饋至下一輪演化。

---

### 潛在風險與注意事項

**風險一：災難性遺忘幅度可能極大**
論文顯示，Meta-Harness 在 SWE-Bench 上達到 94.0% 後，僅經五輪 FeatureBench 演化即降至 32.0%，相對下降 66%。實作時不可假設「小幅下降可接受」，必須設定明確的遺忘警報閾值（例如來源任務效能下降超過 10% 即觸發警示）。

**風險二：不同演化方向的遺忘程度不一**
六種演化方向的遺忘幅度並不對稱。實作前應先以小型實驗掃描所有方向，找出最容易引發遺忘的轉換，並優先設計防護機制。

**風險三：手動軌跡分析成本高**
論文依賴手動分析 520 條以上軌跡來分類衝突，實務上難以規模化。可考慮建立半自動化的衝突偵測規則（例如：比對演化前後的驗證條件差異），但需注意規則可能無法涵蓋所有衝突類型。

**風險四：基礎模型版本影響結果**
論文中 DeepSeek-V4-Flash-0731 的結果未必能直接外推到其他模型。不同基礎模型對代理框架修改的敏感度不同，遷移至新模型時需重新評估。

**風險五：單一代理框架難以同時最佳化所有任務**
論文的隱含結論是：現有方法在單一任務上表現良好，但在持續演化下會失效。實作時應考慮是否改用「多代理框架分工」而非「單一代理框架持續演化」的架構。

**緩解建議**
- 為每個任務類型維護「效能保留快照」，定期比對。
- 在演化流程中加入「來源任務回放驗證」步驟。
- 設計模組化代理框架，使驗證、工作流程、預算等元件可獨立演化，降低耦合性。

### 與其他技術的整合建議

**與持續學習（Continual Learning）技術整合**
可借鏡持續學習中的經驗回放（experience replay）、知識蒸餾（knowledge distillation）與參數隔離（parameter isolation）等技術，將其概念移植到代理框架層級：保留先前任務的軌跡樣本、在演化時混入重播、或為不同任務維護獨立的代理框架子模組。

**與版本控制系統整合**
將每次代理框架演化視為一次「commit」，使用 Git 等工具管理代理框架版本。當偵測到災難性遺忘時，可快速回溯至前一版本，並比對差異以定位衝突來源。

**與 CI/CD 管線整合**
將「演化—評估—衝突分析」流程整合至 CI/CD，每次代理框架更新自動觸發來源任務回歸測試。這與傳統軟體工程中的回歸測試概念一致，可直接借用既有基礎設施。

**與多代理人系統整合**
若系統中已有任務分派機制，可考慮為不同任務類型部署獨立的代理框架實例，僅共享基礎模型。這雖會增加運算成本，但能徹底避免代理框架層級的災難性遺忘。

**與可觀測性工具整合**
整合 OpenTelemetry、LangSmith 等軌跡追蹤工具，自動記錄每次演化的代理行為差異，使衝突分析從「手動」轉為「半自動」，降低長期維運成本。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「程式碼代理 = 基礎模型 + 代理框架」這個基本架構，再閱讀論文的問題定義章節（Section 2）。重點掌握「災難性遺忘」這個核心概念——代理在學會新任務後，反而忘記了舊任務。讀完摘要與問題定義後，可先跳至結論與圖表，建立直觀印象，再回頭細讀方法章節。

**給 AI 工程師**：重點關注 RQ1 的實驗設計與六種演化方向的建構方式，這對實務上設計多任務代理系統極具參考價值。特別留意 Meta-Harness 從 94.0% 降至 32.0% 的案例，這提醒我們：單一指標的最佳化不等於系統的長期可用性。建議在自己的代理系統中加入「來源任務回歸評估」機制，並將代理框架元件模組化以便隔離衝突。

**給研究者**：本論文開啟了一個新研究方向——代理框架層級的持續學習。RQ2 的三類衝突分類（驗證、工作流程、預算）是重要的理論貢獻，但目前僅基於 520 條軌跡的手動分析，未來可朝自動化衝突偵測、衝突量化指標、以及設計「衝突感知」的演化方法等方向延伸。此外，論文僅探討兩個任務的序列，可進一步研究更長任務序列與非順序演化情境。

**給產品經理**：本研究的核心理念是「代理不能只會一件事」。在規劃 AI 程式助手產品時，應將「多任務持續可用性」列為關鍵需求，而非僅追求單一基準測試的高分。論文的實證數據（效能從 94% 降至 32%）是向高層與技術團隊溝通此風險的有力證據。建議在產品 roadmap 中預留「代理框架穩定性測試」階段，避免在實際部署後才發現代理「學了新技能、忘了舊技能」。
