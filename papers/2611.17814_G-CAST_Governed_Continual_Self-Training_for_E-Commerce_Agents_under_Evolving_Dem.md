G-CAST 的核心設計理念是將「檢查點轉換（checkpoint transition）」而非「訓練任務完成」視為適應的單位，這是一個根本性的系統架構轉變。整個系統圍繞五個被聯合版本化的物件建構：已部署模型（deployed model）、當前能力合約（capability contract）、可執行獎勵（executable reward）、學習證據（learning evidence）以及累積評估分類帳（cumulative evaluation ledger）。這種設計確保了模型、訓練資料、獎勵函數三者之間的同步性，避免了傳統後訓練（post-training）流程中三者各自演進而產生的錯位問題。

**獎勵路由、熵優先的資料編排機制（Reward-Routed, Entropy-Prioritized Data Orchestration）**

此機制的關鍵創新在於將「是否訓練」與「如何優先排序訓練範例」兩個決策解耦。系統對每個查詢（query）使用已接受的檢查點（accepted checkpoint）產生多個展開（rollouts），並根據獎勵模式將其分流至三個訓練分支：

1. **全失敗查詢（all-failure queries）**：當所有展開都失敗但具有已驗證的目標（verified targets）時，路由至監督式微調（Supervised Fine-Tuning, SFT）。這類樣本提供了明確的正確行為信號，適合用模仿學習的方式注入新能力。
2. **混合結果查詢（mixed-outcome queries）**：部分展開成功、部分失敗時，路由至強化學習（Reinforcement Learning, RL）。此類樣本提供了相對偏好信號，適合策略優化。
3. **全成功查詢（all-success queries）**：所有展開都成功時，路由至回歸監控（regression monitoring），僅用於評估而不直接參與訓練，避免過擬合於已掌握的行為。

在每個分支內部，系統使用**詞元級熵（token-level entropy）**作為範例優先排序的信號。這個設計的精妙之處在於：熵僅用於衡量模型的不確定性，而非正確性，因此它作為「池內優先排序信號（within-pool prioritization signal）」使用，而非作為路由決策的依據。這種解耦避免了將「模型不確定的樣本」與「模型錯誤的樣本」混為一談的常見陷阱。

**能力合約驅動的獎勵演化機制（Capability-Contract-Driven Reward Evolution）**

當獎勵可靠性檢查（reward reliability check）標記出可能的獎勵錯誤時，訓練會被暫停，系統進入獎勵演化迴圈。該迴圈將可執行獎勵（executable reward）對照當前能力合約進行稽核，確認存在錯位後，通過以下閘門（gates）修復獎勵：

- **目標案例驗證（target-case validation）**：確認獎勵能正確評估預期行為
- **新舊重打分（old-versus-new rescoring）**：確保獎勵更新不會破壞既有評估的一致性
- **軌跡重播（trajectory replay）**：在歷史軌跡上驗證更新後的獎勵表現

通過這些閘門後，學習證據才會被重新打分（rescored），確保進入訓練階段的監督信號是有效的。

**受控檢查點轉換（Governed Checkpoint Transition）**

候選模型從不可變的父模型（immutable parent）訓練而成，僅在同時通過新興任務（emerging tasks）與所有先前保留能力（previously retained capabilities）的評估後，才能取代已接受的檢查點。被拒絕的候選、回歸案例與獎勵錯誤都會被記錄，引導下一輪的訓練。這種設計形成了閉環的負回饋機制，使系統能夠持續自我修正。

3. **多模態/多通路零售助手**：當購物助手從純文字擴展到支援圖片搜尋、語音輸入，或整合直播、社交電商通路時，能力合約（capability contract）會大幅擴張，G-CAST 的受控獎勵演化能防止獎勵函數錯評新行為。

4. **企業內部流程代理（IT/HR/採購）**：當企業內部代理需要串接新 API、新審批流程或新資料源時（例如新增合約審查工具、差旅訂票系統），G-CAST 可在保護既有功能的同時學習新流程。

5. **監管/合規要求快速變動的金融或醫療助理**：當新法規要求代理必須使用新的合規檢查工具或遵循新的詢問程序時，G-CAST 的獎勵演化與軌跡重播（trajectory replay）機制可確保獎勵函數與新規範同步。

## 實作前置條件

### 資料面
- **生產環境日誌**：需有完整的對話軌跡、工具呼叫記錄、最終獎勵分數（即使是粗略的），這是「生產證據」的來源。
- **能力合約版本庫**：所有工具、技能、操作程序的 schema 與說明需有版本控制，能與模型版本、獎勵版本對齊。
- **黃金標註集（golden set）**：需準備一份「已知正確」的標註資料，用於獎勵演化時的目標案例驗證（targeted validation）與已知正確回歸檢查（known-correct regression checks）。
- **累積評估分類帳（cumulative evaluation ledger）**：需保存歷次檢查點在所有「已接受能力」上的評估結果，作為不退化保證。

### 計算面
- **可產生多次 rollout 的推理環境**：每個查詢需能產生多個軌跡以觀察獎勵分布（全失敗/混合/全成功）。
- **可中斷與恢復的訓練管線**：訓練需能在獎勵可靠性檢查失敗時暫停，並在獎勵修復後重新評分。
- **不可變父檢查點（immutable parent checkpoint）**：需有儲存與管理多代檢查點的基礎設施。
- **Token-level 熵擷取能力**：推理引擎需能輸出每個 token 的熵值，用於池內優先排序。

### 技能面
- 熟悉 SFT 與 RL（建議 GRPO/PPO 等可處理 token-level 訊號的演算法）。
- 能撰寫「可執行獎勵規則」（executable reward rules），並對其做版本化、單元測試與回歸測試。
- 具備 MLOps 經驗：檢查點管理、A/B 評估、灰度發布。
- 對領域（電商/客服/採購）的業務流程與失敗模式有深入理解。

## 實作步驟建議

### 階段一：建立「能力合約」與版本化基礎
1. 盤點現有工具、技能、操作程序，定義結構化的 capability contract schema。
2. 建立模型版本、capability contract 版本、可執行獎勵版本的三方聯合版本控制。
3. 準備黃金標註集與累積評估分類帳的儲存結構。

### 階段二：實作獎勵路由與熵優先的資料編排
1. 為每個查詢產生多個 rollout，計算獎勵分布。
2. 實作三路分流：
   - **全失敗 + 已驗證目標** → SFT 池
   - **混合結果** → RL 池
   - **全成功** → 回歸監控池
3. 在每池內以 token-level 熵排序，優先訓練高不確定性樣本。
4. 設計「獎勵可靠性檢查」：當某分支獎勵分布異常（如全成功但語意可疑）時，暫停訓練並觸發獎勵稽核。

### 階段三：實作受控獎勵演化
1. 將獎勵函數拆解為可執行的規則元件，每個元件可獨立版本化。
2. 當 capability contract 更新時，自動比對哪些規則需要調整。
3. 任何獎勵更新必須通過四道閘門：
   - **目標案例驗證**（在黃金集上表現正確）
   - **已知正確回歸檢查**（不退化既有正確行為）
   - **新舊獎勵離線重評分**（old-vs-new rescoring）
   - **軌跡重播**（trajectory replay，確認更新後評分穩定）
4. 通過後才對歷史證據重新評分並進入訓練。

### 階段四：受控檢查點轉換
1. 從不可變父檢查點訓練候選模型。
2. 候選模型必須同時通過：
   - **新興任務評估**（emerging tasks）
   - **既有能力評估**（previously retained capabilities）
3. 僅當雙通過才替換 accepted checkpoint；否則記錄拒因，引導下一輪。
4. 灰度發布到生產，累積新一輪的生產證據。

### 階段五：建立持續運轉的閉環
1. 設定每日/每週自動觸發新一輪自我訓練。
2. 監控「拒絕率」、「獎勵演化頻率」、「新能力採用率」等指標。
3. 定期審查累積評估分類帳，識別長期未改善的子能力。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解措施 |
|------|------|----------|
| **獎勵博弈（reward hacking）** | 模型可能學會「騙過獎勵」而非真正改善行為 | 嚴格執行四道獎勵閘門；保留軌跡重播；定期人工抽檢 |
| **災難性遺忘** | 新能力訓練可能犧牲既有能力 | 累積評估分類帳是強制閘門；全成功樣本進入回歸監控池 |
| **獎勵演化過於頻繁** | capability contract 變動可能觸發大量獎勵更新，造成訓練不穩 | 設定獎勵更新冷卻期；要求每次更新必須有可解釋的契約變更對應 |
| **熵訊號誤用** | 高熵不等於高價值，可能選到無意義的困難樣本 | 熵僅作為池內優先排序，不跨池使用；保留一定比例隨機抽樣 |
| **黃金集漂移** | 隨業務變化，黃金集可能過時 | 定期由領域專家更新黃金集；追蹤黃金集上的模型表現趨勢 |
| **生產證據偏差** | 線上分布可能偏向特定使用者群 | 對證據做分層抽樣；監控子群表現差異 |
| **檢查點轉換的灰度風險** | 即使通過評估，線上長尾場景仍可能失敗 | 採用小流量灰度；保留快速回退機制 |
| **可執行獎勵規則的維護成本** | 規則越多越難維護 | 模組化設計；為每條規則撰寫單元測試；建立規則依賴圖 |

## 與其他技術的整合建議

- **與 ACE（context playbook 演化）整合**：ACE 在固定的模型上更新上下文，G-CAST 在更新模型。可將 ACE 的 playbook 視為「快速層」，G-CAST 為「慢速層」，當 playbook 變得過於複雜或無法收斂時，觸發 G-CAST 將行為內化到模型權重。
- **與 Q-Evolve 整合**：Q-Evolve 的過程回饋可作為 G-CAST 獎勵演化的一個輸入來源，但需注意 Q-Evolve 假設任務固定，G-CAST 需在其上加入 capability contract 版本對齊。
- **與 SIA（harness + weight 共同更新）整合**：SIA 處理固定任務下的共同更新；G-CAST 可借用其「harness 變更 → 觸發 weight 更新」的觸發邏輯，但補上「任務本身也在變」的治理機制。
- **與自主訓練後管線（PostTrainBench、AutoTrainess）整合**：這些系統擅長構造訓練管線，G-CAST 可作為其上層的「治理層」，決定何時啟動、何時暫停、如何驗證。
- **與 RAG / 工具檢索整合**：當新工具加入時，G-CAST 的 capability contract 變更可自動觸發工具描述的重新嵌入與檢索索引更新。
- **與監控系統整合**：將 G-CAST 的「拒絕率」、「獎勵演化事件」、「新能力採用率」接入企業級可觀測性平台（如 Grafana、Datadog），便於跨團隊協作。

## 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節前半段，理解「為什麼部署後的 LLM 代理會越來越不好用」這個核心問題——這是「需求漂移」與「工具框架演進」共同造成的。接著看圖 1（系統總覽）與第 1 節後半段的「三種不匹配」（模型、資料、獎勵）。先建立直覺，再進入技術細節。

**給 AI 工程師**：重點讀第 1 節的「獎勵路由 + 熵優先」機制、第 3 節（假設存在）的實作細節，以及消融實驗。特別注意「為什麼熵只用作池內優先排序而非跨池」這個設計選擇——這是論文的核心 insight 之一。建議在自己的資料上重現三路分流，觀察分布是否符合預期。

**給研究者**：本文的核心貢獻在於把「checkpoint transition」而非「training job completion」定義為適應單位，並提出 capability contract 驅動的獎勵演化。可從三個方向延伸：(1) 形式化 capability contract 的語義與版本對齊；(2) 研究獎勵演化閘門的最優組合；(3) 探索在多代理協作場景下，如何為每個代理維護獨立的 capability contract 與共享的累積評估分類帳。

**給產品經理**：重點理解「為什麼不能只靠人工定期重訓」——因為需求與工具都在以天為單位變化。G-CAST 的價值在於把「模型更新」從一次性專案變成持續運轉的閉環。建議關注三個產品指標：新需求的首次解決率、既有需求的退化率、獎勵/工具變更到模型上線的延遲。論文的部署案例（Yuancai）證明了這條路徑在真實 B2B 場景可行。
