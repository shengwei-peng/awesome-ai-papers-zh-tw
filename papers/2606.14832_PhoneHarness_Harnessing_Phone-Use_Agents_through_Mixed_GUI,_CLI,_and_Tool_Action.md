# PhoneHarness：透過混合 GUI、CLI 與工具動作運用手機使用代理

## ⚡ TL;DR

現有手機代理基準僅評估 GUI 螢幕操作，無法涵蓋真實混合工作流程。
本文提出 PhoneHarness，整合 CLI、GUI 委派與主機端工具，並以可驗證執行追蹤評估。
在標註評估集上達 75.0% 通過率，超越非 PhoneHarness 設定 12.9 百分點。

## 摘要翻譯

手機使用代理（phone-use agent）被日益期待能完成真實的行動工作流程（mobile workflow），而不僅僅是預測下一個螢幕動作（screen action）。然而，目前許多行動代理文獻仍主要將代理視為 GUI（Graphical User Interface，圖形使用者介面）控制器來評估——觀察螢幕、發出點擊與滑動，並以目標應用狀態（target app state）進行評分。真實的手機使用任務範疇更為廣泛：這類任務需要判斷何時該使用應用 GUI、裝置端（device-side）命令或結構化工具（structured tools），並留下預期副作用（side effect）確實發生的證據。我們提出 PhoneHarness，一個用於研究手機使用代理在可驗證行動工作流程上表現的混合動作基準（mixed-action benchmark）與執行框架（execution harness）。PhoneHarness 在 GUI、CLI（Command Line Interface，命令列介面）與主機端（host-side）工具動作上執行裝置端代理迴圈（agent loop），結合確定性動作路由（deterministic action routing）、有界 GUI 委派（bounded GUI delegation）與可稽核執行追蹤（auditable execution trace）。其基準 PhoneHarness Bench 評估代理是否能以可觀察的副作用完成任務，而不僅僅是能否產生看似合理的最終答案。在標註評估分割（annotated evaluation split）上，PhoneHarness 達到 75.0% 的通過率（pass rate），超越最強的非 PhoneHarness 設定（non-PhoneHarness settings）12.9 個百分點（percentage points）。因此，PhoneHarness 與 PhoneHarness Bench 扮演著不同但相互依存的角色：執行框架使混合手機工作流程得以執行，而基準則衡量代理是否能可靠且安全地使用該執行框架。我們的發現顯示，可靠的手機自動化有賴於動作介面路由（action-surface routing）與可驗證執行（verifiable execution），而非僅憑視覺 GUI 控制。

### 核心貢獻（3～5點）
- **提出 PhoneHarness 系統**：一個結合 GUI、CLI 與主機端工具動作的混合動作執行框架，支援裝置端代理迴圈，使手機使用代理能在可驗證的行動工作流程上運作。
- **設計 PhoneHarness Bench 基準**：以可觀察的副作用而非僅以最終螢幕狀態作為評估依據，強調代理必須留下預期副作用確實發生的證據。
- **整合三大技術機制**：確定性動作路由（deterministic action routing）、有界 GUI 委派（bounded GUI delegation）與可稽核執行追蹤（auditable execution trace），兼顧執行的可預測性與安全性。
- **實證效能優勢**：在標註評估分割上達到 75.0% 的通過率，超越最強的非 PhoneHarness 設定達 12.9 個百分點，驗證混合動作路由相較於純視覺 GUI 控制的效益。
- **釐清系統與基準的互補角色**：PhoneHarness（執行框架）使混合手機工作流程得以執行，PhoneHarness Bench（基準）則衡量代理使用該框架的可靠性與安全性，兩者相輔相成。

### 適合對象
- **行動代理（mobile-agent）研究人員**：關注 GUI 控制、視覺定位（visual grounding）與螢幕導航（screen-navigation）技術的學者與工程師。
- **語言模型代理（language-model agents）開發者**：從事工具使用基準（tool-use benchmarks）、模型路由（model routing）與代理迴圈設計的研究團隊。
- **企業自動化與工作流程研究者**：探討企業工作流程基準（enterprise workflow benchmarks）、行動工作流程自動化與可驗證執行（verifiable execution）的實務應用者。
- **AI 安全與稽核從業者**：對副作用驗證（side-effect verification）、安全／追蹤稽核（safety / trace audit）與可稽核執行追蹤（auditable execution trace）感興趣的研究者。
- **基準設計與評估方法論學者**：從事混合動作基準（mixed-action benchmark）、標註評估分割（annotated evaluation split）與通過率（pass rate）量測設計的研究人員。

## 深度分析

#### 方法論解析

PhoneHarness 的核心方法論建立在「混合動作空間」(mixed-action space) 的設計哲學上，試圖突破現有行動代理研究將手機使用窄化為螢幕導航 (screen-navigation) 問題的框架。其方法論可從三個層次解析：

**一、執行框架 (Harness) 的架構設計**

PhoneHarness 採用「裝置端–主機端」(device-side / host-side) 雙層架構。裝置端在 Android 環境中運行手機代理迴圈 (agent loop)，負責感知螢幕狀態並做出決策；主機端則提供模型路由 (model routing)、GUI 執行 (GUI execution) 與 MCP 風格 (Model Context Protocol) 的工具存取。這種分離設計的關鍵在於：手機本身仍是「有狀態的執行介面」(stateful execution surface)，而需要較大計算資源或敏感權限的操作則委派給主機端工具。

動作空間 (action space) 由三種介面 (action surface) 組成：
1. **確定性 CLI 執行 (deterministic CLI execution)**：透過命令列介面執行裝置端指令，適合結構化、可預測的操作。
2. **有界 GUI 委派 (bounded GUI delegation)**：將視覺導航任務委派給 GUI 代理，但限制其執行範圍以避免無限探索。
3. **主機端 MCP 工具呼叫 (host-side MCP tool calls)**：透過標準化協議存取外部工具，處理裝置端難以或不適合執行的任務。

「確定性動作路由」(deterministic action routing) 是此設計的關鍵機制——代理根據任務特性決定使用哪種介面，而非盲目地依賴 GUI 操作。

**二、基準 (Benchmark) 的任務設計**

PhoneHarness Bench 的任務池包含 14 個 mock-app 任務、45 個真實應用程式 (real-app) 任務、30 個探索性安全任務，並從 181 個候選任務中篩選出 124 個標註評估分割 (annotated evaluation split)。任務設計刻意涵蓋需要跨介面協作的真實工作流程，例如「在應用程式中尋找電影、查詢額外發行資訊、摘要結果並寄送電子郵件」——此任務橫跨 app 導航、外部擷取 (external retrieval)、文字處理 (text processing) 與改變狀態的通訊動作 (state-changing communication action)。

**三、副作用驗證 (Side-effect Verification) 模式**

此方法論最具創新性的部分在於其驗證機制。不同於傳統 GUI 代理僅評估「目標應用狀態」(target app state)，PhoneHarness 採用「追蹤支撐、副作用感知」(trace-backed, side-effect-aware) 的驗證模式，包含：
- **工具呼叫檢查 (tool-call checks)**：驗證是否呼叫了正確的 API。
- **產出物檢查 (artifact checks)**：確認檔案、記錄等可觀察產出。
- **系統設定檢查 (system-setting checks)**：驗證裝置設定變更。
- **訊息傳送檢查 (sent-message checks)**：確認電子郵件、訊息確實送出。
- **安全檢查 (safety checks)**：驗證確認對話 (confirmation) 與無意外資料外洩 (no unintended data egress)。

這種驗證設計將「代理是否宣稱完成任務」與「任務是否真的發生副作用」區分開來，是評估哲學上的重要轉變。

#### 實驗數據解讀

**核心結果**：在標註評估分割上，PhoneHarness 達到 75.0% 的通過率 (pass rate)，較最強的非 PhoneHarness 設定 (non-PhoneHarness settings) 高出 12.9 個百分點 (percentage points)。

此結果的解讀重點：

**一、絕對通過率的意義**

75.0% 的通過率在行動代理領域屬於較高水平，但更重要的是其相對意義。12.9 百分點的差距顯示，混合動作空間的設計帶來了實質性的能力提升，而非僅是基準難度差異造成的假象。這暗示現有 GUI-only 代理在面對需要跨介面協作的任務時，存在結構性的能力瓶頸。

**二、基準構成的影響**

基準包含 mock-app 與 real-app 兩類任務。Mock-app 任務通常較易控制與重現，但 real-app 任務涉及真實應用程式的狀態變化，可能引入環境不穩定性。30 個探索性安全任務的存在表明基準也關注代理的安全性行為，這在現有基準中較為少見。

**三、失敗診斷的價值**

論文強調提供「經驗性與質性評估協議」(empirical and qualitative evaluation protocol) 來診斷失敗來源——模型推理、動作空間路由、GUI 定位 (visual grounding)、工具使用、環境不穩定性或驗證器不匹配 (verifier mismatch)。這種診斷框架比單一通過率指標更具研究價值，因為它揭示了「為什麼」失敗，而非僅「是否」失敗。

**四、需注意的數據限制**

由於僅提供標註評估分割的單一數字，無法判斷：(1) 不同任務類型（mock-app vs. real-app vs. safety）的細粒度表現；(2) 結果的統計顯著性與信賴區間；(3) 不同模型骨幹的表現差異。這些資訊對於完整理解方法效能至關重要。

#### 與現有研究的比較

**一、相關系統定位**

從 Table 1 的能力涵蓋範圍 (capability coverage) 比較可見，PhoneHarness 是唯一同時支援 GUI 控制、裝置 CLI、MCP/主機工具、副作用驗證與安全/追蹤稽核的系統。具體對比：

- **Mobile GUI benchmarks (Zhang et al., 2023; Wang et al., 2024a)**：僅支援 GUI 控制，副作用驗證與安全稽核為部分支援。
- **AndroidWorld / MobileAgentBench (Rawles et al., 2024; Wang et al., 2024b)**：GUI 控制完整，副作用驗證完整，但缺乏 CLI 與 MCP 工具支援。
- **MobileWorld (Kong et al., 2025)**：GUI 控制完整，MCP 工具部分支援，但 CLI 與副作用驗證僅部分支援。
- **MobileClaw**：各項能力均為部分支援。

**二、方法論創新點**

相較於 AndroidWorld 等將手機使用框定為螢幕導航問題的基準，PhoneHarness 的核心創新在於：
1. **動作介面的多元化**：承認真實任務需要 GUI、CLI、工具的協作。
2. **驗證的可觀察性**：從「最終 UI 狀態」轉向「副作用證據」。
3. **安全性的整合考量**：將確認對話與資料外洩檢查納入評估。

**三、相關研究脈絡**

論文將自身定位於三條研究路線的交會：
- **行動 GUI 代理**：承襲 AppAgent、Mobile-Agent-v2 的視覺控制能力，但擴展動作空間。
- **電腦使用與執行型基準**：呼應 OSWorld、WebArena、WorkArena 的執行型獎勵哲學，但聚焦於手機環境。
- **工具使用與 MCP 增強代理**：與 API-Bank、τ-bench 等工具使用基準共享「工具不可或缺」的觀點，但將工具使用置於手機代理框架內。

**四、限制與不足**

1. **任務規模有限**：124 個標註任務相較於 AndroidWorld 等大型基準規模較小，可能限制結論的泛化性。
2. **模型依賴性未明**：未說明評估使用的具體語言模型骨幹，影響結果的可比較性。
3. **環境可重現性**：真實應用程式任務可能因 app 版本更新而失效，這是所有 real-app 基準的共同挑戰。
4. **安全任務的探索性質**：30 個探索性安全任務的設計原則與評分標準需要更詳細的說明。

#### 可重現性評估

從提供的文本內容判斷，PhoneHarness 的可重現性存在以下考量：

**一、潛在的可重現性資產**

- **基準任務定義**：124 個標註任務的規格應可公開，使其他研究者能重現評估。
- **執行框架程式碼**：PhoneHarness 作為執行框架，其程式碼（裝置端代理迴圈、主機端服務、動作路由器）應可開源。
- **驗證器實作**：副作用驗證的具體實作（工具呼叫檢查、產出物檢查等）是重現的關鍵。

**二、可重現性挑戰**

1. **Android 環境配置**：裝置端環境的精確配置（Android 版本、app 版本、權限設定）對結果影響重大，需詳細記錄。
2. **真實應用程式依賴**：real-app 任務依賴特定版本的應用程式，app 更新可能導致基準失效。
3. **模型 API 依賴**：若使用商業語言模型 API，模型版本變更會影響結果。
4. **MCP 工具實作**：主機端工具的具體實作需要公開才能重現。

**三、評估**

基於論文的系統性設計與詳細的驗證模式描述，PhoneHarness 應具備中等以上的可重現性潛力，但需待完整程式碼與基準釋出後才能確切評估。論文中未明確提及開源程式碼、資料集或模型權重的可用性，這是當前描述中的一個重要缺口。

#### 未來研究方向

**一、動作空間的擴展**

1. **多模態動作介面**：整合語音、藍牙、NFC 等手機原生介面，擴展動作空間的覆蓋範圍。
2. **跨裝置協作**：探索手機與其他裝置（手錶、筆電、IoT 裝置）的協作代理框架。
3. **動態動作介面發現**：讓代理能動態發現並整合新的工具，而非僅限於預定義介面。

**二、驗證機制的深化**

1. **因果驗證**：從「副作用發生」深化為「副作用由代理動作引起」的因果歸因。
2. **長期副作用追蹤**：追蹤任務完成後的長期狀態變化，而非僅驗證即時副作用。
3. **對抗性驗證**：設計刻意誘使代理產生錯誤副作用的測試案例。

**三、安全與隱私研究**

1. **細粒度權限模型**：設計更精細的權限授予機制，讓代理僅能存取任務所需的最小權限。
2. **隱私保護評估**：系統性評估代理在處理敏感資料時的隱私保護行為。
3. **確認對話的最佳化**：研究如何設計確認對話以平衡效率與安全性。

**四、基準的擴展與標準化**

1. **任務規模擴展**：將基準擴展至數百甚至數千個任務，提升統計可靠性。
2. **跨平台支援**：將框架擴展至 iOS，實現跨平台的手機代理評估。
3. **動態基準更新**：建立基準的持續更新機制，應對 app 版本變化。
4. **標準化評估協議**：與社區合作建立標準化的評估指標與協議。

**五、模型與代理架構研究**

1. **專用模型訓練**：針對混合動作空間訓練專用的手機代理模型。
2. **推理增強**：研究如何增強代理在動作介面路由上的推理能力。
3. **失敗恢復機制**：設計代理從動作失敗中恢復的機制，提升魯棒性。

**六、應用領域探索**

1. **企業工作流程自動化**：將 PhoneHarness 應用於企業內部的手機工作流程自動化。
2. **無障礙輔助**：探索 PhoneHarness 在輔助技術 (assistive technology) 中的應用。
3. **教育與訓練**：利用 PhoneHarness 進行手機使用技能的訓練與評估。

總結而言，PhoneHarness 的核心貢獻在於重新框定了手機代理研究的問題——從「能否點擊下一個按鈕」轉向「能否在 CLI、GUI 與工具之間路由真實的行動工作流程，並驗證其副作用」。這一架構性轉變為未來研究開啟了豐富的方向，特別是在動作介面設計、副作用驗證、與安全性整合等面向。

## 論文問答

**Q1：PhoneHarness 主要解決了什麼核心問題？**
A：PhoneHarness 針對的是當前手機代理研究過度聚焦於「螢幕導航」而忽略真實行動工作流程的問題。傳統的行動代理基準（如 AndroidWorld、AppAgent、Mobile-Agent-v2 等）將手機使用簡化為「觀察螢幕、輸出點擊或滑動、以目標應用狀態評分」的單一動作介面。然而真實任務（例如「在 App 中找電影、查詢額外發行資訊、彙整結果並寄信」）橫跨 App 導航、外部擷取、文字處理與狀態改變的通訊動作，需要代理能在多種動作介面間靈活切換。PhoneHarness 因此提出一個混合動作空間的執行框架與基準，強調「可驗證執行」而非僅僅視覺 GUI 控制。

**Q2：為什麼現有的行動代理基準不足以評估真實的手機使用任務？**
A：現有基準大多將手機使用視為純粹的 GUI 控制問題，僅支援螢幕動作而缺乏裝置端 CLI 與主機端工具的整合能力。從論文的 Table 1 可知，Mobile GUI benchmarks、AndroidWorld/MobileAgentBench、MobileWorld、MobileClaw 等系統在「裝置 CLI」、「MCP/主機工具」、「副作用驗證」與「安全/追蹤稽核」等欄位上幾乎都是 ❖（部分支援）或 ✗（不支援）。這代表它們無法處理需要跨介面協作的真實工作流程，也難以驗證任務是否真的產生預期的副作用。此外，僅以最終 UI 狀態評分容易讓代理「看起來完成」但實際上未達成使用者意圖。

**Q3：為什麼「可驗證執行」對手機代理的發展至關重要？**
A：隨著語言模型代理從「產生答案」轉向「完成任務」，評估的焦點必須從模型能否描述解法，轉向能否真正關閉「感知–規劃–動作」迴圈並留下可驗證的執行證據。手機是個人化、有狀態且權限豐富的運算環境，許多真實使用者工作流程從手機開始也在手機結束，因此手機代理的可信度高度依賴於副作用能否被客觀檢驗。若缺乏可驗證執行，代理可能產生「看似合理」的最終答案但實際上未完成任務，這對企業部署與使用者信任都會構成嚴重風險。

**Q4：PhoneHarness 的核心架構與代理迴圈是如何設計的？**
A：PhoneHarness 採用裝置端與主機端分離的雙層架構：裝置端在 Android 環境中執行手機代理迴圈，主機端則提供模型路由、GUI 執行與 MCP 風格的工具存取。代理迴圈統一整合三種動作介面——確定性的 CLI 執行、有界的 GUI 委派，以及主機端的結構化工具呼叫——並透過確定性動作路由機制決定每一步該使用哪個介面。這樣的設計讓代理不必把所有任務都強行映射到螢幕點擊，而是能根據任務性質選擇最合適的執行路徑，同時保留可稽核的執行追蹤以供事後檢驗。

**Q5：PhoneHarness Bench 在評估方法上有什麼關鍵創新？**
A：PhoneHarness Bench 的核心創新在於採用「追蹤支撐、副作用感知」的驗證模式，而非僅檢查最終 UI 狀態。具體而言，驗證器涵蓋五大類型：工具呼叫檢查、產物檔案檢查、系統設定檢查、已送出訊息檢查，以及針對確認機制與非預期資料外洩的安全檢查。基準本身由 14 個 mock-app 任務、45 個真實 App 任務、30 個探索性安全任務，以及從 181 個候選池中抽出的 124 個標註評估任務所組成。這樣的設計讓評分能反映代理是否真的完成了工作，而非只是「看起來完成」。

**Q6：PhoneHarness 在動作路由與 GUI 委派的設計上做了哪些關鍵取捨？**
A：PhoneHarness 採用「確定性動作路由」來決定每一步該走 CLI、GUI 還是工具，這避免了代理在多介面間猶豫或產生不一致行為。GUI 委派則被刻意設計為「有界」（bounded），代表 GUI 動作被限制在特定範圍內執行，而非允許代理無限地自由點擊整個螢幕，這降低了誤觸與安全風險。同時，所有動作都會留下可稽核的執行追蹤，使得診斷失敗原因時能區分出是模型推理、動作介面路由、GUI 視覺定位、工具使用、環境不穩定還是驗證器不匹配等不同因素。

**Q7：PhoneHarness Bench 使用了哪些任務集與比較基準？**
A：PhoneHarness Bench 的任務組成涵蓋四個面向：14 個 mock-app 任務用於受控實驗、45 個真實 App 任務反映真實使用情境、30 個探索性安全任務檢驗代理的安全行為，以及從 181 個候選池中精心挑選並標註的 124 個評估分割。比較對象則涵蓋 Table 1 所列的多個代表性系統，包括 Mobile GUI benchmarks、AndroidWorld/MobileAgentBench、MobileWorld 與 MobileClaw 等，從「執行框架端支援」與「基準端評估支援」兩個維度進行能力涵蓋範圍的對比。

**Q8：PhoneHarness 的關鍵實驗結果為何？**
A：在標註評估分割上，PhoneHarness 達到 75.0% 的通過率，比最強的非 PhoneHarness 設定高出 12.9 個百分點。這個差距顯示出混合動作空間與可驗證執行框架相較於純 GUI 控制基準的實質優勢。更重要的是，結果支持了論文的核心論點：可靠的手機自動化取決於動作介面路由與可驗證執行，而非僅僅視覺 GUI 控制能力。

**Q9：PhoneHarness 提供了哪些診斷性分析來理解失敗模式？**
A：論文提供了一套經驗性與質性並重的評估協議，用於診斷失敗究竟來自模型推理、動作介面路由、GUI 視覺定位、工具使用、環境不穩定還是驗證器不匹配。這種多層次的失敗歸因對於基準的持續改進至關重要，因為它能讓研究者知道該從哪個環節著手優化。此外，透過可稽核的執行追蹤，研究者可以重現代理的決策過程並進行細粒度的錯誤分析，這是傳統僅以最終狀態評分的基準所無法提供的洞見。

**Q10：PhoneHarness 適用於哪些實際的手機自動化場景？**
A：PhoneHarness 特別適合需要跨 App、跨系統協作的複雜行動工作流程，例如「在電商 App 找商品、查外部評論、彙整後寄 email 給同事」這類任務。它也能應用於需要裝置端 CLI 操作（如透過 adb 設定系統參數）與主機端工具（如 MCP 工具）共同完成的企業內部流程。此外，對於涉及敏感操作（如發送訊息、修改設定）的場景，PhoneHarness 的安全檢查機制能確保代理在執行前取得確認並避免非預期的資料外洩。

**Q11：PhoneHarness 在產品化部署上有哪些重要的設計考量？**
A：在產品化層面，PhoneHarness 的「有界 GUI 委派」與「確定性動作路由」是關鍵的安全設計，能避免代理在真實使用者裝置上產生不可預測的行為。可稽核的執行追蹤則提供了企業所需的合規與除錯能力，讓部署方能完整檢視代理的每一步動作。此外，副作用驗證機制（如「已寄出郵件檢查」、「系統設定檢查」）確保代理真的完成了使用者委託的工作，而非只是回報一個看似合理的結果，這對建立使用者信任至關重要。

**Q12：PhoneHarness 對整個手機代理與工具使用研究領域有何影響？**
A：PhoneHarness 將手機代理研究從「純 GUI 控制」推向「混合動作空間」的典範轉移，鼓勵未來基準設計者考慮 CLI、GUI 與工具的整合。它也呼應了 OSWorld、WebArena、WorkArena 等桌面/網頁代理研究中「以執行證據評分」的哲學，並將其落實到手機這個獨特的執行環境中。透過強調副作用驗證與安全稽核，PhoneHarness 為整個領域樹立了更嚴謹的評估標準，推動研究者不再滿足於「模型能否點擊下一個按鈕」，而是追問「代理能否可靠且安全地完成真實工作流程」。

**Q13：PhoneHarness 與 PhoneHarness Bench 存在哪些已承認的限制？**
A：從基準規模來看，PhoneHarness Bench 目前僅有 124 個標註評估任務（從 181 個候選池中篩選），相較於一些大型基準（如 Android in the Wild）規模仍有限，這可能影響結果的統計穩定性與泛化性。此外，雖然 PhoneHarness 強調跨介面整合，但其在不同 Android 版本、裝置型號與 App 版本間的相容性仍是未知數。最後，mock-app 任務雖然提供受控環境，但與真實 App 任務之間仍存在生態落差，這限制了基準對生產環境的完全代表性。

**Q14：PhoneHarness 在實驗中觀察到哪些典型的失敗案例？**
A：雖然具體失敗案例未在提供的文本中詳列，但根據論文的診斷框架，失敗可歸因於六大類：模型推理錯誤、動作介面路由決策失當、GUI 視覺定位失敗、工具呼叫錯誤、環境不穩定（如 App 狀態異常）以及驗證器與實際任務意圖的不匹配。這種多層次的失敗歸因顯示，即使在 75.0% 通過率的表現下，仍有相當比例的任務因為非模型本身的原因而失敗，凸顯了建構穩健執行環境的難度。

**Q15：PhoneHarness 未來可以朝哪些方向發展？**
A：未來發展方向可能包括：擴大基準規模並增加任務多樣性，以提升統計穩定性與領域覆蓋；強化跨裝置、跨 Android 版本的相容性測試，使基準更貼近真實部署環境；深化安全稽核機制，特別是在涉及個資與金融操作的任務上；以及探索與更多主機端工具（如雲端服務 API）的整合，進一步擴展代理的能力邊界。此外，將 PhoneHarness 的「可驗證執行」哲學推廣到其他行動平台（如 iOS）或新興裝置形態（如穿戴式裝置、汽車資訊娛樂系統）也是值得探索的方向。

## 實務應用指南

### 適用場景

1. **跨 App 資訊彙整與外發工作流程**：例如「在串流平台找到某部電影、查詢外部資料源補充上映資訊、彙整摘要後寄送電子郵件」。此類任務需要 App GUI 導航、外部擷取、文字處理與狀態改變的通訊動作，正是 PhoneHarness 設計的核心場景。

2. **企業內部行動辦公自動化**：例如「從行事曆讀取今日會議、查詢 CRM 系統中對應客戶資料、將彙整結果寫入記事本並設定提醒」。這類任務涉及多個 App 狀態、需要可驗證的副作用（行事曆事件、記事檔案、系統設定），適合用 PhoneHarness 的 trace-backed 驗證機制。

3. **裝置設定與權限管理自動化**：例如「關閉特定 App 的定位權限、調整通知設定、清理快取並產生設定變更報告」。PhoneHarness 的 device-side CLI 與 system-setting 檢查可直接驗證設定是否真的被改動。

4. **行動 App 測試與迴歸驗證**：QA 團隊可利用 PhoneHarness 對 Android App 進行混合動作的端到端測試，CLI 用於環境準備、GUI 用於互動驗證、host-side tools 用於測試資料注入與結果擷取。

5. **個資保護與資料外洩稽核**：透過 PhoneHarness 的 safety / trace audit 機制，檢查代理是否在未經確認的情況下執行資料外傳動作（例如未授權的電子郵件發送、檔案上傳），適用於金融、醫療等高敏感產業的內部代理部署。

### 實作前置條件

**資料準備**
- 一組 Android 裝置或模擬器（建議使用實體裝置以反映真實 side effect），需可被 ADB 控制。
- 任務定義資料集：包含任務描述、預期副作用、可驗證的 ground truth（系統設定值、寄出的信件內容、產生的檔案、行事曆事件等）。PhoneHarness Bench 採用 14 個 mock-app、45 個 real-app、30 個 exploratory safety task 與 181 個候選任務池，可作為起點。
- App 與系統狀態的 baseline snapshot 機制，以便任務結束後可重置並驗證變更。

**運算資源**
- 一台主機端伺服器執行 host-side 服務（模型路由、GUI 執行、MCP-style tool 服務）。GPU 需求取決於所選語言模型；若是呼叫雲端 LLM API，則主機端只需輕量推理協調。
- Android 裝置需保持穩定連線（ADB over USB 或 Wi-Fi），建議每台裝置獨立執行一個 agent loop 以避免狀態污染。

**技能前提**
- 熟悉 Android Debug Bridge（ADB）、shell 指令與裝置權限模型。
- 具備 LLM agent 開發經驗（prompt engineering、tool calling、function schema 設計）。
- 了解 MCP（Model Context Protocol）或類似 tool-use 框架的運作方式。
- 具備測試自動化與 CI/CD 經驗，以整合驗證流程。

### 實作步驟建議

1. **釐清任務邊界與副作用定義**：從一個具體工作流程出發（例如「查電影並寄信」），列出所有可能的動作介面（GUI、CLI、host-side tool）以及每個動作完成後應留下的可驗證證據（寄出的信件、修改的設定、產生的檔案）。這對應論文中「trace-backed, side-effect-aware verification」的設計原則。

2. **建置 device-side agent loop**：在 Android 裝置上部署一個 agent 迴圈，能夠接收模型決策、執行 CLI 指令、委派 GUI 動作、呼叫 host-side tool，並回報執行結果與狀態變化。論文中強調此迴圈需具備 deterministic action routing 與 bounded GUI delegation。

3. **設計 host-side 服務層**：在主機端實作模型路由（決定何時呼叫哪個模型）、GUI 執行代理（將高層 GUI 決策轉為 tap/swipe/type）、以及 MCP-style tool server（提供外部擷取、檔案處理、訊息發送等結構化工具）。

4. **定義動作介面與路由規則**：為每個動作類型（CLI、GUI、tool）設計明確的 schema 與觸發條件。CLI 用於確定性高、可腳本化的操作；GUI 用於需要視覺定位的 App 互動；tool 用於跨 App 或外部資源存取。論文的 Table 1 顯示 PhoneHarness 同時支援三種介面，這是其相較於 AndroidWorld、MobileWorld 等系統的關鍵差異。

5. **實作驗證器（verifier）**：針對每類副作用設計對應檢查：tool-call 檢查（確認特定 API 被呼叫）、artifact 檢查（確認檔案或信件存在且內容正確）、system-setting 檢查（讀取裝置設定值）、sent-message 檢查（驗證訊息已送達）、safety 檢查（確認未發生未授權的資料外傳）。

6. **建立任務集與標註評估分割**：從候選任務池中挑選具代表性的子集進行人工標註，標註內容包含預期動作路徑、副作用證據、安全邊界。PhoneHarness Bench 的 124-task annotated split 是此步驟的具體實例。

7. **執行基準實驗並診斷失敗模式**：依論文的評估協議區分失敗來源——模型推理、動作介面路由、GUI grounding、tool 使用、環境不穩定、verifier mismatch——並針對各類失敗進行改善。論文中 75.0% 通過率與 12.9 百分點的領先幅度可作為初步目標基準。

8. **整合到產品流程**：將 PhoneHarness 包裝為可重複執行的服務，串接企業內部的任務排程、權限管理與稽核日誌系統。

### 潛在風險與注意事項

- **環境不穩定導致誤判**：Android 裝置的 App 狀態、網路連線、權限提示可能隨版本更新而改變，使 verifier 失效。緩解方式：建立裝置狀態快照與重置機制，並在 CI 中定期回歸測試 verifier 本身。

- **GUI grounding 失敗的連鎖效應**：當視覺定位錯誤時，後續所有 GUI 動作都會偏離預期路徑。緩解方式：採用 bounded GUI delegation，將 GUI 動作限制在明確範圍內，並在每步驟後以 CLI 或 tool 驗證狀態。

- **未授權的資料外傳**：代理可能誤觸發寄信、上傳、分享等狀態改變動作。緩解方式：對所有 state-changing communication action 加上 confirmation 機制，並在 safety check 中明確比對「預期副作用 vs. 實際副作用」。

- **Verifier 與實際行為的脫節**：檢查項目設計不夠嚴謹時，可能出現「通過驗證但任務未真正完成」的情況。緩解方式：採用多層驗證（tool call + artifact + system state），並定期以人工抽查驗證結果。

- **裝置權限與隱私合規**：host-side tool 可能存取敏感資料，需符合企業資安政策。緩解方式：在 tool schema 中明確標示資料存取範圍，並透過 trace audit 記錄所有資料流向。

- **模型路由成本**：若同時使用多個模型（規劃、決策、反思），整體推理成本可能快速攀升。緩解方式：根據任務難度分層路由，簡單動作使用輕量模型，僅在關鍵決策點使用大型模型。

### 與其他技術的整合建議

- **與 AndroidWorld / MobileAgentBench 整合**：可將既有 GUI 任務導入 PhoneHarness 作為 GUI delegation 子任務，保留原有 reward 機制，同時新增 CLI 與 tool 動作的驗證層。

- **與 MCP 工具生態系整合**：PhoneHarness 的 host-side tool 層採用 MCP-style 設計，可直接複用既有 MCP server（例如檔案管理、API 呼叫、資料庫查詢），降低重複開發成本。

- **與 OSWorld / TheAgentCompany 等桌面代理整合**：將桌面代理作為 PhoneHarness 的 host-side tool 之一，用於處理需要在桌面環境完成的子任務（例如長文件編輯、複雜試算表操作），形成「手機 + 桌面」的混合工作流程。

- **與企業 SSO 與權限管理整合**：透過 OAuth / SAML 將 PhoneHarness 的 tool 呼叫綁定至企業身分驗證，確保所有狀態改變動作可追溯到具體使用者。

- **與 Observability 平台整合**：將 auditable execution trace 匯入 ELK、Grafana 或類似監控平台，建立儀表板追蹤 pass rate、失敗模式分布、安全事件告警。

- **與 CI/CD 整合**：將 PhoneHarness Bench 的任務集納入迴歸測試流程，每次 App 或模型更新後自動執行評估，及早發現 grounding 或 routing 退化。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題陳述，理解為何「手機代理不應只是 GUI 控制器」，再跳到 Table 1 觀察 PhoneHarness 與其他系統在能力涵蓋範圍上的差異。接著閱讀術語表（glossary）熟悉 GUI、CLI、MCP、side effect 等核心概念，最後回到摘要確認整體論點。避免一開始就深入技術細節。

**給 AI 工程師**：重點閱讀第 1 節的設計動機與第 2 節的相關工作比較，理解 PhoneHarness 在 agent stack 中的定位。接著關注「trace-backed, side-effect-aware verification patterns」與「action-surface routing」的實作意涵，並參考 75.0% pass rate 與 12.9 百分點領先幅度的實驗數據，評估導入成本與效益。可直接將 PhoneHarness 的動作介面設計套用到現有手機代理專案。

**給研究者**：第 2 節提供了完整的相關工作分類（mobile GUI agents、computer-use benchmarks、tool-use benchmarks、agent safety），是建立研究定位的絕佳起點。建議進一步追蹤論文中引用之 Xie et al. (2024)、Rawles et al. (2024)、Kong et al. (2025) 等文獻，並思考「mixed-action evaluation」與「side-effect verification」如何延伸至其他代理場景（機器人、IoT、嵌入式系統）。Table 1 的能力矩陣也是值得延伸比較的分析框架。

**給產品經理**：聚焦於摘要與第 1 節的應用場景描述，理解 PhoneHarness 解決的具體痛點（跨 App 工作流程、可驗證副作用、安全稽核）。75.0% 通過率代表技術已接近可用水準，但仍需注意「環境不穩定」、「未授權資料外傳」、「verifier 脫節」等產品化風險。建議將 PhoneHarness 定位為「企業內部行動辦公自動化的執行框架」，而非消費端產品，並優先在高敏感、高重複性的內部流程中試點。
