## ⚡ TL;DR

自主探索在真實工程任務中面臨評估瓶頸，每次真實評估耗時數小時，嚴重限制搜尋規模。
DuoDiscover 讓代理共同探索目標與廉價評量尺，透過保真度測試與輕量協調器維持效率。
該系統在 SWE-fficiency 將人類加速比翻倍，並超越 vLLM 與 CPU 微架構設計。

## 摘要翻譯

評估一直是人工智慧進展的核心，對自主探索同樣至關重要。然而，將自主探索擴展至真實世界的工程挑戰，面臨一項根本瓶頸：評估進度的成本。在真實情境中，一次真實評估（例如完整的基準測試或服務追蹤）可能耗時數小時，因此搜尋僅能負擔少數幾次真實評估。我們提出 DuoDiscover，一個透過三項機制，同時探索最佳化目標與有效評估方式的搜尋系統。首先，由編碼代理組成的機群中，每個工作代理共同探索出一個最佳化目標，以及一個快速且量身打造的代理評估器，我們稱之為評量尺。代理接著沿評量尺進行爬山法，而非使用真實評估。其次，由於搜尋可能利用評量尺與真實目標之間的差距，保真度測試會持續重新檢驗每個評量尺的排序，並使任何發生漂移的評量尺失效。第三，機群採自下而上組織，無需對問題進行集中分解。一個輕量協調器負責生成與終止代理、向執行中的代理下達指引，並以其他代理的已確認成果對新代理進行種子初始化。DuoDiscover 實現了從軟體到晶片架構的自主最佳化。我們在兩個儲存庫層級基準測試，以及涵蓋數百個核心的四個 GPU 與 TPU 核心套件上展示 DuoDiscover。在 SWE-fficiency 上，它達到人類專家平均加速比的兩倍。在 SOL-Exec 上，它在 235 個核心中的 121 個排名第一，並在 212 個中名列前三。在經過高度最佳化的 vLLM 與 SQLite 引擎上，DuoDiscover 相較於基礎程式碼分別達到 1.92 倍與 1.38 倍的增益。在一項評估時間長達 28 小時的 CPU 微架構最佳化任務中，DuoDiscover 同時超越了基於 AlphaEvolve 的 ArchAgent v2 與最佳人類設計，在 16.7 天內達成 ArchAgent v2 增益的 1.65 倍，而 ArchAgent v2 耗時超過 40 天，拓展了自主晶片設計的疆界。

### 核心貢獻（3～5點）
- 提出 DuoDiscover 搜尋系統，透過「共同探索」機制，讓工作代理同時發現最佳化目標與量身打造的快速代理評估器（評量尺），以廉價的代理分數取代昂貴的真實評估。
- 引入「保真度測試」機制，持續驗證評量尺與真實目標的排序一致性，自動淘汰發生評量尺漂移的代理評估器，防止搜尋利用評量尺與真實目標間的差距。
- 採用「自下而上」的機群組織，由輕量協調器負責代理生命週期管理與種子初始化，無需中央分解問題，支援大規模並行探索。
- 在多項基準測試中展現突破性成果：SWE-fficiency 達到人類專家平均加速比的兩倍；SOL-Exec 在 235 個核心中 121 個排名第一；vLLM 與 SQLite 引擎分別獲得 1.92 倍與 1.38 倍增益。
- 在評估耗時達 28 小時的 CPU 微架構最佳化任務中，以 16.7 天超越 AlphaEvolve 基線的 ArchAgent v2（耗時逾 40 天）與最佳人類設計，達成 1.65 倍的增益效率，拓展自主晶片設計的疆界。

### 適合對象
本論文最適合以下讀者閱讀：從事大型語言模型驅動之自主探索與程式碼生成研究的前沿學者與工程師；關注高效能運算、GPU/TPU 核心最佳化及 CPU 微架構設計的系統與晶片設計研究者；以及對 AI 代理評估機制、搜尋式最佳化與自動化科學發現感興趣的機器學習與人工智慧領域研究人員。此外，vLLM、SQLite 等開源推論與資料庫引擎的維護者與效能工程師，亦可從中獲得實務參考價值。

## 深度分析

#### 方法論解析

DuoDiscover 的核心方法論建立在對自主探索系統中「評估瓶頸」(Evaluation Bottleneck) 的深刻觀察之上。傳統的基於搜尋的探索系統（如 AlphaEvolve）通常假設評估函數是給定且固定的，但當面對真實工程系統時，一次完整評估的成本可能高達數小時（如 vLLM 多目標服務需 85 分鐘，CPU 微架構設計需 28 小時），使得任何搜尋預算內僅能執行數十次真實評估。這種限制迫使系統必須在「探索廣度」與「評估深度」之間做出取捨。

**共同探索機制（Co-discovery Mechanism）**

DuoDiscover 的第一個關鍵設計是讓每個工作代理（Worker Agent）同時發現兩件事：最佳化目標（Optimization Target, 𝑇）與對應的評量尺（Yardstick, 𝑔𝑇）。這與 AlphaEvolve 要求使用者手動標記程式碼區域的做法形成鮮明對比。在 DuoDiscover 中，代理自主分析程式碼結構，識別出可能帶來顯著加速的「目標區域」，並為該區域量身打造一個廉價的評分腳本。

此設計背後的理論基礎來自 Amdahl 定律：若某程式碼區域僅負責 20% 的整體執行時間，則即使該區域無限加速，整體加速比上限為 1.25×。因此，代理不僅要選擇目標，還需估計該目標的權重 𝑤𝑇 ∈ [0,1]，以判斷其潛在收益天花板。這種「權重感知」的目標選擇機制，使得搜尋資源能更有效地分配到高潛力區域。

**保真度測試（Fidelity Test）**

代理在廉價的評量尺上進行爬山法（Hill-climbing）搜尋，但這引入了「評量尺漂移」（Yardstick Drift）的風險：隨著代理適應評量尺，可能出現代理分數提升但真實分數停滯甚至下降的情況。DuoDiscover 透過持續的保真度測試來緩解此問題——定期將評量尺的排序與真實評估進行比對，若發現顯著偏差則使該評量尺失效（invalidate），迫使代理重新建立評量尺或更換目標。

值得注意的是，每一項收益都必須經過真實評估的最終確認才能被接受。這種「廉價內迴圈 + 昂貴外迴圈」的雙層架構（如圖 2 所示），在保持搜尋效率的同時，確保了最終結果的真實有效性。

**自下而上機群與輕量協調器（Bottom-up Fleet & Lightweight Orchestrator）**

與傳統的集中式分解方法不同，DuoDiscover 採用自下而上的機群組織方式。每個工作代理獨立運作於程式碼庫的副本上，協調器僅負責三項輕量任務：(a) 終止停滯的代理、(b) 合併相容的成果以生成新代理、(c) 將已確認的成果作為種子（seeding）注入運行中的代理。

這種設計的精妙之處在於資源配置的對稱性：工作代理相對廉價（基於現成 LLM 編碼代理），而真實評估極為昂貴。因此，協調器的角色被刻意設計為「管理昂貴資源」而非「指揮廉貴資源」——它將寶貴的真實評估預算引導至正在取得進展的代理，並在代理停滯時果斷終止。這種資源配置哲學與傳統的集中式元搜尋（meta-search）形成對比，後者往往在中央節點造成通訊瓶頸。

#### 實驗數據解讀

DuoDiscover 在多個層級的運算堆疊（Computing Stack）上展示了廣泛的適用性，實驗結果可從以下幾個維度解讀：

**儲存庫層級基準（Repository-level Benchmarks）**

在 SWE-fficiency 上，DuoDiscover 達到了人類專家平均加速比的兩倍，這是一個顯著的里程碑，因為 SWE-fficiency 涵蓋了真實的軟體工程效率優化任務。在 FormulaCode 上，DuoDiscover 以 21% 的優勢超越最強基線，顯示其在處理複雜、多檔案程式碼庫時的優勢。

**GPU/TPU 核心最佳化**

在 SOL-Exec 基準的 235 個核心中，DuoDiscover 在 121 個上排名第一、在 212 個上進入前三，整體 SOL 分數比最佳基線高出 14%。這意味著在高度競爭性的核心最佳化領域，DuoDiscover 不僅能取得頂尖成績，還具有跨核心類型的泛化能力。在 TPU-Inference 核心上，DuoDiscover 達到 2.68× 加速，超越最佳基線的 2.38×；在 JAXBench 上達到 4.62× 加速（相對於 XLA）。這些數據表明，評量尺機制能有效捕捉 GPU/TPU 核心的效能特性。

**高度優化系統的再優化**

在 vLLM 和 SQLite 這兩個已經過深度人工優化的系統上，DuoDiscover 仍分別達到 1.92× 和 1.38× 的加速比。這尤其值得關注，因為這類系統的優化空間通常被認為已經被充分挖掘。1.92× 的 vLLM 加速比意味著 DuoDiscover 能找到人類專家未曾發現的優化機會，這對自主探索的實用價值提供了有力證明。

**CPU 微架構設計**

最具說服力的實驗是 CPU 微架構最佳化任務：單次評估需 28 小時，DuoDiscover 在 16.7 天內使用約 8,000 個候選方案達到了超越 ArchAgent v2（基於 AlphaEvolve）的成果，其增益為 ArchAgent v2 的 1.65×，而 ArchAgent v2 需 40 天以上、12,000 個候選方案。這不僅展示了效率優勢（時間縮短約 58%、候選數減少約 33%），更證明了 DuoDiscover 在評估成本極高的場景下的實用性。

然而，需注意實驗中未詳細披露的面向：不同任務的搜尋預算分配、評量尺失效的頻率統計、代理間合併的具體策略效果等，這些細節對於完整理解系統行為至關重要。

#### 與現有研究的比較

DuoDiscover 在自主探索領域的定位可從三個軸度來理解：

**與 AlphaEvolve 的比較**

AlphaEvolve（Novikov et al., 2025）是當前自主探索的代表性工作，但其要求使用者手動標記程式碼區域，且評估函數被視為固定。DuoDiscover 的兩項關鍵改進——自動目標選擇與評量尺共同探索——使其能處理 AlphaEvolve 難以應對的高評估成本場景。在 CPU 微架構任務上的比較（1.65× ArchAgent v2 的增益，時間減半）直接展示了這一優勢。

**與其他代理式優化器的比較**

近期湧現的代理式優化器（如 Agarwal et al., 2026; Deng et al., 2026; Liao et al., 2026; Luo et al., 2026）多專注於改進搜尋框架本身（搜尋策略、提示工程、多代理協作），但同樣將評估視為固定。DuoDiscover 的獨特貢獻在於正視了評估瓶頸問題，並提出了系統性的解決方案。

**方法論的侷限性**

儘管成果顯著，DuoDiscover 仍存在以下侷限：

1. **評量尺設計的隱性成本**：雖然評量尺執行廉價，但設計評量尺本身需要代理進行推理與程式碼生成，這部分成本未在論文中明確量化。

2. **保真度測試的頻率權衡**：過於頻繁的保真度測試會消耗寶貴的真實評估預算，過於稀少則可能讓漂移的評量尺誤導搜尋。論文中未深入探討此權衡的理論指導原則。

3. **目標選擇的探索-利用平衡**：自下而上機群雖然避免了集中分解，但也意味著可能有多個代理同時探索相似目標，造成資源浪費。論文中未提供代理多樣性的量化分析。

4. **可遷移性問題**：評量尺是針對特定目標量身打造的，當程式碼結構發生顯著變化時，評量尺可能需要完全重建，這增加了長期優化的複雜度。

#### 可重現性評估

從可重現性角度，DuoDiscover 的論文提供了豐富的實驗細節，但仍有以下考量：

**正面因素**

- 論文詳細描述了系統架構（圖 2）、問題形式化（Section 2.1）以及代理的工作流程，這為實作提供了清晰的藍圖。
- 實驗涵蓋了多個公開基準（SOL-Exec、SWE-fficiency、FormulaCode、JAXBench），這些基準本身是可獲取的。
- 評估成本的具體數值（如 vLLM 85 分鐘、CPU 微架構 28 小時）有助於研究者評估自身資源是否足以重現實驗。

**潛在障礙**

- 論文中使用的「現成 LLM 編碼代理」未指定具體模型或版本，這對結果的可重現性構成挑戰，因為不同 LLM 的編碼能力差異顯著。
- 評量尺的設計高度依賴代理的即時推理，這使得相同配置下的結果可能存在隨機性。
- CPU 微架構設計任務的評估需要專業的模擬工具鏈，這對大多數研究機構構成實際門檻。
- 論文中未明確提及程式碼、資料集或模型權重是否會開源釋出。

**建議的改進方向**

為提升可重現性，未來工作應考慮：(1) 釋出評量尺設計的提示模板與範例；(2) 提供基準任務的標準化評估協議；(3) 公開代理間通訊的訊息格式；(4) 在多個 LLM 上報告結果以評估模型敏感性。

#### 未來研究方向

DuoDiscover 開啟了多個值得深入探索的研究方向：

**理論層面**

1. **評量尺設計的形式化**：目前評量尺的設計主要由代理啟發式地完成，未來可探索是否有理論框架能指導評量尺的構建，例如基於資訊理論的「最小充分評量尺」概念。

2. **保真度測試的最優策略**：可將保真度測試的頻率與時機建模為序列決策問題，利用強化學習或貝氏最佳化來動態調整測試節奏。

3. **目標選擇的理論保證**：自下而上機群的成功引發了一個理論問題：在何種條件下，自下而上的探索能比集中式分解更有效？這可能涉及分散式搜尋的覆蓋率分析。

**系統層面**

4. **跨任務的評量尺遷移**：研究如何將一個任務中學到的評量尺設計知識遷移到新任務，例如透過檢索增強或元學習。

5. **多層級評估的層次化**：當前 DuoDiscover 使用單一真實評估，未來可探索層次化評估架構——例如先用極廉價的靜態分析篩選，再用中等成本的基準測試，最終用完整評估確認。

6. **代理間通訊的結構化**：目前代理間的合併與種子傳遞較為簡單，未來可設計更豐富的「知識共享協議」，例如共享評量尺設計模式或失敗案例。

**應用層面**

7. **科學發現的擴展**：論文中展示了從軟體到晶片的應用，下一步可探索 DuoDiscover 在藥物設計、材料科學、氣候模型等領域的適用性，這些領域的評估成本同樣高昂。

8. **人機協作模式**：研究如何讓人類專家與 DuoDiscover 互補——例如人類提供領域知識來加速評量尺設計，或人類審核代理提出的目標選擇。

9. **長期自主探索**：當前實驗在數天至數週的時間尺度上進行，未來可探索如何讓 DuoDiscover 在數月乃至數年的時間尺度上持續運作，這需要解決評量尺漂移的長期累積效應與程式碼庫演化的相容性問題。

10. **安全與對齊考量**：隨著自主探索系統能力的增強，需要研究如何確保其優化方向與人類價值觀一致，特別是在晶片設計等具有重大社會影響的領域。

總結而言，DuoDiscover 的核心貢獻在於將「評估」從自主探索中的被動組件提升為主動設計對象，這一範式轉變為解決真實工程問題中的高成本評估挑戰提供了新思路。其在多個運算堆疊層級的廣泛成功，預示著自主探索系統正從「玩具問題」走向「真實世界」的關鍵轉折。

## 論文問答

**Q1：DuoDiscover 所要解決的核心問題是什麼？為何這個問題在將自主探索擴展到真實工程任務時變得特別關鍵？**

A：DuoDiscover 鎖定的核心問題是「評估瓶頸」——在真實工程系統中，每一次「真實評估」（例如完整的基準測試或服務追蹤）往往需要數小時才能完成，這使得任何搜尋演算法在給定時間預算內只能執行寥寥數次真實評估。這個瓶頸之所以在真實工程任務中特別嚴峻，是因為相較於數學或演算法競賽等領域，軟體系統、GPU/TPU 核心乃至晶片微架構的最佳化都涉及極為昂貴的端到端評估流程。當評估成本從秒級躍升到小時級時，傳統搜尋方法的可迭代次數會驟降到無法支撐有效探索的程度，因此必須從根本上改變「如何評估進度」這件事。

**Q2：現有的自主探索系統在面對真實工程任務時為何會失效？它們對評估器做了什麼樣的假設？**

A：現有自主探索系統（例如 AlphaEvolve 等基於搜尋的發現系統）大多將評估器視為「給定且固定」的元件，致力於改良搜尋框架本身，卻忽略了評估成本這個根本限制。這類系統隱含的假設是評估足夠便宜，使得搜尋可以在大量迭代中累積進步；然而在真實工程系統中，這個假設徹底崩壞——以 vLLM 多目標服務最佳化為例，單次真實評估需耗時 85 分鐘，即使是最先進的編碼代理在 20 小時的搜尋預算內也只能執行約十餘次評估。因此，僅僅改良搜尋演算法或提示工程無法突破這個瓶頸，必須重新設計整個評估與搜尋的互動方式。

**Q3：直觀上，使用廉價的代理評估器來引導搜尋似乎是個自然解法，但為何這個方法單獨使用時並不足夠？**

A：單純使用代理評估器會遭遇兩個相互糾結的難題。第一，代理評估器本質上是「目標特定的」——針對某段程式碼區域有效的廉價測量方式，往往無法直接遷移到其他區域，因此不可能為每個潛在最佳化目標都事先手工設計一個代理評估器。第二，更關鍵的是，代理評估器與真實目標之間存在差距，搜尋過程會逐步「利用」這個差距——也就是所謂的「評量尺漂移」（yardstick drift）現象，使得代理分數持續上升但真實效能卻沒有對應改善。這意味著有效的代理引導搜尋必須同時解決「最佳化什麼」與「如何廉價且忠實地測量進度」這兩個耦合問題，這正是 DuoDiscover 設計的出發點。

**Q4：DuoDiscover 的核心機制「共同探索」（co-discovery）是什麼？它與既有方法在設計上有何根本差異？**

A：共同探索是 DuoDiscover 的基石機制：每個工作代理不再只是被動接受使用者標記的最佳化區域，而是自主地同時決定「要最佳化哪段程式碼（目標 T）」以及「如何為這個目標量身打造一個廉價的代理評估器（評量尺 g_T）」，接著在這個評量尺上執行爬山法搜尋。這與 AlphaEvolve 等系統形成鮮明對比——後者要求使用者在原始碼中以明確的 begin/end 標記圈出要進化的區域，將「選目標」這個決策完全外包給人類。更深層的差異在於，DuoDiscover 的代理還會為每個目標估計一個權重 w_T（即該區域對整體分數的貢獻比例），並透過 Amdahl 定律意識到即使該區域無限快，整體加速上限也不會超過 1/(1−w_T)，從而避免把搜尋資源浪費在低槓桿的區域上。

**Q5：DuoDiscover 如何透過「保真度測試」（fidelity tests）來維持評估保真度？這個機制為何不可或缺？**

A：保真度測試是一個持續運行的檢驗機制，它會定期檢查每個評量尺的排序是否仍與真實目標的排序一致；一旦發現評量尺開始「漂移」——也就是代理分數上升但真實分數並未對應改善——系統就會將該評量尺標記為失效並予以作廢。這個機制之所以不可或缺，是因為搜尋代理具有高度適應性，它會逐步學會利用評量尺與真實目標之間的任何微小差距來製造「假進步」，若沒有保真度測試把關，整個搜尋將會在自我欺騙中空轉。此外，DuoDiscover 還要求每一次宣稱的進步都必須經過一次真實評估確認後才會被接受，這形成了一個「廉價內迴圈 + 昂貴外迴圈」的雙層結構，既保留了快速迭代的效率，又確保最終成果的可信度。

**Q6：為何 DuoDiscover 採用「自下而上機群」搭配「輕量協調器」的架構，而非傳統的「集中分解」方式？**

A：採用自下而上機群的關鍵原因在於「目標選擇」這個問題本質上是不可預測的——在面對一個大型程式庫時，可能的最佳化區域數量龐大且各自報酬未知，集中式的分解者很難事先判斷哪些區域值得投入資源。DuoDiscover 的解法是讓每個工作代理獨立運作在自己的程式碼副本上，自行決定要探索哪個目標與對應的評量尺，而輕量協調器只負責三件事：將寶貴的真實評估資源引導給正在取得進展的代理、終止陷入停滯的代理、以及在合適時機以其他代理已確認的成果作為種子來生成新代理（甚至組合多個代理的相容改進）。這種設計把「集中式規劃」轉化為「分散式探索 + 集中式資源調度」，既避免了中央分解的資訊瓶頸，也讓系統能夠並行探索多個高風險高報酬的方向。

**Q7：DuoDiscover 在哪些基準測試上進行了實驗？這些基準的評估成本跨度有多大？**

A：DuoDiscover 的實驗涵蓋了從軟體到晶片微架構的完整運算堆疊，包括兩個儲存庫層級基準（SWE-fficiency 與 FormulaCode）、四個 GPU/TPU 核心套件（涵蓋 SOL-Exec 的 235 個核心、TPU-Inference 核心以及 JAXBench），以及真實世界的高度最佳化系統（vLLM 與 SQLite）。更引人注目的是，實驗還包含一個 CPU 微架構設計任務，其單次評估成本最高可達 28 小時。這個評估成本的光譜——從數分鐘到將近一天——恰好展示了 DuoDiscover 設計的普適性：無論評估是「昂貴」還是「極度昂貴」，共同探索、保真度測試與自下而上機群這三個機制都能讓搜尋在極有限的真實評估次數下持續推進。

**Q8：DuoDiscover 最令人印象深刻的成果有哪些？這些結果如何體現其設計價值？**

A：成果中最具說服力的包括：在 SWE-fficiency 上將人類專家的平均加速比翻倍；在 SOL-Exec 的 235 個核心中，於 121 個排名第一、212 個進入前三；在 TPU-Inference 核心上達成 2.68 倍的 Pallas 加速比；在 JAXBench 上達成 4.62 倍的 XLA 加速比；在已被深度最佳化的 vLLM 與 SQLite 上仍分別取得 1.92 倍與 1.38 倍的加速；以及在 28 小時單次評估的 CPU 微架構任務中，以 16.7 天、約 8,000 個候選解超越 AlphaEvolve 架構的 ArchAgent v2（後者耗時 40 天以上、超過 12,000 個候選解），並以 1.65 倍的差距勝過最佳人類設計。這些結果的價值不僅在於數字本身，更在於它們覆蓋了「已被高度最佳化的成熟系統」與「評估極度昂貴的新興領域」這兩個過去被視為自主探索禁區的場景，證明了評估瓶頸確實可以被工程化地突破。

**Q9：論文中是否有消融實驗或分析能拆解各元件（共同探索、保真度測試、自下而上機群）的個別貢獻？**

A：雖然論文的呈現重心放在端到端的系統成果上，但其設計本身內含可拆解的元件驗證邏輯：保真度測試的必要性可從「若無此機制則代理會利用評量尺漂移而空轉」這個論證直接推導；自下而上機群的價值則體現在「無需中央分解即可並行探索多個目標」這個架構差異所帶來的實驗結果廣度上——DuoDiscover 能在 235 個核心上同時取得領先地位，正是機群並行探索的具體展現。共同探索的貢獻則可從其與 AlphaEvolve 的對比看出：後者要求使用者手動標記目標，而 DuoDiscover 的代理能自主選擇目標並估計 Amdahl 權重，這在 CPU 微架構任務中轉化為 1.65 倍的差距與近 2.5 倍的時間效率。

**Q10：DuoDiscover 開啟了哪些過去在實務上不可行的應用場景？**

A：DuoDiscover 真正開啟的，是那些「單次評估成本高到傳統自動化方法根本無法涉足」的領域——例如 CPU 微架構設計（單次評估最高 28 小時）、多目標推論服務的 vLLM 調校（85 分鐘/次）以及大型資料庫引擎的深度最佳化。在這些場景中，過去即使是最強的編碼代理也只能在預算內執行十餘次真實評估，等同於「試一次錯一次」的盲目搜尋；DuoDiscover 透過評量尺讓代理能在廉價的內迴圈中進行數千次迭代，再以稀疏的真實評估做確認，使得這些過去被視為「必須由人類專家長期投入」的任務，得以在數週內由自主系統產出超越人類的成果。

**Q11：將 DuoDiscover 部署到實際產品或工作流程時，需要考量哪些工程與營運因素？**

A：實務部署時首先需要考量的是「真實評估資源的排程與隔離」——由於真實評估極為昂貴且耗時，輕量協調器必須具備佇列管理、優先級排序與公平分享的能力，避免少數代理壟斷評估資源。其次是「評量尺的可審計性」：每個代理自行生成的評量尺腳本必須經過正確性檢查與沙箱執行，以防止代理產生誤導自身或繞過安全邊界的評量尺。此外，由於代理會終止、合併與重生，整個系統需要可靠的狀態保存機制來追蹤每個程式碼版本的譜系，確保最終被接受的改進可被追溯與復現；最後，部署到生產環境時還需考量成本——單次執行的雲端算力與評估資源消耗可能相當可觀，需要權衡 ROI。

**Q12：DuoDiscover 對自主探索這個研究領域的整體影響為何？**

A：DuoDiscover 對領域的影響在於「重新定位了評估在自主探索中的角色」——它論證了評估器不應被視為固定前提，而應與搜尋目標共同演化，這個觀點將引發後續研究重新檢視各應用領域中「評估成本 vs. 搜尋迭代次數」的權衡。此外，論文中展示的「從軟體到晶片」的跨層級泛化能力，暗示了自主探索的下一個前沿將是那些評估成本極高、領域知識高度專業化的工程與科學問題；同時，Amdahl 權重估計、保真度測試與自下而上機群等具體機制也為後續工作提供了可借鏡的設計藍圖，可能催生一系列針對特定領域（如藥物設計、材料科學）的「共同探索」變體。

**Q13：DuoDiscover 論文本身承認了哪些限制？**

A：雖然論文主軸聚焦於成果展示，但從其設計與實驗設定可推論出幾項內在限制：第一，整個系統高度依賴真實評估的最終確認，因此對於「完全無法取得任何真實評估」的純模擬或黑盒環境，其有效性會大打折扣；第二，評量尺漂移的偵測仰賴保真度測試的頻率與覆蓋率，若真實評估預算極度受限（例如只能每數小時驗證一次），則漂移可能在被偵測前已造成大量無效迭代；第三，自下而上機群雖然避免了中央分解，但也意味著代理之間的知識共享僅限於「已確認的成果種子」，缺乏更細粒度的協作，這在需要多區域同步協調的最佳化任務中可能成為瓶頸。

**Q14：DuoDiscover 在哪些情境下可能會失敗或表現不佳？**

A：可能失敗的情境包括以下幾類：當最佳化目標高度分散且彼此耦合時（例如需要同時修改多個互相依賴的模組），單一代理的「單一目標 + 單一評量尺」框架可能難以捕捉全域互動；當評量尺本身難以廉價建構時（例如某些效能瓶頸只能透過昂貴的 profiling 工具才能測量），共同探索的優勢會被削弱；當真實評估本身具有高度隨機性或雜訊時，保真度測試的判斷可能不穩定，導致評量尺被頻繁誤判失效；此外，若初始程式碼的正確性檢查極為嚴苛（例如形式化驗證），代理可能花費大量時間在建構可通過正確性檢查的評量尺上，而非真正最佳化效能。

**Q15：基於 DuoDiscover 的成果，未來有哪些值得探索的研究方向？**

A：未來值得探索的方向可分為幾個層面：在機制層面，可研究「評量尺的遷移學習」——讓代理在某領域學到的評量尺設計經驗能加速其他領域的冷啟動；在理論層面，可建立共同探索的收斂性分析框架，回答「在何種條件下評量尺引導的搜尋能保證逼近真實最優解」；在應用層面，可將此範式推廣到藥物設計（濕實驗評估極為昂貴）、材料科學（合成與表徵成本高）、晶片實體設計（佈局與繞線驗證耗時）等領域；在系統層面，則可探索多代理之間更豐富的協作模式，例如共享評量尺函式庫或建立代理間的競標市場來分配評估資源，進一步突破當前「輕量協調器」的簡潔架構所帶來的協作上限。

## 實務應用指南

### 適用場景

DuoDiscover 適用於「真實評估昂貴、但程式碼可迭代修改」的工程最佳化任務。以下列舉五個最具實務價值的場景：

1. **LLM 推論引擎效能調校**：vLLM、TGI、TensorRT-LLM 等推論框架的吞吐量與延遲最佳化。單次完整基準（如多輪對話、批次推論、混合精度）往往需 60–90 分鐘，傳統調參只能覆蓋數十次評估。DuoDiscover 可同時探索 KV cache 排程、連續批次（continuous batching）策略、注意力實作等子模組。

2. **資料庫查詢與交易效能最佳化**：SQLite、PostgreSQL、DuckDB 等嵌入式或伺服器端資料庫的查詢計畫、索引策略、儲存引擎參數調校。TPC-C、YCSB 等基準單次執行需數小時，DuoDiscover 可針對熱點 SQL 路徑建立廉價代理評量尺。

3. **GPU/TPU 核心程式碼最佳化**：CUDA、Pallas/XLA、Triton 核心的融合、向量化、記憶體佈局調整。KernelBench、SOL-Exec 等基準涵蓋數百個核心，單核心評估需數分鐘到數十分鐘，DuoDiscover 可平行探索多個核心的向量化策略。

4. **CPU 微架構與晶片設計探索**：分支預測器、Cache 替換策略、執行埠分配等微架構參數的設計空間搜尋。論文中的 CPU 微架構任務單次評估需 28 小時，DuoDiscover 在 16.7 天內超越人類最佳設計與 ArchAgent v2。

5. **大型程式庫層級的程式碼加速**：SWE-fficiency、FormulaCode 等儲存庫級基準。DuoDiscover 在 SWE-fficiency 上將人類專家加速比翻倍，適用於企業內部框架、開源函式庫的長期效能治理。

### 實作前置條件

**資料與資產**
- 可迭代修改的程式碼儲存庫（單一檔案到完整 monorepo 皆可）

- 領域專家標註的「熱點區域」清單（可選，但能加速初期收斂）

**運算資源**
- 多個 LLM API 存取權（建議支援長上下文、工具呼叫的模型，如 Claude、GPT-4 等級）

- LLM agent 工程：能設計工具呼叫迴圈、上下文管理、錯誤恢復

- 基準測試設計：理解統計顯著性、避免過擬合單一工作負載

### 實作步驟建議

**第一步：建立真實評估的「黃金標準」**
先固定一個可重複、低變異的真實評估流程。論文中 vLLM 評估需 85 分鐘、CPU 微架構需 28 小時，這代表每次評估都必須可信。建議：
- 固定硬體、軟體版本、隨機種子
- 收集多次基準結果建立信賴區間
- 設計正確性檢查（編譯通過、單元測試通過、無 NaN/Inf）

**第二步：實作輕量協調器（Orchestrator）**
協調器是 DuoDiscover 的「稀缺資源管理者」，負責：
- 接收工作代理提交的「目標 + 評量尺」提案
- 排程真實評估（優先給進展中的代理）
- 執行保真度測試（fidelity test）：定期用真實評估驗證評量尺的排序一致性
- 終止停滯代理、合併相容成果、種子初始化新代理

**第三步：建構工作代理的共同探索迴圈**
每個工作代理需具備：
- 程式碼剖析工具（profiler、靜態分析）
- 評量尺生成能力：能根據目標區域撰寫 Python/Bash 腳本，回傳分數與正確性旗標
- 爬山法邏輯：根據評量尺分數決定保留或捨棄編輯
- 自我終止條件：當評量尺分數停滯 N 次後，主動結束

**第四步：設計保真度測試機制**
這是 DuoDiscover 區別於純代理搜尋的關鍵：
- 定期從代理的評量尺歷史中抽樣 K 個候選解
- 用真實評估重新評分，檢查與評量尺的排序相關性（Spearman 等）
- 若相關性跌破閾值，標記該評量尺為「漂移」並強制代理重建
- 每個被接受的加速都必須經過至少一次真實評估確認

**第五步：機群規模與預算調校**
論文中機群規模與任務難度相關：
- 簡單核心最佳化：2–4 個代理並行
- 儲存庫級任務：8–16 個代理並行
- 微架構設計：數十個代理，但真實評估排程需嚴格節流
- 設定每代理的真實評估配額（例如 10–20 次），避免單一代理耗盡預算

**第六步：建立成果合併與種子初始化流程**
當多個代理各自找到加速時：
- 檢查相容性（修改的檔案是否重疊）
- 合併相容的 patch，產生新代理的初始狀態
- 將已確認的加速作為「種子」傳遞給新代理，縮短探索路徑

### 潛在風險與注意事項

**風險一：評量尺漂移（Yardstick Drift）**
代理會「學會欺騙」評量尺——找出能提升代理分數但對真實效能無益的編輯。緩解措施：
- 強制每 N 次代理迭代後執行保真度測試
- 設定嚴格的「真實評估確認」閾值：只有真實分數提升才接受
- 監控代理分數與真實分數的差距，若差距擴大則觸發重建

**風險二：評估成本失控**
真實評估是稀缺資源，若協調器排程不當，可能：
- 浪費在低品質代理上
- 阻塞高潛力代理的進展
緩解措施：實作優先權佇列，根據代理近期進展速度動態調整；設定硬性預算上限與熔斷機制。

**風險三：正確性迴歸**
效能最佳化常伴隨正確性風險（數值誤差、邊界條件、並發競爭）。緩解措施：
- 每個評量尺必須包含正確性檢查（單元測試、斷言、參考實作比對）
- 正確性失敗的解直接標記為 ⊥，不計入評量尺分數
- 真實評估階段加入更嚴格的回歸測試套件

**風險四：過擬合單一工作負載**
代理可能找到僅對特定基準有效的加速。緩解措施：
- 評量尺應包含多個代表性輸入
- 真實評估階段使用保留的「測試集」工作負載驗證
- 監控加速比在不同輸入分佈下的穩定性

**風險五：程式碼品質與可維護性下降**
代理生成的加速可能犧牲可讀性、引入 hack、增加技術債。緩解措施：
- 設定程式碼風格檢查、複雜度上限
- 將「可合併性」作為代理評分的一部分
- 定期由人類工程師審查已確認的加速

### 與其他技術的整合建議

**與 AlphaEvolve 整合**
AlphaEvolve 要求使用者手動標記 begin/end 區域，DuoDiscover 則由代理自動發現目標。可採混合策略：對已知熱點使用 AlphaEvolve 風格的標記驅動搜尋，對未知區域使用 DuoDiscover 的共同探索。

**與 CI/CD 整合**
- 將 DuoDiscover 的真實評估包裝為 CI job，僅在合併請求觸發
- 將已確認的加速自動產生 PR，附帶基準報告
- 在 nightly build 中運行長期探索，持續尋找新加速

**與效能監控系統整合**
- 將生產環境的 profiling 資料（如 Pyroscope、eBPF 追蹤）作為代理的初始上下文
- 將 DuoDiscover 找到的加速回饋到監控系統，建立「自動最佳化」儀表板
- 用 A/B 測試框架驗證加速在真實流量下的效果

**與現有 LLM Agent 框架整合**
DuoDiscover 的工作代理是「off-the-shelf」設計，可直接包裝現有 agent（如 SWE-agent、Aider、Continue）。建議：
- 為代理新增「評量尺生成」工具（執行 Python 腳本、回傳分數）
- 為代理新增「保真度測試請求」工具（呼叫協調器排程真實評估）
- 保留代理的自主性，僅在協調器層介入資源分配

**與領域特定工具鏈整合**
- 資料庫場景：整合 EXPLAIN、pg_stat_statements
- GPU 核心場景：整合 nvprof、Nsight Compute
- 晶片設計場景：整合 Gem5、Synopsys 工具鏈

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）與第 2 節的圖 2，建立「機群 + 評量尺 + 保真度測試」的心智模型。理解「為什麼不能直接用真實評估」是關鍵——這是 DuoDiscover 存在的前提。可跳過數學符號，專注於三個機制的故事：共同探索目標與評量尺、持續驗證評量尺、自下而上的機群協調。

**給 AI 工程師**：重點閱讀第 2.2 節的共同探索迴圈設計、第 3 節的保真度測試實作細節、以及附錄中的評估成本表（Table 8）。思考如何將現有的 LLM agent 框架改造成 DuoDiscover 的工作代理——特別是評量尺生成工具的設計介面。論文的實驗章節展示了不同任務下的機群規模與預算分配，這是工程化時的直接參考。

**給研究人員**：第 2.1 節的問題形式化（X、f、c_f、N 代理、預算）是後續理論分析的起點。可深入探討的開放問題包括：保真度測試的最佳抽樣策略、機群規模與任務難度的理論關係、評量尺漂移的形式化分析、與貝氏最佳化或元學習的結合。論文的實驗涵蓋從軟體到晶片的完整運算堆疊，是少數能橫向比較自主探索系統泛化能力的基準。

**給產品經理**：聚焦於第 1 節的應用場景與第 4 節的實驗結果。DuoDiscover 的商業價值在於「將昂貴的專家調校自動化」——vLLM 的 1.92× 加速、SQLite 的 1.38× 加速、CPU 微架構的 1.65× ArchAgent v2 增益，都是可量化的 ROI。部署時需評估：真實評估的單次成本、預期加速比、程式碼可維護性的取捨。論文的 16.7 天 vs 40+ 天對比，說明了在昂貴評估場景下，DuoDiscover 的效率優勢更為顯著。
