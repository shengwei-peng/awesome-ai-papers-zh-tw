# 跳過壓縮器：程式碼代理在挑選完整檔案時能修正更多議題

**原文標題：** Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files  
**作者：** Xiaocong Yang、Rishit Chatterjee、Himanshu Udupi 等 5 位作者  
**發布日期：** 2026-10-15  
**HF 連結：** [https://huggingface.co/papers/2610.21073](https://huggingface.co/papers/2610.21073)  
**arXiv：** [https://arxiv.org/abs/2610.21073](https://arxiv.org/abs/2610.21073)  

---

## ⚡ TL;DR

程式碼代理的上下文視窗遠小於儲存庫，現有壓縮器與檢索器常遺漏需修改的檔案或破壞原始文字。
本文提出 CQ2-CARE，兩次詢問模型需修改的檔案並完整逐字呈現，無需壓縮模型介入。
CQ2-CARE 解決 43.7% 與 46.7% 議題，超越所有壓縮器與檢索器基線。

---

## 摘要翻譯

程式碼代理（coding agent）處理的程式碼儲存庫（repository），其規模往往遠超過其上下文視窗（context window）所能容納的範圍。提示壓縮器（prompt compressor）與檢索器（retriever）提供了此問題的解決方案，但修補（patch）一個議題需要同時具備兩項要素：必須修改的檔案，以及這些檔案原貌的程式碼，因為模型必須重現其編輯的程式碼行。檢索器依據程式碼與議題的相似度進行排序，而非依據該程式碼是否需要修改；壓縮器則為了符合詞元預算（token budget）而刪除文字。我們展示，在相同的詞元預算下，當預算用於選擇哪些檔案以逐字（verbatim）方式呈現（正如我們所提出的簡單選擇器 CQ2-CARE 所為），代理所解決的議題數量，比將預算用於詞元剪除（token pruning）或區塊檢索（chunk retrieval）時更多。我們在 300 個最近的 SWE-rebench 議題上，將每個上下文限制在相同的每議題預算內，並以該基準測試的測試案例評分每個修補。在 GPT-5.6 與 Claude Opus 5 上，CQ2-CARE 的解決率（resolved rate）分別達 43.7% 與 46.7%，在任一模型上皆比三種壓縮器中最佳者高出 6.3 個百分點，比三種檢索器中最佳者分別高出 9.3 與 12.7 個百分點。CQ2-CARE 甚至比兩種專為議題解析（issue resolution）所訓練的方法解決更多議題，分別比 SweRank 高出 0.7 與 1.7 個百分點，比 SWE-Pruner 高出 2.0 與 7.3 個百分點。我們的分析揭示了基線方法（baseline method）的缺陷：檢索器經常遺漏需要編輯的檔案，而壓縮器雖保留了這些檔案卻改動了其文字內容，導致較少的修補能成功套用（以 ε 衡量）。精確檔案選擇（exact-file selection）無需壓縮模型（compression model），並以程式碼儲存庫中的原始樣貌呈現每一行程式碼，使模型能夠重現其所編輯的程式碼。

### 核心貢獻（3～5點）
- 提出 CQ2-CARE 精確檔案選擇方法，證明在相同詞元預算下，將預算用於選擇完整檔案逐字呈現，比用於詞元剪除或區塊檢索能解決更多議題。
- 在 300 個 SWE-rebench 議題上以 GPT-5.6 與 Claude Opus 5 進行端到端（end-to-end）實驗，CQ2-CARE 解決率達 43.7% 與 46.7%，顯著優於三種壓縮器、三種檢索器，以及專為議題解析訓練的 SweRank 與 SWE-Pruner。
- 系統性分析基線方法的失敗模式：檢索器因依相似度排序而常遺漏需修改的檔案；壓縮器雖保留目標檔案卻改動文字，導致修補無法成功套用。
- 論證精確檔案選擇的獨特優勢：無需壓縮模型即可呈現檔案原貌，使模型能逐字重現所編輯的程式碼行，避免中段遺失效應（lost in the middle）與文字失真問題。

### 適合對象
從事自動化程式碼修復、軟體工程大型語言模型（LLM）應用、檢索增強生成（RAG）於程式碼任務、以及提示壓縮技術研究之學者與工程師；亦適合關注 AI 程式碼代理（coding agent）實務部署與基準測試（benchmark）評估之業界研發人員。

## 深度分析

#### 方法論解析

本論文提出 CQ2-CARE，一種極簡卻有效的「精確檔案選擇器」（exact-file selector），其核心洞見在於：當程式碼代理（coding agent）需要在大型程式碼儲存庫（repository）中修復議題（issue）時，token 預算（token budget）應該花在「選擇哪些檔案完整且逐字（verbatim）地呈現」，而非花在壓縮或檢索既有內容上。

**核心設計理念**

傳統方法分為兩大路線，各有致命缺陷：
- **檢索器（retriever）**：依據與議題的相似度排序程式碼區塊或檔案，但相似度高的內容（如議題範本 issue template）未必是需要編輯的檔案，導致「黃金檔案召回率」（gold-file recall, ρ）低落。
- **提示壓縮器（prompt compressor）**：透過小型模型刪減被認為不重要的詞元（token），但會破壞需要編輯的程式碼行，導致「逐字行數比率」（verbatim line ratio, ε）下降，使修補（patch）無法正確套用。

CQ2-CARE 的解法是：直接讓目標模型（under test）兩次獨立回答「哪些檔案必須修改」，取兩次答案的交集（intersection）作為最終選擇。這種「雙重取樣取交集」的設計基於一個假設：兩次獨立判斷皆指向同一檔案，代表該檔案確實需要修改的可靠度較高（呼應 Wang et al., 2023 的 self-consistency 概念）。

**方法流程**

1. **雙重取樣**：將議題文本 q 與儲存庫 R 提供給模型 m，詢問「哪些檔案必須修改」，獨立取樣兩次得到檔案集合 F₁ 與 F₂。
2. **交集篩選**：取 F₁ ∩ F₂ 作為候選檔案集，確保選擇的可靠性。
3. **補充依賴程式碼**：使用 grep 找出模型額外請求的定義（definitions）、呼叫者（callers）或字串（strings）對應的短程式碼片段，即使這些片段位於未選檔案中，也以逐字形式加入上下文。
4. **完整呈現**：所有選中的檔案以原始、未經修改的完整形式放入上下文，無需任何壓縮模型介入。

**關鍵設計權衡**

論文強調 CQ2-CARE 的優勢在於「選擇單位」（unit of selection）而非「取樣機制」。實驗顯示，即使將雙重取樣簡化為單次取樣並截斷至相同檔案數量，表現仍相近（§4.4），這意味著「選對少數檔案」比「如何取樣」更為關鍵。

此設計巧妙地避開了兩個常見陷阱：
- **中段遺失效應（lost in the middle）**：由於只選擇少數檔案，重要內容自然落在上下文的前後端，模型注意力較可靠。
- **壓縮失真**：完全不經過壓縮模型，保留所有原始語法元素（如 f字串 的 `f` 前綴、引號等），使模型能準確引用（quote）需要編輯的程式碼。

**與 SWE-bench 預設管線的差異**

SWE-bench 預設使用檔案級 BM25 檢索器，而 CQ2-CARE 改用模型自身的判斷。這個轉換的代價是兩次額外的模型呼叫，但換來的是更高的黃金檔案召回率與逐字保留率。

#### 實驗數據解讀

**實驗設計**

論文在 SWE-rebench 排行榜（Badertdinov et al., 2025）上選取 300 個議題，每個儲存庫一個議題，並採用嚴格的預算匹配（budget-matched）設計：每個方法在每個議題上都被限制在相同的 token 預算 Bᵢ 下，產生一個修補，並由基準測試的測試套件評分。這種設計消除了「方法 A 表現較好只是因為它用了更多 token」的混淆變因。

**主要結果**

| 方法類型 | 方法 | GPT-5.6 解決率 | Claude Opus 5 解決率 |
|---------|------|---------------|---------------------|
| 檢索器 | BM25 (chunks) | 29.0% | 34.0% |
| 檢索器 | Dense (chunks) | 22.7% | 33.7% |
| 檢索器 | BM25 (files) | 34.3% | 34.0% |
| 訓練方法 | SweRank (files) | 43.0% | 45.0% |
| 壓縮器 | LongCodeZip | 37.3% | 36.0% |
| 壓縮器 | LongLLMLingua | 35.0% | 29.0% |
| 壓縮器 | LLMLingua-2 | 30.0% | 40.3% |
| 訓練方法 | SWE-Pruner | 41.7% | 39.3% |
| **本文方法** | **CQ2-CARE** | **43.7%** | **46.7%** |

**關鍵發現解讀**

1. **CQ2-CARE 在兩個模型上皆達到最高解決率**：43.7%（GPT-5.6）與 46.7%（Claude Opus 5），比最佳壓縮器高出 6.3 個百分點，比最佳檢索器高出 9.3 至 12.7 個百分點。

2. **擊敗專門訓練的方法**：CQ2-CARE 比 SweRank（訓練用於議題解析的函數級檢索器）高出 0.7 與 1.7 點，比 SWE-Pruner（訓練用於程式碼代理的行級剪除器）高出 2.0 與 7.3 點。這尤其值得注意，因為 CQ2-CARE 本身不需要任何訓練。

3. **失敗模式清晰分離**：
   - **檢索器**：保留逐字內容（ε 高）但經常遺漏需編輯的檔案（ρ 低）。圖 1 的範例顯示 BM25 將預算填滿議題範本（與議題文字高度相似），卻完全未包含 `twine/sdist.py`。
   - **壓縮器**：保留需編輯的檔案（ρ 高）但破壞其文字（ε 低）。圖 1 顯示 LLMLingua-2 刪除了第 23 行的 `f` 前綴與引號，導致模型寫出對不存在行的修改。

4. **受控實驗驗證因果關係**：
   - 從 CQ2-CARE 的上下文刪除詞元（檔案不變），損失程度與主實驗中壓縮器的損失相近。
   - 從相同檔案出發、保留完整行的壓縮器，能匹配 CQ2-CARE 的表現。
   - 這證明「黃金檔案召回率」與「逐字保留率」各自獨立地影響最終表現。

**量化指標 ρ 與 ε 的意義**

論文定義兩個關鍵指標：
- **ρ（黃金檔案召回率）**：上下文中包含的黃金修補檔案比例。
- **ε（逐字行數比率）**：上下文行數中與儲存庫原始內容逐字相同的比例。

圖 1 同時展示這兩個指標的極端案例：BM25 的 ρ = 0.0%、ε = 100.0%（完全沒選對檔案，但選中的內容完整）；LLMLingua-2 的 ρ = 100.0%、ε = 0.5%（選對檔案但內容幾乎全被破壞）；CQ2-CARE 則兩者皆達 100%。

**模型差異觀察**

Claude Opus 5 在多數方法上表現略優於 GPT-5.6，但 CQ2-CARE 在兩個模型上的領先幅度不同：在 Claude 上對 LLMLingua-2 的領先較窄（46.7% vs 40.3%，差距 6.4 點），在 GPT-5.6 上對 LongCodeZip 的領先較大（43.7% vs 37.3%，差距 6.4 點）。這暗示不同模型對壓縮失真的敏感度可能不同。

#### 與現有研究的比較

**與三大既有路線的定位**

1. **提示壓縮路線**（Jiang et al., 2023; Pan et al., 2024; Shi et al., 2025）：
   - 代表方法：LLMLingua-2、LongLLMLingua、LongCodeZip。
   - 共同假設：刪除「不重要」的詞元對最終輸出影響有限。
   - CQ2-CARE 的挑戰：對於「答案生成」任務（如摘要、問答），這個假設成立；但對於「程式碼編輯」任務，模型必須逐字引用需要修改的行，任何刪除都會導致修補無法套用。

2. **檢索路線**（Zhang et al., 2023; Jimenez et al., 2024; Suresh et al., 2025）：
   - 代表方法：BM25、Dense retrieval、SWE-bench 預設的檔案級 BM25。
   - 共同假設：與議題相似的程式碼最可能需要修改。
   - CQ2-CARE 的挑戰：相似度不等於「必須修改」。議題範本、錯誤訊息字串、相關測試都可能與議題高度相似，但只有少數檔案真正需要編輯。

3. **議題解析專用方法**（Wang et al., 2026; Jia et al., 2026）：
   - 代表方法：SWE-Pruner（行級剪除）、SweRank（函數級檢索）。
   - 共同特徵：專門為議題解析任務訓練。
   - CQ2-CARE 的優勢：無需訓練，僅依靠模型自身的判斷與簡單的交集邏輯，即能超越這些專用方法。

**改進幅度**

- 相對最佳壓縮器：+6.3 個百分點（兩個模型平均）。
- 相對最佳檢索器：+9.3 至 +12.7 個百分點。
- 相對 SweRank：+0.7 至 +1.7 個百分點（最接近的競爭者）。
- 相對 SWE-Pruner：+2.0 至 +7.3 個百分點。

**限制與邊界條件**

1. **依賴模型自身判斷**：CQ2-CARE 假設模型能正確識別需要修改的檔案。若模型判斷錯誤（例如不理解議題），雙重取樣的交集仍會是錯誤的。對於較弱或未針對程式碼任務微調的模型，此方法可能失效。

2. **未處理多檔案複雜編輯**：論文未明確討論需要同時編輯多個分散檔案的情況。SWE-rebench 的議題可能涉及跨檔案依賴，但 CQ2-CARE 的「選少數檔案」策略可能在這類議題上遇到瓶頸。

3. **未涵蓋動態探索**：CQ2-CARE 是單次選擇，沒有迭代探索機制。相較之下，實際的程式碼代理（如 SWE-agent）會在多輪中動態讀取檔案、執行測試、調整方向。

4. **SWE-Pruner 的窄幅差距**：在 Claude Opus 5 上，CQ2-CARE 對 SWE-Pruner 的領先達 7.3 點，但在 GPT-5.6 上僅 2.0 點，顯示 SWE-Pruner 在某些模型上仍有競爭力。

5. **未與最新代理框架比較**：論文未與 SWE-agent、AutoCodeRover 等完整代理系統比較，這些系統結合了多輪探索、測試執行與反思機制。

#### 可重現性評估

**程式碼與資料可用性**

從論文內容可推斷以下可重現性要素：

1. **基準測試**：使用 SWE-rebench 排行榜（Badertdinov et al., 2025）的 300 個議題，該排行榜是公開的基準測試，議題與測試套件應可從官方取得。

2. **評估流程**：採用基準測試的測試套件進行評分，這是 SWE-rebench 標準做法，應可重現。

3. **CQ2-CARE 實作**：方法本身極為簡單（兩次模型呼叫 + 交集 + grep），不依賴複雜的訓練流程或專有模型，理論上易於實作。

4. **基線方法**：BM25、LongCodeZip、LongLLMLingua、LLMLingua-2、SweRank、SWE-Pruner 皆有公開實作或論文可供參考。

**可重現性疑慮**

1. **模型版本**：論文使用 GPT-5.6 與 Claude Opus 5，這些是商業模型的特定版本。若讀者使用不同版本（如 GPT-4o、Claude 3.5 Sonnet），結果可能不同。論文未說明是否會公開 API 呼叫記錄或具體的 prompt 模板。

2. **預算設定**：每個議題的 token 預算 Bᵢ 是「CQ2-CARE 上下文的實際大小」，這是一個事後定義（post-hoc），可能引入選擇偏差。讀者重現時需先執行 CQ2-CARE 以確定預算，再執行其他方法。

3. **隨機性**：雙重取樣的溫度（temperature）參數、grep 的具體正則表達式、補充片段的長度限制等細節未在論文中詳述。

4. **未提供開源承諾**：從提供的文本片段無法確認作者是否會釋出程式碼儲存庫。論文的 arXiv 編號（2610.21073v1）顯示這是預印本，正式發表時可能會補充可重現性聲明。

**重現難度評估**

整體而言，CQ2-CARE 的概念簡單且實作成本低，但要在完全相同的條件下重現所有 300 個議題的精確數字，需要：
- 存取相同的模型版本（GPT-5.6、Claude Opus 5）。
- 精確的 prompt 模板與超參數。
- SWE-rebench 的完整評估環境。

對於資源有限的研究者，可先在較小的議題子集上驗證 CQ2-CARE 的相對優勢是否成立。

#### 未來研究方向

**1. 結合動態探索的混合策略**

CQ2-CARE 目前是單次檔案選擇，未來可探索與多輪代理框架的結合：
- 第一輪使用 CQ2-CARE 選擇初始檔案。
- 後續輪次根據測試失敗訊息動態調整選擇。
- 這種「靜態選擇 + 動態修正」的混合策略可能進一步提升解決率。

**2. 檔案選擇的理論分析**

論文指出「選擇單位」比「取樣機制」更關鍵，但未深入分析：
- 為何雙重取樣的交集比單次取樣更可靠？是否存在理論上的共識保證？
- 對於不同類型的議題（單檔案修改 vs. 跨檔案重構），最佳檔案數量是否不同？
- 模型判斷的「校準度」（calibration）如何影響選擇品質？

**3. 處理大型儲存庫的可擴展性**

SWE-rebench 的儲存庫平均有 3,010 個非測試檔案，但更大的工業級儲存庫可能有數萬個檔案：
- CQ2-CARE 的兩次模型呼叫成本是否會成為瓶頸？
- 是否需要預先過濾（例如用 BM25 選出前 100 個候選檔案，再讓模型從中選擇）？
- 階層式選擇（先選目錄，再選檔案）是否更有效？

**4. 與其他壓縮技術的正交組合**

CQ2-CARE 選擇的檔案本身仍可能很長，未來可探索：
- 在選中的檔案內部，使用結構感知（structure-aware）的壓縮（例如保留函數簽名與註解，壓縮函數主體）。
- 對於不需要編輯但需要參考的檔案，使用摘要 + 關鍵片段的混合表示。
- 這種「檔案級精確選擇 + 函數級語意壓縮」的組合可能進一步節省 token。

**5. 跨語言與跨領域泛化**

論文實驗僅限於 Python 儲存庫（基於 SWE-rebench），未來可探索：
- CQ2-CARE 在 Java、JavaScript、Go 等語言的儲存庫上是否同樣有效。
- 對於非程式碼任務（如文件編輯、設定檔修改），精確檔案選擇是否仍優於壓縮。
- 在多模態情境下（如包含圖片的議題），如何擴展選擇單位。

**6. 失敗案例的深入分析**

論文展示了 ρ 與 ε 的極端案例，但未系統分析 CQ2-CARE 失敗的議題：
- 失敗的議題是因為模型判斷錯誤、還是因為需要編輯的檔案不在模型「認為」重要的檔案中？
- 是否存在議題特徵（如議題長度、涉及檔案數量）可以預測 CQ2-CARE 的成功率？
- 對於失敗案例，是否需要 fallback 機制（如自動切換到檢索器）？

**7. 與人類專家的比較**

CQ2-CARE 模擬了「讓模型自己判斷哪些檔案重要」的過程，未來可與人類軟體工程師的判斷比較：
- 人類專家選擇的檔案與模型選擇的檔案重合度有多高？
- 人類專家會選擇更多還是更少的檔案？
- 這種比較有助於理解模型在程式碼理解任務上的能力邊界。

**8. 成本效益分析**

CQ2-CARE 需要兩次額外的模型呼叫，但避免了壓縮模型的運算成本：
- 在不同模型價格下，CQ2-CARE 的總成本（選擇 + 修補）是否仍低於壓縮器（壓縮 + 修補）？
- 對於較小的儲存庫，雙重取樣的額外成本是否值得？
- 是否存在「單次取樣 + 信心閾值」的更便宜變體？

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於程式碼代理（coding agent）在處理大型程式碼儲存庫時所面臨的上下文視窗限制問題。SWE-bench 的程式碼儲存庫平均包含 3,010 個非測試檔案與 438K 行程式碼，遠超過模型能一次容納的範圍。要成功修補一個議題，代理必須同時滿足兩個條件：找出「必須修改的檔案」，以及「精確呈現這些檔案的原始內容」，因為模型必須能逐字引用它要編輯的程式碼。這使得「在固定詞元預算下，應該採用何種儲存庫壓縮方式」成為一個關鍵的實務問題。

**Q2：為什麼現有的檢索器與壓縮器方法會失敗？**
A：檢索器根據與議題的相似度來排序程式碼區塊或檔案，因此措辭與議題相似的文字（例如議題範本）可能會排在使用者真正需要編輯的檔案之前，導致模型看不到目標檔案。壓縮器則會刪除被小型模型評為「最不有用」的詞元或程式碼區塊，這在產生摘要時影響不大，但對於編輯任務卻是致命的——因為模型必須逐字引用要修改的程式碼，一旦詞元被刪除，修補就會引用不存在的行而無法套用。論文中以 f字串 缺失的議題為例，清楚展示了這兩種失敗模式。

**Q3：為什麼這個問題在實務上很重要？**
A：基於大型語言模型的代理現在已經能端到端地解決真實的軟體議題，因此管理進入上下文的內容已成為降低成本的關鍵——研究顯示這能將代理成本減半，或削減五分之一到三分之一。此外，每個提示詞元在每次呼叫時都要付費，且模型對長輸入中段資訊的使用可靠度較低（即「中段遺失」效應）。因此，如何在有限預算內最大化議題解決率，直接影響程式碼代理的實用性與經濟效益。

**Q4：CQ2-CARE 的核心方法是什麼？**
A：CQ2-CARE 是一個簡單的選擇器，它對同一個模型進行兩次獨立詢問，請模型指出哪些檔案必須修改，然後保留兩次回答都同意的檔案，作為可靠性的訊號。接著，它會透過 grep 找出模型所要求的定義、呼叫者或字串等短跨度內容，將這些依賴的程式碼也以逐字方式加入上下文。由於每個被選中的檔案都完整呈現，選擇器必須精準地只挑出少數且正確的檔案。

**Q5：CQ2-CARE 的關鍵創新點為何？**
A：其核心創新在於「將預算花在選擇哪些檔案完整呈現」，而非壓縮或裁切內容。這種做法完全不需要壓縮模型參與運算迴圈，因此簡化了流程並避免了壓縮帶來的資訊損失。論文的分析顯示，方法的優勢來自於「選擇單元」的設計——將單次回答裁剪到相同數量的檔案，效果也差不多，證明了「選對少數檔案」比「如何壓縮」更為關鍵。

**Q6：CQ2-CARE 有哪些重要的設計選擇？**
A：第一個關鍵設計是利用兩次獨立取樣的「一致性」作為可靠性的代理，因為兩次都同意的檔案更可能是真正需要修改的。第二個設計是結合 grep 來補充模型請求的依賴程式碼，即使這些程式碼不在被選中的檔案中，也能以逐字方式呈現。第三個設計是堅持以「整個檔案」為單位呈現，而非區塊或函數，這保證了模型能完整看到檔案內容並準確引用要編輯的行。

**Q7：實驗使用了哪些基準測試與模型？**
A：實驗採用 SWE-rebench 排行榜中的 300 個議題，每個儲存庫一個議題，並使用兩個模型家族進行測試：GPT-5.6 與 Claude Opus 5。比較對象包括三個提示壓縮器（LongCodeZip、LongLLMLingua、LLMLingua-2）、三個檢索器（BM25 區塊、稠密區塊、BM25 檔案），以及兩個專為議題解析訓練的方法（SweRank 與 SWE-Pruner）。每個方法都被限制在與 CQ2-CARE 相同的逐議題詞元預算下，並由基準測試的測試套件評分修補。

**Q8：主要的實驗結果為何？**
A：在 GPT-5.6 與 Claude Opus 5 上，CQ2-CARE 分別解決了 43.7% 與 46.7% 的議題，比任一模型下三個壓縮器中最佳的還高出 6.3 個百分點，比三個檢索器中最佳的還高出 9.3 與 12.7 個百分點。更值得注意的是，它甚至勝過兩個專為議題解析訓練的方法：比 SweRank 高出 0.7 與 1.7 點，比 SWE-Pruner 高出 2.0 與 7.3 點，顯示簡單的選擇策略可以超越專門訓練的系統。

**Q9：消融研究揭示了哪些洞見？**
A：論文將損失分解為兩個面向：黃金檔案召回率（ρ，即修補所需檔案是否在上下文中）與逐字行數比例（ε，即上下文中的行是否完整呈現）。控制測試顯示，從 CQ2-CARE 的上下文中刪除詞元（不改變檔案）所造成的損失，與主要比較中壓縮器所損失的相當；而從相同檔案出發、保留整行的壓縮器則能匹配選擇器的表現。這證明了檢索器主要輸在「找不到要編輯的檔案」，而壓縮器主要輸在「改變了檔案文字」，兩者各造成獨立的損失。

**Q10：哪些實際情境最能受惠於這項技術？**
A：任何需要在大型程式碼儲存庫上進行端到端議題解析的程式碼代理都能直接受惠，特別是在企業級或開源專案中，儲存庫規模往往遠超模型上下文視窗。在成本敏感的部署情境中，由於 CQ2-CARE 不需要壓縮模型參與運算，可以降低運算開銷與延遲。此外，對於需要產生精確修補並通過專案測試套件的自動化工作流程，這種方法能顯著提升修補的可套用率。

**Q11：在產品化時需要考慮哪些實務因素？**
A：首先，CQ2-CARE 不需要額外的壓縮模型，這簡化了部署管線並降低了維護成本。其次，由於它對 GPT-5.6 與 Claude Opus 5 都有效，顯示其具有跨模型家族的泛化能力，產品不必綁定特定模型供應商。然而，由於方法仰賴模型本身對「哪些檔案需要修改」的判斷，模型品質會直接影響選擇結果，因此選擇夠強的基礎模型仍是關鍵。

**Q12：這項研究對領域的影響是什麼？**
A：這項研究挑戰了「必須壓縮才能處理長上下文」的普遍假設，證明了在議題解析任務中，「精確選擇」比「聰明壓縮」更有效。它可能促使研究者重新思考程式碼代理的上下文管理策略，將更多精力放在檔案選擇機制上，而非開發更複雜的壓縮模型。此外，論文中對「黃金檔案召回率」與「逐字行數比例」的分解框架，也為未來評估上下文管理方法提供了清晰的分析工具。

**Q13：論文承認了哪些限制？**
A：論文坦承其評估僅限於 300 個 SWE-rebench 議題與兩個模型家族，因此結果的泛化性仍需在更多基準與模型上驗證。此外，雖然 CQ2-CARE 在議題解析任務上表現優異，但對於程式碼補完、程式碼審查或其他程式碼相關任務的適用性尚未探討。論文中也指出，單次回答裁剪到相同檔案數量時效果相近，這意味著方法的優勢主要來自「選擇單元」而非取樣機制本身，這也暗示了進一步改進的空間有限。

**Q14：在哪些情況下 CQ2-CARE 可能會失敗？**
A：當議題描述模糊或涉及多個儲存庫時，模型可能難以準確判斷哪些檔案需要修改，導致兩次獨立詢問的共識檔案集合不正確。此外，當修補需要修改的檔案依賴於許多其他檔案中的定義或呼叫者時，即使加入了 grep 找到的短跨度，仍可能遺漏關鍵上下文。對於需要跨多個檔案進行協調性修改的大型重構任務，這種「精確選擇少數檔案」的策略也可能不夠用。

**Q15：未來的研究方向有哪些？**
A：未來可以探索更聰明的檔案選擇機制，例如結合靜態分析、程式依賴圖或專案結構資訊來輔助模型的判斷。另一個方向是將這種「選擇優於壓縮」的理念推廣到其他程式碼任務，例如程式碼補完、漏洞修復或測試生成。此外，也值得研究如何動態調整預算分配——例如在議題簡單時減少檔案數量，在議題複雜時增加——以進一步提升效率與效果的平衡。

## 實務應用指南

### 適用場景

1. **企業內部程式碼維護自動化**：大型企業的程式碼儲存庫常包含數千個檔案（如金融機構的核心交易系統、電商平台），開發團隊難以手動追蹤所有議題。CQ2-CARE 可部署為內部 Jira/GitHub Issues 自動分流代理，自動定位需修改的檔案並產生修補草案，縮短從議題建立到 PR 審查的時間。

2. **開源專案的維護者助手**：開源專案（如 Python 的 `twine`、`requests`）常面臨大量 issue 積壓，但維護者人手有限。CQ2-CARE 可作為 GitHub Bot 自動回應，針對明確的 bug 報告（如缺少 f-string 前綴、錯誤訊息格式錯誤）產生可套用的修補，維護者只需審查而非從頭撰寫。

3. **CI/CD 流程中的自動修復**：在持續整合流程中，當測試失敗時自動呼叫 CQ2-CARE 代理，根據錯誤日誌與測試名稱定位需修改的原始檔並嘗試修復，特別適用於回歸測試失敗的場景。

4. **程式碼審查前的預處理**：在送交人類審查前，先用 CQ2-CARE 產生候選修補並驗證其可套用性（patch apply），過濾掉無法套用的低品質建議，減少審查者負擔。

5. **教育訓練環境的除錯助教**：在程式設計課程中，學生提交的作業出現錯誤時，系統可使用 CQ2-CARE 定位錯誤檔案並提供精確的修正建議，幫助學生理解問題所在。

### 實作前置條件

**資料需求**：
- 目標程式碼儲存庫的完整檔案樹與檔案內容（需可被代理讀取）
- 議題描述資料集（標題、內文、錯誤訊息），格式與 SWE-rebench 或 SWE-bench 相容
- 議題對應的測試案例，用於評估修補是否成功（黃金檔案清單與測試通過/失敗狀態）
- 至少 200–300 筆歷史議題作為驗證集，用於校準檔案選擇的準確率

**運算資源**：
- 具備大型上下文視窗（建議 ≥ 64K tokens）的 LLM API 存取權限（如 GPT-5.6、Claude Opus 5，或同等級開源模型如 DeepSeek-Coder-V2、Qwen2.5-Coder-32B）
- 兩次獨立推理的計算預算（每次議題約 2× 模型呼叫成本）
- 基本的 grep/ripgrep 工具用於擷取定義、呼叫者與字串片段
- 沙箱環境執行測試套件（Docker 容器或 VM）

**技能需求**：
- 熟悉 LLM 提示工程（prompt engineering），特別是結構化輸出與函式呼叫
- 具備 Python 後端開發能力，能整合 Git 操作、檔案 I/O 與 API 呼叫
- 了解 SWE-bench 評估協議（patch apply + 測試執行）
- 基本的統計分析能力，用於比較不同方法的解決率

### 實作步驟建議

**步驟 1：建立檔案選擇器 CQ2-CARE**
- 對每個議題，向目標模型發出兩次獨立提示：「根據以下議題，列出解決此問題必須修改的檔案清單」，設定 `temperature > 0` 以取得多樣性
- 取兩次回答的交集（intersection）作為高信心度的檔案清單；若交集為空，退而採用聯集（union）
- 將選定的檔案完整、逐字地放入上下文，確保沒有任何詞元被剪除或改寫

**步驟 2：補充依賴程式碼片段**
- 從模型回答中解析「需要的定義、呼叫者或字串」請求
- 使用 grep/ripgrep 在儲存庫中搜尋對應的程式碼片段
- 將這些片段以「檔名:行號」格式附加至上下文，確保修補依賴的程式碼也逐字呈現

**步驟 3：建構修補生成流程**
- 將議題描述 + 選定檔案內容 + 補充片段組裝為單一提示
- 呼叫同一模型產生 unified diff 格式的修補
- 解析模型輸出，提取 `diff --git` 區塊

**步驟 4：建立評估管線**
- 在乾淨的 git 工作樹中套用修補（`git apply` 或 `patch` 指令）
- 執行議題對應的測試套件，記錄通過/失敗狀態
- 計算兩個關鍵指標：ρ（黃金檔案召回率，修補中包含的黃金檔案比例）與 ε（逐字行比例，修補中與原始碼完全一致的行數比例）

**步驟 5：基準比較與調校**
- 在 300 筆 SWE-rebench 議題上比較 CQ2-CARE 與基線方法（BM25、LongCodeZip、LLMLingua-2、SweRank、SWE-Pruner）
- 目標：GPT-5.6 達到 ≥ 43% 解決率、Claude Opus 5 達到 ≥ 46% 解決率
- 若效能未達標，調整檔案選擇的提示詞或增加第三次取樣以提升信心度

**步驟 6：部署與監控**
- 將管線容器化（Docker），設定 API rate limit 與重試機制
- 建立儀表板追蹤每日解決率、平均詞元使用量、修補可套用率
- 設定人工審查閘門：當 ρ < 0.5 或 ε < 0.8 時自動標記為低信心度

### 潛在風險與注意事項

**風險 1：模型幻覺導致選錯檔案**
- 現象：模型可能將議題中的關鍵字誤導至相似但無關的檔案（如議題範本、文件）
- 緩解：採用兩次取樣交集機制；若交集為空則退回聯集並標記低信心度；對 ρ < 0.5 的修補一律送人工審查

**風險 2：跨檔案修改的議題失敗率較高**
- 現象：當修補需同時修改多個檔案時，單一檔案選擇可能遺漏部分依賴
- 緩解：擴大檔案選擇數量上限（從預設的少數檔案放寬至 5–8 個）；加入 grep 補充片段以涵蓋跨檔案依賴

**風險 3：上下文視窗不足**
- 現象：選定檔案總和超過模型上下文視窗時被迫截斷
- 緩解：優先保留黃金檔案；對輔助檔案僅保留函式簽章與相關行；考慮使用 128K+ 視窗的模型

**風險 4：修補無法套用（patch apply failure）**
- 現象：模型產生的 diff 與當前檔案狀態不符（行號偏移、空白字元差異）
- 緩解：在提示中明確標示行號；採用 fuzzy patch 工具（如 `patch --fuzz=3`）；對 ε < 1.0 的修補自動重試一次

**風險 5：API 成本與延遲**
- 現象：兩次取樣 + 修補生成 = 至少 3 次模型呼叫，單議題成本可能偏高
- 緩解：使用較小的模型（如 GPT-5.6-mini）做檔案選擇，僅在最終修補階段使用大型模型；快取常見議題類型的檔案選擇結果

**風險 6：評估偏誤**
- 現象：SWE-rebench 議題可能與實際企業議題特性不同（議題品質、測試覆蓋率）
- 緩解：建立內部評估集，包含真實議題與測試；在部署前先在內部集上驗證

### 與其他技術的整合建議

**與 RAG 系統整合**：CQ2-CARE 並非取代檢索器，而是作為「精確檔案定位」層。在大型儲存庫中，可先用 BM25 或稠密檢索器縮小候選範圍（例如從 3000 個檔案縮至 50 個），再由 CQ2-CARE 從中精選 3–5 個檔案，兼顧效率與準確率。

**與程式碼索引工具整合**：搭配 Sourcegraph、ctags 或 LSP 伺服器，提供精確的符號定義、引用關係圖，輔助 CQ2-CARE 的 grep 補充步驟，提升跨檔案依賴的擷取品質。

**與版本控制系統整合**：在 GitHub Actions 或 GitLab CI 中部署 CQ2-CARE，當新 issue 建立時自動觸發；產生的修補以 PR 形式提交，附上自動生成的測試結果與信心度標籤。

**與 Agent 框架整合**：在 LangGraph、AutoGen 或 CrewAI 等多代理框架中，將 CQ2-CARE 作為「檔案探索代理」模組，與「測試執行代理」、「修補審查代理」協作，形成完整的自動化修復流程。

**與監控與可觀測性工具整合**：將 ρ、ε、解決率等指標匯入 Prometheus/Grafana，設定告警閾值；使用 LangSmith 或 Helicone 追蹤每次推理的提示與回應，便於除錯與回歸分析。

**與靜態分析工具整合**：在 CQ2-CARE 產出修補後，自動執行 pylint、mypy、ruff 等靜態分析，攔截型別錯誤或風格問題，減少後續審查負擔。

### 給不同背景讀者的閱讀建議

**給初學者**：本文的核心訊息簡單而反直覺：當你想讓 AI 修復程式碼 bug 時，與其用複雜的壓縮或檢索技巧，不如直接讓 AI 選出「需要修改的檔案」，然後把這些檔案完整地給它看。建議先讀 Figure 1 的範例，理解「檢索器選錯檔案」與「壓縮器改壞程式碼」兩種失敗模式，再讀第 1 節的問題陳述，即可掌握全文 80% 的重點。

**給 AI 工程師**：重點關注 §2 的 CQ2-CARE 設計（兩次取樣交集 + grep 補充）與 §4.4 的消融實驗（單次取樣 vs. 兩次取樣的差異很小，說明關鍵在於「選擇單位」而非「取樣機制」）。實作時應特別注意 ρ（黃金檔案召回率）與 ε（逐字行比例）這兩個診斷指標——它們能幫你快速定位瓶頸是「選錯檔案」還是「改壞程式碼」。建議在自己的儲存庫上重現 §3.3 的基準比較，驗證效果是否一致。

**給研究者**：本文的價值在於建立了一個「預算匹配」的公平比較框架，並將失敗模式分解為兩個可獨立控制的變因（檔案召回率 vs. 文字保真度）。後續研究方向包括：(1) 將 CQ2-CARE 擴展至多語言、多檔案複雜修改場景；(2) 探索檔案選擇與測試導向搜尋（如 SWE-Agent 的測試執行回饋）的結合；(3) 研究「選擇單位」（檔案 vs. 函式 vs. 區塊）對不同議題類型的最佳邊界。§4 的控制變因實驗設計值得借鏡。

**給產品經理**：這項研究的商業意涵是：對於「AI 自動修復程式碼」這類產品，技術選擇的優先順序應是「精確檔案選擇 > 進階壓縮/檢索」。CQ2-CARE 不需要訓練專用模型，部署成本低，且在兩個主流模型上都達到 43–47% 的解決率，已具備實用價值。建議在產品路線圖中，將「檔案選擇準確率」列為核心 KPI，並規劃人工審查閘門以處理剩餘 50%+ 的失敗案例。長期可考慮結合測試執行回饋，逐步提升自動化程度。
