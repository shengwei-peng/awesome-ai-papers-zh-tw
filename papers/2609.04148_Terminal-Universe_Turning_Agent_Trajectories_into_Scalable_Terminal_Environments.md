## ⚡ TL;DR

終端智慧體軌跡雖多，但缺乏可執行環境供後訓練使用。
Terminal-Universe 重播檔案操作、補齊依賴，從軌跡重建環境並合成跨工作區與多輪任務。
產生 37.3k 環境，Qwen3.5-27B 於單輪與多輪基準各提升 11.9 與 13.8 分。

## 摘要翻譯

隨著基於終端（terminal-based）的程式碼智慧體（code agents）日益普及，智慧體軌跡（agent trajectories）已大量累積，但真實且可執行環境（executable environments）仍然稀少。然而，環境才是智慧體後訓練真正所需：每個環境都能被重新查詢，轉化為多個可驗證任務，並提供執行回饋；相對地，軌跡僅是單一且凍結的示範。與其從頭生成環境，我們觀察到現有軌跡中的工具執行歷史（tool-execution history）揭露了其所執行環境的結構與內容，使得從軌跡本身重建這些環境成為可能。因此，我們提出 Terminal-Universe（終端宇宙），一個將每條軌跡轉化為可重複使用環境，並探索該環境以合成新任務並延續互動的框架。具體而言，Terminal-Universe 重播軌跡中記錄的檔案操作（file operations），將每個檔案還原至智慧體修改前的狀態，產生部分工作區（partial workspace）；接著由補全智慧體（completion agent）補齊遺失的檔案與相依套件（dependencies）。在此復原後的工作區上，我們同時重建原始意圖任務，並合成全新的任務。此外，我們沿廣度與深度兩個互補軸向擴充任務：在廣度方面，挖掘相關環境之間的方向性依賴關係（directional dependency relations），並合成橫跨多個程式碼庫的跨工作區查詢（cross-workspace queries），如同開發人員在真實開發中日常進行的操作；在深度方面，將最初的單輪查詢擴展為多輪會話（multi-round session），透過使用者智慧體（user agent）捕捉迭代的使用者回饋與需求細化。應用於公開的終端程式碼智慧體軌跡，Terminal-Universe 產生了 37.3k 個任務完備的環境。在此語料庫上對 Qwen3.5-27B 執行監督式微調（supervised fine-tuning），使 Terminal-Bench 2.1 的單輪效能提升 11.9 分，並使 EvoCode-Bench v2 MT@4 的多輪效能提升 13.8 分。

### 核心貢獻（3～5點）
- 提出 Terminal-Universe 框架，能從現有智慧體軌跡重建可重複使用的可執行環境，解決後訓練資料中環境稀缺的問題。
- 設計兩階段重建流程：先以確定性重播（deterministic replay）還原檔案操作產生部分工作區，再由補全智慧體補齊遺失檔案與相依套件。
- 在復原環境上同時重建原始意圖任務，並合成全新任務，實現任務條件式合成（task-conditioned synthesis）與資料擴增。
- 沿廣度與深度擴充任務：廣度上挖掘方向性依賴關係以產生跨工作區查詢；深度上將單輪查詢延伸為多輪會話，捕捉迭代回饋與需求細化。
- 實證規模與效益：從公開軌跡產出 37.3k 個任務完備環境，並以監督式微調顯著提升 Qwen3.5-27B 在 Terminal-Bench 2.1 與 EvoCode-Bench v2 MT@4 上的單輪與多輪效能。

### 適合對象
本論文適合對終端程式碼智慧體、後訓練資料合成、可執行環境重建，以及多輪程式碼互動有興趣的研究人員與工程師；特別是關注如何從既有軌跡中規模化生成高品質訓練環境與可驗證任務的讀者。

## 深度分析

#### 方法論解析

Terminal-Universe（終端宇宙）的核心洞察是 **trajectory–environment duality（軌跡–環境對偶性）**：傳統上，我們從一個 executable environment（可執行環境）中 roll out（展開）出一條 agent trajectory（智慧體軌跡），而本文則反轉這個映射，把現有軌跡還原成可重複使用的環境。整個流程可分為兩大階段：**environment reconstruction（環境重建）** 與 **re-query methods（重新查詢方法）**。

##### 1. Environment Reconstruction（環境重建）

重建分為兩個子階段：

- **Deterministic replay（確定性重播）**：  
  軌跡中記錄的 file operations（檔案操作），例如 `Read`、`Write`、`Edit` 等 tool-execution history（工具執行歷史），實際上已經暴露了當時工作區的內容與結構。Terminal-Universe 會把這些操作依序重播，但刻意把 agent 自己做的修改「回滾」，讓每個檔案恢復到「被 agent 修改之前」的狀態。這樣得到的是一個 **partial workspace（部分工作區）**，也就是尚未被解決的初始狀態。

- **Agentic completion（智慧體式補全）**：  
  重播後的工作區通常不完整，可能缺少某些檔案、相依套件或設定。此時由一個 **completion agent（補全智慧體）** 自動補齊 missing files（遺失檔案）與 dependencies（相依套件 / 依賴項）。關鍵在於這個補全過程不能洩漏原始解答，否則新任務就失去意義。補全完成後，便得到一個 **executable workspace（可執行工作區）**。

這個做法的優勢在於不需要原始 repository（儲存庫），也不需要從零生成環境，而是直接從既有軌跡中「提煉」出真實專案的結構與狀態。

##### 2. Re-query Methods（重新查詢方法）

得到可執行環境後，Terminal-Universe 進一步把每個環境轉換成多種訓練任務，並沿兩個互補軸向擴展：

- **單一工作區（single-WS）任務**：  
  除了重建原始 intent query（意圖查詢）外，還會 synthesize（合成）全新的查詢，讓同一個環境可以被反覆用於不同任務。

- **廣度擴展（Breadth Expansion）— Cross-WS（跨工作區）**：  
  透過挖掘不同環境之間的 **directional dependency relations（方向性依賴關係）**，合成 **cross-workspace queries（跨工作區查詢）**。這類任務橫跨多個 codebases（程式碼庫），例如閱讀 reference implementation（參考實作）、把功能從 A 專案搬到 B 專案、或串接兩個元件。這更貼近真實軟體開發中開發者同時操作多個專案的情境。

- **深度擴展（Depth Expansion）— Multi-Round（多輪會話）**：  
  把原本 single-turn（單輪）的查詢延伸成 **multi-round session（多輪會話）**。在 agent 完成初始查詢後，一個 **user agent（使用者智慧體）** 會根據工作區的變化提出 grounded follow-ups（有根據的後續問題），例如追加新需求，或在某一輪失敗時根據錯誤訊息要求修正。每一輪都會經過驗證，結果再以自然語言形式回饋給 agent。

##### 3. Verification（驗證）

每個新產生的任務都會配上一個由容器內 agent 撰寫的 **verifier（驗證器）**。只有所有測試都通過的 trajectories 才會被保留，確保訓練資料的品質與可驗證性。

#### 實驗數據解讀

##### 規模數據

應用於公開的 terminal agent trajectories 上，Terminal-Universe 產生了：

- **37.3k task-sufficient environments（任務充足環境）**
- **32.0k 個經過驗證的任務 / 訓練實例**

與 Table 1 中的其他方法相比，Terminal-Universe 在環境數量上與 RST（37.5k）相當，但額外支援 Multi-Round（多輪）與 Cross-WS（跨工作區）兩種擴展，這是其他方法所不具備的。

##### 微調成效

作者使用 Qwen3.7-Max 作為 teacher model（教師模型）在每個任務上 roll out 解答軌跡，再以這些資料對 **Qwen3.5-27B** 進行 **supervised fine-tuning（監督式微調，SFT）**。結果顯示：

- 在單輪基準 **Terminal-Bench 2.1** 上，相較於相同 base model，效能提升 **+11.9 points**。
- 在多輪基準 **EvoCode-Bench v2 MT@4** 上，效能提升 **+13.8 points**。

這兩個數字具有幾層意義：

1. **環境比軌跡更有訓練價值**：Ablations 明確指出，在重建後的環境中重新求解（re-solving），遠優於直接模仿原始 raw trajectories（原始軌跡）。這呼應了本文的核心論點—environment 才是值得規模化的資源。
2. **多輪訓練帶來顯著增益**：MT@4 提升 13.8 分，顯示 multi-round session 確實能增強 agent 處理迭代式使用者回饋與需求細化的能力。
3. **跨工作區與單工作區互補**：雖然摘要未單獨列出 cross-WS 的獨立分數，但整體效能提升暗示 breadth 與 depth 兩種擴展都對模型泛化有貢獻。

##### 限制與解讀注意事項

- 實驗僅針對 Qwen 系列模型，對其他模型族（如 Llama、GPT 等）的通用性尚需更多驗證。
- 基準測試分數的提升雖顯著，但並未完整呈現在不同難度、不同領域任務上的細部分布，因此難以判斷增益是否均勻。
- 驗證器由 agent 自動生成，雖然有「全測試通過」的門檻，但仍可能存在測試覆蓋率不足或驗證器本身有偏誤的風險。

#### 與現有研究的比較

Table 1 清楚呈現了 Terminal-Universe 與先前研究的定位差異：

| 方法類型 | 代表工作 | 主要機制 | 優點 | 缺點 |
|---|---|---|---|---|
| **Repository-based methods（基於儲存庫的方法）** | Pan et al., 2024; Jain et al., 2025 | 從 Git history 回滾到修復前的狀態 | 真實、可驗證 | 受限於既有 bug 與儲存庫歷史 |
| **Perturbation methods（擾動方法）** | Yang et al., 2025; Lin et al., 2026 | 在通過測試的儲存庫中注入 bug | 可從少數儲存庫產生大量任務 | 任務類型單一（多為修復任務） |
| **Task-conditioned synthesis（任務條件式合成）** | Gandhi et al., 2026; Ivison et al., 2026; Hua et al., 2026; Fan et al., 2026 | 從頭生成任務與環境 | 可控、覆蓋面廣 | 環境與真實專案脫鉤，常過於小型與整潔 |
| **Trajectory reconstruction（軌跡重建）** | **Terminal-Universe（本文）** | 從既有軌跡還原環境 | 無需原始儲存庫、真實專案結構、支援多輪與跨工作區 | 依賴軌跡品質、補全可能失敗或洩漏答案 |

##### 主要改進

1. **重新定義 trajectories 的價值**：過去 trajectories 多半被視為模仿學習的資料來源，本文將其視為環境的「觀測紀錄」，開啟了從軌跡到環境的逆向工程。
2. **支援 Multi-Round 與 Cross-WS**：現有方法幾乎都聚焦於 single-WS、single-turn 任務，Terminal-Universe 是少數同時在廣度與深度上擴展任務合成的方法。
3. **可驗證性**：每個任務都配備 agent-authored verifier，並以全測試通過作為篩選條件，確保訓練資料不是「看起來合理」而是「可執行且正確」。

##### 局限性

- **軌跡品質依賴**：若原始軌跡來自較弱的 policy model（策略模型），其工具執行歷史可能不完整或錯誤，進而影響重建品質。
- **補全智慧體的風險**：completion agent 可能無法正確補齊複雜 dependencies，或在補全過程中無意間引入解答資訊。
- **跨工作區依賴關係的準確性**：directional dependency relations 的挖掘若出錯，會產生不合理或過於困難的 cross-workspace queries。
- **任務類型仍受限於 terminal 場景**：目前方法針對 terminal-based code agents，對於 GUI、IDE 插件或其他互動形式的軌跡是否適用，仍待研究。

#### 未來研究方向

1. **擴展至非終端場景**：  
   將 trajectory reconstruction 的想法應用到 GUI-based agents、IDE 外掛、或網頁操作軌跡，探索更廣泛的「觀測紀錄→可執行環境」映射。

2. **更精準的 dependency graph（依賴圖）挖掘**：  
   目前 cross-workspace queries 仰賴 direction dependency relations，未來可結合靜態分析、動態執行追蹤、或程式語意模型，建立更可靠的跨專案依賴圖。

3. **人機協作驗證**：  
   雖然 agent-authored verifier 已能篩選大部分錯誤，但對於複雜任務，可引入 human-in-the-loop（人類在迴路）或 CI/CD 整合，進一步提升驗證品質。

4. **課程式學習（Curriculum Learning）與難度控制**：  
   根據環境複雜度、任務難度、與多輪互動長度設計訓練課程，讓模型從簡單 single-WS 任務逐步學習到複雜 cross-WS、multi-round 任務。

5. **結合更強大的 base model 與 RL**：  
   目前使用 SFT，未來可嘗試 reinforcement learning（強化學習，RL）或 DPO（Direct Preference Optimization），讓模型從 verifier 回饋中進一步優化。

6. **多語言與跨領域擴展**：  
   目前聚焦於程式碼任務，未來可探索是否適用於資料科學、系統管理、DevOps 等不同領域，以及多語言程式碼庫的處理。

7. **動態環境與長期互動**：  
   真實開發往往不是一次性任務，而是持續數小時甚至數天的迭代。未來可研究如何從長期軌跡中重建「動態演化的環境」，並生成對應的長期多輪任務。

## 論文問答

**Q1：Terminal-Universe 主要想解決什麼問題？**

A：Terminal-Universe 旨在解決基於終端端的程式碼智慧體在後訓練階段缺乏真實可執行環境的問題。雖然智慧體軌跡已經大規模累積，但這些軌跡只是單次、固定的示範，無法重複驗證或提升難度。相較之下，可執行環境可以讓更強的模型重新解題、透過測試驗證結果，並在同一工作區上設計更困難的任務，因此是更值得規模化的訓練資源。

**Q2：現有方法為何難以規模化地產生可執行環境？**

A：現有方法主要分為三類，但各有局限：基於儲存庫的方法依賴 Git 歷史與大量人工整理，擾動方法只能產生修復類任務且受限於原始程式庫，而任務條件式合成則容易產出脫離真實專案的小型整齊工作區。這些方法要不是從既有環境出發，就是從頭同時生成任務與環境，未能善用已經存在的軌跡資源。更重要的是，它們忽略了軌跡中工具執行歷史所蘊含的環境結構與內容資訊。

**Q3：為什麼環境比軌跡更適合做為後訓練資源？**

A：軌跡的品質受限于產生它的策略模型，而且我們無法檢查其中對程式碼的修改是否真正正確。環境則沒有這些限制，因為同樣的任務可以由更強的模型重新求解，結果也能透過驗證器確認，甚至可以在同一工作區上設計更難的任務。因此，對於後訓練來說，可重複查詢與驗證的環境才是應該被規模化的核心資源。

**Q4：Terminal-Universe 的核心方法是什麼？**

A：Terminal-Universe 透過「確定性重播」與「智慧體式補全」兩個階段，將每條軌跡轉換為可重複使用的環境。首先，系統重播軌跡中記錄的檔案操作，把每個檔案還原到智慧體修改之前的狀態，並保留智慧體的編輯不洩漏，形成一個部分工作區。接著，補全智慧體會自動補齊缺失的檔案與相依套件，但不會洩漏正確解答，最終產生可執行的完整工作區。

**Q5：Terminal-Universe 的關鍵創新是什麼？**

A：關鍵創新在於提出「軌跡–環境對偶性」，將記錄下來的智慧體軌跡重新視為可執行環境的來源。過去的研究通常是從環境中產出軌跡，而 Terminal-Universe 反轉這個對應關係，從軌跡中還原環境。這種方法無需從頭建構環境，也無需取得原始儲存庫，就能大規模產出真實且可驗證的訓練環境。

**Q6：Terminal-Universe 有哪些重要的設計選擇？**

A：重要設計包括保留智慧體的修改不洩漏，使工作區處於未解決狀態；使用補全智慧體在不洩漏解答的前提下補齊缺失內容；以及為每個新任務配備由智慧體撰寫的驗證器，並只保留所有測試都通過的軌跡。此外，框架沿著廣度與深度兩個互補軸擴展任務：廣度透過跨工作區查詢橫跨多個程式碼庫，深度則透過多輪會話模擬迭代使用者回饋。

**Q7：論文使用了哪些評測基準？**

A：實驗使用 Terminal-Bench 2.1 評估單輪任務表現，並使用 EvoCode-Bench v2 的 MT@4 指標評估多輪任務表現。這兩個基準都提供可執行的驗證環境，能夠檢驗智慧體產出的程式碼是否正確。研究團隊在產出的語料庫上對 Qwen3.5-27B 進行監督式微調，以驗證方法的有效性。

**Q8：Terminal-Universe 取得了哪些關鍵實驗結果？**

A：在 Qwen3.5-27B 上的監督式微調結果顯示，Terminal-Bench 2.1 提升了 11.9 分，EvoCode-Bench v2 MT@4 提升了 13.8 分。整個流程從公開的智慧體軌跡中產出了 3.73 萬個任務充分的環境，以及 3.2 萬個新任務。這些結果證明，從軌跡重建的環境確實能有效提升終端程式碼智慧體的後訓練表現。

**Q9：論文進行了哪些消融實驗？**

A：消融實驗確認了每個元件都對整體表現有貢獻，其中最重要的是證明「在重建環境中重新求解」遠優於「直接模仿原始軌跡」。這顯示環境的價值不僅在於保存原始任務，更在於讓更強的模型能夠產出經過驗證的解答。相較於複製可能包含錯誤的固定示範，重新求解能顯著提升訓練資料的品質與多樣性。

**Q10：Terminal-Universe 可應用於哪些實際場景？**

A：Terminal-Universe 可支援真實軟體開發中的多種情境，例如閱讀參考實作、將功能從一個專案搬移到另一個專案，或串接不同程式碼庫中的元件。透過跨工作區查詢，它能模擬開發者日常處理多個相依程式庫的複雜流程。此外，多輪會話機制也能模擬使用者逐步提出回饋與需求細化的迭代開發過程。

**Q11：在產品化過程中需要考慮哪些問題？**

A：產品化時必須確保補全智慧體不會意外洩漏正確解答，同時維持驗證器的高品質與覆蓋率。由於重播後通常只得到部分工作區，系統需要穩健地處理缺失檔案與相依套件的補全問題。此外，如何將流程擴展到不同來源與品質的軌跡資料，也是部署到實際訓練管線時的重要考量。

**Q12：Terminal-Universe 可能對研究領域帶來什麼影響？**

A：Terminal-Universe 可能改變學界對智慧體軌跡的看法，從單純的訓練示範轉變為可重複使用的環境來源。它有助於減少對人工整理環境的依賴，並為終端程式碼智慧體的大規模後訓練提供新途徑。其在廣度與深度上的任務擴展方式，也可能成為未來真實情境任務合成的新標竿。

**Q13：論文承認了哪些限制？**

A：論文指出，確定性重播通常只能得到部分工作區，因此必須依賴智慧體式補全，而這可能引入錯誤或不一致。重建環境的品質取決於軌跡中工具執行歷史的完整性與正確性，若軌跡記錄不足則難以還原。此外，整個流程仰賴夠強的補全智慧體與教師模型，這在資源受限的情境下可能構成挑戰。

**Q14：Terminal-Universe 可能出現哪些失敗案例？**

A：當軌跡缺乏足夠的檔案操作記錄時，系統可能無法正確重建原始工作區；若補全智慧體未能補齊關鍵相依套件，則環境可能無法執行。跨工作區任務可能因錯誤識別方向性依賴關係而失敗，而多輪會話則可能因使用者智慧體產生不切實際的後續問題而偏離主題。此外，由智慧體撰寫的驗證器若存在漏洞，也可能導致錯誤解答被誤判為通過。

**Q15：未來可以朝哪些方向延伸？**

A：未來可以將此方法擴展到非終端型的智慧體軌跡，例如網頁操作或機器人控制領域。另一個方向是提升補全智慧體的穩健性，並在重建流程中引入人類回饋機制。此外，針對特定領域的私有軌跡進行規模化應用，以及自動發掘更豐富的跨環境依賴關係，也都是值得探索的研究方向。

## 實務應用指南

## 適用場景

1. **大規模終端程式碼智慧體的後訓練資料擴充**  
   當企業已累積大量智慧體軌跡，卻缺乏可驗證、可重複執行的訓練環境時，可將這些軌跡轉換為可重複使用的可執行環境，並從中生成新任務與對應驗證器，快速擴充監督式微調（SFT）語料。

2. **跨程式碼庫的複雜開發任務合成**  
   適用於需要模擬真實開發者行為的場景，例如參考實作移植、跨專案功能搬遷、元件串接等。透過挖掘方向性依賴關係，可合成橫越多個工作區（cross-WS）的查詢任務，提升模型處理真實多庫協作的能力。

3. **多輪互動式程式設計助理的訓練與評測**  
   對話式程式設計工具需要模型理解迭代使用者回饋與需求精煉。Terminal-Universe 可將單輪任務延伸為多輪會話，由使用者智慧體（user agent）根據工作區變化提出接續問題，適合用於訓練與評測多輪程式碼助理。

4. **現有基準測試的環境重建與難度提升**  
   對於 Terminal-Bench、EvoCode-Bench 等基準，可利用軌跡重建原始工作區，並透過重新查詢（re-query）產生更困難或更多樣的任務變體，進一步推動模型能力邊界。

5. **內部開發知識的結構化與再利用**  
   企業內部智慧體在處理專案時產生的軌跡，可轉為可執行的部分工作區與相依環境，協助新進開發者重現問題起點，或作為自動化測試與教學案例的素材。

## 實作前置條件

**資料條件**
- 大量終端程式碼智慧體軌跡，需包含完整的工具執行歷史，尤其是 `Read`、`Write`、`Edit` 等檔案操作記錄。
- 軌跡應具備足夠的上下文資訊，例如原始指令、執行結果、容器或系統環境描述，以便重建部分工作區（partial workspace）。
- 建議軌跡來源多樣，涵蓋不同程式語言、框架與任務類型，以提升重建環境的覆蓋率。

**運算條件**
- 具備執行隔離容器（container）的運算叢集，用於重播檔案操作、執行補全智慧體（completion agent）與驗證器。
- 足夠的 GPU/CPU 資源供教師模型（如 Qwen3.7-Max）進行軌跡重解（re-solve）與新任務生成。
- 可擴展的儲存空間，用於保存 37k 等級的重建環境、測試檔案與生成軌跡。

**技術與人力條件**
- 熟悉容器化技術（Docker/Podman）與終端智慧體框架。
- 具備設計與維護驗證器（verifier）的能力，能判斷測試通過與否。
- 至少一名熟悉大型語言模型微調流程的工程師，負責資料篩選、SFT 訓練與效果評測。

## 實作步驟建議

1. **軌跡收集與前處理**  
   蒐集內部或公開的終端智慧體軌跡，清理無效或過短的記錄，並標準化工具呼叫格式，確保 `Read`、`Write`、`Edit` 等操作可被解析。

2. **確定性重播（Deterministic Replay）**  
   依序重播軌跡中的檔案操作，將每個檔案還原至智慧體修改前的狀態，保留未修改的檔案與目錄結構，形成部分工作區。

3. **智慧體式補全（Agentic Completion）**  
   部署補全智慧體，根據重播後的工作區內容與任務需求，自動補齊遺失檔案、相依套件與環境設定，但避免洩漏原始解答。

4. **任務重建與重新查詢**  
   在恢復的工作區上，一方面重建原始意圖查詢，另一方面利用重新查詢方法生成全新任務，包括單一工作區（single-WS）、跨工作區（cross-WS）與多輪（multi-round）變體。

5. **驗證與篩選**  
   為每個新任務由智慧體在容器內撰寫驗證器，執行測試並只保留所有測試通過的軌跡，確保訓練資料品質。

6. **教師模型重解與微調**  
   使用較強的教師模型（如 Qwen3.7-Max）對每個任務重新求解，產生高品質解題軌跡，再用於監督式微調目標模型（如 Qwen3.5-27B）。

7. **持續評測與迭代**  
   在 Terminal-Bench 2.1、EvoCode-Bench v2 等基準上評測模型表現，分析失敗案例，並將新的優質軌跡回流至重建流程，形成資料飛輪。

## 潛在風險與注意事項

- **重播不完整導致環境缺漏**  
  若原始軌跡未記錄所有檔案操作，重播後可能遺失關鍵檔案。建議結合補全智慧體與人工抽樣檢查，確認工作區可執行且任務可解。

- **補全過程洩漏解答**  
  補全智慧體可能意外寫入與解答相關的程式碼。應明確限制其提示詞，禁止生成任務目標相關的實作，並透過驗證器檢查初始狀態是否為「未解決」。

- **驗證器品質不穩定**  
  由智慧體自動生成的驗證器可能過於寬鬆或嚴格。需設計自動化檢核機制，例如對同一任務使用多組驗證器交叉驗證，並定期人工審查邊界案例。

- **跨工作區任務過於複雜**  
  cross-WS 任務若涉及過多程式碼庫，可能超出模型處理能力。建議從小型、明確的依賴關係開始，逐步增加難度。

- **多輪會話偏離主題**  
  user agent 生成的接續問題可能與原始任務脫節。應讓 user agent 根據工作區實際變化與驗證結果產生回饋，並設定每輪目標一致性檢查。

- **資料安全與授權問題**  
  使用內部軌跡時，需注意程式碼授權、敏感資訊與隱私保護。重建環境應在隔離容器中執行，避免外洩原始專案機密。

## 與其他技術的整合建議

- **與現有 Git 儲存庫流程結合**  
  可將重建後的工作區與企業內部 Git 儲存庫對接，把通過驗證的環境與任務納入版本控制，作為持續整合（CI）測試案例或新人訓練素材。

- **與資料選擇與去重工具整合**  
  搭配語意去重、難度分級與多樣性採樣工具，避免訓練資料過度重複，並優先選擇對模型能力提升最大的任務變體。

- **與 RLHF / DPO 流程銜接**  
  重建環境與驗證器不僅可用於 SFT，也可作為強化學習或偏好最佳化的獎勵訊號來源，進一步提升模型在真實終端任務上的穩定性。

- **與企業知識庫整合**  
  將重建環境的元資料（語言、框架、任務類型、依賴關係）匯入向量資料庫，支援檢索增強生成（RAG），讓智慧體在面對新任務時能參考相似歷史案例。

- **與模型評測平台整合**  
  將 Terminal-Universe 產生的環境與驗證器匯入內部評測平台，定期對不同模型版本進行回歸測試，追蹤單輪與多輪能力變化。

## 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於「軌跡–環境對偶性」這個核心概念：軌跡不只是智慧體做過什麼的紀錄，還能反過來還原出它當時運作的環境。理解這一點後，再閱讀確定性重播與補全智慧體的兩階段流程，並透過圖 1 掌握整體架構。技術細節如驗證器生成與多輪會話設計可暫時略讀。

**AI 工程師**  
請重點關注環境重建的實作細節，包括如何從工具執行歷史中還原檔案、如何設計補全智慧體的提示詞以避免洩漏解答，以及如何建立可靠的驗證器篩選機制。實驗章節的消融結果也值得參考，特別是「在重建環境中重新求解遠優於直接模仿原始軌跡」這一發現。

**研究人員**  
本文的貢獻在於將軌跡重新定義為可規模化環境的來源，並提出廣度（cross-WS）與深度（multi-round）兩個互補的擴展軸。建議深入分析重新查詢方法的設計動機、方向性依賴關係的挖掘方式，以及這些方法對後訓練資料品質與模型泛化能力的影響。

**產品經理**  
請將本文視為一種「把既有資產（軌跡）轉化為可驗證訓練資料」的解決方案。重點評估它如何幫助團隊降低手動建構環境的成本、提升模型在真實終端任務上的表現，以及是否適合與現有 CI/CD、知識庫或模型評測流程整合。實驗結果顯示在兩大基準上均有顯著提升，可作為推動內部試點的依據。
