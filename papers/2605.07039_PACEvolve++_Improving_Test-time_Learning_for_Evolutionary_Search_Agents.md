## ⚡ TL;DR

現有演化搜尋代理仰賴固定的提示式策略，無法在測試時適應任務特定的搜尋動態。
本文提出PACEvolve++，以可訓練顧問模型負責假設生成與選擇，並搭配階段自適應強化學習。
實驗顯示其在負載平衡、序列推薦與蛋白質適應度任務上超越現有方法並加速收斂。

## 摘要翻譯

大型語言模型（Large Language Models, LLMs）已成為演化式搜尋（Evolutionary Search）的驅動力，但多數系統仰賴固定的提示引出式推理策略（Prompt-Elicited Reasoning Policy）來採樣下一組候選。這限制了其在實際工程與研究任務中的適應性——此類任務的評估成本高昂，且進展仰賴學習任務特定的搜尋動態（Search Dynamics）。我們提出 PACEvolve++，一個用於演化式搜尋代理中測試時策略適應（Test-Time Policy Adaptation）的顧問模型強化學習（Advisor-Model Reinforcement Learning）框架。PACEvolve++ 將策略性搜尋決策與實作解耦：可訓練的顧問模型（Advisor Model）負責生成、評估並選擇假設（Hypotheses），而更強大的前沿模型（Frontier Model）則將所選假設轉換為可執行的候選。為了在非平穩回饋（Non-Stationary Feedback）下訓練顧問，我們提出一種階段自適應方法（Phase-Adaptive Approach），使其能根據演化過程的不同階段調整最佳化策略。在演化初期，該方法採用群組相對回饋（Group-Relative Feedback）以學習廣泛的搜尋偏好；隨著獎勵差距（Reward Gaps）逐漸收窄，後期則強調 k 選最佳前沿貢獻（Best-of-k Frontier Contribution）以支援穩定精煉（Stable Refinement）。在專家並行負載平衡（Expert-Parallel Load Balancing）、序列推薦（Sequential Recommendation）以及蛋白質適應度外推（Protein Fitness Extrapolation）等任務上，PACEvolve++ 優於使用前沿模型的最先進（State-of-the-Art, SOTA）演化式搜尋框架，實現更快的收斂（Convergence），並在演化式搜尋過程中穩定測試時訓練（Test-Time Training）。

### 核心貢獻（3～5點）
- **提出 PACEvolve++ 框架**：將策略性搜尋決策與候選實作解耦，由可訓練的顧問模型（Advisor Model）負責生成、評估與選擇假設（Hypotheses），並由前沿模型（Frontier Model）將所選假設轉化為可執行程式碼，使兩者得以各自優化。
- **提出階段自適應方法（Phase-Adaptive Approach）**：在演化初期使用群組相對回饋（Group-Relative Feedback）學習廣泛的搜尋偏好；於獎勵差距（Reward Gaps）收斂後切換為 k 選最佳前沿貢獻（Best-of-k Frontier Contribution）以支援穩定精煉（Stable Refinement），有效因應非平穩回饋（Non-Stationary Feedback）下的訓練挑戰。
- **跨領域實證優於現有 SOTA**：在專家並行負載平衡（Expert-Parallel Load Balancing）、序列推薦（Sequential Recommendation）與蛋白質適應度外推（Protein Fitness Extrapolation）三項異質任務上，PACEvolve++ 均超越以前沿模型為基礎的最先進演化式搜尋框架，展現更快收斂（Convergence）並穩定測試時訓練（Test-Time Training）。

### 適合對象
從事大型語言模型（LLM）驅動之自動化演算法發現（Algorithm Discovery）、神經演化搜尋、測試時學習（Test-Time Learning）／測試時訓練（Test-Time Training）、強化學習（RL）應用於程式合成，以及推薦系統、蛋白質工程、高效能運算（如混合專家模型 MoE 之負載平衡）等領域的研究者與工程師；亦適合關注 AI 代理（Agent）自我調適工作流程（Self-Adaptive Workflows）與長程搜尋（Long-Horizon Search）策略的學術與產業界讀者。

## 深度分析

#### 方法論解析

PACEvolve++ 的核心方法論建立在兩個關鍵設計之上：**顧問模型（Advisor Model）範式**與**階段自適應強化學習（Phase-Adaptive RL）演算法**。這兩個設計共同解決了演化式搜尋代理在測試時策略適應上的根本難題。

##### 1. 顧問模型範式：策略與實作解耦

傳統的演化式程式搜尋框架（如 AlphaEvolve、FunSearch、PACEvolve）通常採用單一模型同時負責「決策」與「實作」：同一個 LLM 既要判斷「下一步該嘗試什麼方向」，又要負責將該方向轉化為可執行的程式碼。PACEvolve++ 主張這種耦合在實際研究與工程任務中是次優的，原因在於：

- **搜尋信號與實作信號的混淆**：在複雜程式庫、整合細節與系統限制下，實作失敗可能源於程式碼錯誤而非假設本身不佳。端到端訓練會將假設品質與實作正確性糾纏在一起，產生對搜尋偏好適應而言過於雜訊的訊號。
- **搜尋決策的特殊性**：在推薦系統設計、MoE 負載平衡、蛋白質適應度外推等任務中，搜尋方向涵蓋架構變更、最佳化選擇、路由策略、特徵交互、序列層級轉換等多元範疇。能產生可測量改進的方向往往只佔少數，需要模型內化對「哪些突變族系反覆失敗、哪些部分改進值得重訪、哪些方向相對於演化前沿仍具新穎性」的判斷。

基於此，PACEvolve++ 將演化搜尋拆解為兩個角色：

| 角色 | 功能 | 訓練狀態 |
|------|------|----------|
| **顧問模型（Advisor）** | 構想生成、新穎性評估、假設選擇 | 可訓練 |
| **前沿實作模型（Frontier Implementation Model）** | 將選定假設轉化為可執行程式碼 | 凍結 |

顧問模型專注於學習「要評估什麼」，而前沿模型負責「如何實作」。這種解耦使得強化學習的信用分配（Credit Assignment）能夠聚焦於搜尋決策本身，而非被實作雜訊稀釋。

##### 2. 階段自適應強化學習：對齊演化動態

演化搜尋的回饋結構具有顯著的**非平穩性（Non-Stationarity）**：早期候選之間在機制與品質上差異巨大；晚期則是在已強後代上進行微調，候選間差異趨於邊際。PACEvolve++ 據此提出兩階段信用分配策略：

**早期探索階段（Group-Relative Feedback）**
- 使用群組相對回饋：在一個 rollout 批次內，根據候選相對於群組平均的表現來計算優勢。
- 目的：鼓勵探索多元搜尋方向，避免過早收斂到少數高分配銷出。
- 直覺：當候選品質差異大時，絕對分數的雜訊高，但相對排序能提供穩定的「哪些突變族系有希望」訊號。

**晚期精煉階段（Best-of-k Frontier Contribution）**
- 切換至前沿貢獻回饋：信用不再基於「此 rollout 是否為群組最高分」，而是「此候選是否對演化中的 k 選最佳前沿（Best-of-k Frontier）產生貢獻」。
- 目的：在獎勵差距（Reward Gaps）壓縮時，避免群組相對訊號失效，轉而獎勵真正推動前沿改進的精煉動作。
- 直覺：當所有候選分數都很接近時，模仿最高分配銷出並無意義；真正有價值的是「此候選是否進入了前沿集合」。

**理論保證（Theorem 1）**
論文宣稱此階段自適應配方對齊了演化搜尋動態的「對數遞減獎勵結構」，能穩定晚期訓練同時避免早期過度利用。這暗示該方法在數學上具有收斂性或穩定性邊界，使其不僅是經驗技巧，而是有理論支撐的設計選擇。

##### 3. 整體工作流程

從圖 1 可看出，PACEvolve++ 的 rollout 流程為：
1. 顧問模型根據當前最佳程式、評估指標與搜尋歷史生成多個假設。
2. 顧問模型對假設進行新穎性評估與篩選。
3. 選定假設由前沿實作模型轉化為可執行程式碼。
4. 評估器給出評估指標。
5. 根據當前搜尋階段，選擇對應的信用分配策略更新顧問模型參數。

此設計將 RL 目標與 rollout 批次耦合，並使信用分配自適應於搜尋階段，從而實現測試時訓練的穩定化。

#### 實驗數據解讀

論文在三個截然不同的真實世界任務上驗證 PACEvolve++，這些任務覆蓋了工程最佳化、機器學習系統設計與生物序列設計三大領域：

##### 1. 專家並行負載平衡（Expert-Parallel Load Balancing）

此任務屬於 MoE（混合專家模型）系統中的關鍵工程問題：在專家並行架構下，如何平衡各 GPU 裝置上的專家計算負載。實驗意義在於：
- **任務特性**：評估昂貴（需實際部署與 profiling）、候選方向涵蓋路由策略、負載預測、token 分配等。
- **預期結果**：PACEvolve++ 應展現更快收斂，因為顧問模型能學會避開反覆失敗的負載平衡策略族系。

##### 2. 序列推薦（Sequential Recommendation）

此任務涉及推薦系統中的序列建模，候選方向包含架構變更（如注意力機制變體）、特徵交互設計、損失函數選擇等。
- **任務特性**：評估涉及完整訓練流程，耗時長；改進空間細微但可測量。
- **預期結果**：階段自適應機制應在晚期精煉階段發揮作用，因為此時候選間品質差距已壓縮。

##### 3. 蛋白質適應度外推（Protein Fitness Extrapolation）

此任務要求從已知突變數據外推未見突變的適應度，候選方向包含序列層級轉換、特徵工程、模型架構選擇。
- **任務特性**：資料稀疏、評估基於與實驗值的相關性；屬於開放式生物設計問題。
- **預期結果**：顧問模型應學會優先探索「結構合理且可能提升適應度」的序列變換方向。

##### 關鍵實驗結論

根據摘要與引言的描述，PACEvolve++ 在三項任務上均：
- **超越 SOTA 演化搜尋框架**（含使用前沿模型者）。
- **收斂更快**：這直接歸因於顧問模型內化了搜尋偏好，避免重複試錯。
- **穩定測試時訓練**：這是階段自適應機制的核心收益——傳統 RL 在演化搜尋中常因獎勵差距壓縮而崩潰，PACEvolve++ 透過前沿貢獻回饋緩解此問題。

#### 與現有研究的比較

##### 定位

PACEvolve++ 屬於「**測試時學習（Test-Time Learning）**」與「**LLM 驅動的演化搜尋**」兩條研究線的交會點，並明確承接其前身 PACEvolve 的工作。

##### 與 PACEvolve 的比較

PACEvolve 透過階層式上下文管理、動量式回溯、島嶼式協作與持久構想池改善了長程搜尋的外部機制，但**仍依賴固定的提示引出式推理策略（Prompt-Elicited Reasoning Policy）**。PACEvolve++ 的核心進步在於：
- 將搜尋經驗從「上下文」內化為「模型參數」。
- 透過顧問模型範式使策略適應變得可行（避免實作雜訊干擾）。
- 透過階段自適應 RL 使訓練在非平穩回饋下穩定。

##### 與 AlphaEvolve / FunSearch 的比較

AlphaEvolve 與 FunSearch 展示了強大的演算法發現能力（箱型裝箱、矩陣乘法、圓形裝箱等），但同樣使用固定策略。PACEvolve++ 的差異化在於：
- **可訓練的決策層**：這是質的差異，而非僅量的改進。
- **任務範疇**：AlphaEvolve 偏向經典演算法發現，PACEvolve++ 偏向現代 ML 系統與生物序列設計。

##### 與其他測試時訓練方法的比較

近期測試時訓練工作（如 TTT、Test-Time RL）多聚焦於單一模型的自適應。PACEvolve++ 的獨特之處在於：
- **雙模型分工**：顧問 + 前沿實作，這在概念上類似 Mixture-of-Experts，但用於搜尋而非推理。
- **階段感知信用分配**：這比固定 RL 配方更貼合演化搜尋的實際動態。

##### 限制與未明示的權衡

- **顧問模型的訓練成本**：雖然評估昂貴，但訓練顧問模型本身需要大量 rollout，這在實務上可能成為瓶頸。
- **對前沿實作模型的依賴**：若前沿模型無法正確實作某些假設，顧問模型的學習訊號仍會被污染——只是程度低於端到端訓練。
- **階段切換的啟發式**：何時從群組相對切換到前沿貢獻？論文未詳細說明切換準則，這可能影響實際部署的穩健性。
- **理論保證的強度**：Theorem 1 提供穩定性邊界，但實際收斂速度與最優性仍依賴經驗設定。

#### 未來研究方向

PACEvolve++ 開啟了多條值得探索的研究路徑：

##### 1. 顧問模型的規模化與蒸餾

- **小模型顧問**：當前顧問模型可能與前沿模型規模相當，未來可探索將搜尋策略蒸餾到更小的模型，降低測試時訓練成本。
- **多任務顧問**：是否可訓練一個跨任務的通用顧問模型，使其在 MoE 負載平衡上學到的「避免重複失敗」策略遷移到推薦系統？

##### 2. 階段自適應機制的理論深化

- **自適應階段切換**：當前階段切換可能依賴啟發式（如獎勵差距閾值），未來可探索基於變化點偵測（Change-Point Detection）或線上學習的自動切換。
- **多階段細粒度**：除了「探索 vs 精煉」二分，是否可設計更細粒度的階段劃分（如「廣域探索 → 局部探索 → 微調 → 穩定化」）？
- **理論保證的強化**：Theorem 1 的穩定性邊界可進一步擴展到 regret bound 或 sample complexity。

##### 3. 顧問與實作的更深度解耦

- **多顧問協作**：是否可讓多個顧問模型分別負責不同面向（如新穎性 vs 可行性 vs 改進潛力），再由元顧問整合？
- **實作模型的線上適應**：當前前沿實作模型凍結，但若允許其根據任務特性進行輕量適應（如 LoRA），是否能進一步提升？

##### 4. 應用領域擴展

- **科學發現**：除蛋白質適應度外，可應用於材料設計、藥物發現、催化劑最佳化等。
- **ML 系統自動化**：將 PACEvolve++ 應用於 AutoML、神經架構搜尋（NAS）、超參數最佳化等。
- **程式合成**：在更通用的程式合成任務（如 HumanEval、MBPP）上測試顧問模型範式。

##### 5. 與其他測試時學習範式的結合

- **測試時蒸餾（Test-Time Distillation）**：將顧問模型的搜尋經驗蒸餾回前沿模型，使其在無顧問時也能表現優異。
- **測試時擴展（Test-Time Scaling）**：將 PACEvolve++ 與 inference-time compute scaling（如思維鏈、樹搜索）結合，探索「搜尋 + 推理」的雙重擴展。
- **持續測試時學習**：在多輪部署中累積搜尋經驗，避免每次從零開始。

##### 6. 安全與對齊考量

- **顧問模型的偏見**：若訓練資料偏向某些突變族系，顧問模型可能系統性忽略其他方向，需要審計機制。
- **實作模型的越權**：前沿實作模型可能在「實作」過程中引入未授權的程式碼變更，需要沙盒與驗證機制。

##### 7. 基準與評估標準

- **建立演化搜尋基準**：目前缺乏統一的演化搜尋評估基準，未來可建立涵蓋多領域、可重現的 benchmark，推動領域發展。
- **長期穩定性指標**：除收斂速度外，應關注「在 1000 次迭代後是否仍能改進前沿」等長期穩定性指標。

總結而言，PACEvolve++ 的核心貢獻在於將「測試時學習」從單一模型的自適應擴展到「雙模型分工 + 階段感知」的範式，為 LLM 驅動的演化搜尋開啟了新的設計空間。其理論與實務的結合（Theorem 1 + 三領域實驗）使其成為該方向的重要里程碑。後續研究若能在顧問模型規模化、階段切換自動化、應用領域擴展等方面推進，將進一步釋放測試時學習在開放式最佳化中的潛力。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於一個關鍵問題：如何讓大型語言模型（LLM）在長程演化式搜尋過程中，持續地適應並改進其推理策略。現有的演化式搜尋系統（如 AlphaEvolve、FunSearch、PACEvolve）雖然在開放式最佳化任務上表現出色，但它們大多仰賴固定的、提示引出式推理策略，僅透過上下文來參考搜尋歷史，卻無法將搜尋回饋內化為穩定的決策偏好。這意味著模型雖然能「看到」哪些方向曾經失敗或成功，卻無法真正「學會」優先選擇那些新穎、可行且有助於推進前沿的搜尋方向。

**Q2：為什麼現有的演化式搜尋方法會遭遇瓶頸？**
A：現有方法主要透過兩種方式改進搜尋流程：一是強化搜尋支架（如階層式上下文管理、動量式回溯、島嶼式協作、構想池等），二是使用更強的模型來產生候選突變。然而，這些方法都共享一個根本限制：它們使用同一個模型同時負責「決定要嘗試什麼」與「實作該突變」，導致假設品質與實作正確性糾纏在一起。在實際的研究與工程任務中，複雜的程式碼庫整合細節與系統限制常導致實作失敗，使得強化學習收到的回饋訊號夾雜了大量雜訊，無法有效學習搜尋偏好。

**Q3：為什麼測試時策略適應在實務上如此重要？**
A：在推薦系統設計、混合專家模型（MoE）負載平衡、蛋白質適應度外推等真實研究與工程任務中，候選方向可能涵蓋架構變更、最佳化選擇、路由策略、特徵交互、序列層級轉換等多元面向。雖然許多方向都能透過通用的 LLM 推理來論證其合理性，但實際上只有少數能在評估後產生可測量的改進。有效的搜尋決策仰賴於辨識跨多次嘗試的模式——哪些突變族系反覆失敗、哪些局部改善值得重新探索、哪些方向相對於演化中的前沿仍具新穎性——這使得將搜尋回饋內化為穩定決策偏好成為關鍵。

**Q4：PACEvolve++ 的核心方法是什麼？**
A：PACEvolve++ 提出了一個顧問模型強化學習框架，將策略性搜尋決策與程式實作解耦。具體而言，一個可訓練的顧問模型負責構想生成、新穎性評估與假設選擇等策略性決策，而一個更強大的前沿實作模型則負責將選定的假設轉化為可執行的程式碼。這種分工使得強化學習訊號能聚焦於「下一步該評估什麼」，而非糾纏於實作細節的正確性。

### 實作步驟建議

**步驟一：建立評估基礎設施**
- 實作可程式化評估器 `E`，確保評估結果可重現且成本可控。
- 建立候選程式儲存庫，記錄每次 rollouts 的程式碼、分數、所屬族系標籤。
- 設定評估預算上限（例如單次任務最多 N 次評估），避免無止境搜尋。

**步驟二：設計顧問模型架構**
- 選擇中等規模的開源模型（例如 7B–14B 等級）作為顧問模型，權重可訓練。
- 設計顧問模型的輸入格式：當前最佳程式、評估指標、搜尋歷史濃縮、構想池。
- 設計三個決策頭：(1) 假設生成（產生新方向）、(2) 新穎性評估（過濾重複）、(3) 假設選擇（從候選中挑選）。

**步驟三：建立前沿實作模型介接層**
- 將選定的假設轉換為前沿模型的提示，呼叫 API 產生可執行程式碼。
- 實作程式碼解析、語法檢查、沙盒執行與錯誤回傳機制。
- 將實作失敗的案例回饋給顧問模型，作為負面訓練信號。

**步驟四：實作階段自適應強化學習**
- **早期階段（探索期）**：使用群組相對回饋（GRPO 風格），計算同一 rollout 批次內的相對優勢，鼓勵多樣化探索。
- **後期階段（精煉期）**：切換為前沿貢獻回饋，根據候選是否進入 best-of-k 前沿集合給予信用。
- **階段切換判斷**：監控獎勵差距（reward gap）壓縮程度，當差距縮小到閾值以下時觸發切換。
- 參考論文的 Theorem 1 設定學習率與信用分配權重，避免早期過度利用少數高分 rollout。

**步驟五：建立長程搜尋管理機制**
- 實作階層式上下文管理（避免上下文爆炸）、動量式回溯（保留有潛力的中間解）、島嶼式協作（多個搜尋線程）。
- 維護持久化構想池，記錄成功與失敗的假設族系。
- 設定收斂判斷條件：當前沿在 K 次迭代內無改善時停止。

**步驟六：部署與監控**
- 將訓練好的顧問模型部署為服務，對接前沿模型 API 與評估叢集。
- 監控每次 rollouts 的獎勵曲線、階段切換時機、實作失敗率。
- 收集線上回饋，定期以新資料微調顧問模型。

### 潛在風險與注意事項

**風險一：非平穩回饋導致訓練不穩定**
- 演化搜尋的回饋分佈隨時間劇烈變化，早期的群組相對信號在後期可能完全失效。
- **緩解**：嚴格遵循階段自適應機制，使用 Theorem 1 提供的學習率邊界，避免在獎勵差距壓縮時仍使用群組相對優勢。

**風險二：實作失敗污染訓練信號**
- 前沿模型產生的程式碼可能因語法錯誤、API 呼叫錯誤或整合問題而執行失敗，這些失敗會被誤認為「假設品質差」。
- **緩解**：在信用分配前過濾實作失敗案例，僅對成功執行的候選計算優勢；將實作錯誤回傳給前沿模型以改進提示。

**風險三：評估成本失控**
- 對於蛋白質工程、MoE 負載平衡等任務，每次評估可能耗時數小時或佔用大量 GPU。
- **緩解**：設定嚴格的評估預算上限；使用低保真代理評估器做早期篩選，僅對通過篩選的候選執行完整評估。

**風險四：顧問模型過擬合到少數族系**
- 強化學習可能使顧問模型快速收斂到少數高分族系，喪失探索多樣性。
- **緩解**：在獎勵中加入新穎性獎勵項；定期重置構想池；使用島嶼式協作維持多個搜尋線程。

**風險五：階段切換時機錯誤**
- 若過早切換到前沿貢獻模式，可能錯失探索機會；若過晚切換，則會在已無信號的群組相對回饋上浪費訓練步驟。
- **緩解**：監控獎勵差距的移動平均與變化率，採用多指標聯合判斷（例如同時觀察 rollout 內分數標準差與 best-of-k 更新頻率）。

**風險六：前沿模型 API 成本與延遲**
- 每次假設實作都需呼叫前沿模型，長期搜尋的 API 成本與延遲可能成為瓶頸。
- **緩解**：批次化 API 呼叫；對高信心假設使用較小模型；快取常見實作模式。

### 與其他技術的整合建議

**與 AlphaEvolve / FunSearch 整合**
- PACEvolve++ 的顧問模型可作為 AlphaEvolve 的「策略層」，由 AlphaEvolve 負責程式碼生成與評估，PACEvolve++ 負責假設選擇。
- FunSearch 的程式碼骨架可作為前沿實作模型的提示範本，提升實作成功率。

**與 PACEvolve 整合**
- PACEvolve++ 是 PACEvolve 的強化學習擴充版本，可直接替換 PACEvolve 的固定策略模組。
- 保留 PACEvolve 的階層式上下文管理、動量式回溯、島嶼式協作與持久化構想池，僅將決策層升級為可訓練的顧問模型。

**與 GRPO / PPO 等強化學習演算法整合**
- 階段自適應機制可包裝為策略梯度計算的外層框架，內層仍使用標準 GRPO 或 PPO。
- 群組相對回饋階段直接對應 GRPO 的群組優勢估計；前沿貢獻階段可設計為二元獎勵（是否進入 best-of-k）。

**與 MLOps 平台整合**
- 將顧問模型註冊為 MLflow / Weights & Biases 的可追蹤實驗。
- 評估器可整合到 Kubeflow / Airflow 排程，支援分散式平行評估。
- 構想池與搜尋歷史可存入向量資料庫（如 Milvus、Qdrant），支援相似度檢索。

**與領域專屬工具鏈整合**
- **MoE 負載平衡**：整合 Megatron-LM、DeepSpeed 的 profiling 工具。
- **推薦系統**：整合 RecBole、TensorFlow Recommenders 的評估管線。
- **蛋白質工程**：整合 AlphaFold、ESMFold 的預測介面作為評估器。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 2 節「演化式搜尋代理人」的背景介紹，理解「候選生成 → 評估 → 選擇」的基本迴圈概念。接著重點閱讀第 1 節的 Figure 1，掌握「顧問模型負責決策、前沿模型負責實作」的核心分工意圖。數學細節（Theorem 1）可先跳過，重點理解「為什麼需要把決策和實作分開」以及「為什麼搜尋不同階段需要不同的回饋信號」。

**給 AI 工程師**：建議從第 3.2 節的顧問模型設計開始閱讀，理解假設生成、新穎性評估、假設選擇三個決策頭的介面設計。接著深入第 3.3 節的階段自適應強化學習演算法，特別關注群組相對回饋與前沿貢獻回饋的切換條件與信用分配權重。實作時可參考論文的演算法偽碼，先以小規模任務（例如符號回歸）驗證流程，再擴展到 MoE 負載平衡等大型任務。

**給研究者**：建議從第 1 節的研究動機開始，理解「固定策略 vs. 可訓練策略」在長程演化搜尋中的根本差異。接著仔細閱讀 Theorem 1 及其證明，理解階段自適應機制的理論保證。實驗章節（第 4 節）值得仔細分析，特別是不同任務上階段切換時機的差異，以及顧問模型與前沿模型的分工如何影響收斂速度。可考慮將此框架擴展到多代理人協作、多目標演化等方向。

**給產品經理**：建議先閱讀摘要與第 1 節，理解 PACEvolve++ 解決的問題是「如何讓 AI 在長期任務中越搜尋越聰明」。重點關注三個應用場景（MoE 負載平衡、序列推薦、蛋白質工程）的商業價值：對於需要昂貴評估的研發任務，此框架可顯著降低搜尋成本並加速收斂。實作門檻方面，需評估團隊是否具備強化學習訓練能力、領域評估函數設計能力，以及前沿模型 API 的預算。建議從單一高價值任務切入驗證，再逐步擴展到其他場景。
