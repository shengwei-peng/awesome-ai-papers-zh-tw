# 規則轉工具：科學計算中大語言模型代理之可執行檢查

**原文標題：** Rules to Tools: Executable Checks for LLM Agents in Scientific Computing  
**作者：** Jingjie Ning、Guojiang Zhao、Chen Xu 等 7 位作者  
**發布日期：** 2026-09-29  
**HF 連結：** [https://huggingface.co/papers/2610.00313](https://huggingface.co/papers/2610.00313)  
**arXiv：** [https://arxiv.org/abs/2610.00313](https://arxiv.org/abs/2610.00313)  

---

## ⚡ TL;DR

科學編碼代理需驗證修訂後程式是否符合科學需求，但缺乏實用可執行檢查機制。
R2T將公開科學需求封裝為可呼叫檢查工具，供代理反覆量測演化中程式。
配對實驗顯示任務相依成效，部分任務以工具組表現較佳，PDE比較中模型輸出降低31.2%。

## 摘要翻譯

科學編碼代理以書面形式接收方程式（Equations）、邊界條件（Boundary conditions）與輸出需求（Output requirements），接著必須評估其所修訂的程式。規則轉工具（R2T）提供針對公開科學需求（Scientific requirements）所預先準備的可執行檢查（Executable checks）。配對 SciCode 修復組（Matched SciCode repair groups）共享書面檢查（Written checks）、起始程式（Starting programs）、模型與預算；工具組則接收一份可呼叫實作（Callable implementation）。在兩個任務 ID 群組（Task-ID cohorts）中，文字組完整修復（Complete repair）為 26/30，檢查組則為 29/30。三個任務 ID 偏好工具，一個偏好文字，十一個平手。八任務 ID 群組得分為 13/16 對比 15/16，差異的任務集群自助法（Task cluster bootstrap）95% 區間（95% interval）為 [-12.5, 43.75] 百分點（Percentage points）。較大的共享定義 SciCode 群組每組以 13/24 平手。五個含替代起始程式（Alternate starting programs）之開發暴露任務（Development-exposed tasks）得分為 3/10 對比 7/10。工具組偏好任務 17、77 與 11；初始檢查（Initial checks）標記任務 17，並對任務 77 與 11 回報無違規（Reported violation）。任務 37 偏好文字，且無初始回報違規。一個新源碼透 Python 組（Source-through-Python arm）亦達到 15/16，與專用命令（Dedicated command）之總計（Aggregate）相符。在配對偏微分方程（PDE）比較中，詳細文字得分為 23/24，檢查得分為 24/24，且檢查組之回報模型輸出（Model output）較文字組降低 31.2%。代理端輸出節省（Agent-side output savings）隨群組而異，而公開 CPU 使用（Public CPU use）在兩個任務 ID 群組中皆上升。這些結果以預先準備的檢查衡量任務相依（Task-dependent）修復結果（Repair outcomes）與代理端成本。

### 核心貢獻（3～5點）
- 提出「規則轉工具（R2T）」方法，將書面科學規則轉化為可執行檢查工具，使大語言模型代理得以在程式修訂過程中即時驗證科學需求之滿足情形。
- 透過嚴謹的配對實驗設計（Matched comparison），量化比較工具組與純文字組於 SciCode 基準測試中之修復成效，揭示任務相依之差異模式。
- 報告多項具體實驗數據，包括修復率（26/30 vs. 29/30）、任務勝敗分布、任務集群自助法 95% 信賴區間，以及開發暴露任務之表現落差，驗證方法之有效性與侷限性。
- 證實替代實作路徑（源碼透 Python 組）可達到與專用命令相當之總計分數，顯示方法具備實作彈性。
- 量化分析代理端成本效益：模型輸出降低 31.2%，同時記錄公開 CPU 使用上升之取捨關係，為實務部署提供參考依據。

### 適合對象
從事科學計算、數值模擬與物理建模之研究人員；開發或評估 AI 編碼代理（特別是科學編碼代理）之研究團隊；對大語言模型於科學程式自動化修訂與驗證之應用感興趣之學者與工程師；以及關注 AI 代理可執行規格（Executable specifications）與工具化科學知識（Callable scientific knowledge）設計之方法論研究者。

## 深度分析

#### 方法論解析

**核心概念：從書面規則到可呼叫工具的轉化**

R2T（Rules to Tools，規則轉工具）的核心方法論在於將科學計算任務中的「公開科學需求」（public scientific requirements）從自然語言描述轉化為可執行的檢查函式（callable checks）。論文中定義了一個形式化框架：令 $P_t$ 為任務 $t$ 的完整公開規格，$c$ 為當前候選產物（artifact，包含程式碼、輸出檔案或數值場），則診斷函式（diagnostic）$d_j(c; P_t)$ 將產物映射為一組量測結果，包含關係式（relation）、探測點（probe）、容差（tolerance）等資訊。這種設計使代理（agent）能在每次程式修訂後，將當前版本提交給檢查器，讀取量測值或錯誤報告，並據此決定下一步編輯方向。

**檢查器覆蓋的科學需求類型**

R2T 所建構的可執行檢查涵蓋四類可量測的科學需求：
1. **邊界值（boundary values）**：例如在偏微分方程（PDE, Partial Differential Equations）任務中，特定領域邊界（domain boundary）的溫度設定；
2. **物理關係（physical relations）**：物理量之間應滿足的守恆律或函數關係；
3. **方程式（equations）**：數學方程式本身的數值驗證；
4. **必要輸出檔案（required output files）**：任務規定的產出格式與內容。

**配對修復比較設計（Matched Repair Comparisons）**

方法論上最關鍵的設計是「配對修復比較」：兩組代理共享相同的書面規則、起始程式（starting programs）、模型（model）與預算（budgets），唯一的差異在於「工具組」（tool group）額外獲得一個可呼叫的檢查實作（callable implementation），而「文字組」（text group）僅依賴書面描述與普通 Python 執行（ordinary Python execution）。這種控制變因的實驗設計（controlled comparison）使研究者能夠隔離「可執行檢查」這一單一變因的因果效應。

**多層次的評估指標體系**

R2T 不僅測量最終的「完整修復」（complete repair）成功率，還追蹤：
- **元件進度（component progress）**：部分元件的完成程度；
- **代理端輸出節省（agent-side output savings）**：模型輸出（model output）的 token 消耗變化；
- **公開 CPU 使用（public CPU use）**：執行檢查所帶來的計算成本；
- **保留追蹤（retained traces）**：記錄代理如何使用檢查器的量測結果。

**檢查器交付方式的補充實驗**

除了直接提供可呼叫實作外，R2T 還設計了「源碼透 Python 組」（source-through-Python arm），即透過普通 Python 介面提供檢查器的源碼（checker source），測試不同交付方式的效果。實驗結果顯示此組同樣達到 15/16，與專用命令（dedicated command）的總計（aggregate）相當，說明檢查內容的可及性比介面形式更為關鍵。

#### 實驗數據解讀

**主要配對實驗結果**

論文報告了兩個任務 ID 群組（task-ID cohorts）的配對修復結果：

| 群組 | 文字組 | 工具組 | 差異 |
|------|--------|--------|------|
| 8-ID cohort | 13/16 | 15/16 | +2 |
| 15-ID cohort | 13/14 | 14/14 | +1 |

在 8-ID 群組中，工具組的任務集群自助法（task cluster bootstrap）95% 區間為 [-12.5, 43.75] 百分點（percentage points），這個寬廣的信賴區間反映了樣本量小所帶來的高變異性，意味著雖然點估計顯示工具組有優勢，但統計上無法排除文字組在某些任務集群上表現更好的可能性。

**任務層級的細粒度分析**

在 30 個任務的完整修復比較中：
- **26/30 文字組修復成功**；
- **29/30 工具組修復成功**；
- **3 個任務 ID 偏向工具**（任務 17、77、11）；
- **1 個任務 ID 偏向文字**（任務 37）；
- **11 個任務平手**。

值得注意的是，偏向工具的三個任務中，初始檢查（initial checks）僅對任務 17 標記出違規（flagged），而任務 77 和 11 的初始檢查報告無違規（no violation）。這暗示 R2T 的效益不僅來自於「發現錯誤」，還可能來自於「確認正確性」所帶來的編輯信心。

**開發暴露任務的反向結果**

在 5 個開發暴露任務（development-exposed tasks）使用替代起始程式（alternate starting programs）的測試中，結果出現反轉：文字組 3/10，工具組 7/10。這顯示 R2T 的效益可能與起始程式的品質或特性存在交互作用。

**較大共享定義 SciCode 群組的平手結果**

在更大的共享定義 SciCode 群組中，兩組均為 13/24，呈現平手。這暗示在更廣泛的任務分布下，可執行檢查的邊際效益可能被稀釋。

**PDE 配對比較的成本效益**

在 PDE 配對比較中：
- 詳細文字組：23/24；
- 檢查組：24/24；
- 檢查組的模型輸出降低 31.2%。

這顯示在 PDE 任務中，可執行檢查不僅提升了修復成功率，還大幅降低了代理端的 token 消耗，提供了明確的成本效益證據。

**資源成本的權衡**

論文觀察到一個重要的權衡現象：雖然代理端輸出（agent-side output）在不同群組中變化方向不一致，但公開 CPU 使用（public CPU use）在兩個任務 ID 群組中均上升。這意味著將運算從模型推理轉移到檢查執行雖然可能降低 token 成本，但會增加整體計算資源消耗。

#### 與現有研究的比較

**與反饋驅動語言代理的關係**

R2T 建立在反饋驅動語言代理（feedback-driven language agents）的研究脈絡之上，與 Self-Refine（Madaan et al., 2023）、Reflexion（Shinn et al., 2023）、CRITIC（Gou et al., 2023）等方法共享「反饋-修訂」的迭代模式。然而，R2T 的獨特貢獻在於將「外部工具反饋」具體化為「公開科學需求的量測」，而非泛化的語言模型反饋或通用測試輸出。相較於 SWE-bench Verified 上代理撰寫測試僅提供列印值（Chen et al., 2026b），R2T 的檢查器直接對應科學規格中的物理關係與方程式。

**與科學編碼基準的互補**

R2T 並非提出新的基準測試，而是作為一個「支援套件」（support package）應用於既有基準：SciCode/SciCode-Verified（Tian et al., 2024; Hu et al., 2026）、PDEAgentBench（Hang et al., 2026）、MDArena、AInsteinBench（Anand et al., 2026; Duston et al., 2025）以及 SWE-bench Science（Xu et al., 2026）。這種定位使 R2T 能夠橫跨多個基準進行評估，但也意味著其效益高度依賴於各基準的任務特性。

**與可執行規格研究的區別**

相較於 CodeMetaAgent（Akhond & Uddin, 2025）透過變形規格（metamorphic specifications）構造測試、SecTDD（Liang et al., 2026）研究生成前測試與修復中反饋、R2T 的特點在於：
1. **檢查器由作者構造**（author-constructed），而非由語言模型生成；
2. **基於公開科學需求**，而非從程式行為推導；
3. **應用於演化中程式**（evolving program），而非僅在最終版本上驗證。

這與 CodeSpec（Wang et al., 2026）對比文字與可執行架構規格的研究方向相近，但 R2T 聚焦於科學計算領域的數值關係。

**與科學知識工具化的連結**

Paper2Agent（Miao et al., 2026）將論文與程式碼轉化為可呼叫科學代理，並比較 MCP 工具與 Markdown 技能。R2T 與其共享「將科學知識工具化」的願景，但 R2T 專注於「檢查」這一特定功能，而非完整的科學工作流程。

**方法論限制**

R2T 的配對設計雖然嚴謹，但存在以下限制：
1. **檢查器建構成本**：作者構造的可呼叫檢查需要人工投入，這限制了其可擴展性；
2. **任務相依性（task-dependent）**：效益在不同任務上差異顯著，從 +2/16 到平手不等；
3. **開發暴露偏差**：在開發階段曾接觸過的任務上，工具組的優勢可能部分來自於記憶效應而非真正的檢查效益。

#### 可重現性評估

**實驗設計的可重現性要素**

R2T 的配對修復比較設計在方法論層面具備良好的可重現性基礎：
1. **凍結定義（frozen definitions）**：任務特定書面定義（task-specific written definitions）與可執行檢查在配對修復前固定；
2. **獨立評分器（independent graders）**：最終程式由獨立的基準評估器（benchmark evaluator）評分，避免評估偏差；
3. **保留追蹤（retained traces）**：記錄代理如何使用檢查器的量測結果，使行為分析成為可能；
4. **控制變因**：書面規則、起始程式、模型、預算均固定，僅變更檢查器的可及性。

**資源記錄的透明度**

論文明確報告了模型輸出（model output）與 CPU 使用（CPU use）的記錄，這使得成本效益分析可被獨立驗證。31.2% 的模型輸出降低與公開 CPU 使用的上升提供了具體的數字基準。

**可重現性的潛在障礙**

然而，論文中未明確提及以下要素：
1. **檢查器源碼（checker source）的公開性**：雖然設計了源碼透 Python 組，但未說明檢查器本身的程式碼是否隨論文發布；
2. **起始程式的具體內容**：替代起始程式（alternate starting programs）的具體差異未詳細描述；
3. **模型的具體版本與設定**：雖然提到「模型」固定，但未指明具體的語言模型及其參數設定；
4. **任務 ID 的完整列表**：雖然提及任務 17、77、11、37 等，但未提供完整的任務 ID 對照表。

**統計方法的嚴謹性**

任務集群自助法（task cluster bootstrap）95% 區間的使用顯示作者意識到任務間的非獨立性，並採取了適當的統計校正。然而，[-12.5, 43.75] 百分點的寬廣區間也凸顯了樣本量不足的問題，這限制了結論的統計強度。

#### 未來研究方向

**自動化檢查器生成**

目前 R2T 的檢查器由作者手動構造，這限制了其可擴展性。未來研究可以探索：
1. **從書面規格自動合成可執行檢查**：利用語言模型將自然語言描述的科學需求轉化為 Python 函式；
2. **檢查器品質驗證機制**：確保自動生成的檢查器與人工版本具有等效的診斷能力；
3. **檢查器庫的累積建構**：隨著任務類型的擴展，建立可重用的檢查器元件庫。

**任務特性與檢查效益的交互分析**

論文揭示了明顯的任務相依性（task-dependent gains），但未深入分析其成因。未來可以探討：
1. **哪些任務特性預測工具組的優勢**？例如起始程式的錯誤密度、書面規格的明確性、科學需求的數值嚴格度等；
2. **為何任務 77 和 11 在無初始違規的情況下仍從工具組受益**？這可能涉及「確認偏誤」或「編輯信心」的心理機制；
3. **開發暴露任務的反向結果**是否反映了「過度依賴工具」或「檢查器誤導」的可能性。

**成本效益的優化**

31.2% 的模型輸出降低伴隨著公開 CPU 使用的上升，這提出了資源配置的優化問題：
1. **檢查頻率的自適應控制**：代理應根據當前編輯狀態決定何時呼叫檢查器，而非每次修訂後都執行；
2. **檢查粒度的分層設計**：粗粒度快速篩選與細粒度精確診斷的組合；
3. **跨任務的檢查結果快取**：相似任務間的診斷結果可能具有可遷移性。

**與其他反饋機制的整合**

R2T 的可執行檢查可以與其他反饋來源結合：
1. **與 SWE-bench 風格的代理撰寫測試互補**：人工構造的科學檢查與語言模型生成的測試可能覆蓋不同的錯誤類型；
2. **與物理啟發神經網路（PINN）的符號檢查整合**：Lang-PINN（He et al., 2025）的符號檢查方法可作為 R2T 的補充；
3. **多代理檢查器辯論**：不同代理對同一產物進行獨立檢查，透過共識機制提升診斷可靠性。

**領域擴展與泛化**

雖然 R2T 在科學計算領域展示了效益，但其方法論可推廣至：
1. **形式化規格可寫的工程領域**：如控制系統、訊號處理等；
2. **法律或財務文件的合規檢查**：將「物理定律」替換為「法規條文」；
3. **教育評測中的自動批改**：將「科學需求」替換為「評分標準」。

**長期研究方向：可執行科學知識的生態系**

R2T 的願景與 Paper2Agent、Executable Code Knowledge（Gao, 2026）等研究共同指向「可執行科學知識的生態系」建構。未來可以探索：
1. **檢查器的版本控制與演進管理**；
2. **跨論文的檢查器互操作性標準**；
3. **檢查器品質的社群評估機制**。

## 論文問答

**Q1：科學編碼代理面臨的核心問題是什麼？為何僅靠執行程式不足以驗證正確性？**
A：科學編碼代理接收書面形式的方程式、邊界條件與輸出需求，必須在反覆修訂程式的過程中評估自身成果是否滿足科學需求。問題在於一個模擬即使順利執行完畢，仍可能產生違反物理定律或偏離指定方程式的數值結果。換言之，「程式能跑」與「結果符合科學需求」之間存在落差，代理需要可重複、可量化的方式來測量當前程式與需求的距離，而這正是 R2T 欲解決的根本痛點。

**Q2：現有的回饋驅動方法（如 Self-Refine、Reflexion、CRITIC）為何無法充分支援科學編碼任務？**
A：Self-Refine 與 Reflexion 等方法仰賴同一語言模型產生自我回饋或儲存文字反思，屬於通用型回饋機制，未必能精準捕捉科學計算中的物理關係與數值容差。CRITIC 雖引入外部工具回饋，但並未針對科學需求的「可量測性」設計專屬介面。CodePDE 與 Lang-PINN 雖將回饋整合進 PDE 求解與物理資訊神經網路，卻缺乏控制變因後的配對比較，難以隔離「可執行科學檢查」本身的貢獻。因此 R2T 透過配對 SciCode 修復設計，在書面條件、起始程式、模型與預算皆固定的前提下，單獨檢驗準備好的可執行檢查之附加價值。

**Q3：為何「可重複量測」在科學計算中特別重要？**
A：科學需求通常以邊界值、物理關係、方程式等形式呈現，這些需求本質上是可量化的——例如某邊界上的溫度值是否符合規定，或輸出是否符合某物理守恆律。若代理每次修訂後只能憑直覺或文字描述判斷，便難以穩定追蹤進度，也無法分辨「部分改善」與「完全修復」。R2T 將這些公開需求包裝為可呼叫的檢查，使代理能在每次修改後取得具體的量測值或錯誤報告，進而形成可重複、可比較的修訂循環。

**Q4：R2T 的核心方法是什麼？如何將「規則」轉化為「工具」？**
A：R2T 的核心是將公開的科學需求封裝為可呼叫的檢查工具。具體而言，對於任務 t 的完整公開規格 P_t 與當前候選產物 c，定義診斷函式 d_j(c; P_t) 對應一項科學關係（例如邊界值、方程式、輸出檔案）。代理將當前程式提交給檢查，讀取量測結果或錯誤報告，再據此繼續編輯。這種「提交—量測—修訂」的循環讓書面規則變成可重複執行的工具，使代理能在每次修改後即時取得科學層面的回饋。

**Q5：R2T 在實驗設計上的關鍵創新為何？**
A：R2T 的關鍵創新在於「配對修復比較」（matched repair comparison）：書面條件、起始程式、模型與預算皆固定，唯一變項是「是否取得準備好的可執行實作」。這種控制變因的設計能乾淨地隔離出可執行檢查本身的貢獻，避免混淆變因。此外，R2T 還設計了「源碼透 Python 組」（source-through-Python arm），透過普通 Python 取得檢查器源碼，與專用命令組比較，檢驗「如何交付」實作是否影響成效。

**Q6：R2T 在設計上做了哪些關鍵選擇？為何採用「作者建構」的可呼叫檢查而非自動生成？**
A：R2T 選擇由作者依據公開科學需求手工建構可呼叫檢查，而非讓 LLM 自動生成測試或斷言。這是因為科學需求（如物理關係、容差、探測點）需要精確定義，自動生成容易引入錯誤或遺漏關鍵條件。此外，R2T 將任務專屬的書面定義與可執行檢查在配對修復前「凍結」，確保兩組代理面對完全相同的科學標準，避免評分偏差。這種設計選擇換來的是量測的可信度與可重複性，但同時也帶來人工建構成本的限制。

**Q7：R2T 在哪些基準測試上進行評估？為何選擇這些基準？**
A：R2T 在 SciCode（兩個任務 ID 群組）、PDEAgentBench（配對 PDE 任務）、MDArena、AInsteinBench、SWE-bench Science 等四個科學計算基準上進行評估。選擇這些基準的理由是它們涵蓋了數值計算、分子模擬、科學軟體儲存庫修復等多元科學編碼場景，能檢驗 R2T 在不同科學領域的通用性。其中 SciCode 是核心比較場景，因為它提供研究導向的數值程式設計任務，適合進行嚴格的控制變因配對實驗。

**Q8：R2T 的關鍵實驗結果為何？任務相依的效應如何呈現？**
A：在 8 個任務 ID 的群組中，文字組得分 13/16，工具組得分 15/16；在 15 個任務 ID 的群組中，文字組 13/14，工具組 14/14。然而任務叢集自助法 95% 區間為 [-12.5, 43.75] 百分點，顯示差異具高度不確定性。深入檢視個別任務：任務 17、77、11 偏向工具組，任務 37 偏向文字組；其中任務 17 在初始檢查即被標出違規，而 77 與 11 的初始檢查未回報違規。這說明 R2T 的效益是任務相依的，並非全面性提升。

**Q9：R2T 在「開發暴露任務」與「PDE 比較」中的消融結果為何？**
A：在五個開發暴露任務（使用替代起始程式）中，文字組僅得 3/10，工具組達 7/10，差距更為顯著，顯示在較困難的起點下，可執行檢查的價值更高。在配對 PDE 比較中，詳細文字組得分 23/24，檢查組得分 24/24，且檢查組的模型輸出降低 31.2%，代表可執行檢查不僅提升完成度，還降低代理端的 token 成本。然而公開 CPU 使用量在兩個任務 ID 群組中皆上升，說明檢查機制會帶來額外運算負擔。

**Q10：R2T 在實際科學研究工作流程中可應用於哪些場景？**
A：R2T 可應用於任何需要反覆修訂科學程式的研究場景，例如物理模擬的邊界條件調整、分子動力學的能量守恆檢查、PDE 求解器的數值精度驗證等。在這些場景中，研究者通常需要花費大量時間手動驗證輸出是否符合物理直覺或數學約束，而 R2T 將這些驗證自動化為可重複呼叫的檢查，使代理（或人類研究者）能在每次修改後即時取得量測結果，加速迭代並降低人為疏失的風險。

**Q11：將 R2T 整合至產品時需考量哪些工程因素？**
A：整合 R2T 至產品時需考量：(1) 檢查器的建構成本——目前由作者手工建構，規模化時需考慮自動化或半自動化流程；(2) 公開 CPU 使用量上升的問題，需評估是否在邊緣部署或雲端執行檢查；(3) 檢查器源碼的保護與版本管理，避免代理繞過或誤用；(4) 與現有代理框架（如 MCP 工具、Markdown 技能）的相容性，參考 Paper2Agent 的設計進行整合。

**Q12：R2T 對科學計算自動化領域的潛在影響為何？**
A：R2T 揭示了「可執行科學知識」作為代理工具的可行性，將書面規則轉化為可量測、可重複的檢查介面。這種模式可推廣至更廣泛的科學軟體開發，讓領域專家將其專業知識編碼為檢查工具，供 LLM 代理使用。長期而言，R2T 的配對修復設計可作為評估「工具化科學知識」效益的標準方法論，推動科學編碼代理從「能跑」邁向「跑對」，並促成更嚴謹的科學軟體品質保證流程。

**Q13：R2T 論文本身承認了哪些限制？**
A：論文坦承效益具高度任務相依性——任務叢集自助法 95% 區間寬達 [-12.5, 43.75] 百分點，統計不確定性高，意味著在某些任務叢集下工具組甚至可能落後文字組。此外，公開 CPU 使用量在兩個任務 ID 群組中皆上升，意味著可執行檢查雖降低代理端模型輸出，卻增加整體運算成本。論文也指出部分任務（如任務 37）反而偏向文字組，說明可執行檢查並非萬靈丹，其適用範圍仍有邊界。

**Q14：R2T 在哪些情況下會失敗或效果不佳？**
A：當科學需求難以形式化為可量測檢查時（例如涉及複雜視覺判斷或開放式科學推理），R2T 的效益可能有限。任務 37 偏向文字組即可能源於其需求特性不適合可執行檢查。此外，若起始程式已高度正確（初始檢查未回報違規），可執行檢查能提供的增量資訊較少，效益自然降低。值得注意的是，開發暴露任務中差距擴大（3/10 vs 7/10）反向說明：在困難起點下 R2T 效果最佳，凸顯其作為「診斷工具」的價值。

**Q15：R2T 未來可延伸的研究方向為何？**
A：未來方向包括：(1) 自動化檢查器建構流程，降低人工成本並提升規模化能力；(2) 探索更高效的檢查執行機制，以降低公開 CPU 使用量上升的問題；(3) 將 R2T 模式推廣至更多科學領域（如生物資訊、計算化學），檢驗其通用性；(4) 研究檢查器與代理推理的深度整合，例如讓代理能根據檢查結果動態調整修訂策略，而非僅被動接收量測值；(5) 結合 Paper2Agent 等科學知識工具化方法，建立更完整的「科學知識—可執行檢查—代理修訂」生態系。

## 實務應用指南

### 適用場景

1. **科學程式碼修復工作流**：在氣象模擬、計算流體力學（CFD）、結構力學等領域，開發團隊可將物理邊界條件、能量守恆律、單位一致性等公開科學需求封裝為可呼叫檢查工具，讓 LLM 代理在每次修訂後自動驗證當前程式是否符合科學約束，減少「程式可執行但結果違反物理」的情況。

2. **偏微分方程（PDE）求解器開發**：針對熱傳導、波動方程、Navier-Stokes 等 PDE 家族任務，研發團隊可將符號關係式、解析解探測點、容差閾值等公開需求轉為檢查函式，代理提交候選解後即可獲得殘差量測，支援迭代式求解器生成與除錯。

3. **分子模擬與材料科學代理**：在分子動力學（MD）模擬工作流中，將公開的物理關係（如徑向分布函數、能量最小化準則）包裝為檢查工具，協助代理在修改模擬參數或程式碼時即時驗證是否符合科學規範，適用於 MDArena、AInsteinBench 等基準的實務部署。

4. **科學軟體儲存庫維護**：在 SWE-bench Science 類型的儲存庫修復任務中，將任務說明中的科學指引（scientific guidance）抽取為可執行檢查，使代理在修補 bug 時能針對科學正確性而非僅語法正確性進行驗證，提升修復品質。

5. **自動化科研代理人（Auto-Research）管線**：在端到端的科研代理系統中，將論文方法章節中的方程式、假設條件、輸出規格轉為檢查工具，作為代理修訂實驗程式碼時的科學守門員，銜接 Paper2Agent 等可呼叫科學知識系統。

### 實作前置條件

**資料前置條件**
- 任務的公開科學規格文件：包含方程式、邊界條件、輸出檔案格式、容差閾值、探測點定義等。
- 起始程式碼（starting program）：每個任務需有統一的初始程式版本，以利配對比較。
- 獨立評分器（independent grader）的評分腳本：與檢查工具解耦，確保最終評估公正性。
- 任務 ID 與分群定義：區分開發暴露任務（development-exposed）與全新任務，避免資料洩漏。

**運算前置條件**
- LLM API 存取權限（建議使用與原實驗相同或相當的模型版本）。
- Python 執行環境（含 NumPy、SciPy、SymPy 等科學計算套件）。
- 隔離的程式碼執行沙箱（支援重複提交、錯誤回傳、CPU 時間記錄）。
- 資源監控機制：能分別記錄模型輸出 token 與 CPU 使用量。

**技能前置條件**
- Python 進階程式設計能力（特別是函式封裝、錯誤處理、序列化）。
- 科學計算領域知識（能將物理關係轉為可量化檢查）。
- LLM 代理開發經驗（熟悉工具呼叫、迭代修訂、軌跡記錄）。
- 統計分析能力（任務集群自助法、信賴區間估計）。

### 實作步驟建議

1. **需求盤點與分類**：盤點目標任務集中的所有公開科學需求，依類型分為邊界值、物理關係、方程式、輸出檔案四類。為每項需求指派唯一的關係標籤（relation）與探測點（probe）。

2. **設計檢查函式介面**：定義統一的檢查函式簽章 `dj(c; Pt) = (relation, problem, measurement)`，其中 `c` 為當前候選程式產物，`Pt` 為完整公開規格。函式應回傳結構化量測結果或錯誤報告，便於代理解析。

3. **建構配對實驗設計**：為每個任務 ID 建立兩個修復組——文字組（僅接收書面檢查）與工具組（額外接收可呼叫實作）。固定書面定義、起始程式、模型版本、token 與 CPU 預算，僅改變「是否提供可執行檢查」此一變因。

4. **實作檢查器並凍結**：撰寫每個任務的檢查器實作後凍結版本，避免在實驗過程中修改。對開發暴露任務，另準備替代起始程式以測試泛化性。

5. **建立代理執行迴圈**：代理流程為「提交程式 → 呼叫檢查 → 讀取量測或錯誤 → 修訂程式 → 重複」，直到預算耗盡或代理宣告完成。保留完整追蹤紀錄（traces）供後續分析。

6. **整合獨立評分器**：使用與檢查器解耦的評分腳本評估最終程式，記錄完整修復（complete repair）與元件進度（component progress）兩類指標。

7. **量測資源成本**：分別記錄模型輸出 token 與 CPU 使用時間，計算代理端輸出節省比例與公開 CPU 使用增幅。

8. **執行統計分析**：採用任務集群自助法（task-cluster bootstrap）估計差異的 95% 信賴區間，注意任務相依性（task-dependent）效應——部分任務有利於工具、部分有利於文字、部分平手。

9. **部署補充實驗組**：除專用命令呼叫外，新增「源碼透 Python 組」（source-through-Python arm），透過普通 Python 執行取得檢查器源碼，驗證遞送方式的影響。

10. **建立持續評估管線**：將上述流程封裝為可重複執行的基準測試管線，定期在新任務上重新評估，追蹤檢查器品質與代理表現的長期趨勢。

### 潛在風險與注意事項

**風險一：任務相依效應導致整體效益被掩蓋**
- 現象：八任務群組中，工具組 15/16、文字組 13/16，看似工具全面勝出；但擴大至 24 個共享定義任務後，兩組皆為 13/24，呈現平手。
- 緩解：避免僅以總分判定優劣，應同時報告逐任務結果與任務集群自助法信賴區間；部署前先在目標任務集上做小規模配對實驗。

**風險二：開發暴露導致評估偏差**
- 現象：開發暴露任務使用替代起始程式時，工具組僅 3/10，文字組達 7/10，顯示檢查器可能在開發階段過擬合特定起始程式。
- 緩解：嚴格區分開發集與測試集；對開發暴露任務使用替代起始程式重新評估；凍結檢查器版本後不再修改。

**風險三：CPU 使用成本上升**
- 現象：兩個任務 ID 群組的公開 CPU 使用量皆上升，即使模型輸出 token 下降 31.2%。
- 緩隔：優化檢查函式效率；考慮快取中間結果；評估時同時報告 CPU 與 token 兩項成本，而非僅看模型輸出。

**風險四：初始檢查可能遺漏違規**
- 現象：任務 77 與 11 的初始檢查未回報違規，但工具組在這些任務上表現較佳，顯示初始檢查的覆蓋率有限。
- 緩隔：設計多層次檢查（淺層語法檢查 + 深層語義檢查）；結合單元測試與符號驗證；定期審查檢查器的誤報與漏報率。

**風險五：書面定義與檢查器不一致**
- 現象：書面規則與可執行檢查可能存在語義落差，導致代理依據書面定義修訂卻仍被檢查器標記違規。
- 緩隔：建立書面定義與檢查器的對應表；在實驗前進行一致性審查；讓書面定義成為檢查器的註解來源。

**風險六：評估器與檢查器耦合風險**
- 現象：若評估器與檢查器共用邏輯，可能造成「檢查通過即評估通過」的循環。
- 緩隔：嚴格分離檢查器（過程中量測）與評估器（最終評分）；評估器應基於獨立測試案例或隱藏測試集。

### 與其他技術的整合建議

**與 Self-Refine / Reflexion 整合**：R2T 的檢查工具可作為 Self-Refine 的外部反饋來源，取代或補充語言模型自身的自我批評；亦可整合至 Reflexion 的記憶機制，將檢查量測結果存入長期反思儲存。

**與 CRITIC 框架整合**：CRITIC 強調「透過外部工具反饋支援自我修正」，R2T 的可呼叫檢查正是此模式的科學計算實例；可將檢查器封裝為 CRITIC 風格的工具介面。

**與 MCP（Model Context Protocol）整合**：參考 Paper2Agent 的做法，將檢查器以 MCP 工具形式提供，使代理透過標準化協定呼叫；同時保留 Markdown 技能版本供文字組使用，便於 A/B 比較。

**與 SWE-bench 評估管線整合**：在 SWE-bench Science 任務中，將任務說明中的科學指引抽取為檢查工具，與既有的代理測試（printed values）並行運作，提升修復的科學正確性。

**與 Lang-PINN / CodePDE 整合**：將 R2T 檢查器與物理資訊神經網路（PINN）的符號檢查、PDE 求解器的數值精煉流程結合，形成多層次的科學驗證堆疊。

**與 SecTDD / CodeMetaAgent 整合**：借鏡其「測試驅動開發」與「變質規格」（metamorphic specification）概念，將 R2T 檢查器視為任務前預先生成的測試套件，於代理修訂過程中持續執行。

**與可執行規格基準（CodeSpecBench、SpecCoder）整合**：將 R2T 檢查器視為「行為規格」的一種實例，與既有的規格生成與驗證研究接軌。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節「Introduction」掌握 R2T 的核心問題意識——為何科學程式需要可執行檢查；再閱讀第 3 節了解檢查函式的形式化定義 `dj(c; Pt) = (relation, problem, measurement)`。重點關注「任務相依效應」與「配對實驗設計」兩個概念，這是理解全文結果的關鍵。

**給 AI 工程師**：重點閱讀第 2 節「Related Work」中關於反饋驅動代理（Self-Refine、Reflexion、CRITIC）與可執行規格（SecTDD、CodeMetaAgent）的段落，理解 R2T 在既有技術譜系中的定位。實作時應特別注意「凍結檢查器版本」、「分離評估器」、「記錄 CPU 與 token 雙重成本」三項工程紀律。

**給研究者**：重點閱讀第 4 節的實驗設計與統計分析方法，特別是任務集群自助法（task-cluster bootstrap）的使用——這是處理任務相依性時的關鍵統計技術。同時關注「開發暴露任務使用替代起始程式」此一嚴謹的泛化性測試設計，可作為後續研究的參考範式。

**給產品經理**：重點關注「任務相依效應」與「成本權衡」兩個面向。R2T 並非在所有任務上都優於純文字方案，且會帶來 CPU 使用量上升；產品決策應基於目標任務集的配對實驗結果，而非總體平均分數。建議在導入前先進行小規模概念驗證，並建立逐任務的效益追蹤機制。
