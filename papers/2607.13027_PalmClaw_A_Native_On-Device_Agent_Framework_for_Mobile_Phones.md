## 摘要翻譯

大型語言模型（Large Language Model, LLM）代理（Agent）已不僅止於生成回應，而是能透過呼叫工具（Tool）、觀察結果（Observation），並迭代決定下一個動作（Action），以執行多步驟任務（Multi-Step Task）。大多數代理系統執行於桌上型電腦或伺服器上，支援工具使用（Tool Use）與任務自動化（Task Automation）。行動裝置（Mobile Device）同樣是重要的代理環境，因其普及性高，且包含使用者資料、感測器（Sensor）與日常應用程式（Daily-Use Application）。現有的行動代理主要透過圖形使用者介面（Graphical User Interface, GUI）操作（例如點擊（Tap）、滑動（Swipe）與輸入（Type））來操控智慧型手機（Mobile Phone），這類操作常形成冗長且依賴介面的序列，無法直接存取裝置能力（Device Capability），也使得執行邊界（Execution Boundary）難以界定。我們提出 PalmClaw，一個原生執行於智慧型手機上的開放原始碼（Open-Source）代理框架，能直接在裝置上管理工作階段（Session）、記憶（Memory）、技能（Skill）、工具與代理迴圈（Agent Loop）。PalmClaw 將裝置能力公開為具備明確引數（Explicit Argument）、結構化結果（Structured Result）與清楚定義之執行邊界的裝置工具（Device Tool）。此設計使代理能夠直接使用行動裝置能力，同時讓每個動作保持明確且受控。實驗顯示，相較於最強基線，任務成功率（Task Success）相對提升 11.5%，完成時間（Completion Time）減少 94.9%，且設定負擔（Setup Burden）更低，追蹤記錄（Trace）亦展示執行邊界的應用方式。程式碼可於 https://github.com/ModalityDance/PalmClaw 取得。

### 核心貢獻（3～5點）
- PalmClaw 是一個原生執行於智慧型手機上的開放原始碼代理框架，將代理迴圈、工作階段、記憶、技能與工具的管理直接置於裝置端完成。
- 透過將裝置能力封裝為具備明確引數、結構化結果與清楚執行邊界的裝置工具，使代理能直接且可控地使用行動裝置功能。
- 相較於僅依賴圖形使用者介面（GUI）操作的行動代理，PalmClaw 避免了冗長且介面相依的動作序列，並能明確界定每個動作的執行範圍。
- 實驗結果顯示，相較於最強基線，任務成功率相對提升 11.5%，完成時間減少 94.9%，且設定負擔顯著降低。

### 適合對象
對行動裝置端人工智慧、大型語言模型（LLM）代理、任務自動化與工作流程自動化有興趣的研究人員與開發者；特別適合關注隱私保護、低延遲、原生裝置執行，以及希望將感測器、相機、麥克風、位置等裝置能力整合進代理系統的讀者。

## 深度分析

#### 方法論解析

PalmClaw 的核心設計目標是將傳統由**桌上型或雲端主機（Desktop or Cloud Host）**託管的代理框架，遷移到**智慧型手機（Mobile Phone）**本地執行。與現有大多數行動代理透過**圖形使用者介面操作（GUI Action）**（如點擊、滑動、輸入）控制手機不同，PalmClaw 採用「**裝置工具（Device Tool）**」作為主要動作空間，使代理能夠以結構化、可解釋且具備明確邊界的方式呼叫手機能力。

從架構圖（Figure 2）可以看出，PalmClaw 包含以下幾個關鍵元件：

1. **工作階段（Session）**：負責組織來自本地聊天、遠端頻道與定時喚醒等多種來源的輸入。每個 Session 保存對話歷史、工具追蹤記錄（Tool Trace）、附件以及專屬工作空間（Workspace），讓多工與跨回合任務能夠被清楚區隔與延續。

2. **記憶（Memory）**：分為兩層。第一層是跨 Session 的**長期記憶（Long-term Memory）**，用於儲存可在所有代理回合中共享的資訊；第二層是每個 Session 專屬的摘要（Per-session Summary），用於壓縮與回顧單一任務脈絡。

3. **技能（Skill）**：可重複使用的任務模板或流程，讓代理在面對相似任務時不必每次都從頭規劃，降低 LLM 呼叫次數與錯誤累積。

4. **裝置工具（Device Tool）**：這是 PalmClaw 方法論上最重要的創新。每個 Device Tool 具備：
   - **明確引數（Explicit Argument）**：代理必須以結構化方式傳入參數，而非透過模糊的螢幕座標或手勢。
   - **結構化結果（Structured Result）**：執行後回傳的觀察結果（Observation）是 schema 明確的資料，便於 LLM 理解與後續推理。
   - **工具特定執行邊界（Tool-Specific Execution Boundary）**：每個工具只被允許執行其定義範圍內的操作，從而限制代理的權限範圍，降低過度操作或誤用系統資源的風險。

5. **代理迴圈（Agent Loop）**：在裝置端完成「組裝上下文 → 呼叫 LLM → 解析工具呼叫 → 執行 Device Tool → 回傳 Observation → 進入下一回合」的完整循環。這意味著 Session Management、Memory、Skill、Tool Registry 與 Tool Execution 都運行於手機本地，而非依賴外部電腦透過 ADB 或無線介面遠控。

這種設計帶來的方法論優勢在於：它把行動裝置的相機、麥克風、位置、檔案、媒體、網頁、自動化通道等資源，封裝成具有穩定介面的可執行能力。相較於 GUI Action 必須面對螢幕解析、元素定位、佈局變化等脆弱性，Device Tool 的動作空間更貼近「能力呼叫」的抽象層次，使**任務分解（Task Decomposition）**後的每一步都對應到一個語義明確、邊界清晰的裝置操作。

#### 實驗數據解讀

根據摘要與內文所述，PalmClaw 在代表性行動任務上進行了評估，主要結果有兩項：

- **任務成功率（Task Success）**相較於最強基線提升 **11.5%**。
- **完成時間（Completion Time）**相較於最強基線減少 **94.9%**。

這兩個數字需要分開解讀。首先，11.5% 的相對提升（Relative Improvement）雖然看似不大，但在行動代理領域，GUI Action 基線通常已經具備相當高的表面相容性（幾乎可以操作任何可見介面），因此能在此基礎上再提升超過一成，代表 Device Tool 在處理需要直接存取裝置資源或精確參數的任務時，確實減少了因介面解析錯誤或長操作鏈累積失敗所造成的問題。

更值得關注的是 94.9% 的完成時間縮減。GUI-based 代理通常需要執行大量連續的點擊、滑動、等待畫面更新等動作，才能完成一個高層級任務；而 PalmClaw 的 Device Tool 可以直接呼叫底層能力（例如直接讀取檔案、發送訊息、查詢媒體庫），大幅縮短動作序列長度。這個時間降幅強烈暗示：PalmClaw 的動作空間在「任務層級」與「裝置能力」之間的對應更為直接，從而減少了不必要的介面導航開銷。

此外，論文提到「更低的設定負擔（Lower Setup Burden）」以及「追蹤記錄（Trace）」展示了執行邊界如何被應用。這說明 PalmClaw 不僅在效率與成功率上改善，也在可部署性與可解釋性上具備優勢。透過 Trace，開發者與使用者可以清楚看到每一個 Device Tool 被呼叫的時機、傳入引數、回傳結果以及是否觸發權限確認，這對於除錯與安全稽核非常重要。

不過，由於目前可取得的上下文未詳細說明實驗任務種類、基線名稱、LLM 後端、評分標準與樣本數，對於這些數字的絕對解讀仍須謹慎。例如，若測試任務本身高度依賴裝置能力（如檔案整理、訊息發送），則 Device Tool 的優勢會被放大；若任務主要是操作第三方 App 的複雜 GUI 流程，則提升幅度可能不同。

#### 與現有研究的比較

PalmClaw 在相關研究中處於一個介於「通用代理框架」與「行動代理」之間的位置。

相較於 **AutoGen**、**AgentScope**、**OpenClaw** 等通用框架，PalmClaw 的差異在於「部署位置」：這些框架通常將 Session、Memory、Skill、Tool 與 Agent Loop 託管於電腦或雲端伺服器，再透過網路與手機互動；PalmClaw 則把這些元件全部搬到行動裝置本地。這帶來幾個潛在優勢：更低的網路延遲、更接近使用者資料的運算位置、以及減少對外部主機的依賴。

在行動代理領域，現有研究如 **AndroidWorld**、**MobileAgentBench**、**Mobile-Bench**、**AgentCPM-GUI**、**Mobile-Agent-v3.5** 以及 **ApkClaw**、**MobileClaw**、**ClawMobile** 等，大多採用 GUI Action 作為主要操作方式。PalmClaw 明確指出這種方式的三大限制：

1. **長且介面依賴的動作序列**：高層級任務需要拆解成大量點擊、滑動等低階操作，對螢幕佈局變化極為敏感。
2. **無法直接存取裝置能力**：例如本地檔案、感測器資料等，GUI Action 只能透過間接方式操作。
3. **執行邊界難以定義**：GUI 控制賦予代理對可見介面的廣泛操作權限，難以針對特定任務限制其範圍。

PalmClaw 透過 Device Tool 同時回應了這三個問題：動作空間從「像素級手勢」提升為「能力級呼叫」、可直接使用裝置資源與感測器、並透過 Tool-Specific Execution Boundary 明確限制每個動作的權限範圍。

然而，這種設計也有其侷限。Device Tool 的覆蓋範圍取決於開發者事先實作了哪些工具；對於尚未被封裝的第三方 App 或新興服務，PalmClaw 可能無法像 GUI-based 代理那樣泛化。換句話說，PalmClaw 在「已知能力」上更高效、更可控，但在「未知介面」的通用性上可能不如純 GUI 方法。未來若能結合兩者——以 Device Tool 處理系統級與常用能力，以 GUI Action 作為後備機制——可能會是更穩健的方向。

#### 可重現性評估

從論文與提供的上下文來看，PalmClaw 在可重現性方面具備以下條件：

- **開放原始碼（Open-Source）**：論文明確指出 PalmClaw 是開源專案，並採用 AGPLv3 授權。原始碼與可安裝套件可於 https://github.com/ModalityDance/PalmClaw 取得。
- **可安裝套件**：內文提到 installable packages 已發布於 GitHub Releases，這降低了部署門檻。
- **追蹤記錄（Trace）**：論文提供 Trace 來說明執行邊界的應用方式，這對於理解系統行為與驗證結果具有幫助。

不過，可重現性仍存在一些未在現有上下文中充分說明的部分：

- **基準資料集（Benchmark Dataset）**：目前未清楚說明實驗使用的任務集合是否公開、是否提供標準測試腳本與評分器。
- **LLM 後端與模型權重**：論文未說明 PalmClaw 使用的基礎大型語言模型（Foundational LLM）是本地模型還是遠端 API。若使用商業 API，則結果的可重現性會受到模型版本、溫度參數與提示工程細節影響。
- **裝置環境**：不同 Android 版本、廠商客製化系統、權限管理行為可能影響 Device Tool 的執行結果，論文是否提供標準化測試環境說明尚不可知。
- **對照基線實作**：最強基線的具體名稱與設定未在提供的片段中出現，這會影響其他研究者比較與驗證 11.5% / 94.9% 數據的難度。

整體而言，PalmClaw 在「開源釋出」這一層已經達到不錯的可重現性基礎，但要達到完全可重現的學術標準，仍需要補充實驗設定、基準資料、LLM 配置與裝置環境等細節。

#### 未來研究方向

基於 PalmClaw 的設計與現有侷限，未來研究可以朝以下幾個方向延伸：

1. **擴充 Device Tool 生態系**：目前 Device Tool 的效用取決於工具覆蓋範圍。未來可以建立標準化的行動裝置工具註冊表（Tool Registry），讓第三方開發者能夠為不同 App 與系統服務貢獻新的 Device Tool，並統一引數與回傳 Schema。

2. **結合 GUI Action 作為後備機制**：為了兼顧 Device Tool 的效率與 GUI Action 的通用性，未來可以設計混合代理架構：當 Device Tool 無法完成任務時，自動降級為 GUI-based 操作，並在執行過程中學習將新的 GUI 流程封裝成新的 Skill 或 Device Tool。

3. **強化權限與執行邊界機制**：Tool-Specific Execution Boundary 是 PalmClaw 的重要特色，未來可以進一步研究如何根據使用者指令、裝置狀態與風險等級動態調整邊界，並在涉及敏感操作（如發送訊息、刪除檔案、存取位置）時引入更細緻的使用者確認機制。

4. **原生裝置端大型語言模型（On-Device LLM）整合**：目前 PalmClaw 的 Agent Loop 雖在裝置端執行，但 LLM Call 仍可能依賴遠端服務。未來可以探索與量化後的裝置端 LLM 結合，進一步降低延遲、保護隱私，並減少對網路連線的依賴。

5. **建立專屬評估基準**：現有行動代理基準多針對 GUI Action 設計。未來需要發展專門評估 Device Tool 導向代理的基準，涵蓋檔案管理、感測器使用、自動化流程、跨 App 協作等任務，並納入執行邊界、隱私洩漏與權限使用等評估維度。

6. **多代理與跨裝置協作**：PalmClaw 的 Session 與 Channel 設計已具備支援多輸入來源的潛力。未來可以研究多部行動裝置或多個代理之間的協作，例如手機代理與穿戴式裝置、智慧家居代理共同完成任務。

7. **能源效率與長時間運行**：在裝置端持續執行 Agent Loop 會消耗電量與運算資源。未來需要研究如何根據任務優先級、電量狀態與使用者行為模式，動態調整代理活躍度與記憶更新頻率。

## 論文問答

**Q1：現有以圖形使用者介面操作為主的行動代理存在哪些主要問題？**  
A：現有行動代理大多透過點擊、滑動、輸入等圖形使用者介面操作來控制智慧型手機，這會讓高層級任務被拆解成冗長且高度依賴介面佈局的動作序列，只要畫面稍有變化就容易失敗。此外，這種方式無法直接存取裝置資源與功能，例如本地檔案、相機、麥克風或位置資訊，限制了代理能執行的任務範圍。更重要的是，圖形使用者介面操作賦予代理過於廣泛的介面存取權限，缺乏針對特定工具的執行邊界，使得動作範圍難以明確界定與控管。

**Q2：為什麼要在行動裝置上原生執行代理，而不是依賴桌上型或雲端主機？**  
A：智慧型手機是全球最普及的個人運算裝置之一，能讓沒有持續使用個人電腦的使用者也能使用代理服務，顯著擴大潛在使用者群。其次，行動裝置儲存了大量高度個人化的資料，並配備相機、麥克風、位置等感測器，以及日常生活中頻繁使用的應用程式。將代理直接部署在裝置端，可以讓代理更貼近使用者、個人資料與日常所需能力，同時減少對外部主機的依賴與資料傳輸風險。

**Q3：PalmClaw 的設計動機與近期終端機原生代理的趨勢有何關聯？**  
A：近期如 Codex CLI、Claude Code、Gemini CLI 等終端機原生代理顯示，明確且可執行的工具式互動正成為主流，這促使作者思考在行動裝置上也應採用類似的原生裝置端設計。相較於圖形使用者介面操作的模糊與廣泛，工具呼叫能透過明確引數與結構化結果，讓每次動作都具備清楚的執行邊界。PalmClaw 因此將代理框架直接搬到手機上，並以裝置工具取代單純的畫面操作，實現更直接、可控的行動代理互動。

**Q4：PalmClaw 的核心架構包含哪些主要元件，它們如何協同運作？**  
A：PalmClaw 在行動裝置上原生託管代理迴圈、工作階段、記憶、技能與工具等核心元件，形成完整的裝置端代理框架。當使用者輸入複雜指令後，系統會在工作階段中組裝上下文，由代理迴圈呼叫大型語言模型進行推理，再根據需要呼叫裝置工具。工具呼叫會在裝置上經過檢查與執行，並將結構化結果回傳給代理迴圈，進入下一回合的迭代決策，直到任務完成。

**Q5：PalmClaw 提出的「裝置工具」與傳統圖形使用者介面操作有何本質差異？**  
A：裝置工具將行動裝置的資源與能力封裝成具有明確引數、結構化結果與工具特定執行邊界的可執行操作，而不是模擬使用者在螢幕上的手勢。這種設計讓每次動作都像應用程式介面呼叫一樣清晰可控，代理能直接讀取檔案、發送訊息或取得感測器資料，而無需繞過圖形介面。相較之下，傳統圖形使用者介面操作容易因介面變化而失效，且難以界定代理實際能觸及的範圍。

**Q6：PalmClaw 為何選擇以工具為中心的設計，而非強化圖形使用者介面動作空間？**  
A：因為圖形使用者介面動作雖然通用，卻會將高層級任務展開成大量低階、介面依賴的步驟，導致執行軌跡冗長且脆弱。工具導向的設計能讓代理直接利用裝置能力，例如檔案管理、媒體存取或網頁操作，並以結構化方式取得觀察結果。此外，每個裝置工具都有預先定義的執行邊界，能讓開發者與使用者更清楚知道代理正在做什麼、能觸及哪些資源，從而提升安全性與可解釋性。

**Q7：PalmClaw 在實驗中評估了哪些類型的任務，並與何種基準進行比較？**  
A：論文在具代表性的行動裝置任務上評估 PalmClaw，涵蓋需要直接存取裝置資源與能力的場景，例如檔案管理、訊息處理與自動化流程。實驗將 PalmClaw 與現有最強的基準方法進行比較，後者主要採用外部託管的圖形使用者介面操作方式。透過這樣的對照，作者能夠驗證原生裝置端工具框架在任務成功率與完成時間上的優勢。

**Q8：PalmClaw 實驗結果的主要數據為何，這代表什麼意義？**  
A：實驗顯示 PalmClaw 相較於最強基準，任務成功率相對提升了 11.5%，平均完成時間大幅減少 94.9%。這表示以裝置工具為核心的設計不僅能完成更多任務，還能顯著縮短執行所需的步驟與時間。此外，部署分析顯示 PalmClaw 的設定負擔更低，進一步降低使用者與開發者採用的門檻。

**Q9：論文如何透過追蹤記錄說明執行邊界的實際應用？**  
A：作者提供追蹤記錄來展示每次工具呼叫的輸入引數、執行範圍與回傳結果，清楚呈現代理在何處開始與結束某個裝置操作。這些追蹤記錄顯示裝置工具能將代理行為限制在特定功能與資料範圍內，避免無限制的圖形介面漫遊。透過這樣的分析，讀者可以具體理解執行邊界如何讓每個動作變得明確、可驗證且易於除錯。

**Q10：PalmClaw 在實際應用中適合哪些日常場景？**  
A：PalmClaw 特別適合需要結合個人資料與裝置能力的任務，例如自動整理本地檔案、根據行事曆與位置發送提醒、拍攝照片後自動分類或上傳，以及跨應用程式的工作流程自動化。由於代理直接運行在裝置端，這些任務可以在不依賴雲端的情況下快速完成。對於經常在外行動、沒有穩定電腦環境的使用者而言，這樣的原生裝置端代理能帶來更即時的協助。

**Q11：從產品化與部署角度來看，PalmClaw 有哪些值得注意的設計考量？**  
A：PalmClaw 以開放原始碼形式釋出，並提供可安裝套件，降低開發者整合與部署的門檻。由於核心代理元件與工具執行都在行動裝置上進行，能減少敏感資料離開裝置的機會，對隱私保護較為有利。不過，實際產品化仍需處理權限管理、裝置相容性與不同作業系統版本的工具實作差異，以確保穩定與安全的使用體驗。

**Q12：PalmClaw 對行動代理領域可能帶來什麼樣的影響？**  
A：PalmClaw 示範了將完整代理框架原生部署在行動裝置上的可行性，推動行動代理從「遠端控制螢幕」走向「裝置端工具化執行」。這不僅能讓更多沒有個人電腦的使用者享受到 LLM 代理的便利，也為未來結合個人資料、感測器與日常應用程式的智慧助理奠定基礎。若此模式被廣泛採納，行動裝置將從被動的應用程式載體轉變為能主動執行多步驟任務的智慧代理平台。

**Q13：PalmClaw 目前有哪些可能的限制或挑戰？**  
A：PalmClaw 的效能與功能範圍取決於已實作的裝置工具數量與品質，若某個應用程式或系統功能尚未被封裝成工具，代理就無法直接操作。此外，裝置工具需要取得相應的系統權限，權限被拒或設定不當都可能導致任務失敗。目前大型語言模型的推理呼叫可能仍須透過網路連線至遠端模型，這在無網路或注重完全離線的場景中會是一項限制。

**Q14：在哪些情況下 PalmClaw 可能會出現執行失敗？**  
A：當使用者指令與現有工具的模式或引數要求不符時，代理可能產生無效的工具呼叫，導致執行中斷。若目標應用程式的介面或資料格式發生變化，但對應的工具尚未更新，也可能出現結構化結果解析錯誤。另外，涉及多個未支援應用程式之間複雜互動的任務，由於缺乏圖形使用者介面後備機制，可能無法順利完成。

**Q15：未來可以從哪些方向進一步擴展 PalmClaw？**  
A：未來可以擴充更多裝置工具，涵蓋更廣泛的系統功能與第三方應用程式，並建立工具自動發現或生成機制。另一方面，整合完全在裝置端運行的大型語言模型，將能進一步強化隱私與離線執行能力。此外，結合有限的圖形使用者介面操作作為後備、發展多代理協作，以及設計更細緻的安全沙箱與執行邊界，也都是值得探索的後續方向。

## 實務應用指南

### 適用場景

1. **本地隱私優先的個人助理**  
   使用者可在智慧型手機上直接執行「整理相簿並依地點分類」「把錄音轉成逐字稿後存成筆記」等任務。由於 PalmClaw 的代理迴圈與裝置工具都在裝置端執行，敏感資料（照片、錄音、位置）不必上傳到雲端，適合醫療、法律或個人財務等隱私要求高的場景。

2. **現場作業與離線自動化**  
   外勤人員（維修、巡檢、物流）可在沒有穩定網路的環境中，透過裝置工具呼叫相機、麥克風、GPS 與本地檔案，完成「拍攝設備條碼 → 記錄位置 → 產生離線報告」等流程。原生裝置端執行讓任務不依賴遠端主機，降低網路延遲與斷線風險。

3. **智慧型手機上的可重複工作流程**  
   例如每日自動「擷取螢幕截圖 → 擷取關鍵數字 → 寫入工作區試算表 → 透過訊息工具傳送摘要」。PalmClaw 的技能（Skill）與工作階段（Session）機制可將這類多步驟任務模組化，並透過排程喚醒自動觸發。

4. **無障礙與長輩輔助操作**  
   將複雜的 GUI 操作序列封裝成高階裝置工具，例如「幫我打開視訊通話並調大音量」，讓使用者用自然語言完成原本需要多次點擊、滑動的動作，減少對介面佈局變化的依賴。

5. **邊緣裝置與 IoT 閘道整合**  
   以智慧型手機作為輕量邊緣代理，透過藍牙、NFC、本地網路或 USB 連接感測器與其他裝置，執行「讀取環境數據 → 本地判斷 → 觸發自動化」的閉環任務，例如智慧家庭場景控制或穿戴式裝置資料彙整。

### 實作步驟建議

1. **環境建置與安裝**  
   從 PalmClaw 的 GitHub Releases 下載安裝包，部署到目標智慧型手機；確認裝置可正常啟動代理迴圈，並能連線至所選 LLM（本地模型或遠端 API）。

2. **定義核心裝置工具**  
   針對目標任務，將裝置能力封裝為裝置工具：例如 `take_photo()`、`read_location()`、`send_message()`、`write_file()`。每個工具需包含明確引數、結構化結果與執行邊界（如僅能寫入工作區、僅能傳送給已授權聯絡人）。

3. **設計技能與工作階段流程**  
   把常見任務抽象為可重複使用技能，例如「會議紀錄整理」或「每日報告產生」。設定工作階段（Session）以區隔不同任務，並配置長期記憶與每回合摘要，讓代理能跨回合保留上下文。

4. **權限與安全策略配置**  
   在 Android 系統層授予必要權限，並在 PalmClaw 內設定工具特定執行邊界：例如相機工具僅在前景執行、檔案工具僅能存取專屬工作區、網頁工具需經使用者確認後才能送出表單。

5. **本機測試與追蹤記錄分析**  
   在受控環境中執行代表性任務，收集追蹤記錄（Trace），檢查每個工具呼叫的輸入、輸出與邊界觸發情況。比較任務成功率與完成時間，找出瓶頸工具或容易失敗的步驟。

6. **迭代優化與產品化封裝**  
   根據測試結果調整工具 Schema、提示詞與執行邊界；將穩定的技能打包為預設模板，並加入錯誤處理、重試機制與使用者確認對話框，再發布給終端使用者。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **過度權限與隱私外洩** | 原生裝置端代理可直接存取相機、麥克風、位置與個人資料，一旦權限過大，可能導致資料被不當讀取或傳輸。 | 採用最小權限原則，為每個裝置工具設定執行邊界；敏感操作加入使用者確認；敏感資料優先留在工作區內。 |
| **模型幻覺導致錯誤動作** | LLM 可能產生不存在或引數錯誤的工具呼叫，進而引發非預期行為（例如傳錯訊息、刪錯檔案）。 | 嚴格驗證工具 Schema 與引數範圍；對破壞性操作（刪除、傳送、購買）強制二次確認；保留完整追蹤記錄供稽核。 |
| **GUI 相容性與系統更新** | 雖然 PalmClaw 以裝置工具取代部分 GUI 操作，但仍可能依賴系統 API 與應用程式版本，Android 更新後可能出現行為差異。 | 建立裝置與系統版本矩陣測試；將依賴特定應用程式的操作封裝為獨立工具，降低耦合。 |
| **電池與效能消耗** | 持續執行代理迴圈與 LLM 推理會增加耗電與發熱，影響使用者體驗。 | 使用排程喚醒而非持續輪詢；在充電或 Wi-Fi 環境下執行重型任務；評估裝置端模型量化與快取策略。 |
| **執行邊界難以完整定義** | 某些高階任務的邊界模糊，可能讓代理在「完成任務」與「過度干預」之間難以拿捏。 | 與使用者共同定義任務範圍；在技能層級設定終止條件；提供隨時中斷與回復機制。 |

### 與其他技術的整合建議

- **與現有 Android 應用程式整合**  
  透過 Android Intent、Content Provider 與系統服務，讓 PalmClaw 的裝置工具呼叫相機、日曆、聯絡人、簡訊等原生應用程式；對於第三方 App，可透過其公開的 URL Scheme 或輔助功能服務（Accessibility Service）進行有限互動，但需特別注意權限與穩定性。

- **與雲端或企業後端同步**  
  雖然代理迴圈在裝置端執行，但可設計「同步工具」在必要時將去識別化後的結構化結果上傳至企業後端、雲端儲存或協作平台（如 Slack、Notion、企業 LINE）。建議採用端對端加密與差異同步，減少頻寬與隱私風險。

- **與 RAG / 知識庫結合**  
  將長期記憶與裝置端向量資料庫（如 sqlite-vss、ONNX Runtime）整合，讓代理能根據本地文件、過往對話與個人知識進行檢索增強生成（RAG），適合個人筆記、維修手冊或產品規格查詢。

- **與 MLOps / 模型管理流程整合**  
  若使用裝置端輕量模型，需建立模型版本管理、A/B 測試與遠端更新機制；若使用雲端 LLM API，則需監控 Token 使用量、延遲與錯誤率，並設計降級方案（fallback 到本地模型或提示使用者）。

- **與 MDM / 企業行動管理整合**  
  在企業場景中，可透過行動裝置管理（MDM）統一部署 PalmClaw、預載技能、限制可使用的裝置工具清單，並集中收集稽核日誌，確保符合企業資安政策。
