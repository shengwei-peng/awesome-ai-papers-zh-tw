## ⚡ TL;DR

單純把執行時間加入獎勵會因雜訊與稀疏性導致強化學習失敗。
本文提出三階段框架：建構DMC-Optim與校準沙箱、設計正確性與速度獎勵組合，並調整GRPO。
Qwen7B與CWM32B的top-50%pass@1分別升至31.3%與50.4%，正確性未下降。

## 摘要翻譯

針對程式碼正確性（Code Correctness）的強化學習（Reinforcement Learning, RL）現已確立：讓模型生成程式，針對隱藏測試案例（Hidden Test Cases）執行，並對通過的解答給予獎勵（Reward）。將此方法延伸至程式碼最佳化（Code Optimization）看似簡單：只需將執行時間（Execution Time）納入獎勵。然而在實務中，一旦計時主導獎勵，測量雜訊（Measurement Noise）、獎勵稀疏性（Reward Sparsity）或群組相對策略最佳化（GRPO）不穩定性等細微問題便會淹沒訊號，導致強化學習失敗：生成的解答幾乎沒有更快，且更多解答反而可能失敗。我們透過三個階段使執行時間變得可學習：（1）如何測試程式碼，透過建構包含大型最佳化測試資料集與校準沙箱（Calibrated Sandbox）的 DMC-Optim；（2）如何將速度轉換為獎勵，透過在強化學習環境（RL Environment）中組合正確性與速度，並使用離線模擬器（Offline Simulator）預測最有前景的配置（Most Promising Configurations）；（3）模型如何從該獎勵中學習，透過調整 GRPO 與評估（Evaluation）方式以適應更稀疏、更雜訊的計時執行設定（Timed-Execution Setting）。在 DMC-Optim 上，最強的最佳化感知配置將 Qwen 2.5 7B 的嚴格 top-50% pass@1 從 18.0% 提升至 31.3%，並將 CWM 32B 從 30.7% 提升至 50.4%。這些提升在更嚴格的百分位數（例如 top-30%）更為顯著，CWM 32B 的相對改進（Relative Improvement）達到 125%，同時維持純正確性分數（Pure-Correctness Score）。當計時沙箱退化時，穩健最佳化強化學習（Robust Optimization RL）相較於可驗證獎勵的標準強化學習（Standard RLVR）可達到 100% 至 200% 的相對改進，視評估準則（Evaluation Criterion）而定。在 LCB 上，CWM 32B 在中位樣本速度比較（Median-Sample Speed Comparison）中相較於標準 RLVR 贏得高達 83%。相較於每題最快正確的人類提交（Fastest Correct Human Submission），其複雜度類別改進率（Rate of Complexity-Class Improvements）約達人類的一半（14% 對 28%）。

### 核心貢獻（3～5點）
- 建構 DMC-Optim 大型最佳化測試資料集與校準沙箱，解決程式碼最佳化在測量與評估上的基礎設施問題。
- 提出獎勵組合（Reward Composition）與離線模擬器機制，將正確性與執行時間有效整合為可學習的獎勵訊號。
- 針對計時執行設定的稀疏與雜訊特性，調整 GRPO 訓練與評估流程，提升強化學習在程式碼最佳化任務上的穩定性。
- 在 Qwen 2.5 7B 與 CWM 32B 上顯著提升嚴格 top-50% 與 top-30% pass@1，且未犧牲純正確性分數。
- 提出穩健最佳化強化學習，在計時沙箱退化情境下仍能大幅優於標準 RLVR，展現對測量雜訊的強健性。

### 適合對象
本論文適合對大型語言模型（LLM）程式碼生成、強化學習（RL）、程式碼最佳化、競技程式設計（Competitive Programming）以及獎勵設計有興趣的研究人員與工程師。特別是關注如何將執行時間效率納入 RL 訓練、處理獎勵稀疏性與測量雜訊，以及希望建構高品質程式碼效率評估基準的讀者，將能從本文的資料集、方法與實驗洞察中獲益。

## 深度分析

#### 方法論解析

本研究的核心命題是：在程式碼正確性（code correctness）已經可以透過可驗證獎勵的強化學習（Reinforcement Learning with Verifiable Rewards, RLVR）有效學習的前提下，為何直接將執行時間（execution time）納入獎勵（reward）會導致訓練失敗？作者將失敗歸因於一條「轉換鏈」（chain of transformations）：計時來源（timing source）必須能區分解答、強化學習環境（RL environment）與獎勵組合（reward composition）必須正確權衡正確性與速度、而最佳化器（optimizer）必須在更稀疏且雜訊更大的訊號下保持穩定。為此，論文提出三階段方法論：測試建構、獎勵設計、以及模型學習。

##### 1. 可學習的計時來源：DMC-Optim 與校準沙箱（calibrated sandbox）

作者從 DeepMind Code Contests（DMC）語料庫中篩選出 2,723 道清理過的問題，建構成 DMC-Optim 資料集，並將測試案例（test cases）區分為兩類：

- **正確性測試（correctness tests）**：用於驗證程式輸出是否正確。
- **最佳化測試（optimization tests）**：專門設計為較大輸入規模，執行時間（runtime）更長，以便區分不同演算法複雜度（complexity-class）的實作。

DMC-Optim 共新增 430,215 筆正確性測試與 352,740 筆最佳化測試，其中 1,302 道問題具有足夠的執行時間離散度（duration spread），適合作為以時間為基礎的獎勵來源。為了降低計時雜訊（timing noise）與沙箱飄移（sandbox drift）的影響，作者採用遠端校準執行服務（remote calibrated execution service, CES）作為計時沙箱（timing sandbox），相較於本地沙箱（local sandbox）能提供更穩定的測量訊號。這一步是整個方法的基礎：若測試本身無法區分快慢程式，後續的獎勵設計與策略學習都無從談起。

##### 2. 強化學習環境與獎勵組合

作者將過去文獻中零散的執行限制整理為三大環境家族，並提出新的組合形式：

- **執行前過濾（pre-execution filtering）**：在執行程式前，依據絕對或相對準則篩選要納入的最佳化測試，避免測試過難（too hard）、過易（too easy）或區分度太平（too flat）。
- **執行中限制（intra-execution constraints）**：對每筆測試設定時間限制（time limit），並決定使用本地或遠端沙箱執行。
- **執行後排名（post-execution ranking）**：將測得的執行時間與每題的人類參考解答（human reference）分布比較，產生品質分數 q（quality score）。

執行後會產生三個訊號：

- 正確性閘門 c（correctness gate）：是否通過所有正確性測試，值域為 0–1。
- 最佳化閘門 g（optimization gate）：是否通過最佳化測試與時間限制，值域為 0–1。
- 品質分數 q（quality score）：依據與人類參考排行榜（human reference leaderboard）的排名比較，將執行時間轉換為純量分數。

這三個訊號再透過不同的獎勵組合（reward composition）形成最終獎勵，包括：

- **純最佳化獎勵（optimization-only reward）**
- **加權相加混合（additive blend）**：例如 r = α·c + β·g + γ·q
- **多工獎勵（multitask reward）**
- **折疊獎勵（collapsed reward）**
- **硬閘門獎勵（hard-gated reward）**：只有在正確性閘門與最佳化閘門都通過時，才給予速度相關獎勵，避免模型被誘導產生快但錯誤的程式碼（fast-but-wrong code）。

作者特別強調，**獎勵設計必須避免讓模型從「錯誤但快速」的程式中獲得優勢**。這是樸素最佳化訓練目標（naive optimization training objective）失敗的主因之一：若僅在二元正確性獎勵上加上平均執行時間獎勵，模型可能為了降低執行時間而犧牲正確性，或因測量雜訊而無法穩定學習。

##### 3. 離線模擬器（offline simulator）篩選配置

由於線上 GRPO 訓練需要大量 GPU 資源（8–32 GPU nodes × hours），直接對所有環境與獎勵配置進行網格搜尋不可行。作者因此建立離線模擬器（offline simulator），使用人類解答與預先儲存的執行時間（stored durations），在相同的環境程式路徑（same env code path）上重播（replay）並評估各種環境–獎勵配對。模擬器會將配置標記為「過難」、「過易」或「過於平坦」，並以 AUC 等指標挑選最有前景的配置（most promising configurations），再啟動真正的線上 GRPO 訓練。這大幅降低了實驗成本，也讓方法更具可擴展性。

##### 4. 適應稀疏計時獎勵的 GRPO

標準 RLVR 的獎勵是二元通過／失敗，訊號相對密集；而計時執行設定（timed-execution setting）下的獎勵則更為稀疏且雜訊更大。作者針對 GRPO（Group Relative Policy Optimization）進行調整，包括：

- 使用群組相對優勢估計（advantage estimate），例如 A_i = R_i − µ_x，其中 µ_x 為同一提示（prompt）下各樣本（sample）獎勵的平均值。
- 調整每個提示的樣本數（samples per prompt）與批次大小（batch size），以穩定稀疏訊號下的梯度估計。
- 在評估階段採用 p_τ 指標：解答必須正確，且執行時間不慢於人類參考排行榜的第 τ 百分位數（τ-th percentile），才計入通過。

這些調整讓 GRPO 在「正確性與速度耦合」的獎勵下仍能保持穩定更新。

#### 實驗數據解讀

論文在 DMC-Optim 與 LiveCodeBench（LCB）兩個場景進行評估，並使用嚴格的 p_τ pass@1 指標：解答必須同時正確且速度達到人類參考的第 τ 百分位。

##### DMC-Optim 上的主要結果

| 模型 | 基線 p50 pass@1 | 最佳化 RL p50 pass@1 | 基線 p30 pass@1 | 最佳化 RL p30 pass@1 |
|---|---|---|---|---|
| Qwen 2.5 7B | 18.0% | 31.3% | — | — |
| Qwen 2.5 32B | 21.1% | 39.6% | — | — |
| CWM 32B | 30.7% | 50.4% | 13.7% | 30.9% |

數據顯示幾個重要現象：

1. **絕對增益顯著**：CWM 32B 在 p50 從 30.7% 提升至 50.4%，Qwen 2.5 7B 也從 18.0% 提升至 31.3%。這代表在適當的測試、環境與獎勵設計下，執行時間訊號確實可被學習。
2. **越嚴格的百分位，相對改進越大**：CWM 32B 在 p30 的相對改進（relative improvement）高達 125%（從 13.7% 到 30.9%）。這說明方法不僅能讓程式「稍微快一點」，而是能推動演算法複雜度類別（complexity-class）層級的改進。
3. **純正確性分數（pure-correctness score）保持穩定**：這是關鍵——最佳化並未以犧牲正確性為代價。若獎勵設計不當，常見的副作用是程式變快但錯誤率上升；此處並未觀察到此現象，顯示硬閘門與正確性閘門的設計有效。

##### 沙箱退化下的穩健性

作者進一步將計時沙箱（timing sandbox）設定為「退化狀態」（degraded sandbox state），模擬測量雜訊更高或資源更不穩定的情境。結果顯示，穩健最佳化強化學習（robust optimization RL）相較於標準 RLVR（standard RLVR）可達到 **100%–200% 的相對改進**，依評估準則（evaluation criterion）而異。這驗證了方法在現實部署中面對不穩定執行環境時的實用價值。

##### LCB 上的泛化能力

在 LCB 上，由於 timeout 與 percentile 分數不可靠，作者改採**中位樣本速度比較（median-sample speed comparison）**：比較兩種方法在同一問題上產生的樣本誰更快。結果顯示 CWM 32B 相較於標準 RLVR 的勝率高達 **83.0%**，同時仍維持 54.4% 的 pass@1。這表示 DMC-Optim 上學到的最佳化行為能泛化到另一個競技程式設計（competitive programming）基準，而非僅是過擬合（overfit）於 DMC-Optim 的測試分布。

##### 與人類專家的差距

相較於每題最快正確人類提交（fastest correct human submission），CWM 32B 的複雜度類別改進率（rate of complexity-class improvements）約為人類的一半（14% vs. 28%）。這說明雖然方法已能顯著提升模型速度，但在演算法層級的創新能力上仍遜於頂尖人類程式設計者。這也為後續研究保留了明確的改進空間。

#### 與現有研究的比較

##### 定位

本研究處於「程式碼強化學習」與「程式碼效率最佳化」的交會點。現有 RLVR 研究大多將執行視為二元驗證器（binary verifier）：程式通過隱藏測試案例（hidden test cases）就給獎勵，失敗則不給。這種設定在程式碼正確性（code correctness）上已相當成功，但無法引導模型產生更快的程式。

另一方面，軟體工程效率基準（如 SWE-efficiency）與競技程式設計效率指標（如 Venus 的 Beyond-T、BigO(Bench)）已顯示出當前大型語言模型（LLM）在速度上遠不如人類。例如 Claude 4.5 Sonnet 在 SWE-efficiency 上正確率高達 81%，但只捕捉到 4.1% 的專家加速比（expert speedup）；o4-mini 在 Venus 上 pass@1 達 89.1%，但 Beyond-T 僅 56.9%。這些研究指出了問題，但並未系統性地提出讓執行時間成為可學習訊號的方法。

##### 相較於既有方法的主要改進

1. **系統性地將執行時間訊號變得可學習**：過去研究多將「速度」視為次要的評估指標，本研究則從資料建構、沙箱校準、環境設計到獎勵組合，完整處理了計時雜訊、獎勵稀疏性（reward sparsity）與 GRPO 不穩定性（GRPO instability）等問題。
2. **提出三大家族環境設計框架**：將執行前過濾、執行中限制、執行後排名系統化，並與多種獎勵組合進行比較。這種結構化分類有助於未來研究在此基礎上擴展。
3. **離線模擬器降低實驗成本**：不同於直接進行昂貴的線上 GRPO 網格搜尋，作者利用人類參考解答（human reference）與儲存執行時間進行離線篩選，這是一個可重複且可擴展的方法論貢獻。
4. **證明正確性與速度可同時提升**：許多樸素最佳化目標會導致正確性下降，而本研究在提升 p_τ 的同時維持純正確性分數，顯示出獎勵設計的穩健性。

##### 限制

1. **領域侷限於競技程式設計**：雖然競技程式設計提供了一個控制良好的研究場域，但真實世界軟體工程（如 SWE-efficiency）涉及更複雜的程式庫、I/O、並行與系統層級最佳化，方法是否能直接遷移仍需驗證。
2. **依賴人類參考分布**：p_τ 與執行後排名都需要每題的人類參考排行榜。對於缺乏足夠人類提交的新問題或私有題目，此方法可能難以直接套用。
3. **複雜度類別改進仍不及人類**：14% vs. 28% 顯示模型尚未能穩定地進行演算法層級的創新，更多是在既有實作範圍內調整。
4. **計時雜訊無法完全消除**：即使在校準沙箱下，測量雜訊仍然存在，只是被控制在可學習的範圍內。

#### 可重現性評估

##### 資料與模型權重

- **DMC-Optim 資料集**：論文說明是從 DeepMind Code Contests（DMC）語料庫建構而來。DMC 原始資料已公開，但作者新增的 430,215 筆正確性測試與 352,740 筆最佳化測試、以及清理後的 2,723 道問題，目前從提供的文本中無法確認是否已開源。
- **模型**：Qwen 2.5 7B/32B 基礎檢查點（base checkpoints）已公開；CWM 32B 的 SFT 檢查點（released CWM 32B SFT checkpoint）也已釋出。這部分相對容易取得。
- **校準沙箱與遠端執行服務（CES）**：論文未詳細說明是否開放原始碼或提供 API，這是重現結果的關鍵瓶頸之一。

##### 方法細節

論文提供了高階方法論與圖示，但部分實作細節在提供的文本中仍不完整：

- 各種獎勵組合（additive blend、multitask、collapsed、gated）的確切數學公式與超參數（α、β、γ 等）。
- 離線模擬器的具體評分函數與篩選閾值。
- GRPO 調整的詳細配方，例如學習率、KL 懲罰、群組大小、樣本數、獎勵標準化方式等。
- 沙箱校準的具體流程，包括如何測量與修正沙箱飄移。

##### 整體評估

目前可重現性處於**中等偏低**水準：研究問題與方法論描述清楚，基礎模型可取得，但核心資料集、沙箱程式碼、獎勵實作與訓練腳本是否公開尚不明朗。若作者能釋出 DMC-Optim、離線模擬器程式碼、以及 GRPO 訓練配方，將大幅提升社群重現與延伸此研究的能力。

#### 未來研究方向

1. **擴展到真實軟體工程場景**：將方法從競技程式設計（competitive programming）遷移到 SWE-efficiency 等儲存庫層級任務，處理函式呼叫、資料結構選擇、快取策略與 I/O 瓶頸等更複雜的最佳化問題。
2. **降低對人類參考分布的依賴**：發展無需人類參考排行榜（human reference leaderboard）的獎勵設計，例如透過模型自身產生的解答進行相對排名，或利用形式化複雜度分析作為輔助訊號。
3. **多目標與安全導向的最佳化**：除了執行時間，同時納入記憶體使用量、能源消耗、可讀性與維護性等目標，並確保在追求速度時不犧牲安全性與正確性。
4. **更細緻的執行時間建模**：利用程式分析（profiling）或執行追蹤（execution tracing）產生更密集的獎勵訊號，而非僅依賴最終執行時間。
5. **跨平台與硬體感知最佳化**：考慮不同 CPU/GPU、編譯器最佳化層級（如 O1/O2/O3）與執行環境對計時的影響，發展硬體感知的獎勵正規化方法。
6. **提升複雜度類別改進率**：結合搜尋演算法、形式化驗證與大規模預訓練，讓模型能更頻繁地發現演算法層級的改進，逐步逼近人類的 28% 複雜度類別改進率。
7. **自動化測試生成與環境配置**：讓離線模擬器（offline simulator）不僅篩選配置，還能主動生成更具區分力的最佳化測試（optimization tests），形成自我改進的迴路。
8. **LLM-as-a-judge 與混合獎勵**：探索使用大型語言模型作為演算法效率的評判者，與執行時間訊號互補，特別是在測量不可靠或無法執行的情境下。
9. **可解釋的最佳化決策**：研究模型為何選擇特定最佳化策略，並開發工具解釋速度提升來自於資料結構改變、迴圈展開、還是演算法複雜度降級。
10. **開源基礎設施**：建立公開的 DMC-Optim、校準沙箱與標準化 RLVR-for-optimization 訓練框架，讓社群能在此基礎上進行公平比較與後續創新。

## 論文問答

**Q1：這篇論文核心要解決的問題是什麼？**
A：這篇論文指出，現有的程式碼大型語言模型即使透過強化學習訓練到很高的正確率，產出的程式仍然常常不夠快。無論是在 SWE-efficiency、Venus 還是 BigO(Bench) 等基準測試上，正確性分數與執行時間效率分數之間都存在明顯落差。因此，作者要解決的核心問題是：如何讓「執行時間」成為一個可被強化學習穩定學習的訊號，而不只是二元正確性獎勵的附屬品。

**Q2：為什麼現有的可驗證獎勵強化學習（RLVR）無法直接套用到程式碼最佳化？**
A：標準 RLVR 的執行回饋本質上是二元驗證器，只告訴模型程式對或錯；一旦把執行時間加入獎勵，就會引入計時雜訊、獎勵稀疏性以及 GRPO 不穩定性等問題。微小的執行時間差異很容易被測量雜訊淹沒，而且獎勵設計稍有不慎就會讓「快但錯誤」的程式獲得不當加分。結果是，直接把平均執行時間疊加到正確性獎勵上的樸素目標，幾乎無法提升速度，甚至還可能損害正確性。

**Q3：這個問題為什麼重要？**
A：在實際應用中，程式必須同時正確且高效，否則會造成服務延遲、運算成本上升與使用者體驗下降。多個基準測試都顯示，目前模型離人類專家在執行時間效率上的表現還有很大差距，例如 Claude 4.5 Sonnet 在 SWE-efficiency 上只捕捉到 4.1% 的專家加速比。若能讓模型透過強化學習自動學會寫出更快的程式，將對競技程式設計、軟體工程與生產環境部署都有重大價值。

**Q4：論文提出的核心方法是什麼？**
A：作者提出一個三階段框架，分別處理「如何測試程式碼」、「如何把速度轉換成獎勵」以及「模型如何從這個獎勵中學習」。首先建立 DMC-Optim 資料集與校準過的計時沙箱，將正確性測試與大型最佳化測試分開；接著設計多種正確性與速度的獎勵組合，並透過離線模擬器篩選最有前景的配置；最後調整 GRPO 訓練與評估流程，使其適應更稀疏、更嘈雜的計時執行環境。

**Q5：這個方法有哪些關鍵創新？**
A：關鍵創新包括把正確性測試與最佳化測試分離、針對每個測試將執行時間與人類參考解答的分布進行排名比較，以及引入離線 RL 模擬器來預測環境與獎勵配置的效果。此外，論文系統化地比較了加法混合、多工、折疊與硬閘門等多種獎勵組合，並針對計時獎勵調整 GRPO。這些設計共同把原本難以學習的執行時間訊號，轉換成穩定的策略梯度訊號。

**Q6：RL 環境中有哪些重要的設計選擇？**
A：論文把環境設計分為三大類：執行前的測試篩選、執行中的時間限制，以及執行後與人類參考解答的排名比較。這些選擇會與獎勵組合產生交互作用，例如硬閘門可以防止快但錯誤的程式獲得獎勵，而加法混合則可能讓速度訊號被正確性訊號稀釋。離線模擬器會在正式線上訓練前，先評估各種環境與獎勵配對的表現，從而找出最穩定的配置。

**Q7：實驗使用了哪些資料集與基準測試？**
A：論文建構了 DMC-Optim，從 12,275 個原始 DeepMind Code Contests 題目清理出 2,723 道題目，並新增 430,215 個正確性測試與 352,740 個最佳化測試，其中有 1,302 道題目的執行時間分布足以支撐計時獎勵。此外也在 LiveCodeBench（LCB）上進行跨域評估，並以人類參考排行榜作為 p_τ 評估的依據。這樣的設計讓研究能在控制良好的競技程式設計環境中，隔離最佳化強化學習失敗的原因。

**Q8：論文報告了哪些關鍵量化結果？**
A：在 DMC-Optim 的嚴格 top-50% pass@1 上，Qwen 2.5 7B 從 18.0% 提升到 31.3%，CWM 32B 從 30.7% 提升到 50.4%；在更嚴格的 top-30% 上，CWM 32B 相對提升了 125%，從 13.7% 達到 30.9%，同時純正確性分數保持穩定。在 LCB 上，CWM 32B 在中位樣本速度比較中對標準 RLVR 的勝率高達 83.0%，並維持 54.4% 的 pass@1。

**Q9：消融實驗與穩健性研究顯示了什麼？**
A：論文發現，單純把平均執行時間加到二元正確性獎勵上的樸素目標，在 p_30 只讓 pass@1 變動 +0.6 個百分點，在 p_100 則介於 -0.3 到 +1.4 之間，幾乎等同於沒有最佳化效果。當計時沙箱被人為劣化時，穩健最佳化強化學習相較於標準 RLVR 仍能帶來約 100% 到 200% 的相對改進，視評估準則而定。離線模擬器也能有效篩選出適合線上 GRPO 訓練的配置，避免直接進行昂貴的線上實驗。

**Q10：這項研究有哪些實際應用場景？**
A：這項技術可應用於任何對執行時間敏感的程式碼生成場景，例如競技程式設計、後端服務、資料處理管線與嵌入式系統。它不僅能讓模型產出「可以跑」的程式，還能引導模型自動選擇更高效的演算法與實作方式。更廣泛來說，這個框架也適用於其他具有可驗證回饋且需要最佳化連續品質指標的任務。

**Q11：若要在產品中落地，需要考慮哪些因素？**
A：首先需要一個低飄移、經過校準的計時沙箱，並準備足夠大的最佳化測試，否則測量雜訊會迅速腐蝕獎勵訊號。其次，獎勵設計必須避免誘導模型產出快但錯誤的程式，因此需要正確性閘門與人類參考分布來把關。最後，產品團隊還需持續監控沙箱狀態，並根據實際使用者對延遲的要求調整評估百分位門檻。

**Q12：這項研究對整個領域可能帶來什麼影響？**
A：它為「如何在 RLVR 中學習執行時間」建立了一套系統化的方法論，讓研究者不再只停留在二元正確性獎勵。DMC-Optim 提供了一個控制良好的程式碼最佳化研究基準，有助於後續比較不同方法。而環境、獎勵與最佳化器協同設計的思路，也可以推廣到其他具有嘈雜連續獎勵的可驗證任務。

**Q13：論文承認了哪些限制？**
A：儘管有顯著進步，CWM 32B 在複雜度類別改進率上仍只有人類的一半左右（14% 對比 28%）。此外，整個方法依賴校準沙箱與人類參考解答的執行時間分布，這些資源在某些領域可能不易取得。研究也主要聚焦於競技程式設計風格的問題與最大 32B 的模型規模，尚未涵蓋倉庫級軟體工程等更複雜場景。

**Q14：這個方法在哪些情況下可能會失敗？**
A：當沙箱嚴重劣化或最佳化測試太弱時，計時訊號會變得不可靠，最佳化效果也會大幅下降。如果獎勵設計不當，例如過度強調速度而忽略正確性閘門，模型可能學會投機取巧，產生快但錯誤的程式。另外，對於不同解答之間執行時間差異很小的題目，計時獎勵過於稀疏，模型也難以從中學到有意義的最佳化方向。

**Q15：未來可以朝哪些方向延伸？**
A：未來可以將這個框架擴展到倉庫級軟體工程最佳化，並同時考慮記憶體、能耗與延遲等多目標權衡。另一個方向是發展線上沙箱校準與自適應獎勵塑形技術，讓系統能隨環境變化自動調整。此外，結合更大的模型規模、更強的測試生成方法，以及將經驗應用到其他可驗證最佳化任務，也都是值得探索的後續研究。

   對於延遲敏感的關鍵路徑程式碼，可利用計時執行設定與校準沙箱，讓 RL 模型在保證正確性的前提下，學習降低執行時間與記憶體佔用。

3. **雲端函式與 Serverless 成本最佳化**  
   在 AWS Lambda、Cloud Functions 等按執行時間與記憶體計費的場景，可將「正確通過測試」與「縮短執行時間」組合成獎勵，自動生成更省成本的程式碼變體。

4. **資料處理管線與 ETL 作業**  
   針對大規模資料轉換、排序、聚合等批次作業，可建立大型最佳化測試（optimization tests）與人類參考解答的執行時間分布，訓練模型產生複雜度類別更優的實作。

5. **嵌入式與邊緣裝置程式碼**  
   在資源受限裝置上，可透過穩健最佳化強化學習（robust optimization RL）在計時雜訊較大的硬體沙箱中，仍持續產生更快且正確的程式碼。

### 實作前置條件

**資料前提**
- 一組已清理的程式設計題目與對應的**正確性測試**（correctness tests），數量需足以區分對錯。
- 額外建構的**最佳化測試**（optimization tests）：輸入規模更大、執行時間更長，能拉開不同複雜度類別解答的時間差距。
- **人類參考解答**及其在每個測試上的執行時間分布，用於計算 pτ 百分位門檻與後執行排名（post-execution ranking）。
- 測試案例需與訓練/驗證資料去汙染（decontaminated），避免資料洩漏。

**運算前提**
- **RL 訓練**：論文使用 8–32 個 GPU 節點 × 數小時，建議至少具備多卡 A100/H100 叢集與高速互連。
- **沙箱執行**：需要穩定的 CPU 執行環境（local sandbox 或校準過的 remote execution service），並能重複測量執行時間。
- **離線模擬**：1 CPU × 數分鐘即可篩選大量環境–獎勵配置，但需預先儲存人類解答與測量時間。

**技能前提**
- 熟悉強化學習基礎，尤其是 GRPO 與優勢估計。
- 能建構與維護隔離執行沙箱（sandbox）與測試基礎設施。
- 具備競技程式設計或演算法複雜度分析經驗，以設計有效的最佳化測試與評估指標。
- 熟悉 MLOps：實驗追蹤、模型版本管理、A/B 測試與線上監控。

### 實作步驟建議

1. **建構資料集與校準計時沙箱**  
   參考 DMC-Optim 的做法，從現有題庫清理出 2,000+ 題目，分離正確性測試與最佳化測試，並為每題建立人類參考執行時間分布。部署**校準過的沙箱**（calibrated sandbox），定期偵測沙箱飄移（sandbox drift），必要時使用遠端校準執行服務降低雜訊。

2. **設計 RL 環境的三階段壓力注入點**  
   - **執行前（pre-execution）**：依絕對或相對條件篩選要執行的最佳化測試，避免過難或過易的測試淹沒訊號。  
   - **執行中（intra-execution）**：設定每個測試的時間限制（time limit），將超時視為最佳化閘門（optimization gate）失敗。  
   - **執行後（post-execution）**：將測得的執行時間與人類參考排行榜比較，產生品質分數 q，再與正確性閘門 c 組合。

3. **用離線模擬器篩選環境–獎勵配置**  
   在啟動昂貴的線上 GRPO 訓練前，先以離線 RL 模擬器（offline simulator）回放人類解答與儲存的執行時間，評估不同配置（pre/intra/post 組合 × 獎勵組合）的 AUC 與訊號強度，挑出最有前景的配置。

4. **選擇穩健的獎勵組合並啟動線上 GRPO**  
   避免單純「正確性 + 平均執行時間」的樸素目標。建議採用**閘門縮放組合**（gate scale combination）或 hard-gated 變體：先確保 c = 1，再根據 g 與 q 給予速度獎勵。針對稀疏且雜訊大的計時獎勵，調整 GRPO 的批次大小、優勢估計與採樣策略。

5. **以嚴格指標評估，不只純正確性**  
   使用 pτ（正確且執行時間不慢於第 τ 百分位）作為主要指標，同時追蹤純正確性分數（pure-correctness score）以確保沒有犧牲正確性。在 LCB 等不穩定基準上，可改採**中位樣本速度比較**（median-sample speed comparison）等成對指標。

6. **部署與持續監控**  
   將訓練好的模型接入 CI/CD 或程式碼建議工具，對產出的程式碼進行沙箱計時驗證。持續監控沙箱狀態、獎勵分布與正確性回歸，並定期以新題目與新的人類參考解答重新校準。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **計時雜訊與沙箱飄移** | 執行時間受 CPU 負載、背景程序影響，導致獎勵訊號不穩定。 | 使用校準遠端沙箱、多次測量取中位數、定期校正參考分布。 |
| **獎勵駭入：快但錯誤的程式碼** | 模型可能發現捷徑，用錯誤但超快的程式騙取速度獎勵。 | 將正確性閘門 c 設為必要條件；速度獎勵僅在 c = 1 時發放。 |
| **獎勵稀疏性** | 在嚴格 pτ 下，多數樣本拿不到正向訊號，GRPO 難以更新。 | 採用分層閘門與相對排名獎勵；適度放寬初始門檻再逐漸收緊。 |
| **正確性回歸** | 過度強調速度可能導致 pass@1 下降。 | 同時監控純正確性分數，必要時加入多工（multitask）正確性損失。 |
| **對測試分布過度擬合** | 模型可能只記住特定最佳化測試的輸入模式。 | 使用隱藏測試案例（hidden test cases）、動態生成測試、跨資料集驗證。 |
| **運算成本高昂** | 每次 RL rollout 都需實際執行程式，成本遠高於純文字 RL。 | 先用離線模擬器篩選配置；對昂貴測試採用抽樣執行與快取機制。 |

### 與其他技術的整合建議

- **編譯器最佳化與剖析工具**：先以 `-O2`/`-O3`、profile-guided optimization（PGO）建立基線，再讓 RL 負責演算法層級的複雜度類別改進，兩者互補而非取代。
- **靜態分析與 linter**：在 RL 環境的 pre-execution 階段加入靜態檢查，過濾明顯低效或危險程式碼，減少沙箱負擔。
- **現有 RLVR / GRPO 訓練管線**：可將本論文的環境–獎勵組合與 GRPO 調整視為外掛模組，疊加在現有的程式碼正確性 RLVR 流程之上。
- **人機協作審查**：對於高風險場景（如交易系統），將模型輸出視為建議，仍需工程師審查正確性與複雜度，並由人類決定是否合併。
- **MLOps 與實驗追蹤**：記錄每個配置對應的 pτ、pass@1、沙箱版本與測試案例版本，方便回溯沙箱飄移與效能變化。
- **合成資料生成**：當真實最佳化測試不足時，可用程式合成技術擴充輸入規模，但需驗證其與真實分布的一致性。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦論文圖 1 的整體流程，理解「為什麼把執行時間加入獎勵會讓 RL 變困難」——關鍵在於計時雜訊、獎勵稀疏性與快但錯誤的程式碼。接著掌握三個階段（執行前篩選、執行中限時、執行後排名）與 pτ 評估指標即可，技術細節可暫時略過。

**AI 工程師**：請仔細閱讀第 3–5 節關於 RL 環境、獎勵組合與 GRPO 調整的內容。重點學習如何用離線模擬器篩選配置、如何設計 hard-gated / multitask 獎勵，以及如何在計時雜訊下穩定 GRPO 訓練。這些是將論文方法落地到產品管線的核心。

**研究人員**：建議深入分析作者對「轉換鏈」（chain of transformations）的拆解，以及 DMC-Optim 資料集的建構方式。可進一步探討的問題包括：更細緻的複雜度類別改進率指標、跨語言與跨領域的最佳化測試泛化、以及將此方法擴展到非競技程式設計的真實軟體系統。

**產品經理**：請把重點放在商業價值與風險權衡。論文顯示最佳化 RL 能在保持正確性的同時顯著提升速度，但前提是必須投資於校準沙箱、測試資料建構與持續監控。建議以「降低雲端運算成本」或「縮短關鍵 API 延遲」作為首批落地場景，並用 pτ 與中位樣本速度比較作為可解釋的成效指標。
