EvoViM 的核心設計理念在於將「記憶」與「技能」統一視為互動經驗的兩種用途，並以單一視覺程式 (Visual Program) 的形式同時承載兩者。此一架構從根本上挑戰了現有代理系統中記憶與技能分離設計的典範。

**視覺程式的雙重角色**

該視覺程式包含兩類運算 (Operations)：
1. **證據保留運算**：負責儲存當前回合的觀察結果，例如 `save_view` 將特定畫格 (Frame) 寫入畫格記憶 (Frame Memory)。
2. **證據使用運算**：負責從過去觀察中擷取證據或從當前狀態建議動作，例如 `match_query_image` 直接在像素空間計算相似度。

這種設計的關鍵洞見在於：對於「延遲查詢探索」(Exploration with Deferred Queries) 這類任務，決定性的視覺證據往往是難以用語言描述的細微差異（例如兩幅幾乎相同的畫作、兩個相似的門景觀）。文字型記憶 (Text Notes) 無法保留這些像素級的視覺特徵，而手工設計的視覺記憶則缺乏跨任務的適應能力。EvoViM 透過讓同一個凍結的多模態大型語言模型 (Frozen MLLM) 直接操作像素，繞過了文字抽象的資訊瓶頸。

**遞迴自我演化機制**

EvoViM 的演化過程分為兩個交織的循環：

- **任務執行循環**：凍結的 MLLM 載入當前世代的視覺程式，在環境中執行回合並記錄視覺軌跡 (Visual Trajectory)。
- **記憶演化循環**：在世代之間，同一個 MLLM 閱讀開發回合 (Development Episodes) 的軌跡摘要，進行失敗追溯 (Failure Tracing)——將每個失敗歸因到具體的運算（例如某個 `match_query_image` 誤判了相似度），然後重寫該運算。

更精巧的是，EvoViM 不僅修訂運算本身，還修訂「指導修訂的元工具」——即筆記 (Notes) 與分析腳本 (Analysis Scripts)。這使得後續世代的修訂能建立在先前發現之上，並跳過已嘗試過的失敗修改方向。這種「修訂修訂規則」的設計，賦予了系統真正的遞迴自我改進 (Recursive Self-Improvement) 能力，而非單純的單輪優化。

**與傳統自改進方法的區別**

相較於透過更新模型權重 (Fine-Tuning) 實現的自改進方法（如 Voyager、MemSkill），EvoViM 保持模型凍結，僅修改圍繞模型的程式碼。這大幅降低了運算成本，並保留了基礎模型的一般化能力。同時，相較於僅修改提示 (Prompt) 的方法，EvoViM 修訂的是結構化的視覺程式，具備更強的可解釋性與可組合性。

#### 與現有研究的比較

**相較於手工設計記憶的方法**

VISTA 等方法儲存每一畫格，但缺乏任務適應性——它們無法判斷哪些畫格值得保留、哪些視覺特徵對未來查詢重要。EvoViM 透過演化出的運算實現了「選擇性保留」與「任務相關擷取」，這是手工設計難以達成的。

**相較於文字型記憶演化方法**

MemSkill 等方法演化的是文字記憶，但如論文所論證，當決定性證據難以言說（例如兩幅畫作的細微色調差異），文字抽象會丟失關鍵資訊。EvoViM 的像素級運算保留了這類資訊，這是其超越文字型方法的核心優勢。

**相較於技能學習方法**

Voyager 累積可執行的動作技能，AtlasVA 從軌跡統計演化空間地圖。這些方法將記憶與技能分離處理，而 EvoViM 將兩者統一在單一視覺程式中，使證據保留與證據使用能夠共同演化、互相適配。

**相對於權重更新的自改進方法**

權重更新方法（如 RL-based approaches）需要大量互動且運算昂貴，且會有災難性遺忘風險。EvoViM 保持模型凍結，僅修改結構化程式碼，在效率與可逆性上具有優勢。

**現有限制**

1. **演化成本**：雖然比權重更新便宜，但跨世代的失敗追溯與程式修訂仍需多次 MLLM 推論，總成本不可忽視。
2. **起始程式的依賴性**：演化從一個通用起始程式出發，起始程式的設計品質會影響演化效率與最終性能上限。
3. **視覺程式的表達力**：目前程式以結構化運算組合實現，對於極複雜的視覺推理（例如多步驟的空間推疊），其表達力是否足夠仍待驗證。
4. **跨領域遷移**：實驗集中在六個視覺任務，演化出的程式能否遷移到截然不同的領域（如機器人操控、醫療影像）尚未探討。

**Q1：什麼是「延遲查詢探索」(Exploration with Deferred Queries)？為什麼這對視覺代理構成特殊挑戰？**

A：「延遲查詢探索」指的是代理必須先在環境中進行探索，事後才會收到具體的查詢問題，這與傳統任務導向環境中「先給指令再行動」的設定截然不同。在這種情境下，代理在探索階段並不知道哪些視覺細節日後會被需要，因此必須保留廣泛且細緻的視覺證據，而非僅針對已知問題進行選擇性記錄。論文中以「走過畫廊後被問某幅畫掛在哪扇門旁」為例，說明代理在沒有預先知道查詢的情況下，需要保留足夠的視覺細節才能在事後正確回答，這對視覺記憶系統提出了極高要求。

**Q2：現有的記憶方法（手工設計記憶與文字記憶演化方法）為何無法有效處理延遲查詢？**

A：手工設計的視覺記憶（如文字筆記或畫格儲存）雖然保留了觀察，但其擷取與使用規則由設計者固定，難以適應不同任務的需求；即使儲存了所有畫格，也無法靈活地根據不同查詢調整證據的使用方式。文字記憶演化方法雖然能從經驗中學習規則，但其演化對象是文字，無法記錄區分近似相同影像所需的細緻視覺特徵。當決定性的證據難以用文字描述時（例如兩扇門外觀極為相似但畫作位置不同），這些方法就會失效，無法正確擷取或運用視覺證據。

**Q3：為什麼「延遲查詢探索」這個問題值得深入研究？它在實務上為何重要？**

A：這個問題反映了真實世界中許多任務的本質——人們經常需要在不知道具體問題的情況下先進行探索，事後才需要回憶探索中所見的細節，例如巡邏保全、博物館導覽或環境監測等場景。現有多模態大型語言模型代理在這類任務上的表現仍然不足，限制了它們在真實世界中的應用範圍。透過系統性地研究這個問題並提出解決方案，可以推動多模態代理在需要長期視覺記憶的場景中更接近人類水準的表現。

**Q4：EvoViM 的核心機制是什麼？它如何將記憶與技能統一為單一視覺程式？**

A：EvoViM 的核心機制是將記憶與技能視為「經驗的兩種用途」，並將它們統一為一個由凍結多模態大型語言模型執行的視覺程式。這個程式儲存當前回合的觀察，而其運算（由早期回合塑造）則決定要保留什麼以及如何使用這些證據。程式的運算直接在像素上運作，能夠擷取過去觀察中的視覺證據，或根據當前狀態建議動作，從而將記憶擷取與動作決策整合在同一個可演化的程式結構中。

### 實作前置條件

**資料需求**

- 一個可呼叫的凍結 MLLM（如 GPT-4o、Gemini、Qwen-VL 等），需具備視覺理解與程式碼生成能力。
- 足夠的 token 預算：每次修訂（revision）需將多回合的視覺軌跡、失敗分析、修訂指令送入 MLLM。
- 像素級運算的本地執行環境（Python + NumPy / OpenCV），用於 NCC 比對、影像裁切等操作。

**技能前提**
- 熟悉 MLLM API 呼叫、提示工程（prompt engineering）與工具使用（tool use）。
- 具備 Python 程式設計能力，能將 MLLM 生成的視覺程式包裝為可執行模組。
- 了解基本的影像處理（相似度比對、ROI 裁切、特徵匹配）。
- 具備任務環境的模擬器或 API（如遊戲引擎、網頁自動化、機器人模擬）。

### 實作步驟建議

1. **定義任務與環境介面**
   - 明確區分「探索階段」與「查詢階段」。
   - 設計觀察空間（畫格格式）、動作空間、查詢格式與評分指標。
   - 準備開發回合與保留測試回合的切分。

2. **撰寫起始視覺程式**
   - 從環境的初始指令出發，讓 MLLM 生成一個「通用」視覺程式骨架，包含：
     - `save_view`：儲存當前畫格到畫格記憶。
     - `match_query_image`：以像素比對擷取證據。
     - `suggest_action`：根據當前狀態建議動作。
   - 將程式包裝為可被 MLLM 工具呼叫的函式。

3. **執行開發回合並記錄視覺軌跡**
   - 用起始程式在開發回合上執行，記錄每一步的畫格、動作、記憶狀態、最終答案。
   - 標記每回合的成功／失敗，以及失敗的具體環節（記錯、比對錯、動作錯）。

4. **執行記憶演化（Memory Evolution）**
   - 將失敗回合的視覺軌跡送入 MLLM，要求它：
     - 追溯失敗到具體運算（例如「`match_query_image` 在第 12 步比對到了錯誤的門景」）。
     - 修訂該運算的實作。
   - 同時修訂「筆記（notes）」與「分析腳本（analysis scripts）」，讓後續修訂能建立在先前發現之上、跳過已失敗的修改方向。

5. **多世代遞迴演化**
   - 重複步驟 3–4，每一代用前一世代的程式產生新的開發回合軌跡，再進行修訂。
   - 在保留測試回合上定期評估，避免過擬合開發回合。

6. **部署與監控**
   - 將最終視覺程式版本化並部署。
   - 監控實際使用中的失敗案例，累積新的開發回合以啟動下一輪演化。

---

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|------|------|----------|
| **運算成本高昂** | 每次修訂需將多回合視覺軌跡送入 MLLM，token 消耗大。 | 對畫格做摘要或抽樣；只送「失敗回合」而非全部回合；快取可重用的分析結果。 |
| **過擬合開發回合** | 程式可能只記住開發回合的特殊情境。 | 保留獨立的測試回合；限制每代修訂幅度；採用多樣化的開發回合。 |
| **失敗追溯不可靠** | MLLM 可能將失敗歸因到錯誤的運算。 | 要求 MLLM 給出具體的證據引用（哪個畫格、哪個步驟）；對修訂後的程式做單元測試式驗證。 |
| **視覺程式可解釋性不足** | 自動生成的像素運算難以審核。 | 保留所有版本的程式與修訂日誌；對關鍵運算加上人類可讀的註解。 |
| **起始程式偏差** | 若起始程式結構不佳，後續演化可能受限。 | 提供多個起始程式範本；允許 MLLM 在演化早期重組程式骨架。 |
| **畫格記憶膨脹** | 保留所有畫格會造成儲存與比對成本上升。 | 演化出「去重」或「代表性畫格選取」運算；對畫格做降解析度處理。 |
| **延遲查詢的時序錯位** | 探索與查詢之間的時間差可能讓證據失效。 | 在視覺程式中加入「時間戳記」與「位置標記」，方便事後定位。 |

---

### 與其他技術的整合建議

- **與 RAG（檢索增強生成）整合**：可將 EvoViM 的畫格記憶視為「視覺 RAG」，文字 RAG 處理可文字化的知識，視覺程式處理像素級證據，兩者互補。
- **與強化學習（RL）整合**：EvoViM 演化的「動作建議運算」可作為 RL 策略的啟發式先驗，或在 RL 訓練初期提供動作樣板。
- **與傳統電腦視覺整合**：NCC、ORB、SIFT 等經典比對方法可作為視覺程式的基礎運算原語，由 MLLM 組合與調參。
- **與 Agent 框架（如 LangChain、AutoGen）整合**：將視覺程式包裝為工具，讓 MLLM 在推理時動態呼叫。
- **與人類回饋（RLHF／RLAIF）整合**：在修訂階段引入人類專家對失敗案例的標註，提升演化效率。
- **與模型蒸餾整合**：將演化後的視覺程式邏輯蒸餾到小型視覺模型，降低部署成本。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與圖 1，理解「為什麼需要視覺記憶」以及「視覺程式長什麼樣子」。不必急著看修訂機制，可先嘗試在小型遊戲（如記憶翻牌）中手動實作 `save_view` 與 `match_query_image` 兩個運算，感受像素比對與文字描述的差異。

**給 AI 工程師**：重點關注第 3 節的「記憶演化」流程與工具呼叫設計。建議先在自有環境中復現一個簡化版：用 GPT-4o 當作凍結 MLLM，設計 5–10 個開發回合，觀察 MLLM 如何追溯失敗並修訂運算。注意控制 token 成本與畫格數量。

**給研究者**：核心創新在於「將記憶與技能統一為一個視覺程式」以及「遞迴修訂自身的修訂指引」。可深入分析的問題包括：失敗追溯的可靠性、視覺程式的搜尋空間結構、跨任務的可遷移性，以及與程式合成（program synthesis）、神經符號 AI 的理論連結。建議從消融實驗（移除筆記／分析腳本）切入，理解各元件的貢獻。

**給產品經理**：EvoViM 的價值在於「讓現成 MLLM 透過經驗自我改善」，無需微調模型權重即可在特定任務上取得顯著提升（31.3–47.6 點）。適合需要快速部署、資料量有限、但任務具有「探索後查詢」特性的場景。導入時需評估：任務是否能產生足夠的開發回合、是否能接受 MLLM 推理成本、以及失敗追溯的可審核性。建議先在單一任務上做 POC，再評估跨任務推廣的可行性。
