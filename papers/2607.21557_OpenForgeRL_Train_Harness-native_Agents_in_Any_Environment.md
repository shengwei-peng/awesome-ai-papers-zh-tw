## ⚡ TL;DR

現有開源基礎設施難以對複雜推論 harness 進行端對端訓練。
提出輕量代理與 Kubernetes 編排器，將 harness 推論記錄為標準 RL 訓練資料。
在工具與 GUI 代理基準上超越同規模開源模型，並分析 harness 與 RL 對行為的影響。

## 摘要翻譯

現代 AI 代理依賴精巧的推論 harness（inference harness），例如 Claude Code、Codex 與 OpenClaw，來驅動多輪推理、工具使用與外部系統存取。這些 harness 雖然強大，卻也讓代理難以透過開放基礎設施（open infrastructure）進行端對端訓練（end-to-end training），因為開放基礎設施的 SFT/RL 堆疊無法原生表達有狀態（stateful）、多程序（multi-process）的 harness 推論。為了解決此問題，我們提出 OpenForgeRL，一個可在多樣化環境中端對端訓練 harness-based（harness-native）代理的開源框架（open-source framework）。OpenForgeRL 透過輕量代理（proxy）承接 harness 的模型呼叫（model calls），同時將其記錄為標準強化學習程式碼庫（RL codebase），例如 veRL，的訓練資料，並以 Kubernetes 編排器（Kubernetes orchestrator）讓每個 rollout 在獨立的遠端容器（remote container）中執行；兩者結合即可在任何環境中對任何 harness 進行規模化（scale）訓練。透過訓練與推論解耦（decoupling training and inference），研究人員能直接在代理實際部署的 harness 與環境中輕鬆地訓練、研究並改進代理。

我們在多元且複雜的 harness 與環境中驗證本框架，涵蓋工具使用代理（tool-use agents）、Claw 型代理（claw-based agents），以及多模態 GUI 瀏覽器使用代理（multimodal GUI browser-use agents）與電腦使用代理（multimodal computer-use agents）。僅使用數百到數千個任務，OpenForgeClaw 在 ClawEval 上達到 31.7 pass^3 與 55.9 pass@3，並在 QwenClawBench 上達到 33.7；OpenForgeGUI 在 OSWorld-Verified 上達到 37.7、Online-Mind2Web 上達到 63.0，並在 WebVoyager 上達到 72.3。兩者在幾乎所有基準測試（agentic benchmarks）上都勝過規模相近的開源基線（open baselines），且在 GUI 情境中媲美或超越數倍大的模型。除了基準測試之外，我們也分析 harness 選擇（例如 ZeroClaw、OpenClaw、Codex）與強化學習（RL）如何形塑代理行為。我們發現某些 harness 比其他 harness 更難學習，而強化學習能提升代理可靠性，例如自我驗證（self-verification）、工具覆蓋率（tool coverage）以及完成多步驟計畫（multi-step plans），但諸如錯誤復原（error recovery）等關鍵能力仍然薄弱。

### 核心貢獻（3～5點）
- 提出 OpenForgeRL，首個能讓標準 SFT/RL 技術堆疊原生支援 harness-native 代理端對端訓練的開源框架。
- 設計輕量代理（proxy）與 Kubernetes 編排器，將訓練與推論解耦，使任何 harness 在任何容器化環境（containerized environments）中皆可規模化訓練。
- 在工具/Claw 型代理與多模態 GUI 瀏覽器/電腦使用代理等多元環境中驗證框架有效性。
- 透過實證分析揭示不同 harness 的學習難度差異，以及 RL 對代理可靠性（自我驗證、工具覆蓋率、多步驟計畫）的影響與限制。

### 適合對象
本論文適合對代理系統、推論 harness、強化學習訓練基礎設施，以及開源 AI 研究有興趣的研究人員與工程師，特別是希望在真實 harness 與環境中端對端訓練、研究並改進工具使用代理或 GUI 代理的讀者。

## 深度分析

#### 方法論解析

OpenForgeRL 的核心目標是讓「harness-native 代理（harness-native agents）」能夠在真實的 inference harness（推論 harness）內進行 end-to-end training（端對端訓練）。傳統上，這類 harness 會把 inference（推論）變成一個 stateful inference（有狀態推論）、multi-process inference（多程序推論）的過程，包含 nested tool calls（巢狀工具呼叫）、subagents（子代理）與 long-horizon context（長期上下文）。這些特性使得 veRL（veRL 開源 RL 程式碼庫）等標準 RL codebase（強化學習程式碼庫）難以直接表達整個 rollout（rollout / 回合）過程。

為了解決這個問題，作者將複雜的 harness 抽象成一個黑箱環境，並提出兩個輕量級元件：

1. **輕量代理（proxy）**：proxy 負責攔截 harness 對模型的所有 model calls（模型呼叫）。當 harness 內部需要生成下一步動作時，它實際上是向 proxy 發出請求；proxy 再將請求轉發給可訓練的語言模型或視覺–語言模型（vision-language model），並把回傳結果交還給 harness。同時，proxy 會把每一次的 prompt-response pairs（提示–回應配對）記錄下來。透過 trajectory reconstruction（軌跡重建），這些離散的 prompt-response pairs 可以被重組成標準的 RL 訓練樣本，供 PPO、GRPO 等演算法使用。

2. **Kubernetes 編排器（Kubernetes orchestrator）**：每個 rollout 都在自己的 remote container（遠端容器）中執行。這個 container（容器）內部運行完整的 harness、外部環境（例如瀏覽器、桌面、MCP 伺服器）以及被評估的任務。Kubernetes orchestrator 負責在雲端供應商（例如 Microsoft Azure）上動態調度這些 containerized environments（容器化環境），讓訓練可以 scale（規模化）到數百甚至數千個並行環境。

這種 decoupling training and inference（訓練與推論解耦）的設計帶來幾個關鍵優勢：

- **Harness 無關性**：只要 harness 能透過標準 API 呼叫模型，就能接入 OpenForgeRL，不需要為每個 harness 改寫訓練迴圈。
- **環境無關性**：無論是 tool-use agents（工具使用代理）、claw-based agents（Claw 型代理）、multimodal GUI browser-use agents（多模態 GUI 瀏覽器使用代理）還是 multimodal computer-use agents（多模態電腦使用代理），都可以透過遠端容器執行。
- **RL 演算法無關性**：proxy 產生的樣本格式與標準 RL codebase 相容，因此可以沿用現有的 SFT（Supervised Fine-Tuning，監督式微調）/RL 技術棧。

在符號層面，作者將任務建模為 Markov Decision Process（MDP）⟨S, A, T, R, γ⟩。與傳統 ReACT loop（ReACT 迴圈）不同的是，harness 會把原始互動歷史轉換成內部提示 H(s_t)，因此實際上被記錄下來的軌跡是 τ = ⟨(H(s_0), a_0), (H(s_1), a_1), …, (H(s_T), a_T)⟩。這裡的 H(·) 就是 harness 對觀察與上下文的封裝，而 RL 的更新則作用在產生 a_t 的底層模型 π_θ 上。

整體訓練流程可以概括如下：

1. RL trainer 從任務池中取出一個任務，並透過 Kubernetes orchestrator 啟動一個遠端容器。
2. 容器內的 harness 開始執行任務，過程中所有 model calls 都經過 proxy。
3. Proxy 記錄 prompt-response pairs，並在任務結束後收集 terminal reward（終端獎勵）r_T。
4. 記錄的軌跡被送回 trainer，進行 advantage estimation 與 policy update。
5. 更新後的模型權重透過 proxy 再次提供給 harness 使用，形成閉環。

#### 實驗數據解讀

論文在兩個差異很大的 agentic settings（代理設定）上進行驗證：daily tool-use / claw-based 任務，以及 multimodal GUI 任務。

##### OpenForgeClaw（工具 / Claw 型代理）

OpenForgeClaw 使用一個 30B-A3B MoE（Mixture of Experts，混合專家模型）作為底層模型，總參數 30B、啟動參數約 3B。它訓練於多個 harness，包括 ZeroClaw、OpenClaw、Codex 以及標準 ReACT loop。主要結果如下：

- ClawEval：31.7（pass^3）、55.9（pass@3）
- QwenClawBench：33.7
- MCPAtlas：28.1

這裡的 pass^3 與 pass@3 是兩種不同的可靠性指標。pass@3（pass@k 的特例）代表「只要三次嘗試中有一次成功就算通過」，衡量的是模型在多樣性採樣下的最佳表現；而 pass^3 則更嚴格，通常要求三次輸出都正確或一致，反映的是代理的穩定性與可靠性。31.7 的 pass^3 明顯低於 55.9 的 pass@3，顯示即使模型有機會找到正確答案，要讓它在多次獨立嘗試中穩定重現仍具挑戰性。這也呼應了後續分析：RL 能提升 reliability（可靠性），但 error recovery（錯誤復原）等能力仍偏弱。

MCPAtlas 的 28.1 則顯示，在涉及 MCP 伺服器的真實工具使用場景中，代理還有很大的進步空間。這類任務通常需要理解外部 API、處理動態回傳結果，並進行多步推論。

##### OpenForgeGUI（多模態 GUI 代理）

OpenForgeGUI 使用一個 8B 模型，訓練於修改後的 Kimi-Agent 與 Molmo-Web harness。結果如下：

- OSWorld-Verified：37.7
- Online-Mind2Web：63.0
- WebVoyager：72.3

這些數據相當突出。OSWorld-Verified 是電腦使用（computer-use）領域的高難度基準，37.7 已能與數倍大的模型競爭；Online-Mind2Web 與 WebVoyager 則是網頁操作（browser-use）基準，63.0 與 72.3 顯示 8B 模型在這類任務上已達到實用水平。論文指出，OpenForgeGUI 不僅優於同等規模的 open baselines（開源基線），在 GUI 設定中甚至能 match or surpass（匹配或超越）數倍大的模型。這強烈說明：在真實 deployment harness（部署 harness）中訓練，能讓模型學到更貼近實際應用的行為模式，而不僅是基礎模型規模的堆疊。

##### Harness 選擇與 RL 對行為的影響

除了 benchmark 數字，這篇論文最有價值的貢獻之一在於能夠直接研究 harness choice（harness 選擇）與 RL 如何塑造代理行為。主要發現包括：

- **不同 harness 的學習難度差異顯著**：某些 harness 雖然在推理時表現強大，但對 RL 來說更難學習。這可能與 harness 的 action space、提示設計、內部控制流程是否與模型能力對齊有關。
- **簡單且對齊的 harness 更容易學習**：這暗示 harness 設計本身應該考慮可學習性（learnability），而不只是最終性能。
- **RL 提升 agentic reliability（代理可靠性）**：包括 self-verification（自我驗證）、tool coverage（工具覆蓋率）、完成 multi-step plans（多步驟計畫）的能力。
- **Error recovery（錯誤復原）仍是弱點**：即使經過 RL 訓練，代理在遭遇錯誤後重新規劃、修正路徑的能力仍然有限。這是長期 horizon 任務中亟待解決的問題。

#### 與現有研究的比較

##### 相對於開源 RL 框架

現有的 open infrastructure（開放基礎設施）如 veRL、Slime 等，雖然支援 PPO、GRPO 等先進演算法與分散式訓練，但它們通常假設 rollout 是相對簡單的：single-turn generation（單輪生成）或輕量級 tool calls（例如沙盒程式執行）。當 harness 內部需要管理多輪互動、巢狀工具呼叫與長期上下文時，這些框架無法直接表達。OpenForgeRL 透過 proxy 與遠端容器，把複雜 harness「包裝」成標準環境，從而繞過了這個限制。

##### 相對於簡化 harness 的訓練方法

過去許多開放研究為了訓練代理，會重新實作一個簡化的 harness（例如簡化版 ReACT），導致嚴重的 train-deploy mismatch（訓練–部署不一致）：模型在簡化環境中學到的行為，未必能遷移到真實、複雜的 deployment harness。OpenForgeRL 直接在真實 harness 中訓練，消除了這道鴻溝。

##### 相對於專有系統

Claude Code、Codex 等 proprietary harness-based systems（專有推論框架系統）雖然能力強大，但其訓練流程與基礎設施並不對外開放。OpenForgeRL 提供了一個開源替代方案，讓 open research community（開放研究社群）也能訓練、研究並改進 harness-based agents。

##### 限制

儘管設計優雅，OpenForgeRL 仍存在一些限制：

- **基礎設施門檻**：需要 Kubernetes 叢集與雲端供應商（如 Microsoft Azure）資源，對於沒有足夠運算預算的研究者來說門檻不低。
- **延遲與成本**：每個 rollout 都在遠端容器中執行，頻繁的網路通訊與容器啟動會帶來額外延遲與成本。
- **Harness 整合仍需人工**：雖然 proxy 抽象了 model calls，但要把新的 harness 接入系統，仍需要處理其內部狀態、工具定義與獎勵訊號。
- **終端獎勵稀疏**：目前主要依賴 terminal reward，長期 horizon 任務的 credit assignment（信用分配）問題仍未完全解決。
- **部分 harness 不開源**：例如 Codex 是專有系統，研究社群可能無法完全重現相關實驗。

#### 可重現性評估

從論文描述來看，OpenForgeRL 被定位為 open-source framework（開源框架），理論上應該會釋出原始碼。然而，從目前提供的上下文無法確認是否已公開程式碼、資料集與模型權重。以下從幾個面向評估可重現性：

- **程式碼**：proxy 與 Kubernetes orchestrator 是核心貢獻，若釋出完整程式碼，將大幅降低社群復現門檻。但論文處於 under review 階段，實際釋出狀況仍需觀察。
- **資料集**：實驗使用的 benchmark（ClawEval、QwenClawBench、MCPAtlas、OSWorld-Verified、Online-Mind2Web、WebVoyager）多為公開資料集，這部分相對容易取得。
- **模型權重**：OpenForgeClaw 與 OpenForgeGUI 的 fine-tuned weights（微調後權重）是否釋出，對可重現性影響重大。若僅釋出訓練框架而不釋出權重，社群需要從頭訓練，成本高昂。
- **基礎設施**：即使程式碼開源，要在 Microsoft Azure 上部署 Kubernetes 並執行大量遠端容器，仍需要雲端帳號、配額與運算預算。這使得「可重現」不等於「可負擔」。
- **Harness 與 API**：部分實驗使用 Codex 等專有 harness，這會限制完全復現的可能性；ZeroClaw、OpenClaw 等開源 harness 則相對容易取得。

整體而言，OpenForgeRL 在方法論層面具有很高的透明性，但實際可重現性仍取決於原始碼、模型權重與雲端資源的釋出程度。

#### 未來研究方向

OpenForgeRL 為 harness-native 代理的訓練開闢了多條後續研究路徑：

1. **提升 error recovery（錯誤復原）能力**：這是當前最明顯的弱點。未來可以研究專門的 reward shaping、error-aware prompting，或讓模型學習顯式的 backtracking（回溯）與 replanning（重新規劃）策略。

2. **Harness 可學習性（learnability）的系統研究**：既然不同 harness 的學習難度差異顯著，未來可以發展一套衡量與設計 harness 的原則，讓 harness 不僅強大，也更容易被 RL 學會。

3. **多 harness 聯合訓練與遷移**：探索如何讓代理在多個 harness 上同時訓練，並將從簡單 harness 學到的技能遷移到複雜 harness，類似 curriculum learning（課程學習）的概念。

4. **更細緻的獎勵設計**：目前多依賴 terminal reward，未來可以引入 intermediate reward（中間獎勵）、process reward model（過程獎勵模型）或 outcome reward model（結果獎勵模型），以改善長期 horizon 任務的信用分配。

5. **擴展到更多 RL 演算法與模型規模**：雖然論文使用 veRL，但 OpenForgeRL 的設計原則上可與其他 RL codebase 整合。未來可以測試更大規模的模型，以及線上 RL、offline RL、DPO 等變體。

6. **多模態 grounding 與 GUI 理解**：OpenForgeGUI 已展現 8B 模型的潛力，未來可以進一步研究如何讓模型更精準地理解螢幕截圖、UI 元素與操作語義之間的對應關係。

7. **安全性與對齊**：在真實 harness 與外部環境中訓練，代理可能接觸到真實的網頁、檔案與 API。未來需要研究如何防止有害行為、確保訓練過程的安全性，以及避免 reward hacking（獎勵作弊）。

8. **降低基礎設施門檻**：開發更輕量的本地模擬版本，或支援邊緣運算與低成本雲端方案，讓更多研究者能夠參與 harness-native 代理的訓練與研究。

9. **自動化 harness 設計**：最終目標可能是讓模型與 RL 共同設計或優化 harness 本身，而不只是學習在固定 harness 中行事，從而實現更高層次的 agentic capability（代理能力）。

## 論文問答

**Q1：OpenForgeRL 主要想解決什麼問題？為什麼訓練 harness-based 代理的端對端模型如此困難？**

A：現代 AI 代理越來越依賴 Claude Code、Codex、OpenClaw 等複雜的推論 harness，這些 harness 負責多輪推理、工具呼叫、上下文管理與外部系統連接。然而，這些 harness 讓推論變成有狀態、多程序、甚至包含巢狀工具呼叫與子代理的長期過程，現有開放式 SFT/RL 訓練框架無法原生表達這類推論流程。此外，harness 的 rollout 需要獨立的容器化環境與專屬資源，無法與訓練節點共置，導致開放研究社群難以端到端訓練與研究這類代理。

**Q2：現有的開源 RL 框架為什麼無法直接支援真實 harness 的訓練？**

A：諸如 veRL 等開源 RL 框架通常假設 rollout 是單輪生成或僅涉及輕量級的工具呼叫，並且可以在 trainer 節點本地執行。但真實 harness 會在內部自行管理多輪互動、工具使用與上下文，需要專屬的 CPU、記憶體與容器化環境。因此研究者往往只能為訓練重新實作簡化版 harness，或針對特定任務逐一修改訓練迴圈，造成訓練與部署不一致，也讓程式碼難以維護與擴展。

**Q3：為什麼直接在部署用的真實 harness 中訓練代理，比使用簡化版訓練 harness 更重要？**

A：近年來代理能力的進步不僅來自基礎模型變強，也來自 harness 設計的精進，因此 harness 本身就是能力的關鍵來源。在真實 harness 中訓練可以消除訓練–部署不一致的問題，讓模型學習到實際上線時會遇到的控制流程、工具介面與上下文格式。這也讓研究者能夠直接研究不同 harness 與 RL 訓練如何塑造代理行為，而這在過往的開放研究中難以做到。

**Q4：OpenForgeRL 的兩個核心元件是什麼？它們如何協同運作？**

A：第一個核心元件是輕量代理（proxy），它負責攔截並記錄 harness 對模型的呼叫，同時讓 harness 保持原有的推論邏輯不變。第二個核心元件是 Kubernetes 編排器，它將每一次 rollout 放到遠端容器中執行，並可彈性擴展到大量並行環境。兩者結合後，訓練程式碼庫只需處理標準的提示–回應配對與軌跡資料，就能與任意 harness 及任意環境對接。

**Q5：輕量 proxy 如何在解耦訓練與推論的同時，仍保留 harness 的原生行為？**

A：proxy 的角色是「服務」harness 的模型呼叫，因此 harness 內部的多輪互動、工具呼叫與控制流程都無需修改。在服務過程中，proxy 會記錄每一組提示–回應配對 \((H(s_t), a_t)\)，這些配對後續可透過軌跡重建轉換成標準 RL 樣本。由於 harness 本身不知道自己被訓練，推論行為與部署時完全一致，從而實現真正的 harness-native 訓練。

**Q6：為什麼 OpenForgeRL 選擇用 Kubernetes 編排器在遠端容器中執行 rollout，而非在訓練節點本地執行？**

A：複雜 harness 的 rollout 通常需要瀏覽器、MCP 伺服器、GUI 桌面等外部系統，並且需要隔離的 CPU 與記憶體資源，這些資源無法大規模與 GPU 訓練節點共置。Kubernetes 編排器可以為每個 rollout 啟動獨立的遠端容器，提供環境隔離並彈性擴展到數百甚至數千個並行環境。這樣的設計也讓 RL 程式碼庫保持環境無關，不必為每種新環境修改訓練邏輯。

**Q7：論文評估了哪些代理變體與 harness？涵蓋哪些應用領域？**

A：論文提出了 OpenForgeClaw 與 OpenForgeGUI 兩個代理變體。OpenForgeClaw（30B-A3B MoE）在工具使用與 Claw 型代理場景中，評估了 ZeroClaw、OpenClaw、Codex 以及標準 ReACT 迴圈。OpenForgeGUI（8B）則聚焦多模態 GUI 瀏覽器與電腦使用，使用修改後的 Kimi-Agent 與 Molmo-Web 進行訓練與評估。

**Q8：OpenForgeRL 的主要實驗結果為何？與開源基線相比表現如何？**

A：OpenForgeClaw 在 ClawEval 上達到 31.7 pass^3 與 55.9 pass@3，在 QwenClawBench 達到 33.7，在 MCPAtlas 達到 28.1。OpenForgeGUI 則在 OSWorld-Verified 達到 37.7、Online-Mind2Web 達到 63.0、WebVoyager 達到 72.3。兩者在幾乎所有基準測試上都優於規模相近的開源基線，而 GUI 代理甚至在多項指標上追平或超越規模數倍大的模型。

**Q9：論文對 harness 選擇與 RL 效應做了哪些分析？有什麼關鍵發現？**

A：研究發現不同 harness 的學習難度差異顯著，結構更簡單、與任務更對齊的 harness 更容易被學會。RL 訓練普遍提升了代理的可靠性，包括自我驗證、工具覆蓋率與完成多步驟計畫的能力。然而，錯誤復原能力仍然薄弱，顯示這是未來需要特別加強的關鍵能力。

**Q10：OpenForgeRL 最適合應用在哪些實務場景？**

A：它特別適合需要代理在真實複雜環境中運作的場景，例如使用 Claude Code 或 Codex 進行軟體工程、使用 OpenClaw/ZeroClaw 處理日常工具任務、自動化網頁瀏覽器操作，以及控制桌面作業系統。由於它直接在原生 harness 中訓練，任何 harness 需要管理外部工具與長期上下文的領域都能受益。這讓產品團隊可以在與上線環境幾乎相同的條件下迭代模型。

**Q11：在實際產品或基礎設施層面，部署 OpenForgeRL 時需要考慮哪些因素？**

A：首先需要整合 Kubernetes 與雲端供應商（如 Microsoft Azure），以彈性管理大量遠端 sandbox 容器的生命週期。其次，proxy 必須能夠低延遲地服務 harness 的模型呼叫，同時可靠地記錄與傳輸軌跡資料。此外，容器之間的網路安全、外部系統存取控管，以及遠端環境的擴展成本，都是大規模部署時不可忽視的營運議題。

**Q12：OpenForgeRL 對開放研究社群與相對於專有系統可能帶來什麼影響？**

A：它降低了使用開放基礎設施訓練 harness-based 代理的門檻，讓研究社群能夠縮小與專有系統之間的差距。由於可以重複使用真實的 harness 生態系，研究者無需重新實作訓練堆疊，就能比較不同 harness、RL 演算法與環境組合。這有望加速代理系統在開放社群中的創新，並促進更多關於 harness 設計與訓練交互作用的科學研究。

**Q13：論文承認了哪些主要限制？**

A：儘管 RL 帶來許多改善，代理在錯誤復原方面仍然表現不佳，難以在長期任務中偵測並修正自己的失誤。此外，某些 harness 的學習難度遠高於其他 harness，意味著並非所有 harness 設計都同樣適合端到端訓練。框架本身也依賴 Kubernetes 與遠端容器基礎設施，對部分研究團隊而言可能增加部署與維運的複雜度。

**Q14：論文指出了哪些失敗案例或特別難學的行為？**

A：代理雖然提升了自我驗證與工具覆蓋率，但在遭遇錯誤後往往無法有效恢復並繼續完成任務。具有複雜巢狀子代理或控制流程與任務不夠對齊的 harness，會讓學習效率明顯下降。此外，在觀察雜訊、工具失敗或需要長期規劃的情況下，代理仍難以穩定地執行多步驟計畫。

**Q15：OpenForgeRL 指出了哪些未來研究方向？**

A：未來可以設計「更容易訓練」的 harness，在強大能力與學習友善性之間取得更好平衡。提升錯誤復原與強健的長期規劃能力將是關鍵研究課題。此外，將框架擴展到更多 RL 演算法、更大規模模型，以及機器人、多代理協作等更廣泛的環境，也有助於進一步放大其影響力。

## 實務應用指南

### 適用場景

1. **企業內部自動化工具代理**  
   若組織已部署大量 MCP 伺服器、內部 API 與資料庫工具，可利用 OpenForgeRL 在真實的 Claude Code、Codex 或 OpenClaw harness 中訓練專屬代理，讓模型學會依據自然語言指令正確選擇工具、填寫參數並完成多步驟流程，例如自動產生財務報表、更新工單狀態或執行 DevOps 腳本。

2. **多模態 GUI 瀏覽器與桌面自動化**  
   適合需要讓代理操作網頁後台、ERP 系統或桌面應用程式的場景，例如自動化客服後台建單、跨系統資料搬運、軟體測試腳本生成。OpenForgeGUI 可在 Kimi-Agent、Molmo-Web 等 harness 中進行端到端訓練，並透過 Kubernetes 遠端容器安全隔離每個 rollout。

3. **軟體工程與程式碼生成代理**  
   適用於想讓代理在真實 IDE 或命令列環境中完成除錯、重構、測試與提交任務的團隊。透過 harness-native 訓練，模型能學習 harness 內部的子代理排程、規劃模式與長期上下文管理，減少訓練與部署時的 harness 不一致問題。

4. **開放研究與基準測試複現**  
   學術團隊若希望系統性比較 ZeroClaw、OpenClaw、Codex 等不同 harness 對代理行為的影響，可使用 OpenForgeRL 統一訓練流程，在 ClawEval、OSWorld-Verified、WebVoyager 等基準上進行公平實驗，並分析 RL 對自我驗證、工具覆蓋率與錯誤復原能力的影響。

5. **雲端規模化的 RL 微調服務**  
   對於擁有自有任務資料與容器化環境的團隊，可將 OpenForgeRL 作為基礎設施層，把任意 harness 與任意遠端 sandbox 對接到 veRL 等 RL 程式碼庫，建立可彈性擴充的代理訓練流水線。

### 實作前置條件

**資料準備**
- 任務指令與對應的環境初始狀態：需涵蓋目標 harness 會遇到的真實情境，數量從數百到數千筆即可看到效果（論文使用數百至數千筆任務）。
- 獎勵訊號：每個任務需有明確的成功／失敗判定，例如單元測試通過、網頁元素檢查、API 回傳狀態碼等。
- Harness 與工具定義：需準備好目標 harness（如 OpenClaw、Kimi-Agent）及其使用的工具/MCP 伺服器規格，確保訓練與部署使用相同版本。

**運算資源**
- GPU：訓練端需支援 LLM/VLM RL 訓練的 GPU 叢集，例如 30B-A3B MoE 或 8B 模型規模對應的記憶體與算力。
- Kubernetes 叢集：用於執行遠端 rollout 容器，建議部署在雲端供應商（如 Microsoft Azure），每個 rollout 獨立容器以確保隔離與彈性擴展。
- 網路頻寬：訓練節點與遠端容器之間需穩定低延遲，因為 prompt-response pairs 會在兩端往返記錄與重建。

**技能要求**
- 熟悉 RL 訓練流程（PPO、GRPO）與 veRL 或類似 RL codebase 的操作。
- 具備 Kubernetes 與容器化部署經驗，能夠打包 harness 執行環境並管理遠端 sandbox。
- 理解目標 harness 的內部控制流（子代理、巢狀工具呼叫、規劃模式），以便正確設定 proxy 與軌跡重建邏輯。

### 實作步驟建議

1. **選定 harness 與環境**  
   根據應用場景選擇要訓練的 harness（例如工具使用選 OpenClaw/Codex，GUI 選 Kimi-Agent/Molmo-Web），並準備對應的容器化環境與工具/MCP 伺服器。

2. **部署 OpenForgeRL Proxy**  
   在 harness 與模型之間插入輕量代理，攔截所有模型呼叫並記錄 prompt-response pairs。確保 proxy 對 harness 透明，不會改變 harness 原有的多輪推理與工具呼叫行為。

3. **設定 Kubernetes 編排器**  
   為每個 rollout 建立獨立的遠端容器，配置好環境初始狀態、工具存取權限與網路隔離。根據並行需求自動擴展容器數量。

4. **產生與重建訓練軌跡**  
   執行初步 rollout，透過 proxy 收集軌跡資料，再利用自動軌跡重建機制將 prompt-response pairs 轉換為標準 RL 樣本格式，餵入 veRL 等 RL codebase。

5. **執行 RL 訓練**  
   選擇適合的 RL 演算法（如 PPO、GRPO），設定獎勵函數與訓練超參數。持續監控訓練穩定性、KL 散度與 rollout 成功率。

6. **評估與迭代**  
   在對應基準（ClawEval、OSWorld-Verified、WebVoyager 等）或自有測試集上評估 pass@k/pass^k 指標。分析 harness 選擇與 RL 對自我驗證、工具覆蓋率、錯誤復原的影響，並根據弱項補充資料或調整獎勵設計。

7. **部署到生產 harness**  
   由於訓練與部署使用同一套 harness，可直接將訓練後的模型權重或 checkpoint 載回原始 harness，進行 A/B 測試與漸進式上線。

---

### 潛在風險與注意事項

- **訓練–部署不一致風險**  
  雖然 OpenForgeRL 強調在真實 harness 中訓練，但若 proxy 版本、容器環境或工具版本與生產環境不同，仍會產生不一致。建議使用相同的容器映像檔與 harness 版本貫穿開發、訓練與部署。

- **獎勵設計稀疏或偏差**  
  長期任務的終端獎勵可能過於稀疏，導致 RL 難以學習。可考慮加入中間獎勵（例如工具呼叫正確性、步驟完成度），但需避免獎勵駭取（reward hacking）行為。

- **錯誤復原能力仍弱**  
  論文發現即使經過 RL 訓練，代理在錯誤復原方面仍然不足。實務上應保留人機協作機制或設定明確的失敗重試與安全閥，避免代理在錯誤路徑上持續執行。

- **遠端 rollout 成本與延遲**  
  每個 rollout 都在獨立遠端容器中執行，規模化時會產生顯著的雲端運算與網路成本。建議設定並行上限、使用 spot 實例，並對輕量任務進行批次處理。

- **安全與隔離**  
  Harness 可能會執行任意程式碼或操作真實網頁，必須確保遠端容器具備足夠隔離，避免影響生產系統或外洩敏感資料。

---

### 與其他技術的整合建議

- **與現有 RL 程式碼庫整合**  
  OpenForgeRL 的設計是與 veRL 等標準 RL codebase 協同運作。若團隊已使用 Slime、TRL 或其他框架，可透過標準化的 prompt-response pairs 與軌跡重建介面進行銜接，降低遷移成本。

- **與 MCP 生態系整合**  
  若企業已採用 MCP 伺服器作為工具標準，可直接將這些伺服器掛載到遠端 rollout 容器中，讓代理在訓練階段就學習正確呼叫 MCP 工具。

- **與現有 MLOps 平台整合**  
  可將 Kubernetes 編排器對接到現有的模型訓練排程系統（如 Kubeflow、MLflow），統一管理實驗追蹤、checkpoint 儲存與模型版本。

- **與監控與可觀測性工具整合**  
  由於 harness 推理是有狀態且多程序的，建議將 proxy 記錄的軌跡資料匯入追蹤系統（如 LangSmith、Langfuse 或自研平台），方便後續除錯與行為分析。

- **與人機協作介面整合**  
  針對錯誤復原與高風險操作，可在 harness 中保留暫停、確認或人工接管節點，讓 RL 訓練後的代理在生產環境中與人類協作。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先理解「harness」與「純語言模型」的差別：現代 AI 代理不只是模型本身，還包含多輪推理、工具呼叫與上下文管理的推論框架。本論文的核心貢獻是讓這些複雜框架也能被標準 RL 方法訓練。可先閱讀第 1 節與第 3 節的概念介紹，再回頭看實驗結果。

**AI 工程師**  
重點關注第 3 節的方法與系統架構：輕量 proxy 如何攔截模型呼叫、Kubernetes 編排器如何管理遠端 rollout、以及軌跡重建如何與 veRL 對接。這些是實際落地時最需要複現與調整的部分，建議搭配論文附錄或開源程式碼一起閱讀。

**研究人員**  
第 5 節的行為分析與實證結果最值得細讀：不同 harness 的學習難度、RL 對自我驗證與工具覆蓋率的影響、以及錯誤復原的侷限性，都是未來可以延伸的研究方向。也可思考如何將此框架擴展到更多樣的環境或 RL 演算法。

**產品經理**  
本論文提供了一個關鍵訊號：在真實 harness 中訓練的代理，能夠在數百至數千筆任務內達到接近或超越更大模型的表現。建議聚焦於「適用場景」與「潛在風險」兩節，評估哪些內部流程適合優先導入，以及需要預留哪些工程資源與安全機制。
