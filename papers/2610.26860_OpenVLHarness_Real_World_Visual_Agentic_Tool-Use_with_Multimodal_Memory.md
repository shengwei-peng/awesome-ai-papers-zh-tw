## 摘要翻譯

多模態大型語言模型 (MLLMs) 在視覺推理方面進展迅速，然而許多任務需要單憑內部推理難以取得的證據：我們在 22 個基準測試上進行的受控研究顯示，單純增加基礎模型的推論預算只能帶來有限的提升。此類任務需要透過異質工具取得具視覺依據的感知、外部知識與數值測量，而這些工具的輸出必須轉化為模型可讀的形式，並在推理步驟間加以保留。我們提出 OpenVLHarness，一個圍繞能力層與持久多模態記憶所建構的多模態推理框架。能力層結合任務層級工具介面與證據渲染，提供對異質後端的一致存取，並將其輸出轉換為模型可讀觀察值。持久多模態記憶則在整個查詢過程中，將對應的影像、結構化資料與網路參考保留為可定址工件。程式碼介面可對儲存的資料執行所產生的程式，實現結合多個工具結果的運算。這些機制共同支援取得、檢查與組合多模態證據的迭代過程。在 22 個基準測試上以八個開放與專有骨幹模型進行評估，OpenVLHarness 相較於匹配的無工具基線，平均分數提升了 9.7 至 12.6 點，其中包括 Qwen3-VL-8B 提升 11.2 點、Kimi K3 提升 9.7 點，以及 GPT-6 Astra 提升 9.9 點。搭配 GPT-6 Luna 於中等推理強度下，OpenVLHarness 以最多僅 37% 的模型符元成本，超越最大推理強度下的基礎模型、Codex 與 Visual Sketchpad 達 7.7 至 8.5 點。

### 核心貢獻（3～5點）
- 提出 OpenVLHarness 多模態推理框架，圍繞能力層與持久多模態記憶建構，解決純粹增加推論預算效果有限的問題
- 設計能力層，整合任務層級工具介面與證據渲染，提供異質後端的一致存取，並將輸出轉為模型可讀觀察值
- 引入持久多模態記憶，將影像、結構化資料與網路參考保留為可定址工件，支援跨推理步驟的證據保留
- 透過程式碼介面執行所產生的程式，實現結合多個工具結果的運算
- 在 22 個基準測試上以八個開放與專有骨幹模型進行評估，平均分數提升 9.7 至 12.6 點，並以最多 37% 的模型符元成本超越既有方法

### 適合對象
從事多模態大型語言模型、視覺推理、工具使用代理（Tool-Use Agents）與 AI 系統設計的研究者與工程師；尤其適合關注真實世界視覺任務、推論時間擴展（Inference-Time Scaling）、異質工具整合與成本效益評估之學術與產業界人士。

## 深度分析

#### 方法論解析

OpenVLHarness 的核心設計理念在於解決多模態大型語言模型 (MLLMs) 在真實世界視覺任務中面臨的兩個關鍵瓶頸：異質工具輸出的可解釋性問題，以及跨推理步驟的證據重用問題。整體架構圍繞「編排器 (Orchestrator) + 能力層 (Capability Layer) + 持久多模態記憶 (Persistent Multimodal Memory)」三大支柱運作。

**能力層 (Capability Layer) 的雙重設計**

能力層採用「任務層級工具介面 (Task-Level Tool Interfaces)」與「證據渲染 (Evidence Rendering)」的解耦設計，這是本方法最具巧思的工程決策之一。任務層級介面將操作定義與具體後端分離，例如「視覺定位 (Visual Grounding)」這個任務可由 Segment Anything、Grounding DINO 等不同模型實現，但編排器只需透過統一的介面呼叫，無需感知後端差異。這種抽象使得工具可被熱插拔 (hot-swappable)，同時維持編排器任務詞彙 (Task Vocabulary) 的穩定性。

證據渲染則負責將異質後端的輸出轉化為「模型可讀觀察值 (Model-Readable Observations)」。以視覺定位為例，後端可能回傳 RLE 編碼的分割遮罩 (Segmentation Masks)、邊界框座標等結構化資料，但這些原始輸出對 MLLM 並不直觀。能力層將其渲染為：(1) 帶有標註框的標註影像 (Annotated Image)，(2) 簡潔的文字描述，(3) 結構化的座標資訊。這種「視覺化 + 文字 + 結構化資料」的三合一呈現方式，使模型既能進行視覺檢查 (Visual Inspection)，又能取得精確數值。

**持久多模態記憶 (Persistent Multimodal Memory) 的定址機制**

記憶模組採用「可重複使用控制代碼 (Reusable Handles)」機制，將工具產生的工件 (Artifacts) 註冊為可定址資源。具體而言，記憶中保存三類工件：(1) 影像工件 (Image Artifacts)，包括輸入影像與工具生成的渲染影像；(2) 結構化資料 (Structured Data)，如相機姿態、深度圖字典、分割遮罩字典等；(3) 網路參考 (Web References)，即搜尋引擎回傳的網頁 URL。

這個設計的關鍵在於「跨回合可存取性」。在論文中「窗戶與櫥櫃中心距離」的範例中，編排器先呼叫視覺定位取得窗戶與櫥櫃的遮罩，再呼叫深度估計取得深度陣列，最後透過編碼代理 (Coding Agent) 在儲存的資料上執行程式碼進行測量。若沒有持久記憶，每個步驟都需重新呼叫工具，會造成巨大的計算浪費與誤差累積。

**編碼介面 (Coding Interface) 的組合能力**

編碼代理是本系統的「組合引擎」。編排器以自然語言描述計算目標，底層的程式碼生成模型（與骨幹模型同源）會產生 Python 程式碼，並在儲存的結構化資料上執行。這使得跨工具結果的數值計算成為可能——例如將分割遮罩的像素座標轉換為世界座標，再結合深度圖計算實際距離。這種「自然語言意圖 → 程式碼 → 數值結果」的閉環，是純文字推理或單純工具呼叫無法達成的。

**迭代式證據獲取流程**

整體運作形成一個「獲取 → 檢查 → 組合」的迭代循環：編排器呼叫工具取得證據，透過渲染後的觀察值進行視覺檢查，必要時呼叫編碼代理進行數值組合，再根據結果決定下一步行動。這與 ReAct、Reflexion 等代理框架的思路一致，但 OpenVLHarness 的差異化在於將「證據的可解釋性」與「工件的可重用性」明確分離並工程化。

#### 實驗數據解讀

**基準測試的廣度與分層**

實驗在 22 個基準測試 (Benchmarks) 上進行，涵蓋四大類別：(1) 接地感知 (Grounded Perception)，如指稱表達分割、視覺定位；(2) 視覺搜尋與深度研究 (Visual Search and Deep Research)，如多模態問答中的知識檢索；(3) 通用視覺問答與幻覺 (General VQA and Hallucination)，如 MME、POPE 等；(4) 空間推理 (Spatial Reasoning)，如距離估計、3D 場景理解。這樣的分層設計使得評估能夠區分系統在不同能力維度上的表現，而非僅看單一總分。

**骨幹模型的多元性**

實驗採用 8 個骨幹模型 (Backbones)，包括開放權重模型 (Qwen3-VL-8B、Kimi K3 等) 與專有模型 (GPT-6 Astra、GPT-6 Luna 等)。這種設計驗證了系統的「骨幹無關性」——即 OpenVLHarness 並非針對特定模型調優，而是作為通用框架運作。

**核心結果的解讀**

平均分數提升 9.7–12.6 個百分點是相當顯著的增益。具體而言：
- Qwen3-VL-8B：+11.2 點
- Kimi K3：+9.7 點
- GPT-6 Astra：+9.9 點

這些數字顯示 OpenVLHarness 對不同規模、不同訓練背景的模型都有穩定增益，並非僅對弱模型有「救援效應」。

**推論時間擴展 (Inference-Time Scaling) 的關鍵發現**

最值得關注的實驗是「推理強度 (Reasoning Effort)」的消融。基礎模型從 xhigh 提升到 max effort 時，模型符元成本 (Model-Token Cost) 增加 2.7 倍，但平均分數僅提升 0.7 點——呈現明顯的邊際遞減。這證明了論文的核心理論主張：純粹增加推理預算 (Inference Budget) 並非最佳路徑，「證據獲取」與「推理擴展」是互補而非替代關係。

**成本效益的突破**

GPT-6 Luna 在中等推理強度 (Medium Effort) 下使用 OpenVLHarness，超越基礎模型、Codex、Visual Sketchpad 在最大強度 (Maximum Effort) 下的表現 7.7–8.5 點，且模型符元成本僅為後者的 37%。這個數據極具說服力：它意味著透過工具獲取外部證據，比單純增加模型自身的推理計算更為經濟。這對於實際部署的成本考量至關重要。

**消融研究的意涵**

雖然摘要未詳述消融細節，但提到「能力層與記憶的增量效應」，暗示兩者各自獨立貢獻。能力層解決「工具輸出可解釋性」，記憶解決「工件可重用性」，兩者缺一不可。

#### 與現有研究的比較

**與 Visual Sketchpad 的定位差異**

Visual Sketchpad 是視覺代理領域的代表性工作，其核心思路是讓模型在「草圖本」上繪製視覺輔助（如邊界框、遮罩疊加）來輔助推理。OpenVLHarness 與其差異在於：(1) Visual Sketchpad 偏向「模型內部視覺化」，而 OpenVLHarness 強調「外部異質工具整合」；(2) OpenVLHarness 引入持久記憶，使工件可在多步推理中重用，而非僅作為單步輔助；(3) OpenVLHarness 的編碼代理提供了數值計算能力，這是 Visual Sketchpad 所缺乏的。

**與 Codex 的比較**

Codex（此處應指多模態程式碼執行代理類工作）強調「程式碼即推理」，將視覺任務轉化為程式碼生成。OpenVLHarness 並非取代此路線，而是將其整合為「編碼介面」子模組，並補充了感知工具與搜尋工具的整合。這種「包容式創新」使得 OpenVLHarness 在功能面上更為完整。

**與其他視覺代理框架的關係**

相較於 MM-ReAct、Visual ChatGPT 等早期工作，OpenVLHarness 的進步在於：(1) 明確分離任務介面與後端實作，提升可維護性；(2) 引入證據渲染，解決「模型看不懂工具輸出」的根本問題；(3) 持久記憶機制支援真正的多步推理，而非單步工具呼叫。

**論文中承認的限制**

從方法論描述可推導出幾項隱含限制：(1) 系統依賴編排器正確選擇工具與組合順序，若骨幹模型的規劃能力不足，可能陷入無效迴圈；(2) 編碼代理的程式碼品質受骨幹模型能力限制，對弱模型可能產生錯誤計算；(3) 持久記憶的容量管理未在摘要中詳述，長期任務可能面臨上下文溢出問題；(4) 22 個基準測試雖廣，但未涵蓋影片理解、3D 點雲等更複雜的模態。

#### 可重現性評估

**程式碼與資料的開放性**

從摘要與方法描述判斷，OpenVLHarness 似乎定位為一個可擴展的框架。論文中提到「harness search」與「tool generation」兩個客製化工作流程，暗示作者希望使用者能基於此框架進行領域適配，這通常伴隨著程式碼釋出。然而，僅憑現有文本無法確認 GitHub 倉庫、模型權重、評估腳本的具體釋出狀況。

**可重現的關鍵要素**

若要重現此工作，需要取得：(1) 編排器的提示工程模板；(2) 各工具的呼叫介面規範；(3) 證據渲染的輸出格式定義；(4) 持久記憶的資料結構設計；(5) 22 個基準測試的評估協議。論文中圖 1 展示了系統架構與資料流，這對實作有重要參考價值。

**骨幹模型的可取得性**

實驗涵蓋的 8 個骨幹模型中，開放模型（如 Qwen3-VL-8B）可從 Hugging Face 等平台取得；專有模型（如 GPT-6 系列）需透過 API 存取，這對完全重現構成一定障礙，特別是涉及模型版本更新可能導致結果波動。

**基準測試的標準化程度**

22 個基準測試多為公開資料集（如 POPE、MME 等），但部分基準（如「深度研究」類別）的評估可能涉及即時網路搜尋，這會引入時間敏感性，使重現結果產生波動。

#### 未來研究方向

**多模態記憶的進階機制**

當前持久多模態記憶採用「全量保留」策略，未來可探索：(1) 分層記憶架構，區分短期工作記憶與長期知識庫；(2) 記憶蒸餾與摘要機制，避免上下文溢出；(3) 跨查詢的記憶共享，使相關任務能累積經驗。

**工具生態的自動化擴展**

論文已展示「tool generation」工作流程，未來可進一步研究：(1) 自動工具發現與整合，從開源模型庫中挑選合適的後端；(2) 工具鏈的自動組合最佳化，根據任務特性動態選擇工具序列；(3) 工具失敗的容錯機制，當某後端不可用時自動切換。

**編碼代理的強化學習**

編碼代理目前依賴骨幹模型的零樣本 (Zero-Shot) 程式碼生成能力。未來可透過：(1) 專門的程式碼生成微調，使其更擅長處理視覺工件；(2) 引入執行回饋的強化學習，從程式碼執行錯誤中學習；(3) 形式化驗證機制，確保生成程式碼的正確性。

**真實世界部署的魯棒性**

論文標題強調「Real World」，但評估仍以基準測試為主。未來應探索：(1) 開放領域的真實使用者任務；(2) 工具呼叫失敗、網路不穩定等異常情境；(3) 人機協作模式，讓使用者介入修正推理路徑。

**多模態推理的可解釋性**

證據渲染已部分解決「模型如何理解工具輸出」的問題，但「模型為何選擇此工具」的決策可解釋性仍待加強。未來可引入：(1) 工具選擇的信心度評估；(2) 推理路徑的視覺化呈現；(3) 反事實分析，說明若選擇不同工具會產生何種結果。

**與其他推理範式的融合**

OpenVLHarness 目前以「工具呼叫 + 程式碼執行」為主，未來可與其他範式融合：(1) 與思維鏈 (Chain-of-Thought) 結合，使推理過程更透明；(2) 與神經符號系統結合，引入形式化邏輯；(3) 與多代理系統結合，實現任務分解與協作。

**領域特化與垂直應用**

論文已展示客製化能力，未來可深入特定垂直領域：(1) 醫療影像分析，整合 DICOM 處理與醫學知識庫；(2) 工業檢測，整合缺陷檢測模型與品質標準；(3) 自動駕駛，整合 3D 感知與交通規則推理。這些垂直應用將考驗框架的可擴展性與實用性。

## 論文問答

**Q1：這篇論文試圖解決什麼核心問題？**
A：這篇論文聚焦於多模態大型語言模型 (MLLMs) 在處理真實世界視覺任務時的根本限制——許多任務需要模型無法僅憑內部推理取得的證據，例如在密集場景中定位微小物件、檢索長尾實體的外部知識，或是從中間測量值計算數量。論文的推論時間擴展研究顯示，單純增加基礎模型的推論預算只能帶來微幅進步，從 xhigh 提升到 max 強度時，模型符元成本增加 2.7 倍，但平均分數僅提升 0.7 點。這意味著視覺推理的進一步突破需要超越「對初始輸入做更多推理」的範式，轉向取得任務相關的多模態證據。

**Q2：為什麼僅靠擴展推論預算（inference-time scaling）無法有效解決問題？**
A：論文透過控制實驗明確展示，MLLMs 在純內部推理模式下呈現嚴重的報酬遞減現象——更高的推理強度並不能換來相應的準確度提升。這是因為許多視覺任務本質上需要外部資訊，例如物件的精確座標、深度資訊或網路知識，這些資訊無法從模型的權重中可靠推導出來。換言之，推理預算的增加只能讓模型「想得更久」，但無法讓它「看得更清楚」或「查到更多」，因此必須結合工具使用來取得外部證據。

**Q3：為什麼這個問題在實務上很重要？**
A：在真實世界的視覺任務中，使用者往往提出需要精確測量、跨模態資訊整合或外部知識查詢的問題，例如「窗戶和櫥櫃中心相距多遠」這類需要深度估計、物件分割與數值計算的任務。這類任務若僅依賴模型內部知識，不僅容易產生幻覺，也無法達到實務所需的精確度。因此，建立一個能夠取得、檢查並組合多模態證據的系統，對於將 MLLMs 真正部署到現實應用中至關重要。

**Q4：OpenVLHarness 的核心架構是什麼？**
A：OpenVLHarness 是一個圍繞「能力層 (Capability Layer)」與「持久多模態記憶 (Persistent Multimodal Memory)」兩個核心元件所建構的多模態推理框架。能力層結合任務層級工具介面與證據渲染，提供對異質後端的一致存取，並將其輸出轉換為模型可讀的觀察值；持久多模態記憶則將對應的影像、結構化資料與網路參考以可定址工件的形式保留在整個查詢過程中。這兩個元件共同支援一個取得、檢查並組合多模態證據的迭代過程。

**Q5：OpenVLHarness 的關鍵創新點為何？**
A：第一項創新是將任務層級介面與特定後端解耦，使工具可以被替換而無需更改編排器的任務詞彙，這大幅提升了系統的可擴展性與可維護性。第二項創新是證據渲染機制，能將異質輸出（如分割遮罩、深度圖、網頁內容）轉換為結合視覺化、簡潔描述與結構化資訊的觀察值，讓模型能以統一方式解讀。第三項創新是持久多模態記憶，透過可重複使用控制代碼讓後續推理步驟能夠重新使用先前取得的工件，並透過 Python 編碼代理支援跨工具的計算組合。

**Q6：在設計上有哪些重要的取捨與選擇？**
A：設計上的一個關鍵選擇是採用「任務層級」而非「後端層級」的介面抽象，這使得新增或替換工具時無需修改編排器邏輯。另一個重要選擇是將視覺化呈現與結構化資料分開保留——視覺化用於模型檢查，結構化資料用於精確計算，這種雙軌設計兼顧了模型的直觀理解與數值運算需求。此外，編碼代理使用同一個骨幹模型來生成程式碼，降低了系統對額外模型的依賴，同時也讓使用者能透過自然語言指定計算目標。

**Q7：實驗使用了哪些基準測試？**
A：論文評估涵蓋 22 個基準測試，橫跨四大類別：基礎感知（grounded perception）、視覺搜尋與深度研究（visual search and deep research）、通用視覺問答與幻覺（general VQA and hallucination），以及空間推理（spatial reasoning）。這種多元的基準組合能夠全面檢驗系統在不同視覺推理面向上的能力，避免單一領域的過擬合。

**Q8：主要的實驗結果為何？**
A：在 8 個開放與專有的 MLLM 骨幹模型上，OpenVLHarness 一致地將平均表現提升 9.7 至 12.6 個百分點，具體包括 Qwen3-VL-8B 提升 11.2 點、Kimi K3 提升 9.7 點、GPT-6 Astra 提升 9.9 點。特別值得注意的是，使用 GPT-6 Luna 在中等推理強度下，OpenVLHarness 即以最多 37% 的模型符元成本，超越基礎模型、Codex 與 Visual Sketchpad 在最大強度下的表現 7.7 至 8.5 點，展現出極高的成本效益。

**Q9：消融研究揭示了哪些元件的貢獻？**
A：消融研究分別檢驗了能力層與持久多模態記憶的增量效果，結果顯示兩者皆對最終表現有實質貢獻，缺一不可。這證明了「可解讀的工具輸出」與「可重用的多模態工件」是兩個互補而非冗餘的設計面向——前者讓模型能正確理解工具結果，後者讓模型能在多步驟推理中持續運用先前取得的證據。

**Q10：OpenVLHarness 適用於哪些實際場景？**
A：在需要精確空間測量的場景中（如室內設計、工程估價），系統可結合視覺定位、深度估計與編碼計算來得出具體數值。在需要外部知識查詢的場景中（如長尾實體辨識、文件理解），系統可透過搜尋引擎取得網路參考並整合進推理過程。此外，對於需要處理密集場景中微小物件的任務（如醫療影像、衛星圖分析），放大與分割工具的組合也能顯著提升準確度。

**Q11：在產品化部署上有哪些考量？**
A：論文展示了兩種無需更新 MLLM 權重的客製化工作流程：harness search 透過編輯提示、工具描述與輸出模板來適配特定領域；tool generation 則將現有能力組合成新工具。這種設計大幅降低了領域適配的成本與技術門檻，讓使用者能在不重新訓練模型的情況下，將系統調整至符合其業務需求。此外，系統對異質後端的支援也意味著企業可靈活替換感知模型或搜尋引擎供應商。

**Q12：這項研究對領域的影響為何？**
A：這項研究最重要的啟示在於：證據取得與推論時間擴展是互補而非替代的關係。過去許多研究專注於提升模型的內部推理能力，但本文證明了結合外部工具與記憶機制能以更低的成本取得更大的進步。這為視覺推理系統的設計開啟了新方向——未來的進展可能不僅來自更大的模型或更長的推理鏈，也來自更結構化的證據管理與工具整合。

**Q13：論文承認了哪些限制？**
A：雖然論文未明確列出所有限制，但從實驗結果可推論，系統的表現仍受限於底層工具的能力——若視覺定位或深度估計模型本身不夠準確，後續計算也會受到影響。此外，22 個基準測試雖然涵蓋面廣，但對於某些高度專業化的領域（如醫療診斷、科學影像分析）的適用性仍待驗證。論文中也暗示，工具組合的複雜度增加可能帶來新的錯誤來源，例如編碼代理生成的程式可能存在 bug。

**Q14：可能存在哪些失敗案例？**
A：當任務所需的工具不存在於系統中時，模型將無法取得必要證據而退化為純內部推理模式。另一個潛在失敗情境是當證據渲染無法正確轉譯工具輸出時，模型可能誤解觀察值而導致錯誤推理。此外，在多步驟組合中，若中間步驟的工件未被正確保留或引用，後續步驟可能基於錯誤前提進行計算，造成錯誤的連鎖效應。

**Q15：未來的研究方向有哪些？**
A：未來可朝幾個方向延伸：首先是更細粒度的證據管理，例如支援證據的可信度評估與衝突解決；其次是更強的編碼代理，使其能處理更複雜的多工具組合與錯誤恢復；再者是將系統擴展至影片與時序資料，處理需要跨時間步推理的任務；最後，自動化的工具生成與領域適配機制也值得深入探索，以進一步降低客製化成本並提升系統的通用性。

## 實務應用指南

### 適用場景

1. **室內空間丈量與裝潢規劃**：使用者拍攝房間照片後，系統透過視覺定位工具框出窗戶、櫥櫃等家具，再以深度模型取得距離，最後由程式碼代理計算中心點距離，輸出如「窗戶與櫥櫃中心相距 1.1957 公尺」這類精確量測結果，協助設計師與屋主快速完成丈量。

2. **工業產線瑕疵檢測**：在密集的電路板或紡織品影像中，MLLM 單靠內部推理難以定位微小瑕疵。透過 Segment Anything 等感知後端進行細粒度分割，並以持久記憶保留遮罩與座標，可支援後續的面積、長度統計與缺陷分級。

3. **長尾實體視覺研究**：當問題涉及冷門品牌、罕見地標或非主流產品時，模型內部知識不足。整合網路搜尋工具並保留網頁參考，可讓系統在多輪推理中反覆查證、交叉比對，適用於市場調查、學術文獻回顧與新聞查證。

4. **文件與票據自動化處理**：結合 PaddleOCR-VL 等 OCR 工具抽取文字，再透過程式碼代理對結構化欄位進行彙總、計算與驗證（例如發票金額核對、合約條款比對），適用於財會、法務與行政流程自動化。

5. **醫療影像輔助量測**：在 X 光、CT 或病理切片中定位病灶區域，結合深度估計與分割結果，由程式碼代理計算體積、長徑等量化指標，作為放射科醫師的第二意見工具（仍須由專業人員覆核）。

### 實作前置條件

**資料面**
- 領域影像資料集：至少數百張涵蓋目標場景的影像，用於評估工具後端在自家資料上的表現。
- 標註資料：若採用微調後端，需準備 bounding box、分割遮罩或深度真值；若直接使用預訓練模型（如 Segment Anything 2、Depth Anything V2），可降低標註成本。
- 評測基準：建議準備 22 個基準中與自身任務最相關的子集，用於離線評估。

**運算面**
- MLLM 推論資源：依骨幹模型規模決定，本地部署 Qwen3-VL-8B 等開放模型約需單張 A100/H100；GPT-6 等專有模型可走 API。
- 感知後端 GPU：分割、深度、OCR 等模型可與 MLLM 共用 GPU，但尖峰時段建議分離以避免排隊。
- 程式碼執行沙箱：需具備隔離環境（Docker / Firecracker）以安全執行程式碼代理生成的 Python。

**技能面**
- Python 後端開發、MLLM API 串接、提示工程。
- 熟悉常見視覺模型（SAM、Depth Anything、PaddleOCR）的輸入輸出格式。
- 具備工具呼叫（function calling / tool use）協定的設計經驗。
- 對評測方法論有基本理解，能區分無工具基線與工具增強基線的差異。

### 實作步驟建議

1. **選定骨幹模型並建立基線**：先以無工具方式評估候選 MLLM（開放與專有各一），建立平均分數基線，作為後續比較的錨點。

2. **盤點並部署異質後端**：依任務需求挑選感知（分割、深度、OCR、視覺定位）、搜尋（文字、影像、網頁）與程式碼執行後端，統一封裝為可替換模組。

3. **設計任務層級工具介面**：以「任務詞彙」而非「後端 API」定義工具，例如 `Visual_Grounding_Tool(image, query)`，使後端可替換而不影響編排器。

4. **實作證據渲染層**：為每個工具設計「模型可讀觀察值」，結合視覺化（標註影像、深度圖）、簡潔文字描述與結構化資訊（座標、bbox、JSON），讓 MLLM 能同時「看見」與「讀取」結果。

5. **建立持久多模態記憶**：為每次查詢建立可定址工件庫，註冊影像 ID、結構化資料綁定與網頁參考，確保後續推理可重複取用。

6. **整合程式碼代理**：讓 MLLM 以自然語言描述計算目標，由同一骨幹（或專用程式碼模型）生成 Python，於沙箱中對記憶中的資料執行，並將結果回寫記憶。

7. **設計迭代迴圈**：支援「取得證據 → 視覺檢查 → 組合計算 → 再取得證據」的多輪流程，並在環境更新中即時回報可用的影像 ID 與資料綁定。

8. **離線評估與消融實驗**：分別關閉能力層與記憶，量化兩者的邊際貢獻，作為後續優化方向的依據。

9. **領域特化（可選）**：透過「harness search」自動編輯提示與工具描述，或透過「tool generation」組合既有能力產生新工具，無需更新 MLLM 權重即可適配垂直場景。

10. **上線監控與成本控管**：追蹤每次查詢的模型符元成本、工具呼叫次數與延遲，設定預算上限與降級策略（例如推理強度切換）。

### 潛在風險與注意事項

- **錯誤傳播與幻覺放大**：工具輸出若含噪聲（如不準確的分割、錯誤的網頁摘錄），會被後續推理放大。緩解方式：為每個工具加入信心分數或一致性檢查，並在程式碼代理層加入斷言驗證。

- **成本失控**：多輪工具呼叫與高強度推理會快速累積模型符元成本。緩解方式：設定每查詢最大步數、工具呼叫預算，並在成本逼近上限時自動切換至較低推理強度。

- **程式碼執行安全**：程式碼代理生成的 Python 可能在沙箱外造成損害。緩解方式：使用強隔離執行環境、限制網路與檔案系統存取、靜態掃描危險函式。

- **隱私與資料外洩**：上傳影像與查詢至專有 MLLM API 可能違反個資法規。緩解方式：優先採用本地部署的開放骨幹，或簽署資料處理合約並進行脫敏。

- **後端版本漂移**：感知模型升級可能改變輸出格式，破壞既有渲染邏輯。緩解方式：為每個後端加上版本標籤與相容性測試。

- **基準與真實落差**：論文中 22 個基準的平均提升 9.7–12.6 點未必能直接外推到自家資料。緩解方式：在自有資料上做小規模先導實驗，並關注基準中與自身任務最相近的子集表現。

- **長尾失敗模式**：當工具全部失敗時，編排器可能陷入空轉。緩解方式：設計明確的終止條件與「無法回答」回退路徑。

### 與其他技術的整合建議

- **RAG 系統**：將持久多模態記憶視為視覺版的 RAG 索引，文字 RAG 負責文件知識，視覺工具負責影像證據，兩者可共享同一個編排器與評測框架。

- **企業知識庫**：將搜尋工具的後端換成企業內部搜尋引擎（如 Elasticsearch、Confluence API），即可把 OpenVLHarness 改造成內網視覺助理，處理內部圖表、流程圖與產品照片。

- **BI 與儀表板**：將程式碼代理的計算結果串接至儀表板（例如將量測數據寫入資料庫，再由 Tableau / Power BI 視覺化），形成「提問 → 推理 → 報表」閉環。

- **CI/CD 與評測流水線**：把 22 個基準的評測腳本化，納入模型升級或後端替換時的自動回歸測試，避免效能倒退。

- **多代理系統**：可將 OpenVLHarness 作為「視覺專家」節點，與文字推理代理、規劃代理組成更大的多代理工作流，由上層代理分派視覺子任務。

- **邊緣部署**：對於延遲敏感場景，可將輕量感知後端（小型分割、單目深度）部署於邊緣裝置，僅將高階推理交由雲端 MLLM，兼顧即時性與能力。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節的「問題動機」部分，理解「為什麼單純加大推論預算效果有限」這個關鍵洞察；接著瀏覽圖 1 的系統架構圖，建立「編排器 ↔ 能力層 ↔ 持久記憶」的三層心智模型，再回頭看細節會輕鬆許多。

**給 AI 工程師**：重點放在第 2 節的能力層設計與證據渲染機制，這是與一般 function calling 框架最大的差異；同時仔細閱讀持久記憶的工件定址方式與程式碼代理的整合細節，這些是落地時最容易踩坑的地方；評測章節的消融實驗則提供了明確的優化優先順序。

**給研究者**：第 3 節的 22 個基準分布與第 4 節的消融設計值得深讀，特別是「能力層 vs. 記憶」的拆解方式，以及「harness search / tool generation」這類無需更新權重的特化路徑；推論時間擴展與工具使用的互補性結論（圖 1c）也是值得延伸的研究方向。

**給產品經理**：聚焦在「真實世界視覺任務需要什麼」這個問題意識，以及 9.7–12.6 點的平均提升背後代表的使用者價值；成本段落（GPT-6 Luna 中等強度即可超越最大強度的 Codex 與 Visual Sketchpad，且僅需 37% 符元成本）是評估 ROI 的關鍵數字；領域特化段落則說明了如何以低成本將系統導入垂直場景。
