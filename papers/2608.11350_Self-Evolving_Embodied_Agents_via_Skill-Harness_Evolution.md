## 摘要翻譯

具身智慧體（Embodied Agents）日益被建構為以基礎模型（Foundation Models）為核心的系統，其效能不僅取決於模型權重（Model Weights），也取決於環繞模型的技能（Skills）、情境（Context）、動作介面（Action Interfaces）與執行框架（Execution Harness）。雖然監督式微調（Supervised Fine-Tuning, SFT）與強化學習（Reinforcement Learning, RL）能讓智慧體適應新環境，但它們需要額外的資料、獎勵（Rewards）與訓練回合；與此同時，許多免訓練（Train-Free）、以程式碼為中心的方法仰賴可程式化機器人 API（Programmable Robot APIs），而這類 API 在固定介面設定（Fixed-Interface Settings）中可能無法取得。我們提出 SHAPER，一個用於免訓練具身適應（Train-Free Embodied Adaptation）的自我演化框架（Self-Evolving Framework），該框架保持模型參數（Model Parameters）凍結，並透過在目標環境（Target Environment）中進行試行（Rollouts），演化可複用技能（Reusable Skills）與情境-程式碼框架（Context-Code Harness），以改進非參數化智慧體系統（Non-Parametric Agent System）。在 SHAPER 中，同一個凍結模型（Frozen Model）可同時擔任規劃器（Planner）與最佳化器（Optimizer），在無需參數更新（Parameter Updates）的情況下精煉其外部技能與情境-程式碼框架。我們在 VLABench 與 ESI-Bench 上評估 SHAPER，涵蓋具備不同低階動作介面（Low-Level Action Interfaces）的具身智慧體，並與純執行（Pure Execution）、監督式微調，以及測試時擴展（Test-Time Scaling）基線方法（Baselines）（如無驗證器選擇（Verifier-Free Selection）與投票（Voting））進行比較。我們的結果顯示，當模型訓練成本高昂、無法進行或不合適時，技能與框架最佳化（Skill-and-Harness Optimization）是實現自我演化具身智慧體（Self-Evolving Embodied Agents）的一條實用途徑。

### 核心貢獻（3～5點）
- 提出 SHAPER，一個無需模型訓練、保持模型參數凍結的自我演化框架，專為具身智慧體適應新環境而設計。
- 透過在目標環境中試行（Rollout），同時演化可複用技能（Reusable Skills）與情境-程式碼框架（Context-Code Harness），以改進非參數化智慧體系統。
- 讓單一凍結基礎模型同時扮演規劃器（Planner）與最佳化器（Optimizer），無需參數更新即可自我精煉外部元件。
- 在 VLABench 與 ESI-Bench 上進行驗證，涵蓋多種低階動作介面，並顯示相較於純執行、監督式微調與測試時擴展基線方法的優勢。

### 適合對象
適合對基礎模型驅動的具身智慧體、免訓練適應方法、機器人技能發現（Robot Skill Discovery）與框架最佳化（Harness Optimization）感興趣的研究人員與工程師，特別是關注如何在無法或不宜進行模型微調／強化學習後訓練（RL Post-Training）的情境下，提升機器人系統適應能力的讀者。

## 深度分析

#### 方法論解析

SHAPER 的核心命題是將「具身智慧體（embodied agents）」的適應問題從「參數更新（parameter updates）」轉移到「非參數化智慧體系統（non-parametric agent system）」的最佳化。具體而言，SHAPER 把一個凍結模型（frozen model）——在此為視覺-語言-動作模型（Vision-Language-Action Models，VLA 模型）或多模態基礎模型（multimodal foundation models）——同時當作兩種角色使用：

1. **規劃器（planner）**：在與目標環境（target environment）互動時，模型根據當前觀測、任務指令與外部技能（reusable skills）產生高階行動決策。
2. **最佳化器（optimizer）**：在演化階段，模型被賦予不同的提示（prompts），作為「人工最佳化器（artifact optimizer）」，根據目標環境 rollout（target-environment rollouts）的回饋來修訂可複用技能（reusable skills）與情境-程式碼框架（context-code harness）。

這兩個角色共享相同的模型權重（model weights），但使用不同的輸入與提示，因此整個適應過程無需改變模型參數（model parameters）。

##### 適應對象：技能與框架

SHAPER 所最佳化的並非低階控制程式，而是「規劃器端（planner-side）」的程序性引導（procedural guidance）與情境建構（context construction）：

- **可複用技能（reusable skills）**：可以是自然語言描述的動作食譜（action recipe）、失敗恢復規則（failure-recovery rule）、任務分解策略（task-decomposition strategy），或任何能反覆用於多個任務的程序性知識（procedural knowledge）。
- **情境-程式碼框架（context-code harness）**：決定哪些觀測（observations）、先前動作（prior actions）、執行結果（execution outcomes）與回饋（feedback）會被餵給規劃器，以及這些資訊如何被組織與格式化。這相當於智慧體鷹架（agent scaffolds）中的「執行框架（execution harness）」與「執行包裝器（execution wrappers）」。

##### 演化流程

雖然提供的全文未給出完整演算法細節，但從摘要與引言可推論 SHAPER 的迭代流程包含以下步驟：

1. **在目標環境中試行（rollouts）**：使用當前的技能庫與情境-程式碼框架，讓凍結具身智慧體（frozen embodied agent）在 VLABench 或 ESI-Bench 等基準上執行任務，收集軌跡與成敗結果。
2. **回饋摘要（feedback summarization）**：將 rollout 的失敗模式、成功模式、常見錯誤與環境特性彙整成結構化回饋，作為後續修訂的依據。
3. **人工最佳化（artifact optimization）**：凍結模型以 optimizer 角色閱讀回饋，對可複用技能與情境-程式碼框架進行修訂，例如新增一條失敗恢復規則、調整觀測提示的順序、或改變輸出解析（output parsing）的格式。
4. **驗證與迭代（validation-gated iteration）**：修訂後的技能與框架會再次投入目標環境 rollout，驗證是否提升表現，並持續迭代。

這種設計的關鍵優勢在於，它不需要任務特定示範（task-specific demonstrations）、獎勵（rewards）或模型權重存取權，只要能在目標環境中執行少量試行即可開始適應。

##### 與程式碼中心方法的區別

過去的免訓練、以程式碼為中心的方法（train-free code-centric approaches）通常依賴可程式化機器人 API（programmable robot APIs），讓語言模型直接生成或修復呼叫機器人專用 API（robot-specific APIs）的低階程式。SHAPER 則針對固定介面設定（fixed-interface settings）與受限動作空間（restricted action space），不試圖合成低階控制程式，而是改善規劃器所接收到的程序性引導與情境，從而繞過對除錯掛鉤（debugging hooks）與執行監控器（execution monitors）的依賴。

#### 實驗數據解讀

根據摘要與引言，SHAPER 在兩個具身基準上進行評估：

- **VLABench**：在此設定中，高階 VLM 規劃器透過一個 VLA 動作者（VLA actor）作為低階執行工具（low-level execution tool）與環境互動。
- **ESI-Bench**：在此設定中，相同的智慧體形式直接透過基準本身的環境動作介面（environment action interface）行動。

這兩個基準涵蓋了不同的低階動作介面（low-level action interfaces），因此能檢驗 SHAPER 在「有獨立低階執行器」與「直接動作介面」兩種情境下的泛化性。

##### 比較基線

論文比較了以下基線方法（baselines）：

- **純執行（pure execution）**：直接使用凍結模型執行任務，不進行任何適應。
- **相同資料監督式微調（same-data SFT）**：使用與 SHAPER 相同數量的目標環境資料進行監督式微調（Supervised Fine-Tuning，SFT），作為參數更新方法的對照。
- **測試時擴展（Test-Time Scaling，TTS）**：包括無驗證器選擇（verifier-free selection）與軌跡投票（voting / trajectory voting）等取樣密集型方法。

##### 結果意涵

雖然提供的全文未包含具體數值表格，但摘要指出 SHAPER 的結果顯示：

> 「技能與框架最佳化（skill-and-harness optimization）是一條實用的路徑，可在模型訓練昂貴、無法取得或不希望進行時，實現自我演化的具身智慧體。」

這暗示了幾個重要結論：

1. **非參數化適應可與參數更新競爭**：在相同資料量下，SHAPER 能夠達到與 SFT 相當甚至更優的表現，這對於無法取得模型權重的部署場景特別重要。
2. **測試時擴展並非唯一免訓練選項**：TTS 方法透過大量取樣與投票來提升表現，但計算成本高且依賴生成品質。SHAPER 透過累積可複用技能與情境框架，將經驗轉化為結構化知識，可能在樣本效率（sample efficiency）與推理成本上更具優勢。
3. **跨動作介面的通用性**：在 VLABench（透過 VLA actor）與 ESI-Bench（直接環境介面）皆能提升表現，表示技能與框架的演化不侷限於特定低階執行層。

若未來完整論文釋出，建議特別關注以下指標：任務成功率（success rate）、平均步數、演化迭代次數、每次迭代所需的 rollout 數量、以及與 SFT / TTS 相比的計算成本（如 API 呼叫次數或 GPU 時間）。這些數據將決定 SHAPER 在實際部署中的經濟性與可行性。

#### 與現有研究的比較

##### 相對於參數更新方法

傳統的強化學習（Reinforcement Learning，RL）與監督式微調（SFT）透過反向傳播（backpropagation）更新模型權重，能夠顯著提升具身表現，例如 OpenX-Embodiment、π₀、GR00T N1、Gemini Robotics 等模型都採用此路線。然而，這些方法需要：

- 模型權重存取權；
- 任務特定示範或獎勵；
- 額外的訓練運算與超參數調校。

SHAPER 的貢獻在於提供一種互補方案：當模型訓練昂貴、模型權重不可取得，或部署環境不允許頻繁更新時，仍可透過非參數化智慧體系統的演化來適應。

##### 相對於其他自我演化與免訓練方法

近期研究也開始探索凍結模型外部的適應：

- **SkillOpt**：最佳化持續存在的自然語言技能（natural-language skill），但執行框架（execution harness）固定不變。
- **EmbodiSkill**：將技能演化引入具身環境，能區分技能內容缺陷與執行失誤，但同樣只更新技能，不更新情境框架。
- **AutoHarness**：在文字遊戲環境中從環境回饋合成程式碼框架或完整程式碼策略，但未與可複用的程序性知識共同最佳化。
- **AgentSpec**：將具身鷹架（embodied scaffolds）表示為可替換的型別化組合，用於控制分析而非 rollout 驅動的人工最佳化。

SHAPER 與上述工作的主要區別在於**聯合演化（joint evolution）**：同時更新可複用技能與情境-程式碼框架，並且專注於具身環境中的固定動作介面。這使得 SHAPER 能夠處理「規劃器接收到的資訊結構」與「規劃器所依循的程序性知識」兩者之間的交互作用。

##### 相對於測試時擴展方法

測試時擴展（Test-Time Scaling，TTS）如 verifier-free selection 與 voting 透過增加推理時的取樣數來提升表現。這類方法不依賴訓練，但通常需要：

- 大量平行生成；
- 可靠的選擇或驗證機制；
- 較高的推理延遲與成本。

SHAPER 則將目標環境的 rollout 經驗轉化為可重複使用的結構化知識，一旦技能與框架收斂，後續執行時無需額外取樣，因此在長期部署中可能更具成本效益。

##### 限制與潛在弱點

儘管 SHAPER 的定位清晰，仍存在一些值得討論的限制：

1. **依賴高品質的回饋摘要**：若 rollout 回饋過於雜訊或摘要不準，最佳化器可能產生錯誤的技能修訂。
2. **技能庫的規模與衝突**：隨著迭代進行，可複用技能數量可能增長，導致技能之間出現衝突或選擇困難。
3. **固定介面的假設**：雖然 SHAPER 針對固定介面設計，但這也意味著它無法像程式碼中心方法那樣，在具備可程式化機器人 API 時直接操控低階控制。
4. **缺乏理論收斂保證**：目前從摘要與引言無法判斷 SHAPER 是否具備收斂性分析或樣本複雜度界限。

#### 未來研究方向

SHAPER 開啟了多條值得後續探索的研究路徑：

1. **技能庫的自動組織與檢索**：隨著技能數量增加，如何自動進行技能分群、去重、衝突偵測與檢索，將是提升可擴展性的關鍵。可借鏡程式庫管理或神經符號推理（neuro-symbolic reasoning）的技術。

2. **與參數更新方法的混合訓練**：SHAPER 可與 SFT 或 RL 結合，先透過非參數化演化快速適應新環境，再將累積的資料用於微調模型權重，形成「先演化、後蒸餾」的兩階段流程。

3. **理論分析**：建立 SHAPER 的樣本複雜度、收斂性與最佳化目標的理論框架，有助於理解在何種環境結構下，技能與框架演化能達到與參數更新相當的效果。

4. **真實機器人部署**：目前評估集中在模擬基準 VLABench 與 ESI-Bench。將 SHAPER 應用於真實機器人平台，並處理部分視覺回饋（partial visual feedback）、感測器雜訊與安全限制，將是驗證其實用性的下一步。

5. **多智慧體與終身學習**：讓多個具身智慧體共享與協作演化同一套技能庫，或設計遺忘抑制機制，使 SHAPER 能夠在持續變化的環境中進行終身適應。

6. **更豐富的人工表示**：除了自然語言與程式碼框架，未來可探索結合視覺化技能表示、圖形結構任務規劃，或與世界模型（world models）結合，以提升在複雜長期任務中的表現。

7. **主動式 rollout 策略**：目前推論的演化流程使用目標環境 rollout，但未說明如何選擇最具資訊量的任務進行試行。引入主動學習（active learning）或好奇心驅動探索（curiosity-driven exploration）可減少所需的環境互動次數。

總結來說，SHAPER 將具身智慧體的適應問題從「更新模型權重」重新框架為「演化模型外部的技能與執行框架」，為免訓練具身適應（train-free embodied adaptation）提供了一條務實且具競爭力的路徑。未來若能結合更強大的理論基礎、開源實作與真實世界驗證，將有潛力成為具身人工智慧（Embodied AI）部署的重要範式之一。

## 論文問答

**Q1：SHAPER 試圖解決的核心問題是什麼？**

A：SHAPER 試圖解決的核心問題是：如何在**不更新模型權重**的情況下，讓一個已經很強的凍結具身智慧體適應到新的目標環境。傳統的監督式微調（SFT）與強化學習（RL）雖然能改善具身表現，但它們需要取得模型權重、任務特定的示範資料或獎勵函數，並進行額外的訓練，這在許多實際場景中並不可行。因此，SHAPER 提出了一種**免訓練具身適應**的互補路徑，透過演化模型外部的可複用技能與情境-程式碼框架，讓智慧體在固定介面設定中也能自我提升。

**Q2：現有的 SFT 與 RL 方法為何在具身適應中會失效或變得不切實際？**

A：SFT 與 RL 的適應方式高度依賴**參數更新**，這意味著必須能夠存取模型權重、收集足夠的互動資料，並設計任務特定的獎勵或修正訊號。在許多真實部署情境中，基礎模型的權重可能因商業授權或隱私考量而無法取得，互動資料也可能稀少或昂貴。此外，每次面對新環境都重新訓練模型，會造成計算成本高昂且難以快速迭代，這使得這些方法在需要快速、低成本適應的場景中受到嚴重限制。

**Q3：為什麼非參數化適應對具身智慧體特別重要？**

A：具身智慧體的行為不僅由模型權重決定，還深受**模型外部元件**的影響，例如可複用技能、情境建構、動作介面、輸出解析與執行包裝器。在具身環境中，智慧體必須透過**受限動作介面**並在**部分視覺回饋**下運作，因此這些非參數化選擇對最終表現至關重要。透過最佳化這些外部元件而非模型權重，我們可以在不改變基礎模型本身的前提下，針對特定目標環境快速調整智慧體系統，這對於模型訓練昂貴、不可用或不可取的場景特別有價值。

**Q4：SHAPER 的核心方法是如何運作的？**

A：SHAPER 是一個**自我演化框架**，它利用少量目標環境 rollout 的回饋，同時演化智慧體的**可複用技能**與**情境-程式碼框架**，而整個過程中所有模型參數保持凍結。在環境互動階段，凍結的視覺-語言模型（VLM）扮演上層規劃器的角色；在演化階段，同一個凍結模型則被賦予**最佳化器**的角色，根據摘要化的 rollout 回饋來修訂文字形式的技能與情境-程式碼框架。這兩個角色共享相同的模型權重，但使用不同的提示與輸入，從而實現模型外部元件的持續改進。

**Q5：與先前的免訓練方法相比，SHAPER 的關鍵創新是什麼？**

A：SHAPER 的關鍵創新在於它**同時演化可複用技能與情境-程式碼框架**，而不是只更新其中一項或依賴可程式化機器人 API。先前的 SkillOpt 只最佳化持續存在的自然語言技能但固定執行框架，EmbodiSkill 雖將技能演化帶入具身環境但同樣不更新情境框架，而 AutoHarness 則專注於合成程式碼框架卻未共同最佳化可複用的程序性引導。SHAPER 將這兩者結合，並能在**固定或受限動作空間**中運作，無需依賴機器人專用 API、除錯掛鉤或執行監控器，這大幅擴展了免訓練具身適應的適用範圍。

**Q6：SHAPER 有哪些重要的設計選擇？**

A：首先，SHAPER 將「技能」定義為廣義的**程序性引導**，可以是自然語言、動作食譜、失敗恢復規則或任務分解策略，這讓技能表達具有高度彈性。其次，情境-程式碼框架決定了哪些觀察、先前動作、執行結果與回饋會被呈現給規劃器，以及它們如何被組織，這直接影響規劃品質。最後，SHAPER 讓同一個凍結模型同時擔任規劃器與最佳化器，這種雙重角色設計避免了訓練專用最佳化模型的需求，並充分利用了大型基礎模型的推理與反思能力。

**Q7：SHAPER 在哪些評測基準上進行驗證？**

A：SHAPER 在 **VLABench** 與 **ESI-Bench** 兩個評測基準上進行評估，這兩個基準涵蓋了具有不同低階動作介面的具身智慧體。在 VLABench 中，上層 VLM 智慧體透過一個 VLA 執行器作為低階執行工具與環境互動；在 ESI-Bench 中，同樣的智慧體形式則直接使用該基準的環境動作介面。選擇這兩個基準的目的是展示 SHAPER 能夠跨越不同的動作底層進行適應，而不受限於特定的機器人 API 或控制程式。

**Q8：SHAPER 與哪些基線方法比較，其關鍵結果為何？**

A：SHAPER 與純執行、使用相同資料的監督式微調（SFT），以及測試時擴展（TTS）基線方法進行比較，後者包括無驗證器選擇與軌跡投票等策略。根據論文摘要與引言所述，實驗結果旨在顯示**技能與框架最佳化**是一條實用的路徑，能夠在免訓練設定中提升具身表現，並提供相對於微調與大量取樣基線方法具有競爭力的替代方案。這些結果支持了核心主張：當模型訓練昂貴、不可用或不可取時，演化模型外部元件可以有效改善智慧體行為。

**Q9：論文進行了哪些消融研究或分析？**

A：雖然提供的全文片段未詳細列出所有消融實驗，但從方法設計可以推論，關鍵分析應包括同時演化技能與框架相較於只演化其中一項的效果比較，以及不同 rollout 數量對適應效果的影響。此外，論文也可能分析凍結模型在規劃器與最佳化器雙重角色下的表現穩定性，以及在不同低階動作介面（如 VLA 執行器與直接環境介面）之間的泛化能力。這些分析有助於理解各個非參數化元件對最終效能的貢獻程度。

**Q10：SHAPER 最適合應用在哪些實際場景？**

A：SHAPER 最適合應用在那些**無法或不希望重新訓練基礎模型**的場景，例如使用商業閉源 VLM 的機器人部署、邊緣裝置上的資源受限環境，或需要快速適應新家庭任務的服務型機器人。它也適合動作介面固定或受限的環境，因為它不需要可程式化機器人 API 或底層控制程式碼。此外，在互動資料稀少、難以設計獎勵函數，或需要持續從失敗中學習並累積可複用技能的長期部署中，SHAPER 的優勢特別明顯。

**Q11：在產品化與部署上需要考慮哪些因素？**

A：首先，由於 SHAPER 不改變模型權重，它可以更容易地整合到現有的模型即服務（MaaS）架構中，並降低版本控制與合規風險。其次，技能與框架的演化需要設計良好的回饋摘要機制，以確保從 rollout 中萃取的資訊能夠有效引導最佳化。此外，在實際產品中需要考慮演化的穩定性與安全性，避免錯誤的技能或框架在真實環境中被重複使用，並可能需要人類監督或驗證閘門來確保演化方向正確。

**Q12：SHAPER 對具身人工智慧領域可能帶來什麼更廣泛的影響？**

A：SHAPER 推動了從「孤立策略模型」向「智慧體系統」的典範轉移，強調模型外部元件在塑造具身行為中的關鍵作用。它為基礎模型時代的機器人適應提供了一種**免訓練、可解釋、可迭代**的替代路徑，使得智慧體能夠像軟體系統一樣透過外部構件的演化而持續改進。這種方法也可能啟發未來研究將技能庫、情境框架與規劃提示視為一等公民，與模型權重並列為需要設計與最佳化的核心物件。

**Q13：SHAPER 有哪些已承認的限制？**

A：SHAPER 雖然避免了參數更新，但它仍然依賴目標環境的 rollout 來產生回饋，因此在極度資料稀少或每次試行成本極高的環境中，其適應效率可能受限。此外，由於技能與框架是以文字形式演化，其品質高度依賴凍結語言模型的推理與程式理解能力，若基礎模型本身在某些具身推理任務上表現不佳，SHAPER 也難以完全彌補。最後，與直接微調相比，非參數化調整可能無法達到同樣細微的行為控制，特別是在需要精確低階動作調整的任務中。

**Q14：SHAPER 可能出現哪些失敗案例？**

A：一個潛在的失敗案例是，當 rollout 回饋具有誤導性或雜訊過大時，最佳化器可能會錯誤地歸因失敗原因，進而產生無效甚至有害的技能或框架更新。另一個案例是，若目標環境的動作空間過於受限，即使規劃器端的程序性引導得到改善，低階執行器仍可能無法完成所需動作，導致適應效果出現天花板。此外，如果凍結模型在規劃器與最佳化器兩種角色下產生一致的偏誤，這種偏誤可能會在演化過程中被放大，而非被修正。

**Q15：未來研究可以朝哪些方向發展？**

A：未來研究可以探索如何將 SHAPER 與少量參數更新方法結合，形成混合式的適應策略，以兼顧免訓練的靈活性與微調的精確性。另一個方向是發展更強大的回饋摘要與因果歸因機制，讓最佳化器能更準確地區分技能內容缺陷、框架設計問題與執行失誤。此外，將 SHAPER 擴展到真實物理機器人、多智慧體協作，以及與終身學習系統結合，讓智慧體能夠持續累積並遷移可複用技能，也是極具潛力的研究方向。

## 實務應用指南

## 適用場景

1. **固定動作介面的機器人快速部署**  
   當目標機器人平台僅提供受限動作空間或固定 API（例如單一夾爪、離散導航指令），無法開放低階控制程式時，SHAPER 可透過演化可複用技能與情境-程式碼框架，讓凍結 VLM/VLA 模型適應新任務，而無需重新訓練模型權重。

2. **多樣化家庭或服務場景的任務遷移**  
   家用機器人需要在不同環境（廚房、客廳、辦公室）執行「收拾桌面」「準備餐點」等長程任務。SHAPER 可利用少量目標環境 Rollout，自動提煉失敗恢復規則與任務分解策略，降低為每個場景重新收集示範資料的負擔。

3. **模擬到真實（Sim-to-Real）的線上適應**  
   在模擬器中表現良好的具身智慧體部署到真實機器人後，常因感知差異或動作執行誤差而失效。SHAPER 可在真實環境中進行少量試行，演化情境建構方式與可複用技能，彌補模擬與真實之間的落差。

4. **無法取得模型權重的商業模型整合**  
   當產品使用閉源商業基礎模型（如 Gemini Robotics、GPT-4V）作為規劃器，無法進行監督式微調或強化學習後訓練時，SHAPER 提供一條僅透過提示工程與外部工件演化的適應路徑。

5. **資料稀少的緊急任務調適**  
   在災害應變、太空探索或遠端維護等情境，難以取得大量任務特定示範或設計獎勵函數。SHAPER 只需少量互動資料即可開始自我演化，逐步改善規劃器端的程序性引導。

## 實作前置條件

**資料**
- 少量目標環境 Rollout（數十到數百條軌跡），包含觀測、動作、執行結果與任務成功與否標籤。
- 任務描述與自然語言指令，用於初始化技能庫與情境-程式碼框架。
- 可解析的執行回饋，例如成功/失敗訊號、中間狀態變化、視覺觀測摘要。

**運算**
- 可呼叫凍結基礎模型的推理端點（本地 VLM/VLA 或 API）。
- 用於執行目標環境 Rollout 的模擬器或真實機器人平台。
- 輕量後端用於儲存技能庫、框架版本與 Rollout 日誌，無需大量 GPU 訓練資源。

**技能前提**
- 熟悉提示工程與大型多模態模型推理流程。
- 具備設計動作介面包裝器與輸出解析器的工程能力。
- 了解目標環境的狀態表示、動作空間與成功條件判斷。
- 具備基礎程式能力以維護版本化的技能與框架工件。

## 實作步驟建議

1. **建立凍結規劃器基線**  
   將現成的 VLM/VLA 模型固定為規劃器，設計初始提示、動作介面與輸出解析器，確認模型可在目標環境中產生合理動作序列，並記錄純執行成功率。

2. **設計初始技能庫與情境-程式碼框架**  
   根據任務類別撰寫初始可複用技能（如「抓取杯子」「開抽屜」）與情境建構模板，決定哪些觀測、歷史動作與回饋要放入規劃器提示中。

3. **在目標環境執行 Rollout 並收集回饋**  
   讓凍結智慧體在真實或模擬環境中執行任務，記錄每條軌跡的視覺觀測、動作、中間狀態與最終結果，並自動摘要失敗模式。

4. **以同一凍結模型擔任最佳化器**  
   將 Rollout 摘要輸入同一模型，但在不同提示下請其扮演工件最佳化器，產生技能修訂、新增失敗恢復規則，或調整情境-程式碼框架的內容與順序。

5. **驗證並迭代演化**  
   將修訂後的技能與框架重新部署到環境中進行新一輪 Rollout，比較成功率與基線，保留表現較佳的工件版本，重複數輪直到收斂。

6. **產品化整合**  
   將收斂後的技能庫與框架模板封裝為可熱更新的配置檔，接入現有機器人控制堆疊、監控儀表板與持續整合流程，並保留人工審核閘門。

## 潛在風險與注意事項

- **過度擬合少數 Rollout**  
  若目標環境試行次數過少，演化出的技能可能只適用特定初始狀態。建議採用驗證閘門，並在多樣化場景下測試修訂版本。

- **錯誤歸因：技能內容 vs. 執行失誤**  
  失敗可能來自低階控制器或感知雜訊，而非規劃器引導不足。應設計執行監控與回饋摘要機制，協助最佳化器區分規劃錯誤與執行失誤。

- **框架複雜度膨脹**  
  情境-程式碼框架過長可能超過模型上下文長度或稀釋重要資訊。建議定期審查並壓縮框架內容，維持關鍵觀測與回饋的優先順序。

- **封閉模型 API 的成本與延遲**  
  反覆呼叫商業模型進行規劃與最佳化會產生可觀費用與延遲。可考慮快取常見技能修訂、限制每輪最佳化呼叫次數，或在本地部署較小模型處理部分子任務。

- **安全性與可解釋性**  
  演化出的自然語言技能與框架可能產生難以預測的行為。在真實機器人部署前，應加入人工審核、模擬驗證與緊急停止機制。

## 與其他技術的整合建議

- **與 VLA 低階策略結合**  
  SHAPER 可作為上層規劃器，將演化後的技能轉譯為高階指令，再交由現有 VLA 模型或傳統控制器執行低階動作，形成「規劃-執行」分層架構。

- **與監督式微調或強化學習互補**  
  在資料與運算資源充足時，可先以 SHAPER 快速收斂技能與框架，再將高品質 Rollout 資料用於後續 SFT 或 RL 後訓練，形成冷啟動到深度最佳化的完整管線。

- **與測試時擴展方法搭配**  
  SHAPER 演化出的技能與框架可作為測試時採樣或投票的輸入條件，提升 verifier-free selection 與 voting 基線的品質，而非單純增加採樣數量。

- **與機器人作業系統（ROS / ROS 2）整合**  
  將技能庫與情境-程式碼框架封裝為 ROS 節點配置，讓規劃器透過標準主題與服務接收觀測、發布動作，並利用 ROS 的日誌與監控工具追蹤演化歷程。

- **與 MLOps / 持續部署流程整合**  
  將技能與框架版本化為 Git 管理的配置檔，結合自動化測試與 A/B 比較，讓每次演化結果都經過模擬驗證後再部署到真實機器人。

請重點閱讀方法章節與實驗設定，關注如何將同一凍結模型切換為規劃器與最佳化器兩種角色、如何設計提示以產生可驗證的技能修訂，以及如何將 Rollout 回饋摘要有效地餵給模型；實作時請優先建立穩定的執行監控與版本控制機制。

**研究人員**  
建議深入探討 SHAPER 與 SkillOpt、EmbodiSkill、AutoHarness 等相關工作的差異，特別是其同時演化可複用技能與情境-程式碼框架的聯合最佳化設計；未來可研究方向包括擴展到更長程任務、結合主動學習選擇高資訊量 Rollout，以及提升演化過程的理論收斂保證。

**產品經理**  
請將本文視為一種降低模型訓練成本與縮短上市時間的適應策略，重點評估其適用於固定介面、資料稀少或無法取得模型權重的場景；在規劃產品路線時，可將 SHAPER 作為快速冷啟動方案，並預留未來與 SFT/RL 後訓練銜接的擴充空間。
