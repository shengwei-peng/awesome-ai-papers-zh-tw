## 深度分析

#### 方法論解析

Video-Coder 提出了一種嶄新的「程式碼驅動影片生成」(code-driven video generation) 範式，將傳統端到端 (end-to-end) 的影片生成重新框架化為一個代理式程式設計任務 (agentic programming task)。其核心方法論可從以下幾個層面深入剖析：

**1. 整體框架設計**

Video-Coder 的運作流程可分為三個階段：(1) 給定文字提示 (text prompt)，代理 (agent) 透過大型語言模型 (LLM) 撰寫可執行程式碼 (executable program)；(2) 程式碼在 Video-Coder Harness 沙盒 (sandbox) 中執行，建構動態三維場景 (dynamic 3D scene)，並渲染為草稿影片 (Draft Video)；(3) 草稿影片作為下游影片生成器 (downstream video generator) 的結構與運動條件訊號，產出最終影片。這種「程式碼 → 3D 場景 → 草稿影片 → 最終影片」的兩階段設計，本質上是將隱式學習的影片分佈 (video distribution) 轉化為顯式、可驗證的程式語意。

**2. Video-Coder Harness 的設計**

Video-Coder Harness 是支撐整個代理訓練與推論 (inference) 的統一互動式環境 (interactive environment)，整合了三項關鍵功能：(a) 程式碼執行 (code execution)，提供安全的沙盒環境；(b) 三維場景渲染 (3D scene rendering)，將程式碼建構的場景轉為視覺化輸出；(c) 執行回饋 (execution feedback)，將錯誤訊息與渲染結果回傳給代理，使其能進行多輪互動 (multi-turn interaction) 修正程式碼。這種「環境即獎勵來源」的設計，是將 LLM 代理從靜態提示流程推向真正代理式強化學習 (agentic reinforcement learning) 的關鍵基礎設施。

**3. 資料建構流程 (Data Construction Pipeline)**

作者設計了一套專屬的資料建構流程，產出兩個高品質資料集：
- **Video-Coder-SFT-6k**：用於監督式微調 (SFT)，包含 6,000 筆多樣化提示與對應的代理軌跡 (agentic trajectories)，由 Gemini 3.8 Flash 透過反覆的「撰寫→執行→修訂」過程產生。
- **Video-Coder-RL-2k**：用於強化學習 (RL)，包含 2,000 筆經品質篩選的提示與真實參考影片 (ground-truth reference video)，後者由 Minimax-H3 根據提示與草稿影片合成。

此流程的巧妙之處在於：先以強大的閉源模型產生高品質軌跡作為「教師示範」，再以小型開源模型學習這些軌跡，最終透過 RL 進一步超越教師模型的侷限。

**4. 雙階段訓練策略**

訓練分為兩個階段：
- **SFT 階段**：賦予模型基礎的場景程式設計與工具呼叫 (tool-calling) 能力，使其能產生可執行的程式碼。
- **Harness-native Agentic RL 階段**：在互動式環境中，透過獎勵訊號 (reward signal) 進一步最佳化代理軌跡。

**5. 雙重獎勵回饋 (Dual Reward Feedback) 設計**

這是本文最具方法論創新性的部分：
- **基於執行的獎勵 (Execution-based Reward)**：衡量生成程式的可執行性，確保程式碼能正確運行並建構預期場景。
- **基於影片的獎勵 (Video-based Reward)**：評估最終生成影片的品質，包括視覺保真度 (visual fidelity)、時間一致性 (temporal consistency) 與物理合理性。

**6. 退火訓練策略 (Annealing Training Strategy)**

作者引入了一個精心設計的退火排程：在訓練初期，執行獎勵佔主導地位，穩定早期訓練並確保程式可執行性；隨著訓練進行，執行獎勵的權重逐漸降低，影片獎勵的影響逐漸增強，最終在後期階段由影片獎勵主導，直接最佳化最終影片品質。這種設計解決了 RL 中常見的「獎勵權衡」問題——若僅依賴影片獎勵，早期訓練可能因程式無法執行而缺乏有效學習訊號；若僅依賴執行獎勵，則無法直接最佳化最終目標。退火策略在兩者間取得了動態平衡。

#### 實驗數據解讀

**1. 主要量化結果**

根據摘要與引言所述，Video-Coder 帶來了顯著的效能提升：
- **PhyGenBench**：以 Minimax-H3 為基座模型時，提升約 **7 點**。
- **VBench-2.0**：同樣以 Minimax-H3 為基座，提升約 **24 點**。

這兩個基準的選擇具有重要意義：PhyGenBench 專注於物理生成評測，衡量模型對物理定律（如重力、碰撞、運動慣性）的遵循程度；VBench-2.0 則是更全面的影片生成評測基準，涵蓋多個維度。24 點的 VBench-2.0 提升幅度極為可觀，顯示 Video-Coder 不僅改善物理一致性，也在更廣泛的影片品質維度上帶來增益。

**2. 結果的深層意涵**

- **物理合理性的顯著改善**：PhyGenBench 上的 7 點提升直接驗證了「程式碼作為物理先驗」假設的正確性。透過顯式建構 3D 場景，模型被迫遵守物理約束，這是純像素空間 (pixel space) 或潛在空間 (latent space) 學習難以達成的。
- **跨基準的泛化能力**：在兩個不同性質的基準上同時取得大幅提升，說明 Video-Coder 並非僅針對特定指標過擬合，而是帶來了結構性的改善。
- **基座模型的相對獨立性**：實驗聲稱「across different backbones」皆有一致提升，這暗示 Video-Coder 的草稿影片機制可作為通用外掛模組，無需修改下游影片生成器的架構。

**3. 消融實驗的隱含訊息**

雖然摘要未明確列出消融實驗細節，但從方法論設計可推測：(a) 雙重獎勵的必要性——單獨使用任一獎勵可能導致訓練不穩定或次佳結果；(b) 退火策略的關鍵作用——若無退火，模型可能過度依賴執行獎勵而忽略最終影片品質；(c) SFT 預訓練的必要性——直接從零開始進行 RL 訓練可能因冷啟動問題而失敗。

**4. 結果的侷限性**

需注意：(a) 摘要未提供絕對數值，僅給出相對提升，因此難以判斷 Minimax-H3 的基線表現；(b) 缺乏與其他影片生成模型（如 Sora、Wan、Kling）的直接比較；(c) 缺乏人類主觀評估的數據。

#### 與現有研究的比較

**1. 在影片生成領域的定位**

相較於 Sora [1]、CogVideoX [24]、HunyuanVideo [25]、Wan [5]、Kling [3]、Seedance [4] 等擴散模型 (diffusion-based models) 與 VideoPoet [26] 等自回歸模型 (autoregressive models)，Video-Coder 並非試圖從頭建立一個強大的影片生成器，而是提出了一種「中間表示」(intermediate representation) 範式。這與近期使用深度 [27]、軌跡與相機姿態 [28, 29]、3D 追蹤影片 [30] 或物理模擬 [31, 32] 作為條件訊號的研究方向一致，但 Video-Coder 的獨特之處在於：這些條件訊號是由代理自動產生的，而非由使用者手動提供或來自固定流程。

**2. 在程式碼驅動視覺生成領域的定位**

相較於早期使用 LLM 產生 2D 版面配置引導擴散模型的工作 [34, 18, 17]，Video-Coder 採用了更具表現力的 3D 表示，能忠實描述幾何、遮擋 (occlusion) 與相機運動。相較於使用 Blender 程式碼生成或編輯場景的工作 [14, 15, 16]，Video-Coder 將場景建構與影片生成任務緊密耦合。與最相近的 GPT4Motion [32] 和 VideoCoCo [36] 相比，Video-Coder 的關鍵差異在於：(a) 不依賴凍結的專有模型，而是訓練專屬的開源代理；(b) 不採用固定提示流程，而是透過 RL 最佳化代理軌跡以直接提升最終影片品質。

**3. 在代理式程式設計領域的定位**

Video-Coder 將 LLM 代理從傳統的軟體工程任務擴展到視覺內容創作，展示了「程式碼作為視覺生成媒介」的可行性。這與近期將 LLM 應用於代理式任務 (agentic tasks) 的研究 [11, 12, 13, 33] 一脈相承，但將獎勵函數從「程式正確性」擴展到「視覺品質」，開創了新的研究方向。

**4. 局限性與未解決問題**

- **場景複雜度上限**：程式碼驅動方法在處理高度複雜、非剛體、流體或布料等現象時可能力不從心，因為這些現象難以用簡潔的程式碼精確描述。
- **草稿影片的視覺品質**：由 3D 渲染產生的草稿影片在視覺上可能較為簡陋，與真實影片存在顯著域差距 (domain gap)，下游生成器需具備強大的「草稿→真實」轉譯能力。
- **計算成本**：程式碼執行、3D 渲染、影片生成三階段串聯，整體推論延遲與資源消耗可能高於純端到端方法。
- **泛化至未見概念**：對於訓練資料中未充分涵蓋的物理現象或物件類型，代理可能無法產生合理的程式碼。

**1. 開源承諾**

作者明確聲明「fully open-source our data, models, and code」，這在當前影片生成研究中屬於難得的高透明度承諾。具體開源內容包括：
- **資料**：Video-Coder-SFT-6k 與 Video-Coder-RL-2k 兩個資料集。
- **模型**：訓練後的 Video-Coder 模型權重。
- **程式碼**：完整的訓練、推論與評測流程。

**2. 可重現性優勢**

- **資料建構流程的詳細描述**：論文中提供了從提示收集、軌跡生成、品質篩選到參考影片合成的完整流程，使其他研究者可重現資料集。
- **Video-Coder Harness 的開源**：統一互動式環境的開源意味著其他研究者可在相同基礎上進行實驗比較，避免因環境差異導致的結果不一致。
- **基座模型的明確指定**：使用 Minimax-H3 作為下游影片生成器，使消融與比較實驗具有明確基準。

- **依賴閉源模型**：資料建構流程中使用 Gemini 3.8 Flash 產生代理軌跡，若該模型的版本或行為發生變化，可能影響資料品質與訓練結果。

**4. 整體評估**

Video-Coder 在可重現性方面表現優於多數影片生成研究，開源承諾涵蓋了資料、模型與程式碼三大要素，為後續研究奠定了堅實基礎。然而，對閉源模型的依賴仍是潛在風險。

#### 未來研究方向

**1. 程式碼表示的擴展**

當前方法依賴傳統的 3D 場景程式碼（如 Blender Python API）。未來可探索：

## 論文問答

**Q1：這篇論文試圖解決影片生成領域中的什麼核心問題？**
A：這篇論文聚焦於當前影片生成模型在「精確空間結構、連貫運動動態、可控場景組成」三大面向上的根本性缺陷。雖然擴散模型與自回歸模型在視覺品質與短期時間一致性上已有長足進步，但它們僅在像素空間或潛在空間中擬合影片分佈，並未對底層的三維世界進行顯式建模。因此，當提示涉及精確空間關係、多物件互動或物理約束運動時，生成的影片常出現物件數量錯誤、位置錯亂、遮擋不一致、軌跡不自然，甚至物件變形或消失等問題。Video-Coder 正是為了突破此一瓶頸，提出以可執行程式碼作為中介表示，讓生成過程變得可控、可解釋且可驗證。

**Q2：為什麼現有的端到端影片生成模型難以處理精確的空間與運動控制？**
A：現有模型採用端到端方式直接在像素空間或潛在空間學習影片分佈，缺乏對三維幾何、物件運動與相機軌跡的顯式建模。這種「黑盒」特性使得模型難以區分「視覺上看似合理」與「物理上正確」的影片差異，例如無法可靠地維持物件數量、空間關係或遵守牛頓運動定律。論文中也引用 Kang 等人的研究指出，單純擴大模型規模並不足以讓模型學會這些物理法則。此外，端到端生成的影片難以編輯或重現，使用者只能透過反覆嘗試修改提示，效率低落且缺乏可控性，這正是 Video-Coder 欲解決的根本痛點。

**Q3：為什麼「程式碼」被選為影片生成的中介表示？相較於其他表示有何優勢？**
A：程式碼具備精確、可執行、可組合三大特性，能以極簡潔的程式明確描述場景幾何、物件運動與相機軌跡。例如一段短短的程式就能無歧義地指定「三顆球從不同高度同時落下」，這對像素級模型而言是極為困難的約束。相較於深度圖、軌跡、3D 追蹤影片等被動條件訊號，程式碼是由代理主動建構的，並可透過執行回饋進行多輪修正。相較於 2D 佈局，程式碼能更忠實地描述三維幾何、遮擋與相機運動，因此成為兼顧表達力、可控性與可驗證性的理想中介表示。

**Q4：Video-Coder 的核心方法是什麼？它如何將影片生成重新框架為代理式程式設計任務？**
A：Video-Coder 的核心在於將影片生成重新框架為「代理式程式設計任務」：給定一段文字提示，代理會撰寫並執行程式碼來建構一個動態三維場景，再將其渲染為「草稿影片」，最後由下游影片生成器基於此草稿產出最終影片。這個兩階段流程讓場景由可執行程式決定，使生成過程變得可控、可解釋且可重現。更重要的是，代理會透過多輪互動觀察執行錯誤與渲染結果，持續修正程式碼，這與過去單輪、固定提示流程的做法有本質差異。透過這樣的設計，Video-Coder 把「影片生成」轉化為一個可被強化學習最佳化的代理決策問題。

**Q5：什麼是 Video-Coder Harness？它在訓練與推論中扮演什麼關鍵角色？**
A：Video-Coder Harness 是一個整合「程式碼執行、三維場景渲染、執行回饋」的統一互動式環境，是支撐整個代理訓練與推論的基礎設施。在訓練階段，它讓代理能在沙盒中執行程式、接收錯誤訊息與渲染結果，並據此進行多輪修正；在推論階段，則提供一致的執行環境以確保結果可重現。這個環境的關鍵在於它把「程式碼是否可執行」、「渲染結果是否符合提示」這兩個層級的回饋統一回傳給代理，使強化學習能針對最終影片品質進行端到端最佳化。沒有這樣的環境，就無法實現所謂的「harness-native agentic RL」訓練範式。

**Q6：為什麼採用「雙重獎勵回饋」加上「退火訓練策略」？這樣的設計解決了什麼難題？**
A：雙重獎勵包含「基於執行的獎勵」與「基於影片的獎勵」，前者衡量程式可執行性，後者評估最終影片品質。單獨使用影片獎勵在訓練初期會因程式錯誤率高而訊號稀疏、不穩定；單獨使用執行獎勵則無法直接最佳化視覺與運動品質。為兼顧兩者，作者設計了退火策略：在訓練前期以執行獎勵為主以穩定學習，隨著訓練進行逐步降低其權重，讓影片獎勵在後期主導最佳化。這種「先穩定、後精修」的設計為強化學習提供了穩定且資訊豐富的學習訊號，同時兼顧程式可靠性與最終影片品質。

**Q7：論文中使用了哪些評測基準？Video-Coder 的關鍵實驗結果為何？**
A：論文主要使用 PhyGenBench（專注於物理合理性）與 VBench-2.0（綜合性影片生成評測）兩個基準，並以 Minimax-H3 作為下游影片生成器進行評估。實驗結果顯示，Video-Coder 為 Minimax-H3 帶來 PhyGenBench 上約 7 分、VBench-2.0 上約 24 分的大幅提升。這樣的進步幅度在影片生成領域屬於非常顯著的成果，證明了以可執行程式碼建構三維場景作為中介訊號，能有效提升生成影片的物理合理性與整體品質。值得注意的是，這些增益是在不同骨幹模型上都能穩定觀察到的，顯示方法的泛用性。

**Q8：PhyGenBench 提升 7 分、VBench-2.0 提升 24 分代表什麼意義？**
A：這兩個基準的提升幅度具有不同意義：PhyGenBench 專門評估物理一致性，7 分的提升代表 Video-Coder 在「球體滾落斜坡、碰撞方塊」這類物理約束運動上有明顯改善，驗證了「以程式碼顯式建構三維場景」對物理合理性的直接助益。VBench-2.0 則是更全面的影片品質評測，24 分的提升幅度極為可觀，顯示方法不僅改善物理性，也帶來整體視覺品質的提升。這兩個數字共同說明：透過代理式程式設計引入結構性先驗，比單純擴大模型或微調提示詞更能從根本上提升影片生成的可控性與品質。

**Q9：論文中是否有進行消融實驗來驗證各元件的貢獻？**
A：雖然提供的全文片段未完整展示消融實驗細節，但從方法描述可推論關鍵元件包括：雙重獎勵設計、退火訓練策略、SFT 預訓練階段，以及 Video-Coder Harness 本身。這些元件的組合對於穩定訓練與最終效能都至關重要——例如若無 SFT 預訓練，模型將缺乏基本的場景程式設計與工具呼叫能力；若無退火策略，純影片獎勵在初期會因程式錯誤而訊號不穩。論文中強調「執行獎勵穩定早期訓練、影片獎勵主導後期最佳化」的設計哲學，暗示每個元件都對最終結果有不可替代的貢獻。

A：Video-Coder 特別適合需要精確空間控制與物理一致性的場景，例如電影預覽、動畫製作、遊戲場景設計、教育內容創作（如物理現象演示）以及廣告影片生成。在這些場景中，使用者往往需要「三顆球從不同高度落下並撞倒方塊」這類精確描述，傳統模型難以勝任，但 Video-Coder 能透過程式碼明確指定。此外，由於場景由可執行程式決定，使用者還能進一步編輯程式以調整細節，實現真正的可控生成，這對專業內容創作流程尤其重要。

**Q13：Video-Coder 有哪些已知的限制？**

商家輸入產品擺放與運動描述（例如「手錶從桌面滑落並翻轉 360 度」），系統生成具備正確物理運動與空間結構的展示影片，避免傳統擴散模型常見的物件變形、消失或數量錯誤問題。

**5. 廣告與社群短影片快速產製**
行銷團隊以提示詞描述品牌場景（產品飛入畫面、堆疊、旋轉），透過 Video-Coder 結合下游影片生成器（如 Minimax-H3）產出符合物理直覺的高品質短影片，縮短從概念到成品的週期。

### 實作前置條件

**資料需求**
- **文字提示集**：需蒐集多樣化、涵蓋空間關係與物理運動的影片生成提示，可從現有資料集（如 PhyGenBench、VBench）或內部標註取得。
- **參考影片**：每筆提示需對應一支高品質 ground-truth 影片，用於 SFT 階段的監督訊號與 RL 階段的影片獎勵計算。
- **代理軌跡資料**：需使用具備工具呼叫與多輪互動能力的 LLM（如 Gemini 3.8 Flash）搭配 Video-Coder Harness 產生「寫程式 → 執行 → 觀察錯誤 → 修正」的完整軌跡，作為 SFT 訓練資料。
- **建議規模**：參考論文的 Video-Coder-SFT-6k（6k 筆）與 Video-Coder-RL-2k（2k 筆），實際部署可視領域需求等比例擴充。

**運算資源**
- **資料建構階段**：需要執行 Blender / 3D 渲染沙盒（單次場景渲染約數秒至數分鐘，依複雜度而定），以及呼叫下游影片生成模型合成參考影片，建議配備多張 A100 / H100 等級 GPU。
- **SFT 訓練**：對 7B–13B 級 LLM 進行監督式微調，建議至少 8 張 80GB GPU，訓練時間約數天。
- **RL 訓練**：需在 Video-Coder Harness 中反覆執行程式碼、渲染 3D 場景、計算雙重獎勵，運算成本最高，建議預留 16 張以上 GPU 並使用分散式訓練框架（如 verl、OpenRLHF）。

**技能門檻**
- **3D 程式化建模**：熟悉 Blender Python API 或 Three.js，能撰寫可執行的場景描述程式碼。
- **LLM 微調與 RL**：熟悉 Hugging Face Transformers、TRL、verl 等框架，理解 PPO / GRPO 等演算法。
- **獎勵函式設計**：能根據業務需求調整 execution-based reward 與 video-based reward 的權重與退火曲線。
- **影片品質評測**：理解 PhyGenBench、VBench-2.0 等基準的評分邏輯，以便自訂影片獎勵。

### 實作步驟建議

**步驟 1：環境與沙盒建置**
部署 Video-Coder Harness，整合程式碼執行沙盒（建議使用 Docker 隔離）、3D 渲染引擎（Blender headless 或 Three.js + WebGL）與回饋收集模組。確認沙盒能回傳執行錯誤訊息、渲染幀與中繼狀態，供代理觀察與修正。

**步驟 2：資料建構流程搭建**
依照論文方法，從多源蒐集文字提示，使用 Gemini 3.8 Flash 等強模型搭配 Harness 產生代理軌跡（多輪寫程式、執行、修正），再將「提示 + 草稿影片」餵入下游影片生成器（如 Minimax-H3）合成 ground-truth 參考影片。經品質過濾後產出 SFT 與 RL 兩份資料集。

**步驟 3：SFT 監督式微調**
以 Video-Coder-SFT-6k 對基座 LLM 進行監督式微調，目標是讓模型學會基本的場景程式設計與工具呼叫格式。訓練時應監控程式碼可執行率（execution success rate）作為早期收斂指標。

**步驟 4：Harness-native 代理式強化學習**
以 Video-Coder-RL-2k 為基礎，在 Harness 中進行 RL 訓練，採用雙重獎勵：
- **Execution-based reward**：衡量程式碼可執行性、語法正確性。
- **Video-based reward**：以 ground-truth 影片與生成影片的相似度（可使用 PhyGenBench / VBench 評測指標或自訂視覺模型評分）作為訊號。
套用**退火策略**：訓練前期以執行獎勵為主穩定學習，後期逐步降低其權重，讓影片獎勵主導，直接最佳化最終影片品質。

**步驟 5：下游影片生成器整合**
將訓練完成的 Video-Coder 與下游影片生成模型串接：代理輸出草稿影片後，由生成器以草稿為結構與運動引導產出最終影片。可透過 ControlNet、條件擴散或 I2V（image-to-video）介面實作。

**步驟 6：評測與迭代**
在 PhyGenBench、VBench-2.0 等基準上評測，並針對失敗案例分析是程式碼錯誤、渲染失真或下游生成器限制。持續擴充資料、改寫獎勵函式或調整退火曲線。

**步驟 7：部署與 API 化**
將代理包裝為服務（FastAPI / gRPC），提供文字提示輸入、草稿影片預覽、程式碼回傳等端點；對外暴露時務必做好沙盒隔離與資源配額管控。

### 潛在風險與注意事項

**1. 程式碼執行安全性**
代理會自主執行程式碼，若沙盒隔離不足，可能被誘導執行惡意指令（刪除檔案、存取網路）。**緩解措施**：使用 Docker / gVisor 嚴格隔離執行環境、限制檔案系統與網路權限、設置資源配額（CPU / 記憶體 / 時間上限）。

**2. 3D 渲染品質與真實感落差**
程式碼生成的 3D 場景在材質、光照、物理模擬上可能與真實世界有差距，導致下游生成器以「低保真草稿」為條件時輸出受限。**緩解措施**：在 Harness 中引入更精細的物理模擬引擎（如 PyBullet、MuJoCo），並允許代理呼叫材質 / 光照資產庫。

**3. 訓練成本與資料稀缺**
RL 階段需大量沙盒互動與影片評分，運算成本極高；高品質代理軌跡資料仰賴強模型（Gemini 3.8 Flash）生成，授權與成本需考量。**緩解措施**：採用 GRPO 等較省樣本的 RL 演算法、對獎勵模型做蒸餾以降低評分成本、建立內部資料標註流程減少對外部 API 依賴。

**4. 泛化能力不足**
代理可能在訓練分布外的提示（罕見物理場景、抽象藝術風格）上表現不佳。**緩解措施**：擴充資料多樣性、加入領域外提示的評測集、保留 fallback 機制（草稿品質過低時改用純文字生成）。

**5. 退火策略調參困難**
執行獎勵與影片獎勵的權重曲線若設計不當，可能導致訓練不穩定或收斂至次佳解。**緩解措施**：以較小模型與子集先做消融實驗、監控 KL 散度與獎勵曲線、保留 checkpoint 以便回溯。

**6. 開源模型與授權**
論文提及完全開源資料、模型與程式碼，但下游影片生成器（如 Minimax-H3）可能有授權限制，商業部署前須確認條款。

### 與其他技術的整合建議

**1. 與現有影片生成模型整合**
Video-Coder 的草稿影片可作為 ControlNet、Trajectory Control、Camera Pose Conditioning 等條件控制機制的輸入。建議優先整合支援 I2V / V2V 的擴散模型（如 Wan、CogVideoX、HunyuanVideo），並針對不同模型調整草稿解析度與幀率。

**2. 與遊戲引擎整合**
將代理生成的 Blender / Three.js 程式碼轉換為 Unity / Unreal 可用的資產或邏輯腳本，實現「文字描述 → 遊戲關卡原型」的工作流。可進一步串接 PhysX 等物理引擎提升模擬真實度。

**3. 與 VFX / 動畫工具鏈整合**
對接 Houdini、Nuke 等專業工具的 Python API，讓代理生成的場景程式碼能直接匯入既有製作流程；草稿影片可作為特效合成（compositing）的參考層。

**4. 與 RAG 與領域知識庫整合**
為提升代理在專業領域（醫學模擬、工程物理）的準確性，可整合領域知識庫（如物理公式、醫學解剖模型）作為工具，讓代理在生成程式碼時查閱正確參數。

**5. 與多模態輸入整合**
擴展代理以接受圖片、草圖、參考影片等多模態輸入，讓使用者能以「圖片 + 文字」混合提示引導生成，提升互動性。

**6. 與 MLOps / 監控系統整合**
將代理的執行程式碼、渲染結果、獎勵分數納入模型監控（MLOps）平台，追蹤線上表現與資料漂移，並建立自動回饋迴圈以持續改進模型。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）了解「為什麼需要程式碼驅動的影片生成」，再跳到圖 1 掌握整體流程（文字提示 → 寫程式 → 渲染草稿 → 下游生成）。不必急於理解訓練細節，重點是體會「可執行程式碼」作為中間表示所帶來的可控性與可驗證性，這是與傳統擴散模型最大的差異。

**給 AI 工程師**：重點關注第 2.2 節（Related Works）了解程式碼驅動視覺生成的脈絡，並仔細研讀 Video-Coder Harness 的設計（程式碼執行、3D 渲染、回饋整合）以及雙重獎勵 + 退火策略的實作細節。建議直接 clone 官方開源程式碼，從 SFT 階段開始復現，再逐步加入 RL 與自訂獎勵，評估在自身業務資料上的效益。

**給研究者**：本文的核心創新在於「將影片生成重新框定為代理式程式設計任務」，並提出 harness-native RL 與退火獎勵策略。可從以下方向延伸：(1) 探索更強的程式碼中間表示（例如結合符號物理引擎、神經輻射場）；(2) 研究多代理協作（場景代理 + 鏡頭代理 + 物理代理）；(3) 將退火獎勵策略推廣到其他程式碼驅動的視覺任務（3D 建模、遊戲關卡生成）。

**給產品經理**：Video-Coder 的價值在於「可控、可編輯、可重現」，這對需要快速迭代視覺內容的場景（廣告、教育、遊戲原型）特別有吸引力。建議評估自身業務中是否有「精確空間結構 / 物理運動 / 多物件互動」的需求——若有，Video-Coder 相較純擴散模型能顯著降低錯誤率與重試成本。導入時應優先關注沙盒安全、運算成本（尤其 RL 階段）與下游生成器的授權相容性，並規劃 MVP 範圍（例如先聚焦單一垂直場景如電商產品展示）。
