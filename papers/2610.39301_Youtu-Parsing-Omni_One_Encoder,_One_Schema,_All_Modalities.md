我們提出 Youtu-Parsing-Omni，一個全模態解析器，能將文件、圖像、音頻和視頻轉換為基於時空座標的結構化記錄，為能夠跨模態讀取、定位與引用證據的代理提供感知層。其設計基於一個編碼器處理所有模態，以及一套架構適用於所有任務。Youtu-Omni-Encoder 從預訓練語言模型初始化以強化文本閱讀能力，在統一時空座標系統中以共享權重編碼所有模態，並透過少量融合層使視頻幀能關注同步音頻，將跨模態融合與時間對齊融入感知本身。OmniSchema 統一了所有十個解析任務的輸出，使單一的自演化後訓練程序——OmniSchema感知在線策略蒸餾 (OSAD)——能夠提供跨任務共享的基於 token（詞元）角色的目標函數。在每一輪訓練中，模型以其自身的滾動展開，對比來自參考條件副本的 token 級目標，隨後以訓練後的權重刷新該副本，使解析器與其監督信號共同演化。憑藉單一 5B 參數的檢查點，Youtu-Parsing-Omni 在 OmniDocBench v1.6 上達到最先進性能（整體分數 96.96），並在 OmniParsingBench 上領先所有開源權重模型（平均分 75.08），其優勢集中在音頻與視頻任務上。此外，該模型在圖表解析上取得最佳整體分數（95.02），並在所有對比系統中達到最高的精確化學指紋一致性，同時在印刷樂譜的字符級轉錄任務上與專用的光學音樂識別模型持平，並大幅領先通用系統。程式碼與模型權重均已開源。

Youtu-Parsing-Omni 的方法論核心建立在「一個編碼器、一個架構、所有模態」的統一設計哲學上，試圖從根本上解決當前多模態解析系統中模態分離、任務分散的問題。

**Youtu-Omni-Encoder 的設計理念**

傳統的全模態模型（如 Logics-Parsing-Omni、Qwen3-Omni）採用雙編碼器架構，分別使用獨立的視覺編碼器和音頻編碼器，這帶來三個根本性限制：（1）各模態在感知階段完全隔離，跨模態融合被迫延後到語言模型層；（2）兩個編碼器各自獨立索引時間軸，導致同一時刻的視訊幀與音訊在感知層缺乏時間對齊；（3）每新增一個模態都需要新增一座編碼塔，參數無法跨模態共享。

Youtu-Omni-Encoder 採用了一種大膽的策略：從預訓練語言模型初始化編碼器，並以共享權重的方式編碼所有模態。這一設計的關鍵洞察在於：語言模型在預訓練過程中已建立了強大的文本閱讀能力，將其作為編碼器初始化起點，能夠強化符號內容（如化學式、樂譜、數學公式）的識別能力。編碼器在統一時空座標系統下運作，使視訊幀與音訊樣本能在同一時間軸上對齊，這對於結構化解析至關重要——因為解析輸出必須明確指出「哪個內容在哪個時間發生」。

**融合層的設計**

針對視訊-音訊的跨模態融合，模型僅引入少量融合層，讓視訊幀能夠關注（attend to）並發的音訊。這是一種輕量級的設計選擇，避免了完整跨模態注意力帶來的計算開銷，同時將跨模態融合與時間對齊能力下沉到感知層本身，而非依賴語言模型進行後處理。

**OmniSchema 統一輸出架構**

OmniSchema 將十個解析任務的輸出統一為單一架構，這十個任務涵蓋：文件（→Markdown/LaTeX/OTSL 表格）、自然圖像（→接地物件、文字、標題）、圖表（→OTSL 表格/Mermaid）、幾何圖形（→點、關係、描述）、化學結構（→SMILES）、樂譜（→ABC 記號）、語音與聲音（→時間分段、ASR）、音視訊（→事件、螢幕文字、語音）。這種統一使得單一後訓練流程能夠同時優化所有任務。

**OSAD 自演化蒸餾機制**

OmniSchema-Aware On-Policy Distillation（OSAD）是本文最具方法論創新性的部分。傳統監督微調（SFT）僅在參考前綴上訓練，從未在模型自身推理時產生的前綴上訓練，這造成了訓練-推理分布的不匹配。OSAD 採用在線策略蒸餾：每一輪訓練中，模型先在自己的滾動展開（rollouts）上產生輸出，然後與來自「參考條件副本」的 token 級目標進行對比學習。關鍵在於這個參考副本會在每輪結束後用訓練後的權重刷新，使得解析器與其監督信號共同演化（co-evolve）。

這種設計的優勢在於：（1）解決了 SFT 的曝光偏差問題；（2）基於 token 角色的目標函數天然跨任務共享，因為不同任務的輸出雖然欄位不同，但 token 在架構中的角色（如鍵、值、邊界符）是可統一分類的；（3）自演化機制使監督信號隨模型能力提升而提升，避免了固定參考模型的性能天花板。

#### 與現有研究的比較

**與 Logics-Parsing-Omni 的比較**

Logics-Parsing-Omni 是目前最直接的全模態解析對比對象。兩者都試圖構建統一的多模態解析器，但路徑截然不同：Logics-Parsing-Omni 採用雙編碼器（視覺+音頻）架構，而 Youtu-Parsing-Omni 採用單一編碼器。在 OmniParsingBench 上，Youtu-Parsing-Omni（75.08）領先 Logics-Parsing-Omni（72.26）約 2.8 分，這一差距主要來自音頻和視頻任務——驗證了共享權重編碼器在跨模態融合上的優勢。

**與文件解析專用模型的比較**

在文件解析子任務上，Youtu-Parsing-Omni 超越了 TeleOCR、OvisOCR2、PaddleOCR-VL 系列、MinerU2.5-Pro、GLM-OCR 等專用或半專用系統。這表明統一架構並未犧牲專用領域的性能，反而通過共享表示實現了正向遷移。

**與通用全模態模型的比較**

與 Qwen3-Omni-30B-A3B（66.44）等通用全模態模型相比，Youtu-Parsing-Omni 在解析任務上的優勢顯著（領先約 8.6 分）。這反映了通用模型在「接地結構化輸出」這一特定需求上的不足——它們擅長描述和問答，但難以產生精確錨定空間或時間的結構化記錄。

**與閉源 API 模型的比較**

Gemini-3-Pro 在 OmniParsingBench 上以 77.44 領先，GPT-5.2 在 OmniDocBench 上僅得 86.59。這一對比揭示了一個重要現象：在文件解析這一相對成熟的領域，開源模型已能超越頂級閉源模型；但在更廣泛的全模態解析上，閉源模型仍保持領先。Youtu-Parsing-Omni 作為 5B 參數的開源模型，能在多個維度逼近甚至超越閉源對手，展示了開源生態的快速進步。

**局限性分析**

從實驗數據可以推斷出幾個潛在局限：
1. **自然圖像解析相對薄弱**（62.84），這可能是因為統一編碼器在通用視覺理解上的容量被符號內容識別任務分散。
2. **化學結構解析總分不高**（54.20），雖然化學指紋一致性領先，但整體解析質量仍有提升空間。
3. **5B 參數的規模限制**：雖然效率出色，但在某些需要更深推理的任務上可能受限於容量。
4. **OSAD 的計算成本**：自演化蒸餾需要在每輪刷新參考模型並進行在線採樣，訓練成本高於標準 SFT。

Youtu-Omni-Encoder 從預訓練語言模型初始化的策略開啟了新的研究方向。未來可探索：（1）更大規模語言模型初始化對解析性能的影響；（2）不同模態編碼器共享權重 vs 部分共享的權衡；（3）將觸覺、3D 點雲等更多模態納入統一編碼器的可行性。

**OSAD 機制的理論深化**

自演化蒸餾的成功引發了若干值得深入探討的問題：（1）共同演化的收斂性理論分析；（2）參考模型刷新頻率與最終性能的關係；（3）將 OSAD 推廣到其他結構化生成任務（如程式碼生成、資料庫查詢生成）的可能性。

**接地能力的強化**

當前模型在自然圖像解析（62.84）上相對薄弱，未來可探索：（1）引入更細粒度的視覺接地監督；（2）結合場景圖（scene graph）生成提升物件關係理解；（3）將物件追蹤技術整合到視訊解析中。

**領域專用解析的深化**

雖然模型在化學結構、樂譜等領域已達到與專用模型相當的水平，但仍有提升空間：（1）化學結構解析可結合分子性質預測的多任務學習；（2）樂譜識別可引入音樂理論約束提升結構正確性；（3）數學公式解析可與符號計算引擎聯動。

**代理整合與下游應用**

作為「感知層」，Youtu-Parsing-Omni 與 LLM 代理的整合是自然的下一步：（1）探索解析輸出作為代理長期記憶的格式；（2）研究多輪解析中的一致性維護；（3）將解析能力擴展到即時串流場景。

**效率優化**

5B 參數已是相對高效的設計，但仍有優化空間：（1）模型量化對解析質量的影響；（2）投機性解碼在結構化輸出上的應用；（3）針對特定模態的動態計算分配。

**多語言與多文化擴展**

當前評測主要基於中英文內容，未來可探索：（1）低資源語言的解析能力；（2）從右到左書寫系統（如阿拉伯文、希伯來文）的支援；（3）文化特定符號（如傳統音樂記號、地圖符號）的識別。

**可解釋性與可信度**

作為代理的感知層，解析結果的可信度至關重要：（1）為每個解析元素提供信心分數；（2）支援反事實解析（給定不同輸入會產生什麼輸出）；（3）建立解析錯誤的診斷與修復機制。

Youtu-Parsing-Omni 的提出不僅是一個技術貢獻，更是對「統一感知」這一願景的有力推演——它證明了用單一架構處理所有模態、所有解析任務的可行性，並通過自演化訓練機制為這一願景提供了可持續優化的路徑。隨著開源社區的進一步探索，這一架構有望成為下一代多模態代理的標準感知層。

## 論文問答

**Q1：什麼是全模態解析（omni-modal parsing），為什麼它對LLM代理很重要？**

A：全模態解析是一種將文件、圖像、音頻和視頻等異質輸入統一轉換為結構化記錄的技術，每筆記錄都錨定在特定的空間或時間位置上。這種解析為LLM代理提供了一個「感知層」，使代理能夠讀取、定位並引用跨模態的證據，而無需反覆重新編碼長序列的視覺與聲學token。更重要的是，結構化記錄使得任何LLM（包括純文本模型）都能讀取並追溯每個主張的來源，從而大幅提升可審計性與推理效率。

**Q2：現有的解析器在處理多模態輸入時面臨哪些主要限制？**

A：現有解析器在覆蓋範圍上呈現嚴重的不平衡：文件解析器雖然在標準頁面上表現強勁，但對化學結構、樂譜等符號內容仍主要依賴領域專用模型。在文件之外，解析技術更為不成熟——現有的全模態模型主要用於字幕生成和問答，而非接地（grounded）的結構化輸出。此外，不同輸入類型通常由不同模型服務，輸出格式各異，無法形成統一的解析範式，這迫使系統需要維護多個專門模型。

**Q3：為什麼需要「一個編碼器、一個架構」的統一設計？**

A：論文的核心理念是：跨模態的目標輸出本質上是相同的——都是結構化記錄，其單元錨定於空間或時間，因此應該用單一解析器配合統一輸出架構來處理，而非為每種輸入類型配備專家模型。這種統一設計帶來三大優勢：跨模態共享感知參數、降低新模態接入成本，以及在統一時空座標系統中實現真正的跨模態融合與時間對齊。相較於現有方案中視覺與音頻編碼器各自獨立預訓練的安排，統一編碼器能讓感知階段本身承擔跨模態關係建模的責任。

**Q4：Youtu-Omni-Encoder的核心設計理念是什麼？**

A：Youtu-Omni-Encoder從預訓練語言模型初始化，以強化文本閱讀能力，這是因為許多解析任務（如文件、字幕、樂譜）都涉及密集的文字內容。該編碼器以共享權重的方式編碼所有模態，使所有輸入都被映射到同一個統一的時空座標系統中。此外，僅需少量融合層即可讓視頻幀關注並發音頻，從而將跨模態融合與時間對齊直接融入感知過程本身，而非延後到語言模型階段。

**Q5：OmniSchema如何統一十個解析任務的輸出？**

A：OmniSchema將所有十個解析任務的輸出統一在一個架構下，無論輸入是文件、自然圖像、圖表、幾何、化學結構、樂譜、音頻還是視頻，最終都產生結構化的、接地元素的記錄。這種統一使得單一的後訓練程序能夠跨任務運作，因為所有任務共享基於token角色的目標函數。透過這種設計，模型無需為每個任務設計獨立的輸出頭或損失函數，大幅簡化了訓練流程並促進了跨任務的知識遷移。

**Q6：OSAD（OmniSchema感知在線策略蒸餾）如何實現自演化？**

A：OSAD是一種自演化的後訓練程序，其核心思想是讓解析器與其監督信號共同演化。在每一輪訓練中，模型首先在自身生成的滾動展開（rollouts）上進行訓練，而token級目標則來自一個參考條件副本（reference-conditioned copy）——這個副本隨後會用訓練後的權重重新整理。這種設計解決了傳統監督微調（SFT）僅在參考前綴上訓練、永遠無法匹配模型自身推理時實際產生前綴的問題，使訓練目標與推理分布更為一致。

**Q7：Youtu-Parsing-Omni在OmniDocBench v1.6上的表現如何？**

A：在OmniDocBench v1.6上，Youtu-Parsing-Omni以96.96的整體分數達到了最先進性能（SOTA），超越了TeleOCR（96.91）、OvisOCR2（96.47）、PaddleOCR-VL-1.6（96.34）以及其前代模型Youtu-Parsing（93.74）。在細分任務中，它在文件解析（96.96）、圖表解析（95.02）等多項任務上均表現出色，並在化學結構解析上取得了所有對比系統中最高的精確指紋一致性。這些結果證明了統一編碼器與架構設計在文件解析領域的強大競爭力。

**Q8：在OmniParsingBench上的表現及與其他模型的比較如何？**

A：在OmniParsingBench上，Youtu-Parsing-Omni以75.08的平均分領先所有開源權重模型，包括Logics-Parsing-Omni（72.26）和Qwen3-Omni-30B-A3B（66.44）。其唯一未能超越的對手是通過API訪問的Gemini-3-Pro（77.44），但考慮到Youtu-Parsing-Omni僅有5B參數，這一成績尤為亮眼。值得注意的是，論文中明確指出其優勢集中在音頻和視頻解析上，這恰恰驗證了統一編碼器在跨模態融合方面的設計選擇是正確的。

**Q9：在領域特定基準上的表現如何？**

A：在領域特定基準上，Youtu-Parsing-Omni展現了令人印象深刻的通用性：在化學結構解析中取得了所有對比系統中最高的精確指紋一致性；在樂譜字符級轉錄任務上，其表現能夠匹配專用的光學音樂識別模型（character error rate為22.73），同時遠遠領先通用系統。這些結果尤為重要，因為它們表明統一解析器不僅在通用任務上表現出色，還能夠在通常需要專用模型的符號理解任務上保持競爭力，證明了「一個編碼器」設計的泛化能力。

**Q10：實際應用場景有哪些？**

A：Youtu-Parsing-Omni的實際應用場景極為廣泛：在企業文件處理中，它可以自動解析合同、報告、發票等多種文件格式並輸出結構化記錄；在多媒體內容分析中，它能夠從視頻中提取事件時間軸、屏幕文字和語音內容；在教育領域，它可以用於解析包含圖表、幾何圖形和化學式的教科書內容。此外，作為LLM代理的感知層，它使得代理能夠在多模態環境中進行證據引用和可審計的推理，這對於法律、醫療和金融等高風險應用尤其重要。

**Q11：部署和產品化考量有哪些？**

A：從部署角度來看，Youtu-Parsing-Omni僅使用單一5B參數的檢查點即可處理所有十個解析任務，這在多模態模型中屬於相對精簡的配置，有利於降低推理成本和硬體需求。論文公開了代碼（GitHub）和模型權重（Hugging Face），這為學術界和工業界的進一步研究與應用提供了便利。然而，產品化時仍需考慮推理延遲、吞吐量優化以及與現有LLM代理框架的整合介面等工程問題。

**Q12：對多模態AI領域的影響是什麼？**

A：Youtu-Parsing-Omni對多模態AI領域的影響主要體現在三個方面：首先，它提出了「統一解析」的新範式，挑戰了傳統的「每個模態配一個專家模型」的做法；其次，其共享權重的編碼器設計為跨模態融合提供了新的研究方向，將融合從語言模型階段前移到感知階段；最後，OSAD自演化蒸餾方法為多任務聯合優化提供了新思路，可能啟發更多關於自演化訓練的研究。這些貢獻共同推動了多模態AI從「各自為政」走向「統一感知」的轉變。

**Q13：論文承認的限制有哪些？**

A：雖然論文取得了令人矚目的成果，但仍存在一些可識別的限制：5B參數規模雖然高效，但與Gemini-3-Pro等更大規模的閉源模型相比仍有差距；在某些高度專業化的領域（如複雜化學結構或罕見樂譜符號），專用模型可能仍具優勢。此外，OSAD自演化訓練流程的計算成本和訓練穩定性也是實際部署中需要考慮的因素，論文中對此並未深入討論。

**Q14：可能的失敗案例有哪些？**

A：基於論文描述和一般多模態模型的特性，可以推測幾類可能的失敗案例：在極度複雜的多人對話場景中，說話人分離（speaker diarization）可能出現錯誤；在低品質音頻或視頻中，時間對齊可能不準確；對於訓練數據中罕見的模態組合（如特定語言的方言加上特殊視覺效果），解析品質可能下降。此外，在極長視頻的處理上，時間分段和全局描述的一致性也是潛在的挑戰點。

**Q15：未來研究方向有哪些？**

A：基於論文的設計理念和當前限制，未來研究可以朝多個方向延伸：首先，可以探索將統一編碼器擴展到更多模態（如3D點雲、觸覺信號或腦電信號）；其次，OSAD自演化蒸餾方法可以進一步改進，例如結合強化學習或對抗訓練以提升穩定性；此外，將Youtu-Parsing-Omni與更大的語言模型結合，探索其在代理系統中的端到端應用也是重要方向。最後，如何在保持統一架構優勢的同時進一步縮小與頂級閉源模型的性能差距，將是衡量該範式長期價值的關鍵問題。

### 實作前置條件

**資料準備**
- 至少需準備各任務類型的標註樣本：文件（Markdown/LaTeX/OTSL）、自然圖像（grounded objects/captions）、圖表（OTSL/Mermaid）、幾何（點與關係）、化學（SMILES）、樂譜（ABC）、音頻（時間分段 + ASR）、影片（事件軸 + 螢幕文字 + 語音）。
- 標註需包含空間座標（bbox）與時間戳（start–end），這是 OmniSchema 的核心錨點。
- 建議先以 OmniDocBench v1.6 與 OmniParsingBench 的子集做驗證基準。

**算力需求**
- 5B 參數單一檢查點推論：建議至少 1 張 A100/H100（80GB）或等效 GPU；FP16/BF16 推論約需 10–12GB VRAM，量化（INT8/INT4）後可降至消費級顯卡。
- 完整 OSAD 後訓練（rollouts + 蒸餾循環）需多卡節點（建議 8×H100 或以上）與較長訓練週期。
- 若僅做領域微調（凍結部分層），單卡 A100 即可起步。

**技能門檻**
- 熟悉 Hugging Face Transformers 與多模態模型載入流程。
- 理解 OTSL、ABC、SMILES 等領域標記語法（用於後處理與驗證）。
- 具備基本的時空標註工具使用經驗（如 Label Studio、CVAT、Audino）。
- 若要做 OSAD 自演化訓練，需熟悉分散式訓練（DeepSpeed/FSDP）與 on-policy RL 概念。

### 實作步驟建議

**Step 1：環境與權重取得**
從 Hugging Face `tencent/Youtu-Parsing-Omni` 下載 5B 檢查點，從 GitHub `TencentCloudADP/youtu-parsing` 取得官方推論程式碼與 OmniSchema 定義；建立 Python 環境並安裝依賴（建議使用官方提供的 Dockerfile 或 requirements）。

**Step 2：基準評測先行**
先用 OmniDocBench v1.6 與 OmniParsingBench 的公開子集跑一次零樣本評測，確認模型在自家硬體上的吞吐量與品質基線；同時驗證 OmniSchema 輸出格式與下游系統的相容性。

**Step 3：定義產品輸出契約**
依業務需求從 OmniSchema 中挑選需要的欄位（例如：文件任務的 `element.box/category/order/content`、影片任務的 `s_001 00:00–00:15 · static` 事件軸），設計 JSON Schema 或 Pydantic 模型作為下游契約。

**Step 4：建立領域標註管線**
針對自家資料（合約、發票、會議錄影等）建立標註流程，產出符合 OmniSchema 的訓練樣本；標註工具需支援 bbox 與時間戳輸出，並能匯出 token-role 標籤（OSAD 所需）。

**Step 5：領域微調（可選）**
若零樣本表現不足，可先用 SFT 在小量高品質樣本上微調；若需跨任務聯合優化，再啟動 OSAD：以自家資料產生 rollouts，用 reference-conditioned 副本產生 token-level 目標，反覆迭代。

**Step 6：串接下游 Agent / 系統**
將解析結果以結構化記錄形式注入 RAG 知識庫、Agent 工具呼叫結果、或 BI 報表生成器；保留 `box` 與時間戳以便在 UI 上高亮引用來源。

**Step 7：監控與持續改進**
上線後監控解析失敗率、schema 違例率、引用準確度；定期以新資料重跑 OSAD 循環，讓模型與監督信號共同演化。

### 潛在風險與注意事項

**1. 領域漂移與符號內容錯誤**
化學式、樂譜、幾何題等符號內容對單一字元錯誤極度敏感（SMILES 一個位錯就改變分子結構）。建議在後處理加入語法驗證器（RDKit 驗 SMILES、music21 驗 ABC、幾何關係一致性檢查），並對低信心輸出走人工覆核。

**2. 時空座標的可靠性**
模型輸出的 bbox 與時間戳是「引用證據」的基礎，若座標偏移會導致下游 Agent 引用錯誤區段。建議在 UI 端做座標可視化抽查，並對座標 IoU/時間重疊率設立閾值告警。

**3. 多語言與字型覆蓋**
雖然編碼器以預訓練語言模型初始化有利於文字閱讀，但罕見字型、垂直文字、手寫字仍可能誤讀；部署前應以自家語料做抽樣測試，必要時加入字型增強或微調。

**4. OSAD 自蒸餾的成本與不穩定性**
On-policy 蒸餾需要持續產生 rollouts 並刷新 reference，計算成本高且對超參敏感；若資料量小或品質不穩，可能出現「自我確認偏誤」。建議保留一份固定的 reference 基準用於早期停止，並監控 token-level 目標的分布漂移。

**5. 音訊/影片的隱私與合規**
會議錄音、客戶來電等資料可能含個資；解析後的 ASR 文字與時間戳同屬個資範疇，需配合去識別化、存取控管與稽核日誌。

**6. 單一檢查點的泛化邊界**
5B 參數單一模型雖覆蓋十項任務，但在極長影片、極密集文件、低資源語言上仍可能觸頂；建議設計降級路徑（例如：長影片切片、極複雜文件走專用模型）。

### 與其他技術的整合建議

**1. 與 RAG 系統整合**
將 OmniSchema 輸出（特別是 `content` 欄位與時空錨點）作為文件 chunks 寫入向量資料庫；`box` 與時間戳存入 metadata，檢索時可一併回傳座標供前端高亮。建議搭配 BGE、Qwen3 Embedding 等多語言嵌入模型。

**2. 與 LLM Agent 框架整合**
在 LangChain、AutoGen、CrewAI 等框架中，將 Youtu-Parsing-Omni 包裝為 `parse_document` / `parse_video` / `parse_audio` 工具；輸出結構化 JSON 直接餵入 Agent 的 reasoning loop，並把錨點作為 `cite_source` 的依據。

**3. 與 OCR / 專用模型互補**
雖然模型在多項任務上 SOTA，但對極度專業場景（如古文字辨識、手寫化學式）仍可採「Youtu-Parsing-Omni 先解析 → 信心低區域送專用模型補強」的級聯架構，兼顧效率與極限品質。

**4. 與 BI / 報表工具整合**
圖表解析的 OTSL/Mermaid 輸出可直接餵入 Tableau、Power BI、Apache Superset 的資料表重建流程；也可轉為 Vega-Lite 規格做互動式視覺化。

**5. 與影片理解 / 摘要系統整合**
影片事件軸可作為影片摘要、章節生成、字幕翻譯的骨架；搭配 Whisper（多語 ASR）或 Qwen3-Omni 做進一步摘要時，建議以 Youtu-Parsing-Omni 的時間分段作為分段依據，避免重切。

**6. 與 MLOps 平台整合**
模型權重可註冊到 MLflow / Weights & Biases；OSAD 訓練循環的 rollouts、reference 刷新、評測結果建議完整記錄，方便回溯與審計。

### 給不同背景讀者的閱讀建議

**給初學者：** 建議先讀摘要與 Figure 1/2，建立「一個編碼器、一個架構、十項任務」的整體印象；接著跳過技術細節，直接看 GitHub README 的推論範例，用官方 Colab 或本地小範例跑一次文件解析，感受 OmniSchema 的輸出格式；不必急於理解 OSAD，先體會「多模態 → 結構化記錄」的價值即可。

**給 AI 工程師：** 重點放在 §1 的兩個挑戰（C1 跨模態聯合感知、C2 跨任務聯合優化）以及 OmniSchema 與 OSAD 的設計；建議直接 clone 官方 repo，閱讀 `Youtu-Omni-Encoder` 的視覺/音訊 stem 與融合層實作，並嘗試在自己的領域資料上做 SFT 微調，評估是否需要啟動 OSAD。

**給研究者：** 核心創新在「共享權重編碼器 + 統一時空座標」與「token-role-based 自演化蒸餾」兩處；建議仔細閱讀 OSAD 的 reference-conditioned 設計與 co-evolution 機制，並與 Logics-Parsing-Omni、Qwen3-Omni 等雙編碼器方案做對比實驗；OmniDocBench v1.6 與 OmniParsingBench 是現成的實驗平台。

**給產品經理：** 聚焦在「為什麼需要感知層」與「能解決什麼業務問題」；Figure 1 的雷達圖與各任務分數是與利害關係人溝通的最佳素材；建議先以「文件 + 影片」兩個高頻場景做 POC，評估 ROI 後再擴展到化學、樂譜等長尾任務；同時把可審計性（時空引用）作為對內推廣的核心賣點。
