# Crafter：用於從多樣輸入生成可編輯科學圖表的多代理框架

## ⚡ TL;DR

現有科學圖表生成系統僅支援單一類型與文字輸入，且點陣輸出無法局部編輯。
Crafter 多代理框架含意圖推理、計畫、評審與精煉代理；CraftEditor 將點陣轉為可編輯 SVG。
實驗顯示 Crafter 在兩個基準上大幅超越基準，CraftEditor 也能產出更佳的可編輯 SVG。

## 摘要翻譯

科學圖表是傳達複雜研究理念最有效的手段之一，然而製作出版品質的插圖仍是論文準備工作中最耗時費力的環節之一。現有的自動化系統各自僅針對純文字輸入下的單一圖表類型，未能涵蓋研究人員實際使用的多樣圖表類型與輸入條件；此外，其點陣輸出也無法進行局部修訂。由於科學圖表是由離散語意元件所組成的結構化組合，生成器在此類版面配置上所產生的局部錯誤需要的，並非更強的主幹模型，而是一個框架。我們將此框架實例化為兩個互補的系統：Crafter——一個無需架構變更、即可在不同圖表類型與輸入條件間泛化的圖表生成多代理框架；以及 CraftEditor——沿用相同模式將點陣輸出轉換為可編輯 SVG 的系統。此外，我們提出 CraftBench，一個涵蓋三種圖表類型與四種輸入條件並附有人工品質標註的基準測試。實驗結果顯示，Crafter 在 PaperBanana-Bench 與 CraftBench 上皆大幅超越獨立生成器與代理式基準，消融實驗也證實了各元件的獨立貢獻；CraftEditor 則能忠實地將輸出轉換為可編輯 SVG，其品質超越所有基準方法。我們的程式碼與基準測試已公開於 https://github.com/HaozheZhao/Crafter。

### 核心貢獻（3～5點）
- 提出 **Crafter**：一個無需架構變更即可跨圖表類型與輸入條件泛化的多代理框架，用於可編輯科學圖表生成。
- 提出 **CraftEditor**：沿用相同的多代理框架模式，將點陣輸出忠實轉換為可編輯 SVG，解決現有系統無法局部修訂的問題。
- 提出 **CraftBench**：涵蓋三種圖表類型與四種輸入條件、附有人工品質標註的基準測試，填補該領域評測資源的缺口。
- 透過在 PaperBanana-Bench 與 CraftBench 上的實驗，驗證 Crafter 大幅超越獨立生成器與代理式基準，並以消融實驗確認各元件的獨立貢獻。
- 驗證 CraftEditor 能將輸出轉換為品質超越所有基準的可編輯 SVG，體現「框架勝於更強主幹模型」的核心設計理念。

### 適合對象
- 從事科學圖表自動化生成、可編輯向量圖形轉換或文字生成影像研究的 NLP／電腦視覺研究者。
- 關注多代理系統（Multi-Agent Harness）架構設計與其在結構化生成任務中應用的 AI 研究者。
- 需要快速產出出版品質插圖、且希望支援局部修訂的學術論文作者與海報／簡報設計者。
- 從事學術出版工具、預印本（arXiv）輔助系統或研究自動化平台開發的工程師與產品研究者。

## 深度分析

#### 方法論解析

本論文的核心論點在於一個重要的範式轉移：科學圖表（scientific figure）生成任務的瓶頸不在於更強的影像生成主幹模型（backbone），而在於缺乏一個能夠容納結構化修正記憶的編排層（orchestration layer），即所謂的「框架」（harness）。這個觀察源於一個關鍵的結構性差異：科學圖表並非自然影像，而是由離散語意元件（discrete semantic components）——標註方塊、方向箭頭、圖示、註解——所組成的結構化版面，每個元件在精確的空間關係中承載特定語意。現代生成器在此類結構化版面上表現出高方差（high variance），產生諸如標籤錯亂、連接器錯位等局部錯誤（localized errors），而單純的提示詞重述（rephrasing）無法有效修正，且累積的自由文字修正會引入矛盾。

**Crafter 架構詳解**

Crafter 採用六個協作代理（agent）共享一份演化中的圖表規格（figure specification）作為結構化記憶：

1. **意圖推理器（Intent Reasoner）**：根據上下文與文件（Docs）初始化規格種子 S₀，將使用者意圖形式化為可操作的結構化描述。
2. **計畫生成器（Plan Generator, D）**：提出 K 個候選計畫（candidate plans），實現「多樣性驅動的計畫探索」（diversity-driven plan exploration），這是三個核心機制中的第一個。
3. **影像生成後端（Image-Gen Backend, E）**：負責所有渲染工作，與任務特定行為解耦。
4. **評審器（Critic, V）**：發出指令式診斷（directive diagnostics）而非純量分數，構成「驗證後精煉迴圈」（verify-then-refine loop）的核心。
5. **規格精煉器（Specification Refiner, R）**：將評審器診斷轉化為型別化編輯（typed edits）並寫入共享規格 S，這是「結構化修正層」（structured corrective layer）的實作，避免自由文字修正帶來的提示詞矛盾。
6. **收斂判斷器（Convergence Judge）**：根據每輪結果路由至接受、精煉或還原（revert）至最終輸出（final output）。

此設計的關鍵優雅之處在於：所有任務特定行為皆封裝於代理提示詞（agent prompts）中，因此同一架構可在不同圖表類型（figure types）與輸入條件（input conditions）間無需架構變更（architectural changes）即可泛化。

**CraftEditor 三階段流程**

CraftEditor 將相同的框架模式應用於點陣轉向量（raster-to-vector）任務：

1. **擷取階段（Extraction Phase）**：剝離文字覆蓋層與視覺雜訊，從原始版面取得乾淨的圖形資產（graphical assets）。
2. **處理階段（Processing Phase）**：為每個資產產生標題（caption）並分類為向量或點陣。
3. **組合階段（Composition Phase）**：將資產組裝為 SVG 骨架（SVG skeleton），並透過混合式評審器（hybrid critic）反覆精煉。

此設計直接回應了現有點陣轉向量方法（如 AutoFigure-Edit、Edit-Banana）所面臨的元素擷取（element extraction）不可靠與組合（composition）脆弱的問題。

#### 實驗數據解讀

**CraftBench 基準測試設計**

CraftBench 是一個 279 樣本的基準測試，橫跨三種圖表類型（方法論圖表、學術示意圖、海報/資訊圖表）與四種輸入條件（純文字、粗略草圖、部分版面配置、參考視覺元素）。樣本來源涵蓋十八個研究領域的已發表論文、獎項級會議海報（award-tier conference posters）以及研究部落格，採用多階段管線搭配人工品質標註（human quality annotation）進行策展。評估協議採用視覺語言模型（VLM）作為評審，遵循 PaperBanana-Bench 的方法論，但擴展至條件式圖表評估（conditional figure assessment）。

**主要實驗結果**

Crafter 在 PaperBanana-Bench 與 CraftBench 上均大幅超越獨立生成器（standalone generators）與最強的代理式基準（agentic baseline），這在受控比較下尤為重要，因為它證明了框架設計本身（而非底層生成器）的貢獻。

**消融實驗（Ablations）**

消融實驗驗證了每個機制的獨立貢獻：移除任一單一元件會造成 5.04 至 8.90 分的下降。這個範圍值得關注——下限 5.04 分代表即使是看似次要的元件也具有實質影響，而上限 8.90 分則指出存在關鍵依賴路徑。雖然論文未明確指出哪個元件對應哪個下降幅度，但根據架構描述可推測：移除多樣性驅動計畫探索會導致單一計畫偏差；移除結構化修正層會引入提示詞矛盾；移除驗證後精煉迴圈則會失去局部修正能力。

**CraftEditor 評估**

CraftEditor 在三 VLM 集成評估（three-VLM ensemble evaluation）下超越所有基準，這個多評審者設計有助於緩解單一 VLM 偏誤。然而，由於缺乏人工評估的對照基準，VLM 評審的可信度仍需進一步驗證。

#### 與現有研究的比較

**與程式碼生成方法（Code-Generation Methods）的比較**

以 TikZ 等格式合成可編輯圖表的方法（如 Belouadi 等、Zala 等、Greisinger 與 Eger）受限於示意圖（schematic diagrams），缺乏圖示與風格化版面的視覺豐富度（visual richness）。Crafter 的策略不同：保留點陣輸出但透過 CraftEditor 提供結構化可編輯性（structurally editable），試圖兼顧視覺品質與可編輯性。

**與代理式管線（Agentic Pipelines）的比較**

現有代理式管線（如 PaperBanana、FigGen、PosterGen 等）專注於文字生成影像（text-to-image generation），且多數針對單一圖表類型。Crafter 的差異化在於：(1) 跨類型、跨條件的泛化能力；(2) 結構化記憶避免提示詞矛盾；(3) 指令式診斷支援局部修正。然而，這些方法共享一個根本限制：對底層影像生成器的依賴，當生成器在結構化版面上失敗時，框架的修正能力有其上限。

**與點陣轉向量嘗試的比較**

AutoFigure-Edit 採用單次 LLM 呼叫偵測元素並輸出 SVG，Edit-Banana 將分割與 OCR 輸出轉為 DrawIO 儲存格。兩者皆受制於元素擷取不可靠與組合脆弱。Crafter 的三階段分離（擷取、處理、組合）加上反覆精煉迴圈，理論上應能更穩健地處理這些失敗模式，但代價是更高的計算成本。

**論文承認的限制**

從全文脈絡可推導出幾個未充分探討的限制：(1) 評估完全依賴 VLM 評審，缺乏與人類專家評估的相關性分析；(2) 279 樣本的基準測試規模相對有限，可能無法充分覆蓋所有研究領域的細微差異；(3) 框架的計算成本（多代理、多輪精煉）未明確報告；(4) 對底層影像生成器的特定依賴性未充分討論。

#### 可重現性評估

**優點**

論文明確聲明程式碼與基準測試均公開於 GitHub（https://github.com/HaozheZhao/Crafter），這對於促進後續研究至關重要。Crafter 的設計哲學——所有任務特定行為封裝於代理提示詞——有利於重現，因為無需訓練新模型或修改架構。

**疑慮**

然而，重現性面臨幾個挑戰：(1) 框架依賴多個 LLM 與影像生成 API，其版本與配置可能影響結果；(2) 評估採用 VLM 評審，不同 VLM 的選擇會導致評分差異；(3) 提示詞工程的細節對於多代理系統的行為有決定性影響，但論文中提示詞的完整內容未在摘錄中展示，需查閱附錄確認；(4) CraftBench 的人工品質標註流程未詳細說明，可能影響基準的可重現策展。

**模型權重**

論文未提及釋出模型權重，這與其「框架而非模型」的定位一致——Crafter 本質上是編排現有模型的層，不涉及新模型訓練。

#### 未來研究方向

**1. 評估方法的標準化**

當前 VLM 評審的可信度是開放問題。未來工作應建立 VLM 評分與人類專家評分的相關性基準，並探索更穩健的多評審者協議（如考慮評審者間一致性加權）。

**2. 框架效率優化**

多代理、多輪精煉的計算成本是實際部署的障礙。未來可探索：(1) 早期停止策略；(2) 計畫生成器的候選數量自適應調整；(3) 評審器診斷的快取與重用。

**3. 跨模態條件輸入的擴展**

目前支援四種輸入條件，但科學圖表創作中常涉及更複雜的條件（如多張參考圖、領域特定符號庫）。擴展框架以支援更豐富的條件輸入是自然的下一步。

**4. 領域特定最佳化**

不同研究領域（如生物醫學、電腦科學、物理）對圖表有不同的慣例與符號系統。未來可探索領域特定的代理提示詞或領域適應的規格表示法。

**5. 互動式編輯工作流程**

CraftEditor 提供了點陣到 SVG 的轉換，但完整的科學圖表工作流程還包括後續的互動式編輯（如拖放、屬性面板）。將 Crafter 框架擴展為支援互動式編輯的代理系統是值得探索的方向。

**6. 錯誤分析與失敗模式理解**

論文未深入分析 Crafter 在哪些類型的圖表或輸入條件下仍會失敗。系統性的錯誤分析將有助於識別框架的當前盲點，並指導後續改進。

**7. 與其他編排模式的整合**

「框架」（harness）模式可與其他編排模式（如工作流程引擎、規劃演算法）結合，探索更強大的編排策略。例如，將收斂判斷器從啟發式規則升級為學習式策略。

**8. 開源生態系建構**

釋出標準化的代理介面、評估工具與基準測試，有助於建立科學圖表生成的開源生態系，降低後續研究的進入門檻。

## 論文問答

**Q1：為什麼科學圖表的自動化生成至今仍未被有效解決？**
A：科學圖表是學術研究中傳達複雜研究概念最有效的媒介之一，但其製作仍是論文準備過程中最耗時費力的環節之一。雖然文字生成影像技術近年快速進展，已能產出照片級真實感與設計品質的影像，但這些進展尚未真正轉化為實用的科學繪圖工具。根本原因在於科學圖表不同於一般自然影像，它是由帶有特定語意的離散元件（如標註方塊、方向箭頭、圖示、註解）所組成的結構化版面，每個元件都承載著精確的空間關係與意義，這對自動化生成提出了獨特挑戰。

**Q2：現有的自動化科學圖表生成方法有哪些根本性的不足？**
A：現有方法在兩個根本面向有所不足。第一，現有系統的適用範圍過於狹窄：實務上研究者會產生各類圖表（從學術示意圖到海報、資訊圖表），且很少單純從文字出發，而是會從粗略草圖、部分版面配置或參考視覺元素進行迭代，但現有方法主要聚焦於文字生成影像，無法處理圖表類型與輸入條件的多樣性。第二，輸出影像在實務上無法編輯：點陣式生成器產出的是靜態影像，無法局部修改（例如調整個別標籤、替換配色、重排元件），而程式碼生成方法雖可編輯但缺乏圖示與風格化版面的視覺豐富度，使得「生成到編輯」的完整工作流程至今仍未實現。

**Q3：為什麼單純提升生成模型的能力不足以解決這個問題？**
A：現代生成器在這類結構化版面上呈現高度的輸出變異，會產生局部錯誤（例如雜亂的標籤、錯位的連接線），而這些問題無法單靠重新措辭提示詞來修正。天真的重試也無效，因為每次嘗試會產生不同的錯誤組合，且在多輪迭代中累積自由文字修正會引入矛盾，進一步降低品質。真正需要的是一個「框架」（harness）層——一個包裝現有引擎、以持續演化的結構化規格作為記憶的協調層，藉此對個別失敗點進行針對性修正，並對原始意圖進行閉迴圈驗證，這正是本文的核心論點。

**Q4：Crafter 的核心架構設計是什麼？**
A：Crafter 採用多代理框架，由意圖推理器（Intent Reasoner）、計畫生成器（Plan Generator）、評審器（Critic）、規格精煉器（Specification Refiner）與收斂判斷器（Convergence Judge）等協作代理組成，它們共享一個持續演化的圖表規格作為管線的結構化記憶，而所有渲染工作則交由影像生成後端（Image-Gen Backend）負責。具體流程為：意圖推理器根據上下文與文件建立初始規格 S0；計畫生成器 D 提出 K 個候選計畫；影像生成後端 E 將每個計畫渲染成影像；評審器 V 發出指令式診斷；規格精煉器 R 將型別化編輯寫入 S；最後由收斂判斷器決定每輪要接受、精煉或還原為最終輸出。

**Q5：Crafter 的三大關鍵機制是什麼？它們如何解決現有方法的問題？**
A：三大關鍵機制分別為「多樣性驅動的計畫探索」、「結構化修正層」與「驗證後精煉迴圈」。多樣性驅動的計畫探索會平行生成多個候選框架，避免單一計畫陷入局部錯誤；結構化修正層將評審驅動的型別化編輯累積進共享規格，避免自由文字修訂中常見的提示詞矛盾；驗證後精煉迴圈則讓指令式評審器發出針對性修正，而非僅給出單一分數，從而實現對個別失敗點的精準修正與閉迴圈驗證。

**Q6：為什麼 Crafter 能在不改變架構的情況下泛化到不同圖表類型和輸入條件？**
A：Crafter 的設計將所有任務專屬行為都封裝在代理的提示詞中，而非寫死在架構或程式碼裡，因此同一套架構可以無需結構性變更即可處理不同圖表類型（方法論圖表、學術示意圖、海報、資訊圖表等）與不同輸入條件（純文字、粗略草圖、部分版面配置、參考視覺元素等）。這種「行為在提示詞中、架構在框架中」的解耦設計，使得框架本身具備高度的可重用性與可擴展性，研究者只需更換或調整代理提示詞即可適應新任務。

**Q7：CraftBench 這個新基準測試有什麼特色？**
A：CraftBench 是一個涵蓋三種圖表類型與四種輸入條件、共 279 個樣本的基準測試，樣本來源涵蓋十八個研究領域的已發表論文、得獎等級的會議海報以及研究部落格，並透過多階段管線搭配人工品質標註進行策展。它採用基於視覺語言模型（VLM）的評估協議，能評估輸出品質對照真實影像，並評估系統是否能跨圖表類型泛化以及是否保留使用者的條件輸入，彌補了現有評測僅涵蓋文字生成影像方法論圖表的狹隘範圍。

**Q8：Crafter 在實驗中取得了哪些具體成果？**
A：在受控比較下，Crafter 在 PaperBanana-Bench 與 CraftBench 上都大幅優於獨立生成器與最強的代理式基準，證明了框架設計的實質效益。同時，CraftEditor 在三個 VLM 集成的評估中將生成的輸出轉換為可編輯 SVG，且表現優於所有基準，確立了從生成到編輯端到端工作流程的可行性。這些結果顯示 Crafter 不僅在生成品質上突破，也在後處理的可編輯性上樹立了新標竿。

**Q9：消融實驗揭示了哪些元件的重要性？**
A：消融實驗顯示，移除任何單一元件都會造成 5.04 到 8.90 分的顯著下降，驗證了多樣性驅動計畫探索、結構化修正層與驗證後精煉迴圈三大機制各自獨立且關鍵的貢獻。這意味著這三個機制並非冗餘設計，而是互補且缺一不可：少了多樣性探索會陷入單一計畫的錯誤；少了結構化修正層會累積提示詞矛盾；少了驗證後精煉迴圈則無法進行針對性修正與閉迴圈驗證。

**Q10：Crafter 和 CraftEditor 組合後能形成什麼樣的端到端工作流程？**
A：Crafter 與 CraftEditor 共同構成科學圖表領域第一個從生成到編輯的端到端管線：Crafter 負責從多樣化輸入產生高品質的點陣圖表，CraftEditor 則將這些點陣輸出轉換為結構化可編輯的 SVG，使研究者能在後續進行局部修改（如調整標籤、替換配色、重排元件）。這個工作流程涵蓋了科學圖表生命週期中最關鍵的兩個階段——生成與編輯——解決了過去「生成品質高但無法編輯」或「可編輯但視覺豐富度不足」的兩難。

**Q11：這項研究對學術出版和科學傳播有哪些實際影響？**
A：對學術出版而言，這項研究能大幅降低研究者製作出版品質圖表的時間成本，使研究者能將精力集中在研究本身而非繪圖細節上。對科學傳播而言，由於系統支援海報、資訊圖表等多種圖表類型與多種輸入條件，研究者能更便利地將研究成果轉化為適合不同受眾（學術同儕、大眾、政策制定者）的視覺化形式，進而提升科學知識的傳播效率與影響力。

**Q12：從產品化的角度來看，這個系統有哪些設計考量？**
A：從產品化角度，Crafter 採用的框架模式（harness pattern）具有高度模組化特性，影像生成後端可獨立替換為更新或更強的模型，而無需修改框架本身，這對長期維護與成本控制相當有利。此外，所有任務專屬行為集中在代理提示詞中，使得系統能透過提示詞工程快速適應新場景，而無需重新訓練或重新部署，這對快速迭代的產品開發極為重要。CraftEditor 的引入則讓產品能覆蓋生成後的編輯需求，提升使用者黏著度與工作流程完整性。

**Q13：這項研究承認了哪些限制？**
A：雖然論文中未明確列出所有限制，但從方法設計可推論出幾項已知限制：首先，系統仰賴視覺語言模型作為評審器與判斷器，這意味著其表現上限受制於底層 VLM 的能力；其次，雖然框架設計支援多樣化輸入，但對於極度複雜或高度專業領域的圖表（如特定學科的特殊符號系統），仍可能需要領域專屬的提示詞調整；最後，雖然 CraftEditor 能將點陣轉為可編輯 SVG，但對於極度密集或非標準版面，元素擷取與組合的精確度仍可能受到限制。

**Q14：在什麼樣的情況下系統可能會失敗？**
A：系統可能在以下情況下表現不佳：當輸入的粗略草圖或參考視覺元素極度模糊或語意不清時，意圖推理器可能無法準確捕捉使用者意圖；當圖表包含大量密集且高度耦合的元件時，單一輪次的精煉可能無法同時修正所有局部錯誤，需要更多迭代；當目標圖表類型涉及高度領域專屬的視覺慣例（如特定學科的標準符號）時，通用提示詞可能不足以產出符合領域期待的結果。此外，若底層影像生成後端在特定風格上有弱點，框架的修正機制也只能緩解而無法完全克服。

**Q15：未來的研究方向有哪些？**
A：未來研究方向可從幾個層面展開：在評估面，可建立更細緻的人機協作評估協議，結合專家評分與自動化指標；在生成面，可探索將框架模式擴展至影片、互動式圖表或多模態科學內容；在編輯面，可進一步提升 CraftEditor 對複雜版面與領域專屬符號的處理能力；此外，將整個系統與學術出版工作流程（如 LaTeX、Overleaf、期刊投稿系統）深度整合，也是值得探索的實用化方向，使科學圖表的生成與編輯能無縫嵌入研究者的日常工作流。

## 實務應用指南

### 適用場景

1. **學術論文方法論圖表自動化產製**：研究團隊在準備期刊或會議投稿時，可將方法論章節的文字描述、粗略草圖或參考架構圖輸入 Crafter，由系統自動生成符合出版品質的方法論示意圖，縮短從草稿到定稿的反覆迭代時間。

2. **研究海報與學術展示素材生成**：研究生準備國際會議海報時，可輸入部分版面配置與參考視覺元素（圖示、圖標），由 Crafter 生成具視覺豐富度的海報初稿，再透過 CraftEditor 將點陣輸出轉為可編輯 SVG，方便在地修改文字、配色與元件位置。

3. **跨領域教材與科普資訊圖表製作**：教科書編輯、科普內容創作者可輸入教學流程描述或粗略草圖，由 Crafter 生成涵蓋多種類型（學術示意圖、資訊圖表、教學插圖）的圖片，並透過 CraftEditor 取得結構化可編輯版本，便於後續翻譯、調色與排版。

4. **企業研發報告與技術白皮書插圖**：技術寫作團隊在撰寫內部技術報告或對外白皮書時，可將系統架構描述與既有參考元件輸入 Crafter，快速產出風格統一的架構圖，並透過 CraftEditor 將其轉為 SVG 以便嵌入企業設計系統或品牌模板。

5. **研究部落格與線上教學內容視覺化**：研究人員撰寫個人部落格、線上課程或技術分享文章時，可輸入文字脈絡與粗略草圖，由 Crafter 生成具備視覺吸引力的圖片，並透過 CraftEditor 取得可編輯版本，方便日後更新內容時同步調整圖片。

### 實作前置條件

**資料準備**
- 目標圖表的文字描述、上下文文件（Docs）以及任何粗略草圖、部分版面配置或參考視覺元素。
- 若使用 CraftEditor，需準備欲轉換的點陣圖（PNG、JPG 等）作為輸入。
- 評估階段需準備 CraftBench 風格的標註資料或自有的品質標註流程。

**運算資源**
- 後端影像生成模型（Image-Gen Backend）需具備足夠的 GPU 資源以支援多輪渲染，建議使用支援文字生成影像的擴散模型 API 或自部署模型。
- 多代理推論需要可承載多個 LLM 代理同時運行的運算環境，建議使用雲端 API 或具備充足 GPU 記憶體的自部署 LLM。
- 迭代式 verify-then-refine 迴圈會產生多次渲染與評審呼叫，需預留相應的 API 配額與成本預算。

**技能門檻**
- 熟悉 LLM 代理設計、提示工程（prompt engineering）與多代理編排框架（如 LangGraph、AutoGen 等）。
- 具備 SVG 結構、向量圖形編輯與基本排版知識，以便理解 CraftEditor 輸出並進行後續調整。
- 了解科學圖表的語意元件組成（標註框、方向箭頭、圖示、註解）與空間關係設計原則。
- 具備 VLM 評審與基準測試設計經驗，以便建立內部評估流程。

### 實作步驟建議

1. **釐清輸入條件與圖表類型**：先盤點實際使用情境中會遇到的圖表類型（方法論圖表、學術示意圖、海報、資訊圖表）與輸入條件（純文字、粗略草圖、部分版面、參考視覺元素），確認 Crafter 的多代理框架能涵蓋這些場景而無需架構變更。

2. **建置多代理管線骨架**：依據 Crafter 架構，依序組裝意圖推理器（Intent Reasoner）、計畫生成器（Plan Generator）、影像生成後端（Image-Gen Backend）、評審器（Critic）、規格精煉器（Specification Refiner）與收斂判斷器（Convergence Judge），並設計共享的圖表規格（Specification）作為管線的結構化記憶體。

3. **設計多樣性驅動的計畫探索機制**：在計畫生成器中設定 K 個候選計畫的平行生成策略，確保不同候選計畫在版面配置、視覺風格與元件組合上具有足夠差異，避免收斂至單一框架。

4. **實作結構化修正層與指令式評審**：將評審器的輸出設計為指令式診斷（directive diagnostics）而非純量分數，並由規格精煉器將這些診斷轉為型別化編輯（typed edits）寫入共享規格，避免自由文字修正累積產生矛盾。

5. **建立 verify-then-refine 收斂迴圈**：設定收斂判斷器的路由邏輯，根據評審結果決定接受、精煉或還原至前一輪狀態，並定義最大迭代次數與品質門檻以平衡品質與成本。

6. **整合 CraftEditor 完成端到端流程**：將 Crafter 的點陣輸出串接至 CraftEditor，依序執行擷取（去除文字疊加與視覺雜訊）、處理（為每個資產加上標題並分類為向量或點陣）與組合（組裝 SVG 骨架並以混合式評審迭代精煉）三個階段。

7. **建立評估流程與基準測試**：採用 CraftBench 的 VLM 評審協議，針對三種圖表類型與四種輸入條件進行系統性評估，並輔以人工品質標註作為最終把關。

8. **執行消融實驗驗證元件貢獻**：依據論文的消融實驗結果（移除任一元件會造成 5.04 至 8.90 分的下降），逐一關閉多樣性計畫探索、結構化修正層或 verify-then-refine 迴圈，確認各機制在自身環境中的獨立貢獻。

9. **部署與持續監控**：將管線部署為可重複執行的服務，記錄每輪的規格狀態、評審診斷與最終輸出，並建立品質回饋機制以持續優化提示與代理行為。

### 潛在風險與注意事項

- **迭代成本失控**：verify-then-refine 迴圈可能因收斂條件設計不當而產生過多輪次的渲染與評審呼叫，造成 API 成本與延遲顯著上升。建議設定明確的最大迭代次數與品質門檻，並監控每輪的成本變化。

- **評審診斷的累積矛盾**：若評審器輸出未嚴格結構化為指令式診斷，而是混入自由文字描述，後續的型別化編輯可能產生邏輯衝突。應嚴格限制評審輸出的格式與語義範圍，並在規格精煉器中加入一致性檢查。

- **點陣轉向量的元素擷取失敗**：CraftEditor 在處理複雜版面或低品質點陣圖時，可能出現元素擷取不完整或分類錯誤。建議在擷取階段加入信心分數門檻，對低信心資產標記為人工複核。

- **圖表類型與輸入條件的覆蓋盲區**：雖然 Crafter 設計為無需架構變更即可泛化，但極端特殊的圖表類型或輸入條件仍可能超出代理提示的承載範圍。應建立未涵蓋案例的回報機制，並定期擴充提示與評估基準。

- **VLM 評審的偏誤與不穩定性**：VLM 評審結果可能受模型版本、提示措辭與隨機性影響。建議採用多模型集成評審（如三個 VLM 的一致性投票）並定期以人工標註校正。

- **SVG 輸出的後續維護負擔**：CraftEditor 產生的 SVG 雖然可編輯，但若元件命名、群組結構與樣式屬性未標準化，後續維護成本可能偏高。應在組合階段建立命名與結構規範，並提供對應的編輯工具或外掛。

### 與其他技術的整合建議

- **與 LaTeX 寫作流程整合**：將 Crafter 嵌入 LaTeX 編譯流程，於 `\includegraphics` 巨集中呼叫 Crafter API 自動生成方法論圖表，並透過 CraftEditor 將 SVG 轉為 TikZ 或保留 SVG 格式以相容不同期刊模板。

- **與設計系統與品牌模板整合**：將企業或機構的設計系統（配色、字型、圖示庫）注入 Crafter 的計畫生成器與 CraftEditor 的組合階段，確保所有產出符合品牌規範。

- **與版本控制與協作平台整合**：將 Crafter 的共享規格、評審診斷與最終輸出納入 Git 版本控制，並串接至 GitHub、GitLab 等協作平台，使團隊成員能追蹤圖表的演進歷史並進行審閱。

- **與文件管理與知識庫整合**：將 Crafter 串接至內部文件管理系統（如 Confluence、Notion）或研究知識庫，於文件撰寫流程中直接呼叫 Crafter 生成對應圖表，並將 SVG 輸出回存至知識庫供後續引用。

- **與 VLM 評審與品質監控平台整合**：將 CraftBench 的 VLM 評審協議整合至內部品質監控平台，持續追蹤 Crafter 與 CraftEditor 的輸出品質，並在品質下降時觸發警示與回歸測試。

- **與其他代理框架整合**：Crafter 的多代理架構可與 LangGraph、AutoGen 等代理編排框架結合，利用其狀態管理與工具呼叫能力簡化管線建置，並與既有代理生態系共享元件。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀論文摘要與第 1 節的問題陳述，理解科學圖表生成相較於一般文字生成影像的特殊性（結構化語意元件、局部錯誤、可編輯性需求），再瀏覽圖 1 的 Crafter 架構圖，建立對意圖推理器、計畫生成器、評審器、規格精煉器與收斂判斷器等元件的高階認知，最後透過 GitHub 儲存庫的範例與 CraftBench 基準感受實際運作方式。

**給 AI 工程師**：建議聚焦於第 1 節後半段的三個核心機制（多樣性驅動計畫探索、結構化修正層、verify-then-refine 迴圈）與第 2 節的相關工作比較，理解 Crafter 相較於既有代理式管線與程式碼生成方法的設計取捨，並參考消融實驗結果評估各元件在自身系統中的整合優先順序。

**給研究者**：建議深入閱讀 Crafter 的共享規格設計、指令式評審診斷的語義定義，以及 CraftBench 的建構流程與評估協議，思考如何將此框架延伸至其他結構化視覺生成任務（如技術插圖、資料視覺化），並關注 VLM 評審的偏誤與人類標註的對齊問題。

**給產品經理**：建議從適用場景章節出發，盤點自身產品中需要自動化生成科學圖表的具體情境（論文、海報、教材、白皮書），評估 Crafter 在多圖表類型與多輸入條件下的泛化能力是否符合需求，並關注迭代成本、SVG 後續維護與品牌一致性等實務風險，以規劃合理的導入時程與資源配置。
