# SoftwareGym：以多樣化合成軟體環境擴展電腦使用代理（Computer-Use Agent, CUA）訓練

**原文標題：** SoftwareGym: Scaling Computer-Use Agent Training with Diverse Synthesized Software Environments

**發布日期：** 2026-10-08

## ⚡ TL;DR

訓練電腦使用代理需要大量多樣可靠的軟體環境，但原生應用整合成本高，瀏覽器環境互動深度有限。
本文提出 SoftwareGym 管線，透過多代理設計與 GUI 迭代修復，合成多樣可靠的桌面應用。
該系統合成182個應用，GUI通過率91.5%，訓練後OSWorld Pass@3提升至56.97%。

## 摘要翻譯

電腦使用代理（Computer-Use Agents, CUAs）正快速進步，然而大規模合成多樣且可靠的軟體環境仍具挑戰性。原生應用程式環境（native application environment）需要大量的建構與整合工作，這限制了應用程式的覆蓋範圍並增加了應用程式特定過擬合（application-specific overfitting）的風險。瀏覽器託管環境（browser-hosted environment）在互動深度（interaction depth）與工作流程複雜度（workflow complexity）方面有所不足。這些限制催生了 SoftwareGym，一個用於合成具有多樣化介面、可執行功能（executable functionality）與執行階段驗證行為（runtime-verified behavior）之 GUI 軟體環境的自動化管線（automated pipeline）。它會產生結構上多樣化的設計，將其實現為可執行應用程式（runnable application），並採用結合迭代修復（iterative repair）機制的 GUI 評估來確保功能可靠性（functional reliability）。使用 SoftwareGym，我們在十二個類別中合成了 182 個應用程式，並達到 91.5% 的平均 GUI 任務通過率（pass rate）。我們建構了 SoftwareGym-Bench，一個涵蓋相同十二個類別的 120 項任務評估套件（evaluation suite），並使用從這些環境中收集的軌跡（trajectory）來進行 CUA 訓練。所得到的模型在嚴格意義上的域外（out-of-domain）OSWorld 基準上將 Pass@3 從 41.39% 提升至 56.97%，並在 SoftwareGym-Bench 上達到 40.0%。這些結果展示了合成軟體環境作為 CUA 訓練之可擴展（scalable）且可遷移監督訊號（supervision signal）的潛力。

### 核心貢獻（3～5點）
- **問題分析**：系統性地指出原生應用程式環境（建構成本高、易過擬合）與瀏覽器託管環境（互動深度受限）兩大現有路徑的瓶頸，為合成式環境路線奠定動機基礎。
- **方法創新**：提出 SoftwareGym 自動化管線，透過「結構多樣化設計 → 可執行應用程式實現 → 結合迭代修復的 GUI 評估」三階段機制，確保合成環境同時具備介面多樣性、可執行性與功能可靠性。
- **規模化成果**：在十二個軟體類別中合成 182 個應用程式，平均 GUI 任務通過率達 91.5%，證明合成管線在規模與品質上皆可兼顧。
- **基準與訓練資源**：建構 SoftwareGym-Bench（120 項任務評估套件），並利用所收集的軌跡作為 CUA 訓練資料，提供可重現的訓練與評估基礎設施。
- **泛化能力驗證**：在嚴格域外（strictly out-of-domain）的 OSWorld 基準上將 Pass@3 從 41.39% 提升至 56.97%，證明合成環境所產生的監督訊號具備良好的遷移性與泛化能力。

### 適合對象
- **電腦使用代理（Computer-Use Agent, CUA）研究者**：關注代理在桌面、瀏覽器及 GUI 環境中自主操作能力的研究團隊。
- **強化學習與代理訓練研究者**：尋求可擴展、可重現訓練環境與監督訊號來源的學者與工程師。
- **GUI 自動化與軟體測試領域從業者**：對自動化 GUI 評估、迭代修復機制感興趣的實務工作者。
- **AI for Software Engineering 研究者**：探討軟體合成、程式生成與自動化管線設計的研究人員。
- **基準測試與評估方法論研究者**：關注如何建構具備多樣性與遷移性的代理評估套件之學者。

## 深度分析

#### 方法論解析

SoftwareGym 的核心方法論建立在「自動化 GUI 軟體合成」這一範式轉移之上，旨在解決電腦使用代理（Computer-Use Agent, CUA）訓練中環境建構的瓶頸問題。其方法設計可從三個維度深入剖析：

**1. 三階段管線架構（Three-Stage Pipeline）**

整個合成流程被劃分為三個遞進階段：

- **設計階段（Software Design）**：從最小化的人工輸入出發，擴展為完整的「軟體規格（Software Specification）」與多個「變體特定設計套件（Verified Design Packages）」。此階段的關鍵創新在於「類別層級功能規格（Category-level Functional Specification）」與「變體特定介面設計（Variant-specific Interface Design）」的解耦——前者確保同一類別軟體共享核心功能語意，後者則透過風格變體（style variants）避免介面同質化。這種設計直接回應了「介面與互動多樣性（interface and interaction diversity）」的挑戰。

- **實作階段（Software Implementation）**：將設計套件轉換為可執行應用程式（runnable application），並進行原始碼層級驗證（source-level verification）。此階段確保程式碼語法與邏輯層面的正確性。

- **評估階段（Evaluation）**：執行基於檢查點的 GUI 評估（checkpoint-based GUI evaluation），透過實際 GUI 互動觀察失敗模式，並引導迭代修復（iterative repair）。只有同時通過原始碼驗證與 GUI 驗證的應用程式才能進入軟體函式庫（software library）。

**2. 多代理協作機制（Multi-Agent Collaboration）**

從「multi-agent pipeline」的描述可推斷，設計、實作、評估各階段均由專門化的代理負責協作。這種分工反映了「驗證負擔（verification burden）」的分散化思路——單一代理難以同時兼顧多樣性設計、程式碼生成、與 GUI 行為驗證，而多代理架構允許每個代理專注於其能力範圍內的子任務。

**3. 雙層驗證策略（Dual-Layer Verification）**

「原始碼層級驗證 + GUI 檢查點評估」的雙層機制是功能可靠性（functional reliability）的核心保障。原始碼驗證捕捉語法與邏輯錯誤，GUI 評估則捕捉介面層級的可用性問題——例如按鈕無法觸發預期行為、狀態轉換異常等。這種「端到端可執行性」的驗證標準，比純粹的程式碼正確性檢查更貼近真實使用情境。

**4. 任務合成（Task Synthesis）**

第三節末尾提及的「Task Synthesis」階段（圖 3）將已驗證的功能轉化為可執行的 GUI 任務（executable GUI tasks），這是從「環境」到「訓練資料」的橋樑。透過軌跡（trajectory）收集，模型得以從結構化互動中學習泛化能力。

**方法論的關鍵洞察**：SoftwareGym 的設計哲學是「以合成取代採集、以驗證取代假設」。相較於依賴既有應用程式或瀏覽器託管環境，它主動建構可控的軟體分佈（software distribution），這對「應用程式特定過擬合（application-specific overfitting）」的防範具有結構性優勢。

#### 實驗數據解讀

**1. 環境規模與品質指標**

- **182 個可執行應用程式**橫跨 **12 個軟體類別**，平均 GUI 任務通過率（pass rate）達 **91.5%**。這個數據揭示了管線的兩個關鍵特性：
  - **規模化能力**：182 個應用程式的數量遠超典型手動開發的基準集規模。
  - **品質穩定性**：91.5% 的平均通過率意味著雙層驗證機制有效過濾了功能性缺陷，僅有約 8.5% 的任務在合成環境中失敗。

- **代表性應用程式**（圖 1）涵蓋 Pic-Editor、VideoPlayer、TableEditor、CodeEditor 等多元類別，每個類別展示出實質的「互動深度（interaction depth）」——例如 Pic-Editor 包含「開啟影像 + 灰階轉換 + 繪製矩形 + 筆刷塗抹 + 旋轉」等多步驟工作流程（multi-step workflow），這對訓練代理的長程規劃能力至關重要。

**2. 域外泛化效能（Out-of-Domain Generalization）**

最關鍵的實驗結果是 **OSWorld Pass@3 從 41.39% 提升至 56.97%**，提升幅度達 **15.58 個百分點**。此結果的解讀重點在於：

- **嚴格的域外設定**：模型未使用任何 OSWorld 的應用程式、任務或軌跡進行訓練，純粹依賴 SoftwareGym 合成資料。
- **絕對效能**：56.97% 的 Pass@3 在 OSWorld 這類高難度基準上屬於強勁表現，證明合成環境學到的技能具有高度可遷移性。
- **相對增益**：15.58 點的提升幅度顯示合成資料的「資訊密度」極高——相較於真實環境資料，合成資料在單位成本下提供了更多樣化的監督訊號（supervision signal）。

**3. 內部基準表現**

在 SoftwareGym-Bench（120 個任務，涵蓋相同 12 個類別）上，模型達到 **40.0% Pass@3**，並「超越數個更大的專用電腦使用代理」。此結果的解讀需注意：

- **領域內 vs. 域外的落差**：40.0%（領域內）vs. 56.97%（域外 OSWorld）的反直覺現象，可能反映 SoftwareGym-Bench 的任務設計更具挑戰性，或 OSWorld 的某些任務結構恰好與合成環境的訓練分佈更為對齊。
- **相對優勢**：擊敗「更大的專用代理」意味著 SoftwareGym 訓練的模型在參數效率（parameter efficiency）上具有競爭力，這對實際部署具有重要意義。

**4. 消融實驗的隱含訊息**

論文提及「透過廣泛的評估與消融實驗驗證管線的關鍵組件」，雖然具體數字未在提供的文本中展開，但可推測消融對象至少包括：設計階段的多樣性機制、雙層驗證機制、以及任務合成策略。這些消融結果將是判斷各組件實際貢獻度的關鍵依據。

#### 與現有研究的比較

**1. 與原生應用程式環境的比較**

原生應用程式環境（如 OSWorld、Windows Agent Arena、AndroidWorld）保留了真實的軟體狀態與複雜工作流程，但存在兩個結構性限制：

- **整合成本高**：將真實桌面與行動應用程式整合至可重現的訓練環境（reproducible training environment）需要大量工程投入（engineering effort），限制了應用程式覆蓋率。
- **過擬合風險**：在固定的軟體池（software pool）上反覆訓練，可能導致代理學習到應用程式特定的捷徑，而非通用的 GUI 操作技能。

SoftwareGym 的優勢在於「可控的軟體分佈」——透過合成新應用程式，主動擴展訓練分佈，從根本上緩解過擬合風險。然而，其代價是合成應用程式的「真實性」可能不及原生應用，這需要在後續研究中持續驗證。

**2. 與瀏覽器託管環境的比較**

瀏覽器託管環境（InfiniteWeb、AutoWebWorld、GUI-GENESIS、ScaleWoB）以網頁作為共享底層（shared substrate），具備部署簡便與狀態控制（state control）的優勢，但受限於：

- **互動深度受限**：HTML/DOM 結構難以模擬原生應用程式的複雜狀態管理與持久化工作流程。
- **介面同質化**：所有網頁應用本質上共享相似的渲染與互動範式。

SoftwareGym 透過合成獨立桌面應用程式（standalone desktop application），突破了瀏覽器底層的限制，能夠實現更豐富的 GUI 多樣性（GUI diversity）與互動深度。

**3. 與其他資料合成方法的比較**

- **CUA-Universe、Gym-Anything**：適配與配置既有軟體，仍受制於既有應用程式的覆蓋範圍。
- **軌跡精煉與人類示範**（Qin et al., 2025; Wang et al., 2025b;a）：依賴線上資料或人類示範，資料規模與多樣性受限。

SoftwareGym 的定位獨特之處在於「從零合成」——它不依賴既有軟體或人類示範，而是透過自動化管線生成全新的可執行環境，這在 CUA 訓練領域屬於範式層面的創新。

**4. 局限性與未解問題**

- **真實性差距**：合成應用程式的視覺與互動保真度與真實軟體仍有差距，這可能限制在高度擬真任務上的遷移效果。
- **任務複雜度上限**：雖然展示了多步驟工作流程，但合成任務的「真實業務邏輯」複雜度仍待驗證。
- **領域覆蓋偏置**：12 個類別的選擇可能無法完全代表真實使用情境的多樣性。

#### 未來研究方向

**1. 環境真實性的提升**

當前合成環境在視覺保真度與互動細節上仍有提升空間。未來研究可探索：

- **高保真渲染技術**：整合更先進的 GUI 渲染引擎，提升合成應用程式的視覺真實性。
- **真實軟體行為模擬**：引入更複雜的業務邏輯模擬，使合成環境的行為模式更貼近真實軟體。
- **跨平台一致性**：擴展至行動裝置、嵌入式系統等更多平台，構建統一的合成環境框架。

**2. 任務複雜度的擴展**

- **長程任務設計**：探索需要數十步甚至上百步互動的複雜任務，這對代理的長程規劃與記憶能力提出更高要求。
- **多應用程式協作**：設計需要跨多個合成應用程式協作的工作流程，例如「在 TableEditor 中整理資料 → 在 CodeEditor 中撰寫分析腳本 → 在 Pic-Editor 中生成視覺化圖表」。
- **錯誤恢復情境**：引入需要代理從錯誤狀態恢復的任務，提升代理的魯棒性。

**3. 訓練方法的創新**

- **課程學習（Curriculum Learning）**：根據任務難度動態調整訓練資料的組成，提升學習效率。
- **自我對抗訓練**：讓代理在合成環境中自我探索並產生訓練資料，進一步降低對人工設計任務的依賴。
- **多模態監督**：整合視覺、文字、語音等多模態監督訊號，提升代理的感知能力。

**4. 評估方法的完善**

- **更細粒度的能力評估**：將 GUI 任務通過率分解為「感知」、「規劃」、「執行」、「恢復」等子能力指標，提供更精細的診斷資訊。
- **跨基準泛化研究**：系統性地評估在 SoftwareGym 上訓練的模型在其他 CUA 基準（如 Windows Agent Arena、AndroidWorld）上的表現。
- **人類專家對齊評估**：引入人類專家對合成環境與任務品質的評估，補充自動化指標的不足。

**5. 理論層面的探索**

- **合成資料的資訊理論分析**：量化合成環境相較於真實環境的「資訊增益」，理解為何合成資料能帶來如此顯著的泛化提升。
- **環境多樣性與泛化能力的因果關係**：透過控制變數實驗，釐清介面多樣性、功能多樣性、互動深度等因素對泛化能力的獨立貢獻。
- **可擴展性的理論邊界**：探索合成環境規模與模型效能之間的 scaling law，為未來的資源配置提供理論指導。

**6. 應用領域的拓展**

- **垂直領域應用**：將 SoftwareGym 的方法論應用於醫療、金融、教育等垂直領域，合成領域特定的 GUI 環境。
- **人機協作研究**：探索合成環境作為「安全沙盒」在人類-Agent 協作研究中的應用價值。
- **代理安全與對齊**：利用合成環境研究代理的潛在風險行為，例如未授權操作、資料洩漏等。

## 論文問答

**Q1：為什麼訓練電腦使用代理（CUA）需要大量多樣化的軟體環境？這個問題為何成為瓶頸？**

A：訓練具備泛化能力的 CUA 需要從可執行的軟體環境中收集大量互動軌跡，因為代理必須在多樣、真實且可靠的介面中學習操作模式。然而，建構這樣的環境需要投入大量工程資源來整合真實應用程式並確保其可重現性，使得「環境建構」成為整個 CUA 訓練流程中最主要的瓶頸。論文中明確指出，目前的資料合成方法無法同時滿足介面與互動多樣性、功能可靠性與可擴展性這三項要求，這正是 SoftwareGym 試圖解決的核心問題。

**Q2：現有的兩種環境建構方法（原生應用程式環境與瀏覽器託管環境）各有什麼限制？**

A：原生應用程式環境（如 OSWorld、Windows Agent Arena）能保留真實的軟體狀態與複雜工作流程，但將這些應用整合到可重現的訓練環境中需要高昂的工程成本，限制了應用覆蓋範圍，並增加了代理在特定應用上過擬合的風險。瀏覽器託管環境（如 InfiniteWeb、AutoWebWorld）雖然部署簡單且易於控制狀態，但受限於共享的瀏覽器／HTML／DOM 底層架構，互動深度與工作流程複雜度都受到限制，難以模擬真實桌面應用的完整功能。

**Q3：為什麼「介面多樣性」、「功能可靠性」與「可擴展性」這三個需求難以同時滿足？**

A：這三個需求之間存在明顯的張力：介面與互動多樣性要求在相同軟體類別內產生差異化的設計，但無約束的生成往往會收斂到相似的佈局與互動模式；功能可靠性要求每個指定功能在完整的 GUI 工作流程中都保持可用，這對自動化生成來說是巨大的驗證負擔；可擴展性則要求上述多樣性控制與可靠性檢查能應用於大規模軟體池。當這三者結合時，手動開發無法承受的驗證負擔成為主要障礙，因此需要像 SoftwareGym 這樣的自動化管線來同時兼顧。

**Q4：SoftwareGym 的核心方法是什麼？它如何運作？**

A：SoftwareGym 是一個自動化的多代理管線，用於合成 GUI 軟體環境，其運作分為三個階段。第一階段是「軟體設計」，將最少的人類輸入擴展為詳細的功能規格、多樣化的 UI 藍圖與對應的互動方案；第二階段是「軟體實作」，將每個設計套件轉換為可執行的應用程式並進行原始碼層級的功能驗證；第三階段是「評估」，執行基於檢查點的 GUI 測試並引導迭代式實作修復。通過這三個階段，SoftwareGym 能以批次方式產生多樣化且功能可靠的軟體環境。

**Q5：SoftwareGym 如何確保「功能可靠性」？它採用了哪些驗證機制？**

A：SoftwareGym 結合了兩層驗證機制來確保功能可靠性：首先是原始碼層級驗證，檢查每個應用程式的程式碼是否正確實作其規格；其次是基於檢查點的 GUI 評估，透過實際的圖形介面互動來測試功能的可用性。當 GUI 測試發現失敗時，系統會引導迭代式的實作修復流程，只有同時通過原始碼層級與 GUI 兩種驗證的應用程式才會進入最終的軟體函式庫，這種雙重把關大幅降低了產生「殘破應用」的機率。

**Q6：SoftwareGym 如何在「介面多樣性」與「功能可靠性」之間取得平衡？**

A：SoftwareGym 採用「類別層級功能規格」加上「變體特定介面設計」的策略來平衡這兩個需求。在類別層級，系統定義共享的功能規格，確保同一類別內所有變體都具備一致的核心功能；在變體層級，則為每個變體產生獨特的介面與互動設計，避免佈局與互動模式收斂到單一形式。這種「共享功能、差異化介面」的設計哲學讓系統既能維持功能可靠性，又能產生豐富的 GUI 多樣性，從而支撐代理的泛化能力。

**Q7：SoftwareGym-Bench 是什麼？它如何設計？**

A：SoftwareGym-Bench 是一個專門設計的 120 個任務評估套件，涵蓋與 SoftwareGym 軟體函式庫相同的十二個軟體類別。這個基準測試的目的是提供一個與訓練環境同源但任務獨立的評估場景，用來衡量代理在合成環境中的真實表現。值得注意的是，雖然訓練軌跡來自 SoftwareGym，但 SoftwareGym-Bench 的任務設計是獨立的，這使得它能作為訓練效果的補充驗證，而非單純的同域測試。

**Q8：在 OSWorld 上訓練後的模型表現如何？這個結果為何重要？**

A：使用 SoftwareGym 軌跡訓練的模型在 OSWorld 基準上將 Pass@3 從 41.39% 提升至 56.97%，提升了 15.58 個百分點。這個結果之所以重要，是因為訓練過程中完全沒有使用任何 OSWorld 的應用程式、任務或軌跡，純粹是「域外泛化」的表現。這證明了合成軟體環境能提供可遷移的監督訊號，代理從中學到的操作能力並非僅限於特定應用，而是能泛化到真實的桌面環境。

**Q9：消融研究揭示了哪些關鍵設計選擇的貢獻？**

A：論文中透過廣泛的消融研究驗證了管線中各個關鍵元件的必要性，包括設計階段的多樣性控制、實作階段的原始碼驗證，以及評估階段的 GUI 檢查點測試與迭代修復機制。這些消融實驗顯示，移除任何一個元件都會導致最終應用程式的功能可靠性或多樣性下降，進而影響訓練出的代理在 OSWorld 上的表現。這些結果強調了 SoftwareGym 並非僅靠「大量生成」取勝，而是其多層次的品質控制機制共同造就了優異的泛化效果。

**Q10：SoftwareGym 對實際 GUI 軟體開發有何影響？**

A：SoftwareGym 展示了自動化 GUI 軟體合成的可行性，能以遠低於手動開發的時間與金錢成本產出可執行的應用程式，這對於需要大量原型或測試環境的場景特別有價值。實際上，開發者可以利用這個管線快速生成特定類別的多個變體，用於使用者研究、A/B 測試或教學示範，而無需為每個變體投入完整的開發週期。此外，合成環境的可控性也讓研究者能精準調整介面與互動模式，系統性地研究 GUI 設計對使用者行為的影響。

**Q11：這個方法對 CUA 訓練領域的影響是什麼？**

A：SoftwareGym 為 CUA 訓練提供了一種可擴展的監督訊號來源，打破了過去依賴真實應用程式或瀏覽器環境的兩難。透過合成多樣化且可靠的軟體環境，研究者不再受限於既有應用程式的覆蓋範圍，可以根據訓練需求主動擴展軟體池。這種「按需生成」的能力對於推動 CUA 從特定應用專家邁向通用電腦使用代理至關重要，因為它讓訓練資料的規模與多樣性得以獨立於真實軟體生態系的發展。

**Q12：SoftwareGym 對 GUI 軟體合成領域的影響？**

A：在 GUI 軟體合成領域，SoftwareGym 將過去以瀏覽器／網頁為主的方法擴展到獨立的桌面應用程式，填補了「可擴展性」與「原生應用深度」之間的空白。它證明了透過多代理管線結合設計、實作與評估三個階段，能產出具有真實多步驟工作流程的可執行應用，這對整個軟體工程自動化領域都是重要的進展。未來，這種方法論也可能被借鏡到其他類型的軟體合成任務中，例如行動應用程式或嵌入式系統介面。

**Q13：SoftwareGym 的局限性是什麼？**

A：儘管 SoftwareGym 展現了強大的合成能力，但其生成的應用本質上仍是「為訓練而設計」的軟體，與真實世界中經過長期使用者回饋迭代的成熟應用相比，可能在功能完整性、邊緣案例處理與真實工作流程的細節上有所不足。此外，雖然管線涵蓋了十二個軟體類別，但相對於整個桌面軟體生態系，這仍然是相對有限的覆蓋。論文中也坦承，合成環境與真實環境之間存在分布差距，這是未來需要持續縮減的方向。

**Q14：可能存在哪些失敗案例或弱點？**

A：在實際應用中，SoftwareGym 可能會在以下場景中表現不佳：當任務需要極度複雜的多步驟工作流程時，合成環境可能無法完整模擬真實應用中的所有狀態轉換；當代理面對高度視覺化或非標準的 GUI 元件（如自訂繪圖工具、特殊手勢操作）時，合成介面可能缺乏足夠的訓練樣本。此外，對於需要整合外部服務（如雲端 API、第三方外掛）的任務，純本地的合成應用無法提供真實的互動經驗，這些都是目前方法的明顯弱點。

**Q15：未來研究方向有哪些？**

A：未來的研究可以朝多個方向延伸：首先，可以擴大軟體類別的覆蓋範圍，納入更多專業領域的應用（如 IDE、CAD、資料科學工具），進一步提升代理的通用性；其次，可以探索將合成環境與真實應用程式軌跡相結合的混合訓練策略，兼顧可擴展性與真實性。此外，研究如何讓合成環境動態適應代理的能力成長（curriculum learning），或是將 SoftwareGym 的方法論應用於行動應用程式與網頁應用，都是值得探索的方向。最終目標是讓合成環境成為 CUA 訓練的標準基礎設施，如同 ImageNet 之於電腦視覺領域。

## 實務應用指南

### 適用場景

1. **企業內部 GUI 自動化測試環境建置**：金融、保險、零售等產業需要為內部業務系統（如報表工具、訂單管理後台、客服工作台）訓練專屬的電腦使用代理。透過 SoftwareGym 風格的合成管線，可在不洩漏真實業務資料的前提下，產生結構相似但內容可控的桌面應用程式，用於訓練代理處理表單填寫、批次匯入、跨頁籤資料核對等高頻工作流程。

2. **跨平台辦公軟體代理預訓練**：針對 LibreOffice、OnlyOffice 等開源辦公套件，企業可參考 SoftwareGym 的「類別層級功能規格 + 變體特定介面設計」策略，合成多版本試算表、文件編輯器、簡報工具，作為代理在進入真實環境前的預訓練場域，降低直接於生產環境試錯的成本。

3. **無障礙輔助技術的代理開發**：為視障或行動不便使用者開發螢幕閱讀器輔助代理時，可利用合成環境產生大量具備可預測 GUI 結構的應用程式，訓練代理正確解讀焦點順序、ARIA 屬性與快捷鍵行為，避免在真實軟體上反覆測試造成使用者干擾。

4. **教育與訓練領域的 GUI 教學助理**：程式設計或資訊素養課程需要讓學生在受控環境中練習操作各類軟體（從影像編輯到資料庫管理）。合成環境可依教學目標動態調整介面複雜度，並內建可驗證的任務評分機制。

5. **紅隊演練與資安測試平台**：資安團隊需要大量結構相似但內容相異的應用程式來測試代理對釣魚介面、惡意對話框、權限提升嘗試的辨識能力。合成管線可在短時間內產出數百個變體，用於壓力測試與對抗樣本生成。

### 實作前置條件

**資料面**
- 至少一份「軟體類別種子清單」（例如：影像編輯、影片播放、表格處理、程式碼編輯、終端機、檔案管理、繪圖、簡報、音訊、3D 模型、PDF 閱讀、瀏覽器），每類需附 3–5 個代表性功能描述作為起點規格。
- 對應類別的 GUI 設計參考資料（截圖、線框圖、Figma 檔案或公開的開源應用程式介面截圖），用於引導「變體特定介面設計」階段的多樣性。
- 任務範本庫：每個軟體類別至少準備 10 個可驗證的 GUI 任務範本（含起始狀態、操作序列、驗證條件），作為 SoftwareGym-Bench 風格評估套件的基礎。

**運算面**
- 多代理 LLM 推論環境：設計階段需要至少 2 個角色（規格撰寫代理、介面設計代理），實作階段需要程式碼生成代理，評估階段需要 GUI 測試代理與修復代理。建議使用 GPT-4 等級以上的模型，整體單次完整合成流程（含迭代修復）平均耗時與成本需預先估算。
- 桌面虛擬化或容器化執行環境：每個合成應用程式需在隔離的桌面環境（建議使用 QEMU/KVM、VMware 或 Docker-based X11 轉發）中執行 GUI 測試，單機建議至少 8 vCPU、32 GB RAM，並配置 GPU 加速 LLM 推論。
- 螢幕錄製與動作回放基礎設施：用於收集代理軌跡，需支援座標、點擊、輸入、捲動等事件的精確記錄與重播。

**技能面**
- 熟悉 GUI 自動化測試框架（PyAutoGUI、Playwright for desktop、xdotool）以建置檢查點式評估。
- 具備前端或桌面應用程式開發經驗（Electron、Tauri、Qt、PyQt、HTML/CSS/JS），以便審視合成程式碼的可行性與安全性。
- 對 LLM 代理編排框架（LangGraph、AutoGen、CrewAI）有實務經驗，能設計多代理協作流程與失敗回退機制。

### 實作步驟建議

**階段一：類別規格與設計多樣性建置（對應 §3.1）**
1. 盤點目標軟體類別，為每類撰寫「最小人類輸入」：3–5 句功能描述、2–3 個核心使用者情境、1 個代表性工作流程。
2. 設計「類別層級功能規格」模板，強制每個變體必須實作核心功能，但允許在次要功能、快捷鍵、選單結構上產生差異，避免收斂至相同佈局。
3. 為每個類別定義 3–5 種「介面風格變體」（例如：極簡風、傳統工具列風、ribbon 風、暗色主題、觸控友善風），並在提示詞中明確要求 LLM 不得跨變體複製佈局。
4. 將規格與設計封裝為「Verified Design Package」，內含功能清單、UI 藍圖、互動方案、可驗證的 GUI 任務清單。

**階段二：實作與原始碼層級驗證（對應 §3.2 前段）**
5. 將每個 Design Package 餵入程式碼生成代理，產出可執行的桌面應用程式（建議優先採用 Electron 或 Tauri 以加速開發，並支援跨平台）。
6. 執行「原始碼層級驗證」：靜態分析、依賴解析、單元測試自動生成與執行，過濾語法錯誤、缺失套件、無法編譯的程式碼。
7. 將通過驗證的應用程式部署至隔離桌面環境，記錄其初始 GUI 狀態截圖與可互動元素清單。

**階段三：GUI 檢查點評估與迭代修復（對應 §3.2 後段）**
8. 為每個應用程式定義 5–10 個「檢查點任務」，每個任務包含起始狀態、目標狀態、操作序列上限、驗證腳本（斷言特定 UI 元素出現/消失、檔案內容變更、狀態欄數值等）。
9. 驅動 GUI 測試代理執行任務，記錄每個檢查點的成功/失敗狀態與失敗截圖。
10. 將失敗案例連同截圖與錯誤訊息回傳給修復代理，要求其修改程式碼並重新驗證；設定最多 3–5 輪迭代上限，避免無限修復。
11. 僅保留通過所有檢查點的應用程式進入軟體函式庫；記錄其通過率作為品質指標（目標 ≥ 90%，對齊論文的 91.5%）。

**階段四：任務合成與軌跡收集（對應 §3.3）**
12. 為通過驗證的應用程式自動合成 GUI 任務：隨機化起始狀態、組合操作序列、設定驗證條件，產生類似 SoftwareGym-Bench 的評估套件。
13. 部署專屬 CUA 模型（可從開源基座如 UI-TARS、Qwen2-VL 等開始）在合成環境中執行任務，收集成功與失敗軌跡。
14. 對失敗軌跡進行錯誤分析（動作錯誤、規劃錯誤、感知錯誤），並將修正後的成功軌跡納入訓練資料。

**階段五：訓練與域外評估**
15. 以收集到的軌跡微調 CUA 模型，採用行為克隆 + 拒絕採樣（rejection sampling）策略，僅使用成功軌跡作為監督訊號。
16. 在嚴格域外基準（如 OSWorld）上評估 Pass@1、Pass@3，確認泛化能力（論文達到 Pass@3 56.97%，相對未訓練模型提升 15.58 個百分點）。
17. 同時在自有 SoftwareGym-Bench 風格套件上評估，監控是否出現「應用程式特定過擬合」（即在自有環境表現優異但 OSWorld 下降的現象）。

### 潛在風險與注意事項

**風險一：合成應用程式品質不穩定**
- **現象**：LLM 生成的程式碼可能在某些邊界條件下崩潰，或 GUI 元素命名不一致導致自動化測試失敗。
- **緩解**：設定嚴格的多輪迭代修復上限（建議 3–5 輪），並對連續 2 輪修復失敗的應用程式直接捨棄，避免在低品質樣本上浪費運算資源；同時建立「失敗模式分類表」，將崩潰、UI 不一致、邏輯錯誤分開追蹤。

**風險二：介面多樣性表面化**
- **現象**：LLM 容易在「顏色、字型、圖示」上做表面變化，但在「資訊架構、互動流程、狀態轉移」上仍高度相似，導致訓練出的代理僅學到視覺變化而非真正的泛化能力。
- **緩解**：在提示詞中明確禁止「僅改變外觀」，並要求每個變體必須重新設計至少一個核心工作流程（例如：表格編輯器中，變體 A 用右鍵選單、變體 B 用工具列、變體 C 用拖放操作完成同一任務）。

**風險三：訓練資料偏誤與獎勵 hacking**
- **現象**：代理可能學會「猜測驗證腳本的特徵」（例如：總是點擊右下角的確定按鈕）而非真正理解任務。
- **緩解**：驗證腳本應檢查「狀態結果」而非「操作序列」（例如：確認檔案已儲存，而非確認點擊了儲存按鈕）；同時在域外基準上持續監控，避免過度擬合自有環境。

**風險四：合成成本失控**
- **現象**：迭代修復可能消耗大量 LLM API 額度與桌面環境運算時間，單一應用程式成本可能超出預期。
- **緩解**：建立成本儀表板，記錄每個應用程式的 LLM token 用量、迭代次數、桌面環境占用時數；對成本超標的類別暫停合成並重新審視提示詞設計。

**風險五：安全性與程式碼供應鏈風險**
- **現象**：LLM 生成的程式碼可能引入惡意依賴、硬編碼密鑰或已知漏洞。
- **緩解**：對所有合成程式碼執行 SCA（軟體組成分析）掃描、依賴白名單檢查、敏感字串過濾；僅在隔離環境中執行，且不允許合成應用程式存取真實網路或檔案系統。

**風險六：與真實軟體的分布漂移**
- **現象**：合成環境的 GUI 模式、錯誤訊息、效能特性可能與真實軟體差異過大，導致代理在真實環境表現不佳。
- **緩解**：定期以小規模真實軟體軌跡進行「分布對齊檢查」，若代理在真實環境表現顯著低於合成環境，需調整合成管線以納入更多真實軟體的設計特徵。

### 與其他技術的整合建議

**與 OSWorld、Windows Agent Arena、AndroidWorld 等既有基準整合**
- 將 SoftwareGym 風格的合成環境作為「預訓練場域」，在進入真實基準微調前先讓代理熟悉多樣化 GUI 模式；訓練流程採「合成環境預訓練 → 真實基準軌跡微調」的兩階段策略。
- 在評估時同時報告合成環境與真實基準的分數，計算「泛化落差」指標，作為模型選擇的參考。

**與開源 CUA 基座模型整合**
- 可將合成軌跡用於微調 UI-TARS、Qwen2-VL-Computer-Use、ShowUI 等開源模型；建議採用 LoRA 或 QLoRA 以降低運算成本，並保留基座模型的視覺編碼器不動，僅微調動作解碼器。
- 與 Hugging Face 的 AgentBench、VisualAgentBench 等框架整合時，可將合成環境包裝為標準化的 Gym 環境介面。

**與企業 RPA 平台整合**
- 將合成環境產生的「成功軌跡」轉換為 UiPath、Power Automate 等 RPA 平台可匯入的工作流程定義，作為業務流程自動化的起點。
- 透過合成環境快速產生大量 RPA 候選流程，再由人類專家審核後部署至生產環境，縮短從概念到可運行自動化的時間。

**與測試自動化平台整合**
- 將合成應用程式與 Selenium、Playwright、Cypress 等測試框架整合，使每個合成應用程式同時也是一個可迴歸測試的目標。
- 在 CI/CD 流程中，每次 LLM 模型更新後自動執行合成環境測試套件，快速偵測迴歸問題。

**與資料合成與標註平台整合**
- 與 Label Studio、Argilla 等標註工具整合，讓人類標註員審核合成軌跡的品質，並提供修正後的軌跡作為額外訓練資料。
- 將合成管線與主動學習結合：優先針對「代理信心度低」的任務合成更多變體，提升訓練效率。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，理解「為什麼需要合成軟體環境」以及「合成環境長什麼樣子」；接著跳過方法論細節，直接看貢獻列表與實驗結果（OSWorld Pass@3 從 41.39% 提升到 56.97%），建立對整體價值的直覺。若對 GUI 自動化或電腦使用代理完全陌生，可先閱讀 OSWorld 原始論文以建立背景知識，再回頭看 SoftwareGym 如何解決其資料擴展瓶頸。

**給 AI 工程師**：重點閱讀 §3 方法章節，特別是「Software Design」與「Software Implementation and Evaluation」兩個子章節，理解多代理管線如何分工、迭代修復的迴圈如何設計、以及檢查點式 GUI 評估如何兼顧可靠性與可擴展性。實作時可直接參考論文的管線架構圖（圖 2、圖 3），將其映射到 LangGraph 或 AutoGen 的工作流定義；評估階段的「原始碼層級 + GUI 雙重驗證」策略值得直接採用。

**給研究者**：除方法章節外，建議深入分析實驗與消融研究，特別是「為什麼合成環境的訓練能泛化到 OSWorld」這個核心問題。可從「介面多樣性」、「互動深度」、「任務分布」三個維度設計後續實驗，探討合成環境與真實環境之間的「分布橋樑」；此外，論文中 182 個應用程式、12 個類別的規模仍屬中等，如何進一步擴展至數千個類別、並控制合成成本，是值得延伸的研究方向。

**給產品經理**：聚焦於「這個技術解決了什麼業務問題」與「投入產出比」。論文的關鍵訊息是：相較於手動開發軟體環境，自動化合成管線能以更低時間與金錢成本產生大量訓練環境，並使代理在域外基準上提升 15.58 個百分點。在評估導入價值時，應關注三個指標：合成環境的 GUI 任務通過率（論文達 91.5%）、域外泛化能力（OSWorld Pass@3）、以及單一應用程式的合成成本。建議先以單一類別（例如：表格處理）進行概念驗證，再逐步擴展至企業所需的全部軟體類別。
