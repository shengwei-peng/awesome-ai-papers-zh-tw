## ⚡ TL;DR

現有子詞分詞器將拼寫變異視為無關詞元，造成嵌入空間碎片化，或有損正規化會永久丟失資訊。
Functionalizer以PUA操作碼前綴，把正字法變異無損分解為標準基底詞元與參數化運算子。
詞彙槽位需求最高降19.7%，GPT-2模型提升Python語法有效性並減少重複n-gram。

## 摘要翻譯

標準的子詞分詞器（Subword Tokenizer）若非將單一詞語的每種正字法變異（Orthographic Variation，例如 hello、Hello、HELLO 與 Héllo）視為互不相關的詞彙表（Vocabulary）項目，導致嵌入空間（Embedding Space）碎片化，便是透過有損正規化（Lossy Normalization）捨棄這些變異。我們提出 Functionalizer，一個無損的預分詞器框架（Pre-tokenizer Framework），可在分詞前將正字法與結構變異分解為組合式操作碼／運算元（Opcode/Operand）前綴串流（Prefix Stream）：由標準基底詞元（Canonical Base Token，運算元）前綴以編碼於 Unicode 私人使用區（Unicode Private Use Area）的參數化轉換運算子（Parametric Transformation Operator，操作碼）所構成。我們引入的運算子涵蓋大小寫變化（Casing，如 CAPITALIZE（大寫化運算子））、變音符號（Diacritics，附加符號，共 13 個專用操作碼）以及字元重複（Character Repetition，如 REPEAT（重複運算子）、MULTIREPEAT（多重重複運算子）），且皆完全可逆（Fully Reversible）。橫跨自然語言語料庫（Natural Language Corpus）與程式碼語料庫（Code Corpus），Functionalizer 在無約束窮盡條件（Unconstrained Exhaustion Conditions）下，能以顯著更小的詞彙表達成完整的語料庫覆蓋率（Corpus Coverage），實際詞彙槽位需求（Vocabulary Slot Requirement）最高可減少 19.7%。在 9800萬參數 GPT-2 模型（98M-parameter GPT-2 Model）上的下游評估（Downstream Evaluation）顯示，Functionalizer 使 Python 程式碼語法有效性（Python Code Syntax Validity）從 7.70% 提升至 9.12%，同時減少了自然語言散文（Prose）中的重複 n-gram（Duplicate n-gram Repetition）。這些結果顯示，功能分解可作為一種實現詞彙效率高且具結構感知能力之語言建模（Structurally Aware Language Modeling）的有效機制，並為在生產規模上進行進一步驗證提供動機。

### 核心貢獻（3～5點）
- 提出 Functionalizer，一個無損預分詞器框架，可在子詞分詞前將正字法與結構變異分解為組合式操作碼／運算元前綴串流，避免嵌入空間碎片化或有損正規化。
- 設計並實作涵蓋大小寫變化、變音符號與字元重複的參數化轉換運算子，且所有轉換皆完全可逆。
- 在無約束窮盡條件下，Functionalizer 能以更小的詞彙表達成完整語料庫覆蓋率，實際詞彙槽位需求最高可減少 19.7%。
- 下游評估顯示，Functionalizer 可提升 9800萬參數 GPT-2 模型的 Python 程式碼語法有效性，並減少自然語言散文中的重複 n-gram。
- 證明功能分解是一種實現詞彙效率高且具結構感知能力之語言建模的有效機制。

### 適合對象
本論文適合從事大型語言模型分詞器設計、詞彙表效率最佳化、程式碼生成與自然語言處理研究的學者與工程師，特別是關注無損正規化、嵌入空間結構化，以及希望在生產規模語言模型中降低詞彙表成本並提升下游任務表現的讀者。

## 深度分析

#### 方法論解析

**Functionalizer（無損功能分解器）** 的核心思想是將傳統子詞分詞器（Subword Tokenizer）在面對正字法變異（Orthographic Variation）時的兩難——要麼把每種表面形式（Surface Form）視為獨立詞元（Token）導致詞彙擴張（Vocabulary Expansion），要麼透過有損正規化（Lossy Normalization）永久丟失資訊——轉化為一個「無損功能分解（Lossless Functional Decomposition）」問題。作者借鑑指令集架構（Instruction Set Architecture, ISA）中操作碼（Opcode）與運算元（Operand）分離的設計，將每個詞分解為：

1. **標準基底詞元（Canonical Base Token）**：即經過小寫化（Lowercasing）與去除結合變音符號（Combining Diacritics）後的語義根。
2. **參數化轉換運算子（Parametric Transformation Operator）**：以 PUA（Unicode Private Use Area，Unicode 私人使用區）碼點編碼，負責記錄大小寫變化（Casing）、變音符號（Diacritics）與字元重複（Character Repetition）等資訊。

這種設計使得下游模型只需要學習一組共享的標準基底嵌入（Canonical Base Embedding），而所有格式變異（Formatting Variation）則由可重複使用運算子（Reusable Operator）來表達，從而壓縮嵌入空間（Embedding Space）並保留完整可逆性（Fully Reversible）。

##### PUA 指令佈局

Functionalizer 的編碼（Encoding）採用前綴串流（Prefix Stream）形式：

```
[operator] [param 1] [param 2] ... → [base token]
```

具體碼點配置如下：

- **數值參數（U+E000–U+E0FF）**：可編碼 0–255 的整數，計算方式為 `value = codepoint - 0xE000`。
- **運算子（U+E100–U+EFFF）**：每個 Opcode 消耗固定數量的參數，剩餘空間保留給未來擴充。

作者特別討論了前綴（Prefix）與後綴（Suffix）兩種排序的取捨。雖然後綴排序 `[base] → [opcode]` 在自迴歸生成（Autoregressive Generation）中可能讓語義意圖先出現，但前綴排序的優勢在於：當一個詞被 BPE（Byte Pair Encoding）拆成多個子詞時（例如 `["neuro", "computation", "al"]`），運算子會出現在每個子詞之前，使格式轉換資訊在所有 Self-Attention 層中對每個組成部分都可見。

##### 編碼與解碼流程

整個轉換管線是完全雙射（Bijective）的：

- **編碼階段**：提取結合變音符號並轉為序列化運算子；定位大寫位置以供 CAPITALIZE（大寫化運算子）使用；去除結合符號並將剩餘字元小寫化；最後將運算子前綴附加到標準基底（Canonical Base）之前。
- **解碼階段**：依相反順序套用運算子，恢復變音符號與大小寫，再移除前綴，即可精確還原原始文字。

重複運算子（REPEAT / MULTIREPEAT）在解碼順序中最後執行，其位置參數指的是「重複擴展前」個別片段內的索引。對於異質大小寫重複（例如 `Abcabcabc`），系統會退回未折疊（Uncollapsed）表示，避免過度泛化。

##### 運算子規格

目前已實作的運算子涵蓋三大類：

1. **大小寫變化（Casing）**：`CAPITALIZE` 透過位置參數標記哪些字元需大寫。
2. **變音符號（Diacritics）**：提供 13 個專用 Opcode，例如 `ACUTE`、`GRAVE` 等，用於記錄結合變音符號的位置與類型。
3. **字元重複（Character Repetition）**：`REPEAT` 與 `MULTIREPEAT` 用於折疊重複字元或子字串，特別適合程式碼語料庫（Code Corpus）中常見的重複模式。

整體而言，Functionalizer 是一個**無詞典（Dictionary-free）**、**完全可逆**、**組合式（Compositional）** 的預分詞器（Pre-tokenizer）框架，能與標準 BPE（如 Hugging Face 的 BPE）無縫整合，無需修改分詞器核心演算法。

#### 實驗數據解讀

論文在兩個層面進行驗證：**語料庫層級的詞彙效率分析**與**下游任務的語言模型評估**。

##### 語料庫覆蓋率與詞彙槽位需求

在無約束窮盡條件（Unconstrained Exhaustion Conditions）下——即讓 BPE 合併窮盡（Merge Exhaustion）至無法再合併為止——Functionalizer 能夠以顯著更小的詞彙表達到完整語料庫覆蓋率（Corpus Coverage）。具體而言，實際詞彙槽位需求（Vocabulary Slot Requirement）最高可減少 **19.7%**。

這個數字的意義在於：傳統子詞分詞器必須為每種正字法變異保留獨立的嵌入槽位（Embedding Slot），例如 `hello`、`Hello`、`HELLO`、`Héllo` 各自佔用一個詞彙槽位（Vocabulary Slot）。Functionalizer 則將它們折疊為同一個標準基底 `hello`，再透過 `CAPITALIZE`、`ACUTE` 等運算子區分表面形式。當語料庫中存在大量大小寫、重音符號或重複結構時，這種折疊效應會被放大，因此詞彙壓縮效果在自然語言與程式碼語料庫中皆顯著。

值得注意的是，19.7% 是在「無約束窮盡」這種極端條件下測得的上限。在實際生產環境中，詞彙表大小通常受到固定預算限制（例如 32k、50k、100k），此時 Functionalizer 的效益可能表現為更低的未登錄詞率（Out-of-vocabulary, OOV Rate）或更好的罕見詞表現，而非直接等比例的詞彙縮減。

##### 下游語言模型評估

作者訓練了約 **9800 萬參數語言模型（98M-parameter Language Model）**，採用 GPT-2 架構，比較標準 BPE 與 Functionalizer 的差異：

- **Python 程式碼語法有效性（Python Code Syntax Validity）**：Functionalizer 從 7.70% 提升至 9.12%。
- **Python 的字元層級困惑度（Character-level Perplexity）**：相較於基線有所降低。
- **FineWeb-Edu 散文上的重複 n-gram（Duplicate n-gram Repetition）**：Functionalizer 能減少重複片段的生成。

**Python 語法有效性的提升** 可能來自兩個機制。首先，程式碼語料庫（Code Corpus）中充斥著縮排、重複字元（如 `====`、`*`、空白）與大小寫敏感的識別碼。Functionalizer 的 `REPEAT` / `MULTIREPEAT` 運算子能將這些結構性重複壓縮為規則，使模型更容易學習語法模式而非記憶具體表面形式。其次，大小寫與變音符號的解耦讓模型將更多容量用於學習語義與語法結構，而非分散在冗餘表面形式（Redundant Surface Form）上。

**重複 n-gram 的減少** 則暗示 Functionalizer 可能有助於緩解語言模型常見的「重複生成（Repetition）」問題。當大小寫與格式變異被折疊後，模型對於「同一概念的多種拼寫」不再傾向於機械式地複製先前出現過的表面形式，從而提升自然語言散文（Prose）的多樣性。

然而，這些實驗規模仍屬於中小型模型（98M 參數），且評估指標相對有限（語法有效性、困惑度、重複 n-gram）。要確認這些效益能否穩定遷移到更大規模的語言模型與更廣泛的下游任務，仍需更多驗證。

#### 與現有研究的比較

Functionalizer 的定位介於傳統子詞分詞、行內正字法預處理（Inline Orthographic Preprocessing）、形態學感知分詞（Morphology-aware Tokenization）與無分詞模型（Tokenization-free Models）之間。

##### 相較於標準子詞分詞器

BPE、WordPiece、Unigram 與位元組級 BPE（Byte-level BPE）都將每種表面形式視為潛在的獨立詞元。Functionalizer 的優勢在於：

- **無損壓縮**：不同於強制小寫化（Aggressive Lowercasing）或去除重音符號（Accent-stripping）等有損正規化（Lossy Normalization），Functionalizer 保留所有資訊。
- **結構感知**：透過 `REPEAT` / `MULTIREPEAT` 捕捉字元重複，這是標準 BPE 難以顯式建模的。

##### 相較於行內正字法預處理

Bérard et al. (2019)、Etchegoyhen & Gete (2020) 的大小寫標記（Case Flag）、TokenMonster 的 Capcode Marker、InCa / InDia 的位置索引變音符號（Position-indexed Diacritics）都與 Functionalizer 有相似目標。然而 Functionalizer 的差異在於：

1. **統一框架**：將大小寫變化、變音符號與字元重複統一在單一 PUA Opcode/Operand ISA 下，而非使用多種獨立標記機制。
2. **無詞典**：不依賴形態學詞典（如 Bayram et al., 2025）或頻率表（如 Semenov & Popel, 2025），避免語言特定資源與維護成本。
3. **參數化位置資訊**：數值參數可明確指向片段內的字元位置，使運算子能精確作用於任意子詞片段。

##### 相較於 Factorizer

Samuel & Øvrelid (2023) 提出的 Factorizer 使用 VQ-VAE（向量量化變分自編碼器）將子詞分解為離散學習碼三元組（Discrete Learned Code Triplet）。這是一種**學習式、非雙射**的表示法，可能出現資訊損失或解碼不一致。Functionalizer 則採用**確定性、規則式、完全雙射**的 Opcode/Operand 設計，保證編碼與解碼一對一對應。

##### 相較於形態學感知方法

Morfessor 與 MorphBPE 聚焦於語言學形態結構，例如詞根與詞綴的切分。Functionalizer 並不取代這些方法，而是與之互補：形態學方法處理語義結構，Functionalizer 處理正字法表面變異。兩者理論上可以組合使用。

##### 相較於無分詞模型

ByT5、MrT5、MEGABYTE 等模型透過直接操作原始位元組（Raw Bytes）來達成正字法穩健性，但代價是顯著更長的序列長度。Functionalizer 在保留子詞粒度（Subword Granularity）的同時獲得類似的表面形式不變性，避免位元組級序列擴展（Byte-level Sequence Expansion）。

##### 相較於 SCRIPT-BPE 與 Unicode 正規化

SCRIPT-BPE 透過重新編碼 Unicode 文字類別來減輕跨語言偏見；Unicode 正規化文獻則警告不當去除變音符號會造成下游損失。Functionalizer 與這些研究方向一致：它將變音符號從基底字元提取出來以折疊冗餘詞彙形式，但同時以參數化 PUA 運算子（如 `ACUTE`、`GRAVE`）明確保留，確保非破壞性可逆。

##### 限制

儘管設計優雅，Functionalizer 仍存在一些潛在限制：

- **序列長度開銷**：每個運算子與參數都佔用額外詞元。Jain et al. (2023) 已指出未融合的獨立標記詞元會帶來序列長度開銷與解碼速度下降。Functionalizer 雖將 Opcode 與 Operand 緊密結合，但 PUA 碼點仍可能增加某些短詞的詞元數量。
- **前綴排序的生成影響**：前綴排序雖有利於 Self-Attention 可見性，但可能使自迴歸模型在生成時需要先決定格式的 Opcode，再生成語義基底，這對某些生成任務的流暢性影響尚待研究。
- **運算子覆蓋範圍**：目前僅涵蓋大小寫、13 種變音符號與字元重複。對於更複雜的正字法現象（如連字、全形半形、阿拉伯文或梵文字母變形），仍需擴充。
- **異質大小寫重複的退化**：如 `Abcabcabc` 會退回未折疊表示，這在某些程式碼命名慣例（如 camelCase 重複片段）中可能削弱壓縮效益。

#### 可重現性評估

根據目前提供的論文內容，**可重現性（Reproducibility）面臨一定挑戰**。

##### 已提供的細節

- **編碼規格明確**：PUA 碼點範圍（U+E000–U+E0FF 用於參數、U+E100–U+EFFF 用於運算子）、Opcode/Operand 結構、編碼與解碼流程均有清楚說明。
- **運算子類型清楚**：列出 CAPITALIZE、13 個變音符號 Opcode、REPEAT / MULTIREPEAT 等。
- **實驗設定部分揭露**：使用 ∼98M 參數的 GPT-2 模型、FineWeb-Edu 與 Python 語料庫、無約束窮盡條件。

##### 缺失的關鍵資訊

- **原始碼與實作**：論文未提及是否釋出原始碼、訓練腳本或 Functionalizer 的參考實作。沒有開源程式碼，其他研究者難以精確複製 PUA 編碼細節、BPE 前處理管線與訓練流程。
- **資料集與前處理**：雖然提到 FineWeb-Edu 與 Python 語料庫，但具體的資料切分、清洗步驟、詞表大小、訓練步數、學習率等超參數均未詳述。
- **模型權重**：未說明是否公開訓練好的 98M 參數模型權重，這限制了下游任務的直接比較與微調實驗。
- **評估腳本與指標定義**：Python 語法有效性（Python Code Syntax Validity）的判定方式、重複 n-gram 的計算方式、困惑度（Perplexity）的評估協議等細節不足。

##### 綜合評估

以目前資訊而言，Functionalizer 的**概念與高階規格足夠讓有經驗的研究者重新實作**，但要達到論文宣稱的 19.7% 詞彙槽位減少、9.12% 語法有效性等數字，仍需要更多實作細節與開源資源。建議作者釋出：

1. Functionalizer 的 Python 實作與 Hugging Face Tokenizers 整合範例。
2. 訓練語料的前處理與分詞腳本。
3. 98M 參數基線與 Functionalizer 模型的權重。
4. 評估指標的原始碼與測試集。

#### 未來研究方向

Functionalizer 為結構感知語言建模（Structurally Aware Language Modeling）開啟了多條值得探索的路徑：

##### 1. 大規模生產級驗證

論文已明確指出需要「在生產規模（Production Scale）進一步驗證」。未來應在數十億甚至數百億參數模型上測試 Functionalizer，觀察其對訓練穩定性、收斂速度與下游任務（如問答、摘要、程式碼生成）的影響。

##### 2. 前綴與後綴排序的系統性比較

目前作者選擇前綴排序是基於 Self-Attention 可見性的直覺，但未提供實證比較。未來可針對前綴 `[opcode] → [base]` 與後綴 `[base] → [opcode]` 兩種佈局，在生成品質、序列長度、訓練效率與注意力模式上進行消融實驗。

##### 3. 擴充運算子集合

目前運算子僅涵蓋大小寫、13 種變音符號與字元重複。可進一步加入：

- **連字與拆分形式**：如 `ﬁ` 與 `fi`。
- **全形／半形轉換**：對亞洲語言與程式碼混用場景尤為重要。
- **空白與縮排運算子**：針對 Python 等縮排敏感語言，設計專用的縮排 Opcode。
- **Unicode 正規化形式轉換**：如 NFC / NFD 的參數化表達。

##### 4. 與形態學與語法結構的結合

Functionalizer 處理的是正字法層級的變異，未來可與 Morfessor、MorphBPE 或句法資訊結合，形成「多層次功能分解」：先進行形態切分，再對每個形態素套用 Functionalizer 的 Opcode/Operand 編碼。

##### 5. 跨語言與多語言評估

目前實驗主要聚焦於自然語言散文（FineWeb-Edu）與 Python 程式碼。對於變音符號豐富的語言（如法文、越南文、阿拉伯文、希伯來文）以及表意文字（如中文、日文漢字），Functionalizer 的效益與限制仍需深入分析。

##### 6. 解碼效率與硬體加速

PUA 碼點雖然對標準 Tokenizer 透明，但可能增加序列長度與解碼延遲。未來可研究：

- 將多個 Opcode/Operand 融合為單一特殊詞元（類似 TokenMonster 的 Capcode Marker）以減少長度開銷。
- 在 GPU / TPU 核心中針對 PUA 運算子進行專用解碼加速。
- 開發與 Functionalizer 相容的快速推論框架。

##### 7. 與無分詞模型的混合架構

Functionalizer 與 ByT5、MrT5、MEGABYTE 等位元組級方法並非互斥。未來可探索「Functionalizer + 位元組級骨幹」的混合模型：在低位元組層級使用 Functionalizer 進行結構壓縮，同時保留位元組模型的正字法穩健性。

##### 8. 可解釋性與注意力分析

由於 Opcode/Operand 結構明確，未來可利用注意力可視化技術分析模型如何學習與使用各種運算子，例如 CAPITALIZE 是否被模型視為與命名實體識別相關的特徵，或 REPEAT 是否與程式碼區塊結構對齊。

##### 9. 資料增強與對抗穩健性

Jain et al. (2023) 指出行內大小寫標記需要針對性資料增強才能提升大寫穩健性。Functionalizer 的確定性規則可能降低對資料增強的依賴，但仍需系統性評估其在對抗樣本、大小寫擾動與變音符號擾動下的表現。

##### 10. 詞彙表預算受限情境下的最佳化

目前 19.7% 的詞彙槽位減少是在無約束窮盡條件下測得。未來應研究在固定詞彙表大小（如 16k、32k、64k）下，Functionalizer 如何與 BPE 合併順序互動，以及如何設計最佳詞彙表配置以最大化下游效能。

## 論文問答

**Q1：標準子詞分詞器在處理正字法變異時面臨什麼樣的兩難困境？**
A：標準子詞分詞器在處理如 hello、Hello、HELLO 和 Héllo 等正字法變異時，面臨著詞彙擴張與資訊遺失之間的兩難困境。一方面，若將每種拼寫變體都視為獨立的詞彙項目，會導致冗餘表面形式大量消耗嵌入槽位，並使相關語義詞元之間的梯度更新無法有效共享。另一方面，若採用強制小寫化或去除重音符號等有損正規化手段，雖然能壓縮詞彙表，卻會永久丟失原始正字資訊，使下游模型永遠無法復原這些重要的表面形式特徵。

**Q2：為什麼現有的兩種主流方法（獨立詞元化與有損正規化）都無法妥善解決正字法變異問題？**
A：將每種正字法變異都編碼為獨立詞元的方法會造成嵌入空間碎片化，因為語義相同但大小寫或附加符號不同的詞會被分散到不同的向量位置，阻礙了模型對共同語義的學習與泛化。相對地，有損正規化雖然能減少詞彙槽位需求，但它會破壞原始文字的可逆性，例如將「Héllo」轉為「hello」後，模型再也無法判斷原始詞是否包含尖音符或首字母大寫。這兩種方法都未能同時兼顧詞彙效率與資訊完整性，因此需要一種能夠無損分解正字法變異的新機制。

**Q3：無損保留正字法變異對於語言建模為何重要？**
A：正字法變異往往承載重要的語義、語用與結構資訊，例如專有名詞的首字母大寫、法語或西班牙語中的變音符號，以及程式碼中的大小寫區分，這些特徵對於正確理解與生成文字至關重要。有損正規化會永久移除這些訊號，導致模型在處理需要精確正字資訊的任務時表現不佳，例如程式碼語法有效性或專有名詞辨識。Functionalizer 透過無損功能分解保留所有表面形式細節，使模型既能享受詞彙壓縮的好處，又不會喪失復原原始文本的能力。

**Q4：Functionalizer 框架的核心方法是什麼？**
A：Functionalizer 是一種無損的預分詞器框架，它將正字法與結構變異分解為組合式的操作碼／運算元前綴串流，再進行標準子詞分詞。具體而言，系統會先將文本轉換為標準基底詞元作為運算元，並在前面加上一個或多個參數化轉換運算子作為操作碼，這些操作碼編碼於 Unicode 私人使用區中。這種設計借鏡自指令集架構中中央處理器將運算與資料分離的概念，讓下游模型可以共享標準基底的嵌入表示，同時透過操作碼保留完整的可逆轉換資訊。

**Q5：與先前的行內標記方法相比，Functionalizer 的關鍵創新有哪些？**
A：Functionalizer 的關鍵創新在於它建立了一個統一、確定性、無詞典且完全雙射的操作碼／運算元指令集架構，能夠同時處理大小寫變化、變音符號與字元重複等問題。不同於 Factorizer 使用學習得到的離散碼三元組而無法保證可逆性，Functionalizer 採用基於規則的轉換，確保編碼與解碼之間完全雙射。此外，它不需要外部形態學詞典或頻率表，並透過 Unicode 私人使用區的數值參數精確定位字元位置，使其能夠統一處理多種正字法與結構變異。

**Q6：Functionalizer 為何選擇將操作碼置於基底詞元之前，而非置於其後？**
A：Functionalizer 選擇前綴排序的主要原因是，當一個詞被分割為多個 BPE 子詞時，前置的操作碼能夠讓格式轉換運算子對所有組成子詞都保持可見。這意味著在自注意力機制中，每個子詞都能夠察覺到整個詞的整體正字法狀態，有助於模型學習跨子詞的結構一致性。雖然後綴排序可能讓語義意圖在自迴歸生成中更早出現，但前綴排序在處理多詞元詞彙時提供了結構上的優勢，特別是對於程式碼等需要精確大小寫與重複模式的領域。

**Q7：本研究使用了哪些語料庫與評估指標來驗證 Functionalizer？**
A：本研究橫跨自然語言與程式碼語料庫進行驗證，包括用於自然語言散文評估的 FineWeb-Edu，以及用於程式碼評估的 Python 語料庫。在詞彙效率方面，研究者在無約束窮盡條件下測量達成完整語料庫覆蓋率所需的詞彙槽位數量。在下游評估方面，則訓練約 9800 萬參數的 GPT-2 模型，並評估字元層級困惑度、Python 程式碼語法有效性，以及自然語言生成中重複 n-gram 的比例。

**Q8：Functionalizer 在詞彙效率與下游任務上取得了哪些關鍵成果？**
A：在無約束合併窮盡條件下，Functionalizer 能夠以顯著更小的詞彙表達成完整語料庫覆蓋，實際詞彙槽位需求最高可減少 19.7%。在下游任務中，使用 Functionalizer 訓練的 9800 萬參數 GPT-2 模型在 Python 程式碼語法有效性上從 7.70% 提升至 9.12%，顯示其對程式碼結構的理解有所改善。同時，在自然語言散文生成中，Functionalizer 也減少了重複 n-gram 的出現，表明其有助於緩解生成文本中的冗餘重複現象。

**Q9：不同運算子對整體效果的貢獻是否經過分析或消融實驗？**
A：論文提及了多種專用運算子的設計，包括 CAPITALIZE、13 個專門處理變音符號的操作碼，以及 REPEAT 和 MULTIREPEAT 等字元重複運算子，這些運算子各自針對不同類型的正字法與結構變異。雖然摘要與主要內容強調了整體框架的效益，但具體的消融實驗細節可能需要參考論文附錄中的表格與補充分析。整體而言，這些運算子的組合設計使得系統能夠無損地處理大小寫變化、變音符號與字元重複三大類變異，並在詞彙效率與下游性能上產生協同效應。

**Q10：Functionalizer 在哪些實際應用場景中最能發揮價值？**
A：Functionalizer 特別適合需要精確正字法資訊的多語言場景，例如法語、西班牙語、德語等大量使用變音符號的語言，因為它能無損保留這些語言的拼寫細節。在程式碼領域，由於 Python 等語言對大小寫敏感且常出現重複模式，Functionalizer 能夠改善語法有效性並降低字元層級困惑度。此外，對於詞彙表受限的邊緣裝置或需要高度壓縮的應用，Functionalizer 透過減少詞彙槽位需求，能夠在保持完整資訊的同時提升部署效率。

**Q11：在實際產品部署 Functionalizer 時需要考慮哪些因素？**
A：首先，由於 Functionalizer 使用 Unicode 私人使用區來編碼操作碼，產品團隊需要確保整個處理管線（包括分詞器、模型與解碼器）都能正確處理這些非標準碼位，避免在資料交換或儲存時發生損毀。其次，前綴操作碼會增加序列長度，因此需要評估其對推理速度與記憶體佔用的影響，特別是在高吞吐量的生產環境中。最後，由於此方法改變了傳統子詞分詞器的詞彙結構，現有的預訓練模型與資料增強策略可能需要相應調整，以確保與 Functionalizer 訓練出的模型相容。

**Q12：Functionalizer 可能對語言建模與分詞研究領域帶來什麼影響？**
A：Functionalizer 展示了功能分解可以作為一種詞彙高效且結構感知的語言建模機制，這可能啟發未來研究將更多類型的語言學與結構資訊編碼為可逆操作碼。它挑戰了傳統上在詞彙擴張與有損正規化之間二選一的思維，提供了一條兼顧效率與資訊完整性的第三條路徑。此外，由於該方法可與形態學感知分詞或位元組級模型互補，未來可能出現結合多種分解策略的混合式分詞架構，進一步提升多語言與程式碼模型的表現。

**Q13：Functionalizer 目前有哪些已承認的限制？**
A：論文指出部分研究仍需要在生產規模上進一步驗證，目前實驗主要集中於 9800 萬參數的 GPT-2 模型與特定語料庫，尚未涵蓋更大規模的工業級模型。此外，對於異質大小寫重複（例如 Abcabcabc）等複雜表面形式，系統會退回到未折疊的原始表示，無法完全發揮分解效益。這些限制意味著 Functionalizer 在面對極端多樣或高度不規則的文本模式時，可能仍有最佳化空間。

**Q14：在哪些情況下 Functionalizer 可能表現不佳或失效？**
A：當文本包含異質大小寫的重複模式，例如「Abcabcabc」這類每個重複單元內部大小寫不一致的情況，Functionalizer 會退回到未折疊表示，無法減少詞彙槽位需求。此外，若處理管線中的任何元件不支援 Unicode 私人使用區碼位，可能導致操作碼遺失或解碼錯誤，進而破壞無損復原的保證。對於極度罕見或不符合常規正字法規則的表層形式，現有運算子集也可能無法找到合適的分解方式，需要進一步擴充操作碼集合。

**Q15：Functionalizer 未來有哪些有前景的研究方向？**
A：未來研究可以擴充操作碼集合，納入更多語言學現象（如形態變化、詞幹變化）或程式碼專屬結構（如縮排、括號配對），進一步提升分解能力。另一個方向是將 Functionalizer 與現有的大規模生產模型整合，驗證其在數十億參數模型與多語言預訓練中的可擴展性與穩定性。此外，探索前綴與後綴排序在不同生成任務中的權衡、開發針對操作碼序列的專用注意力機制，以及結合無詞典規則與少量學習來自動發現新的運算子，都是值得深入研究的課題。

## 實務應用指南

### 適用場景

1. **多語言基座模型預訓練**  
   當語料同時包含 `café`、`Café`、`CAFÉ` 等變體時，Functionalizer 可將它們折疊為標準基底詞元 `cafe` 加上 `ACUTE`、`CAPITALIZE` 等操作碼，避免詞彙表被大小寫與變音符號的組合爆炸撐大，特別適合法語、西班牙語、越南語等重度使用附加符號的語料。

2. **程式碼生成模型（Python、JavaScript、SQL 等）**  
   程式碼中常出現 `HELLO`、`hello`、`Hello` 以及重複字元（如 `aaaa`）或縮排空白。Functionalizer 的 `CAPITALIZE`、`REPEAT`、`MULTIREPEAT` 運算子能將這些格式變異無損分解，讓 9800 萬參數級模型在 Python 語法有效性與字元層級困惑度上獲得改善。

3. **低資源或邊緣裝置上的小型模型**  
   在詞彙槽位受限（例如 8K–32K）的情境下，Functionalizer 可在無約束窮盡條件下減少最多約 19.7% 的詞彙槽位需求，讓輕量模型用更小的嵌入表達完整語料庫覆蓋率。

4. **OCR 後處理與文字正規化管線**  
   對於掃描文件或語音轉錄後需要保留原始拼寫的場景，Functionalizer 提供完全可逆的替代方案：相較於強制小寫化或去除重音符號等「有損正規化」，下游仍可精準還原原始表面形式。

5. **檢索與語意搜尋的索引前處理**  
   在建立向量索引前，可先以 Functionalizer 將正字法變異折疊為標準基底，使 `resume` 與 `résumé` 共享語意嵌入，同時透過操作碼保留還原資訊，兼顧召回率與顯示準確度。

### 實作前置條件

**資料條件**
- 原始語料應盡量保留原始大小寫、變音符號與重複字元，避免預先進行有損正規化。
- 需要一份具代表性的語料子集（建議至少數百萬詞元）用於訓練 BPE 或 Unigram 分詞器。
- 若語料包含大量非基本拉丁文字，需先評估目前 13 個專用變音符號操作碼是否足夠覆蓋。

**運算資源**
- 訓練子詞分詞器本身只需一般 CPU 叢集即可，與標準 BPE 訓練成本相近。
- 若進行下游 9800 萬參數級語言模型微調或從頭預訓練，建議至少 4–8 張 A100 / H100 等級 GPU。
- 需要能處理 Unicode 私人使用區（PUA）字元的儲存與傳輸環境。

**技術能力**
- 熟悉 Hugging Face `tokenizers` 或 SentencePiece 的內部運作。
- 理解 Unicode 正規化（NFC/NFD）、結合附加符號（combining diacritics）與 PUA 碼點。
- 具備 Python 編碼／解碼管線開發經驗，能實作自訂的 `PreTokenizer` 與後處理解碼器。

### 實作步驟建議

1. **語料變異盤點**  
   抽樣分析語料中大小寫、變音符號、字元重複與空白重複的分佈，決定需要啟用哪些操作碼（`CAPITALIZE`、13 個變音符號、`REPEAT`、`MULTIREPEAT`）。

2. **實作編碼器與解碼器**  
   依據論文的 PUA 指令佈局（U+E000–U+E0FF 為參數、U+E100–U+EFFF 為運算子）撰寫雙射轉換函式。編碼時先分離結合附加符號、記錄大寫位置、小寫化後產生標準基底，再於前方加上操作碼前綴。

3. **訓練 Functionalizer 分詞器**  
   將編碼後的語料餵入標準 BPE（如 Hugging Face `tokenizers`），在無約束窮盡條件下觀察詞彙槽位需求，並與未編碼的基線比較詞彙表大小與語料庫覆蓋率。

4. **可逆性驗證**  
   在開發與測試集上執行「原始文字 → 編碼 → 分詞 → 解碼 → 還原文字」的迴路測試，確保所有樣本 100% 無損還原。特別注意異質大小寫重複（如 `Abcabcabc`）會退回未折疊表示。

5. **下游任務評估**  
   在相同參數規模（如 9800 萬參數 GPT-2）下，比較字元層級困惑度、Python 程式碼語法有效性、重複 n-gram 比例等指標，確認 Functionalizer 不會對特定任務造成負面影響。

6. **產品化封裝**  
   將編碼／解碼邏輯包裝為 `PreTokenizer` 與後處理器，整合至模型推論服務；並在資料管線中保留原始文本對照表，以便除錯與版本控制。

### 潛在風險與注意事項

- **PUA 碼點相容性**  
  部分舊版字型、瀏覽器或資料清洗工具會過濾私人使用區字元，導致操作碼遺失。建議在儲存與傳輸層使用 UTF-8 並加入完整性檢查，避免中間系統誤刪 PUA 前綴。

- **序列長度開銷**  
  每個操作碼與參數都會增加詞元數量。雖然詞彙表變小，但對於短句或大量變音符號的語言，序列長度可能略微增加，需在延遲敏感的應用中實測。

- **前綴排序對生成行為的影響**  
  論文採用 `[opcode] → [base]` 前綴排序，雖有利於多詞元詞的注意力對齊，但在自迴歸生成中，模型必須先預測格式操作碼再預測語意內容。若應用對生成順序敏感，可評估後綴排序 `[base] → [opcode]` 的變體。

- **異質重複與未涵蓋變音符號的 fallback**  
  `Abcabcabc` 等異質大小寫重複會退回未折疊表示；若語料包含 13 個專用操作碼未涵蓋的罕見變音符號，也會保留原始字元。這些 fallback 會佔用額外詞彙槽位，需在詞彙表預算中預留緩衝。

- **與 Unicode 正規化的互動**  
  若管線中同時使用 NFC/NFD，需確保 Functionalizer 在正規化之後執行，否則結合附加符號的位置可能改變，導致編碼不一致。

---

### 與其他技術的整合建議

- **Hugging Face `tokenizers`**  
  可將 Functionalizer 實作為自訂 `PreTokenizer`，在 `Tokenizer.train_from_iterator()` 前套用；解碼時則在 `decode()` 後加入後處理器還原操作碼。

- **SentencePiece / Unigram**  
  Functionalizer 是獨立於分詞演算法的預分詞器框架，可與 SentencePiece 的 `normalizer` 與 `pretokenizer` 介面結合，但需注意 SentencePiece 對 PUA 的預設處理可能需關閉 `remove_extra_whitespaces` 等選項。

- **與形態學感知分詞器（如 Morfessor、MorphBPE）搭配**  
  Functionalizer 處理正字法變異，Morfessor 處理形態學詞根，兩者可串接：先以 Functionalizer 折疊大小寫與變音符號，再進行形態學分割。

- **與檢索系統整合**  
  在建立向量索引前套用 Functionalizer 編碼，使語意嵌入對大小寫與變音符號更穩健；檢索結果顯示時再解碼還原原始表面形式。

- **監控與日誌**  
  在生產環境記錄操作碼分佈（如 `CAPITALIZE`、`ACUTE`、`REPEAT` 的使用頻率）與 fallback 比例，作為詞彙表迭代與操作碼擴充的依據。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「為什麼需要 Functionalizer」這個問題切入：傳統子詞分詞器會把 `Hello` 與 `hello` 當成兩個無關詞元，而強制小寫又會丟失資訊。Functionalizer 就像給每個詞加上「格式說明書」，讓模型知道它們其實是同一個基底的不同變化。閱讀時可專注於第 1 節與第 3 節的操作碼範例，暫時跳過 BPE 合併窮盡的數學細節。

**AI 工程師**  
請把重點放在第 3 節的 PUA 指令佈局、第 4 節的實作細節，以及下游評估指標。你需要判斷這套框架能否無縫接入現有的 Hugging Face 或 SentencePiece 管線，並評估 PUA 相容性、序列長度開銷與推論延遲。建議直接複現論文中的 Python 程式碼語法有效性與重複 n-gram 實驗，作為內部採用的決策依據。

**研究人員**  
論文的核心貢獻在於將指令集架構（ISA）的 opcode/operand 概念引入子詞分詞，並證明無損功能分解能同時縮小詞彙表並改善下游表現。建議深入檢視其雙射性證明、與 Factorizer / InCa / InDia 的理論差異，以及前綴排序對自迴歸模型注意力機制的影響。未來可探索擴充更多 Unicode 腳本、操作碼後綴排序，或與位元組級模型（如 ByT5）進行比較研究。

**產品經理**  
這篇論文提供了一個「在縮小詞彙表的同時不丟失資訊」的技術選項。評估時請關注兩個商業指標：詞彙槽位需求降低約 19.7% 所帶來的模型體積與訓練成本節省，以及 Python 語法有效性與自然語言重複 n-gram 減少所對應的產品體驗提升。同時需與工程團隊確認 PUA 碼點在現有資料管線、儲存系統與前端顯示上的相容風險。
