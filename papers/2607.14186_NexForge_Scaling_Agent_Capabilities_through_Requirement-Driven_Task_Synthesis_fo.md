## ⚡ TL;DR

## 摘要翻譯

大型語言模型（Large Language Model, LLM）後訓練（Post-training）所需的可執行智慧代理（Agent）訓練資料，其規模擴充目前受限於基質綁定方法（Substrate-bound methods）：這類方法將任務生成綁定至預設工具、倉庫或技能圖譜（Skill graphs）；擴展涵蓋範圍須手動進行基質（Substrate）工程；每個新領域皆需客製化流程（Bespoke pipeline）；而生成的任務分布（Task distribution）往往反映基質偏差（Substrate biases），而非真實世界需求（Real-world demand）。我們提出 NexForge，一個需求驅動式任務合成（Requirement-Driven Task Synthesis）框架，以高階能力需求（Capability requirements）作為輸入，合成多樣化的可執行代理任務（Executable agent tasks）與專家軌跡（Expert trajectories），供監督式微調（Supervised Fine-Tuning, SFT）使用。NexForge 首先探究真實世界需求，建構代表性情境（Representative scenarios）與任務輪廓（Task profiles），接著進行分布感知編譯（Distribution-aware compilation）以生成任務指令（Task directives）。針對每項任務指令，NexForge 自動檢索或建構所需檔案、相依性與執行階段配置（Runtime configurations），最後合成專家展開（Expert rollouts，即專家執行軌跡）並產出訓練軌跡（Training trajectories）。無需特定領域基礎設施（Domain-specific infrastructure），NexForge 即可生成 3.6K 個終端機任務（Terminal tasks）與 2K 個辦公室任務（Office tasks），使 Qwen3.5-35B-A3B 基礎模型在 Terminal-Bench 2.0 上的表現從 22.5% 提升至 52.0%，並在 GDPval 上的 Elo 評分（Elo）從 813 提升至 1338；進一步擴增至 43.2K 個終端機任務後，模型表現達到 58.4%，與配備 Claude Code 的 Claude Opus 4.6 相當。再擴大規模後，NexForge 合成之資料用於訓練 Nex-N2——一系列公開可用（Open-source）的代理模型，可將 Qwen3.5-35B-A3B 在 Terminal-Bench 2.1 上的表現提升至 75.3%，並將 GDPval 上的 Elo 評分提升至 1585——達到最尖端的（State-of-the-art）開源表現，並超越多個前沿專有系統（Frontier proprietary systems）。Nex-N2 模型可於 https://nex.sii.edu.cn/ 取得。

### 核心貢獻（3～5點）
- 提出 NexForge，一個需求驅動式任務合成框架，直接以高階能力需求為輸入，合成多樣化的可執行代理任務與專家軌跡，無需依賴特定領域基礎設施。
- 建立從真實世界需求分析、代表性情境與任務輪廓建構，到分布感知編譯、可執行環境與執行階段配置自動生成，再到專家展開與訓練軌跡產出的完整後訓練資料生成流程。
- 大規模合成終端機與辦公室任務，顯著提升 Qwen3.5-35B-A3B 在 Terminal-Bench 2.0 與 GDPval 上的表現；進一步擴增資料後，訓練出 Nex-N2 公開代理模型系列，在 Terminal-Bench 2.1 與 GDPval 上達成開源最尖端水準，並超越多個前沿專有系統。

### 適合對象
適合對大型語言模型後訓練、智慧代理能力擴展、合成資料生成與自動化任務建構有興趣的研究人員與工程師，特別是關注開源代理模型、終端機與辦公室自動化應用，以及希望降低領域專屬基礎設施依賴以規模化生成訓練資料的開發者。

## 深度分析

#### 方法論解析

NexForge（需求驅動式任務合成框架）將傳統的「基質綁定方法（Substrate-bound methods）」轉換為「需求驅動的任務合成（Requirement-Driven Task Synthesis）」。具體而言，它接受一個高階的 Capability requirements（能力需求） \(I\)、期望的任務數量 \(N\)，以及可選的批次級限制 \(B\)（例如語言、難度預算），最終輸出一組可執行的任務套件 \(T = \{\tau_1, \dots, \tau_N\}\)。每個 \(\tau_i\) 都是一個 Executable workspace（可執行工作空間），內含 Task descriptions（任務描述）、Grounded materials（基礎材料）、Workspace files（工作空間檔案）、Software dependencies（軟體依賴）與 Runtime configurations（執行階段配置）。值得注意的是，這些套件是為 Trajectory generation（軌跡生成）而設計，而非為 Benchmarking（基準測試）設計，因此不需要人工撰寫的參考答案或任務專屬驗證器。

在形式化上，每個任務被拆解為 Task form（任務形式） \(f_i\) 與 Scenario（情境） \(s_i\)，即 \(\tau_i \leftarrow (f_i, s_i)\)。其中 Task form 進一步細分為：Task type（任務類型） \(t_i\)、Expected deliverable（預期交付物） \(d_i\)、Source strategy（來源策略） \(\sigma_i\)、Runtime env（執行環境） \(e_i\)、Language（語言） \(\ell_i\) 與 Difficulty（難度） \(h_i\)。這種解耦（Decoupling）讓「代理應該練習什麼」與「如何讓練習可執行」分離，從而讓同一套流程能跨 Domain-specific infrastructure（特定領域基礎設施）運作。

整個框架分為三個階段：

1. **Demand discovery（需求發現）**：NexForge 先調查 Real-world demand（真實世界需求），建構 Representative scenarios（代表性情境）與 Task profiles（任務輪廓）。文中提到會產生 Demand profile \(\Phi(I)\) 與 Scenario reservoir \(G_I\)，並依據真實發生頻率進行加權取樣。這一步是對抗 Substrate biases（基質偏差）的核心：任務分布不再由預設倉庫或工具決定，而是由能力需求在真實世界中的出現頻率決定。

2. **Distribution-aware compilation（分布感知編譯）**：透過 Directive Composer（指令編排器）將取樣後的 Task form 與 Concrete scenarios（具體情境）進行組合，檢查兩者之間的相容性，輸出 Task directives（任務指令） \(\delta\)。這裡的「分布感知」意味著生成過程會主動控制 Task distribution（任務分布），確保訓練資料能反映需求側的結構，而非單純隨機組合。

3. **Trajectory generation（軌跡生成）**：對每個 Task directive，系統自動檢索或建構所需檔案、依賴與執行環境，接著合成 Expert rollouts（專家展開），最終產生 Training trajectories（訓練軌跡）。這些 Expert trajectories（專家軌跡）可直接用於 SFT（Supervised Fine-Tuning，監督式微調）。由於不需要人工標註答案，這大幅降低了 Long-horizon interaction trajectories（長期互動軌跡）的生產成本。

總結來說，NexForge 的方法論核心在於把 Environment synthesis（環境合成）從「圍繞基質打轉」轉為「圍繞能力需求打轉」。這不僅讓 Terminal tasks（終端機任務）、Office tasks（辦公室任務）、Science tasks（科學任務）等不同領域能共用同一條 Bespoke pipeline（客製化流程），也讓訓練資料的組成變得可解釋、可調控。

#### 實驗數據解讀

論文在兩個差異極大的能力領域上驗證 NexForge：Terminal operations（終端機操作）與 Office work（辦公室工作）。使用的基礎模型是 Qwen3.5-35B-A3B，這是一個 35B 總參數、3B 啟動參數的 MoE 模型。

在終端機領域，實驗結果如下：

- 僅使用 3.6K 個由 NexForge 合成的 Terminal tasks，模型在 Terminal-Bench 2.0 上的表現從 22.5% 提升至 52.0%，絕對進步達 29.5 個百分點。
- 將資料規模擴大到 43.2K 個 Terminal tasks 後，分數進一步提升至 58.4%，與 Claude Opus 4.6 搭配 Claude Code 的表現相當。
- 在後續更進一步的規模化訓練中，Nex-N2（以 NexForge 合成資料訓練的公開模型系列）在 Terminal-Bench 2.1 上達到 75.3%，並在 GDPval 上達到 1585 Elo（Elo 評分），成為 State-of-the-art（最尖端的）開源模型，並超越若干 Frontier proprietary systems（前沿專有系統）。

在辦公室工作領域：

- 使用 2K 個 Office tasks，模型在 GDPval 上的 Elo 從 813 提升至 1338，進步幅度達 525 分。

這些數據有幾層意義：

首先，**相對增益極大**。無論是終端機任務將近 30 個百分點的提升，還是辦公室任務超過 500 分的 Elo 成長，都顯示 NexForge 合成的資料確實命中了模型原本欠缺的真實能力分布，而非僅僅增加資料量。

其次，**規模效應存在但呈現邊際遞減**。從 3.6K 到 43.2K（約 12 倍）的終端機資料，分數從 52.0% 提升至 58.4%，僅增加 6.4 個百分點。這暗示在資料量持續放大時，單純增加任務數量的效益會趨緩，未來可能需要更精細的 Distribution-aware compilation 或難度調控來維持成長。

第三，**跨領域通用性得到驗證**。同一套框架在終端機與辦公室兩個截然不同的領域都能產生有效訓練資料，這強化了「需求驅動優於基質綁定」的論點。

最後，**與專有系統的可比性**。Claude Opus 4.6 搭配 Claude Code 是業界頂尖的程式輔助配置，NexForge 僅用合成資料就讓開源模型逼近甚至超越這一水準，顯示出資料合成在 Agent（智慧代理）後訓練中的戰略價值。

#### 與現有研究的比較

在相關研究中，現有方法大致可分為兩大類：

第一類是「指令與任務分布合成」，例如 Self-Instruct、GLAN、TRouter、Benchmark Agent。這些方法擅長透過 Taxonomy（分類體系）或 Task profiles（任務輪廓）來控制文字指令或評測基準的分布。然而，它們主要生成的是文字形式的指令或 Benchmark specifications（基準規格），並未處理 Executable environments（可執行環境）所需的 Grounded materials、Dependencies（依賴）與 Runtime configurations。NexForge 的貢獻在於把這套分布建模思想延伸到完整的可執行代理任務與專家軌跡。

第二類是「代理任務與環境合成」，例如 Agent-World、AgentWorldModel、DIVE、AgentSynth、TaskCraft、SkillSynth、Terminal-World、CLI-Universe、TerminalTraj、Nemotron-Terminal、LiteCoder-Terminal、OpenThoughts-Agent、SWE-smith、R2E-Gym 等。這些方法已經能產生可執行環境，但它們大多屬於 Substrate-bound methods：任務生成被綁定在預設的 Tools（工具）、Repositories（倉庫）、Skill graphs（技能圖譜）或 Execution traces（執行軌跡）上。這帶來三個瓶頸：

1. **Input-bounded scale（規模受輸入基質限制）**：任務數量與多樣性取決於既有基質的大小。
2. **High transfer cost（轉移成本高）**：每個新領域都需要重新打造 Bespoke pipeline。
3. **Substrate-biased distributions（基質偏差分布）**：生成的任務分布反映的是既有資料的結構，而非真實世界需求。

NexForge 透過 Requirement-driven formulation（需求驅動式形式化）同時解決這三個問題：它從 Capability requirements 出發，先決定 Task types 與其頻率，再動態建構所需環境，因此不需要預設倉庫或技能圖，也能跨領域擴展。

然而，NexForge 也有其潛在限制：

- **需求發現的品質決定上限**：若 \(\Phi(I)\) 與 \(G_I\) 未能準確捕捉真實需求，分布感知編譯只會把偏差系統化。
- **專家軌跡的品質與安全**：Expert rollouts 可能來自更強大的模型，其錯誤或偏見會被蒸餾到訓練資料中；同時，自動執行合成環境存在資安風險。
- **無參考答案的驗證挑戰**：雖然省去人工標註，但如何確保每個 Executable agent task 的軌跡確實正確完成，仍需要額外的驗證機制。
- **領域覆蓋仍待驗證**：文中雖提到 Science tasks，但實驗數據主要集中在 Terminal 與 Office，其他領域的有效性尚需更多證據。

#### 可重現性評估

從提供的文本來看，NexForge 的模型權重已公開：Nex-N2 系列可於 https://nex.sii.edu.cn/ 取得。這對於重現論文最終的效能數字（Terminal-Bench 2.1 的 75.3% 與 GDPval 的 1585 Elo）是重要的一步，因為研究者可以直接下載模型進行推論與評測。

然而，就完整的可重現性而言，目前資訊仍有不足：

- **程式碼與完整資料集**：文中並未明確說明 NexForge 的合成流程、Scenario reservoir、Task directives 與 Expert trajectories 是否會開源。若僅釋出模型權重，社群難以重現從 Capability requirements 到 Training trajectories 的完整過程，也難以在新的能力領域上套用同一框架。
- **執行環境的再現**：Executable workspace 涉及特定版本的作業系統、Shell、Python 套件、Office 軟體等 Dependencies。若沒有容器化（如 Docker）的 Runtime configurations 與依賴鎖定檔，實驗結果可能因環境差異而難以復現。
- **訓練細節**：包括 SFT 的學習率、Batch size、資料混合比例、訓練步數、是否結合其他資料等，都會影響最終模型表現。這些細節若未完整公開，將限制結果的可重現性。

因此，目前的可重現性處於「模型可取得、流程部分透明」的階段。若要達到完全可重現，建議作者釋出：(1) NexForge 的合成程式碼；(2) 至少一個中等規模的公開資料子集（如 3.6K Terminal tasks 與 2K Office tasks）；(3) 對應的 Runtime configurations（例如 Dockerfile 或 VM 映像檔）；(4) 完整的訓練日誌與超參數。

#### 未來研究方向

NexForge 的 Requirement-Driven Task Synthesis 為代理後訓練開啟了多條後續研究路徑：

1. **擴展至更多能力領域**：文中已暗示 Science tasks 的可能性。未來可進一步探索 Web agents（網頁代理）、Multi-modal environments（多模態環境）、Software engineering（軟體工程）乃至機器人控制等領域，驗證框架的通用性。

2. **結合強化學習（RL）**：目前 NexForge 主要服務 SFT。未來可將合成資料作為 RL 的初始環境，結合 PPO（Proximal Policy Optimization）、DPO（Direct Preference Optimization）或 Process Reward Models（過程獎勵模型），進一步提升 Long-horizon interaction trajectories 的品質。

3. **動態需求發現與線上更新**：目前的 Demand discovery 可能依賴靜態資料。未來可引入即時使用者日誌、Issue 追蹤系統或社群討論，讓 Scenario reservoir 隨真實世界需求演進而更新。

4. **自動化驗證與獎勵模型**：由於 NexForge 不產生人工參考答案，發展自動化 Verifier（驗證器）或 Unit-test generator（單元測試生成器）將是關鍵，特別是針對開放式任務的交付物品質評估。

5. **規模化法則（Scaling Laws）研究**：文中已觀察到資料量增加時的邊際遞減現象。未來可系統性研究 Task diversity（任務多樣性）、Difficulty distribution（難度分布）與資料量之間的最佳權衡，發展出類似 LLM 領域的 Scaling laws。

6. **降低合成成本**：NexForge 的每個階段都可能呼叫大型語言模型，成本不菲。未來可研究如何用較小的模型進行初步合成，再以大型模型進行精煉，或建立可重複使用的 Task form 與 Scenario 快取機制。

7. **安全性與對齊**：自動生成並執行任務可能產生惡意程式碼、資料外洩或環境破壞風險。未來需要建立更強大的 Sandbox（沙箱）、有害任務過濾機制，以及與人類價值對齊的約束條件。

8. **開源完整生態系統**：釋出程式碼、資料、容器與評測工具，將有助於社群複製並改進 NexForge，並推動 Open-source（開源）Agent 模型的整體發展。

## 論文問答

**Q1：NexForge 試圖解決什麼核心問題？為什麼現有的可執行代理訓練資料難以大規模擴展？**

A：NexForge 針對的是「基質綁定方法」（substrate-bound methods）在擴展可執行代理訓練資料時的瓶頸，這類方法把任務生成綁定在預設的工具、程式碼倉庫或技能圖譜上。每當要涵蓋新領域，研究者就必須手動打造特定領域的基礎設施與客製化流程，導致擴展成本高昂且難以複用。此外，任務分布往往反映基質本身的偏差，而非真實世界需求，因此訓練出的代理可能無法應對實際場景。

**Q2：為什麼基質綁定方法無法真實反映真實世界需求？**

A：基質綁定方法的規模受限於輸入基質的覆蓋範圍，例如預設倉庫或工具清單的數量與種類，因此能產生的任務類型與數量都有上限。由於每個新領域都需要量身打造的流程，這些方法難以根據實際應用場景動態調整任務組成。結果是生成的任務分布常常由既有基質決定，產生系統性偏差，而非依照真實世界中各種能力需求的頻率與重要性來設計。

**Q3：需求驅動的任務合成為何對代理後訓練至關重要？**

A：需求驅動的合成方式把「代理應該練習什麼」與「如何讓練習可執行」解耦，讓資料生成從高階能力需求出發，而不是從既有工具或倉庫出發。這使得同一套流程可以跨終端機、辦公室、科學等不同能力領域擴展，無需為每個領域重建基礎設施。同時，這種方式能先調查真實世界需求，再決定任務類型與分布，從而讓訓練資料更貼近實際應用。

**Q4：NexForge 的核心方法包含哪三個主要階段？**

A：NexForge 包含「需求發現」（demand discovery）、「分布感知任務編譯」（distribution-aware task compilation）與「軌跡生成」（trajectory generation）三個階段。首先，系統調查真實世界需求，建立代表性情境與任務輪廓；接著，透過組合採樣的任務形式與具體情境，生成符合需求分布的任務指令；最後，系統為每個指令自動檢索或建構所需檔案、依賴與執行階段配置，並合成專家展開軌跡，形成完整的訓練資料包。

**Q5：與先前研究相比，NexForge 的關鍵創新是什麼？**

A：NexForge 的關鍵創新在於將任務生成與預設基質解耦，改以高階能力需求作為起點。不同於以往需要預定義工具、倉庫或技能圖譜的方法，NexForge 能自動根據任務指令建構可執行工作空間，包含檔案、軟體依賴與執行階段配置。這種統一架構讓同一套流程能跨越多個差異極大的能力領域，並產出多樣且可執行的專家軌跡供監督式微調使用。

**Q6：NexForge 如何表示一個任務？輸出的任務包包含哪些內容？**

A：NexForge 將每個任務表示為任務形式（task form）與情境（scenario）的組合，其中任務形式包含任務類型、預期交付物、來源策略、執行環境、語言與難度等屬性。輸出的可執行任務包則包含任務指令、基礎材料、工作空間檔案、軟體依賴與執行階段配置。這些任務包專為軌跡收集而設計，不需要人工撰寫的參考答案或任務專屬驗證器，從而降低大規模資料生成的成本。

**Q7：論文使用了哪些基準與模型來評估 NexForge？**

A：論文在終端機能力上使用 Terminal-Bench 2.0 與 Terminal-Bench 2.1，在辦公室與通用代理能力上使用 GDPval 的 Elo 評分系統。基礎模型採用 Qwen3.5-35B-A3B，並透過 NexForge 合成的資料訓練出 Nex-N2 系列公開代理模型。比較對象包括 Claude Opus 4.6 搭配 Claude Code 等前沿專有系統，以檢驗開源模型在資料規模化後能否達到相近甚至更好的表現。

**Q8：NexForge 取得了哪些關鍵量化結果？**

A：僅使用 3,600 筆終端機任務，NexForge 就將 Qwen3.5-35B-A3B 在 Terminal-Bench 2.0 上的表現從 22.5% 提升至 52.0%；在辦公室任務方面，2,000 筆任務讓同一模型在 GDPval 的 Elo 從 813 提升至 1338。進一步將終端機任務擴大到 43,200 筆後，模型在 Terminal-Bench 2.0 達到 58.4%，與配備 Claude Code 的 Claude Opus 4.6 相當。更大規模的 NexForge 資料則訓練出 Nex-N2，在 Terminal-Bench 2.1 達到 75.3%，在 GDPval 達到 1585 Elo，創下開源最尖端表現並超越多個專有系統。

**Q9：從實驗結果可以得出哪些關於規模化與跨領域的洞察？**

A：實驗顯示，隨著 NexForge 合成資料量增加，模型表現持續提升，從 3.6K 到 43.2K 終端機任務都帶來明顯進步，顯示需求驅動的資料規模化具有強大潛力。更重要的是，同一套 NexForge 流程無需特定領域工程，就能同時為終端機與辦公室這兩個差異極大的領域生成有效訓練資料。這證明了解耦任務生成與基質後，資料合成流程具備良好的可轉移性與可擴展性。

**Q10：NexForge 可以應用在哪些實際場景？**

A：NexForge 可應用於需要大量可執行互動軌跡的代理能力訓練，例如終端機操作、辦公室生產力工具使用，以及潛在的科學計算或軟體工程任務。由於它從高階能力需求出發，任何具備明確需求描述與可執行環境的領域，都能透過同一套框架產生訓練資料。這對於企業或研究機構希望快速為新應用場景訓練專屬代理特別有價值。

**Q11：在產品化或部署方面，NexForge 帶來哪些考量？**

A：NexForge 大幅降低了為每個新領域打造客製化資料流程的成本，使代理訓練資料的生产更具規模化與自動化潛力。然而，自動建構執行環境與合成專家軌跡仍需確保環境的可執行性與軌跡品質，否則可能影響微調效果。論文也釋出了 Nex-N2 系列公開模型，為社群提供了可重現與進一步研究的基礎。

**Q12：NexForge 可能對代理訓練領域產生什麼影響？**

A：NexForge 推動了從「基質綁定」到「需求驅動」的典範轉移，讓訓練資料的生成不再受限於既有工具或倉庫。這使得開源代理模型有機會透過資料規模化追上甚至超越部分前沿專有系統，如 Claude Opus 4.6 搭配 Claude Code。長遠來看，這種方法有助於民主化高品質代理訓練資料的取得，加速各領域智慧代理的發展。

**Q13：NexForge 可能存在哪些限制？**

A：雖然論文未詳細列舉所有限制，但 NexForge 仰賴自動化環境建構與大型語言模型生成，可能偶爾產生無法正確執行或依賴不一致的工作空間。由於任務包設計用於軌跡收集而非基準測試，缺乏人工撰寫的參考答案，可能增加品質控管與錯誤偵測的難度。此外，需求發現階段的覆蓋範圍若不足，仍可能導致任務分布無法完全反映真實需求。

**Q14：NexForge 可能出現哪些失敗案例？**

A：自動檢索或建構的檔案與依賴可能與任務指令不匹配，導致環境無法執行或專家軌跡無法完成目標。合成專家展開時，模型可能在長期互動中累積錯誤，產生次優或錯誤的示範軌跡。若需求調查未能涵蓋某些邊緣但重要的任務類型，訓練資料分布也會出現缺口，使代理在相關情境下表現不佳。

**Q15：未來可以朝哪些方向延伸 NexForge？**

A：未來可將 NexForge 擴展到更多能力領域，例如科學實驗、程式碼生成與複雜多模態任務，並進一步強化自動驗證與錯誤修復機制。結合強化學習或偏好學習，可讓合成軌跡不僅用於監督式微調，也能支援更進階的後訓練策略。此外，引入真實使用者日誌或互動資料來改進需求發現，將有助於讓任務分布更精準地貼近實際應用場景。

## 實作前置條件

### 資料準備
- **高階能力需求文件**：明確定義希望代理習得的能力範圍，例如「終端機檔案操作」、「辦公室試算表分析」等。
- **情境素材庫（Scenario Reservoir）**：收集真實世界任務範例、文件範本、程式碼片段、工具使用紀錄，作為需求發現與情境生成的基礎材料。
- **任務形式與分布規範**：定義任務類型、交付物、執行環境、語言、難度等屬性，以及各類型的目標分布比例。
- **工具與 API 描述**：若任務需呼叫外部工具，需準備 OpenAPI／MCP 規格或工具說明文件。

### 運算資源
- **生成端**：可呼叫大型語言模型（如 Qwen3.5-35B-A3B 或更強模型）進行情境調查、任務指令編譯與專家軌跡合成。
- **執行沙箱**：具網路隔離的容器或虛擬機環境，用於執行合成出的終端機或辦公室任務，並收集長期互動軌跡。
- **儲存與資料管線**：可儲存數萬筆工作空間檔案、依賴套件、執行階段配置與軌跡記錄。
- **訓練叢集**：用於監督式微調（SFT）的 GPU 資源，規模視模型大小與資料量而定。

### 技能與團隊
- **AI 工程師**：熟悉 LLM 後訓練、SFT、提示工程與代理評測。
- **MLOps／平台工程師**：能建置安全沙箱、自動化資料管線與持續整合流程。
- **領域專家**：協助驗證任務是否反映真實世界需求，並審核專家軌跡品質。
- **資安人員**：確保自動執行程式碼與下載依賴時不會造成系統風險。

## 實作步驟建議

1. **定義能力需求與評測目標**  
   從產品目標出發，列出代理需要具備的能力清單，並對應到可量化的下游評測（如 Terminal-Bench 2.1、GDPval），作為資料規模與分布的設計依據。

2. **建立需求發現流程**  
   蒐集真實世界任務樣本、使用者日誌、公開文件與論壇討論，分析各任務類型的出現頻率與難度分布，形成代表性情境與任務輪廓。

3. **建構情境素材庫（Scenario Reservoir）**  
   將蒐集到的素材結構化，包含檔案範本、資料表、程式碼片段、網頁內容等，並標註其適用的任務類型與執行環境相容性。

4. **實作分布感知任務編譯器**  
   根據目標分布抽樣任務形式（Task Form）與具體情境，組合成任務指令（Directive）。確保編譯過程能控制任務類型、語言、難度與交付物等屬性。

5. **自動化可執行工作空間生成**  
   對每個任務指令，自動檢索或建構所需檔案、依賴套件與執行階段配置，產生可執行工作空間。此步驟應與預設工具或倉庫解耦。

6. **收集專家軌跡**  
   在沙箱中執行任務，使用強模型或自動化腳本產生專家展開（Expert Rollouts），記錄完整互動過程作為訓練軌跡。

7. **品質過濾與驗證**  
   透過執行結果檢查、語法驗證、重複性檢測與人工抽樣，過濾低品質或不可執行的任務。注意此處不需要人工撰寫標準答案，但需確保軌跡可重現。

8. **監督式微調與迭代**  
   使用合成資料對基礎模型進行 SFT，並在下游評測上驗證成效。根據表現缺口回頭調整能力需求、任務分布或情境素材庫。

9. **持續擴展與維運**  
   隨著產品需求演進，持續加入新的能力需求與情境，讓 NexForge 管線自動生成新任務，避免每次擴展都重建客製化流程。

## 潛在風險與注意事項

- **任務分布偏離真實需求**  
  若需求發現階段的素材不足或來源單一，合成的任務分布可能仍帶有基質偏差。建議結合多源資料並定期由領域專家審核分布比例。

- **沙箱執行安全風險**  
  自動執行終端機指令或下載依賴套件可能引入惡意程式碼。務必使用隔離容器、限制網路權限、禁止敏感系統呼叫，並記錄所有執行日誌。

- **專家軌跡品質不穩定**  
  生成模型可能產生看似合理但實際錯誤的軌跡。應加入執行驗證、單元測試或結果比對機制，避免將錯誤行為餵入訓練資料。

- **過度擬合合成任務**  
  模型可能在合成資料上表現良好，但無法泛化到真實使用者指令。建議保留部分真實任務作為驗證集，並進行對抗性測試。

- **版權與授權問題**  
  自動檢索或建構的基礎材料可能涉及第三方版權。需建立素材來源追蹤機制，並避免直接使用有授權爭議的程式碼或文件。

- **規模化成本**  
  隨著任務數量從數千擴展到數萬，生成、執行與儲存成本會快速上升。建議採用批次處理、快取常用情境與漸進式擴展策略。

## 與其他技術的整合建議

- **與 RAG 系統整合**  
  將 NexForge 合成的任務指令與基礎材料納入向量資料庫，讓代理在執行時能檢索相關範例與文件，提升長期互動任務的準確度。

- **與工具使用框架（MCP / OpenAPI）整合**  
  將 NexForge 的任務編譯器與模型上下文協定（MCP）或 OpenAPI 規格對接，使合成任務能自動對應到企業內部工具與外部服務。

- **與 CI/CD 管線整合**  
  把可執行工作空間的生成與驗證納入持續整合流程，每次更新能力需求或情境素材庫時自動產生新任務並執行迴歸測試。

- **與評測平台整合**  
  將 NexForge 輸出的任務與軌跡對接到 Terminal-Bench、GDPval 或自建的代理評測平台，形成「資料生成 → 模型訓練 → 能力評測」的閉環。

- **與資料標註平台整合**  
  對於需要人工複審的任務，可將合成結果匯入標註平台，由領域專家進行品質確認與分布校正，再回流至訓練管線。
