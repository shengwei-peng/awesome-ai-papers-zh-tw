## 深度分析

#### 方法論解析

**基準測試建構流程**

Co-Design Bench 的方法論核心在於從真實使用者編碼會話 (coding sessions) 中萃取任務，而非採用合成或預定義的編輯操作。具體流程包含以下幾個關鍵步驟：

1. **資料源頭策劃 (Data Curation)**：從 26,314 個真實使用者編碼會話中收集 37,463 個去重查詢 (deduplicated queries)，最終策劃為 273 個任務。這種從真實互動中萃取任務的方式，與 WebCompass-edit 等使用預定義編輯操作池 (predefined edit operations pool) 再以查詢建構 (query construct) 合成任務的方法形成鮮明對比。

2. **任務正規化 (Task Normalization)**：將使用者請求標準化為有界編輯任務 (bounded editing tasks)，同時保留可用的會話上下文與附件 (attachments)，確保任務既具備真實性又具有可評估性。

3. **預編輯應用程式恢復 (Pre-Edit Application Recovery)**：恢復並驗證可執行的預編輯應用程式 (runnable pre-edit applications)，這是實現無參考評估 (reference-free evaluation) 的基礎——評估者無需黃金程式碼 (gold code) 或目標截圖 (target screenshots) 即可判斷修訂是否滿足需求。

**雙軌道設計 (Dual-Track Design)**

基準測試劃分為兩個互補軌道：

- **多模態編輯 (Multimodal Editing, ME)**：評估局部視覺、結構與內容編輯，可選擇性接受圖像、音訊、影片或文件輸入。這對應「紮根理解」(Grounded Understanding) 與「UI 轉換」(UI Transformation) 能力維度。

- **儲存庫編輯 (Repository Editing, RE)**：評估跨元件、路由、狀態與資料流的協調式 UI 與功能變更。這對應「功能實作」(Functional Implementation) 能力維度。

兩個軌道共享同一任務表述框架，將相依修訂 (dependent revisions) 編碼為可稽核的需求 (auditable requirements)，連結使用者證據的詮釋與編輯後應用程式中可觀察的視覺變化和狀態轉換。

**先評判再反駁協議 (Judge-then-Refute Protocol)**

此評估協議是方法論的另一核心創新，包含三個階段：

1. **證據收集階段**：使用原始碼與瀏覽器證據 (source and browser evidence) 對隱藏標準進行評分。視覺聲明 (visual claims) 需要成功渲染與截圖，互動聲明 (interaction claims) 需要記錄的瀏覽器動作；證據缺失時評估在分數彙總前中止。

2. **裁決階段**：對每個標準產出 PASS、PARTIAL 或 FAIL 裁決 (verdicts)。

3. **反駁階段 (Refutation Pass)**：獨立的 LLM 驗證器 (LLM verifier) 挑戰 PASS 與 PARTIAL 裁決，檢查存根 (stubs)、硬編碼 (hardcoding)、不可達功能 (unreachable functionality) 與需求不匹配 (requirement mismatches)。這是一種對抗性驗證 (adversarial verification) 機制。

此協議的精妙之處在於：它不需要參考實作，而是透過「預編輯應用程式作為錨點」來判斷變更是否符合需求，同時保留所有裁決與追蹤記錄供檢查。

**代理式執行框架 (Agentic Harness)**

所有模型端點 (model endpoints) 在共享的代理式執行框架下評估，該框架提供迭代工具存取 (iterative tool access)。論文特別強調執行模式對評分結果的影響：在 WebCompass-edit 的 150 個任務上，將 qwen3.7-plus 從單次執行 (single-shot execution) 切換至代理式執行 (agentic execution)，平均評分特徵達成率 (mean graded feature completion) 從 73.6% 提升至 95.1%（提升 21.5 個百分點），而 opus-4-8 在代理式執行下達到 99.4%。這顯示執行條件對測量結果有實質影響，因此基準測試選擇在代理式執行下進行評估。

#### 實驗數據解讀

**整體效能落差 (Overall Performance Gap)**

實驗結果揭示了一個關鍵的「部分需求滿足 vs. 完整任務成功」落差：

- 最佳模型端點平均通過 69.9% 的標準 (criteria)，但僅完全滿足 26.4% 的任務。
- 這意味著即使模型能處理大多數個別需求，仍有近四分之三的任務存在某些未滿足的標準。

這個 43.5 個百分點的落差（69.9% - 26.4%）是論文最關鍵的發現之一，顯示「標準達成率」(criterion completion) 與「完整任務成功率」(complete task success) 是兩個本質不同的測量維度。

**軌道間差異 (Inter-Track Variation)**

模型排名在兩個軌道間會產生變化，這暗示多模態編輯與儲存庫編輯考驗的是不同的能力組合。雖然論文未提供具體的軌道細分數據，但此現象本身已說明：單一軌道的效能不足以代表整體能力。

**變更類型寬度的影響 (Effect of Change Type Breadth)**

所有十個模型端點在跨越三或四種變更類型 (change types) 的儲存庫編輯上，標準達成率均低於跨越一或兩種變更類型的編輯。這是一個普遍且穩健的發現，顯示：

1. 變更類型數量是任務複雜度的有效代理指標。
2. 當任務需要同時協調多種類型的變更時，所有模型都會遇到瓶頸。
3. 這可能是因為多類型變更需要更複雜的狀態管理與跨元件依賴追蹤。

**分數飽和問題 (Score Saturation)**

論文圖 1(a) 揭示了一個重要的方法論警示：在 WebCompass-edit 上，opus-4-8 在代理式執行下達到 99.4% 的平均特徵達成率，呈現分數飽和 (score saturation) 現象。這意味著：

1. 該基準測試在代理式執行下已接近「解決」(solved)，無法有效區分頂尖模型。
2. Co-Design Bench 的設計刻意避免此問題——透過真實使用者任務的複合性與多模態性，保留了 35.1 個百分點的提升空間 (headroom)。
3. 這顯示基準測試設計需要在「足夠困難以保留區辨力」與「足夠簡單以利於分析」之間取得平衡。

**範例任務分析 (Example Task Analysis)**

論文圖 1(b) 對比的兩個範例說明了任務來源的差異：

- **WebCompass-edit 範例**：「招聘指揮中心」(Recruiter Command Center) 儀表板，從預定義編輯操作池（儀表板、富文本、視差滾動等）合成查詢，使用 LLM-as-a-Judge 對指令、特徵、風格各給 0-10 分。
- **Co-Design Bench 範例**：運動片段編輯器 (Sports Clip Editor)，從真實編碼會話恢復的查詢：「新增片段；限制數量與時長。縮放時保持錨點對齊。移除/分割片段以重新啟用新增功能。」此任務耦合了片段計數限制、時長限制、縮放時的時間軸對齊 (timeline alignment)、以及移除/分割後的狀態更新 (state updates) 以重新啟用插入功能。

後者展現了真實使用者任務的「複合修訂」(compound revisions) 特性——單一請求繫結多個互動需求，這正是現有基準測試覆蓋不足的地方。

**與參考重建類基準的比較 (vs. Reference Reconstruction Benchmarks)**

Design2Code、WebSight-Test、WebRenderBench、IWR-Bench 等基準測試專注於從設計稿重建程式碼，屬於「從無到有」的任務。Co-Design Bench 則專注於「從現有到修訂」，更貼近真實的迭代共同設計循環。這兩類任務考驗的能力組合不同：前者考驗視覺理解與程式碼生成，後者還需考驗對現有程式碼的理解、修改與整合。

**與頁面層級編碼基準的比較 (vs. Page-Level Coding Benchmarks)**

MT-Web2Code、DesignBench、WebCompass-edit 等基準測試處理頁面層級的編碼任務。WebCompass-edit 雖使用真實使用者會話（部分子集），但其任務源自預定義編輯操作池。Co-Design Bench 的差異在於：

1. **任務真實性**：直接從真實會話恢復，而非從預定義操作池合成。
2. **變更複合性**：允許多種類型變更的耦合，而非單一類型的編輯。
3. **模態豐富度**：支援音訊、影片、文件等 WebCompass-edit 未涵蓋的模態。

**與儲存庫軟體工程基準的比較 (vs. Repository Software Engineering Benchmarks)**

SWE-bench M、SWE-Lancer 等基準測試處理儲存庫層級的問題，但通常來自獨立問題報告而非編碼會話。Co-Design Bench 的 RE 軌道保留了會話上下文，使任務更具體且更貼近實際協作場景。

**方法論創新 (Methodological Innovations)**

相較於現有工作，Co-Design Bench 的三項主要方法論貢獻：

1. **真實任務策劃**：從 26,314 個會話中策劃任務，而非合成或預定義。
2. **先評判再反駁協議**：結合程式碼與瀏覽器證據，加上獨立反駁階段，實現無參考的穩健驗收。
3. **雙重視角評估**：同時報告標準達成率與完整任務成功率，揭示部分滿足與完全成功之間的落差。

**侷限性 (Limitations)**

1. **任務規模**：273 個任務相對較小，可能限制統計分析的細粒度。
2. **領域範圍**：聚焦於 Web 應用程式共同設計，未涵蓋行動應用、桌面應用或後端系統。
3. **語言限制**：未明確說明支援的程式語言範圍，雖然從上下文推測為 JavaScript/TypeScript 等 Web 技術棧。
4. **評估成本**：代理式執行加上反駁階段需要大量計算資源，可能限制大規模實驗。
5. **標準主觀性**：雖然標準由專家撰寫，但「多個有效實作」的設計可能引入評估者間分歧。

#### 可重現性評估

**資料可取得性 (Data Availability)**

從論文內容可推斷：

1. **基準測試資料**：273 個任務與 2,331 個驗收標準 (acceptance criteria) 應會公開釋出，因為這是基準測試的核心資產。
2. **預編輯應用程式**：作為可執行的起點，這些應用程式對於重現實驗至關重要，預期會隨基準測試一同釋出。
3. **會話資料**：原始的 26,314 個編碼會話可能因隱私考量而不會完整公開，但策劃後的去重查詢與任務定義應會提供。

**程式碼可取得性 (Code Availability)**

1. **評估協議實作**：先評判再反駁協議 (judge-then-refute protocol) 的實作，包括證據收集、裁決生成與反駁邏輯，應會開源以促進採用。
2. **代理式執行框架**：共享的代理式執行框架 (agentic harness) 對於重現實驗至關重要，預期會公開。
3. **渲染管線 (Render Pipeline)**：用於視覺聲明的渲染與截圖系統需要公開，以便其他研究者驗證視覺評估結果。

**模型權重可取得性 (Model Weights Availability)**

1. **評估的模型端點**：論文評估了十個模型端點，包括 qwen3.7-plus 與 opus-4-8 等。這些模型本身由各公司提供，論文不涉及模型訓練。
2. **驗證器模型**：反駁階段使用的 LLM 驗證器需要明確說明，以便其他研究者使用相同或可比較的驗證器。

**實驗重現的挑戰 (Reproducibility Challenges)**

1. **代理式執行的隨機性**：代理式執行涉及多輪工具呼叫，每次執行的軌跡可能不同，這對結果的精確重現構成挑戰。
2. **瀏覽器環境差異**：不同瀏覽器版本或作業系統可能影響渲染結果，進而影響視覺評估。
3. **LLM 評判的變動性**：LLM-as-a-Judge 本身具有隨機性，即使固定溫度參數，跨版本的模型行為也可能變化。
4. **基準測試的動態性**：真實使用者會話隨時間變化，基準測試的「快照」性質意味著未來的重現可能使用不同的底層資料。

**促進重現的設計 (Reproducibility-Friendly Design)**

1. **隱藏標準 (Hidden Criteria)**：驗收標準對模型隱藏，但對評估者公開，這有助於防止過擬合同時保持評估透明。
2. **保留裁決與追蹤**：每個標準裁決都連結到支援證據，便於檢查與爭議解決。
3. **無參考設計**：不需要黃金程式碼或目標截圖，降低了重現的資源需求。

#### 未來研究方向

**基準測試擴展 (Benchmark Extension)**

1. **跨領域遷移**：將方法論擴展至行動應用、桌面應用或後端系統的共同設計任務，測試基準測試設計在不同領域的適用性。
2. **多語言支援**：擴展至 Python、Java、Go 等其他程式語言，評估模型在不同技術棧上的表現差異。
3. **任務規模擴大**：從 273 個任務擴展至更大規模，以支援更細粒度的子群體分析與統計檢定。
4. **動態基準測試**：設計隨時間更新的基準測試機制，避免模型過擬合特定任務集。

**評估協議改進 (Evaluation Protocol Improvement)**

1. **多驗證器共識**：使用多個獨立的 LLM 驗證器並取共識裁決，減少單一驗證器的偏差。
2. **人類專家對照**：定期以人類專家評估結果作為黃金標準，校準 LLM 驗證器的判斷。
3. **證據豐富化**：整合更多類型的證據，如靜態分析、單元測試結果、效能基準等，提供更全面的評估視角。
4. **可解釋性增強**：開發視覺化工具展示每個標準的證據鏈，幫助研究者理解模型失敗的原因。

**能力維度深化 (Capability Dimension Deepening)**

1. **紮根理解 (Grounded Understanding)**：研究模型如何更好地從多模態證據（圖像、音訊、影片、文件）中提取使用者意圖，特別是當證據模糊或矛盾時。
2. **UI 轉換 (UI Transformation)**：探索視覺設計原則的編碼化，使模型能更準確地將視覺變更轉化為程式碼修改。
3. **功能實作 (Functional Implementation)**：研究跨元件狀態管理的最佳實踐，幫助模型處理複雜的相依修訂。

**代理式執行最佳化 (Agentic Execution Optimization)**

1. **執行策略比較**：系統比較不同的代理式執行策略（如 ReAct、Reflexion、Tree of Thoughts）在 Co-Design Bench 上的表現。
2. **工具使用效率**：分析模型在迭代過程中的工具使用模式，識別效率瓶頸。
3. **早期停止機制**：開發能預測任務是否會成功的早期信號，避免在已知失敗的任務上浪費計算資源。

**人機協作模式 (Human-AI Collaboration Patterns)**

1. **互動式評估**：擴展基準測試以支援多輪互動，模擬真實的迭代共同設計過程。
2. **使用者意圖建模**：研究模型如何從模糊或不完整的請求中推斷真實意圖。
3. **反饋整合**：探索模型如何從使用者反饋中學習並改進後續修訂。

**理論分析 (Theoretical Analysis)**

1. **部分滿足的數學建模**：形式化「部分需求滿足」與「完整任務成功」之間的關係，建立預測模型。
2. **變更類型的圖論分析**：將任務建模為變更類型圖，分析圖結構如何影響任務難度。
3. **能力下限定理**：探索是否存在某些任務類型對所有當前模型構成根本性挑戰。

**產業應用 (Industrial Applications)**

1. **企業內部評估**：將基準測試方法論應用於企業特定的程式碼庫與設計規範。
2. **持續整合整合**：將評估協議整合至 CI/CD 管線，作為程式碼變更的品質門檻。
3. **教育應用**：使用基準測試任務作為程式設計教育的實作練習，培養學生的多模態需求理解能力。

**倫理與社會影響 (Ethics and Social Impact)**

1. **偏見審計**：分析基準測試任務是否對特定使用者群體、文化或設計風格存在系統性偏見。
2. **可及性考量**：評估模型在處理無障礙設計需求（如螢幕閱讀器相容性、鍵盤導航）方面的表現。
3. **智慧財產權**：研究基準測試中真實使用者會話的使用是否符合智慧財產權與隱私規範。

這些研究方向不僅能深化對代理式模型在共同設計任務中表現的理解，也能推動整個領域向更實用、更可靠、更公平的方向發展。Co-Design Bench 的真正價值不僅在於當前的評估結果，更在於它為未來研究提供了一個嚴謹、可重現且具有豐富提升空間的測試平台。

**Q4：Co-Design Bench 的「先評判再反駁協議」（Judge-then-Refute Protocol）是如何運作的？為何需要這個雙階段設計？**

A：先評判再反駁協議分為兩個階段：第一階段使用原始碼與瀏覽器執行證據對隱藏驗收標準進行評判，給出 PASS、PARTIAL 或 FAIL 的裁決；第二階段則由獨立的 LLM 驗證器挑戰 PASS 與 PARTIAL 的正向裁決，檢查是否存在存根程式碼、硬編碼、無法達成的功能或需求不符等問題。這種雙階段設計的必要性在於，單一評判器容易受到「表面通過」的欺騙——例如代理可能寫出能渲染但實際上不具備功能的程式碼。視覺與互動聲明還需要通過強制性的證據稽核：視覺聲明必須有成功的渲染與截圖，互動聲明必須有錄製的瀏覽器動作，否則評估在分數彙總前就會中止。這確保了每個裁決都有可追溯的證據支援。

A：Co-Design Bench 的關鍵設計是將「編輯前應用程式」（pre-edit application）作為評估錨點。每個任務都配對了可執行的編輯前應用程式、標準化的請求，以及隱藏的專家撰寫驗收標準。這些標準指定了所請求的變更，但允許多個有效的實作方式，因此不需要唯一的黃金程式碼。視覺與互動的評估透過實際執行編輯後的應用程式來進行，而非比對目標截圖。這種設計反映了真實共同設計的本質：使用者關心的是「修改後的應用程式是否滿足需求」，而非「是否與某個參考實作完全一致」。保留的裁決與追蹤記錄也讓每個標準判斷都能連結到其支援證據，供檢查使用。

A：兩個軌道的設計是為了涵蓋共同設計的不同面向。多模態編輯（ME）軌道評估局部視覺、結構與內容編輯，可選擇性接受圖像、音訊、影片或文件輸入，著重於單一元件或頁面層級的修改；儲存庫編輯（RE）軌道則評估跨元件、路由、狀態與資料流的協調式 UI 與功能變更，著重於多檔案、多模組的相依修改。這兩個軌道共同對應到三個能力維度：紮根理解（Grounded Understanding）考驗代理解讀多模態證據的能力；UI 轉換（UI Transformation）考驗代理將意圖轉化為介面變更的能力；功能實作（Functional Implementation）則考驗代理實作可運作行為的能力。這種雙軌道設計使得基準測試能夠區分模型在不同複雜度任務上的強項與弱項。

**Q7：Co-Design Bench 的任務是如何從真實使用者會話中策劃出來的？資料規模與品質如何？**

A：Co-Design Bench 從 26,314 個真實使用者程式編碼會話中收集了 37,463 個去重查詢，最終策劃出 273 個任務，配對 2,331 個專家撰寫的隱藏驗收標準。策劃過程包括：恢復並驗證可執行的編輯前應用程式、保留可用的會話上下文與附件、將使用者請求整合為有界線的編輯任務。這個過程確保了任務來自真實的使用情境，而非合成或預定義的操作池。相較於 WebCompass-edit 使用預定義編輯操作來構造查詢，Co-Design Bench 的任務保留了真實使用者請求的複合性與多模態特性，例如運動片段編輯器範例中耦合的多重約束。

**Q8：在十個模型端點的評估中，最關鍵的發現是什麼？為何「部分需求滿足」與「完整任務成功」之間存在巨大差距？**

A：最關鍵的發現是：最強的模型端點平均通過了 69.9% 的標準，但僅完全滿足 26.4% 的任務。這意味著模型能夠處理大部分個別需求，但在同時滿足所有需求以達成完整任務成功方面仍有顯著落差。此外，所有十個端點在跨越三或四種變更類型的儲存庫編輯上的標準達成率，都低於跨越一或兩種變更類型的編輯。這顯示隨著任務複雜度提升，模型維持跨元件一致性的能力下降。這個差距凸顯了僅報告標準達成率可能掩蓋實際的任務完成能力，因此基準測試同時報告標準滿足與完整任務成功兩個指標。

**Q9：相較於 WebCompass-edit，Co-Design Bench 在評估上提供了什麼額外的鑑別力？**

A：根據圖 1(a) 的對比，opus-4-8 在 WebCompass-edit 上達到 99.4% 的平均特徵達成率，但在 Co-Design Bench 上僅達到 64.9%，存在 35.1 分的提升空間（headroom）。這個差距反映了兩個基準測試的本質差異：WebCompass-edit 使用預定義編輯操作構造查詢，任務相對單一；而 Co-Design Bench 的任務來自真實使用者會話，涉及複合修訂、跨元件變更與多模態證據整合。因此，Co-Design Bench 能夠在 WebCompass-edit 已達到「分數飽和」的情況下，提供更細粒度的能力區分，特別是在處理真實世界複雜性方面。

**Q10：Co-Design Bench 的設計對實際產品開發中的程式編碼代理有什麼意義？**

A：對實際產品而言，Co-Design Bench 的設計揭示了幾個重要意涵。首先，真實使用者請求往往比預定義操作更複雜，涉及多模態輸入與跨元件變更，這意味著產品中的代理必須具備處理複合修訂的能力，而非僅僅執行單一指令。其次，「部分需求滿足」與「完整任務成功」之間的差距提醒產品設計者：使用者對「應用程式能否正常運作」的期望是整體性的，即使個別功能看似正常，狀態不一致或互動斷裂仍會導致使用者體驗失敗。因此，產品中的代理需要具備自我檢查與跨需求協調的能力，而非僅僅逐一實作個別功能。

**Q11：基準測試的多模態支援（圖像、音訊、影片、文件）對未來的程式編碼代理發展有何啟示？**

A：Co-Design Bench 支援 T、I、V、A、D 五種輸入模態（文字、圖像、影片、音訊、文件），這反映了真實共同設計中使用者表達意圖的多樣性。例如，使用者可能提供設計參考圖、語音備忘錄、螢幕錄影或規格文件，期望代理將這些證據整合到應用程式修改中。這對未來代理發展的啟示是：僅處理文字指令的代理將無法滿足真實使用情境；代理需要發展跨模態理解能力，能夠從視覺證據推斷佈局意圖、從音訊證據提取時序約束、從文件證據理解規格細節。這也意味著訓練資料與評估方法都需要擴展到多模態領域。

**Q12：Co-Design Bench 的「代理式評判法」（Agentic-as-a-Judge）相較於傳統的「LLM 評判法」（LLM-as-a-Judge）有何優勢？**

A：傳統的 LLM 評判法（如 WebCompass-edit 使用的）僅根據靜態評估給出 0-10 分的評分，無法實際執行應用程式來驗證功能。相較之下，Co-Design Bench 的代理式評判法讓評判代理能夠執行、互動並檢查編輯後的應用程式，收集原始碼與瀏覽器證據。這種方法能夠驗證功能是否真的可達成，而非僅僅看起來正確。結合獨立的 LLM 驗證器進行反駁，這個雙層架構大幅降低了誤判的風險。對於涉及狀態轉換、互動邏輯的任務，這種基於實際執行的評估是不可或缺的。

**Q13：Co-Design Bench 存在哪些已知的限制？**

A：根據論文的描述，Co-Design Bench 的限制包括以下幾點。首先，雖然基準測試涵蓋了多模態輸入，但任務主要來自 Web 應用程式共同設計的情境，可能無法完全代表其他領域（如行動應用、桌面軟體）的共同設計挑戰。其次，基準測試仰賴專家撰寫的驗收標準，這些標準雖然經過品質控制，但仍可能存在主觀性或遺漏。第三，代理式執行框架的設計會影響評估結果，雖然論文中已固定了執行環境以確保公平比較，但不同框架之間的差異仍可能影響分數的絕對值。最後，273 個任務的規模雖然足以進行統計分析，但對於訓練或微調模型而言可能不夠大。

**Q14：基準測試結果揭示了哪些典型的失敗案例？模型在哪些情況下表現較差？**

### 實作步驟建議

**步驟一：任務策展與資料管線建置**
從真實使用者程式編碼會話資料庫出發，進行去重（論文中 37,463 條去重查詢）、請求標準化、附件保留，並還原每個任務對應的可執行編輯前應用程式。建議採用雙人獨立策展＋第三方仲裁的流程以確保任務品質。

**步驟二：雙軌道任務設計**
將任務分流至「多模態編輯（ME）」與「儲存庫編輯（RE）」兩個軌道。ME 軌道聚焦局部視覺、結構、內容編輯，可附帶圖像／音訊／影片／文件輸入；RE 軌道聚焦跨元件、路由、狀態、資料流的協調變更。為每個任務標註「變更類型數量」（1–2 種 vs. 3–4 種），因為論文中所有 10 個端點在 3–4 種變更類型上的標準達成率都顯著較低。

**步驟三：驗收標準撰寫**
聘請專家為每個任務撰寫 5–10 條隱藏驗收標準，標準需涵蓋三個能力維度：紮根理解（Grounded Understanding）、UI 轉換（UI Transformation）、功能實作（Functional Implementation）。標準應允許多個有效實作存在，避免綁定特定實作細節。

**步驟四：代理式執行框架部署**
建置共享的代理式執行框架，提供統一的工具介面（檔案讀寫、終端機執行、瀏覽器互動、截圖擷取）。所有候選模型端點必須在相同框架下執行，以確保比較的公平性——論文中明確指出執行模式（單次 vs. 代理式）會造成 21.5 分的差異。

**步驟五：實作先評判再反駁協議**
第一階段：使用 LLM 評判器，根據收集到的原始碼證據與瀏覽器證據，對每條驗收標準給出 PASS／PARTIAL／FAIL 裁決。第二階段：使用獨立的 LLM 驗證器挑戰 PASS 與 PARTIAL 裁決，檢查是否存在樁函式、硬編碼、無法觸達的功能或需求錯配。視覺聲明需附截圖，互動聲明需附瀏覽器操作記錄；證據缺失則中止評分。

**步驟六：證據稽核與裁決追溯**
對所有裁決進行證據稽核：視覺聲明必須有成功渲染與截圖，互動聲明必須有錄製的瀏覽器動作。保留所有裁決與證據的關聯鏈，支援後續人工檢視。

**步驟七：多指標報告**
同時報告「標準達成率」（criterion completion）與「完整任務成功率」（complete task success）。論文的關鍵發現是：最強模型可達 69.9% 標準達成率，但僅 26.4% 完整任務成功率——兩者落差達 43.5 個百分點，單一指標會嚴重誤導決策。

**步驟八：跨軌道與變更類型分析**
分別報告 ME 與 RE 兩個軌道的表現，並依變更類型數量（1–2 種 vs. 3–4 種）進行切分。論文中所有 10 個端點在 3–4 種變更類型上的表現都低於 1–2 種，這是部署前的關鍵風險指標。

### 潛在風險與注意事項

**風險一：分數飽和導致基準測試失效**
論文中 opus-4-8 在 WebCompass-edit 的 150 個任務上以代理式執行達到 99.4% 平均特徵達成率，顯示基準測試容易被頂級模型「玩穿」。**緩解方式**：定期更新任務池、引入更具挑戰性的複合修訂任務、關注「完整任務成功率」而非僅看平均特徵達成率。

**風險二：評判器與驗證器同質化偏誤**
若評判器與驗證器使用相同或相似的 LLM，可能產生同質化偏誤，無法有效挑戰裁決。**緩解方式**：使用不同廠商或不同規模的模型作為評判器與驗證器；保留所有證據鏈以支援人工抽樣覆核。

**風險三：證據缺失導致評估中斷**
若渲染失敗、瀏覽器操作失敗或截圖缺失，整個評估可能在評分聚合前中止，造成資料浪費。**緩解方式**：建置容錯機制，自動重試渲染、記錄失敗原因、對失敗任務進行人工分流。

**風險四：可執行編輯前應用程式的維護成本**
每個任務都需要一個 runnable 的起始狀態，隨著任務數增加，維護成本呈線性成長。**緩解方式**：採用容器化快照、自動化環境還原腳本、定期清理已失效的任務。

**風險五：真實使用者會話的隱私與授權問題**
使用真實使用者程式編碼會話涉及隱私與智慧財產權問題。**緩解方式**：取得使用者明確授權、進行去識別化處理、僅使用公開或已授權的會話資料。

**風險六：變更類型耦合導致評估失真**
論文中所有 10 個端點在 3–4 種變更類型的儲存庫編輯上表現都較差，但若任務設計不當，可能將「模型能力不足」誤判為「任務設計過難」。**緩解方式**：邀請人類專家對基準測試任務進行難度校準，建立「人類天花板」對照組。

**風險七：執行模式混淆導致結果不可比**
論文中同一模型從單次執行切換到代理式執行，特徵達成率提升 21.5 分。**緩解方式**：在報告中明確標註執行模式，跨基準測試比較時必須固定執行模式。

### 與其他技術的整合建議

**與 SWE-bench 系列整合**

**與 WebCompass-edit 整合**
WebCompass-edit 使用預定義編輯操作，Co-Design Bench 使用真實使用者會話。兩者可互補：WebCompass-edit 提供可控的難度階梯，Co-Design Bench 提供真實分佈的任務樣貌。建議在模型選型流程中先用 WebCompass-edit 進行快速篩選，再用 Co-Design Bench 進行實戰驗證。

**與 LLM-as-a-Judge 框架整合**

**與設計工具整合**
對於 Figma-to-Code、Whimsical-to-Code 等設計協作工具，可將 Co-Design Bench 的 ME 軌道作為評估基準，特別關注「圖像附件 → 程式碼變更」的轉譯品質。建議擴展任務池，加入更多設計稿類型的附件。

**與 CI/CD 管線整合**

**與 RLHF / RLAIF 訓練流程整合**
論文中 2,331 條專家撰寫驗收標準可作為高品質獎勵信號來源。建議將「標準達成率」與「完整任務成功率」分別作為稠密獎勵與稀疏獎勵，訓練模型在追求部分標準達成的同時，也關注完整任務的交付能力。
