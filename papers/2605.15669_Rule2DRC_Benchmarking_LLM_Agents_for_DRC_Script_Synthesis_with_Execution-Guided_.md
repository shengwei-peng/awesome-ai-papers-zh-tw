## ⚡ TL;DR

現有DRC腳本合成基準規模小且未以執行正確性評估，本研究建立大規模執行導向評測框架。
提出Rule2DRC基準與SplitTester代理，利用執行回饋生成區分性測試案例以篩選候選腳本。
實現無需輸入評估佈局即可驗證腳本功能正確性，並顯著提升Best-of-N程式選擇效能。

## 摘要翻譯

可製造的（Manufacturable）晶片佈局（Chip Layouts）必須滿足數千條幾何設計規則（Geometry-Based Design Rules），而設計規則檢查（Design Rule Checking, DRC）透過在佈局上執行可執行的 DRC 腳本（DRC Script）來強制執行這些規則。將自然語言規則（Natural Language (NL) Rules）轉譯為正確的 DRC 腳本（DRC Script）不僅耗費人力，且需要專業知識，因而推動以大型語言模型代理（LLM Agents）進行 DRC 腳本合成（DRC Script Synthesis）與除錯（Debugging）。然而，現有的基準測試評估集規模較小，且經常透過程式碼相似度（Code Similarity）而非執行正確性（Execution Correctness）來評估腳本；此外，先前的機器學習方法（Machine Learning-Based Methods）若非忽略執行回饋（Execution Feedback），便是需要將標記測試佈局（Labeled Test Layouts）作為代理的輸入。為此，我們提出了 Rule2DRC，一個針對 DRC 腳本編寫代理的大規模基準測試，包含 1,000 項規則到腳本任務（Rule-to-Script Tasks）以及 13,921 個評估晶片佈局（Evaluation Chip Layouts），以進行基於執行的評分（Execution-Based Scoring）。Rule2DRC 提供了一個評估流程（Evaluation Pipeline），可透過 DRC 執行結果來衡量功能正確性（Functional Correctness），且無需將評估晶片佈局（Evaluation Chip Layouts）作為代理的輸入。我們也提出了 SplitTester，一個用於程式選擇（Program Selection）的測試代理（Tester Agent），其利用執行回饋（Execution Feedback）生成區分性測試案例（Discriminative Test Cases），並區分先前無法區分的候選腳本（Candidate Scripts），在此領域中顯著提升了 Best-of-N 選擇（Best-of-N Selection）的效能。我們於 https://github.com/snu-mllab/Rule2DRC 釋出了程式碼。

### 核心貢獻（3～5點）
- 建立大規模 DRC 腳本合成基準測試 Rule2DRC：涵蓋 1,000 項規則到腳本任務與 13,921 個評估晶片佈局，以基於執行的評分直接衡量功能正確性，解決現有基準測試規模過小且仰賴程式碼相似度之問題。
- 設計無需評估晶片佈局作為代理輸入之評估流程：僅透過 DRC 執行結果即可判定腳本執行正確性，降低對標記測試佈局之依賴。
- 提出 SplitTester 測試代理：藉由執行回饋生成區分性測試案例，有效區分先前無法區分之候選腳本，顯著提升 Best-of-N 選擇之程式選擇效能。

### 適合對象
從事電子設計自動化（EDA）、積體電路實體設計驗證，以及大型語言模型代理與程式合成相關研究之學者與工程師；特別適合關注如何結合執行回饋與自動化測試生成以提升程式選擇效能之研究者。

## 深度分析

#### 方法論解析

本研究提出兩大核心貢獻：Rule2DRC 大型基準測試（Benchmark）與 SplitTester 測試代理（Tester Agent）。

在 Rule2DRC 基準測試（Benchmark）方面，作者建構了包含 1,000 個 rule-to-script tasks（規則到腳本任務）與 13,921 個 evaluation chip layouts（評估晶片佈局）的資料集。其中 310 條為擷取自開源 SkyWater 130nm 製程節點的真實幾何設計規則（Geometry-Based Design Rules），另 690 條為合成的複雜多條件設計規則（Design Rules）。此規模較現有基準測試（Benchmark）大上一個數量級。評估流程（Evaluation Pipeline）採用 execution-based scoring（基於執行的評分），透過 DRC Engine（DRC 引擎，即 KLayout）執行候選腳本，比對其 violation outputs（違規輸出）與 ground-truth DRC script（真值 DRC 腳本）的 violation labels（違規標籤），以衡量 functional correctness（功能正確性）。特別值得注意的是，Rule2DRC 在評估時不要求將 evaluation chip layouts（評估晶片佈局）或 labeled test layouts（標記測試佈局）作為 LLM Agents（大型語言模型代理）的輸入，這與先前 DRC-Coder 等方法假設可取得測試資料作為輸入的設定不同，更能反映真實工程場景。在此框架中，LLM Agents（大型語言模型代理）透過 Tool Use（工具使用）將 DRC Engine（DRC 引擎）作為外部工具呼叫，僅依據 natural language (NL) rules（自然語言規則）或 NL description（自然語言描述）生成可執行的 DRC Script（DRC 腳本）。

SplitTester 則是針對 program selection（程式選擇）所設計的 execution-guided test generation（執行導向測試生成）方法，用於強化 Best-of-N Selection（Best-of-N 選擇）。其運作邏輯如下：首先針對一組 candidate scripts（候選腳本）生成初始測試佈局並執行，依據各腳本在當前測試上的 violation outputs（違規輸出）進行分群（clustering）；接著，SplitTester 會針對規模最大或難以區分的群組，迭代生成 discriminative test cases（區分性測試案例），透過 execution feedback（執行回饋）將原先 indistinguishable 的 candidate scripts（候選腳本）拆散。此過程重複直到測試預算耗盡，最後再由 Judge LLM 依據所有具區分性的測試結果，從 top-3 候選中選出最佳腳本。相較於 CodeMonkey 僅嘗試區分前三大候選，或 S* 從已被分開的群組中浪費預算生成測試，SplitTester 維持完整候選池並專注於「切分」尚未分離的群組，顯著提升測試資源的使用效率。

#### 實驗數據解讀

Rule2DRC 的實驗設計凸顯了從 code similarity（程式碼相似度）轉向 execution correctness（執行正確性）的評估典範轉移。傳統以程式碼相似度為指標的方法，無法正確捕捉語法不同但功能等價的 DRC Script（DRC 腳本），亦可能高估表面相似但執行結果錯誤的候選腳本。Rule2DRC 透過在 13,921 個 evaluation chip layouts（評估晶片佈局）上實際執行，直接比對 functional correctness（功能正確性），使評估結果與可製造（Manufacturable）晶片的真實需求更為一致。

在 Best-of-N Selection（Best-of-N 選擇）的實驗中，SplitTester 透過執行回饋（Execution Feedback）迭代生成 discriminative test cases（區分性測試案例），有效分離行為相近的 candidate scripts（候選腳本）。文中指出，SplitTester 在此領域的 Best-of-N 選擇表現上顯著優於基線方法。這顯示：僅比對程式碼表面特徵不足以篩選出正確腳本，而必須透過 DRC Engine（DRC 引擎）實際執行並觀察 violation outputs（違規輸出），才能可靠地進行 program selection（程式選擇）。此外，資料集中 310 條真實規則與 690 條合成規則的混合設計，讓實驗同時驗證了方法在已知製程規則與複雜假設情境下的泛化能力。

#### 與現有研究的比較

相較於現有基準測試（Benchmark），Rule2DRC 在規模與評估方式上均有重大突破。既有基準通常僅含不到 200 對規則與腳本，且多以 code similarity（程式碼相似度）作為評估指標，而非執行正確性；此外，許多資料集因涉及專利設計規則（Design Rules）與佈局資料而未公開。Rule2DRC 不僅將資料量擴充至千級任務與萬級 evaluation chip layouts（評估晶片佈局），更採用 execution-based scoring（基於執行的評分），並完整開源評估流程（Evaluation Pipeline）。

在方法層面，現有的 Machine Learning-Based Methods（機器學習方法）大致可分為兩類：一類如 Zhu et al. (2022; 2023) 與 Abdelmalak et al. (2025)，雖運用 LLM Agents（大型語言模型代理）或檢索增強生成技術進行 DRC Script Synthesis（DRC 腳本合成），但完全忽略 execution feedback（執行回饋）；另一類如 DRC-Coder，雖引入執行回饋，卻假設 agent 在生成階段即可存取 labeled test layouts（標記測試佈局），此設定在實務上往往難以成立。Rule2DRC 移除了這項不切實際的假設，僅允許 agent 接收 natural language (NL) rules（自然語言規則）或 NL description（自然語言描述），並在後續透過獨立的 evaluation pipeline 驗證執行結果。

SplitTester 與其他 tester agent（測試代理）相比，其核心差異在於「維持完整候選池並主動切分模糊群組」。CodeMonkey 僅針對 top-3 candidates 進行區分，容易在候選腳本眾多時遺漏潛在最佳解；S* 則傾向於對已分離的群組繼續生成測試，造成測試預算的浪費。SplitTester 透過反覆切割最大群組，最大化 discriminative test cases（區分性測試案例）的資訊增益。

然而，本研究仍存在若干限制：首先，所有執行均基於 KLayout DRC Engine（DRC 引擎），與業界主流的 SVRF、Calibre 等商業引擎在語法與行為上仍有落差；其次，SkyWater 130nm 屬於較成熟的製程節點，先進製程（如 7nm 及以下）的設計規則（Design Rules）數量與複雜度將大幅提升；最後，無論是腳本生成或 SplitTester 中的 Judge LLM，皆依賴外部大型語言模型 API，其隨機性與不可完全掌控的特性，可能對 reproducibility 造成挑戰。

#### 可重現性評估

Rule2DRC 在可重現性（Reproducibility）方面採取了積極的開源策略。作者已將完整程式碼釋出於 https://github.com/snu-mllab/Rule2DRC，並採用開源的 KLayout 作為 DRC Engine（DRC 引擎），搭配業界標準的 GDSII 格式處理 chip layouts（晶片佈局）。資料集中 310 條真實設計規則（Design Rules）來自開源的 SkyWater 130nm PDK，降低了取得門檻；13,921 個 evaluation chip layouts（評估晶片佈局）與對應的 violation labels（違規標籤）亦一併提供，使其他研究者能完整復現 execution-based scoring（基於執行的評分）流程。

不過，仍有數項因素可能影響完全的重現：第一，690 條合成規則的生成演算法與參數設定雖在論文中提及，但具體的隨機種子與資料產生器細節需仰賴開源程式碼的完整度；第二，論文中的 LLM Agents（大型語言模型代理）與 SplitTester 內的 Judge LLM 極可能呼叫如 GPT-4 等商業 API，這些模型的版本更新、溫度參數（temperature）與 prompt 設計細節，將直接影響 candidate scripts（候選腳本）的生成品質與最終選擇結果，而模型權重（model weights）通常無法公開取得；第三，Best-of-N Selection（Best-of-N 選擇）需要多次取樣與執行，運算成本較高，對於資源有限的研究團隊可能構成門檻。儘管如此，相較於過往未公開或僅以 code similarity（程式碼相似度）評估的基準，Rule2DRC 在透明度與可重現性上已邁出重要一步。

#### 未來研究方向

1. 先進製程節點擴展：當前資料集主要基於 SkyWater 130nm，未來可朝向 7nm、5nm 乃至 3nm 等先進製程節點擴充 design rules（設計規則）。這些節點的 geometry-based design rules（幾何設計規則）更為繁複，將對 DRC Script Synthesis（DRC 腳本合成）與 execution-guided test generation（執行導向測試生成）提出更高挑戰。

2. 多引擎相容性：目前評估流程（Evaluation Pipeline）綁定 KLayout，未來可開發跨 DRC Engine（DRC 引擎）的抽象層，支援 SVRF、Calibre 等工業標準語言，驗證方法在不同執行環境下的泛化能力。

3. 從選擇到除錯的閉環：SplitTester 目前聚焦於 program selection（程式選擇），下一步可結合 debugging（除錯）機制，讓 LLM Agents（大型語言模型代理）在取得 execution feedback（執行回饋）後，不僅挑選最佳腳本，更能自動修正錯誤候選腳本，形成「生成—測試—修復」的自主循環。

4. 開源模型微調：降低對商業 LLM API 的依賴，針對 DRC 領域微調開源大型語言模型，使其具備更穩定的 DRC Script（DRC 腳本）生成能力，並釋出模型權重以提升可重現性。

5. 形式驗證結合：將 execution-based scoring（基於執行的評分）與形式驗證（Formal Verification）結合，不僅在有限的 evaluation chip layouts（評估晶片佈局）上測試，更嘗試證明腳本對於特定規則類別的完備性與正確性。

6. 主動式測試生成：將 SplitTester 的 discriminative test cases（區分性測試案例）生成機制與主動學習（Active Learning）結合，以最少量的 labeled test layouts（標記測試佈局）達到最大的區分效果，降低評估成本。

7. 多模態輸入：除了 natural language (NL) rules（自然語言規則）外，可探索將佈局圖像或結構化幾何資訊一併輸入 LLM Agents（大型語言模型代理），利用多模態感知強化對複雜幾何限制的理解。

8. 跨晶圓廠遷移學習：研究不同 foundry 的 design rules（設計規則）之間的共通性，發展可跨製程節點與跨廠商遷移的 DRC Script Synthesis（DRC 腳本合成）模型，縮短新製程導入時的 DRC deck 開發週期。

## 論文問答

**Q1：為什麼將自然語言設計規則轉換為可執行的 DRC 腳本是一個重要的研究問題？**
A：在晶片製造前，佈局必須符合數千條由製程節點決定的幾何設計規則，而設計規則檢查（DRC）正是透過在佈局上執行 DRC 腳本來強制執行這些約束。然而，將高層次的自然語言規格轉譯成正確且可執行的 DRC 腳本極度耗費人力，並且需要具備專業領域知識的工程師才能完成。隨著製程技術微縮至 7 奈米及以下，設計規則的數量與複雜度大幅增加，使得手動撰寫與驗證 DRC 腳本成為流程中的重大瓶頸，延長了製程轉移的週轉時間並提高了維護成本。

**Q2：現有的 DRC 腳本合成基準測試與機器學習方法存在哪些主要缺陷？**
A：現有的基準測試普遍存在評估規模過小的問題，通常只有不到 200 組規則與腳本配對，而且許多研究僅以表面化的程式碼相似度來評估腳本品質，而非實際執行後的功能正確性。此外，過往的機器學習方法要不是完全忽略 DRC 引擎提供的執行回饋，就是必須將已標記的測試佈局作為代理程式的輸入，這在實務上難以取得且限制了方法的通用性。這些限制導致現有方法難以準確衡量腳本在真實晶片佈局上的執行正確性，也無法有效利用執行結果來迭代改進合成品質。

**Q3：Rule2DRC 的推出對於 DRC 腳本合成領域為何具有關鍵意義？**
A：Rule2DRC 是首個大規模且開源的 DRC 腳本編碼代理基準測試，包含 1,000 項規則到腳本的任務以及 13,921 個用於執行導向評分的評估晶片佈局，規模比現有基準大上一個數量級。該基準提供了一套完整的評估流程，能夠在不將評估佈局提供給代理作為輸入的前提下，透過 DRC 引擎的實際執行結果來衡量生成腳本的功能正確性。這不僅解決了過往基準資料集過小、評估指標偏離實際功能正確性的問題，也為後續研究提供了一個標準化且可重現的測試平台，推動大型語言模型代理在電子設計自動化領域的發展。

**Q4：Rule2DRC 基準測試的整體架構與評估流程是如何設計的？**
A：如圖 1 所示，Rule2DRC 的每一項任務都包含一條自然語言設計規則、一個真值 DRC 腳本、一組評估晶片佈局，以及每個佈局對應的違規標籤。大型語言模型代理僅根據自然語言描述生成可執行的 DRC 腳本，隨後評估系統將該腳本與真值腳本分別在相同的評估佈局上執行，並比較兩者輸出的違規結果是否一致。這種設計確保了評分完全基於執行正確性，而非僅比對程式碼文字，同時也確保代理在生成腳本時無法直接存取評估佈局，從而更貼近真實工程場景。

**Q5：SplitTester 的核心運作機制為何？它如何解決候選腳本難以區分的問題？**
A：SplitTester 是一個利用執行回饋來進行程式選擇的測試代理，其創新之處在於維護完整的候選腳本池，並根據當前測試佈局上的執行輸出模式將候選腳本分群。當多個候選腳本在所有現有測試上都產生完全相同的輸出時，SplitTester 會主動生成額外的區分性測試案例，以「分裂」這些先前無法區分的群集，直到測試預算耗盡為止。最後，再由一個評判用的大型語言模型根據所有具區分性的測試結果，從最頂尖的候選中選出最佳腳本，這種機制顯著提升了 Best-of-N 選擇的準確度。

**Q6：相較於其他測試生成基線方法，SplitTester 在設計上做出了哪些關鍵的差異化選擇？**
A：與 CodeMonkey 僅嘗試區分前三名候選腳本的做法不同，SplitTester 從一開始就保留並評估完整的候選池，確保不會過早排除潛在的正確解答。此外，相較於 S* 等方法傾向於從已經被初始測試分開的群組中生成額外測試，SplitTester 則專注於針對仍然無法區分的大型群集生成新的測試佈局，從而最大化每次測試的資訊增益。這種設計選擇使得 SplitTester 能夠更有效地利用有限的測試預算，在候選腳本間找出最細微的行為差異，進而選出功能正確性最高的腳本。

**Q7：Rule2DRC 的資料集組成與規模相較於現有基準有何具體優勢？**
A：Rule2DRC 收錄了 310 條來自各種製程節點的真實世界設計規則，以及 690 條額外的合成規則，這些合成規則涵蓋了現代先進製程中更複雜的多重約束情境，總計達到 1,000 項規則到腳本的任務。在評估資源方面，該基準提供了 13,921 個評估晶片佈局，整體規模比現有基準大上一個數量級，能夠更全面地檢驗代理的泛化能力。更重要的是，Rule2DRC 使用 KLayout 作為 DRC 引擎，並以業界標準的 GDSII 格式表示佈局，確保評估環境貼近實際的電子設計自動化流程。

**Q8：SplitTester 在 Best-of-N 候選腳本選擇任務上取得了什麼樣的效能表現？**
A：實驗結果顯示，SplitTester 在 Best-of-N 選擇設定下顯著優於其他測試代理基線方法，能夠有效地從大量候選腳本中挑選出功能正確的解決方案。透過不斷生成區分性測試案例來分裂無法區分的候選群集，SplitTester 大幅提高了最終選定腳本的執行正確性。這項成果證明了執行導向的測試生成策略在 DRC 腳本合成領域具有實質的效益，能夠彌補單純依靠大型語言模型生成多樣本時品質不穩定的問題。

**Q9：從 SplitTester 的設計中，我們可以觀察到哪些關鍵元件對整體效能的貢獻最為重要？**
A：雖然文中未以獨立表格呈現傳統意義上的消融實驗，但從方法論的比較可以推論，維護「完整候選池」而非僅關注前幾名候選，是避免過早排除正確解答的關鍵因素。此外，「動態分裂群集」的策略——即持續針對最大且無法區分的群集生成新測試——確保了測試預算被用在最具資訊價值的地方，而非浪費在已分離的群組上。最後，引入一個獨立的評判大型語言模型來綜合所有區分性測試的結果進行最終選擇，也為整個流程提供了更高層次的語意理解與決策能力，這些設計環環相扣，共同促成了效能的提升。

**Q10：Rule2DRC 與 SplitTester 在實際的半導體設計流程中可能應用於哪些具體場景？**
A：在實務上，當半導體廠商導入新的製程節點時，必須將大量的自然語言設計規格手動轉譯為 DRC 腳本，Rule2DRC 所評估的代理能力可直接應用於加速這項繁瑣的初始腳本開發工作。此外，當設計規則因製程微縮而變得更加複雜時，工程師可以利用 SplitTester 這類執行導向的測試代理，從大型語言模型生成的多個候選腳本中自動篩選出功能正確的實作，減少人工除錯的負擔。這對於需要頻繁進行製程轉移或維護大量 DRC 規則檔案的設計團隊而言，能夠顯著縮短開發週期並降低因人為疏失導致的設計瑕疵風險。

**Q11：將 Rule2DRC 的技術整合到商業 EDA 工具中時，需要考量哪些產品化因素？**
A：首先，商業 EDA 環境通常使用專有的 DRC 引擎與腳本語法，因此需要確保大型語言模型代理能夠適應不同廠商的特定語言與執行環境，而不僅限於開源的 KLayout。其次，在企業內部部署時，設計規則與佈局資料往往涉及高度機密的製程資訊，必須建立嚴格的資料隔離與安全機制，避免在呼叫外部模型 API 時發生資料外洩。最後，為了讓工程師信任並採用自動生成的腳本，工具必須提供透明的執行回饋與視覺化的違規比對介面，讓使用者能夠理解 SplitTester 的選擇依據並在必要時進行人工覆核。

**Q12：這項研究對電子設計自動化（EDA）領域與大型語言模型代理的發展可能帶來哪些深遠影響？**
A：Rule2DRC 為 EDA 領域建立了一個標準化的大規模評估平台，首次將執行正確性作為 DRC 腳本合成的核心評量指標，這有望引導後續研究從單純的程式碼生成轉向更重視功能驗證的範式。同時，SplitTester 展示了將領域特定工具（如 DRC 引擎）作為大型語言模型代理的外部工具進行深度整合的價值，為其他 EDA 子領域（如佈局繞線、靜態時序分析）提供了可複現的代理設計範本。長遠來看，這類結合執行回饋與自動化測試生成的代理框架，將有助於推動 EDA 工具鏈的智能化，降低先進製程節點的設計門檻與成本。

**Q13：作者在本研究中承認了哪些方法或基準測試上的限制？**
A：儘管 Rule2DRC 已經比現有基準大上一個數量級，但 1,000 項任務與 13,921 個評估佈局相對於實際產業中數以萬計的設計規則而言，規模仍然有限，可能無法涵蓋所有極端或罕見的幾何約束組合。此外，目前的評估流程雖然不需要將評估佈局提供給代理作為輸入，但生成高品質的區分性測試佈局本身仍依賴大型語言模型的能力，其生成效率與測試覆蓋率可能存在上限。最後，該基準目前主要基於 KLayout 引擎與 GDSII 格式，對於使用其他商業 DRC 引擎（如 SVRF）的業界環境，仍需額外的工程努力來進行移植與驗證。

**Q14：在哪些情況下，SplitTester 或 Rule2DRC 的評估流程可能會遭遇失敗或表現不佳？**
A：如果大型語言模型生成的候選腳本全部存在相同類型的系統性錯誤，並且在現有與生成的測試佈局上都呈現一致的錯誤輸出，那麼 SplitTester 將難以透過執行回饋來區分這些錯誤候選，導致最終選擇仍然失準。同樣地，當設計規則涉及極為細微的幾何條件或需要跨層複雜互動時，自動生成的測試佈局可能無法充分觸發所有邊界情況，使得評估流程誤判腳本的正確性。此外，若自然語言規則描述本身含糊不清或存在多重詮釋，即使腳本在執行層面通過測試，也可能與工程師的原始設計意圖不符，這是單純依賴執行比對難以完全捕捉的語意鴻溝。

**Q15：基於 Rule2DRC 與 SplitTester 的成果，未來研究可以朝哪些方向進一步延伸？**
A：未來研究可以探索將執行導向的回饋機制進一步整合到生成階段，發展出能夠在生成 DRC 腳本時就主動參考 DRC 引擎輸出的迭代式大型語言模型代理，而非僅在後期的候選選擇階段使用回饋。另一個方向是擴展基準測試的規模與多樣性，納入更多來自先進製程節點的真實設計規則，並支援多種商業 DRC 引擎與佈局格式，以提升評估結果在產業界的通用性。此外，結合形式化驗證方法或神經符號推理技術，來補足執行導向測試可能遺漏的邊界情況，並進一步縮小自然語言規格與可執行程式碼之間的語意差距，也是極具潛力的後續研究方向。

## 實務應用指南

### 適用場景

**1. 先進製程節點 DRC 腳本自動生成**  
在 7nm 及以下製程，幾何設計規則的數量與複雜度急遽增加。晶圓廠或設計團隊可將自然語言規格書輸入 LLM 代理，自動產生可執行的 DRC 腳本，縮短新製程節點的開發週期。

**2. PDK 遷移與製程設計套件驗證**  
當晶片設計從舊製程遷移至新製程時，需重新撰寫大量 DRC 腳本。透過 Rule2DRC 的執行導向評估流程，團隊可快速驗證自動生成腳本在大量評估晶片佈局上的功能正確性，確保 PDK 品質。

**3. 設計規則除錯與回歸測試**  
對於現有 DRC 腳本庫，可利用 SplitTester 針對語意模糊或執行結果不一致的候選腳本生成區分性測試案例，協助工程師定位邊界條件錯誤，並建立持續整合（CI）環境中的自動回歸測試。

**4. 跨部門規格與執行檔同步維護**  
設計規則常以自然語言撰寫於規格書，而執行檔則由不同團隊維護。本方法可作為「規格到程式碼」的同步橋樑，當自然語言描述更新時，自動產生對應 DRC 腳本並透過執行回饋驗證一致性。

**5. EDA 工具鏈智慧化擴充**  
EDA 廠商可將此技術整合為外掛模組，讓使用者在圖形介面中輸入自然語言設計規則，由後端 LLM 代理呼叫 DRC 引擎即時生成並驗證腳本，降低使用者撰寫領域特定語言的門檻。

**資料需求**  
- 自然語言設計規則語料庫（至少數百條規則與對應真值 DRC 腳本對，用於微調或評估基準）  
- 評估晶片佈局（GDSII 格式）與其違規標籤，用於執行導向評分  
- 現有 DRC 語法文件與領域特定語言（如 KLayout Ruby DSL 或 SVRF）範例庫

**運算資源**  
- LLM 推論端點：具備足夠 VRAM 的 GPU 叢集（若使用開源模型進行本地微調與 Best-of-N 取樣），或商用 LLM API 配額  
- DRC 執行環境：高效能 CPU 叢集與大容量記憶體，因 DRC 引擎執行於大量佈局上屬於計算密集型任務  
- 儲存空間：需容納萬級以上的佈局檔案與執行產生的違規輸出

**技能需求**  
- 熟悉 EDA 流程與設計規則檢查語義（幾何設計規則、佈局層次關係）  
- 具備 KLayout 或其他 DRC 引擎的操作經驗，能解析違規輸出  
- LLM 代理開發能力（提示工程、工具使用架構、Best-of-N 選擇策略）  
- Python 與版本控制經驗，用於建構評估流程與資料管線

### 實作步驟建議

**步驟一：建構領域資料集與執行環境**  
收集內部自然語言規則與歷史 DRC 腳本，轉換為 Rule2DRC 格式。部署 KLayout 作為 DRC 引擎，建立 GDSII 佈局資料庫，並確保每筆資料均具備真值違規標籤以供執行正確性比對。

**步驟二：建立 LLM 代理推論管線**  
開發具備工具使用能力的 LLM 代理，使其能接收自然語言描述並生成 DRC 腳本。設計提示模板納入領域語法範例與操作符說明，並實作 Best-of-N 取樣機制以產生多組候選腳本。

**步驟三：導入執行導向評估機制**  
捨棄僅比對程式碼相似度的傳統評估方式，改為將候選腳本與真值腳本分別執行於相同評估晶片佈局上，比較兩者的違規輸出是否一致，以此作為功能正確性的唯一標準。

**步驟四：部署 SplitTester 進行程式選擇**  
針對 Best-of-N 產生的候選腳本池，實作 SplitTester 代理。利用初始測試佈局執行候選腳本，依輸出模式分群；對無法區分的群組，迭代生成額外的區分性測試案例，直至預算耗盡，最終由 Judge LLM 自頂尖候選中選出最佳腳本。

**步驟五：整合至設計流程並建立人機協作迴路**  
將自動生成與驗證後的 DRC 腳本導入現有 EDA 工具鏈，設定人工複核閘道。對於通過執行驗證的腳本，自動更新至規則庫；對於未通過的案例，回饋錯誤訊息至代理以進行除錯與迭代。

### 潛在風險與注意事項

**執行正確性與程式碼相似度的認知落差**  
許多團隊習慣以程式碼相似度（如 BLEU、Code-BLEU）評估生成品質，但 DRC 腳本即使語法結構不同，也可能在功能上等價；反之，微小語法差異可能導致完全不同的違規輸出。務必以 DRC 引擎實際執行結果作為評分依據。

**佈局資料機密性與資安控管**  
評估晶片佈局通常涉及晶圓廠機密。實作時應在隔離的內網環境部署 DRC 引擎與評估流程，避免將敏感佈局上傳至外部 LLM API；若使用第三方模型，僅傳輸自然語言規則與腳本程式碼，佈局執行保留在本地。

**LLM 幻覺與領域語法錯誤**  
LLM 可能生成看似合理但實際無效的 DRC 語法，或誤解幾何約束（如將「enclosed by」與「inside」混淆）。建議在代理中加入語法檢查器與 DRC 引擎的錯誤回饋迴路，並透過少樣本提示（few-shot）強化語法正確性。

**測試覆蓋率不足導致的偽陽性通過**  
若評估佈局數量過少或場景同質性過高，候選腳本可能在現有測試上與真值一致，卻在實際設計中失效。Rule2DRC 雖提供大規模佈局，但實務上仍需確保測試集涵蓋邊角案例（corner cases），並持續擴充 SplitTester 生成的區分性測試案例。

**計算成本與延遲**  
Best-of-N 搭配執行導向驗證意味著需對大量候選腳本執行 DRC，在先進製程的大型佈局上可能耗時甚鉅。建議設定嚴格的候選數量上限與測試預算，並採用平行化執行與快取機制降低重複計算。

### 與其他技術的整合建議

**檢索增強生成（RAG）**  
將現有 DRC 腳本庫與自然語言規則文件向量化，建立檢索索引。在 LLM 代理生成腳本前，先檢索相似歷史規則與對應程式碼作為上下文，可顯著降低語法錯誤率並加速收斂。

**傳統 EDA 工具鏈**  
透過標準化介面（如 KLayout Python API 或 SVRF 轉換器）將生成結果無縫匯入現有 Calibre、IC Validator 等簽核流程。保留人工專家在最終簽核（sign-off）前的審查權限，形成「AI 生成—自動驗證—專家確認」的三層防線。

**版本控制與知識管理系統**  
將自動生成的 DRC 腳本與其對應的自然語言描述、測試佈局與執行結果一併存入 Git 或 PLM 系統。當設計規則更新時，可追溯歷史版本差異，並利用 SplitTester 的測試案例作為回歸測試資產。

**持續整合／持續部署（CI/CD）**  
在晶片設計的 CI/CD 管線中設立 DRC 腳本自動生成閘道。當規格書發生異動時，觸發 LLM 代理重新生成腳本，並以 Rule2DRC 評估流程進行自動化驗證，僅在通過所有執行測試後才合併至主分支。

本研究的核心貢獻在於提出大規模的執行導向基準測試，並揭示程式碼相似度評估在 DRC 領域的不足。建議深入分析 Rule2DRC 的資料建構方式、13,921 筆評估晶片佈局的標註邏輯，以及 SplitTester 與其他測試生成基準（如 CodeMonkey、S*）在資訊增益與樣本效率上的比較。

**給產品經理**  
本技術直接對應縮短先進製程 DRC 腳本開發週期與降低人力成本的商業目標。閱讀時請聚焦於 Rule2DRC 相較現有方案在資料規模與評估真實性上的優勢，以及 SplitTester 如何提升 Best-of-N 選擇的準確率；評估導入時需權衡 LLM 推論與 DRC 執行的運算成本，並規劃與現有簽核流程的人機協作介面。
