## 摘要翻譯

我們提出一個基準測試（FVSpec），用於評估 AI 模型與代理在真實世界軟體的形式驗證（Formal Verification, FV）任務上的表現。我們首先從真實世界的 Python 程式碼儲存庫中爬取（scrape）11,039 個屬性化測試（Property-Based Tests, PBTs），然後自動將其中 2,772 個（25%）轉譯（transpile）為 9,415 個帶有 sorry 佔位符（sorry placeholder）的 Lean 4 規格（specifications）（約每個 PBT 3 種形式化（formalization）；當沒有任何嘗試在品質指標（quality metric）上佔優時，我們保留多個嘗試）。將 PBT 轉譯為 Lean 規格具有挑戰性：它需要在 Lean 中建模 Python 語意（Python semantics），推斷命令式屬性化測試（imperative PBT）中編碼的邏輯屬性（logical property），並處理在較少使用的語言中進行相依類型程式設計（dependently-typed programming）的固有困難。我們提出一個用於將 PBT 轉譯為 Lean 規格的三代理 LLM 流程（Three-Agent LLM Pipeline），評估覆蓋率指標（coverage metric）與品質指標，並提供使用多種自動化與基於模型的方法進行證明生成（proof generation）的基準線（baseline）。所有程式碼（爬蟲（scraper）與代理）以及資料（PBT 與 Lean 規格）皆為開源（open source）。我們的基準測試旨在推動 AI 輔助形式驗證（AI-Assisted Formal Verification）真實世界軟體（real-world software）這一尚未充分探索領域的研究進展，隨著 AI 產出全球越來越多的程式碼，該問題日益受到關注。

### 核心貢獻（3～5點）
- 建構首個專注於真實世界軟體形式驗證的大規模基準測試 FVSpec，涵蓋 11,039 個爬取自真實 Python 專案的屬性化測試。
- 提出三代理 LLM 流程，成功將 2,772 個 PBT 自動轉譯為 9,415 個 Lean 4 規格，並產出多版本候選以利品質比較。
- 系統性評估覆蓋率指標與品質指標，並提供多種自動化與基於模型之證明生成方法的基準線。
- 完整開源所有程式碼（爬蟲與代理）與資料（PBT 與 Lean 規格），促進後續研究重現與延伸。
- 填補 AI 輔助形式驗證真實世界軟體此一尚未充分探索領域的研究空缺。

### 適合對象
從事 AI 輔助形式驗證、自動化定理證明、程式語言轉譯、軟體工程 AI、以及屬性化測試研究的學者與工程師；亦適合關注 AI 安全（AI Safety）與大語言模型代理（LLM agent）能力評估的研究團隊。

## 深度分析

#### 方法論解析

FVSpec 的方法論核心在於建立一條從「真實世界 Python 程式碼」到「Lean 4 形式驗證挑戰」的端到端轉譯管線 (pipeline)，其架構可分為兩個主要階段：FVSpec:PBT（屬性化測試語料庫建構）與 FVSpec:FV（形式驗證挑戰生成）。

**第一階段：PBT 語料庫建構（FVSpec:PBT）**

此階段採用多層過濾策略。首先透過 GitHub Discovery 從 18,494 個公開儲存庫 (repository) 中進行初步探索，接著使用 ripgrep 工具以 `@given` 裝飾器作為識別標記，鎖定使用 Hypothesis 框架的 Python 檔案。經過授權篩選器 (License Filter) 排除 copyleft（著佐權）授權後，從 7,413 個獨立 PBT 中保留 497 個儲存庫的內容。這個設計反映了對授權相容性的重視——僅保留寬鬆授權的程式碼以利後續開源釋出。

**第二階段：Lean 形式化轉譯（FVSpec:FV）**

此階段採用三代理 LLM 流程 (Three-Agent LLM Pipeline)，包含以下子步驟：

1. **函式探索 (Function Discovery)**：使用 tree-sitter（程式碼語法解析工具）對 Python 程式碼進行靜態分析，自動識別被測試函式及其依賴項。
2. **代理式轉譯 (Agentic Transpilation)**：由 LLM 代理將 Python 實作翻譯為 Lean 4 的 `Impl.lean`，並將 PBT 轉化為 `Spec.lean` 中的定理陳述。
3. **LSP 修復迴圈 (LSP Repair Loop)**：利用 Lean 的 Language Server Protocol 對轉譯結果進行迭代修復，處理編譯錯誤、未知識別符 (unknown identifier) 與型別不符 (type mismatch) 等問題。
4. **後製處理 (Post-Production)**：進行合併、驗證與去重複 (deduplication)，並依品質指標對多重轉譯嘗試進行評分。

**翻譯過程面臨的三大挑戰**

論文明確指出將 PBT 轉譯為 Lean 規格的三個核心難題：

- **Python 語意建模 (Python Semantics)**：Lean 4 是基於相依類型 (dependently-typed programming) 的純函式語言，與 Python 的命令式語意存在根本差異。例如，論文中 `isort` 範例顯示 Python 使用 `bisect.insort` 進行原地插入，而 Lean 版本則需重新定義為純函式的 `insert` 操作。
- **邏輯屬性推斷 (Logical Property Inference)**：命令式 PBT (Imperative PBT) 中以斷言 (assert) 形式表達的屬性，需被提煉為 Lean 中的定理陳述。論文中 `test_isort` 的兩個斷言——「輸出已排序」與「輸出是輸入的排列」——分別被形式化為 `(isort l).Sorted LE.le` 與 `(isort l).Perm l` 兩個獨立定理。
- **無意義定理的產生**：論文坦承管線會產生三類「well-formed but useless」的問題：(i) Unit 型態的平凡定理（當代理無法恢復函式回傳型態時的後退策略）；(ii) 型別錯誤或未解析符號的定理；(iii) 規格定理洩漏至實作檔案的情況。

值得注意的是，論文採用「保留多重嘗試」的策略——當沒有任何單一轉譯在品質指標上佔優時，平均每個 PBT 保留約 3 個形式化版本（總計 9,415 個 FVC 來自 2,623 個 PBT，平均每個 PBT 約 8 個 FV 挑戰）。這種「保留多樣性」的設計哲學體現了對當前 LLM 轉譯不確定性的務實態度。

#### 實驗數據解讀

**規模與轉譯成功率**

從原始資料規模來看，整體漏斗效應 (funnel effect) 十分顯著：18,494 個儲存庫 → 7,413 個獨立 PBT（40% 留存率）→ 2,623 個成功轉譯的 PBT（35% 轉譯成功率）→ 9,415 個 FVC 樣本。最終僅 25% 的 PBT 能成功轉譯為 Lean 規格，這個數字反映了真實世界軟體形式化的固有難度——大多數 PBT 涉及複雜的 Python 標準庫互動、動態型別或外部依賴，難以直接映射到 Lean 的純函式語意。

**基準模型表現**

論文報告了三個模型的基準表現：Claude Sonnet 4.6、Claude Opus 4.7 與 GPT 5.4。在「簡單」題目上平均成功率約 70%，在「困難」題目上約 49%。這個差距（約 21 個百分點）揭示了題目難度分層的有效性——「簡單」題目可能涉及標準資料結構操作（如列表排序），而「困難」題目則可能涉及複雜的數學性質（如數論恆等式）或涉及多個元件互動的系統性質。

**評分機制的設計意涵**

評分採用二元標準：「證明是否仍包含 sorry 佔位符或特殊用途公設」。這個設計避免了部分給分的模糊性，但也意味著一個幾乎完成但缺少最後一步的證明與完全空白提交的得分相同。這對未來的研究既是挑戰（需要更細粒度的評估）也是機會（明確的成功標準便於自動化評分）。

**品質指標的多重性**

論文提到「品質指標」但未在提供的文本中詳列具體指標。從上下文推測，可能包括：編譯成功率、型別正確性、語意保真度（如 `Perm` 關係是否正確表達）等。多重轉譯的保留策略暗示品質指標之間可能存在權衡 (trade-off)——沒有一個轉譯在所有指標上同時最優。

#### 與現有研究的比較

**與既有基準的差異化定位**

論文明確將 FVSpec 定位為填補現有基準的空白：

| 既有基準 | 限制 | FVSpec 的改進 |
|---------|------|--------------|
| Loughridge et al. [2024]、Ravi and Coblenz [2025] | 規模過小 | 提供 9,415 個樣本 |
| Glazer et al. [2024] | 聚焦於數學而非軟體驗證 | 直接源自真實軟體專案 |
| Chakraborty et al. [2025] | 專家驅動的驗證專案 | 反映一般軟體開發的引導式驗證 (bootstrapping verification) 需求 |

這個定位策略凸顯了 FVSpec 的核心價值主張：「從第一天就為驗證而設計的軟體」與「需要從零開始建立驗證的真實軟體」之間存在本質差異——後者需要推理黑盒外部系統 (black-box external systems) 與多語言、多架構元件的互動。

**與 FV APPS（Dougherty and Mehta [2025]）的關係**

兩者採用相似的方法論框架：將命令式程式碼轉化為形式化規格，再提升為定理。然而，FV APPS 的源頭是 APPS 競賽程式碼（competitive programming），而 FVSpec 的源頭是真實世界的 Hypothesis PBT。這差異至關重要——APPS 程式碼通常設計為自包含且語意明確，而真實世界的 PBT 涉及實際軟體工程的複雜性（如外部 API 呼叫、副作用處理）。從這個角度，FVSpec 代表了更困難但更實用的任務設定。

**限制與不足**

儘管定位明確，FVSpec 仍存在以下限制：

1. **語言侷限性**：僅涵蓋 Python 生態，未涵蓋其他主流語言（如 Rust、TypeScript）的 PBT 框架。
2. **Lean 4 的單一性**：雖然 Lean 正成為 AI 驗證的事實標準，但僅支援單一證明輔助工具限制了基準的通用性。
3. **25% 轉譯成功率**：意味著 75% 的 PBT 被排除，這可能引入選擇偏差 (selection bias)——被成功轉譯的 PBT 可能偏向較簡單的程式碼模式。
4. **基準模型的有限性**：僅測試三個模型，且未涵蓋專門為證明設計的模型（如 LeanDojo、ReProver 等）。

#### 可重現性評估

**開源釋出的完整性**

論文承諾釋出完整的管線元件與資料集，採用 MIT/Apache 雙重授權 (dual license)，這在學術基準中屬於較為寬鬆的授權選擇，有利於商業應用。具體釋出內容包括：

- **爬蟲 (Scraper)**：GitHub Discovery 與授權篩選的完整實作
- **依賴提取器**：從 Python 程式碼中識別被測試函式的工具
- **代理 (Agent)**：三代理 LLM 流程的實作
- **後製腳本**：驗證、去重複與評分邏輯
- **資料集**：7,413 個 PBT 與 9,415 個 Lean FVC 樣本

**資料釋出的時序**

值得注意的是，FVSpec:PBT 於 2026 年 1 月在 HuggingFace 釋出，早於 Hypothesis Corpus DeV [2026]。這個時序引發一個問題：兩者之間是否存在資料重疊或互補關係？論文中未明確說明差異化，但暗示 FVSpec 採用了更嚴格的授權篩選（排除 copyleft）。

**可重現性的潛在挑戰**

1. **LLM 隨機性**：三代理流程涉及 LLM 呼叫，其隨機性可能導致每次轉譯結果不同。論文中「保留多重嘗試」的策略部分緩解了這個問題，但完整重現需要固定隨機種子或記錄所有 LLM 互動。
2. **GitHub 狀態變化**：爬取的 PBT 可能因儲存庫被刪除、修改或重新授權而無法重現。論文中包含 URL 與授權資訊是良好的實踐，但仍存在時間衰減風險。
3. **評分環境**：使用 `lake build` 進行編譯驗證，但未明確說明 Lean 版本、依賴項與數學庫版本，這些都可能影響評分結果。

#### 未來研究方向

**短期可探索方向**

1. **提升轉譯成功率**：當前僅 25% 的 PBT 能成功轉譯，研究如何處理複雜 Python 模式（如生成器、裝飾器、上下文管理器）將大幅擴展基準覆蓋面。
2. **細粒度評分機制**：當前的二元評分（有無 sorry）過於粗糙，可發展基於證明步驟數、戰術使用或證明長度的連續評分指標。
3. **錯誤分析與分類**：對 75% 失敗的 PBT 進行系統性錯誤分析，識別最常見的失敗模式（如特定 Python 函式庫無法映射、複雜邏輯屬性難以形式化），以指導後續改進。

**中期研究方向**

1. **多語言擴展**：將方法論擴展至其他 PBT 框架（如 Rust 的 proptest、QuickCheck 的 Haskell 版本），建立跨語言的形式驗證基準。
2. **多證明器支援**：雖然 Lean 4 是當前焦點，但 Coq、Isabelle/HOL 等證明輔助工具各有優勢。發展翻譯層以支援多目標輸出將提升基準的實用價值。
3. **互動式驗證**：當前設定是「一次性提交證明」，但真實的形式驗證是迭代過程。研究 AI 代理在互動式證明環境（如 Lean 的 VS Code 整合）中的表現將更貼近實際應用。
4. **與程式碼生成整合**：將 FVSpec 與程式碼生成基準（如 HumanEval、MBPP）結合，研究「生成-驗證」閉環中 AI 的自我修正能力。

**長期願景方向**

1. **真實部署驗證**：將 FVSpec 的方法論應用於實際安全關鍵系統（如加密函式庫、分散式系統協定），評估 AI 輔助驗證在工業環境中的可行性。
2. **形式化語意橋接**：發展更系統化的 Python-to-Lean 語意映射理論，而非依賴 LLM 的類比推理。這可能涉及 denotational semantics（指稱語意）或 refinement types（精化類型）的中間表示。
3. **AI 安全應用**：論文開頭提及多個 AI 安全提案依賴形式驗證。FVSpec 可作為評估這些提案可行性的實證基礎——例如，測試 AI 是否能驗證自身產生的程式碼的安全性。
4. **證明複雜度理論**：隨著基準規模擴大，可研究不同類型定理的證明複雜度分布，建立形式驗證任務的計算複雜性分類法。

**方法論反思**

FVSpec 的方法論本身也值得進一步審視。「保留多重轉譯」的策略雖然務實，但可能掩蓋了 LLM 轉譯品質的系統性問題。未來研究可探索：(1) 為何某些 PBT 會產生多個品質相當的轉譯——這反映了任務的內在模糊性還是 LLM 的不確定性？(2) 不同 LLM 在轉譯任務上的失敗模式是否存在系統性差異？這些問題的答案將直接影響 AI 輔助形式驗證的發展路徑。

## 論文問答

**Q1：FVSpec 試圖解決的核心問題是什麼？**
A：FVSpec 試圖解決 AI 模型在真實世界形式驗證任務上缺乏高品質基準測試的問題。現有的基準測試規模太小、過於聚焦於數學而非軟體驗證，或是來自專家驅動的驗證專案，無法反映一般軟體專案中引導式驗證的複雜性。透過從真實的 Python 開源專案中爬取屬性化測試（PBT），並將其轉譯為 Lean 4 形式驗證挑戰，FVSpec 為評估 AI 在自動化軟體驗證能力上提供了更貼近實務的測試場域。

**Q2：為什麼現有的形式驗證基準測試無法滿足需求？**
A：現有基準測試存在三個主要缺陷：規模過小（如 Loughridge 等人 [2024] 與 Ravi 和 Coblenz [2025] 的工作）、偏向數學而非軟體驗證（如 Glazer 等人 [2024] 的工作）、或是源自專家驅動的驗證專案（如 Chakraborty 等人 [2025] 的工作），這些專案從一開始就是為了被驗證而設計的軟體。真實世界的軟體引導式驗證比這困難得多，因為它通常需要推理黑盒外部系統以及多個不同元件（甚至跨語言、跨架構）的互動。因此，需要一個能反映真實軟體開發情境的基準測試，而非僅僅評估「為了被驗證而設計」的程式碼。

**Q3：為什麼 AI 輔助形式驗證對 AI 安全如此重要？**
A：許多 AI 安全提案都建立在以形式驗證實作安全防護的前提上——也就是能夠產生並認證證明的軟體系統。隨著 AI 產生越來越多全球的程式碼，自動化形式驗證成為確保這些程式碼正確性的關鍵手段。然而，目前幾乎沒有證據顯示 AI 能有效自動化驗證流程，因此建立高品質的訓練與評估基準成為推動該領域發展的迫切需求。FVSpec 正是為了填補這一空白而設計，其目標是驅動 AI 輔助形式驗證這一被低估的研究方向的進展。

**Q4：FVSpec 的核心方法論是什麼？**
A：FVSpec 的核心方法論分為兩個階段：首先從 GitHub 上爬取使用 Hypothesis 框架的 Python 屬性化測試，建立 FVSpec:PBT 語料庫；接著透過基於 tree-sitter 的函式探索、代理式轉譯（含 LSP 修復迴圈）以及後製處理（合併、驗證、去重複）等步驟，將 PBT 提升為 Lean 4 的 (實作, 規格) 配對，形成 FVSpec:FV 形式驗證挑戰集。最終從 7,413 個獨立 PBT 中產出 9,415 個 Lean 4 形式驗證挑戰樣本，平均每個 PBT 產生約 3 個形式化版本，這種「保留多個嘗試」的設計反映了真實轉譯過程中的不確定性。

**Q5：三代理 LLM 流程的關鍵創新是什麼？**
A：三代理 LLM 流程的關鍵創新在於將複雜的 Python 到 Lean 轉譯任務分解為可管理的子任務，並透過 Language Server Protocol（LSP）修復迴圈自動修正編譯錯誤。這種代理式設計使得模型能夠在迭代中學習並修正自身的錯誤，模擬人類專家進行證明工程時的反覆除錯過程。此外，流程保留了多個轉譯嘗試（當沒有任何一個在品質指標上明顯勝出時），增加了基準測試的多樣性與挑戰性，這也使得後續的證明生成任務更具實務參考價值。

**Q6：在轉譯過程中做了哪些關鍵的設計選擇？**
A：關鍵設計選擇包括：使用 tree-sitter 進行精確的函式探索以正確識別待測程式碼；採用 ripgrep 進行授權篩選（過濾掉 copyleft 授權）以避免授權爭議；採用 LSP 修復迴圈處理 Lean 編譯錯誤；保留多個形式化嘗試而非僅取最佳結果，以反映真實轉譯的不確定性；以及在後製階段進行嚴格的驗證、去重複與品質分級。這些選擇使得基準測試既具有足夠的規模（9,415 個樣本），又能維持一定的品質標準，同時也為未來的研究提供了可重現的基礎設施。

**Q7：FVSpec 使用了哪些基準測試與評估方法？**
A：FVSpec 本身即是基準測試，其評估對象為 Claude Sonnet 4.6、Claude Opus 4.7 與 GPT 5.4 等先進 AI 模型在 Lean 4 證明生成任務上的表現。每個問題包含四個組成部分：原始 Python 函式、PBT、Lean 實作與帶有 sorry 佔位符的 Lean 定理，AI 的任務是填入正確的證明或反證。評分依據是提交內容能否在 `lake build` 下乾淨編譯，以及證明中是否仍殘留 sorry 或特殊用途的公設，這樣的評估方式直接反映了形式驗證的實務標準。

**Q8：基準評估的關鍵結果為何？**
A：基準評估顯示 Claude Sonnet 4.6、Claude Opus 4.7 與 GPT 5.4 在「簡單」題目上平均成功率約為 70%，但在「困難」題目上平均成功率僅約 49%。這顯示即使是當前最強的 AI 模型，在真實世界的形式驗證任務上仍有顯著的進步空間，特別是在處理複雜的真實世界軟體邏輯時。這一結果凸顯了 AI 輔助形式驗證領域的挑戰性，也證明了 FVSpec 作為基準測試的區辨能力——它能夠有效區分不同難度的任務，並揭示現有模型的具體弱點。

**Q9：FVSpec 進行了哪些消融研究或品質指標分析？**
A：論文分析了覆蓋率與品質指標，包括轉譯成功率（從 11,039 個 PBT 中僅 25% 成功轉譯為 Lean 規格）以及每個 PBT 平均產生約 3 個形式化版本的多樣性。此外，論文詳細討論了轉譯過程中可能產生的三類無意義定理：平凡的 Unit 類型猜想、類型錯誤或未解析符號的定理，以及洩漏到實作檔案中的規格定理。這些分析有助於理解管線的限制與改進方向，也為未來的工作提供了明確的優化目標，例如提升轉譯成功率與減少無意義輸出。

**Q10：FVSpec 能支援哪些實際應用情境？**
A：FVSpec 可用於訓練與評估 AI 模型在自動化形式驗證任務上的能力，這對於需要高可靠性的軟體系統（如安全關鍵系統、加密貨幣協議、嵌入式系統）尤為重要。此外，它也可作為研究 AI 推理能力的測試平台，因為形式證明需要嚴密的邏輯推理與對程式語義的深入理解。隨著 AI 產生更多程式碼，這類工具將成為確保程式碼品質的關鍵基礎設施，特別是在 AI 安全提案中以形式驗證建立安全防護的願景下。

**Q11：在產品化時需要考慮哪些實務因素？**
A：產品化時需考慮的因素包括：授權合規性（FVSpec 採用 MIT/Apache 雙重授權，便於商業使用）、與現有開發流程的整合（Lean 4 證明可作為 CI/CD 的一部分）、對開發者技能的要求（形式驗證仍需專業知識，學習曲線陡峭）、以及成本效益（形式驗證的成本遠高於單元測試）。此外，如何處理真實軟體中常見的黑盒外部系統與跨語言互動，也是產品化必須面對的挑戰，這也是 FVSpec 試圖反映但尚未完全解決的問題。

**Q12：FVSpec 對形式驗證與 AI 安全領域的整體影響為何？**
A：FVSpec 推動了 AI 輔助形式驗證這一被低估但日益重要的研究方向，為該領域提供了首個大規模、源自真實軟體開發的基準測試。透過開源釋出完整的爬蟲、代理與資料集，FVSpec 降低了研究門檻並促進了可重現的研究，這對於學術界與工業界的合作至關重要。隨著 AI 產生更多程式碼，這項工作對於實現 AI 安全提案中以形式驗證建立安全防護的願景至關重要，也為未來 AI 系統的可信度提供了基礎。

**Q13：FVSpec 存在哪些已知的限制？**
A：FVSpec 的主要限制包括：僅 25% 的 PBT 成功轉譯為 Lean 規格，轉譯成功率仍有提升空間；轉譯過程中可能產生無意義的定理（如平凡的 Unit 類型猜想或類型錯誤的定理），需要後製過濾；僅支援 Python 的 Hypothesis 框架，無法涵蓋其他語言或 PBT 框架；以及 Lean 4 作為較少使用的相依類型語言，其學習曲線與生態系統成熟度仍有限。此外，基準測試的品質高度依賴 LLM 的能力，這也意味著隨著模型演進，基準可能需要持續更新。

**Q14：FVSpec 的失敗案例有哪些？**
A：論文明確指出三類失敗案例：(i) 當代理無法恢復函式的返回類型時，會退回到 Unit 類型，導致產生的定理是恆真式（如 `isort lst = ()`），不具任何驗證價值；(ii) 代理可能發明 Lean 中不存在的名稱（如 `permutationOf`）或附加與周圍程式碼不一致的類型簽名，導致 Lean 編輯器拒絕該檔案並產生「unknown identifier」或「type mismatch」等錯誤；(iii) 規格定理可能洩漏到實作檔案中，違反檔案分離的設計原則。這些失敗案例凸顯了 Python 語意建模與相依類型程式設計的固有困難。

**Q15：FVSpec 未來的發展方向為何？**
A：未來發展方向可能包括：擴展支援更多程式語言與 PBT 框架（如 QuickCheck、fast-check 等），以提升基準的通用性；提升轉譯成功率與品質，減少無意義定理的產生；整合更強的證明自動化工具與 AI 模型，以推動證明生成能力的進步；探索如何處理真實軟體中常見的黑盒外部系統與跨語言互動問題；以及將 FVSpec 與其他 AI 安全研究結合，推動形式驗證在實際 AI 系統中的應用，最終實現 AI 安全提案中以形式驗證建立安全防護的願景。

## 實務應用指南

### 適用場景

1. **AI 程式碼助理的「可證明正確性」能力評估**
   將 FVSpec 整合進企業內部的程式碼助手評估流程，作為「生成程式碼是否具備可形式化驗證潛力」的客觀指標。相較於僅以單元測試通過率評估，能更早攔截「看起來能跑、但語意錯誤」的程式碼，特別適合金融交易、醫療器材控制、航電系統等高可靠性領域的內部 AI 工具採購驗收。

2. **開源函式庫的「形式化護欄」建置**
   針對 NumPy、Pandas、Requests 等被廣泛依賴的 Python 函式庫，運行 FVSpec 的爬蟲與轉譯流程，將社群貢獻的 PBT 自動升級為 Lean 4 規格。對開源維護者而言，這能在不改變既有測試習慣的前提下，產出可選用的形式化證明骨架，作為長期安全保證的起點。

3. **AI 安全研究中的「對齊驗證」實驗平台**
   將 FVSpec:FV 作為「AI 是否能自我驗證所寫程式」的測試場，用於研究 AI 是否能在生成程式碼的同時產生對應的形式化證明。這對 Dalrymple 等學者提出的「以形式驗證作為 AI 安全護欄」路線圖，提供可量化的實證基礎。

4. **教育訓練用的「形式化方法入門教材」**
   將 FVSpec 的範例（如 isort 的排序性與排列性證明）整理為漸進式教材，讓學生從熟悉的 Python PBT 過渡到 Lean 4 證明。相較於傳統從 Peano 公理開始的教材，更貼近業界實務，也更容易讓軟體工程背景的學習者入門。

5. **企業內部「遺留系統形式化」先導專案**
   針對難以重寫但又需要高可靠性的遺留 Python 系統，先以 FVSpec 流程將關鍵函式的 PBT 轉為 Lean 規格，再以 AI 代理嘗試產生證明。即使最終無法完整證明，也能作為「哪些函式最值得人工投入形式化」的優先排序依據。

### 實作前置條件

**資料面**
- 需具備 GitHub API 存取權限（建議使用認證 token 以提高 rate limit），或可離線存取已爬取的 FVSpec:PBT 資料集（HuggingFace 上於 2026 年 1 月發布）。
- 需具備 Python 原始碼與其授權資訊的解析能力；建議預先準備授權白名單（MIT、Apache-2.0、BSD 等寬鬆授權），以符合論文中「copyleft → drop」的篩選原則。
- 需有 Lean 4 工具鏈（`lake`、`elan`）以及 Mathlib 等標準函式庫的本地或 CI 環境，因為每個 FVC 都需通過 `lake build` 驗證。

**運算資源**
- 轉譯階段需呼叫具備長上下文（建議 ≥ 128K tokens）與工具使用能力的 LLM API（如 Claude Sonnet 4.6、Opus 4.7、GPT 5.4 等級），單次 PBT 轉譯可能消耗數萬 tokens。
- 證明生成階段若採模型法，每個 sorry 需獨立呼叫 LLM；9,415 個樣本 × 平均 2 個 sorry 的全量評估，預估需數萬美元級的 API 成本。
- 建議準備可平行化的工作排程器（如 Ray、Modal 或 Kubernetes Job），因為 LSP 修復迴圈與 `lake build` 驗證是 I/O bound，可大量平行。

**技能門檻**
- 必須熟悉 Lean 4 語法與 `sorry` 機制，理解 `lake build` 的錯誤訊息分類（unknown identifier、type mismatch、unsolved goals）。
- 需具備 Python AST 處理經驗（Tree-sitter 使用能力），以及 Hypothesis 框架的 `@given` 裝飾器語意。
- 建議團隊中至少有一位同時熟悉 Python 與 Lean 4 的工程師，用於處理轉譯管線中「Python 語意如何在 Lean 中建模」的棘手案例（如可變狀態、副作用、動態型別）。

### 實作步驟建議

1. **從 FVSpec:PBT 開始，先建立本地語料庫**
   直接下載 HuggingFace 上的 FVSpec:PBT 資料集（7,413 個去重 PBT），跳過自行爬 GitHub 的步驟。優先挑選與目標領域（金融、醫療、網通等）相關的子集，以降低後續轉譯的領域落差。

2. **建置最小可行的轉譯管線（MVP）**
   採用論文中描述的三代理 LLM 流程（Impl 代理、Spec 代理、LSP 修復代理），但先用 50–100 個 PBT 做小規模試跑，統計「Unit 型後備」、「未解析符號」、「規格洩漏到 Impl.lean」三類失敗的發生率，作為後續優化的基準。

3. **建立品質評估儀表板**
   實作論文中提到的覆蓋率與品質指標：每個 PBT 成功產出的 FVC 數、sorry 數量、是否通過 `lake build`、是否為 Unit 型後備等。將這些指標寫入 CI 報告，方便追蹤每次管線調整的成效。

4. **選定基準模型並執行證明生成評估**
   從 Claude Sonnet 4.6 開始（成本最低），對「easy」子集（約 70% 成功率）建立基準；再以 Opus 4.7 或 GPT 5.4 評估「hard」子集。記錄每個 sorry 的嘗試次數、平均耗時、失敗模式，作為後續微調或提示工程的事實基礎。

5. **設計「人機協作」介面**
   將 FVSpec 整合進 IDE（如 VS Code 的 Lean 擴充套件），讓工程師能在 AI 產生的 sorry 旁直接編輯、接受或拒絕 AI 的證明建議。這比「全自動證明」更貼近實務，因為論文中 49% 的 hard 樣本失敗率顯示完全自動化仍有相當距離。

6. **建立回饋迴圈，持續擴充語料**
   將企業內部專有的 PBT（可能未在 GitHub 公開）以相同流程轉譯，並把成功案例回饋到內部 FVSpec 衍生資料集。這能逐步建立「企業專屬的形式化基準」，作為內部 AI 工具的長期評估標準。

### 潛在風險與注意事項

- **Unit 型後備導致假性高分**：論文中明確指出，當代理無法推斷函式回傳型別時會退回到 `Unit`，產生恆真定理。這類樣本若未過濾，會嚴重膨脹 AI 的「成功率」。**緩解**：在評估腳本中強制檢查 `theorem ... : f x = ()` 模式並標記為無效。

- **未解析符號與型別錯誤**：代理可能發明 Lean 中不存在的名稱（如 `permutationOf`），導致 `lake build` 失敗。**緩解**：強化 LSP 修復迴圈，將錯誤訊息回傳給代理重試，並設定最大重試次數（例如 3 次）以避免無限迴圈。

- **規格洩漏到 Impl.lean**：當 Impl 代理預先寫入 `theorem` 區塊時，會破壞檔案分離。**緩解**：在後製階段以 AST 掃描 Impl.lean，若發現 `theorem` 或 `sorry` 關鍵字則自動剔除該樣本。

- **授權污染風險**：爬取的 PBT 可能來自 copyleft 授權（如 GPL），若未過濾而用於商業產品會衍生法律問題。**緩解**：嚴格執行論文的「copyleft → drop」步驟，並在資料集中保留每個樣本的授權 metadata。

- **領域落差導致轉譯品質不穩**：論文的 PBT 來自一般開源專案，若企業應用涉及高度專業領域（密碼學、量化金融），代理可能無法正確建模語意。**緩解**：在轉譯前先以領域專家標註 50–100 個「黃金樣本」，用於評估代理的領域理解能力。

- **成本失控**：全量 9,415 個樣本的證明生成可能耗費數萬美元 API 費用。**緩解**：採用分層抽樣（stratified sampling），僅對代表性子集做完整評估，並以較小模型做大規模預篩。

### 與其他技術的整合建議

- **與 CI/CD 整合**：將 FVSpec 評估嵌入 GitHub Actions 或 GitLab CI，在每次 PR 中對受影響的 Python 函式自動產生 Lean 規格並嘗試證明。當 AI 證明失敗時，自動產生 issue 並指派給工程師。

- **與既有測試框架整合**：Hypothesis 已是 Python 生態主流 PBT 函式庫，FVSpec 的爬蟲可直接掛在企業內部的 Hypothesis 使用統計上，優先挑選「使用頻率高、覆蓋路徑多」的 PBT 進行形式化。

- **與靜態分析工具互補**：將 FVSpec 與 mypy、Pyright、SonarQube 等工具並用。靜態分析擅長捕捉型別錯誤與常見 bug，FVSpec 則專注於「語意正確性」；兩者結合能形成更完整的程式碼品質保證。

- **與 AI 程式碼助手整合**：在 Cursor、Copilot 等助手的提示中注入「請同時產生 Hypothesis PBT 與 Lean 規格」的指令，使 AI 在生成程式碼時即考慮可驗證性。這呼應論文中「AI 產生愈來愈多程式碼」的觀察。

- **與形式驗證工具鏈整合**：Lean 4 並非唯一選項，可考慮將 FVSpec 的轉譯管線擴展至 Coq、Rocq、Isabelle 等其他證明輔助工具，以避免對單一工具鏈的過度依賴。

- **與知識管理系統整合**：將成功證明的 Lean 規格存入企業內部 Wiki 或 Confluence，作為「函式語意契約」的權威來源，供新進工程師與 AI 助手參考。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的「isort」範例（Figure 2），理解 PBT 與形式驗證的對應關係，再跳過技術細節，直接看第 2 節的「Task Definition」掌握「AI 要做什麼」。不必急於理解三代理管線的細節，先建立「PBT 是猜想、Lean 證明是定理」的直覺即可。

**給 AI 工程師**：重點放在第 2 節的「Nonsensical theorems pre-validation」與三代理管線設計，這是評估 LLM 在形式化任務上失敗模式的最佳教材。建議實際跑一次論文的開源管線，並嘗試用不同提示詞改善 Unit 型後備與未解析符號的問題，這比閱讀論文更能累積實務經驗。

**給研究者**：第 1 節對「為何現有基準不足」的論述（太小、偏數學、專家驅動）是論文最有學術價值的部分，建議從這裡切入，再延伸到與 FV APPS（Dougherty and Mehta, 2025）的比較。實驗結果（70% easy / 49% hard）可作為後續研究的基準線，特別是探討「為何 hard 樣本失敗率仍高」的方向。

**給產品經理**：把 FVSpec 視為「AI 程式碼品質的下一個評估維度」即可，不必深入技術細節。關鍵訊息是：當 AI 產生愈來愈多程式碼，企業需要新的方式驗證其正確性，而形式驗證是其中一個選項。建議評估自家產品中哪些場景值得導入，並關注基準的後續演進與生態系成熟度。
