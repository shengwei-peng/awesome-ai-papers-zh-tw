## ⚡ TL;DR

現有 GUI 代理難以從基準測試走向真實世界，因環境覆蓋不足、任務建構脆弱且獎勵驗證不可靠。
提出 UI-Venus-2，以統一閉環框架跨行動、網頁與桌面，以功能導向任務與多模型視覺驗證強化學習。
開源的 UI-Venus-2 在多項 GUI 基準達同規模領先，推動可泛化、可驗證且自我反思的安全實用代理。

## 摘要翻譯

多模態 GUI 代理（Multimodal GUI agents）已成為數位任務自動化（digital task automation）中極具前景的典範，然而從面向基準測試的模型（benchmark-oriented models）轉向可靠的真實世界應用仍具挑戰，原因在於環境覆蓋率（environment coverage）有限、任務建構（task construction）過於脆弱，以及獎勵驗證（reward verification）不可靠。在本研究中，我們提出 UI-Venus-2，一個通用基礎 GUI 代理（general-purpose foundation GUI agent），旨在透過統一閉環推理-行動框架（unified closed-loop reasoning-action framework），在行動（mobile）、網頁（web）與桌面（desktop）環境中運作。為縮小與實際部署之間的差距，我們同步擴展三個關鍵維度：（1）環境（Environments），將覆蓋範圍擴展至超過 170 個多語言行動應用程式（multilingual mobile apps），並涵蓋原生桌面作業系統（native desktop operating systems）；（2）任務（Tasks），採用深度研究流程（deep-research pipeline）進行功能導向指令生成（function-grounded instruction generation）；以及（3）驗證（Verification），採用結合視覺關鍵點（visual keypoints）與多模型投票（multi-model voting）的軌跡層級（trace-level）與樣本層級（sample-level）評估器（evaluators），以確保訓練所需的可靠強化學習訊號（RL signals）。此外，我們整合安全感知機制（safety-aware mechanisms），以確保重大影響動作（consequential actions）在受控狀態下執行。透過提供一個強大且高效率的開源基礎（open-source foundation），UI-Venus-2 推動該領域朝向更可泛化（generalizable）、可驗證（verifiable）且具自我反思能力（self-reflective），並適用於真實世界應用的代理邁進。

### 核心貢獻（3～5點）
- 擴展環境覆蓋率：支援超過 170 個多語言行動應用程式與原生桌面作業系統，突破既有基準測試的環境限制。
- 功能導向的任務生成：透過深度研究流程自動生成高品質、貼近真實應用情境的指令。
- 可靠的獎勵驗證機制：結合軌跡層級與樣本層級評估器、視覺關鍵點與多模型投票，提供穩定的強化學習訊號。
- 安全感知執行：針對重大影響動作設計控制機制，降低實際部署風險。
- 開源基礎模型：提供可泛化、可驗證且具自我反思能力的通用基礎 GUI 代理。

### 適合對象
本技術報告適合多模態大型語言模型、GUI 代理、數位任務自動化與強化學習領域的研究人員與工程師，以及希望將自動化代理部署於行動、網頁與桌面等真實環境的產品開發者與 AI 從業人員。

## 深度分析

#### 方法論解析

##### 1. 統一閉環推理-行動框架（unified closed-loop reasoning-action framework）
UI-Venus-2（通用基礎 GUI 代理）的核心運作邏輯可視為一個「觀察—推理—行動—反饋」的閉環：
1. **視覺感知（visual perception）**：模型接收當前渲染介面（rendered interfaces）的截圖，而非依賴結構化 API。
2. **狀態推理（state reasoning）**：基於自然語言指令與歷史互動軌跡，判斷任務進度與下一步意圖。
3. **動作執行（action execution）**：輸出類人動作（human-like actions），如點擊、輸入、滾動、鍵盤操作等。
4. **環境反饋整合（environmental feedback integration）**：將執行後的新介面狀態納入下一輪決策，形成 closed-loop。

這種端到端（end-to-end）設計的優勢在於對 API 不完整或無 API 的應用程式具有通用性，但挑戰在於長程規劃、動態介面變化與錯誤恢復。

##### 2. 三大聯合擴展維度
作者明確將環境覆蓋率（environment coverage）、任務建構（task construction）與獎勵驗證（reward verification）視為相互耦合的系統問題，而非孤立優化：

- **Environments（環境）**：從原本偏向行動與網頁的範圍，擴展到 100+ 中文與 70+ 英文行動應用程式，並新增原生桌面作業系統（desktop operating systems）支援，涵蓋 mobile、web、desktop 三大領域。
- **Tasks（任務）**：採用 deep-research pipeline（深度研究流程）進行功能導向指令生成（function-grounded instruction generation）。其關鍵在於讓生成的查詢扎根於應用程式的實際功能，確保指令在變化的介面狀態下仍可執行，從而提升準確性、有效性與可執行性。
- **Verification（驗證）**：引入 trace-level evaluators（軌跡層級評估器）與 sample-level evaluators（樣本層級評估器），並結合 visual keypoints（視覺關鍵點）與 multi-model voting（多模型投票），以提供更可靠的強化學習訊號（RL signals）。

##### 3. 訓練流程
根據引言與方法概述，UI-Venus-2 的訓練包含以下階段：
- **GUI mid-training（GUI 中期訓練）**：在大規模 GUI 資料上進行視覺與動作對齊，建立基礎的 GUI grounding（GUI 定位）能力。
- **Offline reinforcement learning（離線強化學習）**：利用已收集的軌跡資料進行策略學習。
- **OPD（推測為 Online Policy Distillation，線上策略蒸餾）**：進一步進行線上互動與策略精煉。

此流程延續 UI-Venus-1.5 的設計，但透過更豐富的環境與更精細的驗證機制，將模型從「動作導向的導航（navigation）代理」推向「可驗證、可自我反思的基礎代理」。

##### 4. 精細化驗證機制
驗證是本文方法論的最大亮點之一：
- **Visual keypoints（視覺關鍵點）**：驗證器不再僅對最終介面做整體判斷，而是檢查與任務目標直接相關的視覺元素（例如特定按鈕是否被點擊、訂單確認頁面是否出現）。
- **Trace-level vs. sample-level**：trace-level 關注整條互動軌跡的過程正確性；sample-level 則對單一樣本或最終狀態進行評估。兩者互補可避免「部分進度被誤判為完成」。
- **Multi-model voting（多模型投票）**：聚合多個異質模型的判斷，降低單一 judge 的偏誤，並減少 reward hacking（獎勵駭取）風險。

這對 RL 訓練至關重要，因為強化學習（reinforcement learning）的效能上限往往取決於獎勵（reward）訊號的品質。

##### 5. 安全感知機制與 CAPTCHA 處理
- **Safety-aware mechanisms（安全感知機制）**：針對 consequential actions（重大影響動作），如付款、刪除帳號、發送訊息等，設計控制機制，確保高風險操作受到約束。具體實現細節（如動作分級、確認閾值、人工介入點）在提供的文本中尚未詳述。
- **CAPTCHA solving**：將驗證碼處理視為「最後一哩路」能力，避免登入、註冊等流程中的驗證閘門阻斷軌跡收集，並透過針對性資料強化此能力。這雖有助於資料規模化，但也帶來潛在的濫用與倫理風險，需審慎評估。

#### 實驗數據解讀

由於提供的全文僅包含摘要、引言與部分方法概述，未包含具體的數據表格、圖表數值或完整實驗設定，因此本節以「實驗設計邏輯」與「作者宣稱的含義」為主，並指出數據解讀的限制。

##### 1. 評估領域與任務類型
根據 Figure 1 的描述，UI-Venus-2 的評估涵蓋：
- **行動裝置（mobile）**：VenusBench-Mobile 等使用者中心評測基準，測試導航（navigation）與 grounding 能力。
- **網頁（web）**：動態網站（dynamic websites）上的互動任務。
- **桌面作業系統（desktop operating systems）**：OSWorld 等電腦使用基準。
- **CAPTCHA 處理**：作為獨立能力進行評估。

這樣的設計反映了從「單一應用程式基準」轉向「跨平台真實場景」的趨勢。

##### 2. 可能的評估指標
雖然文中未列出明確數字，但 GUI 代理常見的指標包括：
- **任務成功率（task success rate）**：完成指令的比例，是最核心的指標。
- **平均步數 / 效率（average steps）**：衡量完成任務所需的互動次數。
- **動作準確率（action accuracy）**：預測動作（如點擊座標、輸入內容）的正確性。
- **軌跡層級正確性（trace-level correctness）**：中間步驟是否符合合理流程。
- **驗證一致性（verification consistency）**：多模型投票後的判斷穩定性。

若作者宣稱「在可比規模模型中達到接近最先進（almost state-of-the-art）表現」，則意味著在相同參數量級下，UI-Venus-2 在多個 GUI benchmarks 上的成功率與領先模型差距很小。

##### 3. 數據解讀的限制
- **缺乏數值表格**：無法進行量化比較，也無法判斷「almost state-of-the-art」的具體差距。
- **未說明測試條件**：例如是否使用多次嘗試（pass@k）、是否允許人工重試、環境解析度與延遲等，都會顯著影響結果。
- **Figure 1 不可見**：無法確認評估任務的分布與難度。
- **消融實驗細節不足**：雖然文中提到有 ablations，但具體驗證了哪些設計選擇尚不清楚。

#### 與現有研究的比較

##### 1. 相對於 UI-Venus / UI-Venus-1.5 的進展
- **環境擴展**：前代主要聚焦行動與網頁，UI-Venus-2 首次從頭建構桌面作業系統（desktop operating systems）能力，形成 mobile + web + desktop 的統一代理。
- **任務品質**：引入 deep-research pipeline 與功能導向指令生成，改善任務的可執行性與真實性。
- **驗證強化**：前代可能較依賴最終狀態判斷，UI-Venus-2 則強調 trace-level 與 sample-level 的雙層驗證。
- **安全與 CAPTCHA**：新增 safety-aware mechanisms 與驗證碼處理，補齊實際部署的最後一哩路。

##### 2. 相對於其他 GUI Agent 研究
- **OSWorld**：作為桌面作業系統評測基準，OSWorld 強調真實電腦使用場景，但多數研究僅在其上測試。UI-Venus-2 則將桌面能力整合進統一框架，並從訓練資料層面從頭建構。
- **VenusBench-Mobile**：強調使用者中心、跨應用程式的真實任務。UI-Venus-2 擴展至多語言（中文 + 英文）應用程式，提升環境覆蓋率。
- **其他 MLLM-based GUI agents**：許多工作依賴單一 judge 或規則式驗證，容易出現 reward hacking。UI-Venus-2 的多模型投票與 visual keypoints 是較為先進的驗證設計。

##### 3. 主要限制與潛在問題
- **驗證成本**：multi-model voting 與 visual keypoints 雖提升可靠性，但會顯著增加訓練與推理階段的計算成本。
- **安全機制細節不足**：safety-aware mechanisms 的具體設計、評估標準與失敗案例未充分說明。
- **CAPTCHA 的雙面性**：雖然有助於資料收集與真實任務完成，但可能被用於繞過安全機制，需配套倫理規範。
- **桌面能力建構難度**：桌面作業系統的狀態空間遠大於單一應用程式，從頭建構資料與訓練流程的規模與穩定性仍有待更多數據驗證。
- **與商業模型的比較**：文中未與 Claude Computer Use、Operator 等閉源商業代理進行直接比較，「almost state-of-the-art」的參照對象主要限於開源或可比規模模型。

#### 可重現性評估

##### 1. 已開放資源
作者明確表示 UI-Venus-2 是 open-source foundation（開源基礎），並公開：
- **完整參數權重（full-parameter weight）**
- **評估基礎設施（evaluation infrastructure）**

這對 GUI agent 研究社群是重要貢獻，有助於降低研究門檻、促進可重現研究，並加速強化學習與驗證方法的社群創新。

##### 2. 重現所需但尚未明確的要素
要達到完全可重現，仍需以下資訊：
- **訓練資料與任務生成流程**：deep-research pipeline 的具體實作、應用程式清單、查詢生成模板與過濾規則。
- **環境配置**：mobile、web、desktop 的模擬器或真實裝置設定、作業系統版本、解析度、延遲等。
- **超參數與訓練細節**：mid-training、offline RL、OPD 的學習率、batch size、獎勵函數設計、訓練步數等。

- **授權條款與硬體需求**：模型權重的授權是否允許商業使用、推理所需的 GPU 記憶體與運算資源。
- **CAPTCHA 與安全資料**：是否公開相關資料集，以及相關倫理審查說明。

##### 3. 可重現性評價
目前可給予「部分良好」的評價：模型權重與評估基礎設施的開放是重要進展，但訓練資料、環境與驗證細節的透明度將決定社群能否真正復現其完整流程，而不僅是執行預訓練模型。

#### 未來研究方向

##### 1. 多模態與多感官擴展
目前的 UI-Venus-2 主要依賴視覺截圖。未來可整合：
- **音訊反饋**：例如語音助理、影片播放狀態。
- **觸覺 / 裝置狀態**：例如震動、電量、網路連線狀態。
- **影片序列理解**：不僅是單幀截圖，而是連續動態介面變化。

##### 2. 更強大的驗證與獎勵設計
- **程式化驗證（programmatic verification）**：結合視覺關鍵點與應用程式底層狀態，減少對多模型投票的依賴。
- **分層獎勵函數**：區分「探索獎勵」、「進度獎勵」與「完成獎勵」，改善長程任務的 RL 訊號。
- **對抗式驗證**：主動尋找模型可能 reward hacking 的案例，提升驗證器魯棒性。

##### 3. 安全與可控性研究
- **安全基準（safety benchmarks）**：建立針對 consequential actions 的標準化測試集。
- **人機協作機制**：在高風險操作前引入確認、撤銷與人類監督。
- **價值對齊（value alignment）**：透過 RLHF 或憲法式 AI 讓代理理解使用者隱含的安全偏好。

##### 4. 跨平台遷移與終端部署
- **知識遷移**：研究 mobile、web、desktop 三域之間的共享表徵與遷移學習。
- **邊緣裝置推理**：開發更輕量的模型變體，支援在手機或 PC 上本地執行。
- **持續學習（continual learning）**：讓代理能適應新應用程式與介面更新，而無需從頭訓練。

##### 5. 真實世界部署與評估
- **長期使用者研究**：在真實使用者環境中評估成功率、效率與信任度。
- **動態網頁與登入狀態**：處理需要帳號、Cookie、二階段驗證的複雜網頁流程。
- **多代理協作**：讓多個 GUI agent 分工完成跨裝置、跨應用程式的複雜任務。

##### 6. 倫理與社會影響
- **CAPTCHA 與自動化濫用**：研究如何防止 GUI agent 被用於繞過安全機制、垃圾訊息發送或未經授權操作。
- **可解釋性（interpretability）**：讓代理能解釋其決策過程，提升使用者信任與除錯效率。

總結來說，UI-Venus-2 透過聯合擴展環境、任務與驗證，並強調安全與開源，為通用電腦使用（general-purpose computer use）代理奠定了重要基礎。未來研究應在驗證效率、安全可控性、真實部署與倫理規範等方向持續深化。

## 論文問答

**Q1：多模態 GUI 代理在從基準測試走向真實世界部署時，面臨哪些實務挑戰？**

A：根據本文摘要與引言，主要挑戰包含環境覆蓋率不足、任務建構過於脆弱，以及獎勵驗證不可靠這三大問題。傳統基準測試往往只涵蓋少數應用程式，無法反映多語言行動生態系統、動態網站與完整桌面作業系統的複雜性。此外，許多驗證器僅能偵測表面進度，容易將部分完成誤判為真正完成，導致強化學習訊號不穩定，進而限制代理在真實場景中的可靠性。

**Q2：為何僅追求基準測試表現的 GUI 代理不足以應付實際應用？**

A：現有許多研究過度聚焦於「下一個動作預測」的準確率，但真實世界任務需要長期規劃、錯誤恢復與跨應用協作等综合能力。以應用程式為中心或任務同質化的基準測試，往往會遮蔽代理在真實環境變化下的脆弱性，例如介面狀態改變或跨語言應用。因此，單純提升基準分數無法保證代理在開放、動態且多樣的數位環境中穩定執行。

**Q3：為什麼 UI-Venus-2 選擇同時擴展環境、任務與驗證這三個維度？**

### 實作步驟建議

**步驟一：環境盤點與可行性評估**  
先列出需要自動化的應用程式清單，區分為行動 App、網頁與桌面作業系統三類，並確認每個環境是否可取得渲染畫面、可注入點擊與鍵盤事件，以及是否能復原執行後的狀態。對於涉及登入、註冊或 CAPTCHA 的流程，需額外評估資料收集與驗證閘門的可行性。

**步驟二：建立功能導向的任務資料庫**  
參考論文的深度研究流程，從應用程式功能說明出發生成任務指令，而非憑空產生自然語言查詢。每個任務應標註預期起始狀態、目標狀態、關鍵中繼步驟，以及對應的視覺關鍵點，作為後續軌跡層級與樣本層級驗證的依據。

**步驟三：部署基礎模型與驗證基礎設施**  
下載並部署 UI-Venus-2 全參數權重，建立統一的推理服務。同步建置 trace-level 與 sample-level 評估器，設定視覺關鍵點擷取規則與多模型投票門檻，確保獎勵訊號能反映真實任務完成度，而非僅判斷最終畫面是否相似。

**步驟四：領域適應性微調與強化學習**  
在目標環境收集的軌跡資料上進行 GUI 中期訓練與離線強化學習，再視需求進行線上強化學習或偏好最佳化。訓練過程中應持續監控驗證器一致性，避免策略學到利用驗證漏洞的捷徑行為。

**步驟五：建立安全閘門與人工接管機制**  
針對送出交易、刪除帳號、修改權限等重大影響動作，設定明確的動作白名單與黑名單，並在執行前要求二次確認或自動轉交人工審核。同時記錄完整執行軌跡，便於事後稽核與錯誤分析。

**步驟六：漸進式上線與持續監控**  
先從低風險、可復原的任務開始試行，逐步擴大到高風險流程。上線後持續追蹤任務成功率、驗證器置信度分布、平均執行步數與人工介入頻率，並定期以新收集的軌跡重新訓練模型。

### 潛在風險與注意事項

**獎勵駭客（Reward Hacking）**  
單一驗證器可能僅依據最終畫面的表面特徵給予獎勵，導致代理學到跳過關鍵步驟或偽造完成狀態。建議採用論文中的多模型投票機制，並在軌跡層級檢查中繼狀態的視覺關鍵點，降低單一判斷偏差。

**重大影響動作的安全控管**  
自動化代理在具備更高操作能力時，也可能造成更大損害。必須在訓練與推論階段都納入安全感知機制，例如對刪除、付款、授權等動作設定明確限制，並保留人工接管通道。

**環境動態性與介面改版**  
行動 App 與網頁經常更新，按鈕位置、流程順序或驗證方式可能改變。建議將任務指令與功能層級綁定，而非僅依賴像素座標，並建立定期回歸測試機制，及早發現因介面改版導致的失敗。

**驗證器本身的偏差與延遲**  
多模型投票雖可提升穩健性，但也會增加運算成本與回饋延遲，可能拖慢強化學習訓練。建議在驗證準確率與訓練吞吐量之間取捨，對高風險任務使用嚴格驗證，對低風險任務使用輕量驗證。

**隱私與合規風險**  
GUI 代理會擷取螢幕畫面，可能包含個人資料、商業機密或受監管資訊。實作時應確保資料去識別化、傳輸加密、存取紀錄完整，並符合適用的資料保護法規。

### 與其他技術的整合建議

**與 RPA 或低程式碼平台整合**  
可將 UI-Venus-2 作為傳統 RPA 的「視覺補強層」，處理無法透過 API 或 DOM 選擇器穩定操作的步驟；同時保留既有 RPA 在結構化流程控制、排程與日誌管理上的優勢。

**與 LLM 編排框架整合**  
透過 LangChain、LlamaIndex 或自研 Agent Orchestrator 將 UI-Venus-2 規劃為工具之一，負責執行需要視覺互動的步驟，而其他 LLM 則負責意圖解析、知識檢索與多輪對話管理。

**與企業 IAM 與單一登入整合**  
在執行需要身分驗證的任務時，透過 OAuth、SAML 或企業密碼管理系統安全取得憑證，避免將帳號密碼直接寫入代理的提示或訓練資料。

**與監控與可觀測性工具整合**  
將代理的執行軌跡、驗證結果與異常事件匯入 Prometheus、Grafana 或 ELK 等監控系統，並設定告警規則，例如連續失敗率上升、重大影響動作被觸發或驗證置信度異常偏低。

**與資料管線和向量資料庫整合**  
利用向量資料庫儲存應用程式功能說明、常見任務範例與歷史成功軌跡，讓深度研究流程在生成新任務時能檢索相關上下文，提升指令的準確性與可執行性。
