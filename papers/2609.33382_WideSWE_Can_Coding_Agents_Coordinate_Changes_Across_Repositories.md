# WideSWE：程式設計智慧體（Coding Agents）能否跨儲存庫協調變更？

**原文標題：** WideSWE: Can Coding Agents Coordinate Changes Across Repositories?

## ⚡ TL;DR

現有評測多限單一儲存庫，難以檢驗跨儲存庫協同修改能力。
本文提出 WideSWE，收錄 120 個真實跨儲存庫任務，並調整隱藏測試以支援多樣正確實作。
七組智慧體完整成功率僅 10.83%–42.50%，顯示範圍遺漏、交付不全與編輯後錯誤等難題。

## 摘要翻譯

程式設計智慧體（Coding Agents）的評測已從解決單一議題（Issues），進展到執行長期開發（Long-horizon Development），但任務完成度（Task Completion）的評估仍多侷限於單一程式碼庫（Codebase）。在軟體生態系統（Software Ecosystems）中，許多功能（Features）與錯誤修復（Bug Fixes）都需要在多個儲存庫（Repositories）間進行協調式變更（Coordinated Changes）。我們提出 WideSWE，用於評估程式設計智慧體在這類跨儲存庫任務（Cross-repository Tasks）上的表現。透過挖掘變更（Mining Changes）與審查變更（Reviewing Changes）103 個軟體生態系統中的變更，我們獲得 120 個真實世界任務（Real-world Tasks），錯誤修復與功能各 60 個。我們從相關議題與拉取請求（Pull Requests, PRs）衍生提示（Prompts），並系統化地審查與調整隱藏測試（Hidden Tests），以支援多樣正確實作（Diverse Correct Implementations），同時保留預期行為（Required Behavior）與迴歸檢查（Regression Checks）。在七種智慧體配置（Agent Configurations）中，完整任務成功率（Full Task Success）介於 10.83% 至 42.50% 之間，其中以 Codex CLI 搭配 GPT-5.6-sol 的配置達到最高。執行軌跡（Trajectories）顯示，智慧體可能未能識別必要變更、識別到變更卻未完成，或雖修改了所需儲存庫卻未完全滿足請求。為了檢驗一次處理一個儲存庫是否能緩解這些困難，我們在相同提示下比較獨立執行（Independent Execution）與聯合執行（Joint Execution）。獨立執行主要可補回遺漏的工作，但在修正先前嘗試但未成功的實作方面效果較差；聯合執行則能利用相關儲存庫的資訊來引導實作與驗證。程式碼可於 https://github.com/ZJU-ACES-ISE/WideSWE 取得。

### 核心貢獻（3～5點）
- 提出 WideSWE 基準，首次系統化評估程式設計智慧體在跨儲存庫任務上的協調變更能力。
- 從 103 個真實軟體生態系統中挖掘並審查變更，建構出 120 個平衡的真實世界任務（60 個錯誤修復與 60 個功能）。
- 設計系統化的隱藏測試調整流程，在保留預期行為與迴歸檢查的前提下，支援多樣正確實作。
- 對七種智慧體配置進行實證評估，完整任務成功率介於 10.83% 至 42.50%，並分析智慧體的失敗模式。
- 比較獨立執行與聯合執行策略，發現聯合執行更能利用跨儲存庫資訊引導實作與驗證。

### 適合對象
本論文適合對程式設計智慧體、自動化軟體工程、長期開發任務，以及跨儲存庫軟體演化感興趣的研究人員與工程師閱讀；特別是正在開發或評估能夠在真實軟體生態系統中自主作業（Autonomous Work）之 AI 系統的讀者。

## 深度分析

#### 方法論解析

WideSWE（本論文提出的跨儲存庫程式設計智慧體評測基準）將 coding agents（程式設計智慧體）的評測從 single repository（單一儲存庫）延伸至 cross-repository tasks（跨儲存庫任務）。其核心方法論可從五個層面拆解：

1. **任務形式化（Task Formulation）**  
   每個 WideSWE 任務代表一個需要在多個 target repositories（目標儲存庫）間協調完成的 shared feature（共享功能）或 bug fix（錯誤修復）。任務成功的定義是「所有相關儲存庫都正確實作同一需求」，而非僅有單一儲存庫通過測試。這與 SWE-bench（要求智慧體在單一儲存庫中解決真實 GitHub 議題的基準）有本質區別。

2. **大規模資料挖掘與篩選（Mining and Case Selection）**  
   研究團隊從 Gitstar Ranking 前 200 名的 GitHub organizations 中，辨識出 103 個 active software ecosystems（活躍軟體生態系統），其 repositories（儲存庫）共同支撐某個產品、平台或技術。透過分析 1,729,171 筆 pull requests（PRs，拉取請求），發現 109,233 筆 PR records（PR 記錄）明確引用同一生態系的其他儲存庫。接著從中挖掘 linked, merged PRs（相互連結且已合併的拉取請求），並輔以 manual review（人工審查）與 executable validation（可執行驗證），篩選出需要實質性跨儲存庫變更的案例。最終產出 120 個 real-world tasks（真實世界任務），橫跨 41 個 ecosystems（生態系統），並平衡為 60 個 bug fixes（錯誤修復）與 60 個 features（功能）。

3. **Prompt 與測試建構（Prompt and Test Construction）**  
   Prompts（提示）是將原始 issues（議題）與相關 PRs 的需求合併、重寫而成，確保 agent（智慧體）收到的任務描述能反映跨儲存庫的整體目標。在測試方面，作者發現直接繼承原始 PR 的測試常會與 task requirements（任務需求）產生 mismatch（不匹配），例如測試過度綁定特定實作細節。為此，他們進行 rule-guided manual revisions（規則導向人工修訂），在保留 required behavior（預期行為）與 regression checks（迴歸檢查）的前提下，讓 hidden tests（隱藏測試）能夠支援 diverse correct implementations（多樣正確實作）。這一步對於公平評估 LLM-based agents（基於大型語言模型的智慧體）尤為重要，因為這類智慧體的解法往往與人類原始 PR 不同。

4. **評估指標設計（Evaluation Metrics）**  
   主要指標為 full task success（完整任務成功率），即所有 target repositories 都通過對應的 F2P（fail-to-pass，失敗轉通過）tests。此外，作者也記錄 per-repository pass rate（單一儲存庫通過率）、不同 error types（錯誤類型）的分布，以及 joint execution（聯合執行）與 independent execution（獨立執行）之間的 outcome reversals（結果翻轉）數量，以細緻地理解失敗原因。

5. **聯合執行 vs. 獨立執行（Joint vs. Independent Execution）**  
   Joint execution 讓 coding agent 在整個 ecosystem workspace（生態系工作區）中同時接觸多個儲存庫，能夠讀取相關儲存庫的程式碼與測試作為 reference（參考），並在實作與驗證時利用跨儲存庫資訊。Independent execution 則將相同 prompt 分別餵給只在單一 target repository 中執行的 agent，測試「一次專注一個儲存庫」是否能降低協調難度。這兩種設計的對照是 WideSWE 方法論中最具實驗洞察力的部分之一。

#### 實驗數據解讀

實驗結果顯示，即便在最先進的 agent configuration（智慧體配置）下，cross-repository task completion（跨儲存庫任務完成）仍然極具挑戰性：

- **整體成功率偏低**：七種 agent configurations 的 full task success rate（完整任務成功率）介於 10.83% 至 42.50% 之間。表現最佳的是 Codex CLI（OpenAI 的程式設計智慧體命令列工具）搭配 GPT-5.6-sol（本實驗使用的 OpenAI 模型），但也僅達 42.50%。這表示即使是最強配置，仍有超過一半的案例無法完成跨儲存庫協調。

- **失敗模式可分為三類**：作者從 trajectories（執行軌跡）中歸納出三種典型錯誤：
  - **Scope Error（範圍錯誤）**：agent 未能識別所有需要修改的儲存庫。例如 Sentry 案例中，需求要求同時實作 Go SDK、Python SDK 與 Ruby SDK（語言軟體開發套件），但 agent 只修改了 Go SDK，便將目標窄化為「Go SDK」。
  - **Delivery Error（交付錯誤）**：agent 已識別範圍，卻未在所有儲存庫中完成變更。例如 Godot / Native SDK 案例中，agent 知道 Godot 呼叫端需要配合 Native SDK 的更新，但最終只實作了 Native SDK，遺漏了 Godot 端的已知修正。
  - **Post-edit Error（編輯後錯誤）**：agent 已修改所有必要儲存庫，但最終行為仍不符合任務要求。例如 Kubernetes 的 kube-openapi（Kubernetes 相關的 OpenAPI 產生器儲存庫）與 Kubernetes consumer（消費端）都被修改，但 consumer behavior（消費端行為）仍然不正確。

- **局部成功不等於全局成功**：在 Codex CLI + GPT-5.6-sol 失敗的 69 個案例中，有 48 個案例出現「至少一個儲存庫通過所有 F2P tests，但其他儲存庫未通過」的情況。這顯示 agent 常在單一儲存庫測試通過後就停止，缺乏將 shared requirement（共享需求）貫徹到所有 affected repositories（受影響儲存庫）的全局意識。

- **聯合執行與獨立執行各有優劣**：在 89 個使用相同 prompt 的案例中，joint execution 解決了 36 個，independent execution 解決了 32 個，並出現 20 次 outcome reversals（同一案例在兩種模式下結果相反）。Trajectory analysis（執行軌跡分析）揭示：
  - Independent execution 能透過縮小 scope（範圍）來 recover omitted work（補回被遺漏的工作），因為 agent 不會被其他儲存庫分散注意力。
  - 但 independent execution 也可能失去來自相關儲存庫的 behavioral references（行為參考），例如無法參考 Python SDK 的實作來完成 Ruby SDK。
  - Joint execution 能利用跨儲存庫資訊來引導實作與驗證，但也可能因資訊過載或過早滿足於單一儲存庫的測試而失敗。

- **任務特性影響難度**：雖然摘錄未提供完整細節，但作者提到實驗涵蓋不同 task types（任務類型）、repository counts（儲存庫數量）與 language diversity（語言多樣性）。一般而言，涉及越多儲存庫或越多程式語言的任務，對 agent 的規劃與驗證能力要求越高，成功率也越低。

#### 與現有研究的比較

WideSWE 在 coding agent 評測領域中填補了一個重要的空白：

- **相較於 SWE-bench**：SWE-bench 要求 agent 在單一 repository 中解決真實 GitHub issues，重點在於單一程式碼庫的 bug fixing（錯誤修復）。WideSWE 則將場景擴展到多個相互依存的儲存庫，強調 coordinated changes（協調式變更）與 cross-repository links（跨儲存庫連結）。

- **相較於 DeepSWE**：DeepSWE 評估的是 original, long-horizon engineering tasks（原創長期工程任務），雖然任務跨度長，但仍主要局限於 single codebase（單一程式碼庫）。WideSWE 的長期挑戰來自於「跨儲存庫協調」而非單一專案內的複雜度。

- **相較於 ProgramBench**：ProgramBench 要求從 reference executables（參考可執行檔）與 documentation（文件）重建完整程式，屬於從零開始的程式合成。WideSWE 則是在既有、真實的軟體生態系中進行增量式變更，更貼近實際軟體維護情境。

- **主要貢獻**：
  1. 提出 cross-repository task completion（跨儲存庫任務完成）的形式化定義與對應基準。
  2. 建立 requirement-aligned test review（需求對齊的測試審查）流程，兼顧行為正確性與實作多樣性。
  3. 提供大規模實證研究，比較七種 agent configurations、兩種執行模式，並從 trajectories 中歸納失敗模式。

- **限制與不足**：
  - **樣本規模**：從 103 個生態系、超過 170 萬筆 PR 中僅選出 120 個任務，雖然品質經過嚴格把關，但覆蓋面仍有限。
  - **選擇偏差**：任務來源是明確引用其他儲存庫的 merged PRs，可能遺漏那些跨儲存庫關係較隱晦或透過其他管道（如 issue 討論、郵件列表）協調的變更。
  - **人工測試調整的主觀性**：requirement-aligned test review 雖然有規則引導，但仍需人工判斷，可能影響測試的客觀性與可重複性。
  - **模型與工具限制**：實驗主要使用 Codex CLI 與 GPT-5.6-sol 等 proprietary models（專有模型），結果可能無法直接推廣到其他開源模型或不同 scaffold（腳手架）。
  - **評估維度有限**：目前主要依賴 hidden tests 與 F2P tests，尚未涵蓋非功能性需求（如效能、安全性、文件更新、版本號協調、CI/CD 整合等）。

#### 可重現性評估

- **開放資源**：論文指出程式碼已公開於 `https://github.com/ZJU-ACES-ISE/WideSWE`。這通常意味著 task list（任務列表）、prompts、adapted tests（調整後的測試）與 evaluation harness（評估腳手架）都會一併釋出，對於重現 benchmark 結構與評分邏輯非常有幫助。

- **模型與 API 的封閉性**：雖然評測框架開源，但實驗使用的 Codex CLI 與 GPT-5.6-sol 屬於 OpenAI 的 proprietary services（專有服務）。若未來模型版本更新、API 行為改變或存取權限受限，將難以完全重現原始實驗結果。此外，LLM 本身具有 stochasticity（隨機性），即使使用相同 prompt，多次執行也可能產生不同 trajectories。

- **儲存庫快照與時間敏感性**：WideSWE 的任務來自真實 GitHub repositories，其程式碼狀態會隨時間演進。論文提到篩選條件包含「Latest PR: Jun 1, 2025 onward」，因此重現時必須使用特定 commit 或提供 frozen snapshots（凍結快照），否則上游儲存庫的變更可能導致測試失效。

- **測試調整流程的文件化**：requirement-aligned test review 涉及人工修訂 inherited tests。若論文僅釋出最終測試而未詳細記錄修訂規則與決策過程，其他研究者將難以在新增任務時複製相同標準。

- **綜合評價**：WideSWE 在 benchmark 設計與評估工具層面具備中高程度的可重現性；但在 exact agent behavior（精確的智慧體行為）與 proprietary model outputs（專有模型輸出）層面，可重現性受到商業服務與隨機性的限制。

#### 未來研究方向

基於 WideSWE 的發現，未來研究可朝以下方向延伸：

1. **強化跨儲存庫規劃能力**  
   開發能夠主動建構 repository dependency graph（儲存庫相依圖）並據此規劃修改順序的 agents，例如先更新被依賴的 library（程式庫），再更新其 consumers（消費端）。

2. **多智慧體協作架構**  
   探索 multi-agent systems（多智慧體系統），讓每個 agent 負責一個 repository，並透過明確的 coordination protocol（協調協定）交換需求、介面變更與測試結果，以減少單一 agent 的認知負荷。

3. **自適應的聯合／獨立執行策略**  
   設計能根據任務特性動態選擇 joint execution 或 independent execution 的 meta-agent（後設智慧體），例如在儲存庫間高度相依時採用聯合執行，在需要補遺漏工作時切換為獨立執行。

4. **自動化測試調整與跨儲存庫驗證**  
   將 requirement-aligned test review 自動化，並發展能夠同時執行多個儲存庫測試、檢查 cross-repo integration（跨儲存庫整合）的 verification framework（驗證框架），甚至模擬 CI/CD pipeline（持續整合／持續部署流程）。

5. **擴展基準的規模與多樣性**  
   增加更多 ecosystems、程式語言、任務類型，並納入 implicit cross-repository changes（隱性跨儲存庫變更），例如透過相依套件傳播的漏洞修復或 API 破壞性變更。

6. **成本、延遲與實用性分析**  
   Cross-repository tasks 通常需要更長的 trajectories 與更多 API 呼叫，未來可研究如何在成功率、執行時間與 API 成本之間取得平衡。

7. **結合真實開源維護流程**  
   將 WideSWE 的任務部署為自動化維護機器人，在真實開源專案中協助處理 cross-repo PRs，並收集人類維護者的反饋以持續改進。

8. **安全性與供應鏈風險**  
   跨儲存庫變更可能影響大量 downstream projects（下游專案），未來可研究如何評估與防範因協調不當而引入的 supply-chain vulnerabilities（供應鏈漏洞）或 regression risks（迴歸風險）。

## 論文問答

**Q1：WideSWE 主要想解決什麼問題？**
A：WideSWE 針對的是現有程式設計智慧體評測大多只聚焦在「單一儲存庫」內完成任務，但真實軟體生態系統中，許多功能新增或錯誤修復必須在多個儲存庫之間進行協調式變更。例如 Sentry 的語言軟體開發套件就必須分別在 Go、Python、Ruby 等多個儲存庫實作同一項功能，而相依儲存庫的更新也會牽動下游消費端。因此，WideSWE 首次系統性地把「跨儲存庫任務」納入評測，檢驗智慧體能否識別並完成所有相關儲存庫的必要修改。

**Q2：為什麼現有的基準測試無法充分衡量這項挑戰？**
A：SWE-bench、DeepSWE 與 ProgramBench 等基準雖然已從孤立式程式碼生成擴展到真實儲存庫中的自主作業，但它們的核心評估場景仍局限於單一程式碼庫。這些基準無法檢驗智慧體在跨儲存庫連結中辨識影響範圍、同步實作與驗證下游行為的能力。結果是，現有方法容易忽略範圍錯誤、交付錯誤與編輯後錯誤等真實生態系統中常見的失敗模式。

**Q3：跨儲存庫協調為什麼對軟體工程很重要？**
A：在實務上，跨儲存庫連結非常普遍，研究團隊分析 103 個軟體生態系統中超過 172 萬筆拉取請求後，發現有 109,233 筆 PR 記錄明確引用了同一生態系統中的其他儲存庫。這表示單一功能或錯誤修復經常需要在多個儲存庫同步落地，否則就會出現部分實作或下游行為異常。若程式設計智慧體無法處理這類協調，即使單一儲存庫看起來正常，整體任務仍會失敗。

**Q4：WideSWE 的核心方法是什麼？**
A：研究團隊從 103 個活躍軟體生態系統中挖掘相互連結且已合併的拉取請求，並將實作同一功能或修復同一錯誤的多個儲存庫變更群組成單一任務。接著從原始議題與拉取請求衍生提示，並透過人工審查與可執行驗證建立隱藏測試。最終形成 120 個真實世界任務，平均涵蓋 60 個錯誤修復與 60 個功能，橫跨 41 個生態系統。

**Q5：WideSWE 的關鍵創新點有哪些？**
A：第一項創新是將跨儲存庫任務完成形式化為「在多个目標儲存庫中實作同一共享需求」，並提供相對應的基準資料集。第二項創新是提出需求對齊的測試審查流程，針對繼承自原始 PR 的測試與任務需求之間的落差進行規則導向的人工修訂。第三項創新則是透過聯合執行與獨立執行的對比實驗，系統性分析智慧體在生態系統層級的協調行為。

**Q6：WideSWE 在資料建構上做了哪些重要設計選擇？**
A：研究團隊先從 Gitstar Ranking 前 200 大的 GitHub 組織中，篩選出 103 個支援共同產品、平台或技術的活躍軟體生態系統，並要求最新拉取請求落在 2025 年 6 月 1 日以後，以確保任務的現實性與可執行性。為了兼顧任務類型的代表性，最終資料集平衡了 60 個錯誤修復與 60 個功能。此外，所有測試都經過人工調整，在保留預期行為與迴歸檢查的同時，允許多樣正確實作。

**Q7：實驗中使用了哪些智慧體配置，主要結果為何？**
A：研究團隊評估了七種智慧體配置，完整任務成功率介於 10.83% 到 42.50% 之間，其中 Codex CLI 搭配 GPT-5.6-sol 的組合表現最佳，但也僅達到 42.50%。在該最佳配置的 69 個失敗案例中，有 48 個案例出現「至少一個儲存庫通過所有 fail-to-pass 測試，但另一個儲存庫未通過」的情況。這顯示即使是最強的智慧體，也難以穩定地將共享需求貫徹到所有受影響的儲存庫。

**Q8：聯合執行與獨立執行的比較實驗得出什麼結論？**
A：在 89 個使用相同提示的任務中，聯合執行解決了 36 個，獨立執行解決了 32 個，並出現 20 次結果反轉。獨立執行有助於縮小範圍、補回被遺漏的工作，但容易失去來自相關儲存庫的行為參考；相對地，聯合執行能利用生態系統工作空間中的跨儲存庫資訊來引導實作與驗證。這說明兩種執行模式各有優劣，並非單純地「一次只處理一個儲存庫」就能解決所有問題。

**Q9：智慧體在跨儲存庫任務中出現哪些典型失敗模式？**
A：研究團隊歸納出三種主要失敗：範圍錯誤是指智慧體未能識別所有需要修改的儲存庫，例如 Sentry 任務中只修改了 Go SDK 卻遺漏 Python 與 Ruby SDK；交付錯誤是指智慧體雖然知道要改哪些儲存庫，卻沒有全部完成，例如 Godot／Native 任務只改了 Native SDK 卻未處理 Godot 呼叫端；編輯後錯誤則是兩個儲存庫都已修改，但最終行為仍不正確，例如 Kubernetes 任務中 kube-openapi 與 Kubernetes 都改了，消費端行為卻仍錯誤。

**Q10：WideSWE 的任務在實務上對應哪些場景？**
A：這些任務反映了大型組織日常維護中常見的跨儲存庫工作，例如在多個語言軟體開發套件中同步新增共享功能、更新程式庫後連帶調整相依的呼叫端，以及遷移產生器後確保下游消費端行為正確。這類協調式變更廣泛存在於平台型產品、開源框架與多語言 SDK 生態系統中。因此，WideSWE 的評測情境與真實軟體工程需求高度貼近。

**Q11：若要將這類智慧體落地到產品中，需要考慮哪些因素？**
A：產品化時必須讓智慧體具備跨儲存庫感知能力，例如自動解析相依關係、追蹤哪些儲存庫會被同一功能或修復影響。此外，智慧體不能因為單一儲存庫的測試通過就停止，而需要持續驗證所有目標儲存庫的預期行為與迴歸檢查。工具層面也需要提供生態系統層級的工作空間，讓智慧體能同時檢視、編輯與測試多個儲存庫。

**Q12：WideSWE 對程式設計智慧體研究領域可能帶來什麼影響？**
A：WideSWE 把評測焦點從單一程式碼庫的孤立任務，推向整個軟體生態系統的協調任務，促使研究者正視多儲存庫推理與執行的挑戰。它提供了 120 個真實世界任務與相應的測試流程，可作為未來開發與評估跨儲存庫智慧體的標準資料集。長遠來看，這將推動更具生態系統級維護能力的自主程式設計智慧體誕生。

**Q13：WideSWE 有哪些已知的限制？**
A：首先，120 個任務雖然涵蓋 41 個生態系統，但相較於全球數以百萬計的開源專案，規模與領域覆蓋仍有限。其次，任務來源僅限於有明確跨儲存庫連結的已合併拉取請求，可能遺漏那些沒有顯式引用但實際需要協調的隱性變更。最後，評估仰賴經過調整的隱藏測試，雖然已盡力保留預期行為，但仍可能無法涵蓋所有正確性面向。

**Q14：從失敗案例中可以看出智慧體還有哪些根本性的弱點？**
A：即使是最強配置，完整任務成功率也不到五成，顯示智慧體在長期開發與多儲存庫協調上仍不穩定。常見問題包括過早滿足於局部測試通過、無法持續追蹤已識別但尚未完成的下游工作，以及難以利用相關儲存庫的實作細節來修正錯誤。這些弱點反映出智慧體在規劃、記憶與跨儲存庫驗證方面仍有很大的進步空間。

**Q15：未來研究可以朝哪些方向改進？**
A：未來可以發展能夠自動建構跨儲存庫相依圖的規劃機制，讓智慧體在動手修改前先明確識別所有目標儲存庫與修改順序。也可以強化跨儲存庫驗證能力，使智慧體能根據一個儲存庫的實作結果去推導並檢查其他儲存庫的行為。此外，擴充資料集的規模與語言多樣性、探索人機協作模式，以及設計能記憶並重用跨儲存庫實作經驗的智慧體，都是值得深入的方向。

## 實務應用指南

## 適用場景

1. **多語言 SDK 同步開發**  
   當產品需要同時在 Go、Python、Ruby、PHP 等多個語言軟體開發套件（SDK）中推出同一功能或修補同一缺陷時，可運用跨儲存庫任務框架，讓程式設計智慧體在一個共享工作區中協調變更，避免只改到其中一個 SDK 而遺漏其他語言實作。

2. **平台核心程式庫與下游消費端協同更新**  
   例如 Kubernetes 的 `kube-openapi` 產生器與 Kubernetes 本體、或 Godot 引擎與 Native SDK 這類「上游改規格、下游要配合」的場景，可用來驗證智慧體是否能同時修改產生器與其消費端，並確保產生的模型名稱與消費端行為一致。

3. **微服務或跨服務 API 契約變更**  
   當 API 規格（如 OpenAPI）變動需要同步更新服務端實作、客戶端 SDK、文件與相依元件時，跨儲存庫評測可協助確認智慧體是否識別出所有受影響儲存庫，並完成端到端變更。

4. **企業內部共享元件與多產品線同步修補**  
   企業常見一個共享程式庫被多條產品線或部門專案引用。透過建立跨儲存庫任務，可自動化追蹤「共用元件修補後，所有引用專案是否同步更新、測試是否通過」，降低單點遺漏風險。

5. **開源生態跨倉貢獻自動化與迴歸驗證**  
   針對活躍開源組織（如 Sentry、Hugging Face、PaddlePaddle），可將相關議題與拉取請求（PR）彙整為跨儲存庫任務，用於自動化初稿生成、迴歸檢查與人工審查前的預先驗證。

## 實作前置條件

- **資料準備**
  - 目標軟體生態系統的多個儲存庫原始碼與提交歷史。
  - 相互關聯的議題（issues）與拉取請求（PRs），最好包含明確的跨儲存庫引用。
  - 可執行的單元測試、整合測試，以及用於評估的隱藏測試（hidden tests）。
  - 黃金標準答案或參考實作，用於確認「預期行為」與產生評測標籤。

- **運算資源**
  - 能呼叫大型語言模型（LLM）的 API 額度或本地 GPU/TPU 推論環境。
  - 可同時掛載多個儲存庫的容器化工作區（如 Docker）與 CI 執行環境。
  - 足夠的儲存空間與網路頻寬，用於複製與測試多個相依儲存庫。

- **技能需求**
  - 熟悉軟體工程流程、版本控制、測試設計與持續整合。
  - 具備建構與除錯程式設計智慧體（如 Codex CLI、OpenAI 模型）的經驗。
  - 能進行人工審查與規則導向的測試調整，以支援多樣正確實作。
  - 了解目標生態系統的語言、相依關係與建置工具。

## 實作步驟建議

1. **界定跨儲存庫任務範圍**  
   選定一個軟體生態系統，明確哪些儲存庫屬於同一產品、平台或技術，並定義「單一共享功能或錯誤修復」必須橫跨哪些儲存庫才算完成。

2. **挖掘與審查相關變更**  
   從 GitHub 組織中找出相互連結且已合併的 PR，透過自動化挖掘與人工審查，篩選出需要多個儲存庫實質變更的案例，並區分為錯誤修復與功能新增兩大類。

3. **建立聯合與獨立執行環境**  
   準備兩種工作區：一種是同時掛載所有目標儲存庫的聯合工作區（joint execution），另一種是每次只掛載單一目標儲存庫的獨立工作區（independent execution），以便後續比較。

4. **設計提示與調整測試**  
   將原始議題與 PR 描述整合為給智慧體的提示。檢查繼承來的測試是否與任務要求一致，必要時進行規則導向的人工修訂，保留預期行為與迴歸檢查，同時允許多樣正確實作。

5. **選擇智慧體配置並執行**  
   選定智慧體與模型組合（例如 Codex CLI 搭配 GPT-5.6-sol），分別在聯合與獨立環境中執行任務，記錄完整執行軌跡（trajectories）與測試結果。

6. **分類失敗模式並迭代改進**  
   根據結果將失敗歸類為範圍錯誤（Scope Error）、交付錯誤（Delivery Error）或編輯後錯誤（Post-edit Error），針對性地改進提示、增加跨儲存庫驗證步驟，或強化智慧體的範圍識別能力。

7. **整合至開發流程**  
   將驗證過的跨儲存庫任務與評測機制嵌入 CI/CD 管線，作為自動化初稿生成、迴歸測試或人工審查前的預檢閘道。

## 潛在風險與注意事項

- **範圍遺漏（Scope Error）**  
  智慧體可能只修改部分儲存庫，忽略其他同樣需要變更的目標。建議在提示中明確列出所有目標儲存庫，並要求智慧體在開始實作前回報完整影響範圍。

- **交付不完全（Delivery Error）**  
  即使識別到所有需要變更的儲存庫，智慧體仍可能在某些儲存庫中只做一半。可在每個儲存庫變更後強制執行對應測試，並要求智慧體確認所有儲存庫的 F2P 測試皆通過。

- **編輯後仍不符合要求（Post-edit Error）**  
  智慧體可能修改了所有儲存庫，但整體行為仍不正確。應設計跨儲存庫的整合測試與端到端驗證，避免僅依賴單一儲存庫的單元測試。

- **測試與需求不一致**  
  繼承自原始 PR 的測試可能過度綁定特定實作方式。需要人工審查並調整隱藏測試，使其能夠接受多樣正確實作，同時守住預期行為。

- **成本與執行安全**  
  跨儲存庫任務通常步驟更長、呼叫次數更多，需留意 API 費用與執行時間。此外，智慧體會自動執行指令與測試，必須在隔離環境中運行，防止惡意或錯誤程式碼影響生產系統。

- **維護負擔**  
  隨著上游儲存庫持續更新，基準任務與測試可能失效。建議定期重新驗證並鎖定特定版本快照，或建立自動化更新流程。

## 與其他技術的整合建議

- **議題追蹤與專案管理工具**  
  將跨儲存庫任務與 Jira、GitHub Issues、Linear 等工具串接，自動從相關議題與 PR 產生提示，並將執行結果回寫為任務狀態或審查意見。

- **持續整合／持續部署（CI/CD）**  
  在 CI 管線中加入跨儲存庫評測步驟，當共享元件變更時自動觸發下游儲存庫的建置與測試，及早發現範圍遺漏或相容性問題。

- **程式碼審查平台**  
  將智慧體產生的跨儲存庫變更匯入 Pull Request，並透過 GitHub/GitLab 審查介面呈現各儲存庫的修改摘要與測試結果，輔助人類審查者快速掌握全貌。

- **知識圖譜與檢索增強生成（RAG）**  
  建立儲存庫間相依關係與 API 契約的知識圖譜，讓智慧體在規劃階段就能查詢「修改 A 儲存庫會影響哪些下游儲存庫」，降低範圍錯誤。

- **多智慧體協作框架**  
  針對每個目標儲存庫配置專責智慧體，再由協調智慧體統籌任務分配與結果彙整，結合聯合執行的全局視野與獨立執行的專注度。

- **可觀測性與軌跡記錄工具**  
  整合日誌、追蹤與執行軌跡視覺化工具，方便事後分析智慧體為何遺漏特定儲存庫，或在哪一步停止變更。

## 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦圖 1 的三個失敗案例與「範圍錯誤、交付錯誤、編輯後錯誤」這三種分類，理解跨儲存庫任務與單一儲存庫任務的差異；技術細節如測試調整與模型配置可暫時略讀，重點放在「為什麼需要同時改多個儲存庫」以及「智慧體目前還會漏做什麼」。

- **AI 工程師**  
  請仔細閱讀實驗設計、七種智慧體配置的比較，以及聯合執行與獨立執行的對照分析；特別留意軌跡分析中揭示的失敗模式，這些是改進提示工程、工具設計與多步驟規劃策略的直接線索。

- **研究人員**  
  建議深入檢視任務形式化、資料挖掘流程、人工審查與測試調整方法論，以及基準建構的統計分布（錯誤修復與功能、儲存庫數量、語言多樣性）；這些內容對設計下一代長期開發或多智慧體協作基準具有參考價值。

- **產品經理**  
  請優先關注適用場景、成功率數據與風險章節，評估這類技術在自家多儲存庫產品線中的落地可行性；重點思考「哪些重複性跨倉更新最適合先導入」「需要多少人機協作審查閘門」，以及「預期能節省多少工程工時」。
