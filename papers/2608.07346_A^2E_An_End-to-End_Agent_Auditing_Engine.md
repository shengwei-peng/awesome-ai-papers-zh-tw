## ⚡ TL;DR

現有智慧體評估工具多僅支援部分流程，難以系統化且端到端地評估不同harness與模型組合。
本文提出A^2E，以ATP銜接基準與harness，自動記錄標準軌跡並依生命週期進行多維度評估。
實驗顯示沒有單一模型–harness組合能橫跨各任務領先，多維指標比正確性更能區分harness差異。

## 摘要翻譯

隨著大型語言模型（Large Language Models, LLMs）的快速發展，智慧體載具（Agent Harness）已成為在各領域部署智慧體（Agent）的關鍵基礎設施。快速演進的 harness 生態系統也使得嚴謹的能力評估（Capability Evaluation）日益重要。然而，有效率地建立一個端到端（End-to-End）、系統化且全面的評估流程仍是一大挑戰。為解決此挑戰，我們提出 A^2E（Agent Auditing Engine，智慧體稽核引擎），一個專為智慧體 harness 設計的端到端評估引擎。A^2E 運用我們新提出的智慧體任務協定（Agent Task Protocol, ATP），使評估任務得以快速整合至不同的 harness。透過自動插樁的 Monitor（監控器），A^2E 在實驗過程中擷取並生成標準化的執行追蹤（execution traces）。在評估階段，A^2E 使用一組多維度指標系統性地評估 harness 能力。相較於僅考量正確性（Correctness），這些指標能更細緻地刻畫不同 harness 在執行效率（execution efficiency）、工具使用（tool use）、任務規劃（task planning）與錯誤復原（error recovery）等方面的差異。使用 A^2E 進行的實驗進一步揭示，模型與 harness 的組合在不同類型任務上呈現顯著的效能差異，且沒有任何單一組合能在所有任務上始終優於其他組合。這些發現不僅證明了系統化評估的必要性，也為模型與 harness 的共同演化（Co-evolution）提供了有用的指引。我們的程式碼已釋出於 https://github.com/datamllab/A2E。

### 核心貢獻（3～5點）
- 提出智慧體任務協定（ATP），使評估任務能快速整合至不同的智慧體 harness，降低跨 harness 評估的建置成本。
- 設計自動插樁的 Monitor，在實驗過程中擷取並生成標準化執行追蹤，為後續分析提供一致且可重現的資料基礎。
- 建立多維度評估指標體系，從執行效率、工具使用、任務規劃與錯誤復原等面向，細緻刻畫 harness 能力差異。
- 透過大規模實驗揭示模型與 harness 組合在不同任務類型上的效能變異，並為模型與 harness 的共同演化提供實證指引。

### 適合對象
本論文適合從事大型語言模型智慧體（LLM Agent）研究與開發的學者與工程師，特別是關注智慧體 harness 設計、基準測試（Benchmark）建構、能力評估方法論，以及部署後智慧體系統（Deployed Agent System）效能分析的讀者。對於希望系統化比較不同模型–harness 組合、並尋求模型與基礎設施共同演進方向的實務團隊亦具高度參考價值。

## 深度分析

#### 方法論解析

A^2E（Agent Auditing Engine，智慧體稽核引擎）的核心設計目標是建立一個輕量、低侵入性且 harness-agnostic（不特定於某一 harness）的端到端（end-to-end）評估基板，將基準測試編排（benchmark orchestration）、軌跡監控（trajectory monitoring）與生命週期對齊評估（lifecycle-aligned evaluation）整合在單一技術堆疊中。整體架構由三個層級組成：Task Layer（任務層）、Monitor Layer（監控層）與 Evaluation Layer（評估層）。

**Task Layer：以 Agent Task Protocol（ATP，智慧體任務協定）解耦基準測試與 harness**

傳統上，若要將一個新的基準測試（benchmark）接入某個智慧體 harness（智慧體載具），通常需要為每一組 benchmark–harness 組合撰寫專屬 adapter（轉接器）。A^2E 透過 ATP 將「任務定義」與「harness 執行」解耦：benchmark 只需描述輸入、期望輸出、工具需求與評分規則，而 harness 則負責將這些任務映射到自身的系統提示（system prompts）、工具介面（tool interfaces）與執行策略（execution policies）。這種模組化抽象讓新的 benchmark 與 harness 能以極少的 adapter 程式碼加入，避免組合爆炸式的 pairwise implementation（成對實作）。

此外，Task Layer 內建一個階層式的 benchmark tree（基準測試樹），沿三個維度索引：time（時間，區分已飽和與新釋出的 benchmark）、category（類別，如 coding、web research、science、tool use、productivity 等）以及 difficulty（難度，easy / medium / hard）。這讓評估不再只是單一總分，而能進行細粒度的縱向與橫向比較。

**Monitor Layer：以 OpenInference 與 OpenTelemetry spans 建立標準化執行軌跡**

Monitor Layer 的關鍵在於「自動儀器化」（instrumentation）。A^2E 基於 OpenInference 規範，在 harness 執行迴圈中自動插入追蹤點，產生與 OpenTelemetry 相容的 spans（跨度）。相較於僅記錄最終輸入輸出，這種 span-based traces（基於跨度的軌跡）能結構化地保留模型呼叫（model invocations）、工具呼叫（tool calls）、中間推理與各執行階段的事件。由於採用 OpenTelemetry 生態系，這些軌跡可與現有的可觀測性（observability）基礎設施互通，同時維持對原生執行路徑的高保真度（trajectory fidelity），避免透過 model API proxy 改變生成參數或呼叫路徑所帶來的失真。

**Evaluation Layer：Lifecycle-Aligned Evaluation（生命週期對齊評估）與可擴充指標**

Evaluation Layer 提出 Lifecycle-Aligned Evaluation：每個指標（metric）都會註冊到特定的執行階段（execution stage）與評估維度（evaluation dimension），例如規劃（planning）、工具使用（tool use）、最終答案（final answers）、作業品質（operational quality）等。這樣的設計確保指標與智慧體生命週期中的對應階段一致，避免將所有差異壓縮成單一正確性（correctness）分數。A^2E 同時支援 Extensible Evaluation（可擴充評估），讓研究者新增自訂指標；並透過 Scalable Evaluation（可擴展評估）將軌跡、指標定義與評估結果儲存在資料庫中，而非散落於獨立 log 檔案，從而支援增量式（incremental）、持久化（persistent）與縱向（longitudinal）評估。

#### 實驗數據解讀

論文利用 A^2E 進行了大規模的 harness–model 交互研究，主要涵蓋三個面向：Harness–Benchmark Evaluation Matrix（harness–benchmark 評估矩陣）、Cross-Benchmark Harness Comparison（跨基準 harness 比較）以及 Case Study（個案研究）。

**Harness–Benchmark Evaluation Matrix**

實驗橫跨多個代表性 benchmark，包括 GDPVal（Patwardhan et al., 2025）、MMLU-Pro（Wang et al., 2024）與 τ3-bench（Yao et al., 2024; Barres et al., 2025），並搭配多個智慧體 harness 與大型語言模型（LLMs）。結果顯示，model–harness 組合在不同類型任務上呈現顯著的性能變異：在某個 benchmark 上成功率高或 token 效率佳的組合，換到另一個 benchmark 可能表現不佳。這說明 harness 的有效性並非全域可排序，而是具有模型依賴性（model-dependent）與任務依賴性（task-dependent）。

**Cross-Benchmark Harness Comparison**

作者以 DeepSeek-V4-Pro 搭配九個不同 harness，進行 matched campaign（配對實驗），並比較規劃、工具使用、最終答案與作業品質等多維度指標。如圖 1 的雷達圖所示，若干流程指標（process metrics）與作業指標（operational metrics）的「花瓣」張開幅度明顯大於正確性（correctness）：即使多個 harness 在最終答案正確率上看起來相近，它們在規劃品質、工具呼叫次數、token 消耗、錯誤恢復（error recovery）與安全性等面向仍有顯著差異。這證明了單純以 endpoint correctness（端點正確性）評估 harness 的解析度有限，必須透過生命週期對齊的多維度指標才能診斷從 deliberation（審議）、action（行動）到 answer（答案）的完整軌跡。

**Case Study**

個案研究進一步具體化上述發現，展示特定 harness 在特定任務類型上的優劣。例如，某些 harness 在需要多步工具呼叫的任務中展現較佳的任務規劃（task planning）與錯誤恢復能力，但在簡單問答任務中卻因過度複雜的執行策略而浪費 token；反之，輕量 harness 在簡單任務上成本效益高，卻在長程規劃中容易迷失。這些案例凸顯了系統化評估的必要性，也為模型與 harness 的共同演化（co-evolution）提供實證依據。

#### 與現有研究的比較

A^2E 的定位介於兩類現有框架之間：一端是以 Inspect AI（AI Security Institute, UK, 2024）為代表的 comprehensive benchmark runner（全面型基準測試執行器），另一端是以 Phoenix（Arize AI, 2024）為代表的 OpenInference-based observability system（可觀測性系統）。

**相較於 Inspect AI**

Inspect AI 提供完整的 benchmark orchestration、sandboxed execution（沙箱執行）與 scoring（評分）功能，但其整合外部 harness 主要依賴 harness-specific adapters 與 model API proxies。這帶來兩個問題：第一，隨著 harness 介面與事件格式快速演進，adapter 需要持續維護；第二，proxy 可能改變生成參數、呼叫路徑或其他原生執行細節，降低軌跡保真度。A^2E 透過 ATP 與自動儀器化，減少了對 harness-specific adapter 的依賴，並在原生執行環境中收集標準化軌跡，從而在輕量核心的前提下提供更高的軌跡真實性。

**相較於 Phoenix 等 OpenInference 系統**

Phoenix 等系統能為原生智慧體執行提供標準化可觀測性，但它們本身並非端到端的 benchmark runner，缺乏任務編排與結果驗證機制，使用者仍需自行整合 benchmark、harness 與追蹤基礎設施。A^2E 則將這三者統一為單一評估堆疊，並透過資料庫化儲存支援縱向與增量評估。

**主要貢獻與限制**

A^2E 的主要貢獻在於提出一個「最小必要抽象」的整合框架：ATP 解耦 benchmark 與 harness、OpenTelemetry spans 標準化軌跡、Lifecycle-Aligned Evaluation 擴充評估維度。然而，其限制也同樣來自於這種輕量設計：對於某些高度客製化或具有特殊執行語義的 harness，ATP 可能無法完整捕捉其特有行為，仍需額外 adapter；此外，雖然 A^2E 強調低侵入性，但在實際部署時仍需確保儀器化不會對 harness 的效能或行為產生不可忽略的副作用。最後，目前論文呈現的實驗主要聚焦於特定模型（如 DeepSeek-V4-Pro）與少數 benchmark，對於更廣泛的模型規模、多模態（multimodal）任務與分散式多智慧體（multi-agent）場景的適用性仍有待驗證。

#### 可重現性評估

**程式碼開放性**

論文明確指出原始碼已公開於 https://github.com/datamllab/A2E，這為可重現性（reproducibility）奠定基礎。開源程式碼應包含 Task Layer、Monitor Layer 與 Evaluation Layer 的核心實作，以及 ATP 的規範與範例 adapter。

**資料集與模型權重**

實驗使用的 benchmark——GDPVal、MMLU-Pro、τ3-bench——均為已發表或公開釋出的基準測試，理論上可透過對應管道取得。然而，部分 benchmark 可能需要申請、授權或特定資料處理流程。模型方面，DeepSeek-V4-Pro 等模型通常透過 API 或特定平台提供，未必開放模型權重（model weights）；因此，即使 A^2E 的評估流程可重現，底層模型行為可能因 API 版本、溫度參數（temperature）與速率限制而有所差異。建議未來在論文或文件中詳細記錄 API 版本、呼叫參數與隨機種子設定，以提升跨環境重現的一致性。

**軌跡與資料庫儲存**

A^2E 將 trajectories（軌跡）、metric definitions（指標定義）與 evaluation results（評估結果）儲存在資料庫中，這對於縱向比較與增量評估非常有利，但也意味著重現實驗需要正確設定資料庫環境與 schema。若論文能釋出預先計算的軌跡與評估結果（例如透過 Hugging Face Datasets 或專案附屬儲存空間），將大幅降低後續研究者的重現門檻。

#### 未來研究方向

**擴充 ATP 至多智慧體與串流場景**

目前的 ATP 主要針對單一智慧體的任務定義。未來可將其擴展至多智慧體協作（multi-agent collaboration）、對話式互動（conversational interaction）與串流式工具呼叫（streaming tool calls），並定義相應的 span 語義，以支援更複雜的部署情境。

**自動化 harness 設計與共同演化**

A^2E 揭示 harness 效能具有強烈的模型與任務依賴性，這為「自動化 harness 搜尋」或「harness 超參數最佳化」提供動機。未來可結合神經架構搜尋（NAS）或貝葉斯最佳化（Bayesian optimization），在 A^2E 的評估回饋下自動調整系統提示、工具介面與上下文管理策略，實現模型與 harness 的共同演化。

**線上與持續評估（Online & Continuous Evaluation）**

現有實驗多為離線批次評估。未來可將 A^2E 整合至 CI/CD 流程，對每次 harness 或模型更新進行回歸測試（regression testing），並建立長期監控儀表板，追蹤性能漂移（performance drift）與成本漂移（cost drift）。

**因果歸因與可解釋性**

多維度指標雖能描述差異，但難以直接指出「為何某個 harness 表現較差」。未來可引入因果推論（causal inference）或反事實分析（counterfactual analysis），將軌跡中的特定行為（如重複工具呼叫、錯誤恢復失敗）與最終結果建立因果連結，提升評估的診斷價值。

**安全性、公平性與永續性指標**

除了正確性、效率與規劃品質，未來的評估框架應納入更多面向，例如工具使用的安全性（safety）、輸出的公平性（fairness）、能源消耗（energy consumption）與碳足跡（carbon footprint）。A^2E 的 Extensible Evaluation 設計為這些指標的整合提供了良好基礎。

**標準化排行榜與社群驅動的 benchmark 擴充**

最後，A^2E 可作為社群級 harness 評估 leaderboard（排行榜）的基礎設施。透過統一的 ATP 與軌跡格式，不同研究團隊貢獻的 benchmark、harness 與指標能夠互通，從而加速智慧體生態的透明化與可比較性。

## 論文問答

**Q1：隨著大型語言模型快速進步，為什麼單獨評估模型已經不足以理解部署後的智慧體系統？**
A：因為智慧體 harness 決定了系統提示、工具介面、上下文管理與執行策略，最終系統效能高度依賴這些設計，而非僅由底層模型決定。單純評估模型無法反映真實部署時的規劃品質、工具呼叫模式與錯誤恢復能力。因此，必須針對 harness 層級進行端到端評估，才能完整掌握智慧體的實際表現。

**Q2：現有框架（如 Inspect AI、Phoenix）在評估智慧體 harness 時的主要不足是什麼？**
A：Inspect AI 雖然提供基準測試編排、沙箱執行與計分，但整合外部 harness 時需要專屬 adapter 與模型 API proxy，容易改變原生執行參數與呼叫路徑，降低軌跡真實性。Phoenix 等基於 OpenInference 的系統雖能標準化地觀察原生執行，但缺乏完整的基準執行、任務編排與結果驗證功能。兩者擴展到新基準、新 harness 或新軌跡語義時，通常都需要大量框架專屬工程，難以快速適應快速演進的 harness 生態。

**Q3：為什麼可重現且細粒度的 harness 層級評估越來越重要？**
A：因為 harness 生態快速演進，不同模型與 harness 組合會在效能上產生顯著差異，只有系統化評估才能客觀比較這些組合。細粒度軌跡收集能診斷規劃、工具使用、執行效率與錯誤恢復等過程，而不只是最終答案是否正確。這對於指導模型與 harness 的共同演化、提升整體系統可靠性至關重要。

**Q4：A^2E 的三層架構各自負責什麼，又如何協同運作？**
A：Task Layer 基於 Agent Task Protocol（ATP）負責基準測試管理與任務執行，並將基準測試與智慧體 harness 解耦。Monitor Layer 透過 OpenTelemetry 相容的 span 擷取標準化執行軌跡，涵蓋模型呼叫、工具呼叫與各執行階段。Evaluation Layer 引入 Lifecycle-Aligned Evaluation，把每個指標註冊到對應的生命週期階段與評估維度，三層共同構成從任務準備、執行監控到多維評估的完整流程。

**Q5：Agent Task Protocol（ATP）的核心作用與優勢是什麼？**
A：ATP 作為輕量抽象層，讓不同基準測試與智慧體 harness 能夠獨立整合，避免每對基準–harness 都需要撰寫專屬 adapter。它只需少量 adapter 程式碼即可加入新基準或新 harness，大幅降低維護成本與整合時間。這種解耦設計同時保留了原生執行路徑，有助於提升軌跡真實性與評估結果的可信度。

**Q6：Lifecycle-Aligned Evaluation 的設計理念是什麼？**
A：每個評估指標都會被註冊到特定的執行階段與細粒度評估維度，例如規劃、工具使用、最終答案與執行品質。這確保指標與智慧體生命週期緊密對應，能診斷從思考、行動到產出答案的完整軌跡。同時，這種設計也讓評估框架易於擴充，新增指標時不會與無關階段混淆，維持評估的結構化與可解釋性。

**Q7：實驗使用了哪些基準測試與 harness，評估矩陣如何設計？**
A：文中實驗涵蓋 GDPVal、MMLU-Pro、τ3-bench 等基準測試，並對多個 harness 進行系統化比較，例如 DeepSeek-V4-Pro 搭配九個不同 harness。實驗建構了 Harness–Benchmark Evaluation Matrix，以比較不同模型–harness 組合在跨任務上的表現。Task Layer 的基準樹也按時間、類別與難度建立索引，支援區分已飽和與新釋出的基準，並進行跨領域與跨難度的細緻比較。

**Q8：A^2E 實驗的兩大關鍵發現是什麼？**
A：第一，沒有任何單一模型–harness 組合在所有任務上持續領先，佔據成功–效率前緣的最佳組合會隨基準、模型與任務而變。第二，僅看最終正確性難以區分 harness，因為不同 harness 在規劃、工具呼叫與計算成本等過程與操作指標上差異顯著。這些發現凸顯多維度、生命週期對齊評估的必要性，也說明 harness 效能本質上具有模型相依性與任務相依性。

**Q9：個案研究（Case Study）展示了什麼樣的深入洞察？**
A：個案研究透過細粒度軌跡與多維指標，深入分析特定 harness 在規劃、工具使用或錯誤恢復上的具體行為。這類分析能揭示最終答案正確但過程低效、成本過高或不安全的案例，而這些問題僅靠正確性指標無法發現。透過 A^2E 的 Monitor Layer 與 Evaluation Layer，研究者可重現並量化這些過程差異，從而針對性地改進 harness 設計。

**Q10：A^2E 在實務上適合哪些應用場景？**
A：A^2E 適合需要持續評估與比較多個智慧體 harness 的團隊，例如模型提供者、harness 開發者或企業 AI 平台。它能自動化執行基準測試、收集標準化軌跡並產出多維度報告，減少人工介入與重複工程。對於需要監管合規、安全稽核或長期追蹤系統演化的場景，A^2E 也能提供可重現且持久的評估證據。

**Q11：若將 A^2E 產品化，需要考慮哪些工程與設計因素？**
A：需要支援更多 harness 與基準測試的即插即用，並持續維護 ATP adapter 的生態系，以降低整合門檻。資料庫儲存設計需能橫向擴展，以因應大規模、長期縱向評估所產生的軌跡與指標資料。此外，使用者介面應能視覺化雷達圖等指標，並支援鑽取到單一軌跡進行除錯與根因分析。

**Q12：A^2E 對智慧體研究領域可能帶來什麼影響？**
A：它推動從單一模型評估轉向 harness 層級的系統化評估，強調模型與 harness 的共同演化。標準化軌跡與多維指標有助於建立更細緻、可重現的比較基準，促進社群共享評估結果與最佳實踐。長期來看，A^2E 可加速更安全、更有效率且更易於稽核的智慧體基礎設施發展。

**Q13：作者在文中承認了哪些限制？**
A：雖然提供的上下文未明確列出所有限制，但從設計可推知，A^2E 仍需為每個新 harness 或基準測試撰寫 ATP adapter，並非完全零成本整合。Monitor Layer 依賴 OpenTelemetry 與 OpenInference，若 harness 未遵循相關標準則需要額外插樁工作。此外，現有評估維度與指標的選擇可能仍無法涵蓋所有應用場景的特定需求，例如高度客製化的業務邏輯。

**Q14：A^2E 可能在哪些情況下失效或表現不佳？**
A：若 harness 內部狀態不透明或無法插樁，Monitor Layer 可能無法完整擷取執行軌跡，導致指標計算出現偏差。對於需要高度互動、長期記憶或多輪複雜協作的任務，現有指標可能不足以充分捕捉品質差異。此外，若基準測試本身缺乏明確的階段定義，Lifecycle-Aligned Evaluation 的階段對齊會變得困難，影響評估的準確性與可解釋性。

**Q15：未來可以朝哪些方向擴展 A^2E？**
A：可加入更多執行階段專屬指標，例如安全性、隱私保護、公平性與多智慧體協作品質。也可整合線上持續評估能力，讓 A^2E 在生產環境中監控真實流量，而不僅限於離線基準測試。進一步可發展自動診斷與建議功能，根據軌跡直接推薦 harness 調整或提示改進策略，實現從評估到最佳化的閉環。

## 實務應用指南

### 適用場景

1. **多 harness 選型與採購決策**  
   企業在導入 LLM 智慧體時，常面臨 LangGraph、AutoGen、OpenAI Agents SDK、smolagents 等多種智慧體 harness 的選擇。A^2E 可在同一組基準測試上，對不同 harness–模型組合進行端到端評估，協助團隊依據正確性、成本、工具使用與錯誤恢復等維度，選出最適合自身任務的 harness。

2. **模型升級前的迴歸測試**  
   當底層模型從 GPT-4o 升級到 GPT-4.5，或從 Claude 3.5 Sonnet 切換到 Claude 4 時，harness 的提示、工具介面與上下文管理策略可能不再適用。A^2E 可建立持續的 harness–基準測試評估矩陣，在模型更新前快速發現效能衰退或行為偏移。

3. **內部智慧體產品的品質閘道**  
   對於已上線的客服、程式輔助或研究助理智慧體，A^2E 能作為 CI/CD 中的品質閘道：每次 harness 或工具介面變更後，自動執行一組標準化任務，並透過資料庫留存軌跡與指標，進行縱向比較。

4. **第三方 harness / 開源貢獻者的稽核驗證**  
   開源社群或企業內部平台團隊，可利用 A^2E 驗證新 harness 或新基準測試的整合品質，確保其符合 ATP 規範，並產生可重現的執行軌跡與多維度評分。

5. **學術研究中的智慧體行為分析**  
   研究者可以透過 A^2E 的 Monitor Layer 收集標準化 span，分析不同 harness 在規劃、工具呼叫、錯誤恢復等生命週期階段的行為差異，而不僅止於最終答案是否正確。

### 實作前置條件

- **資料準備**
  - 至少一組已標準化的基準測試資料集（如 GDPVal、MMLU-Pro、τ3-bench），或依 ATP 自行封裝的內部任務集。
  - 每個任務需包含輸入、預期驗證邏輯（scorer）與難度 / 類別標籤，以便利用 A^2E 的分層基準測試樹進行索引。

- **運算資源**
  - 可執行目標 harness 的運算環境（本地 GPU/CPU 或雲端 VM）。
  - 模型 API 存取權限與足夠的呼叫額度，因為端到端評估會產生大量模型呼叫與工具執行。
  - 用於儲存軌跡、指標定義與評估結果的資料庫（A^2E 採用資料庫化儲存，建議準備 PostgreSQL 或相容的持久化儲存）。

- **技術能力**
  - 熟悉 Python 與智慧體 harness 的基本運作（prompt、tool call、context management）。
  - 了解 OpenTelemetry / OpenInference 概念，以便理解 span-based trace 的結構。
  - 具備撰寫輕量 adapter 的能力，因為整合新 harness 時通常需要實作 ATP 介面與必要的 instrumentation。

---

### 實作步驟建議

1. **環境建置與安裝**  
   從官方 GitHub 取得 A^2E 程式碼，安裝核心相依套件，並設定資料庫連線與模型 API 金鑰。

2. **定義或匯入基準測試**  
   將現有基準測試轉換為 ATP 格式，或直接使用 A^2E 已支援的基準測試。為每個任務標註時間、類別與難度維度，建立可檢索的基準測試樹。

3. **整合目標智慧體 harness**
   - 為每個待測 harness 實作 ATP adapter，讓 A^2E 能夠統一餵入任務並接收執行結果。
   - 在 harness 執行迴圈中掛載 Monitor，確保模型呼叫、工具呼叫與執行階段事件都被記錄為 OpenTelemetry-compatible span。

4. **執行軌跡生成實驗**  
   選定一組 harness–模型組合，執行端到端評估。Monitor Layer 會自動產生標準化執行軌跡，並寫入資料庫。

5. **設計 Lifecycle-Aligned Evaluation 指標**
   - 依據智慧體生命週期（規劃、工具使用、最終答案、運作品質等）註冊指標。
   - 除了正確性，也納入執行效率、token 成本、錯誤恢復次數、工具呼叫精準度等維度。

6. **執行評估與產出報告**  
   利用 Evaluation Layer 對軌跡進行多維度評分，產生 harness–基準測試評估矩陣與雷達圖等視覺化結果，並比較不同組合的優劣。

7. **建立持續評估流程**  
   將上述步驟納入自動化排程或 CI/CD，每次 harness、模型或工具介面更新後重新執行，並利用資料庫進行縱向比較。

### 潛在風險與注意事項

- **Adapter 維護成本**  
  雖然 ATP 減少了每對 benchmark–harness 的 adapter 需求，但 harness 內部介面仍會演進。建議將 adapter 與 harness 版本綁定，並在 CI 中納入相容性測試。

- **軌跡保真度下降**  
  若 adapter 改變了生成參數、呼叫路徑或事件格式，可能導致 Monitor 記錄的軌跡無法真實反映原生執行行為。整合時應盡量保持最小侵入性，並定期抽樣比對原生日誌與 A^2E 軌跡。

- **評估指標過度擴張**  
  Lifecycle-Aligned Evaluation 雖然支援多維度指標，但過多指標會讓解讀困難。建議先聚焦與業務目標最相關的 4–6 個核心維度，再逐步擴充。

- **成本與時間爆炸**  
  大規模 harness–模型–基準測試矩陣會產生大量 API 呼叫。建議先以小型子集進行試驗，設定呼叫頻率與預算上限，並利用 A^2E 的資料庫支援增量評估。

- **資料隱私與合規**  
  若評估任務涉及敏感資料，軌跡與資料庫儲存需符合內部資安與隱私規範。建議對軌跡進行去識別化或限制儲存欄位。

### 與其他技術的整合建議

- **OpenTelemetry 生態系**  
  A^2E 的 Monitor Layer 採用 OpenTelemetry-compatible span，可直接匯入現有可觀測性平台（如 Jaeger、Grafana Tempo），讓開發團隊在正式環境與評估環境使用一致的追蹤工具。

- **CI/CD 與 MLOps 平台**  
  可將 A^2E 包裝為容器化評估任務，整合進 GitHub Actions、GitLab CI 或 Kubeflow Pipelines，作為智慧體產品的自動化品質閘道。

- **LLM 閘道與成本管理工具**  
  搭配 LiteLLM、Helicone 或自建的模型路由閘道，統一管理多模型 API 金鑰、速率限制與成本追蹤，並與 A^2E 的執行效率指標互相驗證。

- **向量資料庫與知識檢索系統**  
  若評估任務需要 RAG 能力，可將 A^2E 與現有向量資料庫（如 Milvus、Weaviate、Qdrant）整合，並在 ATP 任務中定義檢索工具與評分邏輯。

- **現有評估框架**  
  若團隊已使用 Inspect AI 或 Phoenix，可將 A^2E 視為專注於 harness-level、端到端評估的補充層：利用 ATP 銜接外部 harness，並將軌跡與結果匯出至既有報表系統。

- **產品經理**  
  建議優先閱讀「1 Introduction」與「6 Experiments」，掌握核心發現：模型與 harness 的組合效應強、正確性不足以區分 harness。這有助於在產品規劃中推動「以多維度評估驅動選型」的決策流程，並向技術團隊明確提出效率、成本與穩定性等商業指標需求。
