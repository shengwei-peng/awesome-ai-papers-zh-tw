## 摘要翻譯

電腦使用代理（CUA）已展現出在完成數位任務方面的強大能力。然而，現有的CUA僅依賴圖形使用者介面（GUI）互動（這通常效率低下且容易出錯），或者是透過應用程式特定API或工具來增強GUI互動（這需要大量的工程工作，且難以跨應用程式擴展）。我們主張，下一代CUA應結合GUI互動與命令列介面（CLI），發揮GUI的通用性與殼層命令的效率。然而，一項關鍵挑戰在於，現有模型在任務執行過程中並不知道何時或如何使用CLI。為解決此挑戰，我們開發了一套資料建構流程，可產生三種類型的軌跡：僅GUI軌跡、僅CLI軌跡，以及GUI與CLI交錯軌跡。此流程產生了HybridCUA-8K資料集，包含5K混合軌跡與3K已驗證RLVR任務。基於這些資料，我們提出了一個兩階段的訓練框架：先對建構的軌跡進行監督式微調（SFT），接著使用我們的CLI感知獎勵進行強化學習，鼓勵代理選擇性地且可靠地使用CLI。實驗顯示，HybridCUA-9B在OSWorld上達到53.6%的準確率，較基礎模型提升了14.8個百分點，並在WindowsAgentArena上提升了4.0個百分點。這些結果證明了混合GUI與CLI範式對電腦使用代理的有效性與跨平台泛化能力。

### 核心貢獻（3～5點）
- **問題重新定位**：指出現有CUA受限於「僅依賴GUI」或「以API/工具增強GUI」兩種路線的瓶頸，提出結合GUI通用性與CLI效率的混合範式作為下一代CUA的發展方向。
- **資料建構流程**：設計可產生三類軌跡（僅GUI軌跡、僅CLI軌跡、GUI與CLI交錯軌跡）的資料建構流程，並據此發布HybridCUA-8K資料集（5K混合軌跡＋3K已驗證RLVR任務）。
- **兩階段訓練框架**：提出「監督式微調（SFT）→ 具CLI感知獎勵的強化學習」兩階段訓練框架，使模型學會在任務執行中選擇性地且可靠地切換使用CLI。
- **實驗成效與跨平台泛化能力**：HybridCUA-9B在OSWorld基準測試中達到53.6%準確率，較基礎模型提升14.8個百分點，並在WindowsAgentArena上提升4.0個百分點，驗證了混合GUI與CLI範式的有效性與跨平台泛化能力。

### 適合對象
從事電腦使用代理（Computer-Use Agents）、多模態大型語言模型（MLLM）、強化學習（特別是RLVR）、人機互動介面設計，以及自動化數位任務執行相關研究的學者與工程師；亦適合關注GUI與CLI整合、跨平台代理泛化能力及AI訓練資料建構流程的業界研發人員閱讀。

## 深度分析

#### 方法論解析

HybridCUA 的核心方法論建立在兩個關鍵觀察之上：其一，現有電腦使用代理（Computer-Use Agents, CUAs）受限於單一介面範式，無法兼顧通用性與效率；其二，混合監督訊號的缺失導致模型無法學習「何時」與「如何」使用命令列介面（Command Line Interface, CLI）。論文提出的解決方案是一個統一的資料與訓練框架，涵蓋資料建構、監督式微調（Supervised Fine-Tuning, SFT）與可驗證獎勵強化學習（Reinforcement Learning with Verifiable Rewards, RLVR）三個環節。

**問題形式化（Problem Formulation）**

作者將電腦使用任務形式化為部分可觀察馬可夫決策過程（Partially Observable Markov Decision Process, POMDP），定義為 $M = \langle S, A, P, R, \Omega, O, \gamma \rangle$。此形式化的關鍵在於動作空間 $A$ 不再僅限於 GUI 動作（如點擊、輸入），而是擴展為 GUI 動作與殼層命令（shell commands）的聯合空間。這種設計使模型能在每個決策步驟中選擇最合適的介面，而非被動遵循單一互動模式。

**資料建構流程（Data Construction Pipeline）**

HybridCUA-8K 資料集採用三軌並行的建構策略：

1. **僅 GUI 軌跡（GUI-only trajectories）**：從開源資料集轉換而來，提供視覺互動的基礎監督訊號。
2. **僅 CLI 軌跡（CLI-only trajectories）**：透過強模型取樣並搭配執行框架（execution harness）驗證，確保命令的正確性與可執行性。
3. **交錯軌跡（interleaved trajectories）**：透過兩種方式產生——自由形式介面切換（free-form interface switching）與 GUI 到 CLI 改寫（GUI-to-CLI rewriting）。後者利用「許多 GUI 動作序列存在等效殼層命令」的觀察，將冗長的點擊序列壓縮為單一命令。

此設計的精妙之處在於：交錯軌跡不僅展示混合行為，更透過 GUI-to-CLI 改寫明確標示出「哪些步驟適合用 CLI 替代」，為後續獎勵設計提供監督基礎。

**兩階段訓練框架（Two-Stage Training Framework）**

第一階段為標準 SFT，在 5,000 條軌跡上進行監督式學習，使模型初步掌握 GUI 與 CLI 的混合互動模式。第二階段為線上代理強化學習（online agentic RL），在雙介面環境中以 CLI 感知獎勵（CLI-aware rewards）進行優化。獎勵函數設計分為兩個層次：

- **任務級獎勵 $R_{\text{CLI}}$**：教導模型「何時」呼叫 CLI，透過任務完成度與 CLI 使用適切性的聯合評估，引導模型選擇最具執行優勢的介面。
- **動作級獎勵 $R_{\text{exec}}$**：教導模型「如何」正確執行命令，利用終端機回饋（terminal feedback）改善命令可靠性。

這種獎勵分解設計直接對應論文所識別的兩項缺口——介面選擇的監督盲點與命令執行的可靠性問題，使介面路由（interface routing）與命令執行成為可學習的明確訊號。

#### 實驗數據解讀

**主要效能指標**

HybridCUA-9B 在 OSWorld 基準上達到 53.6% 準確率（accuracy），較基礎模型提升 14.8 個百分點（percentage points），在同尺寸模型中表現最佳。更值得注意的是其在 WindowsAgentArena 上達到 36.0%，較基礎模型提升 4.0 個百分點，驗證了跨平台泛化能力（cross-platform generalizability）。

**CLI 使用率分析**

模型在 64.0% 的步驟中使用 CLI，與最重度依賴 CLI 的基準模型相當。然而，關鍵差異在於：該基準模型因過度使用 CLI 而導致效能下降，HybridCUA-9B 則在高效使用 CLI 的同時實現效能提升。這驗證了論文的核心理論——效能提升源自「知道何時與如何使用殼層」，而非單純增加命令使用頻率。

**消融與對比實驗的意涵**

圖 2a 揭示一個反直覺的現象：為四個代表性代理加入 CLI 介面後，OSWorld 準確率反而下降 2.5 至 11.5 個百分點。這說明單純賦予模型 shell 存取權限並無助益，甚至有害，因為模型缺乏將 shell 存取轉化為有效動作的能力。圖 2b 進一步顯示 Qwen3.5-27B 與 EvoCUA-32B 的 CLI 步驟佔比分別僅為 15.0% 與 0.15%，反映「不知道何時使用 CLI」的問題。

**獎勵設計的驗證邏輯**

$R_{\text{CLI}}$ 與 $R_{\text{exec}}$ 的分離設計具有清晰的實驗意涵：前者解決路由錯誤（routing errors），後者解決執行錯誤（execution errors）。這種分解使消融實驗能精確定位每個獎勵組件的貢獻，也為未來研究提供了可組合的獎勵設計範式。

#### 與現有研究的比較

**與 GUI 專用代理的比較**

相較於僅依賴 GUI 互動的代理（如基於大規模 GUI 資料集訓練的模型），HybridCUA 的優勢在於突破了「原子動作」（atomic actions）的效率瓶頸。對於涉及檔案操作、文本編輯或重複操作的任務，GUI 序列往往冗長且易產生連鎖錯誤（cascading errors），而 CLI 可將其壓縮為單一命令。

**與 API/工具增強代理的比較**

MCPWorld、OSWorld-MCP、ComputerRL、UltraCUA、ToolCUA、UI-TARS-2 等工作透過應用程式特定 API 或 MCP 工具擴展動作空間。雖然能加速特定任務，但其覆蓋範圍與可移植性受限於預定義介面。HybridCUA 的 CLI 方案則利用作業系統原生提供的殼層，無需為每個應用程式建構專用介面，具有更佳的可擴展性。

**與近期混合工作的比較**

CUA-Universe 與 RecreationWorld 是最接近的兩項相關工作。差異在於：CUA-Universe 使用視覺語言模型（VLM）評分而非任務特定的程式化驗證，回饋過於粗糙不適合線上訓練；RecreationWorld 雖提供可驗證環境，但僅監督任務結果，介面選擇仍隱含於軌跡模仿中。HybridCUA 的突破在於將介面選擇本身納入學習訊號，透過 CLI 感知獎勵直接監督介面路由與命令可靠性。

**限制與未解決問題**

儘管成果顯著，仍存在若干限制：首先，CLI 使用率 64.0% 雖優於基準，但「何時使用 CLI」的決策邊界仍可能受訓練資料分布影響，對訓練未覆蓋的任務類型泛化能力有待驗證。其次，獎勵函數依賴任務級程式化驗證器，對於難以自動驗證的任務（如創意設計），CLI 感知獎勵的適用性受限。此外，CLI 命令的執行安全性與錯誤恢復機制在論文中未深入討論。

#### 可重現性評估

**資料與模型的可取得性**

論文明確聲明將釋出軌跡資料、RLVR 任務、資料生成與訓練流程，以及 HybridCUA-9B 模型權重。HybridCUA-8K 資料集（5,000 軌跡 + 3,000 已驗證 RLVR 任務）的釋出為後續研究提供了寶貴資源，特別是其中標註「CLI 使用是否提供明確執行優勢」的任務標籤，可直接用於研究介面選擇的決策模式。

**訓練流程的可重現性**

兩階段訓練框架（SFT + RLVR with CLI-aware rewards）的設計相對標準，主要超參數與獎勵權重若在論文中充分披露，應能支援獨立重現。然而，RLVR 階段的線上環境配置、執行框架的具體實作細節，以及強模型取樣 CLI 軌跡時的提示工程（prompt engineering）策略，可能成為重現的潛在障礙。

**評估的可重現性**

OSWorld 與 WindowsAgentArena 均為公開基準測試，評估流程可標準化重現。但需注意 OSWorld 環境的隨機性與任務版本演進可能影響結果的精確比較。

#### 未來研究方向

**多介面擴展與動態路由**

當前框架僅整合 GUI 與 CLI 兩種介面，未來可探索納入更多介面類型（如語音控制、API 呼叫、程式語言介面），並發展動態路由機制。關鍵研究方向包括：如何讓模型根據任務特性、當前狀態與歷史軌跡，自主決定最優介面組合；以及如何處理介面間的狀態同步與錯誤傳播。

**獎勵函數的理論化與泛化**

CLI 感知獎勵的成功驗證了「介面選擇作為顯式學習訊號」的價值。未來可探索更系統化的獎勵設計理論，例如：基於資訊理論的介面選擇度量、考慮長期規劃的獎勵塑形（reward shaping），以及在無可驗證獎勵場景下的替代監督訊號（如偏好學習）。

**安全性與可靠性強化**

CLI 命令的執行具有不可逆性（如 `rm -rf`），未來研究應著重於：發展命令預執行驗證機制、設計安全的命令沙箱（sandbox）、建立錯誤恢復與回滾策略，以及研究模型對抗性攻擊的防禦。這對於將混合代理部署至真實環境至關重要。

**跨平台與跨裝置泛化**

雖然 WindowsAgentArena 的結果證實了跨平台泛化能力，但 macOS、行動裝置、嵌入式系統等平台的 CLI 語義與 GUI 結構存在差異。未來可探索統一的多平台混合代理架構，以及針對特定平台優化的介面路由策略。

**與人類協作模式的整合**

當前代理以自主執行為主，未來可探索人機協作模式：模型主動詢問人類何時使用 CLI、對高風險命令請求確認，或在 GUI 與 CLI 之間切換時提供可解釋的決策依據。這將提升代理在敏感場景中的可信度與可控性。

## 論文問答

**Q1：HybridCUA 試圖解決的核心問題是什麼？為何電腦使用代理需要同時整合 GUI 與 CLI？**
A：HybridCUA 試圖解決的核心問題是現有電腦使用代理（CUA）在介面選擇上的「雙重盲點」——它們既不知道「何時」該使用命令列介面（CLI），也不知道「如何」將 GUI 操作有效轉化為殼層命令。傳統 CUA 僅依賴圖形使用者介面（GUI）的點擊與按鍵輸入，雖然具備跨應用程式的通用性，但對於檔案處理、批次編輯等任務往往需要冗長的動作序列，容易產生連鎖錯誤並降低效率。CLI 雖然能以單一命令取代多步 GUI 操作，卻缺乏視覺互動能力。作者主張下一代 CUA 應採混合 GUI 與 CLI 範式，兼顧 GUI 的通用性與 CLI 的程式化效率，這也是 HybridCUA 立論的基礎。

**Q2：為何現有的 GUI-only 代理與 API 增強代理都無法滿足需求？**
A：GUI-only 代理受限於原子化動作（點擊、輸入、捲動），在面對重複性或可程式化任務時效率低落，且長動作序列容易累積連鎖錯誤。應用程式特定 API 或工具（如 MCP）雖然能加速操作，但每個介面都需針對特定應用程式手工建置，工程成本高昂且難以跨應用擴展。更關鍵的是，論文的 Figure 2a 顯示，當直接為現有代理開放 CLI 存取時，四個代表性代理在 OSWorld 上的表現反而下滑 2.5 至 11.5 個百分點，證明「擁有 shell 存取權」與「能有效運用 shell」是兩回事，這正是 HybridCUA 要填補的能力鴻溝。

**Q3：為什麼「知道何時與如何使用 CLI」是電腦使用代理發展的關鍵瓶頸？**
A：這個問題之所以關鍵，是因為它揭示了當前 CUA 訓練資料與監督訊號的兩項結構性缺口。首先，訓練資料呈現「孤島化」現象：CUA 資料集幾乎只包含 GUI 動作，而終端機與程式碼資料集則缺少 GUI 情境，導致模型從未見過混合行為的示範。其次，監督訊號對介面選擇「視而不見」：步驟級模仿只獎勵局部似真的動作，結果獎勵僅檢查任務是否完成，兩者都無法區分「選擇了恰當介面」與「雖完成任務但路徑冗長」。HybridCUA 的重要性在於它首次把介面編排（orchestration）從隱性行為提升為顯性訓練目標，使代理能學會依任務特性彈性切換 GUI 與 CLI。

**Q4：HybridCUA 的核心方法是什麼？其資料建構流程如何運作？**
A：HybridCUA 的核心方法是建構一個可擴展的資料生成流程，產出三類互補軌跡：僅 GUI 軌跡（從開源資料集轉換而來）、僅 CLI 軌跡（由強模型搭配執行框架取樣）以及交錯軌跡（透過自由形式介面切換與 GUI 到 CLI 改寫獲得）。其關鍵觀察是「許多 GUI 動作序列存在等效的殼層命令」，因此不必從零收集混合監督，而是可系統性地將現有 GUI 軌跡改寫為混合形式。最終形成的 HybridCUA-8K 包含 5,000 條軌跡與 3,000 個已驗證 RLVR 任務，每個任務皆標註 CLI 使用是否具備明確執行優勢，為後續訓練提供高品質且語意平衡的監督訊號。

**Q5：HybridCUA 在訓練框架上的關鍵創新為何？**
A：訓練框架的關鍵創新在於採用兩階段設計，並首度引入「CLI 感知獎勵」使介面編排成為可學習的訊號。第一階段在 5,000 條軌跡上進行監督式微調（SFT），讓模型學會混合行為的表面模式；第二階段在 3,000 個已驗證任務上進行可驗證獎勵強化學習（RLVR），並設計兩個 CLI 感知獎勵：任務級獎勵 R_CLI 教導模型「何時」呼叫 CLI，動作級獎勵 R_exec 則利用終端機回授教導模型「如何」可靠執行命令。這種把介面路由與命令執行分離監督的設計，是 HybridCUA 區別於 CUA-Universe（僅以 VLM 評分）與 RecreationWorld（僅監督任務結果）等先前混合代理研究的根本差異。

**Q6：HybridCUA 在資料與獎勵設計上做了哪些關鍵取捨？**
A：在資料層面，作者選擇「改寫而非從零收集」的策略，藉由 GUI 到 CLI 改寫充分利用既有 GUI 軌跡，大幅降低蒐集成本並兼顧多樣性。在獎勵層面，刻意將 R_CLI 與 R_exec 分離，而非合併為單一獎勵，目的是讓模型能分別學會「路由判斷」與「命令正確性」兩種能力，避免單一稀疏訊號造成的學習困難。此外，3,000 個 RLVR 任務皆經過程式化驗證，確保獎勵訊號可信且可重現，這與僅以 VLM 評分或僅看最終結果的做法相比，提供更細緻且可線上訓練的回饋。

**Q7：HybridCUA 在哪些基準測試上評估？這些基準各自代表什麼能力？**
A：HybridCUA 主要在兩個基準上評估：OSWorld 與 WindowsAgentArena。OSWorld 是 Linux 桌面環境的綜合性電腦使用基準，涵蓋檔案管理、瀏覽器操作、系統設定等多樣化任務，用以衡量代理在開放式桌面情境下的泛化能力；WindowsAgentArena 則是 Windows 平台基準，用以驗證跨平台泛化能力。選擇這兩個基準的策略意義在於：OSWorld 證明混合範式在主流 Linux 桌面有效，而 WindowsAgentArena 則驗證所學的 GUI–CLI 編排能力能否遷移至不同作業系統與應用程式生態，是衡量「跨平台泛化能力」的關鍵測試。

**Q8：HybridCUA-9B 的關鍵實驗結果為何？這些數字透露了什麼訊息？**
A：HybridCUA-9B 在 OSWorld 上達到 53.6% 準確率，較基礎模型提升 14.8 個百分點，並在同規模模型中達到最先進水準；在 WindowsAgentArena 上則達到 36.0%，較基礎模型提升 4.0 個百分點。更值得注意的是，HybridCUA-9B 在 64.0% 的步驟中使用 CLI，與 CLI 使用率最高的基準相當，但卻在該基準退步時「進步」，證明效能提升來自於「知道何時與如何使用」而非「更頻繁使用」。這個對比直接驗證了論點：CLI 的價值不在於使用頻率，而在於編排智慧，這也是 HybridCUA 對電腦使用代理領域最重要的經驗性貢獻。

**Q9：論文中有哪些消融實驗或對比分析支持其設計選擇？**
A：論文中 Figure 2 的對比分析是最關鍵的消融證據：當僅為現有代理開放 CLI 存取而未調整訓練時，四個代理在 OSWorld 上平均下滑 2.5 至 11.5 個百分點，證明「單純賦予 shell 存取權」並無助益，甚至有害。Figure 2b 進一步顯示 Qwen3.5-27B 與 EvoCUA-32B 的 CLI 步驟占比分別僅有 15.0% 與 0.15%，說明它們「不知道何時該用 CLI」。HybridCUA-9B 在 CLI 使用率達 64.0% 的同時仍能提升效能，與上述基準形成鮮明對比，間接證明了 CLI 感知獎勵與混合監督資料的必要性，雖然論文未提供更細粒度的逐項消融，但此對比已足以支持其核心設計選擇。

**Q10：HybridCUA 在哪些實際場景最具應用價值？**
A：HybridCUA 在需要混合視覺互動與程式化操作的場景中價值最高，例如：批次檔案重新命名、系統設定調整、開發者工作流程（git 操作、套件安裝）、辦公室文件處理（試算表批次編輯、郵件歸檔）等。這類任務的共同特徵是「部分步驟需要 GUI 視覺確認（如開啟應用程式、瀏覽對話框），部分步驟則可由 CLI 一次完成（如批次處理、檔案搜尋）」。在企業 IT 自動化、軟體測試、數位流程機器人（RPA）等領域，HybridCUA 的混合編排能力可望顯著降低任務完成時間與錯誤率，特別是在需要跨應用程式協作的真實工作流程中。

**Q11：若將 HybridCUA 部署為產品，需要考量哪些工程與安全因素？**
A：產品化 HybridCUA 需考量三大工程因素：第一，CLI 執行的沙箱化與權限控管，因為殼層命令可直接存取檔案系統與系統資源，必須設計嚴格的權限邊界與可撤銷機制；第二，命令驗證與可逆性，模型生成的命令可能誤刪檔案或修改系統設定，需提供「乾跑（dry-run）」預覽與一鍵復原功能；第三，使用者信任建立，介面切換的決策應對使用者透明，例如顯示「為何此步驟選擇 CLI 而非 GUI」的解釋，以利除錯與稽核。此外，跨平台部署時需處理不同作業系統的 CLI 語法差異（PowerShell 與 bash），這對 WindowsAgentArena 上僅 4.0 百分點的提升幅度提示了跨平台適應仍是工程難點。

**Q12：HybridCUA 對電腦使用代理領域的整體影響為何？**
A：HybridCUA 對領域的影響體現在三個層面：方法論上，它把「介面編排」從隱性行為提升為顯性學習目標，為後續研究提供了「CLI 感知獎勵」的可複製範式；資料上，HybridCUA-8K 與其生成流程公開後，將降低混合監督資料的蒐集門檻；實證上，跨平台（Linux 與 Windows）的效能提升證明了混合範式的可行性，可能促使更多研究從「純 GUI」或「純 API」轉向「GUI–CLI 混合」。長期而言，這項工作可能推動 CUA 從「模擬人類操作」轉向「善用機器原生能力」，重新定義人機協作中代理應扮演的角色。

**Q13：HybridCUA 存在哪些已承認的限制？**
A：論文中可推論的限制包括：其一，HybridCUA-9B 僅 9B 參數，雖然在同規模中表現最佳，但與更大模型（如 32B 以上）相比仍有差距，規模化效益尚未充分探索；其二，CLI 使用率達 64.0% 雖證明編排能力，但對於高度視覺依賴的任務（如圖形設計、影片剪輯），CLI 的適用性仍有限；其三，跨平台提升幅度（WindowsAgentArena +4.0 百分點）小於 OSWorld（+14.8 百分點），暗示 CLI 語法差異與 Windows 生態的特殊性仍是挑戰；其四，3,000 個 RLVR 任務的覆蓋範圍有限，面對未見過的應用程式組合時，泛化能力仍待驗證。

**Q14：HybridCUA 在哪些情境下可能失敗？**
A：HybridCUA 可能失敗的情境包括：第一，當任務需要高度 GUI 視覺判斷（如辨識圖片內容、處理非標準化介面）時，CLI 介入可能無用甚至干擾；第二，當 CLI 命令需要特定環境設定（如未安裝的套件、特殊權限）時，R_exec 獎勵雖能改善命令可靠性，但無法解決環境本身的限制；第三，當任務跨越多個具有不同安全模型的應用程式時，模型可能誤判介面切換時機，導致動作序列不連貫；第四，對於需要精確視覺對齊的操作（如拖曳、繪圖），CLI 無法取代 GUI，這類任務仍須回歸純 GUI 模式，而模型是否能正確判斷「此時不該用 CLI」則是 R_CLI 獎勵能否泛化的關鍵考驗。

**Q15：HybridCUA 的未來研究方向為何？**
A：未來研究方向可朝四個方向延伸：第一，擴大混合介面範疇，從 GUI–CLI 二元編排擴展至包含 API、瀏覽器腳本、語音等多模態介面的統一編排；第二，引入更細粒度的獎勵設計，例如對命令的時間成本、風險等級進行評分，使模型學會「效率與安全」的權衡；第三，結合大型推理模型強化長程規劃能力，使介面選擇能基於多步預測而非局部貪婪；第四，探索個人化編排，根據使用者偏好與裝置特性動態調整介面使用策略。此外，將 HybridCUA 與程式設計代理（如 Claude Code）的能力互補，讓 CUA 不僅執行任務還能撰寫可重複使用的腳本，將是邁向真正「通用數位助手」的關鍵一步。

## 實務應用指南

### 適用場景

1. **企業 IT 自動化與桌面流程機器人（RPA 2.0）**：在 Windows 與 Linux 桌面環境中，自動執行跨應用程式任務，例如從 Excel 匯出資料、用 CLI 工具（`awk`、`sed`、`jq`）批次清洗後，再透過 GUI 將結果填入 CRM 系統。HybridCUA 的混合介面能力可避免傳統 GUI-only 代理在長動作序列中累積的連鎖錯誤。

2. **軟體品質保證與回歸測試**：QA 工程師可讓代理在 CI/CD 失敗後，自動開啟截圖、定位錯誤訊息，並透過 CLI 執行 `git bisect`、`pytest --collect-only` 等偵錯指令，再回到 GUI 驗證修復結果，縮短除錯循環。

3. **無障礙輔助與生產力工具**：為行動不便或重度鍵盤使用者打造個人助理，在 LibreOffice、GIMP 等 GUI 應用中以 CLI 巨集或腳本取代繁瑣點擊路徑，同時保留視覺互動的直覺性。

4. **跨平台遷移與設定部署**：在 macOS、Windows、Linux 之間批次調整系統偏好、套件管理（`brew`、`apt`、`winget`）與應用程式設定，CLI 處理可程式化部分，GUI 處理需要視覺確認的對話框或權限請求。

5. **安全研究與數位鑑證（Digital Forensics）**：分析師可在隔離環境中以 CLI 快速擷取日誌、雜湊檔案，再用 GUI 開啟鑑識工具（如 Autopsy）進行視覺化標註與報告產出。

### 實作前置條件

**資料需求**
- 至少數百筆高品質 GUI 軌跡（可從開源資料集如 OSWorld、Aguvis 轉換），用於 SFT 階段的 GUI-only 監督。
- 對應任務的 CLI 等價命令集，需具備可程式化驗證腳本（Python + `subprocess` 或 shell assertion）。
- 標註「CLI 是否具執行優勢」的二元標籤，用於 RLVR 的 `R_CLI` 獎勵計算。
- 建議參考 HybridCUA-8K 的規模（5K 軌跡 + 3K 驗證任務）作為下限。

**運算資源**
- SFT 階段：單節點 8×A100/H100（80GB）即可處理 9B 規模模型的全參數微調；若使用 LoRA，可降至 4×A100。
- RLVR 階段：需要可並行啟動多個 OSWorld / WindowsAgentArena 風格的容器化環境（Docker + VNC/Xvfb），建議至少 16–32 個並行 rollout worker。
- 儲存：軌跡資料約 50–200 GB（取決於截圖解析度），RLVR 經驗池另需 100 GB 以上。

**技能門檻**
- 熟悉多模態模型訓練流程（Hugging Face Transformers、vLLM 部署）。
- 具備強化學習實作經驗（GRPO / PPO 變體、reward shaping）。
- Linux 系統管理能力（容器化、shell 腳本、權限沙箱）。
- 對 OSWorld、WindowsAgentArena 等基準的評估協議有實務理解。

### 實作步驟建議

1. **界定任務範圍與介面分流規則**：盤點目標任務，逐一判斷哪些步驟適合 CLI（批次、可程式化、可逆）、哪些必須 GUI（視覺確認、拖放、無 CLI 等價物）。此規則將直接影響資料標註與獎勵設計。

2. **建構三類軌跡資料**：
   - **GUI-only 軌跡**：從既有 CUA 資料集轉換，保留截圖與原子動作。
   - **CLI-only 軌跡**：以強模型（如 GPT-4o、Claude）搭配執行框架（execution harness）採樣，確保每條命令可被驗證。
   - **交錯軌跡**：混合「自由形式介面切換」與「GUI-to-CLI 改寫」兩種生成方式，後者可將冗長 GUI 序列壓縮為單一命令。

3. **標註 RLVR 任務**：為每個任務加上「CLI 優勢標籤」，並準備可程式化驗證器（檔案存在、內容比對、系統狀態檢查），用於 `R_CLI` 與 `R_exec` 兩個獎勵。

4. **兩階段訓練**：
   - **階段一（SFT）**：在 5K 軌跡上做監督式微調，學習何時切換介面、如何撰寫可靠命令。
   - **階段二（RLVR）**：在雙介面環境中做線上強化學習，`R_CLI` 教導「何時」用 CLI，`R_exec` 利用終端回授（exit code、stderr）教導「如何」用得正確。

5. **部署與監控**：以 vLLM 或 SGLang 部署 HybridCUA-9B，搭配動作執行器（PyAutoGUI / `xdotool` + shell wrapper）。上線後持續記錄 CLI 使用率、任務成功率、平均步數，建立回歸基準。

6. **跨平台驗證**：先在 Linux（OSWorld）驗證，再遷移至 Windows（WindowsAgentArena），檢查命令可用性差異（PowerShell vs. bash）並補齊對應資料。

### 潛在風險與注意事項

- **CLI 誤用導致災難性動作**：`rm -rf`、`chmod 777`、誤寫入系統設定檔等命令可能造成不可逆損害。**緩解**：在沙箱環境執行、強制白名單、對高風險命令要求二次確認、為每個動作設定快照與還原點。

- **獎勵 hacking（Reward Hacking）**：模型可能學會「為了拿 CLI 獎勵而濫用 CLI」，或用無意義命令湊步數。**緩解**：在 `R_CLI` 中加入「CLI 使用率上限」與「命令語意有效性檢查」，並對照人類示範的 CLI 比例分佈。

- **GUI 截圖解析漂移**：不同作業系統版本、DPI 縮放、深色模式會破壞視覺接地（visual grounding）。**緩解**：在訓練資料中納入多樣化外觀樣本，並定期以真機截圖重新校驗。

- **跨平台命令不相通**：bash 指令在 PowerShell 無法直接執行。**緩解**：維護雙語命令對照表，或在 Windows 環境額外微調；評估時分平台報告指標。

- **資料洩漏與隱私**：軌跡中可能含有真實個資或公司機密。**緩解**：使用合成資料或去識別化工具（Microsoft Presidio），並在資料合約中明確規範使用範圍。

- **基準過擬合**：在 OSWorld 上表現優異不代表真實使用者任務同樣有效。**緩解**：建立內部私有評估集，涵蓋長序列、多應用切換、異常恢復等場景。

### 與其他技術的整合建議

- **與 MCP（Model Context Protocol）工具生態整合**：HybridCUA 的 CLI 能力可作為 MCP server 的補充——當 MCP 缺乏對應工具時，自動降級至 shell 呼叫；反之，CLI 結果可透過 MCP 回傳結構化資料給其他代理。

- **與程式設計代理（Claude Code、OpenClaw）協作**：將 HybridCUA 定位為「桌面操作層」，由程式設計代理負責程式碼生成與版本控制，HybridCUA 負責執行 GUI 驗證與 CLI 部署，形成「寫程式 ↔ 跑程式」的閉環。

- **與傳統 RPA 平台（UiPath、Power Automate）共存**：對於已有 RPA 流程的企業，可將 HybridCUA 作為「例外處理層」——當結構化流程遇到未預期 UI 變化時，交由 HybridCUA 動態決策，事後再將成功路徑回灌為 RPA 腳本。

- **與觀測與稽核系統整合**：將每次 CLI 呼叫與 GUI 動作寫入 OpenTelemetry trace，串接 SIEM（Splunk、Elastic）進行異常偵測與合規稽核。

- **與多代理編排框架（LangGraph、AutoGen）整合**：HybridCUA 可作為「執行者（executor）」節點，上層由規劃代理決定任務分解，HybridCUA 負責實際介面操作，並回報結構化進度。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的問題陳述（圖 2 的「加了 CLI 反而變差」現象）與第 3.1 節的問題形式化，理解「為什麼單純給模型 shell 不夠」。實作上可先從 HybridCUA-8K 的小型子集開始，用 Hugging Face Transformers + LoRA 跑通 SFT pipeline，再逐步加入 RLVR。

**給 AI 工程師**：重點關注第 3 節的資料建構流程與獎勵設計（`R_CLI` 與 `R_exec` 的解耦），以及第 4 節（若可取得）的訓練細節。建議直接以 HybridCUA-9B 為起點做領域微調，並建立內部評估集驗證「CLI 使用率 vs. 成功率」是否符合論文中 64% 的甜蜜點。

**給研究者**：本論文的核心洞見在於「介面選擇本身應成為學習信號」，可延伸至多個方向：探索其他介面（語音、API、機器人手臂）的統一編排、研究 CLI 使用率與任務難度的理論關係、或將 CLI-aware reward 推廣至程式設計代理的測試案例生成。資料建構流程中的「GUI-to-CLI 改寫」也值得獨立研究其可逆性與正確性邊界。

**給產品經理**：關鍵訊息是「HybridCUA-9B 在 OSWorld 提升 14.8 個百分點、跨平台通用」，代表混合介面是當前 CUA 產品的務實演進路徑。建議在產品 roadmap 中規劃「GUI 為主、CLI 為輔」的混合模式，優先處理內部 IT 自動化、QA 回歸測試等高 ROI 場景，並將 CLI 使用率與任務成功率作為核心監控指標，避免過度強調「自動化比例」而忽略可靠性。
