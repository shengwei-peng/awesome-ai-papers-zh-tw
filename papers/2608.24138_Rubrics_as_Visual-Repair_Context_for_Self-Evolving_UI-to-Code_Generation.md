# 以評分準則作為自我演化式 UI 轉程式碼生成之視覺修復情境

## ⚡ TL;DR

UI轉程式碼生成存在視覺修復耦合：局部編輯會透過版面與樣式相依性引發非局部退化，使自我演化不穩定。
本文提出RubSE框架，以評分準則建立結構化視覺修復情境，並透過演化、選擇與歷史引導範圍明確的修復。
跨六模型與三基準，RubSE於最終與最佳回合均優於天真自我演化，提升穩定性、軌跡上限並減緩軌跡崩潰。

## 摘要翻譯

大型視覺語言模型（Large Vision-Language Models, VLMs）在 UI 轉程式碼生成（UI-to-Code Generation）方面已展現長足進展，然而其測試時自我演化（Test-Time Self-Evolution）仍不穩定。本研究首先指出一項根本性障礙，稱為視覺修復耦合（Visual Repair Coupling）：局部程式碼編輯（Local Code Edit）可能透過版面配置（Layout）、樣式（Style）與元件相依性（Component Dependencies）傳播，在修正一處視覺不匹配（Visual Mismatch）的同時，使原本忠實呈現的區域退化。為解決此問題，我們提出 RubSE（Rubric-guided Self-Evolution framework），一個評分準則引導的自我演化框架，將視覺回饋（Visual Feedback）以評分準則（Rubrics）形式表達為結構化視覺修復情境（Structured Visual-Repair Context）。在每個細化回合（Refinement Round）中，RubSE 生成具類型候選評分準則（Typed Candidate Rubrics）、選取一個優先修復目標（Prioritized Repair Target），並將先前選取的評分準則儲存為修復歷史（Repair History），從而引導每次修訂朝向範圍明確的視覺修復（Well-Scoped Visual Repair），同時避免重複或過度廣泛的修改（Over-Broad Changes）。跨六個視覺語言模型（VLMs）與三個 UI 轉程式碼生成基準測試（Benchmarks）的評估顯示，RubSE 在最終回合設定（Final-Round Setting）與最佳回合設定（Best-Round Setting）下均大幅優於天真自我演化（Naïve Self-Evolution），達到更穩定的細化軌跡（Refinement Trajectory）與更高的軌跡層級效能上限（Trajectory-Level Performance Ceiling）。進一步分析顯示，RubSE 透過提升從嚴重視覺迴歸（Severe Visual Regressions）中恢復的能力，緩解軌跡崩潰（Trajectory Collapse）；且更強大的評分準則生成器（Rubric Generators）能將有效的視覺修復指引轉移至較弱的程式碼改進模型（Code Improvers）。

### 核心貢獻（3～5點）
- 揭示 UI 轉程式碼生成中測試時自我演化的核心障礙——視覺修復耦合（Visual Repair Coupling），說明局部程式碼編輯可能因版面配置、樣式與元件相依性而引發連帶視覺退化。
- 提出 RubSE（Rubric-guided Self-Evolution framework），以評分準則（Rubrics）將視覺回饋結構化為視覺修復情境，並透過生成、選取與歷史儲存機制，引導每次修訂朝向範圍明確的視覺修復。
- 在六個視覺語言模型與三個基準測試上驗證，RubSE 相較於天真自我演化，在最終回合與最佳回合設定下均達成更穩定的細化軌跡與更高的軌跡層級效能上限。
- 證明 RubSE 能透過提升從嚴重視覺迴歸中恢復的能力，緩解軌跡崩潰；並發現強大的評分準則生成器可將有效的視覺修復指引轉移給較弱的程式碼改進模型。

### 適合對象
本論文適合對視覺語言模型（VLMs）、UI 轉程式碼生成、測試時改進（Test-Time Improvement）與自我演化（Self-Evolution）感興趣的研究人員與工程師，特別是關注如何透過結構化視覺回饋提升多回合程式碼細化穩定性的前端自動化、人機互動與機器學習領域讀者。

## 深度分析

#### 方法論解析

本研究針對 UI-to-Code Generation（UI 轉程式碼生成）在 Test-Time Self-Evolution（測試時自我演化）場景下的不穩定性，提出 RubSE（Rubric-guided Self-Evolution framework，評分準則引導的自我演化框架）。其核心洞見在於：傳統的 generate–critique–revise loops（生成–評論–修訂迴圈）雖然在純文字任務中表現良好，但在 UI 轉程式碼任務中會遭遇 Visual Repair Coupling（視覺修復耦合）——局部的程式碼修改會透過 Layout（版面配置）、Style（樣式）與 Component Dependencies（元件相依性）傳播，導致原本正確的區域被連帶破壞。

為了解決這個問題，RubSE 將 Visual Feedback（視覺回饋）重新定義為 Structured Visual-Repair Context（結構化視覺修復情境）。具體來說，每一次 Refinement Round（細化回合）都會產生一組 Typed Candidate Rubrics（具類型候選評分準則），每一條 rubric（評分準則）都包含三個要素：(1) 具體的 Visual Failure（視覺錯誤）描述；(2) 對應的 Predefined Visual Aspect（預先定義的視覺面向），例如 Spatial Layout（空間版面配置）、Color（顏色）、Typography（字體排印）、Component Hierarchy（元件階層）或 Visual Density（視覺密度）；(3) 明確的 Correction Direction（修正方向）。這種表示法提供了 Soft Control（軟控制）：它讓 Repair Objective（修復目標）變得明確，但具體如何修改仍交由 Code Improvers（程式碼改進模型）決定，保留了程式碼生成的靈活性。

RubSE 的運作由三個 Atomic Operations（原子操作）組成：

1. **EVOLVE（演化）**：根據 Current Rendering（目前渲染結果）與 Target Screenshot（目標截圖）之間的 Visual Comparison（視覺比較），生成多條候選評分準則。這一步相當於「錯誤發現」，但輸出不是自由形式的評論，而是結構化、可歸類的修復項目。
2. **SELECT（選擇）**：從候選中挑選一條 Prioritized Rubric（優先評分準則）作為下一回合的 Repair Target（修復目標）。透過每次只聚焦一個面向，RubSE 大幅降低了 Broad, Entangled Edits（廣泛且糾纏的編輯）的風險，從而抑制 Visual Coupling（視覺耦合）所造成的非預期渲染變化。
3. **HISTORY（歷史）**：將已選取的評分準則儲存為 Repair History（修復歷史），帶入後續回合。這讓模型記得 Previous Repair Decisions（先前的修復決策），避免 Repeated Failures or Regressions（重複失敗或迴歸），同時也提醒模型哪些區域已經被處理過、應予以保留。

這三個操作把 Naïve Self-Evolution（天真自我演化）中經常混淆的三種角色——發現錯誤、選擇聚焦目標、保存跨回合情境——明確分離。整體流程為：生成程式碼草稿 → 渲染 → 視覺比較 → EVOLVE 產生候選 rubrics → SELECT 選出單一目標 → 結合 HISTORY 修訂程式碼 → 更新 HISTORY。如此反覆進行，形成一個導向 Well-Scoped Visual Repair（範圍明確的視覺修復）的迭代過程。

從設計哲學來看，RubSE 同時控制了「應該改什麼」與「應該保留什麼」。Free-Form Critique（自由形式評論）往往只告訴模型錯誤所在，容易誘發 Over-Broad Changes（過度廣泛的修改）；而 rubric 則把視覺回饋轉換成帶有類型標籤與修正方向的結構化提示，讓 Code Draft（程式碼草稿）的每次修訂都更局部、更可追蹤。此外，RubSE 將 rubric generator（評分準則生成器）與 code improver（程式碼改進模型）解耦，這不僅讓系統模組化，也為「強模型產生 rubric、弱模型執行修復」的轉移學習奠定基礎。

#### 實驗數據解讀

本研究在六個 VLMs（Vision-Language Models，視覺語言模型）與三個 UI-to-Code 基準測試上進行評估，比較 RubSE 與 Naïve Self-Evolution 的差異。評估分為 Final-Round Setting（最終回合設定）與 Best-Round Setting（最佳回合設定）兩種：前者關注迭代結束時的表現，反映 Trajectory（軌跡）末端的穩定性；後者關注整條軌跡中的最佳表現，反映 Trajectory-Level Performance Ceiling（軌跡層級效能上限）。

主要結果顯示：

- 在 18 組設定中，RubSE 有 15 組在 Final-Round Setting 優於 Naïve Self-Evolution，平均提升 +1.20 overall points 與 +0.11 aspect-mean score。
- 在 Best-Round Setting 中，RubSE 有 14 組表現更佳，平均提升 +1.13 overall points。

這些數據可以從幾個角度解讀。首先，Final-Round 的穩定提升意味著 RubSE 有效抑制了 Trajectory Collapse（軌跡崩潰）。文中圖 2 顯示，Naïve Self-Refinement 在 Design2Code 等基準上會出現「初期進步、後期退化」的現象，甚至最終分數低於初始生成；而 RubSE 透過 HISTORY 與 SELECT 的機制，讓後期回合不再輕易破壞已正確的區域。其次，Best-Round 的提升說明 rubric 不僅穩定，還能幫助模型觸及更高的視覺保真度上限——每次聚焦一個具體的 Visual Aspect，使修復動作更為精準。

進一步分析有兩項重要發現：

1. **從 Severe Visual Regressions（嚴重視覺迴歸）中恢復**：RubSE 能加速從嚴重視覺退化中恢復。這對實務非常關鍵，因為一次錯誤的 CSS Rule（CSS 規則）或 Parent Container（父容器）調整，可能讓整個頁面面目全非；而結構化的 rubric 提供了可感知、可執行且範圍明確的修復目標，使模型能逐步拉回正軌。
2. **Rubric 的跨模型轉移性**：研究發現，由 GPT-5.4（一種強大的語言模型）生成的 rubrics，能夠持續提升 Qwen（通義千問視覺語言模型）的自我演化表現。這顯示 rubric 是一種可移植的中間表徵：高品質的視覺判斷可以與較弱的程式碼修改能力分離，從而降低部署成本。

不過，數據解讀也需注意限制。文中未提供每個模型在每個基準上的完整表格，也沒有報告標準差或統計顯著性檢定，因此難以判斷 +1.20 overall points 在該分數尺度上的實際意義。若總分為百分制，這約是 1.2% 的相對提升；若為十分制，則是 12% 的相對提升，意義大相逕庭。此外，aspect-mean score 平均提升 +0.11 雖然顯示一致性，但幅度偏小，可能表示 rubric 對某些視覺面向的改善較為有限。

#### 與現有研究的比較

在 UI-to-Code Generation 領域，既有研究大多聚焦於 Training-Time Improvement（訓練時改進），例如擴充 Instruction-Tuning Data（指令微調資料）或設計 Stage-Wise Training Pipelines（分階段訓練流程）。RubSE 則選擇從 Test-Time Improvement（測試時改進）切入，這與訓練時方法互補：即使基礎模型已經過微調，測試時的結構化回饋仍能進一步提升輸出品質。

在 Self-Evolution（自我演化）與 Generate–Critique–Revise Loops（生成–評論–修訂迴圈）方面，相關研究在文字生成與 General-Purpose Coding Agents（通用程式設計代理）中已相當成熟。然而，這些方法直接套用到 UI 轉程式碼時，會因 Visual Repair Coupling 而產生不穩定 Trajectory。RubSE 的貢獻在於將「評論」升級為「結構化、可類型化、可追蹤的 rubric」，並透過 SELECT 與 HISTORY 控制每次修訂的範圍與記憶。

Rubrics（評分準則）在 LLM/VLM 研究中並非新概念，過去主要用於 LLM-as-a-Judge 系統、醫療或學術評分等開放式領域，作為細粒度評判標準或獎勵信號。RubSE 的創新在於把 rubric 從「評判工具」轉化為「修復情境」：它不只用來打分，更用來引導程式碼修改。相較於單純的 rubric-based reward，RubSE 增加了 EVOLVE–SELECT–HISTORY 的動態循環，使 rubric 成為迭代修復過程中的主動控制訊號。

相較於既有方法，RubSE 的主要優勢包括：

- **結構化回饋抑制過度重寫**：將自由評論轉為具類型的 rubric，降低 Over-Broad Changes 的機率。
- **歷史機制防止震盪**：HISTORY 讓模型記得過去決策，減少在同一問題上反覆擺盪。
- **解耦產生器與改進器**：rubric generator 與 code improver 可分開選擇，強模型的視覺判斷可轉移給弱模型使用。
- **同時提升最終與最佳回合表現**：不僅穩定後期軌跡，也提高整體效能上限。

然而，RubSE 也存在一些相對於理想方法的限制。首先，整體表現高度依賴 rubric generator 的品質：若產生的 rubric 遺漏關鍵錯誤或歸類錯誤的 Visual Aspect，SELECT 選出的 Prioritized Repair Target 也可能失準。其次，每回合只選擇單一 rubric 雖然降低耦合，但對於需要多個面向同時協調修改的複雜 UI，可能顯得過於保守。此外，HISTORY 的管理方式在文中未詳細說明，若只是簡單拼接，長期下來可能導致提示過長或資訊淹沒。最後，研究主要針對 web UI，對於 mobile、desktop 或其他結構–細節生成任務的適用性仍需驗證。

#### 可重現性評估

從提供的資訊來看，本研究提供了專案頁面連結：https://tyxiong23.github.io/rubse。然而，文中並未明確說明是否公開原始碼、資料集或模型權重，也沒有提供 GitHub repository 連結。因此，在可重現性方面處於「部分開放」的狀態：概念與方法已清楚描述，但具體實作細節仍需作者釋出才能完整復現。

有利於重現的因素包括：

- 使用的 Benchmarks（基準測試）如 Design2Code 是公開資料集，其他基準測試若也為公開資料，則資料取得不成問題。
- 實驗採用的 VLMs 多為可透過 API 或開源權重取得的模型（如 GPT 系列、Qwen 等），降低了硬體與模型取得的門檻。
- RubSE 的核心概念簡潔，EVOLVE、SELECT、HISTORY 三個步驟可透過提示工程實現，理論上不需要額外訓練。

不利於重現的因素包括：

- 缺乏公開的提示模板（prompt templates）：EVOLVE、SELECT、HISTORY 的具體提示內容、rubric 的 JSON schema、選擇策略等均未揭露。
- 渲染與評分流程的細節不明：如何渲染 Code Draft、如何計算 overall points 與 aspect-mean score、如何比較渲染結果與 Target Screenshot，這些都會影響結果。
- 超參數設定未詳細說明：例如每個實例進行多少 Refinement Rounds、每次 EVOLVE 產生多少 Candidate Rubrics、SELECT 的排序依據等。
- 部分實驗使用 GPT-5.4 等尚未廣泛開放或名稱可能變動的模型，若其他研究者無法取得相同模型，則難以完全復現轉移學習的結果。

綜合而言，RubSE 的可重現性屬於「中等」。若作者能在專案頁面補上原始碼、提示模板與評估腳本，將大幅提升社群復現與延伸研究的可能性。

#### 未來研究方向

基於 RubSE 的貢獻與限制，未來研究可以朝以下方向發展：

1. **多準則協調規劃（Multi-Rubric Planning）**：目前每回合只選擇單一 rubric，未來可研究如何選擇一組彼此相容、可同時修復的 rubrics，並預測它們之間的交互影響，以在降低耦合的同時提升修復效率。

2. **顯式耦合建模（Explicit Coupling Modeling）**：除了用範圍限制來間緩解 Visual Repair Coupling，也可嘗試建立視覺相依圖或因果模型，預測某個程式碼修改會影響哪些其他 Visual Aspect，從而選擇副作用最小的修復路徑。

3. **學習式 Rubric Generator（Learned Rubric Generator）**：目前 rubric 由通用 VLM 產生，未來可針對 UI 視覺比較任務微調專門的 rubric generator，甚至使用 Reinforcement Learning（強化學習）與 Rubric-Based Rewards 來優化其產生策略。

4. **訓練時與測試時的整合（Training-Time Integration）**：將 rubric 作為輔助監督信號或獎勵塑形（reward shaping）融入 UI-to-Code 模型的訓練過程，從根本上提升基礎模型的生成品質，而不僅依賴測試時修復。

5. **擴展到其他領域（Cross-Domain Extension）**：將 RubSE 應用於 mobile app UI、desktop 應用程式、資料視覺化、簡報排版或文件版面生成等結構–細節生成任務，驗證 Visual Repair Coupling 是否普遍存在以及 rubric 引導是否同樣有效。

6. **人機協作式修復（Human-in-the-Loop Repair）**：讓設計師能夠檢視、編輯或新增 rubrics，使 RubSE 成為互動式設計轉碼工具，結合人類語意理解與模型自動修復能力。

7. **自動化 Rubric 驗證（Automated Rubric Validation）**：在每次修訂後自動檢查該 rubric 是否確實被修復、是否引入新的 Visual Regression，並據此動態調整 HISTORY 與下一回合目標。

8. **自適應停止與回合分配（Adaptive Stopping）**：根據軌跡穩定性自動決定何時停止迭代，或將更多回合分配給難以修復的視覺面向，提升計算效率。

9. **Rubric 引導的知識蒸餾（Rubric-Guided Distillation）**：利用強大 rubric generator 產生的高品質修復目標，訓練更小、更便宜的 code improver，實現高效能且低成本的部署。

10. **單調改進的理論保證（Theoretical Guarantees for Monotonic Improvement）**：探討在何種條件下，rubric 引導的自我演化能達到 Monotonic Improvement（單調改進），並給出收斂性分析，為方法設計提供更堅實的理論基礎。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**

A：這篇論文主要探討大型視覺語言模型在 UI 轉程式碼生成任務中，測試時自我演化不穩定的問題。作者發現一個核心障礙稱為「視覺修復耦合」，也就是局部的程式碼編輯會透過版面配置、樣式與元件相依性產生非局部的渲染影響，導致修正一處視覺不匹配時，反而破壞原本已經正確的區域。這種現象使得天真自我演化難以產生單調改進，後續回合甚至可能降低整體視覺保真度。

**Q2：為什麼現有的訓練時改進方法無法充分解決這個問題？**

A：現有方法主要透過擴充指令微調資料或採用分階段訓練流程來提升效能，但這些都是訓練時的干預手段，無法在測試時針對具體的渲染錯誤進行動態調整。UI 轉程式碼生成具備天然的測試時回饋來源，因為生成的程式碼草稿可以被渲染並與目標截圖進行視覺比較，但現有研究較少探索這個方向。更重要的是，即使採用生成–評論–修訂迴圈，自由形式的視覺回饋也無法有效控制修復範圍，容易引發過度廣泛的修改與視覺迴歸。

**Q3：視覺修復耦合為什麼是 UI 轉程式碼生成中的根本性挑戰？**

A：視覺修復耦合之所以根本，是因為 UI 程式碼中的版面配置、樣式與元件階層彼此緊密相連，修改一條 CSS 規則可能影響整個頁面的排版，調整父容器也會連帶改變子元件的位置與間距。這種耦合不僅存在於網頁 UI 開發，也反映了結構–細節生成任務中的普遍難題：對實作細節的局部編輯會透過整體結構傳播，造成全局性的視覺變化。因此，單純告訴模型哪裡錯了並不足夠，還必須同時控制「應該改變什麼」與「應該保留什麼」。

**Q4：RubSE 框架的核心方法是什麼？**

A：RubSE 是一個評分準則引導的自我演化框架，它將視覺回饋轉換為結構化的視覺修復情境。框架透過三個原子操作運作：EVOLVE 會根據目前渲染結果生成具類型候選評分準則，SELECT 從中選擇一個優先評分準則作為下一回合的修復目標，HISTORY 則將已選取的評分準則保存為修復歷史。這三個操作分別承擔發現錯誤、選擇聚焦目標與保存修復情境的角色，避免天真自我演化中這些功能相互混淆的問題。

**Q5：評分準則與自由形式評論相比有什麼優勢？**

A：評分準則是一種結構化的視覺修復項目，每個準則會描述特定的視覺錯誤、歸類到預先定義的視覺面向，並指定修正方向。相較於自由形式評論，評分準則提供了一種軟控制機制，讓修復目標變得明確，但同時保留程式碼生成模型決定如何實作編輯的彈性。這種表示方式能夠引導模型進行範圍明確的視覺修復，降低廣泛且糾纏的編輯所帶來的視覺迴歸風險。

**Q6：EVOLVE、SELECT 與 HISTORY 的設計選擇各自解決了什麼問題？**

A：EVOLVE 解決了回饋發現的問題，它會針對目前渲染結果生成多個候選評分準則，確保修復方向是基於具體的視覺錯誤而非籠統描述。SELECT 解決了聚焦問題，透過每次只選擇一個優先修復目標，避免模型同時處理過多問題而引發新的視覺迴歸。HISTORY 則解決了記憶與穩定性問題，它將先前的修復決策帶入後續回合，提醒模型避免重複失敗或已經處理過的問題，從而穩定整個細化軌跡。

**Q7：實驗在哪些基準測試與模型上進行？**

A：論文在三個 UI 轉程式碼基準測試上進行評估，並涵蓋六個不同的視覺語言模型。雖然摘要中未詳細列出所有基準名稱，但從相關工作可以推知包括 Design2Code 等真實網頁 UI 資料集。這樣的實驗設計能夠驗證 RubSE 在不同模型能力與不同資料分佈下的泛化性與穩定性。

**Q8：RubSE 相較於天真自我演化的主要實驗結果是什麼？**

A：RubSE 在 15 個最終回合設定中優於天真自我演化，平均整體分數提升 1.20 分，視覺面向平均分數提升 0.11 分。在最佳回合設定中，RubSE 在 14 個設定中表現更佳，平均整體分數提升 1.13 分。這些結果顯示 RubSE 不僅能讓最終輸出更穩定，也能提升整個細化軌跡的效能上限。

**Q9：進一步分析揭示了哪些關鍵發現？**

A：進一步分析發現 RubSE 能夠減緩軌跡崩潰現象，特別是當模型遭遇嚴重視覺迴歸時，評分準則引導的修復能加速恢復。另一個重要發現是評分準則具有可轉移性：由較強模型生成的評分準則能夠有效改善較弱模型的自我演化表現，例如 GPT-5.4 生成的評分準則能持續提升 Qwen 的細化效果。這表示高品質的評分準則提供了感知上可行、行動導向且範圍明確的修復目標，即使程式碼改進模型較弱也能受益。

**Q10：RubSE 在實際產品開發中有哪些應用場景？**

A：RubSE 可以應用於任何需要將設計稿自動轉換為可執行程式碼的工具，例如前端開發輔助系統、低程式碼平台或設計師與工程師協作的自動化流程。由於它能夠在測試時持續細化生成的 UI 程式碼，因此特別適合需要高視覺保真度的企業級應用。此外，評分準則的結構化特性也便於整合到現有的程式設計代理中，作為視覺回饋模組的一部分。

**Q11：在產品化過程中需要考慮哪些因素？**

A：產品化時需要考慮評分準則生成的成本與延遲，因為每個細化回合都需要額外的模型呼叫來執行 EVOLVE 與 SELECT。同時也需要設計適當的視覺面向分類與優先順序策略，以符合不同產品對版面配置、顏色、字體排印等面向的品質要求。此外，修復歷史的管理與儲存也會影響系統的可擴展性，特別是在長軌跡或多使用者場景中。

**Q12：這項研究對 UI 轉程式碼領域可能帶來什麼影響？**

A：這項研究將焦點從訓練時改進擴展到測試時自我演化，並提出結構化視覺回饋作為穩定細化過程的關鍵機制。它也可能影響更廣泛的結構–細節生成任務，因為視覺修復耦合的問題同樣存在於文件生成、簡報製作或其他需要同時維護全局結構與局部細節的應用。未來，評分準則引導的方法或許能與通用程式設計代理結合，提升自動化程式碼生成系統的可靠性與實用性。

**Q13：這篇論文有承認哪些限制？**

A：雖然論文摘要與引言未明確列出所有限制，但從方法設計可以推知，RubSE 依賴評分準則生成器的品質，若生成器無法準確識別視覺錯誤，後續的 SELECT 與 HISTORY 也會受到影響。此外，每次只選擇一個優先修復目標雖然提升了穩定性，但也可能降低處理多個獨立錯誤的效率。最後，實驗主要聚焦於網頁 UI 程式碼，對於其他平台或更複雜的互動式應用可能需要額外調整。

**Q14：RubSE 可能在什麼情況下失敗？**

A：當視覺錯誤之間高度耦合且無法被拆解為獨立的評分準則時，RubSE 可能難以找到有效的單一修復目標。如果目前渲染結果與目標截圖在多個視覺面向同時存在嚴重差異，優先順序的選擇也可能導致次佳的修復順序。此外，當程式碼改進模型過弱而無法理解或執行評分準則所描述的修正方向時，即使有高品質的評分準則，細化效果仍然有限。

**Q15：未來有哪些值得探索的研究方向？**

A：未來可以探索更智慧的評分準則選擇策略，例如同時處理多個不相關的修復目標以加速收斂，同時保持穩定性。另一個方向是將 RubSE 擴展到動態或互動式 UI，讓評分準則不僅涵蓋靜態視覺面向，也包含互動行為與狀態轉換。此外，研究如何將評分準則進一步整合到強化學習或獎勵模型中，以實現更自動化且可擴展的測試時改進，也是一個有潛力的方向。

## 實務應用指南

### 適用場景

**網頁前端自動化開發**：將 Figma、Sketch 或截圖直接轉為可執行的 HTML/CSS/React 程式碼，並透過多次細化回合自動修正版面配置、顏色、字體排印等視覺不匹配問題，減少人工反覆調整。

**設計系統遷移與一致性檢查**：在將舊版介面遷移至新設計系統時，利用評分準則鎖定單一視覺面向（如間距、色碼、元件階層）進行範圍明確的視覺修復，避免一次改動牽動全局版面配置。

**低程式碼／無程式碼平台**：為視覺編輯器加入「生成後自動自校正」能力，讓平台不僅產出初稿，還能依據結構化視覺回饋持續改進，提升最終輸出與使用者預期的吻合度。

**行動應用 UI 原型開發**：從 App 設計稿生成跨平台框架（如 Flutter、React Native）程式碼，並透過 RubSE 的修復歷史避免相同視覺錯誤在多次細化中反覆出現。

**設計師與工程師協作工具**：作為設計交付與程式碼實作之間的橋樑，自動標註視覺差異並產生優先修復目標，讓審查流程從自由形式評論轉為結構化、可追蹤的修復任務。

### 實作前置條件

**資料準備**：需要成對的「目標截圖＋對應參考程式碼」資料集以建立評估基線；同時需預先定義視覺面向分類（如空間版面配置、顏色、字體排印、元件階層、視覺密度），作為評分準則的類型標籤。

**運算資源**：需可呼叫大型視覺語言模型（VLM）的 API 或自有部署環境；每個細化回合都要能渲染程式碼草稿並進行視覺比較，因此需要穩定的無頭瀏覽器（如 Puppeteer、Playwright）與截圖比對基礎設施。

**技能組合**：團隊需具備前端開發知識（理解 CSS 規則、父容器與子元件關係）、提示工程能力（設計 rubric 生成與選擇提示）、以及模型評估經驗（能追蹤軌跡層級效能上限與最終回合穩定性）。

### 實作步驟建議

1. **建立渲染與視覺比較管線**：先讓任意程式碼草稿能被渲染成截圖，並與目標截圖計算視覺相似度分數，這是後續所有自我演化的基礎。

2. **定義評分準則結構**：為每個視覺面向設計統一格式的評分準則模板，包含「錯誤描述、所屬視覺面向、修正方向、影響範圍」，讓視覺回饋成為結構化視覺修復情境。

3. **實作 EVOLVE–SELECT–HISTORY 迴圈**：
   - EVOLVE：讓模型針對目前渲染結果產生多條候選評分準則；
   - SELECT：依嚴重程度、可修復性、與歷史不重複等條件選出單一優先評分準則；
   - HISTORY：將已選取的評分準則寫入修復歷史，供下一回合參考。

4. **設計 rubric 生成與選擇策略**：可先用較強大的 VLM 擔任評分準則生成器，較輕量模型擔任程式碼改進模型；實驗顯示高品質評分準則能遷移到較弱的改進模型。

5. **建立軌跡監控與 early stopping**：持續記錄每回合分數變化，當出現連續下降或嚴重視覺迴歸時中斷細化，避免軌跡崩潰。

6. **整合至現有開發流程**：將 RubSE 包裝成 API 或插件，接入設計工具、程式碼倉儲或 CI/CD，讓生成–評論–修訂迴圈成為產品管線的一環。

### 潛在風險與注意事項

**視覺修復耦合導致的迴歸**：局部程式碼編輯可能透過版面配置、樣式或元件相依性影響其他區域。建議每次只選擇單一優先修復目標，並在渲染後比對全域截圖，確認沒有破壞原本已正確的區域。

**評分準則品質不穩定**：若 rubric 生成器產出模糊或過度廣泛的修改建議，程式碼改進模型容易做出廣泛且糾纏的編輯。可透過預定義視覺面向與範例 few-shot 提示來提升評分準則的具體性。

**計算成本遞增**：每個細化回合都需呼叫 VLM、渲染與評分，成本會隨回合數線性成長。建議設定最大回合數，並結合 early stopping 與最佳回合選擇機制。

**過度細化導致的軌跡崩潰**：天真自我演化常出現後期分數低於初稿的現象。應保留修復歷史、避免重複失敗，並在產品層級回報「最佳回合」結果而非僅「最終回合」。

**領域適應問題**：論文基準多為網頁 UI，若應用於行動應用或桌面軟體，需重新校準視覺面向與評分指標，並補充該領域的渲染環境。

### 與其他技術的整合建議

**與設計工具插件整合**：開發 Figma、Sketch 或 Adobe XD 插件，直接將畫布選區作為目標截圖送入 RubSE，並將產生的程式碼與評分準則回寫至設計註解。

**與設計系統和元件庫整合**：在 rubric 生成階段注入組織內部的設計 token、元件名稱與樣式規範，讓視覺修復不僅「看起來像」，更符合企業設計系統的實作標準。

**與 CI/CD 和視覺迴歸測試整合**：將 RubSE 作為視覺迴歸測試的修復層，當自動化測試發現 UI 差異時，先產生結構化視覺修復情境，再由開發者確認或自動套用。

**與人機協作審查流程整合**：讓 RubSE 輸出的候選評分準則成為審查清單，由設計師或資深工程師進行 SELECT 決策，兼顧自動化效率與人類對品牌細節的判斷。

### 給不同背景讀者的閱讀建議

**給初學者**：這篇論文討論的是「如何讓 AI 看圖寫網頁程式碼後，還能自己越改越好」。你可以先聚焦在第一章的視覺修復耦合概念與圖一，理解為什麼「直接叫 AI 一直改」會反而改壞；接著看 RubSE 的三個操作 EVOLVE、SELECT、HISTORY，把它想像成「先列缺點、再選一個最重要的來修、並記住已經修過什麼」。

**給 AI 工程師**：建議從方法論與實驗設定開始，深入理解評分準則的結構化設計與提示工程細節。特別注意 SELECT 策略如何降低廣泛且糾纏的編輯風險，以及 HISTORY 如何透過修復歷史穩定軌跡。實作時可優先驗證「強 rubric 生成器＋弱 code improver」的組合是否能降低部署成本。

**給研究人員**：本文的核心貢獻在於將視覺回饋重新概念化為結構化視覺修復情境，並提出視覺修復耦合作為 UI-to-code 自我演化的關鍵失效模式。可進一步探索不同 SELECT 演算法、rubric 類型學、以及跨領域（行動應用、桌面軟體、3D 介面）的泛化性；軌跡崩潰與恢復機制也是值得延伸的理論問題。

**給產品經理**：這項技術適合需要「從設計稿自動產出高品質前端程式碼」的產品場景，能顯著縮短設計到開發的往返時間。評估導入時請同時關注最終回合穩定性與最佳回合效能上限，並預留渲染與 VLM 呼叫的運算預算；建議先從元件級或頁面級的試點開始，再擴展至完整設計系統。
