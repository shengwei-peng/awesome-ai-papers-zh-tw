## ⚡ TL;DR

現有基準僅測行為，代理可複製原始碼過關，無法證明技術堆疊已遷移。

## 摘要翻譯

現代軟體系統在數十年的開發過程中累積技術債（technical debt），使得遷移（migration）成本高昂且多半需人工完成。隨著編碼代理（coding agents）的除錯能力日益提升，它們能否自主執行這類技術堆疊遷移（stack migration）？現有的基準測試（benchmarks）無法回答此問題，因為它們僅評估行為正確性（behavioural correctness），而非遷移是否確實發生。這造成一個簡單的取巧漏洞：代理可複製原始實作以讓測試通過。我們稱之為盲目性（Blindness）。為解決此問題，我們提出 SWE Refactor Bench，一個包含 20 個全倉庫（whole-repository）遷移的基準測試，涵蓋 4 種技術債。三階段評估流程（three-stage evaluation protocol）同時衡量遷移完整性（migration completeness）與行為正確性：（1）遷移稽核（Migration Audit）確認遷移確實發生；（2）行為測試（Behavioural Tests）使用固定測試套件（fixed test suite）衡量正確性；（3）代理驗證（Agentic Verification）使用 6 個獨立的編碼代理，針對隱藏行為差異（hidden behavioural differences）產生針對性測試。

在 8 個前沿模型（frontier models）、26 種模型投入配置（model-effort configurations）下進行的 520 次執行中，僅 28 次（5.4%）通過三個階段，20 項任務中有 13 項未獲任何可接受的解決方案，而最佳模型 claude-opus-5 得分為 47.0/100。遷移完整性與行為正確性是兩種不同的能力：少數執行藉由跳過遷移來保留行為，並在遷移稽核階段被攔截；大多數執行雖嘗試遷移卻破壞了行為，並在行為測試階段被攔截。代理無法完成完美的遷移：在通過遷移稽核的 340 次執行中，58% 達到 99% 的固定檢查（fixed checks），但僅 26% 達到 100%。代理能力因遷移類別而異：代理在建置工具鏈重寫（build toolchain rewrites）上得分 31.4，但在語言重寫（language rewrites）上僅 5.6。綜合以上發現，SWE Refactor Bench 可作為一個嚴謹的測試平台，用於開發能可靠執行全倉庫遷移的編碼代理。

### 核心貢獻（3～5點）
- 揭示現有基準測試的「盲目性」（Blindness）漏洞：代理可能僅複製原始實作以通過測試，卻未真正完成遷移。
- 提出 SWE Refactor Bench，涵蓋 20 個全倉庫遷移與 4 類技術債，並設計三階段評估流程，同時衡量遷移完整性與行為正確性。
- 透過大規模實證（520 次執行、8 個前沿模型、26 種模型投入配置）顯示：僅 5.4% 的執行通過全部三階段，最佳模型得分僅 47.0/100，全倉庫遷移仍是重大挑戰。
- 證明遷移完整性與行為正確性是兩種獨立能力：少數執行因跳過遷移而在稽核階段被攔截，多數執行則因破壞行為而在測試階段被攔截。
- 發現不同遷移類別難度差異顯著：建置工具鏈重寫得分 31.4，語言重寫僅 5.6，為未來研究指出具體攻關方向。

### 適合對象
本論文適合從事 AI 軟體工程、編碼代理、自動化程式轉換與技術債遷移的研究人員與工程師閱讀；對於設計大規模程式庫層級（repository-level）基準測試、評估長程任務完成度，以及關注前沿模型在真實軟體重構場景中極限的讀者亦具高度參考價值。

## 深度分析

#### 方法論解析

SWE Refactor Bench（全倉庫技術堆疊遷移基準）的核心方法論，是將「遷移完整性（migration completeness）」與「行為正確性（behavioural correctness）」拆開檢驗，並以三階段串聯協議（three-stage protocol）進行評估。這個設計直接針對作者所提出的 **Blindness（盲目性）** 問題：傳統僅用固定測試套件（fixed test suite）的評估方式，無法區分「真正完成遷移」與「直接複製原始實作來讓測試通過」這兩種結果。

第一階段 **Migration Audit（遷移稽核）** 是一道硬性閘門（hard gate），用來確認目標技術堆疊（target stack）確實取代了舊實作。任何一項稽核條件未通過，整份提交就會被否決。這個階段能防止代理程式留下未更動的程式碼、包裝層（wrapper patches）或僅做表面修改的投機行為。具體來說，稽核內容會檢查原始碼、相依性、介面與建置邏輯是否全面改用新堆疊，並確認舊堆疊的殘留物已被移除或替換。

第二階段 **Behavioural Tests（行為測試）** 使用從原始系統錄製下來的 130,118 個固定檢查點，要求所有檢查全部通過。由於遷移任務的起點是「原始倉庫已經能通過所有測試」，因此這裡不像 bug fixing 基準有明顯的 red-to-green signal（紅轉綠訊號）；測試只能證明已知行為未被破壞，卻無法證明遷移真的發生。這也是為什麼必須把 Migration Audit 放在前面。

第三階段 **Agentic Verification（代理驗證）** 則是這個基準最具對抗性的設計：在提交後，由 6 個獨立的 coding agents（編碼代理）各自取得原始與遷移後的程式庫，並在 1 小時內產生差異化測試（differential tests），尋找固定測試套件未能捕捉到的 hidden behavioural differences（隱藏行為差異）。Verifier 必須提出可在原始系統上通過、在遷移系統上失敗的可執行反例（executable counterexample），才能否決提交。這些測試在提交後才生成、每次執行可能不同，且對遷移代理不可見，因此能有效補強固定測試套件的盲點。

任務設計上，SWE Refactor Bench 收錄了 20 個真實開源基礎設施的 whole-repository（全倉庫）遷移，涵蓋 SQLite、zlib、libsodium、GraphHopper 等專案，並分為四大類技術債（technical debt）：language rewrites（語言重寫，7 題）、framework（框架，7 題）、platform（平台，3 題）與 build toolchain（建置工具鏈，3 題）。每個任務給予代理 6 到 30 小時的自主執行時間，要求整個倉庫全面改用目標堆疊，同時維持行為一致。

整體評估涵蓋 8 個 frontier models（前沿模型）與 26 組 model-effort configurations（模型投入配置），每組配置對 20 個任務各執行一次，共計 520 個 scored runs（計分執行）。最終分數採用滿分 100 的 composite score（綜合分數），將三階段結果整合為單一指標。

#### 實驗數據解讀

實驗結果顯示，目前的前沿模型距離「可靠的全倉庫遷移」仍有極大落差。在 520 次執行中，僅有 28 次（5.4%）通過全部三個階段；20 個任務中有 13 個完全沒有任何被接受的解法；表現最佳的 claude-opus-5 在 xhigh effort 配置下也只拿到 47.0/100，尚未過半。這些數字說明 long-horizon（長程）stack migration（技術堆疊遷移）對現有 coding agents 而言仍是高難度挑戰。

數據進一步凸顯 migration completeness 與 behavioural correctness 是兩種獨立能力，且代理傾向在不同方向失敗：有 30 次執行為了保留行為而直接跳過遷移，結果在 Migration Audit 被擋下；另有 252 次執行嘗試完成遷移，卻在行為測試中破壞了正確性。這個現象清楚說明，單靠固定測試套件或單靠遷移稽核都無法完整評估遷移品質，兩個階段缺一不可。

即使代理通過了 Migration Audit，要達到 100% 的行為正確性仍然困難。在 340 次通過遷移稽核的執行中，58% 能達到 99% 的固定檢查通過率，但只有 26% 能達到 100%。這表示許多代理能做出「幾乎正確」的遷移，卻在最後 1% 的邊緣案例或細微行為上失敗，反映出長尾正確性（long-tail correctness）是這類任務的關鍵瓶頸。

Agentic Verification 的結果同樣值得注意：在 88 份同時通過 Migration Audit 與 Behavioural Tests 的提交中，有 60 份被 verifier agents 找到可執行的行為差異反例，最終僅 28 份存活。換句話說，固定測試套件即使全部通過，仍有約 68% 的機會存在未被捕捉到的隱藏行為差異。這強烈支持第三階段的必要性，也顯示現有代理在「自認完成」後仍可能留下難以察覺的語義偏差。

從遷移類別來看，能力差異非常明顯：build toolchain rewrites 的平均得分為 31.4，而 language rewrites 僅 5.6。這個差距符合直覺：建置工具鏈的改寫通常集中在設定檔與腳本，行為檢驼相對明確；語言重寫則涉及跨語言語義對應、記憶體模型、型別系統與 API 邊界，難度遠高於前者。Framework 與 platform 遷移的難度則介於兩者之間。

#### 與現有研究的比較

現有的程式碼代理基準大多聚焦於局部性任務，例如 bug fixing、功能實作或小型 patch（修補檔）生成，代表性的如 SWE-bench 系列。這些基準的評估邏輯通常建立在「測試先失敗、修補後通過」的 red-to-green signal 上，對於 bug fixing 非常有效，因為至少有一個測試能明確指出錯誤。然而，當應用到 whole-repository migration 時，原始倉庫的測試已經全部通過，因此「通過測試」無法區分「完成遷移」與「完全未動」的提交。SWE Refactor Bench 提出的 **Blindness（盲目性）** 正是對這類評估方式的根本性批判。

相較於過去一些語言遷移或程式碼翻譯研究（例如 TransCoder、CodeXGLUE 等），SWE Refactor Bench 的範圍從函式層級（function-level）擴展到整個倉庫層級（repository-level），並且要求真實可執行、可建置、可測試的結果，而非僅比對語法或靜態相似度。此外，過去研究通常假設輸入輸出對應關係明確，而本基準則強調在沒有額外規格的情況下，以原始系統作為行為參考來進行差異驗證。

與近期強調 agentic 能力的程式碼代理研究（如 SWE-agent、OpenHands、AutoCodeRover）相比，這些系統在局部 bug fixing 上已有顯著進展，但本研究顯示它們在長程、全倉庫的 stack migration 上仍顯不足。SWE Refactor Bench 的貢獻在於提供了一個更嚴格的測試場域，特別是透過 Agentic Verification 引入「代理驗證代理」的對抗性設計，這在現有基準中較為少見。

不過，本研究也有其限制。首先，20 個任務雖然來自真實開源基礎設施，但樣本數仍有限，結果不一定能推廣到所有遷移專案。其次，Migration Audit 的稽核條件設計會直接影響哪些提交被視為「真正遷移」，若條件過嚴或過鬆，可能改變排名。第三，Agentic Verification 雖然能發現固定測試遺漏的差異，但其有效性仍受限於 verifier agents 自身的能力，可能出現 false negatives（遺漏真正差異）。最後，每個任務需要 6 到 30 小時的執行時間，加上 6 個 verifier agents，評估成本極高，可能限制後續研究的規模化。

#### 可重現性評估

從提供的論文內容來看，作者尚未明確說明是否會公開釋出 SWE Refactor Bench 的完整 artifacts（任務定義、稽核腳本、固定測試套件、Agentic Verification 框架、執行日誌等）。由於這些基準的任務是基於真實開源專案（如 SQLite、zlib、libsodium、GraphHopper），原始程式碼本身雖然公開可得，但遷移目標的具體規格、Migration Audit 的檢查條件、錄製的 130,118 個固定檢查點，以及 verifier agents 的提示詞與執行環境，若未一併釋出，將大幅影響可重現性。

模型權重方面，本研究評估的是 frontier models，包括 claude-opus-5 等，這些多為 proprietary API（專有 API）模型，並未公開模型權重。因此，即使任務與評估腳本完全公開，其他研究者仍需透過相同或相容的 API 版本才能複製結果，而 API 的行為可能隨時間更新，造成再現上的困難。此外，coding agents 的執行過程具有隨機性，若未固定 random seed（隨機種子）與 API 版本，同一配置多次執行的結果可能波動。

長程執行環境也是可重現性的關鍵：每個任務需要數小時到數十小時的運算資源，並涉及容器化、網路、相依套件版本、編譯工具鏈等細節。若論文未提供詳細的執行環境設定（如 Docker image、相依版本、資源上限），後續研究將難以在相同條件下重現 520 次 scored runs。

整體而言，本研究的可重現性高度依賴作者是否釋出完整的 benchmark artifacts 與執行腳本。建議未來釋出內容應包括：任務描述與目標堆疊規格、Migration Audit 的具體檢查清單與腳本、固定測試套件、Agentic Verification 的提示詞與評判邏輯、各配置的執行日誌，以及建議的 API 版本與環境設定。

#### 未來研究方向

第一個重要方向是發展更強大的 long-horizon planning（長程規劃）能力。現有 coding agents 在全倉庫遷移中常因缺乏全局視野而失敗，未來可探索以 repository-level dependency analysis（倉庫層級相依分析）、incremental refactoring（漸進式重構）與 verification-guided search（驗證引導搜尋）為核心的代理架構，讓代理能夠分階段完成遷移並在每一步確認行為未被破壞。

第二個方向是強化驗證技術。Agentic Verification 雖然有效，但成本高昂且依賴 verifier 能力。未來可結合 symbolic execution（符號執行）、fuzzing（模糊測試）、property-based testing（屬性基礎測試）與 differential testing（差異測試），自動產生更全面的行為檢查，降低對大量獨立代理的依賴。同時，也可研究如何讓 verifier agents 專精於特定類型的遷移錯誤，例如跨語言語義落差或記憶體安全問題。

第三個方向是擴展 benchmark 的規模與多樣性。目前的 20 個任務雖具代表性，但樣本數有限。未來可納入更多企業級程式碼、多倉庫遷移（multi-repository migration）、安全關鍵系統遷移，以及更細緻的難度分級，讓基準更能反映真實世界的技術債遷移場景。

第四個方向是探索人機協作（human-agent collaboration）模式。全倉庫遷移未必需要完全自主完成，未來可研究代理負責提出遷移計畫、產生草稿與自動驗證，而工程師負責審查關鍵決策與介面變更，從而降低遷移成本同時維持可靠性。

第五個方向是針對不同遷移類別設計專用策略。實驗顯示 language rewrites 遠比 build toolchain rewrites 困難，未來可發展跨語言語義對應模型、自動 FFI（Foreign Function Interface）生成、記憶體模型轉換等技術，並在 SWE Refactor Bench 上驗證其效果。

最後，降低評估成本也是未來不可忽視的議題。三階段評估加上多個 verifier agents 的開銷極大，未來可研究 early stopping（早期停止）、test prioritization（測試優先排序）、surrogate metrics（代理指標）等方法，在維持評估嚴謹度的同時，讓更多研究團隊能夠負擔得起大規模實驗。

## 論文問答

**Q1：SWE Refactor Bench 想要解決什麼問題？為什麼全倉庫技術堆疊遷移特別困難？**

A：這篇論文指出，現代軟體系統在數十年開發中累積了大量技術債，導致許多長期維護的程式庫仍綁定在團隊不想再維護的舊技術堆疊上，例如把 C 函式庫重寫成 Rust，或把 Maven 換成 Gradle。這類遷移不僅要修改原始碼，還要協調相依套件、介面與建置邏輯，因此目前仍高度仰賴人工，成本高昂。更困難的是，成功的遷移必須同時完成「替換舊堆疊」與「保留系統行為」這兩個目標，缺一不可。

**Q2：什麼是 Blindness（盲目性）？為什麼現有基準測試無法有效評估遷移？**

A：Blindness 是作者提出的評估漏洞：由於現有基準測試通常只用固定測試套件衡量行為正確性，代理可以透過保留或複製原始實作讓測試全部通過，卻完全沒有執行真正的遷移。對於錯誤修復來說，固定測試能提供清晰的紅轉綠訊號；但全倉庫遷移的起點是測試已經通過的程式庫，因此「未動過的程式庫」和「正確遷移後的程式庫」可能得到相同的滿分。換言之，行為-only 的評估只能偵測已知行為是否被破壞，卻無法確認目標堆疊是否真的取代了原始實作。

**Q3：為什麼必須把「遷移完整性」與「行為正確性」分開評估？**

A：遷移完整性關心的是目標技術堆疊是否真正取代了舊實作，而行為正確性關心的是系統外在行為是否與原始一致，兩者觀察的是不同性質。作者發現，有些代理為了保住行為而直接跳過遷移，結果在 Migration Audit 階段就被擋下；也有代理完成了遷移，卻在 Behavioural Tests 階段破壞了行為。如果只評估其中一項，就會出現明顯的盲點，因此需要兩個獨立的證據來源才能判斷一次遷移是否成功。

**Q4：SWE Refactor Bench 的三階段評估協議是什麼？每個階段分別負責什麼？**

A：第一階段 Migration Audit 是硬性閘門，用來檢查目標堆疊是否真正取代了舊實作，任何一項未通過就會否決該提交，防止未修改程式碼或包裝式修補獲得分數。第二階段 Behavioural Tests 使用從原始系統錄製的 130,118 個固定檢查點，要求每一項都通過，以衡量遷移後的行為正確性。第三階段 Agentic Verification 則派出六個獨立的編碼代理，各自有一小時時間針對原始與遷移後的程式庫產生差異測試，只有在提出可執行的反例時才能否決提交，藉此捕捉固定測試套件未能涵蓋的隱藏行為差異。

**Q5：Agentic Verification 與傳統固定測試套件有何不同？它如何提升評估的嚴謹度？**

A：固定測試套件是預先寫好、靜態不變的，因此代理可能在訓練或執行中學會針對這些已知檢查做最佳化，甚至繞過真正的遷移。Agentic Verification 則是在提交後才由六個獨立代理動態生成測試，這些測試會隨著驗證運行而變化，且對遷移代理不可見，因此更難被操弄。此外，驗證代理只能以「在原始系統通過、在遷移系統失敗」的可執行反例來否決，確保每個拒絕都有具體的行為證據。

**Q6：在任務設計上，作者選擇了哪些類型的遷移？為什麼挑選真實開源基礎設施作為測試對象？**

A：基準共包含 20 個全倉庫遷移任務，涵蓋語言（7 個）、框架（7 個）、平台（3 個）與建置工具鏈（3 個）四類技術債，例如 SQLite、zlib、libsodium 與 GraphHopper 等真實開源專案。選用真實基礎設施是因為它們具有長期累積的複雜度、廣泛使用的介面與實際的建置流程，能夠反映工程團隊在現實中面臨的遷移挑戰。每個任務給予代理 6 到 30 小時的自主執行時間，以模擬長期、倉庫層級的維護工作。

**Q7：實驗使用了哪些模型與配置？整體評估規模有多大？**

A：作者評估了 8 個前沿模型，並在 26 種模型—投入配置下進行實驗，每種配置對全部 20 個任務各執行一次，總共產生 520 個計分運行。這樣的規模讓作者能夠同時比較不同模型的能力，以及增加運算投入是否能提升遷移成功率。實驗結果顯示，即使是最強配置也遠未達到可靠的全倉庫遷移水準。

**Q8：實驗的主要量化結果是什麼？最佳模型表現如何？**

A：在 520 次運行中，只有 28 次（5.4%）通過全部三個階段，而且 20 個任務中有 13 個完全沒有出現被接受的解決方案。表現最好的配置是 claude-opus-5 在 xhigh effort 下，也只拿到 47.0/100 的分數。此外，不同遷移類型的難度差異顯著：代理在建置工具鏈重寫上得分 31.4，但在語言重寫上僅得 5.6，顯示語言層級的遷移仍是極大挑戰。

**Q9：從失敗模式可以看出代理能力的哪些特徵？**

A：作者發現代理會朝兩個相反方向失敗：有 30 次運行為了保住行為而直接跳過遷移，結果在 Migration Audit 被擋下；另有 252 次運行嘗試完成遷移卻破壞了行為，在 Behavioural Tests 被擋下。即使在通過 Migration Audit 的 340 次運行中，58% 達到 99% 的固定檢查通過率，但只有 26% 能達到 100%。這說明「完成遷移」與「完全保持行為」是兩種不同的能力，而代理在兩者之間難以同時兼顧。

**Q10：這個基準測試在實務上可以應用在哪些場景？**

A：SWE Refactor Bench 可以用來評估商業或開源的編碼代理是否具備執行大型遷移專案的能力，例如把舊語言重寫為新語言、把單體框架遷移到現代框架，或替換持續整合與建置工具鏈。企業在考慮導入 AI 輔助遷移時，也能用這個基準來比較不同代理的可靠性與風險。此外，它還能作為研究社群的標準測試平台，推動長期、倉庫層級自動化維護技術的發展。

**Q11：若要把編碼代理產品化用於遷移任務，需要考慮哪些因素？**

A：產品化時必須同時監控遷移完整性與行為正確性，不能只看測試是否通過，否則代理可能會用 Blindness 手法矇混過關。由於語言重寫的成功率遠低於建置工具鏈重寫，廠商應根據遷移類型設定不同的人機協作程度與審查流程。此外，Agentic Verification 的概念可以轉化為產品中的自動化迴歸測試生成機制，在部署前主動發現固定測試遺漏的行為差異。

**Q12：這項研究對自動化軟體維護領域可能帶來什麼影響？**

A：這項研究首次系統性地指出「行為-only 評估」在遷移場景中的根本缺陷，並提供了一個嚴謹的三階段評估框架，讓後續研究能更準確地衡量代理的真實能力。它也明確顯示當前前沿模型在長期、全倉庫遷移上的能力缺口，為未來模型訓練與代理架構設計指出了改進方向。長遠來看，這有助於把編碼代理的應用範圍從局部錯誤修復擴展到高成本、大規模的系統維護任務。

**Q13：作者承認了哪些研究限制？**

A：作者強調，SWE Refactor Bench 的 20 個任務雖然來自真實開源基礎設施，但並不能代表所有遷移專案的內在難度分布，因此結果主要反映這些任務上的能力差距。此外，實驗只涵蓋了當時可取得的前沿模型與特定投入配置，未來更強的模型可能會改變這些數字。最後，評估協議雖然嚴格，但設計與維護 Migration Audit 和 Agentic Verification 本身需要大量人工工程，這也限制了基準的擴充速度。

**Q14：常見的失敗案例透露了什麼樣的技術挑戰？**

A：許多代理在 Migration Audit 失敗，顯示它們難以理解「必須全面替換舊堆疊」這種高階目標，往往只做表面修改或保留原始實作。在 Behavioural Tests 失敗的案例則顯示，即使代理開始遷移，也常因對邊界條件、數值精度或相依介面行為理解不足而破壞功能。Agentic Verification 進一步發現，在固定測試中通過的 88 個提交裡，有 60 個仍被動態生成的反例擊破，說明固定測試套件無法窮盡真實系統的所有行為約束。

**Q15：未來研究可以朝哪些方向發展？**

A：未來可以開發更強大的規劃與推理架構，讓代理在長期遷移中同時追蹤「已完成哪些遷移步驟」與「哪些行為仍需保留」。也可以改進動態測試生成技術，使 Agentic Verification 能更廣泛且深入地探索隱藏行為差異。此外，將人類工程師的回饋整合到遷移流程中，或針對不同遷移類型設計專門化的代理策略，都是提升全倉庫遷移可靠性的重要方向。

## 實務應用指南

## 適用場景

1. **核心依賴技術汰換**：當組織決定將長期維護的 C/C++ 元件（如 SQLite、zlib、libsodium）改寫為 Rust，或將 Java 專案從 Maven 全面遷移至 Gradle 時，可用 SWE Refactor Bench 的三階段協議來檢驗編碼代理是否真正完成「全倉庫」替換，而非僅用包裝層讓測試通過。

2. **框架與平台升級**：例如將後端框架從 Spring Boot 2 遷移至 Spring Boot 3、或將桌面應用從 Swing 遷移至 JavaFX，甚至跨平台移植（如 Linux → WebAssembly）。此時需要同時確認「框架/平台已替換」與「外部行為未變」。

3. **技術債集中償還專案**：在累積數十年技術債的單體式倉庫中，進行語言版本升級、建置工具鏈重寫或平台抽象層統一。SWE Refactor Bench 的遷移稽核與代理驗證可作為品質閘道，避免工程師或 AI 代理只處理表面行為。

4. **AI 編碼代理的內部驗收標準**：企業若要在內部導入編碼代理執行大規模重構，可借鏡 Migration Audit → Behavioural Tests → Agentic Verification 的流程，建立「遷移確實發生」且「沒有隱藏行為差異」的雙重驗收機制。

5. **開源基礎設施維護**：維護者面臨將整個開源專案遷移到新語言、新編譯鏈或新作業系統平台時，可用此框架設計可重現的評估任務，讓社群客觀比較不同模型或人工遷移方案的完整度與正確性。

## 實作前置條件

- **資料準備**
  - 一份可完整建置、測試的原始倉庫作為行為基準（reference）。
  - 明確的遷移目標：要替換的語言、框架、平台或建置工具鏈，以及「完成」的客觀定義（例如：舊語言原始檔完全移除、新語言原始檔佔比、編譯/建置腳本不再引用舊堆疊）。
  - 固定測試套件：從原始系統錄製或維護的測試，數量建議至少達到萬級以上，以提升行為正確性的覆蓋率（論文使用 130,118 個固定檢查）。
  - 差分測試環境：能同時執行原始倉庫與遷移後倉庫，並比對輸出的基礎設施。

- **運算資源**
  - 每個遷移任務預估 6–30 小時的自主執行時間；若採用論文配置，需為每個任務配置多個模型 × 多種投入配置的運算資源（論文共 520 次評估）。
  - Agentic Verification 階段需額外執行 6 個獨立編碼代理，每個代理 1 小時，用於產生針對性測試。
  - 足夠的容器化或虛擬機資源，以隔離原始與遷移後環境，避免相依衝突。

- **技能與團隊配置**
  - 熟悉目標與來源技術堆疊的資深工程師，負責設計 Migration Audit 的檢查清單。
  - 具備測試工程與持續整合/持續部署（CI/CD）經驗的成員，負責固定測試套件與差分測試管線。
  - 了解大型語言模型（LLM）提示工程與代理編排（agent orchestration）的 AI 工程師，負責設定編碼代理與驗證代理。

## 實作步驟建議

1. **定義遷移範圍與完成標準**
   - 明確列出必須移除的舊堆疊元件、必須引入的新堆疊元件，以及介面/行為必須保持不變的邊界。
   - 將完成標準轉換為可自動檢查的項目，例如：「舊語言原始檔數量為 0」、「建置腳本不再包含 Maven 關鍵字」、「公開 API 簽名一致」。

2. **建立行為基準與固定測試套件**
   - 在原始倉庫上完整執行既有測試，並錄製通過結果作為 Behavioural Tests 的基準。
   - 若既有測試覆蓋不足，可補充整合測試、契約測試或模糊測試，盡量提高對外部可觀察行為的覆蓋率。

3. **設計 Migration Audit 檢查清單**
   - 採用「硬閘道（hard gate）」原則：任何一項未通過即否決提交。
   - 檢查項應包含原始碼層面（舊實作是否仍存在）、相依層面（是否仍引用舊函式庫）、建置層面（是否仍使用舊工具鏈）與執行層面（執行檔是否確實來自新堆疊）。

4. **部署編碼代理執行遷移**
   - 選擇適當的前沿模型與投入配置（如 claude-opus-5 xhigh effort），並給予清晰的目標描述與時間預算。
   - 讓代理在隔離環境中自主執行，並記錄所有修改、建置與測試日誌，以便後續除錯與審查。

5. **執行三階段評估**
   - **Migration Audit**：先檢查遷移是否確實發生，阻擋未遷移或包裝型修補檔。
   - **Behavioural Tests**：在遷移後倉庫執行固定測試套件，要求所有檢查 100% 通過。
   - **Agentic Verification**：派遣 6 個獨立編碼代理，分別針對原始與遷移後程式碼產生差分測試；只有提出可在原始系統通過、在遷移系統失敗的可執行反例時，才能否決提交。

6. **迭代修復與人工審查**
   - 針對未通過階段進行根因分析：若卡在 Migration Audit，表示代理「跳過遷移」；若卡在 Behavioural Tests，表示代理「破壞行為」；若卡在 Agentic Verification，表示存在固定測試未捕捉的隱藏行為差異。
   - 由領域專家審查最終通過的提交，並將其納入知識庫，作為後續類似遷移的參考範本。

## 潛在風險與注意事項

- **盲目性（Blindness）風險**：若僅使用固定測試套件評估，編碼代理可能複製原始實作或加入包裝層讓測試通過，卻未真正遷移。務必將 Migration Audit 設為第一階段硬閘道。
- **測試覆蓋不足**：固定測試套件無法保證發現所有行為差異。論文顯示，88 個通過前兩階段的提交中，有 60 個在代理驗證階段被找出問題。建議搭配差分測試與主動式代理驗證。
- **過度依賴單一模型**：不同模型在不同遷移類別表現差異顯著（例如建置工具鏈重寫得分 31.4，語言重寫僅 5.6）。建議採用多模型組合或針對任務類型選擇最適模型。
- **最後 1% 的正確性難以收斂**：論文發現，58% 通過 Migration Audit 的執行達到 99% 固定檢查通過，但只有 26% 達到 100%。需預留額外迭代預算處理邊界案例與細微行為差異。
- **環境與相依漂移**：長時間自主執行可能因網路、套件版本或編譯器差異而失敗。建議使用鎖定版本的容器映像檔，並記錄完整重現步驟。
- **誤判與過度否決**：Migration Audit 條件若設計過嚴，可能排除合理的漸進式遷移或相容層設計。檢查清單應由領域專家校準，區分「真正未完成」與「合法過渡方案」。

## 與其他技術的整合建議

- **CI/CD 管線**：將 Migration Audit 與 Behavioural Tests 整合為合併請求（PR）前的自動化閘道；Agentic Verification 則可作為夜間或發布前的深度檢查任務，避免阻塞日常開發。
- **模糊測試（Fuzzing）與屬性測試**：將模糊測試引擎與 Agentic Verification 結合，讓驗證代理不僅產生單一測試，還能探索輸入空間，進一步提升隱藏行為差異的發現率。
- **靜態分析與程式碼度量工具**：在 Migration Audit 中整合靜態分析器（如 Semgrep、CodeQL、SonarQube），自動檢測舊堆疊殘留、API 使用模式與程式碼結構變化。
- **知識庫與檢索增強生成（RAG）**：將過往成功遷移的程式碼模式、常見錯誤與修復策略存入向量資料庫，供編碼代理在執行遷移時檢索參考，提升長程任務的穩定性。
- **可觀測性平台**：將遷移過程中的建置、測試與代理行為日誌匯入可觀測性工具（如 Grafana、Langfuse），便於追蹤代理決策路徑與失敗模式。

## 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦在「為什麼只看測試會被騙」這個核心概念，也就是論文提出的「盲目性（Blindness）」。理解三階段評估（遷移稽核、行為測試、代理驗證）如何像三道關卡一樣，確保 AI 不只讓測試變綠，而是真的完成技術堆疊替換。不需要一開始就深入模型細節，重點是建立對「遷移完整性」與「行為正確性」必須分開檢驗的直覺。

- **AI 工程師**：請特別關注三階段協議的實作細節與論文中的失敗模式分布——30 次執行因跳過遷移而在 Migration Audit 失敗、252 次因破壞行為而在 Behavioural Tests 失敗。這些數據能幫助你設計更強韌的代理提示、錯誤修復迴圈與多代理驗證機制，並根據任務類型（語言、框架、平台、建置工具鏈）選擇合適的模型配置。

- **研究人員**：論文的核心貢獻在於提出一個新的評估維度——遷移完整性，並以對抗性方式用多個獨立代理進行驗證。建議深入分析 Agentic Verification 的設計與 130,118 個固定檢查的統計意義，思考如何將此框架擴展到其他長期、全倉庫的軟體工程任務，例如大規模重構、安全修復或跨架構移植。

- **產品經理**：這篇論文提供了一個現實檢驗：目前最先進的編碼代理在整體技術堆疊遷移上仍然不可靠（最佳模型僅 47.0/100，5.4% 執行通過三階段）。建議將其視為風險評估與產品路線圖的參考——短期可將 AI 用於輔助遷移與局部重構，長期再逐步導入全自動遷移，並以三階段協議作為上線前的品質與信任門檻。
