Evolving Infra 的核心設計理念在於「解耦」(decoupling)——將計算資源分配與 KV 快取管理這兩個原本緊密耦合的元件徹底分離,這是理解整個系統架構的關鍵起點。

**第一層解耦:節點角色與 KV 儲存的分離**

傳統 PD 分離式服務系統中,每個節點的「角色」(預填充或解碼)與其本地 KV 快取是綁定的。當規劃器決定將某節點從預填充切換到解碼時,該節點上累積的 KV 快取要麼被丟棄,要麼變得無法被其他節點存取。Evolving Infra 採用共享記憶體池 (memory pool) 設計,將所有節點的主機記憶體 (host memory) 組成一個全域可存取的 KV 儲存層,並維護一個叢集範圍的 KV 目錄 (directory),記錄每個 KV 副本被多少活躍分支 (active branch) 引用。這種設計使得節點角色切換時,KV 不會「擱淺」(stranded) 或失效——任何節點都能讀取池中的任何 KV 副本。

**第二層解耦:計算需求估計與粗粒度訊號的分離**

現有線上規劃器依賴佇列深度 (queue depth) 或預測的 TTFT 等粗粒度訊號來調整 PD 分配比例。問題在於,代理型工作負載中常出現短暫的預填充突發 (例如同時生成多個子代理),這些訊號會誤觸發昂貴的階段切換。Evolving Infra 的規劃器改為學習「迭代時間模型」(iteration-time models)——即在線上學習每個請求在預填充和解碼階段所需的時間,並將 KV 復用納入預填充時間估算。這使得規劃器能基於工作負載本身的平均工作量 (而非叢集瞬時負載) 來評估新的 PD 分配比例,並且只在預測的吞吐量增益能持續整個規劃視窗時才執行切換。

**第三層解耦:快取驅逐與存取時近性的分離**

傳統系統使用 LRU (Least Recently Used) 驅逐策略,但代理型工作負載中,「最近存取」不等於「即將被復用」。例如,等待工具呼叫或子代理的分支可能在長時間閒置後仍會復用其前綴 KV;而壓縮 (compaction) 操作剛存取過的歷史紀錄,反而會在後續請求中被移除。Evolving Infra 引入代理感知的 KV 管理器,根據代理上下文管理動作(分支建立、子代理生成、壓縮)來更新 KV 目錄中的引用計數,引導驅逐決策保留活躍分支所需的 KV,丟棄已結束分支或重複副本。

**整體架構運作流程**

系統運作可分為三個層次:
1. **規劃層**:線上規劃器持續學習預填充/解碼時間模型,根據工作負載組成 (workload composition) 的變化,在每個規劃視窗評估並執行 PD 分配比例調整。
2. **路由層**:快取感知路由器 (cache-aware router) 將請求導向持有匹配前綴 KV 的節點,但同時考慮負載平衡,避免少數預填充節點過載。
3. **記憶體層**:分散式 KV 管理器協調節點間的 KV 傳輸,並根據代理上下文管理訊號更新目錄引用計數,指導驅逐策略。

3. 設定切換觸發條件：僅當新分配比例的預測吞吐量增益在多個視窗持續成立時才執行切換，避免短暫突發造成的頻繁切換
4. 整合 Arrow 等無重啟切換機制，並設計 KV 保留策略以維持切換後的快取復用率

**階段三：代理感知 KV 管理（4-6 週）**
1. 與代理框架整合，取得分支、子代理、壓縮等上下文管理事件
2. 改造快取驅逐策略：以「活躍分支引用計數」取代單純的 LRU，保留等待工具/子代理/使用者的分支 KV，驅逐已被壓縮取代的歷史
3. 改造快取感知路由器：避免將同一分支的請求集中到少數節點造成預填充過載，同時兼顧前綴復用
4. 設計 KV 傳輸的去重機制，避免記憶體池中產生重複副本

**階段四：評估與調優（2-4 週）**
1. 在程式設計、數學、電腦使用三類代理任務上進行基準測試
2. 對比 Dynamo 等現有框架，目標：平均端到端延遲降低 4 倍以上、P95 TTFT 降低 14 倍以上
3. 監測切換頻率與每次切換的成本，論文報告 Dynamo 平均每次切換需 681 秒，目標應遠低於此
4. 收集生產環境回饋，持續優化迭代時間模型的特徵工程

### 潛在風險與注意事項

**1. 切換成本控制不當**
若規劃器對短暫的工作負載波動過於敏感，會觸發頻繁的節點角色切換。Dynamo 平均每次切換需 681 秒，Arrow 在 34 次切換中損失 55.5% 的 KV 復用。緩解方式：要求吞吐量增益預測在多個規劃視窗持續成立才執行切換，並設置最小切換間隔。

**2. KV 目錄一致性問題**
叢集級 KV 目錄需記錄活躍分支引用計數，在分散式環境下維持強一致性成本高昂。若目錄更新延遲，可能誤刪仍有分支引用的 KV，或保留已被壓縮取代的無用 KV。緩解方式：採用最終一致性模型並設計補償機制，或使用分散式鎖服務。

**3. 預填充工作量被高估**
現有線上規劃器常以完整輸入長度估算預填充工作量，忽略 KV 復用。代理工作負載的 KV 復用率可達 99.8%（Claude Code 工具呼叫後），若忽略會嚴重高估預填充節點需求。緩解方式：預填充模型必須將 KV 復用率作為顯式特徵。

**4. 路由器設計的權衡陷阱**
純粹的快取感知路由會將同一分支請求集中到持有前綴的少數節點，造成預填充過載並拉高 P95 TTFT；過於注重負載平衡的路由則會把請求送到必須重算前綴的節點。緩解方式：設計混合策略，兼顧前綴復用與節點負載，並利用分散式 KV pool 減少重算需求。

**5. 壓縮操作的 KV 驅逐誤判**
壓縮（compaction）會移除近期存取的歷史，但 LRU 策略反而會保留這些即將被取代的 KV。論文顯示 Claude Code 在 12 秒的壓縮後僅 14% 的 prompt 匹配先前 KV，但 LRU 仍會優先保留。緩解方式：整合代理框架的壓縮事件，主動標記並驅逐對應 KV。

**6. 記憶體池的重複副本問題**
KV 在節點間傳輸時可能在 pool 中留下重複副本，浪費記憶體並降低有效快取容量。緩解方式：在 KV 目錄中實作引用計數與去重邏輯，傳輸完成後及時清理來源副本。

### 與其他技術的整合建議

**與 NVIDIA Dynamo 整合**
Evolving Infra 定位為 Dynamo 的替代或增強層。建議先在 Dynamo 之上實作代理感知 KV 管理（風險較低），再逐步引入節點角色動態切換與線上規劃器。最終目標是取代 Dynamo 的靜態 PD 分配與 LRU 驅逐策略。

**與 vLLM / SGLang 整合**
兩者皆提供 KV 快取管理與連續批次（continuous batching）功能。可將 Evolving Infra 的分散式 KV pool 設計移植到 vLLM 的 PagedAttention 或 SGLang 的 RadixAttention 之上，將節點本地快取抽離為共享結構。

**與 LangChain / AutoGen 等代理框架整合**
這些框架負責產生分支、子代理、壓縮等上下文管理事件。建議在框架層暴露事件回呼（callback），讓 Evolving Infra 的 KV 管理器能即時更新活躍分支引用計數。

**與監控與可觀測性系統整合**
將切換事件、KV 命中率、預填充/解碼工作量預測誤差等指標匯入 Prometheus / Grafana，建立切換成本與吞吐量增益的儀表板，用於持續調優規劃器參數。

**與多租戶資源排程器整合**
在 Kubernetes 環境中，可將 Evolving Infra 的節點角色視為可調度的標籤（label），由自定義排程器根據規劃器的決策動態更新節點角色，與現有 GPU 排程邏輯共存。
