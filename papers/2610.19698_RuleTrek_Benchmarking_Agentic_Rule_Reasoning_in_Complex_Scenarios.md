## ⚡ TL;DR

現有規則推理基準測試場景過於簡化，無法評估LLM代理在多檔案複雜情境中應用領域規則的能力。
本文提出RuleTrek多領域基準測試，透過規則圖組合子情境，評估規則識別、推導與端到端推理能力。
實驗顯示11款LLM規則識別與推導僅62.47%與60.43%，端到端推理27%至55%，凸顯挑戰。

## 摘要翻譯

大型語言模型（LLMs）越來越多地被用於處理專業領域中的複雜真實世界任務。然而，當情境資訊分散於多個檔案中時，識別並正確應用領域特定規則仍然具有挑戰性。現有的規則推理基準測試通常僅使用少數事實陳述來表示情境，簡化了相關規則的識別與應用。為了解決此差距，本文介紹 RuleTrek，一個用於複雜情境下代理式規則推理的多領域基準測試。其基於規則的建構流程提取結構化規則圖，生成並增量組合規則特定子情境，同時確保一致性與可解性。為了系統性地評估複雜情境下的代理式規則推理，RuleTrek 在互動式工作區中評估三項能力：規則識別（RI）、規則推導（RD）和端到端規則推理（E2E）。對 11 個前沿大型語言模型進行的實驗顯示，最高的 RI 和 RD 分數僅分別為 62.47% 和 60.43%，而 E2E 分數介於 26.97% 至 55.29% 之間。這些結果表明，當前的大型語言模型代理在複雜情境下的規則推理中面臨重大挑戰。我們將程式碼和資料集公開發布於 https://github.com/yuan247/RuleTrek。

### 核心貢獻（3～5點）
- 提出 RuleTrek，一個專為複雜情境下代理式規則推理設計的多領域基準測試，填補現有基準測試僅以少數事實陳述簡化情境的不足。
- 設計基於規則的建構流程（Rule-Grounded Construction Pipeline），能從政策文件自動提取結構化規則圖（Structured Rule Graphs），並增量組合規則特定子情境，同時確保一致性與可解性。
- 建立系統化的三維評估框架，於互動式工作區中衡量規則識別（Rule Identification, RI）、規則推導（Rule Deduction, RD）與端到端規則推理（End-to-End Rule Reasoning, E2E）三項核心能力。
- 對 11 個前沿大型語言模型（Frontier LLMs）進行實驗評估，揭示其在多檔案、異質檔案情境下進行規則推理的顯著局限性（E2E 最高僅 55.29%）。
- 公開程式碼與資料集，推動代理式規則推理（Agentic Rule Reasoning）領域的後續研究。

### 適合對象
從事大型語言模型（LLM Agents）推理能力、工具使用（Tool Use）與資訊檢索（Information Retrieval）研究的學者與工程師；關注法規遵循、稅務評估、社會保險等領域特定規則自動化應用的實務工作者；以及對多領域基準測試（Multi-Domain Benchmark）設計與思維鏈推理（Chain-of-Thought Reasoning）評估方法感興趣的研究人員。

## 深度分析

#### 方法論解析

RuleTrek 的核心方法論圍繞「基於規則的建構流程」（Rule-Grounded Construction Pipeline）展開，該流程旨在解決現有規則推理基準測試中「情境過於簡化」的關鍵缺陷。整體方法可分為三個遞進階段：

**階段一：結構化規則圖（Structured Rule Graphs）的萃取**

此階段從真實世界的規則庫（rule repositories）中萃取結構化規則圖 Γd，將領域特定規則（domain-specific rules）及其相互依賴關係編碼為圖結構。圖中的節點代表個別規則，邊則捕捉規則之間的引用、條件觸發或邏輯依賴關係。這種圖結構化表示的優勢在於：（1）保留了規則之間的語意關聯，使後續情境生成能夠依循真實的依賴鏈；（2）支援增量組合時的依賴驗證；（3）為評估代理的「規則識別」能力提供了可對齊的標準答案。

**階段二：規則特定子情境（Rule-Specific Sub-Scenarios）的生成**

針對規則圖中的每一條規則，系統性地生成對應的子情境，每個子情境都必須「需要應用其對應規則才能求解」。這種「一規則一子情境」的設計確保了：（1）每個子情境的可解性（solvability）可被獨立驗證；（2）規則與情境之間存在明確的對應關係，便於評估代理是否正確識別並應用了規則；（3）子情境可作為後續組合的原子單元。

**階段三：增量組合（Incremental Composition）與一致性／可解性驗證**

依據規則圖中的依賴關係，將子情境增量地組合為複雜的多檔案情境（multi-file scenarios）。在每一步組合中，系統都會驗證兩個關鍵性質：（1）一致性（consistency）——組合後的情境不會產生邏輯矛盾；（2）可解性（solvability）——組合後的情境仍可由給定規則庫中的規則求解。這種「逐步驗證」的設計避免了傳統批次生成中常見的「組合爆炸導致不可解」問題。

**評估框架的三層能力分解**

RuleTrek 將代理式規則推理（agentic rule reasoning）分解為三個可獨立評估的能力層次：

1. **規則識別（Rule Identification, RI）**：評估代理從原始規則文件中識別出適用規則及其依賴關係的能力。此任務提供完整的規則文件庫 Dr 與情境文件 Ds，要求代理輸出應用規則的集合。
2. **規則推導（Rule Deduction, RD）**：評估代理整合分散式情境資訊並正確應用「已提供必要規則」進行推理的能力。此任務提供規則圖 Γd 加上情境文件 Ds，繞過規則識別的瓶頸，專注於推理品質。
3. **端到端規則推理（End-to-End Rule Reasoning, E2E）**：聯合評估規則識別與規則推導，要求代理僅憑原始規則文件 Dr 與情境文件 Ds，自主完成從規則探索到答案推導的完整流程。

這種「RI → RD → E2E」的分解設計具有方法論上的優勢：透過比較 RI 與 RD 的得分差距，可診斷代理失敗究竟源自「找不到正確規則」還是「找到了但用錯了」；而 E2E 則反映真實部署場景下的整體表現。

**領域覆蓋**

RuleTrek 涵蓋六個領域：稅務（taxation）、PostgreSQL、網路安全（cybersecurity）、軟體政策（software policy）、採購（procurement）與遊戲規則（game rules）。這種多領域設計避免了單一領域的過擬合，並使評估結果更具泛化性。

#### 實驗數據解讀

論文報告了 11 個前沿大型語言模型（frontier LLMs）在 RuleTrek 三項任務上的表現，數據揭示了當前 LLM 代理在複雜規則推理上的嚴峻現實：

**規則識別（RI）瓶頸**

最高 RI 分數僅達 62.47%，意味著即便是表現最佳的模型，仍有近 38% 的機率無法從複雜的規則文件中正確識別出所有適用規則及其依賴關係。這反映出大型語言模型在「長文件中的規則定位」與「規則依賴鏈追蹤」上的根本性弱點。傳統的檢索增強生成（RAG）方法在面對規則間的條件觸發、例外條款與交叉引用時，往往難以建構完整的規則集合。

**規則推導（RD）的分散式資訊整合挑戰**

最高 RD 分數為 60.43%，顯示即便規則已明確提供，模型在整合分散於多個異質檔案（heterogeneous files）中的情境資訊時仍會犯錯。稅務領域的典型情境涉及納稅人個人資料（Profile.xlsx）、薪資紀錄（Salary.xlsx）、權利金紀錄（Royalties.xlsx）等多個檔案，模型必須正確交叉比對才能套用所得稅稅率、標準免稅額（standard allowance）與扣除規則（deduction rules）。60.43% 的得分意味著模型在多步驟、跨檔案的數值推理上仍有顯著錯誤率。

**端到端（E2E）表現的崩塌**

E2E 分數介於 26.97% 至 55.29% 之間，與 RI、RD 相比出現了明顯的「效能崩塌」。這個現象極具診斷價值：E2E 並非 RI 與 RD 的簡單線性組合，而是兩者錯誤的「複合放大」——若規則識別錯誤，後續推導必然失敗；若規則識別正確但推導出錯，答案仍不正確。E2E 最低分 26.97% 接近隨機猜測水準，顯示在完全自主的代理式設定下，當前 LLM 幾乎無法可靠地完成複雜規則推理任務。

**跨領域與跨模型的規律**

雖然論文中未完整列出每個領域的細部數據，但從整體趨勢可推測：（1）結構化程度較高的領域（如 PostgreSQL、軟體政策）可能表現較好，因為其規則語意較明確；（2）需要大量數值計算與跨檔案整合的領域（如稅務、採購）表現較差；（3）模型規模與 E2E 表現並非完全正相關，說明「代理式規則推理」不僅是模型容量問題，更是架構與訓練目標的問題。

**對實務部署的意涵**

這些數據對實際應用 LLM 代理於法規遵循、稅務計算、合規審查等場景提出了警示：在 RuleTrek 這種「受控但複雜」的環境下，最佳模型僅有約一半的正確率，意味著在真實世界中更為嘈雜、更為龐大的規則體系中，現有 LLM 代理尚不具備可靠部署的條件。

#### 與現有研究的比較

RuleTrek 在規則推理基準測試的光譜上佔據了一個獨特的位置，其相較於現有研究的改進與限制可從以下幾個面向分析：

**相較於早期規則推理基準的改進**

RuleTaker（Clark et al., 2020）採用標準化的事實陳述與規則，雖然便於控制變數，但完全脫離了真實文件的語境。PolicyQA（Ahmad et al., 2020）與 LegalBench（Guha et al., 2023）雖引入真實政策與法律文本，但情境仍以簡短段落呈現。RuleTrek 的核心改進在於：（1）情境以多檔案、異質格式（.docx、.xlsx）呈現，更貼近真實工作環境；（2）規則文件保持原始結構，迫使代理進行真正的「文件探索」而非「預處理後的規則匹配」；（3）透過增量組合流程，系統性地控制情境複雜度，使其可解且一致。

**相較於近期複雜規則基準的定位**

RuleArena（Zhou et al., 2025）雖評估真實世界複雜規則，但缺乏多檔案分散式情境；RuleWeaver（Yu et al., 2026b）從語料庫衍生規則，但情境結構較為單一。RuleTrek 的差異化在於「規則圖 + 子情境增量組合」的建構方法論，這使其能夠系統性地生成「可解但困難」的複雜情境，並支援三層能力的細粒度評估。

**相較於代理基準的互補性**

在互動式工作區（interactive workspaces）中評估代理的基準（如 Xu et al., 2025；Malay et al., 2026；Guo et al., 2026；Tang et al., 2026）側重於資訊檢索、工具使用與多步任務完成，但鮮少聚焦於「規則識別與應用」這一特定認知能力。RuleTrek 填補了這個空白，將「規則推理」作為一等公民進行評估。

**現有方法的侷限性**

儘管 RuleTrek 有諸多改進，仍存在以下限制：

1. **領域覆蓋的深度有限**：六個領域雖具多樣性，但每個領域的規則深度可能不足以代表該領域真實專家系統的複雜度。例如稅務領域可能僅涵蓋所得稅，未涉及企業稅、國際稅務等更複雜的子領域。
2. **規則圖萃取的自動化程度**：論文中未詳細說明規則圖萃取是人工、半自動或全自動。若高度依賴人工標註，則可擴展性受限；若全自動化，則規則圖的品質可能不穩定。
3. **評估指標的單一性**：論文主要報告準確率（accuracy），未深入分析錯誤類型（如規則遺漏、規則誤用、計算錯誤、跨檔案整合錯誤）的分佈。
4. **代理架構的單一性**：實驗中的代理架構是否統一？是否允許模型使用工具（如 Python 計算器、SQL 查詢）？這些細節直接影響 RD 與 E2E 的得分。
5. **缺乏人類基線**：未報告人類專家在 RuleTrek 上的表現，使得「62.47%」這個數字缺乏絕對參照——可能是人類可輕鬆達到 95% 的簡單任務，也可能是人類也僅能達到 70% 的困難任務。

#### 可重現性評估

RuleTrek 在可重現性方面展現了明確的承諾：

**程式碼與資料集的公開**

論文提供了 GitHub 儲存庫連結（https://github.com/yuan247/RuleTrek），明確聲明程式碼與資料集均為公開。這符合現代機器學習研究的最佳實踐，使其他研究者能夠：（1）重現論文中報告的 11 個模型的評估結果；（2）將 RuleTrek 應用於新模型的評估；（3）基於其建構流程開發新的基準測試。

**建構流程的模組化**

基於規則的建構流程分為三個明確階段（規則圖萃取、子情境生成、增量組合），這種模組化設計有利於：（1）單獨替換或改進某一階段；（2）將流程應用於新的領域；（3）對各階段進行消融實驗（ablation study）。

**可重現性的潛在挑戰**

儘管程式碼與資料集公開，仍有以下潛在的可重現性挑戰：

1. **規則文件的版本控制**：真實世界的規則文件（如稅法、PostgreSQL 文件）會隨時間更新。論文中使用的規則文件版本是否被精確記錄，將影響長期可重現性。
2. **LLM API 的隨機性**：實驗中使用的 11 個前沿模型中，部分為閉源 API（如 OpenAI、Anthropic），其輸出可能因模型更新而改變。論文中是否設定了固定的 temperature 與隨機性種子，將影響結果的可重現性。
3. **評測環境的標準化**：代理在互動式工作區中的行為可能受檔案系統、工具版本、提示工程細節的影響。論文中是否提供了標準化的評測腳本與環境配置，將決定其他研究者能否「開箱即用」地重現結果。
4. **建構流程中 LLM 的使用**：若子情境生成或一致性驗證使用了 LLM，則這些步驟的可重現性將依賴於所使用的具體模型與提示。

**整體評估**

相較於許多僅釋出資料集而未釋出建構流程的基準測試，RuleTrek 同時釋出了程式碼與資料集，並提供了清晰的建構流程描述，這在可重現性方面屬於較高水平。然而，對於上述細節的明確說明，仍需查閱 GitHub 儲存庫中的具體實作才能確認。

#### 未來研究方向

RuleTrek 的提出開啟了多個值得深入探索的研究方向：

**方向一：規則識別能力的專門增強**

既然 RI 是 E2E 瓶頸的主要來源之一，未來研究可專注於：（1）開發專門的規則文件索引與檢索方法，例如結合規則圖結構的圖神經網路檢索器；（2）設計「規則摘要」預處理步驟，使 LLM 能夠在長文件中快速定位相關規則；（3）探索「規則依賴鏈追蹤」的專門訓練目標，例如讓模型學習預測「給定一條規則，其依賴的前置規則為何」。

**方向二：分散式資訊整合的代理架構**

RD 任務中 60.43% 的得分上限顯示，當前 LLM 在跨檔案、跨格式的資訊整合上仍有根本性限制。未來可探索：（1）結構化中間表示（structured intermediate representation），例如讓代理先將異質檔案轉換為統一的表格或知識圖譜，再進行推理；（2）專門的「檔案路由」與「資訊彙總」模組；（3）結合符號推理（symbolic reasoning）與神經推理的混合架構，例如在數值計算步驟引入確定性的計算工具。

**方向三：建構流程的擴展與自動化**

RuleTrek 的建構流程目前涵蓋六個領域，未來可：（1）將流程應用於更多高價值領域，如醫療規章、金融合規、教育政策；（2）提高規則圖萃取的自動化程度，減少對人工標註的依賴；（3）探索「動態情境生成」，即根據代理的弱點自動生成更具挑戰性的情境，實現自適應評測。

**方向四：錯誤分析與可解釋性**

論文中缺乏對錯誤類型的細部分析。未來研究可：（1）建立錯誤分類法（如規則遺漏、規則誤用、計算錯誤、跨檔案整合錯誤、邏輯推理錯誤）；（2）分析不同領域、不同模型架構的錯誤模式差異；（3）開發可解釋的代理，使其能夠輸出「推理軌跡」供人類審查，這在法規遵循等高風險場景尤為重要。

**方向五：人類基線與認知負荷分析**

未來研究應納入人類專家的基線表現，以釐清 RuleTrek 的難度定位。同時，可透過認知科學方法（如眼動追蹤、思考過程記錄）分析人類專家解決此類任務的策略，並將其蒸餾到 LLM 代理中。

**方向六：多模態與時序規則**

現有 RuleTrek 主要處理結構化文件與表格，未來可擴展至：（1）包含圖表、圖像的多模態規則文件；（2）涉及時序邏輯的規則（如「納稅人若在過去三年內符合 X 條件，則適用 Y 規則」）；（3）跨語言的規則推理。

**方向七：代理的安全與魯棒性**

在法規遵循等場景中，代理的錯誤可能導致嚴重後果。未來研究應評估：（1）代理在面對對抗性情境（如刻意設計的混淆資訊）時的魯棒性；（2）代理的「拒答能力」——當情境資訊不足或規則不明確時，代理是否能正確識別並請求澄清，而非胡亂猜測。

這些方向不僅能推動 RuleTrek 本身的演進，也將對「LLM 代理在專業領域的可靠部署」這一更宏大的研究議題產生深遠影響。

## 論文問答

**Q1：RuleTrek 試圖解決的核心問題是什麼？**
A：RuleTrek 試圖解決的核心問題在於，當大型語言模型代理（LLM Agents）面對複雜的真實世界任務時，如何正確識別並應用領域特定規則（Domain-Specific Rules）。隨著任務情境日益複雜，相關資訊往往分散於多個異質檔案（Heterogeneous Files）之中，例如稅務評估（Tax Assessment）需要同時參考納稅人資訊（Taxpayer Information）、薪資紀錄（Salary Records）與權利金（Royalties）等多份文件。代理不僅需要從法規文件（Regulatory Documents）中找出適用的規則，還必須整合分散資訊才能正確推導出答案。這個問題反映了現實部署中 LLM 代理最關鍵、卻也最缺乏系統性評估的能力。

**Q2：為什麼現有的規則推理基準測試無法有效評估這項能力？**
A：現有的規則推理基準測試（如 RuleTaker、PolicyQA、LegalBench 等）通常僅以少量事實陳述（Factual Statements）來呈現情境，大幅簡化了規則識別與應用的難度。這類基準測試多採用正規化或簡化的規則表示，缺乏對原始規則文件（Native Rules）的真實呈現，也未涵蓋分散式情境（Distributed Scenario）的挑戰。此外，雖然部分代理基準測試（如在真實工作區中運作的代理）評估了資訊檢索（Information Retrieval）與工具使用（Tool Use）能力，但鮮少聚焦於領域特定規則的識別與應用，因此無法全面衡量代理在複雜多檔案情境（Multi-File Scenarios）下的規則推理（Rule Reasoning）表現。

**Q3：為什麼這個問題對 LLM 代理的實際部署至關重要？**
A：在專業領域中，許多決策（例如稅務居民身分判定、稅務評估、納稅義務計算）都高度依賴精確的規則應用（Rule Application），任何錯誤都可能導致法律或財務上的嚴重後果。當情境資訊分散於多個檔案時，代理必須具備跨檔案整合資訊的能力，才能正確識別如 183 天門檻（183-Day Threshold）或標準免稅額（Standard Allowance）等關鍵規則。RuleTrek 透過模擬這種真實工作環境，揭示了當前前沿大型語言模型（Frontier LLMs）在這類任務上的重大不足，對於推動可信賴 AI 代理的部署具有重要意義。

**Q4：RuleTrek 的「基於規則的建構流程」（Rule-Grounded Construction Pipeline）包含哪些階段？**
A：該流程包含三個關鍵階段：第一階段從真實世界的規則庫中萃取結構化規則圖（Structured Rule Graphs, Γd），以捕捉領域特定規則及其相互依賴關係；第二階段為圖中的每條規則生成對應的規則特定子情境（Rule-Specific Sub-Scenarios），每個子情境都必須能透過應用其對應規則來求解；第三階段則依據規則依賴關係，以增量組合（Incremental Composition）的方式將這些子情境逐步組合，並在每一步驗證一致性（Consistency）與可解性（Solvability）。這種設計確保了最終建構出的複雜情境既真實又可解，並能系統性地測試代理在不同複雜度下的規則推理能力。

**Q5：RuleTrek 設計的三項評估能力（Rule Identification、Rule Deduction、E2E）有何獨特之處？**
A：這三項評估能力分別針對規則推理的不同面向：規則識別（Rule Identification, RI）評估代理能否從原始規則文件中找出適用的規則及其依賴關係；規則推導（Rule Deduction, RD）則在已提供必要規則的前提下，評估代理整合分散情境資訊並正確應用規則的能力；端到端規則推理（End-to-End Rule Reasoning, E2E）則是兩者的結合，要求代理在沒有提示的情況下，自行完成從規則識別到應用的完整流程。這種分層設計的創新之處在於，它能精確診斷代理失敗的根源——究竟是在「找規則」還是「用規則」上出問題，從而為模型改進提供更具體的方向。

**Q6：為何選擇使用規則圖（Rule Graphs）與增量組合（Incremental Composition）來建構情境？**
A：選擇規則圖是因為它能自然地表示規則之間的依賴關係，這對於建構需要多條規則共同求解的複雜情境至關重要。透過增量組合的方式，每一步組合都會驗證一致性與可解性，這不僅保證了最終情境的品質，也使得基準測試能夠系統性地控制任務的複雜度。這種設計選擇使得 RuleTrek 能夠涵蓋從簡單到複雜的多層次任務，並支援跨領域（包括稅務、PostgreSQL、資安、軟體政策、採購、遊戲規則等六個領域）的評估，大幅提升了基準測試的實用價值與泛用性。

**Q7：RuleTrek 涵蓋哪些領域，並測試了哪些模型？**
A：RuleTrek 是一個多領域基準測試（Multi-Domain Benchmark），涵蓋了六個截然不同的專業領域：稅務（Taxation）、PostgreSQL、資安（Cybersecurity）、軟體政策（Software Policy）、採購（Procurement）以及遊戲規則（Game Rules）。在實驗部分，研究團隊針對 11 個前沿大型語言模型（Frontier LLMs）進行了系統性評估，這些模型來自 OpenAI、Anthropic、Google DeepMind、GLM-5 團隊等主要機構。這樣的設計不僅展示了基準測試的跨領域適用性，也確保了評估結果能反映當前最先進模型的整體表現。

**Q8：實驗結果揭示了哪些關鍵發現？**
A：實驗結果揭示了令人警醒的發現：在三項評估任務中，最高分表現都不盡理想——規則識別（RI）的最高分僅為 62.47%，規則推導（RD）為 60.43%，而端到端規則推理（E2E）的分數區間則落在 26.97% 至 55.29% 之間。這些數據顯示，即使是當前最先進的 LLM 代理，在面對分散於多檔案的複雜情境時，於規則識別與正確應用上都面臨重大挑戰。特別是 E2E 任務的低分表現，更凸顯了「找規則」與「用規則」兩項能力結合時所產生的複合困難。

**Q9：從 RI、RD 與 E2E 三項分數的比較中，可以得到哪些深入洞見？**
A：透過比較三項分數可以發現，RD 分數普遍高於 E2E，這說明當必要規則已被明確提供時，代理在規則應用上表現較好；但一旦要求代理自行從原始文件中找出規則，表現便顯著下降。此外，RI 分數（最高 62.47%）雖然略高於 RD，但仍未達到令人滿意的水準，顯示即使是「單純的規則識別」對 LLM 代理而言也是一大挑戰。這種分數差距模式揭示了一個重要洞見：當前 LLM 代理的瓶頸不僅在於推理能力，更在於從大量異質文件中精準定位適用規則的資訊檢索與理解能力。

**Q10：RuleTrek 適用於哪些實際應用情境？**
A：RuleTrek 的設計直接反映了多種高價值的實際應用情境，其中最典型的是稅務評估（Tax Assessment）——代理需要從多份文件中整合納稅人資訊、薪資紀錄與權利金等資料，並依據稅務居民身分規則（Tax Residency Rules）、所得稅稅率（Income Tax Rates）以及扣除規則（Deduction Rules，如社會保險 Social Insurance 與住房公積金 Housing Fund）來計算納稅義務。此外，該基準測試也適用於 PostgreSQL 查詢優化、資安政策遵循、軟體授權合規、採購流程審核以及遊戲規則裁判等場景，這些都是規則密集且需要精確推理的領域。

**Q11：RuleTrek 的研究成果對 AI 代理產品的開發有何具體啟示？**
A：RuleTrek 的研究成果對產品開發提出了幾項重要啟示：首先，產品設計不能假設 LLM 代理能自動從複雜文件中找出正確規則，必須考慮提供更智慧的規則索引、摘要或檢索輔助功能；其次，應採用模組化架構，將規則識別與規則應用分離，以便在失敗時能精確診斷問題所在；最後，產品應設計「人在迴圈」（human-in-the-loop）的驗證機制，特別是在稅務評估這類高風險應用中，因為實驗顯示即使是前沿模型在 E2E 任務上的最高分也僅約 55%，遠未達到自主部署的安全標準。

**Q12：RuleTrek 對整個 LLM 代理研究領域有何更廣泛的影響？**
A：RuleTrek 對領域的更廣泛影響在於，它首次系統性地將「規則推理」這一核心能力從簡化的學術設定推向真實的複雜工作環境，填補了規則推理基準測試與代理工作區基準測試之間的空白。透過揭示當前前沿模型在 RI、RD 與 E2E 上的顯著不足，該研究為學術界與工業界提供了明確的改進方向。此外，該基準測試採用的基於規則的建構流程（Rule-Grounded Construction Pipeline）也為未來建構高品質、可控複雜度的基準測試樹立了方法論典範，有望推動整個領域朝著更實用、更嚴謹的方向發展。

**Q13：RuleTrek 存在哪些已知的限制？**
A：儘管 RuleTrek 在設計上有諸多創新，但仍存在若干已知限制：首先，雖然涵蓋了六個領域，但相較於現實世界中無窮無盡的專業規則系統，其覆蓋範圍仍屬有限；其次，基準測試的建構依賴於從真實規則庫中萃取結構化規則圖，這個過程可能無法完全捕捉所有規則的細微互動與例外情況；再者，評估主要聚焦於規則推理能力，但實際部署中還涉及許多其他重要因素（如延遲、成本、用戶體驗等），這些都未在基準測試中直接反映。

**Q14：實驗結果揭示了哪些典型的失敗案例模式？**
A：從實驗結果可以推論出幾種典型的失敗模式：第一種是「規則遺漏」——代理可能只識別出部分必要規則，忽略了規則依賴圖中的關鍵節點；第二種是「規則誤用」——即使找到了正確規則，代理在將其應用於分散情境資訊時仍可能產生錯誤，例如錯誤計算標準免稅額或誤判 183 天門檻；第三種是「跨檔案整合失敗」——代理可能無法有效整合來自納稅人資訊、薪資紀錄與權利金等不同檔案的資訊，導致推導出錯誤的納稅義務。這些失敗模式凸顯了當前 LLM 代理在處理真實複雜任務時的多重脆弱性。

**Q15：基於 RuleTrek 的發現，未來有哪些值得探索的研究方向？**
A：基於 RuleTrek 的發現，未來研究可朝多個方向探索：首先，可發展專門增強規則識別能力的技術，例如更好的文件結構理解、規則索引與檢索機制；其次，可探索如何將大型規則庫有效壓縮或摘要，使 LLM 代理能在有限上下文窗口中處理更廣泛的規則；再者，可研究多代理協作架構，讓專門負責規則識別的代理與負責規則應用的代理分工合作；最後，也可將思維鏈（Chain-of-Thought, CoT）推理等技術與 RuleTrek 的評測框架結合，探索如何系統性地提升代理在端到端規則推理任務上的表現，朝向真正可信賴的 AI 代理邁進。

## 實務應用指南

### 適用場景

1. **稅務諮詢與自動申報助理**：參考 RuleTrek 的稅務領域設定，企業可建置能讀取散落在多份文件（個人資料、薪資紀錄、權利金收入、社會保險與住房公積金紀錄）的代理，自動比對稅務居民身分規則、所得稅稅率與扣除規則，產出申報建議或試算結果，協助會計師事務所與企業財會部門處理高重複性的稅務評估工作。

2. **企業 IT 政策與軟體授權合規檢查**：利用 RuleTrek 的軟體政策（software policy）與採購（procurement）領域，建置能在內部檔案伺服器、SharePoint、Confluence 中穿梭的代理，依據授權條款、採購規範與使用情境，自動判斷某項軟體部署是否符合公司政策，輸出合規報告與違規項目。

3. **資安事件回應與政策對應**：參考 RuleTrek 的網路安全（cybersecurity）領域，SOC（Security Operation Center）團隊可部署代理讀取警報日誌、資產清單與資安政策文件，自動識別應套用的應變程序（例如隔離、通知、復原步驟），並產出符合規範的處置建議。

4. **遊戲與平台客服自動化**：參考 RuleTrek 的遊戲規則（game rules）領域，線上遊戲或 SaaS 平台的客服系統可使用代理讀取散落在多份規則文件中的條款，根據玩家實際操作紀錄判斷申訴是否成立、退款比例與懲處依據，降低人工客服負擔。

5. **PostgreSQL 與資料庫管理政策自動化**：參考 RuleTrek 的 PostgreSQL 領域，DBA 團隊可建置代理依據資料庫管理規範（權限設定、備份政策、稽核規則）與實際環境組態，自動檢查是否符合內部規範並產出修正建議。

### 實作前置條件

**資料準備**
- 領域規則文件集：需具備結構化或半結構化的規則文件（如稅法條文、公司政策 PDF、Markdown、Word、Excel 等異質檔案），並事先整理為可被代理讀取的格式。
- 情境資料檔案：納稅人/員工/玩家等實際紀錄檔案，需模擬真實世界的分散式儲存情境（多檔案、跨格式）。
- 標註資料：用於驗證規則識別（RI）與規則推導（RD）的正確答案，建議至少準備數百題以獲得統計顯著的評估結果。

**運算資源**
- 至少一組前沿大型語言模型的 API 存取權限（OpenAI、Anthropic、Google DeepMind、GLM-5 等），並準備預算因應多回合互動式評估的 token 消耗。
- 互動式工作區環境：可模擬檔案系統、命令列工具、Python 直譯器的容器化執行環境（建議使用 Docker 或 Kubernetes 部署）。
- 評估基礎設施：評判器（Judge）模組與自動化評分管線，需具備可重現性與日誌保存機制。

**技能需求**
- 具備 LLM 代理開發經驗，熟悉工具呼叫（tool use）、資訊檢索（information retrieval）與思維鏈（CoT）推理的提示工程。
- 熟悉規則圖（rule graph）抽取與結構化技術，能將非結構化規則文件轉為可推理的圖結構。
- 具備領域專家知識或與領域專家協作的能力，以驗證規則抽取與情境生成的正確性。
- 基本的軟體工程能力（Python、API 整合、CI/CD）以建置可重現的評估管線。

### 實作步驟建議

**步驟一：建構規則圖（Rule Graph Extraction）**
參考 RuleTrek 的第一階段流程，從真實世界的規則儲存庫中抽取結構化規則圖 Γd。實作上可使用 LLM 搭配結構化輸出（JSON Schema）將規則文件解析為節點（單條規則）與邊（規則間相依關係），並由領域專家抽樣驗證抽取品質。

**步驟二：生成規則特定子情境（Sub-Scenario Generation）**
針對規則圖中的每一條規則，使用 LLM 生成對應的子情境，確保每個子情境都必須套用其對應規則才能正確回答。建議設定自動驗證機制，確認子情境的答案確實依賴該規則。

**步驟三：增量組合情境（Incremental Composition）**
依據規則圖的相依關係，將子情境增量組合成更複雜的多檔案情境。每一步組合都需進行一致性（consistency）與可解性（solvability）檢查，避免產生矛盾或無解的情境。建議建立自動化檢查腳本，並由領域專家抽樣審核。

**步驟四：部署互動式工作區（Interactive Workspace）**
建置代理可操作的環境，包含檔案系統瀏覽、文件讀取、Python 執行、命令列工具等能力。環境需支援多回合互動，並完整記錄代理的操作軌跡以便除錯與分析。

**步驟五：實作三項評估任務**
- **規則識別（RI）**：提供原始規則文件與問題，要求代理輸出應套用的規則清單與其相依規則。
- **規則推導（RD）**：提供已標記的必要規則與分散式情境檔案，要求代理產出正確答案。
- **端到端規則推理（E2E）**：僅提供問題，要求代理自主探索規則文件與情境檔案，產出最終答案。

**步驟六：執行評估與分析**
在 11 個前沿 LLM 上執行評估，記錄 RI、RD、E2E 三項分數。特別注意 E2E 分數通常遠低於 RI 與 RD（RuleTrek 實驗中 E2E 僅 26.97%–55.29%），這代表「識別」與「推導」能力的乘積效應是主要瓶頸。

**步驟七：迭代優化與部署**
根據評估結果，針對弱項進行優化（例如改善檢索策略、加入思維鏈提示、引入自我驗證機制），並將通過驗證的代理部署到實際業務流程中。

### 潛在風險與注意事項

**風險一：規則幻覺與錯誤套用**
LLM 代理可能捏造不存在的規則條款，或將規則套用至錯誤的條件。**緩解措施**：在 E2E 任務中加入引用追蹤機制，要求代理標註每個結論對應的規則來源；導入規則驗證器（rule validator）對產出答案進行二次檢查。

**風險二：多檔案資訊整合失敗**
RuleTrek 實驗顯示，E2E 分數（最高 55.29%）顯著低於 RI（最高 62.47%）與 RD（最高 60.43%），代表代理在「找到規則」與「套用規則」之間存在整合斷層。**緩解措施**：設計明確的中間狀態輸出（例如先列出找到的規則，再列出整合後的事實，最後產出結論），並使用結構化推理框架。

**風險三：領域知識不足導致規則抽取錯誤**
規則圖抽取階段若品質不佳，後續所有評估都將失真。**緩解措施**：建立領域專家審核流程、設定自動化一致性檢查、保留規則來源的可追溯性。

**風險四：評估成本過高**
互動式工作區涉及多回合 LLM 呼叫，token 消耗可能遠超預期。**緩解措施**：使用較小模型做初篩、限制最大互動回合數、對簡單子任務使用快取機制。

**風險五：情境組合的可解性無法保證**
增量組合多個子情境時，可能產生邏輯矛盾或無解情境。**緩解措施**：每步組合後執行自動化求解器驗證、由領域專家抽樣審查、保留組合日誌以便回溯。

**風險六：基準測試與真實業務的落差**
RuleTrek 雖強調複雜度，但仍屬受控環境，實際業務中的規則可能更模糊、文件品質更差。**緩解措施**：在部署前使用真實業務文件進行小規模試點，並持續監控代理表現。

### 與其他技術的整合建議

**與 RAG（Retrieval-Augmented Generation）整合**
RuleTrek 的 RI 任務本質上是規則檢索問題。建議將規則文件建立向量索引（使用 embedding 模型）與關鍵字索引（BM25）的混合檢索系統，並在代理的工作流程中加入「檢索 → 重排序 → 套用」三階段管線，可顯著提升規則識別準確率。

**與工具呼叫框架整合**
可將 RuleTrek 的互動式工作區概念整合至 LangChain、AutoGen、CrewAI 等代理框架中，定義標準化的工具介面（讀取文件、執行 Python、查詢資料庫），讓代理能跨框架複用。

**與領域知識圖譜整合**
將規則圖（Γd）擴展為更完整的領域知識圖譜，加入實體關係（例如納稅人與收入來源的關聯），可提升代理在多檔案情境中的資訊整合能力。

**與企業系統整合**
- **ERP/HR 系統**：將情境檔案連結至 SAP、Workday 等系統，自動擷取真實資料。
- **文件管理系統**：與 SharePoint、Confluence、Google Drive 整合，讓代理能直接存取企業內部規則文件。
- **合規管理平台**：將代理輸出整合至 GRC（Governance, Risk, Compliance）平台，自動產合規報告。

**與評估與監控工具整合**
整合 LangSmith、Weights & Biases 或自建評估儀表板，持續追蹤代理在 RI、RD、E2E 三項任務上的表現，並設定自動告警機制。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀圖 1 了解「簡單情境」與「複雜情境」的差異，並理解三項評估任務（RI、RD、E2E）的定義。接著重點閱讀「Rule-Grounded Construction Pipeline」段落，掌握規則圖、子情境、增量組合三個核心概念。實作上可先從小規模的單一領域（例如遊戲規則）開始，避開複雜的法律或稅務領域。

**給 AI 工程師**：重點關注互動式工作區的設計、代理的工具呼叫流程、評判器（Judge）的實作細節，以及 11 個前沿 LLM 的評估結果差異。建議直接閱讀 GitHub 程式碼（https://github.com/yuan247/RuleTrek{RuleTrek}），理解評估管線的工程實作，並思考如何將 RI/RD/E2E 的評估框架整合至現有的代理系統中。實驗結果顯示 E2E 分數遠低於 RI 與 RD，這是工程優化的重點方向。

**給研究者**：重點閱讀規則圖抽取、子情境生成、增量組合的方法論章節，並關注「為何 E2E 分數顯著低於 RI 與 RD」這個現象背後的學術問題——這可能涉及代理的「組合泛化」（compositional generalization）能力不足。可進一步探索的方向包括：更好的規則檢索策略、推理過程的可驗證性、領域遷移學習等。Table 1 對現有基準測試的比較也值得深入分析。

**給產品經理**：重點理解 RuleTrek 要解決的商業問題——「現有 LLM 代理在真實業務規則推理上的表現仍不足以可靠部署」。實驗數據（E2E 最高僅 55.29%）是評估產品成熟度的關鍵指標。建議將 RuleTrek 視為「採購 LLM 代理前的驗證工具」，在實際導入前先用類似框架評估供應商表現。閱讀時可跳過技術細節，聚焦於「適用場景」與「實作步驟」兩節，並與業務團隊討論哪些場景適合優先導入。
