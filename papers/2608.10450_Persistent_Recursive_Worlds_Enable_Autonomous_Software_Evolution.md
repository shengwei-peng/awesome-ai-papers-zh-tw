## ⚡ TL;DR

現有長期開發多靠延續代理本身，難以跨越代理生命週期維持專案一致性。
Genesis 以版本–路徑構成持續遞迴世界，有限代理透過驗證閘控的委派與接受推進專案歷史。
從零建構出通過測試的 Rust C 編譯器，在模型替換後持續開發，將 MESA 模組重構為 Rust 顯著加速。

## 摘要翻譯

複雜軟體系統的開發時間尺度往往超越任何單一程式設計代理（coding agent）的生命週期。大多數代理式軟體系統透過持續會話（persistent sessions）、記憶（memories）、管理代理（managers）或共享上下文（shared context）來維持延續性。我們提出 EvoX Genesis（以下簡稱 Genesis），改以讓軟體專案（software project）本身持續存在，同時使本地代理（local agents）維持有限生命週期。Genesis 將軟體建模為持續遞迴世界（persistent recursive world）：每個本地世界（local world）由已接受版本（accepted version）與儲存庫路徑（repository path）所定位，有限生命週期代理（finite-lived agents）提出本地變更（local changes），遞迴委派（recursive delegation）將工作跨路徑移轉，僅有已接受結果（accepted consequences）會推進持續版本歷史（persistent version history）。我們在建構（formation）、延續（continuation）與重新開發（redevelopment）三個階段評估此組織架構。

從一個無編譯器實作的儲存庫開始，Genesis 使用 DeepSeek V4 Flash 建構了一個以 Rust 為基礎的 C 編譯器（Rust-based C compiler），約有 25 萬行追蹤行數（tracked lines）；整個執行歷時超過 120 小時，封存了超過 1,000 個代理回合（agent episodes），且模型 token 費用（model-token charges）僅 44 美元。該編譯器通過完整的 c-testsuite，以及大部分 LLVM 與 Csmith 測試。在另一個以 GLM 5.2 產生的編譯器世界（compiler world）中，在多次代理替換（agent replacement）後，開發仍持續進行，並保持完整的測試表現（test performance）。Genesis 也將 13 個 MESA 模組（MESA modules，超過 10 萬行 Fortran）重新實作（reimplemented）為一個 Rust 工作空間（Rust workspace，近 9 萬行 Rust 程式碼）；在六個數值工作負載（numerical workloads）上，達到 1.55 至 6.87 倍的中位數加速比（median speedups）。這些結果顯示，長期軟體開發（long-horizon software development）可以圍繞持續專案（persistent project）、而非持續代理來組織。

### 核心貢獻（3～5點）
- 提出 Genesis 框架，以持續專案（persistent project）取代持續代理，讓有限生命週期代理（finite-lived agents）透過已接受版本（accepted version）與儲存庫路徑（repository path）協作，解決長期軟體開發的延續性問題。
- 從無實作內容的儲存庫（implementation-empty repository）綠地建構（greenfield formation）出約 25 萬行的 Rust C 編譯器，通過完整 c-testsuite 與大部分 LLVM、Csmith 測試，整體模型 token 費用僅 44 美元。
- 驗證代理替換（agent replacement）後開發仍可延續：在 GLM 5.2 產生的編譯器世界中，多次替換代理後仍保持完整測試表現。
- 將 13 個 MESA Fortran 模組重新實作為 Rust 工作空間（Rust workspace），在六個數值工作負載（numerical workloads）上達到 1.55–6.87 倍的中位數加速比（median speedups）。

### 適合對象
適合對軟體工程、AI 代理系統、自動化程式設計及長期自主系統有興趣的研究者與工程師，特別是關注多代理協作、專案持續性、儲存庫層級軟體開發（repository-level software development）與大規模科學程式碼庫（scientific codebase）演化的讀者。

## 深度分析

#### 方法論解析

##### 持續遞迴世界（persistent recursive world）的核心抽象

EvoX Genesis（以下簡稱 Genesis）將軟體專案（software project）視為一個持續遞迴世界（persistent recursive world），其核心抽象是一個最小版本–路徑模型（minimal version–path model）：

\[
w = (v, p)
\]

其中 \(v\) 代表已接受版本（accepted version），\(p\) 代表儲存庫路徑（repository path）。已接受版本決定了代理進入時所繼承的完整專案狀態與歷史；儲存庫路徑則決定代理的本地責任範圍與修改範圍。這個設計把「專案狀態」與「代理執行」解耦：專案狀態與歷史是持續存在的，而代理本身是有限的、可替換的。

與傳統持續會話（persistent sessions）、持續記憶（persistent memory）或共享上下文（shared context）不同，Genesis 並不延長任何單一代理的生命週期，而是讓軟體專案（software project）本身成為延續性的載體。每次代理進入時，都從一個被驗證過的已接受版本（accepted version）出發，從而降低「代理狀態漂移」對長期開發的影響。

##### 有限生命週期代理（finite-lived agents）與遞迴委派（recursive delegation）

Genesis 中的代理是有限生命週期代理（finite-lived agents）。每個代理 \(A_i\) 在本地世界（local world）\((v, p)\) 中接收一個回合目標 \(g_i\)，執行有界任務（bounded task）後提出候選變更 \(\Delta_i\)，然後終止。這種設計強制每個代理的貢獻都是有界貢獻（bounded contributions），避免單一代理長時間累積未經驗證的修改。

當目標過大時，Genesis 使用遞迴委派（recursive delegation）：管理代理（manager agent）將工作拆分到更細的儲存庫路徑（repository path），形成新的本地世界（local world），並由執行代理（executor agents）在路徑範圍上下文（path-scoped contexts）中完成。這種遞迴分解與軟體工程中的模組化原則一致，能將複雜任務逐步細化為可在單一回合內處理的子任務。

##### 驗證閘控接受（validation-gated acceptance）與持續版本歷史（persistent version history）

Genesis 的關鍵機制是驗證閘控接受（validation-gated acceptance）：只有通過驗證的本地變更（local changes）與已接受結果（accepted consequences）才會進入持續版本歷史（persistent version history），成為後續代理繼承的已接受軟體事件（accepted software events）。未通過驗證的候選變更不會污染主線歷史，從而維持專案長期一致性。

這個流程可視為一種自動化的「分支–驗證–合併」循環：代理在本地世界（local world）中工作，產生候選變更，經過測試或品質閘控後，才由父層代理或系統決定是否接受。這與傳統版本控制系統（如 Git）的差異在於，分支、驗證與合併的決策由代理架構自動化驅動，而非完全依賴人工程式設計師。

##### 方法論的設計意涵與未明之處

Genesis 的方法論有幾個重要意涵：

1. **以專案為中心的延續性**：代理的能動性（agency）被反覆實例化，而專案歷史（project history）持續累積。
2. **路徑範圍降低認知負荷**：透過儲存庫路徑（repository path）限定上下文，減少單一代理需要同時處理的資訊量。
3. **驗證作為信任邊界**：驗證閘控接受（validation-gated acceptance）是防止技術債快速累積的核心防線。

然而，從提供的文本中，仍有若干實作細節未完全揭露：驗證準則如何設計（單元測試、整合測試、靜態分析或數值稽核？）、多個並行本地世界（local world）之間的衝突如何解決、接受決策是由管理代理（manager agent）還是外部規則做出、以及失敗變更的回收與重試策略為何。這些細節對於評估系統的可擴展性與穩健性至關重要。

#### 實驗數據解讀

##### 綠地建構（greenfield formation）：從無到有建構 C 編譯器

Genesis 最具說服力的實驗是以 DeepSeek V4 Flash 為基礎模型，從一個無編譯器實作（implementation-empty repository）的儲存庫（repository）開始，建構一個以 Rust 為基礎的 C 編譯器（Rust-based C compiler）。數據如下：

- 追蹤行數（tracked lines）：約 248,989 行
- 執行時間：超過 120 小時
- 代理回合（agent episodes）：超過 1,000 個
- 模型 token 費用（model-token charges）：僅約 44 美元
- 測試覆蓋：完整通過 c-testsuite，並通過大部分 LLVM 測試（LLVM tests）與 Csmith 測試（Csmith tests）

這組數據顯示 Genesis 能將大量有限生命週期代理（finite-lived agents）的本地變更（local changes）累積成複雜系統。值得注意的是，44 美元的成本極低，暗示系統在提示設計、工具呼叫頻率與模型選擇上做了顯著優化，或者 DeepSeek V4 Flash 的定價極具競爭力。然而，追蹤行數（tracked lines）本身並不等同於「高品質程式碼行數」，可能包含測試、產生文件或重複結構；需要進一步區分原始碼、測試碼與生成輔助檔案。

##### 延續（continuation）：代理替換（agent replacement）與基礎模型（foundation model）切換

在第二個實驗中，Genesis 使用 GLM 5.2 繼續開發同一個編譯器世界（compiler world），並在多次代理替換（agent replacement）後仍保持完整測試表現（test performance）。這直接驗證了論文的核心主張：延續性屬於持續專案（persistent project），而非個別代理。即使作用中代理（active agent）不斷更換，甚至底層基礎模型（foundation model）改變，已接受版本（accepted version）與持續版本歷史（persistent version history）仍能確保開發不中斷。

##### 重新開發（redevelopment）：MESA Fortran → Rust

第三個實驗將 13 個 MESA 模組（MESA modules）、超過 10 萬行 Fortran 程式碼，重新實作（reimplemented）為一個約 9 萬行 Rust 程式碼的 Rust 工作空間（Rust workspace）。在六個數值工作負載（numerical workloads）上，中位數加速比（median speedups）達到 1.55–6.87 倍，且保留了經過稽核的數值行為（numerical behaviour）。

這項結果的意義在於：Genesis 不僅能進行綠地建構（greenfield formation），也能處理需要保留科學計算語義的重新開發（redevelopment）。然而，加速比的來源需要謹慎解讀：Rust 相較於 Fortran 在某些記憶體配置與現代化編譯器優化下可能自然帶來效能提升，因此部分加速可能來自語言遷移本身，而非 Genesis 的代理協作機制。此外，論文未提供與人工重寫或傳統遷移工具的直接比較，因此難以判斷 Genesis 在效率或正確性上的相對優勢。

##### 整體評估與限制

整體而言，三組實驗涵蓋了長期軟體開發（long-horizon software development）的三個關鍵階段：形成（formation）、延續（continuation）與重新開發（redevelopment）。實驗規模與測試覆蓋度令人印象深刻，但仍存在以下限制：

- 缺乏與其他程式設計代理（coding agents）或基準測試（benchmarks）的直接對照。
- 測試通過率雖高，但「大部分 LLVM 測試與 Csmith 測試」並非全部，對於編譯器這類高正確性要求系統，剩餘失敗案例的性質值得深入分析。
- 數值行為（numerical behaviour）的稽核方法未詳細說明，科學軟體的重新開發需要更嚴謹的誤差分析與可重現性驗證。

#### 與現有研究的比較

##### 相較於議題導向程式設計代理（coding agents）

現有主流基準測試（benchmarks）如 SWE-bench、SWE-agent、OpenHands 主要聚焦於議題解決（issue resolution），即針對單一錯誤或功能請求產生修補。Genesis 則將視角拉長到儲存庫層級軟體開發（repository-level software development）的整個生命週期，包括從無實作內容的儲存庫（implementation-empty repository）開始的綠地建構（greenfield formation）與後續的軟體演化（software evolution）。這不是取代現有代理，而是將其嵌入一個更大的持續專案（persistent project）框架中。

##### 相較於記憶、協調與持續狀態機制

許多現有系統透過記憶（memories）、可重用技能庫、多代理角色與工作流來維持延續性。這些方法通常透過延長代理的某個部分（如上下文視窗（context window）、共享草稿區（shared scratchpad）或管理器（managers））來解決延續性問題（continuity problem）。Genesis 的組織選擇則相反：它讓已接受專案狀態（accepted project state）與專案歷史（project history）成為持續存在的物件，而代理執行狀態保持回合有界。這種以專案為中心的設計在理論上更能抵禦單一代理失敗、上下文截斷與模型漂移。

##### 相較於 EvoGit 與版本控制

EvoGit 提出讓獨立代理在無集中協調、無顯式訊息傳遞、無共享記憶體的情況下修改與重組 Git 圖。Genesis 同樣重視版本歷史（version history），但更進一步將其與遞迴委派（recursive delegation）、路徑範圍上下文（path-scoped contexts）以及父層中介的接受機制結合。換言之，Genesis 不是把 Git 當成被動儲存，而是把版本歷史當成主動組織代理能動性（agency）的結構。

##### 相較於程式演化系統

FunSearch、AlphaEvolve、ERA 等系統透過反覆生成與評估來改進程式變體，本質上是在一個候選程式群體或搜尋樹中進行演化。Genesis 的焦點不同：它追蹤的是單一軟體專案的持續歷史，而非一群候選程式的競爭與篩選。這使得 Genesis 更適合需要長期維護、介面穩定性與架構承諾（architectural commitments）的實際軟體工程場景。

##### 相較於科學軟體重新開發

科學程式碼庫（scientific codebase）的重新開發特別困難，因為可重現性不僅取決於程式能否執行，更取決於數值行為（numerical behaviour）是否在不同環境與實作間保持一致。Genesis 以 MESA 模組（MESA modules）為案例，展示了在保留數值行為的前提下，將 Fortran 遷移至 Rust 的可行性，回應了近期對於 AI 輔助變更可能威脅科學軟體品質的擔憂。

##### 主要限制

儘管概念新穎，Genesis 與現有研究相比仍有待釐清之處：

- **接受準則的設計**：驗證閘控接受（validation-gated acceptance）的具體規則與閾值未詳細說明。
- **衝突解決**：當多個本地世界（local world）同時修改重疊路徑時，系統如何合併與仲裁？
- **安全與監督**：自主軟體演化（autonomous software evolution）帶來程式碼注入、惡意工具呼叫與未經審查變更的風險，論文未深入討論。
- **路徑分解啟發式**：遞迴委派（recursive delegation）的粒度由誰決定？過細會增加回合數，過粗則失去範圍限縮效益。

#### 可重現性評估

論文提到專案網站為 https://genesis.evox.group/，但從提供的文本中無法確認原始碼、資料集、提示模板與執行日誌是否已公開。可重現性（reproducibility）的評估可分為以下層面：

##### 已公開或可取得的元件

- **測試套件**：c-testsuite、LLVM 測試（LLVM tests）、Csmith 測試（Csmith tests）均為公開資源，便於第三方驗證編譯器正確性。
- **MESA**：Modules for Experiments in Stellar Astrophysics（MESA）為開源科學軟體，原始 Fortran 程式碼與文件可取得。
- **基礎模型（foundation models）**：DeepSeek V4 Flash 與 GLM 5.2 可透過 API 呼叫，但模型權重（model weights）與內部訓練細節未必完全公開，這會影響結果在不同時間點的一致性。

##### 尚待釋出的關鍵資訊

若要達到高可重現性，作者社群需要釋出：

1. Genesis 系統的原始碼與代理編排邏輯。
2. 管理代理（manager agent）與執行代理（executor agents）的系統提示與工具定義。
3. 驗證閘控（validation gate）的具體實作，包括測試選擇、逾時設定與接受條件。
4. 每次代理回合（agent episodes）的完整日誌、成本明細與產生的候選變更。
5. 執行環境規格（作業系統、Rust 編譯器版本、相依套件版本）。
6. MESA 重新開發（redevelopment）案例中的數值稽核腳本與誤差容忍度設定。

##### 綜合評估

目前可重現性處於「中等不確定」狀態：若專案網站最終釋出完整程式碼與實驗紀錄，由於外部測試資源均公開，第三方應能重現主要結果；若僅釋出論文與高階說明，則難以驗證 1,000 多個代理回合（agent episodes）如何協作、驗證與合併。建議作者遵循軟體工程與機器學習領域的 artifact review 標準，提供可執行的容器化環境與重現腳本。

#### 未來研究方向

基於 Genesis 的持續遞迴世界（persistent recursive world）框架，未來研究可朝以下方向延伸：

##### 1. 形式化驗證與更強的接受閘控

目前的驗證閘控接受（validation-gated acceptance）主要依賴測試通過率。未來可整合靜態分析、型別檢查、符號執行、模型檢查或形式化規範，以提升高風險模組（如編譯器後端、數值核心）的正確性保證。

##### 2. 自動化且適應性的路徑分解

遞迴委派（recursive delegation）的效能高度依賴路徑分解品質。未來可研究如何根據程式碼結構、相依圖與歷史修改頻率，自動決定最適儲存庫路徑（repository path）粒度，並在開發過程中動態調整。

##### 3. 多基礎模型（foundation model）協作與專家代理

Genesis 已展示在不同基礎模型（foundation model）間切換的可行性。下一步可設計模型選擇機制：例如讓擅長規劃的模型擔任管理代理（manager agent），讓擅長低階實作的模型擔任執行代理（executor agents），並根據任務難度與成本動態調度。

##### 4. 與持續整合／持續部署（CI/CD）的整合

將 Genesis 的持續版本歷史（persistent version history）與現有 CI/CD 管線結合，可讓人類開發者在關鍵接受點進行監督，同時讓代理在背景進行實驗性分支與重構。

##### 5. 長期軟體開發（long-horizon software development）的標準基準測試（benchmarks）

目前缺乏針對數週至數月尺度、多代理替換、跨階段演化的標準基準測試（benchmarks）。未來可建立涵蓋形成（formation）、延續（continuation）、重新開發（redevelopment）與技術債管理的綜合評估框架。

##### 6. 安全、可解釋性與人機協作

自主軟體演化（autonomous software evolution）必須面對惡意程式碼生成、權限提升與不可解釋變更的風險。未來研究可探索人機迴圈（human-in-the-loop）治理、變更說明生成、來源追蹤與最小權限工具執行。

##### 7. 跨專案技能轉移與可重用知識

Genesis 的已接受專案狀態（accepted project state）可擴展為跨專案的可重用技能庫。研究如何從一個持續專案（persistent project）中提取通用模式、重構策略與測試模式，並遷移到另一個專案，是提升長期效益的重要方向。

##### 8. 成本–品質權衡與能源效率

雖然本研究的模型 token 費用（model-token charges）極低，但隨著專案規模擴大，1,000 個以上的代理回合（agent episodes）仍可能產生顯著成本與碳足跡。未來可研究如何根據變更風險與預期效益，動態分配模型資源與驗證深度。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**  
A：核心問題是長期軟體開發中的延續性問題：軟體系統的生命週期遠超過任何單一程式設計代理的存在時間，但現有方法往往透過延長代理本身的記憶、會話或管理器來維持連續性。Genesis 提出讓軟體專案本身成為持續存在的實體，而本地代理則保持有限生命週期。如此一來，後續代理可以繼承已接受的專案狀態與歷史，而不必依賴同一個作用中代理。

**Q2：現有的持續性方法為何不足？**  
A：現有方法通常藉由更大的上下文視窗、持續記憶、管理代理或共享草稿區來保存資訊，但這些做法本質上是把延續性建立在代理流程的某個部分之上。當代理必須被替換或基礎模型改變時，這些依附於代理的狀態可能斷裂或難以轉移。Genesis 認為真正需要持續的是已接受專案狀態與持續版本歷史，而非代理的執行狀態。

**Q3：為什麼區分代理生命週期與開發流程生命週期很重要？**  
A：真實的軟體專案會累積介面、測試、架構承諾與部分解決方案，這些約束會隨時間影響後續貢獻者；因此長期開發不是單一長任務，而是許多有界貢獻持續保持連貫的過程。如果連續性綁定在單一代理身上，一旦代理替換或模型更新，整個開發流程就容易中斷。把延續性還給專案，才能讓不同基礎模型與多次代理回合協同演化同一個軟體系統。

**Q4：Genesis 的核心方法是什麼？**  
A：Genesis 將軟體表示為持續遞迴世界，每個本地世界由一個已接受版本與一個儲存庫路徑共同定位。有限生命週期代理在這個本地世界中接收目標、執行有界任務並提出本地變更；遞迴委派可把細部工作移轉到更特定的路徑，而只有通過驗證閘控接受的已接受結果才會推進持續版本歷史。這種組織讓專案狀態隨時間累積，而代理則在完成任務後終止。

**Q5：這項研究最關鍵的創新點是什麼？**  
A：最關鍵的創新在於顛覆了「要讓代理持續存在才能維持開發連續性」的預設，改為讓軟體專案本身持續存在並反覆實例化代理能動性。最小版本–路徑模型把已接受版本、儲存庫路徑、本地代理、遞迴委派與驗證閘控接受區分開來，使個別代理的生命週期與軟體開發流程的生命週期解耦。結果是後續代理只繼承經過驗證的專案歷史，而不是繼承前任代理的內部狀態。

**Q6：哪些設計選擇讓 Genesis 能夠實現這種組織？**  
A：首先，版本–路徑模型把專案狀態與代理責任範圍分離，讓代理從特定路徑開始但繼承整個已接受版本。其次，管理與執行代理在路徑範圍上下文內運作，遞迴委派可將工作細分到子路徑而不立即改變已接受版本。最後，只有父層中介並通過驗證的已接受軟體事件才會進入持續版本歷史，確保後續代理看到的是穩定且可繼承的專案狀態。

**Q7：論文進行了哪些實驗來評估 Genesis？**  
A：論文從三個階段評估：形成階段從無實作內容的儲存庫綠地建構一個以 Rust 為基礎的 C 編譯器；延續階段在反覆代理替換並更換基礎模型後，觀察編譯器世界是否仍能持續開發並保持測試表現；重新開發階段則將 13 個 MESA 模組從超過 10 萬行的 Fortran 重新實作為近 9 萬行 Rust 的工作空間，並檢驗數值行為。

**Q8：實驗中最主要的結果是什麼？**  
A：在 C 編譯器形成實驗中，Genesis 使用 DeepSeek V4 Flash 耗時超過 120 小時、累積超過 1,000 個代理回合、僅花費約 44 美元模型 token 費用，就建構出約 25 萬追蹤行的編譯器，並通過完整的 c-testsuite 以及大部分 LLVM 與 Csmith 測試。在延續實驗中，以 GLM 5.2 生成的編譯器世界經過多次代理替換後，仍保留完整的測試表現。MESA 重新開發則在六個數值工作負載上達到 1.55 至 6.87 倍的中位數加速比。

**Q9：這些實驗是否包含傳統的消融研究？**  
A：論文沒有採用傳統的單一變數消融，而是透過三個互補階段來論證同一套專案中心組織的通用性與穩健性。延續階段可視為對「代理必須持續存在」這一假設的實證消融：反覆代理替換後專案仍能運作，顯示持續性來自專案而非代理。重新開發階段則進一步證明該組織能處理跨語言、跨領域的大規模改造，同時保留經審計的數值行為。

**Q10：Genesis 適合哪些實際應用場景？**  
A：Genesis 特別適合生命週期長、需要持續維護與演化的軟體系統，例如編譯器、科學計算程式庫、作業系統元件與大型基礎設施專案。在這些場景中，開發者或基礎模型會不斷更替，但專案必須保持一致性與可驗證性。透過讓專案本身持續存在，Genesis 能夠在代理替換或模型升級時，繼續進行錯誤修復、功能新增、重構甚至語言遷移。

**Q11：若要把 Genesis 產品化，需要考慮哪些因素？**  
A：產品化時必須強化驗證閘控與人工監督機制，確保只有高品質的已接受結果才能進入持續版本歷史，避免錯誤累積。此外，路徑範圍上下文雖然有助於並行與責任劃分，但需要良好的儲存庫結構與安全沙箱，以防止代理誤改關鍵檔案。成本方面，實驗顯示以極低模型 token 費用就能產出大規模程式碼，但長時間運行仍需穩定的執行環境、完整的審計紀錄與版本控制整合。

**Q12：這項研究可能對相關領域帶來什麼影響？**  
A：Genesis 把研究焦點從「如何讓單一代理記得更多」轉向「如何讓專案狀態成為可繼承的持續實體」，這可能重塑長期軟體開發與自主軟體演化的設計典範。對科學軟體而言，它提供了一種在重構或遷移時保留數值行為與可重現性的組織方式。更廣泛地，它為開源維護、跨模型協作與大規模程式碼庫的自主演化開闢了新的可能性。

**Q13：論文承認哪些限制？**  
A：論文指出，目前評估僅涵蓋編譯器建構與 MESA 模組重新開發兩大類任務，尚未在更多領域與更大規模的真實儲存庫上驗證。此外，系統高度依賴驗證機制的品質：若測試或數值審計不完整，錯誤的已接受結果仍可能進入專案歷史。路徑範圍上下文雖然降低耦合，但對於跨越多個路徑的橫切關注點，仍可能需要額外的協調機制。

**Q14：Genesis 可能在哪些情況下失敗？**  
A：如果驗證閘控無法捕捉語義或數值上的細微錯誤，系統可能會把看似通過測試但實際有缺陷的程式碼納入已接受版本。遞迴委派過度細分時，也可能導致代理遺失巨觀上下文，產生局部最優但整體不一致的修改。此外，當專案存在大量未記錄的隱含依賴或跨路徑交互作用時，單純依賴已接受專案狀態可能不足以讓新代理立即理解全貌。

**Q15：未來可以朝哪些方向延伸？**  
A：未來可將持續遞迴世界擴展到更多程式語言、分散式系統與多專案協作場景，並結合形式化驗證以補強測試導向的驗證閘控。另一方向是讓系統從持續版本歷史中自動學習可重複使用的技能與約束，減少對外部提示的依賴。最後，引入適度的人機協作接受機制，並在真實開源專案上進行長期部署，將有助於驗證其在實際軟體演化中的穩健性。

## 實務應用指南

## 適用場景

1. **長期維護的關鍵基礎設施程式碼庫**  
   作業系統元件、資料庫核心、編譯器或金融結算系統等需要數月甚至數年持續演化的專案，最適合採用持續遞迴世界。當個別程式設計代理的生命週期有限，專案歷史與已接受版本能確保後續代理繼承正確上下文，避免因代理替換而遺失架構承諾。

2. **科學計算與遺留語言重構（如 Fortran → Rust）**  
   天文、氣候、材料模擬等領域的科學程式碼庫常累積大量 Fortran 程式碼。Genesis 的重新開發模式可在保留已審計數值行為的前提下，將 MESA 模組等程式碼逐步重寫為 Rust 工作空間，並透過數值工作負載驗證中位數加速比與結果正確性。

3. **從無到有的綠地建構（Greenfield Formation）**  
   當團隊需要從實作空白的儲存庫開始建構複雜系統——例如 Rust 為基礎的 C 編譯器——Genesis 能將大任務遞迴委派至多個本地世界，讓有限生命週期的代理分別處理語法分析、語意檢查、程式碼產生與測試，最終累積成可通過 c-testsuite、LLVM tests 與 Csmith tests 的完整系統。

4. **多基礎模型協作的持續開發**  
   當單一 LLM 供應商無法滿足成本、速度或能力需求時，Genesis 允許在不同回合使用 DeepSeek V4 Flash、GLM 5.2 等不同基礎模型，並透過持續版本歷史維持延續性，適合需要跨模型、跨團隊長期協作的產品。

5. **需審計軌跡的受監管軟體演化**  
   醫療器材、自動駕駛、航太軟體等領域要求每項變更都可追溯。由於 Genesis 只讓已接受結果進入持續版本歷史，每個代理回合的目標、修改與驗證結果都能成為 provenance record，便於監管審查與回滾。

## 實作前置條件

- **資料準備**  
  - 現有儲存庫（可為無實作內容的儲存庫或既有科學程式碼庫）。  
  - 完整且可自動執行的驗證閘：單元測試、整合測試、外部基準測試（如 c-testsuite）、數值工作負載與黃金結果（golden outputs）。  
  - 路徑層級的責任劃分文件，說明各儲存庫路徑的介面、架構承諾與修改範圍。

- **運算資源**  
  - 可長時間運行的執行環境（論文中編譯器世界運行超過 120 小時）。  
  - 足夠的儲存空間保存每個代理回合的狀態、候選變更與驗證紀錄（論文存檔超過 1,000 個代理回合）。  
  - LLM API 預算與配額管理（論文僅花費約 US$44，但實際規模可能更高）。  
  - 沙箱化執行環境，避免代理執行任意指令影響主機安全。

- **技能需求**  
  - 熟悉目標語言與領域（如 Rust、Fortran、編譯器理論或數值模擬）。  
  - 具備設計驗證閘與持續整合/持續部署（CI/CD）管線的能力。  
  - 理解代理編排、版本控制（Git）與遞迴任務分解。  
  - 能夠審查代理產生的程式碼，特別是數值行為與安全關鍵路徑。

## 實作步驟建議

1. **定義最小版本–路徑模型**  
   為專案建立 `local world = (accepted version, repository path)` 的座標系統。已接受版本必須包含完整原始碼、路徑特定上下文、約束條件、驗證結果與來源紀錄。

2. **建立驗證閘控接受機制**  
   在每次代理提出本地變更後，必須先執行自動化測試與基準測試，只有通過驗證的已接受結果才能寫入持續版本歷史。建議設計分層驗證：快速煙霧測試 → 完整測試套件 → 長時間數值工作負載。

3. **設計遞迴委派策略**  
   將大任務拆解為可放入單一代理回合的有界任務。當某路徑的修改需要更細部處理時，透過遞迴委派將工作移轉到更特定的儲存庫路徑，而非直接改變已接受版本。

4. **配置管理代理與執行代理**  
   管理代理負責解析目標、決定委派與審查候選變更；執行代理負責在路徑範圍上下文內產生具體修改。兩者皆為有限生命週期代理，完成任務後即終止。

5. **啟動形成、延續或重新開發**  
   - **形成**：從空白或極小儲存庫開始，逐步累積介面、測試與實作。  
   - **延續**：在代理替換或更換基礎模型後，讓新代理從最新已接受版本與指定路徑進入，繼承完整專案歷史。  
   - **重新開發**：鎖定需要重寫的模組路徑，保留原始數值測試作為行為錨點，逐步以新語言或架構重新實作。

6. **監控、審計與週期性重構**  
   持續追蹤代理回合數、token 費用、測試通過率與技術債累積。定期讓代理檢視專案歷史中的失敗紀錄與部分解決方案，避免重複錯誤。

## 潛在風險與注意事項

- **驗證不足導致的隱性迴歸**  
  若驗證閘僅覆蓋語法或編譯成功，可能遺漏數值行為漂移。建議對科學計算程式碼加入黃金結果比對與統計檢定。

- **代理在局部最優停滯**  
  有限生命週期代理可能傾向選擇短期可通過測試的權宜方案。可透過管理代理定期審查架構承諾，並在專案歷史中標記技術債。

- **工具執行安全風險**  
  代理可執行指令與修改檔案，必須在隔離容器或虛擬機器中運行，並限制網路與檔案系統權限。

- **成本與時間低估**  
  雖然論文中編譯器僅花費約 US$44，但長期軟體開發的總 token 消耗、驗證運算與儲存成本可能迅速成長。建議設定每回合與每日預算上限。

- **過度委派造成的協調開銷**  
  遞迴委派雖能細分工作，但過細的路徑拆分可能增加整合難度。應根據模組邊界與測試覆蓋率調整委派粒度。

## 與其他技術的整合建議

- **版本控制系統（Git）**  
  將 Genesis 的已接受版本映射為 Git commit 或 branch，利用現有分支策略、code review 與 revert 機制強化審計能力。

- **CI/CD 管線**  
  把驗證閘接入 Jenkins、GitHub Actions 或 GitLab CI，讓代理提出的候選變更先經過標準化持續整合流程，再決定是否接受。

- **現有 LLM 平台與代理框架**  
  Genesis 可與 SWE-agent、OpenHands 等程式設計代理框架互補：後者負責單一問題解決，Genesis 負責跨回合的專案歷史與委派。

- **記憶與技能庫系統**  
  雖然 Genesis 以專案為持續主體，但仍可整合反射記憶或 reusable skill libraries，讓常用重構模式、測試樣板與領域知識在代理回合間加速調用。

- **議題追蹤與專案管理工具**  
  將代理回合目標對應到 Jira、GitHub Issues 或 Linear 的工單，讓人類團隊能監控進度、設定優先順序並在關鍵決策點介入。

## 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦第 1 節與第 3.1 節，理解「持續的是專案，不是代理」這個核心概念；把 Genesis 想像成一個永遠不關機的軟體專案，許多短期工讀生（代理）輪流進來做有界任務，但只有通過測試的修改才會被留下。不必急著理解編譯器或 MESA 的技術細節，重點是掌握版本–路徑模型與驗證閘控接受的思想。

- **AI 工程師**  
  請仔細閱讀第 3 節的系統設計與第 4 節的實驗設定，特別注意管理代理與執行代理的分工、遞迴委派的實作方式，以及如何把驗證回饋轉化為接受/拒絕訊號。建議對照你目前使用的代理框架，思考哪些部分可以替換為 Genesis 的持續版本歷史機制，並評估驗證閘的延遲與成本。

- **研究人員**  
  本文的貢獻在於將軟體演化重新概念化為持續遞迴世界，而非單純延長代理上下文。建議深入分析第 2 節與第 3 節的形式化論述，並將其與程式演化（FunSearch、AlphaEvolve）、多代理協調與軟體工程經典理論（Parnas、Lehman）進行比較。實驗部分可作為設計長期軟體開發基準測試的參考。

- **產品經理**  
  重點看摘要、第 1 節與三階段評估（形成、延續、重新開發），評估 Genesis 是否適用於你負責的長期產品線。請特別關注成本數據（US$44、120 小時、1,000 個代理回合）與風險可控性（驗證閘、審計軌跡），並思考如何將其包裝為可管理的開發流程，讓人類工程師在關鍵節點進行監督與決策。
