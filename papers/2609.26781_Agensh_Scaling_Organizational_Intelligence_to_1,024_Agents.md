## ⚡ TL;DR

現有多智能體框架受中央協調器限制，難以擴展並行處理複雜任務。
提出 Agensh，以共享工作空間、訊息介面與共享上下文支援工作者自我組織、非同步協作。
128 智能體使測試通過率提升 49%，擴至 1,024 個達 55.06%，顯示數量為新擴展維度。

## 摘要翻譯

多智能體系統（multi-agent system）可透過並行（concurrent）執行工作來降低複雜任務的延遲（latency）。目前已有若干開創性的多智能體協作框架（multi-agent harness）支援多智能體系統。然而，現有多智能體協作框架的可擴展性（scalability），往往受限於中央協調器（central orchestrator）分配任務與協調工作者（worker）的能力。為解決此限制，我們提出 Agensh，一種可擴展（scalable）、自我組織（self-organized）且無中央協調器的多智能體協作框架：並行運作的工作者執行多智能體協作迴圈（multi-agent cooperation loop），持續收集上下文（context）、認領並自我分配子任務（sub-task）、採取行動（action）與分享發現、驗證結果，並以非同步（asynchronous）方式合併進度。此迴圈由智能體組織基礎設施（agentic organization infrastructure）所支援；該基礎設施包含三個元件：共享工作空間（shared workspace）存放已提出、進行中與已完成的工作；訊息介面（message interface）供工作者彼此溝通；共享上下文（shared context）則保留可重複使用的發現（reusable findings）與工作意圖（work intentions）。

為測試 Agensh 的可擴展性，我們使用 GPT-5.6-sol (high) 在 ProgramBench 最困難的五項任務上進行評估。將智能體（agent）數量從 1 擴展至 128，平均最終測試通過率（mean final test-pass rate）從 19.31% 提升至 28.78%，相對改善幅度（relative improvement）約為 49%。規模更大的組織能更早達到相近的測試通過率。在 pandoc 任務上，將智能體數量從 1 擴展至 1,024，最終測試通過率（final test-pass rate）從 33.89% 提升至 55.06%。工作者軌跡（worker trajectory）進一步顯示，隨著組織規模擴大，不同形式的自我組織協作（self-organized cooperation）會逐漸湧現並標準化（emerge and standardize）。這些結果揭示，智能體數量是多智能體組織的一個全新擴展維度（scaling dimension），可拓展通用智能（general intelligence）的邊界，並為在嚴格延遲限制（hard latency constraints）或時間預算（time budget）下的複雜任務提供實用的解決方案。

### 核心貢獻（3～5點）
- 提出 Agensh，一種無中央協調器、可擴展且自我組織的多智能體協作框架，讓工作者能並行且非同步地執行協作迴圈。
- 設計智能體組織基礎設施，包含共享工作空間、訊息介面與共享上下文，以支援大規模智能體協作。
- 在 ProgramBench 最困難的五項任務上驗證可擴展性：智能體數量從 1 增至 128 時，平均最終測試通過率相對提升約 49%。
- 在 pandoc 任務上展示從 1 到 1,024 個智能體的擴展效益，最終測試通過率從 33.89% 提升至 55.06%。
- 透過工作者軌跡觀察到自我組織協作形式會隨組織規模擴大而逐漸湧現並標準化，揭示智能體數量是拓展通用智能的新擴展維度。

### 適合對象
本論文適合多智能體系統、大型語言模型智能體協作、智能體軟體工程，以及關注低延遲、大規模分散式協調與組織智能的研究者與工程師閱讀。對於需要在嚴格延遲限制或時間預算內解決複雜任務的實務應用開發者，亦具高度參考價值。

## 深度分析

#### 方法論解析

Agensh（可擴展自我組織多智能體協作框架）的核心設計是移除傳統的 central orchestrator（中央協調器），改由多個 worker（工作者）透過一個共用的 multi-agent cooperation loop（多智能體協作迴圈）與 agentic organization infrastructure（智能體組織基礎設施）進行自我組織。整體方法論可拆解為兩個互補的層面：協作迴圈與組織基礎設施。

在協作迴圈中，每個 worker 反覆執行以下五個步驟：

1. Gather context（收集上下文）：worker 讀取使用者的目標、shared workspace（共享工作空間）中的最新狀態、shared context（共享上下文）裡的同儕發現與工作意圖，以及 message interface（訊息介面）中的公告與直接訊息，必要時與環境互動以判斷下一步。
2. Claim sub-task（認領子任務）：worker 自行提出一個 sub-task（子任務），並在 shared context 中以 CLAIM 標記其範圍。若與其他 worker 的認領發生重疊或衝突，則透過訊息協商解決。
3. Take action（採取行動）：worker 在本地使用 available tools（可用工具）執行該子任務，並在過程中把可能對同儕有用的 reusable findings（可重複使用的發現）寫回 shared context。
4. Verify results（驗證結果）：worker 將本地成果與子任務的 acceptance criteria（驗收準則）比對，未通過則修正。
5. Merge progress（合併進度）：worker 把通過驗證的貢獻合併到 shared workspace，並發布更新說明變更內容、背後思路與驗證證據。若發生 merge conflict（合併衝突），則整合最新同儕進度後再次嘗試。

這個迴圈的關鍵在於「非同步」與「自我分配」。worker 不需要等待所有同儕完成同一輪迭代，而是持續從共享基礎設施中讀取最新狀態，自主決定下一步要做什麼。這消除了 central orchestrator 在 task decomposition（任務分解）、assign tasks（分配任務）與 manage workers（管理工作者）上的瓶頸。

組織基礎設施包含三個協調元件：

- Shared workspace：以 Git 平台實作，支援 concurrent writes（並行寫入）、asynchronous reads（非同步讀取）、版本歷史與衝突暴露，讓 worker 能在私有分支上開發，再將成果整合回組織。
- Message interface：承載 organization-wide announcement（組織範圍公告）與 urgent direct message（緊急直接訊息），用於協調衝突、避免重複工作。
- Shared context：保留 reusable findings、CLAIM 標記、失敗嘗試與工作意圖，使組織記憶得以累積並被所有 worker 讀取。

這套設計的優勢在於極度輕量：它不需要訓練專門的 orchestrator，也不依賴預先定義的任務圖。worker 透過 CLAIM 與訊息達成共識，透過 Git 達成整合，透過 shared context 達成記憶共享。然而，這也對底層 large language model（大型語言模型）的自我規劃與自我協調能力提出很高要求；若 worker 無法正確判斷子任務範圍或有效解決衝突，可能出現重複探索、整合失敗或方向發散。

#### 實驗數據解讀

論文在 ProgramBench（智能體軟體工程基準測試）上評估 Agensh，選取其中五個最困難的任務，這些 reference repository（參考儲存庫）包含數千個檔案、數百萬位元組的 source code（原始碼），並在無網路、6 小時 time budget（時間預算）下進行。實驗使用 GPT-5.6-sol（high）作為底層模型。

主要量化結果如下：

- 從 1 個 worker 擴展到 128 個 worker，五個任務的 mean final test-pass rate（平均最終測試通過率）從 19.31% 提升至 28.78%，relative improvement（相對改善幅度）約 49%。
- 在 pandoc 任務上，從 1 個 worker 擴展到 1,024 個 worker，final test-pass rate（最終測試通過率）從 33.89% 提升至 55.06%。
- 更大的組織能「更早」達到與小組織相當的測試通過率，顯示增加 worker 數量可降低達到特定性能所需的 latency（延遲）。

這些數據有幾層意義。首先，它證明了在沒有 central orchestrator 的情況下，單純增加 agent（智能體）數量仍能帶來顯著性能增益，這把 agent count 確立為一個新的 scaling dimension（擴展維度）。其次，pandoc 上 1,024 個 worker 的結果顯示該框架在極大規模下仍具可擴展性，並未因協調開銷而崩潰。第三，「較大組織較早達標」的現象對 hard latency constraints（嚴格延遲限制）或固定時間預算的應用場景特別重要：與其讓單一智能體循序執行六小時，不如讓數百個 worker 並行探索六小時。

論文還透過 worker trajectory（工作者軌跡）進行質性分析，發現隨著組織規模擴大，self-organized cooperation（自我組織協作）會逐漸 emerge and standardize（湧現並標準化），包括同儕協調、多 worker 整合、標準化工作流程，乃至規模化後的專業化角色分工。這暗示 organizational intelligence（組織智能）可能不只是單一智能體能力的線性加總，而是透過互動結構產生的集體現象。

不過數據也應謹慎解讀。平均測試通過率仍低於 30%，顯示即便有 128 個 worker，這些任務對當前模型仍極具挑戰。論文未報告變異數、token 消耗、成本或失敗模式分佈，因此難以判斷 49% 相對改善的穩健性與經濟可行性。此外，實驗僅涵蓋五個任務與單一模型設定，泛化性仍有待驗證。

#### 與現有研究的比較

現有主流 multi-agent harness（多智能體協作框架）如 Codex sub-agent、Claude Code sub-agent and agent teams、Copilot fleet 與 Kimi Agent Swarm 普遍採用 orchestrator-worker structure（協調器-工作者架構）。在這種架構中，一個主要的 orchestrator 負責 plan（規劃）、decompose tasks（分解任務）、assign tasks（分配任務）並 manage workers（管理工作者）。這類方法的優點是結構清晰、易於追蹤全局進度，且對簡單任務通常較穩定；但其 scalability（可擴展性） fundamentally limited by the orchestrator’s capacity（根本上受協調器能力限制），因為所有協調決策都需經過單一節點。

Agensh 的改進在於完全移除 central orchestrator，將協調責任分散到每個 worker。這帶來幾項優勢：

- 消除單點瓶頸：協調負載隨 worker 數量分散，而非集中於單一智能體。
- 降低對 orchestrator 訓練的依賴：不需要專門訓練一個會規劃與分配的 orchestrator。
- 提升並行度：worker 可 asynchronous（非同步）執行，減少 sequential execution constraint（循序執行限制）帶來的延遲。
- 促進組織智能湧現：透過 shared context 與訊息互動，可能產生傳統 orchestrator 難以預設的協作模式。

然而，這種去中心化設計也有其代價。相較於 orchestrator-worker 架構，Agensh 缺乏一個全局規劃者，可能導致子任務覆蓋不完整、重複探索或方向衝突。現有 orchestrator 系統在任務結構明確時，通常能提供更可預測的執行路徑與更高的可解釋性。Agensh 則更適合高度複雜、難以預先分解、且對延遲敏感的任務。

與更廣泛的多智能體研究（如 swarm intelligence、多智能體強化學習或開放式 LLM 社會）相比，Agensh 的獨特之處在於它是一個針對 agentic software engineering（智能體軟體工程）的實用 harness，並以 Git 作為 shared workspace 的具體實作，使程式碼整合與版本控制成為協調機制的一部分。

#### 可重現性評估

從目前提供的論文內容來看，Agensh 的可重現性面臨幾項挑戰：

- 程式碼與實作細節未公開：摘要與方法章節未提及是否釋出原始碼、prompt 設計、CLAIM 格式、訊息協議、驗證準則或 Git 分支策略。沒有這些細節，其他研究者難以精確復現。
- 模型可取得性：實驗使用 GPT-5.6-sol（high），這並非公開可取得的模型。即使未來透過 API 提供，"high" 設定的具體參數（如 temperature、sampling 策略、context window 大小）也未說明。
- 資料集與任務選擇：ProgramBench 雖然是已知基準，但論文未詳細說明選取「五個最困難任務」的標準、評分方式與測試環境配置。
- 運算資源與成本：128 至 1,024 個 worker 在 6 小時內並行運行，代表極高的運算與 token 成本。論文未披露成本數據，使得評估其實用性與可重現性變得困難。
- 軌跡資料：雖然論文提到分析 worker trajectory，但未說明是否會公開這些軌跡，而軌跡對於理解 self-organized cooperation 的湧現過程至關重要。

綜合而言，Agensh 的方法論描述處於中高層次，足以理解其設計哲學，但距離完全可重現仍有相當距離。建議作者釋出原始碼、prompt 模板、設定檔、完整 trajectories 以及每個實驗的資源消耗紀錄，以提升社群驗證與後續研究的可能性。

#### 未來研究方向

Agensh 開啟了幾個值得深入探索的研究方向：

1. 層級式自我組織：在完全去中心化與 central orchestrator 之間尋找平衡，例如讓 worker 動態形成小組並選出臨時協調者，以兼顧全局一致性與局部自主性。
2. 動態 worker 數量調整：根據任務難度、當前進度與資源預算，自動增加或減少 worker 數量，避免資源浪費。
3. 學習型通訊協議：目前 CLAIM 與訊息格式似乎依賴模型 zero-shot 能力。未來可透過微調或強化學習，讓 worker 學會更有效率的協調語言與衝突解決策略。
4. 長上下文與記憶壓縮：隨著組織規模擴大，shared context 的資訊量會快速成長。研究如何摘要、檢索或分層儲存上下文，是維持可擴展性的關鍵。
5. 擴展法則的系統性研究：建立 performance、agent 數量、通訊頻寬、時間預算與任務複雜度之間的定量關係，預測何時會出現收益遞減。
6. 錯誤容忍與品質保證：設計機制偵測並修復錯誤的 merge、誤導性的 findings 或陷入無效迴圈的 worker，提升系統穩健性。
7. 更廣泛的基準測試：將 Agensh 應用於程式碼生成以外的領域，例如科學推理、多模態創作或開放式問題解決，檢驗其泛化能力。
8. 成本、能源與效率分析：量化更多 worker 所帶來的 token 消耗、延遲改善與碳足跡之間的權衡，為實務部署提供依據。
9. 人機協作：引入 human-in-the-loop（人類參與迴路）機制，讓使用者在關鍵時刻調整目標、審查方向或解決歧義。
10. 安全性與對齊：確保大規模 self-organized cooperation 不會產生偏離使用者意圖的集體行為，並維持可審計性與可控性。

## 論文問答

**Q1：單一智能體系統在處理複雜任務時面臨哪些根本性限制？**

A：單一智能體系統受限於單一上下文視窗、單一行動流與單一記憶流，無法同時從多個角度處理問題或並行探索解決方案。這種循序執行限制使得複雜真實世界任務的延遲顯著增加，因為智能體必須一步一步依序完成所有工作。為了突破這些瓶頸，研究者需要將智能體數量擴展至多智能體系統，以實現並行處理與更低的延遲。

**Q2：現有的多智能體協作框架為何難以有效擴展？**

A：現有框架如 Codex sub-agent、Claude Code sub-agent、Copilot fleet 與 Kimi Agent Swarm 廣泛採用協調器-工作者架構，由中央協調器負責規劃、分解任務、分配子任務並管理工作者。然而，這種設計使整體系統的可擴展性 fundamentally 受限於中央協調器的管理能力、協調能力以及整合貢獻的能力。當工作者數量增加時，中央協調器容易成為單一瓶頸，無法有效處理大規模並行組織中的複雜動態。

**Q3：為什麼降低延遲對智能體系統很重要，而 Agensh 的發現有何意義？**

A：在許多真實應用中，複雜任務面臨嚴格延遲限制或有限的時間預算，例如需要在數小時內完成的大型軟體工程任務。Agensh 揭示智能體數量是 multi-agent organization 的一個全新擴展維度，類似於模型規模與資料規模之於單一模型的重要性。這不僅為嚴苛延遲情境提供了實用解決方案，也顯示擴展多智能體組織能夠拓展通用智能的前沿。

**Q4：Agensh 的核心設計是什麼？**

A：Agensh 是一個無中央協調器的可擴展自我組織多智能體協作框架，讓並行工作者以非同步方式執行多智能體協作迴圈。該迴圈包含收集上下文、認領子任務、採取行動、驗證結果與合併進度五個步驟，並透過智能體組織基礎設施支撐運作。此基礎設施由三個協調元件組成：存放已提出、進行中與已完成工作的共享工作空間；傳遞組織範圍公告與緊急直接訊息的訊息介面；以及保留可重複使用發現與工作意圖的共享上下文。

**Q5：多智能體協作迴圈如何運作，為何能實現自我組織？**

A：在每個迴圈迭代中，工作者首先收集關於使用者目標、同儕進度與累積發現的上下文，接著自行認領一個子任務並將其範圍公告為 CLAIM。然後工作者在本地採取行動解決子任務，同時將可能有助於同儕的中間發現更新至共享上下文，完成後驗證結果並合併至共享工作空間。由於工作者自行發現、認領與執行子任務，並以非同步方式推進，整個組織無需等待中央協調器即可持續運作，從而實現真正的自我組織協作。

**Q6：Agensh 為何選擇自我組織而非中央協調器？這帶來哪些設計上的權衡？**

A：中央協調器在工作者數量增加時會成為無法迴避的瓶頸，因為所有規劃、分配與整合都必須經過它，這從根本上限制了系統的可擴展性。Agensh 透過讓工作者自行認領子任務並透過訊息介面處理重疊或衝突，消除了這個單一限制點。雖然這種設計增加了同儕間協調的複雜度，並可能產生衝突認領，但換來的是更高的並行度與隨著智能體數量增加的規模效益。

**Q7：Agensh 使用什麼基準測試進行評估，實驗設定為何？**

A：Agensh 在 ProgramBench 上進行評估，這是智能體軟體工程領域最具挑戰性的基準測試之一。研究者選擇了其中五個最困難的任務，這些任務的參考儲存庫包含數千個檔案，原始碼規模達數百萬位元組。在每個實驗中，智能體組織必須在無網路連線且僅有六小時時間預算的情況下，重現參考軟體的行為。

**Q8：Agensh 的主要量化結果是什麼？**

A：在五個最困難任務上，將組織規模從 1 個智能體擴展到 128 個智能體，平均最終測試通過率從 19.31% 提升至 28.78%，相對改善幅度約為 49%。更大的組織能更早達到與較小組織相當的測試通過率，顯示更多並行智能體能縮短達到特定效能水準所需的延遲。在 pandoc 任務上，將規模從 1 擴展到 1,024 個智能體，最終測試通過率更從 33.89% 提升至 55.06%。

**Q9：工作者軌跡揭示了哪些關於自我組織協作的質化發現？**

A：記錄下來的工作者軌跡顯示，隨著組織規模成長，不同形式的自我組織協作會逐漸湧現並標準化。這些形式從初期的同儕協調與多工作者整合，發展到組織規模下的標準化工作流程與專門化角色。這項發現表明，單純增加智能體數量不僅提升效能，還能促使複雜的組織行為與分工結構自然出現。

**Q10：Agensh 最適合應用在哪些實務場景？**

A：Agensh 特別適合面臨嚴格延遲限制或有限時間預算的複雜任務，例如需要在短時間內完成的大規模軟體工程重現、複雜問題的並行探索，或需要同時從多個角度驗證假設的研究任務。它允許系統以計算資源換取更低的延遲，透過並行執行大幅縮短完成時間。對於傳統單一智能體或中央協調架構難以在時限內完成的任務，Agensh 提供了一個具吸引力的替代方案。

**Q11：若要將 Agensh 部署到實際產品中，需要考慮哪些實務因素？**

A：產品化部署需要穩固的共享工作空間，能夠支援並行寫入、非同步讀取、版本歷史記錄與合併衝突解決，論文中採用 Git 平台來實現這些需求。訊息介面與共享上下文必須在輕量級與資訊完整性之間取得平衡，確保工作者能及時獲取必要資訊而不至於被過多雜訊淹沒。此外，同時運行數百甚至數千個大型語言模型智能體將帶來顯著的計算成本，因此需要仔細評估成本效益與資源調度策略。

**Q12：Agensh 可能對多智能體系統與人工智慧領域產生什麼影響？**

A：Agensh 將智能體數量確立為多智能體組織的一個新擴展維度，這可能改變研究者設計與優化 multi-agent system 的方式。它證明組織智能可以透過去中心化的自我組織機制從大量並行工作者中湧現，而不需要依賴單一強大的中央協調器。這可能促使未來研究更多關注分散式協調機制、同儕通訊協定，以及如何在無中央控制的情況下實現高效分工。

**Q13：Agensh 存在哪些主要限制？**

A：Agensh 高度依賴工作者自行協調的能力，當子任務之間存在高度相互依賴或需要緊密同步時，自我組織可能難以維持一致性。隨著智能體數量增加，訊息介面與共享上下文中的資訊量可能急劇成長，導致個別工作者難以有效篩選相關資訊。此外，雖然論文展示了規模擴展的正面效果，但對於不同任務類型的最佳組織規模、通訊拓撲與角色分工，仍需要更多系統性研究。

**Q14：在哪些情況下 Agensh 可能會失敗或表現不佳？**

A：當任務需要從一開始就具備全局一致性的詳細規劃，且子任務之間的介面極為複雜時，缺乏中央協調器可能導致整體方向分散。如果多個工作者對重疊範圍提出衝突認領，而無法透過直接訊息有效解決，可能會造成重複工作、進度停滯或合併衝突頻繁發生。此外，對於獎勵稀疏或驗證標準不明確的任務，工作者可能難以自行判斷子任務的價值與完成度，進而影響整體效能。

**Q15：Agensh 的研究結果指向哪些未來方向？**

A：未來研究可以探索結合自我組織與輕量級協調的混合架構，在保留可擴展性的同時處理高度相互依賴的子任務。另一個方向是發展更智慧的共享上下文機制，例如自動摘要、相關性排序或動態角色分配，以減少大規模組織中的通訊負擔。此外，研究者可以進一步探討不同任務特性所對應的最佳智能體數量、組織結構與協作協定，從而讓 Agensh 類型的系統在更廣泛的應用中發揮最大效益。

## 實務應用指南

### 適用場景

1. **大規模遺留程式碼重構與現代化**  
   當企業需要同時重構數千個檔案、更新依賴套件或遷移語言版本時，Agensh 可讓數百個工作者並行分析不同模組、提出子任務、驗證單元測試並合併結果，顯著縮短原本需要數週的作業時間。

2. **複雜軟體行為復現與自動化工程**  
   類似 ProgramBench 的情境：在無法存取外部網路、僅有參考軟體行為與測試案例的條件下，讓智能體組織在 6 小時內重建大型專案（如 pandoc 等級的專案）。適用於內部工具重建、第三方元件替代方案開發或競品功能快速復刻。

3. **高頻事件回應與維運協作**  
   在需要同時診斷多個告警、查閱日誌、比對版本差異並提出修補的維運場景中，Agensh 的非同步自我組織迴圈可讓多個工作者並行調查不同可疑根因，並透過共享上下文避免重複排查，適合 SRE 團隊處理大規模事故。

4. **大型技術文件或法規報告共筆生成**  
   當一份報告需要整合多個章節、引用大量資料並維持格式與術語一致時，可將每個工作者指派為不同章節的貢獻者，利用共享工作空間與訊息介面協調重疊內容，最後合併成統一稿件。

5. **科學實驗設計與模擬參數探索**  
   在需要同時測試多組假設、調整參數並記錄可重複使用發現的研究流程中，Agensh 的自我組織機制可讓智能體並行探索不同實驗分支，並將有效發現寫入共享上下文供同儕接續使用。

### 實作前置條件

| 類別 | 具體需求 |
|---|---|
| **資料** | 明確的使用者目標與可驗證的驗收準則；可存取的參考儲存庫、測試案例或行為規格；共享上下文所需的結構化資料格式（如 CLAIM、發現、驗證證據）。 |
| **運算** | 可並行執行數十至上千個工作者的運算叢集或容器化環境；足夠的 LLM API 配額（建議使用高階推理模型如 GPT-5.6-sol (high)）；Git 或支援版本歷史與合併衝突處理的共享工作空間。 |
| **技能** | 熟悉提示工程與智能體迴圈設計；具備軟體工程實務（Git 分支策略、合併衝突解決、測試驅動開發）；能設計輕量級訊息介面與共享上下文儲存；具備分散式系統除錯與可觀測性經驗。 |

### 實作步驟建議

1. **定義目標與驗收準則**  
   將使用者目標寫成可驗證的陳述，並準備自動化測試或評分腳本作為最終驗證依據。

2. **建置智能體組織基礎設施**  
   - **共享工作空間**：使用 Git 平台管理主要分支與各工作者的獨立分支，確保並行寫入與合併衝突可視化。  
   - **訊息介面**：建立組織範圍公告與緊急直接訊息的傳遞機制，例如輕量級訊息佇列或結構化日誌。  
   - **共享上下文**：設計可持久化的資料結構，記錄已認領子任務、可重複使用的發現、失敗嘗試與工作意圖。

3. **實作多智能體協作迴圈**  
   為每個工作者實作五個步驟：收集上下文、認領子任務、採取行動、驗證結果、合併進度。確保每個步驟都能非同步執行，並在合併衝突時自動重新收集上下文並重新嘗試。

4. **提供工具與環境**  
   讓工作者能呼叫檔案讀寫、程式碼執行、測試執行、靜態分析等工具；建議在隔離容器中執行以避免副作用。

5. **小規模試點**  
   先以 2–8 個工作者運行，觀察是否出現重複工作、衝突無法解決或上下文遺失等問題，調整提示與基礎設施後再擴大。

6. **逐步擴展並監控軌跡**  
   從 16、64、128 逐步增加到 1,024 個工作者；記錄工作者軌跡以觀察自我組織協作形式（如同儕協調、角色分工、標準化流程）是否自然湧現。

7. **引入角色專業化與標準化流程**  
   當組織規模變大，可根據軌跡分析讓部分工作者專注於測試、文件、衝突解決或程式碼審查，進一步提升效率。

8. **持續迭代與成本控管**  
   定期檢視 LLM 呼叫次數、合併成功率與測試通過率，設定時間預算與成本上限，避免無限制擴展導致邊際效益遞減。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **合併衝突頻繁** | 大量工作者同時修改相同檔案，導致共享工作空間衝突不斷。 | 採用細粒度子任務切分、模組化架構，並在合併前強制重新同步最新進度。 |
| **重複工作** | 多個工作者同時認領相似子任務，浪費運算與模型呼叫成本。 | 強化共享上下文中的 CLAIM 機制，並設計衝突偵測與直接訊息協調流程。 |
| **上下文視窗超限** | 隨著組織累積越來越多發現與訊息，單一工作者可能無法讀取全部上下文。 | 實作摘要與檢索機制，只將最相關的共享上下文與同儕進度餵入工作者。 |
| **成本快速膨脹** | 1,024 個工作者同時呼叫高階 LLM 會產生可觀費用。 | 設定時間預算、呼叫頻率限制與自動縮減規模的閾值。 |
| **驗證不穩定** | 自動測試可能因環境差異或 flaky test 而誤判結果。 | 使用確定性測試、多次驗證與隔離執行環境。 |
| **協調失敗** | 無中央協調器時，極少數情境可能無法收斂。 | 保留人類介入或監督者機制，在長時間無進展時重新設定目標或重啟組織。 |
| **安全與權限** | 共享工作空間與工具呼叫可能暴露敏感程式碼或允許危險操作。 | 實作最小權限原則、沙箱環境與操作審計日誌。 |

### 與其他技術的整合建議

- **CI/CD 管線**：將 Agensh 的驗證步驟與現有持續整合系統對接，讓每次合併都觸發自動化測試與品質閘道。
- **議題追蹤系統**：把使用者目標對應到 Jira、GitHub Issues 或 Linear 的史詩與任務，並將工作者產生的子任務與進度更新回寫至議題系統。
- **現有協調器**：雖然 Agensh 強調無中央協調器，但在邊界任務（如初始目標分解、最終審查）仍可與傳統 orchestrator-worker 架構混用，讓中央協調器負責高階規劃，Agensh 負責大規模並行執行。
- **知識庫與向量檢索**：將共享上下文中的可重複使用發現定期同步至企業知識庫或向量資料庫，供未來組織或人類團隊查詢。
- **可觀測性平台**：將訊息介面與工作者軌跡匯出至 Prometheus、Grafana 或 LangSmith，即時監控組織健康度、衝突率與測試通過率。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦在「多智能體協作迴圈」與「智能體組織基礎設施」這兩個核心概念，理解 Agensh 如何讓多個工作者像一個團隊般自行分工；不必一開始就深入 1,024 個工作者的擴展細節，可先從 2–4 個智能體的小實驗開始體會自我組織的運作方式。

**AI 工程師**：請重點閱讀多智能體協作迴圈的五個步驟與共享上下文設計，特別注意 CLAIM、合併衝突解決與驗證機制的實作細節；這些是將論文轉化為可上線系統的關鍵，並建議參考 ProgramBench 的實驗設定來設計自己的評估環境。

**研究人員**：建議深入分析工作者軌跡與擴展維度之間的關係，探討自我組織協作從湧現到標準化的過程；可進一步研究在不同任務難度、模型規模與時間預算下，智能體數量的邊際效益與最佳組織規模。

**產品經理**：請將重點放在適用場景與商業價值上，理解 Agensh 最適合解決「複雜、可並行、有明確驗收準則且受嚴格時間預算限制」的任務；在規劃產品路線圖時，建議從單一高價值場景試點，再評估擴展至更多業務單位的可行性與成本。
