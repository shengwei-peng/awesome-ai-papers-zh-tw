AgentBaton 的核心方法論建立在「模型交接」(model handoff) 框架之上，系統性地探討異質模型在長時間跨度代理任務 (long-horizon agentic tasks) 中的協作機制。整體方法可拆解為三個關鍵設計維度：交接方向 (handoff direction)、上下文傳遞 (context transfer) 策略，以及交接時機的偵測機制。

**交接方向的設計選擇**

論文首先區分兩種交接方向：高效能至高效率模型交接 (capable-to-efficient handoffs) 與高效率至高效能模型交接 (efficient-to-capable handoffs)。前者由高效能模型 (capable models) 先執行任務的前段，再將控制權移交給高效率模型 (efficient models)；後者則相反。這種雙向設計的動機在於直覺上兩種方向皆合理：高效能模型可先產出初始計畫 (initial plan) 或關鍵中間結果 (intermediate results)，由高效率模型接手完成後續工作；反之，高效率模型可先進行資訊蒐集 (information gathering) 等初步步驟 (preliminary steps)，再交由高效能模型處理高難度步驟 (demanding steps)。

**上下文傳遞的兩種機制**

針對互動歷史 (interaction history) 的傳遞，論文提出兩種互補方法：

1. **上下文內傳遞 (in-context transfer)**：直接將交接前的完整對話歷史納入接收模型 (receiving model) 的上下文中，保留訊息角色、助手回應、工具呼叫及對應的工具輸出。當來源模型使用不同的回應格式時，會將可見文字與工具互動轉換為接收模型的聊天格式；若來源模型未暴露其思維鏈 (chain-of-thought)，則省略 `reasoning_content` 欄位而非重建不可得的推理內容。

2. **日誌檔案傳遞 (log file transfer)**：將歷史寫入任務環境中的 `.jsonl` 檔案，接收模型可使用標準 Unix 指令如 `cat`、`grep`、`sed` 進行檢查。每筆 JSON 記錄包含回合索引、原始模型回應及動作列表，記錄原始指令、工具輸出、回傳碼、標準輸出與標準錯誤。接收模型以全新代理會話啟動，僅持有原始任務指令、日誌檔案路徑及描述欄位結構的文字綱要。

兩種機制下，接收模型皆繼承來源模型的工作區 (workspace) 狀態，包含所有檔案修改與產出物 (artifacts)。

**一次性交接策略的理論基礎**

論文採用一次性交接 (one-time handoff) 設計，而非每回合路由 (per-turn routing)。此設計基於一個關鍵觀察：高效能模型建立的進度可使高效率模型完成其獨立執行時難以勝任的任務，形成單向依賴關係。頻繁切換模型會累積軌跡誤差 (trajectory errors)，迫使高效能模型反覆耗費精力進行修正，因此每回合路由在實務上並不可行。

**AgentBaton 偵測器架構**

基於個案研究中觀察到的週期性模式 (recurring patterns)——高效能模型通常已產出實質實作或產物並取得任務相關回饋，後續僅剩局部修復、驗證或收尾工作——論文提出 AgentBaton，一個輕量級偵測器 (lightweight detector)，用於從執行歷史中學習識別合適的交接點。其運作流程為：高效能模型啟動任務，AgentBaton 在每個回合後評估進度；一旦預測出合適的交接點，高效率模型即接手並執行至任務終止。

**方法論的關鍵洞察**

論文的核心洞察在於交接方向的不對稱性：高效能至高效率模型交接在合適的任務進度階段可大幅保留甚至提升準確率並顯著降低成本，而高效率至高效能模型交接則普遍表現不佳，有時甚至成本更高。這項發現挑戰了傳統查詢層級路由 (query-level routing) 與串接式路由 (cascading) 的直覺——後者通常假設「先嘗試便宜模型，失敗時升級至昂貴模型」。在長時間跨度代理任務中，工作區狀態與任務軌跡 (task trajectory) 的累積特性使得初始模型的選擇對後續執行具有深遠影響。

**交接方向的實驗驗證**

實驗結果明確支持以下論點：

1. **高效能至高效率模型交接的優勢**：在合適的任務進度階段執行此方向交接，可大幅保留甚至超越高效能模型獨立執行的準確率，同時顯著降低成本。個案研究顯示，高效能模型通常已完成實質實作並取得任務相關回饋，後續工作偏向局部修復、驗證或收尾，這正是高效率模型能勝任的範疇。

2. **高效率至高效能模型交接的劣勢**：此方向普遍表現不如僅使用高效能模型執行，有時甚至在更高成本下仍無法達到對應準確率。雖然日誌檔案傳遞在此方向上略優於上下文內傳遞，但整體效益仍有限。

3. **上下文傳遞方法的模型依賴性**：對於高效能至高效率模型交接，偏好的上下文傳遞方法因模型而異。這暗示不同模型對歷史資訊的處理能力存在差異，部分模型能有效利用完整對話歷史，部分則更適合透過結構化日誌進行選擇性檢查。

**推理強度設定的影響**

在不同推理強度設定下的實驗顯示，AgentBaton 的效益具有跨設定的泛化能力。這點對於實務部署至關重要，因為使用者可根據成本與品質需求調整推理強度，而 AgentBaton 仍能維持其成本效益優勢。

#### 與現有研究的比較

**與查詢層級路由的比較**

傳統的查詢層級路由 (query-level routing) 與串接式路由 (cascading) 方法（如 RouteLLM、FrugalGPT 等）將每個查詢獨立分配給模型，僅根據初始查詢的特徵決定模型選擇。AgentBaton 的關鍵差異在於其考慮任務軌跡的動態特性：代理任務中，動作會改變工作區並產生動態回饋，實際所需能力隨回合演進而非預先確定。因此，僅基於初始查詢的路由在長時間跨度任務中顯著不足，而 AgentBaton 透過監控執行進度並在合適時機交接，更貼合代理任務的本質。

**與模型級聯的比較**

模型級聯 (model cascading) 通常採用「先嘗試便宜模型，信心不足時升級」的策略。AgentBaton 的發現與此形成鮮明對比：在長時間跨度代理任務中，高效率至高效率模型交接（即「先便宜後昂貴」）普遍表現不佳，反而是高效能至高效率模型交接（即「先昂貴後便宜」）更為有效。這項反直覺的發現凸顯了代理任務與單輪問答任務在協作策略設計上的根本差異。

**與多代理系統的比較**

現有多代理系統 (multi-agent systems) 通常涉及多個專門化代理的並行或序列協作，每個代理負責特定子任務。AgentBaton 則專注於單一任務軌跡內的模型切換，僅涉及兩個模型的交接，且交接點由學習而來而非預先定義。這種設計更為輕量，部署複雜度低，且保留了任務的單一控制流。

**優勢總結**

相較於現有方法，AgentBaton 的主要優勢包括：

1. **任務感知**：基於實際執行進度而非靜態查詢特徵進行決策
2. **成本效益**：平均 65.9% 的 API 成本降低，顯著優於多數路由策略
3. **準確率增益**：在部分情境下超越高效能模型獨立執行，最高達 8.8 百分點
4. **輕量級**：偵測器本身設計為輕量，推理開銷低
5. **泛化性**：跨 11 個模型配對與兩個基準測試皆有效

**現有限制**

儘管成果顯著，論文仍存在若干限制：

1. **一次性交接的假設**：方法僅考慮一次性交接，未探索多次交接或動態切換的可能性。雖然論文論證了頻繁切換的風險，但對於極長任務或高度異質的子任務，多次交接可能仍有價值。

3. **模型配對的覆蓋範圍**：雖然測試了 11 個模型配對，但對於特定領域（如純對話任務、創意寫作）的代理任務，方法的適用性尚待驗證。

## 論文問答

**Q1：這篇論文主要解決什麼問題？**
A：這篇論文主要解決長時間跨度代理任務（long-horizon agentic tasks）中，使用高效能模型（capable models）所帶來的高昂 API 成本問題。雖然高效能模型透過雲端服務提供商能提供可靠且最先進的表現，但反覆呼叫會產生可觀的推論成本。論文中提出的 AgentBaton 方法試圖在保留任務準確率的前提下，透過模型協作大幅降低 API 成本。

**Q2：為什麼現有的查詢層級路由（query-level routing）與串接式路由（cascading）方法在代理任務中效果不佳？**
A：現有方法主要根據任務的初始查詢來決定指派給哪個模型，但這種做法在長時間跨度代理任務中有所不足。在這類環境中，代理的動作會改變工作區並產生動態回饋，因此實際所需的能力會隨著回合演進，而非在任務開始時就能確定。這意味著僅憑初始查詢做路由決策，無法應對任務過程中不斷變化的能力需求，因此需要整個任務軌跡中的協作。

**Q3：為什麼這個問題在實務上很重要？**
A：這個問題在實務上很重要，因為它直接影響語言模型代理的大規模部署可行性。透過 AgentBaton，API 成本平均可降低 65.9%，同時保留任務準確率，甚至在某些情況下比僅使用高效能模型執行還高出 8.8 個百分點。這對於需要在成本與效能間取得平衡的產品部署而言，是一個關鍵的進展。

**Q4：AgentBaton 的核心方法是什麼？**
A：AgentBaton 是一個輕量級偵測器（lightweight detector），經訓練後能從執行歷史中識別出合適的交接點。高效能模型先開始執行任務，AgentBaton 在每個回合後評估進度；一旦預測到合適的交接點，便由高效率模型接手並繼續執行直到任務結束。這種設計避免了頻繁切換所帶來的軌跡錯誤累積風險。

**Q5：這篇論文最重要的發現或創新是什麼？**
A：最重要的發現是交接方向存在不對稱性：高效能至高效率模型交接（capable-to-efficient handoffs）在合適的任務進度階段能大幅降低成本並保留準確率，但高效率至高效能模型交接（efficient-to-capable handoffs）通常表現不如僅使用高效能模型執行。這種單向依賴關係暗示著每回合路由可能不切實際，因為頻繁切換會累積軌跡錯誤，需要高效能模型反覆耗費精力來修正。

**Q6：論文中探討了哪些關鍵的設計選擇？**
A：論文中系統性地探討了兩個關鍵設計選擇：交接方向（handoff direction）與上下文傳遞（context transfer）方式。交接方向分為高效能至高效率與高效率至高效能兩種；上下文傳遞則分為上下文內傳遞（in-context transfer，直接將對話歷史放入接收模型的 context 中）與日誌檔案傳遞（logfile transfer，將歷史寫成 .jsonl 檔案讓接收模型用 cat、grep、sed 等指令檢視）。研究發現，對於高效能至高效率交接，不同模型偏好的上下文傳遞方式並不一致。

**Q7：論文中使用了哪些基準測試（benchmarks）？**
A：論文中使用了兩個具有代表性的代理任務基準測試：Terminal Bench 2.1 與 DeepSWE v1.1。這兩個基準涵蓋了終端機操作與軟體工程等長時間跨度的代理任務情境，並在 11 組模型配對（model pairs）上進行評估，以驗證方法的泛用性。

**Q8：AgentBaton 的主要實驗結果為何？**
A：AgentBaton 在 11 組模型配對與兩個基準測試上，平均降低了 65.9% 的 API 成本，同時在很大程度上保留了任務準確率。值得注意的是，在某些情況下其準確率比僅使用高效能模型執行還高出 8.8 個百分點。此外，實驗結果顯示 AgentBaton 擴展了經驗上的準確率與成本帕累托前緣（accuracy-cost Pareto frontier），超越了所有評估過的單一模型配置。

**Q9：論文中進行了哪些消融實驗（ablation studies）？**
A：論文中針對每種交接方向，比較了兩種上下文傳遞方法：上下文內傳遞與日誌檔案傳遞。實驗結果顯示，對於高效率至高效能交接，日誌檔案傳遞優於上下文內傳遞；但對於高效能至高效率交接，在合適的任務進度階段，兩種方法都能在很大程度上保留高效能模型的準確率。這些消融實驗幫助釐清了不同設計選擇對準確率與成本權衡的影響。

**Q10：AgentBaton 適用於哪些實際應用情境？**
A：AgentBaton 適用於任何需要長時間跨度的代理任務，特別是那些成本考量重要的場景，例如軟體工程任務（DeepSWE）、終端機操作任務（Terminal Bench），以及任何高效能模型能建立實質進度、而高效率模型能接手完成後續局部修復、驗證或最終化工作的任務。這種模式在許多實際部署中相當常見。

**Q11：在產品化部署 AgentBaton 時需要考慮哪些因素？**
A：產品化部署時需要考慮幾個關鍵因素：首先是模型配對的選擇，不同的高效能與高效率模型組合可能產生不同的結果；其次是交接時機的判斷，這需要 AgentBaton 偵測器能準確識別合適的交接點；最後是上下文傳遞方式的選擇，因為不同模型偏好的傳遞方式並不一致，需要根據實際使用的模型配對進行調整。

**Q12：這項研究對學術界與產業界的影響是什麼？**
A：這項研究對學術界與產業界都有重要影響。在學術上，它擴展了經驗上的準確率與成本帕累托前緣，挑戰了傳統認為高效能模型必須全程執行的假設，並為代理任務中的模型協作提供了系統性的設計指引。在產業界，它提供了一個實用的方法來大幅降低 API 成本（平均 65.9%），同時保留甚至提升任務準確率，對於大規模部署語言代理的組織而言具有直接的經濟效益。

**Q13：論文中承認了哪些限制？**
A：論文中承認的一個主要限制是，為了簡化分析與控制變因，他們僅研究了一次性交接（one-time handoff），即接收模型接手後不再切換回原始模型。這種設計可能限制了方法在需要多次切換的任務中的適用性。此外，論文的實驗主要聚焦於兩種基準測試與 11 組模型配對，對於其他類型的代理任務與模型組合的泛用性仍需進一步驗證。

**Q14：在哪些情況下 AgentBaton 可能會失敗？**
A：AgentBaton 在高效率至高效能交接的方向上表現不佳，這些交接通常無法超越僅使用高效能模型執行的表現，有時甚至成本更高。這種失敗案例說明了交接方向的選擇至關重要，並非所有協作模式都能帶來效益。此外，如果高效能模型未能建立實質的進度或留下可供高效率模型接手的成果，AgentBaton 的效益也會大打折扣。

**Q15：未來的研究方向有哪些？**
A：未來的研究方向可能包括：探索多次交接（multi-handoff）策略以處理更複雜的任務；研究更精細的上下文傳遞方法，例如摘要式傳遞或選擇性傳遞；將方法應用於更廣泛的代理任務與模型配對；以及深入分析交接時機的理論基礎，例如探討任務進度與交接效益之間的數學關係。此外，也可以研究如何將 AgentBaton 與其他成本優化技術（如模型量化、推理強度調整）結合，以進一步提升整體效率。

接收模型繼承工作區狀態（檔案修改、產出物），從交接點繼續執行直到任務終止。

**步驟五：線上部署與監控**
將 AgentBaton 整合進 agent 執行迴圈：高效能模型執行每輪後，由偵測器評估是否為合適交接點；一旦預測為正，立即切換至高效率模型。持續監控成本節省比例與任務準確率，並定期以新資料重新訓練偵測器以適應任務演進。

**步驟六：跨推理強度設定調校**
論文顯示 AgentBaton 在不同 reasoning-effort 設定下都能延伸帕累托前緣。建議為不同任務類型設定不同的偵測閾值，平衡成本與準確率。

### 潛在風險與注意事項

**風險一：交接時機判斷錯誤導致任務失敗**
AgentBaton 可能過早交接，使高效率模型在尚未取得足夠進度時接手，導致後續無法完成任務。
*緩解措施*：設定保守的偵測閾值（提高 precision），並在交接後保留 fallback 機制——若高效率模型在 N 輪內未取得進展，自動切回高效能模型。

**風險二：上下文傳遞方式選擇不當**
不同模型對 in-context 與 logfile transfer 的適應性不同，錯誤選擇可能造成接收模型誤解歷史或產生偏見。
*緩解措施*：針對每個模型配對進行小規模 A/B 測試，根據結果選擇較佳的傳遞方式；可在 prompt 中明確指示接收模型如何解讀歷史。

**風險三：高效能模型的推理內容無法取得**
部分雲端模型不暴露 chain-of-thought，導致 in-context transfer 時缺少 `reasoning_content` 欄位，可能影響接收模型理解。
*緩解措施*：優先採用 logfile transfer，或在 prompt 中明確說明「僅有可見文字與工具呼叫，無內部推理」。

**風險四：工作區狀態不一致**
交接時若工作區存在未儲存的中間狀態或環境變數，接收模型可能無法正確接續。
*緩解措施*：在交接前強制執行狀態檢查點，確保所有檔案修改已持久化、必要的環境資訊已記錄於日誌。

**風險五：成本節省被偵測器推論成本抵消**
若偵測器本身過於複雜或被呼叫過於頻繁，可能侵蝕成本節省效益。
*緩解措施*：使用極輕量的分類器（如小型 MLP 或蒸餾後的小模型），並限制偵測頻率（例如每 2–3 輪評估一次而非每輪）。

**風險六：任務類型分布漂移**
訓練資料的任務分布與實際部署場景差異過大時，偵測器泛化能力下降。
*緩解措施*：建立持續學習機制，定期以新任務軌跡更新偵測器；監控交接後的任務成功率作為模型漂移指標。

### 與其他技術的整合建議

**與查詢層級路由（Query-level Routing）整合**：AgentBaton 處理任務內的軌跡層級交接，可與傳統的查詢層級路由器串接——先用路由器決定初始模型（高效能或高效率），再由 AgentBaton 決定是否在任務中途交接，形成兩階段決策。

**與串接式路由（Cascading）整合**：可將 AgentBaton 視為串接式路由的時序擴展，在多輪代理任務中動態決定「升級」或「降級」時機，與既有 cascading 框架（如 FrugalGPT、RouteLLM）的信心度評分機制互補。

**與成本監控系統整合**：將交接事件、成本節省比例、任務成功率等指標匯入現有的 FinOps 儀表板，設定自動告警閾值（例如成本節省低於 30% 時觸發偵測器重訓練）。

**與 Agent 框架整合**：在 LangChain、AutoGen、CrewAI 等框架中以 callback 或 hook 形式插入 AgentBaton 評估點，無需大幅修改既有 agent 程式碼。

**與模型蒸餾與量化技術整合**：高效率模型端的選擇可結合模型蒸餾（如將高效能模型能力蒸餾至小模型）與量化技術（INT4/INT8），進一步降低接收模型的推論成本。

**與評估基準整合**：將 Terminal Bench 2.1、DeepSWE v1.1 等基準納入 CI/CD 流程，每次偵測器更新後自動跑回歸測試，確保不退步。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題動機，理解「為什麼不能只用一個模型」以及「為什麼交接方向很重要」；接著重點理解圖 2 的一次性交接與兩種上下文傳遞方式的概念圖，不需要深入數學細節；最後看摘要中的關鍵數字（65.9% 成本降低、最高 8.8 百分點準確率提升）即可掌握整體價值主張。

**給 AI 工程師**：重點關注第 2 節的實驗設計，特別是 in-context transfer 與 logfile transfer 的實作細節、`.jsonl` 日誌格式設計、以及如何將偵測器整合進現有 agent 執行迴圈；可參考「實作步驟建議」中的管線設計，將論文概念轉化為可部署的系統；建議實際重現論文中的 11 個模型配對實驗以驗證偵測器在不同模型組合下的泛化性。

**給研究者**：核心研究問題是「為什麼 capable-to-efficient 交接能保留甚至提升準確率，而反向不行」，這涉及代理任務中能力需求的時序分布；可進一步探索的方向包括：將一次性交接擴展至多次交接、結合強化學習動態學習交接策略、分析交接點的特徵可解釋性、以及將方法推廣至多代理協作場景；論文中的 Pareto 前緣分析方法是值得參考的實驗設計範式。

**給產品經理**：核心訊息是 AgentBaton 提供了一個「低成本、高效益」的模型協作方案，能在保留任務品質的前提下降低 65.9% 的 API 成本；產品定位上可思考如何將此能力包裝為「智慧模型路由服務」或「成本最佳化代理平台」；商業模式上可考慮按成本節省比例收費，或作為企業 LLM 代理方案的附加價值；需注意的產品風險是偵測器失效時的 fallback 設計，以及不同任務類型下的成本效益差異。
