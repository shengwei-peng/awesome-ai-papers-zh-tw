# 還有哪些需要修訂？探索對話生成產物中修訂傳播的具成本效益測試時運算

**原文標題：** What Else Needs Fixing? Exploring Cost-Effective Test-Time Compute for Revision Propagation in Artifacts Generated Through Conversation

## ⚡ TL;DR

LLM在對話生成的產物中，用戶局部修訂請求時，模型需識別隱含依賴並傳播修訂以保持一致性。
本文提出RevPropBench基準測試，評估九種修訂方法，探討成本效益高的測試時運算策略。
實驗顯示基線準確率68.3–93%，以LLM或中心點選三平行樣本最省成本，提升2.2–9.7%。

## 摘要翻譯

Large Language Models (LLMs)（大型語言模型）經常透過 conversation（對話）中 generation（生成）與 revision（修訂）的 iterative cycle（迭代循環），協助使用者產出 artifact（產物）。此處的挑戰在於，當使用者在修訂時僅指定 local change（局部變更），LLM 必須識別相關的 dependency（依賴關係），並將 revision propagation（修訂傳播）至產物中所有受影響的部分。本研究探討 LLM 在對話生成產物上進行修訂傳播的能力，其中產物上下文及其依賴關係可能內嵌於 conversation history（對話歷史）中。為貼近實務應用，我們也針對此新情境探索具成本效益的 test-time compute（測試時運算）。具體而言，我們針對此情境提出一個新的 benchmark（基準測試），並使用 gpt-oss-20b/120b、gpt-5.4-mini 與 qwen3.5-9b/27b/122b 在該基準測試上評估九種修訂方法，包含 sequential reflection（序列式反思）與 parallel sampling（平行取樣）的變體。結果顯示，基線方法達到 68.3% 至 93% 的 accuracy（準確率），而最具成本效益的方法是從三個 parallel samples（平行樣本）中，使用 LLM-based selection（基於 LLM 的選擇）或 medoid selection（中心點選擇）進行挑選，可將準確率提升 2.2 至 9.7 個百分點。我們的程式碼與資料集可於 https://github.com/ntt-dkiku/llm-revision-propagation 取得。

### 核心貢獻（3～5點）
- 提出一個針對對話生成產物中修訂傳播問題的新基準測試，填補現有研究在對話歷史內嵌產物上下文情境下的評估缺口。
- 系統性評估九種修訂方法，涵蓋序列式反思與平行取樣變體，並於多種開源大型語言模型上進行實證比較。
- 發現從三個平行樣本中，使用基於 LLM 的選擇或中心點選擇進行挑選，是最具成本效益的方法，可將準確率提升 2.2 至 9.7 個百分點。
- 公開釋出程式碼與資料集，供後續研究複現與延伸。

### 適合對象
對大型語言模型、對話式生成系統、測試時運算，以及程式庫層級程式編寫有興趣的研究人員與工程師；特別適合關注如何以具成本效益的方式，處理對話中產物局部修訂後之相依部分一致性問題的讀者。

## 深度分析

#### 方法論解析

本研究的核心問題是：當使用者僅提出一個**局部修訂請求（local revision request）**時，**大型語言模型（Large Language Model，LLM）**能否在**對話歷史（conversation history）**中辨識出隱含的**依賴關係（dependency）**，並將必要的修改**傳播（propagate）**到**產物（artifact）**的所有相關部分，以維持**一致性（consistency）**。為此，作者提出了 **RevPropBench**，並系統性地比較了九種修訂方法在成本與效能上的表現。

##### 任務定義

RevPropBench 將任務分為兩個階段：

1. **生成階段（generation phase）**：LLM 透過多輪**對話（conversation）**，逐步建立一個 JSON 格式的產物。
2. **修訂階段（revision phase）**：使用者給出一個僅涉及局部變更的修訂請求，受評估的 LLM 必須輸出符合 **JSON Patch（RFC 6902）** 規範的修補序列。

每個 Patch 操作由 `(op, path, value)` 組成，其中 `op` 可為 `replace`、`add` 或 `remove`。評估時，系統會比對模型生成的 Patch 與**黃金修補檔（gold patch）**在路徑與數值上是否完全一致；對於自由格式的數值，則使用預先定義的關鍵字**匹配器（matcher）**來判斷是否語義等價。這種設計讓任務聚焦在「結構化且可驗證」的修訂傳播，而非開放式生成。

##### 基準測試建構流程

RevPropBench 的資料並非直接取自真實對話，而是採用**合成資料取樣（synthetic data sampling）**加**人工標註（annotation）**的混合方式：

- 首先使用強大的 LLM（如 GPT-5.5）產生**情境（scenario）**、**對話流程（conversation flow）**、**修訂模式（revision pattern）**與**傳播模式（propagation pattern）**。
- 接著使用 Claude-Opus-4.8 產生初步的黃金修補檔。
- 最後由人工標註者透過圖形化標註工具檢視與修正，必要時可諮詢 LLM。

最終資料集包含 150 個樣本，涵蓋 9 個**領域（domain）**、50 種情境，並依產物大小分為 10、50、100 個 JSON 元素三種等級。領域包括旅遊行程（travel_itinerary）、購物車（shopping_cart）、組織存取計畫（org_access_plan）、製造物料清單（manufacturing_bom）、專案排程（project_schedule）、發票（invoice）、軟體設定（software_config）、資料管線（data_pipeline）與課程規劃（course_plan）。這些領域設計了不同類型的傳播模式，例如算術重算（arithmetic recompute）、時間平移（temporal shift）、參照更新（reference）與替換（substitution）。

##### 修訂方法設計

本研究評估了九種修訂方法，可大致分為三大類：

1. **單輪直接生成（single-pass baseline）**：模型僅根據對話歷史與修訂請求直接輸出 Patch。
2. **序列式反思（sequential reflection）**：模型先生成初步 Patch，再進行自我檢查或批判，最後根據反思結果重新修訂。這類方法通常會增加額外的推論輪次。
3. **平行取樣（parallel sampling）**：同時生成多個候選 Patch，再透過選擇策略挑選最終答案。選擇策略包括：
   - **基於 LLM 的選擇（LLM-based selection）**：使用另一個 LLM 作為評判者，從多個樣本中選出最佳 Patch。
   - **中心點選擇（medoid selection）**：根據樣本間的相似度，選出最具代表性的中心樣本，無需額外 LLM 評判。
   - 其他可能變體，如多數決（majority voting）或最佳樣本 oracle 等。

整體方法論的亮點在於，它將「修訂傳播」從傳統的程式碼或文件編輯場景，轉移到「對話生成產物」這個更動態、更貼近實際應用的設定，並且同時考慮了**測試時運算（test-time compute）**的成本效益。

#### 實驗數據解讀

##### 基準表現

實驗結果顯示，單輪直接生成的**準確率（accuracy）**已達 68.3%–93%，顯示現代 LLM 具備一定的隱含依賴推理能力。然而，即使是較強的模型，也無法達到 100%，這說明「僅從對話歷史中推導出所有需要修改的元素」仍然具有挑戰性。常見的失敗模式如圖 1 所示：當使用者要求「移除目的地 B」時，模型雖然更新了行程與時段，卻遺漏了預算的調整，這正是**隱含依賴關係（implicit dependency）**未被正確捕捉的典型案例。

##### 測試時運算的效果

在九種方法中，最具成本效益的是「從三個平行樣本中選擇一個」，無論使用 **LLM-based selection** 或 **medoid selection**，都能將準確率提升 2.2%–9.7%。這個結果有幾層意義：

- **平行取樣優於序列式反思**：在相同或更低的成本下，平行生成多個候選答案並加以選擇，通常比讓模型進行多輪自我反思更有效。這可能因為反思過程容易陷入「確認偏誤」，而平行樣本能提供多樣化的解題路徑。
- **Medoid selection 的性價比高**：與 LLM-based selection 相比，medoid selection 無需額外呼叫評判模型，卻能達到相近的效能提升，對於實際部署非常有吸引力。
- **樣本數量存在甜蜜點**：實驗聚焦在「三個樣本」，暗示過度增加樣本數可能會進入邊際效益遞減區間，而成本卻線性上升。

##### 產物大小與領域的影響

從圖 3 的統計可觀察到，隨著**產物大小（artifact size）**從 10 個元素增加到 100 個元素，需要傳播的修訂元素數量也隨之增加。這對模型的**長上下文（long-context）**理解能力與多步推理能力提出更高要求。可以合理推測，在 100 個元素的設定下，模型的準確率會明顯低於 10 個元素的設定，因為模型需要在更長的對話與更大的 JSON 結構中追蹤依賴關係。

不同領域的難度也有所差異。例如，涉及算術重算或時間平移的領域，可能需要模型進行數值推理；而涉及參照替換的領域，則考驗模型對結構對應關係的理解。這些差異意味著，未來在設計專用模型或提示策略時，應針對不同傳播模式設計不同的處理機制。

##### 評估指標的嚴格性

本研究採用「Patch 完全匹配」作為主要指標，這是一個非常嚴格的標準。即使模型正確識別了所有需要修改的元素，只要數值表達方式與黃金修補檔不完全一致（且未被關鍵字匹配器涵蓋），就會被視為錯誤。這種嚴格性有助於客觀比較，但也可能低估模型的語義正確性。例如，預算寫成 `$180 × 3` 與 `$540` 在語義上等價，但在嚴格匹配下可能被記為失敗。

#### 與現有研究的比較

本研究與現有文獻的主要差異在於「依賴關係的性質」：

- **程式庫層級程式編寫（repository-level coding）**：相關研究（如 Jimenez et al., 2024；Bairi et al., 2024）通常仰賴**呼叫圖（call graph）**、**匯入（import）**、**變數引用（variable reference）**等可靜態分析的結構。這些依賴關係相對明確，可以透過程式分析工具輔助定位。相較之下，對話生成產物中的依賴關係是隱含且動態的，無法單純用靜態分析解決。
- **知識編輯（knowledge editing）**：此領域（Cohen et al., 2024；Dong et al., 2025）假設事實之間的關係已記錄在**知識圖譜（knowledge graph）**中，編輯後的傳播路徑相對固定。本研究則沒有預先定義的圖結構，依賴關係必須從對話脈絡中推導。
- **文件編輯（document editing）**：既有研究（Wang et al., 2026；Kruthof, 2026）處理的依賴多為章節、圖表、引用等明確參照。本研究則進一步挑戰「對話中自然語言所隱含的依賴」。

總體而言，本研究填補了「對話生成產物」這一特定場景的空白，並首次系統性地探討了成本效益高的測試時運算策略。

##### 主要貢獻

1. 提出首個針對對話生成 JSON 產物的修訂傳播**基準測試（benchmark）**。
2. 全面評估九種修訂方法與六個 LLM，提供實用的方法選擇建議。
3. 開放資料、程式碼與標註工具，促進後續研究。

##### 限制

儘管如此，本研究仍存在一些限制：

- **資料形式單一**：僅聚焦於 JSON 產物，尚未涵蓋文件、程式碼、多模態內容等更廣泛的產物類型。
- **合成資料的真實性**：雖然使用強大 LLM 生成並經人工標註，但對話仍為合成，可能無法完全反映真實使用者的模糊、不完整或帶有歧義的請求。
- **規模有限**：150 個樣本、9 個領域對於全面評估 LLM 能力而言仍屬中小型資料集。
- **評估指標過於嚴格**：完全匹配可能忽略語義等價的合理答案。
- **僅考慮單輪局部修訂**：未探討多輪修訂、使用者回饋或模型主動詢問澄清的互動情境。

#### 可重現性評估

本研究在可重現性方面表現良好，作者已將程式碼與資料集公開於：

> https://github.com/ntt-dkiku/llm-revision-propagation

具體開放內容包括：

- **基準測試實例（benchmark instance）**
- **資料取樣（data sampling）**腳本
- **人工標註（annotation）**工具

這些資源讓其他研究者能夠重複實驗、擴充領域或比較新方法，對學術社群相當有價值。

然而，可重現性仍受到以下因素影響：

- **模型取得性**：實驗使用的模型包括 gpt-oss-20b/120b、gpt-5.4-mini、qwen3.5-9b/27b/122b 等。若這些模型為特定內部版本、未公開權重或需特殊授權，其他團隊可能難以完全複製結果。論文應更清楚說明各模型的取得管道、API 版本與參數設定。
- **合成資料生成的隨機性**：使用 GPT-5.5 與 Opus 4.8 進行資料生成時，溫度（temperature）、取樣種子（seed）與提示詞（prompt）會顯著影響產出品質。若這些細節未完整公開，重現出的資料分布可能有所差異。
- **人工標註的主觀性**：雖然有標註工具，但黃金修補檔的判定仍涉及人類判斷。不同標註者對於「何謂必要修訂」可能有不同理解，論文可補充標註者一致性（inter-annotator agreement）數據。
- **評估腳本的匹配器設計**：關鍵字匹配器的覆蓋範圍會直接影響準確率。若匹配器過於寬鬆或嚴格，結果將難以橫向比較。

整體而言，本研究在開放性上已達到一定水準，但若要達成完全可重現，仍需補充更多實作細節與模型版本資訊。

#### 未來研究方向

基於本研究的發現與限制，未來可從以下幾個方向深入：

1. **擴展產物類型與領域**
   將修訂傳播任務從 JSON 擴展到 Markdown 文件、程式碼、簡報、試算表，甚至多模態產物，並納入更多真實世界領域。

2. **真實對話資料收集**
   建立基於真實使用者互動的資料集，捕捉自然語言中常見的歧義、省略與上下文依賴，提升基準測試的外部效度。

3. **顯式依賴關係建模**
   設計讓模型在生成 Patch 之前，先輸出「需要更新的元素及其理由」的中間結構，例如透過**思維鏈（chain-of-thought）**或依賴圖預測，提升可解釋性與準確率。

4. **更先進的測試時運算策略**
   除了平行取樣，可探索**蒙地卡羅樹搜尋（Monte Carlo Tree Search，MCTS）**、**過程監督（process supervision）**、學習式獎勵模型（learned reward model）或驗證器（verifier）導向的選擇機制。

5. **語義等價評估**
   開發更細緻的評估指標，例如允許部分得分（partial credit）、語義相似度比對，或結合 LLM 作為評判者來判斷功能等價性。

6. **互動式修訂與主動澄清**
   當模型不確定哪些元素需要更新時，可主動向使用者詢問，而非直接猜測。這種人機協作模式在實際應用中可能更穩健。

7. **效率與成本最佳化**
   研究如何根據任務難度動態調整平行取樣數量、使用較小模型進行初步篩選，或將 medoid selection 等輕量策略蒸餾成更快速的選擇器。

8. **多輪修訂與一致性維護**
   探討在連續多輪修訂下，如何防止錯誤累積並長期維持產物一致性。

總結來說，本研究為「對話生成產物的修訂傳播」開闢了一個新的研究方向，並透過系統性的基準測試與成本效益分析，為未來的模型設計與應用部署提供了重要參考。

## 論文問答

**Q1：什麼是「對話生成產物中的修訂傳播」問題，為什麼它很困難？**  
A：當使用者透過對話與大型語言模型協作生成產物（如計畫、設定檔或記錄）時，往往只會提出局部的修訂請求，例如「刪除景點 B」。此時模型不能僅修改被提及的元素，還必須找出所有隱含的依賴關係，並把必要的變更傳播到產物的其他部分，以維持整體一致性。困難之處在於這些依賴關係常常不是直接寫在產物裡，而是嵌入在對話歷史與上下文中，模型必須同時理解對話流程與產物結構才能正確推論。例如刪除一個景點後，行程時間與預算都可能需要連帶調整，但使用者未必會明確指出。

**Q2：現有的程式庫層級程式編寫、知識編輯或文件編輯方法，為何無法直接解決這個問題？**  
A：現有研究大多處理的是依賴關係相對明確或可被靜態分析的產物，例如程式碼中的呼叫圖、匯入關係與變數引用，知識編輯中的知識圖譜，或文件編輯中的章節、圖表與引用連結。這些方法可以透過靜態分析或預先建構的圖結構來定位需要修改的範圍，但對話生成的產物中，元素之間的依賴往往是隱含且動態建立的。由於這些依賴關係散佈在對話歷史之中，單純分析產物本身無法完整捕捉，因此需要新的設定與評估方式。

**Q3：為什麼這個問題對實務上的大型語言模型應用很重要？**  
A：在真實使用情境中，使用者通常以迭代循環的方式逐步修訂產物，很少一次就清楚列出所有連帶影響。如果模型無法正確傳播修訂，就會產生內部不一致的結果，例如行程時間與預算互相矛盾，進而降低使用者信任與實用性。因此，讓模型在測試時運算階段以成本效益高的方式自動識別並傳播修訂，是提升對話式生成系統可靠度的關鍵。

**Q4：RevPropBench 是什麼，它的建構流程為何？**  
A：RevPropBench 是本論文提出的新基準測試，專門用來評估大型語言模型在對話生成產物中進行修訂傳播的能力。每個樣本包含生成階段的對話歷史、一個局部修訂請求，以及對應的黃金修補檔；資料透過強大的大型語言模型進行合成取樣後，再由人工標註者審查與修正。該基準涵蓋 9 個領域、50 個情境，共 30 個開發樣本與 120 個測試樣本，並依 JSON 元素數量分為 10、50、100 三種產物大小。

**Q5：論文評估了哪些核心修訂方法？**  
A：論文共評估了九種修訂方法，包括單次推論基線、序列式反思變體，以及平行取樣變體。在平行取樣中，模型會產生多個候選修補檔，再透過基於 LLM 的選擇或中心點選擇挑選最終答案。這些方法的設計目標是在增加測試時運算量的同時，盡可能以成本效益最高的方式提升修訂傳播的準確率。

**Q6：評估指標與修補檔表示法的關鍵設計選擇是什麼？**  
A：論文採用 JSON Patch（RFC 6902）作為標準修補格式，每個操作以三元組（op, path, value）表示，並將修補檔視為有序的修改序列。對於可以用多種方式表達的自由文字數值，則設計關鍵字比對器來判斷是否正確，而非要求完全字串匹配。此外，標註者可以為某些元素加上選用旗標，表示修改或不修改皆可接受，讓評估更能反映真實語意。

**Q7：實驗中基線方法的準確率表現如何？**  
A：在單次推論的基線設定下，各模型在 RevPropBench 上的準確率介於 68.3% 到 93% 之間，顯示大型語言模型已具備一定程度的修訂傳播能力，但表現會隨模型而異。這個結果也說明，即使在對話歷史中隱含依賴關係，模型仍能透過推論找出部分連帶修改。然而，基線準確率尚未達到完全可靠，仍有透過測試時運算進一步改善的空間。

**Q8：哪種測試時運算方法最具成本效益，帶來多少改善？**  
A：實驗結果顯示，從三個平行取樣結果中挑選一個最具成本效益，無論是使用基於 LLM 的選擇或中心點選擇，都能顯著提升準確率。相較於基線，這種方法可帶來 2.2% 到 9.7% 的準確率提升。由於平行取樣可以同時生成多個候選答案，並透過輕量選擇機制挑出最終結果，因此在成本與效能之間取得了較佳平衡。

**Q9：實驗是否針對產物大小或領域進行分析？**  
A：是的，論文透過圖表呈現了不同產物大小與領域下的傳播規模與模式分布。領域涵蓋旅遊行程、購物車、專案時程、發票、軟體設定、課程規劃、製造物料清單、資料管線與組織存取計畫等。傳播模式則包括算術重算、時間平移、替換等多種類型，顯示修訂傳播的複雜度會隨情境與產物規模而變化。

**Q10：哪些實務場景最能受惠於修訂傳播技術？**  
A：任何透過多輪對話逐步建構的結構化產物都可能受惠，例如旅遊規劃、購物車與訂單、專案排程、發票與預算、軟體設定檔、課程計畫、製造物料清單、資料處理管線，以及權限存取計畫。在這些場景中，使用者的一句局部修改往往會牽動多個欄位或元素。能自動傳播修訂的模型可以減少使用者反覆檢查與補充說明的負擔，提升協作效率。

**Q11：在實際產品部署時，應該考慮哪些成本與效能權衡？**  
A：首先，平行取樣雖然能提升準確率，但會增加推論次數與延遲，因此需要根據應用對即時性的要求調整取樣數量。其次，選擇機制本身也會帶來額外成本，基於 LLM 的選擇通常比中心點選擇更昂貴，但可能在複雜情境下更準確。最後，輸出格式採用 JSON Patch 有助於後續確定性套用與稽核，但產品仍需處理語意等價但格式不同的合法編輯。

**Q12：這項研究對大型語言模型編輯與生成領域可能帶來什麼影響？**  
A：本研究將焦點從傳統的靜態依賴分析轉移到對話歷史中的隱含依賴，提醒研究者與工程師：產物的一致性不僅取決於產物本身，也深受對話脈絡影響。它也證明了測試時運算，特別是平行取樣與選擇策略，在修訂傳播任務上具有實質效益。這些發現有助於設計更穩健的對話式生成系統，並為未來結合反思、重排序與互動式確認的方法奠定基礎。

**Q13：論文承認了哪些限制？**  
A：本研究主要聚焦於 JSON 格式的產物，雖然 JSON 是大型語言模型系統常見的輸出格式，但仍無法涵蓋所有真實文件或程式碼場景。此外，基準中的情境是透過合成取樣產生，雖然經過人工標註，仍可能與真實使用者對話存在分布差異。評估採用與黃金修補檔比對的方式，也可能對語意正確但表達不同的合法修訂過度懲罰。

**Q14：目前仍存在哪些失敗案例或挑戰？**  
A：如圖一所示，模型可能成功刪除景點並調整行程時間，卻遺漏了預算的連帶修改，顯示算術重算與跨欄位推論仍是難點。當產物規模變大或依賴鏈較長時，模型更容易漏掉間接影響的元素。此外，若平行取樣產生的多個候選答案都出現相同盲點，選擇機制也無法修正錯誤。

**Q15：未來可以朝哪些方向延伸這項研究？**  
A：未來可以將研究擴展到非 JSON 產物，例如自然語言文件、程式碼庫或混合媒體內容，並收集真實使用者對話資料以提升外部效度。另一個方向是結合更強大的依賴建模、互動式澄清與序列式反思，進一步提升傳播正確率。此外，探索如何根據問題難度動態調整測試時運算量，也有機會在成本與準確率之間取得更佳平衡。

## 實務應用指南

### 適用場景

1. **智慧行程與專案規劃助手**  
   使用者透過多輪對話產出旅遊行程、專案時程或會議議程後，常提出局部修訂請求，例如「刪除景點 B」或「把參加人數改為 5 人」。系統必須自動傳播修訂，連帶更新交通時間、預算、餐廳訂位等相依項目，避免產生物料不一致。

2. **軟體設定與基礎設施即程式碼（IaC）編輯器**  
   在對話中生成 JSON/YAML 形式的雲端設定、API 閘道規則或 CI/CD pipeline 時，修改一個參數（如區域、執行個體規格）可能牽動相依的資源、權限或環境變數。修訂傳播可確保設定檔在變更後仍保持語義一致。

3. **財務與商業文件協作編輯**  
   發票、報價單或採購單等文件常由對話生成。當使用者調整數量、折扣稅率或幣別時，系統需要自動重新計算小計、稅額與總金額，並同步更新相關條款與備註。

4. **電子商務購物車與訂單管理**  
   對話式購物助理在生成購物車或訂單 JSON 後，若顧客更改商品規格、數量或配送方式，系統應傳播修訂至庫存、運費、優惠券適用性與預計到貨日等相依欄位。

5. **教育課程與學習計畫產生器**  
   學生或教師透過對話建立課程規劃 JSON 後，若調整先修課程、學分上限或學期目標，系統需自動調整後續課程順序、畢業時程與建議修課負擔。

### 實作前置條件

**資料條件**
- 需具備結構化的對話歷史與對應 JSON 產物，建議先定義清晰的 artifact schema。
- 需要黃金修補檔（gold patch）作為評估標準，可透過強模型合成取樣再經人工標註校正，類似 RevPropBench 的建構流程。
- 建議收集涵蓋不同領域（規劃、記錄、設定）、不同產物規模（如 10/50/100 個 JSON 元素）的樣本，以驗證傳播模式的多樣性。

**運算條件**
- 需能呼叫受評估的大型語言模型 API（如 gpt-oss-20b/120b、gpt-5.4-mini、qwen3.5 系列）。
- 採用平行取樣策略時，每次修訂請求會產生 3 個樣本並進行選擇，需預留約 3 倍推論成本與延遲預算。
- 若使用 medoid 選擇，需額外準備嵌入模型與相似度計算資源。

**技能條件**
- 熟悉 JSON Patch（RFC 6902）規範與 diff/patch 比對邏輯。
- 具備提示工程能力，能設計「僅針對必要元素修訂」的系統提示，避免過度傳播。
- 具備基礎評估能力，能設計路徑與數值比對的 matcher，並處理自由格式文字的關鍵字驗證。

---

### 實作步驟建議

1. **定義產物結構與對話流程**  
   先為目標應用設計 JSON schema，並規劃生成階段的對話輪次，讓相依關係自然嵌入對話歷史中。

2. **建立修訂傳播評估資料集**  
   使用強模型（如 GPT-5.5 或 Opus 4.8）合成情境、對話與初步黃金修補檔，再由領域專家人工審查與校正，確保隱含依賴關係被正確標註。

3. **實作基礎單次推論管線**  
   將「對話歷史＋目前產物＋修訂請求」輸入 LLM，要求模型輸出 JSON Patch。先以單一樣本建立準確率基線。

4. **導入成本效益最佳的測試時運算**  
   根據論文結果，優先採用「3 個平行樣本＋選擇機制」：可選擇基於 LLM 的選擇（讓模型自評）或 medoid 選擇（挑選與其他樣本最相似的輸出），此策略在成本與準確率提升間取得最佳平衡。

5. **建立評估與監控機制**  
   比對生成修補檔與黃金修補檔的路徑與數值，特別關注「遺漏傳播」（該改沒改）與「過度傳播」（不該改卻改）兩類錯誤。

6. **部署人機協作審查介面**  
   在正式環境中，將模型輸出的修訂以 diff 形式呈現給使用者或審核者，讓其可一鍵接受、部分修改或退回重跑。

7. **持續迭代與領域擴充**  
   隨著產品上線，收集真實修訂案例並回補至資料集，定期重新評估模型表現與成本曲線。

---

### 潛在風險與注意事項

- **遺漏隱含依賴關係**  
  模型可能只修改使用者明確提到的元素，卻忽略對話歷史中建立的隱含依賴。建議在提示中明確要求「檢查所有可能受影響的元素」，並輔以領域特定的檢查清單。

- **過度傳播與幻覺修訂**  
  模型可能為了「保持一致」而修改不該變動的內容。可透過嚴格的系統提示限制僅輸出必要修補，並在評估階段比對未變更元素的穩定性。

- **成本與延遲上升**  
  平行取樣雖能提升準確率，但會增加推論開銷。建議在產品中根據請求複雜度動態決定取樣數量，對簡單請求維持單次推論。

- **自由格式數值的比對困難**  
  預算、描述等欄位可能有多種合法表達方式。應設計關鍵字 matcher 而非強制字串完全比對，並在標註階段定義可接受的同義表達。

- **Schema 漂移與版本控制**  
  隨著產品迭代，JSON schema 可能改變，導致舊的黃金修補檔失效。建議將 schema 版本納入資料集管理，並與版本控制系統整合。

---

### 與其他技術的整合建議

- **檢索增強生成（RAG）**  
  將過去的修訂案例與領域知識庫作為檢索內容，在推論前注入相關範例，可提升模型對隱含依賴關係的識別能力。

- **Agent 框架**  
  可將修訂傳播設計為專責 agent 的工具之一，讓規劃 agent 負責拆解複雜請求，再由修訂傳播 agent 產出結構化 patch，最後由驗證 agent 檢查一致性。

- **版本控制與協作系統**  
  將 JSON Patch 輸出直接對應到 Git diff 或文件編輯器的變更追蹤功能，讓使用者能以熟悉的介面審查與合併修訂。

- **CI/CD 與自動化測試**  
  對於程式碼或設定檔產物，可將生成的 patch 套用後執行靜態分析、單元測試或 schema 驗證，作為額外的品質閘門。

- **人機協作（Human-in-the-loop）平台**  
  在關鍵場景（如財務文件、法律合約）中，將模型輸出導入審核 workflow，並把人工修正結果回饋至訓練或評估資料集。

### 給不同背景讀者的閱讀建議

**給初學者**  
這篇論文探討的是「當你跟 AI 聊天產生一份計畫或表格後，只說改一個小地方，AI 怎麼知道還要連動改哪些其他地方」。建議先從圖 1 的旅遊行程範例開始理解問題，再閱讀第 2 節的任務定義與資料格式，最後看實驗結果中「平行取樣 3 次再選最好」這個最實用的結論。

**給 AI 工程師**  
本文提供了一個可落地的評估框架與具體方法比較。建議重點研讀第 2 節的 benchmark 設計、JSON Patch 評估方式，以及第 4 節中九種修訂方法的準確率與成本權衡。實作時可直接參考「3-sample parallel + LLM/medoid selection」的組合，並根據你的延遲與成本預算調整取樣數。

**給研究人員**  
這篇工作開拓了「對話生成產物中的隱含依賴傳播」這個尚未被充分研究的設定，與程式庫層級程式編寫、知識編輯等既有問題形成對比。建議關注其與現有工作的差異（第 1 節）、RevPropBench 的建構方法論（第 2 節），以及未來可延伸的方向，例如更長的對話歷史、更複雜的傳播鏈或多模態產物。

**給產品經理**  
這篇論文的核心訊息是：在對話式 AI 產品中，局部修訂請求很容易導致產物前後不一致，而透過「多生成幾個版本再挑最好」是一個成本可控且效果顯著的解法。建議聚焦於圖 1 的使用者情境、實驗結果的準確率提升幅度，以及潛在的產品風險（如過度修改與審核需求），以評估是否值得在現有產品中導入此機制。
