A：現有的基準測試（如 Physics-IQ、Video2World、4DCodeBench、PhysCodeGym 等）各自定義了不同的輸入格式、交付物形式與評分程式碼。例如 Physics-IQ 提供影片前三秒並要求預測接下來五秒的畫面，而 Video2World 則要求產出包含重建場景與機器人動作的模擬套件。這種異質性導致評估 N 個方法在 M 個基準上需要 N×M 次整合，每對方法與基準都需要客製化適配器，大幅增加了評估成本，也阻礙了跨論文的公平比較。

A：隨著 Claude Fable 5.2、GPT-6 等基礎模型的快速進展，程式碼代理已具備撰寫、除錯並迭代大型程式的能力。這開啟了一個新典範：與其為每種場景設計專用流程，不如直接讓代理從影片錄影中撰寫模擬程式。例如給定一段紅色飲料倒入玻璃杯的影片，代理可寫出一個在物理模擬器中設置玻璃與液體並重現傾倒動作的程式。同一個代理能嘗試處理多種場景，朝自動化建構模擬的方向邁出了關鍵一步。

**Q4：Real2SimLab 的核心設計理念是什麼？**

A：Real2SimLab 的核心設計理念是將「方法所撰寫的程式」作為方法與基準之間的共同介面。在方法端，每個方法只需透過一個方法級適配器連接一次，接收任務並回傳程式；在基準端，每個基準只需透過一個基準級適配器連接一次，將資料轉換為統一格式的任務並保留官方評分器。如此一來，評估 N 個方法在 M 個基準上只需 N+M 次整合，而非傳統的 N×M 次。

**Q5：Real2SimLab 如何避免資料污染（data contamination）問題？**

A：Real2SimLab 的訓練資料生成流程會比對每段訓練影片的畫面與評估任務的畫面，過濾掉任何出現在評估任務中的錄影，包括重新編碼、調整解析度或剪輯過的版本。對於通過過濾的每段錄影，流程會先讓方法產生一個程式，再用與評估完全相同的評分程式碼計算該程式的獎勵。這種設計確保了訓練資料與評估資料之間的嚴格分離，避免了真實到模擬領域常見的影片片段被多個資料集重複使用的污染問題。

**Q6：Real2SimLab 在方法與基準兩端分別採用了什麼樣的適配器架構？**

A：在方法端，Real2SimLab 透過一個橋接層連接到 Harbor 框架，使 47 個程式碼代理（如 OpenHands、Aider 等）都能接入；其中 5 個常用的代理（Codex、Claude Code、Gemini CLI 等）也可直接在 Real2SimLab 的沙盒中執行。在基準端，Real2SimLab 為 Physics-IQ、Video2World、4DCodeBench、PhysCodeGym、PhySimCode、IRIS 等 6 個基準各自建立了適配器，並新增了一個具有精確真值的合成套件，每個適配器都經過與原始基準版本的對齊驗證。

**Q7：Real2SimLab 目前支援哪些程式碼代理與非代理方法？**

A：截至目前，Real2SimLab 支援 47 個程式碼代理與 5 個非代理方法。47 個代理透過橋接層接入 Harbor 框架，其中 Codex、Claude Code、Gemini CLI 等 5 個廣泛使用的代理還能在 Real2SimLab 的沙盒中直接執行。非代理方法則涵蓋傳統的物理參數擬合、三維場景重建等專用流程。這樣的覆蓋範圍讓研究者能在統一平台上比較新興的程式碼代理與成熟的傳統方法。

**Q8：Real2SimLab 整合了哪些基準測試，各自的特點為何？**

A：Real2SimLab 整合了 6 個現有基準：Physics-IQ 評估從前三秒影片預測後續五秒畫面的能力；Video2World 要求從機器人操作影片重建場景與動作；4DCodeBench 要求產出能建構隨時間變化的三維世界的腳本；PhysCodeGym 要求產出能重現參考影片的 Blender 場景；PhySimCode 與 IRIS 則各有不同的任務設計。此外，Real2SimLab 還新增了一個具有精確真值的合成套件，方便診斷方法在受控條件下的表現。

**Q9：Real2SimLab 如何驗證其評分結果與原始基準一致？**

A：Real2SimLab 為每個基準建立了基準級適配器，並明確保留各基準的官方評分器與評分環境。論文中提到，每個適配器都會與其基準的原始發行版本進行對齊檢查，確保透過 Real2SimLab 得到的分數與直接使用原始基準得到的分數一致。這種「保留原始評分器」的策略是平台可信度的關鍵，因為它避免了重新實作評分邏輯可能帶來的偏差。

**Q10：Real2SimLab 對機器人研究與合成資料生成有何實務價值？**

A：在機器人研究中，從真實房間掃描建構模擬訓練環境一直是重要需求，而 Real2SimLab 統一的介面讓研究者能快速評估不同代理在重建機器人操作場景上的表現。在合成資料生成方面，模擬程式能從新視角渲染、存取任意時刻狀態的特性，使其成為生成大規模、多樣化訓練資料的理想來源。透過 Real2SimLab 的獎勵標註流程，這些資料還能用於線上強化學習與離線微調。

**Q11：Awesome-Real2Sim 研究地圖對學術社群有什麼幫助？**

A：Awesome-Real2Sim 收錄了近 300 篇真實到模擬轉移相關論文，並依據研究動機或交付物類型進行分類組織。由於該領域文獻散佈於電腦視覺、電腦圖學與機器人學等多個領域，且各論文以不同方式呈現結果（從物理參數、模擬就緒資產到場景級模擬、模擬程式、學習型模擬器），新研究者往往難以快速定位相關工作。這個研究地圖降低了文獻搜尋成本，並會隨新論文出現持續更新。

**Q12：Real2SimLab 對產業界部署模擬系統有何影響？**

A：產業界在部署模擬系統時，常面臨為不同場景類型維護多套專用流程的高昂成本。Real2SimLab 透過統一的程式介面，讓企業只需整合一次其內部方法與外部基準，即可橫向評估多個場景類別的表現。此外，平台開源且邀請社群共同擴展的特性，使其能隨著新代理、新基準的出現持續演進，降低企業長期維護模擬管線的技術債。

**Q13：Real2SimLab 目前存在哪些已知的限制？**

A：論文中明確指出，本研究聚焦於平台的設計，至於所連接方法的系統性比較則留待未來工作。此外，目前支援的 47 個代理與 5 個非代理方法雖然覆蓋面已相當廣泛，但對於需要特殊硬體、特殊模擬器或極長執行時間的方法，整合仍可能面臨工程挑戰。基準方面，雖然已涵蓋 6 個代表性基準，但仍有許多領域專屬的真實到模擬任務尚未被納入。

**Q14：在什麼情況下 Real2SimLab 的方法可能會失敗？**

A：當一段影片的物理現象極為複雜（例如多體碰撞、流體耦合、軟體變形等）時，程式碼代理可能無法在合理時間內產出能正確重現現象的模擬程式。此外，若影片畫質過低、視角單一或包含嚴重遮擋，代理對場景三維結構與物理參數的推斷將受到限制，導致重建結果不準確。對於需要精確感測器模型（如 LiDAR、相機雜訊特性）模擬的任務，目前的程式介面也尚未完全涵蓋。

**Q15：Real2SimLab 未來的發展方向為何？**

A：未來發展方向包括：擴展支援更多基準與方法，特別是涵蓋尚未整合的領域專屬任務；推動 Real2SimHub 社群共同維護平台與研究地圖，形成共享的基礎建設；探索更自動化、更多樣化的訓練資料生成流程，以支援下一代真實到模擬方法的訓練；以及在平台上進行系統性的方法橫向比較，產出類似排行榜的公開評測結果，引導領域發展方向。

### 潛在風險與注意事項

- **資料污染風險**：同一支影片可能以不同編碼、解析度或裁切版本出現在多個基準中。Real2SimLab 雖提供 frame-level 比對過濾，但若影片經過大幅剪輯或特效處理，仍可能漏抓。建議在自建訓練集時額外做 perceptual hash 與時間軸比對。

- **API 成本與不確定性**：coding agent 每次呼叫都可能產生數十次 tool-use 迭代，單支影片成本可能從數十美分到數美元不等；且 LLM 升版後結果可能不可重現。建議固定模型版本、記錄 prompt 與隨機性，並預留預算緩衝。

- **安全與沙箱逃逸**：coding agent 會執行程式碼，雖然 Real2SimLab 使用 sandbox，仍應限制網路與檔案系統權限，避免 agent 誤刪主機資料或外洩 API key。

- **基準過時風險**：6 個基準的影片與任務設計反映特定時期的研究重點，新興領域（如 generative physics、neural simulator）可能尚未被涵蓋，使用時應注意 benchmark 的代表性邊界。

- **RL 訓練框架**：reward annotation 輸出可直接餵入 TRL、OpenRLHF、verl 等 offline RL 或 preference learning 框架；建議將 reward 標準化（如 z-score）後再使用，以穩定訓練。

- **數位孿生平台**：若企業已有 Siemens、NVIDIA Omniverse 或 Unity 為基礎的數位孿生系統，可將 Real2SimLab 產出的程式作為「場景原型產生器」，再由既有 pipeline 轉成正式資產。

- **MCP / Tool-use 生態**：coding agent 多支援 Model Context Protocol，可將 Blender CLI、PyBullet Python API 包裝成 MCP tools，讓 agent 更穩定地呼叫，減少 hallucinated API。
