## 摘要翻譯

大型語言模型代理（Large Language Model Agents）在短任務上通常能做出合理的局部決策（Local Decisions），但當任務成功需要執行一長串彼此相依的動作（Dependent Actions）與工具呼叫（Tool Calls）時，其表現便會下降。在執行過程中，任務需求、歷史證據與當前執行狀態可能逐漸脫節，導致後續決策偏離原始目標。我們透過提出自適應一致性圖（Adaptive Consistency Graph, ACG）來研究此問題，該方法專為支援長時程代理（Long-Horizon Agent）執行而設計。ACG 將執行證據（Execution Evidence）及其來源出處（Provenance）以增量方式組織於持久化圖（Persistent Graph）中，並在有界上下文預算（Bounded Context Budget）下，為每個決策建構一個臨時的以需求為中心的視圖（Requirement-Centered View）。ACG 並非取代基礎代理（Base Agent）的規劃器（Planner）或工具執行器（Tool Executor），而是為每個決策提供一個結構化且可追溯的上下文視圖。在配對評測（Matched Evaluation）中，ACG 將 GPT-5.6-luna 的平均成功率（Success Rate）從使用推理-行動循環（ReAct）時的 44.5% 提升至 50.2%，其中在 BrowseComp-Plus 上的提升幅度最大（73.5% 對比 62.4%）。我們進一步分析軌跡結構（Trajectory Structure）與推論成本（Inference Cost），以分析此項改進的特徵。

### 核心貢獻（3～5點）
- 提出自適應一致性圖（ACG），透過持久化圖結構增量累積執行證據及其來源出處，系統性地緩解長時程任務中的決策漂移（Decision Drift）問題。
- 設計以需求為中心的視圖（Requirement-Centered View）機制，在有界上下文預算（Bounded Context Budget）下為每個決策提供結構化且可追溯的上下文，無需修改基礎代理的規劃器或工具執行器，具備高度可移植性。
- 在配對評測（Matched Evaluation）中驗證 ACG 的有效性：將 GPT-5.6-luna 搭配推理-行動循環（ReAct）的平均成功率從 44.5% 提升至 50.2%，並於 BrowseComp-Plus 上取得最大增幅（73.5% 對比 62.4%）。
- 透過軌跡結構（Trajectory Structure）與推論成本（Inference Cost）之分析，系統性地闡明 ACG 帶來之改進的特徵與計算代價。

### 適合對象
從事大型語言模型代理（LLM Agent）研究、代理記憶（Agent Memory）機制設計、長上下文行為（Long-Context Behavior）分析，以及檢索增強生成（Retrieval-Augmented Generation, RAG）與基於圖的關聯式檢索（Graph-Based Associative Retrieval）等領域的研究者與工程師；亦適合關注代理於長序列任務中決策穩定性與可追溯性之議題的實務應用開發者。

## 深度分析

#### 方法論解析

ACG（Adaptive Consistency Graph，自適應一致性圖）的核心設計理念在於解決長時程代理（Long-Horizon Agent）所面臨的「決策漂移」（Decision Drift）問題：當任務需要多個依賴性動作（Dependent Actions）時，後續決策可能逐漸與原始任務需求、歷史證據及當前執行狀態脫節。

**持久化執行記憶（Persistent Execution Memory）**

ACG 的第一個關鍵設計是建立一個持續累積的圖結構（Persistent Graph），用於儲存任務執行過程中的證據單元（Evidence Units）。每個證據單元都與其來源事件（Source Events）建立連結，並保留事件之間的關聯性。這種設計與傳統的壓縮式記憶（Compressed Memory）有本質區別——後者通常透過摘要（Summarization）來縮減歷史資訊，但摘要過程中可能丟失事件級細節與來源出處（Provenance），導致後續決策無法重建「為何記錄此一事實」的脈絡。ACG 選擇保留原始證據而非生成摘要，這是其在長時程任務中能維持一致性的關鍵基礎。

**自適應決策視圖（Adaptive Decision Views）**

ACG 的第二個關鍵設計是為每個決策點動態建構一個「以需求為中心的視圖」（Requirement-Centered View）。其運作流程包含三個步驟：

1. **種子檢索（Seeded Retrieval）**：以當前任務需求（Task Requirements）與最新互動事件（Latest Interaction Event）作為檢索種子，從持久化圖中選取相關證據。
2. **需求限定組織（Requirement-Qualified Organization）**：將選中的證據組織成一個臨時視圖，該視圖以任務需求為中心，圍繞相關證據展開。
3. **預算渲染（Budget Rendering）**：在有界上下文預算（Bounded Context Budget）下渲染該視圖，確保不超出模型的上下文視窗（Context Window）。

值得注意的是，這個視圖是**臨時性**的——它不會覆寫或修改底層的持久化記憶。這意味著同一份證據可以根據不同決策的需求被重新組織成不同的視圖，而原始證據始終保留供後續決策使用。

**與基礎代理的解耦設計**

ACG 的一個重要設計哲學是「不替換基礎代理的規劃器（Planner）或工具執行器（Tool Executor）」。它僅作為一個外部的上下文建構（Context Construction）層介入，在每個決策點為基礎代理提供結構化、可追溯的上下文視圖。這種設計使得 ACG 可以與各種代理框架（如 ReAct）組合使用，具有良好的通用性。

#### 實驗數據解讀

**整體效能提升**

在配對評測（Matched Evaluation）中，ACG 將 GPT-5.6-luna 的平均成功率（Success Rate）從 ReAct 基線的 44.5% 提升至 50.2%，絕對提升約 5.7 個百分點。雖然這個數字看似不大，但在長時程代理任務中，這樣的提升已經相當可觀，因為長時程任務的成功率通常較低，且每一步的錯誤都可能級聯放大。

**基準任務分析**

論文在三類任務上進行評測：

1. **受限規劃（Constrained Planning）**：測試代理在多約束條件下完成規劃的能力。
2. **語料庫資訊檢索（Corpus-Based Information Retrieval）**：測試代理從大量文本中提取並整合資訊的能力。
3. **程式碼修復（Repository-Level Code Repair）**：測試代理在大型程式碼庫中定位並修復問題的能力。

這三類任務覆蓋了長時程代理的主要應用場景，且都涉及多步驟依賴動作。

**BrowseComp-Plus 上的顯著提升**

最引人注目的是在 BrowseComp-Plus 上的表現：ACG 達到 73.5%，而 ReAct 基線僅為 62.4%，相對提升約 17.8%。這個基準屬於瀏覽類任務，需要代理在多個網頁間導航、收集資訊並整合答案。ACG 在此類任務上的優勢尤為明顯，可能原因在於：瀏覽任務天然涉及大量分散的證據點，且需要維持對原始查詢的一致理解——這正是 ACG 設計的核心場景。

**軌跡結構與推論成本**

論文進一步分析了軌跡結構（Trajectory Structure）與推論成本（Inference Cost）的關係。ACG 透過結構化的證據組織，可能減少了冗餘的工具呼叫（Tool Call）次數，因為代理能更有效地定位所需資訊。然而，由於 ACG 需要在每個決策點進行檢索與視圖建構，這會引入額外的計算開銷。論文聲稱「建立任務成功率與成本的提升不同於將該提升歸因於單一記憶機制」，這是一個審慎的表述——他們觀察到了整體改善，但並未聲稱是某個特定機制（如檢索效率或證據保留）獨自帶來的。

#### 與現有研究的比較

**與代理記憶方法的比較**

| 方法 | 核心機制 | 與 ACG 的差異 |
|------|----------|---------------|
| Generative Agents | 記憶流檢索 + 反思 + 規劃 | 強調反思與抽象，ACG 保留原始證據 |
| Reflexion | 嘗試間的語言反饋 | 跨嘗試學習，ACG 專注單次執行的上下文建構 |
| ExpeL | 從成功/失敗軌跡中提煉經驗 | 強調經驗重用（Experience Reuse），ACG 強調即時證據組織 |
| HiAgent | 以子目標（Subgoal）組織工作記憶（Working Memory） | 層次化組織，ACG 以需求為中心 |

ACG 的獨特之處在於：它不進行摘要或抽象，而是保留事件級證據與來源出處。這避免了「摘要丟失關鍵細節」的問題，但也帶來了儲存成本較高的權衡。

**與檢索增強方法的比較**

| 方法 | 核心機制 | 與 ACG 的差異 |
|------|----------|---------------|
| RAG | 段落檢索 + 生成 | 靜態文檔檢索，ACG 處理動態執行證據 |
| Self-RAG | 自我判斷檢索 | 將檢索決策融入生成，ACG 將檢索與生成解耦 |
| LongMem | 外部記憶擴展上下文 | 通用外部記憶，ACG 專注執行時的關聯組織 |
| HippoRAG | 基於圖的關聯式檢索（Graph-Based Associative Retrieval） | 跨文檔整合，ACG 處理單一軌跡內的證據演化 |

HippoRAG 與 ACG 都採用圖結構，但 HippoRAG 主要用於跨文檔的關聯式檢索，而 ACG 專注於單一執行軌跡內的證據演化與組織。

**與長上下文方法的比較**

Transformer-XL、Compressive Transformers、Memorizing Transformers 等方法透過循環式記憶（Recurrent Memory）或壓縮式記憶來擴展上下文容量（Context Capacity）。ACG 並不試圖擴展上下文視窗本身，而是透過更智慧的上下文建構來提升現有視窗的利用效率。這與 Liu 等人（2024）關於「資訊即使在上下文視窗內也難以使用」的發現相呼應。

**限制與不足**

1. **歸因不明確**：論文坦承「建立任務成功率與成本的提升不同於將該提升歸因於單一記憶機制」，這意味著讀者難以判斷是持久化圖、需求中心視圖，還是有界預算渲染各自貢獻了多少。
2. **計算開銷**：每個決策點的檢索與視圖建構會增加延遲，在即時性要求高的場景中可能不適用。
3. **圖結構的維護成本**：隨著執行步數增加，持久化圖可能膨脹，需要相應的剪枝或索引策略（論文中未詳細說明）。

#### 未來研究方向

**1. 動態預算分配機制**

當前的有界上下文預算採用靜態或均勻分配策略，未來可以研究：
- 基於決策重要性的自適應預算分配
- 根據任務剩餘步數動態調整證據保留粒度
- 跨決策點的預算預測與規劃

**2. 圖結構的演化與剪枝**

持久化圖隨執行步數增長可能膨脹，未來方向包括：
- 基於資訊理論的節點重要性評估
- 時間衰減與任務相關性的聯合剪枝策略
- 層次化圖結構以支援多尺度檢索

**3. 跨任務經驗遷移**

ACG 目前專注於單次執行的上下文建構，未來可以探索：
- 將成功軌跡的圖結構作為範本遷移到新任務
- 結合 ExpeL 的經驗重用思想，在 ACG 圖中累積可遷移的模式
- 元學習（Meta-Learning）層面的圖結構初始化

**4. 與其他記憶機制的混合架構**

ACG 不替換基礎代理的設計使其易於組合，未來可以：
- 與 Reflexion 的語言反饋結合，形成「即時證據 + 跨嘗試反思」的雙層記憶
- 與 HiAgent 的子目標層次化結合，在子目標切換時觸發視圖重建
- 整合 Self-RAG 的自我判斷機制，讓代理主動決定何時擴展檢索範圍

**5. 歸因分析與消融研究**

論文坦承未明確歸因於單一機制，未來需要：
- 系統性的消融研究（Ablation Study），分別移除持久化圖、需求中心視圖、有界預算渲染
- 在不同任務類型上分析各機制的相對貢獻
- 建立可解釋性指標，量化「決策漂移」的減少程度

**6. 多代理協作場景**

在多代理系統中，每個代理可能維護各自的 ACG，未來可以研究：
- 代理間的圖結構共享與同步
- 衝突證據的仲裁機制
- 全局視圖與局部視圖的一致性維護

**7. 理論分析**

目前 ACG 的有效性主要透過實驗驗證，未來可以：
- 形式化定義「一致性」並證明 ACG 在何種條件下能維持一致性
- 分析視圖建構的計算複雜度與近似比
- 與資訊瓶頸（Information Bottleneck）理論建立聯繫

## 論文問答

**Q1：長時程代理面臨的核心問題是什麼？為什麼這是一個重要議題？**
A：長時程代理面臨的核心問題是「決策漂移」(decision drift)，亦即隨著動作序列與工具呼叫的累積，任務需求、歷史證據與當前執行狀態之間的連結會逐漸斷裂，導致後續決策偏離原始目標。此問題之所以重要，是因為現代大型語言模型代理已從單回合生成擴展為多步驟互動，後續決策高度依賴先前累積的資訊。一旦代理無法在長程執行中維持「需求—證據—狀態」三者的一致性，即使每個局部決策看似合理，整體任務仍可能失敗。這在具身機器人控制、開放式技能獲取與反饋驅動規劃等場景中尤其關鍵，因為這些任務的成功取決於跨多步驟的依賴性動作。

**Q2：現有的代理記憶方法（如 Generative Agents、Reflexion、ExpeL、HiAgent）為何無法完全解決長時程的一致性問題？**
A：現有方法各有側重：Generative Agents 著重於記憶檢索與反思，Reflexion 透過跨嘗試的語言反饋學習，ExpeL 從成功與失敗軌跡中提煉可重用的經驗，而 HiAgent 則以子目標組織工作記憶。這些方法雖然提升了經驗的持久性與抽象重用能力，但往往以「生成的摘要」取代原始證據，當後續決策需要還原某個事實為何被記錄時，必須從已被壓縮的表示中重新推論，過程中容易遺失事件層級的細節與來源出處(provenance)。換言之，這些方法在「壓縮簡潔性」與「細節可重建性」之間存在取捨，而長時程代理的決策往往正需要後者所提供的可追溯性。

**Q3：為什麼長上下文模型或檢索增強生成(RAG)無法直接解決長時程代理問題？**
A：長上下文模型雖然擴展了上下文視窗，但研究顯示即使資訊能放入視窗內，模型仍可能難以有效利用(Liu et al., 2024)，且單純堆疊歷史紀錄會稀釋與當前決策相關的訊號。RAG 與基於圖的關聯式檢索(如 HippoRAG)雖然提供了強大的外部證據擷取能力，但其設計主要針對靜態文件集合，而非隨執行持續演化的軌跡。長時程代理需要的不是「從固定語料庫檢索」，而是「從持續增長的執行歷史中選擇並組織與當前需求相關的證據」，並在有限的上下文預算下兼顧證據的解讀所需的周邊脈絡。這正是 ACG 試圖填補的研究缺口。

**Q4：ACG 的核心設計理念是什麼？它如何區別於傳統的記憶架構？**
A：ACG 的核心設計理念是將「執行記憶」視為一個持續演化的關聯式結構，並將「持久化儲存」與「決策視圖建構」分離。具體而言，ACG 將任務相關證據儲存為來源連結的記憶單元，保留其事件出處與彼此關係，形成一個持久化圖(persistent graph)；在每個決策點，則根據當前任務與最新互動進行檢索，並在有界上下文預算下組裝為一個臨時的「以需求為中心的視圖」。這種設計的關鍵區別在於：底層記憶不會被生成的摘要所覆寫，因此事件層級的證據與來源出處始終可供後續決策追溯，而每個決策所看到的上下文則是依需求動態裁剪的。

**Q5：「以需求為中心的視圖」(requirement-centered view) 如何運作？其在上下文預算管理上有何巧思？**
A：在每個決策點，ACG 以當前任務需求與最新互動事件作為種子(seed)進行檢索，從持久化圖中挑選相關的證據單元；接著，這些被選中的紀錄會被組裝成一個以需求為中心的臨時視圖，並在剩餘的上下文預算下渲染呈現給基礎代理。這種設計的巧思在於「適應性」：預算分配會依據當前決策的資訊需求動態調整，而非對所有歷史紀錄一視同仁地壓縮或截斷。如此一來，代理既能獲得與當前需求高度相關的證據及其解讀所需的周邊脈絡，又不會因為上下文過長而稀釋關鍵訊號，從而緩解長時程決策中常見的「需求—證據—狀態」脫節問題。

**Q6：ACG 為何選擇不取代基礎代理的規劃器與工具執行器？這種設計選擇帶來什麼優勢？**
A：ACG 明確定位為「上下文視圖供應者」，而非取代基礎代理的規劃器(planner)或工具執行器(tool executor)，這體現了模組化與正交化的設計原則。從優勢來看，這種設計使 ACG 能與各種基礎代理框架（如 ReAct）無縫整合，無需重新訓練或大幅改寫代理的核心邏輯；同時，由於底層規劃與執行機制保持不變，ACG 所帶來的效果可以更純粹地歸因於「上下文建構」的改善，而非推理或動作選擇機制的改動。這也使得 ACG 具備良好的可移植性，能應用於不同的任務領域與模型架構。

**Q7：實驗使用了哪些基準測試？為什麼選擇這些任務類型？**
A：實驗涵蓋三類任務：受限規劃(constrained planning)、基於語料庫的資訊檢索(corpus-based information retrieval)以及儲存庫層級的程式碼修復(repository-level code repair)。選擇這些任務的理由在於它們各自代表了長時程代理的不同挑戰面向：受限規劃考驗代理在多步驟約束下的決策一致性；語料庫資訊檢索（如 BrowseComp-Plus）要求代理在大量文件中追蹤並整合證據；程式碼修復則需要跨多個檔案與函式呼叫維持依賴關係。這三類任務共同覆蓋了「依賴性動作」、「大量歷史證據」與「跨資源狀態追蹤」等長時程代理的典型痛點，使評估結果更具代表性。

**Q8：ACG 的主要實驗結果為何？哪些發現最值得關注？**
A：在配對評測(matched evaluation)中，ACG 將 GPT-5.6-luna 的平均成功率從 ReAct 基線的 44.5% 提升至 50.2%，其中在 BrowseComp-Plus 上的提升最為顯著，從 62.4% 提升至 73.5%。最值得關注的發現是 ACG 的增益在「需要大量歷史證據整合」的任務上最為突出，這與其「以需求為中心組織上下文」的設計直覺一致。此外，論文橫跨三個基準與兩個模型、與五個基線進行比較，顯示 ACG 的改善並非偶然，而是具有跨任務與跨模型的穩健性。

**Q9：ACG 在推論成本與軌跡結構方面呈現哪些特性？**
A：從推論成本來看，ACG 透過有界上下文預算限制了每次決策的輸入長度，避免了隨執行步驟線性增長的計算開銷，這對於實際部署的經濟可行性至關重要。在軌跡結構方面，ACG 的持久化圖保留了事件之間的關聯，使得代理的執行軌跡不再是線性的動作序列，而是一個可追溯、可查詢的證據網路；這種結構化紀錄不僅有助於當前決策，也為後續的除錯、審計與經驗重用提供了基礎。論文中對軌跡結構與模型呼叫支出的分析進一步揭示了 ACG 改善的來源不僅是「成功率提升」，也包含「執行行為的規律化」。

**Q10：ACG 適用於哪些實際應用場景？**
A：ACG 特別適合需要多步驟、長序列操作且每步決策都依賴先前證據的場景，例如：複雜的網頁研究與資訊彙整（如 BrowseComp-Plus 所代表的情境）、跨多個 API 呼叫的資料處理流程、大型程式碼庫中的除錯與重構，以及需要持續追蹤環境狀態變化的具身機器人任務。在這些場景中，代理不僅要記住「做過什麼」，更要理解「為什麼這樣做」以及「這些動作之間如何關聯」，而 ACG 的來源連結與關聯式儲存正好提供了這種可追溯性。

**Q11：在實際產品部署中，ACG 需要考慮哪些工程因素？**
A：部署 ACG 時需考量多項工程因素：首先，持久化圖的儲存成本會隨任務長度累積，需要設計有效的剪枝或分層機制以平衡記憶完整性與儲存開銷；其次，檢索與視圖組裝本身會引入額外的延遲與 token 消耗，需評估其對整體回應時間的影響；再者，來源連結與關係標註的品質直接影響下游決策，因此需要考慮如何從非結構化的代理輸出中可靠地抽取事件與關係。此外，與現有代理框架（如 ReAct）的整合介面、錯誤恢復機制，以及多使用者隔離等產品化需求，也都是實際落地時必須處理的課題。

**Q12：ACG 對代理研究領域的帶來哪些觀念上的影響？**
A：ACG 將研究焦點從「如何增強推理能力」轉向「如何為推理提供正確的上下文」，這對代理研究領域具有觀念上的啟發意義。它提醒研究者：即使是最先進的推理模型，其決策品質仍受限於所接收到的資訊；而在長時程任務中，「看見什麼」往往比「怎麼想」更具決定性。此外，ACG 將「持久化記憶」與「決策視圖」分離的設計哲學，為未來的代理記憶研究提供了一個新的架構範式，可能啟發更多關於「執行時上下文工程」(execution-time context engineering) 的研究。

**Q13：ACG 的方法論有哪些已知的局限性？**
A：ACG 的局限性主要體現在三方面：第一，其效果仰賴證據的來源連結與關係標註品質，若代理的原始輸出難以可靠地結構化，持久化圖的效用將大打折扣；第二，ACG 假設任務需求在執行過程中保持穩定，但對於需求本身動態演化的任務（如探索性研究），以「固定需求」為中心的視圖可能不夠靈活；第三，論文中也坦承，雖然 ACG 提升了成功率與成本效益，但「不一致狀態是否為失敗主因」的因果歸因仍待更細緻的分析，這意味著 ACG 的改善可能部分來自其他未明確識別的機制。

**Q14：ACG 在哪些情況下可能表現不佳或失效？**
A：當任務需求本身模糊、需要隨探索過程動態調整時，ACG 的「以需求為中心」假設可能失效，因為此時「需求」本身就不是一個穩定的錨點。此外，若代理的動作空間極為龐大或工具輸出高度非結構化，持久化圖中的關係抽取可能變得不可靠，進而影響檢索品質。在極短任務中，ACG 的圖建構與視圖組裝開銷可能反而超過其帶來的收益，導致「殺雞用牛刀」的成本效率問題。最後，若環境反饋具有高度隨機性或對抗性，僅靠歷史證據的組織仍不足以保證決策正確。

**Q15：基於 ACG 的研究，未來有哪些值得探索的方向？**
A：未來研究方向可分為數個層次：在架構層面，可探索多代理協作下的共享一致性圖，使多個代理能共同維護一個可追溯的執行記憶；在需求建模層面，可研究如何讓「需求中心」隨任務演化動態調整，而非假設其固定；在效率層面，可設計更精煉的圖剪枝與摘要機制，在保留可追溯性的同時控制儲存成本。此外，將 ACG 與線上學習或持續學習結合，使代理能從長程軌跡中提煉可重用技能，以及將其應用於更複雜的多模態環境（如視覺與文字混合的具身任務），都是值得探索的延伸方向。最終，論文所指出的「執行時上下文建構」這一研究維度本身，仍有大量開放問題等待解答。

## 實務應用指南

### 適用場景

1. **企業級多步驟資料分析助理**：當使用者要求代理從多個內部資料庫、API 與檔案中依序擷取、轉換、彙整資料（例如「比對 Q3 各區域銷售異常並交叉查 ERP 與 CRM 系統」），代理需在數十次工具呼叫間維持對原始需求的對齊。ACG 的「以需求為中心視圖」可避免代理在後段決策時遺忘「異常」定義或「Q3」邊界。

2. **長時程程式碼修復與重構代理**：在 repository-level 程式碼修復任務中，代理需跨檔案追蹤錯誤根源、測試結果與先前嘗試。ACG 將每次編輯、測試輸出、堆疊追蹤以「來源出處」形式保留在持久化圖中，使後續決策可回溯到具體事件，避免「為何當初這樣改」的脈絡流失。

3. **自動化研究助理與文獻回顧**：當代理需依序搜尋、閱讀、引用數十篇論文並產出綜合報告時，ACG 可保留每筆引用的來源事件（搜尋詞、頁碼、引用脈絡），讓後續段落引用時能回到原始出處驗證，減少幻覺式引用。

4. **瀏覽型任務代理（BrowseComp-Plus 類）**：需要跨多個網頁導航、擷取資訊、交叉驗證的任務，代理常在數十次頁面跳轉後忘記最初問題的具體約束。ACG 透過每次決策重新建構「需求限定視圖」，使代理在第 30 次點擊時仍記得「要找的是 2024 年後發布且引用數 > 50 的論文」。

5. **客服與工單處理代理**：當工單需經歷分類、查詢知識庫、聯繫多個部門、撰寫回覆等多步驟時，ACG 確保代理在最後回覆階段仍記得客戶原始問題與所有已收集的事證，避免回覆內容與工單主旨脫鉤。

### 實作前置條件

**資料面**
- 代理執行環境的工具呼叫日誌（tool call、tool response、observation）需可結構化記錄，包含時間戳、輸入輸出與事件 ID。
- 任務需求描述需可解析為可查詢的「需求單元」（requirement units），例如子目標、關鍵約束詞、評估標準。
- 評估資料集：建議準備至少 100 個長時程任務（>15 步）作為離線驗證集，並標註成功標準。

**運算面**
- 需具備向量檢索基礎設施（如 FAISS、Milvus 或 pgvector）以支援「任務與最新事件」種子檢索。
- 圖資料儲存（Neo4j、TigerGraph 或輕量級 NetworkX + SQLite）以保存持久化圖。
- 基礎模型 API 額度需足以支撐每步決策的額外檢索與視圖建構成本（論文顯示 ACG 會增加推論成本，需預估 1.5–3 倍 token 消耗）。
- 建議使用與論文相近規模的模型（GPT-5.6-luna 等級）以重現效益；小型模型可能因無法有效利用結構化視圖而效益打折。

**技能面**
- 具備 prompt engineering 經驗，能設計「以需求為中心」的視圖渲染模板。
- 熟悉 ReAct 或類似推理-行動框架的內部運作，以便在不替換規劃器的前提下插入 ACG 層。
- 具備圖結構設計與檢索排序（ranking）調參經驗。
- 具備評估管線建置能力，能分離「記憶機制帶來的效益」與「基礎代理本身的進步」。

### 實作步驟建議

**步驟一：建立執行證據的持久化圖骨架**
從現有 ReAct 代理的軌跡日誌出發，定義「證據單元」（evidence unit）的最小結構：`{event_id, source_event, content, timestamp, requirement_links}`。每當代理完成一次工具呼叫或觀察，就將結果包裝為一個節點並寫入圖資料庫，同時記錄它由哪個事件觸發、與哪些需求單元相關。

**步驟二：實作需求解析器**
在任務開始時，將使用者輸入解析為一組「需求單元」，每個單元包含：需求文字、優先級、相關實體、可量化標準。這些單元會作為後續每次檢索的固定種子之一。

**步驟三：設計雙種子檢索機制**
每次代理需做下一步決策時，以「任務需求單元」與「最新一次互動事件」作為雙種子，從持久化圖中檢索相關證據節點。檢索分數需結合語意相似度、需求相關度與時間近因性。

**步驟四：建構有界上下文預算下的需求中心視圖**
將檢索回的證據節點組織為一個臨時視圖，結構包含：(1) 原始需求摘要、(2) 與當前決策最相關的證據（含來源出處）、(3) 必要的周邊脈絡、(4) 預算剩餘時填入次相關證據。視圖需在 token 預算內完成渲染，超出預算的細節以摘要或省略號取代，但底層圖節點不丟棄。

**步驟五：包裝為非侵入式中介層**
將上述流程封裝為一個介面層，介接在基礎代理的「規劃器」與「工具執行器」之間：規劃器輸出候選行動前，先呼叫 ACG 取得視圖；工具執行器回傳結果後，ACG 自動將新證據寫入持久化圖。基礎代理的內部邏輯無需修改。

**步驟六：建立配對評測管線**
參考論文的「matched evaluation」設計：同一基礎模型、同一任務集，比較「ReAct 基準」與「ReAct + ACG」的差異。記錄成功率、平均步數、token 消耗、軌跡結構（節點數、邊數、檢索命中率），以便分離 ACG 帶來的效益。

**步驟七：迭代調參與部署**
根據評測結果調整：(1) 證據單元的粒度（太細則檢索成本高，太粗則丟失脈絡）、(2) 視圖預算大小（需在「資訊充足」與「成本可控」間取捨）、(3) 檢索排序權重。確認穩定後再部署至生產環境，並設置監控指標追蹤「決策漂移」發生率。

### 潛在風險與注意事項

**風險一：推論成本顯著上升**
ACG 每次決策都需執行檢索與視圖建構，會增加 token 消耗與延遲。緩解方式：對簡單、短步數任務啟用「快速路徑」（跳過 ACG）；將視圖預算設為可調參數，根據任務難度動態調整；快取高頻出現的視圖模板。

**風險二：證據圖無限膨脹**
長時程任務可能累積數千個證據節點，導致檢索效率下降。緩解方式：定期對已「結案」的事件進行摘要歸檔（但保留來源出處索引）；設定節點保留政策，例如超過 N 步未再被引用的節點降級為冷儲存。

**風險三：需求解析錯誤導致視圖偏離**
若初始需求解析有誤，後續所有視圖都會帶著錯誤的「中心」運作。緩解方式：允許使用者在任務過程中更新需求；設計需求變更偵測機制，當代理行為偏離時主動詢問使用者確認。

**風險四：將效益誤歸因於 ACG**
論文中明確警告「建立任務成功率與成本的提升」與「歸因到特定記憶機制」是兩件事。緩解方式：在評測中同時報告軌跡結構變化（節點數、檢索命中率），而非僅看成功率；進行消融實驗，關閉 ACG 各元件確認各自貢獻。

**風險五：基礎模型能力不足時效益打折**
若基礎代理本身的推理能力不足以解讀結構化視圖，ACG 的結構化資訊反而成為雜訊。緩解方式：先確認基礎模型在長上下文任務上至少有中等表現，再啟用 ACG；對小型模型考慮簡化視圖結構。

**風險六：來源出處追蹤的隱私與合規問題**
持久化圖保留了所有工具呼叫的原始輸出，可能包含敏感資料。緩解方式：對證據節點套用與底層資料相同的存取控制；設計自動脫敏機制；明確資料保留期限。

### 與其他技術的整合建議

**與 ReAct / Reflexion 整合**：ACG 不替換 ReAct 的推理-行動循環，而是在每次推理前注入結構化視圖。可與 Reflexion 互補——Reflexion 提供跨嘗試的反思，ACG 提供單次嘗試內的脈絡保持。

**與 HiAgent 整合**：HiAgent 以子目標組織工作記憶，ACG 可作為其子目標間的「證據橋樑」，將每個子目標的執行結果以來源出處形式串接，避免子目標切換時的脈絡斷裂。

**與 HippoRAG 整合**：HippoRAG 的圖關聯式檢索可作為 ACG 持久化圖的檢索引擎；ACG 則提供任務驅動的視圖建構層，雙方在「圖結構」上有共同基礎但關注點不同（HippoRAG 偏文件關聯，ACG 偏執行事件）。

**與 Self-RAG 整合**：Self-RAG 的「是否需要檢索」決策可作為 ACG 的前置過濾器——當 Self-RAG 判斷不需外部證據時，ACG 可跳過視圖建構以節省成本。

**與 LongMem 整合**：LongMem 提供跨對話的長期記憶，ACG 可作為其「單次任務內」的細粒度記憶層，兩者形成「跨任務粗粒度 + 任務內細粒度」的雙層架構。

**與監控與可觀測性系統整合**：將 ACG 的圖節點變化、檢索命中率、視圖渲染成本等指標匯入既有監控平台（如 LangSmith、Phoenix），便於追蹤「決策漂移」發生率與成本趨勢。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與介紹的前兩段，理解「為什麼長時程代理會失敗」（決策漂移）這個核心問題，再看圖 1（若有）理解 ACG 的雙層結構（持久化圖 + 臨時視圖）。不必急於理解實作細節，先建立「記憶 ≠ 摘要」、「上下文組織方式會影響表現」的直覺。

**給 AI 工程師**：重點放在第 3–4 節的方法細節與第 5 節的實驗設計，特別是「雙種子檢索」與「有界預算下的視圖渲染」這兩個可工程化的元件。建議直接動手做一個最小可行版本：以 ReAct 為基礎代理，用 NetworkX + FAISS 模擬持久化圖與檢索，先在 10 個長任務上驗證效益是否如論文所述出現，再考慮優化。

**給研究者**：論文的價值在於「將執行記憶視為演化中的關聯結構」這個觀點，以及「matched evaluation」這個嚴謹的評測設計。建議關注：(1) ACG 與 Generative Agents、HiAgent、HippoRAG 的理論定位差異；(2) 為何 ACG 選擇「不替換基礎代理」這個設計約束的影響；(3) 軌跡結構分析（節點數、邊數）能否作為「決策漂移」的量化指標，這是後續可延伸的研究方向。

**給產品經理**：ACG 解決的是「代理在多步驟任務中後段表現下滑」這個使用者會直接感受到的痛點。關鍵訊息是：此方法不改變使用者與代理的互動介面，僅提升成功率（44.5% → 50.2%）但會增加推論成本。產品決策時需權衡「成功率提升帶來的價值」與「成本增加帶來的毛利侵蝕」，並關注在 BrowseComp-Plus 類任務上的顯著效益（73.5% vs 62.4%）是否對應到自家產品的核心場景。
