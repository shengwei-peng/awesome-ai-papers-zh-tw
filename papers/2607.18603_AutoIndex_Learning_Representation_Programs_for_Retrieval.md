## ⚡ TL;DR

文件表徵常被視為靜態前置處理，而非針對檢索效能進行最佳化。
AutoIndex 透過驗證導向程式搜尋，由代理診斷失效並合成可執行轉換。
在 CRUMB 固定 BM25 下，8 項任務 Recall@100 與 nDCG@10 平均各提升逾 8%。

## 摘要翻譯

我們提出 AutoIndex，一個用於學習表徵程式（representation program）的框架：表徵程式是可執行轉換（executable transformation），能將原始文件（raw document）轉換為檢索系統（retrieval system）所使用的文件表徵（document representation）。不同於調整檢索器（retriever）、重排器（reranker）或少數前置處理超參數（preprocessing hyperparameter），AutoIndex 搜尋能在建立索引（indexing）前對文件進行切片（slice）、擴充（enrich）、正規化（normalize）、重新加權（reweight）或重組（reorganize）的程式。在每次迭代中，AutoIndex 執行驗證導向程式搜尋（validation-guided program search）：智慧代理（agent）會診斷目前程式的失效模式（failure mode）並生成候選更新（candidate update），僅保留那些能在所產生索引下提升檢索品質（retrieval quality）的更新。我們在 CRUMB（一個異質檢索任務（heterogeneous retrieval task）基準（benchmark））上評估 AutoIndex，並在所有實驗中將 BM25 固定不變。學習到的程式在全部 8 項任務中，相較於靜態全文文件 BM25 基線（static full-document BM25 baseline）均提升了召回率，Recall@100 平均提升 +8.4%，nDCG@10 平均提升 +8.3%，最大提升分別達到 Recall@100 +30.5% 與 nDCG@10 +43.6%。這些結果顯示，文件表徵不應被視為檢索開始前就已固定的前置處理選擇，而應被視為明確的最佳化目標（optimization target）。重現本研究結果的程式碼請見 https://github.com/auto-index/autoindex。

### 核心貢獻（3～5點）
- 提出 AutoIndex 框架，將文件表徵視為可學習、可執行的程式，而非檢索前固定的前置處理步驟。
- 設計驗證導向程式搜尋機制，透過智慧代理診斷失效模式並合成候選更新，再以離線指標篩選能提升檢索品質的修訂。
- 在異質檢索任務基準 CRUMB 上進行實證，於固定 BM25 的條件下，學習到的表徵程式在全部 8 項任務中均優於靜態全文文件 BM25 基線。
- 主張文件表徵應成為資訊檢索系統中明確的最佳化目標，為檢索增強生成（Retrieval Augmented Generation, RAG）管線的文件前置處理提供新方向。

### 適合對象
適合對資訊檢索、檢索增強生成（RAG）管線最佳化，以及將大型語言模型應用於程式合成感興趣的研究者與工程師；特別是關注如何在不重新訓練檢索器的前提下，透過學習文件表徵來提升檢索效能的讀者。

## 深度分析

#### 方法論解析

AutoIndex 的核心貢獻在於將 **retrieval indexing（檢索索引）** 重新定義為對 **executable document representation program（可執行文件表徵程式）** 的 **code optimization（程式碼最佳化）**。具體而言，給定一個固定的 **retriever（檢索器）**（此處為 BM25）、固定的 **ranking function（排序函數）** 與固定的 **indexing backend（索引後端）**，AutoIndex 只把 **document representation（文件表徵）** 當作可調整的變數，透過離線驗證指標反覆搜尋更好的表徵程式。

在形式化上，令 θ 表示一段可執行的表徵程式，fθ 為該程式所誘導的 **document-to-units mapping（文件到單位的映射）**。對於任一 **raw document（原始文件）** d，程式會將其轉換為一組 **indexable unit（可索引單位）**：

fθ(d) = {c1, ..., ck}

每個單位仍保留其來源文件的識別符，以便後續將單位層級的分數彙整回文件層級。將 fθ 套用至整個 **corpus（語料庫）** D 後，得到索引表徵 Cθ = ⋃d∈D fθ(d)。由於 **retriever（檢索器）** R 固定，查詢 q 對某文件 d 的分數透過 **MaxP（最大池化）** 彙整：

Sθ(q, d) = max_{c∈fθ(d)} R(q, c)

文件即依 Sθ(q, d) 排序。因為 R、彙整規則與索引後端皆固定，任何效能差異都可歸因於 θ 的差異，這正是 AutoIndex 所強調的「把 representation program（表徵程式）孤立為唯一的 **optimization target（最佳化目標）**」。

最佳化流程是一個 **iterative framework（迭代式框架）**，每輪包含四個步驟：

1. **Analysis Agent（分析代理）**：在目前的索引上執行 **retrieval failure analysis（檢索失效分析）**，診斷當前 θ 的 **failure mode（失效模式）**，例如某些查詢找不到相關文件、相關單位被不相關單位淹沒、或文件結構導致重要詞彙被切斷等。
2. **Code-Generation Agent（程式碼生成代理）**：根據診斷摘要 s(t) 與搜尋歷史 H(t)，透過 **LLM-based program synthesis（基於大型語言模型的程式合成）** 產生若干 **candidate update（候選更新）** θ'。
3. **Sandboxed Execution（沙箱執行）**：每個候選程式都在隔離環境中執行，對語料庫進行轉換並重建索引。
4. **Offline Metric-Based Selection（基於離線指標的選擇）**：在 **validation set（驗證集）** Q_val 上計算 **offline metric（離線指標）** J(θ')，例如 **Recall@100** 與 **nDCG@10**，只保留能提升目標函數的更新作為下一輪的 incumbent。

搜尋空間涵蓋 **slice（切片）**、**enrich（擴充）**、**normalize（正規化）**、**reweight（重新加權）** 與 **reorganize（重組）** 等操作。這些操作可以組合：例如把長文件切成 **chunk of text（文字區塊）** 並在每個區塊附加 **attached context（附加脈絡）**、為文件加入 **metadata（中繼資料）**、對特定 **normalized field（正規化欄位）** 調高權重、或以預測查詢擴充文件內容。由於程式是通用程式碼，理論上可表達比傳統 **chunk size（區塊大小）**、**overlap（重疊）**、**normalization rule（正規化規則）** 等 **preprocessing hyperparameter（前置處理超參數）** 更豐富的轉換。

值得注意的是，一旦學習完成，最終的 representation program（表徵程式）只在 **indexing time（索引時間）** 套用一次，後續檢索與排序不再呼叫 LLM，也不需 **online feedback（線上回饋）**、**retriever fine-tuning（檢索器微調）** 或 **embedding update（嵌入更新）**。這讓 AutoIndex 在部署階段保持與傳統 BM25 系統相近的推理成本，僅在離線學習階段付出搜尋與索引重建的開銷。

#### 實驗數據解讀

論文在 **CRUMB（Complex Retrieval Unified Multi-task Benchmark，複雜檢索統一多工基準）** 上進行評估，並將 BM25 固定為 **fixed retriever（固定檢索器）**。CRUMB 包含 8 個 **heterogeneous retrieval task（異質檢索任務）**，涵蓋不同文件長度、結構與查詢特性，因此能檢驗 representation program（表徵程式）在多樣情境下的適應能力。

主要結果相當顯著：相較於 **static full-document BM25 baseline（靜態全文文件 BM25 基線）**（即不對文件做任何轉換，直接將整份文件索引），AutoIndex 在全部 8 個任務上都提升了 **recall（召回率）**。平均而言，**Recall@100** 提升 +8.4%，**nDCG@10** 提升 +8.3%；最大單一任務增益分別達到 Recall@100 +30.5% 與 nDCG@10 +43.6%。

這幾個數字有以下幾層意義：

- **Recall@100** 衡量前 100 筆結果中包含多少相關文件，**nDCG@10** 衡量前 10 筆結果的排序品質。兩者同時提升，表示學到的表徵程式不僅讓檢索器找回更多相關文件，也讓排名更靠前。
- 由於 **retriever（檢索器）**、**ranking function（排序函數）** 與 **indexing backend（索引後端）** 完全固定，所有進步都只能來自於文件表徵的改變。這強化了論文的主張：文件表徵本身就是一個被低估的 **optimization target（最佳化目標）**。
- 最大增益高達 30%–40%，暗示在某些任務中，靜態全文索引會嚴重遺失 **lexical cue（詞彙線索）** 或讓重要資訊被冗長文件稀釋；透過適當的切片、擴充或重組，BM25 仍能發揮遠超預期的效能。
- 平均增益約 8% 雖不如最大值驚人，但在 BM25 已相當成熟、且未更動任何排序模型的前提下，這樣的跨任務穩定提升具有實務價值。

不過，從現有片段也能看出實驗報告的侷限。論文並未詳細說明每個任務的性質、學到的程式具體長相、搜尋過程中評估了多少 candidate update（候選更新）、每次索引重建的計算成本、索引大小變化、或不同 **offline metric（離線指標）** 之間的權衡。此外，所有實驗皆以 BM25 為固定檢索器，尚不清楚同樣學到的 representation program（表徵程式）是否能直接遷移到 **dense architecture（密集架構）** 或 **hybrid architecture（混合架構）** 的檢索器上。

#### 與現有研究的比較

AutoIndex 與過去研究的主要差異在於「最佳化對象」與「搜尋方式」。

相較於傳統的 **adaptive chunking（適應性切片）** 與文件表徵研究，過去方法多半圍繞 **chunk size（區塊大小）**、**overlap（重疊）**、標題是否加入、或固定 **metadata template（中繼資料範本）** 等 **preprocessing hyperparameter（前置處理超參數）** 進行網格搜尋或手動調整。AutoIndex 則把這些選擇統一納入可執行程式空間，並以 **validation-guided program search（驗證導向程式搜尋）** 自動探索，減少對人工啟發式的依賴。

與 **late chunking（晚期切片）**、kNN-LM 風格的 token-level 或 chunk-level 檢索相比，這些方法通常需要在檢索時對每份文件進行額外編碼或 LLM 推理。AutoIndex 選擇在 **indexing time（索引時間）** 一次性完成轉換，避免在線上檢索時呼叫 LLM，這對延遲敏感或成本敏感的應用更具吸引力。

在 **index enrichment（索引擴充）** 領域，Doc2Query 透過預測查詢擴充文件，但可能引入幻覺或低品質擴充；近期 LLM-based 方法會加入摘要、正規化、擷取事實或理由；Document Optimization 與 RL-Index 則透過黑箱回饋或強化學習學習特定類型的文件改寫。這些方法通常學習「某一種」轉換模型，而 AutoIndex 搜尋的是「可組合多種轉換的通用程式」，並且始終保持 **retriever（檢索器）** 與 **ranking function（排序函數）** 不變，從而更清楚地把效能變化歸因於文件表徵本身。

至於 **agentic program optimization（代理式程式最佳化）** 與 RAG **pipeline optimization method（管線最佳化方法）**，過去研究多聚焦於改進 retriever（檢索器）、**reranker（重排器）**、**prompt（提示）** 或 **generation component（生成元件）** 的組合。AutoIndex 則把焦點前移到「進入檢索器之前的 pre-indexing representation program（索引前表徵程式）」，這是一個相對被忽略但影響深遠的環節。

然而，AutoIndex 也存在可預見的限制：

- **計算成本**：每個 candidate update（候選更新）都需要執行程式、重建索引並在驗證集上評估，對大型語料庫而言可能非常昂貴。
- **程式正確性與安全性**：雖然論文提到 **sandboxed execution（沙箱執行）**，但 LLM 生成的程式仍可能產生非預期行為、資訊遺失或索引膨脹。
- **驗證集過擬合**：以 **offline metric（離線指標）** 為目標反覆搜尋，可能過度適應 validation set（驗證集）的查詢分布。
- **僅驗證 BM25**：目前結果僅能證明對 BM25 有效，對 **dense architecture（密集架構）**、**hybrid architecture（混合架構）** 或 **late-interaction architecture（晚期互動架構）** 的適用性仍待驗證。
- **缺乏理論保證**：目前框架屬於經驗性搜尋，尚未提供關於表徵轉換何時會提升或損害檢索效能的理論分析。

#### 可重現性評估

論文作者已將程式碼釋出於 https://github.com/auto-index/autoindex，這是提升 **reproducibility（可重現性）** 的重要基礎。CRUMB 作為公開 **benchmark（基準）**，理論上可由其他研究者取得並重跑實驗。由於檢索器固定為 BM25，不涉及神經模型權重釋出問題；但 AutoIndex 的 **analysis agent（分析代理）** 與 **code-generation agent（程式碼生成代理）** 依賴 LLM，若論文使用閉源 API（如 GPT-4 系列），則重現結果會受到 API 版本、**prompt（提示）** 設計與取樣隨機性的影響。

目前從提供的片段無法判斷作者是否一併釋出了：

- 完整的 agent **prompt（提示）** 與 few-shot 範例；
- 搜尋歷史 H(t) 與每輪產生的 candidate update（候選更新）；
- 最終學到的 representation program（表徵程式）內容；
- 確切的 CRUMB 資料切分、種子設定與超參數；
- 每次迭代所需的計算資源與總執行時間；
- 沙箱環境的詳細配置與安全限制。

若這些資訊能在未來版本中補充，將大幅提升研究的可重現性與可比較性。特別是釋出「學到的程式」本身，能讓其他研究者直接檢視哪些文件轉換對哪些任務有效，而無需重新執行昂貴的搜尋過程。

#### 未來研究方向

AutoIndex 開啟了幾個值得後續探索的方向：

1. **跨檢索器泛化**：將學到的 representation program（表徵程式）同時或分別應用於 **dense architecture（密集架構）**、**hybrid architecture（混合架構）**、**late-interaction architecture（晚期互動架構）** 與學習式 **reranker（重排器）**，檢驗表徵最佳化是否與檢索模型獨立，或是否存在協同效應。
2. **聯合最佳化**：目前只最佳化文件表徵，未來可考慮同時微調 **retriever（檢索器）**、嵌入模型或排序函數，形成 representation–retriever 聯合學習框架。
3. **降低搜尋成本**：開發 surrogate model（代理模型）、partial index update（部分索引更新）、early stopping（早期停止）或 bandit-based search（強盜式搜尋），以減少每次 candidate update（候選更新）都需重建完整索引的開銷。
4. **多目標最佳化**：除了 Recall@100 與 nDCG@10，同時納入索引大小、查詢延遲、LLM 呼叫次數與能耗，學習在效能與成本之間權衡的 Pareto 表徵程式。
5. **理論理解**：建立文件表徵轉換對 BM25 或神經檢索器效能影響的理論框架，例如分析何種 slicing（切片）或 enrichment（擴充）能保證 recall 不下降，以及資訊遺失與索引膨脹之間的 trade-off（權衡）。
6. **線上適應**：將 AutoIndex 從離線驗證導向擴展到具備 **online feedback（線上回饋）** 的持續學習系統，使表徵程式能隨使用者查詢分布漂移而自動更新。
7. **可解釋性與安全約束**：為生成的程式加入語意約束，避免過度刪減、幻覺擴充或引入偏見；同時提供人類可讀的失效分析報告，讓工程師理解為何某個轉換有效。
8. **與 RAG 管線整合**：把 AutoIndex 納入更廣泛的 **Retrieval Augmented Generation（檢索增強生成）** **pipeline optimization method（管線最佳化方法）**，同時搜尋文件表徵、retriever（檢索器）、reranker（重排器）與 **prompt（提示）**，以端到端方式提升下游生成品質。

## 論文問答

**Q1：AutoIndex 主要想解決什麼問題？**

A：AutoIndex 針對的是資訊檢索中「文件表徵」這個核心卻常被低估的環節。在文件能被搜尋或排序之前，必須先被轉換成可索引單位，例如文字區塊、附加脈絡、正規化欄位或中繼資料，但這些選擇通常被當成靜態基礎設施，而非最佳化目標。AutoIndex 主張應該直接學習可執行的文件表徵程式，讓檢索器看到的表示方式本身成為可以被改進的對象。

**Q2：現有的檢索模型研究與 RAG 管線最佳化方法為何無法充分解決這個問題？**

A：現有研究大多聚焦於改進配對函數，例如稀疏、密集、混合或晚期互動架構，或是搜尋檢索器、重排器、提示與生成元件的最佳組合。然而，這些方法通常把語料庫表徵視為手動指定的前置處理，或僅從預先定義的設定中挑選，並未直接學習能將原始文件轉換為索引單位的可執行轉換。因此，文件在進入檢索器之前的切片、擴充、正規化與重組等潛在改進空間，往往被忽略。

**Q3：為什麼文件表徵應該被視為明確的最佳化目標？**

A：文件表徵決定了哪些詞彙線索、附加脈絡與文件結構會在檢索時被看見，直接影響召回率與排序品質。如果表徵設計不良，即使檢索器與重排器再強大，也可能因為遺失關鍵資訊而無法找到相關文件。AutoIndex 的實驗顯示，在固定 BM25 檢索器的情況下，僅透過學習更好的表徵程式就能顯著提升檢索品質，證明表徵本身值得被直接最佳化。

**Q4：什麼是 AutoIndex 中的「表徵程式」？**

A：表徵程式是一種可執行文件表徵程式，負責將原始文件映射為一組可索引單位。它可以對文件進行切片、擴充、正規化、重新加權或重組，而每個產生的單位仍保留其來源文件的識別碼。透過執行這個程式，整個語料庫會被轉換成特定的索引表示，並由固定的檢索器進行搜尋。

**Q5：AutoIndex 的核心最佳化迴路是如何運作的？**

A：在每一次迭代中，AutoIndex 會先根據目前索引上的檢索結果，由分析代理診斷失效模式，再由程式碼生成代理提出候選更新。每個候選程式都會被沙箱執行、建立索引，並在驗證集上以離線指標評估檢索品質。只有能夠真正改善目標函數的更新才會成為下一個 incumbent，形成驗證導向程式搜尋。

**Q6：AutoIndex 在設計上有哪些關鍵創新與選擇？**

A：AutoIndex 的關鍵設計是將檢索器、排序函數與索引後端全部固定，從而把效能差異完全歸因於表徵程式。它不只調整少數前置處理超參數，而是搜尋一個廣泛的程式空間，讓智慧代理根據檢索失效分析自動合成修訂程式。此外，整個學習過程使用離線指標，不需要線上回饋，學成的程式只在索引時間套用一次，檢索時無需再呼叫大型語言模型。

**Q7：AutoIndex 在哪些實驗設定下進行評估？**

A：論文使用 CRUMB（Complex Retrieval Unified Multi-task Benchmark）進行評估，這是一個包含多種異質檢索任務的基準。實驗涵蓋 8 個不同的任務，並在所有實驗中固定使用 BM25 作為檢索器。這樣的設定能夠清楚檢驗文件表徵程式本身對檢索品質的貢獻，而不受檢索器改變的干擾。

**Q8：AutoIndex 的主要實驗結果是什麼？**

A：在全部 8 個任務中，AutoIndex 學得的表徵程式都優於靜態全文文件 BM25 基線。平均而言，Recall@100 提升了 8.4%，nDCG@10 提升了 8.3%；在部分任務上，最大增益分別達到 Recall@100 提升 30.5% 與 nDCG@10 提升 43.6%。這些進步完全來自文件表徵的學習，沒有進行檢索器微調、嵌入更新或線上回饋。

**Q9：從實驗設計可以推論出哪些重要的消融或設計意涵？**

A：由於檢索器與排序函數始終固定，實驗結果明確顯示表徵程式的改變是效能提升的唯一來源。這也說明文件表徵的設計與檢索模型本身的改進同樣重要，兩者可以互補。此外，透過驗證集上的離線指標進行選擇，有助於避免過度擬合種子查詢，並確保學得的程式對未見查詢具有泛化能力。

**Q10：AutoIndex 適合應用在哪些實務場景？**

A：AutoIndex 特別適合企業內部搜尋、法律或醫療文件檢索，以及檢索增強生成管線等情境，因為這些場域的文件格式異質且內容複雜。當組織已經固定使用某個檢索器或嵌入模型，但希望進一步提升召回率時，可以直接最佳化文件表徵程式。它也能針對不同語料庫或任務，自動學習最適合的區塊切分、擴充策略與欄位結構。

**Q11：在實際產品化時，需要考慮哪些因素？**

A：首先，候選程式必須在沙箱環境中執行，以避免惡意或不穩定程式影響系統。其次，每次評估都需要重建索引，這在大型語料庫上會帶來可觀的計算成本，因此需要有效的搜尋策略來減少評估次數。最後，產品團隊需要提供具代表性的驗證查詢與離線指標，並理解學習階段的一次性成本與後續索引時間的應用成本之間的權衡。

**Q12：AutoIndex 對資訊檢索領域可能帶來什麼影響？**

A：AutoIndex 將研究焦點從單純改進檢索模型，擴展到「文件表徵也應該被學習與最佳化」這個新視角。它挑戰了把前置處理視為固定啟發式的傳統假設，並提出將檢索索引視為程式碼最佳化問題的框架。未來這個方向可以與密集檢索、混合檢索或重排器結合，進一步釋放整體檢索系統的潛力。

**Q13：AutoIndex 有哪些已知的限制？**

A：一個主要限制是每次候選程式的評估都需要重建索引，當語料庫龐大或程式空間廣泛時，搜尋成本會相當高。此外，整個方法依賴驗證集查詢的品質與涵蓋度，若驗證集不具代表性，學得的程式可能無法泛化。目前論文也僅在 BM25 這類稀疏檢索器上進行評估，尚未驗證於密集或混合檢索器。

**Q14：AutoIndex 在哪些情況下可能會失敗或表現不佳？**

A：如果驗證查詢無法涵蓋真實任務分布，學得的表徵程式可能會過度擬合特定查詢類型，導致在實際應用中效果下降。過度積極的擴充或重組也可能遺失重要上下文，甚至引入錯誤資訊，反而傷害檢索品質。此外，由於程式搜尋是離散的，智慧代理可能陷入區域最佳解，無法找到全局最佳的表徵程式。

**Q15：未來可以朝哪些方向延伸 AutoIndex？**

A：未來可以將 AutoIndex 擴展到密集檢索器、混合檢索器，甚至多模態文件表徵的學習。也可以結合線上回饋或使用者點擊訊號，讓表徵程式能隨時間適應真實使用行為。另外，發展更高效的搜尋演算法、探索學得程式在不同語料庫間的遷移能力，以及同時最佳化表徵程式與檢索器參數，都是值得深入研究的方向。

## 實務應用指南

## 適用場景

1. **企業內部知識庫與 RAG 系統**：當語料橫跨 Wiki、Confluence、PDF 手冊、票務系統與程式碼倉儲，且文件長度與結構差異極大時，AutoIndex 可學習最適合的切片、附加脈絡與中繼資料策略，而非手動調整區塊大小與重疊量。
2. **法律、醫療與技術長文件檢索**：這類文件通常具有嚴謹的章節結構與專業術語。AutoIndex 可學習保留標題脈絡、正規化實體名稱，並將定義、條文與案例適當重組為可索引單位。
3. **電商與產品目錄搜尋**：透過學習重組產品規格、擴充屬性同義詞、調整欄位權重，AutoIndex 能讓稀疏檢索器更有效地配對使用者查詢與商品欄位。
4. **技術文件與 API 文件檢索**：可學習如何將程式碼範例、參數說明與敘述文字適當配對，避免單純按字數切片導致語意斷裂。
5. **多語言或跨語料檢索**：AutoIndex 可學習正規化規則與跨語言擴充策略，統一不同來源文件的表徵方式。

## 實作前置條件

- **資料條件**：
  - 原始文件語料庫（支援文字或可解析為文字的格式）。
  - 種子查詢與驗證查詢集合，並具備相關性標註（qrels），用於計算 Recall@100、nDCG@10 等離線指標。
  - 建議至少有數百至數千筆驗證查詢，才能穩定評估候選程式。

- **運算條件**：
  - 能夠多次重建索引的運算資源（CPU 或輕量 GPU 即可，因為檢索器固定為 BM25）。
  - 大型語言模型呼叫預算，用於分析代理與程式碼生成代理。
  - 沙箱執行環境，確保候選程式不會影響主機系統。

- **技能條件**：
  - Python 程式開發與資料工程能力。
  - 資訊檢索基礎知識（BM25、召回率、nDCG）。
  - 大型語言模型提示工程經驗，以便理解與調整代理行為。
  - 具備索引後端（如 Elasticsearch、Lucene、Pyserini）的操作經驗。

## 實作步驟建議

1. **建立靜態基線**：使用固定檢索器（如 BM25）對全文文件建立索引，計算 Recall@100 與 nDCG@10，作為後續比較基準。
2. **定義表徵程式空間**：明確允許候選程式執行的操作，例如切片、擴充、正規化、重組、重新加權，並提供可呼叫的函式庫與範例。
3. **準備驗證集**：整理種子查詢與相關性標註，確保涵蓋主要失效模式與任務類型。
4. **啟動迭代最佳化迴圈**：
   - 分析代理診斷目前索引下的檢索失效模式。
   - 程式碼生成代理根據診斷結果提出多個候選更新。
   - 在沙箱中執行每個候選程式，重建索引，並以離線指標評估。
   - 僅保留能提升目標函數的程式作為下一輪的現任方案。
5. **收斂與部署**：當驗證指標不再顯著提升時，選出最佳表徵程式，並在索引時間應用於新進文件。
6. **監控與再訓練**：定期收集新的查詢與標註，重新執行驗證導向程式搜尋，以適應語料與查詢分布的變化。

## 潛在風險與注意事項

- **索引重建成本高昂**：每個候選程式都需要重新執行、建立索引並評估，可能消耗大量時間與運算資源。建議先縮小驗證集規模進行快速篩選，再對 promising 的候選進行完整評估。
- **生成程式碼的安全性**：大型語言模型可能產生非預期或惡意程式碼。務必在沙箱中執行，限制檔案系統、網路與系統呼叫權限。
- **過度擬合驗證集**：程式搜尋可能針對驗證集過度調整。應保留獨立測試集、使用多個離線指標，並對程式複雜度施加懲罰。
- **可解釋性與維護**：學習到的表徵程式可能難以理解，需建立版本控制、文件化與人工審查機制。
- **資料隱私與合規**：若使用雲端大型語言模型，原始文件內容可能外洩。建議對敏感資料進行脫敏，或採用本地部署模型。

## 與其他技術的整合建議

- **與現有 RAG 管線整合**：AutoIndex 專注於索引前的文件表徵，不更動檢索器、重排器或生成器，因此可無縫嵌入既有 RAG 架構，作為索引階段的最佳化模組。
- **與密集檢索器搭配**：雖然論文以 BM25 為固定檢索器，但「學習輸入給檢索器的可索引單位」這一概念同樣適用於 dense retriever，可學習最適合嵌入模型的文件表徵。
- **與重排器協同**：表徵程式可針對重排器的輸入特性進行最佳化，例如保留重排器需要的結構化欄位或上下文。
- **與 MLOps 與資料管線整合**：將表徵程式納入持續整合與部署流程，與索引重建作業排程結合，實現自動化的索引更新與品質回歸測試。

## 給不同背景讀者的閱讀建議

- **初學者**：建議先掌握文件切片、BM25、Recall 與 nDCG 等基本概念，再把 AutoIndex 理解為「自動幫你做前置處理 A/B 測試的框架」，重點放在它為什麼把文件表徵當成可最佳化的目標。

- **AI 工程師**：請聚焦於分析代理與程式碼生成代理的協作迴圈、沙箱執行機制，以及離線指標如何驅動候選選擇。思考如何將這個框架落地到現有 RAG 或企業搜尋系統中，並處理索引重建成本與安全問題。

- **研究人員**：本文的核心貢獻在於將檢索索引形式化為「可執行文件表徵程式」的程式碼最佳化問題。建議對照 adaptive chunking、index enrichment 與 agentic program optimization 等研究方向，評估此形式化框架的通用性與理論限制。

- **產品經理**：AutoIndex 是一種發生在索引階段的一次性最佳化，能在不改動使用者介面或線上延遲的前提下提升檢索品質。評估導入時，請關注驗證資料品質、索引重建預算，以及學習到的程式是否易於維護與解釋。
