# SWE-at-Scale：從歷史錯誤修復進行可擴展議題合成

**原文標題：** SWE-at-Scale: Scalable Issue Synthesis from Historical Bug Fixes  
**作者：** Silin Chen、Zihan Zhang、Xiaodong Gu 等 10 位作者  
**發布日期：** 2026-10-15

## ⚡ TL;DR

現有 SWE 基準受限於真實議題數量稀少與人工策展成本高，且合成方法缺乏真實錯誤機制。
本文提出 SWE-at-Scale 框架，反轉真實修復以建立錯誤誘導監督，學習可重用的錯誤模式。
實驗顯示其任務比合成基準更真實多樣，對程式碼代理更具挑戰，且每檔案可穩定擴展至 200 次生成。

## 摘要翻譯

隨著程式碼代理（coding agents）的能力日益提升，穩健的評估需要更廣泛且更多樣化的可驗證軟體工程（SWE）任務供應。然而，真實世界的任務受到議題回報（issue reporting）的自然頻率以及人工策展（manual curation）的高昂成本所限制。此外，現有的合成方法主要依賴大型模型（large models）的預訓練知識（pretrained knowledge）結合啟發式提示（heuristic prompting），往往無法捕捉軟體故障（software failures）的真實且複雜的機制。為了指數級地擴展 SWE 任務的生產，我們引入了 SWE-at-Scale，這是一個透過逆向工程（reverse-engineering）真實世界軟體修復來自動合成逼真議題的框架。我們的核心洞察在於，歷史修復蘊含了錯誤形成（bug formation）的深層機制性知識（mechanistic knowledge）：反轉修復（inverting a fix）將修復監督（repair supervision）轉化為植基於實際開發情境（development scenarios）的錯誤誘導監督（bug-induction supervision）。SWE-at-Scale 將這些學習到的錯誤模式（bug patterns）轉移到新穎的程式碼情境（novel code contexts）中，反覆抽樣（sampling）多樣化的錯誤類型學（bug typologies）以建構可執行的 SWE 任務（executable SWE tasks）。大量實驗顯示，SWE-at-Scale 比目前的合成基準方法（synthesis baselines）產生更多樣化且更逼真的 SWE 任務，同時對最先進的（state-of-the-art）程式碼代理構成更大的挑戰。值得注意的是，SWE-at-Scale 能從單一程式碼情境產生不同的錯誤類型，即使每檔案生成數（generations per file）高達 200 次，錯誤多樣性（bug diversity）仍能穩健擴展。總體而言，SWE-at-Scale 將有限真實修復（finite real-world fixes）轉化為可重用監督（reusable supervision），用於可擴展地合成逼真、多樣且具挑戰性的 SWE 任務。

### 核心貢獻（3～5點）
- 提出 SWE-at-Scale 框架，透過逆向工程真實世界的軟體修復，自動合成具備真實感且可驗證的 SWE 任務，突破議題回報頻率與人工策展成本對任務供應的限制。
- 提出「反轉修復」的核心洞察：將歷史修復中的修復監督轉化為錯誤誘導監督，從中萃取錯誤形成的機制性知識，並轉移至新穎的程式碼情境。
- 透過反覆抽樣多樣化的錯誤類型學，實現可擴展合成（scalable synthesis），即使每檔案生成數高達 200 次，錯誤多樣性仍能穩健擴展。
- 實驗證明 SWE-at-Scale 生成的任務比現有合成基準方法更多樣、更逼真，且對最先進的程式碼代理構成更大挑戰。

### 適合對象
從事軟體工程自動化、程式碼代理（coding agents）研發、基準測試（benchmark）設計、合成資料生成（synthetic data generation）與大型語言模型評估的研究者與工程師；尤其適合關注 SWE-bench Verified 等儲存庫層級軟體工程（repository-level software engineering）評測、以及希望以有限真實修復資料擴展訓練與評測規模的團隊。

## 深度分析

#### 方法論解析

SWE-at-Scale 提出了一種創新的「反轉學習」(reverse-learning) 範式，將傳統的修復監督 (repair supervision) 轉化為錯誤誘導監督 (bug-induction supervision)，其方法論可從兩個階段進行深入剖析。

**第一階段：從真實修復中學習（Learn From Real Fixes）**

此階段的核心在於「雙重監督構建」(Dual Supervision Construction)。給定一個真實修復 (Real Fix)，系統同時包含三個元素：錯誤程式碼 (Buggy Code)、開發者修復 (Developer Fix) 與黃金程式碼 (Golden Code)。SWE-at-Scale 透過反轉修復 (inverting a fix) 過程，將黃金程式碼作為起點，生成對應的錯誤誘導補丁 (Bug-Inducing Patch)，並建構出所謂的「反向修復語料庫」(Reverse-Fix Corpus)。此語料庫包含兩種監督信號：

1. **補丁監督 (Patch Supervision)**：直接學習從程式碼檔案到錯誤誘導補丁的映射關係，用於訓練 SWE-at-Scale 模型。
2. **錯誤模式監督 (Bug Pattern Supervision)**：學習從程式碼檔案到自然語言描述的錯誤模式 (Bug Pattern) 的映射，這些模式說明了應如何修改目標程式碼以誘導錯誤，用於訓練 SWE-at-Scale+ 模型。

這種雙重監督設計的精妙之處在於：它將「如何修復錯誤」這一向後推理的過程，轉化為「如何引入錯誤」這一向前的生成過程，從而將有限的真實修復轉化為可重用的監督資源。

**第二階段：雙模式錯誤合成（Dual-Mode Bug Synthesis）**

此階段將第一階段學到的轉換模式應用於新的黃金儲存庫 (Golden Repository)，透過兩個互補的合成模型運作：

- **SWE-at-Scale（直接補丁生成模式）**：直接從黃金程式碼生成錯誤誘導補丁，並透過 `git apply` 將其應用於黃金儲存庫以產生錯誤版本。
- **SWE-at-Scale+（錯誤模式實現模式）**：先以自然語言形式生成錯誤模式，再由「錯誤模式執行器」(Bug Pattern Executor) 將其實作為程式碼變更。

兩種模式的差異在於抽象層級：前者直接操作程式碼層級，後者先在高層語意層面規劃錯誤模式，再進行低層實作。這種設計借鑒了「規劃-執行」(plan-and-execute) 的代理架構思想，有助於提升生成錯誤的多樣性與可控性。

**訓練配置**

模型以 Qwen3.5-9B 作為骨幹網路 (backbone)，在來自 688 個儲存庫的 13,407 個真實修復轉換上進行訓練。訓練資料涵蓋九大錯誤類型（如介面、邏輯、邊界等）以及十大領域類別（如 Web/API、科學計算、機器學習、開發工具等），呈現出良好的領域與錯誤類型覆蓋廣度。

#### 實驗數據解讀

**錯誤類型分佈的真實性驗證**

圖 1 呈現了四種資料來源的錯誤類型分佈：SWE-bench Verified（真實議題）、SWE-smith（合成議題）、SWE-at-Scale 與 SWE-at-Scale+（合成議題）。從分佈形態觀察：

- SWE-bench Verified 中「邏輯」(Logic) 類型佔 59%，「介面」(Interface) 佔 15%，呈現出真實軟體開發中邏輯錯誤為主的特性。
- SWE-smith 的分佈明顯偏向「介面」(65%)，而「邏輯」僅佔 9%，反映出基於啟發式提示 (heuristic prompting) 的方法容易過度生成表面性的介面變更。
- SWE-at-Scale 與 SWE-at-Scale+ 的分佈則更接近真實基準，「邏輯」分別佔 34% 與 37%，「介面」分別佔 10% 與 12%，呈現出更平衡且更貼近真實的錯誤類型組合。

這項結果驗證了核心假設：透過反轉真實修復學得的錯誤模式，比純粹依賴預訓練知識 (pretrained knowledge) 與啟發式提示更能捕捉真實軟體故障的機制性知識 (mechanistic knowledge)。

**人類評估結果**

在與 SWE-bench Verified 真實議題的成對比較中，人類評估者在 55.9% 的案例中選擇 SWE-at-Scale 生成的錯誤「更可能發生於真實軟體開發中」，而 SWE-at-Scale+ 的對應比例更高，達到 61.2%。這顯示出錯誤模式的中間表示形式有助於生成更自然的錯誤變體。

**多樣性與可擴展性**

論文宣稱 SWE-at-Scale 能從單一程式碼情境生成不同的錯誤類型，且錯誤多樣性在每檔案 200 次生成 (generations per file) 的規模下仍能穩健擴展。這是一項重要的實驗結果，因為現有合成方法在重複生成時容易陷入模式坍縮 (mode collapse)，反覆產生相似的錯誤變體。SWE-at-Scale 透過從有限真實修復中學得可重用的錯誤分佈 (reusable distribution)，實現了「有限真實修復 → 大量多樣合成任務」的轉換。

**對程式碼代理的挑戰性**

實驗橫跨四個解析模型 (resolution models) 進行評估，結果顯示 SWE-at-Scale 生成的任務對最先進的 (state-of-the-art) 程式碼代理構成顯著挑戰。雖然具體數字在提供的文本中未完整呈現，但這暗示了合成任務的難度並未因自動化而降低，反而可能因為更貼近真實錯誤機制而更具鑑別力。

**訓練資料特性**

圖 3 顯示訓練資料中錯誤類型分佈以「邏輯」(47.6%) 為主，「介面」(17.1%) 次之，「邊界」(9.9%) 與「檔案系統」(9.4%) 隨後。圖 4 則顯示領域分佈以 Web/API (20.9%)、科學計算 (16.2%)、機器學習 (14.8%) 為主，呈現出多元的領域覆蓋。

#### 與現有研究的比較

**與 SWE-smith 的比較**

SWE-smith (Yang et al., 2025) 透過提示 LLM 修改選定的程式碼實體 (code entities) 來注入錯誤，屬於「提示驅動」(prompt-driven) 的合成方法。SWE-at-Scale 與其相比的關鍵差異在於：

- **監督來源**：SWE-smith 依賴 LLM 的預訓練錯誤生成知識；SWE-at-Scale 則從真實修復中學習專門的錯誤誘導模式。
- **多樣性**：SWE-smith 在重複生成時容易重訪熟悉的錯誤模式；SWE-at-Scale 透過學得的錯誤分佈實現更穩健的多樣性擴展。
- **真實性**：SWE-smith 的錯誤類型分佈偏向介面錯誤；SWE-at-Scale 的分佈更貼近真實基準。

**與 SWE-Synth 的比較**

SWE-Synth (Pham et al., 2025) 採用基於 LLM 的元件重新實作 (component re-implementation) 並結合測試過濾。SWE-at-Scale 的方法論更為直接：直接從程式碼到錯誤補丁的端到端映射，避免了重新實作帶來的複雜性與不確定性。

**與 BugPilot 的比較**

BugPilot (Sonwane et al., 2025) 探索功能新增 (feature addition) 與行為回歸 (behavioral regression) 作為合成錯誤的來源。SWE-at-Scale 則專注於從現有修復中反轉學習，兩者代表了不同的合成哲學：BugPilot 偏向「從零生成」，SWE-at-Scale 偏向「從真實中提煉」。

**SWE-at-Scale 與 SWE-at-Scale+ 的互補性**

兩種變體並非簡單的優劣關係，而是呈現互補特性：

- SWE-at-Scale 直接生成補丁，效率較高，適合大規模批次合成。
- SWE-at-Scale+ 先生成錯誤模式再實作，可解釋性更強，且人類評估中獲得更高的真實性偏好（61.2% vs 55.9%）。

**侷限性分析**

儘管 SWE-at-Scale 展現出多項優勢，仍存在以下侷限：

1. **訓練資料偏差**：訓練資料以 Python 生態為主（從儲存庫數量與領域分佈推測），對其他程式語言的泛化能力未經驗證。
2. **錯誤類型覆蓋**：雖然涵蓋九大錯誤類型，但對於並發錯誤、安全漏洞等需要深層語意理解的錯誤類型，生成品質可能受限。
3. **測試基礎設施依賴**：合成任務仍需仰賴儲存庫的測試基礎設施，對於測試覆蓋不足的程式碼，錯誤的可驗證性會下降。
4. **領域轉移風險**：從 688 個儲存庫學得的錯誤模式，在面對高度專業化領域（如嵌入式系統、形式化驗證）時可能表現不佳。

#### 可重現性評估

**程式碼與模型權重的可用性**

根據論文提供的資訊，SWE-at-Scale 框架基於 Qwen3.5-9B 骨幹網路，並在 13,407 個真實修復轉換上訓練。然而，論文中未明確說明是否會開源：

- 訓練程式碼與推論管線
- 預訓練的錯誤誘導模型權重
- 反向修復語料庫 (Reverse-Fix Corpus)
- 合成任務的評估基準

**資料集可獲得性**

訓練資料來自 688 個公開儲存庫的真實修復，這些儲存庫本身可透過 GitHub 取得，但「反轉修復」的具體轉換對（黃金程式碼 → 錯誤誘導補丁）需要依據論文中描述的流程重新生成。論文中提及的「行號標記檔案」(Line-Numbered File) 等中間產物，其生成細節需從附錄或補充材料中確認。

**可重現性的關鍵變數**

影響可重現性的關鍵因素包括：

1. **儲存庫快照的時間點**：真實修復的選取需要固定到特定 commit，否則訓練資料會隨時間漂移。
2. **錯誤類型分類標準**：九大錯誤類型的具體定義與標註流程需要清晰說明。
3. **評估指標的計算方式**：人類評估的具體協議、成對比較的抽樣策略等。

**建議的補強措施**

為提升可重現性，建議作者：

- 釋出完整的訓練資料與模型權重
- 提供標準化的評估腳本與基準
- 公開錯誤類型分類的標註指南
- 詳細記錄儲存庫選取與修復過濾的標準

#### 未來研究方向

**多語言與跨領域擴展**

當前方法主要針對 Python 生態系統，未來可探索：

- 將反轉學習範式擴展至 Java、JavaScript、C++ 等主流語言
- 針對特定領域（如系統程式設計、嵌入式系統、分散式系統）訓練領域專門的錯誤誘導模型
- 探索跨語言的錯誤模式遷移學習

**錯誤模式的階層化抽象**

SWE-at-Scale+ 已初步引入自然語言錯誤模式作為中間表示，未來可進一步：

- 建構多層次的錯誤模式抽象（從語法層、語意層到架構層）
- 結合程式分析技術（如抽象語法樹、控制流圖）強化錯誤模式的結構化表示
- 探索錯誤模式與程式碼變更之間的形式化對應關係

**與程式碼代理的閉環互動**

SWE-at-Scale 與程式碼代理的關係目前是單向的（合成 → 評估），未來可探索：

- 利用程式碼代理的失敗案例作為新的錯誤模式來源，形成「代理失敗 → 模式學習 → 任務合成」的閉環
- 設計主動學習機制，根據代理的弱點動態調整合成任務的難度與類型
- 將錯誤誘導模型與程式碼代理進行對抗式訓練 (adversarial training)

**可驗證性與測試生成**

合成任務的可執行性仰賴現有測試基礎設施，未來可：

- 結合自動化測試生成技術，為合成任務產生更全面的驗證測試
- 探索基於屬性的測試 (property-based testing) 以驗證錯誤的語意正確性
- 研究測試覆蓋率與錯誤真實性之間的相關性

**錯誤誘導的可控性與安全性**

隨著錯誤合成規模的擴大，需要關注：

- 防止合成錯誤被惡意利用於訓練資料污染或後門攻擊
- 設計錯誤誘導的「安全邊界」，避免生成可能導致系統性危害的錯誤模式
- 建立合成任務的品質審計機制，確保錯誤的代表性與非偏誤性

**理論基礎的深化**

SWE-at-Scale 的核心假設是「反轉修復可作為錯誤誘導監督」，未來可從理論層面：

- 形式化定義「修復可反轉性」(fix invertibility) 的條件
- 分析錯誤模式分佈的覆蓋率與泛化邊界
- 建立合成任務與真實任務之間分佈距離 (distribution distance) 的理論刻畫

**整合至代理訓練流程**

最終，SWE-at-Scale 的合成任務不僅可用於評估，更可用於訓練：

- 將合成任務作為程式碼代理的訓練資料，探討「合成-訓練-評估」的完整閉環
- 研究合成資料量與代理能力提升之間的 scaling law
- 探索課程學習 (curriculum learning) 策略，從簡單錯誤類型逐步過渡到複雜錯誤類型

## 論文問答

**Q1：為什麼現有的 SWE 任務基準在評估程式碼代理時面臨擴展性瓶頸？**
A：現有的真實世界 SWE 基準（如 SWE-bench Verified）受限於議題回報的自然發生頻率，新任務只能以真實軟體開發的速度出現。此外，收集這些任務還受到儲存庫可用性與建構可執行環境成本的雙重限制，使得單純依靠自然發生的議題來擴展 SWE 任務資料變得極為困難。這種供需失衡促使研究者必須尋找合成方法來補足真實資料的不足。

**Q2：現有的合成方法（如 SWE-smith、SWE-Synth、BugPilot）為何無法產生足夠真實且多樣的錯誤？**
A：這些方法主要依賴大型語言模型的預訓練知識搭配啟發式提示來注入錯誤，但缺乏專門針對錯誤注入的訓練。由於沒有從真實錯誤修復中學習錯誤形成的機制，這些方法在重複生成時更容易反覆產生模型已熟悉的錯誤模式，而非持續擴展合成任務的多樣性。這意味著它們難以捕捉真實軟體故障中複雜且細緻的機制性知識。

**Q3：為什麼「從歷史錯誤修復中學習」對於合成高品質 SWE 任務如此重要？**
A：歷史修復封裝了錯誤形成的深層機制性知識——每一個真實的開發者修復都反映了在特定開發情境下錯誤是如何被引入與解決的。透過反轉這些修復，可以將「修復監督」轉化為「錯誤誘導監督」，使模型學習到的是基於實際開發經驗的錯誤模式，而非僅憑語言模型的內部臆測。這種從真實資料中提煉的可重用監督訊號，是突破有限真實修復數量限制、實現可擴展合成的關鍵。

**Q4：SWE-at-Scale 框架的核心方法論是什麼？其「雙重監督構建」如何運作？**
A：SWE-at-Scale 採用兩階段流程：第一階段從真實修復中反轉學習，第二階段將學到的轉換應用於新的黃金程式碼儲存庫。在雙重監督構建中，框架同時建構兩種監督訊號——一是「補丁監督」（從程式碼檔案直接到錯誤誘導補丁），二是「錯誤模式監督」（從程式碼檔案到自然語言描述的錯誤模式）。這兩種監督互補，使模型不僅學會如何產生具體的程式碼變更，也學會理解錯誤背後的語意意圖。

**Q5：SWE-at-Scale 與 SWE-at-Scale+ 兩個變體在設計理念上有何差異？**
A：SWE-at-Scale 直接學習從黃金程式碼生成錯誤誘導補丁，屬於端到端的補丁生成路徑；而 SWE-at-Scale+ 則先學習產生自然語言形式的錯誤模式描述，再由「錯誤模式執行器」將該模式實現在新程式碼上。這種雙模式設計讓 SWE-at-Scale+ 能在生成過程中引入更高層級的語意規劃，從而可能產生更多樣化且更貼近人類思考方式的錯誤注入方式。

**Q6：框架如何將「有限的真實修復」轉化為「可擴展的合成產能」？**
A：核心在於將每個歷史修復視為一個可轉移的錯誤模式範本，而非一次性使用的任務實例。透過在多樣化的儲存庫上聚合反轉後的轉換，模型學會的是真實世界錯誤模式的可重用分佈。當應用於新穎程式碼情境時，框架可以反覆抽樣這些錯誤模式並將其實例化，使單一修復能支援多個合成任務的產生，實現從有限監督到指數級擴展的轉變。

**Q7：SWE-at-Scale 在與 SWE-bench Verified 等基準的比較中表現如何？**
A：在人類評估的成對比較中，SWE-at-Scale 與 SWE-at-Scale+ 生成的錯誤分別在 55.9% 與 61.2% 的案例中被評為「更可能發生於真實軟體開發中」，超越了真實議題的評價。此外，從錯誤類型分佈圖可看出，SWE-at-Scale 生成的錯誤涵蓋介面、邏輯、邊界、參數、屬性等多種類型，分佈比 SWE-smith 更接近 SWE-bench Verified 的真實分佈，顯示其在多樣性與真實性上的優勢。

**Q8：SWE-at-Scale 在「錯誤多樣性可擴展性」上的關鍵實驗發現是什麼？**
A：實驗顯示，SWE-at-Scale 能從單一程式碼情境中產生截然不同的錯誤類型，且錯誤多樣性在每檔案高達 200 次生成時仍能穩健擴展。這項結果突破了傳統合成方法在重複生成時容易陷入模式重複的瓶頸，證明了基於反轉學習的錯誤誘導模型確實學會了一個可重用的錯誤分佈，而非僅記憶有限的範本。

**Q9：訓練資料的規模與組成如何支撐框架的泛化能力？**
A：框架基於從 688 個儲存庫收集的 13,407 筆真實修復轉換進行訓練，並以 Qwen3.5-9B 作為骨幹模型。訓練資料涵蓋 Web/API、科學計算、機器學習、開發工具、基礎設施、資料科學、CLI/TUI、文件、儲存系統與測試等多個領域，且錯誤類型分佈包含介面（17.1%）、邏輯（47.6%）、邊界（9.9%）等多元類別。這種跨領域、跨錯誤類型的多樣化訓練資料，是模型能泛化到新穎程式碼情境的基礎。

**Q10：SWE-at-Scale 在實際產品化與工業部署中可能面臨哪些考量？**
A：在實際部署時，需考量合成任務的品質控管管線——雖然框架能大規模產生任務，但每個任務仍需通過可執行性驗證與測試基礎設施的相容性檢查。此外，訓練資料來源儲存庫的授權合規性、生成任務的潛在偏見，以及與企業內部程式碼風格的契合度，都是工業化應用前必須處理的議題。框架的可擴展特性也意味著需要建立相應的篩選與排序機制，以確保產出品質的一致性。

**Q11：SWE-at-Scale 對程式碼代理研究領域的長期影響為何？**
A：此框架將 SWE 任務的生產從「被動收集真實議題」轉變為「主動合成可驗證任務」，大幅降低了評估資料的取得成本。這使得研究者能在更受控的條件下系統性地探測程式碼代理的能力邊界，並能針對特定錯誤類型進行定向壓力測試。長期而言，這種可擴展的合成能力將加速程式碼代理基準測試的迭代與標準化，推動整個領域朝更嚴謹的評估方法論邁進。

**Q12：SWE-at-Scale 生成的任務如何應用於模型訓練與能力提升？**
A：除了作為評估基準，合成任務還能作為強化學習或監督微調的訓練資料，用於持續提升程式碼代理的除錯與修復能力。由於框架能產生多樣化的錯誤類型與情境，訓練資料可以涵蓋代理在真實世界中較少遭遇的邊界案例，幫助模型發展更全面的錯誤處理策略。這種「評估—訓練」一體化的循環，是 SWE-at-Scale 對領域的另一項重要貢獻。

**Q13：SWE-at-Scale 框架存在哪些已知的局限性？**
A：框架的效能高度依賴訓練資料中真實修復的品質與代表性——若某些錯誤類型在訓練集中比例偏低（如協定、檔案系統類錯誤），模型在這些領域的合成能力可能受限。此外，反轉修復的過程假設修復本身是正確且最小化的，但實務中部分修復可能包含重構或多重變更，這會增加監督訊號的雜訊。框架目前也較難處理需要跨檔案協調或深層架構變更的複雜錯誤。

**Q14：SWE-at-Scale 在實際應用中可能出現哪些失敗案例？**
A：在邊界情況下，模型可能產生語法正確但語意不合理的錯誤注入，例如修改了無關的程式碼路徑或引入了無法被現有測試捕捉的行為偏差。此外，當目標程式碼情境與訓練資料差異過大（如使用了訓練集中未涵蓋的特殊框架或領域特定語言）時，生成的錯誤可能不夠自然或無法形成可驗證的測試案例。這些失敗模式提醒我們合成品質仍需後續的自動化驗證與人工抽檢把關。

**Q15：SWE-at-Scale 的未來發展方向有哪些？**
A：未來可探索的方向包括：擴展訓練資料至更多程式語言與領域、引入多代理或迭代式精煉機制以提升合成品質、結合形式化驗證以確保生成錯誤的語意正確性，以及將框架應用於錯誤修復模型的對抗訓練。此外，將 SWE-at-Scale 與真實議題結合，建立混合式評估基準，也是值得探索的方向，以兼顧真實性與可擴展性的雙重優勢。

## 實務應用指南

### 適用場景

1. **程式碼代理評測基準的持續擴充**：當團隊需要定期評估內部或商用程式碼代理（如 Claude Code、Cursor、Devin 等）時，可利用 SWE-at-Scale 從既有專案的歷史修復紀錄中持續產出新任務，避免等待自然議題累積導致的評測空窗期。

2. **企業內部訓練資料生成**：大型軟體公司可將自家 GitHub / GitLab 上的真實修復紀錄反轉，建立內部專屬的「錯誤誘導模型」，用於產生符合自家程式碼風格與領域特性的合成訓練資料，補強代理在內部系統上的泛化能力。

3. **紅隊測試與安全性弱點挖掘**：透過反轉安全修復（例如權限檢查、輸入驗證的修復），可在受控環境中產生「已知會被引入的弱點模式」，用於壓力測試程式碼審查代理、靜態分析工具與 CI 防線。

4. **教育訓練與除錯能力評量**：程式設計教育平台可利用此框架從開源專案產生多樣化、可自動驗證的除錯題目，學生提交的修補方案可透過既有測試套件即時評分，支援大規模線上課程。

5. **領域專屬 SWE 基準建構**：針對金融、醫療、嵌入式等垂直領域，可從該領域的開源專案蒐集修復樣本，訓練領域專屬的合成模型，建立比通用 SWE-bench 更貼近實際工作負載的評測集。

### 實作前置條件

**資料需求**
- 至少數百個具備完整測試基礎設施的開源儲存庫（論文使用 688 個），每個儲存庫需有可解析的 commit 歷史與對應的測試套件。
- 每個儲存庫需能透過 Docker 或類似機制重現執行環境（建議參考 SWE-bench 的環境建構流程）。
- 修復紀錄需具備「修復前」與「修復後」的程式碼差異（diff），並能對應到具體的檔案與行號。
- 議題描述（issue body）需與修復 commit 對應，可透過 GitHub API 的 issue-to-PR 連結取得。

**運算資源**
- 訓練階段：建議至少 4×A100 80GB 等級 GPU，用於微調 Qwen3.5-9B 等級的骨幹模型；若使用更大骨幹（如 32B），需相應升級至 8×A100/H100。
- 推論階段：單張 A100 即可批次產生錯誤誘導補丁；若需大規模批次生成（每檔案 200 次），建議配置多節點並行。
- 儲存空間：訓練資料（13,407 筆反轉樣本）約需數十 GB；完整儲存庫快照與 Docker 映像則需 TB 等級。

**技能門檻**
- 熟悉 Git 操作、commit 解析與 diff 處理（建議使用 PyDriller 或類似工具）。
- 具備 LLM 微調經驗（LoRA / 全參數微調、SFT 流程）。
- 了解 Docker 環境封裝與 SWE-bench 風格的測試執行框架。
- 具備基本的靜態分析能力，能識別修復紀錄中的「邏輯變更」與「純格式化變更」並加以過濾。

### 實作步驟建議

1. **建立反轉修復語料庫（Stage 1 前期）**
   - 從 GitHub 蒐集具備 issue-to-PR 連結的儲存庫，使用 PyDriller 遍歷 commit 歷史。
   - 篩選條件：PR 標題或議題中含 `bug`、`fix`、`broken`、`regression` 等關鍵字，且 diff 觸及非測試檔案。
   - 對每筆修復產生「黃金程式碼 → 錯誤程式碼」的反向配對，並保留行號標註。

2. **建構雙重監督訊號**
   - **補丁監督（Patch Supervision）**：直接以反向 diff 作為訓練目標，訓練 SWE-at-Scale 模型從黃金程式碼生成錯誤誘導補丁。
   - **錯誤模式監督（Bug Pattern Supervision）**：以自然語言描述「應如何修改目標程式碼以引入錯誤」，訓練 SWE-at-Scale+ 模型先產生模式描述，再由執行器（Bug Pattern Executor）將其落實為補丁。
   - 兩種監督可同時訓練同一骨幹模型，或分別訓練兩個專家模型。

3. **微調骨幹模型**
   - 以 Qwen3.5-9B 為起點，使用 LoRA（rank 64–128）進行參數高效微調，訓練 3–5 個 epoch。
   - 學習率建議 1e-5 至 2e-5，搭配 cosine schedule 與 warmup。
   - 驗證集應來自與訓練集不同的儲存庫，避免資料洩漏。

4. **建構可執行環境**
   - 為每個目標儲存庫封裝 Docker 映像，預先安裝相依套件並設定測試執行指令。
   - 參考 SWE-bench 的 `fail-to-pass` 與 `pass-to-pass` 測試定義，確保合成任務具備可驗證性。

5. **執行雙模式合成（Stage 2）**
   - **SWE-at-Scale 模式**：直接呼叫模型對黃金檔案生成錯誤誘導補丁，套用後執行測試套件，僅保留「使既有測試失敗」的補丁。
   - **SWE-at-Scale+ 模式**：先取得自然語言錯誤模式，再由執行器（可為另一 LLM 或規則引擎）將模式轉為具體程式碼變更。
   - 每個檔案可重複抽樣 50–200 次以擴展多樣性，論文實驗顯示多樣性在 200 次內仍穩定成長。

6. **品質過濾與多樣性驗證**
   - 自動過濾：保留能讓至少一個 `pass-to-pass` 測試失敗、且所有 `fail-to-pass` 測試通過的補丁。
   - 多樣性檢查：使用錯誤類型分類器（如論文中的 9 大類別）確認不同樣本涵蓋不同錯誤類型。
   - 人工抽樣評估：邀請開發者進行成對比較，確認合成任務的「真實感」。

7. **釋出與持續迭代**
   - 將合成任務以 SWE-bench 相容格式釋出，並隨新修復紀錄持續增量訓練模型。
   - 建議每季重新訓練一次，以納入最新的錯誤模式。

### 潛在風險與注意事項

- **資料洩漏風險**：若訓練集與評測集來自相同儲存庫，模型可能「記住」修復內容而非學到泛化模式。務必以儲存庫為單位切分訓練/驗證/測試集，並定期檢查重疊率。
- **測試套件健全性**：若目標儲存庫的測試覆蓋率不足，合成補丁可能無法被既有測試偵測，導致「假陽性」任務。建議優先選擇測試覆蓋率 > 70% 的儲存庫。
- **錯誤類型偏移**：模型可能傾向生成訓練集中較常見的錯誤類型（如邏輯、介面），而忽略罕見但重要的類型（如協定、檔案系統）。可透過類別平衡抽樣或後處理重加權緩解。
- **過度擬合於特定程式碼風格**：若訓練資料集中於 Python 專案，模型在 Java/Go 等語言上表現可能下降。建議針對目標語言分別訓練或採用多語言預訓練骨幹。
- **合成任務的可解性**：並非所有生成的補丁都能被現代代理解決，需在評測時明確區分「任務真實性」與「代理能力」兩個維度，避免將代理失敗歸因於合成品質。
- **倫理與授權**：使用開源專案作為訓練資料時，應遵守各專案的授權條款；若涉及企業內部程式碼，需特別注意智慧財產權與機密保護。
- **執行環境成本**：每個合成任務都需獨立 Docker 環境，批次生成 10,000 個任務的環境建構成本可能達數千美元；建議使用容器池與快取機制降低成本。

### 與其他技術的整合建議

- **與 SWE-bench / SWE-bench Verified 整合**：合成任務可採用相同的 JSON 格式與 Docker 環境規範，直接接入既有評測管線，無需重建基礎設施。
- **與程式碼代理框架整合**：可將合成任務餵入 OpenHands、AutoCodeRover、SWE-Agent 等開源代理框架，進行大規模能力評測；亦可作為 RLHF 訓練資料來源，用於代理的偏好學習。
- **與靜態分析工具整合**：將合成補丁餵入 SonarQube、CodeQL 等工具，評估其偵測能力，或反向用於產生靜態分析規則的訓練資料。
- **與 CI/CD 整合**：在企業 CI 流程中，可定期從最新修復紀錄增量合成新任務，作為「迴歸測試代理」的評測基準，監控代理能力隨時間的變化。
- **與錯誤類型分類器整合**：論文中使用的 9 大錯誤類型分類（介面、邏輯、邊界、參數、屬性、簿記、複製語義、協定、檔案系統）可獨立部署，用於監控合成資料集的類型分佈平衡。
- **與向量資料庫整合**：將所有合成的「黃金程式碼—錯誤誘導補丁—錯誤模式」三元組存入向量資料庫，支援後續相似性搜尋與去重，避免重複生成。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）與圖 2 的整體流程圖，建立「反轉修復 = 學習錯誤模式」的核心直覺；接著跳過技術細節，直接看圖 1 的錯誤類型分佈圖，理解 SWE-at-Scale 與 SWE-smith 在多樣性上的差異；最後瀏覽實驗結論，了解「為什麼這比單純提示 LLM 更好」。技術細節可留待具備基礎後再深入。

**給 AI 工程師**：重點關注第 2 節的雙重監督建構（Dual Supervision Construction）與 Stage 2 的雙模式合成（Dual-Mode Bug Synthesis），特別是 SWE-at-Scale 與 SWE-at-Scale+ 的差異——前者直接生成補丁、後者先生成自然語言模式再由執行器落實。建議實際嘗試以 Qwen3.5-9B + LoRA 重現訓練流程，並評估在自有儲存庫上的合成品質；亦可探索將骨幹換為更大模型（如 Qwen3-32B、DeepSeek-Coder-V2）以提升品質。

**給研究者**：論文的關鍵創新在於「將修復監督反轉為錯誤誘導監督」的問題重構，這個思路可延伸至其他領域（如將測試案例反轉為錯誤注入案例、將型別簽名反轉為型別錯誤案例）。建議深入分析第 3 節的資料建構流程、第 4 節的評測協議（特別是與 SWE-bench Verified 的成對人類評估），並思考如何將此框架應用於多模態程式碼（如 Jupyter Notebook）、多語言、或長上下文（多檔案）任務。

**給產品經理**：此框架的核心商業價值在於「將有限的人工修復紀錄轉化為可擴展的評測資產」，特別適合需要持續驗證程式碼代理能力的企業（如 IDE 廠商、DevOps 平台、AI 程式碼審查工具供應商）。建議評估將其整合至內部評測管線的成本（GPU + 環境建構）與收益（更貼近真實工作負載的代理能力評估）；同時關注其在紅隊測試、教育訓練等場景的延伸應用機會。
