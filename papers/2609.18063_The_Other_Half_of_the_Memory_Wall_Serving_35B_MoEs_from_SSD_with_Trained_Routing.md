## ⚡ TL;DR

消費級硬體上 350 億 MoE 權重記憶體不足，單純卸載 SSD 又因路由延遲無法重疊計算。
Edge0 用逐層預路由頭提前預測下層專家，並以未合併復原 LoRA 彌補量化與替換損失。
24GB機器僅用3GiB記憶體跑350億MoE達20tok/s，品質近fp16教師且已開源。

## 摘要翻譯

在消費級硬體（consumer hardware）上進行混合專家模型（Mixture-of-Experts, MoE）推理（inference）受權重記憶體（weight memory）所限：一個 350 億參數級模型（35B-class model）經 4 位元量化（4-bit quantization）後為 19.5GB，而稀疏性（sparsity）縮減的是每個 token 的運算量（compute per token），而非必須保存的位元組數量。單純將權重（weights）卸載（offloading）至 SSD 本身並無助益，因為在取得第 N 層（layer N）輸出（output）之前，就必須選定第 N+1 層（layer N+1）的專家（experts），因此讀取作業無法及早啟動並與運算重疊，從而隱藏延遲。我們提出 Edge0，一個串流式 MoE 推理引擎（streaming MoE inference engine），透過預路由器（prerouter）彌補此缺口：逐層預測頭（per-layer head）會提前一個 token（one token ahead）預測下一層的路由（routing），且該預測即被當作路由本身使用，因此預備專家集合（staged expert set）等於實際路由專家集合（routed expert set），沒有任何 token 被丟棄。一個未合併的復原 LoRA（unmerged recovery LoRA）在學生路徑（student path）上訓練，彌補 int4 量化（int4 quantization）與路由替換（routing replacement）所損失的品質（quality）。在單台配備 24GB 記憶體的機器上，Edge0 以每秒 20 個 token 的吞吐量（throughput）提供 350 億參數級 MoE 服務，峰值活躍記憶體（peak active memory）僅 3GiB，在五個公開基準測試（benchmarks）上平均與其 fp16 教師模型（fp16 teacher）相差僅幾個百分點。80 億參數級版本（8B tier）亦可在同一框架上運行，且該框架、檢查點（checkpoints）與適配器（adapters）皆為開源（open source）。

### 核心貢獻（3～5點）
- 指出 MoE 推理在消費級硬體上的核心瓶頸在於權重記憶體，而非運算量：稀疏性只降低每個 token 的運算量，卻無法減少必須載入的權重位元組數。
- 提出 Edge0 串流式 MoE 推理引擎，透過預路由器與逐層預測頭提前一個 token 預測下一層路由，使預備專家集合等於實際路由專家集合，無需丟棄 token。
- 設計未合併的復原 LoRA，在學生路徑上訓練以彌補 int4 量化與路由替換造成的品質損失。
- 在單台 24GB 機器上實現 350 億參數級 MoE 以每秒 20 個 token 運行，峰值活躍記憶體僅 3GiB，且品質接近 fp16 教師模型。
- 框架、檢查點與適配器均開源，並支援 80 億參數級版本。

### 適合對象
本論文適合對大型語言模型邊緣部署、混合專家模型（MoE）推理加速、模型量化與壓縮，以及記憶體受限環境下高效能推理系統設計感興趣的研究人員與工程師。特別是希望在消費級硬體或本地裝置上部署大型 MoE 模型、探索 SSD 串流載入與預測式路由技術的開發者與系統架構師。

## 深度分析

#### 方法論解析

Edge0 的核心命題是：在消費級硬體（consumer hardware）上，350 億參數級（35B-class）的混合專家模型（Mixture-of-Experts, MoE）無法靠單純量化或稀疏性（sparsity）塞入有限記憶體，因此必須把權重（weights）這一半「記憶體牆（memory wall）」從 DRAM 移到 SSD，並透過訓練過的預路由模組（prerouter）與未合併復原 LoRA（unmerged recovery LoRA）同時解決延遲與品質問題。

##### 1. SSD 串流專家層（SSD Streaming Expert Layers）

系統將所有專家（experts）權重保留在 SSD，透過 `mmap` 隨需載入（on-demand loading），並依賴作業系統（operating system, OS）的分頁快取（page cache）維持熱資料。由於每次解碼步驟（decode step）只啟動極少數專家，峰值活躍記憶體（peak active memory）由「當前活躍集合（active set）」決定，而非總參數量（parameter count）。以 35B MoE 為例，每層 256 個專家、int4 量化後每層約 453MB，整份檢查點（checkpoint）約 19.5GB，但活躍記憶體可壓到約 3GiB。

為了避免每步重建執行堆疊的開銷，Edge0 引入 slot 機制：專家記憶體槽位可重複使用，減少動態配置與釋放的稅負。此外，所有路由數學實現都與原始模型位元一致（bit-identical to vendored models），並對每條執行路徑與反量化參考（dequantized reference）做元素級驗證（element-wise verification），確保串流執行不會偷偷改變模型語意。

##### 2. 預測即路由：跨 token 的預路由器（Prerouter）

單純把權重卸載（offloading）到 SSD 不夠快，因為傳統 MoE 路由（routing）具有層內依賴：第 N+1 層的專家選擇必須等第 N 層輸出（output）出現後才能決定。若採用 naive on-demand loading，每層每 token 都會因磁碟延遲（disk latency）產生一次停頓（stall），無法被前向傳播（forward pass）遮蓋。

Edge0 的解法是讓預路由器提前一個 token（one token ahead）預測：在第 t 個 token 處理第 N 層時，用第 N 層在上一個 token 的狀態預測第 N+1 層在 t+1 時刻的路由。這個預測在解碼時直接被當作路由使用，因此：

- 預備專家集合（staged expert set）與實際路由專家集合（routed expert set）在構造上完全相同；
- 不需要回退載入（fallback load），也不會丟棄 token（dropped tokens）；
- 專家讀取可以與當前層計算重疊，從而將 I/O 隱藏在 compute 之後。

預路由器是逐層預測頭（per-layer head），並且完整實現了兩種主流路由家族：softmax-top-k（如 Qwen3.6）與 sigmoid-group（如 DeepSeek-V3、Ling），訓練與推論使用同一組函式，避免實現不一致造成的誤差。

##### 3. 未合併復原 LoRA（Unmerged Recovery LoRA）

int4 量化（int4 quantization）與路由替換（routing replacement）都會損失品質（quality）。Edge0 的做法是：

- 將 int4 基底模型（int4 base）凍結；
- 在低秩適配器（adapter）上進行知識蒸餾（distillation），監督訊號來自 fp16 教師模型（fp16 teacher）；
- 蒸餾過程走「學生路徑（student path）」，也就是讓 LoRA 在「預測路由已被替換」的真實推理路徑下學習，而非只在原始路由下學習。

關鍵在於部署時**不將 LoRA 合併（unmerged）**進 int4 基底，而是以平行增量（parallel delta）形式與基底並行相加。作者指出，若把 LoRA 合併（merge）到 int4 權重後再重新量化（re-quantizing）為 4 位元，適配器的細微更新會被四捨五入抹除，導致大部分復原效果流失。未合併部署雖然多一次矩陣乘法，但成本可忽略，卻能保留蒸餾得來的品質增益。

##### 4. 系統抽象與模組化

Edge0 把 MLX 相關程式碼封裝在後端外觀（backend facade）之後，核心邏輯（model specs、prerouter、streaming pool、server）只依賴這層介面。模型透過單一的 `MoESpec` 描述：專家數量（expert count）、Top-K、路由家族、量化方式、權重佈局與鍵模板。同一個通用串流層可服務不同模型。LoRA 與 prerouter 權重以 safetensors 儲存，並帶有來源詮釋資料（provenance metadata），從模型目錄解析，永不併入基底。

#### 實驗數據解讀

論文提供的量化結果可歸納為三組：

| 指標 | 數據 | 意涵 |
|---|---|---|
| 吞吐量（throughput） | 35B MoE 在單張 24GB 機器上達 20 tok/s | 在權重無法整份放進 DRAM 的情境下，透過預測即路由把 SSD 讀取與計算重疊，達到可用等級的每秒 token 數（tokens per second, tok/s） |
| 記憶體 | 峰值活躍記憶體（peak active memory）約 3GiB | 相對 19.5GB 的 int4 檢查點，活躍集合（active set）僅佔約 16%，釋出空間給 OS 與 KV cache |
| 品質 | 在五項公開基準測試（benchmark）上平均接近 fp16 教師模型「幾個百分點」 | int4 量化與路由替換的誤差被復原 LoRA 大部分補回 |

進一步解讀：

- **+80% 至 +84% 的解碼加速**：這是預路由器（prerouter）相對於無預測串流的貢獻。當檢查點無法放入記憶體時，若沒有預測，每層每 token 都要等待 SSD 讀取；有了跨 token 路由預測，讀取可與計算流水線化，幾乎把 I/O 完全遮蓋。
- **3GiB 的記憶體佔用**：這並非模型總大小，而是「當前需要留在 DRAM 的權重 + 執行中間值」的峰值。它證明 MoE 的稀疏性雖然不減少總位元組，但確實可以轉化為「同時間只需載入少量專家」的優勢，前提是路由必須提前知道。
- **品質「within a few points」**：雖然論文未給出每個基準的詳細分數，但「平均幾個百分點」暗示復原 LoRA 已將 int4 量化損失與預測路由誤差壓到可部署範圍。不過「平均」可能掩蓋某些任務上較大的落差，這在實際應用中仍需逐項檢視。
- **8B tier**：同一框架也能跑 80 億參數級版本，且該版本結合了 MLA（multi-head latent attention）與 MoE，顯示 Edge0 與 KV cache 壓縮技術正交。

需要注意的限制：實驗數據高度依賴 SSD 頻寬與延遲、OS page cache 命中率、以及機器上其他程序佔用。若換成較慢儲存或首次啟動（cold start），20 tok/s 可能會下降。

#### 與現有研究的比較

##### 1. 與量化研究的關係

GPTQ / AWQ 等後訓練量化方法已把 4-bit 確立為實用下限；低於 4-bit 時，事後補救技術（post-hoc technique）難以挽回誤差。Edge0 不試圖突破 4-bit，而是坦然接受 int4 損失，再透過蒸餾式復原 LoRA 把品質拉回。這與 QLoRA 的精神相近：QLoRA 證明 4-bit 基底加 LoRA 可逼近 16-bit 微調品質；Edge0 則進一步指出，**在服務時必須以未合併（unmerged）方式保留 LoRA**，否則重新量化會抵消適配器效果。

##### 2. 與 KV cache 壓縮的關係

MLA、稀疏注意力（sparse attention）、線性狀態模型（linear state model）等技術處理的是動態狀態（state）這一半記憶體牆，與 Edge0 處理靜態權重（weights）互補。論文明確將兩者區分，並在 8B tier 中結合 MLA + MoE，顯示未來可同時壓縮兩半。

##### 3. 與卸載 / 分層服務的關係

現有卸載方案多數只「搬移」權重，無法預知下一步需要哪些專家：

- `llama.cpp --cpu-moe`：把專家放在 CPU/system memory；
- PowerInfer：將神經元分為冷熱集合，跨 GPU/CPU 放置；
- Mixtral-offloading / MoE-Infinity：依流行度或重用距離快取專家；
- FlexGen：把權重與 KV 一起卸到磁碟。

這些方法雖然降低 GPU 記憶體壓力，但權重仍佔數十 GB，且抵達磁碟時不知道下一步要讀哪些專家。Edge0 的預路由器讓系統在需要權重之前就知道該讀什麼，這是從「被動卸載」到「主動預取」的關鍵躍進。

##### 4. 與預門控（Pre-gating）的關係

Pre-gated MoE 在同一 token 內、第 N 層 attention 之後就決定第 N+1 層的專家。但對串流引擎而言，這個「提前量」不夠：因為權重讀取需要跨越多層計算時間才能被遮蓋。Edge0 改為提前一個完整 token（one token ahead），讓 SSD 讀取與整個 forward pass 重疊，這是專為串流 SSD 權重設計的排程。

##### 5. 與專家跳過蒸餾的關係

expert-skip self-distillation 證明，若訓練時就讓 MoE 適應「只使用一半專家」，模型可以容忍專家數量減半。Edge0 把同樣觀察應用到「預測即路由」：不是減少專家數，而是讓模型在訓練時就學習「路由被預測器取代」的學生路徑，從而讓推論時的近似路由成為可學習的目標。

##### 主要限制

- **模型專屬訓練成本**：每個模型都需要訓練 prerouter 與 recovery LoRA，且需要 fp16 教師模型進行蒸餾，對開源社群復現而言並非零成本。
- **儲存效能依賴**：雖然 20 tok/s 在 SSD 上可行，但若使用較慢儲存裝置或 page cache 未命中，效能會顯著下降。
- **僅適用 MoE**：方法核心是利用 MoE 稀疏性與專家級路由預測，對於密集模型（dense models）需要額外設計。
- **無回退機制**：預測被直接當作路由，雖然避免 fallback load，但也意味著任何預測偏差都必須靠訓練與 LoRA 吸收，無法在推論時動態補救。

#### 可重現性評估

Edge0 在可重現性（reproducibility）上的設計相當積極：

- **開源釋出**：框架、檢查點（checkpoints）、適配器（adapters）皆開源（open source）。
- **兩個完整 tier**：同時釋出 35B 與 8B 模型，且兩者都包含可一起載入的 checkpoint 與 adapters。
- **模組化程式碼**：後端外觀（backend facade）與 `MoESpec` 讓新增後端或模型規格有明確介面；核心邏輯不依賴特定深度學習框架細節。
- **權重來源詮釋資料**：safetensors 檔案帶有 provenance metadata，有助於追蹤哪些權重屬於基底、prerouter 或 LoRA。
- **數值驗證**：每條執行路徑都與反量化參考做元素級驗證，降低「串流實作偷偷改變模型」的風險。

但仍有一些潛在缺口：

- **訓練資料與超參數**：論文摘要與提供的節錄未詳細說明蒸餾用的語料、訓練步數、學習率、LoRA rank 等，這會影響社群從頭訓練新模型的能力。
- **硬體平台限制**：Edge0 使用 MLX，主要面向 Apple Silicon 生態；雖然 backend facade 理論上可移植到 CUDA/ROCm，但目前釋出的可執行環境可能以 Mac 為主。
- **基準細節**：僅提到「五項公開基準測試」，未列出確切名稱與各項分數，難以與其他工作做細部比較。
- **評估腳本**：未在提供的節錄中看到自動化評估腳本或測試資料前處理流程，這對嚴格復現品質數字很重要。

整體而言，Edge0 在「可下載、可執行」這一層已達到高可重現性；若要從頭訓練新模型或移植到新硬體，則仍需更多訓練與評估細節。

#### 未來研究方向

1. **跨硬體後端移植**  
   利用 backend facade 將 Edge0 擴展到 CUDA / ROCm / Intel 等加速器，讓 SSD 串流 MoE 不限於 MLX/Apple Silicon。

2. **與 KV cache 壓縮技術深度整合**  
   將 MLA、稀疏注意力、線性狀態模型與 Edge0 結合，進一步壓低動態狀態（state）佔用的記憶體，使長上下文（long context）也能在消費級硬體上執行。

3. **更長提前量的路由預測**  
   目前 prerouter 提前一個 token；可研究多 token 預測或信心度導向的投機式專家載入（speculative expert loading），在 SSD 頻寬充裕時預載更多候選專家。

4. **階層式快取策略**  
   結合 reuse distance 或流行度資訊，在 DRAM、SSD 甚至遠端儲存間動態排程專家，提升 cold start 與多輪對話場景的效能。

5. **擴展到非 MoE 架構**  
   對密集模型（dense models）設計層級權重串流與預測機制，例如預測下一層所需的參數區塊或注意力頭子集。

6. **低於 4-bit 的量化與復原**  
   研究 int3 / int2 基底搭配更強大的復原 adapter，或動態 rank 的 LoRA，在極端記憶體限制下維持品質。

7. **理論分析預測路由的誤差傳播**  
   建立路由替換（routing replacement）對生成品質與 perplexity 的理論上界，指導 prerouter 的訓練目標設計。

8. **多裝置與邊緣叢集**  
   將專家分散到多台邊緣裝置，結合專家並行（expert parallelism）與 SSD 串流，探索去中心化、無資料中心（datacenter-free）部署。

9. **與推測解碼（speculative decoding）結合**  
   讓 prerouter 同時服務 draft model 與 target model 的專家預載，進一步提升端到端吞吐量。

10. **能耗與壽命分析**  
    評估頻繁 SSD 讀取對功耗與 NAND 磨耗的影響，設計能耗感知的專家排程與快取策略。

## 論文問答

**Q1：為什麼 350 億參數級的 MoE 模型在消費級硬體上會遇到「記憶體牆」問題？**

A：雖然 MoE 的稀疏性讓每個 token 只啟動約 30 億參數，大幅降低了運算量，但整個模型的權重仍然必須儲存在某處。以 4 位元量化來說，一個 35B 級 MoE 仍佔用 19.5 GB，幾乎佔滿 24 GB 消費級 GPU 的全部記憶體，擠壓作業系統、KV cache 與其他應用程式的空間。因此瓶頸不在運算，而在於必須被載入記憶體的位元組數量，這正是 Wulf 與 McKee 所描述的記憶體牆在生成式 AI 時代的體現。

**Q2：現有的量化與卸載方法為什麼無法單獨解決 35B MoE 的本地部署問題？**

A：4 位元量化已經是後訓練量化的實用下限，再往下壓縮會使誤差快速放大，模型品質變得無法使用，而且事後補救技術也難以挽回。另一方面，單純把權重卸載到 SSD 並不足夠，因為在標準解碼流程中，第 N+1 層的專家選擇必須等到第 N 層輸出後才能決定，導致磁碟讀取無法提前開始，每層每個 token 都會停頓在磁碟延遲上。換句話說，量化解決不了「必須放進記憶體的總量」，而卸載解決不了「讀取無法與運算重疊」的時序問題。

**Q3：動態狀態壓縮技術與 Edge0 的權重卸載是什麼關係？**

A：MLA、稀疏注意力與線性狀態模型主要壓縮的是 KV cache 這類動態狀態，而 Edge0 處理的是靜態權重的儲存與載入，兩者正交互補。事實上，Edge0 的 8B 版本就結合了 MLA 與 MoE，利用壓縮後的注意力機制釋出更多記憶體預算給活躍專家集合。這顯示未來的本地大模型部署很可能需要同時從「狀態」與「權重」兩個方向一起降低記憶體壓力。

**Q4：Edge0 的「預路由器」與傳統預門控機制有什麼根本差異？**

A：傳統預門控在同一個 token 內完成下一層專家選擇，也就是在第 N 層注意力後產生決策，再於第 N+1 層載入權重前使用，這種方式無法給 SSD 串流足夠的提前量。Edge0 的預路由器則跨 token 預測：它根據第 N 層在前一個 token 的狀態，預測第 N+1 層在下一個 token 的路由。這種「提前一個 token」的設計讓專家權重的讀取可以與當前 token 的前向傳播完全重疊，從而隱藏磁碟延遲。

**Q5：為什麼 Edge0 敢於直接把預測路由當作真實路由使用，而不設計回退載入或丟棄 token 的機制？**

A：因為預測路由在訓練階段就被當作真實路由來優化，模型學會在這條「學生路徑」下產生高品質輸出，所以推論時預備的專家集合與實際路由集合在構造上完全相同。這與其他預門控方案不同，後者把預測誤差留到推論時用回退載入或丟棄 token 來吸收，會造成延遲抖動與品質損失。Edge0 把近似成本一次性地支付在訓練階段，並透過知識蒸餾與復原 LoRA 在訓練中就把品質損失補回來。

**Q6：為什麼復原 LoRA 必須以「未合併」的平行增量方式部署，而不是合併後重新量化到 int4？**

A：因為把 LoRA 合併進 int4 基底權重後再重新量化，會摧毀適配器原本引入的大部分修正效果，使得蒸餾與適應訓練幾乎白費。Edge0 選擇在推論時把未合併的 LoRA 作為平行增量與 int4 基底並行相加，這樣可以保留低秩適配器的完整表達能力。實驗顯示這種做法的額外成本極低，卻能顯著彌補 int4 量化與路由替換所造成的能力衰退。

**Q7：Edge0 在公開基準測試上的整體表現如何？**

A：在單張 24 GB 機器上，Edge0 能夠以每秒 20 個 token 的速度服務 35B MoE，且峰值活躍記憶體僅約 3 GiB。平均而言，其在五個公開基準上的表現與 fp16 教師模型相差僅幾個百分點，顯示量化與預測路由帶來的品質損失已被有效回收。此外，8B 版本也在同一框架下運行，證明該架構具備跨規模的通用性。

**Q8：預路由器對解碼吞吐量的具體貢獻有多大？**

A：在權重無法完整放進記憶體的機器上，預路由器讓專家讀取與前向運算重疊，帶來約 80% 到 84% 的解碼吞吐量提升。如果沒有這個跨 token 的預測機制，每個解碼步驟都會因為等待 SSD 讀取而產生停頓，嚴重拖累生成速度。這個數字說明，單純的 SSD 串流並不足夠，關鍵在於能否提前知道要讀取哪些專家。

**Q9：Edge0 在系統實作上如何確保與原始模型行為一致？**

A：Edge0 實作了兩種主流路由家族——softmax-top-k 與 sigmoid-group——並且逐字重用它們來訓練與推論預路由器，確保數學完全一致。此外，所有執行路徑都會與反量化後的參考實作進行元素級驗證，保證輸出位元級正確。專家權重透過 mmap 隨需串流，作業系統分頁快取負責熱資料，而峰值記憶體只追蹤活躍集合而非總參數量。

**Q10：Edge0 最適合哪些實際應用場景？**

A：Edge0 特別適合需要在無資料中心環境中本地執行大型語言模型的場景，例如個人工作站、邊緣裝置或對資料隱私要求極高的應用。由於它能在 24 GB 消費級硬體上運行 35B 模型，開發者與研究者無需租用昂貴的雲端 GPU 就能使用高品質模型。此外，對於需要長篇生成、低延遲互動或離線運作的產品，這種本地 SSD 串流架構也極具吸引力。

**Q11：Edge0 的開源釋出對研究社群與產業有什麼意義？**

A：作者釋出了 35B 與 8B 兩個層級的檢查點、適配器與框架原始碼，讓其他研究者可以重現、驗證並延伸這項工作。這降低了大型 MoE 本地部署研究的門檻，也為量化、蒸餾與儲存層級卸載的交叉研究提供了可運作的基礎設施。對產業而言，這意味著企業可以在不依赖資料中心的情況下，探索將大型模型整合進桌面軟體、遊戲或生產力工具的商業模式。

**Q12：Edge0 的設計對未來模型架構與硬體協同設計有什麼啟示？**

A：Edge0 顯示，單靠壓縮動態 KV cache 無法解決記憶體牆，權重儲存這「另一半」同樣需要創新。它提示未來的模型設計可以將「可預測路由」納入訓練目標，讓稀疏性不僅節省運算，也節省儲存與 I/O。同時，這也呼籲硬體與作業系統層級針對大模型權重的分頁快取、SSD 預取與記憶體映射進行更深入的協同最佳化。

**Q13：Edge0 目前有哪些明確的限制或假設？**

A：Edge0 假設預測路由可以透過訓練被模型充分適應，但這可能取決於模型規模、路由稀疏度與任務特性，並非所有 MoE 架構都能輕易遷移。此外，雖然 SSD 串流降低了峰值記憶體，但持續的磁碟讀取仍會消耗 SSD 壽命與電力，對行動裝置的續航與耐久度構成挑戰。最後，實驗主要針對語言生成任務，對於需要極高確定性或長程一致性的應用，預測路由的誤差累積效應仍需更多研究。

**Q14：預測路由在哪些情況下可能失效或表現變差？**

A：當輸入分佈與訓練資料差異極大時，預路由器可能無法準確預測下一層專家，導致模型進入較少被優化的路徑。在需要精確事實推理或程式碼生成的任務中，路由替換所引入的近似誤差可能會被放大，影響輸出品質。此外，若 SSD 延遲或頻寬出現劇烈抖動，原本設計來隱藏 I/O 的管線也可能被打亂，進而影響生成速度的穩定性。

**Q15：未來研究可以從哪些方向延伸 Edge0 的工作？**

A：一個方向是將預測路由與更激進的權重量化或專家剪枝結合，進一步降低儲存與記憶體需求。另一個方向是探索多 token 提前預測或層級間聯合預測，以爭取更大的 I/O 重疊窗口並適應更慢的儲存媒介。最後，也可以研究如何將類似的 SSD 串流與預取機制應用到多模態模型或長上下文模型，讓本地部署的規模上限持續提升。

## 實務應用指南

### 適用場景

1. **消費級桌機與筆電上的大型 MoE 推理**  
   適合需要在單張 24GB GPU 或純 CPU 環境中執行 35B 級 MoE 的場景，例如個人知識庫問答、本地文件摘要、程式碼輔助，避免將資料上傳至資料中心。

2. **邊緣裝置與資料隱私優先的部署**  
   醫療、法律、金融等對資料外洩敏感的應用，可利用 Edge0 將模型留在本地 SSD，僅保留極小的活躍記憶體足跡（約 3GiB），實現無資料中心部署。

3. **長上下文互動式對話系統**  
   由於權重駐留 SSD、記憶體只放活躍專家與 KV cache，Edge0 適合需要長時間對話、KV cache 持續成長的客服或個人助理產品。

4. **多租戶或與 OS 共存的桌面 AI 代理**  
   傳統 35B 模型會佔滿整張 GPU 記憶體，導致無法與其他應用程式並存；Edge0 的峰值活躍記憶體極低，適合與瀏覽器、IDE、創作軟體一起運行。

5. **開源模型發行與輕量微調生態**  
   研究者或模型廠商可釋出 int4 基底檢查點 + 未合併復原 LoRA + 預路由適配器，讓使用者在消費級硬體上直接執行，無需額外量化或合併。

### 實作前置條件

**資料**
- 原始 fp16 教師模型權重與對應的 int4 量化基底檢查點。
- 訓練語料：用於蒸餾復原 LoRA 與訓練逐層預路由頭的文本資料，建議涵蓋目標應用領域的分布。
- 評測基準：至少 3–5 個公開 benchmark，用於驗證路由替換與 int4 量化後的品質損失是否可接受。

**運算**
- 訓練階段：需能載入 fp16 教師模型進行知識蒸餾，建議具備 40GB 以上 GPU 記憶體或採用模型分片。
- 推理階段：目標為單機 24GB GPU / 32GB 系統記憶體，並配備高速 SSD（NVMe 為佳），以支撐隨需載入的頻寬與延遲。
- 儲存：35B 模型約需 19.5GB 檢查點空間，加上未合併 LoRA 與預路由頭權重。

**技能**
- 熟悉 MoE 路由機制（softmax-top-k 與 sigmoid-group）。
- 具備低秩適配器（LoRA）訓練與知識蒸餾經驗。
- 能操作記憶體映射（mmap）與 SSD I/O 特性，理解作業系統分頁快取行為。
- 有能力驗證推理路徑與 fp16 / dequantized 參考結果的逐元素一致性。

### 實作步驟建議

1. **建立 int4 量化基底與教師參考**  
   使用 GPTQ / AWQ 類方法將 fp16 MoE 量化為 int4 group-64 專家權重，保留 group scale 與 zero point。同時保留 fp16 教師模型作為蒸餾監督來源。

2. **設計並訓練逐層預路由頭（prerouter）**  
   在每層後方接入輕量預測頭，輸入為第 N 層在前一個 token 的狀態，輸出為第 N+1 層在下一個 token 的路由。訓練目標為最小化預測路由與真實路由的差異，並使用與推理時完全相同的路由函式（softmax-top-k 或 sigmoid-group）。

3. **訓練未合併復原 LoRA**  
   將 int4 基底凍結，在學生路徑（使用預測路由）上以 fp16 教師進行知識蒸餾，訓練低秩適配器。切記不要合併回 int4 基底後重新量化；應以平行增量方式部署。

4. **實作 SSD 串流專家層**  
   透過 mmap 將量化後的專家 safetensors 映射到記憶體，設計 slot 機制管理活躍專家集合，避免每步重建執行堆疊。確保路由數學與原始模型位元一致，並對每條執行路徑進行逐元素驗證。

5. **整合預路由與 I/O 重疊**  
   在解碼步驟中，當第 N 層計算進行時，背景觸發第 N+1 層預測專家權重的 SSD 讀取，使磁碟延遲被前向傳播遮蓋。

6. **端到端評估與發布**  
   在 24GB 機器上測量吞吐量（tok/s）、峰值活躍記憶體與五項以上 benchmark 表現。將 int4 基底、未合併 LoRA、預路由頭與執行框架一併開源釋出。

---

### 潛在風險與注意事項

- **預測路由誤差累積**  
  雖然預路由頭的預備專家集合與實際路由集合理論上相同，但若訓練分布與部署分布偏移，可能出現路由替換誤差。建議在目標領域資料上進行持續微調或監控 perplexity 變化。

- **SSD 磨損與延遲抖動**  
  頻繁隨機讀取小塊專家權重會對 SSD 造成壓力，且作業系統分頁快取未命中時會產生明顯停頓。建議使用 NVMe SSD、預留足夠系統記憶體作為快取，並對熱門專家進行常駐快取。

- **合併 LoRA 後重新量化會摧毀復原效果**  
  這是本文明確指出的陷阱：不要為了節省記憶體而將 LoRA 合併進 int4 基底再重新量化。應始終以平行增量方式服務。

- **量化誤差與低秩適配器容量不足**  
  int4 量化損失可能超過 LoRA 可復原範圍，特別是對數學、程式碼等需要高精度的任務。建議在關鍵 benchmark 上設定品質門檻，必要時提高基底位元數或增加 LoRA rank。

- **多後端相容性維護成本**  
  Edge0 將核心邏輯與後端（MLX 等）分離，雖然提升可移植性，但新增後端時需重新驗證量化與路由的位元一致性。

---

### 與其他技術的整合建議

- **KV cache 壓縮技術**  
  MLA、稀疏注意力、線性狀態模型等專注於動態狀態壓縮，與 Edge0 的權重卸載互補。特別是 8B 等級的 MLA + MoE 混合模型，可將更多記憶體預算留給活躍專家集合。

- **現有推論框架**  
  可將 Edge0 的 SSD 串流層封裝為 llama.cpp、vLLM 或自訂後端的 plugin，重點在於提供統一的 `MoESpec` 介面，讓現有排程器與批次處理邏輯繼續運作。

- **快取與分層儲存系統**  
  結合專家熱度快取（如 Mixtral-offloading、MoE-Infinity 的思路），在記憶體中常駐高頻專家，進一步降低 SSD 讀取次數，但需保留預路由機制作為主要 I/O 遮罩手段。

- **模型發行與版本管理**  
  建議將 int4 基底、LoRA、預路由頭分開版本化，並在 safetensors 中加入來源 metadata，方便使用者追蹤每個適配器對應的基底檢查點與教師模型。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先理解「記憶體牆」與 MoE 稀疏性的基本矛盾：MoE 雖然每個 token 只算少數專家，但所有專家權重仍要存在某處。接著把 Edge0 想成「用預測提前知道下一層要讀哪些專家，並在計算同時從 SSD 載入」，最後記住「不要把 LoRA 合併後重新量化」這個實務禁忌即可。

**AI 工程師**  
請聚焦第 3 節的系統設計：預路由頭的訓練目標必須與原始路由函式完全一致、LoRA 要在學生路徑上蒸餾、int4 基底凍結且平行部署。實作時優先驗證每條執行路徑與 fp16 參考的逐元素一致性，並把 SSD I/O 重疊與 slot 管理視為效能關鍵。

**研究人員**  
本文的核心貢獻在於將「預測即路由」與「未合併復原 LoRA」結合，把傳統 pre-gating 在推理時吸收的近似成本轉移到訓練階段。可進一步探索預測路由的理論誤差界、不同路由族（softmax-top-k vs. sigmoid-group）的預測難度，以及更低位元量化下的復原極限。

**產品經理**  
Edge0 的商業價值在於讓 35B 級 MoE 脫離資料中心，進入消費級裝置。評估時請同時看三個指標：吞吐量（20 tok/s）、峰值活躍記憶體（3GiB）與 benchmark 品質損失（相對 fp16 僅幾個百分點）。適合資料隱私要求高、無法持續連網、或需要與桌面應用共存的產品場景。
