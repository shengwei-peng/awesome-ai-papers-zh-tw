## ⚡ TL;DR

基礎模型資料準備管線在跨父節點批次處理時，難以保留子項目的順序、血緣與完成狀態。
本文提出 RayOrch，以宣告式展開—匯聚對與執行期血緣追蹤，實現跨父節點的安全批次與重組。
H20 上 MinerU 與影片管線擴至 64 GPU 分別加速 15.14 與 7.82 倍，優於現有系統。

## 摘要翻譯

為基礎模型（Foundation Model）準備高品質訓練資料（Training Data），需要可擴展的管線（Pipeline）來將異質（Heterogeneous）文件與影片轉換為結構化記錄（Structured Record）。這類管線會將每個父節點（Parent）展開（Expansion）為有序（Ordered）且依輸入而定的子節點（Children）序列，子節點數量可能呈長尾分佈（Long-Tailed Distribution）。GPU 應跨父節點批次處理（Cross-Parent Batching）子節點，同時保留父子關係（Parent-Child Relation）、子節點順序、完成狀態（Completion Status）與結果路由（Result Routing）。現有系統若非將平行性隱藏於粗粒度（Coarse-Grained）作業之後，就是暴露扁平記錄（Flat-Record），迫使應用程式自行管理資料血緣（Data Lineage）與重新分組（Regroup）。我們提出 RayOrch，一種在整個執行過程中保留父子關係的程式設計模型（Programming Model）與分散式執行引擎（Distributed Execution Engine）。程式宣告有序可變基數展開（Ordered Variable-Cardinality Expansion）與配對匯聚（Matching Gather）；編譯器（Compiler）驗證每一對展開與匯聚，執行階段（Runtime）則記錄子成員關係（Child Membership）、直接父節點（Immediate Parent）、不可變序數（Immutable Ordinal）與終止狀態（Terminal State）。每次呼叫先進先出就緒佇列（Per Call FIFO Ready Queue）會跨父節點將就緒子節點組成批次（Batch）。匯聚（Gather）根據宣告的子成員關係與序數重建結果，而非依賴批次邊界或完成順序。一旦所有必要的子節點都達到終止狀態，父節點即可繼續推進。型別化父節點範圍失敗（Typed Parent-Scoped Failure）會抑制失敗父節點的未分派兄弟節點（Undispatched Sibling），同時允許無關的父節點繼續執行。在 NVIDIA H20 GPU 上，RayOrch 將 MinerU 從 4 張 GPU 擴展至 64 張 GPU 時達到 15.14 倍加速比（Speedup），並將影片管線從 8 張 GPU 擴展至 64 張 GPU 時達到 7.82 倍加速比。在 MinerU 上，相較於 Ray Data 端對端時間（End-to-End Time）縮短 13.1%，相較於 Daft 縮短 29.0%；在 Docling 上，相較於 Ray Data 端對端時間縮短 16.0%。程式碼可於 https://github.com/OpenDCAI/RayOrch 取得。

### 核心貢獻（3～5點）
- 提出 RayOrch，一個保留父子關係的血緣控制多粒度資料流程式設計模型與分散式執行引擎，解決現有系統在粗粒度作業與扁平記錄之間的兩難。
- 支援有序可變基數展開與配對匯聚，並由編譯器驗證展開／匯聚配對的正確性。
- 執行階段透過子成員關係、直接父節點、不可變序數與終止狀態追蹤資料血緣，使匯聚不依賴批次邊界或完成順序。
- 設計每次呼叫先進先出就緒佇列以實現跨父節點批次處理，並以型別化父節點範圍失敗隔離錯誤、允許無關父節點繼續執行。
- 在 MinerU、Docling 與影片管線上相較 Ray Data 與 Daft 顯著縮短端對端時間，並在 NVIDIA H20 GPU 上展現良好的擴展加速比。

### 適合對象
適合從事基礎模型資料準備、大規模資料管線、分散式系統與 GPU 批次排程的研究人員與工程師，特別是關注文件／影片解析、資料血緣追蹤、異質資料平行處理，以及需要在粗粒度作業與扁平記錄之間取得平衡的讀者。

## 深度分析

#### 方法論解析

RayOrch（本論文提出之程式設計模型與分散式執行引擎）的核心設計，是將「邏輯上的父子結構」與「物理上的批次分派」明確分離。傳統管線（pipeline）要麼把整份文件或整部影片當成不透明作業（opaque job），隱藏了內部可並行的細粒度單位；要麼把所有項目攤平成扁平記錄（flat-record），讓應用程式自己管理資料血緣（data lineage）與重新分組（regroup）。RayOrch 則在系統層級維護血緣圖（lineage graph），讓 GPU 能夠安全地進行跨父節點批次處理（cross-parent batching），同時保證每個父節點（parent）的結果能依正確的順序與成員關係重建。

##### 1. 程式設計模型：Expansion 與 Gather 的成對宣告

開發者使用 RayOrch 時，主要宣告兩種運算：

- **Expansion（展開）**：一個父項目依輸入內容產生一個有序、可變基數（variable-cardinality）的子項目序列。例如一份 PDF 產出多頁、一個影片產出多個片段。每個子節點（child）在父節點內擁有不可變序數（immutable ordinal）。
- **Matching Gather（配對匯聚）**：與前述 Expansion 配對，負責把該父節點的所有子節點結果，按照宣告的成員關係（child membership）與序數重新組裝回父節點層級的輸出。

編譯器（compiler）會靜態驗證每一組 Expansion–Gather 配對：確保型別、基數範圍、順序語意彼此相容。這樣一來，應用程式不需要在 UDF（使用者定義函式）裡面自己攜帶 parent key 或 ordinal，也不需要在管線末端做全域的 GROUP BY + SORT + REDUCE。

##### 2. 執行階段：結構化血緣作為系統狀態

Runtime（執行階段）把血緣視為系統中繼資料，而非應用程式資料。對於每一次 Expansion，RayOrch 記錄：

- 具體的子成員關係（child membership）：這個父節點實際產生了哪些子節點；
- 每個子節點的直接父節點（immediate parent）；
- 每個子節點的不可變序數（immutable ordinal）；
- 每個結果的終止狀態（terminal state）：成功完成或失敗。

這些資訊讓系統能夠在任意時刻判斷：一個父節點是否已經收集到「所有需要的子結果」，從而可以進入下一個階段。

##### 3. Per-Call FIFO Ready Queue：邏輯邊界與物理批次解耦

為了兼顧 GPU 利用率與正確性，RayOrch 提出 **Per-Call FIFO Ready Queue（每次呼叫先進先出就緒佇列）**：

- 每個 Call（可理解為某個階段或某個 UDF 的呼叫上下文）擁有自己的 FIFO Ready Queue。
- 當子節點就緒時，依先進先出順序進入佇列。
- 系統根據設定的保留策略（reservation policy）從佇列中組成物理批次（batch），這個批次可以混合來自不同父節點的子節點。
- 因此，分派邊界（dispatch boundary）與邏輯上的父子邊界無關：同一個父節點的子節點可能被拆到多個批次，不同父節點的子節點也可以被併到同一個 GPU 批次。

這種設計解決了長尾分佈（long-tailed distribution）問題：少數擁有大量子項目的父節點不會阻塞其他已經完成的小父節點。

##### 4. Gather 解析：不依賴批次或完成順序

Gather 的重建依據是「宣告的成員關係與序數」，而不是「子節點在哪個批次完成」或「完成的先後順序」。這帶來兩個關鍵好處：

- 父節點只要所有必要子結果都進入終止狀態（terminal state），就可以立刻 finalize 並前進到下一階段，不需要等待同一批次的其他父節點。
- 系統不需要在子階段結束後做全域的重新分組（regroup）或 shuffle，重建是區域性的。

##### 5. Typed Parent-Scoped Failure：精準的失敗隔離

RayOrch 支援 **Typed Parent-Scoped Failure（型別化父節點範圍失敗）**：

- 當某個 Call 針對特定父節點回報失敗時，執行階段會為該 Call 與該父節點建立屏障（barrier）。
- 尚未分派（undispatched）的兄弟節點（sibling）會被抑制，不會再進入 UDF。
- 正在執行中的兄弟節點回報會被拒絕，避免無效結果污染血緣。
- 其他不相關的父節點不受影響，繼續執行。

這種機制比傳統「整個 stage 失敗重算」更細緻，能減少浪費的計算，並確保未受影響的父節點仍產出正確結果。

#### 實驗數據解讀

論文在 NVIDIA H20 GPU 上進行評估，涵蓋文件解析管線（MinerU、Docling）與影片管線。以下分項解讀：

##### 1. 強擴展性（Strong Scaling）

- **MinerU**：從 4 張 GPU 擴展到 64 張 GPU，獲得 **15.14× speedup（加速比）**。理想線性加速為 16×，因此效率約 94.6%，顯示 RayOrch 在 16 倍資源擴展下額外開銷極低。
- **影片管線**：從 8 張 GPU 擴展到 64 張 GPU，獲得 **7.82× speedup**。理想值為 8×，效率約 97.8%，表現接近線性。

這兩組數據說明，即使在子節點數量長尾分佈、需要跨父節點批次處理的場景下，RayOrch 仍能維持優異的擴展效率。

##### 2. 端對端時間（End-to-End Time）比較

- 在 MinerU 上，相較於 Ray Data 減少 **13.1%** 的端對端時間，相較於 Daft 減少 **29.0%**。
- 在 Docling 上，相較於 Ray Data 減少 **16.0%** 的端對端時間。

這些改善主要來自兩方面：一是避免了扁平記錄系統在子階段後需要做的全域重新分組 / shuffle；二是已完成的父節點不需要等待其他父節點，減少閒置。

##### 3. FIFO 分派消融實驗

論文比較了使用 Per-Call FIFO Ready Queue 與不使用的情況，牆面時間（wall time）從 **634.1 秒降至 579.3 秒**，改善 **8.6%**。這驗證了「依就緒順序組成跨父節點批次」對於減少整體等待時間的貢獻，特別是在長尾分佈下。

##### 4. 失敗注入實驗

在受控的失敗注入實驗中：

- RayOrch 阻止了 **23,514 個可能觸發的兄弟計算中的 6,241 個** 進入 UDF，約為 26.5% 的無效計算被省下。
- 相較於配對的無失敗執行，牆面時間平均減少 **14.93%**。
- 所有未受影響的父節點仍產出預期輸出。

這顯示 Typed Parent-Scoped Failure 不僅能節省計算資源，還能縮短整體執行時間，因為失敗父節點不會繼續佔用 GPU 做無用功，同時其他父節點並行推進。

#### 與現有研究的比較

##### 1. 相對於粗粒度管線

傳統 coarse-grained（粗粒度）系統把一份 PDF 或一部影片視為單一作業。這種做法雖然簡單，但隱藏了頁面、片段、影格等細粒度並行性，也無法讓 GPU 批次處理來自不同父節點的子項目。RayOrch 在保留父子關係的前提下，把這些細粒度單位暴露出來給執行引擎排程。

##### 2. 相對於扁平記錄系統

Spark、Dask、Ray、Ray Data、Daft 等系統提供分散式集合與任務圖，並支援 cardinality-changing operator 與跨記錄批次處理。然而，當它們表達 fan-out 時，通常會把子項目攤平成獨立記錄，parent key 與 ordinal 變成應用程式資料欄位。這導致：

- 應用程式必須自己追蹤每個子項目的直接父節點與順序；
- 子階段結束後需要全域 GROUP BY、SORT、REDUCE 或 shuffle 來重建父節點結果；
- 失敗處理通常是全域或 stage 層級，無法精準抑制單一父節點的兄弟計算。

RayOrch 把這些結構事實提升為系統狀態，讓編譯器驗證、執行階段追蹤，從而避免全域重組障礙，並支援精細的失敗隔離。

##### 3. 主要限制

論文也明確指出 RayOrch 的適用範圍：

- 只支援「每個來源 microbatch 內的有序匯聚」，不支援 general joins（一般性連結）、跨 microbatch 的 windows（視窗運算）或 feedback loops（回饋迴路）。
- Expansion 產生的子節點序數是不可變的，若應用需要動態重新排序或刪除中間節點，可能需要額外設計。
- 目前的失敗模型是 parent-scoped，對於跨父節點的相依性或全域一致性需求，可能需要額外機制。

#### 可重現性評估

##### 1. 程式碼開放性

- 論文使用的 MinerU 與 Docling 是公開的文件解析工具，原則上可取得。
- 影片管線的具體資料集與預訓練模型權重在提供的摘要與片段中並未詳細說明，可能存在部分資料無法公開的問題。

##### 3. 重現建議

為了提升可重現性，建議作者補充：

- 完整的 artifact evaluation 腳本，包含環境安裝、資料前處理、執行指令；
- 用於實驗的樣本資料集或資料產生器；
- 各項比較實驗（Ray Data、Daft）的設定檔與版本資訊；
- 失敗注入實驗的觸發條件與評估腳本。

#### 未來研究方向

##### 1. 支援更廣泛的資料流模式

目前 RayOrch 不支援 general joins、跨 microbatch 的 windows 與 feedback loops。未來可以擴展血緣模型，讓多個父節點的結果能夠依結構化條件合併，同時仍維持批次處理與失敗隔離的正確性。

##### 2. 動態批次與資源感知排程

Per-Call FIFO Ready Queue 目前已經能混合不同父節點的子項目，但未來可進一步引入：

- 依據子項目大小、GPU 記憶體、推論模型輸入形狀做動態批次調整；
- 針對長尾分佈設計更聰明的保留策略（reservation policy），在「填滿批次」與「減少等待」之間自動權衡。

##### 3. 結合資料品質與主動學習

基礎模型資料準備不僅是轉換與重組，還涉及過濾、去重、品質評分。未來可讓 RayOrch 的血緣資訊與資料品質指標連動，例如當某父節點的子項目品質過低時，以 Typed Parent-Scoped Failure 的方式整組剔除，而不影響其他父節點。

##### 4. 異質硬體與跨雲部署

目前的評估集中在 NVIDIA H20 GPU。未來可探索 CPU-intensive 階段（如解碼、解析）與 GPU inference 階段的協同排程，並將執行引擎擴展到多雲或邊緣環境。

##### 5. 檢查點與細粒度容錯

Typed Parent-Scoped Failure 已經提供精細的失敗隔離，但未來可進一步加入 checkpointing（檢查點）與 lineage snapshot（血緣快照），讓長時間運行的大規模語料庫規模（corpus scale）管線能夠從中間狀態恢復，而不需要重新執行整個父節點。

##### 6. 程式設計模型的人因工程

目前開發者需要正確宣告 Expansion 與 Gather 配對。未來可研究如何透過靜態分析或視覺化工具，輔助開發者理解多粒度資料流（multi-grain dataflow）的結構，並在編譯階段提供更豐富的錯誤訊息與修復建議。

## 論文問答

**Q1：基礎模型資料準備管線中，RayOrch 試圖解決的核心問題是什麼？**  
A：RayOrch 針對的是基礎模型資料準備過程中，管線會反覆在不同粒度單位之間轉換的執行挑戰，例如一份 PDF 會展開成頁面、區域與表格，而一部影片會展開成片段、影格與音訊段落。在每一次展開步驟中，父項目會產生一個數量由輸入決定且有序的子項目序列，而這些子項目的數量在不同父項目之間通常呈現長尾分佈。系統必須在讓 GPU 跨父節點批次處理這些子項目的同時，仍然正確維護父子關係、子項目順序、完成狀態以及結果路由，這正是 RayOrch 要解決的核心問題。

**Q2：現有的粗粒度與扁平記錄系統為何無法妥善處理這類多粒度資料流？**  
A：粗粒度函式把整份文件或整部影片視為一個不透明作業，雖然保留了父子關係，卻把頁面、片段或影格等可平行處理的細粒度工作隱藏起來，導致 GPU 無法獨立排程與批次化這些子項目。相對地，扁平記錄系統雖然能暴露每個子項目，卻把隸屬關係、順序與完成狀態當成應用程式資料，迫使開發者自行追蹤每個子項目的直接父節點與不可變序數，並在子階段結束後執行全域的重新分組或排序。這種全域重組不僅增加程式複雜度，還會引入額外的 shuffle 或同步障壁，進而降低端對端效能。

**Q3：為什麼在基礎模型資料準備中，維護資料血緣與父子關係至關重要？**  
A：訓練資料的品質高度依賴最終輸出能否正確反映原始文件或影片的結構，例如頁面必須按原始順序組回文件，影片片段也必須按時間順序重建。若失去血緣資訊，系統無法判斷哪些子項目屬於同一父節點、是否全部完成，也無法在部分失敗時只抑制受影響的父節點而讓其他父節點繼續執行。因此，將資料血緣視為執行階段的一等公民，是兼顧高效率批次處理與正確重組、容錯隔離的關鍵。

**Q4：RayOrch 的核心程式設計抽象是什麼，編譯器如何確保其正確性？**  
A：RayOrch 的核心抽象是「有序可變基數展開」與「配對匯聚」：開發者宣告一個父節點如何產生有序且數量依輸入而定的子項目序列，並宣告對應的匯聚運算將這些子項目重組回父節點結果。編譯器會驗證每一組展開與匯聚是否配對，確保資料流的結構語意正確，避免應用程式在執行時才發現成員關係或順序不一致。這種宣告式設計讓開發者專注於資料轉換邏輯，而不必自行實作成員追蹤、排序與完成判斷。

**Q5：執行階段如何同時維護血緣並實現跨父節點的批次處理？**  
A：執行階段會記錄每次展開的具體子項目集合、每個子項目的直接父節點、不可變序數以及每個結果的終止狀態，這些結構資訊與應用程式資料分開管理。為了提升 GPU 利用率，RayOrch 使用每次呼叫專屬的先進先出就緒佇列，將來自不同父節點且已就緒的子項目混合成物理批次進行分派。當匯聚發生時，系統根據宣告的成員關係與序數重建父節點結果，而非依賴批次邊界或完成順序，因此父節點只要所有必要子項目進入終止狀態就能立即前進。

**Q6：什麼是型別化父節點範圍失敗，RayOrch 如何透過它提升容錯效率？**  
A：型別化父節點範圍失敗是一種只影響特定父節點與特定呼叫階段的失敗語意，當某個父節點在某一階段回報失敗時，執行階段會抑制該父節點尚未分派的兄弟子項目，並拒絕來自同一父節點正在飛行中子項目的報告。與此同時，其他不相關的父節點仍然可以繼續執行，不會因為單一父節點失敗而全部停滯。實驗顯示，這種機制能在受控失敗注入實驗中避免 6,241 個不必要的兄弟計算進入使用者定義函式，並相較於無失敗對照組平均減少 14.93% 的牆面時間。

**Q7：論文在哪些管線與硬體上進行評估？**  
A：論文選擇了文件解析管線 MinerU 與 Docling，以及一條影片處理管線作為主要評估對象，並在 NVIDIA H20 GPU 叢集上進行實驗。MinerU 與 Docling 代表了版面豐富文件的多粒度展開需求，而影片管線則展現了片段、影格與音訊段落的層次化處理。這些管線結合了解碼、解析、CPU 轉換、GPU 推論與最終組裝，能夠充分檢驗 RayOrch 在真實基礎模型資料準備場景中的效能與擴展性。

**Q8：RayOrch 在擴展性與端對端時間上取得了哪些關鍵數據？**  
A：在 MinerU 管線中，RayOrch 從 4 張 GPU 擴展到 64 張 GPU 時取得了 15.14 倍的處理時間加速比；在影片管線中，從 8 張擴展到 64 張 GPU 則取得了 7.82 倍加速比。端對端時間方面，RayOrch 在 MinerU 上相較 Ray Data 減少 13.1%，相較 Daft 減少 29.0%；在 Docling 上相較 Ray Data 減少 16.0%。這些結果顯示 RayOrch 不僅能有效擴展到多 GPU，也能在實際管線中縮短整體執行時間。

**Q9：消融實驗與失敗注入實驗分別驗證了哪些設計的價值？**  
A：FIFO 分派機制的消融實驗顯示，啟用每次呼叫的先進先出就緒佇列可將牆面時間從 634.1 秒降至 579.3 秒，改善幅度達 8.6%，證明跨父節點批次化與獨立推進能帶來實質效益。在受控失敗注入實驗中，型別化父節點範圍失敗機制阻止了 23,514 個非觸發兄弟計算中的 6,241 個進入使用者定義函式，同時仍保留所有未受影響父節點的預期輸出。這兩項實驗分別說明了排程策略與容錯語意對於端對端效率與正確性的貢獻。

**Q10：哪些實際的基礎模型資料準備場景最適合採用 RayOrch？**  
A：RayOrch 特別適合需要反覆改變處理單位的異質資料管線，例如將 PDF 文件展開為頁面、區域與表格以產生結構化訓練記錄，或將長影片切割為片段、影格與音訊段落後進行多模態特徵萃取。這些場景的共同特徵是父項目會產生數量不均且需保持順序的子項目，並且需要在 GPU 上批次執行細粒度推論。透過將血緣控制內建於執行引擎，RayOrch 能讓開發者不必在應用層實現複雜的分組、排序與完成邏輯。

**Q11：在實際部署與產品化時，RayOrch 帶來哪些優勢與需要注意的取捨？**  
A：RayOrch 的主要優勢在於它把血緣追蹤與跨父節點批次化內建於執行階段，消除了全域重新分組的需求，從而降低延遲並簡化應用程式碼。其型別化父節點範圍失敗也提供了更細緻的容錯隔離，讓單一文件或影片的問題不會拖垮整個批次。然而，開發者需要注意 RayOrch 目前僅支援來源微批次內的有序匯聚，不支援跨微批次的通用連結、視窗或回饋迴路，因此在設計管線時應確認資料依賴範圍是否符合這些限制。

**Q12：RayOrch 對資料準備系統與基礎模型訓練基礎設施可能帶來什麼影響？**  
A：RayOrch 示範了將資料血緣視為執行階段一等公民的價值，可能促使未來的資料準備系統在設計之初就內建多粒度展開與匯聚的抽象，而非僅依賴應用程式自行維護。它結合高平行度 GPU 批次處理與正確的父子關係重建，有助於縮短大規模語料庫前置處理的端對端時間，進而加速基礎模型迭代。長遠來看，這類血緣控制的執行引擎也可能影響資料品質監控、除錯與部分重算等下游工具的設計。

**Q13：論文承認了哪些主要限制？**  
A：論文明確指出 RayOrch 目前支援的是來源微批次內的有序匯聚，並不支援通用連結、跨微批次的視窗運算或回饋迴路。這表示當管線需要合併來自不同來源微批次的資料，或需要根據後續結果動態調整前面階段時，RayOrch 的程式設計模型無法直接表達。這些限制反映了系統在專注於基礎模型資料準備常見的層次化展開場景時，為了換取執行效率與正確性所做出的設計取捨。

**Q14：在什麼樣的失敗情境或工作負載下，RayOrch 可能表現不如預期？**  
A：如果失敗無法被歸類為特定父節點與特定呼叫階段的型別化失敗，RayOrch 就難以精準抑制僅受影響的兄弟子項目，可能導致不必要的計算或過度取消。此外，當管線需要跨微批次進行狀態聚合或通用連結時，RayOrch 不支援這類運算，開發者仍需藉助其他系統或自行實現。對於子項目數量極度長尾且後續階段必須等待極大父節點全部完成的場景，雖然其他父節點可以獨立前進，但整體吞吐量仍可能受到少數超大父項目的影響。

**Q15：未來可以朝哪些方向延伸 RayOrch？**  
A：未來可以擴展程式設計模型以支援通用連結、跨微批次視窗與回饋迴路，使 RayOrch 能夠處理更廣泛的資料流模式。另一個方向是引入自適應批次化與動態資源配置策略，根據長尾分佈與 GPU 利用率即時調整物理批次大小與分派順序。此外，將血緣控制機制與資料品質監控、部分重算以及模型訓練排程器整合，也有助於打造從資料準備到模型訓練的端到端高效基礎設施。

## 實務應用指南

### 適用場景

1. **大規模文件解析與結構化管線**  
   例如使用 MinerU 或 Docling 將 PDF、掃描文件或學術論文展開為頁面、區塊、表格、圖片等細粒度單位，進行版面分析、OCR、表格還原後，再依原始文件血緣匯聚成結構化訓練記錄。RayOrch 可在跨父節點批次處理時保留頁面順序與完成狀態，避免全域重新分組。

2. **長影片分段與多模態特徵萃取**  
   將長影片依鏡頭或時間展開為片段、影格、音訊片段，分別進行解碼、視覺推論、語音辨識，最後按原始影片與時間序數重組結果。適用於基礎模型的影片-文字對訓練資料準備。

3. **網頁語料清洗與層級結構重建**  
   爬取網頁後，把每個網頁展開為段落、標題、程式碼區塊、表格與內嵌圖片，經過過濾、分類、摘要後，再依網頁父節點範圍匯聚，產生保留原始結構的訓練樣本。

4. **科學或法律長文件的多階段推理資料合成**  
   父文件先展開為章節，章節再展開為命題或問答對，經過模型推論與品質過濾後，依章節與文件血緣進行配對匯聚，確保合成資料的上下文一致性與順序正確。

5. **需要父節點範圍容錯的批次推論服務**  
   當某個父項目在特定階段發生型別化錯誤（如某 PDF 損毀導致後續頁面無法處理）時，系統可抑制該父節點未分派的兄弟節點，避免浪費 GPU 運算，同時讓其他父節點繼續執行。

### 實作前置條件

**資料條件**
- 輸入資料必須能明確定義「父項目」與其「有序可變子項目」，例如一份 PDF、一部影片、一個網頁。
- 每個父節點的展開結果需能產生不可變序數，且子節點數量分佈允許長尾（多數短、少數極長）。
- 資料來源建議已具備穩定的儲存與讀取介面，例如物件儲存（S3、GCS、MinIO）或分散式檔案系統。

**運算條件**
- 具備多張 NVIDIA GPU 的叢集環境，論文評估使用 NVIDIA H20；實務上建議至少 4–8 張 GPU 才能發揮跨父節點批次處理的效益。
- 節點間需有穩定低延遲網路，因為執行階段需要追蹤血緣、回報終止狀態與進行結果路由。
- CPU 資源需足以支撐前置的解碼、解析與 CPU 轉換階段，避免成為瓶頸。

**技術條件**
- 熟悉 Python 與 Ray 生態系，因為 RayOrch 建構於 Ray 之上。
- 能夠將現有 UDF 改寫為「展開（Expansion）」與「匯聚（Gather）」的宣告式配對。
- 具備分散式系統除錯經驗，能夠理解 FIFO Ready Queue、terminal state、typed parent-scoped failure 等執行階段語意。
- 建議先能在單機或小規模環境重現 MinerU / Docling / 影片管線的基線效能，再進行規模化。

### 實作步驟建議

1. **拆解現有管線的粒度單位**  
   先將現有資料準備流程繪製成血緣圖，標示出哪些階段會改變處理單位（例如 PDF → 頁面 → 區域 → 表格）。每個改變單位的位置就是一個潛在的 Expansion；需要重組回父節點的位置就是對應的 Gather。

2. **定義 Expansion-Gather 配對**  
   在 RayOrch 中宣告每個 Expansion 的輸出型別、子項目序數產生方式，以及對應的 Matching Gather。編譯器會驗證配對是否合法，例如 Gather 使用的成員資格與序數必須來自對應 Expansion。

3. **將模型推論封裝為 Call**  
   把 GPU 推論或 CPU 轉換邏輯封裝成 Call，設定批次大小與 FIFO Ready Queue 的保留策略。此時系統會自動將不同父節點的就緒子節點混合成物理批次，開發者不需要手動重新分組。

4. **設定終止狀態與失敗語意**  
   為每個 Call 定義何謂 terminal state，以及哪些錯誤屬於 typed parent-scoped failure。這能避免單一父節點失敗時，無謂地分派其兄弟節點，同時不影響其他父節點。

5. **逐步擴展與效能調校**  
   先以 4 GPU 驗證正確性，確認每個父節點的輸出結構、順序與完成狀態正確。再擴展到 16、32、64 GPU，觀察加速比與瓶頸。若發現長尾父節點拖慢整體，可調整保留策略或拆分過大父項目。

6. **與現有資料儲存與品質監控整合**  
   將 RayOrch 的輸出寫入資料湖或訓練資料倉儲，並針對每個父節點記錄完成狀態、失敗原因與中繼結果，方便後續品質過濾與重新執行。

### 潛在風險與注意事項

- **血緣宣告錯誤導致結果錯位**  
  若 Expansion 產生的子項目序數與 Gather 預期不一致，會造成重組後的父節點結果順序錯誤或遺漏。建議在編譯器驗證之外，加入小樣本的一致性檢查。

- **長尾分佈造成負載不均**  
  少數父節點可能產生數千個子項目，拖慢整個 microbatch。可考慮在資料前置階段拆分過大文件或影片，或為超大父節點設定獨立的保留策略。

- **失敗語意設定過寬或過嚴**  
  若將所有錯誤都設為 parent-scoped failure，可能過度抑制本可獨立完成的兄弟節點；若設得太窄，則可能浪費 GPU 運算在已知無效的父節點上。建議依錯誤型別細分。

- **狀態追蹤帶來的記憶體與網路開銷**  
  執行階段需維護每個子項目的直接父節點、不可變序數與終止狀態。在超大規模下，這些 metadata 可能成為瓶頸，需監控調度器與佇列的資源使用。

- **與現有扁平記錄系統混用時的語意落差**  
  若將 RayOrch 與 Ray Data、Daft 等扁平記錄系統串接，需特別注意轉換時是否遺失血緣資訊，避免下游又需要全域重新分組。

### 與其他技術的整合建議

- **與 Ray 生態整合**  
  RayOrch 本身建構於 Ray，因此可沿用 Ray 的叢集管理、Actor 模型與資源排程。建議將 RayOrch 作為資料準備層，與 Ray Train、Ray Serve 分別負責訓練與推論服務。

- **與物件儲存及資料湖整合**  
  輸入輸出可放在 S3、GCS 或 MinIO，並使用 Parquet、JSONL 或 Arrow 格式儲存結構化訓練記錄。中繼結果可保留在低成本儲存，供失敗重跑或品質稽核使用。

- **與現有文件/影片解析工具整合**  
  MinerU、Docling、PyMuPDF、pdf2image、FFmpeg、Decord 等可封裝在 RayOrch 的 Call 中作為 UDF。建議把 I/O 密集的解碼與 CPU 轉換放在獨立 Call，與 GPU 推論 Call 分開設定資源。

- **與 MLflow / Weights & Biases 等實驗追蹤工具整合**  
  將每個父節點的完成狀態、子項目數量分佈、失敗型別與端對端時間寫入實驗追蹤系統，便於監控資料準備管線的健康度。

- **與資料品質與去重工具整合**  
  在 Gather 之後可銜接品質過濾、語意去重、隱私檢測等模組。由於 RayOrch 已確保結構化記錄的完整性，這些下游模組可以專注於內容品質，不必處理血緣與順序問題。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從圖 1 與「為何需要血緣控制」的動機讀起，理解「粗粒度作業隱藏平行度」與「扁平記錄迫使應用程式自己分組」這兩個極端。接著對照 MinerU 或影片管線的範例，把 Expansion 想成「把一份文件拆成頁面」、Gather 想成「把頁面結果組回文件」，就能掌握核心概念，無需一開始深入 FIFO Ready Queue 的實作細節。

**AI 工程師**  
重點閱讀程式設計模型與執行階段設計，特別是 Expansion-Gather 配對、Per-Call FIFO Ready Queue 的批次形成機制，以及 typed parent-scoped failure 的語意。建議直接參考 GitHub 上的 MinerU 與 Docling 範例，將現有 UDF 改寫為 RayOrch 的 Call，並在 4→64 GPU 的擴展實驗中觀察 wall time 與加速比。

**研究人員**  
值得關注的貢獻在於「邏輯展開邊界」與「物理批次邊界」的分離：RayOrch 讓執行階段在跨父節點混合批次的同時，仍能用不可變序數與終止狀態正確解析 Gather。可進一步探討如何將此框架推廣到更一般的動態資料流、join、視窗或回饋迴路，以及在不同硬體拓撲下的排程理論分析。

**產品經理**  
本論文解決的是「大規模基礎模型資料準備」中常被低估的基礎設施問題：資料管線因為要保留父子關係而難以規模化。請聚焦於端對端時間改善（相對 Ray Data 與 Daft 分別降低 13.1% 與 29.0%）與 GPU 利用率提升，評估導入 RayOrch 對訓練資料迭代速度與成本的影響，並注意其適用於具有明確父-子-序數結構的管線，而非所有通用 ETL 場景。
