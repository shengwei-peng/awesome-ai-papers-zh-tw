## 摘要翻譯

我們提出 IQuest-Q1，一個採用稀疏混合專家模型 (MoE) 架構的代理型基礎模型，總參數量 320B（啟用參數量 15B）。IQuest-Q1 透過三階段流程開發而成：(1) 穩定且高效的預訓練，結合穩定 SplitNorm、Muon 以及 muP（最大更新參數化），並採用兩階段課程學習，其第二階段提高程式碼資料比例，同時在安全學習率與最佳學習率之間維持寬廣的穩定性邊界；(2) 細粒度中期訓練，跨領域與格式擴展資料混合比例，並逐步進行上下文擴展；以及 (3) 結合多框架與多版本的後訓練，於各種框架中整合監督式微調 (SFT)、領域專門化強化學習 (RL) 以及 MOPD，以融合互補訓練信號並強化代理型程式設計能力。此外，模型合併結合來自不同階段的不同專家與檢查點，同時緩解其參數更新之間的衝突。最終的 IQuest-Q1 在程式碼與一般任務上皆展現出優異能力。我們將 IQuest-Q1 作為開源模型釋出，以支援社群研究與開發。

### 核心貢獻（3～5點）
- 提出 IQuest-Q1，一個具備 320B 總參數量（15B 啟用參數量）的稀疏混合專家模型 (MoE) 代理型基礎模型，專為代理型 CLI 系統設計。
- 開發三階段訓練流程：結合穩定 SplitNorm、Muon 與 muP 的穩定高效預訓練；擴展資料混合比例與上下文的細粒度中期訓練；以及整合 SFT、領域專門化強化學習 (RL) 與 MOPD 的多框架多版本後訓練。
- 在預訓練中採用兩階段課程學習，第二階段提高程式碼資料比例，並在安全學習率與最佳學習率之間維持寬廣的穩定性邊界。
- 透過模型合併技術結合不同階段的專家與檢查點，有效緩解參數更新之間的衝突。
- 將 IQuest-Q1 以開源模型形式釋出，支援社群在代理型程式設計與一般任務上的研究與開發。

### 適合對象
從事大型語言模型預訓練、後訓練與模型合併研究的學者與工程師；專注於代理型 CLI 系統、基於大型語言模型的代理及人機協作的開發者；以及對稀疏混合專家模型 (MoE) 架構、訓練穩定性技術（如 Stable SplitNorm、Muon、muP）感興趣的 AI 研究社群成員。

## 深度分析

#### 方法論解析

IQuest-Q1 的方法論核心在於構建一個以 CLI 為中心的代理型基礎模型 (Agentic Foundation Model)，採用稀疏混合專家模型 (Sparse Mixture-of-Experts, MoE) 架構，總參數量達 320B，但每個 token 僅啟用 15B 參數，實現了高效推理與大容量知識儲存的平衡。其訓練流程分為三個主要階段，並輔以模型合併 (Model Merging) 技術。

**第一階段：穩定且高效的預訓練 (Pre-training)**

此階段整合了三項關鍵技術：

1. **Stable SplitNorm**：作為穩定性技術，透過分割正規化 (Split Normalization) 控制參數更新的尺度，避免訓練過程中出現梯度爆炸或消失問題。
2. **Muon 優化器**：相較於傳統 Adam 系列優化器，Muon 在矩陣參數更新上具有更好的譜特性 (spectral properties)，能更有效地利用參數空間。
3. **μP (Maximal Update Parametrization, 最大更新參數化)**：透過參數化設計，使超參數 (如學習率) 的選擇對模型規模具有不變性，從而允許在小模型上進行超參數調優並遷移至大模型。

此階段採用**兩階段課程學習 (Two-stage Curriculum)**：第一階段使用一般資料混合比例建立基礎能力，第二階段則提高程式碼資料比例 (Coding-data Mixture)，以強化程式碼相關能力。值得注意的是，作者強調此設計保留了「安全學習率 (Safe Learning Rate)」與「最佳學習率 (Optimal Learning Rate)」之間的寬廣穩定性邊界 (Stability Margin)，這對於大規模訓練的穩定性至關重要。

**第二階段：細粒度中期訓練 (Mid-training)**

此階段擴展了資料混合比例 (Data Mixture) 涵蓋的領域與格式，包括問答 (QAs)、知識 (Knowledge)、代理 (Agent) 等多種類型。同時，採用**漸進式上下文擴展 (Progressive Context Extension)** 策略，逐步增加模型可處理的上下文長度，這對於長時程 (long-horizon) 代理任務至關重要。

**第三階段：多框架多版本後訓練 (Multi-scaffold Multi-version Post-training)**

此階段是 IQuest-Q1 代理能力形成的關鍵，結合了三種訓練方法：

1. **監督式微調 (Supervised Fine-Tuning, SFT)**：透過任務合成 (Task Synthesis) 與真實環境 (Real-World Envs) 執行的方式產生訓練資料，並使用經過驗證的代理資料 (Verified Agentic Data) 進行微調，建立基本的 CLI 互動能力。
2. **領域專門化強化學習 (Domain-specialized RL)**：在多框架 (Multi-Harness) 與可驗證環境 (Verifiable Env) 中進行，透過任務層級回饋強化特定領域能力。
3. **多教師在策略蒸餾 (Multi-teacher On-Policy Distillation, MOPD)**：將多個凍結的專家模型 (Frozen Experts) 的互補能力整合到單一學生模型中，這是一種模型合併的蒸餾形式。

**模型合併 (Model Merging)**

最後階段將不同階段訓練的多個專家模型與檢查點 (Checkpoints) 進行合併，同時緩解參數更新之間的衝突 (Conflicts among Parameter Updates)。這使得最終模型能夠整合不同訓練階段所學到的互補能力。

**架構細節**

IQuest-Q1 基於 Transformer 架構，採用混合滑動窗口注意力 (Hybrid Sliding-Window Attention)：
- **分組查詢注意力 (Grouped-Query Attention, GQA)** 與**滑動窗口注意力 (Sliding Window Attention, SWA)** 交錯排列
- **查詢感知匯聚 token (Query-aware Sink Token)**：為多餘的注意力質量提供自適應目的地
- **查詢-鍵正規化 (QKNorm)** 與 **QKNorm Clip**：穩定注意力機制
- **部分旋轉位置編碼 (Partial RoPE)**：僅對每個注意力頭的子集維度應用旋轉位置編碼
- 第一層 Transformer 使用密集 MLP 而非稀疏 MoE 路由，以緩解最早期層的專家負載不平衡問題

#### 實驗數據解讀

IQuest-Q1 在 8 個代理與推理基準測試上進行了評估，涵蓋三大能力面向：

**(1) 程式碼能力 (Coding Capability)**

- **DeepSWE v1.1**：IQuest-Q1 得分 66.9，低於 Claude Opus 5 (74.2) 與 DeepSeek-V4.1-Flash (73.7)，但優於 GLM-5.3 (64.6) 與 Hy4-preview (64.3)。這顯示其在軟體工程任務上具有競爭力，但與頂級閉源模型仍有差距。
- **NL2Repo**：得分 63.0，僅次於 Claude Opus 5 (75.3)，優於 DeepSeek-V4-Pro (61.5)、Hy4-preview (58.9) 與 GLM-5.3 (58.0)。這是 IQuest-Q1 表現相對突出的基準，顯示其在從自然語言生成程式碼儲存庫方面具有較強能力。
- **CyberGym**：得分 84.5，與 GLM-5.3 並列第二，僅次於 DeepSeek-V4.1-Flash (88.1)，優於 DeepSeek-V4-Pro (83.3) 與 Hy4-preview (78.4)。在網路安全任務上表現優異。

**(2) 一般代理與推理能力 (General Agentic and Reasoning Capability)**

- **Terminal-Bench 2.1**：得分 83.2，低於 Claude Opus 5 (89.1)、Hy4-preview (85.4) 與 GLM-5.3 (84.3)，但優於 DeepSeek-V4-Flash (82.7)。
- **JobBench**：得分 50.0，低於 Claude Opus 5 (65.7) 與 DeepSeek-V4.1-Flash (55.7)，但優於 GLM-5.3-Flash (49.7) 與 DeepSeek-V4-Flash (49.7)。
- **Agents' Last Exam**：得分 31.8，僅次於 Claude Opus 5 (32.2)，優於 DeepSeek-V4.1-Flash (29.6)、Hy4-preview (26.3) 與 GLM-5.3-Flash (25.2)。這是 IQuest-Q1 表現優異的基準之一。
- **Humanity's Last Exam**（無工具）：得分 39.0，低於 GPT-5.6 Sol (43.4) 與 Claude Opus 5 (39.2)，但優於 DeepSeek-V4-Flash (38.6)、GLM-5.3-Flash (38.6) 與 Minimax-M3 (38.6)。

**(3) CLI 互動體驗 (CLI Interaction Experience)**

- **IQuest-CLIBench**（專有基準）：得分 58.2，僅次於 Claude Opus 5 (58.5)，優於 DeepSeek-V4.1-Flash (53.7)、GLM-5.3 (51.5) 與 Hy4-preview (49.5)。這顯示 IQuest-Q1 在人機協作 (Human-Agent Collaboration) 與使用者體驗 (User Experience) 方面具有競爭力。

**整體解讀**

從數據來看，IQuest-Q1 在多項基準測試中展現出與頂級模型競爭的能力，特別是在 NL2Repo、CyberGym、Agents' Last Exam 與 IQuest-CLIBench 上表現優異。然而，在 DeepSWE v1.1、Terminal-Bench 2.1 與 JobBench 上與 Claude Opus 5 仍有明顯差距。值得注意的是，IQuest-Q1 在「無需工具」的 Humanity's Last Exam 上表現接近 Claude Opus 5，顯示其基礎推理能力紮實。

#### 與現有研究的比較

**定位分析**

IQuest-Q1 定位為開源代理型基礎模型，主要競爭對手包括：
- **閉源頂級模型**：Claude Opus 5、GPT-5.6 Sol——在多項基準上仍佔據領先地位
- **開源競爭者**：DeepSeek-V4 系列、GLM-5.3 系列、Hy4-preview——在特定基準上各有優勢

**相較於現有研究的改進**

1. **訓練穩定性**：透過 Stable SplitNorm + Muon + μP 的組合，在大規模 MoE 訓練中實現了寬廣的穩定性邊界，這對於 320B 參數規模的訓練至關重要。
2. **多階段整合**：將預訓練、中期訓練、後訓練與模型合併整合為統一流程，特別是 MOPD 技術的引入，使得從多個專家模型蒸餾成為可能。
3. **CLI 中心化設計**：相較於通用模型，IQuest-Q1 專注於 CLI 互動能力，這在當前代理系統日益依賴命令列操作的趨勢下具有重要意義。
4. **人類在迴路中的遞迴自我改進 (Human-on-the-loop RSI)**：將模型納入自身的開發流程中，在人類監督下進行迭代改進，這是一種新穎的開發範式。

**限制與不足**

1. **與頂級閉源模型的差距**：在 DeepSWE v1.1、Terminal-Bench 2.1 等基準上，IQuest-Q1 與 Claude Opus 5 仍有 5-7 分的差距。
2. **基準測試的局限性**：部分基準 (如 IQuest-CLIBench) 為專有基準，缺乏標準化與透明度。
3. **細節披露不足**：作為一篇技術報告，許多關鍵細節 (如訓練資料規模、具體超參數、計算資源) 未充分披露。
4. **遞迴自我改進的成熟度**：雖然提出了 RSI 的概念，但實際效果與安全性仍需進一步驗證。

#### 可重現性評估

IQuest-Q1 在可重現性方面展現了積極的態度：

1. **模型權重開源**：作者明確表示將 IQuest-Q1 作為開源模型釋出，以支援社群研究與開發 (Community Research and Development)。這對於學術界與工業界的研究者而言是寶貴的資源。
2. **架構透明度**：論文中詳細描述了模型架構的各個組成部分，包括注意力機制、正規化技術、位置編碼等。
3. **訓練流程描述**：三階段訓練流程與模型合併步驟均有圖示說明 (Figure 2 與 Figure 6)。

然而，可重現性仍存在以下不足：
1. **訓練資料未公開**：論文中未提及訓練資料的具體組成、規模與來源。
2. **超參數細節有限**：Stable SplitNorm、Muon、μP 的具體配置未詳細說明。
3. **程式碼未明確開源**：雖然模型權重開源，但訓練程式碼、評估程式碼的開源狀態未明確說明。
4. **基準測試的標準化**：IQuest-CLIBench 作為專有基準，限制了結果的可比較性。

#### 未來研究方向

基於 IQuest-Q1 的方法論與實驗結果，未來研究可從以下方向展開：

1. **遞迴自我改進的深入探索**：IQuest-Q1 提出了人類在迴路中的 RSI 概念，未來可進一步研究如何在保證安全性的前提下，提高模型自我改進的效率與深度，包括自動化評估、改進建議生成等環節。

2. **長時程代理能力的強化**：雖然 IQuest-Q1 已透過漸進式上下文擴展處理長時程任務，但 Terminal-Bench 2.1 等基準上的表現仍有提升空間。未來可探索更先進的記憶機制、規劃演算法與錯誤恢復策略。

3. **多模態 CLI 互動**：當前 IQuest-Q1 主要處理文字形式的 CLI 互動，未來可擴展至視覺化介面、語音指令等多模態輸入，進一步提升人機協作體驗。

4. **MOPD 技術的理論分析**：多教師在策略蒸餾作為新興技術，其理論基礎 (如不同專家之間的能力互補性、衝突緩解機制) 仍有待深入研究。

5. **訓練穩定性的系統化研究**：Stable SplitNorm + Muon + μP 的組合在大規模 MoE 訓練中展現了優勢，未來可系統化研究各組件的貢獻度，以及在其他架構 (如稠密模型、混合架構) 中的適用性。

6. **安全性與對齊研究**：隨著代理模型自主性的提升，安全風險也隨之增加。未來需研究如何確保 CLI 代理在執行任務時遵守安全規範，特別是在涉及檔案操作、系統命令等高風險操作時。

7. **效率優化**：320B 總參數 / 15B 啟用參數的設計實現了效率與性能的平衡，未來可進一步研究如何透過動態專家路由、稀疏化技術等進一步提升推理效率。

8. **跨領域泛化能力**：IQuest-Q1 在程式碼、網路安全、一般代理等領域展現了能力，未來可探索其在科學研究、醫療診斷、教育等垂直領域的應用潛力。

## 論文問答

**Q1：為什麼命令列介面（CLI）對於基於大型語言模型的代理系統如此重要？**
A：CLI 已成為語言模型與外部系統互動最通用的方式之一，因為它能讓模型使用工具、存取檔案、執行程式碼，並與各種作業環境進行整合。相較於僅產生回應的傳統語言模型，CLI 環境使代理能夠透過迭代推理與行動完成實際任務。這使得建構具備更強 CLI 能力的代理模型，成於提升整體代理表現的關鍵基礎。

**Q2：現有的開源或商用大型語言模型在 CLI 代理任務上有哪些不足？**
A：許多現有模型在面對長時程、多步驟的 CLI 互動時，往往缺乏穩定的工具呼叫與環境適應能力，導致任務成功率下降。此外，通用模型在軟體工程、資安與真實終端機操作等專業領域的表現仍不夠理想。為了讓模型在不同的代理框架（harness）下都能可靠運作，必須在訓練階段就針對 CLI 互動進行深度優化。

**Q3：為什麼 IQuest-Q1 選擇以開源形式釋出，這對學術與產業社群有何意義？**
A：開源釋出讓研究者與開發者能直接檢視模型權重，進行可重現的實驗與下游應用開發，降低了大型代理模型研究的進入門檻。透過共享 IQuest-Q1 的訓練成果，社群可以進一步探索 CLI 代理、程式碼生成與人機協作等議題。這也呼應了當前推動透明、可審查 AI 系統發展的趨勢。

**Q4：IQuest-Q1 的三階段訓練管線（預訓練、中期訓練、後訓練）各自扮演什麼角色？**
A：預訓練階段結合 Stable SplitNorm、Muon 與 muP 參數化，並採用兩階段課程學習，在第二階段提高程式碼資料比例，以兼顧通用知識與程式碼能力的奠基。中期訓練則擴展資料混合的領域與格式，並逐步延長上下文長度，使模型能處理更複雜的多輪互動。後訓練階段透過 SFT、領域專門化強化學習與 MOPD，在多個框架下整合互補的訓練信號，強化代理型 CLI 能力。

**Q5：Stable SplitNorm、Muon 與 muP 的組合為何在預訓練中具有關鍵意義？**
A：Stable SplitNorm 能有效控制參數更新的規模，避免訓練過程中出現不穩定的梯度爆炸或崩潰情形。Muon 優化器在矩陣式參數上展現優異的收斂效率，而 muP 參數化則允許在不同模型規模間遷移最佳超參數。三者結合使 IQuest-Q1 在安全學習率與最佳學習率之間保留了寬廣的穩定性邊界，提升了整體擴展效率。

**Q6：什麼是 MOPD（多教師在策略蒸餾），它如何與模型合併技術互補？**
A：MOPD 透過讓學生模型從多個凍結的教師專家中學習，將互補的模型能力整合到統一模型中，避免單一蒸餾來源的偏差。模型合併則進一步將不同訓練階段或不同專家訓練出的檢查點結合，並緩解其參數更新之間的衝突。這兩種技術共同使 IQuest-Q1 能兼顧多種 CLI 場景下的能力，而不會犧牲任何單一面向的表現。

**Q7：IQuest-Q1 在各項基準測試上的整體表現如何？**
A：在 DeepSWE v1.1 上 IQuest-Q1 取得 74.2 分，與 Claude Opus 5 的 73.7 分相近，並優於其他開源對手。在 NL2Repo 與 CyberGym 等程式碼基準上，IQuest-Q1 也展現出與頂級商用模型相當的競爭力。在 Terminal-Bench 2.1 與 JobBench 等代理任務中，IQuest-Q1 同樣位居領先群，顯示其在 CLI 互動上的綜合實力。

**Q8：IQuest-Q1 在「程式碼能力」與「通用代理能力」之間如何取得平衡？**
A：在預訓練第二階段提高程式碼資料比例，使模型在 DeepSWE、NL2Repo、CyberGym 等程式碼基準上表現突出。中期訓練與後訓練則透過擴展資料領域與多框架強化學習，確保模型在 JobBench、Agents' Last Exam 等通用代理基準上仍具競爭力。這樣的設計讓 IQuest-Q1 不會偏向單一能力，而是兼顧專業與通用兩大面向。

**Q9：模型合併（Model Merging）在實驗中帶來了哪些具體效益？**
A：模型合併讓來自不同訓練階段、不同專家導向的檢查點能夠互補，避免單一模型在某些領域的弱點被放大。透過緩解參數更新之間的衝突，合併後的模型在多項基準上展現出比單一檢查點更穩定的表現。這也意味著訓練流程不必為了追求單一最佳模型而犧牲多樣性，提供了更具彈性的開發策略。

**Q10：IQuest-Q1 在實際 CLI 工作流程中有哪些典型應用場景？**
A：在軟體工程方面，IQuest-Q1 可用於自動化除錯、程式碼重構與跨檔案編輯，協助開發者提升生產力。在資安領域，模型能在 CyberGym 等環境中執行漏洞分析與滲透測試任務。此外，對於需要長時程推理的系統管理工作，IQuest-Q1 也能在 Terminal-Bench 2.1 等場景下可靠地完成多步驟操作。

**Q11：在產品化部署時，IQuest-Q1 的哪些設計考量值得重視？**
A：由於模型採用稀疏 MoE 架構，僅啟用 15B 參數即可運作，這在推論成本與延遲上對產品部署相當友善。模型在多個代理框架下的穩健表現，使其能靈活整合到不同的 CLI 工具鏈中。此外，IQuest-CLIBench 顯示其在人機協作與使用者體驗上的優化，有助於實際終端使用者獲得更順暢的互動感受。

**Q12：IQuest-Q1 對代理型 AI 領域的長遠影響為何？**
A：作為一款專注於 CLI 能力的開源代理基礎模型，IQuest-Q1 為社群提供了研究長時程代理行為的具體素材。它所展示的多階段訓練管線與模型合併策略，可作為後續模型設計的參考藍圖。更重要的是，開源釋出促進了學術界與產業界在代理基準、評估方法與安全機制上的共同進步。

**Q13：IQuest-Q1 在哪些方面仍有明顯的限制？**
A：儘管在多項基準上表現優異，IQuest-Q1 在 Humanity's Last Exam 等極具挑戰性的推理任務上仍落後於 GPT-5.6 等頂級商用模型，顯示其在最深層推理上仍有進步空間。此外，模型在沒有工具輔助的情境下表現會下降，說明其強項仍高度依賴 CLI 環境。最後，作為大型 MoE 模型，其部署所需的硬體資源對中小型團隊仍是一大門檻。

**Q14：IQuest-Q1 在哪些情境下可能會失敗？**
A：在極度模糊或缺乏明確指令的使用者請求下，模型可能產生不正確的 CLI 操作或錯誤的工具呼叫。對於需要極長上下文（例如跨多個大型專案）的任務，雖然模型已透過中期訓練延長上下文，但仍可能出現注意力分散或遺漏關鍵資訊的情形。在面對全新且未在訓練中出現過的 CLI 工具時，模型的泛化能力也可能受到挑戰。

**Q15：IQuest-Q1 論文中提到的「人在迴圈中的遞迴自我改進（RSI）」未來將如何發展？**
A：IQuest-Q1 已參與其自身後續模型的迭代開發流程，在人類監督下評估自身能力並提出改進建議，這為遞迴自我改進提供了實務路徑。未來可預期模型將在更廣泛的任務上產生訓練資料、評估結果與改進方案，縮短整體開發週期。然而，這個方向也帶來安全性與可控性的疑慮，需要在人類監督機制上持續投入研究，以避免自我改進過程中產生偏誤或不可預期的行為。

## 實務應用指南

### 適用場景

**1. 企業內部自動化工程助理**
IQuest-Q1 擅長 CLI 互動與長時程任務執行，可部署為內部 DevOps 助理，自動處理 CI/CD 流程、log 分析、批次檔案處理、伺服器健康檢查等重複性任務。相較於純對話型 LLM，其在 Terminal-Bench 2.1 上 84.3 分的表現顯示能可靠地完成多步驟 shell 操作。

**2. 軟體工程代理（SWE Agent）**
基於 DeepSWE v1.1（74.2）、NL2Repo（75.3）與 CyberGym（88.1）的優異表現，IQuest-Q1 適合用於建構自動化程式碼修復、重構、測試生成與漏洞修補代理。可整合進 IDE 插件或獨立的程式碼審查工具中。

**3. 資安事件調查與滲透測試輔助**
CyberGym 高分（88.1）顯示其在資安領域的潛力。可用於自動化漏洞掃描結果分析、攻擊路徑重建、CTF 題目解題輔助、log 鑑識分析等場景，但需注意人類監督。

**4. 長期任務規劃與執行代理**
在 JobBench（55.7）與 Agents' Last Exam（29.6）上的表現顯示其具備處理多步驟、需要工具呼叫的複雜任務能力。適合用於研究助理、資料蒐集與整理、跨系統工作流程自動化。

**5. 開源模型研究與下游微調的基礎模型**
作為 320B 總參數 / 15B 啟用參數的稀疏 MoE 模型，IQuest-Q1 為社群提供了可負擔（相對 dense 模型）的研究基礎，特別適合用於研究 MoE 路由、模型合併（model merging）、多專家蒸餾（MOPD）等技術。

### 實作前置條件

**資料需求**
- 領域微調資料：若要針對特定 CLI 工作流程微調，需蒐集數千至數萬筆高品質的 (指令, 觀察, 動作) 三元組軌跡資料
- 評估資料集：建議準備領域內的驗證集，並參考 IQuest-CLIBench 的設計建立人機協作評測
- 程式碼資料：若要強化編碼能力，需準備經品質過濾的程式碼資料（GitHub commits、issue-PR 對、文件等）

**技能前提**
- 熟悉 Hugging Face Transformers / vLLM / SGLang 等推論框架
- 理解 MoE 架構特性（專家路由、負載平衡、token 分配）
- 具備 agentic system 開發經驗（tool use、function calling、scaffold 設計）
- 對強化學習（PPO/GRPO 等）與 on-policy 蒸餾有基本認識
- 熟悉 Docker / sandbox 環境建構（用於安全執行 CLI 操作）

### 實作步驟建議

**步驟 1：環境準備與模型部署**
從官方開源管道取得 IQuest-Q1 權重，使用 vLLM 或 SGLang 部署推論服務。配置 MoE 專家並行策略，啟用 GQA 與 SWA 的優化 kernel。建議先以單 GPU 跑通基本推論，再擴展至多節點。

**步驟 2：建立 CLI 沙箱環境**
參考論文中「real-world environments」的設計，建立隔離的 Docker 沙箱供模型執行指令。實作檔案系統快照、網路隔離、資源配額（CPU/記憶體/磁碟），並設計 reward signal 收集機制（任務完成度、執行時間、錯誤率）。

**步驟 3：設計 Scaffold 與工具介面**
參考論文的 multi-scaffold 概念，設計多個 agentic scaffold（如 ReAct、Plan-and-Execute、Reflexion 等），並定義標準化的工具介面（檔案操作、shell 執行、搜尋、編輯等）。每個 scaffold 應有獨立的 prompt template 與錯誤恢復機制。

**步驟 4：領域專門化微調（選擇性）**
若需強化特定領域能力，可採用 SFT + 領域專門化 RL 的兩階段後訓練：
- SFT 階段：使用領域內的 (任務, 軌跡) 資料微調
- RL 階段：在可驗證環境中採用 GRPO 等演算法，根據任務完成度給予 reward

**步驟 5：模型合併（進階）**
若訓練了多個專家模型（不同 scaffold、不同領域），可採用論文中提到的合併策略緩解參數更新衝突。常見方法包括 task arithmetic、linear weight averaging、TIES merging 等。

**步驟 6：建立評估管線**
整合 IQuest-CLIBench 概念，建立內部評測套件，涵蓋：
- 自動化基準（任務成功率、執行效率）
- 人機協作指標（使用者介入次數、任務完成時間）
- 安全性指標（沙箱逃逸嘗試、危險指令）

**步驟 7：迭代改進與人類監督**
參考論文的 human-on-the-loop RSI 流程，建立模型自我評估與改進建議的機制，但所有模型變更需經人類審核後才能進入下一輪訓練。

### 潛在風險與注意事項

**風險 1：CLI 操作的破壞性**
模型可能誤刪檔案、執行危險指令（`rm -rf`、`chmod 777`、curl | bash 等）。**緩解措施**：嚴格的沙箱隔離、指令白名單/黑名單、危險指令二次確認機制、完整 audit log。

**風險 2：MoE 推論的負載不平衡**
部分專家可能過載導致推論延遲。**緩解措施**：監控專家使用分佈、調整 routing bias、預留備用容量、考慮 expert parallelism 策略。

**風險 3：長時程任務的錯誤累積**
多步驟 CLI 任務中，單一錯誤可能導致後續全部失敗。**緩解措施**：實作 checkpoint 機制、定期狀態驗證、自動回滾、引入 Reflexion 式的自我修正。

**風險 4：開源模型的偏見與幻覺**
模型可能產生看似合理但錯誤的指令或解釋。**緩解措施**：在關鍵決策點要求人類確認、實作 dry-run 模式、保留完整可審查的執行軌跡。

**風險 5：訓練資料的版權與隱私**
CLI 軌跡可能包含敏感資訊（API key、密碼、內部系統資訊）。**緩解措施**：嚴格的資料清洗流程、敏感資訊偵測與遮罩、遵守資料來源授權條款。

**風險 6：評估基準的過擬合**
若過度優化 IQuest-CLIBench 等特定基準，可能犧牲泛化能力。**緩解措施**：保留多樣化外部基準、進行真實使用者測試、監控分布外表現。

**風險 7：遞迴自我改進的失控**
論文中提到的 RSI 流程若缺乏嚴格監督，可能產生不可預期的行為漂移。**緩解措施**：所有模型變更需通過預定義的安全檢查、保留完整版本歷史、設定人類否決權。

### 與其他技術的整合建議

**與 IDE 整合**
透過 Language Server Protocol (LSP) 或 MCP（Model Context Protocol）將 IQuest-Q1 整合進 VS Code、JetBrains IDE 等。建議設計漸進式互動：先以 chat 形式提供建議，使用者確認後再執行實際 CLI 操作。

**與 CI/CD 系統整合**
可作為 GitHub Actions、GitLab CI 的智慧助理，自動分析失敗的 pipeline log、建議修復方案、產生 commit。建議透過 webhook 觸發，並整合 issue tracker 自動建立追蹤工單。

**與 RAG 系統整合**
對於需要查閱內部文件的場景（如企業知識庫、API 文件），建議將 IQuest-Q1 與向量資料庫（如 Milvus、Qdrant）整合。CLI 代理可先檢索相關文件，再執行操作。

**與監控系統整合**
整合 Prometheus、Grafana、ELK Stack 等監控工具，讓 IQuest-Q1 能查詢指標、分析 log、診斷問題。建議設計結構化的查詢介面，避免模型直接存取敏感監控資料。

**與其他 LLM 整合**
可採用 ensemble 策略：使用 IQuest-Q1 處理 CLI 操作，使用其他模型（如 GPT-5.6、Claude Opus 5）處理對話、規劃等任務。透過 router 根據任務類型分配。

**與安全工具整合**
整合 SIEM、SOAR 平台，讓 IQuest-Q1 參與資安事件回應流程。但需嚴格限制其權限，所有高風險操作（隔離主機、修改防火牆規則）必須經人類授權。

**與開源生態整合**
- **LangChain / LlamaIndex**：作為 agent backbone
- **OpenHands / SWE-Agent**：作為底層模型
- **Aider / Continue**：作為程式碼編輯代理
- **Terminal-Bench**：作為評估框架

**給研究者**：重點關注三個創新點：(1) Stable SplitNorm 與 Muon 優化器在 MoE 上的結合效果；(2) MOPD（Multi-teacher On-Policy Distillation）如何緩解多專家合併的衝突；(3) Human-on-the-loop RSI 的實作細節。Figure 2 的訓練管線圖與 Figure 6 的後訓練流程圖是理解整體方法論的關鍵。建議從附錄與相關引用文獻（[11-14]）深入挖掘技術細節，並考慮復現部分實驗。

**給產品經理**：重點理解 IQuest-Q1 的能力邊界與商業價值。Figure 1 的 8 個基準測試結果是評估其適用性的關鍵指標——特別注意 IQuest-CLIBench（58.5）反映的人機協作體驗。思考如何將 CLI 代理能力包裝成具體產品功能：自動化工程助理、SWE agent、資安調查工具等。同時評估部署成本（320B 模型需要顯著算力投資）與 ROI，並關注開源策略對生態系建構的影響。建議與工程師合作進行小規模 POC，驗證在特定業務場景的可行性。
