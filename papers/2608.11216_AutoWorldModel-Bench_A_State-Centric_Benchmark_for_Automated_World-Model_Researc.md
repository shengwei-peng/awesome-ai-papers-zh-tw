## 摘要翻譯

世界模型研究仍是一個尚未定論的領域：模型架構（architectures）、訓練目標（training objectives）與狀態表徵（state representations）以複雜方式交互影響，沒有任何單一方法能在所有環境中佔主導地位。這使其成為 AI 編碼代理（AI coding agents）作為自主研究者（autonomous researchers）的理想試驗平台——在這種設定中，改進方向並未預先指定，不同於目前代理基準測試（agent benchmarks）中主流的依規格工程任務（engineering-to-spec tasks）。我們提出 AutoWorldModel-Bench，這是一個閉環基準測試（closed-loop benchmark），讓前沿編碼代理（frontier coding agents）在固定運算預算（fixed compute budget）內，自主改進一個給定的初始世界模型（world-model starter）。此基準測試涵蓋八個遊戲環境（game environments），採用統一的結構化狀態表徵（structured-state representation）——從每個遊戲中擷取的真值實體狀態（ground-truth entity state），並透過共享的張量格式（shared tensor format）取用——藉此將動態建模（dynamics modeling）與感知（perception）分離，並使每次執行僅需數分鐘，從而實現快速迭代。在 64 場執行（sessions）中，Codex-5.4 與 Claude Opus 4.6 在 63 場中改進了其初始模型；在 91% 的執行中，最終勝出的修改屬於非瑣碎的研究型修改（non-trivial research-style modification）——例如新的訓練目標、表徵、rollout 程序（rollout procedure）或架構變更（architectural change）——而非超參數（hyperparameter）的微調。我們的基準測試提供了一個場景，讓前沿編碼代理能在開放式研究（open-ended research）上接受評估，而非僅限於依規格工程問題。

### 核心貢獻（3～5點）
- 提出 AutoWorldModel-Bench，首個針對自動化世界模型研究的閉環基準測試，讓前沿編碼代理能在固定運算預算內自主改進初始世界模型。
- 設計統一的結構化狀態表徵與共享張量格式，將動態建模與感知分離，使每次執行僅需數分鐘即可完成迭代。
- 透過八個遊戲環境與 64 場執行，驗證 Codex-5.4 與 Claude Opus 4.6 能在 63 場中改進初始模型，且 91% 的勝出修改為非瑣碎研究型修改。
- 提供一個評估前沿編碼代理開放式研究能力的場景，彌補現有代理基準測試偏重依規格工程任務的不足。

### 適合對象
本論文適合對自主 AI 研究代理、世界模型、AI 編碼代理評估，以及開放式科學發現自動化有興趣的研究人員與工程師；特別是關注如何設計基準測試以評估 AI 代理在方向未預先指定的研究任務上表現的讀者。

## 深度分析

#### 方法論解析

AutoWorldModel-Bench 的核心設計理念，是將「世界模型研究（automated world-model research）」從傳統的「依規格工程任務（engineering-to-spec tasks）」轉換為「開放式研究問題（open-ended research problems）」。具體而言，該基準測試（benchmark）讓前沿編碼代理（frontier coding agents）在固定運算預算（fixed compute budget）內，自主改進一個給定的世界模型入門架構（starter world-model architecture），並透過預測性能來衡量其研究成果。

**狀態表示（state representation）**  
為了將動態建模（dynamics modeling）與感知（perception）分離，作者採用「實體組件系統（Entity-Component-System, ECS）」快照來表示遊戲狀態。ECS 是遊戲引擎中常見的架構模式：實體（entities）為唯一識別的物件、組件（components）為附加在實體上的型別資料容器、系統（systems）則是依組件簽名運作的函式。AutoWorldModel-Bench 直接從遊戲模擬器中提取真值實體狀態（ground-truth entity state），並將其轉換為統一的張量格式（shared tensor format）。這種結構化狀態表示（structured-state representation）讓代理無需處理影像辨識或物件對應問題，而能專注於學習狀態轉移動態。

**環境設計（game environments）**  
該基準涵蓋八款經典街機遊戲（classic arcade games），在實體數量、動態類型（網格、連續物理、多代理）與終止條件上具有多樣性。每款遊戲的畫面都伴隨著模擬器的結構化實體狀態，使研究者能夠直接在世界模型學習層面進行控制實驗。

**閉環協議（closed-loop protocol）**  
AutoWorldModel-Bench 採用六小時運算受限的閉環協議（compute-bounded closed-loop protocol）。代理會收到一個入門世界模型架構，並可反覆執行以下循環：閱讀程式碼、形成假設（formulating hypotheses）、修改模型或訓練流程、執行實驗、分析結果、再次迭代。整個過程無需人類指定改進方向，成功與否取決於代理能否在有限預算內產生並驗證新穎假設。

**評估指標（evaluation metrics）**  
評估聚焦於實體狀態層級的動作條件預測（action-conditioned prediction at the entity-state level），包含：
- **教師強制預測（teacher-forced prediction）**：衡量單步狀態轉移的擬合能力。
- **多步開環展開（multi-step open-loop rollouts）**：衡量長期軌跡想像能力，能反映誤差累積（error accumulation）問題。
- **保留情境測試套件（held-out scenario suite）**：從特定初始狀態出發，測試碰撞、得分事件、終止條件等機制，評估規則一致性（rule consistency）與動作反應性（action responsiveness）。

**編輯分類（edit classification）**  
為了區分「真正的研究型修改」與「瑣碎的超參數調整」，作者使用零樣本評判器（zero-shot judge）對每次實驗相對於入門版本的修改進行分類，類別包括：新目標函數（new objective）、新表示法（new representation）、新展開程序（new rollout procedure）、架構變更（architectural change），以及純量旋鈕調整（scalar-knob adjustment）。

#### 實驗數據解讀

作者在 64 個（遊戲、入門模型）組合上測試了 Codex-5.4 與 Claude Opus 4.6 兩個前沿編碼代理。整體結果顯示：

**絕大多數 session 都能超越入門模型**  
在 64 個 session 中，有 63 個 session 的最終模型相較於入門版本獲得性能提升。這表示在結構化狀態與固定運算預算的設定下，現有的大型語言模型編碼代理已具備一定程度的自主世界模型研究能力，能夠在未知改進方向的情況下持續迭代。

**長期展開是進步的主要來源**  
性能提升主要集中在多步開環展開（multi-step open-loop rollouts），而非單步教師強制擬合（one-step fit）。這一現象具有重要的方法論意涵：代理發現的改進多半針對誤差累積與長期一致性問題，例如透過潛在空間正則化、多步訓練目標、自回歸精煉（autoregressive refinement）或更穩定的轉移結構來改善長期軌跡品質。相對地，單純提升單步預測準確性（accuracy）並不足以帶來長期優勢。

**91% 的勝出修改屬於研究型修改**  
零樣本評判器發現，在 91% 的 session 中，最終勝出的修改屬於非瑣碎的研究型修改，例如引入新的訓練目標、改變狀態表示、設計新的展開程序或進行架構變更；只有極少數情況是單純的超參數調整（hyperparameter tweak）。這強化了 AutoWorldModel-Bench 作為「開放式研究基準」的價值：它確實測量了代理在廣大設計空間（design space）中探索與組合新想法的能力，而非僅僅執行已知的調參流程。

**仍需注意的變異性**  
雖然成功率很高，但仍有 1 個 session 未能超越入門模型，顯示自主研究並非總能成功。這種失敗可能來自於環境難度、入門架構的品質、代理在有限預算內的搜尋效率，或是大型語言模型本身的隨機性。未來分析應進一步探討哪些遊戲特性或入門條件更容易導致失敗。

#### 與現有研究的比較

**相對於像素級或影片級世界模型**  
傳統世界模型研究多從像素（pixels）或從像素推論出的潛在變數中學習，導致感知錯誤與動態錯誤相互糾纏。AutoWorldModel-Bench 採用狀態中心（state-centric）視角，直接提供真值實體狀態，從而將動態建模本身獨立出來。這與學習緊湊狀態動態的互補路線一致，但更進一步利用遊戲引擎內部已維護的結構化實體狀態，避免物件對應與身份推論問題。

**相對於物件中心或實體中心方法**  
物件中心方法（object-centric methods）通常需要從影像中推論出一組物件或槽位（slots），而動態模型則在這些推論出的表示上運作。這類方法的挑戰在於感知錯誤會傳播到動態學習。AutoWorldModel-Bench 直接暴露模擬器的結構化實體狀態，使研究者能在受控條件下研究基於真實實體的動態學習，這是與現有物件中心研究的重要區別。

**相對於現有代理基準測試（agent benchmarks）**  
目前的 AI 研究代理評估多集中於目標與指標已預先給定的機器學習工程任務，或過於開放而難以受控復現（controlled and reproducible）的研究複製與科學發現任務。AutoWorldModel-Bench 試圖結合兩者優點：它讓代理面對真正的研究前沿——設計空間龐大、決策間交互不明、實驗在有限預算內序列展開——但同時透過保留預測性能提供可量化的成功標準。

**相對於其他世界模型評估基準**  
WorldTest/AutumnBench 側重無獎勵探索與衍生測試任務，WorldModelBench 則將影片生成模型視為世界模型進行評估。AutoWorldModel-Bench 與它們有兩大差異：（i）它是狀態中心而非像素或影片中心；（ii）它在代理側是閉環（closed-loop）的——被測試的模型是由自主編碼代理在固定運算預算內產生，而非評估一個預先訓練好的模型。

**限制（limitations）**  
儘管設計新穎，AutoWorldModel-Bench 仍有若干限制：環境僅限八款街機遊戲，領域相對狹窄；狀態完全可觀測，未涵蓋部分可觀測或感知學習情境；固定運算預算可能偏向某些需要較短訓練週期的方法；僅測試兩個大型語言模型代理，缺乏人類研究者基線；零樣本評判器的分類可能存在偏差，無法完全捕捉修改的真正新穎性；此外，大型語言模型的隨機性與 API 版本變動也可能影響結果的可復現性。

#### 可重現性評估

從提供的文本來看，AutoWorldModel-Bench 目前仍處於預印本（preprint）階段，尚未明確說明原始碼、資料集或模型權重是否公開釋出。因此，其可重現性（reproducibility）在現階段仍有待確認。

要達到嚴謹的可重現性，以下項目應該公開：
- 八款遊戲的模擬器與真值實體狀態擷取程式碼（data extraction pipelines）。
- 統一張量格式轉換與資料準備（data preparation）流程。
- 入門世界模型架構（starter architectures）與訓練腳本。
- 教師強制與多步開環展開的評估腳本，以及保留情境測試套件（held-out scenario suite）。
- 六小時固定運算預算（fixed compute budget）的精確定義，包括硬體規格、平行度與浮點運算上限。
- 代理提示詞（prompts）、實驗日誌與最終模型檢查點（model checkpoints）。
- API 版本、隨機種子（random seeds）與容器化執行環境。

此外，由於 Codex-5.4 與 Claude Opus 4.6 屬於具有隨機性的商業 API，即使釋出完整程式碼，也很難逐位元復現完全相同的研究軌跡。建議作者採取快取 API 回應、固定溫度參數（temperature）、提供多次獨立執行的統計區間，並建立公開排行榜（leaderboard）來降低復現難度。

#### 未來研究方向

**整合感知迴路**  
目前 AutoWorldModel-Bench 直接提供真值實體狀態，未來可擴展為從原始像素（raw pixels）或部分觀測中學習，要求代理同時發現狀態抽象（state abstraction）與動態模型，這將更貼近真實世界應用。

**擴展環境多樣性**  
可加入連續物理模擬（continuous physics）、三維環境、程序生成世界（procedural worlds）、多代理策略互動，以及更接近真實機器人任務的模擬器（如 MuJoCo、Habitat），以測試代理在不同動態特性下的泛化性（generalization）。

**彈性與適應性運算預算**  
除了固定六小時預算，未來可研究動態運算分配（adaptive compute allocation）或不同預算下的成本—性能帕累托前沿（cost-performance Pareto frontier），評估代理在資源極度受限或充裕時的策略差異。

**人類研究者基線與人機協作**  
引入人類研究者基線可量化 AI 代理與人類在相同時間與運算限制下的表現差距。此外，可探索人機協作研究（human-AI collaborative research），例如由人類提供高層次直覺、由代理執行實驗與迭代。

**發現修改的機制性分析**  
對代理發現的編輯進行機制性解釋（mechanistic interpretation），例如哪些設計選擇在哪些環境中有效、為何有效，將有助於提煉出可遷移的世界模型設計原則。

**自動化新穎性與安全性審查**  
隨著自主研究代理能力提升，需要自動化評判器來評估修改的新穎性、正確性與潛在風險，避免代理為了提升指標而採取投機或不可解釋的捷徑。

**下游任務驗證**  
除了預測性能，未來可將學到的世界模型應用於模型強化學習規劃（model-based RL planning）、反事實推理（counterfactual reasoning）或策略評估，驗證世界模型是否真正具備可用於決策的因果理解。

**跨環境遷移與元學習**  
研究代理是否能將在一款遊戲中發現的動態建模技巧遷移到其他遊戲，甚至發展出跨環境的元學習策略（meta-learning of world-model design），將是衡量自主研究能力的重要下一步。

## 論文問答

**Q1：AutoWorldModel-Bench 旨在解決什麼問題？**
A：這個基準測試旨在填補現有 AI 研究代理評估的缺口，因為大多數現有基準測試集中在預先指定目標、資料集與改進方向的依規格工程任務，難以評估代理在開放式研究前沿的表現。世界模型研究正好處於這樣的開放領域：模型架構、訓練目標與狀態表徵之間存在複雜交互作用，且沒有任何單一方法能在所有環境中稱霸。AutoWorldModel-Bench 因此提供一個閉環基準測試，讓前沿編碼代理在固定運算預算內自主改進世界模型，從而衡量其提出並驗證新假說的能力。

**Q2：現有的代理基準測試為何無法充分評估自主研究能力？**
A：現有的大多數代理基準測試屬於依規格工程任務，其資料集、外部指標與改進方向在實驗開始前就已大致確定，代理只需按預定規格組合已知技術即可完成。這類設定雖然便於受控且可復現的評估，卻無法反映真實研究中設計空間廣闊、決策交互不明、實驗需依序進行且成功取決於產生新假說的特質。相較之下，AutoWorldModel-Bench 要求代理在運算受限的條件下自主探索模型架構、訓練目標與推展策略，因此更能檢驗其開放式研究能力。

**Q3：為何世界模型研究適合作為自主 AI 研究代理的測試平台？**
A：世界模型研究具有廣闊的設計空間，研究人員必須在狀態表徵、動態架構、訓練目標與推展策略之間做出權衡，而這些選擇會在準確性、泛化性與計算成本上產生不同結果。由於目前沒有任何單一配方能在所有環境中佔據主導地位，系統性地探索這個設計空間具有高度科學價值，也為自主代理提供了真正的研究前沿。此外，世界模型的成功與否可以透過保留資料的預測性能來衡量，這使得開放式探索仍能保持可量化的評估標準。

**Q4：AutoWorldModel-Bench 的核心方法為何？**
A：該基準測試建立在一個統一的結構化實體狀態表徵之上，涵蓋八個經典遊戲環境，並從每個遊戲模擬器中提取真值實體狀態，再透過共享張量格式供模型使用。實驗協議為六小時運算受限的閉環協議：代理會收到一個初始世界模型架構，並在固定運算預算內自主閱讀程式碼、提出假說、修改模型、執行訓練並根據驗證結果迭代。整個流程將動態建模與感知分離，使代理能專注於學習環境動態，並實現每次執行僅需數分鐘的快速迭代。

**Q5：使用實體元件系統（ECS）結構化狀態表徵的關鍵創新是什麼？**
A：關鍵創新在於直接暴露遊戲引擎內部維護的結構化實體狀態，而非讓模型從像素或潛在變數中推斷物件身份與對應關係。這種狀態中心的方法將動態建模與感知錯誤分離，避免了物件中心方法中常見的感知誤差傳播到動態學習的問題。透過統一的 ECS 快照與共享張量格式，不同遊戲環境的狀態可以被一致地消費，使代理能夠專注於改進動態架構與訓練目標，而不必處理視覺表徵的複雜性。

**Q6：作者為何選擇遊戲環境與閉環協議作為設計？**
A：遊戲環境提供多樣化的動態挑戰，包括網格移動、連續物理與多智能體互動，同時又能透過模擬器取得精確的真值實體狀態，這在真實物理環境中難以實現。閉環協議則能忠實反映研究的本質：代理必須依序設計實驗、觀察結果、調整假說並重新執行，而非一次性完成預定任務。將運算預算固定為六小時，則確保了評估的公平性與可復現性，同時迫使代理在有限資源下做出有效的研究決策。

**Q7：實驗涵蓋哪些基準環境與設定？**
A：實驗涵蓋八個經典街機類型的遊戲環境，這些環境在實體數量、動態類型與終止條件上各不相同，能夠測試模型對不同機制的泛化能力。每個遊戲都會產生成對的視覺畫面與真值實體狀態，後者以 ECS 快照形式呈現並轉換為共享張量格式。作者針對每個遊戲與初始模型的組合進行會話，總共執行 64 個會話，並使用教師強制與多步開環推展來評估動作條件化的實體狀態預測性能。

**Q8：實驗的主要結果是什麼？**
A：在 64 個會話中，Codex-5.4 與 Claude Opus 4.6 兩個前沿編碼代理成功在 63 個會話中提升了初始世界模型的表現，顯示其具備強大的自主改進能力。進一步分析發現，性能提升主要集中在長期推展而非單步擬合上，這表示代理發現的改進更能增強模型對未來多步狀態的預測能力。此外，透過零樣本評判器對每次實驗進行分類，發現 91% 的獲勝修改屬於非瑣碎的研究式變更，例如新的訓練目標、表徵方式、推展程序或架構變更。

**Q9：對代理修改的分類分析揭示了什麼？**
A：作者使用零樣本評判器將每次代理實驗相對於初始模型進行分類，結果顯示絕大多數有效修改並非單純的超參數調整，而是涉及訓練目標、狀態表徵、推展程序或模型架構的研究式創新。這項發現至關重要，因為它證明代理不只是在已知配方中微調標量參數，而是能夠主動提出並實現新的研究想法。這也突顯了 AutoWorldModel-Bench 作為評估開放式研究能力工具的價值，因為它能區分真正的研究創新與工程層面的微調。

**Q10：這個基準測試在哪些實際場景中具有應用價值？**
A：AutoWorldModel-Bench 可直接用於評估與比較不同前沿編碼代理的自主研究能力，協助研究機構篩選更適合承擔開放式 ML 研究任務的模型。在產品開發上，這類閉環基準測試能夠協助建立自動化世界模型研究的管線，加速遊戲模擬、機器人規劃與決策支援系統中的動態模型迭代。此外，由於該基準將動態建模與感知分離，它也適合作為教學工具，幫助研究人員專注於理解不同設計選擇如何影響環境動態學習。

**Q11：在部署這類基準測試時需要考慮哪些產品與工程因素？**
A：首先必須確保資料擷取與資料準備管線的穩定性，因為任何來自遊戲模擬器的真值實體狀態錯誤都會直接影響動態模型的學習與評估。其次，固定運算預算的設計需要仔細校準，既要讓代理有足夠時間進行有意義的探索，又要避免過度寬鬆導致評估失去區分度。最後，由於代理會自主修改程式碼，平台必須具備完善的沙箱、版本控制與錯誤復原機制，以確保實驗過程安全、可追蹤且可復現。

**Q12：這項工作可能對自動化 AI 研究領域產生什麼影響？**
A：AutoWorldModel-Bench 為自動化 AI 研究提供了一個介於依規格工程任務與完全開放科學發現之間的評估橋樑，使研究者能夠在受控環境中衡量代理的開放式研究能力。透過證明前沿編碼代理能夠在世界模型設計空間中產生有意義的非瑣碎創新，這項工作鼓勵更多研究投向自主科學探索的管線設計。長遠來看，這類基準測試有助於建立標準化的自動化研究能力評估框架，加速科學發現從人類主導走向人機協作甚至自主執行。

**Q13：這個基準測試有哪些已知的限制？**
A：雖然該基準測試涵蓋八個遊戲環境，但這些環境仍屬於相對簡單的經典街機類型，與真實世界的高維度、部分可觀測環境相比仍有差距。此外，由於直接使用真值實體狀態，該基準無法評估代理同時處理感知與動態聯合學習的能力，而這正是許多實際應用中的核心挑戰。最後，六小時的固定運算預算雖然便於比較，但可能無法反映需要數天甚至數週才能收斂的真實研究專案。

**Q14：實驗中觀察到哪些失敗案例或邊緣情況？**
A：在 64 個會話中，仍有一個會話未能相對於初始模型取得提升，顯示即使在結構化狀態與快速迭代的條件下，自主代理也可能陷入無效的探索或做出損害性能的修改。部分代理修改雖然在驗證指標上獲勝，但可能僅對特定環境過擬合，而非發現具有廣泛泛化性的原理。此外，零樣本評判器的分類雖然有助於理解修改性質，但對於複雜修改的判斷仍可能存在誤差，需要進一步的人工驗證。

**Q15：未來有哪些有前景的研究方向？**
A：未來可以將基準擴展到更複雜、部分可觀測或視覺導向的環境，以評估代理在感知與動態聯合學習中的研究能力。另一個方向是延長運算預算並引入多輪元學習，觀察代理是否能夠跨環境遷移已發現的設計原則，從而實現更高效的科學探索。此外，開發更精細的評判器與可解釋性工具，以自動識別並總結代理發現的有效修改，將有助於將自動化世界模型研究從評估工具轉化為真正的研究加速器。

## 實務應用指南

## 適用場景

1. **遊戲原型與關卡設計的動態模擬器開發**  
   在遊戲開發早期，可用 AutoWorldModel-Bench 的狀態中心協定快速訓練「可想像未來幾秒遊戲狀態」的世界模型，協助設計師預測玩家行為、碰撞事件與通關條件，而無需等待完整像素級渲染管線。

2. **機器人與自動系統的緊湊轉移模型迭代**  
   若已能從模擬器或感測器融合系統取得結構化真值狀態（如物件位置、速度、類別），可借用本基準的閉環協定，在固定運算預算內自動探索動態架構與訓練目標，加速學習環境轉移模型。

3. **自主 AI 研究代理的能力評估與篩選**  
   對於正在開發或採購 AI 編碼代理的團隊，可把本基準當作「開放式研究能力」的測試場：代理必須在六小時內自主改進 starter 模型，並產生可解釋的改動分類，而非僅執行依規格工程任務。

4. **強化學習的學習環境與資料擴增**  
   將訓練好的世界模型嵌入 RL 訓練流程，作為輕量級替代模擬器，產生額外軌跡資料或進行模型預測控制（MPC），特別適合需要大量互動樣本但真實模擬成本高的場景。

5. **可解釋性與規則一致性驗證**  
   由於基準提供真值實體狀態與 hold-out 情境套件（碰撞、得分、終止條件），可用來檢驗學習模型是否學到正確的遊戲規則，適合需要對動態模型進行因果/規則審查的教育或合規應用。

## 實作前置條件

- **資料準備**  
  - 每個環境需提供「真值實體狀態」軌跡，格式建議統一為類 ECS（Entity-Component-System）的結構化張量。  
  - 動作序列、獎勵與終止旗標需與狀態時間對齊，並切分為訓練 / 驗證 / 測試集。  
  - 建議額外準備 hold-out 情境套件，針對特定機制（碰撞、得分、終止條件）進行規則一致性測試。

- **運算資源**  
  - 每個 session 至少需一張中階以上 GPU（如 NVIDIA A100 / H100 或同等級），以在六小時固定運算預算內完成多次訓練迭代。  
  - 需要 LLM API 額度供編碼代理（如 Codex-5.4、Claude Opus 4.6）與 zero-shot judge 使用。  
  - 建議配備實驗追蹤與檢查點儲存空間，避免代理中間結果遺失。

- **技能與工具**  
  - 熟悉 PyTorch 或 JAX，並具備序列建模、動態建模或強化學習基礎。  
  - 能夠操作遊戲引擎或模擬器，並從中抽取結構化狀態。  
  - 具備 LLM 代理編排經驗（tool use、prompt engineering、沙箱執行）。  
  - 建議熟悉 MLOps 工具（Weights & Biases、MLflow）與容器化部署。

## 實作步驟建議

1. **環境封裝與狀態擷取**  
   將目標環境（遊戲或模擬器）改寫為可輸出 ECS 快照的形式，統一轉換成共享張量格式，讓動態建模與感知完全分離。

2. **建立 starter 世界模型與資料管線**  
   提供一個簡單但可運作的 baseline（例如 MLP 或輕量 Transformer），並建立資料載入器、訓練迴圈與 one-step / multi-step 評估指標。

3. **設計閉環協定**  
   定義固定運算預算（如六小時）、評估頻率、early stopping 條件，以及「是否勝過 starter」的判定標準。建議同時評估長期 rollout 準確性與規則一致性。

4. **部署 AI 編碼代理**  
   讓代理能讀取程式碼、修改模型架構 / 訓練目標 / rollout 程序、執行實驗並讀取指標。務必在沙箱中執行，避免代理修改系統檔案。

5. **執行實驗與迭代追蹤**  
   代理根據實驗結果持續提出假設並修改程式碼。使用實驗追蹤工具記錄每次改動、loss 曲線與最終指標。

6. **改動分類與可解釋性審查**  
   以 zero-shot judge 對每次勝過 starter 的改動進行分類（新目標、新表示法、新 rollout 程序、架構變更或僅調整超參數），確保收穫來自研究型修改。

7. **部署與監控**  
   將勝出的世界模型匯出為標準格式（ONNX / TorchScript），整合到遊戲引擎、RL 訓練管線或決策系統中，並持續監控 drift。

## 潛在風險與注意事項

- **感知與動態脫鉤的轉移風險**  
  本基準直接使用真值實體狀態，若實際產品只能取得像素或雜訊感測資料，模型效能可能大幅下降。建議在後續階段加入感知誤差或進行 sim-to-real 驗證。

- **固定預算下的過擬合**  
  代理可能在驗證集上過度調整。應保留完全獨立的測試集與 hold-out 情境套件，並將長期 rollout 指標納入最終評分。

- **Judge 偏差與分類不一致**  
  Zero-shot judge 對「研究型修改」的定義可能因 prompt 而異。建議建立明確分類規則，並以人工抽樣驗證 judge 標註。

- **代理行為不可控**  
  自主編碼代理可能產生無限迴圈、耗盡磁碟或引入難以維護的程式碼。務必設定資源上限、程式碼 diff 審查機制與自動復原檢查點。

- **環境特定性**  
  在某款遊戲有效的架構不一定泛化到其他動態（網格、連續物理、多智能體）。建議跨多個環境驗證，避免將單一環境結果過度推廣。

## 與其他技術的整合建議

- **遊戲引擎（Unity / Unreal / Godot）**  
  在引擎內建立 ECS 狀態匯出插件，將真值實體狀態即時餵給世界模型，並把模型預測結果用於關卡預演或 AI 對手規劃。

- **強化學習框架（Ray RLlib、Stable-Baselines3）**  
  將訓練好的世界模型包裝成 gym/gymnasium 環境，作為輕量替代模擬器進行策略訓練或模型預測控制。

- **LLM 代理框架（LangChain、AutoGen、OpenAI Agents SDK）**  
  使用這些框架管理編碼代理的工具呼叫、記憶體與多輪迭代，並將實驗結果自動寫入實驗追蹤系統。

- **MLOps 與 CI/CD**  
  把閉環協定納入 nightly benchmark：每次模型或代理更新後，自動跑固定預算 session，並以儀表板呈現勝率與改動分類。

- **視覺感知模型**  
  若最終產品需要從像素輸入，可在後端串接物件偵測或場景圖模型，將其輸出轉為 ECS 格式後再餵給世界模型，形成「感知 → 動態預測 → 決策」的端到端管線。
