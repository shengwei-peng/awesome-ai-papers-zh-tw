# PolicyGuard：基於對話的子代理驗證器，確保 LLM 代理之政策遵循

**原文標題：** PolicyGuard: A Dialogue-Grounded Sub-Agent Verifier for Policy Adherence in LLM Agents  
**作者：** Seongjae Kang、Taehyung Yu、Sung Ju Hwang  
**發布日期：** 2026-06-28  
**HF 連結：** [https://huggingface.co/papers/2606.29225](https://huggingface.co/papers/2606.29225)

## ⚡ TL;DR

現有防護僅檢查工具參數，忽略對話上下文，導致LLM代理難以遵循流程層級的企業政策。
本文提出PolicyGuard，一個能讀取完整對話、依情境推理政策並提供補救回饋的子代理驗證器。
在三種模型上，PolicyGuard提升PASS4達6至12個百分點，阻擋率僅為參數防護的一半。

## 摘要翻譯

LLM 代理（LLM Agents）代表組織透過工具呼叫（Tool Calls）處理使用者請求，且必須遵循其系統提示詞（System Prompts）中所述的公司政策。先前研究將此視為安全防護（Safeguarding）問題——透過外部檢查（External Checks）阻擋不符合政策的代理行為。我們認為政策遵循（Policy Adherence）是一個更廣泛的問題：真實工作流程在多個回合中展開，需要明確使用者確認（Explicit User Confirmation）與前置讀取（Prerequisite Reads），且取決於對話內容，而非任何單一參數值（Argument Value）。要達到此門檻，需要（i）完整對話上下文（Full Conversation Context）、（ii）針對政策與當前對話進行自我推理（Self-Reasoning），以及（iii）用於引導代理下一回合的對話特定補救措施（Conversation-Specific Remediation）——這三項能力在先前的安全防護（Safeguarding）研究中經常被低估。我們提出 PolicyGuard，一個與代理共享相同對話視圖（Shared View）的子代理驗證器（Sub-Agent Verifier），能夠依上下文對政策進行推理，並為代理的下一回合提供可執行的回饋（Actionable Feedback）。在 τ²-BENCH（tau^2-BENCH）航空領域中，針對三家供應商（Vendors）（GPT-5.4、Claude Sonnet 4.6、Gemini 2.5 Pro）的每種設定各進行四次試驗，PolicyGuard 使 PASS4 分別提升 +12.0 / +6.0 / +12.0 百分點（Percentage Points, pp）。每次呼叫分析（Per-Call Analyses）顯示，PolicyGuard 達到更高的政策違規召回率（Policy-Violation Recall），同時阻擋（Blocking）頻率約為參數層級防護機制（Argument-Level Guards）的一半。

### 核心貢獻（3～5點）
- 重新定義研究問題：將 LLM 代理的政策遵循從傳統安全防護的單點阻擋視角，擴展為涵蓋多回合對話流程、前置讀取與明確使用者確認的整體政策遵循問題。
- 提出三項關鍵能力：論證達成政策遵循必須具備完整對話上下文、自我推理，以及能引導代理下一回合的對話特定補救措施。
- 設計 PolicyGuard 架構：透過與代理共享對話視圖的子代理驗證器，在上下文中對政策進行推理，並提供可執行的回饋以導正代理行為。
- 顯著提升最壞情況可靠性：在 τ²-BENCH 航空基準測試中，針對三家頂尖模型供應商，PolicyGuard 將 PASS4 提升達 +12.0 / +6.0 / +12.0 百分點。
- 實現召回率與阻擋率的更佳權衡：相較於參數層級防護機制，PolicyGuard 達到更高的政策違規召回率，同時將阻擋頻率降低約一半。

### 適合對象
從事 LLM 代理安全防護與政策遵循研究的學者與工程師；建構需執行工具呼叫並遵循複雜公司政策之企業級代理系統的產品開發者；以及關注多回合對話驗證、子代理架構與最壞情況可靠性評估的 AI 從業人員與風險管理人員。

## 深度分析

#### 方法論解析

POLICYGUARD 的核心論點在於重新定義 LLM agents（LLM 代理）的企業 policy adherence（政策遵循）問題，將其與傳統的 safeguarding（安全防護）明確區隔。過往研究多將此議題視為外部檢查（external checks）問題，透過 action gatekeepers（動作閘門守衛）阻擋有害內容（harmful content）或越獄攻擊（jailbreaks）。然而，真實 workflow 中的違規往往源於遺漏 procedural steps（程序性步驟），而非 adversarial（對抗式）攻擊。在 τ²-BENCH（tau^2-BENCH）航空情境中，約三分之二的 policy 屬於 process-level policy（流程層級政策），例如：explicit user confirmation（明確使用者確認）訂位、保險詢問與 consent（同意）、identity prerequisites（身份驗證先決條件）等。這些 predicates 是對話層級的命題，無法透過 tool arguments（工具參數）或動作順序窮舉，傳統的 argument-level guards（參數層級防護機制）與 structure-level verifiers（結構層級驗證器）在設計上即無法處理此類需求。

為此，作者群提出 policy adherence 所需的三項關鍵能力：
1. **完整對話上下文（full conversation context）**：驗證器必須讀取完整的 agent-user dialogue（代理與使用者對話），而非僅檢視單一 tool call（工具呼叫）。
2. **自我推理（self-reasoning）**：針對原始政策文本與當前對話狀態，逐條檢視 preconditions（前置條件）。
3. **對話特定補救措施（conversation-specific remediation）**：阻擋時不回傳靜態錯誤碼，而是產生可指導代理下一回合行動的自然語言回饋，例如「請先提供保險報價並詢問使用者同意」。

架構上，POLICYGUARD 是一個 verifier sub-agent（驗證子代理），部署於代理與環境之間的 tool-calling loop 中。其政策規格採用雙軌設計：保留原始政策文本，並搭配由 LLM 自動生成的 per-tool checklist（逐工具檢查清單）。當代理發出 mutation（變更操作）——如訂票或修改訂單——驗證器會評估該 tool call 是否符合清單上的每一項流程要求。若通過則放行（PASS）；若未通過，則阻擋（BLOCK）並回傳具體的 remediation 訊息，指明遺漏的 prerequisite reads（前置讀取）或下一個應該詢問的問題。

實驗採用 paired-verifier protocol（配對驗證器協議）：驗證器模型與代理模型使用同一 vendor（供應商）的同款模型，以確保跨供應商差異歸因於方法本身，而非強驗證器救援弱代理的模型能力差距。

#### 實驗數據解讀

評估基準採用 τ²-BENCH（tau^2-BENCH）航空領域，衡量指標為 PASS4——即四試全過（n=4 trials）的 worst-case reliability score（最壞情況可靠性分數）。此指標嚴格懲罰單次失敗，能反映真實生產環境對一致性的要求。

在三個 frontier（前沿）模型供應商上，PG-CHECKLIST（即 POLICYGUARD 的檢查清單配置）的 PASS4 提升如下：
- GPT-5.4：+12.0 percentage points (pp)（百分點）
- Claude Sonnet 4.6：+6.0 pp
- Gemini 2.5 Pro：+12.0 pp

值得注意的是，此配置是唯一在所有代理上均提升 PASS4，且無論在「需 refusal（拒絕）」或「需 mutation（變更）」軸向上皆未退步的設定。在較小模型 GPT-5.4-mini 配對 GPT-5.4-mini 驗證器的實驗中，PASS4 提升甚至達到 +16 pp，顯示方法在資源受限場景下仍具強健性。

Per-call analyses（每次呼叫分析）進一步揭示機制優勢：POLICYGUARD 達到更高的 policy-violation recall（政策違規召回率），同時 blocking（阻擋）率僅約 argument-level guards（參數層級防護機制）的一半。這意味著它更少過度阻擋合法請求，並在補救回合數與 near-miss rate 上均優於基線。對企業應用而言，這直接轉化為更高的任務完成率與更佳的使用者體驗。

#### 與現有研究的比較

作者群透過 Table 1 系統性比較九個代表性系統與 POLICYGUARD 在三項能力上的差異。結果顯示，過往系統至多具備部分能力，無一能同時滿足對話感知、政策自我推理與行為導向補救。

具體而言：
- **TOOLGUARD**（Zwerdling et al., 2025）作為最直接可比基線，使用 Python 防護函式檢查 tool arguments（工具參數），但對 agent-user dialogue（代理與使用者對話）完全不可見，因此結構上無法處理 process-level policy（流程層級政策）要求。
- **SOLVER-AIDED**（Winston et al., 2026）將政策轉譯為 Z3 SMT 求解器，同樣僅能處理參數層級約束，缺乏自然語言理解能力以判斷對話中的 paraphrase（改述）或隱含 consent（同意）。
- **PCAS**（Palumbo et al., 2026）雖能存取事件 DAG 與訊息文本，但其 Datalog 監控器無法對自然語言進行語義推理，僅能依賴人工調校的 string-matching（字串匹配），在面對改述時脆弱。
- **NEMO GUARDRAILS**（Rebedea et al., 2023）支援對話腳本，但屬於腳本化流程，缺乏 self-reasoning（自我推理）與動態補救。

相較之下，POLICYGUARD 明確區分 safeguarding（安全防護）與 policy adherence（政策遵循）的問題範疇：前者假設 adversarial（對抗式）攻擊者，後者假設誠實參與者但可能遺漏 procedural steps（程序性步驟）。此區分使 POLICYGUARD 能專注於對話脈絡中的 preconditions（前置條件）驗證，而非僅偵測 harmful content（有害內容）。

然而，此方法亦存在侷限。首先，LLM-as-judge 的驗證器本身引入顯著的推理延遲與成本，每次 tool call（工具呼叫）皆需額外調用 frontier 模型。其次，雖然論文主張 policy adherence 不同於 safeguarding，但真實場景中兩者範疇仍有重疊（如 refusal 與身份查驗），POLICYGUARD 並未宣稱能取代對抗式安全防護層。最後，per-tool checklist（逐工具檢查清單）由 LLM 自動生成，其正確性與完備性依賴於生成模型的能力，對於極長或高度交錯的政策文件，可能產生遺漏。

#### 可重現性評估

從論文揭露的資訊來看，τ²-BENCH（tau^2-BENCH）為公開評估基準（Yao et al., 2024; Barres et al., 2025），且基線系統 TOOLGUARD 具有公開程式碼（public code）。然而，POLICYGUARD 本身的實作細節——特別是 LLM 生成 per-tool checklist（逐工具檢查清單）的提示詞模板、verifier sub-agent（驗證子代理）的 system prompts（系統提示詞）設計，以及與 ReAct（ReAct）代理的整合介面——在提供的摘要與節錄中並未完整公開。

實驗使用商業 API 模型（GPT-5.4、Claude Sonnet 4.6、Gemini 2.5 Pro），其潛在的非確定性（non-determinism）與版本更新可能影響精確重現。paired-verifier protocol（配對驗證器協議）雖然控制變因，但不同 vendors（供應商）的 API 行為差異（如溫度參數、token 限制）仍需嚴格記錄方能重現。此外，論文提及的「我們的測量（our measurements）」暗示部分數據為作者自行蒐集，若未釋出原始對話紀錄或評分腳本，社群將難以驗證 PASS4（PASS4）的計算細節。

整體而言，方法概念清晰，但完整重現需依賴作者後續釋出原始碼、檢查清單生成流程與評估流水線（evaluation pipeline）。

#### 未來研究方向

1. **跨領域泛化**：當前驗證僅在 τ²-BENCH（tau^2-BENCH）航空領域驗證。未來可探索電商、金融、醫療等領域的 policy adherence（政策遵循），檢視 per-tool checklist（逐工具檢查清單）的遷移性，以及領域特定 preconditions（前置條件）的複雜度上限。

2. **安全防護與政策遵循的整合框架**：真實系統同時需要防範 jailbreaks（越獄攻擊）與確保 process-level policy（流程層級政策）合規。未來研究可設計分層驗證架構，讓 POLICYGUARD 與現有 safeguarding（安全防護）模組協作，明確劃分並覆蓋重疊的關切點（如 identity prerequisites（身份驗證先決條件）與 refusal（拒絕）機制）。

3. **驗證器效率最佳化**：以完整 LLM 作為 sub-agent verifier（子代理驗證器）成本高昂。可研究方向包括知識蒸餾（distillation）至輕量模型、快取對話狀態的推理結果，或將政策文本預編譯為可微分結構，以降低延遲與 API 花費。

4. **人類回饋強化的補救策略**：當前 remediation（補救措施）由驗證器單向產生。引入人類在迴路（human-in-the-loop）機制，讓客服主管標註最佳補救訊息，可進一步提升 conversation-specific remediation（對話特定補救措施）的品質與可解釋性。

5. **動態政策更新與版本控制**：企業政策經常變動。未來可研究如何讓 POLICYGUARD 自動偵測政策文本變更、增量更新 checklist，並在對話中處理新舊政策過渡期的邊界案例。

6. **多驗證器協議與對抗性測試**：擴展 paired-verifier protocol（配對驗證器協議）至多驗證器投票或階層式驗證，並針對驗證器本身進行紅隊測試（red-teaming），評估其在面對刻意誘導跳過 procedural steps（程序性步驟）時的穩健性。

## 論文問答

**Q1：為什麼現有的安全防護方法無法充分解決 LLM 代理在政策遵循上的問題？**
A：現有的安全防護方法大多將政策遵循視為外部阻擋問題，僅在工具呼叫的邊緣檢查參數是否包含有害內容或不安全參數，卻忽略了真實工作流程往往橫跨多輪對話。這些方法對於代理與使用者之間的完整對話上下文視而不見，因此無法驗證流程層級的程序性要求，例如使用者是否明確確認、是否已完成前置讀取或身份驗證先決條件。由於現有防護機制缺乏對自然語言對話的推理能力，它們只能依賴脆弱的字串匹配或靜態規則，導致在面對改述時容易失效，也無法提供引導代理下一步行動的對話特定補救措施。

**Q2：PolicyGuard 如何重新定義「政策遵循」與傳統「安全防護」之間的區別？**
A：傳統安全防護假設存在對抗式攻擊者，其失敗模式是有害內容、越獄攻擊或不安全參數，判斷依據來自單一工具呼叫；而政策遵循則假設參與者是誠實的，其失敗模式是遺漏程序性步驟，判斷依據來自整段代理與使用者對話。在 τ²-BENCH 航空基準中，約三分之二的政策屬於流程層級，例如「使用者明確確認訂位」或「已提供保險選項並取得回應」，這些都是對開放式對話的命題，而非對工具參數的約束。因此，PolicyGuard 將政策遵循視為一個更廣泛的問題，需要完整對話上下文、政策自我推理以及對話特定補救措施，而非僅是動作閘門守衛式的通過或阻擋。

**Q3：為什麼單靠系統提示詞層級的指令無法確保 LLM 代理確實遵守公司政策？**
A：儘管公司政策被寫入系統提示詞，但僅靠提示詞層級的指令並不足以讓代理在複雜的多輪互動中穩定執行所有程序性前置條件。在 τ²-BENCH 航空場景的實證測量中，即使是最前沿的 ReAct 代理，其 PASS4 分數仍存在顯著差距，顯示它們經常遺漏諸如明確使用者確認或唯讀呼叫等關鍵步驟。這是因為代理在生成工具呼叫時，往往無法自動將冗長的多頁政策規則與當前對話狀態進行精確比對與推理，因此需要一個具備對話感知與政策推理能力的外部驗證機制來補強。

**Q4：PolicyGuard 的核心架構與運作流程為何？**
A：PolicyGuard 是一個基於對話的子代理驗證器，被安置在代理與環境之間的工具呼叫迴路中，與代理共享相同的對話視圖。它會讀取完整的代理與使用者對話記錄，並針對每個變更操作，將原始政策文本與由 LLM 生成的逐工具檢查清單進行配對，在當前對話上下文中進行自我推理。若發現違規，它不會僅給出靜態阻擋訊號，而是回傳包含具體遺漏前置條件或下一個應提問內容的對話特定補救措施，直接引導代理的下一回合行動。

**Q5：相較於現有的參數層級或結構層級驗證器，PolicyGuard 的三項關鍵能力差異為何？**
A：PolicyGuard 同時具備完整對話上下文感知、政策自我推理以及驅動下一回合行為的補救能力，這是現有方法無法同時滿足的。現有的參數層級防護機制（如 TOOLGUARD）僅檢查工具參數，對代理與使用者對話完全盲目；結構層級驗證器雖能檢視動作順序，卻只能透過脆弱的字串匹配來檢查對話內容，無法理解改述後的語意。PolicyGuard 則以 LLM 作為驗證核心，能夠在完整對話中進行自然語言推理，並針對具體情境產生如「請先提供保險選項，再詢問使用者確認」這類可操作的回饋，而非僅輸出靜態的通過或阻擋標籤。

**Q6：PolicyGuard 在設計上為何選擇「子代理驗證器」而非傳統的規則引擎或求解器？**
A：作者選擇子代理驗證器架構，是因為公司政策中大量的流程層級要求本質上是對自然語言對話的語意命題，難以被傳統的規則引擎或 SMT 求解器精確形式化。例如 SOLVER-AIDED 方法雖使用 Z3 求解器，但僅能處理工具參數的約束，無法推理「使用者是否以不同措辭表達同意」這類開放式對話內容。透過將 LLM 作為驗證器，PolicyGuard 能夠彈性地將原始政策文本與逐工具檢查清單結合，在保持政策原意的同時，針對每一輪對話的獨特語境進行動態推理與補救。

**Q7：PolicyGuard 在 τ²-BENCH 航空基準上的主要實驗結果為何？**
A：在三個頂尖模型供應商（GPT-5.4、Claude Sonnet 4.6、Gemini 2.5 Pro）的評估中，PolicyGuard 的 PG-CHECKLIST 配置分別將 PASS4 分數提升了 12.0、6.0 與 12.0 個百分點，且是唯一在所有代理上均提升 PASS4、同時在拒絕必要與變更必要兩個政策軸上都未退步的配置。在較小的 GPT-5.4-mini 模型上，當代理與驗證器使用相同模型時，PASS4 的提升幅度甚至達到 16 個百分點。這些結果顯示，PolicyGuard 能夠顯著改善最壞情況下的可靠性，且其效益具有跨模型供應商的穩健性。

**Q8：每次呼叫分析（Per-Call Analyses）揭示了 PolicyGuard 相較於參數層級防護的哪些優勢？**
A：每次呼叫分析顯示，PolicyGuard 在達到更高政策違規召回率的同時，其阻擋頻率僅約為參數層級防護機制的一半。這表示 PolicyGuard 能更精準地識別真正違規的情況，減少不必要的錯誤阻擋，從而降低對正常流程的干擾。此外，PolicyGuard 所需的補救回合數更少，且在每個供應商上的近失誤率也更低，代表其回饋能更有效率地導正代理行為，而非僅僅被動封鎖。

**Q9：實驗中的「配對驗證器協定」（paired-verifier protocol）有何重要性？**
A：在實驗設計中，作者刻意讓驗證器模型與代理模型使用相同供應商與版本的模型，以確保觀察到的性能差異可歸因於方法本身，而非由更強大的驗證器去救援較弱的代理。這種配對驗證器協定提供了更嚴謹的因果推論基礎，避免了因模型能力不對稱而產生的混淆。在此公平比較下，PolicyGuard 仍能在所有三個前沿代理上穩定提升 PASS4，證明其對話感知與政策推理的設計確實能為代理帶來實質增益，而非依賴外部更強大的語言模型。

**Q10：在實際的企業應用場景中，PolicyGuard 最適合部署在哪些類型的 LLM 代理工作流程？**
A：PolicyGuard 最適合部署在需要執行實際變更操作且受嚴格公司政策規範的客戶面向 LLM 代理工作流程，例如航空訂位、訂單修改或付款請求等場景。這些應用的共同特點是政策不僅涉及參數正確性，更包含多輪對話中的程序性要求，如必須先完成身份驗證先決條件、明確取得使用者同意或提供特定資訊選項。由於 PolicyGuard 能夠讀取完整對話上下文並提供對話特定補救措施，它特別適合那些無法僅靠靜態規則或單輪檢查就能確保合規的複雜互動流程。

**Q11：從產品設計的角度來看，PolicyGuard 的「對話特定補救措施」為何比傳統的靜態阻擋更有價值？**
A：傳統的靜態阻擋僅能回傳錯誤訊息或拒絕執行，這往往導致對話中斷或代理陷入無法自行修復的僵局，需要人工介入或使用者重複請求。相較之下，PolicyGuard 的補救措施會具體指出遺漏的前置條件或代理下一回合應該提出的問題，例如「請先提供保險選項，然後詢問使用者確認」，這讓代理能夠在當前對話中無縫地自我修正並繼續服務。這種設計不僅提升了使用者體驗，也減少了客服流程中的摩擦，使代理更接近真人客服依據標準作業程序進行引導與確認的行為模式。

**Q12：PolicyGuard 對學術界與產業界在「政策遵循」研究領域可能帶來哪些影響？**
A：PolicyGuard 的核心貢獻在於將公司政策遵循從傳統的安全防護框架中獨立出來，確立了流程層級政策與對話語意推理的研究價值，這可能引導學術界發展出更多針對程序性合規的評估基準與方法論。對產業界而言，它提供了一個可實際部署的子代理驗證器架構，證明透過共享對話視圖與 LLM 推理，可以在不過度阻擋正常操作的前提下顯著提升代理的可靠性。這項研究也凸顯了單純依賴系統提示詞或參數檢查的不足，未來可能推動企業在設計代理時，更重視對話層級的合規驗證與動態回饋機制。

**Q13：PolicyGuard 目前有哪些潛在的限制或適用範圍上的邊界？**
A：PolicyGuard 主要針對誠實參與者情境下的程序性政策遵循進行設計，而非對抗式攻擊或越獄攻擊等惡意安全威脅，因此其適用範圍並不包含傳統安全防護所需處理的有害內容過濾。此外，作為一個基於 LLM 的驗證器，它的推理準確性仍然受限於底層語言模型的能力，可能在面對極度模糊或高度複雜的政策條文時產生誤判。目前的研究也僅在 τ²-BENCH 航空基準上進行驗證，雖然該基準涵蓋了豐富的流程層級政策，但其在其他領域（如金融、醫療）的泛化能力仍有待進一步研究。

**Q14：在哪些情況下 PolicyGuard 可能出現失誤或近失誤（near-miss）？**
A：儘管 PolicyGuard 的近失誤率低於現有基線，但在政策條文本身語意模糊、或使用者以高度間接與隱晦的方式表達同意與確認時，驗證器仍可能未能正確識別對話狀態而誤判為合規。另一個潛在的失誤情境是當對話歷史過長且包含大量無關資訊時，驗證器可能在注意力分散的情況下遺漏關鍵的程序性步驟。此外，若 LLM 生成的逐工具檢查清單未能完整覆蓋原始政策文本中的所有邊界條件，也可能導致特定罕見情境下的違規未被攔截。

**Q15：未來研究可以從哪些方向延伸或強化 PolicyGuard 的架構？**
A：未來研究可以探索將 PolicyGuard 的架構擴展至更廣泛的領域，例如醫療保健或金融服務，這些領域同樣具有嚴格的程序性合規要求，但對話模式與政策結構可能更加複雜。另一個方向是結合更輕量級的規則引擎與 LLM 驗證器，在保留自然語言推理彈性的同時降低推理延遲與計算成本，使其更適合高吞吐量的生產環境。此外，研究者亦可發展自動化的檢查清單生成與驗證機制，減少對 LLM 生成檢查清單的依賴，並進一步提升驗證器在面對動態更新政策時的適應性與穩健性。

## 實務應用指南

### 適用場景

1. **航空訂票與行程變更客服**  
   當 LLM 代理處理機位預訂、退改或加購行李時，必須確認「已明確告知保險選項並取得使用者回應」、「身份已透過唯讀呼叫完成驗證」等流程層級政策。這些命題建立在開放式的代理與使用者對話上，無法僅透過工具參數判斷。

2. **金融保險商品銷售與契約變更**  
   壽險或投資型商品的下單、解約、受益人變更等變更操作，通常需要「風險告知 → 使用者明確確認 → 錄音存證摘要」等程序性步驟。PolicyGuard 可讀取完整對話上下文，確認每一項前置條件已在自然語言互動中完成，而非僅檢查 API 欄位。

3. **醫療預約掛號與處方調劑代理**  
   預約手術或領取管制處方時，政策可能要求「再次確認過敏史」、「提供注意事項並取得同意」。這類流程層級政策佔實務規範相當比例，需要對話特定補救措施來引導代理在下一回合追問缺失項目。

4. **電商高風險訂單異動（退款、地址修改、付款方式變更）**  
   退款或寄送地址變更涉及資金與物流風險，政策往往要求「與使用者核對訂單細節並取得口頭確認」。參數層級防護機制只能確認金額格式正確，無法判斷對話中是否已完成核對程序。

5. **企業內部 IT 服務台權限申請**  
   當員工透過對話申請敏感系統權限時，政策可能規定「直屬主管已於對話中明示批准」或「已完成身分驗證先決條件」。PolicyGuard 作為子代理驗證器，能在工具呼叫前攔截並確認這些對話層級的命題。

### 實作前置條件

**資料準備**
- **原始政策文本**：需取得完整的公司政策文件（非僅工具參數規則），且能區分流程層級政策（約佔 τ²-BENCH 航空情境三分之二）與參數層級規則。
- **工具定義與變更操作標記**：清楚識別哪些工具呼叫屬於 mutating tools（會產生實際異動），因為 PolicyGuard 主要針對這類呼叫進行驗證。
- **歷史對話紀錄**：用於生成與校驗 per-tool checklist，並驗證改述（paraphrase）情境下的穩健性。

**運算資源**
- **與代理同級的 LLM**：論文採用 paired-verifier protocol，建議驗證器模型與代理模型使用相同供應商與等級（如 GPT-5.4 代理配對 GPT-5.4 驗證器），以確保自我推理能力對等。
- **延遲預算**：每個變更操作都需額外一次完整對話上下文的推理，需預留工具呼叫迴路中的延遲配額。

**技術能力**
- **中介層開發**：能在 Agent→Env 的工具呼叫迴路中插入驗證子代理，並讓其共享與代理相同的對話視圖（shared view）。
- **提示工程**：具備將政策文本轉換為 LLM-generated per-tool checklist 的 prompt 設計能力，並能保留原始政策文本供上下文參照。
- **補救流程設計**：能設計非靜態阻擋的對話特定補救措施，讓代理收到反饋後能在下一回合正確追問或執行前置讀取。

---

### 實作步驟建議

1. **政策盤點與切片**  
   將現行政策文件拆分為「流程層級」（如：須提供保險報價、須取得明確使用者確認、須完成身份驗證先決條件）與「參數層級」（如：日期格式、金額上限）。優先針對流程層級導入 PolicyGuard。

2. **生成 Per-Tool Checklist**  
   針對每個 mutating tool，使用 LLM 將相關政策文本轉為結構化檢查表（checklist），但保留原始政策文字作為推理上下文。此為論文中 PG-CHECKLIST 配置的核心。

3. **部署驗證子代理於 Tool-Calling Loop**  
   在代理與環境之間插入 PolicyGuard，確保其能讀取完整的代理與使用者對話（chat_history），而非僅接收單一工具呼叫的輸入輸出。

4. **設計補救訊息 Schema**  
   定義阻擋時的回傳格式，例如：`{"status": "BLOCK", "missing_prerequisite": "insurance_offer", "next_action": "offer insurance and ask user to confirm yes/no"}`。讓代理能將此 verbal feedback 直接用於下一回合的 ReAct 思考。

5. **實施配對驗證協定**  
   驗證器模型建議與代理模型同級部署，避免「強驗證器救援弱代理」的不可解釋性，使跨供應商（vendors）的差異真正歸因於方法本身。

6. **漸進式上線與監控**  
   先對單一高風險工具（如 `book_reservation`）進行試點，監控政策違規召回率與阻擋率，再擴展至所有變更操作。同步追蹤 PASS4 與每次呼叫分析指標。

### 潛在風險與注意事項

- **推理延遲顯著增加**  
  每個變更操作都需讀取完整對話上下文並進行自我推理，可能成為系統瓶頸。  
  *緩解方式*：僅對 mutating tools 啟用 PolicyGuard，唯讀呼叫可繞過；對常見政策檢查結果建立快取。

- **過度阻擋（Over-Blocking）**  
  即使論文顯示其阻擋率約為參數層級防護機制的一半，語意推理仍可能因對話改述而誤判。  
  *緩解方式*：對邊緣案例設置信賴門檻，或導入人工在環（human-in-the-loop）覆核佇列。

- **政策漂移與 Checklist 過時**  
  原始政策文本更新後，LLM-generated checklist 可能未同步失效。  
  *緩解方式*：建立政策文件版本控制與 checklist 自動重新生成管線，確保兩者連動。

- **長對話超出上下文限制**  
  多輪對話可能導致上下文長度爆炸，或稀釋驗證器對關鍵發言的注意力。  
  *緩解方式*：實作對話摘要機制，保留與政策相關的關鍵語句（如確認、拒絕、身份驗證片段）。

- **與現有安全防護職責重疊**  
  拒絕（refusal）與身份驗證先決條件等檢查可能與現有安全防護層重疊。  
  *緩解方式*：明確劃分職責——現有 guard 專責對抗式攻擊、越獄攻擊與有害內容；PolicyGuard 專注程序性步驟與政策遵循。

---

### 與其他技術的整合建議

- **與現有安全防護層（Safeguarding）串接**  
  建議形成「雙閘門」架構：現有動作閘門守衛先過濾有害內容與對抗式輸入，PolicyGuard 再接續檢查流程層級政策，最後才執行工具呼叫。

- **與參數層級防護機制互補**  
  保留 TOOLGUARD 等機制處理工具參數的型別、範圍與格式檢查；PolicyGuard 補足對話語意與程序性步驟的缺口，兩者並行而非取代。

- **與 ReAct / 規劃代理整合**  
  將 PolicyGuard 的對話特定補救措施直接注入代理的 next thought，作為 verbal feedback 引導 ReAct 循環，使代理在下一回合自動執行缺失的前置條件。

- **與可觀測性平台整合**  
  透過 LangSmith、Langfuse 等 tracing 系統記錄驗證器的 PASS/BLOCK 決策、政策違規召回率與補救回合數，建立持續優化的資料迴路。

- **與人工審核工作流整合**  
  對於 BLOCK 案例，可導入人工覆核佇列，由領域專家確認是否為真實違規，並將結果用於微調 checklist 生成提示詞。

### 給不同背景讀者的閱讀建議

**初學者**  
建議從圖 1 與表 1 開始，先建立「安全防護」與「政策遵循」的區別：前者像機場安檢，阻擋危險物品；後者像標準作業程序，確認每一步都已確實執行。重點不在技術細節，而在理解「為什麼只看工具參數不夠」——當政策要求「使用者必須明確說好」時，驗證器必須回頭讀完整對話上下文，而不是只看 API 呼叫裡的布林值。

**AI 工程師**  
請聚焦論文的系統架構與實驗設定。特別注意三個實作細節：(1) verifier 在 tool-calling loop 中的確切位置（Agent→Env 之間）；(2) per-tool checklist 如何與原始政策文本配對使用；(3) 為何採用 paired-verifier protocol（verifier model = agent model）。這三點直接決定了你在現有代理框架中插入中介層時的設計取捨。

**研究人員**  
請深入分析 §2 Related Work 的 Table 1，觀察 conversation-awareness、self-reasoning、remediation 三項能力的組合缺口。論文的核心貢獻在於將 policy adherence 從 safeguarding 中獨立出來，並以 τ²-BENCH 的 process-level policy 證明：僅檢查工具參數或動作順序的結構層級驗證器，在結構上就無法處理對話層級的程序性步驟。

**產品經理**  
請關注 PASS4 提升數據與每次呼叫分析。+12.0 百分點的最壞情況可靠性分數意味著代理在四次獨立執行中全部成功的機率顯著提高；而「阻擋率減半但政策違規召回率更高」則代表更少的用戶流程中斷與更高的合規信心。評估導入成本時，請同時計算額外的 LLM 推理延遲、政策文件維護開銷，以及與現有客服系統整合所需的中介層開發資源。
