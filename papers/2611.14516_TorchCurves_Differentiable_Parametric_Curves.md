## 摘要翻譯

我們提出 TorchCurves，一個將向量值（vector-valued）參數曲線視為可學習基元（learnable primitives）的 PyTorch 函式庫。其核心運算將批次的純量輸入映射至 B-樣條（B-spline）或勒讓德多項式（Legendre Polynomial）基底所表示曲線上的點，並支援對輸入與係數進行微分。曲線係數（curve coefficients）可與周邊模型共同最佳化，或由另一個網路產生。該函式庫提供可訓練模組（trainable modules）、可重複使用的基底模組（basis modules）以及函式介面（functional interface），支援從連續特徵嵌入（continuous feature embeddings）到 Kolmogorov-Arnold 網路（KAN）以及函數回歸（functional regression）等應用。其實作結合古典求值演算法與向量化 PyTorch 運算（vectorized operations），強調可讀性（readability）與可維護性（maintainability），且無需自訂硬體核心（custom hardware kernels）。計時實驗（timing experiments）將曲線求值（curve evaluation）與 NumPy 和 SciPy 進行比較，並將 KAN 訓練與 EfficientKAN 進行比較，涵蓋各種問題規模（problem size）。結果說明此通用性在哪些情況下仍具計算實用性，以及在哪些情況下計算負擔（computational overhead）顯著。函式庫已於 GitHub 上公開，網址為 https://github.com/alexshtf/torchcurves。

### 核心貢獻（3～5點）
- 提出 TorchCurves 函式庫，將向量值參數曲線視為可學習基元，統一支援 B-樣條與勒讓德多項式兩種基底表示。
- 實現對曲線輸入與係數的雙向微分，使曲線係數可與下游模型端到端聯合最佳化，亦可由其他網路動態產生。
- 提供模組化（可訓練模組、基底模組）與函式化雙重介面，涵蓋連續特徵嵌入、Kolmogorov-Arnold 網路（KAN）、函數回歸等多元應用場景。
- 結合古典求值演算法與向量化 PyTorch 運算，在不依賴自訂硬體核心的前提下兼顧可讀性與可維護性。
- 透過系統性計時實驗，量化界定該通用設計在不同問題規模下的計算實用性邊界。

### 適合對象

TorchCurves 的核心方法論建立在「將參數曲線（parametric curves）視為可學習基元（learnable primitives）」這一抽象概念之上。其數學基礎相當直觀：給定一條曲線 $c(x) = \sum_{i=1}^{n} v_i B_i(x)$，其中 $B_i$ 為基底函數（B-spline 或 Legendre 多項式），$v_1, \ldots, v_n$ 為可學習係數，函式庫的核心運算即為將一批純量輸入映射至多維曲線上的點。

**基底函數設計的雙重選擇**

函式庫同時支援 B-spline 與 Legendre 多項式兩種基底，這是一個重要的設計決策。B-spline 的優勢在於其局部支撐性（local support），即修改某個區間的係數僅影響該區間附近的曲線形狀，這對平滑度控制與局部擬合特別有利。Legendre 多項式則是全域基底（global basis），具有正交性與解析表達式明確的優勢，適合需要全域逼近或與數值方法（如譜方法）整合的情境。兩種基底共享同一介面，使研究者能在不改動模型架構的前提下切換表示方式。

**輸入映射機制的必要性**

由於 B-spline 與 Legendre 多項式本質上定義於緊緻區間（compact interval），預設為 $[-1, 1]$，但機器學習中的輸入特徵往往無界。TorchCurves 透過 `input_map` 參數提供數種映射策略來解決此問題：

- `real.arctan`：將 $x \mapsto \frac{2\arctan(x)}{\pi}$，這也是預設選項，提供平滑且雙射的映射
- `real.rational`：將 $x \mapsto \frac{x}{\sqrt{1+x^2}}$，靈感來自微分方程文獻中處理無界域的方法（Boyd, 1987；Guo and Wang, 2004）
- `real.clamp`：直接截斷至 $[-1, 1]$，最簡單但可能在邊界產生不連續
- `nonneg.*`：針對非負輸入的對應版本

這種設計承認了一個常被忽略的事實：基底函數的數值穩定性高度依賴於輸入域的適當變換。

**三層 API 架構的設計哲學**

函式庫刻意區分三個抽象層次：

1. **可訓練模組（trainable modules）**：如 `BSplineCurve` 與 `LegendreCurve`，繼承自 `torch.nn.Module`，內建可學習參數
2. **基底模組（basis modules）**：快取中間張量以避免重複計算，但本身無可訓練參數，適合係數由外部網路產生的場景
3. **函式介面（functional interface）**：純函式，無狀態，類似 `torch.nn.functional`，提供最大靈活性

這種分層設計反映了 PyTorch 生態中「模組化封裝 vs. 函式化組合」的經典權衡。值得注意的是，函式介面允許曲線係數由另一個神經網路動態產生，這對 conditional generation 或 meta-learning 應用至關重要。

**純 PyTorch 實作的取捨**

作者明確聲明未實作自訂硬體核心（custom hardware kernels），而是選擇純 PyTorch 實作以換取可讀性與可維護性。這是一個務實的工程決策：對於研究階段的函式庫而言，演算法的清晰度往往比極致效能更重要。向量化（vectorization）消除了特徵、批次與曲線維度上的迴圈，但仍依賴 PyTorch 的標準運算子。

#### 與現有研究的比較

TorchCurves 的定位需要從三個層面理解：

**與數值軟體的關係**

NumPy 與 SciPy 提供成熟的 B-spline 與多項式求值，但它們不原生支援 PyTorch 的自動微分（autograd）。TorchCurves 的核心貢獻在於將這些經典演算法整合進可微分計算圖（computational graph），使曲線係數與輸入都能透過反向傳播（backpropagation）進行最佳化。

**與既有可微分樣條套件的關係**

論文中提到的 `torchcubicspline`（Kidger）專注於從觀測值構造自然三次插值（natural cubic interpolation），這是一個不同的問題——它解決的是「給定資料點，構造插值曲線」，而非「給定參數化曲線，學習其係數」。`torch-bspline`（Melchers and Cochran, 2025）則更接近 TorchCurves 的功能，提供可微分 B-spline 求值。TorchCurves 的差異化在於：

- 同時支援 B-spline 與 Legendre 多項式
- 提供三層 API（模組、基底、函式）
- 明確支援「係數由外部網路產生」的模式
- 強調可讀性與可維護性

**與 KAN 生態的關係**

Liu et al. (2025) 的 Kolmogorov-Arnold 網路將可學習單變量函數作為網路邊，而 EfficientKAN（Cao, 2024）是其高效實作。TorchCurves 並非要取代這些實作，而是提供更通用的底層抽象。KAN 是曲線的一個特定應用，而 TorchCurves 試圖服務所有需要「可微分參數曲線」的場景。

**定位的優勢與限制**

優勢：
- 抽象層次恰當，將曲線提升為一等公民（first-class citizen）
- 介面設計考慮了多種使用模式
- 純 PyTorch 實作降低了貢獻門檻

限制：
- 缺乏 GPU 最佳化，在大規模應用中可能成為瓶頸
- 目前僅支援兩種基底，缺少 Chebyshev、傅立葉基底等選項
- 與領域專用實作（如 EfficientKAN）相比，通用性帶來的效能損失在某些場景下可能不可忽略

A：在需要極高效能的大規模部署場景中，TorchCurves 可能因為缺乏自訂硬體核心而表現不佳，特別是當曲線數量、批次大小或多項式次數都非常高時。在即時推論或邊緣裝置部署中，純 PyTorch 實作的開銷可能成為瓶頸。此外，對於需要特殊曲線表示（如週期樣條、球面樣條等）的應用，目前的基底選擇可能不夠用。

## 實務應用指南

### 適用場景

1. **表格資料的數值特徵嵌入（Numerical Feature Embeddings for Tabular Data）**
   在金融、信用評分、醫療紀錄等表格資料任務中，原始的連續數值（如年齡、收入、血壓）通常直接餵入模型，缺乏平滑性與可學習性。TorchCurves 可將每個數值特徵映射為一條可學習曲線上的向量點，作為神經網路的輸入嵌入，取代傳統的線性投影或固定分箱（binning）。相較於 Gorishniy 等人的 PLR / Periodic 嵌入，這種做法在 B-spline 與 Legendre 基底下更具表達力，且支援端到端訓練。

2. **Kolmogorov–Arnold 網路（KAN）建構**
   對於科學機器學習（scientific ML）任務，例如 PDE 求解、符號回歸、物理資訊神經網路（PINN），KAN 架構以可學習的一元函數取代 MLP 的固定活化函數，往往在低維平滑函數上表現優異。TorchCurves 提供統一的曲線基元，可直接組裝成 KAN 層，並與既有 PyTorch 優化器無縫整合，無需依賴 EfficientKAN 等特定實作。

3. **函數回歸與函數逼近（Functional Regression）**
   在統計學習與訊號處理中，常需從稀疏或帶噪樣本中估計一條平滑曲線。TorchCurves 的 B-spline 曲線可作為非參數回歸器，係數透過梯度下降擬合；Legendre 多項式則適合在固定區間 \([-1, 1]\) 上做譜展開（spectral expansion），用於頻域分析或函數分解。

4. **時間序列與訊號的平滑表示**
   對於感測器資料、ECG、語音特徵等一維訊號，可將時間軸視為輸入特徵，將訊號值視為曲線輸出，學習一條平滑、可微分的曲線表示。這種表示對資料增強、異常偵測、插值都很實用，且曲線係數本身就是壓縮後的潛在表示。

5. **電腦輔助幾何設計（CAGD）與貝茲曲線類應用**
   在 CAD、字型設計、動畫路徑生成中，B-spline 是業界標準。TorchCurves 雖未直接提供貝茲曲線，但其 B-spline 基底可作為可微分幾何建模的基礎，允許曲線形狀由神經網路輸出（例如從圖片生成設計草圖），並透過下游任務（如物理模擬、渲染損失）端到端最佳化。

### 實作前置條件

**資料需求**
- 結構化表格資料（CSV/Parquet），含連續數值特徵；或
- 一維訊號／時間序列資料；或
- 函數回歸任務中的 \((x_i, y_i)\) 配對樣本。
- 資料規模彈性大，從數千筆到數百萬筆皆可，但需注意批次維度對記憶體的影響。

**計算資源**
- 建議使用 GPU（CUDA）以加速 PyTorch 運算；CPU 亦可運行但速度較慢。
- 純 PyTorch 實作意味著無需特殊硬體或編譯工具鏈。
- 對於大型 KAN 架構（高維輸入 × 大量曲線），VRAM 需求會顯著上升。

**技能門檻**
- 必備：熟悉 PyTorch 基本操作（`nn.Module`、`autograd`、`DataLoader`）。
- 建議：理解 B-spline 與 Legendre 多項式的數學基礎（節點、階數、區間映射）。
- 進階：若要自訂 `input_map` 或整合到複雜模型，需具備 Python 函數設計與張量操作能力。

### 實作步驟建議

1. **釐清任務與曲線類型選擇**
   - 若資料分佈在緊緻區間且需要局部控制，優先選 **B-spline**（可調節點數、階數）。
   - 若需要全域平滑逼近或頻譜分析，選 **Legendre 多項式**（固定 \([-1,1]\) 區間，階數即表達力）。
   - 確認輸入特徵的範圍，選擇合適的 `input_map`（如 `real.arctan` 處理無界實數，`real.clamp` 處理已知邊界）。

2. **安裝與環境驗證**
   ```bash
   pip install torchcurves
   ```
   執行官方範例確認安裝成功，並對照 GitHub 倉庫的 README 確認版本相容性。

3. **原型驗證（單一曲線）**
   - 先用小批次資料（如 32 筆樣本）建立單一 `BSplineCurve` 或 `LegendreCurve` 模組。
   - 設定 `num_curves`、`dim`、`degree`、`num_knots` 等超參數，觀察輸出形狀是否符合預期。
   - 驗證梯度流：呼叫 `loss.backward()` 確認 `coefs` 與上游網路參數皆收到梯度。

4. **整合到下游模型**
   - **表格資料**：將每個連續特徵替換為一條曲線，輸出向量串接後送入 MLP。
   - **KAN**：以曲線模組取代 `nn.Linear` 層，組合多層形成 KAN 架構。
   - **函數回歸**：直接擬合曲線係數，最小化與目標函數的 MSE。

5. **超參數調校**
   - B-spline：階數（3–7 為常用起點）、節點數（控制擬合彈性）。
   - Legendre：階數（10–100，依平滑度需求）。
   - 學習率：曲線係數通常需要比一般網路權重更小的學習率（如 \(10^{-3}\) 至 \(10^{-4}\)）。

6. **效能基準測試**
   - 參考論文中的計時實驗，對自己的問題規模評估曲線求值與訓練時間。
   - 若發現瓶頸，考慮降低 `num_curves` 或 `degree`，或改用 `basis` 模組快取中間張量。

7. **部署與監控**
   - 將訓練好的曲線係數儲存為 `state_dict`，隨模型一同序列化。
   - 在推論階段，使用函式介面（functional API）以避免模組實例化開銷。

### 潛在風險與注意事項

1. **計算負擔顯著**
   論文明確指出，純 PyTorch 實作在大型問題上會有 substantial overhead。對於高維輸入 × 大量曲線的 KAN，訓練時間可能遠高於 EfficientKAN 等專用實作。**緩解措施**：先用小模型驗證概念，必要時考慮自訂 CUDA 核心或改用 JAX/Flax 等編譯式框架。

2. **超參數敏感度高**
   B-spline 的節點數、階數與 Legendre 的階數對模型表現影響極大，且無統一準則。**緩解措施**：建立驗證集網格搜尋流程；對 Legendre 階數做由小到大的逐步增加觀察過擬合現象。

3. **區間映射的隱含假設**
   預設 `input_map='real.arctan'` 將實數壓縮到 \((-1, 1)\)，但這個非線性變換會改變特徵的相對距離，可能影響模型可解釋性。**緩解措施**：若需保留線性距離，改用 `real.clamp` 並明確邊界；若資料恆正，用 `nonneg.*` 系列。

4. **梯度爆炸或消失**
   高階多項式（特別是 Legendre）在邊界附近梯度可能極大。**緩解措施**：使用梯度裁剪（gradient clipping）；對輸入做標準化；選擇較低階數。

5. **與現有 KAN 實作不相容**
   TorchCurves 的曲線介面與 EfficientKAN 的內部結構不同，無法直接載入彼此權重。**緩解措施**：若需遷移，須重新訓練或撰寫權重轉換腳本。

6. **缺乏自訂硬體最佳化**
   對於即時推論或邊緣部署，純 PyTorch 實作可能不夠快。**緩解措施**：推論階段可將曲線係數預計算並轉為靜態查表（lookup table）。

### 與其他技術的整合建議

1. **與 PyTorch 生態整合**
   - **優化器**：直接使用 `torch.optim.Adam`、`AdamW` 等，無需特殊處理。
   - **學習率排程**：可搭配 `torch.optim.lr_scheduler`，但建議對曲線係數與其他參數使用不同學習率群組。
   - **分散式訓練**：透過 `DistributedDataParallel` 自動支援，但需注意批次維度對通訊成本的影響。
   - **TorchScript / ONNX 匯出**：目前函式介面較容易追蹤（trace），模組介面可能需要實作 `forward` 的標準化。

2. **與 EfficientKAN 互補**
   - 若專案已使用 EfficientKAN，可將其內部一元函數替換為 TorchCurves 模組，以獲得更靈活的基底選擇（B-spline vs. 純樣條）。
   - 反之，若需要極致效能，可先用 TorchCurves 快速實驗，再將訓練好的曲線係數移植到 EfficientKAN 的固定結構中。

3. **與特徵工程管線整合**
   - 在 sklearn 管線中，可將 TorchCurves 曲線包裝為自訂轉換器（transformer），但需注意 PyTorch 張量與 numpy 陣列的轉換成本。
   - 對於大規模表格資料，建議先在 PyTorch `DataLoader` 中完成曲線求值，再送入下游模型。

4. **與符號回歸工具整合**
   - 將訓練好的 B-spline 曲線取樣後，可餵入 PySR、SINDy 等符號回歸工具，嘗試發現解析表達式。

5. **與視覺化工具整合**
   - 使用 TensorBoard 或 Weights & Biases 記錄曲線係數隨訓練的變化，有助於診斷學習動態與過擬合。

**研究者**：第 2 節的相關工作提供了完整的定位圖譜——從 NumPy/SciPy 的傳統數值軟體，到 `torchcubicspline`、`torch-bspline` 等專用套件，再到 EfficientKAN 等應用驅動實作。TorchCurves 的貢獻在於「將曲線本身提升為可組合的可學習基元」，這對函數空間學習、神經 ODE、隱式神經表示等方向都有啟發。建議進一步閱讀 B-spline 與 Legendre 多項式的評值演算法（如 de Boor 演算法），理解其與自動微分的互動。

**產品經理**：TorchCurves 解決的是「如何讓模型更平滑地處理連續數值」這個普遍需求，適用於金融、醫療、工業等表格資料密集的場景。採用此技術的決策點在於：是否願意為可解釋性與平滑性付出額外的訓練時間成本。論文的計時實驗明確指出 overhead 在哪些規模下「substantial」，這是評估 ROI 的關鍵資訊。建議先在一個小規模 POC 中驗證業務指標（如 AUC、RMSE）的提升幅度，再決定是否擴展到全量資料。
