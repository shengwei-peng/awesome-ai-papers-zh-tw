## 摘要翻譯

隨著大型語言模型（LLM）逐漸演進為自主代理，對統一評測基礎設施的需求日益迫切。然而，現有的評測流程仍然高度碎片化且緊密耦合，妨礙了可重現性，並導致重複工程。為了解決此問題，我們提出 AgentCompass，一個開源、輕量級且可擴充的基礎設施，用於評測基於 LLM 的代理。AgentCompass 以三個獨立元件為核心組織評測流程，即基準測試（Benchmark）、執行框架（Harness）與環境（Environment），從而實現彈性配置，而無需重新實作複雜的執行邏輯。此外，它具備容錯非同步執行環境與完備的軌跡分析工具，能夠透明地診斷諸如獎勵駭取（reward-hacking）等細微的失效模式。AgentCompass 原生支援超過 20 個橫跨五項能力維度的基準測試，為社群提供可擴展且可重現的基礎設施，以推進代理研究。

### 核心貢獻（3～5點）
- 提出統一評測基礎設施 AgentCompass，將評測流程解耦為基準測試（Benchmark）、執行框架（Harness）與環境（Environment）三個獨立元件，支援彈性配置並避免重複工程。
- 設計容錯非同步執行環境，能夠穩定處理長時間執行的代理軌跡與大規模平行化評測。
- 提供完備的軌跡分析工具，可透明地診斷獎勵駭取（reward-hacking）等細微的失效模式。
- 原生支援超過 20 個基準測試，涵蓋工具使用、程式編寫、網頁與研究、生產力與科學推理等五項能力維度。
- 以開源、輕量級、可擴充且可擴展的架構，提升代理研究的可重現性並降低評測門檻。

### 適合對象
本論文適合從事基於 LLM 的代理、自主代理與代理評測研究的學者與工程師，特別是關注基準測試設計、可重現性、軌跡分析與大規模評測基礎設施的讀者；對於希望整合多項基準測試、降低重複工程並系統性診斷代理失效模式的研究團隊亦具高度參考價值。

## 深度分析

#### 方法論解析

AgentCompass 的核心方法論在於將傳統上緊密耦合（tightly coupled）的代理評測流程，解構為三個可獨立配置的核心元件：**基準測試（Benchmark）**、**執行框架（Harness）** 與 **環境（Environment）**。這種解耦（decoupling）設計使得研究者能夠以「基準測試 × 執行框架 × 環境」的組合方式來定義一次評測，而不必為每一個新資料集或新互動協定（interaction protocol）重新實作複雜的執行邏輯（execution logic）。

在具體實作上，AgentCompass 透過一份宣告式的 **RunRequest** 來描述一次評測。RunRequest 將評測的實質內容與執行時的運作選項分離：
- **BenchmarkSpec** 負責定義任務內容與評測指標；
- **HarnessSpec** 定義代理與每個任務互動的程序；
- **EnvironmentSpec** 指定執行脈絡；
- **ModelSpec** 描述模型端點、憑證、推論參數與支援的 API 協定；
- **ExecutionSpec** 則獨立管理執行時選項，例如平行化、容錯與資源配置。

這種分離的優勢在於，研究者可以在同一個 **基準測試（Benchmark）** 上比較多個 **執行框架（Harness）**，也可以將同一個 Harness 跨不同 Benchmark 重複使用，甚至能夠在不改寫基準測試程式碼的前提下，測試不同的互動協定。為了實現這種組合彈性，AgentCompass 採用輕量的裝飾器式註冊表（decorator-based registries）來管理 Benchmark、Harness、Environment、Recipe 與 Analyzer，讓新元件可以透過本地註冊的方式加入，而無需修改中央執行環境或其他無關模組。

在執行層面，AgentCompass 提供了一個**容錯非同步執行環境（fault-tolerant asynchronous runtime）**，專門為長時間執行的代理軌跡（long-running agent trajectories）進行平行化（parallelizing）處理。這對於需要多次工具呼叫（tool calls）與環境回饋（environment feedback）的互動式代理工作流程（interactive agent workflows）尤為重要。執行過程中產生的中間行動（intermediate actions）、工具呼叫、標準輸出／錯誤、回傳碼與環境檔案等，都會被記錄為完整的 **軌跡（trajectory）**，供後續的 **軌跡分析（trajectory analysis）** 與視覺化（visualization）使用。

此外，AgentCompass 內建多種評分機制，包括確定性比對、執行驗證與 **LLM-as-judge** 評分，並能透過軌跡層級分析來透明地診斷細微的失效模式（nuanced failure modes），例如 **獎勵駭取（reward-hacking）**。這種透明性對於理解代理在動態環境（dynamic environments）中的真實行為至關重要。

#### 實驗數據解讀

雖然提供的上下文未包含完整的實驗表格，但從摘要與圖一（Figure 1）可以觀察到幾個關鍵訊息。AgentCompass 原生支援超過 20 個基準測試，涵蓋五大核心評測維度（core evaluation dimensions）：**工具使用（tool use）**、**具代理性的能力（agentic）**、**程式編寫（coding）**、**網頁與研究（web & research）**、**生產力（productivity）** 與 **科學推理（scientific reasoning）**。圖一展示了數個代表性模型（representative models）在這五個維度上的能力輪廓（capability profiles）。

從能力輪廓可以推論出以下幾點：
1. **模型能力並非均勻分佈**：不同模型在不同維度上表現差異顯著，例如某些模型在程式編寫（coding）上表現突出，但在科學推理（scientific reasoning）或網頁研究（web & research）上相對較弱。這凸顯了單一分數無法完整描述代理能力，必須透過多維度評測來進行全面評估。
2. **統一基礎設施的價值**：由於所有模型都在同一套 AgentCompass 框架下進行評測，結果具有較高的可比較性，減少了因不同評測套件（isolated evaluation suites）所導致的基線實作（baseline implementations）不一致問題。
3. **軌跡分析的重要性**：透過記錄完整的代理軌跡（agent trajectories），研究者可以進一步分析模型在特定維度上失敗的原因，例如是否因為工具呼叫順序錯誤、對環境回饋理解不足，或是出現獎勵駭取（reward-hacking）等投機行為。

整體而言，AgentCompass 的實驗設計強調的不是單一排行榜，而是提供一個可擴展、可重複且可診斷的評測生態系統，讓社群能夠系統性地追蹤代理能力（agent capabilities）的進展。

#### 與現有研究的比較

在現有研究中，代理評測領域呈現高度碎片化（fragmented）的狀態。許多專門基準測試（specialized benchmarks）各自擁有獨立的資料格式（data formats）、執行環境與評分協定（scoring protocols），導致重複工程（redundant engineering）與可重現性（reproducibility）下降。相較之下，AgentCompass 的定位是一個**統一評測基礎設施（unified evaluation infrastructure）**，其改進與限制可分述如下：

**相較於既有基礎設施的改進：**
- **相較於 AgentGym**：AgentGym 強調跨多樣環境的代理演化（evolving agents），而 AgentCompass 更專注於評測流程的模組化與可重複性，並提供完整的軌跡分析工具。
- **相較於 Harbor**：Harbor 雖然也針對代理導向評測，但其重點偏向程式編寫與技能型場景（coding and skill-based scenarios）。AgentCompass 則涵蓋更廣泛的能力維度，包括科學推理、生產力與網頁研究等。
- **相較於 OpenCompass 與 VLMEvalKit**：OpenCompass 主要針對廣泛的推理與安全性評測，VLMEvalKit 聚焦於圖文多模態評測，兩者對於互動式代理工作流程（interactive agent workflows）的原生支援較為有限。AgentCompass 填補了這一缺口，專為需要反覆環境互動（environment interaction）的代理設計。
- **相較於 MASLab**：MASLab 專注於多代理系統（multi-agent systems），而 AgentCompass 目前更側重於單一代理的能力評測，雖然其模組化設計未來可擴展至多代理場景。

**限制：**
- **範圍仍受限於已整合的基準測試**：雖然已支援超過 20 個基準測試，但代理領域的新基準測試層出不窮，AgentCompass 需要持續更新才能保持覆蓋率。
- **環境保真度（environment fidelity）的挑戰**：代理評測高度依賴模擬環境的真實性，若環境無法準確反映真實世界工具與服務的行為，評測結果可能無法外推至實際部署。
- **LLM-as-judge 的變異性**：雖然 AgentCompass 支援 LLM-as-judge 評分，但這類評分方式本身可能受到評判模型偏見、提示設計與評分標準不一致的影響。
- **獎勵駭取與評測污染（benchmark contamination）**：統一基礎設施雖然提升了可比較性，但仍無法完全避免模型在訓練資料中見過特定任務，或利用評分漏洞進行獎勵駭取（reward-hacking）的問題。

#### 可重現性評估

AgentCompass 在可重現性（reproducibility）方面採取了多項具體措施：
- **開源（open-source）**：原始碼已公開於 `https://github.com/open-compass/AgentCompass`，研究者可以取得完整實作並進行驗證或擴展。
- **宣告式配置**：透過 RunRequest 與各類 Spec，評測的語義定義與執行選項被清楚分離，便於分享與重現。
- **模組化註冊機制**：新 Benchmark、Harness 與 Environment 可透過裝飾器註冊，無需修改核心程式碼，降低了重複工程（redundant engineering）與版本不一致的風險。
- **標準化執行原語**：AgentCompass 統一了任務分派（task dispatch）、環境互動（environment interaction）與指標聚合（metric aggregation）等關鍵操作，確保不同研究者在相同配置下能獲得一致結果。
- **容器化環境支援**：架構圖中顯示支援 Host、Docker 與 Sandbox 等執行環境，這有助於隔離依賴並提升跨平台可重現性。
- **軌跡記錄**：完整的代理軌跡（agent trajectories）記錄讓研究者能夠回溯每一步行動與環境回饋，進一步驗證分數的合理性。

不過，可重現性仍可能受到外部因素影響，例如模型 API 版本更新、推論參數差異、容器環境的網路狀態，以及部分基準測試所需的私有資料集或授權工具。未來若能提供鎖定版本（version pinning）的環境配置與預設模型快照，將進一步提升可重現性。

#### 未來研究方向

AgentCompass 作為一個統一評測基礎設施，為多個後續研究方向奠定了基礎：

1. **擴展基準測試覆蓋率**：持續整合更多新興的代理基準測試，特別是涉及長期規劃（long-horizon planning）、多模態感知與真實世界工具使用的任務。

2. **多代理與協作評測**：目前 AgentCompass 主要針對單一代理設計，未來可擴展其 Harness 與 Environment 協定，以支援多代理系統（multi-agent systems）的協作、競爭與通訊評測。

3. **自動化失效模式診斷**：在現有軌跡分析（trajectory analysis）基礎上，發展基於規則或學習式的自動診斷工具，自動識別常見失效模式（failure modes），例如無窮迴圈、錯誤的工具選擇與獎勵駭取（reward-hacking）。

4. **安全性與對齊評測**：除了能力評測，未來可強化對代理安全性、對齊性與魯棒性的評測，包括對抗式攻擊、越權行為與社會偏見等面向。

5. **效率與成本指標**：目前的評測多聚焦於正確性，未來可加入更多效率指標，例如平均工具呼叫次數、執行時間、API 成本與記憶體使用量，以評估代理在實際部署中的可行性。

6. **與訓練流程的整合**：將 AgentCompass 從純評測基礎設施擴展為訓練—評測一體化平台，支援線上學習（online learning）與強化學習（reinforcement learning）的即時反饋。

7. **社群驅動的元件註冊表**：建立公開的 Benchmark、Harness 與 Environment 註冊表，讓社群能夠共享與審查評測元件，進一步促進可重現性與標準化。

8. **真實世界部署評測**：發展從模擬環境過渡到真實世界服務的評測協定，並建立環境保真度（environment fidelity）的量化指標，以縮小模擬與現實之間的差距。

## 論文問答

**Q1：AgentCompass 主要想解決什麼問題？**
A：AgentCompass 旨在解決目前基於 LLM 的代理評測流程高度碎片化且緊密耦合的問題。現有評測套件多為各自獨立運作，研究者必須反覆配置異質執行環境、資料格式與評分協定，造成大量重複工程並損害可重現性。因此，AgentCompass 提出一個統一、輕量且可擴充的評測基礎設施，以標準化並簡化代理能力評估。

**Q2：為什麼現有的評測方法或基礎設施無法滿足需求？**
A：現有方法多為針對特定能力設計的專門基準測試，例如工具呼叫或深度研究，但它們彼此孤立，缺乏統一的執行與評分介面。另一方面，通用型基礎設施要不是缺乏對互動式代理工作流程的原生支援，就是僅聚焦於程式編寫等狹窄領域，難以涵蓋多維度代理能力。這種片段化的現況使得跨基準比較、複現結果與整合新資料集都變得困難且容易出錯。

**Q3：統一的評測基礎設施為何對代理研究很重要？**
A：隨著 LLM 從遵循指令的文字生成器演進為具備推理、規劃與工具互動能力的自主代理，評測方法必須同步發展以確保嚴謹評估。統一的基礎設施能減少重複工程、提供一致的基線實作，並提升實驗的可重現性。此外，它讓研究者能專注於方法創新，而非耗費時間在環境配置與資料轉換上，從而加速整個領域的進步。

**Q4：AgentCompass 的核心方法與整體架構是什麼？**
A：AgentCompass 的核心方法是將評測流程解耦為三個獨立元件：基準測試（Benchmark）、執行框架（Harness）與環境（Environment）。透過宣告式的 RunRequest，研究者可以分別指定 BenchmarkSpec、HarnessSpec、EnvironmentSpec、ModelSpec 與 ExecutionSpec，將評測語意與執行機制分離。這種模組化抽象讓原本僵化的流程轉變為可組合的「基準測試 × 執行框架 × 環境」配置。

**Q5：AgentCompass 的關鍵創新有哪些？**
A：關鍵創新在於將 Harness 抽象為獨立的中介執行層，使同一基準可搭配不同代理互動協定，而無需重寫基準程式碼。此外，AgentCompass 內建容錯非同步執行環境，可平行化長時間執行的代理軌跡，並提供完整的軌跡層級分析與視覺化工具。這些設計讓研究者能透明地診斷細微失效模式，例如獎勵駭取（reward hacking）。

**Q6：AgentCompass 做了哪些重要的設計選擇？**
A：首先，它將實質評測物件與執行選項分離，例如把執行緒、逾時、重試等參數放在 ExecutionSpec，而不改變評測語意。其次，它採用輕量的裝飾器式註冊機制，讓新的基準、執行框架、環境、配方與分析器可以本地註冊，無需修改核心執行期。最後，它透過統一的會話介面與執行原語，將環境互動、工具呼叫與觀察回饋標準化，降低跨基準整合成本。

**Q7：AgentCompass 支援哪些基準測試與能力維度？**
A：AgentCompass 原生支援超過 20 個基準測試，涵蓋工具使用、具代理性（agentic）、程式編寫、網頁與研究、生產力與科學推理等核心評測維度。這些基準分別評估代理在不同任務型態下的表現，例如工具呼叫、長程規劃、程式碼生成、網頁瀏覽與科學問題求解。透過統一架構，研究者可以在相同基礎設施下對多種能力進行一致且可比的評估。

**Q8：論文中展示了哪些關鍵結果或能力輪廓？**
A：論文透過圖 1 展示了數個代表性模型在五個核心評測維度上的能力輪廓，顯示不同模型在工具使用、科學推理、程式編寫等面向各有強弱。這種綜合視角有助於辨識模型的優勢與短板，而不僅是單一總分。雖然摘要與引言未詳列所有數值，但該輪廓圖凸顯了統一評測基礎設施在全面刻畫代理能力上的價值。

**Q9：AgentCompass 是否進行了消融實驗？若有，結論為何？**
A：在提供的摘要與前文脈中，並未明確呈現傳統意義上的消融實驗數據。然而，AgentCompass 的模組化設計本身即支援系統性的元件替換，例如在同一基準上比較不同 Harness，或在同一 Harness 下測試不同 Environment。這種「架構即消融」的彈性，使研究者能夠清楚分離各元件對最終表現的貢獻，這正是其設計優勢所在。

**Q10：AgentCompass 可應用於哪些實務場景？**
A：AgentCompass 可應用於評估各類基於 LLM 的代理，包括具備工具使用能力的對話代理、自動化研究助理、程式編寫代理與生產力工具。研究團隊也能利用它快速比較不同互動協定或提示策略，並在新增資料集時無需重寫複雜執行邏輯。此外，其軌跡分析功能特別適合用於偵測與診斷代理的獎勵駭取等不當行為。

**Q11：從產品化角度來看，AgentCompass 有哪些設計考量？**
A：AgentCompass 強調開源、輕量與可擴充，降低社群採用與貢獻的門檻。其容錯非同步執行環境能穩定處理長時間、高並行的代理軌跡，減少大規模評測時的執行中斷。同時，內建的軌跡視覺化與分析工具提升了除錯透明度，使產品團隊能更快定位模型、執行框架或環境層面的問題。

**Q12：AgentCompass 對代理研究領域可能帶來什麼影響？**
A：AgentCompass 已作為 Intern-S 代理系列的基礎評測設施，顯示其在實際大規模研究中的可擴展性與可靠性。它為社群提供了一個可重現、可共享的評測工具包，有助於建立一致的基線實作並減少重複工程。長遠來看，這種統一架構能促進跨研究團隊的結果比較，加速代理能力的系統性提升。

**Q13：AgentCompass 有哪些可能的限制或尚未涵蓋的面向？**
A：雖然全文未詳盡列出所有限制，但作為基礎設施，其評測品質仍受制於所收錄基準測試的廣度與深度，某些新興或高度專業的代理能力可能尚未被涵蓋。此外，部分評分機制依賴 LLM-as-judge，可能引入評判者本身的偏誤或不穩定性。未來仍需持續擴充基準與改進評分協定，以跟上快速演進的代理技術。

**Q14：在實際使用中，AgentCompass 可能遇到哪些失效案例？**
A：常見失效案例包括代理為追求高分而進行獎勵駭取，例如繞過題目要求直接輸出看似正確的答案。非同步執行環境中也可能因環境逾時、資源清理不完全或容器狀態不一致而導致軌跡中斷。幸好 AgentCompass 提供詳細的軌跡記錄與環境回饋，讓開發者能回溯中間行動與工具呼叫，從而定位並修復問題根源。

**Q15：AgentCompass 未來可以朝哪些方向發展？**
A：未來可進一步擴充更多領域的基準測試，例如多代理協作、長期記憶與更複雜的動態環境互動。同時，可強化軌跡分析與自動診斷工具，例如引入更細緻的失效模式分類與根因分析。此外，透過持續吸引社群貢獻新的 Harness、Environment 與評分器，AgentCompass 有望成為代理研究領域更完整、更長久的公共基礎設施。

## 實務應用指南

### 適用場景

1. **模型能力選型與採購評估**：企業在導入 LLM 代理時，可利用 AgentCompass 統一比較不同模型在工具使用、程式編寫、網頁與研究、科學推理與生產力等維度的能力輪廓，作為選型或 API 採購的客觀依據。
2. **代理開發迭代與回歸測試**：代理開發團隊可在每次演算法、提示詞或工具鏈調整後，於同一套基準測試與執行框架上執行回歸測試，快速定位效能衰退或細微失效模式。
3. **學術研究中的可重現評測**：研究人員發表新模型或新基準測試時，可透過 AgentCompass 的宣告式配置與標準化執行流程，降低異質執行環境造成的可重現性問題。
4. **多環境互動協定比較**：需要評估不同互動協定（例如 ReAct、Plan-and-Execute、Toolformer 風格）對同一任務表現的影響時，可透過獨立的 Harness 層進行 A/B 測試，而無需重寫基準測試程式碼。
5. **教育與開源社群的能力剖析**：教學單位或開源社群可利用其視覺化軌跡分析與能力剖面圖，向學員或貢獻者解釋代理在長時間執行軌跡中的決策過程與失敗原因。

### 實作前置條件

- **資料準備**：需取得目標基準測試的資料集與對應評分金鑰（gold labels / test cases），並確認授權允許自動化執行；部分涉及網頁或外部服務的基準測試需要穩定的網路連線與 API 配額。
- **運算資源**：建議具備可平行執行多條長時間代理軌跡的運算環境，例如具備多核心 CPU、充足記憶體（視基準測試規模建議 32 GB 以上）以及可選的 GPU 推論後端；若使用 Docker / Sandbox 環境，則需預留容器映像檔空間與執行權限。
- **技能要求**：團隊應熟悉 Python 非同步程式設計、容器化技術（Docker）、LLM API 呼叫與錯誤處理；若需新增自訂基準測試或 Harness，則需理解 AgentCompass 的 decorator-based registry 與 TaskSpec / Interaction 協定。
- **環境與權限**：需準備模型端點（OpenAI、Anthropic、自架 vLLM 等）的憑證與速率限制設定；執行涉及檔案系統、網路或終端機操作的基準測試時，建議使用隔離的 Sandbox 以降低安全風險。

### 實作步驟建議

1. **安裝與環境建置**：從官方倉儲取得 AgentCompass，建立虛擬環境並安裝相依套件；同時設定 Docker 或本地 Sandbox，確保 Environment 層可正常啟動與清理。
2. **選定基準測試與能力維度**：根據產品需求選擇對應的基準測試（例如工具使用選 ToolBench、程式編寫選 HumanEval、網頁研究選 WebArena 等），並確認評分機制為確定性比對、執行驗證或 LLM-as-judge。
3. **配置模型端點與 Harness**：撰寫 `ModelSpec` 指定端點、憑證與推論參數；選擇或自訂 `HarnessSpec`，定義代理的觀察—思考—行動迴圈、上下文建構方式與工具呼叫格式。
4. **執行小規模試驗**：先以少量樣本（例如每個基準測試 10–50 筆）執行非同步試驗，檢查軌跡記錄、環境回饋與評分結果是否正確，並確認容錯機制能處理超時、API 錯誤或環境崩潰。
5. **擴展至完整評測與指標聚合**：在試驗通過後，調整 `ExecutionSpec` 的平行度與重試策略，執行完整資料集；利用內建的指標聚合與視覺化工具產生能力輪廓與詳細軌跡報告。
6. **軌跡分析與迭代優化**：針對低分樣本進行軌跡層級分析，識別獎勵駭取、工具誤用或迴圈停滯等細微失效模式，並據此調整 Harness、提示詞或工具描述後重新評測。
7. **整合至 CI/CD 或模型發布流程**：將評測腳本納入持續整合管線，設定閾值自動阻擋效能衰退的提交，並在模型版本發布時附上標準化的 AgentCompass 評測報告。

### 潛在風險與注意事項

- **環境異質性導致結果不可重現**：不同作業系統、套件版本或網路延遲可能影響執行結果。建議使用 Docker 固定環境，並在報告中詳細記錄映像檔版本、模型版本與隨機種子。
- **API 成本與速率限制**：長時間代理軌跡可能產生大量 LLM 呼叫與工具執行費用。建議先以小樣本估算成本，設定合理的並行上限與預算上限，並啟用快取機制避免重複呼叫。
- **獎勵駭取與評分漏洞**：代理可能利用評分機制的弱點取得高分但無法真正完成任務。應結合執行驗證與人工抽樣檢查，並利用軌跡分析工具交叉比對中間行動與最終分數。
- **安全性與隔離不足**：部分基準測試會執行任意程式碼或網路操作。務必在 Sandbox 或最小權限容器中執行，避免污染主機環境或外洩敏感憑證。
- **過度擬合特定 Harness 或提示詞**：若比較多個模型時使用不同 Harness，可能混淆模型能力與工程技巧的貢獻。建議在相同 Benchmark × Harness × Environment 配置下進行公平比較。

### 與其他技術的整合建議

- **與 OpenCompass / VLMEvalKit 整合**：若組織已使用 OpenCompass 進行通用推理與安全性評測，可將 AgentCompass 作為其代理能力評測的延伸模組，統一管理模型端點與報告格式。
- **與 MLOps / 實驗追蹤工具整合**：可將 AgentCompass 的執行結果匯出至 MLflow、Weights & Biases 或自建的實驗管理平台，便於長期追蹤不同模型版本與 Harness 設定的能力輪廓變化。
- **與 CI/CD 管線整合**：透過命令列介面與宣告式 `RunRequest`，可將評測任務嵌入 GitHub Actions、GitLab CI 或 Jenkins，在每次代理程式碼變更時自動執行回歸測試。
- **與自架推論後端整合**：AgentCompass 的 `ModelSpec` 支援多種 API 協定，可無縫對接 vLLM、TGI、SGLang 或內部部署的模型服務，降低對單一商業 API 的依賴。
- **與監控與可觀測性工具整合**：可將軌跡記錄送至 OpenTelemetry、LangSmith 或自訂日誌系統，進一步進行延遲分析、錯誤追蹤與成本歸因。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從官方文件中的快速入門範例開始，選擇一個已原生支援的基準測試（如 HumanEval 或 ToolBench 子集），使用預設 Harness 與 OpenAI API 執行一次完整評測；重點觀察軌跡記錄與最終分數的對應關係，不必急著自訂元件，先建立對「基準測試 × 執行框架 × 環境」解耦設計的直覺。

**AI 工程師**：可聚焦於第 3 節的架構設計與協定細節，特別是 TaskSpec、Interaction、Environment Session 與 decorator-based registry 的實作方式；建議實際撰寫一個自訂 Harness 或 Analyzer，並嘗試將現有內部評測腳本遷移至 AgentCompass，以驗證其對平行化、容錯與軌跡視覺化的改善。

**研究人員**：建議深入閱讀其模組化抽象與可重現性機制，評估是否能作為新基準測試或新模型的標準化發布平台；可關注其如何分離評測語義與執行機制，以及軌跡分析工具對於診斷獎勵駭取等細微失效模式的幫助，並思考如何擴展至新的能力維度或多代理場景。

**產品經理**：可將本文視為代理產品選型與品質管線的參考藍圖，重點理解五個核心評測維度與能力輪廓圖的商業意義；建議與工程團隊討論如何將 AgentCompass 整合進模型評估、發布審查與客戶 POC 的標準流程，並關注 API 成本、執行時間與安全隔離等落地議題。
