ToolSpace 的核心方法論在於翻轉傳統「資料中心環境合成」(Data-Centric Environment Synthesis) 的因果順序，提出「工具中心環境合成」(Tool-Centric Environment Synthesis) 的新範式。此一方法論轉向具有深層的理論意涵：它將工具視為代理能力成長的「原子單元」(atomic unit)，而非環境資料的衍生產物，這與軟體工程中「組合性」(compositionality) 原則相呼應。

**第一階段：工具空間探索 (Tool Space Exploration)**

此階段採用「軌跡到環境」(Trace-to-ENV) 原則，從真實 MCP 服務的執行軌跡 (execution trace) 與開放代理語料庫 (open agent corpus) 中萃取工具呼叫。關鍵創新在於使用「確定性規則」(deterministic rule) 而非 LLM 判斷 (LLM judgment) 來挖掘三類依賴關係：

1. **資料依賴 (data dependency)**：後續呼叫的輸入參數源自先前呼叫的輸出欄位，這種結構性依賴可透過參數名稱匹配與型別推斷自動判定。
2. **狀態依賴 (state dependency)**：工具呼叫對環境狀態的隱性影響，例如建立訂單後查詢訂單狀態。
3. **重試依賴 (retry dependency)**：相同或相似工具的重複呼叫模式，反映錯誤恢復或迭代探索行為。

這三類依賴構成加權工具組合圖 (weighted tool-composition graph) 的邊，權重反映共現頻率與依賴強度。圖上的節點聚類 (clustering) 形成環境集群 (environment cluster)，緊密耦合的工具被劃入同一環境。值得注意的是，ToolSpace 僅為「狀態變更環境」(state-mutating environment) 合成底層資料庫；對於查詢工具 (query tool) 與無狀態工具 (stateless tool)，則直接重播 (replay) 記錄的返回值。這種「按需合成」策略大幅降低環境建構成本，同時保留工具組合的真實性。

**第二階段：跨環境可驗證任務合成 (Cross-Environment Verifiable Task Synthesis)**

此階段在 ToolSpace 圖上執行「狀態感知隨機遊走」(state-aware random walk) 搭配回溯採樣 (rollback sampling)。狀態感知機制確保後續節點的選擇與當前環境狀態相容，避免產生語義上不可達 (unreachable) 的工具序列。回溯機制則在執行失敗時恢復至先前狀態，繼續探索其他分支。

每條成功執行的遊走鏈會被「反編譯」(decompile) 為自然語言任務描述，並附帶基於斷言的檢查腳本 (assertion-based check)。此處的關鍵設計選擇是「僅保留可從初始狀態重播成功」的樣本，這構成了一種隱式的可驗證性過濾器——任何無法在乾淨環境中重現的任務都被剔除，確保訓練資料的執行可信度。

從方法論角度，ToolSpace 的設計體現了三個深層原則：(1) 執行見證優先於語言直覺，使用真實軌跡作為邊的證據；(2) 環境是工具關係的副產物而非先驗設定；(3) 任務複雜度源自工具組合空間的擴展，而非單一環境的資料規模膨脹。

#### 實驗數據解讀

**基準測試建構結果**

ToolSpace 將 AutomationBench 與 tau3-Bench Banking 升級為 Pro 版本，這些 Pro 版本在任務難度、工具呼叫輪數與跨環境廣度上均超越標準版本。在 AutomationBench Pro 上，七個前沿模型 (frontier model) 的表現下降幅度最高達 38.2 分，這一數字具有重要意涵：它不僅證明 Pro 版本確實更具挑戰性，更顯示現有模型在面對「執行見證式跨環境任務」時存在顯著的能力缺口。38.2 分的降幅相當於某些模型從及格邊緣跌至接近隨機水準，說明 Pro 版本捕捉到了標準版本未能涵蓋的真實長時程推理需求。

**模型規模的提升效果**

Qwen3.6-35B-A3B 從 23.0 提升至 41.0 平均分數（搭配強化學習後達 43.2），提升幅度達 18 分（相對提升約 78%）。GLM-5.2 從 44.6 提升至 56.6，提升 12 分。這些數據揭示幾個重要現象：

1. **小模型受益更顯著**：Qwen3.6-35B-A3B 的相對提升遠高於 GLM-5.2，暗示 ToolSpace 合成的高品質資料對中等規模模型具有更強的「知識蒸餾」效果，可能填補了這些模型在工具使用方面的先天不足。

2. **強化學習的疊加效應**：在 ToolSpace 合成資料上進行 RL 訓練可進一步提升 2.2 分，說明這些資料不僅適合監督式微調，也提供有效的獎勵訊號供 RL 探索。

3. **競爭力對標**：GLM-5.2 達到 56.6 分，與 Claude Opus 5 持平，並超越 GPT 5.6 Sol 的 48.9 分。這顯示 ToolSpace 合成資料可使開源或中等規模模型逼近頂級閉源模型的工具使用能力。

**消融實驗的關鍵發現**

「執行見證邊」(execution-witnessed edge) 明顯優於 LLM 判斷邊，這是方法論層面的重要驗證。LLM 判斷邊可能引入幻覺 (hallucination) 與語義偏差，而執行見證邊則保留了工具呼叫的真實共現模式。此外，效能隨資料規模、環境規模與任務多樣性的擴展持續提升，呈現清晰的縮放規律 (scaling law)，這與神經網路中觀察到的「規模效應」相呼應，暗示 ToolSpace 的合成方法可能受益於更大的執行軌跡語料庫。

#### 與現有研究的比較

**與模擬式方法的比較**

Simia 與 GenEnv 等模擬式方法將 LLM 視為「隱式文字世界模型」(implicit textual world model)，從工具規格與互動歷史生成模擬回饋。ToolSpace 與此類方法的根本差異在於：模擬式方法成本低廉但易產生幻覺且難以保證狀態一致性；ToolSpace 則透過執行軌跡確保回饋的真實性，但需承擔軌跡收集與環境合成的較高成本。這是一種「真實性 vs. 成本」的權衡，ToolSpace 選擇前者。

**與可執行環境方法的比較**

Dong 等人 (2026a)、Fang 等人 (2025)、Song 等人 (2026)、Wang 等人 (2026) 等可執行環境方法採取了資料中心路徑：先合成資料庫與主題，再衍生工具與任務。ToolSpace 對此提出三項系統性批評：

1. **工具—功能不匹配 (tool–functionality mismatch)**：從資料庫反向合成的工具，其參數邏輯 (parameter logic) 容易偏離真實工具介面定義，導致代理學習到的是「合成工具協議」(synthetic tool protocol) 而非可遷移至真實生態系的操作知識。

3. **缺乏跨環境任務合成 (lack of cross-environment task synthesis)**：任務被鎖定在單一環境沙盒 (sandbox) 內，無法自然產生跨環境的長時程複雜度。

當前實驗集中於通用工具與銀行領域，未來可探討：(1) 領域特化的確定性規則（如醫療、法律場景的合規依賴）；(2) 跨領域遷移——在一個領域合成的訓練資料能否提升其他領域的表現；(3) 領域適配機制，如何以最少標註將通用 ToolSpace 擴展至新領域。

**6. 安全性與對齊考量**

跨環境任務可能涉及敏感操作（如金融交易、隱私資料存取）。未來需研究：(1) 合成資料中的安全性過濾機制；(2) 紅隊測試任務的自動生成；(3) 對齊評估——代理在跨環境任務中是否會產生有害行為。這些研究對 ToolSpace 的實際部署至關重要。

**7. 與代理自我改進的閉環**

一個大膽的方向是讓代理本身參與軌跡生成：代理在真實環境中探索，產生新軌跡，再由 ToolSpace 合成新訓練資料，形成「探索—合成—訓練—部署」的自我改進閉環。這類似 AlphaGo 的自我對弈機制，但應用於工具使用場景。

**8. 多模態工具的擴展**

當前 ToolSpace 主要處理文字介面的工具，未來可擴展至多模態工具（如圖像生成、語音合成、視訊處理）。這需要重新設計確定性規則以處理非結構化輸出，並研究跨模態依賴的挖掘方法。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於長時程代理（long-horizon agent）在真實 MCP 服務中編排多樣工具時所面臨的訓練資料合成瓶頸。隨著大型語言模型從單輪聊天機器人演進為能完成多步驟、可執行工作流的協作型代理，如何擴展工具組合的規模與真實性已成為代理能力成長的基礎問題。現有的環境合成方法以資料為中心，先建立資料庫與情境再衍生工具與任務，導致合成出的工具介面、組合關係與任務難度都與真實代理執行場景脫節。ToolSpace 因此主張應以工具為原子單元，從真實執行軌跡重建可探索、可擴展的工具空間，再據此合成跨環境的長時程任務。

**Q2：為什麼現有的「資料中心環境合成」方法會失敗？**
A：現有方法採取「先合成資料庫、再衍生工具」的順序，會產生三個根本性缺陷。第一，工具—功能不匹配：可執行工具是從環境資料庫與主題描述反向合成，其參數邏輯容易偏離真實工具介面定義，使代理學到的是一套合成工具協議，而非可遷移到真實工具生態系的操作。第二，工具編排不真實：既有方法透過隨機連結或淺層 LLM 判斷建立工具連結圖，缺乏執行證據，且真實工具服務本身具不穩定性與雜訊，主觀難以建立邏輯關係。第三，缺乏跨環境任務合成：任務合成被鎖在單一環境的資料與規則內，無法自然產生跨越多個環境的長時程複雜度。這三項缺陷共享同一個根源——資料中心合成顛倒了真實代理執行中「工具先於環境」的依賴關係。

**Q3：為什麼這個問題對長時程代理領域至關重要？**
A：長時程代理的價值在於能將多樣工具組合成可執行的工作流，而工具正是代理執行的原子單元。若訓練資料中的工具介面、組合關係與真實 MCP 服務不一致，代理在部署時將面臨嚴重的轉移落差，無法將所學遷移至真實工具生態系。此外，真實世界的任務常橫跨多個環境（例如同時操作銀行、郵件、行事曆等服務），單一環境的合成方法無法支撐這種跨域複雜度。隨著代理能力被視為模型從聊天機器人邁向通用人工智慧的關鍵指標，如何在保留真實工具編排的前提下擴展訓練資料規模，已成為擴展代理能力的基礎性問題。

**Q4：ToolSpace 的核心方法是什麼？**
A：ToolSpace 採用「Trace-to-ENV」原則，先從真實 MCP 服務與開放代理語料庫的執行軌跡中，以確定性規則（而非 LLM 判斷）挖掘工具呼叫之間的資料依賴、狀態依賴與重試依賴，並據此建構一個加權工具組合圖。接著將耦合緊密的工具聚類成環境叢集，僅對狀態變更環境合成底層資料庫，查詢與無狀態工具則直接重播記錄的回傳值。在任務合成階段，ToolSpace 在該圖上執行帶回溯機制的狀態感知隨機遊走，逐步執行並只保留能從初始狀態端到端重播成功的鏈，最後將每條鏈反編譯為帶有基於斷言之檢查腳本的自然語言任務。

**Q5：ToolSpace 相較於既有方法最關鍵的創新是什麼？**
A：最關鍵的創新在於翻轉了合成順序——從「資料中心」轉為「工具中心」，並以執行軌跡作為唯一可信的證據來源。具體而言，ToolSpace 用確定性規則從真實執行軌跡中挖掘執行見證邊（execution-witnessed edges），取代了既有方法中隨機連結或 LLM 主觀判斷所產生的不可靠邊。這種設計不僅保留了真實工具介面與組合關係，還透過聚類自然形成跨環境的可達性關係，使長時程複雜度能從工具組合空間的擴展中自然湧現，而非依賴單一環境資料規模的線性放大。

**Q6：ToolSpace 在設計上有哪些關鍵的取捨與選擇？**
A：ToolSpace 在多個設計環節做出了務實的取捨。第一，在邊生成上選擇確定性規則而非 LLM 判斷，雖然犧牲了部分靈活性，但換來了邊的可驗證性與可重播性，這對消融實驗中證明「執行見證邊明顯優於 LLM 判斷邊」至關重要。第二，在環境建構上採取「按需合成」策略——只為狀態變更環境合成資料庫，查詢與無狀態工具直接重用記錄回傳值，大幅降低了環境合成成本。第三，在任務採樣上採用帶回溯的狀態感知隨機遊走，僅保留能從初始狀態完整重播成功的鏈，確保每筆訓練樣本都具備可審計性與可驗證性。

**Q7：ToolSpace 使用了哪些基準測試進行驗證？**
A：ToolSpace 將完整管線錨定於兩個長時程代理基準——AutomationBench 與 tau3-Bench Banking，並延伸出難度更高的 AutomationBench Pro 與 tau3-Bench Banking Pro 版本。這兩個 Pro 版本在任務難度、工具呼叫輪數與跨環境廣度上都超越標準版本，例如在 AutomationBench Pro 上，七個前沿模型的表現相較標準版本下滑了多達 38.2 分。此外，ToolSpace 也在七個長時程工具使用基準上進行了廣泛評測，涵蓋 8B 至 744B 的不同模型規模，以驗證其在不同基準間的泛化能力。

**Q8：ToolSpace 的關鍵實驗結果為何？**
A：在七個長時程工具使用基準的平均分數上，ToolSpace 將 Qwen3.6-35B-A3B 從 23.0 提升至 41.0（搭配強化學習可達 43.2），並將 GLM-5.2 從 44.6 提升至 56.6，後者已與 Claude Opus 5 持平。值得注意的是，ToolSpace-744B-A40B 在平均分數上以 56.6 超越了 GPT 5.6 Sol 的 48.9，達到了與 Claude Opus 5 相當的水準。這些結果顯示 ToolSpace 不僅能顯著提升中小型模型的代理能力，也能在頂尖模型等級上維持競爭力，證明了工具中心合成路徑的可擴展性。

**Q9：消融實驗揭示了哪些關鍵發現？**
A：消融實驗中最關鍵的發現是「執行見證邊明顯優於 LLM 判斷邊」，這驗證了 ToolSpace 以確定性規則從執行軌跡挖掘依賴關係的設計選擇是正確的。此外，實驗還揭示了清晰的縮放關係——代理性能隨著資料規模、環境規模與任務多樣性的提升而持續改善，這意味著 ToolSpace 的合成管線具備良好的可擴展性，而非僅在某個特定規模點上有效。這些發現共同支持了「工具中心合成」相較於「資料中心合成」在長時程代理訓練上的根本優勢。

**Q10：ToolSpace 有哪些實際應用場景？**
A：ToolSpace 的實際應用場景涵蓋任何需要長時程代理在多個 MCP 服務間編排工具的領域，例如企業內部的跨系統自動化（同時操作 CRM、ERP、財務系統）、個人助理的跨服務任務（同時處理郵件、行事曆、雲端硬碟、第三方 API），以及金融服務中的多步驟工作流（跨銀行、支付、風控合規等服務）。由於 ToolSpace 生成的訓練樣本能從初始狀態完整重播並通過基於斷言的檢查，它特別適合用於需要高可靠性與可審計性的產業部署，例如金融、醫療與政府服務中的自動化代理訓練。

**Q11：在將 ToolSpace 應用於實際產品時，需要考量哪些因素？**
A：實際產品化時需考量幾個關鍵因素。首先，ToolSpace 仰賴真實 MCP 服務的執行軌跡作為證據來源，因此需要穩定、可觀測的工具呼叫記錄基礎設施，這在企業環境中可能涉及隱私與合規議題。其次，雖然 ToolSpace 大幅降低了環境合成成本（僅為狀態變更環境合成資料庫），但狀態變更環境的資料庫合成仍需領域專家介入以確保語義正確性。第三，產出的 Pro 版本基準雖然難度更高，但也意味著訓練出的代理在部署初期可能表現不如在標準基準上訓練的模型，需要在訓練強度與部署可用性間取得平衡。

**Q12：ToolSpace 對長時程代理研究領域的更廣泛影響是什麼？**
A：ToolSpace 的更廣泛影響在於重新定位了「代理能力成長的原子單元」——從環境資料轉為工具組合，這個觀點轉移可能影響整個領域的研究路線。透過證明執行見證邊優於 LLM 判斷邊、且性能隨資料與環境規模持續改善，ToolSpace 為「以執行軌跡為基礎的可擴展代理訓練」這條路線提供了實證支持。這也意味著未來的研究可以更專注於工具介面標準化、執行軌跡收集基礎設施，以及跨環境可達性的形式化建模，而不必受限於單一環境的資料規模瓶頸。

**Q13：ToolSpace 有哪些已聲明的限制？**
A：雖然論文展示了顯著成果，但仍存在幾項可推論的限制。第一，ToolSpace 的有效性高度依賴高品質、可觀測的真實 MCP 服務執行軌跡，若缺乏足夠多樣化的真實呼叫記錄，工具組合圖的覆蓋範圍將受限。第二，狀態變更環境的資料庫合成仍需一定程度的人工介入或領域知識，這在高度專業化的垂直領域（如醫療、法律）中可能成為瓶頸。第三，雖然 Pro 版本基準提升了難度，但論文的評測主要集中在七個基準與七個前沿模型，對於更廣泛模型家族與任務類型的泛化性仍需進一步驗證。

**Q14：ToolSpace 在哪些情境下可能會失敗？**
A：ToolSpace 可能在幾種情境下面臨挑戰。第一，當真實 MCP 服務的執行軌跡本身存在偏誤（例如僅記錄了特定使用者的工具呼叫模式），所建構的工具組合圖將無法反映完整的工具組合空間，導致合成任務缺乏多樣性。第二，對於極少被呼叫的長尾工具，由於缺乏足夠的執行見證邊，它們可能無法被有效納入工具空間，從而限制了代理學習罕見但重要的工具組合的能力。第三，當任務需要跨越尚未在執行軌跡中共同出現過的工具組合時，狀態感知隨機遊走可能無法找到可重播的鏈，導致部分潛在的長時程任務無法被合成出來。

**Q15：基於 ToolSpace 的未來研究方向有哪些？**
A：基於 ToolSpace 的未來研究方向可從幾個維度展開。第一，可以探索更自動化的狀態變更環境資料庫合成技術，減少對領域專家的依賴，例如透過形式化規格或自監督學習從執行軌跡中推導資料庫結構。第二，可以將 ToolSpace 的「執行見證邊」概念擴展到多模態工具（如影像、語音工具），並研究跨模態工具組合的依賴挖掘規則。第三，可以結合強化學習與 ToolSpace 生成的訓練樣本，進一步探索「合成資料 + RL」管線在長時程代理上的最佳實踐，例如論文中 Qwen3.6-35B-A3B 搭配 RL 後從 41.0 提升至 43.2 的初步結果所暗示的方向。第四，可以研究如何將 ToolSpace 應用於持續學習場景，使代理能在新 MCP 服務上線時自動擴展其工具空間。

## 實務應用指南

### 適用場景

1. **企業內部跨系統業務代理訓練**：企業同時部署 CRM、ERP、HR、財會等多個 MCP 服務，需要訓練代理處理「客戶下單 → 庫存查詢 → 財務記帳 → 出貨通知」這類跨四個系統的長時程工作流。ToolSpace 可從員工實際操作軌跡中挖掘工具組合關係，自動生成涵蓋多系統的訓練樣本。

2. **電商客服退換貨代理**：退換貨流程橫跨訂單系統、物流追蹤、客服工單、財務退款四個環境，每一步都涉及狀態變更與跨系統資料傳遞。ToolSpace 的狀態感知隨機遊走與回溯機制特別適合此類「必須依序執行且每步都改變全域狀態」的工作流。

3. **金融業務流程代理（KYC、貸款審核）**：銀行核心、信貸審批、風控模型、合規審查等 MCP 服務之間存在嚴格的狀態依賴與重試規則（例如風控未過需回到補件步驟）。ToolSpace 的 retry 邊挖掘與斷言驗證可直接對應真實業務的合規檢查點。

4. **DevOps 故障響應代理**：監控告警、日誌查詢、CI/CD 觸發、Issue Tracker 更新、知識庫檢索構成典型跨環境鏈。ToolSpace 可從 on-call 工程師的歷史操作軌跡合成「告警 → 定位 → 修復 → 驗證 → 結案」的多步代理訓練資料。

5. **個人 AI 助理工作流自動化**：日曆、郵件、雲端硬碟、Notion、Slack 等 MCP 服務的組合可由 ToolSpace 從使用者授權的軌跡中學習，自動生成「會議排程 → 寄送議程 → 建立會議記錄文件 → Slack 通知」等長鏈任務。

### 實作前置條件

**資料前置條件**
- 真實 MCP 服務的執行軌跡（建議至少數萬筆呼叫序列），需包含工具名稱、參數、回傳值、時間戳
- 開放代理語料庫（如 AgentBench、τ-bench 系列公開軌跡）作為冷啟動來源
- 工具介面規格文件（JSON Schema 或 OpenAPI），用於驗證挖掘出的邊是否與真實介面一致
- 目標領域的狀態變更操作清單（哪些工具會改寫底層資料）

**計算前置條件**
- 中等規模 GPU 叢集：用於 LLM 判斷輔助（若採用混合策略）、任務反編譯、模型訓練（SFT 與 RL）
- 大規模 CPU 儲存：用於儲存工具組合圖、隨機遊走採樣的狀態快照
- 沙盒執行環境：能重播 MCP 工具呼叫並支援狀態回溯（建議容器化隔離每個環境叢集）
- 分散式圖計算引擎（如 NetworkX + Dask 或 Neo4j）以處理數十萬節點的工具組合圖

**技能前置條件**
- 熟悉 MCP 協議、工具呼叫格式、JSON Schema 驗證
- 具備圖論基礎（節點、邊權重、社群偵測、隨機遊走演算法）
- 了解狀態機與回溯機制設計
- 具備 LLM 訓練經驗，特別是 RL with verifiable rewards（用於後續 §3.7 的代理訓練）
- 領域專家參與斷言設計，確保任務驗證符合業務邏輯

### 實作步驟建議

**步驟 1：軌跡收集與清洗（2–4 週）**
部署 MCP 軌跡收集器，在不影響生產環境的前提下記錄工具呼叫序列。清洗階段需過濾個資、補齊缺失參數、統一時間格式，並標註每筆軌跡的領域標籤。

**步驟 2：確定性規則挖掘工具組合邊（1–2 週）**
實作三類邊的挖掘規則：
- **資料邊**：工具 B 的輸入欄位與工具 A 的回傳欄位語義匹配（型別 + 欄位名相似度）
- **狀態邊**：工具 B 讀取的資源 ID 與工具 A 寫入的資源 ID 相同
- **重試邊**：在固定時間窗內對同一資源重複呼叫相同工具族
所有規則必須是確定性的，禁止使用 LLM 判斷，以保證可重現性。

**步驟 3：環境聚類與資料庫合成（2–3 週）**
以 Louvain 或 Leiden 演算法在工具組合圖上做模組化聚類，將緊密耦合的工具劃為同一環境。僅為「狀態變更環境」合成底層資料庫（建議用 Faker 或領域專家撰寫 schema），其餘環境直接重播原始回傳值。

**步驟 4：狀態感知隨機遊走採樣（1–2 週）**
實作帶回溯的隨機遊走：每步依邊權重抽樣下一個工具，執行後比對實際狀態變更是否符合預期；若不符合則回溯到上一快照。建議每個環境叢集採樣數萬條長度 ≥ 5 的鏈。

**步驟 5：任務反編譯與斷言生成（1–2 週）**
將每條成功鏈餵入 LLM 反編譯為自然語言任務描述，並由領域專家或第二個 LLM 撰寫斷言腳本（檢查最終狀態是否符合預期）。僅保留能從初始狀態完整重播的樣本。

**步驟 6：代理訓練（SFT → RL）（3–6 週）**
先用合成資料做監督微調，再以斷言驗證結果作為 reward signal 進行 RL 訓練。建議採用 verifiable rewards 框架（如 VERL、RLVR），因為每個樣本都有可執行的檢查腳本。

**步驟 7：評測與迭代（持續）**
在 AutomationBench Pro、τ3-Bench Banking Pro 等基準上評測，並持續將生產環境新軌跡回流到步驟 2，動態擴充工具組合圖。

### 潛在風險與注意事項

**軌跡品質風險**
- *風險*：生產軌跡含大量噪聲、失敗呼叫、重試循環，會污染工具組合圖。
- *緩解*：設定最小成功鏈長度過濾、移除超時與錯誤呼叫、對低頻邊設定信賴度閾值。

**工具介面漂移風險**
- *風險*：MCP 服務升級後參數語義改變，導致挖掘出的邊失效。
- *緩解*：建立介面版本控管，每次升級自動重跑邊挖掘；保留版本化資料庫快照以便回滾。

**隱私與合規風險**
- *風險*：軌跡中含客戶個資、商業機密，合成資料可能洩漏。
- *緩解*：在步驟 1 強制 PII 偵測與遮罩；採用差分隱私或合成資料取代真實回傳值；建立資料血緣審計日誌。

**確定性規則覆蓋不足風險**
- *風險*：純確定性規則可能漏掉罕見但關鍵的跨環境邊（例如人工觸發的例外流程）。
- *緩解*：保留少量 LLM 判斷作為「探索模式」，僅在確定性規則覆蓋率低於閾值時啟用，並標記為低信賴邊。

**隨機遊走產生不自然任務風險**
- *風險*：高權重邊集中於熱門路徑，導致任務分布偏斜，代理只會處理常見場景。
- *緩解*：引入 ε-greedy 探索、稀有邊上採樣、領域專家審核低頻任務樣本。

**斷言設計錯誤風險**
- *風險*：錯誤的斷言會讓代理學到錯誤行為（例如「繞過風控」也能通過檢查）。
- *緩解*：雙人審核斷言、為每個斷言撰寫反例測試、定期以紅隊樣本驗證斷言有效性。

**評估過擬合風險**
- *風險*：在 AutomationBench Pro 等基準上表現優異，但泛化到未見過的真實 MCP 服務時下降。
- *緩解*：保留 held-out 真實軌跡做為最終驗證集；監控代理在生產環境的失敗率而非僅看基準分數。

### 與其他技術的整合建議

**與既有 MCP 服務整合**
ToolSpace 不取代 MCP 服務，而是作為「訓練資料層」運行。建議在 MCP gateway 旁部署軌跡收集器，將收集到的呼叫序列匯入 ToolSpace pipeline，產出的訓練資料再餵入代理訓練框架。訓練後的代理仍透過同一 MCP gateway 呼叫真實服務。

**與 RL 框架整合**
ToolSpace 產出的每個樣本都帶有可執行斷言，天然適合 verifiable rewards 訓練流程。可與 VERL、OpenRLHF、Tulu 等 RL 框架對接，把斷言執行結果直接作為 reward signal，省去人工標註成本。

**與評測基準整合**
ToolSpace 的「Pro 版本生成」能力可作為基準難度增強器。建議將 AutomationBench Pro、τ3-Bench Banking Pro 納入內部評測套件，並定期用 ToolSpace 自動產生新一批困難樣本以避免基準污染。

**與監控與可觀測性整合**
將代理在生產環境的執行軌跡回流到 ToolSpace pipeline，形成「部署 → 收集 → 挖掘 → 訓練 → 部署」的閉環。建議整合 OpenTelemetry 或 LangSmith 等可觀測性工具，統一軌跡格式。

**與領域專家系統整合**
斷言設計與環境聚類都需要領域知識。建議建立領域專家標註平台（類似 Label Studio），讓專家審核低信賴邊、修正斷言、標註任務難度，並將其回饋寫入 ToolSpace 的規則庫。

**與資料版本管理整合**
工具組合圖、合成資料庫、訓練樣本都應納入 DVC 或 LakeFS 等資料版本控管系統，確保實驗可重現，並支援 A/B 測試不同版本的合成資料對代理表現的影響。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先跳過方法論細節，直接閱讀第 1 節的「Data-Centric vs Tool-Centric」對比圖，理解為什麼「先有資料庫再推導工具」會出問題。接著看 §3.2 的工具組合圖示意，建立「工具是原子單元、邊是真實執行見證」的直覺，最後再回頭讀方法章節會順暢許多。

**給 AI 工程師**：重點放在 §3 的兩階段 pipeline 與 §5 的消融實驗。特別注意「execution-witnessed edges 明確優於 LLM-judged edges」這個結論——這意味著在生產環境中部署軌跡收集器比調用 GPT-4 來判斷工具關係更划算。實作時優先投資確定性規則的覆蓋率，而非追求 LLM 判斷的精緻度。

**給研究者**：聚焦 §1 的三項既有方法侷限性（工具—功能不匹配、不真實的編排、缺乏跨環境合成）與 §5 的縮放規律分析。ToolSpace 提出的「Trace-to-ENV」原則與「狀態感知隨機遊走 + 回溯」是值得延伸的方向，例如可探索如何把這套框架應用於多代理協作或具身代理的環境合成。

**給產品經理**：關注的是商業價值與落地節奏。ToolSpace 的核心承諾是「用更便宜的合成資料訓練出更強的長時程代理」，關鍵指標是「跨多少個 MCP 服務、平均多少步、斷言通過率」。建議先用 2–3 個內部 MCP 服務做小規模 PoC，驗證合成資料品質後再擴展到全企業工具鏈；同時預留預算處理隱私合規與介面漂移這兩個長期議題。
