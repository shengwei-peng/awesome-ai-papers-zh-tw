# DeNovoSWE：擴展長程環境規模以從零生成整個儲存庫

**原文標題：** DeNovoSWE: Scaling Long-Horizon Environments for Generating Entire Repositories from Scratch

## ⚡ TL;DR

現有軟體工程訓練資料多聚焦於單一議題修復，缺乏長程整個儲存庫生成的可驗證資料。
本文提出DeNovoSWE資料集，採用沙盒代理流程結合分治法與批評修復機制，並加入難度感知軌跡過濾。
微調Qwen3-30B-A3B後，BeyondSWE-Doc2Repo分數從5.8%躍至47.2%。

## 摘要翻譯

隨著基於大型語言模型的程式碼代理（LLM-based code agents）能力持續提升，其預期角色正從在現有程式碼庫（codebase）中進行局部錯誤修復（bug fixing），擴展到根據高階規格（high-level specifications）設計架構並實作完整的軟體儲存庫（repository）。然而，由於缺乏大規模、可驗證的整個儲存庫生成（whole-repository generation）資料，訓練代理（agent）執行此類長程（long-horizon）軟體工程（Software Engineering, SWE）任務仍然困難。在本文中，我們介紹 DeNovoSWE，一個用於整個儲存庫生成的大規模資料集。DeNovoSWE 包含 4,818 個高品質實例（instance），其中每個實例都需要依據文件（documentation）生成完整的儲存庫。我們的資料集透過精心設計的沙盒化代理工作流（sandboxed agentic workflow）自動建構，無需人工標註（human annotation）即可實現可擴展策展（scalable curation）。DeNovoSWE 採用「分治法」（divide and conquer）與批評-修復（critic-repair）的理念建構。為了平衡資料品質（data quality）與資料多樣性（data diversity），我們進一步引入難度感知的軌跡過濾（difficulty-aware trajectory filtering）策略。將 Qwen3-30B-A3B 在 DeNovoSWE 上微調（fine-tuning）後，大幅提升了其長程軟體工程效能（long-horizon SWE performance），在具挑戰性的 BeyondSWE-Doc2Repo 基準測試（benchmark）上，其分數（score）從 5.8% 提升至 47.2%。

### 核心貢獻（3～5點）
- **提出 DeNovoSWE 資料集**：包含 4,818 個高品質實例，每個實例需從文件生成完整儲存庫，為長程軟體工程任務提供大規模、可驗證的訓練資料，填補現有資料缺口。
- **設計全自動化資料建構流程**：透過沙盒化代理工作流，結合「分治法」與「批評-修復」理念，無需人工標註即可實現可擴展策展，大幅降低資料建構成本。
- **引入難度感知的軌跡過濾策略**：在資料品質與資料多樣性之間取得平衡，使資料集同時具備可信度與覆蓋廣度。
- **驗證微調效益**：將 Qwen3-30B-A3B 在 DeNovoSWE 上微調後，於 BeyondSWE-Doc2Repo 基準測試的分數從 5.8% 大幅躍升至 47.2%，實證該資料集對長程軟體工程效能的顯著助益。

### 適合對象
從事大型語言模型程式碼代理研究、軟體工程自動化、儲存庫級程式碼生成與長程任務規劃的學者與工程師；以及關注 AI 訓練資料建構、自動化資料策展流程、難度感知過濾機制與基準測試設計的研究人員。

## 深度分析

#### 方法論解析

DeNovoSWE 的核心方法論圍繞「從文件生成整個儲存庫」(document-to-repository generation) 這一極具挑戰性的長程軟體工程任務 (long-horizon SWE task) 展開。整體方法可拆解為三大核心模組：文件建構 (documentation construction)、評估設計 (evaluation design)、以及無洩漏任務執行 (leakage-free task execution)。以下逐一深入剖析其技術內涵。

**1. 沙盒化多代理工作流 (Sandboxed Multi-Agent Workflow)**

論文採用沙盒化 (sandboxed) 的多代理系統作為基礎設施，這是因為現代程式碼代理 (code agent) 通常具備工具存取能力 (tool access)，若無適當隔離，代理可能透過非預期管道存取參考實作 (oracle leakage)。沙盒機制確保任務執行環境的封閉性，這對於建構可驗證的訓練資料至關重要，因為任何洩漏都會污染資料品質並使下游評估失去意義。

**2. 分治法文件生成 (Divide-and-Conquer Documentation Generation)**

論文採用分治法 (divide and conquer) 哲學來處理文件建構問題。具體而言，每個儲存庫 (repository) 會被分解為若干獨立的能力單元 (capabilities)，然後由沙盒化代理分別為每個能力生成對應的文件。這種模組化設計的優勢在於：

- **降低單次生成複雜度**：將整個儲存庫的文件化任務拆解為多個子任務，避免單一代理在長上下文 (long context) 中產生品質衰減。
- **提升文件結構性**：分治後的文件天然具有更好的組織性，更貼近人類工程師撰寫技術文件的思維模式。
- **支援平行化生成**：各能力模組可平行處理，提升資料建構的可擴展性 (scalability)。

**3. 批評-修復機制 (Critic-Repair Mechanism)**

僅靠分治法並不足以保證文件品質，因為單次生成的文件往往難以同時滿足「完整性」、「組織性」與「與評估套件一致性」三項要求。為此，論文引入迭代式批評-修復 (critic-repair) 機制：

- **批評階段 (Critic)**：由專門的批評代理 (critic agent) 評估當前文件是否：(a) 完整覆蓋所有功能、(b) 結構清晰、(c) 與評估套件 (evaluation suite) 的期望行為一致。
- **修復階段 (Repair)**：根據批評結果，由修復代理對文件進行針對性修正。
- **迭代收斂**：重複上述過程直至文件通過品質閾值或達到最大迭代次數。

此機制的關鍵在於其「可執行性導向」(executable behavior alignment)：文件不僅要語義完整，更必須使後續從該文件生成的程式碼能通過儲存庫的測試套件。這比一般性的文件摘要或說明書生成要求更高。

**4. 難度感知軌跡過濾 (Difficulty-Aware Trajectory Filtering)**

這是論文最具方法論創新性的部分之一。在長程任務中，完全成功的軌跡 (trajectory) 往往難以取得——若僅保留完全成功的軌跡，會導致訓練資料過於簡單且缺乏多樣性 (diversity)；但若保留所有軌跡，則會引入大量低品質或錯誤的訓練信號。

難度感知過濾策略 (difficulty-aware trajectory filtering strategy) 試圖在資料品質 (data quality) 與任務多樣性 (task diversity) 之間取得平衡：

- **難度分層**：根據任務的內在複雜度對實例 (instance) 進行分層。
- **自適應保留率**：對於困難實例，即使成功率低，也保留部分部分成功的軌跡，以提供學習信號；對於簡單實例，則僅保留高品質完整軌跡。
- **可驗證性優先**：所有保留的軌跡都必須通過可執行測試的驗證，確保訓練資料的可信度。

此策略的設計動機在於：長程任務的學習價值不僅來自最終成功，更來自於代理在過程中展現的推理與規劃模式。透過難度感知過濾，可以保留這些富含學習信號的中間軌跡。

**5. 整體方法論評價**

DeNovoSWE 的方法論展現了「自動化資料建構」(automated data construction) 的成熟設計哲學：透過精心設計的多代理工作流，在無需人工標註 (human annotation) 的前提下，實現大規模、高品質的訓練資料生成。其方法論的優勢在於：(a) 可擴展性強，無標註瓶頸；(b) 品質可控，透過批評-修復機制保證；(c) 多樣性兼顧，透過難度感知過濾實現。然而，其方法論的潛在風險在於：若批評代理本身存在系統性偏差，可能會在資料中放大此偏差。

#### 實驗數據解讀

**1. 核心實驗結果**

最關鍵的實驗數據來自於 Qwen3-30B-A3B 模型在 BeyondSWE-Doc2Repo 基準測試 (benchmark) 上的表現：

| 模型 | BeyondSWE-Doc2Repo 分數 |
|------|------------------------|
| Qwen3-30B-A3B (基準) | 5.8% |
| Qwen3-30B-A3B + DeNovoSWE 微調 | 47.2% |

這個從 5.8% 到 47.2% 的提升幅度（約 8.1 倍）極為顯著，說明：

- **資料品質的有效性**：DeNovoSWE 的訓練資料確實包含了對長程儲存庫生成任務有直接幫助的學習信號。
- **任務遷移能力**：從 DeNovoSWE 訓練資料學到的能力可有效遷移至 BeyondSWE-Doc2Repo 這一獨立基準測試，顯示資料具有良好的泛化性。
- **基線模型的弱勢**：5.8% 的基準分數表明，即使 Qwen3-30B-A3B 是一個具有 300 億參數的模型，在未經專門訓練時，幾乎無法勝任整個儲存庫的生成任務。這凸顯了長程 SWE 能力並非隨模型規模自然湧現的湧現能力 (emergent capability)，而是需要專門的訓練資料。

**2. 資料規模與品質的權衡**

DeNovoSWE 包含 4,818 個高品質實例。這個數字在 SWE 訓練資料領域屬於中等規模——相比於 SWE-Gym、Scale-SWE、OpenSWE 等專注於議題修復 (issue resolution) 的大型資料集可能更大規模，但對於整個儲存庫生成這一更複雜的任務而言，4,818 個實例已足以支撐有效的微調 (fine-tuning)。這暗示了資料品質比單純的資料數量更為重要。

**3. 評估指標的解讀**

BeyondSWE-Doc2Repo 採用可執行測試 (executable tests) 作為評估手段，這是一種客觀且可驗證的評估協議 (evaluation protocol)。相較於基於相似度或人工評分的指標，測試通過率更能反映生成程式碼的實際功能性。然而，這也意味著評估結果對測試覆蓋率 (test coverage) 敏感——若測試套件本身不夠全面，可能無法完全捕捉程式碼品質的差異。

**4. 結果的侷限性與注意事項**

- **單一模型驗證**：實驗僅展示了 Qwen3-30B-A3B 的結果，未說明在其他模型架構（如 Dense 模型、不同規模的 MoE 模型）上的效果是否一致。
- **基準測試單一性**：主要結果集中在 BeyondSWE-Doc2Repo，雖然摘要提到 NL2RepoBench 的評估，但具體數據未在提供的文本中呈現。
- **未提供消融實驗 (ablation study) 細節**：分治法、批評-修復機制、難度感知過濾各自的貢獻程度未在文本中明確量化。

#### 與現有研究的比較

**1. 在 SWE 訓練資料領域的定位**

現有的 SWE 訓練資料集可大致分為兩類：

| 類別 | 代表性工作 | 任務範圍 |
|------|-----------|---------|
| 議題級修復 | SWE-Gym、Scale-SWE、OpenSWE、SWE-rebench | 單一議題修復 (single-issue fixes) |
| 儲存庫級生成 | DeNovoSWE | 整個儲存庫生成 (whole-repository generation) |

DeNovoSWE 的核心差異化在於：它將訓練任務從「修復現有程式碼中的局部問題」提升至「從零開始建構完整系統」。後者需要更強的長程規劃 (long-horizon planning)、架構設計、以及跨模組相互依賴的程式設計 (interdependent coding) 能力。

**2. 與相關基準測試的關係**

- **BeyondSWE (Chen et al., 2026b)**：專注於從文件生成儲存庫的長程任務，DeNovoSWE 的訓練資料與此基準測試的任務設定高度一致，這解釋了為何微調後在 BeyondSWE-Doc2Repo 上有如此顯著的提升。
- **NL2RepoBench (Ding et al., 2025)**：同樣評估從自然語言生成儲存庫的能力，DeNovoSWE 在此基準上也有正面結果，顯示其泛化性。
- **SWE-bench-Verified**：雖然是 SWE 領域的主流基準，但其議題級任務設定與 DeNovoSWE 的儲存庫級任務有本質差異，因此 DeNovoSWE 並不直接針對 SWE-bench-Verified 最佳化。

**3. 相比現有方法的改進**

- **相比議題級資料集**：DeNovoSWE 填補了「長程可驗證 SWE 資料」(long-horizon verifiable SWE data) 的關鍵空白，這是現有資料集普遍缺乏的。
- **相比人工標註方法**：透過沙盒化代理工作流實現完全自動化，避免了人工標註的成本與一致性問題。
- **相比單純的代理軌跡收集**：DeNovoSWE 的分治法 + 批評-修復機制提供了更結構化的品質控制，而非簡單地收集代理的原始執行軌跡。

**4. 局限性與不足**

- **語言與領域覆蓋**：文本未明確說明 DeNovoSWE 涵蓋的程式語言範圍與應用領域。若僅限於 Python 或特定領域，其泛用性將受限。
- **文件品質的理論保證**：雖然批評-修復機制提升了文件品質，但缺乏對文件「忠實性」(faithfulness) 的形式化保證。
- **與人類開發流程的對齊**：從文件生成儲存庫的流程與真實世界軟體工程工作流程 (real-world SWE workflows) 之間的差距未充分討論。真實開發中，文件往往與程式碼共同演進，而非先有完整文件再有程式碼。

#### 可重現性評估

**1. 資料集可用性**

DeNovoSWE-Data 包含 4,818 個高品質實例，從論文描述來看，這是一個明確可發布的資料集。然而，僅從提供的文本中，無法確認以下關鍵細節：

- 資料集是否已公開釋出 (publicly released)？
- 釋出平台為何（Hugging Face、GitHub、官方網站）？
- 資料格式與結構描述是否隨論文提供？
- 是否包含評估套件 (evaluation suite) 以支援下游驗證？

**2. 程式碼與模型權重**

- **DeNovoSWE-Agent**：論文提到訓練了 DeNovoSWE-Agent，但未明確說明模型權重 (model weights) 是否公開。
- **建構流程程式碼**：沙盒化代理工作流的實作程式碼是否開源 (open-source) 未在文本中說明。對於一個以「自動化資料建構」為核心貢獻的工作而言，開源建構流程對於可重現性至關重要。
- **基礎模型**：Qwen3-30B-A3B 是已有的開源模型，這部分具備可重現性基礎。

**3. 可重現性風險**

- **代理系統的隨機性**：多代理工作流中的代理決策具有隨機性，若未固定隨機種子 (random seed) 或溫度參數 (temperature)，不同運行可能產生不同資料。
- **評估環境依賴**：BeyondSWE-Doc2Repo 的評估需要特定的執行環境與依賴套件，若環境配置有差異，可能導致評估結果不可直接比較。
- **訓練超參數 (hyperparameters) 未充分披露**：微調 Qwen3-30B-A3B 的具體超參數（學習率、batch size、訓練步數等）在提供的文本中未呈現。

**4. 整體可重現性評級**

基於現有資訊，DeNovoSWE 的可重現性處於中等水平。資料集的規模與品質描述清晰，但具體的釋出管道、建構程式碼、訓練細節尚需從完整論文或附錄中確認。對於希望基於此工作進行後續研究的團隊而言，最關鍵的需求是：(a) 資料集的公開存取、(b) 建構流程的程式碼開源、(c) 訓練超參數的完整披露。

#### 未來研究方向

**1. 資料規模與多樣性的擴展**

當前 DeNovoSWE 包含 4,818 個實例，雖然已證明有效，但相對於真實世界的軟體開發場景仍屬小規模。未來可考慮：

- **跨語言擴展**：將資料建構流程擴展至更多程式語言（Java、JavaScript、Rust、Go 等），提升資料的語言覆蓋面。
- **跨領域擴展**：涵蓋更多應用領域（網頁開發、系統程式設計、機器學習、資料工程等），使訓練出的代理更具泛用性。
- **規模化至數萬甚至數十萬實例**：探索更大規模資料對長程 SWE 能力的邊際效益。

**2. 方法論的深化**

- **形式化品質保證**：為批評-修復機制引入形式化驗證 (formal verification) 手段，例如透過靜態分析或符號執行 (symbolic execution) 來驗證文件與程式碼的一致性。
- **自適應難度分層**：目前的難度感知過濾策略可進一步精緻化，例如根據代理在訓練過程中的學習曲線動態調整難度分層。
- **多代理協作機制**：探索不同代理角色（如架構師代理、實作代理、測試代理）之間的更細粒度分工與協作。

**3. 評估方法的演進**

- **更全面的測試覆蓋**：BeyondSWE-Doc2Repo 的測試套件覆蓋率可進一步提升，以更準確地評估生成程式碼的品質。
- **過程評估 (process evaluation)**：除了最終的測試通過率，可引入對代理推理過程的評估，例如規劃品質、模組化程度、程式碼可維護性等。
- **人類專家對齊評估**：將自動化評估與人類專家評估相結合，以彌補測試套件在捕捉「程式碼品質」方面的不足。

**4. 與真實開發流程的對齊**

- **迭代式開發模擬**：真實軟體開發很少是「一次完成」，而是迭代演進的。未來可探索讓代理在多輪互動中逐步完善儲存庫的訓練設定。
- **需求變更處理**：模擬真實開發中需求變更 (requirement change) 的場景，訓練代理處理動態規格變化的能力。
- **團隊協作模擬**：探索多個代理協作開發同一儲存庫的場景，更貼近真實的軟體工程團隊工作流程。

**5. 下游應用與影響**

- **自動化軟體原型生成**：將 DeNovoSWE 訓練的代理應用於快速原型開發 (rapid prototyping)，加速軟體創新週期。
- **教育與訓練工具**：利用此類代理作為程式設計教學助手，幫助學習者理解從規格到實作的完整流程。
- **開源生態貢獻**：探索如何讓此類代理自動生成高品質的開源專案，降低開源貢獻的門檻。

**6. 理論基礎的建立**

目前 DeNovoSWE 的方法論主要是經驗性的 (empirical)，未來可從理論角度探討：

- 為什麼分治法 + 批評-修復機制在長程任務中特別有效？

這些理論問題的解答將有助於從「經驗驅動的資料建構」走向「理論指導的資料工程」，進一步提升類似資料集的建構效率與品質。

## 論文問答

**Q1：DeNovoSWE 試圖解決的核心問題是什麼？**
A：DeNovoSWE 試圖解決長程軟體工程（long-horizon SWE）訓練資料稀缺的問題。傳統的 SWE 訓練資料集（例如 SWE-Gym、Scale-SWE、OpenSWE、SWE-rebench 等）大多聚焦於單一議題修復（single-issue fixes），無法支援需要長程規劃（long-horizon planning）與跨元件相互依賴程式設計（interdependent coding）的整個儲存庫生成（whole-repository generation）任務。論文中明確指出，當前的 SWE-bench-Verified 正面臨「區辨度下降」與「無法充分壓測長程儲存庫級推理」的雙重限制，因此需要新的資料集來填補這個關鍵缺口。

**Q2：為什麼現有的 SWE 基準測試與資料集無法有效支援長程任務的訓練？**
A：現有 SWE 基準測試（如 SWE-bench-Verified）以議題級任務（issue-level tasks）為主，主要評估單一錯誤修復（bug fixing）能力，無法反映真實世界軟體工程工作流程（real-world SWE workflows）中需要從零開始設計整個系統的場景。此外，雖然近期出現了 BeyondSWE、NL2RepoBench 等專門評估長程能力的基準測試，但對應的訓練資料仍然嚴重不足——多數 SWE 訓練資料集仍以議題解決（issue resolution）為中心，無法用於訓練代理（agent）進行整個儲存庫級別的生成。這種「評測進步但訓練資料落後」的不平衡，是 DeNovoSWE 想要解決的根本問題。

**Q3：為什麼長程能力對程式碼代理如此重要？**
A：長程能力是真實世界軟體工程任務的核心需求，因為實際開發往往涉及從高階規格（high-level specifications）出發，進行架構設計、模組劃分、介面定義與跨檔案整合等複雜工作。論文中強調，僅僅能修復單一議題的代理無法勝任「從文件到完整儲存庫」的任務，因為這需要代理同時進行儲存庫級推理（repository-level reasoning）與長程規劃（long-horizon planning）。當前沿模型（frontier models）在 BeyondSWE 等基準測試上的表現仍然偏低，正是因為缺乏足夠的長程可驗證軟體工程資料（long-horizon verifiable SWE data）來進行有效訓練。

**Q4：DeNovoSWE 的核心資料建構方法是什麼？**
A：DeNovoSWE 採用了一個自動化的沙盒化代理工作流（sandboxed agentic workflow），透過「分治法」（divide and conquer）與「批評-修復」（critic-repair）的雙重哲學來建構高品質的文件到儲存庫生成（document-to-repository generation）任務實例。具體而言，系統會將每個儲存庫分解為不同的能力模組，由沙盒化代理分別為各模組生成對應的文件，再透過迭代式的批評-修復機制來確保文件的完整性與可執行性。這種設計讓整個資料建構流程無需人工標註（human annotation），即可達到可擴展策展（scalable curation）的目標。

**Q5：「分治法」與「批評-修復」哲學為何重要？它們解決了什麼挑戰？**
A：「分治法」的重要性在於它將「為整個儲存庫撰寫完整文件」這個極度困難的單一任務，分解為多個較小且可管理的子任務——每個子任務對應儲存庫中的一個特定能力模組，從而大幅降低了單次生成的複雜度。「批評-修復」機制則解決了「單次生成難以產出與評估套件（evaluation suite）完全一致的文件」這個核心難題，透過迭代式的品質檢查與修正，確保最終文件能夠支援從文件生成的實作通過可執行測試（executable tests）。這兩種哲學的結合直接決定了任務有效性（task validity）與資料品質（data quality），是 DeNovoSWE 能產出 4,818 個高品質實例的關鍵設計選擇。

**Q6：難度感知的軌跡過濾（difficulty-aware trajectory filtering）策略如何平衡資料品質與多樣性？**
A：對於複雜的整個儲存庫生成任務而言，完全成功的軌跡（trajectory）往往難以取得，若僅保留成功案例會嚴重犧牲資料多樣性（data diversity）。難度感知的軌跡過濾策略透過根據任務難度動態調整過濾標準，在資料品質（data quality）與任務多樣性之間取得平衡——對於較困難的實例保留部分成功的軌跡，而對於較容易的實例則要求更嚴格的成功標準。這種設計使得策展（curation）出來的訓練資料既能反映真實任務的複雜度分布，又能提供足夠數量的可驗證專家軌跡供模型學習。

**Q7：DeNovoSWE 使用哪些基準測試來評估模型效能？**
A：DeNovoSWE 主要在兩個長程軟體工程基準測試上進行評估：BeyondSWE-Doc2Repo（Chen et al., 2026b）與 NL2RepoBench（Ding et al., 2025）。BeyondSWE-Doc2Repo 是專門用於評估「從文件生成整個儲存庫」能力的基準測試，而 NL2RepoBench 則是另一個用於評估長程程式碼生成的重要基準。這兩個基準測試的共同特點是它們都強調長程編碼能力，能夠更好地反映真實世界的軟體工程工作流程（real-world SWE workflows），而非僅僅是單一議題修復。

**Q8：DeNovoSWE 的關鍵實驗結果為何？**
A：最關鍵的實驗結果是：在 DeNovoSWE 上微調（fine-tuning）Qwen3-30B-A3B 模型後，其在 BeyondSWE-Doc2Repo 基準測試上的分數（score）從原本的 5.8% 大幅提升至 47.2%。這個將近 8 倍的效能躍升，證明了 DeNovoSWE 訓練資料對於長程儲存庫級任務（long-horizon repository-level tasks）的有效性。這個結果也顯示 DeNovoSWE 填補了長程可驗證軟體工程訓練資料（long-horizon verifiable SWE training data）的關鍵缺口。

**Q9：DeNovoSWE 資料集規模與組成為何？是否有進行消融研究？**
A：DeNovoSWE 資料集（DeNovoSWE-Data）共包含 4,818 個高品質實例（instance），每個實例都需要從文件生成一個完整的儲存庫。雖然論文中未明確列出詳細的消融研究（ablation studies）章節，但從方法描述可以推論，分治法、批評-修復機制與難度感知過濾策略這三個核心元件都對最終資料品質有重要貢獻。論文中強調了「無人工標註的可擴展策展」這一事實，意味著整個流程的每個環節都經過精心設計以確保資料品質。

**Q10：DeNovoSWE 適用於哪些實際應用場景？**
A：DeNovoSWE 適用於需要從高階規格（high-level specifications）或文件自動生成完整軟體系統的場景，例如快速原型開發、自動化工具鏈建構、教育用途的程式設計範例生成等。在實際軟體開發中，這類技術可以幫助開發者從設計文件快速產出可執行的程式碼骨架，或在遺失原始碼的情況下根據文件重建系統。此外，對於需要大量相似但客製化軟體的企業（例如內部工具開發），DeNovoSWE 訓練的代理可以大幅降低開發成本。

**Q11：將 DeNovoSWE 應用於實際產品時需要考慮哪些因素？**
A：實際產品化時需要考慮幾個重要因素：首先，沙盒化（sandboxed）執行的安全性與成本，因為整個儲存庫生成需要大量計算資源；其次，生成程式碼的可維護性與安全性，自動生成的程式碼可能引入難以察覺的漏洞；第三，與現有開發工具鏈的整合性，包括版本控制、CI/CD 流程等；最後，文件品質對生成結果的影響——若輸入文件本身不完整或不一致，代理的輸出品質將會受到限制。產品設計時也需要考慮如何讓人類開發者能有效審查與修改自動生成的程式碼。

**Q12：DeNovoSWE 對軟體工程領域的更廣泛影響為何？**
A：DeNovoSWE 對領域的影響主要體現在三個層面：學術上，它推動了長程軟體工程（long-horizon SWE）這個新興研究方向，提供了一個可擴展的資料建構範式；技術上，它展示了如何透過沙盒化代理工作流（sandboxed agentic workflow）自動化產生高品質訓練資料，減少對人工標註（human annotation）的依賴；產業上，它為「從規格自動生成軟體」這個長久以來的願景提供了實證基礎，可能改變未來軟體開發的工作流程。這項工作也呼應了軟體工程領域從「議題修復」走向「系統建構」的典範轉移。

**Q13：DeNovoSWE 有哪些已知的限制？**
A：DeNovoSWE 的限制包括：首先，雖然 4,818 個實例已具一定規模，但相較於真實世界儲存庫（real-world repositories）的多樣性仍屬有限，可能無法涵蓋所有程式語言、領域與架構風格；其次，文件到儲存庫生成任務假設輸入文件是完整且一致的，但真實世界的文件往往並非如此；第三，評估主要依賴可執行測試（executable tests），但測試覆蓋率本身可能不足以完整反映程式碼品質；最後，沙盒化執行雖然能防止 oracle 洩漏，但也限制了代理可使用的工具與環境複雜度。

**Q14：DeNovoSWE 可能面臨哪些失敗案例或邊緣情況？**
A：可能的失敗案例包括：當文件描述的系統極為複雜或涉及高度專業領域（如作業系統核心、編譯器）時，代理可能無法產出可通過所有測試的實作；當儲存庫需要特定外部依賴或硬體資源時，沙盒化環境可能無法完整支援；當文件本身存在歧義或不一致時，代理的生成結果可能與預期行為有偏差；對於需要創新演算法或非平凡數學推導的任務，純粹從文件生成可能無法達到人類專家的水準。這些邊緣情況凸顯了「文件到儲存庫生成」任務的內在難度。

**Q15：DeNovoSWE 未來的研究方向為何？**
A：未來研究方向可能包括：擴展資料集規模與領域覆蓋範圍，納入更多程式語言與應用場景；改進文件建構（documentation construction）方法，使其能處理更複雜、更模糊的真實世界文件；探索更強的評估設計（evaluation design），例如結合靜態分析、形式化驗證與動態測試；研究如何在無洩漏任務執行（leakage-free task execution）的前提下，允許代理使用更豐富的工具與環境；以及將 DeNovoSWE 的方法論擴展到其他長程任務領域，如長程對話、長程規劃等，進一步推動長程可驗證軟體工程資料（long-horizon verifiable SWE data）的發展。

程式設計課程或競賽主辦單位可使用此技術，根據題目敘述自動生成完整的參考實作儲存庫（含測試），用於評分或教學示範，大幅降低命題與準備參考解答的人力成本。

針對文件尚完整但程式碼已難以維護的遺留系統，可將既有文件餵入代理，生成符合現代架構（如從 Java 改寫為 Go、從單體改為微服務）的新儲存庫，作為重構的起點。

### 實作前置條件

**資料需求**
- 至少數千份結構化文件（README、API 規格、技術文件），需與可執行測試對齊

- 文件與程式碼之間的對應關係資料（用於訓練與評估）

**運算資源**
- 訓練階段：至少 8 張以上 A100/H100 等級 GPU，建議使用 70B 級以上基座模型進行微調

- 沙盒環境：每個任務實例需獨立的 Docker 容器或 VM，建議配置 Kubernetes 叢集以支援大規模並行評估

**技能門檻**
- 熟悉 LLM 微調流程（LoRA、全參數微調、SFT 資料準備）
- 具備多代理系統設計經驗（任務分解、批評-修復迴圈）
- 熟悉 Docker、沙盒隔離、CI/CD 與自動化測試框架
- 具備軟體工程領域知識，能判斷生成程式碼的品質與正確性

### 實作步驟建議

**步驟 1：盤點現有文件與程式碼資產**
盤點組織內部或目標領域中「文件完整且對應可執行測試」的儲存庫，作為資料來源。優先選擇文件結構化程度高、測試覆蓋率超過 70% 的專案。

**步驟 2：建構文件生成管線**
依照論文的「分治法 + 批評-修復」哲學，設計多代理工作流：
- 分解代理：將儲存庫功能拆解為獨立能力模組
- 文件生成代理：為每個模組產出對應文件
- 批評代理：檢查文件是否與測試套件行為一致
- 修復代理：根據批評結果迭代修正文件

**步驟 3：建立沙盒化評估環境**
為每個任務實例配置獨立沙盒，內含：
- 參考儲存庫的測試套件
- 隔離的網路與檔案系統，防止代理存取參考實作
- 標準化的評估協議（執行測試、收集通過率）

**步驟 4：實施難度感知軌跡過濾**
針對複雜任務（完全成功的軌跡稀少），採用論文提出的過濾策略：
- 為每個實例設定難度等級
- 保留部分成功的軌跡（如通過率 ≥ 30%），以維持資料多樣性
- 對高難度實例放寬品質門檻，避免資料過度集中於簡單任務

**步驟 5：微調基座模型**
使用策展後的資料對 Qwen3-30B-A3B 或同等級模型進行微調。建議先以小樣本驗證流程，再擴展至完整 4,818 實例規模。

**步驟 6：建立持續整合與監控機制**
將訓練好的代理整合至 CI/CD 管線，設定：
- 自動化的回歸測試（使用 BeyondSWE-Doc2Repo 或自建基準）
- 生成品質監控儀表板（測試通過率、程式碼品質指標）
- 人工抽樣審核機制，定期檢查生成結果

**步驟 7：迭代優化與領域適配**
根據實際使用回饋，持續收集失敗案例，並將其轉化為新的訓練資料，形成閉環改進。

### 潛在風險與注意事項

**風險 1：文件與程式碼不一致導致任務失效**
若輸入文件與參考實作存在偏差，代理可能生成「通過測試但不符合文件意圖」的程式碼。
*緩解措施*：在建構階段強化批評-修復迴圈，確保文件與測試行為雙向一致；部署後加入人工審核環節。

**風險 2：沙盒洩漏導致評估失真**
代理可能透過網路、檔案系統或環境變數存取參考實作，造成評估分數虛高。
*緩解措施*：採用多層沙盒隔離（網路遮罩、唯讀檔案系統、隨機化路徑）；定期進行紅隊測試，驗證沙盒穩固性。

**風險 3：生成程式碼的安全性漏洞**
自動生成的程式碼可能引入 SQL 注入、XSS、依賴套件漏洞等安全問題。
*緩解措施*：整合靜態分析工具（如 Semgrep、CodeQL）與依賴掃描（如 Snyk）至評估流程；對生成結果進行強制安全審查。

**風險 4：訓練資料的版權與授權爭議**
使用 GitHub 公開儲存庫作為資料來源時，需注意授權協議（MIT、Apache、GPL 等）的相容性。
*緩解措施*：建立授權過濾機制，僅納入相容授權的儲存庫；對生成輸出的授權狀態進行標註。

**風險 5：模型對長程任務的幻覺與遺漏**
即使經過微調，代理仍可能在長程任務中遺漏需求細節或產生幻覺實作。
*緩解措施*：採用分階段驗證（先架構、再模組、最後整合）；保留人類工程師在關鍵決策點的介入權。

**風險 6：運算成本過高**
訓練與大規模評估的 GPU 成本可能超出預期。
*緩解措施*：採用 LoRA 等參數高效微調方法；使用 spot instance 或雲端彈性運算；建立成本監控與預算告警。

### 與其他技術的整合建議

**與 RAG（檢索增強生成）整合**
在生成前，先從組織內部知識庫檢索相關 API 文件、設計規範與過往實作，作為代理的額外上下文，提升生成結果的領域契合度。

**與現有 SWE 代理框架整合**
可將 DeNovoSWE 訓練的模型作為 OpenHands、SWE-agent 等框架的後端模型，取代或增強其原有的規劃與程式碼生成能力。

**與 CI/CD 管線整合**
將代理部署為「規格到程式碼」的自動化服務，串接至 GitHub Actions 或 GitLab CI：當 PR 包含新的規格文件時，自動觸發儲存庫生成並提交草稿 PR。

**與靜態分析與測試工具整合**
在評估流程中整合 pytest、Jest、ESLint、mypy 等工具，作為多層次的品質閘門，不僅依賴單一測試套件。

**與版本控制與 Issue 追蹤系統整合**
將生成結果自動關聯至對應的 Issue 或 Ticket，記錄生成過程的決策依據，便於後續追溯與審查。

**與企業級 LLM 平台整合**
透過 vLLM、TGI 或雲端服務（如 Azure ML、AWS Bedrock）部署模型，與企業既有的 LLM Gateway、權限管理、審計日誌系統對接。

### 給不同背景讀者的閱讀建議

**給初學者**
建議先閱讀摘要與介紹章節，建立「整個儲存庫生成」這個任務的基本概念；接著跳過技術細節，直接看實驗結果（5.8% → 47.2% 的提升），感受此技術的潛力。實作層面可先從小規模的「單一檔案生成」工具（如 Cursor、Copilot Workspace）開始體驗，再逐步理解多代理與沙盒化的概念。

**給 AI 工程師**
重點閱讀第 3 節的「分治法 + 批評-修復」管線設計，這是本論文的核心方法論；仔細研究難度感知軌跡過濾策略的實作細節，這對處理真實世界不平衡資料極具參考價值。實作時建議先復現論文的沙盒環境，再逐步替換為組織內部的工具鏈。

**給研究者**
本論文在「長程可驗證資料建構」上提出了一套系統性方法，三大挑戰（文件建構、評估設計、無洩漏執行）的拆解框架值得深入研究。可進一步探索的方向包括：文件品質的自動量化指標、批評-修復迴圈的收斂性分析、以及此方法在其他領域（如論文寫作、影片生成）的可遷移性。

**給產品經理**
理解此技術的關鍵在於「從文件到可執行程式碼」的端到端自動化能力，這將改變軟體交付的成本結構與時程。建議評估組織內部哪些場景（內部工具、客戶 PoC、樣板專案）適合導入，並關注三個商業指標：交付時間縮短比例、人力成本下降幅度、以及生成程式碼的維護成本。導入初期建議設定保守的成功標準（如 30% 任務可由人類工程師接手完成），再逐步提升自動化比例。
