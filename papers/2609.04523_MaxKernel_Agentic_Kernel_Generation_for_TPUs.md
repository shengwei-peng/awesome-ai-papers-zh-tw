## ⚡ TL;DR

開發高效能 TPU 自訂核心需深厚硬體專業，過程複雜且耗時。

## 摘要翻譯

為加速器（accelerator）設計與撰寫高效能自訂核心（custom kernels）是一項複雜任務，需要深厚的硬體層級專業知識（hardware-level expertise）。大型語言模型（Large Language Model, LLM）可與即時編譯器回饋（compiler feedback）結合，以建構用於核心生成的智能體系統。在本研究中，我們提出 MaxKernel，一個多智能體系統（multi-agent system），為 TPU（Tensor Processing Unit）核心開發實作三種不同範式：（1）人在迴路（Human-in-the-Loop, HITL）智能體，用於協作式逐步設計；（2）自主智能體（Autonomous / Auto agent），執行全自動化、指標／追蹤驅動的最佳化迴路（metric/trace-driven optimization loop）；以及（3）基於圖形的自主搜尋（Graph-Based Autonomous Search），擴展 Auto 智能體以進行設計空間的全域探索（global exploration of the design space）。這三種範式皆利用一組共享的專門化子智能體（specialized sub-agents）來處理規劃（planning）、實作（implementation）、自我除錯（self-debugging）、測試（testing）與硬體剖析（hardware profiling）。我們在 JaxBench（一套包含 50 個多樣化 TPU 核心任務的綜合測試套件）上評估 MaxKernel，並搭配來自最先進開源模型（state-of-the-art open-source models）的複雜真實世界工作負載（real-world workloads）。我們證實 MaxKernel 能穩定生成高度最佳化的實作，匹配專家手工調校基準（expert hand-tuned baselines），並在整個基準測試中帶來顯著的效能提升。我們的智能體已開源（open-sourced），可於 https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel 取得。

### 核心貢獻（3～5點）
- 提出 MaxKernel，一個專為 TPU 設計的多智能體系統（multi-agent system），整合人在迴路（HITL）、全自動（Auto）與基於圖形的自主搜尋（Graph-Based Autonomous Search）三種運作範式。
- 建立由專門化子智能體（specialized sub-agents）組成的共享協作架構，涵蓋規劃、實作、自我除錯、測試與硬體剖析等核心開發階段。
- 實作指標／追蹤驅動的最佳化迴路（metric/trace-driven optimization loop），讓自主智能體能根據編譯器回饋與硬體剖析資料反覆改進核心效能。
- 透過基於圖形的自主搜尋擴展 Auto 智能體，支援設計空間的全域探索（global exploration of the design space），提升找到高效能核心的機會。
- 在 JaxBench（50 個 TPU 核心任務）與真實世界工作負載（real-world workloads）上驗證，證明 MaxKernel 能匹配專家手工調校基準（expert hand-tuned baselines）並達到顯著效能提升，且已開源釋出。

### 適合對象
本論文適合從事加速器核心開發、深度學習編譯器最佳化、AI 輔助軟體工程，以及多智能體系統研究的學術研究者與工程師。特別是對 TPU / JAX / Pallas 核心生成、LLM 驅動的程式合成，以及自動化硬體效能調校有興趣的讀者，將能從中獲得具體的方法論與實證結果。

## 深度分析

#### 方法論解析

MaxKernel 的核心設計理念，是將「高效能加速器核心（accelerator kernel）」這項高度依賴硬體層級專業知識（hardware-level expertise）的任務，拆解為一組可迭代、可驗證、可回饋的子任務，並以多智能體系統（multi-agent system）協作完成。整體方法論可從四個層次理解：

1. **專門化子智能體（specialized sub-agents）的分工架構**  
   系統將核心生成流程拆成規劃（Planning）、實作（Implementation）、測試（Testing）、自動調校（Autotuning）與硬體剖析（Hardware Profiling）五大職能。  
   - **規劃智能體（Planning Agent）**：根據硬體規格（如 TPU 的 HBM、SRAM/VMEM 容量、向量單元寬度）與參考實作，提出高階演算法最佳化計畫，例如多維度分塊策略（multi-dimensional tiling strategies）、DMA 管線化（DMA pipelining）與記憶體階層（memory hierarchies）配置。  
   - **實作智能體（Implementation Agent）**：將規劃轉譯為 JAX/Pallas 程式碼，並透過編譯器回饋（compiler feedback）進行自我除錯（self-debugging）。由於加速器 API 嚴格且低階編譯器錯誤不透明（opaque low-level compiler errors），此處的反覆編譯—修復迴路是關鍵。  
   - **測試與驗證智能體（Testing and Verification Agents）**：由測試合成智能體（Test Synthesis Agent）產生測試案例，再由執行智能體（Execution Agent）在真實 TPU 上執行，並依據該世代 TPU 的動態數值容忍度（numerical tolerances）驗證功能正確性（functional correctness）。  
   - **自動調校智能體（Autotuning Agent）**：在程式碼結構確定後，系統性地探索區塊大小（block sizes）、分塊維度（tile dimensions）等超參數空間。  
   - **剖析智能體（Profiling Agent）**：利用 XProf 擷取執行追蹤（trace），提取執行延遲、記憶體頻寬利用率、運算密度等指標，形成指標／追蹤驅動的最佳化迴路（metric/trace-driven optimization loop）。

2. **三種編排範式（orchestration paradigms）**  
   - **Human-in-the-Loop（HITL，人在迴路）**：在關鍵決策點保留人類開發者的控制權，適合複雜或高風險核心，確保安全性與架構一致性（safety and architectural alignment）。  
   - **Autonomous Loop（Auto，自主迴路）**：全自動執行規劃—生成—測試—剖析的封閉迴路，適合已有明確目標且希望快速迭代的情境。  
   - **Graph-Based Autonomous Search（基於圖形的自主搜尋）**：將核心設計空間建模為形式化搜尋圖（formal search graph），支援簡單平行搜尋、束搜尋（beam search）等演算法，進行設計空間的全域探索（global exploration of the design space），以避免區域最佳解。

3. **知識儲存與檢索增強生成（Retrieval-Augmented Generation, RAG）**  
   由於硬體規格、框架文件與技術報告內容龐大，無法全部塞入上下文視窗，MaxKernel 採用 RAG 管線，在需要時從外部知識儲存（knowledge store）動態檢索相關資訊。這讓子智能體能取得最新、最切題的 API 細節與硬體限制，降低幻覺風險。

4. **編譯器與剖析工具構成的閉環回饋**  
   與單純的零樣本（zero-shot）或少樣本（few-shot）LLM 生成不同，MaxKernel 把編譯成功／失敗訊號、執行追蹤與數值正確性都納入回饋。這種「生成—驗證—再規劃」的迴路，是應對加速器 API 剛性（rigidity）、嚴格記憶體限制（strict memory constraints）與不透明錯誤訊息的必要設計。

#### 實驗數據解讀

論文在兩類評估場景中驗證 MaxKernel：

1. **JaxBench 綜合測試套件**  
   包含 50 個多樣化的 TPU 核心任務（kernel tasks），涵蓋不同運算模式與記憶體存取型態。MaxKernel 在這些任務上達到 **1.58× 幾何平均（geometric mean）加速**。幾何平均的意義在於它對極端值較不敏感，能反映「整體」效能提升；1.58× 表示在廣泛的核心類型中，系統多能穩定產生比參考實作更快的核心。

2. **真實世界工作負載（real-world workloads）**  
   針對八個來自最先進開源模型（state-of-the-art open-source models）且存在人工撰寫核心的生產級核心，MaxKernel 相對於參考程式碼（reference code）達到 **2.32× 幾何平均加速**，而人類專家手工調校基準（expert hand-tuned baselines）僅達 **2.02×**。這意味著在部分實際應用中，智能體式生成不僅能逼近專家水準，還能超越人類調校結果。

**數據的深層意涵：**

- **功能正確性與效能並重**：實驗同時評估功能正確性（functional correctness）與執行時間（execution time），顯示系統並非以犧牲正確性換取速度，而是在滿足數值容忍度的前提下達成加速。  
- **跨領域泛化能力**：JaxBench 的 50 個任務多樣性高，1.58× 的整體加速暗示 MaxKernel 的規劃與搜尋策略具備一定泛化性，而非僅對單一運算過擬合。  
- **人機效能比較的解讀**：2.32× 對 2.02× 的結果雖然振奮，但需注意「參考程式碼」的基準定義。若參考程式碼是未經最佳化的純 JAX 實作，則 2.02× 與 2.32× 都是相對於該基準的加速；MaxKernel 的優勢在於它比人類專家更能挖掘硬體細節，但也可能反映人類調校時間成本較高、未能窮盡設計空間。  
- **未揭露的變異性**：論文摘要與引言未提供每個任務的個別加速分布、失敗率、LLM 呼叫次數或搜尋預算。因此，1.58× 與 2.32× 雖具代表性，但無法直接推論系統在邊角案例或極高記憶體壓力任務上的穩定性。

#### 與現有研究的比較

MaxKernel 的定位介於「傳統編譯器自動排程」與「純 LLM 程式生成」之間，並試圖結合兩者優勢：

1. **相較於傳統編譯器最佳化技術（Halide、TVM、Ansor）**  
   Halide、TVM 與 Ansor 透過演算法定義與排程解耦（decoupling algorithm definitions from scheduling）來探索最佳化空間，但仍需大量領域知識（domain knowledge）或昂貴的演化式搜尋階段（expensive evolutionary search phases）。MaxKernel 的差異在於：  
   - 使用 LLM 作為「搜尋導航器」，能根據編譯器回饋與剖析結果主動提出演算法層級變更，而不只是調整排程參數。  
   - 透過 RAG 動態注入硬體與框架知識，降低對人類領域知識的依賴。  
   - 然而，傳統方法在可解釋性與確定性上仍具優勢；MaxKernel 的黑箱 LLM 決策可能較難審計。

2. **相較於 AutoComp 等 LLM 導航張量程式（tensor programs）研究**  
   AutoComp 已展示 LLM 可在張量程式搜尋空間中導航，並在想法過於複雜導致無法編譯前及時放棄。MaxKernel 進一步擴展為多智能體架構，加入：  
   - 專門的測試、剖析與自動調校智能體，形成更完整的閉環。  
   - Graph-Based Autonomous Search，支援多種搜尋演算法與大規模平行探索。  
   - TPU/JAX-Pallas 專屬的硬體回饋整合（XProf、VMEM、DMA）。

3. **相較於零樣本／少樣本 LLM 生成**  
   單純的 LLM 生成難以應對加速器 API 的剛性與不透明錯誤。MaxKernel 透過自我除錯、編譯器回饋與數值驗證，大幅提升生成成功率與效能品質。

4. **相較於演化式搜尋（evolutionary search）、貪婪搜尋（greedy search）與協作式搜尋（collaborative search）**  
   這些方法多聚焦於參數空間或程式變異。MaxKernel 的 Graph-Based Autonomous Search 將設計空間形式化為圖，能更靈活地結合不同搜尋策略，並透過平行化擴展至全域探索。

**限制：**

- **評估範圍**：論文明言主要評估聚焦於 TPU 上的 JAX/Pallas，雖然底層智能體原則可推廣至 GPU（CUDA/Triton）、AWS Trainium（NKI）、MTIA 等加速器，但尚未提供跨平台實證。  
- **成本與效率**：LLM 多次呼叫、反覆編譯與真實硬體剖析的計算與金錢成本未被量化。對於生產環境中的快速迭代，這些成本可能成為瓶頸。  
- **基準比較的完整性**：未與所有相關方法（如 Ansor、AutoComp）在相同硬體與相同任務上進行直接對照，難以嚴格判定絕對優勢。  
- **依賴外部工具品質**：RAG 檢索結果、XProf 追蹤解析與編譯器錯誤訊息的品質，都會影響最終效能；若文件不完整或錯誤訊息過於模糊，智能體可能陷入無效迭代。

#### 可重現性評估

1. **程式碼開放性**  
   MaxKernel 已於 GitHub 開源（https://github.com/AI-Hypercomputer/accelerator-agents/tree/main/MaxKernel），這是正向訊號。開源釋出讓其他研究者能檢視子智能體實作、提示設計與 orchestration 邏輯。

2. **資料集與評估基準**  
   論文使用 JaxBench 作為綜合測試套件，並從最先進開源模型中選取真實世界工作負載。若 JaxBench 與這些 OSS 模型均公開，則資料層面的可重現性較高。

3. **硬體與軟體依賴**  
   實驗需要 TPU 硬體、JAX/Pallas 環境、XProf 剖析工具與特定世代 TPU 的數值容忍度設定。這些資源並非所有研究機構都能輕易取得，可能限制完全重現。

4. **模型權重與 API 依賴**  
   論文未提及訓練新的模型權重；MaxKernel 應是呼叫現有 LLM API（如 Gemini、GPT 等）。因此可重現性取決於：  
   - 使用的 LLM 版本與 API 存取權。  
   - 提示工程（prompt engineering）與 RAG 語料庫是否完整釋出。  
   - 搜尋預算、溫度參數、束寬等超參數是否透明。  
   若倉庫僅釋出高階框架而未釋出完整提示與知識儲存內容，則難以完全複製論文結果。

5. **整體評估**  
   在「程式碼開源 + 公開基準」的前提下，MaxKernel 具備良好的可重現性基礎；但由於涉及專屬硬體、API 型 LLM 與可能未完全公開的 RAG 語料，**達到論文宣稱的 1.58×／2.32× 加速可能需要相當的資源與環境配置，且對 LLM 版本變化敏感**。

#### 未來研究方向

1. **跨加速器泛化**  
   將 MaxKernel 的智能體原則擴展至 CUDA/Triton（GPU）、NKI（AWS Trainium）、MTIA 等平台，並驗證其跨硬體遷移能力。這需要為各平台建立專屬知識儲存與剖析工具介接。

2. **降低搜尋與剖析成本**  
   結合學習式成本模型（learned cost models）或強化學習（Reinforcement Learning, RL），減少對真實硬體反覆剖析的依賴；同時發展早期終止（early stopping）與預算感知搜尋策略，降低 LLM 呼叫次數。

3. **多目標最佳化**  
   目前主要聚焦執行時間，未來可同時考量記憶體用量、功耗、編譯時間與數值穩定性，形成多目標帕雷托前沿（Pareto frontier）搜尋。

4. **形式化驗證與安全強化**  
   自主生成核心時，如何保證無記憶體越界、無數值溢出、無競爭條件？引入形式化驗證（formal verification）或符號執行（symbolic execution）可提升 Autonomous 模式的安全性。

5. **知識儲存的持續學習**  
   讓 RAG 知識儲存隨著生成歷程持續更新，形成「核心資料庫」，使後續類似任務能利用過往成功／失敗經驗，實現測試時擴展（test time scaling）與終身學習。

6. **更豐富的搜尋演算法整合**  
   在 Graph-Based Autonomous Search 中引入貝葉斯最佳化（Bayesian optimization）、蒙地卡羅樹搜尋（Monte Carlo Tree Search, MCTS）或神經架構搜尋（Neural Architecture Search, NAS）風格的探索策略，以處理更高維度的設計空間。

7. **人機協作介面強化**  
   針對 HITL 模式，開發更直覺的可視化介面，讓開發者能理解 LLM 的規劃意圖、追蹤瓶頸與設計空間分支，進而提升協作效率與信任度。

8. **自動化排程語言的抽象**  
   除了直接生成 Pallas 程式碼，未來可讓智能體輸出高階排程描述（類似 Halide 的 schedule），再由編譯器自動映射至不同硬體，進一步提升可移植性與可解釋性。

## 論文問答

**Q1：MaxKernel 主要想解決什麼問題？**
A：MaxKernel 旨在解決為加速器（如 TPU）設計高效能自訂核心時所面臨的高度複雜性與專業門檻。開發者必須手動管理記憶體階層（例如 HBM 與 SRAM/VMEM）、協調 DMA 管線化，並推導多維度分塊策略，這些都需要深厚的硬體層級專業知識。隨著深度學習架構持續擴展，對專用加速器的需求不斷增加，如何自動化且加速這類核心工程已成為重要挑戰。

**Q2：為什麼現有的零樣本／少樣本 LLM 方法與傳統編譯器最佳化技術不足以解決這個問題？**
A：標準的零樣本或少樣本 LLM 方法難以應對加速器 API 的嚴格性、嚴苛的記憶體限制，以及不透明且低階的編譯器錯誤訊息。即使 LLM 產生了功能正確的程式碼，要達到最佳硬體效能通常仍需反覆的實證剖析、組態調校與追蹤分析。傳統編譯器最佳化技術如 Halide、TVM 與 Ansor 雖然將演算法定義與排程解耦，但仍需要大量領域知識或昂貴的演化式搜尋階段。

**Q3：這個問題為什麼重要？**
A：自訂核心是充分發揮加速器運算與記憶體頻寬的關鍵，直接影響深度學習模型的訓練與推論效率。然而，手動撰寫這些核心不僅耗時，還嚴重依賴少數具備硬體專長的工程師，成為系統效能提升的瓶頸。因此，發展能自動生成並最佳化硬體核心的智能體式方法，對於加速 AI 基礎設施發展具有重大意義。

**Q4：MaxKernel 的核心方法是什麼？**
A：MaxKernel 是一個多智能體系統，透過一組專門化子智能體分別負責規劃、實作、測試、自我除錯、自動調參與硬體剖析。它結合大型語言模型與即時編譯器回饋，並利用 XProf 等效能分析工具形成閉迴路反饋。系統透過三種編排範式——人在迴路、自主迴路與基於圖形的自主搜尋——反覆生成、驗證與最佳化 TPU 上的 Pallas 核心。

**Q5：MaxKernel 的關鍵創新有哪些？**
A：MaxKernel 的關鍵創新在於其模組化的多智能體架構，能將核心生成拆解為可獨立處理的專門任務，提升系統可靠性與彈性。另一項創新是提供三種不同的編排範式，讓開發者能在手動架構控制、快速自動迭代與廣泛設計空間探索之間動態權衡。此外，基於圖形的自主搜尋將核心設計空間建模為正式搜尋圖，可進行全域探索並避免落入區域最佳解。

**Q6：MaxKernel 在設計上做了哪些重要選擇？**
A：MaxKernel 選擇將核心生成流程拆解為多個專門化子智能體，例如規劃智能體、實作智能體、測試驗證智能體、自動調參智能體與剖析智能體，以降低單一智能體的負擔並提升可維護性。為了避免將大量硬體規格文件全部載入上下文視窗，系統採用檢索增強生成（RAG）管線，從外部知識庫動態檢索相關資訊。同時，三種運作模式的設計讓使用者能依任務複雜度與安全需求選擇最適合的協作或自動化程度。

**Q7：MaxKernel 使用了哪些評測基準？**
A：MaxKernel 在 JaxBench 上進行評估，這是一個包含 50 個多樣化 TPU 核心任務的綜合測試套件。此外，論文也評估了來自最先進開源模型的真實世界工作負載，特別是那些有現成人類撰寫核心的生產級核心。評估同時檢驗功能正確性與執行時間，主要聚焦於透過 JAX/Pallas 進行 TPU 開發。

**Q8：MaxKernel 取得了哪些關鍵實驗結果？**
A：在 JaxBench 工作負載上，MaxKernel 達到了 1.58 倍的幾何平均加速。在八個擁有人工撰寫基準的生產級核心上，MaxKernel 相較於參考程式碼達到 2.32 倍的幾何平均加速，甚至優於人類撰寫核心的 2.02 倍加速。這些結果顯示 MaxKernel 能夠持續生成高度最佳化的實作，並達到或超越專家手工調校的基準。

A：根據提供的摘要與前段內文，論文並未明確詳細描述傳統意義上的消融研究。不過，透過與參考程式碼及人類撰寫核心的比較，已能間接驗證智能體式方法與閉迴路硬體回饋的有效性。更完整的消融分析，例如個別子智能體或搜尋策略的貢獻，可能會在論文後續章節中呈現，但不在目前提供的片段範圍內。

**Q10：MaxKernel 有哪些實際應用場景？**
A：MaxKernel 可協助加速器工程師快速原型化並最佳化新的深度學習運算子核心，縮短開發週期。對於架構一致性與安全性要求較高的複雜核心，可使用人在迴路模式進行協作設計；而對於較常見的核心任務，則可採用自主迴路或圖形搜尋模式進行大規模自動最佳化。由於其底層智能體原則具有通用性，未來也可擴展至 GPU、AWS Trainium 或 MTIA 等其他加速器平台。

**Q11：在產品化過程中需要考慮哪些因素？**
A：產品化時應根據任務複雜度與風險選擇適當的編排範式，例如關鍵核心可保留人在迴路以確保安全與架構對齊。系統必須與現有編譯器管線和剖析工具緊密整合，才能為 LLM 提供即時且可操作的回饋。此外，由於自動化搜尋可能耗費大量運算資源，也需要在搜尋廣度、執行成本與效能提升之間取得平衡。

**Q12：MaxKernel 對相關領域可能帶來什麼影響？**
A：MaxKernel 有望降低高效能核心開發的專業門檻，使更多開發者能為加速器撰寫最佳化核心。它彌補了靜態 LLM 程式碼生成與反覆硬體感知最佳化之間的落差，可能加速深度學習系統的創新與部署。由於該框架已開源，研究與工程社群可以在此基礎上進一步擴展，推動加速器程式設計自動化的整體發展。

**Q13：論文中有哪些已承認的限制？**
A：根據目前提供的內文，論文並未明確列出系統限制，但從其評估焦點可推知，MaxKernel 主要針對 TPU 與 JAX/Pallas 進行最佳化，直接移植到其他加速器生態系可能需要調整。此外，系統效能高度依賴 LLM 生成程式碼的品質，以及編譯器回饋與剖析工具是否能提供足夠清晰的訊號。對於極度複雜或前所未見的核心結構，可能仍需要透過人在迴路模式引入人工判斷。

**Q14：MaxKernel 可能面臨哪些失敗案例？**
A：當核心涉及極其複雜或新穎的記憶體存取模式時，LLM 可能無法在多次迭代後仍生成正確或高效的實作。若編譯器錯誤訊息過於模糊，或 XProf 等剖析工具未能清楚指出瓶頸，自我除錯與最佳化迴路可能難以收斂。此外，在廣大的設計空間中進行圖形搜尋時，也可能因為搜尋成本過高或評估雜訊而收斂到次佳解。

**Q15：未來有哪些可能的研究方向？**
A：未來研究可將 MaxKernel 擴展至更多加速器平台，例如 NVIDIA GPU、AWS Trainium 與 Meta MTIA，驗證其跨硬體的通用性。另一個方向是提升基於圖形的自主搜尋效率與穩健性，例如結合更強大的推論模型或學習式搜尋策略。此外，進一步強化知識庫的檢索能力、開發更嚴謹的自動化安全檢查機制，也有助於減少對人類監督的依賴。

## 實務應用指南

## 適用場景

1. **大型語言模型推論與訓練的客製化融合核心**  
   在 TPU 上執行 Transformer 的 attention、FFN、MoE 路由或自訂歸一化層時，若 XLA 編譯器產生的排程無法充分重疊 DMA 管線化與 VMEM 重用，可使用 MaxKernel 的 Autonomous Loop 或 Graph-Based Autonomous Search 產生 Pallas 融合核心，降低記憶體搬移並提升運算密度。

2. **新穎模型架構的運算子落地**  
   當研究團隊提出標準 JAX/XLA 未支援的運算（例如稀疏注意力、自訂量化、非標準矩陣乘法變體），可透過 HITL 模式讓硬體工程師與智能體協作，逐步確認多維度分塊策略與數值正確性，再進入自動調校。

3. **推薦系統與大規模嵌入表的記憶體密集核心**  
   推薦模型常受 HBM 頻寬與嵌入查詢延遲限制。MaxKernel 可針對 gather、reduce-scatter、unique 等記憶體密集運算，自動探索 tile 大小與資料布局，產生貼合 TPU 記憶體階層的核心。

4. **跨 TPU 世代的生產核心遷移與維護**  
   當硬體從 TPU v4 升級至 v5e/v5p 時，既有手工 Pallas 核心可能因 VMEM 容量、矩陣單元規格改變而失效。MaxKernel 可將參考實作與新硬體規格納入 RAG 知識庫，自動重寫並重新調校核心。

5. **MLOps 平台的核心微基準與效能資料庫建置**  
   平台團隊可針對常見張量程式（如 softmax、layer norm、flash attention 變體）批次執行 Graph-Based Autonomous Search，建立每代 TPU 的最佳核心組態資料庫，供上層模型訓練管線直接呼叫。

## 實作前置條件

- **運算資源**：可存取的 TPU 叢集（v4/v5e/v5p），且能執行 JAX/Pallas 程式；建議至少具備單一 TPU slice 以進行功能驗證，並保留額外 slice 供剖析與自動調校平行執行。
- **軟體環境**：已安裝相容版本的 JAX、jaxlib、Pallas、libtpu，以及 XProf 或等效效能追蹤工具；Python 版本建議使用專案支援的穩定發行版。
- **LLM 後端**：可呼叫的 LLM API（如 Gemini、GPT-4、Claude）或自行託管的開源模型，並設定好速率限制與成本預算。
- **知識庫資料**：整理 Pallas 官方文件、TPU 硬體規格（VMEM 大小、矩陣單元維度、DMA 行為）、內部最佳實踐、參考核心實作與常見編譯錯誤對照表，供 RAG 檢索。
- **測試與基準**：每個核心任務需有參考實作、輸入形狀分佈、數值容忍度（atol/rtol）與效能基準；建議包含單元測試、壓力測試與真實模型片段的整合測試。
- **團隊技能**：至少一名熟悉 JAX/Pallas 與 TPU 記憶體階層的硬體工程師負責 HITL 審查；一名具備 LLM 智能體開發經驗的 AI 工程師負責編排與 RAG；一名 MLOps 工程師負責 CI/CD 與執行環境隔離。

## 實作步驟建議

1. **建立基線與目標**  
   在現有參考實作上執行 XProf，記錄執行時間、記憶體頻寬利用率、矩陣單元利用率與瓶頸運算子，明確要最佳化的核心與效能目標。

2. **選擇運作範式**  
   複雜且安全敏感的首次開發選 **HITL**；已有明確規格、需要快速迭代的核心選 **Autonomous Loop**；需要大範圍探索 tile、layout、融合策略時選 **Graph-Based Autonomous Search**。

3. **建置 RAG 知識庫**  
   將 Pallas API 文件、TPU 硬體規格、內部範例核心、常見編譯器錯誤訊息與對應解法向量化，並依核心任務動態檢索相關片段注入智能體上下文。

4. **定義核心規格與測試套件**  
   撰寫輸入/輸出規格、數學語意、數值容忍度、支援的 TPU 世代，以及涵蓋典型與邊界形狀的測試案例。

5. **執行規劃智能體**  
   讓 Planning Agent 根據硬體規格與參考實作產生演算法最佳化計畫（包含分塊策略、DMA 管線化、VMEM 配置）；HITL 模式下由工程師審查並修正。

6. **產生、編譯與自我除錯**  
   Implementation Agent 產生 Pallas 程式後，立即編譯並將編譯器回饋傳給 Fix Agent 迭代修正語法與結構錯誤，直到可執行。

7. **功能驗證**  
   使用 Test Synthesis Agent 產生的測試套件，比對生成核心與參考實作的輸出，確保在指定數值容忍度內功能正確。

8. **自動調校組態**  
   Autotuning Agent 在安全的執行環境中搜尋 block size、tile dimension、unroll factor 等超參數，記錄每組組態的執行時間與資源利用率。

9. **追蹤驅動最佳化**  
   Profiling Agent 使用 XProf 擷取執行追蹤，分析記憶體頻寬、計算密度與管線氣泡，將瓶頸回饋給 Planning Agent 進行下一輪演算法層級改進。

10. **圖形搜尋全域探索（可選）**  
    若 Autonomous Loop 陷入區域最佳，啟動 Graph-Based Autonomous Search，將不同設計決策建模為搜尋節點，以 beam search 或平行搜尋探索更廣的設計空間。

11. **回歸測試與版本控制**  
    將通過驗證的核心、組態與測試結果納入版本控制，建立跨 TPU 世代的回歸測試，防止未來 API 變更導致效能衰退。

12. **部署與監控**  
    將最佳核心以 JAX custom call 或 Pallas 核心形式整合進模型訓練/推論管線，並在生產環境持續監控執行時間與數值穩定性。

## 潛在風險與注意事項

- **不透明編譯器錯誤**：TPU 低階編譯器錯誤訊息可能難以解讀。建議在 RAG 知識庫中累積錯誤訊息與對應修復範例，並讓 Fix Agent 多次迭代；若持續失敗，切換至 HITL 由人工介入。
- **嚴格記憶體限制**：VMEM 超用或配置錯誤會導致執行失敗。應在規劃階段即估算 tile 大小與暫存記憶體用量，並在測試階段加入記憶體壓力案例。
- **數值發散**：自動生成的核心可能在特定形狀或資料分佈下與參考實作數值不一致。必須設定動態數值容忍度，並進行多種隨機種子與邊界形狀測試。
- **API 與硬體上下文頻繁變更**：JAX/Pallas 與 libtpu 版本更新可能使原本正確的核心失效。建議鎖定版本、建立 CI 回歸測試，並定期以 MaxKernel 重新生成核心。
- **LLM 幻覺與不安全程式碼**：智能體可能產生無效或具破壞性的程式碼。執行環境必須沙箱化，限制網路與檔案系統存取，並禁止直接執行未經測試的程式碼。
- **成本與時間爆炸**：Graph-Based Autonomous Search 與大量 LLM 呼叫可能快速消耗預算。應設定搜尋深度、並行度與總呼叫次數上限，並優先針對高影響力核心啟動大規模搜尋。
- **過度擬合特定硬體**：針對某代 TPU 調校的核心可能在其他世代表現不佳。建議將硬體規格明確納入 RAG，並為每代 TPU 維護獨立的組態資料庫。

## 與其他技術的整合建議

- **JAX/XLA 管線**：將 MaxKernel 生成的 Pallas 核心封裝為 JAX custom call 或 `jax.jit` 內的 `pallas_call`，使其無縫銜接現有模型程式碼，無需改寫上層訓練邏輯。
- **MLOps CI/CD**：在每次提交或 nightly build 中執行核心生成、編譯、功能驗證與效能回歸測試，並將結果寫入效能資料庫，作為模型選型依據。
- **效能剖析與監控**：與 XProf、TensorBoard 及內部監控系統整合，自動擷取執行追蹤並視覺化瓶頸，讓 Profiling Agent 能持續接收真實生產數據。
- **現有自動調校工具**：可將 Autotuning Agent 與 Vizier、Optuna 或內部貝葉斯最佳化服務結合，利用其成熟的搜尋演算法補強 MaxKernel 的組態探索。
- **模型服務框架**：對於 MaxText、JetStream 等推論框架，可將優化後的核心打包為可重複使用的 kernel library，供不同模型共享。
- **內部知識管理**：將 RAG 知識庫與企業 wiki、技術文件系統連動，隨著文件更新自動重新索引，確保智能體始終使用最新 API 與硬體資訊。

- **產品經理**：應關注適用場景、投資報酬率與風險控管；優先選擇效能瓶頸明確、影響面大的核心任務導入 MaxKernel，並以 HITL 模式確保安全性與架構一致性，同時為 LLM 呼叫與大規模搜尋設定明確預算與上線驗收標準。
