# 無資源、無基準測試、沒問題？評估與改進用於無資源語言程式碼生成之大型語言模型（LLMs）

## ⚡ TL;DR

解決無資源程式語言缺乏基準測試與LLM支援的問題。
建立無資源語言基準，並以基礎模型預訓練結合權重差異轉移注入指令遵循能力。
顯著提升無資源語言的程式碼生成效能，降低企業部署專屬指令模型的運算成本。

## 摘要翻譯

大型語言模型（LLMs）顯著推進了軟體工程（software engineering）任務的自動化（automation）。其中一個突出的例子是程式碼生成（code generation），即大型語言模型（LLMs）根據自然語言描述（natural language description），以指定的程式語言產生程式碼。此領域的多數研究聚焦於高資源語言（high-resource languages）（如 Python 或 Java），這些語言擁有豐富的訓練資料（training data）。較少研究探討低資源語言（low-resource languages），其在訓練語料庫（training corpora）中代表性不足。相較之下，無資源語言（no-resource languages）（即訓練語料中幾乎無資料的程式語言）仍鮮少受到探討。這些語言經常出現於產業界，組織在其中開發不受 GitHub Copilot 等商業工具（commercial tools）支援的專有語言（proprietary languages）或領域特定語言（domain-specific languages），因此必須自行部署企業內部（in-house）程式碼推薦系統（code recommenders）。為了在此情境下探究可能的解決方案，我們針對兩種近期提出且訓練資料（training data）極少的程式語言，建構並發布了三個無資源語言之程式碼生成基準測試（benchmarks）。利用這些基準測試（benchmarks），我們實驗並探討多種使大型語言模型（LLMs）學習無資源語言的解決方案，包括基於提示的技術（prompt-based techniques），以及利用少量現有資料進行的預訓練（pre-training）與微調（fine-tuning）。雖然進一步預訓練（further pre-training）為無資源語言帶來最大的效能提升（performance gains），但將其直接應用於指令微調模型（instruction-tuned models）會損害其指令遵循能力（instruction-following capabilities）。為了解決此問題，我們從基礎模型（base model）出發，針對目標語言對其進行進一步預訓練，然後透過權重差異轉移（weight diff transfer），從指令模型（instruct model）注入指令遵循能力（instruction-following capabilities）。這種方法顯著提升了無資源情境下的程式碼生成能力，使企業能夠以低成本部署專門化的指令模型（instruct model），而無需承擔指令微調的運算成本（computational cost）。

### 核心貢獻（3～5點）
- 針對兩種訓練資料極少的新程式語言，建構並公開三個無資源語言的程式碼生成基準測試，填補該領域缺乏評估工具的空白。
- 系統性比較多種技術路線（包括基於提示的技術、預訓練與微調），探討如何以有限資料教會大型語言模型理解無資源語言。
- 揭示將進一步預訓練直接應用於指令微調模型時，會損害其指令遵循能力的衝突現象。
- 提出以基礎模型進行進一步預訓練後，透過權重差異轉移注入指令遵循能力的解決方案，使企業得以低成本部署專門化的指令模型。

### 適合對象
從事大型語言模型與程式碼生成研究的學者及工程師、在企業內部維護專有語言或領域特定語言之軟體工程團隊，以及關注低資源或無資源情境下模型適配與高效微調技術的研究者。

## 深度分析

#### 方法論解析
本研究的方法論圍繞「無資源語言（no-resource languages）」的程式碼生成（code generation）評估與模型適應，可拆解為基準測試（benchmarks）建構、效能落差量化，以及解耦式模型適應三大支柱。

首先，在基準測試建構層面，由於無資源語言多為企業內部（in-house）的專有語言（proprietary languages）或領域特定語言（domain-specific languages），幾乎不存在公開的程式設計任務（coding tasks）與測試套件（test suite）。作者選定 Gleam 與 MoonBit 作為無資源語言的代表性案例，兩者皆為近期發布的通用程式語言（general-purpose languages），在程式碼倉儲平台（repository platforms）如 GitHub 上的能見度極低（分別僅約 280 與 35 個擁有 ≥10 stars 的倉儲），遠低於過去研究中被視為低資源語言（low-resource languages）的 R 或 Lua，因此極不可能出現於現有大型語言模型（LLMs）的訓練語料庫（training corpora）中。作者將 HumanEval、MBPP 與 McEval-Hard 三個主流基準測試翻譯為這兩種語言，從而建立了目前極少數針對無資源語言的公開評估工具，解決了「無基準可測」的困境。

其次，在研究設計上，RQ₁ 透過零樣本（zero-shot）設定橫向比較高資源語言（high-resource languages，如 Python、Java）、低資源語言（如 Julia、Lua、R、Racket、Haskell）與無資源語言的表現，旨在確立無資源情境的合理效能上界，並驗證現代 LLMs 是否真如預期般完全無法處理訓練資料（training data）極度稀缺的語言。RQ₂ 則系統性地檢驗多種技術路徑，包括基於提示的技術（prompt-based techniques）如少樣本提示（few-shot）與檢索增強生成（Retrieval-Augmented Generation, RAG），以及利用少量可得資料進行的進一步預訓練（further pre-training）與微調（fine-tuning）。

最具方法論創新之處在於作者對「指令遵循能力（instruction-following capabilities）」與「語言專業化」之間衝突的處理。實驗發現，直接對指令微調模型（instruction-tuned models）進行進一步預訓練雖能帶來最大的效能提升（performance gains），卻會嚴重損害其遵循自然語言描述（natural language description）的能力。為此，作者提出三階段管道：（1）以基礎模型（base model）為起點；（2）針對目標無資源語言執行進一步預訓練，使模型習得該語言的語法特徵（syntactic characteristics）與語意特徵（semantic characteristics）；（3）透過權重差異轉移（weight diff transfer），將指令模型（instruct model）相對於基礎模型的權重差異注入已適應目標語言的模型中。此設計的實質是將「語言知識學習」與「指令對齊」解耦，使企業無需從頭承擔高昂運算成本（computational cost）的指令微調，即可部署具備指令遵循能力的專精模型。

#### 實驗數據解讀
實驗結果清晰地揭示了預訓練分佈（pre-training distribution）內外的巨大鴻溝。在最具挑戰性的 McEval-Hard 基準測試（benchmark）上，GPT-4o、o3-mini、Qwen 2.5 Coder 32B Instruct 與 Qwen 3 32B Instruct 四個模型在零樣本（zero-shot）設定下呈現斷崖式落差：

高資源語言（high-resource languages）的 pass@1 分數落在約 59% 至 89% 區間，顯示現代 LLMs 對主流語言已具備成熟的自動化（automation）實作能力。低資源語言（low-resource languages）的表現則下滑至 27% 至 84%，雖有明顯衰退，但部分模型仍能維持可接受的泛化水準，這與過去研究認為 LLMs 可透過語法相似性泛化至低資源語言的結論一致。然而，無資源語言（no-resource languages）的 pass@1 竟低至 0% 至 1%，幾近完全失效。這不僅驗證了商業工具（commercial tools）如 GitHub Copilot 或 ChatGPT 無法支援此類語言的現實，也確立無資源情境是一個獨立且更嚴峻的研究挑戰——其效能上界可參考低資源語言的中高段表現（約 50% 以上），但起點幾乎為零。

在 RQ₂ 的適應性技術評估中，少樣本提示（few-shot）與檢索增強生成（RAG）等基於提示的技術受限於模型對目標語言的先驗知識幾近於無，其邊際效益相對有限。相較之下，進一步預訓練（further pre-training）利用少量可蒐集的訓練資料（training data），能帶來最顯著的效能提升。然而，實驗也證實，若直接對指令微調模型（instruction-tuned models）執行此操作，會導致模型遺忘指令遵循能力，產生「會寫語法但聽不懂指令」的現象。

作者提出的權重差異轉移（weight diff transfer）方法則有效緩解了上述兩難。該方法在保留進一步預訓練所獲得的語言專業化知識之餘，成功恢復了模型的指令遵循能力，使企業能夠以較低運算成本部署專精於無資源語言的企業內部（in-house）程式碼推薦系統（code recommenders）。雖然具體的絕對數值未在摘要中詳列，但從「顯著改善（significantly improves）」的論述可推斷，該方法成功將無資源語言的生成能力從「幾乎不可用」推升至「具實用價值」的門檻。

#### 與現有研究的比較
本研究在程式碼生成（code generation）領域中填補了一個長期被忽視的空白。既有研究絕大多數聚焦於高資源語言（high-resource languages），如 Python 與 Java，這些語言在訓練語料庫（training corpora）中佔據主導地位，因此模型效能優異。近期雖有少數研究開始探討低資源語言（low-resource languages）如 Lua、R 與 Racket，並發現大型語言模型（LLMs）仍能透過泛化維持合理表現，但本研究明確指出：一旦語言完全脫離預訓練分佈（pre-training distribution）——即成為無資源語言（no-resource languages）——這種泛化將徹底崩潰，pass@1 趨近於零。這意味著低資源與無資源之間存在非線性的「斷崖式」落差，而非僅是資料量遞減的線性關係。

在技術方法上，過往研究通常將預訓練（pre-training）與指令微調（instruction tuning）視為連續或獨立的階段，較少深入探討「在指令微調模型上繼續進行領域預訓練會破壞指令遵循能力」的問題。本研究的權重差異轉移（weight diff transfer）策略，本質上是一種模型能力解耦與重組的技術，與模型合併（model merging）或任務算術（task arithmetic）等領域有概念上的親緣關係，但將其應用於「無資源語言適應 + 指令遵循保留」的特定場景，具有明確的實務價值。對於需要部署企業內部（in-house）AI 輔助程式設計（AI-assisted programming）工具的組織而言，此方法避免了從頭進行昂貴指令微調的需求，提供了一條經濟上可持續的路徑。

然而，本研究亦存在若干侷限。首先，選用的 Gleam 與 MoonBit 雖為無資源語言，但本質上仍屬通用程式語言（general-purpose languages），其語法特徵（syntactic characteristics）與語意特徵（semantic characteristics）與主流語言仍有共通之處。對於結構差異極大的專有語言（proprietary languages）或高度專化的領域特定語言（domain-specific languages），此方法是否依然有效，仍需驗證。其次，基準測試（benchmarks）係透過翻譯現有 Python 導向的資料集而來，可能無法完全捕捉目標語言的慣用語法或真實工業場景的複雜度。最後，實驗模型以 Qwen 系列開源模型與少數商業模型為主，尚未涵蓋更多元的模型架構與規模。

#### 可重現性評估
本研究在可重現性（reproducibility）方面採取了積極的開放科學策略。作者明確聲明建構並釋出了三個針對無資源語言的程式碼生成基準測試（benchmarks），涵蓋 Gleam 與 MoonBit。若這些資料集與對應的測試套件（test suite）確實公開釋出，將為後續研究提供寶貴的標準化評估工具，解決過往因無資源語言多為專有語言（proprietary languages）而難以取得公開基準的困境。

在模型與方法層面，研究主要採用 Qwen 2.5 Coder 32B Instruct 與 Qwen 3 32B Instruct 等開源權重模型進行適應性實驗。權重差異轉移（weight diff transfer）技術僅需取得基礎模型（base model）與指令模型（instruct model）的公開權重即可執行，無需依賴閉源系統，這大幅降低了學術界與產業界復現該方法的門檻。此外，作者強調此管道無需承擔完整指令微調的運算成本（computational cost），對於運算資源有限的企業或研究團隊而言，這不僅是經濟上的優勢，也是實務重現的關鍵誘因。

不過，可重現性仍存在一些潛在挑戰。首先，基線評估中使用的商業工具（commercial tools）如 GPT-4o 與 o3-mini 屬於閉源 API，其模型版本可能隨時間更新（API drift），導致未來研究者難以完全復現相同的零樣本（zero-shot）基線數據。其次，儘管進一步預訓練（further pre-training）的成本低於從頭訓練，但仍需相當規模的 GPU 資源與資料清洗流程，論文中未詳述這些實作細節（如訓練步數、學習率、資料來源與去重策略），若未在釋出的程式碼中完整提供，可能影響精確復現。最後，由於無資源語言的訓練資料（training data）極度稀少，資料的蒐集與前處理過程本身帶有高度的不確定性，不同團隊復現時可能因資料品質差異而導致效能浮動。

#### 未來研究方向
基於本研究的發現與侷限，未來研究可從以下數個方向深入拓展：

第一，擴展至真正的領域特定語言（domain-specific languages, DSLs）與企業專有語言（proprietary languages）。Gleam 與 MoonBit 作為通用程式語言（general-purpose languages），其語法結構仍與主流語言有一定相似性。未來應挑戰語法特徵（syntactic characteristics）與語意特徵（semantic characteristics）更為獨特的語言，驗證方法在極端分佈外（out-of-distribution）情境下的穩健性。

第二，發展原生而非翻譯的基準測試（benchmarks）。現有資料集由 HumanEval、MBPP 等翻譯而來，可能帶有原始語言（多為 Python）的慣用偏見。未來應邀請領域專家設計符合目標語言慣用語法與生態系的原生程式設計任務（coding tasks），以更真實地評估模型在實務場景的表現。

第三，結合參數高效微調（Parameter-Efficient Fine-Tuning, PEFT）技術。本研究的權重差異轉移（weight diff transfer）雖已降低運算成本，但進一步預訓練（further pre-training）仍涉及全模型更新。未來可探索將 LoRA、Adapter 或 Prefix Tuning 等技術應用於無資源語言的適應，以實現更低成本的企業內部（in-house）部署。

第四，探究跨語言遷移學習（cross-lingual transfer）的極限。本研究暗示模型對無資源語言幾無先驗知識，但未系統性探討是否能透過與語法相似的高資源語言（high-resource languages）進行聯合訓練或對比學習，來加速無資源語言的掌握。

第五，自動化訓練資料生成。針對訓練資料（training data）極度稀缺的痛點，未來可研究如何利用大型語言模型（LLMs）自動生成高品質的合成程式碼與對應的自然語言描述（natural language description），以人工方式從零建立「偽資源」，並研究需要多少合成資料才能跨越無資源與低資源（low-resource）的門檻。

第六，探索指令遵循能力的替代注入機制。權重差異轉移並非唯一解，未來可比較直接偏好優化（Direct Preference Optimization, DPO）、正則化微調或其他模型合併策略，在保留語言專業化的同時恢復指令遵循能力，並評估其對程式碼推薦系統（code recommenders）長期維護性的影響。

## 論文問答

**Q1：這篇論文核心要解決的問題是什麼？**
A：這篇論文聚焦於大型語言模型在「無資源程式語言」上進行程式碼生成的困境，這類語言指的是在模型預訓練階段幾乎未曾接觸過的程式語言。與擁有豐富訓練資料的高資源語言（如 Python、Java）或資料相對稀少的低資源語言不同，無資源語言在公開程式碼倉儲中極度罕見，導致現有模型幾乎無法生成正確的程式碼。這個問題在產業界尤其嚴重，因為許多企業使用專有或領域特定語言，卻無法獲得商業工具（如 GitHub Copilot）的支援。

**Q2：為何現有的 LLM 程式碼生成方法在無資源語言上會失效？**
A：現有的商業工具主要針對高資源語言進行訓練，其預訓練分佈並未涵蓋無資源語言，因此模型缺乏理解這些語言語法與語意特徵的基本能力。雖然少樣本提示或檢索增強生成等上下文學習技術在某些情境下有所幫助，但當模型對目標語言完全陌生時，這些方法只能帶來極為有限的效能提升。此外，研究發現直接對指令微調模型進行進一步預訓練雖然能增強語言知識，卻會嚴重損害其遵循自然語言指令的能力，使得現有適配策略面臨兩難。

**Q3：研究無資源語言的重要性為何？**
A：許多企業為了滿足特定業務需求而開發專有語言，但由於缺乏商業 AI 輔助程式設計工具的支援，這些組織難以享受自動化帶來的生產力提升。從頭打造企業內部的程式碼推薦系統不僅成本高昂，完整的指令微調更需要龐大的運算資源，對許多公司而言並不經濟實惠。因此，探索低成本且有效的無資源語言適配方法，不僅能填補學術研究空白，更能直接回應產業界對於客製化 AI 解決方案的迫切需求。

**Q4：本文提出的核心方法論是什麼？**
A：作者提出一個多階段的模型適配流程：首先以基礎模型為起點，利用目標無資源語言的少量資料進行進一步預訓練，再透過權重差異轉移將指令微調模型的指令遵循能力注入該模型。這個流程與單純的基於提示的技術（如少樣本提示、檢索增強生成）以及直接微調策略進行了全面比較。透過將「語言知識學習」與「指令遵循能力」解耦，此方法旨在避免傳統方法中改善語言理解卻犧牲指令遵循的問題，並顯著降低運算成本。

**Q5：這項研究的關鍵技術創新是什麼？**
A：關鍵創新在於「權重差異轉移」機制，它能將指令微調模型所具備的指令遵循能力，有效地注入到已針對無資源語言進行過進一步預訓練的基礎模型中。這項技術巧妙地規避了直接對指令微調模型進行進一步預訓練時，會導致其遺忘如何理解自然語言指令的副作用。透過結合基礎模型在進一步預訓練中獲得的目標語言知識，以及從指令模型轉移而來的權重差異，研究團隊成功建構出既懂無資源語言又能遵循指令的專門化模型。

**Q6：作者為何選擇 Gleam 與 MoonBit 作為無資源語言的代表？**
A：Gleam 與 MoonBit 是近期才發表的通用程式語言，在 GitHub 等公開平台上的倉儲數量極為稀少（分別僅有約 280 與 35 個高星標倉儲），完全符合無資源語言的定義。它們在語法與語意特徵上與主流語言有相似之處，但卻幾乎不存在於現有大型語言模型的預訓練語料庫中，因此能真實反映模型在零樣本或極少資料情境下的適配難度。此外，選用公開的新語言而非企業內部專有語言，使作者能夠建構並釋出可重現的基準測試，供學術界進行後續研究。

**Q7：作者建構了哪些基準測試，以及如何建構？**
A：研究團隊將三個現有的標準程式碼生成基準測試——HumanEval、MBPP 以及 McEval 中的困難子集——翻譯成 Gleam 與 MoonBit 語言版本。每個基準測試包含一系列程式設計任務，每個任務都提供自然語言描述與用於驗證生成程式碼正確性的測試套件。這些是學術界首次公開釋出的無資源語言程式碼生成基準測試，填補了過往因這類語言多為專有而無法取得評估資料的缺口。

**Q8：實驗中最顯著的結果是什麼？**
A：在 McEval-Hard 基準測試上，最先進的大型語言模型對高資源語言的 pass@1 分數落在 59% 至 89% 之間，對低資源語言為 27% 至 84%，但對無資源語言僅有 0% 至 1%，顯示出巨大的效能落差。在各種適配技術中，進一步預訓練為無資源語言帶來了最顯著的效能提升，證明讓模型接觸目標語言分佈是不可或缺的。最關鍵的是，結合權重差異轉移的方法在大幅提升 Gleam 與 MoonBit 程式碼生成正確率的同時，成功恢復並維持了模型的指令遵循能力。

**Q9：比較不同適配技術的實驗提供了哪些深入見解？**
A：實驗結果顯示，少樣本提示與檢索增強生成等上下文學習方法對無資源語言的幫助相當有限，遠不及基於預訓練的方法。直接對指令微調模型進行進一步預訓練雖然能增強對目標語言的理解，卻會顯著破壞其遵循自然語言指令的能力，揭示了這種直接應用方式的嚴重副作用。這些比較證實了從基礎模型開始進行進一步預訓練，再輔以權重差異轉移的組合，才是兼顧語言能力與指令遵循的最佳配置。

**Q10：這項研究可以應用在哪些實務情境？**
A：這項研究可直接應用於使用專有或領域特定語言、卻無法獲得 GitHub Copilot 等主流商業工具支援的企業。組織可以利用本文提出的流程，針對自家語言建構客製化的企業內部程式碼推薦系統，而無需承擔從頭進行完整指令微調的龐大運算成本。對於希望在特殊技術生態系中提升開發者生產力、同時控制 AI 導入預算的公司而言，此方法提供了具體且可行的解決方案。

**Q11：在生產環境中部署此方法需要考慮哪些關鍵因素？**
A：首要考量是目標語言必須具備少量可取得的訓練資料，因為進一步預訓練階段仍需一定語料來讓基礎模型適應目標語言的分佈。企業也必須評估進一步預訓練所需的運算資源，雖然這遠低於完整指令微調的成本，但仍需相應的硬體支援。此外，組織應確認所選的指令微調模型與基礎模型在架構上相容，以確保權重差異轉移能順利進行，成功整合指令遵循能力。

**Q12：這項工作對 LLM 軟體工程領域的廣泛影響是什麼？**
A：這項工作將程式碼生成研究的範疇從高資源與低資源語言，擴展到長期被忽視的無資源語言情境，開創了全新的研究前沿。透過釋出首批無資源語言的公開基準測試並展示可行的適配技術，本文為未來研究人員與實務工作者處理專有語言支援問題提供了基礎框架。這項研究挑戰了「大型語言模型僅適用於主流程式語言」的既定印象，為更具包容性與客製化的 AI 輔助程式設計工具鋪平了道路。

**Q13：作者承認了哪些研究限制？**
A：作者坦承實驗僅在兩種近期發表的通用程式語言上進行，這可能無法完全涵蓋產業界各種專有或領域特定語言的多樣性。雖然 Gleam 與 MoonBit 的訓練資料極為稀少，但對於某些高度專門化的企業內部語言而言，可取得的資料量可能更少，這限制了研究結果在極端資料稀缺情境下的泛化性。此外，本研究聚焦於程式碼生成基準測試，並未探討其他軟體工程任務（如程式碼摘要、漏洞修復或測試生成）在無資源語言上的表現。

**Q14：研究中發現了哪些失敗案例或負面結果？**
A：最顯著的負面結果是，直接對指令微調模型進行進一步預訓練會嚴重損害其指令遵循能力，實質上破壞了模型理解自然語言提示的功能。此外，在未經適配的情況下，即使是最先進的大型語言模型在無資源語言上的基線表現也接近零分，顯示現有模型完全無法對訓練分佈外的語言進行泛化。這些失敗案例凸顯了單純的提示工程或現成商業模型，根本不足以支援無資源程式語言的開發需求。

**Q15：這項工作指出了哪些未來研究方向？**
A：未來研究可以將本文提出的適配流程應用於更廣泛的專有與領域特定語言，包括那些語法結構與主流語言差異極大的案例。研究者也可以探索參數高效微調方法（如 LoRA 或 adapter layers）作為完整進一步預訓練的替代方案，以進一步降低運算需求。另一個有潛力的方向是將研究擴展至無資源語言的其他軟體工程任務，例如自動化程式修復、程式碼轉換與文件生成，從而為這些語言建構更全面的人工智慧支援生態系。

## 實務應用指南

### 適用場景

1. **企業內部專有語言（DSL）的 AI 輔助程式設計**  
   金融、電信或硬體製造業常擁有內部領域特定語言（Domain-Specific Languages）或腳本語言。這些語言不具備商業工具（如 GitHub Copilot）支援，可運用本文方法低成本建置企業內部程式碼推薦系統。

2. **新興通用程式語言的開發工具鏈補強**  
   對於剛問世、GitHub 上僅有數百個倉儲的通用程式語言（如 Gleam、MoonBit），開發者生態系尚未成熟。透過進一步預訓練與權重差異轉移，可快速打造專屬的程式碼生成模型，加速語言採用。

3. **遺留系統語言的現代化與維護輔助**  
   組織內部遺留的第四代語言（4GL）或古董級腳本，往往僅有極少量數位化語料。本文框架允許利用有限的歷史程式碼庫，訓練模型協助維護、重構或轉譯至現代語言。

4. **硬體描述語言與科學計算環境的程式碼生成**  
   在 EDA（電子設計自動化）或科學模擬領域，特定硬體描述語言或實驗室內部使用的計算腳本缺乏 LLM 支援。可依此流程建立專用模型，從自然語言規格生成可合成或可執行的程式碼。

5. **教育與研究機構的實驗性語言教學工具**  
   學術界設計的新教學語言或驗證型語言，可利用自建基準測試與輕量級持續預訓練，快速驗證 AI 輔助教學的可行性，無需負擔從頭訓練指令模型的運算成本。

### 實作前置條件

**資料條件**
- 目標無資源語言的原始碼語料，即使規模極小（如數百至數千個檔案或數十個倉儲）亦可起步，但需具備一定語法多樣性。
- 可將現有基準測試（如 HumanEval、MBPP）翻譯為目標語言的專家人力，並建立可執行的測試套件（test suite）以計算 pass@1。
- 目標語言的文件、語法規格或內部 Wiki，作為評估自然語言描述品質與後續 RAG 管線的知識來源。

**運算條件**
- **進一步預訓練（Further Pre-training）**：需具備多卡 GPU 叢集（如 NVIDIA A100 / H100），記憶體需求取決於基礎模型規模（以 32B 參數模型為例，建議至少數十 GB 至百 GB 級 VRAM）。
- **權重差異轉移（Weight Diff Transfer）與推論**：中等規格 GPU（如單卡 A100 或同等級）即可執行；若僅採用提示工程（少樣本提示 / RAG），則可使用商用 API 或單卡消費級 GPU。
- 儲存空間需預留基礎模型、指令微調模型、持續預訓練後模型及差異權重的多份檢查點。

**技能條件**
- 熟悉 LLM 預訓練與微調流程（尤其是 Hugging Face Transformers、DeepSpeed 或類似框架）。
- 目標語言的編譯器 / 直譯器與測試框架知識，能夠自動化執行編譯與單元測試以驗證生成結果。
- MLOps 與資料工程能力，包含語料清洗、去重、格式化，以及模型部署與 API 化經驗。

### 實作步驟建議

**步驟一：建立基準測試與現況評估**  
將 HumanEval、MBPP 或 McEval 等現有基準測試翻譯為目標無資源語言，並確保每道題目皆附有可執行的測試套件。使用現成指令模型（如 GPT-4o、Qwen 2.5 Coder Instruct）進行 zero-shot 評估，建立 pass@1 基線，確認其效能接近 0% 的「無資源」現況。

**步驟二：蒐集與建構目標語言語料庫**  
從企業內部倉儲或公開平台（如 GitHub）爬取目標語言的所有可用程式碼。進行語料清洗（去除重複、低品質檔案、個資與機敏資訊），並格式化為適合預訓練的純文字或程式碼語料。此階段語料量可能僅有數百 MB，但需確保涵蓋常見語法結構。

**步驟三：基礎模型持續預訓練**  
選擇一個程式碼導向的基礎模型（base model，如 Qwen 2.5 Coder Base），**切勿直接使用指令微調模型**。使用步驟二的語料進行進一步預訓練，讓模型學習目標語言的語法與語意分佈。監控訓練損失與語言建模困惑度（perplexity）作為收斂指標。

**步驟四：注入指令遵循能力（Weight Diff Transfer）**  
取得同系列指令微調模型（instruct model）與其對應基礎模型的權重差異（weight diff）。將此差異注入至步驟三所得的持續預訓練模型中，使其恢復指令遵循與對話能力，同時保留對目標語言的專業知識。此步驟避免了從頭進行昂貴的指令微調。

**步驟五：端到端評估與錯誤分析**  
使用步驟一建立的基準測試評估新模型的 pass@1。同時比較以下變體：(a) 純 zero-shot、(b) 少樣本提示（few-shot）、(c) 搭配 RAG。針對生成失敗案例進行分類（語法錯誤、語意錯誤、測試邏輯誤解），決定後續優化方向。

**步驟六：部署為企業內部服務**  
將最終模型封裝為 REST API 或 gRPC 服務，整合至 IDE（如 VS Code、IntelliJ）外掛或企業內部開發平台。建立持續監控機制，收集開發者回饋與生成失敗的程式碼片段，定期回流至訓練語料庫進行迭代。

### 潛在風險與注意事項

- **指令能力災難性遺忘**：若直接在指令微調模型上執行進一步預訓練，將嚴重損害其指令遵循能力，導致模型無法理解自然語言規格。務必從基礎模型出發，再透過權重差異轉移重建指令能力。
- **語料稀缺導致的過擬合**：無資源語言的語料極少，模型可能過度記憶少數程式碼模式，泛化至未見過的基準測試題目時表現不佳。建議嚴格切分訓練語料與評估題目，並監控訓練集與驗證集的 perplexity 差距。
- **基準測試翻譯偏差**：自動翻譯高資源語言的基準測試至無資源語言時，可能產生語法不自然或慣用語錯誤的題目，導致評估失真。需由目標語言專家進行人工審查與母語化潤飾。
- **編譯與執行環境建置成本**：無資源語言通常缺乏成熟的沙箱與標準函式庫，自動化測試基礎設施（如 Docker 化編譯環境）需自行建置，否則無法正確計算 pass@1。
- **權重差異轉移的相容性限制**：權重差異轉移假設基礎模型與指令模型架構完全一致。若選用不同系列模型或經過量化（quantization），可能導致注入失敗或效能劣化。

### 與其他技術的整合建議

- **IDE 與 Language Server Protocol（LSP）整合**：將專用模型透過 LSP 或 VS Code Extension API 嵌入開發環境，提供自動完成、區塊生成與內聯建議。對於無資源語言，可補足現有工具鏈缺乏的智慧功能。
- **檢索增強生成（RAG）管線**：連接企業內部文件系統、語言規格書與內部函式庫說明，在生成前檢索相關語法範例與 API 文件。此舉可彌補模型對最新內部函式庫或私有框架的知識缺口。
- **CI/CD 與編譯驗證閉環**：將模型生成的程式碼自動提交至持續整合流程，執行編譯與單元測試。僅將通過測試的程式碼片段推薦給開發者，並將失敗案例記錄為負面樣本供後續訓練。
- **與商業工具互補部署**：在企業環境中，可將通用商業工具（如 GitHub Copilot）設為預設，而當偵測到檔案屬於無資源語言（透過副檔名或 shebang）時，自動切換至內部部署的專用模型，實現無縫雙軌支援。

建議先聚焦論文的動機與問題定義：理解「無資源語言」與「低資源語言」的區別，以及為何企業無法直接使用 ChatGPT 或 Copilot 處理內部專有語言。技術細節上，請掌握「不能直接在指令模型上續訓」這一核心教訓，並從少樣本提示與基準測試翻譯的章節開始理解整體流程，無需急著深入權重差異轉移的數學推導。

**給 AI 工程師（AI Engineers）**  
請重點研讀進一步預訓練的資料管線設計與權重差異轉移的實作細節。評估自身基礎建設：是否具備足夠的 GPU 記憶體載入 32B 參數級別的基礎模型？是否能夠在目標語言上建立自動化編譯與測試環境以計算 pass@1？論文提供的「base model → further pre-training → weight diff transfer」三步驟是可直接落地的 SOP，建議優先復現此路徑。

**給研究人員（Researchers）**  
請注意本研究對「無資源（no-resource）」的嚴格定義——訓練語料中幾乎不存在，而非僅是樣本較少的低資源情境。論文的方法論貢獻在於自建基準測試與權重差異轉移的組合策略。後續研究可探索：(i) 此方法在不同模型架構（如 MoE 或不同 tokenizer）上的泛用性；(ii) 當目標語言與高資源語言語法差異極大時（如邏輯式語言 vs. 指令式語言），權重差異轉移是否仍有效。

**給產品經理（Product Managers）**  
請將本文視為一份成本效益分析藍圖：相較於從頭進行完整的指令微調（instruction fine-tuning），論文提出的「基礎模型續訓 + 權重差異轉移」方案顯著降低了運算成本與資料門檻，使企業能以合理預算為內部專有語言部署專屬的 AI 輔助工具。評估專案時，請同步考量內部語料累積的時程、編譯環境建置的一次性成本，以及開發者生產力提升的預期效益。
