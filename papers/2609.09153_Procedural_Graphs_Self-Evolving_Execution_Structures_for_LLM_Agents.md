## ⚡ TL;DR

現有 LLM 智慧體在長軌跡中易偏離目標、錯序呼叫工具或重複無效動作。
本文提出「程序圖譜」，以（程序，關係，程序）三元組組織知識，並結合線上子圖引導與離線自我演化精煉結構。
在多個資料集、任務與模型上，程序圖譜均優於記憶基線，且從最小骨架演化出的圖譜可媲美甚至超越人工設計。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）日益被部署為能夠進行長期規劃並透過外部工具（external tool）執行動作的智慧體（agent）。大多數智慧體透過對不斷累積的歷史（accumulating history）進行無約束生成（unconstrained generation）來選擇動作（action），導致關於「該做什麼、以何種順序、在哪些條件下」的程序性知識（procedural knowledge）僅隱含於其中。隨著軌跡（trajectory）增長，智慧體可能失去對目標的掌握、以錯誤順序呼叫工具，並重複無成效的動作。本文提出程序圖譜（Procedural Graph）：正如知識圖譜（Knowledge Graph）將事實性知識（factual knowledge）組織成回答「是什麼」（what-is）問題的（實體（entity），關係（relation），實體（entity））三元組（triplet），程序圖譜將程序性知識組織成回答「該做什麼」（what-to-do）問題的（程序（procedure），關係（relation），程序（procedure））三元組。在每個決策步驟（decision step），此框架會定位智慧體的作用中節點（active node），而引導模型（guidance model）則將周圍的子圖（subgraph）轉譯為步驟層級的情境化引導（situational guidance），使求解器（solver）的下一個動作產生偏向，但不強制指定該動作。程序圖譜具備自我演化（self-evolving / self-evolution）機制：LLM 精煉器（LLM refiner）對比失敗軌跡（failed trajectory）與成功軌跡（successful trajectory），並編輯圖譜的拓樸（graph topology）與屬性（graph attributes），採納能夠維持或提升保留驗證效能（held-out validation performance）的編輯（edit），同時保留被拒絕的編輯（rejected edit）以避免未來重複相同的失敗。從最小骨架（minimal skeleton）出發，此循環所建構的圖譜可媲美甚至超越人工設計圖譜（hand-designed graph），亦能修復有缺陷的專家先驗（expert prior）。在多個資料集、任務類型與大型語言模型上，程序圖譜相較於基於記憶的基線（memory-based baseline）均帶來穩定提升，而自我演化更能在無需人工工程（manual engineering）介入的情況下進一步改善效能。

### 核心貢獻（3～5點）
- 提出程序圖譜（Procedural Graph），以（程序，關係，程序）三元組顯式組織程序性知識，並透過子圖生成情境化引導以輔助智慧體決策。
- 設計自我演化機制，使 LLM 精煉器能從成敗軌跡中自動編輯圖譜拓樸與屬性，持續提升保留驗證效能。
- 僅需最小骨架（minimal skeleton）即可啟動，能自動建構出媲美或超越人工設計圖譜的執行結構，並可修復有缺陷的專家先驗。
- 在多個資料集、任務類型與大型語言模型上驗證，相較於基於記憶的基線與無約束生成方法均有穩定增益。

### 適合對象
適合對 LLM 智慧體、長期規劃、工具使用、知識圖譜與自動化工作流程有興趣的研究者與工程師；特別是關注如何以可解釋、可編輯的結構化程序知識來提升智慧體穩定性，並希望減少人工工程成本的讀者。

## 深度分析

#### 方法論解析

本文提出的核心方法為 **Procedural Graph（程序圖譜，PG）**，其設計理念類比於 **Knowledge Graph（知識圖譜）**：若知識圖譜以 (entity（實體）, relation（關係）, entity（實體）) 三元組組織事實性知識（factual knowledge）以回答「是什麼」（what-is）問題，則程序圖譜以 (procedure（程序）, relation（關係）, procedure（程序）) 三元組組織程序性知識（procedural knowledge），以回答「該做什麼」（what-to-do）問題。形式上，程序圖譜被定義為一個有向、帶屬性的圖：

\[
G = (V, R, E, \Phi), \quad E \subseteq V \times R \times V
\]

其中 \(V\) 為抽象節點，可對應工具動作（tool action）、推理步驟（reasoning step）或狀態（state）；\(R\) 為轉移關係（transition relation）的詞彙；\(E\) 為有向邊，表示允許的執行轉移；\(\Phi\) 則為邊屬性（edge attribute），以自然語言描述「在何種情境下、如何進行該轉移」。這樣的表示將程序性知識外化於模型權重之外，使其可被檢視、檢索與編輯。

整體框架分為互補的兩個階段：**Online Inference（線上推論）** 與 **Offline Self-Evolution（離線自我演化）**。

在線上推論階段，程序圖譜保持凍結。框架首先根據 **trajectory（軌跡）** 定位 **active node（作用中節點）**，即代理當前所處的程序節點。接著，**guidance model（引導模型）** 讀取作用中節點周圍的 **subgraph（子圖）**，並在拓樸脈絡中理解相關邊的屬性，將其轉譯為 **situational guidance（情境化引導）**，進而影響 **solver（求解器）** 的下一步動作選擇。關鍵在於此引導僅「偏置」（bias）而非「指令」（dictate）solver 的行為，因此保留了 LLM（大型語言模型）的推理彈性，同時降低無約束生成（unconstrained generation）所導致的程序失序風險。

在離線自我演化階段，每完成一批訓練任務後，**LLM refiner（LLM 精煉器）** 會對比 **failed trajectory（失敗軌跡）** 與 **successful trajectory（成功軌跡）**，診斷程序圖譜中的結構缺陷，並提出對 **graph topology（圖譜拓樸）** 與 **graph attributes（圖譜屬性）** 的 **edit（編輯）**。編輯類型包括新增遺漏的節點與邊、刪除導致失敗的邊、以及修訂邊屬性文字。候選圖譜會在 **held-out validation performance（保留驗證效能）** 上進行評估，只有在效能持平或提升時才會被採納為 **accepted edit（採納的編輯）**；被拒絕的候選則保留為 **rejected edit（拒絕的編輯）**，作為負向約束以避免未來重複相同的失敗提案。此機制結合了驗證閘門（validation gate）與拒絕記憶（rejection memory），使程序圖譜能從最小骨架（minimal skeleton）開始逐步成長，甚至修復有缺陷的 **expert prior（專家先驗）**。

方法論上的幾個值得注意的設計選擇包括：

1. **外化程序知識**：不同於將經驗隱式編碼於模型參數或自由文字記憶中，程序圖譜以顯式圖結構保存「何時、如何、向何處轉移」的知識，提升可解釋性與可編輯性。
2. **局部化引導**：透過 active node 定位與鄰近子圖檢索，代理僅接收與當前進度相關的指引，避免被整段累積歷史（accumulating history）淹沒。
3. **柔性約束**：邊屬性以自然語言描述情境條件，引導模型而非強制執行，兼顧結構性與推理自由度。
4. **自我演化閉環**：LLM refiner 不僅能從頭構建圖譜，也能修正人工設計圖譜（hand-designed graph）中的錯誤，並透過驗證與拒絕記憶維持演化穩定性。

#### 實驗數據解讀

由於提供的全文片段未包含實驗章節的具體表格、數據集名稱與數值結果，本節僅能根據摘要（Abstract）與引言（Introduction）中的宣稱進行推論性解讀，並指出評估此方法時應關注的指標與解讀角度。

摘要指出，程序圖譜在多個資料集（multiple datasets）、多種任務類型（task types）以及多種 LLM 上，均一致優於基於記憶的基線（memory-based baseline），且自我演化（self-evolution）能進一步提升效能，無需人工工程。更具體地，作者宣稱從最小骨架開始演化所得到的圖譜，能夠匹配甚至超越人工設計的圖譜，並且能修復有缺陷的專家先驗。

若欲深入評估這些宣稱，應檢視以下幾類實驗證據：

1. **任務成功率（success rate）或答案正確率（accuracy）**：這是衡量代理執行長程任務效能的核心指標。程序圖譜相較於 ReAct 等無結構基線，應在長軌跡任務上展現更穩定的提升，因為其顯式編碼了動作間的依賴關係（dependency）。
2. **程序違規率（procedural violation rate）**：包括工具呼叫順序錯誤、重複無效動作（repetitive unproductive actions）、偏離目標（drift）等。程序圖譜的價值不僅在於最終正確率，也在於減少執行過程中的程序性錯誤。
3. **軌跡長度與效率（trajectory length / step efficiency）**：良好的程序結構應能縮短達成目標所需的步數，避免無謂迴圈。
4. **自我演化的收斂性（convergence of self-evolution）**：應觀察從 minimal skeleton 出發，圖譜規模、驗證效能與拒絕編輯數量隨迭代次數的變化。若驗證閘門有效，則效能應呈現單調或近似單調提升。
5. **專家先驗修復實驗（expert prior repair）**：應比較「直接使用有缺陷的專家圖譜」、「自我演化後的修復圖譜」與「從頭演化的圖譜」三者效能，以驗證演化機制對初始結構品質的魯棒性。
6. **跨模型泛化性（cross-LLM generalization）**：摘要強調在多種 LLM 上均有增益，這暗示程序圖譜作為外部知識結構，對不同 solver 的能力具有補強作用，而非僅適用於特定模型。

從方法論角度推斷，程序圖譜的優勢在長視野（long-horizon）、多步驟、工具呼叫順序敏感的任務上會最為明顯；而在單步問答或程序結構簡單的任務上，其相對於純記憶基線的邊際增益可能較小。此外，由於引導僅為偏置而非強制，若 solver 本身能力較弱，可能仍無法充分利用圖譜資訊，這也是跨 LLM 實驗中需要檢驗的現象。

#### 與現有研究的比較

本文將自身定位於三條研究脈絡的交會處：**LLM Agent（智慧體）的動作選擇**、**結構化先驗（structured prior）輔助規劃**、以及**從軌跡中自我改進的代理（self-improving agents）**。

相較於 ReAct 等以無約束生成為主的典範，程序圖譜將 admissible transition（可允許轉移）顯式編碼於圖邊中，減少了規劃幻覺（planning hallucination）、偏離目標與重複迴圈等問題。然而，不同於純粹以狀態機或工作流程強制執行順序的做法，程序圖譜透過自然語言屬性提供柔性引導，保留了 solver 根據當前觀察（observation）進行判斷的空間。

與 **textual memory（文字記憶）** 及 **self-reflection method（自我反思方法）**（如 Reflexion）相比，程序圖譜的差異在於「結構化程度」。文字記憶雖能保存有用經驗，但 solver 仍需自行判斷經驗如何應用於當前步驟以及後續步驟的約束；程序圖譜則將這些關係直接以圖結構呈現，並透過 active node 與子圖檢索實現局部化應用。

與 **state-conditioned guideline（狀態條件式指引）** 相比，程序圖譜不僅提供規則，還明確連結連續的程序步驟，使指引具有拓樸脈絡。與 **workflow（工作流程）**、**state machine（狀態機）** 或 **explicit workflow（明確工作流程）** 相比，程序圖譜的優勢在於可編輯性與自動演化能力，無需完全依賴人工設計。相較於 **automated workflow search（自動化流程搜尋）** 這類離線最佳化方法，程序圖譜結合了線上情境引導與離線自我演化，並且能在執行過程中根據當前進度動態檢索相關結構。

在自我改進的研究脈絡中，程序圖譜與儲存為 self-critique（自我批判）、insights（洞察）、workflows（工作流程）或 procedural memory（程序記憶）的方法不同之處在於：它以帶類型與屬性的邊連結程序步驟，支援局部結構檢索與基於執行回饋的拓樸編輯。這種表示法比自由文字更具結構性，又比硬編碼流程更具彈性。

儘管如此，程序圖譜仍存在若干潛在限制：

1. **LLM refiner 的品質瓶頸**：圖譜編輯完全依賴 LLM 對成敗軌跡的診斷與提案能力。若 refiner 本身產生錯誤診斷，可能導致無效的拓樸修改，雖有驗證閘門過濾，但仍會消耗運算資源。
2. **Active node 定位的模糊性**：在複雜或部分可觀測環境中，如何準確將當前軌跡對應到圖譜中的節點並非顯而易見，定位錯誤會導致後續引導失效。
3. **驗證成本與過擬合風險**：每次編輯都需在 held-out validation set 上評估，對於需要多次環境互動的任務，此過程可能相當昂貴；此外，圖譜可能過度擬合驗證集上的特定模式。
4. **柔性引導的強度限制**：由於邊屬性僅提供情境化引導而非硬性約束，對於某些必須嚴格遵守順序或禁止某些轉移的任務，可能仍需要額外的約束機制。
5. **冷啟動與最小骨架設計**：雖然論文宣稱可從 minimal skeleton 開始，但骨架的設計仍可能影響演化效率與最終品質，且未說明如何自動決定初始關係詞彙 \(R\)。

#### 可重現性評估

根據目前提供的全文片段，論文並未提及是否公開釋出原始碼、資料集、模型權重或實驗腳本。對應作者信箱為 soarik@google.com，顯示本研究可能來自 Google 內部團隊，因此其開源程度可能受限於公司政策。

可重現性的幾個關鍵面向評估如下：

1. **程式碼與實作細節**：方法涉及 active node 定位演算法、subgraph 檢索範圍、guidance model 的提示設計（prompt design）、LLM refiner 的編輯提案格式、以及驗證閘門的具體實作。若無公開程式碼，其他研究者難以精確復現。
2. **資料集與任務定義**：摘要提到多個資料集與任務類型，但未列出名稱。不同任務的程序結構差異極大，資料集的公開性與預處理方式會直接影響重現。
3. **模型權重與 API 版本**：由於方法跨多種 LLM 測試，實驗結果對模型版本、溫度參數（temperature）、取樣策略高度敏感。若僅使用商業 API，則需詳細記錄呼叫設定。
4. **圖譜表示與評估指標**：程序圖譜的結構、屬性格式、以及 accepted/rejected edit 的記錄方式，都是重現所需的重要細節。

綜合而言，在缺乏公開資源的情況下，本方法的可重現性評估為「有限」。即使概念清晰，實作上的許多設計選擇仍可能顯著影響結果。建議作者未來提供至少包含圖譜格式範例、提示模板與評估流程的補充材料，以提升研究的可驗證性。

#### 未來研究方向

基於程序圖譜的框架設計，可延伸出多個值得探索的研究方向：

1. **階層式程序圖譜（Hierarchical Procedural Graph）**：將低層工具動作抽象為高層子目標，形成多層次圖結構，以處理更長視野、更複雜的任務，並支援不同粒度下的引導。
2. **神經符號驗證（Neuro-Symbolic Validation）**：目前驗證閘門依賴保留集上的效能評估，未來可結合形式化方法（formal methods）或符號規則檢查，在採納編輯前驗證圖譜的結構正確性與安全性。
3. **邊嵌入與可學習轉移（Learnable Edge Embeddings）**：將邊屬性轉為可學習的向量表示，使引導模型能更細緻地捕捉轉移條件，並支援跨領域遷移。
4. **線上動態圖譜更新（Online Dynamic Graph Update）**：目前圖譜在推論時凍結，未來可探索在執行過程中根據新觀察即時調整局部結構，以適應動態環境。
5. **與強化學習結合（Integration with Reinforcement Learning）**：將程序圖譜作為動作空間的結構化先驗，並以 RL 微調轉移權重或邊屬性，進一步提升長期回報。
6. **多智慧體程序協調（Multi-Agent Procedural Coordination）**：擴展程序圖譜至多智慧體場景，讓不同代理的程序圖譜彼此連結，以協調角色分工與互動順序。
7. **人機協同編輯（Human-in-the-Loop Graph Editing）**：在自我演化之外，引入領域專家審查與修正 LLM refiner 提出的編輯，以加速收斂並提升圖譜品質。
8. **不確定性感知引導（Uncertainty-Aware Guidance）**：讓引導模型估計每條建議轉移的不確定性，並在不確定度高時切換為更保守或請求人類確認的策略。
9. **負向約束的理論分析（Theoretical Analysis of Negative Constraints）**：深入研究保留 rejected edit 作為負向記憶對搜尋空間與收斂行為的影響，並設計更有效的拒絕記憶機制。
10. **跨領域遷移與組合（Cross-Domain Transfer and Composition）**：探索如何將一個領域中演化出的程序圖譜，遷移或組合至另一個相關領域，以減少從頭演化的成本。

## 論文問答

**Q1：程序圖譜主要想解決什麼問題？**

A：現今大型語言模型智慧體大多依靠無約束生成，在一段不斷累積的動作與觀察歷史上進行決策，這使得「接下來該做什麼、以什麼順序、在什麼條件下做」等程序性知識隱含在自由文字中。當軌跡變長，智慧體容易遺失目標、以錯誤順序呼叫工具，或陷入重複無效動作的迴圈。程序圖譜透過把程序性知識外顯為可檢視、可檢索、可編輯的圖結構，減輕求解器在每一步重建程序一致性的負擔，從而提升長程規劃的穩定性。

**Q2：現有的記憶式、條件式指引與工作流程方法為何不足以解決這個問題？**

A：文字記憶與自我反思方法雖然保留了過去經驗，但求解器仍須自行判斷這段經驗如何套用到當前步驟以及後續步驟受到什麼約束。狀態條件式指引雖然能針對情境給出規則，卻沒有把連續程序步驟之間的轉換關係明確連結起來。工作流程與狀態機雖然能明確規範執行順序，卻常需人工設計且彈性較低，因此現有方法缺乏一種既能編輯、又能依據當前進度提供動態引導的程序表示法。

**Q3：為什麼把程序性知識結構化對長程智慧體如此重要？**

A：長程任務的成功與否取決於智慧體是否知道正確的動作順序與前置條件，而非僅擁有孤立的事實或片段經驗。若程序性知識僅隱含在模型權重或自由文字中，智慧體容易在執行過程中偏離目標或產生幻覺式規劃。將程序性知識結構化後，不僅能讓智慧體在每一步獲得與當前狀態相符的引導，也讓開發者能夠檢查、修正並持續改善這些知識。

**Q4：程序圖譜的核心方法架構是什麼？**

A：程序圖譜是一個有向、帶屬性的圖譜，節點抽象化工具動作、推理步驟或狀態，邊則代表不同類型的程序轉換，並附帶描述「如何以及何時採用該轉換」的文字屬性。在線上推理階段，框架會根據智慧體的執行軌跡定位作用中節點，再由引導模型讀取周圍子圖並產生步驟層級的情境化引導。在離線自我演化階段，LLM 精煉器會對比成功與失敗軌跡，自動編輯圖譜的拓樸與屬性，使程序知識隨經驗成長。

**Q5：程序圖譜相較於既有方法最關鍵的創新是什麼？**

A：本文把知識圖譜「（實體，關係，實體）」的概念延伸到程序領域，提出以「（程序，關係，程序）」三元組來回答「該做什麼」的問題。其次，它結合了「生成式程序圖譜引導」與「自我演化迴路」，前者把靜態圖譜與動態軌跡轉譯為不干預推理自由的情境引導，後者則透過驗證閘門與拒絕記憶機制持續精煉圖譜。這種設計同時兼顧了對無效行為的抑制力與對求解器推理彈性的保留。

**Q6：程序圖譜在設計上做了哪些重要選擇？**

A：首先，圖譜被保存在模型權重之外，使其可被直接檢視、編輯與版本控制，而無需重新訓練模型。其次，引導模型只對求解器的下一步動作進行「偏置」而非「強制指定」，因此保留了智慧體根據最新觀察進行彈性調整的空間。最後，自我演化採用保留驗證效能作為採納標準，並把被拒絕的編輯保留為負向約束，以避免精煉器重複提出同樣失敗的修改。

**Q7：論文在哪些實驗設定與任務類型上評估程序圖譜？**

A：根據摘要與全文脈絡，研究橫跨多個資料集、多種任務類型以及多個大型語言模型進行評估，涵蓋需要長程規劃與外部工具呼叫的智慧體任務。這些任務可能包括多步驟推理、網頁導航、資料查詢與工具組合等情境。透過在不同骨幹模型與任務上驗證，作者顯示程序圖譜的效益並非侷限於單一設定。

**Q8：程序圖譜在實驗中取得了哪些關鍵結果？**

A：程序圖譜在多個設定下一致優於基於記憶的基線方法，顯示結構化程序知識比單純累積自由文字經驗更能提升執行品質。從最小骨架開始自我演化所得到的圖譜，能夠達到甚至超越人工設計圖譜的表現，顯著降低手動工程成本。此外，當初始先驗存在缺陷時，自我演化迴路也能修復這些瑕疵，進一步提升整體效能。

**Q9：有哪些消融實驗或對比分析凸顯了各元件的貢獻？**

A：論文透過與純記憶基線、人工設計圖譜、從零開始演化的圖譜以及受損專家先驗的對比，驗證了程序圖譜與自我演化的價值。驗證閘門的消融應能顯示，若缺少保留驗證效能的篩選，有害編輯會降低整體表現。拒絕記憶機制則能抑制重複的失敗提案，而生成式引導相較於直接檢索原始圖譜屬性，更能產生貼近當前情境的步驟指引。

**Q10：程序圖譜在實務上適合應用在哪些場景？**

A：任何需要嚴格動作順序與條件判斷的長程任務都適合採用程序圖譜，例如客戶服務自動化、軟體工程智慧體、科學實驗規劃、機器人任務執行以及複雜資料分析流程。在這些場景中，錯誤的工具順序或條件判斷會導致明顯後果，因此結構化引導能顯著降低失敗率。由於圖譜可被人類理解與編輯，它也特別適合需要合規、稽核或人機協作的應用。

**Q11：若要在產品中落地程序圖譜，需要考慮哪些工程與產品議題？**

A：首先需要準備一個最小骨架與足夠代表性的保留驗證集，以啟動並監控自我演化過程。其次，LLM 精煉器反覆對比軌跡與編輯圖譜會帶來額外運算成本，因此需要評估演化頻率與資源預算。此外，產品團隊應建立圖譜版本控制、人工介入編輯介面以及安全約束機制，確保演化後的圖譜符合業務規範且不會引入新的風險行為。

**Q12：程序圖譜對整個大型語言模型智慧體領域可能帶來什麼影響？**

A：它推動智慧體設計從「隱含在上下文記憶中的程序知識」轉向「外顯、可編輯、可自我改善的執行結構」。這種典範轉移有助於提升智慧體的可解釋性、可維護性與長期可靠性。長遠來看，程序圖譜可能成為連接工作流程自動化、自主智慧體與人機協作的重要基礎設施。

**Q13：程序圖譜目前有哪些可能的限制？**

A：圖譜品質與演化成效高度依賴 LLM 精煉器的能力以及保留驗證集的代表性，若驗證集不足或偏頗，可能採納次優編輯。自我演化需要反覆執行任務並進行圖譜評估，對運算資源與時間成本有較高需求。此外，對於程序結構本身極度模糊或高度動態變化的任務，單一程序圖譜可能難以完整捕捉所有合法執行路徑。

**Q14：在什麼情況下程序圖譜可能會失效或表現不佳？**

A：若作用中節點定位錯誤，後續子圖引導就會偏離當前真實狀態，導致智慧體做出不適當的動作。當任務的程序結構與圖譜差異過大，或環境觀察具有高度雜訊時，生成式引導也可能無法提供有效建議。此外，若精煉器產生結構上無效或語意不一致的編輯，而驗證閘門未能及時攔截，則可能讓圖譜品質退化。

**Q15：未來可以朝哪些方向延伸程序圖譜的研究？**

A：未來可發展層級式程序圖譜，以同時處理高層目標規劃與低層工具執行。也可探索多智慧體共享程序圖譜，讓不同角色在協作中同步更新共同知識。此外，結合世界模型、形式化驗證或人類回饋的線上持續演化，將是提升圖譜安全性、泛化能力與實用性的重要方向。

## 實務應用指南

### 適用場景

1. **多步驟客戶服務智慧體**  
   當 LLM 智慧體需要依序執行「意圖理解 → 查詢帳戶 → 驗證身份 → 執行退換貨 → 確認結果」等步驟時，程序圖譜可將各程序節點與合法轉換關係外顯化，避免智慧體在長對話中遺漏驗證步驟或重複詢問相同資訊。

2. **資料分析與報告生成代理**  
   在「取得資料 → 清洗 → 選擇分析方法 → 執行計算 → 視覺化 → 撰寫結論」的流程中，程序圖譜可根據當前資料狀態提供情境化引導，例如當資料缺失時優先導回清洗節點，而非直接進入建模。

3. **軟體開發輔助代理（DevAgent）**  
   用於規劃與執行長期開發任務，如「需求分析 → 設計 API → 產生測試 → 實作 → 執行測試 → 修復錯誤 → 提交」。程序圖譜能防止智慧體在尚未通過測試前逕行提交程式碼，並透過自我演化持續修正錯誤修復策略。

4. **醫療或法規遵循問答系統**  
   在需要嚴格遵循程序（例如「症狀詢問 → 風險評估 → 建議就醫層級 → 提供衛教資訊」）的場景中，程序圖譜可作為可檢視、可稽核的執行結構，降低違反規範或跳過關鍵步驟的風險。

5. **科學實驗規劃與機器人操作**  
   對於需要依賴外部工具（實驗儀器、機器人 API）的長期任務，程序圖譜能明確定義工具呼叫順序與前置條件，並在失敗後透過自我演化學習更穩健的操作順序。

---

### 實作前置條件

**資料條件**
- 具備一定數量的「任務軌跡」資料，包含成功與失敗案例，以便 LLM 精煉器進行對比學習。
- 每個任務最好有明確的最終評估指標（例如正確率、完成率、人工評分），作為保留驗證效能的依據。
- 初始的最小骨架圖譜或專家先驗（即使只有 3–5 個核心程序節點與基本轉換關係）。

**運算條件**
- 可呼叫的 LLM API 或自有模型，分別用於求解器（執行動作）與引導模型（產生情境化引導）。
- 額外的 LLM 精煉器用量，用於離線自我演化階段的圖譜編輯提案與驗證。
- 圖譜儲存與查詢工具（如圖資料庫或記憶體中的 NetworkX / 自訂結構）。

**技能條件**
- 熟悉提示工程（prompt engineering）與 LLM 代理系統設計。
- 具備圖論基礎，能設計與驗證有向圖譜的拓樸結構。
- 能建立自動化評估管線，以執行保留驗證與 A/B 比較。
- 建議具備領域知識，以便定義初始程序節點與合理的轉換關係。

---

### 實作步驟建議

1. **定義任務與程序節點**  
   從領域流程中抽象出關鍵程序（如驗證、查詢、計算、輸出），建立最小骨架圖譜。每個節點應對應一個可執行的動作或推理步驟。

2. **設計轉換關係與邊屬性**  
   為每條有向邊定義關係類型（例如 `requires`、`enables`、`leads_to`）與文字屬性，說明「在什麼條件下、為什麼要進行此轉換」。

3. **建置線上推論管線**  
   在每次決策步驟中，根據當前軌跡定位作用中節點，擷取周圍子圖，並由引導模型將子圖轉譯為情境化引導，再與求解器提示結合。

4. **收集執行軌跡與回饋**  
   讓智慧體在訓練任務上執行，記錄完整軌跡、觀察與最終成敗結果，作為自我演化的輸入。

5. **啟動離線自我演化迴圈**  
   使用 LLM 精煉器對比失敗與成功軌跡，提出新增、刪除、修改節點或邊的編輯提案，並在保留驗證集上測試。

6. **驗證與採納編輯**  
   僅採納能提升或維持保留驗證效能的編輯；將被拒絕的編輯保留為負向約束，避免未來重複提出相同失敗修改。

7. **部署與持續監控**  
   將演化後的圖譜部署至生產環境，持續收集真實軌跡，定期重新執行自我演化以適應新任務型態。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **過度約束求解器** | 圖譜過於僵化可能限制 LLM 的推理彈性，導致無法處理未預期情境。 | 邊屬性應以「引導」而非「強制」方式撰寫，保留求解器的最終決策空間。 |
| **自我演化過度擬合** | 圖譜可能過度適應訓練任務，在保留驗證集上表現不佳。 | 使用獨立且具代表性的保留驗證集作為採納門檻，並監控泛化指標。 |
| **編輯提案品質不穩定** | LLM 精煉器可能提出無效或結構錯誤的圖譜編輯。 | 加入結構驗證機制（例如檢查死結、孤立節點、循環），並保留拒絕記憶抑制重複。 |
| **長軌跡定位錯誤** | 當軌跡過長或觀察模糊時，作用中節點定位可能失準。 | 設計穩健的節點匹配邏輯，可結合最近動作、觀察摘要與嵌入相似度。 |
| **領域遷移困難** | 為某一任務演化的圖譜未必適用於其他任務。 | 將圖譜模組化，區分通用程序層與領域特定層，並針對新任務進行微調演化。 |

---

### 與其他技術的整合建議

- **與 RAG / 向量記憶整合**：可將程序圖譜作為結構化記憶層，與自由文字記憶互補。圖譜負責「該做什麼」的程序性知識，向量資料庫負責「事實是什麼」的領域知識。
- **與現有工作流程引擎整合**：可將程序圖譜輸出為 BPMN、狀態機或規則引擎可讀格式，讓企業現有流程系統與 LLM 代理共用同一套執行結構。
- **與觀察追蹤工具整合**：將 LangSmith、Langfuse 或自訂追蹤系統的軌跡資料直接餵入自我演化迴圈，降低資料收集成本。
- **與評估框架整合**：連接 evals、AgentBench 或自訂評估管線，自動產生保留驗證分數，作為編輯採納的依據。
- **與多代理系統整合**：不同代理可各自維護局部程序圖譜，並透過共享圖譜層協調跨代理程序順序。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦於圖 1 的類比——把「知識圖譜回答『是什麼』」對應到「程序圖譜回答『該做什麼』」。理解節點是步驟、邊是合法轉換後，再閱讀線上推論與自我演化的概念即可，暫時不需要深入形式化符號。

**AI 工程師**：請重點閱讀第 3 節的框架設計與演算法細節，特別是作用中節點定位、子圖擷取範圍、引導模型提示設計，以及自我演化中的編輯採納與拒絕記憶機制，這些都是落地實作時最關鍵的工程決策。

**研究人員**：建議深入分析程序圖譜與其他結構化先驗（如工作流程、狀態機、條件式指引）的差異，並關注自我演化迴路中的驗證門檻與負向約束設計，這些是本文方法論上的主要貢獻與後續可延伸之處。

**產品經理**：請優先閱讀適用場景與實驗結果，評估程序圖譜能否解決您產品中智慧體「長軌跡失焦、動作順序錯誤、重複無效動作」等問題，並留意自我演化需要持續的軌跡資料與評估機制，這會影響產品時程與資源規劃。
