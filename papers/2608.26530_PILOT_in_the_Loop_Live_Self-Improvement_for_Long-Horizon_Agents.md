## ⚡ TL;DR

現有長程智慧體多於執行結束後才檢討，無法即時修正當前執行並驗證所學。
本文提出PILOT監督器-工作者框架，透過即時引導與即時自我演化形成閉迴路改進。
在六組設定中五組排名第一，自我改進後通過率最高提升14.6百分點，輸出詞元顯著下降。

## 摘要翻譯

長程智慧體（long-horizon agent）的執行會產生能夠改進當前執行（current run）與後續工作（future work）的經驗。大多數自我改進（self-improvement）方法僅在執行結束後才處理這些經驗，因此無法重新導向（redirect）當前執行（active run），也無法立即應用並驗證從中汲取的經驗教訓。我們主張自我改進應是即時的（live），運用新興經驗（emerging experience），同時重新導向當前執行並更新持久框架（persistent harness）。現有的智慧體（agent）架構無法完全支援此目標。單一智慧體自我修正（single-agent self-correction）將任務執行（task execution）與軌跡評估（trajectory assessment）結合在同一上下文（context）中，而子代理委派（subagent delegation）雖將執行分離，但通常無法重新導向當前子代理（active subagent）。我們提出 PILOT，一個透過兩項耦合機制（coupled mechanisms）實現即時自我改進的監督器-工作者框架（supervisor-worker harness）：（1）即時引導（live steering）讓獨立的監督器（supervisor）在執行期間重新導向或中止（abort）當前工作者（active worker）；（2）即時自我演化（live self-evolution）將執行過程中浮現的程序（procedures）與失敗模式（failure modes）提煉（distil）為可重複使用技能（reusable skills）與記憶（memory）。橫跨兩個凍結骨幹模型（frozen backbones）與三個基準測試（benchmarks），PILOT 在六項設定（configurations）中有五項排名第一（ranks first）。在 Terminal-Bench 2.0 上，PILOT 優於對應框架（counterpart harnesses）高達 9.8 個百分點（percentage points）。在自我改進設定（self-improvement setting）中，PILOT 在 GLM-5.1 上取得 14.6 百分點的增益，在 Kimi-K2.6 上則取得 12.4 百分點的增益；平均輸出詞元數（mean output tokens）分別下降 42.9% 與 47.4%，而每百萬輸出詞元的成功評估次數（successful evaluations per million output tokens）則分別上升 110.3% 與 134.0%。

### 核心貢獻（3～5點）
- 提出即時自我改進（Live Self-Improvement）概念，強調在執行過程中同時重新導向當前執行並更新持久框架，突破僅於執行結束後才處理經驗的既有限制。
- 設計 PILOT 監督器-工作者框架（Supervisor-Worker Harness），透過即時引導（Live Steering）與即時自我演化（Live Self-Evolution）兩項耦合機制形成閉迴路改進。
- 在即時引導機制中，由獨立監督器於執行期間重新導向或中止工作者，克服單一智慧體自我修正與子代理委派無法即時介入當前執行的限制。
- 在即時自我演化機制中，將執行過程浮現的程序與失敗模式提煉為可重複使用技能與記憶，提升後續執行的效率與成功率。
- 在 Terminal-Bench 2.0 等基準測試上取得顯著性能增益與效率提升，驗證方法於凍結骨幹模型上的有效性。

### 適合對象
對長程智慧體、自我改進機制、監督器-工作者架構，以及大型語言模型代理系統有興趣的研究人員與工程師；特別適合關注即時回饋、閉迴路學習與代理效率最佳化的進階讀者。

## 深度分析

#### 方法論解析

PILOT（論文提出的監督器-工作者框架）將 **live self-improvement（即時自我改進）** 視為一個 **closed loop（閉迴路）**：在 **active run（當前執行）** 進行中，同時利用 **emerging experience（新興經驗）** 來重新導向當前執行，並更新 **persistent harness（持久框架）** 以供後續執行使用。這與傳統 **post-hoc review（事後檢討）** 在 **execution ends（執行結束）** 後才更新有本質區別。

##### 整體架構：Supervisor–Worker Harness（監督器-工作者框架）

PILOT 採用雙角色設計：

- **Worker（工作者）**：負責 **task execution（任務執行）**，在與環境互動的 **isolated context（隔離上下文）** 中產生 **trajectory（軌跡）**。Worker 的上下文吸收大量 **execution details（執行細節）**、死路與冗餘工具輸出。
- **Supervisor（監督器）**：負責 **self-improvement role（自我改進角色）**，維持獨立的上下文，專注於目標、近期事件與 **recurring failure mode（反覆出現的失敗模式）**。

兩者透過 **live channel（即時通道）** 持續連線，Supervisor 不等待 **completed trace（已完成軌跡）**，而是在 Worker 執行期間即時介入。

##### 即時引導（Live Steering）

Live steering（即時引導）讓 Supervisor 在 Worker 執行期間進行 **redirect（重新導向）** 或 **abort（中止）**。通道支援三種 Worker → Supervisor 事件與兩種 Supervisor → Worker 動作：

- Worker → Supervisor：
  1. **Notification（通知）**：回報進度、中間結果或潛在風險。
  2. **Question（問題）**：向 Supervisor 請求決策。
  3. **Result / Error / Inactivity Alert（結果、執行錯誤、無活動警示）**：回報最終結果、錯誤或停滯。
- Supervisor → Worker：
  1. **Steer（引導）**：指示 Worker 改變策略或行動。
  2. **Abort（中止）**：提前結束無效的執行。

這種設計讓 Supervisor 的上下文保持「目標導向」與「診斷導向」，而 Worker 的上下文專注於低階執行，避免 **single-agent self-correction（單一智慧體自我修正）** 中執行與診斷爭奪同一上下文的問題。

##### 即時自我演化（Live Self-Evolution）

Live self-evolution（即時自我演化）將執行過程中發現的 **procedure（程序）**、**project convention（專案慣例）** 與 **failure mode（失敗模式）** 提煉為 **reusable skill（可重複使用技能）** 與 **memory（記憶）**，並寫入 **persistent harness（持久框架）**。

關鍵在於：這些知識在產生它的同一執行中即可被應用與驗證。例如，Supervisor 發現某條命令常導致權限錯誤，可立即指示 Worker 改用 `sudo`，同時將此 **failure mode（失敗模式）** 記錄為記憶，供後續 Worker 載入。後續 **worker's session（工作者的執行階段）** 會載入更新後的 harness，進入相同的 live steering 與 live self-evolution 迴路。

##### 閉迴路設計的優勢

PILOT 的閉迴路具備三個層次：

1. **當前執行層次**：Supervisor 即時修正 Worker 的錯誤策略。
2. **驗證層次**：修正後的知識在同一執行中接受驗證。
3. **持久層次**：驗證有效的知識被保留為 **reusable skill（可重複使用技能）**，提升後續 **later rollout（後續推出）** 的效率。

這解決了 **post-hoc review（事後檢討）** 中「知識無法幫助產生它的執行」與「無法即時驗證」的缺陷。

#### 實驗數據解讀

論文在兩種設定下評估 PILOT：**one-shot setting（一次性設定）** 與 **self-improvement setting（自我改進設定）**，使用兩個 **frozen backbone（凍結骨幹模型）**（GLM-5.1 與 Kimi-K2.6）與三個 **benchmark（基準測試）**。

##### One-Shot Setting（一次性設定）

在一次性設定中，PILOT 在六個 backbone–benchmark **configuration（設定）** 組合中有五組排名第一。特別是在 **Terminal-Bench 2.0** 上，PILOT 相較於 **counterpart harness（對應框架）** 提升最高達 **9.8 percentage points（百分點）**。

這顯示即使不進行跨任務累積，單靠 **live steering（即時引導）** 與上下文分離，就能顯著改善長程任務表現。原因在於 Supervisor 能及時發現 **action drift（行動偏離）** 或 **reasoning tool action drift（推理工具行動偏離）**，避免 Worker 在錯誤路徑上消耗過多 token。

##### Self-Improvement Setting（自我改進設定）

在自我改進設定中，研究者將 Terminal-Bench 2.0 的任務組織成多個 iteration（迭代），每個迭代內所有任務共享固定的 **persistent harness（持久框架）** 狀態，且執行期間不提供 **benchmark feedback（基準測試回饋）**。迭代結束後，才將成功執行中提煉出的 **skill（技能）** 保留至下一迭代。

主要結果：

| 指標 | GLM-5.1 | Kimi-K2.6 |
|---|---|---|
| Best observed pass rate gain（最佳通過率增益） | +14.6 pp | +12.4 pp |
| Reusable skill set growth（可重複使用技能增長） | +21 skills | +31 skills |
| Mean output tokens fall（平均輸出詞元數下降） | −42.9% | −47.4% |
| Successful evaluations per million output tokens rise（每百萬輸出詞元的成功評估次數上升） | +110.3% | +134.0% |

###### 數據意涵

1. **通過率提升**：GLM-5.1 與 Kimi-K2.6 分別提升 14.6 與 12.4 百分點，顯示 **live self-evolution（即時自我演化）** 能有效累積任務相關知識。由於執行期間無基準測試回饋，這些增益來自 harness 本身的演化，而非對答案的投機。
2. **技能增長**：兩個模型分別累積 21 與 31 個 **reusable skill（可重複使用技能）**，說明 Terminal-Bench 2.0 中存在可泛化的程序性知識。
3. **Token 效率大幅提升**：平均 **output tokens（輸出詞元）** 下降超過四成，而 **successful evaluations per million output tokens（每百萬輸出詞元的成功評估次數）** 提升超過一倍。這表示累積的 skill 與 memory 減少了 Worker 的重複探索與試錯，使模型在相同 token 預算下完成更多成功評估。
4. **模型差異**：Kimi-K2.6 的 token 下降幅度與效率提升幅度略高於 GLM-5.1，可能反映其作為 Worker 時對 Supervisor 引導的遵循度較高，或基線探索行為較為冗餘。

##### 個案研究

論文透過兩個 **case study（個案研究）** 說明 Supervisor 如何在 Worker 持續負責解決方案的前提下，重新導向策略或修正實作錯誤。這強化了 PILOT 的設計哲學：Supervisor 不干預低階執行細節，而是修正高階策略與錯誤假設。

#### 與現有研究的比較

PILOT 的定位可從三個現有典範的對比來理解：

| 方法典範 | 代表機制 | 主要限制 | PILOT 的改進 |
|---|---|---|---|
| **Post-hoc review（事後檢討）** | Reflection（反思）、Judge-based evaluation（評判式評估）、Self-evolving harness（自我演化框架） | 更新在 **execution ends（執行結束）** 後才開始，無法 **redirect（重新導向）** **active run（當前執行）** | 在執行中即時更新並驗證知識 |
| **Single-agent self-correction（單一智慧體自我修正）** | 同一 Agent 同時執行與診斷 | 執行細節與診斷共享上下文，難以辨識無效策略 | 將執行與自我改進分離為 Worker 與 Supervisor |
| **Subagent delegation（子代理委派）** | Main Agent 委派 Subagent 執行，完成後接收 **final summary（最終摘要）** | 無法在 Subagent 執行期間重新導向 | Supervisor 透過 **live channel（即時通道）** 全程連線 Worker |

##### 相對於 Post-Hoc Review 的改進

傳統 **self-evolving harness（自我演化框架）** 雖能從已完成軌跡更新 **prompt（提示）**、**skill（技能）** 或 **memory（記憶）**，但新知識無法幫助產生它的執行，也無法在該執行中 **validate（驗證）** 其效用。PILOT 讓知識在「誕生」的當下就被應用與檢驗，縮短了學習迴路。

##### 相對於 Single-Agent Self-Correction 的改進

在單一智慧體架構中，**context（上下文）** 同時被執行細節與高階診斷佔據，容易導致 **reasoning tool action drift（推理工具行動偏離）**。PILOT 透過 **isolated context（隔離上下文）** 讓 Worker 專注執行，Supervisor 專注目標與風險，實現 **dedicated role（專門角色）** 的分工。

##### 相對於 Subagent Delegation 的改進

雖然 **subagent delegation（子代理委派）** 已將執行分離，但 Main Agent 通常只能在委派執行結束後根據 **final summary（最終摘要）** 做決策。PILOT 的 Supervisor 則是「在執行上 live（即時）」的監督者，能主動 **steer（引導）** 或 **abort（中止）**。

##### 限制

儘管 PILOT 設計精巧，仍有以下潛在限制：

1. **Supervisor 成本**：維持 **live channel（即時通道）** 與持續診斷會增加額外的推理開銷，雖然整體 **output tokens（輸出詞元）** 下降，但 Supervisor 本身的 token 消耗需納入總成本評估。
2. **過度引導風險**：若 Supervisor 過早或過度介入，可能限制 Worker 的探索，導致局部最優。
3. **依賴骨幹模型品質**：Supervisor 與 Worker 均為 **frozen backbone（凍結骨幹模型）**，其診斷與遵循能力受模型本身能力限制。
4. **可擴展性**：當同時存在多個 active Worker 時，Supervisor 可能成為瓶頸，需要進一步的多 Worker 排程機制。
5. **無模型參數更新**：PILOT 的 **self-improvement（自我改進）** 僅更新 **persistent harness（持久框架）**，不更新模型參數 θ，對於需要深層能力改變的任務可能有限。

#### 可重現性評估

根據目前提供的論文內容，可重現性面臨以下狀況：

##### 程式碼與實作

論文未提及是否公開原始碼、提示詞模板或 **skill distillation（技能提煉）** 的具體演算法。若要完整重現 PILOT，需要：

- Supervisor 與 Worker 的 **prompt（提示）** 設計。
- **Live channel（即時通道）** 的實作細節，包括事件觸發條件、通知頻率與逾時機制。
- **Skill（技能）** 與 **memory（記憶）** 的儲存格式、檢索方式與更新策略。
- **Abort（中止）** 與重新 **spawn（產生）** Worker 的決策邏輯。

##### 資料集

**Terminal-Bench 2.0** 是已發表的基準測試，原則上可取得。但論文中將任務組織成 iteration（迭代）的方式、每個迭代的任務分配與狀態共享規則，需要作者補充才能精確重現。

##### 模型權重

GLM-5.1 與 Kimi-K2.6 均為專有 API 模型，**frozen backbone（凍結骨幹模型）** 的權重並未公開。這意味著其他研究者只能透過 API 呼叫重現，無法在本地完全複製模型行為。此外，API 版本、溫度參數、最大 token 數等超參數也會影響重現結果。

##### 整體評估

目前可重現性屬於「中等受限」：基準測試可取得、模型可透過 API 使用，但核心 harness 實作與實驗細節尚未公開。建議作者釋出：

1. PILOT harness 的開源實作。
2. 所有 prompt 與 skill/memory 範本。
3. 自我改進設定的迭代劃分與種子設定。
4. 完整的超參數與 API 版本資訊。

這將大幅提升社群驗證與延伸研究的可能性。

#### 未來研究方向

PILOT 的 live self-improvement（即時自我改進）框架開啟了多個值得探索的方向：

1. **多 Worker 並行監督**：發展能同時監督多個 active Worker 的 Supervisor 排程與注意力機制，提升吞吐量並降低單點瓶頸。
2. **自適應引導策略**：研究何時該 **steer（引導）**、何時該讓 Worker 自行探索的決策模型，避免過度或不足介入。
3. **Supervisor 自身的學習**：目前 Supervisor 為 **frozen backbone（凍結骨幹模型）**，未來可讓 Supervisor 從多次監督經驗中學習更有效的診斷與引導策略。
4. **與微調結合**：將 harness 中累積的 **reusable skill（可重複使用技能）** 轉化為微調資料，更新模型參數 θ，實現更深層的能力提升。
5. **自動化技能驗證**：建立機制自動檢驗新提煉 skill 的正確性與泛化性，避免錯誤知識被永久保留。
6. **跨任務遷移**：研究在不同領域 **benchmark（基準測試）** 之間遷移 skill 與 memory 的有效性，特別是從 Terminal-Bench 2.0 擴展到網頁操作、程式開發或科學實驗等長程任務。
7. **理論分析**：從 **regret（遺憾）** 與樣本複雜度角度分析 live steering 與 live self-evolution 的收斂性與最優性。
8. **人機協作**：將人類操作員整合為 Supervisor 的一部分，形成 **human-in-the-loop（人在迴路）** 的 live self-improvement 系統。
9. **開放式環境**：將 PILOT 應用於無明確成功準則的開放式環境，發展即時的內在獎勵與目標推斷機制。
10. **成本效益優化**：設計輕量級 Supervisor，例如使用較小模型或快取機制，在保持效能的同時降低即時監督的推理成本。

## 論文問答

**Q1：長程智慧體在自我改進方面面臨的核心問題是什麼？**
A：長程智慧體在執行過程中會持續產生新興經驗，這些經驗原本可以同時改善當前執行與未來執行。然而，現有大多數自我改進方法屬於事後檢討，只能在執行結束後才處理這些經驗，因此無法在當前執行偏離目標時即時重新導向。這導致新提煉出的知識無法幫助產生它的那趟執行，也無法在發現問題的當下立即應用並驗證其效用。

**Q2：為什麼單一智慧體自我修正與子代理委派無法充分支援即時自我改進？**
A：單一智慧體自我修正把任務執行與軌跡診斷放在同一個上下文中，執行細節會佔據原本用於診斷的上下文空間，使智慧體難以辨識並修正整體策略上的問題。子代理委派雖然把執行分離出去，但主智慧體通常只能在委派執行結束後收到最終摘要，無法在子代理仍在運行時進行即時引導。因此，這兩種架構都無法同時滿足「即時修正當前執行」與「設立專門自我改進角色」這兩項需求。

**Q3：相較於事後檢討，即時自我改進為何更重要？**
A：即時自我改進能把執行過程中浮現的經驗同時用於重新導向當前執行與更新持久框架，形成閉迴路。這讓監督器可以在問題發生的當下介入，避免智慧體繼續浪費詞元在錯誤或低效的路徑上。同時，新提煉的技能與記憶也能在同一趟執行中接受驗證，而不是等到後續推出才能測試其真正效用。

**Q4：PILOT 的兩個耦合機制是什麼？**
A：PILOT 透過「即時引導」與「即時自我演化」兩個機制實現即時自我改進。即時引導讓監督器在工作者執行期間透過即時通道重新導向或中止工作者；即時自我演化則把執行中揭示的有用程序、專案慣例與失敗模式提煉成可重複使用的技能與記憶。這兩個機制共享同一條執行經驗流，使當前執行的修正與持久框架的更新能夠同步進行。

**Q5：PILOT 如何分離角色並保護上下文？**
A：PILOT 採用監督器—工作者框架，工作者負責實際任務執行，監督器負責自我改進與監督。工作者的隔離上下文吸收執行細節、死胡同與冗餘的工具輸出，而監督器的獨立上下文則專注於目標、近期事件與執行是否偏離軌跡。監督器只在需要診斷時才讀取工作者軌跡的相關部分，從而避免執行細節干擾高層判斷。

**Q6：哪些設計選擇使即時引導成為可能？**
A：PILOT 在監督器與工作者之間建立雙向即時通道，並在整趟執行中保持連線。工作者可以主動傳送通知、問題、最終結果、執行錯誤與閒置警報等事件；監督器則可以回傳「引導」或「中止」兩種動作。這種設計讓監督器不必等待已完成軌跡，就能在工作者仍在運行時即時介入並改變其行動方向。

**Q7：實驗使用了哪些基準測試與骨幹模型？**
A：論文在兩個凍結骨幹模型與三個長程基準測試上評估 PILOT，其中包括 Terminal-Bench 2.0。兩個骨幹模型分別是 GLM-5.1 與 Kimi-K2.6，模型參數在實驗中保持凍結，自我改進只發生在持久框架而非模型本身。這樣的設定能夠清楚檢驗監督器—工作者框架與即時自我改進機制所帶來的效益。

**Q8：PILOT 的關鍵量化結果有哪些？**
A：在單次執行設定中，PILOT 在六個骨幹—基準組合中有五組排名第一；在 Terminal-Bench 2.0 上，PILOT 比對應框架最高多出 9.8 個百分點。在即時自我改進設定中，最佳觀察通過率分別提升 14.6 百分點（GLM-5.1）與 12.4 百分點（Kimi-K2.6）。同時，平均輸出詞元數分別下降 42.9% 與 47.4%，每百萬輸出詞元的成功評估次數則分別上升 110.3% 與 134.0%。

**Q9：自我改進設定的實驗流程與技能成長情況為何？**
A：研究者將 Terminal-Bench 2.0 的任務組織成多個迭代，每個迭代內的所有任務共享同一個固定框架狀態，且執行過程中不提供基準回饋。每個迭代結束後，框架會保留成功執行中提煉出的技能，供下一個迭代使用。隨著迭代推進，可重複使用的技能庫分別成長了 21 個與 31 個技能，顯示出持續累積經驗的效果。

**Q10：PILOT 在哪些實務場景中最具價值？**
A：PILOT 特別適合需要長時間執行且容易偏離目標的場景，例如終端自動化、軟體工程任務、資料分析流程或科學研究助理。在這些場景中，工作者可能會陷入重複錯誤、選擇低效策略或忽略專案慣例，監督器的即時引導能夠及時糾正方向。此外，即時自我演化累積的技能與記憶可以讓後續類似任務執行得更穩定、更省詞元。

**Q11：部署 PILOT 時需要考慮哪些產品層面問題？**
A：首先必須確保監督器與工作者之間的即時通道具備低延遲與高可靠性，否則引導動作可能錯過最佳介入時機。其次，需要設計合理的並發管理、持久框架儲存與版本控制，以便多個工作者能正確載入更新後的技能與記憶。最後，監督器擁有中止與重新導向的權限，必須評估其安全性與對使用者體驗的影響，並在成本節省與系統複雜度之間取得平衡。

**Q12：PILOT 可能對智慧體自我改進領域帶來什麼影響？**
A：PILOT 將研究典範從執行結束後的反思與評判，轉向執行過程中的閉迴路即時自我改進。它證明了把執行角色與自我改進角色分離、並透過即時通道持續互動，可以同時提升成功率與詞元效率。這可能啟發未來更多具備專屬監督器角色、持久技能庫與即時干預能力的智慧體架構設計。

**Q13：PILOT 的設計隱含哪些限制？**
A：監督器本身也是凍結模型，其診斷與引導能力受限於預訓練知識與提示設計，未必能正確理解所有複雜執行情境。此外，即時引導的效果部分依賴工作者主動傳送通知與問題，若工作者回報不完整，監督器可能錯過關鍵時機。目前評估主要集中在終端指令類基準，對於更廣泛的多模態或開放式長程任務，其通用性仍需進一步驗證。

**Q14：PILOT 仍可能出現哪些失敗案例？**
A：監督器可能誤判執行狀態，給出錯誤的引導方向，反而讓工作者離目標更遠。工作者也可能忽略或誤解監督器的指令，導致修正無法生效。另外，持久框架若持續累積低品質或過時的技能與記憶，可能產生雜訊，影響後續執行的判斷，因此需要有效的技能篩選與遺忘機制。

**Q15：未來可以朝哪些方向延伸 PILOT？**
A：未來可以針對監督器進行微調或強化學習，使其更擅長即時診斷與決策，並學會自適應地決定何時介入。也可以探索多層級監督器架構、更聰明的工作者通知策略，以及結合世界模型進行前瞻性風險預測。此外，將即時自我改進機制擴展到終端以外的領域，例如網頁操作、機器人控制或多人協作流程，並建立線上技能驗證與淘汰機制，都是值得研究的方向。

## 實務應用指南

### 適用場景

1. **長時間終端指令與 DevOps 自動化**  
   在需要連續執行多步 shell 指令、讀取日誌、排查錯誤的場景中，PILOT 的監督器可即時發現工作者走錯分支或陷入無效重試，並即時重新導向，避免整批 CI/CD 流程或基礎設施巡檢任務失敗。

2. **複雜軟體開發與程式碼重構**  
   當智慧體需要跨檔案修改、執行測試、修復編譯錯誤時，監督器可在工作者執行期間偵測策略偏離（例如選錯重構方向），即時中止或給予新任務，並把成功程序提煉為可重複使用技能，供後續類似任務使用。

3. **多步驟資料分析與科學實驗管線**  
   在資料清理、特徵工程、模型訓練與評估的長程流程中，監督器可監控中間結果與異常，即時調整分析策略；同時將有效的分析程序與常見資料陷阱記錄到持久框架，提升後續實驗效率。

4. **企業流程自動化與客服決策輔助**  
   面對需要查詢多個內部系統、遵循專案慣例並逐步收斂答案的任務，PILOT 可讓監督器在工作者偏離公司規範或客戶需求時即時介入，並把正確流程與常見錯誤模式沉澱為組織記憶。

5. **持續學習的自主研究助理**  
   在文獻綜述、實驗設計迭代或報告撰寫等長期專案中，監督器可根據新興經驗即時修正研究方向，並把已驗證有效的研究方法與失敗模式寫入持久框架，形成可累積的知識資產。

### 實作前置條件

| 類別 | 需求說明 |
|---|---|
| **資料** | 需要可執行的長程任務軌跡資料，包括動作、環境觀察、執行錯誤與最終結果；同時需要領域相關的技能與記憶範本，以便初始化持久框架。 |
| **運算** | 至少兩個可獨立運行的模型上下文：一個給工作者執行任務，一個給監督器進行診斷與引導。兩者通常共用同一凍結骨幹模型，但需支援長上下文與即時事件串流。 |
| **技能** | 團隊需熟悉提示工程、代理架構設計、事件驅動系統與狀態持久化；若涉及終端或程式碼執行，還需具備沙箱環境建置與安全隔離經驗。 |
| **基礎設施** | 需要可讓監督器與工作者保持即時連線的通道（例如 WebSocket、訊息佇列），以及儲存技能庫與記憶的資料庫或向量儲存。 |

### 實作步驟建議

1. **定義監督器與工作者的角色分離**  
   將任務執行邏輯放入工作者，讓其專注於觀察、工具呼叫與行動；監督器則專注於目標、近期事件、風險判斷與重新導向，避免兩者上下文互相干擾。

2. **建立即時雙向通道**  
   實作工作者到監督器的通知、問題與結果事件，以及監督器到工作者的引導與中止指令。確保監督器能在工作者執行期間持續接收事件，而非僅在執行結束後取得摘要。

3. **設計監督器的決策觸發條件**  
   定義何時該介入：例如長時間無進度、反覆出現相同錯誤、偏離目標、產生潛在風險或工作者主動提問。這些條件應可配置，以平衡即時修正與過度干預。

4. **建置持久框架與技能庫**  
   將成功程序、專案慣例與失敗模式以結構化方式儲存，並讓後續工作者在啟動時載入。技能應包含適用條件、執行步驟與預期結果，方便監督器在適當時機推薦。

5. **實作即時自我演化機制**  
   在監督器介入並確認修正有效後，自動或半自動地將新提煉出的技能與記憶寫入持久框架。建議先經過簡單驗證（例如在下一次類似任務中載入），再正式納入框架。

6. **迭代評估與效率監控**  
   追蹤通過率、平均輸出詞元數、每百萬輸出詞元的成功評估次數等指標，並定期檢視新增技能是否真正被後續執行使用，避免框架膨脹。

### 潛在風險與注意事項

| 風險 | 說明與因應 |
|---|---|
| **過度干預導致工作者失去自主性** | 監督器若頻繁介入，可能讓工作者無法探索替代方案。應設定介入門檻，並讓工作者保留一定試錯空間。 |
| **監督器上下文過載** | 長程任務產生大量事件，監督器可能難以聚焦。可透過事件摘要、滑動窗口或只讀取關鍵片段來維持上下文清晰。 |
| **技能庫膨脹與品質下降** | 自動提煉的技能可能包含錯誤或未經驗證的知識。建議加入人工或自動驗證機制，並定期清理低使用率項目。 |
| **即時通道延遲影響效能** | 若監督器決策過慢，可能錯過最佳介入時機。需評估通道延遲，並在監督器端設計輕量級快速決策路徑。 |
| **安全與權限控管** | 工作者常在沙箱中執行指令，監督器的中止與重新導向權限需嚴格控管，避免惡意或錯誤指令造成資料損毀。 |
| **無法取得即時基準回饋** | 在自我改進設定中，執行期間沒有基準測試回饋，因此監督器必須依靠環境觀察與內部一致性來判斷是否介入。 |

### 與其他技術的整合建議

- **與現有 ReAct / Toolformer 代理整合**：可將現有單一代理改裝為 PILOT 工作者，保留其工具使用邏輯，再外掛監督器與即時通道，無需重新訓練模型。
- **與向量資料庫 / RAG 系統整合**：將技能庫與記憶儲存於向量資料庫，讓監督器與工作者在執行期間根據任務相似度檢索相關技能，強化即時引導。
- **與 CI/CD 與可觀測性平台整合**：把監督器的事件流接入現有日誌、追蹤與告警系統，讓開發團隊能視覺化長程任務的執行軌跡與介入點。
- **與評判式評估（Judge-based Evaluation）整合**：雖然 PILOT 強調即時改進，但仍可在執行結束後使用評判者進行最終品質確認，並將結果回饋給監督器作為長期學習信號。
- **與多代理協作框架整合**：PILOT 的監督器可視為一種輕量級協調層，與現有子代理委派機制並行，負責監控與即時修正，而非取代既有分工。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於圖 2 與「監督器—工作者」角色的直覺理解：把 PILOT 想像成一位在旁即時指導的教練，能在學員（工作者）做錯時立刻糾正，並把有用的方法記下來供下次使用。不必一開始就深入技術細節，重點是理解「即時」與「分離」這兩個核心概念。

**AI 工程師**  
建議仔細閱讀第 2 節的架構設計與附錄 A.2 的虛擬碼，特別關注即時通道的事件類型、監督器介入時機與持久框架的更新流程。實作時應優先驗證雙向通道的延遲與監督器上下文的裁剪策略，這兩點對產品化最為關鍵。

**研究人員**  
建議從「即時自我改進」這個問題形式化切入，思考其與事後檢討、反思、自我演化框架的理論區別。可進一步探討監督器最適介入理論、技能提煉的可靠性驗證，以及長期記憶累積對模型行為的影響。

**產品經理**  
建議把重點放在實驗結果與效率指標：PILOT 在 Terminal-Bench 2.0 上提升通過率同時降低平均輸出詞元數，代表它既能提升成功率也能降低成本。評估導入時應優先選擇失敗成本高、任務步驟長、且可明確定義成功與失敗訊號的場景作為試點。
