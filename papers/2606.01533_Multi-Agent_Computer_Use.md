## ⚡ TL;DR

現今單一序列電腦使用智慧體難以有效處理需分解、平行執行與持續重新規劃的複雜長程任務。
本文提出多智慧體電腦使用系統，由管理者模型以有向無環圖分解任務，並派遣平行子智慧體執行與動態修正。
在桌面與網頁基準測試中，該系統較強基線提升3.4%至25.5%成功率，並加快約1.5倍完成時間。

## 摘要翻譯

現今的電腦使用智慧體（Computer Use Agents, CUAs）大多以單一序列智慧體（single serial agent）的形式部署。這種架構對於能從任務分解（task decomposition）、平行執行（parallel execution），以及基於新資訊的持續重新規劃（re-planning）中受益的複雜長程任務（long-horizon tasks）而言並非最佳。在本文中，我們主張應轉向評估與建構多智慧體電腦使用（Multi-Agent Computer Use, MACU）系統。這類系統強調規劃與平行執行，能夠緩解許多單一智慧體 CUA 的不足。我們提出了一個通用的多智慧體架構，其中管理者模型（manager model）將電腦使用任務分解為有向無環圖（Directed Acyclic Graph, DAG），並在 DAG 中編碼子智慧體（subagents）所需的相關依賴關係（dependencies）與目標。在每個迭代（iteration）中，管理者模型分派平行的電腦使用子智慧體（CUA subagents）執行 DAG 就緒邊界（ready frontier）上的節點（nodes），並隨著子智慧體回傳的新發現持續修訂 DAG（新增、取消或重寫節點）。此設計將電腦使用的部分可觀測環境（partially observable environment）視為首要挑戰：下游智慧體（downstream agents）可能無法重新觀察到的資訊，會透過管理者與 DAG 結構保留並向前傳遞。我們證實，MACU 在桌面環境（OSWorld）與網頁導航（Online-Mind2Web、WebTailBench、Odysseys）基準測試（benchmarks）上，持續優於強大的單一智慧體基線（single-agent baselines）3.4% 至 25.5%，展現出更優異的測試時擴展（test-time scaling）特性，

## 深度分析

#### 方法論解析

MACU 的核心架構由一個管理者模型（manager model）與一組同質的電腦使用子智慧體（computer use subagents, CUA subagents）組成。管理者模型並非直接操作圖形使用者介面（Graphical User Interfaces, GUIs），而是維護並動態修改一個有向無環圖（Directed Acyclic Graph, DAG），其中每個節點（node）代表一個子任務（subtask），邊則編碼了子任務間的依賴關係（dependencies）。這種設計使得任務分解（task decomposition）的結構化表達成為可能，並為平行執行（parallel execution）提供了明確的排程語義。

在執行流程上，MACU 採用排程器迴圈（Scheduler Loop）與後續迴圈（Follow Up Loop）交錯運作。首先，管理者模型依據使用者以自然語言下達的指令，產生一個初始的 DAG，此時的計畫本質上是一個最佳猜測假說（best-guess hypothesis），因為電腦使用環境屬於部分可觀測環境（partially observable environment），初始資訊必然不完整。接著，系統辨識出就緒邊界（ready frontier）——即所有前置依賴皆已滿足的節點集合——並將這些子任務分派給虛擬機池（Virtual Machines Pool）中閒置的電腦使用子智慧體平行執行。每個子智慧體在獨立的虛擬機（VM）上運作，確保狀態（state）隔離，避免彼此干擾。

當子智慧體完成任務後，其產出的交付成果（deliverables）與觀測到的環境資訊（例如檔案系統（filesystem）變更、登入 Cookie（login cookies）、動態內容（dynamic content）等）會回傳給管理者模型。此時進入重新規劃（re-planning）階段：管理者模型根據新取得的資訊，對 DAG 進行結構性調整，包括新增節點、取消無效節點、重新連線（rewire）依賴路徑，或重寫待處理子任務（pending subtasks）的指令（instructions）。這種迭代（iteration）機制直接回應了電腦使用領域的核心挑戰：許多狀態資訊（如背景處理程序（background processes）、開啟的瀏覽器分頁（open browser tabs））一旦錯過便無法被下游智慧體（downstream agents）重新觀測，因此必須透過管理者模型與 DAG 結構顯式地保留並向前傳遞。

值得注意的是，MACU 在設計上刻意保持極簡：全系統僅有兩種智慧體——負責規劃的管理者模型，以及一群基於相同骨幹模型（backbone）的同質工作者。所有子智慧體皆使用相同的 CUA 骨幹，不區分專長模組。這種同質性讓 MACU 能直接受益於未來任何單一電腦使用智慧體（CUA）的技術進步，因為進步的模型可無縫替換為更強大的子智慧體，而無需重構編排（orchestrating）邏輯。

#### 實驗數據解讀

本研究在桌面與網頁導航兩大類基準測試（benchmarks）上進行評估，涵蓋 OSWorld（桌面環境）、Online-Mind2Web、WebTailBench-v2 與 Odysseys（長期網頁導航）。相較於強大的單一序列智慧體（single serial agent）基線（baselines），MACU 在所有測試集上均取得一致且顯著的提升：OSWorld 提升 4.7%、Online-Mind2Web 提升 3.4%、WebTailBench-v2 提升 8.7%，而在長程任務（long-horizon tasks）導向的 Odysseys 上更是大幅提升 25.5%。

這組數據揭示了幾個重要現象。首先，任務的時間跨度與複雜度與 MACU 的增益呈強正相關：在 Odysseys 這類基於真實人類瀏覽模式、需要長時間多步驟執行的任務中，單一序列智慧體容易因為累積錯誤或陷入局部狀態而卡住，而 MACU 透過任務分解與動態重新規劃，能夠在任務後期修正前期錯誤，因此長程任務的邊際效益最大。其次，在 WebTailBench-v2 這類包含跨網站與多步驟任務的基準測試上，8.7% 的提升顯示平行執行對於需要等待外部頁面載入或查詢多個資訊來源的任務特別有效。

除了任務完成率（task completion）的提升，MACU 在牆面時間（wall-clock time）上也展現優勢。在 Odysseys 上，平均任務完成的牆面時間縮短了約 1.5 倍；在 OSWorld 上亦有顯著改善。這證明了多智慧體平行化不僅提升成功率，也能實際加速傳統上緩慢的 CUA 管線。對於需要部署在真實環境的電腦使用智慧體（CUA）而言，時間效率與成功率同等重要。

此外，MACU 展現出更有利的測試時擴展（test-time scaling）特性。當增加推論階段的運算資源（例如允許更多迭代或更多平行子智慧體）時，MACU 的效能曲線優於單一智慧體，這暗示多智慧體協調（multi-agent coordination）是一條有潛力的擴展軸線，能讓電腦使用系統在更長、更複雜的任務上持續受益於額外運算。研究中的詳細消融實驗（ablations）也指出，管理者模型對 DAG 的動態修改能力（而非僅靜態分解）是效能的關鍵來源。

#### 與現有研究的比較

在定位上，MACU 與現有文獻存在數個根本性差異。首先，相較於當前主流的單一序列智慧體（single serial agent）典範——無論是 GPT-5.4、Opus 4.6 或 Kimi K2.6 等前沿模型在 OSWorld 等基準測試上的部署方式——MACU 首次系統性地將多智慧體協調引入通用電腦使用（computer use）領域，並將部分可觀測環境（partially observable environment）視為首要考量（first-class consideration）。過往的單一智慧體在面對長程任務時缺乏有效的回溯與重規劃機制，而 MACU 透過 DAG 的顯式結構與管理者模型的持續介入，解決了這一瓶頸。

與先前的多智慧體大型語言模型（Large Language Models, LLMs）系統相比，例如軟體工程（SWE）領域的程式編寫智慧體（coding agents）、數學或科學發現系統，這些工作大多在完全可觀測的文字環境中運作（如程式碼、符號數學式），並且常採用異質化的專家子模組（例如專門的工具使用（tool use）模組或驗證器）。MACU 則針對 GUI 互動的獨特性：狀態包含檔案系統、背景處理程序、動態內容等，且許多資訊無法被下游智慧體重新觀察。因此，MACU 不採用專業分工的異質子智慧體，而是使用同質的電腦使用子智慧體（computer use subagents），透過管理者模型統一處理資訊傳遞與狀態保留，大幅簡化了系統複雜度。

在電腦使用智慧體的文獻中，近期亦有動態重新規劃（dynamic replanning）的探索，例如基於樹狀搜尋（tree search）的 lookahead 與回溯 [18]、即時歸納程式化技能 [36]、或階層式規劃 [3]。然而，這些方法本質上仍是序列式的探索，缺乏 MACU 的平行執行能力。另一方面，Agent S2 [1]、CoAct-1 [33] 等系統雖然也採用管理者-工作者架構，但它們傾向於將任務委派給專門的 GUI 操作員或程式碼智慧體（code agent），形成了異質管線。MACU 證明僅需同質子智慧體與 DAG 編排，即可超越這些更複雜的專業化設計，這對於系統的可擴展性與維護性是一大優勢。

然而，MACU 也存在若干侷限。由於所有子任務的品質與 DAG 的結構正確性高度依賴管理者模型，若管理者在初始分解或中期重新連線時產生邏輯錯誤，錯誤會透過 DAG 傳播至多個子智慧體。此外，對於極簡單的短程任務，建立 DAG 與虛擬機池的開銷可能反而不如單一智慧體直接執行來得經濟。最後，雖然 MACU 簡化了子智慧體的設計，但管理者模型需要同時具備規劃、依賴推理與部分可觀測狀態追蹤的能力，這對目前 LLM 的長上下文與結構化推理能力仍是一大考驗。

#### 可重現性評估

本研究在可重現性（reproducibility）方面採取了相對開放的策略。作者已於 https://jykoh.com/multi-agent-computer-use 公開所有程式碼（code）與互動式視覺化（interactive visualizations），這讓其他研究者能夠檢視 DAG 的建構邏輯、管理者模型的提示設計（prompt design）以及子智慧體的執行流程。實驗所使用的基準測試（benchmarks）——包括 OSWorld、Online-Mind2Web、WebTailBench-v2 與 Odysseys——皆為已發表的公開資料集，降低了資料取得的門檻。

然而，可重現性仍面臨幾項挑戰。首先，論文中提及的強大單一智慧體基線（baselines）與 MACU 的子智慧體骨幹模型（backbone）多為前沿的專有模型（如 GPT-5.4、Opus 4.6、Kimi K2.6 等），這些模型的權重（model weights）並未公開，且其行為可能隨供應商更新而變化。若研究者無法取得相同版本或同等能力的模型，將難以完全復現論文報告的絕對數值。其次，MACU 需要同時運行多個虛擬機（Virtual Machines）以隔離平行子智慧體的執行環境，這對運算資源（如記憶體、CPU/GPU、授權）有較高需求，可能超出部分學術實驗室的硬體預算。儘管如此，由於框架本身不依賴特殊硬體或專屬 API，理論上可使用開源權重模型（如 Qwen3.5、MolmoWeb 等 4–9B 參數等級模型）作為骨幹進行復現，這為資源有限的研究者保留了可行性。

#### 未來研究方向

MACU 的提出為多智慧體電腦使用（multi-agent computer use）開闢了多條值得深入探索的路徑。第一，管理者模型（manager model）的強化是當務之急。目前的 DAG 規劃與重新連線（rewire）依賴通用 LLM 的推理能力，未來可研究專門的微調模型或結構化輸出機制，以提升管理者在長程任務中進行依賴關係（dependencies）推理與衝突偵測的準確率，甚至引入形式化驗證確保 DAG 的語義正確性。

第二，最適平行度（optimal parallelism）的決策機制仍有待研究。MACU 目前由管理者模型決定哪些就緒邊界（ready frontier）節點可以平行執行，但過度平行可能導致資源浪費或環境狀態競爭（例如多個子智慧體同時修改同一檔案系統（filesystem）區域）。未來可發展自適應排程演算法，根據子任務的資源需求與環境狀態動態調整虛擬機池（Virtual Machines Pool）的大小與任務分派策略。

第三，部分可觀測環境（partially observable environment）下的記憶體機制可進一步強化。雖然 MACU 透過管理者模型與 DAG 保留了部分觀測資訊，但對於極長任務，管理者上下文可能不足以容納所有歷史交付成果（deliverables）。引入外部記憶體（如向量資料庫或結構化日誌）讓下游智慧體（downstream agents）能按需檢索過往狀態，將是提升長程穩定性的關鍵。

第四，異質性（heterogeneity）的適度引入。MACU 目前證明同質子智慧體已足夠強大，但未來可在保持 DAG 編排框架的前提下，讓特定節點由具備特殊能力的子智慧體執行（例如專精程式碼生成的 code agent 或具備視覺強化能力的視覺-語言模型），以處理更廣泛的跨領域任務，同時避免過度複雜化系統。

最後，測試時擴展（test-time scaling）與成本效益（cost-efficiency）的權衡值得深究。MACU 展現了有利的擴展趨勢，但多智慧體平行執行必然增加 API 呼叫與運算成本。未來研究可建立明確的成本-效能帕雷托邊界（Pareto frontier），發展早期終止機制或子任務結果快取策略，讓 MACU 在實際部署時能根據預算與任務難度自動調整運算投入。

## 論文問答

**Q1：單一序列電腦使用智慧體在處理複雜任務時存在什麼根本問題？**
A：現有的電腦使用智慧體大多以單一序列形式部署，這種架構在面對複雜的長程任務時顯得次優。這類任務通常需要任務分解、平行執行以及根據新資訊持續重新規劃，但單一智慧體難以同時滿足這些需求。因此，當任務涉及多個環節且需要動態調整時，單一序列智慧體容易陷入瓶頸，無法有效完成目標。

**Q2：為什麼現有的單一智慧體方法難以應對電腦使用場景中的部分可觀測性挑戰？**
A：電腦使用環境具有高度的部分可觀測性，因為作業系統的狀態包含檔案系統、背景處理程序、瀏覽器分頁和登入 Cookie 等眾多動態元素。單一序列智慧體在執行過程中，往往無法保留下游智慧體可能無法重新觀察到的關鍵資訊，導致資訊在傳遞過程中遺失。這使得後續步驟難以基於完整的上下文做出正確決策，進而影響長程任務的成功率。

**Q3：為何多智慧體協調被視為擴展電腦使用智慧體的關鍵軸線？**
A：多智慧體協調能夠同時解決任務分解、平行執行與動態重新規劃等核心挑戰，這些都是單一智慧體難以兼顧的面向。透過管理者模型持續迭代與調度，系統能夠在測試時擴展運算資源以獲得更佳效能，展現出更有利的擴展趨勢。這種架構讓智慧體能夠在更長的時間跨度內保持高效運作，為處理更複雜的實際工作流程奠定基礎。

**Q4：MACU 的核心架構與運作流程為何？**
A：MACU 採用一個管理者模型來協調多個同質的電腦使用子智慧體，其核心是將任務分解為有向無環圖（DAG）。管理者首先根據自然語言指令產生初始的 DAG 分解，將任務劃分為多個子任務節點並編碼彼此間的依賴關係。在每次迭代中，管理者會將就緒邊界上的節點平行分派給子智慧體執行，並根據子智慧體回傳的新發現持續修訂 DAG，包括新增、取消或重寫待處理節點。

**Q5：MACU 如何將部分可觀測環境視為首要考量，並據此設計資訊傳遞機制？**
A：MACU 明確將電腦使用中的部分可觀測性視為一等挑戰，而非假設環境完全可觀測。系統設計讓管理者與 DAG 結構成為資訊保留與傳遞的樞紐，確保下游子智慧體可能無法重新觀察到的關鍵資訊能夠被保留並向前傳遞。此外，管理者將初始計畫視為一個最佳猜測假說，隨著子智慧體回傳的新資訊不斷修正，使系統能夠適應動態變化的環境狀態。

**Q6：相較於先前的多智慧體研究，MACU 在設計上有哪些關鍵區別與簡化？**
A：與許多依賴專門化模型或模組的先期研究不同，MACU 僅使用兩種類型的智慧體：一個規劃管理者與一組同質的子智慧體工作者。所有子智慧體都基於相同的 CUA 骨幹模型，執行由管理者產生的指令，這使得架構極為簡潔且易於擴展。這種設計讓 MACU 能夠直接受益於未來 CUA 模型的進步，無需開發特殊的專家模組即可應用於一般的電腦使用場景。

**Q7：MACU 在哪些基準測試上進行評估，且相較於單一智慧體基線取得了什麼成果？**
A：研究團隊在桌面環境的 OSWorld 以及網頁導航的 Online-Mind2Web、WebTailBench-v2 和 Odysseys 等多個基準測試上進行評估。實驗結果顯示，MACU 相較於強大的單一智慧體基線，成功率分別提升了 4.7%、3.4%、8.7% 與 25.5%。此外，在 Odysseys 這類長程網頁導航基準上，MACU 將平均任務完成的牆面時間縮短了約 1.5 倍，顯著加快了傳統上較慢的 CUA 流程。

**Q8：MACU 在測試時擴展（test-time scaling）方面展現出什麼優勢？**
A：MACU 展現出比單一智慧體基線更有利的測試時擴展趨勢，意味著在推論階段增加運算資源能夠帶來更顯著的效能提升。具體而言，MACU 能夠解決許多讓單一智慧體陷入停滯的複雜長程任務，顯示其具備更強的容錯與回溯能力。這項特性對於需要長時間執行的實際應用尤為重要，因為它證明多智慧體協調是有效擴展電腦使用智慧體運算規模的可靠途徑。

**Q9：根據論文的消融實驗與分析，哪些設計選擇對於最大化 MACU 的效能至關重要？**
A：論文透過詳細的消融實驗分析 MACU 的各項設計，指出管理者動態修訂 DAG 的能力對於適應部分可觀測環境至關重要。明確在有向無環圖中編碼子任務間的依賴關係，並僅在就緒邊界上啟動平行執行，能夠在提升效率的同時維持執行順序的正確性。這些設計選擇共同確保了系統在面對複雜長程任務時，既能充分利用平行化優勢，又能妥善處理動態出現的新資訊與不確定性。

**Q10：MACU 最適合應用於哪些實際場景？**
A：MACU 特別適合需要跨應用程式協作、多步驟網頁導航以及長時間執行的複雜工作流程。例如，同時需要在多個網站間蒐集資料、整理檔案系統並撰寫報告的任務，便能受益於其任務分解與平行執行的能力。對於那些涉及動態內容且中間狀態難以重新取得的電腦操作，MACU 透過管理者保留關鍵資訊的機制，能夠顯著提升完成任務的可靠性。

**Q11：在產品化部署方面，MACU 的架構設計帶來哪些實務上的優勢？**
A：MACU 的架構設計極為簡潔，僅需一個管理者模型與多個同質子智慧體，無需訓練或維護多種專門化模型，大幅降低了系統複雜度與部署成本。由於所有子智慧體都基於相同的 CUA 骨幹模型，未來只要基礎模型效能提升，MACU 便能直接受惠，具備良好的技術迭代適應性。此外，系統在縮短牆面時間上的顯著成效，使其在實際產品中更具可用性，能夠為使用者提供更即時的互動體驗。

**Q12：這項研究對電腦使用智慧體領域可能帶來什麼深遠影響？**
A：這項研究為電腦使用智慧體的發展提供了新的典範轉移，從單一序列執行轉向多智慧體協調與平行執行。研究結果明確顯示，多智慧體架構不僅能提升成功率，還能改善測試時擴展行為與執行效率，為後續研究奠定了堅實基礎。這將激勵更多學者與工程師投入多智慧體電腦使用系統的開發，推動智慧體在真實世界中處理更長期、更複雜的任務。

**Q13：MACU 目前存在哪些潛在的限制或瓶頸？**
A：MACU 的效能高度依賴管理者模型的規劃與 DAG 修訂能力，若管理者產生錯誤的分解或無法正確解讀子智慧體的回饋，整體系統可能受到牽連。此外，對於極度簡單或本質上完全序列化的任務，維護多個虛擬機與子智慧體的開銷可能無法帶來相應的收益。目前架構中管理者作為單一協調點，雖然簡化了設計，但在面對超大規模任務時也可能成為潛在的瓶頸。

**Q14：MACU 可能在哪些情況下失效或表現不佳？**
A：當管理者無法正確識別任務中的依賴關係，導致 DAG 結構存在邏輯錯誤時，平行執行的子智慧體可能產生衝突或無效操作。如果子智慧體在執行過程中破壞了環境狀態且管理者未能及時察覺，後續節點可能基於錯誤的前提繼續執行。另外，對於那些幾乎沒有平行化空間、必須嚴格按順序完成的任務，MACU 的額外排程開銷可能使其表現不如精簡的單一智慧體。

**Q15：基於這項研究，未來有哪些值得探索的方向？**
A：未來研究可以進一步強化管理者模型的動態規劃能力，例如引入更精細的環境觀察機制或學習導向的 DAG 優化策略。另一個方向是探索在保持架構簡潔的前提下，適度引入專門化子智慧體來處理特定類型的低階操作，以結合通用性與專精性。此外，如何更有效地分配測試時的運算資源、減少子智慧體間的通訊延遲，以及將 MACU 框架擴展到更廣泛的部分可觀測環境，都是極具潛力的後續研究課題。

## 實務應用指南

### 適用場景

1. **企業跨系統財務結算**：同時操作 ERP、銀行網頁與試算表軟體，執行登入多個平台、下載報表、核對帳務、上傳憑證等長程任務，利用平行執行縮短月結牆面時間。
2. **電商營運與競品監控**：平行瀏覽多個電商網站進行比價、庫存檢查與截圖存證，再由管理者模型彙整分析報告，適合需頻繁重新規劃路徑的動態網頁環境。
3. **軟體發行與桌面環境測試**：在 Ubuntu 或 Windows 虛擬機池中，平行執行安裝套件、設定環境、執行測試腳本與檢查日誌，驗證多應用程式工作流程的正確性。
4. **長程網頁資料建檔**：從多個內部或外部網站依序（但部分可平行）擷取客戶資料、填寫表單、下載憑證，過程中需持續依據新資訊調整有向無環圖（DAG）節點。
5. **IT 維運事件排查**：同時監控多個儀表板與日誌系統，發現異常後由管理者模型動態分解排查步驟，派遣子智慧體平行執行根因分析與初步修復。

### 實作前置條件

- **資料**：目標任務的圖形使用者介面（GUI）操作流程影片或截圖序列、成功與失敗案例的軌跡資料、應用程式介面元素定位資訊（DOM 或 UI tree），以及用於驗證任務完成的評分準則。
- **運算**：可平行啟動多個隔離環境的虛擬機池（VM Pool）、足夠的 GPU/CPU 資源供多個電腦使用子智慧體同時推論、管理者模型的高階大型語言模型（LLM） API 配額與低延遲網路。
- **技術**：熟悉有向無環圖（DAG）編排與平行計算、具備大型語言模型提示工程能力、了解作業系統與網頁自動化框架（如 Playwright）、能處理部分可觀測環境的狀態管理與錯誤重試機制。

### 實作步驟建議

1. **基線評估與可平行化分析**：先以單一序列智慧體執行目標任務，記錄瓶頸步驟與可拆解為子任務的區段，識別子任務間的依賴關係。
2. **建構虛擬機池與觀測層**：部署隔離的 VM 環境作為虛擬機池，確保子智慧體間狀態不互相干擾，並建立截圖、檔案系統與瀏覽器狀態的擷取與快照機制。
3. **設計管理者模型與 DAG 結構**：定義節點格式（子任務指令、交付成果、依賴關係），實作 DAG 初始化、就緒邊界偵測，以及動態新增、取消、重寫或重新連線節點的邏輯。
4. **部署同質子智慧體池**：基於相同骨幹模型（如 Qwen3.5、MolmoWeb 或商用多模態 LLM）部署電腦使用子智慧體，確保它們能接收管理者指令並回傳結構化觀測結果。
5. **建立資訊保留與傳遞機制**：針對部分可觀測環境，設計機制讓下游子智慧體取得上游已結束任務的關鍵狀態（如登入 Cookie、檔案路徑、一次性驗證碼、截圖），避免資訊遺失。
6. **迭代優化與測試時擴展**：從靜態 DAG 開始驗證，逐步加入動態重新規劃能力，並透過增加子智慧體數量或管理者推理預算進行測試時擴展，監控成功率與牆面時間的權衡。

### 潛在風險與注意事項

1. **狀態競態與環境污染**：多個子智慧體若共用檔案系統或瀏覽器狀態可能產生衝突，必須透過 VM 隔離或明確的狀態鎖定機制緩解。
2. **管理者模型幻覺導致 DAG 錯誤**：管理者可能基於不完整資訊產生錯誤依賴關係，需加入驗證層檢查就緒邊界與子任務結果的一致性。
3. **部分可觀測性資訊遺失**：子任務結束後某些狀態（如彈出視窗、一次性驗證碼）可能無法重現，必須強制要求子智慧體在交付成果中保留這些不可重觀測資訊。
4. **成本與延遲爆炸**：平行執行雖能縮短牆面時間，但多個 VM 與 LLM 呼叫會增加總運算成本，需設定預算上限、超時機制與節點粒度下限。
5. **任務粒度失衡**：DAG 節點若切太細會增加管理者負擔，太粗則失去平行優勢，建議從 3–5 分鐘可完成的子任務為單位開始實驗。

### 與其他技術的整合建議

1. **RAG 與企業知識庫**：將內部系統操作手冊、常見錯誤排除文件建入向量資料庫，供管理者模型在重新規劃時檢索，提升 DAG 品質。
2. **傳統 RPA 工具**：對於穩定、規則明確的單步操作，可保留現有 RPA 腳本作為電腦使用子智慧體的「工具呼叫」，讓 MACU 專注於需要適應性與決策的複雜段落。
3. **可觀測性平台**：整合 LangSmith、Prometheus 或自訂追蹤系統，記錄每個 DAG 節點的執行軌跡、延遲與錯誤率，協助識別需重寫的瓶頸子任務。
4. **權限與零信任架構**：搭配 IAM 與細粒度 API 金鑰管理，確保每個子智慧體僅能存取其任務所需的最低權限資源，降低多代理並行時的資安風險。

### 給不同背景讀者的閱讀建議

- **初學者**：先理解單一電腦使用智慧體的運作原理，再將 MACU 想像為「一位專案經理（管理者模型）帶領多位實習生（子智慧體）同時作業」，重點關注有向無環圖（DAG）如何幫助分工與避免漏步驟，無需深入大型語言模型（LLM）架構細節。
- **AI 工程師**：著重實作 DAG 排程器與資訊傳遞機制，特別注意論文強調的「部分可觀測環境」處理——這是讓系統從玩具 demo 變成生產級工具的關鍵；建議從開源電腦使用骨幹模型（如 Qwen3.5、MolmoWeb）開始搭建同質子智慧體池。
- **研究人員**：關注 MACU 在測試時擴展（test-time scaling）的表現與長程任務的瓶頸分析，論文提供的消融實驗與基準測試結果（OSWorld、Odysseys）可作為未來多代理架構、動態重規劃演算法研究的起點。
- **產品經理**：聚焦「適用場景」與「牆面時間」效益，評估哪些內部流程最適合從單一自動化腳本升級為 MACU；注意成本結構會從「序列執行時間」轉為「平行運算資源」，需重新計算 ROI 並設計人機協作檢查點。
