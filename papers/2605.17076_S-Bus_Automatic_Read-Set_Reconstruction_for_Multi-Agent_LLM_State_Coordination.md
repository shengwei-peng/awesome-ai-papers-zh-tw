## 摘要翻譯

並發 LLM 智慧體在共享可變自然語言狀態時會產生結構性競態條件 (SRC)：寫入-寫入衝突與跨分片過時讀取衝突會靜默損壞智慧體輸出。現有多智慧體框架（LangGraph、CrewAI、AutoGen）未針對共享狀態提供寫入所有權語義。

本文提出 S-Bus，一個 HTTP 中介軟體，其核心機制為伺服器端 DeliveryLog（交付日誌）：一個逐智慧體的 HTTP GET 操作日誌，在 HTTP/1.1 下無須更改智慧體 SDK，即可於提交時刻自動重建每個智慧體的讀取集合。DeliveryLog 提供的一致性性質——可觀測讀取隔離 (ORI)，一種針對讀取集合之 HTTP 可觀測投影的部分因果一致性——可在智慧體透過共享分片協作時防止結構性競態條件。

三項貢獻：(C1) 基於 HTTP 流量自動重建讀取集合之 DeliveryLog 機制，並具備三層機械化驗證證據：讀取集合健全性 (ReadSetSoundness) 與 ORI 提交安全性 (ORICommitSafety) 已於 TLAPS 完成機器驗證（保留一條型別公理）；TLC 窮舉驗證至 N=3（20,763,484 個相異狀態，零違規）；Dafny 證成 9 條歸納健全性引理。(C2) 在共享分片爭用掃描中，針對 427,308 起 HTTP-409 衝突，於結構性衝突防止能力上與 PostgreSQL 17 SERIALIZABLE 及 Redis 7 WATCH/MULTI 達到實證等效：三個後端皆零 Type-I 損壞。(C3) ORI 的運作範圍為拓撲條件式：於專用分片工作負載中語義中性；於單分片協作寫入中則有害，因為保留傳播並發矛盾。

## 深度分析

#### 方法論解析

當 concurrent LLM agents（並發 LLM 智慧體）共享 mutable natural-language state（可變自然語言狀態）時，現有框架（LangGraph、CrewAI、AutoGen）缺乏 write-ownership semantics（寫入所有權語義），導致 Structural Race Conditions（結構性競態條件, SRCs）——包括 write-write conflicts（寫入-寫入衝突）與 cross-shard stale-read conflicts（跨分片過時讀取衝突）——在無預警的情況下污染智慧體輸出。S-Bus 的核心貢獻在於將此問題重新框定為「HTTP 可見事件追蹤（HTTP-visible event trace）的語法性質（syntactic property）」，從而迴避了「有效目標軌跡（valid goal trajectory）」這類難以操作化的語義循環定義。

S-Bus 是一個 HTTP middleware（HTTP 中介軟體），其伺服器端（server-side）機制為 DeliveryLog（交付日誌）：一個逐智慧體（per-agent）的 HTTP GET 操作日誌。該日誌利用 HTTP/1.1 連線層的 FIFO 順序（即論文假設 A1），在 commit time（提交時刻）自動重建每個智慧體的 read set（讀取集合），無需修改 agent SDK（智慧體 SDK）。這種 Automatic Read-Set Reconstruction（自動讀取集合重建）的關鍵在於，它將普通的 HTTP 流量轉化為可驗證的讀取證據，而非要求智慧體顯式宣告交易邊界。

S-Bus 提供的一致性性質為 Observable-Read Isolation（可觀測讀取隔離, ORI），這是一種 partial causal consistency（部分因果一致性），僅作用於 read set 的 HTTP-observable projection（HTTP 可觀測投影）。ORI 不保證完整可序列化或快照隔離，而是保證在專用分片拓撲（dedicated-shard topology）下，智慧體對 shared reference shards（共享參考分片）的讀取不會在提交時因跨分片過時而被靜默覆蓋。具體而言，當智慧體 α_i 提交其 shard 的差異（deltas δ_i）時，系統會比對其 DeliveryLog 中記錄的分片版本與當前版本；若發現預期版本（expected version）已因其他智慧體提交而改變（如動機範例中 db_schema 從版本 v=3 升至 v=4），則回傳 HTTP-409 衝突（HTTP-409 conflicts），強制重新讀取（re-read）並重新生成差異。

形式化證據分為三個層次，這是本文方法論可信度的支柱：
1. **TLAPS**：在 TLA+ 證明系統（TLAPS）中完成 687/687 項驗證義務（verification obligations），證明讀取集合健全性（ReadSetSoundness）與 ORI 提交安全性（ORICommitSafety），僅保留一條函數型別重建（FUNTYPINGRECONSTRUCTION）的基礎型別公理（typing axiom）。
2. **TLC**：TLA+ 模型檢查器（TLC）窮舉 N=3 的狀態空間達 20,763,484 個相異狀態（distinct states）、深度 28，以及 N=4 簡化組態的 2,811,301 個狀態、深度 24，皆零違規。
3. **Dafny**：以驗證導向程式語言 Dafny  discharge 9 條歸納健全性引理（inductive soundness lemmas），涵蓋 19 項驗證義務，確保抽象演算法（abstract algorithm）的歸納不變量成立。

從抽象演算法到 Rust 原始碼的實作細緻化（Implementation refinement）則屬經驗性驗證，非機械化證明，這是方法論上刻意保留的「信任邊界」——證明保證協議正確，而實作正確性依賴測試與審查。

值得批判性檢視的是，ORI 的效力嚴格受限於 HTTP 可觀測投影。若智慧體透過非 HTTP 管道（如外部 API、本地快取、提示內隱含知識）取得狀態，這些 hidden reads（隱藏讀取）無法被 DeliveryLog 捕捉。論文坦承此覆蓋率缺口（coverage gap），並將其量化為 R_hidden，這在方法論上是一項誠實且必要的風險揭露。

#### 實驗數據解讀

實驗設計圍繞三個軸線展開：形式化驗證的完備性、結構性衝突預防的實證強度，以及 ORI 在不同拓撲下的語義影響。

**讀取集合覆蓋率與語義提取限制**
在 PH-2 工作負載（PH-2 workload）中，HTTP 可觀測投影僅涵蓋 ≤70% 的實際讀取，R_hidden gap 高達 p_hidden = 0.739（CI 0.736–0.741）；PH-3 工作負載（PH-3 workload）中則降至 0.074（CI 0.061–0.081），顯示隱藏讀取比例高度依賴任務型態。儘管 DeliveryLog 的累積可觀測覆蓋率（DL-cumulative observable coverage）達到自稱引用（self-reported refs）的 99.8%，但智慧體的自稱引用存在 29%–37% 的過度聲稱率（over-claim rate），且語義提取召回率（semantic extraction recall）僅 0.59、精確率（precision）0.92（gpt-4o analyst）。這組數據揭示了一個深層張力：S-Bus 對「智慧體承認自己讀過什麼」幾乎無遺漏，但智慧體本身並不總是知道自己讀了什麼。方法論上，這意味著 ORI 的保證是「對 HTTP 可觀測行為完備」，而非「對智慧體認知狀態完備」。

**結構性衝突預防的實證強度**
在共享分片爭用掃描（shared-shard contention sweeps）中，S-Bus 與 PostgreSQL 17 SERIALIZABLE、Redis 7 WATCH/MULTI 兩個 OCC 後端（OCC backends）進行對照。在 427,308 次主動 HTTP-409 衝突（active HTTP-409 conflicts）與全掃描 884,110 次提交的條件下，三個後端的 Type-I 損壞（Type-I corruptions）皆為 0。以三法則（Rule-of-Three）估計，Type-I 損壞率上限為 7.0×10⁻⁶。這項結果極具份量：它證明即使 S-Bus 的 read set 重建是自動且部分覆蓋的，其在防止靜默結構性破壞（silent structural corruption）上與成熟資料庫的顯式 OCC 機制達到同等水準。這暗示在 multi-agent LLM state coordination（多智慧體 LLM 狀態協調）場景中，跨分片過時讀取（cross-shard stale-read）是 SRC 的主要來源，而這些讀取恰好高度 HTTP-可觀測（如共享的 db_schema 參考分片）。

**語義一致性與拓撲條件式效應**
實驗 WORKLOAD-B（Exp.WORKLOAD-B）針對非程式碼領域（資料管線架構規劃，data-pipeline architecture planning）進行測試。在 ORI 關閉（ORI-OFF）組態下，590/639 次提交為分歧提交（divergent commits）；ORI 開啟（ORI-ON）組態下則為 0/638，卡方檢定（χ²）= 1,094.98，p < 10⁻²⁴⁰。此結果顯示，防止結構性競態條件（structural race conditions）在實務上幾乎等價於防止語義軌跡發散——儘管形式化上 ORI 不保證語義正確性。

然而，實驗 DEDICATED-SHARD（Exp.DEDICATED-SHARD, n=600）與實驗 SHARED-STATE（Exp.SHARED-STATE）揭示了 ORI 的運作範圍（operating envelope）是拓撲條件式（topology-conditional）的。在專用分片工作負載（dedicated-shard workloads）中，ORI 語義中性（semantically neutral）；但在單分片協作寫入（single-shard collaborative writing）中，ORI 反而有害，因為保留傳播並發矛盾（preservation propagates concurrent contradictions）。這項「負面結果」極大地增強了論文的科學嚴謹性：它明確劃定了 S-Bus 的適用邊界，避免讀者將結構性衝突預防誤解為萬靈丹。

#### 與現有研究的比較

現有多智慧體框架（LangGraph、CrewAI、AutoGen）將自然語言狀態（NL state）視為無結構字串，未提供任何並行控制或寫入所有權語義（write-ownership semantics）。在這些框架中，共享狀態（shared state）的協調通常依賴順序式管線或外部人類介入，無法處理並發 LLM 智慧體（concurrent LLM agents）同時讀寫 mutable natural-language state 的場景。S-Bus 填補了此空白，首次將樂觀並行控制（Optimistic Concurrency Control, OCC）引入 LLM 智慧體的共享狀態管理，且無需修改智慧體 SDK。

與傳統資料庫後端的比較更具細微差別。PostgreSQL 17 SERIALIZABLE 與 Redis 7 WATCH/MULTI 均提供成熟的 OCC 保證，但它們要求客戶端顯式宣告讀取集合或交易邊界。S-Bus 的獨特性在於 Automatic Read-Set Reconstruction（自動讀取集合重建）：它完全從 HTTP 流量推導讀取集合，對智慧體透明。這大幅降低了整合門檻——任何透過 HTTP/1.1 存取狀態的智慧體都能自動獲得 ORI 保護——但代價是僅能觀測 HTTP 可觀測投影（HTTP-observable projection），無法捕捉隱藏讀取（hidden reads）。相較於資料庫交易的「完整讀取集合」模型，S-Bus 是一種「夠好且輕量」的折衷。

形式化方法層面，本文的三層次機械化證據（TLAPS、TLC、Dafny）在 multi-agent LLM 系統文獻中屬於少見的高標準。多數相關研究僅提供概念驗證或經驗測試，而 S-Bus 對抽象演算法（abstract algorithm）的 read-set monotonicity 與 cross-shard equality 提供了可機械檢驗的證明。然而，實作細緻化（Implementation refinement）至 Rust 的過程並未機械化驗證，這與 seL4 或 CompCert 等完整細緻化專案相比仍有距離。

本文的主要限制在於其狹義的運作範圍（operating envelope）。專用分片拓撲（dedicated-shard topology）——每個智慧體擁有獨特的寫入鍵（write key）並僅讀取共享參考分片（shared reference shards）——是 ORI 的設計前提。單分片協作寫入（single-shard collaborative writing）不僅未被支援，更被證明為有害。此外，系統依賴 HTTP/1.1 的連線層 FIFO（假設 A1），HTTP/2 的多工（multiplexing）會破壞此假設，需額外的反向代理釘選或顯式 ARSI-mode 宣告。最後，形式化證明僅保證結構正確性；智慧體語義正確性（agent semantic correctness）仍是依模型而定的問題（model-dependent question），需仰賴 LLM 評審評分標準（LLM-as-judge rubric）與人類語義評估（human semantic evaluation）。

#### 可重現性評估

原始碼已開源於 https://github.com/sajjadanwar0/sbus，提供 Rust 實作的 HTTP 中介軟體（HTTP middleware）核心邏輯，這是正向的可重現性基礎。然而，論文提供的全文脈絡中，未明確說明是否一併釋出以下關鍵資產：
- PH-2/PH-3 評估（PH-2/PH-3 evaluation）所使用的 2,100 筆步驟日誌（step-logs）；
- 實驗 WORKLOAD-B（Exp.WORKLOAD-B）的 80 筆領域資料與提示設計；
- TLAPS/TLA+/Dafny 的完整證明腳本與規格檔案（雖然論文詳細記載了驗證義務數量與 TLC 狀態空間規模）。

實驗的可重現性（reproducibility）面臨一項結構性障礙：評估高度依賴專有模型 gpt-4o-mini 與 gpt-4o，這些 API 具有非確定性（nondeterminism）與版本漂移風險。即使原始碼與提示固定，不同時間點的 API 回應可能導致不同的 step-logs 與語義提取結果，使得精確重現 PH-2/PH-3 的 R_hidden 與語義提取召回率（semantic extraction recall）成為挑戰。SWE-bench 任務雖為公開基準，但多智慧體協調的分片指派策略、提示工程細節與超參數設定，仍需從原始碼或文件中仔細推導。

整體而言，S-Bus 的核心機制（DeliveryLog、ORI 驗證協議）與後端比較實驗（PostgreSQL、Redis）具備良好的可重現性；但涉及 LLM 語義評估的完整管線，其可重現性受限於封閉式 LLM 服務的固有特性與部分評估資料的釋出程度。

#### 未來研究方向

1. **適應性合併路由（adaptive merge-routing）**：論文已指出單分片協作寫入（single-shard collaborative writing）中 ORI 的負面效應，並提及一項調適性合併路由擴充正在獨立開發中。未來研究可探索如何將自動讀取集合重建（Automatic Read-Set Reconstruction）與差異合併策略（如基於 LLM 的語義合併或 CRDT 風格的 NL state 整合）結合，使單分片場景從「拒絕並發」轉向「有條件地消解並發矛盾」。

2. **HTTP/2 與 HTTP/3 支援**：目前系統依賴 HTTP/1.1 的 FIFO-per-connection 假設 A1。未來需發展反向代理釘選（reverse-proxy pinning）或顯式 ARSI-mode 讀取集合宣告機制，以在現代 HTTP 多工環境下維持 ORI 的因果順序保證，這是工程部署上的必要演進。

3. **縮小隱藏讀取缺口（R_hidden gap）**：PH-2 工作負載中 73.9% 的隱藏讀取比例顯示，純 HTTP 流量重建存在根本限制。未來可研究混合式重建：結合 DeliveryLog 與輕量級智慧體側插樁（如提示層的自我報告或函數呼叫攔截），在不破壞「無需修改 agent SDK」承諾的前提下，提升語義提取召回率（semantic extraction recall）。

4. **分散式正確性（distributed correctness）**：目前的形式化證明聚焦於抽象演算法的內部一致性。論文提及 TLC Raft（3-node abstract）探索了 247,000 個狀態，但未完整整合進主要證明。未來可將 TLAPS/TLC 的驗證擴展至完整分散式共識與複製協議，彌補目前聲稱的「分散式正確性缺口（distributed-correctness gap）」。

5. **跨領域驗證與人類語義評估**：論文明確指出，轉移至客戶服務（customer service）、科學綜合（scientific synthesis）等領域需要獨立評估，因為 p_hidden 可能不同。未來應建立標準化的跨領域評估套件，並以人類語義評估（human semantic evaluation）補強 LLM 評審評分標準（LLM-as-judge rubric），特別是在判定自然語言狀態（NL state）的目標軌跡（goal trajectory）是否 coherent 時。

6. **動態拓撲偵測與自動降級**：既然 ORI 的運作範圍（operating envelope）是拓撲條件式（topology-conditional），未來可研究執行期拓撲偵測機制，在偵測到單分片協作寫入模式時自動切換至序列化或合併模式，避免保留傳播並發矛盾（preservation propagates concurrent contradictions）。

## 論文問答

**Q1：什麼是 S-Bus 試圖解決的核心問題？**
A：S-Bus 針對的是並發 LLM 智慧體在共享可變自然語言狀態時所產生的結構性競態條件（SRCs）。這類衝突包含寫入-寫入衝突以及跨分片過時讀取衝突，會在無預警的情況下腐蝕智慧體的輸出品質。與傳統程式設計中的競態條件不同，SRCs 是純粹語法性質，可從 HTTP 可見事件追蹤中判定，且現有多智慧體框架如 LangGraph、CrewAI 與 AutoGen 皆未提供共享自然語言狀態的寫入所有權語義，使得衝突無法被偵測與預防。

**Q2：為何現有多智慧體框架無法防止 SRCs？**
A：現有框架如 LangGraph、CrewAI 與 AutoGen 雖然支援智慧體間的狀態共享，但它們完全缺乏針對自然語言狀態的寫入所有權語義與樂觀並行控制機制。這表示多個智慧體可以同時讀取同一分片的相同版本，各自產生差異更新後直接提交，而系統不會驗證其讀取集合是否已過時，導致後提交的智慧體無聲覆蓋先提交者的結果。這種缺乏跨分片驗證步驟的設計，使得過時讀取所引發的結構性競態條件無法被偵測，最終產生內部一致但實際錯誤的輸出。

**Q3：為何在多智慧體 LLM 系統中特別需要解決 SRCs？**
A：在多智慧體協作場景中，智慧體經常需要讀取共享的參考分片（如資料庫架構描述）來產生各自負責的輸出，一旦參考狀態在讀取後被其他智慧體更新，後續基於舊版本產生的差異就會導致整體狀態語意不一致。由於自然語言狀態缺乏像傳統資料庫欄位那樣的嚴格結構化語義，這種「結構性」腐蝕往往不會觸發任何執行期錯誤，而是靜默地污染最終結果。因此，若無法在 HTTP 可觀測層面重建讀取集合并進行提交時驗證，系統將無法保證多智慧體協作的因果一致性與最終輸出的正確性。

**Q4：S-Bus 的核心機制是什麼，它如何運作？**
A：S-Bus 的核心機制是伺服器端的 DeliveryLog（交付日誌），它會為每個智慧體維護一份 HTTP GET 操作的逐日誌記錄。在智慧體提交時，系統會自動根據這份日誌重建其 HTTP 可觀測的讀取集合，並透過可觀測讀取隔離（ORI）機制檢查該讀取集合中的各分片版本是否仍為最新。若發現跨分片過時讀取（例如共享的 db_schema 已從 v3 更新為 v4），中介軟體會回傳 HTTP 409 Conflict 拒絕提交，迫使智慧體重新讀取並再生差異，整個過程無需修改智慧體端的 SDK 或變更應用程式碼。

**Q5：什麼是可觀測讀取隔離（ORI），為何它被定義為部分因果一致性？**
A：ORI 是 S-Bus 提供的一致性性質，它保證在 HTTP 可觀測投影下的讀取集合滿足因果一致性，但僅限於系統能夠從 HTTP 流量中自動重建的讀取集合範圍。由於智慧體可能透過提示詞內容或其他隱式管道讀取狀態（即非 HTTP 可觀測的讀取），S-Bus 無法對這些「隱藏讀取」提供隔離保證，因此稱之為「部分」因果一致性。這種設計務實地將保證範圍限縮在中介軟體可驗證的 HTTP 事件追蹤上，使得形式化驗證與實作部署皆能在不改變智慧體內部運作的前提下達成。

**Q6：S-Bus 實現無需修改智慧體 SDK 的關鍵設計選擇為何？**
A：S-Bus 採用透明 HTTP 中介軟體架構，完全攔截並記錄智慧體與狀態儲存後端之間的標準 HTTP/1.1 GET 請求，利用 HTTP/1.1 連線層級的 FIFO 語義（假設 A1）來確保請求與日誌順序的一致性。由於所有讀取集合的重建都發生在伺服器端，智慧體僅需發出常規的 HTTP 請求即可，無需額外宣告讀取集合或整合特殊客戶端函式庫。此外，提交時的驗證邏輯也封裝在中介軟體層，透過標準的 HTTP 409 狀態碼與智慧體溝通衝突，從而實現與現有 LangGraph、CrewAI 等框架的無縫整合。

**Q7：評估 S-Bus 使用了哪些基準測試與工作負載？**
A：論文採用了兩大類評估：首先是將 SWE-bench 任務改編為多智慧體協調場景（PH-2/PH-3 評估，使用 gpt-4o-mini），用於測量結構覆蓋率與隱藏讀取間隙；其次是針對非程式碼領域的資料管線架構規劃工作負載（Exp.WORKLOAD-B，n=80，橫跨 8 個領域），用於驗證 ORI 在實際業務場景中防止觀點分歧的能力。此外，論文還設計了共享分片爭用掃描實驗，將 S-Bus 與 PostgreSQL 17 SERIALIZABLE 及 Redis 7 WATCH/MULTI 這兩種成熟的 OCC 後端進行對照，在超過 42 萬筆主動 HTTP-409 衝突下比較結構衝突預防能力。

**Q8：關於衝突預防與語意分歧的關鍵實證結果為何？**
A：在共享分片爭用掃描中，S-Bus 與 PostgreSQL 17 SERIALIZABLE、Redis 7 WATCH/MULTI 達成了同等的結構衝突預防效果，在 427,308 筆主動 HTTP-409 衝突與總計 884,110 筆提交中皆觀察到零 Type-I 損壞。在 WORKLOAD-B 實驗中，開啟 ORI 時僅有 0/638 筆提交產生觀點分歧，而關閉 ORI 時則高達 590/639 筆分歧，卡方檢定顯示差異極為顯著（χ²=1,094.98，p<10⁻²⁴⁰）。這些結果證明 ORI 能有效防止跨分片過時讀取所導致的結構性競態條件，並顯著提升多智慧體協作的一致性。

**Q9：關於 ORI 運作範圍的消融或敏感性研究揭示了什麼？**
A：實驗顯示 ORI 的效用具有強烈的拓撲條件性：在專用分片工作負載（Exp.DEDICATED-SHARD，n=600）中，ORI 是語義中性的，即不會對最終結果產生負面影響；然而，在單分片協作寫入情境（Exp.SHARED-STATE）中，ORI 反而有害，因為它會保留並傳播並發矛盾，導致系統將相互衝突的更新全部納入最終狀態。這項發現明確劃定了 S-Bus 的適用邊界——它專為「每個智慧體擁有獨立寫入鍵、共享唯讀參考分片」的拓撲設計，而單分片多寫入者場景則需要額外的順序協調或適應性合併路由機制。

**Q10：S-Bus 最適用於哪些實務場景？**
A：S-Bus 最適用於多智慧體各自負責不同模組或文件（擁有獨立寫入鍵），但共同參照一份共享知識庫或規格說明的協作場景，例如軟體工程中的分工修補（如 SWE-bench 範例中分別負責 ORM 編譯器、遷移腳本、測試夾具與審查註記）。在這類專用分片拓撲中，智慧體可以並行寫入各自的分片，而 S-Bus 確保它們不會基於過時的共享參考狀態（如資料庫架構）做出不一致的決策。這種模式也適用於科學文獻綜述、客戶服務工單分派等需要多角色並行產出且依賴共同語境的領域，但轉移至其他領域時仍需獨立評估其隱藏讀取比例。

**Q11：S-Bus 如何整合到現有的多智慧體產品中？**
A：S-Bus 以輕量級 HTTP 中介軟體形式實作，可部署於現有 LangGraph、CrewAI 或 AutoGen 架構的網路層，無需修改智慧體 SDK 或重構應用程式碼，大幅降低採用門檻。由於它利用標準 HTTP/1.1 語義進行讀取集合追蹤與衝突偵測，開發者只需將智慧體的狀態請求導流經過 S-Bus 閘道即可自動獲得 ORI 保證。不過，若底層使用 HTTP/2 多工傳輸，則需要額外設定反向代理釘選或啟用 ARSI 模式的讀取集合宣告，以維持 FIFO-per-connection 的順序假設。

**Q12：自動讀取集合重建對多智慧體 LLM 領域可能帶來什麼更廣泛的影響？**
A：自動讀取集合重建為多智慧體系統引入了資料庫領域成熟的樂觀並行控制（OCC）思維，使得自然語言狀態也能享有形式化驗證過的一致性保證，這是過去框架所缺乏的基礎設施層創新。透過將 HTTP 流量轉化為可驗證的讀取集合，研究者與工程師可以在不侵入智慧體內部推理過程的前提下，建立可組合、可驗證的協作協定。長遠來看，這種機制可能成為多智慧體作業系統的標準隔離層，支撐更複雜的自主工作流程，並為後續的適應性合併路由、跨域遷移與人機協同審查奠定可信賴的狀態管理基礎。

**Q13：S-Bus 有哪些已承認的限制，特別是關於覆蓋率缺口？**
A：論文明確指出，在主要工作負載（PH-2/PH-3）中，HTTP 可觀測讀取僅佔智慧體實際讀取的約 26.1%，隱藏讀取間隙（R_hidden gap）高達 0.739，表示絕大部分讀取行為無法透過 HTTP 流量自動重建。雖然 DeliveryLog 能覆蓋 99.8% 的自我回報引用，但智慧體的自我回報本身存在 29% 至 37% 的過度聲稱率，且語義提取召回率僅 0.59，顯示讀取集合的完整性仍有顯著侷限。這些殘留的覆蓋缺口意味著 ORI 無法對非 HTTP 可觀測的隱式讀取提供保證，形式化證明也僅涵蓋抽象演算法的內部一致性，而非智慧體的語義正確性。

**Q14：ORI 在什麼條件下會失效或產生危害？**
A：ORI 在單分片協作寫入（single-shard collaborative writing）的拓撲下會從保護機制轉為有害，因為它會強制保留所有並發更新，進而傳播相互矛盾的內容至最終狀態。此外，若底層傳輸使用 HTTP/2 多工而未設定連線釘選，HTTP/1.1 的 FIFO-per-connection 假設（A1）將被破壞，導致 DeliveryLog 的讀取順序與實際請求順序不一致，使讀取集合重建失效。當工作負載中的隱藏讀取比例極高且這些讀取恰好是跨分片驗證的關鍵依據時，ORI 也無法偵測到基於過時隱式狀態所產生的結構性競態條件。

**Q15：論文建議哪些未來方向以擴展 S-Bus？**
A：論文提及一項正在獨立開發的適應性合併路由（adaptive merge-routing）擴充，旨在解決單分片協作寫入場景中 ORI 傳播並發矛盾的問題，這將使 S-Bus 的適用範圍超越專用分片拓撲。另一個方向是支援 HTTP/2 環境，透過反向代理釘選或顯式的 ARSI 模式讀取集合宣告，來彌補 HTTP/1.1 FIFO 語義不再適用的限制。此外，提升語義提取的召回率、降低隱藏讀取間隙，以及將 Rust 實作層的形式化驗證補齊（目前僅抽象演算法經過機械化驗證），都是邁向更完整可信賴多智慧體狀態協調的重要後續工作。

## 實務應用指南

### 適用場景

**1. 多智能體軟體工程協作（Multi-Agent SWE）**
適用於如 SWE-bench 的軟體維修任務，由多個 LLM 智能體分別負責不同模組（例如：ORM 編譯器、遷移腳本、測試檔、審查註釋），各自擁有專屬寫入鍵，但共享唯讀的資料庫結構描述（db_schema）等參考分片。S-Bus 可防止因參考分片版本過時導致的跨分片過時讀取衝突。

**2. 資料管線架構規劃（Data-Pipeline Architecture Planning）**
對應論文中 Exp.WORKLOAD-B 場景：多個智能體分工設計資料管線的不同元件（擷取、轉換、載入），同時讀取共享的資料字典與架構規範分片。ORI 可確保各元件在提交時察覺參考規範的變更，避免產生彼此矛盾的管線設計。

**3. 科學文獻綜合分析與分工撰寫**
研究團隊可由不同智能體分別撰寫論文的引言、方法、結果與討論章節，各章節為獨立寫入分片，但共享參考文獻與實驗數據分片。S-Bus 確保當共享數據更新時，各章節撰寫者能偵測到結構性競態條件並重新讀取。

**4. 企業客戶服務多智能體分工**
不同智能體分別處理帳務、技術支援與物流查詢，各自寫入獨立的對話紀錄或處理摘要分片，但共享客戶基本資料與知識庫參考分片。透過 DeliveryLog 自動重建讀取集合，可避免智能體基於過時客戶狀態給出錯誤建議。

### 實作前置條件

**資料前提**
- 自然語言狀態（NL state）必須已完成分片（shard）設計，明確區分「專屬寫入分片」（每個智能體一個寫入鍵）與「共享參考分片」（多個智能體可讀取）。
- 智能體的所有讀取操作原則上需經由 HTTP GET 發出，以便 DeliveryLog 進行 HTTP 可觀測投影（HTTP-observable projection）與讀取集合重建。

**運算前提**
- 可執行 Rust 中介軟體的伺服器或容器環境。
- 網路層需支援 HTTP/1.1（以滿足 FIFO-per-connection 假設 A1）；若使用 HTTP/2，則必須搭配支援連線釘選（connection pinning）的反向代理。
- 後端儲存需支援樂觀並行控制（OCC），例如 PostgreSQL 17（SERIALIZABLE）或 Redis 7（WATCH/MULTI），或直接使用 S-Bus 原生機制。

**技能前提**
- 具備後端工程與中介軟體部署經驗，能設定 HTTP 路由、日誌收集與反向代理。
- 理解專用分片拓撲（dedicated-shard topology）與單分片協作寫入的區別，避免將 S-Bus 部署於不適用的拓撲。
- 無需形式化驗證（TLAPS/Dafny）背景即可部署，但需理解 ORI 的運作範圍（operating envelope）與覆蓋率限制。

---

### 實作步驟建議

**步驟一：拓撲設計與分片劃分**
確認系統符合專用分片拓撲：每個智能體擁有唯一的寫入鍵（write key），所有跨智能體狀態共享僅透過共享參考分片（shared reference shards）進行。明確禁止多個智能體寫入同一分片。

**步驟二：中介軟體部署與 HTTP 版本控制**
將 S-Bus 部署為 HTTP 中介軟體，置於智能體與狀態儲存層之間。優先使用 HTTP/1.1 以確保連線層 FIFO 順序；若環境強制使用 HTTP/2，請在反向代理（如 Nginx、Envoy）設定連線釘選，或啟用 ARSI-mode 讓智能體顯式宣告讀取集合。

**步驟三：後端選型與 OCC 設定**
選擇後端儲存並啟用樂觀並行控制機制。論文驗證顯示 PostgreSQL 17 SERIALIZABLE、Redis 7 WATCH/MULTI 與 S-Bus 在結構衝突預防上具備同等效果。設定分片版本追蹤，使每次寫入遞增版本號。

**步驟四：啟用 DeliveryLog 與讀取集合重建**
於伺服器端啟用逐智能體 DeliveryLog（交付日誌）。此機制會自動攔截並記錄 HTTP GET 操作，在提交時自動重建該智能體的讀取集合（read set），無需修改現有 Agent SDK。

**步驟五：設定提交時跨分片驗證（Cross-shard Validation）**
在提交協議（ACP）中設定驗證規則：比對 DeliveryLog 記錄的讀取版本與各共享分片當前版本。若發現跨分片過時讀取（cross-shard stale-read），回傳 HTTP 409（Conflict），強制智能體重新讀取（re-read）並重新生成差異（delta）。

**步驟六：漸進式驗證與監控上線**
先在專用分片工作負載（dedicated-shard workload）進行小規模驗證，確認 HTTP-409 衝突正確觸發、無 Type-I 損壞。監控 R_obs（HTTP 可觀測讀取比例）與隱藏讀取缺口（R_hidden gap），確保關鍵讀取皆落入 HTTP 可觀測範圍。

**步驟七：明確排除單分片協作寫入場景**
在產品文件中清楚劃定 S-Bus 的運作範圍：單分片協作寫入（single-shard collaborative writing）為已知有害場景，應透過外部順序協調或自適應合併路由（adaptive merge-routing）處理，而非直接套用 ORI。

### 潛在風險與注意事項

**HTTP/2 多工破壞 FIFO 假設（Assumption A1）**
HTTP/2 的多路複用（multiplexing）會打破單一連線的 FIFO 順序，導致 DeliveryLog 的讀取順序與實際發送順序不一致。**緩解措施**：強制使用 HTTP/1.1，或在反向代理層實施連線釘選（reverse-proxy pinning）；亦可採用 ARSI-mode，要求智能體在提交時顯式宣告讀取集合，降低對傳輸層順序的依賴。

**單分片協作寫入的結構性危害**
若將 S-Bus 用於單分片協作寫入（所有智能體寫入同一鍵），ORI 會保留並傳播並發矛盾（preservation propagates concurrent contradictions），反而導致輸出品質下降。**緩解措施**：嚴格遵守專用分片拓撲設計；若業務需求必須共享寫入分片，請改用順序鎖或等待論文提及的自適應合併路由擴充成熟。

**HTTP 可觀測投影的覆蓋率缺口**
論文指出，在主要工作負載（PH-2/PH-3）中，HTTP 可觀測讀取比例（R_obs）僅約 26.1%，隱藏讀取（R_hidden）缺口顯著。若智能體透過非 HTTP 管道（如記憶體快取、函數呼叫參數）讀取狀態，DeliveryLog 無法重建該部分讀取集合，結構性競態條件仍可能發生。**緩解措施**：將所有關鍵共享狀態的讀取統一導流至 HTTP GET；對於無法導流的讀取，需在架構層視為隱藏風險並輔以驗收測試。

**結構正確不等於語義正確**
ORI 僅保證結構衝突預防（structural conflict prevention），不保證智能體產出的語義正確性。即使無 Type-I 損壞，智能體仍可能生成語義矛盾或偏離目標的內容。**緩解措施**：維持獨立的語義驗收機制（如 SWE-bench 的 acceptance tests、LLM-as-judge 評分標準），並保留人類語義評估（human semantic evaluation）作為最終閘道。

**自我報告過度宣稱**
實驗顯示智能體自我報告的參考讀取存在 29%–37% 的過度宣稱率（self-report over-claim rate），且評審者間一致性僅達中度（κ = 0.46）。**緩解措施**：勿依賴智能體自我宣稱的讀取集合作為除錯依據；以伺服器端 DeliveryLog 的客觀記錄為準。

**實作層非機械驗證**
論文中的 TLAPS、TLC 與 Dafny 證明僅涵蓋抽象演算法；Rust 實作細緻化（implementation refinement）為經驗性驗證，非機械證明。**緩解措施**：在生產部署前進行充分的整合測試與壓力測試，特別針對共享分片爭用（shared-shard contention）情境進行掃描。

### 與其他技術的整合建議

**與現有多智能體框架（LangGraph、CrewAI、AutoGen）整合**
這些框架目前缺乏寫入所有權語義（write-ownership semantics）。S-Bus 可作為其底層狀態層的中介軟體，無需修改既有 Agent SDK，即可為其共享自然語言狀態提供結構性競態條件防護。建議將 S-Bus 置於框架的狀態儲存適配器（state store adapter）之前。

**與資料庫後端（PostgreSQL、Redis）整合**
S-Bus 的讀取集合重建機制可疊加於現有 OCC 後端之上。若已使用 PostgreSQL 17 SERIALIZABLE 或 Redis 7 WATCH/MULTI，可保留既有交易層，但將 S-Bus 的 DeliveryLog 作為跨分片驗證（cross-shard validation）的額外閘道，以補足純資料庫交易無法察覺的 HTTP 層過時讀取。

**與反向代理及負載平衡整合**
為滿足 HTTP/1.1 的 FIFO-per-connection 假設，建議在 Nginx 或 Envoy 設定基於智能體身份（agent ID）的連線釘選或會話保持（session affinity）。若未來支援 HTTP/2，反向代理需確保同一智能體的請求在同一 TCP 連線上按序處理，或降級至 HTTP/1.1。

**與監控及可觀測性整合**
將 DeliveryLog 的讀取集合覆蓋率（R_obs）、HTTP-409 衝突率、提交分歧（divergent commits）數量與 Type-I 損壞指標導入 Prometheus/Grafana。特別監控 ORI-ON 與 ORI-OFF 下的 view-divergence 差異，以量化中介軟體的結構防護效益。

**與 CI/CD 及驗收測試整合**
在軟體工程場景中，將 S-Bus 的提交閘道與 SWE-bench 風格的 acceptance tests 串接：當 ORI 偵測到結構衝突並觸發重新讀取時，確保重新生成的差異仍通過客觀語義測試，形成「結構安全 → 語義驗證」的雙層閘道。

### 給不同背景讀者的閱讀建議

**初學者**
建議從 §1.1 的動機範例（Django bug #11019）與 §1.3 的範圍說明開始，理解「專用分片拓撲」與「結構性競態條件」的基本直覺。無需深入形式化證明，重點掌握 S-Bus 作為 HTTP 中介軟體的角色，以及它與傳統資料庫交易在「防止靜默覆寫」上的相似性。

**AI 工程師**
請優先閱讀 DeliveryLog 的架構設計（§1、§7）與 ORI 的運作範圍（C3、§7-M）。重點關注 HTTP/1.1 假設、HTTP/2 的連線釘選需求，以及 R_obs 覆蓋率缺口對實際系統的影響。形式化證明章節（§V）可略讀，但需理解其結論如何限制你的部署場景（特別是「單分片協作寫入有害」這一條）。

**研究人員**
核心貢獻在於 C1 的形式化框架：請仔細研讀 ORI（Observable-Read Isolation）的定義、ReadSetSoundness 與 ORICommitSafety 的陳述，以及 TLAPS/TLC/Dafny 的三層機械化證據結構。注意 §8 的限制與 §1.3 的精確主張邊界，這些是評估該工作理論完整度與未來延伸空間的關鍵。

**產品經理**
請聚焦 C2 的實證結果（427,308 次主動衝突下零 Type-I 損壞）與 C3 的拓撲條件式效益（專用分片語義中性 vs. 單分片協作有害）。Table 1 的量化摘要（如 WORKLOAD-B 的 view-divergence 對比）是評估商業價值的最佳依據。請記住：S-Bus 是結構安全網，不能取代語義正確性保證或人類最終審核，規劃產品路線圖時需並列配置驗收測試資源。
