## ⚡ TL;DR

本文解決如何讓 AI 在快節奏射擊遊戲中成為能即時協作的語音隊友。
提出 PUBG Ally，以分層架構結合語言模型代理與即時控制層，並透過工具介面感知、決策與對話。
經近三萬九千場對局迭代訓練與上線調查，玩家推薦意願正面回應高出負面 25.1 個百分點。

## 摘要翻譯

我們提出 PUBG Ally，一個用於 PUBG: BATTLEGROUNDS（《絕地求生》）的具身代理人（embodied agent），能夠推理、自主行動，並作為語音啟用隊友（voice-enabled teammate）與玩家並肩遊玩。建構這樣的 AI 隊友（AI teammate）需要結合兩項艱難的能力：它必須在嚴格的延遲限制（latency constraints）下感知並回應不斷變化的遊戲世界，同時與玩家自然地互動，並使其語音與動作保持同步。因此，Ally 結合了代理式工具使用（agentic tool use）與即時遊戲控制（real-time game control）。語言模型代理（language-model agent）透過受控介面（controlled interface）檢視遊戲資訊、理解玩家語音（player speech）、維護上下文（context）、決定說話內容，並發出高階動作選擇（high-level action choices），以引導更快的控制層（control layer）進行移動（movement）、戰鬥（combat）與恢復（recovery）。由於玩家與 Ally 的語音和動作持續相互影響並塑造對局走向，訓練需要來自實際遊戲過程（gameplay）的資料。因此，我們在將近 39,000 場對局場次（sessions）中收集資料，由真實玩家與 Ally 同場遊玩，記錄遊戲過程（gameplay）、玩家語音（player speech）、代理決策（agent decisions）、工具使用（tool use）、動作（actions）以及玩家回饋（player feedback），並將這些記錄用於迭代訓練（iterative training）。為了評估隊友品質，我們運用玩家回饋（player feedback）與偏好比較（preference comparisons），找出離線評估（offline evaluations）與玩家偏好（player preferences）之間的差距，並朝向玩家偏好進行迭代式評估精煉（iterative evaluation refinement toward player preference）。在上線服務（live service）中部署 Ally 還需要低延遲的裝置端執行（on-device execution），以及針對面向玩家的通訊之安全防護措施（safeguards）；我們透過模型壓縮（model compression）、上下文壓縮（context compaction）、針對性安全訓練（targeted safety training）、執行階段護欄（runtime guardrails）與記憶編輯（memory redaction）來解決這些問題。在上線服務（live service）期間，我們調查了 141 個國家的玩家。在遊戲記錄已確認曾與 Ally 同場遊玩的受訪者中，當被問及是否會推薦（recommendation）Ally 時，正面回應（positive responses）較負面回應（negative responses）高出 25.1 個百分點，玩家形容 Ally 不僅是一項工具，更是一位隊友或夥伴（teammate / companion）。

### 核心貢獻（3～5點）
- 提出結合語言模型代理（System 2）與即時控制層（System 1）的分層代理架構（layered agent architecture），使 AI 隊友能同時進行自然語音對話與低延遲遊戲控制。
- 建立大規模真實對局資料收集流程（近 39,000 場 sessions），並以玩家回饋驅動迭代訓練（iterative training）與評估精煉。
- 提出以玩家偏好為導向的評估方法，透過離線評估（offline evaluations）與線上評估（online evaluation）的落差分析，持續精煉評估標準。
- 實現上線服務（live service）所需的裝置端執行（on-device execution）與多層安全防護措施（safeguards），包括模型壓縮、上下文壓縮、針對性安全訓練、執行階段護欄與記憶編輯。
- 透過 141 國玩家的 Live Beta 玩家調查（Live beta player survey）驗證，證明玩家將 Ally 視為隊友或夥伴，而非僅是工具。

### 適合對象
對遊戲 AI、具身代理人（embodied agent）、多模態互動系統、大型語言模型代理安全部署，以及即時遊戲中 AI 隊友設計有興趣的研究人員與工程師；特別適合關注如何將語言模型代理從研究原型推向真實上線服務（live service）的讀者。

## 深度分析

#### 方法論解析

PUBG Ally（以下簡稱 Ally）被定位為一種 **co-playable character（CPC，可共同遊玩的角色）**，也就是能在《PUBG: BATTLEGROUNDS》（以下簡稱 PUBG）的雙排（duo play）模式中，以語音隊友（voice-enabled teammate）身分與人類玩家並肩作戰的 **conversational embodied agent（對話式具身代理人）**。其核心挑戰在於同時滿足兩項高難度能力：一是面對持續變動的戰場進行 **real-time game control（即時遊戲控制）**，二是透過自然語音與玩家互動，並讓語言與行為保持同步。為此，作者提出一種 **layered agent architecture（分層代理架構）**，將認知決策與低階控制解耦。

##### 1. System 2：Event-Driven Agent Harness（事件驅動代理框架）

上層的 **System 2（系統 2）** 是一個以大型語言模型（large language model，LLM）為核心的 **language-model agent（語言模型代理）**，負責慢速但高階的推理。它透過 **controlled interface（受控介面）** 與遊戲互動，包括：

- 檢視遊戲狀態與戰場資訊；
- 解析玩家語音（player speech）；
- 維護對話與戰術 **context（上下文）**；
- 決定 Ally 應該說什麼；
- 發出 **high-level action choices（高階動作選擇）**。

這一層採用 **agentic tool use（代理式工具使用）** 的設計，讓語言模型主動呼叫工具來取得觀測、規劃行動，而非僅被動接收固定輸入。由於 PUBG 是快節奏遊戲，System 2 並不直接控制每個幀的動作，而是把戰術意圖傳遞給下層的 System 1。

##### 2. System 1：Stateful Real-Time Control（狀態化即時控制）

下層的 **System 1（系統 1）** 負責 **stateful real-time control（狀態化即時控制）**，處理移動（movement）、戰鬥（combat）、恢復（recovery）等低階且對延遲極為敏感的動作。它接收 System 2 的高階指令後，在嚴格的 **latency constraints（延遲限制）** 內持續執行，並根據戰場變化即時調整。這種分層設計讓「說什麼」與「做什麼」能夠分開處理，再透過狀態同步避免語言與行為脫節。

##### 3. 語音與行為的同步機制

Ally 必須讓 **speech and actions synchronized（語音與行為同步）**。舉例來說，當玩家被擊倒（knocked）時，Ally 需要評估周遭威脅、投擲煙霧彈掩護、移動到玩家身邊並執行復活（revive）。這一連串行動必須伴隨一致的語音回應，例如告知玩家「我來救你」或「我先丟煙」。System 2 負責生成語意上正確的發言與高階計畫，System 1 則確保這些計畫在毫秒級時間尺度內被落實。

##### 4. 資料驅動的迭代訓練

由於玩家與 Ally 的語音和行動會持續互相影響，單靠靜態資料或模擬環境難以捕捉真實互動動態。因此團隊進行了大規模 **data collection（資料收集）**，在將近 39,000 場對局（sessions）中讓真實玩家與 Ally 同場遊玩，記錄遊戲過程（gameplay）、玩家語音、代理決策、工具使用、動作執行以及玩家回饋（player feedback）。這些記錄被用於 **iterative training（迭代訓練）**，持續改善模型行為。

##### 5. 安全性與部署最佳化

為了將 Ally 部署到 **live service（上線服務）**，論文採取多項工程措施：

- **model compression（模型壓縮）** 與 **context compaction（上下文壓縮）**：降低延遲與記憶體占用，實現 **on-device execution（裝置端執行）**；
- **targeted safety training（針對性安全訓練）**：減少有害或不當發言；
- **runtime guardrails（執行階段護欄）**：在執行階段攔截違規輸出；
- **memory redaction（記憶編輯）**：遮蔽或刪除敏感個資，保護玩家隱私。

整體而言，Ally 的方法論體現了「高階語言推理 + 低階即時控制 + 真實玩家資料迭代 + 安全部署」的整合式架構，而非單純將 LLM 接入遊戲 API。

#### 實驗數據解讀

論文的評估分為 **capability evaluation（能力評估）**、**safety evaluation（安全評估）**、**online evaluation（線上評估）** 以及 **iterative evaluation refinement toward player preference（朝向玩家偏好的迭代式評估精煉）** 四大面向。雖然完整數值未在提供的摘要與目錄中詳列，但可從實驗設計與結果敘述中推導其含義。

##### 1. 能力評估（Capability Evaluation）

能力評估 likely 針對 Ally 在戰術決策、跟隨指令、敵情通報、資源共享、復活支援等任務上的表現。由於 System 2 使用工具呼叫與上下文推理，評估指標可能包含：

- 高階動作選擇的正確率；
- 語音回應與當下遊戲狀態的一致性；
- 任務完成率（例如成功復活玩家、依指令移動到指定地點）；
- 與人類隊友的協調效率。

這些指標有助於確認分層架構是否確實讓語言模型代理能夠有效駕馭複雜戰場。

##### 2. 安全評估（Safety Evaluation）

安全評估檢視 Ally 在玩家面向溝通中的風險，包括毒性語言、個資洩漏、不當建議等。論文提到透過 **safety specifications（安全規格）**、**safety training（安全訓練）** 與 **runtime guardrails（執行階段護欄）** 三層防護。評估結果 likely 以違規率、人工審查通過率、紅隊測試（red-teaming）成功率等方式呈現。

##### 3. PC Bang 資料收集結果

論文特別提到 **PC Bang data collection（PC Bang 資料收集）**。PC Bang 是韓國的網咖文化場域，玩家在此進行遊戲的環境與裝置相對一致，適合進行受控但真實的資料收集。從近 39,000 場對局中取得的資料，不僅用於訓練，也成為 **offline evaluations（離線評估）** 與 **player preferences（玩家偏好）** 對齊的基礎。

##### 4. Live Beta 玩家調查

最重要的線上指標來自 **live beta player survey（Live Beta 玩家調查）**，涵蓋 141 個國家。在遊戲紀錄確認確實與 Ally 同場遊玩的受訪者中，當被問及是否願意推薦 Ally 時，**正面回應（positive responses）比負面回應（negative responses）高出 25.1 個百分點**。這是一個強烈的訊號，表示：

- Ally 不僅在技術層面可運作，在玩家體驗層面也獲得認可；
- 玩家不只將 Ally 視為工具，更將其視為 teammate / companion（隊友 / 夥伴）；
- 語音互動與即時行動的同步性達到了可接受的品質門檻。

值得注意的是，論文強調透過 **preference comparisons（偏好比較）** 發現離線評估與玩家偏好之間存在落差，因此持續進行 **iterative evaluation refinement（迭代式評估精煉）**。這意味著傳統的離線指標（如動作準確率、語言困惑度）並不能完全捕捉「是否像個好隊友」的主觀感受，必須將玩家回饋納入評估迴路。

#### 與現有研究的比較

##### 1. 從「會玩遊戲的 AI」到「會合作的隊友」

過去許多遊戲 AI 研究聚焦於自主遊戲表現，例如 AlphaStar（Vinyals et al., 2019）、OpenAI Five（OpenAI et al., 2019）以及 Jaderberg 等人的工作，目標是在競技環境中擊敗人類。這些系統雖然展現了高超的 **gameplay（遊戲過程）** 能力，但通常不具備自然語言溝通能力，也無法與人類玩家進行即時協調。

Ally 的差異在於：它的目標不是單純贏得比賽，而是成為一位 **AI teammate（AI 隊友）**。這要求它不僅要會玩，還要會「說」、會「聽」、會「配合」。這種從競技導向到協作導向的轉變，是遊戲 AI 研究的重要延伸。

##### 2. 與傳統 NPC 與商業 AI 夥伴的差異

傳統遊戲 NPC 多依賴腳本或行為樹（behavior tree），對話與行為固定，缺乏動態適應能力。商業 **commercial AI game companions（商業 AI 遊戲夥伴）** 雖然開始引入語言模型，但多數仍偏向文字或語音助手，缺乏完整的具身行動能力。

Ally 結合了 **conversational embodied agent（對話式具身代理人）** 的兩大要素：一方面透過 LLM 進行開放式語言理解與生成，另一方面透過 System 1 直接控制遊戲角色執行動作。這比單純的語音機器人或單純的遊戲 bot 都更進一步。

##### 3. 分層架構的優勢

相較於讓單一模型同時處理高階推理與低階控制，Ally 的 **layered agent architecture（分層代理架構）** 有幾項優勢：

- **延遲可控**：System 1 可在毫秒級反應，不受 LLM 推理延遲影響；
- **可解釋性高**：高階動作選擇與語言輸出可被人類理解與審查；
- **模組化**：可獨立改進語言模型、工具介面或控制層；
- **安全性強**：可在 System 2 輸出與 System 1 執行之間插入護欄。

##### 4. 資料收集規模的領先

近 39,000 場真實玩家對局的資料規模，在學術研究中相當罕見。這讓 Ally 能夠學習真實人機協作動態，而非僅依賴模擬資料或專家示範。這也是其能進行 **iterative training（迭代訓練）** 與 **iterative evaluation refinement（迭代式評估精煉）** 的基礎。

##### 5. 限制與挑戰

儘管有上述優勢，Ally 仍存在一些限制：

- **地圖與模式限制**：論文聚焦於 Sanhok 地圖的雙排模式，尚未驗證在其他地圖或四人小隊模式中的泛化能力；
- **語言與文化差異**：雖然調查涵蓋 141 國，但語音理解與文化語境的適應仍可能不均；
- **延遲與硬體依賴**：**on-device execution（裝置端執行）** 與 **model compression（模型壓縮）** 可能犧牲部分模型能力；
- **安全邊界**：即使有多層護欄，開放式語音互動仍可能出現難以預見的違規內容；
- **可解釋性與除錯**：當 System 2 的決策與 System 1 的執行出現不一致時，追蹤根本原因可能複雜。

#### 可重現性評估

根據目前提供的內容，論文並未明確提及是否公開原始碼、資料集或模型權重。這是評估可重現性時的重要限制。

##### 1. 資料集

Ally 的訓練資料來自近 39,000 場真實對局，包含遊戲紀錄、玩家語音、代理決策與玩家回饋。這類資料涉及：

- 玩家隱私（語音內容、遊戲行為）；
- 商業遊戲內部 API 與資料格式；
- 可能包含個人可識別資訊。

因此，完整資料集 likely 無法公開釋出，或僅能以去識別化、片段化的形式釋出。論文提到的 **memory redaction（記憶編輯）** 也暗示了隱私保護是資料釋出的主要障礙。

##### 2. 模型與程式碼

PUBG 是商業遊戲，其遊戲引擎、API 與伺服器架構均為私有。即使作者願意公開 Ally 的模型權重，外部研究者也需要取得 PUBG 的開發者權限才能重現完整系統。因此，這項研究的可重現性主要受限於商業環境，而非研究方法本身不透明。

##### 3. 可重現的面向

儘管無法完全重現，以下面向仍具可重現潛力：

- **分層架構設計**：System 2 / System 1 的分離概念可應用於其他遊戲或機器人平台；
- **工具介面設計**：controlled interface 與 agentic tool use 的設計原則可移植；
- **評估方法論**：結合離線指標、玩家偏好比較與線上調查的評估流程；
- **安全開發流程**：safety specifications、targeted safety training 與 runtime guardrails 的組合可參考。

##### 4. 建議

為提升可重現性，未來可考慮：

- 釋出去識別化的資料子集或模擬環境；
- 公開行為樹引擎（behavior-tree engine）與工具介面的設計文件；
- 在開源遊戲環境（如 Minecraft、StarCraft II 開源模組）中建立簡化版 Ally 的參考實作。

#### 未來研究方向

Ally 的出現為遊戲 AI 與人機協作開啟了多條後續研究路徑：

##### 1. 多模式與多語言擴展

未來可將 Ally 從 Sanhok 雙排模式擴展到其他地圖、四人小隊模式，甚至其他遊戲類型。同時，提升多語言語音理解與文化適應能力，將是全球化部署的關鍵。

##### 2. 更緊密的語言行動對齊

雖然 Ally 已強調 speech-action synchronization，但如何讓語言模型更精準地預測自身與隊友的未來行動，並據此生成更有用的發言，仍是開放問題。可引入心智理論（theory of mind）模型或隊友意圖預測機制。

##### 3. 長期關係建立

玩家將 Ally 視為 companion（夥伴）的現象，暗示未來可研究 AI 隊友如何建立長期信任與個人化互動。例如記住玩家偏好、適應玩家風格、在多次對局中發展出穩定的「個性」。

##### 4. 更強大的安全與對齊機制

開放式語音互動帶來的安全風險不會消失。未來研究可探索：

- 更細緻的 safety specifications，涵蓋不同文化與年齡層；
- 即時學習與適應的 guardrails；
- 玩家可控的 AI 行為邊界，讓玩家自訂 Ally 的溝通風格與主動程度。

##### 5. 可解釋性與除錯工具

當分層系統出錯時，如何快速定位是 System 2 決策錯誤、System 1 執行失敗，還是兩者之間的語意落差？開發視覺化除錯工具與可解釋性介面，將有助於迭代改進與玩家信任。

##### 6. 從遊戲到現實世界的具身代理

Ally 的架構——高階語言推理 + 低階即時控制 + 安全護欄——可應用於其他具身代理場景，例如機器人協作、自動駕駛車內助手、或工業現場的人機協作機器人。未來可研究如何將這套方法論遷移到非遊戲的真實世界環境。

##### 7. 資料效率與模擬到真實的遷移

目前 Ally 依賴大量真實玩家資料。未來可探索如何減少對真實資料的依賴，例如透過高保真模擬環境進行預訓練，再透過少量真實資料進行對齊，以降低部署成本與資料隱私風險。

總結來說，PUBG Ally 不僅是一個遊戲 AI 產品，更是一個展示「語言模型如何成為具身協作夥伴」的重要研究範例。其分層架構、真實資料驅動的迭代訓練，以及對安全與玩家偏好的重視，為未來的 AI teammate 研究提供了寶貴的參考框架。

## 論文問答

**Q1：PUBG Ally 主要想解決什麼問題？**

A：PUBG Ally 旨在打造一位能夠在《絕地求生》雙排模式中與真人玩家並肩作戰的 AI 隊友，使其不僅能自主感知與行動，還能透過語音與玩家自然溝通與協調。這類「可共同遊玩的角色」（co-playable character, CPC）必須同時具備即時具身遊戲能力與對話互動能力，並讓語音與行為保持一致。由於戰場環境瞬息萬變且對延遲極度敏感，傳統只專注於單一能力的代理難以滿足真正的隊友需求。

**Q2：為什麼現有的遊戲代理或對話系統無法直接解決這個問題？**

A：過去的遊戲代理大多強調自主遊玩表現，例如在高操作層面擊敗對手，但缺乏與人類隊友持續溝通與協調的能力；相對地，一般對話代理雖然能自然交談，卻難以即時感知動態的 3D 遊戲世界並在毫秒級延遲內做出反應。更重要的是，語音與行動必須同步，否則玩家會聽到 Ally 說要掩護，實際上卻往反方向移動，造成嚴重的隊友信任崩潰。因此，單純疊加遊戲 AI 與語音機器人並不足夠，需要從架構與資料層面重新設計。

**Q3：這個研究問題為什麼重要？**

A：PUBG Ally 代表了將大型語言模型代理真正部署到快節奏商業遊戲中的嘗試，對於「從基礎模型走向產品級代理」具有指標意義。成功的 AI 隊友不只能提升遊戲體驗，也能為獨自遊玩的玩家提供陪伴感，並降低團隊遊戲的參與門檻。此外，這項工作也為具身人工智慧與多模態人機協作領域提供了真實場景下的驗證基準。

**Q4：PUBG Ally 的核心方法是什麼？**

A：Ally 採用分層代理架構，將高階推理與低階即時控制分離。System 2 是一個事件驅動的語言模型代理，透過受控介面檢視遊戲狀態、理解玩家語音、維護上下文、決定要說的話，並發出高階動作選擇；System 1 則是狀態化即時控制層，負責快速執行移動、戰鬥與恢復等行為。兩層協作讓 Ally 能在嚴格的延遲限制下，同時進行深度推理與流暢操作。

**Q5：這項研究的主要創新點是什麼？**

A：主要創新在於將代理式工具使用與即時遊戲控制結合，使語言模型不僅能「思考」，還能透過工具介面驅動遊戲內的具身行為。另一項創新是強調語音與行動的同步，讓 Ally 的發言與其觀察、決策和動作保持一致。此外，研究團隊透過近 3.9 萬場真實對局資料進行迭代訓練與評估，並針對玩家偏好持續精煉評估標準，這在遊戲 AI 領域相當少見。

**Q6：為什麼要採用 System 2 與 System 1 分層的設計選擇？**

A：這樣的分層設計是為了同時滿足「深度推理」與「低延遲反應」這兩個互相衝突的需求。System 2 可以較慢地進行情境理解與策略決策，而 System 1 則以行為樹等機制在毫秒級時間內執行動作，避免語言模型推理延遲影響戰鬥表現。透過受控介面讓高階系統發出動作意圖而非直接控制每一幀，也提升了系統的安全性與可解釋性。

**Q7：研究團隊使用了哪些實驗與評估方式？**

A：評估分為能力評估、安全評估、線上評估與 Live Beta 玩家調查四個層面。能力評估檢驗 Ally 在戰鬥、移動、資源分享等任務的表現；安全評估確保其語音與行為符合安全規格；線上評估則收集真實對局中的玩家回饋與偏好比較。研究也特別比較離線指標與玩家主觀偏好之間的落差，以迭代精煉評估標準。

**Q8：這項研究最關鍵的實驗結果是什麼？**

A：在 Live Beta 階段，研究團隊調查了 141 個國家的玩家，其中在遊戲紀錄確認曾與 Ally 同隊的玩家中，願意推薦 Ally 的正面回應比負面回應高出 25.1 個百分點。許多玩家不只將 Ally 視為工具，更稱其為隊友或夥伴，顯示其在社交與協作層面獲得認同。能力與安全評估結果也顯示，經過迭代訓練後，Ally 在關鍵任務與風險控制上均有顯著進步。

**Q9：研究中有哪些消融研究或迭代精煉的證據？**

A：研究團隊透過玩家回饋與偏好比較，發現離線評估指標與玩家真實偏好之間存在落差，因此不斷調整評估標準與訓練目標。例如，他們利用 PC Bang 資料收集近 3.9 萬場對局，記錄遊戲過程、玩家語音、代理決策、工具使用與玩家回饋，並用於反覆迭代訓練。此外，附錄中也提到自動化框架修復與上下文最佳化等機制，顯示系統在模型壓縮與推理效率上進行了多輪調校。

**Q10：PUBG Ally 適用於哪些實際場景？**

A：Ally 目前主要部署在《絕地求生》Sanhok 地圖的雙排模式中，可與玩家協調跳傘地點、跟隨語音指令搜刮物資、標記敵人位置、在戰鬥中提供掩護，並在玩家被擊倒時施放煙霧與進行救援。對於沒有固定隊友的玩家，Ally 也能提供類似真人隊伴的協作體驗。未來這類技術也可延伸至其他地圖、模式，甚至其他需要語音協作的遊戲或訓練模擬環境。

**Q11：在實際產品部署上有哪些重要考量？**

A：由於 Ally 需要在真實上線服務中運作，團隊必須解決裝置端低延遲執行、模型壓縮與上下文壓縮等工程挑戰。同時，為了保護玩家體驗，研究設計了安全規格、針對性安全訓練、執行階段護欄與記憶編輯機制，以降低不當發言或行為的風險。整體部署流程也強調迭代式安全開發與持續監控，確保系統在面對全球多元玩家時仍能穩定運作。

**Q12：這項研究對學術界或產業界可能帶來什麼影響？**

A：PUBG Ally 是首批將大型語言模型代理以大規模 Live Beta 形式部署於商業戰術競技遊戲中的案例，為「基礎模型如何成為產品級代理」提供了實證範例。它證明了語言模型不僅能作為聊天介面，也能透過工具使用驅動具身行為，成為人類在動態環境中的協作者。對產業而言，這為遊戲 AI 夥伴、虛擬同伴以及即時人機協作系統的設計開啟了新的可能性。

**Q13：作者承認了哪些限制？**

A：目前 Ally 的範圍仍限於特定地圖與雙排模式，尚未涵蓋所有遊戲模式與地圖，因此其泛化能力仍需進一步驗證。此外，語音辨識在嘈雜環境或口音多樣的情況下可能出錯，進而影響 Ally 對玩家指令的理解。儘管設有多重安全機制，但在快節奏且開放的對話場景中，仍無法保證完全不會出現不當或不合時宜的回應。

**Q14：Ally 可能出現哪些失敗案例？**

A：在激烈戰鬥中，Ally 可能會因為延遲或感知錯誤而做出與語音不一致的行動，例如口頭說要救援卻未能及時抵達玩家身邊。它也可能誤判敵人位置或誤解玩家的隱喻式指令，導致錯誤的戰術決策。此外，即使經過安全訓練與護欄，仍可能在極少數情況下產生讓玩家感到不適的發言，這也是持續迭代安全開發的原因。

**Q15：未來可以朝哪些方向發展？**

A：未來可以將 Ally 擴展到更多地圖、模式以及多人小隊場景，讓 AI 同時與多位人類玩家協作。另一方面，也可強化其長期記憶與個人化能力，使 Ally 能記住玩家的偏好與遊玩風格，提供更貼近真人隊友的互動。最後，在技術層面上，如何在更低延遲下進行更複雜的推理，以及建立更強健的安全保證，將是持續努力的重點。

## 實務應用指南

適用場景

1. **即時多人遊戲的 AI 雙排隊友**  
   在《絕地求生》這類快節奏戰術競技遊戲中，作為玩家的語音啟用隊友，協助標記敵人、分享物資、執行救援與戰術移動，填補真人隊友不在線的缺口。

2. **虛擬實境（VR）協作訓練夥伴**  
   用於軍事、消防或醫療模擬訓練，讓學員與具身代理人並肩完成任務，透過語音協調行動並即時反應環境變化。

3. **現場作業機器人 / 無人機助手**  
   在搜救、巡檢或倉儲場景中，AI 隊友可透過語音與操作員同步資訊、自主執行低階控制（移動、避障、取物），並根據現場狀況調整計畫。

4. **客服與現場服務的語音協助代理**  
   結合企業知識庫與操作介面，讓代理人在工程師或業務人員工作時主動提示步驟、查詢資料並記錄互動，成為「會行動」的語音助手。

5. **語言學習與角色扮演教育應用**  
   讓學習者與虛擬角色進行情境對話，角色不僅回話，還能在虛擬環境中執行動作，提升沉浸感與學習動機。

實作前置條件

- **資料準備**
  - 大量真實對局資料：遊戲遙測（玩家與代理的位置、血量、物品、戰況）、玩家語音轉錄、代理決策與工具使用紀錄、實際動作軌跡。
  - 玩家回饋與偏好比較資料：對局後問卷、推薦意願、語音與行為是否同步的主觀評分。
  - 安全相關資料：有害或敏感對話樣本、需要遮蔽的個人資訊。

- **運算資源**
  - 訓練端：GPU 叢集，用於語言模型微調、偏好學習（preference learning）與語音模型訓練。
  - 推理端：低延遲雲端或裝置端執行環境，需支援模型壓縮與即時上下文壓縮。
  - 遊戲整合端：能與遊戲引擎即時通訊的伺服器或邊緣節點。

- **技術與團隊能力**
  - 熟悉大型語言模型（LLM）代理設計、工具使用（tool use）與行為樹（behavior tree）。
  - 具備遊戲引擎整合、即時系統與低延遲網路程式經驗。
  - 具備語音辨識（ASR）、文字轉語音（TTS）與對話系統經驗。
  - 具備 AI 安全、內容審查、隱私保護與負責任部署經驗。

實作步驟建議

1. **界定互動範圍**  
   先選定特定地圖、模式與任務（例如雙排遊玩），明確 AI 隊友需要執行的高階動作（移動、戰鬥、恢復、溝通）與語音互動情境。

2. **建立受控遊戲介面與工具**  
   設計代理可呼叫的受控介面，讓語言模型代理能查詢遊戲狀態、發出高階動作選擇，並限制不可直接執行危險操作。

3. **設計分層代理架構**  
   - **System 2（系統 2）**：事件驅動的語言模型代理，負責理解玩家語音、維護上下文、決定說什麼與選擇高階策略。  
   - **System 1（系統 1）**：狀�態化即時控制層（如行為樹引擎），負責低延遲執行移動、戰鬥、恢復等動作。

4. **收集真實配對對局資料**  
   讓真人玩家與 AI 隊友實際遊玩，記錄遊戲過程、語音、代理決策、工具使用、動作與玩家回饋，作為迭代訓練基礎。

5. **迭代訓練與偏好對齊**  
   使用收集到的資料微調語言模型與語音模型，並透過玩家偏好比較持續修正，縮小離線評估與玩家偏好之間的差距。

6. **最佳化延遲與部署成本**  
   實施模型壓縮、上下文壓縮與記憶編輯，確保代理能在上線服務中達到低延遲、裝置端或邊緣端執行。

7. **建立安全規格與護欄**  
   制定安全規格，執行針對性安全訓練，部署執行階段護欄，並對敏感記憶進行編輯或遮蔽。

8. **離線能力與安全評估**  
   在上線前進行能力評估與安全評估，確認代理在常見與極端情境下的表現與風險。

9. **小規模 Live Beta 與問卷調查**  
   在有限地區或玩家群中進行 Live Beta，收集玩家回饋與推薦意願，驗證真實體驗。

10. **持續迭代與大規模部署**  
    根據線上評估與玩家調查結果，持續精煉評估標準、模型行為與護欄，再逐步擴大服務範圍。

潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **語音與行為不同步** | 代理說要做某事，但實際動作延遲或沒執行，會破壞隊友信任。 | 採用分層架構，讓 System 2 的高階決策與 System 1 的即時控制緊密同步，並設定動作確認機制。 |
| **幻覺與工具誤用** | 語言模型可能根據錯誤上下文做出不存在的敵人標記或錯誤決策。 | 使用受控介面限制工具範圍，並在訓練中加入真實對局資料與負面樣本。 |
| **安全與不當內容** | 玩家語音可能包含辱罵、個資或敏感話題，代理回應需謹慎。 | 制定安全規格、執行針對性安全訓練、部署執行階段護欄、進行記憶編輯。 |
| **離線指標與玩家偏好脫節** | 模型在離線評估表現好，但玩家實際不滿意。 | 透過偏好比較與 Live Beta 玩家調查，持續進行朝向玩家偏好的迭代式評估精煉。 |
| **延遲與運算成本** | 語音互動與遊戲控制對延遲極敏感，雲端推理成本可能過高。 | 實施模型壓縮、上下文壓縮、快取與裝置端執行，並針對關鍵路徑做效能剖析。 |
| **資料隱私與合規** | 玩家語音與遊戲行為涉及個人資料。 | 在資料收集前取得同意、去識別化、限制資料保留期限，並符合當地法規。 |

與其他技術的整合建議

- **遊戲引擎（Unreal Engine / Unity）**  
  透過官方或自訂 API 將代理的受控介面接入遊戲世界，讓 System 1 能直接驅動角色動畫、導航與戰鬥行為。

  將 AI 隊友視為一種特殊隊友類型，整合至現有配對邏輯，並在玩家選擇雙排遊玩時自動填入。

- **語音基礎設施**  
  與現有語音聊天或 ASR/TTS 服務整合，確保玩家語音能即時轉為文字輸入代理，並將代理回應轉為自然語音輸出。

- **遙測與分析平台**  
  把代理決策、工具使用、玩家回饋與對局結果送入資料倉儲，支援離線評估、A/B 測試與迭代訓練。

- **安全與內容審查服務**  
  串接現有審查 API 或自建護欄，對玩家輸入與代理輸出進行雙重檢查，並與反作弊系統隔離，避免代理被濫用。

- **MLOps / LLMOps 管線**  
  建立從資料收集、標註、訓練、評估到部署的持續整合流程，讓模型更新與護欄調整能安全上線。

給不同背景讀者的閱讀建議

- **初學者**  
  建議先從「適用場景」與「實作步驟建議」開始，理解 AI 隊友不是單一聊天機器人，而是「會聽、會想、會動」的系統。遇到專有名詞時可對照詞彙表，並把重點放在為什麼需要分層架構、為什麼要收集真實玩家資料，以及安全部署的重要性。

- **AI 工程師**  
  請聚焦第 3 章的分層代理架構、System 2 的事件驅動代理框架與 System 1 的狀態化即時控制，以及第 4 章的資料收集與訓練流程。實作時需特別注意延遲最佳化、上下文壓縮、模型壓縮與工具介面的邊界設計，並參考附錄中的行為樹引擎與推論最佳化細節。

- **研究人員**  
  本研究的核心貢獻在於將「對話式具身代理人」與「即時遊戲控制」結合，並透過大規模真實對局資料與玩家偏好進行迭代式評估精煉。建議深入閱讀評估方法、安全規格與 Live Beta 調查結果，思考如何將此框架擴展到更開放的多人環境或其他具身任務。

- **產品經理**  
  請優先關注玩家體驗指標（如推薦意願、語音與行為同步感受）、上線服務的延遲與成本，以及安全與負責任部署的取捨。本案例顯示，離線評估無法完全代表玩家偏好，因此產品迭代應以真實玩家回饋為核心，並預留資源處理資料隱私、內容審查與地區化營運。
