本論文採用的是**比較個案研究法**（comparative case study），而非實驗性研究設計。作者刻意選擇同一作者、同一學科領域（環境科學）、同一版本控制系統（Git）的兩個專案進行稽核式審查（audit-style examination），藉此控制「作者記錄習慣」這個最顯著的混淆變數（confounding variable）。此一設計哲學貫穿全文：作者明確聲稱「工具、產物類別、專案與時間皆為混淆變數」，因此任何差異皆無法單獨歸因於工具本身。

**核心分析框架**包含四個層次：

第一，**產物分類學**（artifact taxonomy）。作者將 AI 輔助研究在版本儲存庫中留下的痕跡區分為兩類：**規範性追蹤**（prescriptive trace）——由持續性規則檔案構成，記錄的是「未來應遵循的指令」；以及**敘事性追蹤**（narrative trace）——由代理工作筆記構成，記錄的是「過程中的發現與狀態」。此分類並非隨意，而是對應到兩種截然不同的記錄本體論：前者是規範性的（normative），後者是記述性的（descriptive）。

第二，**可讀性測量**（legibility measurement）。作者以三個指標量化每個產物在當前版本（current revision）中的可見程度：(a) 歷來提交的所有行數中，仍可在當前版本讀取者所見的比例；(b) 提交次數中「未留下任何可見行」的修訂比例；(c) 與儲存庫中其他所有被追蹤的文字檔案的比較基準。

第三，**揭露通道測量**（disclosure channel measurement）。針對自動化稽核實際會讀取的欄位——Git commit 中的 `Co-Authored-By` trailer——作者計算其**敏感度**（sensitivity），即在已知代理活動的提交中，攜帶該 trailer 的比例。此處的「已知代理活動」是以儲存庫內部證據作為代理指標（within-repository proxy）：在 Project B 中即為「修改了代理工作筆記檔案的提交」。

第四，**時間穩定性分析**。作者並非預先指定時間切點，而是以序列檢視（inspecting the series）方式定位一個「靜默的月份邊界」（silent month boundary），觀察揭露率在該邊界前後的跳躍。

方法論上最值得稱道之處在於**自我約束**（self-restraint）：作者反覆強調「我們不隔離原因，並如此聲明」（we do not isolate the cause, and say so），避免對觀察到的差異做出因果歸因。這在 AI 治理研究中是罕見的克制，因為該領域常見過度詮釋的傾向。

#### 實驗數據解讀

**可讀性的反向結果**是全文最核心的發現。Project A 的規範性追蹤保留了 85.6% 的歷來提交行數，但這恰恰是問題所在：規範性檔案記錄的是「結論」而非「得出結論的過程」。一個持續性規則可能寫著「使用 X 方法」（standing rule states a conclusion），而其背後的探索過程——為何選擇 X、嘗試過哪些替代方案、放棄了什麼——已被抽象化與丟棄。Project B 的敘事性追蹤僅保留 21.8%，但其記錄的是「事件」（records episodes），其餘 78.2% 雖在物件資料庫（object database）中可透過檔案歷史回溯取得，卻不在當前版本的可見內容中。

此處的關鍵洞見是**「可見」與「可記錄」之間的互斥**（the complementarity of failures）：記錄過程的產物不展示過程，展示自身的產物不記錄過程。這是一種結構性的取捨（structural trade-off），而非任一工具的設計缺陷。

**以修訂次數計算時差距縮小**。規範性追蹤 41 個修訂中有 15 個未留下可見行，敘事性追蹤 41 個修訂中有 18 個未留下可見行。兩者差距遠小於以行數計算時的差距（85.6% vs. 21.8%）。這暗示敘事性追蹤的「消失」主要是大量行被覆寫（overwritten）而非整個修訂被丟棄——一個對稽核實務重要的細節：行級遺失（line-level loss）與修訂級遺失（revision-level loss）的後果不同。

**`Co-Authored-By` trailer 的敏感度數據**揭示了揭露通道的嚴重失靈。在 Project A 中，該 trailer 涵蓋 121 個攜帶任何 AI trailer 的提交中的 66 個，是三個 AI trailer 鍵之一。在 Project B 中，39 個修改代理工作筆記的提交中，僅 1 個（2.6%）攜帶該 trailer。換言之，若以 `Co-Authored-By` 作為代理活動的偵測器，在 Project B 中將漏掉 97.4% 的已知代理活動。

**時間不穩定性**同樣令人警覺。Project A 的儲存庫層級揭露率在未預先指定的邊界前後，從 2.7% 跳升至 17.7%。作者明確指出無法判定原因——作者可能僅是在邊界後更頻繁地使用代理——但無論原因為何，**單一專案內的揭露率隨時間波動**這一事實，使得任何基於單一時間點揭露率的比較都失去意義。

**證據帳簿**（evidence ledger）是方法論上的重要產物：每個產物修訂、揭露提交、被追蹤文字檔案與 blame 群組（blame cohort）皆對應一行可稽核記錄。這使得所有數字皆可被獨立驗證，而非依賴於作者的敘述。

#### 與現有研究的比較

本論文在文獻光譜中佔據一個獨特位置：**它不將版本控制系統的局限性視為待緩解的威脅，而是視為研究對象**。

相較於 **Bird 等人 [2009]**、**Kalliamvakou 等人 [2016]**、**Gousios 與 Spinellis [2012]** 的版本控制挖掘（repository mining）研究——這些工作早已警示 Git 歷史並非開發過程的忠實記錄，提交經過策展（curated）、變基（rebased）、壓縮（squashed）與回填日期（back-dated）——本論文將這些警示應用於一個新興問題：AI 參與的揭露。這是從「一般軟體工程」到「AI 輔助研究」的領域轉譯。

相較於 **Moreau 等人 [2011]** 與 **Freire 等人 [2008]** 的形式化溯源模型（formal provenance models）——這些工作規範性地定義了「計算結果應記錄什麼」——本論文採取實證立場，測量「現有系統實際記錄了什麼」。兩者互補：前者告訴我們理想狀態，後者告訴我們現實落差。

相較於 **Torres-Arias 等人 [2019]** 與 **Newman 等人 [2022]** 的供應鏈安全（supply-chain security）工作——這些工作透過密碼學證明（cryptographic attestation）與透明度日誌（transparency logs）將身分綁定於產物——本論文指出此類方案預設「值得證明的事件已被識別」，而這個前置步驟本身在 AI 輔助研究中尚未解決。

相較於 **Wu [2026]** 將 AI 輔助研究的版本控制歷史挖掘為「可重用的代理實踐」，以及 **Geng 等人 [2026]** 將科學程式碼儲存庫轉化為代理學習環境——這些工作將儲存庫視為**代理可重用的資源**——本論文則將儲存庫視為**稽核可讀取的證據**。兩種讀法對儲存庫結構的要求不同：前者偏好豐富的過程記錄，後者偏好可驗證的聲明。

相較於 **Liang 等人 [2024]** 從文本訊號估計 LLM 參與度——這是從已發表文獻回溯測量——本論文從開發過程的原始記錄出發，提供了不同的證據基礎。

**主要限制**作者已明確承認：(1) 樣本僅兩個儲存庫，無法支撐統計推論；(2) 工具、產物類別、專案、時間皆混淆，差異無法歸因；(3) 作者本身是受稽核對象，存在自我審查偏見；(4) 揭露率變化的替代解釋無法排除。這些限制使本論文成為**深度個案研究**（in-depth case study）而非**廣度調查**（broad survey），其結論的可推廣性（generalizability）受限，但內部效度（internal validity）——即對這兩個特定儲存庫的描述準確性——因證據帳簿的存在而強化。

#### 可重現性評估

本論文在可重現性（reproducibility）方面展現了值得稱道的實踐，但也存在明顯的結構性限制。

**正面因素**：

首先，**證據帳簿**（evidence ledger）的設計直接服務於可重現性：每個數字皆可追溯至具體的產物修訂、提交或檔案。這比僅報告百分比的研究更可信，因為讀者可獨立驗證每個計數。

其次，作者明確區分了**測量**（measurement）與**詮釋**（interpretation）：85.6% 與 21.8% 是測量結果，而「這代表規範性追蹤更可讀」是詮釋——後者附帶了「但記錄的是結論而非過程」的反向詮釋，使讀者能自行評估。

### 實作步驟建議

**步驟一：盤點儲存庫中的 AI 代理產物**
掃描儲存庫，識別兩類產物：
- 規範性追蹤：通常為 `AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等持續性規則檔案所在的目錄
- 敘事性追蹤：通常為單一檔案（如 `scratchpad.md`、`notes.md`），隨工作進展被重寫

**步驟二：測量當前版本的可見度**

**步驟三：計算「不留痕跡的修訂」數量**
統計在所有曾經修訂過該產物的提交中，有多少筆在當前版本中沒有留下任何可見行。本論文實測：規範性追蹤 41 筆修訂中有 15 筆、敘事性追蹤 41 筆修訂中有 18 筆。

**步驟四：審計 Co-Authored-By 標記的覆蓋率**
解析所有 commit message，統計帶有 `Co-Authored-By` trailer 的提交比例，並與其他 AI trailer 鍵（如 `Assisted-by`、`Generated-by`）交叉比對。

**步驟五：建立儲存庫內部代理指標**
選定一個明確的「代理活動代理變項」（如：修訂代理工作筆記的提交數），以此檢驗 Co-Authored-By 標記的敏感度。本論文實測：Project B 中 39 筆修訂工作筆記的提交中，僅 1 筆（2.6%）帶有該標記。

**步驟六：檢驗揭露率的時間穩定性**

**步驟七：建立可稽核的證據帳簿**

### 潛在風險與注意事項

**風險一：將揭露率誤讀為參與率**
Co-Authored-By 標記的覆蓋率反映的是「作者記得加上標記」的比例，而非「AI 實際參與」的比例。本論文明確指出：兩者無法從儲存庫證據中互相轉換。

**風險二：時間序列上的不穩定性**
單一儲存庫內的揭露率可能在無預警的時間點發生階梯式變化（從 2.7% 到 17.7%）。若僅以全期平均值對外發布，會掩蓋此種不穩定性。

**風險三：規範性追蹤的「結論取代過程」問題**
持續性規則檔案傾向記錄「最終該怎麼做」，而非「當時為何這樣決定」。讀者看到的是已被抽象化的指令，而非產生該指令的具體情節。

**風險四：敘事性追蹤的「當前版本不可見」問題**
代理工作筆記在當前 HEAD 通常僅保留最新狀態，過去的計畫、發現與決策過程僅存在於物件資料庫中，需主動遍歷歷史才能還原。

**風險五：混淆變數無法拆解**
本論文明確警告：工具、產物類別、專案、時間四者糾纏在一起，無法將任何觀察到的差異單獨歸因於「工具不同」。任何想複製此實驗的人必須接受此限制。

**風險六：未提交即不存在**
所有可讀性數字皆預設該產物「曾被提交」。若代理產物僅存於工作目錄而從未被 `git add`，則無論其內容多詳盡，都不會出現在稽核範圍內。

**風險七：作者身分無法從儲存庫驗證**
Git 儲存庫不記錄「哪個程序（人或代理）實際撰寫了這次提交」。即使所有 metadata 完整，提交者宣稱的身分仍是自我聲明。

**緩解建議**
- 揭露聲明應明確指出「基於哪些儲存庫證據」與「未涵蓋哪些面向」
- 機構政策應要求作者同時說明 AI 工具的設定與使用期間，而非僅給出最終比率
- 稽核時應同時檢查當前版本與歷史版本，兩者缺一不可

### 與其他技術的整合建議

**與 Git 本身的整合**
- 透過 `commit-msg` hook 強制要求 AI 協助的提交必須包含特定 trailer
- 透過 `pre-commit` hook 自動偵測代理產物檔案是否被修改，提示作者加上揭露標記
- 使用 `git notes` 在不修改既有提交的情況下附加溯源註記

**與密碼學簽章機制的整合**
- 採用 Sigstore、in-toto 等供應鏈完整性框架，將提交與特定身分綁定
- 但需注意：本論文指出此類機制預設「值得驗證的事件已被識別」，這一步本身就需要先解決

**與形式化溯源模型的整合**
- 將 W3C PROV 或 PROV-DM 的實體、活動、代理人三元素對應到 Git 的 commit、檔案變更、提交者
- 設計從 Git 歷史到 PROV 文件的轉換器（已有 `git2prov` 等工具）

**與可再現性框架的整合**
- 與 ReproZip、Binder、Whole Tale 等容器化環境整合，確保「代理曾經跑出這個結果」這件事本身可被重現
- 將代理產物視為可再現性封存的一部分，而非僅是輔助文件

**與學術出版管道的整合**
- 在期刊投稿系統中，要求作者上傳「證據帳簿」而非僅有揭露聲明
- 與 ORCID、CRediT 等作者身分機制整合，區分「人類作者」與「AI 工具貢獻者」

**與 AI 工具本身的整合**
- 工具廠商應在產品中內建「就地擷取」機制，而非依賴使用者記得提交
- 應記錄工具設定歷史、模型版本、提示詞範本，這些是 Git 儲存庫目前完全無法承載的資訊
