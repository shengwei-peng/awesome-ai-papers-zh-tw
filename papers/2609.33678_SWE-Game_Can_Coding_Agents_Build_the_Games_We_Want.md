## 摘要翻譯

我們推出 SWE-Game，這是一個包含 247 項任務的基準測試，基於 41 款可執行參考 Godot 遊戲，涵蓋 2D 與 3D 的 13 個玩法類別。五種任務類型涵蓋：簡報生成遊戲（Brief-to-Game Generation）、GDD 實作遊戲（GDD-to-Game Implementation）、骨架補完（Skeleton Completion）、83 個注入錯誤案例的錯誤修復（Bug Repair），以及 Godot 移植至 Unity（Godot-to-Unity Porting）。參考素材明確規範預期玩法，而共享儀器化介面（Shared Instrumentation Interface）使評測者自有驅動程式（Evaluator-Owned Driver）與評測者自有探針（Evaluator-Owned Probe）能夠執行動作並觀察獨立實作的遊戲。評測結合引擎狀態檢查（Engine-State Check）、認證的參考輸入重播（Reference-Input Replay），以及代理撰寫的功能展示（Agent-Authored Feature Demonstration），以評估機制正確性（Mechanic Correctness）與展示可玩性（Demonstrated Playability）。此外，亦評估修復後行為的還原（Behavioral Restoration）與保留（Behavioral Preservation）。遊戲專屬的視覺語言評分規準（Vision-Language Rubric），則分別評估其呈現品質。在六個模型中，Opus5 在所有五種任務類型中皆達到最高的整體分數。在三個建構任務中，最佳整體分數仍未達 60 分（滿分 100），其中簡報生成遊戲達到 50.38。對審查過的提交作品進行分析，識別出需求遺漏（Requirement Omission）與玩法邏輯錯誤（Gameplay Logic Error）為主要的實作問題。在來自 100 款代理建構遊戲的人類標註行為上，可執行檢查達到 92.59% 的平衡準確率（Balanced Accuracy），相較之下，基於影片的視覺語言模型（VLM）評審僅為 78.41%。基於評分規準的視覺分數與 200 段玩法影片片段的人類評分之間，達到 0.829 的 Spearman 相關係數（Spearman Correlation）。總結而言，這些結果描繪出當前代理在遊戲開發活動中的能力，並支持結合執行階段證據（Runtime Evidence）與視覺評估（Visual Assessment）的做法。

### 核心貢獻（3～5點）
- **提出 SWE-Game 基準測試**：涵蓋 247 項任務、41 款可執行的 Godot 參考遊戲，橫跨 2D 與 3D 的 13 個玩法類別，系統性地評估程式碼代理在遊戲開發中的能力。
- **設計多層次評測機制**：結合引擎狀態檢查、認證的參考輸入重播、代理撰寫的功能展示，以及視覺語言評分規準，分別評估機制正確性、展示可玩性、行為還原與保留，以及遊戲呈現品質。
- **揭示當前代理的能力瓶頸**：在六款模型中，Opus5 於五種任務類型皆表現最佳，但三項建構任務的最高分仍未達 60 分（簡報生成遊戲僅 50.38），主要錯誤來自需求遺漏與玩法邏輯錯誤。
- **驗證執行階段檢查優於純視覺評審**：可執行檢查在人類標註行為上達到 92.59% 的平衡準確率，顯著優於基於影片的 VLM 評審（78.41%）；視覺評分規準與人類評分的 Spearman 相關係數達 0.829，證實結合執行階段證據與視覺評估的必要性。

### 適合對象
- **遊戲 AI 與程式碼代理研究者**：從事 LLM 代理在軟體工程、程式碼生成與遊戲開發領域應用之研究者，可將 SWE-Game 作為評測代理在複雜多檔案專案中能力的基準。
- **遊戲引擎開發者與技術美術**：使用 Godot、Unity 等引擎進行遊戲開發的工程師，可從中了解 AI 代理在遊戲邏輯實作、骨架補完與跨引擎移植上的現況與限制。
- **AI 評測方法論研究者**：對自動化評測、可執行檢查、視覺語言評分規準設計感興趣的研究者，本論文提供了結合執行階段證據與視覺評估的具體範例與量化驗證。
- **遊戲開發教育工作者**：關注 AI 輔助遊戲開發教學與工具設計的教師與從業者，可藉此了解當前 AI 工具的能力邊界與常見錯誤模式。

## 深度分析

#### 方法論解析

SWE-Game 的方法論核心在於建立「可執行參考遊戲 (Executable Reference Game)」作為評測錨點，並透過「共享儀器化介面 (Shared Instrumentation Interface)」將任務規格與評測證據連接起來。整體方法論可拆解為三個相互支撐的支柱：任務設計、儀器化介面、以及多層次評測協議。

**任務設計層面**：研究團隊從 41 個 Godot 參考遊戲中衍生出 247 個任務，涵蓋 13 種玩法類別（橫跨 2D 與 3D），並設計五種任務類型以對應真實遊戲開發工作流：(1) 簡報生成遊戲 (Brief-to-Game Generation) 從簡短描述出發；(2) GDD 實作遊戲 (GDD-to-Game Implementation) 從完整設計文件實作；(3) 骨架補完 (Skeleton Completion) 補齊部分實作的程式碼；(4) 錯誤修復 (Bug Repair) 處理 83 個注入錯誤案例；(5) Godot 移植至 Unity (Godot-to-Unity Porting) 進行跨引擎遷移。這種設計反映了從「從零開始」到「維護遷移」的完整開發光譜。

**儀器化介面層面**：此為方法論最具創新性的部分。介面提供對可玩場景、輸入動作、語義物件角色、以及相關狀態欄位的通用存取。代理提交的實作需將這些角色綁定 (binding) 到自身的物件結構上，使評測者自有的驅動程式與探針能獨立執行操作並檢查引擎狀態。這種設計巧妙地解決了「替代實作 (alternative implementation)」的評測難題——不同代理可能使用不同的物件命名、場景層次結構或程式碼組織方式，但只要它們正確綁定了語義角色，評測器就能一致地進行檢查。以平台跳躍遊戲 (Platformer) 中的尖刺 (spike) 為例，評測器可透過綁定定位玩家與危險物，觀察接觸事件，並檢查預期的血量變化或重生行為。

**多層次評測協議層面**：評測結合三類證據：(1) 引擎狀態檢查 (Engine-State Check) 透過確定性狀態斷言與事件斷言驗證機制正確性；(2) 認證參考輸入重播 (Certified Reference-Input Replay) 評估展示可玩性 (Demonstrated Playability)；(3) 代理撰寫的功能展示 (Agent-Authored Feature Demonstration) 補充行為證據。對於修復任務，評測在參考版、錯誤版、與修復版上執行固定情境，量化行為修復 (Behavioral Restoration) 與行為保留 (Behavioral Preservation)。移植任務則採用對應的 Unity 執行契約。對於遊戲呈現 (Game Presentation)，則使用遊戲特定的視覺語言評分規準 (Vision-Language Rubric) 評估視覺呈現、視覺回饋與素材整合。

此方法論的關鍵洞見在於：單純的視覺證據（如勝利畫面）不足以證明遊戲機制正確，因為玩家可能繞過必要互動；單純的程式碼檢查也不足以證明可玩性。因此，必須結合執行階段證據 (Runtime Evidence) 與視覺評估 (Visual Assessment)，並透過人類標註驗證評測器的有效性。

#### 實驗數據解讀

**整體效能數據**：六個模型在五種任務類型上的評測結果顯示，Opus5 在所有任務類型中皆達到最高整體分數，但其他模型的相對排名隨開發活動而異。最關鍵的數據點是：建構類型任務（簡報生成、GDD 實作、骨架補完）的最佳整體分數皆低於 60/100，其中簡報生成遊戲僅達到 50.38。這表明即使是當前最強的編碼代理，在從規格建構完整可玩遊戲方面仍有顯著差距。

**錯誤分析**：經審查的提交中，需求遺漏 (Requirement Omission) 與玩法邏輯錯誤 (Gameplay Logic Error) 為最主要的實作問題。這暗示代理在兩個層面存在困難：(1) 理解並記住多面向的規格需求；(2) 將需求轉化為正確的互動邏輯。需求遺漏反映的是長上下文理解與追蹤能力的不足，而玩法邏輯錯誤則反映狀態管理、事件處理、與碰撞偵測等遊戲開發核心概念的實作困難。

**評測器有效性驗證**：這是論文中極具價值的方法論貢獻。在 100 個代理建構專案的人類標註行為上，可執行檢查達到 92.59% 的平衡準確率 (Balanced Accuracy)，而基於影片的視覺語言模型評審僅達 78.41%。這 14 個百分點的差距量化了「僅靠觀察」與「執行驗證」之間的可靠性落差，證明了儀器化介面設計的必要性。在視覺評分方面，評分規基準則與 200 個玩法影片的人類評分達到 Spearman 相關係數 0.829，顯示視覺評估管道具有高度可靠性，但仍不如執行檢查精確。

**跨任務類型的相對難度**：從數據可推論：(1) 簡報生成最困難（最高僅 50.38），因為規格最模糊；(2) 骨架補完相對容易，因為部分實作已提供；(3) 錯誤修復與移植的評測維度不同（修復/保留 vs. 功能對等），需分別解讀。值得注意的是，論文中未明確給出各任務類型的具體分數表格，但從摘要描述可推斷建構任務的難度梯度。

**模型間差異的解讀**：Opus5 的全面領先可能反映其在長上下文推理、程式碼生成、與多步驟規劃方面的綜合優勢。其他模型在不同任務上的排名波動暗示：沒有單一模型在所有遊戲開發活動上都佔優，這對實務應用中選擇合適工具具有指導意義。

#### 與現有研究的比較

SWE-Game 在遊戲開發代理評測領域的定位需從「任務覆蓋面」與「評測方法論」兩個軸度來理解。

**任務覆蓋面的擴展**：相較於現有基準，SWE-Game 提供了更全面的開發活動覆蓋。GameDevBench 與 JamBench 涵蓋專案編輯、生成與補完；GameEngineBench 聚焦於 Unreal Engine 的 C++ 整合；GameCraft-Bench 使用重播示範與多模態評分規準處理完整遊戲建構；WebGameBench 透過執行階段互動評估瀏覽器遊戲；GameLogicBench 透過確定性狀態與事件斷言測試機制。SWE-Game 的獨特貢獻在於同時涵蓋建構、維護、與遷移三類活動，並透過共享儀器化介面統一評測方法論，這是先前基準未能實現的。

**評測方法論的演進**：SWE-Game 明確指出「僅靠視覺證據不足」的問題——平台跳躍遊戲可能正確顯示尖刺但允許玩家穿越；勝利畫面可能透過繞過必要互動達成。這種批評與 GameCraft-Bench 的多模態評分規準方法形成對比，後者依賴重播示範與視覺評估。SWE-Game 透過執行階段證據補充視覺評估，提供了更嚴謹的評測保證。論文中可執行檢查 92.59% vs. VLM 評審 78.41% 的對比數據，為「執行驗證優於純視覺評估」的論點提供了量化支持。

**相較於 GameLogicBench 的互補性**：GameLogicBench 強調確定性狀態與事件斷言，SWE-Game 則透過共享儀器化介面實現類似的斷言機制，但進一步支援跨任務類型（修復、移植）的評測。兩者方法論上有共通的哲學基礎，但 SWE-Game 的介面設計更通用。

**限制與不足**：(1) 雖然涵蓋 13 種玩法類別，但 41 個參考遊戲的規模仍有限，可能無法完全代表遊戲開發的多樣性；(2) 評測主要聚焦於 Godot 引擎，移植任務雖涵蓋 Unity，但對其他引擎（如 Unreal、HTML5）的支援未明確說明；(3) 視覺評估的 Spearman 相關係數 0.829 雖高，但仍有約 17% 的變異未被人類評分解釋，這可能反映評分規準設計或 VLM 視覺理解的限制；(4) 代理撰寫的功能展示作為評測輸入可能引入「代理偏見」——代理可能選擇展示其實作良好的功能而迴避問題區域。

**與「代理自評」相關研究的關聯**：SWE-Game 的代理撰寫功能展示機制與近期關於代理自我評估可信度的研究形成有趣對比。雖然論文未深入探討此問題，但這是值得進一步研究的面向。

#### 可重現性評估

從提供的摘要與部分內文中，可重現性資訊的明確程度有限，但可從方法論描述推論若干關鍵點。

**基準資源的可及性**：SWE-Game 作為 arXiv 預印本 (Preprint) 發表，標註日期為 2026 年 10 月。論文中提及 41 個參考 Godot 遊戲、247 個任務、共享儀器化介面、以及視覺語言評分規準，但未在提供的文本中明確說明程式碼、資料集、或評測工具是否開源。從學術慣例推測，基準的程式碼與資料通常會伴隨論文發布，但需查閱完整論文或專案頁面確認。

**評測管道的可重現性**：方法論描述提供了足夠細節以理解評測流程——引擎狀態檢查、認證參考輸入重播、代理撰寫功能展示的組合。然而，要完全重現評測，需要：(1) 41 個參考遊戲的完整實作；(2) 共享儀器化介面的規範；(3) 評測驅動程式與探針的實作；(4) 視覺語言評分規準的具體內容；(5) 人類標註資料（100 個專案的行為標註、200 個影片的評分）。這些元素的開源狀態直接影響可重現性。

**模型評測的可重現性**：六個模型的評測結果應可在相同基準上重現，但需注意：(1) 模型版本與 API 快照時間會影響結果；(2) 代理執行環境（隨機性、並行度）可能引入變異；(3) 評測中的某些環節（如代理撰寫功能展示）涉及隨機性。

**人類驗證資料的價值**：100 個專案的行為標註與 200 個影片的人類評分是寶貴的驗證資源，若公開將極大促進後續研究——其他研究者可使用這些資料驗證新的評測方法或訓練專門的評測模型。

**改進建議**：為提升可重現性，論文應明確提供：(1) 基準資料與程式碼的 GitHub 連結；(2) 評測管道的詳細文件；(3) 人類標註資料的釋出計畫；(4) 模型評測的標準化協議（如溫度設定、最大步數、工具配置）。

#### 未來研究方向

SWE-Game 開啟了多條值得探索的研究路徑，從評測方法論的精進到代理能力的提升。

**評測方法論的延伸**：(1) 將共享儀器化介面概念擴展至其他引擎（Unreal、Unity 原生專案、HTML5/瀏覽器遊戲），建立跨引擎評測標準；(2) 探索「評測器自適應」——評測器根據代理實作自動推斷綁定，而非要求預定義綁定，這將降低任務設計成本並支援更開放的實作空間；(3) 結合執行階段證據與更細粒度的視覺評估，例如追蹤特定視覺元素（如血條、分數）的動態變化，而非僅評估整體呈現品質。

**代理能力的提升方向**：(1) 針對識別出的兩大主要錯誤類型（需求遺漏與玩法邏輯錯誤），研究專門的改進策略——前者可透過更好的需求追蹤與檢查清單機制，後者可透過遊戲開發特定的領域知識注入或測試驅動開發流程；(2) 探索多模態規劃——代理在實作前先產生視覺原型或互動流程圖，再據此生成程式碼，可能減少邏輯錯誤；(3) 研究「迭代式修復」工作流——代理在初步實作後自動執行自我測試並修復，而非一次性生成完整實作。

**基準的擴展**：(1) 增加參考遊戲的規模與多樣性，特別是當前覆蓋較少的類型（如策略遊戲、模擬遊戲、敘事遊戲）；(2) 引入多人遊戲與網路功能的評測；(3) 增加長期專案（跨多個開發階段）的評測，追蹤代理在持續開發中的表現；(4) 探索「使用者體驗」維度的評測——不僅是功能正確，還包括遊戲手感、難度曲線、學習曲線等主觀品質。

**人類-AI 協作模式**：(1) 研究人類開發者與代理協作的最佳工作流——人類提供創意方向與品質判斷，代理處理實作細節；(2) 探索「代理作為團隊成員」的多代理協作模式，不同代理負責不同開發活動（設計、實作、測試、美術）；(3) 研究如何利用 SWE-Game 的錯誤分析結果設計更有效的代理訓練資料或提示策略。

**評測可信度的深化**：(1) 擴大人類標註規模，建立統計上更穩健的評測器有效性驗證；(2) 研究評測器在不同遊戲類型上的可靠性差異，識別評測的盲區；(3) 探索「對抗性評測」——設計刻意誘使代理失敗的任務，測試評測器是否能正確識別失敗；(4) 研究評測結果與實際部署表現的相關性，驗證基準的外部效度。

**跨領域應用**：SWE-Game 的方法論（可執行參考、共享介面、多層次評測）可應用於其他需要「規格到實作」轉換的領域——如網頁應用開發、機器人控制、嵌入式系統等。這種方法論的泛化是值得探索的方向。

## 論文問答

**Q1：為什麼遊戲開發對程式碼代理（coding agent）來說是個特別困難的任務？**
A：遊戲開發要求代理同時協調程式碼、素材（assets）與引擎行為，將它們整合為一個互動體驗，而不僅僅是產出可執行的程式。代理必須將玩法示範（gameplay demonstration）翻譯為具體的機制（mechanics）、進程（progression）與呈現（presentation），並在專案完成、修復或遷移時保留原本預期的玩法。這種從「意圖」到「可互動實作」的多層次轉換，使得遊戲開發比一般軟體工程任務更為複雜，因為最終的可玩性取決於玩家輸入、視覺回饋與底層邏輯之間的緊密耦合。

**Q2：現有的遊戲基準測試（如 GameDevBench、GameCraft-Bench、WebGameBench 等）有哪些不足？**
A：現有基準測試在「開發活動覆蓋範圍」與「評估方式」上各有局限：GameDevBench 與 JamBench 涵蓋專案編輯、生成與補完，但缺乏跨引擎遷移；GameEngineBench 僅檢視 Unreal Engine 的 C++ 整合；GameCraft-Bench 仰賴重播示範與多模態評分規準（multimodal rubrics），但難以驗證底層互動邏輯；WebGameBench 透過執行階段互動（runtime interaction）評估瀏覽器遊戲；GameLogicBench 則以確定性狀態與事件斷言測試機制。SWE-Game 的差異化在於橫跨建構、維護與遷移三類活動，並透過可執行參考遊戲將任務規格與評估證據緊密連結。

**Q3：為什麼單純的視覺評估或執行測試不足以評估遊戲代理？**
A：單純的視覺評估容易被「看起來正確但邏輯錯誤」的實作欺騙，例如平台跳躍遊戲（platformer）可能正確顯示尖刺圖示，卻允許玩家直接穿越而無受傷效果；同樣地，僅檢查是否抵達勝利畫面（victory screen）也不足，因為所需互動可能已被繞過。因此 SWE-Game 結合執行階段證據（runtime evidence）與視覺評估（visual assessment），前者透過引擎狀態檢查（engine-state check）與參考輸入重播（reference-input replay）驗證機制正確性（mechanic correctness），後者則透過視覺語言評分規準（vision-language rubric）評估遊戲呈現（game presentation），兩者互補才能完整描繪代理能力。

**Q4：SWE-Game 的核心設計理念是什麼？什麼是「可執行參考遊戲（executable reference game）」？**
A：SWE-Game 的核心設計理念是「以可執行參考遊戲建立任務規格與評估之間的具體連結」。每個任務都基於一個真正可在 Godot 引擎中執行的參考遊戲，這些參考遊戲橫跨 13 個玩法類別（gameplay category）的 2D 與 3D 作品。任務專屬的影片、素材、需求與專案程式碼共同傳達預期的體驗，而可執行參考則為評估提供具體基準。這種設計讓評測者能夠對代理的實作進行「等價性比對」，而不僅僅是表面相似度的判斷。

**Q5：共享儀器化介面（shared instrumentation interface）如何解決不同實作之間的等價性問題？**
A：由於不同代理可能使用不同的物件名稱、場景層級結構與程式碼來實作相同功能，評測需要一個抽象層來對應這些差異。SWE-Game 的共享儀器化介面提供對可玩場景、輸入動作、語意物件角色與相關狀態欄位的通用存取點，提交作品將這些角色綁定到自己的結構上，使評測者自有的驅動程式（evaluator-owned driver）與探針（evaluator-owned probe）能夠執行操作並檢查引擎狀態。例如在尖刺範例中，這種綁定讓評測者能定位玩家與危險物件、觀察接觸事件，並檢查預期的血量變化或重生機制是否真的發生。

**Q6：SWE-Game 包含哪五種任務類型？它們各自評估什麼能力？**
A：SWE-Game 包含五種任務類型：(1) 簡報生成遊戲（brief-to-game generation）從簡短描述開始建構完整遊戲；(2) GDD 實作遊戲（GDD-to-game implementation）根據詳細的遊戲設計文件（game design document, GDD）實作；(3) 骨架補完（skeleton completion）填入預留函式中的待辦邏輯；(4) 錯誤修復（bug repair）處理 83 個注入錯誤案例（injected-fault case），評估行為修復（behavioral restoration）與行為保留（behavioral preservation）；(5) Godot 移植至 Unity（Godot-to-Unity porting）考驗跨引擎遷移能力。前三類屬於建構任務，後兩類則分別屬於維護與遷移活動。

**Q7：SWE-Game 的規模和組成是怎樣的？**
A：SWE-Game 包含 247 個任務，奠基於 41 個可執行的 Godot 參考遊戲，這些遊戲橫跨 13 個玩法類別，涵蓋 2D 與 3D 作品。除了 83 個錯誤修復案例外，其餘四種任務類型各包含 41 個任務。這樣的規模讓基準測試既能提供足夠的統計意義，又能維持每個任務的深度與品質。任務規格結合影片、素材、需求文件與專案程式碼，允許替代性實作但要求保留預期行為。

**Q8：主要的實驗結果是什麼？Opus5 的表現如何？**
A：在六個模型的評比中，Opus5 在全部五種任務類型中都達到最高的整體分數，展現其在遊戲開發活動中的領先地位。然而，即使是最佳模型，在三個建構任務上的整體分數仍低於 60 分（滿分 100），其中簡報生成遊戲僅達到 50.38 分。這顯示目前的程式碼代理在完整遊戲建構上仍有相當大的進步空間。其他模型的相對排名則隨開發活動而異，說明不同任務類型對模型能力的要求並不一致。

**Q9：評測者的有效性如何？執行檢查與視覺評估的比較結果是什麼？**
A：SWE-Game 透過人類標註的行為資料驗證評測者的有效性：在 100 個代理建構專案的人類標註行為上，執行檢查達到 92.59% 的平衡準確率（balanced accuracy），遠高於基於影片的視覺語言模型（VLM）裁判的 78.41%。在視覺評估方面，基於評分規準的視覺分數在 200 個玩法影片的人類評分上達到 0.829 的 Spearman 相關係數。這些結果支持結合執行階段證據與視覺評估的雙軌評估策略，並證明 SWE-Game 的評測設計能有效反映人類對遊戲品質的判斷。

**Q10：SWE-Game 對遊戲開發產業有什麼實際應用價值？**
A：SWE-Game 為遊戲開發團隊提供了一個評估 AI 代理在真實開發流程中表現的標準化工具，涵蓋從簡報到移植的完整活動鏈。透過識別需求遺漏（requirement omission）與玩法邏輯錯誤（gameplay logic error）作為主要實作問題，團隊能更具體地了解 AI 助手在哪些環節需要人類監督。這有助於企業在採用 AI 工具時設定合理的期望值，並設計人機協作流程，讓代理負責初版實作、開發者負責審查與精修。

**Q11：SWE-Game 的設計如何影響 AI 程式碼代理的產品開發？**
A：SWE-Game 強調「執行階段證據」與「視覺評估」並重的雙軌評估，這對代理產品的設計有直接啟示：產品需要整合執行測試、視覺回饋與人類審查機制，而不僅僅是程式碼生成。共享儀器化介面的概念也提示產品應提供標準化的測試掛載點，使代理實作能被自動化驗證。此外，跨引擎移植任務的設計鼓勵產品支援多引擎工作流，反映真實開發中常見的技術棧轉換需求。

**Q12：SWE-Game 對遊戲 AI 研究領域有什麼更廣泛的影響？**
A：SWE-Game 將遊戲開發從「生成可玩片段」提升為「完整開發工作流的基準測試」，推動研究從單一能力（如關卡生成、視覺風格轉換）走向整合性的代理能力評估。其「可執行參考遊戲」與「共享儀器化介面」的設計模式可被其他領域借鏡，例如機器人模擬、網頁應用開發等需要「意圖—實作—驗證」閉環的場景。透過量化 VLM 裁判與執行檢查的差距，該研究也凸顯了視覺語言模型在細粒度行為驗證上的侷限，為未來多模態評估研究指明方向。

**Q13：SWE-Game 目前有哪些已知的局限性？**
A：SWE-Game 目前以 Godot 引擎為主要參考，雖然包含 Godot 移植至 Unity 的任務，但對 Unreal Engine 等其他主流引擎的支援有限。基準測試的 41 個參考遊戲雖然橫跨 13 個玩法類別，但相較於商業遊戲的多元性仍屬小規模。此外，評估主要聚焦於機制正確性與視覺呈現，對音效、敘事深度、長期可玩性等面向的覆蓋較少。任務規格雖然允許替代實作，但仍受限於參考遊戲的設計空間，可能無法完全捕捉創新性的玩法變體。

**Q14：代理在任務中常見的失敗模式是什麼？**
A：根據審查提交的分析，需求遺漏（requirement omission）與玩法邏輯錯誤（gameplay logic error）是兩大主要實作問題。需求遺漏意味著代理未能完整解讀任務規格中的所有約束，導致部分功能缺失；玩法邏輯錯誤則指代理雖然實作了功能，但底層邏輯無法正確產生預期的互動效果。這兩類錯誤凸顯了代理在「理解意圖」與「正確實作」兩個環節的薄弱之處，也說明為何即使 Opus5 在簡報生成任務上也僅達到 50.38 分。

**Q15：SWE-Game 未來可以如何擴展或改進？**
A：未來可從幾個方向擴展 SWE-Game：增加更多參考遊戲與玩法類別以提升多樣性；納入 Unreal Engine、Unity 原生等更多引擎的任務；擴展評估面向以涵蓋音效、敘事與長期可玩性；引入更具挑戰性的任務，例如多人遊戲機制或跨平台部署。此外，可進一步研究如何讓評測介面支援更複雜的語意綁定，或整合大型語言模型作為輔助評審，以處理目前執行檢查難以覆蓋的創意性與美學評估。這些擴展將使 SWE-Game 成為更全面的遊戲開發代理評估平台。

## 實務應用指南

### 適用場景

1. **獨立遊戲工作室的 AI 輔助開發管線**：小型團隊可將 SWE-Game 的「簡報生成遊戲」與「GDD 實作遊戲」任務類型作為內部原型驗證工具，讓編碼代理根據一段文字描述或設計文件快速產出可執行的 Godot 雛型，再由設計師迭代美術與關卡，縮短從概念到可玩版本的前置時間。

2. **遊戲引擎遷移專案的自動化驗證**：當工作室需要將既有 Godot 專案移植到 Unity（例如跨平台發行或團隊技術棧統一）時，可採用「Godot 移植至 Unity」任務類型作為驗收基準，透過共享儀器化介面比對移植前後的行為一致性，減少人工回歸測試成本。

3. **程式教學與能力評估平台**：教育機構可將 SWE-Game 的 247 個任務作為遊戲開發課程的實作題庫，學生提交的程式會被自動評分（機制正確性、展示可玩性、視覺呈現），教師可專注於程式碼審查與設計討論。

4. **AI 編碼代理的內部基準測試**：模型開發團隊可在模型發版前以 SWE-Game 評估其在「建構—修復—移植」三類活動上的綜合表現，特別關注需求遺漏與玩法邏輯錯誤這兩類被論文點名為主要失敗模式的問題。

5. **遊戲品質保證（QA）自動化**：QA 團隊可借用「錯誤修復」任務類型的注入錯誤案例（共 83 個）作為迴歸測試套件，模擬腳本、場景、資源三類缺陷，評估修復代理是否能同時恢復損壞行為並保留原有功能。

### 實作前置條件

**資料準備**
- 41 個可執行的 Godot 參考遊戲原始碼與對應素材（2D 與 3D 各覆蓋 13 種玩法類別），需具備合法授權以供改作與衍生任務。
- 每個參考遊戲需產出至少三種參考材料：簡報（一句話描述）、GDD（結構化設計文件）、骨架程式碼（含 `TODO` 標記的待補完函式）。
- 83 個注入錯誤案例的故障版本與對應的「正確行為」基準紀錄。
- 200 段以上的遊玩影片片段，用於視覺評分規準的人類標註與 Spearman 相關性驗證。

**運算資源**
- Godot 4.x 與 Unity 對應版本的執行環境（建議容器化以便批次評測）。
- 視覺語言模型（VLM）的推論資源，論文中 VLM 評審在影片判斷上僅達 78.41% 平衡準確率，顯示需要相當規模的 GPU 資源才能與人類判斷競爭。
- 自動化驅動程式與探針的執行環境，需能模擬鍵盤滑鼠輸入並擷取引擎狀態、事件與幀畫面。

**技能門檻**
- 熟悉 Godot（GDScript）與 Unity（C#）雙引擎的場景結構、輸入系統與節點／元件生命週期。
- 能撰寫或修改「共享儀器化介面」，理解語意物件角色綁定（semantic object role binding）的設計模式。
- 具備 VLM 提示工程（prompt engineering）經驗，以產出與人類評分高度相關（Spearman ≥ 0.8）的視覺評分規準。
- 對遊戲機制（碰撞、計時、狀態機、重生、勝利條件）有除錯與測試設計能力。

### 實作步驟建議

1. **建立參考遊戲語料庫**：先挑選或開發 41 個涵蓋 13 種玩法類別的可執行 Godot 遊戲，確保每個遊戲都通過「無操控也能展示完成」的對照測試（matched no-input control），避免出現「畫面過關但實際繞過互動」的偽陽性。

2. **設計儀器化介面**：在參考遊戲中實作共通介面，暴露可玩場景、輸入動作、語意物件角色（如「玩家」「障礙物」「目標物」）與相關狀態欄位。提交作品只需綁定自身結構到此介面，評測者即可用自有驅動程式與探針執行測試。

3. **衍生五類任務**：依序產出（a）簡報生成遊戲、（b）GDD 實作遊戲、（c）骨架補完、（d）錯誤修復、（e）Godot 移植至 Unity。每個非修復任務 41 個，修復任務 83 個，總計 247 個。

4. **建立評測組合**：整合三層評估——引擎狀態檢查（機制正確性）、認證參考輸入重播（行為修復與保留）、代理撰寫的功能展示（展示可玩性），並為建構任務加上視覺語言評分規準。

5. **人類標註與驗證**：蒐集至少 100 個代理建構遊戲的人類標註行為資料，以及 200 段遊玩影片的人類評分，用以驗證可執行檢查（目標 92.59% 平衡準確率）與視覺評分（目標 Spearman 0.829）。

6. **基準測試與迭代**：以六款模型（含 Opus5）進行基準測試，記錄需求遺漏與玩法邏輯錯誤的發生率，作為後續模型微調或提示工程的改進依據。

### 潛在風險與注意事項

- **偽陽性過關**：僅靠影片或勝利畫面無法驗證互動是否真實發生。論文已示範平台跳躍遊戲可能顯示尖刺正確但允許玩家穿過。緩解方式：強制使用「無操控對照組」與引擎狀態檢查，確認完成路徑依賴玩家輸入。

- **視覺評分與人類判斷的落差**：VLM 在影片判斷上僅 78.41% 平衡準確率，遠低於可執行檢查的 92.59%。緩解方式：將視覺評分定位為「功能性證據的補充」而非主要依據，並以人類標註持續校正評分規準。

- **任務難度過高導致天花板效應**：最佳模型在三大建構任務得分仍低於 60/100，簡報生成遊戲僅 50.38。緩解方式：將評分視為相對比較而非絕對門檻，並對任務難度做分層（例如區分「基礎機制」與「進階機制」）。

- **語意綁定的維護成本**：當代理採用非預期的物件命名或場景結構時，評測者需重新撰寫綁定腳本。緩解方式：提供寬鬆的綁定 API（如以標籤、群組或介面實作為線索），並允許代理在提交時一併提供綁定宣告檔。

- **移植任務的引擎差異**：Godot 與 Unity 在輸入系統、實體生命週期、資源管線上存在根本差異，純行為對齊可能掩蓋效能或平台相容性問題。緩解方式：在評測中加入幀率、記憶體與平台特定 API 呼叫的次要指標。

- **注入錯誤的代表性偏差**：83 個錯誤案例若集中於腳本層，可能低估場景與資源類缺陷的修復難度。緩解方式：定期擴充錯誤案例庫，並依缺陷類型分層報告修復率。

### 與其他技術的整合建議

- **與 CI/CD 整合**：將 SWE-Game 的評測管線接入 GitHub Actions 或 Jenkins，每次提交自動跑對應任務類型的子集（例如修復任務），把平衡準確率與 Spearman 相關性作為品質門檻。

- **與既有基準互補**：SWE-Game 聚焦 Godot／Unity 與建構—修復—移植全循環，可與 GameCraft-Bench（多模態評分）、WebGameBench（瀏覽器遊戲執行階段互動）、GameLogicBench（確定性狀態與事件斷言）、GameEngineBench（Unreal C++ 整合）形成互補的評測矩陣，避免單一基準的盲區。

- **與編碼代理框架整合**：可作為 SWE-bench、RepoBench 等程式碼基準的「遊戲領域特化版」，評估代理在大型資產、場景圖與引擎 API 環境下的表現，而不限於純文字程式碼。

- **與 VLM 評審管線整合**：將視覺評分規準模組化，使其可獨立呼叫，方便日後替換為更強的視覺模型或人類專家審查，同時保留 Spearman 相關性作為模型選擇指標。

- **與資產生成工具整合**：搭配程式碼代理與圖像／動畫生成模型（例如基於擴散模型的素材生成），形成「文字→素材→程式→評測」的端到端工作流，特別適合獨立遊戲工作室的快速原型階段。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與圖 2 的整體流程圖，理解 SWE-Game 想解決的問題——為什麼「畫面看起來對」不足以證明遊戲機制正確。接著閱讀「簡報生成遊戲」與「骨架補完」兩個任務類型的範例，親自嘗試在 Godot 中實作一個迷你平台跳躍遊戲並用「無操控對照組」驗證，最後再回頭看評測章節，會更容易掌握術語。

**給 AI 工程師**：重點放在「共享儀器化介面」的設計與「評測者自有驅動程式與探針」的實作模式，這是將領域知識編碼為可自動化檢查的典型範例。同時關注 VLM 與可執行檢查的準確率落差（78.41% vs 92.59%），思考如何在自家產品的評測管線中結合兩種證據類型，並以人類標註作為校正基準。

**給研究者**：論文提供了完整的失敗模式分類（需求遺漏、玩法邏輯錯誤）與跨任務類型的模型排名變動，這些是分析編碼代理泛化能力的素材。建議進一步研究：（1）為何 Opus5 在所有任務皆居首但其他模型排名不穩定；（2）視覺評分規準如何設計才能逼近人類 Spearman 0.8 以上；（3）移植任務中引擎差異對行為保留率的影響。

**給產品經理**：把 SWE-Game 視為「AI 輔助遊戲開發」這類產品的驗收框架——它告訴我們當前 AI 在建構任務上仍不及格（<60 分），但在修復與移植上已有實用價值。建議將產品定位為「加速原型與自動化修復」而非「全自動遊戲生成」，並把視覺評分與可執行檢查的雙軌評測作為對客戶展示品質承諾的依據。
