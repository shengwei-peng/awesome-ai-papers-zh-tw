## 摘要翻譯

大型語言模型（Large Language Model, LLM）已從語言生成器（Language Generator）演進為能夠執行複雜長期任務（Long-horizon Tasks）的自主智能體（Autonomous Agent）。這一演進催生了多種範式，包括激發模型能力的提示工程（Prompt Engineering）、管理資訊存取的上下文工程（Context Engineering）、組織外部工具與資源（External Tools and Resources）的駕馭工程（Harness Engineering），以及支援持續反思（Reflection）與自我改進（Self-improvement）的迴路工程（Loop Engineering）。然而，隨著任務日益複雜，個體智能（Individual Intelligence）面臨根本性的限制：許多任務需要異質專業知識（Heterogeneous Expertise）、相互依賴的子任務（Interdependent Subtasks）、平行執行（Parallel Execution）、獨立驗證（Independent Verification）與持續狀態（Persistent State），已超越任何單一智能體的組織能力。僅靠增強單一智能體的能力或上下文，無法解決這種架構層面的錯配；智能必須分散於專業化智能體之間，並在系統層級加以組織。我們稱之為系統智能（System Intelligence）：即智能體系統（Agent System）將多個智能元件組織並協調成一個連貫且具適應性的整體，以追求共享目標（Shared Objective）的能力。實現系統智能不僅僅是增設智能體；它需要明確的結構來組織工作、協調異質智能體，並維護不斷演化的執行狀態（Execution State）。我們介紹圖工程（Graph Engineering），這是面向新一代智能體系統的新興範式。與先前主要最佳化個體互動或智能體層級行為的範式不同，圖工程建構出用以表示任務、智能體與系統狀態的顯式（Explicit）、動態（Dynamic）且演化（Evolving）圖結構（Graph Structure）——即任務圖（Task Graph）、智能體圖（Agent Graph）與系統狀態圖（System State Graph）。這些抽象為組織複雜目標、編排（Orchestration）異質智能體、建模系統動態，以及實現可擴展的智能體演化（Scalable Agent Evolution）提供了統一的基礎。我們系統性地回顧針對 LLM 智能體（LLM Agent）的圖工程原理、方法論與應用。相關論文、開源資料與專案收錄於 https://github.com/DEEP-JLU/Awesome-Graph-Engineering。

### 核心貢獻（3～5點）
- 提出系統智能（System Intelligence）概念，主張當任務涉及異質專業、相互依賴子任務與持續狀態時，智能必須在系統層級組織與協調，而非僅仰賴單一智能體的個體智能（Individual Intelligence）。
- 引入圖工程（Graph Engineering）作為新一代 LLM 智能體（LLM Agent）系統的新興範式，透過顯式、動態且演化的圖結構統一表示任務、智能體與系統狀態。
- 闡明圖工程如何支援複雜目標組織、異質智能體編排（Orchestration）、系統動態建模，以及可擴展的智能體演化（Scalable Agent Evolution）。
- 系統性回顧圖工程在 LLM 智能體上的原理、方法論與應用，並整理相關論文、開源資料與專案資源。

### 適合對象
適合對多智能體系統、LLM 智能體架構與系統層級協調有興趣的研究者與工程師，特別是關注如何透過圖結構組織任務、編排異質智能體，以及設計可擴展、可演化的自主智能體系統的讀者。

## 深度分析

#### 方法論解析

本論文提出 **Graph Engineering（圖工程）** 作為繼 **Prompt Engineering（提示工程）**、**Context Engineering（上下文工程）**、**Harness Engineering（駕馭工程）** 與 **Loop Engineering（迴路工程）** 之後，邁向 **System Intelligence（系統智能）** 的新興典範。其核心方法論並非單純擴充單一 **LLM Agent（LLM 智能體）** 的能力或上下文，而是將「任務（task）」、「智能體（agent）」與「系統狀態（system state）」顯式地建模為動態且可演化的圖結構，從而在系統層級組織異質元件並協調其執行。

具體而言，Graph Engineering 的方法論可拆解為三大結構化支柱：

1. **Task Organization（任務組織）— 結構化「要做什麼」**
   - **Goal Decomposition（目標分解）**：將複雜的長期目標拆解為相互依賴的子目標，形成 **Task Graph（任務圖）**。這不僅是線性拆解，更強調子任務之間的依賴、先後順序與可平行化區塊。
   - **Workflow Optimization（工作流程最佳化）**：在任務圖的基礎上進行執行路徑最佳化，例如排程、資源分配與瓶頸消除，使整體執行效率最大化。

2. **Agent Coordination（智能體協調）— 結構化「由誰執行」**
   - **Agent Capability Modeling（智能體能力建模）**：將每個智能體的專長、可用工具與限制建模為節點屬性，便於根據任務需求進行匹配。
   - **Agent Team Organization（智能體團隊組織）**：依據任務圖的結構動態組建智能體團隊，形成 **Agent Graph（智能體圖）**。
   - **Multi-agent Communication（多智能體通訊）**：定義智能體之間的訊息傳遞協議，避免冗餘溝通或資訊孤島，並支援獨立驗證與協作。

3. **Runtime State Management（執行期狀態管理）— 結構化「系統如何運作」**
   - **State Recording（狀態記錄）**：持續追蹤執行過程中的 **Execution State（執行狀態）**，形成 **System State Graph（系統狀態圖）**。
   - **Fault Localization（故障定位）**：利用圖結構追溯錯誤來源，快速定位哪個子任務或哪個智能體導致失敗。
   - **Failure Recovery（故障恢復）**：基於狀態圖進行回溯、重試或重新規劃，提升系統的魯棒性。

此外，論文進一步提出 **System Evolution（系統演化）**，強調 Graph Engineering 不僅是靜態設計，更支援隨執行經驗持續調整圖結構，實現 **Scalable Agent Evolution（可擴展的智能體演化）**。整體方法論的關鍵貢獻在於：將過去隱含於單一智能體內部的規劃、記憶與協調機制，轉化為顯式、可解釋、可操作的圖抽象，從而突破 **Individual Intelligence（個體智能）** 的架構性限制。

#### 實驗數據解讀

需要特別指出的是，本論文屬於綜述性與架構性論文，並非以單一模型或單一基準測試為主的實證研究。因此，文中並未提出作者自行設計的對照實驗或新的量化指標，而是透過系統性回顧現有文獻、開源專案與評測基準，來論證 Graph Engineering 的必要性與可行性。

在 **Section 7: Benchmarks, Datasets, and Evaluation（基準、資料集與評估）** 中，作者將評估對象分為三個層級：

- **Model Intelligence（模型智能）**：評估基礎模型本身的語言理解、推理與生成能力，例如透過標準化測試衡量預訓練與後訓練效果。
- **Individual Intelligence（個體智能）**：評估單一 LLM Agent 在提示工程、上下文管理、工具使用與迴路執行上的表現，例如 **ReAct**、**Reflexion**、**LATS** 等方法。
- **System Intelligence（系統智能）**：評估多智能體系統在任務分解、協調、狀態管理與演化上的整體表現，這正是 Graph Engineering 所關注的層級。

作者在 **Section 7.4 Evaluation Principles and Open Challenges（評估原則與開放挑戰）** 中指出，現有基準大多仍聚焦於單一智能體或單一任務的表現，缺乏能夠同時衡量「結構正確性」、「協調效率」、「狀態一致性」與「長期適應性」的系統級評估框架。這意味著 Graph Engineering 雖然在概念上提供了完整的架構，但其實證基礎仍高度依賴於現有分散的開源實作與應用案例，尚未形成統一的量化標準。

因此，對於期待看到「新模型打敗舊模型」式實驗結果的讀者而言，本論文的價值不在於提供新的數據點，而在於指出未來評估 System Intelligence 時應關注哪些維度：例如任務圖的分解品質、智能體圖的協調開銷、狀態圖的可追溯性，以及系統在面對動態環境時的演化能力。

#### 與現有研究的比較

本論文將 LLM Agent 的發展劃分為四個階段，並明確定位 Graph Engineering 為下一階段的核心典範：

| 階段 | 代表典範 | 核心關注 | 主要限制 |
|---|---|---|---|
| Model Intelligence（模型智能） | Foundation Model（基礎模型） | 預訓練與後訓練 | 僅具備通用能力，無法直接處理複雜任務 |
| Individual Intelligence（個體智能） | Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering | 激發單一智能體能力、管理上下文、整合工具、支援迭代執行 | 受限於單一智能體的組織與協調能力 |
| System Intelligence（系統智能） | Graph Engineering | 多智能體的顯式結構化組織與協調 | 仍在早期，缺乏統一基準與成熟作業系統 |

與現有研究的比較可從以下幾個面向展開：

1. **相較於單一智能體方法**
   現有方法如 **ReAct**、**Reflexion**、**LATS**、**AdaPlanner** 等，雖然透過 **Loop Engineering（迴路工程）** 強化了單一智能體的反思與規劃能力，但仍無法有效處理需要 **Heterogeneous Expertise（異質專業知識）**、**Parallel Execution（平行執行）** 與 **Independent Verification（獨立驗證）** 的任務。Graph Engineering 將這些需求從「單一智能體內部的隱式規劃」提升為「系統層級的顯式結構」。

2. **相較於現有 Multi-Agent System（多智能體系統）**
   許多多智能體框架（如 **AutoGen**、**MetaGPT**、**CAMEL**）已經引入角色分工與通訊機制，但大多數框架的協調結構是隱含或固定的。Graph Engineering 的差異在於強調「圖」作為第一級抽象：任務圖、智能體圖與狀態圖都是動態且可演化的，這使得系統能夠根據執行過程持續調整結構，而非僅依賴預先定義的角色與流程。

3. **相較於其他 Graph-based Approaches（基於圖的方法）**
   作者在附錄 **Section 11.2 Distinction with Graph-based Approaches in Agents** 中特別區分了 Graph Engineering 與過去在智能體中使用圖的方法。傳統方法多將圖用於知識表示、記憶檢索或規劃搜尋（例如將知識庫建模為圖、將規劃過程視為圖搜尋），而 Graph Engineering 則將圖同時應用於任務組織、智能體協調與系統狀態管理，並強調圖結構的動態演化能力。

4. **主要限制**
   - **理論架構強於實證基礎**：Graph Engineering 提供了一個宏觀框架，但許多具體演算法（如動態任務圖重構、智能體圖最佳化）仍待深入研究。
   - **缺乏統一基準**：如前文所述，System Intelligence 的評估標準尚未成熟，難以客觀比較不同 Graph Engineering 實作的優劣。
   - **工程複雜度高**：相較於單一智能體或固定多智能體框架，Graph Engineering 需要額外的圖建構、維護與演化機制，對開發者與運算資源都提出更高要求。

#### 可重現性評估

本論文作為綜述與架構性研究，並未附帶作者自行開發的原始碼、模型權重或專有資料集。然而，作者在摘要與論文末尾提供了一個資源彙整頁面：

> https://github.com/DEEP-JLU/Awesome-Graph-Engineering

該倉庫收錄了與 Graph Engineering 相關的論文、開源資料與專案，對於希望重現或延伸相關研究的讀者具有重要參考價值。

在 **Section 8: Open-Source Libraries and Engineering Ecosystem（開源函式庫與工程生態）** 中，作者進一步梳理了支援不同層級智能的開源工具：

- **Model Intelligence（模型智能）**：如 **Transformers**、**vLLM**、**LLaMA** 系列等，提供基礎模型推理與微調能力。
- **Individual Intelligence（個體智能）**：如 **LangChain**、**LlamaIndex**、**AutoGPT**、**Semantic Kernel** 等，支援提示管理、工具整合與記憶機制。
- **System Intelligence（系統智能）**：如 **AutoGen**、**MetaGPT**、**CAMEL**、**AgentScope** 等，提供多智能體協作框架。

值得注意的是，雖然這些工具為 Graph Engineering 的實作提供了基礎設施，但目前尚無一個完全以「圖」為核心抽象、並同時涵蓋任務圖、智能體圖與狀態圖的成熟開源框架。作者在 **Section 8.4 Open Challenges in the Engineering Ecosystem** 中也指出，現有生態系統在圖結構的標準化、動態演化支援、除錯與可視化工具方面仍存在明顯缺口。

因此，本論文的可重現性可評估為「概念可重現、實作需整合」：讀者可以根據論文提出的框架，結合現有開源工具進行實作，但無法直接下載一個現成的 Graph Engineering 系統來複製論文結果。對於希望進一步驗證的研究者，建議從該 GitHub 倉庫出發，選擇適合的開源專案進行擴充與比較。

#### 未來研究方向

本論文在 **Section 5: Open Challenges and Research Opportunities（開放挑戰與研究機會）** 與 **Section 6: Future Direction: Ontology Engineering for Next-Generation System Intelligence（未來方向：下一代系統智能的本體工程）** 中，提出了多個值得後續深入研究的方向：

1. **Graph-Native Capability Substrates（圖原生能力基板）**
   未來需要專門為圖結構設計的基礎能力，例如圖神經網路（GNN）與 LLM 的深度融合、圖結構感知的推理與規劃演算法，以及支援動態圖更新的高效資料結構與儲存系統。

2. **Self-Evolving Graph Systems（自我演化的圖系統）**
   目前的 Graph Engineering 多強調人為設計的圖結構，未來應探索讓系統在執行過程中自動學習、重構與最佳化圖結構，包括自動發現新的智能體角色、新的任務分解模式，以及新的協調協議。

3. **Graph-Native Agent Operating Systems（圖原生智能體作業系統）**
   類似傳統作業系統管理程序、記憶體與檔案系統，未來可能出現專門管理智能體、任務圖與狀態圖的作業系統，提供排程、資源分配、隔離、除錯與安全等基礎服務。

4. **Privacy and Ethics（隱私與倫理）**
   當多個異質智能體共享圖結構並協作時，資料隱私、決策透明度與責任歸屬問題將變得更加複雜。未來需要發展圖結構上的隱私保護機制、可解釋性方法與價值對齊技術。

5. **Ontology Engineering for System Intelligence（系統智能的本體工程）**
   作者在第六節進一步指出，Graph Engineering 雖然提供了結構化框架，但仍需更高層次的 **Ontology Engineering（本體工程）** 來解決：
   - **Goal Formation and Value Alignment（目標形成與價值對齊）**：如何讓多智能體系統形成一致且符合人類價值的共享目標。
   - **Shared Semantics and World Grounding（共享語義與世界接地）**：如何讓不同智能體對任務、工具與狀態有一致的理解，並與真實世界建立穩定對應。
   - **Measuring System Intelligence（衡量系統智能）**：如何設計能夠客觀評估系統級智能的指標與基準。

6. **跨領域應用深化**
   論文在 **Section 9** 列舉了多個應用領域，包括 **Software Engineering and IT Operations（軟體工程與 IT 維運）**、**Scientific Discovery and Laboratory Automation（科學發現與實驗室自動化）**、**Healthcare and Clinical Decision Support（醫療與臨床決策支援）**、**Enterprise Workflows and Digital Organizations（企業流程與數位組織）** 等。未來研究可針對這些領域設計專屬的圖結構與評估基準，驗證 Graph Engineering 在真實場景中的價值。

總結來說，Graph Engineering 為 LLM Agent 的發展提供了一個從個體智能邁向系統智能的架構願景，但其真正成熟仍需在圖原生演算法、自我演化機制、作業系統支援、倫理對齊與系統級評估等多個方向上持續突破。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：隨著大型語言模型（LLM）從單純的語言生成器演進為能執行複雜長期任務的自主智能體，許多現實任務已經超出單一智能體能獨立完成的範圍。這些任務通常需要異質專業知識、相互依賴的子任務、平行執行、獨立驗證以及持續狀態管理，因此產生了「個體智能」的架構性瓶頸。本論文提出「圖工程（Graph Engineering）」作為新興典範，旨在透過顯式、動態且可演化的圖結構，把多個智能元件組織成追求共同目標的連貫整體，以實現系統智能（System Intelligence）。

**Q2：為什麼提示工程、上下文工程、駕馭工程與迴路工程不足以解決這個問題？**
A：提示工程與上下文工程主要聚焦於如何激發單一模型能力與管理資訊存取，駕馭工程則負責整合外部工具、記憶與技能，而迴路工程支援單一智能體的迭代反思與自我改進。這些典範雖然能顯著提升個體智能，但它們優化的仍是單一智能體內部的互動與行為，缺乏在系統層級上協調多個異質智能體的顯式結構。當任務需要分散式專業與平行驗證時，僅靠增強單一智能體的能力或上下文無法彌補架構上的不匹配，因此必須把智能分佈到多個專業智能體並在系統層級進行組織。

**Q3：系統智能為什麼重要，圖工程在其中扮演什麼角色？**
A：系統智能指的是智能體系統將多個智能元件組織、協調成連貫且具適應性的整體，以追求共享目標的能力，這是處理高複雜度任務的關鍵。單一智能體無法同時具備所有領域知識，也難以在長期執行中維持穩定的狀態與容錯機制，因此需要系統層級的設計思維。圖工程正是實現系統智能的核心方法，它透過任務圖、智能體圖與系統狀態圖等顯式結構，統一了目標分解、協調編排與執行狀態管理，使多智能體系統能夠規模化地演化與運作。

**Q4：圖工程的核心方法是什麼？**
A：圖工程的核心在於建構並維護三種相互關聯的圖結構：任務圖、智能體圖與系統狀態圖。任務圖描述「要做什麼」，將高層目標分解為可執行的子任務並最佳化工作流程；智能體圖描述「由誰執行」，對智能體能力建模、組織團隊並管理多智能體通訊；系統狀態圖則描述「系統如何運作」，記錄執行狀態、定位錯誤並支援故障恢復。這些圖結構是顯式、動態且可演化的，能夠隨任務進展持續更新，從而提供統一的系統層級抽象。

**Q5：圖工程相較於先前典範的關鍵創新是什麼？**
A：圖工程的關鍵創新在於把優化焦點從「單次互動」或「單一智能體行為」轉移到「系統層級的結構化組織」。不同於提示工程只改變輸入、駕馭工程只擴充工具，圖工程把任務、智能體與狀態都視為可操作的圖節點與邊，從而自然地表達複雜任務中的依賴關係、平行路徑與動態演化。這種顯式結構不僅便於編排與驗證，也為系統的持續演化、故障定位與規模化擴展奠定了基礎。

**Q6：為什麼選擇「圖」作為組織多智能體系統的核心抽象，而不是樹狀或列表式結構？**
A：圖結構能夠自然地表達子任務之間的相互依賴、平行執行路徑以及智能體之間的多對多協作關係，而樹狀結構難以處理跨分支的依賴，列表則無法呈現複雜的拓撲關係。此外，圖能夠動態地新增、刪除或重連節點與邊，非常適合描述長期執行中不斷演化的任務與狀態。透過圖的統一抽象，開發者可以在同一個框架下進行目標分解、能力建模、通訊編排與狀態追蹤，降低系統設計的複雜度。

**Q7：論文中討論了哪些評測面向與基準？**
A：論文將評測分為三個層級：模型智能（Model Intelligence）、個體智能（Individual Intelligence）與系統智能（System Intelligence），並分別回顧了對應的基準測試。在模型智能層級，評測關注基礎模型的語言理解、推理與知識能力；在個體智能層級，則評估單一智能體使用工具、記憶與迴路執行任務的表現；在系統智能層級，則需要衡量多智能體協作、任務分解、協調效率與整體目標達成度。作者指出，目前系統智能的標準化基準仍相對不足，特別是缺乏針對圖工程設計的圖原生評測指標。

**Q8：論文的主要發現或結論是什麼？**
A：論文系統性地論證了從個體智能邁向系統智能的必要性，並提出圖工程作為統一典範來組織任務、智能體與系統狀態。透過跨領域的文獻回顧，作者發現顯式的圖結構能夠顯著改善複雜任務的分解、異質智能體的協調以及執行過程中的故障定位與恢復。然而，由於圖工程仍屬新興領域，許多現有研究仍處於概念或個別應用階段，尚缺乏大規模、系統性的實證比較來驗證不同圖設計選擇的優劣。

**Q9：論文是否進行了消融實驗或量化比較？**
A：作為一篇綜述與觀點性論文，本文並未提出原創的實驗結果或消融研究，而是整合現有文獻並指出研究缺口。作者建議未來研究應設計控制實驗，分別檢驗任務圖、智能體圖與系統狀態圖對整體效能的個別貢獻，例如比較有無顯式狀態圖時的故障恢復率。這類消融實驗將有助於釐清圖工程各組件的設計取捨，並為工程實踐提供更明確的指導原則。

**Q10：圖工程在哪些實際應用場景最具潛力？**
A：圖工程在軟體工程與 IT 維運特別具有潛力，因為這些領域的任務高度模組化、相互依賴，且需要版本控制、測試驗證與錯誤追蹤。科學發現與實驗室自動化也是重要場景，因為長期實驗涉及多步驟規劃、儀器協調與結果驗證。此外，醫療臨床決策支援、企業工作流程與個人自動化助理等應用，也能受益於多專科智能體的協調與持續狀態管理。

**Q11：在產品化與工程生態方面，論文提出了哪些考量？**
A：論文回顧了支援模型智能、個體智能與系統智能的開源函式庫與工具生態，並指出目前仍缺乏真正「圖原生」的智能體作業系統與自我演化圖系統。產品化時必須考慮圖結構的建構與維護成本、動態更新帶來的穩定性風險，以及多智能體之間的隱私與倫理問題。為了讓圖工程真正落地，未來需要標準化的圖表示格式、可觀測性工具，以及能夠自動調整圖結構的執行期平台。

**Q12：圖工程可能對整個 LLM 智能體研究領域帶來什麼影響？**
A：圖工程有望將研究焦點從「如何讓單一智能體更強大」轉向「如何讓多個智能體有效協同」，從而催生系統層級的設計方法論與評測標準。它強調顯式結構的重要性，可能推動圖原生能力基板、智能體作業系統以及自動化協調框架的發展。長遠來看，這種典範轉移將使 LLM 智能體更能處理真實世界中複雜、長期且需要多方協作的任務。

**Q13：作者承認圖工程有哪些限制？**
A：作者指出，建構與維護顯式圖結構會帶來額外的計算與工程成本，並且在高度動態的環境中，圖的頻繁更新可能導致系統不穩定。此外，當任務結構本身極度模糊或難以形式化時，圖工程可能難以產生穩定可靠的任務圖。圖結構本身也無法自動保證目標形成、價值對齊與共享語義，這些仍是需要額外研究的根本挑戰。

**Q14：在什麼情況下圖工程可能失敗或表現不佳？**
A：當任務無法被合理分解為相對穩定的子任務，或者子任務之間的依賴關係過於模糊且快速變化時，任務圖的建構會變得困難甚至誤導執行。如果智能體能力建模不準確，智能體圖可能將任務分配給不適合的智能體，導致協調失敗。同樣地，若系統狀態圖記錄不完整或更新延遲，故障定位與恢復機制將難以發揮作用，進而影響整體系統的可靠性。

**Q15：論文提出了哪些未來研究方向？**
A：未來研究方向包括發展圖原生的能力基板、設計能自我演化的圖系統，以及建構圖原生的智能體作業系統。作者也強調需要解決隱私與倫理問題，並在最後提出「本體工程（Ontology Engineering）」作為下一代系統智能的方向，以處理目標形成、價值對齊、共享語義與世界接地等更深層議題。此外，建立系統智能的標準化衡量方法，以及針對圖工程設計的基準測試，也是推動該領域成熟的重要課題。

## 實務應用指南

## 適用場景

1. **企業級跨部門流程自動化（如新品上市流程）**  
   將市場調查、法規審查、供應鏈規劃、行銷素材製作等相互依賴的子任務建模為 Task Graph，再由具備不同專長的 Agent（法規 Agent、採購 Agent、文案 Agent）依圖結構協作，並以 System State Graph 追蹤每個里程碑的狀態。

2. **軟體工程全生命週期輔助（需求 → 設計 → 開發 → 測試 → 部署）**  
   把軟體開發流程拆解為可動態調整的工作流，讓架構師 Agent、程式碼生成 Agent、測試 Agent、維運 Agent 在 Agent Graph 中溝通，並透過 Runtime State Management 記錄每次建置、測試與部署狀態，支援故障定位與回復。

3. **科學發現與實驗室自動化（假設 → 實驗設計 → 執行 → 分析 → 迭代）**  
   在化學、材料或生物實驗中，以 Graph Engineering 組織文獻知識、實驗假設與儀器操作步驟，讓文獻回顧 Agent、實驗設計 Agent、儀器控制 Agent、數據分析 Agent 平行執行並相互驗證，最終形成可演化的實驗知識圖。

4. **醫療臨床決策支援（多病種、多專科協作診療計畫）**  
   針對複雜病例，建立病人狀態、檢驗項目、診斷假設與治療方案的圖結構，由不同專科 Agent（影像判讀、病理、藥劑、護理）協調產出診療建議，並保留可稽核的決策軌跡。

## 實作步驟建議

1. **定義目標與範圍**  
   釐清要解決的長期任務（Long-horizon Task）與成功指標，確認單一 Agent 無法勝任的原因（異質專業、平行執行、獨立驗證等）。

2. **領域建模：建立三種圖結構**  
   - **Task Graph**：目標分解（Goal Decomposition）與工作流程最佳化（Workflow Optimization）。  
   - **Agent Graph**：智能體能力建模（Agent Capability Modeling）、團隊組織與溝通拓撲。  
   - **System State Graph**：執行狀態、資料流與決策軌跡的顯式表示。

3. **智能體能力建模與分工**  
   為每個 Agent 撰寫明確的能力描述、輸入輸出規格與責任邊界，避免能力重疊或真空。

4. **設計溝通與協調協議**  
   定義 Multi-agent Communication 模式（如請求-回應、發布-訂閱、黑板模式）、訊息格式與衝突解決機制。

5. **實作 Runtime State Management**  
   建立 State Recording、Fault Localization 與 Failure Recovery 機制，確保系統在長期執行中保持一致性與可恢復性。

6. **整合外部工具與記憶（Harness Engineering）**  
   透過 Tool Integration、Memory Management 與 Skill Composition，讓 Agent 能呼叫企業 API、資料庫與領域工具。

7. **建立反思與演化迴路（Loop Engineering）**  
   設計 Reflection 與 Self-improvement 機制，使 Task Graph、Agent Graph 與 State Graph 能依執行回饋動態演化。

8. **評估、部署與迭代**  
   參考論文第 7 章 Benchmarks 與 Evaluation 原則，從 Model Intelligence、Individual Intelligence 到 System Intelligence 分層評測，再持續優化圖結構與協調策略。

## 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **圖結構複雜度爆炸** | 任務與 Agent 數量增加時，圖變得難以維護 | 採用分層圖（Hierarchical Graph）與模組化設計，定期進行 Workflow Optimization |
| **協調開銷過高** | 多 Agent 溝通造成延遲與成本上升 | 設計精簡的通訊協議，允許適度平行執行，並對非關鍵路徑進行批次處理 |
| **錯誤傳播與幻覺放大** | 單一 Agent 的幻覺可能沿圖結構擴散 | 引入 Independent Verification 與交叉檢查機制，保留完整決策軌跡 |
| **狀態不一致** | 長期執行中 State Graph 與實際環境脫節 | 強化 State Recording、環境回饋（Environment Feedback）與週期性一致性檢查 |
| **隱私與倫理** | 多 Agent 系統可能處理敏感資料或產生不當決策 | 落實存取控制、資料去識別化、價值對齊（Value Alignment）與人類監督機制 |
| **評估困難** | System Intelligence 難以用單一指標衡量 | 採用多維度評估（正確性、效率、穩健性、可解釋性、演化能力） |

## 與其他技術的整合建議

- **企業系統（ERP / CRM / BPM）**：將 Graph Engineering 層視為 BPM 引擎的「智慧編排層」，透過 API 與現有工作流引擎互補，而非完全取代。
- **檢索增強生成（RAG）與知識圖譜（KG）**：利用 RAG 提供動態上下文，KG 提供穩定的領域語義，再將兩者整合進 Task Graph 與 State Graph。
- **MCP / Function Calling 工具生態**：採用標準化工具描述協定（如 MCP），降低 Agent 與外部工具整合的成本。
- **LLMOps / MLOps 平台**：將 Graph Engineering 系統的執行軌跡、狀態轉換與 Agent 決策記錄匯入可觀測性平台，支援持續優化。
- **身分識別與存取控制（IAM）**：在 Agent Graph 中嵌入權限模型，確保不同 Agent 只能存取授權資料與工具。
