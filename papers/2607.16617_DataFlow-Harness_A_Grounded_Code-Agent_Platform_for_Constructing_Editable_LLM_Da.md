## 摘要翻譯

大型語言模型（Large Language Model, LLM）日益被用於自動化資料處理工作流程（data-processing workflow），然而程式碼代理（code agent）通常產出腳本，而這些腳本不會自動具現為持久且可編輯的平台產物（platform artifact）。我們將這種落差稱為 NL2Pipeline gap。為了彌合此落差，我們提出 DataFlow-Harness，一個引導 LLM 代理透過型別化的增量修改（typed incremental mutation）（而非自由格式腳本（free-form script））來建構平台原生（platform-native）有向無環圖（Directed Acyclic Graph, DAG）的平台。該平台結合用於程序性引導（procedural guidance）的 DataFlow-Skills、可呈現即時運算子登錄檔（live operator registry）與當前管線狀態（current pipeline state）的模型上下文協定（Model Context Protocol, MCP）層，以及可將對話式編寫（conversational authoring）與視覺化 DAG 編輯器（visual DAG editor）同步的 DataFlow-WebUI。在一個包含 12 項任務的資料工程（data engineering）基準測試（benchmark）上，DataFlow-Harness 達到 93.3% 的觀察端對端通過率（observed end-to-end pass rate）。相較於 Vanilla Claude Code，它將測得的金錢成本（measured monetary cost）降低 72.5%、生成延遲（generation latency）降低 49.9%；其觀察通過率與 Context-Aware Claude Code 基線相差在 0.9 個百分點以內，而成本則低了 42.8%。逐任務分析顯示，當建構仰賴隱含程序性知識（implicit procedural knowledge）時，Skills 最為有用。這些結果顯示，即時平台錨定（live platform grounding）能夠產出持久且可編輯的工作流程產物（persistent editable workflow artifact），其觀察到的可靠性接近腳本生成基線（script-generation baseline），同時測得的建構成本與延遲也更低。

### 核心貢獻（3～5點）
- 提出 NL2Pipeline gap 概念，指出現有程式碼代理產出的一次性腳本難以自動成為持久、可編輯的平台產物。
- 設計 DataFlow-Harness 平台，透過型別化增量修改與即時平台錨定，引導 LLM 代理建構平台原生的 DAG。
- 整合 DataFlow-Skills、MCP 層與 DataFlow-WebUI，實現對話式編寫與視覺化 DAG 編輯器的同步。
- 在 12 項資料工程基準任務上達到 93.3% 的觀察端對端通過率，並相較 Claude Code 基線顯著降低金錢成本與生成延遲。
- 發現 DataFlow-Skills 在需要隱含程序性知識的建構步驟中最具效益。

### 適合對象
本論文適合資料工程師、機器學習平台開發者、研究 LLM 程式碼代理與視覺化工作流程介面的研究者，以及關注生產部署中可治理、可編輯資料管線自動建構的實務工作者閱讀。

## 深度分析

#### 方法論解析

DataFlow-Harness 的核心設計目標是縮小 **NL2Pipeline gap**（自然語言到資料管線的落差）：使用者以自然語言需求（natural-language requirement）描述資料處理意圖，但生產環境需要的是可視化、可編輯、可重複使用且符合平台治理機制（platform governance mechanism）的持久性工作流程產物（persistent editable workflow artifact）。為此，該平台並非讓程式碼代理（coding agent）直接輸出自由格式腳本（free-form script），而是將其限制在一個領域專屬的「馬具（harness）」內，透過**型別化的增量修改（typed incremental mutation）**逐步建構**平台原生的有向無環圖（platform-native DAG）**。

整體架構可拆解為四個緊密耦合的層次：

1. **Data Pipeline Backend（資料管線後端）**  
   負責維護真正的平台狀態，包括運算子（operator）、資料來源（data sources）、有向邊（directed edges）與環境設定（environment settings）。後端內建**驗證引擎（validation engine）**，對每次提出的修改進行 **DAG Check**（DAG 結構檢查）與 **Schema Check**（綱要相容性檢查），確保管線在語法與語意上都合法。

2. **MCP Tools Layer（MCP 工具層）**  
   透過 **Model Context Protocol（MCP，模型上下文協定）** 將後端的**即時運算子登錄檔（live operator registry）**與**當前管線狀態（current pipeline state）**暴露給代理。代理不再憑記憶推測有哪些運算子可用，而是每次都能查詢真實環境，從而避免**虛構依賴（hallucinate dependencies）**、使用**不可用運算子（unavailable operator）**或依賴**過時的平台假設（outdated platform assumption）**。

3. **DataFlow-Skills**  
   這是一組程序性藍圖（procedural blueprint），內含領域專屬的建構知識，例如運算子選擇模式、綱要相依關係與組裝程序。當建構任務依賴**隱含程序性知識（implicit procedural knowledge）**時，Skills 能顯著降低代理的試錯成本。

4. **DataFlow-WebUI**  
   提供**對話式編寫（conversational authoring）**介面與**視覺化 DAG 編輯器（visual DAG editor）**，兩者共享同一份持久管線表示。使用者的自然語言需求與代理的動作會同步反映在圖形化工作流程介面（graphical workflow interface）上，讓人可以即時檢視、編輯與確認。

運作流程可概括為：使用者透過 DataFlow-WebUI 輸入需求 → 代理結合 DataFlow-Skills 的程序性引導（procedural guidance）與 MCP 層的**即時平台錨定（live platform grounding）**→ 對後端提出型別化的增量修改 → 驗證引擎檢查 → 通過後寫回平台狀態 → WebUI 同步更新視覺化 DAG。這種「約束式代理」設計的關鍵在於：代理的每次動作都是對真實平台物件的結構化變更，而非產生一次性腳本（disposable script）。

#### 實驗數據解讀

論文在 12 項資料工程任務上進行評估，涵蓋資料轉換、問答、品質過濾與合成資料生成（synthetic data generation）等情境。主要結果如下：

- **端對端通過率（end-to-end pass rate）**：DataFlow-Harness 達到 **93.3%** 的觀察通過率（observed pass rate），與 **Context-Aware Claude Code** 基線相差僅 **0.9 個百分點**。這顯示透過平台錨定所產生的持久、可編輯工作流程產物，其可靠性已接近直接腳本生成基線（script-generation baseline）。
- **測得的金錢成本（measured monetary cost）**：相較於 **Vanilla Claude Code**，DataFlow-Harness 降低 **72.5%**；相較於 Context-Aware Claude Code，則降低 **42.8%**。成本下降主要來自於：
  - 代理不需要從頭生成完整腳本，只需產生小型的結構化修改；
  - Skills 提供程序性引導，減少無效試錯；
  - MCP 層提供即時運算子資訊，降低反覆查詢與推測所需的 token 消耗。
- **生成延遲（generation latency）**：相較 Vanilla Claude Code 降低 **49.9%**。增量修改與較短的上下文長度有助於縮短每次推理時間。

進一步的**逐任務分析（per-task analysis）**指出，DataFlow-Skills 的貢獻並非均勻分布，而是在「建構過程依賴隱含程序性知識」的任務中最為顯著。這暗示 Skills 的價值在於補足 LLM 無法從平台狀態或運算子文件中直接推論出的組裝經驗。對於較為直觀、運算子組合明確的任務，MCP 層的即時資訊可能已足夠。

此外，論文還包含 **Textbook-to-VQA Workflow Evaluation**（Textbook-to-VQA 工作流程評估）與 **Downstream Training Utility Evaluation（下游訓練效用評估）**兩個控制案例，說明由 DataFlow-Harness 建構的管線不僅能通過結構驗證，還能產生對下游模型訓練（model training）有實際助益的資料。這是評估「平台原生管線」價值的重要一環：若僅驗證結構正確而忽略下游效用，仍難以說服生產團隊採用。

值得注意的解讀是：DataFlow-Harness 並未在通過率上全面超越最強的 Context-Aware Claude Code 基線，而是在「可靠性接近」的前提下，顯著降低建構成本（construction cost）與延遲（latency），並產出可持續維護的平台原生產物。這符合其設計哲學——目標不是取代通用程式碼代理，而是將其輸出錨定到可治理的平台物件。

#### 與現有研究的比較

**相較於通用程式碼代理（agents for code generation）**  
傳統程式碼合成從 Codex、StarCoder 發展到 Reflexion、Self-Debug、SWE-agent、Claude Code 等自主代理，重點在於提升程式碼正確性與迭代除錯能力。DataFlow-Harness 的差異在於**不改良代理本身**，而是將通用代理限制在領域專屬的建構框架內，強迫其輸出符合平台語意的結構化產物。這類似於從「自由書寫」轉向「表單導向編輯」，犧牲部分靈活性以換取可維護性與可稽核性。

**相較於資料工程與 LLM 管線系統**  
Data-Juicer、DCLM 等系統強調大規模資料治理與可擴展運算子；DataFlow、DSPy 則將 LLM 操作視為可組合元件。DataFlow-Harness 建立在 DataFlow 之上，但聚焦於「代理輔助的管線建構」而非「管線執行」。換言之，它解決的是**如何讓代理正確地畫出管線圖**，而非**如何讓管線跑得更快**。

**相較於 LLM 工作流程合成研究**  
AutoFlow 與 Balis et al. 等研究已證明結構化工作流程生成與可重複使用 Skills 的價值。DataFlow-Harness 的互補貢獻在於**互動式、有狀態的平台內編寫**：代理透過 MCP 持續讀取當前管線狀態，套用經過驗證的增量修改，並與視覺化編輯器共享同一份表示。這種「即時平台錨定」是過往自由生成式系統所缺乏的。

**主要限制**  
1. **基準測試（benchmark）規模有限**：12 項任務雖能展示趨勢，但難以涵蓋工業場景中複雜的邊界條件與大規模管線。  
2. **平台依賴性**：方法緊密綁定 DataFlow 平台與其運算子登錄檔，遷移到其他資料工程平台需要重新設計 Skills 與驗證規則。  
3. **代理自主性仍受限**：雖然驗證引擎能攔截結構錯誤，但對於語意層面的錯誤（例如選錯欄位進行過濾）仍可能需要人工介入。  
4. **對比基線的公平性**：Context-Aware Claude Code 已獲得相關平台文件，DataFlow-Harness 則擁有結構化 MCP 工具與 Skills，兩者的資訊不對等，未來需要更細緻的對照實驗來分離各元件的貢獻。

#### 可重現性評估

根據目前提供的論文內容，**並未明確提及原始碼、資料集或模型權重的開放釋出**。這對可重現性（reproducibility）構成一定挑戰：

- **平台與程式碼**：DataFlow-Harness 包含 DataFlow-WebUI、MCP Tools Layer、Data Pipeline Backend 與 DataFlow-Skills 等多個元件，若無開源實作，其他研究者難以複製完整系統行為。
- **12-task benchmark**：基準測試的任務描述、評分標準與測試資料未在摘要與目錄中揭露，影響結果的比較與驗證。
- **模型與 API**：實驗使用 Claude Code 系列作為基線與底層模型，但具體模型版本、溫度參數、重試次數與 token 計價方式會影響成本與延遲數據。
- **環境相依性**：MCP 層需要連接真實的 DataFlow 後端，這意味著重現實驗需要部署相同的平台環境，門檻高於純腳本生成實驗。

建議作者未來補充：原始碼倉庫連結、Docker 化部署方式、基準任務的詳細規格、每筆實驗的原始對話紀錄與成本明細，以及 Skills 的完整目錄。這將大幅提升研究的可重現性與社群採用意願。

#### 未來研究方向

1. **擴大基準測試規模與多樣性**  
   將 12 項任務擴展至跨領域、跨規模的資料工程情境，並納入需要長期規劃與多步驟推理的複雜管線，以驗證方法在真實生產環境中的穩健性。

2. **跨平台通用 Harness 框架**  
   目前 DataFlow-Harness 高度綁定 DataFlow 平台。未來可研究如何將 MCP 層、Skills 與驗證引擎抽象為通用中間層，使其能適配 Apache Airflow、Prefect、Kubeflow 等不同資料管線平台。

3. **自動化 Skills 發現與演化**  
   現有 Skills 由人類專家編寫。可結合程式分析與使用紀錄，自動從成功案例中萃取出新的程序性藍圖，並透過版本控制管理 Skills 的演進。

4. **強化語意層驗證**  
   除了 DAG 結構與綱要相容性，未來可引入資料品質預檢、下游任務效用預測與因果相依分析，讓驗證引擎能捕捉更多語意層錯誤。

5. **人機協同的對話式編輯**  
   DataFlow-WebUI 已具備對話與視覺化編輯的同步基礎。下一步可探索主動式建議、衝突視覺化、版本比較與協同註解，提升人在迴路（human-in-the-loop）的效率。

6. **結合專屬微調模型**  
   目前仍使用通用 LLM 作為底層代理。針對型別化增量修改任務微調小型模型，有機會進一步降低金錢成本與生成延遲，同時減少對商用 API 的依賴。

7. **與 CI/CD 及治理機制整合**  
   將 DataFlow-Harness 產生的管線產物納入版本控制、自動測試與稽核流程，實現從自然語言需求到生產部署（production deployment）的完整生命週期管理。

## 論文問答

**Q1：什麼是 NL2Pipeline gap，為什麼它在資料工程領域值得被特別關注？**
A：NL2Pipeline gap 指的是使用者以自然語言描述資料處理意圖，但現有程式碼代理通常只產出一次性腳本，無法自動轉化為持久且可編輯的平台原生資料管線產物之間的落差。在生產環境中，工作流程產物必須能夠被視覺化、稽核、重複使用，並與平台治理機制整合，而自由格式腳本難以滿足這些生命週期需求。因此，這個落差不僅是技術準確率的問題，更關乎資料管線在真實平台中能否長期維護與治理。

**Q2：現有的程式碼生成代理為何難以直接滿足生產級資料管線的建構需求？**
A：現有代理多以生成可執行腳本為目標，這些腳本往往只是原始碼形式，並未具體化為平台原生的有向無環圖（DAG）物件。它們容易產生幻覺依賴，例如引用不可用運算子、仰賴過時的平台假設，或採用難以推斷的框架特定行為。此外，一次性腳本難以透過圖形化工作流程介面進行稽核與協作，導致高準確率並不等同於可部署性。

**Q3：為何僅追求高任務準確率，仍不足以將 LLM 建構的資料工作流程投入生產部署？**
A：工業環境重視的是產出物在整個生命週期中的可見性、可編輯性、可重複使用性，以及與平台治理機制的相容性。即使代理能產生語法正確且可執行的程式碼，若該程式碼無法成為持久的工作流程產物，就難以進行版本控制、視覺化檢視或後續修改。因此，關閉 NL2Pipeline gap 需要讓建構過程錨定在平台語義上，並產出能被平台原生管理的資料管線物件。

**Q4：DataFlow-Harness 的核心方法是什麼，它與傳統腳本生成代理有何不同？**
A：DataFlow-Harness 並不直接生成自由格式腳本，而是引導 LLM 代理透過型別化的增量修改，逐步建構平台原生的 DAG。平台透過 DataFlow-Skills 提供程序性引導、透過 MCP 層暴露即時運算子登錄檔與當前管線狀態，並透過 DataFlow-WebUI 同步對話式編寫與視覺化 DAG 編輯器。這種方式讓每一次修改都發生在真實平台狀態之上，並經過結構與綱要相容性驗證，從而確保產出物是可編輯且持久的工作流程產物。

**Q5：DataFlow-Harness 的關鍵設計選擇與創新點有哪些？**
A：其關鍵設計在於將領域知識、平台狀態與使用者介面解耦為三個模組：DataFlow-Skills 負責編碼運算子選擇模式、綱要相依性與組裝程序；MCP 工具層提供即時平台錨定；DataFlow-WebUI 則同步對話與視覺編輯。相較於改進通用代理本身，DataFlow-Harness 選擇將通用代理約束在領域特定的建構框架中，並以增量修改取代一次性程式碼生成。這種設計讓代理能夠在受控狀態空間內操作，降低幻覺與無效狀態的風險。

**Q6：DataFlow-Skills 在系統中扮演什麼角色，它與一般提示工程有何差異？**
