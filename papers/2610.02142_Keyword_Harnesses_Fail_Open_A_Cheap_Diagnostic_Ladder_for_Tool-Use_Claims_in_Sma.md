## 摘要翻譯

關鍵字匹配基準測試（keyword-matching benchmarks）可能會將小型語言模型（small language models）從未執行的工具使用記為其功。我們記錄了同架構配對模型（matched-architecture pair）的西班牙語安全領域語言模型（Spanish security language models）中出現的這類偽陽性（false positive），並提出一組嚴格且低成本的診斷階梯（diagnostic ladder）。一個 661.6M 參數模型（約 65% 程式碼／技術文本；未經專屬監督式微調（SFT））與一個 1,109M 模型（以重網頁資料為主的多階段課程（multi-phase curriculum）；60 億詞元的工具使用監督式微調（tool-SFT））共享解碼器（decoder）、分詞器（tokenizer）與特殊詞元（special tokens），在寬鬆工具使用指標（lenient tool-use metrics）上得分幾乎相同（B4：0.660 對 0.650）。

針對訓練範例（training examples）的逐字重現檢查（verbatim-reproduction checks）將兩者完全區分開來：600M 模型在 6/6 個範例中生成帶有泛化引數（generalized arguments）的有效工具呼叫（valid tool calls）；1B 模型在所有檢查點（checkpoints）上均為 0/6。首詞元探針（first-token probe）將 1B 的失效定位於缺失先驗（missing prior）：在工具呼叫詞元（tool-call token）<\|tool_call\|> 上的先驗機率（prior probability）僅 10^{-4}–10^{-5}，此先驗被其重網頁資料的訓練階段（web-heavy training phase）抹除。一個目標式監督式微調配方（targeted SFT recipe；多樣化語料庫（diverse corpus）、高 5 倍的學習率（learning rate）、2,202 步數（steps）、約 3.3 GPU 小時（GPU-hours））以比失效階段少三個數量級（three orders of magnitude）的詞元數修復了 1B。在全部 269 筆語料列上，修復後 1B 的有效生成率（valid emission）從 0.100 提升至 0.959（600M：0.926）。在 238 個未見過提示（unseen prompts）上，修復後的 1B 通過率（pass rate）為 0.536，相較於 600M 的 0.428（配對 p 值（paired p-value）= 0.004）。嵌入漂移檢查（embedding-drift checks）顯示，修復並未移動觸發詞元（trigger token）的綁定嵌入（tied embedding）：bf16 表格（bf16 table）中 97.7% 位元完全相同（bit-identical），意味著改變存在於周邊網路（surrounding network）中。

兩個模型都會過度觸發（over-trigger），鮮少在不呼叫的情況下回答否定提示（negative prompts；600M 為 0.09，修復後的 1B 為 0.17）。因子分析（factorial analyses）確認所有修復配置都能建立格式，但由於隨機種子敏感性（seed sensitivity），多樣化語料庫帶來的抑制效益仍屬假設。這套低成本診斷階梯僅需數分鐘 CPU 時間（CPU time），應作為小型語言模型工具使用宣稱的把關（gate）機制。

### 核心貢獻（3～5點）
- 揭示關鍵字匹配基準測試可能誇大小型語言模型的工具使用能力，並以同架構的西班牙語安全領域 600M／1B 模型為具體案例。
- 提出一套低成本的診斷階梯，結合逐字重現檢查、首詞元探針與嵌入漂移檢查，可在數分鐘 CPU 時間內區分真實工具能力與評測誤判。
- 定位 1B 模型失效的根因：重網頁資料的訓練階段抹除了工具呼叫詞元的先驗機率，並以極少詞元（少三個數量級）的目標式監督式微調配方成功修復。
- 顯示修復主要改變周邊網路而非觸發詞元的綁定嵌入，同時指出過度觸發與隨機種子敏感性等尚待驗證的限制。

### 適合對象
從事小型語言模型、工具使用能力評測與安全領域模型開發的研究者與工程師；設計自動化基準測試框架或關注模型能力宣稱驗證的方法學者；以及需要在有限運算資源下進行低成本、嚴謹診斷的實務人員。

## 深度分析

#### 方法論解析

本研究的核心方法論是一套「低成本診斷階梯（Cheap Diagnostic Ladder）」，用於在小型語言模型（Small Language Models）上驗證工具使用宣稱（Tool-Use Claims）。該階梯由四個由寬到嚴、成本遞增但皆為「分鐘級 CPU 時間」的檢查組成，依序為：逐字重現檢查（Verbatim-Reproduction Check）、首詞元探針（First-Token Probe）、未見提示泛化測試（Novel-Prompt Generalization Battery），以及嵌入漂移檢查（Embedding-Drift Check）。

**1. 逐字重現檢查（Verbatim-Reproduction Check）**  
作者從模型自身的工具使用監督式微調（Tool-SFT）訓練語料中，取出真實的系統前導（system preamble）與訓練範例（Training Examples），包含可用的 MCP 工具宣告與預期輸出格式。將提示的前半段輸入模型，以貪婪解碼（greedy decoding）進行前向傳播，並要求模型輸出格式正確的工具呼叫 JSON（Valid Tool Calls），且其引數必須是訓練答案的「泛化變體（generalized variant）」而非位元級抄襲。此檢查的關鍵在於區分「記憶（memorization）」與「結構化生成能力」：若模型只會背誦（recite）訓練範例，則無法證明其具備原生工具呼叫（Native Tool Calling）能力；只有能生成語法正確且語意合理的非相同引數，才算通過。

**2. 首詞元探針（First-Token Probe）**  
當逐字重現失敗時，作者進一步檢視模型在應該開始工具呼叫的位置，對 `<|tool_call|>` 這個觸發詞元（Trigger Token）的先驗機率（Prior Probability）。這是一個局部化的診斷：若模型對該特殊詞元（Special Token）的機率極低（例如 10^{-4}–10^{-5}），則代表問題並非解碼競賽中的「險敗」，而是根本缺乏對該結構的先驗（Missing Prior）。此方法能將失效點從「整體格式錯誤」縮小到「第一個 token 就不會被選中」。

**3. 未見提示泛化測試（Novel-Prompt Generalization Battery）**  
修復後，作者使用 238 個針對未見實體（unseen entities）設計的提示，例如未出現在訓練中的 CVE 識別碼、IP 位址、搜尋查詢等，測試模型是否能在正確情境下選擇五個宣告工具中的適當一個，並正確抑制（suppression）不該呼叫工具的對話式問題。此步驟確認修復不是對訓練語料庫（Corpus）的過擬合，而是具備某種程度的泛化（Generalize）。

**4. 嵌入漂移檢查（Embedding-Drift Check）**  
最後，作者比較修復前後的詞嵌入表（Embedding Table），特別是觸發詞元 `<|tool_call|>` 的綁定嵌入（Tied Embedding）。結果顯示 97.7% 的 bf16 表格位元完全相同（bit-identical），意味著修復並未改變該特殊詞元的嵌入向量，而是發生在周邊網路（Surrounding Network）中。這提供了機制性說明（Mechanistic Statement），將能力修復定位到模型的後續層而非輸入嵌入層。

**5. 目標式監督式微調配方（Targeted SFT Recipe）**  
基於上述診斷，作者針對 VectraYX-1B 設計了一個修復配方：使用多樣化語料庫（Diverse Corpus，包含對話式 OASST ES/EN、工具語料與領域推理軌跡）、解除嵌入凍結、並使用 5× 較高的學習率（Learning Rate），在 2,202 步、約 3.3 GPU 小時內完成。此配方使用的 token 數量比原本失敗的專屬工具使用監督式微調（Tool-SFT）階段少約三個數量級（Three Orders of Magnitude），卻成功恢復了工具呼叫能力。

#### 實驗數據解讀

**同架構配對模型（Matched-Architecture Pair）的偽陽性（False Positive）**  
VectraYX-600M（661.6M 參數）與 VectraYX-1B（1,109M 參數）共享解碼器（Decoder）、分詞器（Tokenizer）、特殊詞元配置（Special-Token Layout）與保留特殊詞元 ID（Reserved Special-Token IDs）。在寬鬆工具使用指標（Lenient Tool-Use Metrics）B4（BLEU-4）上，兩者分數幾乎相同：0.660 vs. 0.650。然而逐字重現檢查卻完全區分兩者：600M 在 6/6 範例中生成格式正確且泛化的工具呼叫；1B 在所有測試檢查點（Checkpoint）上皆為 0/4–6。這清楚展示了關鍵字匹配基準測試（Keyword-Matching Benchmarks）如何將「在散文中提到工具」誤判為「實際執行工具呼叫」，也就是「關鍵字評測框架誤判開啟（Keyword Harnesses Fail Open）」。

**首詞元探針的失效定位**  
1B 模型在應輸出 `<|tool_call|>` 的位置，其先驗機率僅 10^{-4}–10^{-5}，相較於 600M 會貪婪地生成該詞元，顯示 1B 並非「差一點選到」，而是幾乎沒有賦予該結構任何機率質量。進一步檢視 38 個封存檢查點（Archived Checkpoints）發現，1B 在較早階段曾經擁有某種記憶化先驗（Memorized Prior），但在重網頁資料的訓練階段（Web-Heavy Training Phase）被抹除。這說明多階段課程（Multi-Phase Curriculum）的資料組成（bootstrap composition）會決定某項能力是「預設出現」還是「必須額外工程化」。

**修復效果**  
在目標式監督式微調（SFT）後，1B 在所有 269 筆語料列上的格式正確生成（Well-Formed Emission）從 0.100 提升至 0.959，已接近 600M 的 0.926。在 238 個未見提示（Unseen Prompts）上，修復後的 1B 通過率（Pass Rate）為 0.536，顯著高於 600M 的 0.428（配對 p 值 Paired p-Value = 0.004）。這顯示修復不僅恢復了訓練語料上的表現，也具備一定的域外泛化能力。然而作者也坦承，在模型自身語料上，修復後的 1B 大多呈現背誦（recite）行為，因此未見提示測試才是更可信的泛化證據。

**嵌入漂移與機制定位**  
修復後 97.7% 的 bf16 嵌入表位元完全相同，觸發詞元的綁定嵌入（Tied Embedding）幾乎未移動。這意味著修復並非透過重新學習 `<|tool_call|>` 的語意表徵來達成，而是改變了周邊網路（Surrounding Network）在該詞元出現前後的轉換行為。這是一個重要的機制性發現，暗示小型模型中結構化輸出的能力可以透過非嵌入層的調整來恢復。

**過度觸發（Over-Trigger）與因子分析（Factorial Analyses）**  
兩個模型在否定提示（Negative Prompts）或提及 CVE、Shell 指令但不該呼叫工具的情境下，都傾向過度觸發：600M 僅有 0.09 的比例正確抑制呼叫，修復後的 1B 為 0.17。這顯示工具呼叫的「開關」仍不夠精細。五輪因子分析發現所有修復配置都能成功安裝呼叫格式；但「多樣化語料庫在低學習率下帶來更好抑制效果」這一發現，因隨機種子敏感性（Seed Sensitivity）未能在部分第二種子中重現，因此僅被視為假說（hypothesis）。

#### 與現有研究的比較

**對基準測試方法論的貢獻**  
過去許多工具使用基準測試依賴關鍵字匹配（Keyword-Matching）或 BLEU 等寬鬆指標來評判模型是否完成工具呼叫。本研究以具體案例證明，這類「框架（Harness）」會因為模型在輸出中提及工具名稱或相關術語而給分，即使模型從未生成可被 MCP 伺服器（MCP Server）執行的結構化 JSON 載荷（JSON Payload）。這與近期對大型語言模型工具使用評測的批評一致，但本研究特別聚焦於小型語言模型與氣隙隔離部署（Air-Gapped Deployment）場景，並提出一套可執行的把關（Gate）流程。

**延續並精煉「Bootstrap Composition」觀點**  
作者在先前的 VectraYX-Nano 研究中提出「bootstrap register 主導下游行為」的論點。本研究將此觀點從對話語域（conversational register）延伸至結構化輸出（structured output），並進一步精煉為：資料組成（composition）不會讓某項能力變得不可能，而是決定該能力是「免費出現」還是「必須被工程化」。600M 因預訓練課程中約 65% 為程式碼與技術文本，僅靠約 0.1% 的指令混合比例就自然湧現工具呼叫行為；1B 雖然經歷了約 6B token 的專屬 Tool-SFT，卻因重網頁階段而喪失該先驗。這挑戰了「更多專屬 SFT 資料必然帶來更好工具使用能力」的直覺。

**與工具學習研究的對話**  
相較於許多研究聚焦於大型模型（如 GPT 系列）透過大量工具使用資料進行微調，本研究顯示小型模型對訓練課程的順序與組成極為敏感，且「專用階段」可能適得其反。修復配方使用更少 token、更高學習率與多樣化混合資料，反而成功，這與傳統認為需要長時間、低學習率、專一語料進行 SFT 的做法形成對比。

**限制（Limitations）**  
本研究的主要限制在於其並非嚴格消融實驗（ablation）。600M 的訓練運行在 64% 計畫進度時被永久凍結，訓練虛擬機與雲端帳號已不存在；部分 1B 檢查點與原始修復檢查點也已遺失。現有結果來自對倖存父檢查點的端到端重現，且多為單一隨機種子（single seed）。因此，雖然證據鏈強烈支持「重網頁階段抹除先驗」的解釋，但無法排除其他混淆變因。此外，過度觸發（Over-Trigger）問題顯示修復後的模型在判斷「何時不該呼叫」方面仍有明顯缺陷；因子分析中的種子敏感性也讓「多樣化語料抑制過度觸發」的結論只能保留為假說。

#### 可重現性評估

從開放科學的角度，本研究的可重現性（Reproducibility）處於中等偏低水準。作者明確指出這是一篇預印本（preprint），且研究是在獨立於其 Globant 職務的個人角色下完成。最大的障礙是基礎設施已經遺失：VectraYX-600M 的訓練運行被永久凍結在 64%，訓練虛擬機與雲端帳號不再存在；1B 的原始修復檢查點與其父檢查點也隨基礎設施消失。因此，許多關鍵數據屬於「歷史運行」的快照，無法由他人直接重新執行。

然而，診斷階梯本身的設計極具可重現性優勢。逐字重現檢查、首詞元探針、未見提示測試與嵌入漂移檢查皆只需「分鐘級 CPU 時間」，且不需要重新訓練模型。只要研究者能取得模型的封存檢查點與其 Tool-SFT 訓練語料，就可以獨立驗證這些診斷。遺憾的是，目前上下文並未明確說明模型權重、訓練程式碼、語料庫或診斷腳本是否已公開釋出。若 VectraYX 系列為內部或商業模型，則外部研究者難以直接複製；若作者未來能釋出檢查點與診斷腳本，將大幅提升本研究的可重現性與影響力。

另一個可重現性挑戰是單一種子與單一檢查點。因子分析已顯示隨機種子敏感性（Seed Sensitivity）會影響「抑制效果」的結論，這意味著即使釋出程式碼，其他研究者使用不同種子可能得到略有差異的數值。因此，建議未來工作應進行多種子重現，並將診斷階梯包裝成標準化測試套件。

#### 未來研究方向

**1. 多種子與多檢查點的嚴格重現**  
未來應以多個隨機種子重新執行目標式 SFT 配方，並在 1B 模型的多個父檢查點上驗證修復是否穩定。這能將「多樣化語料庫有助於抑制過度觸發」從假說提升為較穩固的結論。

**2. 課程組成的因果消融實驗**  
本研究觀察到重網頁資料的訓練階段（Web-Heavy Training Phase）似乎抹除了工具呼叫先驗，但缺乏真正的兩臂消融。未來可在受控環境中系統性變動預訓練與 SFT 階段的資料比例、順序與領域組成，建立「bootstrap composition → 結構化輸出能力」的因果圖。

**3. 機制詮釋的深化**  
嵌入漂移檢查顯示修復發生在周邊網路（Surrounding Network），但未指出具體層或電路。未來可結合機制性可解釋性方法（如探針、消融、置換檢驗或因果中介分析），定位哪些注意力頭與前饋層負責觸發 `<|tool_call|>` 的生成，以及它們如何在重網頁訓練後被抑制。

**4. 過度觸發（Over-Trigger）的緩解策略**  
兩個模型在否定提示（Negative Prompts）上的抑制率都偏低。未來可探索專門的「不呼叫」負樣本、對比學習、或強化學習方法，來提升模型判斷「何時不該輸出工具呼叫」的能力，同時維持高召回率。

**5. 診斷階梯的標準化與自動化**  
本研究提出的低成本診斷階梯應被推廣為小型語言模型工具使用宣稱的標準把關流程。未來可開發開源工具套件，自動執行逐字重現、首詞元探針、結構化 JSON 驗證與嵌入漂移比較，並支援多種工具格式（如 function calling、MCP、ReAct）。

**6. 跨語言與跨領域驗證**  
VectraYX 系列專注於西班牙語／拉丁美洲網路安全（Spanish/LATAM Cybersecurity）領域。未來應在英語、中文及其他低資源語言，以及醫療、法律、金融等不同領域的小型模型上測試此診斷階梯，以確認其普適性。

**7. 動態基準測試框架的設計**  
既然關鍵字匹配基準測試（Keyword-Matching Benchmarks）容易偽陽性，未來可設計結合語法驗證器、執行模擬器與語意等價判斷的動態框架（Dynamic Harness），在模型聲稱完成工具呼叫時，實際檢查輸出是否可被 MCP 伺服器（MCP Server）解析並執行，從源頭減少誤判。

**8. 離線部署場景的端到端評估**  
考慮到 VectraYX 系列目標為透過 llama.cpp 進行氣隙隔離部署（Air-Gapped Deployment），未來應在真實邊緣裝置上執行此診斷階梯，並評估量化（quantization）對工具呼叫先驗與泛化能力的影響，以確保診斷結果能轉移到實際部署環境。

## 論文問答

**Q1：這篇論文指出的核心問題是什麼？**
A：這篇論文指出，關鍵字匹配基準測試會對小型語言模型的工具使用能力產生偽陽性判斷，也就是把實際上不會使用工具的模型誤判為具備此能力。作者以 VectraYX-600M 與 VectraYX-1B 這對同架構模型為例，兩者在寬鬆的 B4 指標上幾乎相同（0.660 對 0.650），但實際行為卻天差地遠：600M 能自發生成格式正確的工具呼叫，而 1B 只會產出不連貫的散文。這個現象顯示，現行的自動化評測框架可能嚴重高估小型模型的原生工具呼叫能力，進而誤導部署決策。

**Q2：為什麼現有的關鍵字匹配評測方法會失效？**
A：關鍵字匹配評測的失效原因在於它只檢查模型是否在回應中提到工具名稱或相關詞彙，卻不驗證是否產出可執行的結構化 JSON 載荷。例如 VectraYX-1B 雖然在訓練中經歷了約 60 億詞元的工具監督式微調，但它從未被觀察到發出 `<|tool_call|>` 包覆的 JSON 結構，卻仍能在寬鬆指標上獲得高分。這種「誤判開啟」的特性使得評測框架把「提到工具」與「真正呼叫工具」混為一談，無法區分表面詞彙與實質能力。

**Q3：為什麼準確評估工具使用能力對小型安全語言模型特別重要？**
A：這類西班牙語／拉丁美洲網路安全模型常部署於氣隙隔離環境，作為離線運作的安全助理，其工具呼叫能力直接關係到能否執行漏洞查詢或 shell 指令等任務。如果評測錯誤地宣稱某模型會使用工具，實際部署後可能發現它無法呼叫 `bash_exec` 或查詢 CVE，造成營運風險與安全決策失誤。因此，建立嚴謹且低成本的診斷機制，是避免過度信賴偽陽性分數的關鍵。

**Q4：論文提出的「低成本診斷階梯」包含哪些步驟？**
A：診斷階梯由四個漸進嚴格的檢查組成：首先是帶有泛化準則的逐字重現檢查，接著是首詞元機率探針，再來是未見提示的泛化測試電池，最後是嵌入漂移檢查。每一項都只需數分鐘 CPU 時間，卻能提供比關鍵字匹配更強的證據，分別用於抓出偽陽性、定位失效點、驗證修復效果，以及說明修復發生在網路的哪個部位。這四個步驟共同構成一道獨立於既有評測框架的把關機制，適合常態性檢驗小型模型的工具使用宣稱。

**Q5：這項研究最重要的方法創新是什麼？**
A：最重要的創新在於使用首詞元機率探針，將失效精確定位到 `<|tool_call|>` 這個觸發詞元上的缺失先驗。結果顯示 1B 模型在應該開始工具呼叫的位置，對該詞元僅賦予 10^{-4} 到 10^{-5} 的機率，這說明它幾乎完全沒有結構化輸出的先驗，而非僅是解碼競爭中落敗。這種機制性診斷讓作者能設計出目標式監督式微調配方，僅用約 3.3 GPU 小時、2202 步就完成修復，比原本失敗的專屬階段少了約三個數量級的詞元。

**Q6：為什麼作者選擇以逐字重現檢查作為診斷階梯的第一步？**
A：逐字重現檢查被選為第一步，是因為它是最便宜卻已足夠的儀器，能直接測試模型是否能從自身訓練範例中重現並泛化出正確格式。作者要求模型產出格式正確的工具呼叫 JSON，且引數必須是訓練答案的合理非相同變體，藉此區分真正的能力與單純背誦。這個檢查的結果非常明確：600M 在 6/6 範例中成功，而 1B 在所有測試檢查點都是 0/4–6，徹底分開了兩個在寬鬆指標上幾乎相同的模型。

**Q7：實驗使用了哪些資料集與評估設定？**
A：實驗使用了 269 筆來自模型自身工具監督式微調語料庫的資料列，以及 238 筆針對未見實體設計的新提示，用於測試泛化能力。此外，作者檢視了 1B 模型的 38 個封存檢查點，以追蹤 `<|tool_call|>` 先驗是在哪個訓練階段被抹除。評估指標包括有效生成率、逐字重現通過率、首詞元機率，以及未見提示上的配對 p 值，從多個角度檢驗模型的真實能力。

**Q8：論文的主要實驗結果是什麼？**
A：經過目標式修復後，1B 模型在全部 269 筆語料列上的有效生成率從 0.100 大幅提升到 0.959，甚至超過 600M 的 0.926。在 238 筆未見提示上，修復後的 1B 通過率為 0.536，顯著高於 600M 的 0.428（配對 p = 0.004），顯示修復確實帶來泛化能力。然而，兩個模型在否定提示上都出現過度觸發：600M 僅在 0.09 的不呼叫項目上正確抑制，修復後的 1B 也僅達 0.17，顯示抑制能力仍是弱點。

**Q9：因子分析揭示了哪些關於修復配方的訊息？**
A：因子分析橫跨語料組成與學習率，確認每一種修復配置都能成功安裝工具呼叫格式。其中最大的對比顯示，在低學習率下使用多樣化語料庫可能有較好的抑制效果，但這個結果在部分第二隨機種子中未能重現。因此，多樣化語料對抑制過度觸發的益處目前仍只能視為假設，而非已確立的結論，這也凸顯了隨機種子敏感性在小型模型訓練中的影響。

**Q10：實務部署中應如何運用這套診斷階梯？**
A：在宣稱任何小型模型具備工具使用能力之前，開發者應先以真實訓練範例執行逐字重現檢查，再視需要進行首詞元探針與未見提示測試。整個階梯只需數分鐘 CPU 時間，卻能有效避免部署那些只會在散文中提到工具、卻無法產出可執行 JSON 的模型。對於要作為安全助理上線的產品而言，通過這四項診斷比單純依賴關鍵字匹配基準分數更能提供可信的能力保證。

**Q11：過度觸發的發現對產品設計有什麼啟示？**
A：過度觸發的發現意味著即使模型學會了工具呼叫格式，也不代表它能在應該純對話回應的提示上正確抑制。產品團隊必須額外設計抑制機制，並針對否定提示進行獨立評估，而非只關注正面工具使用案例。兩個模型在不呼叫提示上的正確抑制率都低於兩成，這說明原始能力與適當節制是兩回事，部署時需要分開處理與優化。

**Q12：這項工作可能如何改變學界與業界評估小型語言模型的方式？**
A：這項工作提醒學界與業界，應對關鍵字匹配的工具使用指標保持懷疑，並採用結構化驗證來取代表面分數。它進一步指出，啟動註冊（bootstrap composition）——也就是預訓練課程的內容組成——決定了結構化輸出能力是自然浮現還是必須後天工程化補強。這可能促使評估實務從單純比較基準分數，轉向結合機制性診斷與嚴格重現測試的綜合把關流程。

**Q13：論文明確承認了哪些限制？**
A：論文承認修復後的檢查點是單一隨機種子的重現，且原始訓練執行的檢查點已隨基礎設施遺失。此外，VectraYX-600M 的訓練執行被永久凍結在計畫進度的 64%，因此所有 600M 相關結果都是未完成執行的快照。因子分析中關於多樣化語料抑制優勢的發現也未能跨種子完全重現，這些限制都讓部分結論帶有初步探索的性質。

**Q14：還有哪些失效模式或邊緣案例尚未解決？**
A：兩個模型都會在提到 CVE 或 shell 指令的對話式提示上過度觸發，顯示抑制能力仍是未解決的問題。修復後的 1B 雖然在語料上表現優異，卻大多呈現背誦行為，暗示格式安裝與自然泛化之間存在取捨。此外，由於隨機種子敏感性，最適合抑制過度觸發的配方尚未確定，這些都是後續需要進一步研究的失效模式。

**Q15：這項工作指出了哪些未來研究方向？**
A：未來研究應進行多種子、多檢查點的修復配方複製，以解決抑制性能的種子敏感問題。研究者也可以深入探討為何重網頁資料的訓練階段會抹除結構化輸出的先驗，以及如何設計預訓練混合物讓工具使用能力自然浮現。將這套低成本診斷階梯擴展到其他工具格式與更大規模模型，也有助於將其建立為評估工具使用宣稱的標準程序。

## 實務應用指南

## 適用場景

1. **離線安全助理的模型驗收**：在氣隙隔離環境內部屬西班牙語／拉丁美洲網路安全模型時，採用此診斷階梯驗證模型是否真的能發出 `bash_exec` 或 MCP 工具呼叫，而非僅在回應中提到工具名稱。
2. **小型模型選型與採購評估**：當面對兩個同架構、同分詞器、同特殊詞元配置的小型語言模型，且其基準測試分數相近時，用低成本檢查區分「會呼叫工具」與「只會談論工具」的模型。
3. **工具使用監督式微調（Tool-SFT）失敗根因分析**：當模型經過數十億 token 的 Tool-SFT 後仍無法輸出 JSON 結構，可透過首詞元探針判斷是否為 `<|tool_call|>` 先驗機率過低所致，並據此調整訓練配方。
4. **模型修復後的泛化驗證**：在對模型進行目標式 SFT 修復後，使用未見過提示（unseen prompts）與嵌入漂移檢查確認修復是學到能力而非背誦訓練範例。
5. **關鍵字匹配基準測試的獨立稽核**：對於宣稱具備工具使用能力的小型模型，以逐字重現檢查作為第三方把關機制，避免被寬鬆指標誤導。

## 實作前置條件

- **資料**：需取得模型自身的 Tool-SFT 訓練範例（含真實系統前導詞與可用 MCP 工具清單），以及一批未見過的測試提示（建議至少 200 筆以上，涵蓋需要呼叫與不應呼叫兩類）。
- **運算**：逐字重現與首詞元探針僅需 CPU 或單張 GPU 數分鐘；目標式 SFT 修復則需單張 GPU 約 3.3 GPU-hours（參考 2,202 steps）。嵌入漂移檢查只需比對訓練前後 bf16 嵌入表。
- **技能**：熟悉 Python、PyTorch 或相容框架；能執行貪婪解碼（greedy decode）並解析 JSON 載荷；具備基礎統計檢定能力以計算配對 p 值；了解特殊詞元配置與嵌入表結構。
- **工具**：模型推論框架（如 llama.cpp 或 Hugging Face Transformers）、JSON 格式驗證器、模型檢查點存取權限。

## 實作步驟建議

1. **建立嚴格評估基線**：先以關鍵字匹配基準測試取得 B4 等寬鬆指標，作為對照組。
2. **執行逐字重現檢查**：從 Tool-SFT 訓練語料中挑選 6–10 筆真實範例，使用訓練時的系統前導詞與貪婪解碼，要求模型輸出格式正確的 JSON 工具呼叫，且引數必須是訓練答案的泛化變體（非位元級複製）。
3. **進行首詞元探針**：在應該開始工具呼叫的位置，檢查 `<|tool_call|>` 的先驗機率。若機率僅 10⁻⁴–10⁻⁵，表示模型幾乎沒有結構化輸出的先驗。
4. **回溯檢查點**：若封存檢查點存在，比對各階段首詞元機率，定位先驗是在哪個訓練階段（例如重網頁資料的訓練階段）被抹除。
5. **設計目標式 SFT 配方**：採用多樣化語料庫（對話、工具語料、領域推理軌跡）、不凍結嵌入表、並將學習率提高約 5 倍，進行短週期微調。
6. **驗證修復效果**：
   - 在全部語料列上計算有效生成比例；
   - 在未見過提示上計算通過率，並與對照模型做配對檢定；
   - 執行嵌入漂移檢查，確認觸發詞元的綁定嵌入是否位元完全相同，以判斷改變發生在周邊網路。
7. **評估過度觸發**：對否定提示（no-call prompts）測量模型不呼叫工具的比例，確保模型不會濫發工具呼叫。
8. **建立持續把關閘門**：將上述階梯自動化為 CI 流程，任何宣稱具備工具使用能力的新檢查點都必須通過才能發布。

## 潛在風險與注意事項

- **偽陽性評分**：寬鬆的關鍵字匹配基準測試會把「提到工具名稱」誤判為「會使用工具」，切勿單獨依賴 B4 等指標做產品決策。
- **過度觸發**：即使修復後的模型仍可能在不需要呼叫時輸出工具呼叫（例如遇到 CVE 或 shell 指令時），需額外設計抑制機制或後處理過濾。
- **種子敏感性**：因子分析顯示多樣化語料對抑制過度觸發的效益可能受隨機種子影響，建議多種子驗證後再下結論。
- **嵌入表凍結陷阱**：若 SFT 時凍結嵌入表，可能無法修復 `<|tool_call|>` 的先驗缺失；但即使不凍結，也可能發現改變主要發生在周邊網路，需搭配嵌入漂移檢查理解機制。
- **單一檢查點限制**：論文中的修復是單一配方在單一檢查點上的結果，部署前應在不同檢查點與不同資料分佈上重複驗證。
- **基礎設施遺失風險**：訓練 VM 與雲端帳號可能隨時終止，務必即時封存檢查點與訓練紀錄，避免無法重現。

## 與其他技術的整合建議

- **MCP 伺服器**：將通過診斷階梯的模型對接 MCP 伺服器，並在伺服器端加上 JSON Schema 驗證，形成「模型生成＋伺服器把關」的雙層防護。
- **llama.cpp 推論管線**：由於目標場景常為離線部署，可將驗證流程整合進 llama.cpp 的貪婪解碼與 logits 探針腳本，直接在邊緣裝置上執行診斷。
- **CI/CD 模型閘門**：把逐字重現檢查、首詞元探針與未見過提示測試包裝成自動化測試，嵌入模型訓練完成後的發布管線。
- **觀測與可解釋性工具**：搭配嵌入漂移檢查與注意力視覺化工具，持續監控 `<|tool_call|>` 觸發詞元的機率分佈，作為線上模型健康度指標。
- **安全後處理層**：在模型與實際執行之間加入權限控管與沙箱，特別針對 `bash_exec` 等高危工具，避免過度觸發導致未授權指令執行。

## 給不同背景讀者的閱讀建議
