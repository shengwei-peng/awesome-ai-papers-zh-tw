AutoPILOT 的核心洞見在於重新定位「代理框架（harness）」設計的第三個面向——模型輸出如何隨時間轉化為動作。傳統的單步代理迴圈（single-step agent loop）遵循 ReAct 模式，每一次模型呼叫（model call）至多產生一個動作，這在遊戲會等待代理的環境（如 ARC-AGI-3）中運作良好，但在即時（real-time）遊戲中卻形成嚴重瓶頸：代理的行動頻率被限制為模型的思考頻率，且只能基於過時的畫面做決策。

**三種執行模式的設計哲學**

AutoPILOT 將每一次模型呼叫擴展為可選擇三種執行模式，這個設計靈感來自「飛行員配備自動駕駛」的隱喻——模型如同飛行員，可將例行控制委託給自動駕駛系統，僅在必要時接管：

1. **基本動作（primitive action）**：直接傳送單一原子動作至遊戲，適用於需要精確即時反應的情境。

2. **開放迴路巨集（open-loop macro）**：模型撰寫一連串預先定義的動作序列，由工作執行緒（worker）以約 0.36 秒的間隔依序執行，不讀取螢幕畫面。論文中 Trichromat 遊戲的範例展示模型如何將九個方向鍵操作打包成單一巨集，每個按鍵按住 0.15 秒、釋放後擷取畫面、再執行下一個按鍵。

3. **閉迴路控制器（closed-loop controller）**：模型在執行階段即時撰寫一段 Python 程式碼，該程式以約 0.4 秒的週期讀取螢幕畫面並執行動作，無需進一步的模型呼叫。論文中 Praxis Fighter X 的範例展示控制器如何透過顏色特徵辨識太空船位置與子彈威脅，自動閃避並射擊，直到迴圈結束或請求交接。

**喚醒事件（awake event）機制**

控制權在以下三種情況下回歸模型：巨集或控制器執行完畢、控制器主動呼叫 `request_handoff`、或畫面出現控制器未預期的場景。這種設計確保模型不會完全失去對遊戲狀態的感知，同時讓例行操作得以高效執行。

**與 VISTA 的關鍵差異**

VISTA 雖然改善了「模型看見什麼」與「模型記住什麼」（透過視覺記憶與檢視工具），但仍遵循單步代理迴圈。AutoPILOT 繼承了這些視覺能力，但根本性地改變了「模型輸出如何隨時間轉化為動作」——這正是論文中所強調的、以往被忽略的代理設計核心面向。

**觀察介面的一致性**

值得注意的是，無論是模型本身或其撰寫的控制器，皆透過螢幕畫面（而非遊戲狀態）進行觀察，這維持了視覺代理（visual agent）的純粹性，避免依賴遊戲專屬的內部狀態資訊，使框架能跨遊戲通用。

#### 實驗數據解讀

**AFK-Bench 的基準設計**

AFK-Bench（Away From Keyboard）包含 120 個瀏覽器遊戲，依據「代理閒置時遊戲如何反應」均分為三類：

- **敵意即時環境（hostile real-time environments）**：閒置會導致失敗，例如敵人持續攻擊、資源持續流失。
- **良性即時環境（benign real-time environments）**：環境持續變化但不懲罰閒置，例如場景動畫或背景移動。
- **回合制環境（turn-based environments）**：僅在代理行動時推進。

每款遊戲皆可即時或暫停時鐘遊玩，兩者的差異即衡量「即時性對代理的成本」。失敗的遊戲會在固定的模型呼叫、遊戲時間與環境步驟預算內重新開始。

**主要效能數據**

在 GPT-6.1 Sol 與相同預算下：

| 指標 | AutoPILOT | VISTA |
|------|-----------|-------|
| AFK-Bench 即時成功率 | 68.6% | 38.3% |
| AFK-Bench 敵意即時成功率 | 62.5% | 16.7% |
| GameWorld 即時成功率 | 80.0% | 42.9% |
| GameWorld 暫停時鐘成功率 | 82.9% | 84.1% |

AutoPILOT 在即時環境中相對 VISTA 的提升幅度極為顯著，尤其在敵意即時環境中從 16.7% 提升至 62.5%，差距近 46 個百分點，凸顯閉迴路控制器在需要持續反應的場景中的價值。

**即時性成本分析**

「讓時鐘運行」對 AutoPILOT 與 VISTA 的影響差異極大：

- AFK-Bench：AutoPILOT 僅損失 4.5 個百分點（73.1% → 68.6%），VISTA 損失 17.8 個百分點。
- GameWorld：AutoPILOT 損失 2.9 個百分點（82.9% → 80.0%），VISTA 損失 41.2 個百分點。

這顯示 AutoPILOT 的設計有效緩解了即時性帶來的效能損失。

**暫停時鐘的優勢**

即使在暫停時鐘的條件下，AutoPILOT 仍以 73.1% 對 56.1% 領先 VISTA，差距約 17 個百分點。這說明 AutoPILOT 的優勢不僅來自於處理即時性，更來自於「單次模型呼叫可執行整個計畫」帶來的效率提升——模型無需為每個動作單獨呼叫，減少了推理開銷與上下文切換成本。

**成本效益分析**

AutoPILOT 使用比 VISTA 少 47% 的 tokens，並以 VISTA API 成本的 0.2 倍（即五分之一）即可達到 VISTA 的最終成功率。這是因為控制器與巨集在執行階段無需持續呼叫模型，大幅降低了 API 開銷。

**跨模型泛化**

增益在 Claude Opus 5.5 與另外四個模型上皆成立，顯示 AutoPILOT 的設計並非依賴特定模型的特性，而是框架層面的通用改進。

**推理努力的影響**

論文中提到更多推理（reasoning）僅為 VISTA 帶來 4-7 個百分點的提升（在高推理努力下），這暗示單純增加模型思考時間無法解決即時性瓶頸，必須從框架設計著手。

#### 與現有研究的比較

**與 VISTA 的定位**

VISTA 透過視覺記憶與檢視工具改善了「模型看見什麼」與「模型記住什麼」，在 ARC-AGI-3 上將現成模型提升至完美分數。然而，VISTA 仍遵循單步代理迴圈，在即時環境中表現不佳。AutoPILOT 與 VISTA 的關係是互補而非取代：AutoPILOT 改變的是「模型輸出如何隨時間轉化為動作」，可與 VISTA 的視覺增強機制結合。

**與其他遊戲代理的比較**

從表 1 的比較可見：

- **Voyager、Cradle、Game-TARS**：需要遊戲專屬訓練或無法即時評估。
- **Code as Policies**：僅限於機器人領域。
- **HLA、DPT-Agent**：專注於 Overcooked，泛化性有限。
- **Lumine**：專注於 3D 動作遊戲，僅 4 個環境。
- **Realtime-Bench**：雖支援即時評估，但不支援巨集動作或模型撰寫控制器。
- **AsyncLLM**：雖嘗試非同步處理，但僅限於 QA、影片與 ViZDoom。

AutoPILOT 是唯一同時滿足「無遊戲專屬訓練」、「一個框架適用多種遊戲」、「即時評估」、「支援巨集動作」與「支援模型撰寫控制器」五項條件的方法，且涵蓋 154 個環境（AFK-Bench 120 + GameWorld 34）。

**改進的核心**

相較於現有研究，AutoPILOT 的主要改進在於：

1. **將時間維度納入框架設計**：以往研究多專注於空間維度（觀察、記憶），AutoPILOT 強調時間維度（動作序列的執行方式）同樣關鍵。

2. **模型撰寫程式碼作為策略**：閉迴路控制器的概念類似 Code as Policies，但 AutoPILOT 將其整合進即時遊戲代理框架，並提供喚醒機制避免失控。

3. **量化即時性成本**：AFK-Bench 的設計讓研究者能精確測量「即時性對代理的影響」，這是過往基準測試較少關注的面向。

**現有限制**

1. **控制器安全性**：模型撰寫的 Python 程式碼在沙盒中執行，但若沙盒存在漏洞，可能造成安全風險。

2. **控制器正確性**：模型可能撰寫含有錯誤的控制器，導致代理陷入無效行為。雖然喚醒機制可緩解此問題，但錯誤控制器的偵測仍仰賴後續模型呼叫。

3. **遊戲類型覆蓋**：AFK-Bench 雖包含 120 款瀏覽器遊戲，但對於需要複雜長期策略或高度精確操作（如競技類遊戲）的場景，AutoPILOT 的表現仍待驗證。

4. **模型撰寫程式碼的能力**：閉迴路控制器依賴模型具備撰寫正確 Python 程式碼的能力，對於較弱的模型可能無法有效運用此機制。

- 沙盒強化機制限制控制器的系統呼叫權限。

**2. 學習式控制器生成**

目前控制器由模型在執行階段即時撰寫，未來可探索：

- 結合強化學習，讓控制器在多次嘗試中自我優化。

**3. 理論分析**

AutoPILOT 的成功引發若干理論問題：

- 在何種條件下，閉迴路控制器優於持續模型呼叫？是否存在計算複雜度下界？
- 喚醒事件的設計如何影響代理的探索與利用平衡？
- 巨集動作的長度與即時性需求之間的最佳取捨為何？

**4. 跨領域應用**

AutoPILOT 的時間維度設計可應用於其他即時環境：

- **機器人控制**：在物理世界中，代理無法等待模型思考，必須即時反應。
- **自動駕駛**：類似飛行員與自動駕駛的關係，模型可處理複雜決策，控制器處理例行操作。
- **工業控制系統**：在需要即時反應的製程中，模型撰寫的控制器可作為監督層。

**5. 與其他框架的整合**

AutoPILOT 可與現有框架結合：

- 與 VISTA 的視覺記憶整合，進一步提升觀察品質。
- 與 Cradle 的遊戲通用介面整合，擴展至更多遊戲類型。
- 與 Voyager 的技能庫整合，將成功控制器累積為可重複使用的技能。

**6. 人機協作模式**

AutoPILOT 的「飛行員與自動駕駛」隱喻自然延伸至人機協作：

- 人類可作為「喚醒事件」，在特定時刻接管控制。
- 控制器可作為人類決策的輔助工具，自動處理例行操作。
- 多代理協作：不同模型或人類代理可同時運行控制器與監督層。

**7. 評估方法的擴充**

AFK-Bench 的分類標準（敵意、良性、回合制）可進一步細化：

- 加入「部分可觀察」與「完全可觀察」的區分。
- 考慮多代理場景下的協作與競爭。
- 設計長期任務（跨多個遊戲階段）的評估指標。

**8. 開源生態系建立**

為促進研究發展，未來可建立：

- 標準化的控制器描述語言，便於跨框架分享。
- 公開的控制器庫，收集成功案例供後續研究參考。
- 統一的即時遊戲評估協議，簡化基準測試的設計。

這些研究方向不僅能深化對 AutoPILOT 的理解，更能推動整個視覺代理領域朝「處理真實世界中不等待代理的環境」邁進，這正是論文標題「in a world that does not wait」所揭示的願景。

## 論文問答

**Q1：為什麼現有的視覺代理框架在即時遊戲中表現不佳？**

A：現有的視覺代理框架（如 VISTA）大多遵循單步代理迴圈（single-step agent loop）的預設，即每次模型呼叫最多產生一個動作，並假設環境會等待代理行動。然而在即時遊戲中，遊戲時鐘持續運行，代理只能在模型思考時才能行動，且只能基於過時的幀做決策。這造成了嚴重的瓶頸：代理行動的頻率受限於模型思考的速度。實驗數據顯示，VISTA 在 GameWorld 上即時模式的成功率從 84.1% 驟降至 42.9%，即使加入視覺記憶和檢視工具也無法有效解決此問題。

**Q2：什麼是「代理框架」（harness），為什麼它在代理設計中如此重要？**

A：代理框架是指圍繞模型的系統，決定模型看到什麼、記住什麼，以及其輸出如何隨時間轉化為動作。雖然過去的研究主要改進了前兩個面向（觀察與記憶），但第三個面向——模型輸出如何隨時間轉化為動作——通常被隱含處理。一個更好的框架可以在不改變模型的情況下大幅提升成功率，例如 VISTA 將現成模型在 ARC-AGI-3 上提升到完美分數。本文的核心論點是：如何將模型輸出轉化為隨時間的動作，是代理設計中一個核心但被低估的部分。

**Q3：為什麼僅靠改進模型觀察與記憶無法解決即時遊戲的瓶頸？**

A：即使 VISTA 配備了視覺記憶和檢視工具，在即時模式下其表現仍與基本的 Codex 框架相當（38.3% vs. 38.9%），這說明僅改進觀察與記憶並不能消除瓶頸。同樣地，增加推理努力也僅為 VISTA 帶來 4-7 個百分點的提升。這些結果表明，瓶頸主要在於框架如何將模型輸出轉化為動作——當模型呼叫頻率跟不上遊戲節奏時，再好的視覺記憶也無法彌補行動延遲的問題。

**Q4：AutoPILOT 的核心方法是什麼？它如何改變模型輸出轉化為動作的方式？**

A：AutoPILOT 的核心創新在於讓單次模型呼叫可以涵蓋多個環境步驟，模型可以選擇三種執行模式之一：(1) 基本動作直接發送給遊戲；(2) 開放迴路巨集（open-loop macro）是由模型編寫的動作序列；(3) 閉迴路控制器（closed-loop controller）是模型在運行時編寫的短 Python 程式，能讀取螢幕畫面並約每 0.4 秒執行一次動作而無需進一步的模型呼叫。這就像飛機的自動駕駛系統——模型將常規控制委託給巨集或控制器，僅在被喚醒時接管。

**Q5：開放迴路巨集和閉迴路控制器有什麼區別？各自適用於什麼場景？**

A：開放迴路巨集是一系列由模型編寫的動作，不依賴螢幕回饋，適用於環境變化可預測或不需要持續反應的場景，例如回合制遊戲 Trichromat 中模型預先規劃的九個按鍵動作。閉迴路控制器則是模型在運行時編寫的 Python 程式，會持續讀取螢幕畫面並根據視覺資訊做出反應，適用於需要即時反應的敵對即時環境，例如 Praxis Fighter X 中透過顏色識別船隻位置與子彈並進行閃避與射擊。兩者都會在完成、被要求交還控制權、或遇到未預期的畫面時將控制權交還給模型。

**Q6：AutoPILOT 在設計上有哪些重要的選擇？為什麼選擇讓模型撰寫 Python 控制器？**

A：AutoPILOT 選擇讓模型撰寫 Python 程式作為閉迴路控制器，而非使用預定義的動作模板或專門訓練的模型，這樣做有多重考量。首先，這保持了「無遊戲專屬訓練」的原則，使同一個框架能適用於 154 個不同的環境。其次，Python 程式提供了極大的靈活性，模型可以根據具體遊戲需求編寫自定義的視覺處理邏輯（如顏色過濾、位置計算）。最後，控制器的設計包含「喚醒事件」（awake event）機制，確保模型在必要時能夠重新接管控制，這種設計兼顧了自主性與可控性。

**Q7：AFK-Bench 是什麼？它如何衡量即時環境對代理的影響？**

A：AFK-Bench（Away From Keyboard）是一個包含 120 個瀏覽器遊戲的基準測試，這些遊戲根據代理閒置時的行為均勻分為三類：敵對即時環境（閒置會導致失敗）、良性即時環境（會持續變化但不懲罰閒置）、回合制環境（僅在代理行動時推進）。每款遊戲都可以在即時模式或暫停模式下遊玩，兩者的差異即衡量了即時性對代理的代價。失敗的遊戲會在固定的模型呼叫、遊戲時間和環境步驟預算內重新開始，這種設計使得基準測試能夠系統性地評估代理在不同即時性要求下的表現。

**Q8：AutoPILOT 在實驗中的主要成果是什麼？**

A：在相同的 GPT-6.1 Sol 模型和預算下，AutoPILOT 在 AFK-Bench 即時模式中達到 68.6% 的成功率，而 VISTA 僅為 38.3%；在敵對即時環境中，AutoPILOT 達到 62.5%，VISTA 僅為 16.7%。在 GameWorld 上，AutoPILOT 在即時模式下保持 80.0% 的成功率，而 VISTA 從 84.1% 降至 42.9%。值得注意的是，即使在暫停模式下，AutoPILOT 也以 73.1% vs. 56.1% 領先 VISTA，因為單次模型呼叫即可執行整個計畫。此外，AutoPILOT 使用少 47% 的 token，以 0.2 倍的 API 成本達到 VISTA 的最終成功率。

**Q9：AutoPILOT 的哪些設計組件對其效能貢獻最大？**

A：從整體分析可以看出，三種執行模式的組合是關鍵——基本動作處理簡單情況，開放迴路巨集處理可預測的動作序列，閉迴路控制器處理需要即時反應的情況。預算分配、推理努力和生成速度等因素也被分析為重要的影響變數。實驗還顯示，AutoPILOT 的增益在多個模型上都成立（包括 Claude Opus 5.5 和其他四個模型），這證明了框架設計的通用性，而非依賴特定模型的特性。

**Q10：AutoPILOT 在實際應用中可能適用於哪些場景？**

A：AutoPILOT 的設計理念——讓單次模型呼叫涵蓋多個環境步驟——適用於任何需要即時反應且環境不會等待代理的場景。這包括視訊遊戲代理、即時監控系統、自動化交易、機器人控制等。在遊戲領域，由於其「無遊戲專屬訓練」的特性，AutoPILOT 可以快速部署到新遊戲中，無需重新訓練模型。對於電腦使用代理（computer-use agents），AutoPILOT 的巨集和控制器機制也能讓代理更有效率地處理需要快速反應的使用者介面操作。

**Q11：AutoPILOT 在產品化時需要考慮哪些實際因素？**

A：產品化 AutoPILOT 時需要考慮幾個關鍵因素：首先是安全性，模型撰寫的 Python 控制器需要在沙箱環境中執行以防止意外行為；其次是可靠性，需要確保控制器在遇到未預期畫面時能正確地將控制權交還給模型；此外還有成本效益，雖然 AutoPILOT 已展示出以 0.2 倍 API 成本達到 VISTA 表現的能力，但實際部署仍需考慮 token 使用量與延遲的權衡。最後，使用者體驗也很重要，需要設計良好的介面讓使用者能理解和介入代理的決策過程。

**Q12：AutoPILOT 對視覺代理研究領域有什麼更廣泛的影響？**

A：AutoPILOT 最重要的貢獻是將「模型輸出如何隨時間轉化為動作」提升為代理框架設計的核心面向，這挑戰了傳統單步代理迴圈的預設。這種思路可以啟發更多關於代理自主性、巨集學習和閉迴路控制的研究。AFK-Bench 作為一個專門衡量即時性代價的基準測試，也將推動該領域更系統地評估代理在真實即時環境中的表現。整體而言，AutoPILOT 強調了「世界不會等待」這一現實，對於通用人工智慧代理的設計具有重要啟示意義。

**Q13：AutoPILOT 有哪些已承認的限制？**

A：雖然摘要未明確列出所有限制，但從設計和實驗中可以推斷出一些潛在限制。首先，模型撰寫的 Python 控制器需要模型本身具備良好的程式設計能力，這對較弱的模型可能是一個挑戰。其次，閉迴路控制器依賴於視覺處理（如顏色識別），對於視覺資訊複雜或難以用簡單規則描述的遊戲可能效果不佳。此外，雖然 AutoPILOT 在 154 個環境中表現良好，但對於需要極精細操作或極快反應速度的遊戲，0.4 秒的控制週期可能仍然不夠。

**Q14：AutoPILOT 可能會在哪些情況下失敗？**

A：AutoPILOT 可能在以下情況下遇到困難：(1) 當遊戲的視覺資訊過於複雜，模型難以用簡單的 Python 程式（如顏色過濾）來識別關鍵物件時；(2) 當遊戲需要極快的反應速度（低於 0.4 秒）時，控制器的反應可能不夠及時；(3) 當模型本身的程式設計能力不足，無法寫出正確的控制器邏輯時；(4) 當遊戲狀態空間極大，模型難以預先規劃完整的巨集或控制器時。此外，在敵對即時環境中，即使有控制器，長期的策略規劃仍然需要模型介入，這可能會限制 AutoPILOT 的表現上限。

**Q15：AutoPILOT 和 AFK-Bench 未來可以朝哪些方向發展？**

A：未來的研究可以從多個方向延伸：在方法層面，可以探索更複雜的控制器結構（如神經網路控制器）、更好的喚醒機制設計、以及模型與控制器之間更緊密的協作。在評估層面，AFK-Bench 可以擴展更多遊戲類型、更長的遊戲時長，以及更細粒度的即時性測量。在應用層面，可以將 AutoPILOT 的理念應用於機器人控制、自動駕駛、即時監控等更廣泛的領域。此外，研究如何讓模型從經驗中學習和改進其撰寫的控制器，也是值得探索的重要方向。

## 實務應用指南

### 適用場景

1. **即時網頁遊戲自動化測試（QA 自動化）**：遊戲公司可在 CI/CD 流程中部署 AutoPILOT 代理，自動遊玩數百款瀏覽器遊戲並回報 bug、平衡性問題與玩家流失點。相較於傳統單步代理迴圈，AutoPILOT 的閉迴路控制器能在模型推理期間持續操作角色，特別適合測試需要即時反應的射擊、格鬥、節奏類遊戲。

2. **直播與內容創作輔助**：實況主可在掛機或休息時段讓 AutoPILOT 代理接手遊玩，自動完成重複性刷寶、每日任務等內容。開放迴路巨集適合執行已知流程（如「連續施放三個技能」），閉迴路控制器則可在遭遇突發事件（如 PvP 對手出現）時自動應對。

3. **瀏覽器內即時網頁自動化**：企業可將 AutoPILOT 框架延伸至搶票系統、限時搶購、自動化表單填寫等場景。當目標網頁在倒數計時或即時更新時，閉迴路控制器能在不呼叫模型的情況下持續監控畫面並執行操作，避免因 API 延遲而錯失機會。

4. **教育與訓練模擬器**：用於駕駛模擬、飛行模擬、醫療手術模擬等需要即時反應的訓練環境。AutoPILOT 可作為示範代理，示範如何在高頻操作中穿插高層次決策，並在關鍵時刻喚醒模型進行策略調整。

5. **無障礙遊玩輔助**：為行動不便的玩家設計的代理，可根據玩家的高層次意圖（如「想贏這場對戰」）自動處理低階操作。模型只需偶爾介入做戰略決策，控制器負責持續執行，大幅降低玩家的操作負擔。

### 實作前置條件

**資料需求**
- 至少數十款瀏覽器遊戲或即時互動環境作為測試場域（AFK-Bench 提供 120 款現成遊戲）
- 每款環境的螢幕畫面擷取介面（截圖 API）與動作注入介面（鍵盤/滑鼠事件）
- 環境分類標註：敵意即時（hostile real-time）、良性即時（benign real-time）、回合制（turn-based），用於決定預算配置

**運算資源**
- 多模態基礎模型 API 存取權限（GPT-6.1 Sol、Claude Opus 5.5 等）或自架模型所需的 GPU 叢集
- 程式碼沙箱環境（Python 3.x）以執行模型撰寫的閉迴路控制器，建議使用容器化隔離（如 Docker + gVisor）
- 瀏覽器自動化基礎設施（Playwright、Selenium Grid 或無頭瀏覽器叢集）

**技能門檻**
- 熟悉多模態模型的 prompt engineering，特別是讓模型選擇三種執行模式（基本動作、開放迴路巨集、閉迴路控制器）的指令設計
- Python 中階能力：能閱讀模型產生的控制器程式碼、處理 NumPy 影像陣列、實作喚醒事件（awake event）機制
- 基本的代理框架概念：理解 ReAct 迴圈、視覺記憶、檢視工具的設計取捨
- 成本與預算管理經驗：能根據任務難度設定模型呼叫次數、遊戲時間、環境步驟上限

### 實作步驟建議

**階段一：環境建置（2-4 週）**
1. 部署瀏覽器自動化基礎設施，確保能以約 0.4 秒的頻率擷取螢幕畫面並注入鍵鼠事件
2. 將目標遊戲或網頁環境包裝成統一介面，提供 `observe()` 回傳 RGB 陣列與 `act()` 接收動作
3. 建立環境分類系統，依「閒置時是否懲罰玩家」將環境分為三類

**階段二：核心框架實作（4-6 週）**
1. 實作三種執行模式的執行器：
   - 基本動作：直接傳遞單一鍵鼠事件
   - 開放迴路巨集：解析模型輸出的動作序列，依時間間隔依序執行
   - 閉迴路控制器：在沙箱中執行程式碼，提供 `api.observe()`、`api.act()`、`api.request_handoff()` 介面
2. 設計喚醒事件機制：當巨集/控制器完成、請求交還、或畫面超出預期時，自動喚醒模型
3. 整合視覺記憶與檢視工具（可參考 VISTA 的設計），讓模型能回顧過去幀

**階段三：模型整合與 prompt 設計（2-3 週）**
1. 設計系統提示詞，明確說明三種執行模式的選擇時機與語法
2. 提供 few-shot 範例（論文 Figure 2 的 Trichromat 巨集與 Praxis Fighter X 控制器是良好範本）
3. 設定預算限制：模型呼叫次數、遊戲時間、環境步驟上限

**階段四：評估與迭代（持續）**
1. 在 AFK-Bench 或自建基準上評估即時成功率
2. 分析失敗案例，特別關注敵意即時環境（hostile real-time）的表現
3. 調整推理強度、控制器頻率、預算分配等超參數

**階段五：產品化（4-8 週）**
1. 加入成本監控儀表板，追蹤 API 用量與單次任務成本
2. 實作安全機制：控制器程式碼靜態分析、執行時間上限、資源使用上限
3. 設計使用者介面，讓非技術使用者能設定任務目標與預算

### 潛在風險與注意事項

**風險一：模型撰寫的控制器具安全疑慮**
- **問題**：閉迴路控制器是模型在執行階段產生的 Python 程式碼，可能包含無限迴圈、資源耗盡、或意外副作用
- **緩解**：在沙箱中執行（限制 CPU 時間、記憶體、檔案系統存取）；設定最大迭代次數（如 240 步）；實作強制中斷機制

**風險二：API 成本失控**
- **問題**：雖然 AutoPILOT 整體成本較低，但若模型頻繁呼叫 API 或撰寫過於複雜的控制器，成本仍可能超出預期
- **緩解**：設定硬性預算上限；監控每個任務的 token 用量；對簡單任務優先使用開放迴路巨集而非控制器

**風險三：即時環境的延遲敏感性**
- **問題**：模型推理時間（數秒）可能導致錯過關鍵操作時機，特別在高速動作遊戲中
- **緩解**：使用較小的模型處理常規操作；將高頻操作交給閉迴路控制器；設定合理的喚醒閾值

**風險四：泛化能力不足**
- **問題**：模型可能在訓練分布外的遊戲類型表現不佳，例如從未見過的 UI 風格或遊戲機制
- **緩解**：在 AFK-Bench 等多樣化基準上持續評估；保留視覺記憶讓模型能學習環境特性；設計容錯機制（如自動重試）

**風險五：評估指標偏誤**
- **問題**：成功率可能掩蓋部分失敗模式（如「接近成功但差一點」），無法反映真實玩家體驗
- **緩解**：加入進度指標（如完成關卡百分比）；分析失敗原因分布；進行人工質性評估

### 與其他技術的整合建議

**與現有代理框架整合**
- AutoPILOT 可作為 VISTA、ReAct 等框架的擴充模組，保留原有的視覺記憶與檢視工具，僅替換動作執行層
- 對於已有代理基礎設施的團隊，建議採用漸進式遷移：先在特定高頻任務上試用閉迴路控制器，再逐步擴展

**與遊戲引擎整合**
- 透過 WebSocket 或 gRPC 將 AutoPILOT 連接至 Unity、Unreal 等遊戲引擎的測試介面
- 利用引擎的 headless 模式進行大規模平行評估

**與 MLOps 平台整合**
- 將模型呼叫、控制器執行、沙箱監控整合至現有的 MLOps 流程（MLflow、Kubeflow 等）
- 使用特徵儲存（feature store）記錄環境狀態與代理決策，便於離線分析

**與成本管理系統整合**
- 串接雲端服務商的成本 API（如 AWS Cost Explorer），即時監控 API 開支
- 設定自動降級機制：當成本接近預算上限時，自動切換至較便宜的模型或減少控制器複雜度

**與人類監督系統整合**
- 設計 human-in-the-loop 介面，讓人類可在關鍵決策點介入
- 記錄代理決策日誌，便於事後審查與除錯

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與 Figure 1，理解 AutoPILOT 解決的核心問題——「為什麼現有代理在即時遊戲中表現不佳」。重點掌握三種執行模式（基本動作、開放迴路巨集、閉迴路控制器）的概念差異，以及「喚醒事件」如何讓模型與控制器分工。不需深入技術細節，先建立「代理框架設計不只是 prompt 工程，也包含動作執行策略」的觀念。

**給 AI 工程師**：重點閱讀 Section 3 的方法描述與 Figure 2 的程式碼範例，特別是閉迴路控制器的 API 設計（`observe()`、`act()`、`request_handoff()`）。建議實際部署 AFK-Bench，在幾款遊戲上重現論文的實驗結果，理解預算配置、推理強度、控制器頻率等超參數的影響。程式碼層面的整合重點在於沙箱安全、視覺記憶管理、與現有代理框架的相容性。

**給研究者**：本論文的核心貢獻在於將「模型輸出如何隨時間轉化為動作」提升為框架設計的一階考量。建議從這個角度重新審視現有的代理框架，思考在機器人控制、強化學習、embodied AI 等領域是否有類似的設計空間。AFK-Bench 的環境分類法（敵意/良性即時、回合制）也是值得參考的評估設計模式，可應用於其他即時互動基準的建構。

**給產品經理**：AutoPILOT 的商業價值在於「以五分之一的成本達到相同成功率」，這對任何依賴多模態模型 API 的產品都有直接意義。建議關注三個面向：(1) 哪些產品場景屬於「即時互動」類型（如即時客服、自動化搶購、遊戲測試），(2) 如何設計使用者介面讓非技術使用者能受益於三種執行模式，(3) 成本節省的具體數字如何轉化為商業提案。論文的 Figure 4d 是與利害關係人溝通時的最佳視覺化素材。
