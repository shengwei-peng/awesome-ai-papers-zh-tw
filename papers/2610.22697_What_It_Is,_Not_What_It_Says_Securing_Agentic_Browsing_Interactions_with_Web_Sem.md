## ⚡ TL;DR

AI代理瀏覽網頁時將內容攤平為文字，喪失網頁語意，使第三方內容可透過提示注入操控LLM代行用戶權限。
本文提出Intact與GenTree，記錄元素來源與語意，逐一傳遞給LLM並依權限執行。
Intact僅讓12.8%攻擊通過（至多為同意請求），遠勝傳統73.1%，僅影響3.7%任務。

## 摘要翻譯

AI 代理日益代表使用者瀏覽網路，然而它們以截圖或文字的形式處理網頁，使其大型語言模型（LLM）暴露於未經審核的第三方內容中。瀏覽器強制實施語意規範，規定元素的功能取決於其本質與來源，而非其內容所述。代理將這些語意扁平化，使注入的文字得以說服大型語言模型，替本無權限的內容行使使用者權限。由於大型語言模型仍易受說服，代理與網路的介面本身必須確保代理所讀取、解讀及執行內容的完整性。我們提出 Intact，其運行於未修改的瀏覽器（unmodified browser）之上。Intact 建構 GenTree，一種擷取來源出處（provenance）與網頁語意（web semantics）的客製化表示法（bespoke representation）。Intact 透過 GenTree 一次將一個元素傳遞給大型語言模型，使模型在不參考其他元素文字的情況下，獨立對每個元素進行決策。其執行框架（harness）僅在該步驟元素（element）的權限（capabilities）範圍內執行操作，並在對第三方內容（third-party content）採取行動前以同意請求（consent request）徵詢使用者。在 1,270 個真實網頁上，GenTree 將第三方元素的歸屬數量提升為瀏覽器的 2.3 倍，而瀏覽器將其中 58.7% 錯誤歸屬（misattribute）於第一方（first-party）。在其中 1,091 個含有注入攻擊的網頁上，僅 12.8% 的攻擊能突破 Intact 的規劃器（planner），且至多僅以同意請求的形式出現，而傳統規劃器（conventional planner）的對應比例則為 73.1%。隔離機制（isolation）僅在 3.7% 的任務（task）上干擾功能（functionality），而平行排程（parallel schedule）可消除其所增加的大部分延遲（latency）。

### 核心貢獻（3～5點）
- **Intact 系統設計**：提出運行於未修改瀏覽器之上的安全代理式瀏覽架構，無需更動瀏覽器核心即可部署。
- **GenTree 表示法**：建構擷取來源出處與網頁語意的客製化資料結構，將第三方元素的歸屬準確率提升為瀏覽器的 2.3 倍。
- **一次一元素決策機制**：使 LLM 在隔離的上下文下獨立判斷每個元素，避免注入文字污染決策依據。
- **權限綁定執行框架**：每個步驟僅在對應元素的權限範圍內執行，並對第三方內容觸發同意請求。
- **實驗驗證**：在 1,091 個含注入攻擊的真實網頁上，攻擊突破率僅 12.8%（相較傳統規劃器的 73.1%），且隔離機制僅干擾 3.7% 的任務功能。

### 適合對象
- **資安研究者**：關注提示注入（prompt injection）、跨站腳本攻擊（XSS）及第三方內容威脅模型的研究人員。
- **AI 代理開發者**：從事代理式瀏覽（agentic browsing）框架（如 Comet、Claude in Chrome、Gemini in Chrome、Browser Use）設計與實作之工程師。
- **瀏覽器與網頁安全工程師**：負責網頁語意、來源出處追蹤及攻擊面（attack surface）評估的專業人員。
- **LLM 應用架構師**：規劃大型語言模型對外介接、已驗證工作階段（authenticated sessions）防護及模型層級防禦（model-level defenses）的技術決策者。

## 深度分析

#### 方法論解析

本文提出的核心方法論圍繞一個關鍵洞見展開：瀏覽器已具備豐富的網頁語意（Web Semantics）強制執行機制，但現有的代理式瀏覽（Agentic Browsing）系統將網頁扁平化為截圖或純文字，徹底丟失了這些語意資訊，從而讓大型語言模型（LLM）暴露於未經審查的第三方內容之下。INTACT 的設計哲學是「元素能做什麼，取決於它是什麼以及來自哪裡，而非它說了什麼」，這與傳統的提示注入（Prompt Injection）防禦思路形成根本對比。

**GenTree 表示法的設計**

GenTree 是一個客製化表示法（Bespoke Representation），為每個 DOM 元素記錄兩類關鍵資訊：（1）來源出處（Provenance），即哪個腳本負責建立或修改該元素；（2）網頁語意，即元素在瀏覽器語意模型中的權限（Capabilities）。這與瀏覽器內建的歸屬機制有本質差異——瀏覽器將第三方腳本在第一方上下文中建立的所有內容都歸屬於第一方，而 GenTree 透過追蹤 DOM 創建與修改的腳本來源，能夠精確標記哪些元素實際上由第三方控制。

**虛擬隔離機制**

INTACT 引入「虛擬隔離」（Virtual Isolation）概念，這是一個巧妙的架構設計：它在未修改的瀏覽器（Unmodified Browser）之上運作，無需改動瀏覽器核心。其核心運作方式是將網頁透過 GenTree 一次一個元素地傳遞給 LLM，使每個元素的決策過程中完全無法看到其他元素的文字內容。這種「資訊流隔離」有效阻斷了跨元素的提示注入攻擊——一個 `<p>` 元素的文字內容無法影響 LLM 對另一個按鈕元素的決策。

**三層完整性保證**

INTACT 的方法論建立在三層完整性之上：
1. **輸入完整性（Input Integrity）**：透過 GenTree 的來源出處追蹤，確保代理讀取內容時知道其真實來源。
2. **處理完整性（Processing Integrity）**：透過虛擬隔離，確保任何元素都不能引導代理做出超出該元素本身權限的行為。
3. **輸出完整性（Output Integrity）**：執行框架（Harness）根據元素的來源、權限、效果與安全邊界控制每個動作；對於頁面無法決定的事項（如使用第三方預訂小工具），則向使用者請求同意（Consent Request）。

這種設計的精妙之處在於：INTACT 不需要識別注入內容是否惡意，也不需要防止代理被說服，而是限制被說服的代理能做的事情。這是一種「縱深防禦」思路，將安全邊界從不可靠的 LLM 判斷轉移到可驗證的網頁語意規則上。

#### 實驗數據解讀

**GenTree 歸屬準確性實驗**

在 1,270 個真實網頁上的測試結果揭示了一個驚人的事實：瀏覽器將 58.7% 的第三方元素錯誤歸屬（Misattribute）為第一方內容，而 GenTree 能夠識別出瀏覽器遺漏的 2.3 倍第三方元素。這意味著現有瀏覽器的歸屬機制在代理式瀏覽場景下存在嚴重的盲點——超過半數的第三方內容被錯誤地標記為可信的第一方內容。這項數據對所有依賴瀏覽器同源策略的代理系統都是一個警訊。

**攻擊防禦效果實驗**

在 1,091 個含有注入攻擊的真實網頁上，INTACT 的規劃器（Planner）僅讓 12.8% 的攻擊通過，且這些通過的攻擊最多只能以同意請求的形式呈現給使用者。相比之下，傳統規劃器（VANILLA）讓 73.1% 的攻擊成功執行。從 73.1% 到 12.8% 的降幅代表了攻擊成功率減少約 82.5%，這是一個極為顯著的安全改進。值得注意的是，即便攻擊通過 INTACT，仍需要使用者主動同意，這將攻擊從「自動化執行」降級為「需要社會工程學」。

**功能保留率實驗**

隔離機制僅在 3.7% 的任務上破壞功能（Functionality），這是一個相當低的數字，證明了虛擬隔離在提供強安全保證的同時，對正常使用情境的影響有限。然而，這 3.7% 的功能損失值得進一步分析——它們是集中在特定類型的任務（如複雜表單填寫、跨框架互動），還是分散在各種任務中？

**延遲效能實驗**

論文提到平行排程（Parallel Schedule）可以顯著降低 INTACT 增加的延遲（Latency），但未提供具體數字。鑑於一次一個元素的處理方式本質上是序列化的，這個延遲開銷在實際部署中可能成為採用障礙。平行化的可行性與效益需要更詳細的評估。

**實驗設計的侷限**

實驗採用了 1,091 個含有注入攻擊的網頁，但這些攻擊的類型分佈、複雜度分級、以及是否涵蓋最先進的攻擊技術（如多輪對話攻擊、視覺提示注入等）需要更詳細的說明。此外，實驗似乎未涵蓋跨網站工作流程（如登入後的多步驟操作），這是代理式瀏覽的典型場景。

#### 與現有研究的比較

**與模型層級防禦的比較**

現有的提示注入防禦主要分為兩類：模型層級防禦（Model-level Defenses）和系統層級防禦。模型層級方法（如額外訓練、提示工程）已被證明只能減少但無法消除攻擊，且 OpenAI 公開承認提示注入「不太可能被完全解決」。INTACT 屬於系統層級方法，其優勢在於不依賴 LLM 的判斷，而是透過架構設計強制執行安全邊界。這與近期研究趨勢一致——學界逐漸認識到 LLM 安全性必須從介面設計著手，而非僅靠模型本身。

**與執行隔離方法的比較**

現有研究中有基於執行隔離（Execution Isolation）的方法（如參考文獻 [30]），以及基於控制流與資料流強制執行（Control- and Data-flow Enforcement）的方法（如參考文獻 [31], [32]）。INTACT 的虛擬隔離與這些方法有相似目標，但實現路徑不同：它不需要修改瀏覽器，而是透過 GenTree 與序列化處理在應用層實現隔離。這種「無修改瀏覽器」的特性大幅降低了部署障礙，但也可能限制其能夠強制執行的安全策略範圍。

**與權限管理方法的比較**

參考文獻 [33] 等基於權限管理（Permission Management）的方法試圖為代理操作引入細粒度權限控制。INTACT 的同意請求機制與此類似，但其決策依據更結構化——基於元素的來源出處與權限，而非全域策略。這使得 INTACT 的決策更具確定性與可審計性。

**改進與侷限**

相較於現有工作，INTACT 的主要改進在於：（1）精確的來源出處追蹤，解決了瀏覽器歸屬盲點；（2）無需修改瀏覽器的虛擬隔離；（3）將使用者意圖與頁面語意明確分離的決策模型。

然而，INTACT 也存在明顯侷限：（1）一次一個元素的處理方式可能無法處理需要跨元素上下文的複雜任務；（2）對於動態載入的內容（如單頁應用程式的非同步更新），GenTree 的更新機制需要進一步驗證；（3）平行排程雖被提及，但具體實作與效益評估尚不充分；（4）實驗主要在靜態網頁上進行，對現代 Web 應用程式框架（如 React、Vue）的支援程度需要更多測試。

#### 可重現性評估

**程式碼與資料釋出**

作者明確表示將在 https://github.com/llm-platform-security/intact 釋出 INTACT 的原始碼與包含 1,091 個真實網頁的攻擊基準測試集。這是可重現性研究的良好實踐，特別是攻擊基準測試集的釋出，對於後續研究建立可比較的評估基準至關重要。

**可重現性的優勢**

- 攻擊基準測試集包含 1,091 個真實網頁，這比合成資料更具代表性
- 開源程式碼允許其他研究者直接驗證實作細節
- 評估指標（攻擊成功率、功能保留率）明確且可重複測量

**可重現性的潛在挑戰**

- 實驗依賴於特定版本的 LLM，不同模型版本可能產生不同結果
- 真實網頁的內容會隨時間變化，基準測試集的「快照」性質可能影響長期可重現性
- 第三方內容的載入涉及網路狀態、地理位置等因素，實驗環境的一致性是挑戰
- 未說明是否釋出預訓練的模型權重或特定提示詞範本

**建議改進**

為了提升可重現性，作者可以考慮：（1）提供基準測試網頁的封存版本（如使用 Web Archive）；（2）記錄實驗時使用的 LLM 版本與提示詞；（3）提供 GenTree 的標準化輸出格式規範，使其他研究者能夠實作相容的系統。

#### 未來研究方向

**GenTree 作為安全基礎設施**

作者將 GenTree 定位為「現有代理防禦的基礎載體」，這是一個極具前景的方向。未來研究可以探索 GenTree 如何整合到不同的防禦框架中：（1）結合執行隔離方法，提供更全面的安全保障；（2）作為控制流與資料流分析的輸入，實現更精細的污點追蹤；（3）支援基於權限管理的細粒度存取控制。

**動態內容與現代 Web 框架**

當前實驗主要針對靜態網頁，未來需要研究 GenTree 如何處理：（1）單頁應用程式（SPA）的動態內容更新；（2）Web Components 與 Shadow DOM 的巢狀結構；（3）WebAssembly 模組的互動；（4）即時通訊（如 WebSocket）場景下的代理行為。

**多模態代理的擴展**

隨著多模態 LLM 的發展，代理開始能夠處理圖像、音訊、影片等內容。未來研究需要擴展 GenTree 以涵蓋：（1）圖像中的視覺提示注入；（2）音訊內容中的隱藏指令；（3）影片中的時序性攻擊。這需要將網頁語意概念擴展到多媒體內容的「能力」與「來源」。

**跨網站工作流程的安全性**

代理式瀏覽的典型場景涉及跨網站操作（如從電子郵件中擷取資訊並填入表單）。未來研究需要探討：（1）跨網站資料流的來源出處如何標記與追蹤；（2）如何在保持隔離的同時支援複雜的多步驟任務；（3）跨網站同意請求的使用者體驗設計。

**效能優化與可擴展性**

平行排程被提及但未深入實作，這是未來的重要研究方向：（1）哪些元素可以安全地平行處理；（2）如何平衡隔離保證與處理速度；（3）GenTree 的增量更新機制以支援大型網頁。

**形式化安全分析**

未來可以對 INTACT 進行形式化安全分析：（1）證明虛擬隔離在特定威脅模型下的安全性；（2）分析 GenTree 歸屬機制的完整性；（3）建立可證明安全的代理瀏覽架構理論。

**使用者體驗與信任校準**

同意請求機制的設計涉及使用者體驗與信任校準的權衡：（1）如何避免「同意疲勞」導致使用者盲目點擊；（2）如何呈現風險資訊以輔助使用者決策；（3）如何學習使用者的偏好以自動化部分決策。

**對抗性攻擊的演進**

隨著 INTACT 等防禦機制的部署，攻擊者會發展對應的對抗技術：（1）利用合法元素組合進行攻擊；（2）透過時間分散攻擊（如在不同頁面載入階段注入）；3）利用代理的記憶體或上下文視窗進行攻擊。這需要持續的紅隊演練與防禦演進。

**標準化與生態系統**

長期來看，GenTree 的概念可能需要標準化以形成生態系統：（1）定義標準化的網頁語意擴展規範；（2）建立跨瀏覽器的相容性測試；（3）推動 W3C 等標準組織採納相關概念。這將使代理式瀏覽安全從學術研究走向產業實踐。

## 論文問答

**Q1：為什麼 AI 代理在瀏覽網頁時會面臨特殊的安全風險？**

A：AI 代理在瀏覽網頁時面臨的根本問題在於，網頁內容並非由單一可信任的來源所控制——研究顯示 92% 的網頁包含第三方內容，而前一千大網站中位數載入 66 個第三方，當第三方又載入更多第三方時，約半數網站會渲染出「網站本身未直接載入」的內容。其次，現有的代理瀏覽器（如 Comet、Claude in Chrome、Gemini in Chrome）與框架（如 Browser Use）將網頁簡化為螢幕截圖或從標記語言衍生的文字，這種「扁平化」處理抹除了瀏覽器原本強制執行的網頁語意——也就是「元素能做什麼取決於它是什麼、來自哪裡，而非它說了什麼」。最後，由於 LLM 已知會遵循內嵌於內容中的指令（即提示注入攻擊），且容易受詐騙影響，攻擊者可透過注入文字說服代理行使使用者權限，導致代理淪為「困惑代理人」(confused deputy)，替沒有權威的內容執行操作。

**Q2：現有的模型層級防禦為何不足以保護 AI 代理？**

A：模型層級防禦（包括各種提示注入防護措施）雖然能降低攻擊成功率，但無法完全消除風險，因為 LLM 在面對精心設計的社會工程式攻擊時仍會被說服。OpenAI 甚至公開承認，提示注入「就像網路上的詐騙和社交工程一樣，不太可能永遠被完全『解決』」。更嚴峻的是，這類攻擊已在實務中發生——Reddit 貼文與留言中的隱藏指令已導致部署中的代理洩漏使用者的一次性登入碼與信用卡號碼，偽造連結也使代理外洩電子郵件與行事曆資料，顯示僅依靠模型本身的判斷力無法建立可信的安全邊界。因此，論文的論點是：安全不能寄託於模型的判斷，而必須由代理與網頁之間的介面本身來確保完整性。

**Q3：為什麼「輸入完整性、處理完整性、輸出完整性」這三個概念對代理安全至關重要？**

A：這三種完整性構成了代理與網頁互動時不可妥協的安全基礎，三者必須同時成立才能確保代理行為的可信賴性。輸入完整性要求代理必須知道其所讀取之每段內容的建立或修改者，這是因為若無法區分第一方與第三方內容，代理就無法判斷哪些文字值得信任。處理完整性要求任何單一元素都不能誘使代理做出該元素本身所不能達成的事，例如一個 `<p>` 元素的文字無論如何說服，都不應導致代理發出網路請求。輸出完整性則要求每個動作及其引發的資料流都必須由使用者請求所正當化、且為網頁安全邊界所允許，這三者缺一不可，因為僅有輸入與處理完整性而無輸出完整性，代理仍可能在被說服後執行超出權限的動作。

**Q4：Intact 系統的核心設計理念是什麼？**

A：Intact 的核心設計理念是「重複利用瀏覽器已強制執行的語意，並以來源出處加以延伸」，而非從頭打造一套新的安全機制。具體而言，Intact 透過 GenTree 這種「逐元素」的網頁表示法來中介代理所讀取、解讀與執行的內容，使每個元素的來源與其在網頁語意下的能力都被明確記錄。這個理念的關鍵在於：瀏覽器已投入大量心力強制執行標記語言的語意，包括元素能力、來源與框架邊界等，而 Intact 並非取代這些機制，而是將其延伸至代理層面，使「元素能做什麼」這個事實不再被其文字內容所覆蓋。這也體現在 Intact 能在「未修改的瀏覽器」上運作的事實上——它不需要改變瀏覽器架構，而是透過虛擬隔離在代理與網頁之間建立額外的安全層。

**Q5：GenTree 表示法的關鍵創新點為何？**

A：GenTree 的關鍵創新在於它是一種「客製化、逐元素」的網頁表示法，能同時擷取每個元素的來源出處（provenance）與其在網頁語意下的能力，這是傳統的螢幕截圖或文字序列化所完全喪失的資訊。在來源出處方面，GenTree 將每個 DOM 的建立與修改歸因到負責的腳本，並對第三方建立或修改的內容加上汙染標記，這比瀏覽器預設的歸因更精確——實驗顯示 GenTree 歸屬到第三方的元素數量是瀏覽器的 2.3 倍，而瀏覽器將其中 58.7% 的第三方元素誤歸於第一方。在語意方面，GenTree 保留了每個元素的類型與能力資訊，使 Intact 的執行框架能在後續步驟中強制執行「該步驟只能在其元素能力範圍內執行」的原則，從而使元素的文字內容無法改變其實際可執行的事項。

**Q6：「虛擬隔離」(Virtual Isolation) 如何在不修改瀏覽器的情況下實現安全性？**

A：虛擬隔離是 Intact 將瀏覽器對標記語言語意的強制執行「延伸」至代理層的關鍵機制，其核心做法是「一次只將一個元素傳遞給 LLM」。這種設計的巧妙之處在於：由於 LLM 在對某個元素做決策時不會看到其他元素的文字，因此任何元素都無法透過其文字內容影響對其他元素的決策，從而杜絕了「一個無害元素的文字說服代理去點擊另一個危險按鈕」這類攻擊。每個由代理衍生的動作都會與其來源元素綁定，而 Intact 的執行框架會根據該元素在網頁語意下的能力來強制執行該動作——例如，一個 `<p>` 元素的文字即使說服代理「按下 submit 按鈕」，該動作也只會在 `<p>` 元素本身的能力範圍內被評估，而不會被允許觸發實際的表單提交。這種隔離完全在代理與瀏覽器之間的介面層實現，因此能在「未修改的瀏覽器」上運作，無需改動瀏覽器架構本身。

**Q7：研究中使用了哪些基準測試來評估 Intact？**

A：本研究的評估基於兩個大規模的真實網頁基準：第一個基準包含 1,270 個真實網頁，用於評估 GenTree 在元素歸屬方面的準確性；第二個基準則從中選取 1,091 個網頁並注入攻擊，用於評估 Intact 與傳統規劃器（稱為 VANILLA）在面對提示注入時的防禦能力。這些基準的規模與真實性是研究可信度的重要基礎——1,270 與 1,091 個網頁的樣本量足以涵蓋多樣化的網頁結構與第三方內容配置，而非僅依賴合成或小規模測試。此外，研究團隊也釋出了這 1,091 個含攻擊的網頁基準與 Intact 的原始碼，以促進後續研究，這體現了學術界對可重現性與基準共享的重視。

**Q8：Intact 在抵禦提示注入攻擊方面的關鍵實驗結果為何？**

A：在 1,091 個含注入攻擊的真實網頁上，Intact 的規劃器僅讓 12.8% 的攻擊通過，而 VANILLA（傳統規劃器）則讓 73.1% 的攻擊通過，差距高達約 5.7 倍。更重要的是，即使這 12.8% 的攻擊通過了 Intact 的規劃器，它們最多也只會以「同意請求」(consent request) 的形式呈現給使用者，由使用者決定是否執行，而非由代理自動執行——這與 VANILLA 直接執行攻擊指令的情況形成鮮明對比。這項結果的意義在於：Intact 並不需要「識別」注入內容是否惡意，也不需要「防止」代理被說服，它只需「限制」被說服的代理能做的事，從而將攻擊的實際危害降至最低。

**Q9：GenTree 在元素歸屬方面的表現如何？**

A：GenTree 在元素歸屬方面展現了顯著優於瀏覽器預設歸因的能力：在 1,270 個真實網頁上，GenTree 歸屬到第三方的元素數量是瀏覽器標準歸因的 2.3 倍。這意味著瀏覽器預設的歸因機制遺漏了大量實際上由第三方建立或修改的元素。更令人警覺的是，瀏覽器將其中 58.7% 的第三方元素「誤歸」於第一方——也就是說，當使用者（或代理）以為自己在與第一方互動時，實際上有超過一半的第三方元素被當作第一方內容處理。這項結果凸顯了 GenTree 的必要性：若沒有精確的來源出處追蹤，後續的處理與輸出完整性檢查都將建立在錯誤的前提之上，因為代理會把第三方內容誤認為可信任的第一方內容。

**Q10：Intact 在實際部署中可能面臨哪些使用者體驗方面的考量？**

A：Intact 在實際部署中需考量三項主要的使用者體驗權衡：首先是同意請求的頻率，由於 Intact 會在使用者任務涉及第三方內容（例如第三方預訂小工具）時向使用者請求同意，這可能增加使用者的決策負擔。其次是功能性的輕微損失——實驗顯示隔離機制僅在 3.7% 的任務上干擾了功能，雖然比例不高，但仍需在設計上考量如何處理這些邊緣情況。最後是延遲問題，由於 Intact 一次只將一個元素傳遞給 LLM 並依序執行步驟，這會增加額外的時間成本；不過研究指出，透過平行排程（parallel schedule）可以顯著降低大部分的延遲開銷，使實際部署成為可行方案。

**Q11：Intact 如何與現有的代理瀏覽器產品（如 Comet、Claude in Chrome、Gemini in Chrome）整合？**

A：Intact 能在「未修改的瀏覽器」上運作的特性，使其與現有代理瀏覽器產品的整合具有高度的可行性——它不需要瀏覽器供應商改動底層架構，而是作為代理與瀏覽器之間的中介層運作。具體而言，Intact 可作為一個外掛或中介服務，攔截代理對網頁內容的存取請求，將其轉換為 GenTree 表示法後再逐元素傳遞給 LLM，並在執行階段根據元素能力與來源出處強制執行動作。這種「外掛式」整合方式降低了部署門檻，使 Comet、Claude in Chrome、Gemini in Chrome 等現有產品能在不重新設計的情況下獲得額外的安全防護層。此外，Intact 的同意請求機制也能與瀏覽器現有的權限管理 UI 結合，為使用者提供一致的決策介面。

**Q12：Intact 對代理安全研究領域的更廣泛影響是什麼？**

A：Intact 對代理安全研究領域的更廣泛影響在於它將 GenTree 定位為「現有代理防禦機制的基礎底層」(substrate)，而非一個獨立的解決方案。論文明確指出，基於執行隔離（execution isolation）、控制流與資料流強制執行（control- and data-flow enforcement）、以及權限管理（permission management）的防禦機制，都預設了「知道哪些輸入是不可信賴的」這個前提，而 GenTree 正好提供了這個前提所需的精確來源出處資訊。這意味著 GenTree 不僅服務於 Intact 自身的虛擬隔離機制，還能為其他研究方向提供可靠的元素級歸屬資料，從而加速整個領域的進展。此外，研究團隊釋出原始碼與 1,091 個網頁的攻擊基準，也為後續研究提供了可重現的實驗基礎，有助於建立統一的評估標準。

**Q13：Intact 的已知限制和權衡為何？**

A：Intact 的已知限制與權衡主要體現在三個面向：第一，功能性干擾——雖然比例僅 3.7%，但隔離機制仍會在少數任務上破壞正常功能，這代表在某些邊緣情況下，嚴格的能力邊界可能過於保守。第二，攻擊無法完全阻擋——12.8% 的攻擊仍會通過 Intact 的規劃器，雖然它們最多只會以同意請求的形式呈現，但這顯示 Intact 並非追求「零攻擊通過率」，而是將攻擊的危害降至最低。第三，延遲成本——一次一個元素的處理方式會增加執行時間，雖然平行排程可顯著緩解，但仍非完全消除。這些權衡反映了 Intact 的設計哲學：在功能性、延遲與安全性之間尋求務實平衡，而非追求任一極端。

**Q14：在哪些情況下 Intact 可能無法有效防禦？**

A：Intact 在以下幾種情況下可能無法完全有效防禦：第一，當攻擊發生在使用者任務「本身就需要」與第三方內容互動時，例如使用者要求代理透過第三方預訂小工具完成預訂，此時 Intact 必須向使用者請求同意，而攻擊者可能透過精心設計的場景誘導使用者同意惡意操作。第二，當攻擊結合了多個元素的資訊時，雖然 Intact 一次只將一個元素傳遞給 LLM，但若使用者同意後續步驟，跨元素的攻擊鏈仍可能形成。第三，當攻擊利用了 Intact 無法從網頁本身推論的「使用者意圖」時，Intact 必須將決定權交還給使用者，這本身也是攻擊面的一部分——社會工程式的同意請求攻擊仍可能繞過 Intact 的技術防禦。這些限制說明了為何 Intact 將自己定位為「限制被說服代理能做的事」而非「完全防止代理被說服」。

**Q15：未來的研究方向有哪些？**

A：基於本研究的成果，未來的研究方向可從三個層面展開：第一，在 GenTree 的應用層面，可將其作為基礎底層，進一步整合執行隔離、控制流與資料流強制執行、以及更精細的權限管理等機制，建立多層次的防禦體系。第二，在效能優化層面，平行排程雖已顯示能顯著降低延遲，但如何進一步最佳化排程策略、減少同意請求的頻率、以及處理更複雜的多步驟任務，仍是值得探索的方向。第三，在攻擊與防禦的演化的博弈上，隨著攻擊者開始針對 GenTree 與 Intact 的特性設計新型攻擊（例如利用同意請求機制的社會工程式攻擊），需要持續發展新的對應防禦機制。此外，將 GenTree 與其他領域（如資訊流追蹤、形式化驗證）結合，也可能是建立更嚴�安全保障的有前景方向。

## 實務應用指南

### 適用場景

1. **金融與醫療等高敏感產業的代理瀏覽部署**：銀行、醫療機構的內部代理需要在其已驗證工作階段中執行轉帳、查詢病歷等操作。INTACT 的來源出處追蹤與第三方內容同意請求機制，可避免 Reddit 留言或網頁中隱藏的提示注入導致一次性登入碼、信用卡號外洩。

2. **企業內部自動化代理（採購、客服、報表彙整）**：企業代理經常需要跨多個供應商網站填寫表單、擷取報價、登入後台。透過 GenTree 的元素級權限控管，可防止第三方廣告或追蹤腳本注入的「假按鈕」誤導代理點擊。

3. **AI 瀏覽器產品的安全強化（Comet、Claude in Chrome、Gemini in Chrome 等）**：這些產品直接將網頁文字或截圖餵入 LLM，是論文點名的攻擊面。將 INTACT 的虛擬隔離層整合進產品，可在不修改瀏覽器核心的前提下，把攻擊成功率從 73.1% 降至 12.8%。

4. **開發者代理框架（Browser Use、LangChain Browser Toolkit 等）的安全中介層**：開源框架通常只做最基本的安全檢查。INTACT 可作為這些框架與瀏覽器之間的中介層，提供標準化的來源出處標記與權限執行框架。

5. **紅隊演練與代理安全基準測試**：論文釋出的 1,091 個真實網頁攻擊基準，可作為企業評估自家代理安全性的標準測試集，用於 CI/CD 中的安全迴歸測試。

### 實作前置條件

**資料需求**
- 真實網頁的 DOM 結構與第三方資源清單（用於建立 GenTree）
- 已知攻擊樣本庫（提示注入、詐騙頁面、惡意彈窗）
- 網站的「第一方／第三方」分類規則集
- 元素的權限對映表（`<a>`、`<form>`、`<button>`、`<iframe>` 等可執行什麼動作）

**運算資源**
- LLM 推理算力：因 INTACT 採「一次一個元素」序列化決策，token 消耗與推理次數會增加，建議準備可批次處理的 LLM API 或本地推論叢集
- 瀏覽器自動化環境（Playwright、Selenium、Puppeteer 等）
- 平行排程所需的額外 worker（論文指出可顯著降低延遲）

**技能需求**
- 熟悉瀏覽器內部機制：DOM、Script Attribution、Same-Origin Policy、跨框架政策
- 具備 LLM 整合經驗：能設計「一次一個元素」的 prompt 流程
- 網頁安全知識：XSS、混淆代理人攻擊（Confused Deputy）、提示注入分類
- 軟體工程能力：能將 GenTree 表示法落地為可維護的資料結構

### 實作步驟建議

1. **盤點現有代理流程並標註風險點**：先記錄代理目前如何讀取網頁（截圖、文字、DOM 序列化），以及哪些任務涉及第三方內容或敏感操作，作為整合 INTACT 的優先順序依據。

2. **建構 GenTree 表示法**：參考論文的設計，為每個 DOM 元素附加來源出處（哪個腳本建立／修改）與語意屬性（元素類型、權限、所在框架的 origin）。論文的實測顯示，瀏覽器原生歸屬會把 58.7% 的第三方元素誤判為第一方，這是必須修正的關鍵。

3. **實作虛擬隔離的 LLM 介面**：將「一次丟整頁」改為「一次一個元素」送入 LLM，並設計 prompt 讓模型只能基於單一元素的資訊做決策。這是處理完整性的核心，必須嚴格避免元素間的文字洩漏。

4. **設計執行框架（Harness）的權限檢查**：每個步驟執行前，根據該步驟對應元素的權限與來源出處進行檢查。若涉及第三方內容且任務需要，則觸發同意請求而非直接執行。

5. **整合使用者同意流程**：在 UI 層加入明確的同意請求介面，告知使用者「此動作將與第三方網域互動」，並提供取消選項。

6. **建立評估管線**：使用論文釋出的 1,091 個攻擊網頁基準，以及自家業務的真實網頁，持續量測攻擊成功率、功能性中斷率（目標 < 5%）、延遲變化。

7. **導入平行排程**：將多個元素的 LLM 決策平行化，以降低「一次一個元素」帶來的延遲成本。論文的初步結果顯示可移除大部分額外延遲。

8. **灰度上線與監控**：先在低風險任務試用，監控同意請求頻率、功能性中斷率、使用者投訴，再逐步擴大到高敏感場景。

### 潛在風險與注意事項

- **功能性中斷（3.7%）**：部分任務仰賴跨元素的文字脈絡（例如閱讀表格後決策），序列化隔離會破壞這些任務。緩解方式：為已知需要跨元素的任務設計白名單，但仍須嚴格限制其權限。

- **同意請求疲勞**：若代理頻繁觸發第三方同意，使用者會習慣性點「同意」，反而削弱防護。緩解方式：批次同意、依網域記憶偏好、只在涉及敏感操作時才請求。

- **攻擊者適應 GenTree**：攻擊者可能改用「合法元素」承載惡意文字（例如在 `<a>` 標籤內藏指令）。緩解方式：結合 LLM 層級防禦與行為監控，不要只依賴單一防線。

- **延遲成本**：序列化決策會增加 LLM 呼叫次數。緩解方式：採用平行排程、快取常見元素的決策結果、對低風險元素使用較小的模型。

- **瀏覽器更新造成的歸屬規則變動**：瀏覽器升級可能改變 Script Attribution 行為，導致 GenTree 的來源出處標記失準。緩解方式：建立回歸測試，鎖定瀏覽器版本或自行實作歸屬邏輯。

- **動態網頁的時序問題**：現代網頁大量使用 JavaScript 動態載入內容，GenTree 必須在正確的時間點擷取快照，否則會遺漏攻擊載荷。緩解方式：設計明確的擷取時機（例如等待網路閒置後），並對 MutationObserver 事件做增量更新。

- **LLM 本身的侷限**：即使介面安全，LLM 仍可能在單一元素內被「說服」。緩解方式：將 INTACT 視為深度防禦的一層，而非唯一防線。

### 與其他技術的整合建議

- **與現有代理框架整合**：INTACT 可作為 Browser Use、LangChain Browser Toolkit、AutoGen 等框架的「瀏覽器中介層」，在不改動框架核心的情況下替換其網頁讀取與動作執行模組。

- **與執行隔離技術整合**：GenTree 提供的元素級來源出處，可作為瀏覽器行程隔離（Site Isolation）、iframe 沙箱等機制的策略依據，實現更細粒度的隔離。

- **與權限管理系統整合**：將 GenTree 的元素權限對映到企業既有的 IAM／DLP 系統，例如「涉及第三方網域的表單提交需經 DLP 掃描」。

- **與 SIEM／審計系統整合**：所有「代理被說服而執行的動作」與「使用者同意請求」都應寫入審計日誌，供事後分析與合規報告使用。

- **與紅隊工具整合**：將 INTACT 與 PromptArmor、AgentDojo 等紅隊框架結合，定期對自家代理做自動化攻擊演練。

- **與瀏覽器擴充功能生態整合**：可考慮以瀏覽器擴充形式部署 INTACT 的 GenTree 建構層，讓使用者無需切換瀏覽器即可獲得保護。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與第 1 節，理解「為什麼代理瀏覽有危險」這個核心問題——瀏覽器原本用「元素是什麼、來自哪裡」來決定它能做什麼，但代理只看「它說了什麼」，於是攻擊者可以用文字說服代理做危險的事。接著看 GenTree 的概念圖，理解「每個元素附上來源標籤」這個比喻即可，暫時跳過實作細節。

**給 AI 工程師**：重點放在第 2、3 節的 GenTree 設計與「一次一個元素」的 LLM 介面。思考如何把這個模式套用到你現有的代理框架：你的 prompt 流程是否允許跨元素文字洩漏？你的動作執行器是否檢查了元素的權限與來源？論文釋出的程式碼與基準是很好的起點。

**給研究者**：第 4 節的評估方法是精華——1,091 個真實網頁、攻擊成功率對比、功能性中斷率、延遲分析。建議追蹤 GenTree 作為「代理安全基底」這個研究方向，思考如何與控制流／資料流強制執行、執行隔離、權限管理等其他防禦路線結合。論末提到的「GenTree as a substrate」是值得延伸的開放問題。

**給產品經理**：把 INTACT 視為「在不改變使用者瀏覽器的前提下，把代理瀏覽的安全性從 73% 漏洞率降到 13%」的方案。關鍵取捨是：3.7% 的功能性中斷 vs 大幅降低的安全風險，以及同意請求對使用者體驗的影響。建議在產品路線圖中將「代理安全」列為與「模型能力」同等重要的投資項目，並以論文基準作為評估自家產品的標準。
