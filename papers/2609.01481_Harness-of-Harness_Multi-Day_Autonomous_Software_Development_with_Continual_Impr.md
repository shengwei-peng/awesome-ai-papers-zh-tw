## ⚡ TL;DR

現有LLM編碼代理難以在長期自主開發中持續改進，容易陷入局部修復與軌跡失控。
提出HoH框架，在現有harness上建立規劃–編碼–測試迭代迴圈，以小增量與獨立評估維持持續改進。

## 摘要翻譯

本文研究自主軟體開發，其中基於 LLM 的程式設計代理能夠在無人類介入的情況下，將高階需求轉化為完整、可運作且可用的軟體系統。我們提出 Harness-of-Harness（HoH），一個讓程式設計代理在自主開發過程中持續改進軟體的框架。HoH 疊加於現有的程式設計代理執行框架之上，並將其執行過程組織為迭代式的規劃–編碼–測試迴圈。為了在各次迴圈之間維持改進，HoH 在修復與能力成長之間取得平衡，將開發範圍劃分為小型且可驗證的增量，把實作階段的測試與獨立評估分離，並約束可驗證的輸出，而非規定代理的工作流程。它逐步開放交付成果、角色專屬工具與技能，鼓勵複用而非重新建立，並維護版本化的專案歷史。在 GameCraft-Bench、FrontierSWE 與 ProgramBench 上，針對三組執行框架–模型配對（Codex 搭配 GPT-5.5、OpenCode 搭配 DeepSeek-V4-Pro，以及 Pi 搭配 MiniMax-M3），HoH 始終優於對應的獨立執行框架，在三輪迭代後達到平均相對增益 52.25%、最高增益 82.86%。在一項為期多日、超過 70 輪迭代的部署中，HoH 自主開發了一款第一人稱射擊遊戲，具備連貫的故事情節、完整實作的核心機制、可供人類遊玩的體驗、精緻視覺效果，以及整合式音效。

### 核心貢獻（3～5點）
- 提出 Harness-of-Harness（HoH）框架，使基於 LLM 的程式設計代理能在自主開發過程中持續改進軟體。
- 將程式設計代理執行框架的執行過程組織為迭代式的規劃–編碼–測試迴圈，並透過平衡修復與能力成長、分離測試與獨立評估等設計原則維持長期改進。
- 在 GameCraft-Bench、FrontierSWE 與 ProgramBench 三個基準測試上，相較於獨立執行框架達到平均 52.25%、最高 82.86% 的相對增益。
- 展示多日自主開發能力：在超過 70 輪迭代中自主完成一款具備連貫劇情、完整核心機制、精緻視覺與整合音效的第一人稱射擊遊戲。

### 適合對象
本論文適合對自主軟體開發、LLM 程式設計代理、軟體工程自動化與長期規劃問題有興趣的研究人員與工程師閱讀，特別是關注如何讓代理在多日、多輪迭代中持續改進大型軟體系統的讀者。

## 深度分析

#### 方法論解析

本論文提出的 **Harness-of-Harness（HoH）** 並非要取代現有的 **coding-agent harness（程式設計代理執行框架）**，而是在其上疊加一層「執行框架的執行框架」，將原本單次或人在迴路（human-in-the-loop）的開發流程，重新組織成反覆運作的 **planning–coding–testing loop（規劃–編碼–測試迴圈）**。其核心設計可從以下六個層面理解：

1. **角色分離與閉環證據鏈**  
   HoH 在每次迭代中配置三個角色：**planner（規劃器）**、**developer（開發者）** 與 **QA tester（品質保證測試者）**。planner 根據 **high-level requirement（高階需求）** 與前一次迭代產生的結構化測試報告，產出一份 **development plan（開發計畫）**；developer 執行該計畫並在實作過程中嵌入聚焦測試；QA tester 則在開發者測試通過後，獨立從功能正確性、完整性、可用性、視覺與音效品質等多個視角進行 **white-box test（白箱測試）** 與 **black-box test（黑箱測試）**，並將結果回傳給 planner。這種分離避免了「運動員兼裁判」的偏差，也讓每次迭代都有可檢驗的證據驅動下一步。

2. **修復與能力成長的平衡**  
   每份開發計畫必須同時處理尚未解決的問題，並交付一個「小而具體」的新能力。這對應到 **iterative and incremental development（迭代與增量式開發）** 原則：一方面防止代理陷入無止境的 **local fix（局部修復）** 迴圈，另一方面透過小範圍增量降低變更風險，使進度更容易驗證。

3. **實作時測試與獨立評估的分離**  
   developer 在實作階段進行的是即時、聚焦的 **implementation-time testing（實作時測試）**，用於快速回饋局部修改；QA tester 則進行獨立、互補的整體評估。這種雙層測試架構可減少 **premature declaration of completion（過早宣告完成）** 與 **redundant verification（冗餘驗證）** 的問題。

4. **以產出物與結構化證據約束，而非規範工作流程**  
   HoH 只規定每個角色必須回傳符合特定 schema 的 **deliverable（交付成果）**，例如開發計畫、測試報告、版本紀錄等；若輸出違反 schema 則觸發重試。這種做法在「可驗證產出」與「代理自主性」之間取得平衡：代理仍可自由決定推理路徑、工具使用與實作策略，但最終結果必須可被後續角色與外部系統檢查。

5. **漸進式揭露與工具／技能管理**  
   為了避免長 **trajectory（執行軌跡）** 撐爆上下文視窗，HoH 採用 **progressive disclosure（漸進式揭露）**：計畫、報告、歷史紀錄等持續化儲存於檔案系統，先透過簡潔的分類索引呈現，只在需要時檢索詳細內容。此外，工具（如 MCP servers、專家模型、領域演算法）按角色組織，並以輕量的 Markdown-based **skill（技能）** 提供隨選指引；代理會被鼓勵 **reuse（複用）** 既有資源而非重新建立標準能力，以降低例行工程負擔。

6. **版本化專案歷史與回滾機制**  
   HoH 在代理角色層級與迭代層級都維護 **versioned project history（版本化專案歷史）**，不僅保存軟體狀態，也記錄變更摘要。這使得系統在遭遇重大迴歸時能回到先前已驗證狀態，也能在類似失敗再次發生時引用過去證據進行診斷與解決。

在多日遊戲開發部署中，HoH 進一步引入角色專屬工具與技能，支援開發引擎互動、資產取得與生成、參考檢索、測試與專案狀態管理，並將每個代理階段的程式碼與產出物提交至公開 GitHub 倉庫，使完整開發軌跡可被追蹤。

#### 實驗數據解讀

論文在兩種互補情境下進行評估：三個受控 **benchmark（基準測試）** 與一個開放式多日遊戲開發案例。

**受控基準測試結果**  
測試涵蓋 **GameCraft-Bench**、**FrontierSWE** 與 **ProgramBench**，並使用三組 **harness–model pair（執行框架–模型配對）**：Codex 搭配 **GPT-5.5**、OpenCode 搭配 **DeepSeek-V4-Pro**，以及 Pi 搭配 **MiniMax-M3**。在僅使用 HoH 迴圈、未額外加入工具、技能或版本控制機制的條件下，HoH 相較於對應的 **standalone harness（獨立執行框架）** 均穩定提升：

- **GameCraft-Bench**：三次迭代後絕對分數提升 16.62–22.08 分；
- **FrontierSWE**：三次迭代後絕對分數提升 19–29 分；
- **ProgramBench**：三次迭代後絕對分數提升 6.09–16.85 分。

整體平均 **relative gain（相對增益）** 達 52.25%，最高達 82.86%。這些數據有幾點值得注意：

1. **跨模型與跨框架的一致性**：三組配對在三大基準上皆呈現正向增益，顯示 HoH 的效益並非來自單一強大模型，而是來自於「規劃–編碼–測試」閉環對長期開發軌跡的結構化作用。  
2. **持續改進而非一次性跳躍**：在 FrontierSWE 上，Codex 搭配 GPT-5.5 的組合在十次迭代中從 22% 持續提升至 72.67%，說明 HoH 確實能支援 **continual improvement（持續改進）**，而非僅在前幾次迭代有效。  
3. **不同基準的增益幅度差異**：ProgramBench 的絕對增益相對較小，可能與其評分粒度或任務性質有關；GameCraft-Bench 與 FrontierSWE 的增益較大，暗示計畫–測試迴圈對於具有明確可驗證行為的遊戲機制與軟體工程任務特別有效。

**開放式多日遊戲開發案例**  
在超過 70 次迭代的多日部署中，HoH 僅憑高階產品需求就自主開發出第一人稱射擊遊戲，具備連貫劇情、完整核心機制、可供人類遊玩的體驗、精緻視覺效果與整合式音效。這個案例的價值在於展示傳統基準難以衡量的開放式創作能力，例如一致性敘事、美術風格統一與長期架構演化。然而，該案例屬於質性展示，缺乏客觀量化指標，且僅為單一專案，無法直接推論到其他領域。

#### 與現有研究的比較

**定位**  
既有研究大多聚焦於單一 **coding agent（程式設計代理）** 的能力強化，例如 **function completion（函式補全）**、**repository-level issue（儲存庫層級問題）** 修復，或透過 **prompting（提示工程）**、**external memory（外部記憶體）**、**ReAct**、多代理協作（如 GPTSwarm）與 harness 自動合成（如 AutoHarness）來優化代理表現。相較之下，HoH 選擇在現有 harness 之上建立一層元執行框架，將重點從「單次任務執行」轉移到「長期自主開發中的持續改進」。

**主要改進**  
- **長期一致性**：透過 planner 持續綜合需求與歷史測試證據，減少代理在長軌跡中遺漏早期設計決策或 **constraint（約束）** 的問題。  
- **獨立評估機制**：相較於許多系統僅依賴開發者自我測試，HoH 引入獨立 QA tester，降低過早宣告完成的風險。  
- **產出物導向的約束**：以 schema 約束交付成果，而非規定代理內部推理流程，兼顧可驗證性與自主性。  
- **漸進式揭露與版本控制**：在無專用記憶模組的情況下，透過檔案系統持續化與分類索引維持連續性；版本化歷史則提供回滾與經驗複用能力。  
- **複用導向**：鼓勵代理使用既有資源與技能，減少重複造輪子。

**限制**  
- **對底層 harness 與模型的依賴**：HoH 的表現上限仍受制於所包裹的 coding-agent harness 與 LLM 能力；若底層代理無法理解計畫或執行測試，閉環難以運作。  
- **開銷**：schema 檢查、重試、獨立測試與版本控制都會增加 token 消耗與執行時間，多日部署的成本相當可觀。  
- **無專用記憶模組的潛在瓶頸**：progressive disclosure 雖節省上下文，但在極長專案中，跨迭代關聯推理可能不如顯式記憶模組靈活。  
- **評估侷限**：現有基準仍偏向可驗證的短中期任務；開放式遊戲案例雖具說服力，但缺乏客觀指標，且僅有一例。  
- **安全與對齊**：完全無人介入的自主開發可能產生難以預測的行為、錯誤或不符合規範的程式碼，論文對此著墨較少。  
- **測試報告過擬合風險**：若 planner 過度針對測試報告中的顯性項目進行優化，可能忽略未被測試覆蓋的隱性需求。

#### 可重現性評估

論文提供了 **GitHub** 倉庫與專案頁面，並在多日遊戲開發案例中將每次代理階段的程式碼變更與角色產出物提交至公開倉庫，這對於追蹤完整開發軌跡非常有幫助。三大基準測試（GameCraft-Bench、FrontierSWE、ProgramBench）亦為公開資料集，理論上可供他人重跑。

然而，可重現性仍面臨以下挑戰：

- **模型與 harness 的封閉性**：GPT-5.5、DeepSeek-V4-Pro、MiniMax-M3 均為商業或雲端模型，Codex、OpenCode、Pi 等 harness 也可能需要特定 API 權限或內部設定，完整復現需取得對應服務存取權。  
- **超參數與提示細節**：雖然倉庫可能包含 skill、schema 與部分提示，但實際執行時的溫度、重試次數、上下文裁剪策略、工具呼叫順序等細節，可能影響重現結果。  
- **成本與時間**：多日部署涉及 70 次以上迭代，每次迭代包含規劃、實作、多輪測試與版本提交，復現所需運算與 API 費用極高。  
- **無開放模型權重**：論文未釋出任何模型權重，僅提供框架與軌跡 artifacts。

綜合而言，HoH 在「框架程式碼」與「開發軌跡」層面具備高度開放性，但在「端到端數值復現」層面受限於商業 API 與 harness 配置，屬於部分可重現。

#### 未來研究方向

1. **專用記憶模組與漸進式揭露的權衡**  
   可進一步比較 progressive disclosure 與顯式外部記憶體在超長專案中的效果，探索混合式記憶架構。

2. **從版本化歷史中學習**  
   目前版本紀錄主要用於回滾與參考；未來可發展基於案例的推理（case-based reasoning），讓 planner 自動識別重複出現的失敗模式並套用過去解決方案。

3. **自動化技能庫的演化**  
   現有 skill 為靜態 Markdown 指引。未來可讓系統在開發過程中自動發現、抽象並累積可複用技能，形成持續成長的領域知識庫。

4. **動態增量範圍調整**  
   目前計畫強調「小而具體」的增量，但未來可研究如何根據模型能力、任務難度與剩餘預算動態調整每次迭代的範圍。

5. **擴展至非遊戲領域**  
   將 HoH 應用於網頁應用、分散式系統、資料庫遷移或嵌入式軟體等領域，驗證其通用性。

6. **整合形式化驗證與更強的測試生成**  
   在關鍵模組引入形式化方法或符號執行，提升對安全性與正確性的保證。

7. **多代理辯論與共識機制**  
   除了 planner–developer–tester 三角，可引入更多專家角色或辯論機制，以減少單一代理的偏誤。

8. **人機協作的安全閘門**  
   研究在完全自主與完全人在迴路之間的漸進式監督機制，例如在高風險變更時請求人類確認。

9. **開放式軟體品質的客觀評估指標**  
   建立能衡量長期自主開發中「一致性」、「可維護性」、「使用者體驗」與「架構品質」的標準化指標。

10. **成本效率與可持續性**  
    分析迭代次數、模型選擇與測試深度之間的取捨，發展在有限預算下最大化進度的策略。

## 論文問答

**Q1：什麼是「自主軟體開發」，它與傳統「人在迴路」的程式設計代理有何不同？**
A：自主軟體開發是指僅以高階需求作為人類輸入，由基於 LLM 的程式設計代理從零開始獨立完成完整、可運作且可部署的軟體系統，過程中不再需要人類指導或介入。相對地，傳統「人在迴路」模式要求開發者定義任務、引導中間決策、審查生成程式碼，並在失敗時出手干預。這使得自主軟體開發不只是一種自動化輔助，而是一個必須同時處理規劃、協調、整合與驗證的長期規劃問題。

**Q2：當開發軌跡變長時，會出現哪些根本性挑戰？**
A：隨著執行軌跡增長，代理可能逐漸遺忘早期需求與設計決策，或在局部修復時違反其他元件的約束。失敗嘗試與次佳決策會不斷累積，而測試產生的新證據也可能推翻先前的假設，導致重複檢修、冗餘驗證，甚至過早宣告完成。這些問題顯示，自主軟體開發的難題不在於單純延長執行時間，而在於如何在長時間內維持連貫且有效的進展。

**Q3：為什麼自主軟體開發不能僅靠放大現有程式設計代理的規模來解決？**
A：從無到有建構系統需要代理將高階需求轉譯為可執行計畫、協調相互依賴的任務、設計與整合元件，並持續測試與除錯不斷演化的系統。現有代理大多仍聚焦於函式補全或儲存庫層級問題，並在人在迴路的設定下運作，缺乏長期自主推進的能力。因此，必須在執行框架層面引入持續改進機制，才能支撐多輪迭代後仍保持正確性與一致性。

**Q4：Harness-of-Harness（HoH）是什麼？它與現有 coding-agent harness 的關係為何？**
A：HoH 是一個疊加於現有程式設計代理執行框架之上的多層次框架，旨在賦予 coding agent 持續改進的能力以進行自主軟體開發。它並非取代原有 harness，而是將其執行組織成迭代式的規劃–編碼–測試迴圈，透過更高層次的協調來放大底層 harness 的效能。換言之，HoH 是「執行框架的執行框架」，在保留既有工具與環境介面的同時，引入長期開發所需的結構化流程。

**Q5：HoH 透過哪些核心設計原則來維持跨迴圈的持續改進？**
A：HoH 同時平衡缺陷修復與能力成長，並將開發範圍切分為小型且可驗證的增量，以降低變更風險。它區分實作階段的測試與獨立評估，透過互補的白箱與黑箱測試從功能正確性、完整性、可用性、視覺與音效等多元視角檢驗系統。此外，HoH 約束可驗證的交付成果而非規定代理的工作流程，並採用漸進式揭露、角色專屬工具與技能、鼓勵複用，以及版本化專案歷史來維持連續性。

**Q6：HoH 如何在確保結構化產出的同時，保留代理的自主性？**
A：HoH 要求每個角色回傳符合特定結構的交付成果，若輸出違反所需格式則會觸發重試，從而約束可驗證的結果。然而，它並不強制規定代理必須如何推理、使用工具或實作程式碼，因此代理仍保有在實作策略與細節上的自主空間。這種「管產出、不管過程」的設計讓系統既能被檢驗，又能充分利用 LLM 的靈活性與創造力。

**Q7：論文在哪些基準測試與代理–模型組合上評估了 HoH？**
A：論文選用了 GameCraft-Bench、FrontierSWE 與 ProgramBench 三個基準測試，涵蓋遊戲開發、軟體工程與程式設計等不同面向。實驗考慮了三組 harness–model 配置：Codex 搭配 GPT-5.5（high）、OpenCode 搭配 DeepSeek-V4-Pro，以及 Pi 搭配 MiniMax-M3。這樣的組合能檢驗 HoH 在不同底層代理與模型上的通用性與穩定性。

**Q8：HoH 相較於獨立執行框架取得了哪些關鍵量化結果？**
A：在三個基準測試上，HoH 在三輪迭代後平均相對增益達到 52.25%，最高相對增益為 82.86%，並且在所有配置下都穩定優於對應的 standalone harness。絕對分數方面，GameCraft-Bench 提升 16.62–22.08 分，FrontierSWE 提升 19–29 分，ProgramBench 提升 6.09–16.85 分。在 FrontierSWE 上，Codex 搭配 GPT-5.5（high）經過十輪迭代後，表現從 22% 持續提升至 72.67%，顯示出長期改進的潛力。

**Q9：多天的開放式遊戲開發展示補足了基準測試無法呈現的哪些面向？**
A：開放式遊戲開發涉及資產取得與生成、開發引擎互動、參考檢索、專案狀態管理等真實挑戰，這些問題在傳統基準測試中較少出現。在這個設定中，HoH 啟用了角色專屬工具與技能，並將每次代理階段的程式碼變更與產出提交到公開 GitHub 儲存庫，使完整開發軌跡可被追溯。經過超過 70 輪迭代，HoH 自主完成了一款第一人稱射擊遊戲，具備連貫故事情節、完整核心機制、可供人類遊玩的體驗、精緻視覺效果與整合式音效。

**Q10：HoH 在哪些實務場景中最具應用價值？**
A：HoH 特別適合從高階產品需求快速產出可運作原型或最小可行產品的場景，例如獨立遊戲開發、內部工具建置，以及需要反覆試驗的實驗性專案。由於它能夠在多輪迭代中持續修復與擴充功能，因此可以減少開發者持續介入的成本。對於希望將創意快速轉化為可玩、可測試軟體的團隊而言，HoH 提供了一種新的自動化開發範式。

**Q11：在真實組織中部署 HoH 時，需要考慮哪些產品與工程議題？**
A：長時間自主執行會帶來顯著的 API 呼叫成本與延遲，因此需要評估經濟可行性與運算資源配置。此外，自動生成的程式碼與資產可能涉及授權、安全性漏洞或品質不一致等風險，組織應建立審查閘道與持續整合流程。版本化專案歷史雖有助於追溯，但仍需搭配人類最終審核、部署授權與合規檢查，才能安全地融入既有軟體工程實務。

**Q12：HoH 可能對 LLM 軟體工程研究與實務產生什麼影響？**
A：HoH 將研究焦點從單輪程式碼生成或局部任務輔助，轉向長期、端到端的系統建構能力。它證明了在執行框架層次進行編排、結構化交付成果、漸進式資訊揭露與鼓勵複用，能顯著提升多輪開發的成效。未來的實務與基準測試可能會更重視代理從需求到可部署產品的完整自主開發能力，而非僅衡量單一程式片段的正確性。

**Q13：論文已指出或暗示了 HoH 的哪些限制？**
A：目前評估主要集中於三個基準測試與一個開放式遊戲專案，對於其他領域、程式語言或大型企業級系統的泛化能力仍有待驗證。HoH 的表現高度依賴底層 harness 與 LLM 的能力，若基礎模型在推理或工具使用上存在瓶頸，上層框架也難以完全彌補。此外，多天執行所帶來的成本、延遲與潛在錯誤累積，都是實際應用前必須審慎評估的限制。

**Q14：在多天自主開發過程中，可能出現哪些失敗模式或風險？**
A：隨著迭代次數增加，錯誤可能不斷累積，導致架構漂移或難以修復的迴歸問題。代理也可能過度擬合測試案例，忽略隱含需求或非功能性需求，例如安全性、效能與可維護性。此外，自動取得或生成的資產與程式碼可能涉及授權爭議，而長上下文管理即使採用漸進式揭露，仍可能在極長軌跡下面臨資訊遺失的風險。

**Q15：未來可以從哪些方向進一步擴展 HoH？**
A：未來可引入更強大的記憶與檢索機制，或讓規劃器透過學習歷史計畫與回饋來提升長期規劃品質。結合人類回饋、多代理專業分工，以及形式化驗證技術，也有助於提高系統的正確性與安全性。此外，建立領域專屬技能庫、自動化部署與運維監控，並針對更大規模的團隊協作與程式碼庫進行擴展，都是值得探索的後續方向。

## 實務應用指南

### 適用場景

1. **獨立遊戲原型與完整遊戲開發**  
   當團隊只有一份高階遊戲設計文件（類型、核心機制、美術風格、音效需求）時，可利用 HoH 的規劃–編碼–測試迴圈，從零開始迭代產出可遊玩的原型，並在數十個迭代後擴展為具備完整劇情、視覺與音效的遊戲。

2. **內部工具與自動化系統的快速建置**  
   例如需要一套「自動彙整多來源報表並產出視覺化儀表板」的內部服務時，HoH 可將高階需求轉為可執行計畫，逐步實作資料擷取、處理、前端介面與測試，並持續根據獨立測試報告修正。

3. **新創產品 MVP（最小可行產品）開發**  
   在資源有限的情況下，產品經理可用自然語言描述使用者故事與驗收條件，由 HoH 自主產出前後端程式碼、資料庫結構與部署設定，並透過迭代補齊遺漏功能。

4. **程式設計教育與自動化回饋系統**  
   教師可將課程專案需求輸入 HoH，讓代理在每次迭代中產出程式碼、測試與結構化報告，作為學生參考範例，或反向檢查學生作業是否符合規格。

5. **遺留系統重構與現代化**  
   面對長期累積、文件不足的舊系統，可將「重構目標與驗收準則」作為高階需求，由 HoH 分階段重寫模組、補上測試並持續驗證，避免一次性大規模改動造成的迴歸風險。

### 實作前置條件

**資料與規格**
- 一份清晰的高階需求文件，包含功能、非功能需求、驗收準則與限制條件。
- 若為既有專案，需提供可執行的基礎程式碼、儲存庫結構與相依套件清單。
- 預先定義各角色（planner、developer、tester）必須回傳的結構化交付成果 schema。
- 測試資料、範例輸入／輸出，以及（若適用）美術、音效等資產描述或授權來源。

**運算資源**
- 可呼叫的 LLM API 或本地部署模型，建議至少準備一個強大的通用模型（如 GPT-5.5、DeepSeek-V4-Pro 等級）作為規劃與開發主力。
- 可長時間執行的運算環境（容器、虛擬機或具備自動重啟機制的 CI runner），因多輪迭代可能持續數小時至數天。
- 足夠的檔案系統空間與版本控制儲存庫，用於保存每次迭代的程式碼、計畫、測試報告與專案歷史。

**技能與團隊準備**
- 熟悉基礎 harness（如 Codex、OpenCode、Pi）的設定與工具呼叫方式。
- 具備提示工程、結構化輸出驗證與錯誤重試機制的實作經驗。
- 了解軟體測試（單元測試、整合測試、白盒／黑盒測試）與版本控制流程。
- 能夠設計輕量 Markdown-based skills，並視需要整合 MCP servers、專家模型或領域演算法。

---

### 實作步驟建議

1. **選擇並封裝基礎 harness**  
   根據專案特性選定 coding agent（Codex、OpenCode、Pi 等），確認其原生工具與環境介面，再將 HoH 的規劃–編碼–測試迴圈疊加於其上。

2. **定義結構化交付 schema**  
   為 planner、developer、tester 分別設計強制輸出格式，例如開發計畫必須包含「本次增量目標」「相依風險」「驗收方式」；測試報告必須包含「功能正確性」「完整性」「可用性」等欄位。輸出不符合 schema 時自動重試。

3. **建立專案環境與版本控制**  
   初始化儲存庫，設定自動提交機制，讓每個角色階段結束後都留下可追蹤的 commit，並保留計畫、報告與程式碼的對應關係。

4. **準備高階需求與驗收準則**  
   將需求拆解為可驗證的陳述，並建立初始測試集。避免過於籠統的描述，讓 tester 在獨立評估時有明確依據。

5. **配置角色專屬工具與 skills**  
   為 developer 提供開發引擎互動、資產取得、參考檢索等工具；為 tester 提供白盒與黑盒測試工具。以 Markdown skills 提供簡潔、隨選的使用指引，鼓勵複用而非重新建立。

6. **啟動迭代迴圈**  
   每一輪由 planner 綜合需求與上一輪測試報告產出小範圍開發計畫；developer 執行計畫並在實作中嵌入測試；通過後再由 tester 獨立評估整體系統。

7. **實作漸進式歷史揭露**  
   將計畫、報告與歷史紀錄存放於檔案系統，透過分類索引讓代理快速定位相關內容，只在需要時載入詳細內容，避免上下文視窗超載。

8. **監控迴歸與狀態復原**  
   利用版本化專案歷史，在發現重大迴歸時回退至先前驗證過的狀態，並讓 planner 參考過去類似失敗的證據來診斷與解決。

9. **收斂與人工閘門**  
   設定迭代次數上限或預算上限，並在關鍵里程碑安排人工審查最終交付成果，確認符合產品目標後再部署。

### 潛在風險與注意事項

| 風險 | 說明 | 因應方式 |
|---|---|---|
| **上下文視窗超載** | 長期開發累積大量歷史，導致模型遺漏早期需求。 | 採用漸進揭露機制，僅載入相關摘要；定期由 planner 重新整理需求與設計決策。 |
| **局部修復引發迴歸** | 為解決當前錯誤而修改程式碼，反而破壞其他功能。 | 堅持小增量開發，並由 tester 執行獨立黑盒測試與整合測試。 |
| **過早宣告完成** | 代理在功能尚未完整時即認定任務結束。 | 要求 tester 對照整體需求與計畫進行結構化評估，並將報告強制回饋給 planner。 |
| **schema 違規與無效輸出** | 角色輸出未依規定格式的內容，導致下游無法解析。 | 實作嚴格的 schema 驗證與自動重試，必要時加入範例提示。 |
| **重複造輪子** | 代理傾向重新實作標準功能，浪費 token 與時間。 | 建立可複用元件庫與 skills，並在提示中明確鼓勵複用。 |
| **成本與時間膨脹** | 多輪迭代與多角色呼叫可能產生高額費用。 | 設定迭代次數、token 用量與執行時間上限；在關鍵節點加入人工決策。 |
| **資產授權與安全風險** | 自動產生或下載的圖片、音效、套件可能涉及授權或漏洞。 | 建立資產來源審查流程，使用可信賴套件來源，並對生成內容進行授權檢查。 |
| **幻覺測試或虛假通過** | 代理可能宣稱測試通過，但實際未執行或測試本身有誤。 | 要求 tester 產出可重現的測試指令與實際執行紀錄，並由獨立環境驗證。 |

### 與其他技術的整合建議

- **版本控制系統（Git）**：將 HoH 的每次角色階段與迭代結果自動 commit，並標註對應的計畫與測試報告，讓完整開發軌跡可追溯。
- **CI/CD 管線**：把 tester 的黑盒測試與部署步驟串接到 CI/CD，讓通過獨立評估的程式碼自動觸發建置、部署或發布預覽環境。
- **MCP Servers 與專家模型**：透過 MCP 提供檔案系統、瀏覽器、資料庫等工具；針對特定領域（如遊戲物理、資安掃描）接入專家模型，提升測試深度。
- **問題追蹤與專案管理工具**：將每輪測試報告中的未解問題同步到 issue tracker，方便人類團隊在必要時介入。
- **可觀測性與日誌平台**：記錄每次迭代的規劃內容、工具呼叫、測試結果與成本，便於後續分析瓶頸與優化提示。
- **資產管線**：對於需要美術、音效的專案，整合自動化資產生成與管理流程，並確保生成內容符合授權與風格規範。
- **模型路由與成本管理**：根據任務難度動態選擇模型（例如規劃使用高階模型、重複性測試使用較輕量模型），以平衡效能與成本。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦在「自主軟體開發」與「人在迴路」的差別，理解 HoH 如何透過規劃–編碼–測試迴圈讓代理持續改進。可以先從 GameCraft-Bench 的遊戲開發案例著手，觀察高階需求如何一步步變成可執行程式碼，再回頭看技術細節。

**AI 工程師**：重點關注 HoH 的架構設計，包括結構化交付 schema、漸進式歷史揭露、角色專屬工具與 skills 的整合方式，以及如何利用版本化專案歷史處理迴歸。建議對照你目前使用的 harness（如 Codex、OpenCode）思考如何疊加 HoH 迴圈。

**研究人員**：可深入分析 HoH 在長期規劃問題上的設計原則，例如「平衡修復與能力成長」「小範圍可驗證增量」「實作中測試與獨立評估分離」等機制，並評估其在不同基準測試（GameCraft-Bench、FrontierSWE、ProgramBench）上的增益來源與泛化性。

**產品經理**：請將 HoH 視為一種「需求驅動的自主交付流程」。重點理解它能降低哪些重複性工程成本、在哪些場景下仍需人工閘門，以及如何透過高階需求與驗收準則的設計來引導代理產出符合商業目標的產品。
