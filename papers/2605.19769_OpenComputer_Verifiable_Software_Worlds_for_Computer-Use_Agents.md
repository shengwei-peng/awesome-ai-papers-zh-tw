## ⚡ TL;DR

現有電腦使用代理程式的桌面環境建構與狀態驗證難以大規模擴展，且 LLM 評審不可靠。
本文提出 OpenComputer，以驗證器為核心自動生成可驗證的桌面任務與評估環境。
實驗顯示驗證器評估比 LLM 評審更接近人工判定，且現有代理在端對端桌面任務上仍難以穩健完成。

## 摘要翻譯

我們提出 OpenComputer，一個以驗證器為基礎的框架（verifier-grounded framework），用於為電腦使用代理程式（computer-use agents）建構可驗證的軟體世界（verifiable software worlds）。OpenComputer 整合四個元件：（1）應用程式專屬狀態驗證器（app-specific state verifiers），針對真實應用程式公開結構化檢查端點（structured inspection endpoints）；（2）自我演進驗證層（self-evolving verification layer），利用以執行為基礎的回饋（execution-grounded feedback）提升驗證器可靠性；（3）任務生成管線（task-generation pipeline），合成真實且機器可檢查的桌面任務（machine-checkable desktop tasks）；以及（4）評估架構（evaluation harness），記錄完整軌跡（full trajectories）並計算可稽核的部分得分獎勵（auditable partial-credit rewards）。在目前的形式下，OpenComputer 涵蓋 33 個桌面應用程式（desktop applications）與 1,000 項已定案任務，橫跨瀏覽器、辦公工具、創意軟體、開發環境、檔案管理程式與通訊應用程式。實驗顯示，OpenComputer 的硬編碼驗證器相較於以 LLM 為評審的評估（LLM-as-judge evaluation），更貼近人工評審（human adjudication），尤其在成功與否取決於細粒度應用程式狀態（fine-grained application state）時更是如此。前沿代理程式（frontier agents）即使已有部分進展，仍難以達成端對端完成（end-to-end completion）；而開源模型（open-source models）相較於其在 OSWorld-Verified 的得分則出現急遽下滑，暴露出穩健的電腦自動化（robust computer automation）方面持續存在的差距。

### 核心貢獻（3～5點）
- 提出 OpenComputer 框架，整合應用程式專屬狀態驗證器、自我演進驗證層、任務生成管線與評估架構，為電腦使用代理程式建立可驗證的軟體世界。
- 透過結構化檢查端點與以執行為基礎的回饋，提升驗證器對細粒度應用程式狀態的判斷可靠性，實驗證明其比以 LLM 為評審的評估更貼近人工評審。
- 建置涵蓋 33 個桌面應用程式與 1,000 項機器可檢查任務

## 深度分析

#### 方法論解析

OpenComputer 的核心方法論在於將 verification（驗證）從傳統的下游評估細節，提升為環境與任務建構的組織原則。框架由四個 tightly coupled components（緊密耦合元件）構成，形成一個 verifier-grounded framework（以驗證器為基礎的框架）。

首先，app-specific state verifiers（應用程式專屬狀態驗證器）透過 structured inspection endpoints（結構化檢查端點）對真實 desktop applications（桌面應用程式）進行程式化檢查。這些驗證器並非臨時腳本，而是經過嚴格的 debug-fix-retry testing loop（除錯-修正-重試測試迴圈）淬煉，透過 stable interfaces（穩定介面）暴露 application state（應用程式狀態），從而明確定義哪些任務成果可被程式化檢驗。這解決了傳統 custom inspection logic（客製化檢查邏輯）難以標準化的問題。

第二，self-evolving verification layer（自我演進驗證層）透過 execution-grounded self-evolution loop（以執行為基礎的自我演進迴圈）持續提升驗證器可靠性。具體而言，系統在 sandboxed desktops（沙盒化桌面）中執行 calibration tasks（校準任務），將程式化驗證器的輸出與 criterion-level LLM judgments（準則層級 LLM 判斷）進行比對；當發生 verifier-side failures（驗證器端失敗）時，系統會自動精煉 checker logic（檢查器邏輯）、inspection endpoints（檢查端點）或相關文件。這層設計巧妙地利用 LLM 作為暫時的參照標準，但最終目標是減少對 LLM-as-judge evaluation（以 LLM 為評審的評估）的依賴。

第三，task-generation pipeline（任務生成管線）在驗證器堆疊之上合成真實的使用者任務。該管線並非任意產生 natural-language instruction（自然語言指令），而是根據難度、資料可生成性與狀態可檢查性進行結構化篩選，確保每個產出的任務都是 machine-checkable desktop tasks（機器可檢查的桌面任務）。

第四，evaluation harness（評估架構）在全新的 sandboxed desktops（沙盒化桌面）中執行 computer-use agents（電腦使用代理程式），記錄 full trajectories（完整軌跡）——包含畫面截圖與 GUI 動作——並在最終 software state（軟體狀態）上執行驗證器指令，計算 auditable partial-credit rewards（可稽核的部分得分獎勵）。這種設計使得評估不再僅依賴視覺外觀，而是能夠偵測 persistent side effects（持續性副作用）與 fine-grained application state（細粒度應用程式狀態）的正確性。

從問題形式化來看，OpenComputer 將每個任務實例定義為 τ = (x, e, c)，其中 x 為任務描述，e 為可執行的環境初始化程序，c 為機器可檢查的成功準則。代理程式從初始 environment state（環境狀態）s₀ 出發，透過互動產生最終狀態 s_T，再由 verification layer（驗證層）判定是否達成目標。這種設計將 verifiable software worlds（可驗證的軟體世界）的建構與評估緊密結合。

#### 實驗數據解讀

實驗結果揭示了當前 computer-use agents（電腦使用代理程式）在真實桌面工作流程上的能力邊界。在 end-to-end completion（端對端完成）指標上，frontier agents（前沿代理程式）的表現呈現明顯落差：GPT-5.4 以 68.3% 的全任務成功率領先，Claude-Sonnet-4.6 與 Kimi-K2.6 分別為 64.4% 與 58.8%。值得注意的是，儘管這些模型在部分子任務上有所進展，卻仍難以穩定地完成端到端流程，顯示現有系統在長程規劃與跨步驟狀態維持上存在結構性弱點。

更關鍵的發現來自 open-source models（開源模型）的表現：相較於它們在 OSWorld-Verified（OSWorld-Verified）基準上的分數，這些模型在 OpenComputer 上出現顯著下滑。這項落差凸顯了兩個問題：其一，現有基準可能因採用較 weak proxy evaluation（弱代理評估）而過度高估真實能力；其二，開源模型在面對需要 robust computer automation（穩健的電腦自動化）的複雜 desktop environments（桌面環境）時，泛化性遠不如前沿閉源模型。

在驗證品質方面，實驗明確顯示 hard-coded verifiers（硬編碼驗證器）與 human adjudication（人工評審）的一致性高於 LLM-as-judge evaluation（以 LLM 為評審的評估），特別是當任務成功與否取決於無法從畫面截圖單獨推論的 fine-grained application state（細粒度應用程式狀態）時。這直接證明了 verifier-grounded framework（以驗證器為基礎的框架）之價值：LLM 評審容易受到 prompt wording（提示詞措辭）、incomplete observations（不完整觀察）與 model-specific biases（模型特定偏差）影響，甚至可能獎勵表面上合理但底層軟體狀態實則錯誤的結果。OpenComputer 透過 auditable partial-credit rewards（可稽核的部分得分獎勵）與 full trajectories（完整軌跡）記錄，提供了更嚴謹且可重複的評估基礎。

#### 與現有研究的比較

相較於既有研究，OpenComputer 在電腦使用代理程式的評估光譜上佔據獨特位置。傳統靜態軌跡資料集（如 Mind2Web、Android in the Wild）僅評估離線動作預測，缺乏互動式環境回饋；而互動式基準測試（如 OSWorld、Windows Agent Arena）雖然允許代理程式與環境互動，但大多仍依賴人工策劃任務，且受限於任務實例數量、應用領域範圍與手寫獎勵檢查。OpenComputer 的突破在於將環境建構本身視為可規模化的流程，並透過自動化任務生成與可執行驗證器擺脫人工瓶頸。

在合成環境領域，近期研究如 AgentScaler、AgentWorldModel 與 Simia 雖然展示了規模化互動世界的價值，但主要針對抽象 API 或模型模擬回饋，而非原生桌面軟體。同期針對 GUI 與電腦使用環境的研究（如 InfiniteWeb、GUI-Genesis、Gym-Anything、TermiGen、Scale-SWE）則各自從網站生成、行動應用重建或終端環境自動化等角度切入。OpenComputer 與它們的根本差異在於「獎勵感知合成」（reward-aware synthesis）：每個生成的任務在誕生之初就配對了可執行的 state verifiers（狀態驗證器），直接檢查 application state（應用程式狀態），而非依賴視覺代理或 LLM 判斷作為評分依據。

然而，OpenComputer 仍存在若干限制。首先，目前涵蓋的 33 個 desktop applications（桌面應用程式）與 1,000 個定稿任務雖具規模，但相較於真實使用者可能遭遇的數萬種專業軟體仍屬有限；其次，app-specific state verifiers（應用程式專屬狀態驗證器）的建構仍需針對個別軟體投入工程成本，其 debug-fix-retry testing loop（除錯-修正-重試測試迴圈）雖能提升品質，卻尚未達到完全無人監督的通用擴展。此外，self-evolving verification layer（自我演進驗證層）在校準階段仍須仰賴 criterion-level LLM judgments（準則層級 LLM 判斷）作為參照，某種程度上仍內化了 LLM-as-judge 的局限性，只是將其限制在驗證器開發階段而非最終評估階段。

#### 可重現性評估

就提供的論文脈絡而言，OpenComputer 的可重現性（reproducibility）面臨機遇與挑戰並存的局面。框架的設計原則——包括 sandboxed desktops（沙盒化桌面）、可執行的環境初始化程序、基於 stable interfaces（穩定介面）的驗證器指令集，以及記錄 full trajectories（完整軌跡）的 evaluation harness（評估架構）——理論上為第三方復現提供了嚴謹的基礎。特別是 machine-checkable desktop tasks（機器可檢查的桌面任務）與 auditable partial-credit rewards（可稽核的部分得分獎勵）機制，大幅降低了主觀評分帶來的變異性。

然而，根據目前提供的全文內容，作者並未明確說明原始碼、資料集、驗證器實作或模型權重的公開釋出計畫。若缺乏開放的 task-generation pipeline（任務生成管線）腳本與各應用程式對應的 structured inspection endpoints（結構化檢查端點），其他研究團隊將難以完全復現這 1,000 個任務的執行環境與評分邏輯。此外，由於部分驗證器涉及與真實 desktop applications（桌面應用程式）的深層整合，其行為可能受作業系統版本、應用程式版本與區域設定影響，進一步提高了復現門檻。因此，雖然方法論在設計上具備高度可稽核性，實際的可重現性仍取決於作者後續是否釋出完整的虛擬機映像檔、自動化建置腳本與驗證器原始碼。

#### 未來研究方向

基於 OpenComputer 的驗證器核心設計，未來研究可沿多個軸線展開。第一，規模化擴展：將目前的 33 個 desktop applications（桌面應用程式）與 1,000 個任務擴展至更廣泛的專業領域軟體（如 CAD、生物資訊工具、影音後製套件），並探索跨應用程式的複雜工作流程，使代理程式必須在多個軟體間協調 persistent side effects（持續性副作用）。

第二，訓練導向應用：OpenComputer 目前主要作為評估框架，但其提供的可靠獎勵訊號非常適合用於強化學習（Reinforcement Learning）或模仿學習的訓練管線。未來可研究如何將 state verifiers（狀態驗證器）的回饋即時注入代理程式的決策迴路，而不僅止於最終狀態評分，以解決長程任務中的信用分配（credit assignment）問題。

第三，驗證器自主演化：雖然現有的 execution-grounded self-evolution loop（以執行為基礎的自我演進迴圈）已能修復部分 verifier-side failures（驗證器端失敗），但未來可進一步降低對 criterion-level LLM judgments（準則層級 LLM 判斷）的依賴，改以形式化規格（formal specifications）或人類回饋的少量樣本學習來引導驗證器更新，從而建立更嚴謹的自我改進閉環。

第四，處理非確定性：真實 desktop applications（桌面應用程式）常存在非確定性行為（如網路延遲、背景更新、彈出式通知）。未來的 verification layer（驗證層）需發展對抗此類雜訊的 checker logic（檢查器邏輯），例如透過重複取樣或狀態差分比對來提升驗證的穩健性。

最後，縮小開源與前沿模型的差距：實驗已揭露 open-source models（開源模型）在真實桌面自動化上的顯著落差。未來研究可深入分析這些模型在何種 fine-grained application state（細粒度應用程式狀態）推論上失敗，並利用 OpenComputer 的 full trajectories（完整軌跡）記錄與 partial-credit rewards（部分得分獎勵）設計針對性的訓練資料增強或模型架構改進方案。

## 論文問答

**Q1：OpenComputer 試圖解決電腦使用代理程式在評估與訓練上的哪些核心挑戰？**
A：建構真實且可重現的桌面環境與任務需要耗費大量人力，開發者必須設計合理的使用者目標、手動準備底層環境狀態，並確保軟體狀態既連貫又可重現，這些步驟繁瑣且難以標準化。此外，評估代理程式是否成功不能僅依賴螢幕截圖，還需要檢查應用程式內部狀態、檔案內容、詮釋資料或持續性副作用，這使得大規模任務驗證變得極為困難。OpenComputer 正是為了同時解決可擴展的環境建構與可信賴的狀態驗證這兩大瓶頸而設計。

**Q2：為何現有的 LLM-as-judge 評估方式與傳統基準測試不足以應對電腦使用代理程式的評估需求？**
A：LLM-as-judge 的判斷容易受到提示詞措辭、不完整觀察與模型特定偏差的影響，且往往難以在不同執行之間進行稽核或重現。更重要的是，大型語言模型評審可能僅從螢幕截圖判斷結果看似合理，卻忽略了底層軟體狀態中的錯誤，導致獎勵與真實任務完成度脫鉤。相較之下，傳統基準測試多為人工策劃，受限於任務數量、應用領域與手動撰寫的獎勵檢查，難以擴展到涵蓋多樣化的真實桌面軟體工作流程。

**Q3：以驗證器為基礎的評估對於發展穩健的電腦自動化為何至關重要？**
A：在桌面環境中，任務成功與否經常取決於細粒度的應用程式狀態，而非僅是視覺上可見的介面變化，例如試算表中的數值、檔案系統的中繼資料或瀏覽器的歷史紀錄。如果評估僅依賴螢幕截圖或語言模型的表面判斷，代理程式可能在未真正達成目標的情況下獲得正向回饋，進而強化錯誤的行為模式。因此，建立能夠直接檢查軟體內部狀態的可驗證機制，是確保評估結果可信、並能據以訓練出可靠代理程式的根本基礎。

**Q4：OpenComputer 的四個緊密耦合元件分別是什麼，它們如何協同運作？**
A：第一個元件是應用程式專屬狀態驗證器，它透過穩定的結構化檢查端點來檢視真實應用程式的內部狀態；第二個是自我演進驗證層，透過以執行為基礎的回饋迴圈不斷改進驗證器的可靠性；第三個是任務生成管線，負責合成既真實又可被機器檢查的桌面任務；第四個是評估架構，用於在隔離的桌面環境中執行代理程式、記錄完整軌跡，並計算可稽核的部分得分獎勵。這四個元件以驗證為核心設計原則，從任務生成、環境初始化到最終評分都圍繞著可執行的狀態檢查機制緊密協作。

**Q5：OpenComputer 的「以驗證器為基礎」方法與先前合成環境建構的主要區別為何？**
A：過往研究通常將驗證視為下游的評估細節，或依賴視覺代理與 LLM 判斷作為獎勵訊號，這些方法本質上屬於弱代理評估。OpenComputer 則從一開始就將驗證作為組織原則，每個生成的桌面任務都會配對一組可執行的檢查器，直接檢驗應用程式的內部狀態。這種設計確保了評估依據的是軟體的真實狀態變化，而非僅從螢幕截圖推測的近似結果，從而大幅提升評估的精確度與可稽核性。

**Q6：自我演進驗證層如何提升驗證器的可靠性，為何選擇這樣的設計？**
A：該層級會在沙盒化桌面中執行校準任務，將程式化驗證器的輸出與準則層級的 LLM 判斷進行比對，並利用驗證器端的失敗案例來精煉檢查器邏輯、端點或文件。這種設計被採用是因為硬編碼的驗證器在面對多樣化的真實軟體行為時，難以一次性涵蓋所有邊界情況，需要透過實際執行產生的回饋持續迭代修正。透過這種除錯-修正-重試的測試迴圈，系統能夠自動發現並修復驗證器本身的誤判問題，減少對人工除錯的依賴。

**Q7：OpenComputer 建構的基準測試在規模與涵蓋範圍上達到什麼程度？**
A：目前的 OpenComputer 涵蓋了 33 種桌面應用程式，並包含 1,000 個最終確定的任務，這些任務橫跨瀏覽器、辦公工具、創意軟體、開發環境、檔案管理員與通訊應用程式等多種類型。這樣的規模遠超許多傳統人工策劃的基準測試，能夠更全面地反映真實桌面工作流程的多樣性與複雜度。透過自動化的任務生成與狀態驗證，該框架得以在不需要大量人工介入的情況下，持續擴展任務數量與應用領域。

**Q8：實驗結果揭示了前沿與開源電腦使用代理程式的哪些性能表現？**
A：在前沿代理程式中，GPT-5.4 表現最佳，完整任務成功率達到 68.3%，Claude-Sonnet-4.6 與 Kimi-K2.6 分別為 64.4% 與 58.8%，顯示即使是頂尖模型也難以完美完成所有真實桌面任務。開源代理程式的表現則明顯落後，且相較於它們在 OSWorld-Verified 等現有基準上的分數出現急劇下滑，暴露出這些模型在面對更嚴謹、可驗證的桌面自動化流程時的脆弱性。整體而言，實驗顯示目前的代理程式即使能取得部分進展，在端對端完成複雜任務方面仍存在顯著挑戰。

**Q9：硬編碼驗證器與 LLM-as-judge 在對齊人工評審方面有何差異？**
A：實驗證明，硬編碼驗證器的評估結果與人工評審的一致性高於以 LLM 為評審的評估方式，特別是在任務成功與否取決於無法僅從螢幕截圖推斷的細粒度應用程式狀態時。這是因為結構化的檢查端點能夠精確讀取軟體內部的數值、格式與中繼資料，而 LLM 評審則受限於視覺觀察的不完整性與模型自身的推論偏差。這項比較結果強化了以驗證器為基礎的評估框架在建立可信賴基準測試上的必要性與優越性。

**Q10：OpenComputer 的可驗證軟體世界在哪些實際應用場景中最能發揮即時效用？**
A：在自動化軟體測試領域，OpenComputer 能夠提供可重現的桌面環境與機器可檢查的通過準則，協助開發團隊驗證複雜的跨應用程式工作流程。對於需要大量訓練資料的桌面自動化代理程式開發者而言，該框架可自動生成真實且帶有精確獎勵訊號的任務實例，降低資料標註成本。此外，企業內部涉及文書處理、檔案管理與網頁操作的品質保證流程，也能受益於其可稽核的部分得分獎勵機制，實現更細緻的效能監控。

**Q11：對於建構電腦使用代理程式的開發者而言，OpenComputer 在產品層面提供了哪些優勢？**
A：OpenComputer 大幅減少了開發者在建立評估環境時所需的手動準備工作，因為任務描述、環境初始化程序與驗證器都能自動生成。其提供的穩定檢查端點將應用程式特有的複雜性抽象化，使開發者無需為每個軟體撰寫客製化檢查邏輯，即可取得可靠的狀態回饋。此外，評估架構所記錄的完整軌跡與可稽核的部分得分獎勵，讓開發團隊能夠精確定位代理程式在哪些步驟失敗，從而加速迭代與除錯流程。

**Q12：OpenComputer 可能如何影響電腦使用代理程式與互動式 AI 基準測試的未來研究方向？**
A：OpenComputer 將研究典範從人工策劃的基準測試與 LLM 近似評判，轉向可擴展且以驗證為優先的合成框架，這可能促使更多研究者關注細粒度狀態操作的穩健性。它證明了在真實桌面軟體上建立大規模、可驗證環境的可行性，未來或將啟發類似的驗證器優先方法應用於行動裝置、網頁或企業軟體等其他領域。長遠來看，這種強調可稽核獎勵的設計哲學，有助於建立更嚴謹的代理程式能力標準，推動整個領域從示範走向可量產的可靠自動化。

**Q13：OpenComputer 目前在應用程式覆蓋範圍與驗證器建構上存在哪些已知的限制？**
A：雖然目前已涵蓋 33 種桌面應用程式，但這相對於生態系中數以千計的專業與遺留軟體而言仍屬有限，且每種新應用程式都需要經過繁複的除錯-修正-重試測試迴圈來建構專屬驗證器。對於內部架構封閉、動態變化頻繁或缺乏可程式化介面的應用程式，建立穩定的結構化檢查端點可能面臨技術障礙。因此，框架的擴展性在某種程度上仍受制於應用程式本身是否允許外部程式進行可靠的狀態檢查。

**Q14：即使具備 OpenComputer 的驗證器，哪些類型的任務或代理程式行為仍可能難以被準確評估？**
A：當任務的成功標準涉及主觀判斷或細微的視覺排版差異時，純粹基於結構化狀態的檢查可能無法完全捕捉人類對於「正確性」的感知。此外，代理程式可能透過非預期的副作用路徑達成驗證器所檢查的最終狀態，但實際操作過程違反了任務隱含的程序性要求，而這類行為可能逃過現有檢查器的偵測。若應用程式的狀態檢查介面本身不穩定或無法暴露關鍵內部變數，驗證器也可能產生誤判或無法覆蓋完整的任務完成條件。

**Q15：根據目前的發現，OpenComputer 未來可以朝哪些方向進行改進與擴展？**
A：未來可以擴展覆蓋範圍至更多專業領域或遺留桌面應用程式，並進一步降低為新軟體建構驗證器所需的人工工程成本。自我演進驗證層也可持續優化，逐步減少對準則層級 LLM 判斷的依賴，轉而透過更純粹的執行回饋與形式化規範來驅動驗證器精煉。此外，鑒於目前代理程式在端對端完成率上的不足，未來研究可探索如何利用 OpenComputer 的可驗證世界進行強化學習訓練，而不僅止於評估，從而縮小部分進展與完整任務成功之間的差距。

## 實務應用指南

### 適用場景

1. **企業級桌面流程自動化驗收**：例如財務月結時需在試算表、ERP 用戶端與郵件軟體間搬移資料，傳統 RPA 僅驗證截圖或元件點擊，OpenComputer 可透過應用程式專屬狀態驗證器確認儲存格公式、郵件主旨與檔案總管中繼資料皆正確，並提供可稽核的部分得分獎勵。
2. **電腦使用代理程式的訓練與基準測試**：針對需要操作瀏覽器、文書工具、創意軟體、開發環境等 33 類以上桌面軟體的代理程式，建立機器可檢查的桌面任務，避免以 LLM 為評審的評估所帶來的模型特定偏差與不完整觀察。
3. **軟體回歸測試與持續性副作用確認**：在發布新版應用程式前，利用沙盒化桌面執行端到端工作流程，透過結構化檢查端點驗證檔案內容、資料庫狀態與設定檔變更，確保不會產生非預期的持續性副作用。
4. **多步驟客服或行政任務的數位孿生環境**：為新進人員或 AI 代理建立可重現的桌面環境，自動生成包含自然語言指令的任務，並以完整軌跡記錄操作過程，便於事後稽核與教學。
5. **跨應用程式資料整合的穩健度評測**：評估代理程式在面對細粒度應用程式狀態（如瀏覽器歷史、行事曆邀請、試算表儲存格格式）時的端對端完成能力，特別是當成功與否無法僅靠視覺畫面判斷的場景。

### 實作前置條件

- **資料需求**：目標桌面應用程式的自動化介面文件（API、CLI、輔助功能樹）、用於建立校準任務的領域知識庫，以及作為黃金標準的準則層級 LLM 判斷或人工評審標註資料。
- **運算資源**：可執行沙盒化桌面的虛擬機或容器叢集（支援快照與還原）、儲存完整軌跡（截圖與動作序列）的物件儲存空間，以及用於執行自我演進驗證層與任務生成管線的 GPU／LLM 推論資源。
- **技術能力**：具備 Python 或系統程式設計能力以開發檢查端點與檢查器邏輯；熟悉 GUI 自動化（如 accessibility APIs）；能設計提示工程與過濾邏輯以驅動任務生成管線；具備 DevOps 經驗以維護隔離且可重現的桌面環境。

### 實作步驟建議

1. **盤點目標軟體並建立結構化檢查端點**：針對每個桌面應用程式，梳理其可程式化查詢的穩定介面（如 COM、AppleScript、無頭瀏覽器協定、檔案系統 API），定義可暴露的應用程式狀態欄位。
2. **開發應用程式專屬狀態驗證器**：為每個應用撰寫客製化檢查邏輯，並執行除錯-修正-重試測試迴圈，確保驗證器能可靠判斷軟體狀態是否達標，而非僅依賴畫面像素。
3. **部署以執行為基礎的自我演進迴圈**：在沙盒化桌面中執行校準任務，將驗證器輸出與準則層級 LLM 判斷或人工評審進行比對，針對驗證器端失敗（誤判或漏判）自動修正檢查器邏輯、檢查端點或文件。
4. **建構任務生成管線**：設計結構化流程，從自然語言使用者目標出發，自動產生環境初始化程序（檔案、設定、資料預備），並過濾掉難度過低、資料無法生成或狀態無法檢查的任務。
5. **搭建評估架構**：整合沙盒化桌面、代理程式介面與狀態驗證器，確保每次評測都在全新環境中開始，記錄完整軌跡，並依據驗證器回傳計算可稽核的部分得分獎勵。
6. **持續擴充與維護**：隨著應用程式版本更新，重新執行自我演進驗證層，擴充檢查端點以覆蓋新的細粒度應用程式狀態，並累積執行資料以優化任務生成管線的難度與多樣性。

### 潛在風險與注意事項

- **驗證器脆性風險**：桌面應用程式更新可能破壞穩定介面，導致狀態驗證器失效。應建立版本對應的檢查端點迴歸測試，並在 CI/CD 中自動偵測介面變更。
- **過度依賴 LLM 評審的誘惑**：初期可能想直接採用以 LLM 為評審的評估來節省成本，但這會引入提示詞措辭敏感與不完整觀察問題。應堅持以驗證器為基礎的框架，僅在校準階段使用 LLM 作為輔助。
- **沙盒隔離與重現性**：若環境初始化程序未徹底清理持續性副作用（如下載殘留、註冊表變更），會造成任務重現性下降。建議每次評測還原至乾淨快照，並將環境狀態腳本化。
- **部分得分獎勵的人為偏差**：可稽核的部分得分獎勵雖優於二元判斷，但其權重設計若未對齊人工評審，仍可能誤導代理程式訓練。應定期抽樣比對驗證器輸出與人工評審，維持對齊度。
- **儲存與運算成本**：記錄完整軌跡與大規模沙盒並行執行會快速消耗資源。建議分層儲存（熱儲存近期軌跡、冷儲存歷史資料），並採用動態資源調度。
- **開源模型效能落差**：若目標使用者主要採用開源模型，需注意其在現有基準（如 OSWorld-Verified）的分數可能無法直接遷移至 OpenComputer，應預留額外的適應與微調資源。

### 與其他技術的整合建議

- **與現有 RPA 工具（如 Selenium、Playwright、PyAutoGUI）整合**：將這些工具作為代理程式的動作執行層，而 OpenComputer 的驗證層負責最終的軟體狀態確認，補強傳統工具僅能驗證畫面或 DOM 的弱代理評估。
- **與 CI/CD 管線整合**：將評估架構嵌入 Jenkins、GitLab CI 或 GitHub Actions，在每次軟體更新後自動執行機器可檢查的桌面任務，作為回歸測試閘道。
- **與容器編排平台整合**：利用 Docker 或 Kubernetes 管理沙盒化桌面叢集，透過 API 動態配置乾淨的桌面環境，支援大規模並行評測與彈性擴展。
- **與 LLM 代理框架（如 LangChain、AutoGPT）整合**：將 OpenComputer 的狀態驗證器輸出作為細粒度獎勵訊號，取代僅依賴截圖的視覺回饋，提升代理程式在長期任務中的穩健的電腦自動化能力。
- **與可觀測性平台整合**：將完整軌跡與驗證器結果匯出至 ELK、Grafana 或自研稽核系統，實現企業級的任務執行透明化與除錯。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從「為何不能以截圖判斷成敗」這個核心問題出發，理解應用程式狀態與畫面像素之間的差異；先掌握沙盒化桌面與狀態驗證器的概念，再逐步了解任務生成管線如何自動產生可驗證的桌面任務，無需深入程式碼細節。
- **AI 工程師**：請聚焦於第 3 節的技術實作，特別是結構化檢查端點的設計、除錯-修正-重試測試迴圈的實作細節，以及以執行為基礎的自我演進迴圈如何具體比對驗證器輸出與準則層級 LLM 判斷；同時評估將此框架整合進現有代理程式訓練流程所需的介面改動。
- **研究人員**：建議深入分析驗證器與人工評審的對齊實驗，以及前沿代理程式與開源模型在端對端完成表現上的落差；可進一步探討自我演進驗證層的收斂性、部分得分獎勵設計對策略學習的影響，或將此框架擴展至行動裝置與網頁環境的可行性。
- **產品經理**：請關注 OpenComputer 在 33 個桌面應用程式與 1,000 個任務上的覆蓋範圍，以及可稽核的部分得分獎勵如何為企業提供合規與品質保證；評估導入此框架後，相較於傳統以 LLM 為評審的評估，能為客戶節省多少人工複審成本，並思考如何將「驗證優先」的設計原則轉化為產品競爭優勢。
