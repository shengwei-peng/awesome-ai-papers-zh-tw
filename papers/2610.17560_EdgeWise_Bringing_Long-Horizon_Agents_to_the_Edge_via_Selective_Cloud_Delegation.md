# EdgeWise：透過選擇性雲端委託將長時程代理部署至邊緣

## ⚡ TL;DR

長時程代理任務全程仰賴雲端大型語言模型，推論成本高昂且非必要。
本文提出 EdgeWise 框架，以本地小型模型為主，選擇性將關鍵步驟委託雲端。
實驗顯示效能可比擬純雲端執行，平均降低推論成本達四成六。

## 摘要翻譯

複雜且長時程的代理任務通常仰賴部署於雲端的前沿模型（Frontier Model）以達成強大的效能。然而，即使並非所有步驟都需要相同層級的模型能力，對長時程任務軌跡中的每個步驟皆使用這些模型仍會產生龐大的推論成本。本文發現，僅將大型語言模型（LLM）配置給一小部分關鍵步驟，即可在大幅降低推論成本的同時，達到與完整 LLM 執行相當的效能。基於此觀察，我們提出 EdgeWise，一個邊緣-雲端協作（Edge-Cloud Collaboration）框架，於本地裝置上部署小型語言模型（SLM）作為主要求解器（Primary Solver），並在需要更強模型能力時，選擇性地將關鍵步驟委託給雲端 LLM。為了在推論時無需額外模型即可實現自主委託，我們引入一種步驟層級強化學習（Step-level RL）方法，共同最佳化任務求解與委託，並對個別委託決策進行細粒度信用分配（Fine-grained Credit Assignment）。我們亦提出一種外部判斷器式委託（External Judge-based Delegation）策略，並利用該策略系統性地探討邊緣-雲端協作中的關鍵設計選擇，包括何時委託、委託決策應如何制定、應共享哪些上下文，以及雲端 LLM 應以何種頻率被呼叫。實驗顯示，EdgeWise 在 SWE-Rebench 上降低推論成本最高達 62%，在 Terminal-Bench 2.1 上降低 34%，同時達到匹敵或超越純 LLM 執行的效能。我們進一步將 EdgeWise 部署於本地工作站（Local Workstation），證明在實際邊緣-雲端設定（Practical Edge-Cloud Setting）中可實現相當的成本節省。

### 核心貢獻（3～5點）
- **關鍵觀察**：揭示僅將 LLM 配置給一小部分關鍵步驟，即可在大幅降低推論成本的同時，達到與完整 LLM 執行相當的效能。
- **框架提出**：提出 EdgeWise 邊緣-雲端協作框架，於本地裝置部署 SLM 作為主要求解器，並選擇性地將關鍵步驟委託給雲端 LLM。
- **方法創新**：引入步驟層級強化學習方法，結合細粒度信用分配機制，使 SLM 能在推論時無需額外模型即可自主做出委託決策。
- **設計準則**：透過外部判斷器式委託策略，系統性地探討邊緣-雲端協作中的關鍵設計選擇（委託時機、決策方式、上下文共享、呼叫頻率）。
- **實驗驗證**：在 SWE-Rebench 與 Terminal-Bench 2.1 上達到匹敵或超越純 LLM 執行的效能，並於本地工作站實際部署驗證成本節省的可行性。

## 深度分析

#### 方法論解析

EdgeWise 的核心方法論建立在兩個關鍵觀察之上：(1) 長時程任務中的各步驟對模型能力的需求並不均勻；(2) 將雲端大型語言模型（LLM）僅用於關鍵步驟即可維持與全程使用 LLM 相當的表現。基於此，框架採用「邊緣-雲端協作（Edge-Cloud Collaboration）」的雙層架構，將小型語言模型（SLM）部署於本地裝置作為主要求解器（Primary Solver），並透過選擇性雲端委託（Selective Cloud Delegation）機制在必要時呼叫雲端 LLM。

**整體流程設計**

EdgeWise 的運作流程遵循「規劃與執行（Plan & Act）」代理範式。SLM 持續與執行環境互動，產生下一步動作（讀取檔案、編輯程式碼、執行測試等），並接收觀察（Observation）作為回饋。在每個步驟結束後，系統會評估是否需要將當前步驟委託給雲端 LLM。圖 2 的範例清楚展示了這種分工：簡單的步驟如探索儲存庫結構（`ls`、`cat`）由 SLM 處理，而複雜的步驟如修復深層錯誤（Assertion Error 分析）則委託給雲端 LLM。

**兩種委託機制**

第一種是**外部判斷器式委託（External Judge-based Delegation）**：使用一個獨立的判斷模型（通常也是 LLM）來評估當前狀態的複雜度，並決定是否需要升級到雲端模型。這種方法的優勢在於決策與執行分離，便於系統性分析不同設計選擇的影響。

第二種是**SLM 自主委託（SLM Self-delegation）**：將委託決策能力直接整合進 SLM 本身。這是透過**步驟層級強化學習（Step-level RL）**實現的，並搭配**細粒度信用分配（Fine-grained Credit Assignment）**機制。具體而言，RL 訓練過程不僅對最終任務成敗給予獎勵，還會對每個個別的委託決策進行信用歸因，使 SLM 能學會在哪些步驟類型上值得呼叫雲端資源。這種設計避免了推論時需要額外決策模型（Decision Model）的負擔，提升了實用性。

**關鍵設計因素的系統性分析**

論文特別強調對邊緣-雲端協作中四個核心設計選擇的系統性研究：

1. **何時委託（When to delegate）**：分析哪些步驟類型真正受益於更強的模型能力。實驗顯示效益集中在少數關鍵步驟（如根因定位、複雜程式碼生成）。

2. **如何委託（How to delegate）**：比較外部判斷器與 SLM 自主決策兩種機制的效能與成本權衡。

3. **應共享什麼上下文（What context to share）**：探討完整上下文（Full Context）、最近 k 步上下文（Recent-k Context）、摘要上下文（Summary Context）三種資訊共享策略對雲端 LLM 表現的影響。

4. **委託頻率（Delegation Frequency）**：控制雲端 LLM 的呼叫比例，平衡成本與效能。

**理論意涵**

此方法論的深層貢獻在於揭示了長時程代理任務中「模型能力異質性需求」的現象。傳統做法假設所有步驟都需要相同等級的模型能力，導致資源浪費；EdgeWise 則透過細粒度的步驟分析，將模型選擇從「查詢層級」提升到「步驟層級」，這對多步驟設定（Multi-step Setting）下的模型選擇（Model Selection）研究具有方法論上的推進意義。

#### 實驗數據解讀

**基準測試與成本節省**

實驗在兩個長時程程式設計代理基準上進行評估：

- **SWE-Rebench**：推論成本降低最高達 **62%**
- **Terminal-Bench 2.1**：推論成本降低最高達 **34%**
- **跨模型與基準的平均成本節省**：**46%**

這些數據顯示 EdgeWise 在維持任務表現的同時，能顯著降低雲端 API 呼叫成本。值得注意的是，SWE-Rebench 的成本節省幅度（62%）明顯高於 Terminal-Bench 2.1（34%），這可能反映了兩個基準在任務結構上的差異：SWE-Rebench 的程式碼修復任務可能包含更多可由 SLM 處理的常規步驟（如檔案讀取、測試執行），而 Terminal-Bench 2.1 的終端機操作任務可能更均勻地需要較強的推理能力。

**Pass@3–成本權衡曲線**

圖 1 展示了 Pass@3 準確率與成本之間的權衡曲線。從曲線形態可以解讀出：(1) EdgeWise 的方法在曲線上佔據優越位置，即在相同成本下提供更高準確率，或在相同準確率下使用更低成本；(2) 純雲端（Only Cloud）與純邊緣（Only Edge）兩端點之間存在明顯的 Pareto 前沿改善空間。

**雲端使用率分析**

圖 3 揭示了一個關鍵發現：當雲端使用率僅約 **40%** 時，選擇正確步驟進行委託即可達到與全程使用 GPT-5.5 相當的表現，同時大幅降低成本。這強烈支持了「效益集中在少數關鍵步驟」的核心假設。具體而言：

- **左圖（準確率 vs. LLM 使用率）**：呈現出非線性關係——從 0% 到約 40% 的雲端使用率帶來顯著準確率提升，但超過 40% 後邊際效益遞減。
- **右圖（成本 vs. LLM 使用率）**：成本隨使用率線性增長，凸顯了精準選擇委託時機的重要性。

**實際部署驗證**

論文進一步在本地工作站（Local Workstation）上進行實際邊緣-雲端設定（Practical Edge-Cloud Setting）部署驗證，證明了該框架在真實環境中的可行性。這項驗證特別重要，因為它跨越了單純的學術實驗，展示了從理論到實務的轉譯能力。

**實驗設計的侷限**

雖然數據令人振奮，但需注意以下幾點：(1) 實驗主要集中在程式設計代理任務，對於其他類型的長時程任務（如深度研究、網頁導航）的泛化性尚未充分驗證；(2) Pass@3 指標雖然反映了多次嘗試的成功率，但對於單次部署的可靠性評估可能不夠全面；(3) 成本計算是否包含延遲、本地運算成本等因素需要更透明的說明。

#### 與現有研究的比較

**與模型路由方法的比較**

EdgeWise 明確定位於改進現有的模型選擇（Model Selection）方法：

- **vs. 單查詢路由（Single-query Routing）方法（如 [4, 5, 6, 7]）**：這些方法僅處理單一查詢的難度分級，無法捕捉長時程任務中步驟間的依賴關係與累積狀態。EdgeWise 的步驟層級設計填補了這一空白。

- **vs. Router-R1 [8] 與 MERA [9]**：這些方法將模型選擇擴展到多步驟設定，但仍存在兩個關鍵限制：(1) 缺乏對真實長時程任務（如程式設計、深度研究）的評估，主要在多跳問答（Multi-hop QA）上測試；(2) 依賴預定義模型池（Model Pool）並訓練額外的決策模型，這使得決策品質受限於模型池的組成，且在推論時需要維護多個模型。

**EdgeWise 的改進**

相較於上述方法，EdgeWise 的核心優勢在於：

1. **真實長時程評估**：直接在 SWE-Rebench 與 Terminal-Bench 2.1 等實務基準上驗證，而非僅限於學術性的多跳問答。

2. **無需獨立決策模型**：透過步驟層級強化學習將委託能力內化於 SLM 本身，避免了模型池依賴性（Model-Pool Dependency）問題。這使得框架對模型演進更具魯棒性。

3. **細粒度信用分配**：傳統 RL 通常只在軌跡結束時給予稀疏獎勵，而 EdgeWise 對每個委託決策進行信用歸因，使學習訊號更為精準。

4. **系統性設計分析**：論文對「何時、如何、共享什麼、頻率」四個維度進行了系統性的消融實驗，這在現有文獻中較為少見。

**與 TwinRouterBench 的關聯**

論文引用 TwinRouterBench [10] 指出現有方法在長時程評估上的不足，這顯示 EdgeWise 的定位是回應一個已被識別但尚未充分解決的研究缺口。

**仍存在的限制**

儘管有上述改進，EdgeWise 仍面臨以下挑戰：

1. **任務類型侷限**：目前主要在程式設計任務上驗證，對於開放式長時程任務（如多輪對話代理、複雜規劃任務）的適用性需要進一步研究。

2. **SLM 能力下限**：框架假設 SLM 具備足夠的基本能力來處理大部分步驟。若 SLM 能力過弱，可能導致過度委託，反而增加成本。

3. **委託決策的可解釋性**：雖然 RL 方法有效，但學到的委託策略可能缺乏可解釋性，難以進行故障分析。

4. **動態環境適應**：對於環境回饋高度不確定的任務，固定的委託策略可能不夠靈活。

#### 未來研究方向

**1. 跨領域泛化研究**

EdgeWise 目前主要在程式設計任務上驗證，未來可探索以下方向的泛化：

- **深度研究任務（Deep Research）**：需要多輪資訊檢索、整合與寫作的長時程研究任務。
- **網頁導航與 GUI 代理**：在動態網頁環境中執行多步驟操作。
- **科學發現與實驗設計**：需要假設生成、實驗執行、結果分析的迭代流程。
- **多輪對話代理**：在長期對話中維持一致性與目標導向。

**2. 更精細的委託策略**

- **不確定性量化委託**：結合 SLM 的預測不確定性（如 token entropy、信心度）來決定是否委託，而非僅依賴 RL 學到的策略。
- **階層式委託**：在 SLM 與 LLM 之間引入中間層模型，形成更細粒度的能力梯度。
- **前瞻性委託規劃**：不僅考慮當前步驟，還預測未來若干步驟的需求，進行更長視野的資源分配。

**3. 信用分配機制的改進**

- **基於反事實推理的信用分配**：透過反事實分析（counterfactual reasoning）評估「若不委託會怎樣」，提供更精準的學習訊號。
- **多層級獎勵設計**：結合步驟級、軌跡級、任務級的多層獎勵結構。
- **元學習式的委託策略**：使 SLM 能快速適應新任務類型的委託需求。

**4. 理論分析與形式化**

- **委託決策的最優性理論**：在何種條件下，選擇性委託能保證不顯著損失效能？
- **成本-效能權衡的理論邊界**：推導不同任務結構下的理論最優委託率。
- **資訊理論視角**：從資訊傳遞角度分析哪些步驟真正需要雲端模型的額外資訊容量。

**5. 系統與基礎設施**

- **邊緣硬體協同設計**：針對 NVIDIA DGX Spark 等邊緣裝置的最佳化，包括模型量化、KV cache 管理、批次處理策略。
- **延遲感知委託**：在成本之外，將延遲納入最佳化目標，特別是對於即時互動場景。
- **隱私保護委託**：在共享上下文時，如何保護敏感資訊（如程式碼中的商業邏輯）。

**6. 評估方法的演進**

- **更全面的代理評估指標**：除 Pass@3 外，引入步驟效率、錯誤恢復能力等維度。
- **動態難度基準**：建構能動態調整任務難度的基準，以更細緻地評估模型選擇策略。
- **真實使用者研究**：在實際應用場景中評估 EdgeWise 的使用者體驗與信任度。

**7. 與其他技術的結合**

- **與測試時計算擴展（Test-time Compute Scaling）結合**：在委託決策中考慮是否透過更多推理計算來替代模型升級。
- **與工具使用整合**：將外部工具呼叫（如搜尋、計算）作為另一種「委託」形式，統一在 EdgeWise 框架下。
- **多代理協作**：將 EdgeWise 的邊緣-雲端分工思想擴展到多個 SLM 與 LLM 的協作場景。

這些方向不僅能深化 EdgeWise 本身的技術內涵，也能推動整個長時程代理（Long-Horizon Agent）研究社群朝向更實用、更高效的方向發展。

## 論文問答

**Q1：EdgeWise 試圖解決的核心問題是什麼？**
A：EdgeWise 試圖解決長時程代理任務中「每一個步驟都依賴雲端前沿大型語言模型（LLM）」所造成的成本過高問題。論文的關鍵觀察是，在一個長時程任務軌跡中，並非所有步驟都需要相同等級的模型能力——許多較簡單的步驟（例如探索檔案目錄、執行測試）其實可以由本地的小型語言模型（SLM）勝任。因此，EdgeWise 的核心目標是設計一個邊緣-雲端協作框架，讓本地 SLM 作為主要求解器，僅在關鍵步驟選擇性地委託給雲端 LLM，從而在維持任務表現的同時大幅降低推論成本。

**Q2：現有的模型路由方法為什麼無法有效處理長時程任務？**
A：現有方法如 Router-R1 與 MERA 主要在單查詢推理或多跳問答（Multi-hop QA）等場景下評估，缺乏對真實世界長時程任務（如程式設計、深度研究）的驗證，因此難以推論其在複雜代理軌跡中的表現。此外，這些方法通常依賴預定義的模型池，並需要額外訓練一個決策模型來決定模型選擇，這使得其決策與特定模型能力綁定，當模型池演進或更換時可能變得不穩定。EdgeWise 則跳脫這個框架，讓 SLM 本身透過步驟層級強化學習（RL）學會何時需要委託，無需在推論時額外部署決策模型。

**Q3：為什麼邊緣-雲端協作在當前時機特別具有意義？**
A：近年來 SLM 的能力快速提升，加上邊緣運算硬體（如 NVIDIA DGX Spark）的進展，使得在本地裝置上部署具備一定能力的 SLM 已成為可行方案。這種硬體與模型的雙重進步，創造了一個過去不存在的設計空間：讓本地 SLM 承擔大部分任務執行，僅在必要時呼叫雲端前沿模型。EdgeWise 正是在這個技術轉折點上提出，試圖將長時程代理從「完全依賴雲端」解放出來，使其能在兼顧成本與隱私的情況下部署於邊緣裝置。

**Q4：EdgeWise 的核心機制是什麼？**
A：EdgeWise 的核心機制是「選擇性雲端委託」（Selective Cloud Delegation），由本地 SLM 作為主要求解器持續與環境互動，並在每個步驟動態判斷是否需要將該步驟委託給雲端 LLM。系統會將任務狀態、執行回饋與程式碼儲存庫資訊提供給模型，SLM 根據當前狀態決定是自行產生動作（讀取、編輯、執行），還是將該步驟升級給雲端 LLM 進行深度推理或複雜程式碼生成。雲端 LLM 回傳的結果會被整合回本地軌跡，由 SLM 繼續推進後續步驟，形成一個閉環的協作流程。

**Q5：EdgeWise 在步驟層級強化學習上的關鍵創新是什麼？**
A：EdgeWise 的關鍵創新在於將「任務求解」與「委託決策」聯合訓練，並透過細粒度信用分配（Fine-grained Credit Assignment）讓 SLM 學會在每個步驟獨立判斷是否需要雲端協助。傳統 RL 通常只在軌跡結束時給予整體獎勵，難以分辨哪一個具體的委託決策是有效的；EdgeWise 則將信用歸因到個別的委託動作上，使 SLM 能精確學習「哪些情境下委託能帶來最大效益」。這個設計讓 SLM 在推論時無需額外的決策模型，即可自主決定何時升級到雲端。

**Q6：EdgeWise 系統性地探討了哪些關鍵設計選擇？**
A：論文透過外部判斷器式委託策略，系統性地研究了邊緣-雲端協作中的四個核心設計問題：（1）何時委託——哪些步驟真正受益於更強的模型；（2）如何委託——是由外部判斷器決定，還是由 SLM 自主決定；（3）共享什麼上下文——完整軌跡、近期 k 步、還是摘要；（4）雲端 LLM 的呼叫頻率應如何控制。這些設計選擇的探討揭示了一個重要現象：雲端 LLM 的效益集中在少數關鍵步驟，因此可以大幅降低呼叫次數而不犧牲整體表現。

**Q7：EdgeWise 使用了哪些基準測試？為什麼選擇這些？**
A：實驗主要在 SWE-Rebench 與 Terminal-Bench 2.1 兩個長時程程式設計代理基準上進行。SWE-Rebench 涵蓋真實的軟體工程任務（如錯誤修復、測試通過），Terminal-Bench 2.1 則聚焦於終端機環境下的代理操作，這兩個基準都要求代理執行多步驟的探索、編輯與測試循環。選擇這些基準正是為了回應論文的批評——現有路由方法多在單查詢或多跳 QA 上評估，缺乏對真實長時程任務的驗證，因此 EdgeWise 刻意在更具實務代表性的場景中檢驗其方法。

**Q8：EdgeWise 的關鍵量化成果為何？**
A：在 SWE-Rebench 上，EdgeWise 達到與純雲端 LLM 執行相當或更佳的表現，同時將推論成本降低最多 62%；在 Terminal-Bench 2.1 上則降低最多 34%。跨模型與跨基準的平均成本節省約為 46%，這代表在不犧牲任務完成率的前提下，近一半的雲端呼叫可以被本地 SLM 取代。此外，Pass@3–成本權衡曲線顯示，僅使用約 40% 的雲端呼叫比例即可達到與全雲端執行相當的準確率，凸顯了「關鍵步驟委託」策略的高效率。

**Q9：從設計選擇的消融研究中得到了哪些關鍵洞察？**
A：消融研究揭示了幾個重要洞察：首先，雲端 LLM 的價值高度集中於少數複雜步驟（如根因定位、複雜程式碼生成），而非均勻分佈於整個軌跡；其次，上下文共享策略會影響委託效益——過於簡化的摘要可能遺漏關鍵資訊，而完整軌跡則增加成本，需要在兩者間取得平衡；最後，委託頻率應根據任務難度動態調整，而非固定比例。這些洞察共同支持了 EdgeWise 的設計哲學：與其盲目增加雲端使用，不如精準識別真正需要前沿模型的步驟。

**Q10：哪些實際場景最能受益於 EdgeWise？**
A：EdgeWise 特別適合需要長時間與環境互動的代理任務，例如自動化軟體工程（錯誤修復、重構、測試生成）、深度研究（多輪搜尋、資料彙整）、以及終端機操作類的系統管理任務。這些任務的共同特徵是步驟數量多、步驟間異質性高，且部分步驟（如檔案探索、簡單指令執行）對模型能力要求不高。對於成本敏感或需要保護程式碼隱私的企業部署，EdgeWise 也能在維持表現的同時，將敏感資料保留在本地，僅將必要資訊上傳雲端。

**Q11：在實際部署 EdgeWise 時需要考慮哪些產品化因素？**
A：實際部署時需考量幾個關鍵因素：本地 SLM 的硬體需求（EdgeWise 已在 NVIDIA DGX Spark 等本地工作站上驗證）、雲端呼叫的延遲對整體任務完成時間的影響、以及上下文共享時的隱私保護設計。此外，模型池的演進管理也是實務議題——當雲端 LLM 升級或更換時，EdgeWise 的 SLM 委託策略應能適應新模型的能力分佈。論文中提到的「無需額外決策模型」設計，正是為了降低部署複雜度，使框架更容易整合到現有的代理系統中。

**Q12：EdgeWise 對邊緣 AI 與代理研究的領域影響是什麼？**
A：EdgeWise 推動了從「單一強大模型處理所有任務」轉向「異質模型協作」的典範轉移，證明了在長時程任務中，模型能力的精準調度比單純堆疊參數量更具成本效益。這也為邊緣 AI 研究提供了一個具體的落地範例，說明如何結合本地運算與雲端資源，在效能、成本與隱私間取得平衡。更廣泛地看，這種「選擇性升級」的概念可能延伸到多模態代理、機器人控制等領域，成為未來代理系統設計的基礎模式之一。

**Q13：EdgeWise 存在哪些已承認的限制？**
A：論文中坦誠指出，EdgeWise 的效益高度依賴「關鍵步驟集中」的觀察——若任務的每個步驟都需要前沿模型能力，則選擇性委託的優勢將大幅縮減。此外，外部判斷器式委託需要一個可靠的判斷模型來識別困難步驟，這在跨領域遷移時可能需要重新調整；自委託 RL 方法則需要額外的訓練成本與獎勵設計。論文也未深入探討當雲端 LLM 與本地 SLM 能力差距極大或極小時的行為，這些都是潛在的研究邊界。

**Q14：EdgeWise 在哪些情境下可能會失敗？**
A：當任務的步驟間耦合度極高、每一步都依賴前一步的細節推理時，EdgeWise 可能難以精準切割「可委託」與「不可委託」的邊界，導致委託過少而表現下降，或委託過多而失去成本優勢。此外，若本地 SLM 對任務領域完全不熟悉（例如高度專業的領域知識），其自主判斷可能不可靠，需要更頻繁地呼叫雲端。另一個潛在失敗情境是當雲端 LLM 的回應品質不穩定時，SLM 難以有效整合錯誤的修正結果，可能導致整個軌跡偏離。

**Q15：EdgeWise 未來可以朝哪些方向發展？**
A：未來方向包括：（1）將選擇性委託的概念擴展到多模態代理，處理影像、音訊等多種輸入；（2）探索更細粒度的委託機制，例如在單一步驟內部分委託（例如僅委託推理部分，動作生成仍由 SLM 完成）；（3）研究跨任務、跨領域的委託策略遷移，使 SLM 學到的委託模式更具泛化性；（4）結合聯邦學習或差分隱私技術，進一步強化邊緣-雲端協作中的資料保護。這些方向都可能將 EdgeWise 從「成本優化工具」推向「通用代理協作框架」。

## 實務應用指南

### 適用場景

**1. 企業內部程式碼助理與 CI/CD 自動化修復**
企業內部開發團隊可將 EdgeWise 部署於開發者工作站或內部伺服器，使用本地 SLM 處理日常的程式碼探索、檔案讀取、測試執行等例行步驟，僅在遇到複雜的錯誤根因分析、跨檔案重構或演算法設計等關鍵步驟時，才委託雲端前沿模型。這對於需要保護程式碼隱私（程式碼不外流到雲端）但又希望獲得前沿模型能力的金融機構、國防承包商或醫療軟體公司特別有價值。

**2. 邊緣裝置上的個人 AI 助理（NVIDIA DGX Spark 等本地工作站）**
個人開發者或研究者可在配備 NVIDIA DGX Spark 等邊緣運算硬體的工作站上部署 EdgeWise，將其作為日常編碼助理。對於長時間的軟體工程任務（如除錯、開發新功能、重構），本地 SLM 持續運作，僅在關鍵設計決策時呼叫雲端模型，可大幅降低 API 費用，同時維持與純雲端方案相當的任務完成率。

**3. 終端自動化與 DevOps 代理（Terminal-Bench 類任務）**
對於系統管理員、DevOps 工程師或 SRE 團隊，EdgeWise 可用於自動化終端操作任務，例如伺服器配置、批次部署腳本撰寫、系統故障排除等。本地 SLM 處理簡單的指令執行與狀態檢查，雲端 LLM 僅在需要深度推理的步驟（如分析複雜的系統日誌、規劃多步驟修復策略）介入。

**4. 深度研究與多步驟資訊蒐集代理**
對於需要長時間、多步驟的研究任務（如文獻回顧、技術調研、市場分析），EdgeWise 可讓本地 SLM 處理大量的網頁瀏覽、資料擷取、初步摘要等步驟，僅在需要深度推理、跨來源綜合分析或撰寫結論時委託雲端模型。這對於學術機構、智庫或新聞媒體特別實用。

**5. 邊緣運算環境中的機器人流程自動化（RPA）**
在工廠自動化、倉儲管理或遠端監控等場景中，邊緣裝置上的 SLM 可持續處理感測器資料、即時決策等低延遲需求，僅在遇到需要複雜規劃或異常處理的關鍵步驟時，才透過低頻寬連線委託雲端模型，兼顧即時性與模型能力。

### 實作前置條件

**資料需求**
- **長時程代理軌跡資料**：需要蒐集或生成大量長時程任務（如程式設計、終端操作）的成功與失敗軌跡，用於訓練 RL 策略。建議至少數千條完整軌跡，每條包含數十至數百個步驟。
- **步驟層級標註資料**：若採用外部判斷器式委託策略，需要標註每個步驟的「難度」或「是否需要 LLM」，可透過比較 SLM 與 LLM 在該步驟的表現差異來產生標籤。
- **獎勵訊號**：任務完成結果（如測試通過率、任務成功率）作為 RL 的稀疏獎勵；亦可設計步驟層級的密集獎勵（如執行回饋是否朝目標前進）。

**運算資源**
- **本地 SLM 部署**：需配備支援本地推論的硬體，建議使用 NVIDIA DGX Spark（GB10 Grace Blackwell）、配備 RTX 4090/5090 的工作站，或其他具備足夠 VRAM（建議 24GB 以上）的邊緣裝置。
- **RL 訓練資源**：步驟層級 RL 訓練需要大量 GPU 運算，建議使用多張 A100/H100 GPU 的訓練叢集。
- **雲端 LLM API 存取權限**：需要取得前沿模型（如 GPT-5.5、Claude 等）的 API 金鑰與配額。

**技能需求**
- **強化學習知識**：理解 PPO、GRPO 等策略最佳化演算法，以及信用分配（credit assignment）機制。
- **代理框架開發經驗**：熟悉 ReAct、Plan-and-Act 等代理範式，能夠建構任務執行環境與工具呼叫介面。
- **LLM 推論優化**：了解 vLLM、TGI、TensorRT-LLM 等推論引擎，能夠在本地高效部署 SLM。
- **雲端 API 工程**：能夠設計容錯、重試、流量控制的雲端呼叫機制。

### 實作步驟建議

**步驟一：定義長時程任務環境與評估基準**
選擇目標任務領域（如程式設計、終端操作），建構或採用現有的代理評估環境（如 SWE-Rebench、Terminal-Bench）。定義任務的初始狀態、可用工具、執行環境與成功標準。建議先在小型基準上驗證框架可行性，再擴展至完整基準。

**步驟二：部署本地 SLM 作為主要求解器**
選擇適合的開源 SLM（如 Qwen3.5-9B、Llama-3.1-8B 等），使用 vLLM 或 TensorRT-LLM 在本地裝置部署。設定代理迴圈：觀察環境 → 規劃下一步動作 → 執行動作 → 取得觀察 → 更新狀態。確認 SLM 在簡單步驟上已能達到可接受的表現。

**步驟三：設計委託決策機制**
根據需求選擇兩種策略之一：
- **外部判斷器式委託**：訓練或設計一個輕量級判斷器（可以是另一個小型模型或啟發式規則），根據當前狀態、步驟類型、SLM 信心度等訊號決定是否委託。
- **SLM 自主委託（推薦）**：在 SLM 的輸出中新增特殊的委託標記（如 `<DELEGATE>`），透過步驟層級 RL 讓 SLM 學會在何時輸出此標記。

**步驟四：設計上下文共享策略**
決定委託時應傳遞給雲端 LLM 的內容。論文中分析了完整上下文、最近 k 步上下文、摘要上下文等選項。建議從「最近 k 步 + 關鍵狀態摘要」開始，平衡資訊完整性與 token 成本。

**步驟五：實作步驟層級 RL 訓練（自主委託策略）**
設計獎勵函數：任務完成給予正向獎勵；每次委託給予負向成本獎勵（與 token 費用成正比）。採用 GRPO 或 PPO 進行策略最佳化，關鍵在於細粒度信用分配——將最終獎勵正確歸因到各個委託決策。建議使用群組相對優勢估計來穩定訓練。

**步驟六：建立雲端呼叫的容錯與成本控制機制**
實作 API 重試、逾時處理、速率限制等功能。設定每日/每月的預算上限，避免意外超支。記錄每次委託的成本與延遲，用於後續分析與優化。

**步驟七：端到端評估與調校**
在完整基準上評估 EdgeWise 的任務成功率與總推論成本。繪製 Pass@3–成本 trade-off 曲線，找出最佳的委託比例。根據失敗案例分析，調整委託策略、上下文設計或獎勵函數。

**步驟八：實際部署與監控**
將系統部署到目標邊緣裝置，設定監控儀表板追蹤任務成功率、平均成本、委託頻率等指標。建立回饋迴圈，持續蒐集實際使用資料以改進模型。

### 潛在風險與注意事項

**風險一：委託決策錯誤導致任務失敗**
若 SLM 在應該委託時未委託，或在不必要時過度委託，都會影響整體表現。**緩解措施**：採用保守的委託策略（傾向過度委託），並透過 RL 訓練持續優化；保留外部判斷器作為備援機制；設定信心度門檻，低信心度時自動委託。

**風險二：上下文共享不足導致雲端 LLM 表現下降**
若傳遞給雲端的上下文過於簡略，LLM 可能缺乏足夠資訊做出正確判斷。**緩解措施**：實驗不同的上下文策略（完整、最近 k、摘要），找出最佳平衡點；保留關鍵狀態資訊（如錯誤訊息、已嘗試的方案）。

**風險三：雲端 API 成本失控**
若委託頻率過高或單次委託的 token 數過大，可能導致成本超過預期。**緩解措施**：設定硬性預算上限與速率限制；監控每次委託的成本；設計獎勵函數時明確納入成本懲罰項。

**風險四：網路不穩定導致委託失敗**
邊緣裝置的網路連線可能不穩定，雲端 API 呼叫可能失敗或延遲過高。**緩解措施**：實作完善的重試與降級機制；委託失敗時自動切換回本地 SLM；設計非同步委託機制，避免阻塞本地執行。

**風險五：RL 訓練不穩定**
步驟層級 RL 的信用分配困難，訓練可能不穩定或收斂到次優策略。**緩解措施**：使用較小的學習率與梯度裁剪；採用群組相對策略最佳化（GRPO）而非標準 PPO；加入 KL 散度約束防止策略偏移過大；進行多次實驗取最佳結果。

**風險六：模型版本演進導致策略失效**
雲端 LLM 持續更新，原本針對特定版本最佳化的委託策略可能失效。**緩解措施**：定期重新評估與調整委託策略；設計模型無關的委託特徵（如步驟類型、任務難度）；保留人工覆寫機制。

### 與其他技術的整合建議

**與開源代理框架整合**
EdgeWise 可與 LangChain、AutoGen、CrewAI 等代理框架整合，作為其模型呼叫層的路由機制。建議將 EdgeWise 封裝為一個「模型路由器」元件，攔截框架的 LLM 呼叫請求，根據當前狀態決定使用本地 SLM 或雲端 LLM。

**與模型路由系統整合**
可與 RouteLLM、Router-R1、MERA 等現有路由系統結合。EdgeWise 專注於長時程任務的步驟層級委託，而這些系統擅長單查詢或多步驟的模型選擇。建議將 EdgeWise 作為長時程任務的專用路由器，與通用路由器互補。

**與 MLOps/LLMOps 平台整合**
將 EdgeWise 的訓練流程整合到現有的 ML 平台（如 Weights & Biases、MLflow），追蹤實驗、模型版本、評估指標。生產部署可整合到 Kubernetes 架構，本地 SLM 作為 sidecar 容器，雲端呼叫透過 API gateway 統一管理。

**與成本監控系統整合**
整合至企業的成本監控平台（如 CloudHealth、AWS Cost Explorer），追蹤每個任務、每個團隊的 LLM 使用成本。設定成本異常告警，並提供成本歸因報表。

**與程式碼助理工具整合**
對於程式設計場景，可與 GitHub Copilot、Cursor 等工具整合。EdgeWise 可作為這些工具的後端引擎，在 IDE 中提供長時程任務的自動化能力，同時降低 API 成本。

**與邊緣運算平台整合**
整合至 NVIDIA Metropolis、Azure IoT Edge 等邊緣運算平台，利用其裝置管理、模型部署、OTA 更新等功能，簡化 EdgeWise 在大規模邊緣裝置上的部署與維運。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）了解 EdgeWise 想要解決的問題——為什麼不是每個步驟都需要最強的模型。接著閱讀第 2 節（Observation）的圖 3，這個圖直觀展示了「只委託約 40% 的步驟給雲端，就能達到與全雲端方案相當的表現」，是理解整篇論文核心洞見的關鍵。最後閱讀圖 2 的範例軌跡，了解 EdgeWise 在實際任務中如何運作。論文中較深的 RL 訓練細節可以先略過，重點掌握「本地 SLM + 選擇性雲端委託」這個核心概念即可。

**給 AI 工程師**：建議重點閱讀第 3 節（Method），特別是兩種委託機制的設計——外部判斷器式委託與 SLM 自主委託。理解步驟層級 RL 的獎勵設計與信用分配機制是關鍵。此外，論文中關於「何時委託」、「如何委託」、「共享什麼上下文」、「委託頻率」的系統性分析（第 4 節的消融實驗）對實際系統設計非常有價值。實作時可先從外部判斷器式委託開始，驗證框架可行性後再投入 RL 訓練。

**給研究者**：建議完整閱讀論文，特別關注以下幾點：(1) 步驟層級 RL 的細粒度信用分配方法論，這是相較於 Router-R1、MERA 等現有方法的主要區別；(2) 委託決策的設計空間分析（when、how、what、how often），這為未來研究提供了系統性的框架；(3) 在 SWE-Rebench 與 Terminal-Bench 2.1 上的實驗設計與基準貢獻；(4) 圖 1 的 Pass@3–成本 trade-off 分析方法。建議進一步探索的方向包括：更複雜任務領域的泛化、多模態代理的委託策略、以及理論上對「關鍵步驟」的定義與分析。

**給產品經理**：建議先閱讀摘要與第 1 節，理解 EdgeWise 的商業價值——在維持任務表現的同時降低 46% 的推論成本（平均），這對於 LLM 應用的單位經濟性有重大影響。重點關注「實際部署驗證」（第 5 節），了解在真實邊緣-雲端設定中的可行性。思考 EdgeWise 如何應用於你們的產品：哪些場景涉及長時程任務？目前的 LLM 成本佔比是多少？EdgeWise 能在哪些場景帶來成本節省？建議與工程團隊討論實作的優先順序，從單一場景的 POC 開始驗證價值。
