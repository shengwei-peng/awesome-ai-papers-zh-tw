# 超越惡意性：代理技能的靜態與執行時攻擊面剖析

**原文標題：** Beyond Maliciousness: Static and Runtime Attack-Surface Profiling of Agent Skills  
**作者：** Ratnesh Pandey、Japneet Singh、Harsh Akshit 等 5 位作者  
**發布日期：** 2026-10-13  
**HF 連結：** [https://huggingface.co/papers/2610.19264](https://huggingface.co/papers/2610.19264)  
**arXiv：** [https://arxiv.org/abs/2610.19264](https://arxiv.org/abs/2610.19264)  

---

## ⚡ TL;DR

代理技能安裝時授予代理現有工作階段的授權，但現有權限模型幾乎失效，能力聲明與實際套件能力嚴重不符。
提出結合靜態分析、依賴來源檢查與沙盒執行的兩階段攻擊面剖析方法，涵蓋 6,309 個上架條目。
70.2% 條目具備提升權限能力，僅 770 個有聲明且 59% 低度聲明，凸顯能力剖析的必要性。

## 摘要翻譯

代理技能（Agent skill）是 Markdown 文檔，使用工具的代理（tool-using agent）會將其作為指令讀取，並以載入該技能之工作階段（session）的權限（privilege）行事。安裝此類技能即授予授權（authority，亦即指揮代理的地位，而非新增權限），而我們所測量的正是該授權的大小。我們提出一種兩階段攻擊面剖析方法論（two-phase attack-surface profiling methodology），結合全套件靜態分析（whole-bundle static analysis）與依賴來源檢查（dependency provenance checking），並輔以插裝式沙盒執行（instrumented sandbox execution），以及對所產生追蹤記錄（trace）的獨立基於模型之評估（model-based assessment）。我們將此方法論應用於兩個市集（marketplace）共 6,309 個上架條目（listing），在選擇上架條目進行執行時，並未以先前的威脅或風險信號（threat/risk signal）作為決策依據。語料庫（corpus）中有一半帶有 Shell 執行能力（shell-execution capability）的證據；對應的比例分別為：檔案系統讀取（filesystem read）35%、檔案系統寫入（filesystem write）與網路外連（network egress）各 31%、憑證存取（credential access）13%；每十個上架條目中有七個至少帶有一項提升權限能力（elevated capability）。這就是使用者在安裝時點（install time）所接受的攻擊面，而其中幾乎沒有任何部分是當時可見的。存在一個權限模型（permission model），但它幾近失效（inert）。作者（author）可在其技能的前言區塊（frontmatter）中列出該技能預先核准的工具（pre-approved tools），這會移除確認提示（confirmation prompt），但並未限制該技能可觸及之範圍；在前言區塊可解析的 6,061 個上架條目中，僅有 770 個有宣告任何內容，該詞彙（vocabulary）表無法表達憑證或環境存取（environment access），且沒有任何機制檢查其所宣告內容與套件（bundle）實際能力是否一致。宣告本身亦不準確：在有宣告的上架條目中，59% 低度聲明（under-declare）其套件實際所能執行之事。ClawHub 的宣告頻率約為 skillsmp 的兩倍，但在其宣告中有 88% 屬於低度聲明，相較於 skillsmp 的 31%。因此，在市集邊界（boundary）進行的分流（triage）不能依賴上架條目所宣告的內容，而必須依據套件實際所能執行之事。這些結果將能力導向的攻擊面剖析（capability-oriented attack-surface profiling）定位為惡意性偵測（maliciousness detection）的必要補充（complement）。

### 核心貢獻（3～5點）
- 提出兩階段攻擊面剖析方法論，整合全套件靜態分析、依賴來源檢查、插裝式沙盒執行與基於模型的評估四項技術
- 對兩個市集共 6,309 個上架條目進行大規模實證分析，量化各類能力（Shell 執行、檔案讀寫、網路外連、憑證存取）的分布與提升權限能力之普及率
- 系統性揭示現有權限模型之缺陷：詞彙表不完整、缺乏宣告與套件實際能力的一致性檢查、宣告普遍低度聲明（59%），且 ClawHub 與 skillsmp 之間存在顯著差異
- 論證市集邊界分流（triage）應以套件實際能力為依據，而非上架條目之宣告內容
- 將能力導向的攻擊面剖析定位為惡意性偵測之必要補充，確立其在代理技能安全生態系中的方法論地位

### 適合對象
從事 AI 代理安全、LLM 工具使用安全、軟體供應鏈安全、權限模型設計，以及 Markdown-based 指令套件審查之研究人員與工程師；亦適合關注 AI 生態系攻擊面量化、威脅建模與市集治理之資安從業者與政策制定者。

## 深度分析

#### 方法論解析

本論文提出一套**兩階段攻擊面剖析方法論**（two-phase attack-surface profiling methodology），用以系統性地評估代理技能（agent skill）在安裝時點所帶來的授權範圍。其核心設計理念在於：與其聚焦於「技能是否惡意」，不如量化「安裝此技能會帶入多少既有授權」。方法論由兩個互補階段組成：

**第一階段：靜態分析與依賴來源檢查（Static Analysis + Dependency Provenance Checking）**

此階段對整個技能套件（whole-bundle）進行靜態掃描，涵蓋 SKILL.md 主文件以及隨附的腳本與資料檔案。靜態分析的目的並非判斷意圖，而是從程式碼與指令中萃取**能力指紋**（capability fingerprint），識別套件可能動用的動作類別，包括：
- Shell 執行能力（shell-execution capability）
- 檔案系統讀取（filesystem read）
- 檔案系統寫入（filesystem write）
- 網路外連（network egress）
- 憑證存取（credential access）

同時進行**依賴來源檢查**，追蹤套件所引用的外部函式庫、腳本或資料的來源（provenance），以判斷其供應鏈是否引入額外的潛在攻擊面。此階段的關鍵設計選擇是「**不以先驗威脅或風險信號作為篩選條件**」（without conditioning that decision on a prior threat or risk signal），即對所有上架條目一視同仁地進行剖析，避免選擇偏差（selection bias）導致對攻擊面規模的低估。

**第二階段：插裝式沙盒執行與基於模型的追蹤評估（Instrumented Sandbox Execution + Model-based Trace Assessment）**

此階段將選定的上架條目部署至受監控的沙盒環境中實際執行，並透過插裝（instrumentation）機制記錄所有系統呼叫、檔案存取與網路行為，產出**執行追蹤記錄**（execution trace）。這些追蹤記錄隨後被送交一個**獨立的模型**進行評估，模型的角色是從行為序列中萃取能力證據，而非判斷惡意性。這種「靜態推論 + 動態驗證」的雙軌設計，能有效降低單一方法的誤判率：靜態分析可能因程式碼混淆或動態載入而漏報，動態執行則可能因觸發條件未滿足而未展現全部能力。

**方法論的核心概念區分**

論文嚴謹地劃分了四個易混淆的術語：
- **能力（capability）**：套件可能動用的動作，由證據推論而得
- **攻擊面（attack surface）**：能力的集合與其覆蓋範圍
- **風險（risk）**：基於攻擊面範圍與放大因子（amplification factors）所評估的嚴重程度
- **威脅（threat）**：惡意意圖的證據

此區分至關重要，因為論文的中心論點正是：**能力本身不等於惡意**，但能力的規模決定了安裝時的暴露程度。一個完全良意的技能仍可能帶入大量授權，成為「困惑代理人」（confused deputy）攻擊的媒介。

**權限模型的剖析**

方法論亦對 Agent Skills 規範中的 `allowed-tools` 前言區塊（frontmatter）進行結構化分析，檢驗其是否能反映套件的實際能力。論文指出三項結構性缺陷：
1. **詞彙不足**：該欄位無法表達憑證存取或環境變數存取
2. **無驗證機制**：沒有任何檢查機制比對宣告內容與套件實際行為
3. **語意誤導**：在某些代理實作中，宣告預先核准的工具僅是**移除確認提示**，而非限制可呼叫的工具範圍

#### 實驗數據解讀

論文將方法論應用於 **6,309 個上架條目**，來源涵蓋兩個市場（ClawHub 與 skillsmp），實驗結果揭示了多層次的發現：

**能力分布的量化結果**

| 能力類型 | 占比 |
|---------|------|
| Shell 執行 | 50% |
| 檔案系統讀取 | 35% |
| 檔案系統寫入 | 31% |
| 網路外連 | 31% |
| 憑證存取 | 13% |
| 至少一項提升權限能力 | 70.2%（4,431 個技能） |

這些數據的意涵在於：**七成以上的上架條目在安裝時即帶入至少一項提升權限能力**，而其中超過半數具備 Shell 執行能力，這是最具放大效應的能力——一旦代理在 Shell 環境中執行任意指令，所有作業系統層級的邊界控制都可能被繞過。13% 的憑證存取比例雖然看似較低，但考慮到憑證通常具備橫向移動（lateral movement）與持久化（persistence）的潛力，其風險權重應遠超表面占比。

**三層屬性的對比（Fig. 1）**

論文以同一語料庫的三個不同屬性進行對比：
- **提升權限能力**：70.2%（4,431 個技能）
- **高暴露程度**：25.7%（1,621 個技能）
- **威脅判定**：5.4%（338 個技能）

此對比是論文最具說服力的視覺化證據：**能力、暴露與威脅之間存在巨大的數量落差**。換言之，若僅以惡意性偵測作為市場邊界的審查標準，將有近 70% 的高能力技能完全處於審查盲區，其中四分之一更被評估為高暴露風險，但僅有 5.4% 會被標記為威脅。

**權限宣告的失能狀態**

在 6,061 個可解析前言區塊的上架條目中：
- 僅 **770 個（12.7%）** 宣告了任何工具
- **59% 的宣告者少報**（under-declare）其套件實際能力
- ClawHub 的宣告率約為 skillsmp 的兩倍，但**少報率達 88%**，遠高於 skillsmp 的 31%

此數據揭示了一個反直覺的現象：**更頻繁地宣告並不代表更誠實地宣告**。ClawHub 的高宣告率伴隨著極高的少報率，暗示該平台的作者可能將 `allowed-tools` 視為「形式上的合規」而非「實質的能力聲明」，甚至可能利用宣告行為來營造透明假象。skillsmp 雖較少宣告，但少報率較低，顯示其作者群體在宣告時較為準確（或較不傾向於系統性地隱藏能力）。

**方法論選擇的意涵**

論文強調「**不以先驗威脅或風險信號作為執行篩選條件**」，這是一個重要的方法論選擇。若僅對已被標記為可疑的技能進行動態分析，將無法回答「整體生態系統的攻擊面有多大」這個問題。這種**無條件抽樣**（unconditional sampling）設計使結果具有生態系統層級的代表性，而非僅反映已知的威脅子集。

#### 與現有研究的比較

本論文在快速發展的代理技能安全研究領域中佔據獨特位置，需與三類既有研究進行比較：

**與靜態惡意性研究的比較**

先前的大規模靜態研究（如對 31,132 個技能的分析）報告約四分之一帶有漏洞模式、約二十分之一顯示可能的惡意意圖。本論文與此類研究的關鍵差異在於**研究問題的轉向**：既有研究問的是「這個技能是否想造成傷害」，本論文問的是「安裝這個技能會帶入多少授權」。兩者並非競爭關係，而是互補——惡意性偵測能識別意圖，攻擊面剖析能量化暴露。論文的結論明確指出，能力導向的剖析是惡意性偵測在市場邊界的**必要補充**（necessary complement）。

**與引爆（detonation）研究的比較**

既有引爆研究在受控環境中實際執行技能並確認了 157 個惡意技能。本論文的沙盒執行階段在方法論上與引爆研究相似，但目的不同：引爆研究旨在確認惡意行為，本論文旨在萃取能力證據。此外，本論文的執行是**非條件式**的，不預先假設技能可疑，這使其結果更接近生態系統的真實分布。

**與採用趨勢研究的比較**

論文引用了多項採用趨勢數據：2025 年 12 月一個市場有 15,082 個技能，一個月後增至 73,193，至 2026 年 3 月跨三平台與 GitHub 統計達 238,180 個唯一技能。這種爆炸性成長意味著任何基於人工審查的安全機制都將迅速失效，凸顯了**自動化攻擊面剖析**的必要性。

**本研究的獨特貢獻**

1. **概念框架的清晰化**：嚴格區分能力、攻擊面、風險與威脅四個概念，避免術語混淆導致的安全決策失誤
2. **雙階段方法論的整合**：結合靜態與動態分析，兼顧覆蓋率與準確性
3. **權限模型的形式化評估**：首次系統性地量化 `allowed-tools` 欄位的失能程度
4. **市場層級的實證**：跨兩個市場的比較揭示了平台間的差異（如 ClawHub 與 skillsmp 的宣告行為對比）

**論文的局限性**

- **樣本偏差**：雖然語料庫規模可觀（6,309 個），但僅涵蓋兩個市場，可能無法代表整個生態系統
- **動態分析的覆蓋限制**：沙盒執行受限於觸發條件，未被實際呼叫的能力可能被低估
- **模型評估的可重現性**：第二階段使用「獨立的模型」進行追蹤評估，但未明確說明模型類型、規模或評估標準，這影響結果的可驗證性
- **時間快照**：攻擊面是動態變化的，單一時間點的剖析可能無法反映技能的演變
- **未涵蓋的攻擊面類型**：論文聚焦於五類核心能力，但代理技能可能涉及更多維度，如 GPU 存取、硬體介面、跨代理通訊等

#### 可重現性評估

論文的可重現性呈現**部分透明**的狀態，需從多個面向評估：

**正面因素**

- **語料庫規模與來源明確**：6,309 個上架條目來自兩個具名市場（ClawHub 與 skillsmp），便於其他研究者進行獨立驗證或擴展研究
- **方法論描述詳盡**：兩階段方法論的設計理念、執行流程與篩選原則均有清楚說明
- **量化指標具體**：所有關鍵指標（能力占比、宣告率、少報率）均以絕對數值與百分比雙重呈現
- **概念定義嚴謹**：術語表（glossary）明確區分能力、攻擊面、風險與威脅，有助於後續研究的方法論對齊

**可重現性的挑戰**

- **程式碼與工具未公開聲明**：論文中未明確提及是否釋出分析工具、沙盒環境或靜態分析器，這是評估可重現性的關鍵缺口
- **模型細節不足**：第二階段使用的「獨立模型」未指定具體模型（如 GPT-4、Claude 或開源模型）、提示工程（prompt engineering）細節或評估協議，這使得追蹤評估的結果難以獨立重現
- **沙盒配置未詳述**：插裝式沙盒的具體配置（作業系統版本、系統呼叫過濾規則、網路模擬方式）未在提供的文本中說明
- **依賴來源檢查的標準**：供應鏈檢查的具體規則集或資料庫來源未明確引用
- **前言區塊解析的容錯處理**：6,061 個可解析條目意味著有 248 個解析失敗，但失敗原因與處理方式未說明

**改善建議**

若要提升可重現性，論文應補充：
1. 靜態分析器的開源釋出與規則集文件
2. 沙盒環境的完整配置與插裝腳本
3. 模型評估的提示模板、模型版本與評估者間一致性（inter-rater reliability）指標
4. 解析失敗條目的分類統計
5. 兩個市場的資料快照時間與擷取方法

#### 未來研究方向

本論文開啟了多個值得深入探索的研究方向：

**1. 動態攻擊面演化追蹤**

代理技能的攻擊面並非靜態——作者會更新技能、引入新依賴、修改指令。建構**縱貫性追蹤研究**（longitudinal study），對同一技能的多次版本進行攻擊面比對，將能揭示攻擊面的演化模式與惡意技能的「潛伏期」特徵。這對於早期預警系統的設計至關重要。

**2. 攻擊面與實際利用的關聯模型**

本論文量化了能力與暴露，但未直接連結到**實際的利用事件**。未來研究可建構從「能力存在」到「實際被利用」的機率模型，識別哪些能力組合最具攻擊價值，哪些是「紙面上危險但實務中難以利用」的能力。這需要與入侵偵測系統（IDS）日誌或威脅情資（threat intelligence）進行關聯分析。

**3. 權限模型的重新設計**

論文明確指出當前 `allowed-tools` 機制的三大缺陷（詞彙不足、無驗證、語意誤導）。未來工作可設計**以能力為中心的宣告語言**（capability-centric declaration language），使其能表達憑證存取、環境變數、跨代理通訊等維度，並內建**形式化驗證機制**（formal verification），自動比對宣告與套件實際行為。這需要跨學科合作，結合程式語言理論、形式化方法與人機互動設計。

**4. 市場層級的信任框架**

論文揭示了 ClawHub 與 skillsmp 在宣告行為上的顯著差異。未來研究可探索**市場層級的信任機制**，例如：
- 第三方能力認證（third-party capability certification）
- 聲譽系統（reputation system）整合攻擊面歷史
- 漸進式權限授予（progressive permission granting），根據能力剖析結果建議使用者採取不同的確認策略

**5. 代理感知的安全分析**

本論文將技能視為被動的程式碼，但代理技能的核心特性是**被代理「讀取並遵循」的指令**。這意味著技能的「行為」不僅來自腳本，還來自 LLM 對 Markdown 指令的詮釋。未來研究可探索**代理感知的安全分析**（agent-aware security analysis），模擬不同代理在載入技能後的行為差異，識別「指令注入」（prompt injection）與「指令混淆」（instruction confusion）等新型攻擊面。

**6. 跨平台與跨代理的可移植性**

不同代理實作對 `allowed-tools` 的解讀不同（如某些將其視為限制，某些視為預先核准）。未來研究可系統性地映射**代理實作差異**（agent implementation divergence），建立代理安全行為的基準測試（benchmark），使攻擊面剖析能考慮部署環境的具體控制。

**7. 使用者決策支援**

最終，攻擊面剖析的目的是協助使用者做出更好的安裝決策。未來研究可探索**使用者介面設計**，將複雜的能力剖析結果轉化為可理解的風險指標，並研究不同的呈現方式（如圖示、顏色編碼、文字摘要）對使用者決策品質的影響。這需要結合資訊安全與行為科學的跨領域方法。

**8. 對抗性攻擊面規避**

若攻擊面剖析成為市場邊界的標準做法，惡意作者將嘗試**規避偵測**（evasion）。未來研究應預先考慮對抗情境，例如：
- 將惡意能力編碼於自然語言指令中而非程式碼
- 利用動態載入、延遲執行或環境條件觸發來躲避靜態分析
- 將惡意行為分散於多個互依的技能中

這需要發展**對抗穩健的剖析方法**（adversarially robust profiling methods），類似於對抗機器學習中的防禦技術。

**9. 標準化與生態系統治理**

最後，本論文凸顯了缺乏標準化安全機制的問題。未來工作可推動**產業標準的制定**，包括：
- 技能套件的能力宣告標準
- 市場上架的安全審查流程
- 跨市場的威脅情資共享機制

這需要學術界、產業與政策制定者的協作，以建立可持續的生態系統安全治理框架。

## 論文問答

**Q1：這篇論文主要解決什麼問題？**
A：這篇論文聚焦於「代理技能」（agent skills）的安全評估問題，特別是安裝一個技能時究竟授予了多少授權（authority）。作者指出，現有研究多聚焦於「這個技能是否企圖造成傷害」（惡意性偵測），但忽略了一個對使用者而言更關鍵的問題：「安裝這個技能會帶進多少能力？」。論文的核心理念是，一個完全良性的技能仍可能擴展代理可執行的動作範圍，因為技能會在代理既有工作階段的權限下運作。這種「能力足跡」（capability footprint）才是安裝決策時應該被評估的真正對象。

**Q2：為什麼現有的惡意性偵測方法不足以保護使用者？**
A：現有方法主要回答「這個技能是否企圖造成傷害」，但無法回答「安裝後會帶進多少授權」。論文的實證顯示，70.2% 的上架條目帶有至少一項提升權限能力，但僅有 5.4% 被判定為帶有威脅意圖，兩者之間存在巨大落差。此外，現有的權限模型幾乎處於失效狀態：技能前言區塊（frontmatter）中的「預先核准工具」清單只是用來移除確認提示，並非真正限制技能能觸及的能力；詞彙本身無法表達憑證或環境存取，且沒有任何機制檢查宣告內容是否與套件實際能力一致。因此，僅依賴惡意性偵測會讓絕大多數具有實質攻擊面的技能逃過審查。

**Q3：為什麼這個問題在當前特別重要？**
A：代理技能的採用速度極快，從 2025 年 12 月單一市集約 15,082 個技能，到一個月後成長至 73,193 個，至 2026 年 3 月跨三個平台與 GitHub 已累計 238,180 個獨立技能。安裝流程僅要求使用者核准檔案複製本身，並不對技能實際能行使的能力進行任何審查，這代表使用者預設信任了所有安裝內容。更令人憂心的是，這些能力在安裝時點幾乎完全不可見——七成條目帶有提升權限能力，但市集邊界缺乏有效的分流機制，使得攻擊面的可見性與實際風險嚴重脫節。

**Q4：論文的兩階段方法論具體包含哪些步驟？**
A：第一階段是靜態分析，包含對整個套件（whole-bundle）的靜態檢查以及依賴來源（dependency provenance）檢查，目的是從程式碼與相依性中推論技能可能行使的能力。第二階段則是執行時分析，在插裝式沙盒（instrumented sandbox）中實際執行上架條目，並透過獨立的基於模型的評估來檢視產生的追蹤記錄（trace）。這種「靜態＋執行時」的組合能同時捕捉程式碼層面的能力聲明與實際執行時展現的行為，避免單一分析方法造成的盲區。

**Q5：這篇論文相較於過往研究的核心創新是什麼？**
A：核心創新在於將評估重心從「惡意意圖」轉向「能力導向的攻擊面剖析」（capability-oriented attack-surface profiling）。作者刻意在選擇執行哪些上架條目時，不以其是否帶有先驗威脅或風險信號為條件，這種「無條件抽樣」避免了確認偏誤（confirmation bias），使得能力足跡的測量能反映整體市集的真實分布。此外，將「威脅」（threat）、「攻擊面」（attack surface）與「風險」（risk）三個概念明確區分開來，是方法論上的重要釐清，有助於後續研究建立更精確的評估框架。

**Q6：方法論中有哪些關鍵的設計選擇值得深入探討？**
A：首先是「整個套件」而非僅 SKILL.md 的靜態分析範圍，因為技能常附帶腳本與資料，僅檢查 Markdown 指令會遺漏大量能力來源。其次是將「來源檢查」納入靜態階段，以評估依賴項的可信度，這對判斷供應鏈風險至關重要。第三，執行時階段採用「插裝式沙盒」並由獨立模型評估追蹤記錄，這種分離設計減少了評估者本身偏見對結果的污染。最後，方法論刻意不對上架條目施加威脅預過濾，這個選擇讓 5.4% 的威脅判定率與 70.2% 的能力足跡率得以被公平地並列比較。

**Q7：實驗所使用的資料集規模與組成為何？**
A：研究團隊從兩個市集（ClawHub 與 skillsmp）蒐集了 6,309 個上架條目作為分析語料庫。其中 6,061 個條目的前言區塊能成功解析，770 個條目有宣告任何內容。這個資料規模足以支撐統計推論，且涵蓋兩個風格迥異的市集——ClawHub 的宣告頻率約為 skillsmp 的兩倍，但低度聲明率卻高達 88%，遠高於 skillsmp 的 31%，呈現出市集層級的系統性差異。

**Q8：實驗揭露了哪些關鍵的量化結果？**
A：最關鍵的數字是：50% 的上架條目帶有 Shell 執行能力證據，35% 帶有檔案系統讀取能力，31% 各帶有檔案系統寫入與網路外連能力，13% 帶有憑證存取能力；70.2% 至少擁有一項提升權限能力，25.7% 被判定為高曝險，僅 5.4% 帶有威脅意圖判定。在宣告準確性方面，59% 的宣告條目少報了其套件實際能做的事，而 ClawHub 的 88% 與 skillsmp 的 31% 之間的落差，更凸顯市集層級治理差異對使用者曝險的直接影響。

**Q9：不同市集之間的比較能否視為一種「自然對照」？**
A：可以視為某種程度的對照實驗，因為 ClawHub 與 skillsmp 在宣告頻率與準確性上呈現鮮明對比：ClawHub 宣告頻率約為 skillsmp 的兩倍，但低度聲明率卻是 skillsmp 的近三倍（88% vs 31%）。這個落差說明「鼓勵宣告」本身並不等於「提升安全性」——若缺乏對宣告內容與套件實際能力的比對機制，更多的宣告反而可能製造虛假的安全感。此外，兩市集在威脅判定率上的差異也提供了市集治理政策對安全結果影響的初步證據。

**Q10：這項研究對市集審查流程有哪些實務意涵？**
A：研究結果直接挑戰了「以宣告內容進行分流」的現行做法，因為宣告既不完整也不準確，市集邊界的分流必須改為以套件實際能做的事為基礎。這意味著市集需要導入自動化的能力剖析管線，在上架時即對每個技能進行靜態與執行時分析，而非僅依賴作者自我宣告。同時，25.7% 的高曝險比例顯示，目前的審查漏掉了大量實質風險，必須將能力剖析列為必備的審查環節，而非可選的補充工具。

**Q11：對代理框架（harness）與權限模型的設計有何產品層面的啟示？**
A：產品設計上需要重新思考「預先核准工具」清單的語意——目前它只是用來略過確認提示，但被誤認為是限制機制，這種「介面誤導」是嚴重的可用性問題。詞彙需要擴充以涵蓋憑證與環境存取，否則使用者與審查者都無法表達或檢查這些高敏感能力。更根本地，框架應引入「宣告驗證」機制，自動比對前言區塊宣告的工具與套件實際可呼叫的能力是否一致，否則 59% 的少報現象將持續存在。

**Q12：這項研究對整個領域的長遠影響為何？**
A：論文將「能力導向的攻擊面剖析」定位為惡意性偵測的必要補充，這個定位為後續研究建立了一個新的研究軸線：安全評估不僅要問「是否惡意」，更要問「授予多少授權」。這個框架可應用於其他類似的可信程式碼生態系（如瀏覽器擴充功能、VS Code 套件、CI/CD 動作），因為它們都面臨類似的「安裝即信任」問題。此外，作者明確區分 capability、attack surface、risk、threat 等概念，有助於領域內建立更精確的術語共識，避免未來研究中概念混淆。

**Q13：論文本身承認了哪些研究限制？**
A：作者明確指出，能力剖析僅回答「套件可能帶進什麼能力」，並不等同於「代理會安全地使用這些能力」。安全運作還取決於授權政策、隔離機制，以及執行時的動作控制——這些都超出能力剖析的範疇。此外，方法論仰賴沙盒執行與模型評估，這兩者都可能受到環境繞過或評估偏誤的影響。最後，研究聚焦於兩個市集，結論是否能外推至其他技能生態系仍需驗證。

**Q14：在哪些情況下這套方法論可能會失效或產生誤判？**
A：當技能使用高度混淆或編碼手段時，靜態分析可能無法正確推論其能力；執行時分析則受限於沙盒環境，若技能偵測到沙盒並改變行為（即「沙盒感知」），追蹤記錄將無法反映真實執行狀況。此外，詞彙無法表達憑證或環境存取這項限制，意味著即使是「完整且準確」的宣告，仍無法涵蓋所有高風險能力，這是權限模型本身的結構性缺陷。最後，模型評估階段的判斷標準若未與領域專家充分校準，可能在新型攻擊手法出現時產生系統性偏差。

**Q15：基於這些發現，未來有哪些值得探索的研究方向？**
A：未來可朝幾個方向推進：首先，設計能真正「限制」而非僅「預先核准」的能力邊界機制，例如基於能力宣告的系統呼叫過濾或強制最小權限的沙箱配置。其次，擴充權限詞彙以涵蓋憑證、環境變數、敏感 API 等目前無法表達的維度，並建立宣告與套件內容的自動比對機制。第三，將能力剖析整合進代理框架的安裝流程，讓使用者在安裝時即看到具體的能力清單而非僅有作者自述。最後，跨市集、跨生態系的大規模縱向研究將有助於理解技能攻擊面的演化趨勢與防禦策略的長期有效性。

## 實務應用指南

### 適用場景

1. **代理技能市集上架審查（Marketplace Pre-publication Review）**：在 ClawHub、skillsmp 等市集將第三方技能上架前，自動執行兩階段剖析，產生「能力指紋」與「暴露等級」標籤，作為人工審查的客觀依據。論文顯示 70.2% 的上架條目帶有至少一項提升權限能力，僅靠作者自填的 `allowed-tools` 會漏掉 88%（ClawHub）至 31%（skillsmp）的實際能力。

2. **企業內部代理部署前的供應商風險評估（Enterprise Skill Vetting）**：金融、醫療等受監管產業在導入第三方代理技能前，將 SKILL.md 與其附帶腳本送入剖析流程，產出符合內部資安政策的「能力白名單／黑名單」對照表，避免將具備 Shell 執行或網路外連能力的技能部署到處理敏感資料的代理工作階段。

3. **CI/CD 中的技能安裝守門員（Pipeline Gate）**：在開發者於 IDE 或自動化流程中 `install skill <name>` 之前，攔截該指令並對技能套件執行靜態掃描；若偵測到未宣告的 Shell 執行、憑證存取或網路外連能力，阻擋安裝並提示風險摘要。

4. **已安裝技能的盤點與持續監控（Installed Skill Inventory & Drift Detection）**：定期對代理工作階段中已載入的技能重新剖析，比對新版本或上游更新是否引入新的能力（例如從純檔案讀取升級為網路外連），作為組態漂移偵測的一部分。

5. **事件回應中的技能鑑識（Incident Response Forensics）**：當代理發生可疑行為（例如非預期的對外連線、敏感檔案外洩）時，對當下載入的所有技能執行回溯剖析，根據執行追蹤記錄（trace）與靜態能力指紋判定哪個技能是「被授予權限」的可疑來源，區分「惡意意圖」與「能力被濫用」兩種情境。

### 實作前置條件

**資料面**
- 至少一個代理技能市集的完整上架清單（含 SKILL.md 與附帶腳本的原始套件），論文使用 6,309 條來自兩個市集的樣本。
- 技能的 `frontmatter`（YAML 前言區塊）解析結果，用於比對「宣告」與「實際能力」。
- 選用：依賴套件的來源資訊（Git commit hash、套件登錄帳號、首次發布時間）以支援「依賴來源檢查」。

**運算與基礎設施**
- 隔離的沙盒環境（容器或微型 VM），需具備完整的系統呼叫與網路流量插裝能力，能在執行技能腳本時擷取檔案讀寫、網路外連、Shell 呼叫、憑證／環境變數存取等事件。
- 靜態分析引擎：能對 Markdown、Shell、Python、JavaScript 等常見技能腳本語言進行語法樹與危險 API 模式比對。
- 一個獨立的「基於模型的評估」通道（可使用 LLM），用於解讀執行追蹤記錄並產出威脅／暴露判定；該模型應與代理本體解耦，避免評估結果被代理上下文污染。

**技能與角色**
- 具備靜態分析、動態插裝、LLM 評估三條管線整合經驗的工程團隊。
- 對 Agent Skills 規範（`SKILL.md`、`allowed-tools` 欄位語意）有正確認知，避免把「預先核准」誤讀為「權限限制」。
- 資安人員能定義「提升權限能力」的組織特定閾值（例如：哪些 API 視為憑證存取）。

### 實作步驟建議

**步驟 1：建立能力分類法（Capability Taxonomy）**
依照論文的四類核心能力——Shell 執行、檔案系統讀取、檔案系統寫入、網路外連、憑證／環境存取——定義每類的靜態特徵（例如：`subprocess`、`os.system`、`requests.`、`open(..., 'w')`、`os.environ`、`~/.aws/credentials`）與動態特徵（系統呼叫、檔案事件、socket 連線）。

**步驟 2：實作第一階段——全套件靜態分析與依賴來源檢查**
- 對整個技能目錄（含 SKILL.md 與所有附帶檔案）執行靜態掃描，輸出每個條目的能力集合。
- 解析 frontmatter 中的 `allowed-tools` 宣告，記錄「宣告集合」與「靜態推論集合」的差異。
- 對腳本中引用的外部依賴（pip、npm 套件）記錄來源、版本與首次出現時間，標記可疑或新建立的依賴。

**步驟 3：實作第二階段——插裝式沙盒執行**
- 將技能載入隔離沙盒，使用一個最小化的代理驅動程式（driver）依照 SKILL.md 的指令序列執行腳本。
- 插裝層需獨立於代理本體，僅記錄「能力是否被實際呼叫」與呼叫的參數摘要，不允許沙盒內的程式影響評估通道。
- 對無法在沙盒內執行的技能（例如需要特定硬體或外部服務），仍保留靜態結果並標記為「僅靜態」。

**步驟 4：獨立的模型評估通道**
- 將靜態特徵、依賴來源、沙盒追蹤記錄三項輸入送入一個獨立的 LLM 評估器，產出三個量值：威脅（惡意意圖證據）、攻擊面（能力足跡）、風險（暴露嚴重度）。
- 評估器提示詞應明確區分「能力存在」與「意圖為惡意」，避免將高能力誤判為高威脅。

**步驟 5：產品化整合**
- 將兩階段結果封裝為一個可呼叫的剖析 API（輸入：技能套件路徑或市集條目 ID；輸出：能力集合、宣告差異、暴露等級、威脅判定）。
- 在市集上架流程、安裝指令、CI/CD 守門員三個節點掛接此 API。
- 提供人類可讀的風險摘要面板，列出「未宣告的能力」與「被低估的能力」，作為審查者決策依據。

**步驟 6：校準與回饋迴圈**
- 以論文中 70.2%／25.7%／5.4% 的三層比例（提升權限能力／高暴露／威脅判定）作為基準，監測自家管線的分布是否偏離過遠。
- 收集誤判案例（特別是「宣告低估」案例），回頭更新靜態特徵庫與評估提示詞。

### 潛在風險與注意事項

1. **把「能力」誤當成「威脅」**：論文明確區分 capability 與 threat——70.2% 的條目帶有提升權限能力，但僅 5.4% 帶有威脅判定。實作時若把能力指紋直接當作阻擋條件，會誤殺大量良性但功能完整的技能（例如需要 Shell 執行的部署工具）。**緩解**：能力指紋僅作為「需人工審查」或「需使用者明確同意」的觸發條件，不直接阻擋。

2. **沙盒逃逸與插裝盲點**：技能若偵測到沙盒環境（例如檢查 `/proc`、時序差異）可能改變行為，使追蹤記錄失真。**緩解**：使用硬體隔離或不可觀測的插裝層；對「沙盒內無行為」的條目保留靜態結果並標記為「未經執行驗證」。

3. **評估模型的幻覺與偏誤**：用 LLM 解讀追蹤記錄時，模型可能對模糊證據過度解讀為惡意，或對巧妙偽裝的惡意技能給出過低評分。**緩解**：要求評估器輸出「證據引用」而非僅給結論；對高風險判定保留人工覆核。

4. **frontmatter 詞彙表不足**：論文指出 `allowed-tools` 的詞彙無法表達憑證或環境存取，且無任何機制檢查宣告是否符合套件實際內容。**緩解**：不要把作者的宣告當作信任依據；剖析結果應以「套件能做什麼」為主、「作者說能做什麼」為輔。

5. **市集間的差異**：ClawHub 與 skillsmp 在宣告頻率與低估率上差異顯著（88% vs 31%），單一市集校準出的閾值無法直接套用到另一個。**緩解**：以市集為單位維護閾值與基準分布。

6. **技能快速演進導致的剖析過時**：技能被複製、修改、上游更新的速度很快，靜態特徵庫容易過期。**緩解**：對每次安裝或更新都重新剖析，而非快取結果。

### 與其他技術的整合建議

- **SBOM（軟體物料清單）工具**：將技能套件視為一種軟體供應物，把剖析出的能力集合與依賴來源輸出為 SBOM 格式（SPDX / CycloneDX），與企業既有的軟體組成分析工具對接。
- **SIEM 與 EDR**：把沙盒執行階段擷取的系統呼叫與網路事件以 Syslog / OCSF 格式送入 SIEM，與代理工作階段的執行記錄關聯，便於事件回應時快速定位「哪個技能授予了這項權限」。
- **身分與存取管理（IAM）**：對被剖析出「憑證存取」能力的技能，要求其執行環境綁定最小權限的服務帳號，並透過短期憑證取代長期金鑰，降低「被授予權限」後的實際暴露。
- **政策即程式碼（Policy-as-Code）**：將剖析結果以結構化政策（例如 OPA / Rego）形式表達，例如「禁止安裝同時具備 Shell 執行與網路外連且未宣告的技能」，在 CI/CD 守門員中強制執行。
- **代理沙盒與權限控管**：剖析結果可作為代理執行環境隔離策略的輸入——對高暴露技能強制使用更嚴格的網路 egress 限制或檔案系統唯讀掛載，而非僅依賴代理本身的工具呼叫審核。
- **威脅情報平台**：將剖析出的「常見能力組合」與「常見低估模式」回饋到威脅情報平台，作為新進技能比對的基準。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與第一節的「術語」段落，掌握「能力（capability）」、「攻擊面（attack surface）」、「威脅（threat）」、「風險（risk）」四個詞在本文中的精確定義——它們不是同義詞。接著看圖 1 的三層比例（70.2%／25.7%／5.4%），這是整篇論文的視覺化核心：大多數技能帶有權限能力，但只有少數帶有惡意意圖，這正是「超越惡意性」標題的由來。

**給 AI 工程師**：重點關注方法論章節（兩階段剖析的具體管線：靜態分析 → 依賴來源檢查 → 插裝沙盒執行 → 獨立模型評估）。特別注意「評估通道與代理本體解耦」的設計——這是避免評估結果被代理上下文污染的關鍵工程決策。實作時可直接借用論文的能力分類法作為靜態特徵庫的起點。

**給研究者**：本文最大的貢獻是把「能力剖析」與「惡意性偵測」明確切開，並用 6,309 條實證資料展示現有權限模型（`allowed-tools`）的失效程度。可延伸的研究方向包括：能力組合的風險評分模型、跨市集的技能重用與變體追蹤、評估模型的可重現性研究，以及把這套方法套用到 MCP 工具描述等其他代理擴充機制。

**給產品經理**：這篇論文回答的是「使用者安裝技能時實際交出了多少權限」，這是任何代理平台都必須面對的產品決策。核心訊息是：現有的權限 UI（`allowed-tools` 勾選框）幾乎是裝飾性的，因為作者可以少報、詞彙表無法表達關鍵能力、系統不會驗證宣告。產品上需要的是「安裝前的能力摘要」與「基於套件實際內容而非作者宣告」的審查流程，而不是更花俏的權限對話框。
