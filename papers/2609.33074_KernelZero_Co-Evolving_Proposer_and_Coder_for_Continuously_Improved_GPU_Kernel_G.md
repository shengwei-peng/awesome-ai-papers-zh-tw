# KernelZero：共同演化 Proposer 與 Coder 以持續改進 GPU 核心生成

**原文標題：** KernelZero: Co-Evolving Proposer and Coder for Continuously Improved GPU Kernel Generation  
**作者：** Changxin Ke、Rui Zhang、Zixiang Fang 等 11 位作者  
**發布日期：** 2026-09-27

## ⚡ TL;DR

現有 LLM 難以同時生成正確且高效的 GPU 核心，且缺乏與模型能力對齊的訓練資料。
KernelZero 讓 Proposer 與 Coder 共同演化，並以 CA-GRPO 先保正確再優效能。
KernelZero-7B 在核心生成上超越多個頂尖大模型，pass@1 逾七成且 pass@10 近滿分。

---

## 摘要翻譯

高效能 GPU 核心（GPU kernel）對現代機器學習系統（machine learning systems）至關重要，然而自動生成兼具正確性與效率的核心仍具挑戰性。現有基於大型語言模型（LLM）的方法面臨兩大侷限：高品質且與模型當前能力對齊（capability-aligned）的訓練資料稀缺，以及固有的正確性與效能權衡（correctness-performance trade-off）。為解決這些挑戰，我們提出 KernelZero，一個共同演化框架（co-evolution framework），透過兩個專門模型持續改進 GPU 核心生成：Proposer 負責從 API 集合（API set）生成 Torch 模組（Torch module），Coder 則將其翻譯為 CUDA 或 Triton 核心。KernelZero 採用前沿驅動模組生成機制（frontier-driven module generation mechanism），針對 Coder 當前的弱項持續產生能力對齊（capability-aligned）的訓練模組。此外，我們提出正確性感知群組相對策略最佳化（Correctness-Aware Group Relative Policy Optimization, CA-GRPO），僅在正確性足夠可靠後，才進一步最佳化效能。透過交替最佳化 Proposer 與 Coder，KernelZero 形成自動課程（automatic curriculum），實現具針對性且訓練效率高的能力提升。實證結果顯示，KernelZero-7B 在 CUDA 上超越 Claude-4.5-Sonnet，在 Triton 上超越 DeepSeek-V4-Pro。在 KernelBench Level 1 與 Level 2 上，其 CUDA pass@1 分別達到 75.8% 與 69.6%，pass@10 則分別達到 100% 與 97%。在 Triton 上，pass@1 分別達到 77.2% 與 72.5%。

### 核心貢獻（3～5點）
- 提出 KernelZero 共同演化框架（co-evolution framework），透過 Proposer 與 Coder 兩個專門模型交替最佳化，持續改進 GPU 核心生成能力。
- 設計前沿驅動模組生成機制（frontier-driven module generation mechanism），根據 Coder 當前弱項動態產生能力對齊（capability-aligned）的訓練模組。
- 提出 CA-GRPO 強化學習演算法，在確保正確性足夠可靠後才進一步最佳化效能，緩解正確性與效能權衡（correctness-performance trade-off）。
- 形成自動課程（automatic curriculum），使訓練過程具針對性並提升訓練效率。

### 適合對象
適合對 GPU 核心最佳化、大型語言模型（LLM）程式生成、強化學習（RL），以及機器學習系統編譯與高效能計算領域的研究人員與工程師閱讀。

## 深度分析

#### 方法論解析

KernelZero 的核心貢獻在於將 GPU kernel（GPU 核心）生成重新定義為一個 **co-evolution framework（共同演化框架）**，透過兩個具備明確介面的專家模型——**Proposer（提案模型）** 與 **Coder（編碼模型）**——交替優化，形成自動化的訓練課程。整體流程可形式化為一個兩階段映射：

\[
a \xrightarrow{P} m \xrightarrow{C} k
\]

其中 \(a\) 為 **API set（API 集合）**，\(m\) 為 **Torch module（Torch 模組）**，\(k\) 則為最終的 CUDA（CUDA）或 Triton（Triton）**GPU kernel（GPU 核心）**。Proposer 負責在高層次探索運算子組合空間，Coder 則負責將高階規格轉譯為底層、正確且高效能的實作。

##### 1. 交替優化的共同演化架構

不同於傳統單一模型端到端生成 kernel 的做法，KernelZero 採用 **alternating optimization（交替最佳化）** 策略：在每一次迭代中，固定其中一個模型，僅使用對應的 reward（獎勵）透過 **GRPO（Group Relative Policy Optimization，群組相對策略最佳化）** 更新另一個模型。這種設計有幾個好處：

- **穩定性**：避免兩個模型同時更新導致的非平穩分布與訓練發散。
- **介面清晰**：Proposer 與 Coder 之間透過 Torch module 作為中間表示，降低聯合優化的複雜度。
- **自動課程生成**：Proposer 根據 Coder 當前弱點動態調整訓練樣本難度，Coder 則在更貼近其能力邊界的資料上持續進步，兩者形成 **automatic curriculum（自動課程）**。

##### 2. Proposer：前沿驅動的模組生成

Proposer 的目標並非隨機產生任意 Torch module，而是產出位於 Coder **capability frontier（能力前沿）** 的模組——也就是「Coder 目前剛好可能解出、但仍有挑戰性」的題目。為達成此目標，論文設計了三個機制：

**（1）API List Sampling（API 列表抽樣）**

Proposer 的輸入並非單一 API，而是從真實世界 Torch 模組中統計得到的 **API co-occurrence distribution（API 共現分布）** 抽樣出來的 API set。這樣做的好處是：

- 保留真實運算子組合的結構特性，避免生成過於人工或不切實際的模組。
- 同時維持足夠多樣性，讓 Coder 能泛化到廣泛的運算子組合。

**（2）Validation Check（驗證檢查）**

生成的模組必須通過嚴格的正確性與可用性檢查，包括：功能正確、可執行無 runtime error、數值穩定。這確保了進入 Coder 訓練階段的資料是「可靠」的，避免 Coder 在語法錯誤或語意不明的規格上浪費訓練資源。

**（3）Frontier Reward（前沿獎勵）**

這是 Proposer 訓練的關鍵。具體而言，系統會從 Coder 在當前迭代中「無法解決的模組」裡提取 API set，作為下一輪 Proposer 的輸入提示；同時根據 **correctness-based feedback（基於正確性的回饋）** 調整 Proposer，使其生成難度剛好落在 Coder 能力邊界附近的模組。這種 **frontier-driven module generation mechanism（前沿驅動模組生成機制）** 能自動避開兩類無效樣本：

- 過於簡單的模組：對 Coder 沒有學習價值。
- 過於困難的模組：超出 Coder 目前能力，無法提供有效梯度。

由此產生的訓練資料是 **capability-aligned（能力對齊的）**，並且無需人工標註即可持續產生。

##### 3. Coder：CA-GRPO 與正確性—效能權衡

Coder 的挑戰在於 GPU kernel 生成中固有的 **correctness-performance trade-off（正確性與效能權衡）**：過度追求 **speedup（加速比）** 容易導致數值錯誤或記憶體問題；只追求正確性則會產生過於保守、效能平庸的 kernel。為此，論文提出 **Correctness-Aware Group Relative Policy Optimization（正確性感知群組相對策略最佳化，CA-GRPO）**。

CA-GRPO 在 GRPO 的群組層級設計上加入一個 gating（閘控）機制，將 **correctness signal（正確性訊號）** 與 **performance signal（效能訊號）** 分離：

- 當群組內樣本的正確性尚未達到足夠可靠的程度時，訓練主要優化正確性。
- 只有在正確性變得「足夠可靠」後，效能相關的 reward 才會被啟動，進一步推動 speedup。

這種設計避免了早期訓練中效能優化干擾正確性學習，也防止模型為了追求加速比而犧牲正確性。對於 kernel 生成這類「正確性是前提、效能是目標」的任務，CA-GRPO 提供了一個結構化的解決方案。

##### 4. 整體訓練動態

綜合來看，KernelZero 形成了一個 **continuous training paradigm（持續訓練範式）**：

1. Proposer 根據 Coder 當前弱點生成 frontier modules。
2. Coder 在這些模組上透過 CA-GRPO 學習，先確保正確性，再提升效能。
3. Coder 能力提升後，原本困難的模組變得可解，Proposer 再根據新的弱點繼續推進能力邊界。

這種循環使得訓練資料與模型能力始終保持對齊，從而實現 targeted and training-efficient capability improvement（具針對性且訓練高效的能力提升）。

#### 實驗數據解讀

論文在 **KernelBench（KernelBench）** 的 **Level 1（Level 1）** 與 **Level 2（Level 2）** 上進行評測，同時涵蓋 CUDA 與 Triton 兩種輸出格式。主要評估指標包括 **pass@1（pass@1）**、**pass@10（pass@10）**，以及 **fast@1（fast@1）**。

##### 1. CUDA 結果

| 指標 | Level 1 | Level 2 |
|------|---------|---------|
| pass@1 | 75.8% | 69.6% |
| pass@10 | 100% | 97% |

解讀：

- **pass@1 已達相當高水準**：單次生成即可正確的機率在 Level 1 接近 76%，Level 2 仍接近 70%。這顯示 KernelZero-7B 不僅具備多樣性，單一最佳樣本的品質也相當穩定。
- **pass@10 接近天花板**：十次採樣中至少一次正確的機率在 Level 1 達到 100%，Level 2 達 97%。這意味著幾乎所有題目都在模型的「可解空間」內，問題主要在於如何從多個候選中挑選或進一步提升最佳樣本品質。
- **Level 2 相對 Level 1 的下降幅度約 6.2%（pass@1）與 3%（pass@10）**，顯示隨著運算子組合複雜度增加，正確性仍會下降，但幅度可控。

##### 2. Triton 結果

| 指標 | Level 1 | Level 2 |
|------|---------|---------|
| pass@1 | 77.2% | 72.5% |

解讀：

- Triton 的 pass@1 表現略優於 CUDA，Level 1 達 77.2%，Level 2 達 72.5%。這可能反映 Triton 語法相對高階、記憶體管理由編譯器處理，降低了生成錯誤的機率；也可能與 Coder 在 Triton 上的訓練資料分布較為友善有關。
- Level 1 到 Level 2 的下降幅度約 4.7%，小於 CUDA 的 6.2%，暗示 Triton 生成在面對複雜模組時具有較好的穩健性。

##### 3. 連續更新 Proposer 的消融實驗

論文報告，持續更新 Proposer 相較於固定 Proposer 帶來以下提升：

| 指標 | CUDA L1/L2 | Triton L1/L2 |
|------|------------|--------------|
| pass@1 | +0.9 / +5.2 pp | +2.3 / +4.2 pp |
| fast@1 | +1.7 / +0.4 pp | +1.2 / +3.5 pp |

解讀：

- **Proposer 的持續演化對較難的 Level 2 幫助更大**：在 CUDA 與 Triton 的 Level 2 上，pass@1 分別提升 5.2 與 4.2 個百分點。這驗證了 frontier-driven module generation 的價值——當題目變複雜時，貼近模型能力邊界的訓練資料變得更加關鍵。
- **fast@1 的提升顯示 Proposer 也間接改善了效能**：透過生成更具挑戰性且多樣的模組，Coder 被促使學習更積極的優化策略，而非停留在保守實作。

##### 4. 與大型商業模型的比較

KernelZero-7B 在 CUDA 上超越 **Claude-4.5-Sonnet（Claude-4.5-Sonnet）**，在 Triton 上超越 **DeepSeek-V4-Pro（DeepSeek-V4-Pro）**。這一結果意義重大：

- **參數規模並非唯一決定因素**：僅 7B 的專門化模型，透過針對性的共同演化訓練，可以在特定領域擊敗數十倍規模的通用 **LLM（Large Language Model，大型語言模型）**。
- **資料品質與訓練範式的重要性**：這也凸顯了 capability-aligned 資料與 automatic curriculum 對於領域專家模型訓練的關鍵作用。

#### 與現有研究的比較

##### 1. 相較於 cudaLLM、Kevin、Dr.Kernel 等相關工作

現有研究如 cudaLLM、Kevin、Dr.Kernel 已展示 LLM 在 KernelBench 與 FlashInfer-Bench（FlashInfer-Bench）等基準上的潛力，但仍面臨兩大瓶頸：

- **資料稀缺與不對齊**：傳統 **SFT（Supervised Fine-Tuning，監督式微調）** 或單純 **RL（Reinforcement Learning，強化學習）** 往往依賴靜態資料集，難以隨模型能力動態調整。例如 cudaLLM 即便使用 128 張 H100 GPU（H100 GPU）訓練，在 KernelBench Level 1 的 pass@10 也僅達 81%。
- **正確性與效能難以兼顧**：多數方法將兩者混為一談，導致模型要么過於保守，要么頻繁出錯。

KernelZero 的改進在於：

- 以 Proposer 動態生成 **capability-aligned** 訓練資料，解決資料稀缺問題。
- 以 CA-GRPO 明確分離正確性與效能訊號，解決 trade-off 問題。
- 透過 co-evolution 形成自動課程，提升訓練效率。

##### 2. 相較於直接使用 Claude、DeepSeek 等通用模型

通用大型模型雖然具備廣泛知識，但在 GPU kernel 這類高度專業、需要嚴格正確性與硬體知識的任務上，往往缺乏：

- 針對特定 DSL（如 CUDA、Triton）的密集訓練。
- 根據模型當前弱點動態調整的訓練機制。
- 明確的正確性閘控，避免效能優化犧牲數值正確性。

KernelZero-7B 的勝出說明：在狹義但高價值的領域，專門化的小型模型配合良好的訓練範式，可以超越通用大模型。

##### 3. 限制與潛在問題

儘管結果亮眼，仍有以下限制值得注意：

- **評測範圍集中於 KernelBench**：雖然 KernelBench 是系統性評測框架，但真實世界中的 kernel 需求（如分散式訓練、自訂融合運算子、特定硬體指令集）可能更為複雜，論文未展示在這些場景的泛化能力。
- **硬體相依性**：CUDA 與 Triton 的效能表現高度依賴 GPU 架構（如 H100），在不同世代 GPU 上的遷移能力未明確討論。
- **pass@10 高但 pass@1 仍有提升空間**：雖然 pass@10 接近 100%，但實際部署中通常只能執行單一 kernel，因此如何將 pass@10 的優勢轉化為 pass@1 與 fast@1 仍是關鍵。
- **訓練成本與穩定性**：雖然論文強調訓練效率，但具體的訓練 GPU 時數、收斂曲線、超參數敏感性等細節在提供的片段中未完整揭露。

#### 未來研究方向

KernelZero 開啟了幾個值得深入探索的研究方向：

##### 1. 擴展至其他領域特定語言與硬體平台

目前 KernelZero 聚焦於 CUDA 與 Triton。未來可將相同框架應用至 **BangC（BangC）**、ROCm、OpenCL，甚至 CPU/NPU 的 kernel 生成，驗證 co-evolution framework 的跨平台泛化能力。

##### 2. 多 GPU 與分散式 Kernel 生成

現有評測主要針對單一 GPU kernel。未來可探索 Proposer 生成需要跨裝置通訊的模組，Coder 則學習產生考慮通訊開銷與記憶體層級的分散式 kernel。

##### 3. 與編譯器更緊密的結合

Triton 已經將部分優化交給編譯器，但未來可進一步讓 Coder 學習產生對編譯器友善的程式碼，或與 MLIR、TVM 等編譯器堆疊協同設計，實現「生成 + 編譯」聯合優化。

##### 4. 形式化正確性驗證

雖然 CA-GRPO 透過 reward 設計強化正確性，但最終仍依賴數值測試。未來可結合形式化方法（如 SMT solver、等價性檢查）對生成的 kernel 進行嚴格驗證，特別是對浮點數精度、記憶體越界等問題。

##### 5. 從 pass@10 到 pass@1 與 fast@1 的轉化

由於 pass@10 已接近天花板，未來研究可聚焦於：

- 更好的 reward shaping，讓模型在單次生成時就傾向於高品質 kernel。
- 引入 verifier 或 critic 模型，從多個候選中篩選最佳 kernel。
- 結合 beam search、MCTS 等搜尋策略，提升最佳樣本品質。

##### 6. 更大規模模型與資料效率的權衡

KernelZero-7B 已能擊敗大型商業模型，但未來可探討：

- 將 co-evolution framework 擴展至 14B、70B 甚至更大模型時，效能是否持續提升。
- 在更大模型上，frontier-driven data generation 是否仍能保持資料效率，或會出現飽和現象。

##### 7. 持續學習與線上部署

KernelZero 的 continuous training paradigm 非常適合線上學習場景。未來可研究如何在使用者實際部署過程中，根據真實效能回饋持續更新 Proposer 與 Coder，形成真正的「自我演化」kernel 生成系統。

##### 8. 人機協同與可解釋性

最後，讓工程師能夠理解 Coder 為何選擇特定 tile size、memory layout 或 fusion 策略，將有助於提升系統的可信度與可維護性。未來可加入可解釋性模組，讓 Proposer 與 Coder 不僅產出 kernel，也能說明其設計決策。

## 論文問答

**Q1：為什麼自動生成高效能 GPU 核心至今仍然困難？**

A：高效能 GPU 核心的開發需要同時掌握 CUDA、Triton 等領域特定語言，以及電腦架構與記憶體層級等專業知識，因此門檻極高。即使使用大型語言模型，生成結果也經常面臨正確性與執行效能之間的權衡：過度保守的實作雖然正確但加速比有限，而過度激進的優化又容易產生數值錯誤或執行失敗。此外，與模型當前能力精準對齊的高品質訓練資料非常稀少，導致監督式微調或強化學習難以收斂或成本極高。

**Q2：現有以大型語言模型為基礎的方法主要失敗在哪些地方？**

A：現有方法面臨兩大根本限制：第一是缺乏與模型當前能力對齊且對其弱點敏感的高品質訓練資料，使得訓練往往無法針對性地提升能力。第二是正確性與效能之間存在明顯的權衡，單獨優化其中一項通常會犧牲另一項。例如 cudaLLM 即便在 128 張 H100 GPU 上進行大量訓練，在 KernelBench Level 1 的 pass@10 也僅達 81%，顯示現有範式在效率與成效上仍有明顯不足。

**Q3：為什麼「針對性訓練」對 GPU 核心生成如此重要？**

A：現代機器學習系統的運算成本很大程度上取決於底層 GPU 核心的效率，因此持續提升自動生成能力具有重大實務價值。相較於廣泛但無差別的資料餵入，針對性訓練能讓模型專注於目前仍無法解決、但接近其能力邊界的問題，避免在已掌握或過度困難的樣本上浪費運算資源。這種方式不僅能加速收斂，也能在較少訓練步數內同時提升正確性與效能。

**Q4：KernelZero 的核心框架由哪些元件組成，彼此如何協作？**

A：KernelZero 是一個共同演化框架，包含兩個具有明確介面的專門模型：Proposer 負責接收一組 Torch API，並生成可執行的 Torch 模組；Coder 則負責將該模組翻譯為最佳化的 CUDA 或 Triton 核心。整體流程形成兩階段映射：API 集合先轉換為高階計算圖，再由 Coder 實現為低階高效能核心。兩個模型透過交替優化進行共同演化，各自依據專屬獎勵函數進行 GRPO 訓練，並在過程中互相拉抬能力。

**Q5：前沿驅動模組生成機制如何解決訓練資料稀缺的問題？**

A：該機制會從 Coder 在每一輪迭代中無法正確解決的模組裡提取 API 集合，並將這些 API 集合作為 Proposer 的輸入，從而生成針對 Coder 當前弱點的訓練樣本。同時，基於正確性的回饋會引導 Proposer 生成位於 Coder 能力前沿附近的模組，避免產生過於簡單或過度困難的樣本。這種方式能持續產生高品質、自動對齊模型當前能力的訓練資料，無需人工標註即可形成自動課程。

**Q6：Correctness-Aware Group Relative Policy Optimization（CA-GRPO）的設計理念是什麼？**

A：CA-GRPO 是為了解決正確性與效能之間的權衡而設計的強化學習演算法，它透過群組層級的門控機制將正確性訊號與效能訊號分離。只有在群組內核心的正確性達到足夠可靠的程度後，效能優化才會被啟動，從而避免模型在尚未能正確執行時就盲目追求加速比。這種「先求正確、再求快」的策略確保了 Coder 的學習過程更穩定，並能持續產出既正確又高效的 GPU 核心。

**Q7：KernelZero 在哪些基準測試與指標上進行評估？**

A：論文主要在 KernelBench 的 Level 1 與 Level 2 上進行評估，分別測試 CUDA 與 Triton 兩種核心生成能力。評估指標包括 pass@1（單次生成即正確的比率）、pass@10（十次生成中至少一次正確的比率），以及 fast@1（在正確結果中是否為最快實作）。此外，KernelZero-7B 也與 Claude-4.5-Sonnet、DeepSeek-V4-Pro 等規模更大的通用大型語言模型進行比較。

**Q8：KernelZero 的主要實驗結果為何？**

A：KernelZero-7B 在 CUDA 生成上超越了 Claude-4.5-Sonnet，在 Triton 生成上超越了 DeepSeek-V4-Pro。具體而言，CUDA 的 pass@1 在 Level 1 與 Level 2 分別達到 75.8% 與 69.6%，pass@10 更高達 100% 與 97%；Triton 的 pass@1 則分別為 77.2% 與 72.5%。這些結果顯示，即使參數量僅有 7B，透過共同演化與自動課程設計，也能在專業領域超越規模更大的通用模型。

**Q9：持續更新 Proposer 對整體表現帶來什麼影響？**

A：消融實驗顯示，持續更新 Proposer 能顯著提升 Coder 的表現：在 CUDA 上，Level 1 與 Level 2 的 pass@1 分別提升 0.9 與 5.2 個百分點；在 Triton 上則分別提升 2.3 與 4.2 個百分點。此外，fast@1 指標在 CUDA 上提升 1.7 與 0.4 個百分點，在 Triton 上提升 1.2 與 3.5 個百分點。這證明了 Proposer 與 Coder 的共同演化不僅提升正確率，也能逐步改善生成核心的執行效率。

**Q10：KernelZero 在實務上可以應用在哪些場景？**

A：KernelZero 可應用於機器學習編譯器與自動算子優化系統，為新出現的神經網路運算自動生成客製化 GPU 核心。它也能加速深度學習框架在訓練與推論階段的執行效率，減少對資深核心工程師手寫最佳化程式碼的依賴。對於需要頻繁嘗試新模型架構或新硬體平台的團隊而言，這種自動化生成能力能顯著縮短開發週期並降低維護成本。

**Q11：若將 KernelZero 產品化，需要考慮哪些部署與整合問題？**

A：產品化時必須建立穩定的驗證與測試基礎設施，因為生成的核心必須經過功能正確性、數值穩定性與效能測試後才能上線。此外，需要將 Proposer 與 Coder 無縫整合到 PyTorch 等深度學習框架中，並支援 CUDA 與 Triton 的編譯與執行環境。由於共同演化涉及反覆訓練與採樣，部署時也需評估運算成本、模型版本管理，以及針對特定硬體目標的獎勵設計。

**Q12：KernelZero 對 GPU 核心生成領域可能帶來什麼影響？**

A：KernelZero 展示了專門化的小型模型透過共同演化與自動課程，可以在特定領域擊敗通用大型模型，這為領域特定程式碼生成提供了新的訓練典範。它強調了「能力對齊的資料」與「正確性感知的強化學習」在複雜程式合成任務中的關鍵角色。長遠來看，這種方法可能推動自動化機器學習系統編譯器的發展，使硬體效能優化更加普及與自動化。

**Q13：KernelZero 目前有哪些已知的限制？**

A：論文的評估主要集中在 KernelBench 的 Level 1 與 Level 2，對於更複雜或更廣泛的運算模式覆蓋仍有限。此外，目前方法主要針對 CUDA 與 Triton，對於其他硬體平台如 AMD ROCm 或華為昇騰的 BangC 並未深入探討。整體框架也依賴驗證檢查與獎勵設計來引導生成，若獎勵訊號設計不當，仍可能導致訓練不穩定或收斂至次優解。

**Q14：在什麼情況下 KernelZero 可能會失敗或表現不佳？**

A：當 Proposer 生成的模組包含極度新穎或複雜的運算組合，遠超過 Coder 當前能力前沿時，Coder 可能無法產出正確結果。此外，某些數值穩定性的邊界案例或特定硬體限制未被獎勵函數充分捕捉時，也可能導致生成核心雖然通過部分測試，但在實際應用中出錯。如果 CA-GRPO 中的正確性門檻設定過早放寬，模型也可能在尚未建立穩固正確性基礎前就過度追求效能。

**Q15：未來可以朝哪些方向延伸 KernelZero 的研究？**

A：未來可將此共同演化框架擴展到更多領域特定語言與硬體平台，例如 AMD GPU、華為昇騰或其他 AI 加速器。另一方面，可引入形式化驗證技術來進一步確保生成核心的正確性，降低對大量測試案例的依賴。此外，讓 KernelZero 能從真實生產環境的線上工作負載中持續學習，並結合更多專家代理進行多智能體共同演化，也是極具潛力的發展方向。

## 實務應用指南

## 適用場景

1. **大型模型推理與訓練的客製化算子加速**  
   在 Transformer、MoE、擴散模型等場景中，經常需要將特定注意力變體、啟動函數或記憶體密集運算手寫成 CUDA/Triton 核心。KernelZero 可持續產生與目前 Coder 能力對齊的訓練模組，協助團隊自動化生成並迭代優化這些客製化 GPU 核心。

2. **AI 編譯器與圖最佳化後端的算子合成**  
   當編譯器（如 TorchInductor、TVM、AITemplate）遇到未支援的融合模式（fusion pattern）時，可用 KernelZero 的 Proposer 探索 Torch API 組合，再由 Coder 產生對應的低階核心，補足編譯器算子庫的缺口。

3. **異質硬體（NPU/ASIC）的領域特定語言核心生成**  
   雖然論文聚焦 CUDA 與 Triton，但 Proposer 與 Coder 分離的架構可擴充至 BangC 等領域特定語言。適合需要為自研 AI 加速器持續產生高效能核心的團隊。

4. **自動化 KernelBench 類型的內部迴歸測試與能力評測**  
   企業可建立內部算子基準，利用 KernelZero 的交替訓練流程持續產生新測試案例，並監控模型在正確性（pass@1）與效能（speedup）上的能力前沿變化。

5. **高效能運算（HPC）與科學計算的運算核心原型開發**  
   對於需要反覆試驗不同 tile size、記憶體配置與平行策略的數值計算核心，KernelZero 可作為自動化原型生成工具，加速從 PyTorch 參考實作到最佳化 GPU 核心的迭代。

## 實作前置條件

### 資料
- **Torch API 語料與真實模組樣本**：用於建立 API 共現分佈，確保 Proposer 產生的模組具現實性與多樣性。
- **參考實作與測試輸入**：每個 Torch 模組需對應可執行的 PyTorch 參考實作，以及用於驗證正確性的輸入張量與數值容忍度。
- **Coder 弱點案例庫**：從 Coder 當前無法解決或效能不佳的模組中提取 API 集合，作為 Frontier Reward 與能力對齊訓練的種子。

### 運算
- **多張高階 NVIDIA GPU（建議 H100 等級）**：論文提及 cudaLLM 使用 128 張 H100，實務上至少需數張至數十張 GPU 進行 GRPO/CA-GRPO 訓練與核心編譯驗證。
- **長時間穩定訓練環境**：交替優化 Proposer 與 Coder 需要反覆抽樣、編譯、執行與回饋，對叢集穩定性與排程效率要求高。

### 技能
- **CUDA/Triton 程式設計與效能分析**：需能判斷 Coder 輸出核心的正確性與加速比，並設計合理的數值驗證與效能評測流程。
- **強化學習與 LLM 微調經驗**：熟悉 GRPO、PPO、SFT、reward shaping，以及 7B 等級語言模型的分散式訓練。
- **PyTorch 圖表示與編譯器知識**：能將 Torch 模組轉換為 Coder 可理解的中間規格，並處理動態形狀、資料型別等邊界條件。

## 實作步驟建議

1. **建立 Proposer 的初始監督式微調資料**  
   從真實 PyTorch 程式碼與公開算子庫中抽取 Torch API 組合，產生可執行的 Torch 模組，對 Proposer 進行 SFT，使其學會根據 API 集合生成語法正確、數值穩定的模組。

2. **建立 Coder 的初始監督式微調資料**  
   收集現有的 CUDA/Triton 核心與對應的 Torch 參考模組，訓練 Coder 將高階模組翻譯為可編譯、可執行的低階核心。此階段以「可編譯 + 數值正確」為主要目標，不強求極致加速比。

3. **建構驗證與回饋管線**  
   對每個生成的核心執行：編譯檢查、數值正確性比對（相對於 Torch 參考實作）、效能測量（speedup）。將結果轉換為 Proposer 的 Frontier Reward 與 Coder 的 CA-GRPO 獎勵訊號。

4. **啟動交替共同演化訓練**  
   固定 Coder，使用 Frontier Reward 對 Proposer 進行 GRPO 訓練，使其產生位於 Coder 能力前沿的模組；再固定 Proposer，使用 CA-GRPO 訓練 Coder，讓正確性訊號優先收斂後才啟動效能優化。

5. **迭代擴充能力前沿**  
   每輪訓練後，從 Coder 仍未解決或效能不佳的模組中提取新的 API 集合，餵入 Proposer 進行下一輪模組生成，形成自動課程。

6. **部署至產品管線**  
   將訓練完成的 Coder 整合為編譯器後端或算子生成服務，並保留 Proposer 作為持續產生回歸測試案例與新訓練資料的引擎，定期重新訓練以適應新硬體與新模型架構。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **正確性與效能權衡失衡** | 過早強調 speedup 可能導致數值錯誤或記憶體不安全的核心。 | 嚴格採用 CA-GRPO 的群組門控機制，先以正確性獎勵為主，待 pass 率穩定後再逐步加入效能獎勵。 |
| **Proposer 產生過難或過易模組** | 模組太簡單無法推動能力前沿，太困難則 Coder 無法學習。 | 透過 Frontier Reward 與 Coder 未解決案例動態調整難度，並設定可解率區間（例如 30%–70%）作為篩選條件。 |
| **編譯與執行回饋成本高昂** | 每個核心都需實際編譯與 GPU 執行，訓練迴圈可能極慢。 | 建立快取機制避免重複驗證相同模組；對顯然語法錯誤的核心提前過濾；使用容器化環境平行執行。 |
| **獎勵駭入（reward hacking）** | Coder 可能學會通過數值驗證但實際不穩定的技巧，例如過度依賴特定輸入形狀。 | 使用多組輸入形狀與隨機種子進行測試；加入靜態分析與記憶體安全檢查；定期以人工抽樣審查生成核心。 |
| **模型能力漂移** | 持續訓練可能遺忘先前已學會的算子類型。 | 保留歷史通過案例作為 replay buffer，在每一輪 CA-GRPO 中混合舊樣本與新前沿樣本。 |

## 與其他技術的整合建議

- **與 PyTorch/TorchInductor 整合**  
  將 KernelZero 的 Coder 作為 TorchInductor 的後端算子生成器，當編譯器遇到無法自動融合的算子組合時，呼叫 Coder 產生 Triton 核心並註冊為自定義 op。

- **與 MLIR/TVM 整合**  
  把 Proposer 產生的 Torch 模組轉換為 MLIR 或 Relay 表示，再讓 Coder 針對特定 target（如 CUDA、ROCm、自研 NPU）生成對應程式碼，擴充跨硬體能力。

- **與 CI/CD 及效能迴歸測試整合**  
  在每次模型或硬體驅動更新後，自動執行 Proposer 產生的一批新模組，並用 Coder 生成核心進行正確性與效能迴歸測試，確保核心品質不隨版本退化。

- **與現有 LLM 程式碼生成工具整合**  
  可將 KernelZero-7B 作為 Claude-4.5-Sonnet 或 DeepSeek-V4-Pro 的專家模型（expert model），在偵測到 CUDA/Triton 生成任務時路由至 KernelZero，提升 pass@1 與加速比。

## 給不同背景讀者的閱讀建議

**初學者**：建議先理解「Proposer 負責出題、Coder 負責解題」這個核心分工，並把 KernelZero 想像成一位會自動出考古題、再自己學會解題的學生。閱讀時可跳過 CA-GRPO 的數學細節，專注於圖 1 與圖 2 的流程，以及「能力對齊」與「自動課程」這兩個概念。

**AI 工程師**：請重點研讀第 2.2 節的 Frontier Reward 設計與 CA-GRPO 的群組門控機制，思考如何將其移植到你目前的 RLHF/RLAIF 管線。特別注意驗證管線的實作細節，因為編譯與執行回饋是整個系統能否規模化的關鍵。

**研究人員**：論文的核心貢獻在於將「共同演化」與「能力前沿」形式化為可訓練的 LLM 系統。建議深入分析 Proposer 與 Coder 交替最佳化的收斂性、CA-GRPO 對正確性—效能權衡的理論保證，以及該框架能否擴展至其他程式合成領域（如資料庫查詢優化、硬體描述語言生成）。

**產品經理**：請關注論文的數據指標：KernelZero-7B 在 CUDA Level 1/2 達到 75.8%/69.6% pass@1，Triton 達到 77.2%/72.5%，且 pass@10 接近滿分。這代表它適合作為「自動化算子工程」產品的核心引擎，但需評估 GPU 訓練成本、驗證基礎建設與維護人力，並規劃與現有編譯器或模型訓練平台的整合路徑。
