# StateAct：程式狀態先於像素，用於長期電腦使用代理

**原文標題：** StateAct: Program State, before Pixels, for Long-Horizon Computer-Use Agents

## ⚡ TL;DR

現有電腦代理依賴截圖，但畫面是有損渲染，難以反映底層程式狀態，長期任務易累積錯誤。
StateAct以程式碼優先直接操作程式狀態，必要時委派GUI子代理，並以獨立閘門驗證結果。
於OSWorld 2.0，二元20.6→26.9%、部分54.8→61.6%，成本為九分之一。

## 摘要翻譯

電腦使用代理（computer-use agents）通常透過強化感知（perception）來改進：使用更好的模型讀取螢幕截圖（screenshot）並選擇點擊位置。然而，螢幕截圖僅是底層程式狀態（program state）的有損渲染（lossy rendering），例如儲存任務資料的檔案、應用程式後端（application backends）與文件物件模型（DOM）。不同的狀態可能產生相同的像素（pixels），而程式碼卻能直接檢查並修改該狀態。StateAct 正是基於這項區別所建構、以程式碼優先（code-first）的多智慧體框架（multi-agent harness）：其主代理（main agent）透過程式碼直接操作程式狀態，而專責的 GUI 子代理（GUI subagent）則處理少數需要螢幕截圖與點擊互動的子目標（subgoals）——在 108 項任務中僅 28 項，且這類互動僅佔主代理步驟（main-agent steps）的 1.1%。同樣地，直接存取程式狀態也支援驗證（verification）：獨立的完成閘門（finish gate）會再次檢查已儲存結果（saved result）是否出現結構性失敗（structural failures），例如輸出遺失（missing）、未儲存（unsaved）或寫入錯誤路徑（wrong path）。為了在數百個步驟中維持正軌，主代理採用新鮮上下文委派（fresh-context delegation），將子目標交給新的子代理執行，使自身上下文保持專注。在 OSWorld 2.0 上，StateAct 將 Claude Opus 4.8 的二元成功（binary success）率從 20.6% 提升至 26.9%，部分成功（partial success）率從 54.8% 提升至 61.6%，且每項任務成本（cost per task）約為僅由螢幕截圖驅動的同模型的 1/9；不含 GUI 子代理的純程式碼變體（code-only variant）僅達到 45.9% 的部分成功率，低於該以截圖為基準的基線（screenshot-based baseline）的 54.8%。整體而言，將動作（action）、驗證與記憶（memory）建立在狀態之上，亦即所謂的狀態接地（state-grounding），會將主要瓶頸（main bottleneck）從感知轉向推理（reasoning）：失敗更多取決於代理怎麼想，而非它看到什麼。

### 核心貢獻（3～5點）
- 提出狀態接地（state-grounding）觀點：相較於僅依賴螢幕截圖（screenshot）這類有損渲染（lossy rendering），直接以程式碼操作底層程式狀態（program state）可提升長期電腦使用代理的可靠性與效率。
- 設計以程式碼優先（code-first）的多智慧體框架（multi-agent harness）StateAct：主代理（main agent）負責程式狀態操作，GUI 子代理（GUI subagent）僅在必要子目標（subgoals）進行視覺互動，視覺步驟僅佔主代理步驟的 1.1%。
- 利用直接狀態存取（direct state access）進行獨立驗證：完成閘門（finish gate）檢查持久化結果（persisted result）的結構性失敗（structural failures），如遺失（missing）、未儲存（unsaved）或錯誤路徑（wrong path）。
- 透過新鮮上下文委派（fresh-context delegation）管理長期任務上下文：主代理將子目標交給新子代理執行，避免上下文過長導致偏離。
- OSWorld 2.0 實證：在顯著降低每項任務成本（cost per task）的同時提升成功率，並顯示瓶頸從感知（perception）轉向推理（reasoning）。

### 適合對象
適合研究長期電腦使用代理、GUI 自動化、多模態大型語言模型與機器人流程自動化的研究人員與工程師，特別是關注如何以程式狀態（program state）取代或輔助以螢幕截圖（screenshot）為基礎之視覺互動的讀者。

## 深度分析

#### 方法論解析

##### 狀態接地的核心概念
StateAct 的核心論點是：桌面任務最終被評判的依據是「程式狀態（program state）」——也就是檔案（files）、應用程式後端（application backends）、文件物件模型（DOM）、資料庫表格等實際儲存任務資料的底層結構——而非螢幕截圖（screenshot）上的像素（pixels）。作者將觀察通道形式化為兩個映射：

- 像素通道（pixel channel）：\(o_{\text{pix}} = f_{\text{render}}(s)\)
- 狀態通道（state channel）：\(o_{\text{state}} = g(s)\)

由於 \(f_{\text{render}}\) 是**有損渲染（lossy rendering）**且**非單射（non-injective）**，多個不同的程式狀態可能產生幾乎相同的畫面。例如試算表（spreadsheet）中某個儲存格顯示的總和，可能是公式（formula）計算結果，也可能是手動輸入的常數（literal）；相關資料列可能被隱藏（hidden rows）或位於螢幕外（off-screen）。這些「任務關鍵區別（task-critical distinctions）」無法從截圖復原，但透過直接狀態存取（direct state access）即可暴露並修改。StateAct 將這種把動作、驗證與記憶都建立在程式狀態上的設計稱為**狀態接地（state-grounding）**。

##### 多智慧體架構
StateAct 是一個**多智慧體框架（multi-agent harness）**，由以下角色組成：

- **主代理（main agent）**：負責整體任務流程，預設直接操作程式狀態。
- **GUI 子代理（GUI subagent）／GUI 專家（GUI specialist）**：專職處理需要截圖與點擊的視覺互動（visual interaction）。
- **瀏覽器專家（web specialist）**：處理需要導航與讀取 DOM 的網頁子任務。
- **通用代理（general agent）**：執行任何被委派的子任務。
- **完成閘門（finish gate）**：獨立於主代理，對持久化產出（persisted artifact）進行結構性檢查。
- **上下文管理器（context manager）**：透過新鮮上下文委派（fresh-context delegation）、壓縮（compaction）與外部化計畫（externalized plan）維持長期記憶。

這種分工讓主代理的預設路徑是「以程式碼優先（code-first）」讀寫真實狀態，視覺互動僅作為後備（fallback）。

##### 動作空間：程式碼優先與 GUI 後備
主代理的動作空間包含持續性 bash（persistent bash）、Python 與檔案編輯器（file editor）。透過這些工具，代理可以直接讀取檔案內容、呼叫應用程式 API（application API）、修改 DOM 或執行 shell 指令。然而，並非所有應用程式都暴露完整的可存取狀態（accessible state），因此需要 GUI 子代理作為補充。實驗顯示，**純程式碼變體（code-only variant）**（沒有 GUI 子代理）的部分成功（partial success）僅 45.9%，甚至低於以截圖為基準的基線（screenshot-based baseline）54.8%，證明視覺互動在部分任務中不可或缺。但整體而言，GUI 子代理只出現在 108 項任務中的 28 項，且僅佔主代理步驟（main-agent steps）的 1.1%，顯示大多數操作可由狀態接地動作（state-grounded action）完成。

##### 完成閘門：敘事盲驗證
StateAct 的驗證機制強調「敘事盲（narration-blind）」：完成閘門不閱讀主代理對自身工作的描述，而是直接檢查已儲存結果（saved result）的程式狀態。它能捕捉結構性失敗（structural failures），例如輸出遺失（missing）、未儲存（unsaved）或寫入錯誤路徑（wrong path）。這與傳統的自我反思（self-reflection）不同——後者通常讓模型檢視自己的軌跡敘述，容易產生偏見；完成閘門則類似獨立的驗收測試（acceptance test）或演員–評論家（actor–critic）分離。

##### 長期執行的上下文管理
在長期任務（long-horizon tasks）中，單一代理的上下文會隨步數增加而充斥過時細節，導致遺忘任務事實（task facts）與計畫（plans）。StateAct 透過以下機制維持專注：

1. **新鮮上下文委派**：將子目標（subgoals）交給新上下文的子代理執行，避免主代理上下文膨脹。
2. **壓縮**：精簡過長的對話歷史。
3. **外部化計畫**：將計畫與檢查清單（plan checklist）儲存在外部，減輕主代理的記憶負擔。

實驗指出，遞迴委派僅在 108 項任務中的 7 項觸發且從未巢狀化，說明效能提升主要來自觀察品質，而非單純增加代理深度。

#### 實驗數據解讀

##### OSWorld 2.0 設定與指標
實驗在 **OSWorld 2.0** 上進行，這是一個長期電腦使用基準（computer-use benchmark），共 108 項任務。評估指標分為：

- **二元成功（binary success）**：任務是否完全成功。
- **部分成功（partial success）**：任務達成程度的細粒度分數。

##### 主要結果
在相同的骨幹模型（backbone）**Claude Opus 4.8** 上，StateAct 相較於參考電腦使用代理框架（reference computer-use-agent harness）取得顯著提升：

| 指標 | 參考框架 | StateAct | 提升 |
|---|---|---|---|
| 二元成功（binary success） | 20.6% | 26.9% | +6.3% |
| 部分成功（partial success） | 54.8% | 61.6% | +6.8% |

26.9% 的二元成功不僅超越同一模型的基線，也高於當時公開前沿（public frontier）的 <21%，是圖 1 中唯一突破該門檻的方法。

##### 成本效益
StateAct 的每項任務成本（cost per task）約為 **$7.8**，而相同模型在參考截圖框架下約為 **$72**，成本降低約 **9 倍**。這顯示狀態接地不僅提升準確率，也大幅減少昂貴的視覺推理呼叫。

##### 消融實驗：純程式碼變體
移除 GUI 子代理後，純程式碼變體的部分成功降至 **45.9%**，低於視覺基線（vision baseline）的 54.8%。這說明：

- 單靠程式碼無法處理所有任務；
- GUI 子代理雖使用頻率低（1.1% 步驟、28/108 任務），卻是填補「狀態不可達」缺口的關鍵；
- StateAct 的優勢來自「狀態為主、視覺為輔」的混合策略，而非完全摒棄 GUI。

##### 限制診斷
完成閘門雖能捕捉結構性錯誤，但在沒有真值神諭（ground-truth oracle）的情況下，無法獨立重新推導數值正確性。數據顯示，到達閘門的 76 項非完美任務中，閘門仍通過了 68 項，意味著多數殘留錯誤是**值錯誤（value errors）**而非結構錯誤。這支持作者的核心論點：狀態接地將主要瓶頸（main bottleneck）從感知（perception）轉移到推理（reasoning）——失敗更多取決於代理「怎麼想」，而非「看到什麼」。

#### 與現有研究的比較

##### 與強化感知方法的關係
現有大量研究聚焦於強化螢幕感知（screen perception），例如 UI-TARS（Qin et al., 2025）、Aguvis（Xu et al., 2024）、GTA1（Yang et al., 2025a）與 Set-of-Mark（Yang et al., 2023）。這些方法讓代理更擅長讀取畫面，但本質上仍受限於像素通道的有損性。StateAct 與其互補但反轉預設：它將程式狀態作為主要介面，視覺互動僅作為委派後備。

##### 與程式碼/混合動作空間的差異
以程式碼作為動作空間並非新概念：CodeAct（Wang et al., 2024）將可執行程式碼視為動作空間；OSWorld 的原生動作空間也是透過 pyautogui 的 Python；CoAct-1（Song et al., 2025）以協調器（orchestrator）統合程式設計師與 GUI 操作員；UltraCUA（Yang et al., 2025b）與 ComputerRL（Lai et al., 2025）透過強化學習學習混合 API/GUI 動作空間；UFO2（Zhang et al., 2025）融合統一的 GUI–API 層；SWE-agent（Yang et al., 2024）則主張代理應擁有專用介面。

StateAct 的架構區別在於**預設路由（default routing）**：主代理始終優先使用程式碼/狀態操作，GUI 控制被降級為子代理層級的後備，並將同樣的狀態檢查擴展到驗證閘門。

##### 與自我驗證研究的對比
在驗證方面，OpenComputer（Wei et al., 2026）使用針對每個應用程式硬編碼的狀態驗證器；Agentic Reward Modeling（Cui et al., 2026）透過主動互動探測隱藏系統狀態；MCPWorld（Yan et al., 2025）利用後端儀器化（backend instrumentation）進行驗證。這些方法通常具有較高的值檢查能力，但需要大量工程。

StateAct 的完成閘門則刻意採取「弱值檢查、強通用性」的策略：它是一個單一提示層級（prompt-level）檢查，適用於全部 108 項任務，無需逐任務驗證器工程。這是以犧牲數值正確性檢查為代價，換取可擴展性與零額外設計成本。

相較於 Reflexion（Shinn et al., 2023）與 Self-Refine（Madaan et al., 2023）等基於自我敘述軌跡的反思方法，StateAct 的完成閘門是獨立第三方檢查，拒絕閱讀主代理敘述，直接檢視持久化產出。這避免了敘述條件化判斷（narration-conditioned judgment）的偏見問題（Andrade et al., 2025）。

#### 可重現性評估

##### 開放資源與實作細節
本文為 arXiv 預印本（v1 89722.7062），文中詳細描述了 StateAct 的架構、動作空間、完成閘門設計與上下文管理策略。然而，就目前提供的內容而言，作者並未明確釋出開源程式碼、資料集或模型權重。因此，完整的系統實作細節（例如提示詞模板、子代理間的協議、完成閘門的確切提示）尚無法直接取得。

##### 環境與模型依賴
再現本研究需要：

- **OSWorld 2.0**：此為公開基準，環境可取得。
- **Claude Opus 4.8**：屬於 Anthropic 的商業 API，需付費呼叫；模型權重不公開。
- **GUI 與瀏覽器子代理**：需要能夠執行桌面環境、截圖與模擬輸入的容器化設定。

##### 再現難度
整體而言，StateAct 的**概念與高階設計可重現**，但**完整系統的精確復現難度中等偏高**。原因包括：

1. 缺乏官方開源實作，研究者需自行搭建多智慧體協調層；
2. 使用 Claude Opus 4.8 等專有模型，結果可能對模型版本與 API 行為敏感；
3. 每項任務約 $7.8 的成本雖低於截圖基線，但 108 項任務的完整評估仍需數百美元；
4. 完成閘門的泛化能力依賴提示工程，若無原始提示，難以完全複製其結構性檢查行為。

若作者未來釋出程式碼，將大幅提升社群驗證與擴展的可能性。

#### 未來研究方向

1. **強化數值驗證能力**
   當前完成閘門無法獨立判斷值正確性。未來可結合領域特定神諭（domain-specific oracles）、單元測試或輕量級 LLM 評判器（LLM judge），在不犧牲通用性的前提下提升值錯誤檢出率。

2. **動態狀態–視覺路由**
   發展學習式或啟發式策略，讓代理自動判斷何時使用狀態通道、何時呼叫 GUI 子代理，進一步降低視覺互動比例與成本。

3. **擴展至其他平台**
   將狀態接地原則應用於行動裝置（mobile）、網頁代理（web agents）或企業軟體（如 ERP、CRM），探索不同應用程式後端的狀態表示與可存取性。

4. **狀態接地資料的訓練與強化學習**
   利用 StateAct 產生的狀態軌跡作為訓練資料，微調或透過強化學習（reinforcement learning）訓練原生支援狀態操作的代理，降低對昂貴多模態模型的依賴。

5. **更深層的遞迴規劃與錯誤修復**
   雖然目前遞迴委派很少觸發，但未來可研究在推理錯誤發生時，如何自動觸發多輪、巢狀式的子代理規劃與修復迴路。

6. **開源框架與標準化介面**
   建立開源的 StateAct 實作與應用程式狀態存取介面（類似 MCP 或 A2A 協議），讓研究社群能夠貢獻不同桌面應用程式的狀態讀取器與驗證器。

7. **人機協同驗證**
   在關鍵任務中引入人類在迴路（human-in-the-loop），讓完成閘門將不確定的數值結果提交給人類確認，兼顧自動化與正確性。

## 論文問答

**Q1：StateAct 主要想解決什麼問題？為什麼傳統以截圖為主的電腦使用代理在長期任務上會遇到瓶頸？**

A：StateAct 針對的是長期電腦使用任務中，代理必須操作並驗證真實交付成果的問題。傳統方法強化螢幕感知，但螢幕截圖只是程式狀態的有損渲染，例如試算表上的總和可能來自公式或常數、相關列可能被隱藏，這些任務關鍵區別無法從像素判斷。在數百個相依步驟中，每次讀取畫面時的微小誤判會逐漸累積，最終導致錯誤的交付成果；而且截圖無法可靠地告訴代理「結果是否已正確儲存」。

**Q2：既然強化視覺感知是當前主流，為什麼 StateAct 認為這條路會碰到上限？**

A：因為渲染函式本質上不是一對一映射，不同的程式狀態可能產生幾乎相同的畫面，所以再強的視覺模型也無法從像素唯一還原底層狀態。舉例來說，一個儲存格顯示的數字可能是公式計算結果，也可能是手動輸入的常數，而截圖無法區分兩者。這種「畫面看起來對，但狀態其實錯」的情況會隨任務長度放大，使得單純提升螢幕感知無法解決長期任務的根本問題。

**Q3：什麼是「狀態接地」（state-grounding），它為何對長期任務如此重要？**

A：狀態接地是指把代理的動作、驗證與記憶都建立在程式狀態上，例如檔案、應用程式後端與 DOM，而不是以截圖為主要介面。這讓代理能直接讀取並修改儲存任務資料的底層結構，也能檢查結果是否確實被持久化到正確路徑。透過狀態接地，代理的主要瓶頸從「看清楚畫面」轉移到「推理正確與否」，這對需要數百步推理的長期任務至關重要。

**Q4：StateAct 的核心架構由哪些元件組成？它們各自負責什麼？**

A：StateAct 的核心包含主代理、GUI 子代理、瀏覽器子代理、完成閘門與上下文管理器。主代理以程式碼優先的方式直接操作程式狀態，例如透過持續性 bash、Python 與檔案編輯器讀寫真實產出；GUI 子代理與瀏覽器子代理則在少數需要視覺互動或 DOM 導航的子目標上提供支援。完成閘門獨立檢查已儲存的結果，而上下文管理器透過新鮮上下文委派、壓縮與外部化計畫，幫助主代理在數百步中保持專注。

**Q5：StateAct 與純視覺代理或純程式碼代理相比，關鍵創新在哪裡？**

A：StateAct 的關鍵創新在於「反轉預設路由」：它把程式狀態當作主要介面，而把直接螢幕互動降為委派給專家子代理的後備方案。這與不斷強化螢幕感知的視覺代理互補，也與完全不用 GUI 的純程式碼代理不同，因為後者在無法透過 API 存取狀態的應用程式上表現較差。此外，StateAct 把同樣的狀態檢查原則延伸到驗證階段，讓完成閘門獨立檢視持久化產出，而非閱讀代理自己的工作敘述。

**Q6：為什麼 StateAct 仍保留 GUI 子代理，而且只在極少數步驟中使用它？**

A：因為並非所有應用程式都提供完整的 API 或可存取狀態，有些任務仍必須透過點擊與輸入來完成。實驗顯示，純程式碼變體的部分成功率只有 45.9%，甚至低於以截圖為基準的視覺基線 54.8%，可見 GUI 仍是必要的後備能力。然而，在 108 項任務中，GUI 子代理只被用於 28 項任務，且僅佔主代理步驟的 1.1%，說明絕大多數操作都可以透過直接狀態存取更有效率地完成。

**Q7：StateAct 在哪個基準測試上進行評估？使用了什麼骨幹模型？**

A：StateAct 在 OSWorld 2.0 這個長期電腦使用基準測試上進行評估，該測試包含 108 項任務。骨幹模型採用 Claude Opus 4.8，並與同一模型在參考電腦使用代理框架下的表現進行比較。評估指標包括二元成功與部分成功，同時也報告了每項任務的成本，以凸顯狀態接地在效率上的優勢。

**Q8：StateAct 在實驗中取得了哪些關鍵成果？成本表現如何？**

A：在 Claude Opus 4.8 上，StateAct 把二元成功率從參考框架的 20.6% 提升到 26.9%，部分成功率從 54.8% 提升到 61.6%，成為唯一超越公開前沿水準（低於 21%）的方法。同時，每項任務成本約為 7.8 美元，相較於同一骨幹模型以截圖操作時的約 72 美元，降低了約 9 倍。這顯示 StateAct 不僅提升了成功率，也大幅改善了經濟性。

**Q9：StateAct 的效能提升主要來自哪裡？又有哪些因素仍然限制它的表現？**

A：提升主要來自「觀察什麼」的改變，也就是讓代理直接存取程式狀態，而非來自額外的代理深度；實際上，遞迴委派只發生在 7 項任務中，且從未巢狀化。限制則在於「數值正確性」：完成閘門能捕捉結構性錯誤，例如輸出遺失、未儲存或寫入錯誤路徑，但在沒有 ground-truth 神諾的情況下，無法獨立重新推導正確數值；在到達閘門的 76 項非完美任務中，有 68 項因為數值錯誤而通過，顯示失敗主要仍是推理問題。

**Q10：StateAct 在哪些實際應用場景中最能發揮價值？**

A：StateAct 特別適合需要操作並驗證持久化產出的長期任務，例如批次處理檔案、編輯試算表、管理行事曆、操作瀏覽器 DOM 或撰寫電子郵件。在這些場景中，結果是否儲存到正確路徑、公式是否正確、隱藏資料是否完整，都無法單靠截圖確認。透過直接存取程式狀態，代理能夠像人類工程師一樣用指令與腳本檢查系統，並在完成後進行結構性驗證。

**Q11：若要把 StateAct 產品化，需要考慮哪些成本與可靠性的權衡？**

A：StateAct 已經把每項任務成本壓到約 7.8 美元，遠低於純視覺方案，對大規模部署非常有利。然而，完成閘門目前只能保證結構正確，無法保證數值正確，因此對於高風險場景，仍需搭配領域專用的驗證器或人工確認。產品化時也必須權衡應用程式是否提供可存取狀態：若應用程式缺乏 API 或後端介面，GUI 子代理的使用比例與成本可能會上升。

**Q12：StateAct 對電腦使用代理這個研究領域可能帶來什麼影響？**

A：StateAct 提醒研究者，長期任務的瓶頸不只是「看得更清楚」，而是如何讓代理在正確的狀態上進行推理與驗證。它與 UI-TARS、Aguvis 等強化視覺感知的方向互補，鼓勵社群同時發展更好的狀態介面與視覺後備機制。未來我們可能會看到更多結合狀態接地、獨立驗證與長期上下文管理的混合式代理設計。

**Q13：StateAct 的完成閘門有哪些明確的限制？**

A：完成閘門是一個通用、無需針對每項任務工程設計的結構性檢查，因此它無法像 OpenComputer 那樣進行神諾級的數值驗證。它能發現輸出遺失、未儲存或寫入錯誤路徑等結構性失敗，但對於「計算結果是否正確」這類數值錯誤無能為力。論文也坦承這是一個刻意 trade-off：用通用性換取絕對正確性，並把這個結構性上限明確測量出來。

**Q14：StateAct 的失敗案例主要由什麼類型的錯誤主導？**

A：失敗主要由推理錯誤主導，也就是「代理怎麼想」比「代理看到什麼」更容易出錯。即使能直接存取程式狀態，代理仍可能在任務分解、公式選擇、資料轉換或子目標規劃上出錯。這呼應了論文的核心論點：狀態接地把瓶頸從感知移向推理，因此未來的改進重點應放在提升代理的長期規劃與數值推理能力。

**Q15：針對 StateAct 的限制，未來可以朝哪些方向改進？**

A：未來可以引入更強的數值驗證機制，例如輕量級的領域規則、單元測試或部分 ground-truth 檢查，以補足完成閘門的不足。另一個方向是結合強化學習或學習型 GUI 策略，讓 GUI 子代理在狀態不可存取時仍能有效運作。此外，進一步改善長期上下文管理、自動化計畫修正，以及擴展到更多提供可程式化介面的應用程式，都是值得探索的後續研究。

## 實務應用指南

## 適用場景

1. **大量重複性辦公室流程自動化**  
   例如財務月結：從電子郵件下載附件、寫入試算表、執行公式計算、匯出報表並存到指定路徑。StateAct 的狀態接地動作可直接讀寫檔案與試算表後端，避免逐格點擊造成的累積誤判。

2. **跨應用程式的資料搬運與格式轉換**  
   例如將 CRM 匯出的 CSV 整理後寫入簡報、或把網頁表單資料回填到本機文件。主代理可用 Python/bash 直接處理檔案與 DOM，只在少數需要視覺確認的步驟呼叫 GUI 子代理。

3. **長時間軟體測試與驗收檢查**  
   例如持續執行一連串安裝、設定、編譯、輸出比對的步驟。完成閘門可獨立檢查持久化產出是否存在、路徑正確、結構完整，降低「以為成功但實際未儲存」的風險。

4. **知識工作者輔助：研究彙整與報告生成**  
   例如從瀏覽器收集資料、整理到文件、產出 PDF。瀏覽器子代理負責網頁導航與 DOM 擷取，主代理負責檔案編輯與最終驗證，讓長篇任務不易在數百步後遺失上下文。

5. **企業內部舊系統的半自動化操作**  
   對於沒有現代 API、只能透過桌面應用程式操作的舊系統，StateAct 把 GUI 互動當作後備方案，優先嘗試資料庫、檔案或命令列存取，只在必要時才回到截圖點擊。

## 實作前置條件

- **資料準備**
  - 目標任務的完整流程說明與成功標準（輸出檔案、路徑、欄位結構、預期值範圍）。
  - 應用程式的可存取狀態清單：檔案位置、資料庫連線、DOM 結構、可用的 CLI/API。
  - 錯誤案例樣本：例如過去人工操作時曾發生的未儲存、寫錯路徑、公式被覆寫成常數等。

- **運算資源**
  - 可執行桌面環境的容器或虛擬機（論文使用 OSWorld 2.0 環境，實務上可用 Docker + VNC、VM 或雲端桌面）。
  - 足夠呼叫大型語言模型的預算與 API 配額；論文顯示 StateAct 每項任務成本約為純截圖方法的 1/9，但仍需評估總量。
  - 穩定的檔案系統與網路，讓主代理能持續使用 bash/Python 與檔案編輯器。

- **技能需求**
  - 熟悉 Python/bash 與常見桌面應用程式的資料結構（如試算表公式、DOM、檔案格式）。
  - 具備設計多智慧體系統與提示工程的能力，能區分「狀態操作」與「GUI 操作」的適用時機。
  - 有能力撰寫獨立的完成閘門檢查邏輯，並理解其只能抓結構性錯誤、無法完全驗證數值正確性的限制。

## 實作步驟建議

1. **拆解任務並標註狀態接點**  
   把目標流程拆成子目標，並為每個子目標判斷：是否能透過檔案、API、資料庫或 DOM 直接操作？若可以，歸給主代理；若必須視覺互動，才標給 GUI 子代理。

2. **建立主代理的狀態優先工具箱**  
   提供 persistent bash、Python 直譯器、檔案編輯器等工具，並封裝常用操作：讀寫 CSV/Excel、查詢資料庫、解析 HTML DOM、執行 shell 指令。讓主代理預設使用程式狀態而非截圖。

3. **實作 GUI 與瀏覽器專家子代理**  
   為少數無法程式化操作的步驟準備專職子代理。設計清晰的子目標輸入與結果輸出格式，並限制其使用範圍，避免主代理過度依賴視覺互動。

4. **設計完成閘門**  
   在任務結束後，由獨立的完成閘門直接檢查持久化產出：檔案是否存在、路徑是否正確、格式與必要欄位是否齊全。切記不要讓閘門讀取主代理的執行敘述，以保持客觀。

5. **加入長期上下文管理機制**  
   使用外部化計畫（如待辦清單）、新鮮上下文委派與壓縮機制，避免主代理在數百步後被過時細節淹沒。定期讓主代理回顧計畫與任務事實。

6. **迭代評估與瓶頸診斷**  
   先以二元成功與部分成功指標衡量整體表現，再分析失敗類型：是結構性失敗（可透過完成閘門補救）還是數值/推理錯誤（需要更強的規劃或領域知識）。根據結果調整工具與提示。

## 潛在風險與注意事項

- **過度信任完成閘門**  
  完成閘門擅長抓結構性失敗，但對數值正確性、語意合理性無能為力。建議把閘門視為「必要條件檢查」，而非「充分條件保證」。

- **狀態存取權限與安全性**  
  主代理直接操作檔案與後端，誤刪或覆寫的風險高於純 GUI 操作。應設定沙箱、備份機制與最小權限原則，並對寫入動作加上確認或復原點。

- **GUI 子代理使用比例失控**  
  若發現主代理頻繁呼叫 GUI 子代理，表示狀態工具不足或提示設計有問題。應回頭補強程式化介面，否則會失去成本與準確度優勢。

- **長期任務中的計畫漂移**  
  即使有了外部化計畫，模型仍可能在數十步後偏離目標。建議設立週期性計畫檢查點，並在關鍵里程碑後重新驗證子目標。

- **應用程式版本與狀態格式變動**  
  桌面軟體更新可能改變 DOM、檔案格式或 API。狀態接地工具需要持續維護，並建立回退到 GUI 子代理的容錯路徑。

## 與其他技術的整合建議

- **與 RAG / 知識庫整合**  
  把企業內部的操作手冊、常見錯誤處理方式、應用程式狀態結構說明放入向量資料庫，讓主代理在規劃階段檢索相關背景知識，減少推理錯誤。

- **與傳統 RPA 工具並行**  
  對於已經穩定運作的 RPA 腳本，可將其包裝成狀態操作工具供主代理呼叫；StateAct 負責需要彈性判斷的長期決策，RPA 負責高確定性、重複性的原子動作。

- **與監控與審計系統整合**  
  由於主代理直接修改程式狀態，建議把每個狀態變更、委派事件與完成閘門結果寫入日誌，方便事後追蹤、合規審查與錯誤重現。

- **與強化學習或微調管線結合**  
  論文指出瓶頸已從感知轉向推理。可收集失敗軌跡，針對規劃與驗證階段進行模型微調，或結合 ComputerRL 等混合動作空間的訓練方法進一步提升。

## 給不同背景讀者的閱讀建議

- **初學者**：這篇論文的核心訊息很直觀——「不要只看畫面，要直接操作背後的資料」。建議先理解「截圖是有損渲染」這個概念，再對照日常生活中「試算表顯示的數字可能是公式也可能是常數」的例子，就能掌握狀態接地的價值。技術細節如多智慧體委派與完成閘門可以稍後再深入。

- **AI 工程師**：重點放在架構設計與實作權衡。論文證明把 code/state 操作保留在主代理、把 GUI 互動降為後備子代理，能顯著降低成本並提升成功率。建議仔細研究完成閘門的獨立性設計，以及新鮮上下文委派如何解決長期任務的上下文膨脹問題。

- **研究人員**：這是一篇把瓶頸從感知推向推理的診斷型研究。建議關注第 5、6 節的消融與失敗分析，特別是「遞迴委派其實很少被使用」與「完成閘門仍會放行大量數值錯誤」這兩個發現，它們為後續的驗證機制與推理增強研究指出了明確方向。

- **產品經理**：這項技術適合「流程長、產出明確、可程式化程度高」的企業場景。評估導入時，請優先盤點目標任務是否能透過檔案/API/DOM 直接操作；若過度依賴視覺點擊，成本與準確度優勢會大打折扣。同時要記得，完成閘門能抓「有沒有交卷」，但抓不到「答案對不對」。
