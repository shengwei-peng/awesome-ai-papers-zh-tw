## 摘要翻譯

自然語言服務請求（Natural-Language Service Request）在執行開始前，往往需先由語言模型做出決策，因而消耗部分請求的延遲預算（Latency Budget）。本研究將 Jev 的決策導向應用程式介面（Decision-Oriented API）整合至邊緣服務編排（Edge Service Orchestration），以降低此額外開銷，同時維持服務完成（Service Completion）。該整合會擷取四到八個有限意圖欄位（Bounded Intent Fields），並套用共用驗證器（Shared Validator）、准入策略（Admission Policy）與排程器（Scheduler），將決策等待（Decision Waiting）納入整個請求時間軸（Request Timeline）。我們在 8,280 筆已驗證請求（Verified Requests），以及一條結合模型化執行（Modeled Execution）與真實光學字元辨識（Optical Character Recognition, OCR）服務的即時准入路徑（Live Admission Path）上，比較 Jev、兩個自架決策模型（Self-Hosted Decision Model）與三個託管大型語言模型（Hosted Large Language Model, LLM）。在 33 種測試條件下，相較於最快的 LLM，Jev 可將決策延遲中位數（Median Decision Latency）降低 22.7% 至 64.5%，且此延遲幾乎不受輸入大小（Input Size）、合約寬度（Contract Width）或目錄大小（Catalog Size）影響。在四欄位合約上，Jev 每次正確決策的 API 費用（API Fees per Correct Decision）降低 59.7% 至 80.9%，僅伴隨少許精確匹配點數（Exact-Match Points）的損失；而寬合約（Wide Contracts）則標示出此取代方式的極限。Jev 隨每個請求接收服務目錄（Service Catalog），對未見過的服務（Unseen Services）的命名準確度與已知服務相當。在即時准入路徑上，當負載高到使 LLM 的精確且準時（Exact and On Time）比例降至 0.1 以下時，Jev 仍能讓 0.91 至 0.95 比例的請求精確且準時。由於快取（Caching）重複描述會使各解譯器（Interpreter）的延遲趨於一致，Jev 的優勢主要來自全新決策（Fresh Decisions）。這些結果支持在有限合約上，以決策模型取代大型語言模型來執行延遲受限的准入。

### 核心貢獻（3～5點）
- 將 Jev 決策導向 API 整合至邊緣服務編排，顯著降低自然語言請求在執行前的決策延遲，同時維持服務完成。
- 設計包含有限意圖欄位擷取、共用驗證器、准入策略與排程器的整合架構，並將決策等待時間納入整個請求時間軸。
- 在 8,280 筆已驗證請求與即時准入路徑上驗證，Jev 相較於最快的 LLM 可降低 22.7% 至 64.5% 的決策延遲中位數，且延遲幾乎不受輸入大小、合約寬度或目錄大小影響。
- 在四欄位合約上，Jev 每次正確決策的 API 費用降低 59.7% 至 80.9%，並在高負載下仍能維持 0.91 至 0.95 的精確且準時比例，顯著優於 LLM。
- 證明寬合約標示出以決策模型取代 LLM 的極限，而 Jev 對未見過服務的命名準確度與已知服務相當。

### 適合對象
適合對邊緣運算、低延遲系統、服務編排、自然語言介面，以及尋求以輕量決策模型替代大型語言模型以降低延遲與成本的研究人員與系統工程師閱讀。

## 深度分析

#### 方法論解析

本研究的核心命題是：在邊緣服務編排（Edge Service Orchestration）的准入路徑（Admission Path）上，以決策導向應用程式介面（Decision-Oriented API）取代傳統的大型語言模型（Large Language Model, LLM），從而縮短自然語言服務請求（Natural-Language Service Request）被轉換為可執行任務前的決策延遲（Decision Latency），並在有限延遲預算（Latency Budget）內保留服務完成（Service Completion）率。

方法論可拆解為三個層次：**意圖合約（Intent Contract）的設計**、**共享下游元件的建立**，以及**兩層式評估架構**。

首先，研究將自然語言請求轉換為一組「有限意圖欄位（Bounded Intent Fields）」，形成 4 到 8 個欄位的型別化合約（Typed Contract）。這與 LLM 常見的自由生成（Free-Form Generation）再解析不同：Jev Decision Model（Jev 決策模型）直接輸出結構化決策，省去逐字生成與後續正規化的開銷。合約欄位可能包含服務名稱、資料落地位置、截止時間等，並由共用驗證器（Shared Validator）檢查語法與語意一致性。

其次，為了公平比較不同解譯器（Interpreter），研究建立共用的准入策略（Admission Policy）與排程器（Scheduler）。無論後端是 Jev、自架決策模型（Self-Hosted Decision Model）如 SemIf-Qwen3.5-4B 與 Laya，或是託管大型語言模型（Hosted Large Language Model）如 DeepSeek-V4.1-Flash、GLM-5.3-Flash、Qwen3.8-Flash，所有解譯器都面對相同的驗證、准入與排程邏輯。這種隔離設計確保觀察到的差異主要來自解譯器本身，而非下游策略。

第三，研究將**解譯**、**排隊（Queueing）**、**通訊（Communication）**與**執行（Execution）**放在同一條請求時間軸（Request Timeline）上，並把決策等待（Decision Waiting）時間納入計算。這對邊緣運算（Edge Computing）尤為重要，因為即使解譯只佔數百毫秒，也可能吃掉整個回應時間（Response Time）預算，導致任務逾時。

評估分為兩層。**解譯層**使用 EdgeIntent v1 基準資料集（EdgeIntent v1 Benchmark），包含 8,280 筆英文請求；其標籤先固定，文字僅在盲驗證器（Blind Verifier）能完整還原所有標籤時才保留，確保語意可從文字中恢復，降低標籤洩漏風險。**服務層**則結合即時解譯、模型化執行（Modeled Execution）以及真實的三節點光學字元辨識（Optical Character Recognition, OCR）服務：影像實際傳輸、執行辨識，再將回傳文字與參考標註比對。

此外，研究設計了目錄測試（Catalog Test）：每次請求都附上服務目錄（Service Catalog），檢驗解譯器能否正確命名未見過的服務（Unseen Services），並以凍結的服務分類器（Frozen Service Classifier）作為參考。同時，單一快取（Caching）策略套用到所有解譯器，以區分全新決策（Fresh Decisions）與重複請求的延遲貢獻。

#### 實驗數據解讀

實驗在 33 種測試條件下進行，變因包括輸入大小（Input Size）、請求捆綁方式與合約寬度（Contract Width）。主要量測指標為決策延遲中位數（Median Decision Latency）、每次正確決策的 API 費用（API Fees per Correct Decision）以及精確匹配點數（Exact-Match Points）。

**延遲表現**：相對於最快的 LLM，Jev 在 33 種條件下將決策延遲中位數降低 22.7% 至 64.5%。更關鍵的是，Jev 的延遲幾乎不受輸入大小、合約寬度或目錄大小（Catalog Size）影響。這顯示決策導向模型並非自迴歸生成，其計算成本與輸出結構較為固定，對於邊緣場景中常見的短請求與動態目錄具有規模穩定性。

**成本與正確性權衡**：在四欄位合約（Four-Field Contracts）上，Jev 每次正確決策的 API 費用比 LLM 低 59.7% 至 80.9%，而精確匹配分數僅下降少許。這個「以些微正確率換取大幅成本與延遲改善」的權衡，對於延遲受限的准入決策相當有利。值得注意的是，費用指標以「正確決策」為分母，已將錯誤決策浪費的金額納入考量，因此成本優勢並非來自於單純降價，而是來自於正確且便宜的決策。

**寬合約的極限**：當合約欄位增加（寬合約，Wide Contracts）時，決策模型的替代效益出現邊界。這意味著在欄位眾多、欄位間語意交互複雜的情境下，LLM 的生成與推理能力仍難以被完全取代。研究因此明確標示了 Jev 的適用範圍： bounded contracts，而非任意複雜的開放式任務。

**未見服務泛化**：在每次請求都接收服務目錄的設定下，Jev 對未見過服務的命名準確率與已知服務相當。這項結果非常重要，因為邊緣服務目錄會動態更新，解譯器不能僅依賴訓練時記憶的服務名稱。Jev 透過目錄條件化決策，展現出良好的即時泛化能力。

**即時准入路徑（Live Admission Path）**：在真實 OCR 服務與模型化執行組成的端到端系統中，當負載（Load）升高到 LLM 的「精確且準時（Exact and On Time）」比例跌至 0.1 以下時，Jev 仍能維持 0.91 至 0.95。這說明決策延遲不僅影響解譯階段，還會透過排隊效應放大；Jev 的低延遲使更多請求能在截止時間（Deadline）前完成正確服務。

**快取效應**：若重複描述被快取，所有解譯器的延遲都會趨於相近，因此 Jev 的主要優勢來自於全新決策。這對工作負載（Workload）特性有實務意涵：在高度重複的請求場景中，快取可緩解 LLM 的延遲劣勢；但在動態、個人化或首次請求為主的邊緣環境中，Jev 的效益最為顯著。即使延遲被快取拉平，成本與正確性之間的差異仍然存在。

#### 與現有研究的比較

本研究在相關文獻中的定位介於「自然語言解譯」與「服務編排」之間，並以統一的評估框架彌合兩者。

過去研究如 Lumi、NetConfEval、Manias et al. 主要聚焦於網路意圖解譯或網路配置任務（Network Configuration Tasks），較少將解譯器放入完整的准入路徑並量測服務完成率。服務編排方面，Chat-Driven Optimal Management、Intent Engine、InferLine 等系統雖結合解譯與編排，但多數未同時量測決策延遲（Decision Latency）、尾延遲（Tail Latency）、金錢成本、未見目錄（Unseen Catalog）、安全違規（Safety Violations）、截止完成（Deadline Completion）、提供負載（Offered Load）與系統測試平台（System Testbed）等全部維度。

根據文中 Table 1，最接近的十四項研究最多僅報告六項維度，而本研究對同一組解譯器量測了全部十一項維度。這是方法論上的重要進展：它不只在解譯層比較模型，還在真實 OCR 測試平台上比較端到端回應時間、負載承受能力與快取行為。

相較於 GLiNER2 等判別式擷取（Discriminative Extraction）方法，本研究進一步將擷取結果連結到服務放置決策（Placement Decision）與排程；相較於 InferLine 等系統，本研究則同時考慮自然語言解譯的延遲與正確性。Small models 與判別式方法在有限語言任務（Bounded Language Tasks）上的潛力已被討論，本研究以具體的邊緣服務場景驗證了它們在延遲、成本與動態目錄上的實用性。

然而，本研究也存在可討論的限制。首先，實驗僅針對 4 至 8 欄位的有限合約，寬合約（Wide Contracts）已顯示替代極限。其次，EdgeIntent v1 為英文資料集，未涵蓋多語言或更口語化的表達。第三，服務層實驗以 OCR 為主，雖具代表性，但其他類型的邊緣服務（如視訊分析、感測器融合）可能有不同的通訊與執行特性。第四，安全違規雖透過驗證器與准入策略在設計上防範，但文中未將其作為獨立量測結果報告。最後，與託管 LLM 的比較會受到 API 定價、模型版本與區域延遲影響，這些外部因素可能隨時間變化。

#### 可重現性評估

就本文提供的上下文而言，作者並未明確說明是否公開原始碼、資料集或模型權重。可重現性可從以下幾個面向評估：

**資料集**：EdgeIntent v1 是本文自建的基準資料集，包含 8,280 筆已驗證請求（Verified Requests）。若作者未釋出該資料集，其他研究者將難以直接複製解譯層的比較結果。資料集中的標籤固定與盲驗證器機制雖在方法上描述清楚，但具體的標籤定義、生成流程與驗證程式碼仍是重現所需。

**模型與 API**：Jev 是外部決策導向 API，其內部模型架構與訓練細節若未公開，則屬於黑箱元件。SemIf-Qwen3.5-4B 與 Laya 為自架決策模型，若其權重與推論程式未釋出，重現性亦受限。託管 LLM 雖可透過商業 API 呼叫，但不同時期的模型版本、定價與延遲可能影響可比性。

**系統層實作**：即時准入路徑包含共用驗證器、准入策略、排程器、快取策略、模型化執行與真實 OCR 服務。這些元件的程式碼、參數設定、負載產生器與成本計算公式若未公開，則端到端實驗難以完全重現。

整體而言，本研究的方法論描述相對完整，但在**開源（Open Source）釋出**方面，依目前資訊判斷仍屬有限。建議作者未來釋出 EdgeIntent v1、編排器程式碼、模型檢查點（Model Checkpoints）、API 呼叫腳本與成本模型，以提升社群的可重現性與後續比較基準。

#### 未來研究方向

基於本研究的發現，以下幾個方向值得進一步探索：

1. **擴展合約表達能力**：針對寬合約與階層式意圖（Hierarchical Intent）設計混合架構，讓決策模型處理常見欄位，LLM 僅在複雜或邊界案例上作為後備（Fallback），在延遲與正確性之間取得更佳平衡。

2. **多語言與多模態請求**：將 EdgeIntent 擴展至多語言，並結合影像、語音等多模態輸入，檢驗決策導向模型在更豐富邊緣場景中的穩定性。

3. **動態與對抗式目錄**：進一步測試目錄頻繁變動、服務名稱相似或惡意構造的目錄項目，評估解譯器的穩健性與安全違規風險。

4. **能源與碳成本**：雖然本研究未量測能耗，但邊緣裝置常受電力限制。未來可比較決策模型與 LLM 在能源消耗（Energy Consumption）上的差異，並將其納入准入策略。

5. **線上學習與個人化**：讓決策模型在邊緣端根據使用者回饋持續適應，減少對雲端 API 的依賴，同時維持低延遲。

6. **快取與預取策略**：設計針對自然語言描述的語意快取（Semantic Caching）與預取機制，並量化其對不同解譯器在真實工作負載下的影響。

7. **形式化驗證與安全保證**：將共用驗證器與准入策略擴展為可形式化驗證的元件，明確量測並降低安全違規機率。

8. **開放生態系統與標準化基準**：建立公開的邊緣服務解譯基準，涵蓋延遲、成本、正確性、負載與服務完成率，促進決策模型與 LLM 之間的公平比較。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文聚焦於自然語言服務請求在邊緣運算場景中，必須先經過語意解譯與放置決策才能開始執行，而這段決策等待會消耗整體回應時間的延遲預算。傳統使用大型語言模型（LLM）作為解譯器雖然具備強大的語意理解能力，但其決策延遲較高，容易壓縮後續排隊、通訊與執行階段可用的時間。因此，作者希望以專門的決策模型取代 LLM，在保留服務完成度的同時降低准入路徑上的延遲。

**Q2：為什麼現有的 LLM 方法在邊緣服務編排中不夠理想？**
A：現有託管或自架的 LLM 主要針對開放式生成任務設計，並非為「有限意圖欄位」的決策擷取最佳化，因此決策延遲與成本都偏高。實驗顯示，LLM 的決策延遲會隨輸入大小、合約寬度與目錄大小而明顯變動，對於具有嚴格截止時間的邊緣服務來說難以預測。此外，過去相關研究很少同時衡量決策尾端延遲、計費 API 成本、未見目錄選項與截止時間完成率，使得系統設計者難以全面評估 LLM 在准入路徑上的實際代價。

**Q3：低延遲的邊緣服務編排為什麼重要？**
A：邊緣運算中的服務通常面臨嚴格的回應截止時間與有限的資源，每一毫秒的解譯延遲都會直接壓縮實際執行可用的時間餘裕。更快的准入決策能讓系統在相同負載下接納更多請求，並提高「精確且準時」完成的比率。這對光學字元辨識、擴增實境、工業控制等延遲敏感型應用尤其關鍵。

**Q4：Jev 決策模型的核心方法是什麼？**
A：Jev 提供一個決策導向應用程式介面（API），能從自然語言請求中擷取四到八個有限意圖欄位，形成型別化的意圖合約。這些欄位接著由共用的驗證器、准入策略與排程器處理，並將解譯、排隊、通訊與執行統一放在同一條請求時間軸上考量。透過把決策等待視為延遲預算的一部分，系統能更準確地判斷每個解譯器對服務完成度的影響。

**Q5：Jev 相較於 LLM 的關鍵創新在哪裡？**
A：Jev 以判別式決策擷取取代生成式語言建模，專注於輸出有限且邊界明確的意圖欄位，因此能顯著降低決策延遲中位數。與 LLM 不同，Jev 的延遲幾乎不會隨輸入大小、合約寬度或目錄大小而變動，表現更穩定。此外，當每次請求都附上服務目錄時，Jev 對未見過的服務也能達到與已知服務相近的命名準確率。

**Q6：為什麼要採用有限意圖欄位與共用元件的設計？**
A：有限意圖欄位能縮小輸出空間，使驗證與排程更快完成，並降低決策模型的負擔。共用驗證器、准入策略與排程器則確保不同解譯器之間的比較是公平的，並能單獨凸顯解譯速度對整體服務的貢獻。同時，把決策等待納入請求時間軸的設計，讓系統能真實反映邊緣環境中各階段延遲的交互影響。

**Q7：論文進行了哪些實驗來驗證方法？**
A：實驗分為兩層：解譯層使用 EdgeIntent v1 基準資料集，包含 8,280 個經盲驗證器確認的英文請求；服務層則結合即時解譯、模型化執行階段，以及一個真實的三節點光學字元辨識服務。作者比較了 Jev、兩個自架決策模型（SemIf-Qwen3.5-4B 與 Laya）和三個託管 LLM，在 33 種測試條件下衡量決策延遲、語意正確性、API 費用與截止時間完成率。

**Q8：論文的主要量化結果是什麼？**
A：在 33 種測試條件下，Jev 相較於最快的 LLM 可降低 22.7% 至 64.5% 的決策延遲中位數。在四欄位合約上，每次正確決策的 API 費用比 LLM 低 59.7% 至 80.9%，僅犧牲少數精確匹配點數。在即時准入路徑上，當負載高到使 LLM 的精確且準時完成率降至 0.1 以下時，Jev 仍能維持 0.91 至 0.95 的水準。

**Q9：Jev 的表現對輸入大小、目錄大小與快取有何敏感度？**
A：Jev 的延遲對輸入大小、合約寬度與目錄大小幾乎不敏感，而 LLM 則會隨這些因素明顯變慢。當重複描述被快取時，各解譯器的延遲會趨於相近，因此 Jev 的優勢主要來自全新決策。不過，寬合約是替代 LLM 的極限，隨著欄位增加，Jev 的精確匹配準確率會出現較明顯下降。

**Q10：Jev 適合部署在哪些實際場景？**
A：Jev 適合部署在必須在嚴格截止時間內解譯自然語言服務請求的邊緣准入控制器，例如光學字元辨識、影像分析、物聯網指令路由等。它可以作為一個決策導向的微服務，與現有的邊緣服務編排系統並存。由於其低延遲特性，能為下游服務保留更多執行時間，提升整體回應品質。

**Q11：在產品化時需要考慮哪些成本、延遲與準確性的權衡？**
A：Jev 以少許精確匹配點數為代價，換取顯著的延遲與成本降低，對於下游驗證器與排程器能修正或容忍輕微語意偏差的場景來說是合理取捨。相較於託管 LLM，Jev 每次正確決策的 API 費用明顯較低，適合高頻請求。產品團隊在導入前應先確認有限意圖合約能否涵蓋目標服務的語意需求。

**Q12：這項研究可能對邊緣服務編排領域帶來什麼影響？**
A：這項研究支持在延遲受限的准入路徑上以專用決策模型取代通用 LLM，使自然語言介面在即時邊緣系統中更具可行性。它將研究焦點從生成式流暢度轉向有限、可驗證的決策品質。未來可能促使網路與邊緣編排領域出現更多針對特定決策任務設計的輕量 API 與模型。

**Q13：論文承認了哪些限制？**
A：論文指出，寬合約是 LLM 替代的極限，當合約欄位增加時，決策模型的精確匹配準確率下降，使得替代效益減弱。實驗中的執行階段為模型化，且僅使用一個真實 OCR 服務，因此對於更多樣化的服務與網路條件仍需進一步驗證。此外，快取重複請求會縮小各解譯器之間的延遲差距，降低 Jev 在高重複性工作負載上的優勢。

**Q14：Jev 在哪些情況下可能表現不佳？**
A：當合約欄位很多時，判別式擷取的準確率會低於生成式 LLM，導致精確匹配分數下降。如果請求用詞嚴重劣化，或服務目錄包含大量未見選項而分類器支援不足，Jev 也可能出錯。另外，在高度重複的工作負載中，由於快取能讓 LLM 也達到相近延遲，Jev 的速度優勢會被削弱。

**Q15：未來可以朝哪些方向繼續研究？**
A：未來可將有限意圖合約擴展到超過八個欄位，並設計動態或自適應的准入策略以兼顧準確與速度。結合 Jev 與輕量 LLM 後備機制，在模糊請求時啟用生成式模型，可在保持低延遲的同時提升準確率。此外，針對未見服務的線上學習、能源效率，以及在更多真實異質服務上的評估，也都是值得深入的方向。

## 實務應用指南

### 適用場景

1. **智慧城市邊緣影像服務**：交通監控、公共安全或工業巡檢系統中，使用者以自然語言下達「辨識這張路口影像中的車牌，30 秒內回傳，資料不離開本區域」等指令。Jev 決策模型可在毫秒級完成意圖解譯與放置決策，保留完整回應時間給後續影像傳輸與 AI 推論。

2. **低延遲工業物聯網（IIoT）控制**：產線操作員以口語或簡短文字請求「在 A 機台執行品質檢測，延遲低於 50 ms」。由於延遲預算極緊，傳統 LLM 的數百毫秒決策等待會直接吃掉可用時間，Jev 的有限意圖欄位與共用驗證器可快速完成准入與排程。

3. **電信網路意圖導向編排**：5G/6G 網路切片、頻寬預留或邊緣運算節點選擇等場景，營運商以自然語言輸入服務需求。Jev 適合做為准入路徑上的解譯器，將「期望結果」轉成可執行的合約欄位，再交給後端排程器與策略引擎。

4. **零售或醫療端點 OCR 服務**：收銀台、倉儲或醫療影像工作站需要即時文字辨識，請求常伴隨「本地執行、特定截止時間、指定解析度」等約束。Jev 可在輸入大小、合約寬度或目錄規模變化時維持穩定決策延遲，避免 LLM 隨輸入增長而變慢。

5. **快取命中率低的高變動服務目錄**：當服務目錄頻繁更新、使用者請求用詞多樣且難以依賴快取時，Jev 對「未見過服務」的命名準確度與已知服務相當，適合做為持續演進的邊緣服務閘道。

### 實作前置條件

**資料前提**
- 必須先定義「有限意圖合約」：將自然語言請求對應到 4–8 個有界欄位（例如服務名稱、執行地點、截止時間、資料保留策略、優先權等）。
- 需要已驗證的請求資料集，並以盲驗證器確認每筆標註可從文字完整復原，確保訓練與評估基準可靠。
- 服務目錄需結構化，並能隨請求傳入，讓模型在決策時看見完整選項空間。

**運算前提**
- 若採用 Jev 這類決策導向 API，主要成本在於 API 呼叫延遲與計費；若採用自架決策模型（如 SemIf-Qwen3.5-4B 或 Laya），則需準備邊緣 GPU/CPU 推論資源。
- 准入路徑需部署共用驗證器、准入策略與排程器，並將決策等待納入請求時間軸監控。

**技能前提**
- 團隊需熟悉意圖導向網路、邊緣服務編排與延遲預算分析。
- 需具備將自然語言需求轉為型別化合約的領域工程能力，以及設計盲驗證與服務完成度評估指標的能力。

### 實作步驟建議

1. **定義意圖合約與服務目錄**：從現有自然語言請求日誌中萃取出 4–8 個核心欄位，建立型別化合約範本，並將服務目錄結構化為每個請求都會攜帶的上下文。

2. **建立已驗證評估基準**：收集數千筆真實請求，由盲驗證器檢查文字是否能完整復原所有標註欄位，形成 EdgeIntent v1 等級的內部資料集，做為後續比較基準。

3. **選擇解譯器並建立准入路徑**：同時導入 Jev 決策模型與一至兩個對照 LLM，在相同合約、相同驗證器與排程器下進行比較。確保決策等待時間被記錄在請求時間軸中。

4. **量測決策延遲、正確性與成本**：在不同輸入長度、合約寬度、目錄大小與請求率下，量測中位數決策延遲、每次正確決策的 API 費用、精確匹配分數，以及未見服務的命名準確度。

5. **加入快取政策並區分全新與重複決策**：對所有解譯器套用統一快取策略，比較快取命中與全新決策的延遲差異，確認 Jev 的優勢主要來自「全新決策」而非快取。

6. **接上真實服務並評估完成度**：將解譯器接入即時准入路徑，搭配模型化執行或真實 OCR 服務，評估「精確且準時」的請求比例，找出 LLM 無法滿足延遲預算的負載區間。

7. **迭代合約寬度與欄位設計**：若寬合約（欄位較多）導致決策模型準確度顯著下降，則將其視為替代極限，考慮拆分合約或保留 LLM 處理複雜欄位。

### 潛在風險與注意事項

- **合約過寬導致準確度下降**：Jev 在 4 欄位合約表現最佳，寬合約可能逼近替代極限。建議先從窄合約開始，逐步增加欄位並監控精確匹配分數。
- **過度簡化語意**：決策導向 API 犧牲部分生成彈性，若使用者請求包含合約未涵蓋的細微條件，可能遺失關鍵語意。需設計良好的驗證器與拒絕機制。
- **快取掩蓋真實延遲**：若評估時未區分全新與重複請求，可能誤以為 LLM 也足夠快。實務上應分別報告兩種情況，並以全新決策做為主要優化目標。
- **目錄動態更新**：雖然 Jev 對未見服務表現良好，但若目錄規模或命名方式劇烈變化，仍需重新評估並可能重新訓練或微調模型。
- **成本與正確性的權衡**：Jev 可顯著降低 API 費用，但會損失少數精確匹配點數。對於安全關鍵場景（如醫療、自動駕駛），需額外評估錯誤決策的後果。

### 與其他技術的整合建議

- **與現有 LLM 閘道並存**：可將 Jev 設為低延遲、有限合約請求的預設解譯器，僅在合約過寬、語意異常或驗證失敗時，將請求升級至託管 LLM 處理。
- **與意圖導向網路框架整合**：Jev 的輸出可直接對接 Lumi、Intent Engine 等中間表示法，再交由網路編排器或 Kubernetes 邊緣排程器執行。
- **與服務網格或邊緣閘道結合**：將 Jev 部署在 API Gateway 或 Envoy 等閘道層，負責請求准入、服務命名與放置決策，後端維持既有微服務架構。
- **與監控與可觀測性工具串接**：將決策等待、快取命中、合約欄位驗證結果寫入 Prometheus/Grafana，建立延遲預算消耗與服務完成度的即時儀表板。
- **與小型判別式模型互補**：對於命名實體辨識或欄位擷取，可結合 GLiNER2 等判別式模型做前處理，再由 Jev 進行最終決策與准入判斷。

### 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦「適用場景」與「實作步驟建議」兩節，理解為何自然語言請求需要「解譯器」、什麼是「有限意圖欄位」，以及 Jev 為何比大型語言模型更適合低延遲邊緣應用。遇到技術名詞可對照文末詞彙表，不必深究所有模型名稱與實驗條件。

**AI 工程師**：請重點閱讀「實作前置條件」與「潛在風險與注意事項」，特別留意合約寬度、快取政策、盲驗證器設計，以及決策等待如何納入請求時間軸。建議將本文的評估維度（延遲、成本、正確性、未見服務、完成度）作為導入決策模型時的檢查清單。

**研究人員**：本文的貢獻在於系統性地比較決策模型與 LLM 在 11 個維度上的表現，並提出「決策模型替代」的邊界條件。建議關注實驗設計、EdgeIntent v1 基準的建構方式，以及寬合約與未見服務測試如何標定替代極限，這些都可延伸為後續研究問題。

**產品經理**：請從「適用場景」與「與其他技術的整合建議」切入，評估 Jev 是否適合貴產品的延遲與成本結構。關鍵取捨在於：以少量精確匹配點數換取 22.7–64.5% 的決策延遲降低與 59.7–80.9% 的 API 成本下降。若產品面對的是高頻、低延遲、合約可預先定義的邊緣服務，Jev 值得優先試點。
