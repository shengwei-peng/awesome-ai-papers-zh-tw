**核心問題定義**

本文針對 LLM 代理 (LLM agents) 在呼叫 API 時遭遇的「靜默 API 失敗」(silent API failure) 問題進行研究。所謂靜默失敗，是指 API 回傳 HTTP 200 狀態碼與格式正確的回應，但內容卻未真正回答請求——例如忽略命名錯誤的篩選條件 (misnamed filter)、悄悄截斷分頁 (page)、或接受拼字錯誤的參數值。這類失敗無法僅從單次回應本身察覺，必須透過額外的查詢才能驗證。

**系統架構：SilentGuard**

SilentGuard 的設計哲學是將「是否信任工具結果」的決策權從語言模型移轉到執行環境 (harness)，即實際執行工具呼叫的程式碼層級。其運作流程分為三個階段：

1. **不變式檢查 (Invariant Check)**：對每個工具結果套用兩類檢查
   - **精確不變式 (Exact Invariants)**：基於數學必然性的檢查，例如「帶條件 A 的計數 + 帶條件 ¬A 的計數 = 不帶條件的總計數」、「列表回傳的每筆記錄都必須符合篩選條件」、「請求參數必須符合 API 公開文件記載的合法參數名稱」
   - **學習型不變式 (Learned Contracts)**：當不存在精確不變式時，從乾淨回應中學習契約 (contracts)，用於捕捉異常模式

2. **重複驗證 (Re-check)**：對失敗結果再執行一次相同呼叫，以排除暫時性錯誤

3. **差異化處置 (Differentiated Action)**：
   - 若精確不變式失敗（α̂ⱼ ≤ τ），執行環境**直接扣留 (withhold)** 該值，僅允許通過檢查的答案進入代理
   - 若學習型檢查失敗，僅**發出警告 (warn)**，保留數值但告知代理哪項檢查未通過

此設計的關鍵洞見在於：精確不變式失敗在邏輯上證明 API 未正確回答請求，因此可以安全地強制執行；而學習型檢查本身可能誤判，因此只能作為非約束性的警告。

**三項關鍵要素的受控比較**

論文透過控制變數實驗分離出三個獨立要素：

| 要素 | 作用 | 實驗結果 |
|------|------|----------|
| 證據 (Evidence) | 提供一致性檢查結果 | 缺乏證據時，無論是建議 (71.7% 錯誤) 或阻擋 (70.8% 錯誤)，效果皆有限 |
| 許可 (Permission) | 允許代理回答「無法確定」(cannot be determined) | 搭配警告可將錯誤率從 70.1% 降至 18.2%，但各模型差異極大 (0–59%) |
| 強制執行 (Enforcement) | 由執行環境決定結果處置 | 跨模型表現穩定，錯誤率降至 1.7%，最高僅 4% |

此三要素的發現揭示一個反直覺的事實：即使代理「看見」警告（陳述信心度下降且會提及警告），仍有 64.4% 的機率回報被標記的計數。唯有將決策權從模型手中移走，才能可靠地防止錯誤答案。

**風險-覆蓋率權衡 (Risk-Coverage Trade-off)**

由於 SilentGuard 透過「棄答」(abstaining) 而非「恢復」來避免錯誤，其設計必然面臨覆蓋率下降。在 25% 錯誤率情境下，SilentGuard 能回答 67% 的任務，其中僅 3.3% 為錯誤答案；而無防護或僅有建議的方法則維持約 24.6% 的錯誤風險。

#### 實驗數據解讀

**靜默失敗的普遍性測量 (§5.1)**

在 15 個公開研究 API 中，有 11 個 (73%) 會以靜默方式處理至少一類合理錯誤，某些案例的計數膨脹高達 691 倍。這項數據顯示問題並非邊緣案例，而是研究領域 API 生態的系統性缺陷。

**基準測試結果**

| 場景 | 無防護代理 | SilentGuard | 改善幅度 |
|------|-----------|-------------|----------|
| 7 個開源模型 (open models)，目標錯誤 | 74.0% 錯誤 | 1.7% 錯誤 | -72.3 pp |
| 3 個前沿模型 (frontier models)，目標錯誤 | 70.2% 錯誤 | 0.5% 錯誤 | -69.7 pp |
| 9 個真實 API，文件被竄改一個篩選名稱 | 89.8% 錯誤 | 21.3% 錯誤 | -68.5 pp |
| 僅使用參數文件檢查 | — | 21.0% 錯誤 | 接近完整系統 |

**關鍵觀察：警告 vs. 強制執行的差異**

實驗中一個驚人的數據是：當僅提供警告（不扣留數值）時，錯誤率仍高達 70.1%。這證明了「代理並非看不見問題，而是看見了仍然回答」。相較之下，由執行環境強制扣留則將錯誤率降至 1.7%。此差距凸顯了當前以模型為中心 (model-centric) 的修正策略的根本侷限。

**新錯誤類型的泛化能力**

在新錯誤類型 (new fault types) 上，僅靠執行環境的檢查可將錯誤率從 61.1% 降至 24.5%。雖然改善幅度不如目標錯誤，但顯示系統對未見過的錯誤模式仍有一定程度的泛化能力。

**裁判模型 (LLM Judge) 的盲點**

提供一致性檢查結果給裁判模型時，82.4% 的錯誤執行會被標記，但 13.9% 的乾淨執行也會被誤標。更關鍵的是，被標記的執行中有 77.4% 仍被代理回報為答案。這顯示單純提升模型感知能力並不足以解決問題。

**無錯誤任務的保持能力**

在 fault-free tasks 上，SilentGuard 不會造成表現損失，這對實務部署至關重要——防護機制不應在正常情境下產生負面影響。

#### 與現有研究的比較

**與既有修正策略的對比**

| 方法類型 | 代表文獻 | 錯誤率 | 核心限制 |
|---------|---------|--------|----------|
| 檢查清單提示 (Checklist prompt) | Sun et al., 2024 | ~74% | 模型傾向忽略自身觀察 |
| 審查模型 (Reviewer model) | Ta et al., 2026 | ~74% | 仍依賴模型判斷 |
| 結果監控器 (Outcome Monitors) | Panthi & Abdelfattah, 2026 | ~74% | 警告為非約束性 |
| LLM 裁判 (LLM judge) | 多項 | 77.4% 被標記仍被回報 | 模型「知情仍答」 |
| **SilentGuard** | 本文 | **1.7%** | 需預先定義不變式 |

**相較於先前工作的核心突破**

1. **從模型中心轉向執行環境中心**：現有方法皆假設模型能正確處理警告，但本文實證顯示此假設不成立。SilentGuard 將信任決策從模型移至程式碼層級，繞過了「模型明知故犯」的根本問題。

2. **精確 vs. 學習型檢查的分層處理**：相較於結果監控器僅使用學習型契約，SilentGuard 區分精確不變式（可強制扣留）與學習型檢查（僅警告），提供了更細緻的風險管理。

3. **量化「模型知情仍答」現象**：本文不僅指出問題，更透過控制實驗量化了證據、許可、強制執行三要素的獨立貢獻，這在先前研究中付之闕如。

**本文承認的限制**

1. **無法處理查詢字串內的篩選條件**：參數檢查無法看見嵌入查詢字串 (query string) 中的篩選，這是當前架構的盲點。

2. **對短暫性錯誤的處理不如盲目重試**：對於一兩次呼叫內即可恢復的錯誤，盲目重試 (blind retry) 表現更佳。

3. **覆蓋率下降的代價**：SilentGuard 透過棄答避免錯誤，這意味著在錯誤率高的環境中，回答率會顯著下降。

4. **新錯誤類型的泛化有限**：對未見過的錯誤模式，僅靠執行環境檢查只能將錯誤率降至 24.5%，仍有相當大的改進空間。

5. **不變式需要預先定義**：精確不變式需要領域專家設計，這對快速演化的 API 生態構成部署障礙。

對於學習型檢查失敗的情境，未來可探索：
- 將警告升級為人類審核請求
- 設計有效的人機協作介面
- 從人類回饋中持續改進契約

**10. 理論基礎的建立**

當前方法以經驗為主，未來可建立：
- 不變式檢查的計算複雜度分析
- 風險-覆蓋率權衡的理論界限
- 與資訊理論的連結（證據的資訊量）

## 論文問答

**Q1：什麼是「靜默 API 失敗」(silent API failure)，為什麼它對 LLM 代理特別危險？**
A：靜默 API 失敗指的是 API 在收到請求時，雖然回傳 HTTP 200 狀態碼與格式正確的資料，卻因為忽略部分請求（例如命名錯誤的篩選條件、拼字錯誤的參數值，或悄悄截短分頁）而給出看似合理但實際錯誤的結果。這種失敗對 LLM 代理特別危險，因為代理通常依賴工具回傳的內容來建構答案，而靜默失敗不會留下任何錯誤訊號——沒有 timeout、沒有格式錯誤、沒有狀態碼異常，僅憑回應本身無法察覺問題。論文指出，這類故障需要額外對同一 API 進行查詢才能偵測，因此單純檢查回應內容的傳統方法完全失效。更糟的是，代理即使被告知結果有問題，仍有 77.4% 的機率會回報被標記的錯誤計數，顯示出模型在面對「看似成功」的錯誤結果時缺乏可靠的自我修正機制。

**Q2：為什麼現有的方法（如檢查清單提示、審查模型、LLM 裁判）無法有效解決靜默 API 失敗？**
A：現有方法的核心問題在於它們把「是否信任工具結果」的決策權交給了模型本身，但實驗顯示模型即使看見問題仍會繼續作答。論文的受控比較揭示了三個關鍵發現：第一，沒有證據（evidence）時，無論裁判的判定是建議（71.7% 錯誤率）還是被強制阻擋（70.8% 錯誤率），效果都接近無防護代理的 74.0%。第二，代理預設傾向給出數字，即使被允許回答「無法確定」，沒有證據的提示也毫無作用。第三，也是最關鍵的一點——單純警告（warning）效果極差，因為代理在收到警告後仍有 64.4% 的機率回報錯誤答案。這說明問題不在於模型「看不見」故障，而在於它「看見了卻不行動」，因此必須由執行環境（harness）強制介入才能可靠地防護。

**Q3：靜默 API 失敗在真實世界的研究 API 中有多普遍？**
A：論文的測量結果顯示靜默 API 失敗極為普遍——在 15 個公開研究 API 中，有 11 個會以這種方式回應至少一個看似合理的錯誤。更令人震驚的是，某些故障會讓計數結果膨脹最多達 691 倍，這意味著代理可能會給出與正確答案相差數百倍的數字卻渾然不覺。這些故障涵蓋三種類型：忽略命名錯誤的篩選條件、悄悄丟棄有拼字錯誤的篩選值，以及無預警地截短分頁結果。論文也引用了先前研究，證明正式環境（production）的 API 在面對僅以散文描述的限制時也會以 HTTP 200 回應未理解的查詢。這些證據共同顯示，靜默失敗並非罕見的邊緣案例，而是 LLM 代理在真實部署中必須面對的常態風險。

**Q4：SilentGuard 的核心方法是什麼？它與現有解決方案的根本差異為何？**
A：SilentGuard 的核心方法是「不變式感知執行環境強制」(invariant-aware harness enforcement)，它把「是否信任工具結果」的決策從模型手中轉移到執行工具呼叫的執行環境中。具體而言，SilentGuard 會對每個工具結果套用不變式檢查——任何正確的 API 都必須滿足的性質，例如「帶條件的計數加上其否定的計數必須等於無條件的總計數」。當結果通過檢查時正常釋放給代理；當結果失敗時會重新檢查一次，若再次失敗則根據檢查的確定性採取不同行動：精確不變式失敗時由執行環境直接扣留該值，學習型不變式失敗時則附加警告。這個設計的根本差異在於它不依賴模型自身的判斷力，因此跨模型的表現差異極小——在 7 個開源模型上將錯誤率從 74.0% 降至 1.7%，在 3 個前沿模型上從 70.2% 降至 0.5%，且無需額外的模型呼叫。

**Q5：SilentGuard 中的「不變式」(invariant) 是什麼？如何分類？**
A：不變式是任何正確的 API 都必須滿足的性質，是 SilentGuard 用來偵測靜默失敗的「證據」來源。論文將不變式分為兩大類：精確不變式（exact invariants）與學習型不變式（learned invariants）。精確不變式包括三種：計數恆等式（如「條件 A 的計數 + 非 A 的計數 = 總計數」）、列表完整性（回傳的每筆記錄都必須符合篩選條件）、以及規格符合性（請求必須使用 API 文件記載的參數）。學習型不變式則在沒有精確規則可用時，從乾淨的回應中學習契約（contracts）。這個分類至關重要，因為它決定了執行環境後續的行動：精確不變式一旦被違反就證明 API 沒有正確回答請求，因此執行環境會直接扣留該值；學習型不變式本身可能也有錯，所以只能附加警告而非阻擋。

**Q6：為什麼 SilentGuard 要區分「扣留」(withhold) 和「警告」(warn) 兩種處理方式？**
A：這個設計選擇反映了對不確定性的嚴謹處理。當精確不變式失敗時，邏輯上是確定性的——例如「計數 A + 計數非 A ≠ 總計數」這種數學恆等式被違反，就證明了 API 沒有回答原始請求，此時執行環境扣留該值並只接受通過檢查的答案是完全合理的。相對地，學習型不變式是從歷史乾淨資料中歸納出來的契約，它本身可能並非永遠正確，若直接扣留可能會在乾淨任務上造成過度防護。因此 SilentGuard 對學習型不變式失敗只附加警告，讓代理仍可使用該值但知道可能有問題。這個區分也解釋了為什麼論文的消融實驗顯示「單純警告」效果很差（70.1% 錯誤率）——警告無法強制改變模型的行為，只有扣留才能可靠地防止錯誤答案的產生。

**Q7：什麼是 AgentOrchBench？它評估了哪些面向？**
A：AgentOrchBench 是論文作者為此研究設計的基準測試，特色是包含精確答案（exact answers）以便準確評估代理的正確性。整個評估涵蓋四個基準測試、計數與列表兩種類型的答案、已發表的方法與控制組、7 個開源模型，以及後續加入的 3 個前沿模型。更重要的是，評估採用了「預先寫下的預測」(predictions written down in advance) 的方式，這種方法論設計避免了評估過程中的隨機性或事後調整，確保結果的可重現性與公平性。基準測試的設計也涵蓋了故障注入，使研究者能系統性地測量代理在不同故障情境下的表現，並與 SilentGuard 的防護效果進行對比。

**Q8：SilentGuard 的主要實驗結果為何？**
A：最關鍵的結果是錯誤率的大幅下降：在 7 個開源模型上，SilentGuard 將目標錯誤（target faults）下的錯誤率從 74.0% 降至 1.7%，且在無錯誤任務（fault-free tasks）上沒有任何損失；在 3 個前沿模型上，錯誤率從 70.2% 降至 0.5%。在 9 個真實 API 上，當文件中的某個篩選名稱被刻意更改時，錯誤率從 89.8% 降至 21.3%，而單獨使用「參數符合文件」的檢查就能達到 21.0%。在風險與覆蓋率的權衡上，當故障率為 25% 時，SilentGuard 能回答 67% 的任務且僅有 3.3% 的錯誤率，而無證據或僅有建議的方法則停留在接近 24.6% 的風險水準。這些結果一致顯示，強制執行（enforcement）而非僅僅建議或警告，才是跨模型可靠防護的關鍵。

**Q9：受控比較揭示了「證據」、「許可」、「強制執行」三個要素的相對重要性為何？**
A：論文的受控比較（Table 2）清晰地分離了三個要素的貢獻。第一個要素是證據（evidence）：沒有證據時，無論裁判的判定是建議（71.7% 錯誤率）還是被阻擋（70.8% 錯誤率），效果都與無防護代理相近，證明單獨的模型判讀無法取代實證檢查。第二個要素是許可（permission）：代理預設傾向給出數字，而一個簡短的提示允許回答「無法確定」就能把警告後的錯誤率從 70.1% 降至 18.2%，但這個降幅因模型而異（0–59%），且沒有證據時同樣的提示毫無作用。第三個要素是強制執行（enforcement）：當執行環境決定如何處理失敗結果時，結果對模型的依賴大幅降低——扣留值的執行環境在任何模型上都只留下最多 4% 的錯誤率。這三個要素的相對重要性說明：證據是必要前提，許可能改善但不可靠，唯有強制執行才能跨模型穩定防護。

**Q10：SilentGuard 在哪些真實場景中價值最大？**
A：SilentGuard 在任何 LLM 代理需要依賴外部 API 做出關鍵決策的場景中都極具價值，特別是科學研究、醫療資訊查詢、金融數據分析等領域。在這些場景中，代理可能會查詢文獻資料庫、基因與蛋白質資料庫、樣本目錄等，而一個被靜默失敗污染的計數可能導致研究結論錯誤或臨床決策失誤。論文特別強調了 15 個公開研究 API 中有 11 個存在靜默失敗，計數膨脹可達 691 倍，這對依賴精確數據的科學應用是巨大的風險。此外，在生產環境中部署的代理——例如自動預訂旅遊、查詢庫存、處理訂單等——也面臨同樣風險，因為正式環境的 API 經常接受未理解的查詢卻仍回傳 HTTP 200。SilentGuard 的價值在於它不需要修改 API 本身，也不需要重新訓練模型，就能為這些場景提供一層可靠的防護。

**Q11：使用 SilentGuard 時，風險與覆蓋率之間的權衡為何？**
A：論文透過 Figure 2 明確呈現了風險（risk，即錯誤率）與覆蓋率（coverage，即回答率）之間的權衡關係。SilentGuard 的策略是透過棄答（abstaining）而非恢復（recovering）來避免錯誤答案——在故障情境下，它主要回應「無法確定」，因此覆蓋率會下降但錯誤率也大幅降低。具體而言，在 25% 故障率下，SilentGuard 能回答 67% 的任務且僅有 3.3% 的錯誤率，而無證據或僅有建議的方法則停留在接近 24.6% 的高風險水準。這個權衡對產品設計很重要：若應用場景對錯誤極度敏感（例如醫療或財務），則應選擇較高的棄答率以換取極低的錯誤率；若應用場景需要高覆蓋率，則可調整不變式的嚴格度。值得注意的是，SilentGuard 無法看見讓其檢查仍然成立的故障，這是其覆蓋率的天然上限。

**Q12：SilentGuard 對 LLM 代理設計領域可能產生什麼影響？**
A：SilentGuard 的研究結果可能從根本上改變 LLM 代理的設計思路，從「讓模型更聰明」轉向「讓執行環境更可靠」。論文的消融實驗揭示了一個重要洞見：模型即使看見問題也常常不行動，這意味著單純提升模型能力或加入更多提示並不能解決工具可靠性問題。這促使研究者重新思考代理架構中「誰該負責什麼決策」的分工——涉及安全與正確性的關鍵決策應由執行環境強制執行，而非交給模型自行判斷。此外，論文中對「證據」、「許可」、「強制執行」三要素的分離，也為未來的代理設計提供了清晰的分析框架。從產業角度，這項研究鼓勵 API 提供者與代理開發者更重視「契約式設計」(contract-based design)，讓 API 行為可以被形式化驗證，進而建構更可信賴的代理生態系。

**Q13：論文承認 SilentGuard 有哪些限制？**
A：論文明確承認了幾項重要限制。首先，SilentGuard 無法看見讓其檢查仍然成立的故障——例如若一個故障讓所有不變式都恰好滿足，則系統無法偵測，這是其覆蓋率的天然上限。其次，盲目重試（blind retry）在某些故障類型上表現更好，特別是那些在一兩次呼叫內就能自行清除的故障，而 SilentGuard 的棄答策略在這些情況下反而會損失覆蓋率。第三，參數檢查無法看見藏在查詢字串（query string）內部的篩選條件，這是一個具體的技術盲點。最後，學習型不變式本身可能並非永遠正確，因此對這類檢查失敗只能警告而無法扣留，這意味著某些故障仍可能逃過防護。這些限制說明 SilentGuard 並非萬靈丹，而是需要在特定故障模型下才能發揮最大效用。

**Q14：SilentGuard 在哪些情況下會失敗或表現不佳？**
A：SilentGuard 在以下幾種情況下表現較弱。第一，對於「新型錯誤類型」(new fault types)，僅靠執行環境本身只能把錯誤率從 61.1% 降至 24.5%，效果不如對目標錯誤那樣顯著，這是因為新型錯誤可能繞過現有的不變式檢查。第二，當故障讓所有不變式都仍然成立時（例如 API 內部邏輯錯誤但回傳的計數仍滿足恆等式），SilentGuard 完全無法偵測。第三，對於藏在查詢字串內部的篩選條件，參數檢查無法辨識，因此這類故障可能會逃過防護。第四，學習型不變式可能誤判，導致在乾淨任務上產生不必要的警告或過度棄答。第五，模型之間的差異在「許可」要素上仍然存在——同一個允許棄答的提示在不同模型上效果差異極大（0–59%），這說明僅靠執行環境無法完全消除模型行為的不確定性。

**Q15：這項研究指出哪些未來研究方向？**
A：這項研究開啟了幾個重要的未來方向。第一，更廣泛的不變式發現機制——目前的不變式涵蓋計數恆等式、列表完整性、規格符合性三類，但真實 API 的行為契約遠多於此，需要研究如何自動從乾淨資料中學習更豐富、更可靠的不變式。第二，處理新型錯誤的泛化能力——論文顯示對新錯誤類型的防護效果有限（61.1% → 24.5%），未來需要研究如何讓執行環境在不熟悉的故障模式下仍能保持一定的防護力。第三，風險與覆蓋率的自適應調整——根據應用場景對錯誤的敏感度，動態調整不變式的嚴格度與棄答門檻。第四，與其他防護機制的整合——例如結合盲目重試（適用於暫時性故障）與不變式檢查（適用於靜默故障），建構多層次的防護體系。第五，API 設計層面的改變——鼓勵 API 提供者採用更嚴格的契約式設計，讓不變式檢查能更全面地涵蓋 API 行為，從根本上減少靜默失敗的發生。

## 實務應用指南

### 適用場景

**1. 學術文獻搜尋代理**
部署於研究助理或系統性回顧工具中，代理會透過 PubMed、arXiv、Semantic Scholar 等 API 查詢文獻。當使用者要求「過去五年關於 X 治療 Y 的隨機對照試驗」時，若 API 因篩選條件命名錯誤而忽略部分條件，代理可能回傳看似合理但錯誤的篇數。SilentGuard 可在計數結果進入 LLM 上下文前驗證「(X ∧ Y) + (X ∧ ¬Y) = X」等恆等式，避免錯誤文獻數量誤導下游分析。

**2. 生物醫學資料查詢代理**
應用於基因體、蛋白質體、藥物資料庫（如 UniProt、Ensembl、ChEMBL）的查詢流程。當代理查詢「在人類細胞中表現且與某 pathway 相關的基因數量」時，靜默錯誤可能讓代理少算或多算一個物種/組織的結果。透過清單不變式（每筆回傳記錄都必須符合篩選條件）與規格檢查（參數必須在 API 文件中），可在不增加模型呼叫的前提下攔截錯誤。

**3. 樣本目錄與生物銀行查詢**
用於查詢臨床試驗樣本、病理切片、基因組樣本目錄的代理。當使用者詢問「符合收案條件 A 與 B 的乳癌檢體數量」時，若 API 忽略 B 條件，回傳的數字會遠高於實際。SilentGuard 的計數恆等式檢查能直接證明此類錯誤並由執行環境阻擋輸出。

**4. 旅遊與訂位代理**
應用於航班、飯店、活動場地搜尋的代理。當使用者要求「下週三台北到東京、預算 3 萬日圓以內的航班數量」時，API 可能因預算篩選條件被忽略而回傳過多結果。執行環境可在結果進入 LLM 前驗證「符合預算的航班 ⊆ 所有航班」等集合包含關係。

**5. 企業內部資料與 BI 查詢代理**
應用於對 ERP、CRM、資料倉儲進行自然語言查詢的代理。當使用者詢問「上季來自亞太區、訂單金額超過 10 萬的客戶數量」時，內部 API 可能因區域代碼拼字錯誤而回傳錯誤數字。SilentGuard 的規格檢查（參數必須在 API 文件中）能在不存取原始資料庫的情況下攔截此類錯誤。

### 實作前置條件

**資料需求**
- 目標 API 的完整官方文件（用於規格檢查與參數白名單建立）
- 乾淨（無錯誤）的歷史回應樣本（用於學習契約式不變式，建議至少數十至數百筆）
- 已知正確答案的測試案例集（用於校驗不變式的有效性，可參考 AgentOrchBench 的設計）

**運算資源**
- 極低額外運算成本：SilentGuard 不需要額外的 LLM 呼叫，主要成本為規則比對與簡單的集合/計數運算
- 單次重查的網路成本：失敗結果會重查一次，需評估 API 是否有 rate limit 與成本影響
- 儲存空間：乾淨回應樣本與學習到的契約（通常為 KB 等級）

**技能需求**
- Python 中階能力（能撰寫裝飾器/中介層攔截工具呼叫）
- 熟悉目標代理框架的 hook 機制（如 LangChain 的 tool wrapper、AutoGen 的 function calling）
- 基礎的 API 測試與契約測試概念
- 對目標領域的資料特性有基本理解（才能設計有意義的不變式）

### 實作步驟建議

**步驟一：盤點 API 端點與錯誤模式**
盤點代理會呼叫的所有 API 端點，依據論文中提到的三類靜默錯誤進行分類：(1) 篩選條件命名錯誤被忽略、(2) 篩選值拼字錯誤被丟棄、(3) 分頁被悄悄截斷。為每個端點列出可能的靜默錯誤情境。

**步驟二：設計精確不變式（Exact Invariants）**
針對每個端點定義必須成立的精確不變式：
- 計數恆等式：`count(A ∧ B) + count(A ∧ ¬B) = count(A)`，可透過組合查詢驗證
- 清單包含關係：每筆回傳記錄都必須符合篩選條件，可透過重新查詢個別記錄驗證
- 規格符合性：請求參數必須出現在 API 文件中，可透過靜態比對驗證

**步驟三：收集乾淨樣本並學習契約式不變式（Learned Invariants）**
對於沒有精確不變式的端點，從乾淨回應中學習契約：
- 欄位型態與值域（如狀態碼只能是特定列舉值）
- 記錄數量的一致性（如分頁大小應固定）
- 跨欄位的關聯（如總價 = 單價 × 數量）
使用簡單的統計或規則學習即可，不需訓練模型。

**步驟四：實作執行環境中介層**
在代理框架中插入 SilentGuard 中介層，攔截所有工具呼叫的回應：
1. 收到回應後，依序執行精確與學習不變式檢查
2. 失敗時自動重查一次（同一呼叫）
3. 仍失敗時，依檢查類型決定動作：
   - 精確不變式失敗 → 由執行環境直接阻擋該值，僅允許「無法確定」回應
   - 學習不變式失敗 → 保留值但附加警告訊息

**步驟五：設定代理的棄答許可**
在系統提示中加入明確的「無法確定」棄答選項。論文的受控比較顯示，沒有此許可時，即使有警告，代理仍會在 64.4% 的情況下回報被標記的數字。

**步驟六：建立評估基準**
參考 AgentOrchBench 的設計，建立包含精確答案的測試集，並預先登記預測以避免評估偏差。評估指標應包含：
- 錯誤率（在注入錯誤的任務上）
- 乾淨任務的正確率（確認無退化）
- 覆蓋率（代理願意回答的任務比例）
- 風險-覆蓋率曲線

**步驟七：部署與監控**
上線後持續監控：(1) 阻擋率（多少比例的工具結果被執行環境攔截）、(2) 棄答率、(3) 乾淨任務的正確率是否維持。建議先以「警告模式」上線觀察，再切換到「阻擋模式」。

### 潛在風險與注意事項

**1. 覆蓋率下降的取捨**
SilentGuard 透過棄答而非恢復來避免錯誤答案。在 25% 錯誤率的場景下，它只回答 67% 的任務。對於需要高覆蓋率的應用（如即時客服），需評估「寧可說不知道」是否可接受。緩解方式：對高信心任務保留回答，對低信心任務啟用更嚴格的檢查。

**2. 學習不變式本身的錯誤**
學習到的契約可能不準確（例如某欄位在特殊情況下確實可為空）。論文中對此採取保守策略：學習不變式失敗時只警告不阻擋。緩解方式：定期用人工標註的黃金樣本驗證學習契約的精確度與召回率。

**3. 重查成本與副作用**
對於寫入型 API 或昂貴的查詢，重查一次可能造成成本翻倍或副作用。緩解方式：僅對讀取型 API 啟用自動重查；對寫入型 API 改用冪等性檢查或規格符合性檢查。

**4. 查詢字串內的篩選條件**
論文明確指出，規格檢查無法看見埋在查詢字串內的篩選條件。若代理框架將參數序列化為 URL query string，需在中介層解析後再檢查。

**5. 短暫性錯誤的處理**
對於會在 1-2 次重試內自行恢復的錯誤（如暫時性網路問題），論文中指出「盲目重試」可能比 SilentGuard 更有效。緩解方式：將重試邏輯設計為「先重試一次，若仍失敗再進入 SilentGuard 檢查」。

**6. 評估偏差**
論文中強調「預先登記預測」的評估方式，避免在看到結果後調整判斷。實作時應確保評估流程的盲性，否則容易高估效果。

**7. 領域遷移的通用性**
論文中的不變式設計偏向計數與清單類查詢。對於複雜的聚合（如時間序列、圖查詢），需要領域專家設計新的精確不變式。

### 與其他技術的整合建議

**1. 與重試機制整合**
建議採用「重試 → SilentGuard 檢查 → 阻擋/警告」的三段式流程。重試處理短暫性錯誤，SilentGuard 處理邏輯性錯誤，兩者互補。

**2. 與審查模型（Reviewer Model）整合**
審查模型（如 Ta et al., 2026）在工具呼叫「執行前」檢查參數合理性，SilentGuard 在「執行後」檢查結果合理性。兩者可串接：審查模型攔截明顯錯誤的請求，SilentGuard 攔截 API 端產生的靜默錯誤。

**3. 與結果監控器（Outcome Monitors）整合**
結果監控器學習契約並附加非綁定警告，SilentGuard 的學習不變式與其概念類似但更進一步——精確不變式失敗時直接由執行環境強制。可將結果監控器視為 SilentGuard 的子集，兩者整合時以 SilentGuard 的精確不變式為主、學習不變式為輔。

**4. 與日誌與可觀測性系統整合**
將 SilentGuard 的阻擋/警告事件結構化記錄，與既有的代理可觀測性工具（如 LangSmith、Helicone）整合。這有助於：(1) 追蹤哪些 API 容易產生靜默錯誤、(2) 量化執行環境介入的頻率、(3) 累積資料以改進不變式設計。

**5. 與防護框架（Guardrail Frameworks）整合**
SilentGuard 可視為防護框架中的一個專門針對工具結果的規則層。可在 NeMo Guardrails、Guardrails AI 等框架中註冊 SilentGuard 作為自訂驗證器。

**6. 與人類回饋機制整合**
對於學習不變式失敗但被警告放行的案例，可設計回饋機制讓使用者標註「這個結果其實是錯的」，將這些案例加入訓練資料以改進契約。

### 給不同背景讀者的閱讀建議

**給初學者**
重點閱讀第 1 節的問題描述與第 5 節的實驗結果。理解「靜默 API 失敗」的概念——API 回傳 HTTP 200 但結果是錯的，這比想像中常見（15 個公開 API 中有 11 個）。記住三個關鍵詞：證據（不變式檢查）、許可（允許棄答）、強制（由執行環境而非模型決定）。即使不實作，理解這個問題的存在就能讓你在使用 LLM 代理時多一分警覺。

**給 AI 工程師**
重點閱讀第 1 節的「三個要素」對照表（Table 2）與第 5 節的評估設計。論文證明了「只有證據 + 許可 + 強制三者齊備才能跨模型可靠地降低錯誤率」，這對生產環境的代理設計有直接指導意義。實作時可從論文的 GitHub 儲存庫開始，先在內部 API 上重現實驗，再逐步擴展到正式環境。特別注意「預先登記預測」的評估方法，這是避免自我欺騙的重要實驗紀律。

**給研究者**
重點閱讀第 2 節的相關工作與第 5 節的消融實驗。論文在三個層面有貢獻：(1) 對 15 個真實 API 的靜默錯誤測量、(2) 證據/許可/強制三要素的受控分離實驗、(3) AgentOrchBench 基準。可延伸的研究方向包括：設計更通用的不變式學習方法、探索代理在「知道結果可疑」時仍選擇回答的認知機制、以及將此框架擴展到多輪對話與規劃型代理。

**給產品經理**
重點閱讀摘要與第 1 節的「風險-覆蓋率」概念。這個研究的商業意涵是：當前的 LLM 代理在面對錯誤資料時，會「自信地給出錯誤答案」，這對需要高可靠性的場景（如醫療、金融、法律）是不可接受的風險。SilentGuard 提供了一個「寧可說不知道，也不要給錯答案」的工程化方案。在評估採用 LLM 代理的產品時，應將「靜默錯誤率」與「棄答率」列為關鍵指標，並與業務方溝通覆蓋率下降的取捨。
