# 當模型過度編輯時：論最小程式碼編輯之保真度

**原文標題：** When Models Edit Too Much: On the Fidelity of Minimal Code Edits  
**作者：** Tongyao Zhu、Wei Hern Lim、Min-Yen Kan  
**發布日期：** 2026-09-03

## ⚡ TL;DR

研究大型語言模型在程式碼修復中的過度編輯問題。
以四百題 BigCodeBench 注入 AST 損壞建立評估框架，測試提示與後訓練方法。
保留指令降低過量編輯並提升 Pass@1，強化學習在領域外達最佳保真度權衡。

## 摘要翻譯

大型語言模型（Large Language Models, LLMs）日益被用於編輯現有程式碼，然而僅有正確性並不足夠：有用的修復同時應保持最小化（minimal）、可審查，並忠於原始實作（original implementation）。本研究探討過度編輯（over-editing），即模型傾向重寫超出修復缺陷（bug）所需範圍的程式碼。我們以 400 個 BigCodeBench 問題為基礎，透過在參考解答（reference solutions）中注入受控的 AST 層級損壞（AST-level corruption）來建構評估框架（evaluation framework），並為每個修復任務（repair task）提供已知的最小修補（known minimal patch）。在各前沿大型語言模型（frontier LLMs）中，過度編輯普遍存在，即使在 GPT-5.5 等強大模型中亦然：高 Pass@1 可能與不必要的大規模編輯以及增加的認知複雜度（cognitive complexity）並存。保留指令（preservation instruction）能顯著減少此一行為，將平均過量萊文斯坦距離（excess Levenshtein distance）從 0.195 降至 0.131，使增加的認知複雜度降低 26.6%，並將 Pass@1 提升 2.3 個百分點。然而，這些提升並非單純來自更大的推理預算（reasoning budget）或更大的模型規模。接著我們探討最小編輯是否能在後訓練（post-training）階段直接被學習。我們觀察到監督式微調（supervised fine-tuning）會對已見過的損壞模式（seen corruption patterns）過度擬合，而強化學習（reinforcement learning）則在領域外（out-of-domain）的編輯保真度（edit fidelity）與效能保留權衡（performance-retention trade-off）之間取得最佳權衡。這些結果將編輯保真度定位為程式碼修復品質（code-repair quality）的一個獨立軸向，並顯示其可被衡量與學習。

### 核心貢獻（3～5點）
- 提出「過度編輯（over-editing）」問題，並以 BigCodeBench 為基礎建立可控的 AST 層級損壞（AST-level corruption）評估框架，為每個修復任務提供已知最小修補（known minimal patch）。
- 發現前沿大型語言模型（frontier LLMs）普遍存在過度編輯現象，高 Pass@1 可能與不必要的大規模編輯及增加的認知複雜度（cognitive complexity）並存。
- 驗證保留指令（preservation instruction）能顯著降低過度編輯，減少過量萊文斯坦距離（excess Levenshtein distance）與認知複雜度，同時提升 Pass@1，且增益並非來自更大的推理預算（reasoning budget）或模型規模。
- 比較後訓練（post-training）方法：監督式微調（supervised fine-tuning）對已見過的損壞模式過度擬合，而強化學習（reinforcement learning）在領域外（out-of-domain）的編輯保真度（edit fidelity）與效能保留權衡（performance-retention trade-off）上表現最佳。
- 將編輯保真度（edit fidelity）定位為程式碼修復品質（code-repair quality）的獨立軸向，並證明其可被衡量與學習。

### 適合對象
本論文適合軟體工程、程式語言與機器學習領域的研究人員與工程師，特別是關注自動化程式碼修復（automated program repair, APR）、大型語言模型（LLMs）在程式碼編輯應用，以及希望評估與改進模型輸出最小化與忠實度之開發者與研究者。

## 深度分析

#### 方法論解析

本研究的核心貢獻在於把「程式碼修復品質（code-repair quality）」從單一的「功能正確性（functional correctness）」擴展成多維度評估，並特別聚焦於 **over-editing（過度編輯）** 現象。為了讓這個現象可被量化，作者設計了一個控制嚴謹的評估框架，其方法論可拆解為以下幾個層次：

1. **受控的缺陷注入（controlled corruption injection）**  
   研究從 **BigCodeBench** 中選出 400 道題目，針對每題的 **reference solution（參考解答）** 注入一至兩個局部化的 **AST-level corruption（AST 層級損壞）**。AST 層級的操作確保了缺陷是語法結構上的、可定位的，例如把 `range(len(x))` 改成 `range(len(x) - 1)` 這類 off-by-one bug（差一錯誤）。只有當注入後的程式確實無法通過原始測試時，該樣本才會被保留。這樣一來，每個修復任務都擁有一個 **known minimal patch（已知最小修補）**：只要把注入的損壞反向還原，即可得到理論上的最小修復。

2. **將 over-editing（過度編輯）孤立為失敗模式**  
   因為最小修補是已知的，任何超出反向損壞範圍的修改，都可以被視為不必要的過度編輯。這種設計巧妙地排除了「修復本身就需要大改」的模糊地帶，讓研究者能夠專注於「模型在已經找到正確解的前提下，為何仍改寫了無關程式碼」。

3. **多維度評估指標**  
   - **Pass@1**：衡量功能正確性，即模型輸出是否能通過所有測試。  
   - **normalized token-level Levenshtein distance（正規化詞元層級萊文斯坦距離）**：衡量修補大小。作者進一步提出 **excess Levenshtein distance（過量萊文斯坦距離）**，將模型修補與已知最小修補之間的距離差異量化。  
   - **added cognitive complexity（新增認知複雜度）**：衡量結構性負擔，例如模型額外加入的輸入驗證、型別轉換、錯誤處理等是否讓程式更難理解與審查。

4. **兩種降低 over-editing（過度編輯）的策略**  
   - **Prompting（提示工程）**：加入一條 **preservation instruction（保留指令）**，要求模型在修復缺陷時盡量保留原始程式碼。  
   - **Post-training（後訓練）**：分別測試 **supervised fine-tuning（監督式微調，SFT）** 與 **reinforcement learning（強化學習，RL）**，探討模型是否能直接學會「最小化編輯」。

5. **研究範圍的刻意限縮**  
   本研究聚焦於單一函式層級的局部修復（local code repair），而非開放式生成或架構重構。這樣的選擇雖然限制了外部效度，卻能更精確地分離出 over-editing（過度編輯）這個變因。

#### 實驗數據解讀

從提供的摘要與圖例來看，實驗結果呈現出幾個值得深入討論的現象：

1. **Over-editing（過度編輯）在前沿模型中普遍存在**  
   圖一的範例極具代表性：一個只需要把 `range(len(x) - 1)` 改回 `range(len(x))` 的單行缺陷，**GPT-5.4** 卻刪除了 5 行、新增了 60 行，包含輸入驗證（input validation）、資料型別強制轉換（dtype coercion）、NaN 遮罩（NaN masking）、重新取樣（resampling）等。這些程式碼雖然讓輸出通過測試，卻完全超出題目規格所需。更值得注意的是，在 20 個前沿模型中，即使所有輸出都通過測試，中位數新增行數仍從 2 行到 60 行不等，且最新版模型未必比舊版更保守。這顯示 **Pass@1** 與 **edit fidelity（編輯保真度）** 並非單調相關。

2. **Preservation instruction（保留指令）效果顯著**  
   實驗顯示，加入保留指令後：  
   - 平均 **excess Levenshtein distance（過量萊文斯坦距離）** 從 0.195 降至 0.131；  
   - **added cognitive complexity（新增認知複雜度）** 降低 26.6%；  
   - **Pass@1** 反而提升 2.3 個百分點。  
   這三個數字共同說明：要求模型保留原始實作不僅能減少無謂改動，還能略微提升正確率。可能的解釋是，當模型被明確限制不要過度改寫時，它更傾向於精準定位缺陷，而非用大量防禦性程式碼「掩蓋」問題。

3. **Reasoning budget（推理預算）與模型規模並非萬靈丹**  
   研究特別指出，上述增益並非單純來自更大的推理預算或更大的模型。換言之，讓模型「想更久」或換成更新、更大的模型，並不保證會產生更小、更簡潔的修補。這對當前業界普遍追求「更大模型 + 更長推理」的趨勢是一個重要提醒：若沒有明確的 fidelity（保真度）目標，模型可能只是把更多 token 花在不必要的重構上。

4. **Post-training（後訓練）的差異：SFT 過擬合，RL 泛化較佳**  
   - **Supervised fine-tuning（監督式微調，SFT）** 在已見過的損壞模式（seen corruption patterns）上表現不錯，但會過度擬合這些特定缺陷類型，導致 **out-of-domain（領域外）** 表現下降。  
   - **Reinforcement learning（強化學習，RL）** 則達到最佳的權衡：在領域外達到 0.782 的 **Pass@1**，同時 **excess Levenshtein distance（過量萊文斯坦距離）** 僅 0.050，且未損害一般程式碼能力。  
   這暗示最小編輯是一種可以透過獎勵 shaping 學習的行為，而不是單純靠示範資料記憶。

5. **質性觀察：粒度錯配（granularity mismatch）**  
   作者指出，over-editing（過度編輯）經常源於「粒度錯配」：模型可能正確識別了缺陷位置，卻選擇改寫資料流、加入防禦性檢查或改變鄰近行為，而非進行局部修復。這與人類工程師的直覺相反——人類傾向於「只動該動的地方」。

#### 與現有研究的比較

本研究在程式碼生成與自動化修復的文獻中，填補了一個長期被忽視的空白：

1. **與功能正確性導向基準的比較**  
   傳統程式碼生成基準如 **HumanEval**、**MBPP**、**BigCodeBench** 主要衡量 **Pass@1** 或 **Pass@k**，強調「能不能跑對」。本研究則進一步問：「跑對之後，改了多少不該改的？」這讓 **edit fidelity（編輯保真度）** 成為與正確性並行的獨立維度。

2. **與倉庫級除錯基準的比較**  
   **SWE-bench**、**GitHub issue resolution** 等任務關注的是真實缺陷能否被解決，但評估重點仍是 issue 是否關閉、測試是否通過。雖然社群已觀察到這些模型會產生龐大 patch，但本研究首次在控制環境中系統性地量化這種「過度編輯」行為，並提供可重複的指標。

3. **與編輯導向基準的比較**  
   **HumanEvalFix**、**EditPack**、**InstructEdit** 等基準測試模型根據自然語言指令修改現有程式碼的能力，但它們通常沒有「已知最小修補」作為對照。本研究的貢獻在於透過受控缺陷注入，為每個任務建立了一個客觀的最小修補基準，從而能精確測量多餘編輯。

4. **與自動化程式修復（Automated Program Repair, APR）研究的呼應**  
   早期 APR 文獻已區分 **plausible patch（看似合理的修補）** 與 **correct/maintainable patch（正確且可維護的修補）**。本研究把這個概念帶入 LLM 時代，並用具體指標（Levenshtein distance、認知複雜度）將其可操作化。

5. **主要限制**  
   - **合成缺陷與真實缺陷的落差**：AST-level corruption（AST 層級損壞）雖然可控，但真實世界缺陷往往涉及跨函式、跨檔案的語意錯誤，未必能透過局部反向操作修復。  
   - **最小修補的非唯一性**：由注入反轉定義的「最小修補」在語意上未必唯一，某些情況下可能存在同樣小但結構不同的等價修復。  
   - **指標的粗糙性**：token-level Levenshtein distance（詞元層級萊文斯坦距離）會懲罰無關緊要的格式或命名差異；cognitive complexity（認知複雜度）的具體計算方式在摘要中未詳細說明。  
   - **語言與模型限制**：實驗僅針對 Python 與 BigCodeBench； frontier LLM（前沿大型語言模型）多為黑盒 API，難以深入分析其內部決策過程。

#### 可重現性評估

1. **程式碼與資料管線**  
   論文提供了公開的 GitHub 程式碼連結，這讓評估框架、缺陷注入流程、指標計算與提示模板原則上可以被重現。由於基礎資料集 **BigCodeBench** 本身是公開基準，研究者可以根據論文描述重新產生受損樣本。

2. **模型與權重的可取得性**  
   實驗中使用的多為 frontier LLM（前沿大型語言模型），例如 **GPT-5.5**、**GPT-5.4**、**Claude-opus-4.7**、**Qwen3.8-2.4t**、**Gemini-3.1-pro**、**Kimi-k3** 等，這些模型通常只能透過商業 API 存取，權重並不公開。因此，其他研究者雖然可以重跑實驗，但無法完全複製模型內部行為，也無法保證 API 版本與溫度（temperature）、取樣參數完全一致。

3. **後訓練模型的釋出狀況**  
   摘要與引言中並未明確說明經過 SFT 與 RL 訓練後的模型權重是否會公開。若僅釋出訓練腳本與資料，則後續研究需要自行承擔訓練成本，這會降低部分可重現性。

4. **整體評估**  
   本研究在「方法可重現」與「結果可驗證」之間取得了不錯的平衡：評估框架透明、基準資料公開，但受限於 frontier model（前沿模型）的黑盒特性，完全一致的復現仍有挑戰。

#### 未來研究方向

1. **擴展到真實與倉庫級缺陷**  
   將評估框架從單一函式的 AST-level corruption（AST 層級損壞）擴展到 **SWE-bench**、GitHub issue 等真實多檔案場景，並探討 over-editing（過度編輯）在跨檔案、跨模組修復中的表現。

2. **發展語意層級的編輯距離指標**  
   超越 token-level Levenshtein distance（詞元層級萊文斯坦距離），引入 AST diff、程式等價性檢驗、或基於變更語意的指標，以減少對無關格式差異的懲罰。

3. **結合人類評估的 reviewability（可審查性）研究**  
   建立人類標註資料集，衡量工程師對不同 patch 的審查負擔、理解難度與信任程度，補足自動化指標無法捕捉的維度。

4. **設計更精細的 RL 獎勵函數**  
   未來可嘗試同時優化功能正確性、編輯大小、認知複雜度、風格一致性與回歸風險，並研究不同獎勵權重對 over-editing（過度編輯）的影響。

5. **校準模型的「保守程度」**  
   開發能根據任務特性動態決定「何時該小修、何時該大改」的機制，例如讓模型在輸出前先產生 edit plan（編輯計畫），並評估其必要性。

6. **建構大規模最小編輯指令微調資料集**  
   類似 **EditPack** 的資料集可進一步標註「已知最小修補」，用於訓練更擅長保守編輯的專門模型，並減少 SFT 的過擬合問題。

7. **整合至 IDE 與開發流程**  
   將 fidelity（保真度）指標嵌入程式碼助理的 diff 預覽與迭代 refinement（細化）流程中，讓開發者能即時看到模型建議相對於最小修補的偏離程度。

8. **跨語言與跨領域驗證**  
   探討 over-editing（過度編輯）是否同樣存在於 Java、C++、JavaScript 等語言，以及在不同領域（如資料科學、系統程式、網頁開發）中的嚴重程度差異。

9. **理論理解 over-editing（過度編輯）的根源**  
   從訓練資料偏差、安全對齊、指令遵循粒度等角度，分析為何 LLM 傾向於過度改寫，並據此設計更有效的緩解策略。

## 論文問答

**Q1：什麼是「過度編輯」（over-editing），為什麼它會降低程式碼修復的實用價值？**
A：過度編輯指的是模型在修復缺陷時，雖然產出的程式碼能通過測試，卻改寫了遠超必要範圍的原始實作，例如額外加入輸入驗證、資料型別強制轉換或重新取樣等。這種行為會增加審查負擔、製造不必要的 diff churn，並可能遮蔽原始設計意圖，甚至引入測試未涵蓋的回歸風險。因此，單純以 Pass@1 衡量正確性無法反映修補是否精簡且忠於原始實作。

**Q2：現有的程式碼生成與修復基準測試為何難以衡量編輯保真度？**
A：現有基準大多只關注功能正確性，例如 Pass@1 或 Pass@k，或僅評估問題是否被解決，卻未比較模型輸出與已知最小修補之間的差異。由於這些測試不知道「真正需要改多少行程式碼」，因此無法區分一行程式碼的局部修正與六十行程式碼的大規模重寫。這使得過度編輯長期被忽視，成為程式碼修復品質中一個未被量化的維度。

**Q3：在既有系統（brownfield）的維護情境中，最小編輯為何特別重要？**
A：在 brownfield 環境中，開發者面對的是已存在的實作，而非從頭生成新程式碼，因此修補應盡量保留原始設計選擇與程式結構。過度編輯會破壞既有慣例、增加認知負荷，並可能在測試未涵蓋的邊界案例中引發回歸。最小編輯不僅降低審查成本，也有助於維持程式碼庫的長期可維護性。

**Q4：作者如何建構具有已知最小修補的評估框架？**
A：他們從 BigCodeBench 選取 400 道題目，對參考解答注入一或兩個局部化的 AST 層級損壞，並只保留那些損壞後無法通過原始測試的範例。由於損壞是人為控制且可逆的，因此可以精確定義最小修補為「將注入的損壞還原」所需的最小變更。這種設計讓評估者能夠把過度編輯孤立為一種可量化的失敗模式，而非僅僅觀察功能是否正確。

**Q5：本研究使用了哪些評估指標，各自衡量什麼面向？**
A：研究使用 Pass@1 衡量功能正確性，使用歸一化後的 token 層級萊文斯坦距離衡量編輯大小，並以新增的認知複雜度衡量結構性負擔。萊文斯坦距離可量化模型輸出與最小修補之間的「過量」編輯，而認知複雜度則反映修補是否引入額外的控制流或巢狀結構。這三項指標共同構成編輯保真度的多維評估，彌補單一指標的不足。

**Q6：與現有的 repository-level 或直接編輯基準相比，本研究的核心創新是什麼？**
A：核心創新在於將「編輯保真度」提升為獨立的程式碼修復品質軸，並提供一個知道最小修補的受控框架來精確測量過度編輯。不同於僅檢查問題是否解決的基準，此框架能判斷模型是否不必要地改寫了功能正確的程式碼。這讓研究者可以區分「能修復缺陷」與「以最小、可審查的方式修復缺陷」這兩種不同層次的表現。

**Q7：在前沿大型語言模型上的主要實驗結果顯示什麼？**
A：實驗發現過度編輯在前沿模型中非常普遍，即使像 GPT-5.5 這樣的強大模型也會產生不必要的大規模編輯。高 Pass@1 並不保證小編輯或低認知複雜度，模型間的中位數插入行數差異顯著，從 2 行到 60 行不等。更值得注意的是，最新版本並不一定比舊版本更保守，顯示模型規模與釋出時間並非編輯保真度的可靠預測指標。

**Q8：「保留指令」（preservation instruction）帶來了哪些具體改善？**
A：加入保留指令後，平均過量萊文斯坦距離從 0.195 降至 0.131，新增認知複雜度降低 26.6%，同時 Pass@1 提升 2.3 個百分點。這顯示簡單的提示工程就能顯著抑制過度編輯，並在不犧牲正確性的前提下產生更精簡的修補。然而，這些改善並非單純來自更大的推理預算或模型規模，而是與提示內容本身密切相關。

**Q9：監督式微調與強化學習在學習最小編輯方面有何差異？**
A：監督式微調雖然在已見過的損壞模式上表現不錯，但容易過度擬合，導致領域外泛化能力差。相較之下，強化學習在領域外資料上達到最佳的編輯保真度與效能保留權衡，例如達到 0.782 的 Pass@1 同時僅有 0.050 的過量萊文斯坦距離，且未損害一般程式碼能力。這說明最小編輯可以透過後訓練直接學習，但訓練典範的選擇至關重要。

**Q10：這些發現對程式碼輔助工具或 IDE 外掛的產品設計有何實務啟示？**
A：產品不應只向使用者展示「能通過測試」的修補，而應優先推薦變更範圍最小、最接近原始實作的候選方案。開發者介面可加入 diff 大小、認知複雜度或與最小修補的相似度等輔助資訊，幫助使用者快速判斷修補的可審查性。此外，在提示中內建保留指令或提供「僅修改必要部分」的選項，能直接提升使用者對修復建議的信任度。

**Q11：在實際應用中，應如何平衡正確性與編輯保真度？**
A：正確性仍是底線，因為無法通過測試的修補沒有價值，但在通過測試的多個候選中，應以編輯保真度作為排序與篩選依據。產品可設計多目標評分機制，同時考量 Pass@1、過量萊文斯坦距離與認知複雜度，並讓使用者根據任務風險調整權重。對於關鍵系統，偏好最小修補能降低回歸風險；對於原型或快速迭代場景，則可適度放寬對編輯大小的限制。

**Q12：本研究對自動化程式碼修復（APR）領域可能帶來什麼影響？**
A：本研究將「可審查性」與「最小性」重新帶回 APR 的評估視野，呼應早期區分「看似合理」與「真正可維護」修補的研究傳統。透過提供可量化的編輯保真度指標，未來的 APR 模型與基準可以同時追蹤功能正確性與對原始實作的尊重程度。這有助於引導社群開發出更適合實際維護情境、而非僅追求測試通過率的修復技術。

**Q13：本研究的評估框架有哪些主要限制或範圍界定？**
A：研究聚焦於局部程式碼修復，損壞是人工注入且可逆的 AST 層級錯誤，因此不一定涵蓋真實世界中開放式重構或跨檔案缺陷的複雜性。此外，框架假設存在單一已知最小修補，但實際維護任務可能有多種同樣合理的修正方式。這些限制意味著研究結果最適合解釋「可控局部修復」情境下的過度編輯行為，而非所有程式碼編輯任務。

**Q14：即使加入保留指令或使用強化學習，仍可能存在哪些失敗案例？**
A：模型可能因粒度不匹配而將局部錯誤理解為整體資料流問題，進而重寫相關但無需修改的程式碼。此外，防禦性檢查、型別轉換或命名風格變更等「無害」改動雖不影響測試通過，卻會增加 diff 與審查負擔。在領域外或更開放的任務中，模型也可能為了提高穩健性而加入過多額外邏輯，顯示過度編輯尚未被完全消除。

**Q15：未來研究可以朝哪些方向延伸？**
A：未來可將框架擴展到真實缺陷資料集、跨檔案修復或自然語言驅動的編輯請求，以驗證指標在更開放情境下的適用性。另一方面，可探索結合人類偏好資料的強化學習獎勵設計，直接對最小性、可讀性與審查友好度進行最佳化。最後，發展能即時比對多個候選修補與最小修補差異的解釋工具，將有助於開發者更快理解並信任模型建議。

## 實務應用指南

### 適用場景

1. **企業內部程式碼審查與自動修復助手**  
   在既有程式庫中，開發者常使用 LLM 自動修復靜態分析或測試回報的缺陷。本研究可幫助團隊評估並降低模型「過度編輯」的傾向，確保修復後的 diff 最小、易於審查，並保留原始設計意圖。

2. **持續整合／持續部署（CI/CD）中的自動補丁生成**  
   當測試失敗時，CI 管線可呼叫程式碼修復模型產生補丁。透過引入「保留指令」與編輯保真度指標，團隊可過濾掉那些雖通過測試、卻夾帶大量不必要改動的補丁，減少合併風險與回歸問題。

3. **程式碼教學與學習平台**  
   在程式設計教育場景中，系統可針對學生程式碼的局部錯誤（如差一錯誤、條件判斷錯誤）給出最小修補。最小編輯能讓學生聚焦於真正需要修正的觀念，避免被模型額外加入的防禦性程式碼分散注意力。

4. **遺留系統維護與重構輔助**  
   對於歷史悠久的 brownfield 專案，開發者需要局部修復而非大規模重寫。評估與控制過度編輯有助於在修 bug 的同時，維持程式碼風格一致、降低 diff churn，並保留隱含的設計選擇。

5. **模型後訓練與微調的品質優化**  
   對於正在訓練或微調程式碼 LLM 的團隊，本研究提供可量化的編輯保真度指標，可作為強化學習或監督式微調的獎勵／評估訊號，訓練出更懂得「精準下刀」的修復模型。

### 實作前置條件

**資料前提**
- 需擁有「原始正確實作」與「已知最小修補」的配對資料，或能透過 AST 層級損壞注入自動產生這類配對。
- 若無現成標註，可參考本研究以 BigCodeBench 參考解答為基礎，注入單一或兩個局部化損壞，並驗證損壞後程式確實無法通過原始測試。
- 需要可執行的測試案例，以計算 Pass@1 並驗證修復是否正確。

**運算前提**
- 推論階段：需能呼叫前沿大型語言模型（如 GPT-5.x、Claude-4.x、Gemini、Qwen、Kimi 等）或部署自有模型。
- 評估階段：需具備執行 Python 程式、計算萊文斯坦距離與認知複雜度的環境。
- 後訓練階段：若要走強化學習或監督式微調路線，需具備 GPU 叢集與 RLHF/DPO/RL 訓練框架經驗。

**技能前提**
- 熟悉 Python 與抽象語法樹（AST）操作。
- 了解程式碼生成基準測試（如 BigCodeBench）與 Pass@1 評估流程。
- 具備提示工程經驗，能設計並測試「保留指令」。
- 若進行後訓練，需熟悉強化學習或監督式微調流程。

---

### 實作步驟建議

1. **建立可控的評估資料集**  
   選定一組參考解答（如 BigCodeBench 的 400 題），對每題注入局部 AST 層級損壞，並確保損壞後程式無法通過原始測試。記錄注入的反向操作作為「已知最小修補」。

2. **定義編輯保真度指標**  
   採用三項核心指標：Pass@1（功能正確性）、過量萊文斯坦距離（相對於最小修補的額外編輯量）、以及新增認知複雜度（結構性額外負擔）。

3. **設計並測試保留指令**  
   在提示中加入明確的保留指令，例如：「請只修改修復缺陷所需的最少程式碼，保留原始實作的結構與風格，不要加入額外的輸入驗證或重構。」測量其對過量萊文斯坦距離與 Pass@1 的影響。

4. **評估現有模型的過度編輯行為**  
   對多個前沿大型語言模型執行修復任務，記錄每個模型的 Pass@1、過量萊文斯坦距離與新增認知複雜度，識別哪些模型傾向過度編輯。

5. **選擇後訓練策略**  
   若提示工程不足以滿足需求，可考慮後訓練：
   - **監督式微調**：適合快速擬合已見過的損壞模式，但需注意領域外泛化問題。
   - **強化學習**：以編輯保真度與正確性作為獎勵，能在領域外取得較佳的編輯保真度與效能保留權衡。

6. **整合至開發流程並持續監控**  
   將評估指標與保留指令整合到程式碼審查工具或 CI/CD 管線中，對自動生成的補丁進行過濾與排序，並持續追蹤過度編輯率。

---

### 潛在風險與注意事項

- **過度編輯難以單靠正確率發現**  
  模型可能通過所有測試，卻同時重寫大量程式碼。僅監控 Pass@1 會低估問題，必須同時追蹤編輯大小與認知複雜度。

- **保留指令效果因模型而異**  
  雖然整體上保留指令能顯著降低過度編輯，但不同前沿模型的反應不一致，建議針對目標模型進行 A/B 測試。

- **監督式微調容易過度擬合**  
  若訓練資料中的損壞模式過於單一，模型可能學會「背答案」而非真正理解最小修復，導致領域外表現下降。

- **最小修補不等同於最佳修補**  
  已知最小修補是相對於注入損壞的反向操作，現實世界中的最佳修補可能涉及額外的防禦性程式碼。需根據應用場景定義何謂「可接受」的編輯。

- **安全性與測試覆蓋率風險**  
  過度編輯有時會加入不必要的輸入驗證或資料型別強制轉換，這些改動雖不影響現有測試，卻可能改變邊界行為或引入效能問題。

---

### 與其他技術的整合建議

- **與靜態分析工具整合**  
  將 AST 層級損壞注入與靜態分析（如 pylint、mypy、bandit）結合，可自動產生更多樣化的修復任務，並用於持續評估模型。

- **與版本控制系統整合**  
  在提交前對 LLM 生成的補丁執行編輯保真度檢查，將過量萊文斯坦距離或新增認知複雜度超過門檻的補丁標記為需人工審查。

- **與強化學習管線整合**  
  將過量萊文斯坦距離、認知複雜度與 Pass@1 組合成獎勵函數，用於 RLHF 或直接偏好優化（DPO），引導模型學習最小編輯行為。

- **與程式碼審查平台整合**  
  在 GitHub/GitLab 的 PR/MR 流程中嵌入編輯保真度報告，幫助審查者快速識別哪些自動修復是「最小且安全」的。

- **與檢索增強生成（RAG）整合**  
  在提示中檢索並提供原始函式的相關上下文與編碼規範，可進一步強化模型對原始實作風格的保留。

### 給不同背景讀者的閱讀建議

**初學者**  
本研究的核心訊息很直觀：AI 修復程式碼時，「能跑」不代表「修得好」。建議先閱讀圖 1 的範例，理解什麼是「過度編輯」，再關注「保留指令」這個簡單卻有效的改進方法。技術細節如 AST 損壞注入與強化學習可暫時略過。

**AI 工程師**  
重點放在實作面：如何建立可控評估資料集、如何計算過量萊文斯坦距離與認知複雜度、如何設計有效的保留指令，以及監督式微調與強化學習在編輯保真度上的取捨。這些內容可直接應用於模型評估與後訓練管線。

**研究人員**  
本研究提出了一個新的評估維度——編輯保真度，並以已知最小修補作為控制變因。可進一步探討的問題包括：過度編輯的因果機制、不同損壞類型對模型行為的影響、以及如何設計更貼近真實維護場景的評估基準。

**產品經理**  
本研究提供了一個可量化的品質指標，幫助團隊在「自動修復速度」與「程式碼審查成本」之間取得平衡。建議關注保留指令帶來的 2.3 點 Pass@1 提升與 26.6% 認知複雜度降低，並思考如何將這些指標轉化為產品內的補丁評分或審查輔助功能。
