## 摘要翻譯

我們提出 3DCodeVerse，一個使程式碼代理（Coding Agent）能夠大規模創造可編輯且可驗證的 3D 內容（Editable and Verifiable 3D Content）的研究生態系（Research Ecosystem）。3DCodeVerse 包含大規模、高品質的可執行 3D 程式碼（Executable 3D Code）資料集、用於空間推理（Spatial Reasoning）與自動化驗證（Automated Verification）的程式碼框架，以及 3D 程式碼生成（3D Coding）的實務指引。首先，我們建構 3DCodeVerse-2M，一個大規模策展的獨立可執行 3D 程式碼（Standalone Executable Code）資料集。我們以三種方式建立此語料庫：蒐集開源資料、轉換專門的表示法，以及利用程式碼代理生成新程式。每個程式皆封裝了其於宣告環境（Declared Environment）中執行所需的原始檔案（Source File）與相關資產（Asset），並附上可用的描述與驗證紀錄（Verification Record）。其次，我們開發 3DCodeVerse Harness，一個用於生成與精煉 3D 內容的多代理有向無環圖（Multi-Agent Directed Acyclic Graph）框架。它利用執行檢查（Execution Check）、空間測量（Spatial Measurement）與視覺回饋（Visual Feedback），在生成過程中無需人工回饋即可自動評估並修正所生成的程式。第三，我們對 3D 程式碼生成進行系統性的實證研究（Empirical Study），透過微調開放模型（Fine-Tuned Open Model）建立基準（Baseline），並透過對我們框架的元件層級分析（Component-Level Analysis）歸納出實務指引。大量實驗證明，在我們的資料集上進行微調能顯著提升開源模型（Open-Source Model）的 3D 程式碼生成能力。值得注意的是，在 Claude Opus 5.5 同時運用兩者時，我們的 3DCodeVerse 框架在成對人工評估（Pairwise Human Evaluation）中對 Claude Design（3D 物件）達到 90% 的勝率（Win Rate）。

### 核心貢獻（3～5點）
- **3DCodeVerse-2M 大規模策展資料集**：建構包含 200 萬個獨立可執行 3D 程式的大規模資料集，涵蓋原始檔案、相關資產、描述與驗證紀錄，支援開源模型微調與 3D 程式碼生成研究。
- **3DCodeVerse Harness 多代理框架**：提出基於多代理有向無環圖（DAG）的生成與精煉框架，整合執行檢查、空間測量與視覺回饋，實現無需人工介入的自動化評估與迭代式精煉（Iterative Refinement）。
- **系統性實證研究與實務指引**：透過元件層級分析（Component-Level Analysis）對 3D 程式碼生成進行系統性實證研究，建立微調開放模型的基準（Baseline），並歸納出可實務應用的指引。
- **開源模型能力顯著提升**：實驗證明在 3DCodeVerse-2M 上進行微調，能顯著提升開源模型（Open-Source Model）的 3D 程式碼生成能力。
- **關鍵對比成果**：在 Claude Opus 5.5 同時運用兩者的條件下，3DCodeVerse 框架於成對人工評估中對 Claude Design（3D 物件）達到 90% 的勝率。

### 適合對象
- **3D 內容生成與電腦圖學研究者**：關注基於程式碼的 3D 生成（Code-Based 3D Generation）、CAD 建構（CAD Construction）、Blender 腳本（Blender Scripting）、著色器（Shader）與場景組合（Scene Composition）等領域的學者與工程師。
- **程式碼代理與多代理系統開發者**：從事 Coding Agent、Multi-Agent Directed Acyclic Graph 框架、自動化驗證（Automated Verification）與推論時間迴圈（Inference-Time Loop）設計的研究人員。
- **空間推理與視覺語言模型研究者**：對空間推理（Spatial Reasoning）、視覺回饋（Visual Feedback）、視覺語言材質（VLMaterial）等多模態議題有興趣的學者。
- **開源模型微調實踐者**：希望利用高品質策展資料集提升開源語言模型（Language Model）在特定領域表現的 AI 工程師與研究者。

## 深度分析

#### 方法論解析

3DCodeVerse 提出了一套完整的「資料—框架—模型」三位一體研究生態系，其方法論設計體現了對 3D 程式碼生成任務本質的深刻理解。以下從三個核心元件進行解析。

**一、3DCodeVerse-2M 資料集的建構方法**

資料集建構採用「策展—轉換—生成」三階段流程，而非單純聚合既有資料集，這是方法論上的關鍵設計決策：

1. **異質表示的統一化轉換**：將 DeepCAD 的建構序列（construction sequences）翻譯為 CadQuery 程式碼，並將 Articraft 的幾何常式內聯化（inlining）同時保留 URDF 關節規格。這種轉換解決了 3D 領域長期存在的「表示碎片化」問題——不同系統使用各自的專用格式（如構造序列、網格、URDF），導致模型難以跨環境泛化。透過將所有表示統一為「可執行程式碼」，資料獲得了可編輯性、可重複執行性與可驗證性三重屬性。

2. **自包含化處理（Self-Containment）**：每個程式都封裝了「宣告環境中執行所需的原始檔案與關聯資產」，並移除對專用或不可用函式庫的依賴。這項設計對訓練資料的實用性至關重要——若程式碼依賴無法取得的私有函式庫，則無法用於監督式學習或測試時執行。

3. **驗證信號的內嵌**：每筆資料不僅包含程式與描述，還附帶「驗證紀錄」，這為後續的偏好學習（preference learning）與監督式微調提供了多層次的監督信號。

**二、3DCodeVerse Harness 的多代理 DAG 框架**

Harness 的設計是本文最具方法論創新性的部分，採用「多代理有向無環圖」（Multi-Agent Directed Acyclic Graph, DAG）架構：

1. **任務分解與並行化**：將多元件專案分解為 DAG 結構的編碼與組裝任務，使多個代理能夠結構化地開發並整合原始檔案。這種設計突破了傳統單代理順序生成的瓶頸，使生成過程可擴展至「包含數千行程式碼的複雜專案」。

2. **三層驗證機制**：
   - **執行檢查（Execution Check）**：確保程式碼可在宣告環境中成功執行
   - **空間測量（Spatial Measurement）**：偵測結構不一致性，防止「視覺上看似合理但幾何上無效」的解
   - **視覺回饋（Visual Feedback）**：獨立評審代理根據明確驗收標準評估輸出

3. **局部化修復目標（Localized Repair Objectives）**：將驗證回饋轉換為局部化的修復目標，實現「執行—評估—修訂」循環，無需人類介入。這種設計使框架同時具備推論時間擴展（inference-time scaling）能力與資料生成引擎功能。

4. **閉環生態系**：Harness 不僅是推論系統，更是資料生成引擎——透過記錄成功程式、失敗嘗試、目標化修復與偏好比較，其執行軌跡為監督式微調與偏好學習提供監督信號，形成「資料建構→程式合成→驗證→精煉→模型改進」的閉環。

**三、訓練方法論**

採用「在 3DCodeVerse-2M 上微調開放模型」的路徑，並透過元件層級分析（component-level analysis）推導實務指引。這種「資料驅動的實證研究」方法論避免了純粹的演算法猜測，透過系統性的消融實驗建立可重現的訓練食譜。

#### 實驗數據解讀

**一、執行率指標的解讀**

在 3DCodeBench 基準上，微調後的 9B 模型達到 84.9% 執行率，27B 模型達到 92.9% 執行率。這項數據揭示了幾個重要訊息：

1. **規模效應明顯**：從 9B 到 27B，執行率提升約 8 個百分點，符合語言模型領域的標準 scaling 規律。然而，9B 模型已達到 84.9% 的高執行率，顯示 3DCodeVerse-2M 的資料品質足以讓中等規模模型獲得強健的可執行性。

2. **基準對比的相對性**：需注意 3DCodeBench 是程式碼可執行性基準，並非視覺品質或幾何正確性基準。高執行率僅代表程式能跑起來，不保證生成的 3D 內容符合使用者意圖。

**二、Harness 增益的解讀**

「Harness 在編碼代理上帶來 15.5–29.1 分的增益，相較於單次生成（one-shot generation）」這項數據極具說服力：

1. **增益幅度跨模型穩健**：15.5–29.1 分的範圍顯示 Harness 並非僅對特定模型有效，而是具有跨模型的通用改進能力。

2. **迭代精煉的價值驗證**：如此大的增益證明了「執行—評估—修訂」循環相較於單次生成的巨大優勢，這與軟體工程領域中「測試驅動開發」的價值觀一致。

3. **推論時間擴展的可行性**：Harness 支援的迭代精煉實質上是一種「推論時間計算擴展」，與 LLM 領域的 test-time scaling 趨勢呼應。

**三、人類評估結果的解讀**

「3DCodeVerse Harness 在成對人類評估中對 Claude Design（3D Object）達到 90% 勝率，當兩者都由 Claude Opus 5.5 使用時」——這項結果需要謹慎解讀：

1. **條件設定的影響**：90% 勝率是在「Claude Opus 5.5 同時驅動兩個系統」的條件下獲得，這意味著比較的焦點是 Harness 框架本身，而非底層 LLM。換言之，勝率反映的是「Harness 的迭代精煉機制相較於 Claude Design 的單次生成流程的優勢」。

2. **基準的代表性問題**：Claude Design（3D Object）是何種系統？其能力邊界為何？論文中未充分說明，使得 90% 勝率的絕對意義難以評估。

3. **人類評估的侷限**：成對人類評估易受呈現順序、視覺偏好等偏差影響，且未說明評估者數量、評估協議與評估維度。

**四、資料集規模的解讀**

2.03M 配對（pairs）的規模在 3D 程式碼領域堪稱最大，但需注意：

1. **單位異質性**：如表 1 所示，不同資料集使用不同單位（程式、配對、任務、腳本），規模數字無法直接比較。
2. **6 種程式碼類型**：涵蓋 CAD、Blender、著色器、瀏覽器圖形等，這種多樣性是 3DCodeVerse 的核心優勢，但也帶來了「跨類型泛化」的評估難題。

#### 與現有研究的比較

**一、定位差異化**

從表 1 的系統性比較可看出，3DCodeVerse 在三個維度上同時達到最廣覆蓋：

1. **內容維度**：同時支援靜態（Static）、關節式（Articulated）、場景（Scene）、圖形（Graphics）四類內容，而既有資料集多僅覆蓋其中一至兩類。例如 Shaders21k 僅涵蓋圖形，BlendNet 僅涵蓋靜態物件。

2. **程式碼類型維度**：支援 6 種程式碼類型，遠多於既有工作的 1–2 種。這種多樣性使模型能學習跨環境的程式碼生成能力。

3. **框架能力維度**：同時具備迭代精煉、視覺回饋、幾何檢查三項能力，而既有框架多僅具備部分能力。例如 SceneCraft 與 LL3M 缺乏幾何檢查，CAD-Assistant 缺乏視覺回饋。

**二、相較於關鍵先驅工作的改進**

1. **vs. SceneCraft（Hu et al., 2024）**：SceneCraft 開啟了視覺回饋驅動的 3D 程式碼生成範式，但僅支援部分幾何檢查。3DCodeVerse Harness 透過空間測量機制補足了這一缺口。

2. **vs. Articraft（Zhou et al., 2026）**：Articraft 專注於關節式資產生成，3DCodeVerse 則將關節式生成整合進更廣泛的生態系，並透過 DAG 架構支援多代理並行開發。

3. **vs. CAD-Recode / MeshCoder**：這些工作專注於 CAD 或網格重建，3DCodeVerse 透過將 DeepCAD 序列轉換為 CadQuery 程式碼，統一了 CAD 領域的表示。

4. **vs. BlenderGym / 3DCodeBench**：這些基準測試特定環境下的任務表現，3DCodeVerse 則提供跨環境的統一訓練語料與框架。

**三、侷限性與未解決問題**

1. **閉環生態系的驗證深度不足**：雖然論述了「資料—框架—模型」的閉環，但實驗部分似乎未充分展示閉環的多輪迭代效果——即 Harness 生成的資料如何反過來改進模型，模型改進後又如何提升 Harness 的資料品質。

2. **人類評估的維度單一**：僅報告成對勝率，未細分視覺品質、幾何正確性、可編輯性、使用者意圖符合度等維度。

3. **與商業系統的比較深度有限**：90% 勝率對比 Claude Design 的結果雖然亮眼，但缺乏與其他商業 3D 生成系統（如 Meshy、Tripo3D 等）的比較。

4. **DAG 分解的自動化程度未明**：DAG 任務分解是手動設計還是由 LLM 自動生成？分解品質如何影響最終結果？這些關鍵細節未充分說明。

5. **「宣告環境」的相容性問題**：雖然強調自包含化，但不同環境（CAD、Blender、瀏覽器）的版本相容性、資產授權問題未深入討論。

#### 可重現性評估

**一、開源承諾的評估**

論文標題為「3DCodeVerse」，並在摘要中明確提及「open-source foundational framework」、「open models」與「reproducible training recipes」，顯示作者群對可重現性的重視。然而，僅從提供的全文片段中，無法完全確認以下細節：

1. **程式碼釋出**：3DCodeVerse Harness 的程式碼是否在 GitHub 公開？採用何種授權（MIT、Apache 2.0 等）？

2. **資料集釋出**：3DCodeVerse-2M 是否完整釋出？2.03M 配對的資料量是否全部可下載？若受限於儲存或授權，部分資料是否僅提供元資料與下載連結？

3. **模型權重釋出**：微調後的 9B 與 27B 模型權重是否公開？基模型是哪些（LLaMA、Qwen、DeepSeek 等）？

4. **訓練食譜**：訓練超參數、資料混合比例、訓練步數、硬體配置等是否完整記錄？

**二、可重現性的潛在障礙**

1. **資產授權問題**：3D 程式碼常依賴第三方 3D 模型、紋理、HDRI 影像等資產，這些資產的授權可能限制資料集的再散佈。

2. **環境依賴**：不同 3D 環境（Blender 版本、CadQuery 版本、瀏覽器引擎）的版本敏感性可能導致執行結果不一致。

3. **評估的非確定性**：人類評估的隨機性、LLM 評審的溫度參數等都會影響結果的可重現性。

4. **閉環系統的複雜度**：資料—框架—模型的閉環涉及多個互動元件，完整重現需要同時部署資料生成管道、訓練流程與推論框架。

**三、可重現性評級**

基於現有資訊，可重現性評估為「中等偏上」：作者明確承諾開源並提供訓練食譜，但具體的程式碼、資料、權重釋出狀態需待正式版本或補充材料確認。對於學術界而言，2M 規模的資料集與多代理框架的完整釋出將是重大貢獻。

#### 未來研究方向

**一、閉環生態系的深化**

1. **多輪自我改進**：當前閉環似乎僅展示單輪或有限輪次的迭代，未來可探索「模型改進→資料品質提升→模型再改進」的多輪自我演化機制，類似 AlphaGo 的自我對弈範式。

2. **跨模態閉環**：將文字、圖像、影片輸入統一納入閉環，使 Harness 能根據不同輸入模態生成對應的 3D 程式碼，並透過閉環持續優化。

**二、幾何推理與物理正確性**

1. **物理模擬整合**：當前框架主要關注幾何正確性，未來可整合物理模擬（如剛體動力學、軟體模擬）以確保生成的 3D 內容在物理上合理。

2. **尺度與比例推理**：空間測量機制可進一步擴展為「尺度感知」推理，使模型能根據使用者指定的尺度（如「一個房間大小的場景」）自動調整幾何比例。

3. **拓撲正確性**：除幾何有效性外，拓撲正確性（如流形性、邊界一致性）也是 3D 內容的關鍵屬性，值得在 Harness 中加入專門檢查。

**三、可編輯性與可組合性**

1. **模組化程式碼生成**：當前生成的是整體程式碼，未來可探索「模組化」生成，使生成的程式碼易於重用、組合與修改。

2. **版本控制整合**：將 Git 等版本控制系統整合進 Harness，使 3D 內容的演進過程可追溯、可分支、可合併。

3. **差分式編輯**：支援「基於現有 3D 程式碼的差分式編輯」，而非每次都從頭生成，這對實際工作流程至關重要。

**四、評估方法的革新**

1. **多維度人類評估**：除成對勝率外，應建立涵蓋視覺品質、幾何正確性、可編輯性、執行效率、使用者意圖符合度等多維度的評估協議。

2. **自動化評估指標**：發展與人類判斷高度相關的自動化指標，如基於 CLIP 的語義一致性、基於 3D 特徵的幾何相似度等。

3. **長期任務評估**：當前評估多為單次生成任務，未來應評估「多輪迭代、長期專案開發」等更接近實際使用場景的任務。

**五、應用領域的擴展**

1. **工業設計整合**：將 3DCodeVerse 整合進工業設計工作流程，使其能處理 CAD 標準、製造約束、材料規格等工業級需求。

2. **遊戲與影視產業**：探索在遊戲關卡設計、影視場景預覽等領域的應用，這些場景對迭代速度與可編輯性有極高要求。

3. **教育與訓練**：利用 3DCodeVerse 生成可執行的 3D 教學內容，使學生能透過程式碼理解 3D 幾何原理。

4. **機器人與具身智慧**：將 3DCodeVerse 生成的場景作為機器人模擬訓練環境，支援具身智慧的 sim-to-real 轉移。

**六、理論基礎的建立**

1. **3D 程式碼的語言模型理論**：當前 3D 程式碼生成多基於經驗，未來應建立嚴格的理論框架，分析 3D 程式碼的表達能力、學習複雜度、泛化邊界等。

2. **多代理協作的理論分析**：DAG 架構的多代理協作缺乏理論指導，未來可借鑑分散式最佳化、多智慧體強化學習等理論，建立代理分工與協作的原則性方法。

3. **可驗證 3D 程式碼的形式語意**：為 3D 程式碼定義形式語意，使其能被形式化驗證，這將大幅提升生成內容的可靠性。

**七、社會與倫理影響**

1. **3D 內容的智慧財產權**：生成的 3D 程式碼與衍生資產的 IP 歸屬問題需要明確的法律與技術框架。

2. **偏見與公平性**：3D 程式碼生成模型可能從訓練資料中學到文化、種族、性別等偏見，未來應建立偏見檢測與緩解機制。

3. **對 3D 設計師的影響**：3DCodeVerse 等系統對 3D 設計師職業的影響需要深入研究，包括技能需求轉變、工作流程重塑等。

總結而言，3DCodeVerse 為 3D 程式碼生成領域建立了堅實的基礎設施，其閉環生態系設計理念具有深遠的影響力。未來研究應在深化閉環、擴展應用、建立理論基礎三個方向同步推進，使 3D 程式碼生成從「演示系統」走向「生產級工具」，最終實現 Ivan Sutherland 在 Sketchpad 中所憧憬的願景——3D 內容不僅是靜態的繪圖集合，而是可編輯、可推理、可組合的結構化知識。

## 論文問答

**Q1：為什麼「以程式碼生成 3D 內容」這條路線值得投入研究？它相較於傳統 2D 生成或直接 3D 表徵生成有何根本優勢？**

A：以程式碼生成 3D 內容的核心價值在於「可執行性」與「可編輯性」——所產生的不是靜態網格或點雲，而是可在 Blender、CadQuery、瀏覽器等環境中實際執行的結構化程式。這意味著使用者可以修改參數、重組元件、檢查邏輯，並把資產嵌入更大的工作流程中。相較於 2D 生成工作流程（其輸出多為像素圖像），程式碼形式的 3D 內容具備可重用、可組合、可審查的特性，更利於工業級的可控建模。論文中引用 Ivan Sutherland 在 1963 年 Sketchpad 的引言，正是為了強調「程式化描述」超越「靜態部件集合」的長期願景。

**Q2：現有的 3D 程式碼資料集與生成框架各自存在什麼不足，使得 3DCodeVerse 有整合的必要性？**

A：從 Table 1 可以看出，現有資料集高度碎片化：Shaders21k 僅涵蓋著色器、BlendNet 與 CAD-Recode 聚焦靜態 CAD、BlenderGym 雖含場景但規模僅 245 個任務、Articraft 雖含關節式資產卻無場景與圖形支援。在框架（Harness）方面，SceneCraft 與 LL3M 缺乏幾何檢查、CAD-Assistant 雖有幾何檢查卻不支援迭代精煉的多模態回饋、VIGA 雖有視覺回饋但任務數僅 27 個。這種「資料分散於任務與環境、框架能力不完整」的局面，使得跨環境的 3D 程式碼研究難以系統化比較與擴展，因此需要一個同時具備統一資料集、完整回饋迴圈、與閉環改進機制的生態系。

**Q3：3DCodeVerse 試圖解決的「共享基礎設施」問題為何對整個領域至關重要？**

A：3D 程式碼生成涉及多種異質環境（CAD、Blender、著色器、瀏覽器圖形），每種環境都有自己的依賴、執行模型與失敗模式。沒有共享基礎設施，研究者就必須各自從零搭建資料管線、撰寫執行器、設計評估指標，導致成果難以累積與比較。3DCodeVerse 透過提供統一的資料格式（每個程式封裝原始檔、資產、描述、驗證紀錄）與標準化的推論迴圈（執行—評估—修訂），讓資料建構、程式合成、驗證、精煉、模型改進形成閉環。這種「基礎設施先行」的策略，正是推動整個領域從單點示範走向規模化研究的關鍵。

**Q4：3DCodeVerse-2M 資料集是如何建構的？為何強調「獨立可執行」與「異質表示轉換」？**

A：3DCodeVerse-2M 並非單純聚合現有資料，而是採用三種策略並行：收集開源資料、轉換專門表示（例如將 DeepCAD 建構序列翻譯成 CadQuery 程式、將 Articraft 幾何常式內聯同時保留 URDF 關節規格）、以及使用程式碼代理生成新程式。每支程式都被封裝成「獨立可執行」的單元——包含原始檔、所需資產、宣告環境、描述與驗證紀錄——確保它能在目標 runtime 中直接執行而無需外部依賴。這種設計解決了既有資料集「依賴專用或不可得函式庫」的痛點，使資料真正可用於監督式微調與偏好學習。

**Q5：3DCodeVerse Harness 的「多代理有向無環圖（DAG）」架構有何獨特之處？**

A：傳統的單代理迴圈容易在複雜專案（數千行程式碼）中迷失或產生不一致的修改，而 3DCodeVerse Harness 將多元件專案分解為 DAG 上的編碼與組裝任務，使多個代理能並行開發並結構化地整合原始檔。生成後的程式會被執行與渲染，再由獨立的「評審代理」對照明確的接受標準進行評估；同時輔以空間測量偵測結構不一致，避免「視覺上看似合理但幾何上無效」的解僈倖通過。這種「執行—評估—修訂」的迭代迴圈可在無人工介入下反覆運行，並把回饋轉化為局部化的修復目標，從而支援推論時間的規模化擴展。

**Q6：為何 3DCodeVerse Harness 同時被設計為「資料生成引擎」？這種雙重角色帶來什麼策略優勢？**

A：Harness 在執行過程中會記錄成功程式、失敗嘗試、目標化修復與偏好比較，這些執行軌跡本身就構成了監督式微調與偏好學習的高品質監督訊號。這意味著同一個系統既是「推論工具」又是「資料工廠」，形成資料建構→程式合成→驗證→精煉→模型改進的閉環。這種設計避免了「資料與推論脫節」的常見問題——訓練資料的分布會隨著模型能力提升而持續演化，使開源模型能透過自我對抗式迭代不斷進步，而非停留在固定語料的天花板。

**Q7：3DCodeVerse 在 3DCodeBench 上的執行率達到多少？這代表什麼樣的能力躍升？**

A：在 3DCodeBench 上，經 3DCodeVerse-2M 微調後的 9B 模型達到 84.9% 的執行率，27B 模型更達到 92.9%。這代表開源模型在「寫出能跑的 3D 程式」這項基本能力上已逼近可用門檻——過去開源模型常因語法錯誤、依賴缺失或 API 誤用而無法執行，而 92.9% 的執行率意味著絕大多數產出都能進入後續的視覺與幾何評估階段。這對實際部署至關重要，因為無法執行的程式在工業流程中等同於零產出。

**Q8：3DCodeVerse Harness 在成對人工評估中對 Claude Design（3D Object）的勝率為何？這個數字如何解讀？**

A：當兩者皆由 Claude Opus 5.5 驅動時，3DCodeVerse Harness 在成對人工評估中取得 90% 的勝率。這個數字需要謹慎解讀：它衡量的是「同一底層模型 + 不同生成框架」的相對表現，而非「3DCodeVerse 整體 vs. Claude Design 整體」。換言之，勝利的關鍵在於 Harness 的迭代精煉、空間檢查與視覺回饋機制，而非底層語言模型本身。這也暗示，對於閉源旗艦模型而言，框架設計的紅利可能比模型規模更為顯著。

**Q9：論文中提到「元件層級分析」（component-level analyses）具體包含哪些消融實驗？**

A：雖然完整細節需參考實驗章節，但根據方法描述可推斷元件層級分析涵蓋：DAG 分解相較於單代理序列生成的效益、執行檢查的必要性、空間測量相較於純視覺回饋的貢獻、評審代理的獨立性設計、以及迭代次數對最終品質的影響。這類消融實驗的目的是把 Harness 的整體增益拆解到各個機制，讓研究者了解哪些元件是「必須」、哪些是「錦上添花」，並為未來的框架設計提供可遷移的經驗法則。

**Q10：3DCodeVerse 在實際產品開發中可應用於哪些場景？**

A：在遊戲與影視產業，3DCodeVerse 可讓美術透過文字指令快速生成可編輯的 Blender 場景、關節式角色骨架或自訂著色器，並直接整合進既有管線。在工程與製造領域，CAD 程式碼生成可加速參數化零件設計，使用者只需調整尺寸變數即可衍生整個產品線。在教育與研究上，學生可透過程式碼形式理解 3D 建構邏輯，而非操作黑盒工具。此外，瀏覽器圖形支援讓生成的 3D 內容可直接嵌入網頁，用於電商展示、互動教學或元宇宙應用。

**Q11：將 3DCodeVerse 整合到現有 3D 工作流程時，產品層面需要考量哪些因素？**

A：首先，執行環境隔離是關鍵——Harness 會執行程式碼並渲染輸出，必須在沙箱中運行以避免損壞主機系統。其次，資產管理需要標準化封裝格式，確保生成的程式碼與相依資產能跨平台移植。第三，迭代成本（執行時間、API 額度、GPU 算力）必須被預算化，因為 Harness 的迭代精煉本質上是「以算力換品質」。最後，使用者介面需提供「接受/拒絕/修改」的控制權，因為自動化評審代理並非萬能，人類設計師的判斷在美學與品牌一致性上仍不可取代。

**Q12：3DCodeVerse 對 3D 生成領域的長期影響可能為何？**

A：長期來看，3DCodeVerse 推動了「3D 內容即程式碼」的範式轉移，使 3D 創作從「手工建模」走向「程式合成 + 自動驗證」的工業化流程。這種範式讓 3D 內容具備版本控制、差異比對、自動化測試等軟體工程優勢，從根本上改變資產管理方式。同時，閉環資料生成機制為開源模型提供了自我改進路徑，可能縮小開源與閉源模型在 3D 程式碼任務上的差距。更深遠地，當 3D 程式碼與大型語言模型深度整合時，可能催生「會寫 3D 程式的 AI 設計師」這類新職業角色。

**Q13：3DCodeVerse 存在哪些已知的限制？**

A：根據方法描述可推斷幾項限制：第一，Harness 的品質高度依賴評審代理的判斷力，若評審標準設計不當，可能陷入「代理互相認可低品質產出」的循環。第二，空間測量雖能捕捉幾何不一致，但對「美學品質」（如構圖、光影氛圍）的評估仍主要依賴視覺回饋，而視覺評估本身具有主觀性。第三，2.03M 配對的資料規模雖大，但相較於真實世界 3D 資產的長尾分布，仍可能存在類別不平衡。第四，框架目前聚焦於六種程式碼類型，對新興環境（如遊戲引擎、AR/VR 工具鏈）的支援尚未涵蓋。

**Q14：在什麼情況下 3DCodeVerse 可能會失敗？**

A：當任務需要高度創意或風格化的藝術表達時，Harness 的明確接受標準可能反而限制探索空間，導致產出趨向「安全但平庸」。當目標環境存在版本差異或非標準 API 時，獨立可執行的假設可能被打破，導致執行失敗。當輸入提示極為模糊或自相矛盾時，DAG 分解可能產生衝突的子任務，使代理間難以協調。此外，對於需要即時互動（如遊戲邏輯）或物理模擬（如流體、軟體動力學）的場景，純程式碼生成可能無法捕捉時間維度的細節，需要額外的模擬器整合。

**Q15：3DCodeVerse 的未來發展方向為何？**

A：未來可朝幾個方向延伸：首先是擴展程式碼類型與執行環境，涵蓋遊戲引擎（如 Unity、Unreal）、物理模擬器與 AR/VR 工具鏈；其次是引入更豐富的輸入模態，例如從影片、點雲或多視角影像直接合成 3D 程式；第三是強化評審代理的能力，例如引入基於物理的合理性檢查、語意一致性驗證與風格匹配度評估；第四是探索「人類設計師在迴圈中」的協作模式，讓 Harness 成為設計師的智慧助手而非完全自主的代理人；最後，隨著開源模型規模成長，可研究如何讓模型在無外部 Harness 的情況下內化迭代精煉能力，實現真正的「自我改進」。

## 實務應用指南

### 適用場景

1. **遊戲開發與關卡原型自動化**：獨立遊戲工作室或中型工作室可利用 3DCodeVerse Harness 從文字描述快速生成 Blender 場景腳本，將關卡設計師從重複性的場景佈局工作中解放出來，專注於核心玩法設計。對於需要大量程序化關卡的 Roguelike、模擬經營類遊戲特別有價值。

2. **電商產品 3D 展示管線**：電商平台可將產品照片或文字規格輸入 Harness，自動生成可旋轉、可縮放、可編輯的 3D 模型程式碼，輸出至 WebGL 或 USDZ 格式，支援 AR 預覽功能，取代傳統昂貴的手工建模流程。

3. **建築與室內設計快速視覺化**：建築事務所可將平面圖或客戶需求文字轉換為場景程式碼，於瀏覽器即時渲染出具備基本照明、材質的 3D 預覽，用於業主會議的快速迭代討論，縮短前期溝通週期。

4. **教育訓練教材的 3D 內容生成**：STEM 教育平台可利用 Harness 將抽象概念（如分子結構、幾何定理、機械構造）轉化為可互動的 3D 場景，教師只需提供文字描述即可生成教學素材，並保留可編輯的程式碼供進階學生修改學習。

5. **電影/廣告前期視覺預覽（Previs）**：影視製作團隊可將分鏡腳本轉換為粗略的 3D 場景，用於鏡頭規劃與燈光測試，雖然精度不足以用於最終成片，但能顯著降低 previs 階段的人力成本。

### 實作前置條件

**資料準備**
- 下載 3DCodeVerse-2M 資料集（2.03M 配對），需準備至少 500GB 以上的儲存空間
- 確認目標程式碼類型（CAD、Blender、Shaders、瀏覽器圖形等 6 種）的執行環境已部署
- 準備領域專屬的補充資料集（如特定產業的 CAD 模型庫）

**運算資源**
- 微調 9B 模型：建議 4×A100 80GB 或同等級 GPU，訓練時間約 3-7 天
- 微調 27B 模型：建議 8×H100 80GB，訓練時間約 1-2 週
- 推論部署：單張 A100 即可支援單一使用者請求；多用戶服務建議配備 GPU 叢集
- 執行環境：需預先安裝 Blender、FreeCAD、Three.js 等目標執行環境

**技能需求**
- 熟悉 Python 與至少一種 3D 程式碼框架（Blender Python API、CadQuery、Three.js）
- 具備 LLM 微調經驗（LoRA、QLoRA、全參數微調）
- 理解 DAG 工作流設計與多代理系統架構
- 基本的空間幾何概念（邊界框、體積計算、碰撞偵測）

**階段一：環境建置與資料準備（2-4 週）**
1. 從官方開源倉庫取得 3DCodeVerse-2M 資料集，依目標領域篩選子集
2. 部署 3DCodeVerse Harness 的執行環境，確保所有目標程式碼類型可在本機執行
3. 對資料集進行領域特化篩選，例如電商場景保留 Blender 場景類別，剔除 CAD 構造序列
4. 建立驗證基準集（建議 100-500 個任務），用於後續評估

**階段二：基線模型建立（2-3 週）**
1. 選擇基礎開源模型（建議從 9B 規模開始驗證可行性）
2. 使用 3DCodeVerse-2M 進行監督式微調，採用論文提及的訓練食譜
3. 在 3DCodeBench 上評估執行率，目標達到 80% 以上
4. 收集失敗案例，分析錯誤模式（語法錯誤、幾何錯誤、邏輯錯誤）

**階段三：Harness 整合與迭代（4-6 週）**
1. 整合 3DCodeVerse Harness 至現有工作流，配置 DAG 節點
2. 設定領域專屬的驗收標準，例如電商場景需包含特定視角與材質
3. 調校空間檢查的閾值參數，避免過度嚴格導致反覆修訂
4. 實作 A/B 測試框架，比較單次生成與 Harness 迭代生成的品質差異

**階段四：領域特化與產品化（4-8 週）**
1. 收集領域專屬的執行軌跡，用於持續微調
2. 建立使用者回饋機制，將人工評估結果回流至訓練資料
3. 開發 API 介面與前端整合，支援文字/圖片/影片輸入
4. 部署監控系統，追蹤執行成功率、平均迭代次數、使用者滿意度

**階段五：規模化與優化（持續）**
1. 根據使用數據擴充資料集，特別是失敗案例的修復軌跡
2. 嘗試更大的模型規模（27B）以提升品質
3. 探索偏好學習（DPO/RLHF）以對齊人類偏好
4. 建立資料飛輪，實現「使用越多、模型越好」的閉環

### 潛在風險與注意事項

**執行安全性風險**
- 風險：生成的程式碼可能在執行環境中執行任意操作，導致系統損壞或資料外洩
- 緩解：使用沙箱環境（如 Docker 容器）隔離執行；限制可存取的 API 與檔案系統；對輸入進行嚴格的清理與驗證

**幾何驗證誤判**
- 風險：空間檢查可能將視覺上正確但幾何參數微幅偏差的結果判定為失敗，造成無謂的迭代
- 緩解：為不同任務類型設定差異化的容差閾值；結合視覺回饋與幾何檢查的加權評分；定期校驗驗證標準與人類判斷的一致性

**訓練資料偏誤**
- 風險：3DCodeVerse-2M 主要源自開源資料，可能對特定風格或領域過度代表
- 緩解：建立領域專屬的平衡資料集；監控模型在不同子類別上的表現差異；定期進行公平性審計

**推論成本控制**
- 風險：Harness 的迭代精煉機制可能導致單次請求消耗大量 token，營運成本難以預估
- 緩解：設定最大迭代次數上限；實作早期停止機制；對簡單任務使用單次生成，僅對複雜任務啟動 Harness

**程式碼可維護性**
- 風險：生成的程式碼可能難以閱讀或修改，降低「可編輯」的核心價值
- 緩解：在訓練中加入程式碼風格規範；後處理階段進行格式化與註解補全；提供程式碼品質評分機制

**智慧財產權疑慮**
- 風險：訓練資料中的開源資產可能涉及授權問題，商業使用時需謹慎
- 緩解：建立授權追蹤機制；優先使用明確授權的資料來源；諮詢法律顧問確認商業使用合規性

### 與其他技術的整合建議

**與遊戲引擎整合**
- 將 Harness 生成的 Blender 場景透過 FBX/glTF 匯出至 Unity 或 Unreal Engine
- 利用引擎的材質系統替換生成的基礎材質，提升視覺品質
- 整合引擎的物理引擎，補強 Harness 缺乏的物理模擬能力

**與雲端渲染服務整合**
- 將生成的 3D 場景上傳至雲端渲染平台（如 AWS Deadline、Azure Batch Rendering），用於高品質離線渲染
- 整合 CDN 服務，將 3D 內容快取至邊緣節點，降低終端使用者延遲
- 與 WebXR 服務整合，支援瀏覽器內的 AR/VR 體驗

**與版本控制系統整合**
- 將生成的程式碼納入 Git 工作流，支援團隊協作與版本管理
- 整合 CI/CD 流程，自動執行幾何驗證與視覺回歸測試
- 建立程式碼審查機制，確保生成的內容符合品質標準

**與現有 CAD 工作流整合**
- 將生成的 CadQuery 程式碼匯入現有的 CAD 系統（如 FreeCAD、SolidWorks）
- 整合 PLM 系統，追蹤設計變更與版本歷史
- 與製造執行系統（MES）對接，將設計轉換為製造指令

**與 AI 輔助設計工具整合**
- 將 3DCodeVerse 作為生成式 AI 模組，嵌入現有的設計軟體外掛
- 與 Stable Diffusion、ControlNet 等 2D 生成模型結合，實現「2D 概念圖 → 3D 模型」的工作流
- 整合 NeRF、Gaussian Splatting 等新興 3D 表示法，擴展可生成的內容類型

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節的動機說明，理解「為什麼要用程式碼來生成 3D 內容」這個核心問題。接著瀏覽 Table 1 的資料集比較表，建立對 3D 程式碼生成領域的整體認知。實作上可從下載 3DCodeVerse-2M 的小型子集開始，嘗試執行其中的範例程式碼，體驗「程式碼即 3D 內容」的概念，無需立即投入模型訓練。

**給 AI 工程師**：重點關注第 1 節中關於 Harness 架構的描述，特別是多代理 DAG 框架的設計理念、執行-評估-修訂迴圈的實作細節。Table 1 的工具比較能幫助你評估是否要採用 3DCodeVerse 或自行建置。實作建議從整合現成的 Harness 開始，驗證其在你的領域資料上的表現，再決定是否需要進行領域特化的微調。論文中提及的 84.9% 與 92.9% 執行率是重要的效能基準。

**給研究者**：第 2 節的相關工作分類整理了完整的 3D 程式碼生成研究譜系，是建立研究定位的重要參考。建議深入分析 3DCodeVerse-2M 的資料建構流程，特別是「將異質 3D 表示法轉換為可執行程式碼」的方法論，這對建構其他領域的大規模程式碼資料集具有示範意義。Harness 的閉環設計（資料建構 → 程式合成 → 驗證 → 精煉 → 模型改進）也是值得延伸研究的方向，例如探索其在機器人、自動化化學等其他領域的應用。

**給產品經理**：重點理解 3DCodeVerse 解決的商業問題——「如何讓 3D 內容變得可編輯、可驗證、可規模化生產」。論文中提及的 90% 勝率（相較於 Claude Design）是關鍵的競爭力指標。實務上應評估目標使用者的技術能力：對於設計師，可強調可編輯性；對於一般使用者，則應包裝成對話式介面。建議先以 POC 形式驗證單一場景的端到端流程，量測實際的單位成本與品質，再決定是否擴大投資。資料飛輪的設計理念（使用越多、模型越好）是建立長期競爭優勢的核心。
