## 深度分析

#### 方法論解析

本論文提出兩項互補的核心貢獻：EasyProver 證明系統與 Aegis 任務生成管線。兩者共同構成一個「無需訓練即可近飽和現有基準、並能持續生成更困難驗證任務」的閉環框架。

**EasyProver 系統架構**

EasyProver 的設計哲學是「不訓練模型，而是改進搜尋結構」。其核心由四個相互獨立的元件組成：

1. **遞迴代理（recursive agents）**：採用樹狀分解策略，父代理接收子代理回傳的結果（完成的證明、反例或失敗訊息），再決定繼續、修正或擴展哪些分支。這與傳統 MCTS（蒙地卡羅樹搜尋）不同——後者依賴統計平均值更新節點值，而 EasyProver 直接讀取子代理的具體輸出（如證明文本或反例），屬於更接近 ReAct 風格的決策迴圈。

2. **隔離上下文（isolated contexts）**：每個子代理在獨立的上下文視窗中運作，避免長推理鏈中常見的上下文污染問題。這對程式驗證尤其關鍵，因為實作層級證明義務（implementation-level proof obligations）往往需要多層輔助引理（auxiliary lemmas）堆疊。

3. **非同步搜尋（asynchronous search）**：父代理不必等待所有子代理完成即可進行下一輪決策，提升整體吞吐量。

4. **平行戰術探測（parallel tactic probing）**：在單一證明步驟層級同時嘗試多個候選戰術（tactic），快速淘汰無效選項。

5. **INFINILEAN 彈性精化服務**：這是基礎設施層的關鍵創新。傳統的 Lean 介面（如 LeanDojo、lean-lsp-mcp）將 Lean 編譯器綁定於單一機器，導致每個證明者只能使用一個 Lean 伺服器。INFINILEAN 將精化（elaboration）服務拆分為無狀態（stateless）的網路端點，接收 Lean 原始碼後回傳結果，因此可在負載平衡池中水平擴展。這使得 EasyProver 能從單機架構轉向分散式架構，突破單一 Lean 伺服器的吞吐量瓶頸。

整體而言，EasyProver 的搜尋策略可類比為「LLM 引導的啟發式搜尋」：模型負責提出分解方案與戰術選擇，INFINILEAN 負責即時驗證，遞迴結構負責管理長程推理的一致性。

**Aegis 任務生成管線**

Aegis 解決了現有基準「靜態、易污染、規模小」的根本問題。其管線分為四個階段：

1. **合成安全 Rust 解決方案**：從競爭型程式設計（competitive programming）題庫出發，生成符合 Rust 安全子集（safe Rust）的實作。這排除了未定義行為，使得後續驗證具有語義意義。

2. **透過 Aeneas 翻譯為 Lean**：Aeneas 是 Rust 到 Lean 的翻譯工具，能保留遞迴程式結構、資料表示與控制流。翻譯後的 Lean 程式承載了定寬算術（fixed-width arithmetic）、顯式失敗（explicit failure）、生成迴圈（generated loops）、型別轉換（casts）與函式化變動（functionalized mutation）等實作層級細節——這些正是手寫基準難以大規模覆蓋的證明義務來源。

3. **生成規格（specification generation）**：為每個翻譯後的程式產生形式化規格（formal specification），描述其預期行為。

4. **核心檢查標註（kernel-checked labeling）**：對每個凍結陳述（frozen statement）標註核心檢查證明（kernel-checked proof）或反駁（refutation）。由於陳述與信任策略一旦固定即可重檢，這些標籤天然適合作為 RLVR（來自可驗證獎勵的強化學習）的獎勵訊號。

Aegis 的關鍵設計選擇是「分離任務生成與求解」：生成階段不依賴於任何特定證明者，因此產生的任務對所有證明者都是公平的測試集。此外，反駁標籤的引入填補了純證明或純執行評分迴圈的盲區——前者無法產生負標籤，後者容易被測試框架（test harness）利用。

**兩者的協同關係**

EasyProver 在現有基準上接近飽和（669/672 PutnamBench、6/6 IMO 2026、597/600 NTP4VC、189/189 VERINA），證明了其搜尋架構的有效性；但正因如此，作者需要 Aegis 來產生「尚未飽和」的更難任務。EasyProver 在 Aegis 產生的 2,000 條陳述上僅達到 52.7% 的證明率，驗證了 Aegis 任務確實具有區辨力。

#### 實驗數據解讀

**基準飽和度分析**

| 基準 | EasyProver 結果 | 飽和程度 |
|------|----------------|----------|
| PutnamBench | 669/672（99.55%） | 接近飽和 |
| IMO 2026 | 6/6（100%） | 完全飽和 |
| NTP4VC | 597/600（99.5%） | 接近飽和 |
| VERINA | 189/189（100%） | 完全飽和 |

這些數據揭示了兩個重要現象：首先，在數學競賽題目上，現成的（off-the-shelf）前沿模型（frontier model）配合精心設計的搜尋架構已能達到近乎完美的表現，這意味著 PutnamBench 與 IMO 2026 已失去作為「區辨不同證明者能力」的基準價值。其次，在程式驗證領域，VERINA 雖小（189 題）但已被完全解決，NTP4VC 也僅剩 3 題未解——這與作者在緒論中「現有驗證程式基準規模小」的觀察一致。

值得注意的是，所有回報結果均為「核心檢查證明或反駁」，而非模型自報的正確率。這在形式化推理領域是重要的可信度指標，因為核心檢查獨立於模型與搜尋演算法。

**Aegis 任務的規模與難度**

- **2,045 個差分驗證（differentially validated）的 Rust-Lean 程式配對**：差分驗證意味著 Rust 實作與 Lean 翻譯之間存在語義對應關係，這是保證驗證任務有意義的前提。
- **11,533 個候選規格（candidate specifications）**：規格數量遠超程式數量，說明每個程式可能對應多個不同角度的規格陳述。
- **2,000 條陳述的分層樣本（stratified sample）中，EasyProver 在 30 分鐘預算內證明 1,054 條（52.7%）**。

52.7% 的證明率是本文最關鍵的數據點。它證明了：(1) Aegis 任務對一個「能近飽和現有基準」的證明者而言仍具挑戰性；(2) 任務難度分佈合理——既非全部可解也非全部不可解，而是呈現中間態，這對訓練 RLVR 獎勵函數尤為重要（過於簡單或過於困難的任務都無法提供有效學習訊號）。

**時間預算的意義**

30 分鐘/陳述的預算設定值得關注。這比一般競賽題目的求解時間長得多，說明程式驗證任務的計算成本遠高於純數學證明。對於實際部署，這暗示了「即時驗證」目前仍不可行，但「批次離線驗證」已具實用價值。

#### 與現有研究的比較

**與神經定理證明系統的比較**

| 系統 | 訓練方式 | 搜尋策略 | 與 EasyProver 的差異 |
|------|----------|----------|----------------------|
| Goedel-Prover-V2 | 專家迭代 + RL | 整體證明生成 | 需要訓練；EasyProver 不訓練 |
| DeepSeek-Prover-V2 | RL + 大推論預算 | 整體證明生成 | 同上 |
| Seed-Prover | 專家迭代 | 形式化搜尋 | 同上 |
| Goedel-Code-Prover | 策略訓練 | 將目標歸約為核心檢查引理 | 專注程式驗證但需訓練 |

EasyProver 的定位是「零訓練、純架構改進」。這與近年主流的「以訓練換表現」路線形成對比。其優勢在於：(1) 不受訓練資料污染影響；(2) 可直接受益於前沿模型的持續進步；(3) 避免了 RL 訓練的不穩定性。劣勢在於：缺乏專門優化可能在特定領域表現不如專用系統。

**與現有基準的比較**

- **miniF2F**：已被 Mistral AI 等系統達到 100%，作者明確指出其已飽和。
- **PutnamBench、VERINA、NTP4VC**：EasyProver 接近或完全飽和。
- **CLEVER、AlgoVeri**：未在本文實驗中直接比較，但作者暗示這些基準同樣面臨規模限制。

Aegis 相對於這些基準的優勢在於：(1) 自動生成，無需專家標註；(2) 規模可擴展（更多計算即可產生更多任務）；(3) 包含實作層級證明義務，這是手寫基準難以系統性覆蓋的；(4) 提供反駁標籤，支援負向學習。

**與程式驗證管線的比較**

Aegis 的「Rust → Aeneas → Lean → 規格 → 核心檢查標註」管線是首個端到端自動化的驗證任務生成系統。現有系統如 Ye et al. (2025) 的 VERINA 與 Xu et al. (2026) 的 NTP4VC 均依賴人工撰寫規格與證明，規模受限於專家時間。Aegis 的瓶頸在於 Aeneas 翻譯的語義保真度與規格生成的正確性——若翻譯引入語義偏差或規格未能捕捉預期行為，則驗證任務將失去意義。

**限制與不足**

1. **Aeneas 翻譯的覆蓋範圍**：Aeneas 對 Rust 安全子集的支援可能不完整，某些進階特性（如異步、unsafe 區塊）無法翻譯。
2. **規格生成的品質**：自動生成的規格可能過弱（無法捕捉所有預期行為）或過強（包含不可能成立的性質）。
3. **52.7% 的證明率意味著近半任務未被解決**，這對 RLVR 訓練是雙刃劍——既提供了困難樣本，也意味著獎勵訊號稀疏。
4. **30 分鐘/陳述的計算成本**對實際應用仍偏高。

- **動態基準**：Aegis 開啟了「基準即服務」的模式——基準不再是靜態集合，而是可持續生成的流水線。這對抗污染與維持區辨力至關重要。
- **跨領域驗證**：將競賽程式設計擴展至工業級程式碼庫（如開源系統軟體），產生更具實用價值的驗證任務。
- **人機協作驗證**：探索 LLM 代理與人類專家協作的驗證流程，例如 LLM 提出證明骨架、人類填補關鍵步驟。

**5. 理論基礎的深化**

- **搜尋複雜度的形式化分析**：EasyProver 的遞迴搜尋在最壞情況下的複雜度如何？是否存在可證明的收斂條件？
- **任務難度的可預測性**：能否在給定程式與規格後，預測其對特定證明者的難度？這對任務分配與資源排程極有價值。
- **核心檢查標籤的信賴區間**：當規格生成可能出錯時，如何量化標籤的可信度？

**6. 實際部署的工程挑戰**

- **降低單任務成本**：將 30 分鐘預算壓縮至分鐘級，是實際應用的關鍵門檻。

這些方向共同指向一個更宏觀的願景：將形式化驗證從「專家手工藝」轉變為「可擴展的工程實踐」，而 EasyProver 與 Aegis 是這一轉變的重要里程碑。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於兩個相互關聯的核心問題。首先是如何建構一個能有效處理形式化定理證明與程式驗證任務的 LLM 代理系統，因為現有方法在有限上下文視窗與計算預算下，難以同時兼顧單步正確性與長期推理的連貫性。其次是如何產生足夠困難且規模龐大的驗證任務，因為現有基準已接近飽和且手寫基準規模太小，無法有效評估下一代證明器的能力。這兩個問題的結合使得論文必須同時推進「證明器」與「任務生成」兩條技術路線。

**Q2：為什麼現有的神經定理證明方法不足以解決這些問題？**
A：現有方法如 Goedel-Prover-V2、DeepSeek-Prover-V2 與 Seed-Prover 等，雖然透過專家迭代、強化學習與大規模推理預算提升了準確率，但它們都依賴在精選證明語料上訓練，並使用學習過的策略或價值函數來引導搜尋。這種訓練式方法不僅成本高昂，也使其容易受到資料污染與記憶化的影響。此外，現有的 Lean 介面（如 LeanDojo 與 lean-lsp-mcp）都將 Lean 綁定在與代理同一台機器上，限制了可擴展性，也讓每個證明器只能對應單一 Lean 伺服器。

**Q3：為什麼這項研究對形式化推理領域很重要？**
A：這項研究的重要性體現在三個層面。第一，它展示了一個無需額外訓練、僅憑現成前沿模型就能接近飽和多項基準的證明系統，大幅降低了部署門檻。第二，Aegis 流水線能自動產生帶有核心檢查標籤的困難驗證任務，解決了靜態基準易受污染且規模有限的根本問題。第三，這些任務可作為來自可驗證獎勵的強化學習（RLVR）的訓練獎勵，比基於測試的獎勵更可靠，因為測試只能提供有限證據且容易被代理利用測試框架而非真正實作預期行為。

**Q4：EasyProver 的核心方法架構是什麼？**
A：EasyProver 的核心架構由四個關鍵元件組成：具有隔離上下文的遞迴代理、非同步搜尋、平行戰術探測，以及一個名為 INFINILEAN 的無狀態彈性精化服務。遞迴代理採用類似 ReAct 的迴圈，交替進行模型呼叫與工具呼叫，並透過 Model Context Protocol 暴露 Lean 工具。父代理會被提示子代理回傳的證明狀態與結果，並據此決定繼續、修正或擴展哪些分支，這與傳統蒙地卡羅樹搜尋中維護平均值估計的方式不同。

**Q5：Aegis 流水線的關鍵創新是什麼？**
A：Aegis 的關鍵創新在於將競爭型程式設計題目自動轉化為遠比現有基準更困難的 Lean 驗證任務。其流程包含四個步驟：先寫出安全的 Rust 解答，再用 Aeneas 將其翻譯成 Lean，接著自動產生形式化規格，最後為每個凍結陳述附上核心檢查的證明或反駁。這種方法產生的任務帶有定寬算術、顯式失敗、生成迴圈、型別轉換與函式化變動等實作層級的證明義務，這些都是手寫基準難以大規模涵蓋的細節。

**Q6：EasyProver 在系統設計上有哪些重要的取捨？**
A：最重要的設計取捨是將 INFINILEAN 設計為無狀態服務，透過網路接受 Lean 原始碼，這使得負載平衡池中的任何副本都能檢查任何證明，從而打破了「一個證明器綁定一個 Lean 伺服器」的限制。另一個關鍵取捨是父代理直接讀取子代理的結果（如完成的證明或反例），而非維護統計平均值，這讓搜尋更靈活但也讓推理更依賴模型的判斷。此外，遞迴代理使用隔離上下文來避免上下文污染，這雖然增加了通訊成本，但換來了更好的長期推理穩定性。

**Q7：論文中使用了哪些基準來評估 EasyProver？**
A：論文中使用了四個已建立的基準與一個新提出的基準。已建立的基準包括：包含 672 題的 PutnamBench（奧林匹克級數學）、IMO 2026 的六個形式化題目、包含 600 個驗證條件的 NTP4VC（工業級程式驗證套件），以及包含 189 個任務的 VERINA。新提出的 Aegis 基準則包含 2,045 個經差分驗證的 Rust-Lean 程式配對與 11,533 個候選規格，並從中分層抽樣 2,000 個陳述進行評估。

**Q8：EasyProver 的關鍵實驗結果為何？**
A：EasyProver 在已建立基準上幾乎達到飽和：證明了 PutnamBench 的 669/672 題、IMO 2026 的全部 6 個形式化題目、NTP4VC 的 597/600 個驗證條件，以及 VERINA 的全部 189 個任務（透過證明或反駁）。然而在 Aegis 產生的新基準上，從 2,000 個分層樣本陳述中僅證明了 1,054 個（52.7%），每個陳述有 30 分鐘的預算，這顯示新任務對即使是接近飽和的證明器仍具挑戰性。所有回報的結果都是核心檢查過的證明或反駁，而非僅僅是模型自我評估。

**Q9：論文中是否有消融實驗來驗證各元件的貢獻？**
A：從提供的全文內容來看，論文並未明確呈現傳統意義上的消融實驗，例如逐一移除遞迴代理、隔離上下文、非同步搜尋或 INFINILEAN 等元件來比較效能。然而，論文透過比較 EasyProver 在不同基準上的表現，間接展示了各元件的價值：例如在已建立基準上的近飽和表現證明了整體架構的有效性，而在 Aegis 新基準上僅 52.7% 的通過率則顯示了任務難度對系統設計的考驗。論文中提到的「差分驗證」機制也可視為一種隱含的消融，用以確保 Rust 解答與 Lean 翻譯之間的語意一致性。

**Q10：這項研究的實際應用場景有哪些？**
A：實際應用場景相當廣泛。首先，Aegis 可用於自動化產生大規模的程式驗證基準，無需專家標註即可持續擴充，這對程式語言社群與形式化方法社群都有直接價值。其次，EasyProver 可用於驗證真實世界的 Rust 程式碼，因為 Aegis 流水線已經展示了從 Rust 程式到 Lean 證明的完整路徑。第三，這些帶有核心檢查標籤的任務可作為 RLVR 的訓練獎勵，用於訓練下一代更強大的證明器模型。最後，該流水線支援突變測試，可透過對已驗證程式進行小幅修改來產生更刁鑽的測試案例。

**Q11：在將 EasyProver 部署為產品時需要考慮哪些工程因素？**
A：產品化部署需要考慮多項工程因素。INFINILEAN 的無狀態設計雖然簡化了水平擴展，但需要可靠的網路基礎設施與負載平衡機制來處理大量並行的精化請求。30 分鐘的單任務預算意味著需要仔細的成本控制與資源排程，特別是在雲端環境中。隔離上下文的設計雖然提升了推理品質，但也增加了代理間通訊的複雜度，需要設計良好的序列化與錯誤恢復機制。此外，由於 Lean 工具是透過 Model Context Protocol 暴露的，整合到現有 IDE 或 CI/CD 流程時需要考慮相容性與使用者體驗。

**Q12：這項研究對形式化推理與程式驗證領域的更廣泛影響是什麼？**
A：這項研究的影響可分為短期與長期兩個層面。短期而言，它提供了一個可立即使用的強大證明系統與一個持續成長的困難基準庫，這將推動整個領域的基準提升與方法比較。長期而言，Aegis 展示的「自動產生帶有核心檢查標籤之任務」範式，可能成為未來訓練與評估神經證明器的標準方法，因為它同時解決了污染、規模與獎勵可信度三大問題。更深遠地，這種「任務生成與解決分離」的設計哲學，可能會影響整個 AI for Math 與 AI for Code 研究的方向。

**Q13：論文中承認了哪些限制？**
A：論文坦率承認了幾項重要限制。首先，雖然 EasyProver 在已建立基準上接近飽和，但在 Aegis 新基準上僅 52.7% 的通過率顯示仍有大量進步空間。其次，Aegis 流水線雖然無需專家標註，但仍需要額外計算資源來產生更多任務，這意味著規模擴展並非免費。第三，論文中提到「差分驗證」機制在某些情況下可能不足以捕捉所有語意差異，特別是涉及定寬算術與顯式失敗等實作細節時。最後，雖然 EasyProver 不需要訓練，但所使用的現成前沿模型本身的限制（如上下文視窗大小與推理能力）仍會影響整體表現。

**Q14：EasyProver 在哪些情況下會失敗？**
A：從實驗數據可推論出幾類失敗情況。在 PutnamBench 上有 3 題未能證明，在 NTP4VC 上有 3 個驗證條件未能解決，在 Aegis 的 2,000 個樣本中有 946 個陳述在 30 分鐘預算內未能證明。這些失敗可能源於多種原因：對於需要特定抽象選擇或分層輔助引理的數學題目，代理可能無法找到正確的分解策略；對於程式驗證任務，涉及定寬算術、顯式失敗、生成迴圈、型別轉換與函式化變動等實作細節的證明義務可能特別困難；此外，當證明需要跨越多個層級的推理時，有限的上下文視窗可能導致早期決策的錯誤成本在後期才顯現。

**Q15：這項研究的未來方向有哪些？**
A：論文中暗示了幾個明確的未來方向。第一，由於 Aegis 流水線的設計是模組化的，可以透過增加計算資源來產生更多任務，這將持續擴充基準的規模與難度。第二，這些任務可作為 RLVR 的訓練獎勵，用於訓練專門的程式驗證模型，這與 Goedel-Code-Prover 的路線形成互補。第三，Aegis 任務可用於基準測試其他證明器，促進領域內的公平比較。第四，論文中提到的突變測試支援是一個尚未完全展開的方向，未來可透過系統性地修改已驗證程式來產生更具針對性的困難案例。最後，將 EasyProver 與其他證明助手（如 Coq、Isabelle）整合，或將其應用於其他程式語言的驗證，都是值得探索的延伸方向。

## 實務應用指南

### 適用場景

1. **安全關鍵系統的形式化驗證**：將 EasyProver 應用於航空、醫療、汽車等領域的嵌入式 Rust 程式碼驗證。透過 Aeneas 將 Rust 程式翻譯為 Lean，再用 EasyProver 自動產生核心檢查證明，特別適合處理定寬算術溢位、顯式失敗回傳、生成迴圈等實作層級證明義務。

2. **競賽程式解題正確性審核**：將 Aegis 流程整合進程式設計競賽平台，自動將選手提交的 Rust 解法轉譯為 Lean 並產生規格，驗證解法是否真正符合題意而非僅通過測試案例。這能有效防止「測試框架漏洞攻擊」(test harness exploitation)。

3. **企業內部程式庫的契約驗證**：針對內部 Rust SDK 或關鍵函式庫，使用 Aegis 產生 2,045 個差分驗證過的 Rust-Lean 程式配對作為基準，並用 EasyProver 對新提交的 PR 自動檢查是否符合既有規格，產生 11,533 個候選規格作為回歸測試基準。

4. **強化學習訓練獎勵訊號產生**：將 Aegis 產生的凍結陳述搭配核心檢查標籤（證明或反駁）作為 RLVR 的獎勵函數，訓練新一代程式碼生成模型。由於標籤可被 Lean 核心重新檢查，無需擔心獎勵 hacking。

5. **學術研究中的基準測試與污染防範**：使用 Aegis 自動產生新驗證任務，避免現有基準（如 PutnamBench、VERINA）已接近飽和或遭受訓練資料污染的問題。同一組任務可同時用於評估不同證明器。

### 實作前置條件

**資料需求**：
- 來源程式設計競賽題庫（如 Codeforces、AtCoder 風格的題目與其參考解）
- 欲驗證的 Rust 程式碼（須為安全 Rust 子集，能被 Aeneas 翻譯）
- 領域專家撰寫的初始規格草案（可由 LLM 草擬後人工審閱）

**計算資源**：
- 大型語言模型 API 存取權（前沿模型如 Claude、GPT 等）
- INFINILEAN 風格的無狀態精化服務叢集（建議至少 8-16 個 Lean 伺服器節點以支援平行戰術探測）
- 異步搜尋所需的訊息佇列基礎設施（如 AWS SQS 或自建 Redis/RabbitMQ）
- 每個陳述 30 分鐘的證明預算（EasyProver 在 2,000 個陳述的 52.7% 證明率以此為基準）

**技能前提**：
- 熟悉 Lean 4 證明助手語法與戰術系統
- 具備 Rust 程式設計能力，特別是理解其所有權系統與型別轉換
- 了解 Aeneas 翻譯工具的限制與適用範圍
- 具備分散式系統設計經驗以部署 INFINILEAN
- 對遞迴代理架構與 ReAct 風格迴圈有實務理解

### 實作步驟建議

**階段一：基礎建設（2-4 週）**
1. 部署 INFINILEAN 無狀態精化服務：將 Lean 編譯器封裝為 HTTP API，確保負載平衡池中的任何副本都能處理任意證明請求。
2. 整合 Model Context Protocol（MCP）介面，將 Lean 工具暴露給 LLM 代理。
3. 建立隔離上下文環境：每個子代理運行在獨立的對話上下文，避免主代理的上下文視窗被戰術輸出淹沒。

**階段二：EasyProver 系統建置（4-6 週）**
4. 實作遞迴代理架構：父代理接收子代理回傳的證明狀態與結果，決定繼續、修訂或擴展哪些分支。
5. 加入平行戰術探測：對同一個證明目標並行嘗試多個戰術候選，由 INFINILEAN 並行檢查。
6. 設定異步搜尋協調器：管理子代理生命週期、收集結果、處理逾時。

**階段三：Aegis 流程整合（4-8 週）**
7. 建立 Rust 解題管線：使用 LLM 撰寫安全 Rust 解法，確保通過編譯與基本測試。
8. 整合 Aeneas 翻譯：將 Rust 程式轉為 Lean 表達式，處理定寬算術、顯式失敗、生成迴圈等實作細節。
9. 自動產生規格：使用 LLM 從題目敘述產生形式化規格，並以差分測試驗證 Rust 與 Lean 實作在多組輸入上行為一致。
10. 凍結陳述並標記：將每個陳述（含其證明或反駁）凍結，確保可被 Lean 核心重新檢查。

**階段四：評估與部署（2-4 週）**
11. 在分層樣本上評估 EasyProver 的證明率，預期在 30 分鐘預算下達到約 50% 證明率。
12. 將產生的 Rust-Lean 程式配對與候選規格匯入版本控制，作為基準資料集。
13. 設定持續整合鉤子：對新提交的程式碼自動產生驗證任務並呼叫 EasyProver。

### 潛在風險與注意事項

**風險一：基準飽和與過度自信**
- **現象**：EasyProver 在 PutnamBench 達到 669/672、VERINA 達到 189/189，看似完美但實際上這些基準已接近飽和，無法反映真實世界困難度。
- **緩解**：務必同時在 Aegis 產生的新任務上評估，因為其 52.7% 證明率顯示仍有大量進步空間。

**風險二：訓練資料污染**
- **現象**：靜態基準（如 miniF2F）可能已進入模型的訓練資料，導致高準確率不代表真實能力。
- **緩解**：使用 Aegis 自動產生新任務，因為其來源題目雖公開，但翻譯後的程式與規格是全新的。

**風險三：獎勵 hacking 與測試漏洞**
- **現象**：當使用測試通過率作為訓練獎勵時，模型可能學會利用測試框架漏洞而非實作正確行為。
- **緩解**：使用核心檢查證明或反駁作為獎勵訊號，因為這些標籤由 Lean 核心驗證，無法被規避。

**風險四：證明預算管理不當**
- **現象**：30 分鐘的證明預算對單一陳述看似充裕，但若無適當的早停機制，會快速耗盡計算資源。
- **緩解**：實作異步搜尋時設定多層逾時，並讓父代理根據子代理回傳的進度訊號主動放棄無望分支。

**風險五：Aeneas 翻譯限制**
- **現象**：Aeneas 無法處理所有 Rust 構造，特別是非安全 Rust、unsafe 區塊、複雜巨集。
- **緩解**：在管線前端過濾，僅接受安全 Rust 子集；對無法翻譯的程式明確標記為失敗而非強行轉譯。

**風險六：規格錯誤傳播**
- **現象**：若 LLM 產生的規格本身有誤，EasyProver 證明的將是錯誤的陳述。
- **緩解**：採用差分驗證（differential validation）確保 Rust 與 Lean 實作在大量隨機輸入上行為一致，作為規格正確性的間接證據。

### 與其他技術的整合建議

**與現有 CI/CD 系統整合**：
將 EasyProver 包裝為 GitHub Actions 或 GitLab CI 的步驟，對 Rust PR 自動觸發驗證。建議設定為非阻塞式檢查（報告但不阻擋合併），並依賴人工審查處理 EasyProver 無法證明的 47.3% 陳述。

**與程式分析工具鏈整合**：
- **Kani / MIRAI**：先用這些 Rust 模型檢查器快速過濾明顯錯誤，再將通過的程式送入 EasyProver 進行深度驗證。
- **Prusti**：可作為規格產生器的替代方案，產生更精確的前置/後置條件供 EasyProver 使用。

**與其他 LLM 證明器整合**：
Aegis 產生的 2,045 個程式配對與 11,533 個候選規格可作為評估 Goedel-Code-Prover、DeepSeek-Prover-V2 等其他證明器的標準化基準。建議建立公開排行榜追蹤各證明器在這些任務上的表現。

**與 RLVR 訓練管線整合**：
將凍結陳述的核心檢查標籤直接作為強化學習的獎勵訊號。建議使用 GRPO 或 PPO 等演算法，並設定適當的獎勵塑形（如對證明給予 +1、對反駁給予 +0.5、對逾時給予 0）。

**與教育平台整合**：
將 EasyProver 包裝為互動式學習工具，學生可看到代理如何分解目標、嘗試中間引理、從失敗方法中恢復。這對教授形式化推理特別有價值。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題動機，理解為何現有基準已飽和以及為何需要新的驗證任務。接著跳到第 4 節的實驗結果，體會 EasyProver 在不同基準上的表現差異（PutnamBench 的 99.6% vs. Aegis 的 52.7%）。技術細節可暫時略過，重點掌握「證明器不只是一個模型加上一個檢查器」的核心理念。

**給 AI 工程師**：重點閱讀第 3.1 節的 EasyProver 架構，特別是遞迴代理、隔離上下文、INFINILEAN 無狀態服務的設計。理解父代理如何根據子代理回傳的具體結果（而非平均值估計）來決定搜尋方向，這與傳統 MCTS 有本質差異。建議實際部署一個小型 INFINILEAN 叢集來體驗平行戰術探測的吞吐量提升。

**給研究者**：第 3.2 節的 Aegis 管線是本文最具長期影響力的貢獻。深入分析其如何將競賽題目轉化為帶有實作層級證明義務的驗證任務，特別是定寬算術、顯式失敗、生成迴圈等細節如何產生比手寫基準更難的任務。此外，第 2 節對污染與飽和問題的討論值得延伸思考：如何設計能持續產生新任務的自動化管線。

**給產品經理**：聚焦於兩個數字：EasyProver 在現有基準上接近 100% 但在 Aegis 上僅 52.7%，這意味著「現有基準已無法區分頂尖證明器」。若產品定位是程式碼驗證，應將 Aegis 類型的任務作為內部評估標準。同時注意 30 分鐘/陳述的計算成本，這對商業模式的定價有直接影響。建議將 EasyProver 定位為「安全關鍵程式碼的深度審查工具」而非「全自動 CI 檢查」，因為仍有近半任務需要人工介入。
