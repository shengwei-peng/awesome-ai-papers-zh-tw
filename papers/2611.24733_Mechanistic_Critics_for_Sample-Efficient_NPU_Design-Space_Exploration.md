本文提出 CriticNPU 框架，核心思想是將「機制式評論器 (mechanistic critic)」引入 NPU 設計空間探索 (DSE) 的搜尋迴圈中，以解決純量回饋 (scalar feedback) 資訊不足的問題。整體方法論可從三個層次剖析：

**1. 問題重新定義：從純量評分到評論器引導搜尋**

傳統 DSE 方法將模擬器視為黑盒，僅以延遲 (latency) 與功耗 (power) 等純量指標排序候選配置 (candidate configuration)。本文指出此模式有兩個根本缺陷：(a) 無法解釋「為何某配置慢」；(b) 無法預測「未模擬的配置是否值得模擬」。CriticNPU 將 DSE 重新表述為「評論器引導搜尋 (critic-guided search)」問題，評論器在搜尋迴圈中扮演雙重角色——模擬前過濾弱候選 (weak candidates)，模擬後診斷瓶頸並預測參數變更效果。

**2. 評論器的數學基礎：線上校準的 Roofline 模型**

評論器實作為 Roofline 風格模型 (Roofline-style model)，其核心公式推導自 NPU 架構參數：

- **計算上限 (compute limit)**：由脈動陣列 (systolic array) 數量、維度、向量單元 (vector unit) 數量與時脈頻率 (clock frequency) 共同決定，反映尖峰 FLOPS。
- **記憶體上限 (memory limit)**：由 HBM 頻寬 (HBM bandwidth)、晶片間互連 (ICI, Inter-Chip Interconnect) 頻寬與晶片上記憶體 (on-chip memory) 容量決定，反映資料傳輸尖峰頻寬。

關鍵創新在於「線上校準 (online-calibrated)」機制：模擬器觀測值 (simulator observations) 被用來校正每運算子類型 (per-operator-type) 的有效限制 (effective limits)。這意味著 Roofline 模型並非靜態理論上限，而是隨搜尋過程動態調整，使其能反映實際硬體行為中的非理想因素（如排程開銷、記憶體存取模式不規則性等）。

**3. 三元件協作架構**

- **工作負載擷取器 (Computing Demand Agent)**：將 LLM 規格 (LLM specification) 與部署設定 (deployment setting) 映射為運算子層級 (operator-level) 的工作負載描述，包含各運算子的計算量與記憶體存取需求。
- **評論器 (Online-Calibrated Roofline Model)**：提供三項功能——候選過濾 (candidate filtering)、階段瓶頸摘要 (per-phase bottleneck summary)、候選參數變更預測 (candidate parameter-change prediction)。
- **架構規劃器 (Architecture Design Agent)**：基於 LLM 的代理，根據評論器回饋提出下一個 NPU 配置。

此架構的精妙之處在於「分工」：LLM 代理僅負責「提案」，而「決策」——哪些候選值得模擬、哪些參數應優先調整——完全由評論器驅動。這避免了 LLM-assisted DSE 方法中 LLM 幻覺導致的無效模擬。

**4. 評論器的雙時點使用**

- **模擬前 (pre-simulation)**：評論器估計候選配置是否優於當前最佳 (current best)，弱候選被直接跳過，無需呼叫模擬器。
- **模擬後 (post-simulation)**：評論器聚合運算子層級執行時間 (operator-level runtime) 為預填充/解碼瓶頸摘要，並預測候選參數變更的延遲影響。例如，若診斷為記憶體受限 (memory-bound)，下一輪更新應調整影響記憶體時間的參數，而非盲目增加脈動陣列。

此雙時點設計是樣本高效 (sample-efficient) 的關鍵——它將寶貴的模擬器呼叫次數 (simulator calls) 集中於資訊量最大的候選上。

#### 與現有研究的比較

**1. 與黑盒搜尋方法的比較**

貝氏優化 (Bayesian optimization)、CMA-ES、貪婪搜尋 (greedy search)、網格搜尋 (grid search) 等黑盒方法僅利用純量回饋，需大量模擬器呼叫學習有用的配置區域。CriticNPU 的評論器提供了「結構化先驗」，使搜尋能直接聚焦於硬體限制所允許的 Pareto 前緣，樣本效率提升約一倍。

**2. 與瓶頸感知方法的比較**

Bai 等人 (2023b) 與 Zhang 等人 (2026) 的瓶頸感知方法透過分析模擬器追蹤 (simulator traces) 或關鍵路徑 (critical paths) 解釋「為何已模擬的配置慢」。此診斷雖有價值，但僅限於已評估的配置——無法預測未模擬候選的潛力。CriticNPU 的評論器將瓶頸分析從「事後解釋」提升為「事前預測」，這是質的躍進。

**3. 與 LLM 輔助 DSE 方法的比較**

ChatDSE、LLM-DSE、LLM-Box 等方法利用 LLM 從提示詞 (prompts)、搜尋歷史 (search history) 與設計規則 (design rules) 中提出多參數配置 (multi-parameter configurations)。然而，這些方法仍依賴模擬器純量回饋決定是否接受提案。CriticNPU 的差異化在於：LLM 僅負責「提案」，評論器負責「決策」，形成明確的職責分離。這降低了 LLM 幻覺導致無效模擬的風險。

**4. 與 Roofline 模型經典應用的比較**

Roofline 模型 (Williams et al., 2009) 傳統上用於後處理分析——給定硬體與工作負載，計算理論加速比。本文將 Roofline 從「分析工具」轉化為「搜尋引導工具」，並透過線上校準解決其「過於理想化」的傳統批評。

## [Limitations & Future 限制與未來]

**Q13：CriticNPU 存在哪些已知的限制？Roofline 風格模型的根本假設是什麼？**

A：Roofline 模型的核心假設是運算時間可分解為計算時間與記憶體時間，並取兩者之最大值。這個假設在運算與記憶體存取能清晰分離、且兩者不會動態重疊的場景下是合理的，但在實際硬體中，許多效應會打破這個假設：快取命中率的動態變化、運算與記憶體存取的時間重疊、互連拓撲對通訊模式的影響、脈動陣列的數據重用效率等。雖然線上校準機制能部分緩解這些問題，但對於校準資料未涵蓋的配置區域，模型的預測準確度仍可能下降。此外，評論器的有效性也受限於模擬器本身的準確度——若模擬器無法精確建模某些硬體效應，評論器也無法診斷這些效應帶來的瓶頸。

**Q14：在哪些情境下 CriticNPU 可能會失敗或表現不佳？**

A：CriticNPU 可能面臨幾類失敗情境。第一，當工作負載的瓶頸模式高度動態或非典型時（例如極度稀疏的注意力模式、不規則的運算子融合），Roofline 風格模型可能無法準確捕捉瓶頸的動態變化。第二，當 LLM 規劃器提議的配置落在設計空間中校準資料極為稀疏的區域時，評論器的預測可信度會下降。第三，當架構參數之間存在 Roofline 模型無法表達的複雜耦合效應時（例如特定的互連拓撲對集體通訊的影響），評論器的診斷可能誤導參數調整方向。第四，對於訓練階段的工作負載（而非純推論），由於瓶頸模式截然不同，方法可能需要重新校準。

**Q15：未來有哪些值得探索的研究方向？**

A：基於本文的框架，未來研究有多個值得探索的方向。首先，可以發展更豐富的評論器模型，例如結合資料流分析、互連拓撲模型與熱效應模型，超越傳統 Roofline 的兩維度分析。其次，可以將評論器概念延伸到多目標最佳化，同時考慮延遲、功耗、面積與成本等多個目標。再次，可以探索評論器與硬體合成工具的深度整合，使評論器不僅評估配置，還能直接指導 RTL 層級的設計決策。此外，將 CriticNPU 應用於其他加速器類型（如資料流加速器、近記憶體計算架構）也是重要的延伸方向。最後，結合形式化方法（如 satisfiability modulo theories）來驗證評論器預測的正確性，將有助於提升方法在安全關鍵應用中的可信度。

### 潛在風險與注意事項

**風險一：Roofline 模型假設過於簡化**
Roofline 模型假設計算與記憶體可完美平行，但實際 NPU 有管線排程、資料移動、bank conflict 等非理想因素。若模擬器本身已包含這些效應，校準後的「有效限制」可能與理論值差距甚大，導致評論器預測失準。
**緩解**：在評論器中加入「信心區間」而非單一點估計；定期用新模擬資料重新校準；保留一定比例的「探索性」模擬以發現模型盲區。

**風險二：LLM 規劃器的幻覺與不穩定性**
LLM 可能提出違反硬體約束的配置（例如：HBM 容量不足容納模型權重），或在不同次執行中提出截然不同的候選，導致搜尋結果難以重現。
**緩解**：在評論器中加入硬約束驗證層；設定隨機種子並多次執行取最佳；對 LLM 輸出進行格式驗證與自動修正。

**風險三：模擬器與真實晶片的差距（simulation-to-silicon gap）**
模擬器通常無法完全捕捉製程變異、溫度效應、DRAM 排程等真實硬體特性。若 CriticNPU 找到的「最佳配置」在實際晶片上表現不如預期，將造成嚴重的設計錯誤。
**緩解**：在關鍵設計決策點保留安全邊際（safety margin）；結合矽後量測資料持續校準評論器；不要將模擬器結果視為唯一真理。

**風險四：校準資料不足導致的過擬合**
若僅用少數幾個配置校準評論器，可能使「有效限制」過度擬合這些特定配置，無法泛化到設計空間的其他區域。
**緩解**：採用分層抽樣確保校準資料涵蓋設計空間的不同區域；使用正則化避免校準參數過度膨脹；保留獨立的驗證集。

**風險五：預填充與解碼最佳配置衝突**
本文已指出 TTFT 與 TPOT 的最佳 NPU 配置可能不同。CriticNPU 目前分別報告兩者的最佳結果，但實務上只能選擇單一晶片配置。
**緩解**：在產品化時加入「權重設定」介面，讓使用者根據應用情境（聊天機器人重視 TTFT vs 程式碼生成重視 TPOT）調整最佳化目標；或考慮可重配置（reconfigurable）NPU 設計。

### 與其他技術的整合建議

**與 ML 編譯器整合**
CriticNPU 的工作負載擷取器可與 ML 編譯器（如 TVM、MLIR、XLA）整合，直接從編譯器的運算圖（computation graph）推導運算子層級的工作負載描述，避免手動映射的錯誤。建議在編譯器的 cost model 中嵌入 CriticNPU 的 Roofline 評論器，使兩者共享校準資料。

**與硬體描述語言（HDL）整合**
當 CriticNPU 找出最佳架構參數後，可透過參數化 HDL（如 Chisel、SpinalHDL、BlueSpec）自動生成對應的 RTL 程式碼，進一步串接至合成（synthesis）與佈局（place-and-route）工具，實現從「演算法層級 DSE」到「電路實作」的端到端流程。

**與雲端部署平台整合**
將 CriticNPU 部署為 Kubernetes 上的服務，當使用者提交新的 LLM 部署請求時，自動觸發 DSE 並回傳推薦的 NPU 配置。可與 AWS Inferentia、Google Cloud TPU、Azure Maia 等雲端加速器的配置管理 API 整合。

**與 LLM 代理框架整合**
CriticNPU 的架構規劃器本質上是一個 LLM 代理，可整合至 LangGraph、AutoGen、CrewAI 等代理框架中，使其能與其他設計代理（如功耗分析代理、驗證代理）協作，形成更完整的「AI 晶片設計助理」。

**與版本控制與實驗管理整合**
將 CriticNPU 的搜尋歷史、模擬器輸出、校準參數納入 MLflow 或 Weights & Biases 等實驗管理平台，方便團隊協作、追溯設計決策、比較不同 DSE 策略。

**與現有 DSE 工具鏈整合**
若組織已使用 Timeloop、Accelergy、CoSA、OpenROAD 等開源工具，建議將 CriticNPU 作為「上層搜尋策略」與這些「下層模擬/合成工具」解耦，透過標準化介面（如 JSON Schema）交換資料，避免重複造輪。
