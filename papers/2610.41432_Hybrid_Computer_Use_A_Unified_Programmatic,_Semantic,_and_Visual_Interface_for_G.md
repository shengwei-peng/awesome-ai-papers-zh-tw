#### 核心設計理念

Hybrid Computer Use (HCU, 混合電腦使用) 的提出基於一個關鍵觀察：現有的電腦使用代理 (Computer-Use Agent) 介面過度依賴截圖與滑鼠鍵盤操作，這種設計強加了**人類互動先驗 (Human-Interaction Prior)**，迫使模型反覆進行螢幕畫面解讀 (Screen Interpretation)，卻未能充分利用電腦系統本身提供的語意與程式化能力。HCU 的核心論點是：應當**暴露**這些底層能力，並讓模型**自主選擇與組合**它們。

#### 三通道統一架構

HCU 將電腦互動抽象為三個互補的通道 (Channel)：

1. **程式化通道 (Programmatic Channel)**：透過程式碼與命令列工具 (Command-Line Interface, CLI) 直接存取檔案、資料與軟體。例如，當需要批次處理資料時，與其反覆執行點擊拖曳操作，不如直接撰寫腳本完成。

2. **語意通道 (Semantic Channel)**：透過作業系統的無障礙功能 (Accessibility, AX) 取得 UI 控制項的結構化資訊，包含其身份、屬性與支援的操作。AX 原本為輔助科技設計，現已成為自動化領域的重要工具。

3. **視覺通道 (Visual Channel)**：透過圖形使用者介面 (Graphical User Interface, GUI) 進行截圖觀察與滑鼠鍵盤操作，提供視覺證據與控制能力。

這三個通道透過 **Model Context Protocol (MCP)** 整合，使代理能夠在統一介面下靈活調用。

#### AX 通道的關鍵設計

HCU 在語意通道的設計上有三項重要創新：

- **精簡觀察 (Compact Observation)**：AX 工具回傳的是結構化的精簡資訊，而非完整截圖，大幅減少模型需要處理的資料量。
- **批次執行 (Batch Execution)**：支援在單次呼叫中對多個目標執行動作，減少來回往返 (Round Trip) 次數。
- **AX 差異回報 (AX Diff)**：動作執行後，工具直接回報狀態變化，無需額外的觀察步驟即可確認執行結果。

此外，HCU 引入了**等待步驟 (Wait Step)** 機制，處理非同步操作（如檔案下載、應用程式啟動）所帶來的狀態延遲問題。

#### 跨通道動作守衛 (Action Guards)

由於三個通道作用於同一桌面，一個通道的動作可能使另一通道持有的證據失效（例如 AX 取得的控制項參考可能在 GUI 操作後改變）。HCU 設計了**跨通道動作守衛**，在每次輸入前重新檢查目標與版面配置是否與當前狀態一致，防止**過時狀態動作 (Stale-State Action)** 的發生。

#### HCU 技能 (HCU Skill)

HCU 附帶一個補充性的技能模組，用於引導代理：
- 何時該使用哪個通道
- 如何遵循執行與回饋契約
- 如何減少呼叫錯誤

實驗數據顯示，這個技能將 AX 與 GUI 呼叫因參數錯誤被拒的比例從 17.37% 降至 1.36%，效果顯著。

### 與現有研究的比較

#### 定位

HCU 並非從零開始，而是建立在多項先驅工作之上：

| 先驅工作 | 貢獻 | HCU 的改進 |
|----------|------|------------|
| **UFO2** [7] | 結合 UI Automation、GUI 與應用程式 API | HCU 進一步組織參考位址化的 AX 動作、呼叫中等待步驟與動作後回饋 |
| **Tactile** [8] | 暴露語意動作，搭配 OCR 與視覺回退 | HCU 提供更完整的統一介面與跨通道守衛 |
| **CUA Driver** [9] | 支援三通道，但偏好背景 AX 以保留使用者桌面 | HCU 將選擇權交給模型，實現真正的彈性組合 |
| **程式化+視覺混合工作** [5, 6] | 結合程式化與視覺互動 | HCU 加入語意通道，補齊 AX 維度 |

#### 關鍵差異化優勢

1. **模型主導的通道選擇**：相較於 CUA Driver 的固定偏好策略，HCU 讓模型根據任務特性動態決策。
2. **跨通道一致性保證**：動作守衛機制是 HCU 的獨特設計，解決了多通道並行時的狀態同步問題。
3. **HCU 技能模組**：透過引導而非硬編碼，提升代理對介面的理解與使用正確率。

#### 局限性

- **依賴 AX 支援**：語意通道的有效性取決於應用程式是否正確暴露無障礙資訊。某些老舊或客製化應用可能 AX 覆蓋不足。
- **模型能力差異**：雖然所有評測模型都從 HCU 中獲益，但提升幅度因模型而異，較弱的模型可能無法充分利用多通道的彈性。
- **跨平台複雜度**：雖然評測涵蓋 macOS (MacAgentBench) 與 Windows (Windows Agent Arena)，但不同作業系統的 AX API 差異可能增加實作複雜度。

**緩解**：嚴格執行 action guards；通道切換時主動 invalidate 其他通道的觀察快取。

**風險五：HCU skill 提示詞被模型忽略**
論文顯示加入 skill 後，AX/GUI 呼叫的 malformed 比例從 17.37% 降至 1.36%，但仍非零。
**緩解**：在 tool schema 中加入更嚴格的 enum 與 regex 驗證；對錯誤回傳設計明確的修正指引。

**風險六：評測基準的過擬合風險**
OSWorld 上的高效能未必能直接轉移到真實使用者的桌面環境。
**緩解**：在內部建立反映真實使用者工作流程的私有評測集；進行小規模真人試用。

### 與其他技術的整合建議

**與 MCP 生態系整合**
HCU 本身就是 MCP 伺服器，可直接接入任何支援 MCP 的 agent 框架（如 Claude Desktop、Cursor、自建 agent runtime）。建議將 HCU 的三個通道設計為可獨立掛載的 tool group，方便使用者依需求啟用。

**與既有 RPA 平台整合**
UiPath、Power Automate 等 RPA 平台可將 HCU 作為「AI 決策層」嵌入：傳統 RPA 處理結構化流程，HCU 處理需要視覺理解與彈性決策的例外。透過 MCP 或 REST API 橋接即可。

**與測試自動化框架整合**
Playwright、Selenium 主要處理網頁；HCU 可補齊桌面應用程式的覆蓋。建議將 HCU 的 AX 動作包裝為 pytest / Jest 的 fixture，方便既有測試套件呼叫。

**與無障礙輔助技術整合**
HCU 的語意通道本質上是無障礙 API 的延伸，可與 NVDA、VoiceOver、JAWS 等螢幕閱讀器共享同一份 AX 資訊。對輔助科技廠商而言，HCU 提供了一個標準化的 AI 代理接入點。

**與企業 IAM 與稽核系統整合**
HCU 的所有動作都應記錄至 audit log，包含通道類型、目標元素、執行結果。建議整合 SIEM 系統（如 Splunk、Sentinel）以符合企業合規需求。

**與多模態模型管線整合**
HCU 的視覺通道可與 GPT-4V、Claude Vision 等多模態模型解耦：HCU 負責動作執行，視覺模型負責畫面理解。透過非同步訊息佇列（如 Redis Streams）串接，可降低延遲。

### 給不同背景讀者的閱讀建議

**給初學者**
建議先閱讀第 1 節（Introduction）與圖 1，理解「為什麼電腦使用代理不該只靠截圖與滑鼠」這個核心論點。接著跳到第 4 節的實驗結果（OSWorld 2.0 圖表），直觀感受 HCU 在效能與成本上的改善。不需要深入 AX API 細節，先建立「三通道互補」的概念即可。

**給 AI 工程師**
重點閱讀第 2 節（Method）與第 3 節（Implementation），特別是 AX 工具的 compact observation、batch execution、AX diff 三個設計選擇。建議直接 clone 官方 GitHub repo，在本地 MCP 環境中跑通範例，並嘗試將 HCU 接入自己的 agent 框架。論文第 4 節的 component ablation 與 tool-call 分析對優化 prompt 與 tool schema 很有參考價值。

**給研究者**
重點關注第 4 節的 trajectory 分析——不同模型在三個通道上的使用偏好差異，以及 HCU 為何能同時改善效能與效率。論文提出的「unified interface + model-directed channel selection」框架，可作為後續研究（例如 learned channel router、per-task channel policy）的基礎。建議進一步閱讀附錄 A 的 WeaveBench、MacAgentBench、Windows Agent Arena 結果，評估泛化性。

**給產品經理**
重點閱讀摘要、第 1 節、以及第 4 節的效率數據（成本下降 20–50%、步數減少 17%）。這些數字直接對應到企業部署 AI 代理的 ROI 計算。建議關注「與其他技術的整合建議」一節，思考 HCU 如何嵌入既有產品線（例如 RPA、輔助科技、客服自動化）。論文的 Pareto frontier 圖是向高階主管溝通價值的最佳素材。
