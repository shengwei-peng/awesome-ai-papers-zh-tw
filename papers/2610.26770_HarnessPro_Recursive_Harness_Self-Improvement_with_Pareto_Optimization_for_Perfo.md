# HarnessPro：以帕累托最佳化進行遞迴代理程式框架自我改進，實現效能-成本權衡

## ⚡ TL;DR

現有遞迴自我改進方法雖提升代理效能，卻伴隨更高的執行成本與延遲。
HarnessPro 提出無標籤多代理框架，透過軌跡分析、規劃與編輯遞迴演化框架，並以帕累托最佳化產出精簡、平衡、效能三種版本。
在三項基準測試中，效能模式較 RHO 平均通過率提升 2.0 百分點、成本降低 26.1%。

## 摘要翻譯

代理程式框架開發在建構能力優異的 AI 代理中扮演關鍵角色。近期方法透過遞迴自我改進 (RSI) 來改善框架，但其效能提升常伴隨較高的執行成本。我們提出 HarnessPro，這是一種無標籤方法，用於演化框架以提升任務效能並降低執行成本。在此設定中，候選框架使用大型語言模型 (LLM) 生成的測試進行評估，無需存取真實解答或官方測試。專責代理診斷執行軌跡，根據不同的效能-成本優先順序規劃更新，並將其實作為候選框架。HarnessPro 並非僅回傳單一框架；其採用標準化加權平方距離選擇法，針對不同的部署預算提供成本導向（精簡模式）、平衡（平衡模式）與效能導向（效能模式）的框架。選定的框架進入下一輪迭代，由執行回饋引導進一步更新。我們的實驗涵蓋 Terminal-Bench 2、SWE-Bench Pro 與 ProgramBench，使用 GPT-5.5 搭配 Codex，以及 GLM-5.2 搭配 Claude Code。在使用 GPT-5.5 搭配 Codex 的這些基準測試中，HarnessPro 的效能模式相較於 RHO，平均通過率提升 2.0 百分點，每任務平均成本降低 26.1%。此優勢在使用 GLM-5.2 搭配 Claude Code 時亦同樣成立。程式碼公開於 https://github.com/pzs19/HarnessPro

### 核心貢獻（3～5點）
- 提出 HarnessPro，一種無標籤的遞迴自我改進方法，透過演化代理程式框架同時提升任務效能並降低執行成本，無需依賴真實解答或官方測試。
- 設計專責代理分工機制，由軌跡分析器診斷執行軌跡、規劃器依不同效能-成本優先順序擬定更新策略、編輯器將更新實作為候選框架。
- 採用標準化加權平方距離選擇法，從帕累托前緣中挑選框架，一次輸出對應不同部署預算的三種模式：成本導向（精簡模式）、平衡（平衡模式）、效能導向（效能模式）。
- 建立遞迴迭代流程，選定的框架進入下一輪迭代輪次，由執行回饋持續引導框架更新。
- 在 Terminal-Bench 2、SWE-Bench Pro 與 ProgramBench 三大基準測試上驗證，於 GPT-5.5 搭配 Codex 與 GLM-5.2 搭配 Claude Code 兩種骨幹模型組合下，效能模式相較於 RHO 平均通過率提升 2.0 百分點、每任務平均成本降低 26.1%。

### 適合對象
從事大型語言模型代理程式框架設計與最佳化的研究人員與工程師；關注 AI 代理效能與成本權衡、自動化軟體工程、程式碼生成基準測試的學術界與產業界人士；以及對遞迴自我改進、帕累托最佳化方法在 LLM 代理系統中應用感興趣的讀者。

## 深度分析

#### 方法論解析

HarnessPro 的方法論核心在於將「代理程式框架（agent harness）」視為可遞迴演化的軟體工件，並透過多代理協作將執行回饋轉化為結構化的框架更新。整體流程可拆解為三個關鍵設計層次：

**1. 診斷—規劃—編輯的多代理管線（Diagnosis–Planning–Editing Pipeline）**

HarnessPro 並非以單一 LLM 一次性產生框架修改，而是將更新流程拆解為三個專責代理：

- **軌跡分析器（Trajectory Analyzer）**：對同一任務進行多次展開執行（rollouts），從中萃取出兩類訊號——失敗模式（failure patterns）與可避免的開銷（avoidable overhead）。這種「重複執行取共識」的設計降低了單次軌跡的隨機性，使診斷更具統計意義。
- **規劃器（Planner）**：接收診斷結果，並依據不同的效能-成本權重產生對應的改進計畫。這裡的關鍵創新在於「多目標規劃」——同一組診斷可衍生出偏重成本或偏重效能的不同更新方向，而非僅追求單一最優解。
- **編輯器（Editor）**：將規劃結果落實為可執行的候選框架（candidate harness），涵蓋提示詞、技能文件、工具呼叫、執行期掛鉤（runtime hooks）與驗證規則等元件。

**2. 無標籤的測試合成機制（Label-Free Test Synthesis）**

傳統遞迴自我改進（RSI）方法常依賴真實解答（ground-truth solutions）或官方測試（official tests）作為評估基準，但這在實際部署中往往不可取得。HarnessPro 引入測試合成代理（test-synthesis agent），在演化開始前先生成一組固定的測試案例，並在整個迭代過程中重複使用。這種設計的優勢在於：

- 避免測試集洩漏（test-set leakage），因為官方測試僅在最終評估時使用。
- 提供穩定的相對比較基準，使候選框架間的排序具有一致性。
- 不需依賴 LLM 裁判（LLM-as-judge）進行主觀評分，降低評估偏差。

**3. 帕累托選擇與三層級輸出（Pareto Selection with Tiered Output）**

在每個迭代輪次（epoch）結束後，HarnessPro 並非僅保留單一最佳框架，而是採用標準化加權平方距離選擇法（normalized weighted squared-distance selection, Marler & Arora, 2004）從帕累托前緣（Pareto frontier）中挑選出三個代表性框架：

- **精簡模式（lite）**：成本導向，適用於預算受限的部署。
- **平衡模式（medium）**：在效能與成本間取得折衷。
- **效能模式（heavy）**：效能導向，適用於對通過率要求嚴格的場景。

這種設計的實務價值在於：同一套演化流程可同時服務不同部署預算（deployment budgets）的需求，無需為每種預算單獨訓練。

**4. 演化的具體機制（Evolved Mechanisms）**

根據論文分析，演化後的框架並非單純壓縮上下文或加大推理力度，而是發展出以下動態行為：

- **依任務描述動態配置推理力度與工具預算**（dynamic allocation of reasoning effort and tool budgets）。
- **執行期掛鉤根據預算將執行從探索導向收斂**（steering execution from exploration toward convergence）。
- **採用類似 RTK 的工具輸出壓縮**（tool-output compression）。
- **精簡提示詞但保留必要的最終驗證步驟**。

這些機制的共同特徵是「結構性優化」而非「暴力壓縮」，這也是 HarnessPro 能同時提升效能並降低成本的核心原因。

#### 實驗數據解讀

**1. 基準測試與模型配置**

實驗涵蓋三個互補的程式碼代理基準：

- **Terminal-Bench 2**：終端機操作與系統管理任務。
- **SWE-Bench Pro**：軟體工程修復任務，考驗長程除錯能力。
- **ProgramBench**：程式合成任務，評估演算法實作能力。

骨幹模型（backbone models）採用兩組配置：GPT-5.5 搭配 Codex，以及 GLM-5.2 搭配 Claude Code。這種雙模型設計有助於驗證方法的模型無關性（model-agnosticism）。

**2. 主要量化結果**

根據摘要揭露的數據：

- 在三個基準上，使用 GPT-5.5 與 Codex 時，**效能模式平均通過率提升 2.0 百分點（percentage points），每任務平均成本降低 26.1%**，相較於基準方法 RHO（Pan et al., 2026a）。
- 在 Terminal-Bench 2 上，效能模式通過率提升 **4.5 百分點**，成本降低 **33.9%**。
- **平衡模式**在效能上與 RHO 相當，但執行成本顯著降低，適合成本敏感的部署。

**3. 結果意涵解讀**

這組數據揭示了幾個重要訊息：

- **效能與成本可同時改善**：傳統觀點認為提升通過率必然伴隨成本增加（因需更多探索與驗證），但 HarnessPro 透過結構性優化打破了此權衡。
- **基準差異性**：Terminal-Bench 2 的增益最大（+4.5 pp），可能反映該基準中可避免的開銷比例較高；而 SWE-Bench Pro 與 ProgramBench 的增益幅度需參照全文表格才能完整評估。
- **模型泛化性**：在 GLM-5.2 與 Claude Code 配置下仍維持優勢，顯示方法不依賴特定模型的特性。

**4. 評估指標的完整性**

論文定義了三項指標：通過率（pass rate）、執行成本（execution cost）、執行延遲（latency）。任務被劃分為訓練、驗證、測試三集，訓練集用於框架更新，驗證集用於候選選擇，測試集僅在最終評估時使用——這種劃分有效防止過擬合（overfitting）並確保結果的泛化可信度。

#### 與現有研究的比較

**1. 在遞迴自我改進譜系中的定位**

HarnessPro 與近期 RSI 方法的差異可從表 1 的比較中清楚看出：

| 方法 | 目標 | 範圍 | 回饋類型 | 迭代方式 | 輸出 |
|------|------|------|----------|----------|------|
| AFlow | 通過率 | 工作流程 | 真實標籤 | 遞迴 | 單一 |
| SkillMOO | 通過率+成本 | 技能 | 真實標籤 | 遞迴 | 帕累托集 |
| RHO | 通過率 | 技能+工具 | 無標籤 | 單輪 | 單一 |
| AHE | 通過率 | 框架 | 真實標籤 | 遞迴 | 單一 |
| **HarnessPro** | **通過率+成本** | **框架** | **無標籤** | **遞迴** | **帕累托集** |

HarnessPro 是唯一同時滿足「多目標（pass + cost）」、「全框架範圍」、「無標籤」、「遞迴」、「帕累托集輸出」五項特性的方法，這使其在實用性上具有明顯優勢。

**2. 相較於 RHO 的具體改進**

RHO（Pan et al., 2026a）是與 HarnessPro 最接近的基準方法。兩者的關鍵差異在於：

- **目標函數**：RHO 僅優化通過率，HarnessPro 同時考量成本。
- **輸出形式**：RHO 輸出單一框架，HarnessPro 輸出三層級框架。
- **評估機制**：RHO 使用 LLM 比較軌跡，HarnessPro 使用固定測試集。

這些差異使 HarnessPro 在保持無標籤特性的同時，提供了更細緻的部署彈性。

**3. 相較於元件優化方法的互補性**

SkillOpt、SkillMOO、FRAMES 等方法聚焦於技能文件（skill documents）的優化，而 HarnessPro 演化整個框架（包括指令、技能、工具、掛鉤、驗證規則）。這是一種「垂直整合」vs「水平分工」的差異——HarnessPro 的整合性更強，但也意味著搜尋空間更大。

**4. 與預算分配方法的關係**

BATS、COMPAS 等方法在推論時（inference time）動態分配預算，而 HarnessPro 在訓練階段（演化階段）學習預算分配策略。兩者屬於互補而非競爭的關係，未來可考慮結合使用。

**5. 潛在限制**

- **搜尋空間爆炸**：全框架演化的搜尋空間遠大於僅優化技能，雖然遞迴機制緩解了此問題，但仍可能面臨局部最優（local optima）風險。
- **測試合成的可靠性**：LLM 生成的測試品質直接影響候選評估的準確性，若測試本身有偏誤，可能誤導演化方向。
- **基準偏誤**：實驗集中在程式碼任務，對其他領域（如網頁導航、資料分析）的泛化性尚待驗證。

#### 可重現性評估

**1. 程式碼開源**

論文提供了 GitHub 連結（https://github.com/pzs19/HarnessPro），這是可重現性的基本前提。建議在引用時確認以下細節：

- 程式碼是否包含完整的演化管線（軌跡分析器、規劃器、編輯器、測試合成代理）。
- 是否提供預訓練的框架工件或僅提供訓練腳本。
- 是否包含評估腳本與基準測試的整合程式碼。

**2. 資料集可用性**

三個基準測試（Terminal-Bench 2、SWE-Bench Pro、ProgramBench）均為公開資源，理論上可直接取得。但需注意：

- Terminal-Bench 2 與 SWE-Bench Pro 的任務劃分（訓練/驗證/測試）是否與論文一致。
- 官方測試的存取權限（部分基準可能需要申請）。

**3. 模型權重**

GPT-5.5 與 GLM-5.2 均為閉源模型，無法本地重現。但 Codex 與 Claude Code 作為程式碼代理框架，其行為應可透過 API 重現。建議重現時：

- 記錄 API 版本與日期戳記（model snapshot），因模型行為可能隨時間漂移。
- 控制溫度（temperature）與其他取樣參數的一致性。
- 多次執行取平均以降低隨機性。

**4. 計算資源需求**

遞迴演化涉及多次展開執行與 LLM 呼叫，計算成本不低。論文中未明確揭露總花費，但從「每任務平均成本降低 26.1%」可推估單次實驗的規模。重現時需準備相應的 API 預算。

**5. 可重現性風險**

- **測試合成的隨機性**：LLM 生成的測試可能因隨機種子不同而異，影響候選評估的一致性。
- **演化的路徑依賴**：遞迴過程中每一步的隨機性可能導致最終框架不同，建議重現時固定所有隨機種子。
- **基準評分標準**：官方測試的評分方式（如容錯率、執行時間限制）需嚴格對齊。

#### 未來研究方向

**1. 多目標權重的自動化學習**

目前 HarnessPro 的三層級（lite/medium/heavy）由人工預設權重產生，未來可探索：

- 根據使用者偏好或歷史部署資料自動學習權重分布。
- 引入更多維度（如延遲、能源消耗、安全性）擴展帕累托前緣。
- 動態權重調整，根據任務特性即時決定成本-效能權衡。

**2. 測試合成品質的提升**

測試合成的可靠性是方法的潛在瓶頸，可考慮：

- 結合形式化驗證（formal verification）與 LLM 生成，提升測試的覆蓋率與正確性。
- 引入對抗性測試（adversarial testing）以更全面地診斷失敗模式。
- 研究測試多樣性與候選評估穩定性間的關係。

**3. 跨領域泛化**

目前實驗集中在程式碼任務，可延伸至：

- **網頁導航**（如 WebArena）：考驗視覺理解與多步驟操作。
- **資料分析**（如 DA-Bench）：考驗統計推理與工具使用。
- **科學研究**（如 ScienceQA）：考驗領域知識整合。

跨領域實驗將驗證方法是否捕捉到通用的框架優化原則。

**4. 與推論時預算分配的整合**

HarnessPro 在訓練階段學習預算分配策略，可與 BATS、COMPAS 等推論時方法結合：

- 訓練階段：演化出具有預算感知能力的框架。
- 推論階段：根據任務難度即時調整預算分配。
- 形成「靜態演化 + 動態調整」的雙層架構。

**5. 框架元件的可解釋性分析**

目前演化後的框架機制（動態推理配置、執行期掛鉤等）僅有定性描述，未來可：

- 進行消融研究（ablation study）量化各元件的貢獻。
- 使用可解釋 AI 技術分析框架決策的因果鏈。
- 建立框架設計模式（design patterns）的分類學。

**6. 安全與對齊考量**

遞迴自我改進涉及自主修改執行環境，需關注：

- 框架更新是否可能引入安全漏洞或對齊偏差（alignment drift）。
- 如何在演化過程中加入安全約束（safety constraints）。
- 遞迴改進的收斂性與穩定性分析。

**7. 與人類專家知識的融合**

目前框架更新完全由 LLM 驅動，未來可探索：

- 將人類專家的領域知識注入演化過程。
- 建立人機協作的框架設計介面。
- 利用人類回饋強化學習（RLHF）指導演化方向。

**8. 理論分析**

HarnessPro 的收斂性、樣本複雜度、泛化界限等理論性質尚待研究：

- 在何種條件下遞迴演化能保證帕累托前緣的改善？
- 訓練集規模與最終效能間的縮放法則（scaling law）為何？
- 框架複雜度與效能增益間是否存在最優平衡點？

## 論文問答

**Q1：HarnessPro 主要解決什麼核心問題？為何這個問題在當前 AI 代理領域特別重要？**

A：HarnessPro 主要解決代理程式框架（agent harness）在遞迴自我改進過程中，效能提升往往伴隨執行成本增加的問題。代理框架作為管理大型語言模型與環境互動的軟體基礎設施，直接影響任務成功率與資源消耗。這個問題之所以重要，是因為在實際部署場景中，token 消耗量與延遲同樣是關鍵指標，純粹追求通過率的提升會讓部署成本過高、響應過慢，難以在成本敏感的商業應用中落地。HarnessPro 透過同時最佳化效能與成本，將帕累托前緣往前推進，使框架改進能真正服務於真實世界的部署需求。

**Q2：現有的遞迴自我改進方法（如 RHO、AFlow 等）有哪些不足之處？**

A：現有方法如 RHO 雖然採用無標籤方式引導框架演化，但僅追求單一通過率指標，輸出單一框架，無法適應不同部署預算的需求。AFlow 仰賴真實解答作為回饋訊號，在缺乏標籤的場景中難以應用；而 AHE 等方法雖然遞迴改進整個框架，但仍以通過率為唯一目標。SkillMOO 雖考慮成本，但僅限於技能層級的改進，無法觸及整個框架結構。這些方法共同的不足在於：缺乏對成本與延遲的系統性考量、輸出單一框架無法彈性部署，以及評估候選框架時過度依賴標籤或 LLM 判斷。

**Q3：為什麼效能-成本權衡在實際部署中至關重要？**

A：在實際部署中，AI 代理的成本不僅包含 API 呼叫費用，還涉及使用者等待的延遲時間與運算資源的佔用。即使一個框架能將通過率提升幾個百分點，若執行成本翻倍，對於大規模商用部署而言經濟上不可行。不同應用場景對成本的敏感度差異極大——即時客服需要低延遲，批次處理則可接受較長執行時間。HarnessPro 透過提供精簡、平衡、效能三種模式，讓同一套框架改進成果能服務於多元部署預算，這正是回應業界對彈性化 AI 代理解決方案的迫切需求。

**Q4：HarnessPro 的核心架構為何？使用了哪些專責代理？**

A：HarnessPro 的核心架構由四個專責代理組成：軌跡分析器（Trajectory Analyzer）檢視多次展開執行的軌跡以識別失敗模式與可避免的開銷；規劃器（Planner）根據不同的效能-成本優先順序將診斷結果轉化為框架改進計畫；編輯器（Editor）將計畫實作為可執行的候選框架；測試合成代理（Test-Synthesis Agent）則在無法取得真實解答或官方測試的情況下，提供固定的測試集用於評估候選框架。這種分工設計讓診斷、規劃、實作、評估四個環節解耦，每個代理能專注於自身職責，從而提升整體框架演化的品質與效率。

**Q5：標準化加權平方距離選擇法如何運作？為何要設計三種模式？**

A：標準化加權平方距離選擇法（Marler & Arora, 2004）透過計算候選框架在標準化效能與成本空間中的加權距離，挑選出能代表不同權衡位置的代表性框架。具體而言，該方法會在帕累托前緣上選取三個點：成本導向的精簡模式（lite）優先考慮低執行成本、平衡模式（medium）在兩者間取得折衷、效能導向的效能模式（heavy）則最大化通過率。設計三種模式的目的是讓部署者能根據預算彈性選擇——同一個框架演化流程的產出，能同時服務於成本敏感的邊緣部署與效能優先的關鍵任務，大幅提升框架改進成果的可重用性與商業價值。

**Q6：HarnessPro 如何在沒有真實解答或官方測試的情況下評估候選框架？**

A：HarnessPro 採用由測試合成代理生成的固定測試集來評估候選框架，這些測試不依賴真實解答，而是基於任務描述與執行軌跡自動產生。候選框架在這些固定測試上的表現會與初始框架進行比較，若新框架在效能或成本上被帕累托支配（即兩者皆更差），則會被淘汰。這種設計的優勢在於：避免了直接使用 LLM 判斷所帶來的不穩定性與偏誤，同時也防止了測試集洩漏問題——訓練、驗證、測試集被明確劃分，候選框架的選擇僅依據驗證集表現，測試集則保留至演化完成後才用於最終評估。

**Q7：實驗採用了哪些基準測試？為何選擇這些特定的基準？**

A：實驗選用了三個互補的基準測試：Terminal-Bench 2 涵蓋終端機操作與系統管理任務、SWE-Bench Pro 聚焦於軟體工程修復任務、ProgramBench 則涉及程式設計問題。這三個基準分別測試代理在不同領域的能力——從系統層級操作到程式碼修復再到演算法實作，能全面評估框架改進的泛化性。同時，實驗使用 GPT-5.5 搭配 Codex 與 GLM-5.2 搭配 Claude Code 兩種骨幹模型組合，以驗證方法對不同模型架構的適應性，避免結果僅反映特定模型的特性。

**Q8：相較於 RHO 基線，HarnessPro 的關鍵實驗結果為何？**

A：在 GPT-5.5 搭配 Codex 的設定下，HarnessPro 的效能模式在三個基準上平均通過率提升 2.0 百分點，同時每任務平均成本降低 26.1%。最具代表性的結果是在 Terminal-Bench 2 上，效能模式通過率超越 RHO 達 4.5 百分點，而平均成本降低 33.9%。平衡模式則提供另一個關鍵優勢：在效能與 RHO 相當的情況下，大幅降低執行成本，適合成本敏感的部署。這些結果在 GLM-5.2 搭配 Claude Code 的設定下同樣成立，證明了方法的穩健性與跨模型可遷移性。

**Q9：演化後的框架採取了哪些具體機制來提升效能並降低成本？**

A：分析顯示演化後的框架並非簡單地壓縮上下文或增加推理力度，而是發展出更精巧的策略。首先，框架會根據任務描述動態配置推理力度與工具預算，避免在簡單任務上過度探索；其次，執行期掛鉤（runtime hooks）會根據分配的預算將執行從探索導向收斂；再者，框架採用類似 RTK 的工具輸出壓縮技術，並精簡指令以減少冗餘的提示內容，同時保留必要的脈絡與最終驗證步驟。這些機制的組合讓框架能在削減可避免開銷的同時，保留任務成功所需的推理與驗證能力。

**Q10：哪些實際部署場景最能受益於 HarnessPro？**

A：成本敏感的大規模商用部署最能受益，例如即時客服代理、批次文件處理、程式碼審查助手等需要控制單次互動成本的場景。對於邊緣運算或資源受限環境，精簡模式能在維持可接受通過率的前提下大幅降低運算需求。另一方面，對於研發輔助、複雜除錯等效能優先的場景，效能模式則提供了超越基線的可靠性。多模式設計讓單一框架改進流程能服務於企業內部不同部門、不同專案的多元需求，無需為每個場景單獨訓練專用框架。

**Q11：HarnessPro 對 AI 代理產品化有哪些重要啟示？**

A：HarnessPro 揭示了 AI 代理產品化必須從「單一最佳模型」思維轉向「彈性化框架組合」思維。產品團隊可將同一套經過遞迴改進的框架，根據使用者訂閱等級或任務重要性分配不同模式——免費使用者使用精簡模式、付費使用者使用平衡模式、企業客戶使用效能模式。此外，無標籤評估機制降低了框架改進對標註資料的依賴，使產品能在缺乏真實解答的新興領域快速迭代。這種設計哲學讓框架投資能產生更高的商業回報。

**Q12：HarnessPro 對整個 AI 代理領域的影響為何？**

A：HarnessPro 推動了領域從「追求單一指標最佳化」轉向「多目標帕累托最佳化」的典範轉移，強調代理框架改進必須同時考量效能、成本、延遲等多維度指標。其無標籤評估方法降低了對標註資料的依賴，使遞迴自我改進能應用於更廣泛的真實世界任務。多模式輸出設計則為框架即服務（Harness-as-a-Service）的商業模式奠定基礎，可能催生新型的框架市集與部署平台。整體而言，HarnessPro 將遞迴自我改進從學術概念推向可落地的工程實踐。

**Q13：HarnessPro 有哪些已聲明的限制？**

A：根據論文內容，HarnessPro 的限制包括：測試合成代理生成的測試品質會直接影響候選框架的評估準確性，若測試無法有效區分框架優劣，演化過程可能偏離最優方向。此外，框架改進的效果依賴於執行軌跡的品質與多樣性，在某些任務上若多次展開執行的軌跡高度相似，軌跡分析器可能難以識別有意義的改進空間。標準化加權平方距離選擇法假設效能與成本可被標準化至可比空間，但對於極度異質的任務類型，這種標準化可能不夠精確。

**Q14：HarnessPro 可能在哪類任務或場景中表現不佳？**

A：對於需要極長推理鏈或高度創造性解決方案的任務，HarnessPro 的成本削減機制可能過度壓縮必要的探索空間，導致通過率下降。在高度專業化的領域（如醫療診斷、法律分析），若測試合成代理無法產生足夠高品質的測試案例，候選框架的評估將失去可靠性。此外，對於需要即時反應的低延遲場景，雖然精簡模式能降低成本，但若任務本身就需要大量工具呼叫，壓縮空間可能有限。涉及多模態輸入或需要外部真實世界互動的任務，則可能超出當前框架改進的範疇。

**Q15：基於 HarnessPro 的成果，未來有哪些值得探索的研究方向？**

A：未來可探索的方向包括：將帕累托最佳化擴展至更多維度，如能源消耗、碳排放、模型公平性等，使框架改進能服務於永續 AI 目標；研究如何讓測試合成代理產生更強健、更多樣的測試集，以提升候選框架評估的可靠性；探索跨任務、跨領域的框架遷移學習，使在一個領域演化的框架能快速適應新領域。此外，將人類回饋整合進遞迴改進循環、發展框架改進的可解釋性工具，以及探討多代理協作場景下的分散式框架演化，都是值得深入研究的方向。

## 實務應用指南

### 適用場景

1. **分級訂閱制的程式碼助理服務**：SaaS 廠商可依客戶付費等級自動切換精簡模式、平衡模式、效能模式三種框架，在不重寫底層模型的情況下提供差異化服務體驗。

2. **企業內部 CI/CD 自動化代理**：在批次處理大量程式碼審查、測試生成、依賴更新等任務時，依任務複雜度動態配置推理力度與工具預算，避免簡單任務消耗過多 token。

3. **多租戶程式生成平台**：當平台同時服務個人開發者（成本敏感）與大型企業（效能敏感）時，可依部署預算選用對應層級的框架，無需為不同客群維護多套獨立系統。

4. **程式碼遷移與重構專案**：面對數千個檔案的 legacy 系統現代化任務，可先用精簡模式快速產出初版，再用效能模式處理關鍵模組，兼顧時程與品質。

5. **邊緣部署或成本受限的內部工具**：在無法負擔高延遲或高 API 成本的環境中，精簡模式可在保留必要推理與驗證的前提下，將每任務平均成本降低約 26%。

### 實作前置條件

**資料準備**
- 需將任務集切分為訓練集、驗證集、測試集三部分，且測試集僅供最終評估使用，避免資料洩漏。
- 需蒐集初始框架在訓練任務上的執行軌跡，包含工具呼叫、環境回饋、最終產出。
- 需準備或建立任務描述的標準化格式，便於軌跡分析器與規劃器處理。

**運算資源**
- 需具備 GPT-5.5 或 GLM-5.2 等骨幹模型的 API 存取權限，並搭配 Codex 或 Claude Code 等編碼代理。
- 遞迴迭代本身會消耗大量 token，需預留約初始實驗成本 3–5 倍的預算作為框架演化的開銷。
- 建議準備分散式任務排程系統，以平行處理多個候選框架的評估。

**技能門檻**
- 熟悉代理執行環境的組成元件（提示詞、工具、技能、執行期掛鉤、驗證策略）。
- 具備多代理編排經驗，能設計軌跡分析器、規劃器、編輯器、測試合成代理之間的協作流程。
- 理解帕累托最佳化與標準化加權平方距離選擇法的數學原理，以便調整不同部署預算下的權重設定。

### 實作步驟建議

1. **建立基準框架**：先部署一個未經優化的初始框架，在訓練集上收集執行軌跡與成本資料，作為後續比較的基準線。

2. **實作軌跡分析器**：讓專責代理檢視多次展開執行的結果，識別失敗模式與可避免的開銷（例如冗餘工具呼叫、過度探索）。

3. **設計規劃器與優先權機制**：為規劃器定義成本導向、平衡、效能導向三種優先權，使其根據診斷結果產生對應的框架改進計畫。

4. **實作編輯器**：將改進計畫轉化為可執行的框架候選版本，涵蓋提示詞、技能文件、工具配置、執行期掛鉤與驗證規則的修改。

5. **建立測試合成代理**：在無法取得真實解答或官方測試的情況下，由 LLM 生成固定測試集，用於評估候選框架的表現。

6. **執行候選評估與篩選**：在驗證集上評估所有候選框架，淘汰表現不如初始框架或被帕累托支配的版本。

7. **套用標準化加權平方距離選擇法**：從剩餘候選中選出代表精簡、平衡、效能三種模式的框架，進入下一輪迭代。

8. **執行遞迴迭代**：以選出的框架為起點，重複步驟 2–7，直到效能-成本帕累托前緣不再顯著改善。

9. **於測試集做最終評估**：迭代結束後，僅在測試集上評估三種模式的框架，並與 RHO 等基準方法比較通過率與成本。

10. **部署分級框架**：依不同客戶或場景的部署預算，將對應模式的框架接入生產環境。

### 潛在風險與注意事項

- **測試集洩漏風險**：若訓練、驗證、測試集的切分不夠嚴謹，框架演化可能過擬合特定任務類型。緩解方式：嚴格隔離測試集，僅在最終評估時使用。

- **LLM 生成測試的可靠性**：測試合成代理產出的測試可能無法涵蓋所有邊界情況，導致候選框架評估失準。緩解方式：結合多輪測試生成與人工抽樣審查，並監控測試通過率與官方測試的一致性。

- **遞迴迭代成本失控**：每輪迭代都會消耗大量 token，若未設定迭代上限或成本門檻，可能導致總成本遠超預期。緩解方式：設定每輪最大迭代次數與單次迭代成本上限，並監控帕累托前緣的改善幅度。

- **模式選擇的營運複雜度**：維護三種模式的框架會增加部署與監控的複雜度。緩解方式：建立自動化的模式切換機制，並在監控儀表板上統一呈現三種模式的效能與成本指標。

- **框架過度特化**：演化後的框架可能在訓練任務上表現優異，但對新型任務的泛化能力下降。緩解方式：保留初始框架作為 fallback，並定期以新任務重新評估演化後的框架。

- **執行期掛鉤的副作用**：動態配置推理力度與工具預算的執行期掛鉤可能引入非預期的執行路徑。緩解方式：在沙盒環境中充分測試掛鉤邏輯，並設置安全閾值防止無限迴圈或資源耗盡。

### 與其他技術的整合建議

- **與現有 CI/CD 系統整合**：將三種模式的框架封裝為不同的 CI/CD 階段（例如 PR 階段用精簡模式、合併前用平衡模式、發版前用效能模式），依任務重要性自動切換。

- **與監控與可觀測性平台整合**：將每任務平均成本、通過率、延遲等指標匯入 Prometheus 或 Grafana，建立帕累托前緣的即時儀表板，便於營運團隊追蹤框架演化的長期趨勢。

- **與成本管理系統整合**：將框架執行的 token 消耗與企業內部的雲端成本核算系統對接，實現按部門、按專案的程式生成成本歸屬。

- **與模型服務基礎設施整合**：在多模型路由層（例如 LiteLLM、OpenRouter）中加入框架模式作為路由維度，使不同部署預算的請求自動導向對應模式的框架。

- **與技能與記憶系統整合**：將演化後框架中的技能文件與動態 Cheatsheet、Reasoning-Bank 等記憶系統對接，使跨任務的可重用策略得以累積。

- **與預算感知策略整合**：將 BATS、COMPAS 等預算感知或難度感知的模型選擇機制嵌入規劃器，使框架演化能同時考慮模型選擇與框架配置的聯合最佳化。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與引言，理解「代理執行環境」與「遞迴自我改進」的基本概念，再跳過數學細節，直接看實驗結果中三種模式（精簡、平衡、效能）的通過率與成本差異，建立對效能-成本權衡的直覺。

**給 AI 工程師**：重點閱讀問題設定章節中對代理執行環境的元件拆解（提示詞、工具、技能、執行期掛鉤、驗證策略），以及方法章節中軌跡分析器、規劃器、編輯器、測試合成代理的協作流程，並參考 Table 1 與 RHO 等基準方法的差異，思考如何將此架構落地到現有的代理編排系統中。

**給研究者**：建議仔細研讀標準化加權平方距離選擇法的數學定義、帕累托支配的篩選條件，以及遞迴迭代的收斂條件，並關注實驗設計中訓練/驗證/測試集的切分方式與無標籤評估的可信度，這些都是後續可延伸的研究方向。

**給產品經理**：聚焦於三種模式對應的部署預算情境、每任務平均成本降低約 26% 的實務意義，以及分級訂閱或內部成本分攤的商業模式設計，並思考如何在不增加底層模型成本的情況下，透過框架演化提供差異化的產品體驗。
