## ⚡ TL;DR

現有終端機基準測試多為專家設計，偏離真實工作流程且難以擴充。
本文提出 TerminalWorld，自動將真實終端機錄製逆向工程為可執行的高保真驗證任務。
實驗顯示前沿模型通過率僅62.5%，且與現有基準測試僅呈弱相關。

## 摘要翻譯

我們提出 TerminalWorld，一個可擴充資料引擎（Scalable Data Engine），可自動從真實環境（In-the-Wild）的終端機錄製內容（Terminal Recording）中，透過逆向工程（Reverse-Engineer）產生高保真（High-Fidelity）的評估任務（Evaluation Task）。該引擎處理了 80,870 份終端機錄製內容，產生一個包含 1,530 項經驗證任務（Validated Task）的完整基準測試（Benchmark），涵蓋 18 個真實世界類別（Real-World Category），從簡短的日常操作到超過 50 個步驟的工作流程

## 深度分析

#### 方法論解析

TerminalWorld（本文提出之基準測試平台）的核心方法論建立在「Naturally Occurring Terminal Operation（自然發生的終端機操作）若能被忠實記錄，即可透過 Reverse-Engineer（逆向工程）轉化為 High-Fidelity（高保真）Evaluation Task（評估任務）」之假設上。作者選用 Asciinema Platform（Asciinema 平台）作為資料來源，該平台收錄開發者 Self-Curated（自行整理）且經 Human-Vetted（人工審核）的 Terminal Session Recording（終端機工作階段錄製），每段錄製均包含 Structured Transcript（結構化文字紀錄），詳實記錄 Command（指令）與 System Response（系統回應）。以此為基礎，TerminalWorld 的 Data Engine（資料引擎）將 In-the-Wild（真實環境）的 Terminal Recording（終端機錄製內容）轉化為可執行的評估任務，並針對三大實務挑戰提出系統性解方：

第一，Recording Transcript（錄製文字紀錄）充斥 Noisy（雜訊），包含 Typo（錯字）、Retry（重試）、Verbose System Output（冗長系統輸出），且缺乏 Developer's Goal（開發者目標）的 Explicit Statement（明確陳述）。為此，引擎利用 Large Language Model (LLM)（大型語言模型）（例如 Claude Sonnet 4.6）進行 Distillation（提煉），將原始紀錄轉化為兩項產物：Outcome-Oriented Instruction（結果導向指令）以捕捉 Underlying Intent（潛在意圖），以及 Clean Command Script（乾淨指令腳本）作為 Reference Solution（參考解答）。

第二，Terminal Recording（終端機錄製內容）未捕捉底層執行環境。作者部署 Agent（智慧體）（如 Claude Code）進行環境的 Reverse-Engineer（逆向工程）：該 Agent（智慧體）推斷實際需求並排除幻覺化依賴，實際建構 Docker 映像檔、啟動容器，並重播 Reference Solution（參考解答），以執行階段失敗作為回饋進行針對性修復。此「物理建構—重播—修復」迴路確保了 Executable Environment（可執行環境）的 Authenticity（真實性）。

第三，錄製內容缺乏明確測試套件以自動判斷任務目標是否達成。若僅以 LLM（大型語言模型）靜態生成測試，易產生偽陰性（正確解答因脆弱測試被拒絕）與偽陽性（任務被繞過或有缺陷的 Workflow（工作流程）通過）。因此引擎引入基於試驗的校準迴路：在重建的 Docker 容器中透過實際執行回饋反覆生成與校準測試，直至測試具備足夠判別力。

透過此全 Automated Engine（自動化引擎）流程，處理 80,870 筆原始錄製後，產出 1,530 項 Validated Task（經驗證任務），涵蓋 18 個 Real-World Category（真實世界類別）、長短不一的 Workflow（工作流程）（最長逾 50 步）與 1,280 項 Unique Command（獨特指令）。其中 200 項經 Manually Reviewed（人工審查）構成 Verified Subset（已驗證子集），作為嚴謹的標準測試床。

#### 實驗數據解讀

在 Verified Subset（已驗證子集）上，作者對八個 Frontier Model（前沿模型）（如 Claude Opus 4.7、GPT-5.5、Gemini 3.1 Pro）與六個 Terminal Agent（終端機智慧體）（含 Claude Code、Codex CLI、Gemini CLI 等 Open-Source Framework（開源框架）與 Commercial CLI Assistant（商業 CLI 助理））進行全面 Benchmarking（基準測試）。數據揭示四項關鍵發現：

其一，Real-World Terminal Task（真實世界終端機任務）對現有系統仍具高度挑戰性，最高 Pass Rate（通過率）僅 62.5%。這顯示即便具備 Multi-Step Reasoning（多步驟推理）與 Tool Use（工具使用）能力的模型，在面對 Authentic Terminal Workflow（真實終端機工作流程）時仍存在顯著能力缺口。更值得關注的是「效率悖論」：Agent（智慧體）常耗費額外運算資源探索環境，卻未實質推進任務進度，反映現有決策機制在 In-the-Wild（真實環境）中的探索效率低落。

其二，Agent Framework（智慧體框架）主要影響成本效益，而非底層能力上限。這意味為 Terminal Environment（終端機環境）設計的實用 Agent（智慧體），應著重降低探索摩擦，而非單純堆疊編排複雜度。換言之，現有框架（如 SWE-agent、OpenHands）在 Action Space（動作空間）的設計上，可能過度強調結構化約束，反而限制了原生 CLI（命令列介面）的靈活性。

其三，與現有 Expert-Curated Benchmark（專家策劃基準測試）的脫鉤現象顯著。Terminal-Bench 的分數對 TERMINALWORLD-VERIFIED 的表現僅具 Weak Correlation（弱相關），Pearson r（皮爾森相關係數）僅 0.20。這強烈暗示 Domain Expert（領域專家）設計的 Adversarial Puzzle（對抗性難題）並未涵蓋 Authentic Terminal Workflow（真實終端機工作流程）所需的核心能力，現有 Benchmarking（基準測試）體系存在評估維度單一的盲點。

其四，儘管任務根植於真實人類錄製，Agent（智慧體）往往透過截然不同的有效指令路徑完成任務，而非模仿原始開發者 Workflow（工作流程）。整體 Command（指令）集合重疊率的中位數僅 21.4%，顯示 Agent（智慧體）具備發現替代解法的潛力，但同時也說明「行為克隆」並非評估重點，結果導向的評估指標更為關鍵。

#### 與現有研究的比較

相較於 Terminal-Bench、LongCLI-Bench 等 Expert-Curated Benchmark（專家策劃基準測試），TerminalWorld（本文提出之基準測試平台）的根本差異在於「由建構即具 Authenticity（真實性）與可擴充性」。傳統專家策劃模式傾向設計 Adversarial Puzzle（對抗性難題）以人為最大化難度，導致任務分布偏離日常 Developer Workflow（開發者工作流程），且勞力密集的生產流程使其面臨 Scalability Bottleneck（可擴充性瓶頸），難以隨終端機實務演進而更新。近期自動化合成方法雖試圖繞過此瓶頸，但多服務於訓練用途，缺乏 Rigorous Validation（嚴謹驗證）以確保 Authenticity（真實性）。

相較於早期狹隘的單技能評估（如 NL2Bash、InterCode），TerminalWorld 涵蓋 Multi-Step Reasoning（多步驟推理）與 Interactive CLI Session（互動式 CLI 工作階段），任務長度與複雜度均大幅提升。1,280 項 Unique Command（獨特指令）中 91% 未見於 Terminal-Bench，顯示其語義與工具覆蓋率的廣度。

然而，本研究亦存在侷限。首先，資料來源依賴 Asciinema Platform（Asciinema 平台）的使用者上傳，存在選擇性偏差：願意公開分享錄製的開發者可能傾向特定技術族群或任務類型。其次，僅 200 項任務經 Manually Reviewed（人工審查），其餘 1,330 項任務雖經自動化驗證，但在極端複雜的系統狀態下，Docker 重建仍可能遺漏部分隱性依賴或環境副作用。第三，測試套件生成雖有執行回饋校準，但對於涉及外部網路狀態、硬體資源或大型資料集的操作，自動化測試的判別力可能受限。

#### 可重現性評估

本研究在可重現性方面採取開放科學原則：資料與程式碼已釋出於 GitHub。由於整個 Data Engine（資料引擎）為全 Automated Engine（自動化引擎），理論上研究者可在取得 Asciinema Corpus（語料庫）後重新執行管線，產生相同的 1,530 項 Validated Task（經驗證任務）。Docker 化環境的採用大幅提升了 Executable Environment（可執行環境）的再現穩定度，重播 Reference Solution（參考解答）的機制亦提供了可驗證的基線。

不過，完全重現仍面臨若干實務障礙。Data Engine（資料引擎）在 Distillation（提煉）階段與環境 Reverse-Engineer（逆向工程）階段均依賴商業 LLM（大型語言模型）（如 Claude Sonnet 4.6、Claude Code），其模型權重未公開，且 API 行為可能存在版本漂移或隨機性，導致不同時間點執行管線可能產生些微差異。此外，Verified Subset（已驗證子集）的 Manually Reviewed（人工審查）涉及作者主觀語義對齊判斷，雖已交叉審查，但難以完全排除人為因素。對於希望僅使用現成基準的研究者而言，釋出的資料集與 Docker 映像應已足夠；但若要擴充或修改引擎，則需承擔商業 API 的成本與不可完全控制的隨機性。

#### 未來研究方向

基於 TerminalWorld（本文提出之基準測試平台）的發現，未來研究可沿以下方向展開：

第一，針對「效率悖論」，需發展具備環境感知探索策略的 Agent（智慧體），減少在 Terminal Environment（終端機環境）中的無效試錯。這可能涉及強化學習或基於世界模型的規劃，以在發出 Command（指令）前預測系統狀態轉移。

第二，既然 Agent Framework（智慧體框架）主要影響成本效益而非能力上限，未來框架設計應回歸簡化 CLI（命令列介面）的原生互動，降低編排摩擦，而非增加結構化 Action Space（動作空間）的層級。Open-Source Framework（開源框架）可借鏡 Commercial CLI Assistant（商業 CLI 助理）的設計哲學，賦予 Agent（智慧體）更靈活的 Tool Use（工具使用）組合權限。

第三，Automated Engine（自動化引擎）可與持續整合結合，隨 Asciinema Platform（Asciinema 平台）新增上傳自動擴充 Benchmark（基準測試），形成動態演進的評估生態系。這需要建立更穩健的測試套件版本控制與環境依賴追蹤機制。

第四，目前 Pass Rate（通過率）天花板僅 62.5%，剩餘 37.5% 的失敗案例構成寶貴的錯誤分析語料。系統性分類這些失敗模式（如語義理解錯誤、工具參數誤用、長程依遺忘）將直接指導下一代 Frontier Model（前沿模型）的訓練與微調策略。

第五，測試驗證可從目前的 Manually Reviewed（人工審查）與試驗校準，進一步邁向形式化規格或契約式驗證，以降低偽陽性與偽陰性風險，尤其對涉及安全性關鍵的 Complex Software System（複雜軟體系統）任務。

第六，擴展至多模態或跨介面評估：真實開發者 Workflow（工作流程）常交錯使用 Terminal Environment（終端機環境）、整合開發環境與圖形化介面。將 TerminalWorld 的 Reverse-Engineer（逆向工程）方法論延伸至混合 Action Space（動作空間），將更完整評估 Autonomous Agent（自主智慧體）在真實軟體開發場景中的能力。

## 論文問答

**Q1：TerminalWorld 旨在解決什麼核心問題？**
A：TerminalWorld 旨在解決「如何可靠地評估自主智慧體在真實世界終端機任務上的表現」這一開放性問題。隨著大型語言模型在多步驟推理與工具使用方面的進展，終端機環境已成為自主智慧體完成複雜軟體系統任務的主要動作空間，但現有評估方法卻難以真實反映日常開發者的工作流程。因此，本文提出一個既真實又可擴充的評估系統，以回答「終端機智慧體在與日常實踐同步演化的真實任務上表現如何」這一關鍵問題。

**Q2：現有的專家策劃基準測試與自動化合成方法為何不足以評估終端機智慧體？**
A：現有的專家策劃基準測試，例如 Terminal-Bench 與 LongCLI-Bench，往往由領域專家設計對抗性難題以人為最大化難度，導致其偏離真實的終端機工作流程。此外，這種勞力密集的過程難以隨著不斷演化的終端機實踐與新興工具進行擴充，使得基準測試範圍狹窄且迅速過時。另一方面，近期的自動化合成方法雖然試圖突破可擴充性瓶頸，但它們主要用於訓練而非評估，且鮮少經過嚴謹驗證以確保真實性，因此無法保證評估結果能忠實反映智慧體在真實環境中的能力。

**Q3：為何對真實世界終端機任務進行真實性評估對自主智慧體的發展特別重要？**
A：真實世界終端機任務的評估能確保智慧體不僅能解決人為設計的抽象難題，更能處理實際開發者日常面對的雜訊、重試與多步驟工作流程。由於終端機環境是智慧體與複雜軟體系統互動的主要介面，若評估脫離真實情境，將導致研究與產品開發過度擬合於不自然的對抗性案例，而忽略實際部署時的摩擦與探索成本。因此，建立真實且可擴充的評估系統，是縮短實驗室性能與實際應用落差、並推動終端機智慧體持續進步的關鍵基礎。

**Q4：TerminalWorld 資料引擎的核心運作機制是什麼？**
A：TerminalWorld 資料引擎的核心運作機制是將真實環境 (In-the-Wild) 的終端機錄製內容，透過自動化流程逆向工程為可執行且經嚴謹驗證的評估任務。該引擎處理來自 Asciinema 平台的終端機工作階段錄製，利用大型語言模型提煉錄製文字紀錄，從雜訊中萃取出結果導向指令與乾淨指令腳本作為參考解答。接著，引擎透過智慧體自動重建底層執行環境並產生測試套件，最終將原始錄製轉化為高保真的評估任務，使整個流程在構造上即具備真實性與可擴充性。

**Q5：將原始終端機錄製轉換為評估任務時存在哪三大挑戰，TerminalWorld 如何解決？**
A：第一個挑戰是錄製文字紀錄充滿雜訊且缺乏明確意圖，例如包含錯字、重試與冗長系統輸出；對此，引擎使用大型語言模型將其提煉為結果導向指令與乾淨指令腳本，以捕捉開發者的潛在意圖。第二個挑戰是錄製未捕捉底層執行環境，引擎因此部署智慧體推斷實際需求、消除幻覺依賴，並透過建構 Docker 映像檔與重播參考解答，以執行時錯誤作為回饋進行針對性修復。第三個挑戰是缺乏明確測試套件，單靠靜態生成容易出現偽陰性與偽陽性，故引擎配備基於試驗的校準迴路，在重現的 Docker 容器中透過實際執行回饋來生成並校準測試套件。

**Q6：作者為何選擇 Asciinema 平台作為資料來源，「已驗證子集」的設計意義為何？**
A：作者選擇 Asciinema 平台是因為該平台匯集了開發者自願分享、經人工審核且持續增長的終端機工作階段錄製，形成一個自行整理的真實開發者工作流程語料庫，這使得自然發生的終端機操作得以被忠實記錄並逆向工程為評估任務。至於「已驗證子集」則是從 1,530 個經驗證任務中精選出 200 個代表性任務，由作者人工執行參考解答並審查所有成品之間的語義一致性。這個子集不僅提供了一個嚴謹且具挑戰性的測試平台，用於基準測試前沿模型與智慧體，也確保了在自動化擴充之餘，仍保有高品質的人工監督與可信度。

**Q7：TerminalWorld 基準測試與其已驗證子集的主要特徵為何？**
A：TerminalWorld 基準測試源自 80,870 份原始錄製，最終產出 1,530 個經驗證任務，涵蓋 18 個真實世界類別，從簡短的日常操作到超過 50 步驟的複雜工作流程，並涉及 1,280 個獨特指令。其中高達 91% 的獨特指令未出現在 Terminal-Bench 中，顯示其與現有基準測試在內容覆蓋度上的顯著差異。已驗證子集則進一步從中挑選 200 個任務進行人工審查，確保參考解答與重現環境的語義對齊，為評估真實終端機工作流程提供了一個既具代表性又嚴謹的黃金標準測試床。

**Q8：綜合基準測試實驗揭示了哪四項關鍵發現？**

## 實務應用指南

### 適用場景

1. **企業內部 CLI 助理驗收**：利用 TerminalWorld 的可擴充資料引擎，將內部開發者的終端機錄製內容轉為評估任務，驗證商業 CLI 助理或自研智慧體在真實公司程式碼庫與工具鏈上的表現，避免僅以人工設計的對抗性難題衡量能力。

2. **DevOps 自動化智慧體回歸測試**：在 CI/CD 流程中部署 TerminalWorld-Verified 類型的測試集，持續評估自動化部署、日誌排查等真實終端機工作流程的通過率，防止模型更新或框架改版後能力退化。

3. **開源專案維護者知識固化**：透過逆向工程將核心貢獻者的終端機工作階段錄製轉為可執行環境與參考解答，建立新人 onboarding 的互動式教材與能力測驗，降低口耳相傳的知識流失風險。

4. **終端機教育平台內容生成**：利用資料引擎自動提煉 Asciinema 平台上高品質的開發者工作流程，批量產生結果導向指令與乾淨指令腳本，將真實環境 (In-the-Wild) 語料轉為結構化學習資源。

5. **多智慧體成本效益比較**：運用已驗證子集進行標準化基準測試，比較 Claude Code、Codex CLI、Gemini CLI 等不同代理程式框架在相同真實世界終端機任務上的探索摩擦與執行成本，輔助採購或自研決策。

### 實作前置條件

- **資料**：取得原始終端機錄製內容（如 Asciinema 匯出檔或內部錄影紀錄）、對應的系統回應文字紀錄，以及可存取的 Docker Registry 空間；若為內部語料，需預先規劃敏感資訊脫敏流程。
- **運算**：具備呼叫前沿模型 API（如 Claude Sonnet 4.6、GPT-4o 等）的預算與配額；建置 Docker 映像檔所需的運算節點（建議具備 x86_64 環境以確保相容性），並預留重試與校準迴圈的執行時間。
- **技能**：熟悉命令列介面操作與 Shell 腳本撰寫；具備大型語言模型提示工程經驗以優化提煉與環境重建流程；了解容器化技術（Dockerfile 調校、Volume 掛載與網路隔離），能判斷執行階段錯誤並進行針對性修復。

### 實作步驟建議

1. **語料收集與清洗**：蒐集目標領域的終端機錄製內容，過濾掉包含敏感資訊（如密鑰、IP 位址）的片段，保留具有明確開發者目標的工作階段，並依時間戳記排除已棄用的操作。
2. **意圖提煉與腳本生成**：使用大型語言模型將錄製文字紀錄轉換為結果導向指令與乾淨指令腳本，作為參考解答；此階段需設計提示詞以消除錯字、重試與冗長系統輸出造成的雜訊。
3. **執行環境逆向工程**：部署 LLM 智慧體（如 Claude Code）分析參考解答的依賴關係，自動撰寫 Dockerfile；透過實際建置容器並重播腳本，以執行階段錯誤作為回饋進行針對性修復，消除幻覺依賴。
4. **測試套件校準**：在重建的 Docker 容器內執行試驗性驗證，利用智慧體生成測試邏輯，並透過實際執行回饋調整，避免偽陰性（正確解答被誤判）與偽陽性（繞過任務目標）。
5. **人工審查與子集策展**：針對關鍵任務執行人工審查，確認語義對齊與環境可重現性，策劃出代表性強、難度分布均勻的已驗證子集，作為正式基準測試集。
6. **持續整合與迭代**：將自動化引擎接入內部資料管線，隨著開發者實務演進定期重新執行，確保評估任務不會快速過時，並追蹤不同版本智慧體的通過率變化。

### 潛在風險與注意事項

- **敏感資料外洩**：終端機錄製內容常包含環境變數、憑證或內部網址，需在語料收集階段導入自動化脫敏流程，並限制重建環境的網路存取。
- **環境再現性陷阱**：作者機器上的隱性系統狀態（如特定 shell 設定、全域安裝的工具）難以完全捕捉，可能導致 Docker 重建失敗；建議記錄 `uname`、`which`、`env` 等系統快照輔助推理。
- **測試脆化**：靜態生成的測試邏輯容易因輸出格式微幅差異而產生偽陰性，必須保留試驗式校準迴圈，並允許多種有效指令路徑通過驗證。
- **成本控管**：全自動化引擎需多次呼叫大型語言模型並反覆建置容器，規模化時 API 與運算成本可能急遽上升；建議先以小規模語料驗證管線準確率，再擴充至大量錄製內容。
- **過度擬合真實雜訊**：真實環境資料雖具真實性，但可能包含已棄用的指令或特定版本漏洞；需搭配時間戳記篩選，避免評估任務基於過時的最佳實踐。

### 與其他技術的整合建議

- **整合現有代理程式框架**：將 TerminalWorld 的評估任務匯入 SWE-agent、OpenHands 或 Claude Code 的執行環境，作為標準化能力測驗，並比較不同框架在相同動作空間下的表現。
- **嵌入 CI/CD 管線**：在 Jenkins、GitHub Actions 或 GitLab CI 中設立「智慧體回歸測試」階段，於每次模型更新或框架改版時，自動執行已驗證子集並追蹤通過率變化。
- **銜接可觀測性平台**：將智慧體執行過程中的指令軌跡、探索摩擦點與系統回應寫入 ELK 或 Prometheus，建立真實終端機工作流程的除錯與效能儀表板。
- **搭配專家策劃基準測試**：同時運行 Terminal-Bench 等現有基準與 TerminalWorld，利用皮爾森相關係數分析模型在對抗性難題與真實工作流程上的能力落差，補足單一測試的盲點。
- **對接內部知識庫**：將逆向工程後的結果導向指令與乾淨指令腳本輸出至 Confluence、Notion 或內部 Wiki，自動生成可執行的標準作業程序（SOP）文件。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從第一節的動機與整體管線架構著手，理解「為何真實世界終端機任務不同於人工設計的題目」；不必深究 Docker 重建或測試校準的技術細節，重點掌握「真實性」與「可擴充性」這兩個核心價值。
- **AI 工程師**：請聚焦於資料引擎的實作細節，特別是第三章關於環境逆向工程的 LLM 智慧體設計、以執行失敗作為回饋的修復迴圈，以及測試套件生成中的偽陰性/偽陽性處理；這些是將論文方法落地為內部評估系統的關鍵。
- **研究人員**：建議深入分析 TerminalWorld-Verified 與 Terminal-Bench 的弱相關（Pearson r = 0.20）實驗結果，思考「專家策劃的對抗性難題」與「真實環境操作語料」各自捕捉了哪些不同的能力維度；此外，可關注智慧體與人類原始工作流程僅 21.4% 指令重疊的發現，這對行為對齊研究具有啟發性。
- **產品經理**：請將閱讀重點放在通過率天花板（62.5%）與成本效益分析，理解當前前沿模型在真實終端機環境中的實際限制；同時關注自動化引擎帶來的規模化優勢，評估導入此類基準測試對縮短 CLI 助理上市驗證週期的商業價值。
