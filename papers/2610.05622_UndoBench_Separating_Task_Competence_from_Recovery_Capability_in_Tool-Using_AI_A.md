# UndoBench：在使用工具的人工智慧代理（Tool-using AI agents）中分離任務能力（Task Competence）與恢復能力（Recovery Capability）

## ⚡ TL;DR

現有基準測試僅評估標稱任務完成，混淆任務能力與故障恢復能力。
本文提出 UndoBench，透過反事實配對試驗與雙重預言機，分離兩種能力。
實驗顯示標稱成功率 83.54%，條件式恢復成功率僅 46.72%，暴露階段相依安全漏洞。

## 摘要翻譯

使用工具的人工智慧代理（Tool-using AI agents）日益廣泛地部署於各企業軟體系統，然而現有基準測試主要評估標稱任務完成與否（Nominal Task Completion），混淆了基線規劃能力（Baseline Planning Competence）與運作故障恢復（Operational Fault Recovery）能力。我們提出 UndoBench，一個涵蓋 36 個基礎工作流程與 36 個故障情境、橫跨 8 個企業領域的基準測試，透過在相同隨機種子（Identical Seeds）下進行反事實配對試驗（Counterfactual Paired Trials），並搭配線路層級效應歷史預言機（Wire-level Effect-history Oracle）與環境狀態預言機（Environment-state Oracles），以解耦任務能力（Task Competence）與恢復能力（Recovery Capability）。在凍結遺失確認研究（Frozen Lost-acknowledgment Study）中，針對 12 個保留的 TEST 工作流程（Held-out TEST Workflows），於兩個開放權重模型（Open-weight Models）、兩個框架與三種恢復典範（Recovery Paradigms）下進行 5,760 次執行（共 2,880 組配對試驗），標稱能力成功率（Nominal Competence）達到 83.54%，而條件式恢復成功率（Conditional Recovery Success Rate, CRSR）降至 46.72%，且樸素重試（Naive Retry）在 53.33% 的試驗中產生重複外部效應（Duplicate External Effects）。延伸至商業 API 模型（Commercial API Models）的實驗亦重現了此能力與恢復分離（Competence-recovery Separation）的現象。橫跨互補執行邊界（Complementary Execution Boundaries）的評估顯示，恢復具有階段相依性（Phase-dependent Recovery）：在變更前（PRE_MUTATION），各方法在具備標稱能力的試驗中表現相近且未產生重複效應；在部分變更期間（DURING_MUTATION），樸素重試、每次呼叫冪等性（Per-call Idempotency）與零權限日誌記錄（Zero-privilege Journaling）在所評估的複合工作流程（Composite Workflows）上效能崩解；在提交後、確認前的階段（After Commit but Before Acknowledgment），驗證（Verification）與伺服器端冪等性（Server-side Idempotency）大幅提升安全性（Safety）。這些發現證實，僅評估標稱完成會掩蓋自主代理（Autonomous Agents）中關鍵且階段相依的恢復漏洞。

### 核心貢獻（3～5點）
- 提出 UndoBench 基準測試，首次系統性地將「任務能力」與「恢復能力」解耦評估，避免傳統端到端成功率掩蓋故障後的脆弱性。
- 設計反事實配對試驗與雙重預言機機制（線路層級效應歷史與環境狀態），在相同隨機種子下精確測量代理於外部系統故障後的恢復表現。
- 發現能力與恢復分離現象：標稱能力成功率達 83.54%，但條件式恢復成功率（CRSR）僅 46.72%，顯示正常條件下的高成功率並不保證運作故障時的安全恢復。
- 揭示恢復表現的階段相依性：在變更前、部分變更期間與提交後確認前等不同執行邊界，各恢復典範（樸素重試、冪等性、日誌記錄、驗證）的效能與安全性差異顯著。
- 驗證常見的樸素重試策略會在過半數試驗中產生重複外部效應，強調評估執行安全性與恰好一次語義的重要性。

### 適合對象
本論文最適合 AI 代理與自主系統研究者、企業軟體與分散式系統工程師、基準測試設計者，以及關注大型語言模型驅動代理在真實運作環境中安全性、可靠性與故障恢復能力的工程與研究人員。對於正在設計或部署工具使用型代理、需要評估其於支付閘道、訂閱管理、供應鏈等企業領域中面對網路逾時、確認遺失等故障時行為的實務團隊，尤具參考價值。

## 深度分析

#### 方法論解析

##### 1. 問題形式化與能力解耦

UndoBench 的核心貢獻在於把傳統端到端任務成功指標（end-to-end task success metric）拆解為兩個獨立維度：**任務能力（Task Competence）** 與 **恢復能力（Recovery Capability）**。任務能力指代理在**標稱條件（nominal conditions）** 下，能否正確協調多個工具呼叫（tool call）完成目標；恢復能力則指當外部系統故障（external system fault）發生於執行中途（mid-execution）時，代理能否診斷、協調並安全修復執行狀態。

傳統基準測試若僅報告無條件恢復成功率（unconditional Recovery Success Rate, RSR），會把標稱規劃失敗（nominal planning failures）與故障誘發的恢復失敗（recovery failures）混為一談：

\[
RSR = P(\text{Success} \mid \text{Fault})
     = P(\text{Success} \mid \text{Fault}, \text{Comp})P(\text{Comp})
     + P(\text{Success} \mid \text{Fault}, \neg\text{Comp})P(\neg\text{Comp})
\]

為了分離兩者，UndoBench 提出**條件式恢復成功率（Conditional Recovery Success Rate, CRSR）**：

\[
CRSR = P(\text{Success} \mid \text{Fault}, \text{Comp})
\]

實作上，UndoBench 對每一個工作流程進行**配對反事實執行（paired counterfactual execution）**：在相同隨機種子（identical seeds）下，先執行一次無故障的**對照執行（control execution）** 記錄標稱能力 \(C_i\)，再執行一次注入故障的**故障執行（faulted run）** 記錄恢復結果 \(F_i\)。只有當對照執行成功（\(C_i=1\)）時，該配對才會被計入 CRSR 的分母，從而把「本來就不會做」與「會做但故障後做壞」區分開來。

##### 2. 外部變更生命週期與執行邊界

UndoBench 把分散式架構（distributed architectures）中的遠端狀態修改（remote state modification）形式化為三個層次：

- **物理呼叫（Physical Invocation）**：API 請求或遠端程序呼叫（RPC）跨網路邊界發出，產生暫態傳輸狀態。
- **已提交變更（Committed Mutation）**：遠端服務實際執行並持久化的狀態修改，例如寫入資料庫、提交 Git tree、扣款。
- **語義效應（Semantic Effect）**：任務規格要求達成的更高層業務不變量，例如帳戶餘額正確、金絲雀部署（canary release）完成、通知發送。

基於此，論文定義五個**執行邊界（execution boundaries）**：

1. **PRE_MUTATION**：遠端狀態尚未開始修改前的傳輸失敗（如 DNS 錯誤、連線逾時）。
2. **DURING_MUTATION**：進行中的非原子狀態更新（active non-atomic state updates）期間發生失敗（如唯一鍵衝突、並行中止）。
3. **POST_MUTATION_PRE_ACK**：遠端變更已提交（commit），但回應封包遺失（response packet drops），造成客戶端未收到確認（acknowledgment loss）。
4. **POST_ACK_PRE_CHECKPOINT**：客戶端已收到 ACK，但在持久化檢查點（checkpoint）前當機。
5. **DURING_COMPENSATION**：補償回滾（compensatory rollback）執行期間發生故障。

主要凍結驗證性實驗聚焦於 **POST_MUTATION_PRE_ACK**，因為這是實務上最難處理、也最容易導致重複外部效應（duplicate external effects）的階段；凍結後次要擴充（post-freeze secondary extensions）再補充評估 PRE_MUTATION 與 DURING_MUTATION。

##### 3. 雙重預言機與執行安全性指標

UndoBench 同時部署兩種預言機（oracles）：

- **環境狀態預言機（environment-state oracle）**：驗證實體環境不變量（physical environment invariants）是否滿足。
- **效應歷史預言機（effect-history oracle）**：在線路層級（wire-level）監控外部系統實際產生的效應，區分：
  - **重複效應率（Duplicate Effect Rate, DER）**
  - **遺失效應率（Missing Effect Rate, MER）**
  - **恰好一次執行率（Exactly-Once Execution Rate, EOR）**

這種**雙重狀態與效應歷史預言機（dual state and effect-history oracles）** 設計，能夠發現傳統只看最終字串答案的基準無法偵測的問題：例如代理因盲目重試而重複扣款，卻仍通過最終斷言。

##### 4. 基準規模與實驗設計

UndoBench 涵蓋 36 個基礎工作流程（base workflows）、36 個故障情境（fault scenarios），橫跨 8 個企業領域（enterprise domains）。在凍結遺失確認研究（frozen lost-acknowledgment study）中，使用 12 個保留的 TEST 工作流程（held-out TEST workflows）、兩個開放權重模型（open-weight models）、兩個框架（frameworks）與三種恢復典範（recovery paradigms），共進行 5,760 次執行 / 2,880 組配對試驗（paired trials）。

#### 實驗數據解讀

##### 1. 凍結遺失確認研究的核心數據

在固定條件下針對 lost ACK 情境的實驗顯示：

- **標稱能力（nominal competence）**：對照執行成功率達 **83.54%**。
- **條件式恢復成功率（CRSR）**：在標稱成功的配對中，僅 **46.72%** 能在故障後正確恢復。
- **樸素重試（naive retry）**：在 53.33% 的試驗中產生**重複外部效應（duplicate external effects）**。

這三個數字構成論文所謂的**能力與恢復分離（competence-recovery separation）**：一個代理在標稱條件下表現優秀，並不保證它在運作故障恢復（operational fault recovery）時同樣安全。CRSR 與標稱成功率之間約 37 個百分點的差距，清楚說明僅評估標稱任務完成（nominal task completion）會嚴重掩蓋關鍵脆弱性。

##### 2. 階段相依恢復（phase-dependent recovery）

論文進一步指出，恢復並非單一純量能力，而是**階段相依（phase-dependent）** 的系統特性：

- **PRE_MUTATION（變更前）**：此時遠端狀態尚未修改，各種恢復方法表現相近；在有能力成功的試驗中，不會產生重複效應。
- **DURING_MUTATION（變更期間）**：面對部分變更（partial mutation），**樸素重試（naive retry）**、**每次呼叫冪等性（per-call idempotency）** 與**零權限日誌記錄（zero-privilege journaling）** 在評估的複合工作流程（composite workflows）上皆「崩潰」——無法保證語義正確性。原因是單一呼叫的冪等性無法保證整個多步驟序列的語義正確，而無額外權限的日誌也無法完整重建中間狀態。
- **POST_MUTATION_PRE_ACK（提交後但確認前）**：此階段中，**驗證（verification）** 與**伺服器端冪等性（server-side idempotency）** 能顯著提升安全性。代理若能先查詢遠端狀態再決定是否重發，或伺服器本身以冪等鍵（idempotency key）去重，就能避免重複計費違規（duplicate billing violation）等問題。

這項發現對系統設計極具實務意義：不同執行邊界需要不同的恢復原語，不能期望單一「重試迴圈（retry loop）」或單一冪等性機制解決所有問題。

##### 3. 商業 API 模型的擴充結果

論文將實驗擴展至**商業 API 模型（commercial API models）**，發現同樣出現能力與恢復分離的現象。這表示該問題並非特定開放權重模型（open-weight models）或框架（frameworks）的缺陷，而是當前使用工具的人工智慧代理（Tool-using AI agents）在面對真實分散式系統時的普遍脆弱性。

##### 4. 指標的綜合意涵

綜合來看，UndoBench 的指標體系揭示了三個層次的風險：

1. **規劃風險**：標稱成功率 83.54% 顯示仍有約 16% 的任務在無故障時也無法完成。
2. **恢復風險**：CRSR 僅 46.72%，代表即使代理「會做」，故障後也有一半以上機會做錯。
3. **安全風險**：樸素重試導致 53.33% 試驗出現重複外部效應，這在支付、資料庫遷移、庫存管理等企業領域可能造成不可逆的實際損失。

#### 與現有研究的比較

##### 1. 傳統任務導向基準測試的不足

現有基準測試如 AgentBench（Liu et al., 2024）與 WebArena（Zhou et al., 2024）主要評估代理在**標稱條件（nominal conditions）** 下的任務完成率。這些基準測試通常：

- 不注入執行中途（mid-execution）的外部系統故障（external system fault）。
- 不監控線路層級效應歷史（wire-level effect-history），因此無法偵測重複外部效應或遺失效應。
- 不區分標稱規劃失敗與恢復失敗，導致單一成功率指標無法回答關鍵運作問題：「如果代理有能力標稱完成任務，它能否在故障發生時安全恢復？」

##### 2. UndoBench 的主要改進

相較於傳統基準，UndoBench 在以下幾個維度有顯著提升：

- **反事實配對試驗（counterfactual paired trials）**：透過相同種子（identical seeds）的對照執行與故障執行配對，數學上嚴格分離任務能力與恢復能力。
- **線路層級效應監控**：效應歷史預言機（effect-history oracle）能偵測最終答案正確但實際產生重複或遺失效應的情況。
- **外部變更生命週期（external-mutation lifecycle）** 的多邊界覆蓋：把恢復從單一純量能力重新定義為階段相依的系統特性。
- **執行安全性指標**：引入 DER、MER、EOR 等指標，補充傳統正確性指標的不足。

##### 3. 限制與適用範圍

儘管設計嚴謹，UndoBench 仍有若干限制：

- **主要實驗範圍集中**：凍結驗證性遺失 ACK 研究（frozen confirmatory lost-ACK study）主要聚焦 POST_MUTATION_PRE_ACK，雖有凍結後次要擴充涵蓋 PRE_MUTATION 與 DURING_MUTATION，但 POST_ACK_PRE_CHECKPOINT 與 DURING_COMPENSATION 的系統性評估仍待未來工作。
- **領域與工作流程代表性**：36 個基礎工作流程橫跨 8 個企業領域，但相較於真實企業軟體的無窮組合，仍屬簡化模型。
- **預言機建置成本**：雙重狀態與效應歷史預言機需要針對每個工作流程與外部系統進行精細的線路層級儀器化（instrumentation），在真實第三方閉源服務上可能難以完全複製。
- **故障模型範圍**：目前主要處理遺失確認（lost acknowledgment）、連線逾時、部分變更等故障，尚未涵蓋拜占庭式故障（Byzantine faults）或長時間延遲等更複雜情境。

#### 可重現性評估

從提供的上下文來看，論文尚未明確說明原始碼、資料集、環境設定與預言機實作的公開釋出方式。因此，在缺乏官方 artifact 的情況下，**可重現性（reproducibility）仍屬不確定**。不過，UndoBench 的設計本身具備多項有利於重現的特質：

- **相同隨機種子（identical seeds）**：對照執行與故障執行配對，降低隨機性帶來的變異。
- **程式化預言機（programmatic oracles）**：狀態與效應檢查若公開，可提供客觀、自動化的評分標準。
- **確定性故障注入（deterministic fault injection）**：在固定邊界注入故障，使實驗條件可被精確描述與複製。

若要達成高品質可重現性，建議作者釋出：

1. 完整的基礎工作流程與故障情境定義。
2. 環境狀態預言機與效應歷史預言機的實作。
3. 代理框架（frameworks）與模型設定，包括提示詞（prompts）與工具描述。
4. 可執行的 Docker 或虛擬環境，內含模擬的企業服務與故障注入器。
5. 原始執行日誌與評分腳本，以便第三方驗證 5,760 次執行 / 2,880 組配對試驗的結果。

#### 未來研究方向

基於 UndoBench 的發現，以下幾個方向值得後續深入研究：

##### 1. 擴充執行邊界與故障模型

系統性評估 POST_ACK_PRE_CHECKPOINT 與 DURING_COMPENSATION 兩個目前較少觸及的邊界；同時引入更複雜的故障類型，例如網路分區、長時間延遲、部分回應、以及第三方服務的拜占庭式行為。

##### 2. 自動化恢復策略學習

目前實驗比較的是樸素重試、冪等性、日誌等固定恢復典範。未來可研究如何讓大型語言模型代理（LLM agents）透過強化學習或示範學習，自動學習階段相依的恢復策略，並在安全性與任務成功率之間取得平衡。

##### 3. 形式化驗證與安全保證

將線路層級效應歷史與環境狀態預言機結合形式化方法，嘗試證明特定恢復策略在某些執行邊界下能保證恰好一次執行安全性（exactly-once execution safety），或至少給出可量化的風險上界。

##### 4. 真實企業系統整合

把 UndoBench 的儀器化方法擴展到真實的企業軟體系統（如 Salesforce、Stripe、AWS、GitHub Enterprise），驗證在真實 API 與真實冪等性機制下的恢復表現，並建立與實務 SRE（Site Reliability Engineering）指標的對應關係。

##### 5. 成本與延遲感知的恢復評估

除了正確性與安全性，未來基準可納入恢復成本（例如額外 API 呼叫次數、補償交易金額）與延遲，發展多目標評估框架，避免為了追求安全而無限制重試。

##### 6. 人機協同恢復

研究在關鍵執行邊界引入人類監督（human-in-the-loop）或人類確認機制，如何在降低自動化風險的同時，維持代理的自主性與效率。

##### 7. 跨代理與多代理系統的恢復

當多個使用工具的人工智慧代理同時操作共享外部狀態時，單一代理的恢復行為可能與其他代理的動作交錯，產生新的競態條件與部分變更問題。未來可發展多代理版本的 UndoBench。

##### 8. 恢復可解釋性

除了評估恢復是否成功，也應評估代理能否對其恢復決策提供正確、可理解的解釋，這對企業稽核與除錯至關重要。

總結而言，UndoBench 不僅提出了一套更嚴謹的評估方法，更重要的是把「恢復能力」從隱含假設中拉出來，變成可量化、可比較、可改進的獨立研究對象。後續工作若能在更多執行邊界、更多真實系統、以及更智慧的恢復策略上持續擴展，將有助於推動企業級自主代理（autonomous agents）從「示範可用」走向「生產可信」。

## 論文問答

**[背景與動機]**

**Q1：UndoBench 旨在解決什麼核心運作問題？**
A：現有基準測試通常只衡量代理在標稱條件下完成任務的能力，卻無法區分「任務能力」與「恢復能力」。UndoBench 的核心問題是：當代理具備正常完成工作流程的能力時，是否能在執行中途遭遇外部系統故障後安全且正確地恢復。這對企業級自主代理至關重要，因為真實環境中網路逾時、回應遺失等故障可能導致重複計費或資料不一致。

**Q2：為什麼現有的任務導向基準測試難以發現恢復漏洞？**
A：這些基準幾乎只在未受擾動的標稱條件下評估代理，不會在執行中途注入如遺失確認（lost ACK）等外部系統故障。此外，它們通常只檢查最終輸出字串或高階任務成功與否，無法監控線路層級的外部效應歷史。因此，代理若因盲目重試而產生重複外部效應，傳統評估仍可能將其視為成功，掩蓋了實際的運作風險。

**Q3：為何將任務能力與恢復能力分離具有實務重要性？**
A：高標稱成功率並不保證代理在故障發生時能安全恢復，兩者是不同的系統特性。若僅報告端到端任務成功指標，會把正常規劃失敗與故障後恢復失敗混為一談，使開發者誤以為系統已足夠安全。在支付、資料庫遷移等企業場景中，恢復不當可能導致重複計費或遺失關鍵副作用，因此必須獨立評估恢復能力。

**[方法與創新]**

**Q4：UndoBench 的核心評估典範是什麼？**
A：UndoBench 採用「配對反事實執行」（paired counterfactual execution），在相同隨機種子下同時執行一組無故障的對照執行與一組注入故障的執行。透過這種解耦配對評估，可以先把標稱任務能力（Control pass rate）與故障後的恢復表現分開。接著以條件式恢復成功率（CRSR）衡量「在標稱執行已成功的條件下，故障執行能否安全恢復」，從而精確量化恢復能力。

**Q5：雙重狀態與效應歷史預言機扮演什麼角色？**
A：環境狀態預言機負責驗證實體環境不變量是否成立，例如資料庫記錄、帳戶餘額或 Git 樹狀態是否符合任務規範。效應歷史預言機則監控線路層級的實際呼叫，量化重複效應率（DER）、遺失效應率（MER）與恰好一次執行率（EOR）。兩者結合才能揭露終端獎勵無法發現的問題：代理可能在最終答案上看似成功，卻已對外部系統造成重複或遺失的副作用。

**Q6：UndoBench 的故障分類與執行邊界設計有何特色？**
A：論文將外部變更生命週期劃分為五個執行邊界，包括變更前（PRE_MUTATION）、變更期間（DURING_MUTATION）、提交後但確認前（POST_MUTATION_PRE_ACK）、確認後但檢查點前，以及補償執行期間。主要凍結實驗聚焦於最關鍵的 POST_MUTATION_PRE_ACK 遺失確認窗口，因為此時遠端狀態已變更但代理不知情，最容易引發重試導致的重複效應。後續次要擴充則補充評估 PRE_MUTATION 與 DURING_MUTATION，並依效應可逆性將工具效應分為可逆、可補償與不可逆三類。

**[實驗與結果]**

**Q7：凍結遺失確認研究的實驗規模與設定為何？**
A：該研究涵蓋 36 個基礎工作流程與 36 個故障情境，橫跨 8 個企業領域，並在 12 個保留的 TEST 工作流程上進行評估。實驗使用兩個開放權重模型、兩個代理框架與三種恢復典範，總計執行 5,760 次並形成 2,880 對配對試驗。如此大規模的配對設計確保了統計穩定性，並能在相同種子下精確比較對照執行與故障執行的差異。

**Q8：主要量化結果揭示了什麼能力與恢復分離現象？**
A：在凍結遺失 ACK 研究中，代理的標稱能力達到 83.54%，但條件式恢復成功率（CRSR）僅有 46.72%，顯示出顯著的能力與恢復分離。更進一步，樸素重試策略在 53.33% 的試驗中產生了重複外部效應，例如重複計費。商業 API 模型的擴充實驗也複製了這種分離現象，證明問題不僅限於開放權重模型，而是當前工具使用代理的普遍挑戰。

**Q9：跨互補執行邊界的擴充實驗有何發現？**
A：恢復表現具有明顯的階段相依性：在 PRE_MUTATION 階段，各種方法表現相近且不易產生重複效應，因為遠端狀態尚未改變。在 DURING_MUTATION 階段，樸素重試、每次呼叫冪等性與零權限日誌記錄在評估的複合工作流程上均告崩潰，顯示部分變更情境下的恢復極為困難。相對地，在 POST_MUTATION_PRE_ACK 階段，驗證機制與伺服器端冪等性能顯著提升執行安全性，減少重複或遺失效應。

**[應用與影響]**

**Q10：UndoBench 模擬了哪些實務應用場景？**
A：基準涵蓋企業軟體中常見的 8 個領域，包括支付續約、資料庫遷移、程式碼倉儲操作、客戶關係查詢等。文中以訂閱續約為例：代理呼叫支付閘道後，若回應封包遺失，代理可能在未確認交易已提交的情況下重試，導致重複計費違規。這類情境直接對應真實世界中分散式系統的網路不穩定與外部服務故障，凸顯評估恢復能力的必要性。

**Q11：部署工具使用代理時應考慮哪些產品設計因素？**
A：產品團隊不應僅以標稱任務成功率作為上線依據，而需針對不同故障階段設計對應的恢復機制。例如，在提交後但確認前的情境，應優先採用伺服器端冪等性與執行後驗證，以避免重複呼叫造成副作用；在變更期間故障時，則需要更強大的狀態協調與補償邏輯。此外，必須透過線路層級監控與環境狀態預言機持續追蹤外部效應，而非僅檢查代理的最終輸出。

**Q12：UndoBench 對學術界與產業界可能帶來什麼影響？**
A：UndoBench 將代理評估從單純的任務完成導向，轉向同時關注運作安全性與恢復能力，為企業級自主代理的部署提供更嚴謹的測試標準。它提供的 CRSR、DER、MER、EOR 等指標，使研究者能夠量化過去難以觀察的恢復漏洞。長遠來看，這有助於推動更安全的代理框架設計，並促使產業在實際系統中採用階段相依的恢復策略。

**[限制與未來]**

**Q13：本研究有哪些已承認的限制？**
A：主要凍結確認性實驗集中於 POST_MUTATION_PRE_ACK 的遺失確認情境，雖然涵蓋廣泛，但並未窮盡所有分散式系統故障類型。次要擴充雖然補充了 PRE_MUTATION 與 DURING_MUTATION，但部分工作流程因條件限制僅進行限定評估。此外，實驗模型、框架與恢復典範的組合雖具代表性，仍無法涵蓋所有商業部署中的異質環境與策略。

**Q14：哪些失敗案例或漏洞仍未被現有方法解決？**
A：在 DURING_MUTATION 階段的複合工作流程中，樸素重試、每次呼叫冪等性與零權限日誌記錄均無法安全恢復，顯示部分變更中的非原子狀態更新仍是重大挑戰。某些代理可能選擇安全停機，卻因任務未完整執行而被視為失敗；另一些代理則可能盲目重試，導致重複效應或資料不一致。這些案例說明，單一恢復機制難以應對所有階段，必須針對故障發生的確切邊界設計策略。

**Q15：UndoBench 指出了哪些未來研究方向？**
A：未來可將基準擴展到更多執行邊界與故障類型，例如確認後但檢查點前的客戶端崩潰，或補償執行期間的二次故障。研究者也可開發全基準範圍的冪等性機制，並結合更強大的驗證與補償策略來提升複合工作流程的恢復表現。此外，將 UndoBench 應用於更多當代模型、真實生產日誌與多代理協作系統，將有助於進一步理解並強化自主代理的運作恢復能力。

## 實務應用指南

### 適用場景

1. **金融支付與帳務代理**
   當 AI 代理執行訂閱續約、退款、轉帳或發票開立時，遠端支付閘道可能在扣款成功後遺失確認（lost ACK）。UndoBench 可用來驗證代理是否會因樸素重試而產生重複計費違規，並評估伺服器端冪等性鍵或執行後驗證機制的有效性。

2. **DevOps 與 CI/CD 部署代理**
   自動化部署、資料庫遷移或基礎設施即程式碼（IaC）流程中，Git 提交、容器推送或資料庫變更可能在網路層確認遺失後被重複執行。透過 UndoBench 的線路層級效應歷史預言機，可偵測重複部署、遺失 canary 釋出或部分變更造成的狀態不一致。

3. **CRM 與銷售自動化代理**
   在更新客戶記錄、建立工單或發送通知時，外部 SaaS API 的逾時或回應遺失可能導致重複建立工單或漏發通知。UndoBench 可協助區分「代理本來就不會正確建立工單」與「代理在故障後無法安全恢復」。

4. **資料庫遷移與 ETL 流程**
   長時間執行的批次寫入或結構遷移若在中途發生連線逾時，代理必須判斷哪些步驟已提交、哪些尚未執行。UndoBench 的階段相依評估可指出在 DURING_MUTATION 與 POST_MUTATION_PRE_ACK 階段應採用何種恢復策略。

5. **醫療與製造業的設備控制代理**
   當代理透過 API 控制醫療裝置、工業 IoT 或庫存系統時，指令已送達但確認遺失可能導致重複給藥、重複下單或重複生產指令。此類不可逆外部效應特別需要環境狀態預言機與恰好一次執行安全性（EOR）評估。

### 實作前置條件

**資料前置條件**
- 至少 8–12 個與業務相關的基礎工作流程，每個流程需明確定義目標、工具呼叫順序與預期外部效應。
- 每個工作流程的環境不變量（physical environment invariants），例如帳戶餘額、資料庫記錄唯一性、Git 樹狀態等。
- 完整的線路層級效應歷史紀錄能力，包括每個工具呼叫的請求、回應、錯誤碼與遠端實際產生的副作用。
- 故障情境清單，至少涵蓋 PRE_MUTATION、DURING_MUTATION 與 POST_MUTATION_PRE_ACK 三個核心執行邊界。

**運算前置條件**
- 可重複執行相同種子（identical seeds）的代理執行環境，以支援反事實配對試驗。
- 足夠的 LLM 推論預算：以本文規模為例，單一模型與框架組合可能需要數千次執行（如 5,760 次執行 / 2,880 對配對試驗）。
- 獨立的沙箱環境或模擬外部服務，避免在評估過程中對生產系統產生真實副作用。

**技能前置條件**
- 熟悉分散式系統概念，尤其是冪等性、確認遺失、兩階段提交與補償交易。
- 具備 LLM 代理框架實作經驗，能夠設計工具描述、錯誤處理邏輯與重試策略。
- 能夠設計與維護預言機（oracle），包括狀態預言機與效應歷史預言機的程式化驗證邏輯。

### 實作步驟建議

1. **盤點關鍵工作流程與外部變更**
   從生產日誌或產品規格中挑選具有高業務衝擊的工作流程，標記每個流程中會產生遠端狀態修改的關鍵工具呼叫。

2. **建立環境狀態預言機**
   針對每個工作流程定義成功執行後必須滿足的物理環境不變量，例如「帳戶只被扣款一次」、「工單編號唯一」、「canary 部署版本正確」。

3. **建立線路層級效應歷史預言機**
   攔截並記錄所有對外部系統的實際呼叫，計算重複效應率（DER）、遺失效應率（MER）與恰好一次執行率（EOR）。

4. **設計反事實配對試驗**
   對每個工作流程使用相同隨機種子執行兩次：一次為無故障的對照執行（Control），一次為注入特定故障的故障執行（Faulted run）。

5. **計算標稱能力與條件式恢復成功率**
   先計算對照執行的標稱成功率（Ctrl），再僅針對標稱成功的配對計算 CRSR，避免將任務能力與恢復能力混為一談。

6. **按執行階段注入故障並分析**
   分別在 PRE_MUTATION、DURING_MUTATION 與 POST_MUTATION_PRE_ACK 階段注入故障，觀察恢復表現是否隨階段變化。

7. **導入並驗證恢復機制**
   根據實證結果選擇適當機制，例如伺服器端冪等性鍵、執行後驗證、零權限日誌記錄或補償交易，並重新執行配對試驗以量化改善幅度。

8. **整合至持續評估管線**
   將 UndoBench 評估納入模型選型、提示工程迭代與代理框架升級的 CI/CD 閘道，確保新任務能力不會以犧牲恢復安全性為代價。

### 潛在風險與注意事項

- **誤把標稱成功率當成整體可靠性**
  若只看端到端任務成功指標，可能會高估代理在生產環境中的安全性。務必同時報告 CRSR、DER、MER 與 EOR。

- **預言機設計不完整導致誤判**
  若狀態預言機只檢查最終字串輸出而未檢查外部系統狀態，可能遺漏重複外部效應。建議同時使用雙重狀態與效應歷史預言機。

- **故障注入過度簡化**
  僅測試連線逾時而忽略回應封包遺失、部分變更或補償失敗，會低估實際風險。應涵蓋外部變更生命週期的多個執行邊界。

- **冪等性並非萬靈丹**
  論文顯示在 DURING_MUTATION 階段，每次呼叫冪等性與零權限日誌記錄在複合工作流程上可能失效。需針對具體階段選擇機制，而非一概採用冪等性。

- **商業 API 模型與開放權重模型行為差異**
  即使兩者在標稱任務上表現相近，恢復行為可能不同。建議在模型切換或升級時重新執行 UndoBench 評估。

- **沙箱與生產環境落差**
  模擬外部服務的行為可能與真實系統不同，特別是競爭條件與部分失敗語義。應定期以生產影子流量或分段環境驗證預言機假設。

### 與其他技術的整合建議

- **與現有代理基準測試互補**
  UndoBench 不應取代 AgentBench 或 WebArena 等任務導向基準測試，而是作為補充，專門評估故障恢復與執行安全性。

- **與可觀測性平台整合**
  將效應歷史預言機的輸出對接至現有分散式追蹤（distributed tracing）與日誌聚合系統，使生產環境也能持續監控 DER 與 EOR。

- **與冪等性與 Saga 模式整合**
  對於 POST_MUTATION_PRE_ACK 階段，優先採用伺服器端冪等性鍵；對於 DURING_MUTATION 階段，可考慮結合 Saga 補償交易與執行後驗證。

- **與模型評估與 CI 管線整合**
  將 UndoBench 作為模型選型、提示版本控制與代理框架升級的閘道測試，確保新任務能力不會伴隨恢復能力退化。

- **與模擬環境整合**
  使用服務虛擬化（service virtualization）或契約測試工具建立可注入故障的外部服務替身，降低在生產環境直接測試的風險。

### 給不同背景讀者的閱讀建議

**給初學者**
建議先從論文的動機與訂閱續約範例讀起，理解為何「任務成功」不等於「故障後安全恢復」。不必急著深入數學公式，重點掌握反事實配對試驗、條件式恢復成功率（CRSR）與三個執行邊界（變更前、變更期間、提交後確認前）的直覺意義，再回頭看預言機與指標定義。

**給 AI 工程師**
請聚焦於第 2 節的問題形式化、故障模型與評估指標，並仔細研究如何將線路層級效應歷史預言機實作進現有代理框架。實務上最關鍵的是把相同種子對照執行與故障執行配對自動化，並正確計算 CRSR 而非僅看整體成功率。論文中不同恢復典範（樸素重試、冪等性、日誌）的階段相依表現，可直接作為選型依據。

**給研究人員**
本論文的核心貢獻在於將任務能力與恢復能力解耦，並提出階段相依的恢復評估架構。建議深入檢視其形式化定義、五種執行邊界分類，以及雙重預言機的設計如何解決傳統終端獎勵評估無法區分重複效應與安全停機的問題。後續可延伸至更複雜的補償交易、多代理協調或長期記憶機制對恢復行為的影響。

**給產品經理**
請把本文視為評估 AI 代理是否「可上線」的風險檢查清單。重點關注標稱成功率（83.54%）與條件式恢復成功率（46.72%）之間的巨大落差，以及樸素重試導致 53.33% 重複外部效應的發現。這些數字意味著即使代理在示範環境中表現良好，仍可能在生產環境中造成重複計費、重複工單或資料損毀，因此需要將 UndoBench 類型的評估納入上線前的驗收標準。
