## ⚡ TL;DR

原始DCI在大規模語料庫上操作緩慢且不穩定，傳統檢索介面也難以讓代理靈活驗證跨文件證據。

BrowseComp-Plus達71.2%，較DCI提升8.3點，並可擴展至千萬級語料庫。

## 深度分析

#### 方法論解析

Agentic search（代理式搜尋）的核心張力在於 scale（規模）與 control（控制）之間的權衡。傳統 Retrieval-augmented generation（RAG，檢索增強生成）系統透過 retriever（檢索器）將語料庫壓縮為 ranked top-k list（前 k 項排序列表），雖然具備良好的 corpus-level exploration（語料庫層級探索）能力，但其暴露給 agent（代理）的介面僅限於 ranked results（排序結果）、snippets（片段）或 bounded document views（受限文件檢視），無法支援跨文件的任意重組、比較與 verification（驗證）。

Direct Corpus Interaction（DCI，直接語料庫互動）試圖解決此問題，它提供 shell-executable corpus operations（Shell 可執行語料庫操作）如 grep、rg、find、read、cat 等，讓代理能對 evidence（證據）進行細粒度操作。然而，當 DCI 直接套用於 full corpus（完整語料庫）時，terminal-style DCI commands（終端機式 DCI 指令）會隨語料庫增長而變得緩慢且不穩定，容易發生 timeouts（逾時），且廣泛搜尋會回傳過多無關匹配，狹隘搜尋則可能遺漏關鍵證據。

DR-DCI 的核心設計是將 retrieval（檢索）重新定義為 agent-callable action（代理可呼叫動作），具體化為 pull（拉取）此一 workspace expansion action（工作區擴展動作）。在 inference（推論）過程中，代理並非直接對全語料庫執行終端機指令，而是透過 pull 搭配 query（查詢）與 retrieval budget（檢索預算），從完整語料庫中將 candidate documents（候選文件） materialize（具現化）至一個 evolving workspace（演進式工作區）。隨後，代理在這個 local workspace（本機工作區）內執行 DCI 操作，進行搜尋、filtering（過濾）、comparison（比較）與 verification（驗證）。

此方法論的關鍵在於將 corpus-level candidate discovery（語料庫層級候選發現）與 workspace-level document interaction（工作區層級文件互動）解耦：前者由 retriever-level recall（檢索器層級召回率）負責，確保探索的可擴展性；後者由 DCI-style precision（DCI 風格的精確度）負責，保留代理對證據進行靈活操作的能力。代理可根據逐漸演化的 evidence constraints（證據限制），交替執行 pull 以擴展工作區，並在當前工作區內進行 cross-document operations（跨文件操作），形成可擴展的語料庫互動迴路。

此外，作者提出 workspace-preserving context reset（保留工作區的上下文重設）機制。即使原始推理軌跡未能有效利用已具現化的證據，只要工作區狀態被保留，重置推理上下文後仍可從中獲益。這顯示 materialized workspace（已具現化工作區）本身具有獨立於推理鏈的證據價值。

#### 實驗數據解讀

論文在三個大規模設定下進行驗證，數據呈現出明確的規律：

1. BrowseComp-Plus 基準測試：DR-DCI 達到 71.2% 的 accuracy（準確率），相較於 raw DCI（原始 DCI）與 ablated variants（消融變體）提升最高達 8.3 個百分點。同時，tool usage（工具使用量）、wall time（實際經過時間）與 estimated cost（估計成本）均顯著下降，顯示動態工作區不僅提升效能，也改善效率。引入 workspace-preserving context reset 後，準確率進一步提升至 73.3%，證明已拉取的工作區即使脫離原始推理上下文，仍蘊含高價值證據。

2. Corpus-scaling experiments（語料庫規模擴展實驗）：作者透過加入 FineWeb 的干擾資料，將語料庫從 100K 擴增至 10M 份文件，同時固定測試問題與其支撐文件。在此設定下，DR-DCI 能將可見工作區維持在有限範圍內，表現平穩退化；相對地，raw DCI 因重複執行 full-corpus terminal commands（全語料庫終端機指令）而變得不可行，BM25（經典稀疏檢索演算法）的表現亦大幅衰退。這直接證實了 DR-DCI 在無關語料總量增加時的穩健性。

3. Wiki-18 QA（20M 規模、file-per-document（每份文件一個檔案）設定）：在此極大語料庫中，DR-DCI 於六項基準的平均分達到 63.0，超越 retrieval-based baselines（基於檢索的基線模型）與 trained search-agent baselines（經過訓練的搜尋代理基線模型）。此結果顯示該介面設計具備跨領域轉移能力，不限於 BrowseComp-Plus 的特定分佈。

4. Ablation analysis（消融分析）：ranked previews（排序預覽）能協助代理優先處理高潛力候選文件，但單靠排序並不足夠；inter-document DCI（跨文件 DCI）才是比較候選、結合 lexical constraints（詞彙限制）與驗證 exact evidence spans（精確證據片段）的關鍵。這說明 DR-DCI 的價值不僅在於「把檢索當成入口」，更在於「把工作區當成操作場域」。

#### 與現有研究的比較

與標準 RAG 的差異：傳統 RAG 將 retrieval 視為一次性的上下文選擇模組，檢索結果直接決定模型能讀取什麼。DR-DCI 則將 retrieval 轉化為環境管理操作，候選文件被具現化為持續性的 workspace（工作區）狀態，使後續工具呼叫能跨文件搜尋、比較與驗證。這從「檢索決定輸入」轉變為「檢索擴展環境」。

與 Raw DCI 的差異：Raw DCI 讓代理直接操作完整語料庫，缺乏 global ranking prior（全局排序先驗）。DR-DCI 透過 pull 機制引入 retriever-mediated interfaces（檢索器中介介面）的優勢，在維持 DCI 精細操作能力的同時，解決了全語料庫掃描的規模瓶頸。

與現有 Agentic search（代理式搜尋）系統的比較：ReAct、WebGPT、IRCoT、FLARE、Self-RAG 等方法雖然允許模型交錯推理與搜尋，但其互動仍圍繞檢索器暴露的介面（如片段、pagination（分頁）、document-opening interfaces（文件開啟介面））。DR-DCI 的獨特之處在於讓代理在 materialized workspace 內執行任意 cross-document operations（跨文件操作），例如追蹤 bridge entities（橋接實體）、結合 lexical constraints（詞彙限制）進行多條件過濾，這是傳統「開啟-閱讀-關閉」模式難以支援的。

限制與定位：DR-DCI 並非試圖改進 BM25（經典稀疏檢索演算法）或 ColBERT（晚期互動神經檢索模型）等檢索器的排名機制，而是探討「檢索結果應如何被組織為代理的工作空間」。因此，其效能天花板仍受 pull 階段檢索器 recall（召回率）的束縛；若關鍵文件未在初始檢索中進入工作區，後續 DCI 操作亦無從發揮。此外，工作區的儲存與管理雖然比全語料庫操作輕量，但仍需額外的狀態維護成本。

#### 可重現性評估

本論文目前為 preprint（預印本）形式。從提供的文本脈絡來看，作者並未明確宣告原始碼、模型權重或完整實作介面的開源釋出。實驗所使用的資料集多為已公開資源：BrowseComp-Plus（Chen et al., 2025）、FineWeb（Penedo et al., 2024）以及 Wiki-18 QA 設定，這些外部資料具備一定可取得性。

然而，DR-DCI 的核心可重現性挑戰在於系統層面的實作細節：pull 動作與後端檢索器的整合方式、workspace 的沙箱化實作、終端機式工具（rg、grep、find 等）的 API 封裝、agent 的 prompt engineering（提示工程）以及工作區狀態在推理迴路中的生命週期管理。這些介面層的設計選擇對結果影響重大，但文中未提供足夠的偽代碼或架構圖細節。若作者未來釋出原始碼與容器化環境，將大幅提升社群復現與延伸研究的可能性。

#### 未來研究方向

1. 自適應檢索預算（Adaptive Retrieval Budget）：當前 pull 動作使用固定的 retrieval budget（檢索預算）。未來可根據查詢複雜度、工作區內證據飽和度或代理的不確定性，動態調整每次 pull 的文件數量，以在 recall（召回率）與成本間取得更佳平衡。

2. 可學習的 Pull 策略：將「何時執行 pull、何時在工作區內搜尋」視為決策問題，透過強化學習或啟發式策略訓練代理，使其具備更精準的 corpus-level exploration（語料庫層級探索）能力，而非僅依賴靜態規則。

3. 階層式工作區（Hierarchical Workspace）：對於 10M 以上甚至更大規模語料庫，可設計多層級具現化機制——先 pull 文件集合，再於集合內 pull 精細段落，降低單一工作區的負載。

4. 工作區壓縮與摘要：隨著 pull 次數增加，工作區可能膨脹至超出上下文長度限制。研究如何對已具現化文件進行選擇性壓縮或摘要，同時保留跨文件比較所需的關鍵細節，將是重要課題。

5. 與長上下文模型（Long-context Models）的協同：隨著大型語言模型上下文窗口擴增，需重新評估 optimal workspace size（最佳工作區大小）。未來可探討在極長上下文下，DR-DCI 是否可減少 pull 次數，或反而利用更大工作區進行更激進的跨文件推理。

6. 多代理共享工作區：將 workspace（工作區）擴展為多個 search agents（搜尋代理）可協作讀寫的共享狀態空間，支援分工檢索與集體驗證，可能進一步提升 evidence resolution（證據解析）的深度與廣度。

7. 超越純文字語料庫：目前 DCI 主要針對文字文件設計。將動態工作區概念擴展至結構化資料（如資料庫、知識圖譜）或多模態語料庫，將開啟新的應用場景。

## 論文問答

**Q1：代理式搜尋中存在什麼根本張力，促使 DR-DCI 的誕生？**

A：代理式搜尋的核心挑戰在於規模與控制之間的根本張力：代理必須能夠在龐大語料庫中發現有希望的候選文件，同時又必須在找到證據後與之進行精確互動。傳統的檢索增強生成系統雖然能透過 BM25 或 ColBERT 等檢索器中介介面實現可擴展的候選發現，但這些介面僅以排序結果或受限文件檢視的形式暴露證據，限制了代理重新組織材料、執行跨文件操作以及驗證複雜限制條件的能力。直接語料庫互動雖然提供了精細的證據操作能力，卻因全語料庫終端機指令在規模擴大時變得緩慢且不穩定而難以擴展，因此亟需一種能同時兼顧語料庫層級探索規模性與工作區層級操作精確度的新框架。

**Q2：現有的檢索器中介介面與原始 DCI 為何無法有效解決大規模語料庫上的代理式搜尋問題？**

A：現有的檢索器中介介面（例如 BM25 或 ColBERT）雖然在候選發現方面具備良好的擴展性，但它們通常只向前 k 項排序列表或片段的形式呈現證據，這種受限文件檢視使代理難以進行跨文件比較、追蹤橋接實體或驗證精確證據片段。另一方面，原始 DCI 透過 Shell 可執行語料庫操作（如 grep、find、cat 等）賦予代理極高的靈活性，但當語料庫從十萬級成長到百萬甚至千萬級文件時，全語料庫終端機指令會變得極度緩慢且容易逾時，導致效能與效率雙雙下降。因此，這兩種範式各自在規模性或精確度上存在明顯缺陷，無法單獨滿足大規模代理式搜尋對於可擴展探索與精細互動的雙重需求。

**Q3：為何讓代理直接與語料庫互動如此重要，而標準檢索介面缺少了哪些關鍵能力？**

A：讓代理直接與語料庫互動之所以重要，是因為許多複雜的推理任務需要代理在發現候選文件後，能夠以任意粒度搜尋、組合詞彙限制、比較不同文件內容，並透過靈活的跨文件操作來驗證假設。標準檢索介面通常僅提供排序結果或分頁式的文件開啟介面，這種設計本質上將證據的呈現方式綁定在檢索器的輸出格式上，導致代理無法根據推理過程中的動態需求重新組織材料或在多份文件間建立關聯。直接語料庫互動則彌補了這一缺口，它允許代理執行終端機式 DCI 指令來進行工作區層級的文件互動，從而實現更細緻且符合推理邏輯的證據解析。

**Q4：DR-DCI 的核心機制是什麼，它與標準 RAG 和原始 DCI 有何本質區別？**

A：DR-DCI 的核心機制是將檢索重新定義為一種代理可呼叫的工作區擴展動作（pull），而非僅作為一次性上下文選擇模組；代理透過 pull 從完整語料庫中將候選文件具現化到演進式本機工作區，再於其中執行終端機式 DCI 指令。這與標準 RAG 有本質區別，因為標準 RAG 中檢索決定了模型讀取的固定上下文，而 DR-DCI 中的檢索則是動態修改代理的環境狀態，使文件能夠在工作區中持續存在並供後續操作使用。同時，它也不同於原始 DCI，因為原始 DCI 直接對全語料庫執行操作，而 DR-DCI 透過檢索器引導的方式將操作範圍限制在動態建構的工作區內，從而分離了規模性問題與精確度問題。

**Q5：何謂「工作區擴展」觀點，DR-DCI 如何藉此分離規模性與精確度的挑戰？**

A：「工作區擴展」觀點是指將檢索視為一種逐步建構與擴展代理工作區的過程，而非單純的證據介面；在此框架下，檢索負責語料庫層級探索，將相關文件拉取到本機工作區，而 DCI 則負責工作區層級的文件互動，例如搜尋、過濾、比較與驗證。這種設計巧妙地將規模性挑戰交由檢索器處理，利用檢索器層級召回率來確保在數百萬文件中快速定位候選文件，同時讓 DCI 專注於局部精確度，無需每次指令都掃描全語料庫。透過在 pull 與本地操作之間交替執行，代理能夠遵循一個可擴展的語料庫互動循環，既保留了檢索的規模優勢，又維持了直接互動的精細控制能力。

**Q6：DR-DCI 有哪些關鍵設計選擇，為何排序預覽與跨文件 DCI 對效能至關重要？**

A：DR-DCI 的關鍵設計選擇包括將檢索作為工作區管理機制、提供排序預覽以協助代理優先處理新候選文件，以及保留跨文件 DCI 能力以支援工作區內的多文件操作。排序預覽之所以重要，是因為它為代理提供了檢索器的全域排序先驗，幫助代理在動態擴展工作區時判斷哪些文件最可能包含相關證據，從而提升探索效率。然而，僅有排序預覽並不足夠，跨文件 DCI 才是讓代理能夠比較候選文件、組合不同來源的限制條件，並驗證超越檢索器排序順序的證據的關鍵；消融分析顯示，這兩項設計對於實現高效能的證據解析缺一不可。

**Q7：作者使用了哪些評測基準與實驗設定來驗證 DR-DCI 的有效性？**

A：為了全面驗證 DR-DCI，作者設計了三個大規模實驗設定：首先在 BrowseComp-Plus 基準上測試動態工作區擴展相較於原始 DCI 與靜態工作區消融變體的優勢；其次進行語料庫規模擴展實驗，透過加入隨機抽樣的 FineWeb 網站作為干擾文件，將語料庫從十萬份擴展至一千萬份文件，以直接檢驗方法在無關語料質量增加時的穩定性。最後，作者在一個兩千萬規模的 Wiki-18 每份文件一個檔案問答設定上進行評估，以確認該介面是否能轉移至極大規模的文件集合，並與基於檢索的基線模型以及經過訓練的搜尋代理基線模型進行比較。

**Q8：DR-DCI 的主要量化結果為何，與基線模型相比表現如何？**

A：在 BrowseComp-Plus 上，DR-DCI 達到了 71.2% 的準確率，相較於原始 DCI 與消融變體提升了最高達 8.3 個百分點，同時降低了工具使用量、實際經過時間與估計成本；若搭配保留工作區的上下文重設機制，準確率更可進一步提升至 73.3%。在語料庫規模擴展實驗中，當文件數量從十萬成長至一千萬時，DR-DCI 仍能保持有效且穩定地運作，而原始 DCI 則因重複執行全語料庫終端機搜尋而變得不可行，BM25 的表現也顯著較差。在兩千萬規模的 Wiki-18 QA 設定中，DR-DCI 在六個基準上平均獲得 63.0 分，超越了基於檢索的基線模型與經過訓練的搜尋代理基線模型，顯示其具備良好的跨領域擴展能力。

**Q9：消融分析揭示了哪些關於元件必要性的重要發現？**

A：消融分析明確指出，排序預覽與跨文件 DCI 是 DR-DCI 達成高效能的兩大關鍵元件，缺少任一都會顯著削弱代理的證據解析能力。具體而言，排序預覽幫助代理在擴展工作區時優先處理最具潛力的候選文件，但僅依賴檢索排序並無法完成複雜的推理任務；跨文件 DCI 則提供了在工作區內比較文件、組合詞彙限制與驗證精確證據片段的能力，這是單純檢索介面無法替代的。這些結果證明，檢索排序應該引導而非取代代理的調查過程，而工作區內的跨文件操作對於解決需要多源證據協同的複雜查詢至關重要。

**Q10：相較於傳統搜尋代理，DR-DCI 在哪些實際應用場景中最能發揮優勢？**

A：DR-DCI 特別適合需要大規模證據驗證與複雜多文件推理的場景，例如法律研究中的跨判例比對、醫學文獻中的多源臨床證據整合，以及金融監管中的分散式資訊交叉核實。在這些情境中，代理不僅需要從數百萬份文件中召回相關材料，更必須在工作區內對不同文件執行精確的詞彙限制比較、追蹤橋接實體，並驗證各項條件是否同時滿足。傳統的檢索增強生成系統往往受限於固定長度的前 k 項排序列表，難以支援這種反覆推敲與重組證據的過程，而 DR-DCI 透過動態工作區擴展與終端機式操作，為這類高風險、高複雜度的決策任務提供了更靈活且可擴展的解決方案。

**Q11：DR-DCI 的設計理念可能如何影響未來代理式搜尋產品或檢索系統的開發方向？**

A：DR-DCI 提出的「檢索即工作區管理」典範可能促使未來產品從「檢索作為上下文供給」轉向「檢索作為環境修改」，即將檢索結果視為代理可操作與持續互動的持久狀態，而非一次性消耗的靜態輸入。這種轉變意味著搜尋代理的產品設計需要更重視工具呼叫介面的標準化，讓代理能夠透過 pull 等動作動態擴展其工作區，並在工作區內執行多樣化的終端機式指令。此外，這也暗示未來的檢索系統不應僅追求排序準確率，還需提供有利於代理後續操作的結構化預覽與跨文件操作介面，從而打造更具互動性與自主性的搜尋體驗。

**Q12：工作區擴展典範對檢索增強生成與代理設計領域可能產生哪些更廣泛的影響？**

A：工作區擴展典範為檢索增強生成領域提供了一個調和召回率與精確度的新框架，證明兩者不必在單一介面中相互妥協，而是可以透過分工讓檢索器負責語料庫層級召回、讓 DCI 負責工作區層級精確操作。這種分離式設計可能啟發新一代代理架構，使其具備更長期的證據工作記憶與結構化的環境互動能力，而非僅依賴語言模型的上下文視窗來暫存檢索結果。更廣泛地說，這項工作確立了「代理可呼叫的環境操作」在大型語料庫互動中的核心地位，為未來開發更複雜的科學研究代理、程式碼搜尋代理與多模態知識探勘系統奠定了重要的介面設計基礎。

**Q13：作者承認 DR-DCI 框架存在哪些限制或約束條件？**

A：儘管 DR-DCI 在實驗中表現出色，其效能仍部分依賴底層檢索器的品質，若初始 pull 階段的檢索器層級召回率不足，後續的工作區操作將難以補救遺漏的關鍵文件。此外，隨著工作區在推論過程中不斷擴展，如何有效管理工作區大小以避免上下文視窗超載或工作區膨脹，仍是實際部署時需要仔細權衡的問題。框架目前也假設代理具備足夠的能力來決定何時執行 pull、何時執行本地 DCI 操作，這對於推理能力較弱的模型可能構成挑戰，暗示該方法在極端資源受限或模型能力較低的場景中可能需要額外的引導機制。

**Q14：在哪些條件或失敗案例中，DR-DCI 可能難以維持效能或出現顯著退化？**

A：DR-DCI 可能在證據高度分散且需要極多次 pull 才能完整收集的任務中面臨挑戰，因為頻繁的工作區擴展會增加工具使用量與推論步驟，進而拉高實際經過時間與估計成本。如果目標證據涉及極為罕見的橋接實體，且這些實體在語料庫中出現次數極多，檢索器可能難以在有限的檢索預算內篩選出真正相關的文件，導致工作區充斥雜訊。此外，當查詢所需的跨文件限制條件過於複雜，而代理無法有效組合終端機式指令時，即使工作區內已包含正確文件，本地 DCI 操作也可能因為代理的規劃失誤而無法成功解析證據。

**Q15：基於這項工作，未來有哪些自然延伸的研究方向或改進空間？**

A：未來研究可以探索更智慧的工作區管理策略，例如根據代理當前推理狀態動態調整檢索預算，或開發學習式的工作區壓縮與淘汰機制，以在擴展至億級文件時維持效率。另一個有潛力的方向是將 DR-DCI 與經過訓練的搜尋代理基線模型結合，讓代理透過強化學習或模仿學習來優化 pull 與本地 DCI 指令的決策序列，而非僅依賴提示工程。此外，該框架的核心理念也可以擴展至多模態語料庫（如圖像、影片或程式碼庫），透過設計對應的具現化操作與工作區互動介面，使代理能夠在更廣泛的知識領域中實現可擴展的直接語料庫互動。

## 實務應用指南

### 適用場景

1. **法律與合規盡職調查**：律師或法務團隊需在數百萬份合約、判決書與法規中交叉比對條款、日期與當事人。DR-DCI 可先透過檢索將可能相關的文件 **Pull** 進本機工作區，再由代理使用 `grep`、`diff` 等終端機式 DCI 指令驗證精確證據片段與跨文件約束，避免人工逐一開啟。
2. **企業內部知識庫問答**：大型企業的技術文件、會議記錄與維運日誌規模常達百萬級。當員工詢問需要跨文件比對版本差異、追蹤橋接實體（如專案代號在不同部門文件中的指涉）時，DR-DCI 的動態工作區擴展能逐步收斂相關檔案，並以跨文件 DCI 完成精確解析。
3. **學術文獻綜述與事實查核**：在千萬級論文語料庫中進行系統性文獻回顧時，研究者可讓代理依據演進式查詢多次 **Pull** 候選文獻，於工作區內比較實驗數據、方法學與結論，驗證假設是否成立。
4. **資安威脅情資與日誌調查**：SOC 分析師面對千萬級安全日誌與威脅情資報告，可先以檢索器縮小時間範圍與攻擊指標（IoC），再由代理在工作區內執行跨檔案 `rg` 與 `find`，比對攻擊鏈證據，避免全語料庫掃描造成的嚴重逾時。
5. **大型電商商品規格驗證**：當平台商品頁面達數千萬筆，代理可動態 **Pull** 同類別候選商品至工作區，跨文件比較規格參數、價格區間與賣家聲明，自動偵測不一致或誇大宣稱。

### 實作前置條件

- **資料條件**：語料庫需已完成索引（支援 BM25、ColBERT 或密集向量索引），且文件內容為可搜尋文字格式；需具備穩定的檢索 API 供代理呼叫。若為企業內部文件，需確保權限控管可與 **Pull** 動作整合。
- **運算條件**：需有檢索索引伺服器（支援百萬至千萬級文件）、代理執行環境（具備 Shell 可執行語料庫操作能力的 LLM API 或本地模型），以及足夠的上下文長度（建議 128K tokens 以上，以容納工作區中繼資料與排序預覽）。
- **技能條件**：團隊需熟悉檢索系統建置（如 Elasticsearch、Milvus、Faiss）、具備 LLM 代理開發經驗（Function Calling / Tool Use），並具備基礎 DevOps 能力（容器化、路徑隔離、指令逾時設定）。

### 實作步驟建議

1. **建構檢索層與 `Pull` 介面**：為語料庫建立混合檢索索引（稀疏 + 密集），並封裝 **Pull** 為代理可呼叫動作，允許代理依據檢索預算（retrieval budget）具現化前 k 項候選文件至本機工作區。
2. **設計工作區檔案系統**：在代理環境中建立隔離的工作目錄，確保 **Pull** 寫入的檔案保留來源識別與排序分數（供排序預覽使用），並限制代理僅能在此目錄執行終端機式 DCI 指令。
3. **實作 DCI 工具組**：提供代理可呼叫的工具：`rg` / `grep`（跨檔案搜尋）、`find`（檔案篩選）、`read` / `cat`（讀取內容）、`diff`（跨文件比較）。為每項工具設定執行逾時與輸出長度上限，防止單次呼叫阻塞。
4. **開發代理決策迴圈**：設計推論迴圈讓代理交替執行：(a) 評估目前證據缺口 → (b) 決定呼叫 **Pull** 擴展演進式工作區，或執行本地 DCI 操作 → (c) 驗證證據並決定是否進行保留工作區的上下文重設（workspace-preserving context reset）。
5. **強化排序預覽與跨文件機制**：在 **Pull** 回傳結果中加入 ranked previews（標題、摘要、相關分數），並確保 DCI 工具支援跨文件操作（如多檔案聯合過濾、比較），這兩項是論文消融分析中確認的關鍵設計。
6. **規模化測試與成本監控**：從 100K 文件開始驗證，逐步擴增至目標規模（如 10M 或 20M）。持續監控工具使用量、實際經過時間與估計成本，依據語料庫規模擴展實驗結果調整檢索預算與工作區上限。

### 潛在風險與注意事項

- **全語料庫掃描風險**：若代理繞過 **Pull** 直接對完整語料庫執行終端機指令，將導致嚴重逾時與系統不穩定。必須透過檔案系統權限與路徑隔離，強制代理僅能在工作區內操作。
- **工作區膨脹**：連續 **Pull** 可能使工作區過大，超出上下文窗口或檔案系統負荷。應設定工作區文件數量上限，或實作淘汰機制（如 LRU），並在代理提示中鼓勵優先使用排序預覽篩選，減少無效擴展。
- **檢索召回不足**：若檢索器層級召回率過低，關鍵證據可能永遠不會進入工作區。建議採用混合檢索，並允許代理以不同查詢多次 **Pull**，避免單次檢索偏差造成答案遺漏。
- **工具呼叫成本累積**：頻繁的跨大檔案 `grep` 或 `rg` 會累積延遲與 API 成本。需設定單次呼叫逾時、輸出截斷，並在介面設計上讓代理先讀取排序預覽，再決定深入哪些文件。
- **上下文重設遺失狀態**：標準上下文重設可能清空代理記憶，但論文顯示保留工作區的上下文重設可進一步提升準確率。實作時應區隔「推理軌跡」與「已具現化文件」，確保重設時後者不被清除。

### 與其他技術的整合建議

- **與現有 RAG 管線整合**：將 DR-DCI 作為檢索增強生成的「深度驗證層」。簡單查詢由標準 RAG 直接回答；當系統偵測到需要跨文件比對、精確驗證或複雜約束時，移交給 DR-DCI 代理進行工作區層級文件互動。
- **與向量資料庫整合**：將 **Pull** 動作對接至現有向量資料庫（如 Pinecone、Weaviate、Milvus），利用其混合搜尋與中繼資料過濾能力召回候選，再將結果寫入代理工作區，無需重建索引。
- **與企業搜尋平台整合**：對接既有企業搜尋（如 Elasticsearch、OpenSearch）作為稀疏檢索層，保留現有權限控管與文件存取紀錄，僅在代理層疊加 DCI 的靈活操作能力。
- **與 LLM 編排框架整合**：可將 DR-DCI 封裝為 LangChain、LlamaIndex 或 AutoGen 中的客製化 Agent Tool，專責擔任「證據調查員」角色，與其他代理（如摘要代理、生成代理）協同工作。

### 給不同背景讀者的閱讀建議

- **初學者**：請先掌握核心概念——「先縮小範圍、再精確操作」。把 DR-DCI 想像成圖書館研究：檢索系統幫你從百萬藏書中挑出相關書架（**Pull**），你再親自在書架間翻閱、比對、做筆記（DCI）。建議重點閱讀論文的 Introduction，理解為何直接對全館翻書（原始 DCI）在規模變大時會變慢且不穩定。
- **AI 工程師**：請聚焦於介面設計與系統架構。仔細研讀 **Pull** 動作與終端機式 DCI 指令的 API 定義、工作區狀態管理、逾時與檢索預算控制機制。實作時務必參考消融分析章節，理解排序預覽與跨文件 DCI 對準確率的具體貢獻，並據此調整工具提示（tool descriptions）與代理提示詞。
- **研究人員**：建議關注論文對「檢索作為環境管理」的重新概念化，以及保留工作區的上下文重設之實驗設計。深入分析 BrowseComp-Plus 與 Wiki-18 QA 的語料庫規模擴展實驗設定，評估此方法對其他代理推理任務（如科學發現、程式碼考古）的泛化可能性。
- **產品經理**：請從商業價值與成本效益角度切入。論文顯示 DR-DCI 在提升準確率的同時降低工具使用量與估計成本，這意味著更高的回答品質與更低的營運支出。請評估貴司知識庫規模是否達到「原始 DCI 開始不穩定」的臨界點（約 100K 以上文件），並規劃分階段導入：先以高價值、高複雜度的查詢場景（如法務、研發）為試點。
