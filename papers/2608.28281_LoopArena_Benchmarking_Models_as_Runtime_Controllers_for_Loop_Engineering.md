## ⚡ TL;DR

現有端到端基準無法區分迴圈引導與程式設計代理能力，難以評估模型作為執行階段控制器的表現。
迴圈競技場以控制器–工作者雙代理框架搭配三類互補設定，評估單步決策、任務片段與完整任務的控制能力。
嚴格成功率僅24.69%，改善空間仍大；第二類省64.4%成本，與第三類排序一致，ρ=0.9747。

## 摘要翻譯

Loop Engineering（迴圈工程）正逐漸成為一種以程式設計代理（coding agent）為中心來組織開發工作的實務。實務工作者不再手動撰寫每個提示詞，而是設計能監控進度、指派工作、執行檢查，並決定代理下一步該做什麼的迴圈。即使程式設計代理本身能力出色，迴圈仍可能採信過時的進度註記、跳過必要的驗證、將預算花在錯誤方向，或在可安全提交前停止。然而，單次端到端執行（end-to-end run）的最終結果，無法判斷成功或失敗究竟反映的是迴圈的引導，還是程式設計代理執行任務的能力。我們提出 LoopArena（迴圈競技場），一個用於評估單一模型能在多大程度上引導獨立的程式設計代理完成長時間執行任務（long-running task）的基準測試。受評模型即為 Controller（控制器）：在每個程式設計回合（coding round）結束後，它會收到該次執行的結構化摘要（structured summary），並指示 Worker（工作者）下一步該做什麼或驗證什麼，或決定是否停止。LoopArena 在三種互補設定中評估此能力，這些設定在執行範圍（execution scope）與成本上有所不同。Type I（第一類評估設定）在不執行 Worker 的前提下，透過經執行驗證的問題（execution-validated questions），對下一步迴圈合約（Loop Contract）選擇進行評分。Type II（第二類評估設定）在完整任務（full task）的選定片段（selected slice）上執行重複控制（repeated control），而 Type III（第三類評估設定）則從初始狀態（original state）評估成對的完整任務。在完整任務上，觀測到的最佳嚴格成功率（Strict Success Rate）為 24.69%，顯示長視野（long-horizon）迴圈控制仍有大幅改善空間。在不同 Controller 之間，估計推理成本（estimated inference cost）的成對減少量（paired reduction）平均為 64.4%，且 Type II 在主要核心指標（main Core criterion）下產生了相似的排序（史皮爾曼等級相關係數 ρ，Spearman's ρ=0.9747）。我們在 https://github.com/AMAP-ML/LoopArena 釋出基準資料（benchmark data）與評估程式碼（evaluation code）。

### 核心貢獻（3～5點）
- 提出 LoopArena（迴圈競技場）基準測試，用於評估單一模型作為執行階段控制器（runtime controller），引導獨立程式設計代理完成長時間執行任務的能力。
- 設計 Controller（控制器）–Worker（工作者）架構：Controller 在每個程式設計回合後根據結構化摘要決定下一步指令或停止，Worker 則是固定不變的程式設計代理。
- 提出三種互補的評估設定——Type I、Type II、Type III——分別從下一步迴圈合約選擇、選定片段上的重複控制，以及成對完整任務的端到端執行進行評估。
- 實證顯示完整任務的最佳嚴格成功率僅 24.69%，且 Controller 可平均降低 64.4% 的估計推理成本；Type II 與 Type III 在主要核心指標下具有高度排序一致性（Spearman's ρ=0.9747）。
- 公開釋出基準資料與評估程式碼，供後續研究重現與擴展。

### 適合對象
適合對自動化軟體工程、程式設計代理、多代理系統、迴圈工程，以及長視野任務控制有興趣的研究者與實務工作者；特別適合需要設計或評估能持續監控進度、指派工作、執行檢查並決策停止時機的執行階段控制器的開發者與基準測試研究者。

## 深度分析

#### 方法論解析

LoopArena 的核心設計是將「模型作為執行階段控制器（runtime controller）」這一能力獨立出來進行評估。傳統的程式設計代理（coding agent）基準測試通常把整個系統——規劃、執行、驗證——視為一個黑箱來評分，成功或失敗難以歸因於「誰在指揮」還是「誰在執行」。LoopArena 透過一個雙代理測試框架（harness）解決這個問題：受評模型扮演 Controller（控制器），負責外部迴圈（outer loop）的決策；而一個固定、獨立的程式設計代理則扮演 Worker（工作者），負責內部迴圈（inner loop）的實際程式設計工作。

在 Controller 引導條件（Controller-guided condition）下，每一輪 Worker 完成其當前指派後，測試框架會建立一個臨時報告代理（temporary Reporter agent）。Reporter 使用與 Worker 相同的模型，並在一份 Worker 對話歷史的副本上運作，對當前任務狀態進行結構化摘要（structured summary），同時可唯讀檢查工作空間。由於 Reporter 運作於臨時副本中，其探索不會污染 Worker 的持續對話歷史。測試框架接著將 Reporter 的摘要與 Worker 所引用的工作證據，格式化為一份 Evidence Packet（證據包）。Controller 只能讀取這份唯讀摘要，無法直接使用任何程式設計工具；它必須根據當前證據（current evidence）輸出一份 Loop Contract（迴圈合約），決定 Worker 下一輪該做什麼、該驗證什麼，或決定是否停止（decide whether to stop）。這份合約再被轉換為 Worker 的下一個提示（prompt）。

為了對照，論文設計了兩個基線：無控制基線（no-control baseline）讓 Worker 僅依原始任務指令自主運作（work autonomously）到完成；持續目標基線（persistent-goal baseline）則是受到 Codex 的 `/goal` 指令啟發的固定控制（fixed control），在每個控制點確定性重述（deterministically restate）原始任務目標，但不根據當前證據調整引導（adapt guidance）。這兩個基線幫助區分「有無 Controller」以及「Controller 是否根據進度動態調整」所帶來的差異。

LoopArena 進一步將評估分為三種互補設定（complementary settings），以在執行範圍（execution scope）與成本之間取得平衡：

- **Type I：迴圈合約選擇（Contract selection）**：評估單一控制決策。Controller 在某一控制點收到 Evidence Packet，並從四個候選 Loop Contract 中選出最適合下一輪 Worker 執行的選項。正確答案在基準建構階段已透過執行驗證（execution-validated questions）預先確定，因此評估新 Controller 時無需再執行 Worker，成本極低。
- **Type II：選定片段任務（Condensed coding task）**：從完整任務中截取一個連貫階段，從已準備好的中間工作空間開始，要求 Controller–Worker 迴圈完成下一階段。任務評估器（task evaluator）檢查截至該階段為止的累積需求，從而減少每次評估所需的執行量。
- **Type III：完整任務（Full coding task）**：從初始狀態（original state）開始執行成對的完整任務（paired full task），Controller 必須管理從調查、實作、驗證到最終停止的整個端到端執行（end-to-end run）。

這三種設計讓研究者能夠分別在「決策點」、「任務片段」與「完整長視野任務」三個層次診斷 Controller 的能力，並透過 Type II 與 Type III 的成對設計量化評估成本的降低與排序一致性。

#### 實驗數據解讀

論文報告的關鍵數據可從三個面向解讀：任務完成度、成本效益，以及不同評估設定間的一致性。

首先，在完整任務（Type III）上，最佳觀測值（best observed）的嚴格成功率（Strict Success Rate）僅為 24.69%。這個數字顯示，即使使用現今能力最強的模型作為 Controller，長視野（long-horizon）的迴圈控制仍然極具挑戰性。失敗模式可能包括：信任過時的進度註記（stale progress note）、跳過必要的驗證（skip needed verification）、將預算花在錯誤方向（spend budget in the wrong direction），或在可安全提交前停止（stop before safe to submit）。24.69% 也意味著這個領域存在大幅改善空間（substantial room for improvement），未來的模型架構與控制策略仍有顯著進步餘地。

其次，Type II 相對於 Type III 展現出顯著的成本優勢。實驗中，成對減少量（paired reduction）在估計推理成本（estimated inference cost）上平均達到 64.4%。這表示 Type II 作為一種「濃縮版」評估，能夠以約三分之一的成本近似捕捉 Controller 在完整任務上的表現。對於需要頻繁迭代與比較不同 Controller 的研究者來說，這是一個極具實用價值的設計。

第三，Type II 與 Type III 在主要核心指標（main Core criterion）上的排序高度一致，史皮爾曼等級相關係數 ρ（Spearman's ρ）達到 0.9747。這項結果強烈支持 Type II 可作為 Type III 的可靠代理指標：若某個 Controller 在 Type II 上表現較好，它在完整任務上也很可能表現較好。這使得研究者能夠先用低成本的 Type I 與 Type II 快速篩選候選模型或策略，再將最有希望的組合放到昂貴的 Type III 上驗證。

綜合來看，這三項數據描繪出一個清晰的評估階梯：Type I 用於低成本診斷單一決策、Type II 用於中成本比較 Controller 排序、Type III 用於高成本但最權威的端到端驗證。目前的數據也暗示，單純提升 Worker 的程式設計能力並不足以解決長視野任務，如何設計更好的外部迴圈控制器才是下一個瓶頸。

#### 與現有研究的比較

LoopArena 與現有程式設計代理基準測試的關鍵差異在於「評估對象」不同。傳統基準如 SWE-bench（Jimenez et al., 2024）或 DS-1000（Zan et al., 2025）主要評估單一 coding agent 在給定任務上的端到端完成能力，透過可執行測試（executable tests）或任務專用評估器（task-specific evaluators）評分最終儲存庫狀態。長視野與迭代式基準則進一步延長任務長度或引入演進中的需求（evolving requirements），但仍將整個代理系統（agent system）視為評估單位（Orlanski et al., 2026）。

流程導向基準測試（process-oriented benchmarks）則聚焦於軌跡（trajectory）中的個別能力，例如儲存庫探索（repository exploration）（Fan et al., 2026; Zhang et al., 2026a）。這類工作有助於理解代理的局部能力，但無法直接評估「如何持續管理多輪互動」。近期也有研究開始評估不同程式設計模型與迴圈實作在長視野任務上的組合（Li et al., 2026），但這些研究通常同時變動模型與迴圈設計，難以分離 Controller 的貢獻。

LoopArena 的創新在於將 Controller 與 Worker 解耦，並固定 Worker、工具、任務環境、執行預算與控制介面，從而使「模型作為執行階段控制器」成為可直接評估的對象。這類似於強化學習中將「策略」與「環境」分離的做法，讓研究者能夠單獨比較不同 Controller 模型在相同條件下的表現。

然而，這種設計也有其限制。第一，Worker 與 Reporter 使用相同模型，這意味著 Controller 的表現可能受到 Reporter 摘要品質的影響；若 Reporter 遺漏關鍵證據，即使 Controller 能力再強也難以做出正確決策。第二，Controller 只能透過 Loop Contract 影響 Worker，無法直接修改程式碼或執行測試，這雖然符合「純控制器」的抽象，但也可能低估了具備工具使用能力的 Controller 的潛力。第三，目前公開的內容未詳細說明任務分佈、領域涵蓋範圍或人類表現上限，這使得判斷 24.69% 的絕對難度時缺少參照基準。

#### 可重現性評估

可重現性方面，論文明確表示已在 GitHub 釋出（release）基準資料（benchmark data）與評估程式碼（evaluation code），網址為 https://github.com/AMAP-ML/LoopArena。這是正向訊號：研究者可以取得資料集、執行相同測試框架（harness），並比較自己的 Controller 模型。

不過，有幾點需要留意。首先，論文並未提及是否釋出模型權重（model weights）。由於 LoopArena 評估的是現有大型語言模型作為 Controller，理論上只要使用相同 API 或開源模型即可重現，但具體的模型版本、溫度參數、提示模板與解析邏輯若未完整公開，仍可能影響重現結果。其次，Type I 的正確選項依賴於基準建構階段的執行驗證，這部分過程若未詳細記錄，未來研究者難以擴充或修改題目。第三，估計推理成本（estimated inference cost）的計算方式——例如是否包含 Reporter、Controller 與 Worker 的全部 token、是否使用官方定價、是否考慮快取折扣——需要透明化，才能讓成本比較具有可重現性。

整體而言，LoopArena 在開源資料與程式碼層面已達到當前頂尖基準測試的水準，但若要成為長期使用的標準，仍需補充更詳細的實驗配置、提示設計與成本計算說明。

#### 未來研究方向

LoopArena 的設計與實驗結果揭示了多個值得後續探索的研究方向：

1. **更強大的 Controller 架構**：目前的 Controller 僅接收結構化摘要並輸出 Loop Contract。未來可探索具備長期記憶（long-term memory）的 Controller，能夠追蹤跨輪次的假設、失敗與恢復策略，避免被過時進度註記誤導。

2. **主動驗證與錯誤恢復**：論文提到的失敗模式多與驗證不足或錯誤停止有關。未來 Controller 可學習主動要求 Worker 執行特定可執行測試，或在發現進度停滯時觸發恢復程序，而非僅被動等待 Worker 回報。

3. **成本感知控制（cost-aware control）**：Type II 已顯示成本可降低 64.4%，但未來可進一步讓 Controller 在決策時納入預算（budget）限制，學習在「繼續執行」、「驗證」與「停止」之間做權衡，以最大化給定預算下的成功率。

4. **多 Controller 協作與階層式控制**：單一 Controller 可能難以同時處理高層規劃與低層細節。未來可設計階層式或多 Controller 系統，例如一個專注於任務分解，另一個專注於驗證決策，並在 LoopArena 上評估其協同效果。

5. **Reporter 品質與資訊瓶頸**：由於 Controller 完全依賴 Evidence Packet，提升 Reporter 的摘要能力——例如只保留相關證據、標示不確定性、主動提出疑問——可能直接提升 Controller 表現。這也引發一個研究問題：Controller 與 Reporter 是否應使用不同模型或共同訓練？

6. **擴展至非程式設計領域**：Loop Engineering 的概念不限於 coding agent。未來可將類似的 Controller–Worker 分離框架應用於科學實驗、資料分析、機器人控制等長時間執行任務，發展跨領域的執行階段控制器基準。

7. **人機協作與可解釋性**：在實務中，開發者可能希望介入 Controller 的決策。未來可研究如何讓 Controller 提供決策理由、接受人類修正，並在 LoopArena 中評估人機迴圈（human-in-the-loop）的效益。

8. **動態與對抗性任務設計**：目前的任務可能具有相對固定的完成路徑。未來可引入需求變更、環境擾動或對抗性陷阱，測試 Controller 在動態情境下的穩健性。

總結來說，LoopArena 不僅是一個基準測試，更是一個研究平台，讓「模型作為執行階段控制器」從隱含設計轉變為可測量、可比較、可改進的核心能力。隨著程式設計代理日益強大，如何有效指揮這些代理將成為決定其實用上限的關鍵。

## 論文問答

**Q1：LoopArena 想要解決什麼核心問題？為什麼長時間執行任務中的迴圈控制特別困難？**
A：LoopArena 針對的是迴圈工程中「執行階段控制器」難以被獨立評估的問題。在長時間執行任務中，Controller 必須持續監控 Worker 的進度、決定下一步要實作或驗證什麼，並判斷何時可以安全停止。然而，端到端執行的最終結果無法區分成功或失敗是來自 Controller 的指導，還是 Worker 本身執行任務的能力，因此需要一個能將兩者分離評估的基準測試。

**Q2：現有的程式設計代理基準測試為什麼無法充分評估 Controller 的能力？**
A：現有基準測試大多評估整個程式設計代理系統或單一代理完成任務的結果，無法區分外部迴圈控制與內部程式執行的貢獻。流程導向基準雖然評估軌跡中的個別動作，但通常不針對「模型作為另一個代理的管理者」這個角色。LoopArena 透過固定 Worker 與執行環境，讓比較對象僅限於 Controller 模型本身，從而彌補這個缺口。

**Q3：為什麼將 Controller 與 Worker 分離評估對迴圈工程很重要？**
A：在實務中，即使 Worker 能力很強，不良的 Controller 仍可能信任過時的進度註記、跳過必要驗證、把預算花在錯誤方向，或在可安全提交前停止。如果無法獨立評估 Controller，開發者就難以判斷該改進的是指導策略還是底層程式設計代理。LoopArena 讓 Controller 成為可直接評測的對象，使代理協作系統的設計與優化更有依據。

**Q4：LoopArena 的雙代理測試框架如何運作？請說明 Controller、Worker、Reporter 與 Evidence Packet 的角色。**
A：LoopArena 的測試框架中，受評模型扮演 Controller，負責外部迴圈的決策；一個固定、獨立的程式設計代理則是 Worker，負責內部迴圈的實際程式開發。每當 Worker 完成一輪工作後，測試框架會建立臨時的 Reporter 代理，根據 Worker 的對話紀錄與唯讀工作區檢查產生結構化摘要，再由框架格式化為 Evidence Packet 提供給 Controller。Controller 閱讀這份唯讀證據包後，發出 Loop Contract 指定 Worker 下一階段的任務或決定停止，但 Controller 本身沒有程式設計工具，只能透過指令影響任務。

**Q5：LoopArena 提出的三類互補評估設定各有什麼特點？它們如何平衡評估成本與真實性？**
A：第一類評估透過預先執行驗證的四選一問題，在評估時不需要執行 Worker，成本最低但聚焦單一決策。第二類評估從完整任務的選定片段開始，讓 Controller–Worker 迴圈完成下一個連貫階段，兼顧真實性與成本。第三類評估則從初始狀態執行成對的完整任務，最能反映真實長視野場景，但執行成本最高；三者相互補充，讓研究者依需求選擇適當的評估粒度。

**Q6：為什麼 LoopArena 要透過臨時 Reporter 產生唯讀 Evidence Packet，而不是讓 Controller 直接檢視工作區？**
A：這個設計是為了確保 Controller 的輸入是結構化、唯讀且不受 Worker 持續對話干擾的摘要，從而精確評估 Controller 根據當前證據做出決策的能力。Reporter 在臨時對話副本中運作，不會改變 Worker 的持久歷史，避免額外互動污染內部迴圈。同時，限制 Controller 只能透過 Loop Contract 影響 Worker，可以清楚區分控制決策與程式執行能力，使評估更加公平與可重現。

**Q7：LoopArena 使用了哪些對照條件與基線來評估 Controller 的效果？**
A：LoopArena 除了 Controller 引導條件外，還設有無控制基線與固定控制基線作為對照。無控制基線讓 Worker 僅依任務指令自主完成任務，用來衡量 Controller 是否帶來顯著改善。固定控制則是受到 Codex /goal 啟發的持續目標基線，每個控制點都確定性重述原始任務目標，但不根據當前證據調整引導，用來檢驗單純持續提醒目標是否足夠。

**Q8：LoopArena 的主要實驗結果有哪些？這些數字代表什麼意義？**
A：在完整任務上，最佳觀測到的嚴格成功率僅為 24.69%，顯示長視野迴圈控制仍有大幅改善空間。相較於對照組，Type II 評估的成對估計推理成本平均減少 64.4%，意味著用片段任務評估能顯著降低評估開銷。此外，Type II 與 Type III 在主要核心指標上的史皮爾曼等級相關係數 ρ 高達 0.9747，表示片段層級的評估能有效預測完整任務層級的 Controller 排序。

**Q9：Type I、Type II 與 Type III 之間的相關性對研究者有什麼啟示？**
A：Type I 雖然成本最低，但透過預先執行驗證的正確選項，能診斷 Controller 在關鍵控制點的決策品質。Type II 與 Type III 之間極高的排序一致性則說明，研究者可以用成本較低的片段任務來篩選與比較 Controller 模型，而不必每次都執行昂貴的完整任務。這三種互補設定讓診斷、比較與端到端驗證能夠在不同資源條件下進行。

**Q10：在實務開發場景中，團隊可以如何運用 LoopArena 來選擇或改進 Controller 模型？**
A：開發團隊可以先利用 Type I 快速檢視候選 Controller 在關鍵決策點的表現，找出容易選錯迴圈合約的模型。接著透過 Type II 在選定片段上反覆測試，比較不同 Controller 在較真實但成本可控的執行環境中的排序。最後再用 Type III 對最有潛力的少數模型進行完整任務驗證，從而形成由低成本篩選到高成本確認的模型選型流程。

**Q11：在實際產品中部署 Controller 時，需要考慮哪些工程權衡？**
A：部署時必須權衡 Controller 的推理成本與控制品質，因為更頻繁或更複雜的控制決策會增加延遲與費用。同時，Evidence Packet 的設計與 Reporter 的摘要品質會直接影響 Controller 的判斷，因此需要確保摘要既完整又不會遺漏關鍵證據。此外，過度控制可能限制 Worker 的自主性，而控制不足則可能導致預算浪費或提前停止，產品團隊需根據任務特性調整控制粒度。

**Q12：LoopArena 對程式設計代理與代理協作領域可能帶來什麼影響？**
A：LoopArena 將「模型作為執行階段控制器」變成可直接評測的研究對象，促使社群不再只關注單一程式設計代理的能力。它提供了一個受控協定，讓不同 Controller 模型能在相同 Worker 與環境下公平比較，有助於加速迴圈工程相關研究。長遠來看，這類基準能推動更專業化的代理分工，讓未來的程式設計系統由專門負責規劃、監督與決策的 Controller 與專注執行的 Worker 協同運作。

**Q13：LoopArena 的設計有哪些可能的限制？**
A：LoopArena 固定了 Worker 模型與工具環境，因此評估結果可能無法直接推廣到不同 Worker 或不同程式設計工具組合上。此外，Evidence Packet 的結構化格式雖然有助於公平比較，但也可能簡化了真實開發中更豐富、更非結構化的資訊。還有，Type I 的正確選項是在基準建構階段透過執行驗證所確立，若任務空間或 Worker 行為改變，這些選項可能需要重新檢驗。

**Q14：LoopArena 揭示了 Controller 哪些典型的失敗模式？**
A：實驗顯示 Controller 可能誤把看似合理的部分結果當成完成，忽略尚未觸及的需求。它也可能發出過於狹隘的驗證指令，導致 Worker 通過局部檢查卻違反整體需求。此外，有些 Controller 會在可安全提交前停止，或持續將 Worker 導向錯誤方向而耗盡預算，這些都是長視野控制中需要特別關注的失敗案例。

**Q15：LoopArena 開啟了哪些未來研究方向？**
A：未來可以探索如何讓 Controller 主動提出更豐富的驗證策略，而不僅限於選擇或發出下一階段指令。另一個方向是研究 Controller 與不同能力 Worker 之間的適配性，發展能根據 Worker 強弱動態調整控制策略的模型。此外，也可以擴充基準到更多程式語言、更長的任務軌跡，以及包含人機協作的混合控制場景，進一步推動迴圈工程的實務應用。

## 實務應用指南

### 適用場景

1. **長期維護型程式碼重構**：當需要將大型遺留系統從一種架構遷移到另一種架構（例如單體式轉微服務、Python 2 轉 Python 3）時，Controller 可以根據每輪 Worker 的回饋決定下一步要重構哪個模組、執行哪些回歸測試，以及何時確認整體遷移完成。

2. **多輪除錯與根因定位**：在生產環境出現難以重現的 Bug 時，Controller 可指揮 Worker 依序收集日誌、縮小觸發條件、撰寫修補、執行驗證，並在證據不足時要求繼續調查，避免過早停止。

3. **需求持續演進的迭代開發**：在敏捷或產品開發中，當任務會隨著程式碼儲存庫狀態而改變優先順序（例如先實作 API、再補測試、再補文件），Controller 可動態調整 Worker 的下一階段目標，而非一成不變地重複原始指令。

4. **自動化程式碼審查與合併前把關**：在 CI/CD 流程中，Controller 可作為合併前的「執行階段控制器」，根據 Worker 執行測試、靜態分析與安全掃描的結果，決定是否要求修正、補充驗證，或允許提交。

5. **多步驟資料工程管線建置**：例如建立 ETL、特徵工程或模型部署管線時，Controller 可依據每輪執行結果決定下一步要處理哪個資料來源、修復哪個轉換錯誤，或確認端對端管線已可穩定運行。

### 實作前置條件

**資料**
- 可還原的任務初始狀態（程式碼儲存庫、相依環境、資料集）。
- 明確的任務目標與可執行的評估器（executable tests 或 task-specific evaluators）。
- 用於建構 Evidence Packet 的結構化欄位定義，例如當前進度、已執行驗證、發現的錯誤、剩餘需求等。

**運算**
- 可穩定呼叫的 Worker 程式設計代理（建議固定模型與工具，避免實驗變因混淆）。
- 足夠的推理預算供 Controller 在每個控制點產生 Loop Contract；若採用 Type II 或 Type III，還需預留多輪 Worker 執行的成本。
- 可執行沙箱環境，用於還原任務狀態、執行測試與評估結果。

**技能**
- 熟悉 prompt engineering 與結構化輸出設計，能將 Reporter 摘要轉換為 Controller 可讀的 Evidence Packet。
- 具備設計任務評估器與可重現執行環境的能力。
- 了解迴圈工程（Loop Engineering）概念，能區分內部迴圈（Worker 執行）與外部迴圈（Controller 決策）的責任邊界。

---

### 實作步驟建議

1. **定義控制介面與資料結構**
   - 設計 Evidence Packet 的欄位，確保 Reporter 能從 Worker 的對話歷史與唯讀工作區產出一致摘要。
   - 設計 Loop Contract 的輸出格式，讓 Controller 能明確指定下一輪任務、驗證項目或停止決定。

2. **建立可還原的任務環境**
   - 為每個任務建立初始狀態快照，並確保每次執行都能從相同狀態開始。
   - 準備 task evaluator，用於判斷 Worker 輸出是否滿足階段性與完整性需求。

3. **實作 Reporter 與測試框架**
   - 使用與 Worker 相同的模型實作臨時 Reporter，讓其在獨立對話中總結進度，避免污染 Worker 的持久歷史。
   - 將 Reporter 輸出與 Worker 引用的工作證據格式化為 Evidence Packet。

4. **從 Type I 開始快速診斷**
   - 針對關鍵控制點預先執行候選 Loop Contract，建立經執行驗證的選擇題。
   - 在無需執行 Worker 的情況下，先評估 Controller 的單步決策品質，快速迭代 prompt。

5. **以 Type II 進行片段級驗證**
   - 從完整任務中選出代表性片段，從中間狀態開始執行 Controller–Worker 迴圈。
   - 比較不同 Controller 在成本與核心指標上的表現，作為篩選依據。

6. **以 Type III 進行端到端驗證**
   - 對通過 Type II 的 Controller，執行成對的完整任務，計算嚴格成功率與推理成本。
   - 同時執行無控制基線與固定控制基線，以量化 Controller 帶來的實際效益。

7. **部署與持續監控**
   - 將驗證過的 Controller 整合到開發流程，並記錄每輪的 Evidence Packet 與 Loop Contract。
   - 定期用真實失敗案例回補 Type I 題庫，持續提升 Controller 的決策品質。

---

### 潛在風險與注意事項

- **過時的進度註記（stale progress note）**：Reporter 摘要可能遺漏 Worker 最新修改，導致 Controller 基於錯誤資訊下達指令。  
  *因應方式*：在 Evidence Packet 中強制包含「最後執行的動作」與「工作區 diff」，並要求 Reporter 引用具體檔案與測試結果。

- **跳過必要的驗證**：Controller 可能過早認定任務完成，要求 Worker 停止。  
  *因應方式*：在 Loop Contract 的停止條件中要求明確列出已通過的驗證項目，並由 task evaluator 獨立檢核。

- **將預算花在錯誤方向**：Controller 可能反覆要求 Worker 在無關緊要的細節上打轉。  
  *因應方式*：設定每輪成本上限與總輪數上限，並在 Evidence Packet 中強調剩餘需求與風險最高的未驗證項目。

- **Worker 能力混淆 Controller 評估**：若 Worker 太弱，即使 Controller 決策正確也會失敗；若 Worker 太強，則會掩蓋 Controller 的錯誤。  
  *因應方式*：在比較 Controller 時固定 Worker 與執行設定，並同時觀察無控制基線與固定控制基線。

- **提示詞過度擬合 Type I 題目**：Controller 可能在選擇題上表現良好，但在開放式 Type III 執行中失效。  
  *因應方式*：Type I 僅作為診斷工具，最終仍須以 Type II 與 Type III 驗證端到端能力。

### 與其他技術的整合建議

- **CI/CD 管線**：可將 LoopArena 的測試框架嵌入 GitHub Actions、GitLab CI 或 Jenkins，讓 Controller 在 PR 階段自動指揮 Worker 執行修補、測試與審查，並根據 evaluator 結果決定是否通過。

- **現有程式設計代理框架**：若已使用 SWE-agent、OpenHands 或類似框架，可將其 Worker 角色固定下來，僅替換或疊加 Controller 層，避免從頭重建執行環境。

- **可觀測性平台**：將每輪的 Evidence Packet 與 Loop Contract 輸出到結構化日誌系統（如 OpenTelemetry、LangSmith、Langfuse），方便追蹤 Controller 為何在某個控制點做出特定決定。

- **模型路由與成本控管**：對於簡單控制點可路由至輕量模型，對於高風險決策點再呼叫高階模型；Type II 的成本數據可作為路由策略的校準依據。

- **知識庫與檢索系統**：在 Evidence Packet 中可加入來自向量資料庫或文件檢索的相關程式碼片段，幫助 Controller 更準確地判斷當前進度與下一步方向。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從圖 1 的測試框架與第 2.2 節的控制週期開始，理解「Controller 發指令、Worker 執行、Reporter 摘要、Evaluator 打分」這四個角色的分工。接著閱讀 Type I 的設計，因為它把複雜的端到端執行簡化成一道選擇題，最容易掌握迴圈工程的核心概念。

**AI 工程師**：請重點關注 Evidence Packet 與 Loop Contract 的結構化設計、Reporter 的臨時對話機制，以及 Type II 與 Type III 的成對比較方法。這些細節直接決定了你能否在現有程式設計代理上疊加一個可評估、可迭代的 Controller 層，並用成本降低數據說服團隊採用。

**研究人員**：建議深入分析三類評估設定的互補性，特別是 Type I 如何將執行成本轉移到基準建構階段，以及 Type II 與 Type III 之間高達 ρ=0.9747 的排序一致性對未來低成本評估的意義。可進一步探討 Controller 在何種任務特徵下會出現過早停止、錯誤驗證或預算錯配等系統性失敗模式。

**產品經理**：請聚焦於「嚴格成功率僅 24.69%」與「成對推理成本平均降低 64.4%」這兩個數字。它們說明了這個領域仍處於早期但潛力巨大：目前不適合直接上線全自動交付，但非常適合作為開發者輔助工具，先從合併前把關、自動化測試補全等場景切入，並以人機協作方式逐步擴大 Controller 的決策權限。
