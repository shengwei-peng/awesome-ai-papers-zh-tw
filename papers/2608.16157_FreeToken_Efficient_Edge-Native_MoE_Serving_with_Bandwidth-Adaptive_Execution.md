## 摘要翻譯

Frontier open-weight models（開源權重模型）日益普及，但為其提供推理服務仍大多預設 datacenter infrastructure（資料中心基礎設施）。我們提出 FreeToken，一個 Edge-Native（邊緣原生） MoE（Mixture-of-Experts，混合專家模型）推理系統，不是將 personal machine（個人機器）視為一張小型 GPU，而是將其視為 unified inference platform（統一推理平台）與 elastic inference platform（彈性推理平台）。FreeToken 協同設計完整的推理堆疊，涵蓋 model layout and loading（模型佈局與載入）、expert residency（專家駐留）、CPU–GPU execution（CPU–GPU 執行）、agentic state reuse（智慧代理狀態重用），以及 runtime memory management（執行階段記憶體管理），並圍繞本地 AI 的兩項現實進行設計：agentic applications（智慧代理應用）的工作負載會持續改變其執行模式，而邊緣硬體展現出 heterogeneous resources（異質資源），其資源配比因機器而異。FreeToken 不固守固定的 offloading strategy（卸載策略），而是持續將計算與模型狀態映射至實際可用的資源。FreeToken 支援超過 20 個 MoE 模型，以及真實的 coding agents（程式設計代理）與 tool-using agents（工具使用代理），涵蓋從 8GB laptop GPU（筆記型電腦 GPU）到單張 workstation GPU（工作站 GPU）的硬體範圍。更重要的是，它改變了這些機器實際能夠服務的模型：從筆記型電腦上的 35B parameters（參數）模型、gaming desktop（電競桌機）上的 284B 參數模型，到單張工作站 GPU 上的 753B GLM-5.2。FreeToken 將開源權重轉化為可部署的本地軟體，讓使用者既有的機器成為承載 frontier-scale intelligence（前沿規模智慧）的實用平台。我們於 flashml.ai 公開釋出本系統。

### 核心貢獻（3～5點）
- 提出邊緣原生 MoE 推理系統 FreeToken，將個人機器視為統一且彈性的推理平台，而非僅是一張小型 GPU。
- 協同設計完整推理堆疊，涵蓋模型佈局與載入、專家駐留、CPU–GPU 執行、智慧代理狀態重用與執行階段記憶體管理。
- 採用頻寬自適應執行，不固守固定卸載策略，而是持續依據實際異質資源動態映射計算與模型狀態。
- 針對智慧代理工作負載優化，應對其持續變化的執行模式，並支援真實的程式設計代理與工具使用代理。
- 在廣泛硬體上實現突破：從 8GB 筆記型電腦 GPU、電競桌機到單張工作站 GPU，可服務 35B 至 753B 規模的模型，並於 flashml.ai 公開釋出。

### 適合對象
對邊緣／本地大型語言模型推理、混合專家模型（MoE）壓縮與卸載、智慧代理應用，以及開源權重模型部署有興趣的研究人員與工程師；特別適合關注如何在筆電、電競桌機與工作站 GPU 等有限異質硬體上，實現前沿規模模型服務的讀者。

## 深度分析

#### 方法論解析

FreeToken 的核心設計是把「個人機器（personal machine）」視為一個統一的彈性推理平台（unified inference platform），而非單純縮小版的資料中心 GPU。為此，它把整個 serving stack——包括模型佈局與載入（model layout and loading）、專家駐留（expert residency）、CPU–GPU 執行（CPU–GPU execution）、智慧代理狀態重用（agentic state reuse）與執行階段記憶體管理（runtime memory management）——圍繞兩個邊緣 AI 的現實進行協同設計：一是 agentic workloads（智慧代理工作負載）會持續改變執行模式；二是邊緣硬體的異質資源（heterogeneous resources）在不同機器間差異極大。以下分三點說明其方法論。

##### 1. 頻寬自適應執行（Bandwidth-Adaptive Execution）

FreeToken 不把有限的 PCIe / 主機記憶體頻寬當成固定瓶頸，而是把它轉化為執行階段的排程訊號。

- **Prefill 階段的雙緩衝（double-buffering）**：在長提示（long prompt）的 prefill 過程中，MoE（混合專家模型）的 working-set sparsity（工作集稀疏性）會被破壞——雖然每個詞元（token）只啟用少數專家（experts），但長提示中所有詞元路由的聯集往往覆蓋幾乎所有專家，導致專家必須反覆從主機記憶體串流進 GPU。FreeToken 在 prefill 時讓 GPU 計算目前層的同時，透過 PCIe 把下一層所需專家預先傳入，形成計算與資料搬移的重疊，從而隱藏專家移動延遲。
- **Decode 階段的 q⋆ 策略**：decode 時每個 token 只啟用稀疏子集，但快取未命中（cache misses）會要求反覆載入、驅逐或在主機記憶體上執行專家。此時 GPU 執行與直接 CPU 執行都會競爭同一條主機記憶體頻寬。FreeToken 提出 q⋆ 策略，把每一步的快取未命中分割成兩部分：一部分透過 PCIe 載入 GPU 執行（GPU cache fill），另一部分直接在 CPU 上執行（direct CPU execution）。分割點根據當下機器可持續的頻寬動態決定，讓總執行時間最小化。

這種「不預先承諾固定卸載策略（offloading strategy），而是按可用資源連續映射計算與模型狀態」的做法，是 FreeToken 與傳統靜態放置（static placement）的根本差異。

##### 2. 語意感知快取（Semantic-Aware Caching）

FreeToken 利用 agentic workloads 的結構性重複來降低冗餘計算與資料搬移。

- **跨回合的狀態重用**：在智慧代理應用（agentic applications）中，對話會在語意邊界（semantic boundaries）——例如 thinking segments（思考段落）與 tool calls（工具呼叫）——之間反覆編輯與延伸。FreeToken 在這些邊界建立 recurrent-state checkpoints（遞迴狀態檢查點），當使用者編輯後，只需重新計算新增的字尾，而不必從頭進行完整 prefill。
- **Decode 階段的共享 LRU 專家快取**：相鄰詞元經常路由到重疊的專家。FreeToken 以共享 LRU（Least Recently Used）專家快取捕捉這種 inter-token routing locality（詞元間路由局部性），讓大多數被路由到的專家命中 VRAM，僅剩的殘差未命中（residual misses）才交給 q⋆ 策略處理。

語意感知快取把「稀疏性」從單純的參數層面，延伸到時間與語意層面，是 FreeToken 能在互動速度下執行大規模 MoE 的關鍵。

##### 3. 彈性邊緣資源管理（Elastic Edge Resource Management）

個人硬體的可用資源會隨時間變動：使用者可能同時開啟瀏覽器、遊戲或其他應用，導致 VRAM 與主機記憶體預算波動。FreeToken 在 scheduler safe points（排程器安全點）動態調整並重建 GPU 專家快取，以符合新的記憶體預算，且無需重啟引擎或重新載入主機常駐的專家池（host-resident expert pool）。此外，它透過直接把專家載入最終主機佈局（host layout）來降低啟動延遲。

整體而言，FreeToken 的方法論可視為一個「資源感知—語意感知—頻寬自適應」的閉環：執行階段持續測量可用資源，語意快取減少必須搬移的狀態，q⋆ 與雙緩衝則把殘差搬移成本隱藏在計算背後。

#### 實驗數據解讀

雖然目前僅能從摘要與引言取得高階實驗結果，但已可看出 FreeToken 在「成本—能力」與「硬體等級—解碼速度」兩個維度上的訴求。

##### 1. 成本—能力帕累托前沿（Cost-Capability Pareto Frontier）

圖 1(a) 把代表模型的混合 API 價格（blended API price，9:1 input:output mix）與 Code Arena Elo 評分對照。FreeToken 標記的模型——Qwen3.6-35B、DeepSeek-V4-Flash 284B、GLM-5.2 753B——正好落在 Pareto frontier（帕累托前沿）上，意味著在給定能力下，本地部署的邊際成本為零（$Free!）。這裡的訊息是：開源權重模型（open-weight models）本身已具備前沿能力，但「可及性差距（accessibility gap）」讓多數使用者無法實際使用；FreeToken 把這些權重轉化為可在個人機器上執行的軟體，從而關閉了可及性差距。

值得注意的是，Kimi-K3 雖然開源，但 594GB 的記憶體需求超出消費級硬體，因此不在 FreeToken 目前可服務範圍內；這也暗示系統仍受限於主機記憶體容量，而非僅 GPU VRAM。

##### 2. 硬體等級與解碼速度

圖 1(b) 比較 FreeToken、llama.cpp、KTransformers 與 Ollama 在三個硬體等級（hardware tier）上的平均 agentic decode speed（智慧代理解碼速度）：

- **8GB 筆電 GPU（Laptop GPU）**：可服務 Qwen3.6-35B；
- **高階電競桌機 GPU（Gaming desktop）**：可服務 DeepSeek-V4-Flash 284B；
- **單一工作站 GPU（Workstation GPU）**：可服務 GLM-5.2 753B。

虛線標示 Codex 在生產環境追蹤中的中位數解碼速度 33 tok/s。FreeToken 宣稱在這些消費級硬體上達到互動速度（interactive speed），而 llama.cpp、KTransformers、Ollama 在某些配置標示為「×」，表示無法服務或無法達到可用速度。

解讀時需注意幾點：

- **工作負載代表性**：實驗使用真實 coding-agent traces（程式設計代理追蹤）與 math agent（數學代理），這比單純的 perplexity 或靜態 prompt 更能反映 agentic workloads 的長上下文、頻繁 tool calls 與編輯行為。
- **比較基準的公平性**：不同引擎支援的量化精度（quantization precision）、CPU 核心數、記憶體通道數可能不同。若 FreeToken 使用較激進的量化或專用 CPU kernel，則速度優勢需連同品質損失一起評估。目前摘要未詳細說明精度設定，這是後續需要檢視之處。
- **啟動參數與總參數的區別**：DeepSeek-V4-Flash 284B 總參數中，每次 token 僅啟用約 13B。FreeToken 的價值在於讓「總參數遠超 VRAM」的模型仍能以啟用參數的計算成本運行，這正是 MoE 架構在邊緣的機會所在。

##### 3. 支援廣度

FreeToken 支援超過 20 個 MoE 模型，並在真實 coding 與 tool-using agents（工具使用代理）上驗證。這顯示其設計並非針對單一模型硬編碼，而是具備一定通用性。然而，具體涵蓋哪些模型家族、是否包含不同路由拓撲（如 shared experts、fine-grained experts）與不同量化格式，仍需完整論文確認。

#### 與現有研究的比較

##### 1. 相對於 llama.cpp

llama.cpp 是邊緣裝置上最廣泛使用的開源推理框架之一，支援多種量化與 CPU/GPU 混合執行。然而，llama.cpp 主要針對密集模型（dense models）與相對靜態的 offloading 設計，對 MoE 的稀疏路由動態、長上下文 prefill 的 working-set 膨脹，以及 agentic state reuse 的支援較為有限。FreeToken 的雙緩衝、q⋆ 策略與語意感知快取，正是為了彌補這些缺口。

##### 2. 相對於 KTransformers

KTransformers 同樣聚焦於在消費級硬體上服務超大模型，通常採用 CPU 執行部分層、GPU 執行熱層的混合策略。KTransformers 的強項在於極端壓縮與 CPU offload，但其策略較為靜態，且對於 agentic workloads 中頻繁的 prefill 與狀態重複利用缺乏針對性最佳化。FreeToken 的彈性資源管理與語意邊界檢查點，使其更能適應個人機器上動態變化的記憶體預算。

##### 3. 相對於 Ollama

Ollama 強調易用性與本地模型管理，但在大規模 MoE 的高效執行上並非其核心最佳化目標。Ollama 的「×」標記在圖 1(b) 中出現，顯示其在高階模型或硬體組合上無法服務或無法達到互動速度。FreeToken 則把目標放在「前沿規模智慧（frontier-scale intelligence）」的實用化，而非僅僅提供可用的本地介面。

##### 4. 相對於資料中心 MoE 推理系統

在資料中心領域，已有許多針對 MoE 的專家並行（expert parallelism）、專家選擇（expert selection）、預取（prefetching）與動態調度研究。FreeToken 的差異在於：

- **單機異質資源**：資料中心通常假設同質 GPU 與高速網路，FreeToken 則面對單機內 GPU、CPU、主機記憶體與 PCIe 的異質頻寬。
- **無專用資源**：個人機器的資源會被其他應用搶佔，因此需要彈性調整而非靜態配置。
- **無需分散式**：FreeToken 不依赖多機多卡，而是把單一消費級機器視為完整平台。

##### 5. 限制與潛在弱點

- **主機記憶體天花板**：雖然 GPU VRAM 可透過 offload 擴展，但完整專家池仍需常駐主機記憶體或 secondary storage。Kimi-K3 的 594GB 需求已超出消費級範圍，顯示 FreeToken 仍受實體記憶體容量限制。
- **精度與品質權衡**：為了讓 753B 模型在單一工作站 GPU 上運行，勢必使用某種形式的量化或稀疏化。論文需說明這些壓縮對 Code Arena Elo 或下游任務的影響，否則速度比較可能不完全公平。
- **CPU 執行效率**：q⋆ 策略依賴直接 CPU 執行專家的能力。若 CPU kernel 最佳化不足，或主機記憶體頻寬成為瓶頸，則整體吞吐量會下降。
- **模型支援範圍**：雖然支援 20+ MoE 模型，但是否涵蓋非 MoE 的大型密集模型、多模態模型或不同 tokenizer 架構，仍有待確認。

#### 可重現性評估

##### 1. 系統釋出

論文明確表示在 flashml.ai 釋出 FreeToken 系統，這是正向訊號。若原始碼、安裝文件與預設配置完整公開，則其他研究者與使用者可在自己的硬體上重現主要結果。

##### 2. 模型權重

FreeToken 服務的模型——DeepSeek-V4-Flash、GLM-5.2、Qwen3.6-35B 等——均為開源權重模型（open-weight models），權重可由模型提供者取得。這降低了重現門檻，因為不需要從頭訓練。

##### 3. 資料集與追蹤

實驗使用 real coding-agent traces（Zhu et al., 2026）與 math agent 追蹤。若這些追蹤資料公開，則可重現工作負載；若僅引用而未釋出，則其他研究者難以精確複製 decode speed 與 token economics（詞元經濟學）測量。這是重現性的一個潛在缺口。

##### 4. 硬體環境

論文涵蓋從 8GB 筆電 GPU 到單一工作站 GPU 的硬體等級。重現時需要取得對應的消費級 GPU，這對部分研究者可能是障礙，但對於「邊緣原生」這類研究而言，使用真實硬體是必要的。

##### 5. 建議

為提升可重現性，作者可考慮：

- 公開完整原始碼與編譯/安裝流程；
- 提供標準化 benchmark script，包含模型下載、量化設定與工作負載載入；
- 釋出或詳細描述 coding-agent traces 的取樣方式與統計特性；
- 提供不同硬體配置下的預設參數與預期性能區間。

#### 未來研究方向

##### 1. 多 GPU 與異質加速器整合

FreeToken 目前聚焦單機單卡或 CPU–GPU 協同。未來可擴展至多 GPU（multi-GPU）配置，並整合 NPU（神經處理單元）、APU 或筆電的整合 GPU，形成真正的異質加速器排程。

##### 2. 路由預測與推測執行

雖然 q⋆ 策略處理已發生的快取未命中，但若能在 token 產生前預測其路由（routing prediction），則可進一步預取專家，減少未命中。結合 speculative decoding（推測解碼）與 draft expert 概念，可望提升 decode 吞吐量。

##### 3. 量化與壓縮的協同設計

FreeToken 的執行效率與模型大小密切相關。未來可研究如何與量化（quantization）、剪枝（pruning）、專家合併（expert merging）或低秩近似（low-rank approximation）協同設計，在維持 Code Arena Elo 的前提下進一步降低記憶體與頻寬需求。

##### 4. 跨裝置邊緣聯邦推理

個人機器數量龐大，但未充分利用。未來可探索把鄰近裝置（如桌機、筆電、手機）組成彈性推理叢集，透過區域網路分攤專家池，讓單一裝置無法承載的模型也能在家庭或小型辦公室環境中運行。

##### 5. 能源、溫度與使用者體驗

邊緣裝置的功耗與散熱有限。未來研究可納入 thermal-aware scheduling（溫度感知排程）與 battery-aware inference（電池感知推理），在效能與使用者體驗（噪音、發熱、續航）之間取得平衡。

##### 6. 安全與隱私強化

本地部署的價值之一是資料不離開裝置。未來可強化模型權重保護、推論過程的機密性，以及針對 agentic tool calls 的安全沙箱，讓 FreeToken 不僅高效，也適合處理敏感資料。

##### 7. 自動化超參數與模型選擇

FreeToken 已具備彈性資源管理，下一步可發展自動化模型選擇：根據當下硬體、工作負載與延遲需求，自動挑選最適模型、量化等級與快取大小，讓非技術使用者也能一鍵獲得最佳配置。

## 論文問答

### 【背景與動機】

**Q1：FreeToken 想要解決的核心問題是什麼？**

A：FreeToken 要解決的是「開源權重模型雖然可取得，但幾乎無法在個人裝置上實際執行」的可及性差距。過往的服務系統多半假設背後有資料中心等級的 GPU 叢集，而忽視了全球數億台已配備獨立 GPU 的消費級電腦。MoE 模型的稀疏啟動特性讓單一詞元只用到少量參數，理論上使邊緣執行成為可能，但完整的專家池仍會超出 GPU 記憶體，因此需要新的系統層設計來把個人機器轉變為統一的彈性推理平台。

**Q2：現有的邊緣推理系統為何在 MoE 服務上表現不足？**

A：現有系統如 llama.cpp、KTransformers 與 Ollama 只處理了邊緣 MoE 服務的片段問題。首先，在 prefill 階段，長提示會讓多個詞元路由到的專家聯集變得幾乎稠密，導致必須反覆從主記憶體搬運專家；其次，在 decode 階段，靜態的專家放置無法跟上每個詞元的稀疏路由變化，而單純的預取也無法決定未命中時應該走 PCIe 傳輸、GPU 執行還是直接 CPU 執行。再加上消費級硬體的 GPU 容量、PCIe 頻寬、CPU 能力與可用記憶體差異極大，任何單一靜態策略都難以在不同裝置與執行階段維持高效。

**Q3：為什麼隨著智慧代理應用興起，本地服務變得越來越重要？**

A：智慧代理應用會急劇增加推理需求，持續呼叫託管 API 對個人使用者與小團隊而言成本負擔沉重。更重要的是，代理工作負載常伴隨長且不斷成長的上下文、頻繁的工具呼叫與狀態更新，這些都會放大資料傳輸與重複計算的成本。讓模型在使用者已擁有的機器上本地執行，不僅能降低費用，也能提升隱私性、降低延遲，並把數億台消費級電腦轉化為可實際運行前沿規模智慧的運算資源。

---

### 【方法與創新】

**Q4：FreeToken 的三大設計支柱是什麼？**

A：FreeToken 建立在兩個執行原則與一個彈性資源管理政策之上。第一個原則是頻寬自適應執行，它把有限的邊緣頻寬視為執行階段的排程訊號，而非固定瓶頸。第二個原則是語意感知快取，用來決定稀缺記憶體中應保留哪些狀態與專家；第三個支柱是彈性邊緣資源管理，讓系統能根據執行階段變化的記憶體預算動態調整 GPU 專家快取，而無需重啟引擎或重新載入主記憶體中的專家池。

**Q5：FreeToken 的 q⋆ 政策如何決定 decode 階段的未命中處理方式？**

A：q⋆ 政策會把每個 decode 步驟的專家快取未命中，劃分為「透過 PCIe 載入 GPU 執行」與「直接在 CPU 上執行」兩部分。由於這兩種路徑都會競爭主記憶體頻寬，q⋆ 會根據當前機器可持續提供的頻寬，計算最適合的分割比例，以最小化該步驟的延遲。這種動態劃分讓 FreeToken 能夠適應不同硬體的 PCIe 與主記憶體頻寬組合，而不是依賴固定的卸載策略。

**Q6：語意感知快取如何協助智慧代理工作負載？**

A：語意感知快取會在語意邊界（例如思考段落與工具呼叫）建立循環狀態檢查點，當使用者在對話中編輯或追加內容後，只需重新計算新的後綴部分，而不必從頭執行整段上下文。在 decode 階段，相鄰詞元經常路由到重疊的專家，FreeToken 透過共享的 LRU 專家快取捕捉這種詞元間路由局部性，使大多數路由存取都能在 VRAM 中命中。如此一來，只有殘餘的未命中需要交給 q⋆ 政策處理，顯著減少了不必要的資料搬運與重複計算。

### 【實驗與結果】

**Q7：FreeToken 在哪些硬體與模型上進行了評估？**

A：FreeToken 支援超過 20 個 MoE 模型，硬體範圍從僅有 8GB VRAM 的筆電 GPU，到單張工作站 GPU。具體展示的配置包括：在筆電上執行 35B 模型、在電競桌機上執行 284B 的 DeepSeek-V4-Flash，以及在單張工作站 GPU 上執行 753B 的 GLM-5.2。實驗也使用了真實的程式設計代理與工具使用代理追蹤，來模擬實際的 agentic 工作負載。

**Q8：FreeToken 的關鍵性能結果是什麼？**

A：FreeToken 能夠服務位於成本–能力帕累托前沿上的模型，並在消費級硬體上達到互動式解碼速度；在部分配置下，平均解碼吞吐量超過了 Codex 在生產環境中的中位數 33 tok/s。與 llama.cpp、KTransformers 和 Ollama 相比，FreeToken 不僅速度更快，還能服務其他引擎無法載入的更大模型。這表示它真正改變了這些機器「能夠實際服務什麼規模模型」的上限。

**Q9：從消融實驗或設計分析中可以得到什麼洞察？**

A：實驗顯示，靜態的卸載或放置策略在不同頻寬與記憶體組合下會顯著退化，而頻寬自適應執行能根據硬體持續調整，維持穩定效能。語意感知快取大幅減少了 agentic 編輯場景中的 prefill 重複計算，而 LRU 專家快取則有效捕捉了 decode 階段的路由局部性。彈性邊緣資源管理進一步證明，即使在執行階段可用記憶體因其他應用程式而變化，FreeToken 也能動態重建快取並繼續服務。

### 【應用與影響】

**Q10：哪些實際應用場景最能受惠於 FreeToken？**

A：程式設計代理、工具使用代理、長文件編輯與本地個人助理都能顯著受惠，因為這些場景常伴隨長上下文、頻繁狀態更新與反覆編輯。對於需要資料隱私或間歇性網路連線的環境，本地執行前沿模型也特別有吸引力。此外，任何希望降低持續 API 成本、同時又想使用最大開源模型的個人開發者或小團隊，都能直接利用自己已有的機器。

**Q11：若要把 FreeToken 產品化，需要考慮哪些因素？**

A：產品化時必須確保系統能在使用者同時執行瀏覽器、遊戲或其他應用程式時，自動偵測並適應剩餘的記憶體與計算預算。FreeToken 透過直接將專家載入最終主記憶體佈局來降低啟動延遲，這對初次使用者體驗至關重要。另外，支援 20 種以上 MoE 模型意味著需要持續維護模型轉換、量化與佈局配置，以跟上快速演進的開源權重生態。

**Q12：FreeToken 對整個領域可能帶來什麼影響？**

A：FreeToken 把「開源權重」進一步轉化為「可部署的本地軟體」，縮小了能取得模型與能實際使用模型之間的可及性差距。它挑戰了「前沿規模模型只能運行在資料中心」的預設，推動推理系統研究從雲端中心轉向邊緣原生設計。長遠來看，這可能改變模型服務的經濟結構，讓數億台消費級電腦成為分散式前沿智慧的重要載體。

### 【限制與未來】

**Q13：FreeToken 目前有哪些明顯限制？**

A：像 Kimi-K3 這樣需要 594GB 記憶體的模型仍超出消費級硬體範圍，因此 FreeToken 雖然大幅擴展了可服務規模，但並非無上限。此外，極大模型在筆電等低階硬體上雖可執行，但效能與互動體驗仍會受到 PCIe 頻寬與 CPU 能力的嚴格限制。系統效能也與執行階段的可用記憶體和背景程序密切相關，過度擁擠的環境會壓縮可使用的專家快取空間。

**Q14：在什麼情況下 FreeToken 可能表現不佳或失效？**

A：當主記憶體頻寬被其他程式大量佔用，或可用 VRAM 突然劇減時，q⋆ 政策對頻寬的估計可能失準，導致該步驟延遲上升。若遇到極長且路由分佈高度分散的 prefill，專家工作集可能趨近稠密，雙緩衝也難以完全隱藏搬運成本。另外，若 CPU 核心數或單核效能過低，直接 CPU 執行專家的路徑會成為瓶頸，使得頻寬自適應策略的效益下降。

**Q15：未來可以朝哪些方向延伸 FreeToken？**

A：未來可結合更激進的量化、剪枝與專家壓縮技術，進一步挑戰千億級以上模型在消費級硬體上的執行。也可支援多 GPU 消費級配置、整合 NPU 或整合式加速器，並發展更精準的路由預測以提升預取命中率。此外，針對能源效率、電池續航與更廣泛的代理框架整合進行最佳化，將是讓邊緣原生推理真正普及的關鍵下一步。

## 實務應用指南

### 適用場景

1. **個人開發者的本機程式設計代理**
   在僅配備 8GB VRAM 的筆電或 24GB 的消費級桌機上，執行 Qwen3.6-35B 或 DeepSeek-V4-Flash 等開源 MoE 模型，做為 GitHub Copilot/Codex 的本地替代方案。適合需要長上下文編輯、反覆生成與修改程式碼，又不希望持續支付 API 費用或上傳程式碼至雲端的開發者。

2. **小型團隊的私有工具使用代理**
   新創或小型企業可在單一工作站 GPU（如 RTX 5090/PRO 6000）上部署 GLM-5.2 或 753B 級別模型，執行具備工具呼叫能力的客服、知識庫問答或資料分析代理。由於 FreeToken 支援執行階段記憶體彈性調整，可在同一台機器同時運行瀏覽器、資料庫與其他背景服務。

3. **離線/邊緣環境的高階推理**
   適用於網路不穩定、資料無法外流的場景，例如醫療診所、法律事務所或政府單位，在本地消費級硬體上執行前沿規模模型，進行文件摘要、合規檢查或專業領域問答。

4. **教育與研究的低成本模型實驗**
   學生與研究人員可在自有遊戲桌機或筆電上，實際執行與量測 284B、753B 等級 MoE 模型，進行提示工程、代理行為分析或系統效能研究，無需申請昂貴的資料中心 GPU 叢集。

5. **長上下文代理工作負載的互動式應用**
   例如具備多輪對話、思考鏈（thinking segments）與工具呼叫的編碼或數學代理。FreeToken 的語意感知快取可在語意邊界建立檢查點，減少編輯後重新計算的成本，適合需要頻繁來回修改的互動場景。

### 實作前置條件

**資料與模型**
- 取得支援的開源 MoE 權重，例如 DeepSeek-V4-Flash、GLM-5.2、Qwen3.6-35B 等（共 20 款以上）。
- 確認模型授權允許本地部署與目標用途。
- 準備足夠的磁碟空間與主記憶體：完整專家池可能遠超 GPU VRAM，需依賴主記憶體甚至 SSD 做為後備。

**運算資源**
- **最低**：8GB VRAM 的筆電 GPU，可執行 35B 級別模型。
- **推薦**：24GB 以上消費級 GPU（如 RTX 4090/5090）執行 284B 模型。
- **高階**：32GB 以上工作站 GPU（如 RTX PRO 6000）執行 753B GLM-5.2。
- 足夠的主記憶體容量與 PCIe 頻寬，因為未常駐 GPU 的專家需透過互連傳輸。

**技術能力**
- 熟悉 Linux/Windows 環境下的 PyTorch、CUDA 與模型推理流程。
- 理解 MoE 架構、KV Cache、CPU–GPU 卸載（offloading）與記憶體管理基礎。
- 具備閱讀與修改推理框架配置的能力，以便根據硬體調整快取大小與頻寬自適應參數。

### 實作步驟建議

1. **硬體能力盤點**
   量測目標機器的 GPU VRAM、主記憶體容量、PCIe 頻寬與 CPU 核心數。這些數值將決定 FreeToken 的專家快取大小與 q⋆ 分割策略。

2. **安裝 FreeToken**
   從 `flashml.ai` 取得發行版本，依照官方文件完成環境建置、CUDA 驅動與相依套件安裝。

3. **載入模型並建立初始佈局**
   使用 FreeToken 的模型載入流程，將專家直接載入最終的主記憶體佈局，減少啟動延遲。根據 VRAM 大小設定 GPU 專家快取（LRU cache）的初始容量。

4. **設定頻寬自適應參數**
   針對目標硬體校準 q⋆ 策略：在解碼階段，決定每一個 step 的 cache miss 有多少比例透過 PCIe 回填至 GPU、有多少比例直接在 CPU 執行。可透過內建基準測試自動搜尋或手動調整。

5. **啟用語意感知快取**
   對於代理工作負載，開啟在 thinking segments、tool calls 等語意邊界建立 recurrent state checkpoint 的功能，並確認編輯後的後綴重新計算流程正確。

6. **執行真實工作負載驗證**
   使用實際的 coding-agent traces 或工具呼叫對話進行壓力測試，觀察 prefill 與 decode 的吞吐量、cache hit rate 與記憶體波動。

7. **部署彈性資源管理監控**
   設定執行階段記憶體預算與安全檢查點。當背景應用佔用記憶體變化時，FreeToken 應能動態縮放 GPU 專家快取而不需重啟引擎。

8. **產品化封裝**
   將 FreeToken 包裝為本地 API 服務或桌面應用後端，整合至 IDE 外掛、聊天介面或代理框架，並設定用量監控與錯誤回退機制。

### 潛在風險與注意事項

- **記憶體不足導致效能斷崖**
  當背景應用佔用記憶體時，FreeToken 雖可動態縮減 GPU 快取，但過度縮放會使 cache miss 激增、PCIe 成為瓶頸。建議保留系統級記憶體緩衝，並設定硬下限。

- **長提示的 prefill 瓶頸**
  長提示會使專家工作集趨於稠密，導致大量專家需從主記憶體搬移。可透過語意邊界切分提示、使用 checkpoint 重用，或避免一次性餵入過長上下文。

- **硬體異質性造成配置難以移植**
  在 RTX 4090 上調好的 q⋆ 與快取大小，未必適用於筆電 GPU 或工作站 GPU。每台部署機器都應重新執行硬體校準，避免直接複製配置檔。

- **模型授權與合規風險**
  部分開源權重模型對商業用途、輸出內容或衍生服務有限制。部署前應確認授權條款，特別是用於對外提供服務時。

- **散熱與電源穩定性**
  長時間執行 284B–753B 模型會讓消費級 GPU 與 CPU 持續高負載，需確保散熱與電源供應穩定，筆電尤其要注意降頻與電池供電限制。

- **與現有推理引擎的預期差異**
  FreeToken 的輸出應與原始模型一致，但快取、卸載與 CPU 執行路徑可能引入數值或延遲差異。上線前應進行輸出品質與延遲基準測試。

### 與其他技術的整合建議

- **與 llama.cpp / Ollama 的互補定位**
  若已使用 llama.cpp 或 Ollama 執行較小模型，可將 FreeToken 專門用於 35B 以上 MoE 模型與代理工作負載；較小模型仍維持原有引擎，避免過度複雜化。

- **與 KTransformers 的選型**
  KTransformers 同樣聚焦本地大型模型推理，但 FreeToken 更強調頻寬自適應執行與代理狀態重用。若工作負載以長上下文、多輪工具呼叫為主，可優先評估 FreeToken。

- **整合代理框架**
  可將 FreeToken 做為 LangChain、AutoGen、OpenAI Agents SDK 等框架的本地模型後端，透過 OpenAI-compatible API 提供服務，讓代理的 tool use 與 state reuse 獲得加速。

- **整合 IDE 與程式輔助工具**
  透過本地 API 將 FreeToken 接到 Continue、Cline、Cursor 替代方案或自製 VS Code 外掛，實現離線程式碼補全與重構。

- **監控與資源調度**
  可結合 Prometheus/Grafana 或系統原生監控，追蹤 GPU VRAM、主記憶體、PCIe 頻寬使用率，並在資源緊張時觸發 FreeToken 的動態快取重建。

可從系統設計與評估方法切入，思考 FreeToken 如何將「稀疏啟動」與「完整專家池的記憶體壓力」這對矛盾轉化為排程問題；未來研究方向可延伸至多 GPU 邊緣裝置、更激進的專家預測策略，或與量化、推測解碼（speculative decoding）的結合。

**產品經理**
聚焦在成本—能力帕累托前沿與實際解碼速度數據，評估 FreeToken 能否讓你的產品以「零 API 成本」在消費級硬體上提供接近雲端前沿模型的體驗；同時需並行評估授權、離線部署維護成本，以及目標用戶硬體分布是否足以支撐產品化。
