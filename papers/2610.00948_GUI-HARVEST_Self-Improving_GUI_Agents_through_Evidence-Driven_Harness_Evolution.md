# GUI-HARVEST：透過證據驅動的框架演進實現自我改進的 GUI 代理

## ⚡ TL;DR

GUI代理框架優化面臨三大挑戰：意圖與視覺對齊、執行變異診斷、任務發現轉化為可重用變更。
本文提出GUI-HARVEST，透過截圖比對與跨任務聚類失敗模式，由工程師提出有界編輯並驗證器把關。
OSWorld六款骨幹模型皆獲提升，Qwen3-VL增12.33點；遷移使GPT-5增13.87點。

## 摘要翻譯

圍繞 GUI 模型的可執行框架決定了觀察如何被彙整、動作如何被執行，以及驗證、恢復與終止如何被控制。相較於非 GUI 代理的框架優化，自動優化此框架面臨三個相互耦合的挑戰：協調模型意圖與觀察到的視覺效果、在變動的執行結果下診斷失敗，以及跨任務識別反覆出現的失敗模式並將其轉化為可重複使用的執行時變更。我們提出 GUI-HARVEST，一個自動框架優化器，能在凍結的骨幹模型下實現自我改進的 GUI 代理。首先，為了將診斷奠基於觀察到的動作效果，它將模型輸出及執行動作與執行前後螢幕截圖對齊，將發現與特定的介面轉換連結起來。其次，為了考量執行變異性，它將同一任務的重複執行視為一個聯合證據單元，利用任務內比較來定位與結果相關的行為差異。第三，它將跨任務已驗證的發現整合為反覆出現的失敗模式，將其對應到有界原始碼編輯，並在評估前記錄預測的行為效果，接著透過重複執行檢查預測的行為效果與任務效能。OSWorld-Verified 上的實驗結果顯示，在六個通用開源、GUI 專用開源與專有骨幹模型上皆有一致的留置集增益；Qwen3-VL-32B-Instruct 在完整測試集上提升 12.33 分。以凍結的框架進行遷移，在不需進一步優化的情況下，於 WindowsAgentArena 上以 50 步使 GPT-5 提升 13.87 百分點。在相同的骨幹模型與初始框架下，GUI-HARVEST 優於 Self-Harness 與 Meta-Harness，這表明 GUI 專屬診斷與驗證有助於框架改進泛化至未見任務。程式碼可於以下網址取得：https://github.com/GaryYang12345/GUI-HARVEST。

### 核心貢獻（3～5點）
- 提出 GUI-HARVEST 自動框架優化器，能在凍結的骨幹模型下實現自我改進的 GUI 代理，無需重新訓練模型即可提升電腦操作效能。
- 透過將模型輸出及執行動作與執行前後螢幕截圖對齊，將診斷奠基於觀察到的動作效果，使發現與特定介面轉換直接連結。
- 將同一任務的重複執行視為聯合證據單元，透過任務內比較定位與結果相關的行為差異，有效處理執行變異性帶來的診斷困難。
- 將跨任務已驗證的發現整合為反覆出現的失敗模式，對應到有界原始碼編輯，並在評估前預測行為效果、透過重複執行加以驗證，確保框架改進可泛化至未見任務。
- 在 OSWorld-Verified 與 WindowsAgentArena 兩個基準測試上，於通用開源、GUI 專用開源與專有骨幹模型皆取得一致的留置集增益，並優於 Self-Harness 與 Meta-Harness 等對比方法。

### 適合對象
從事 GUI 代理、電腦操作自動化、視覺語言模型應用及 AI 代理框架設計的研究人員與工程師；特別適合關注如何在不重新訓練骨幹模型的前提下，透過執行環境框架優化提升代理效能的學者與業界實務工作者；亦適合對自我改進 AI 系統、自動化診斷與程式碼修復感興趣的讀者。

## 深度分析

#### 方法論解析

GUI-HARVEST 的核心定位是「凍結骨幹模型（frozen backbone）下的自動框架優化器（automatic harness optimizer）」，其設計哲學與傳統的模型微調路線形成鮮明對比。整體方法可拆解為一個閉環式的自我改進迴圈，由四個相互耦合的模組構成：**證據分析師（Evidence Analyst）**、**跨任務聚類器（Cross-task Clusterer）**、**框架工程師（Harness Engineer）** 與 **驗證器（Validator）**，並輔以 **GUI 工具事實套件（GUI Artifact & Fact Toolkit, GAFT）** 與 **更新分類帳（update ledger）** 兩個支援元件。

**第一階段——證據驅動的視覺對齊診斷。** 傳統的代理自我改進方法（如 Self-Harness、Meta-Harness）依賴純文字軌跡（textual trace）進行診斷，但 GUI 環境中文字軌跡極具欺騙性：模型可能輸出「已點擊儲存」並回報成功，螢幕卻停留在未關閉的對話框。GUI-HARVEST 透過 Evidence Analyst 將模型輸出、執行動作與「執行前後螢幕截圖（before-and-after screenshot）」三方對齊，使每一條診斷結論都附著於具體的介面轉換（interface transition）。這項設計直接回應了第一個挑戰——模型意圖與視覺效果的解耦問題。

**第二階段——聯合證據單元（joint evidence unit）下的執行變異性處理。** 作者觀察到在確定性解碼（deterministic decoding）下，相同任務重複執行仍會出現 11.8–20.4% 的零分與正分混雜現象（視骨幹模型而定）。GUI-HARVEST 將同一任務的 K=3 次重複執行視為一個聯合證據單元，透過任務內比較（within-task comparison）找出與結果相關的行為差異（outcome-relevant behavioral difference）。當某次執行成功而另一次失敗時，分歧點往往精確指向可改進的框架行為。這種「以成功路徑為錨點」的診斷方式，比單純分析失敗軌跡更具資訊密度。

**第三階段——跨任務聚類與有界編輯（bounded edit）。** 單一任務的修補（patch）容易過擬合，GUI-HARVEST 透過 Cross-task Clusterer 將多任務的驗證後發現聚類為反覆出現的失敗模式（recurrent failure pattern），再由 Harness Engineer 將其映射為有界原始碼編輯。關鍵創新在於「預測先行」：每次編輯都必須在評估前明確記錄預測的行為效果（predicted behavioral effect），驗證器則同時檢查分數提升與行為預測是否成立。這種「先承諾、後驗證」的機制有效防止過擬合於搜尋集分數。

**第四階段——雙閘驗證器（dual-gate validator）。** 驗證器包含兩個閘門：**效用閘（utility gate）** 要求搜尋集分數增量 ΔS ≥ 0 且驗證集分數增量 ΔV ≥ 0，並要求 max(S, V) > 0 以避免雙方皆為零分的退化情況；**行為閘（behavior gate）** 則核對預測的行為變化是否在重複執行中實際發生。僅當兩個閘門同時通過時，編輯才會被寫入並記錄於分類帳，否則觸發回滾（rollback）。分類帳同時作為後續提案的上下文，避免重複嘗試已失敗的編輯方向。

**問題形式化（problem setting）層面的細節。** 框架 H₀ 包含可編輯的提示詞建構、記憶體、動作與工具介面、控制流、驗證、恢復與終止邏輯；優化器被明確禁止修改模型權重、基準任務、評估器、環境基礎設施與資源限制。任務透過領域分層隨機抽樣（domain-stratified random split）劃分為搜尋集 S、驗證集 V 與密封測試集 T，後者在優化結束前完全不開放，這是防止測試集洩漏的嚴格紀律。

#### 實驗數據解讀

**主實驗——OSWorld-Verified 六骨幹模型對比。** 圖 1 顯示在 15、50、100 步三種最大環境步數（maximum environment steps）預算下，GUI-HARVEST 在六個骨幹模型（涵蓋通用開源、GUI 專用開源與專有模型三類）上均取得最高分。值得注意的是，優化僅使用 15 步搜尋推演（search rollout），但最佳化後的凍結框架在 50 步與 100 步評估時仍持續領先，顯示其學到的是穩健的框架行為而非特定步數預算的過擬合。

**量化增益。** 在 15 步設定下，測試集分數提升介於 1.49 至 10.16 個百分點（percentage points），覆蓋全部六個凍結骨幹。Qwen3-VL-32B-Instruct 在完整測試集（full suite）上獲得最大增益，達到 50.94%（+12.33 點）。Gemini 3.1 Pro 在 100 步評估時達到 79.14%，且未經進一步優化——這顯示框架遷移性極強。

**跨環境遷移——WindowsAgentArena（WAA）。** 在 50 步設定下，Qwen3-VL-32B-Instruct 與 GPT-5 分別提升 6.47 與 13.87 個百分點，且未對 WAA 進行任何優化。這項結果特別重要，因為它證明 GUI-HARVEST 學到的是 GUI 操作中的通用機制（如點擊重試、對話框處理），而非 OSWorld 特定的捷徑。

**與同類方法的比較。** 在相同骨幹與初始框架下，GUI-HARVEST 優於 Self-Harness 與 Meta-Harness，這驗證了「GUI 專屬診斷（GUI-specific diagnosis）與驗證」相較於通用文字軌跡方法的優勢。此外，最終框架在兩個 OpenCUA 骨幹上均優於 LFF 釋出的框架，顯示其競爭力超越現有開源方案。

**結果的深層意涵。** 跨骨幹、跨環境、跨步數預算的一致性增益，意味著 GUI-HARVEST 捕捉的是 GUI 代理的「系統性弱點」而非特定模型的偏置。這與人類軟體工程師透過觀察使用者操作來改進 UI 的過程有結構上的相似性——診斷依賴視覺證據而非口頭回報。

#### 與現有研究的比較

**與 Self-Harness、Meta-Harness 的定位差異。** 後兩者將框架優化視為純文字任務，僅依賴軌跡中的自然語言回饋。GUI-HARVEST 的差異化在於：(1) 引入視覺證據作為診斷錨點；(2) 將重複執行的變異性視為資訊來源而非雜訊；(3) 強制要求編輯前預測行為效果。這三點使其在 GUI 領域的適用性顯著高於通用方法。

**與 Agent S/S2/S3 的關係。** Agent S 系列展示了執行時選擇（runtime choices）對電腦操作效能（computer-use performance）的影響，但屬於人工設計的框架演進。GUI-HARVEST 則將這一過程自動化，並透過凍結骨幹模型隔離出「框架本身的價值」。

**與其他代理框架的比較（VLAA、OS-Symphony、CoAct-1、UiPath、GTA1、OpenAPA、S2.5）。** 圖 1 顯示 GUI-HARVEST 在每個模型–預算組合下均居首位，但需注意這些框架通常針對特定骨幹或步數預算進行聯合調校，而 GUI-HARVEST 僅優化框架本身、骨幹完全凍結，這使得比較略有利於專用框架。然而 GUI-HARVEST 的跨骨幹一致性仍顯示其通用性。

**與 LFF 的比較。** LFF 釋出的框架在 OpenCUA 骨幹上被 GUI-HARVEST 超越，但 LFF 屬於 GUI 專用訓練方法，與框架優化屬於正交路線，兩者可組合使用。

**侷限性。** (1) 優化需要大量重複執行（每任務 K=3 次），計算成本不低；(2) 框架編輯被限制在「有界」範圍內，可能無法處理需要大幅重構的系統性缺陷；(3) 雖然跨 WAA 遷移成功，但遷移至行動裝置 GUI（如 AndroidWorld）尚未驗證；(4) 對極小模型（如 8B 參數級別）的增益相對有限，可能反映小模型本身的視覺理解瓶頸難以僅靠框架補償。

#### 可重現性評估

**程式碼開源。** 作者於 GitHub（https://github.com/GaryYang12345/GUI-HARVEST）公開程式碼，這是 GUI 代理研究領域的重要實踐。

**基準與資料集。** OSWorld-Verified 與 WindowsAgentArena 均為公開基準，評估器與任務定義可獲取，使結果可在相同條件下重現。

**骨幹模型可及性。** 六個骨幹模型涵蓋三類：通用開源（Qwen3-VL-8B/32B）、GUI 專用開源（OpenCUA-32B/72B）與專有（GPT-5、Gemini 3.1 Pro）。前三類可本地部署重現，後兩類需透過 API 存取，可能存在版本漂移風險。

**重現的潛在障礙。** (1) 重複執行的隨機性管理（即使在確定性解碼下，環境層仍可能有非確定性）；(2) 框架編輯的具體內容未在論文中完整披露，需仰賴程式碼庫；(3) 領域分層隨機抽樣的具體種子未明示，可能影響搜尋/驗證/測試集的具體劃分。

**整體可重現性評估：中等偏高。** 程式碼與基準公開，但完整重現需要相當的計算資源（多骨幹 × 多步數 × 多回合 × 多基準）與 API 成本。

#### 未來研究方向

**1. 跨平台 GUI 遷移。** 將 GUI-HARVEST 應用於 AndroidWorld、MobileAgentBench 等行動裝置基準，驗證其在觸控手勢、虛擬鍵盤等不同互動範式下的遷移能力。

**2. 框架編輯的語義抽象。** 目前編輯以原始碼層級進行，可探索將其提升至更高層次的「框架設計模式」庫，使編輯更具可解釋性與可組合性。

**3. 與模型微調的協同。** 雖然本文強調凍結骨幹，但框架優化與輕量微調（如 LoRA）的結合可能產生疊加效應，特別是在小模型場景。

**4. 線上持續學習。** 將離線優化擴展至線上模式，使代理在使用過程中持續改進框架，這對長生命週期的個人化助理尤為重要。

**5. 安全性與可逆性。** 框架自我修改帶來安全風險，需研究沙箱機制、編輯可逆性保證與人類監督介入點。

**6. 診斷可解釋性。** 將 Evidence Analyst 的發現以自然語言與視覺化方式呈現，使開發者能理解「為何這次編輯有效」，這對除錯與信任建立至關重要。

**7. 多模態證據的擴展。** 除截圖外，可納入螢幕錄影、輔助技術日誌（如無障礙 API）等更豐富的證據源，提升診斷的時序解析度。

**8. 理論分析。** 為何重複執行能產生有用訊號？可從資訊理論角度分析「執行變異性」與「可改進空間」之間的量化關係，為方法選擇 K 值提供理論依據。

## 論文問答

**Q1：什麼是 GUI 代理的「執行框架」(harness)，為什麼它對電腦操作任務的效能影響如此重大？**

A：執行框架是圍繞在凍結骨幹模型外層的可編輯程式系統，負責組裝觀察與脈絡、執行動作、控制驗證、恢復與終止等所有執行時決策。它涵蓋提示詞與脈絡建構、記憶體管理、動作與工具介面、控制流程、錯誤恢復機制等多個面向。雖然骨幹模型的權重在框架優化過程中保持不變，但這些執行時的選擇會直接影響代理在電腦操作任務上的表現，這也是 Agent S 與 Agent S2/S3 等研究強調框架設計重要性的原因。

**Q2：現有的自動框架優化方法（如 Self-Harness、Meta-Harness）為什麼無法直接應用於 GUI 代理？**

A：現有的自動框架優化方法主要依賴文字軌跡與文字回饋來修訂提示詞與程式碼，這在數學推理或軟體工程等非 GUI 領域已證明有效。然而 GUI 代理面臨三個獨特挑戰：模型意圖與視覺效果的對齊（文字軌跡可能聲稱成功但螢幕顯示未完成狀態）、執行變異性下的失敗診斷（同一任務在確定性解碼下仍可能產生混合結果）、以及將任務專屬發現轉化為可重複使用的執行時變更。這些挑戰使得僅憑文字軌跡的通用方法無法直接處理 GUI 代理特有的多模態執行證據。

**Q3：為什麼單一軌跡不足以診斷 GUI 代理的失敗？**

A：在 GUI 代理的執行中，即使採用確定性解碼，同一代理對同一任務仍可能在多次執行中產生截然不同的結果。根據論文報告，在基準測試中 11.8% 至 20.4% 的完整任務會在三輪執行中同時產生零分與正分，具體比例取決於所使用的骨幹模型。這意味著單一失敗軌跡無法完整描述代理的行為——其他執行可能揭示出成功的替代路徑，以及執行在哪個環節產生分歧。因此 GUI-HARVEST 將同一任務的重複執行視為聯合證據單元，透過任務內比較找出與結果相關的行為差異。

**Q4：GUI-HARVEST 的核心方法是什麼？它如何運作？**

A：GUI-HARVEST 是一個自動框架優化器，透過三個對應的設計選擇來實現自我改進的 GUI 代理。首先，證據分析師（Evidence Analyst）將模型輸出與執行動作與執行前後的螢幕截圖對齊，使診斷結果與具體的介面轉換相連結。其次，跨任務聚類器（Cross-task Clusterer）將經過驗證的發現歸納為反覆出現的失敗模式，並由框架工程師（Harness Engineer）將這些模式映射為有界的原始碼編輯，同時在評估前記錄對行為效果的預測。最後，驗證器（Validator）結合分數檢查與行為檢查，只有在搜尋與留置驗證任務上重複執行皆通過時才會採用該編輯，並透過更新分類帳引導後續提案。

**Q5：GUI-HARVEST 如何透過「證據驅動」的方式將模型意圖與視覺效果對齊？**

A：GUI-HARVEST 的證據分析師並非僅依賴文字軌跡來判斷動作是否成功，而是將模型輸出與執行動作與執行前後的螢幕截圖進行對齊。這種對齊方式能夠識別出意圖與觀察狀態變更之間的差異，例如代理點擊「儲存」按鈕但對話框仍然開啟的情況。透過保留與支援性文字和影像的連結，所產生的發現不僅指出失敗，更能定位到具體的介面轉換點，從而使診斷結果具有可追溯的視覺證據基礎。

**Q6：為什麼 GUI-HARVEST 採用「行為門檻」(behavior gate) 而非僅依賴分數提升來驗證框架修改？**

A：僅依賴總體分數提升來驗證框架修改是不夠的，因為更高的總體分數並不能證明反覆出現的失敗模式已被修正。為此 GUI-HARVEST 在評估前要求框架工程師對每項原始碼編輯記錄可觀察行為效果的預測，然後由驗證器同時進行分數門檻檢查（搜尋集與驗證集分數皆不退步）與行為門檻檢查（預測的行為變更得到支援）。只有當兩個門檻皆通過時，該編輯才會被採用，否則將觸發回滾機制，這種雙重驗證機制確保了框架修改確實針對了預期的失敗模式。

**Q7：GUI-HARVEST 在 OSWorld-Verified 上的主要實驗結果為何？**

A：GUI-HARVEST 在 OSWorld-Verified 上針對六個骨幹模型（涵蓋通用開源、GUI 專用開源與專有模型）皆展現一致的留置集增益。在 15 步預算下，測試分數在所有六個凍結骨幹模型上提升 1.49 至 10.16 個百分點，其中 Qwen3-VL-32B-Instruct 達到最大的完整測試集增益 50.94%（提升 12.33 點）。值得注意的是，在 15 步搜尋推演下優化的框架在 50 步與 100 步評估預算下表現更佳，Gemini 3.1 Pro 在 100 步時達到 79.14%，且無需進一步優化。

**Q8：GUI-HARVEST 優化後的框架是否能遷移到不同的環境？WindowsAgentArena 上的結果如何？**

A：GUI-HARVEST 展現了優秀的跨環境遷移能力。在未對 WindowsAgentArena（WAA）進行任何優化的情況下，將 OSWorld 上優化後的凍結框架遷移至 WAA，在 50 步預算下使 Qwen3-VL-32B-Instruct 與 GPT-5 的分數分別提升 6.47 與 13.87 個百分點。這項結果顯示 GUI-HARVEST 所產生的框架修改並非僅針對特定基準測試的過擬合，而是捕捉到了 GUI 代理執行中更通用的失敗模式與改進機會。

**Q9：GUI-HARVEST 與 Self-Harness、Meta-Harness 等通用框架優化方法的比較結果如何？**

A：在相同的骨幹模型與初始框架條件下，GUI-HARVEST 在 Qwen3-VL-32B-Instruct 上表現優於 Self-Harness 與 Meta-Harness。這項比較結果支持了論文的論點：GUI 專屬的診斷與驗證機制（特別是利用多模態證據與行為門檻）有助於產生對未見任務更具泛化能力的框架改進。此外，GUI-HARVEST 最終的框架在兩個 OpenCUA 骨幹模型上也優於 LFF 釋出的框架，進一步驗證了其在 GUI 專用模型上的有效性。

**Q10：GUI-HARVEST 在實際產品部署中可能有哪些應用場景？**

A：GUI-HARVEST 的技術可應用於任何需要自動化桌面操作的場景，包括企業內部系統的批次操作、客服自動化、軟體測試、資料遷移與報表生成等。透過持續優化執行框架，企業可以在不重新訓練模型的情況下，隨著代理執行的累積逐步提升自動化效率。對於需要長期部署的 GUI 代理系統而言，這種自我改進能力意味著系統能夠從自身的執行經驗中學習，適應新的介面變化與任務模式。

**Q11：在實際部署 GUI-HARVEST 優化後的框架時，需要考量哪些工程因素？**

A：實際部署時需要考量幾項關鍵工程因素：首先，必須將任務劃分為搜尋集、驗證集與密封測試集，並透過領域分層的隨機分割維持各領域比例，以避免資料洩漏。其次，搜尋階段需要每個任務執行 K=3 輪以收集足夠的證據，這會帶來顯著的計算成本，需要評估是否值得投入。此外，能力清單（capability manifest）明確界定了哪些框架檔案可被編輯以及新模組可在何處建立，這種受限的編輯空間有助於維持系統穩定性，但也限制了優化的靈活性。

**Q12：GUI-HARVEST 對 GUI 代理研究領域的影響是什麼？**

A：GUI-HARVEST 將框架優化從以文字軌跡為基礎的方法擴展到多模態證據驅動的方法，這對 GUI 代理研究領域具有方法論上的重要意義。它證明了視覺證據（執行前後螢幕截圖）對於診斷 GUI 代理失敗是不可或缺的，並展示了如何將反覆出現的失敗模式系統性地轉化為可重複使用的程式碼改進。這種「證據驅動自我改進」範式為未來 GUI 代理研究提供了一個新方向，特別是在如何讓代理從自身執行經驗中持續學習的問題上。

**Q13：GUI-HARVEST 的方法有哪些已知的限制？**

A：根據論文設定，GUI-HARVEST 的優化器無法修改模型權重、基準測試任務、評估器、環境基礎設施或資源限制，這些限制雖然確保了評估的公平性，但也意味著某些類型的改進無法透過此方法達成。此外，能力清單限制了可編輯的框架檔案範圍，這種受限的編輯空間雖然有助於維持系統穩定，但可能限制了優化的潛力。論文也指出，搜尋階段每個任務需要 K=3 輪執行，這在計算成本上是一個顯著的負擔。

**Q14：GUI-HARVEST 在哪些情況下可能會失敗？**

A：GUI-HARVEST 在幾種情況下可能會面臨挑戰：當執行變異性過高時，即使經過多次重複執行，聯合證據單元仍可能無法提供清晰的診斷依據。此外，若框架工程師對行為效果的預測不準確，行為門檻可能會拒絕實際有益的編輯或接受無效的編輯。當失敗模式無法被歸納為跨任務的反覆出現模式時，跨任務聚類器可能無法產生有意義的聚類，導致無法提出有效的框架修改。

**Q15：GUI-HARVEST 未來可以朝哪些方向發展？**

A：GUI-HARVEST 的未來發展方向可能包括：擴展到更多樣化的作業系統與應用程式環境、支援更複雜的多步驟任務與長期規劃、整合更大規模的骨幹模型以提升基礎能力。此外，研究如何減少搜尋階段所需的執行次數（從 K=3 降低）以降低計算成本，或探索如何讓框架修改在不同的骨幹模型間共享而非僅針對單一模型優化，都是值得探索的方向。最終，將 GUI-HARVEST 與其他自我改進方法（如反射式提示或記憶增強）結合，可能會產生更強大的 GUI 代理系統。

### 適用場景

1. **企業內部 RPA 自動化升級**：將既有以規則為基礎的桌面自動化流程，替換為基於視覺語言模型的 GUI 代理，並透過 GUI-HARVEST 自動調校執行框架，使其在 ERP、CRM 等企業軟體中能穩定處理對話框殘留、頁面跳轉失敗等常見問題，無需重新訓練模型即可提升任務成功率。

2. **跨平台客服與技術支援助理**：部署於 Windows 與 macOS 環境的客服助理需同時操作瀏覽器、桌面應用與系統設定。GUI-HARVEST 透過凍結框架遷移（frozen-harness transfer）特性，可在 OSWorld 優化後直接套用至 WindowsAgentArena 等不同環境，縮短跨平台部署成本。

3. **無障礙輔助與長者數位包容工具**：為視障或數位能力較弱的用戶打造的輔助代理，常因介面元素位置變動而失敗。GUI-HARVEST 的反覆失敗模式聚類機制可自動產生「點擊前先截圖確認」「對話框未關閉時重試」等可重用的執行時補丁，提升真實使用情境下的可靠性。

4. **軟體測試與回歸驗證代理**：QA 團隊可將 GUI-HARVEST 套用於 GUI 測試代理，使其在執行重複測試時自動比對多次執行的行為差異，識別出偶發性失敗並產生對應的容錯邏輯，減少 flaky test 問題。

5. **開源 GUI 代理框架的持續改進**：如 OpenCUA、Agent S 系列等開源專案的維護者，可將 GUI-HARVEST 整合進 CI/CD 流程，在新版本模型釋出時自動優化框架，避免每次模型更新都需手動調整提示與控制流程。

### 實作步驟建議

**步驟一：建立基準環境與能力清單**
複製官方程式碼（https://github.com/GaryYang12345/GUI-HARVEST），定義 capability manifest，明確列出可編輯的框架檔案（提示組裝、動作介面、控制流程、驗證/恢復/終止模組）以及禁止修改的部分（模型權重、評估器、環境基礎設施）。

**步驟二：準備任務切分與初始框架**
將目標任務集依領域（如瀏覽器、檔案管理、系統設定）以固定比例隨機切分為 search、validation、sealed test 三組。準備初始框架 H0，確保其具備完整的截圖擷取、動作執行、軌跡記錄功能。

**步驟三：執行搜尋推演蒐集證據**
對 search 集中的每個任務執行 K=3 次重複 rollout，產生前/後截圖對齊的軌跡資料。建議同步記錄模型意圖文字（如「點擊 Save」）與實際視覺效果，便於後續 Evidence Analyst 比對。

**步驟四：部署 Evidence Analyst 進行任務內診斷**
針對同一任務的多筆軌跡，自動比對成功與失敗路徑，識別出「意圖與視覺效果不一致」的失敗點（例如宣稱完成但對話框仍開啟）。輸出應保留文字與影像證據的連結。

**步驟五：透過 Cross-task Clusterer 聚類失敗模式**
將多任務的診斷結果聚類為反覆出現的失敗模式（如「迴圈卡住」「誤判完成」「動作路由錯誤」），並標註其對應的共用執行機制。

**步驟六：Harness Engineer 提出有界編輯與預測**
針對每個失敗模式，由 Harness Engineer 提出對框架原始碼的有界編輯（bounded edit），並在套用前明確記錄「預期的行為效果」（例如「點擊後若對話框未關閉則重試 3 次」）。

**步驟七：Validator 雙重閘門驗證**
對每個候選編輯 H'，執行：
- **Utility Gate**：在 search 與 validation 集上重複執行，確認 ΔS ≥ 0、ΔV ≥ 0 且 max(S, V) > 0
- **Behavior Gate**：比對實際行為變化是否與預測一致

僅當兩閘門皆通過才將 H' 寫入更新帳本（update ledger），否則回滾至 H。

**步驟八：迭代直至收斂**
重複步驟三至七，每次迭代以當前最佳框架為起點。建議設定最大迭代次數或預算上限，避免無止境優化。

**步驟九：密封測試與遷移評估**
迭代停止後，於 sealed test 集評估最終框架 H*；若需遷移至其他環境（如 WindowsAgentArena），直接以凍結的 H* 評估，不進行額外優化以驗證泛化能力。

### 潛在風險與注意事項

**風險一：過度擬搜尋集，泛化能力下降**
- **現象**：search 集分數持續上升，但 validation 與 test 集停滯或下降
- **緩解**：嚴格遵守 ΔV ≥ 0 的驗證閘門；保留 sealed test 直至最佳化完全停止；採用 domain-stratified 切分確保各領域皆有代表

**風險二：行為預測與實際效果不一致**
- **現象**：Harness Engineer 宣稱某補丁會修正「對話框未關閉」問題，但實際僅改變了點擊座標
- **緩解**：Behavior Gate 強制比對預測與實測；要求預測以可觀察的視覺或動作指標表述（如「截圖中對話框消失」），而非抽象描述

**風險三：執行變異性導致診斷誤判**
- **現象**：同一任務三次執行結果分歧（11.8–20.4% 的任務會出現零分與正分並存），單次失敗軌跡可能誤導診斷方向
- **緩解**：始終以 K=3 聯合證據單元進行分析；優先採用成功路徑作為對照基準；避免僅憑單一失敗軌跡提出編輯

**風險四：有界編輯累積造成框架複雜度膨脹**
- **現象**：多輪迭代後框架摻雜大量特殊情境補丁，可維護性下降
- **緩解**：定期重構框架、合併相似補丁；設定編輯數量上限；保留完整的 update ledger 以利回溯

**風險五：模型 API 變動或環境升級導致框架失效**
- **現象**：骨幹模型更新版本後，原本優化的提示與動作介面不再適用
- **緩解**：將 capability manifest 與框架版本一同管理；在新模型上線時重新執行小批次驗證，必要時觸發新一輪 GUI-HARVEST 最佳化

**風險六：評估器與環境基礎設施被意外修改**
- **現象**：Harness Engineer 為提升分數而修改了評估邏輯，污染了測試結果
- **緩解**：在 capability manifest 中明確禁止修改評估器與環境；對編輯進行靜態檢查；保留 baseline 評估器作為對照

### 與其他技術的整合建議

**與 Self-Harness、Meta-Harness 等通用框架優化方法整合**
GUI-HARVEST 並非取代通用方法，而是 GUI 專屬的診斷與驗證層。可將 Self-Harness 的 prompt 搜尋作為 GUI-HARVEST 的初始框架產生器，再以視覺證據驅動的迭代精煉其輸出，兼顧通用性與 GUI 特性。

**與 Agent S / Agent S3 等代理框架整合**
GUI-HARVEST 的能力在於優化既有框架的執行時行為。可將其作為 Agent S3 的外掛模組，在不改動其核心架構的前提下，自動產生適配特定模型（如 Qwen3-VL、OpenCUA）的客製化補丁。

**與 LFF（Learning from Failure）等失敗學習方法整合**
LFF 專注於從失敗中學習策略，GUI-HARVEST 則專注於從失敗中學習框架行為。兩者可串接使用：LFF 產生的失敗案例可作為 GUI-HARVEST 的搜尋集證據來源；GUI-HARVEST 修正的框架可作為 LFF 的更穩定執行環境。

**與傳統 RPA 工具（UiPath、Automation Anywhere）整合**
將 GUI-HARVEST 視為「AI 代理層」，傳統 RPA 負責處理結構化、可預測的流程，視覺語言模型代理處理例外與未知介面。GUI-HARVEST 優化後的框架可作為兩者間的協調層，自動將失敗的視覺操作降級為傳統 RPA 規則。

**與 CI/CD 與 MLOps 流程整合**
將 GUI-HARVEST 的迭代流程封裝為 pipeline：每次新模型釋出或環境變更時，自動觸發小批次 search rollout → Evidence Analyst → 候選編輯 → Validator，並將最終 H* 部署至 staging 環境進行 A/B 測試。

**與監控與可觀測性平台整合**
GUI-HARVEST 產生的 update ledger 與診斷報告可匯入 ELK、Loki 等日誌系統，或 Grafana 儀表板，供 SRE 團隊追蹤框架演進歷史與失敗模式分布。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的「三個挑戰」段落，理解為何 GUI 代理的框架優化比一般 LLM 代理更困難——核心在於「模型說它做對了，但螢幕顯示沒做對」這種意圖與視覺效果的落差。接著看 Figure 2 的自我改進迴路圖，掌握 Evidence Analyst、Cross-task Clusterer、Harness Engineer、Validator 四大元件的分工即可，暫時跳過數學與實驗細節。

**給 AI 工程師**：重點關注第 2 節的問題形式化（problem setting）與第 3 節的演算法細節，特別是 Validator 的雙閘門設計（Utility Gate + Behavior Gate）以及 update ledger 的回滾機制。實作時可直接參考官方程式碼，先以 Qwen3-VL-8B 在小規模 search 集上重現 15-step 的結果，再逐步擴展。建議將 capability manifest 與 bounded edit 的概念內化為團隊的框架治理準則。

**給研究者**：本文的核心貢獻在於將「執行變異性」與「視覺證據」納入框架優化的理論框架，並以「預測-驗證」閉環取代單純的分數最大化。可深入分析 Evidence Analyst 的對齊機制、Cross-task Clusterer 的聚類準則，以及為何 frozen-harness transfer 能跨環境泛化（OSWorld → WindowsAgentArena）。Appendix 中的消融實驗與失敗案例分析值得仔細研讀，以找出後續可延伸的研究問題，例如多模態證據的因果推論、跨任務失敗模式的理論刻畫等。

**給產品經理**：聚焦於第 1 節的應用動機與第 4 節的實驗結果。關鍵訊息是：GUI-HARVEST 能在不重新訓練模型的前提下，跨六種骨幹模型（含閉源 GPT-5、Gemini 3 Pro）穩定提升 1.49–12.33 百分點，且優化後的框架可直接遷移至其他環境（WindowsAgentArena 提升 13.87 百分點）。這意味著產品可在既有模型基礎上，以工程化方式持續提升代理可靠性，無需等待下一代模型。建議評估將其納入產品迭代週期，作為模型更新與環境變更時的標準補強流程。
