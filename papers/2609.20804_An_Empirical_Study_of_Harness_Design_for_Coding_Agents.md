## ⚡ TL;DR

現有編碼載具評估多視為整體，難以釐清個別元件貢獻。
本研究提出輕量模組化載具，固定執行迴圈並獨立調整規劃、動作空間與上下文管理。
結果顯示上下文管理防溢位、先省略後摘要最高效、規劃隨模型增強轉為省成本，預定義工具利Bash弱模型。

## 摘要翻譯

編碼載具（coding harnesses）形塑了自主編碼代理（autonomous coding agents）如何將模型能力（model capabilities）轉化為長期軟體工程效能（long-horizon software-engineering performance），然而現有研究通常將載具視為整體式系統（monolithic systems）進行評估，使得個別元件的有效性仍不清楚。為了實現元件層級比較（component-level comparisons），我們使用一個執行迴圈（execution loop）固定、僅變動三個元件的輕量編碼載具（lightweight coding harness）來研究此問題：規劃（planning）、動作空間（action space）與上下文管理（context management）。我們在四個模型上，分別於 SWE-Bench Verified 與 Terminal-Bench 2.1 進行評估，評估了 176 種配對設定（matched settings），涵蓋五種上下文管理策略（context-management strategies）、四種上下文視窗預算（context-window budgets），以及規劃與動作空間的針對性消融實驗（targeted ablations）。我們發現：(1) 隨著上下文視窗預算（context-window budgets）趨緊，上下文管理（context management）變得越來越有價值，其大部分效益來自於防止上下文溢位失敗（context-overflow failures）。(2) 先以分階段規則式省略（staging rule-based elision）處理，再輔以基於 LLM 的摘要（LLM-based summarization），在所有上下文管理策略（context-management strategies）中帶來最高的整體效率；而讓被省略的內容（elided content）可恢復（recoverable）則會引入鮮少被模型使用的額外機制，且無法帶來準確性（accuracy）提升。(3) 對較弱模型而言，規劃（planning）是準確性鷹架（accuracy scaffold）；對較強模型則轉為成本節省機制（cost saver），準確性幾乎不變。(4) 預定義工具（predefined tools）能提升 Bash 熟練度（bash proficiency）較弱模型的表現；而具備 Bash 能力的模型使用僅 Bash 介面（bash-only interface）即可有效運作，並顯著降低成本，尤其在以命令列為中心的任務（command-line-centric tasks）上。軌跡層級分析（trajectory-level analysis）解釋了這些效應：上下文管理（context management）延長了執行軌跡（execution trajectories），而未大幅改變代理行為（agent behavior）；規劃（planning）改變了軌跡終止的位置；動作空間（action space）則改變了程式碼撰寫的粒度（granularity）。這些發現有助於設計能同時考量模型特性與預算限制的載具，並提供一個模組化框架以評估未來的載具元件（harness components）。

### 核心貢獻（3～5點）
- 提出一個執行迴圈固定、可替換規劃（planning）、動作空間（action space）與上下文管理（context management）的輕量編碼載具（lightweight coding harness），使編碼載具能進行元件層級比較（component-level comparisons）。
- 在四個模型、SWE-Bench Verified 與 Terminal-Bench 2.1 上評估 176 種配對設定（matched settings），涵蓋五種上下文管理策略（context-management strategies）、四種上下文視窗預算（context-window budgets）與針對性消融實驗（targeted ablations）。
- 發現上下文管理在視窗預算緊縮時價值提升，分階段規則式省略（staging rule-based elision）搭配基於 LLM 的摘要（LLM-based summarization）效率最佳；可恢復的省略內容（recoverable elided content）則鮮少使用且無助於準確性。
- 揭示規劃對弱模型是準確性鷹架（accuracy scaffold），對強模型則轉為成本節省機制（cost saver）；動作空間設計應視模型 Bash 熟練度（bash proficiency）而定，Bash 能力強的模型使用僅 Bash 介面（bash-only interface）即可顯著降低成本。
- 透過軌跡層級分析（trajectory-level analysis）解釋各元件如何影響執行軌跡（execution trajectories）與程式碼撰寫粒度（granularity），為模型與預算感知的載具設計提供模組化評估框架。

### 適合對象
適合從事自主編碼代理、編碼載具（coding harnesses）或 LLM 代理系統設計與評估的研究者與工程師，特別是關注上下文管理、規劃鷹架（planning scaffold）、動作介面（action interface）與成本效益，以及希望以模組化方式比較不同載具元件的讀者。

## 深度分析

#### 方法論解析

本研究的核心貢獻在於將編碼載具（coding harness）拆解為可獨立操弄的元件，並在固定執行迴圈（execution loop）的前提下，系統性地估計每個元件的條件效應。作者從頭打造了一個輕量編碼載具（lightweight coding harness），其底層遵循 ReAct 迴圈：每一回合包含推理（reasoning）、動作（action）與觀察（observation）。為了隔離單一元件的影響，諸如權限處理（permission handling）、編輯後診斷（post-edit diagnostics）、卡住偵測（stuck detection）等輔助機制均保持固定，僅變動以下三個中央元件：

1. **規劃（planning）**：啟用時，模型會透過 `update_plan` 工具維護一份明確且持續存在的任務進度（task progress）計畫。系統提示（system instruction）與首回合提醒會要求模型先產生初始計畫再行動；後續回合則將計畫附加至模型輸入，但不存入對話歷史。關閉規劃時，研究者移除所有規劃相關指令、提醒、計畫注入與工具，其餘機制不變。
2. **動作空間（action space）**：分為兩種介面——預定義工具組（predefined tools）與僅 Bash 介面（bash-only interface）。前者提供結構化的工作空間操作（workspace operations），後者則讓模型直接以 Bash 指令與環境互動。
3. **上下文管理（context management）**：設計五種策略，從無壓縮到多階段組合：
   - **T0**：不進行跨回合壓縮，超出上下文視窗（context window）即終止。
   - **T1**：規則式省略（rule-based elision）過時的工具觀察。
   - **T2**：在 T1 基礎上加入外部儲存與 `recall_event`，使被省略內容（elided content）可恢復（recoverable）。
   - **T3**：不使用省略，改以基於 LLM 的摘要（LLM-based summarization）壓縮歷史。
   - **T4**：分階段策略，先執行規則式省略，再於必要時呼叫 LLM 摘要，並保留可恢復的外部儲存。

實驗設計上，作者選用 Nemotron-3 家族（30B、120B、550B）作為同一家族模型規模軸度（within-family model-scale axis），並以 Mistral-Medium-3.5-128B 作為跨家族比較。評估基準測試（benchmarks）為 SWE-Bench Verified（倉庫層級 issue 修復）與 Terminal-Bench 2.1（端到端終端機任務）。上下文管理實驗涵蓋 32k、64k、96k、128k 四種上下文視窗預算（context-window budgets），並在 128k 搭配 T4 的條件下額外進行規劃與動作空間的針對性消融實驗（targeted ablations），總計 176 個配對設定（matched settings）。評量指標除了成功率（success rate）與成本（cost）外，還包含軌跡層級分析（trajectory-level analysis），檢視任務進展、終止行為、上下文使用與工具呼叫模式。

#### 實驗數據解讀

**上下文管理：預算緊縮時的關鍵防線**
研究發現上下文管理的價值隨上下文視窗預算收緊而上升，其主要貢獻並非改變模型決策品質，而是防止上下文溢位失敗（context-overflow failures）導致的過早終止。當預算充裕（如 128k）時，各策略間的準確率差距縮小；但在 32k 或 64k 等緊縮情境，缺乏管理的 T0 會因軌跡過長而中斷，無法進入程式碼修改與驗證階段。這顯示上下文管理首先是一種「執行續航力」機制，其次才是資訊品質機制。

**T4 的綜合效率優勢**
在五種上下文管理策略（context-management strategies）中，T4（分階段規則式省略 + 可恢復儲存 + LLM 摘要）在平均成功率上與其他管理策略相當，但能有效控制峰值上下文（peak context）並減少昂貴的 LLM 摘要呼叫。相對地，T3 單純依賴 LLM 摘要，成本較高；T2 雖然讓被省略內容可恢復，但模型很少呼叫 `recall_event`，且相較於僅使用 T1 並未帶來準確率提升。這暗示「可恢復性」在目前設定中屬於過度設計（over-engineering）：規則式省略已能移除大多數無用資訊，而可恢復機制增加的機械複雜度未被模型充分利用。

**規劃：從準確性鷹架到成本節省機制**
規劃（planning）的效應呈現明顯的模型能力依賴性。對於較弱的模型（如 Nemotron-3 30B），規劃鷹架（planning scaffold）能延長執行軌跡（execution trajectories），讓代理有機會嘗試編輯，從而提升成功率，但代價是更高的成本。對於較強的模型（如 Nemotron-3 550B 或 Mistral-Medium-3.5-128B），規劃對準確率的提升有限，主要價值在於減少編輯後多餘的驗證步驟，轉化為成本節省機制（cost saver）。這項發現對實務設計極具啟發：不應將規劃視為「永遠有益」的元件，而需根據模型能力決定其啟用與否。

**動作空間：Bash 熟練度決定最適介面**
預定義工具（predefined tools）對 Bash 熟練度（bash proficiency）較弱的模型有明顯幫助，因為它們降低了對 shell 指令的依賴，將意圖直接轉譯為結構化工作空間操作。相反地，Bash 能力強的模型在僅 Bash 介面（bash-only interface）下表現不遜色，且能透過單次呼叫組合多個操作，顯著降低成本，尤其在以命令列為中心的任務（command-line-centric tasks）如 Terminal-Bench 2.1 上更為明顯。這揭示了動作空間設計中的準確率–成本權衡（accuracy–cost trade-off）具有任務類型與模型能力雙重依賴性。

**軌跡層級分析的機制解釋**
軌跡層級分析（trajectory-level analysis）進一步區分了三種元件的作用機制：
- 上下文管理主要「延長」執行軌跡，但不顯著改變代理行為（agent behavior）的本質；
- 規劃改變軌跡「終止的位置」，決定代理是否會持續到編輯或驗證階段；
- 動作空間則改變程式碼撰寫的粒度（granularity），預定義工具傾向細粒度、單一目的操作，而 Bash 介面則允許粗粒度、批次化操作。

#### 與現有研究的比較

相較於既有研究多將編碼載具視為整體式系統（monolithic systems）進行比較，本研究明確區分出規劃、動作空間與上下文管理三個元件，並估計其各自條件效應。這種模組化視角彌補了跨框架評估（cross-harness evaluation）的一項根本缺陷：當 OpenHands 與 SWE-Agent 等完整載具表現不同時，無法判斷差異來自工具設計（tool design）、規劃鷹架、上下文管理策略，還是與底層模型的交互作用。Cao et al.（2026）已指出不同模型對載具有不同偏好，本研究則進一步說明這些偏好背後的元件層級機制。

此外，過去雖有研究探討元件互動（component interactions）與架構選擇（architectural choices），但鮮少同時涵蓋實作層級的規劃、工作空間動作介面（workspace action interfaces）與上下文管理策略，並在明確的上下文視窗預算掃描與同一家族模型規模軸度下進行長期軟體工程任務評估。本研究透過固定執行迴圈與系統性消融，提供了更具因果解釋力的證據。

**限制**
儘管方法嚴謹，仍有若干限制。首先，實驗僅涵蓋四個模型與兩個基準測試，規劃與動作空間的具體實作（如 `update_plan` 協定、預定義工具集合）可能無法直接推廣至其他語言、框架或任務。其次，成本估算可能受 API 定價與模型推理效率影響，未必能完全反映實際部署開銷。再者，本研究未納入人類評估或真實世界軟體維護情境，成功率的提升是否對應到可維護、可審查的程式碼變更，仍需進一步驗證。最後，上下文管理策略雖多，但未探索動態或學習式策略，例如依任務階段調整壓縮強度。

#### 可重現性評估

在資料與模型可取得性方面，本研究所使用的兩個基準測試 SWE-Bench Verified 與 Terminal-Bench 2.1 均為公開資料集，有利於重現。Nemotron-3 系列與 Mistral-Medium-3.5-128B 可透過 API 或模型權重（model weights）管道取得，但具體可及性取決於授權與服務條款。然而，根據提供的文本，作者並未明確說明是否公開釋出輕量編碼載具的原始碼、設定檔或完整實驗軌跡。文中提及圖 15、16、17、30 等附錄包含系統提示、首回合提醒與工具定義，這些細節對重現至關重要，但僅在論文附錄中呈現並不等同於開源釋出。

若作者後續公開程式碼與配置，則本研究的可重現性（reproducibility）將相當高：執行迴圈固定、元件可獨立開關、上下文管理策略與視窗預算均有明確定義。反之，若僅有論文描述，其他研究者仍需重新實作載具，可能因細節差異（如 stuck detection 閾值、post-edit 診斷邏輯）導致結果漂移。建議未來版本補充以下資訊：完整原始碼倉庫、每個實驗設定的隨機種子與執行軌跡、成本計算公式，以及模型 API 版本與超參數。

#### 未來研究方向

1. **自適應上下文管理（adaptive context management）**：設計依任務階段或剩餘預算動態調整壓縮強度的策略，例如在前期保留完整觀察、後期啟用積極摘要，或根據模型對被省略內容的召回需求自動決定是否啟用可恢復儲存。
2. **學習式摘要與省略**：比較基於 LLM 的摘要與規則式省略後，可進一步探索以輕量模型學習「何時摘要、何時省略」的策略，以降低對昂貴 LLM 呼叫的依賴。
3. **動態規劃粒度**：規劃鷹架對強弱模型效應不同，未來可研究可選式或階層式規劃（hierarchical planning），讓模型依任務複雜度自動決定計畫細緻程度。
4. **更豐富的動作空間**：除了預定義工具與 Bash 介面，可納入 IDE 級操作（如重構、跨檔案搜尋、版本控制指令）或多模態觀察，並探討其對不同模型 Bash 熟練度的互補效應。
5. **成本–準確率聯合最佳化**：建立以資源預算（resource budget）為限制的載具設計框架，自動為給定模型與任務類型選擇最適的規劃、動作空間與上下文管理組合。
6. **跨任務與跨語言驗證**：將模組化載具擴展至更多程式語言、更大規模程式庫與真實 GitHub issues，檢驗研究發現的外部效度。
7. **多代理與人機協作載具**：在單一代理載具的基礎上，探索規劃、動作空間與上下文管理如何在多代理系統或人機回圈（human-in-the-loop）設定中重新配置。

## 論文問答

**Q1：這篇論文要解決的核心研究問題是什麼？**
A：核心問題在於編碼載具的各個元件——規劃、動作空間與上下文管理——是普遍有效，還是其效果取決於模型能力、任務類型與資源預算。過去研究通常把編碼載具當成整體式系統來評估，導致無法釐清單一元件的貢獻。本研究因此提出元件層級比較的框架，以估計每項介入在固定其他條件下的條件效應。

**Q2：為何將現有編碼載具視為單一系統進行評估會造成問題？**
A：跨框架評估雖能指出不同模型偏好不同載具，但這種比較混淆了多種機制，例如規劃鷹架、工具設計與上下文管理策略。因此，兩個代理之間的效能差異無法歸因於特定元件，也難以判斷這些設計是否能轉移到其他模型。本研究強調，唯有在固定執行迴圈與模型的情況下分別變動元件，才能精確識別每個元件的作用。

**Q3：為什麼編碼載具的設計選擇與模型本身同等重要？**
A：即使固定大型語言模型，改變編碼載具仍可能顯著改變長期軟體工程效能，這顯示載具並非可有可無的實作細節。規劃、動作介面與上下文管理被視為長期編碼代理的互補需求，分別影響任務進度、可執行操作與歷史資訊保留。因此，理解這些元件的條件效應，對於把模型能力轉化為實際任務表現至關重要。

**Q4：本研究提出的輕量編碼載具核心方法是什麼？**
A：研究者從頭建構一個輕量編碼載具，採用固定的 ReAct 執行迴圈，並獨立變動三大元件：規劃、動作空間與上下文管理。其他支援機制如權限處理、編輯後處理診斷與卡住偵測則保持固定，以提供共同的執行基板。這種模組化設計讓每次消融實驗都能隔離單一元件的效應，避免不同實作選擇相互耦合。

**Q5：五種上下文管理策略 T0–T4 的設計有何差異？**
A：T0 不進行跨回合壓縮，超出上下文視窗預算時即終止；T1 使用規則式省略來隱藏過時的工具觀察；T2 在 T1 基礎上加入外部儲存與 recall_event，使被省略的內容可恢復；T3 完全依賴基於 LLM 的摘要；T4 則採用分階段規則式省略，先進行省略再視需要呼叫摘要。這樣的設計允許研究者比較規則式與 LLM 式壓縮、以及可恢復性機制的實際價值。

**Q6：動作空間與規劃元件在本研究中如何操作化？**
A：動作空間有兩種設定：一種是提供預定義的工作空間工具集，另一種是僅 Bash 介面，讓模型透過命令列殼層直接操作。規劃則透過系統提示要求模型在執行前建立初始計畫，並在後續回合使用 update_plan 工具維護明確且持續的任務進度表示；禁用規劃時則移除相關指令、提醒、計畫注入與工具。透過這種方式，研究能分別估計動作介面與規劃鷹架對執行軌跡的影響。

**Q7：實驗使用了哪些模型、基準測試與設定？**
A：實驗選用 Nemotron-3 的 30B、120B、550B 作為同一家族模型規模軸度，並以 Mistral-Medium-3.5-128B 作為跨家族比較。評估基準為 SWE-Bench Verified 與 Terminal-Bench 2.1，分別測試倉庫層級 issue 解決與端到端終端機任務完成。上下文視窗預算設為 32k、64k、96k、128k，並在 128k 下搭配 T4 進行規劃與動作空間的針對性消融，共 176 個配對設定。

**Q8：上下文管理的主要實驗發現是什麼？**
A：上下文管理在預算緊迫時最有價值，主要效益來自防止上下文溢位失敗，讓代理能持續推進到程式碼修改與驗證階段。分階段規則式省略後再接 LLM 摘要的 T4 策略，在維持相近平均成功率的同時，有效控制峰值上下文並減少摘要呼叫次數，因此整體效率最佳。相對地，讓被省略內容可恢復的 recall 機制很少被模型使用，也未帶來準確性提升。

**Q9：規劃與動作空間的消融實驗得出什麼結論？**
A：規劃對較弱模型扮演準確性鷹架角色，能延長執行軌跡以嘗試編輯，從而提升成功率但增加成本；對較強模型則主要作為成本節省機制，減少多餘的編輯後驗證，準確性變化不大。在動作空間方面，預定義工具能降低對 shell 命令的依賴，改善 Bash 熟練度較弱模型的表現；而 Bash 熟練度高的模型使用僅 Bash 介面即可有效運作，並能顯著降低成本，尤其在以命令列為中心的任務上。

**Q10：在資源預算有限的產品場景中，應如何選擇上下文管理策略？**
A：當上下文視窗預算較小時，建議採用 T4 這類分階段規則式省略加摘要的策略，以延長執行軌跡並避免溢位。可恢復儲存雖然增加了機械複雜度，但模型很少召回被省略內容，對準確性也無幫助，因此在成本敏感的產品中可優先省略。隨著視窗擴大，上下文管理的邊際效益會遞減，此時可將資源投入其他元件。

**Q11：模型能力如何影響編碼載具的設計決策？**
A：對於能力較弱的模型，應提供規劃鷹架與預定義工具，以彌補其在任務結構化與 Bash 熟練度上的不足。對於能力較強的模型，則可採用僅 Bash 介面並讓規劃主要發揮成本節省作用，因為它們能夠以較粗粒度有效組合多個操作。這意味著實務上不存在一體適用的載具，設計必須根據模型規模與互動風格進行調整。

**Q12：這項研究對編碼代理領域有何更廣泛的影響？**
A：本研究提供了一個模組化框架，使未來研究能夠在元件層級評估新設計，而非僅比較整體式系統。透過軌跡層級分析，研究者能解釋各元件如何改變執行軌跡的終止點、行為模式與程式碼粒度。這些發現為模型感知與預算感知的載具設計提供了實證基礎，有助於加速後續工具設計與最佳化。

**Q13：本研究有哪些主要限制？**
A：研究使用的輕量編碼載具可能未涵蓋完整生產級系統的所有功能，例如進階的權限處理或卡住偵測。實驗僅變動三個核心元件，其他機制保持固定，因此無法評估所有可能的元件互動。此外，所選模型僅作為能力探針，並非針對這些載具永久最佳化，結果在更廣泛的模型家族或真實世界任務上的泛化性仍需進一步驗證。

**Q14：研究觀察到哪些負面結果或失敗案例？**
A：可恢復的省略機制雖然理論上能保留更多資訊，但模型實際上很少呼叫 recall_event，也未能提升成功率，顯示額外機械複雜度並未轉化為效益。當上下文視窗預算擴大時，上下文管理對準確性的貢獻明顯減弱，溢位不再是主要瓶頸。此外，即使配備良好的上下文管理，部分代理仍會因推理錯誤或編輯失誤而失敗，顯示管理策略無法完全彌補模型能力限制。

**Q15：未來研究可以朝哪些方向延伸？**
A：未來可將更多元件納入模組化評估，例如編輯後診斷、卡住偵測與權限處理，以完整描繪載具設計空間。也可探索自適應上下文管理策略，根據任務類型與執行階段動態調整壓縮方式。此外，在更長期、更真實的軟體工程任務上驗證這些發現，並擴展到更多模型家族，將有助於建立更通用的設計原則。

## 實務應用指南

### 適用場景

1. **企業內部自動化維護大型程式碼庫**  
   當開發團隊需要讓自主編碼代理長期處理 GitHub issues、修復跨檔案 bug 或執行重構時，本研究提供的模組化載具設計可協助選擇適合的規劃鷹架、動作空間與上下文管理策略，避免代理因上下文溢位而提前終止。

2. **命令列導向的 DevOps 與終端機自動化**  
   對於以命令列為中心的任務（例如部署腳本修復、容器設定、CI/CD 管線調整），可根據模型的 Bash 熟練度決定採用預定義工具或僅 Bash 介面，以在準確率與成本間取得平衡。

3. **資源受限邊緣或私有雲部署**  
   當上下文視窗預算有限（如 32k–64k tokens）或 API 成本敏感時，T4 分階段規則式省略搭配 LLM 摘要的上下文管理策略能延長執行軌跡、降低峰值上下文用量，並減少昂貴的摘要呼叫次數。

4. **多模型能力評估與選型**  
   團隊在導入新模型前，可利用本文的 176 組配對設定方法，針對自家任務快速比較不同規模模型對規劃、動作介面與上下文管理的敏感度，避免把完整框架的表現差異誤歸因於單一元件。

5. **長期軟體工程代理的產品化原型開發**  
   新創或平台團隊在從 0 到 1 打造編碼代理時，可採用輕量編碼載具的模組化骨架，將執行迴圈固定後獨立調整規劃、動作空間與上下文管理，縮短實驗迭代週期。

### 實作前置條件

**資料前提**
- 具備可執行的任務資料集或內部評估集，建議同時包含倉庫級議題解決（類 SWE-Bench Verified）與端到端終端機任務（類 Terminal-Bench 2.1），以覆蓋不同任務型態。
- 每筆任務需有明確的成功判定準則（如單元測試通過、輸出比對、人工驗收標準），否則難以進行軌跡層級分析。
- 建議預先收集模型在無規劃、無上下文管理基線下的失敗日誌，作為後續消融實驗的對照。

**運算前提**
- 至少能穩定呼叫一個長上下文模型（128k tokens）與一個中階模型（32k–64k tokens），以便複製上下文視窗預算的掃描實驗。
- 需有足夠的推理預算執行 100 組以上的配對設定；若資源有限，可優先聚焦 T0（無管理）與 T4（分階段省略＋摘要）在 32k 與 128k 的對比。
- 軌跡儲存與分析環境：每條執行軌跡需保留工具呼叫、上下文長度、終止原因與成本紀錄。

**技能前提**
- 熟悉 ReAct 執行迴圈與工具呼叫協定，能夠獨立實作或修改 `update_plan` 等規劃工具。
- 具備設計規則式省略策略與 LLM 摘要提示詞的能力，並能評估兩者的成本與延遲。
- 了解 Bash 與預定義工具（如檔案讀寫、搜尋、測試執行）的優劣，能依模型特性切換動作介面。

---

### 實作步驟建議

**步驟一：固定執行迴圈與基礎元件**  
先打造一個輕量編碼載具，採用 ReAct 迴圈（推理→動作→觀察），並將權限處理、編輯後診斷、卡住偵測等輔助機制固定下來。此階段不要同時調整多個元件，否則無法進行元件層級比較。

**步驟二：建立上下文管理策略的梯度**  
依序實作 T0 至 T4：T0 為無管理基線；T1 加入規則式省略陳舊工具觀察；T2 在 T1 基礎上加入可恢復的外部儲存與 `recall_event`；T3 改用純 LLM 摘要；T4 則分階段先執行規則式省略，必要時再呼叫 LLM 摘要。建議優先上線 T4，因為它在控制峰值上下文與成本方面表現最佳。

**步驟三：掃描上下文視窗預算**  
在 32k、64k、96k、128k 四個預算下執行同一組任務，記錄成功率和因上下文溢位失敗的比例。若預算緊迫，上下文管理的價值最大；若預算寬鬆，可將資源轉向規劃或動作空間優化。

**步驟四：針對模型能力調整規劃鷹架**  
對較弱模型，規劃是準確性鷹架，應啟用並允許模型透過 `update_plan` 持續更新任務進度；對較強模型，規劃主要作為成本節省機制，可簡化編輯後的重複驗證流程。建議在同一模型家族內進行規模軸度實驗，觀察規劃效用的轉折點。

**步驟五：依 Bash 熟練度選擇動作空間**  
若模型 Bash 熟練度低，提供預定義工具以降低對 shell 命令的依賴；若模型 Bash 能力強，可嘗試僅 Bash 介面，讓模型在一次呼叫中組合多個操作，特別在以命令列為中心的任務上能顯著降低成本。

**步驟六：進行軌跡層級分析並迭代**  
分析執行軌跡的三個維度：上下文管理是否延長軌跡長度、規劃是否改變終止位置、動作空間是否改變程式碼撰寫粒度。根據分析結果決定下一輪優化方向，而非僅看整體成功率。

### 潛在風險與注意事項

- **過度工程化可恢復機制**：研究發現 `recall_event` 等可恢復外部儲存很少被模型使用，且相較於單純省略並未提升準確率。除非有明確證據顯示模型需要回溯陳舊觀察，否則應避免增加不必要的機械複雜度。
- **把完整框架的差異誤判為單一元件的貢獻**：跨框架評估容易混淆規劃、工具設計與上下文管理的交互效應。實務上應採用模組化載具，固定其他元件後再估計單一介入的條件效應。
- **忽略上下文溢位失敗的隱藏成本**：當上下文視窗預算緊迫時，許多失敗並非模型能力不足，而是軌跡被強制截斷。若未區分「能力不足」與「上下文溢位失敗」，會錯誤地擴大模型規模或增加成本。
- **規劃對強模型的負面干擾**：對強模型而言，規劃可能主要減少冗餘驗證而非提升準確率；若強制加入過度詳細的規劃協定，反而可能增加 token 消耗而無對應收益。
- **動作空間與任務型態錯配**：預定義工具雖能提升 Bash 弱模型的表現，但在以命令列為中心的任務上可能限制靈活性；反之，僅 Bash 介面對 Bash 弱模型會顯著降低成功率。選擇前應先評估模型在兩種介面上的基線表現。

---

### 與其他技術的整合建議

- **與現有 IDE 或程式碼編輯器整合**：可將輕量編碼載具作為後端服務，透過 Language Server Protocol（LSP）或自訂 API 與 VS Code、JetBrains 等編輯器連接，讓規劃鷹架以視覺化任務清單呈現，動作空間則對應編輯器內的檔案操作與終端機指令。
- **與持續整合／持續部署（CI/CD）管線整合**：在 CI 階段啟用編碼代理處理失敗的測試或安全掃描結果，並利用上下文管理策略在長時間建置日誌中保留關鍵片段。對於命令列導向的修復任務，可優先使用僅 Bash 介面以降低成本。
- **與檢索增強生成（RAG）系統整合**：將倉庫文件、常見錯誤模式與歷史修復方案作為外部知識庫，與 T4 上下文管理的外部儲存區分開。RAG 提供靜態背景知識，而上下文管理負責動態執行軌跡的壓縮與召回。
- **與模型閘道或路由層整合**：根據任務難度與上下文預期長度，動態選擇模型與載具配置。例如，簡單任務使用無規劃的僅 Bash 介面與較小模型；複雜跨檔案任務則啟用規劃、預定義工具與 T4 上下文管理。
- **與可觀測性平台整合**：將每條執行軌跡的上下文長度、工具呼叫分佈、終止原因與成本匯入監控系統，設定上下文溢位失敗率與單任務成本警報，作為載具調整的資料回饋。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦「為什麼編碼載具不只是模型包裝」這個核心觀念，理解規劃、動作空間與上下文管理三個元件如何各自影響代理行為。可從「適用場景」與「實作步驟建議」入手，暫時跳過 176 組配對設定的細節，重點記住：預算緊時先做好上下文管理，模型強時規劃可轉為省成本，Bash 強的模型可考慮簡化工具介面。

**AI 工程師**  
本研究提供了一套可直接複製的模組化實作藍圖，建議仔細閱讀「實作步驟建議」與「潛在風險與注意事項」，特別關注 T4 上下文管理策略的實作細節、規劃鷹架的提示詞與工具協定，以及如何在固定執行迴圈的前提下進行消融實驗。可將本文方法論遷移到自家模型與任務上，建立內部的元件層級比較流程。

**研究人員**  
本文的貢獻在於將編碼載具從整體式系統評估推進到元件層級比較，並透過軌跡層級分析解釋各元件的作用機制。建議深入檢視上下文視窗預算掃描、同一家族模型規模軸度與跨家族比較的實驗設計，並思考如何將此框架擴展到多代理協作、更長期任務或其他軟體工程基準測試。

**產品經理**  
本研究直接對應到產品決策中的成本、準確率與使用者體驗權衡。建議從「適用場景」與「與其他技術的整合建議」開始，理解不同配置對終端使用者價值的影響：上下文管理決定代理能否完成長任務而不中斷，規劃影響回應品質與延遲，動作空間則關係到任務覆蓋範圍與營運成本。可據此與工程團隊討論優先投入的元件與預期 ROI。
