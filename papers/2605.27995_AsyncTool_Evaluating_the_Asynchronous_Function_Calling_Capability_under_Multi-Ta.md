## 摘要翻譯

基於大型語言模型（LLM, Large Language Model）的代理（LLM-based Agent）已展現出運用外部工具解決複雜任務的強大能力。然而，現有評估往往忽略了工具使用（Tool Use）的時間維度，特別是工具回應延遲（Tool Response Latency）的影響，且通常僅限於單一任務設定。在實際應用中，多項任務經常需要並行執行（Concurrent Execution），而整體效率取決於代理能否在等待工具回應時利用閒置時間（Idle Waiting Time）。我們稱此能力為非同步工具呼叫（Asynchronous Tool Calling）。為評估此能力，我們提出 AsyncTool，一個用於在互動式多任務工具使用環境（Interactive Multi-Task Tool-Use Environment）中評估基於大型語言模型代理的基準測試（Benchmark），並提供延遲工具回饋（Delayed Tool Feedback）機制。AsyncTool 同時呈現多項異質任務（Heterogeneous Task），並在執行過程中模擬真實的工具回應延遲。我們採用混合式資料演化策略（Hybrid Data Evolution Strategy），建構一個涵蓋多種情境與工具使用模式的非同步多任務資料集（Asynchronous Multitasking Dataset）。我們在步驟層級（Step-Level Evaluation）、子任務層級（Sub-Task Level Evaluation）與任務層級（Task-Level Evaluation）評估模型，並引入效率導向指標（Efficiency-Oriented Metrics）以衡量任務協調（Task Coordination）與完成效率（Completion Efficiency）。大量實驗顯示，延遲工具回饋對當前代理構成重大挑戰，並導致明顯的效能下降（Performance Degradation）。能更佳地協調任務切換（Task Switching）、依賴追蹤（Dependency Tracking）與狀態維護（State Maintenance）的模型，在 AsyncTool 上表現更為出色。我們的分析識別出當前工具使用代理（Tool-Using Agent）的關鍵失敗模式（Failure Mode），並為設計具備更強時間推理（Temporal Reasoning）與協調能力（Coordination Capability）的未來系統提供實用見解。

### 核心貢獻（3～5點）
- **提出 AsyncTool 基準測試**：首度系統性評估代理在多任務情境下的非同步工具呼叫能力，填補現有評估忽略時間維度（工具回應延遲）與多任務設定的雙重盲點。
- **設計互動式多任務工具使用環境**：模擬真實工具回應延遲與失序工具回饋（Out-of-Order Tool Feedback），並採用混合式資料演化策略建構涵蓋多元情境與工具使用模式的資料集。
- **建立三層級評估框架**：結合步驟、子任務與任務層級評估，並引入效率導向指標，全面衡量任務協調與完成效率。
- **揭示關鍵失敗模式與設計指引**：透過大量實驗證實延遲工具回饋導致明顯效能下降，識別當前工具使用代理的關鍵失敗模式，並指出任務切換、依賴追蹤與狀態維護等協調能力為提升效能的核心要素。

### 適合對象
從事大型語言模型代理、工具使用、強化學習與多任務規劃研究之學者與工程師；亦適合關注 AI 代理實際部署效率、互動式系統設計及基準測試開發之研究團隊與業界技術主管閱讀。

## 深度分析

#### 方法論解析

AsyncTool 的方法論核心在於將「時間維度」引入工具使用（Tool Use）評估框架，突破傳統基準測試（Benchmark）僅關注單一任務、立即回應的假設。其方法論可從三個層面深入剖析：

**一、互動範式的形式化**

論文將代理（Agent）重新定位為「並行工具使用系統」（Concurrent Tool-Using System），這是一個關鍵的概念轉移。在傳統設定中，代理發出函式呼叫（Function Call）後會阻塞等待結果；而在 AsyncTool 中，工具回應延遲（Tool Response Latency）被模擬為非同步事件，迫使代理必須在「等待」與「切換」之間做出決策。這種設計將代理的決策空間從「下一步做什麼」擴展為「在多個任務中，下一步該推進哪一個任務」。具體而言，AsyncTool 模擬了以下三個關鍵挑戰：

1. **延遲回饋（Delayed Feedback）**：工具結果並非即時返回，代理必須在結果抵達前決定後續動作。
2. **任務交錯（Task Interleaving）**：多個異質任務（Heterogeneous Task）共享同一互動流程，代理需動態切換。
3. **依賴感知排程（Dependency-Aware Scheduling）**：任務內步驟依賴（Intra-Task Step Dependency）與跨任務依賴必須被正確追蹤，否則會產生依賴違規（Dependency Violation）。

**二、混合式資料演化策略（Hybrid Data Evolution Strategy）**

資料集建構採用四階段管線（Pipeline），如圖 1 所示：

- **STEP 1 資料收集（Data Collection）**：從既有工具使用基準測試中蒐集原始資料，並依情境分類過濾。
- **STEP 2 粗略重建（Coarse Reconstruction）**：使用 Gemini 2.5 Pro 重建執行軌跡，並進行步驟依賴增強（Step-Dependency Enhancement），確保任務內部存在明確的依賴鏈。
- **STEP 3 細粒度標註（Fine-grained Annotation）**：結合 AI 與人類協作進行軌跡驗證（Trajectory Validation）、修正（Correction）與消歧（Disambiguation），確保軌跡的準確性與確定性。
- **STEP 4 多任務組合（Multi-Task Combination）**：透過 Combiner 與混合策略演化（Mixed-strategy Evolution），將單一任務組合成多任務資料集，涵蓋不同任務數量、任務類型與依賴結構。

此策略的精妙之處在於「由單到多」的組合方式：先確保單一任務的正確性與依賴結構，再透過組合產生多任務情境。這避免了直接生成多任務資料時可能產生的不一致或模糊問題。

**三、多層級評估協議（Multi-Level Evaluation Protocol）**

評估設計採用三個層級：

| 評估層級 | 評估對象 | 意義 |
|---------|---------|------|
| 步驟層級（Step Level） | 細粒度工具呼叫正確性 | 衡量代理是否能正確發出函式呼叫 |
| 子任務層級（Sub-Task Level） | 中間子任務完成度 | 衡量代理是否能完成任務的中間階段 |
| 任務層級（Task Level） | 端到端多任務成功率 | 衡量代理是否能完整完成所有任務 |

此外，論文引入了效率導向指標（Efficiency-Oriented Metrics），用於衡量任務交錯行為與完成效率，這填補了傳統基準測試僅關注「是否完成」而忽略「如何完成」的空白。

#### 實驗數據解讀

雖然提供的全文片段未包含具體的數據表格，但從論文的敘述與結論可推導出以下關鍵實驗發現：

**一、延遲回饋導致的效能下降（Performance Degradation）**

論文明確指出：「延遲工具回饋對當前代理構成實質挑戰，並導致明顯的效能下降。」這意味著在非同步設定下，模型的表現顯著低於同步或立即回應設定。具體而言，當模型在依賴工具結果尚未返回時「過早繼續」（Prematurely Continue）任務，會導致依賴違規，進而引發連鎖錯誤。

**二、模型能力差異的體現**

實驗揭示了模型間的顯著差異：

- **強模型**：能夠有效利用閒置等待時間（Idle Waiting Time）推進其他任務，並在適當時機恢復擱置中的任務。這體現了更強的時間推理（Temporal Reasoning）與協調能力（Coordination Capability）。
- **弱模型**：常出現三類失敗模式（Failure Mode）：
  1. **依賴違規（Dependency Violation）**：在依賴結果未到時執行後續步驟。
  2. **任務忽略（Task Neglect）**：切換至其他任務後忘記返回。
  3. **工具混淆（Tool Confusion）**：在多任務環境中誤用工具。

**三、效率指標的意義**

效率導向指標的引入具有重要價值。傳統基準測試僅衡量「任務是否完成」，而 AsyncTool 進一步衡量「任務如何被交錯執行」。這意味著一個即使完成所有任務但未有效利用閒置時間的代理，其效率分數仍會偏低。這種設計促使研究者關注代理的排程策略，而非僅僅是任務完成率。

**四、實驗設計的深層意涵**

論文的實驗設計揭示了一個重要觀點：「有效的非同步工具使用不僅需要頻繁的任務切換，更需要任務切換與依賴追蹤、狀態維護（State Maintenance）的協調。」這暗示單純的「切換頻率」並非越好，而是需要「智慧型切換」——在正確的時機切換到正確的任務。

#### 與現有研究的比較

AsyncTool 在基準測試生態系中具有明確的定位，其與現有研究的差異可從三個面向分析：

**一、與傳統工具使用基準測試的比較**

現有工具使用基準測試（如 Zhuang et al., 2023; Ruan et al., 2023; Xu et al., 2023; Guo et al., 2024; Qin et al., 2023; Ye et al., 2024）通常受限於：
- 單一任務情境
- 工具立即回應假設
- 無時間維度考量

AsyncTool 的突破在於同時考量了延遲工具回饋、並行多任務執行、多步驟函式呼叫（Multi-Step Function Calling）與依賴感知任務協調（Dependency-Aware Task Coordination）。這是首個將這些特性聯合考慮的基準測試。

**二、與非同步規劃基準測試的比較**

Lin et al. (2024) 等非同步規劃（Asynchronous Planning）基準測試雖然考慮了時間因素，但「並非在互動式環境（Interactive Environment）中運作」，這與涉及即時工具呼叫（Real-Time Tool Call）的真實情境不一致。AsyncTool 透過模擬工具特定回應延遲並整合多任務至共享互動流程，更貼近真實部署情境。

**三、與時間延遲基準測試的比較**

Zhang et al. (2024a) 與 Gonzalez-Pumariega et al. (2025) 等涉及時間延遲的基準測試「未涵蓋工具使用任務，無法遷移至代理式任務（Agentic Task）」。AsyncTool 填補了這一空白，將時間維度引入代理式工具使用評估。

**四、優勢與限制**

| 面向 | 優勢 | 限制 |
|------|------|------|
| 評估維度 | 首個聯合考量多項特性的基準 | 模擬延遲可能無法完全反映真實網路延遲的隨機性 |
| 資料建構 | 混合式演化策略確保品質 | 依賴 Gemini 2.5 Pro 進行軌跡重建，可能引入模型偏誤 |
| 評估指標 | 多層級 + 效率指標 | 效率指標的權重設計可能影響最終排名 |
| 真實性 | 互動式環境模擬 | 工具集合可能無法涵蓋所有真實應用場景 |

#### 可重現性評估

從提供的全文片段中，論文未明確提及程式碼、資料集或模型權重的開源狀況。然而，作為一個基準測試（Benchmark）論文，通常應具備以下可重現性要素：

**一、預期應開源的資源**

1. **基準測試程式碼**：包含環境模擬、工具延遲注入、評估流程的完整實作。
2. **資料集**：包含單一任務資料集與多任務組合資料集，以及依賴結構標註。
3. **評估腳本**：用於計算步驟層級、子任務層級與任務層級指標的程式碼。
4. **效率指標實作**：任務交錯行為與完成效率的計算邏輯。

**二、可重現性的潛在挑戰**

1. **工具回應延遲的模擬**：若延遲是隨機抽樣，則不同執行可能產生不同結果，需要固定隨機種子。
2. **LLM 的非確定性**：若評估涉及 LLM 自身的生成，溫度參數（Temperature）等設定會影響結果。
3. **人類驗證環節**：STEP 3 中的手動驗證可能難以完全重現，且不同驗證者可能產生細微差異。

**三、建議**

為提升可重現性，建議作者：
- 提供完整的設定檔（Configuration File）與隨機種子。
- 公開所有提示詞模板（Prompt Template）。
- 提供基準測試的 Docker 映像檔以標準化環境。
- 詳細記錄人類驗證的準則與流程。

#### 未來研究方向

基於 AsyncTool 的發現與限制，可衍生以下研究方向：

**一、代理架構創新**

1. **時間感知代理（Time-Aware Agent）**：設計內建時間推理模組的代理架構，使其能在工具呼叫時預估延遲並主動規劃任務切換。
2. **狀態管理增強**：開發更強大的狀態維護（State Maintenance）機制，例如外部記憶體（External Memory）或結構化狀態追蹤器，以避免任務忽略。
3. **依賴圖推理（Dependency Graph Reasoning）**：將任務依賴顯式建模為圖結構，使代理能進行形式化的依賴推理。

**二、訓練策略改進**

1. **非同步工具使用訓練資料**：利用 AsyncTool 的資料建構流程，產生大規模訓練資料，用於微調（Fine-Tuning）現有 LLM。
2. **強化學習與排程策略**：將任務切換視為排程問題，透過強化學習（Reinforcement Learning）優化切換策略。
3. **合成資料生成**：探索更進階的合成資料生成技術，以擴展非同步多任務情境的多樣性。

**三、評估方法擴展**

1. **真實環境整合**：將 AsyncTool 與真實 API 整合，測量真實網路延遲下的代理表現。
2. **人類評估對照**：引入人類專家作為對照基準，衡量代理的非同步工具使用能力與人類水準的差距。
3. **動態延遲模擬**：研究延遲分佈（Distribution of Latency）對代理表現的影響，例如長尾延遲（Long-Tail Latency）場景。

**四、應用領域拓展**

1. **企業流程自動化**：將 AsyncTool 應用於企業資源規劃（ERP）與客戶關係管理（CRM）等多系統整合場景。
2. **個人助理代理**：研究個人助理代理在處理多個並行請求（如同時安排會議、查詢天氣、發送郵件）時的非同步能力。
3. **機器人與物聯網**：將非同步工具使用概念延伸至機器人控制與物聯網（IoT）裝置協調。

**五、理論基礎建立**

1. **非同步代理的形式化**：建立非同步工具使用的形式化理論框架，明確定義代理能力與任務複雜度的關係。
2. **計算複雜度分析**：分析非同步多任務工具使用問題的計算複雜度，探討其與傳統規劃問題的關聯。
3. **失敗模式的理論分類**：對觀察到的失敗模式進行更系統的理論分類，並探討其與代理架構設計的因果關係。

AsyncTool 的提出不僅填補了基準測試的空白，更開啟了「時間維度」在代理評估中的新研究方向。隨著 LLM 代理在真實應用中的部署日益普及，非同步工具使用能力將成為衡量代理實用性的關鍵指標，而 AsyncTool 正是朝此方向邁出的重要一步。

## 論文問答

**Q1：為什麼現有的工具使用評估基準無法充分評估 LLM 代理在真實世界中的表現？**
A：現有的工具使用評估基準大多侷限於單一任務情境，且假設工具能立即回應，忽略了真實世界中工具呼叫常伴隨的延遲特性。這些基準無法評估代理在等待工具回應時是否能有效利用閒置時間推進其他任務。此外，傳統的時間延遲基準測試並未涵蓋工具使用任務，因此無法直接應用於代理式任務的評估。這種評估缺口使得我們難以了解代理在多任務並行環境下的真實協調能力，也阻礙了實用代理系統的發展。

**Q2：什麼是「非同步工具呼叫」，為什麼它對 LLM 代理至關重要？**
A：非同步工具呼叫是指代理在發出工具呼叫後，不必被動等待結果，而是能夠利用等待期間的空檔去推進其他可獨立執行的任務。這項能力對於真實世界的應用至關重要，因為現實環境中多個任務常需並行處理，且工具回應通常伴隨不可忽略的延遲。若代理僅以同步方式依序執行任務，將無法充分利用閒置等待時間，導致整體效率低落。因此，非同步工具呼叫能力直接影響代理在複雜多任務環境中的實用性與效率，也是衡量代理成熟度的關鍵指標。

**Q3：為什麼現有的非同步規劃基準無法直接應用於評估 LLM 代理的工具使用能力？**
A：現有的非同步規劃基準雖然考慮了時間維度的挑戰，但它們並非設計用於互動式環境中，也未涉及即時工具呼叫的情境。這意味著這些基準無法反映代理在真實世界中與工具互動時所面臨的複雜性，例如工具回傳結果的順序可能失序、不同任務間存在依賴關係等。此外，這些基準缺乏針對並行任務中延遲與失序工具回饋的專門指標與標準化協議。因此，需要一個專門針對代理式任務設計的非同步工具呼叫評估框架，以彌補現有研究的不足。

**Q4：AsyncTool 基準測試的核心設計理念是什麼？**
A：AsyncTool 的核心設計理念是同時考量延遲工具回饋、並行多任務執行、多步驟函式呼叫以及依賴感知任務協調這四個關鍵面向。基準中每個任務包含任務內的步驟依賴關係，而不同任務之間則可以並行推進，使代理能夠利用工具延遲所造成的等待期來推進其他獨立任務。此外，AsyncTool 模擬特定工具的回應延遲，並將多個任務整合到共享的互動過程中，要求代理透過非同步函式呼叫同時推進多項任務的進展。這種設計更貼近真實世界的代理使用情境。

在監控系統中，代理需同時處理多個告警事件，每個事件涉及日誌查詢、指標拉取、通知發送。AsyncTool 評估可幫助識別代理是否能正確處理「告警 A 需等待日誌查詢結果才能升級」這類依賴關係。

當使用者同時下達多個指令（「預約會議、訂餐、查詢天氣」）時，代理需協調多個第三方服務。AsyncTool 的多任務組合策略可作為設計此類編排邏輯的驗證基礎。

**技能門檻**
- 熟悉 LLM 代理框架（如 LangGraph、AutoGen、CrewAI）的工具呼叫機制
- 具備分散式系統概念：理解非同步 I/O、訊息佇列、狀態管理

- 具備基本的資料標註與品質驗證流程設計能力

### 實作步驟建議

**步驟一：建立單任務基準資料集**
從既有工具使用基準（如 ToolBench、BFCL）篩選並分類任務，按場景分群（金融、客服、開發等）。使用 Gemini 2.5 Pro 重建執行軌跡，並由人工驗證確定性與正確性，產出「單任務資料集」。

**步驟二：強化步驟依賴結構**
針對每筆單任務軌跡，明確標註步驟間的依賴關係（哪些步驟必須等待前序結果、哪些可獨立執行）。這是後續組合多任務的基礎，避免產生「假獨立」任務組合。

**步驟三：採用混合策略組合多任務**
依據 AsyncTool 的混合式資料演化策略：
- **依任務數量組合**：產生 2、3、4、5 個任務的組合樣本
- **依任務類型組合**：跨場景混合（如「訂單查詢」+「財報生成」+「日誌分析」）
- **依依賴結構組合**：包含全獨立、部分依賴、鏈式依賴等拓樸

**步驟四：實作延遲回饋模擬器**
為每個工具定義延遲分佈（建議使用真實生產環境的 P50/P90 延遲）。在代理呼叫工具後，模擬器將請求放入佇列，於指定時間後回傳結果。關鍵設計：結果可能失序到達，需保留訊息時間戳。

**步驟五：建立三層級評估協議**
- **步驟層級**：比對代理輸出的工具呼叫與標準答案的精確匹配
- **子任務層級**：評估每個獨立任務的中間完成度
- **任務層級**：評估整體多任務的端到端成功率
- **效率指標**：測量任務交錯密度、總完成時間、閒置區間利用率

**步驟六：迭代優化代理策略**
根據評估結果識別失敗模式（依賴違規、任務遺忘、工具混淆），針對性優化：
- 加入顯式的依賴追蹤模組
- 設計任務狀態持久化機制
- 引入「等待 vs. 切換」決策器

**步驟七：部署前壓力測試**
在生產環境影子模式（shadow mode）下運行，記錄實際延遲分佈與代理行為，持續校準評估基準。

### 潛在風險與注意事項

**風險一：依賴違規導致錯誤結果**
代理在依賴步驟結果未回傳前就繼續執行後續步驟，產生基於錯誤假設的動作。
*緩解措施*：在工具呼叫介面層強制加入「依賴檢查閘門」，未收到依賴結果時拒絕執行；或在提示詞中明確標示依賴關係。

**風險二：任務狀態遺失（Task Neglect）**
代理切換至其他任務後，忘記返回處理先前擱置的任務。
*緩解措施*：設計「擱置任務清單」（pending task queue）並定期提醒；採用結構化狀態物件而非自由格式對話歷史。

**風險三：工具混淆（Tool Confusion）**
多任務環境下，代理將任務 A 的工具呼叫結果誤用於任務 B。
*緩解措施*：為每個工具呼叫與結果附加任務 ID 標籤；在結果回傳時明確標示「此結果屬於任務 X」。

**風險四：評估基準過擬合**
代理在 AsyncTool 上表現優異，但面對真實世界的長尾任務組合時失效。
*緩解措施*：定期從生產環境採樣新任務組合更新基準；保留一定比例的「未見任務類型」作為測試集。

**風險五：延遲分佈失真**
模擬的延遲與真實環境差異過大，導致評估結果無法外推。
*緩解措施*：從生產環境日誌蒐集真實延遲分佈；定期更新模擬器參數；區分「快工具」「慢工具」「極慢工具」三個層級。

**風險六：成本失控**
多任務並行可能導致工具呼叫次數與 token 消耗急劇增加。
*緩解措施*：設定每個任務的預算上限；監控「任務交錯密度」避免無意義的頻繁切換。

### 與其他技術的整合建議

**與既有代理框架整合**
- **LangGraph**：將 AsyncTool 的「擱置任務清單」實作為 Graph State 的一部分；利用其原生支援的條件分支處理「等待 vs. 切換」決策。
- **AutoGen**：在 GroupChat 機制中，為每個任務分配獨立的 agent 角色，透過訊息佇列模擬非同步回饋。
- **CrewAI**：將任務依賴關係映射為 Crew 的 Task 依賴圖，利用其排程器處理並行與等待。

**與監控與可觀測性系統整合**
- 整合 OpenTelemetry，追蹤每個工具呼叫的時間戳、任務歸屬、延遲分佈
- 在 Langfuse、LangSmith 等 LLM 可觀測性平台中，為非同步呼叫新增自訂 span
- 建立儀表板監控「任務擱置時間分布」「依賴違規率」「閒置區間利用率」

**與工作流引擎整合**
- **Temporal / Airflow**：將 AsyncTool 的多任務組合映射為工作流定義，利用引擎的狀態持久化能力處理長時間等待
- **Celery / RabbitMQ**：作為工具呼叫的訊息中介層，支援失序回饋與重試機制

**與評估與測試系統整合**
- 整合 DeepEval、Promptfoo 等框架，將 AsyncTool 的三層級評估封裝為自動化測試案例
- 在 CI/CD 流程中加入「非同步回歸測試」，確保代理改動不會降低多任務協調能力

**與企業系統整合**
- 透過 API Gateway 統一管理工具呼叫，注入延遲模擬與限流
- 整合身分驗證系統（OAuth、SSO），確保多任務環境下的權限隔離

### 給不同背景讀者的閱讀建議

**給初學者**
建議先閱讀第 1 節的動機說明，理解「為什麼需要非同步工具呼叫」——核心概念是：當工具需要時間回應時，聰明的代理不該傻等，而是去做其他事。接著看圖 1 的資料建構流程，建立直觀印象。實作上可從 LangGraph 官方範例開始，嘗試將單任務範例改為雙任務組合，觀察代理行為差異。

**給 AI 工程師**
重點關注第 2.1 節的代理互動範式，理解「延遲回饋 + 並行任務 + 依賴追蹤」三者的耦合關係。實作時建議先建立工具模擬器與延遲注入機制，再設計「擱置任務清單」資料結構。評估階段直接採用 AsyncTool 的三層級指標作為內部基準，並根據自身業務的延遲分佈調整模擬器參數。注意：失敗模式分析（依賴違規、任務遺忘、工具混淆）比整體成功率更能指導工程優化方向。

**給研究者**
本文的核心貢獻在於「將時間維度引入工具使用評估」，這填補了現有基準的空白。建議從三個方向延伸：(1) 探索更複雜的依賴拓樸（如動態依賴、條件依賴）；(2) 將非同步能力與規劃、反思等高階推理能力結合研究；(3) 借鑑人類多工處理的神經認知研究，設計更具生物啟發性的代理架構。資料建構的混合演化策略也值得借鏡，可應用於其他多任務基準設計。

**給產品經理**
AsyncTool 揭示了一個關鍵產品洞察：使用者期待 AI 助理「又快又準」，但在多任務場景下，「快」需要靠非並行處理實現，而「準」需要靠依賴追蹤保證——兩者存在張力。建議在產品設計時：(1) 明確哪些任務可並行、哪些必須序列；(2) 為使用者提供「任務進度儀表板」而非黑盒等待；(3) 設定合理的延遲預期（例如「查詢財報需 30 秒」）。評估指標上，「完成效率」比「成功率」更能反映使用者體驗。
