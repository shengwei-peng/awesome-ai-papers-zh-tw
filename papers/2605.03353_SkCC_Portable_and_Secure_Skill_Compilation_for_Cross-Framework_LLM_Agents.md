## 摘要翻譯

LLM 代理系統已演進為可執行複雜任務的自主系統，其中 SKILL.md 規範已成為封裝代理能力的事實標準。然而，仍存在一項關鍵瓶頸：不同的代理框架對提示詞格式表現出截然不同的敏感程度，造成高達 40% 的效能變異，但幾乎所有技能僅以單一、格式無關的 Markdown 版本存在。手動跨平台改寫帶來難以為繼的維護負擔，而先前的稽核已發現超過三分之一的社群技能含有安全漏洞。為解決此問題，我們提出 SkCC，一個將經典編譯器設計引入代理技能開發的編譯框架。其核心為 SkIR——一個強型別的中間表示（IR）——將技能語意與平台特定格式解耦，使可攜式部署得以在異質代理框架間實現。圍繞此中間表示，編譯時期分析器在部署前透過反技能注入機制強制執行安全約束。透過四階段流水線，SkCC 將適配複雜度從 O(m × n) 降至 O(m + n)。在 SkillsBench 上的實驗顯示，編譯後的技能持續優於其原始版本，在 Claude Code 上將通過率從 21.1% 提升至 33.3%，在 Kimi CLI 上從 35.1% 提升至 48.7%，同時達成低於 10 毫秒的編譯延遲、94.8% 的主動式安全觸發率，以及跨平台 10–46% 的執行時期 Token 節省。

### 核心貢獻（3～5點）
- 提出 **SkCC** 技能編譯框架，將經典編譯器設計引入 LLM 代理技能開發流程，建立從技能編寫到部署的系統化路徑。
- 設計 **SkIR** 強型別中間表示，將技能語意與平台特定格式解耦，使單一技能可攜式部署至異質代理框架，並將適配複雜度由 O(m × n) 降至 O(m + n)。
- 內建編譯時期分析器與**反技能注入**機制，於部署前主動執行安全約束，實驗達到 94.8% 的主動式安全觸發率。
- 透過四階段流水線達成低於 10 毫秒的編譯延遲，並在 SkillsBench 上使 Claude Code 通過率由 21.1% 提升至 33.3%、Kimi CLI 由 35.1% 提升至 48.7%，同時實現跨平台 10–46% 的執行時期 Token 節省。

### 適合對象
從事 LLM 代理系統、終端機代理框架（如 Claude Code、OpenAI Codex、Gemini CLI、Kimi CLI）研究與工程實務的研究者與開發者；關注提示詞工程、格式偏好與模型效能變異關係的學者；負責技能生態系治理、安全稽核與社群技能維護的平台維運者；以及對編譯器設計、程式語言理論應用於 AI 系統感興趣的跨領域研究者。

## 深度分析

#### 方法論解析

SkCC 的核心設計理念是將經典編譯器架構（classical compiler architecture）移植到 LLM 代理技能（LLM Agent skill）開發領域，其方法論可從以下幾個層面深入剖析：

**1. 問題形式化與抽象建模**

論文將跨框架技能部署問題形式化為 m×n 的適配複雜度（adaptation complexity）問題：m 個技能來源需對應 n 個異質代理框架（heterogeneous agent frameworks），傳統手動改寫方式需要 m×n 次人工調整。SkCC 透過引入統一的中間表示層 SkIR（Skill Intermediate Representation），將問題降維至 m+n——只需 m 個技能解析路徑與 n 個框架發射器（Emitter）實作。這一抽象與 LLVM IR 的設計哲學高度同構，體現了「一次編寫、多處編譯」（write once, run anywhere）的工程典範轉移。

**2. 四階段編譯流水線（Four-phase Pipeline）**

SkCC 的編譯流程包含四個明確分工的階段：

- **語法解析器（Syntax Parser）**：從原始 SKILL.md 提取抽象語法樹（AST），處理 YAML frontmatter 與 Markdown 主體的混合語法結構。
- **IR 建構器（IR Builder）**：將 AST 轉換為強型別（strongly-typed）的 SkIR，這是整個系統的語意錨點（semantic anchor），負責將非結構化的 Markdown 內容提煉為可被靜態分析的結構化表示。
- **安全優化器（Security Optimizer）**：執行反技能注入（Anti-Skill Injection）檢查，在編譯時期（compile-time）而非執行時期（runtime）攔截惡意 payload，這與傳統編譯器中的 stack canary 插入、邊界檢查等安全優化策略一脈相承。
- **多型發射器（Polymorphic Target Emitter）**：將驗證後的 IR 渲染為各框架原生格式（framework-native formats），例如 Claude 偏好的 XML 語意分層（XML semantic layering）、GPT 系列偏好的 XML 標籤化 Markdown（XML-tagged Markdown）、深度巢狀資料偏好的 YAML 等。

**3. 強型別中間表示 SkIR 的設計意涵**

SkIR 作為強型別 IR，其設計價值不僅在於語法層面的格式轉換，更在於語意層面的形式化約束。透過型別系統，編譯器能在靜態階段驗證技能描述的一致性、參數邊界的合法性，以及指令序列的邏輯閉合性。這種「編譯時期即驗證」的範式，將傳統 LLM 應用中只能在執行時期（runtime）透過試錯發現的錯誤，前移至開發階段即可攔截。

**4. 反技能注入機制（Anti-Skill Injection）**

論文借鏡傳統編譯器的安全優化思想，提出 Anti-Skill Injection 作為編譯時期的安全閘門（security gate）。該機制針對 Snyk 稽核（Snyk audit）所揭露的「超過三分之一社群技能含有安全漏洞」問題，在技能進入代理上下文視窗（context window）之前進行結構化檢查，實現主動式安全（proactive security）而非被動式補救。

**5. 漸進式揭露（Progressive Disclosure）的整合**

SkCC 與現有技能載入機制相容：輕量級路由清單 route.yaml（每技能約 50 tokens）在代理初始化（agent initialization）時載入，完整技能內容則在語意路由（semantic routing）匹配後動態載入。這種設計保留了原有生態系的運作模式，同時在編譯產物層面引入品質提升。

#### 實驗數據解讀

論文的實驗結果呈現多維度的效能證據，以下逐一解讀其意義：

**1. 通過率（Pass Rate）提升的實質意義**

在 SkillsBench 基準測試上，編譯後技能相較原始版本展現顯著改善：
- Claude Code：21.1% → 33.3%（+12.2 個百分點，約 +57.8% 相對提升）
- Kimi CLI：35.1% → 48.7%（+13.6 個百分點，約 +38.7% 相對提升）

此數據揭示一個關鍵洞見：格式敏感性（format sensitivity）造成的效能變異（performance variation）並非邊際現象，而是高達 40% 的「格式稅」（format tax）。SkCC 透過將技能轉換為各框架偏好的格式結構，實質回收了這部分被格式不適配吞噬的效能。

**2. 編譯延遲（Compilation Latency）的工程可行性**

次 10 毫秒（sub-10ms）的編譯延遲證明 SkCC 的靜態分析與轉換流程具備實務部署的即時性。這對於持續整合（CI/CD）流程中的技能更新場景至關重要——編譯開銷不會成為開發迭代的瓶頸。

**3. 主動式安全觸發率（Proactive Security Trigger Rate）94.8% 的解讀**

94.8% 的觸發率意味著絕大多數潛在惡意技能可在部署前被攔截。然而需注意：此數據反映的是「觸發率」而非「誤報率」，論文未明確說明觸發後的處理策略（阻擋、警告、或人工審核），也未提供 false positive 與 false negative 的細部分析。這是評估安全機制時的關鍵缺口。

**4. Token 節省（Token Savings）10-46% 的雙重意涵**

執行時期 token 用量減少 10-46% 帶來兩層效益：
- **經濟層面**：直接降低 API 呼叫成本，對大規模部署具顯著財務影響。
- **效能層面**：更精簡的提示詞（prompt）意味著更低的注意力稀釋（attention dilution），間接提升模型推理品質。

此數據橫跨多平台呈現，顯示 SkIR 的格式優化具有跨框架的普適性，而非僅針對特定模型。

**5. 實驗設計的侷限**

需指出的是，論文實驗主要聚焦於通過率與效率指標，對於以下面向缺乏深入探討：
- 不同任務類型（程式碼生成、除錯、文件處理等）的細粒度效能差異
- 編譯後技能在長對話、多輪互動場景下的穩定性
- 與人類專家手動調校版本的比較基準

#### 與現有研究的比較

**1. 定位於生態系中的獨特價值**

相較於現有研究，SkCC 的定位具有以下差異化特徵：

| 比較維度 | 既有方法 | SkCC 創新 |
|---------|---------|----------|
| 技能分發 | 格式無關（format-agnostic）單一版本 | 編譯產出框架原生格式 |
| 安全檢查 | 執行時期被動偵測 | 編譯時期主動攔截 |
| 適配成本 | m×n 手動改寫 | m+n 編譯自動化 |
| 格式選擇 | 開發者直覺決定 | 編譯器依框架特性優化 |

**2. 相關技術脈絡的承繼與超越**

- **相較於格式敏感性研究 [13-16]**：既有文獻已證實格式對 LLM 效能的影響，但停留在「觀察現象」層次；SkCC 將其工程化為自動化轉譯機制。
- **相較於編譯器架構研究 [20-25]**：傳統編譯器理論提供 IR 抽象與安全優化的方法論基礎；SkCC 將其首度系統性應用於 LLM 技能領域。
- **相較於代理框架研究 [4-7]**：Claude Code、Codex、Gemini CLI、Kimi CLI 等框架各自定義技能載入機制，但未解決跨框架可攜性（portability）問題；SkCC 填補此生態系缺口。

**3. 局限性與未竟之處**

- **缺乏動態技能支援**：當前 SkCC 似乎聚焦於靜態技能編譯，對於執行時期動態生成或組合的技能（dynamic skill composition）未明確處理。
- **IR 表達能力邊界**：強型別 SkIR 雖提供形式化保證，但對於高度領域特定（domain-specific）的技能邏輯，其表達力是否足夠仍待驗證。
- **安全模型的完整性**：Anti-Skill Injection 達 94.8% 觸發率，但未說明其威脅模型（threat model）的具體範圍——是否涵蓋提示注入（prompt injection）、間接注入（indirect injection）、供應鏈攻擊（supply chain attack）等不同攻擊面。
- **生態系採用成本**：從「單一 SKILL.md」轉換至「編譯流程」需要開發者改變既有工作流，此轉換成本未在論文中量化。

#### 可重現性評估

**1. 程式碼與資源開放程度**

根據論文註記，核心編譯器儲存庫已於 2026 年 4 月 3 日透過 GitHub 開源釋出，專案起始於同年 3 月。此開放策略對學術可重現性（reproducibility）具正面意義，但需進一步確認以下細節：

- **程式碼完整性**：是否包含完整的四階段流水線實作、SkIR 規格定義、所有 n 個框架的 Emitter 實作？
- **基準測試資料**：SkillsBench 是否同步開源？測試案例的授權狀態為何？
- **預訓練模型權重**：本工作不涉及模型訓練，故無權重釋出問題；但若 Emitter 涉及模型微調，則需另行說明。

**2. 實驗可重現性的關鍵變數**

- **框架版本敏感性**：實驗結果依賴特定版本的 Claude Code、Kimi CLI 等框架，這些框架的快速演進可能導致結果漂移（result drift）。
- **提示詞隨機性**：LLM 推理的溫度參數（temperature）、取樣策略等設定若未固定，將影響通過率的穩定性。
- **硬體與 API 環境**：編譯延遲測量依賴執行環境，跨平台比較時需標準化基準。

**3. 第三方驗證的可行性**

目前缺乏獨立的第三方重現實驗報告。建議後續研究社群進行：
- 跨機構的基準重測
- 不同模型版本下的效能驗證
- 安全機制的滲透測試（penetration testing）

#### 未來研究方向

**1. 編譯器技術的縱深拓展**

- **進階優化通道**：借鏡 LLVM 的優化通道（optimization pipeline）設計，引入技能專屬的優化策略，例如指令合併（instruction merging）、死碼消除（dead code elimination）、常數摺疊（constant folding）等。
- **多層級 IR 架構**：參考 MLIR 的多層級 IR 設計，讓 SkIR 支援不同抽象層次的漸進式降階（progressive lowering），兼顧高階語意保留與低階格式優化。
- **增量編譯（Incremental Compilation）**：當技能更新時，僅重編譯變更部分，進一步降低開發迭代成本。

**2. 安全模型的橫向擴展**

- **形式化驗證（Formal Verification）**：將 Anti-Skill Injection 從啟發式規則升級為形式化證明，例如透過型別理論（type theory）或模型檢測（model checking）保證安全性質。
- **威脅模型系統化**：明確定義覆蓋的攻擊面，包含直接注入、間接注入、側通道（side channel）、資料外洩（data exfiltration）等。
- **可解釋安全決策**：提供安全觸發的可解釋性（explainability），讓開發者理解為何特定技能被標記。

**3. 生態系整合與標準化**

- **技能套件管理（Skill Package Management）**：類比 npm、PyPI 等套件管理系統，建立技能的版本控制、相依性管理與安全稽核機制。
- **跨框架技能市集（Cross-framework Marketplace）**：以 SkCC 為基礎建構統一的技能分發平台，開發者一次發布，自動適配所有框架。
- **標準化 SkIR 規範**：推動 SkIR 成為業界標準 IR，類似 LLVM IR 在編譯器領域的地位。

**4. 智慧型編譯策略**

- **自適應格式選擇（Adaptive Format Selection）**：根據目標模型的特性、任務類型、對話歷史動態選擇最佳格式，而非靜態預設。
- **學習式優化器（Learned Optimizer）**：利用機器學習技術自動發現格式轉換規則，超越人工設計的啟發式策略。
- **效能預測模型**：在編譯時期預測技能在特定框架上的預期效能，提供開發者決策支援。

**5. 應用場景的縱向深化**

- **企業級代理系統**：將 SkCC 整合至企業內部代理平台，處理敏感業務流程時的安全合規需求。
- **多代理協作（Multi-agent Collaboration）**：研究 SkIR 在多代理協作場景下的技能共享與組合機制。
- **領域特化編譯器**：為特定領域（如醫療、法律、金融）開發專屬的 SkCC 變體，內建領域知識與合規規則。

**6. 理論基礎的強化**

- **語意保持性證明（Semantic Preservation Proof）**：嚴格證明 SkCC 的格式轉換不改變技能的語意內容。
- **複雜度下界分析**：從理論上論證 O(m+n) 是否為此問題的最佳複雜度，或存在更優的解法。
- **與神經符號 AI（Neuro-symbolic AI）的融合**：將 SkIR 的形式化語意與神經網路的學習能力結合，開創新一代混合編譯架構。

## 論文問答

**Q1：SkCC 主要解決的核心問題是什麼？**
A：SkCC 試圖解決 LLM 代理生態系中兩個相互糾結的挑戰：技能（skill）的跨框架可攜性與部署前安全性。在可攜性方面，不同代理框架（如 Claude Code、OpenAI Codex、Gemini CLI、Kimi CLI）對提示詞格式有截然不同的偏好，僅因格式差異就可能造成高達 40% 的效能變異，但目前社群技能普遍以單一、格式無關的 Markdown 版本發布。在安全性方面，Snyk 稽核報告指出超過三分之一的社群技能含有安全漏洞，卻缺乏系統化的部署前檢查機制。這兩個問題根源於同一假設——單一靜態 Markdown 檔案可同時服務所有框架與威脅模型。

**Q2：為何現有的手動改寫或單一格式發布方式無法持續？**
A：傳統作法需要為 m 個技能與 n 個框架分別進行人工改寫，產生 O(m×n) 的適配複雜度，維護負擔隨生態系成長呈乘積式爆炸。更糟的是，手動改寫容易出錯且難以追蹤格式變更後的語意一致性，使得技能更新時容易在不同框架版本間產生漂移。此外，由於缺乏編譯時期的安全檢查，惡意或含有漏洞的技能會直接進入代理的上下文視窗，攻擊面難以在部署前被有效縮減。

**Q3：為何這個問題對 LLM 代理領域至關重要？**
A：技能是代理能力封裝的「事實標準」，其品質直接決定代理在真實任務中的表現；若格式不匹配，再優秀的技能也可能因「格式稅」而失效。隨著 Anthropic-skills、ecc-skills、sentry-skills 等社群儲存庫累積數千個技能，無法規模化部署的生態系將迅速失去實用價值。更重要的是，技能會透過 MCP 與外部系統互動，安全漏洞不僅影響單一代理，更可能成為跨服務的攻擊媒介，因此編譯時期的安全保證具有系統級重要性。

**Q4：SkCC 的核心方法是什麼？**
A：SkCC 採用經典編譯器架構，將技能編寫與框架特定格式解耦，核心是引入強型別中間表示 SkIR 作為語意承載層。整個系統透過四階段流水線運作：①語法解析器從原始 SKILL.md 抽取 AST；②IR 建構器將其轉為強型別 SkIR；③安全優化器透過反技能注入（Anti-Skill Injection）強制執行安全約束；④多型目標發射器將驗證後的 IR 渲染為各框架原生格式。這條流水線把原本的 O(m×n) 改寫成本壓縮為 O(m+n)，只需 m 個技能來源與 n 個發射器實作。

**Q5：SkCC 相較於既有方案最關鍵的創新點為何？**
A：最關鍵的創新在於把「編譯器即安全邊界」的概念引入代理技能生態——這是過去研究未曾系統化處理的層面。SkIR 不只是格式轉換的中介層，更是承載語意與安全契約的強型別抽象，使安全檢查能在部署前以靜態分析形式完成。反技能注入機制在編譯時期主動攔截可疑指令，將傳統 runtime 防禦前移至 compile-time，呼應了經典編譯器中 stack canary 與 bounds checking 的設計哲學。

**Q6：SkCC 在設計上做了哪些關鍵取捨？**
A：設計上選擇以「單一來源、多框架輸出」取代「多來源、單一交付」，這需要在 IR 層表達足夠豐富的語意資訊以支援後續多型發射，因此 SkIR 採用強型別設計而非鬆散的語法樹。另一個關鍵取捨是把安全檢查放在 IR 建構之後、發射之前，使其同時對所有目標框架生效，避免每個框架各自維護一套安全規則。此外，系統刻意維持 sub-10ms 的編譯延遲，確保編譯成本不會反噬技能部署的迭代速度。

**Q7：SkCC 使用哪些評測基準與實驗設置？**
A：實驗以 SkillsBench 為主要評測基準，橫跨 Claude Code 與 Kimi CLI 兩個主流代理框架進行通過率（pass rate）比較。評測面向涵蓋三個維度：任務完成品質（pass rate）、系統效率（編譯延遲、執行時期 token 用量）以及安全保證（反技能注入觸發率）。同時透過與原始未編譯 SKILL.md 的對照組，量化編譯帶來的實質增益。

**Q8：實驗中最關鍵的量化結果為何？**
A：在 Claude Code 上，通過率從 21.1% 提升至 33.3%；在 Kimi CLI 上，從 35.1% 提升至 48.7%，跨框架皆呈現穩定增益。編譯延遲控制在 sub-10ms 等級，證明編譯開銷對互動體驗可忽略；反技能注入的主動觸發率達 94.8%，顯示安全覆蓋面極為完整。此外，執行時期 token 用量在不同平台上節省 10–46%，反映格式優化同時帶來效率紅利。

**Q9：論文中是否提供消融研究或元件分析？**
A：根據現有文本，論文以端到端增益為主要論證，強調四階段流水線的整體效果（O(m×n) → O(m+n) 的複雜度下降、跨框架 pass rate 提升、token 節省與安全觸發率）。雖然未明確列出逐元件消融表格，但透過區分「原始 SKILL.md」與「編譯後 SKILL.md」的對照實驗，已能間接驗證 SkIR 轉換與發射器優化的實質貢獻。讀者可期待後續工作針對各階段（如僅做格式轉換而不做安全檢查）進行更細粒度的拆解分析。

**Q10：SkCC 在實際部署中有哪些典型應用場景？**
A：在企業內部代理部署中，組織可集中撰寫一份技能源碼，編譯後同時發布到多個代理框架，避免各團隊各自維護格式變體。對技能市集經營者而言，編譯時期的安全檢查能在上架前過濾惡意 payload，降低平台整體風險。對學術研究社群來說，統一的 SkIR 也讓跨框架的技能實驗比較更具可重現性。

**Q11：將 SkCC 整合到產品時需要考量哪些工程因素？**
A：產品整合時需考量發射器（Emitter）的維護成本——每支援一個新框架就要新增一個發射器實作，因此框架 API 變更時需要持續更新。此外，編譯產物（compiled SKILL.md）需與既有漸進式揭露機制（route.yaml）相容，否則會破壞代理初始化時的輕量路由。安全規則集也需要隨新型攻擊手法持續擴充，避免反技能注入規則淪為靜態清單。

**Q12：SkCC 對整個 LLM 代理領域可能產生什麼影響？**
A：SkCC 將「編譯器思維」引入代理技能開發，可能促使後續研究把更多部署前保證（如隱私、版權、合規）納入 IR 層級的檢查。對框架供應商而言，發射器介面標準化有機會促成類似 LLVM 後端的生態分工，催生第三方發射器市場。長遠來看，這套架構也為「代理作業系統」概念奠定基礎——技能如同程式，編譯器如同系統服務層。

**Q13：SkCC 目前已承認的限制有哪些？**
A：論文中坦承編譯增益高度依賴發射器品質，若發射器未能精準捕捉目標框架的格式偏好，效益會打折。安全檢查以編譯時期靜態分析為主，對需要執行時期上下文才能判定的攻擊（如多輪對話中的漸進式注入）覆蓋有限。此外，SkIR 的強型別設計雖提升安全性，卻也提高了技能作者的學習門檻，可能影響社群採用意願。

**Q14：SkCC 在哪些情境下可能失效或表現不佳？**
A：當技能本身語意高度依賴特定框架的隱式行為（例如某框架特有的工具呼叫慣例）時，純格式層的編譯無法彌補語意落差。若社群技能含有非標準 YAML frontmatter 或自訂 Markdown 擴充，語法解析器可能無法正確抽取 AST，導致後續 IR 失真。在安全方面，繞過靜態規則的對抗式攻擊（例如將惡意指令藏在看似無害的自然語言段落中）仍可能通過編譯檢查。

**Q15：SkCC 未來可延伸的研究方向為何？**
A：未來可朝幾個方向推進：首先是擴充 SkIR 的表達能力以涵蓋多模態技能（如圖像、音訊指令）；其次是把更多安全屬性（如資料流追蹤、機密資訊過濾）整合進安全優化器；再者是探索增量式編譯與分散式技能快取，進一步降低大規模技能市集的編譯成本。此外，跨框架的基準測試標準化（如擴充 SkillsBench）也是推動領域可重現性的關鍵下一步。

## 實務應用指南

### 適用場景

**1. 企業內部多框架代理部署**
大型企業同時使用 Claude Code、OpenAI Codex、Gemini CLI 與 Kimi CLI 處理不同部門任務（例如：研發部門用 Claude Code、客服部門用 Kimi CLI）。透過 SkCC 將內部 SOP 撰寫為單一 SKILL.md 來源，編譯後統一部署至各框架，避免每個框架各別維護一份技能副本。

**2. 社群技能市集的安全審核**
經營類似 Anthropic-skills、ecc-skills、sentry-skills 等公開技能儲存庫時，可在技能上架前透過 SkCC 的反技能注入（Anti-Skill Injection）分析器進行編譯時期掃描，自動過濾含有提示詞注入、可疑指令呼叫或未宣告外部服務的惡意技能。

**3. 開源技能貢獻者的單一來源維護**
獨立開發者撰寫一次 SKILL.md 即可發布至多個框架生態系，無需手動針對每個框架調整 XML 語意分層、XML 標籤化 Markdown 或 YAML 巢狀結構等格式偏好，徹底解決格式稅（Format Tax）造成的效能損失。

**4. 跨國 SaaS 產品的本地化代理技能**
針對不同地區使用的 LLM 代理框架（例如：北美偏好 Claude Code、亞太偏好 Kimi CLI），將合規檢查、資料處理流程等領域特定知識封裝為技能後，透過 SkCC 編譯為各框架原生格式，確保各區域用戶體驗一致。

**5. 學術研究中的可重現實驗**
研究團隊需要在 SkillsBench 等基準上比較不同框架的代理表現時，可使用 SkCC 確保所有技能以各框架偏好的最佳格式呈現，消除「格式變異」這個混淆變因，使效能比較聚焦於模型與框架本身。

### 實作前置條件

**資料準備**
- 至少一份符合 SKILL.md 規範的技能來源檔案（含 YAML frontmatter 與 Markdown 內文）
- 目標框架清單（Claude Code、OpenAI Codex、Gemini CLI、Kimi CLI 等）及其原生格式偏好設定
- SkillsBench 或自建評測資料集，用於驗證編譯前後的通過率差異
- 已知惡意技能樣本集，用於校驗反技能注入機制的觸發率（目標 ≥ 94.8%）

**運算資源**
- 一般開發用筆電或工作站即可，編譯延遲低於 10ms 不需 GPU
- CI/CD 環境需支援容器化執行（用於自動化編譯流水線）
- 建議預留約 200MB 磁碟空間存放 SkIR 中間表示快取與各框架發射器（Emitter）模板

**技能門檻**
- 熟悉至少一種 LLM 代理框架的 SKILL.md 載入機制與漸進式揭露（Progressive Disclosure）流程
- 具備編譯器基礎概念：AST、IR、分析器（Analyzer）、發射器
- 理解 YAML、JSON、Markdown、XML 四種結構化格式的語法差異
- 具備基本的提示詞工程與安全威脅建模知識

### 實作步驟建議

**步驟一：盤點現有技能與目標框架**
盤點組織內所有 SKILL.md 技能清單（m 個）與欲支援的代理框架清單（n 個），建立技能—框架對照矩陣，識別目前手動跨平台改寫的維護負擔熱點。

**步驟二：部署 SkCC 編譯環境**
從 GitHub 取得 SkCC 核心編譯器，安裝 SkIR Schema 與四階段流水線（語法解析器 → IR 建構器 → 安全優化器 → 多型目標發射器），並設定 route.yaml 路由清單模板。

**步驟三：撰寫或重構技能為單一來源**
將現有技能改寫為格式無關的 SKILL.md，專注於語意內容而非框架特定格式。技能編寫階段僅需描述領域特定知識與執行意圖，不需考慮目標框架。

**步驟四：執行編譯並驗證安全檢查**
對每份 SKILL.md 執行 SkCC Compile，確認反技能注入分析器觸發率達標（94.8% 為參考基準），檢查被標記的技能是否含未授權的指令鏈或外部服務呼叫。

**步驟五：發射至各框架並量測效能**
透過多型發射器將 SkIR 轉為各框架原生格式（XML 語意分層給 Claude、XML 標籤化 Markdown 給 GPT 系列、YAML 給深度巢狀資料場景），部署至目標代理環境。

**步驟六：建立持續整合與監控**
將 SkCC 編譯流程整合至 CI/CD，設定通過率、Token 節省率（10–46% 為參考基準）、編譯延遲（小於 10ms）等關鍵指標的儀表板，並對新提交的技能自動觸發安全掃描。

### 潛在風險與注意事項

**風險一：發射器覆蓋率不足**
若新增的代理框架未實作對應的 Emitter，技能將無法編譯。**緩解措施**：優先盤點組織內實際使用的框架，採用漸進式新增發射器策略；同時貢獻發射器回饋給 SkCC 開源社群。

**風險二：反技能注入的誤判與漏判**
94.8% 的觸發率意味仍有約 5% 的惡意技能可能未被攔截。**緩解措施**：將 SkCC 安全檢查視為第一道防線，搭配執行時期的代理行為監控與沙箱機制形成縱深防禦；定期更新惡意樣本庫以提升分析器準確率。

**風險三：SkIR Schema 演進造成向後相容問題**
強型別中間表示的結構變更可能導致舊技能無法編譯。**緩解措施**：採用語意化版本控制，明確區分破壞性變更；提供 SkIR 遷移工具與向下相容層。

**風險四：過度優化格式反而犧牲可讀性**
編譯後的框架原生格式可能對人類審閱者不友善，增加除錯難度。**緩解措施**：保留原始 SKILL.md 與編譯產物的對應關係映射；在發射器輸出中保留語意註解。

**風險五：Token 節省的測量偏差**
10–46% 的 Token 節省率可能因任務類型而異，深度巢狀資料場景的節省幅度通常較大。**緩解措施**：在自家業務場景上重新量測，避免直接套用基準數字作為成本估算依據。

### 與其他技術的整合建議

**與 Model Context Protocol（MCP）整合**
SkCC 編譯後的技能可透過 MCP 標準介面連接外部工具與服務。建議在 SkIR 中保留 MCP 工具呼叫的語意標記，讓發射器能正確轉譯各框架的函式呼叫語法。

**與既有 CI/CD 流水線整合**
將 SkCC 編譯階段嵌入 GitHub Actions 或 GitLab CI，在技能合併前自動執行安全掃描與格式編譯，產出可直接部署的框架原生產物作為 Release Artifact。

**與提示詞管理平台整合**
若組織已使用 LangSmith、PromptLayer 等提示詞管理工具，可將 SkCC 編譯後的技能版本與提示詞實驗記錄關聯，追蹤格式變更對代理效能的影響。

**與向量資料庫與語意路由整合**
SkCC 的 route.yaml 輕量級元資料（約 50 tokens/技能）可直接寫入語意路由的 embedding 索引，支援隱式路由（透過描述匹配）與顯式路由（透過技能名稱呼叫）兩種模式。

**與傳統靜態分析工具整合**
將反技能注入分析器與 Semgrep、CodeQL 等程式碼靜態分析工具鏈結，對含有可執行程式碼片段的技能進行雙重檢查，提升整體安全態勢。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題陳述，理解「為什麼同一份技能在不同框架表現差異可達 40%」這個核心痛點；接著跳過編譯器細節，直接看圖 1 的左半部分（代理工作流程）建立直觀印象，再回頭理解 SkCC 如何將 O(m×n) 的改寫成本降至 O(m+n)。

**給 AI 工程師**：重點關注第 2.1 節的格式偏好對照表（Claude 偏 XML 語意分層、GPT 系列偏 XML 標籤化 Markdown、深度巢狀資料偏 YAML）以及四階段流水線的實作細節。建議直接 clone SkCC 開源儲存庫，在自家技能上跑一輪編譯，比較 Claude Code 與 Kimi CLI 上的通過率提升幅度（21.1% → 33.3% 與 35.1% → 48.7%）。

**給研究者**：第 2.2 節的格式敏感度文獻回顧與反技能注入的威脅模型是值得深挖的方向。建議從「格式稅」與「強型別 IR 對代理可解釋性的影響」兩個角度切入，思考 SkIR 是否能進一步用於技能語意相似度分析或自動化技能合成等延伸研究。

**給產品經理**：聚焦於商業價值層面——單一技能來源降低維護成本、跨框架部署加速市場進入、安全編譯時期檢查降低合規風險。建議將 10–46% 的 Token 節省率換算為實際 API 成本節省，並評估在自家產品線上導入 SkCC 的投資報酬率，特別注意 94.8% 安全觸發率對客戶信任度的提升效果。
