## 摘要翻譯

現代的文字轉 SQL (Text-to-SQL) 系統會產生多個候選 SQL 查詢，並對其進行排序以決定最終預測。然而，現有方法面臨兩項限制。首先，它們經常對功能等價 (Functionally Equivalent) 的 SQL 查詢給出不一致的分數，即使這些查詢具有相同的執行結果 (Execution Result)。其次，當正確的 SQL 不在候選集 (Candidate Pool) 中時，排序便無法選出正確答案。我們提出 R^3-SQL，這是一個透過統一獎勵 (Unified Reward) 進行排序與重新取樣 (Resampling) 來解決上述兩個問題的文字轉 SQL (Text-to-SQL) 框架。R^3-SQL 首先根據執行結果將候選分組，並對分組進行排序以確保一致性。為了對每個分組進行評分，它結合了跨分組的配對偏好 (Pairwise Preference) 與來自最佳分組排名和大小的逐點效用 (Pointwise Utility)，以捕捉相對偏好 (Relative Preference)、一致性與候選品質 (Candidate Quality)。為了提升候選召回率 (Candidate Recall)，R^3-SQL 引入了代理式重新取樣 (Agentic Resampling)，會評估所生成的候選集，並在正確的 SQL 可能不在其中時，選擇性地進行重新取樣。R^3-SQL 在 BIRD-dev 上達到了 75.03 的執行準確率 (Execution Accuracy)，在使用已公開模型規模的方法中達到新的最先進 (SOTA) 水準，並在五個基準測試 (Benchmark) 上皆有一致提升。

### 核心貢獻（3～5點）
- 提出統一獎勵 (Unified Reward) 機制，結合跨分組的配對偏好 (Pairwise Preference) 與逐點效用 (Pointwise Utility)，解決功能等價 (Functionally Equivalent) SQL 查詢評分不一致的問題。
- 提出代理式重新取樣 (Agentic Resampling) 策略，透過評估候選集 (Candidate Pool) 並選擇性地重新取樣，提升候選召回率 (Candidate Recall)，緩解正確 SQL 缺失時排序無法恢復的限制。
- 在 BIRD-dev 上達到 75.03 的執行準確率 (Execution Accuracy)，於使用已公開模型規模的方法中締造新的最先進 (SOTA) 紀錄。
- 在五個基準測試 (Benchmark) 上皆展現一致且穩定的性能提升，驗證方法的泛化能力。

### 適合對象
從事文字轉 SQL (Text-to-SQL)、自然語言轉程式碼、資料庫查詢生成、大型語言模型 (LLM) 推理與排序機制 (Ranking Mechanism) 研究的研究人員與工程師；以及對 AI 代理 (Agent)、資訊檢索 (Information Retrieval) 與基準測試 (Benchmark) 評估感興趣的學術界與產業界實務工作者。

## 深度分析

#### 方法論解析

R³-SQL 的方法論核心在於同時解決文字轉 SQL (Text-to-SQL) 系統中兩個被忽視但影響深遠的問題：**功能不一致性 (functional inconsistency)** 與 **有界召回率 (bounded recall)**。其方法設計可分為兩個相互銜接的階段：探索階段（候選生成與分組）與利用階段（獎勵排序與選擇）。

**第一階段：候選生成與執行分組**

R³-SQL 沿用「生成後排序範式 (generate-then-rank paradigm)」，由大型語言模型 (LLM) 採樣多個候選 SQL 查詢。與傳統做法不同的是，R³-SQL 並非直接對個別候選進行評分，而是先根據**執行結果 (execution result)** 將候選分組——所有產生相同執行結果的 SQL 查詢被歸入同一組。這一步驟的關鍵在於：即使 SQL 的**表面形式 (surface form)** 不同（例如 JOIN 順序、子查詢嵌套方式、欄位別名差異），只要執行結果一致，就視為**功能等價 (functionally equivalent)** 的候選。此分組機制直接消除了逐點排序器 (pointwise ranker) 對等價 SQL 賦予不同分數的問題，從根本上緩解了功能不一致性。

**第二階段：分組式獎勵排序 (Groupwise Reward Ranking)**

R³-SQL 的核心創新在於其**統一獎勵 (unified reward)** 函數，該函數整合了三種互補訊號：

1. **組間相對偏好 (inter-group preference)**：採用列表式 (listwise) 配對偏好 (pairwise preference) 機制，跨組比較候選的相對優劣。這捕捉了不同執行結果之間的語意差異，例如哪個查詢更符合自然語言問題的意圖。

2. **組內一致性 (inner-group consistency)**：透過**代表性樣本 (representative sample)** 的排名與組的大小 (group size) 共同計算**分組效用 (group utility)**。代表性樣本通常選自組內排名最高的候選，其**逐點效用 (pointwise utility)** 反映個別候選品質；而組的大小則反映該執行結果被多數生成器認可的程度，作為一致性的代理指標。

3. **候選品質 (candidate quality)**：透過逐點評分器對代表性樣本進行獨立評分，捕捉 SQL 本身的語法正確性與邏輯合理性。

這三種訊號的線性組合形成最終的分組評分，使得排序結果同時考慮相對偏好、組內共識與個別品質。相較於僅依賴組大小的**功能多數決 (Functional Majority Voting, FMV)**，R³-SQL 能夠識別出「小但正確」的組，避免被「大多數但錯誤」的組壓制。

**第三階段：代理式重新取樣 (Agentic Resampling)**

針對有界召回率問題，R³-SQL 引入了一個判斷機制：模型首先評估當前候選集 (candidate pool) 中是否**可能**包含正確的 SQL 查詢。這個判斷基於以下訊號：若所有組的代表性樣本均獲得低獎勵分數，或組的大小分佈過於集中於少數執行結果，則判定候選集可能缺乏正確答案。此時觸發**代理式重新取樣 (agentic resampling)**，由 LLM 根據先前嘗試的失敗訊號（如語法錯誤、語意錯誤）進行有針對性的重新生成，並對語法與語意錯誤同時進行修正。這與僅修正語法錯誤的系統（如 CHASE-SQL、XiYan-SQL）形成對比，能更全面地提升候選召回率 (candidate recall)。

**方法論的統一性**

值得強調的是，R³-SQL 的兩個階段並非獨立運作，而是共享同一個獎勵模型。重新取樣的觸發條件本身即由獎勵訊號驅動，這種**統一建模 (unified modeling)** 設計使得探索與利用形成閉環：排序結果不僅決定最終預測，還影響是否需要進一步探索。

#### 實驗數據解讀

**主要效能結果**

R³-SQL 在 BIRD-dev 上達到 **75.03% 執行準確率 (Execution Accuracy)**，在公開模型大小的方法中創下新的**最先進 (State of the Art, SOTA)** 紀錄。從 Table 1 的對比可見：

| 系統 | 模型大小 | 執行準確率 |
|------|---------|-----------|
| Contextual-SQL | 未公開 | 73.50% |
| CHASE-SQL | 未公開 | 74.90% |
| Agentar-Scale-SQL | 未公開 | 74.90% |
| XiYan-SQL | 未公開 | 73.34% |
| OpenSearch-SQL | 未公開 | 69.30% |
| **R³-SQL** | **32B** | **75.03%** |
| CSC-SQL | 70B | 71.69% |
| Agentar-Scale-SQL | 32B | 71.12% |
| XiYan-SQL | 32B | 67.01% |

關鍵觀察在於：R³-SQL 以 32B 模型超越了多個使用未公開（可能更大）模型大小的系統，且在同為 32B 的公平比較中，領先 Agentar-Scale-SQL 約 3.91 個百分點、領先 XiYan-SQL 約 8.02 個百分點。這顯示其方法論的增益並非單純來自模型規模，而是來自排序與重新取樣機制的設計優勢。

**消融實驗的意涵**

論文報告了三項關鍵消融數據：

1. **分組評分消除分數變異**：分組機制使功能等價 SQL 獲得一致評分，這是功能不一致性問題的直接驗證。

2. **一致性目標提升輸入順序穩健性 +11.89 百分點**：這是一個極為顯著的增益。列表式排序器通常對候選輸入順序敏感（permutation sensitivity），透過組內一致性訊號，R³-SQL 大幅降低了這種脆弱性，對實際部署的穩定性具有重要意義。

3. **代理式重新取樣提升候選召回率 +3.92 百分點**：這證實了有界召回率確實是現有系統的瓶頸，且選擇性重新取樣比盲目重新取樣更有效率。

**跨基準泛化能力**

論文宣稱在五個基準測試上均有一致提升，但具體數字需參閱正文表格。跨基準的一致性增益表明 R³-SQL 並非針對單一資料集過擬合，而是捕捉了文字轉 SQL 任務的通用特性。

**實驗設計的侷限**

需注意以下幾點：(1) 執行準確率僅評估最終預測是否與標準答案產生相同執行結果，無法區分「接近正確」與「完全正確」；(2) 缺乏對錯誤類型的細粒度分析，例如哪些類型的查詢（如巢狀子查詢、多表 JOIN、聚合函數）受益最多；(3) 與人類專家的 SQL 品質比較未被納入。

#### 與現有研究的比較

**功能不一致性問題的處理演進**

文字轉 SQL 排序方法的演進可分為三個階段：

- **逐點排序階段 (Pointwise Era)**：以 Contextual-SQL 為代表，每個候選獨立評分。優點是實作簡單、可並行；缺點是無法捕捉候選間的相對關係，且對等價 SQL 評分不一致。

- **列表式排序階段 (Listwise Era)**：以 CHASE-SQL、Agentar-Scale-SQL 為代表，聯合比較多個候選。優點是能學習相對偏好；缺點是仍未解決功能不一致性，且對輸入順序敏感。

- **分組式排序階段 (Groupwise Era)**：R³-SQL 與 CSC-SQL、XiYan-SQL、OpenSearch-SQL 同屬此階段，但 R³-SQL 是唯一結合逐點與列表式訊號並超越單純 FMV 的方法。CSC-SQL 雖也分組，但僅使用 FMV 且無學習型排序器；XiYan-SQL 雖結合列表式與 FMV，但未引入逐點效用。

**有界召回率問題的獨特貢獻**

在重新取樣機制上，現有系統的差異明顯：

- **CHASE-SQL、XiYan-SQL、OpenSearch-SQL**：僅修正語法錯誤，無法處理語意錯誤導致的召回率瓶頸。
- **Agentar-Scale-SQL**：同時修正語法與語意錯誤，但缺乏判斷機制，可能在候選集已包含正確答案時仍進行不必要的重新取樣。
- **CSC-SQL**：採用合併修訂 (merge-revision) 機制，但無差別地對前兩組進行修訂，可能引入新錯誤。
- **R³-SQL**：唯一採用**選擇性**重新取樣的系統，僅在判斷候選集可能缺乏正確答案時觸發，兼顧效率與效果。

**相對優勢總結**

R³-SQL 的核心優勢在於**雙重統一**：(1) 統一了逐點與列表式獎勵訊號；(2) 統一了排序與重新取樣的觸發邏輯。這種設計哲學使其在功能不一致性與有界召回率兩個維度上同時取得進展，而非僅解決其中一個。

**現有研究的侷限**

儘管 R³-SQL 表現優異，仍存在以下侷限：

1. **依賴執行結果分組**：對於無法執行 SQL 的場景（如某些線上服務、隱私限制），此方法無法適用。
2. **代理式重新取樣的判斷可靠性**：若判斷機制本身出錯，可能導致不必要的計算開銷或錯失重新取樣機會。
3. **未探討與測試階段計算 (Test-Time Compute) 規模的關係**：隨著取樣數增加，R³-SQL 的邊際效益如何變化尚不明確。

**6. 與其他生成任務的遷移**

R³-SQL 的「分組式獎勵排序 + 選擇性重新取樣」框架具有任務無關性，未來可探索其在其他結構化生成任務中的應用：(1) 程式碼生成（Python、Java）；(2) 數學推理（形式化證明）；(3) 知識圖譜查詢（SPARQL）。這些任務同樣面臨「功能等價輸出評分不一致」與「正確解不在候選集中」的挑戰，R³-SQL 的設計哲學可能具有普適價值。

## 論文問答

**Q1：R^3-SQL 試圖解決 Text-to-SQL 領域中的哪些核心問題？**
A：R^3-SQL 主要針對「生成後排序」（generate-then-rank）範式中的兩個關鍵瓶頸。第一個是「功能不一致性」（functional inconsistency），即功能等價但表面形式不同的 SQL 查詢會被排序器給出不一致的分數，導致正確候選被錯誤淘汰。第二個是「有界召回率」（bounded recall），當生成器未能產出正確候選時，無論排序器多麼精準都無法挽回正確答案。這兩個問題分別限制了排序階段的精確度與候選集的覆蓋率，是現代 Text-to-SQL 系統表現的天花板。

**Q2：為什麼現有的逐點（pointwise）與列表式（listwise）排序器會失敗？**
A：逐點排序器對每個候選 SQL 獨立評分，無法察覺功能等價的查詢應獲得相同分數，因此同一執行結果的不同 SQL 會被分散到不同排名位置。列表式排序器雖然能進行候選間的相對比較，但同樣缺乏「按執行結果分組」的機制，使得功能等價的查詢仍可能被賦予不同分數。此外，無論是逐點還是列表式排序器，都無法解決「正確 SQL 根本不在候選池中」的有界召回問題，這是排序階段無法跨越的結構性限制。

**Q3：為什麼「有界召回率」是 Text-to-SQL 系統中不可忽視的問題？**
A：在資訊檢索文獻中，有界召回率指的是當正確答案不在候選池中時，無論排序策略多麼精準，系統都無法輸出正確結果。在 Text-to-SQL 場景中，LLM 採樣的候選 SQL 數量有限，若生成器對特定問題語意理解錯誤，產出的所有候選都可能語意不正確，此時再好的排序器也無能為力。這意味著僅改善排序器並不足以提升整體表現，必須從「擴大候選池覆蓋率」與「精準排序」兩個方向同時著手，這也是 R^3-SQL 引入代理式重新取樣（agentic resampling）的根本動機。

**Q4：R^3-SQL 的分組式排序（groupwise ranking）核心創新是什麼？**
A：R^3-SQL 的核心創新在於先依「執行結果」將候選 SQL 分組，再對「群組」而非個別查詢進行排序，從根本上消除功能等價 SQL 之間的分數差異。為了精準評分每個群組，它結合了三種互補訊號：組間的配對偏好（listwise 相對比較）、組內一致性（透過群組大小反映），以及個別候選品質（pointwise 效用）。這種統一獎勵設計同時捕捉了「相對偏好」、「組內一致性」與「候選品質」三個維度，突破了傳統功能多數決（FMV）僅依群組大小排序的粗糙啟發式。

**Q5：R^3-SQL 的代理式重新取樣（agentic resampling）是如何運作的？**
A：代理式重新取樣是一種「判斷式」的擴充機制：系統會先評估當前候選池是否可能包含正確 SQL，若判斷為「否」才觸發重新取樣。這與 CHASE-SQL、XiYan-SQL 等僅針對語法錯誤進行修正的方法不同，R^3-SQL 同時處理語法與語意錯誤。透過選擇性地重新取樣，系統能在「正確候選已存在」時避免不必要的計算浪費與引入新錯誤的風險，同時在「正確候選可能缺席」時主動擴大候選池以提升召回率。

**Q6：R^3-SQL 在統一逐點與列表式訊號時做了哪些關鍵設計選擇？**
A：R^3-SQL 採用「群組效用」（group utility）作為統一評分框架，將列表式訊號（組間配對偏好）與逐點訊號（代表性樣本的效用）線性組合。其中代表性樣本的效用同時考量其在群組內的排名與群組大小，使評分函數能同時反映相對偏好、組內一致性與候選品質。這種設計避免了單一訊號的偏差：純逐點會忽略組間相對關係，純列表式則難以量化單一群組的絕對品質，而統一獎勵則兼顧兩者優勢。

**Q7：R^3-SQL 在哪些基準測試上進行了評估，關鍵結果為何？**
A：R^3-SQL 在五個 Text-to-SQL 基準測試上進行了實驗，其中最重要的結果是在 BIRD-dev 上達到 75.03% 的執行準確率（execution accuracy），創下「模型規模公開」方法中的新 SOTA。相較於同樣使用 32B 模型的 XiYan-SQL（67.01%）與 Agentar-Scale-SQL（71.12%），R^3-SQL 分別領先約 8 與 4 個百分點，顯示其在相同模型規模下的顯著優勢。此外，跨五個基準的一致性提升證明了該框架的泛化能力，而非僅針對單一資料集過擬合。

**Q8：與其他「模型規模公開」的 Text-to-SQL 系統相比，R^3-SQL 的競爭優勢為何？**
A：從 Table 1 的比較可見，R^3-SQL 是唯一同時具備「執行結果分組」、「群組式排序（結合 pointwise 與 listwise）」與「語法與語意錯誤皆觸發重新取樣」三項特徵的系統。CSC-SQL 雖有分組但僅用 FMV 啟發式排序且無條件重新取樣；XiYan-SQL 雖有分組但排序仍依賴 FMV；Agentar-Scale-SQL 雖有語意重新取樣但無分組機制。R^3-SQL 在功能不一致性與有界召回率兩個維度上同時取得進展，這是其領先同規模模型的結構性原因。

**Q9：消融研究（ablation studies）揭示了各元件的哪些貢獻？**
A：消融研究顯示三項關鍵貢獻：第一，群組式評分消除了功能等價 SQL 之間的分數變異，證明分組機制對功能一致性的必要性；第二，一致性目標（consistency objective）使輸入順序穩健性提升 +11.89 個百分點，顯示該機制有效緩解排序器對候選排列順序的敏感度；第三，代理式重新取樣使候選召回率提升 +3.92 個百分點，驗證了「判斷式擴充候選池」對有界召回問題的實質幫助。這三項數據共同支撐了 R^3-SQL 設計中每個元件的不可取代性。

**Q10：R^3-SQL 適用於哪些實際應用場景？**
A：R^3-SQL 特別適用於企業級資料分析、BI 儀表板查詢、自然語言資料庫介面等需要高準確度 SQL 生成的場景。在這些場景中，使用者通常以自然語言提問（例如「上季各區域營收前五名的產品」），系統需轉換為 SQL 並執行查詢。由於商業決策依賴查詢結果的正確性，R^3-SQL 透過統一獎勵排序與代理式重新取樣，能顯著降低錯誤 SQL 被選中的機率，對金融、醫療、電商等容錯率低的領域尤為關鍵。

**Q11：將 R^3-SQL 部署到實際產品時需要考量哪些工程因素？**
A：實際部署時需考量以下幾點：第一，候選採樣數量與重新取樣次數會直接影響推理延遲與 API 成本，需在準確率與回應時間間取得平衡；第二，執行結果分組需要實際執行 SQL，這在生產環境中需要安全的沙箱機制以避免惡意或破壞性查詢；第三，代理式重新取樣的「判斷器」本身也是一個 LLM 呼叫，會增加額外成本；第四，模型規模（32B）對邊緣部署仍是挑戰，可能需要蒸餾或量化以適配資源受限環境。

**Q12：R^3-SQL 對 Text-to-SQL 領域的更廣泛影響為何？**
A：R^3-SQL 的貢獻超越了單一基準的 SOTA 數字，它將「功能不一致性」與「有界召回率」兩個問題明確形式化，為後續研究提供了清晰的改進方向。其「統一獎勵」框架（結合 pointwise、listwise 與群組大小）可被視為一種通用的「多訊號融合排序」範式，可能啟發其他生成任務（如程式合成、數學推理）採用類似的群組式評分策略。此外，「代理式重新取樣」的概念——讓模型判斷是否需要重新生成——也為解決 LLM 生成品質瓶頸提供了新思路。

**Q13：R^3-SQL 論文中有哪些已承認的限制？**
A：雖然論文未在結論部分明確列出所有限制，但從實驗設計可推論出幾項限制：首先，所有 SOTA 比較都基於 BIRD-dev 單一基準，雖然聲稱跨五個基準有一致提升，但未深入分析各基準的特性差異；其次，32B 模型規模雖屬「公開」，但對許多實際部署場景仍偏大；最後，代理式重新取樣的判斷器本身可能出錯，若判斷錯誤可能導致不必要的重新取樣或錯失重新取樣機會，這是該機制的內在風險。

**Q14：R^3-SQL 在哪些情況下可能會失敗？**
A：R^3-SQL 在以下情境可能表現不佳：第一，當問題極度複雜且涉及多表 JOIN、子查詢巢狀等深層語意時，LLM 生成器可能根本無法產出任何語意正確的候選，此時即使重新取樣也難以突破；第二，當資料庫結構特殊（如非標準 schema、缺乏明確外鍵關係）時，執行結果分組可能產生大量小群組，使群組效用訊號變得雜訊；第三，若代理式重新取樣的判斷器對「正確候選是否存在」判斷錯誤，可能浪費計算資源或錯失關鍵重新取樣時機。

**Q15：基於 R^3-SQL 的成果，未來有哪些值得探索的研究方向？**
A：未來可探索的方向包括：第一，將「統一獎勵」框架擴展至其他程式合成任務（如 Python、Verilog），驗證其通用性；第二，設計更輕量的判斷器以降低代理式重新取樣的成本，例如用小型分類器取代 LLM 呼叫；第三，結合測試時運算縮放（test-time compute scaling）技術，動態調整候選數量與重新取樣次數；第四，探討多模態輸入（如 schema 圖、查詢歷史）如何進一步提升分組與排序的精確度；第五，研究如何在訓練階段將功能一致性與有界召回率納入損失函數，從根本上改善生成器的行為。

## 實務應用指南

### 適用場景

1. **企業級商業智慧查詢自動化**：金融、電商、零售等產業的業務分析師常需以自然語言提問（例如「上季華北區退貨率最高的品類為何？」），由 R³-SQL 自動生成 SQL 查詢並透過分組式排序挑出最可靠的結果，減少人工撰寫查詢的成本。

2. **客服與對話式資料問答系統**：在客服機器人或內部知識庫中，使用者以口語化中文提問資料庫內容，R³-SQL 的代理式重新取樣機制可在候選集品質不佳時自動擴大取樣，提升一次性答對率。

3. **資料治理與合規稽核**：稽核人員需對同一問題產生多個等價 SQL 並交叉驗證，R³-SQL 的功能等價分組可避免「同一執行結果卻被給不同分數」的稽核偏差，提升審查可信度。

4. **教育訓練與 SQL 學習輔助**：SQL 教學平台可利用 R³-SQL 對學生提交的查詢進行功能等價分組與品質評分，給予「邏輯正確但寫法不同」的查詢一致評價。

5. **多資料源聯邦查詢**：當企業同時使用 Snowflake、BigQuery、PostgreSQL 等異質資料庫時，R³-SQL 的執行結果分組可作為跨方言查詢的等價性判斷依據。

### 實作前置條件

**資料面**
- 至少一份結構化資料庫（建議含 schema、欄位說明、外鍵關係），並準備自然語言問題與對應 SQL 的標註資料集（如 BIRD、Spider）。
- 候選 SQL 的執行環境（沙箱化的資料庫連線），需具備權限控管以避免任意查詢影響線上系統。
- 用於功能等價分組的執行結果快取（execution result cache），建議以雜湊值儲存以加速比對。

**運算面**
- 一個 32B 等級以上的 LLM（論文使用 32B 揭露規模模型達到 SOTA），需具備足夠的推理吞吐量以支援多次取樣。
- 候選生成階段建議每題取樣 8–32 個 SQL；代理式重新取樣階段需預留額外 2–4 倍的 token 預算。
- 排序器若採學習式模型，需準備 pairwise 偏好標註資料；若採 prompting 式 LLM 排序，則需較大的 context window（建議 32K tokens 以上）以容納多組候選。

**技能面**
- 熟悉 SQL 語法與資料庫執行計畫。
- 具備 LLM prompting、reward modeling 與 listwise/pairwise 排序經驗。
- 了解資訊檢索中的 recall 概念與 resampling 策略。

---

### 實作步驟建議

1. **建立候選生成管線**：使用 LLM 對每個自然語言問題取樣 N 個 SQL 候選（建議 N ≥ 16），並對每個候選執行語法檢查與資料庫執行，記錄執行結果。

2. **執行結果分組（Execution-based Grouping）**：將所有成功執行的候選依執行結果雜湊分組，每組選取一個代表性樣本（representative sample）。此步驟直接消除功能不一致性。

3. **計算組間相對偏好（Inter-Group Preference）**：對每對分組，使用 LLM 進行 pairwise 比較，產出相對偏好分數，捕捉「哪一組整體更可能正確」。

4. **計算組內效用（Group Utility）**：結合代表性樣本的逐點效用（pointwise utility，由 pointwise ranker 給出）與其在組內的排名與組的大小，產出組級分數。

5. **統一獎勵排序（Unified Reward Ranking）**：將 pairwise 偏好與 group utility 融合為單一分數，對所有分組排序，選出最終 SQL。

6. **代理式重新取樣（Agentic Resampling）**：訓練或設計一個判別器，預測當前候選集中是否包含正確 SQL；若信心不足，觸發重新取樣並重複步驟 1–5。

7. **評估與監控**：在 BIRD-dev 等基準上驗證執行準確率，並持續監控候選召回率（candidate recall）與組間偏好一致性。

8. **部署與迭代**：將管線封裝為 API，記錄每次推理的候選數、分組數、最終選中組別與信心分數，作為後續 fine-tuning 與錯誤分析的依據。

---

### 潛在風險與注意事項

- **執行成本爆炸**：每題多次取樣 + 多次執行 + 多次 pairwise 比較，會使單題成本遠高於單次生成。建議在 production 中限制最大取樣數，並對低信心題目才啟動 resampling。
- **沙箱安全性**：候選 SQL 會被實際執行，必須在唯讀或受限權限的資料庫沙箱中運行，避免 `DROP`、`UPDATE` 等破壞性語句。
- **執行結果快取一致性**：若底層資料變動，相同 SQL 的執行結果可能改變，導致分組不穩定。建議為每次推理建立快照或加上時間戳記。
- **Pairwise 比較的順序敏感性**：LLM 對輸入順序敏感，可能造成組間偏好不一致。論文指出加入一致性目標可提升 +11.89 pp，建議在訓練或 prompting 中加入順序對換的對稱性約束。
- **重新取樣的過度觸發**：若判別器過於敏感，會造成不必要的成本浪費；過於遲鈍則無法解決 bounded recall。需以驗證集校準 threshold。
- **小而正確的組被忽略**：FMV 會讓小組被大組壓過，R³-SQL 雖改善此問題，但若組內代表性樣本本身品質差，仍可能誤判。建議結合執行計畫分析作為輔助訊號。
- **基準外泛化風險**：BIRD 等基準偏英文與特定領域，部署到中文或產業專屬 schema 時，需重新評估並可能需要領域微調。

### 與其他技術的整合建議

- **與 RAG 整合**：將 schema 檢索、文件說明與 few-shot 範例透過 RAG 提供給 LLM，可顯著提升候選品質，進而降低 resampling 觸發率。
- **與 Text-to-SQL 工具鏈整合**：可將 R³-SQL 的排序器模組化，替換現有系統（如 CHASE-SQL、XiYan-SQL）的排序階段，作為 drop-in upgrade。
- **與 SQL 優化器整合**：將最終選中的 SQL 交由傳統查詢優化器（如 Apache Calcite）進行計畫優化，兼顧正確性與效能。
- **與 Agent 框架整合**：將代理式重新取樣包裝為 LangGraph 或 AutoGen 中的節點，與其他資料處理 agent 協作。
- **與評測平台整合**：將 BIRD、Spider 等基準納入 CI/CD 流程，每次模型或 prompt 變更時自動回歸測試，確保執行準確率不退步。
- **與監控系統整合**：把候選召回率、組數分佈、最終信心分數等指標接入 observability 平台（如 Grafana），即時發現資料漂移或模型退化。

**給 AI 工程師**：重點閱讀第 3 節的 groupwise scoring 公式與 agentic resampling 的判別器設計，並對照 Table 1 比較各系統在 grouping、ranker、resample 條件上的差異。可直接以 32B 等級模型重現實驗，並將排序器模組化以便替換到自家 Text-to-SQL 系統中。

**給研究者**：第 2 節的相關工作整理與 Table 1 的系統化比較是切入點；建議深入分析 groupwise reward 的理論基礎（為何 pointwise + listwise + size 的組合能同時捕捉相對偏好、組內一致性與候選品質），以及 agentic resampling 與資訊檢索中 recall 提升策略的連結，作為後續延伸研究的起點。

**給產品經理**：聚焦於「75.03 執行準確率」、「+3.92 pp 候選召回率提升」、「+11.89 pp 順序魯棒性」這三個量化成果，理解 R³-SQL 在「答對率」與「穩定性」上的具體改善。並關注實作前置條件中的成本與沙箱需求，評估導入時的工程投入與 ROI。
