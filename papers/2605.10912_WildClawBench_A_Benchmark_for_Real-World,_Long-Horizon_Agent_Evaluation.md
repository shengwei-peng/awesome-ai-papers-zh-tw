# WildClawBench：真實世界長程智慧體評估基準測試

## ⚡ TL;DR

現有基準測試多使用合成沙盒與短程任務，無法評估智慧體在真實原生環境中的長程執行能力。
本文提出WildClawBench，設計60項雙語多模態長程任務於真實CLI框架並以混合評分驗證。
最佳模型僅達62.2%，顯示長程原生評估仍待解決，且已開放任務與工具供復現。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）與視覺語言模型（Vision-Language Model, VLM）日益驅動能透過命令列介面（Command-Line Interface, CLI）智慧體框架（Agent Harness）代表使用者行動的智慧體（Agent）。然而，大多數智慧體基準測試（Benchmark）仍仰賴合成沙盒（Synthetic Sandbox）、短程任務（Short-Horizon Task）、模擬服務 API（Mock-Service API）與最終答案檢查（Final-Answer Check），使得智慧體能否在其部署的執行環境（Runtime）中完成真實的長程任務（Long-Horizon Task），仍懸而未決。本文提出 WildClawBench，一項原生執行環境（Native-Runtime）的基準測試，包含 60 項人工撰寫（Human-Authored）的雙語（Bilingual）多模態（Multimodal）任務，涵蓋六個主題類別（Thematic Category）。每項任務平均壁鐘時間（Wall-Clock Time）約 8 分鐘、工具呼叫（Tool Call）逾 20 次，於可復現的 Docker 容器（Docker Container）中執行，內含實際的 CLI 智慧體框架（OpenClaw、Claude Code、Codex 或 Hermes Agent），並可存取真實工具（Real Tool）而非模擬服務。評分採混合式評分（Hybrid Grading）機制，結合確定性規則檢查（Deterministic Rule-Based Check）、對副作用（Side Effect）進行環境狀態稽核（Environment-State Auditing），以及用於語意驗證（Semantic Verification）的 LLM/VLM 評判模型（LLM/VLM Judge）。在 19 個前沿模型（Frontier Model）中，表現最佳的 Claude Opus 4.7 在 OpenClaw 下總體僅達 62.2%，其餘所有模型皆低於 60%，且僅切換智慧體框架即可使單一模型分數變動高達 18 個百分點。這些結果顯示，對當前前沿模型而言，長程、原生執行環境下的智慧體評估仍是一項遠未解決的課題。我們公開釋出任務、程式碼與容器化工具，以支援可復現評估（Reproducible Evaluation）。

### 核心貢獻（3～5點）
- 建立 WildClawBench，一項原生執行環境的基準測試，於可復現的 Docker 容器中執行實際 CLI 智慧體框架並存取真實工具，彌補現有基準測試過度依賴合成沙盒與短程任務之不足。
- 設計 60 項人工撰寫的雙語多模態長程任務，涵蓋六大主題類別，每項任務平均壁鐘時間約 8 分鐘且工具呼叫逾 20 次，貼近真實世界工作負載。
- 提出混合式評分機制，整合確定性規則

## 深度分析

#### 方法論解析

WildClawBench 的核心方法論在於將智慧體（Agent）評估從「答案正確性」轉向「過程可稽核性」。其設計可拆解為四個層面：任務設計、原生執行環境（Native-runtime）建構、智慧體框架（Agent Harness）控制，以及混合式評分（Hybrid Grading）。

在任務設計層面，基準測試（Benchmark）收錄 60 道人工撰寫（Human-authored）的雙語（Bilingual）任務，橫跨六大主題類別（Thematic Category）：生產力流程（Productivity Flow）、程式碼智慧（Code Intelligence）、社交互動（Social Interaction）、搜尋與檢索（Search and Retrieval）、創意合成（Creative Synthesis）與安全對齊（Safety Alignment）。其中 26 題為原生多模態任務（Natively Multimodal Task），要求智慧體同時處理文字與視覺輸入。這些長程任務（Long-horizon Task）的執行預算介於 300 至 1200 秒之間，平均壁鐘時間（Wall-clock Time）約 8 分鐘，每趟執行涉及超過 20 次工具呼叫（Tool Call），遠超傳統短程任務（Short-horizon Task）的規模，旨在測試多步編排、從工具失敗中恢復，以及跨模態推理能力。

執行環境採用可復現的 Docker 容器（Docker Container），內部部署實際的命令列介面（CLI）智慧體框架（Agent Harness），包括 OpenClaw、Claude Code、Codex 與 Hermes Agent。關鍵設計在於這些框架連接的是真實工具（Real Tool），如 Shell（命令列殼層）、網頁瀏覽器（Web Browser）、檔案系統（Filesystem）、電子郵件客戶端（Email Client）與可擴充技能（Extensible Skill），而非模擬服務 API（Mock-service API）。這確保了評估是在開放世界執行環境（Open-world Runtime）中進行，能觀察到真實的副作用（Side Effect），而非僅在合成沙盒（Synthetic Sandbox）內驗證最終答案檢查（Final-answer Check）。

為嚴格隔離模型行為，所有前沿模型（Frontier Model）均透過統一的 OpenRouter 端點呼叫，並在同一智慧體框架（Agent Harness）內固定工具綱要（Tool Schemas）與系統提示（System Prompts）。更嚴謹的是，評分專用資產（Grading-only Assets）僅在智慧體程序結束後才進入容器，徹底杜絕執行期間的資訊洩漏（Leakage），確保觀察到的軌跡（Trajectory）與產出物層級稽核（Artifact-level Auditing）皆為模型真實行為。

評分機制採用混合式評分（Hybrid Grading），整合三種訊號：確定性規則檢查（Deterministic Rule-based Check）針對產出檔案進行比對；環境狀態稽核（Environment-state Auditing）檢查執行過程中的副作用（Side Effect）；LLM/VLM 評判模型（LLM/VLM Judge）則負責語意驗證（Semantic Verification），處理規則難以量化的語義正確性。這種設計同時涵蓋最終答案檢查（Final-answer Check）與軌跡（Trajectory）暨產出物層級稽核（Artifact-level Auditing），彌補了僅驗證最終輸出的傳統缺陷。

#### 實驗數據解讀

實驗涵蓋 19 個前沿模型（Frontier Model），包含 6 個專有模型與 13 個開源模型。整體結果顯示長程、原生執行環境（Native-runtime）的評估遠未飽和：在 OpenClaw 框架下，最強的 Claude Opus 4.7 僅達 62.2% 整體成功率，其餘所有模型皆低於 60%，分數橫跨 43 個百分點（19.3% 至 62.2%）。這項數據明確指出，當前 frontier models 在真實、長程、複合式真實工具使用（Compound Real-tool Use）情境下仍面臨巨大挑戰。

數據揭示三個關鍵現象。首先是多模態落差：純文字任務顯著優於多模態（Multimodal）流程。例如 GPT 5.4 在文字任務達 58.0%，但多模態任務僅 40.2%；Claude Opus 4.7 亦從 65.0% 降至 58.5%。這顯示視覺語言模型（VLM）在長程工具編排中的跨模態推理與狀態追蹤仍是明顯瓶頸。

其次是框架效應（Harness Effect）：單一模型在不同智慧體框架（Agent Harness）間的表現可差距高達 18 個百分點（如 MiMo V2 Pro 於 Claude Code 與 Hermes Agent 之間）。這強烈證明腳手架（Scaffold）、工具使用模式與軌跡（Trajectory）並非無關的實作細節，而是被評估系統不可分割的一部分；評估必須將框架與模型視為整體，而非孤立測試模型權重（Model Weights）本身。

第三是資源敏感度：表現隨時間預算與可用技能（Available Skills）而變動。這暗示現有模型在長程任務中的規劃與恢復能力仍高度依賴外部資源配置，而非穩定的內在推理能力。綜合而言，實驗結果支持「長程、原生執行環境（Native-runtime）的智慧體評估對當前前沿模型而言仍是遠未解決的任務」這一核心論點。

#### 與現有研究的比較

相較於既有基準測試（Benchmark），WildClawBench 同時滿足五項軸線：跨模態輸入（Cross-modal）、可稽核軌跡（Auditable Trajectory）、原生執行環境（Native Runtime）、雙語（Bilingual）覆蓋，以及可復現容器（Reproducible Container）搭配混合式驗證（Hybrid Verification）。如 Table 1 所示，過往研究往往只能在部分軸線上達標。

傳統基準如 SWE-bench 與 Terminal-Bench 雖具可執行檢查，但僅限文字且綁定單一表面（Single Surface）。AgentBench 與 τ-bench 同樣受限於單一模態（Single-modality）且僅部分可復現。WebArena 與 VisualWebArena 雖支援瀏覽器互動，但運行於受控沙盒而非原生執行環境（Native Runtime）。OSWorld 採用混合協定，卻僅部分支援原生執行環境。雙語（Bilingual）覆蓋在既有研究中更為罕見，僅 Claw-Eval 提供。

近期並行研究 Claw-Eval 透過腳本化模擬服務（Scripted Mock Services）驅動智慧體，僅具部分原生執行環境支援；ClawBench 雖為全原生，但僅部分支援跨模態且不可復現。WildClawBench 的獨特之處在於不犧牲任何軸線：它在開放世界執行環境（Open-world Runtime）中評估複合式真實工具使用（Compound Real-tool Use），同時保持雙語與多模態（Multimodal）覆蓋，並以 Docker 容器（Docker Container）確保可復現評估（Reproducible Evaluation）。

然而其限制亦明顯：60 道任務的規模相對有限，雖足以揭示能力落差，但對於涵蓋所有真實世界長程工作流程仍顯不足；此外，Docker 容器仍非完整作業系統，且目前僅針對四種 CLI 智慧體框架（CLI Agent Harness）進行驗證，對圖形使用者介面（GUI）為主的智慧體覆蓋不足。這些邊界意味著 WildClawBench 是「原生執行環境」評估的重要起點，而非終點。

#### 可重現性評估

本研究在可復現評估（Reproducible Evaluation）方面採取積極措施。作者已釋出任務規格、容器化工作空間、評分程式碼與智慧體框架（Agent Harness）設定檔，原始碼託管於 GitHub（https://github.com/internlm/WildClawBench）。所有模型透過 OpenRouter 統一端點存取，這雖然意味著專有模型權重（Model Weights）並未開放，但確保了不同實驗室能以相同協定呼叫模型，降低因 API 實作差異導致的變異。

Docker 容器（Docker Container）的採用消除了環境漂移（Environment Drift）問題，而「評分資產後載」的設計也防止了提示工程（Prompt Engineering）或資料汙染（Data Contamination）的疑慮。混合式評分（Hybrid Grading）中的確定性規則檢查（Deterministic Rule-based Check）與環境狀態稽核（Environment-state Auditing）均為可重複執行的程式化邏輯，進一步提升客觀性。

不過，由於部分前沿模型（Frontier Model）為專有 API，研究者若無法取得特定模型存取權限，仍難以完整復現全數 19 個模型的比較結果。此外，LLM/VLM 評判模型（LLM/VLM Judge）本身引入的隨機性與模型版本變動，可能對語意驗證（Semantic Verification）層面造成細微的復現差異，未來若能固定評判模型版本或採用多評判模型共識機制，將可進一步提升可重現性。

#### 未來研究方向

WildClawBench 的結果指出數個值得深入的研究方向。第一，智慧體框架（Agent Harness）與模型本身的共設計（Co-design）：既然切換框架可造成 18 個百分點的波動，未來需建立框架標準化協定，以區分模型能力與腳手架（Scaffold）貢獻，並發展出與模型能力最適配的工具編排策略。

第二，多模態（Multimodal）長程推理：原生多模態任務（Natively Multimodal Task）的低落表現顯示，視覺語言模型（VLM）在跨模態工具編排、視覺狀態追蹤與多模態記憶管理上仍需專屬架構創新，而非僅將影像視為額外輸入脈絡。

第三，動態與對抗性任務生成：目前 60 道靜態任務雖具可復現性，但長期而言需引入動態任務生成或對抗性環境變化，以避免模型過度擬合特定工作流程，並更真實地反映開放世界執行環境（Open-world Runtime）的不可預測性。

第四，副作用（Side Effect）與安全對齊（Safety Alignment）的細粒度稽核：現有環境狀態稽核（Environment-state Auditing）可進一步擴展至權限最小化、隱私外洩、不可逆操作與資源濫用等維度，建立更嚴謹的長程安全評估框架。

最後，時間預算與技能擴充的適應性研究：如何讓智慧體（Agent）在有限壁鐘時間（Wall-clock Time）與部分技能缺失下進行自我評估、策略調整與優先級排序，將是長程任務從實驗室走向實用化的關鍵。這些方向共同指向一個結論：長程、原生執行環境（Native-runtime）的智慧體評估不僅是測量工具，更是驅動下一代智慧體架構創新的核心基礎設施。

## 論文問答

**Q1：WildClawBench 旨在解決現有智慧體評估中的什麼核心問題？**
A：現有的智慧體基準測試大多依賴合成沙盒、短程任務、模擬服務 API 以及僅檢查最終答案的評分方式，導致評估結果無法真實反映智慧體在實際部署環境中的表現。WildClawBench 針對這個缺口，提出一套原生執行環境的長程評估套件，專門檢驗智慧體在真實命令列介面（CLI）框架中完成複雜工作的能力。這個基準測試不僅關注最終答案是否正確，更重視智慧體在執行過程中與底層執行環境互動的可靠性、可稽核性與安全性。

**Q2：現有的基準測試方法在哪些關鍵軸向上存在不足？**
A：根據論文分析，現有方法在四個反覆出現的軸向上覆蓋不均：它們通常使用合成沙盒而非開放世界執行環境、採用短程任務而非長時間跨度的多步驟流程、以少數模擬服務 API 取代複合式真實工具使用，並且僅進行最終答案檢查而缺乏對執行軌跡與產出物的稽核。這些限制使得評估只能確認最終答案的正確性，卻無法得知智慧體實際上如何操作執行環境來達成結果。因此，既有基準測試難以捕捉智慧體在真實世界中的多步驟協調、從工具失敗中恢復以及跨模態推理等關鍵能力。

**Q3：為什麼在原生執行環境中進行長程評估對智慧體發展至關重要？**
A：隨著大型語言模型與視覺語言模型越來越多地透過 CLI 框架實際部署，評估必須超越問答形式，檢驗智慧體在真實執行階段中的多步驟行動、狀態維護與適應能力。原生執行環境能夠呈現真實的工具呼叫、副作用與系統狀態變化，這些都是合成沙盒無法完整模擬的面向。唯有在這樣的環境中進行長程評估，才能確保智慧體在實際為使用者完成工作時，具備可靠、可稽核且安全的互動能力。

**Q4：WildClawBench 的核心設計包含哪些主要元件？**
A：WildClawBench 包含 60 個人工撰寫的雙語多模態任務，橫跨生產力流程、程式碼智慧、社交互動、搜尋與檢索、創意合成與安全對齊六大主題類別，每個任務平均需要約 8 分鐘的壁鐘時間與超過 20 次工具呼叫。所有任務都在可復現的 Docker 容器中執行，容器內託管實際部署用的 CLI 智慧體框架，並提供 Shell、網頁瀏覽器、檔案系統、電子郵件客戶端與可擴充技能等真實工具。評分採用混合式機制，結合確定性規則檢查、環境狀態副作用稽核，以及專門處理語意驗證的 LLM/VLM 評判模型。

**Q5：WildClawBench 相較於先前基準測試的關鍵創新為何？**
A：其關鍵創新在於同時結合了全多模態輸入、可稽核執行軌跡、原生執行環境、雙語任務、可復現容器與混合式驗證，而先前基準測試通常僅支援其中部分特性。此外，WildClawBench 允許在多個不同的 CLI 智慧體框架下進行評估，並透過統一的 OpenRouter 端點與固定的工具綱要來隔離模型行為，從而區分模型能力與框架本身的影響。這種設計讓研究者能夠同時檢視智慧體產出的最終答案、中間執行軌跡以及對環境造成的實際副作用。

**Q6：為什麼 WildClawBench 選擇使用 Docker 容器、多框架支援與雙語任務？**
A：Docker 容器確保了評估環境的安全、穩定與可復現，讓不同研究團隊能在一致的條件下重複實驗，同時隔離智慧體執行時可能產生的副作用。支援 OpenClaw、Claude Code、Codex 與 Hermes Agent 等多種框架，是因為論文認為智慧體的腳手架、工具使用方式、執行軌跡與產出物都是待評估系統的一部分，而非無關緊要的實作細節。雙語任務的設計則填補了現有基準測試在語言覆蓋率上的空白，使評估更能反映全球使用者的真實需求。

**Q7：實驗中評估了哪些模型與智慧體框架？**
A：實驗涵蓋了 19 個前沿模型，包含 6 個專有模型與 13 個開源模型，並透過 OpenClaw、Claude Code、Codex 與 Hermes Agent 等 CLI 智慧體框架進行測試。所有模型均透過統一的 OpenRouter 端點存取，以確保工具綱要與系統提示詞在相同框架內保持一致，從而有效隔離單一模型的行為差異。這樣的設計讓研究者能夠比較不同模型在相同框架下的表現，以及同一模型在不同框架下的分數變化。

**Q8：WildClawBench 的主要實驗結果揭示了什麼？**
A：在 OpenClaw 框架下，表現最佳的 Claude Opus 4.7 僅達到 62.2% 的整體成功率，其餘所有模型均低於 60%，分數分布橫跨 43 個百分點，顯示長程原生執行環境的評估對當前前沿模型而言仍遠未解決。此外，多模態工作流程的表現普遍落後於純文字任務，而僅僅切換智慧體框架就能讓單一模型的分數波動高達 18 個百分點。這些結果強調了評估必須同時考量模型本身、框架腳手架與執行軌跡，而非僅關注最終輸出。

**Q9：實驗中有哪些關於框架切換、模態與時間預算的敏感性發現？**
A：研究發現，同一模型在不同智慧體框架下的表現差異顯著，例如 MiMo V2 Pro 在 Claude Code 與 Hermes Agent 之間的分數差距可達 18 分，證明框架選擇是影響結果的關鍵變因。在模態方面，純文字任務的表現優於多模態工作流程，如 GPT 5.4 在文字任務達到 58.0%，而多模態僅有 40.2%，顯示跨模態推理與工具協調仍是重大挑戰。此外，效能也會隨著時間預算與可用技能的變化而改動，意味著長程任務的資源配置與工具擴充性直接影響智慧體的成功率。

**Q10：WildClawBench 的任務設計對應到哪些真實世界的應用場景？**
A：六大主題類別涵蓋了現代知識工作者日常面對的核心需求，包括自動化處理電子郵件與日程的生產力流程、進行軟體開發與除錯的程式碼智慧、在社交平台上的互動管理、跨網頁與檔案系統的資訊搜尋與檢索、結合圖像與文字內容的創意合成，以及確保行為符合規範的安全對齊。這些任務要求智慧體在 Shell、瀏覽器、檔案系統與郵件客戶端之間進行複合式操作，真實反映了企業與個人使用者期望智慧體代為執行的長程工作流。因此，通過 WildClawBench 的模型將更有機會在實際部署中處理開放世界裡的跨應用協調問題。

**Q11：這項研究對 CLI 智慧體產品的開發與部署有何實務啟示？**
A：研究結果明確指出，智慧體框架的選擇並非無關緊要的實作細節，而是會顯著影響模型表現的系統組成部分，因此產品團隊在設計 CLI 智慧體時必須同時優化模型能力與框架腳手架。由於多模態任務的表現明顯落後於純文字任務，開發者需要針對視覺輸入與跨模態工具鏈投入更多工程資源，以提升真實工作流中的使用者體驗。此外，混合式評分機制提示產品團隊應建立結合規則檢查、環境稽核與語意驗證的監控系統，才能在生產環境中確保智慧體行為的可信度與安全性。

**Q12：WildClawBench 對智慧體研究領域可能帶來什麼樣的深遠影響？**
A：WildClawBench 透過提供可復現的長程原生執行環境，為社群建立了一個更能反映真實部署條件的評估標準，有望引導未來研究從追求最終答案正確率轉向重視完整執行軌跡與環境互動品質。其雙語與多模態的任務設計也將激勵研究者開發更具包容性與跨模態能力的智慧體系統，而非僅限於英語或單一文本模態。長遠來看，這個基準測試有助於辨識當前前沿模型的具體瓶頸，從而推動工具使用、錯誤恢復與長期規劃等核心能力的下一波突破。

**Q13：這項研究存在哪些已知的限制？**
A：儘管 WildClawBench 提供了 60 個人工撰寫的任務，但相較於無限的開放世界情境，這樣的任務數量與覆蓋範圍仍然有限，可能無法窮盡所有真實世界的長程工作流程。此外，所有任務都在 Docker 容器中執行，雖然確保了安全性與可復現性，但這種受控環境與完全開放、動態變化的真實使用者系統之間仍存在差距。論文也指出，評分過程中使用的 LLM/VLM 評判模型雖然能處理語意驗證，但其本身的偏誤與不一致性可能為混合式評分帶來額外的變異數。

**Q14：從實驗結果中的低分與框架差異，可以推論出哪些失敗模式？**
A：最高分僅 62.2% 且多數模型低於 60% 的結果顯示，當前前沿模型在長程多步驟協調、從工具失敗中恢復以及跨模態推理方面仍存在系統性的弱點。框架切換可造成高達 18 分的波動，暗示智慧體在特定框架下可能過度依賴腳手架提供的提示結構或錯誤處理機制，而非具備穩健的通用推理能力。此外，多模態任務表現較差的現象指出，模型在整合視覺輸入與文字指令以操作真實工具時，容易出現理解偏差或執行鏈斷裂的問題。

**Q15：未來研究可以從哪些方向延伸 WildClawBench 的成果？**
A：未來研究可以擴充任務數量與領域覆蓋率，納入更多動態變化的真實服務與即時協作場景，以進一步縮小基準測試與開放世界之間的差距。另一個重要方向是開發更強大的自動化評判機制，降低對 LLM/VLM 評判模型的依賴，同時提升環境狀態稽核的細緻度與準確性。此外，針對框架本身的優化研究，例如設計能夠自適應不同模型特性並提供更佳錯誤恢復能力的通用智慧體腳手架，將是提升長程任務成功率的關鍵下一步。

## 實務應用指南

### 適用場景

1. **企業級智慧體上線前的原生執行環境驗收**：在實際導入 CLI 智慧體框架（如 Claude Code、OpenClaw）前，利用 Docker 容器化環境驗證智慧體在真實工具（Shell、網頁瀏覽器、電子郵件客戶端、檔案系統）上的長程任務完成率，避免僅以短程玩具任務或模擬服務 API 評估導致上線後失效。
2. **雙語多模態助理的端到端回歸測試**：針對需要同時處理中文與英文、且涉及圖片或文件輸入的生產力流程或創意合成類智慧體，建立可復現的評估管線，確保每次模型或框架更新後，多模態推理與跨語言指令遵循能力不會退化。
3. **跨框架模型選型與 harness 效能基線建立**：由於同一模型在不同智慧體框架下分數可能落差達 18 分，企業可運用 WildClawBench 的多 harness 相容設計，在 OpenClaw、Codex、Hermes Agent 等框架間建立公平比較基線，選出最適合自身工具鏈的模型與 scaffold 組合。
4. **長程任務的安全性與副作用稽核**：針對安全對齊與程式碼智慧類場景，透過環境狀態稽核機制檢查智慧體在 8 分鐘、20 次以上工具呼叫過程中是否產生非預期副作用（如誤刪檔案、未經授權的網路請求），補足僅檢查最終答案無法發現的風險。
5. **開源智慧體框架的持續整合（CI）評測管線**：將 60 項人工撰寫任務與混合式評分系統嵌入 CI/CD，在每次更新 tool schema、系統提示詞或可擴充技能時，自動觸發長程任務抽樣測試，防止框架層變更導致複合能力崩潰。

### 實作前置條件

- **資料**：雙語任務規格書（含中文與英文敘述）、多模態輸入素材（圖片、PDF、音訊等）、預期產出物範本、環境狀態基準快照（用於副作用比對）、以及各主題類別的評分規則與語意驗證標準。
- **運算**：支援 Docker 的 Linux 主機叢集（建議具備巢狀虛擬化能力）、每項任務預留 8–20 分鐘壁鐘時間與對應的 GPU/CPU 資源、前沿模型 API 配額（建議透過 OpenRouter 等統一端點管理以降低整合成本）。
- **技能**：熟悉 CLI 智慧體框架（OpenClaw、Claude Code、Codex、Hermes Agent）的設定與 tool schema 定義；具備 Docker 容器化、網路隔離與磁區掛載實作經驗；能開發 Python 自動化評分腳本（確定性規則檢查與環境狀態稽核）；並具備 LLM/VLM 評判模型的 prompt engineering 能力，以處理語意模糊地帶。

### 實作步驟建議

1. **容器化執行環境建置**：依據目標部署情境建立 Docker 映像檔，內嵌真實工具（Shell、網頁瀏覽器、檔案系統、電子郵件客戶端、可擴充技能），並確保環境可復現，排除模擬服務 API。
2. **任務設計與分類對齊**：參考六大主題類別（生產力流程、程式碼智慧、社交互動、搜尋與檢索、創意合成、安全對齊），人工撰寫雙語任務；每項任務需定義 300–1200 秒的時間預算，並預期執行 20 次以上的工具呼叫，以有效測試長程 orchestration 與容錯能力。
3. **統一模型接入與 harness 控制**：透過統一端點掛接所有待測前沿模型，在單一 harness 內固定 tool schema 與系統提示詞，避免框架差異干擾模型行為；若進行跨 harness 比較，則將 harness 視為獨立實驗變因。
4. **軌跡執行與隔離**：在容器內啟動智慧體程序，嚴格確保評分專用資產（正確答案、測試腳本、稽核規則）僅在智慧體程序結束後才進入容器，防止資料洩漏。
5. **混合式評分系統落地**：先以確定性規則檢查產出物（如檔案內容、程式碼輸出）；再以環境狀態稽核比對副作用（檔案變更、網路日誌、系統狀態差異）；最後對規則無法覆蓋的語意模糊處，啟用 LLM/VLM 評判模型進行語意驗證。
6. **跨維度分析與迭代**：比較不同 harness、時間預算、可擴充技能與模態（純文字 vs. 多模態）對同一模型的影響，將 scaffold、工具使用軌跡與產出物視為被評估系統的一部分進行聯合優化，而非僅微調模型權重。

### 潛在風險與注意事項

- **長程執行的非確定性**：真實工具涉及網路延遲與時間相依操作，可能導致多次執行結果不一致。建議記錄環境狀態快照、設定固定亂數種子（若適用），並為外部網路呼叫設計重試與快取機制。
- **評分資料洩漏**：若評分腳本或正確答案在執行期間誤入容器，智慧體可能透過檔案系統讀取而作弊。必須嚴格遵守「評分資產後載入」原則，並在容器內限制對掛載目錄的讀取權限。
- **成本與時間爆炸**：60 項任務 × 多模型 × 每項 8 分鐘以上的長程呼叫會產生高額 API 費用與運算開銷。建議先以單一主題類別或精簡子集進行試跑，確認評分鏈路通順後再擴展至全量。
- **Harness 差異陷阱**：論文顯示切換智慧體框架單獨可使同一模型分數變動高達 18 分。進行模型能力比較時，必須固定 harness；若宣稱某模型「最強」，需同時聲明是在哪個框架下測得。
- **LLM/VLM 評判模型偏差**：語意驗證環節可能受評判模型偏好影響。建議設計對抗性檢查（如交換候選答案順序）與多評委投票機制，並定期以人工複審校準評判標準。

### 與其他技術的整合建議

- **MLOps 追蹤平台**：將混合式評分的三軌數據（規則分數、環境狀態稽核報告、語意評分）寫入 Weights & Biases 或 MLflow，建立模型版本與 harness 配置之間的長期回歸曲線，便於快速定位能力退化點。
- **CI/CD 管線**：將 Docker 容器化評測整合進 GitHub Actions / GitLab CI，在每次智慧體框架、tool schema 或可擴充技能更新時，自動觸發長程任務抽樣測試，並將混合評分結果作為合併門檻。
- **現有 IDE 外掛**：若目標場景為程式碼智慧類智慧體，可將 OpenClaw 或 Claude Code harness 嵌入 VS Code / JetBrains 外掛，讓開發者在日常工作中直接貢獻真實失敗案例，持續擴充任務庫。
- **人類回饋閉環**：對 LLM/VLM 評判模型無法確定的邊界案例，導入人工標註平台（如 Label Studio）進行複審；將複審結果反向餵入確定性規則庫，逐步降低對語意驗證的依賴。
- **合成資料擴充**：搭配任務生成模型，以 WildClawBench 的 60 項人工任務為種子，自動產生結構相似但內容相異的壓力測試案例，擴大評測覆蓋率而不增加人工撰寫負擔。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從圖 1 與表 1 入手，先理解「合成沙盒 vs. 原生執行環境」「最終答案檢查 vs. 軌跡與產出物稽核」的核心差異，建立對長程智慧體評測的整體認知框架，無需一開始就深入 Docker 實作細節。
- **AI 工程師**：重點研讀 harness 整合、Docker 容器隔離機制與混合式評分的實作細節，特別注意「統一端點固定 tool schema」與「評分資產後載入」的防洩漏設計，這些是將論文方法落地到生產環境的關鍵工程實踐。
- **研究人員**：深入分析跨 harness、跨時間預算與跨模態的實驗設計，關注作者提出的「scaffold、工具使用與產出物皆為被評估系統的一部分」這一方法論主張，並思考如何將此評測哲學延伸至其他開放世界執行環境（如行動裝置或機器人平台）。
- **產品經理**：聚焦六大主題類別與壁鐘時間、工具呼叫次數等任務規格，評估哪些類別最接近您的使用者場景；同時留意「單一模型在不同 harness 下落差可達 18 分」的發現，這意味著產品選型時必須同時考慮模型能力與框架適配性，而非僅看模型排行榜。
