DialFork 的方法論核心在於將「程序性幻覺」（procedural hallucination）從既有的「事實性幻覺」（factual hallucination）框架中抽離出來，並建構一套可量化的評測體系。其方法可分為三個層次：形式化建模、資料集建構、以及評測指標設計。

**形式化模型（Formal Model）**

論文首先將對話代理的預期邏輯抽象為一個四元組 W = (S, A, δ, O)，其中 S 代表對話狀態集合（如步驟或階段）、A 代表代理可執行的動作集合、δ: S × U → S 為狀態轉移函數、O 為代理的最終目標。這種抽象刻意保持通用性，使其能涵蓋任務導向對話（TOD）、臨床問診、客戶支援、排程等不同應用場景。所謂「符合規範的對話」（conformant dialogue）即其輪次序列遵循 W 的對話。這個形式化框架的優勢在於不預設任何特定實作方式，無論底層是有限狀態機、神經對話策略、或是 LLM 隱式學習的流程，皆可套用。

**四種程序性幻覺類型**

論文將程序性幻覺分解為四種互補類型，每種對應 W 中不同元件的破壞：

1. **工作流程身分損壞（Workflow Identity Corruption, WIC）**：整個工作流程 W 被替換為另一個有效但錯誤的 W'。此類型模擬任務消歧失敗（task disambiguation failures）與提示注入（prompt injection）攻擊。

2. **步驟選擇策略損壞（Step Selection Policy Corruption, SSPC）**：保留 O 與 (S, A)，但狀態轉移函數 δ 被替換為損壞版本 δ'，導致重複、跳過、循環或隨機化步驟。

3. **目標替換（Goal Replacement, GR）**：保留 W 但將目標 O 替換，使代理偏離原始任務。

4. **目標衝突（Goal Conflict, CSC）**：保留 W 但部分覆寫 O，引入衝突目標使任務完成受阻。

這四種類型的設計具有正交性（orthogonality），能系統性地覆蓋程序性偏差的不同面向，且每一種都與事實正確性無關——個別發話可能完全真實，但整體對話流程已偏離預期。

**資料集建構：受控分岔法（Controlled Forking）**

DialFork 的建構採用「分岔」策略：對於一個符合規範的對話 D+，在受控的輪次位置 t_k 進行分岔，使用相同種子（seed）重播模擬以重現前綴，然後在分岔輪次前注入幻覺指令。這種設計產生兩個關鍵特性：

- **真實排序（ground-truth ordering）**：分岔位置越早，偏離程度越大，因此資料集天然帶有程序性偏差的連續性標註。
- **四種時間偏差深度（temporal deviation depths）**：透過控制分岔位置，產生不同程度的程序性偏差。

最終資料集包含 36,278 個對話，涵蓋 24 個任務、12 個領域，並由 30 位人類標註員驗證建構品質。整個生成流程以 MIT 授權釋出，且適用於任何具備工作流程標註的對話資料集。

**三層粒度的評測任務**

論文定義三個評測任務，對應程序性偏差的三種粒度：

1. **監控部署代理（Monitoring deployed agents）**：衡量一組對話與符合規範對話的整體偏差程度，適用於批次品質監控。
2. **程序性檢索（Procedural retrieval）**：衡量單一對話與符合規範對話的偏差程度，適用於個案診斷。
3. **即時防護機制（Real-time guardrails）**：判斷對話在何輪首次偏離軌道，適用於即時介入。

**對話流程感知指標：FlowKL 與 FlowScore**

前兩個任務需要比較對話的「展開方式」而非「內容」，因此論文提出兩個新指標：

- **FlowKL**：基於 KL 散度衡量兩個對話流程分佈之間的距離。
- **FlowScore**：在對話層級（dialogue level）比較程序性相似度。

關鍵設計理念是：語義相似度（semantic similarity）無法替代程序性相似度（procedural similarity）。即使兩個對話在語意上高度相似，若其輪次順序、結構或流程不同，仍應被視為程序性偏差。

#### 實驗數據解讀

**FlowScore 的表現**

實驗結果顯示，FlowScore 在七種編碼器（encoder）上均顯著優於所有基線方法。這項結果的意義在於：

1. **驗證程序性相似度的獨立性**：即使使用強大的語義編碼器，僅靠語義相似度仍無法捕捉程序性偏差，證明程序性相似度確實是語義相似度無法替代的維度。

2. **跨編碼器穩定性**：在七種不同編碼器上的一致優勢顯示，FlowScore 的改進並非依賴特定編碼器的特性，而是反映了程序性偏差本身的結構性特徵。

**資料集規模與多樣性**

36,278 個對話、24 個任務、12 個領域的規模，加上四種幻覺類型與四種時間偏差深度的交叉，產生了豐富的實驗空間。這種規模足以支援統計顯著性檢定，並使模型在面對不同領域與任務時的泛化能力得以評估。

**人類標註驗證**

30 位人類標註員的參與確保了資料集建構的品質。雖然具體的標註者間一致性（inter-annotator agreement）數值未在提供的文本中詳述，但標註員的規模與程序性幻覺的細粒度特性（需判斷流程而非內容）暗示標註任務具有相當挑戰性，這也凸顯了自動化指標的必要性。

**三個評測任務的互補性**

三個任務覆蓋了從批次監控到即時防護的完整應用光譜。監控任務關心整體偏差分布，檢索任務關心個案診斷，即時防護任務關心介入時機。這種設計使 DialFork 不僅是學術基準，也具有實際部署價值。

#### 與現有研究的比較

**與事實性幻覺研究的關係**

DialFork 明確將自身定位為事實性幻覺研究的補充而非替代。事實性幻覺研究（Maynez et al., 2020; Kryściński et al., 2020; Lin et al., 2022; Mallen et al., 2023）關心「說了什麼」是否正確，而 DialFork 關心「如何展開」是否正確。DiaHalu（Chen et al., 2024b）等多輪對話幻覺基準仍聚焦於內容真實性，對程序性偏差視而不見。

**與程序遵循研究的關係**

既有程序遵循研究（Chen et al., 2021; White et al., 2023; Ghazarian et al., 2025; Qiao et al., 2025）通常依賴標註的動作、意圖或槽位（slots），評估系統是否遵循預設步驟。DialFork 的差異在於：它評測的是「衡量程序偏差的方法」本身，且直接在原始對話文本（raw dialogue text）上運作，無需預先標註。這使得 DialFork 能評估 LLM 或人類產生的對話，適用範圍更廣。

**與對話相似度研究的關係**

傳統對話相似度方法（如 Reimers and Gurevych, 2019; Zhou et al., 2022）將所有輪次塌縮為單一向量並以餘弦相似度比較，完全丟棄輪次順序資訊。TaskDiff（Bhaumik et al., 2023）雖考慮程序性，但依賴標註的意圖與槽位。DialFork 的 FlowKL 與 FlowScore 則保留輪次順序結構，且不依賴標註，這是方法論上的重要突破。

**限制與不足**

儘管 DialFork 貢獻顯著，仍存在以下限制：

1. **領域覆蓋偏限**：雖然涵蓋 12 個領域，但這些領域可能仍偏向結構化任務，對開放式對話的適用性有待驗證。
2. **幻覺類型的完備性**：四種類型雖互補，但可能未涵蓋所有程序性偏差模式，例如時序錯亂（temporal disorder）或並行流程處理錯誤。
3. **即時防護任務的評測**：文本中未詳述即時防護任務的具體實驗結果與基線表現，這是實際部署的關鍵環節。
4. **人類標註的細節**：標註協議、標註者間一致性、標註品質的量化指標未在提供的文本中充分披露。

- 至少一份帶有工作流程標註（workflow annotation）的對話資料集，例如 MultiWOZ、SGD，或自建的客服日誌（含意圖/動作序列）。
- 領域專家定義的工作流程規格文件（states、actions、transitions、objective），這是生成 conformant dialogues 的基礎。
- 種子對話（seed dialogues）作為 forking 的起點；建議至少數百組以涵蓋不同任務路徑。

**運算資源**
- 多代理生成階段需要呼叫多個 LLM（建議使用 GPT-4 等級或開源替代如 Llama-3.1-70B），單次完整生成 36,278 組對話在 8×H100 上預估需 2–4 天。
- 評測階段使用 7 種編碼器（sentence-transformers、SimCSE 等）產生 embedding，單張 A100 即可處理；FlowKL/FlowScore 的計算為輕量級。

**技能門檻**
- 熟悉對話系統與 dialogue state tracking 的基本概念。
- 能撰寫 LLM prompt 來模擬四種幻覺類型（WIC、SSPC、GR、CSC）的注入指令。
- 具備基本的對話流程建模能力（狀態機或流程圖）。
- 建議至少有 1 位領域專家參與工作流程定義與標註驗證。

### 實作步驟建議

**階段一：工作流程形式化（1–2 週）**
1. 盤點目標代理的對話流程，產出 `W = (S, A, δ, O)` 規格。
2. 將既有對話日誌對應到 `W` 的狀態序列，篩選 conformant dialogues 作為種子。
3. 定義四種幻覺類型在該領域的具體實例（例如客服領域的 WIC = 將「帳號查詢」誤導至「申辦新門號」流程）。

**階段二：基準建構（2–3 週）**
1. 使用論文的 seed-controlled multi-agent pipeline，在每個種子對話的 4 個分岔深度（temporal deviation depths）注入幻覺指令。
2. 邀請 ≥30 位人類標註員驗證生成品質（建議沿用論文的 annotation tool）。
3. 釋出資料集時附上工作流程規格與生成 prompt，便於復現。

**階段三：指標部署（1 週）**
1. 實作 FlowKL 與 FlowScore，比較對話的「展開方式」而非內容。
2. 建立三個評測任務的 API：
   - **監控任務**：批次評估一組對話相對於 conformant set 的偏差。
   - **程序性檢索**：給定單一對話，回傳最相似的 conformant dialogue。
   - **即時防護**：逐輪判斷是否已偏離軌道。
3. 以論文的 7 種編碼器 baseline 作為 sanity check，確認你的實作在 FlowScore 上顯著優於純語義相似度。

**階段四：上線整合（2–4 週）**
1. 將監控任務排入 CI/CD pipeline，每次對話策略更新後自動跑過 DialFork。
2. 將即時防護串接至 production gateway，偏離時觸發告警或人工接管。
3. 持續收集真實對話，定期 retrain 或 recalibrate 流程模型。

### 潛在風險與注意事項

| 風險 | 緩解措施 |
|------|---------|
| **語義相似度 ≠ 程序性相似度**：用 BERT/Sentence-BERT cosine 會誤判 | 強制使用 FlowScore 作為主指標，語義相似度僅作輔助 |
| **工作流程定義過於僵硬**：真實對話常偏離規格但仍合理 | 在 conformant set 中保留少量「合理變體」，避免基準過度理想化 |
| **標註一致性低**：30 位標註員對「是否偏離」看法分歧 | 提供明確指引、計算 Krippendorff's α，剔除低一致性樣本 |
| **多代理生成成本高**：36K 對話 × 多輪 LLM 呼叫費用可觀 | 使用較小模型（如 Llama-3.1-8B）做初篩，僅對候選集用大模型精修 |
| **領域轉移性差**：在客服訓練的基準未必適用於醫療 | 每進入新領域需重新建構工作流程與種子對話，無法直接遷移 |
| **偏離偵測的延遲成本**：即時防護若過於敏感會干擾 UX | 設定分級告警（warning vs. block），並允許人工覆核 |
| **幻覺注入的可信度**：LLM 生成的「偏離對話」可能不夠自然 | 必須做人類驗證；論文中 30 人驗證是最低門檻，醫療等高風險領域建議擴大 |

### 與其他技術的整合建議

- **與 LLM 評測框架整合**：可作為 HELM、OpenCompass 等框架的「程序性」維度擴充，與事實性、安全性維度互補。
- **與 RAG 系統整合**：在 retrieval-augmented 對話中，FlowScore 可偵測代理是否在引用知識的同時偏離了對話流程（例如該確認訂單卻開始閒聊）。
- **與對話狀態追蹤（DST）整合**：將 `W` 的狀態序列與 DST 輸出對齊，可同時評估「狀態正確性」與「流程正確性」。
- **與 Agent 框架整合**：在 LangGraph、AutoGen 的節點間加入 FlowScore 檢查點，作為 multi-agent orchestration 的守門員。
- **與 A/B 測試平台整合**：將 FlowKL 作為實驗指標之一，與任務完成率、CSAT 並列觀察。
- **與日誌分析平台整合**：將 production 對話定期送入監控任務，累積程序性偏差的時序趨勢儀表板。

### 給不同背景讀者的閱讀建議

**初學者**：先讀第 1 節的動機段落，理解「為什麼程序性幻覺與事實性幻覺不同」這個核心論點即可；可跳過形式化模型與指標細節，重點掌握四種幻覺類型的具體例子（Table 1），建立直覺。

**AI 工程師**：聚焦第 5、6 節的評測任務定義與 FlowKL/FlowScore 實作；建議直接 clone 官方 repo 跑通三個任務的 baseline，理解為何 7 種編碼器在語義相似度上都輸給 FlowScore，這對設計自家評測 pipeline 很有啟發。

**研究者**：第 3 節的工作流程模型與第 4 節的 controlled forking 方法論是主要貢獻，值得仔細推敲；可思考如何將此框架擴充至多模態對話、跨語言場景，或與 process mining 領域結合。

**產品經理**：重點看摘要、第 1 節的 use case 列舉，以及本文的「即時防護」與「監控部署代理」兩個任務；理解 DialFork 能回答的產品問題是「我們的代理有沒有按照設計流程走」，而非「代理說的話對不對」——這對建立正確的品質指標至關重要。
