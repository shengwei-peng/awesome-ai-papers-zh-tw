## ⚡ TL;DR

通用智能體跨模態產出能力零碎，擴充模態昂貴且難以協調多工具與中間資產。
Omni-IO技能駕馭層整合階層技能、標準介面、依賴編排與資產註冊，讓宿主智能體隨插即用全模態化。
在UniM-90上，兩種宿主模型輸入支援率達100%，語義品質與結構分數亦顯著提升。

## 摘要翻譯

通用智能體（general-purpose agents）雖能在長時間跨度下進行規劃、推理與行動，但其產出能力仍分散於文字、圖像、音訊、影片、文件、3D 資產與程式碼。將基礎模型（foundation model）擴充至更多模態會使能力成長受制於昂貴的模型更新；而整合模態專家模型（modality specialists）與工具，仍未能解決程序、依賴關係、中間資產（intermediate assets）與跨輪次修訂（cross-turn revisions）應如何協調。我們提出 Omni-IO 技能（Omni-IO Skills），一個隨插即用（plug-and-play）的智能體駕馭層（Agent Harness），透過階層式技能（hierarchical Skills）、標準化多模態執行介面（standardized multimodal execution interface）、依賴感知編排（dependency-aware orchestration），以及持久化資產註冊表（persistent Asset Registry），使既有智能體全原生化（omni-native）。多資產工作流程以宣告式執行圖（Declare Execution Graphs）表示，可並行排程獨立操作，並將成功輸出註冊，供下游任務與跨輪次修訂在可替換的執行後端（execution backends）上重複使用。其 27 項技能涵蓋 38 項代表性任務，橫跨七種產物模態（artifact modalities）與四個能力家族（capability families）：理解（understanding）、生成（generation）、推理（reasoning）與檢索（retrieval）。在 UniM-90 上，此駕馭層將 GPT-5.6 Sol 與 Claude Sonnet 5 的輸入支援率從 40.00% 與 38.89% 提升至 100%，同時將相對語義–品質耦合分數（Semantic–Quality Coupled Score）分別從 26.99 提升至 74.94、從 27.82 提升至 77.78；嚴格結構分數（Strict Structure Score）則達到 100.00 與 99.78。這些結果確立了駕馭層層級的能力組合（capability composition）作為建構廣泛且可演化的 Omni 系統的實用途徑，且無需改變宿主智能體（host agent）的推理核心。

### 核心貢獻（3～5點）
- 提出 Omni-IO 技能（Omni-IO Skills）框架，以隨插即用（plug-and-play）的智能體駕馭層（Agent Harness）使既有通用智能體無需修改推理核心即可全原生化（omni-native），涵蓋七種產物模態（artifact modalities）。
- 設計階層式技能（hierarchical Skills）架構，結合原子技能（Atomic Skills）、專家技能（Expert Skills）與情境技能（Scenario Skills），並透過標準化多模態執行介面（standardized multimodal execution interface）統一銜接異質執行後端（execution backends）。
- 以宣告式執行圖（Declare Execution Graphs）實現依賴感知編排（dependency-aware orchestration），可並行排程獨立操作，並透過持久化資產註冊表（persistent Asset Registry）支援中間資產（intermediate assets）的下游與跨輪次重複利用。
- 在 UniM-90 基準上驗證，將 GPT-5.6 Sol 與 Claude Sonnet 5 的輸入支援率提升至 100%，並顯著改善語義–品質耦合分數（Semantic–Quality Coupled Score）與嚴格結構分數（Strict Structure Score），確立駕馭層層級能力組合（capability composition）的實用性。

### 適合對象
本論文適合多模態智能體（multimodal agents）、基礎模型（foundation model）系統設計、工具使用與編排（tool use & orchestration），以及跨模態生成與推理研究者閱讀；對於希望在不重新訓練或修改核心推理模組的前提下，擴展通用智能體至多種輸入輸出模態的工程師與產品團隊亦具高度參考價值。

## 深度分析

#### 方法論解析

Omni-IO Skills 的核心設計目標，是讓既有的通用智能體（host agent）在不更動其推理核心（reasoning core）的前提下，具備「全原生（omni-native）」的多模態輸入輸出能力。為此，作者提出了一個可隨插即用（plug-and-play）的 Agent Harness（智能體駕馭層），其方法論可從四個層次理解：階層式技能（hierarchical Skills）、標準化多模態執行介面（standardized multimodal execution interface）、依賴感知編排（dependency-aware orchestration），以及持久化資產註冊表（persistent Asset Registry）。

**1. 階層式技能（Hierarchical Skills）**

Skill 是整個框架封裝程序性知識（procedural knowledge）的基本單位，分為三個層級：

- **Atomic Skills（原子技能）**：最基礎、可複用的能力單元，例如圖像理解、音訊轉錄、影片剪輯、3D 格式轉換、程式碼執行等。這些技能對應到單一後端能力，強調可被組合與重複使用。
- **Expert Skills（專家技能）**：針對具體產出物（deliverables）的完整製作程序，例如「製作一張資訊圖表」、「生成一段配音旁白」、「建立一份投影片」。這類技能通常由多個 Atomic Skills 組合而成，並內建領域最佳實踐。
- **Scenario Skills（情境技能）**：涵蓋多個相關產出的應用層任務，例如「製作一門線上課程」或「建立一支產品解說影片」。這類技能對應真實世界中的複雜工作流程，會協調多個 Expert Skills 與 Atomic Skills，並管理跨模態的事實一致性、風格一致性與時間一致性。

目前實作包含 19 個 Atomic Skills、2 個 Expert Skills 與 6 個 Scenario Skills，共 27 個 Skills，涵蓋 38 個代表性任務，橫跨文字、圖像、音訊、影片、文件、3D 資產與程式碼七種產物模態（artifact modalities），以及理解（understanding）、生成（generation）、推理（reasoning）、檢索（retrieval）四個能力家族（capability families）。

**2. 標準化多模態執行介面（Standardized Multimodal Execution Interface）**

為了讓宿主智能體無需了解每個後端的細節，Omni-IO Skills 提供統一的操作與資料交換介面。無論底層是基礎模型（foundation model）、模態專家模型（modality specialists）或媒體引擎，Skill 都以一致的輸入輸出格式被呼叫。這使得執行後端（execution backends）可以被替換，應用層則保持穩定。這種設計與 Model Context Protocol（MCP）[36] 的精神一致，但進一步將多模態資產流動與任務語義封裝進 Skill 層級，而非僅是工具呼叫層級。

**3. 依賴感知編排（Dependency-Aware Orchestration）**

多資產工作流程被表示為 **Declare Execution Graphs（宣告式執行圖）**。這是一種以圖形結構宣告任務與資料依賴關係的執行表示法，具備以下特性：

- **並行排程**：獨立的操作可以同時執行，提升效率。
- **依賴追蹤**：明確標示控制依賴與資料依賴，確保下游步驟只在前置資產就緒後才執行。
- **局部失敗隔離**：單一 Skill 或後端失敗不會導致整個工作流程崩潰，便於錯誤 containment 與恢復。
- **跨輪次修訂（cross-turn revisions）**：由於執行圖與資產狀態被持久化，使用者可以在後續對話回合中修改需求，系統能基於既有資產繼續迭代，而非從頭開始。

**4. 持久化資產註冊表（Persistent Asset Registry）**

Asset Registry 是支撐資產長期保存與追蹤的基底。所有中間資產（intermediate assets）與最終產出都會被註冊，並記錄其來源、版本、依賴關係與後設資料。這帶來幾個關鍵優勢：

- 資產不依賴特定檔案路徑或服務，提升可移植性。
- 支援 downstream reuse（下游重複使用）與 cross-turn reuse（跨輪次重複使用）。
- 讓宿主智能體在規劃時能引用已註冊資產，維持語義與資產連續性（semantic and asset continuity）。

整體架構採用分層設計，將任務知識（task knowledge）、工具存取（tool access）、供應商綁定（provider binding）與資產狀態（artifact state）分離。這種分離讓 Omni-IO Skills 能夠隨著模型、工具與應用需求持續演進，而不需要重新訓練宿主智能體。

#### 實驗數據解讀

作者在 **UniM-90** 上進行評估，這是 UniM 基準 [1] 的一個受控 90 實例子集，涵蓋多種模態交錯的複雜任務。實驗使用兩個不同的宿主智能體：**GPT-5.6 Sol** 與 **Claude Sonnet 5**，以驗證 harness 的跨模型通用性。

**1. 輸入支援率（Input-Support Rates）**

在未載入 Omni-IO Skills 前，GPT-5.6 Sol 與 Claude Sonnet 5 的輸入支援率分別僅為 40.00% 與 38.89%，顯示基礎智能體對於包含多種模態輸入的任務支援非常有限。載入 harness 後，兩者的輸入支援率均提升至 **100%**。這個結果直接證明了 Agent Harness 能夠有效彌補宿主智能體在模態覆蓋上的缺口，而不需要修改模型本身。

**2. 語義–品質耦合分數（Semantic–Quality Coupled Score, SQCS）**

SQCS 是衡量輸出語義正確性與感知品質綜合表現的指標。整體來看：

- GPT-5.6 Sol：SQCS 從 26.99 提升至 **74.94**，進步 **47.95 個百分點**。
- Claude Sonnet 5：SQCS 從 27.82 提升至 **77.78**，進步 **49.96 個百分點**。

值得注意的是，這裡的基線分數（26.99 與 27.82）是只在基礎智能體「能夠處理的狹窄子集」上測得的平均分數 [14, 15]。也就是說，基線不僅覆蓋率低，連已支援任務的品質也僅約 27 分。而載入 harness 後的 74.94 與 77.78 是在「全部 90 個實例」上的平均分數，這意味著系統不僅擴展了覆蓋範圍，還在更困難、更多樣的任務上維持了更高的綜合品質。

**3. 結構分數（Structure Scores）**

- **Strict Structure Score（嚴格結構分數）**：GPT-5.6 Sol 達到 **100.00**，Claude Sonnet 5 達到 **99.78**。這表示輸出在格式、欄位、順序等結構層面幾乎完全符合要求。
- **Lenient Structure Score（寬鬆結構分數）**：兩者均達到 **100.00**。

高結構分數反映出 Declare Execution Graphs 與 Skill 的標準化介面對於輸出格式控制非常有效。對於需要產生多資產、多欄位回應的 Omni 任務而言，結構正確性是使用者能否實際使用結果的關鍵。

**4. 綜合意涵**

實驗結果支持了作者的核心主張：**harness-level capability composition（駕馭層級的能力組合）** 是一條實際可行的路徑，可以在不改變宿主智能體推理核心的情況下，建構出廣泛且可演進的全模態系統。數據也顯示，這種提升具有跨模型一致性：無論是 GPT-5.6 Sol 還是 Claude Sonnet 5，都能從同一套 harness 中獲益，這強化了 Omni-IO Skills 作為通用中間層的價值。

#### 與現有研究的比較

**1. 相較於 Omni Foundation Models**

近期的 Omni 基礎模型 [2, 3, 4, 5, 6, 27, 28] 透過統一自迴歸建模（autoregressive modeling）或混合離散–連續設計（hybrid discrete–continuous designs），將感知、推理與生成整合到單一模型中。這類方法的優勢在於介面統一、支援交錯內容，但面臨幾個結構性挑戰：

- 每新增一種模態，都需要重新設計表徵、編解碼器（codecs）、解碼器（decoders）與對齊階段（alignment stages），成本高昂。
- 模型能力與訓練資料、架構與更新週期緊密耦合，難以快速跟進不斷進步的專業模型與媒體引擎。

Omni-IO Skills 採取互補路線：它將基礎模型、專家模型與媒體引擎視為可替換的執行後端（execution backends），把統一層次放在任務執行與資產流動上。這讓應用能夠獨立於特定模型堆疊而演進，降低了擴展新模態的門檻。

**2. 相較於 Agent Harnesses 與 Skills**

傳統 Agent Harness [32, 33, 34] 提供行動迴圈（action loop）、工具存取、上下文與狀態管理、執行控制、驗證與恢復等機制。ReAct [35] 透過推理–行動–觀察的交錯迴圈讓模型能從環境回饋修正計畫；MCP [36] 則標準化了外部工具與資源的暴露方式。然而，這些機制主要定義了智能體的「行動表面」，對於多模態工作流程中的資產傳遞、依賴協調與跨輪次修訂支援有限。

Agent Skills [11, 12, 13] 將可重複使用的程序性知識封裝起來，供推論時使用，但本身並未解決多模態產出之間的協調問題。Omni-IO Skills 結合了 Agent Harness 的執行基板與 Agent Skills 的程序性知識，並進一步加入：

- 多層級 Skill 組織（Atomic / Expert / Scenario）。
- 標準化多模態執行介面。
- 依賴感知編排與 Declare Execution Graphs。
- 持久化 Asset Registry。

這使得它不僅能「呼叫工具」，還能「協調複雜的多資產生產流程」。

**3. 相較於多模態智能體協調系統**

MM-ReAct [37] 與近期的 Omni 智能體 [10, 38] 展示了語言模型可以委派給視覺專家或模態專家模型（modality specialists），並透過主智能體（master-agent）或主動感知（active perception）協調影像、音訊與影片。這些系統通常評估於證據蒐集、問答與跨模態推理任務。

Omni-IO Skills 的差異在於：

- 它不僅協調「理解」任務，也涵蓋「生成」、「推理」與「檢索」四個能力家族。
- 它強調產出物（artifacts）之間的語義連續性與資產連續性，適用於教育、研究、行銷、創意製作與軟體工程等真實生產場景。
- 透過 Asset Registry 與 Declare Execution Graphs，它支援跨輪次修訂與資產版本追蹤，這是單次委派系統較難提供的。

**4. 限制與待釐清之處**

儘管實驗結果強勁，仍有幾點需要注意：

- **評估規模**：UniM-90 僅有 90 個實例，雖然具代表性，但對於涵蓋七種模態與四種能力家族的系統而言，樣本量仍屬中等。未來需要更大規模、更開放的評估來驗證泛化性。
- **後端品質依賴**：Omni-IO Skills 的表現高度依賴底層執行後端的品質。若某個 Atomic Skill 對應的專家模型或媒體引擎表現不佳，整體產出品質也會受限。
- **規劃複雜度**：雖然 harness 提供了執行圖與資產管理，但宿主智能體仍需負責高階規劃。對於極長期、高度動態的任務，如何讓宿主智能體有效選擇與組合 Skills，仍是挑戰。
- **安全性與對齊**：多模態生成涉及版權、深度偽造、偏見與不當內容等風險，論文對這些面向的討論較少。

#### 可重現性評估

根據目前提供的論文內容，**可重現性資訊相當有限**。具體而言：

- **原始碼（source code）**：文中未提及 Omni-IO Skills 的實作是否開源，也未提供程式碼儲存庫連結。
- **資料集（datasets）**：UniM-90 是 UniM [1] 的子集，但論文未說明該子集的選取標準、分割方式或是否公開釋出。
- **模型權重（model weights）**：由於 Omni-IO Skills 是一個 harness 層，本身不一定需要自有模型權重，但其運作依賴 GPT-5.6 Sol、Claude Sonnet 5 等商業模型，以及可能的專家模型與媒體引擎。這些後端的可取得性與 API 穩定性會直接影響重現。
- **評估指標實作**：SQCS、Strict Structure Score、Lenient Structure Score 等指標的計算方式與評分標準在提供的片段中未詳細說明，這對第三方複現構成障礙。

整體而言，這項研究在方法論上描述詳細，但若要達成學術與工程上的可重現性，作者需要補充：

1. 開源 harness 框架與 Skill 實作。
2. 釋出 UniM-90 子集的選取邏輯與測試樣本。
3. 提供評估指標的程式碼與人工評分準則。
4. 列出所有執行後端的版本、API 與設定，以便他人重建相同環境。

#### 未來研究方向

基於 Omni-IO Skills 的設計與實驗結果，以下幾個方向值得進一步探索：

**1. 動態技能發現與組合**

目前的 27 個 Skills 是預先設計的。未來可研究如何讓宿主智能體在執行時動態發現、組合甚至生成新的 Skills，以應對未見過的任務。這可能結合程式合成（program synthesis）、檢索增強生成（retrieval-augmented generation）與元學習（meta-learning）。

**2. 即時與串流多模態互動**

現有系統主要處理離散的工作流程。未來可擴展至串流（streaming）、全雙工（full-duplex）互動 [29, 30, 31]，例如即時語音對話中同步生成圖像或影片，並維持資產一致性。

**3. 自動化驗證與品質保證**

多模態產出的驗證比文字更困難。未來可發展自動化的品質檢查 Skill，例如視覺一致性檢測、音訊–影片同步驗證、程式碼執行測試，並將這些驗證回饋整合進 Declare Execution Graphs 的迭代迴圈中。

**4. 安全、對齊與可追溯性**

隨著生成能力擴展到影像、音訊、影片與 3D，內容安全、版權歸屬與來源追溯變得更加重要。未來可在 Asset Registry 中內建 provenance 追蹤、浮水印與使用政策，並發展多模態安全對齊機制。

**5. 與 Model Context Protocol（MCP）等標準的整合**

Omni-IO Skills 可進一步與 MCP [36] 等開放工具協議整合，讓 Skill 能夠更容易地接入第三方工具與資料源，並促進社群貢獻新的 Atomic Skills。

**6. 更大規模與開放評估**

需要建立更大規模、涵蓋更多真實應用場景的評估基準，並推動開源實作與標準化評估流程，讓不同研究團隊能夠公平比較各種 Omni 系統的優劣。

**7. 個人化與長期記憶**

結合使用者偏好、歷史產出與長期記憶，讓 Scenario Skills 能夠隨著時間學習使用者的風格與需求，進一步提升跨輪次修訂的效率與品質。

## 論文問答

**Q1：Omni-IO Skills 旨在解決什麼問題？**
A：Omni-IO Skills 旨在解決通用智能體在處理跨模態產出時能力碎片化的問題。現實世界的任務很少侷限於單一模態，例如製作線上課程需要同時處理講座錄音、參考文件、投影片、插圖、旁白與解說影片等多種產物。然而，現有通用智能體的端到端生產能力主要集中在軟體與知識工作上，對於音訊、影片、3D、專業文件與協調式媒體套件仍依賴外部能力與顯式編排。因此，本文提出一個可隨插即用的全模態智能體駕馭層，讓既有智能體無需重新訓練就能原生處理七種產物模態。

**Q2：現有的兩種主流途徑——擴展基礎模型與組裝專家模型——各自存在什麼缺陷？**
A：擴展基礎模型的方式會將能力增長綁定在昂貴的模型更新上，每新增一種模態都需要調和不同的表徵、目標函數與保真度要求，並伴隨新的資料、編解碼器、解碼器與對齊階段。另一方面，單純組裝各領域的專家模型與工具雖然能利用持續進步的專業能力，卻無法解決程序、依賴關係、中間資產與跨輪次修訂之間的協調問題。這兩種途徑都缺乏一個能將分散的模型、工具與程序轉化為可選擇、可組合、可執行且可追溯能力的系統層。

**Q3：為什麼全原生（omni-native）能力對真實世界智能體至關重要？**
A：真實任務的產物並非彼此獨立，而是共享事實、風格、時間軸與製作限制，因此有效的 Omni 系統必須能接收並產出交錯組合的多模態內容，同時在整個工作流程中保持語義與資產連續性。如果智能體只能處理部分模態，就必須由使用者或開發者手動銜接中間產出，導致工作流程斷裂、效率低落且容易出錯。全原生能力讓智能體能夠在單一對話脈絡中規劃、執行與迭代多模態任務，從而更接近真正可用於複雜生產場景的通用助手。

**Q4：Omni-IO Skills 的核心方法與架構是什麼？**
A：Omni-IO Skills 是一個隨插即用的全模態智能體駕馭層，它在不改變宿主智能體推理核心的前提下，提供程序性知識、標準化執行介面與持久化資產基底。其核心由三層能力組成：原子技能（Atomic Skills）封裝可複用的基礎能力單元，專家技能（Expert Skills）針對具體產出物提供製作程序，情境技能（Scenario Skills）則涵蓋多個相關產出的應用層任務。底層架構進一步分離任務知識、工具存取、供應商綁定與資產狀態，並透過依賴感知編排與持久化資產註冊表協調任務組合、資產轉移與後續修訂。

**Q5：相較於先前的智能體駕馭層與多模態協調系統，Omni-IO Skills 的關鍵創新為何？**
A：過往的多模態代理系統多聚焦於將語言模型連接到視覺或音訊專家進行問答或證據收集，而 Omni-IO Skills 則進一步將「能力組合」提升到應用級工作流程的層次，涵蓋理解、生成、推理與檢索四大能力家族。其創新在於結合了多粒度程序性知識、異質執行後端、依賴感知編排與持久化資產狀態於單一可擴展架構中，使模型、工具與媒體引擎成為可替換的執行後端。這種設計讓應用能力可以隨著模型與工具的演進而獨立演化，而不被綁定在特定基礎模型或檔案路徑上。

**Q6：階層式技能與宣告式執行圖的設計選擇背後有何考量？**
A：階層式技能的設計是為了在不同抽象層次上封裝可重複使用的程序性知識：原子技能提供細粒度能力，專家技能組合原子技能以完成具體產出，情境技能則進一步組織多個專家技能來處理複雜應用場景。宣告式執行圖（Declare Execution Graphs）則讓多資產工作流程能夠以圖形方式表達資料與控制依賴，從而並行排程獨立操作、註冊成功輸出供下游與跨輪次重複使用。這種分離關注點的設計讓工作流程不依賴特定執行後端或檔案路徑，同時提升了執行效率與可維護性。

**Q7：實驗採用什麼評估基準，衡量哪些面向？**
A：實驗在 UniM-90 上進行，這是 UniM 基準中一個受控的 90 實例子集，專門用於評估 Omni 系統在多模態輸入支援、語義品質與結構正確性方面的表現。評估指標包括輸入支援率（input-support rate）、語義–品質耦合分數（Semantic–Quality Coupled Score, SQCS）、嚴格結構分數（Strict Structure Score）與寬鬆結構分數（Lenient Structure Score）。這些指標共同衡量系統能否接受多模態輸入、產出高品質且語義一致的回應，並符合預期的輸出結構。

**Q8：Omni-IO Skills 在 UniM-90 上取得了哪些關鍵量化結果？**
A：在輸入支援率方面，Omni-IO Skills 將 GPT-5.6 Sol 從 40.00% 提升至 100%，將 Claude Sonnet 5 從 38.89% 提升至 100%，顯示其能彌補宿主智能體原本無法處理的大量模態缺口。語義–品質耦合分數（SQCS）方面，GPT-5.6 Sol 從 26.99 提升至 74.94，Claude Sonnet 5 從 27.82 提升至 77.78，分別進步 47.95 與 49.96 個百分點。嚴格結構分數分別達到 100.00 與 99.78，寬鬆結構分數則雙雙達到 100.00，顯示輸出的結構正確性極高。

**Q9：這些實驗結果對於駕馭層的跨宿主泛化能力有何意涵？**
A：實驗同時在 GPT-5.6 Sol 與 Claude Sonnet 5 兩個截然不同的宿主智能體上取得一致且顯著的提升，證明 Omni-IO Skills 的能力增益並非依賴特定模型的內在特性，而是來自於駕馭層本身對多模態工作流程的協調能力。即使在原本支援率較低的子集上，加載駕馭層後的絕對 SQCS（74.94 與 77.78）也超過基線智能體僅在其狹窄支援子集上測得的 67.49 與 71.53。這顯示一個共享的駕馭層能夠在不同宿主間彌補模態與工作流程缺口，同時在所有 90 個實例上維持強勁的回應品質。

**Q10：Omni-IO Skills 在哪些具體實務場景中具有應用價值？**
A：Omni-IO Skills 特別適合需要協調多種產物模態的複雜生產任務，例如製作線上課程時需要分析講座錄音與參考文件、設計視覺內容、生成投影片與旁白，最後組合成解說影片。在行銷與創意製作領域，它可用於根據品牌文案同時產生廣告圖像、影片片段與社群貼文，並確保風格與訊息一致。在軟體工程與研究中，它則能協助從論文圖表與程式碼庫中提取資訊、生成視覺化資產與技術文件，形成端到端的知識工作流程。

**Q11：部署這類全模態駕馭層時需要考慮哪些產品與工程議題？**
A：產品層面需要考慮如何管理多種執行後端的成本、延遲與可靠性，因為不同模態的專家模型與媒體引擎可能具有截然不同的計算需求與服務等級協議。工程上必須建立穩健的資產版本控制、錯誤隔離與重試機制，以確保某個後端失敗時不會拖垮整個工作流程，並能跨輪次恢復先前產出。此外，由於涉及音訊、影片與文件等敏感資料，還需審慎處理資料隱私、存取權限與合規性，並提供清晰的執行追蹤以便除錯與稽核。

**Q12：這項工作可能對 Omni 智能體領域帶來什麼更廣泛的影響？**
A：Omni-IO Skills 提出了一條與基礎模型擴展互補的路徑：將全模態能力統一在任務執行與資產流動的系統層，而非全部塞入單一模型，這有助於減緩模型規模與訓練成本持續膨脹的壓力。它示範了如何透過「能力組合」讓專業模型與媒體引擎持續演進的同時，仍能被通用智能體協調成連貫的應用級工作流程。這種駕馭層導向的設計哲學可能促進更開放、模組化且可持續演化的 Omni 生態系統，讓不同供應商的最佳能力更容易被整合與重複利用。

**Q13：這篇論文承認或暗示了哪些限制？**
A：論文主要聚焦於駕馭層的架構與能力組合，對於個別執行後端的內部品質、延遲與成本特性並未深入探討，這些因素在實際大規模部署時可能成為瓶頸。此外，雖然 UniM-90 提供了結構化的評估，但其 90 個實例仍屬於受控子集，未必能完全代表真實世界中高度開放、多輪迭代的複雜任務。駕馭層本身也依賴宿主智能體的規劃與推理能力，若宿主在長期規劃或意圖理解上出錯，後續的技能選擇與編排也可能連帶受到影響。

**Q14：在實際運作中可能出現哪些失敗案例？**
A：當某個專家後端產出品質不佳或格式不符時，可能導致下游技能無法正確解析或組合，進而影響最終產出的語義一致性。如果宣告式執行圖對任務依賴關係的建模不夠精確，可能出現並行操作競爭資源、順序錯誤或遺漏必要前序步驟的情況。此外，跨輪次修訂時若資產註冊表未能正確追蹤版本與語義對應關係，使用者可能會拿到過時或與前後文不一致的產出，破壞工作流程的連續性。

**Q15：未來可以朝哪些方向延伸這項研究？**
A：未來可以進一步擴充技能庫，納入更多新興模態與領域專用工具，例如互動式 3D 場景、虛擬實境資產或科學模擬資料，並讓技能能夠自動學習或從示範中生成。另一個方向是強化駕馭層的自我驗證與修復能力，使其能在執行過程中偵測後端失敗、自動選擇替代方案或請求人類確認。最後，也可以探索更緊密的模型–駕馭層協同設計，例如讓宿主智能體在規劃階段就能更有效地利用執行圖與資產註冊表的結構化資訊，進一步提升長期規劃與跨輪次推理的品質。

## 實務應用指南

### 適用場景

1. **線上課程多媒體套件製作**  
   輸入講師錄音、參考文件與課程大綱，透過情境技能自動產出逐字稿、摘要、投影片、插圖、旁白音訊與解說影片，並在資產註冊表中保留風格與時間軸一致性，方便後續回合修改單一素材後自動級聯更新。

2. **行銷內容跨模態改編**  
   將一份產品白皮書改寫為部落格文章、資訊圖表、社群短影片腳本、配音與 3D 產品展示，利用宣告式執行圖並行處理獨立生成任務，再依賴感知編排確保各產出引用相同數據與品牌語調。

3. **研究文獻多模態分析與報告**  
   上傳 PDF 論文、實驗數據圖表與補充音訊訪談，透過理解、檢索與推理技能家族萃取方法、結果與限制，自動生成結構化綜述、對照表與可視化圖表，並支援跨輪次追問與修訂。

4. **軟體原型全端產出**  
   從自然語言需求出發，協調程式碼生成、UI 設計圖、互動原型影片與技術文件，讓不同執行後端（程式碼智能體、設計模型、文件引擎）在同一個駕馭層中協作，產出可交付的開發套件。

5. **客服與知識庫多模態問答**  
   整合產品手冊、教學影片、常見問題與 3D 拆解圖，讓使用者以文字或語音提問，系統根據檢索技能定位相關資產，並以文字摘要、標註圖片或語音回覆，且所有中間資產可供下一輪對話重複使用。

### 實作前置條件

- **宿主智能體**：需具備長程規劃、指令遵循與工具呼叫能力的通用智能體，例如 GPT-5.6 Sol、Claude Sonnet 5、Codex 或 Claude Code。
- **執行後端**：根據目標模態準備可替換的後端，包括文字模型、圖像生成／理解模型、語音合成與辨識模型、影片編輯引擎、文件解析器、3D 渲染工具與程式碼執行環境。
- **資產儲存與註冊機制**：需具備持久化資產註冊表，能跨輪次保存中間資產、記錄版本與依賴關係，並提供穩定的資產識別碼而非僅依賴本地檔案路徑。
- **技能庫**：載入對應的原子技能、專家技能與情境技能；初次部署建議至少涵蓋目標任務涉及的全部七種產物模態與四大能力家族。
- **運算與網路**：需支援並行執行多個獨立技能節點，並具備足夠頻寬與儲存空間傳輸大型媒體資產（影片、3D 模型、高解析度圖像）。

### 實作步驟建議

1. **任務拆解與技能對照**  
   將目標產品流程拆解為可重複使用的程序性知識單元，對照 Omni-IO 技能庫中的原子技能、專家技能與情境技能，確認是否有缺漏需自行擴充。

2. **設計宣告式執行圖**  
   以圖形描述各技能的輸入、輸出與依賴關係，標示可並行執行的獨立節點與必須依序執行的控制依賴，確保中間資產能正確傳遞給下游技能。

3. **綁定執行後端**  
   為每個技能選擇實際的模型或工具後端，透過標準化多模態執行介面進行封裝，使後端可在不影響上層技能與宿主智能體的情況下替換。

4. **建立持久化資產註冊表**  
   設定資產註冊表，統一管理原始輸入、中間產出與最終交付物，記錄每筆資產的來源技能、版本、依賴與後設資料，支援跨輪次修訂與回溯。

5. **整合宿主智能體**  
   將 Omni-IO 技能作為隨插即用的智能體駕馭層掛載到既有宿主智能體，不改變其推理核心，僅擴充其動作空間與可觀察的資產狀態。

6. **端到端測試與迭代**  
   從簡單的單一模態任務開始驗證，再逐步擴展至多資產工作流程；使用 UniM-90 或自訂評估集檢視輸入支援率、語義–品質耦合分數與結構分數，並根據失敗案例調整技能與執行圖。

### 潛在風險與注意事項

- **依賴鏈失敗傳播**  
  若上游技能產出格式或語義不符預期，下游技能可能連帶出錯。建議在每個節點加入輕量驗證與重試機制，並讓資產註冊表標記失敗資產，避免錯誤結果被重複使用。

- **後端能力不一致**  
  不同執行後端對輸入輸出格式、解析度、編碼或長度限制各異，需在標準化介面中統一轉換與截斷規則，防止格式錯誤導致整個工作流程中斷。

- **資產版本與一致性管理**  
  跨輪次修訂時，若未妥善追蹤版本，可能出現新舊資產混用、風格或事實不一致。應為每筆資產賦予唯一識別碼，並在執行圖中明確引用版本。

- **並行執行成本與延遲**  
  雖然宣告式執行圖可並行處理獨立節點，但多媒體生成與影片渲染成本高昂。建議設定成本預算、快取常用中間資產，並在必要時降級為較輕量的後端。

- **安全與版權**  
  生成式後端可能產生受版權保護風格或敏感內容，應在輸出前加入內容審查與來源標註，並對使用者上傳的私人文件與錄音實施存取控制。

### 與其他技術的整合建議

- **模型上下文協定（MCP）與工具市場**  
  可將 Omni-IO 技能的執行後端視為 MCP 工具伺服器，讓宿主智能體透過統一協定發現與呼叫技能，降低與現有工具生態的整合門檻。

- **現有程式碼智能體（Codex、Claude Code）**  
  對於軟體工程情境，可將程式碼相關技能直接對接到這些智能體的工作空間，讓它們負責程式碼推理，而 Omni-IO 駕馭層負責協調文件、影片與 3D 資產。

- **企業內容管理與知識庫**  
  將持久化資產註冊表與企業 DAM、Wiki 或向量資料庫串接，使中間產出與最終交付物能自動歸檔、檢索與版本控制。

- **自動化流程與 CI/CD**  
  對於重複性內容生產，可將情境技能包裝為 API 端點或排程任務，並透過 CI/CD 管線觸發執行圖，實現批次產出與品質閘道。

- **多模態基礎模型**  
  當新的全模態基礎模型釋出時，可直接將其作為一個執行後端替換或增補到現有技能中，無需重寫上層應用邏輯。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從「適用場景」與「實作步驟建議」入手，理解 Omni-IO 技能如何讓一個通用智能體變得「全原生」。遇到技術名詞時，可對照文末詞彙表，並先聚焦單一模態的簡單任務，例如讓智能體生成一張圖並保存到資產註冊表，再逐步擴展到多資產流程。

**AI 工程師**：重點閱讀「實作前置條件」「實作步驟建議」與「與其他技術的整合建議」，深入理解宣告式執行圖、依賴感知編排與標準化多模態執行介面的設計。實作時請優先處理資產註冊表的版本管理與後端容錯，這是系統能否穩定擴展的關鍵。

**研究人員**：建議聚焦論文的方法論貢獻，包括智能體駕馭層的形式化、階層式技能設計、以及與全模態基礎模型的互補關係。可進一步探討在更長程、更開放的工作流程中，如何量化駕馭層對語義一致性、結構完整性與跨輪次修訂能力的影響。

**產品經理**：請優先閱讀「適用場景」與「潛在風險與注意事項」，評估哪些使用者旅程最適合先用 Omni-IO 技能落地。特別留意成本、延遲、內容安全與版本一致性，這些將直接影響使用者體驗與商業可行性；整合建議則有助於規劃與現有產品堆疊的銜接路徑。
