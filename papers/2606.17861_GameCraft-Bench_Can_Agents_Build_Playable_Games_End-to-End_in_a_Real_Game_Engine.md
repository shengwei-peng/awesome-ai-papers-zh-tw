## 摘要翻譯

遊戲生成（game generation）是編碼智慧體（coding agents）的一項新興應用，要求模型將自然語言規格（natural-language specifications）轉化為可遊玩的互動系統（playable interactive systems）。與傳統編碼任務不同，遊戲生成於遊戲引擎（game engine）中進行，腳本（scripts）、場景（scenes）、資產（assets）、渲染（rendering）與執行階段互動（runtime interactions）須共同產生連貫的遊戲玩法。我們將端對端遊戲生成（end-to-end game generation）形式化為以下問題：在目標環境（target environment）中產出完整遊戲成品（complete game artifact），使其透過可觀察的玩家–遊戲互動（observable player-game interaction）來實現規格。我們主張，評估此設定需要三項要件（desiderata）：引擎扎根（Engine Grounding）、成品完整性（Artifact Completeness），以及互動驗證（Interactive Verification）。我們提出一個以互動為基礎的評估框架（interaction-grounded evaluation framework），透過重播示範（replayed demonstrations）與評分標準引導的多模態評判（rubric-guided multimodal judging）來評估可執行的遊戲玩法（executable gameplay）。我們將此框架實例化為 GameCraft-Bench，一個涵蓋 15 個遊戲家族（game families）、共 140 項 Godot 任務的基準。對前沿編碼智慧體（frontier coding agents）的評估顯示，端對端遊戲生成（end-to-end game generation）仍然極具挑戰性：表現最佳的智慧體僅達 41.46%，且大多數智慧體得分低於 40%。進一步分析顯示，儘管智慧體經常可實作出可辨識的遊戲機制（mechanics），但它們難以產出內容充足、具備功能性視覺回饋（visual feedback）與連貫呈現（coherent presentation）的完整遊戲。展示（demos）、程式碼與資料請參見 https://tongxuluo.github.io/gamecraft-bench-website。

### 核心貢獻（3～5點）
- 將端對端遊戲生成形式化為「在目標環境中產出完整遊戲成品，並透過可觀察的玩家–遊戲互動實現自然語言規格」的問題。
- 提出三項評估要件——引擎扎根、成品完整性與互動驗證，作為評測端對端遊戲生成的基準契約。
- 設計以互動為基礎的評估框架，結合重播示範與評分標準引導的多模態評判，以評估可執行的遊戲玩法。
- 建構 GameCraft-Bench 基準，包含 140 項 Godot 任務並涵蓋 15 個遊戲家族，提供大規模的真實引擎端對端遊戲生成評測環境。
- 透過前沿編碼智慧體評估揭示當前瓶頸：最佳智慧體僅達 41.46%，且多數低於 40%；分析指出智慧體雖能實作遊戲機制，但難以產出內容充足、視覺回饋功能正常且呈現連貫的完整遊戲。

### 適合對象
對 AI 代理、自動化程式生成、遊戲開發與互動系統評估有興趣的研究者與工程師，特別是關注大型語言模型在複雜創意工程任務（如端對端遊戲生成）上表現的學術與產業界人士。

## 深度分析

#### 方法論解析

本文將端對端遊戲生成（end-to-end game generation）形式化為一個映射問題：給定自然語言規格（natural-language specifications）**s** 與目標環境（target environment）**E**，編碼智慧體（coding agents）必須產出完整遊戲成品（complete game artifact）**G**，使得 **G** 可在 **E** 中啟動，並透過可觀察的玩家–遊戲互動（observable player-game interaction）實現 **s** 所描述的設計意圖。為了嚴謹評估此映射，作者提出三項要件（desiderata），構成基準契約（benchmark contract）：

1. **Engine Grounding（引擎扎根）**：開發必須在真實遊戲引擎（real game engine）中進行。GameCraft-Bench 選用 Godot，要求智慧體使用引擎原生的文件（native documentation）、資產（assets）與執行階段（runtime），避免淪為玩具開發環境（toy development settings）或網頁腳本。
2. **Artifact Completeness（成品完整性）**：智慧體交付的必須是可啟動的完整專案（launchable complete project），涵蓋腳本（scripts）、場景（scenes）、資產（assets）、渲染（rendering）設定等所有必要成品，而非局部教學導向的編輯（localized tutorial-derived edits）或單一操作（single operation）。
3. **Interactive Verification（互動驗證）**：評估必須透過直接互動（direct interaction）完成，包含玩家輸入（player inputs）與遊戲過程重播（gameplay replays）。本文提出的以互動為基礎的評估框架（interaction-grounded evaluation framework）結合重播示範（replay demonstrations）與評分標準引導的多模態評判（rubric-guided multimodal judging），將評估焦點從傳統的程式碼正確性（code correctness）轉移至互動系統正確性（interactive system correctness）。

在此框架下，GameCraft-Bench 實例化為包含 140 項任務、橫跨 15 個遊戲家族（game families）的基準。評判維度涵蓋遊戲機制（mechanics）、內容深度（content depth）、功能性視覺回饋（functional visual feedback）與呈現品質（presentation quality），確保評估的是可執行的遊戲玩法（executable gameplay）而非僅靜態程式碼或視覺雛形。

#### 實驗數據解讀

作者評測了多個前沿編碼智慧體（frontier coding agents），結果顯示端對端遊戲生成仍是高度未解的挑戰。最強的智慧體整體得分僅 **41.46%**，且多數受測智慧體分數低於 40%。這些低分並非源自單一能力缺失，而是跨維度的複合性失敗：

- **核心機制（core mechanics）**：智慧體雖常能實作出可辨識的機制（recognizable mechanics），但無法保證其在完整專案中穩定運作。
- **內容深度（content depth）**：生成的遊戲往往缺乏足夠的關卡、敵人、道具或賽道，導致遊玩體驗貧乏。
- **功能性視覺回饋（functional visual feedback）**：玩家操作後，遊戲畫面未能正確反映狀態變化，例如碰撞無動畫、得分無 HUD 更新。
- **連貫的呈現（coherent presentation）**：美術風格不一致、介面破碎或渲染異常，使成品缺乏可遊玩性所需的視覺連貫性。

此外，不同遊戲家族（game families）間的表現差異劇烈，顯示現有智慧體的泛化能力脆弱。整體而言，實驗數據揭示：當前系統能產出「類遊戲軟體片段」（fragments of game-like software），但距離「將自然語言規格可靠地轉化為在真實引擎中可遊玩且視覺連貫的成品」仍有極大落差。

#### 與現有研究的比較

本文透過三項要件精確定位現有基準的不足（見 Table 1）：

- **OpenGame-Bench**：滿足成品完整性（Artifact Completeness），要求生成完整網頁遊戲（web games），但缺乏引擎扎根（非真實引擎專案，real-engine projects）與互動驗證（無透過遊玩重播的評估）。
- **GameDevBench**：滿足引擎扎根（使用 Godot），但僅研究局部教學導向的編輯（localized tutorial-derived edits）與確定性測試（deterministic tests），不具備成品完整性（聚焦單一操作，single operation）亦不進行互動驗證。
- **WebGameBench**（與本文同期）：評估完整的網頁遊戲並透過瀏覽器互動（browser interaction）進行某種程度的互動驗證，但其開發仍 outside real game-engine development，且依賴評估端探索（evaluation-side exploration），未滿足引擎扎根。

GameCraft-Bench 的貢獻在於首次同時滿足三項要件，將評估從「程式碼片段正確性」推進到「完整互動系統正確性」。相較於既有工作，本文強調的是**端對端**的基準契約：從引擎內開發、完整專案交付，到以重播為依據的行為驗證。

**局限性**方面，目前框架僅以 Godot 為目標環境，雖然 Godot 為開源真實引擎，但其對於 Unity、Unreal Engine 等其他產業主流引擎的泛化性仍待驗證。此外，140 項任務的規模相較於大型程式碼生成基準仍屬精緻型（focused benchmark），且任務範例多集中於 2D 類型（如 2D platformer、top-down racing），對於 3D 或需要複雜物理、網路連線的遊戲類型覆蓋有限。最後，評分標準引導的多模態評判可能涉及視覺語言模型（vision-language models）作為評審，其一致性（consistency）與可擴展性（scalability）在基準大規模擴充時可能成為瓶頸。

#### 可重現性評估

本文在摘要與內文皆明確提供專案網站（https://tongxuluo.github.io/gamecraft-bench-website），並聲明公開示範（demos）、程式碼（code）與資料（data）。由於 GameCraft-Bench 屬於評測基準而非模型訓練論文，其可重現性主要取決於以下要素：

- **開源引擎**：Godot 為開源遊戲引擎，任何研究者均可免費取得與論文完全一致的目標環境（target environment）。
- **任務公開**：140 項自然語言規格（natural-language specifications）與對應的遊戲家族分類若完整釋出，可確保不同團隊在相同輸入下測試智慧體。
- **評估協定**：重播示範（replay demonstrations）與評分標準（rubrics）的程式實作若隨程式碼釋出，將大幅提昇評估結果的可比性。

潛在風險在於：若多模態評判依賴商業視覺語言模型（proprietary vision-language models）或特定版本的大型語言模型（LLMs），則 API 行為的漂移（API drift）可能導致長期可重現性下降。此外，論文未提及是否釋出受測前沿編碼智慧體的確切提示詞（prompts）與工具鏈配置，這部分細節將影響社群復現 41.46% 等關鍵數據的難易度。

#### 未來研究方向

基於 GameCraft-Bench 所揭示的瓶頸，未來研究可從以下方向展開：

1. **長期規劃與專案協調（Long-horizon planning）**：現有智慧體在跨檔案、跨場景的長期一致性上表現不佳。未來需發展能同時規劃腳本、場景與資產，並維持設計意圖連貫性的智慧體架構。
2. **內容與視覺的深度生成**：除了核心機制（mechanics），智慧體必須提升內容深度（content depth）與功能性視覺回饋（functional visual feedback）的生成能力，例如自動產生足夠的關卡變化、連貫的 UI/HUD 與狀態轉換動畫。
3. **引擎泛化與基準擴展**：將 Engine Grounding 擴展至 Unity、Unreal Engine 等商業引擎，驗證方法是否通用。同時增加 3D 遊戲、物理模擬與多人連線等高複雜度任務，推升基準天花板。
4. **自動化互動驗證**：發展更自動化、確定性且低成本的 Interactive Verification 管線，減少對多模態評判中主觀或昂貴模型的依賴，同時保持對遊戲玩法（gameplay）語義的敏感度。
5. **執行回饋迭代（Iterative execution feedback）**：強化智慧體利用執行階段除錯（runtime debugging）與遊戲過程重播（gameplay replays）進行自我修正的能力，縮短「生成–執行–驗證」迴路，以逼近可靠端對端遊戲生成的目標。

## 論文問答

**Q1：什麼是端對端遊戲生成，它與傳統程式碼生成任務有何根本不同？**
A：端對端遊戲生成是指將自然語言規格轉化為可在目標環境中執行、並能透過可觀察的玩家–遊戲互動來實現設計意圖的完整遊戲成品。與傳統程式碼生成僅需確保程式碼正確性不同，遊戲生成必須同時協調腳本、場景、資產、渲染與執行階段互動，才能產生連貫的遊戲體驗。因此，其成功標準不僅是編譯通過，更在於建構、啟動、遊玩與觀察整個互動系統的行為是否正確。

**Q2：現有的遊戲生成基準為何無法滿足端對端評估的需求？**
A：現有基準各自只滿足部分要件，未能同時涵蓋引擎扎根、成品完整性與互動驗證這三項必要條件。舉例來說，OpenGame-Bench 針對網頁遊戲而非真實引擎專案，且缺乏透過遊戲過程進行的互動驗證；GameDevBench 雖扎根於 Godot 引擎，但僅研究局部教學導向的編輯與確定性測試，而非完整遊戲建構。就連與本文同期、透過瀏覽器互動評估的 WebGameBench，也因未在專用遊戲引擎中開發而缺乏引擎扎根，無法評估引擎原生的開發與執行環境。

**Q3：為何互動驗證對於遊戲生成評估至關重要，單靠靜態程式碼檢查有何不足？**
A：遊戲是一種可遊玩的互動系統，玩家必須在其中行動並期待世界給予回應，因此成功的關鍵在於成品能否被建構、啟動、遊玩並以互動系統的形式被觀察。單靠靜態程式碼檢查只能確認語法或局部邏輯的正確性，卻無法發現執行階段的遊戲玩法失敗、視覺回饋缺失或呈現不連貫等問題。唯有透過實際的玩家輸入與遊戲過程重播，才能驗證遊戲機制、內容深度與整體體驗是否真正符合規格。

**Q4：GameCraft-Bench 提出的「以互動為基礎的評估框架」核心內容是什麼？**
A：此框架透過重播示範與評分標準引導的多模態評判，來驗證可執行的遊戲玩法，而非僅檢視原始碼或靜態截圖。具體而言，系統會重播預設的玩家操作序列，並依據量規評估遊戲機制、內容深度、功能性的視覺回饋以及整體呈現品質。這種方法將評估焦點從傳統的程式碼正確性轉移至互動系統正確性，確保生成的遊戲不只是能跑，而是真的能玩且體驗連貫。

**Q5：本文提出的三項要件如何共同構成端對端遊戲生成的「基準契約」？**
A：引擎扎根確保智慧體在真實遊戲引擎中使用原生文件與資產進行開發，成品完整性要求產出可啟動的完整遊戲專案而非局部片段，互動驗證則透過直接互動與重播來確認行為正確性。這三項要件依序覆蓋了「在哪裡開發」「交付什麼成品」以及「如何評判結果」的完整成功路徑。若缺少任何一項，評估就會塌陷為玩具開發環境、部分成品或靜態評估，無法真正檢驗從規格到可玩體驗的端到端能力。

**Q6：作者為何選擇 Godot 作為目標引擎，並設計 140 項橫跨 15 個遊戲家族的任務？**
A：Godot 是一款開源的真實遊戲引擎，具備完整的腳本、場景、資產與渲染管線，能夠滿足引擎扎根的要件，讓智慧體在貼近實際開發的環境中作業。140 項任務與 15 個遊戲家族的設計則是為了涵蓋多樣化的遊戲玩法需求，包括不同的機制、進度系統與視覺呈現要求。這樣的規模與多樣性確保基準能夠嚴格檢驗智慧體是否具備跨類型、從自然語言規格生成完整可玩遊戲的泛化能力。

**Q7：GameCraft-Bench 與現有基準在量化與質化層面上有何具體差異？**
A：如表 1 所示，現有基準最多僅能滿足三項要件中的兩項，而 GameCraft-Bench 是同時具備引擎扎根、成品完整性與互動驗證的完整基準。在質化層面上，OpenGame-Bench 與 WebGameBench 聚焦於網頁遊戲，無法評估引擎原生專案的複雜度；GameDevBench 則僅限於單一操作層級的編輯。相較之下，GameCraft-Bench 首次系統性地評估智慧體在真實引擎中從零建構完整專案，並透過可執行的遊戲玩法進行互動驗證。

**Q8：在前沿編碼智慧體的評估中，最主要的量化結果與整體表現為何？**
A：實驗顯示端對端遊戲生成仍是極具挑戰性的任務，即使是最強大的智慧體也僅達到 41.46% 的整體分數，且大多數受測智慧體的得分都低於 40%。這樣的低分並非由單一能力不足所導致，而是反映在遊戲機制、內容深度、功能性視覺與藝術呈現等多個維度上的綜合性失敗。此外，不同遊戲家族之間的表現差異極大，顯示現有系統在處理特定類型遊戲規格時的穩定性與泛化能力仍嚴重不足。

**Q9：診斷分析揭示了智慧體哪些具體的失敗模式？**
A：分析發現智慧體雖然經常能實作出可辨識的遊戲機制，但卻難以交付具備足夠內容、功能完善視覺回饋與連貫呈現的完整遊戲。許多情況下，智慧體產出的只是遊戲軟體的片段或雛形，而非能從頭到尾依規格遊玩的成品。這些失敗橫跨核心機制實作、內容豐富度、視覺功能回饋與整體美術呈現，顯示將自然語言規格一路轉化為真實引擎中可遊玩且視覺協調的成品，仍是目前系統難以可靠完成的任務。

**Q10：端對端遊戲生成智慧體在哪些實際應用場景中最具影響力？**
A：這類智慧體最顯著的應用在於快速原型開發，能讓設計師與開發者將創意意圖迅速轉化為可互動的遊戲雛形，大幅縮短前期驗證週期。在獨立遊戲開發與教育領域，它也能降低技術門檻，使非程式背景的使用者透過自然語言描述即可生成可玩的互動系統。此外，在需要大量生成互動內容的場景，如智慧型個人助理或自動化遊戲測試中，端對端生成能力同樣具有改變產業流程的潛力。

**Q11：若要將此類智慧體部署於實際的遊戲引擎生產環境，需考量哪些工程與設計因素？**
A：首先必須確保智慧體能持續接收並理解執行階段的回饋訊號，因為遊戲開發極度依賴迭代式的建置、執行與除錯循環。其次，智慧體需要有效管理引擎原生的資產管線與場景結構，並保證產出的專案在任何情況下都能完整啟動，而非僅產出片段程式碼。最後，視覺回饋的連貫性與呈現品質必須納入自動化檢查，因為生產環境要求的不只是功能正確，更包含使用者體驗與美術風格的一致性。

**Q12：此基準對編碼智慧體與生成式 AI 領域的研究方向帶來什麼樣的轉變？**
A：GameCraft-Bench 將研究焦點從傳統的程式碼正確性轉移到互動系統正確性，為複雜多模態創意任務設立了新的評估標準。它證明了僅能在靜態程式碼任務上表現優異的智慧體，在面對需要協調多種媒介與即時互動的遊戲生成時仍顯得力不從心。這促使學界與業界重新審視智慧體的長期規劃、多模態推理與環境互動能力，並推動未來研究朝真正能產出可執行、可遊玩且體驗連貫的互動系統邁進。

**Q13：GameCraft-Bench 框架目前存在哪些已知的限制？**
A：目前框架主要聚焦於 Godot 單一引擎，雖然已能反映真實引擎開發的複雜度，但尚未涵蓋 Unreal Engine 或 Unity 等其他主流商業引擎的生態系與資產管線差異。此外，140 項任務雖橫跨 15 個遊戲家族，但仍無法窮盡所有遊戲類型與複雜的敘事結構，評估範圍仍有擴展空間。最後，目前的互動驗證依賴重播示範與評分標準引導的評判，可能無法捕捉所有邊緣案例，且量規設計在某種程度上仍涉及主觀判斷。

**Q14：哪些類型的遊戲或規格對現有智慧體而言特別困難？**
A：當遊戲規格要求多個子系統——例如機制、進度、視覺回饋與美術呈現——必須協同運作以產生連貫體驗時，智慧體的失敗率會顯著上升。特別是需要豐富內容深度、複雜功能性視覺回饋以及一致藝術風格的遊戲家族，往往讓智慧體難以交出完整成品。此外，若規格涉及細緻的執行階段互動邏輯或跨場景的狀態管理，智慧體更容易產出僅具片段機制、卻無法從頭到尾順暢遊玩的半成品。

**Q15：這項工作指出了哪些未來的研究方向？**
A：未來研究應優先提升智慧體在視覺回饋與整體呈現品質上的迭代能力，使其能根據執行階段觀察自動修正美術與介面問題。同時，將基準擴展至其他主流商業引擎，並納入更廣泛的遊戲類型與敘事結構，將有助於更全面地評估通用遊戲生成能力。此外，發展更先進的多模態推理技術、強化智慧體對長期規劃與跨檔案依賴的理解，以及設計更自動化且細緻的互動驗證方法，都是邁向可靠端對端遊戲生成的關鍵途徑。

## 實務應用指南

### 適用場景

1. **自動化遊戲原型開發**：將設計文件快速轉譯為可執行的 Godot 專案，驗證核心玩法循環與機制可行性，縮短前期預製作（pre-production）週期。
2. **程式教育與互動教材生成**：讓學習者以自然語言描述遊戲概念，由編碼智慧體產出可遊玩的教學範例，強化「程式碼→互動回饋」的學習連結。
3. **遊戲引擎自動化測試與品質驗證**：建立以互動為基礎的評估框架，作為遊戲專案的回歸測試與可玩性閘道，確保每次程式碼變更後仍能產出完整且可啟動的成品。
4. **編碼智慧體能力評估與選型**：利用 GameCraft-Bench 的 140 項任務與評分標準，系統性比較不同前沿模型在端對端專案開發的表現，作為模型採購或微調的依據。
5. **UGC 平台與遊戲化行銷工具**：為使用者生成內容平台提供「文字轉遊戲」功能，降低創作門檻；或讓品牌方快速生成簡易互動網頁遊戲，但須認知現階段仍需人工後製。

### 實作前置條件

- **資料**：結構化的自然語言遊戲規格書（涵蓋機制、內容深度、視覺回饋與連貫呈現要求）、Godot 專案模板與原生文件、用於評分標準引導的多模態評判參考資料（含遊玩影片與對應分數標籤）。
- **運算**：可執行 Godot 引擎的容器化或虛擬機環境（支援無頭模式執行與畫面擷取）、執行前沿編碼智慧體的 GPU 運算資源、儲存重播示範與評估日誌的儲存空間。
- **技能**：熟悉 Godot／GDScript 與遊戲引擎專案結構、具備提示工程與智慧體工作流程設計經驗、能建置多模態評分管道（結合程式碼靜態檢查、遊玩重播與視覺語言模型）。

### 實作步驟建議

1. **引擎扎根與環境建置**：部署標準化 Godot 開發與執行階段環境，確保智慧體能在真實引擎中操作檔案、執行腳本並取得執行回饋，避免淪為玩具開發環境。
2. **規格書與評分標準設計**：將遊戲需求拆解為可驗證的互動項目（核心機制、內容深度、功能視覺回饋、連貫呈現），並為每項任務制定量規（rubric），作為後續自動評分的依據。
3. **智慧體開發介面整合**：賦予智慧體讀寫專案檔案、查詢引擎文件、執行建置與除錯工具的能力，使其能依據執行回饋迭代修正，實現端對端開發閉環。
4. **互動驗證管道建置**：開發重播示範系統，透過預設或自動化玩家輸入錄製遊玩過程，並擷取執行階段互動的畫面與狀態日誌，取代僅仰賴靜態程式碼檢查的評估方式。
5. **多模態評判自動化**：結合規則式檢查（專案能否啟動、有無必要資產）與多模態模型（分析遊玩影片與截圖是否符合評分標準），產出量化分數與診斷報告。
6. **診斷回饋與迭代**：針對智慧體常見失敗模式（如成品不完整、視覺回饋缺失、內容深度不足）建立分類標籤，將評估結果回饋至提示（prompt）或工作流程以提升通過率。

### 潛在風險與注意事項

- **成品不完整風險**：智慧體可能僅產出片段腳本或遺失場景資產，導致專案無法啟動。建議在評估流程中加入「啟動檢查」閘道，未通過者直接標記失敗，避免後續無效評分。
- **視覺回饋與機制脫鉤**：模型常實現可辨識的機制，但缺乏功能視覺回饋（例如碰撞無動畫、得分無 UI 更新）。評分標準應獨立檢驗「可玩性」與「可觀察性」，防止僅有後台邏輯正確卻無法被玩家感知。
- **評估成本膨脹**：重播示範與多模態評判涉及大量畫面擷取與模型推論，需預留充足運算預算。可採分層篩選策略：先以靜態檢查與規則式測試淘汰明顯失敗案例，僅對通過者執行完整互動驗證。
- **引擎版本與環境漂移**：Godot 版本差異可能導致建置失敗或 API 行為改變。建議鎖定特定引擎版本，並將開發環境容器化以確保可複現性。
- **過度樂觀的產品預期**：目前最強智慧體僅達 41.46% 通過率，端對端遊戲生成仍屬高難度任務。實務上應先聚焦特定遊戲家族或簡化規格，而非直接開放全品類生成。

### 與其他技術的整合建議

- **檢索增強生成（RAG）**：將 Godot 官方文件與 API 參考資料接入智慧體，強化引擎扎根能力，降低因 API 誤用或路徑錯誤導致的建置失敗。
- **版本控制系統（Git）**：讓智慧體在 Git 倉儲上操作，保留每次迭代的 diff，便於追蹤修正軌跡、進行失敗分析，並支援多人協作時的衝突管理。
- **現有資產生成工具**：串接 AI 美術或音效生成服務，補足編碼智慧體在資產創作上的弱點，提升成品完整性與連貫呈現，減少場景空蕩或預設材質濫用的問題。
- **CI/CD 管線**：將互動驗證框架嵌入持續整合流程，作為遊戲專案合併前的自動化可玩性閘道，確保任何程式碼變更都不會破壞「可啟動且可遊玩」的基準契約。
- **網頁遊戲匯出對照**：若產品目標包含網頁發布，可同時參考 WebGameBench 的瀏覽器互動評估方式，建立跨平台評測能力，但須注意真實引擎專案與網頁遊戲在資產管線與渲染行為上的差異。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從「三項要件」與「端對端遊戲生成」的定義開始理解，掌握「遊戲生成不等於程式碼正確」的核心觀念；可先透過 Godot 官方教學手動完成一個小遊戲，再對照本文評估框架，體會互動系統正確性與程式碼正確性的差異。
- **AI 工程師**：重點研讀互動驗證與評分標準引導的多模態評判實作細節，關注重播示範系統的設計如何兼顧評估覆蓋率與運算成本；同時留意文中對前沿編碼智慧體失敗模式的診斷，作為改進智慧體工具使用與錯誤修復策略的參考。
- **研究人員**：深入分析三項要件的正式化過程與現有基準的缺口對照，思考如何將「引擎扎根、成品完整性、互動驗證」的框架遷移至其他遊戲引擎（如 Unity、Unreal）或更廣泛的互動式軟體生成領域；論文中的 15 個遊戲家族分類亦可作為後續擴充任務難度與多樣性的基礎。
- **產品經理**：聚焦實證數據（最強智慧體僅 41.46%）與失敗模式分析，務實評估「文字轉遊戲」功能在現階段的商業可行性；建議將應用範圍先收斂於原型驗證或輔助開發工具，而非取代完整的人工開發流程，並以本文評估框架作為產品品質指標的設計藍圖。
