## ⚡ TL;DR

現有評估常將代理程式失敗歸因於整體結果，難以判斷問題根源與修復責任。

## 摘要翻譯

現有評估常將代理程式失敗（agent failures）簡化為系統層級的結果，掩蓋了失敗源頭為何，以及何種介入措施能改善代理程式系統（agent system）的表現。這形成了一個修復歸屬問題（repair-assignment problem）：同一個表面上的失敗，依其來源可能需要模型後訓練（model post-training）、支架工程（harness engineering）、環境重新設計（environment redesign），或基準測試修復（benchmark repair）。由於代理程式行為（agent behavior）源於模型（models）、支架（harnesses）、使用者（users）、工具（tools）、記憶（memory）與環境（environments）之間的互動（interactions），僅有結果層級的標籤（outcome-level labels）通常不足以帶來改善。大多數失敗分類法（failure taxonomies）對解決此問題幫助有限，因為它們是特定於基準測試的（benchmark-specific）且缺乏共享結構（shared structure）。本研究提出一個以互動為中心的分類法（interaction-centric taxonomy），將失敗定位於其發源的互動，並辨識出應負責的元件（component）。該分類法將 41 種失敗模式（failure modes）各自指派到兩個元件之間的邊（edge），並標示責任側（fault side）以指出修復應歸屬何處。這使該分類法可據以行動（actionable）：模型側失敗（model-side failures）指出後訓練的目標，支架側失敗（harness-side failures）指向鷹架（scaffolding）與工具整合（tool-integration）的修復，而環境或評分器失敗（environment or grader failures）則揭示需要重新設計的評估條件（evaluation conditions）。此分類架構（schema）適用於各種代理程式架構（agent architectures），從程式設計助理（coding assistants）到長期目標導向的個人助理（long-horizon personal assistants）與多代理程式系統（multi-agent systems）。我們以公開基準測試（public benchmarks）、模型系統卡（model system cards）、已發表報告以及已記錄代理程式軌跡（logged agent trajectories）中的詳解範例為基礎建立此分類法，並以獨立的推理代理程式（reasoning agents）作為評判（judges）來評估其可重現性。在四個前沿模型（frontier models）中，與人類類別標籤（human category labels）相比，表現最佳的評判達到 Cohen's Kappa 係數（Cohen's κ）0.76，顯示這些類別捕捉的是共享結構，而非標註者特定偏好（annotator-specific preferences）。

### 核心貢獻（3～5點）
- 提出以互動為中心的分類法，將代理程式失敗定位到其發源的互動與應負責的元件，解決「同一失敗應由誰修復」的歸屬問題。
- 以「邊（edge）」與「責任側（fault side）」組織 41 種失敗模式，使分類結果可直接對應到模型後訓練、支架工程、環境重新設計或基準測試修復等具體行動。
- 分類架構具有跨架構適用性，涵蓋程式設計助理、長期目標導向的個人助理與多代理程式系統。
- 透過公開基準測試、模型系統卡、已發表報告與代理程式軌跡中的詳解範例驗證分類法，並以獨立推理代理程式擔任評判，最強評判與人類類別標籤的 Cohen's Kappa 係數達 0.76，顯示分類類別具有共享結構與可重現性。

### 適合對象
從事代理程式系統評估、模型後訓練、支架工程、基準測試設計與環境設計的研究者與工程師，以及關注 AI 系統可解釋性、可修復性與責任歸屬的產品經理、政策制定者與進階讀者。

## 深度分析

#### 方法論解析

本研究的核心方法是將 agent（代理程式）失敗的單位從「系統層級結果」轉移到「元件（component）之間的互動（interaction）」。作者將 agent 系統拆解為九個基本元件：Model（模型）、Owner（任務擁有者）、Grader（評分器）、Third party（第三方行為者）、Context（上下文）、Memory（記憶體）、Tool（工具）、Local env（本地環境）、External env（外部環境）。在 multi-agent（多代理程式）情境下，則進一步區分 peer（同儕）與 subagent（子代理程式）的角色。每個失敗模式（failure mode）都被指派到一條連接兩個元件的邊（edge），並標註 fault side（責任側），以指出修復應該落在哪一側。

這樣的設計直接回應了作者所謂的 repair-assignment problem（修復指派問題）：同一個可觀察的失敗表徵，可能源自 model post-training（模型後訓練）、harness engineering（支架工程）、environment redesign（環境重新設計）或 benchmark repair（基準測試修復）等不同層級。舉例來說，當 agent 回報 tool call（工具呼叫）成功但實際上失敗時，若錯誤是 tool wrapper（工具包裝器）壓抑了錯誤訊息，則標註為 TOOL—MODEL · fault: TOOL；若 wrapper 已正確回傳錯誤但 model 忽略，則標註為 TOOL—MODEL · fault: MODEL。互動相同，但責任側不同，對應的修復行動也完全不同。

為了處理單一 trajectory（軌跡）中常見的 cascading failures（連鎖失敗），作者採用逆向因果追蹤：從觀察到的系統層級失敗出發，往回找出 execution does not recover（執行無法恢復）的最早失敗點，並只標註該 initiating failure（起始失敗），而非其下游症狀。這條規則對於 taxonomy（分類法）的穩定性至關重要，因為若允許標註者自由選擇連鎖鏈中的任一節點，同一筆軌跡會得到不一致的標籤。

整體而言，這套方法論具有三個可據以行動的（actionable）對應關係：

- **Model-side failures（模型側失敗）**：指向 post-training（後訓練）、微調或提示策略的改進。
- **Harness-side failures（支架側失敗）**：指向 scaffolding（鷹架）、context compaction（上下文壓縮）、memory management（記憶體管理）與 tool integration（工具整合）的修正。
- **Environment / Grader failures（環境或評分器失敗）**：指向 evaluation conditions（評估條件）或 benchmark（基準測試）本身的重新設計。

這種「邊＋責任側」的結構讓 taxonomy 能跨越多種 agent architectures（代理程式架構），包括 coding assistants（程式設計助理，如 Claude Code、Codex）、long-horizon personal assistants（長期執行個人助理，如 OpenClaw、HermesAgent）以及 multi-agent systems（多代理程式系統），並且是 modality-agnostic（模態無關）的。

#### 實驗數據解讀

本研究的實驗重點不在於提升 agent 效能，而在於驗證 taxonomy 的 operational reproducibility（操作可重現性）。作者使用 independent reasoning agents（獨立推理代理程式）作為 judges（評判者），在四個 frontier models（前沿模型）上測試它們能否根據相同的定義與證據，復現人類標註者的 category labels（類別標籤）。

主要結果如下：

- 最強的 judge 與人類標註者之間的 Cohen's κ（Cohen's Kappa 係數）達到 **0.76**。
- judge 彼此之間的 pairwise agreement（成對一致性）最高達到 **0.84**。

按照 Landis 與 Koch 的慣用解釋，0.76 屬於 substantial agreement（高度一致），0.84 則接近 almost perfect agreement（幾乎完全一致）。這兩個數據的意義在於：taxonomy 的類別並非標註者特定偏好（annotator-specific preferences）的產物，而是捕捉到了某種 shared structure（共享結構）。值得注意的是，judge 彼此之間的一致性與它們對人類標註者的一致性相當，這暗示當給予相同定義與證據時，獨立的推理代理程式會收斂到相似的判斷。

然而，從實驗設計的角度仍有幾點需要謹慎解讀：

1. **樣本規模與代表性不明**：提供的文本未說明用於評估的軌跡數量、涵蓋的任務類型，以及人類標註者的人數與背景。這會影響 0.76 這個數字能否推廣到更廣泛的 agent 應用場景。
2. **僅評估類別標籤，未評估因果鏈品質**：實驗測量的是最終 category label 是否一致，但對於「最早起始失敗」的選取、連鎖失敗的切分等更細緻的判斷，並未提供額外的量化指標。
3. **Judge 本身即為 frontier LLM**：雖然作者強調將 judge 視為 independent analyst（獨立分析師），但這些 judge 仍可能共享某些訓練資料或推理偏誤，進而影響一致性數字的解釋。
4. **未驗證 actionability 的實際效果**：高一致性並不保證依據分類結果進行修復後，agent 效能一定會提升。這是後續研究需要補強的環節。

總體來說，實驗數據支持 taxonomy 具有可重複標註的潛力，但要將其轉化為可靠的工程工具，仍需更大規模、更多元領域的驗證。

#### 與現有研究的比較

現有的 agent failure taxonomies（代理程式失敗分類法）大多存在兩個問題：一是 benchmark-specific（特定於基準測試），雖然能捕捉 fine-grained failure modes（細粒度失敗模式），但缺乏 shared structure（共享結構）；二是傾向於依據內部 agent module（代理程式模組）或 outcome-level labels（結果層級標籤）進行分類，無法區分「失敗在哪裡顯現」與「失敗由誰造成」。

本研究在以下幾個方面做出了改進：

- **從模組導向轉為互動導向**：將分析單位定為 component 之間的 interaction（互動），而非單一元件的內部狀態。這讓同一個可觀察行為可以根據互動脈絡被賦予不同的責任側。
- **引入 fault side（責任側）**：這是與過去研究最關鍵的差異。過去的分類法可能將「工具回報成功但實際失敗」統一歸為工具相關錯誤，但本研究能進一步區分是 tool wrapper 的問題還是 model 理解錯誤的問題。
- **跨架構適用性**：無論是 coding assistant、長期個人助理還是 multi-agent system，都可以使用同一套 component vocabulary（元件詞彙）進行分析。
- **強調 actionability（可據以行動）**：每個分類結果都直接對應到一類修復行動，這在過往以描述現象為主的分類法中較少見。

不過，這套方法也有其限制：

- **41 個失敗模式可能仍不完整**：隨著 agent 系統持續演進，新的互動形式（例如更複雜的 memory hierarchy、adversarial third party）可能產生未被涵蓋的失敗模式。
- **因果鏈的判定依賴標註者詮釋**：雖然作者提出「最早無法恢復的失敗點」規則，但在實際軌跡中，何謂「無法恢復」仍可能需要領域知識與反事實判斷。
- **未與現有分類法進行系統性對照**：研究雖然聲稱過往分類法缺乏共享結構，但並未提供一張明確的對照表，將 41 個模式映射到既有文獻的分類上，這會讓社群難以快速整合。
- **對 harness 的定義較寬泛**：harness（支架）同時涵蓋 context management、memory、tool access 等多個功能，未來可能需要進一步細分，才能更精確地定位 harness-side failures。

#### 可重現性評估

從提供的文本來看，本研究的可重現性面臨幾個挑戰：

- **未明確釋出開源資源**：文中並未提及是否公開原始碼、標註資料集、judge 使用的 prompts（提示）或模型權重。雖然 worked examples（實例分析）取材於 public benchmarks（公開基準測試）、model system cards（模型系統卡）、published reports（已發表報告）與 logged agent trajectories（記錄的代理程式軌跡），但具體的標註樣本與評判流程並未釋出。
- **依賴 frontier models 作為 judges**：要復現實驗，研究者需要能夠存取相同的 frontier models（前沿模型）與 API，這在成本與可及性上都是門檻。
- **人類標註細節不足**：可重現性不僅需要自動化 judge，也需要清楚的人類標註指南（annotation guidelines）。目前文本僅說明核心原則，對於邊界案例的處理、連鎖失敗的切分標準等細節著墨有限。
- **公開資料來源雖可取得，但軌跡可能難以完全復原**：部分 logged trajectories 可能來自 Scale AI 內部系統，外部研究者無法直接取得相同資料。

若要提升可重現性，建議作者釋出以下資源：

1. 完整的 41 個 failure modes 清單與每個模式的正式定義。
2. 標註指南與邊界案例說明文件。
3. 用於 independent reasoning agents 的 judge prompts。
4. 一組已去識別化的 annotated trajectories（帶標註軌跡），供社群驗證。
5. 將 taxonomy 編碼為可重複使用的 schema（模式）或程式庫，方便整合到現有的 agent evaluation pipelines（評估流程）中。

#### 未來研究方向

基於這篇論文提出的 interaction-centric taxonomy（以互動為中心的分類法），未來研究可以朝以下方向延伸：

- **擴充分類法的覆蓋範圍**：針對安全性、對抗性互動、隱私外洩、社會工程攻擊等情境，增加新的 failure modes 與對應的 fault side。
- **自動化失敗定位工具**：將 taxonomy 整合到 agent harness 中，開發能即時偵測並標註失敗邊與責任側的模組，協助工程師在部署階段快速診斷。
- **因果發現方法的結合**：除了人工逆向追蹤，可引入 counterfactual reasoning（反事實推理）或 causal inference（因果推論）技術，自動判斷「最早無法恢復的失敗點」。
- **修復效果的實證驗證**：設計對照實驗，針對 model-side、harness-side、environment-side 的失敗分別施加對應修復，並測量 agent 效能是否確實提升，以驗證 taxonomy 的 actionability。
- **建立大型標註資料集**：彙集跨領域、跨模態、跨架構的 agent trajectories，並由多位專家標註，形成可用於訓練自動化 judge 的標準資料集。
- **與現有分類法的對照與整合**：建立 mapping table（對照表），將本研究的 41 個模式與既有 benchmark-specific taxonomies 連結，降低社群採用門檻。
- **多語言與跨文化適用性**：驗證這套以英文 agent 互動為主的 taxonomy，是否適用於其他語言、文化情境或不同使用者介面設計。
- **即時監控與回饋迴路**：將 failure localization（失敗定位）嵌入 production systems（生產系統），形成持續學習與自動修復的閉迴路。
- **可解釋性與可視化工具**：開發能視覺化呈現 component interaction graph（元件互動圖）與失敗傳播路徑的工具，幫助研究人員與工程師理解複雜的連鎖失敗。

## 論文問答

**Q1：這篇論文提出的「修復歸屬問題」是什麼？為何現有評估方法會造成這個問題？**  
A：現有評估通常把代理程式的失敗簡化為系統層級的結果，導致同一個可見的失敗現象可能源自模型、支架、環境或基準測試的不同環節，因而需要截然不同的修復手段。這種現象被稱為修復歸屬問題：同樣的表徵可能對應到模型後訓練、支架工程、環境重新設計或基準測試修復。由於代理程式的行為來自模型、支架、使用者、工具、記憶與環境之間的互動，單純的結果標籤無法指出真正的責任元件，從而讓後續改善措施難以對症下藥。

**Q2：為什麼既有的失敗分類法難以解決修復歸屬問題？**  
A：既有的失敗分類法多半是特定於基準測試的，雖然能捕捉細粒度的失敗模式，卻缺乏跨系統共享的結構。它們通常只標註結果層級的失敗，無法區分「失敗在哪個互動中浮現」與「應由哪個元件負責修復」。因此，這些分類法無法直接轉化為可據以行動的修復決策，也難以適用於不同代理程式架構。

**Q3：隨著代理程式越來越自主，為什麼失敗定位變得更加重要？**  
A：當大型語言模型被部署在長期自主運作的情境中，代理程式會反覆與使用者、工具、記憶、支架和環境互動，顯著擴大了失敗表面。在這種複雜互動下，同一個可觀察的失敗行為可能來自完全不同的根本原因，例如上下文壓縮導致指令遺失，或是模型即使看到指令也未能遵循。只有準確定位失敗來源，才能選擇正確的後續介入方式，避免把資源浪費在錯誤的元件上。

**Q4：這篇論文提出的互動中心分類法核心方法是什麼？**  
A：作者把元件之間的互動視為分析單位，並將每一種失敗模式對應到兩個元件之間的邊，以及一個指出應由誰負責修復的責任側。整個分類法共整理了 41 種失敗模式，每個模式都被賦予一條互動邊與一個責任側。這樣的結構讓分類結果直接可據以行動：模型側失敗指向後訓練目標，支架側失敗指向鷹架與工具整合的修復，環境或評分器失敗則揭示需要重新設計的評估條件。

**Q5：分類法中使用了哪些核心元件？它們各自扮演什麼角色？**  
A：核心元件包括模型、擁有者、評分器、第三方、上下文、記憶、工具、本地環境與外部環境。模型是處理觀察並產出動作的大型語言模型策略；擁有者給予任務與成功定義；評分器負責判斷結果是否成功；工具則是模型與其他元件交換請求與回應的雙向介面。在多代理程式系統中，還會以同儕或子代理程式的角色來描述其他模型，使同一套詞彙能涵蓋單一代理程式與多代理程式的情境。

**Q6：「互動邊」與「責任側」的區分為什麼是關鍵設計選擇？**  
A：同樣的互動邊可能因為不同元件出錯而需要不同的修復方式，例如工具回傳錯誤但模型忽略，與工具包裝器隱藏錯誤導致模型無從得知，兩者都發生在工具—模型這條邊上，但責任側分別是模型與工具。責任側明確指出應由哪個元件承擔修復責任，避免把觀察到的失敗表象直接等同於根本原因。這種區分讓分類法能夠區別「失敗在哪裡顯現」與「應該修復哪裡」，從而提升修復決策的準確性。

**Q7：作者如何驗證這套分類法的可重複性？**  
A：作者使用獨立的推理代理程式作為評判者，在給定相同定義與證據的情況下對失敗軌跡進行分類。他們同時測量評判者與人類標註者之間的一致性，以及評判者彼此之間的成對一致性。這種做法把每個評判者視為獨立分析師，以檢驗分類類別是否反映共享結構，而非單一標註者的特定偏好。

**Q8：實驗的主要量化結果是什麼？這些結果代表什麼意義？**  
A：在四個前沿模型中，最強的評判者與人類類別標籤的 Cohen's Kappa 係數達到 0.76，顯著高於隨機水準。評判者之間的最高成對一致性更高達 0.84，顯示不同評判者能夠收斂到相同標籤。這些結果支持分類法捕捉的是跨標註者的共享結構，而不是主觀偏好，從而增強了分類結果的可信度與可重複性。

**Q9：面對連鎖失敗時，作者採用了什麼標註規則？為什麼需要這條規則？**  
A：作者從觀察到的系統層級失敗出發，沿著因果鏈往回追溯，標註最早發生且執行過程未能從中恢復的那個失敗，而不是標註後續的症狀。這條規則的必要性在於，若對最早失敗點進行介入，整個軌跡的結果可能會改變，而後續錯誤往往只是前因的衍生結果。若沒有固定規則，不同標註者對同一條軌跡會給出不一致的標籤，進而損害分類法的可重複性與可據以行動性。

**Q10：這套分類法可以如何應用於實際的代理程式系統？**  
A：開發團隊可以將失敗軌跡對應到特定的互動邊與責任側，從而判斷應該進行模型後訓練、支架鷹架調整，還是環境與評分器的重新設計。它適用於程式設計助理、長期個人助理以及多代理程式系統等不同架構，並且是模態無關的。透過這種定位，產品團隊能夠把工程資源導向真正需要修復的元件，縮短除錯與迭代的週期。

**Q11：在產品開發中，模型側失敗與支架側失敗分別帶來什麼考量？**  
A：模型側失敗代表大型語言模型本身的策略或理解能力不足，通常需要透過後訓練、微調或提示工程來改善。支架側失敗則指向上下文管理、記憶機制、工具包裝器或整體鷹架的問題，應由支架工程來解決。正確區分兩者能避免把模型能力問題誤判為工程問題，反之亦然，從而讓產品團隊避免在錯誤的方向上投入大量資源。

**Q12：這套分類法對整個代理程式研究領域可能產生什麼影響？**  
A：它提供了一套跨架構、跨基準測試的共享詞彙，讓不同研究團隊能以一致的方式描述與比較失敗模式。這有助於從特定於基準測試的細粒度標籤，提升到能夠指導修復行動的結構化分類。長遠來看，這種共享結構能促進模型、支架與評估條件之間的協同改善，加速代理程式系統的可靠部署。

**Q13：作者承認這套分類法有哪些限制？**  
A：分類法能夠定位失敗來源，但本身並不直接提供具體的修復方案，也無法保證修復後的效能提升。它的有效運作仰賴對因果鏈的追溯能力，而在觀察性有限或多方互動極度複雜的軌跡中，這種追溯可能變得困難。此外，目前的可重複性驗證僅涵蓋部分公開範例與記錄軌跡，更廣泛的領域覆蓋仍有待後續研究。

**Q14：在哪些失敗情境下，這套分類法可能難以應用？**  
A：當多個元件共同導致失敗，或存在回饋迴路使最早原因難以辨識時，責任側的指派會變得模糊。若對支架、上下文或記憶的內部運作缺乏可觀察性，標註者也難以判斷錯誤究竟發生在哪個互動環節。此外，對抗性或不合作的第三方互動，以及評分標準本身含糊不清的基準測試，都可能讓環境或評分器失敗與模型失敗之間的界線變得難以劃分。

**Q15：作者指出了哪些未來研究方向？**  
A：未來可以將這套分類法擴展到更多基準測試與代理程式架構，並建立自動化的失敗定位流程，自動識別互動邊與責任側。另一個方向是發展更完善的評分器與環境設計指南，讓評估條件本身不再成為失敗的來源。此外，透過因果介入實驗來驗證責任側指派的正確性，以及提升自動評判者的推理品質，都是值得進一步探索的研究課題。

## 實務應用指南

### 適用場景

1. **程式設計助理的錯誤歸因**：當 Claude Code 或 Codex 等代理程式產生錯誤程式碼、忽略測試失敗或誤報工具執行結果時，可用此分類法判斷問題出在模型理解、支架（harness）的上下文壓縮、工具包裝器的錯誤回傳，還是本地執行環境的權限設定。

2. **長期執行個人助理的維運**：針對需要讀取郵件、瀏覽網頁、執行 shell 指令並維護持久記憶的代理程式（如 OpenClaw、HermesAgent），可定位失敗是源於記憶體檢索、上下文遺失、外部 API 變動，還是使用者指令本身的歧義。

3. **多代理程式系統的協調除錯**：在由多個模型組成的系統中，可用來區分子代理程式（subagent）與協調器（orchestrator）之間的互動失敗，判斷責任側是模型策略、通訊通道、還是第三方代理程式的非預期行為。

4. **基準測試設計與修復**：在建立或維護 agent benchmark 時，可識別失敗是否來自評分器（grader）的錯誤判斷、環境設計缺陷或題目本身的歧義，避免將評估條件的問題誤判為模型能力不足。

5. **生產環境代理程式的持續監控**：將分類法整合到可觀測性系統中，對生產軌跡進行自動化標註，協助維運團隊決定該進行模型後訓練、支架工程、環境重新設計，還是基準測試修復。

### 實作前置條件

**資料需求**：
- 完整的代理程式執行軌跡（trajectories），包含模型輸入輸出、工具呼叫與回傳結果、記憶體讀寫紀錄、環境狀態變化。
- 評分器輸出與最終成功/失敗標籤。
- 系統設計文件，說明支架如何管理上下文、記憶體與工具存取。

**運算需求**：
- 儲存與查詢軌跡資料的基礎設施。
- 若使用獨立推理模型作為 judge，需要足夠的推理運算資源（如 frontier model API 配額）。
- 進行一致性分析所需的統計運算環境。

**技能需求**：
- 熟悉代理程式架構與元件互動（模型、支架、工具、記憶體、環境）。
- 具備分類學設計與標註品質評估經驗（如 Cohen's Kappa 計算與解讀）。
- 提示工程能力，用於設計 judge 模型的評估提示。
- 基礎因果推理能力，能從觀察到的系統失敗回溯最早未恢復的失敗點。

### 實作步驟建議

1. **建立元件詞彙表**：根據論文 Table 1，定義組織內代理程式系統的元件（Model、Owner、Grader、Third party、Context、Memory、Tool、Local env、External env），並釐清各元件的邊界。

2. **繪製互動邊圖譜**：列出系統中實際存在的互動邊（如 OWNER→MODEL、MODEL→TOOL、TOOL→MODEL、MODEL→MEMORY 等），作為後續分類的結構基礎。

3. **收集與結構化軌跡**：確保每筆軌跡包含足夠證據，能重建模型觀察到的內容、支架做了什麼處理、工具回傳了什麼、環境實際狀態為何。

4. **客製化 41 種失敗模式**：以論文分類為起點，根據自身系統調整失敗模式定義，並為每種模式指定對應的互動邊與責任側（fault side）。

5. **設計標註流程與 judge 提示**：訓練人工標註者，或設計獨立推理模型的 judge 提示，要求其先重建證據、識別最早未恢復的失敗、再指派互動邊與責任側。

6. **執行回溯式標註**：從觀察到的系統層級失敗出發，沿因果鏈往回追溯，標註最早導致後續錯誤且未恢復的失敗點，而非僅標註最終症狀。

7. **對應到修復行動**：根據責任側產生可執行的修復建議——模型側對應後訓練資料策展，支架側對應 scaffolding 與工具整合修正，環境或評分器側對應評估條件重新設計。

8. **驗證分類一致性**：定期計算標註者間一致性與 judge 模型對人類標籤的 Cohen's Kappa，確保分類捕捉的是共享結構而非標註者特定偏好。

9. **整合到開發循環**：將分類結果回饋至模型訓練、支架迭代、基準測試修復與生產監控流程，形成閉環。

### 潛在風險與注意事項

- **瀑布式失敗的錯誤標註**：若未嚴格追溯最早未恢復的失敗，容易將下游症狀誤標為根本原因。建議建立明確規則：只有對該點進行干預能改變最終結果時，才標註為該失敗。

- **責任側判斷的主觀性**：同一互動可能因證據解讀不同而被歸為模型側或支架側。建議為每種失敗模式撰寫具體判斷準則與範例，並透過 judge 模型進行獨立驗證。

- **Judge 模型的一致性天花板**：雖然最強 judge 可達 κ=0.76，但仍非完美。建議將 judge 輸出視為輔助而非唯一依據，對高風險決策保留人工複審。

- **過度擬合特定基準測試**：若僅用單一 benchmark 的軌跡建立分類習慣，可能遺漏其他架構的失敗模式。建議定期納入不同領域（程式設計、個人助理、多代理程式）的範例。

- **忽略多模態與跨架構差異**：分類法雖然宣稱模態無關，但實作時仍需確認視覺、音訊等輸入的互動邊是否被正確捕捉，避免預設所有代理程式都採用文字介面。

- **修復行動的組織阻力**：分類結果可能指出問題出在評分器或環境設計，而非模型團隊熟悉的領域。建議在導入初期就讓相關團隊（模型、工程、評估、產品）共同參與分類定義。

### 與其他技術的整合建議

- **可觀測性平台**：將互動邊與責任側標註整合到現有 tracing 工具（如 LangSmith、Langfuse、OpenTelemetry），讓維運人員能在單一介面查看失敗定位結果。

- **CI/CD 與回歸測試**：在每次支架或模型更新後，自動對標準軌跡集執行分類標註，追蹤各責任側失敗模式的變化趨勢，作為回歸指標。

- **模型後訓練資料策展**：將模型側失敗的軌跡自動轉換為後訓練或微調資料，針對特定互動邊（如 MODEL→TOOL、MODEL→MEMORY）強化模型能力。

- **提示工程與支架工程工具鏈**：將 harness-side 失敗回饋給提示版本控制系統與工具包裝器開發流程，例如改善錯誤訊息格式、上下文壓縮策略或工具描述。

- **多代理程式協調框架**：在如 AutoGen、CrewAI 等框架中，於代理程式間通訊層嵌入分類標註，協助識別第三方代理程式或子代理程式互動中的責任歸屬。

- **評估與 benchmark 平台**：將 grader-side 與 environment-side 失敗整合到 benchmark 維護流程，作為題目汰換、評分器修正或環境設定調整的依據。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從 Table 1 的元件詞彙表與「互動邊」概念開始，理解代理程式失敗不只是「模型做錯」，而是發生在兩個元件之間的互動問題。接著閱讀論文中的具體範例，特別是工具呼叫成功/失敗的兩種對照案例，就能掌握「同一現象可能對應不同責任側」的核心思想，無需深入統計細節。

**AI 工程師**：請聚焦於分類法如何轉化為實際的除錯與修復流程，尤其是從系統失敗回溯最早未恢復失敗的規則，以及如何利用 judge 模型進行可規模化的標註。建議同時評估你目前系統的軌跡資料是否足以支撐這種細粒度分析，並思考如何將分類結果接入現有的可觀測性與 CI/CD 管線。

**研究人員**：本論文的主要貢獻在於提出一個跨架構、可重複的失敗分類結構，而非另一個特定於某基準測試的失敗清單。建議深入檢視 41 種失敗模式的完備性與互斥性，並可進一步探索不同領域（如多模態、具身智慧）是否需要擴充新的互動邊或責任側，也可將 judge 模型一致性實驗作為後續方法論研究的起點。

**產品經理**：請將此分類法視為一種「失敗歸因的共通語言」，幫助團隊在模型、工程、評估部門之間分配資源與責任。閱讀時可著重於「可據以行動」這個特性——每個分類結果都直接對應到具體的修復行動（後訓練、支架工程、環境重新設計、基準測試修復），這有助於在規劃產品路線圖時，決定下一個迭代該投資在哪個環節。
