WebHarbor 的核心方法論建立在「任務驅動的人機協作建構流程」(task-driven human-agent collaboration) 之上，試圖在「真實網站視覺保真度」(visual fidelity) 與「可控實驗環境」之間取得平衡。此方法論可從三個層面深入剖析：

**1. 任務條件化建構策略 (Task-Conditioned Construction)**

傳統的網站重建方法面臨一個根本困境：商業網站的功能與內容過於龐大，完整重建不切實際；而過度簡化的複製品則缺乏搜尋、帳號管理、預訂、交易等核心邏輯。WebHarbor 採用「任務條件化」策略來界定建構範圍——每個環境的目標任務明確指定了該環境必須支援的頁面、資料與互動工作流程。這種設計的優勢在於：

- **範圍可控性 (Tractable Scope)**：透過任務清單來約束重建範圍，避免無限擴張
- **任務有效性保障 (Task Validity)**：環境設計直接服務於任務需求，減少「答案洩漏」(answer leakage) 或「捷徑」(shortcut) 問題
- **功能深度聚焦**：能夠集中資源實作認證後工作流程 (post-authentication workflows)，這是現有基準測試普遍缺乏的環節

**2. 編碼代理實作層 (Coding Agent Implementation)**

WebHarbor 採用編碼代理 (coding agent) 來實作前端、後端、資料庫與視覺內容，並透過「標準化的環境建構技能」(standardized environment-construction skills) 來確保一致性。這種設計的關鍵考量包括：

- **可重現性 (Reproducibility)**：所有環境皆以 Docker 容器化形式封裝，無需存取目標服務即可執行
- **確定性控制 (Deterministic Control)**：環境可重置至受控的初始狀態，支援強化學習 (RL) 的可重複訓練
- **持久狀態 (Persistent State)**：支援真實的狀態轉移 (state transition)，例如購物車、訂單、帳號餘額等

**3. 人類稽核迴圈 (Human Auditing Loop)**

人類貢獻者在流程中扮演品質守門員的角色，負責檢查渲染後的網站、執行目標工作流程，並針對四個維度進行稽核：

| 稽核維度 | 說明 |
|---------|------|
| 視覺保真度 (Visual Fidelity) | 介面與原網站的相似程度 |
| 功能正確性 (Functional Correctness) | 互動邏輯是否正確執行 |
| 資料真實性 (Data Realism) | 內容是否符合真實情境 |
| 任務有效性 (Task Validity) | 任務是否可解且無洩漏 |

稽核發現的問題由編碼代理進行修正，形成迭代改進迴圈，直到通過審核。這種「人機協作」(human-agent collaboration) 模式結合了 AI 的擴展性與人類的判斷力，是 WebHarbor 能夠兼顧規模與品質的關鍵設計。

**4. 環境特性整合**

從 Table 1 的比較來看，WebHarbor 是目前唯一同時滿足以下四項條件的環境套件：
- 廣泛網站覆蓋 (153 個環境)
- 離線執行 (offline execution)
- 圖像豐富內容 (image-rich content)
- 登入式工作流程 (login-based workflows)

這填補了現有方法的重要缺口：WebVoyager 與 Online-Mind2Web 雖有真實網站但無法離線執行；WebArena 雖可離線但網站數量極少；AutoWebWorld、CUA-Gym、WebArena-Infinity 等合成環境則缺乏完整的認證後功能。

#### 實驗數據解讀

**1. 環境規模與任務覆蓋**

WebHarbor 最終包含 153 個可執行的網站環境與 3,518 個任務，涵蓋資訊檢索、帳號管理、預訂與交易等多類型工作流程。這個規模相較於 WebArena (6 個環境) 與 WebArena-Infinity (13 個環境) 有顯著提升，且任務設計特別強調「多步驟」(multi-step) 與「認證後」(post-authentication) 工作流程，這正是現有基準測試普遍不足之處。

**2. 線上網站基準測試的失敗率**

論文揭露了一個重要的實證數據：在實驗中，約 38% 的 Online-Mind2Web 任務被機器人偵測 (bot detection) 阻擋，22% 的 WebVoyager 任務因網站變更而失效。這些數據凸顯了線上網站作為評估環境的根本不穩定性，也為 WebHarbor 的必要性提供了量化支撐。

**3. 強化學習訓練成效**

實驗結果顯示，一個 Qwen 4B 等級的 GUI 代理在 WebHarbor 中透過強化學習訓練後，能夠：
- **泛化至未見任務 (Unseen Tasks)**：證明環境提供的訓練信號具有遷移價值
- **在四個基準測試上與領先的開源 GUI 網頁代理競爭**：包含 WebVoyager、Online-Mind2Web 等線上基準

這個結果的意義在於：WebHarbor 不僅是穩定的評估環境，也是有效的訓練環境。相較於直接在線上網站上訓練（成本高、不穩定），WebHarbor 提供了「具成本效益」(cost-efficient) 的替代方案。

**4. 視覺保真度的質性比較**

Figure 1 提供了與 AutoWebWorld、CUA-Gym、WebArena-Infinity 的視覺比較案例。從 Amazon 網站的重建結果來看：
- AutoWebWorld 捕捉了廣泛的 Amazon 視覺線索，但主視覺區塊 (hero) 與卡片式佈局 (card layout) 偏離原網站
- CUA-Gym 恢復了店面頁面 (storefront) 結構，但商品欄位 (product slot) 填入的是通用風景圖片
- WebArena-Infinity 未提供 Amazon 網站，最接近的頁面是輕量級的 Handshake 模板
- WebHarbor 結合了目標導向的導覽 (navigation)、密集的商品陳列層級 (merchandising hierarchy) 與商品專屬圖像，產生最連貫且視覺忠實的環境

這個案例研究說明了「視覺保真度」不僅是表面相似，更涉及資訊架構與內容真實性的整合。

#### 與現有研究的比較

**1. 定位差異化**

WebHarbor 在生態系中的定位可從兩個軸向理解：

| 軸向 | WebHarbor 位置 |
|------|---------------|
| 真實性 vs. 可控性 | 偏向「高真實性 + 高可控性」的平衡點 |
| 評估 vs. 訓練 | 同時支援兩者，且特別強化訓練用途 |

相較之下：
- **WebArena / VisualWebArena**：人類手工製作，可離線但網站覆蓋極少（6 個），擴展性受限
- **WebVoyager / Online-Mind2Web**：真實網站但無法離線，受 bot detection、地區限制影響
- **AutoWebWorld / CUA-Gym / WebArena-Infinity**：代理自動合成，規模較大但缺乏認證後功能與圖像豐富內容

**2. 相較於現有工作的改進**

- **規模提升**：153 個環境遠超 WebArena (6) 與 WebArena-Infinity (13)
- **功能完整性**：支援登入式工作流程，填補了現有合成環境的關鍵缺口
- **任務多樣性**：3,518 個任務涵蓋多步驟與認證後場景
- **訓練支援**：專為強化學習設計，提供可重置的初始狀態與可重現的狀態轉移

**3. 現有方法的侷限性**

儘管 WebHarbor 有顯著進展，仍存在以下限制：

- **建構成本**：雖然採用人機協作來提升效率，但 153 個環境的建構仍需大量人類稽核工作，難以快速擴展至數百個以上
- **網站選擇偏差**：環境來源限於 WebVoyager 與 Online-Mind2Web 涵蓋的網站空間，可能遺漏其他重要網站類型
- **真實性上限**：即使是高度保真的重建，仍非真正的線上網站，可能存在代理在轉移至真實環境時的「領域差距」(domain gap)
- **任務設計偏見**：任務由人類設計，可能無法完全反映真實使用者的需求分布

#### 未來研究方向

**1. 自動化程度的提升**

目前的人機協作流程仍需大量人類稽核，未來可探索：
- 自動化視覺保真度評估（透過視覺語言模型比對截圖）
- 自動化功能測試（透過代理模擬使用者行為）
- 自動化任務有效性檢查（偵測捷徑與答案洩漏）

若能將人類稽核的角色轉變為「例外處理」而非「常規檢查」，將大幅提升擴展性。

**2. 領域差距的量化與縮小**

WebHarbor 環境與真實網站之間的「領域差距」是影響代理遷移能力的關鍵因素。未來研究可：
- 系統化量化兩者之間的視覺與功能差距
- 探索「領域隨機化」(domain randomization) 或「領域適應」(domain adaptation) 技術來縮小差距
- 研究在 WebHarbor 訓練的代理在真實網站上的失敗模式

**3. 環境的動態演化**

真實網站會持續更新，WebHarbor 目前是靜態快照。未來可探索：
- 環境的版本控制與更新機制
- 模擬網站內容隨時間變化的「時間軸」功能
- 適應性任務生成，根據代理能力動態調整難度

**4. 多模態與多裝置支援**

目前 WebHarbor 主要針對桌面瀏覽器，未來可擴展至：
- 行動裝置介面
- 不同瀏覽器引擎的渲染差異
- 無障礙 (accessibility) 場景

**5. 認證後工作流程的深化**

雖然 WebHarbor 已涵蓋認證後工作流程，但仍有深化空間：
- 更複雜的多帳號互動（如轉帳、共享文件）
- 權限分級（管理員 vs. 一般使用者）
- 跨網站工作流程（如從一個網站取得資訊後到另一個網站執行操作）

**6. 與其他訓練範式的整合**

WebHarbor 目前主要展示強化學習的應用，未來可探索：
- 與模仿學習 (imitation learning) 的結合
- 自我對弈 (self-play) 機制
- 課程學習 (curriculum learning) 策略

**7. 評估指標的標準化**

目前 GUI 代理的評估指標分散於各基準測試，未來可推動：
- 統一的任務成功率定義
- 步驟效率的標準化衡量
- 錯誤類型的分類體系

這些方向將有助於將 WebHarbor 從一個環境套件發展為一個完整的 GUI 代理研究基礎設施。

**步驟三：人類稽核與迭代修正**
由人類貢獻者對生成的環境進行四面向稽核：

- 功能正確性：實際執行所有目標工作流程，確認狀態轉移正確
- 資料真實性：檢查商品資訊、價格、評論等資料是否符合真實網站語境
- 任務有效性：確認任務無法透過非預期捷徑完成，且答案未洩漏於介面中

**步驟四：Docker 容器化與確定性控制封裝**
將每個環境封裝為 Docker 映像，實作可控的初始狀態重置機制（資料庫快照、種子資料載入），確保評估與訓練的可重現性。設定離線執行模式，隔離對目標服務的依賴。

**步驟五：任務集編纂與評估指標定義**
將 3,518 個任務整理為結構化資料集，每個任務附帶評估腳本（自動檢查目標狀態是否達成）。定義多面向指標：任務完成率、步驟效率、認證後工作流程成功率等。

**步驟六：RL 訓練整合與泛化驗證**
將 WebHarbor 接入 RL 訓練框架，使用 GRPO 等演算法訓練 GUI 代理。訓練後在四個外部基準（WebVoyager、Online-Mind2Web、Mind2Web、VisualWebArena）上驗證泛化能力，確認代理在未見任務上的表現。

**步驟七：持續演進與社群維護**
建立任務擴展機制：當新任務需求出現時，觸發「任務定義 → 程式碼代理實作 → 人類稽核」的循環，使環境隨任務需求持續演進。

### 潛在風險與注意事項

**風險一：視覺保真度不足導致領域偏移**
若重建環境與真實網站視覺差異過大，代理可能學到僅適用於合成環境的捷徑，無法泛化至真實網站。
*緩解措施*：建立嚴格的視覺稽核流程，採用多解析度截圖比對與人類評分；訓練時混入真實網站資料進行領域隨機化。

**風險二：任務捷徑與答案洩漏**
合成環境可能無意中暴露答案（例如在頁面 HTML 中嵌入目標資訊），或允許代理透過非預期路徑（如直接修改 URL 參數）跳過關鍵步驟。
*緩解措施*：在任務設計階段明列禁止行為清單；稽核時執行「紅隊測試」，嘗試以非預期方式完成任務並修補漏洞。

**風險三：功能深度不足限制複雜任務**
部分真實網站的進階功能（如多步驟預訂、條件式退款、跨帳號操作）重建成本高，可能被簡化或省略。
*緩解措施*：採用任務驅動的範圍界定，僅重建目標任務所需的功能；對未覆蓋功能明確標註，避免代理在評估中誤觸發未實作路徑。

**風險四：Docker 環境的資源隔離與安全性**
容器化環境若未妥善隔離，可能造成訓練資料洩漏或被惡意利用。
*緩解措施*：採用唯讀檔案系統、限制網路出站、為每個環境配置獨立資源配額。

**風險五：人類稽核成本與擴展性瓶頸**
人類稽核是品質保證的關鍵，但也是擴展性的主要瓶頸；隨著環境數量增加，稽核工作量線性成長。
*緩解措施*：建立稽核 checklist 與標準化驗收流程；訓練稽核助理模型進行初篩，僅將可疑案例升級至人類審查。

**風險六：RL 訓練中的獎勵 hacking**
代理可能學到在 WebHarbor 中獲得高分但無法泛化的策略（例如過度擬合特定頁面結構）。
*緩解措施*：定期在外部真實網站基準上驗證；引入任務多樣性與環境隨機化；監控代理動作序列的合理性。

### 與其他技術的整合建議

**與既有 GUI 代理框架整合**
WebHarbor 可作為 OpenHands、AutoGen、WebArena 等代理框架的環境後端。建議透過標準化的環境介面（如 Gymnasium API）封裝，使其與主流代理訓練框架無縫對接。

**與視覺語言模型整合**
搭配 GPT-4V、Qwen-VL 等視覺語言模型時，可將 WebHarbor 的截圖作為觀察輸入。建議統一截圖規格（解析度、色彩空間）並提供 DOM 結構作為輔助輸入，提升代理的網頁理解能力。

**與 MLOps 平台整合**
將 WebHarbor 的任務集接入 MLflow 或 Weights & Biases，記錄每次評估的任務完成率、步驟數、錯誤類型等指標，建立代理效能的長期追蹤儀表板。

**與 CI/CD 流程整合**
在代理模型的 CI/CD 流程中加入 WebHarbor 迴歸測試階段，每次模型更新後自動執行核心任務集，確保不退步。

**與真實網站基準互補使用**
建議將 WebHarbor（穩定、可重現）與 WebVoyager、Online-Mind2Web（真實但易變）搭配使用：前者用於訓練與迭代驗證，後者用於最終泛化能力評估。

**與企業 SSO 與權限系統整合**
若企業欲將 WebHarbor 部署於內部並模擬自家系統，需整合企業 SSO（如 SAML、OAuth）以支援真實的認證後工作流程測試。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題陳述，理解為何線上網站無法直接用於代理訓練與評估；接著瀏覽 Table 1 了解 WebHarbor 與既有環境的差異；最後動手安裝 GitHub 上的 Docker 環境，親自體驗一個簡單任務的執行流程，建立直觀認識。

**給 AI 工程師**：重點關注第 3 節的人機協作建構流程與 RL 訓練實驗細節，理解如何將 WebHarbor 接入現有的代理訓練 pipeline；特別注意任務驅動的環境設計理念，這對設計自定義訓練環境具有直接參考價值；建議嘗試重現 Qwen 4B 的 RL 訓練實驗，並在自有業務場景中測試泛化效果。

**給研究者**：深入分析 WebHarbor 在視覺保真度、功能深度、認證後工作流程三個維度上的設計取捨，思考其對 GUI 代理研究方法論的影響；可進一步探索人機協作建構流程的可擴展性邊界，以及如何將此範式應用於其他領域（如行動裝置 GUI、桌面應用代理）的環境建構。

**給產品經理**：從商業價值角度理解 WebHarbor 解決的核心問題——代理訓練與評估的可重現性與成本效益；評估將其導入自家產品的可行性，特別是對於需要自動化操作內部系統或合作夥伴網站的代理產品；關注 Table 1 的功能矩陣，理解 WebHarbor 相較於商業解決方案的定位差異。
