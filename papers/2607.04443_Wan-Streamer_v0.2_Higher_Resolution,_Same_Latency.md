## ⚡ TL;DR

v0.1解析度僅192×336，難以呈現場景中的肢體、手部與周遭物件。
v0.2以單GPUThinker與Ulysses多GPUPerformer讓解析度達640×368。
在維持約200ms模型端與550ms遠端延遲下，支援姿勢、手部與場景清晰可辨的中景互動。

## 摘要翻譯

我們提出 Wan-Streamer v0.2，這是原生串流（native-streaming）、端到端音視覺互動模型（end-to-end audio-visual interaction model）的一項保留延遲的升級（latency-preserving upgrade）。v0.2 保留 v0.1 的建模形式，但將互動輸出串流（interactive output stream）從 192×336 提升至 640×368，同時在 25 FPS 下維持約 200 毫秒的模型端訊號到訊號延遲（model-side signal-to-signal latency）。更高解析度的串流支援場景導向互動（scene-grounded interaction）的中景代理（mid-shot agents），其姿勢（posture）、凝視（視線）（gaze）、手部（hands）、鄰近物體（nearby objects）與局部場景佈局（local scene layout）在即時對話中仍清晰可辨（legible）。為了在不增加使用者可察覺延遲（user-visible delay）的情況下支援更大的視覺串流，v0.2 保留 Thinker（思考器）作為串流感知（streaming perception）的單 GPU 低延遲路徑（single-GPU low-latency path），保留建立生成快取（generation cache）的短語言/狀態 Transformer（轉換器）傳遞（short language/state Transformer pass），並保留最終解碼（final decoding）。Performer（執行器）則改為多 GPU Ulysses 風格上下文並行群組（multi-GPU Ulysses-style context-parallel group），以執行運算成本高昂的下一單元潛在生成（next-unit latent generation）。每個 Performer 運算秩（performer rank）會將傳入的 K/V（鍵/值）寫入預先分片本地快取（pre-sharded local cache）。長高解析度潛在影片序列（long high-resolution latent video sequence）會跨運算秩分片進行去噪（denoising），並透過 Ulysses 通訊（Ulysses communication）聚合；而長度短得多的音訊潛在序列（audio latent sequence）則不進行序列分片（sequence sharding）而生成。在此分割下，Thinker（思考器）的語言/狀態計算僅以 K/V 條件化（鍵/值條件化）（K/V conditioning）的形式傳遞至 Performer（執行器），因此無需在 Performer 群組內部傳輸獨立的語言序列。這將額外硬體集中於視覺生成，同時保留精簡的 Thinker–Performer 邊界（thinker-performer boundary），並在納入 350 毫秒雙向網路延遲預算（bidirectional network budget）後，將總遠端互動延遲（remote interaction latency）維持在約 550 毫秒。

### 核心貢獻（3～5點）
- 在維持約 200 毫秒模型端訊號到訊號延遲的前提下，將互動輸出串流解析度從 192×336 提升至 640×368，實現保留延遲的解析度升級。
- 透過高解析度串流支援場景導向的中景代理，使姿勢、凝視、手部、鄰近物體與局部場景佈局在即時對話中仍清晰可辨。
- 保留 Thinker 作為單 GPU 低延遲路徑，負責串流感知、短語言/狀態 Transformer 傳遞與最終解碼，避免增加使用者可察覺延遲。
- 將 Performer 改為多 GPU Ulysses 風格上下文並行群組，專注處理高解析度長影片潛在序列的去噪與下一單元潛在生成。
- 以 K/V 條件化取代獨立語言序列在 Performer 群組內的傳輸，保留精簡的 Thinker–Performer 邊界，並在納入 350 毫秒雙向網路延遲預算後仍維持約 550 毫秒總遠端互動延遲。

### 適合對象
本論文適合從事即時多模態互動、串流影片生成、互動式數位人、端到端音視覺模型，以及低延遲生成式系統的研究者與工程師閱讀；特別是關注如何在提升輸出解析度的同時，仍維持使用者可察覺延遲與串流因果性（streaming causality）的讀者。

## 深度分析

#### 方法論解析

##### 1. 原生串流（native-streaming）架構的延續
Wan-Streamer v0.2 並未改變 v0.1 的核心建模形式，而是將其視為一個「保留延遲的解析度升級（latency-preserving resolution upgrade）」。模型仍然把使用者文字、音訊、影片與代理文字、音訊、影片放在同一條因果時間軸（causal timeline）上，並以單一 Transformer 進行區塊因果注意力（block-causal attention）建模。這種端到端（end-to-end）設計的關鍵在於：

- **閉合的音視覺互動迴路（audio-visual interaction loop）**：感知、回應時機（response timing）、語音、可見的傾聽行為（visible listening behavior）與同步影片回應（synchronized video response）都共享同一個因果互動狀態（causal interaction state）。
- **潛在表示回寫歷史**：每個 160 ms 單元（160 ms unit）產生的音訊–影片潛在表示（synchronized speech and video latents）會被提交回歷史，使下一單元能同時依賴使用者近期行為與代理自身先前的表情。
- **避免級聯式視覺代理系統（cascaded visual-agent systems）的缺點**：不同於 ASR–LLM–TTS 輪替（ASR–LLM–TTS turns）的級聯流程，v0.2 的輸出無需經過獨立的語音辨識、語言模型與語音合成階段，從而降低模組間延遲與不同步風險。

##### 2. Thinker–Performer 分離的服務拓撲
為了在解析度從 192×336 提升到 640×368 的同時，仍維持約 200 ms 的模型端訊號到訊號延遲（model-side signal-to-signal latency），v0.2 將部署拓撲改為「單 GPU Thinker（思考器）＋多 GPU Performer（執行器）」：

- **Thinker（單 GPU 低延遲路徑）**
  - 負責串流感知（streaming perception）：音訊／影片編碼器（Encoder）。
  - 執行短語言／狀態 Transformer 傳遞（short language/state Transformer pass），建立生成快取（generation cache）。
  - 進行最終解碼（final decoding），將 Performer 回傳的潛在表示轉為可輸出的音訊與影片。
  - 由於語言與狀態計算量相對較小，保留在單一 GPU 上可確保控制路徑的延遲不會被高解析度生成拖慢。

- **Performer（多 GPU Ulysses 風格上下文並行群組）**
  - 負責昂貴的下一單元潛在生成（next-unit latent generation），特別是長高解析度潛在影片序列（long high-resolution latent video sequence）的去噪（denoising）。
  - 採用 Ulysses 通訊（Ulysses communication）進行序列分片（sequence sharding）：將長影片潛在序列切分到不同 Performer 運算秩（performer rank），透過 all-to-all／gather 交換必要資訊。
  - 每個 rank 擁有預先分片本地快取（pre-sharded local cache），Thinker 只需廣播 performer-compatible 的 K/V 切片，各 rank 寫入自己的本地快取即可。

##### 3. 為何能「保留延遲」
解析度提升會使潛在 token 數量大致隨像素增加，若仍在單一 GPU 上執行，去噪步驟的記憶體與計算成本會顯著上升，難以維持 25 FPS（每秒 25 幀）與 160 ms 單元的節奏。v0.2 的設計透過以下機制把額外成本侷限在視覺生成路徑：

1. **緊湊的 Thinker–Performer 邊界（thinker-performer boundary）**：Thinker 只把 K/V 條件化（K/V conditioning）傳給 Performer，語言序列本身不需要在 Performer 群組內部傳遞，減少跨 GPU 通訊量。
2. **視覺序列分片、音訊不分片**：長的影片潛在序列使用序列分片（sequence sharding）平行處理；音訊潛在序列（audio latent sequence）因 token 數少，直接在每個 rank 上生成，避免不必要的通訊開銷。
3. **預先分片快取**：K/V cache 已預先分片到各 rank，Thinker 廣播後各 rank 就地寫入，無需在生成過程中反覆進行全量 K/V 聚合。
4. **控制路徑與生成路徑分離**：語言／狀態更新與最終解碼留在單 GPU Thinker，視覺去噪的硬體擴展不會增加使用者可察覺延遲（user-visible delay）。

##### 4. 延遲預算拆解
根據論文描述，整體延遲目標可拆解為：

- **模型端訊號到訊號延遲**：約 200 ms，包含 Thinker 的感知、狀態更新、K/V 建構、Performer 的潛在生成，以及 Thinker 的最終解碼。
- **雙向網路延遲預算（bidirectional network budget）**：約 350 ms。
- **遠端互動延遲（remote interaction latency）**：約 550 ms。

這意味著每個 160 ms 的串流單元都必須在下一個單元到期前完成：接收當前使用者觀測、更新共享互動狀態、生成同步語音與影片潛在表示、解碼上一單元並輸出回應。這種嚴格的串流因果性（streaming causality）是方法設計的主要約束，也說明為何 v0.2 強調的是「保留延遲」而非單純追求離線渲染品質（offline rendering quality）。

#### 實驗數據解讀

由於提供的全文片段僅包含引言與部分服務拓撲說明，未包含第 4 節「實驗」的具體表格與數據，因此以下分析是根據摘要與方法論所做的合理推論，並指出尚待確認之處。

##### 1. 主要評量指標的預期組合
對於 Wan-Streamer v0.2 這類端到端音視覺互動模型，實驗通常會同時評量「延遲」與「品質」兩大維度：

- **延遲指標**
  - 模型端訊號到訊號延遲（model-side signal-to-signal latency）：目標約 200 ms。
  - 遠端互動延遲（remote interaction latency）：在 350 ms 雙向網路延遲預算下約 550 ms。
  - 每單元處理時間（per-unit processing time）：必須低於 160 ms 才能維持 25 FPS 的串流節奏。

- **視覺品質指標**
  - 解析度相關：640×368 相較於 192×336，像素數提升約 3.7 倍，理論上可顯著改善中景代理（mid-shot agents）的姿勢（posture）、凝視（gaze）、手部（hands）、鄰近物體（nearby objects）與局部場景佈局（local scene layout）的可辨識度。
  - 常見客觀指標可能包括 FID（Fréchet Inception Distance）、FVD（Fréchet Video Distance）、PSNR、SSIM 等，但論文未提供具體數值。
  - 由於強調「場景導向互動（scene-grounded interaction）」，也可能引入針對人臉、手部、視線方向或場景一致性的專項指標。

- **音視覺同步與互動指標**
  - 唇形同步（lip-sync）誤差。
  - 語音與影片動作之間的時間對齊。
  - 可見的傾聽行為（visible listening behavior）與回應時機（response timing）的主觀評分。

##### 2. 從方法論推論的實驗重點
v0.2 的實驗設計很可能聚焦於以下對照：

- **v0.1 vs. v0.2**：在相同模型端延遲預算下，比較 192×336 與 640×368 的視覺品質與互動可用性。
- **單 GPU Performer vs. 多 GPU Ulysses Performer**：驗證序列分片（sequence sharding）與 Ulysses 通訊是否能在不增加延遲的前提下支撐高解析度生成。
- **不同 Performer 群組大小**：觀察增加 GPU 數量對去噪延遲與通訊開銷的權衡。
- **網路預算敏感性**：在 350 ms 雙向網路延遲預算下，確認 550 ms 的遠端互動延遲是否穩定。

##### 3. 數據解讀的限制
目前可確認的數據僅有：

- 輸出解析度：192×336 → 640×368。
- 幀率：維持 25 FPS。
- 模型端延遲：維持約 200 ms。
- 總互動延遲：維持約 550 ms（含 350 ms 網路預算）。

至於客觀品質分數、使用者研究規模、訓練資料量、GPU 型號與數量、批次大小（batch size）、去噪步數等關鍵重現資訊，在提供的片段中均未出現。因此，對「解析度提升是否帶來顯著品質改善」的判斷，目前只能基於方法論與解析度差異進行定性推論，無法進行嚴格的量化比較。

#### 與現有研究的比較

##### 1. 相較於 Wan-Streamer v0.1
v0.2 與 v0.1 的關係是「保留延遲的升級（latency-preserving upgrade）」：

| 比較面向 | v0.1 | v0.2 |
|---|---|---|
| 端到端串流形式 | 原生串流（native-streaming）因果時間軸 | 維持不變 |
| 輸出解析度（output resolution） | 192×336 | 640×368 |
| 幀率 | 25 FPS | 25 FPS |
| 模型端延遲 | 約 200 ms | 約 200 ms |
| 總互動延遲 | 約 550 ms（含 350 ms 網路預算） | 約 550 ms |
| 服務拓撲 | Thinker 與 Performer 皆為單 GPU | Thinker 單 GPU，Performer 多 GPU Ulysses 上下文並行 |
| 視覺應用場景 | 特寫視訊通話構圖（close-up video-call framing） | 高保真特寫互動＋場景導向中景代理（scene-grounded mid-shot agents） |

簡言之，v0.2 在「不動建模形式、不動延遲預算」的前提下，透過服務拓撲重設計換取解析度提升，這是一種工程導向的系統級改進。

##### 2. 相較於級聯式數位人系統
許多現有的即時虛擬化身（real-time avatars）與音訊驅動人臉（audio-driven faces）系統採用 ASR–LLM–TTS 輪替（ASR–LLM–TTS turns）或類似的級聯流程。Wan-Streamer 系列的差異在於：

- **單一因果互動狀態**：感知與生成共享同一個 Transformer，避免模組間延遲累積。
- **同步多模態輸出**：文字、音訊、影片在同一時間軸上生成，減少語音與畫面不同步的問題。
- **可見的傾聽行為**：代理在「聽」的階段也能產生細微臉部與身體動作，而非僅在輪到自己時才反應。

##### 3. 相較於其他串流影片生成方法
因果推出方法（causal rollout methods）與串流影片生成（streaming video generation）技術提供了視覺合成的基礎，但它們通常專注於離線或低延遲單模態影片生成。Wan-Streamer v0.2 的獨特之處在於把這些技術整合到全雙工語音對話（full-duplex spoken dialogue）與互動式數位人（interactive digital humans）場景，並明確以 200 ms 模型端延遲與 550 ms 遠端互動延遲作為設計約束。

##### 4. 主要限制
- **解析度仍屬中低範圍**：640×368 雖然遠優於 192×336，但相較於 720p、1080p 或更高解析度的數位人應用仍有差距。
- **硬體需求增加**：Performer 需要多 GPU Ulysses 風格上下文並行群組，部署成本與能耗高於 v0.1。
- **Thinker 單 GPU 瓶頸**：雖然目前語言／狀態計算量較小，但未來若加入更長的上下文記憶或更複雜的推理，單 GPU Thinker 可能成為延遲瓶頸。
- **網路預算假設**：350 ms 雙向網路延遲預算在某些跨洲或行動網路場景可能過於樂觀。
- **未討論安全性與對齊**：全文未提及幻覺、不當內容、身份保護、隱私等互動式數位人必須面對的議題。
- **實驗細節不足**：缺乏客觀品質指標、使用者研究規模與訓練資料細節，難以與其他方法進行嚴格比較。

#### 未來研究方向

##### 1. 更高解析度與更廣視野
- 從 640×368 進一步提升至 720p、1080p 甚至更高，並支援全身（full-body）或多人場景。
- 結合可變解析度（adaptive resolution）技術，在頻寬或計算受限時自動降低解析度，在資源充足時提升細節。

##### 2. Thinker 的擴展與記憶機制
- 目前 Thinker 為單 GPU 低延遲路徑，未來可研究如何在不破壞延遲預算的前提下，加入長期記憶（long-term memory）、檢索增強生成（RAG）或更複雜的推理能力。
- 探索將 Thinker 也進行輕量化並行，或採用推測解碼（speculative decoding）進一步壓縮延遲。

##### 3. 音訊生成的平行化
- 目前音訊潛在序列（audio latent sequence）因 token 數少而未進行序列分片。若未來提升音訊品質（如高取樣率、多聲道、音樂或環境音），可能需要將音訊也納入 Ulysses 風格上下文並行，或設計專用的音訊並行策略。

##### 4. 網路與邊緣部署
- 降低雙向網路延遲預算（bidirectional network budget）對總互動延遲的影響，例如透過邊緣運算（edge computing）、模型壓縮、自適應位元率傳輸或預測性生成（predictive generation）。
- 研究在消費級 GPU 或甚至行動裝置上部署的可行性。

##### 5. 多代理與場景互動
- 將場景導向互動（scene-grounded interaction）擴展至多代理（multi-agent）環境，讓數位人不僅與使用者對話，也能與場景中的其他代理或實體物件互動。
- 結合 3D 場景表示（如 NeRF、Gaussian Splatting）提升空間一致性與遮擋處理能力。

##### 6. 安全性、對齊與評估
- 建立針對互動式數位人的安全對齊（safety alignment）機制，包括幻覺抑制、不當內容過濾、身份保護與隱私保護。
- 發展更貼近真實對話的評估協議，結合客觀指標與長時間、多輪的使用者研究（user studies），特別針對回應時機、傾聽行為與視覺可信度。

##### 7. 訓練資料與開放生態
- 建構並開放高品質的中景、多輪、同步音視覺對話資料集，降低後續研究的重現門檻。
- 探索半監督或自我對弈（self-play）訓練策略，以減少對昂貴真人互動資料的依賴。

## 論文問答

**Q1：Wan-Streamer v0.2 主要想解決什麼問題？**
A：Wan-Streamer v0.2 旨在解決 v0.1 輸出解析度僅有 192×336、視覺範圍受限的問題，因為這種低解析度只能清楚呈現特寫視訊通話構圖，卻讓身體姿勢、手部動作、鄰近物體與場景上下文變得難以辨識。為了讓互動式數位人從單純的臉部通話走向場景導向互動，v0.2 將輸出串流提升到 640×368，同時保留約 200 毫秒的模型端訊號到訊號延遲。這樣一來，模型就能在即時對話中維持可讀的身體語言與環境脈絡，而不破壞全雙工語音對話的節奏。

**Q2：為什麼不能直接沿用 v0.1 的架構來提升解析度？**
A：直接把解析度從 192×336 提升到 640×368 會讓潛在影片序列長度與去噪成本大幅增加，若仍使用 v0.1 的單 GPU Performer，下一單元潛在生成將超過 160 毫秒的串流處理單位預算，導致使用者可察覺延遲。串流因果性要求每個 160 毫秒單元都要完成感知、狀態更新、同步語音與影片潛在生成、解碼與輸出，因此單純放大解析度會違反這個硬性時序限制。為了在不增加延遲的前提下承擔更高解析度的計算，必須重新設計部署策略，把昂貴的視覺生成路徑分散到多 GPU 上。

**Q3：為什麼「保留延遲」與「提升解析度」同等重要？**
A：在即時音視覺互動中，低延遲是維持自然對話節奏的關鍵，一旦模型端回應延遲超過約 200 毫秒，使用者就會明顯感到卡頓，全雙工對話的流暢度也會被破壞。串流因果性進一步要求每個 160 毫秒單元都必須在固定時間內完成觀察處理、狀態更新與輸出生成，否則輸出會落後於互動節拍。因此 v0.2 把「保留延遲的解析度升級」當作核心目標，確保高畫質不會以犧牲即時性為代價。

**Q4：v0.2 的核心方法是什麼？**
A：v0.2 保留了 v0.1 的原生串流形式化，也就是把使用者與代理人的文字、音訊、影片放在同一條因果時間軸上，並由單一 Transformer 統一建模。在此基礎上，它把模型拆分為 Thinker 與 Performer：Thinker 維持單 GPU 低延遲路徑，負責串流感知、語言／狀態更新、生成快取建構與最終解碼；Performer 則改為多 GPU Ulysses 風格上下文並行群組，專門處理高解析度潛在影片去噪。Thinker 只把 Performer 相容的 K/V 切片廣播給各個運算秩，每個秩再寫入預先分片本地快取，從而把昂貴的視覺生成與延遲關鍵的控制路徑分離開來。

**Q5：v0.2 在服務拓撲上的關鍵創新是什麼？**
A：關鍵創新在於把延遲敏感的 Thinker 與可擴展的 Performer 明確分離，並用 Ulysses 風格的序列並行來處理長高解析度潛在影片序列。Thinker 仍然保持單 GPU，確保語言／狀態計算與快取建構不會被視覺生成拖累；Performer 群組則透過預先分片本地快取與 Ulysses all-to-all／gather 通訊，把去噪成本分散到多張 GPU。最重要的是，語言序列不需要在 Performer 群組內部傳遞，Thinker 只傳送 K/V 條件化資訊，這大幅壓縮了 Thinker–Performer 邊界上的通訊量。

**Q6：為什麼音訊潛在序列不進行序列分片？**
A：因為每個串流單元的音訊潛在序列 token 數量遠少於高解析度影片潛在序列，對其進行序列分片所帶來的通訊與同步開銷會超過計算收益。把音訊生成保留在不分片的路徑上，可以簡化系統設計，並確保語音與影片輸出保持同步。這樣一來，Performer 群組就能把額外的硬體資源集中在最昂貴的長高解析度潛在影片去噪路徑上，進一步鞏固延遲預算。

**Q7：v0.2 報告了哪些實驗結果？**
A：論文報告的核心結果是輸出解析度從 192×336 提升到 640×368，幀率維持 25 FPS，同時模型端訊號到訊號延遲仍約為 200 毫秒，含 350 毫秒雙向網路預算的遠端互動延遲仍約為 550 毫秒。視覺品質方面，v0.2 不僅提升特寫互動的細節，也支援場景導向的中景代理，使姿勢、凝視、手部、鄰近物體與局部場景佈局在對話中保持清晰可辨。實驗重點驗證了服務拓撲對延遲的影響，以及 Thinker–Performer 分離能否在不改變模型形式化的前提下吸收高解析度帶來的額外成本。

**Q8：v0.2 最重要的延遲結果是什麼，為什麼具有意義？**
A：最重要的延遲結果是即使輸出解析度大幅提升到 640×368，模型端延遲仍維持約 200 毫秒，總遠端互動延遲仍維持約 550 毫秒。這表示新增的大量視覺計算被多 GPU Ulysses 上下文並行有效吸收，沒有轉化為使用者可察覺延遲。該結果證明了端到端串流影片生成模型可以在對話級延遲預算內運作，為高解析度互動式數位人的實用部署提供了可行性。

**Q9：論文強調了哪些設計比較或消融分析？**
A：論文主要比較了 v0.1 的單 GPU Performer 與 v0.2 的多 GPU Ulysses 風格上下文並行 Performer，突顯後者如何在不增加延遲的情況下處理高解析度輸出。此外也強調了預先分片本地快取與僅以 K/V 條件化傳遞語言狀態的設計，說明這些機制如何減少群組內通訊。音訊潛在序列不進行序列分片、而影片潛在序列進行分片的對比，也展示了針對不同模態成本特性所做的最佳化取捨。

**Q10：v0.2 適合哪些實際應用場景？**
A：v0.2 適合需要高解析度、低延遲互動式數位人的場景，例如遠端客戶服務虛擬化身、線上教育輔導、虛擬陪伴、遠端協作與具身互動介面。中景構圖讓代理能展現身體姿勢、手部動作與環境中的物體，從單純的臉部通話擴展到場景導向的對話。由於延遲仍維持在對話可接受範圍，這些應用能保留自然的輪替與即時回應。

**Q11：在產品部署上需要考慮哪些因素？**
A：部署時至少需要一張 GPU 給 Thinker，以及多張 GPU 組成 Ulysses 上下文並行 Performer 群組，群組內需要高頻寬互連以支援 all-to-all／gather 通訊。網路方面需預留約 350 毫秒的雙向網路延遲預算，輸出則固定為 25 FPS 的 640×368 影片。此外，Thinker–Performer 邊界必須保持緊湊，避免在群組內傳遞長語言序列，否則會抵消並行化帶來的延遲優勢。

**Q12：v0.2 對互動式數位人領域可能帶來什麼影響？**
A：v0.2 證明端到端原生串流模型可以在提升解析度的同時不回到級聯式 ASR–LLM–TTS 流程，也無需犧牲即時性。它把即時虛擬化身從特寫臉部通話推向場景導向的中景代理，拓寬了數位人的表達與互動空間。其 Thinker–Performer 分離與 Ulysses 並行策略，也為未來多模態串流生成系統的硬體擴展提供了一個可參考的服務範本。

**Q13：v0.2 有哪些已知的限制？**
A：v0.2 主要聚焦於解析度升級與延遲保留，對於長時間對話中的長期視覺一致性、極複雜場景動態，以及超過 640×368 的更高解析度，論文並未深入探討。Thinker 仍維持單 GPU，若未來感知或語言／狀態模型持續放大，這條低延遲路徑可能成為新的瓶頸。此外，350 毫秒的雙向網路預算在全球廣域網路中未必總能滿足，限制了某些地區的部署彈性。

**Q14：v0.2 可能出現哪些失敗案例？**
A：在具有嚴重遮擋、快速動作或大量手部與物體的中景場景中，生成細節可能出現閃爍或與語音不同步的現象。當使用者頻繁打斷或快速切換話題時，因果狀態更新可能來不及完全反應，導致回應時機或視覺表情略微滯後。若實際網路延遲超過 350 毫秒，總遠端互動延遲也會突破約 550 毫秒的目標，影響對話自然度。

**Q15：未來可以朝哪些方向繼續發展？**
A：未來可以進一步提升解析度與幀率，同時維持相同的延遲預算，並加強長時間互動的視覺一致性與場景理解能力。針對 Thinker 的瓶頸，可以探索量化、蒸餾或更輕量的感知模組，以延續單 GPU 低延遲路徑的可行性。此外，也可將此架構擴展到多代理互動、三維空間場景，或設計更強的網路適應機制，讓高解析度即時數位人在全球多樣網路環境中都能穩定運作。

### 實作前置條件

**資料需求**
- 大量**場景導向對話影片**：中景構圖、包含上半身、手部、鄰近物體與局部場景佈局的連續對話片段。
- **全雙工語音對話資料**：包含重疊語音、傾聽行為、回應時機標註，避免訓練成傳統 ASR–LLM–TTS 輪替模式。
- **因果時間軸對齊資料**：使用者文字、音訊、影片與代理文字、音訊、影片需在同一時間軸上對齊，並以 160 ms 單元為基礎切分。
- 若為特定領域（客服、教學），需準備領域專屬微調資料。

**運算需求**
- **Thinker**：至少一張高效能 GPU，負責串流感知、語言／狀態 Transformer、K/V 快取建構與最終解碼。
- **Performer**：多 GPU 叢集，採用 **Ulysses 風格上下文並行** 來分擔 640×368 高解析度潛在影片去噪；GPU 間需具備高頻寬互連（如 NVLink / InfiniBand）以降低 all-to-all/gather 通訊開銷。
- 低延遲網路基礎設施：雙向網路延遲預算建議控制在約 350 ms 以內，才能維持約 550 ms 的遠端互動延遲。

**技術與人才需求**
- 熟悉**因果 Transformer**、**區塊因果注意力**與**串流生成**。
- 具備**分散式推理**與**序列分片**經驗，能調校 Ulysses 通訊與預先分片本地 K/V 快取。
- 熟悉即時音視訊傳輸（WebRTC、RTP）、低延遲解碼與前端渲染。
- 具備模型量化、編譯優化（如 TensorRT、vLLM、Triton）經驗者更佳。

### 實作步驟建議

1. **確認延遲預算與產品規格**  
   先定義目標延遲（模型端約 200 ms、遠端互動約 550 ms）、輸出解析度 640×368、幀率 25 FPS，以及支援的視覺構圖（中景代理）。將延遲拆解為感知、Thinker、Performer、解碼、網路與前端渲染各段。

2. **資料收集與前處理**  
   收集中景對話影片，確保包含清晰可辨的姿勢、凝視、手部、鄰近物體與場景上下文。建立因果時間軸，將使用者與代理的文字、音訊、影片對齊到 160 ms 單元，並標註傾聽行為與回應時機。

3. **模型訓練或微調**  
   以 Wan-Streamer v0.1 或 v0.2 為基礎，在自有資料上進行端到端微調。保持原生串流形式不變，重點加強中景場景導向互動、手部與姿態一致性，以及全雙工語音對話行為。

4. **部署 Thinker–Performer 拓撲**  
   - **Thinker** 部署於單 GPU，負責低延遲串流感知與語言／狀態更新。  
   - **Performer** 部署為多 GPU Ulysses 風格上下文並行群組，將長高解析度潛在影片序列分片去噪；音訊潛在序列因 token 數少，不進行序列分片。  
   - Thinker 廣播 performer 相容的 K/V 切片，各 Performer 運算秩寫入預先分片本地快取。

5. **優化通訊與快取**  
   測量 Thinker 到 Performer 的 K/V 條件化傳輸延遲，以及 Performer 群組內 Ulysses all-to-all/gather 的通訊量。調整分片數量、批次大小與快取配置，避免通訊成為瓶頸。

6. **整合即時音視訊管線**  
   透過 WebRTC 或自訂 RTP 管線接收使用者音視訊，將解碼後訊號送入 Thinker；將模型輸出的音訊與影片潛在表示即時解碼並回傳前端渲染。

7. **端到端延遲與品質驗證**  
   在真實網路條件下測量模型端訊號到訊號延遲與遠端互動延遲，同時評估視覺品質（姿勢、手部、場景清晰度）、語音同步性、回應時機與全雙工對話自然度。

8. **逐步上線與監控**  
   先從特定場景試點，收集使用者回饋，持續監控延遲抖動、GPU 記憶體用量與生成穩定性，再擴展到更多使用情境。

### 潛在風險與注意事項

| 風險 | 說明 | 因應建議 |
|---|---|---|
| **延遲抖動** | 高解析度去噪與 Ulysses 通訊可能導致單元處理時間超過 160 ms。 | 預留緩衝、動態調整去噪步數、使用高頻寬互連，並對 Performer 進行效能剖析。 |
| **GPU 記憶體不足** | 640×368 潛在影片序列長，K/V 快取與啟動值占用顯著增加。 | 採用預先分片本地快取、梯度檢查點、量化或稀疏注意力，必要時增加 Performer 運算秩。 |
| **音視訊不同步** | 音訊與影片潛在序列分開生成，若排程不當會造成嘴型與語音錯位。 | 在 160 ms 單元層級強制同步，使用共享時間戳與緩衝機制對齊輸出。 |
| **場景幻覺或身份漂移** | 中景構圖增加場景細節，模型可能生成不穩定的手部、物體或背景。 | 加強中景與手部資料、使用一致性損失、在產品介面加入安全遮罩或後製濾波。 |
| **網路預算超支** | 若雙向網路延遲超過 350 ms，總互動延遲將明顯惡化。 | 部署邊緣節點、使用 QoS 保障、對前後端進行延遲監控與自動降級（如暫時切回低解析度）。 |
| **隱私與合規** | 即時音視訊互動涉及敏感個人影像與語音。 | 落實端到端加密、資料最小化、在地化部署，並符合當地個資與 AI 監管要求。 |

### 與其他技術的整合建議

- **即時通訊層**：透過 **WebRTC** 或 **SRT** 傳輸使用者音視訊，並利用其 jitter buffer 與前向糾錯機制來穩定網路預算。  
- **現有客服或對話系統**：可將 Wan-Streamer v0.2 作為前端互動引擎，後端透過 API 與 CRM、知識庫或訂單系統連接，由 Thinker 的語言／狀態輸出觸發業務動作。  
- **TTS／ASR 備援**：雖然模型為端到端，但在網路極差或特定合規場景，可設計降級路徑，切換至傳統 ASR–LLM–TTS 輪替以維持基本對話。  
- **3D 渲染與虛擬化身前端**：將模型輸出的 640×368 影片串流直接嵌入網頁或 App；若需更高解析度，可結合超解析度後處理，但需評估是否會突破延遲預算。  
- **監控與 A/B 測試平台**：整合延遲指標、使用者滿意度與視覺品質評分，持續比較不同解析度、構圖與去噪步數的產品表現。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先理解「原生串流」與「端到端音視覺互動」的核心概念：這不是把 ASR、LLM、TTS、影片生成串接起來，而是讓一個模型在同一条因果時間軸上同時處理看、聽、說與表情動作。接著再聚焦為何提升解析度會讓延遲變困難，以及 Thinker–Performer 分工如何解決這個問題。

**AI 工程師**  
重點閱讀第 3 節的延遲保留部署拓撲：Thinker 為何保留在單 GPU、Performer 為何採用 Ulysses 風格上下文並行、K/V 快取如何預先分片、音訊潛在序列為何不進行序列分片。實作時請特別關注 all-to-all/gather 通訊量、160 ms 單元排程與音視訊同步。

**研究人員**  
可從「串流因果性」與「視覺品質之間的權衡」切入，思考在固定延遲預算下，如何進一步擴展解析度、幀率或互動長度。也可探討區塊因果注意力、全雙工語言行為建模，以及中景場景導向互動的評估指標設計。

**產品經理**  
請將技術規格轉譯為使用者體驗指標：約 550 ms 的遠端互動延遲意味著什麼樣的對話自然度？640×368 與中景構圖能解鎖哪些過去 192p 做不到的場景？同時要評估運算成本、網路需求與隱私合規，決定優先導入哪個使用情境。
