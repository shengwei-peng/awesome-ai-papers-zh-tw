## ⚡ TL;DR

現有評估僅看最終答案，無法定位深度研究智慧體軌跡中導致失敗的有害錯誤跨距。
本文建構 TELBench 基準，並提出 DRIFT 多智慧體稽核框架，追蹤驗證軌跡中的主張。
DRIFT 提升跨距級錯誤定位與首次錯誤準確率最高達三十個百分點，提供流程層級可靠性觀點。

## 摘要翻譯

深度研究智慧體（Deep-research agents）透過包含搜尋（Search）、工具使用（Tool use）、證據檢視（Evidence inspection）與答案合成（Answer synthesis）的長軌跡（Agent trajectories）來解決任務。基於最終答案的評估可顯示智慧體是否成功，但無法指出軌跡中哪些部分導致答案不可靠。我們研究深度研究智慧體的跨距級錯誤定位（Span-level error localization）。我們從兩個智慧體框架、三個骨幹模型（Backbone models）與三個基準測試（Benchmarks）中收集 2,790 條真實軌跡，將原始日誌（Raw logs）轉換為語義跨距（Semantic spans），並透過 LLM 輔助專家審查（LLM-assisted expert review）標註有害錯誤跨距（Harmful error spans）。基於這些標註，我們建構了 TELBench，這是一個包含 1,000 筆實例的基準測試，用於從正常探索（Normal exploration）、失敗搜尋（Failed searches）、暫時性假設（Tentative hypotheses）與無害雜訊（Harmless noise）中識別錯誤跨距。我們進一步提出 DRIFT，這是一個以主張為中心的稽核框架（Claim-centric auditing framework），其追蹤智慧體的主張（Claims）、檢查主張在軌跡證據（Trajectory evidence）中的支援情況，並標記因缺乏支援的主張（Unsupported claim）或衝突主張（Conflicting claim）而影響答案路徑（Answer path）的跨距。橫跨不同模型家族與稽核框架的實驗顯示，DRIFT 將跨距級錯誤定位與首次錯誤準確率（First-error accuracy）提升了高達 30 個百分點。本研究為深度研究智慧體的可靠性（Reliability）提供了流程層級觀點（Process-level view）。

### 核心貢獻（3～5點）
- 提出深度研究智慧體的跨距級錯誤定位研究議題，彌補僅評估最終答案的不足，為智慧體可靠性建立流程層級觀點。
- 建構 TELBench 基準測試：收錄 2,790 條真實軌跡並轉換為語義跨距，透過 LLM 輔助專家審查標註有害錯誤跨距，提供 1,000 筆可區分錯誤跨距與正常探索、失敗搜尋、暫時性假設及無害雜訊的實例。
- 提出 DRIFT 以主張為中心的稽核框架，透過追蹤智慧體主張、檢查軌跡證據支援，精準標記因缺乏支援或衝突主張而影響答案路徑的跨距。
- 跨模型家族與稽核框架的實驗顯示，DRIFT 在跨距級錯誤定位與首次錯誤準確率上較基線提升高達 30 個百分點。

### 適合對象
研究大型語言模型智慧體、自動化深度研究系統與可解釋 AI 的學者與工程師；特別適合關注智慧體可靠性評估、長軌跡錯誤分析、多智慧體稽核框架設計，以及需要診斷智慧體於搜尋與推理過程中特定失敗環節的研究者與開發者。

## 深度分析

#### 方法論解析

本研究的核心方法論建立在「深度研究智慧體（deep-research agents）的可靠性必須從流程層級（process-level view）審視」這一前提上。作者指出，智慧體軌跡（agent trajectories）並非單一的輸入輸出映射，而是一個逐步累積承諾（commitment）的決策過程；後續語義跨距（semantic spans）經常將早期主張（claim）視為確立事實（established facts）直接繼承，卻未經重新驗證（revalidation）。因此，有害錯誤往往並非出現在最終答案，而是源於早期某個缺乏支援的主張（unsupported claim）被後續流程關鍵性地（consequentially）採納。

為了精確定位這類錯誤，作者提出兩大支柱：**TELBench（跨距級軌跡錯誤定位基準測試）** 與 **DRIFT（以主張為中心的多智慧體稽核框架）**。

在資料建構端，研究團隊從 GAIA-val、XBench 與 BrowseComp-test 三個基準測試（benchmarks）中收集 2,790 條真實軌跡，涵蓋 GPT-5、Gemini-2.5-Pro 與 Claude-Sonnet-4.5 三種骨幹模型（backbone models），並在 MiroFlow 與 OAgent 兩種智慧體框架（agent frameworks）下執行。由於原始日誌（raw logs）過長、異質（heterogeneous）且充斥框架專屬的（framework-specific）雜訊，作者設計了語義分割流程：將原始步驟轉換為有序語義跨距（ordered semantic spans），每個跨距對應區域連貫的目標（如規劃、檢索、驗證、比較或最終化）。這種分析單元（analysis unit）比原始事件粗粒度，但足以保留定位首次有害承諾（first harmful commitment）所需的語境。接著透過 LLM 輔助專家審查（LLM-assisted expert review）與雙重人工標註（dual human annotation）產生高召回候選，再經聯合審查與難度分層，最終構成 1,000 筆帶有跨距級錯誤標籤（span-level error labels）的 TELBench。

在稽核方法端，DRIFT 採用以主張為中心的稽核框架（claim-centric auditing framework），由四個模組協同運作：

1. **ClaimKeeper（主張保管模組）**：讀取完整軌跡，維護主張分類帳（claim ledger），記錄每個主張何時被引入、何時變得關鍵性（consequential），以及哪些後續跨距依賴它。
2. **SupportSeeker（支援搜尋模組）**：檢視軌跡證據（trajectory evidence），將關鍵主張分類為直接支援（directly supported）、微弱支援（weakly supported）、缺乏支援（missing support）或被反駁（contradicted）。
3. **Specialist Auditors（專家稽核者）**：針對不同主張類型執行技能路由檢查（skill-routed checks），涵蓋實體主張（entity claims）、約束主張（constraint claims）、證據主張（evidence claims）、檢索主張（retrieval claims）、計算主張（compute claims）與流程主張（process claims）。
4. **DependencyTracer（依賴追溯模組）**：對缺乏支援或衝突主張（conflicting claims）進行反向追溯，區分真正有害的錯誤跨距（harmful error spans）與良性探索（benign exploration）、失敗搜尋（failed searches）、暫時性假設（tentative hypotheses）或無害雜訊（harmless noise）。

相較於直接對完整軌跡進行端到端評分，DRIFT 的創新在於將跨距級錯誤定位（span-level error localization）轉化為「主張生命週期管理」問題：透過顯式追蹤主張的支援狀態與依賴結構，辨識出影響答案路徑（answer path）的最早錯誤源頭。

#### 實驗數據解讀

實驗設計的規模與多樣性值得注意：2,790 條軌跡橫跨三個基準測試、三種骨幹模型與兩種智慧體框架，經語義分割後平均每条軌跡產生 11.95 個語義跨距。最終篩選出的 TELBench 包含 1,000 筆實例，並刻意控制跨距密度（span-density）與分層覆蓋（stratified coverage），確保資料同時包含錯誤承載案例（error-bearing case）與正常探索路徑。

從評估指標來看，本研究特別強調**首次錯誤準確率（first-error accuracy）**。這是一個比單純「是否找到任何錯誤」更嚴苛的指標，因為深度研究智慧體的錯誤具有傳播性：一旦早期出現未被挑戰的承諾，後續跨距會基於此前提進行推論，導致錯誤放大。因此，定位首次有害承諾的難度遠高於僅在最終答案處標註失敗。

根據摘要與內文所述，DRIFT 在跨距級錯誤定位與首次錯誤準確率上，相較於直接對完整上下文進行 LLM 提示（direct full-context LLM prompting）的基線，提升幅度高達 30 個百分點。這一差距具有重要方法論意涵：直接提示法容易出現三種不穩定行為——將良性探索誤判為錯誤、過度聚焦最終答案而忽略早期問題，以及遺漏那些看似無害卻被後續繼承的缺乏支援主張。DRIFT 透過顯式建構主張分類帳與依賴圖，有效緩解了這些問題。

此外，TELBench 的難度分級（Easy / Hard）與專家驗證機制，意味著這 30 個百分點的提升並非來自簡單案例的堆疊，而是在經過 LLM 輔助篩選與專家聯合審查的高品質標註上取得。這暗示在真實、冗長且雜訊密集的深度研究場景中，流程層級的可靠性（reliability）必須依賴結構化的主張追蹤，而非單純擴大模型上下文視窗。

#### 與現有研究的比較

在定位上，本研究明確區隔於兩類既有文獻：**結果導向評估（outcome-centered evaluation）** 與 **流程導向診斷（process-level diagnosis）**。

結果導向的基準測試如 GAIA、BrowseComp、WebArena、OSWorld 以及新近提出的 DeepResearch Bench、DRBench 等，雖然提升了任務真實性與評估細緻度（如基於評分標準的引用報告評估），但其核心仍聚焦最終任務完成度，無法回答「軌跡從何處開始變得不可靠」這一診斷問題。TELBench 則直接針對軌跡本身，要求模型從有序語義跨距中辨識有害錯誤，屬於流程層級觀點（process-level view）的典範轉移。

在流程診斷領域，ProcessBench、PRMBench、DeltaBench、VisualProcessBench、AgentProcessBench 與 TRAIL 等研究已開啟先例。然而，如 Table 1 所示，這些工作多針對數學推理（Math CoT）、長鏈推理（Long CoT）、VLM 推理或 API 工作流等較短、結構化程度較高的場景。其分析單元多為推理步驟（reasoning steps）或工具呼叫步驟（trace steps），平均長度約 7.56 至 13.43 步。相較之下，深度研究智慧體軌跡（DR Agent Trace）不僅平均長度達 11.95 個語義跨距，更混合了有用探索、微弱證據、失敗搜尋與有害錯誤，異質性與雜訊遠高於數學或程式軌跡。TELBench 的獨特價值在於提供**跨距級錯誤標籤（Span Err.）**、**最早有害跨距定位（First Err.）** 與**依賴感知錯誤傳播（dependency-aware error propagation）** 的評估維度。

DRIFT 與 MAST、AgentRx、CodeTracer 等故障定位工具相比，進一步將分析粒度從「步驟是否正確」提升為「主張是否被支援及其依賴後果」。這種以主張為中心的稽核框架（claim-centric auditing framework）更貼近深度研究的本質：智慧體並非單純執行工具鏈，而是在動態建構與修訂對世界狀態的信念。透過主張生命週期管理，DRIFT 能區分暫時性假設與被採納為確立事實的有害承諾，這是傳統步驟級評分難以做到的。

然而，本研究亦存在可討論的限制。首先，TELBench 最終僅收錄 1,000 筆實例，雖然來自 2,790 條軌跡的嚴格篩選，但相較於 PRMBench（6,216 筆）或 VisualProcessBench（2,866 筆）規模仍屬精緻型。其次，語義跨距的分割與錯誤標註高度依賴專家判斷，對於「何時構成承諾」與「何謂關鍵性影響」可能存在主觀邊界。第三，目前框架僅涵蓋 MiroFlow 與 OAgent 兩種智慧體框架，且未涉及多模態（multimodal）網頁導航或視覺證據，與 VisualProcessBench 的方向尚未交會。

#### 可重現性評估

從可重現性（reproducibility）角度檢視，本研究具備部分優勢，但也面臨實務挑戰。

在資料端，TELBench 的來源基準測試（GAIA-val、XBench、BrowseComp-test）均為公開資料集，這軌跡收集的基礎環境是透明的。然而，實際產生 2,790 條軌跡所依賴的骨幹模型——GPT-5、Gemini-2.5-Pro 與 Claude-Sonnet-4.5——均為商業前沿模型，其版本更新、溫度參數（temperature）與系統提示（system prompts）若未完整釋出，將導致軌跡難以完全復現。特別是 BrowseComp-test 經過降採樣（downsample）至 200 任務，其採樣隨機性亦需紀錄。

在語義分割與標註流程方面，原始日誌（raw logs）的正規化（normalization）涉及框架專屬的格式轉換，研究團隊雖以圖示說明管線，但原始碼、正則規則或解析腳本若未公開，其他研究者難以對新的智慧體框架套用相同分割邏輯。LLM 輔助專家審查階段使用了前沿 LLM 進行高召回候選標註，其提示工程（prompting）細節與專家審查指南（annotation guideline）是決定標註品質的關鍵，目前由片段內容無法確認是否伴隨釋出。

在方法端，DRIFT 作為多智慧體稽核框架（multi-agent auditing framework），其模組間的介面定義——例如 ClaimKeeper 如何從自由文本中提取主張、SupportSeeker 的證據檢索範圍、Specialist Auditors 的技能路由邏輯，以及 DependencyTracer 的反向傳播演算法——在提供的內容中僅有概念層級描述。若無開源實作與提示模板，重現 DRIFT 的 30 個百分點提升將存在相當門檻。

整體而言，本研究的可重現性處於「方法論可理解、資料部分可取得、細節實作待確認」的狀態。建議作者群釋出語義分割工具、主張提取提示、TELBench 標註準則，以及 DRIFT 的模組化原始碼，以強化社群對流程層級可靠性研究的複製與擴展。

#### 未來研究方向

基於本研究在跨距級錯誤定位（span-level error localization）與以主張為中心的稽核（claim-centric auditing）上打下的基礎，以下幾個方向具有高度潛力：

**1. 即時介入式稽核（Real-time Auditing and Intervention）**
目前的 DRIFT 屬於事後稽核（post-hoc auditing）。未來可將 ClaimKeeper 與 SupportSeeker 嵌入智慧體執行迴圈，在發現缺乏支援主張（missing support）或衝突主張（conflicting claims）時即時觸發重新檢索（retrieval）或重新規劃（replanning），從錯誤定位走向錯誤修復（error recovery）。

**2. 多模態深度研究軌跡診斷**
TELBench 目前聚焦於文本軌跡。未來可擴展至視覺語言模型（VLM）與網頁導航場景，將圖像證據、網頁截圖與 DOM 結構納入語義跨距，發展多模態版本的 DRIFT，與 VisualProcessBench 的研究軸線接軌。

**3. 因果錯誤傳播建模**
DependencyTracer 目前已能反向追溯依賴關係，但未來可引入更正式的因果推論框架（如結構化因果模型或反事實分析），量化「若某跨距的主張未被採納，最終答案將如何改變」，從而區分直接原因與間接雜訊。

**4. 自動化語義分割**
當前語義跨距的分割需經過正規化與專家設計規則。未來可訓練專門的分割模型，直接將異質原始日誌（heterogeneous raw logs）映射為語義跨距，降低建立新基準測試的門檻，並提升跨框架泛化能力。

**5. 跨框架與跨領域遷移**
僅在 MiroFlow 與 OAgent 上驗證的結果，其泛化性有待檢驗。未來應在更多智慧體框架（如 OpenAI 的 Deep Research、LangChain 代理、AutoGPT 等）以及科學文獻綜述、法律檢索、醫療診斷等垂直領域進行驗證，測試主張本體論（claim ontology）的領域適應性。

**6. 機率化證據強度評估**
目前的支援分類為四個離散類別（直接支援、微弱支援、缺乏支援、被反駁）。未來可發展連續型的證據強度分數（evidential strength score）或貝葉斯置信度更新機制，讓 SupportSeeker 的判斷更細緻，並能處理證據相互矛盾時的不確定性。

**7. 人機協同稽核系統**
對於高風險的深度研究任務，DRIFT 可作為人類專家的輔助工具，透過視覺化主張分類帳與依賴圖，幫助審查者快速聚焦可疑跨距。未來研究方向包括設計互動式介面，讓人類專家能夠修正或確認 ClaimKeeper 提取的主張，形成迭代式人機迴路（human-in-the-loop）。

這些方向共同指向一個願景：讓深度研究智慧體的可靠性不再只是結果的賭注，而是每一步主張都可被追蹤、驗證與解釋的流程。

## 論文問答

**Q1：為什麼僅評估深度研究智慧體的最終答案是不足的？這樣的評估方式會遺漏哪些關鍵資訊？**

A：僅評估最終答案只能告訴我們智慧體是否成功完成任務，但無法揭示軌跡中哪個部分導致了結果不可靠。在深度研究智慧體的長軌跡中，後續跨距經常會將早期提出的主張當作確立事實來重複使用，因此真正有害的步驟往往不是最終答案本身，而是早期未經重新驗證的錯誤承諾。若缺乏流程層級的診斷，我們就無法定位首次出現的關鍵性錯誤，也難以理解錯誤是如何在後續步驟中傳播並影響最終結論的。

**Q2：現有的流程層級評估基準測試（如 ProcessBench、AgentProcessBench 等）在處理深度研究軌跡時存在哪些主要限制？**

A：現有的流程層級基準測試大多針對數學推理、視覺語言模型推理或程式碼追蹤等較短且結構化的場景設計，難以應對深度研究軌跡的長度與雜訊。深度研究軌跡混合了有用的探索、微弱的證據、失敗的搜尋以及有害的錯誤，這些異質性內容使得單純的步驟級錯誤識別不足以捕捉問題根源。相較之下，TELBench 專注於從有序語義跨距中定位有害錯誤，並強調最早有害跨距的定位與依賴感知錯誤傳播，更貼近真實深度研究智慧體的複雜決策過程。

**Q3：為什麼直接要求大型語言模型在完整軌跡中找出錯誤是不穩定且不可靠的？**

A：直接對完整上下文進行提示時，大型語言模型容易將良性探索誤判為錯誤，或是過度聚焦於最終答案而忽略早期問題。這種方法經常遺漏那些早期提出、缺乏支援卻在後續被視為確立事實的主張，因為模型難以在長且異質的原始日誌中維持對主張演變的追蹤。此外，原始日誌往往過於冗長且包含框架專屬的雜訊，直接分析容易導致不一致的判斷，無法精準定位首次變得關鍵的有害承諾。

**Q4：TELBench 的資料建構流程包含哪些關鍵階段，為何要將原始日誌轉換為語義跨距？**

A：TELBench 的建構流程涵蓋軌跡收集、日誌正規化、語義跨距分割、LLM 輔助的候選標註以及專家驗證的錯誤標註。原始日誌包含工具重試、使用記錄、訊息包裝器等低階框架專屬產物，過於冗長且異質，不適合直接比較或分析；因此研究團隊將其轉換為語義跨距，使每個跨距對應圍繞局部連貫目標的連續執行片段。語義跨距作為分析單元，比原始事件更粗粒度但仍足夠精確，能夠有效定位首次有害承諾，同時兼顧跨框架的一致性與可解釋性。

**Q5：DRIFT 框架的核心設計理念是什麼？它與獨立為每個跨距打分的方法有何根本差異？**

A：DRIFT 採用以主張為中心的多智慧體稽核設計，核心在於追蹤智慧體在整個軌跡中形成並使用的主張，而非孤立地評分個別跨距。該框架透過 ClaimKeeper 維護主張分類帳，記錄每個主張的引入時機、關鍵性轉變以及後續依賴它的跨距，並由 SupportSeeker 檢視主張是否被軌跡證據直接支援、微弱支援、缺乏支援或被反駁。這種設計能夠揭露主張之間的依賴結構與支援狀態，從而區分真正有害的錯誤與無害的雜訊或良性探索，這是獨立打分方法無法做到的。

**Q6：DRIFT 中的 Specialist Auditors 與 DependencyTracer 分別扮演什麼角色，它們如何協同運作以提升錯誤定位的準確性？**

A：Specialist Auditors 負責針對不同類型的主張執行技能路由檢查，涵蓋實體、約束、證據、檢索、計算與流程等類別，確保各領域的特定錯誤模式能被精準識別。DependencyTracer 則進一步回溯缺乏支援或相互衝突的主張，追溯它們在軌跡中的依賴鏈，以區分錯誤跨距與非錯誤跨距。兩者協同運作時，Specialist Auditors 提供多維度的主張驗證，DependencyTracer 則將這些驗證結果映射到時間軸上的依賴關係，從而精準標記出影響答案路徑的最早有害跨距。

**Q7：TELBench 的數據規模與組成為何？它與現有其他基準測試相比有何獨特之處？**

A：TELBench 包含 1,000 個實例，源自 2,790 條真實深度研究智慧體軌跡，這些軌跡來自兩個智慧體框架、三個骨幹模型與三個公開基準測試，經過語義跨距轉換與專家驗證。與現有基準相比，TELBench 專注於深度研究智慧體軌跡的跨距級錯誤標註，並要求模型定位最早有害跨距與理解依賴感知的錯誤傳播。其平均長度達到 11.95 個跨距，遠超數學推理或工具使用追蹤的規模，更能反映真實世界中長程、雜訊交錯的研究決策過程。

**Q8：DRIFT 在跨距級錯誤定位與首次錯誤準確率上達成了什麼樣的效能提升？這些結果帶來什麼啟示？**

A：實驗結果顯示，DRIFT 在跨距級錯誤定位與首次錯誤準確率上，相較於直接完整上下文提示的大型語言模型方法，提升了高達 30 個百分點。這項顯著進步表明，單純依賴端到端提示難以處理長軌跡中的複雜依賴與主張演變，而明確建模主張支援與依賴結構是解決問題的關鍵。此結果也驗證了流程層級稽核的價值：透過追蹤主張的生命週期，稽核框架能夠更穩定地識別出那些看似無害、實則對最終答案產生決定性影響的早期錯誤。

**Q9：研究團隊在資料收集階段如何確保 TELBench 的任務多樣性與模型覆蓋率？他們採取了哪些措施避免資料偏差？**

A：研究團隊從 GAIA-val、XBench 與 BrowseComp-test 三個公開基準測試收集任務，並刻意將 BrowseComp 下採樣至 200 個任務以避免其主導整個語料庫，最終形成 465 個任務。他們使用 GPT-5、Gemini-2.5-Pro 與 Claude-Sonnet-4.5 三個前沿骨幹模型，並在 MiroFlow 與 OAgent 兩個代表性框架下執行，確保軌跡來源的多樣性。此外，透過跨距密度控制與分層覆蓋策略，團隊進一步平衡了錯誤承載案例與難易度分佈，使基準測試能夠廣泛且公平地評估不同模型與方法的錯誤定位能力。

**Q10：在實際應用中，TELBench 與 DRIFT 可如何協助開發者診斷與改進深度研究智慧體的可靠性？**

A：TELBench 提供了一個標準化的評估場景，讓開發者能夠系統性地測試其智慧體在長軌跡中定位有害錯誤的能力，而不再僅憑最終答案的成敗來判斷系統優劣。DRIFT 則可作為稽核工具整合至開發流程中，自動追蹤智慧體產生的主張並檢視其支援狀態，及早標記出缺乏證據或相互衝突的承諾。透過結合這兩者，開發團隊能夠從流程層級理解智慧體的失敗模式，針對性地強化特定環節的驗證機制，從而提升整體系統在複雜研究任務中的可信度。

**Q11：若將 DRIFT 的稽核機制部署為產品中的即時監控系統，可能會面臨哪些工程與使用者體驗上的考量？**

A：將 DRIFT 部署為即時監控系統時，首先需考量其多模組架構帶來的計算延遲與成本，因為 ClaimKeeper、SupportSeeker 與 Specialist Auditors 需要對長軌跡進行多次推理與檢索。其次，系統必須設計清晰的可視化介面，將主張分類帳、支援狀態與依賴鏈以直觀方式呈現給使用者，否則複雜的稽核資訊可能反而造成理解負擔。此外，如何在不干擾智慧體正常探索流程的前提下，適時介入並提示潛在的錯誤承諾，也是產品設計上需要仔細權衡互動模式與信任邊界的重要課題。

**Q12：這項研究對深度研究智慧體乃至更廣泛的自主智慧體領域可能產生什麼樣的長遠影響？**

A：這項研究推動了從結果導向評估轉向流程層級可靠性分析的典範轉移，為自主智慧體的可解釋性與可稽核性建立了新的方法論基礎。透過強調主張追蹤與依賴感知錯誤定位，它為未來的智慧體設計提供了明確的診斷語言，使開發者能夠建構具備自我糾錯與透明決策能力的系統。在更廣泛的層面上，這種以主張為中心的稽核思維也可延伸至法律分析、醫療診斷輔助與科學文獻綜合等高風險領域，促進人類對複雜 AI 決策過程的信任與監督。

**Q13：這項研究在資料收集與標註方法上存在哪些已知的限制或潛在偏差？**

A：儘管研究團隊採用了雙重人工標註與 LLM 輔助專家審查，但標註過程仍可能受到專家主觀判斷與 LLM 先驗偏好的影響，特別是在區分暫時性假設與有害錯誤跨距的邊界時。此外，軌跡來源雖涵蓋多個框架與模型，但總數 2,790 條軌跡相對於無限可能的任務空間仍屬有限，且所有實驗均基於當時可取得的前沿模型，未來模型行為的演變可能使部分標註模式過時。語義跨距的分割方式雖然提升了可解釋性，但也可能將某些連續的錯誤決策拆散或合併，從而影響錯誤定位的粒度與精確度。

**Q14：DRIFT 框架在哪些類型的錯誤或軌跡結構上可能出現失敗或效能下降的情況？**

A：DRIFT 特別依賴主張的明確提取與證據的顯式呈現，因此當智慧體以隱喻、類比或高度壓縮的方式進行推理，而未將中間承諾清楚表達於軌跡文字中時，ClaimKeeper 與 SupportSeeker 可能遺漏關鍵主張。此外，若錯誤源自多個微小偏差逐步累積，而非單一缺乏支援或衝突的主張，DependencyTracer 可能難以回溯到單一決定性的首次有害跨距。在面對極長且高度循環的軌跡時，主張分類帳的維護成本與依賴鏈的複雜度也可能導致稽核準確率下降。

**Q15：基於這項研究的成果，未來有哪些值得探索的方向可以進一步提升軌跡錯誤定位的精細度與實用性？**

A：未來研究可探索動態跨距分割機制，根據主張的生成與消滅自動調整分析單元的粒度，以捕捉更細緻的錯誤轉折點。另一個方向是將 DRIFT 的稽核框架與智慧體的即時決策迴路結合，發展具備線上自我糾錯能力的深度研究智慧體，在錯誤承諾變得關鍵之前即時重新驗證。此外，擴展至多模態軌跡稽核，整合圖表、影像與網頁截圖等證據來源，並引入人機協作的互動式稽核介面，將有助於在更複雜的真實世界場景中實現全面且可信的流程層級可靠性評估。

## 實務應用指南

### 適用場景

1. **企業級知識管理與研究自動化**：當深度研究智慧體自動生成產業分析報告時，用於定位哪一段搜尋或推論導致最終結論不可靠，避免將錯誤見解寫入決策摘要。
2. **金融合規與投研稽核**：在自動化財報分析或盡職調查流程中，稽核智慧體軌跡，找出首次有害承諾（如錯誤解讀財務數據）並標記後續依賴該錯誤的語義跨距，以符合內控與監管要求。
3. **醫療文獻綜述與臨床決策支援**：追蹤智慧體在長篇醫學文獻檢索中形成的實體主張與證據主張，確保每個中間候選結論都有軌跡證據支援，降低誤導性醫療建議的風險。
4. **法律研究與判例分析**：用於檢視法律 AI 在檢索判例、比對法條約束主張時，是否在某個語義跨距產生缺乏支援的主張，進而影響最終法律意見的可靠性。
5. **教育與學術寫作輔助**：協助學生或研究者審查自動化研究助理的推理流程，區分良性探索與有害錯誤跨距，提升學術寫作與引用論證的嚴謹度。

### 實作前置條件

- **資料**：需要收集真實的智慧體軌跡原始日誌（至少數百到數千條），包含搜尋、工具使用、證據檢視與答案合成的完整記錄。若無現成資料，需先建置可記錄跨距級事件的代理框架，並確保涵蓋成功與失敗案例。
- **運算**：需具備呼叫前沿骨幹模型（如 GPT-5、Claude-Sonnet-4.5、Gemini-2.5-Pro）的 API 配額，用於語義跨距分割、LLM 輔助專家審查與 DRIFT 多智慧體稽核流程。建議準備可處理長上下文（100K+ tokens）的運算環境，以容納完整軌跡。
- **技能**：團隊需具備提示工程能力、基礎的代理框架開發經驗，以及領域專家進行雙重人工標註與主張分類帳設計。此外，需熟悉評估指標如首次錯誤準確率與跨距級 F1，以量化稽核成效。

### 實作步驟建議

1. **軌跡收集與標準化**：從現有深度研究基準測試（如 GAIA、XBench、BrowseComp）或內部系統匯出原始日誌，去除框架專屬的雜訊（重試記錄、訊息包裝器、排程痕跡），統一為可讀的執行序列。
2. **語義跨距分割**：將清理後的軌跡轉換為有序語義跨距，每個跨距對應局部一致的目標（如規劃、檢索、驗證、比對、定稿）。控制跨距密度，避免過細導致雜訊過多，或過粗導致錯誤定位失準。
3. **建構主張分類帳**：部署 ClaimKeeper 模組，讀取全軌跡並記錄每個主張的引入時機、何時變得關鍵性，以及後續哪些跨距依賴該主張，形成可追蹤的承諾演化圖。
4. **支援狀態檢查與專家稽核**：透過 SupportSeeker 與 Specialist Auditors 對實體主張、約束主張、證據主張等進行技能路由檢查，標記直接支援、微弱支援、缺乏支援或被反駁的狀態。
5. **錯誤定位與回溯**：使用 DependencyTracer 對缺乏支援或衝突主張進行回溯，區分有害錯誤跨距與無害雜訊，輸出首次有害承諾位置及其影響的答案路徑。
6. **持續迭代與產品化**：將稽核結果回饋至代理框架的規劃模組，建立「偵測—修正—再驗證」的閉環，並針對特定領域微調跨距級錯誤定位模型，逐步提升首次錯誤準確率。

### 潛在風險與注意事項

- **語義跨距邊界模糊**：若分割粒度不一致，可能導致錯誤定位在錯誤的抽象層級。建議制定明確的跨距分割規則（如以「目標轉換」或「工具呼叫意圖變更」為界），並由領域專家抽樣驗證。
- **主張抽取遺漏**：ClaimKeeper 可能遺漏隱含主張（如預設假設），導致後續依賴追溯不完整。可透過增加「流程主張」與「暫時性假設」的顯式標註來緩解。
- **過度稽核導致延遲**：DRIFT 的多智慧體流程（ClaimKeeper → SupportSeeker → Specialist Auditors → DependencyTracer）會增加推理延遲。在產品環境中，可對高風險跨距啟用完整稽核，對低風險跨距採用輕量級啟發式檢查。
- **領域適配成本**：TELBench 主要涵蓋開放域研究任務，直接遷移至封閉企業知識庫時，主張類型與證據格式可能不同。需預留領域適配的標註預算，重新設計專家稽核者的檢查清單。

### 與其他技術的整合建議

- **與現有代理框架整合**：可將 DRIFT 作為外掛稽核層，嵌入 LangChain、AutoGen 或自研框架，在每次工具呼叫或答案合成後觸發 SupportSeeker 檢查，實現即時流程監控。
- **與 RAG 系統整合**：在檢索增強生成流程中，將 DRIFT 的證據主張檢查與向量資料庫的引用驗證結合，確保檢索到的文件確實支援智慧體的實體主張，而非僅有語意相似。
- **與可觀測性平台整合**：將跨距級錯誤定位結果輸出至 OpenTelemetry 或 LangSmith 等追蹤系統，讓維運人員能在時間軸上直接檢視首次錯誤準確率與主張依賴圖，縮短除錯時間。
- **與人機協作介面整合**：在需要人類專家把關的場景（如醫療、法律），將 DRIFT 標記的有害錯誤跨距以視覺化方式呈現於審查介面，讓專家快速聚焦關鍵決策點，而非閱讀完整原始日誌。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從「適用場景」與「實作步驟建議」著手，理解深度研究智慧體為何會在長軌跡中累積錯誤；接著對照圖一的資料整理流程，建立「語義跨距」與「主張」的基本直覺，無需深入 DRIFT 的模組細節即可掌握核心概念。
- **AI 工程師**：請重點閱讀第三節的資料整理流程與 DRIFT 架構，關注語義跨距分割的實作細節、ClaimKeeper 與 DependencyTracer 的提示設計，以及 TELBench 的評估維度；思考如何將多智慧體稽核流程最佳化為低延遲的產品級服務。
- **研究人員**：建議深入分析跨距級錯誤定位與現有流程層級基準測試（如 ProcessBench、AgentProcessBench）的差異，特別是本文對「首次有害承諾」與「主張依賴傳播」的定義；可進一步探索如何將主張分類帳擴展至多模態軌跡或更長的上下文窗口。
- **產品經理**：請聚焦「適用場景」與「潛在風險與注意事項」，評估導入跨距級錯誤定位對現有產品可靠性的提升幅度與實作成本；將 DRIFT 視為一種「流程可解釋性」功能，規劃與合規、稽核、人機協作產品路線圖的結合點。
