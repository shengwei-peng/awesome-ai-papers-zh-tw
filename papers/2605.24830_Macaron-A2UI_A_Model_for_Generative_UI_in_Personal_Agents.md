## 摘要翻譯

隨著個人助理（personal agents）逐漸演進以處理複雜且以使用者為中心的任務，靜態純文字對話（static plain-text chat）正迅速成為瓶頸。生成式使用者介面（Generative UI）應運而生，作為必要的新介面層，能夠即時從互動情境（interaction context）中動態合成合適的控制項、選項與狀態（controls, options, and state）。我們提出 Macaron-A2UI，一個用於個人助理的生成式使用者介面模型。我們的目標是超越純文字互動，使助理能夠同時生成自然語言（natural language）以及輕量級、可執行的使用者介面動作（lightweight executable UI actions），以支援資訊收集（information collection）、偏好細化（preference refinement）、確認（confirmation）與多目標組織（multi-goal organization）等任務。我們從異質對話來源（heterogeneous dialogue sources）建構大規模生成式使用者介面語料庫（Generative UI corpus），提出 A2UI-Bench 作為控制式評估基準（controlled evaluation benchmark），並採用基於 LoRA（Low-Rank Adaptation）的參數高效（parameter-efficient）監督式微調（supervised fine-tuning，SFT），接續進行獎勵驅動的強化學習（reward-driven reinforcement learning）以訓練 30B、235B 與 754B 參數模型。最佳的 Macaron-A2UI 模型在無明確綱要提示（schema hints）的條件下，於 A2UI-Bench 上整體達到 75.6 分，超越最強的完整綱要前沿基線（full-schema frontier baseline）。我們釋出模型、評測基準與評估協定（evaluation protocol），以支援未來針對個人助理之生成式使用者介面的研究。

### 核心貢獻（3～5點）
- 建構大規模生成式使用者介面語料庫：從異質對話來源彙整資料，建立生成式介面研究所需的訓練資源。
- 提出控制式評估基準：推出 A2UI-Bench 與對應評估協定，提供標準化的生成式介面評測框架。
- 參數高效的模型訓練：採用基於 LoRA 的監督式微調，接續以獎勵驅動的強化學習，成功訓練 30B、235B 與 754B 參數模型。
- 效能超越最強基線：最佳 Macaron-A2UI 模型在無綱要提示下於 A2UI-Bench 達到 75.6 分，勝過完整綱要前沿基線。
- 開源釋出研究資源：公開模型、A2UI-Bench 評測基準與評估協定，支援未來個人助理生成式介面研究。

### 適合對象
適合人機互動、對話系統與自然語言處理領域的研究者，以及關注個人助理、智慧介面與生成式使用者介面應用的開發者與設計師。特別推薦給探索可執行介面、結構化互動與參數高效微調之跨領域研究團隊參考。

## 深度分析

#### 方法論解析

本研究將 Generative UI（生成式使用者介面）形式化為一個端到端的學習問題。給定 System instruction（系統指令）、Dialogue history（對話歷史）與當前 User message（使用者訊息），模型需輸出 Unified response（統一回覆），同時包含 Natural language（自然語言）與可執行的 A2UI（A2UI）訊息序列。此處的 A2UI（A2UI）並非傳統的 HTML、JavaScript 或框架特定之 Code generation（程式碼生成），而是一種宣告式協議（declarative protocol）：模型僅輸出結構化訊息，由客戶端透過受信任元件目錄（trusted component catalog）進行渲染。這種分離式設計提升了安全性、跨環境可攜性（portability），並使自動驗證與 Protocol validity（協議有效性）檢查成為可能。

在資料層面，作者提出可擴展的資料建構管線，將四種 Heterogeneous dialogue sources（異質對話來源）轉換為規模超過 14,000 樣本的 Generative UI corpus（生成式使用者介面語料庫）。該管線採用混合規則與大型語言模型的方法（hybrid rule-and-LLM approach），並輔以確定性驗證（deterministic validation）確保渲染可行性（renderability）。這解決了過往缺乏大規模 UI-grounded dialogue supervision（基於使用者介面的對話監督）之痛點，並透過 rule-based repair（規則式修復）維持資料品質。

訓練策略採用 Parameter-efficient（參數高效）的兩階段配方。第一階段為 LoRA（LoRA（低秩適應））-based Supervised fine-tuning (SFT)（監督式微調），在 Schema hints（綱要提示）極小化的條件下建立文字與介面的對齊（text-UI grounding）；第二階段則引入 Reward-driven reinforcement learning（獎勵驅動的強化學習），針對可執行互動品質進行最佳化。此 minimal-prompt regime（極少提示機制）旨在迫使模型直接內化（internalize）UI 生成能力，而非僅在推論時依賴冗長的結構描述。實驗涵蓋 30B / 235B / 754B models（30B / 235B / 754B 參數模型），驗證了該管線在不同規模下的有效性。

評估方面，研究團隊建立 A2UI-Bench（A2UI-Bench），設計三層 Evaluation protocol（評估協定）：Protocol validity（協議有效性）檢驗動作序列的語法與可渲染性；Interaction quality（互動品質）或稱 task progression 衡量任務推進效率；以及視覺與使用者體驗指標。這種分層設計首次將「協議是否合法」與「互動是否好用」解耦（decouple），提供了更細緻的診斷能力。

#### 實驗數據解讀

實驗核心結果顯示，最佳的 Macaron-A2UI（Macaron-A2UI）模型在 A2UI-Bench（A2UI-Bench）上達到 75.6 的總體分數（overall score）。此數據的關鍵意義在於：該模型是在沒有 Explicit schema hints（明確綱要提示）的條件下達成此成績，並且超越了最強的 Full-schema frontier baseline（完整綱要前沿基線）。這直接證明了 Executable UI actions（可執行的使用者介面動作）的生成能力可以被成功內化至模型參數中，而不需在推論階段注入冗長的協議描述。

從評估架構來看，三層指標的設計使研究者能區分不同類型的失敗模式。高 Protocol validity（協議有效性）代表模型理解 A2UI（A2UI）的結構限制與語法規則；高 Interaction quality（互動品質）則反映模型在 Information collection（資訊收集）、Preference refinement（偏好細化）、Confirmation（確認）與 Multi-goal organization（多目標組織）等任務上的策略適切性。總體分數 75.6 暗示模型在「正確生成」與「有效互動」之間取得了良好平衡。

此外，跨 30B / 235B / 754B models（30B / 235B / 754B 參數模型）的實驗設計，隱含了規模擴展性（scaling）的分析。雖然摘要未詳細披露各規模的個別分數，但強調「pipeline's effectiveness across model scales」，意味著該兩階段訓練配方具備一定的規模泛化性。然而，14,000 樣本對於 754B 參數模型而言屬於相對小規模的語料（small-scale fine-tuning），卻仍能達到超越全綱要基線的表現，這側面說明了資料品質與 RL 階段獎勵訊號設計的關鍵性——模型並非單純記憶大量樣本，而是學習到了可泛化的互動策略。

#### 與現有研究的比較

相較於傳統的 Static plain-text chat（靜態純文字對話），本研究明確指出純文字在 Structured interaction（結構化互動）情境下的侷限：長篇文字回覆會增加 Cognitive load（認知負荷），而 Lightweight structured interfaces（輕量級結構化介面）能顯著提升多回合任務的效率。這與過往 Human-computer interaction（人機互動）文獻中強調 Flexible and personalized interfaces（靈活且個人化的介面）之理念一脈相承，但本研究首次將其系統性地形式化為大規模語言模型的學習問題。

與當前主流的 Code generation（程式碼生成）或 text-to-UI 研究（如生成 HTML、JavaScript）相比，Macaron-A2UI（Macaron-A2UI）選擇了截然不同的技術路徑。現有許多研究聚焦於無限制的網頁或程式碼合成（unconstrained webpage or code synthesis），而本研究則專注於固定宣告式協議下的回合級結構化生成。A2UI（A2UI）的宣告式協議設計避免了直接生成可執行程式碼所帶來的安全風險與跨平台渲染不一致問題，使 Agent-side UI generation（代理端使用者介面生成）更為安全且可驗證。

另一條相關研究軸線是現有數位介面的操作代理，例如 WorldGUI、GUI-Actor、OS-Genesis 等。這些研究屬於「在既有介面上執行動作」（action execution over an existing interface），而 Macaron-A2UI（Macaron-A2UI）則屬於「由助理端主動創造介面」（assistant-side Generative UI）。兩者互補：前者解決「如何操作現有軟體」，後者解決「當純文字不足時，如何即時生成合適的 Interaction loop（互動迴圈）表面」。

相較於 Leviathan et al. (2025)、Chen et al. (2025a) 與 AlignUI (Liu et al., 2026) 等探索介面生成的工作，本研究的獨特貢獻在於提出 Unified formulation（統一形式化）——將 Natural language（自然語言）與 Executable UI actions（可執行的使用者介面動作）統一為單一模型輸出，並提供大規模語料、控制式評估基準，以及無需 Schema hints（綱要提示）即可內化能力的實證證據。這填補了過往研究在「大規模 UI-grounded dialogue supervision（基於使用者介面的對話監督）」、「區分 Protocol validity（協議有效性）與 Interaction quality（互動品質）的評估基準」，以及「模型能否在不依賴長綱要提示下內化生成能力」等三方面的空白。

#### 可重現性評估

本研究在可重現性方面做出了明確承諾：作者聲明將釋出模型權重、A2UI-Bench（A2UI-Bench）評估基準以及完整的 Evaluation protocol（評估協定）。這對 Generative UI（生成式使用者介面）領域的後續研究至關重要，因為該領域長期缺乏標準化的資料集與評測框架。

資料建構方法的透明度亦值得肯定。研究詳細說明採用混合規則與 LLM 的方法（hybrid rule-and-LLM approach）搭配確定性驗證（deterministic validation），從 Heterogeneous dialogue sources（異質對話來源）產出超過 14,000 樣本的 Generative UI corpus（生成式使用者介面語料庫）。這種結合 LLM 自動標註與規則修復（rule-based repair）的管線，具備一定程度的可複製性。此外，使用公開可參照的 A2UI Project（A2UI Project, 2025）作為協議基礎，降低了因私有規格造成的重現門檻。

訓練細節方面，論文明確指出使用 LoRA（LoRA（低秩適應））-based SFT 與 Reward-driven reinforcement learning（獎勵驅動的強化學習），並在 30B / 235B / 754B models（30B / 235B / 754B 參數模型）上進行實驗。這種 Parameter-efficient（參數高效）設定意味著即使運算資源有限的研究者，也能透過 LoRA（LoRA（低秩適應））技術複現類似的訓練流程。

然而，在提供的文本脈絡中，尚未見到具體的儲存庫網址、授權條款或資料集下載連結。此外，14,000 樣本的規模雖足以驗證概念，但對於訓練 754B 參數模型而言仍屬精緻小樣本微調（small-scale fine-tuning）範疇，後續研究者在重現時需特別注意資料品質控制與 LoRA（LoRA（低秩適應））配置的超參數調校，因為小語料在大模型上的訓練穩定性往往對這些細節極為敏感。

#### 未來研究方向

第一，語料規模的擴充是當務之急。當前 14,000 樣本的 Generative UI corpus（生成式使用者介面語料庫）雖已屬該領域先驅，但相較於一般對話模型動輒百萬級的監督資料，規模仍顯不足。未來可探索自動化資料合成管線，例如結合 TaskCraft 或 OS-Genesis 的概念，大規模產生多輪、跨領域的 UI-grounded dialogue supervision（基於使用者介面的對話監督），以進一步釋放 754B 參數模型的潛能。

第二，多模態輸入的整合。目前的問題形式化主要依賴 System instruction（系統指令）、Dialogue history（對話歷史）與 User message（使用者訊息）等文字脈絡。未來的 Personal agents（個人助理）勢必需要處理視覺資訊（如使用者當前畫面截圖、環境影像），將 Screenshot-to-UI 或視覺感知能力融入 Generative UI（生成式使用者介面）生成，可使 Controls, options, and state（控制項、選項與狀態）的動態合成更貼近真實互動情境。

第三，真實使用者研究與線上評估。A2UI-Bench（A2UI-Bench）作為控制式評估基準雖能有效衡量 Protocol validity（協議有效性）與 Interaction quality（互動品質），但最終的 User experience（使用者體驗）仍需在實際部署中驗證。未來研究應進行長期的 Human-computer interaction（人機互動）使用者實驗，測量輕量級結構化介面在真實場景中對 Cognitive load（認知負荷）與任務完成率的影響。

第四，跨協議與跨平台泛化。本研究以 A2UI（A2UI）為固定協議進行概念驗證，但未來可探索模型是否能自動適應不同的宣告式協議（declarative protocol）或客戶端元件目錄。這涉及更廣泛的 Agent-side UI generation（代理端使用者介面生成）框架設計，使單一模型能依據不同裝置（手機、桌面、車載系統）生成對應的 Executable interfaces（可執行介面）。

第五，進階強化學習與個人化。目前的 Reward-driven reinforcement learning（獎勵驅動的強化學習）採用離線獎勵訊號，未來可導入線上使用者回饋（online user feedback）或人類偏好學習（RLHF），針對個別使用者的互動風格進行 Preference refinement（偏好細化）。此外，結合安全性獎勵函數以防止生成誤導性控制項（misleading controls）或惡意表單，亦是邁向實用化不可或缺的環節。

第六，與既有介面操作代理的協同。未來可探索混合架構：由 Macaron-A2UI（Macaron-A2UI）類型的模型主動生成 Lightweight structured interfaces（輕量級結構化介面），再交由 GUI-Actor 或 WorldGUI 類型的代理執行底層操作。這種「生成層＋執行層」的分工，有望統一解決 Personal agents（個人助理）在開放領域中的互動表面與既有系統操作問題。

## 論文問答

**Q1：為什麼靜態純文字對話被視為個人助理發展的瓶頸？**
A：靜態純文字對話在處理複雜且以使用者為中心的任務時，往往會導致互動流程變得冗長且低效。當使用者需要進行資訊收集、偏好細化、確認決策或多目標組織時，純文字回覆會顯著增加認知負荷並減緩閱讀速度。這種互動模式難以在單一回合內有效呈現結構化選項或控制項，使得複雜任務的完成變得繁瑣且容易出錯。

**Q2：現有的語言模型研究在生成式使用者介面方面存在哪些不足？**
A：現有研究主要集中於純文字對話、程式碼生成或操作既有介面，缺乏針對代理端主動生成使用者介面的統一學習問題框架。學界長期缺乏大規模的基於使用者介面的對話監督資料，以及能夠區分協議有效性與互動品質的評估基準。此外，過往方法往往依賴冗長的綱要提示來引導介面生成，而非讓模型真正內化此能力，這限制了其在實際應用中的彈性與效率。

**Q3：生成式使用者介面為何被認為是未來軟體開發的重要方向？**
A：生成式使用者介面能夠在互動當下動態合成符合使用者目標、情境與下一步行動的靈活介面，突破傳統固定畫面僅為廣泛族群設計的限制。這種範式透過輕量級可執行介面，將結構化互動所需的控制項、選項與狀態即時呈現給使用者，使複雜互動變得更短、更清晰且更易完成。隨著個人助理需要處理的任務日益複雜，能夠主動生成適切互動表面的能力將成為提升人機互動效率的關鍵。

**Q4：Macaron-A2UI 的核心運作機制是什麼？它如何處理輸入與輸出？**
A：Macaron-A2UI 是一個專為個人助理設計的生成式使用者介面模型，其運作機制是接收系統指令、對話歷史與當前使用者訊息後，產生統一回覆。該回覆同時包含自然語言與可執行的 A2UI 動作序列，後者透過宣告式協議描述結構化介面元素。不同於生成 HTML 或 JavaScript 程式碼，模型輸出的是結構化訊息，由客戶端透過受信任元件目錄進行渲染，確保安全性與跨平台可攜性。

**Q5：本研究在資料建構與模型訓練上的主要創新為何？**
A：研究團隊提出可擴展的資料管線，利用混合規則與大型語言模型方法，將四種異質對話來源轉換為超過一萬四千筆的生成式使用者介面語料庫，並透過確定性驗證確保可渲染性。在訓練方面，研究採用參數高效的兩階段配方：先以 LoRA 進行綱要輕量的監督式微調建立文字與介面的對應關係，再以獎勵驅動的強化學習提升可執行互動品質。這種設計讓模型能在推論時無需依賴冗長的綱要提示，直接內化生成可執行介面的能力。

**Q6：為何選擇 A2UI 宣告式協議而非直接生成 HTML 或程式碼？**
A：選擇 A2UI 宣告式協議是基於安全性、可攜性與驗證便利性的策略考量，因為讓模型直接輸出 HTML 或框架特定程式碼可能引入安全風險且難以自動檢驗。在 A2UI 框架下，模型僅負責發出結構化訊息，實際渲染交由客戶端的受信任元件目錄處理，這種分離確保了跨渲染環境的一致性。此外，宣告式格式使自動驗證變得可行，讓研究人員能嚴謹評估代理應在何時生成介面、其結構內容為何，以及整體效用如何。

**Q7：A2UI-Bench 的設計理念與評估維度包含哪些層面？**
A：A2UI-Bench 是專為生成式使用者介面互動建模設計的控制式評估基準，涵蓋三個任務家族與三層級評估框架。評估維度包含協議有效性，檢視動作序列是否符合 A2UI 規範；任務推進度，衡量互動是否有效推進目標達成；以及使用者體驗與視覺指標，評估介面呈現的品質與清晰度。此設計能夠區分技術正確性與互動品質，避免單一指標無法反映真實使用情境的問題。

**Q8：Macaron-A2UI 在實驗中達成了哪些關鍵性能成果？**
A：在 A2UI-Bench 的嚴格評估下，最佳的 Macaron-A2UI 模型在未提供明確綱要提示的情況下，達到了 75.6 的整體分數，超越了最強的完整綱要前沿基線。研究團隊成功訓練了 30B、235B 與 754B 三種不同規模的模型，證明此訓練流程在不同參數量級上皆具有效性。這項成果確認了可執行的使用者介面生成能力可以透過參數高效的訓練方法成功內化於模型之中，無需在推論時依賴外部提示輔助。

**Q9：實驗如何驗證兩階段訓練配方的有效性？**
A：研究透過對比不同訓練階段的模型表現，驗證了 LoRA 監督式微調與獎勵驅動強化學習的互補效益：監督式微調階段先建立穩固的文字與使用者介面對應基礎，而強化學習階段則進一步優化互動品質與可執行性。實驗顯示，僅經過微調的模型在協議遵循上表現良好，但加入強化學習後在任務推進與使用者體驗指標上有顯著提升。此外，研究也證明即使在綱要輕量的設定下，模型仍能達到甚至超越依賴完整綱要提示的強大基線，凸顯了參數高效內化的優勢。

**Q10：Macaron-A2UI 在哪些實際互動場景中能發揮最大價值？**
A：Macaron-A2UI 特別適用於需要結構化輸入與多步驟確認的複雜任務，例如餐廳訂位時同時收集料理類型、預算區間與人數等資訊。在偏好細化場景中，模型可生成滑桿、多選框等輕量級控制項，讓使用者快速調整參數而無需反覆輸入文字。對於多目標組織與決策確認，生成式介面能在單一回合內呈現結構化計畫與明確的下一步動作，大幅減少對話輪次並降低使用者的操作負擔。

**Q11：在實際產品部署時，A2UI 協議帶來哪些工程與安全上的優勢？**
A：A2UI 協議透過將介面生成與介面渲染分離，確保模型輸出僅限於宣告式結構描述，而非可直接執行的任意程式碼，這從根本上降低了安全風險。工程團隊只需維護一套受信任的客戶端元件目錄，即可在不同平台與裝置上確保一致的渲染行為與互動體驗。此外，由於協議輸出具有確定性驗證的特性，產品團隊能夠在部署前自動檢查模型產生的介面動作序列是否合法，大幅提升系統的可靠性與可維護性。

**Q12：本研究對生成式使用者介面領域的長遠影響為何？**
A：本研究填補了代理端使用者介面生成作為完整學習問題的空白，為後續研究提供了統一的問題形式化框架與可複現的評估標準。透過釋出模型、A2UI-Bench 基準與評估協定，研究團隊降低了該領域的進入門檻，使社群能夠在此基礎上進行更深入的技術探索。更重要的是，研究證明了模型可以在最小提示的條件下內化介面生成能力，這將推動未來個人助理從被動文字回覆者，轉變為能主動建構互動表面的智慧代理。

**Q13：本研究在問題設定與方法論上存在哪些已知的限制？**
A：本研究聚焦於助理端的介面生成，而非操作既有數位介面的代理行為，因此未涵蓋在現有網頁或桌面環境中執行動作的挑戰。此外，研究採用固定的 A2UI 宣告式協議，雖然確保了安全性與可驗證性，但相較於無限制的程式碼生成，可能在介面表現力的彈性上有所取捨。目前的訓練與評估也主要基於轉換後的異質對話語料，而非完全來自真實世界中人機使用生成式介面的互動紀錄。

**Q14：在哪些情況下 Macaron-A2UI 可能表現不佳或面臨挑戰？**
A：當使用者意圖極度模糊或對話歷史存在複雜的多重上下文依賴時，模型可能難以判斷最適合的介面類型與結構化內容。在需要高度創意或完全客製化視覺設計的場景中，固定元件目錄的 A2UI 協議可能無法產生最貼近使用者期望的獨特介面風格。此外，若任務涉及極為罕見的領域知識或需要動態組合大量互動元素時，模型在協議有效性與互動流暢度之間可能出現權衡失當的情況。

**Q15：未來研究可以從哪些方向延伸與擴展本工作？**
A：未來研究可朝向擴充真實世界互動資料規模發展，透過收集實際使用者與生成式介面的互動紀錄來進一步提升模型的對齊程度。另一個重要方向是融入多模態輸入與輸出，例如結合視覺資訊生成更豐富的介面，或支援語音與觸控的混合互動模式。此外，探索更彈性的協議設計以平衡安全性與表現力，並進行大規模使用者研究來量化生成式介面在真實產品中的認知負荷降低效益，將是推動此領域走向成熟的重要課題。

## 實務應用指南

### 適用場景

**1. 旅遊與餐飲預訂助理**
當使用者詢問「找飯店附近、每人約 20–30 美元、兩人份的義大利餐廳」時，系統可即時生成多選項（cuisine）、滑桿（budget）、數字精確輸入（party size）與結構化計畫（walkable vs. taxi），將原本需要五至六輪的純文字確認濃縮為一輪輕量級結構化互動。

**2. 企業內部智慧助理（IT / HR / 財務）**
處理請假申請、差旅報銷或設備申領時，助理可動態生成表單控制項與確認按鈕，直接在使用者對話視窗內完成「資訊收集 → 偏好細化 → 多目標組織 → 確認」的完整流程，無需導向外部系統。

**3. 醫療與健康諮詢前置篩檢**
在掛號或症狀初篩情境中，代理可產生結構化介面收集病史、用藥紀錄與時間偏好，避免使用者面對開放式問答時的認知負荷，同時確保收集到的資訊符合後端系統的結構化欄位需求。

**4. 客戶服務與退換貨流程**
針對複雜的退換貨情境，生成式使用者介面可同時呈現「原因分類選單」、「商品圖片預覽」、「退款方式選項」與「最終確認按鈕」，讓使用者在單一回合內完成比較與決策，降低對話放棄率。

**5. 智慧家庭與 IoT 情境控制**
當使用者說「設定週末電影模式」時，助理可生成多目標組織介面，讓使用者一次調整燈光亮度、窗簾狀態、空調溫度與播放清單，並在統一回覆中呈現視覺化狀態總覽與執行按鈕。

### 實作前置條件

**資料準備**
- 異質對話來源：現有客服對話紀錄、任務導向對話腳本、或純文字助理的歷史 log，數量建議至少數千輪以上作為轉換基底。
- A2UI 協議規範：定義宣告式訊息格式（如多選、滑桿、日曆、確認按鈕等）與客戶端可信元件目錄（trusted component catalog）。
- 驗證規則集：用於確保模型輸出的可執行使用者介面動作序列在語法與渲染層面均有效。

**運算資源**
- 微調環境：至少具備 80GB 以上 VRAM 的 GPU（如 NVIDIA A100/H100）以載入 30B 參數模型進行 LoRA 監督式微調；若訓練 235B 或 754B 規模，需多卡平行或叢集資源。
- 強化學習叢集：需額外記憶體與算力進行獎勵驅動的強化學習（RL），並支援批次推論以產生 reward signal。
- 渲染驗證環境：可自動化執行 A2UI 協議並截圖評估視覺指標的後端服務。

**技能需求**
- 熟悉參數高效微調（LoRA/PEFT）與分散式訓練流程。
- 具備對話系統工程經驗，能理解互動情境與狀態管理。
- 了解宣告式 UI 協議設計（相對於 HTML/JS 命令式生成），並能建立確定性驗證管線。
- 具備強化學習實作能力，能設計結合協議有效性、互動品質與使用者體驗的多維度獎勵函數。

### 實作步驟建議

**步驟一：定義宣告式協議與元件目錄**
先建立類似 A2UI 的輕量級協議，明確規範模型可發出的訊息類型（如 `multi_select`、`slider`、`confirmation`、`structured_plan`）。同步建立客戶端元件目錄，確保每個協議訊息都有對應的可渲染、可互動元件，並實作自動驗證器檢查協議有效性。

**步驟二：建構生成式使用者介面語料庫**
收集異質對話來源後，採用「LLM 自動標註 + 規則修復」的混合策略，將純文字對話轉換為多輪生成式使用者介面互動資料。關鍵在於加入確定性驗證：每筆樣本必須通過渲染測試，確保模型輸出確實可執行。目標規模建議達到萬級（如 14,000+ 樣本）以支撐後續監督式微調。

**步驟三：LoRA 監督式微調（Schema-Light SFT）**
選定基礎模型（如 30B 至 754B 參數規模），使用 LoRA 進行參數高效的監督式微調。此階段採用 schema-light 設定：不給予冗長的完整綱要提示，而是讓模型直接從對話歷史與互動情境中內化「何時該生成介面、該生成什麼控制項」的能力。

**步驟四：獎勵驅動的強化學習**
設計三層級獎勵信號：（1）協議有效性（輸出是否合法可渲染）、（2）任務進展（是否有效推進資訊收集與確認）、（3）使用者體驗（介面複雜度與互動效率）。以此進行強化學習，讓模型在可執行的互動品質上進一步提升，而非僅模仿訓練資料。

**步驟五：建立控制式評估基準並迭代**
參考 A2UI-Bench 框架，建立內部評測管線，將協議有效性、互動品質與視覺指標分離評估。定期在最小提示（minimal-prompt）條件下測試模型，確保其無需依賴推論時的長綱要提示即可生成正確的統一回覆。

**步驟六：部署與客戶端整合**
將訓練完成的模型部署為代理端服務，並與前端對話 SDK 整合。客戶端收到自然語言與 A2UI 訊息序列後，由信任的渲染引擎轉為原生控制項。同步實作 fallback 機制：當協議驗證失敗時，自動降級為靜態純文字對話。

### 潛在風險與注意事項

**協議一致性與渲染失敗**
模型可能產生語法錯誤或客戶端不支援的動作類型，導致介面無法渲染。緩解方式是在推論後加入確定性驗證層，並設定嚴格的錯誤處理與降級策略。

**過度生成介面（Over-UI）**
並非每輪對話都需要結構化介面。若模型在簡單問候或閒聊情境也輸出複雜控制項，反而增加認知負荷。需在 SFT 與 RL 階段明確標註「無需 UI」的負樣本，並在獎勵函數中懲罰不適當的介面生成。

**獎勵駭入（Reward Hacking）**
強化學習可能讓模型學會鑽研獎勵函數漏洞（例如生成大量無意義但格式正確的控制項）。建議採用人類回饋或更細緻的規則型檢查器作為獎勵模型的一部分，並定期審查邊界案例。

**安全與隱私邊界**
可執行介面可能誘導使用者輸入敏感資料（如信用卡號、病歷）。必須確保 A2UI 協議中的輸入元件具備資料分級標記，且客戶端渲染環境符合安全規範，避免模型生成的表單被用於釣魚攻擊。

**規模與成本門檻**
754B 參數模型的訓練與推論成本極高。若資源有限，建議從 30B 規模開始驗證概念，並透過高品質資料與精細的 LoRA 設定彌補規模差距，而非盲目追求最大模型。

### 與其他技術的整合建議

**現有對話平台（Chatbot SDK）**
將 Macaron-A2UI 作為 NLU / 對話管理層之後的「回覆生成層」。平台只需擴充訊息格式解析器，將 A2UI 協議轉譯為既有前端元件（如 React/Vue 組件），即可在不重寫整個系統的前提下導入生成式介面。

**RAG 與知識庫**
在生成介面前，先透過檢索增強生成（RAG）取得即時選項（如當日可訂位餐廳、庫存商品清單），再將檢索結果注入提示作為互動情境。這可避免模型幻覺不存在的選項，同時讓生成式使用者介面呈現真實可用的控制項。

**語音助理與多模態系統**
對於僅有語音輸出的裝置，可將 A2UI 輸出視為結構化意圖標記，由 TTS 引擎朗讀關鍵選項；對於具螢幕的裝置（如車載系統、智慧音箱附螢幕），則直接渲染輕量級結構化介面，實現語音與視覺的無縫切換。

**低程式碼 / 無程式碼流程引擎**
將 A2UI 的 `confirmation` 與 `structured_plan` 動作對應至既有 BPMN 或表單引擎的節點。當使用者在對話中點擊確認，即觸發後端流程實例化，讓生成式介面成為企業自動化流程的入口。

**設計系統（Design System）**
將 A2UI 元件目錄與公司內部的 Figma 設計系統或 UI Kit 對齊，確保模型生成的控制項在視覺與互動上符合品牌規範，縮短設計與工程之間的協作落差。

請關注本研究提出的統一形式化定義：將生成式使用者介面視為一個完整的學習問題，而非單純的程式碼生成或現有介面導航任務。值得深入探討的貢獻包括：宣告式協議相較於 HTML/JS 生成的安全性與可驗證性、無綱要提示下內化 UI 生成能力的證據，以及 A2UI-Bench 三層級評估框架如何分離語法正確性與互動品質。

**產品經理**
請將閱讀重心放在適用場景、使用者體驗指標與商業價值的對應關係。論文顯示生成式介面能縮短對話輪次並降低使用者負擔，您應評估這些指標如何轉化為任務完成率、客戶滿意度（CSAT）或人工成本節省。同時留意「過度生成介面」的風險，確保產品在導入時保留純文字回覆的彈性，避免為了技術展示而犧牲自然互動體驗。
