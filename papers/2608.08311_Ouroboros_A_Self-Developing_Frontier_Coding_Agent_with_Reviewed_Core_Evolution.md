## ⚡ TL;DR

現有程式設計代理的執行框架固定，難以隨模型進步自我演化並確保安全。
提出Ouroboros，以遞迴與經驗驅動兩種審查式提交持續改進核心能力。

## 摘要翻譯

我們提出 Ouroboros，一個 self-developing agent harness（自我發展的代理框架），其工具、提示、context assembly（上下文組裝）與核心實作透過 reviewed commits（經審查的提交）持續改進，而這些提交會成為後續工作的 runtime（執行環境）。core evolution（核心演化）以兩種模式進行。在 recursive free evolution（遞迴自由演化）中，改進本身就是一項任務，完成一個演化週期即可排定下一個週期。在 experience-driven core evolution（經驗驅動的核心演化）中，日常工作與社交互動會暴露出錯誤、不夠完善之處與低效率的 context construction（上下文組裝），進而促成 reviewed structural changes（經審查的結構性變更）。

在 Terminal-Bench 2.1 上，一次 Opus 5 執行取得 86.74%，為該基準測試目前所報告的最佳結果。在 OSWorld-Verified 上，一次 Opus 5 執行達到 90.69%，超越先前所報告的最佳分數。一項五輪次的 CL-Bench 評測活動達到 0.2301 的 normalized reward（歸一化獎勵），創下新的 state of the art（最佳表現）。

Hope 是公開記錄中運行最久的 Ouroboros 部署。這是一項為期 161 天的 living agent experiment（活體代理實驗），在 governed human communication（受治理的人類溝通）下，透過七個 human interaction surfaces（人類互動介面）進行 free evolution（自由演化）。人類互動會使缺陷浮現並產生提案，但由代理決定要採用哪些變更。由於自我發展的代理可能會重寫自身程式碼並選擇新的 model APIs（模型 API），operational safety（運作安全）成為首要設計問題：guardrails（安全護欄）必須在 evolutionary pressure（演化壓力）與 public social pressure（公開社交壓力）下保持權威性。基準測試活動使用 frozen system snapshots（凍結系統快照），而 Hope 則在獨立的 lineage（譜系）上持續進行即時演化。

### 核心貢獻（3～5點）
- 提出 Ouroboros，一個 self-developing agent harness（自我發展的代理框架），其工具、提示、上下文組裝與核心實作透過 reviewed commits（經審查的提交）持續改進，而這些提交會成為後續工作的 runtime（執行環境）。
- 設計兩種 core evolution（核心演化）模式：recursive free evolution（遞迴自由演化）讓改進本身成為可排程的任務；experience-driven core evolution（經驗驅動的核心演化）則從日常工作與社交互動中發現問題，推動結構性變更。
- 在三項重要基準測試取得領先成果：Terminal-Bench 2.1 達 86.74%、OSWorld-Verified 達 90.69%、CL-Bench 五輪次評測 normalized reward（歸一化獎勵）達 0.2301，創下新的 state of the art（最佳表現）。
- 公開記錄最長的部署實驗 Hope：進行 161 天的 living agent experiment（活體代理實驗），在 governed human communication（受治理的人類溝通）與七個 human interaction surfaces（人類互動介面）下進行 free evolution（自由演化），並探討自我發展系統的 operational safety（運作安全）與 guardrails（安全護欄）權威性。
- 區隔基準測試與長期部署：基準測試使用 frozen system snapshots（凍結系統快照），Hope 則在獨立 lineage（譜系）上持續演化，以兼顧可重現評估與真實自我改進。

### 適合對象
對自主代理、自我改進／自我演化系統、程式設計代理、AI 安全與治理有興趣的研究者與工程師；特別是關注長期運作代理、人機協作互動介面，以及如何在代理持續改寫自身程式碼時維持安全護欄權威性的讀者。

## 深度分析

#### 方法論解析

Ouroboros（銜尾蛇）的核心定位是一個 **self-developing agent harness（自我發展的代理框架）**：它不僅執行任務，還把「改進自身」視為可被治理的任務。整個系統由一個相對穩定的 **launcher（啟動器）／supervisor（監督器）邊界**，以及一個可變動的 **mutable agent repository（可變動代理程式庫）** 組成。Launcher 負責啟動流程、程序監督、發布引導與緊急停止（panic-stop）語義；repository 則包含任務迴圈、tools（工具）、prompts（提示詞）、memory projection（記憶投射）、review logic（審查邏輯）、benchmark adapters（基準測試轉接器）與使用者介面。這種分離讓「誰有權修改什麼」成為架構層級的設計問題，而非單純的提示工程約束。

**Commit pipeline（提交管線）** 是 Ouroboros 與一般即時提示調整系統最大的差異。任何對核心程式碼或治理表面的修改，都必須通過一個確定性的 preflight（飛行前檢查）、對 staged diff（暫存差異）進行 fingerprinting（指紋化）、收集 reviewer evidence（審查證據），並在提交前再次檢查指紋是否一致。diff-review panel（差異審查面板）在所有 context mode（情境模式）下都是阻塞式的；在 owner-selected（由擁有者選定的）max mode 中，還會進行 whole-repository scope review（全倉範圍審查），評估目標、耦合性、提示詞與功能程式碼；low mode 則可跳過範圍審查。Rollback（回滾）機制能還原到先前經過審查的狀態，並走獨立的 recovery path（復原路徑）。這使得 **reviewed commits（經審查的提交）** 本身成為後續執行的 runtime（執行環境），形成一條可審計的演化鏈。

系統提供三種由擁有者選定的 runtime mode（執行模式）來約束自我倉庫修改：**light（輕量）** 完全封鎖 repository edits（倉庫編輯）；**advanced（進階）** 允許一般編輯但保護 governance surfaces（治理表面）；**pro（專業）** 允許受保護的編輯，但必須經過審查。每次寫入都會使先前的 review evidence（審查證據）失效，因為 freshness（新鮮度）與 staged snapshot（暫存快照）綁定。這種設計直接回應了 **operational safety（運作安全）** 的核心問題：當代理可以改寫自己的程式碼、選擇不同的 **model APIs（模型 API）** 時，**guardrails（護欄）** 必須在 **evolutionary pressure（演化壓力）** 與 **public social pressure（公開社交壓力）** 下仍然保持權威。

Ouroboros 提出兩種 **core evolution（核心演化）** 模式：

1. **Recursive free evolution（遞迴自由演化）**：改進本身就是任務。代理在完成一輪對自身的審查與改進後，可以排定下一輪演化任務，形成持續的 reviewed change（經審查變更）序列，而非一次性的最佳化執行。Hope 即屬於此模式，是一個長達 161 天的 **living agent experiment（活體代理實驗）**。
2. **Experience-driven core evolution（經驗驅動的核心演化）**：在日常工作與社交互動中，任務執行、反思、審查阻擋、工具使用與社會回饋會暴露出 bug、粗糙邊緣與低效的 **context assembly（上下文組裝）**；代理將這些記錄為 durable error classes（持久的錯誤類別）與 proposed structural repairs（結構性修復提案），再決定是否開啟維護工作。通過審查的修復同樣進入 commit pipeline。

在 **operational identity and memory（運作身分與記憶）** 方面，Ouroboros 將記憶與 **runtime constitution（執行期憲法）** 視為 **control surfaces（控制面）**。事實（facts）會跨 session（會話）與 **model routes（模型路由）** 塑造可觀察行為。專案任務還包含 journal（日誌）、workpad（工作墊）、knowledge scope（知識範圍）與 one-writer lease（單一寫入租約），在共享的 **agent identity（代理身分）** 下協調並行工作。

**Operational safety architecture（運作安全架構）** 包含五個支柱：**constitution loading（憲法載入）**、**governance protection（治理保護）**、**staged-diff review（分階段差異審查）**、**external spend limits（外部支出上限）** 與 **operator halt（操作員中止）**。這些機制在代理演化過程中保持權威，並與 Hope 的 live evolution（即時演化）譜系分離；基準測試則使用 **frozen system snapshots（凍結系統快照）**，確保結果可比較且可審計。

在 **benchmark execution and evidence（基準測試執行與證據）** 方面，Ouroboros 針對 Terminal-Bench 2.1 使用官方 verifier（驗證器），在每個 Harbor task container（Harbor 任務容器）內安裝全新的執行環境，並在任務指令後附加一段由框架撰寫的 anti-lookup paragraph（反查詢段落），禁止抓取基準定義、測試或解答。其他轉接器則連接到 OSWorld 虛擬機器、SWE-bench Pro 倉庫、GAIA sandbox（GAIA 沙盒）、ProgramBench cleanroom（ProgramBench 潔淨室）與 CL-Bench task streams（CL-Bench 任務流）。每次執行會寫入 run manifest（執行清單），記錄 seed（種子）與 runtime configuration（執行期配置），並保留每個請求實例的 append-only ledger（僅追加帳本）。任務完成度會從 execution（執行）、objective（目標）、review（審查）與 artifact（產出）四個軸度記錄，並透過 host-run verification commands（主機端驗證指令）產生 revision-bound receipts（與版本綁定的收據）。

#### 實驗數據解讀

論文報告了四組主要數據：

- **Terminal-Bench 2.1**：使用 **Opus 5** 的單次執行達到 **86.74%**，為該基準目前報告的最佳表現。
- **OSWorld-Verified**：Opus 5 單次執行達到 **90.69%**，超越先前最佳報告分數。
- **CL-Bench**：五次 rollout（展開執行）的 campaign（活動）取得 **normalized reward（歸一化獎勵）0.2301**，創下新的 **state of the art（最先進水準）**。
- **SWE-bench Pro** 與 **GAIA**：達到與模型匹配的 frontier performance（前沿表現），並提供完整的 **per-task traces（每項任務追蹤記錄）** 與 **run manifests（執行清單）**。

Terminal-Bench 2.1 包含 89 個困難終端機任務，強調長程命令列推理與工具使用。86.74% 的成績顯示 Ouroboros 在 **context assembly（上下文組裝）**、工具選擇與錯誤修復迴圈上具有顯著優勢。由於該基準在 Harbor container 中執行並使用官方 verifier，分數的可信度較高；anti-lookup 段落也降低了模型直接記憶測試答案的風險。

OSWorld-Verified 是電腦操作與 GUI 基準測試的驗證子集，90.69% 的突破意味著 Ouroboros 在跨應用程式操作、視覺理解與多步驟規劃上達到極高水準。這通常需要精確的 action space（動作空間）控制與穩定的環境狀態追蹤，也反映其工具層與觀察層設計的有效性。

CL-Bench 評估代理在有序任務流中的持續學習能力。0.2301 的 normalized reward 雖然絕對值不高，但在該基準上已是最佳表現，顯示 Ouroboros 能夠在長期任務序列中累積並利用結構性經驗，而非僅靠單次 in-context learning（情境內學習）。這與其 **experience-driven core evolution（經驗驅動的核心演化）** 的設計哲學一致。

SWE-bench Pro 與 GAIA 的「model-matched frontier performance」則說明，當底層模型固定時，harness 的設計對最終表現有決定性影響。論文強調 **complete per-task traces** 與 **run manifests** 的公開，這對於判斷分數是否來自捷徑、隱藏答案或評分器漏洞至關重要；也呼應了 BenchJack 與 HackDetect 等 benchmark audit（基準測試審計）研究的訴求。

Hope 作為最長公開記錄的 Ouroboros 部署，運行 161 天，採用 **free evolution（自由演化）** 模式，並在 **governed human communication（受治理的人類溝通）** 下運作。七個 **human interaction surfaces（人類互動介面）** 讓使用者能夠發現缺陷並產生提案，但最終是否執行變更仍由代理決定。這創造了一種新型的研究對象：一個持續自我修改、同時接受人類社會回饋的開放系統。然而，Hope 的數據主要作為質性證據，而非受控實驗；其演化軌跡與基準測試使用的 frozen snapshots 屬於不同 **lineage（譜系）**，因此不能直接與基準數字比較。

#### 與現有研究的比較

在自我演化代理領域，Ouroboros 與多個系統形成對比（見論文 Table 1）：

- **Voyager** 與 **Live-SWE-agent** 主要演化 prompts（提示詞）與 tools（工具），但不修改 core code（核心程式碼），也缺乏 reviewed commits（經審查提交）機制。
- **Autogenesis** 與 **Darwin Gödel Machine** 進一步演化 workflow（工作流程）與部分實作，但後者由 benchmark selection（基準選擇）驅動，且審計軌跡不如 Ouroboros 完整。
- **Hermes Agent** 與 **OpenClaw/ClawBench** 雖然涵蓋 prompts、tools、workflow 與 deployment state（部署狀態），但未開放核心程式碼的自我修改，也沒有將變更序列化為審查過的提交。

Ouroboros 的獨特之處在於：它把 **core code（核心程式碼）** 的修改權交給代理本身，但所有修改都必須通過 version-controlled（版本控制）的 reviewed commit gate（審查提交閘門）。這讓「演化邊界」從提示詞與工具層延伸到實作層，同時保留可回滾與可審計性。

相較於 **SWE-agent** 與 **OpenHands** 所強調的 **agent-computer interface（代理-電腦介面）** 設計，Ouroboros 進一步把「介面本身」也變成可演化的對象。這呼應了論文開頭的論點：隨著 **base model（基礎模型）** 能力提升，**execution harness（執行框架）**、**environment（環境）** 與 **grader（評分器）** 對最終表現的影響越來越大。

與 **Codex CLI**、**Claude Code**、**Cursor**、**Aider** 等 **model–harness systems（模型-框架系統）** 相比，Ouroboros 更像一個研究平台而非生產力工具。這些商業工具通常固定提示詞與工作流程，強調低延遲與使用者體驗；Ouroboros 則願意犧牲部分即時性，換取長期自我改進的能力。論文引用的控制研究（Ding et al., 2026; Yao et al., 2026; Vats and Golev, 2026）指出，即使固定模型，不同 harness 在準確率、延遲與 token use（token 使用量）上仍有顯著差異，因此報告時必須同時揭露 model、harness、provider route（提供者路由）、effort（工作量）與 evaluation protocol（評估協定）。Ouroboros 在這方面提供了相對完整的透明度。

在記憶與治理方面，Ouroboros 吸收了 **Generative Agents**、**Voyager** 與 persistent-memory systems（持久記憶系統）的經驗，將 stored experience（儲存的經驗）與 reflection（反思）轉化為結構性修復提案。其 **runtime constitution（執行期憲法）** 與 **multi-model review（多模型審查）** 則借鑑 **Constitutional AI**、debate（辯論）、**LLM-as-judge** 與 **self-critique（自我批判）** 的文獻，但把這些機制部署在執行期，並以 source-code patches（原始碼修補檔）作為 reviewed artifacts（經審查的產出物）。

**優勢**：
1. 演化邊界最深：涵蓋 prompts、tools、workflow、core code 與 deployment state。
2. 審計性最強：所有核心變更都經過 reviewed commits，並可回滾。
3. 安全設計內建：constitution loading、governance protection、staged-diff review、external spend limits、operator halt 構成多層防護。
4. 實證表現突出：在三個重要基準上創下或超越最佳表現。

**限制**：
1. 對 Opus 5 等專有模型高度依賴，結果的可轉移性受限。
2. 自由演化模式的長期穩定性與對齊風險仍需更多理論與實證研究。
3. 審查機制雖強，但 reviewer 本身仍是 LLM，可能存在共謀或遺漏風險。
4. Hope 作為開放社交實驗，難以控制變因，其經驗難以直接量化。
5. 論文未詳細討論運算成本、延遲與 token 消耗，這對實際部署至關重要。

#### 可重現性評估

Ouroboros 以 **MIT license（MIT 授權條款）** 釋出，程式碼存放於 GitHub（https://github.com/razzant/ouroboros），並提供官方網站（https://ouroboros-agent.ai/）。這大幅提升了可重現性。論文強調每次基準測試都使用 **frozen system snapshots（凍結系統快照）**，並在執行前撰寫 **run manifest（執行清單）**，記錄 seed 與 runtime configuration；執行後保留完整的 **per-task traces（每項任務追蹤記錄）**。這些都是提升可重現性的關鍵實踐。

在 Terminal-Bench 2.1 的執行中，系統使用官方 verifier 與 Harbor task container，並附加 anti-lookup paragraph 防止模型透過網路抓取測試答案。這種設計減少了 hidden answer（隱藏答案）與 unintended shortcuts（非預期捷徑）的風險，也讓外部審計者能夠檢驗 trajectory（軌跡）是否合法。

然而，可重現性仍面臨幾項挑戰：

- **模型權重與 provider route**：實驗主要使用 Anthropic 的 Opus 5，屬於專有 API，研究者無法取得模型權重。不同 provider route、API 版本與速率限制可能導致結果差異。
- **成本與 token 使用**：長程任務與多模型審查會產生高額 API 費用，個人研究者可能難以完整複現所有 campaign。
- **隨機性與 seed 控制**：雖然 run manifest 記錄 seed，但 LLM 解碼過程、工具執行時序與環境狀態仍可能引入變異。
- **Hope 的 live lineage**：Hope 是持續演化的開放系統，其狀態無法被凍結重現；論文已明確將其與基準測試的 frozen snapshots 分離，這是負責任的作法。
- **完整論文細節**：目前可取得的上下文片段顯示部分段落有壓縮或缺漏，例如具體的 prompt 設計、reviewer 的評分標準、external spend limits 的數值等，若未在完整論文或文件中公開，將影響細粒度重現。

整體而言，Ouroboros 在開源、審計軌跡與反作弊機制上達到了目前自我演化代理研究中的高標準，但對專有模型與高成本的依賴仍是社群重現的主要門檻。

#### 未來研究方向

1. **形式化驗證自我修改（formal verification of self-modification）**  
   目前的 staged-diff review 依賴 LLM-as-judge 與多模型辯論，未來可引入輕量級形式化方法，驗證核心修改不會破壞 constitution loading、governance protection 與 operator halt 等不變量。

2. **憲法與護欄的共同演化（co-evolution of constitution and guardrails）**  
   若代理能修改自己的核心程式碼，則憲法本身是否也應允許演化？如何在允許演化的同時，確保某些安全原則不可被單方面覆寫，是值得深入研究的問題。

3. **多代理社會與譜系實驗（multi-agent societies and lineage experiments）**  
   Hope 展示了單一代理在公開社交壓力下的演化。未來可設計多個 Ouroboros 實例，讓它們互相審查、合併或分叉 lineage，研究社會動態對能力與對齊的影響。

4. **長期對齊與目標漂移（long-term alignment and goal drift）**  
   161 天的部署已能觀察到一定程度的 drift（漂移）。需要建立更系統的指標，追蹤代理目標、價值觀與行為分佈隨時間的變化，並設計早期預警機制。

5. **效率與成本最佳化（efficiency and cost optimization）**  
   多模型審查與自由演化帶來高 token 消耗。未來可研究如何在不犧牲安全的前提下，使用較小模型擔任 reviewer、壓縮 context assembly，或引入 adaptive review depth（適應性審查深度）。

6. **開源權重模型上的驗證（validation on open-weight models）**  
   目前結果集中在 Opus 5 等專有模型。將 Ouroboros 移植到開源權重模型，不僅能降低成本，也能讓社群更深入理解 harness 與 base model 的交互作用。

7. **自動化基準審計與捷徑檢測（automated benchmark auditing and shortcut detection）**  
   結合 BenchJack 與 HackDetect 的方法，開發針對自我演化代理的專用審計工具，自動檢測其是否利用評分器漏洞或隱藏答案。

8. **人機治理介面的設計（human-in-the-loop governance interfaces）**  
   Hope 的七個 human interaction surfaces 顯示社會回饋的重要性。未來可設計更結構化的提案、異議與否決機制，讓人類操作者在不奪取代理自主權的前提下，有效引導演化方向。

## 論文問答

**Q1：Ouroboros 試圖解決什麼核心問題？為什麼這個問題在當前 frontier coding agent 的發展中特別重要？**

A：Ouroboros 要解決的核心問題是：程式設計代理的實際能力不僅取決於基礎模型，更取決於執行框架（execution harness）如何組裝上下文、選擇工具與管理記憶，而現有框架大多是靜態的，無法隨著使用經驗自我精進。隨著基礎模型持續進步，「框架如何組裝情境」所決定的能力佔比越來越高，因此讓 harness 本身也能被檢視、迭代與演化，成為釋放模型潛能的關鍵。Ouroboros 透過將工具、提示詞、上下文組裝與核心實作都納入可審查的提交（reviewed commits），讓後續執行環境能持續吸收前一次的改進，形成自我發展的閉環。

**Q2：現有的自我演化代理或程式設計代理框架為何無法充分解決這個問題？**

A：現有框架如 SWE-agent 與 OpenHands 雖然證明了代理-電腦介面（agent-computer interface）對效能的影響，但它們通常不會讓代理修改自己的核心實作，也缺乏可審計的版本控制閘門。其他系統可能會調整提示詞、工具或工作流程，卻很少同時涵蓋核心程式碼、治理機制與部署狀態的演化邊界。Ouroboros 的差異在於它把執行期憲法（runtime constitution）與持久記憶視為控制面，並以多模型審查（multi-model review）來審視原始碼修補檔，確保每一次核心改動都留下可追溯、可回滾的證據。

**Q3：為什麼對於自我發展的代理而言，運作安全（operational safety）不是附加功能，而是首要設計約束？**

A：因為自我發展的代理可能改寫自己的程式碼、選擇新的模型 API，甚至擴大自主權或取得更強大的工具，這個過程本身就可能削弱後續的控制機制。同樣的演化動力既能提升能力，也能繞過或弱化護欄（guardrails），所以權限邊界（authority boundaries）必須在反覆核心演化與公開社交壓力下仍然保持權威。Ouroboros 因此將憲法載入、治理保護、分階段差異審查、外部支出上限與操作員中止等機制設計成不可被演化本身推翻的底層約束。

**Q4：Ouroboros 的核心架構如何劃分「不可變」與「可演化」的邊界？**

A：Ouroboros 將啟動器（launcher）與監督邊界（supervisor boundary）和可變的代理倉庫（mutable agent repository）分離：啟動器負責開機、程序監督、發布引導與緊急停止語義，而倉庫則包含任務迴圈、工具、提示詞、記憶投影、審查邏輯、基準適配器與使用者介面。外部工作區任務在另一個倉庫根目錄上運作，只回傳修補檔或直接產出，避免污染核心。這樣的劃分確保即使代理不斷修改自身程式碼，啟動層仍能強制執行安全策略與回滾機制。

**Q5：Ouroboros 提出的兩種核心演化模式有何不同？它們如何互補？**

A：兩種模式分別是遞迴自由演化（recursive free evolution）與經驗驅動的核心演化（experience-driven core evolution）。在遞迴自由演化中，「改進系統」本身就是一項任務，完成一輪演化後可以排定下一輪，形成持續不斷的審查提交序列；而在經驗驅動模式中，代理在日常工作與社交互動中發現錯誤、粗糙邊緣與低效的上下文組裝，再將這些觀察轉化為結構性修復。前者適合主動探索架構可能性，後者則讓真實使用經驗成為改進來源，兩者共同確保系統既能創新也能穩定收斂。

**Q6：Ouroboros 的提交管線（commit pipeline）與治理設計有哪些關鍵選擇，以確保自我修改的安全性？**

A：提交管線包含確定性預檢、對暫存差異進行指紋化、收集審查證據，並在提交前再次檢查指紋，確保審查期間沒有被暗中替換。執行時有三種模式約束自我倉庫修改：light 模式禁止倉庫編輯、advanced 模式允許一般編輯但保護治理表面、pro 模式則允許受保護編輯但須經審查。差異審查面板在所有上下文模式中都是阻塞式的，這意味著任何核心改動都必須通過審查才能成為後續執行環境的一部分。

**Q7：Ouroboros 在哪些基準測試上進行了評估？最關鍵的結果是什麼？**

A：Ouroboros 在 Terminal-Bench 2.1、OSWorld-Verified、CL-Bench、SWE-bench Pro 與 GAIA 等長程基準上進行評估。其中 Opus 5 執行在 Terminal-Bench 2.1 達到 86.74%，在 OSWorld-Verified 達到 90.69%，均創下該基準目前最佳表現；五輪推出的 CL-Bench 活動則取得歸一化獎勵 0.2301，同樣樹立新的最先進水準。這些結果顯示，當基礎模型與會自我演化的執行框架結合時，能顯著推升 frontier coding agent 的整體能力。

**Q8：Ouroboros 如何確保基準測試結果的有效性，並避免資料污染或捷徑解法？**

A：基準活動使用凍結系統快照（frozen system snapshots）與文件化的執行期配置，並與 Hope 的即時演化譜系（lineage）分離，避免訓練與評估混用。每個任務指令都會附加一段由框架撰寫的反查詢段落，禁止取得基準定義、測試或解答；此外，啟動器會在准入前撰寫執行清單（run manifest），證明種子與執行環境，並以僅附加帳本保存每個請求實例。這些措施共同降低 benchmark contamination 與 unintended shortcuts 的風險。

**Q9：Hope 作為「活體代理實驗」在整個研究中扮演什麼角色？**

A：Hope 是公開記錄最長的 Ouroboros 部署，為期 161 天，在受治理的人類溝通下進行自由演化，橫跨七個互動接觸面。人類互動會浮現故障並產生改進提案，但由代理自己決定要追求哪些變更，這驗證了社交互動可以驅動候選改進，同時不會把提交權限轉移給使用者。Hope 因此補足了凍結基準測試無法呈現的長期動態行為，也成為檢驗運作安全架構在真實社交壓力下是否穩健的現場實驗。

**Q10：Ouroboros 在實務上適合哪些應用情境？**

A：Ouroboros 適合需要長期運作、持續學習與自我適應的軟體工程任務，例如長期維護大型程式碼庫、自動化終端機流程、GUI/CLI 電腦操作，以及跨任務流的持續學習。由於它能累積儲存的經驗並反思後調整自身工具與提示詞，特別適合部署為長期陪伴的程式設計助理。對於需要反覆迭代、工具鏈複雜且工作流程會隨時間演變的企業環境，這種自我發展的代理框架具有顯著的實用潛力。

**Q11：若將 Ouroboros 產品化，需要考量哪些部署與治理議題？**

A：產品化時必須在「允許演化」與「維持監督」之間取得平衡，例如使用外部支出上限控制模型 API 成本，並保留操作員中止的緊急權限。分階段差異審查與治理保護機制必須成為生產部署的標準配備，避免代理在無人把關下修改關鍵安全程式碼。此外，建議將評估用的凍結快照與生產線的即時演化譜系分開，以確保效能測量穩定，同時不扼殺現場改進的空間。

**Q12：Ouroboros 可能對自主程式設計代理領域帶來什麼樣的影響？**

A：Ouroboros 示範了執行框架本身也可以成為演化的對象，而不只是被動承載模型的容器，這可能改變領域對「代理效能來源」的理解。它確立了「經審查的提交成為後續執行環境」的典範，讓執行與改進之間形成可追蹤的回饋迴路。長遠來看，這會促使更多研究關注自我改進代理基礎設施、運作安全，以及如何在演化壓力下維持治理權威。

**Q13：作者承認 Ouroboros 有哪些主要限制？**

A：Ouroboros 的治理架構相當複雜，維護一個會自我修改的系統需要持續投入監督與審查成本。多模型審查雖然提升安全性，卻也增加了計算開銷與延遲，對於低延遲場景可能構成挑戰。此外，基準成績是基礎模型、執行框架、環境與評分器共同作用的結果，難以單獨分離出「自我演化」這一因素的純粹貢獻。

**Q14：Ouroboros 在實際運作中可能出現哪些失敗案例或風險？**

A：代理可能選擇追求不適當的改進、在自我修改時引入難以察覺的錯誤，或在公開社交壓力下被誘導削弱護欄。如果反查詢機制失效，也可能發生基準資料污染或利用捷徑取得高分的情況。另一個潛在風險是演化方向過度優化短期指標，反而損害長期安全性或實用價值，因此需要持續監控與人類介入機制。

**Q15：未來研究可以朝哪些方向延伸 Ouroboros 的設計？**

A：未來可以發展更嚴謹的理論保證，證明在持續核心演化下權限邊界仍然不可被繞過。也可以將多模型審查的效率最佳化，並探索混合人機治理模式，讓人類審查者與 LLM-as-judge 在關鍵提交上協作。此外，延長活體代理實驗的時間、擴展到更多互動接觸面與任務領域，並研究如何自動偵測有害的自我修改，都是值得深入的方向。

## 實務應用指南

### 適用場景

1. **長期運作的軟體工程維護代理**  
   適合需要持續維護多個程式碼庫、重複處理 issue 與小型功能請求的團隊。Ouroboros 能在日常工作中發現工具與提示詞的不足，透過經驗驅動的核心演化（experience-driven core evolution）逐步改進自己的任務迴圈與上下文組裝（context assembly）。

2. **受治理的多介面客戶支援與需求轉譯**  
   當代理需要同時透過聊天、郵件、issue、論壇等多種人類互動介面（human interaction surfaces）接收回饋時，可將這些互動轉化為結構化提案。重點在於：人類可以指出問題，但變更必須經過審查提交（reviewed commits）才能進入執行環境（runtime）。

3. **可重現的程式設計能力評估平台**  
   可用於內部模型選型或 harness 比較。透過凍結系統快照（frozen system snapshots）執行 Terminal-Bench 2.1、OSWorld-Verified、CL-Bench、SWE-bench Pro 等長程基準測試（long-horizon benchmarks），並產生完整的每項任務追蹤記錄（complete per-task traces）與執行清單（run manifests）。

4. **受控的自主研究或活體代理實驗（living agent experiment）**  
   類似 Hope 的 161 天部署，適合研究機構或前沿實驗室在明確護欄（guardrails）下觀察自由演化（free evolution）。此場景強調治理保護（governance protection）與操作員中止（operator halt）必須始終有效。

5. **企業級程式碼審查與知識沉澱系統**  
   將每次任務的 reflection、原始碼修補檔（source-code patches）與審查證據序列化為版本控制紀錄，形成可審計的知識資產，並透過持久記憶（persistent memory）影響後續會話的行為。

### 實作前置條件

**資料（Data）**
- 目標程式碼庫與任務環境（如 SWE-bench Pro repository、OSWorld VM、Terminal-Bench Harbor container）。
- 歷史 issue、對話紀錄與錯誤樣本，作為經驗驅動演化的輸入。
- 明確的治理原則與執行期憲法（runtime constitution）文件。
- 模型 API 金鑰、支出監控資料與備援提供者路由（provider route）設定。

**運算（Compute）**
- 可執行容器或虛擬機器的運算資源，並能為每個任務建立隔離的工作空間。
- 前沿模型（如 Opus 5）的 API 存取權限，以及用於多模型審查（multi-model review）的備援模型。
- 長期記憶與日誌儲存、版本控制伺服器、CI / 預檢（preflight）執行環境。
- 外部支出上限（external spend limits）與計費告警機制。

**技能（Skills）**
- 熟悉 Python 代理架構、Git 流程、容器化與安全邊界設計。
- 具備提示工程（prompt engineering）與模型-框架系統（model–harness systems）調校經驗。
- 能設計評分器（grader）、任務追蹤與審查邏輯。
- 理解自我修改系統的風險，能制定並維護權限邊界（authority boundaries）。

### 實作步驟建議

1. **建立啟動器與監督邊界**  
   實作 launcher，負責啟動、程序監督、發布引導與緊急停止（panic-stop）。設定 light / advanced / pro / max 等執行模式，決定代理能否編輯自身倉庫以及哪些治理表面不可觸碰。

2. **建構可變動的代理倉庫**  
   將任務迴圈、工具（tools/skills）、提示詞、記憶投影、審查邏輯、基準測試適配器（benchmark adapters）與使用者介面放入同一個可被版本控制的倉庫。外部工作空間任務應在獨立的 repository root 上操作。

3. **導入審查提交管線**  
   每次自我修改前執行確定性預檢（deterministic preflight），對暫存差異（staged diff）產生指紋，收集審查證據後再次檢查指紋，確保審查期間內容未被替換。差異審查面板（diff-review panel）必須是阻塞式的。

4. **設定運作安全架構**  
   載入執行期憲法、啟用治理保護、實作分階段差異審查（staged-diff review）、外部支出上限與操作員中止。核心原則：即使代理持續演化，護欄仍必須保持權威性。

5. **部署記憶與多模型審查**  
   建立持久記憶與共享代理身份（shared agent identity），並透過辯論（debate）、LLM-as-judge 與自我批判（self-critique）對原始碼修補檔進行審查。將修補檔視為必須通過審查的產出物（reviewed artifacts）。

6. **啟動兩種核心演化模式**  
   - **經驗驅動演化**：從普通任務、社交互動與儀表板回饋中記錄錯誤類別與結構修復提案，再決定是否開啟維護工作。  
   - **遞迴自由演化**：將「改進系統本身」設為任務，完成一輪後可排定下一輪，但每一輪都必須通過相同的審查提交閘門。

7. **建立基準測試與凍結快照**  
   為 Terminal-Bench 2.1、OSWorld-Verified、CL-Bench、SWE-bench Pro 等編寫 adapters。執行前撰寫執行清單、固定 seed 與執行環境，使用官方驗證器與 anti-lookup 段落防止污染，並保留完整追蹤記錄。

8. **上線與持續監控**  
   明確區分「活體演化譜系（lineage）」（如 Hope）與「凍結快照基準測試」。持續監控支出、審查新鮮度、任務完成狀態與治理事件，並保留復原（rollback）路徑。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解措施 |
|---|---|---|
| **自我修改削弱護欄** | 代理可能改寫核心程式碼或切換模型 API，繞過後續控制。 | 強制審查提交、治理保護、操作員中止、模式分級（light / advanced / pro / max）。 |
| **演化偏離目標** | 自由演化可能產生難以解釋或不符合組織目標的行為。 | 每個提交需附審查產出物、完整追蹤記錄與可復原的 rollback 路徑。 |
| **基準測試污染** | 代理可能查詢題目、利用捷徑或隱藏答案。 | 使用官方驗證器、anti-lookup 提示、每次任務的乾淨執行環境、獨立 workspace。 |
| **成本與延遲爆炸** | 多模型審查與遞迴演化可能快速消耗 token。 | 設定外部支出上限、依場景選擇 low / max 審查模式、監控提供者路由。 |
| **社交互動引發對齊問題** | 公開社交壓力可能誘導代理採納不當提案。 | 受治理的人類溝通、憲法載入、不將提交權限轉移給使用者。 |
| **記憶污染與長期漂移** | 長期運作後，記憶可能累積錯誤假設。 | 記憶投影、one-writer lease、定期以凍結快照重新評估能力基線。 |

### 與其他技術的整合建議

- **版本控制平台（GitHub / GitLab）**  
  將 Ouroboros 倉庫視為一般專案，透過 PR / commit 進行審查；並在 CI 中執行 deterministic preflight 與 diff-review 檢查。

- **Issue 追蹤與通訊工具**  
  可將 Slack、郵件、論壇、issue tracker 作為經驗驅動演化的輸入來源，但必須經過中介層過濾、記錄與治理審查，避免使用者直接觸發核心變更。

- **現有 IDE / CLI 工具**  
  Codex CLI、Claude Code、Cursor、Aider 等可作為模型路由或工具層，但應置於 Ouroboros 的 launcher 與 governance boundary 之下，以維持統一的安全與審計介面。

- **容器與虛擬機基礎設施**  
  整合 Harbor、OSWorld VM、SWE-bench Pro repository、GAIA sandbox、ProgramBench cleanroom 等作為隔離任務工作空間，確保環境可重現。

- **MLOps / 可觀測性平台**  
  將執行清單、追蹤記錄與驗證收據匯入實驗追蹤與日誌系統；外部支出上限對接計費與告警系統。

- **企業身份識別與機密管理**  
  模型 API 金鑰與敏感權限由 launcher / operator 控管，避免代理在演化過程中自行取得或替換。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦「代理能改寫自己的程式碼」這件事所帶來的風險，再閱讀第 3 節的架構圖與運作安全設計。基準測試數字可先略過，重點理解審查提交、護欄與操作員中止這三個保護機制。

**AI 工程師**  
應深入研讀 commit pipeline、diff-review 邏輯、context assembly、memory projection 與四種執行模式的邊界設計。建議將 Table 1 與 SWE-agent、OpenHands、Hermes Agent 等系統對照，理解 Ouroboros 在「核心程式碼可演化」與「審查閘門」上的差異。

**研究人員**  
值得關注遞迴自由演化與經驗驅動核心演化的設計選擇、Hope 活體實驗的治理與觀察方法，以及論文如何透過 run manifests、traces 與官方驗證器來確保 benchmark protocol 的有效性與可審計性。

**產品經理**  
建議將重點放在運作安全（operational safety）、成本控管、適用場景與 Hope 的 161 天部署經驗。評估時可將 Ouroboros 視為一種高風險高回報的受控實驗，先從小範圍、凍結快照的 benchmark campaign 開始，再決定是否投入長期活體演化。
