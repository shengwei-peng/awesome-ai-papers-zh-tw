# LedgerAgent：遵循策略的工具呼叫代理的結構化狀態

## ⚡ TL;DR

標準代理將任務狀態隱含於提示詞中，導致決策時誤用過時或錯誤資訊，並違反領域策略。
本文提出LedgerAgent，以獨立分類帳維護觀察狀態，並在執行環境改變前以策略閘門檢查限制。
於四個客戶服務領域，LedgerAgent 提升 pass^k，在嚴格多試行一致性指標下增益最大。

## 摘要翻譯

遵循策略的工具呼叫代理（policy-adherent tool-calling agents）在客戶服務領域（customer-service domains）中，必須在進行工具呼叫（tool calls）與遵守領域策略（domain policies）的同時，跨回合（turns）維護任務狀態（task states）。任務狀態包含透過使用者互動與工具呼叫所觀察到的相關事實、識別碼、限制與條件。在標準代理（standard agents）中，任務狀態並未被單獨表示；觀察結果（observations）、工具回傳結果（tool returns）與策略指令皆被置於提示詞（prompt）中，使得代理每次決定下一步行動時，都必須從提示詞中重建相關任務狀態。這種設計讓狀態管理（state management）變為隱含式，產生兩種常見的失效模式（failure modes）：代理可能檢索到正確的事實，但後續卻將決策依據（grounding）建立在過時（stale）、遺漏或錯誤的資訊上；此外，一個語法上有效的工具呼叫仍可能違反依賴當前任務狀態的領域策略。我們提出 LedgerAgent，一種用於工具呼叫代理的推論階段方法（inference-time method），該方法將觀察到的任務狀態維護在獨立的分類帳（ledger）中，並將狀態呈現於提示詞中。此分類帳亦用於在改變環境的工具呼叫（environment-changing tool calls）執行前，檢查狀態相依的策略限制（state-dependent policy constraints），以阻擋策略違規（policy violations）。跨四個客戶服務領域，並在混合開放權重（open-weight）與封閉權重（closed-weight）模型的測試下，LedgerAgent 相較於標準基於提示的工具呼叫方法（prompt-based tool-calling approach）提升了平均 pass@k，且在更嚴格的多試行一致性指標（multi-trial consistency metrics）下獲得最大的提升。

### 核心貢獻（3～5點）
- 揭示標準代理因將觀察結果與策略指令隱含於提示詞中所導致的兩大失效模式：代理雖檢索到正確事實，卻以過時或錯誤資訊作為決策依據；以及語法有效但仍違反狀態相依領域策略的工具呼叫。
- 提出 LedgerAgent，一種無需額外訓練的推論階段方法，透過獨立的分類帳明確維護跨回合任務狀態，並將結構化狀態呈現於提示詞中，解決狀態管理隱含化的問題。
- 設計策略閘門機制，於執行改變環境的工具呼叫前，依據分類帳檢查狀態相依的策略限制，即時阻擋策略違規，強化領域策略遵循性。
- 在四個客戶服務領域與混合開放／封閉權重模型的評測中驗證，LedgerAgent 顯著提升平均 pass@k，並於更嚴格的多試行一致性指標下展現最大增益。

### 適合對象
從事大型語言模型代理、工具學習與對話式 AI 系統研究的學者與工程師；特別是關注推論階段強化、狀態管理機制設計，以及需在客戶服務等高風險領域確保代理嚴格遵循業務策略的應用開發者與產品團隊。

## 深度分析

#### 方法論解析

LedgerAgent 的核心假設在於：標準代理（standard agents）將 observations（觀察結果）、tool returns（工具回傳結果）與 policy instructions（策略指示）全部嵌入 prompt（提示詞）中，導致 state management（狀態管理）成為隱式（implicit）流程。這種設計會引發兩種常見的 failure modes（失效模式）：第一，agent 雖然成功檢索到正確事實，但後續 decision making（決策）卻 grounded（依據）在 stale information（過時資訊）、missing information（遺漏資訊）或 incorrectly reconstructed state（錯誤重建的狀態）上；第二，即使 tool call（工具呼叫）在語法上有效，仍可能違反取決於當前 task state（任務狀態）的 domain policy（領域策略）。

為了解決這個問題，作者提出 LedgerAgent，一個純粹的 inference-time method（推論階段方法），在不更動 model weights（模型權重）的前提下，加入兩個確定性元件：

第一，schema-anchored ledger（綱要錨定的分類帳）。每次 read-only tool call（唯讀工具呼叫）成功回傳後，系統會將結果投影為一個 typed dictionary（強型別字典），並以 canonical paths（規範路徑）作為鍵值儲存。這個過程不需要額外的 LLM call（大型語言模型呼叫），完全由確定性程序完成。儲存後的 ledger（分類帳）會在每一個 turn（回合）重新注入 prompt（提示詞），使 agent 能透過 lookup（查閱）直接取得當前狀態，而非從冗長的對話紀錄中重新推導。

第二，policy gate（策略閘門）。在任何的 environment-changing tool calls（改變環境的工具呼叫）——例如取消訂單、退款、修改預訂——被送往外部環境執行前，閘門會先以 ledger 中記錄的狀態欄位作為輸入，評估該呼叫是否違反以 predicate（謂詞）形式表達的 state-dependent policy constraints（狀態相依的策略限制）。若偵測到 policy violation（策略違規），閘門會阻擋該呼叫，回傳具體的違規說明與衝突狀態，讓 agent 有機會在環境被改變前修正計畫。

這樣的設計將錯誤邊界從事後補救（post-hoc correction）轉移到事前預防（prevention）。如圖一所示，當使用者要求取消航班時，標準代理雖然曾呼叫 `get_reservation_details` 取得訂位資料，卻因為提示詞中資訊過於發散，最終仍發出違反 24 小時取消政策的 `cancel_reservation`；而 LedgerAgent 因為在 ledger 中明確記錄了 reservation date（預訂日期）與 current time（當前時間），policy gate 得以在執行前阻擋該動作，並回傳符合政策的拒絕訊息。

#### 實驗數據解讀

本研究在 four customer-service domains（四個客戶服務領域）上進行評估，資料來源包含 τ2-bench 與 τ-Trait（Barres et al., 2025; He et al., 2026）。實驗採用 mixed panel（混合模型群組），同時涵蓋 open-weight models（開放權重模型）與 closed-weight models（封閉權重模型），以驗證方法的通用性。

評估指標採用 pass^k（k 次嘗試中至少成功一次），並特別關注 stricter multi-trial consistency metrics（更嚴格的多試行一致性指標）。後者的意義在於：許多 agent 在單次 trial（試行）中可能因為採樣隨機性而成功，但在多次獨立試行中卻表現不穩定；pass^k 在較高的 k 值下更能反映方法的 robustness（穩健性）。

實驗結果顯示，LedgerAgent 在多數 domain–model pair（領域–模型配對）上均提升了 pass^k，且相較於 standard prompt-based tool-calling approach（標準基於提示的工具呼叫方法），其優勢在更高的 k 值下更加顯著。這表示當 baseline（基線）方法因提示詞累積而變得愈發不一致時，ledger 提供的 explicit state representation（明確狀態表示）能有效穩定決策。Ablation studies（消融實驗）進一步指出，進步來自 typed ledger（強型別分類帳）與 policy-gated action（策略閘門控管動作）兩者的結合，缺一不可。

特別值得注意的是，最大的增益出現在需要 environment-changing actions（改變環境的動作）的任務上。這呼應了方法設計的初衷：read-only tool calls（唯讀工具呼叫）不會造成不可逆的副作用，因此風險較低；但一旦涉及寫入或修改外部狀態，錯誤的代價隨之提高，而 policy gate 的事前攔截價值也因此放大。

#### 與現有研究的比較

在相關文獻中，改善 tool-using agents（工具使用代理）的途徑大致可分為三類：

第一類是模型層面的訓練，包括 fine-tuning（微調）、synthetic data generation（合成資料生成）與 reinforcement learning（強化學習）。這些方法透過 Schick et al. (2023)、Li et al. (2023)、Zhou et al. (2024b) 等工作，教導模型更可靠地產生工具呼叫。然而，它們通常保留原有的 prompt-only state representation（僅以提示詞表示狀態），task state（任務狀態）在決策當下仍然是隱含的。

第二類是 inference-time scaffolding（推論階段鷹架），例如 Yao et al. (2023b) 的 planning（規劃）、Madaan et al. (2023) 與 Shinn et al. (2023) 的 reflection（反思）。這些方法在生成流程中加入思考或驗證步驟，但本質上仍將檢索到的 records（紀錄）與 policies（策略）埋藏在不斷增長的 transcript（對話紀錄）中，agent 仍需在每次行動前從中重建狀態。

LedgerAgent 與上述方法的本質差異在於：它不試圖讓模型「更會記憶」或「更會規劃」，而是直接改變 state representation（狀態表示）的結構。透過將觀察到的狀態外化為獨立的 schema-anchored ledger（綱要錨定的分類帳），並以確定性的 policy gate（策略閘門）進行把關，它將 state tracking（狀態追蹤）與 policy adherence（策略遵循）提升為系統層級的機制，而非僅仰賴模型的推理能力。

然而，本方法也存在侷限。首先，目前的 ledger 僅吸收 successful tool returns（成功的工具回傳結果），對於失敗呼叫或部分資訊的處理尚未著墨。其次，domain policies（領域策略）必須預先定義為可解析的 predicates（謂詞），這在策略極度複雜或需要自然語言詮釋的場景中可能難以擴展。最後，實驗範圍集中於 customer-service domains（客戶服務領域），其在更開放、schema 較難預先定義的領域（如軟體工程或科學研究）中的適用性仍有待驗證。

#### 可重現性評估

就現有提供的文本而言，作者並未明確提及原始碼、ledger 的 schema 定義檔或 policy gate 的 predicate 實作是否公開釋出。評估所使用的 τ2-bench 與 τ-Trait 資料集雖有文獻引用，但從節錄內容無法確認其公開取得管道與授權條款。

從方法論角度來看，LedgerAgent 的優勢在於它是一個完全確定性的 inference-time method（推論階段方法），不涉及模型訓練或權重更新。因此，只要具備以下條件，原則上具備高度可重現性：(1) 目標 LLM 的 API 或權重（open-weight models 或 closed-weight models 的端點）；(2) 完整的工具綱要（tool schemas）；(3) 以 canonical paths（規範路徑）定義的 ledger 結構；以及 (4) 各領域的 policy predicates（策略謂詞）。若作者能釋出上述系統層級的設定檔與評估腳本，將大幅提升社群驗證與後續擴展的可能性。

#### 未來研究方向

LedgerAgent 將任務狀態外化為結構化物件的思路，為後續研究開啟了數條值得探索的路徑：

第一，自動化綱要生成（automatic schema induction）。目前的 schema-anchored ledger（綱要錨定的分類帳）依賴預先定義的綱要，未來可研究如何讓 agent 在執行過程中自動推導並擴充 ledger 的結構，以適應 schema 動態變化的環境。

第二，不完整與不確定狀態的處理。當前的設計主要處理成功的 tool returns（工具回傳結果），但未來可納入 partial observations（部分觀察）、ambiguous user utterances（模糊的使用者語句）或 failed tool calls（失敗的工具呼叫），並在 ledger 中標註 confidence（信賴度）或 alternative hypotheses（替代假設）。

第三，自動化策略學習。現行的 policy gate（策略閘門）需要人工將領域規則撰寫為 predicates（謂詞）。後續研究可探索從示範資料或政策文件中自動抽取並學習這些限制條件，甚至結合 reinforcement learning（強化學習）讓 gate 的決策邊界隨資料演進。

第四，與模型訓練方法的結合。LedgerAgent 目前作為推論階段的「外掛」，若將 explicit state representation（明確狀態表示）的回饋信號融入 fine-tuning（微調）或 RLHF（人類回饋強化學習），可能進一步提升模型對結構化狀態的利用效率。

第五，多代理協作與狀態共享。在多 agent（代理）系統中，ledger 可作為共享的 structured memory（結構化記憶體），讓不同角色（如客服、技術支援、帳務）的代理能基於一致的 task state（任務狀態）進行協作，並由統一的 policy gate 確保跨角色的策略遵循。

最後，跨領域驗證。將 LedgerAgent 從 customer-service domains（客戶服務領域）擴展至醫療決策、軟體開發或工業控制等更高風險的場景，將能驗證其在複雜、長程互動中的穩健性與價值。

## 論文問答

**Q1：LedgerAgent 旨在解決遵循策略的工具呼叫代理中的什麼核心問題？**
A：LedgerAgent 主要解決遵循策略的工具呼叫代理在多輪互動中，任務狀態僅隱含於提示詞內所導致的狀態管理問題。在標準代理中，觀察結果、工具回傳結果與領域策略指令都被塞入不斷增長的對話紀錄中，代理必須在每次決策時從中重新建構相關的任務狀態。這種隱式狀態管理使得代理即使成功檢索到正確紀錄，仍可能在後續回合依據過時、遺漏或錯誤的資訊做出決策，進而違反狀態相依的領域策略。

**Q2：為何標準的基於提示詞方法與現有推論階段鷹架方法難以維持策略遵循？**
A：現有的標準代理與推論階段鷹架方法（如規劃、反思或工作流程限制）大多保留了僅以提示詞為基礎的狀態表示方式。這些方法雖然能改善工具選擇或推理能力，但檢索到的紀錄與策略仍然嵌入在不斷增長的原始互動紀錄中，導致任務狀態在決策當下仍保持隱式。因此，代理在多輪對話後容易遺失關鍵事實的時間脈絡，或無法正確地將領域策略與當前任務狀態進行比對，最終產生語法正確但實質違規的工具呼叫。

**Q3：在客戶服務領域中，明確的狀態管理為何特別重要？**
A：客戶服務領域涉及複雜的領域策略，例如航班取消、訂單修改或退款條件，這些規則往往取決於特定識別碼、時間限制、乘客資格或交易歷史等動態事實。代理必須在跨回合互動中持續追蹤這些任務狀態，才能確保每一個改變環境的工具呼叫都符合當下的業務規範。一旦狀態管理出現錯誤，不僅會導致策略違規，還可能直接對客戶權益或企業營運造成實質損害，因此明確且可靠的狀態追蹤機制至關重要。

**Q4：LedgerAgent 的兩個核心確定性元件是什麼，它們如何在代理迴圈中運作？**
A：LedgerAgent 包含兩個確定性元件：綱要錨定的分類帳（ledger）與策略閘門（policy gate）。分類帳負責將成功的唯讀工具回傳結果投影為以規範路徑為鍵值的強型別字典，並在每一回合重新注入提示詞中，使代理能透過查閱而非搜尋原始紀錄來掌握當前任務狀態。策略閘門則在改變環境的工具呼叫執行前，根據分類帳中的欄位評估其是否違反以述語表達的領域策略，並在偵測到違規時阻擋動作並回傳具體的回饋資訊。

**Q5：相較於標準代理，LedgerAgent 的綱要錨定分類帳在狀態表示上的關鍵創新是什麼？**
A：LedgerAgent 的關鍵創新在於將隱含於提示詞中的任務狀態外顯化為獨立、結構化的強型別物件，從根本上改變了狀態的表示方式。不同於標準代理必須從冗長的對話紀錄中重新建構狀態，分類帳透過綱要錨定的設計，將工具回傳的觀察結果整理成以標準化路徑為鍵的緊湊字典，確保資料型態與語意的一致性。這種設計讓代理在每一回合都能直接查閱當前狀態，並使策略閘門能精確地針對特定欄位進行規則檢查，將失敗邊界從事後補救轉移到事前預防。

**Q6：為何 LedgerAgent 僅針對改變環境的工具呼叫設置策略閘門，其回饋機制如何運作？**
A：LedgerAgent 僅對改變環境的工具呼叫施加策略閘門，因為這類操作（如取消預訂、發放退款或修改帳戶）會對外部系統產生不可逆的實質影響，而唯讀呼叫不會造成狀態汙染或業務風險。策略閘門透過評估以述語形式定義的領域規則來檢查提案呼叫，一旦發現違反狀態相依的策略限制，便會阻擋該動作並回傳明確的回饋，指出違反的具體規則以及與之分類帳狀態衝突的欄位值。這使得代理在真正影響環境之前，有機會根據回饋修正其計畫或向使用者說明無法執行的原因，從而實現以策略為依據的決策修正。

**Q7：LedgerAgent 在哪些基準測試與模型上進行評估？**
A：研究團隊在四個來自 τ2-bench 與 τ-Trait 的客戶服務領域上評估 LedgerAgent，這些領域結合了多輪對話、結構化紀錄與操作性領域策略，能真實反映互動式工具使用場景的複雜度。評估採用混合模型面板，同時納入開放權重模型與封閉權重模型，以驗證方法在不同骨幹模型上的通用性。這樣的設計確保了實驗結果不僅限於特定模型架構，而能廣泛適用於當前主流的大型語言模型生態系。

**Q8：實驗的主要量化結果為何，特別是在一致性指標上的表現？**
A：實驗結果顯示，LedgerAgent 在大多數評估的領域與模型組合上均提升了 pass^k 表現，顯示其能有效改善遵循策略的工具呼叫成功率。特別值得注意的是，在更嚴格的多試行一致性指標（較高的 k 值）下，LedgerAgent 的增益最為顯著，這意味著相較於基於提示詞的標準方法，它在獨立多次試行中展現出更高的一致性與穩定性。這項發現凸顯了顯式狀態管理對於降低代理因提示詞累積雜訊而產生不一致行為的關鍵價值。

**Q9：消融研究揭示了分類帳與策略閘門各自的什麼貢獻？**
A：消融研究證實，LedgerAgent 的整體效能提升主要來自兩個核心元件的協同作用：強型別分類帳與策略閘門的動作管制。單獨引入結構化的分類帳能改善代理對當前任務狀態的查閱與理解，而策略閘門則進一步確保改變環境的呼叫在執行前通過狀態相依的策略限制檢查。這表示若僅將工具回傳結果以非結構化文字形式塞入提示詞，或僅在事後檢查策略，都無法達到同等程度的錯誤預防效果，唯有結合兩者才能顯著降低策略違規的發生率。

**Q10：在哪些實際客戶服務場景中，LedgerAgent 能帶來最大的營運效益？**
A：LedgerAgent 在涉及高風險、多條件業務規則的客戶服務場景中能發揮最大效益，例如航空公司的機票退改簽、金融機構的帳戶異動或電商平台的訂單退款與換貨流程。在這些情境中，代理必須同時追蹤使用者身份、交易時間、商品狀態與保險資格等多項動態事實，且任何錯誤的環境改變都可能導致財務損失或法律糾紛。透過分類帳明確維護這些任務狀態，並在執行前以策略閘門驗證業務規則，企業能顯著降低人為或代理錯誤所帶來的營運風險。

**Q11：從產品整合的角度，LedgerAgent 如何在不重新訓練模型的前提下導入現有系統？**
A：LedgerAgent 作為純推論階段方法，無需對底層語言模型進行額外的訓練、微調或權重更新，因此能直接部署於現有的生產級代理系統之上。開發團隊只需定義好領域資料的綱要結構與策略規則的述語表示，即可將分類帳建構與策略閘門檢查作為代理迴圈中的確定性中間層。這種模組化設計大幅降低了導入門檻，使企業能在保留現有模型與提示工程投資的同時，顯著提升系統在狀態追蹤與策略遵循方面的可靠性。

**Q12：LedgerAgent 的設計哲學可能對未來高風險服務環境的代理架構產生什麼影響？**
A：LedgerAgent 的設計哲學可能會推動未來高風險服務環境中的代理架構，從「純粹依賴模型推理與提示工程」轉向「模型能力與系統級狀態機制互補」的典範。它示範了如何在不更動模型權重的情況下，透過外顯的結構化狀態與確定性管制閘門來彌補大型語言模型在長程記憶與精確規則遵循上的固有侷限。這種將狀態追蹤與策略遵循視為系統層級機制的做法，有望成為醫療、法律、金融等對正確性要求極高之領域的標準設計原則。

**Q13：LedgerAgent 的方法存在哪些已承認的固有侷限？**
A：儘管 LedgerAgent 提升了狀態管理的明確性，但其效能上限仍受制於底層語言模型正確理解綱要、產生符合規範路徑之工具呼叫的能力。分類帳的品質完全依賴成功工具回傳結果的正確性與完整性，若初期的唯讀呼叫因模型幻覺或使用者輸入模糊而導致錯誤狀態被寫入，後續的策略閘門便會基於錯誤前提進行判斷。此外，策略閘門目前僅能檢查已預先定義為述語的規則，對於需要複雜常識推理或隱含語境判斷的灰色地帶策略，其覆蓋範圍仍然有限。

**Q14：即使在有分類帳的情況下，LedgerAgent 仍可能在哪些條件下失效？**
A：LedgerAgent 可能在工具回傳結果本身不完整或語意模糊時失效，例如外部系統回傳的紀錄缺少關鍵時間戳記，導致分類帳無法正確評估 24 小時取消窗口等時間相依策略。另一種失敗情境是模型產生的環境改變呼叫在語法上正確，但其意圖與分類帳欄位的對應關係存在歧義，使得策略閘門無法正確比對述語條件。此外，若領域策略涉及跨多個獨立工具呼叫的隱含狀態推論（例如需要綜合使用者歷史行為與當前對話情緒），單純基於強型別分類帳的欄位檢查可能不足以捕捉所有違規風險。

**Q15：未來研究可以從哪些方向延伸或補強 LedgerAgent 的分類帳方法？**
A：未來研究可探索讓分類帳自動擴展綱要以納入對話中推論出的隱含事實，而非僅限於結構化的工具回傳結果，從而更全面地掌握任務狀態。另一個方向是將策略閘門從目前的確定性述語檢查，擴展為結合輕量級推理模型或神經符號方法的混合式驗證器，以處理更細緻且語境相依的領域規則。此外，研究人員亦可調查在多代理協作環境中，如何透過分散式分類帳機制讓多個代理共享並同步任務狀態，同時維持跨代理的策略一致性與可解釋性。

## 實務應用指南

### 適用場景

1. **航空與旅遊訂位客服**：處理機票取消、改期或升等時，代理需跨回合維護訂位代號、航班編號、乘客資訊、票價規則與 24 小時取消限制等任務狀態，並在執行環境改變工具（如 `cancel_reservation`）前確認策略條件。
2. **金融保險理賠與退費**：執行退款、理賠核可或保單解約等動作前，必須確認保單狀態、猶豫期、理賠次數或帳戶餘額等狀態相依的策略限制，避免語法正確但違規的交易送達核心系統。
3. **醫療掛號與病歷調度**：根據病人過敏史、既有預約、醫師班表或健保給付條件等結構化狀態，決定是否允許新增、修改或取消掛號，確保環境改變工具不會違反臨床或行政政策。
4. **企業 IT 服務台與權限異動**：在變更帳號權限、重置密碼或刪除帳戶前，查核員工在職狀態、部門政策、最近異動紀錄與相依系統狀態，防止錯誤的環境改變工具呼叫影響生產環境。
5. **電商訂單修改與物流攔截**：處理地址變更、商品退換或出貨攔截時，需追蹤訂單狀態、物流階段與促銷活動限制，並在呼叫倉儲或金流 API 前以策略閘門確認是否滿足條件。

### 實作前置條件

**資料需求**
- 領域資料綱要（Schema）：定義工具回傳結果如何映射至分類帳的 canonical paths，以及強型別字典的欄位規格。
- 領域策略規則集：可表示為狀態謂詞的明確業務規則，用於判斷環境改變工具是否違規。
- 工具定義與歷史對話紀錄：包含工具名稱、參數規格與回傳格式，作為分類帳投影的輸入來源。

**運算需求**
- 標準 LLM 推論端點：支援工具呼叫的開放權重模型或封閉權重模型皆可，無需額外訓練叢集。
- 極低額外開銷：分類帳維護與策略閘門皆為確定性元件，僅需傳統後端運算資源（如鍵值儲存與條件判斷），不增加 LLM 呼叫次數。

**技能需求**
- 後端工程能力：建構分類帳的儲存、投影、渲染與查閱（lookup）管線。
- 領域知識工程：將業務規則轉譯為基於分類帳欄位的條件判斷式，並區分環境改變與唯讀工具。
- 提示詞工程：設計分類帳注入提示詞的模板，確保模型能正確利用結構化狀態進行決策。

### 實作步驟建議

1. **綱要設計與分類帳建模**：依據領域資料結構定義 canonical paths，建立強型別字典規格，確保每次成功的工具回傳都能穩定投影至固定欄位，而非散亂地留在原始對話紀錄中。
2. **策略規則形式化**：將領域策略拆解為狀態相依的謂詞，明確標註哪些工具屬於環境改變工具（如取消、退款、更新），哪些為唯讀工具（僅查詢不觸發閘門）。
3. **代理迴圈改裝**：在標準代理每回合成功執行工具後，將回傳結果寫入分類帳；每回合開始時，將當前分類帳狀態渲染至提示詞的獨立區塊，使任務狀態明確化。
4. **策略閘門植入**：在環境改變工具呼叫送達外部系統前，插入確定性檢查層，比對當前分類帳狀態與策略規則；若偵測到策略違規，阻擋該動作並回傳結構化反饋（如違反的規則與衝突狀態）。
5. **提示詞模板化**：設計固定格式（如 Markdown 或 JSON 區塊）將分類帳注入提示詞，與使用者發言及系統指令區隔，降低模型從雜亂歷史中重建狀態的負擔。
6. **漸進式驗證**：先以唯讀流程驗證狀態追蹤與分類帳渲染的正確性，再啟用環境改變動作與策略閘門阻擋機制，最後以多試行一致性指標（如嚴格的 pass^k）評估穩定度。

### 潛在風險與注意事項

1. **分類帳與環境狀態不一致（Stale State）**：外部系統可能透過其他管道被更新，導致分類帳中的任務狀態過時。建議對高風險欄位設計定期刷新機制、版本戳記或唯讀工具重新查核流程。
2. **策略閘門誤殺合法邊緣案例**：過於僵硬的規則可能阻擋正當操作。應保留人工覆核或動態例外處理管道，並記錄所有阻擋事件供後續調校規則。
3. **綱要漂移與解析失敗**：工具回傳格式異動會導致投影至強型別字典失敗。需實作嚴格型別驗證與降級方案（fallback 至原始對話紀錄），避免因解析錯誤而遺失關鍵狀態。
4. **狀態膨脹與提示詞長度**：多回合累積後分類帳可能過大。應設計狀態彙整、過期淘汰或分層渲染機制，避免超出模型上下文限制而影響效能。
5. **模型忽略即時使用者輸入**：過度強調結構化分類帳可能使模型忽視當前回合的新觀察結果。需在提示詞中平衡「分類帳狀態」與「最新使用者發言」的權重，防止決策依據片面化。

### 與其他技術的整合建議

1. **與 RAG／知識庫整合**：分類帳負責動態任務狀態（隨對話變動），RAG 提供靜態領域知識（如政策文件、商品說明），兩者可在提示詞中分區渲染，互補而非重疊。
2. **與 API 閘道／服務網格整合**：策略閘門可部署為 API Gateway 前的獨立策略層（如 OPA、Envoy ext_authz），將代理層的業務規則與基礎設施層的授權機制對齊，形成縱深防禦。
3. **與可觀測性平台整合**：分類帳狀態與阻擋事件應輸出為結構化日誌，接入 LLM Ops 或 SIEM 系統，以便追蹤決策依據、稽核策略違規並進行根因分析。
4. **與模型訓練管線整合**：策略閘門產生的阻擋反饋與修軌跡可作為高品質訓練資料，用於後續微調或強化學習，但 LedgerAgent 本身維持推論階段零訓練的優勢，可與模型層改良並行。
5. **與多代理系統整合**：分類帳可作為跨代理共享狀態的標準化介面，避免每個代理各自從原始對話紀錄重建任務狀態，降低多代理協作時的狀態不一致風險。

### 給不同背景讀者的閱讀建議

**給初學者**：把 LedgerAgent 想像成客服人員的「電子工作單」加上「自動主管審核」：它幫 AI 把查到的客戶資料整理成固定表格，並在執行退款或取消前自動核對公司規定。如果你剛接觸 AI 代理，建議先理解「為什麼 AI 會記錯資料」這個問題，再對照圖一的情境，就能掌握本文核心。

**給 AI 工程師**：本文的實作重點在於「確定性元件」的設計：如何將工具回傳投影為綱要錨定的強型別字典，以及如何在不增加 LLM 呼叫的前提下，於推論迴圈中插入策略閘門。建議聚焦第 3 節的方法論，特別注意環境改變與唯讀工具的分類，並評估你目前使用的代理框架（如 LangChain、LlamaIndex）是否容易植入狀態管理層。

**給研究人員**：本文將狀態追蹤與策略遵循重新定義為系統層級機制，而非純粹的模型能力問題。建議關注論文對「狀態隱含於提示詞」這一主流設計的批判，以及 pass^k 在多試行一致性指標下的實驗設計。這為後續研究開啟了「推論階段狀態抽象」與「形式化驗證」的結合方向。

**給產品經理**：這是一個「低訓練成本、高合規價值」的推論階段方案。重點在於它不需要重新訓練模型，就能降低客服場景中的策略違規風險。建議評估你負責的領域中，哪些環境改變動作（如退款、解約、權限變更）具有明確的狀態條件，這些就是導入 LedgerAgent 的高 ROI 場景。
