## ⚡ TL;DR

現有智能體駕馭架構難以直接整合進RL，且駕馭式訓練帶來重分詞、樣本合併與優勢估計等新挑戰。

## 摘要翻譯

現代智能體運作於智能體駕馭架構（agent harness）之中，該架構負責管理工具、上下文與控制流程，使駕馭架構成為智能體系統的關鍵環節。我們最初提出的 Agent Lightning 引入了一種分離式架構，可透過 LLM 端點代理（LLM endpoint proxy）將任意智能體連接至強化學習訓練；此方法後來被 verl Uni-Agent、AReaL 2.0、slime 與 Polar 等框架採用。我們將此典範稱為駕馭式智能體強化學習（harnessed agentic RL），即部署階段的駕馭架構直接參與模型的後訓練（post-training）。駕馭式智能體強化學習與傳統智能體強化學習有根本差異：由駕馭架構而非訓練引擎主導環境互動迴圈，而訓練器僅觀察到一連串 LLM 請求–回應配對（request-response pairs）。這衍生出重新詞元化（retokenization）、樣本合併（sample merging）、優勢計算（advantage calculation）、損失正規化（loss normalization）與後端排程（backend scheduling）等挑戰，並可能大幅影響訓練的穩定性與成效。我們提出 Agent Lightning v1.0，一個輕量級的駕馭式智能體強化學習框架，僅以約 3,500 行程式碼實作。它支援任意智能體駕馭架構，並可作為研究上述挑戰的實用試驗平台。我們在指令遵循（instruction-following）、搜尋（search）與編碼智能體（coding agents）上進行評估，並提供一套完整可複現（reproducible）的編碼智能體強化學習流程。僅使用 6K 筆訓練範例與適中的運算資源，強化學習便使 Qwen3.5-9B 在 SWE-bench Verified 上的表現從 41.8% 提升至 56.4%，帶來 14.6 個百分點的絕對提升。我們公開釋出完整的工作流程與訓練腳本，以促進駕馭式智能體強化學習的可複現研究。

### 核心貢獻（3～5點）
- 明確界定「駕馭式智能體強化學習（harnessed agentic RL）」典範，說明其與傳統智能體強化學習的關鍵差異：由智能體駕馭架構（agent harness）主導環境互動迴圈，訓練器僅觀察 LLM 請求–回應配對。
- 系統性指出此典範帶來的五大技術挑戰：重新詞元化、樣本合併、優勢計算、損失正規化與後端排程，並強調其對訓練穩定性與成效的影響。
- 提出輕量級開源框架 Agent Lightning v1.0（約 3,500 行程式碼），支援任意智能體駕馭架構，可作為駕馭式智能體強化學習的研究試驗平台。
- 在指令遵循、搜尋與編碼智能體上進行實證評估，並提供完整可複現的編碼智能體強化學習流程。
- 以僅 6K 訓練範例與適中運算資源，使 Qwen3.5-9B 在 SWE-bench Verified 上從 41.8% 提升至 56.4%，並公開釋出工作流程與訓練腳本以促進可複現研究。

### 適合對象
從事大型語言模型後訓練（post-training）、智能體系統設計、強化學習演算法與開源可複現研究的學術研究者與工程師，特別是關注如何將部署階段的智能體駕馭架構整合進 RL 訓練流程的讀者。

## 深度分析

#### 方法論解析

Agent Lightning v1.0 的核心方法論是將 **agent harness（智能體駕馭架構）** 與 **RL trainer（強化學習訓練器）** 解耦，透過一個 **LLM endpoint proxy（LLM 端點代理）** 讓任意的 agent harness 幾乎無需修改即可參與 **harnessed agentic RL（駕馭式智能體強化學習）**。在傳統的 agentic RL 中，訓練引擎本身擁有環境互動迴圈，策略模型（policy model）幾乎直接與環境互動，並產生一條連續的 token 軌跡（rollout）。相對地，在 harnessed agentic RL 中，agent harness 保留了部署時的上下文建構、工具執行、控制流程與編排邏輯，策略模型只透過類似 OpenAI API 的介面看到一連串的 **request-response pairs（請求-回應對）** \((p_1,a_1),(p_2,a_2),\dots\)。這使得 latent state（潛在狀態）同時包含 harness state 與 environment state，而訓練器僅能在模型邊界觀察到離散的 LLM 呼叫。

為了在這種典範下正確且穩定地訓練，Agent Lightning v1.0 針對五項關鍵挑戰提出設計選擇：

1. **Retokenization（重新分詞）與 sample merging（樣本合併）**：agent harness 通常以文字訊息與模型 API 溝通，而 RL 訓練則在 token 層級運作。當把連續兩次呼叫合併時，即使文字內容未變，重新分詞後的 token IDs 可能與模型當初取樣時的 token IDs 不同，破壞 token-level continuity（token 層級連續性）。Agent Lightning v1.0 必須謹慎處理合併條件，避免錯誤地將無法安全合併的樣本拼接。

2. **Advantage calculation（優勢計算）**：一條 rollout 在 harnessed 設定下可能動態產生多個 training samples（訓練樣本），原因包括 retokenization 失敗、spawn subagents（產生子智能體）、context summarization（上下文摘要）等。如何將最終 reward（獎勵）合理分配到這些動態樣本，是影響訓練訊號品質的關鍵。

3. **Loss normalization（損失正規化）**：由於每個 rollout 產生的樣本數不固定，若仍採用 sample-level normalization（樣本層級正規化），則產生較多樣本的 rollout 會獲得較大的最佳化權重，可能導致訓練不穩定。Agent Lightning v1.0 需要在 rollout-level 與 sample-level 之間做出權衡。

4. **Backend scheduling（後端排程）**：一個 rollout batch 實際產生的樣本數必須在 harness 執行後才能確定，但 GPU 數量與平行配置是固定的。系統必須將變動的樣本集合劃分為 training steps（訓練步驟）與 mini-batches（小批次），並在固定 GPU worker 間平衡負載。

5. **輕量化設計**：整個框架僅約 3,500 行程式碼，強調簡潔與可研究性，讓研究者能夠快速實驗不同設計選擇對上述挑戰的影響。

整體而言，Agent Lightning v1.0 並非提出全新的 RL 演算法，而是提供一個「駕馭式」的訓練基礎設施，讓現有 agent harness 的部署語義能夠直接延續到 post-training（後訓練）階段。這種 disaggregated architecture（解耦架構）的價值在於降低整合門檻：研究者無需將複雜的 harness（如 OpenHands、Codex、mini-SWE-agent）重寫進 RL 框架，只需讓 harness 透過 LLM endpoint proxy 呼叫模型即可。

#### 實驗數據解讀

論文評估了三類 agent：instruction-following agent（指令遵循智能體）、search agent（搜尋智能體）與 coding agent（程式碼智能體）。其中最具指標性的結果來自 coding agent 的訓練：

- **基礎模型**：Qwen3.5-9B
- **訓練資料**：基於開源的 SWE-smith dataset，經過資料清理後僅使用 6K 訓練樣本
- **評估基準**：SWE-bench Verified
- **效能提升**：從 41.8% 提升至 56.4%，絕對提升 14.6 個百分點

這個結果具有幾層意義。首先，它證明了 harnessed agentic RL 在複雜的程式碼任務上能夠帶來顯著的相對增益（約 35% 相對提升），而且僅需少量訓練樣本與 modest compute（適中運算資源）。這與傳統認知中 coding agent RL 需要大量資料與大量運算的印象形成對比。其次，41.8% 的基線已經是經過某種形式後訓練或提示工程後的 Qwen3.5-9B，RL 進一步將其推向 56.4%，顯示 RL 能夠有效校正 harness 內的長期決策行為，例如搜尋策略、工具呼叫順序、錯誤恢復等。

然而，也需要謹慎解讀：SWE-bench Verified 的 56.4% 雖然優於基礎模型，但與當前頂尖的專用 coding agent（例如某些基於 Claude 或 GPT-4o 的系統）相比可能仍有差距。此外，6K 樣本的規模相對較小，結果的泛化性與對不同 harness、不同模型規模的適用性仍需更多實驗驗證。論文也提到現有 agent framework 對 coding agent 的支援有限，因此這個實驗更像是一個「可重現的端到端範例」，而非對所有可能設定的全面掃描。

對於 instruction-following 與 search agent，論文僅簡要提及有進行評估，但未提供詳細數據。這使得我們難以判斷 Agent Lightning v1.0 在這兩類任務上的絕對強度，但可以推論其設計選擇在這些相對簡單的互動場景中應能穩定運作。

#### 與現有研究的比較

Agent Lightning v1.0 延續並擴展了原始 Agent Lightning 的解耦架構。與早期框架如 **verl**、**AReaL**、**slime** 相比，這些傳統框架通常要求使用者將 agent loop（智能體迴圈）直接實作在訓練框架內部，導致整合現有 harness 的成本高昂。近年來，**verl Uni-Agent**、**AReaL 2.0**、**slime v0.3.0** 與 **Polar** 也開始採用類似的 proxy-based（基於代理）方法，顯示 harnessed agentic RL 正逐漸成為社群共識。Agent Lightning v1.0 的差異化在於：

- **系統性刻畫挑戰**：論文首次系統性地描述 retokenization、advantage calculation、loss normalization 與 backend scheduling 等實作挑戰，並說明這些選擇如何影響 algorithmic correctness（演算法正確性）與 training stability（訓練穩定性）。
- **輕量可研究**：約 3,500 行程式碼的設計使其成為研究上述挑戰的 practical testbed（實用試驗平台），相較於功能龐大但複雜的框架更易於修改與分析。
- **coding agent 的完整範例**：提供從 SWE-smith 資料清理到可重現訓練腳本的完整 pipeline，填補了現有框架在 coding agent RL 上的支援缺口。

然而，Agent Lightning v1.0 也存在明顯限制。首先，作為輕量框架，它可能缺乏大型分散式訓練系統所具備的進階優化（例如精細的 pipeline parallelism、大規模資料載入、容錯機制）。其次，論文對於各項挑戰的設計選擇雖有說明，但未進行大規模的 ablation study（消融實驗）來量化每個選擇的影響。第三，實驗主要集中在 Qwen3.5-9B 與 SWE-bench Verified，對於更大模型、更多 harness、更長 horizon 任務的適用性仍需驗證。最後，harnessed agentic RL 將環境互動迴圈交還給 harness，雖然保留部署語義，但也限制了訓練器對內部狀態的觀察，可能使得 credit assignment（信用分配）問題更加困難。

#### 可重現性評估

可重現性是本研究的一大賣點。論文明確表示將 release（釋出）完整的 workflow（工作流程）與 training scripts（訓練腳本）。資料方面，實驗基於開源的 **SWE-smith dataset**；模型方面使用開源的 **Qwen3.5-9B**；評估使用公開的 **SWE-bench Verified**。這些選擇大幅降低了重現門檻。

具體而言，可重現性的優勢包括：

- **開放資料與模型**：SWE-smith 與 Qwen3.5-9B 均為公開資源，研究者無需取得私有資料或 API 即可複製主要實驗。
- **完整 pipeline**：論文強調提供資料清理流程與可重現訓練腳本，這對於 coding agent 研究特別重要，因為環境設定與資料清理往往是重現的最大障礙。
- **輕量程式碼**：3,500 行程式碼意味著研究者能夠快速理解、修改與除錯，有助於社群進行後續研究。

不過，可重現性仍有潛在風險。首先，論文未明確說明是否會釋出訓練後的 model weights（模型權重），若僅釋出腳本而無權重，則其他研究者需要自行承擔訓練成本。其次，agent harness 的環境依賴（例如 Docker、特定工具鏈、SWE-bench 的執行環境）可能導致「重現但結果不同」的問題，需要詳細的環境版本紀錄。第三，6K 訓練樣本的規模雖小，但 harness 執行本身可能仍需要可觀的運算資源與時間，對於資源有限的研究者仍是挑戰。整體而言，Agent Lightning v1.0 在可重現性上優於許多僅釋出論文與部分程式碼的研究，但最終評價仍取決於釋出內容的完整性與文件品質。

#### 未來研究方向

Agent Lightning v1.0 所揭示的 harnessed agentic RL 挑戰，為後續研究開啟了多個方向：

1. **Token-level continuity 的保留機制**：發展能夠避免 retokenization 不一致的技術，例如強制使用一致的 tokenizer、在 proxy 層記錄原始 token IDs，或設計無需合併樣本的訓練演算法，以確保多輪 LLM 呼叫能被正確地視為單一軌跡。

2. **多樣本軌跡的 credit assignment**：針對一條 rollout 產生多個 training samples 的情況，研究更細緻的 advantage 分配方法，例如將 harness 內部的中間狀態作為輔助訊號、設計適用於 subagent（子智能體）與 summarization 的獎勵塑形（reward shaping），或引入 hierarchical RL（階層式強化學習）框架。

3. **動態樣本數的後端排程**：設計能夠在樣本數量不確定的情況下，仍保持 GPU 高利用率與負載平衡的 scheduling 演算法，例如動態 mini-batch 重組、彈性資料平行策略，或結合 online 與 offline 混合訓練。

4. **Loss normalization 的理論與實證分析**：系統比較 rollout-level、sample-level、token-level 等不同正規化策略對收斂速度與最終效能的影響，並建立 harnessed agentic RL 的理論收斂保證。

5. **擴展到更多 harness 與任務**：將 Agent Lightning v1.0 應用於 multi-agent（多智能體）harness、網頁瀏覽、科學計算、機器人控制等更長 horizon 與更複雜互動的場景，驗證其通用性。

6. **結合 SFT 與 RL 的混合訓練**：探索在 harnessed 設定下，如何有效地結合 supervised fine-tuning（監督式微調）與 RL，例如利用 SFT 建立穩定基線，再以 RL 進行策略優化，並研究兩階段資料與 harness 語義的一致性。

7. **安全性與評估 harness**：發展專門用於評估與對齊（alignment）的 harness，讓 harnessed agentic RL 不僅提升任務效能，也能改善安全性、可解釋性與人類偏好對齊。

總結來說，Agent Lightning v1.0 不僅是一個輕量框架，更是一個概念驗證：未來的 agentic RL 系統應該尊重並利用部署時的 agent harness，而非試圖將其取代。後續研究若能解決其所提出的核心挑戰，將有機會讓 harnessed agentic RL 成為訓練複雜智能體的主流典範。

## 論文問答

**Q1：駕馭式智能體強化學習（harnessed agentic RL）想要解決的核心問題是什麼？為什麼智能體駕馭架構（agent harness）被視為智能體能力的關鍵組成？**

A：現代智能體並非獨立運作的大型語言模型，而是運行在負責管理工具、執行環境、上下文與控制流程的駕馭架構之中，因此該架構決定了智能體如何觀察環境、進行長程行動以及從失敗中恢復。傳統強化學習框架通常要求把智能體與環境的互動迴圈直接實作在訓練引擎內，這會迫使開發者重寫或遷移既有的複雜駕馭架構。駕馭式智能體強化學習讓部署時的駕馭架構直接參與後訓練，保留其原本的上下文策略、工具協定與執行語義，從而解決了整合困難並確保訓練與部署分佈一致。

**Q2：現有的強化學習框架（如 verl、AReaL、slime）為何難以整合真實世界的智能體駕馭架構？**

A：這些早期框架一般要求使用者在訓練引擎內部自行實作智能體迴圈，這等於要重新實現駕馭架構的上下文建構、工具執行與協調邏輯。真實世界的駕馭架構（例如 OpenHands、Codex 或 Claude Code）往往程式碼龐大、依賴眾多，並且具有特定的執行語義，直接嵌入訓練框架既昂貴又容易出錯。Agent Lightning 提出的解耦式架構透過 LLM 端點代理（proxy）讓駕馭架構保持黑箱運作，從而避免了全面重寫。

**Q3：駕馭式智能體強化學習與傳統智能體強化學習在狀態與觀察上有何根本差異？**

A：兩者都可以用部分可觀察馬可夫決策過程（POMDP）建模，但傳統方法中的潛在狀態主要是環境狀態，策略模型幾乎直接與環境互動並看到一條連續延伸的標記歷史。相對地，駕馭式方法中的潛在狀態同時包含駕馭架構狀態與環境狀態，策略模型只能看到駕馭架構每次呼叫時建構的提示詞以及對應回應。因此，一筆 rollout 不再是一條線性標記軌跡，而是一系列請求–回應對，中間的駕馭與環境轉換對訓練器而言是隱藏的。

**Q4：Agent Lightning 提出的解耦式架構是什麼？它如何將任意智能體連接到強化學習訓練？**

A：該架構在智能體駕馭架構與策略模型之間插入一個 LLM 端點代理，駕馭架構像平常一樣發出 API 呼叫，而代理負責把請求轉發給可訓練模型並記錄請求–回應對。這種分離意味著駕馭架構不需要知道它正被用於訓練，而訓練器也不需要理解駕馭架構的內部實作。由於幾乎不需要修改智能體端，部署時使用的同一個駕馭架構可以直接在後訓練中重複使用。

**Q5：駕馭式智能體強化學習帶來了哪些實作挑戰？為什麼它們會影響演算法的正確性與訓練穩定性？**

A：論文系統性地指出四大挑戰：重新標記化（retokenization）與樣本合併、優勢估計（advantage calculation）、損失正規化（loss normalization），以及在動態樣本數下的訓練後端排程。重新標記化可能破壞連續呼叫之間的標記層級連續性，導致樣本合併不安全；動態樣本數使得回報與優勢的歸因變得複雜；樣本層級正規化會讓產生較多樣本的 rollout 獲得不當的梯度權重；後端則必須在樣本數未知的情況下平衡固定 GPU 的負載。這些選擇都會直接影響梯度計算是否正確以及訓練是否穩定。

**Q6：Agent Lightning v1.0 如何處理重新標記化與損失正規化這兩項挑戰？**

A：針對重新標記化，該框架強調必須在標記層級驗證連續性，只有當後續提示詞中前一次回應的標記 ID 與模型當初取樣的標記完全一致時，才能安全合併樣本。針對損失正規化，它避免僅以樣本數為單位進行正規化，以防某些 rollout 因產生較多片段而獲得過大的優化權重。這些設計選擇旨在讓訓練目標與真實回報保持一致，同時維持程式碼的簡潔與可檢視性。

**Q7：Agent Lightning v1.0 在哪些智能體任務上進行評估？編碼智能體的實驗設定有何特別之處？**

A：該框架在一般指令遵循、搜尋與編碼三類智能體上進行評估。編碼智能體的設定特別值得注意，因為現有框架很少提供完整的資料清理流程與可復現的訓練腳本，原因包括資料清洗複雜、環境設定困難以及運算資源需求大。作者基於開源的 SWE-smith 資料集與 Qwen3.5-9B 模型，提供了一條完整的資料清理管線與可復現的訓練腳本，填補了這一缺口。

**Q8：在 SWE-bench Verified 上的主要量化結果是什麼？為什麼這個結果具有意義？**

A：僅使用 6K 筆訓練樣本與適度運算資源，單靠強化學習就將 Qwen3.5-9B 在 SWE-bench Verified 上的表現從 41.8% 提升到 56.4%，絕對進步達 14.6 個百分點。這個結果顯示，當部署時的駕馭架構被保留在訓練迴路中時，即使資料與運算相對有限，也能帶來顯著的能力提升。它也證明了基於代理的訓練典範對於複雜的編碼智能體是實用且有效的。

**Q9：文中是否提到消融實驗或比較？這些結果對駕馭架構的重要性有何暗示？**

A：提供的摘錄與引言並未包含詳細的消融實驗，但單靠強化學習就取得的大幅進步暗示：讓部署駕馭架構參與訓練迴路對於能力遷移至真實任務執行至關重要。由於駕馭架構掌握上下文建構與工具執行，策略模型的任何改進都是在與部署時相同的提示詞與工具分佈下被優化的。未來研究可以進一步消融樣本合併策略、正規化方式以及駕馭架構特定上下文政策的影響。

**Q10：駕馭式智能體強化學習在哪些實際應用場景中最有價值？**

A：這種典範對於已經擁有成熟駕馭架構的組織特別有價值，例如管理複雜工具呼叫的編碼助理、企業搜尋智能體，或需要多步推理與錯誤恢復的客戶服務機器人。工程師不需要把駕馭架構重寫進訓練框架，而是透過現有的 API 邊界訓練底層模型，從而保留所有部署語義。這大幅降低了以強化學習改進生產級智能體的門檻。

**Q11：在產品化與工程部署上，採用駕馭式智能體強化學習需要考慮哪些問題？**

A：首先必須確保代理端點穩定且低延遲，因為訓練期間每次模型呼叫都會跨越服務邊界。其次，訓練後端需要能夠處理動態樣本數，並監控重新標記化的一致性，同時決定如何在多呼叫 rollout 中分配獎勵。最後，為了可復現性，必須連同模型檢查點一起版本化管理駕馭架構、工具與執行環境。

**Q12：這個典範可能對智能體訓練框架的發展帶來什麼影響？**

A：它將焦點從「由訓練引擎獨占環境互動迴圈」的單體式設計，轉向尊重既有駕馭架構邊界的解耦式系統。這可能促使更多框架採用基於代理的訓練介面，讓缺乏資源重寫複雜駕馭架構的智能體開發者也能使用強化學習。同時，它也凸顯了重新標記化、動態樣本數與跨邊界信用分配等新的演算法問題，值得學界進行系統性研究。

**Q13：作者承認或暗示了哪些限制？**

A：摘錄雖未明確列出限制，但對四大實作挑戰的系統性刻畫暗示目前的解決方案仍是初步且框架相關的。每筆 rollout 產生的樣本數不固定，使得優勢估計與正規化的理論保證變得複雜。此外，代理架構引入了服務邊界，可能帶來延遲、故障模式與除錯複雜度，這些都是傳統迴圈內建於訓練器的設計所不具備的。

**Q14：駕馭式智能體強化學習可能出現哪些失敗案例？它們會如何表現？**

A：若重新標記化處理不當，合併後的樣本可能包含與模型原始取樣不同的標記 ID，導致梯度偏誤或離策略（off-policy）錯誤。若損失以樣本數為單位正規化，那些會產生子智能體或進行上下文摘要的 rollout 可能主導整個批次，進而破壞訓練穩定性。後端排程失誤則可能在某批 rollout 產生遠超預期的樣本數時造成負載不平衡或記憶體不足。

**Q15：這項工作為未來研究與工程指出了哪些方向？**

A：未來研究可以發展針對變長請求–回應序列的理論化優勢估計方法，並為動態樣本數建立嚴謹的正規化目標。工程上則需要設計能適應駕馭架構導致之樣本變異性的 GPU 排程器。此外，將駕馭式智能體強化學習擴展到多智能體系統、安全關鍵工具以及持續線上學習部署，也是重要的下一步。

## 實務應用指南

### 適用場景

1. **企業內部程式碼修復代理（Coding Agent）**  
   當組織已使用 OpenHands、mini-SWE-agent 或自研的程式碼代理框架時，可透過 Agent Lightning v1.0 把「原本部署時的智能體駕馭架構」直接納入 RL 訓練迴路，讓模型學會更符合內部工具鏈、程式碼規範與錯誤處理流程的修復行為。

2. **具備外部搜尋與檢索工具的問答代理（Search Agent）**  
   適合需要讓 LLM 學會「何時搜尋、用什麼關鍵字、如何整合多輪搜尋結果」的場景。由於搜尋 harness 通常包含動態工具呼叫與上下文摘要，駕馭式智能體強化學習能保留這些部署時的互動語義，避免在訓練框架內重寫代理迴路。

3. **多步驟指令遵循與流程自動化代理**  
   例如客服、表單填寫、IT 維運等需要長期規劃、子代理委派與錯誤恢復的任務。透過 harness 直接參與訓練，模型能學到與實際上線環境一致的上下文建構與控制流決策。

4. **快速驗證新 RL 演算法設計的研究原型**  
   Agent Lightning v1.0 僅約 3,500 行程式碼，適合學術或產業研究團隊作為「駕馭式智能體強化學習」的輕量實驗平台，用來比較不同 retokenization、advantage 計算或 loss normalization 策略。

5. **已有 LLM endpoint proxy 的代理產品化**  
   若產品已透過 OpenAI-compatible API 提供模型服務，可最小改動地將現有代理對接到 RL 訓練，縮短從研究到上線的距離。

### 實作前置條件

**資料準備**
- 與目標代理任務對應的訓練樣本，例如 SWE-smith 這類開源程式碼修復資料集，或自行蒐集的指令—軌跡對。
- 每筆資料需能驅動智能體駕馭架構產生一或多個 LLM request-response pairs，並在最終任務層級有可計算的 reward（如 SWE-bench 通過率）。
- 建議先執行資料清理與環境設定驗證，確保 harness 在訓練前後的行為一致。

**運算資源**
- 論文展示使用 6K 訓練樣本與適中運算即可在 Qwen3.5-9B 上取得顯著提升；實際產品化時，建議至少準備可微調 7B–30B 等級模型的 GPU 叢集，並預留 harness 執行環境（容器、沙箱、外部工具）的運算資源。
- 需要能同時承載「代理 harness 執行」與「RL 訓練後端」的排程能力，因為樣本數量在 harness 執行後才會動態決定。

**技術能力**
- 熟悉 LLM 微調與強化學習（PPO / GRPO / REINFORCE++ 等）基本概念。
- 能閱讀與修改智能體駕馭架構程式碼，並確保其可透過 LLM endpoint proxy 被呼叫。
- 具備 tokenization、reward engineering 與分散式訓練除錯經驗，因為 retokenization 與動態樣本數會直接影響訓練穩定性。

---

### 實作步驟建議

1. **固定部署時的 harness 行為**  
   先確認現有智能體駕馭架構在推理階段的上下文建構、工具呼叫與錯誤恢復邏輯，並將其封裝為可重複呼叫的服務。訓練時必須使用與部署時相同的 harness 版本，避免語義漂移。

2. **建立 LLM endpoint proxy**  
   在 harness 與 RL 訓練器之間架設 proxy，攔截每次模型呼叫的 prompt 與 response。proxy 需記錄原始 token IDs、採樣參數與對應的 harness 狀態，供後續樣本合併與優勢計算使用。

3. **設計 reward 與任務評估**  
   定義清晰的最終任務 reward（如測試通過與否、搜尋結果正確性、指令完成度）。避免過度依賴中間步驟 reward，因為 harness 內部狀態對訓練器是潛藏的，不當的中間 reward 可能導致模型學到錯誤的捷徑。

4. **處理 retokenization 與樣本合併**  
   在將 prompt-response pairs 轉為訓練樣本時，檢查前一次 response 的 token IDs 是否與下一次 prompt 中的前綴完全一致。若不一致，應選擇不合併或採用一致的 tokenizer 與特殊 token 處理，避免 token-level 連續性被破壞。

5. **選擇 advantage 計算與 loss normalization 策略**  
   由於一次 rollout 可能產生動態數量的訓練樣本，建議在 rollout 層級進行 reward 歸因與 advantage 估計，並在 batch 層級正規化 loss，防止產生較多樣本的 rollout 獲得不當的優化權重。

6. **建立動態樣本排程後端**  
   訓練後端需能根據 harness 執行後實際產生的樣本數，動態劃分 training steps 與 mini-batches，並在固定 GPU 拓樸下平衡負載，避免部分 worker 閒置或記憶體爆滿。

7. **小規模實驗與逐步放大**  
   先以數百至數千筆樣本進行端到端訓練，驗證 reward 曲線、樣本合併正確性與 harness 穩定性；確認無誤後再擴大資料量與模型規模，並在 SWE-bench 或自訂測試集上進行嚴格評估。

### 潛在風險與注意事項

- **Retokenization 不一致導致訓練偏差**  
  即使文字內容相同，不同時間點或不同 tokenizer 設定可能產生不同 token IDs。若強行合併樣本，會讓模型看到與採樣時不一致的機率分佈。建議統一 tokenizer、記錄原始 token IDs，並在合併前做嚴格檢查。

- **動態樣本數造成優化權重失衡**  
  若仍按 sample-level 正規化 loss，長軌跡或產生多個子代理呼叫的 rollout 會獲得更高權重。應改採 rollout-level 或 token-level 正規化，並監控每個 rollout 貢獻的梯度大小。

- **Harness 執行失敗與超時**  
  外部工具、沙箱或網路搜尋可能失敗，導致 rollout 不完整或 reward 無法計算。需設計重試、逾時與 fallback 機制，並在資料清理階段過濾掉無法復現的失敗案例。

- **Reward hacking 與捷徑學習**  
  由於訓練器無法直接觀察 harness 內部狀態，模型可能學到利用 reward 定義漏洞的行為。建議使用多樣化測試集、隱藏測試案例與人類評估來驗證泛化能力。

- **部署與訓練 harness 版本不一致**  
  任何對 harness 的更新（工具新增、prompt 模板修改、錯誤處理邏輯）都可能讓訓練好的模型在上線後表現下滑。應將 harness 版本納入模型發布紀錄，並建立持續整合測試。

### 與其他技術的整合建議

- **與現有 RL 框架（verl、AReaL、slime、Polar）整合**  
  若團隊已使用這些框架，可參考 Agent Lightning v1.0 的 proxy 設計，將 harness 作為外部環境接入，而非把代理迴路重寫進訓練框架。這能保留既有框架的分散式訓練優勢，同時降低整合成本。

- **與模型服務（vLLM、TGI、SGLang）整合**  
  LLM endpoint proxy 可直接對接到這些推論引擎，利用其高效能生成與批次處理能力。需注意推論引擎的 tokenizer 行為必須與訓練端一致。

- **與可觀測性工具（Langfuse、LangSmith、Weights & Biases）整合**  
  由於 harness 內部狀態對訓練器不透明，建議在 proxy 與 harness 層級記錄完整軌跡、reward 與樣本合併資訊，便於後續除錯與模型診斷。

- **與 CI/CD 及評測平台整合**  
  對於 coding agent，可將 SWE-bench 或自訂測試集納入持續整合流程，每次模型訓練後自動執行評估，確保模型不會因 harness 或資料變動而退化。

- **與資料管線（Apache Beam、Spark、DuckDB）整合**  
  大規模資料清理與軌跡分析可藉由這些工具完成，特別是在處理 SWE-smith 這類需要環境重建與測試過濾的資料集時。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦在「為什麼要用現有代理框架來訓練」這個核心概念：傳統 RL 需要把代理迴路寫進訓練框架，而駕馭式智能體強化學習則是讓部署時的 harness 直接參與訓練。可以先從論文的圖 2 與 SWE-bench 實驗結果入手，理解這種方法如何讓模型學到更貼近實際上線環境的行為，技術細節可暫時略過。

**AI 工程師**  
請重點閱讀「挑戰」章節與 Agent Lightning v1.0 的實作選擇，特別是 retokenization、advantage 計算、loss normalization 與動態樣本排程。這些細節直接決定訓練能否收斂，建議搭配釋出的程式碼與 SWE-bench 訓練腳本一起實作，並在自有 harness 上進行小規模驗證。

**研究人員**  
論文對 harnessed agentic RL 與傳統 agentic RL 的 POMDP 差異進行了系統性刻畫，這是設計新演算法的重要基礎。建議深入分析「harness 狀態成為潛藏狀態」對 credit assignment、探索策略與樣本效率的影響，並利用 Agent Lightning v1.0 的輕量程式碼進行消融實驗。

**產品經理**  
關鍵在於評估「保留現有 harness」能帶來的產品優勢與風險：這種方法能縮短研究到上線的距離、讓模型行為更貼合實際產品，但也需要處理 harness 版本控制、運算排程與 reward 設計等工程挑戰。建議與工程團隊討論資料規模、評估指標與上線後的監控方案，再決定是否採用此路徑。
