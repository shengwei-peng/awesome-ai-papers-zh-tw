## 摘要翻譯

是否應以大型語言模型（large language model, LLM）取代既有的文字嵌入流程（text-embedding pipeline）？本研究透過一項受控的成本感知比較（controlled, cost-aware comparison）來探討此問題，比較對象涵蓋六個模型家族（model family）中的十個 LLM，以及 26 個嵌入模型（embedding model）（參數量（parameters）從 1.18 億至 140 億），並在 37 項橫跨分類（classification）、語意文字相似度（semantic textual similarity, STS）、聚類（clustering）、成對分類（pair classification）與檢索（retrieval）的任務上進行評估。總體（aggregate）而言，兩大典範（paradigm）實際上基本持平（parity）：最佳 LLM（Gemini 3.1 Pro，77.6）與最佳嵌入模型（77.2）僅相差 0.4 分。兩者的優勢因任務而異：LLM 在重推理檢索（reasoning-heavy retrieval）上領先，嵌入模型在分類上領先，兩者在聚類、STS 與成對分類上則不相上下。然而，達到這種對等水準的代價高昂：一個 LLM 的成本最高可比品質相近的嵌入模型高出 1,431 倍（每次基準測試回合（benchmark pass）分別為 154 美元與 0.11 美元），而受測的開源大型語言模型（open LLM）在相同 GPU 上處理標記（token）的速度則慢了 2.5 到 736 倍。推理標記（reasoning token）佔 LLM 推理成本（inference cost）的 28% 到 81%；在我們的消融研究（ablation）中，較低的推理預算（reasoning budget）對大多數模型而言仍能維持甚至提升檢索品質。帕雷托前沿（Pareto frontier）上包含領先的嵌入模型，以及唯一一款進入前沿的 LLM Gemini 3.1 Pro。這些結果支持一種分工（division of labour）：將嵌入模型用於相似度（similarity）、分類與聚類，並把 LLM 保留給重推理檢索。我們的程式碼、資料集與結果已公開於 https://github.com/embeddings-benchmark/embedders-dilemma。

### 核心貢獻（3～5點）
- 提出首個受控的成本感知比較（controlled, cost-aware comparison），系統性對比 LLM 與嵌入模型（embedding model）在 37 項任務上的品質、成本與吞吐量（throughput）。
- 發現 LLM 與嵌入模型在總體（aggregate）表現上基本持平（parity），但優勢任務不同：LLM 擅長重推理檢索（reasoning-heavy retrieval），嵌入模型擅長分類（classification）。
- 量化「嵌入器兩難（Embedder's Dilemma）」：LLM 成本可比同品質嵌入模型高達 1,431 倍，開源 LLM 在相同 GPU 上處理標記（token）的速度慢 2.5 至 736 倍。
- 揭示推理標記（reasoning token）佔 LLM 推理成本（inference cost）的 28%–81%，並透過消融研究（ablation）顯示降低推理預算（reasoning budget）通常可維持甚至提升檢索品質。
- 基於成本效益帕雷托前沿（cost–performance Pareto frontier）提出實務分工（division of labour）建議：嵌入模型負責相似度（similarity）、分類與聚類（clustering），LLM 保留給重推理檢索。

### 適合對象
本論文適合從事資訊檢索（information retrieval）、語意搜尋（semantic search）、推薦系統與大型語言模型（LLM）應用的研究人員與工程師，特別是正在評估是否以 LLM 取代現有文字嵌入流程（text-embedding pipeline）、需要同時考量品質、推理成本（inference cost）與部署成本（deployment cost）的 MLOps 與 AI 基礎建設決策者。

## 深度分析

#### 方法論解析

本文的核心方法論在於建立一個「受控的成本感知比較（controlled, cost-aware comparison）」框架，將生成式大型語言模型（Large Language Model, LLM）與傳統文字嵌入模型（text embedding model）放在同一個評估基礎（evaluation basis）上進行對照。為此，作者提出了 **MTEB(LLM)**，這是首個橫跨分類（classification）、語意文字相似度（Semantic Textual Similarity, STS）、聚類（clustering）、成對分類（pair classification）與檢索（retrieval）五大 MTEB 任務類別、同時記錄品質與成本的基準測試（benchmark）。

**1. 模型選擇與對照設計**

研究評估了十個前沿 LLM，涵蓋六個模型家族（model family），包括：
- 閉源 API 模型：Gemini 3.1 Pro、Gemini 3 Flash、Gemini 3.1 Flash-Lite；
- 開源權重（open-weight）模型：DeepSeek-R1、DeepSeek-V4-Flash、Qwen3.6-27B、Qwen3.6-35B-A3B、GLM-4.7、Kimi-K2.6、MiniMax-M2.7。

這些模型橫跨密集（dense）與混合專家（Mixture-of-Experts, MoE）架構、推理（reasoning）與指令（instruct）變體，以及不同的能力與價格區間。與此同時，研究納入 26 個文字嵌入模型，參數量（parameters）從 118M 到 14B，包含 multilingual-E5、Qwen3-Embedding、NV-Embed、SFR-2、Gemini Embedding 等主流家族。

關鍵在於，LLM 並未經過任務特定訓練（task-specific training），而是透過提示（prompting）直接輸出文字；相對地，嵌入模型則透過專門的對比式訓練（contrastive training）、困難負樣本採礦（hard-negative mining）與多階段蒸餾（multi-stage distillation）來取得向量表示。這樣的對照能夠回答一個實務問題：「是否應該用 LLM 取代現有的文字嵌入流程（text-embedding pipeline）？」

**2. MTEB(LLM) 基準建構**

MTEB(LLM) 是從大規模文字嵌入基準（Massive Text Embedding Benchmark, MTEB）中抽取的固定子集（fixed subset），共 37 個任務。作者強調，MTEB(LLM) 分數僅用於在該基準內比較模型，與 MTEB 排行榜分數（leaderboard scores）使用完整測試集（full test sets）的評估基礎不同。所有模型都在完全相同的子集上評分，確保公平性。

**3. 成本與吞吐量核算**

本文的方法論創新在於將「品質」與「成本」同時納入評估：
- 對於 LLM，透過 API token 追蹤（API token tracking）精確計算輸入與輸出 token 數量，並按實際價格換算為美元；
- 對於嵌入模型，則在相同 GPU 上進行 GPU 吞吐量基準測試（GPU throughput benchmarking），測量每秒處理 token 數。

這使得作者能夠繪製跨越兩種典範（paradigms）的成本效益帕雷托前沿（cost–performance Pareto frontier），並量化「達到相同品質所需的代價」。

**4. 推理標記（reasoning tokens）消融實驗**

針對支援擴展推理的 LLM，作者進行了推理預算（reasoning budgets）的消融研究（ablation），探討降低 reasoning tokens 是否會損害檢索品質。結果顯示，對大多數模型而言，較低的推理預算不僅能降低成本，甚至能保留或提升檢索表現。

---

#### 實驗數據解讀

**1. 總體表現：兩種典範幾乎持平**

在 MTEB(LLM) 的 37 個任務上，最佳 LLM（Gemini 3.1 Pro，77.6 分）與最佳嵌入模型（77.2 分）僅相差 0.4 分，落在統計雜訊（statistical noise）範圍內。這意味著，就總體（aggregate）品質而言，未經專門嵌入訓練的生成式 LLM 已經能夠匹敵專門化的嵌入模型。

**2. 任務特化的優勢分佈**

然而，這種持平並非均勻分佈，而是具有明顯的任務特異性（task-specific）：
- **檢索（retrieval）**：LLM 在需要跨文件推理（cross-document reasoning）的重推理檢索（reasoning-heavy retrieval）上領先。這與 BRIGHT 等基準的發現一致：當查詢與文件之間需要複雜推理才能建立關聯時，獨立編碼查詢與文件的雙編碼器（bi-encoder）架構會遇到瓶頸。
- **分類（classification）**：嵌入模型領先約 5.6 分。這類任務通常只需要幾何相似度（geometric similarity）或標記參考匹配（labelled-reference matching），專門訓練的嵌入模型能更有效率地處理。
- **聚類（clustering）、STS、成對分類（pair classification）**：兩種典範統計上持平。

這支持了作者提出的「分工（division of labour）」結論：嵌入模型仍是相似度（similarity）、分類與聚類的預設（default）選擇；LLM 則應保留給推理密集的檢索場景。

**3. 成本差距：三個數量級**

實驗數據中最震撼的發現是成本不對稱：
- Gemini 3.1 Pro 完成一次基準測試回合（benchmark pass）需花費約 154 美元；
- 品質相近的嵌入模型僅需約 0.11 美元；
- 成本差距高達 **1,431 倍**。

即使考慮不同硬體與部署情境，這種差距依然顯著。對於需要大規模部署的應用而言，這是一個決定性的實務因素。

**4. 吞吐量差距：同 GPU 上慢 2.5 至 736 倍**

在相同的 H100 GPU 上，開源 LLM 的處理速度比嵌入模型慢 **2.5 到 736 倍**。這反映了自迴歸生成（autoregressive generation）與單一編碼器前向傳播（single encoder pass）之間的架構差異。對於高吞吐量（throughput）需求的服務，這是一個嚴重的部署障礙。

**5. 推理標記稅（thinking-token tax）**

Reasoning tokens 佔 LLM 推理成本（inference cost）的 **28% 至 81%**。作者將此稱為「推理標記稅（thinking-token tax）」。消融實驗顯示，降低 reasoning budgets 對大多數模型的檢索品質沒有負面影響，甚至有時能提升表現。這暗示許多 LLM 可能存在「過度思考（overthinking）」現象，即產生過多不必要的推理痕跡（verbose reasoning traces）。

**6. 帕雷托前沿（Pareto frontier）**

在成本–品質權衡圖上，帕雷托前沿主要由領先的嵌入模型與單一 LLM——Gemini 3.1 Pro——組成。這表示：
- 若追求極致成本效益，嵌入模型是最佳選擇；
- 若願意支付三個數量級的代價以換取 0.4 分的總體提升與檢索上的推理優勢，則可選擇 Gemini 3.1 Pro。

#### 與現有研究的比較

**1. 延續 MTEB 生態系**

本文是 MTEB 評估框架的重要延伸。MTEB（Muennighoff et al., 2023）標準化了文字嵌入模型的跨任務評估，後續發展出 MMTEB（多語言）、MIEB（圖像）、MAEB（音訊）、MVEB（影片）等模態擴展。本文首次將 LLM 與嵌入模型放在同一個 MTEB 任務分類下進行系統性比較，並引入成本維度，填補了既有 leaderboard 僅關注品質的缺口。

**2. 與 Green AI 及成本意識研究的呼應**

Schwartz et al.（2020）提出的 Green AI 強調應同時考慮準確度與計算/環境成本；Gonzalez（2026）發現微調後的 BERT 規模編碼器在文字分類上能以低 1–2 個數量級的成本匹敵 GPT-4o。本文將這條研究線擴展到更廣泛的嵌入任務，並提供精確的美元成本與吞吐量數據。

**3. 與 BRIGHT、BEIR 及 RAG 研究的關聯**

BRIGHT（Su et al., 2024）顯示，在重推理檢索上，LLM 增強的檢索能比頂尖嵌入模型提升多達 12.2 個 nDCG@10 點數。本文的發現與之一致：LLM 在需要跨文件推理時具有結構性優勢。相對地，BEIR 與 Dense Retrieval（Karpukhin et al., 2020）則確立了雙編碼器在標準零樣本檢索上的強勁表現。

本文也直接評估了 RAG 中的重排序（reranking）階段，將第一階段檢索器與交叉編碼器（cross-encoder）及 LLM 列表式重排序器（listwise reranker）結合。這補充了 Sun et al.（2023a）與 Lu et al.（2025）的研究，後者發現直接輸出重排序通常優於鏈式思考重排序（CoT reranking）。

**4. 與過度思考（overthinking）文獻的連結**

Sui et al.（2025）與 Snel et al.（2024）探討了自適應測試時計算（adaptive test-time compute）與過度推理的問題。本文的消融實驗提供了具體證據：降低 reasoning budgets 對檢索品質影響有限，支持未來發展動態推理預算控制。

**5. 本文的侷限**

儘管實驗設計嚴謹，仍有若干限制：
- **語言範圍**：MTEB(LLM) 主要基於 MTEB 的英文子集，未涵蓋多語言場景；未來可參照 MMTEB 擴展。
- **成本波動**：API 價格與 GPU 租賃成本會隨時間變動，本文的美元數字僅反映實驗當下的定價。
- **提示工程敏感性**：LLM 的表現可能受提示設計影響，本文雖採用固定策略，但不同提示可能改變絕對分數。
- **未涵蓋所有前沿模型**：雖已納入十個 LLM，但諸如 GPT-5、Claude Opus 4.6 等最新閉源模型未全部納入。
- **推理預算消融僅針對檢索**：對於分類、STS 等任務，降低 reasoning budgets 的影響尚待進一步研究。

#### 可重現性評估

**1. 開源釋出**

作者明確表示程式碼（code）、資料集（datasets）與結果（results）已公開於 GitHub 倉庫 `embeddings-benchmark/embedders-dilemma`，這大幅提升了研究的可重現性（reproducibility）。

**2. 資料集與評估基礎**

MTEB(LLM) 的固定子集已發布在 Hugging Face 上，命名為 `mteb/llm-eval-*`。由於所有模型都在完全相同的子集上評分，其他研究者可以直接使用這些資料集複製實驗，並與本文結果進行公平比較。

**3. 成本核算方法透明**

- 對於 API 模型，作者透過 API token tracking 記錄每個任務的輸入與輸出 token 數，並按當時價格換算；
- 對於開源模型，則在相同 GPU 上進行吞吐量測量，並據此推估成本。

這種雙軌成本核算方式雖然無法完全消除價格波動的影響，但提供了可重複的計算基礎。

**4. 模型權重可取得性**

- 嵌入模型大多為開源，可從 Hugging Face 下載；
- 開源 LLM 透過 OpenRouter 提供服務，部分模型權重也可直接取得；
- 閉源 Gemini 系列則需透過 Google API 存取，重現時需考慮 API 可用性與定價變化。

**5. 潛在重現挑戰**

- **隨機性與 API 行為**：LLM 的輸出可能因溫度（temperature）、採樣策略與 API 版本而異；
- **硬體差異**：GPU 吞吐量數據高度依賴特定硬體與軟體棧，不同環境可能得到不同絕對數字；
- **成本變動**：API 定價調整會影響成本倍數的精確重現，但相對趨勢應仍穩定。

整體而言，本文在可重現性方面表現良好，尤其在資料集釋出與方法透明化上做出了典範級的貢獻。

#### 未來研究方向

**1. 多語言與多模態擴展**

將 MTEB(LLM) 擴展到多語言（參照 MMTEB）與其他模態（圖像、音訊、影片），檢視 LLM 與專門嵌入模型在跨語言、跨模態場景下的成本效益權衡。

**2. 動態與自適應推理預算**

本文發現降低 reasoning budgets 通常不損害檢索品質。未來可發展自適應測試時計算（adaptive test-time compute）機制，根據查詢難度動態調整推理深度，以最小化成本同時維持品質。

**3. 混合流程（hybrid pipeline）的最佳化**

作者已提出「混合流程」概念，但未深入探討其最佳設計。未來研究可針對不同應用場景，系統性比較：
- 嵌入模型第一階段檢索 + LLM 重排序（reranking）；
- 基於查詢難度選擇使用 LLM 或嵌入模型；
- 多階段級聯（cascading）策略的成本效益分析。

**4. 將 LLM 推理能力蒸餾到嵌入模型**

既然 LLM 在重推理檢索上表現較佳，可研究如何透過知識蒸餾（knowledge distillation）將 LLM 的跨文件推理能力轉移到更小、更快速的嵌入模型中，從而降低部署成本。

**5. 真實世界 RAG 系統評估**

MTEB(LLM) 是標準化基準，但未涵蓋真實 RAG 系統中的延遲（latency）、快取、索引更新、使用者互動等動態因素。未來可在生產環境中評估這些發現的適用性。

**6. 環境成本與能源效率**

除了美元成本，未來可進一步量化碳排放與能源消耗，延續 Green AI 的精神，為永續 AI 部署提供依據。

**7. 長文件與複雜結構化檢索**

本文的檢索任務主要來自 MTEB。未來可針對長文件、表格、程式碼、法律文件等需要更複雜推理的檢索場景，進一步區分 LLM 與嵌入模型的適用邊界。

**8. 提示設計與微調 LLM 的比較**

本文的 LLM 未經任務特定訓練。未來可比較「提示工程」、「少量樣本學習（few-shot learning）」與「輕量微調（lightweight fine-tuning）」對成本效益的影響，探索 LLM 在嵌入任務上的最佳使用方式。

## 論文問答

**Q1【背景與動機】：什麼是「嵌入器兩難」（Embedder’s Dilemma），為什麼它在當前 NLP 部署中很重要？**
A：嵌入器兩難指的是大型語言模型如今在整體表現上已能與最佳文字嵌入模型持平，但卻伴隨高得多的推理成本與低得多的吞吐量。具體而言，最佳 LLM Gemini 3.1 Pro 與最佳嵌入模型的總體分數僅差 0.4 分，卻可能貴上 1,431 倍，且在相同 GPU 上處理標記的速度慢上數個數量級。這讓工程團隊面臨抉擇：要選擇便宜高效的專用嵌入流程，還是為了少數重推理檢索任務的優勢而付出高昂代價。

**Q2【背景與動機】：現有的 MTEB 排行榜為什麼無法直接回答「是否該用 LLM 取代嵌入流程」這個問題？**
A：傳統 MTEB 排行榜主要針對輸出向量的嵌入模型設計，並使用完整測試集與不同的評估基礎，而 LLM 是以生成文字的方式回答任務，兩者在評估方式上並不一致。此外，既有排行榜通常只關注品質分數，鮮少同時納入精確的成本核算與吞吐量測量，因此無法呈現部署時的真實取捨。本文因此提出 MTEB(LLM)，讓兩種典範在完全相同的固定子集上評分，並同步記錄每個模型的花費與速度。

**Q3【背景與動機】：為什麼「成本感知」的評估在這項研究中不可或缺？**
A：隨著 frontier LLM 的能力提升，僅比較準確度會讓人忽略其背後龐大的推理開銷與延遲，而這些正是實際產品部署的關鍵限制。研究發現，達到與嵌入模型相近品質的 LLM，其單次基準測試回合可高達 154 美元，而可比較的嵌入模型僅約 0.11 美元，差距超過三個數量級。將成本與品質並列，才能畫出帕雷托前沿，幫助研究者與工程師判斷哪些模型真正位於效率與效能的最佳平衡點。

**Q4【方法與創新】：MTEB(LLM) 的核心設計是什麼，如何確保 LLM 與嵌入模型之間的公平比較？**
A：MTEB(LLM) 是從大規模文字嵌入基準 MTEB 中抽取的 37 項任務固定子集，涵蓋分類、語意文字相似度、聚類、成對分類與檢索五大類別。它要求 LLM 與嵌入模型都在完全相同的資料子集上進行評分，並透過 MTEB 框架實作，使兩種典範的評估基礎一致。這種設計避免了傳統排行榜因使用完整測試集或不同評估協定而產生的偏差，讓品質比較具有直接可比性。

**Q5【方法與創新】：本研究在方法論上的主要創新是什麼？**
A：本研究首次在涵蓋所有五類 MTEB 任務的基準上，同時對 LLM 與嵌入模型進行精確的成本核算與吞吐量測量，並繪製跨越兩種典範的成本效益帕雷托前沿。對於 API 模型，作者追蹤實際 token 使用量與計價；對於開源模型，則在相同 GPU 上進行吞吐量基準測試。這種「品質—成本—速度」三位一體的評估方式，補足了過去只聚焦準確度的研究缺口。

**Q6【方法與創新】：為什麼要同時納入十個來自六個家族的 LLM，以及 26 個參數量從 1.18 億到 140 億的嵌入模型？**
A：納入多個模型家族與架構（包括 dense 與 MoE、推理型與指令型、封閉 API 與開源權重）可以區分普遍趨勢與特定廠商或模型的效應，避免結論過度推論。嵌入模型涵蓋廣泛的參數規模，則能展示專用對比式訓練與蒸餾技術如何在較小模型上達到高品質。這樣的多樣性讓帕雷托前沿更具代表性，也能清楚比較不同部署情境下的成本與效能。

**Q7【實驗與結果】：實驗的主要結果在總體表現與任務別表現上有何差異？**
A：總體而言，兩種典範幾乎打成平手：最佳 LLM Gemini 3.1 Pro 得分 77.6，最佳嵌入模型 77.2，差距僅 0.4 分，落在統計雜訊範圍內。然而任務別的優勢明顯不同：LLM 在需要跨文件推理的重推理檢索上領先，嵌入模型在分類任務上表現較佳，而在聚類、語意文字相似度與成對分類上兩者則無顯著差異。這說明 LLM 的優勢並非全面，而是集中在需要複雜推理的檢索情境。

**Q8【實驗與結果】：成本效益帕雷托前沿顯示了什麼？成本差距的具體規模有多大？**
A：帕雷托前沿主要由頂尖嵌入模型與單一 LLM Gemini 3.1 Pro 組成，顯示大多數 LLM 並未同時達到最佳品質與最低成本。最具體的差距是 Gemini 3.1 Pro 單次完整基準測試回合花費約 154 美元，而品質相近的嵌入模型僅約 0.11 美元，相差高達 1,431 倍。即使在開源模型於相同 GPU 上運行的情境，LLM 的吞吐量仍比嵌入模型慢 2.5 到 736 倍，顯示成本與速度劣勢是結構性的。

**Q9【實驗與結果】：關於推理預算（reasoning budgets）的消融實驗揭示了什麼？**
A：研究發現 reasoning tokens 佔了 LLM 推理成本的 28% 到 81%，作者將此稱為「推理標記稅」（thinking-token tax）。然而降低推理預算後，大多數模型在檢索任務上的品質並未下降，甚至有所提升，顯示過度推理在文件排序等任務上可能是浪費。這項發現對產品部署很重要：透過限制 reasoning budget，可以在保留檢索優勢的同時顯著壓低成本與延遲。

**Q10【應用與影響】：根據研究結果，實務上應如何分工使用嵌入模型與 LLM？**
A：作者建議將嵌入模型作為相似度、分類與聚類任務的預設選擇，因為這些任務幾何相似度或標記參考匹配就足夠，且嵌入模型成本低廉、吞吐量高。LLM 則應保留給需要跨文件推理的重推理檢索，例如 BRIGHT 類型的複雜查詢。採用混合流程可以在第一階段使用嵌入模型快速召回，再由 LLM 進行重排序，兼顧品質提升與成本控制。

**Q11【應用與影響】：產品團隊在決定是否以 LLM 取代嵌入檢索流程時，應考量哪些因素？**
A：團隊應先評估任務是否真正需要跨文件推理：若只是關鍵字或語意相似召回，嵌入模型在成本與速度上遠勝 LLM。其次要估算實際流量規模下的 token 花費與延遲，因為研究顯示 LLM 成本可達嵌入模型的數千倍，吞吐量則慢數百倍。最後可考慮混合架構，用嵌入模型做初篩，再以 LLM 重排少量候選，這樣能在重推理檢索上獲得增益，同時避免全量 LLM 推理的開銷。

**Q12【應用與影響】：這項研究對文字嵌入領域與未來基準設計可能帶來什麼影響？**
A：本研究強調未來的模型評比不應只看準確度，而必須同時納入成本與吞吐量，才能反映真實部署情境。MTEB(LLM) 的釋出也為社群提供了一個統一框架，可比較生成式 LLM 與向量嵌入模型在相同任務上的表現。這可能促使更多研究探索如何在保持嵌入模型效率的同時注入推理能力，或開發能自適應調整推理預算的新型檢索系統。

**Q13【限制與未來】：這項研究有哪些主要限制？**
A：首先，MTEB(LLM) 是從完整 MTEB 中抽取的固定子集，其分數與官方排行榜使用完整測試集的分數屬於不同評估基礎，不能直接混用。其次，API 價格與開源模型的服務配置會隨時間變動，成本與吞吐量數字可能因廠商定價調整或硬體差異而改變。此外，研究主要聚焦英文文字任務，對於多語言、多模態或更長上下文情境的結論仍需進一步驗證。

**Q14【限制與未來】：在哪些任務或情境下，LLM 可能仍然不如嵌入模型？**
A：在分類任務中，嵌入模型透過專門的對比式訓練與標記參考匹配，表現優於零樣本 LLM，這與過去文獻中編碼器顯著領先的發現一致。對於只需要幾何相似度或大量高吞吐量比對的相似度、聚類與成對分類任務，嵌入模型的單一編碼器前向傳遞也遠比自迴歸生成高效。因此，若任務不需要複雜跨文件推理，強行使用 LLM 只會帶來不必要的成本與延遲。

**Q15【限制與未來】：未來研究可以朝哪些方向延伸？**
A：未來可以探索自適應推理預算機制，讓模型根據查詢難度動態決定 reasoning tokens 的用量，以進一步壓低成本。另一個方向是開發結合嵌入模型效率與 LLM 推理能力的新型架構，例如輕量重排序器或具推理意識的嵌入訓練。此外，將成本感知評估擴展到多語言、多模態與更長文件的情境，也有助於建立更全面的部署導向基準。

## 實務應用指南

### 適用場景

1. **企業知識庫的混合檢索（Hybrid RAG）**  
   當使用者問題需要跨文件推理（例如比較多份合約條款、技術文件與故障紀錄）時，先用嵌入模型做第一階段召回，再用 Gemini 3.1 Pro 等 LLM 做重排序（reranking）或列表式排序，可在控制成本的前提下提升重推理檢索品質。

2. **大量文件分類與標籤推薦**  
   新聞分類、客服工單分派、產品評論情緒標記等任務，幾何相似度或標記參考匹配即可勝任，應優先使用 E5、NV-Embed、SFR-2 等領先嵌入模型，以獲得接近 LLM 的準確度並降低 2–3 個數量級的成本。

3. **語意搜尋與重複偵測（STS / 聚類）**  
   內部文件搜尋、FAQ 去重、社群貼文聚類等場景，LLM 與嵌入模型在統計上不相上下，但嵌入模型吞吐量高出數十倍至數百倍，應作為預設方案。

4. **法規 / 醫療 / 學術文獻的精準檢索**  
   查詢需要理解隱含條件、時間範圍或專業術語間的邏輯關係時，LLM 的跨文件推理優勢明顯，可部署為「高價值查詢」專用路徑，而非所有查詢都走 LLM。

5. **成本敏感的多語言內容平台**  
   若服務涵蓋多語種分類與相似度任務，可選用 multilingual-E5 或 Qwen3-Embedding 等多語言嵌入模型家族，避免為每種語言都呼叫高單價 LLM API。

---

### 實作前置條件

- **資料準備**  
  需具備與任務對應的查詢–文件對、標籤或相似度標註。若要走 LLM 重排序路徑，建議先準備 50–200 筆高難度案例作為內部驗證集，用於比較嵌入模型 k-NN 與 LLM 排序的差異。

- **運算資源**  
  嵌入模型可在單張 H100 / A100 上以高吞吐量服務；開源 LLM 在相同 GPU 上吞吐量可能低 2.5–736 倍，需預留足夠推論實例或評估是否使用 API。若採用 Gemini 3.1 Pro 等閉源 API，需準備按 token 計價的預算與額度監控。

- **技能需求**  
  團隊需熟悉 MTEB 評估框架、向量資料庫（如 FAISS、Milvus、Weaviate）、API token 追蹤與成本核算，並具備提示工程能力以設計 LLM 重排序提示與推理預算控制。

- **評估基線**  
  在導入前應先於 MTEB(LLM) 對應子集或自製驗證集上建立分數與延遲基線，避免直接用完整 MTEB 排行榜分數推估自身任務表現。

---

### 實作步驟建議

1. **任務分類與路徑選擇**  
   依任務類型決定主路徑：分類、STS、聚類走嵌入模型；需要跨文件推理的檢索走 LLM 重排序或混合流程。

2. **建立嵌入模型基線**  
   選 2–3 個不同參數量級的嵌入模型（如 118M–1B 輕量版與 7B–14B 高精度版），在 MTEB(LLM) 對應子集或內部資料上評分，同時測量 GPU 吞吐量與每千次查詢成本。

3. **設計 LLM 重排序實驗**  
   對檢索任務，先用嵌入模型召回 top-k 候選文件，再用 Gemini 3.1 Pro / Qwen3 / DeepSeek-R1 等進行列表式重排序。記錄輸入 token、輸出 token 與 reasoning tokens 佔比。

4. **進行推理預算消融**  
   對每個 LLM 測試不同 reasoning budget（例如 0%、50%、100% 預設思考長度），觀察 nDCG@10 等檢索指標變化。根據本文結果，多數模型在較低預算下即可保留甚至提升檢索品質。

5. **繪製成本效益帕雷托前沿**  
   將品質分數（縱軸）對每基準測試回合成本或每千次查詢延遲（橫軸）作圖，標出領先嵌入模型與 Gemini 3.1 Pro 的位置，選擇落在帕雷托前沿上的方案。

6. **上線與持續監控**  
   部署後追蹤實際 token 消耗、推理標記佔比、延遲分佈與業務指標，並設定成本告警。對高價值查詢啟用 LLM 路徑，一般查詢維持嵌入模型路徑。

---

### 潛在風險與注意事項

- **成本失控**  
  Gemini 3.1 Pro 單次完整基準測試可達 154 美元，而同等品質嵌入模型僅約 0.11 美元。若未對 LLM 路徑做流量分級或快取，API 帳單可能迅速膨脹。建議設定每日 token 上限與異常消耗告警。

- **吞吐量瓶頸**  
  開源 LLM 在相同 GPU 上可能比嵌入模型慢數百倍，直接替換所有嵌入流程會導致服務延遲飆升。應將 LLM 限制在少數高難度查詢，並使用非同步佇列或專用推論叢集。

- **過度推理（Overthinking）**  
  Reasoning tokens 佔 LLM 推理成本的 28–81%，但過長思考鏈不一定提升檢索品質。實務上應透過消融實驗找出各模型的最小有效推理預算。

- **評估基礎不一致**  
  MTEB(LLM) 使用固定子集，分數與完整 MTEB 排行榜不同，不可直接比較。產品決策應以相同子集或自製驗證集為準。

- **提示脆弱性**  
  LLM 重排序對提示格式、文件排序與長度敏感，需進行 A/B 測試並監控輸出品質，避免因提示設計不良而抵消模型優勢。

---

### 與其他技術的整合建議

- **向量資料庫與快取層**  
  嵌入模型產生的向量可預先寫入向量資料庫並建立快取；對重複查詢直接返回快取結果，減少 LLM 呼叫次數。

- **查詢路由（Query Router）**  
  使用輕量分類器或規則引擎判斷查詢是否需要跨文件推理，自動分流至嵌入模型路徑或 LLM 重排序路徑，兼顧成本與品質。

- **RAG 管線**  
  在標準 RAG 架構中，將 LLM 作為第二階段重排序器而非取代第一階段嵌入檢索，可保留高吞吐量並利用 LLM 的推理優勢。

- **監控與可觀測性工具**  
  整合 token 追蹤、推理標記佔比分析與延遲分佈監控，持續驗證實際成本是否接近紙本估算，並及時調整 reasoning budget。

- **模型蒸餾與微調**  
  若特定任務需要 LLM 等級品質但無法承受其成本，可考慮用 LLM 產生訓練信號，透過對比式訓練或蒸餾強化專用嵌入模型。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先理解「嵌入器兩難」的核心結論：LLM 雖然在總體分數上與嵌入模型打平，但貴很多、慢很多。重點閱讀摘要、第 1 節與「適用場景」相關段落，掌握「分類 / 相似度 / 聚類用嵌入模型，重推理檢索才考慮 LLM」這條實務原則即可。

- **AI 工程師**  
  請聚焦第 3 節實驗設定、第 4.4–4.6 節成本與推理預算分析，以及圖 1 與圖 7 的帕雷托前沿與吞吐量比較。這些內容直接影響模型選型、API 計價估算與混合管線設計。

- **研究人員**  
  建議深入閱讀 MTEB(LLM) 的建構方式、統計顯著性分析（第 4.2 節）以及 reasoning tokens 的消融實驗。可進一步探討為何 LLM 在跨文件推理檢索佔優，以及能否透過更短的推理鏈達到相同效果。

- **產品經理**  
  重點看摘要的成本數字、第 4.2 節的任務優劣勢對照，以及「分工」結論。用這些數據與工程師討論成本上限、延遲容忍度與高價值查詢定義，避免為了 0.4 分的總體差距付出三個數量級的成本。
