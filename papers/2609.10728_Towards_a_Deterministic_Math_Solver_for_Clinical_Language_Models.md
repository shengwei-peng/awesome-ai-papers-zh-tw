## 摘要翻譯

大型語言模型（Large Language Model, LLM）在算術方面不可靠，這對臨床計算器（clinical calculator）而言是個問題，因為單一數值錯誤就會改變建議。標準做法是將每個計算器逐一硬編碼為經驗證函式（validated function）。我們測試一種替代方案：模型不進行計算，而是撰寫針對個案的 Python 程式碼，由受限的本機執行器（restricted local executor）作為確定性求解器（deterministic solver）執行，而模型的任務簡化為決定如何使用它。我們在 MedCalc-Bench Verified（1,100 個案例、55 個計算器）上評估此 Program-Solve 介面，對照模型直接算術與手寫的 22 個計算器函式庫，使用 Qwen2.5-7B 與 Qwen2.5-32B-AWQ，並先將基準測試的公式對照現行臨床指引（clinical guideline）進行稽核，標記出 55 個中有 16 個在版本、使用或係數方面存在疑慮。在提供公式與標準答案變數、且兩種方式皆讀取完整病歷的情況下，在 7B 模型上，將計算委由求解器執行並未帶來可靠的優勢（75.31% 對 72.02%，配對差異 +3.29 個百分點，95% 計算器叢集區間為 [-3.49, 10.38]），但在 32B 模型上則帶來可靠的優勢（90.53% 對 83.47%，+7.05 [0.47, 14.60]，明確排除零）。手寫函式庫在其支援的 440 個案例上完全正確，但在其他案例上棄答（abstention）（整體 40.0%）。因此，加入執行器對某些開放權重模型（open-weight model）的幫助大於其他模型，即使在公式、變數與病歷存取皆一致的情況下也是如此，且無論如何都不能取代經驗證公式或可靠的變數擷取（variable extraction）。

### 核心貢獻（3～5點）
- 提出 Program-Solve 介面設計：將大型語言模型的角色從「計算者」轉變為「決策者」，由模型撰寫個案特定的 Python 程式碼，交由受限的本機執行器以確定性方式執行，從而將算術錯誤風險從模型端轉移至執行環境端。
- 在 MedCalc-Bench Verified 上進行系統性實證：涵蓋 1,100 個案例與 55 個計算器，並先對基準測試公式進行臨床指引稽核，標記出 16 個存在版本、使用或係數疑慮的計算器，凸顯「經驗證公式」本身的重要性。
- 揭示模型規模對執行器效益的調節作用：7B 模型下 Program-Solve 相較直接算術僅有 +3.29 百分點的非顯著提升（95% 信賴區間包含零），但 32B 模型則達到 +7.05 百分點的顯著優勢（區間明確排除零），說明執行器並非對所有模型皆為可靠增益。
- 與手寫函式庫進行基準對比：手寫 22 個計算器函式庫在其支援範圍內完全精確，但因覆蓋率限制而整體僅達 40.0%，證實 Program-Solve 在覆蓋面與精確度之間提供了不同的取捨點。
- 提出雙重底線結論：無論是否採用執行器，經驗證公式與可靠的變數擷取始終是不可或缺的基礎，執行器僅是輔助而非替代。

### 適合對象
- 從事醫療人工智慧（Medical AI）研究、關注大型語言模型臨床應用可靠性與安全性的研究人員。
- 開發臨床決策支援系統（Clinical Decision Support System）或電子病歷整合工具的工程師與架構師。
- 對程式輔助推理（program-aided reasoning）、工具呼叫（tool calling）與確定性計算在 LLM 中應用感興趣的自然語言處理（NLP）研究者。
- 臨床資訊學（Clinical Informatics）專家與醫師，特別關注臨床計算器版本管理、公式稽核與風險控管者。
- 評估開放權重模型（open-weight model）於高風險領域部署可行性的政策制定者與醫療機構資訊主管。

## 深度分析

#### 方法論解析

本文提出 Program-Solve 介面作為臨床計算器自動化的一種替代方案，其核心設計理念是將大型語言模型（Large Language Model, LLM）從「執行算術」的角色中解放出來，使其轉變為「決定如何使用求解器」的角色。這是一種典型的程式輔助推理（Program-aided reasoning）架構，但本文的特殊貢獻在於對其進行了嚴格的控制變項比較。

**介面架構設計**

Program-Solve 介面的運作流程如下：模型接收病歷筆記（note）、公式（formula）與變數（variables）三項輸入後，生成一段 Python 程式碼，該程式碼被送入一個受限的本機執行器（restricted local executor）執行，最終回傳數值、日期或妊娠週數元組（gestational-age tuple）。關鍵設計細節包括：

1. **執行器的隔離機制**：每個程式在獨立的子行程（subprocess）中執行，內建函數（builtins）採用白名單機制，禁止檔案存取、`eval`、`exec` 等危險原語；匯入限制僅限於標準函式庫中的 `math`、`date`、`time`、`calendar` 模組；靜態拒絕非同步（async）與生成器（generator）結構；並設有 256 MB 記憶體上限、CPU 限制、5 秒牆鐘時間（wall clock）以及執行行數上限。

2. **無計算器專屬程式碼**：執行器內不含任何計算器專屬的函式或常數，這與傳統手寫函式庫（hand-written function library）形成對比。模型必須自行將臨床公式翻譯為程式碼，這使得介面具備通用性，可處理所有 55 個計算器，而手寫函式庫僅實作了 22 個。

3. **安全性權衡**：作者明確指出執行器「受限但非沙箱化（no sandbox）」——沒有容器或系統呼叫過濾器。這是一個重要的安全警示，意味著在實際臨床部署中需要更嚴格的隔離措施。

**實驗臂（Arms）的設計邏輯**

本文採用了精心設計的多臂比較架構，以分離不同變數的影響：

| 實驗臂 | 公式存取 | 變數存取 | 執行方式 |
|--------|----------|----------|----------|
| Note only | 無 | 無 | 模型算術 |
| Page without formula | 隱藏公式 | 無 | 模型算術 |
| Open-book arithmetic | 有 | 黃金變數 | 模型算術 |
| Extract-Solve library | 函式庫內建 | 模型擷取 | 手寫函式 |
| Gold-Solve library | 函式庫內建 | 黃金變數 | 手寫函式 |
| Program-Solve | 有 | 黃金變數 | 模型寫程式＋執行器 |
| Blind Program-Solve | 無 | 模型擷取 | 模型寫程式＋執行器 |

這種設計的核心價值在於「配對比較（matched comparison）」：Program-Solve 與 Open-book arithmetic 在公式、變數、筆記長度三方面完全匹配，因此兩者的差異可純粹歸因於「執行方式」（模型算術 vs. 程式碼執行）。同樣地，Blind Program-Solve 與 Extract-Solve library 的配對則隔離了「變數擷取」這個因素。

**統計方法的嚴謹性**

本文的統計推論設計值得特別注意。由於 1,100 個案例巢套於 55 個計算器中，且每個案例在 5 個隨機種子（seed）下重複評估，主要的不確定性來源採用了計算器叢集自助法（calculator-cluster bootstrap，10,000 次抽樣，百分位數 95% 區間，種子保持在一起）。輔助方法包括案例自助法、精確 McNemar 檢定以及符號翻轉排列檢定（sign-flip permutation p），並在家族內進行 Holm 校正。計算器叢集內相關係數（ICC）達 0.68 至 0.81，意味著函式庫比較的有效樣本量僅 67 至 79 個案例，這對統計檢定力的影響在解讀結果時至關重要。

#### 實驗數據解讀

**主要結果的精細解讀**

在配對條件下（公式、變數、筆記存取完全一致），Program-Solve 相對於 Open-book arithmetic 的表現呈現出明顯的模型規模依賴性：

- **Qwen2.5-7B**：Program-Solve 達到 75.31%，Open-book arithmetic 為 72.02%，配對差異為 +3.29 個百分點，但 95% 計算器叢集區間為 [-3.49, 10.38]，跨越零值。這意味著在 7B 模型規模下，將算術交給執行器並未帶來可靠的優勢。

- **Qwen2.5-32B-AWQ**：Program-Solve 達到 90.53%，Open-book arithmetic 為 83.47%，配對差異為 +7.05 個百分點，95% 區間為 [0.47, 14.60]，完全位於零值之上。這表明在 32B 模型規模下，程式碼執行介面具備統計上可靠的優勢。

**錯誤模式的分析**

從 Table 14 的數據可以深入理解兩種方法的失效模式：

- Open-book arithmetic 在 7B 與 32B 下分別有 28.0% 與 16.5% 的錯誤率，且沒有「無效答案」的情況——模型總是會給出一個數值，但可能是錯的。
- Program-Solve 在 7B 與 32B 下分別有 6.7% 與 0.7% 的「無有效答案」率（程式無法執行或產生無效輸出），以及 18.0% 與 8.8% 的錯誤率。

這揭示了一個重要的權衡：程式碼執行介面將「靜默錯誤」轉化為「顯式失敗」，這在臨床應用中具有重要意義——一個明確表示「無法計算」的系統比一個給出錯誤數值的系統更安全。然而，6.7% 的無效答案率在 7B 模型上仍然偏高，限制了其在臨床場景的直接應用。

**函式庫比較的覆蓋率困境**

Gold-Solve library 在其支援的 440 個案例上完全正確（100% 準確率），但在全集 1,100 個案例上僅達到 40.0%——因為對未實作的計算器採取棄答（abstention）策略。這凸顯了手寫函式庫的核心問題：覆蓋率與準確率之間存在根本性的權衡。由於基準測試平衡為每個計算器 20 個案例，函式庫的全集準確率直接受限於其實作的計算器數量。

Program-Solve 相對於 Gold-Solve library 的優勢在 7B 達 +35.31 個百分點，在 32B 達 +50.53 個百分點，但這個差距主要來自覆蓋率而非執行品質——這是一個容易被誤讀的結果。

**基準測試本身的問題**

本文的一個重要但常被忽略的貢獻是對 MedCalc-Bench Verified 中 55 個計算器公式的審計，發現其中 16 個存在版本、使用方式或係數方面的疑慮。具體提及的問題包括：race-free eGFR（不分種族 eGFR）、MELD 3.0、PREVENT、Sampson LDL 方程式等已取代前代的計算器，基準測試可能仍在獎勵過時版本。這意味著即使在基準測試上取得高分，也不必然代表臨床實用性。

**預算與存取的混淆變項**

Table 20 揭示了一個重要的混淆因素：在變數存取固定的情況下，僅僅將筆記預算從 120 字擴展到 250 字就能在每個家族中帶來 4 至 12 個百分點的提升。這意味著先前研究中未控制筆記長度的比較可能將「更多上下文」的效果誤歸於「更好的方法」。

#### 與現有研究的比較

**相對於程式輔助推理的傳統工作**

本文與 Chen 等人 [4, 5] 的程式輔助推理工作有直接的血緣關係，但本文的獨特價值在於「控制變項」的嚴謹性。傳統的程式輔助推理研究通常比較「模型直接推理」與「模型生成程式碼後執行」，但往往未控制公式存取與變數存取的差異。本文透過配對設計，純粹隔離了「執行方式」這一個變數。

**相對於 MedRaC 的比較**

MedRaC [8] 將檢索（retrieval）與 Python 執行配對，並分別評分公式選擇、變數擷取與算術。本文與 MedRaC 的關鍵區別在於：MedRaC 將三個子任務分開評分，而本文則在端到端設定中評估整體準確率。這使得本文更貼近實際臨床部署場景，但代價是難以定位失敗的具體環節。

**相對於 RiskAgent 與 MeNTi 的定位**

RiskAgent [9] 從經驗證的工具中選擇，MeNTi [11] 透過巢狀工具呼叫（nested tool calling）橋接計算器與代理。本文提出的 Program-Solve 介面則採取了一種「中間路線」：既不像手寫函式庫那樣需要逐一實作每個計算器，也不像完全自主代理那樣承擔選擇錯誤工具的風險。然而，這種中間路線的代價是仍需提供公式文字——這在某些場景下可能不可得。

**相對於 Goodell 等人的 ChatGPT 研究**

Goodell 等人 [3] 報告 ChatGPT 在 48 個計算任務中約三分之一的試驗產生錯誤答案，並發現任務專屬的計算器工具比程式碼直譯器更為準確。本文的結果與此一致：手寫函式庫在其支援範圍內完全正確，但覆蓋率有限。本文進一步量化了「程式碼執行介面」相對於「直接算術」的邊際效益，並揭示了這種效益對模型規模的依賴性。

**相對於 AgentMD 的自動化工具策展**

AgentMD [15] 自動化了本文所描述的「工具策展維護負擔」，這指向一個重要的研究方向：未來的系統可能結合自動化的工具發現與程式碼執行介面，以兼顧覆蓋率與執行保證。

**關鍵限制的坦誠承認**

本文最值得讚賞的方面之一是對限制的坦誠承認：

1. **泛化性範圍有限**：結果僅在一個基準測試（MedCalc-Bench Verified）上建立，對未見公式、其他語言或其他設定的泛化性超出本文範圍。

2. **執行器非沙箱化**：安全性保證不足，實際部署需要更嚴格的隔離。

3. **基準測試本身的問題**：16 個計算器的公式存在疑慮，這意味著基準分數不能直接等同於臨床效用。

4. **模型規模依賴性**：效益在 7B 上不可靠，在 32B 上才統計顯著，這限制了小型模型的實用性。

3. **基準測試公式審計的依據**：16 個被標記的計算器的具體疑慮內容與審計依據需要查閱附錄才能完整理解。

4. **預印本狀態**：本文標記為預印本（arXiv:2609.10728v1），尚未經過同行評議，這可能影響結果的最終可靠性。

**與先前研究的可比較性**

由於使用了標準化的基準測試（MedCalc-Bench Verified）與公開模型，結果可直接與其他使用相同基準的研究進行比較。5 個種子的使用提供了對隨機變異的穩健估計，這在先前研究中並不總是標準做法。

#### 未來研究方向

**模型規模與架構的探索**

本文揭示的「7B 不可靠、32B 可靠」的規模依賴性指向幾個重要問題：

1. **臨界規模的確定**：是否存在一個模型規模閾值，使得程式碼執行介面的優勢變得可靠？系統性地評估不同規模（如 7B、13B、32B、70B）的表現將有助於回答此問題。

2. **專門程式碼模型的效益**：針對程式碼生成微調的模型（如 CodeLlama、DeepSeek-Coder）在臨床計算任務上是否比通用對話模型表現更好？這可能降低對模型規模的需求。

3. **推理時計算的影響**：思維鏈（chain-of-thought）推理與程式碼生成的結合是否能進一步提升準確率？這需要控制額外的推理預算。

**公式版本管理的系統化**

本文對基準測試中 16 個計算器的審計凸顯了臨床計算器版本管理的迫切需求：

1. **自動化版本偵測**：能否建立系統自動偵測基準測試或臨床指引中的過時公式？這需要結合臨床指引的結構化表示與語義比對技術。

2. **公式演化的追蹤**：建立計算器公式的版本歷史資料庫，使評估能夠明確區分「公式選擇正確但版本過時」與「公式選擇錯誤」。

3. **臨床指引整合**：將 Program-Solve 介面與結構化的臨床指引資料庫整合，使模型能夠存取最新的公式版本，而非依賴基準測試中可能過時的公式。

**變數擷取的分離改進**

本文的配對設計揭示了變數擷取是獨立於執行品質的失敗來源。Blind Program-Solve（模型自行擷取變數）的表現將是重要的後續研究方向：

1. **擷取專門化**：開發專門的臨床變數擷取模型，可能比通用 LLM 更可靠。

2. **擷取-執行的聯合最佳化**：當擷取與程式碼生成聯合訓練時，是否能產生更好的端到端表現？

3. **不確定性的量化**：模型應能標記其擷取的不確定性，而非在變數缺失時產生任意值。

**安全執行環境的強化**

本文坦誠承認執行器「非沙箱化」，這指向重要的安全研究方向：

1. **真正的沙箱化**：採用容器化（如 gVisor、Firecracker）或 WebAssembly 隔離，以提供更強的安全保證。

2. **形式化驗證**：對執行器的安全屬性進行形式化證明，確保即使面對惡意程式碼也不會洩漏資源。

3. **審計日誌**：完整的執行日誌對於臨床環境的可追溯性至關重要。

**臨床整合與工作流程**

1. **人機協作介面**：在模型不確定時如何有效提示臨床醫師介入？這需要設計適當的棄答（abstention）機制與不確定性溝通方式。

2. **錯誤恢復**：當程式碼執行失敗時，系統應如何回退到替代策略（如直接算術或人工審核）？

3. **多計算器組合**：臨床決策常需要多個計算器的組合結果，介面應如何支援這種組合？

**評估方法的改進**

1. **臨床效用評估**：超越基準測試分數，評估系統對臨床決策的實際影響。

2. **錯誤嚴重性的分級**：不同計算器的錯誤具有不同的臨床後果（如劑量計算錯誤 vs. 風險評分誤差），應發展嚴重性感知的評估指標。

3. **跨基準泛化**：在多個臨床計算基準上評估，而非僅依賴 MedCalc-Bench。

**理論理解的深化**

1. **為什麼程式碼執行有助於大型模型？** 32B 模型從執行中獲益而 7B 模型沒有，這背後的機制是什麼？是更好的程式碼生成能力、更可靠的變數處理，還是其他因素？

2. **失敗模式的系統分類**：對程式碼執行介面的失敗進行系統分類（如語法錯誤、邏輯錯誤、執行逾時、輸出格式錯誤），以指導改進方向。

3. **與思維鏈的理論比較**：程式碼執行與自然語言推理在表達能力上的理論比較，以及它們在不同任務上的互補性。

這些研究方向不僅將推進臨床計算器自動化的技術水平，也將為更廣泛的醫療 AI 系統中「語言模型 + 確定性執行」的混合架構提供重要的理論與實證基礎。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：論文聚焦於大型語言模型在臨床計算器（clinical calculator）上的算術不可靠問題。由於臨床計算（如 APACHE II、eGFR、MELD 等）直接影響治療決策，任何單一數值錯誤都可能改變臨床建議，因此這是一個高風險場域。傳統上業界依賴為每個計算器手寫、驗證並維護獨立函式，但這種做法維護成本高且覆蓋率有限。論文因此提出一個替代方案：讓模型不直接計算，而是撰寫 Python 程式交由受限執行器執行。

**Q2：為什麼現有方法不足以解決這個問題？**
A：現有方法主要有兩條路線，但各有缺陷。第一條是讓模型直接做算術，但 Goodell 等人的研究顯示 ChatGPT 在 48 個計算任務中約有三分之一的試驗答案錯誤，說明 LLM 的算術能力不足以承擔臨床重任。第二條是為每個計算器手寫經驗證函式，這雖然準確，但只能覆蓋已實作的計算器，其餘案例只能棄答（abstain），形成覆蓋率與準確率的取捨。本文正是針對這兩條路線的不足，提出一個通用的程式化求解介面。

**Q3：為什麼這個問題在臨床場域特別重要？**
A：臨床計算器的輸出會直接影響病人的處置決策，例如腎功能評估、肝病嚴重度分級、心血管風險預測等場景，數值差一點就可能導致截然不同的治療建議。此外，許多公式本身具有版本演進，例如不分種族 eGFR、MELD 3.0、PREVENT、Sampson LDL 方程式都已取代前代版本，但基準測試可能仍獎勵舊公式，因此僅有執行保真度是不夠的，還需要公式本身的版本審核。本研究正是在這個臨床高風險、版本敏感的背景下，探討如何兼顧可靠性與可維護性。

**Q4：論文提出的核心方法是什麼？**
A：核心方法是 Program-Solve 介面：模型接收病歷、公式與變數後，撰寫一個簡短的 Python 程式，由受限的本機執行器（restricted local executor）執行並回傳數值、日期或妊娠週數元組。執行器本身不包含任何計算器專屬的函式或常數，所有計算邏輯都由模型即時翻譯公式產生。這種設計把模型的任務縮減為「決定如何使用求解器」，而非親自執行算術，從而把算術錯誤的風險交給確定性的程式執行。

**Q5：本研究的關鍵創新點為何？**
A：關鍵創新在於以一個通用的執行介面取代逐個計算器的手寫程式碼，並在「公式、變數、病歷長度」三者皆匹配的條件下，進行嚴格的控制變數比較。論文同時比較直接算術、手寫函式庫與程式化求解三條路線，並以叢集自助法（cluster bootstrap）處理案例嵌套於 55 個計算器的統計結構。此外，作者還對基準測試的 55 個公式進行臨床指引稽核，標記出 16 個有版本、使用或係數疑慮的公式，這在一般基準測試論文中並不常見。

**Q6：執行器的設計有哪些重要選擇？**
A：執行器採取了多層防護：每個程式以全新的子行程（subprocess）執行，內建函式採用白名單（allow-list）並禁用檔案、eval、exec 等危險原語；匯入僅限於標準函式庫的 math、date、time、calendar 模組；靜態拒絕 async 與 generator 結構；並設有 256 MB 記憶體、CPU 與 5 秒時鐘上限以及執行行數上限。然而作者也明確指出，這是「受限但非沙盒化」的設計——沒有容器或系統呼叫過濾，因此安全性仍是已知限制。

**Q7：實驗使用了哪些基準測試與模型？**
A：實驗採用 MedCalc-Bench Verified，包含 1,100 個測試案例橫跨 55 個計算器，並依基準定義的容差評分。模型選用兩個開放權重模型：Qwen2.5-7B-Instruct（bf16）與 Qwen2.5-32B-Instruct-AWQ（4-bit），皆透過 vLLM 在雲端 H100 GPU 上本機部署，每個案例以 5 個種子（42 至 46）執行。單次示範（one-shot）範例取自基準的獨立 one-shot 切分，確保任何測試案例的標準答案或解釋都不會進入提示。

**Q8：最重要的實驗結果為何？**
A：在公式、變數與病歷皆匹配的條件下，Program-Solve 在 7B 模型上僅以 75.31% 對比 72.02% 略勝（配對差異 +3.29 百分點），但 95% 計算器叢集區間為 [-3.49, 10.38]，跨越零點，差異不可靠；在 32B 模型上則以 90.53% 對比 83.47% 明顯勝出（+7.05，區間 [0.47, 14.60]），明確排除零點。手寫函式庫在其支援的 440 個案例上完全正確，但對其餘案例棄答，全集僅 40.0%。這顯示執行器對部分模型有幫助，但並非萬靈丹。

**Q9：有哪些消融式（ablation）比較？**
A：論文設計了多個實驗臂以分離不同變數的影響：Note only（僅病歷）、Page without formula（病歷加計算器頁面但抑制公式）、Open-book arithmetic（加入公式並由模型算術）、Extract-Solve library（模型擷取變數後呼叫 22 個手寫計算器）、Gold-Solve library（手寫計算器接收標準變數）、Program-Solve（模型寫程式、執行器執行）以及 Blind Program-Solve（無公式也無標準變數）。其中 Program-Solve 對 Open-book arithmetic 為輸入匹配比較，而 Program-Solve 對 Extract-Solve library 則否；匹配的函式庫比較為 Program-Solve/Gold-Solve 與 Blind Program-Solve/Extract-Solve 兩對。

**Q10：實際部署時有哪些考量？**
A：本機部署（local serving）避免了外部 API 呼叫與資料傳輸，對於受 HIPAA 或類似法規約束的醫療機構特別有吸引力。論文中所有模型皆透過 vLLM 在自有 H100 GPU 上執行，無資料外流風險。然而作者也提醒，未量測的成本包括 GPU 基礎設施、模型維護、提示工程與臨床驗證等，這些都是實際導入時必須納入的總持有成本。

**Q11：產品化時需要考量哪些權衡？**
A：產品化時面臨的核心權衡是覆蓋率與維護成本的取捨：手寫函式庫雖然在其支援範圍內完全準確，但每新增一個計算器都需要撰寫、驗證與持續維護，且對未支援的計算器只能棄答。Program-Solve 介面則以通用執行取代專屬程式碼，覆蓋全部 55 個計算器，但需要可靠的變數擷取與經審核的公式版本。論文的稽核發現 55 個公式中有 16 個有版本、使用或係數疑慮，意味著無論採用哪條路線，公式本身的正確性都是不可迴避的環節。

**Q12：本研究對領域的潛在影響為何？**
A：本研究最重要的貢獻是建立了一個控制變數嚴謹的比較框架，說明「執行器」這一層究竟解決了什麼、又沒解決什麼。它證實了在大型模型上，程式化求解相較直接算術有統計上可靠的優勢，但同時也提醒這並非公式驗證或變數擷取的替代品。對領域而言，這促使後續研究必須把「公式版本」、「變數擷取」與「算術執行」三個失效點分開處理，而非混為一談。

**Q13：論文承認哪些限制？**
A：作者明確指出幾項限制：首先是推廣範圍僅限於一個基準（MedCalc-Bench Verified）與兩個模型，未涵蓋未見公式、其他語言或不同臨床場景。其次，執行器雖受限但並非沙盒化，缺少容器或系統呼叫過濾層，存在已知的安全暴露。再者，基準本身的 55 個公式中已有 16 個被標記為有疑慮，這意味著即使執行完全正確，輸出仍可能與當前臨床指引不一致。

**Q14：主要的失敗案例有哪些？**
A：在 Program-Solve 模式下，7B 模型有 6.7% 的案例-種子列未產生有效答案，32B 模型則為 0.7%；錯誤答案率分別為 18.0% 與 8.8%，相較之下 Open-book arithmetic 沒有未答情形但錯誤率更高（28.0% 與 16.5%）。從相關文獻可知，多數計算器選擇錯誤其實是理解錯誤（comprehension error）而非算術錯誤，這意味著即使把算術外包給執行器，理解層面的失效仍會造成最終答案錯誤。

**Q15：未來的研究方向為何？**
A：作者暗示的未來方向包括：建立可靠的變數擷取機制、持續稽核並更新公式版本以對齊當前臨床指引、強化執行器的安全隔離（如加入容器或系統呼叫過濾），以及把方法推廣到未見公式與其他語言環境。此外，如何把「公式選擇」、「變數擷取」與「算術執行」三個階段各自最佳化並組合成可驗證的端到端系統，將是臨床 LLM 真正落地的關鍵下一步。

## 實務應用指南

### 適用場景

1. **醫院 EHR 內嵌的臨床決策支援**：在既有電子病歷系統中部署本機 LLM 服務，醫師輸入病歷文字後，由模型產生 Python 程式碼呼叫確定性求解器，輸出 APACHE II、MELD 3.0、PREVENT 等分數，避免模型直接算術造成的單一位數誤差導致處置建議錯誤。

2. **基層診所的低頻高風險計算**：基層診所無力維護 55 套臨床計算器的程式庫，但可部署 Program-Solve 介面處理長尾需求；對於未涵蓋的計算器，模型仍可嘗試產生程式碼，比直接棄答更能覆蓋罕見情境。

3. **臨床指引更新後的快速再部署**：當 eGFR、MELD 3.0、PREVENT、Sampson LDL 等公式版本更新時，只需更新提示中的公式文字與黃金變數，無需重寫整個函式庫；適合需要追趕最新臨床指引的機構。

4. **教學醫院的住院醫師訓練工具**：讓住院醫師看到模型如何將臨床公式翻譯為 Python 程式碼，作為計算器原理的教學輔助；同時受限執行器可避免任意程式碼執行造成的資安風險。

5. **跨機構臨床研究資料前處理**：在多中心研究中統一以 Program-Solve 介面從自由文本病歷擷取計算結果，減少各站點因計算器版本不同造成的系統性偏差。

### 實作前置條件

**資料面**
- 經審核的臨床計算器公式清單（建議以 MedCalc-Bench Verified 為起點，並對照現行臨床指引逐條稽核；本文發現 55 個計算器中有 16 個存在版本、使用情境或係數疑慮）
- 每個計算器的標準化變數定義與容差規則
- 至少一份含黃金標註的測試集，用於驗證部署後的準確率

**運算面**
- 具備 H100 等級 GPU 的本機推論環境（vLLM 框架；7B 模型單卡即可，32B-AWQ 單卡，Mistral 等較大模型需兩卡張量平行）
- 受限執行器所需的容器化環境（CPU 限制、記憶體上限 256 MB、5 秒時限、執行程式碼行數上限）
- 雖然執行器有 builtins 允許清單與靜態拒絕 async/generator，但本文明確指出「這不是沙箱」，無系統呼叫過濾器；正式部署需額外加上容器或 seccomp 隔離

**技能面**
- 熟悉 vLLM 部署、量化（AWQ）與溫度/解碼參數調校
- 能撰寫 Python 標準庫（math、datetime、calendar）層級的受限執行器
- 具備臨床計算器領域知識，能辨識公式版本差異（如 race-free eGFR 與舊版的係數差別）

### 實作步驟建議

1. **公式稽核與版本對齊**：以本文附錄的稽核方法為模板，逐條比對 MedCalc-Bench Verified 中的 55 個計算器與現行臨床指引；標記出 16 個有疑慮的計算器，決定要採用哪個版本。

2. **建立黃金變數與公式提示模板**：為每個計算器準備「公式文字 + 黃金變數 + 病歷全文」的標準化提示；one-shot 範例須來自獨立的訓練分割，避免測試洩漏。

3. **部署受限執行器**：實作 subprocess 隔離、builtins 允許清單、靜態拒絕 `async`/`generator`、256 MB 記憶體上限、5 秒時鐘、執行程式碼行數上限；額外加上容器或 syscall 過濾以補本文指出的沙箱缺口。

4. **選擇模型規模**：依本文結果，若使用 7B 等級模型，Program-Solve 對開卷算術的優勢在統計上未排除零（+3.29 點，95% 計算器叢集區間 [-3.49, 10.38]），需自行評估是否值得；若使用 32B 等級模型，優勢明確（+7.05 點，區間 [0.47, 14.60]）。

5. **執行配對評估**：在自家資料上重現本文的配對設計——同一公式、同一變數、同一病歷全文下比較 Program-Solve 與開卷算術；以計算器叢集 bootstrap（10,000 次抽樣）為主要不確定性來源，避免僅看案例層級 p 值。

6. **建立覆蓋率—準確率取捨曲線**：若同時維護手寫函式庫，繪製「實作 N 個計算器時的全集準確率」曲線；本文顯示 22 個計算器的函式庫在全集僅達 40.0%，因為棄答機制限制了覆蓋率。

7. **分離失效模式**：將錯誤分為「無效程式」、「錯誤答案」、「未回答」三類（本文 32B 模型仍有 0.7% 無答案、8.8% 錯誤），並針對每類設計降級策略，例如錯誤答案時退回開卷算術或人工覆核。

### 潛在風險與注意事項

- **執行器非沙箱**：本文明確指出受限執行器「不是沙箱」，沒有容器或 syscall 過濾；模型產生的程式碼若繞過靜態檢查，仍可能存取主機資源。**緩解**：務必在容器或 gVisor/Firecracker 等強隔離環境中執行，並關閉不必要的系統呼叫。

- **公式版本過期**：基準測試中的 16 個計算器存在版本疑慮，若直接採用提示中的公式而未對照最新指引，可能在臨床上使用已被取代的舊公式（如舊版含種族係數的 eGFR）。**緩解**：建立公式版本管理流程，每次臨床指引更新後重新稽核並更新提示。

- **變數擷取失敗**：本文的 Program-Solve 假設黃金變數已給定；若改為盲測（Blind Program-Solve），模型須自行從病歷擷取變數，會引入新的失效點。**緩解**：將變數擷取與程式碼生成分開評估，必要時退回 Extract-Solve 函式庫。

- **小模型效益不確定**：7B 模型下 Program-Solve 對開卷算術的差異區間跨零，部署小模型時不應假設此介面一定帶來準確率提升。**緩解**：在自家資料上做配對評估，若無統計顯著差異，可考慮直接使用開卷算術以降低維運負擔。

- **案例叢集效應**：本文指出案例在計算器內的組內相關係數達 0.68–0.81，傳統案例層級統計的有效樣本數僅 67–79；單看案例 p 值會過度樂觀。**緩解**：以計算器叢集 bootstrap 為主要不確定性度量，並對案例層級 p 值做 Holm 校正。

- **提示預算與存取混淆**：本文顯示在變數存取固定時，預算從 120 字提升到 250 字可額外增加 4–12 點；若同時改變預算與變數存取，會無法歸因改善來源。**緩解**：評估時固定其他維度，逐一改變單一變因。

### 與其他技術的整合建議

- **與既有臨床計算器函式庫共存**：可將手寫函式庫視為「高信心路徑」，僅在函式庫不支援時才走 Program-Solve；如此兼顧函式庫的精確性與 Program-Solve 的覆蓋率。

- **與 MedRaC 風格的檢索增強結合**：在模型產生程式碼前，先以檢索機制從公式庫中挑選候選公式並驗證版本，再交給模型翻譯為 Python；可降低公式選擇錯誤率。

- **與可驗證獎勵訓練整合**：將執行器的輸出與黃金答案比對，作為 RLHF 或 verifiable-reward training 的獎勵訊號；本文引用文獻顯示此作法可提升整體表現。

- **與 EHR 的 FHIR 介面對接**：將模型擷取的變數對應到 FHIR Observation 資源，由執行器計算後寫回 FHIR ServiceRequest 或 ClinicalImpression，維持資料可追溯性。

- **與思維鏈提示分工**：在模型產生 Python 前，先以自然語言思維鏈說明公式選擇與變數對應，再產出程式碼；本文指出多數計算器選擇錯誤其實是理解錯誤而非算術錯誤，思維鏈有助於分離這兩類失效。

- **與監控儀表板整合**：將「無效程式率」、「錯誤答案率」、「未回答率」三項指標（本文 32B 模型為 0.7% / 8.8% / 0%）即時推送至監控系統，設定閾值自動降級或通知人工覆核。

### 給不同背景讀者的閱讀建議

**給初學者**：本文的核心訊息很直觀——與其讓 LLM 直接算數，不如讓它寫程式碼、由確定性求解器執行。閱讀時先看圖 1 與表 2，理解 Program-Solve、開卷算術、手寫函式庫三者的差異；數字上 32B 模型提升 7 個百分點看似不大，但在臨床上一個錯誤的劑量或評分可能致命，這就是為什麼「確定性」值得追求。

**給 AI 工程師**：重點在實作細節——受限執行器的設計（builtins 允許清單、靜態拒絕 async/generator、256 MB/5 秒上限）以及它「不是沙箱」這項警訊；評估方法上，計算器叢集 bootstrap（10,000 次抽樣）與案例叢集相關係數（0.68–0.81）是關鍵，傳統案例 p 值會誤判顯著性；部署時務必補上容器或 syscall 過濾。

**給研究者**：本文的價值在於嚴格控制變因後的配對比較——同一公式、同一變數、同一病歷全文下比較執行路徑，這在文獻中少見；可延伸的方向包括：將此介面推廣到未見公式（泛化性）、其他語言的病歷、以及 verifiable-reward training 的獎勵設計；16 個公式的稽核結果也值得與臨床指引專家合作延伸。

**給產品經理**：商業決策上，32B 模型才顯示明確優勢，7B 模型效益不確定，這影響部署成本評估；手寫函式庫雖然在支援的 440 個案例上 100% 正確，但全集僅 40.0%，代表「精確但覆蓋不足」的取捨；產品定位上，Program-Solve 介面是「覆蓋率優先」的方案，適合無法承擔 55 個計算器維護成本的中小型機構，但需配套臨床指引稽核流程以避免公式過期風險。
