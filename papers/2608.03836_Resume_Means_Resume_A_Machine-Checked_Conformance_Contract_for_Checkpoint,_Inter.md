# 恢復即恢復（Resume Means Resume）：工作流持久層（Workflow Persistence Layers）中檢查點（Checkpoint）、中斷（Interrupt）與恢復（Resume）語意之機器檢驗的一致性合約（Machine-Checked Conformance Contract）

## ⚡ TL;DR

現有智慧代理工作流框架的持久化恢復語意不一致，且缺乏機器可檢驗合約，行為甚至違反自身文件聲明。
本文提出RESUME合約，定義持久化API性質與分支意圖、活性義務，並以TLA+模型和測試框架檢驗。
實測發現五個框架各有合約違規，REMIT參考排序器以Verus驗證核心，修復分支與檢查點有效性問題。

## 摘要翻譯

一個將執行狀態（Execution State）持久化，使一次執行（Run）可被中斷（Interrupt）、於崩潰後存續並繼續的框架，必須界定：對於已觸發的效果（Already Fired Effects），恢復（Resume）究竟意謂為何。五個廣泛部署的智慧代理工作流框架（Agent Workflow Frameworks）各自給出不同答案，沒有任何一個提供機器可檢驗合約（Machine-Checkable Contract），且其行為甚至違反了它們所陳述的片段。RESUME 恢復合約（RESUME CONTRACT）針對持久化 API（Persistence API）陳述了六個性質——前綴延續（Prefix Continuation）、效果恰好一次（Effect Exactly-Once）、分支決定性（Fork Determinism）、檢查點有效性（Checkpoint Validity）、單次消耗（Consume-Once）、復原決定性（Recovery Determinism）——再加上分支意圖（Fork-Intent）與活性義務（Liveness Obligations）。TLA+ 模型（TLA+ Model）窮盡地檢查參考語意（Reference Semantics），在規模化界限（Scaled Bounds）下仍維持不變（740 萬個狀態（7.4 Million States））；39 格故障矩陣（39-Cell Fault Matrix）產生了獨立性（Independence）所需的分離模型（Separating Models），而單次消耗可拆分，其消耗條款（Consumption Clause）獨立於其他六個性質。一個確定性、無 LLM 的測試框架（Deterministic Harness）在固定版本釋出（Pinned Releases）上測量它們。

LangGraph 1.2.9 持久記錄（Durably Recorded）了第二個恢復值（Second Resume Value）卻從未查閱它，默默持久化模式無效狀態（Schema-Invalid State），並在真實 SIGKILL 之後重新執行（Re-execute）持久記錄的工作（Durably Recorded Work）：在同一個 API 上，跨中斷為恰好一次（Exactly-Once）語意，跨崩潰為至少一次（At-Least-Once）語意。CrewAI 1.15.2 重新執行已完成的帶有效果的方法（Effect-Bearing Methods），與其書面聲明相悖；pydantic-graph 1.x 無法在節點中間崩潰（Mid-Node Crash）後恢復；沒有任何兩個被探測的框架共享相同的一致性輪廓（Conformance Profile）。單次消耗在循序情況下成立，但在並發傳遞（Concurrent Delivery）下失效：k 個行程（k Processes）恢復一個暫停中斷（Parked Interrupt）會觸發閘控效果（Gated Effect）k 次，40 格中的 36 格（36 of 40 Cells）飽和度（Saturation）達 1.0（Saturation 1.0），且此失效會跨主機（Cross Hosts）發生。REMIT 是一個參考排序器（Reference Sequencer），其經 Verus 驗證的復原核心與釋出的可執行檔逐行相同，修復了分支與有效性儲存格。跨行程儲存格（Cross-Process Cell）在讀取路徑上被修復，且該修復已隨版本釋出：一個選擇加入的閘控會在共享儲存中宣告消耗，在任何節點執行之前服務一個競爭者並拒絕其餘者。

### 核心貢獻（3～5點）
- 提出 RESUME 恢復合約（RESUME CONTRACT），為工作流持久層（Workflow Persistence Layers）的檢查點（Checkpoint）、中斷（Interrupt）與恢復（Resume）語意建立首個機器可檢驗合約（Machine-Checkable Contract），涵蓋六項核心性質與分支意圖（Fork-Intent）、活性義務（Liveness Obligations）。
- 以 TLA+ 模型（TLA+ Model）窮舉模型檢查（Exhaustive Model Checking）參考語意（Reference Semantics），並透過 39 格故障矩陣（39-Cell Fault Matrix）證明各性質間的獨立性（Independence），特別是單次消耗（Consume-Once）之消耗條款（Consumption Clause）可獨立於其餘六項性質。
- 以確定性、無 LLM 的一致性測試套件（Conformance Suite）與一致性探針（Conformance Probes）評估五個主流智慧代理工作流框架（Agent Workflow Frameworks），發現沒有任何兩個框架共享相同的一致性輪廓（Conformance Profile），且多數行為違反其書面宣稱。
- 揭露 LangGraph 等框架在並發傳遞（Concurrent Delivery）下單次消耗失效的嚴重問題：k 個行程（k Processes）可令閘控效果（Gated Effect）觸發 k 次，飽和度（Saturation）在 40 格中的 36 格達 1.0，且失效會跨主機（Cross Hosts）發生。
- 設計並實作 REMIT 參考排序器（Reference Sequencer），其復原核心（Recovery Core）經 Verus 形式化驗證且與釋出可執行檔逐行相同；同時提出並隨版本釋出讀取路徑上的跨行程儲存格（Cross-Process Cell）修復方案，以選擇加入的閘控在共享儲存中宣告消耗，確保效果恰好一次（Effect Exactly-Once）。

### 適合對象
本論文適合從事工作流引擎、智慧代理工作流框架（Agent Workflow Frameworks）、大型語言模型代理（LLM Agents）系統、分散式系統可靠性與形式化驗證的研究者與工程師；特別是關注檢查點（Checkpoint）、中斷（Interrupt）、恢復（Resume）語意正確性，以及需要以機器檢驗合約（Machine-Checked Conformance Contract）評估框架行為的實務開發者與系統架構師。

## 深度分析

#### 方法論解析

##### 1.1 問題界定：持久層平面（Persistence Plane）的恢復語意（Resume Semantics）

本文並非提出另一套工作流執行模型，而是把工作流持久層（Workflow Persistence Layers）中「中斷（Interrupt）後如何恢復（Resume）」這個長期存在卻未被形式化的承諾，提升到一個可機器檢驗的一致性合約（Machine-Checked Conformance Contract）層級。核心問題是：當一次執行（Run）因為人類審批、搶佔或崩潰而暫停後，已經觸發的效果（Already Fired Effects）——例如付款、發送訊息、寫入檔案——在恢復時是否會再次執行？不同智慧代理工作流框架（Agent Workflow Frameworks）對此給出不同答案，而且這些答案往往連自身文件都無法滿足。作者因此選擇在持久化 API（Persistence API）邊界上定義合約，因為所有框架都共享 checkpoint（檢查點）、interrupt（中斷）、resume command（恢復指令）與狀態查詢這組介面。

##### 1.2 RESUME CONTRACT（RESUME 恢復合約）的六條性質

合約本身由六條性質組成，並額外加上 fork-intent（分支意圖）與 liveness（活性）義務：

- **Prefix Continuation（PC，前綴延續）**：從某個 checkpoint（檢查點）恢復時，應延續該 checkpoint 之前的執行前綴，而非無聲丟棄已完成工作；重新執行的範圍應僅限於中斷後的後綴。
- **Effect Exactly-Once（EO，效果恰好一次）**：對於非冪等效果（Non-idempotent Effects），在中斷前已經觸發的效果（Already Fired Effects）在恢復後不應再次觸發。這裡的 exactly-once（恰好一次）與 at-least-once（至少一次）形成對照。
- **Fork Determinism（FD，分支決定性）**：相同的持久狀態與相同的 resume value（恢復值）必須導致相同的後續執行；不允許把第二個 resume value（第二個恢復值）持久記錄（Durably Recorded）下來卻永遠不查閱。
- **Checkpoint Validity（CV，檢查點有效性）**：只允許持久化符合綱要的狀態；把 schema-invalid state（模式無效狀態）靜默寫入即構成違規。
- **Consume-Once（CO，單次消耗）**：針對同一個暫停中斷（Parked Interrupt）的恢復值只能被消耗一次；多個並發恢復請求必須被閘控，避免閘控效果（Gated Effect）重複觸發。
- **Recovery Determinism（RD，復原決定性）**：復原決策必須是 durable state（持久狀態）的函數，不能依賴尚未持久化的暫態順序資訊。

Fork-intent（分支意圖）義務確保 resume value（恢復值）確實對應到被中斷的意圖；liveness obligations（活性義務）則要求系統最終必須能夠恢復並繼續前進。

##### 1.3 機器檢驗模型：TLA+ 與故障矩陣（Fault Matrix）

作者以 TLA+ Model（TLA+ 模型）刻劃參考語意（Reference Semantics），並設置六個 fault switch（故障開關），每個開關對應一種在真實框架中觀察到的違規類別。TLC 對參考配置進行窮舉模型檢查（Exhaustive Model Checking）：基準配置產生 87 個生成狀態、59 個相異狀態且無任何違規；對單一故障配置則能在深度 4–6 內給出反例。進一步把狀態空間規模化到 740 萬個狀態（7.4 million states）後，性質仍然成立，顯示這些結論並非小模型下的偶然。

在此基礎上，作者建立 39-cell fault matrix（39 格故障矩陣），將每種故障與每條性質交叉比對。矩陣中的「分離模型」（Separating Models）——即在某故障啟動下仍保持某條性質乾淨的模型——被用來證明性質間的獨立性（Independence）：EO、PC、FD、CV、RD 可以獨立於其他五條性質的合取而失效；CO 結構上依賴 EO（若效果已重複觸發，消耗自然失敗），但其 consumption clause（消耗條款）卻獨立於全部六條性質。這種「Consume-Once（單次消耗）分裂」的現象說明：即使六條性質全數滿足，跨行程的消耗閘控仍可能失敗。

##### 1.4 確定性一致性測試框架（Deterministic Harness）

為了在真實框架上測量一致性，作者設計了一個確定性測試框架（Deterministic Harness）。所有探針都是純 Python 的協定序列，直接操作框架的持久化 API（Persistence API）：沒有 LLM 呼叫、沒有競爭時窗。崩潰以兩種方式模擬：多數測試使用例外中斷，而 probe 133 則使用 barrier-synchronized SIGKILL（強制終止信號）來複製真實程序被殺死的場景。效果計數器在每個程序本地維護，並透過一個跨行程的 durable external ledger（持久外部帳本）進行交叉驗證，從而將觀察到的行為與「已觸發的效果（Already Fired Effects）」進行客觀比對。

##### 1.5 REMIT 參考排序器（Reference Sequencer）

REMIT（Reference Sequencer，參考排序器）是作者提出的參考實作。其核心恢復決策函式以 Verus 進行形式化驗證，並且與實際出貨的可執行檔案「行級相同」（line-identical）。該核心以 Rust 實作，透過 PyO3 綁定提供給 Python 框架使用；針對 LangGraph 的 shim 被設計為 decision-free（無決策），所有策略判斷都交給已驗證核心。

REMIT 的貢獻在於修補故障矩陣中的多個儲存格：
- 對於 FD 與 CV，寫入路徑（write path）的金鑰機制與讀取路徑（read path）的 fork-intent filter 形成配對，能夠大聲拒絕無效的持久狀態，並修復 LangGraph issue #6663。
- 對於 cross-process cell（跨行程儲存格），REMIT 在讀取路徑提供一個 opt-in gate（選用閘控）：在共享儲存（shared store）中先聲明消耗，讓第一個競爭者（racer）通過並在節點執行之前拒絕其餘競爭者，從而修復並發傳遞（Concurrent Delivery）下的 CO 失效。

#### 實驗數據解讀

##### 2.1 TLA+ 窮舉模型檢查（Exhaustive Model Checking）結果

參考模型在基準配置下僅有 87 個生成狀態、59 個相異狀態，且 TLC 未發現任何違反六條性質的行為。這說明作者定義的 RESUME CONTRACT（RESUME 恢復合約）在理想參考語意（Reference Semantics）下是自洽的。當逐一切換六個 fault switch（故障開關）後，每個單一故障配置都能在深度 4–6 內產生反例，顯示模型檢查器不僅能驗證正確性，也能精確定位最小違規路徑。

更關鍵的是規模化界限（Scaled Bounds）實驗：當狀態空間被放大到 740 萬個狀態（7.4 million states）時，所有性質仍然成立。這排除了「合約只在過度簡化的模型中成立」的質疑，也為後續在真實框架上的探測提供了理論後盾。

##### 2.2 跨框架一致性輪廓（Conformance Profile）

作者在固定版本釋出（Pinned Releases）上測量了五個框架，發現「沒有兩個被測框架共享相同的一致性輪廓（Conformance Profile）」：

- **LangGraph 1.2.9**：存在多項違規。它會把第二個 resume value（恢復值）持久記錄（Durably Recorded）下來卻從不查閱，構成 fork determinism（分支決定性）違規；會靜默持久化 schema-invalid state（模式無效狀態），構成 checkpoint validity（檢查點有效性）違規；在真實 SIGKILL（強制終止信號）後會重新執行已經持久記錄的工作（Durably Recorded Work），使得同一支 API 在「跨中斷」時表現為 exactly-once（恰好一次），在「跨崩潰」時卻退化為 at-least-once（至少一次）。這些問題在三種 checkpointer backend（包含 live PostgreSQL）上都被複製，顯示並非後端實作瑕疵，而是框架層級的語意缺陷。
- **CrewAI 1.15.2**：文件聲稱恢復時「不會重新執行已完成工作」，但實測卻會重新執行已完成的 effect-bearing methods（帶有效果的方法），直接違背自身文件。
- **pydantic-graph 1.107.1**：在節點中間崩潰（Mid-Node Crash）後無法使用自己的恢復入口點繼續執行，屬於嚴重的恢復能力缺失。
- **LlamaIndex Workflows 2.22.2**：文件明確承認 at-least-once（至少一次）的前綴重放，並要求使用者把 wait_for_event 提前放置、讓前置工作可安全重新執行。這是一種較弱的已知語意，與其他框架不可比較。
- **AutoGen AgentChat 0.7.5**：唯一會對被竄改的狀態發出明確拒絕的框架，在 checkpoint validity（檢查點有效性）上表現最佳。

Probe 160 進一步指出：每一個不完整的持久化邊界都會授權重新執行已完成工作，這顯示整個生態在持久化邊界處理上普遍存在脆弱性。

##### 2.3 Consume-Once（單次消耗）的並發失效

Consume-Once（單次消耗）在順序場景下成立，但在並發傳遞（Concurrent Delivery）下系統性失效：當 k 個行程同時對同一個 parked interrupt（暫停中斷）發出恢復請求時，閘控效果（Gated Effect）會被觸發 k 次。實驗中 40 個儲存格有 36 個達到飽和度（Saturation）1.0，即完全失效；而且失效會跨主機（Cross Hosts）發生。這證明 CO 不是單純的本地順序性質，而是需要跨行程共享儲存（Shared Store）中原子聲明消耗的分散式協議。

##### 2.4 REMIT 的修復效果

REMIT 成功修復了故障矩陣（Fault Matrix）中的 fork determinism（分支決定性）與 checkpoint validity（檢查點有效性）儲存格；針對 cross-process cell（跨行程儲存格），則透過讀取路徑（read path）上的 opt-in gate（選用閘控）在共享儲存中先聲明消耗，只讓一名競爭者（racer）進入節點執行。實驗顯示該修復已隨套件出貨，並能在固定版本上作為差分控制（Differential Control）重新建立。這說明一個小型的、經過形式化驗證的核心，確實能夠修補真實框架中的關鍵語意漏洞。

#### 與現有研究的比較

##### 3.1 與底層沙箱及高層語意回滾研究的區隔

近期有兩個強相關系統從上下兩端包夾本文議題，但並未佔據同一層級：

- **Crab**：在框架 API 之下對 OS-level sandbox state（作業系統級沙箱狀態）進行 checkpoint（檢查點）。它關心的是「如何保存整個執行環境」，而非 checkpoint/interrupt/resume 這組原語本身是否遵守恢復語意（Resume Semantics）。
- **DART**：在框架 API 之上判斷「機械上可行的 rollback（回滾）是否在語意上可接受」。它處理的是高層語意決策，而非持久化原語是否兌現承諾。

本文則精準定位在持久層平面（Persistence Plane）：它問的是 checkpoint（檢查點）、interrupt（中斷）、resume（恢復）這些原語本身是否保持其承諾——這正是 GitHub issues 中開發者實際遭遇問題的層級。

##### 3.2 與同意完整性及並發測試研究的關係

- **Consent-Integrity（同意完整性）研究**：將審批綁定到動作內容。本文的 fork determinism（分支決定性）與 consume-once（單次消耗）則進一步治理審批的生命週期：同一個中斷不能被不同 resume value（恢復值）重複回答，也不能被多個競爭者並發消耗。
- **Concurrent Framework Testing（並發框架測試）研究**：目標是尋找 bug（缺陷）。本文則先定義合約（Contract），再將 bug 視為合約違規進行一致性測量，並提供經過機器驗證的參考實作。

綜合來看，本文的獨特貢獻在於首次結合了「明確的 resume contract（恢復合約）」、「機器檢驗的 TLA+ 模型」與「跨框架一致性測量」，並以 REMIT 參考排序器（Reference Sequencer）證明這些性質可以實作。

##### 3.3 限制與不宣稱事項

作者對宣稱範圍做了嚴格限定，這些限制也應被視為研究誠信的一部分：

- 不宣稱六條性質的集合是最小或完整的。
- 不宣稱各違規的普遍發生率（Prevalence Rates）。
- 不宣稱被測框架代表整個生態系。
- 不宣稱某框架在未測量的性質上必然失敗。
- REMIT 的 composite package（複合套件）並未進行端到端精化驗證；只有 recovery-decision core（復原決策核心）、EO admission（EO 准入）與 PC/CV commit cores（PC/CV 提交核心）是經 Verus 驗證的可執行孿生（Verified Executable Twins），並透過 exhaustive differential suite（窮舉差分測試套件）與出貨的 HashSet/HashMap 實作橋接，但未精化到編譯後的二進位檔。

---

#### 可重現性評估

本文在可重現性（Reproducibility）上做了相當完整的設計：

- **Artifact（工件）**：包含一致性探針（Conformance Probes）、TLA+ 模型、TLC 配置、REMIT 設計文件，以及 `reproduce.sh` 重現腳本。該腳本宣稱能從已提交資料（Committed Data）單一指令重導出所有標題數字。
- **確定性測試框架（Deterministic Harness）**：所有探針鎖定固定版本釋出（Pinned Releases），不使用 LLM，不依賴競爭時窗；崩潰以例外與 barrier-synchronized SIGKILL（強制終止信號）兩種方式重現；效果計數器與 durable external ledger（持久外部帳本）交叉驗證，大幅降低環境敏感度。
- **機器驗證閘道**：REMIT 的 Verus 驗證核心在 CI 閘道下與出貨可執行檔案保持 line-identical（行級相同），這為「驗證即實作」提供了強證據。

目前主要限制是：工件倉庫與 REMIT 套件原始碼在出版前仍為私有，僅能透過審閱存取（Review Access）向作者索取。一旦公開，配合 `reproduce.sh` 與已提交資料，其可重現性應屬高度可信；但社群仍需獨立驗證 CI 閘道與差分測試套件的實際運作。

#### 未來研究方向

基於本文的合約、模型與測量結果，可延伸的研究方向包括：

1. **合約擴展**：將補償（Compensation）、部分失敗（Partial Failure）、巢狀中斷（Nested Interrupts）、動態圖變更與多執行會話（Multi-Run Sessions）納入 RESUME CONTRACT（RESUME 恢復合約）。
2. **更廣泛的框架測量**：把一致性探針（Conformance Probes）應用到更多框架、更多版本，甚至商業級編排器，建立長期的一致性監測。
3. **端到端精化驗證**：從 TLA+ 參考語意（Reference Semantics）精化到 REMIT 的編譯後二進位，補足目前「未宣稱端到端精化」的缺口。
4. **拜占庭與分區容忍的 CO 閘控**：在網路分區或惡意競爭者（Byzantine Racers）存在下，形式化並驗證跨行程的 consume-once（單次消耗）協議。
5. **標準化一致性測試套件**：將本文的探針與合約發展為業界標準的 Persistence API Conformance Suite（持久化 API 一致性測試套件），供框架開發者自我認證。
6. **與 LLM 安全結合**：把恢復語意（Resume Semantics）整合進大型語言模型代理（LLM Agents）的安全框架，確保代理產生的非冪等效果（Non-idempotent Effects）在中斷與恢復過程中保持語意正確。
7. **對抗性與模糊測試**：在確定性測試框架之外，引入對抗性模糊測試（Adversarial Fuzzing）以發現合約未涵蓋的邊界案例。
8. **REMIT 效能與擴展性評估**：測量 opt-in gate（選用閘控）與 Verus 驗證核心在高吞吐量工作流中的延遲與擴展性 overhead。
9. **層次化組合合約**：針對巢狀或層次化工作流框架，研究如何組合多個子合約以形成整體恢復保證。

## 論文問答

**Q1：這篇論文處理的核心問題是什麼？為什麼「恢復」對代理工作流框架而言會變成正確性問題？**

A：這篇論文聚焦於工作流持久層在「中斷—崩潰—恢復」過程中，對已經觸發的副作用（effects）應該如何解釋「恢復」這個動作。隨著 LangGraph、CrewAI、LlamaIndex Workflows 等框架把付款、發訊、寫檔等非冪等操作放在持久化閘門之後，單純的「繼續執行」已經不夠，開發者必須知道哪些已完成的效果會被重跑、哪些不會。然而，各框架對這個語意的回答彼此矛盾，而且連它們自己文件片段所陳述的保證都無法滿足，因此「恢復即恢復」成為一個需要形式化合約與機器檢驗的正確性問題。

**Q2：現有框架為何無法提供足夠的保證？論文引用了哪些來自實際部署框架的證據？**

A：現有框架的問題不只是缺少規格，而是它們對同一個持久化 API 表面給出互不相容的語意，例如 CrewAI 聲稱檢查點能「在不重新執行已完成工作的情況下恢復」，LlamaIndex 卻要求使用者把 `wait_for_event` 放在前面並確保前置工作可安全重跑，LangGraph 則對 `@task` 結果做記憶化。論文進一步以確定性探針重現了 GitHub issues 中的行為：LangGraph 會把第二個恢復值持久記錄卻永遠不查詢、默默寫入模式無效的狀態，並在真實 SIGKILL 後重跑已持久記錄的工作；CrewAI 會重跑已完成且帶副作用的方法；pydantic-graph 在節點中間崩潰後無法恢復。這些觀察顯示，框架文件與實際行為之間存在系統性的不一致。

**Q3：為什麼需要一份「機器可檢驗合約」？它填補了什麼樣的缺口？**

A：網路協定與檔案系統長期以來都有明確合約、機器檢驗模型與一致性測試套件，但工作流持久層卻缺乏這樣的基礎設施，開發者無法透過型別、簽名或文件屬性來判斷當前框架採用哪種恢復紀律。機器可檢驗合約把恢復語意從自然語言文件轉換成可以在形式化模型中驗證、在實作上測試的性質，讓不同執行模型能夠在同一個 API 邊界上被比較。這不僅能區分「採用較弱語意」與「實作缺陷」，也為框架維護者與使用者提供了一個客觀的審計基準。

**Q4：RESUME 恢復合約包含哪六個性質？它們各自管轄什麼層面？**

A：RESUME 恢復合約定義了前綴延續（PC）、效果恰好一次（EO）、分支決定性（FD）、檢查點有效性（CV）、單次消耗（CO）與復原決定性（RD）六個性質。PC 與 EO 決定哪些工作可以在恢復後重新執行、哪些已觸發效果不可重跑；FD 與 CO 管理中斷生命週期，確保同一個中斷不會被重複或衝突地恢復；CV 規範什麼樣的狀態可以被合法持久化；RD 則要求復原決策必須是持久狀態的函數，避免 LangGraph 同步持久模式中的順序缺陷。這六個性質全部只陳述在檢查點、中斷、恢復命令與狀態檢查 API 這個共同邊界上，因此能跨越不同執行模型進行比較。

**Q5：論文如何使用 TLA+ 與故障矩陣來驗證合約？分離模型展示了什麼？**

A：作者建立了一個包含六個故障開關的 TLA+ 模型，每個開關對應一種在實際框架中觀察到的違規類別，並用 TLC 對參考配置進行窮舉模型檢查，確認在無故障時所有六個性質都成立。接著執行 39 格的故障矩陣，把每個故障對每個性質的完整違規足跡找出來，這些足跡是「發現」而非「預設」的。透過這個矩陣，論文證明了 EO、PC、FD、CV、RD 可以獨立於其他五個性質的合取之外被違反，而 CO 在結構上依賴 EO；這些分離模型（separating models）說明合約中的每個性質都捕捉了不同的故障維度，不能互相化約。

**Q6：REMIT 是什麼？它如何修復發現的違規？Verus 在其中扮演什麼角色？**

A：REMIT 是論文提出的參考排序器，它在現有 `BaseCheckpointSaver` 介面之下提供一個效果分類帳，並以標註的成熟度等級交付不變量。其核心恢復決策函式使用 Verus 進行形式化驗證，且與實際出貨的執行檔行程式碼行級完全相同，確保理論保證與執行程式一致。REMIT 透過寫入路徑的金鑰機制修復分支決定性與檢查點有效性單元，並在讀取路徑加入可選閘門：在共享儲存中預先聲明消耗，讓第一個競爭者通過、其餘在節點執行前就被拒絕，從而修復跨行程的單次消耗失效。

**Q7：請描述確定性一致性測試框架的設計。它如何避免非確定性與 LLM 呼叫？**

A：測試框架由純 Python 的協定序列組成，直接操作各框架的持久化 API，完全不呼叫大型語言模型，也不依賴任何時間視窗或競速條件。中斷與崩潰透過例外機制在矩陣中模擬，並在探針 133 中以屏障同步的真實 SIGKILL 重現；效果則透過行程本地的計數器追蹤，並在跨行程後端探針中與磁碟上的外部分類帳交叉驗證。由於所有輸入、版本與執行路徑都被固定，任何開發者都可以使用 `reproduce.sh` 從已提交的資料重新導出每一個標題數字。

**Q8：在五個被測框架中，主要的一致性發現各是什麼？**

A：LangGraph 1.2.9 存在活躍分支違規與靜默的檢查點有效性違規，且在 PostgreSQL 等三種後端都能重現；更嚴重的是，同一個 API 在中斷後表現出「恰好一次」，在 SIGKILL 崩潰後卻變成「至少一次」。CrewAI 1.15.2 會重跑已完成且帶副作用的方法，直接違背其文件聲稱；pydantic-graph 1.107.1 在節點中間崩潰後無法透過自己的恢復入口繼續；LlamaIndex Workflows 2.22.2 出現文件記載的「至少一次」前綴重播；AutoGen AgentChat 0.7.5 則是唯一會大聲拒絕被竄改狀態的框架。結果顯示，沒有任何兩個被測框架擁有相同的一致性輪廓。

**Q9：單次消耗（consume-once）實驗在並發傳遞下揭露了什麼？跨主機失效如何呈現？**

A：在循序執行時單次消耗成立，但當 k 個行程同時對同一個暫停中斷發出恢復請求時，閘控效果會被觸發 k 次，因為各框架沒有在共享儲存中先聲明消耗。在 40 個測試儲存格中，有 36 個達到飽和度 1.0，表示幾乎所有並發情境都會違反單次消耗。這個失效還會跨主機發生，意味著即使把恢復請求分散到不同機器，只要它們共享同一個後端檢查點儲存，重複觸發副作用的風險依然存在。

**Q10：開發者可以如何運用 RESUME 恢復合約來選擇或建構工作流持久層？**

A：開發者可以把六個性質當成一份檢查清單，在評估框架時明確詢問：中斷後是否保證效果恰好一次、崩潰後是否會重跑已完成工作、同一個中斷能否被多次恢復、寫入的檢查點是否經過綱要驗證等。如果業務場景涉及付款或發訊等非冪等副作用，就應優先選擇能滿足 EO 與 CO 的框架，或在框架之上加裝類似 REMIT 的效果分類帳。這份合約也讓開發者能夠把「可接受的最弱語意」寫進系統設計文件，而不是被框架的不明行為牽著走。

**Q11：對框架維護者而言，有哪些產品層面的考量？較弱語意應該如何文件化？**

A：框架維護者應該把恢復語意視為 API 合約的一部分，而不是實作細節；即使選擇提供較弱的「至少一次」或「可安全重跑」語意，也應該明確標註為合約中的偏離（D），並說明哪些操作會被重跑、哪些不會。論文強調，採用較弱紀律應被記錄為 divergent，而不是 defective，這有助於維護者與使用者進行風險溝通。此外，維護者可以引入機器可檢驗的聲明與一致性探針，讓每次發布都能自動驗證這些語意是否仍然成立。

**Q12：一份共享的一致性測試套件對 LLM 代理工作流生態系可能產生什麼更廣泛的影響？**

A：如果產業能採用像 RESUME 這樣的合約與對應測試套件，不同框架之間將首次擁有可比較的恢復語意基準，降低開發者把副作用閘控工作流從一個框架移植到另一個框架時的認知負擔。這也有助於在框架文件、教學與稽核流程中建立共同語言，減少因語意誤解而導致的生產事故。長遠來看，這樣的標準化基礎可以促進更安全的多代理協作系統，因為代理之間的承諾與中斷恢復行為將變得可預測且可驗證。

**Q13：論文明確不聲稱哪些事情？這些承認的限制是什麼？**

A：論文明確表示，它不聲稱六個性質的集合是最小或完整的，也不聲稱測得的違規比例能代表整個生態系，更不聲稱任何框架在未測量的性質上必然失敗。此外，REMIT 的驗證範圍僅限於恢復決策核心、EO 准入與 PC/CV 提交核心，並未聲稱整個複合套件或編譯後二進位檔都經過端到端精化。這些限制意味著研究提供的是一個可擴充的合約與方法論，而不是對所有框架與所有路徑的最終判決。

**Q14：還有哪些失敗案例或邊緣條件尚未被修復或測量？**

A：雖然 REMIT 修復了分支決定性、檢查點有效性與跨行程單次消耗等儲存格，但複合套件層級的端到端正確性並未經過形式化精化，出貨的 PyO3 綁定與 LangGraph shim 仍屬於測量而非驗證範圍。此外，論文只測量了被探針覆蓋的執行路徑，並未窮舉所有可能的崩潰點、後端配置或並發度。對於那些未在合約中明確涵蓋的語意維度，例如長時間執行時的活性保證或分散式時鐘下的順序問題，仍然需要後續研究來補充。

**Q15：這項工作暗示了哪些未來方向？**

A：未來可以把 RESUME 合約擴展到更多框架與更多後端儲存，並建立一個持續整合閘門，在每次框架發布時自動執行一致性探針。另一個方向是將 Verus 驗證從核心恢復決策函式進一步延伸到完整編譯管線，實現對出貨二進位檔的端到端保證。最後，隨著多代理系統越來越依賴中斷與人類審批，把分支意圖（fork-intent）與活性義務形式化，並納入標準化的恢復合約，將是提升整體可信度的關鍵下一步。

## 實務應用指南

## 適用場景

1. **金融支付閘控工作流**  
   當 LLM agent 需要在使用者確認後才觸發轉帳、扣款或合約簽署時，必須保證「中斷後恢復」不會讓同一筆付款被重複執行。RESUME 恢復合約的 **效果恰好一次（Effect Exactly-Once）** 與 **單次消耗（Consume-Once）** 可直接對照支付閘的持久層行為，避免同一個批准被多個恢復行程重複消費。

2. **醫療／法規審批代理**  
   在需要人類專家介入（如醫師簽核、法務審查）的流程中，系統會在關鍵節點 **中斷（Interrupt）** 並等待 **恢復值（Resume Value）**。本研究發現 LangGraph 會持久記錄第二個恢復值卻永不參考，可能導致審批意見被忽略；套用合約的 **分支決定性（Fork Determinism）** 與 **復原決定性（Recovery Determinism）** 可確保審批上下文在崩潰後一致重建。

3. **多步驟供應鏈自動化**  
   跨倉庫、跨 API 的訂單處理常因網路或程序崩潰而停在節點中間。論文指出 pydantic-graph 在 **節點中間崩潰（Mid-Node Crash）** 後無法正確恢復。透過 **檢查點有效性（Checkpoint Validity）** 與 **前綴延續（Prefix Continuation）** 的檢驗，可在重啟時判斷哪些已觸發效果（Already Fired Effects）必須被視為已完成，避免重複下單或出貨。

4. **長篇內容生成與發布管線**  
   從研究摘要、人類審稿到最終發布文章的工作流，若在中斷後重新執行已完成的研究步驟，會浪費 token 並可能改變結果。使用 **RESUME 恢復合約** 作為一致性輪廓（Conformance Profile），可在 LangGraph、CrewAI、LlamaIndex Workflows 等框架間比較其持久層語意，選擇最符合「不重新執行已完成工作」需求的方案。

5. **跨主機分散式 agent 協作**  
   當多個程序同時嘗試恢復同一個 **暫停中斷（Parked Interrupt）** 時，論文顯示並發傳遞會讓閘控效果被觸發 k 次，且失效會跨主機擴散。適合採用 REMIT 參考排序器的 **讀取路徑消耗閘（read-path consumption gate）**，在共享儲存中先聲明消耗、拒絕後到者，再讓任何節點執行。

## 實作前置條件

### 資料準備
- 一份明確的 **持久化 API** 邊界清單：哪些方法會觸發外部效果、哪些只讀取狀態、哪些寫入檢查點。
- 可重現的測試劇本：至少包含「正常中斷恢復」、「節點中間崩潰」、「並發恢復請求」、「SIGKILL 後重啟」四種情境。
- 一個跨行程的 **效果分類帳（effect ledger）**：用於比對框架聲稱的持久狀態與實際發生的副作用。

### 運算資源
- 模型檢查：執行 TLA+ / TLC 需要可窮舉狀態空間的機器；論文參考規模為 740 萬個狀態，建議至少 16 GB RAM 與 SSD。
- 一致性探針執行：可在單機以確定性測試框架（Deterministic Harness）跑 pinned releases；跨主機測試則需至少兩台可同步屏障（barrier-synchronized）的環境。
- REMIT 驗證核心：需安裝 Rust 工具鏈與 Verus，用於 CI 閘門驗證 recovery-decision core。

### 技能需求
- 熟悉至少一種 agent workflow 框架（LangGraph / CrewAI / LlamaIndex Workflows / pydantic-graph / AutoGen AgentChat）。
- 具備基礎形式化規格閱讀能力，能理解 TLA+ 狀態轉換與不變量（invariants）。
- 若使用 REMIT，需要 Rust 與 PyO3 綁定經驗，以及 Verus 驗證流程的基本知識。

## 實作步驟建議

1. **繪製持久層邊界圖**  
   將你的工作流拆解為：檢查點寫入、中斷點、恢復命令、狀態查詢 API。對照 RESUME 恢復合約的六項性質，標記每個 API 呼叫屬於哪一項性質的責任範圍。

2. **選定一致性輪廓**  
   並非所有應用都需要全部六項性質。例如只讀分析流程可接受 **至少一次（At-Least-Once）** 重放；支付流程則必須堅持 **效果恰好一次** 與 **單次消耗**。根據業務風險選擇要滿足的性質組合。

3. **跑論文附贈的確定性探針**  
   使用 `reproduce.sh` 在固定版本釋出（Pinned Releases）上重新導出論文數據，確認你目標框架在當前版本的實際行為。特別關注探針 133（SIGKILL）與探針 160（不完整持久邊界授權重執已完成工作）。

4. **建立效果分類帳**  
   在現有框架外掛一個 durable、跨行程的效果分類帳，作為外部神諭（oracle）。每次節點觸發副作用時先寫入分類帳，再執行實際操作；恢復時以分類帳判斷該效果是否已觸發。

5. **導入 REMIT 的消耗閘**  
   若需要跨行程 **單次消耗**，在共享儲存（如 PostgreSQL、Redis、etcd）實作「先聲明消耗、再執行節點」的讀取路徑閘。REMIT 的設計是：第一個恢復請求獲得消耗權，其餘在同一介面被拒絕。

6. **用 TLA+ 驗證你的修復模型**  
   將你的持久層抽象為 TLA+ 轉換關係，啟用六個故障開關進行窮舉模型檢查。確保在單一故障配置下，每個性質都能通過；若發現反例，依深度 4–6 的 counterexample 修復狀態機。

7. **設定 CI 閘門**  
   將 Verus 驗證過的 recovery-decision core、TLA+ 模型檢查、以及確定性探針納入持續整合。任何框架版本升級都必須先通過這三道閘門，才能部署到生產環境。

## 潛在風險與注意事項

- **沉默的綱要無效狀態**  
  LangGraph 會在無警告的情況下持久記錄 **模式無效狀態（Schema-Invalid State）**。實作時應在寫入檢查點前加入 **檢查點有效性（Checkpoint Validity）** 閘，像 AutoGen AgentChat 一樣大聲拒絕，而非靜默接受。

- **並發恢復的飽和失效**  
  論文顯示在 40 格測試中有 36 格飽和度達 1.0，即 k 個行程恢復同一中斷時幾乎一定重複觸發閘控效果。不要依賴應用層去重；必須在持久層或共享儲存先完成消耗聲明。

- **框架文件與行為不一致**  
  CrewAI 文件聲稱不會重新執行已完成工作，但實測發現它會重跑帶有效果的方法。任何來自官方文件的聲稱都應以確定性探針重新驗證，不可直接採信。

- **跨崩潰與跨中斷語意不同**  
  LangGraph 在同一 API 上呈現「跨中斷恰好一次、跨崩潰至少一次」的混合行為。設計時要區分「人為中斷恢復」與「程序崩潰恢復」兩條路徑，分別設定合約義務。

- **過度追求全性質可能不必要**  
  並非每個工作流都需要 **分支決定性** 或 **復原決定性**。強加過強語意會增加延遲與儲存成本；應根據業務影響選擇最小必要輪廓。

- **REMIT 不是萬用套件**  
  論文明確指出未聲稱對編譯後二進位進行端到端精煉驗證。部署 REMIT 時，仍需對 PyO3 綁定層與 LangGraph shim 進行傳統測試，不能僅依賴 Verus 核心。

## 與其他技術的整合建議

- **與現有資料庫整合**  
  REMIT 的消耗閘可建構在 PostgreSQL、MySQL 或 Redis 之上，利用其原子 compare-and-set 或 Lua 腳本實現「聲明消耗」操作。論文已在 live PostgreSQL 上複製 LangGraph 的失效，因此建議以資料庫層級原子操作作為最終防線。

- **與事件串流（Kafka / Pulsar）整合**  
  將每次 **恢復命令** 視為事件，利用 partition key 將同一個 **執行（Run）** 的恢復請求路由到同一分區，降低並發恢復機率；但不可完全取代消耗閘，因為重平衡或重送仍可能導致重複。

- **與可觀測性堆疊整合**  
  將效果分類帳的寫入、檢查點有效性閘的拒絕、以及消耗閘的競爭結果輸出到 OpenTelemetry。當發生 **飽和度 1.0** 類型的失效時，可透過追蹤快速定位是哪個中斷被多個行程同時恢復。

- **與沙箱層（如 Crab）整合**  
  若需要更強的隔離，可將 Crab 的 OS 級沙箱檢查點放在下層，RESUME 合約放在持久層 API 層，DART 放在上層決策語意層。三者互補：Crab 保程序狀態、RESUME 保恢復語意、DART 保語義可回滾性。

- **與 LLM 推理服務整合**  
  在 LLM-free 的確定性測試框架中，所有 LLM 呼叫應以 mock 或固定 seed 取代。生產環境則應將非冪等效果（如寫入資料庫、發送訊息）與 LLM 推理分離，確保只有效果操作需要經過持久層合約檢驗。

## 給不同背景讀者的閱讀建議

**初學者**  
先聚焦「為什麼恢復很難」：想像你按了暫停鍵、電腦當機、重開後程式該從哪裡繼續。接著閱讀適用場景與潛在風險，理解「已觸發的效果」與「檢查點」這兩個核心概念，暫時跳過 TLA+ 與 Verus 細節。

**AI 工程師**  
重點看實作步驟建議與確定性測試框架。你應該親自跑 `reproduce.sh`，觀察你日常使用的框架（LangGraph / CrewAI / LlamaIndex）在 SIGKILL 與並發恢復下的真實行為，並把效果分類帳與消耗閘整合進現有 pipeline。

**研究人員**  
深入閱讀 RESUME 恢復合約的六項性質、39 格故障矩陣與分離模型。注意 **單次消耗** 對 **效果恰好一次** 的結構性依賴，以及其他五項性質的獨立性見證。可進一步探討合約的最小性與完備性，這正是論文未聲稱的開放問題。

**產品經理**  
把這篇論文當成一份風險評估工具：它告訴你市場上主要 agent workflow 框架在持久層語意上並不相容，且多數連自己文件說的都不滿足。與工程團隊一起選定一致性輪廓，並把「中斷後是否會重複扣款／重複發訊」列為上線前的強制檢查項目。
