## ⚡ TL;DR

工具增強的大型語言模型代理常過度呼叫工具，造成 API 費用與延遲浪費。

## 摘要翻譯

工具增強的大型語言模型代理（Tool-augmented LLM agents）傾向於無差別地呼叫工具，即使模型能夠直接回答。每次不必要的呼叫都會浪費 API 費用（API fees）和延遲（Latency），然而現有的基準測試（benchmark）中沒有系統性地研究何時實際需要進行工具呼叫。我們提出 When2Tool，一個包含 18 個環境（15 個單跳（Single-hop）、3 個多跳（Multi-hop））的基準測試，涵蓋三類工具必要性（Tool necessity）——計算規模（Computational scale）、知識邊界（Knowledge boundaries）和執行可靠性（Execution reliability）——每個類別都具有受控難度等級（Controlled difficulty levels），在需要工具的任務（Tool-necessary tasks）和不需要工具的任務（Tool-unnecessary tasks）之間形成明確的決策邊界（Decision boundary）。我們評估了兩類無需訓練的基線方法（Training-free baselines）：僅提示法（Prompt-only，透過改變提示以抑制不必要的呼叫）以及先推理後行動（Reason-then-Act，要求模型在行動前推理工具必要性）。兩者皆僅能提供有限的控制：僅提示法會同時抑制必要的呼叫和不必要的呼叫，而先推理後行動在困難任務上仍會產生不成比例的準確率損失（Accuracy loss）。為了解這些基線方法為何失敗，我們探測（Probe）模型的隱藏狀態（Hidden states），發現工具必要性可從生成前的表示（Pre-generation representation）中以線性方式解讀出來，在六個模型上 AUROC（接收者操作特徵曲線下面積）達到 0.89 至 0.96，大幅超越模型自身的語言化推理（Verbalized reasoning）。這揭示了模型其實已經知道何時需要工具，但在生成過程中未能運用此知識。基於此發現，我們提出 Probe&Prefill，該方法使用輕量級線性探針（Linear probe）讀取隱藏狀態信號（Hidden-state signal），並以引導句（Steering sentence）預填充（Prefill）模型的回應。在所有測試的模型中，Probe&Prefill 將工具呼叫減少 48%，僅造成 1.7% 的準確率損失；而在相近準確率下表現最佳的基線方法僅減少 6% 的工具呼叫，或達到類似的工具呼叫減少量，但準確率損失高出 5 倍。我們的程式碼可在 https://github.com/Trustworthy-ML-Lab/when2tool 取得。

### 核心貢獻（3～5點）
- **提出 When2Tool 基準測試**：涵蓋 18 個環境（15 個單跳、3 個多跳），橫跨計算規模、知識邊界、執行可靠性三類工具必要性，並透過受控難度等級建立清晰的決策邊界，系統性地填補「何時需要工具呼叫」此一研究缺口。
- **診斷現有基線方法的失敗原因**：透過實驗揭示僅提示法會「連帶抑制」必要呼叫、先推理後行動在困難任務上付出不成比例的準確率代價，說明單純改變提示或要求模型語言化推理皆無法有效控制工具呼叫行為。
- **揭示模型內部已具備工具必要性知識**：透過線性探針分析隱藏狀態，證實工具必要性可從生成前表示中以線性方式解讀出來，六個模型的 AUROC 介於 0.89 至 0.96，遠優於模型自身的語言化推理表現。
- **提出 Probe&Prefill 方法**：結合輕量級線性探針與引導句預填充機制，在所有測試模型上將工具呼叫減少 48%，僅造成 1.7% 的準確率損失，大幅優於現有基線方法（後者在相近準確率下僅能減少 6% 工具呼叫，或在相近工具呼叫減少量下準確率損失高出 5 倍）。

### 適合對象
- 研究大型語言模型代理（LLM Agents）、工具增強推理與代理範式（Agentic paradigm）的學術研究者。
- 從事模型可解釋性（Interpretability）、隱藏表示（Hidden representation）分析與線性探針（Linear probe）技術的研究人員。
- 關注推論成本（Inference cost）、成本效率（Cost efficiency）與真實世界代理部署（Real-world agent deployments）的業界實務工程師與產品負責人。
- 對基準測試設計、受控實驗方法論與工具呼叫效率（Tool-call efficiency）議題感興趣的 NLP 社群成員。

## 深度分析

#### 方法論解析

本論文提出了一套系統性的方法論來解決工具增強的大型語言模型代理（Tool-augmented LLM agents）過度呼叫工具的問題。其方法論可分為三個核心組成部分：基準測試設計、隱藏狀態探測分析、以及基於探測結果的干預機制。

**When2Tool 基準測試的設計理念**

When2Tool 的設計採用了「受控難度等級」（controlled difficulty levels）的實驗典範，這是行為科學中常用的方法論。基準測試涵蓋 18 個環境（15 個單跳（single-hop）與 3 個多跳（multi-hop）），並將工具必要性（tool necessity）劃分為三個正交類別：

1. **計算規模類別**（Computational scale）：測試模型是否能可靠執行特定規模的運算，例如 12+7 屬於簡單運算，而兆級乘法（trillion-scale multiplication）則超出模型可靠計算範圍。
2. **知識邊界類別**（Knowledge boundaries）：區分模型參數中已編碼的常識（如法國首都）與冷門知識（如某字串的 SHA1 雜湊值）。
3. **執行可靠性類別**（Execution reliability）：評估模型是否能可靠地心算追蹤（mentally tracing）多步驟程序，例如簡單的 `print(2+3)` 與深度遞迴（deep recursion）。

每個環境設置三個難度等級：簡單（easy）、中等（medium，決策邊界）、困難（hard）。這種設計的精妙之處在於，「中等」難度刻意製造了決策模糊性（decision ambiguity），迫使模型必須進行真正的工具必要性判斷，而非簡單地依賴啟發式規則。

**隱藏狀態探測方法論**

論文的第二個核心貢獻是採用了「表徵工程」（representation engineering）典範來分析模型內部狀態。具體而言：

- **探測位置選擇**：提取最後一個輸入詞元（last input token）的隱藏狀態（hidden states），這是生成前表示（pre-generation representation）的標準做法。
- **探測器架構**：使用簡單的線性分類器（linear classifier），而非複雜的非線性模型，這一選擇具有方法論意義——若線性探針（linear probe）即可達到高 AUROC，則證明資訊是以線性可解碼（linearly decodable）的方式編碼於表示空間中。
- **標籤定義**：以二元工具必要性標籤訓練探針，區分「需要工具」與「不需要工具」兩類。

關鍵發現是 AUROC 在六個模型上達到 0.89-0.96，這不僅超越了模型的語言化推理（verbalized reasoning）能力，更揭示了一個重要的認知科學類比：模型「知道」何時需要工具，但無法在生成過程中「表達」這項知識。

**Probe&Prefill 干預機制**

基於上述發現，作者提出了 Probe&Prefill 方法，其運作流程分為三步：

1. **隱藏狀態提取**：從模型的最後輸入詞元取得隱藏表示。
2. **線性探針預測**：使用預先訓練的線性探針預測工具必要性機率。
3. **預填充引導**（Prefill steering）：根據探針預測結果，在模型生成回應前預先填入引導句（steering sentence），例如「I can solve this directly without using a tool」或「I need to use a tool for this question」。

此方法的精妙之處在於其「輕量級」特性——無需額外的前向傳遞（forward pass），僅需一次線性預測，延遲開銷小於 1 毫秒。透過調整探針的決策閾值，可實現對準確率—效率權衡（accuracy-efficiency tradeoff）的平滑、細粒度控制。

#### 實驗數據解讀

**基準測試的量化結果**

When2Tool 包含 1,080 個訓練任務與 2,700 個測試任務，這樣的規模在工具呼叫決策研究中屬於中等偏上。18 個環境的設計確保了跨領域的泛化性評估，避免了單一領域的過擬合風險。

**探測實驗的關鍵數據**

AUROC 0.89-0.96 的結果極具說服力。在機器學習實務中，AUROC 超過 0.9 通常被視為「強分類器」的門檻，而 0.96 已接近「優秀」等級。更重要的是，這一結果在六個不同模型上的一致性，證明了工具必要性資訊的編碼是大型語言模型中的一種普遍現象，而非特定架構的偶然特性。

值得注意的是，論文中特別強調：「即使對於在 Reason-then-Act 機制下完全失敗的模型，探針仍能提取強信號」。這項發現具有深遠的理論意義——它表明表徵層級的知識（representation-level knowledge）獨立於模型透過文本表達該知識的能力存在，這與人類認知中的「無言知識」（implicit knowledge）現象高度相似。

**Probe&Prefill 的效能數據**

核心結果顯示：Probe&Prefill 將工具呼叫減少 48%，僅造成 1.7% 的準確率損失（accuracy loss）。作為對比，在相近準確率水準下，最佳基線方法僅能減少 6% 的工具呼叫；若要達到類似的工具呼叫減少幅度，則需承受 5 倍的準確率損失。

這個數據對比揭示了幾個關鍵洞察：

1. **效率提升的數量級差異**：48% vs. 6% 的工具呼叫減少，意味著在實際部署中可節省大量 API 費用（API fees）與延遲（latency）。
2. **準確率—效率權衡的非線性**：基線方法的權衡曲線陡峭，而 Probe&Prefill 的權衡曲線平緩，這表明後者提供了更優的帕累托前沿（Pareto frontier）。
3. **跨任務的可遷移性**：論文聲稱 Probe&Prefill 在任務間具有良好的遷移能力，這暗示探針學到的是通用的「工具必要性概念」，而非特定任務的捷徑。

**基線方法的失敗模式分析**

Prompt-only 方法的失敗在於「過度抑制」——當提示鼓勵減少工具呼叫時，模型不僅減少了不必要的呼叫，也減少了必要的呼叫，導致困難任務的準確率大幅下降。

Reason-then-Act 方法的失敗更為微妙：即使模型被要求先推理工具必要性，其推理結果仍不可靠。這表明語言化推理（verbalized reasoning）並非可靠的決策機制，與探測結果形成鮮明對比。

#### 與現有研究的比較

**與 Wu et al. [2025] 的比較**

Wu 等人透過聯合優化代理指令（agent instructions）與工具描述（tool descriptions）來減少冗餘呼叫（redundant calls）。然而，該方法聚焦於「改善已需要的呼叫」，而非「決定是否需要呼叫」。When2Tool 與 Probe&Prefill 明確區分了這兩個問題，並專注於後者。這種問題分解更具方法論上的清晰度，但也意味著兩種方法可互補使用。

**與 Xu et al. [2025] 的比較**

Xu 等人研究「何時完全跳過工具」，但其評估使用理想工具（oracle tools）——即呼叫即返回正確答案的工具。這種設定過於理想化，無法反映真實 API 的互動模式（interaction pattern），包括參數格式化（argument formatting）錯誤、回應解析（response parsing）失敗等問題。When2Tool 的設計更貼近真實世界代理部署（real-world agent deployments），要求模型以正確格式呼叫工具並解析回應。

此外，Xu 等人依賴監督式微調（SFT）來修改行為，但未深入理解模型過度呼叫（overcall）的根本原因。Probe&Prefill 的優勢在於其「訓練免費」（training-free）特性與對失敗機制的深入理解——透過探測分析揭示了「模型知道但無法表達」的核心問題。

**與思維鏈（Chain-of-thought）研究的關聯**

Reason-then-Act 基線與思維鏈 prompting 有相似之處，但本論文揭示了思維鏈在工具呼叫決策上的局限性。這與近期研究中對「語言化推理是否真正反映模型內部計算」的質疑相呼應。

**方法論的局限性**

1. **探測位置的單一性**：僅使用最後輸入詞元的隱藏狀態，未探索中間層或注意力頭的資訊。
2. **預填充的依賴性**：Probe&Prefill 依賴於模型對預填充文本的順從行為，這在某些經過對齊訓練的模型上可能失效。
3. **二元決策的簡化**：將工具必要性視為二元問題，但實際場景中可能存在「部分需要工具」的情境。

#### 可重現性評估

**程式碼與資料的可用性**

論文提供了 GitHub 程式碼倉庫連結（https://github.com/Trustworthy-ML-Lab/when2tool），這是可重現性研究的良好起點。然而，僅有程式碼連結並不足以保證完整可重現性，需進一步評估：

1. **資料集的釋出**：When2Tool 的 1,080 個訓練任務與 2,700 個測試任務是否隨程式碼一同釋出？任務的生成腳本是否公開？
2. **預訓練探針的釋出**：Probe&Prefill 所需的線性探針權重是否隨倉庫釋出？若需自行訓練，訓練流程是否完整記錄？
3. **評估模型的相容性**：六個測試模型的具體版本與檢查點是否明確標註？

**實驗細節的完整性**

從提供的文本中可見，論文描述了方法論的關鍵細節，包括隱藏狀態提取位置、線性探針架構、預填充文本範例等。但完整的超參數（如探針的正則化係數、學習率、訓練 epoch 數）需從附錄或程式碼中確認。

**可重現性的潛在障礙**

1. **模型版本依賴**：不同版本的同一模型可能產生不同的隱藏狀態，影響探針的可遷移性。
2. **硬體與浮點精度**：隱藏狀態的精確值可能受硬體與浮點精度影響，雖然線性探針對此應具有一定魯棒性。
3. **預填充機制的相容性**：某些模型的 API 可能不支援預填充功能，這會限制 Probe&Prefill 的實際部署。

**與開源工具增強框架的整合潛力**

若 Probe&Prefill 能整合至 LangChain、AutoGen 等主流代理框架，將大幅提升其實用價值。但目前論文中未提及此類整合計畫。

#### 未來研究方向

**1. 多模態與多工具擴展**

當前 When2Tool 主要聚焦於文字工具，未涵蓋多模態工具（如影像辨識、語音處理）。未來可擴展基準測試以包含視覺、音訊等多模態工具，並研究探針是否能跨模態泛化。

**2. 探測機制的理論深化**

線性可解碼性的發現開啟了多個理論問題：
- 工具必要性資訊是否集中在特定的注意力頭或神經元？
- 這種資訊是否在預訓練（pre-training）階段就已形成，還是在指令微調（instruction tuning）後出現？
- 是否存在「工具必要性向量」（tool-necessity vector），可透過類似的引導機制（steering mechanism）進行干預？

**3. 動態與情境化決策**

當前模型將工具決策視為靜態的二元問題，但實際場景中可能需要考慮：
- 使用者的偏好（如成本敏感 vs. 準確率敏感）
- 工具的可用性與回應時間
- 任務的緊急程度

未來可研究如何將這些情境因素編碼至探針中，實現更靈活的決策。

**4. 與強化學習的結合**

雖然 Probe&Prefill 是訓練免費的，但可探索將探測信號作為強化學習（reinforcement learning）的獎勵函數，進一步優化工具呼叫策略。這種結合可能產生比純 prompting 或純探測更優的結果。

**5. 幻覺（Hallucination）與工具呼叫的關聯**

模型過度呼叫工具的現象是否與幻覺傾向相關？過度依賴工具是否反映了模型對自身知識的不確定性？這些問題值得深入研究，可能揭示工具呼叫決策與模型校準（calibration）之間的內在聯繫。

**6. 跨語言與跨文化泛化**

When2Tool 目前以英文任務為主，未來可探索其在多語言環境下的表現。不同語言的知識邊界可能不同，這為探測器的跨語言泛化提供了有趣的測試平台。

**7. 安全與對齊考量**

預填充機制可能被惡意利用，例如透過精心設計的預填充文本繞過安全對齊。未來需研究如何確保 Probe&Prefill 的安全性，並探索其在紅隊測試（red-teaming）中的應用。

**8. 與人類決策的比較研究**

模型「知道但無法表達」的現象與人類的隱性知識（implicit knowledge）高度相似。未來可進行跨學科研究，比較人類與 LLM 在工具使用決策上的異同，這可能為認知科學與人工智慧的交叉研究提供新視角。

**9. 工具呼叫預算的動態管理**

論文提到「工具呼叫預算」（tool call budget）的概念，未來可研究如何在預算約束下動態調整探針閾值，實現長期成本優化。這與即時（online）學習演算法有自然的結合點。

**10. 從二元到連續的工具必要性**

現實中，工具的必要性可能是連續的（例如，模型有 70% 信心能直接回答）。未來可探索使用回歸探針而非分類探針，捕捉工具必要性的細粒度差異，並據此選擇不同強度的工具（如簡單計算 vs. 精確計算）。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？為何「工具呼叫決策」值得系統性地研究？**
A：這篇論文聚焦於一個被忽略但極為關鍵的問題：大型語言模型代理在面對任務時，是否真的知道「何時該呼叫工具、何時該自行回答」。現有的工具增強代理往往傾向於「過度呼叫」(overcall)，即使模型本身已具備直接回答的能力，仍會啟動網路搜尋或檢索增強生成管線，造成不必要的 API 費用與延遲浪費。論文的中心論點是：在部署規模下，每個代理在單一會話中可能做出數十次這樣的決策，浪費的成本會快速累積，因此「工具呼叫決策」本身即是一個值得獨立研究的系統性問題，而非僅是工具使用效率的附屬議題。

**Q2：為何現有的兩類無需訓練的基線方法（Prompt-only 與 Reason-then-Act）無法有效控制工具呼叫？**
A：Prompt-only 透過調整系統提示來抑制不必要的呼叫，但這種「全面抑制」會同時壓制真正必要的呼叫，導致困難任務的準確率大幅下滑，屬於粗粒度且缺乏選擇性的控制。Reason-then-Act 雖然要求模型先推理「是否需要工具」再行動，看似更精緻，但在困難任務上仍會付出不成比例的準確率代價，因為模型難以將內部判斷準確地「語言化」出來。換言之，這兩種方法都暴露了同一個根本缺陷：模型具備判斷工具必要性的內部知識，卻無法在生成過程中將其轉化為校準良好的決策。

**Q3：為什麼這個問題在真實世界的代理部署中特別重要？**
A：在真實世界的代理部署中，工具呼叫往往涉及付費的外部 API（例如搜尋、檢索、執行程式碼），每一次冗餘呼叫都會直接轉化為營運成本，且會累積可觀的延遲，影響使用者體驗。更嚴重的是，當代理在多步驟任務中反覆做出「過度呼叫」的決策時，錯誤會沿著決策鏈傳播，降低整體任務成功率。因此，學會精準判斷「何時不需要工具」不僅是成本議題，更是可靠性與可擴展性的核心挑戰，對於深度研究、軟體工程、搜尋與檢索等高頻代理應用尤其關鍵。

**Q4：Probe&Prefill 方法的核心機制是什麼？它如何運作於推論階段？**
A：Probe&Prefill 的核心機制分為三個步驟：首先從模型最後一個輸入詞元的隱藏狀態中萃取表示，接著以一個輕量級的線性探針（linear probe）對「工具必要性」進行二元分類預測，最後根據探針的預測結果，在模型開始生成之前預先填入一段引導句（steering sentence），例如「我可以直接回答，無需使用工具」或「我需要使用工具來回答這個問題」。這種設計巧妙地繞過了模型「語言化推理」失敗的瓶頸，直接從隱藏狀態中讀取已存在的判斷信號，再以預填充的方式引導模型後續的生成行為，整體額外開銷低於 1 毫秒。

**Q5：本論文最關鍵的發現或創新是什麼？它如何改變我們對模型內部機制的理解？**
A：本論文最關鍵的發現是：工具必要性其實是「線性可解碼」的——僅憑一個簡單的線性分類器，就能從模型的生成前隱藏表示中以 AUROC 0.89 至 0.96 的水準預測出來，且這個表現大幅超越模型自身的語言化推理。這意味著模型「已經知道」何時需要工具，卻在生成階段「未能將此知識付諸行動」，揭示了內部表示與外在行為之間存在一道鴻溝。這個發現挑戰了過去「模型過度呼叫是因為缺乏資訊」的假設，將問題重新定位為「表示與行為之間的解耦」，為未來研究開啟了全新的方向。

**Q6：When2Tool 基準測試在設計上有哪些關鍵選擇？為何採用三類工具必要性與三種難度等級？**
A：When2Tool 涵蓋 18 個環境（15 個單跳、3 個多跳），並刻意區分三類工具必要性：「能否計算」（運算規模）、「是否知道」（知識邊界）以及「能否可靠執行」（執行可靠性），以貼近真實代理部署中的主要決策情境。每個環境又設計了「簡單、中等、困難」三種受控難度等級，其中「中等」刻意落在模型的決策邊界上，使得「需要工具」與「不需要工具」之間存在清晰可分析的界線。這種設計讓研究者能夠系統性地拆解模型在不同情境下的決策行為，而非僅觀察整體的過度呼叫率。

**Q7：本論文使用了哪些基準測試與評估指標？為何選擇這些指標？**
A：本論文以 When2Tool 為主要評估基準，並輔以六款不同的語言模型進行跨模型驗證；評估指標涵蓋工具呼叫減少率、準確率損失，以及兩者之間的取捨曲線（trade-off curve）。之所以同時關注「減少多少呼叫」與「犧牲多少準確率」，是因為單獨優化任一指標都會誤導實務部署：若只追求減少呼叫而犧牲太多準確率，代理將在困難任務上失效；反之，若只追求準確率，則無法解決成本問題。這種雙指標設計呼應了真實部署中「成本—可靠性」的雙重約束。

**Q8：本論文最重要的實驗結果是什麼？Probe&Prefill 相較於基線方法的優勢為何？**
A：最重要的實驗結果是：Probe&Prefill 在所有受測模型上將工具呼叫減少了 48%，卻僅造成 1.7% 的準確率損失；相較之下，最佳的基線方法若要達到相近的準確率，只能減少 6% 的工具呼叫；若要達到類似的工具呼叫減少幅度，則需承受高達五倍的準確率損失。這顯示 Probe&Prefill 在「成本—準確率」取捨曲線上明顯優於所有 Prompt-only 與 Reason-then-Act 基線，並且能透過調整探針的決策閾值提供平滑且細粒度的控制。

**Q9：本論文是否進行了消融實驗或跨任務轉移性的驗證？**
A：是的，論文中明確指出 Probe&Prefill 在不同任務之間具有良好的轉移性（transfers well between tasks），這意味著在某個環境上訓練的線性探針可以應用於其他環境，無需為每個新任務重新訓練。此外，論文也透過調整探針決策閾值的實驗，展示了該方法能提供「平滑且細粒度」的取捨控制，這本質上就是一種消融式的閾值敏感度分析，證明了該方法的穩健性與可調性。

**Q10：哪些實際應用場景最能受益於這項研究成果？**
A：任何涉及大量工具呼叫的代理應用都能直接受益，特別是深度研究代理（需反覆決定是否啟動搜尋）、軟體工程代理（需判斷是否呼叫執行程式碼或測試工具）、企業級檢索增強生成系統（需決定是否查詢知識庫），以及多步驟任務規劃中的成本敏感型部署。在這些場景中，Probe&Prefill 可作為一個輕量級的「決策前濾網」，在不犧牲任務品質的前提下顯著降低 API 費用與回應延遲。

**Q11：從產品化的角度，這項研究帶來哪些設計與部署上的考量？**
A：從產品化角度，Probe&Prefill 的低開銷（<1 毫秒）與無需額外訓練的特性，使其易於整合進現有的代理框架，無需修改底層模型或重新微調。然而，部署時仍需考量：線性探針需要針對每款模型單獨訓練（因為隱藏表示隨模型而異），且探針的訓練資料需要涵蓋足夠多樣的「需要／不需要工具」範例，以確保泛化能力。此外，產品設計者還需根據業務場景調整決策閾值，在成本節省與任務可靠性之間找到符合商業目標的平衡點。

**Q12：這項研究對「代理系統」與「可解釋性」兩個研究領域的更廣泛影響是什麼？**
A：對代理系統領域而言，這項研究提供了一個全新的視角：與其透過監督式微調或更複雜的提示工程來「教」模型何時呼叫工具，不如直接讀取模型內部已存在的判斷信號，這開啟了「表示層干預」作為代理控制新典範的可能性。對可解釋性領域而言，這項研究展示了「線性探針」作為診斷工具的強大威力——即使是極簡的線性分類器，也能揭露模型內部豐富且可解碼的結構化知識，挑戰了「模型內部表示難以解讀」的傳統假設，並鼓勵後續研究探索更多「模型已知但未表達」的現象。

**Q13：本論文承認哪些限制？**
A：論文承認的一項主要限制是：線性探針需要針對每款模型單獨訓練，因為不同模型的隱藏表示空間並不相通，這增加了跨模型部署的成本。此外，雖然 When2Tool 涵蓋 18 個環境，但相較於真實世界中代理面臨的任務多樣性，仍屬於有限的子集；對於高度領域專屬或新興的工具類型，探針的泛化能力仍待驗證。最後，論文的評估主要聚焦於「二元」的工具必要性決策，對於「部分需要工具」（例如需要先檢索再計算）的更細粒度情境尚未深入探討。

**Q14：本方法可能存在哪些失敗案例？**
A：Probe&Prefill 的失敗案例可能發生在以下情境：當任務的「工具必要性」處於模糊地帶（例如中等難度的邊界案例）時，探針的預測可能不夠準確，導致錯誤地預填充引導句並誤導模型。此外，若輸入的提示格式與訓練探針時的格式差異過大（例如新增了少樣本範例或不同的系統提示），隱藏狀態的分佈可能偏移，使探針失效。另一個潛在風險是：對於需要「組合使用」多種工具的複雜多跳任務，僅靠二元預測可能無法捕捉到「先後順序」與「工具組合」的細節。

**Q15：本論文為未來研究開啟了哪些值得探索的方向？**
A：未來值得探索的方向包括：將「二元工具必要性」推廣到「多類型工具選擇」與「工具組合排序」等更細粒度的決策問題；研究如何讓線性探針在不同模型之間共享或遷移，以降低部署成本；探索其他「模型已知但未表達」的現象（例如幻覺偵測、信心度校準），並發展對應的表示層干預方法；以及將 Probe&Prefill 與強化學習或線上回饋結合，使探針能隨著代理的實際使用經驗持續自我更新。這些方向都可能進一步推動「表示層代理控制」成為一個獨立且富有成果的研究子領域。

## 實務應用指南

### 適用場景

**1. 企業級客服與知識庫問答系統**
在客服場景中，模型常被部署為「先檢索再回答」的工作流，但對於「你們的營業時間是幾點？」「退款政策為何？」等常見問題，模型本身已具備足夠知識。Probe&Prefill 可在內部判斷「不需要工具」時直接回答，省下向量資料庫查詢與 LLM 重新生成的費用。

**2. 程式碼助手（IDE 插件 / CLI 工具）**
開發者問「Python 中 list 與 tuple 的差別？」時，模型可直接回答；但問「執行這段遞迴函式並回傳結果」時則需要工具。Probe&Prefill 可避免模型對簡單語法問題過度呼叫程式碼執行環境，縮短回應延遲。

**3. 多代理編排系統中的路由器（Router）**
在 LangChain、AutoGen 等框架中，主代理常需決定「這個子任務該交給搜尋代理、計算代理，還是直接回答」。Probe&Prefill 的線性探針可作為輕量級路由器，<1ms 的額外開銷適合放在每次決策點。

**4. 成本敏感的 API 部署（高 QPS 場景）**
對於每月呼叫數億次 token 的 SaaS 服務，每個不必要的工具呼叫可能包含數百至數千 token 的往返成本。48% 的工具呼叫減少可直接轉化為顯著的毛利率改善。

**5. 邊緣裝置或本地模型部署**
當模型部署在資源受限環境（如 Apple Silicon、本地 LLM）時，減少工具呼叫意味著減少網路往返與外部 API 依賴，提升離線可用性與隱私性。

### 實作前置條件

**資料需求**
- 至少數千筆標註資料，每筆標記為「需要工具」或「不需要工具」。可從 When2Tool 基準（1,080 訓練任務）或自有的代理日誌中取得。
- 標註來源建議混合：人工標註 + 工具呼叫成功/失敗的後設資料（例如「呼叫工具後答案改變」可作為「需要工具」的弱標籤）。
- 需涵蓋目標部署場景的三類情境：計算規模、知識邊界、執行可靠性。

**運算資源**
- 訓練階段：單張消費級 GPU（如 A100 / RTX 4090）即可，因為只需提取隱藏狀態並訓練線性分類器。
- 推論階段：<1ms 額外開銷，可在 CPU 上執行線性探針。
- 必須能存取目標模型的隱藏狀態——這排除了純閉源 API（如 GPT-4o、Claude 透過官方 API），需使用開源模型（Llama、Qwen、Mistral 系列）或自架部署。

**技能前提**
- 熟悉 PyTorch / Transformers，能從模型中提取 `last_hidden_state[:, -1, :]`。
- 具備基本的線性分類器訓練經驗（scikit-learn `LogisticRegression` 即可）。
- 了解 LLM 的 prefill 機制（KV cache 預填），或使用支援 prefill 的推論框架（vLLM、SGLang、TGI）。
- 對自家代理系統的工具呼叫模式有 domain knowledge。

### 實作步驟建議

**步驟 1：建立標註資料集**
從 When2Tool 基準開始，篩選與你部署場景最相似的環境類別（例如客服場景偏重 Category B 知識邊界）。若資料量不足，可採主動學習：先用模型標註，再用人工覆核邊界案例。

**步驟 2：提取隱藏狀態**
使用 `model(**inputs, output_hidden_states=True)` 取得最後一層的最後一個 token 表示。建議快取所有樣本的隱藏狀態，避免重複前向傳播。

**步驟 3：訓練線性探針**
```python
from sklearn.linear_model import LogisticRegression
probe = LogisticRegression(max_iter=1000)
probe.fit(hidden_states_train, labels_train)
```
驗證 AUROC 是否達到 0.85 以上（論文報告 0.89–0.96）。若低於此值，考慮加入多層隱藏狀態的拼接，或使用簡單 MLP。

**步驟 4：實作 Prefill 機制**
在推論時，先執行一次前向傳播取得隱藏狀態，探針預測後選擇對應的引導句：
- 預測「不需要工具」→ 預填 `"I can solve this directly without using a tool."`
- 預測「需要工具」→ 預填 `"I need to use a tool for this question."`

使用 vLLM 的 `prompt_token_ids` 參數或 SGLang 的 prefix prefill 功能實作。

**步驟 5：校準決策閾值**
預設閾值 0.5 通常過於保守。透過在驗證集上掃描閾值，繪製「工具呼叫減少率 vs 準確率損失」曲線，根據業務目標（成本優先 vs 品質優先）選擇工作點。

**步驟 6：部署與監控**
上線後持續追蹤：(a) 探針預測信心分佈的漂移；(b) 預填後模型是否產生預期行為；(c) 整體工具呼叫率與任務完成率。建立自動回滾機制，當準確率下降超過閾值時切換回原始 prompt。

### 潛在風險與注意事項

**風險 1：隱藏狀態分布漂移**
若上游 prompt 模板、用戶語言、或任務類型隨時間變化，探針可能失效。**緩解**：每月用新資料重訓探針；監控探針輸出分布的 KL 散度。

**風險 2：探針的可遷移性有限**
論文顯示探針在同一模型家族內遷移良好，但跨模型（如 Llama → Qwen）需重訓。**緩解**：每個部署模型獨立訓練一份探針；避免將 Llama 的探針套用到微調後的衍生模型。

**風險 3：預填句被模型「覆寫」**
強對齊模型可能忽略預填內容，自行決定是否呼叫工具。**緩解**：選擇與模型對齊風格相符的引導句；A/B 測試不同預填措辭；對頑固模型改用 logit 偏置或 constrained decoding。

**風險 4：閉源 API 無法取得隱藏狀態**
OpenAI、Anthropic 等官方 API 不暴露 hidden states。**緩解**：改用開源模型部署；或退而求其次使用 Reason-then-Act 基線（但接受較差的 trade-off）。

**風險 5：多跳任務的決策點數量爆炸**
在多代理鏈中，每個子任務都需獨立判斷，錯誤會累積放大。**緩解**：在每個 hop 結束後加入信心檢查；若探針信心低，預設呼叫工具（保守策略）。

**風險 6：探針成為新的攻擊面**
若惡意用戶能構造觸發特定預填的輸入，可能繞過安全護欄。**緩解**：將探針預測視為軟信號而非硬決策；保留原有的內容審核層。

---

### 與其他技術的整合建議

**與 RAG 系統整合**
Probe&Prefill 可作為 RAG pipeline 的「閘門」：探針預測「不需要工具」時直接走 LLM-only 路徑，預測「需要工具」時才觸發 embedding + 向量搜尋 + 重排。建議在 LangChain 中以 custom callback 或 router chain 形式實作。

**與 Function Calling 框架整合**
在 OpenAI Function Calling、Anthropic Tool Use 等框架中，可在 `tools` 參數注入前先經過探針過濾——若探針判定不需要，動態將 `tools` 設為空陣列，迫使模型直接回答。

**與成本監控平台整合**
將探針預測結果與 LangSmith、Helicone、Portkey 等可觀測性工具串接，建立「預測信心 vs 實際工具效益」儀表板，持續校準閾值。

**與快取層整合**
對於探針預測「不需要工具」且問題屬於高頻 FAQ 的場景，可進一步在探針前加入語意快取（semantic cache），完全跳過 LLM 呼叫，達到雙重節流。

**與多模型路由整合**
在混合模型部署（如小模型處理簡單查詢、大模型處理複雜任務）中，Probe&Prefill 的探針輸出可同時作為模型選擇的依據——「不需要工具」路由到小模型，「需要工具」路由到大模型。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與圖 1，理解「模型會過度呼叫工具」這個問題的直覺——就像一個學生遇到簡單題目也堅持翻課本。When2Tool 基準的設計（特別是三個難度等級）展示了如何系統性地評估一個看似主觀的決策。建議從 Prompt-only 基線開始實驗，親眼看到「提示工程無法精準控制行為」這個關鍵發現。

**給 AI 工程師**：重點關注 Probe&Prefill 的實作細節，特別是 hidden state 提取與 prefill 機制的銜接。論文證明了「線性可解碼」這個強假設在多個模型上成立，這對生產環境意義重大——你不需要訓練複雜模型，一個 `LogisticRegression` 就能省下近半工具呼叫。建議先在內部代理日誌上重現實驗，再評估是否納入產品 roadmap。

**給研究者**：本文的核心 insight 是「模型內部知識與外部行為的不一致」——這是 mechanistic interpretability 文獻中「polysemantic neurons」與「superficial alignment」假說的延伸。隱藏狀態可解碼但生成失敗，暗示對齊微調可能只改變輸出層而非深層表示。未來方向包括：(1) 為何 Reason-then-Act 反而損害表現？(2) 探針信號在哪些層最清晰？(3) 是否存在更通用的「必要性探測器」適用於其他決策（如是否需要規劃、是否需要反思）？

**給產品經理**：這篇論文直接回應一個商業問題——「我們的 AI 代理每月燒太多 API 費用，怎麼辦？」Probe&Prefill 提供了一個具體的投資回報故事：48% 成本下降 vs 1.7% 品質損失。建議將此納入成本優化 roadmap，但需理解其前提（開源模型、可存取 hidden states），並評估對現有供應商綁定策略的影響。對閉源 API 依賴較重的團隊，可作為「為何我們應該考慮自架模型」的論據之一。
