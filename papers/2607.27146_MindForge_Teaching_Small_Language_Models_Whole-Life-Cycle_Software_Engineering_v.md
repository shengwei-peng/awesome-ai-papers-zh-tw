# MindForge：透過無原始碼程式合成教導小型語言模型掌握全生命週期軟體工程

## ⚡ TL;DR

從零開始建構完整程式困難重重，現有環境框架僅覆蓋單一開發階段，缺乏全生命週期訓練環境。
提出MindForge，將開源命令列程式轉為無原始碼環境，並以GLM-5.2生成全生命週期合成軌跡。
微調後的Qwen3.6-27B在ProgramBench達49.51%，並於七項未見基準全面進步。

## 摘要翻譯

編碼代理（Coding agents）在修改既有程式碼庫（repositories）的軟體工程（software engineering）任務上已取得重大進展，包括錯誤修復（bug fixing）與功能實作（feature implementation）。然而，從零開始建構完整程式仍然是一大挑戰：即使在 ProgramBench 上評估的前沿模型（frontier models），能完整解決的任務也不到 1%。其中一項障礙在於缺乏適用於此從零開始設定（from-scratch setting）、且涵蓋全生命週期軟體工程（whole-life-cycle software engineering）的可擴充訓練環境，因為現有的環境建構框架（environment-construction frameworks）僅專注於軟體開發中的單一階段。為填補此缺口，本文提出 MindForge，一個自動化流程，可將開源（open-source）命令列程式（command-line programs）轉換為無原始碼環境（source-free environments），僅提供編譯後的參考可執行檔（compiled reference executable）及其文件（documentation）。我們利用 MindForge，從與 ProgramBench 所用程式碼庫（repositories）不相交的（disjoint）程式碼庫建構訓練環境，並精選出一份高品質的資料配方（data recipe），其中包含使用 GLM-5.2 作為教師代理（teacher agent）所產生的程式合成軌跡（program synthesis trajectories）。在這些軌跡上微調（fine-tuning）Qwen3.6-27B，使其在 ProgramBench 的平均（average）測試通過率（test pass rate）從 37.98% 提升至 49.51%，達到與規模顯著更大的前沿模型（frontier models）相當的效能。此外，微調後模型（fine-tuned model）在全部七個未見過的基準測試（unseen benchmarks）上均一致優於基礎模型（base model），涵蓋長程程式碼庫生成（long-horizon repository generation）與翻譯（translation）、錯誤修復（bug fixing）、功能實作（feature implementation）及跨語言問題解決（cross-language issue resolution），絕對提升（absolute gains）分別為 RepoZero-C2Rust 31.00 百分點、DeepSWE 14.16 百分點、NL2Repo-Bench 10.70/4.56 百分點（有/無測試）、SWE-bench Verified 5.04 百分點、SWE-bench Pro 5.93 百分點、SWE-bench Multilingual 5.22 百分點，以及 FeatBench 4.94 百分點。

### 核心貢獻（3～5點）
- 提出 MindForge 自動化流程，將開源命令列程式轉換為僅暴露編譯後參考可執行檔與文件的無原始碼環境，建立涵蓋全生命週期軟體工程的從零開始訓練環境。
- 從與 ProgramBench 不相交的程式碼庫自動建構訓練環境，並使用 GLM-5.2 作為教師代理，精選高品質資料配方與程式合成軌跡。
- 在合成軌跡上微調 Qwen3.6-27B，使其於 ProgramBench 的平均測試通過率從 37.98% 提升至 49.51%，達到與規模顯著更大的前沿模型相當的效能。
- 微調後模型在七個未見過的軟體工程基準測試上均一致優於基礎模型，展現跨長程程式碼庫生成、翻譯、錯誤修復、功能實作與跨語言問題解決等任務的強泛化能力。

### 適合對象
適合從事 AI 軟體工程、編碼代理、程式合成、大型語言模型微調，以及自動化軟體工程基準測試研究的學者與工程師閱讀。

## 深度分析

#### 方法論解析

##### 1.1 問題設定與核心動機
MindForge 針對的是**從零開始設定（from-scratch setting）**下的**全生命週期軟體工程（whole-life-cycle software engineering）**。傳統**編碼代理（coding agents）**大多在既有**程式碼庫（repositories）**上進行**錯誤修復（bug fixing）**或**功能實作（feature implementation）**，代理可以觀察原始碼結構、依賴關係與測試案例，再進行局部修改。相對地，從零開始建構完整程式要求代理自行推導規格、設計架構、實作、測試、除錯並迭代精煉，這在 **ProgramBench（從零開始程式合成基準測試）** 上即使是**前沿模型（frontier models）**的完整解決率也低於 1%。因此，現有框架缺乏可規模化、涵蓋全生命週期的訓練環境，MindForge 即為填補此缺口而設計。

##### 1.2 無原始碼環境建構流程
MindForge 是一條自動化管線，可將**開源（open-source）****命令列程式（command-line programs）**轉換為**無原始碼環境（source-free environments）**。在這些環境中，代理只能看到**編譯後的參考可執行檔（compiled reference executable）**與其**文件（documentation）**，無法取得原始碼。這樣的設計有幾項意涵：
- **規格推導**：代理必須從文件描述與可執行檔的輸入輸出行為中，反推出完整規格。
- **避免直接抄襲原始碼**：由於訓練階段不暴露原始碼，可降低模型記憶參考實作的風險。
- **資料隔離**：用於建構訓練環境的**程式碼庫（repositories）**與 ProgramBench 使用的**程式碼庫**互為**不相交的（disjoint）**，減少資料污染疑慮。

根據摘要與引言，MindForge 共建構了 562 個涵蓋六種編譯式程式語言的無原始碼環境。

##### 1.3 教師代理軌跡收集與精煉
作者使用 **GLM-5.2** 作為**教師代理（teacher agent）**，在上述環境中收集 **1,001 條程式合成軌跡（program synthesis trajectories）**。這些軌跡記錄了從需求理解、設計、實作到測試除錯的完整過程。為確保**資料配方（data recipe）**品質，作者進行多層篩選與後處理：
- 只保留能產生「可建置提交（buildable submission）」的軌跡。
- 修復因暫時性基礎設施或鷹架（scaffold）失敗而提前終止的軌跡。
- 針對教師代理真實的**工具使用（tool-use）**錯誤，僅重寫受影響的推理部分，但保留工具呼叫與環境互動的一致性，避免破壞軌跡的連貫性。

分析顯示，這些軌跡涵蓋多個關鍵開發階段：**規格探索（specification exploration）**出現在 99.1% 的軌跡、**架構設計（architecture design）**87.1%、**錯誤定位（bug localization）**59.4%、**精煉（refinement）**64.0%。這表示資料並非單純的「寫程式」片段，而是具備多階段學習訊號的全生命週期軌跡。

##### 1.4 學生模型微調策略
作者以 **Qwen3.6-27B** 作為**基礎模型（base model）**與**學生模型（student model）**，透過**微調（fine-tuning）**讓其學習重現教師代理的端對端開發流程，而非僅模仿孤立的編輯動作。這本質上是一種行為複製（behavioral cloning），但目標是「全生命週期決策序列」，因此模型需要同時學會何時探索規格、何時設計模組、何時執行測試、何時根據錯誤訊息修正程式。

##### 1.5 推論與評估協定
評估以**測試通過率（test pass rate）**為主要指標，涵蓋 ProgramBench 全 200 題，以及七個訓練時未見過的**未見過的基準測試（unseen benchmarks）**，包括 **RepoZero-C2Rust**、**DeepSWE**、**NL2Repo-Bench**、**SWE-bench Verified**、**SWE-bench Pro**、**SWE-bench Multilingual** 與 **FeatBench**。

#### 實驗數據解讀

##### 2.1 ProgramBench 主結果
在 ProgramBench 上，Qwen3.6-27B **基礎模型（base model）**的平均測試通過率為 37.98%，經 MindForge 資料微調後的 **MindForge-27B** 提升至 49.51%，**絕對提升（absolute gain）**達 11.53 個百分點。這一成績：
- 超越 **DeepSeek V4 Pro** 的 47.80%；
- 接近 **GLM-5.1** 的 50.90% 與 **Opus 4.7** 的 51.38%；
- 在圖 1 的**模型參數規模（model parameter scale）**分佈中，27B 規模的 MindForge-27B 顯著優於同規模模型，並進入通常由 500B–1T+ 規模**前沿模型**佔據的效能區間。

##### 2.2 跨基準泛化表現
更令人矚目的是，微調後模型在七個未見過的軟體工程基準測試上全面進步，顯示其學到的並非僅是 ProgramBench 的特定題型，而是可遷移的開發流程：

| 基準測試（Benchmark） | 任務類型 | 絕對提升（Absolute Gain） |
|---|---|---|
| ProgramBench | 從零開始程式合成 | +11.53 pp（37.98→49.51%） |
| RepoZero-C2Rust | C 轉 Rust 翻譯 | +31.00 |
| DeepSWE | 長程軟體工程 | +14.16 |
| NL2Repo-Bench（with tests） | 自然語言轉程式碼庫 | +10.70 |
| NL2Repo-Bench（without tests） | 自然語言轉程式碼庫 | +4.56 |
| SWE-bench Verified | 錯誤修復 | +5.04 |
| SWE-bench Pro | 錯誤修復 | +5.93 |
| SWE-bench Multilingual | 跨語言問題解決 | +5.22 |
| FeatBench | 功能實作 | +4.94 |

這些結果特別值得注意的是：儘管訓練資料來自「無原始碼、從零開始」的環境，模型在需要修改既有程式碼庫的 SWE-bench 系列與 FeatBench 上仍有穩定提升，顯示全生命週期軌跡訓練有助於培養通用的規格理解、錯誤定位與程式修改能力。

##### 2.3 行為層面的質性證據
作者進一步分析軌跡與模型行為，發現 MindForge-27B 的動作分佈顯著更接近教師代理與強**前沿模型**；同時，即使軌跡長度明顯增加，其命令失敗率仍維持較低水準。這暗示微調不僅提升最終分數，也改善了代理的「過程品質」——更懂得規劃、更少無效嘗試、更能持續修正自身錯誤。

##### 2.4 規模效應與資料效率
從圖 1 可觀察到，模型效能通常隨**模型參數規模**單調上升，但 MindForge-27B 以 27B 參數達到接近 1T 規模模型的表現。這凸顯了「高品質、任務對齊的訓練資料」在提升小模型能力上的關鍵作用，也為資源受限場景提供了一條可行路徑。

#### 與現有研究的比較

##### 3.1 相較於程式碼修改典範
現有許多**環境建構框架（environment-construction frameworks）**如 SWE-Smith 與 SWE-Gym，主要針對既有、原始碼可見的程式碼庫，訓練代理進行單一階段任務（例如錯誤修復或功能實作）。MindForge 與之形成鮮明對比：
- **無原始碼 vs. 原始碼可見**：MindForge 僅提供編譯後可執行檔與文件，挑戰代理的規格推導與自主建構能力。
- **從零開始 vs. 修改既有程式碼**：代理無法依賴現有架構，必須自行設計與實作。
- **全生命週期 vs. 單一階段**：訓練資料涵蓋規格探索、設計、實作、測試、除錯與精煉，而非僅有最終修補動作。

##### 3.2 相較於 ProgramBench 的評估角色
ProgramBench 本身主要作為評估**前沿模型**的基準測試，並未提供大規模訓練環境。MindForge 的貢獻在於將 ProgramBench 所衡量的「從零開始程式合成」能力，轉化為可規模化產生訓練資料的流程，並證明小模型可透過此類資料顯著逼近大模型表現。

##### 3.3 限制與潛在偏誤
儘管成果顯著，仍有幾項限制值得注意：
- **領域限制**：目前僅針對**命令列程式**與編譯式語言，尚未涵蓋網頁應用、分散式系統、圖形介面或嵌入式系統。
- **教師代理天花板**：訓練資料由 GLM-5.2 產生，若教師在特定規格或語言上存在系統性錯誤，學生模型可能繼承這些偏誤。
- **軌跡精煉的人為選擇**：後處理步驟雖提升資料品質，但「保留哪些軌跡、如何重寫推理」涉及設計決策，可能引入不可見的篩選偏差。
- **評估指標單一**：測試通過率無法完整反映程式碼可讀性、可維護性、安全性與執行效率。
- **資料污染驗證**：作者宣稱訓練環境與 ProgramBench 不相交，但由於未公開完整程式碼庫清單，獨立驗證仍有困難。

#### 可重現性評估

##### 4.1 開源與公開狀態
根據目前提供的文本，作者並未明確說明是否公開 MindForge 管線原始碼、軌跡資料集或微調後的模型權重。因此，本研究的可重現性在現階段仍屬「未確定」。若作者未來能釋出以下資源，將大幅提升社群再現與延伸研究的可能性：
- MindForge **環境建構框架（environment-construction framework）**的原始碼；
- 562 個無原始碼環境的定義與對應文件；
- 1,001 條**程式合成軌跡（program synthesis trajectories）**；
- 微調腳本、超參數與訓練配置；
- MindForge-27B 模型檢查點。

##### 4.2 再現所需的技術門檻
即使資料公開，重現仍面臨若干挑戰：
- 需要穩定的 **GLM-5.2** 或同等級**教師代理（teacher agent）** API 存取；
- 六種編譯語言的工具鏈與容器化執行環境需仔細配置；
- 軌跡精煉步驟涉及對「暫時性失敗」與「真實工具錯誤」的判斷，若無詳細規則或人工標註，難以完全複製。

##### 4.3 對可重現性的建議
建議作者遵循資料卡片（Data Card）與模型卡片（Model Card）格式，提供環境清單、隨機種子、訓練硬體規格、推論預算與評估腳本，並提供預先建置的 Docker 映像檔，以降低再現門檻。

##### 5.3 多代理協作與人機協作
全生命週期軟體工程可自然分解為需求分析、架構設計、程式實作、測試與審查等子任務。未來可研究多個專精代理的協作機制，並引入人類開發者的回饋，形成人機協同的程式合成流程。

##### 5.4 評估方法革新

##### 5.5 教師多樣性與課程學習
使用單一教師模型可能限制學生見到的策略多樣性。未來可探索多教師蒸餾、依難度漸進的課程學習，以及主動學習挑選最具訓練價值的環境，進一步提升小模型的全生命週期軟體工程能力。

## 論文問答

**Q1：MindForge 主要想解決什麼問題？**
A：MindForge 旨在解決「從零開始完整建構程式」這項軟體工程任務的挑戰。現有前沿模型在 ProgramBench 上的完整解決率甚至低於 1%，顯示從無到有地生成可運行程式仍然非常困難。此外，現有的環境建構框架大多只聚焦於軟體開發的單一階段（例如錯誤修復或功能實作），缺乏能夠涵蓋全生命週期的可擴展訓練環境。MindForge 透過自動化流程填補這個缺口，讓模型能在不接觸原始碼的情況下學習完整的程式開發過程。

**Q2：為什麼現有的環境建構框架無法滿足從零開始程式合成的需求？**
A：現有框架如 SWE-Smith 與 SWE-Gym 主要針對修改既有程式碼庫的任務設計，它們假設代理可以存取完整且可見的原始碼。這些框架擅長訓練錯誤修復或功能實作能力，但無法提供「從無到有」建構程式的訓練訊號。相較之下，從零開始的設定要求代理根據文件與參考執行檔的行為推論規格、設計架構、實作、測試與除錯，這是單一階段框架難以涵蓋的。因此，需要新的無原始碼環境來支援全生命週期的程式合成訓練。

**Q3：從零開始的程式合成為何對軟體工程領域很重要？**
A：從零開始的程式合成能夠評估模型是否具備真正的全生命週期軟體工程能力，而不只是修改他人寫好的程式碼。這項任務要求模型進行規格探索、架構設計、程式實作、自我除錯與迭代優化，與真實開發者從頭建立專案的經驗更為接近。相較於現有的錯誤修復或功能實作基準，從零開始的設定更能反映模型在長程規劃與自主解決問題上的水準。因此，提升這方面的能力對於開發更通用、更自主的編碼代理具有關鍵意義。

**Q4：MindForge 的核心方法是什麼？**
A：MindForge 是一個自動化管線，能將開源命令列程式轉換為無原始碼的訓練環境，環境中只暴露編譯後的參考可執行檔與相關文件。接著，研究團隊在這些與 ProgramBench 不相交的程式碼庫上，使用 GLM-5.2 作為教師代理，收集完整的程式合成軌跡。這些軌跡會經過篩選與精煉，只保留能夠成功建置的提交版本，並修正教師代理因工具使用錯誤而產生的推理問題。最後，他們將這些高品質軌跡用來微調 Qwen3.6-27B，使其學會端到端的程式開發流程。

**Q5：MindForge 相較於先前研究的主要創新是什麼？**
A：MindForge 的主要創新在於結合了「無原始碼環境建構」與「可擴展的全生命週期軌跡收集」。不同於過去需要暴露原始碼的框架，MindForge 只提供編譯後的參考執行檔與文件，迫使模型從觀察行為與文件中推論規格。同時，它收集的軌跡涵蓋規格探索、架構設計、錯誤定位與程式精煉等多個開發階段，提供了豐富且多階段的學習訊號。這種設計讓小型語言模型能透過模仿教師代理的完整開發過程，顯著提升從零開始的程式合成能力。

**Q6：MindForge 在設計上有哪些關鍵選擇？**
A：首先，研究團隊選擇使用 GLM-5.2 作為教師代理來產生高品質的合成軌跡，並確保訓練用的程式碼庫與 ProgramBench 不相交，以避免資料污染。其次，他們只保留能夠成功建置的軌跡，並針對教師代理真正的工具使用錯誤重寫相關推理，同時保留原本合理的工具呼叫與環境互動。此外，他們會恢復因短暫基礎設施或腳手架失敗而提前終止的軌跡，以減少資料浪費。這些設計選擇共同確保了資料配方的高品質與訓練過程的穩定性。

**Q7：MindForge 在哪些基準測試上進行評估？**
A：主要評估基準是 ProgramBench，用於衡量從零開始的程式合成能力。除此之外，研究團隊還在七個未見過的軟體工程基準上測試模型的泛化能力，包括 RepoZero-C2Rust、DeepSWE、NL2Repo-Bench（有測試與無測試兩種設定）、SWE-bench Verified、SWE-bench Pro、SWE-bench Multilingual 以及 FeatBench。這些基準涵蓋了長程程式碼庫生成、程式語言轉換、錯誤修復、功能實作與跨語言問題解決等多種任務。透過這樣廣泛的評估，研究團隊能夠驗證模型是否學到了可遷移的全生命週期軟體工程能力。

**Q8：MindForge 的關鍵實驗結果是什麼？**
A：在 ProgramBench 上，經過 MindForge 微調的 Qwen3.6-27B 平均測試通過率從 37.98% 提升至 49.51%，不僅超越 DeepSeek V4 Pro 的 47.80%，也達到與更大規模前沿模型如 GLM-5.1 和 Opus 4.7 相近的水準。在泛化測試中，微調後的模型在所有七個未見過的基準上都有提升，例如在 RepoZero-C2Rust 上進步 31.00 個百分點，在 DeepSWE 上進步 14.16 個百分點，在 SWE-bench Verified 與 SWE-bench Pro 上分別進步 5.04 與 5.93 個百分點。這些結果顯示，MindForge 的訓練不僅提升了從零開始的合成能力，也強化了模型在傳統程式碼修改任務上的表現。

**Q9：軌跡分析揭示了哪些訓練成效的內部證據？**
A：研究團隊分析了 1,001 條全生命週期程式開發軌跡，發現這些軌跡涵蓋了規格探索（99.1%）、架構設計（87.1%）、錯誤定位（59.4%）與程式精煉（64.0%）等多個關鍵開發階段。這表示模型確實學習到了多階段的開發訊號，而非僅僅模仿單一動作。此外，微調後模型的行為分佈顯著更接近教師代理與強大的前沿模型，儘管軌跡長度更長，其指令失敗率卻更低。這些現象說明 MindForge 不只提升了測試分數，也改善了模型在長程互動中的穩定性與工具使用能力。

**Q10：MindForge 在實務上可以應用在哪些場景？**
A：MindForge 可應用於自動化生成命令列工具、根據自然語言規格從頭建立新程式碼庫，以及將程式從一種語言翻譯成另一種語言（如 C 轉 Rust）。它也能作為教育輔助系統，幫助學習者觀察完整的程式開發流程，從規格理解到測試除錯。對於企業而言，這項技術有助於快速原型開發、自動化重複性程式生成任務，以及降低從零開始建構小型專案的人力成本。這些應用場景都受益於模型在無原始碼環境中學到的自主開發能力。

**Q11：若要将 MindForge 落地為產品，需要考慮哪些因素？**
A：首先，必須建立穩定且安全的沙箱環境，讓模型能夠執行編譯與測試而不影響主機系統。其次，參考可執行檔的可用性與文件品質會直接影響合成成功率，因此需要良好的資料篩選機制。此外，使用開源程式碼庫時必須注意授權合規問題，避免產生法律風險。最後，由於全生命週期軌跡通常較長，推理成本與延遲也是產品化時必須仔細評估的面向。

**Q12：MindForge 對整個編碼代理研究領域可能帶來什麼影響？**
A：MindForge 證明了透過高品質的無原始碼合成軌跡，小型語言模型也能在從零開始的程式合成任務上逼近甚至匹敵大型前沿模型。這可能改變領域內過度依賴模型規模擴張的趨勢，轉而重視資料配方與訓練環境的設計。同時，它將研究焦點從單純的程式碼修改擴展到全生命週期軟體工程，推動編碼代理朝更自主、更完整的開發者角色邁進。長遠來看，這有助於降低先進編碼能力的取得門檻，並促進更多創新應用的出現。

**Q13：MindForge 有哪些已知的限制？**
A：目前 MindForge 主要針對命令列程式，對於圖形介面、網頁應用或分散式系統的適用性仍需進一步驗證。此外，環境建構依賴於能夠取得編譯後的參考可執行檔，若目標程式難以編譯或缺乏文件，則可能無法順利產生訓練環境。教師代理產生的軌跡雖經過篩選與精煉，但仍可能殘留錯誤或次優決策，影響學生模型的學習上限。最後，目前涵蓋的程式語言為六種編譯型語言，對於其他語言生態系統的泛化能力仍有待探索。

**Q14：MindForge 在哪些情況下可能會失敗？**
A：當目標程式的文件過於簡略或規格模糊時，模型可能難以從參考執行檔的行為中準確推論出正確實作。若教師代理在軌跡收集過程中遇到非短暫性的真正工具使用錯誤，後續精煉步驟可能無法完全修正，導致訓練資料品質下降。此外，對於需要極長程規劃或複雜領域知識的任務，即使是微調後的模型也可能無法穩定完成。這些失敗案例提示我們，未來仍需在環境設計與模型能力上持續改進。

**Q15：未來可以朝哪些方向延伸 MindForge？**
A：未來可以將 MindForge 擴展到更多程式語言與應用領域，例如網頁開發、行動應用、嵌入式系統與雲端服務。另一方面，可以結合更強大的教師模型或人類回饋，進一步提升軌跡品質與資料多樣性。也可以探索將無原始碼合成訓練與現有的程式碼修改訓練結合，讓模型同時具備從零建構與維護擴展既有專案的能力。此外，研究如何將這些能力壓縮到更小的模型，或結合測試時運算擴展，也是值得深入發展的方向。

## 實務應用指南

### 適用場景

1. **CLI 工具與開發輔助程式的自動化重製**  
   當團隊需要將現有開源命令列工具（如格式轉換器、靜態分析器、小型編譯器）移植到新語言、新平台，或在不暴露原始碼的前提下重建功能時，可使用 MindForge 產生無原始碼環境，讓模型僅依據可執行檔行為與文件完成從零開始的程式合成。

2. **教育與程式設計訓練教材生成**  
   程式教育平台可利用 MindForge 將真實開源專案轉換為「黑箱規格」練習題，學生必須閱讀文件、觀察參考執行檔輸入輸出、自行設計架構並實作，從而訓練全生命週期軟體工程能力，包括需求推導、架構設計、除錯與測試。

3. **企業內部遺留系統的現代化與重構**  
   針對僅剩編譯後執行檔、文件殘缺或原始碼授權不明的內部工具，MindForge 可協助建立合成訓練環境，讓小型語言模型學習重現其行為，作為重構、補完文件或產生替代實作的起点。

4. **長程程式碼庫生成與跨語言轉換的資料擴增**  
   研究團隊或開源社群可透過 MindForge 大規模產生 RepoZero-C2Rust、NL2Repo-Bench 等長程生成任務的訓練資料，填補從零開始建構完整程式時高品質軌跡不足的缺口。

5. **編碼代理的領域適應與能力強化**  
   對於已有程式碼修改能力（如 SWE-bench）的編碼代理，MindForge 可作為第二階段訓練來源，補強其「從無到有」的設計與實作能力，並提升在錯誤修復、功能實作、跨語言議題解決等下游任務的泛化表現。

### 實作前置條件

**資料前置條件**
- 一批可公開取得或企業內部授權允許使用的**命令列程式**，且能夠成功編譯為穩定的參考可執行檔。
- 每個程式需具備足夠的**文件**（README、man page、help 輸出、範例輸入輸出），以便模型推導規格。
- 訓練用的程式碼庫必須與目標評估基準（如 ProgramBench）**不相交**，避免資料污染。
- 需準備可執行的測試腳本或驗證機制，用於篩選成功建置的軌跡。

**運算前置條件**
- 收集軌跡階段需要呼叫強大的**教師代理**（如 GLM-5.2 等級的前沿模型），需具備足夠的 API 配額或本地推理資源。
- 微調階段需支援至少 27B 參數規模模型的訓練硬體（如多張高記憶體 GPU），並準備對應的框架（如 SFT/RL 訓練管線）。
- 執行環境需能隔離編譯、執行與測試過程，確保安全性與可重現性。

**技能前置條件**
- 熟悉容器化技術（Docker）與沙箱執行環境建置。
- 具備編譯工具鏈（C/C++、Rust、Go 等）與自動化測試經驗。
- 了解大型語言模型微調、資料清理與軌跡後處理流程。
- 具備基準測試設計與資料污染防護意識。

### 實作步驟建議

1. **環境建置：從開源程式產生無原始碼環境**  
   選定一組與目標評估集不相交的開源命令列程式，使用 MindForge 自動化流程移除原始碼，僅保留編譯後的參考可執行檔、文件與測試腳本，並建立可重複執行的沙箱環境。

2. **教師軌跡收集**  
   以強大的教師代理（如 GLM-5.2）在無原始碼環境中執行全生命週期程式合成，記錄其規格探索、架構設計、實作、測試、除錯與精煉的完整軌跡。

3. **軌跡品質篩選與修復**  
   僅保留能產生可建置、可執行提交的軌跡；針對因基礎設施或腳手架失敗而提前終止的軌跡進行復原；對於教師代理真正的工具使用錯誤，僅重寫受影響的推理部分，保持工具呼叫與環境互動的一致性。

4. **資料配方整理**  
   將篩選後的高品質軌跡組成資料配方，確保涵蓋規格探索、架構設計、錯誤定位與精煉等多個關鍵階段，並進行去識別化與格式標準化。

5. **學生模型微調**  
   以整理好的軌跡資料對目標學生模型（如 Qwen3.6-27B）進行監督式微調，讓模型學習重現教師代理的端到端開發流程，而非僅模仿孤立動作。

6. **多基準評估與迭代**  
   在 ProgramBench 及多個未見過的軟體工程基準（SWE-bench、FeatBench、RepoZero-C2Rust 等）上評估微調後模型，分析失敗案例，並回到步驟 2–4 補充特定階段的訓練資料。

7. **產品化部署**  
   將微調後模型整合至 IDE 外掛、CLI 編碼助理或 CI/CD 管線，並持續監控其在真實任務上的通過率、命令失敗率與軌跡長度等指標。

### 潛在風險與注意事項

- **資料污染風險**  
  若訓練用的開源程式碼庫與評估基準重疊，模型可能僅記憶答案而非學會泛化。務必確保訓練與測試程式碼庫嚴格不相交，並定期進行 contamination audit。

- **教師代理錯誤傳遞**  
  教師代理並非完美，其軌跡中可能包含未被即時發現的錯誤或次優設計。後處理時應區分「基礎設施失敗」與「真正工具使用錯誤」，避免將錯誤推理直接餵給學生模型。

- **編譯與執行環境的不穩定**  
  不同語言、依賴版本與作業系統差異可能導致軌跡提前終止。建議使用容器化沙箱並鎖定工具鏈版本，同時記錄環境狀態以便復現。

- **過度擬合特定語言或任務型態**  
  若訓練資料過度集中於某些程式語言或命令列工具類型，模型可能在其他領域表現不佳。應維持語言與應用領域的多樣性，並在多元基準上驗證。

- **安全與授權問題**  
  使用開源程式時需確認授權條款允許此類轉換與再訓練；在沙箱中執行未知編譯檔時，應採取網路隔離與資源限制，避免惡意程式影響訓練基礎設施。

- **評估指標的侷限性**  
  測試通過率雖是重要指標，但無法完全反映程式碼可維護性、效能與安全性。建議搭配人工審查、靜態分析與效能測試進行綜合評估。

### 與其他技術的整合建議

- **與現有編碼代理框架整合**  
  MindForge 產生的無原始碼環境與軌跡可補充 SWE-Smith、SWE-Gym 等以「修改既有程式碼」為主的訓練框架，形成「修改 + 從零建構」的兩階段訓練管線。

- **與檢索增強生成（RAG）結合**  
  在實際產品中，可將參考可執行檔的文件、範例輸入輸出與常見錯誤模式建立索引，讓微調後模型在推理時能即時檢索相關規格資訊，降低對記憶的依賴。

- **與持續整合／持續部署（CI/CD）整合**  
  將 MindForge 訓練出的模型部署為 CI 階段的程式合成助手，自動根據規格文件與可執行參考產生初始實作，再由現有測試管線驗證，形成人機協作的開發迴路。

- **與多智能體系統整合**  
  可將全生命週期軌跡中的不同階段（需求分析、架構設計、實作、測試）分配給不同專長的代理，MindForge 提供的軌跡則可作為多智能體協作範例與訓練資料。

- **與程式碼審查與靜態分析工具整合**  
  模型產生的程式碼應經過 linter、型別檢查、安全掃描等工具過濾，再納入最終提交，以彌補純測試通過率無法捕捉的品質問題。

### 給不同背景讀者的閱讀建議

**初學者**  
  建議先聚焦於「無原始碼程式合成」這個核心概念：想像你只有一個程式的使用說明書和執行檔，必須自己寫出功能相同的程式。本文的價值在於提出一套自動化流程，能大量產生這類練習題與解答範例，讓小型語言模型學會從零開始寫程式。閱讀時可略過微調技術細節，重點看圖 1 的成效與適用場景即可。

**AI 工程師**  
  本研究提供了一個可落地的資料生成與微調範式：從開源命令列程式建立無原始碼環境、以強大教師代理收集全生命週期軌跡、再透過品質篩選與後處理產生訓練資料。建議仔細研究軌跡修復與資料配方設計，並思考如何將此流程移植到你負責的模型與應用場景，同時特別注意資料污染與評估基準的隔離。

**研究人員**  
  本文的核心貢獻在於填補「從零開始程式合成」領域缺乏大規模訓練環境的缺口。建議關注 MindForge 的環境建構方法論、軌跡階段分佈分析，以及跨七個未見基準的泛化結果。未來可延伸的方向包括：擴展至更多程式語言與應用領域、結合強化學習進一步精煉軌跡、以及探討無原始碼環境對模型安全與版權的影響。

**產品經理**  
  這篇論文展示了一個能顯著提升小型模型軟體工程能力的訓練方案，使其逼近大型前沿模型表現，同時降低部署成本。建議評估是否能將 MindForge 應用於內部工具重構、CLI 助手或自動化程式生成產品，並與工程團隊討論資料授權、教師模型 API 成本、以及需要哪些基準測試來驗證產品價值。
