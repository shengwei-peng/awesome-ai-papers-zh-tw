#### 實驗數據解讀

**評估指標的選擇與侷限性**

論文採用 ROUGE 指標家族（ROUGE-1、ROUGE-2、ROUGE-L）作為主要評估標準。ROUGE (Recall-Oriented Understudy for Gisting Evaluation) 透過計算生成文本 (generated texts) 與參考文本 (reference texts) 之間的詞彙重疊率來衡量相似度：

- **ROUGE-1**：衡量單詞層級 (unigram) 的重疊率，反映基本詞彙覆蓋度。
- **ROUGE-2**：衡量雙詞詞組 (bigram) 層級的重疊率，反映局部語序保留能力。
- **ROUGE-L**：基於最長公共子序列 (Longest Common Subsequence, LCS)，反映結構相似度 (structural similarity)。

**ROUGE 指標在金融領域的適用性問題**

這是本論文最值得商榷的方法論選擇。ROUGE 指標源自文本摘要 (text summarization) 研究，其核心假設是「好的摘要應與參考摘要共享大量詞彙」。然而，金融資訊檢索任務有其特殊性：

1. **同義表達豐富**：金融概念可用多種方式表達（如「股價上漲」可寫為「收盤走高」、「買盤湧入」等），ROUGE 僅計算字面重疊，無法捕捉語意等價性。
2. **數據準確性優先**：金融回應中數字（如股價、漲跌幅、市值）的精確性至關重要，但 ROUGE 對數字錯誤不敏感。
3. **幻覺問題難以偵測**：ROUGE 無法識別生成內容中的事實性錯誤 (hallucination)，這恰恰是 RAG 試圖解決的核心問題。

更適合的評估指標應包括：BLEU、BERTScore（基於語意嵌入的相似度）、FactScore（事實準確性）、以及人工評估 (human evaluation) 對回應的「準確性」、「相關性」、「流暢度」進行李克特量表 (Likert scale) 評分。

**實驗結果的解讀**

論文聲稱在 100 條股票市場相關查詢上獲得「高 ROUGE 分數」，但未提供具體數值。從有限的全文內容中，我們僅能得知：

- 100 條查詢的測試集規模偏小，統計顯著性 (statistical significance) 不足，結果的泛化性存疑。

**延遲分析的缺失**

雖然報告了平均延遲，但未提供：
- 延遲的**分布特性**（如 P50、P95、P99）

### 實作步驟建議

**Step 1：定義問題與資料來源**
盤點目標使用情境，選定財經新聞來源（建議從單一可信來源如 VnExpress 開始，避免初期資料雜訊過多），並定義查詢類型（個股查詢、產業概況、事件影響分析等）。

**Step 2：建立文件管線（Document Pipeline）**
撰寫爬蟲定期抓取新聞 → 清洗 HTML、去除廣告與導覽列 → 切分為適當長度的 chunk → 標註 metadata（股票代碼、發布日期、產業分類）→ 存入結構化資料庫。

**Step 3：建立檢索模組（Retriever）**
選擇 embedding 模型（中文建議 BGE-m3、text-embedding-3-large 等）→ 將所有 chunk 編碼為向量 → 建立向量索引（FAISS 或雲端向量庫如 Pinecone）→ 實作 top-k 檢索（k 建議 3–10）。

**Step 4：整合生成模組（Generator）**
選擇 LLM（開源或 API）→ 設計 prompt template，指示模型「僅根據以下檢索結果回答，並標註來源」→ 串接 retriever 與 generator 形成完整 RAG pipeline。

**Step 5：建立評估框架**
準備 100 題測試集（含參考答案）→ 計算 ROUGE-1/2/L 分數 → 同時記錄延遲時間（latency）→ 設計人工評估指標（事實正確性、可讀性、來源準確性）。

**Step 6：迭代優化**
根據錯誤案例分析失敗模式（檢索錯誤 vs 生成錯誤）→ 調整 chunk size、retrieval k 值、prompt 設計 → 考慮加入 reranker（如 BGE-reranker）提升檢索品質。

**Step 7：部署與監控**
包裝為 API 服務（FastAPI、Flask）→ 加上快取層（Redis）降低重複查詢成本 → 監控 token 用量、回應時間、使用者滿意度 → 定期更新知識庫以反映最新市場動態。

### 潛在風險與注意事項

**風險 1：幻覺與事實錯誤**
即使有 RAG 機制，LLM 仍可能忽略檢索結果或自行編造數字。
**緩解**：在 prompt 中明確要求「若資訊不足請回答不知道」、強制要求引用來源編號、加入事實性檢查的後處理腳本。

**風險 2：知識庫時效性不足**
股票市場變化快速，舊新聞可能誤導使用者。
**緩解**：建立自動更新機制（每日/每小時增量更新）、在 metadata 中標註新聞日期、讓模型優先引用近期資料。

**風險 3：檢索品質不佳**
若 embedding 模型對金融術語理解不足，可能檢索到不相關文件。
**緩解**：使用領域微調的 embedding 模型、加入關鍵字混合檢索（BM25 + dense）、導入 reranker 二次排序。

**風險 4：法規與合規問題**
金融資訊涉及投資建議，可能觸發證券法規。
**緩解**：在輸出端加上免責聲明（「本資訊僅供參考，不構成投資建議」）、限制模型不得提供具體買賣建議、諮詢法務團隊。

**風險 5：API 成本失控**
若採用付費 LLM API，大量查詢可能造成成本飆升。
**緩解**：設定 token 用量上限、加入快取機制、評估改用開源模型的總體擁有成本（TCO）。

**風險 6：評估指標的侷限性**
ROUGE 僅衡量詞彙重疊，無法反映事實正確性。
**緩解**：搭配 LLM-as-judge 評估、人工抽樣審查、追蹤使用者回饋（thumbs up/down）。

### 與其他技術的整合建議

**1. 與即時行情 API 整合**
將 RAG 系統串接券商或交易所的即時報價 API（如 Twse、Yahoo Finance），讓使用者查詢「台積電今天表現」時，能同時回傳新聞摘要與即時股價，提供更完整的決策資訊。

**2. 與技術分析工具整合**
串接 TA-Lib、pandas-ta 等技術指標函式庫，在生成回應時自動計算 RSI、MACD、移動平均線等指標，結合新聞文字與數據圖表。

**3. 與情感分析模型整合**
在檢索階段加入情感分數（positive/negative/neutral），讓模型不僅回傳事實，也提供市場情緒解讀，例如「近期 5 篇新聞中有 4 篇偏負面」。

**4. 與企業 IM 整合**
透過 webhook 將 RAG 系統接入 Slack、Teams、LINE 等通訊軟體，讓團隊成員直接在對話視窗中查詢股票資訊，降低使用門檻。

**5. 與 BI 儀表板整合**
將 RAG 查詢紀錄與回應品質指標匯入 Tableau、Power BI，建立監控儀表板，追蹤熱門查詢、錯誤率、使用者滿意度等 KPI。

**6. 與 Agent 框架整合**
進階應用可將 RAG 系統包裝為 LangChain / AutoGen 的工具（tool），讓 AI Agent 能自主決定何時需要查詢股票資訊，執行更複雜的投資研究任務。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先專注理解第 1 節的問題動機（為什麼需要 RAG）與第 3 節的系統架構圖，不必急於深入技術細節。可以先嘗試使用現成的 RAG 工具（如 NotebookLM、Perplexity）體驗「檢索+生成」的效果，再回頭閱讀論文會更有感覺。重點掌握 ROUGE 指標的基本意義，理解「為什麼單純的詞彙重疊不足以評估事實正確性」。

**給 AI 工程師**：重點閱讀第 3 節的 methodology，特別是 retriever 與 generator 的整合方式、chunk 切分策略、embedding 模型選擇。論文提供的 1.16 秒延遲數據是重要的工程參考基準，建議在自己的實作中重現並比較。程式碼實作可參考 LangChain 或 LlamaIndex 的官方範例，並以此論文為基準設計 ablation study（移除 RAG、替換不同 embedding 模型等）。

**給研究者**：本論文的評估設計相對簡化（僅 100 題、僅用 ROUGE），建議從三個方向延伸：(1) 引入更嚴謹的評估指標（如 faithfulness、answer relevance），(2) 探討金融領域的 domain-specific embedding 微調，(3) 研究多語言或跨市場的 RAG 泛化能力。此外，論文中提到的 hallucination 與知識更新問題仍是開放議題，可深入探討如何量化 RAG 對幻覺率的實際改善幅度。

**給產品經理**：本論文展示了一個具體可落地的 AI 應用案例，1.16 秒的回應時間證明了即時性可行性。建議從使用者旅程角度思考：誰會用這個系統？使用頻率？付費意願？關鍵成功指標應包含「事實正確性」而非僅「回應速度」，因為金融場域對錯誤的容忍度極低。商業模式可考慮 B2B（券商、研究機構）或 B2C（訂閱制財經助理），並預留法規合規的設計彈性。
