## ⚡ TL;DR

消費級裝置VRAM與RAM有限，大型MoE權重溢出至SSD，現有系統將記憶體分層獨立快取而產生抖動。
TIDEWAY將主機RAM與GPU VRAM整合為統一記憶體池，搭配階段感知佈局與CUDA圖執行引擎。
實驗顯示TIDEWAY平均端到端加速1.97倍，TTFT提升2.40倍，解碼吞吐量提升1.61倍。

## 摘要翻譯

大型語言模型 (LLM) 代理正迅速成為 AI 應用中的主流範式。近期，在消費級個人電腦上本地部署大規模混合專家模型 (MoE) 的需求日益增長，以平衡資料隱私、API 成本與推論效率。然而，與配備充裕動態隨機存取記憶體 (DRAM) 的資料中心伺服器不同，消費級裝置在 GPU 顯示記憶體與主機記憶體方面均受到嚴格限制，迫使龐大的 MoE 權重必須在 GPU 顯示記憶體、主機記憶體與固態硬碟 (SSD) 之間進行權重溢出。在此權重溢出的情況下，我們觀察到現有系統未能充分利用此記憶體階層，而是將各層級視為獨立快取，導致推論時發生記憶體抖動。

我們提出 TIDEWAY，一個針對記憶體受限消費級裝置上大型 MoE 模型進行高效推論的系統。我們的核心洞見在於將主機記憶體與 GPU 顯示記憶體視為統一記憶體池加以管理。在此統一記憶體池中，TIDEWAY 將兩項設計緊密耦合：(1) 階段感知記憶體佈局，能適應預填充階段與解碼階段的不同存取模式；(2) 執行引擎，在專家分頁機制下最佳化 CUDA 圖執行。我們在具代表性的消費級硬體上以前沿規模 MoE 模型進行的評估顯示，TIDEWAY 顯著優於最先進的系統。平均而言，相較於最快的基線，TIDEWAY 在端到端延遲上達到 1.97 倍加速比，在首次詞元時間 (TTFT) 上達到 2.40 倍加速比，並使解碼吞吐量達到基線的 1.61 倍。

我們的原始碼已公開於 https://github.com/Afterglow231/Tideway 。

### 核心貢獻（3～5點）
- **問題洞察**：揭示現有 MoE 推論系統在消費級裝置上的關鍵缺陷——將 VRAM、主機記憶體、SSD 視為獨立快取，未能利用記憶體階層的整體性，導致嚴重的記憶體抖動。
- **統一記憶體池設計**：提出將主機記憶體與 GPU 顯示記憶體視為統一記憶體池的管理理念，從根本上改變記憶體資源的調度方式。
- **階段感知記憶體佈局**：設計能適應預填充 (Prefill) 與解碼 (Decode) 階段不同存取模式的記憶體佈局，使記憶體配置與推論階段特性緊密匹配。
- **專家分頁下的 CUDA 圖執行引擎**：建構在專家分頁 (Expert Paging) 機制下最佳化 CUDA 圖 (CUDA Graph) 執行的執行引擎，降低執行緒排程與記憶體存取的額外開銷。
- **顯著效能提升**：在代表性消費級硬體與前沿規模 MoE 模型上，平均達到端到端延遲 1.97 倍、TTFT 2.40 倍、解碼吞吐量 1.61 倍的加速比，全面超越現有最先進系統。

### 適合對象
- **LLM 推論系統研究者**：從事大型語言模型推論最佳化、記憶體管理、MoE 架構效率化等方向的學者與博士生。
- **邊緣 AI 部署工程師**：負責在消費級 GPU 或個人電腦上部署大型模型的實務工程師，特別關注記憶體受限環境下的可行性。
- **MoE 模型從業者**：使用 DeepSeek 等 MoE 模型進行本地化推論的開發者，需要了解權重溢出與分頁策略的最新進展。
- **系統架構師**：關注記憶體階層設計、統一記憶體池、CUDA 圖執行最佳化等系統層級議題的技術決策者。
- **AI 隱私與成本敏感應用開發者**：因資料隱私或 API 成本考量而傾向自架部署 (Self-hosting) 開放權重模型 (Open-weight Model) 的團隊。

Tideway 的核心方法論建立在三個相互耦合的設計支柱上：**統一記憶體池 (Unified Memory Pool)**、**階段感知記憶體佈局 (Phase-Aware Memory Layout)**，以及**保留 CUDA Graph 的執行引擎 (Execution Engine)**。這三者共同解決了消費級裝置 (Consumer Device) 上大型混合專家模型 (Mixture-of-Experts, MoE) 推論時的記憶體階層利用率低落問題。

**1. 統一記憶體池的設計哲學**

傳統系統如 FreeToken 將主機記憶體 (Host RAM) 視為 VRAM 後方的交換空間 (Swap Space)，並在 VRAM 中保留主機記憶體已有的專家 (Expert) 副本，形成冗餘儲存。Tideway 反其道而行，將 GPU VRAM 與主機記憶體視為單一邏輯池，並以 SSD 作為最終後備層。此設計帶來兩個關鍵優勢：

- **專家去重 (Expert Deduplication)**：同一個專家僅在池中保留一份實體副本，避免跨層級冗餘。這對於動輒數百 GB 的模型權重尤其關鍵，因為冗餘會直接擠壓可用容量。
- **雙向 PCIe 頻寬利用 (Bi-directional PCIe Bandwidth)**：當 VRAM 中的專家被驅逐時，系統並非直接丟棄，而是選擇性地將其回寫至主機記憶體，避免下次需要時再次從 SSD 重新載入。這相當於在 PCIe 通道上實作了隱式的「降級快取」(Demoted Cache) 機制。

**2. 階段感知記憶體佈局**

MoE 推論的兩個階段具有截然不同的存取模式 (Access Pattern)：

- **預填充階段 (Prefill Phase)**：長提示 (Prompt) 會啟用幾乎每個層 (Layer) 的所有專家，表現為「串流式全模型掃描」(Streaming Full-Model Scan)。此時最佳策略是按層順序預載入權重，最大化循序 I/O 效率。
- **解碼階段 (Decode Phase)**：每個詞元 (Token) 僅觸及少數專家，呈現「稀疏存取」(Sparse Access) 模式。此時應將高頻啟用的熱點專家駐留於 VRAM，冷門專家下沉至主機記憶體或 SSD。

Tideway 為兩個階段維護**獨立的記憶體佈局**，並在階段邊界 (Phase Boundary) 進行切換。這種設計避免了單一固定佈局在階段轉換時產生的跨層級抖動 (Cross-Tier Thrashing)，因為預填充結束後若仍維持「全模型掃描」佈局，解碼時的稀疏存取將導致大量無謂的權重傳輸 (Weight Transfer)。

**3. 保留 CUDA Graph 的執行引擎**

CUDA Graph 是 NVIDIA GPU 上降低核心啟動開銷 (Kernel Launch Overhead) 的關鍵技術，特別對於解碼階段的每詞元執行至關重要。然而，當專家分頁 (Expert Paging) 動態改變駐留位置時，現有系統往往被迫回退至逐核心啟動模式，導致每詞元開銷飆升。

Tideway 的執行引擎採用**動態擷取 (Dynamic Fetch) + 圖形保留 (Graph Preservation)** 的混合策略：對於可重用的解碼計算片段，盡可能維持 CUDA Graph 重新播放 (Replay)；對於超出 VRAM 的專家，則動態擷取並在圖形外部執行。這種設計限制了每詞元的主機端編排 (Host Orchestration) 與核心啟動開銷，使解碼吞吐量 (Decode Throughput) 不因分頁而崩潰。

**4. 系統協同性**

三個支柱並非獨立運作：統一池提供了容量基礎，階段感知佈局決定了池內的資料組織方式，而執行引擎則在佈局變動時維持 GPU 執行效率。這種「容量—組織—執行」的三層耦合，是 Tideway 區別於僅優化單一層級之先前工作的根本差異。

#### 實驗數據解讀

**1. 評估設定的代表性**

實驗在 NVIDIA RTX 5090（32 GB VRAM）上進行，主機記憶體預算涵蓋 16–128 GiB，這恰好對應圖一所揭示的消費級 PC 主流配置（64–84% 的 RTX 5090 持有者僅有 16–64 GiB RAM）。選用的三個模型——Qwen3.6-35B-A3B（67 GiB BF16）、Gemma4-26B-A4B（48 GiB BF16）、DeepSeek-V4-Flash（155 GiB FP4）——覆蓋了「勉強可放入主機記憶體」、「需部分溢出至 SSD」、「完全超出主機記憶體」三種典型情境，使評估具有高度的場景覆蓋面。

**2. 固定形狀配置 (Fixed-Shape Configurations) 的結果**

270 個固定形狀配置（輸入 4K–128K 詞元、輸出 128–2K 詞元）的結果顯示：

- **端到端延遲 (End-to-End Latency)**：平均加速比 1.97×，最高 3.18×。這意味著在最差情境下，Tideway 將推論時間縮短至約三分之一。
- **首次詞元時間 (Time-to-First-Token, TTFT)**：平均 2.40× 加速。TTFT 的顯著改善直接反映了預填充階段的串流式佈局優勢——全模型掃描時的循序 I/O 效率遠優於隨機存取。
- **每輸出詞元時間 (Time-Per-Output-Token, TPOT) / 解碼吞吐量**：平均 1.61× 改善。雖然加速比低於 TTFT，但這符合預期：解碼階段的瓶頸在於每詞元的固定開銷，而 CUDA Graph 保留機制正是針對此瓶頸。

**3. 程式碼代理追蹤 (TraceLab) 的結果**

在八個多輪程式碼代理 (Coding-Agent) 工作階段的追蹤驅動回放 (Trace-Driven Replay) 中，總請求處理時間最高降低 3.14×。此結果尤為重要，因為真實代理場景涉及長對話歷史與多輪上下文，每一輪的 TTFT 與 TPOT 累積效應被放大，凸顯了 Tideway 在真實工作負載下的實用價值。

**4. 數據解讀的注意事項**

- 加速比的「平均」與「最高」差距（1.97× vs 3.18×）暗示存在某些配置下基線系統表現特別差的場景，可能對應於主機記憶體嚴重不足、SSD 流量成為瓶頸的情境。讀者應關注這些極端案例的具體配置，以判斷 Tideway 在自身部署環境中的預期收益。
- 論文中未明確報告各模型、各 RAM 預算下的細粒度分解數據，因此無法直接判斷哪個模型或哪個 RAM 區間受益最大。建議查閱原始論文附錄以獲取更細緻的消融實驗 (Ablation Study) 數據。

#### 與現有研究的比較

**1. 與 FreeToken 的比較**

FreeToken 同樣關注 MoE 推論，但其設計假設完整的專家池 (Expert Pool) 駐留於主機記憶體，VRAM 僅作為副本快取。一旦模型權重超出主機記憶體，FreeToken 便無後備機制。Tideway 的統一池設計突破了此限制，並透過去重避免了 FreeToken 的冗餘儲存問題。此外，FreeToken 對預填充與解碼分別優化，但未明確處理兩者之間的佈局切換；Tideway 的階段感知機制則明確解決了階段轉換時的抖動問題。

**2. 與 llama.cpp 的比較**

llama.cpp 採用記憶體映射檔案 (Memory-Mapped File) 將分頁委派給作業系統，操作粒度為作業系統頁面 (通常 4 KB) 而非專家粒度。當工作集延伸至 SSD 時，作業系統的通用分頁策略無法感知 MoE 的專家存取模式，導致嚴重抖動。Tideway 在專家粒度上進行管理，能根據啟用模式做出語意感知的決策，這是 llama.cpp 架構上無法達成的。

**3. 與 FlashMoE 的比較**

FlashMoE 支援 SSD 支援的推論，並採用學習式替換策略 (Learned Replacement Policy)。然而，在全模型預填充掃描場景下，學習策略仍會產生抖動，因為預填充期間幾乎所有專家都被觸及，替換策略難以預測。Tideway 的階段感知佈局從根本上避免了此問題：預填充階段採用專門的串流佈局，不依賴替換策略的預測準確度。

**4. 與 SSD-LLaMA 的比較**

SSD-LLaMA 透過壓縮、非同步傳輸與跨層級快取減少專家載入開銷，但其佈局在兩個階段間保持固定。Tideway 的階段感知佈局在此基礎上更進一步，承認不同階段需要不同的記憶體組織，這是 SSD-LLaMA 未能利用的優化空間。

**5. Tideway 的侷限性**

- **硬體相依性**：實驗僅在 NVIDIA RTX 5090 上進行，未涵蓋 AMD GPU 或 Apple Silicon（統一記憶體架構）。在統一記憶體架構上，VRAM 與主機記憶體的邊界模糊，Tideway 的統一池概念可能需要重新詮釋。
- **模型範圍**：僅評估三個 MoE 模型，未涵蓋稠密模型 (Dense Model) 或極小規模 MoE。對於權重可完全放入 VRAM 的場景，Tideway 的階段感知機制可能帶來不必要的複雜度。
- **SSD 壽命與磨損**：論文中未深入討論 SSD 寫入量對消費級 SSD 壽命的影響。雙向 PCIe 利用意味著更多的 SSD 寫入操作，長期部署的成本與可靠性值得進一步評估。
- **冷啟動與預熱**：未明確報告系統冷啟動（首次載入模型）所需的時間與資源，這對於使用者體驗至關重要。

- 未提供能源效率 (Energy Efficiency) 數據，這對於消費級裝置的部署至關重要。
- 未報告長時間運行下的穩定性與記憶體洩漏情況。

**1. 統一記憶體架構的延伸**

隨著 Apple Silicon、AMD APU 等統一記憶體架構 (Unified Memory Architecture) 的普及，Tideway 的「統一池」概念需要重新定義。未來工作可探索：

- 在統一記憶體架構上，階段感知佈局是否仍帶來顯著效益，或是被硬體層級的統一性所吸收。
- 跨廠商統一記憶體抽象層的設計，使推論系統能透明地利用不同架構的記憶體特性。

**2. 預測式專家預載**

Tideway 目前對解碼階段的專存取取是被動反應式的。未來可結合：

- **專家啟用預測模型**：基於歷史啟用模式或提示內容，預測下一詞元可能啟用的專家，進行預先載入 (Prefetching)。
- **強化學習驅動的佈局策略**：將階段感知佈局擴展為自適應佈局，根據即時工作負載動態調整。

**3. SSD 壽命感知的管理**

消費級 SSD 的寫入壽命有限。雙向 PCIe 利用帶來的額外寫入可能加速 SSD 磨損。未來方向包括：

- 寫入放大 (Write Amplification) 最小化的專家回寫策略。
- 基於 SSD 健康狀態的動態降級機制，在 SSD 接近壽命終點時自動減少寫入。
- 探索新興儲存技術（如 MRAM、Computational Storage）作為 SSD 的替代層。

**4. 多使用者與多模型共存**

消費級裝置通常僅運行單一推論任務，但隨著本地 LLM 代理的普及，多模型共存 (Multi-Model Coexistence) 將成為常態。未來工作可探索：

- 在統一池中同時管理多個 MoE 模型的權重與啟用狀態。
- 模型間的權重共享機制（若架構相容）。
- 公平性與優先級排程，確保互動式代理的低延遲需求。

**5. 量化與壓縮的整合**

Tideway 目前假設權重以原始精度儲存。整合量化 (Quantization) 與稀疏化 (Sparsification) 可進一步擴展可部署的模型規模：

- 動態精度切換：熱點專家保持高精度，冷門專家降精度。
- 與 SSD-LLaMA 的壓縮技術結合，在統一池中實作分層精度管理。

**6. 形式化分析與理論保證**

目前 Tideway 的設計主要基於經驗觀察與實驗驗證。未來可發展：

- 階段感知佈局的最優性證明，在給定的存取模式與記憶體預算下，證明所選佈局使跨層級傳輸量最小化。
- CUDA Graph 保留率的理論上界，分析在動態分頁下可維持的圖形執行比例。

**7. 邊緣裝置的延伸**

將 Tideway 的設計理念延伸至更極端的資源受限環境（如行動裝置、嵌入式系統），需要：

- 更精細的功耗管理。
- 對 NPU 與異構加速器的支援。
- 在極小主機記憶體（< 8 GiB）下的可行性驗證。

## 論文問答

**Q1：為什麼在消費級裝置上部署前沿規模的 MoE 模型會成為一個日益重要的問題？**
A：隨著 LLM 代理逐漸成為 AI 應用的主流範式，無論是研究、電腦操作還是軟體工程，許多任務都需要長時間執行並處理敏感資料，使得雲端 API 的成本與隱私疑慮日益突出。開放權重的混合專家模型（MoE）僅啟用部分參數即可提供強大的推理與程式設計能力，讓自架部署在資料隱私、token 成本與領域特定適應上都極具吸引力。然而，前沿規模 MoE 模型的權重動輒數十至數百 GiB，遠超消費級 GPU 的 VRAM 容量，因此如何在記憶體受限的個人電腦上高效運行這些模型，便成為推動本地 AI 普及的關鍵挑戰。

**Q2：現有的 MoE 推理系統在記憶體受限的消費級裝置上為什麼會失敗？**
A：現有系統普遍將各記憶體層級視為彼此獨立的快取，缺乏對整體記憶體階層的統一管理。FreeToken 雖然分別最佳化預填充與解碼，但假設完整的專家池必須能放入主機記憶體中，且其 VRAM 快取只是 RAM 中專家的副本，一旦超出主機記憶體容量便無備援機制。llama.cpp 透過記憶體映射檔案將分頁交由作業系統處理，但作業系統以頁面而非專家為粒度運作，當工作集延伸至 SSD 時便會產生嚴重的記憶體抖動。FlashMoE 雖支援 SSD 推論，其學習式替換策略在完整模型預填充掃描下仍會失效；SSD-LLaMA 雖引入壓縮、非同步傳輸與跨層級快取，卻在兩個階段間維持單一固定的記憶體佈局，無法避免可避免的權重傳輸。

**Q3：為什麼記憶體階層的設計對於 MoE 推理效能至關重要？**
A：在 MoE 推論中，啟用的專家在執行階段才決定，因此跨層級的權重傳輸會落在每一次前向傳遞的關鍵路徑上，直接影響延遲。在預填充階段，長提示幾乎會啟用每一層的所有專家，整個模型必須串流進入 VRAM 才能產出第一個詞元，導致首次詞元時間（TTFT）大幅膨脹。在解碼階段，每一步僅觸及少數專家，但任何缺失的專家都會使解碼步驟停擺，延長每輸出詞元時間（TPOT）。在長序列生成與多輪對話中，這些停頓會累積成顯著的端到端延遲，因此專家在層級間的佈局不僅決定模型能否裝載，更直接決定其推論效能。

**Q4：Tideway 的核心設計理念是什麼？**
A：Tideway 的核心洞見在於不應將主機記憶體視為 VRAM 後方的交換空間，而是應將 GPU VRAM 與主機 RAM 整合為一個由 SSD 支援的統一記憶體池。為了最大化有效容量並減少專家未命中，Tideway 在 VRAM 與 RAM 層級之間對專家進行去重複化，並利用 PCIe 的雙向頻寬，選擇性地將從 VRAM 淘汰的專家送回主機 RAM，以避免後續從 SSD 重新載入。這個統一池的概念徹底改變了傳統將各層級視為獨立快取的思維，使消費級裝置有限的記憶體資源得以被更有效率地利用。

**Q5：階段感知記憶體佈局如何運作？**
A：Tideway 認識到預填充與解碼兩個階段具有截然不同的存取模式——前者是串流式、幾乎觸及所有專家，後者則是稀疏、僅觸及少數專家——因此為兩個階段分別維護獨立的記憶體佈局。系統會在階段邊界切換佈局，使每個階段都能維持對其存取模式最佳化的記憶體狀態。這種設計主動防止了階段轉換時的跨層級記憶體抖動，避免了 SSD-LLaMA 等系統因單一固定佈局而產生的可避免傳輸開銷。

**Q6：Tideway 如何在專家分頁下維持 CUDA Graph 的高效執行？**
A：Tideway 的執行引擎會在解碼運算中可重複使用的部分保留 CUDA Graph 的重播機制，即使專家駐留位置隨時間變動也能維持圖形化執行。當遇到不在 VRAM 中的專家時，引擎會動態地從主機 RAM 或 SSD 取得該專家，但會盡可能保留基於圖形的執行路徑。這項設計限制了每個詞元的主機端協調與核心啟動（kernel-launch）開銷，使解碼階段即使在頻繁的專家分頁下仍能維持高吞吐量。

**Q7：Tideway 在實驗中使用了哪些基準測試和模型？**
A：實驗在配備 32 GB VRAM 的 NVIDIA RTX 5090 上進行，主機 RAM 預算涵蓋 16 至 128 GiB 的範圍，以反映消費級裝置的實際配置。評測採用了三個開放權重的 MoE 模型：Qwen3.6-35B-A3B、Gemma4-26B-A4B 與 DeepSeek-V4-Flash，涵蓋 BF16 與 FP4 等不同精度。測試工作負載包含 270 種固定形狀配置（輸入長度 4K 至 128K 詞元、輸出長度 128 至 2K 詞元），以及來自 TraceLab 的八個多輪程式設計代理會話的追蹤驅動重播，以全面評估真實使用情境。

**Q8：Tideway 的關鍵效能結果是什麼？**
A：在所有固定形狀配置中，Tideway 相較最快的基線平均達到 1.97 倍的端到端加速比，最高可達 3.18 倍。在首次詞元時間（TTFT）方面，平均改善達 2.40 倍，反映出預填充階段的串流式載入效率顯著提升。在每輸出詞元時間（TPOT）方面，平均達到 1.61 倍的解碼吞吐量增益，顯示解碼階段的專家分頁與 CUDA Graph 整合有效降低了停頓。在 TraceLab 的程式設計代理會話重播中，Tideway 進一步將總請求處理時間縮短最多達 3.14 倍，證實其在真實多輪互動情境下的實用價值。

**Q9：消融研究或元件分析揭示了哪些設計選擇的重要性？**
A：雖然完整消融數據需參考論文實驗章節，但從設計動機可推論統一記憶體池是相較於獨立快取架構的關鍵差異，因為它消除了 VRAM 與 RAM 之間的冗餘儲存並充分利用 PCIe 雙向頻寬。階段感知佈局同樣不可或缺，因為單一固定佈局無法同時最佳化預填充的串流模式與解碼的稀疏模式，會在階段切換時引發跨層級抖動。此外，CUDA Graph 的保留對於解碼吞吐量至關重要，因為每詞元的主機端協調開銷若未被壓制，將抵消底層記憶體管理帶來的收益。

**Q10：Tideway 適用於哪些實際應用場景？**
A：Tideway 特別適合需要長時間執行的 LLM 代理任務，例如軟體工程中的多輪程式設計助理，這類應用會累積大量 token 成本並涉及敏感程式碼。在資料隱私要求嚴格的場景（如處理個人文件、企業內部資料或醫療資訊）下，本地部署可避免資料外傳至雲端 API。對於需要領域特定適應的應用，使用者可在本地微調與運行客製化模型，無需依賴外部服務。此外，對於預算有限的個人開發者與研究者，Tideway 讓他們能在不升級至數百 GiB RAM 的情況下體驗前沿規模 MoE 模型的能力。

**Q11：從產品化的角度，Tideway 的設計有哪些重要的考量？**
A：Tideway 的設計直接回應了消費級硬體的主流配置——16 至 64 GiB 的系統記憶體佔 RTX 5090 使用者的 64% 至 84%，這正是當前 DIY 與預組裝桌上型電腦的甜蜜點。系統無需使用者投資數百 GiB 的 RAM 即可運行前沿規模 MoE 模型，大幅降低了本地 AI 部署的硬體門檻。Tideway 以開源形式釋出（GitHub 公開），便於社群採用、審查與貢獻，也讓硬體廠商與框架開發者能將其整合至更廣泛的推論生態系。這種「在現有硬體上解鎖更大模型」的定位，對於推動邊緣 AI 與本地代理的普及具有重要意義。

**Q12：Tideway 對 MoE 推理領域和邊緣 AI 的影響是什麼？**
A：Tideway 透過統一記憶體池與階段感知管理的設計，示範了如何將受限的消費級硬體轉化為可行的 MoE 部署平台，挑戰了「前沿模型必須在資料中心運行」的既有假設。這項工作可能促使更多研究者與工程師投入本地 MoE 推理的最佳化，加速從雲端 API 向本地代理的典範轉移。對邊緣 AI 而言，Tideway 證明了即使在嚴格的記憶體預算下，仍可透過軟體系統設計達到接近雲端的互動體驗，為未來在更小裝置（如筆電、迷你 PC）上運行更大模型鋪平道路。

**Q13：Tideway 的已知限制是什麼？**
A：Tideway 的評測僅在 NVIDIA RTX 5090（32 GB VRAM）上進行，其 CUDA Graph 相關的最佳化深度依賴 NVIDIA 的執行模型，因此對 AMD GPU、Apple Silicon 或其他加速器的可移植性尚未驗證。實驗涵蓋的 MoE 模型規模與架構有限，雖然包含 BF16 與 FP4 精度，但對於更大規模（如數百 GiB 權重）或不同專家路由策略的模型，效能特性可能有所不同。此外，SSD 雖然作為第三層儲存提供了容量，但相較於 DRAM 仍有顯著的存取延遲，當工作集頻繁跨越 SSD 時仍會成為瓶頸。

**Q14：在哪些情況下 Tideway 可能會失敗或表現不佳？**
A：當主機 RAM 極度受限（例如低於 16 GiB）且模型權重遠超 VRAM + RAM 總和時，SSD 存取將佔據主導地位，此時即使有統一池管理，PCIe 與 SSD 頻寬仍會成為不可逾越的瓶頸。對於專家啟用模式極度不可預測或高度動態的工作負載，預取與快取策略可能難以跟上變化，導致頻繁的跨層級傳輸。在非 NVIDIA GPU 上，由於缺乏 CUDA Graph 等關鍵執行原語，Tideway 的解碼最佳化可能無法直接發揮效用，需要重新設計執行引擎。

**Q15：未來的研究方向有哪些？**
A：未來可朝多 GPU 支援方向延伸，使 Tideway 能利用多張消費級 GPU 共同承載單一模型，進一步降低單卡 VRAM 壓力。跨硬體平台的擴展（如 AMD ROCm、Apple Metal、國產加速器）將是推動普及的關鍵，需要重新設計執行引擎以對應不同廠商的圖形化執行機制。結合預測式專家預取（基於歷史路由模式或輕量預測模型）可進一步減少跨層級傳輸。此外，與量化、投機式解碼等推論加速技術的整合，以及對更大規模 MoE 模型（如數百 GiB 權重）的支援，都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **本機程式開發代理（Local Coding Agent）**：在配備 RTX 5090 等消費級 GPU 的個人工作站上，長時間執行 TraceLab 類型的多輪程式設計任務。Tideway 的階段感知切換可在長預填充（讀取整個程式碼庫）與稀疏解碼（僅啟用少數專家）之間維持高效能，特別適合需要反覆迭代的軟體工程場景。

2. **隱私敏感的企業內部助手**：金融、醫療、法律等產業需要在不將資料送出公司網路的前提下，使用前沿規模的 MoE 模型進行文件摘要、合約審閱或病例分析。Tideway 讓企業得以在現有 64 GiB RAM 的辦公電腦上部署 35B–155B 等級的模型，避免額外採購高容量伺服器。

3. **研究人員的個人 LLM 實驗環境**：學術研究者需要在單機上對 DeepSeek-V4-Flash、Qwen3.6-35B-A3B 等開放權重模型進行消融實驗或領域微調。Tideway 的統一記憶體池讓 32 GB VRAM + 64 GiB RAM 的組合即可容納並執行這些模型，無需依賴雲端算力。

4. **邊緣裝置的自主代理（Edge Autonomous Agent）**：在工廠產線、零售門市或遠端站點的工業 PC 上，部署可離線運作的 LLM 代理，用於設備故障診斷或客戶服務。Tideway 對 SSD 的友善設計使其能在無穩定網路的環境中持續運作。

5. **長上下文文件處理（Long-Context Document Processing）**：處理 4K–128K 詞元的法律卷宗、研究論文或程式碼庫時，Tideway 的預填充階段最佳化可顯著縮短首次詞元時間（TTFT），讓使用者更快看到初步結果。

### 實作前置條件

**硬體需求**
- **GPU**：具備至少 24 GB VRAM 的消費級 NVIDIA 顯示卡（論文以 RTX 5090 32 GB 為基準），需支援 CUDA 12 以上。
- **主機記憶體**：16–128 GiB DDR5/DDR4（論文實測涵蓋此範圍）。低於 16 GiB 將使 SSD 流量過於頻繁而不實用。
- **儲存裝置**：NVMe SSD（建議 PCIe 4.0 以上），容量至少為模型權重的 1.5 倍以容納溢出資料。
- **PCIe 通道**：建議 PCIe 4.0 x16 或以上，以充分發揮雙向頻寬優勢。

**軟體需求**
- CUDA Toolkit 12.x、cuDNN 9.x
- PyTorch 2.4 以上（支援 CUDA Graph 與專家平行化）
- Linux 作業系統（建議 Ubuntu 22.04 LTS）
- 模型權重檔案（BF16/FP4/FP8 等格式）

**技能門檻**
- 熟悉 MoE 架構與專家路由（routing）機制
- 具備 CUDA 程式設計與 CUDA Graph 經驗
- 理解記憶體階層（VRAM/RAM/SSD）與分頁機制
- 能閱讀並修改 C++/Python 系統程式碼

### 實作步驟建議

**階段一：環境準備與基準建立（1–2 週）**
1. 確認硬體配置符合需求，使用 `nvidia-smi`、`free -h`、`nvme smart-log` 等工具記錄初始狀態。
2. 安裝基準推理引擎（llama.cpp、vLLM 或 Hugging Face TGI）作為比較對象。
3. 下載目標模型權重（建議從 Qwen3.6-35B-A3B 或 Gemma4-26B-A4B 開始，規模較小）。
4. 使用固定輸入輸出長度（如 4K 輸入 + 512 輸出）建立基準延遲與吞吐量數據。

**階段二：部署 Tideway 並驗證（2–3 週）**
5. 從 GitHub 取得 Tideway 原始碼，閱讀 README 與設定說明。
6. 依硬體配置調整記憶體預算參數（VRAM/RAM/SSD 分配比例）。
7. 執行論文提供的測試工作負載，驗證 TTFT、TPOT 與端到端延遲是否達到預期加速比。
8. 使用 `nsys` 或 `ncu` 工具分析 CUDA Graph 執行情況，確認專家分頁未破壞圖重播。

**階段三：工作負載調校（2–4 週）**
9. 針對實際應用場景（如程式碼生成、長文件摘要）收集真實 trace。
10. 調整階段切換閾值（prefill 與 decode 的邊界判定），優化記憶體佈局切換時機。
11. 監控 SSD 寫入量，評估對裝置壽命的影響；必要時啟用寫入合併或更換為高耐久度 SSD。
12. 整合量化技術（INT4/FP8）以進一步降低記憶體壓力。

**階段四：生產化與監控（持續）**
13. 部署 API 服務層（FastAPI、Triton 或自建閘道）。
14. 建立監控儀表板，追蹤 TTFT、TPOT、SSD 流量、PCIe 頻寬利用率。
15. 設定自動降級機制：當 SSD 讀取延遲超過閾值時，自動切換至較小的模型或降低並行度。

### 潛在風險與注意事項

**SSD 壽命與效能衰減**
- **風險**：頻繁的專家分頁會產生大量 SSD 寫入，可能在數月內耗盡消費級 SSD 的寫入壽命（TBW）。
- **緩解**：優先使用企業級 SSD（如 Samsung PM9A3）；啟用 Tideway 的專家去重複化以減少寫入；監控 SMART 資訊並設定寫入量警報。

**PCIe 頻寬瓶頸**
- **風險**：當 VRAM 與 RAM 之間的雙向傳輸飽和時，推理效能將受限於 PCIe 頻寬而非 GPU 算力。
- **緩解**：使用 `nvidia-smi dmon` 監控 PCIe 流量；考慮升級至 PCIe 5.0 平台；調整批次大小以減少傳輸頻率。

**CUDA Graph 相容性問題**
- **風險**：當專家駐留位置變動時，CUDA Graph 可能無法重播，導致核心啟動開銷飆升。
- **緩解**：仔細審查 Tideway 的執行引擎設計，確保圖捕獲策略涵蓋所有可能的專家組合；對關鍵路徑進行 profiling。

**模型版本與架構依賴**
- **風險**：Tideway 針對特定 MoE 架構（如 Qwen3.6、Gemma4、DeepSeek-V4）設計，新模型可能需要重新調整專家佈局策略。
- **緩解**：在採用前先確認目標模型的專家數量、層數與啟用模式；保留原始碼修改能力以便客製化。

**冷啟動延遲**
- **風險**：首次載入模型時需從 SSD 讀取大量權重，可能造成數十秒的等待。
- **緩解**：實作預載入機制；使用 `mmap` 預先觸發 SSD 快取；在 UX 層加入載入進度提示。

**散熱與功耗**
- **風險**：長時間高負載推理會使消費級 GPU 觸及功耗與溫度上限，觸發降頻。
- **緩解**：確保機殼散熱充足；監控 GPU 溫度；必要時限制並行請求數。

### 與其他技術的整合建議

**與 llama.cpp 整合**
- llama.cpp 已是消費級裝置部署的主流引擎。建議將 Tideway 的統一記憶體池設計移植為 llama.cpp 的後端選項，或透過其 `mmap` 介面掛載 Tideway 的分頁管理器。
- 注意：llama.cpp 的 OS 級分頁在 SSD 層級會產生抖動，正是 Tideway 試圖解決的問題，整合時應保留 Tideway 的專家粒度控制。

**與 vLLM 整合**
- vLLM 的 PagedAttention 與連續批次（continuous batching）機制可與 Tideway 的階段感知佈局互補。建議在 vLLM 的 `Worker` 層加入 Tideway 的記憶體管理器，於 prefill/decode 切換時觸發佈局調整。
- 注意：vLLM 預設假設模型完整駐留 VRAM，整合時需修改其記憶體分配器。

**與 Hugging Face Transformers 整合**
- 可將 Tideway 包裝為 `device_map` 的自訂後端，允許使用者透過 `from_pretrained()` 直接載入模型並自動套用階段感知管理。
- 適合快速原型驗證，但生產環境建議改用更輕量的推理引擎。

**與量化工具鏈整合**
- 結合 AutoGPTQ、AWQ 或 BitsAndBytes 等量化工具，在載入前將權重轉為 INT4/FP8，可進一步降低記憶體壓力並減少 SSD 流量。
- 注意：量化會改變專家粒度，需重新評估 Tideway 的去重複化策略。

**與監控與可觀測性平台整合**
- 整合 Prometheus + Grafana 暴露 TTFT、TPOT、SSD 讀寫速率、PCIe 利用率等指標。
- 使用 OpenTelemetry 追蹤單一請求的專家載入路徑，便於除錯效能問題。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）與第 2.1 節（Memory on Consumer PCs），重點理解「為什麼消費級裝置跑不動前沿 MoE 模型」這個問題。圖 1 展示了 RAM 容量與模型權重規模的落差，是建立直覺的好起點。技術細節可先跳過，專注於使用案例與最終的加速比數字（1.97×、2.40×、1.61×），理解 Tideway 解決了什麼樣的痛點。

**給 AI 工程師**：建議從第 2 節的動機分析開始，特別是「現有系統為何失敗」的部分（FreeToken、llama.cpp、FlashMoE、SSD-LLaMA 的限制）。接著仔細閱讀第 3 節的系統設計，聚焦於統一記憶體池的資料結構、階段感知佈局的切換邏輯，以及 CUDA Graph 在專家分頁下的保留策略。建議同步閱讀原始碼（GitHub 連結已提供），對照實作理解論文描述。

**給研究者**：建議關注三個面向：(1) 階段感知（phase-aware）作為一個通用設計原則的應用潛力，是否可延伸至其他稀疏模型架構；(2) 統一記憶體池與傳統分層快取（hierarchical cache）的理論差異；(3) 評估方法的嚴謹度——270 個固定形狀配置加上 TraceLab 多輪代理 trace 的設計值得借鏡。第 4 節的消融實驗（若論文中存在）將有助於釐清各元件的貢獻度。

**給產品經理**：重點關注三組數字：1.97× 端到端加速、2.40× TTFT 改善、1.61× 解碼吞吐量提升，以及在 TraceLab 程式設計代理場景下最高 3.14× 的總處理時間縮短。這些數字直接對應到使用者體驗（更快看到回應、更流暢的互動）與營運成本（單機可服務更多使用者）。同時留意硬體需求（RTX 5090 + 16–128 GiB RAM），評估目標客群的裝置覆蓋率，並將 SSD 壽命列為長期營運的考量項目。
