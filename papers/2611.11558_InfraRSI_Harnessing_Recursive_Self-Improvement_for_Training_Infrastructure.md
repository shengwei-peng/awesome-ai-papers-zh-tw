InfraRSI 採用 `init → doctor → run → report → apply` 的線性流程，每個階段都有明確的職責邊界：

- **init 階段**：鎖定「可編輯範圍 (editable scope)」並定義「固定任務契約 (fixed task contract)」，契約涵蓋工作負載 (workload)、損失 (loss)、時間 (timing) 三類不變量。這是防止「獎勵破解 (reward hacking)」的第一道防線——若不固定契約，LLM 代理可能透過改變有效批次大小 (effective batch size)、延後優化器更新、或使用不穩定的低精度轉換來製造虛假加速。
- **doctor 階段**：對目標叢集進行「基準階段剖析 (baseline phase profiling)」並校準「叢集雜訊 (cluster noise)」，建立配對的步長時間 (step-time) 雜訊模型。這一步至關重要，因為分散式叢集的量測雜訊橫跨兩個數量級，固定接受閾值會在共享主機上推廣隨機抖動，或在安靜節點上丟棄有效的通訊重疊。
- **run 階段**：執行「預算組合式搜尋 (budgeted compositional search)」，這是整個系統的核心引擎。
- **report 與 apply 階段**：稽核來源路徑、追蹤失敗試驗成本、提交通過驗證的變更。

**2. 預算組合式搜尋 (Budgeted Compositional Search) 的三大機制**

run 階段的設計是 InfraRSI 最具技術深度的部分，由三個相互協作的子機制組成：

**(a) 多起點初始化與全域時間/記憶體模型 (Multi-Start Initialization and Global Time/Memory Models)**

與傳統「從單一現行最佳 (single incumbent) 貪婪前進 (stepping greedily)」的搜尋不同，InfraRSI 從「多樣化經驗種子配置 (diverse experience-seeded configurations)」出發，並在所有試驗 (trials) 上擬合兩個全域模型：
- **Cholesky 執行時間模型**：捕捉啟動參數之間的非線性互動（例如 FP8 量化與張量並行 (tensor parallelism) 度的聯合效應）。
- **右審查式 Tobit 峰值記憶體模型 (right-censored Tobit peak-memory model)**：這是處理 OOM 資料的關鍵設計。由於 OOM 試驗沒有觀測到的記憶體值，標準回歸會產生存活偏誤 (survivorship bias)；Tobit 模型透過最大概似估計處理這種「審查 (censored)」資料，讓模型能正確預測哪些配置會 OOM。

**(b) 先驗校準、失敗歸因與套件完成 (Prior Calibration, Failure Attribution, and Bundle Completion)**

LLM 的零樣本先驗 (zero-shot priors) 與實際硬體執行往往相關性不佳。InfraRSI 透過「即時探測 (live probes)」來校準這些先驗，並對失敗試驗進行歸因分析。特別值得注意的是「套件完成 (bundle completion)」機制：當一個高吞吐的配置因記憶體過剩而 OOM 時，系統會自動配對「節省記憶體的最佳化 (memory savers)」與「已驗證的程式碼修補 (verified code patches)」，形成可執行的套件。這解決了單一參數調整常見的「邊界卡住 (boundary stalling)」問題。

**(c) 高槓桿參數逃逸與程式碼修補堆疊 (High-Impact Knob Escape and Code Patch Stacking)**

此機制允許搜尋在「高槓桿啟動設定 (high-leverage launch settings)」周圍擴展，同時將已驗證的程式碼修補「堆疊 (stacking)」到穩定配置上。這種「配置 + 程式碼」的聯合最佳化是必要的，因為硬體敏感機制（如 FP8 量化、torch.compile 圖編譯、FlashAttention、張量/專家並行 (expert parallelism)）會「非線性地 (non-linearly)」互動，且其效能影響會「跨 GPU 架構反轉 (reverse their performance impact across GPU architectures)」。

**3. 兩層遞迴自我改進迴圈 (Two-Level RSI Loop)**

InfraRSI 的 RSI 設計具有雙層結構：
- **內層（線上）**：在單一調校執行 (tuning run) 內，根據即時試驗結果「線上修訂先驗 (revising priors online)」。
- **外層（跨叢集）**：將已驗證的執行時證據 (verified runtime evidence) 蒸餾 (distilling) 到「跨硬體經驗庫 (cross-hardware experience bank)」，供未來搜尋重用。

這種設計呼應了「計算最佳縮放法則 (compute-optimal scaling laws)」的精神——基礎模型 (foundation model) 的進展越來越依賴訓練基礎設施的吞吐量，因此 RSI 不僅是工具改良，更是「基礎模型縮放 (foundation model scaling)」的推動力。

**4. 16 項不變量的驗證契約**

InfraRSI 定義了 16 項工作負載、數值與時間不變量（Table 2），用於過濾無效或獎勵破解的執行。這比單純的「損失值匹配」更為嚴格，能捕捉到「數值漂移 (numerical drift)」、「時間捷徑 (timing shortcuts)」等隱性違規。

#### 實驗數據解讀

**1. 工作負載覆蓋面**

實驗涵蓋四個 LLM 訓練工作負載，橫跨稠密 (dense) 與 MoE 兩種架構、單節點與多節點兩種部署：

| 工作負載 | 硬體 | 架構類型 |
|---------|------|---------|
| Qwen3.5-9B | 8×H100 | 稠密、單節點 |
| Gemma-4-26B-A4B MoE | 8×H200 | MoE、單節點 |
| Qwen3.8-27B | 8×H200 | 稠密、單節點 |
| Qwen3.5-35B-A3B MoE | 16×H100 | MoE、雙節點 |

這個設計刻意覆蓋了「架構 × 硬體 × 部署拓樸」的三維空間，目的是驗證方法的泛化性而非針對特定配置過擬合。

**2. 主要效能指標**

- **幾何平均加速比 (geometric-mean speedup)**：**1.83×**
- **平均 MFU 提升**：從 **17.4% → 30.0%**（絕對提升 12.6 個百分點，相對提升約 72%）
- **峰值加速比**：在 **Gemma-4-26B-A4B MoE** 上達到 **2.75×**

MFU 從 17.4% 提升到 30.0% 是非常顯著的——在大規模 LLM 訓練中，MFU 每提升一個百分點都意味著數百萬美元的運算成本節省。30% 的 MFU 已接近業界頂尖水平（Meta 的 Llama 3 訓練報告約為 40-45%，但其使用了更成熟的基礎設施）。

**3. 與基線的比較**

| 方法 | 加速比 | MFU |
|------|--------|-----|
| **InfraRSI** | **1.83×** | **30.0%** |
| RE-Bench | 1.37× | 25.1% |
| Auto-Research | 1.34× | 24.5% |
| OptiCo（僅參數調整） | 1.23× | 21.3% |

InfraRSI 相對於最強基線 RE-Bench 仍有 **1.34× 的相對加速**（1.83/1.37），相對於僅調參的 OptiCo 則達到 **1.49×**。這顯示「配置 + 程式碼」的聯合最佳化相對於純參數調整有實質優勢。

**4. 跨硬體經驗轉移 (Cross-Hardware Experience Transfer)**

Table 5 展示了從 H100 轉移到 H200（或反之）的效果：使用跨 SKU 經驗初始化比冷啟動搜尋能「加速收斂並提升最終吞吐量」。這驗證了「硬體條件化效能證據 (hardware-conditioned performance evidence)」的可遷移性——儘管具體最佳配置不同，但「哪些參數類別有高槓桿效應」這類元知識可以跨架構共享。

**5. 驗證器的可靠性**

Table 6 的離線審計確認 16 項不變量驗證器能在不同數值容忍度 regime 下可靠過濾無效執行。這對「獎勵破解防禦」至關重要——若驗證器過於寬鬆，LLM 代理會學會規避；若過於嚴格，會丟棄有效但有微小數值差異的最佳化。

**6. 結果的深層意涵**

加速比的來源可分解為三部分：
- **參數調校貢獻**（對應 OptiCo 的 1.23×）：純粹調整啟動旋鈕。
- **程式碼修補貢獻**（從 1.23× 到 RE-Bench 的 1.37×）：加入自動程式碼生成。
- **結構化搜尋 + 經驗轉移貢獻**（從 1.37× 到 InfraRSI 的 1.83×）：全域模型、失敗歸因、套件完成、跨硬體經驗。

這顯示 InfraRSI 的增量價值不僅來自「能做更多事」，更來自「做得更聰明」——透過結構化搜尋避免在無效區域浪費預算。

#### 與現有研究的比較

**1. 與 RSI 相關研究的定位**

InfraRSI 與近期 RSI 系統的關係可從 Table 1 理解：

| 系統 | 目標 | InfraRSI 的差異化 |
|------|------|------------------|
| 數學構造發現 [33, 25] | 孤立演算法 | 處理高度耦合的系統配置 |
| ML 管線合成 [14] | 機器學習流程 | 聚焦訓練基礎設施而非模型設計 |
| 代理框架改寫 [45] | 代理腳手架 | 處理硬體約束與分散式通訊 |
| 單一核心生成 [26, 16] | 單一運算子 | 聯合優化配置 + 多核心互動 |

InfraRSI 的獨特貢獻在於：**RSI 在「耦合系統」上的可行性證明**。傳統 RSI 假設目標函數可獨立評估，但分散式訓練的吞吐量是配置、程式碼、硬體、通訊排程 (collective communication schedules) 的非線性函數，無法獨立分解。

**2. 與自動程式碼代理的比較**

論文明確指出「開放式程式碼編輯 (open-ended code edits)」會引入四種失敗模式：獎勵破解、數值漂移、時間捷徑、量測抖動。InfraRSI 透過「固定任務契約 + 16 項不變量 + 來源路徑稽核」來緩解這些問題，這比直接套用通用程式碼代理（如 SWE-agent 類系統）更為嚴謹。

**3. 與自動調參系統的比較**

OptiCo 等僅調參系統無法處理「需要修改程式碼才能啟用的最佳化」（例如啟用新的融合運算子、調整通訊緩衝區大小）。InfraRSI 的「程式碼修補堆疊」機制填補了這個缺口。

**4. 與 RE-Bench / Auto-Research 的比較**

這些基線代表了「通用研究自動化」的嘗試，但它們缺乏：
- **硬體感知 (hardware awareness)**：未對叢集雜訊進行校準。
- **記憶體預算定價 (memory budget pricing)**：無法處理 OOM 邊界。
- **跨硬體經驗累積**：每次搜尋都是孤立的。

InfraRSI 在這三個維度上的結構化設計是其效能優勢的來源。

**5. 局限性與未解決問題**

- **預算假設**：論文的「預算組合式搜尋」假設有足夠的試驗預算。在實際生產環境中，每次訓練執行成本高昂，預算可能不足以支撐完整搜尋。
- **程式碼修補的可組合性**：堆疊多個修補時可能產生非預期的互動，論文中未深入討論修補間的相容性檢測。
- **MoE 專家排程的細節**：雖然涵蓋了 MoE 工作負載，但「專家並行」的具體排程最佳化（如負載平衡、all-to-all 通訊重疊）未在論文中深入展開。
- **跨叢集轉移的負遷移風險**：若兩個叢集的硬體特性差異過大（如 H100 vs. 國產 GPU），經驗轉移可能產生負面效果，論文中未量化此風險。

#### 未來研究方向

**1. 理論層面的深化**

- **搜尋複雜度的形式化分析**：InfraRSI 的全域模型擬合提供了某種「樣本效率」保證，但缺乏理論上的收斂性證明。未來可探索在何種假設下，「預算組合式搜尋」能以次線性試驗次數逼近全域最佳。
- **Tobit 模型的識別條件**：右審查式 Tobit 模型需要滿足特定假設（如審查機制的可忽略性），未來可研究在 OOM 邊界附近的識別性問題。
- **跨硬體轉移的泛化界**：跨硬體經驗轉移的有效性需要理論支撐——何時轉移有助、何時有害？這涉及「硬體相似度度量」的定義。

**2. 方法層面的擴展**

- **多目標最佳化**：當前 InfraRSI 僅優化吞吐量，未來可擴展到「吞吐量 × 記憶體 × 能源效率 × 數值穩定性」的多目標 Pareto 前沿探索。
- **線上學習與適應性預算**：在預算受限時，動態調整「探索 vs. 利用 (exploration vs. exploitation)」的比率，並根據中間結果重新分配預算。
- **程式碼修補的可組合性分析**：建立修補間的相容性圖譜 (compatibility graph)，避免不相容修補的堆疊導致非預期行為。
- **強化學習驅動的搜尋策略**：將 run 階段視為一個序列決策問題，用強化學習學習更高效的搜尋策略。

**3. 應用層面的拓展**

- **推論基礎設施最佳化**：將 InfraRSI 從訓練擴展到推論 (inference) 基礎設施，處理 KV 快取、批次排程、speculative decoding 等獨特挑戰。
- **異質硬體支援**：當前實驗僅限於 NVIDIA GPU，未來可擴展到 AMD GPU、國產 AI 晶片、TPU 等異質環境，這對「跨硬體經驗轉移」機制提出了新挑戰。
- **聯邦學習與隱私約束下的訓練**：在隱私預算、通訊預算、計算預算的多重約束下進行訓練基礎設施最佳化。
- **永續 AI 與碳感知最佳化**：將碳排放作為優化目標之一，使訓練基礎設施不僅追求吞吐量，也追求碳效率。

**4. 與其他 RSI 系統的整合**

- **演算法 + 基礎設施聯合 RSI**：將 InfraRSI 與演算法發現系統（如 FunSearch、AlphaEvolve）結合，實現「模型架構 + 訓練配置」的聯合自我改進。
- **代理框架的自我改進**：InfraRSI 本身是一個代理框架，未來可探索讓 InfraRSI 改進自己的搜尋策略、驗證契約、經驗庫結構，實現「三層 RSI」。
- **跨組織經驗共享**：建立類似「GitHub for training recipes」的開放生態，讓不同組織能共享經驗庫（同時保護商業機密）。

**5. 安全性與魯棒性**

- **對抗性 LLM 提案的防禦**：惡意或低品質的 LLM 提案可能繞過驗證器，需要研究更強的防禦機制（如形式化驗證、抽象解釋）。
- **獎勵破解的形式化定義**：當前「獎勵破解」是經驗性概念，未來需要形式化定義並證明驗證器的完備性。
- **可解釋性**：理解為何某個配置比另一個快——這對除錯與信任建立至關重要。

**6. 基準與生態建設**

- **標準化評測基準**：建立類似 MLPerf 但專注於「訓練基礎設施最佳化」的基準，讓不同方法可在公平條件下比較。

當團隊想啟用 `torch.compile` 圖編譯、FP8 量化或自訂 CUDA 核心，但擔心編譯器衝突（compiler conflicts）、數值漂移（numerical drift）或 OOM 時，InfraRSI 的 16 項不變量驗證器與失敗歸因機制能安全地探索這些邊界。

### 實作步驟建議

**第一步：建立任務契約與可編輯範圍**
參考論文 §3 的 16 項不變量（Table 2），將工作負載（有效批次大小、序列長度）、損失（容忍度、收斂閾值）、時間（單步時間下限、warm-up 步數）寫入 `init` 階段的配置檔。明確定義哪些檔案路徑可被 LLM 修改、哪些屬於凍結區（如資料集、評估腳本）。

**第二步：部署 `doctor` 階段的環境探針**
實作基準階段分析器（baseline phase profiler），記錄前向、 backward、optimizer、comm overlap 各階段的耗時分佈。執行至少 10 次基準短跑以校準叢集雜訊分佈，計算配對單步時間雜訊（paired step-time noise）作為後續顯著性檢定的依據。

**第三步：建構經驗庫的初始種子**
即使在冷啟動下，也應預先填入幾類「經驗種子配置」：保守配置（全部預設）、激進配置（啟用 `torch.compile` + FP8）、記憶體節約配置（gradient checkpointing + ZeRO-3）。這些將作為 `run` 階段多起點初始化（multi-start initialization）的基礎。

**第四步：實作 `run` 階段的三層搜尋控制器**
1. **多起點初始化與全域模型**：從經驗庫抽樣多個起點，執行後擬合 Cholesky 執行時間模型與 Tobit 峰值記憶體模型（含 OOM 試驗）。
2. **先驗校準、失敗歸因與捆綁完成**：將 LLM 預測的加速比與實際量測比對，修訂先驗；對 OOM 配置估算每個設定的記憶體成本，配對記憶體節約旋鈕。
3. **高槓桿旋鈿逃逸與程式碼修補堆疊**：在 `torch.compile`、FP8、tensor parallel degree 等高槓桿設定周圍擴大搜尋半徑，並將已驗證的程式碼修補堆疊到穩定配置上。

**第五步：建立回測與推廣流程**
`run` 結束後，對頂尖候選執行獨立背靠背（back-to-back）重跑，與基準做配對 t 檢定。通過者進入 `report` 階段，記錄來源路徑、失敗試驗成本、預期 MFU 提升；經人類審核後由 `apply` 階段提交。

**第六步：跨叢集經驗蒸餾**
將通過驗證的配置、量測結果、已知失敗模式正規化為硬體無關的特徵（如「在 NVLink 全互連節點上，TP=8 比 TP=4 快 X%」），寫入跨硬體經驗庫。下次在新硬體啟動時，先用經驗庫初始化先驗，再進入線上修訂迴圈。

### 潛在風險與注意事項

**獎勵破解與數值漂移**
LLM 代理可能透過縮短有效批次大小、延後 optimizer 更新、或套用不穩定的低精度轉換來製造虛假加速。緩解方式：嚴格執行 16 項不變量驗證器，特別是損失不變量（容忍度通常需小於 1e-3 相對誤差）與有效 token 計數不變量。

**叢集雜訊導致誤判**
論文指出叢集雜訊橫跨兩個數量級，固定接受閾值會在共享主機上推廣隨機抖動、在安靜節點上丟棄有效的通訊 overlap。緩解方式：使用 `doctor` 階段校準的配對單步時間雜訊作為自適應閾值，並要求多次重跑確認。

**OOM 邊界停滯**
單一現行最佳（single incumbent）的貪婪搜尋會在 OOM 邊界卡住，因為吞吐量提升的設定單獨使用會超出裝置記憶體。緩解方式：採用多起點初始化，並用 Tobit 模型估算每個設定的記憶體成本，主動配對記憶體節約旋鈕。

**LLM 先驗嚴重失準**
零樣本 LLM 預測的加速比與實際硬體執行相關性差，常否決高收益的編譯或通訊設定。緩解方式：將先驗視為可修訂的假設而非約束，在每次試驗後用實際量測更新 Cholesky 模型。

**跨硬體經驗轉移的負遷移**
在 H100 上有效的設定可能在 H200 上完全失效（例如 FP8 路徑）。緩解方式：經驗庫應儲存硬體條件化的證據，並標註「在 NVLink 全互連 + Hopper 架構下成立」等前置條件，避免盲目套用。

**失敗試驗成本失控**
MoE 模型的單次試驗可能耗費數小時，若搜尋控制器未追蹤失敗成本，可能在無效方向上耗盡預算。緩解方式：為每個搜尋分支設定預算上限，並在 `report` 階段明確列出失敗試驗的累計成本。

### 與其他技術的整合建議

**與 Optuna / Hyperband 等傳統調校器整合**
InfraRSI 的 `run` 階段可將 Optuna 的 TPE 採樣器作為底層搜尋骨幹，但需將其包裝為支援多起點初始化與全域模型擬合的介面。Optuna 本身缺乏程式碼修補能力，InfraRSI 可作為其上層的「程式碼感知」控制器。

**與 AlphaEvolve / RE-Bench 等程式碼代理整合**
RE-Bench 與 Auto-Research 在論文中僅達到 1.37× 與 1.34× 加速比，主要因為缺乏任務契約與跨硬體經驗。建議將 InfraRSI 的 `init` 階段（任務契約）與 `doctor` 階段（雜訊校準）作為這些代理的前置處理器，再讓代理專注於程式碼修補提案。

**與 torch.compile / TorchInductor 整合**
`torch.compile` 的圖編譯邊界是 InfraRSI 高槓桿旋鈕的主要來源。建議在 `run` 階段將 `mode`（default / reduce-overhead / max-autotune）、`dynamic`、`fullgraph` 等參數納入搜尋空間，並在 `apply` 階段將通過驗證的編譯設定寫入訓練腳本。

**與 Megatron-LM / DeepSpeed 的設定系統整合**
Megatron 的 `--tensor-model-parallel-size`、`--pipeline-model-parallel-size` 與 DeepSpeed 的 ZeRO 階段、CPU offload 設定都是 InfraRSI 的搜尋目標。建議將這些 CLI 參數抽象為結構化配置物件，方便全域模型擬合。

**與 Weights & Biases / MLflow 等實驗追蹤平台整合**
InfraRSI 的 `report` 階段產出的稽核結果、失敗試驗成本、推廣變更清單可直接寫入 W&B 的 Reports 或 MLflow 的 Experiments，作為團隊的訓練基礎設施變更日誌。

**與 Kubernetes / Slurm 叢集排程器整合**
`run` 階段的試驗排程可透過 K8s Job 或 Slurm 提交，並將 GPU 時脈、NVLink 拓樸、節點共置資訊自動注入 `doctor` 階段的環境探針，實現叢集感知的搜尋。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與 §1 介紹，理解 InfraRSI 解決的「分散式訓練調校為何比單一核心合成更難」這個核心問題。Figure 1 的五階段工作流程圖是最佳起點，無需深入統計模型即可掌握整體架構。建議搭配閱讀 §2 的失敗模式分析（reward hacking、叢集雜訊、OOM 邊界），這些是任何自動化訓練優化都會遇到的現實障礙。

**給 AI 工程師**：重點閱讀 §3 的任務契約設計（16 項不變量）與 §4 的三層搜尋控制器（多起點初始化、先驗校準、高槓桿旋鈕逃逸）。這些是可直接落地到自家訓練管線的工程模式。特別注意 §4.1 的 Cholesky 執行時間模型與 Tobit 記憶體模型——前者處理參數間的相關性，後者正確處理 OOM 試驗的存活偏誤，這是許多自製調校器忽略的關鍵。

**給研究者**：§4 是方法論核心，建議仔細推導全域模型的擬合目標與先驗校準的貝氏更新規則。§5 的跨硬體經驗轉移協議是值得延伸的研究方向——如何正規化硬體特徵、如何避免負遷移、如何在異質叢集上做 federated 式的經驗聚合。Table 6 的數值容差審計也值得深入研究，特別是不同精度（FP8/BF16/FP16）下的容差邊界設定。

**給產品經理**：聚焦於 §1 的問題陳述與 §6 的實驗結果。理解 InfraRSI 達到的 1.83× 幾何平均加速比與 MFU 從 17.4% 提升至 30.0% 的業務意義——這直接轉化為訓練成本降低與模型迭代加速。特別注意「跨硬體經驗轉移」對多團隊組織的價值：當公司同時擁有 H100 與 H200 叢集時，經驗庫可避免每個團隊從零開始調校。評估導入時，應將「失敗試驗成本」納入 ROI 計算——MoE 模型單次試驗成本可能高達數千美元，InfraRSI 的預算控制機制是關鍵的成本護欄。
