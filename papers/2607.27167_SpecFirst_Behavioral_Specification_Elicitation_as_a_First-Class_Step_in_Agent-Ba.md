# SpecFirst：以行為規格擷取作為從頭進行基於代理人之程式合成的第一級階段

**原文標題：** SpecFirst: Behavioral Specification Elicitation as a First-Class Step in Agent-Based Program Synthesis from Scratch  
**作者：** Yihao Chen、Shi Chang、Feng Lin 等 7 位作者  
**發布日期：** 2026-07-29

## ⚡ TL;DR

ProgramBench顯示現有框架將探測與合成混為一談，導致從頭建構程式的效能低落。
本文提出SpecFirst，規格代理人先探測二進位檔並產出結構化規格，再由程式碼合成代理人實作。
全200題評測中，SpecFirst提升通過率6.9%–21.3%與覆蓋率9.4%–18.5%。

## 摘要翻譯

基於大型語言模型的代理人（LLM-based agents）在已有程式碼庫提供情境的軟體工程任務中表現出色，但從頭建構程式（from-scratch program construction）在本質上仍然困難得多。近期的 ProgramBench 等基準測試量化了這個差距：在僅給定自然語言文件（natural-language documentation）與一個作為行為神諭（behavioral oracle）的僅執行二進位檔（execute-only binary）的情況下，即使是前沿模型（frontier models），能解決的實例也不到 1%。現有框架將文件閱讀、行為探索與程式碼合成（code synthesis）混為單一迴圈，導致代理人探測（probing）不足、隨著上下文漂移（context drifts）而失去行為意圖（behavioral intent），並將早期的誤釋（misinterpretations）傳播到最終實作（implementation）。受經典需求工程（requirements engineering）啟發，我們主張行為規格擷取（Behavioral Specification Elicitation）應該是實作之前的第一級階段（first-class phase）。我們提出 SpecFirst（規格優先框架），一個強制在程式碼合成前先進行規格擷取的兩階段框架（two-stage framework）。首先，專責的規格代理人（spec agent）會探測二進位檔，並將觀察結果與文件結合為結構化規格（structured specification）。接著，程式碼合成代理人（code synthesis agent）使用此規格來驅動實作。這種分解（decomposition）能在開始實作之前解決文件歧義（documentation ambiguities），並在整個合成過程中提供穩定的行為參考（stable behavioral reference）。我們在 ProgramBench 的全部 200 個實例上評估 SpecFirst，使用四個橫跨兩個模型家族且能力相差一個數量級的模型。SpecFirst 始終優於單迴圈基線（single-loop baseline），測試通過率（test pass rates）提升 6.9%–21.3%，二進位檔探索覆蓋率（binary exploration coverage）提升 9.4%–18.5%，且皆達統計顯著（statistically significant）。針對程式碼合成的行為分析進一步顯示，先行的規格能讓程式碼建構更早開始並更持續地進行。我們的結果顯示，明確的需求工程階段是從頭建構程式的有效典範。

### 核心貢獻（3～5點）
- 提出 SpecFirst 兩階段框架，將行為規格擷取獨立為實作前的第一級階段，避免現有單迴圈方法中規格理解與程式碼合成相互干擾。
- 設計專責的規格代理人，透過探測僅執行二進位檔並結合自然語言文件，產出結構化規格以解決文件歧義。
- 在 ProgramBench 全部 200 個實例上進行大規模評估，證明 SpecFirst 能顯著提升測試通過率與二進位檔探索覆蓋率。
- 透過行為分析顯示，先行的規格可促使程式碼建構更早開始並更持續地進行。
- 驗證明確的需求工程階段是從頭建構程式的有效典範。

### 適合對象
適合對軟體工程自動化、大型語言模型代理人、程式合成與需求工程感興趣的研究者與工程師，特別是關注從頭建構程式、基於規格之合成方法，以及如何利用可執行二進位檔作為行為神諭來輔助程式生成者。

## 深度分析

#### 方法論解析

SPECFIRST（規格優先框架）的核心主張是將 **behavioral specification elicitation（行為規格擷取）** 從 **code synthesis（程式碼合成）** 中分離出來，成為一個獨立的 **first-class phase（第一級階段）**。在傳統軟體工程中，**requirements engineering（需求工程）** 強調在實作前先透過訪談、原型操作與情境分析來釐清行為；SPECFIRST 把這個典範移植到 **agent-based program synthesis（基於代理人的程式合成）** 上，並利用 **execute-only binary（僅執行二進位檔）** 作為可自動化的 **behavioral oracle（行為神諭）**。

問題設定可形式化為：目標程式 *P* 是一個確定性的命令列程式，代理人 *L* 只能取得 **natural-language documentation（自然語言文件）** *D* 與 **execute-only binary（僅執行二進位檔）** *B*，最終要產出實作 *Î*。SPECFIRST 將此流程拆為兩階段：

1. **規格擷取階段（Spec Agent）**  
   由專責的 **spec agent（規格代理人）** 獨佔整段 turn budget 的一部分，只進行行為理解而不寫程式碼。它對 *B* 進行系統化的 **black-box probing（黑箱探測）**：餵入不同命令列參數、標準輸入、邊界值、錯誤輸入，觀察標準輸出、標準錯誤與結束碼，並將觀察結果與 *D* 整合成一份結構化的 **structured specification（結構化規格）**，即 `SPEC.md`。這份文件同時記錄了文件宣稱的行為與二進位檔實際展現的行為，因此能解決 **documentation ambiguities（文件歧義）**，並補捉文件未提及的邊界案例、錯誤路徑與旗標互動。

2. **程式碼合成階段（Code Synthesis Agent）**  
   第二階段的 **code synthesis agent（程式碼合成代理人）** 取得 *D*、*B* 與 `SPEC.md`，專注於把規格轉換為可執行程式碼。由於行為意圖已被外顯化並固定下來，合成階段擁有 **stable behavioral reference（穩定的行為參考）**，可減少長 horizon 任務中的 **context drifts（上下文漂移）**，也能避免早期 **misinterpretations（誤釋）** 隨著回合數不斷放大。

這種 **decomposition（分解）** 帶來幾個設計上的好處：

- **強迫探索再實作**：單迴圈基線常在探測不完整時就切換到寫程式碼；SPECFIRST 透過階段切換強制代理人先完成足夠的 **binary exploration（二進位檔探索）**。
- **錯誤隔離**：規格階段的錯誤可以在進入實作前被檢視或修正，而不會一路滲透到最終程式碼。
- **責任分離**：規格代理人專注於「什麼是對的行為」，合成代理人專注於「如何實現」，降低單一代理人在兩種認知模式間切換的負擔。

不過，從現有摘要與前導章節無法得知 `SPEC.md` 的確切綱要、spec agent 使用的工具 API、輸入生成策略，以及兩階段之間的 turn budget 分配比例。這些細節會顯著影響方法的可重現性與上限。

#### 實驗數據解讀

作者在全數 200 個 **ProgramBench** 實例上進行評估，並橫跨四個模型、兩個模型家族，且這些模型能力相差一個數量級。主要評估指標有兩項：

- **test pass rates（測試通過率）**：衡量最終實作通過隱藏測試的比例。
- **binary exploration coverage（二進位檔探索覆蓋率）**：衡量代理人對二進位檔行為空間的探測程度。

實驗結果顯示，SPECFIRST 相較於 **single-loop baseline（單迴圈基線）** 在 **test pass rates（測試通過率）** 上提升 6.9%–21.3%，在 **binary exploration coverage（二進位檔探索覆蓋率）** 上提升 9.4%–18.5%，且皆達 **statistically significant（統計顯著）** 水準。

這些數字可以從三個層次解讀：

1. **探索覆蓋率的提升直接驗證了方法論假設**  
   單迴圈基線的系統性缺陷之一就是 **ineffective exploratory probing（無效的探索性探測）**。SPECFIRST 把探測獨立成階段後，覆蓋率顯著提高，表示 spec agent 確實能發現更多文件未記載的行為，包括邊界條件與錯誤處理路徑。

2. **規格品質轉化為實作品質**  
   測試通過率的提升說明 `SPEC.md` 不只是更詳細的文件，而是真正能被 **code synthesis agent（程式碼合成代理人）** 利用來產出更正確程式碼的 **stable behavioral reference（穩定的行為參考）**。這也呼應了「需求工程前置」的傳統觀點：釐清需求所花的成本會在實作階段得到回報。

3. **跨模型與跨家族的穩定性**  
   提升幅度在不同能力層級的模型上皆一致出現，暗示 SPECFIRST 的兩階段分解並非只對最強模型有效，而是一種具有泛用性的流程改進。對能力較弱的模型，規格文件可能特別有幫助，因為它把複雜的行為理解任務從程式生成任務中卸載出來。

作者進一步進行行為分析，發現擁有先驗規格後，**code synthesis agent（程式碼合成代理人）** 會「更早開始寫程式碼，並持續實作更長時間」。這表示單迴圈基線把大量回合浪費在「邊寫邊探」的來回切換上，而 SPECFIRST 讓合成階段能更專注、連貫地進行 **implementation（實作）**。

需要留意的是，ProgramBench 的基準難度極高：即使是 **frontier models（前沿模型）**，在僅有文件與二進位檔的情況下完整解出的比例低於 1%。因此 6.9%–21.3% 的通過率提升雖然在統計上顯著，但絕對解題率可能仍然有限。未來若能公布絕對通過率、各模型個別表現，以及 per-instance 的變異程度，將有助於更精確評估實務影響。

#### 與現有研究的比較

SPECFIRST 主要與兩類現有研究形成對比：

1. **單迴程式工程代理人框架（SWE-agent、OpenHands）**  
   這些框架把閱讀文件、探測二進位檔、撰寫程式碼放在同一個回合預算內自由切換。作者指出這會導致三個問題：  
   - **探測不足**：代理人在尚未建立完整行為模型前就急於實作。  
   - **規格遺失**：長對話中 **behavioral intent（行為意圖）** 因 **context drifts（上下文漂移）** 與 reasoning token stripping 而逐漸劣化。  
   - **錯誤傳播**：缺乏錨定文件，早期的 **misinterpretations（誤釋）** 會隨著後續決策不斷放大。  
   SPECFIRST 透過明確的兩階段分解，針對性地緩解了上述問題。

2. **以人為本的需求規格框架（OpenSpec、spec-kit）**  
   這類工作同樣強調規格驅動，但依賴人類利害關係人提供規格輸入，無法自動從 **execute-only binary（僅執行二進位檔）** 中擷取行為。SPECFIRST 的貢獻在於把 **behavioral specification elicitation（行為規格擷取）** 自動化，並將其視為 **from-scratch program construction（從頭建構程式）** 的必要前置步驟。

相較於傳統 **requirements engineering（需求工程）**，SPECFIRST 的創新在於把「原型操作」與「情境建構」的對象從人類使用者換成可執行的二進位檔，並讓 LLM 代理人同時扮演需求工程師與實作者的角色。

然而，SPECFIRST 也有其限制：

- **規格錯誤仍會傳播**：雖然兩階段分解能隔離部分錯誤，但如果 spec agent 對二進位檔的行為理解有系統性偏差，這些偏差會被寫入 `SPEC.md` 並成為合成階段的「正確答案」。
- **Turn budget 分配兩難**：規格階段佔用越多預算，合成階段能用的預算就越少。若規格過於冗長，也可能超出合成代理人的上下文長度。
- **假設二進位檔是確定性且可觀察的**：對於具有隨機性、狀態相依或需要網路互動的程式，現有設計可能不敷使用。
- **文件與二進位檔衝突時的處理**：目前摘要未說明當 *D* 與 *B* 的行為不一致時，spec agent 如何決定何者為準。

#### 可重現性評估

從目前可取得的摘要與前導章節來看，論文並未明確說明是否釋出 SPECFIRST 的原始碼、提示詞範本或 `SPEC.md` 的結構化綱要。以下從幾個面向評估可重現性：

- **資料集**：**ProgramBench** 作為公開基準測試，理論上可供其他研究者取得。但實驗中使用的確切版本、測試分割與執行環境必須清楚記載，才能確保結果可比較。
- **程式碼與工具**：SPECFIRST 需要一個能安全執行 **execute-only binary（僅執行二進位檔）** 的沙箱環境、呼叫二進位檔的工具介面、解析輸出與結束碼的邏輯，以及產生 `SPEC.md` 的提示詞。若作者能釋出 Docker 映像檔與評估腳本，將大幅提升可重現性。
- **模型與參數**：實驗使用四個跨家族模型，這些多為專有 API 模型（例如 GPT 系列與 Claude 系列）。由於 API 版本、**temperature**、top-p、最大回合數等參數都會影響結果，論文需詳細記載這些設定。此處並無訓練新模型權重，因此不涉及模型權重釋出問題。
- **規格文件格式**：`SPEC.md` 的結構（例如是否包含輸入輸出範例、錯誤碼表格、命令列參數說明）是方法論的關鍵。若格式不固定，不同執行間的結果可能難以複製。

整體而言，SPECFIRST 的可重現性高度依賴作者是否願意釋出完整的實驗套件。建議未來版本附上 artifact appendix，說明環境設定、提示詞、工具 API 與預算分配策略。

#### 未來研究方向

SPECFIRST 為 **from-scratch program synthesis（從頭建構程式）** 開啟了幾個值得延伸的研究方向：

- **主動式與適應性探測**：目前的 spec agent 可能採用較固定的探測策略。未來可結合 **coverage-guided fuzzing（覆蓋導向模糊測試）** 或主動學習，讓代理人根據已觀察到的行為自動選擇下一個最具資訊量的輸入，以進一步提升 **binary exploration coverage（二進位檔探索覆蓋率）**。
- **規格與合成的迭代回饋**：SPECFIRST 目前是一次性的兩階段流程。未來可設計「規格—實作—驗證—修正規格」的迭代迴路，讓合成階段發現的測試失敗資訊回饋給 spec agent，同時仍保留 `SPEC.md` 作為錨定文件。
- **形式化規格與驗證**：將 `SPEC.md` 轉換為更形式化的規格語言（例如 BDD 情境、前置/後置條件、狀態機），並據此自動生成測試或進行程式驗證，可進一步提高正確性保證。
- **多代理人規格共識**：讓多個 spec agent 各自獨立探測並產出規格，再透過辯論或投票機制產出最終規格，有助於降低單一代理人的系統性誤判。
- **擴展到非命令列程式**：目前的設定針對確定性命令列程式。未來可研究如何將 SPECFIRST 應用於互動式程式、網路服務、具有隨機性的遊戲或具狀態的長期執行系統。
- **人機協作的規格驗證**：在關鍵應用場景中，可讓人類工程師審閱 `SPEC.md` 後再進入合成階段，結合自動化效率與人類領域知識。
- **預算分配與成本最佳化**：研究如何在規格階段與合成階段之間動態分配 turn budget，並探索使用較小模型執行規格擷取、較大模型執行程式合成的成本效益組合。
- **跨語言與真實世界任務**：除了 ProgramBench 的合成任務，未來可將 SPECFIRST 應用於真實世界的遺留系統重建、API 重新實作或跨語言移植等場景，驗證其泛化能力。

## 論文問答

**Q1：ProgramBench 凸顯了從頭建構程式的什麼核心挑戰？**
A：ProgramBench 要求代理人在僅有自然語言文件與僅執行二進位檔作為行為神諭的情況下，重建目標程式的完整行為包絡，這遠比在有既有程式碼庫的任務中困難。即使是最強大的前沿模型，在該基準測試上也只能完整解決不到 1% 的實例，顯示從頭建構程式仍是開放挑戰。這項挑戰的核心在於代理人必須同時決定架構、程式語言與所有行為細節，卻缺乏可錨定的原始碼上下文。

**Q2：現有的單迴圈框架為何在此任務上表現不佳？**
A：現有框架如 SWE-agent 與 OpenHands 將文件閱讀、二進位檔探測與程式碼合成混在同一個迴圈中，沒有機制強制代理人在開始實作前完成充分的行為規格擷取。這種糾纏導致三個系統性問題：探測不足而錯過邊界案例、長對話中因上下文漂移而遺失行為意圖，以及早期誤釋在後續回合中不斷放大。由於缺乏穩定的行為參考，代理人一旦對文件或行為做出錯誤假設，就會在錯誤基礎上持續堆疊決策。

**Q3：為何應將行為規格擷取視為第一級階段？**
A：借鏡傳統需求工程，將行為規格擷取提升為第一級階段能讓代理人在撰寫任何程式碼之前，先透過系統化探測澄清文件歧義並建立結構化規格。這種分解提供了一個穩定的行為參考，使後續實作能夠對齊正確意圖，而非依賴在長對話中逐漸漂移的隱式記憶。此外，先行擷取規格可防止早期誤釋被傳播到最終實作，從而降低錯誤累積的風險。

**Q4：SpecFirst 的核心方法為何？**
A：SpecFirst 採用兩階段框架，明確將行為規格擷取與程式碼合成拆分為獨立階段。第一階段由專責的規格代理人接收自然語言文件與僅執行二進位檔，透過系統化黑箱探測產出結構化的 SPEC.md 規格文件。第二階段再由程式碼合成代理人依據該規格、文件與二進位檔進行實作。這種分解確保規格在實作前已被充分擷取，並讓兩個代理人各自專注於單一目標。

**Q5：相較於先前的規格驅動框架，SpecFirst 的關鍵創新是什麼？**
A：過往如 OpenSpec 與 spec-kit 等規格驅動框架主要依賴提示人類利害關係人提供規格輸入，無法自動透過二進位檔探測進行行為擷取。SpecFirst 則讓規格代理人主動對僅執行二進位檔進行系統化黑箱探測，並將觀察與文件整合為結構化規格。更重要的是，SpecFirst 透過明確的階段邊界強制規格擷取優先於程式碼合成，避免兩者混為一談。這種自動化且前置的規格擷取是其在從頭程式合成場景中的關鍵差異。

**Q6：哪些設計選擇使 SpecFirst 有效？**
A：首先，專責的規格代理人被賦予專屬的回合預算，專注於理解行為而無需分心撰寫程式碼，從而實現更徹底的二進位檔探索。其次，結構化的 SPEC.md 文件作為穩定的行為參考，讓程式碼合成代理人在整個實作過程中都能對齊目標行為。最後，兩階段之間的明確分界防止代理人過早進入實作，確保文件歧義與邊界案例在編碼開始前已被釐清。

**Q7：實驗採用了哪些基準測試與模型？**
A：作者在所有 200 個 ProgramBench 實例上進行評估，涵蓋四個橫跨兩個模型家族且能力相差一個數量級的模型。雖然文中以 GPT-5.5 作為前沿模型的例子，但實驗設計強調在不同能力層級的模型上驗證 SpecFirst 的通用性。這樣的設置能夠檢驗兩階段框架是否優於單迴圈基線，而不僅限於特定強模型。

**Q8：SpecFirst 取得了哪些關鍵量化結果？**
A：SpecFirst 在所有模型上均穩定優於單迴圈基線，測試通過率提升 6.9% 至 21.3%，二進位檔探索覆蓋率提升 9.4% 至 18.5%，且兩者皆達統計顯著水準。這些結果顯示，無論模型能力高低，明確的需求工程階段都能帶來一致的行為發現與實作品質改善。特別值得注意的是，即使在原本表現極差的前沿模型上，SpecFirst 仍能顯著縮小從頭建構程式的能力差距。

**Q9：程式碼合成階段的行為分析發現了什麼？**
A：行為分析顯示，當程式碼合成代理人擁有先行規格時，會更早開始撰寫程式碼，並能更持續地投入實作，而非在探測與編碼之間反覆切換。這表示結構化規格減少了代理人在每個回合重新推導行為意圖的認知負擔，使其能專注於將規格轉譯為程式碼。此現象也間接證明，規格擷取不僅改善最終結果，也改變了合成過程中的工作模式，使其更接近傳統軟體工程的實作流程。

**Q10：SpecFirst 在哪些實務場景中最有價值？**
A：SpecFirst 特別適用於需要從遺留二進位檔重建軟體、依據 RFC 與參考實作實作通訊協定，或僅有自然語言規格與可執行參考品的從頭開發任務。在這些場景中，文件往往存在歧義，而僅執行二進位檔能提供寶貴的行為神諭，SpecFirst 的規格代理人可系統化地發掘文件未記載的邊界行為。此外，任何需要高保真度復現現有程式行為、但無法取得原始碼的場合，都能受益於這種先擷取規格再實作的典範。

**Q11：在產品化部署時應考慮哪些因素？**
A：首先，規格代理人需要足夠的回合預算與 API 呼叫成本才能進行徹底探測，這會使整體延遲與花費高於單迴圈方法。其次，SPEC.md 的格式必須與下游程式碼合成代理人的解析能力相容，否則規格資訊可能無法有效傳遞。最後，產品團隊應評估目標二進位檔的安全性與執行環境隔離，因為自動化探測需要反覆執行未知程式碼。

**Q12：這項研究對代理人軟體工程領域可能產生什麼影響？**
A：SpecFirst 為代理人軟體工程引入了一個明確的需求工程階段，證明將複雜任務分解為專業化角色的多階段流程能顯著提升從頭建構程式的成效。這可能啟發未來框架採用更多模組化的代理人設計，例如分離測試代理人、架構代理人或驗證代理人。更廣泛地說，它挑戰了「單一通用代理人迴圈足以處理長視距任務」的假設，推動領域朝向更具結構化的工作流程發展。

**Q13：SpecFirst 有哪些已承認的限制？**
A：SpecFirst 假設能夠取得一個可作為行為神諭的僅執行二進位檔，這在許多真實場景中可能無法滿足。此外，儘管規格代理人會進行系統化探測，但對於行為空間極大或需要特定環境狀態才能觸發的程式，其覆蓋率仍可能不完整。最後，兩階段設計必然帶來額外的計算成本與延遲，對於需要快速回應的互動式應用可能不是最佳選擇。

**Q14：哪些類型的失敗案例仍可能發生？**
A：若目標程式的某些行為僅在極罕見的輸入組合或特定錯誤路徑下才會觸發，規格代理人可能因探測覆蓋不足而遺漏這些案例。當自然語言文件存在嚴重誤導或與二進位檔行為明顯矛盾時，規格代理人也可能過度偏重文件而產生偏差規格。此外，對於行為包絡極為龐大或涉及複雜狀態互動的程式，結構化規格可能無法完整捕捉所有細節，導致後續實作仍有缺陷。

**Q15：未來有哪些有前景的研究方向？**
A：未來可探索將合成階段的失敗回饋引入規格擷取，形成迭代精化的迴圈，使規格能隨實作驗證結果動態更新。另一方向是結合人類專家的互動式規格擷取，在規格代理人無法確定時請求澄清，以提升複雜系統的規格品質。此外，也可將 SpecFirst 的典範擴展到命令列程式以外的領域，例如網頁應用程式、嵌入式系統或 API 服務，並整合覆蓋率導向的模糊測試以強化探測策略。

## 實務應用指南

### 適用場景

1. **遺留二進位檔重構**  
   組織內部存在僅剩執行檔、原始碼已遺失或授權到期的命令列工具。SpecFirst 可先由規格代理人透過僅執行二進位檔（execute-only binary）進行系統化探測，產出結構化規格 SPEC.md，再由程式碼合成代理人以目標語言重新實作，降低人工作業負擔。

2. **第三方 SDK／CLI 的相容實作**  
   當需要開發與某第三方命令列工具行為一致的開源替代方案，但僅能取得官方自然語言文件與發布二進位檔時，可先利用規格擷取階段補捉文件未記載的邊界條件、錯誤路徑與旗標互動，再進行程式碼合成。

3. **教育與競賽題目的自動解題系統**  
   在程式設計競賽或程式教學情境中，題目敘述相當於自然語言文件，參考解答編譯後的二進位檔可作為行為神諭（behavioral oracle）。SpecFirst 的兩階段框架可協助系統先釐清題意與隱藏測資行為，再產出通過測試的程式。

4. **嵌入式或韌體行為還原**  
   針對可在模擬器或沙箱中執行的嵌入式命令列程式，工程師可透過 SpecFirst 先建立行為包絡（behavioral envelope）規格，再移植到新的硬體平台或程式語言，避免直接逆向工程帶來的法律與技術風險。

5. **API 與服務契約的差異化還原**  
   當微服務僅提供文件與可呼叫的執行檔（例如 gRPC/REST 閘道後方的黑箱服務），SpecFirst 可用於還原其輸入輸出契約，作為產生相容客戶端或模擬器（mock）的基礎。

### 實作前置條件

**資料準備**
- 目標程式的自然語言文件（readme、man page、API 文件等）。
- 可執行的僅執行二進位檔，並能在隔離沙箱中運行。
- 輸入輸出範例或測試腳本，用於驗證規格與最終實作。
- 預期行為的評量機制，例如 ProgramBench 風格的測試通過率與二進位檔探索覆蓋率指標。

**運算資源**
- 可呼叫的 LLM API（建議至少具備函式呼叫與長上下文能力的前沿模型）。
- 安全的容器化或虛擬化執行環境，用於反覆執行未知二進位檔。
- 足夠的 token 預算：規格擷取階段與程式碼合成階段各自需要獨立的對話回合與上下文長度。

**技能需求**
- 熟悉提示工程（prompt engineering）與代理人編排框架。
- 具備基礎黑箱測試與軟體測試概念，能設計探測策略。
- 了解目標程式語言與建置系統，以便審查合成結果。
- 具備需求工程思維，能將文件與觀察轉化為可驗證的結構化規格。

---

### 實作步驟建議

1. **建立隔離探測環境**  
   將僅執行二進位檔部署於沙箱中，確保網路、檔案系統與主機資源受到限制，並記錄所有輸入輸出與執行狀態。

2. **設計規格代理人（spec agent）**  
   賦予該代理人明確角色：只負責行為規格擷取，禁止產出實作程式碼。提供文件、可執行二進位檔與一組基礎探測工具（例如參數生成、模糊測試、邊界值分析）。

3. **執行系統化二進位檔探測**  
   讓規格代理人主動對二進位檔餵入各種輸入，觀察正常路徑、錯誤訊息、退出碼、旗標組合與邊界行為，持續直到探索覆蓋率收斂或達到預算上限。

4. **產出並審查 SPEC.md**  
   將文件觀察與探測結果整合為結構化規格，內容應包含功能描述、輸入輸出格式、錯誤處理、邊界條件與範例。由工程師或自動檢查器審查其一致性與完整性。

5. **啟動程式碼合成代理人（code synthesis agent）**  
   將 SPEC.md、原始文件與二進位檔一併提供給合成代理人，並明確限制其任務為依規格實作，不得回頭進行大規模探測。

6. **迭代驗證與錯誤定位**  
   對產出的實作執行測試，若失敗則將錯誤訊息與對照二進位檔的行為回饋給合成代理人進行修正；若規格明顯不足，則回到規格擷取階段補充。

7. **部署與持續維護**  
   將通過驗證的實作納入版本控制，並把 SPEC.md 作為未來功能擴充、重構或審查的穩定行為參考（stable behavioral reference）。

### 潛在風險與注意事項

- **過度擬合探測樣本**  
  規格代理人可能僅根據已探測輸入歸納行為，導致未觀察到的案例被遺漏。建議結合模糊測試與邊界值生成，並在 SPEC.md 中明確標示「已確認」與「推論」行為。

- **執行未知二進位檔的安全風險**  
  僅執行二進位檔可能包含惡意行為。務必使用不可逃逸的容器或虛擬機，關閉網路存取，並限制檔案系統權限。

- **文件歧義被錯誤固化**  
  若自然語言文件本身存在歧義，規格代理人可能將誤釋（misinterpretations）寫入 SPEC.md，進而傳播到實作。應在規格審查階段引入人工或自動化的一致性檢查。

- **上下文漂移與規格遺失**  
  即使有了 SPEC.md，長對話中仍可能發生上下文漂移（context drifts）。建議在每次合成回合開頭重複注入關鍵規格，並使用 reasoning token stripping 以外的上下文管理策略。

- **成本與延遲**  
  兩階段框架會增加總 token 消耗與執行時間。應為規格擷取與程式碼合成分別設定預算上限，並根據問題難度動態調整。

- **規格與實作不同步**  
  後續修改實作時若未同步更新 SPEC.md，將導致規格失效。建議將 SPEC.md 視為程式碼的一部分，納入版本控制與程式碼審查流程。

---

### 與其他技術的整合建議

- **現有代理人框架**  
  可將 SpecFirst 的兩階段流程作為外掛，整合進 SWE-agent 或 OpenHands 等單迴圈基線（single-loop baseline）框架，使其在面對從頭建構程式（from-scratch program construction）任務時自動切換為規格優先模式。

- **CI／CD 與測試管線**  
  將規格擷取與程式碼合成納入持續整合流程：每次文件或二進位檔更新時，自動重新產生 SPEC.md 並執行迴歸測試，確保實作與行為神諭保持一致。

- **需求管理與文件系統**  
  將 SPEC.md 與現有需求管理工具（如 Jira、Confluence、Notion 或內部 Wiki）連結，使結構化規格成為跨團隊溝通的單一真相來源。

- **模糊測試與符號執行工具**  
  在規格擷取階段結合 AFL、libFuzzer 或 KLEE 等工具，可提升二進位檔探索覆蓋率（binary exploration coverage），補強 LLM 主動探測的盲點。

- **版本控制與程式碼審查平台**  
  將 SPEC.md 與合成程式碼一併提交至 Git，並透過 Pull Request 流程要求人工審查規格變更，降低錯誤傳播風險。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於「為什麼要分兩階段」這個核心概念：把「理解需求」和「寫程式」拆開，就像先寫好企劃書再動工。可以先閱讀論文的 Introduction 與 Background，理解 ProgramBench 的任務設定，再參考實作步驟建議，嘗試用簡單的命令列工具走一遍規格擷取與程式碼合成的流程。

**AI 工程師**  
本論文提供了一個可落地的代理人編排模式：將規格擷取與程式碼合成解耦（decomposition），並以 SPEC.md 作為穩定的行為參考。建議重點閱讀方法論與提示設計細節，思考如何將 spec agent 與 code synthesis agent 整合進現有框架，並評估 token 預算、上下文管理與錯誤回饋機制的實作細節。

**研究人員**  
論文的核心貢獻在於驗證「明確的需求工程階段能顯著提升從頭程式合成表現」。建議深入分析實驗設計、統計顯著性與行為分析結果，並思考可延伸的方向，例如：更強大的主動學習探測策略、規格形式化驗證、多代理人協作機制，或將此框架擴展至非命令列程式（如 Web API、GUI 應用）。

**產品經理**  
這項技術適合應用在遺留系統現代化、第三方工具替代方案與自動化程式生成等場景。建議從適用場景與風險章節入手，評估導入成本、安全隔離需求與人工審查責任，並將 SPEC.md 視為可追蹤的產出物，納入產品開發與合規流程。
