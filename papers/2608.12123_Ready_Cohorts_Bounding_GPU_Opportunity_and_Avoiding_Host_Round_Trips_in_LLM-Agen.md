# 就緒同批（Ready Cohorts）：界定 LLM 代理控制（LLM-Agent Control）中的 GPU 執行機會（GPU Opportunity）並避免主機往返（Host Round Trips）

**作者：** Josef Liyanjun Chen

## ⚡ TL;DR

探討 LLM 代理控制路徑何時有足夠並行工作適合 GPU 執行，以及 GPU 路由決策留裝置能否避免主機往返。
提出就緒同批邊界形式化，以動態規劃計算精確離線份額，並將 GPU 二元決策保留在裝置端。
追蹤回放顯示精確打包可將份額從 30.19% 提升至 43.00%，裝置端決策路徑快 1.19 至 2.39 倍。

## 摘要翻譯

LLM 代理服務反覆執行模型與工具呼叫之間的小型確定性轉換：對結果進行路由（route an outcome）、更新狀態，並發出下一個效應（effect）。我們探討此控制路徑（control path）在何時呈現足夠的並行工作以供 GPU 執行（GPU execution），以及當 GPU 計算路由決策（GPU-computed route decision）保留在裝置上（remains on device）時會有何改變。我們利用固定分區份額 F（fixed-partition share F）、精確離線份額 P*（exact offline share P*）、區域上界 U（local upper bound U）與線上達成份額 A（online achieved share A），對就緒同批邊界（ready-cohort boundary）進行形式化（formalize）。在零服務時間（zero service time）、無限容量（unlimited capacity）與相等相對發射期限（equal relative launch deadlines）的假設下，一個專用動態規劃演算法（specialized dynamic program）可精確計算 P*。在對固定的 851 工作階段公開追蹤面板（pinned 851-session public trace panel）進行平穩卜瓦松回放（stationary Poisson replay）時，主要條件（primary condition）為 100,000 個目標活躍工作階段（target active sessions）、K=256（並發上限）以及 50 ms 發射期限（launch deadline），得到 F=30.19%、P*=43.00% 與 U=45.85%。精確打包（exact packing）挽回了固定視窗邊界（fixed window boundaries）所損失的 81.83% 機會。結果導出路由鍵（outcome-derived route key）是一種條件代理變數（conditioning proxy），而非可執行身分證明（proof of executable identity）。另一項機制研究（mechanism study）將 GPU 計算二元決策（GPU-computed binary decision）保留在裝置上，而非將四個位元組回傳主機（returning four bytes to the host）後重新分派（redispatching）。在四種具名 GPU 佈局（named GPU placements）中，裝置端駐留路徑（device-resident path）在全部 36 種配置下均較快；同佈局列中位數比率（within-placement row-median ratios）介於 1.19 倍至 2.39 倍之間。在兩種可接受機制（admissible mechanisms）下，所有 14,557,440 筆經測試的批次呼叫（batched invocations）均與另外實作的主機預言機（host oracle）相符。未移除任何主機端決策的固定巢狀裝置圖（fixed nested device graph），在五種佈局下的全部 60 種配置中均較慢。綜合而言，這些研究確立了 GPU 代理控制的兩道可量測門檻：期限可行的就緒同批供給與觀察點佈局。需要一個整合的有限線上執行環境（joined finite online runtime）來測量 A、CPU 工作量轉移量（CPU displacement）與服務層級效益（service-level benefit）。

### 核心貢獻（3～5點）
- 形式化就緒同批邊界：提出固定分區份額 F、精確離線份額 P*、區域上界 U 與線上達成份額 A 四個指標，並在理想假設下以專用動態規劃演算法精確計算 P*。
- 量化 GPU 執行機會：透過平穩卜瓦松回放固定的 851 工作階段公開追蹤面板，顯示在 100,000 目標活躍工作階段、K=256、50 ms 發射期限下，精確打包可挽回固定視窗邊界所損失的 81.83% 機會。
- 驗證裝置端駐留決策的效能與正確性：在四種具名 GPU 佈局中，裝置端駐留路徑於全部 36 種配置均較快，且兩種可接受機制下的 14,557,440 筆批次呼叫均與主機預言機一致。
- 確立 GPU 代理控制的兩道可量測門檻：期限可行的就緒同批供給與觀察點佈局，並指出需以整合的有限線上執行環境測量線上達成份額 A、CPU 工作量轉移量與服務層級效益。

### 適合對象
適合對 LLM 代理執行環境、GPU 加速控制路徑、資料中心規模代理系統最佳化，以及異質計算（CPU/GPU）排程與效能評估有興趣的研究人員與系統工程師。特別適合正在設計低延遲代理推理基礎設施、希望減少主機往返開銷，或需評估控制路徑 GPU 執行可行性的讀者。

## 深度分析

#### 方法論解析

本研究的核心是將 LLM 代理控制（LLM-agent control）中「模型呼叫與工具呼叫之間的確定性控制轉換（deterministic control transition）」抽離出來，並回答兩個互補的問題：第一，這段控制路徑（control path）在什麼條件下能夠產生足夠的並行工作以交由 GPU 執行；第二，當 GPU 計算路由決策（GPU-computed route decision）後，若將結果保留在裝置上（remains on device）而非回傳主機（host round trips），效能會如何改變。作者將這兩個問題的交界稱為就緒同批邊界（ready-cohort boundary）。

##### 1. 就緒同批（Ready Cohort）的形式化

研究將控制事件（control events）定義為具有釋放時間（release time）\(t_i\)、最晚可發射時間（launch deadline）\(d_i \ge t_i\)，以及路由標籤（route）\(r_i\) 的單位。對於給定路由 \(r\) 與硬體／執行環境配置 \(h\)，存在一個硬體閾值（hardware threshold）\(K_r(h, v, H)\)：從 \(K_r\) 到某個宣告最大值的任何同批大小（cohort size），在測試中都優於某個可接受的基線（admissible baseline）。這個閾值是方法論的起點，它把「GPU 是否值得執行」轉換成「是否有至少 \(K\) 個同群組事件在發射期限（launch deadline）內就緒」的組合問題。

為了衡量可排程的供給量，作者定義四個層級的份額（share）：

- **固定分區份額 \(F\)（fixed-partition share）**：使用固定時間窗（fixed window）切分追蹤資料時，能夠被涵蓋的就緒同批比例。這代表最簡單、最常見的批次策略。
- **精確離線份額 \(P^*\)（exact offline share）**：在零服務時間（zero service time）、無限容量（unlimited capacity）、相等相對發射期限（equal relative launch deadlines）的理想假設下，透過專用動態規劃（specialized dynamic program）計算出的精確最佳比例。
- **區域上界 \(U\)（local upper bound）**：一個用於快速評估可行性的本地上界，提供比 \(P^*\) 更寬鬆但計算成本可能更低的參考。
- **線上達成份額 \(A\)（online achieved share）**：實際有限線上執行環境（finite online runtime）中真正達成的比例，需要結合真實服務時間、CPU 後備（CPU fallback）與排程器來測量。

這四個量各自有明確的推論邊界（inference boundary）：\(F\) 來自固定視窗啟發式；\(P^*\) 來自離線最佳化；\(U\) 來自區域放鬆；\(A\) 則來自線上實作。這種分層設計讓研究者能夠區分「理論可排程量」與「實際可達成量」，避免把離線最佳值誤認為線上保證。

##### 2. 精確離線打包（Exact Offline Packing）

在數學模型中，服務時間與容量限制被刻意理想化：零服務時間、無限容量、所有事件具有相同的相對發射期限。在這些條件下，作者提出一個專用動態規劃演算法來計算 \(P^*\)。這個演算法的價值在於提供一個可重現的工作負載測量（reproducible workload measurement），而不宣稱演算法本身的原創優先性。它回答的問題是：如果排程器能夠完美預知所有事件的釋放時間與期限，並且可以任意組合同一路由的事件，那麼最多有多少比例的事件可以被組成大小至少為 \(K\) 的同批（cohort）。

值得注意的是，模型中的「路由」並非單純的追蹤標籤，而是「同一實作可以在不改變宣告轉換語義的前提下處理該群組事件」的條件。結果導出路由鍵（outcome-derived route key）只是條件代理變數（conditioning proxy），並不是可執行身分證明（proof of executable identity）。這個區分對安全性與語義正確性至關重要：GPU 可以決定「下一條路徑是什麼」，但並不保證該路徑對應的動作可以在 GPU 上安全執行。

##### 3. 機制研究：裝置端駐留決策 vs. 主機往返

第二個實驗是一個獨立的 CUDA 機制研究（mechanism study）。作者固定狀態轉換與路由主體，只改變一個 GPU 計算二元決策（GPU-computed binary decision）被觀察的位置。傳統路徑會把四個位元組（four bytes）的決策結果回傳主機，主機據此分支並重新分派（redispatching）GPU 核心；新的裝置端駐留路徑（device-resident path）則讓決策直接留在 GPU 記憶體內，由後續的 GPU 步驟讀取。

為了排除「單純使用 CUDA 圖形（CUDA graph）或裝置啟動（device launch）本身就會加速」的解釋，作者加入了一個負向控制（negative control）：一個固定的巢狀裝置圖（fixed nested device graph），它並未移除任何主機決策。如果這個負向控制也變快，那麼加速可能來自圖形啟動開銷本身，而非決策保留在裝置上；實驗結果顯示它在所有 60 個配置中皆較慢，因此強化了「觀察點放置（observation placement）」才是關鍵的結論。

##### 4. 執行合約與範圍限制

作者在表 1 中明確劃定執行合約（execution contract）：範圍內的是具型別確定性轉換（typed deterministic transition）、以路由鍵為條件的同批（route-key-conditioned cohorts）、最晚發射時間（latest launch time）、裝置端純決策（device-resident pure decision），以及具名 GPU 佈局（named GPU placements）與經測試的軌跡（exact tested trajectory）。範圍外則包括任意 Python 在 GPU 上執行、已驗證的語義融合（verified semantic fusion）、端到端完成 SLO（end-to-end completion SLO）、特權工具或 VM 生命週期、分散式提交與復原，以及硬體族群推論。這些排除不是未來系統的預設屬性，而是本研究的宣稱邊界（claim boundaries），有助於避免過度推論。

#### 實驗數據解讀

##### 1. 追蹤回放：固定視窗遺失大量可打包機會

主要實驗使用一個固定的 851 工作階段公開追蹤面板（pinned 851-session public trace panel），以平穩卜瓦松回放（stationary Poisson replay）模擬 100,000 個目標活躍工作階段（target active sessions），並設定 \(K=256\)、發射期限（launch deadline）為 50 ms。在這個主要條件（primary condition）下：

- 固定分區份額 \(F = 30.19\%\)
- 精確離線份額 \(P^* = 43.00\%\)
- 區域上界 \(U = 45.85\%\)

這組數字有幾層意義。首先，固定視窗只能捕捉到約三成就緒同批機會，而精確打包（exact packing）可以將比例提升到四成三，兩者差距約 12.81 個百分點。作者進一步指出，精確打包挽回了固定視窗邊界遺失機會（opportunity lost at fixed window boundaries）的 81.83%。換句話說，固定時間窗造成的對齊損失（alignment gap）中，絕大部分並非事件本質上無法並行，而是排程策略過於粗糙。

其次，\(P^*=43.00\%\) 與 \(U=45.85\%\) 之間的差距僅約 2.85 個百分點，表示區域上界在這個設定下相當緊密，可以作為快速評估的實用代理指標。同時，\(P^*\) 遠低於 100%，說明即使在理想離線條件下，仍有超過一半的控制事件因為路由分散或時間上無法聚集，而無法構成大小達到 \(K\) 的就緒同批。這意味著 GPU 代理控制並非「把所有控制邏輯搬上 GPU」那麼簡單，而是必須面對供給間歇性不足的現實。

##### 2. 機制研究：裝置端駐留路徑全面勝出

在 CUDA 機制研究中，作者比較了四種具名 GPU 佈局（named GPU placements）共 36 個配置。裝置端駐留路徑（device-resident path）在所有 36 個配置中都比對應的主機中介 GPU 路徑更快，同佈局列中位數比率（within-placement row-median ratios）介於 1.19× 到 2.39×。這個範圍顯示：

- 即使在最不利的佈局中，保留決策在裝置上仍有約 19% 的加速；
- 在某些佈局中，加速可達 2.4 倍，顯示主機往返（host round trips）與重新分派（redispatching）的開銷可能佔據控制延遲的相當大比例。

更關鍵的是正確性驗證：在兩種可接受機制（admissible mechanisms）下，全部 14,557,440 個測試批次呼叫（batched invocations）都與獨立實作的主機預言機（host oracle）匹配。這表示裝置端駐留不僅更快，也沒有引入語義偏差；GPU 計算二元決策（GPU-computed binary decision）可以安全地留在裝置上，而不需要回傳主機進行驗證。

##### 3. 負向控制：裝置啟動本身不是答案

固定巢狀裝置圖（fixed nested device graph）在全部 60 個配置、五種佈局中皆較慢。這個結果很重要，因為它排除了「只要使用 CUDA 圖形或裝置端核心啟動就會變快」的簡化解釋。真正的收益來自於移除主機決策點：當 GPU 計算出的中間決策（intermediate decision）不需要經過 CPU 觀察與分支時，控制鏈（control chain）才能避免同步、複製與重新分派的開銷。

##### 4. 兩個可測量閘門

綜合兩項研究，作者提出 GPU 代理控制的兩個必要閘門（gates）：

1. **發射期限可行的同批供給（deadline-feasible cohort supply）**：必須有足夠數量的同路由事件在發射期限內到達，才能形成大小達到 \(K\) 的就緒同批。若此閘門不成立，GPU 執行機會（GPU opportunity）本身就不存在。
2. **觀察點放置（observation placement）**：即使同批供給存在，若每個 GPU 步驟的中間決策都必須回傳主機，則主機往返會侵蝕甚至抵消 GPU 的收益。

這兩個閘門必須同時滿足，GPU 代理控制才具有實用價值。

#### 與現有研究的比較

##### 1. 延續並聚焦於生產觀察

本研究與近期一項生產與開源特性分析 [26] 直接銜接。該研究發現代理式工作流程（agentic workflows）反覆跨越 CPU–GPU 邊界（CPU–GPU boundary），將主機協調（host orchestration）置於關鍵路徑上，並產生爆發性的 CPU 需求。這篇論文把這個高層級觀察轉化為兩個具體、可量化的系統問題：同批供給是否足夠？裝置端決策是否能避免主機往返？因此，它不是對 [26] 的替代，而是提供了一個形式化框架與測量工具，讓後續系統設計能夠回答「何時該把控制邏輯放到 GPU 上」。

##### 2. 相對於一般 GPU 卸載研究的差異

傳統 GPU 卸載（GPU offloading）研究通常關注大型核心、長時間執行的計算任務，例如深度學習訓練或科學模擬。本研究則專注於「小而重複的確定性轉換」，這類任務的單次執行時間可能極短，但頻率極高。因此，瓶頸不在於核心內部的平行度，而在於：

- 事件到達的時間分佈是否允許形成夠大的同批；
- 主機與裝置之間的同步與分派開銷是否被攤平。

這使得本研究的動態規劃與機制設計與傳統批量處理（batch processing）或串流處理（stream processing）有所不同：它強調「發射期限」而非「完成期限」，並且把「路由鍵條件」視為語義分組的約束。

##### 3. 方法論上的改進

相較於單純使用固定視窗或啟發式批次策略，本研究提出精確離線份額 \(P^*\) 作為機會上界，並以區域上界 \(U\) 作為快速評估工具。這種做法讓系統設計者能夠：

- 判斷固定視窗策略浪費了多少潛在機會；
- 評估改進排程器是否仍有顯著空間；
- 在投入複雜線上系統之前，先以離線分析篩選不適合 GPU 控制的場景。

此外，機制研究中的負向控制設計（固定巢狀裝置圖）是一個方法論亮點。許多 GPU 最佳化論文只報告加速比，但本研究透過對照實驗明確指出：加速來自「決策保留在裝置上」，而非「裝置端啟動本身」。

##### 4. 限制與未解問題

本研究的限制主要來自其刻意簡化的假設：

- **零服務時間與無限容量**：動態規劃忽略了核心執行時間與 GPU 佇列延遲，因此 \(P^*\) 是機會上界，而非實際可達成比例。
- **相等相對發射期限**：真實代理工作階段可能具有異質期限，例如某些工具呼叫需要更快回應。
- **路由鍵作為條件代理變數**：研究不處理語義融合（semantic fusion）或已驗證的可執行身分（verified executable identity），這在生產系統中涉及安全與正確性。
- **不涵蓋特權操作**：工具執行、VM 生命週期管理、分散式提交與復原都留在範圍外。
- **線上達成份額 \(A\) 尚未測量**：作者明確指出需要一個結合的有限線上執行環境（joined finite online runtime）來測量 \(A\)、CPU 置換（CPU displacement）與服務層級效益（service-level benefit）。

這些限制不是缺陷，而是研究範圍的刻意收斂；它們也指出了後續工作的必要方向。

#### 可重現性評估

##### 1. 資料集與實驗設定

本研究使用一個固定的 851 工作階段公開追蹤面板（pinned 851-session public trace panel）。雖然摘要與內文未明確指出該追蹤資料集的名稱或下載位置，但「公開追蹤面板」一詞暗示資料來自可公開取得的代理追蹤資料集。若作者後續提供資料集識別碼與前處理腳本，則追蹤回放實驗具有高度可重現性。

主要實驗參數清楚：100,000 目標活躍工作階段、\(K=256\)、50 ms 發射期限。動態規劃的輸入是事件的釋放時間、期限與路由鍵，這些都可以從追蹤資料衍生。然而，\(K_r(h, v, H)\) 的測量需要特定的硬體／執行環境配置與可接受基線，這部分若未公開基準實作，則難以完全複製。

##### 2. 演算法與程式碼

作者描述專用動態規劃（specialized dynamic program）可計算 \(P^*\)，但未在提供的片段中給出虛擬碼或實作連結。作為一篇由獨立研究者（Independent Researcher）撰寫、標示為 2026 年 8 月的預印本，目前無法確認是否伴隨開源程式碼。若未來釋出原始碼，將大幅提升可重現性；反之，讀者只能根據描述自行實作，並驗證是否得到相同的 \(F\)、\(P^*\)、\(U\) 數值。

機制研究部分涉及 CUDA 核心與四種具名 GPU 佈局。由於 GPU 佈局與核心實作細節未在片段中揭露，重現這 36 個配置的加速比需要完整的 CUDA 程式碼、編譯設定與硬體規格。14,557,440 個批次呼叫的測試規模龐大，顯示作者進行了系統性測試，但同樣需要公開測試框架才能完全複製。

##### 3. 模型權重與推論

本研究聚焦控制邏輯，而非 LLM 推論本身，因此不涉及模型權重（model weights）或訓練資料。這降低了部分重現門檻：只要追蹤資料與控制轉換語義可取得，就可以重現工作負載分析。然而，若「結果導出路由鍵」的推導依賴特定模型輸出格式，則需要相應的解析器與語義對照表。

##### 4. 整體可重現性評級

基於現有資訊，本研究在概念與數值層面具備可重現的潛力：主要參數、指標定義與實驗條件都已清楚陳述。但實際可重現性取決於作者是否公開：

- 追蹤資料集名稱與前處理流程；
- 動態規劃演算法的虛擬碼或參考實作；
- CUDA 機制研究的程式碼與硬體環境描述；
- 主機預言機（host oracle）的獨立實作細節。

在這些資源釋出之前，可重現性屬於「中等」：結果可信且可理解，但完整複製需要額外資訊。

#### 未來研究方向

##### 1. 結合有限線上執行環境以測量 \(A\)

最優先的後續工作是建立一個結合的有限線上執行環境（joined finite online runtime），實際測量線上達成份額 \(A\)。這需要引入真實核心服務時間、GPU 佇列、排程器決策延遲，以及 CPU 後備路徑。研究問題包括：在真實服務時間下，\(A\) 與 \(P^*\) 的差距有多大？哪些工作負載特徵會使差距擴大？排程器應該在何時放棄等待同批而直接走 CPU 後備？

##### 2. CPU 置換與服務層級效益量化

作者提出需要測量 CPU 置換（CPU displacement）與服務層級效益（service-level benefit）。未來研究可以設計對照實驗，比較純 CPU 控制平面、GPU 輔助控制平面，以及混合策略在總體擁有成本（TCO）、尾延遲（tail latency）、吞吐量與能源消耗上的差異。特別是對於資料中心規模的代理服務，即使單次控制轉換很小，累積的 CPU 節省可能相當可觀。

##### 3. 異質發射期限與非平穩工作負載

目前模型假設相等相對發射期限與平穩卜瓦松回放。未來可以放寬為異質期限、時變到達率，或具有相關性的突發流量。這將需要更複雜的線上排程演算法，例如基於剩餘期限的優先權、自適應視窗（adaptive windows），或學習式批次預測（learning-based batch prediction）。

##### 4. 已驗證的語義融合與安全邊界

本研究把結果導出路由鍵視為條件代理變數，而非可執行身分證明。未來需要發展形式化方法或執行期檢查，以驗證同一同批（cohort）內的事件確實可以被單一 GPU 核心安全處理，且不會因語義差異導致狀態污染或資訊洩漏。這涉及型別系統、沙箱化 GPU 核心，以及可能的安全證明。

##### 5. 特權工具與外部效應的裝置外處理

雖然本研究排除特權工具呼叫、VM 生命週期與外部效應，但未來系統仍需要處理這些操作。一個可能的方向是讓 GPU 負責純狀態演進與路由決策，然後由 CPU、DPU（Data Processing Unit）或專用硬體負責驗證與提交有序效應描述符（ordered effect descriptors）。這種分工可以保留 GPU 控制平面的效能優勢，同時維持安全與隔離。

##### 6. 分散式提交、復原與容錯

對於多 GPU 或多節點的代理服務，控制狀態的分散式提交（distributed commit）與復原（recovery）成為必要課題。未來研究可以探討如何在裝置端駐留決策的同時，維持可重現的執行軌跡、容錯與 exactly-once 語義。

##### 7. 硬體族群推論與跨平台泛化

本研究在四種具名 GPU 佈局上進行機制研究，但未從硬體族群推論（hardware-population inference）的角度泛化。未來可以建立一個模型，根據 GPU 架構、記憶體頻寬、PCIe 拓撲與核心啟動延遲，預測裝置端駐留決策的收益，並自動選擇最佳佈局。

##### 8. 與 LLM 推論排程的協同設計

最後，代理控制平面與 LLM 推論排程器並非獨立。未來可以研究兩者的協同設計：例如，當 LLM 推論批次正在形成時，是否可以同時預備下一輪控制轉換同批？控制平面的 GPU 執行是否會與推論核心競爭資源？這些問題對於端到端代理服務的效能至關重要。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於 LLM 代理服務在模型呼叫與工具呼叫之間反覆執行的小型確定性控制轉換，例如解析具型別結果、推進狀態機、檢查策略與預算狀態、選擇路由並發出下一個效應。作者問的是：這些控制路徑何時能夠累積足夠的並行工作，使其值得放到 GPU 上執行；以及當 GPU 計算出的路由決定保留在裝置上、不傳回主機時，效能與系統結構會有什麼改變。為此，論文提出「就緒同批邊界」來同時衡量「有沒有足夠可成批的任務」以及「觀察點該放在哪裡」這兩個先決條件。

**Q2：現有的固定視窗或主機中介 GPU 做法為何不足？**
A：固定視窗資格只會捕捉到剛好落在固定時間邊界內的事件，忽略了許多雖然跨越視窗邊界、但仍可在發射期限內被一起打包的相同路由事件；在主要實驗條件下，固定分區份額 F 僅 30.19%，而精確離線份額 P* 可達 43.00%。另一方面，傳統做法把 GPU 計算出的決定傳回主機，再由主機重新分派，會產生複製、同步、分支與重新發射的開銷；機制研究顯示，僅僅把四個位元組回傳主機就會顯著變慢。因此，現有方法要不是低估了可成批的 GPU 執行機會，就是額外增加了主機往返成本。

**Q3：為什麼這個問題對資料中心規模的 LLM 代理很重要？**
A：近期的生產與開源特性分析指出，代理式工作流程會反覆跨越 CPU–GPU 邊界，把主機協調放在關鍵路徑上，並造成突發性的 CPU 需求。如果能把確定性控制轉換卸載到 GPU，就有機會減少 CPU 佔用、降低推論干擾，並改善原始尾端延遲。透過量化「在發射期限內可形成的就緒同批」數量，營運者可以判斷投資 GPU 控制平面是否真的有足夠的工作負載支撐。

**Q4：什麼是就緒同批模型，它包含哪些關鍵量？**
A：就緒同批模型把每個控制事件描述為具有釋放時間、最新發射期限與路由鍵的單位，並針對每個路由與硬體／執行環境配置定義安全後綴閾值 K，即從 K 開始以上的同批大小都能打敗可接受基線。模型進一步區分四個份額：固定分區份額 F 衡量固定視窗能涵蓋的比例；精確離線份額 P* 是在零服務時間、無限容量與相等相對發射期限下的最佳值；區域上界 U 提供可行性評估；線上達成份額 A 則是實際線上執行環境能達到的比例。這四個量各自有明確的推論來源與邊界，避免把工作量特性、演算法表現與執行環境成效混為一談。

**Q5：專用動態規劃如何計算精確離線份額 P*？**
A：在零服務時間、無限容量以及相等相對發射期限的理想假設下，作者設計了一個專用動態規劃演算法，用來離線求解在期限內把相同路由事件打包成大小不低於 K 的同批之最大可涵蓋比例。這個演算法提供了一個可重現的工作量量測工具，讓後續比較有明確的理論上限。由於 P* 是精確最佳解而非啟發式估計，研究者可以準確評估固定視窗究竟浪費了多少潛在的 GPU 執行機會。

**Q6：機制研究有哪些關鍵設計選擇？**
A：機制研究把狀態轉換與路由本體固定，只改變「GPU 計算出的二元路由決定要在哪裡被觀察」這個變因，比較「保留在裝置端」與「回傳四個位元組到主機後重新分派」兩條路徑。它測試了四種具名 GPU 佈局，並在每種佈局下掃描多種配置，以觀察裝置端駐留決策的穩定優勢。此外，作者還加入了一個固定巢狀裝置圖作為負控制組，這個設計雖然把核心放在裝置上，卻沒有移除任何主機決策，用來確認效能提升來自於避免主機觀察，而非單純的裝置端發射。

**Q7：實驗使用了哪些資料集與評測方式？**
A：第一個實驗使用一個固定的 851 工作階段公開代理追蹤面板，以平穩卜瓦松過程進行前瞻性凍結回放，並將目標活躍工作階段擴展到 100,000，主要條件為 K=256 與 50 ms 發射期限。第二個是 CUDA 機制研究，在四種具名 GPU 佈局、36 個配置下比較裝置端駐留與主機中介路徑，並在五種佈局、60 個配置下測試固定巢狀裝置圖的負控制效果。所有 14,557,440 個批次呼叫都與獨立實作的主機神諦進行比對，確保裝置端駐留路徑沒有改變語意。

**Q8：論文的主要量化結果是什麼？**
A：在主要追蹤回放條件下，固定分區份額 F 為 30.19%，精確離線份額 P* 為 43.00%，區域上界 U 為 45.85%，精確打包挽回了固定視窗邊界所遺失機會的 81.83%。在機制研究中，裝置端駐留路徑在四種 GPU 佈局、全部 36 個配置下都更快，同佈局列中位數加速比介於 1.19× 到 2.39× 之間。相對地，固定巢狀裝置圖在五種佈局、全部 60 個配置下都更慢，證明單純把核心放到裝置上並不能解釋效能提升。

**Q9：有哪些消融或負控制實驗？**
A：最重要的負控制是「固定巢狀裝置圖」：它雖然使用裝置端圖形發射，卻沒有移除任何主機決策，結果在所有 60 個配置下都更慢，說明裝置端發射本身並不足夠，關鍵在於避免主機往返。另一個控制是主機神諦比對，橫跨兩種可接受機制與 14,557,440 個批次呼叫，確認裝置端駐留路徑的輸出與主機實作完全一致。區域上界 U 則用來評估線上達成份額 A 還有多少理論空間可以逼近離線最佳值 P*。

**Q10：GPU 代理控制適合哪些實際應用場景？**
A：最適合的是高並行、控制轉換輕量且反覆出現的代理服務，例如互動式助理、多步驟工具使用或需要快速路由決策的對話系統。當大量工作階段同時活躍，並且在每次模型或工具呼叫後都需要執行解析、狀態更新與效應發射時，GPU 才有機會累積足夠的就緒同批。相對地，如果控制邏輯高度動態、需要特權憑證或涉及虛擬機生命週期管理，則不在本文建議的 GPU 執行範圍內。

**Q11：在產品化時需要考慮哪些系統設計議題？**
A：首先必須建立一個結合有限服務時間與 CPU 回退機制的線上執行環境，才能實際測量線上達成份額 A、CPU 佔用與服務水準效益。其次，GPU 應只負責純狀態演變與路由決策，特權工具執行、虛擬機生命週期與分散式提交／復原仍應由 CPU 或 DPU 負責驗證與提交。最後，由於結果導出的路由鍵只是條件代理變數，並非可執行身分證明，產品必須額外確保相同路由鍵的事件確實具有相同的可執行語意。

**Q12：這項研究可能對領域帶來什麼影響？**
A：它為「把 LLM 代理控制卸載到 GPU」這個命題提供了兩個可量化的先決閘門：期限可行的同批供給與觀察點放置，讓討論從定性直覺轉向可測量的證據。研究也指出固定視窗會遺漏大量可排程工作，並量化了主機往返的具體代價。未來的代理執行環境可以依據這些邊界，決定何時值得投資 GPU 控制平面，並在設計上把裝置端駐留決策視為常態而非特例。

**Q13：論文承認了哪些限制？**
A：動態規劃計算 P* 時假設零服務時間、無限容量與相等相對發射期限，因此它是一個理想化的離線上界，而非真實線上系統的效能保證。追蹤回放採用平穩卜瓦松過程與前瞻性凍結面板，可能無法完全反映非平穩、突發或對抗性工作負載。機制研究也僅測量控制轉換本身的延遲，並未涵蓋端到端完成服務水準、CPU 佔用或對推論的干擾。

**Q14：哪些情況下會出現沒有合格同批的失敗 regime？**
A：完整網格實驗指出，當並行度太低、發射期限太緊，或相同路由鍵的事件密度不足時，就可能無法形成大小達到 K 的就緒同批。如果事件到達過於稀疏，或者期限短於同批形成所需等待時間，GPU 執行機會就會崩潰。此外，若路由鍵過於細碎或隨時間快速變化，也會讓可打包的群組數量大幅減少，導致 GPU 控制平面不具經濟效益。

**Q15：未來可以朝哪些方向延伸？**
A：作者明確呼籲建立一個結合有限服務時間的線上執行環境，以實際測量線上達成份額 A、CPU 佔用、精確效應、任務效用與服務水準效益。另一個方向是把 CPU 回退與有限容量納入排程模型，讓 P* 與 U 能更貼近真實部署。最後，需要發展額外的安全機制，使得 GPU 計算出的路由鍵能夠被驗證為真正的可執行身分，同時又不破壞裝置端駐留所帶來的效能優勢。

## 實務應用指南

### 適用場景

1. **高並發 LLM 代理閘道器（Agent Gateway）**  
   當服務同時維護數萬至數十萬個活躍工作階段，且每個工作階段在模型呼叫與工具呼叫之間需要反覆執行「解析結果 → 更新狀態 → 選擇路由 → 發出效應」時，可將控制路徑搬上 GPU，以減少 CPU 突發負載與主機往返。例如客服機器人、程式碼助手或個人化推薦代理的後端排程器。

2. **低延遲路由與條件分支引擎**  
   適合需要根據模型輸出在極短時間內決定下一步的場景，例如對話狀態機、多工具選擇（tool routing）、許可權檢查或預算閘道。若路由決策可在 GPU 上完成並保留在裝置端，就能避免「GPU → CPU → GPU」的重新分派延遲。

3. **事件驅動的代理編排平台**  
   在事件釋放後有明確發射期限（如 50 ms）的系統中，可用就緒同批模型來判斷「同一時段內是否有足夠多同群組事件可打包成 K=256 的批次」。這對即時推薦、互動式遊戲 NPC、IoT 規則引擎等需要嚴格時限的場景特別有用。

4. **GPU 卸載控制平面的原型驗證**  
   若團隊已觀察到代理式工作流程在 CPU–GPU 邊界反覆切換造成瓶頸，可套用本文的固定分區份額 F、精確離線份額 P* 與區域上界 U，量化「還有多少控制工作可被 GPU 吸收」，作為是否投資裝置端控制鏈的數據依據。

5. **大規模追蹤資料的批次重播分析**  
   擁有公開或內部代理追蹤（trace）的團隊，可透過平穩卜瓦松回放與精確打包動態規劃，評估不同目標活躍工作階段數、K 值與發射期限組合下的可排程比例，進而決定硬體與排程參數。

### 實作前置條件

**資料條件**
- 必須能取得或產生具時間戳記的代理追蹤，包含事件釋放時間、結果導出路由鍵、以及可接受的發射期限。公開追蹤面板（如本文 851 工作階段面板）是可行的起點。
- 路由鍵必須是「條件代理變數」，也就是能用來分組同質控制轉換，但不能直接視為可執行身分證明；需要額外驗證對應的狀態轉換與效應描述子在目標 GPU 實作中語義等價。

**運算條件**
- 需有可執行 CUDA 的 GPU 環境，以便進行裝置端駐留路徑與主機中介路徑的對照實驗。
- 需有足夠 CPU 資源執行離線動態規劃與追蹤回放；精確打包雖是離線計算，但對大規模追蹤仍需記憶體與運算時間。
- 線上達成份額 A 的測量需要一個可實際運行的有限服務環境，不能僅靠離線模擬。

**技能條件**
- 熟悉 GPU 核心設計、CUDA graph、記憶體同步與批次發射機制。
- 具備排程理論基礎，能理解發射期限、零服務時間模型、動態規劃與上界分析。
- 能區分「純控制狀態演進」與「特權工具呼叫 / VM 生命週期 / 分散式提交」等必須留在 CPU 或 DPU 的步驟。
- 具備系統測量能力，能獨立實作主機 oracle 並驗證所有批次呼叫的軌跡一致。

### 實作步驟建議

1. **定義控制轉換的執行契約**  
   先劃定哪些步驟屬於「具型別結果的確定性控制轉換」，哪些屬於模型推論、工具執行、外部效應提交或任意 Python 邏輯。後者應排除在 GPU 控制鏈之外。

2. **建立追蹤與事件模型**  
   從現有代理執行環境收集事件，記錄釋放時間、發射期限、路由鍵與狀態依賴。若使用公開追蹤，需進行前瞻性凍結（prospectively frozen）取樣，避免事後挑選偏差。

3. **計算就緒同批邊界指標**  
   對每個路由與硬體配置，測量安全後綴 K；接著計算固定分區份額 F、精確離線份額 P*、區域上界 U。使用本文的專用動態規劃取得 P*，並與固定視窗資格比較，評估精確打包可挽回多少遺失機會。

4. **設計裝置端駐留機制**  
   將 GPU 計算二元決策保留在裝置記憶體，避免回傳四個位元組到主機後重新分派。對照四種具名 GPU 佈局，測量裝置端駐留路徑與主機中介路徑的延遲比率，並以獨立主機 oracle 驗證所有批次呼叫軌跡一致。

5. **排除負面控制干擾**  
   確認「固定巢狀裝置 graph 但未移除主機決策」的配置在所有測試中皆較慢，避免誤將效能提升歸因於單純的 device launch，而非觀察點放置。

6. **建置線上有限運行環境**  
   將離線分析與裝置端機制整合為可運行的線上系統，測量線上達成份額 A、CPU 置換效益、原始尾端延遲、精確效應、任務效用以及對推論的干擾。

7. **迭代調參與 fallback 設計**  
   根據 A 與服務層級指標調整 K、發射期限與批次策略；同時保留 CPU fallback，當就緒同批不足或涉及特權操作時切回主機執行。

### 潛在風險與注意事項

- **將路由鍵誤認為可執行身分證明**  
  結果導出路由鍵只是條件代理變數，不能直接保證對應的狀態轉換在所有工作階段中語義一致。若未驗證，可能導致 GPU 上執行錯誤轉換。建議建立獨立的主機 oracle 與軌跡比對機制，像本文一樣驗證所有批次呼叫。

- **混淆發射期限與完成 SLO**  
  本文的 50 ms 是最新發射時間，不是完成服務水準。若把發射期限直接當成端到端延遲目標，會低估排隊與核心服務時間的影響。線上系統必須額外測量完成時間與尾端延遲。

- **忽略零服務時間與無限容量的理想化假設**  
  P* 是在零服務時間、無限容量與相等相對發射期限下計算的離線上界。實際線上達成份額 A 通常會低於 P*，不能直接以 P* 作為產品承諾。

- **過度樂觀估計裝置端加速**  
  雖然裝置端駐留路徑在 36 個配置中皆較快，但中位數比率從 1.19× 到 2.39× 不等，且實際收益取決於觀察點放置。若只是把決策搬到 GPU 卻仍保留主機分支，可能反而變慢。

- **安全邊界模糊**  
  GPU 控制鏈應僅處理純狀態演進與路由決策，特權工具呼叫、VM 生命週期管理、分散式提交與復原仍應由 CPU 或 DPU 負責，並透過效應描述子進行有序驗證與提交。

- **線上測量不足**  
  離線分析無法取代真實負載下的 A、CPU 位移與服務層級效益測量。建議在漸進式上線過程中同時監控推論干擾與控制鏈延遲。

### 與其他技術的整合建議

- **與現有 LLM 推論服務整合**  
  將 GPU 控制鏈視為推論後處理器（post-processor）與下一輪推論前處理器（pre-processor）之間的批次階段。控制核心可與推論核心共用 GPU，但需隔離記憶體與串流，避免長推論 kernel 阻塞短控制 kernel。

- **與 CPU 編排器 / Kubernetes 整合**  
  CPU 端負責生命週期管理、工具認證、外部效應提交與異常處理；GPU 端負責純狀態演進與路由。兩者透過效應描述子與事件佇列溝通，形成「GPU 控制 + CPU 提交」的分層架構。

- **與追蹤與可觀測性系統整合**  
  將就緒同批指標（F、P*、U、A）匯出至 Prometheus / Grafana，並把每個批次的事件軌跡與主機 oracle 比對結果寫入日誌，作為線上正確性與效能監控依據。

- **與現有 agent framework（如 LangGraph、AutoGen、Temporal）整合**  
  可將控制轉換單元對應到框架中的「節點轉換」或「工作流步驟」，但需先將框架的任意 Python 節點限制在確定性、型別化的子集，再標記哪些節點符合 GPU 執行契約。

- **與 DPU / 機密運算整合**  
  對於需要特權驗證的效應描述子，可交由 DPU 或機密 VM 執行有序提交；GPU 僅產生描述子，不直接持有雲端憑證或執行外部副作用。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「LLM 代理在模型與工具之間反覆切換」這個直覺出發，理解為何控制路徑會成為資料中心瓶頸；接著聚焦兩個核心問題：「有沒有足夠多同類事件可以在期限內一起發射？」以及「GPU 算出的決定是否一定要回傳 CPU？」不必一開始就深入動態規劃，但應記住「發射期限不等於完成期限」與「路由鍵不是可執行身分證明」這兩個重要提醒。

**AI 工程師**  
請重點閱讀就緒同批模型、K 值測量、精確打包與裝置端駐留機制。你會需要判斷自己服務中的控制轉換是否符合「確定性、型別化、無副作用」的執行契約，並評估將路由決策保留在 GPU 上能否減少主機往返。實作時請務必建立獨立 oracle 驗證軌跡，並預留 CPU fallback 路徑。

**研究人員**  
本文的貢獻在於將 GPU 代理控制拆解為「供給邊界」（就緒同批）與「觀察邊界」（決策放置）兩個可測量閘門，並提供精確離線份額 P* 的演算法與公開追蹤證據。建議關注動態規劃的正確性條件、P* 與 U 之間的間隙、以及線上達成份額 A 的測量方法；未來可延伸至非零服務時間、有限容量、不相等發射期限與分散式提交等設定。

**產品經理**  
請把本文視為一份「可行性量化報告」：它告訴你在理想條件下，GPU 控制鏈最多能覆蓋多少控制工作（P*=43.00%），以及固定視窗浪費了多少機會（精確打包可挽回 81.83%）。決策重點在於：你的服務是否有足夠並發與明確發射期限？是否有工程資源建置裝置端駐留與線上 A/B 測量？若兩者皆為肯定，再進入產品化規劃；若否，現階段應優先投資 CPU 編排最佳化與追蹤基礎建設。
