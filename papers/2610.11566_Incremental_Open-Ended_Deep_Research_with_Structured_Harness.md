## 摘要翻譯

既有開放式深度研究 (Open-Ended Deep Research, OEDR) 系統主要從零開始生成報告，在需要隨著新資訊出現而持續維護研究報告的情境下效率不佳。我們提出增量式開放式深度研究 (Incremental Open-Ended Deep Research, Incremental-OEDR)，這是一種將報告視為演化中的研究狀態 (Evolving Research State) 的研究設定，透過保留有效知識、修訂過時或不完整的內容，並納入新可用的資訊來進行增量更新 (Incremental Update)。為支援此設定，我們提出結構化框架 (Structured Harness)，將報告表示為由大綱 (Outline)、章節 (Section) 與支持證據 (Supporting Evidence) 所組成的結構化集合，並提供結構化檢索 (Structured Retrieval)、持久化結構化證據池 (Persistent Structured Evidence Pool) 與結構化生成 (Structured Generation)，以實現選擇性報告更新 (Selective Report Updating) 與證據重用 (Evidence Reuse)。我們進一步建立一個橫跨十年的時間評估框架 (Temporal Evaluation Framework)，透過單步任務 (Single-Step Task, SST) 與長鏈任務 (Long-Chain Task, LCT) 來評估個別轉換與長期更新鏈中的增量更新。在開源配置 (Open-source Configuration, OC) 與專有配置 (Proprietary Configuration, PC) 下，於 DeepResearch 基準測試 (DeepResearch Bench) 與 DeepConsult 上進行的廣泛實驗顯示，增量式開放式深度研究在維持具競爭力的報告品質 (Report Quality) 的同時，大幅提升了報告連續性 (Report Continuity) 並降低了研究成本 (Research Cost)。相較於 OEDR，在 DeepResearch 基準測試上，其內容層級 ROUGE-L F1 (Content-level ROUGE-L F1) 最高高出 0.51，大綱層級精確匹配 F1 (Outline-level EM F1) 最高高出 0.63，Token 消耗 (Token Consumption) 降低 33%，搜尋呼叫次數 (Search Calls) 減少 61%。更多詳情請參閱我們的專案頁面 (Project Page)：https://ioedr-project.github.io/。

### 核心貢獻
- 提出嶄新研究設定「增量式開放式深度研究 (Incremental-OEDR)」，將研究報告視為演化中的研究狀態，支援增量更新而非從零生成，解決既有 OEDR 系統在持續維護報告情境下的效率瓶頸
- 設計結構化框架 (Structured Harness)，以大綱、章節與支持證據的結構化表示為基礎，整合結構化檢索、持久化結構化證據池與結構化生成三大元件，實現選擇性報告更新與證據重用
- 建立橫跨十年的時間評估框架 (Temporal Evaluation Framework)，涵蓋單步任務 (SST) 與長鏈任務 (LCT) 兩種設定，全面評估個別轉換與長期更新鏈中的增量更新效能
- 在 DeepResearch 基準測試與 DeepConsult 上，於開源配置 (OC) 與專有配置 (PC) 下皆驗證能維持競爭性報告品質，同時顯著提升報告連續性並降低研究成本（最高達 33% Token 消耗降低與 61% 搜尋呼叫次數減少）

### 適合對象
從事大型語言模型 (Large Language Models, LLMs) 應用、自動化研究系統與深度研究代理 (Deep Research Agent) 開發之研究人員與工程師；對資訊檢索、報告生成、知識維護與增量學習等議題感興趣之學者；以及需要持續追蹤並更新領域研究報告之產業分析師、政策研究員與知識工作者。

## 深度分析

#### 方法論解析

本文提出了一個全新的研究設定——增量式開放式深度研究（Incremental Open-Ended Deep Research, Incremental-OEDR），並設計了對應的技術框架「結構化框架」（Structured Harness）。整個方法論的核心思想在於將研究報告視為一個**演化中的研究狀態**（Evolving Research State），而非一次性產生的靜態產物。

**問題定義的形式化**

給定先前版本的研究報告 $R_t$，系統的目標是產出下一版本 $R_{t+1}$，過程中需同時完成三項操作：（1）保留仍然有效的既有知識；（2）修訂過時或不完整的內容；（3）整合新湧現的資訊。這種形式化跳脫了傳統 OEDR 系統「從零開始」（from scratch）的研究範式，將研究流程從單次生成轉變為持續維護。

**結構化框架（Structured Harness）的三大元件**

1. **結構化表示（Structured Representation）**：將報告拆解為三層結構——大綱（Outline）、章節（Section）、支持證據（Supporting Evidence）。這種層級化設計使後續操作能夠以最小粒度進行，避免對整份報告的粗粒度重寫。

2. **結構化檢索（Structured Retrieval）**：允許代理（agent）選擇性地存取相關的報告元件及其對應證據，而非一次性載入整份報告。這對於大型研究報告特別關鍵，能有效控制上下文視窗的使用。

3. **持久化結構化證據池（Persistent Structured Evidence Pool）**：這是整個框架最具創新性的元件之一。它不僅儲存先前使用過的證據，還支援**變更偵測**（change detection）與**證據重用**（evidence reuse）。當新資訊進入時，系統能判斷哪些證據仍然有效、哪些需要更新，避免重複檢索相同內容。

4. **結構化生成（Structured Generation）**：使代理能直接操作對應的報告元件，同時保留未受影響的內容與既有結構。這與傳統的全文重新生成形成鮮明對比。

**兩種既有範式的對比**

論文將現有 OEDR 系統區分為兩類：**OEDR 工作流**（OEDR workflow）採用預定義的研究管線，雖然穩定但缺乏對中間發現的適應性；**OEDR 代理**（OEDR agent）則賦予大型語言模型（LLMs）動態規劃、搜尋與迭代修正的能力，靈活性更高但成本也更高。結構化框架本質上是介於兩者之間的第三條路徑——既保留代理的自主性，又透過結構化介面約束操作範圍。

**時間評估框架**

論文設計了橫跨十年的評估框架，包含兩種任務設定：
- **單步任務（Single-Step Task, SST）**：評估單次轉換後的增量更新品質
- **長鏈任務（Long-Chain Task, LCT）**：評估連續多次更新後的累積效果

這種設計反映了真實應用中報告需要長期維護的特性，避免了僅評估單次更新而忽略長期漂移的問題。

#### 實驗數據解讀

**評估指標的三維設計**

論文從三個互補視角評估系統表現：

1. **報告品質（Report Quality）**：以 ECAR 指標衡量最終報告的整體品質
2. **報告連續性（Report Continuity）**：衡量更新後報告與先前版本的結構與內容一致性
3. **研究成本（Research Cost）**：包含每份報告的 Token 消耗（Token Consumption）與搜尋呼叫次數（Search Calls）

**關鍵實驗結果**

在 DeepResearch Bench 的開源配置（Open-source Configuration, OC）下，Incremental-OEDR 展現出顯著優勢：

| 指標 | 改善幅度 | 意義 |
|------|---------|------|
| 內容層級 ROUGE-L F1 | ↑0.51 | 內容連續性大幅提升 |
| 大綱層級精確匹配 F1 | ↑0.63 | 結構穩定性顯著增強 |
| Token 消耗 | ↓33% | 計算成本有效降低 |
| 搜尋呼叫次數 | ↓61% | 外部資訊檢索大幅減少 |

**結果的深層意涵**

- **品質維持**：報告品質（ECAR）在十年跨度內維持與 OEDR 相當甚至更佳的水準，這證明了增量更新並非以犧牲品質換取效率。
- **連續性的雙重提升**：內容層級與大綱層級的雙重改善顯示，結構化框架不僅保留了文字內容，還維持了報告的整體架構，這對長期維護至關重要。
- **成本的非對稱降低**：搜尋呼叫降低 61% 但 Token 消耗僅降低 33%，暗示主要的成本節省來自於減少外部資訊檢索，而非模型推論本身。這反映了「證據重用」機制的有效性——許多先前檢索的證據在後續更新中仍然有效。

**兩種配置的對比驗證**

論文同時在開源配置（OC）與專有配置（Proprietary Configuration, PC）下進行實驗，並使用 DeepResearch Bench 與 DeepConsult 兩個基準測試。這種雙基準、雙配置的設計增強了結論的泛化性，顯示 Incremental-OEDR 的優勢並非依賴特定模型或任務。

**時間維度的穩健性**

從 Figure 1(a) 可以觀察到，ECAR 分數在 2016 至 2025 年間維持穩定，這意味著增量更新機制對不同時間段的資訊變化具有良好的適應性，不會因時間推移而累積誤差。

#### 與現有研究的比較

**定位於研究譜系中**

本文明確定位於填補 OEDR 研究中的一個關鍵缺口：現有系統（無論是工作流還是代理範式）都聚焦於一次性研究任務，而忽略了現實中報告需要持續維護的需求。這與軟體工程中從「瀑布式開發」轉向「持續整合」的演進邏輯相似。

**相較於 OEDR 工作流的改進**

OEDR 工作流（如 Han et al., 2025）雖然結構清晰，但缺乏對中間發現的適應能力。結構化框架保留了工作流的結構化優勢，但透過證據池與選擇性更新機制，賦予了系統對新資訊的響應能力。

**相際於 OEDR 代理的改進**

OEDR 代理（如 Shao et al., 2024; Patel et al., 2025）雖然靈活，但每次運行都從零開始，導致大量重複計算。結構化框架透過持久化證據池與結構化生成，使代理能「記住」先前的研究成果，避免重複勞動。

**方法論的侷限性**

儘管成果顯著，仍存在以下潛在限制：

1. **結構化假設的依賴**：整個框架假設報告可以被清晰地分解為大綱、章節與證據三層結構。對於高度非結構化或創意性寫作任務，這種假設可能不成立。

2. **證據池的儲存成本**：持久化證據池雖然減少了搜尋呼叫，但本身需要儲存空間與管理成本。隨著更新次數增加，證據池可能膨脹，需要額外的剪枝或摘要機制。

3. **變更偵測的準確性**：框架的有效性高度依賴於能否準確判斷哪些內容「過時」或「不完整」。若判斷錯誤，可能導致有效內容被錯誤刪除或過時內容被錯誤保留。

4. **評估框架的範圍**：雖然橫跨十年，但基準測試（DeepResearch Bench、DeepConsult）仍屬特定領域。對於醫學、法律等高度專業化的領域，框架的適用性有待驗證。

5. **與人類專家的協作**：論文未深入探討 Incremental-OEDR 與人類專家協作的可能性。在實際應用中，專家的審核與修正往往是不可或缺的環節。

#### 可重現性評估

**正面因素**

- **專案頁面公開**：論文提供了專案頁面（https://ioedr-project.github.io/），這通常包含程式碼、資料與示範的連結
- **使用公開基準**：DeepResearch Bench 與 DeepConsult 均為公開可用的評測基準
- **雙配置實驗**：同時提供開源與專有配置的結果，使不同資源條件的研究者都能復現
- **作者隸屬透明**：作者隸屬於小紅書（Xiaohongshu Inc.）與浙江大學（Zhejiang University），便於學術聯繫

**潛在的可重現性挑戰**

1. **專有配置的依賴**：專有配置（PC）的結果依賴於特定的商業模型 API（如 GPT-4 等），這些 API 的版本更新可能導致結果難以精確復現。

2. **證據池的實作細節**：持久化結構化證據池的具體實作方式（如儲存格式、索引結構、變更偵測演算法）對於復現至關重要，但論文中提供的細節有限。

3. **評估資料的時間敏感性**：橫跨十年的評估需要特定時間點的資料快照，這些資料的取得與處理方式可能影響結果。

4. **缺乏明確的開源時程**：雖然有專案頁面，但論文中未明確承諾程式碼與資料的開源時程與許可證類型。

**改進建議**

為提升可重現性，未來工作應考慮：（1）提供結構化框架的開源實作；（2）釋出時間評估框架的具體資料集；（3）詳細記錄證據池的資料結構與操作介面；（4）提供基準測試的評估腳本與評分標準。

#### 未來研究方向

**短期延伸（1-2 年）**

1. **多模態研究報告**：目前框架聚焦於文字報告，可延伸至包含圖表、影像的多模態研究產物。這需要擴展結構化表示以支援非文字元素。

2. **人機協作機制**：設計讓人類專家能有效介入增量更新流程的介面，例如標記需要修訂的章節、提供領域知識的注入點等。

3. **證據池的智慧管理**：研究自動化的證據剪枝、摘要與優先級排序機制，避免證據池無限膨脹。

**中期探索（3-5 年）**

4. **跨領域泛化**：將 Incremental-OEDR 應用於醫學、法律、財經等專業領域，驗證框架在不同知識更新模式下的適應性。

5. **因果驅動的更新**：現有框架以「內容變更」為驅動，可探索以「因果關係變化」為驅動的更新機制，使報告能追蹤更深層的知識演進。

6. **多代理協作**：在結構化框架中引入多個專門化代理（如證據收集代理、章節修訂代理、品質檢查代理），透過分工提升更新效率與品質。

**長期願景（5 年以上）**

7. **自主演化的研究系統**：結合 Incremental-OEDR 與終身學習（lifelong learning）技術，構建能自主追蹤特定領域知識演進的研究系統。

8. **知識圖譜整合**：將結構化框架與知識圖譜技術結合，使報告更新能利用結構化的領域知識進行推理，而不僅僅是文字層級的修訂。

9. **可解釋性與可信度**：研究如何讓 Incremental-OEDR 的更新決策更具可解釋性，例如清楚標示每處修改的依據，增強使用者對系統的信任。

10. **基準測試的標準化**：推動 Incremental-OEDR 評估基準的標準化，建立類似 GLUE 或 SuperGLUE 的社群共識基準，促進該領域的系統性發展。

**跨領域影響**

Incremental-OEDR 的理念不僅限於研究報告生成，還可應用於：（1）軟體文件維護；（2）政策文件追蹤；（3）學術文獻綜述更新；（4）企業知識庫管理。這些應用場景的共同特點是「資訊持續演進、結構相對穩定」，正是 Incremental-OEDR 的優勢所在。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼「增量式」深度研究是必要的？**
A：論文指出，現有的開放式深度研究（OEDR）系統主要採用「從零開始生成報告」的單次性研究模式，但現實中許多研究報告並非靜態產物，而是需要隨著新資訊出現而被持續維護與更新的「演化中的研究狀態」（Evolving Research State）。例如 AI 產業分析需要納入新發布的模型與技術，經濟報告則需隨新統計數據更新。論文中提出的「增量式開放式深度研究」（Incremental-OEDR）正是為了處理這種需要週期性回訪、保留既有結構並融入新知的場景，使研究報告能像活文件一樣持續演進，而非每次都從原始查詢重新生成。

**Q2：為什麼現有的 OEDR 工作流（workflow）與 OEDR 代理（agent）兩種範式都無法有效處理增量情境？**
A：OEDR 工作流依賴預先定義的研究管線，由初始大綱引導證據檢索與報告生成，雖然簡單可預測，但隨著檢索證據量增加，這類剛性管線對中間發現的適應性有限；OEDR 代理雖能動態規劃、搜尋並迭代精煉研究流程，靈活度較高，但兩者本質上都將每次新報告視為獨立任務，從原始查詢重新開始研究。當既有報告大部分內容仍然有效時，重新執行完整檢索與生成流程會在未變動的內容上浪費大量搜尋與模型運算資源，且每次獨立執行可能產生結構與內容差異極大的報告，無法維持報告的連貫性與穩定性。

**Q3：為什麼「報告連續性」（Report Continuity）這個問題值得學界重視？**
A：在許多實務場景中，研究報告的價值不僅在於當下的內容品質，更在於其作為長期知識資產的可累積性——使用者期望一份報告能隨時間推移保持結構穩定、內容連貫，並能清楚標示哪些是新加入、哪些是修訂過的知識。若每次更新都產生結構迥異的新報告，使用者將難以追蹤知識演進，也無法有效累積前期研究的成果。論文將「報告連續性」提升為與「報告品質」並列的核心評估維度，反映出學界與業界開始意識到，在動態知識環境中，研究的可持續維護能力與一次性生成能力同樣關鍵。

**Q4：Structured Harness 的核心方法架構是什麼？它由哪些元件組成？**
A：Structured Harness 的核心是將報告表示為「大綱（Outline）、章節（Section）、支持證據（Supporting Evidence）」三層結構化集合，並圍繞此表示提供三項互補能力：結構化檢索（Structured Retrieval）讓代理能選擇性存取相關報告元件及其證據；持久化結構化證據池（Persistent Structured Evidence Pool）持續儲存並刷新先前使用的證據，以支援變更偵測與證據重用；結構化生成（Structured Generation）則讓代理直接操作對應的報告元件，在保留未受影響內容與既有結構的前提下進行選擇性更新。這三項能力共同將 OEDR 從「無約束的重新生成」轉變為「結構化的研究重用、證據刷新與報告編輯」流程。

**Q5：相較於既有方法，Structured Harness 最關鍵的創新點為何？**
A：最關鍵的創新在於「將報告本身視為可操作的結構化物件」，而非單純的最終輸出文字。透過將報告拆解為大綱、章節與證據的結構化集合，系統得以在元件層級進行精細的檢索、重用與更新，而非以整篇文件為單位進行粗粒度的重新生成。持久化證據池的設計更進一步讓系統能追蹤證據的時效性與來源，支援跨時間點的變更偵測，這是既有 OEDR 系統所缺乏的能力，也是實現「增量更新」而非「重新生成」的基礎。

**Q6：為何作者選擇「結構化表示 + 三項能力」這樣的設計組合，而非採用單一機制？**
A：此設計反映了「表示（representation）」與「操作（operation）」必須相互匹配的工程原則：單純的結構化表示若缺乏對應的檢索、證據管理與生成機制，則無法被代理有效利用；反之，僅有操作機制而無結構化表示，則無法支援元件層級的選擇性更新。作者將三項能力設計為互補且獨立的元件，是因為它們各自對應增量更新流程中的不同子任務——檢索決定「更新哪些部分」、證據池決定「如何重用與刷新證據」、生成決定「如何產出修訂內容」，三者缺一不可，共同構成完整的增量研究閉環。

**Q7：實驗採用了哪些基準測試與評估配置？**
A：實驗在兩個基準測試上進行：DeepResearch Bench 與 DeepConsult，並分別於開源配置（Open-source Configuration, OC）與專有配置（Proprietary Configuration, PC）下評估，以驗證方法在不同模型規模與能力下的泛用性。評估框架橫跨十年時間軸，並設計兩種任務型態：單步任務（Single-Step Task, SST）評估單次轉換後的增量更新表現，長鏈任務（Long-Chain Task, LCT）則評估連續多次更新後的長期演化表現，兩者互補以兼顧短期與長期更新品質。

**Q8：相較於傳統 OEDR，Incremental-OEDR 的主要量化成果為何？**
A：在 DeepResearch Bench 的開源配置下，Incremental-OEDR 在內容層級 ROUGE-L F1 上提升達 0.51，在大綱層級精確匹配 F1（EM F1）上提升達 0.63，顯示其在維持報告結構與內容連續性方面有顯著優勢；同時在研究成本方面，Token 消耗降低達 33%，搜尋呼叫次數降低達 61%，證明增量更新能大幅減少冗運算。更重要的是，這些效率提升並非以犧牲品質為代價——報告品質（ECAR）在多年時間軸上仍維持與 OEDR 相當甚至更佳的水準，顯示「又快又穩」是可以同時達成的。

**Q9：論文中是否進行了消融實驗（Ablation Study）來驗證各元件的貢獻？**
A：根據所提供的全文內容，作者主要聚焦於 Incremental-OEDR 與傳統 OEDR 的整體對比，並透過圖表展示報告品質、報告連續性與研究成本三個面向的綜合表現。雖然所提供的摘錄未完整呈現消融實驗細節，但從方法論的設計來看，Structured Harness 的三項能力（結構化檢索、持久化證據池、結構化生成）各自對應不同子任務，理論上應可透過逐一移除來評估各元件的邊際貢獻，這也是讀者期待在完整論文中看到的進一步驗證。

**Q10：Incremental-OEDR 在實際應用上有哪些典型場景？**
A：典型的應用場景包括需要長期追蹤的產業分析報告（如 AI、半導體、新能源等快速演進領域）、經濟與政策研究報告（需隨新統計數據與政策調整更新）、學術綜述（隨新論文發表持續整合最新研究）、以及企業內部的市場競爭情報與技術趨勢報告。在這些場景中，報告的「時效性」與「可累積性」同樣重要，而 Incremental-OEDR 正好滿足了「保留歷史脈絡、融入新知、降低維護成本」的三重需求。

**Q11：將此方法產品化時需要考量哪些工程與產品面向？**
A：產品化時首先需考量證據池的儲存與索引成本——隨著報告數量與更新次數增加，持久化結構化證據池的規模可能快速膨脹，需要設計有效的過期證據清理與壓縮機制。其次是更新觸發機制：產品需決定是採用定期排程、主動偵測新資訊，還是由使用者手動觸發更新，並設計相應的使用者介面來呈現「哪些內容被保留、哪些被修訂、哪些是新加入」的差異化視圖。此外，如何在維持結構穩定性的同時允許使用者進行大幅度的重新組織，也是產品設計上需要權衡的取捨。

**Q12：這項研究對深度研究與 LLM 代理領域的整體影響為何？**
A：這項研究將深度研究的焦點從「單次高品質生成」擴展到「長期可維護性」，為整個領域引入了「研究狀態演化」的新視角，可能促使後續研究重新思考 OEDR 系統的設計目標——不再僅追求單次報告的完美，而是追求報告生命週期中的整體效益。同時，Structured Harness 所提出的「結構化表示 + 元件級操作」範式，也可應用於其他需要長期維護的 LLM 應用場景（如個人知識庫、持續學習系統），具有方法論上的遷移價值。

**Q13：論文中承認了哪些研究限制？**
A：根據所提供的全文內容，論文主要聚焦於方法提出與整體效益驗證，但從 Incremental-OEDR 的設計特性可推論其潛在限制包括：對於結構變動幅度極大的報告（例如主題大幅轉移），增量更新的效益可能不如重新生成；評估框架橫跨十年，但實際可用的歷史資料覆蓋範圍可能受限；此外，方法效能高度依賴結構化表示的品質，若初始報告的結構化不夠完善，後續增量更新的效果也會受到影響。

**Q14：在哪些情況下 Incremental-OEDR 可能會失敗或表現不佳？**
A：當既有報告的結構與新需求差異過大時（例如從「2020 年 AI 產業分析」更新為「2025 年 AI 與量子計算交叉分析」），增量更新可能難以有效重用舊有結構，反而需要大量重組，此時從零生成可能更有效率。此外，若新資訊與既有內容存在矛盾或需要根本性的觀點翻轉，單純的「保留 + 修訂 + 新增」三操作可能無法妥善處理，需要更強的衝突解決與觀點重評機制。對於高度依賴即時資訊、主題快速變化的場景，證據池的刷新延遲也可能導致更新內容的時效性不足。

**Q15：基於這項研究，未來有哪些值得探索的方向？**
A：未來可探索的方向包括：將 Incremental-OEDR 擴展至多代理協作情境，讓不同代理分別負責不同章節的增量維護；結合主動資訊偵測機制，使系統能自動識別何時需要更新以及更新哪些部分；將結構化表示與知識圖譜結合，進一步提升跨報告的知識重用能力；以及探索在更長時間軸（例如數十年）與更複雜主題演化下的長期效能。此外，如何將 Incremental-OEDR 與人類專家的審閱流程整合，實現「人機協作的持續研究」，也是一個兼具學術與實務價值的重要方向。

## 實務應用指南

### 適用場景

以下列舉五個 Incremental-OEDR 特別適合落地的真實場景：

1. **快速演進產業的定期研究報告維護**：例如 AI、半導體、新能源等產業，模型發表、技術突破、供應鏈變動頻繁。傳統做法是每季或每月重新撰寫完整報告，但 80% 以上內容（如產業背景、核心技術原理）其實不變。Incremental-OEDR 可只針對「過去一季新發表的模型」「新公布的製程節點」等增量資訊做更新，大幅降低重複勞動。

2. **競爭情報與市場動態追蹤**：企業策略部門需要持續追蹤競爭對手的新產品發布、併購、人事異動、財報數據。Structured Harness 的「持久化證據池」可保留先前已蒐集過的證據，並透過結構化檢索快速定位「上次報告中關於某競爭對手的段落」，再針對新事件做選擇性更新。

3. **政策法規與監管動態報告**：金融、醫療、資料合規等領域的法規經常修訂。實務上需要的是「差異化更新」——保留既有條文解析，僅針對新增或修訂條文補充影響評估。Incremental-OEDR 的「保留有效知識、修正過時內容、納入新資訊」三步驟正好對應此需求。

4. **學術文獻綜述與研究前沿追蹤**：研究者撰寫 survey paper 或持續追蹤某子領域時，需要定期納入新發表的論文。Structured Harness 可將既有 survey 拆解為「方法論章節」「實驗結果章節」「應用場景章節」等結構，僅針對新論文涉及的章節做增量補充。

5. **投資研究與盡職調查（DD）報告**：賣方分析師對標的公司撰寫的初次覆蓋報告，後續隨季報、公告、產業事件需要持續更新。Incremental-OEDR 可維持報告骨架與既有論點，僅針對新財報數字、新管理層變動、新產品線等做局部修訂，並保留歷史預測與實際結果的對照脈絡。

### 實作前置條件

**資料面**
- **歷史報告語料庫**：至少需要一份結構完整的既有研究報告作為「初始狀態 R₀」，建議具備清楚的章節切分與段落層級。
- **證據來源 API**：可程式化存取的搜尋引擎（如 SerperAPI、Bing Search、Tavily）、學術 API（如 arXiv、Semantic Scholar）、產業資料庫接入權限。
- **時序資料標註**：每筆證據需附帶時間戳記（發布日期、抓取日期），這是判斷「是否為新資訊」的基礎。
- **領域詞典與同義詞表**：用於結構化檢索時的查詢擴展與章節對齊。

**運算面**
- **LLM 推論資源**：可選 Proprietary Configuration（如 GPT-4 等級 API）或 Open-source Configuration（如 Qwen、DeepSeek 等開源模型自部署）。PC 品質較穩定但成本高，OC 需準備 GPU 叢集（如 4×A100 以上）。
- **向量資料庫**：用於結構化檢索的 embedding 儲存與相似度比對，建議採用 Milvus、Qdrant 或 pgvector。
- **持久化儲存**：證據池需長期保存，建議採用物件儲存（如 S3）+ 結構化索引（如 PostgreSQL JSONB 欄位）。
- **排程與工作流引擎**：用於驅動定期增量更新任務（如 Airflow、Prefect）。

**技能面**
- **LLM 應用開發經驗**：熟悉 prompt engineering、function calling、agent loop 設計。
- **RAG 系統建置能力**：理解 chunking、embedding、retrieval、reranking 流程。
- **結構化資料處理**：能設計 outline / section / evidence 的 schema，並處理 JSON / Markdown 之間的轉換。
- **評估方法論素養**：理解 ROUGE-L、EM F1 等指標的意義與限制，能設計領域專屬的評估任務。

### 實作步驟建議

**階段一：最小可行產品（MVP）驗證**
1. 選定一個高頻更新的領域（如 AI 產業週報），蒐集 3–5 篇歷史報告作為初始資料。
2. 將一份歷史報告手動拆解為「outline → section → evidence」三層結構，定義 JSON schema。
3. 實作最簡版的「結構化檢索」：以章節標題作為檢索鍵，回傳對應段落與證據。
4. 串接一個 LLM，實作「結構化生成」：針對單一 section 做增量更新，保留其他 section 不變。
5. 評估：人工比對更新前後報告的差異，驗證「保留有效知識」是否成立。

**階段二：核心能力建置**
6. 建立「持久化結構化證據池」：將每次檢索結果以結構化形式（包含時間戳、來源 URL、信心分數）寫入資料庫。
7. 實作「變更偵測」機制：對新證據與既有證據做時序比對，標記「新增」「過時」「仍有效」三類。
8. 設計 agent loop：讓 LLM 根據變更偵測結果，自主決定哪些 section 需要更新、哪些需要新增、哪些需要刪除。
9. 引入 reranker 與證據驗證步驟，降低幻覺與錯誤引用風險。

**階段三：評估框架落地**
10. 建構時間評估資料集：蒐集同一主題跨越多年的報告版本（如 2016–2025），標註每次更新的「真實差異」。
11. 實作 Single-Step Task（SST）：評估單次轉換的更新品質。
12. 實作 Long-Chain Task（LCT）：模擬多年連續更新，評估長期結構穩定性與錯誤累積。
13. 建立三類指標的自動化評估管線：Report Quality（如 ECAR）、Report Continuity（內容級 ROUGE-L F1、大綱級 EM F1）、Research Cost（token 消耗、搜尋呼叫次數）。

**階段四：產品化與營運**
14. 設計使用者介面：讓領域專家能審閱、修改、批准每次增量更新的提案。
15. 串接排程系統：依領域特性設定更新頻率（每日、每週、每月）。
16. 建立監控儀表板：追蹤更新成功率、證據新鮮度、結構漂移程度。
17. 設計回退機制：當增量更新品質低於閾值時，自動觸發完整重生成作為保險。

### 潛在風險與注意事項

**風險一：結構性偏差累積（Structural Drift）**
- **現象**：每次增量更新可能引入小幅結構變動，經過多次更新後，報告骨架可能嚴重偏離原始設計。
- **緩解**：設定「大綱穩定性指標」監控 EM F1 隨時間的變化；當漂移超過閾值時，自動觸發一次「結構重整」任務。

**風險二：證據過時誤判（Staleness Misjudgment）**
- **現象**：某些「看似過時」的證據其實仍具參考價值（如經典理論、歷史基準數據），被錯誤標記為需更新。
- **緩解**：在證據池中為每筆證據標註「時效敏感度」（time-sensitivity）等級；高敏感度證據（如股價、模型版本）優先更新，低敏感度證據（如理論框架）預設保留。

**風險三：增量更新的錯誤傳播（Error Propagation）**
- **現象**：若某次更新引入錯誤引用或錯誤詮釋，後續更新可能基於此錯誤繼續延伸。
- **緩解**：建立「證據溯源鏈」（evidence provenance chain），每個論點都能追溯到原始來源；定期進行人工抽樣稽核。

**風險四：搜尋 API 成本失控**
- **現象**：雖然 Incremental-OEDR 平均降低 61% 搜尋呼叫，但在長鏈任務中，累積呼叫次數仍可能超出預期。
- **緩解**：設定每日 / 每任務的搜尋呼叫預算上限；對高頻查詢做快取；優先使用低成本 API 進行初步篩選。

**風險五：評估指標的侷限性**
- **現象**：ROUGE-L 與 EM F1 偏向衡量「與參考答案的文字重疊度」，未必能反映報告的「實質正確性」或「論點深度」。
- **緩解**：搭配 LLM-as-a-judge 進行質性評估；引入領域專家進行定期盲測。

**風險六：領域遷移困難**
- **現象**：在 AI 產業報告上表現良好的設定，遷移到醫療或法律領域時，章節結構與證據類型差異極大。
- **緩解**：將「結構化表示」設計為可配置的 schema；針對不同領域提供模板化的 outline 與 evidence 類型定義。

### 與其他技術的整合建議

**與既有 RAG 系統整合**
- Incremental-OEDR 的「結構化檢索」可作為 RAG pipeline 的進階版本：不是回傳 top-k chunks，而是回傳結構化的 section + evidence 組合。
- 既有 RAG 系統的向量資料庫可直接複用，只需新增「時序索引」與「結構化標籤」兩個欄位。

**與知識圖譜（Knowledge Graph）整合**
- 將 outline 對應到知識圖譜的 schema，section 對應到實體類型，evidence 對應到三元組。
- 增量更新時，可先用知識圖譜偵測「哪些實體新增了屬性或關係」，再針對性地更新對應章節。

**與工作流自動化平台整合**
- 透過 n8n、LangGraph、AutoGen 等框架編排增量更新流程：排程觸發 → 證據池刷新 → 變更偵測 → LLM 更新提案 → 人工審核 → 發布。
- 將每次更新視為一個「transaction」，保留完整的 audit log。

**與版本控制系統整合**
- 將每次增量更新視為一次 commit，保留報告的完整版本歷史。
- 支援「diff 檢視」：讓使用者清楚看到本次更新新增、修改、刪除了哪些段落與證據。

**與 BI 與儀表板整合**
- 將 Report Quality、Report Continuity、Research Cost 三類指標接入 Grafana / Metabase。
- 設定異常告警：當某次更新的品質下降超過閾值時，自動通知負責人。

**與人類專家審核流程整合**
- 設計「human-in-the-loop」介面：LLM 提出更新草案，領域專家逐段批准或修改。
- 對高風險章節（如涉及法規解讀、財務預測）強制要求人工覆核。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，掌握 Incremental-OEDR 想解決的核心問題——「為何不每次都從零開始生成報告」。接著閱讀第 1 節的問題動機，理解「增量更新」與「重新生成」的差異。技術細節可先跳過，專注於「結構化表示」的概念——把報告想成「目錄 + 章節 + 證據」三層結構，有助於直觀理解整個方法。

**給 AI 工程師**：重點閱讀 Structured Harness 的三大元件——結構化檢索、持久化證據池、結構化生成。建議直接到專案頁面（https://ioedr-project.github.io/）查看程式碼與 API 規格，思考如何將現有 RAG pipeline 升級為結構化版本。特別關注「變更偵測」與「選擇性更新」的實作細節，這是與傳統 RAG 最大的差異點。評估框架的設計也值得參考，可借鑑到自己的專案中。

**給研究者**：本文的核心貢獻在於「問題定義」與「評估框架」，而非單純的模型改進。建議仔細閱讀時間評估框架的設計——Single-Step Task 與 Long-Chain Task 的區別、三類指標的互補性，以及如何建構跨越十年的時序資料集。這些方法論對任何「長期演化系統」的研究都有參考價值。此外，與 OEDR workflow 和 OEDR agent 兩種既有範式的比較章節（Appendix A）值得深入研讀。

**給產品經理**：重點關注「為何 Incremental-OEDR 適合產品化」——成本降低 33% token、61% 搜尋呼叫的數字背後，代表的是更低的 API 費用與更快的回應速度。思考在你的產品場景中，哪些功能適合採用「增量更新」模式（如產業報告、競品追蹤、法規監控），哪些仍適合「一次性生成」（如市場進入分析、首次盡職調查）。建議與工程師討論「human-in-the-loop」的審核流程設計，這是產品落地的關鍵環節。
