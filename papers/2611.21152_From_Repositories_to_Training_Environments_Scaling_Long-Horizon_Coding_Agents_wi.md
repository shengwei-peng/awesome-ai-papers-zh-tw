## 深度分析

#### 方法論解析

RepoFactory 的核心設計理念在於將「真實儲存庫」轉化為「可驗證環境」，並透過「環境演化迴圈」(Environment Evolution Loop) 持續提升環境的訓練價值。整體方法論可拆解為四個階段：

**第一階段：儲存庫搜尋與篩選 (Repository Search and Filtering)**

此階段採用靜態篩選條件，從 GitHub 等平台蒐集候選儲存庫。篩選條件包括：非 fork 專案、未封存、至少 10 顆星、具備可測試的 manifest、至少 1 個測試、規模介於 5 個檔案至 40k LOC 之間、可離線執行、僅需 CPU。這些條件確保候選儲存庫具備基本的可執行性與規模適中性，避免過於簡單或過於龐大的專案。

**第二階段：執行環境建構與儲存庫分析 (Runtime Construction and Repository Analysis)**

此階段嘗試解決執行環境問題——複製程式碼、安裝依賴、執行所有測試。若全部通過，則封存該執行環境映像 (Runtime Image)。同時透過唯讀 AST 掃描萃取出三類證據：公開 API、測試匯入、以及實作樹。這些證據將作為後續任務合成的基礎。

**第三階段：任務合成與環境具現化 (Task Synthesis and Environment Materialization)**

合成代理 (Synthesis Agent) 根據萃取的證據產生任務規格 (Task Specification)，並透過 API Manifest Coverage Check 驗證規格是否涵蓋必要的 API。任務具現化器 (Task Materializer) 則負責佈局映像、隔離環境，最終產出環境實例 $e = (I, W, V, O)$，其中 $I$ 為可見的規格、$W$ 為工作空間映像與依賴、$V$ 為隱藏的測試與驗證器、$O$ 為隱藏的參考實作。

**第四階段：環境演化迴圈 (Environment Evolution Loop)——本方法的核心創新**

此階段最佳化一個乘法目標函數 $Q = A \cdot C \cdot S$，其中：
- **$A$ (Validity, 有效性)**：衡量環境是否可驗證，即驗證器 $V$ 對參考實作 $O$ 通過 ($V(O) = 1$) 但對原始空專案 $P_0$ 不通過 ($V(P_0) = 0$)。若 $A \neq 1$，則進入修復流程，根據驗證報告與追蹤進行修正。
- **$C$ (Structural Coupling, 結構耦合度)**：衡量任務規格與參考實作之間的結構依賴程度，作為「需要跨元件協調」的代理訊號。
- **$S$ (Implementation Scope, 實作範圍)**：衡量任務所需的實作工作量，作為「需要大量實作」的代理訊號。

當 $S \geq 0.5$ 且 $C \geq 0.01$ 時，迴圈會對 $O$、$I$、$V$ 進行聯合修訂。這個乘法設計的關鍵在於：任一維度為零都會導致 $Q = 0$，迫使演化過程必須同時兼顧三個面向，避免單一指標過度膨脹。

**方法論的關鍵洞見**：相較於 BenchEvolver 與 SETA 仰賴模型推論執行 (model rollouts) 來獲取回饋，RepoFactory 採用「無需模型求解」的代理回饋機制。透過靜態程式碼分析與執行驗證即可獲得及時、低成本的回饋訊號，大幅降低計算成本與回饋延遲。這對於長時程式碼任務尤其重要，因為每次模型推論執行都可能涉及大量實作。

#### 實驗數據解讀

**規模與覆蓋**

RepoFactory 最終產出 10,159 個環境，橫跨 17 個軟體領域。這個規模相當可觀，顯示自動化流程能有效處理大量真實儲存庫。17 個領域的覆蓋面意味著訓練資料具備多樣性，有助於提升代理在不同軟體類型上的泛化能力。

**主要效能增益**

以 Qwen3.5-35B-A3B 為基礎模型，訓練後得到 RepoHorizen-35B-A3B：
- **NL2Repo-Bench**：22.6 百分點的增益
- **五個基準測試平均**：8.5 百分點的增益

這些數字顯示 RepoFactory 環境對長時程式碼代理任務有顯著的訓練價值。22.6 百分點的增益在基準測試中屬於非常顯著的進步，意味著模型從「無法完成完整儲存庫生成」提升到「能可靠完成」的層次。

**消融實驗的關鍵發現**

對照組（無環境演化）僅獲得 17.5 與 6.4 百分點的增益。這意味著：
- 環境演化迴圈額外貢獻了 **5.1 百分點**（NL2Repo-Bench）與 **2.1 百分點**（五基準平均）
- 環境演化帶來的提升約佔總增益的 22.6% 至 32.7%

這個消融結果驗證了「環境演化」不只是錦上添花，而是訓練價值提升的重要來源。值得注意的是，NL2Repo-Bench 上的相對貢獻更高，這暗示環境演化對於「完整儲存庫生成」這類長時程任務的價值更為顯著。

**指標設計的意涵**

乘法目標 $Q = A \cdot C \cdot S$ 的設計避免了「取捨式最佳化」的陷阱。若使用加法目標，演化過程可能會犧牲某一維度以提升另一維度（例如犧牲實作範圍以換取結構耦合度）。乘法設計則強制三個維度同時達標，這對於訓練高品質環境至關重要。

#### 與現有研究的比較

**與線性建構流程的比較 (DeNovoSWE, MindForge)**

DeNovoSWE 與 MindForge 採用線性建構流程：精煉文件或解決建置失敗，同時保持參考實作固定。不適合的儲存庫會被直接丟棄，即使進一步修訂可能使其可用。RepoFactory 的環境演化迴圈打破了這個限制——透過聯合修訂 $O$、$I$、$V$，原本被丟棄的儲存庫有機會被「修復」並納入訓練池。這大幅擴展了可用儲存庫池，提升了擴展性。

**與可靠性導向方法的比較 (RefactorForge, TrajLong, ProgramGym)**

RefactorForge 與 TrajLong 為特定能力設計資料，但未探索環境回饋如何改善任務內容。ProgramGym 使用執行診斷與覆蓋率回饋來修復建置並強化測試，但這些訊號僅改善可靠性，並未明確最佳化訓練價值。RepoFactory 的結構耦合度 ($C$) 與實作範圍 ($S$) 明確將「訓練價值」納入最佳化目標，確保任務不僅可靠，還能驅動代理學習有意義的實作與整合技能。

**與模型回饋方法的比較 (BenchEvolver, SETA, DataMaster)**

BenchEvolver 演化參考解以建構更難的任務；SETA 根據學習者表現調整終端環境；DataMaster 使用下游評估分數最佳化訓練資料。這些方法都仰賴求解器推論執行或下游訓練，導致計算成本增加與回饋延遲。對於長時程式碼任務，每次推論執行可能涉及大量實作，成本與延遲問題被放大。RepoFactory 是首個使用「有效性檢查 + 廉價程式碼指標」組合來演化完整儲存庫生成環境的方法，無需求解器推論或下游訓練即可提供及時回饋。

**定位與優勢**

RepoFactory 的獨特定位在於：
1. **任務粒度**：聚焦於「完整儲存庫生成」這類長時程任務，而非短時程的錯誤修復或功能開發
2. **回饋機制**：採用無需模型的代理回饋，兼顧時效性與成本效益
3. **目標函數**：乘法設計同時兼顧可靠性與訓練價值

**現有限制**

- 環境演化迴圈受限於固定的建構預算，可能無法充分演化某些複雜儲存庫
- 結構耦合度與實作範圍作為代理訊號，可能無法完全捕捉「訓練價值」的所有面向
- 17 個軟體領域的覆蓋面雖然廣泛，但對於某些特定領域（如嵌入式系統、遊戲開發）的深度可能不足

未來可探索如何將 RepoFactory 的環境演化理念擴展到這些任務類型，建構更全面的代理訓練生態系。

**5. 人類專家知識的融入**

目前的環境演化完全自動化，但人類專家對於「什麼是有價值的訓練任務」有更深入的洞察。未來可探索：

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於訓練長時程式碼代理所需的環境建構問題。長時程式碼代理必須能夠在真實環境中持續互動並完成複雜任務，因此需要具備可驗證回饋的訓練環境。然而現有的環境建構流程多為線性且止於驗證階段，僅能確認環境是否可用，卻無法有效提升訓練價值。論文試圖回答的核心問題是：如何利用即時、可靠的代理訊號來提升訓練價值，並大規模合成長時程式碼環境。

**Q2：為什麼現有的線性建構流程無法有效擴展？**
A：現有方法存在三個主要瓶頸。首先，線性建構流程（如 DeNovoSWE 與 MindForge）採用固定需求，無法通過的儲存庫會被直接捨棄，限制了可用儲存庫池的規模。其次，RefactorForge、TrajLong、ProgramGym 等方法雖透過執行診斷與覆蓋率回饋提升可靠性，但這些訊號僅針對固定的參考實作進行修補，並未明確最佳化訓練價值。第三，BenchEvolver 與 SETA 等方法仰賴模型推論執行來獲取回饋，對長時任務而言計算成本高昂且回饋延遲嚴重。這三項限制使得長時程式碼環境的大規模合成仍是未解的研究問題。

**Q3：為什麼長時程式碼代理的訓練如此重要？**
A：隨著大型語言模型逐漸發展為代理，軟體工程已成為程式碼代理的主要應用場景。傳統的錯誤修復與功能開發流程雖然能提供可驗證任務，但僅涵蓋真實程式碼庫中的本地修改，無法反映完整軟體交付所需的開發流程。現代程式碼代理被期待能處理更複雜的開發流程並產出完整、可運作系統，因此單靠短時程任務訓練已不足以涵蓋這種更廣泛的工作型態。建構儲存庫層級的訓練環境成為提升代理能力的關鍵。

**Q4：RepoFactory 的核心方法是什麼？**
A：RepoFactory 是一條自動化流程，能將真實世界的儲存庫轉化為可驗證環境。在這些環境中，代理僅依據語言規格就必須從零建構出完整、可運作的專案。整個流程包含儲存庫搜尋與過濾、執行環境建構與分析、任務合成與環境具體化三個階段，最終產出包含規格、工作區、驗證器與參考實作的環境物件。此方法跳脫了傳統線性流程的框架，強調從真實專案中萃取任務並保留元件間的相互依賴關係。

**Q5：環境演化迴圈的關鍵創新是什麼？**
A：環境演化迴圈的核心創新在於使用乘法目標函數 Q = A · C · S，結合有效性、結構耦合度與實作範圍三項指標，提供即時且低成本的代理回饋。這項設計無需模型推論執行或下游評估即可引導聯合修訂參考實作、任務規格與測試。其中有效性回饋用於修復原本不合用的環境，結構耦合度與實作範圍則作為訓練價值的代理訊號，引導修訂朝實作與整合工作傾斜。據作者所知，這是首個結合有效性檢查與低成本程式碼指標來演化完整儲存庫生成環境的方法。

**Q6：為什麼選擇乘法形式而非加法的目標函數？**
A：乘法形式 Q = A · C · S 的設計具有關鍵的語意意涵：當任何一個分量為零時，整體目標函數也歸零，這意味著三個面向必須同時具備才算有訓練價值。一個無效的環境（A=0）無法提供任何訓練訊號；耦合度極低的任務（C≈0）代表缺乏元件協調需求；實作範圍過小的任務（S<0.5）則代表實作工作量不足。這種設計迫使演化過程同時兼顧可靠性與訓練價值，避免單一指標主導而犧牲其他面向。

**Q7：實驗使用了哪些基準測試？**
A：實驗主要在 NL2Repo-Bench 上評估，這是一個專門針對完整儲存庫生成任務的基準測試。此外，論文還報告了在五個涵蓋長時程式碼與代理式任務的基準測試上的平均表現，這些基準測試涵蓋真實世界的生產環境情境。這樣的評估設計能同時檢驗模型在專門的儲存庫生成任務以及更廣泛的代理式工作上的能力。

**Q8：主要的實驗結果為何？**
A：在 Qwen3.5-35B-A3B 基礎模型上經 RepoFactory 環境訓練後得到的 RepoHorizen-35B-A3B，在 NL2Repo-Bench 上獲得 22.6 百分點的增益，並在五個基準測試上平均提升 8.5 點。這些結果證明了 RepoFactory 環境的訓練價值，以及環境演化迴圈所帶來的額外提升。值得注意的是，跨 17 個軟體領域產出的 10,159 個環境展現了流程的可擴展性。

**Q9：消融實驗顯示環境演化的貢獻為何？**
A：消融實驗清楚展示了環境演化迴圈的價值。在沒有環境演化的情況下，模型在 NL2Repo-Bench 僅獲得 17.5 百分點的增益，在五個基準測試上平均僅提升 6.4 點。這意味著環境演化迴圈分別貢獻了 5.1 與 2.1 點的額外增益，證明了乘法目標函數與代理回饋機制對於提升訓練環境品質的重要性。

**Q10：RepoFactory 適用於哪些實際場景？**
A：RepoFactory 特別適用於需要從零建構完整專案的代理訓練場景，例如自動化軟體開發、教學用程式設計環境，以及企業內部的程式碼助理開發。由於環境涵蓋 17 個軟體領域，橫跨不同規模與類型的專案，因此能支援多元化的訓練需求。此外，流程的自動化特性使其適合需要持續產出新訓練資料的機構，例如大型語言模型研發團隊或代理框架供應商。

**Q11：在產品化時需要考量哪些實務因素？**
A：產品化時需考量幾項關鍵因素。首先，建構預算是固定的，這代表需要在迭代次數與環境品質間取得平衡。其次，靜態過濾條件（如星數、檔案數量、程式碼行數上限、僅使用 CPU 等）會限制可處理的儲存庫範圍，可能需要根據目標應用調整。第三，執行環境的隔離性與離線要求雖然確保了可重現性，但也限制了需要 GPU 或網路存取的專案類型。最後，10,159 個環境的規模雖然可觀，但若要支援特定領域的深度訓練，仍需領域專屬的擴充策略。

**Q12：這項研究對領域的影響為何？**
A：這項研究對長時程式碼代理訓練領域帶來多項深遠影響。首先，它證明了從真實儲存庫合成大規模可驗證環境的可行性，為後續研究提供了具體的流程範本。其次，環境演化迴圈所採用的低成本代理回饋機制，為解決遞迴自我改進中回饋延遲與計算成本問題提供了新方向。第三，將訓練價值明確納入環境設計目標，有助於推動領域從「可靠的環境」邁向「高訓練價值的環境」。整體而言，這項工作將環境合成從資料擴充手段提升為訓練策略的核心環節。

**Q13：論文承認的限制有哪些？**
A：雖然論文中限制的討論較為隱含，但仍可辨識出幾項。首先，固定的建構預算限制了演化的深度，可能在某些複雜儲存庫上無法達到最佳品質。其次，代理訊號（結構耦合度與實作範圍）雖然成本低廉，但可能無法完全捕捉訓練價值的全部面向，例如程式碼風格、可維護性等較難量化的特質。第三，目前的環境主要針對 CPU 環境與離線執行，這排除了需要 GPU 加速或網路存取的現代應用類型。最後，10,159 個環境雖然規模可觀，但相較於真實世界的軟體多樣性仍屬有限。

**Q14：可能出現哪些失敗案例？**
A：潛在的失敗案例包括以下幾類。第一，某些儲存庫即使經過多輪修訂仍無法通過有效性檢查，例如依賴特定硬體或外部服務的專案。第二，代理訊號可能無法反映真實的訓練難度，導致演化出的環境在表面指標上良好，但實際訓練價值有限。第三，對於需要領域專業知識的任務（如金融演算法或醫療軟體），僅靠程式碼指標可能無法確保任務規格的正確性。第四，當參考實作本身存在缺陷時，演化過程可能會強化這些缺陷而非修正它們。

**Q15：未來的研究方向有哪些？**
A：基於這項工作，未來可朝幾個方向延伸。首先，可將環境演化迴圈的概念推廣到其他類型的代理訓練，例如網頁代理、資料分析代理等，驗證乘法目標函數的通用性。其次，可探索更精緻的代理訊號，例如結合靜態分析、符號執行或輕量級模型評估，以更全面地捕捉訓練價值。第三，可研究如何將環境演化與模型訓練更緊密結合，形成端到端的自我改進迴圈。第四，擴展至需要 GPU 或分散式執行的環境，以涵蓋更廣泛的現代軟體開發場景。最後，可探討如何讓演化過程更具可解釋性，使研究者能理解環境品質提升的具體原因。

## 實務應用指南

### 適用場景

1. **企業內部程式碼代理訓練**：將公司私有 Git 儲存庫（如內部框架、業務系統）轉化為可驗證的訓練環境，用於訓練能處理完整專案開發週期的內部程式碼代理，特別適合需要長時間跨檔案協作的任務（如微服務拆分、大型重構）。

2. **AI 程式碼助手產品迭代**：程式碼助手廠商可利用 RepoFactory 持續從開源生態採集高品質訓練環境，針對自家模型弱項（如長時程任務、跨元件整合）進行強化訓練，產出如 RepoHorizen-35B-A3B 般的領域特化模型。

3. **程式設計教育與評核平台**：教育機構可將精選開源專案轉為「從零重建」練習題，學生需根據語言規格產出完整可運作的儲存庫，平台透過隱藏測試自動評分，比傳統 LeetCode 式題目更能訓練系統性工程能力。

4. **開源專案維護機器人**：基金會或大型開源組織可基於自家歷史 commit 與 issue 資料，訓練專屬維護代理，自動處理 routine 重構、依賴升級、新功能 scaffold 等長時程任務。

5. **程式碼審查與遷移自動化**：企業在進行框架遷移（如 Java 8→17、Python 2→3、Angular→React）時，可將目標專案轉為訓練環境，訓練代理自動完成跨版本遷移並通過既有測試套件。

### 實作前置條件

**資料面**
- 候選儲存庫來源：GitHub、GitLab、自架 Git 伺服器，需具備 commit 歷史、issue 追蹤、CI 設定檔

- 領域標註：需有 17 種軟體領域的分類標準（可參考 paper 或自訂 taxonomy）

**計算面**
- 容器化基礎設施：Docker/Podman 環境用於隔離執行每個候選儲存庫的建置與測試

**技能面**

- 軟體工程：理解建置系統（Make/CMage/npm/cargo）、測試框架、依賴管理
- DevOps：能建置可重現的容器化執行環境、處理跨平台相容性
- 程式分析：AST 解析、符號解析、API 抽取（可借助 tree-sitter、semgrep 等工具）

### 實作步驟建議

**步驟 1：儲存庫採集與靜態篩選**
- 從 GitHub API 或自建爬蟲批次下載候選儲存庫
- 套用靜態過濾器：非 fork、未封存、≥10 stars、含 manifest、≥1 測試、≥5 檔案、<40k LOC
- 產出「候選儲存庫池」，預期淘汰率約 60-80%

**步驟 2：執行環境建構與分析**
- 為每個候選儲存庫建立隔離容器，嘗試 clone → build → install → 跑測試
- 通過者封存為「Runtime Image」；失敗者暫存供後續修復
- 對通過的儲存庫執行唯讀 AST 掃描，抽取：公開 API、測試 imports、實作樹
- 產出「Runtime Image + Repository Evidence」

**步驟 3：任務合成與環境物化**
- 訓練/設計 Synthesis Agent，根據證據產生語言規格（Language Specification）
- 進行 API Manifest Coverage Check，確保規格涵蓋關鍵公開介面
- Task Materializer 將規格、workspace image、隱藏 oracle、verifier 組裝為環境 e = (I, W, V, O)
- 隱藏 oracle 與原始實作差異化（移除關鍵符號）以避免抄襲

**步驟 4：環境演化迴圈（核心）**
- 定義乘法目標函數 Q = A · C · S
  - A（Validity）：V(O) = 1 且 V(P₀) = 0（oracle 通過、原始實作失敗）
  - C（Structural Coupling）：跨檔案依賴密度，門檻 ≥0.01
  - S（Implementation Scope）：需實作的程式碼量比例，門檻 ≥0.5
- 對未通過 A 的環境：進入 Repair 分支，根據驗證報告與 trace 修復
- 對通過 A 但 C/S 不足的環境：進入 Revise 分支，由 Construction Agent 修訂 oracle、規格、測試
- 在固定建構預算（如 5-10 輪迭代）內最大化 Q

**步驟 5：代理訓練**
- 以 RepoFactory 產出的 10,159 環境作為 SFT 資料
- 訓練 Qwen3.5-35B-A3B（或自選基模）產出 RepoHorizen-35B-A3B
- 可選擇性加入 RL 階段，以環境 verifier 分數作為 reward signal

**步驟 6：評估與部署**
- 在 NL2Repo-Bench 與五個長時程/代理式基準上驗證
- 預期增益：NL2Repo-Bench +22.6 pp、五基準平均 +8.5 pp
- 環境演化迴圈單獨貢獻：+5.1 pp 與 +2.1 pp
- 部署時建議保留環境的 verifier 邏輯，用於線上監控與持續改進

### 潛在風險與注意事項

**風險 1：儲存庫授權爭議**
- 緩解：建立授權白名單/黑名單系統；商業產品建議僅使用 permissive 授權（MIT、Apache-2.0、BSD）；訓練資料來源透明化

**風險 2：執行環境爆炸與資源耗盡**
- 緩解：嚴格限制每環境 CPU/RAM/磁碟配額；使用 container snapshot 加速重複實驗；設定全域 timeout 與 retry 機制

**風險 3：環境演化陷入局部最佳**
- 緩解：對 Construction Agent 注入多樣性（如不同 temperature、隨機化修訂起點）；定期人工抽樣審查演化結果；保留未演化版本作為 ablation 對照

**風險 4：代理學習「抄捷徑」而非真正實作**
- 緩解：確保 oracle 與原始實作有足夠差異（Missing Symbols 機制）；在 verifier 加入反作弊檢查（如禁止直接 import 隱藏模組）

**風險 5：評估基準過擬合**
- 緩解：保留 held-out 領域的環境；定期在真實企業專案（非公開基準）上做 A/B 測試；監控模型在「未見過領域」的表現

**風險 6：長時程任務的推論成本**
- 緩解：採用 speculative execution、early termination（部分測試失敗即停止）；對長任務做 hierarchical decomposition

**風險 7：環境品質參差不齊**
- 緩解：對 Q 值設定最低門檻（如 Q ≥ 0.1）才納入訓練；定期人工 audit 高 Q 值環境是否真的具訓練價值

**與 CI/CD 系統整合**
- 將 RepoFactory 的 Runtime Construction 階段接入企業 CI pipeline，自動為新儲存庫產生訓練環境

- 將產出的 10,159 環境索引化，支援「找類似任務」「找特定領域環境」等查詢
- 與 RAG 系統結合，讓代理在執行時可檢索相似 oracle 的實作模式

**與 Agent 框架整合**
- 環境的 workspace image 可直接餵給 LangGraph、AutoGen、CrewAI 等 agent 框架
- verifier 可作為 agent 的 termination condition 與 self-critique 模組

**與監控與可觀測性整合**
- 將環境建置成功率、Q 值分布、代理表現接入 Prometheus/Grafana
- 建立 drift detection：當新一輪訓練環境的 Q 值分布顯著偏移時告警

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節（Introduction）了解「為什麼需要長時程程式碼代理」與「現有方法的三大限制」，再看第 3 節的 RepoFactory 整體流程圖，理解從儲存庫到訓練環境的四階段轉換。核心概念是「把真實專案變成可自動評分的練習題」，數學細節可先跳過，重點掌握 Q = A · C · S 三個分數分別代表什麼。

**給 AI 工程師**：重點關注第 3 節的 Environment Evolution Loop 與乘法目標函數設計——這是 paper 最具工程價值的部分。建議將 Q = A · C · S 的設計理念對照自身專案：你的訓練環境是否也有「可靠性 vs 訓練價值」的取捨？C 與 S 作為 proxy signal 的思路可應用於其他領域（如 tool-use、navigation）。實作時可從小規模（100-500 環境）開始驗證 pipeline 穩定性，再逐步放大。

**給研究者**：本 paper 的核心 insight 是「用便宜的程式碼指標取代昂貴的 model rollout 作為環境演化訊號」，這對 recursive self-improvement 領域是重要推進。建議深入分析：(1) 為何乘法而非加法？(2) C 與 S 的具體測量方式與分布；(3) 演化預算與最終品質的 scaling law；(4) 此方法能否泛化至程式碼以外的長時程領域（如 ML engineering、data analysis）。可考慮的延伸方向：把 C/S 換成 learned metric、引入 curriculum learning、結合 human-in-the-loop 修正演化方向。

**給產品經理**：本 paper 展示了一條「從資料到模型到產品價值」的完整鏈路——10,159 環境 → 領域特化模型 → 22.6 pp 基準提升。對產品的意義在於：(1) 開源生態是巨大的「未標註訓練資料」來源，自動化 pipeline 可大幅降低資料成本；(2) 環境演化迴圈讓「訓練資料品質」本身成為可迭代的產品功能；(3) 22.6 pp 的提升在產品體驗上會直接反映為「能完成更複雜任務的助手」。決策時需評估：自家產品的長時程任務占比、訓練資料合規性、與現有模型蒸餾管線的相容性。
