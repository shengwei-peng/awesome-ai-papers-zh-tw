## ⚡ TL;DR

現有評估僅看整體成功率，未能解釋技能何時有效、為何有效、何時失效。
本文提出分類架構，結合控制實驗與配對軌跡分析，拆解技能的作用機制與失效原因。
技能主要透過程序性錨點穩定執行，但檢索困難與情境不適配會導致失效。

## 摘要翻譯

技能（Skills）已成為一種實用且有效的方法，可在推論階段（inference time）透過結構化知識套件（structured packages of knowledge）增強大型語言模型智慧體（LLM agents）。然而，現有評估多半僅衡量技能是否提升聚合任務成功率（aggregated task success），卻讓一個更根本的問題未能充分探討：技能何時有幫助、為何有效，以及在何處失效？本研究透過橫跨多個基準測試、智慧體測試框架（agent harnesses）與大型語言模型的控制實驗，分離出技能的表示形式（representation）、結果標註（outcome annotation）、檢索難度（retrieval difficulty）與跨框架穩健性（cross-framework robustness）等效應。為進一步回答此問題，我們設計了一項對比研究（contrastive study），結合控制定量實驗與配對軌跡分析（paired trajectory analysis）。我們整理並標準化 8,135 筆來自控制實驗的試驗紀錄（trial records），並從 240 筆開放編碼紀錄（open-coded records）中保留 238 個有效獨立標籤（unique labels）。我們將這些觀察整合為一個包含三大高層類別（high-level categories）與十二種技能使用模式（skill-use modes）的分類體系（taxonomy）：當雜訊軌跡（noisy trajectories）轉化為穩定執行的程序性錨點（procedural anchors）時，技能便發揮作用。在配對比較（matched comparisons）中，技能相較於工作流記憶（Workflow Memory）提升 6.06 分。程序性錨定（Procedural anchoring）佔技能案例的 65.7％，而顯式知識注入（explicit knowledge injection）僅佔 4.5％，顯示技能主要是穩定行動，而非注入缺失事實（missing facts）。檢索則是另一個瓶頸：當技能池（skill pools）從 5 個擴大到 100 個，實際使用精確率（actual-use precision）從 29.6％ 下降至 3.3％。易混淆的干擾項（Confusable distractors）會削弱離線識別（offline identification），但下游任務成功率（downstream success）仍保持穩定；精確的真值調用（ground-truth invocation）既非充分亦非必要。技能會因脆弱假設（brittle assumptions）、不相容情境（incompatible contexts）或適應不足（insufficient adaptation）而失效。這些發現使評估超越整體成功率（aggregate success rates），並指引可靠的自我演化智慧體（self-evolving agents）之發展。

### 核心貢獻（3～5點）
- 提出包含三大高層類別與十二種技能使用模式的分類體系，揭示技能主要透過程序性錨定穩定執行，而非注入缺失事實。
- 透過控制實驗與配對軌跡分析，量化技能相較於工作流記憶的優勢，並分離表示形式、結果標註、檢索難度與跨框架穩健性等效應。
- 發現檢索是獨立瓶頸：技能池擴大會顯著降低實際使用精確率，但下游任務成功率仍能保持穩定。
- 指出技能失效的三大原因：脆弱假設、不相容情境與適應不足，為評估與設計可靠的自我演化智慧體提供指引。

### 適合對象
從事 LLM 智慧體、工具使用智慧體、自我演化智慧體與代理記憶系統研究的學者與工程師；特別適合關注推論階段知識增強、技能檢索機制、代理評估方法，以及希望理解技能何時有效與為何失效的研究者與實務開發者。

## 深度分析

#### 方法論解析

本文的核心方法是一套 **contrastive study（對比研究）**，結合控制實驗與 **paired trajectory analysis（配對軌跡分析）**，把 Skill（技能）對 LLM agent（大型語言模型智慧體）的影響從「整體成功率」拆解成可觀察的機制。研究設計可從三個層次理解：

1. **Skill vs. Workflow Memory（技能對照工作流記憶）管線**  
   作者在固定 Docker 環境中執行任務，收集成功與失敗的 **execution trace（執行軌跡）**，形成固定預算下的軌跡組合格子（5s0f 到 0s5f，代表來源軌跡中成功與失敗的比例）。同一組 trace pool（軌跡池）被蒸餾成兩種形式：一是直接注入的 **Workflow Memory（工作流記憶）**，二是壓縮後可重複使用的 SKILL.md。兩者在相同協議下於配對任務上評估，從而隔離「表示形式（representation）」本身的效應。

2. **Skill retrieval（技能檢索）管線**  
   每個任務搭配一個候選 **skill pool（技能池）**，內含一個 ground-truth（真值）技能與 k−1 個干擾項，干擾項分為 random（隨機）、similar（相似）、dissimilar（不相關）三類。研究設計三種獨立評估程序：
   - **(A) embedding-based ranking（基於嵌入的排序）**：不執行任務，僅測量離線檢索表現；
   - **(B) explicit agent selection（顯式智慧體選擇）**：由 agent 在無 Docker 執行與驗證的條件下挑選技能；
   - **(C) full-pool real execution（全池真實執行）**：在真實環境中執行並解析技能調用情形。  
   A 與 B 的輸出不會傳入 C，因此可以分別測量 **offline identification（離線識別）** 與 **downstream success（下游任務成功率）**。

3. **質性編碼與分類法**  
   作者將 8,135 筆 **trial record（試驗紀錄）** 正規化，從 240 筆 **open-coded record（開放編碼紀錄）** 中保留 238 個 valid unique label（有效獨立標籤），歸納為三大高層類別與十二種 **skill-use mode（技能使用模式）**：
   - **SC1 Guided success（引導成功）**：skill-guided success、workflow-guided success、autonomous success；
   - **SC2 Execution & verification（執行與驗證）**：algorithmic logic error、static verify w/o runtime、output format/schema mismatch、env infrastructure failure、background service failure、shell code corruption；
   - **SC3 Invocation & budget（調用與預算）**：timeout/budget exhaustion、skill guidance misapplied、capability/safety limit。  
   這套 **taxonomy（分類體系）** 讓「技能何時有用、為何有用、何時失效」從黑箱變成可歸因的具體模式。

整體而言，方法論的關鍵貢獻在於把 **inference time（推論階段）** 的技能效應拆成「表示形式」、「結果標註（outcome annotation）」、「檢索難度（retrieval difficulty）」與「跨框架穩健性（cross-framework robustness）」四個可獨立操弄的維度，並透過 **matched comparison（配對比較）** 與軌跡對比，將成功與失敗對應到具體機制。

#### 實驗數據解讀

實驗結果挑戰了「Skill 只是成功經驗的壓縮」這一直覺，顯示其主要價值在於**穩定執行程序**，而非補充事實知識：

- **整體增益來自程序性穩定，而非知識注入**  
  在 **matched comparison（配對比較）** 中，Skill 相較於 Workflow Memory 提升 6.06 分。更重要的是，**procedural anchoring（程序性錨點）** 佔了 65.7% 的技能效用案例，而 **explicit knowledge injection（顯式知識注入）** 僅佔 4.5%。這表示 Skill 的主要作用是把 **noisy trajectory（雜訊軌跡）** 轉換成穩定的操作步驟、工具序列與驗證檢查，從而減少環境設定錯誤、輸出格式不符、背景服務生命週期失誤與 shell 指令損壞等執行層錯誤。

- **檢索是獨立瓶頸**  
  當 **skill pool（技能池）** 從 5 個擴大到 100 個，**actual-use precision（實際使用精確率）** 從 29.6% 驟降至 3.3%。這顯示即使下游執行能從 Skill 獲益，「能不能找到對的技能」本身就是嚴重的 **retrieval bottleneck（檢索瓶頸）**。更有趣的是，**confusable distractor（易混淆的干擾項）** 會損害 **offline identification（離線識別）**，但 **downstream success（下游任務成功率）** 仍保持穩定；換句話說，**ground-truth invocation（真值調用）** 既不是充分條件，也不是必要條件——agent 有時能在未精準選中正確技能的情況下仍完成任務，反之亦然。

- **失效模式源於脆弱前提與適應不足**  
  Skill 失效並非單純因為「沒有相關經驗」，而是因為 **brittle assumption（脆弱假設）**、**incompatible context（不相容情境）** 或 **insufficient adaptation（適應不足）**。例如，蒸餾後的指導可能過度特定於原始軌跡、假設了不存在的前置條件，或被 agent 機械式遵循而沒有根據新任務調整。這也解釋了為何同一個 Skill 在某些任務上有效，在另一些任務上卻有害。

- **結果標註與表示形式的效應**  
  雖然摘要未給出每個控制條件的完整數字，但實驗設計明確區分了「經驗本身」與「明確的成功/失敗標註」：透過比較 Raw、Workflow Memory 與 Skill 三種 arms，作者能判斷增益是來自於原始軌跡的資訊量，還是來自於標準化 **representation（表示形式）** 所帶來的穩定性。

#### 與現有研究的比較

現有研究大多以 **aggregated task success（聚合任務成功率）** 作為評估 Skill 的指標：只要載入 Skill 後 agent 解題變多，就認定 Skill 有用。這種做法雖能證明 Skill「有影響」，卻無法回答「為何有影響」或「何時會反噬」。本文的貢獻在於把評估從「是否有效」推進到「為何有效與如何失效」：

- **從黑箱到機制分類**  
  相較於過去把 Skill 視為單一記憶形式的改進，本文提出包含三大類、十二種模式的 **taxonomy（分類體系）**，並用量化比例說明 **procedural anchoring（程序性錨點）** 是主導機制。這比單純比較「有無 Skill」更能指導設計。

- **與 Workflow Memory 的對照**  
  過去許多系統直接儲存 **raw execution trace（原始執行軌跡）** 或 **direct workflow memory（直接工作流記憶）**。本文顯示，把相同經驗蒸餾成 Skill 後，在配對比較中可額外獲得 6.06 分的提升，證明「標準化與壓縮」本身具有獨立價值，而不只是「擁有更多記憶」。

- **與 Anthropic Skill 抽象的呼應**  
  文中提到 Skill 是 Anthropic（2025）提出的抽象，強調「做什麼、檢查什麼、避免什麼」。本文則進一步以實證說明這種抽象在實際執行中如何轉化為程序穩定，並指出其檢索與適應上的極限。

- **限制與待釐清之處**  
  研究仍有一些局限：首先，質性編碼雖經正規化，但最終分類仍依賴人工標註，主觀性難以完全排除；其次，實驗採用固定預算的軌跡組合與特定 **skill pool（技能池）** 設計，干擾項的相似度定義可能無法完全類比真實開放式技能庫；再者，實驗涵蓋多個 benchmark、agent harness 與 LLM，但各組合間的效應量差異在提供的片段中尚未完整呈現。

#### 可重現性評估

就提供的文本與圖表而言，作者尚未明確說明是否釋出原始碼、資料集或模型權重。由於這是一篇 preprint，目前可視為尚無公開 artifact。要達成高可重現性，至少需要以下項目：

- **Docker 環境與任務腳本**：固定執行環境是控制實驗的基礎，必須公開才能複製 Raw、Workflow Memory 與 Skill 三種 arms。
- **Trace pool（軌跡池）與 SKILL.md 模板**：包括 5s0f 到 0s5f 的軌跡組合、蒸餾 prompt，以及最終產生的 Skill 內容。
- **檢索實驗程式**：尤其是 (A) embedding-based ranking、(B) explicit agent selection 與 (C) full-pool real execution 的程式碼、嵌入模型與解析邏輯。
- **正規化後的 trial record（試驗紀錄）與 open-coded label（開放編碼標籤）**：8,135 筆紀錄與 238 個 unique label 的釋出將讓其他研究者驗證 **taxonomy（分類體系）**。
- **Agent harness 與 LLM 版本**：不同框架與模型對 Skill 的解析方式差異甚大，必須詳細記載。

在這些 artifact 公開之前，本文的結論雖具說服力，但外部研究者難以完全重現其數字或延伸驗證。

#### 未來研究方向

基於本文發現，後續研究可沿以下方向推進：

1. **以程序性錨點為目標的自動化 Skill 生成**  
   既然 Skill 的主要價值在於 **procedural anchoring（程序性錨點）**，未來的 Skill 生成器應直接優化「能否把雜訊軌跡轉為穩定步驟」，而非僅追求壓縮比或事實覆蓋率。

2. **檢索感知的 Skill 設計與索引**  
   面對 **retrieval bottleneck（檢索瓶頸）**，可研究如何設計 Skill 的標題、摘要與結構，使其在大型 **skill pool（技能池）** 中仍能被準確檢索，例如加入任務特徵簽名或負面範例。

3. **動態適應與情境相容性檢查**  
   針對 **brittle assumption（脆弱假設）** 與 **incompatible context（不相容情境）**，可開發能判斷「此 Skill 是否適用於當前任務」的 meta-cognitive 機制，避免機械式遵循導致的失敗。

4. **跨框架 Skill 標準**  
   本文觸及 **cross-framework robustness（跨框架穩健性）**，但未深入探討 Skill 表示的通用格式。未來可推動類似 OpenAPI 的 Skill 描述標準，讓 Skill 能在不同 agent harness 間轉移。

5. **拆解式評估協議**  
   延續本文精神，建立將「離線識別 → 調用決策 → 執行穩定 → 最終成功」分開評量的基準，取代單一的 **aggregate success rate（整體成功率）**。

6. **自我演化智慧體的失效回饋迴路**  
   把本文的 **taxonomy（分類體系）** 整合進 **self-evolving agent（自我演化智慧體）** 的學習迴路：當執行落入 SC2 或 SC3 的失效模式時，自動觸發 Skill 修訂、合併或淘汰。

7. **結合顯式知識注入與程序性錨點**  
   雖然目前 **explicit knowledge injection（顯式知識注入）** 佔比低，但在需要特定領域事實的任務中，可設計混合式 Skill，同時提供操作程序與關鍵事實檢查點。

8. **不確定性感知的 Skill 調用**  
   鑑於 **ground-truth invocation（真值調用）** 非必要，未來可研究讓 agent 在檢索結果不確定時，採取保守策略（如要求澄清）或組合多個 Skill 的片段，而非全有或全無地載入單一 Skill。

## 論文問答

**Q1：這篇論文想要解決的核心問題是什麼？**
A：這篇論文指出，現有研究大多只關注「加入技能後整體任務成功率是否提升」，卻忽略了更根本的問題：技能在什麼情境下有用、為什麼有效、又在哪裡會失效。作者認為，僅用聚合成功率來評估技能，會把技能的作用當成黑箱，無法解釋它究竟改變了智慧體的哪些行為。因此，本文旨在拆解技能在推論階段的作用機制，為建立可自我演化的可靠智慧體提供理論基礎。

**Q2：為什麼單純測量聚合任務成功率無法充分評估技能的價值？**
A：聚合成功率只能告訴我們「有技能比沒有好」，但無法區分增益是來自程序性錨定、顯式知識注入，還是單純的檢索運氣。這種評估方式也無法診斷失敗原因，例如技能是否因為脆弱假設、不相容情境或適應不足而導致反效果。結果，開發者只能憑經驗反覆調整提示或技能內容，難以系統性地設計出真正穩定有用的技能。

**Q3：理解技能的作用機制對 LLM 智慧體為何如此重要？**
A：現代工具使用智慧體被期待能從經驗中學習，而不是每次都從頭摸索，技能正是把過去執行軌跡壓縮成可重複使用的程序性知識。如果不懂技能何時、為何、如何生效，智慧體可能會累積雜訊過多、過度特定或與新任務不匹配的技能，反而降低可靠性。因此，建立一套能解釋技能效用的分類法與方法論，是邁向可靠自我演化智慧體的關鍵一步。

**Q4：本文採用的核心研究方法是什麼？**
A：作者設計了一種對比研究，結合控制實驗與配對軌跡分析，針對相同任務比較「有技能」與「無技能」的執行差異。研究沿著技能使用流程的多個階段進行拆解，包括經驗如何被表徵、如何跨框架轉移、如何被檢索以及最終如何被調用。這種對比視角讓研究者能把成功與失敗歸因到具體機制，而不是只看最終成敗。

**Q5：本文提出的分類法有什麼關鍵創新之處？**
A：作者從 8,135 筆試驗紀錄中歸納出 238 個有效標籤，並整理成三大高層類別與十二種技能使用模式。這個分類法首次系統性地區分了「程序性錨定」、「執行與驗證」以及「調用與預算」等不同作用機制，讓技能效用不再只是成功或失敗的二元結果。研究發現，程序性錨定佔了 65.7% 的技能效用案例，而顯式知識注入僅佔 4.5%，顯示技能主要是穩定行動而非補充缺失事實。

**Q6：實驗設計上有哪些重要選擇？**
A：實驗在固定的 Docker 環境中執行，並使用固定預算組成的軌跡混合池，確保比較條件一致。同一批執行軌跡會被分別蒸餾成 Workflow Memory 與可重複使用的 SKILL.md，從而直接比較不同表徵形式的影響。在檢索實驗中，作者為每個任務建立包含真值技能與若干真實干擾項的技能池，並透過離線排序、顯式選擇與真實執行三種程序獨立評估檢索難度。

**Q7：實驗涵蓋了哪些基準測試、智慧體框架與語言模型？**
A：根據論文描述，實驗橫跨多個代表性的工具使用基準測試、不同的智慧體框架以及多種大型語言模型，以確保結論具有跨設定的一般性。雖然摘要與上下文未逐一列出所有名稱，但實驗設計強調在控制條件下進行配對比較，避免單一資料集或模型造成的偏差。這種多設定驗證有助於區分哪些現象是技能本身的特性，哪些只是特定環境的偶然結果。

**Q8：本文有哪些關鍵量化發現？**
A：在配對比較中，技能相較於 Workflow Memory 平均提升了 6.06 分的任務表現，顯示標準化程序性知識比直接注入工作流記憶更有效。在技能效用來源上，程序性錨定佔了 65.7%，而顯式知識注入僅佔 4.5%，說明技能主要是把雜訊軌跡穩定成可執行程序。此外，當技能池從 5 個擴大到 100 個時，實際使用精確率從 29.6% 驟降至 3.3%，顯示檢索是一個獨立且嚴重的瓶頸。

**Q9：檢索與調用相關的消融實驗揭示了什麼？**
A：實驗發現，隨著技能池變大，離線識別正確技能的難度顯著上升，尤其是存在易混淆干擾項時，智慧體更容易選錯技能。然而有趣的是，即使沒有精確調用到真值技能，下游任務成功率仍能保持相對穩定，這說明「正確調用」既不是充分條件，也不是必要條件。這些結果凸顯了檢索與執行是兩個可分離的階段，單純擴大技能池並不一定帶來更好的整體表現。

**Q10：這些發現對實際建構智慧體系統有什麼指導意義？**
A：開發者應把重點放在如何把雜訊軌跡蒸餾成穩定的程序性錨點，而不是無限制地累積更多技能。同時，必須正視檢索瓶頸，設計有效的技能池管理與檢索機制，避免技能數量增加反而降低實際使用精確率。此外，系統應具備適應與驗證機制，確保技能在不相容情境下不會被僵化地套用。

**Q11：在產品化技能庫時需要考慮哪些因素？**
A：首先應控制技能池的規模與品質，因為過大的技能池會顯著降低檢索精確率，進而影響實際效用。其次，需要處理易混淆干擾項，例如透過更細緻的技能描述、任務相似度判斷或動態檢索排序來提升離線識別率。最後，產品系統應監控技能的調用情境，避免技能在不相容環境或脆弱假設下被錯誤使用，並支援根據當前任務進行適度調整。

**Q12：這項研究對整個 LLM 智慧體領域可能帶來什麼影響？**
A：本文把技能評估從單純的聚合成功率，推進到對作用機制的系統性理解，為後續研究提供了可重複的分析框架。它提醒我們，自我演化智慧體的關鍵不只是累積記憶，而是要知道哪些記憶會穩定執行、哪些會帶來風險。這種以機制為導向的視角，將影響未來技能生成、檢索、調用與記憶系統的設計方向。

**Q13：本文承認了哪些主要限制？**
A：研究的結論來自於特定集合的基準測試、智慧體框架與語言模型，雖然已盡量跨設定驗證，但仍可能無法涵蓋所有應用場景。分類法來自開放編碼的質性分析，雖然經過系統化整理，未來仍可能發現新的技能使用模式或失敗類型。此外，檢索實驗中的干擾項設計是研究者預先設定的，真實世界技能庫中的干擾分佈可能更加複雜。

**Q14：研究發現技能會在哪些情況下失效？**
A：技能會在存在脆弱假設時失效，例如技能預設了某種固定環境配置，但當前任務情境並不符合。它們也會在不相容情境或適應不足時產生反效果，例如智慧體機械式地遵循過度特定或已過時的指引。此外，若蒸餾出的程序性指導本身帶有雜訊，或智慧體錯誤地把技能套用到不適用的步驟上，也會導致執行失敗。

**Q15：未來研究可以朝哪些方向發展？**
A：未來可以發展能自動生成並驗證技能的機制，讓智慧體不僅累積經驗，還能判斷哪些經驗值得被蒸餾成穩定程序。另一個方向是改善大規模技能池下的檢索與調用策略，例如結合任務分解、動態索引或反思式檢索來維持高實際使用精確率。最後，也可以把本文的分類法擴展到多智慧體協作、線上持續學習或人機協同等更複雜的場景，進一步提升自我演化系統的可靠性。

## 實務應用指南

### 適用場景

1. **DevOps / SRE 自動化運維**
   在固定容器環境中反覆執行部署、重啟服務、清理磁碟或排查告警時，技能可將過去成功與失敗的執行軌跡壓縮為「程序性錨點」。例如把「檢查 Pod 狀態 → 讀取日誌 → 重啟異常服務 → 驗證健康檢查」封裝成 SKILL.md，降低每次從頭摸索的環境設定錯誤與 shell 指令損壞風險。

2. **資料分析與報告生成管線**
   當 LLM 智慧體需要反覆連接資料庫、執行 SQL、繪製圖表並輸出固定格式報告時，技能可標準化「工具使用模式」與「輸出格式 / 綱要檢查」。這能減少輸出格式不匹配、背景服務連線失敗等執行層錯誤，並確保跨任務的驗證步驟一致。

3. **具工具呼叫能力的客戶支援或業務助理**
   在需要查詢訂單、修改預約、寄送通知的多步驟對話中，技能可將常見處理流程（如「確認身份 → 查詢訂單 → 執行退款 → 發送確認信」）轉為可重複使用的程序知識。這特別適合處理高頻、流程相似但細節多變的任務，避免智慧體每次重新發現相同步驟。

4. **科學實驗或實驗室自動化**
   在控制硬體、設定實驗參數、收集量測結果的場景中，技能可封裝「環境設定序列」與「除錯常規」。例如自動化顯微鏡拍攝流程中，技能能穩定化對焦、曝光、儲存路徑與資料驗證步驟，減少因程序漂移造成的實驗失敗。

5. **內容發布與行銷自動化**
   從草稿生成、圖片生成、SEO 檢查到多平台發布，技能可將整條工作流標準化。透過程序性錨點，智慧體能依序呼叫內容生成工具、圖片工具、發布 API，並在每一步執行靜態與運行時驗證，降低人為疏漏。

### 實作前置條件

**資料**
- 足夠數量的成功與失敗執行軌跡（建議至少數百到數千筆 trial records），且任務情境需具備可重複性。
- 每筆軌跡應包含：任務描述、環境狀態、工具呼叫序列、中間輸出、最終結果、驗證步驟。
- 領域專家或具代理框架經驗的工程師，用於開放編碼與建立分類體系（taxonomy）。

**運算**
- 固定且可重現的執行環境（如 Docker），以便進行配對比較（matched comparison）。
- LLM API 或本地模型推理資源，用於軌跡蒸餾、技能生成、檢索與執行。
- Embedding 模型與向量檢索基礎設施，用於離線識別與技能池檢索實驗。
- 足夠的運算預算進行對比實驗：有無技能、Workflow Memory 對照、跨框架測試。

**技能與系統前提**
- 已選定代理框架（如 LangChain、AutoGen、OpenAI Agents SDK 等），並定義工具介面與觀測格式。
- 具備完整的日誌與軌跡追蹤系統，能記錄每次工具呼叫與環境回饋。
- 建立任務驗證機制（自動化測試或人工驗證），以便區分「執行成功」與「僅表面輸出正確」。

### 實作步驟建議

1. **收集與標準化軌跡**
   在固定環境中執行任務，收集原始執行軌跡，並標註成功 / 失敗結果。確保軌跡格式一致，包含環境設定、工具呼叫、輸出與驗證資訊。

2. **建立分類體系（Taxonomy）**
   對軌跡進行開放編碼，識別常見失敗模式（如環境基礎設施失敗、輸出格式不匹配、shell 指令損壞、預算耗盡等），並對應到三大高層類別：技能引導成功、執行與驗證、調用與預算。

3. **蒸餾技能（SKILL.md）**
   從軌跡池中選出具代表性的成功與失敗案例，將其壓縮為結構化知識套件。重點描述「做什麼、檢查什麼、避免什麼」，而非單純貼上原始指令。

4. **設計對照實驗**
   進行三種實驗臂對照：Raw（無記憶）、Workflow Memory（直接工作流記憶）、Skill（標準化技能）。在相同任務與環境下比較，計算聚合任務成功率與各模式分佈。

5. **評估檢索難度**
   建立技能池，從小規模（如 5 個）逐步擴大到 100 個，測量實際使用精確率（actual-use precision）與離線識別表現。加入隨機、相似與不相干的干擾項，觀察易混淆的干擾項對檢索的影響。

6. **測試跨框架穩健性**
   將同一組技能移植到不同代理框架，檢視程序性知識是否仍能有效穩定執行，特別注意工具呼叫格式、環境假設與驗證步驟的差異。

7. **部署與監控**
   在生產環境中啟用技能檢索，但保留「無技能自主執行」的後備路徑。持續監控技能調用率、真值調用比例、下游任務成功率，以及因脆弱假設或不相容情境導致的失敗。

8. **迭代更新**
   根據監控結果與新軌跡，定期修訂技能內容與檢索閾值。避免技能池無限制膨脹，因為研究顯示當技能池從 5 個增至 100 個，實際使用精確率會從 29.6% 降至 3.3%。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **脆弱假設** | 技能內含過度簡化的前提（如「資料庫一定在 localhost:5432」），當環境變動時立即失效。 | 將環境參數外部化，使用動態發現或設定檔；在技能中標註適用條件與版本。 |
| **不相容情境** | 新任務與技能來源的任務表面相似，但工具版本、API 綱要或權限不同。 | 部署前進行跨框架與跨情境測試；在技能中加入「使用前檢查」步驟。 |
| **適應不足** | 智慧體盲目遵循技能，未根據當前任務調整細節。 | 設計「技能引導但非強制」的調用機制，允許模型在檢測到不匹配時偏離技能。 |
| **檢索瓶頸** | 技能池擴大後，實際使用精確率急劇下降，易混淆的干擾項增加。 | 控制技能池規模；使用多階段檢索（embedding 粗排 + agent 精選 + 執行後驗證）；設定動態閾值與後備路徑。 |
| **過度擬合來源軌跡** | 技能過度綁定特定錯誤或特定環境狀態，無法泛化。 | 從多組成功 / 失敗軌跡中蒸餾，避免單一軌跡；定期用新任務進行對比評估。 |
| **錯誤信心** | 即使調用了正確技能，下游仍可能失敗；反之，未調用真值技能有時仍能成功。 | 不要將「真值調用」視為唯一成功指標；同時監控執行層驗證與最終結果。 |

### 與其他技術的整合建議

- **RAG 與向量資料庫**
  將 SKILL.md 視為高階程序文件而非單純事實片段。建議使用專屬的「程序性知識索引」，與一般文件 RAG 分開管理，並在檢索時同時考慮任務意圖與環境上下文。

- **記憶系統（Memory Systems）**
  技能適合長期、穩定的程序知識；短期對話上下文或個人偏好則保留在短期記憶或使用者配置檔中。兩者結合可避免技能過度膨脹，同時保持個人化。

- **可觀測性平台**
  整合軌跡追蹤、工具呼叫日誌與技能調用標註，才能進行配對軌跡分析。建議使用 OpenTelemetry、LangSmith、Phoenix 等工具，將「是否調用技能」「調用是否為真值」「執行階段失敗模式」一併記錄。

- **MLOps / CI 管線**
  將技能生成、檢索評估與跨框架測試納入 CI。每次更新技能池或代理框架版本時，自動執行對比實驗，確保技能效用沒有退化。

- **人機協作（Human-in-the-loop）**
  在技能生成與修訂階段引入領域專家審查；在生產環境中對低信心檢索結果或失敗案例進行人工標註，形成自我演化智慧體的持續回饋迴路。

### 給不同背景讀者的閱讀建議

**初學者**
建議先從「技能是什麼」與「為什麼比原始軌跡更好」開始理解：把技能想像成一份精簡的標準作業程序（SOP），它告訴智慧體「做什麼、檢查什麼、避免什麼」，而不是讓它每次重新摸索。閱讀時可聚焦在摘要、圖 2 的分類體系，以及「程序性錨點」這個核心概念，暫時不必深入檢索實驗的統計細節。

**AI 工程師**
請特別關注實作步驟與風險緩解：如何從軌跡蒸餾 SKILL.md、如何設計有無技能的配對比較、如何評估檢索難度與跨框架穩健性。本文的關鍵啟示是「技能主要穩定執行，而非注入缺失事實」，這會影響你設計技能內容、檢索機制與後備策略的方式。

**研究人員**
本文的貢獻在於提出技能效用的分類體系與對比研究方法論。建議深入閱讀實驗設計、開放編碼流程、三種檢索評估程序（embedding ranking、agent selection、full execution），以及 8,135 筆 trial records 的標準化處理方式。未來可延伸探討自動技能生成、動態適應機制，以及更大規模技能池下的檢索理論。

**產品經理**
請把重點放在「技能何時有幫助、何時會失效」的商業意涵：技能適合高頻、流程可標準化的任務，但不適合變化劇烈或需要大量事實補充的場景。評估時不要只看整體成功率，而要追蹤執行層失敗模式、檢索精確率與維護成本，才能判斷技能投資是否真正降低營運成本並提升可靠性。
