## 摘要翻譯

程式碼搜尋基準測試顯示密集編碼器大幅領先 BM25，然而程式設計代理卻能透過 Grep 表現良好。這個密集優勢究竟衡量了什麼？現有基準測試無法回答這個問題：它們使用策展查詢、舊版程式碼，以及被削弱的 BM25。為了解答這個問題，我們建立了 Repo-Premium，一個真實的程式碼庫層級程式碼搜尋基準測試。它在真實的程式碼庫中對檔案進行排序，涵蓋 Python、JavaScript、TypeScript、Go、Rust 與 Java 的策展查詢與原始查詢，收錄 2022 至 2026 年的拉取請求（PR），並在超過 91 個程式碼庫上建立預先註冊的測試集。我們的實驗將此優勢追溯到兩個來源：有利於密集檢索的評估選擇（例如將檔案分塊以供 BM25 使用，以及將被修改的測試計為相關），以及缺乏程式碼中罕見識別符的查詢。以大語言模型（LLM）生成的識別符擴充查詢（生成後再 Grep）對 BM25 的幫助遠大於密集檢索，使其能在每個 Python 測試集中與密集檢索匹敵，即使是在大語言模型釋出後才開啟的拉取請求上也一樣。我們嘗試的所有方法都無法預測哪個檢索器會在特定查詢中勝出。從這些結果中，我們歸納出三項指引：相對於公平的詞彙基線來衡量密集增益、將密集檢索與 BM25 融合，以及在缺乏程式碼詞彙的查詢中補上對應的詞彙。

### 核心貢獻（3～5點）
- 建立 Repo-Premium 基準測試：在 91 個真實程式碼庫上，以 2022 至 2026 年的拉取請求為基礎，提供涵蓋六種主流程式語言的策展查詢與原始查詢，並採用預先註冊的測試集以避免偏誤。
- 揭示密集優勢的兩大假象來源：現有基準測試因「將檔案分塊供 BM25 使用」與「將被修改的測試計為相關」等評估選擇，以及查詢缺乏罕見識別符，而人為放大了密集檢索的優勢。
- 提出生成後再 Grep（Generate-then-Grep）方法：以大語言模型生成的識別符擴充查詢後，BM25 的表現大幅提升，能在所有 Python 測試集中與密集檢索匹敵，且此效果在模型釋出後的拉取請求上依然成立。
- 證實無法預測最佳檢索器：實驗顯示沒有任何方法能事先判斷哪個檢索器會在特定查詢中勝出，凸顯融合策略的必要性。
- 歸納三項實務指引：應以公平的詞彙基線衡量密集增益、融合密集檢索與 BM25，以及為缺乏程式碼詞彙的查詢補上對應詞彙。

### 適合對象
從事資訊檢索、程式碼智慧（code intelligence）、AI 程式設計代理（coding agent）研究的學者與工程師；關心基準測試設計偏誤與評估方法論的研究者；以及在實務中建構程式碼搜尋系統、需要在密集檢索與詞彙檢索間取捨的業界開發者。

## 深度分析

#### 方法論解析

本文的核心方法論圍繞「重新審視密集檢索（Dense Retrieval）在程式碼搜尋（Code Search）中的真實優勢」這一問題展開，作者透過建構一個更為嚴謹的基準測試（Repo-Premium），並設計一系列控制變數實驗來拆解所謂的「密集溢價」（Dense Premium，即密集編碼器相對於 BM25 的 nDCG@10 領先幅度）。

**1. 基準測試設計：Repo-Premium**

Repo-Premium 的設計哲學在於「真實性」與「公平性」。具體而言：

- **檔案層級標註（File-level Labels）**：不同於以往將檔案切分為片段（Chunking）後再標註的方式，本基準直接在合併的拉取請求（Pull Request, PR）中提取變更檔案清單作為黃金標籤（Gold Label），更貼近實際的程式碼庫定位（Repository Localization）流程。
- **雙重查詢來源**：同時收錄「策展查詢」（Curated Query，如 SWE-bench Verified 的問題描述）與「原始查詢」（Raw Query，如 GitHub PR 原文），以檢驗密集溢價是否依賴於特定查詢風格。
- **時間切割設計**：刻意選取 2022、2023 與 2026 年的 PR，並跳過 2024–2025 年，目的是讓每個時間窗口明確落在編碼器訓練截止日（Training Cutoff）之前或之後，以排除資料污染（Contamination）的疑慮。
- **多語言與預先註冊（Preregistered）測試池**：涵蓋 Python、JavaScript、TypeScript、Go、Rust、Java 六種語言，並建立 91 個程式碼庫的預先註冊測試池（其中包含 539 個鎖箱查詢，Lockbox Queries），以避免事後挑選有利結果的偏誤。

**2. 控制變數實驗設計**

作者採用「固定程式碼快照、標註規則與協議，僅改變查詢來源與時間」的方式，逐一檢驗可能影響密集溢價的因素：

- **BM25 基線的三層次設定**：(a) 未調校 BM25（沿用密集檢索的分塊設定，c=1,000）；(b) 調校 BM25（以整個檔案為索引單位）；(c) 調校 BM25 並加入 LLM 生成的識別符（Anchors），即「生成後再 Grep」（Generate-then-Grep）。
- **標註規則的雙軌制**：同時報告「包含編輯測試檔」（SWE-bench 排除測試，但 PR 變更清單包含）與「僅原始程式檔」（Source-file Only）兩種標註下的結果，以檢驗測試檔是否被錯誤地計入相關檔案。
- **查詢擴展干預**：透過 LLM 為查詢補上程式碼中的罕見識別符（Rare Identifier），觀察 BM25 與密集檢索各自的增益幅度。

**3. 融合策略與路由器實驗**

作者測試了固定排序融合（Rank Fusion）與多種路由器（Router）方案，包括分類器、LLM 判斷器與預先註冊的路由器，以驗證「是否能預測哪個檢索器會在特定查詢上勝出」這一命題。

#### 實驗數據解讀

**1. 評估選擇對密集溢價的膨�效應**

圖 1 顯示，在 Python 的四個查詢池中，密集溢價隨 BM25 基線的強化而顯著縮減：

- 對未調校 BM25（沿用密集檢索的分塊設定）：密集溢價最高可達 +0.3 以上。
- 對調校 BM25（整檔索引）：溢價縮減至 +0.03 至 +0.13。
- 對調校 BM25 並加入 LLM 識別符：溢價在所有 Python 池中消失，BM25 甚至在策展池上顯著領先。

這意味著過去基準測試中觀察到的密集編碼器大幅領先，很大程度上是「基線過弱」所製造的虛假增益（False Gain），而非密集檢索本身的真實優勢。

**2. 標註規則的影響**

在原始查詢池（特別是 RAW-POST，即 2026 年後的 PR）中，將編輯過的測試檔計入相關檔案會使密集溢價翻倍。這暗示 SWE-bench 等基準排除測試檔的做法，可能低估了密集檢索在真實情境下的相對表現，但也可能高估了其在「僅定位原始程式碼」任務中的優勢。

**3. 查詢擴展的不對稱效應**

這是本文最具啟發性的發現之一：當使用同一擴展查詢時，BM25 獲得的增益遠大於密集編碼器。具體而言：

- BM25 在加入 LLM 生成的識別符後，能在所有 Python 池中匹配甚至超越密集檢索，包括 LLM 發布後才開啟的 PR。
- 密集編碼器僅獲得 BM25 增益的一小部分。
- 若僅移除查詢中的識別符（保留散文部分），則對結果毫無影響，證明增益來自於「罕見識別符的加入」而非語意擴展。

**4. 路由器實驗的失敗**

作者嘗試了分類器、LLM 判斷器與預先註冊路由器等多種方案，無一能可靠預測哪個檢索器會在特定查詢上勝出。然而，固定排序融合（將 BM25 與密集檢索的分數結合）在開發集與 539 個鎖箱查詢上均穩定優於任一單獨檢索器，證明「融合」比「路由」更為實用。

**5. 代理評估**

在 96 個任務上讓代理直接呼叫 grep 的實驗顯示，搜尋工具的選擇對代理表現的影響有限，大語言模型（LLM）本身的推理與編輯能力才是瓶頸。這與 Chen and Flaherty (2025) 的實務報告一致。

#### 與現有研究的比較

**1. 與程式碼搜尋基準的比較**

- **CodeSearchNet（Husain et al., 2019）**與 **AdvBench（Muenighoff et al., 2023）**：這些基準使用策展查詢與舊程式碼，且 BM25 基線往往沿用密集檢索的分塊設定。本文指出，這些設計選擇會系統性地膨脹密集溢價。
- **SWE-bench（Jimenez et al., 2024）**：其黃金補丁（Gold Patch）不含測試檔，而 PR 變更清單包含。本文透過雙軌標註規則，量化了這一差異對評估結果的影響。

**2. 與神經排序研究的對話**

本文呼應了 Lin (2018)、Yang et al. (2019)、Kamphuis et al. (2020) 等關於「弱基線導致虛假增益」的警告，並首次將這一批評引入程式碼搜尋領域，證實了類似問題在程式碼檢索中同樣嚴重。

**3. 與混合檢索研究的關係**

Thakur et al. (2021) 已證實混合檢索在多個領域有效；Wang et al. (2023a) 與 Gao et al. (2023) 則展示了 LLM 查詢擴展對 BM25 與密集檢索均有助益。本文的貢獻在於：透過控制變數實驗，揭示了「擴展對 BM25 的幫助遠大於對密集檢索的幫助」這一不對稱效應，並據此提出具體的實務指引。

**4. 與代理研究的張力**

本文與 SWE-bench、DeepSWE（Huang et al., 2026）等代理基準形成有趣對比：代理基準關注端到端分數（End-to-End Score），而本文主張應拆解搜尋、推理、編輯各環節的貢獻。Chen and Flaherty (2025) 的實務報告支持本文觀點——嵌入向量並非代理的瓶頸。

**5. 局限性**

- **語料污染的疑慮**：即使作者刻意選擇 LLM 發布後的 PR，LLM 可能透過預訓練接觸過相關程式碼庫，因此「生成後再 Grep」能匹配密集檢索，可能部分反映 LLM 的記憶而非真正的語意理解。
- **代理評估規模有限**：僅 96 個任務的代理實驗可能不足以支撐「LLM 比搜尋工具更重要」的強結論。
- **語言覆蓋**：雖然涵蓋六種語言，但 Python 仍是主要分析對象，其他語言的結論可能需要更多驗證。

#### 可重現性評估

本文在可重現性方面表現優異：

- **程式碼與資料集公開**：作者在 GitHub（`github.com/hq-bench/repo-premium`）與 Hugging Face（`huggingface.co/datasets/hq-bench/repo-premium`）公開了完整的基準資料集與評估程式碼。
- **預先註冊機制**：91 個程式碼庫的測試池與 539 個鎖箱查詢在實驗前已預先註冊，避免了事後挑選有利子集的可能。
- **完整協議描述**：固定程式碼快照、標註規則與協議，僅改變查詢來源與時間的設計，使變因控制清晰可追溯。
- **統計檢定**：使用程式碼庫聚類的 95% 信賴區間（Repository-clustered 95% CIs），考慮了同一程式碼庫內查詢的非獨立性，這在資訊檢索評估中並非標準做法，值得肯定。
- **編碼器清單透明**：明確列出 13 個密集編碼器，加上 SPLADE 與 ColBERTv2，便於後續研究直接比較或擴展。

唯一可改進之處在於：未明確說明 LLM 查詢擴展所使用的具體模型、提示詞（Prompt）與溫度設定，這些超參數可能對結果有顯著影響。

#### 未來研究方向

**1. 動態查詢擴展策略**

本文證實「生成後再 Grep」能讓 BM25 匹配密集檢索，但每次查詢都需要一次 LLM 呼叫，成本不低。未來可探索：

- 快取機制：對同一程式碼庫的常見查詢模式預先生成識別符。
- 輕量模型：用較小的模型完成識別符生成，降低延遲與成本。
- 自適應觸發：僅在查詢明顯缺乏識別符時才觸發擴展。

**2. 更細緷的路由器設計**

本文證實現有路由器方案均失敗，但這不代表路由不可行。未來可探索：

- 基於查詢特徵（如長度、識別符密度、語言）的簡單啟發式規則。
- 結合不確定性估計的檢索器選擇。
- 在融合框架中學習動態權重，而非固定權重。

**3. 跨語言與跨程式碼庫泛化**

本文以 Python 為主要分析對象，未來應系統驗證三條指引（G1–G3）在 JavaScript、TypeScript、Go、Rust、Java 上的有效性，特別是：

- 不同語言的識別符特性差異（如 Rust 的生命週期標記、Go 的套件命名慣例）。
- 跨語言程式碼庫（如 TypeScript 同時引用 JavaScript）的檢索挑戰。

**4. 代理與檢索的聯合優化**

本文在 96 個任務上觀察到「LLM 比搜尋工具更重要」，但樣本量有限。未來可：

- 在更大規模的代理基準上拆解搜尋、推理、編輯的貢獻。
- 設計能讓代理主動呼叫查詢擴展或融合檢索的協議。
- 探索「搜尋失敗」與「推理失敗」的可區分訊號。

**5. 評估方法論的標準化**

本文揭示了「評估選擇會系統性影響密集溢價」，這對整個資訊檢索社群都有啟發。未來可：

- 推動建立「公平詞彙基線」（Fair Lexical Baseline）的標準協議。
- 在更多領域（如法律、醫療、生物文獻）檢驗類似偏誤是否存在。
- 將「程式碼庫聚類信賴區間」等統計方法推廣為資訊檢索評估的標準做法。

**6. 資料污染的更嚴格控制**

即使本文刻意選擇 LLM 發布後的 PR，仍無法完全排除 LLM 透過預訓練接觸過相關程式碼庫的可能。未來可：

- 使用完全新創的程式碼庫（如競賽中即時生成的程式碼）。
- 設計能區分「語意理解」與「記憶」的查詢類型。
- 探索差分隱私或聯邦學習等技術，在保護智慧財產的同時支援評估。

## 論文問答

**Q1：這篇論文試圖解決什麼核心問題？**
A：這篇論文探討一個核心矛盾：現有的程式碼搜尋基準測試顯示密集編碼器（embeddings）大幅領先 BM25，但實務上許多程式設計代理（coding agents）僅靠 grep 就能表現良好。作者質疑所謂的「密集優勢」（dense advantage）究竟衡量了什麼，並試圖釐清這個差距是真實的能力差異，還是基準測試設計所造成的人為現象。透過建立更貼近真實情境的 Repo-Premium 基準，他們希望回答密集檢索究竟在哪些情境下真正勝出。

**Q2：為什麼現有的程式碼搜尋基準測試無法回答這個問題？**
A：現有基準測試存在三大缺陷：第一，它們使用經策展的查詢（curated queries）搭配老舊的程式碼，無法反映真實的搜尋情境；第二，BM25 的詞彙基線（lexical baseline）通常被刻意弱化，例如沿用密集檢索的分塊（chunking）方式；第三，黃金標籤（gold labels）的定義不一致，例如將被編輯的測試檔案（test files）計入相關結果，這對密集檢索有利。這些評估選擇共同造成了密集檢索的虛假增益（false gain），使得基準測試無法反映真實的檢索效能。

**Q3：為什麼釐清密集檢索的真實優勢對整個領域很重要？**
A：這個問題至關重要，因為團隊會依據基準測試的差距來決定是否建構昂貴的嵌入索引（embedding index）。如果這個差距是評估方式造成的人為現象，那麼許多團隊可能浪費資源在不必要的神經排序（neural ranking）基礎設施上。此外，程式設計代理的端到端分數（end-to-end score）無法區分搜尋失敗、推理失敗或編輯失敗，因此單獨的檢索基準對於診斷系統瓶頸（bottleneck）至關重要。釐清真實優勢也能幫助研究者設計更公平的評估方法。

**Q4：Repo-Premium 這個新基準與現有基準有何不同？**
A：Repo-Premium 是一個真實的程式碼庫層級（repository-level）基準，涵蓋 Python、JavaScript、TypeScript、Go、Rust 和 Java 等六種語言，並包含 2022 至 2026 年的拉取請求（PR）。它最大的特色是「預先註冊」（preregistered）設計：在 91 個程式碼庫上事先註冊測試池，以避免事後調整造成的偏誤。此外，它同時提供策展查詢和原始查詢（raw queries），並允許研究者切換標籤規則（例如是否將編輯過的測試檔案視為相關），從而能夠分離不同評估選擇對結果的影響。

**Q5：「生成後再 grep」（generate-then-grep）方法的創新之處為何？**
A：這個方法的核心理念是：當查詢缺少程式碼中的罕見識別符（rare identifiers）時，由大語言模型（LLM）先補上這些識別符，再交給 BM25 進行詞彙搜尋。其創新在於揭示了密集檢索的優勢其實來自「查詢缺少程式碼詞彙」這個特性，而非真正的語意理解能力。實驗顯示，這個簡單的查詢擴展方法讓 BM25 在每個 Python 測試池中都能匹配甚至超越密集檢索，而且即使在 LLM 釋出後才開啟的拉取請求上也同樣有效。

**Q6：實驗協定中有哪些關鍵的設計選擇？**
A：作者在每個程式碼庫中固定了程式碼快照、標籤規則和協定，只改變查詢來源和變更時間，以確保比較的公平性。他們評估了十三個密集編碼器，加上 SPLADE 和 ColBERTv2 作為對照，並使用「密集溢價」（dense premium）這個指標來量化密集檢索相對於 BM25 的領先幅度。此外，他們刻意跳過 2024 至 2025 年的資料，確保每個時間窗口都明確落在編碼器訓練截止日期之前或之後，以排除資料污染（contamination）的疑慮。

**Q7：這篇論文最重要的實驗發現是什麼？**
A：最重要的發現是：密集檢索的優勢主要來自兩個來源——評估選擇和查詢特性，而非真正的語意理解能力。具體而言，將 BM25 改為索引整個檔案（而非分塊）後，策展查詢的溢價從 +0.121 降至 +0.034；若將編輯過的測試檔案計入相關，原始拉取請求後測試池的溢價會翻倍。更關鍵的是，當用 LLM 補上查詢中缺少的識別符後，BM25 在每個 Python 測試池中都能匹配密集檢索。

**Q8：在不同的評估條件下，密集溢價如何變化？**
A：在最嚴格的條件下（整檔 BM25、不計入編輯測試、補上識別符），密集溢價幾乎完全消失。圖 1 顯示，調校後的 BM25 將溢價縮減至 +0.03 至 +0.13 的範圍；再加上 LLM 生成的識別符後，BM25 在策展查詢池中甚至顯著領先密集檢索。這顯示原始基準測試所報告的大幅領先，很大程度上是評估方式造成的假象，而非真實的效能差距。

**Q9：論文中進行了哪些消融研究（ablation studies）？**
A：作者進行了多項消融研究來分離各因素的影響：比較未調校 BM25（沿用密集檢索的分塊）、調校 BM25（整檔索引）、以及調校 BM25 加上 LLM 生成的識別符三種條件。他們還測試了不同查詢類型（策展 vs. 原始）、不同時間窗口（2022、2023、2026）、不同語言的影響。此外，他們嘗試了分類器、LLM 評判和預先註冊的路由器（router）來預測哪個檢索器會勝出，但所有方法都失敗了，唯一穩定勝出的策略是固定融合（fusion）。

**Q10：這些發現對程式設計代理的實務應用有何啟示？**
A：對程式設計代理而言，最重要的啟示是：在代理評估中，LLM 本身的品質比搜尋工具更重要，因為代理可以直接呼叫 grep 並自行處理結果。這意味著團隊不應過度投資於複雜的嵌入基礎設施，而應專注於提升 LLM 的推理和編輯能力。此外，代理可以動態地決定何時使用密集檢索、何時使用詞彙搜尋，因為兩者擅長的查詢類型不同。

**Q11：基於這些發現，產品設計應如何調整？**
A：產品設計應遵循三項準則：第一，務必以公平的詞彙基線（fair lexical baseline）來衡量密集檢索的增益，包括整檔索引和明確的標籤規則；第二，保留密集檢索並將其與 BM25 融合，因為固定融合在開發資料和 539 個預先註冊的鎖箱（lockbox）查詢上都勝過單一檢索器；第三，當查詢缺少程式碼詞彙時，先用一次 LLM 呼叫補上識別符再進行搜尋，這特別適合不常被搜尋的程式碼庫。

**Q12：這篇論文對程式碼搜尋領域的整體影響是什麼？**
A：這篇論文挑戰了「密集檢索必然優於詞彙檢索」的普遍信念，促使研究者重新審視基準測試的設計。它強調了評估方法論的重要性，呼籲未來的研究應使用更公平、更透明的比較方式。此外，論文推廣了「生成後再 grep」這種簡單而有效的方法，可能會影響下一代程式碼搜尋工具的設計方向，並促使更多人關注混合檢索（hybrid retrieval）的價值。

**Q13：這篇論文承認哪些限制？**
A：作者承認幾項限制：首先，雖然他們測試了六種程式語言，但每種語言的程式碼庫數量並不均衡，可能影響結論的普適性。其次，「生成後再 grep」需要 LLM 知道相關的識別符，這在某些情境下可能無法滿足，例如當程式碼庫非常新穎或領域專門時。第三，他們無法預測哪個檢索器會在某個特定查詢上勝出，這意味著無法為每個查詢動態選擇最佳檢索器。

**Q14：論文中識別了哪些失敗案例？**
A：最顯著的失敗案例是：所有嘗試預測哪個檢索器會在某個查詢上勝出的方法都失敗了，包括分類器、LLM 評判和預先註冊的路由器。這意味著即使我們知道兩種檢索器擅長不同類型的查詢，也無法可靠地進行查詢級別的路由（routing）。另一個失敗案例是：當查詢完全沒有程式碼詞彙時，密集檢索的優勢仍然存在，但這也意味著密集檢索並非真正「理解」語意，而是依賴某種我們尚未完全理解的機制。

**Q15：這篇論文提出了哪些未來研究方向？**
A：作者提出了幾個未來方向：首先，需要更深入地理解密集檢索在程式碼搜尋中真正擅長什麼，因為目前的解釋（語意匹配）似乎過於簡化。其次，需要研究如何可靠地預測每個查詢的最佳檢索器，以實現真正的自適應混合檢索。第三，「生成後再 grep」的成功表明，查詢擴展（query expansion）可能是比建構更大嵌入模型更具成本效益的方向，值得進一步探索。最後，將這些發現應用於程式設計代理的端到端評估中，以驗證其在實際任務中的價值。

### 潛在風險與注意事項

**風險一：標籤定義不一致**
- 將測試檔案納入相關檔案會顯著膨脹密集檢索的優勢；若與 SWE-bench 比較，務必先確認雙方對測試檔案的處理方式。
- **緩解**：在所有實驗中同時報告「含測試」與「不含測試」兩種標籤規則下的結果。

**風險二：訓練資料污染**
- 若程式碼快照早於嵌入模型的訓練截止日期，評估結果可能高估真實表現。
- **緩解**：保留至少一個「晚於模型發布」的 PR 池（如論文的 RAW-POST），作為污染偵測指標。

**風險三：LLM 擴充查詢的可重現性**
- 不同 LLM 版本對同一查詢可能產生不同識別符，導致結果波動。
- **緩解**：固定 LLM 版本與溫度參數；記錄每次擴充的完整 prompt 與輸出，便於回溯。

**風險四：融合權重難以調校**
- RRF 的 k 值或線性融合的權重若過度擬合驗證集，在 lockbox 上可能失效。
- **緩解**：採用簡單的等權融合（如 RRF k=60），根據論文結果已足夠穩健。

**風險五：忽略代理整體表現**
- 搜尋子系統的進步未必反映在端到端代理分數上；論文中亦指出「在代理中，LLM 比搜尋工具更重要」。
- **緩解**：以代理任務（如 SWE-bench）作為最終驗證，而非僅看搜尋指標。

**風險六：多語言支援差異**
- 論文顯示 Python 池中 BM25 表現最佳，其他語言（Rust、Go、Java 等）的相對優勢可能不同。
- **緩解**：在目標語言上獨立評估，避免直接外推 Python 的結論。

- 將每筆查詢的檢索路徑（BM25 命中、嵌入命中、融合排名）寫入日誌，供後續分析與除錯。
- 當使用者回報「搜尋結果不準」時，可快速定位是哪個檢索器失效。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與三條指引（G1–G3），理解「密集檢索未必全面優於 BM25」這個核心訊息即可，不必深入數學細節。若想動手實作，可從「整檔 BM25 + LLM 擴充查詢」這個最小可行流程開始，使用 Pyserini 與 OpenAI API 即可在數小時內重現論文的主要結論。

**給 AI 工程師**：重點關注第 5 節的實驗設計，特別是「標籤規則」「chunking 對 BM25 的影響」「融合策略」三個面向。在實務系統中，建議直接採用「BM25 + 嵌入融合 + LLM 查詢擴充」的組合，並以 lockbox 測試集驗證穩定性。論文中的 Repo-Premium 基準可作為評估自家系統的起點。

**給研究者**：本論文展示了「基準設計如何系統性地偏袒特定方法」這個值得深究的方向。建議延伸閱讀相關的基準設計文獻（Lin, 2018; Yang et al., 2019; Kamphuis et al., 2020），並思考在程式碼檢索之外，其他領域（如法律、醫療文件）是否存在類似的虛假增益問題。此外，「無法預測哪個檢索器會贏」這個負面結果本身也是重要的研究訊號。

**給產品經理**：核心訊息是「不要盲目相信嵌入向量比 grep 好」這個行銷說法。在評估程式碼搜尋工具時，務必詢問供應商：(1) BM25 基線是否使用整檔索引？(2) 標籤是否包含測試檔案？(3) 是否支援混合檢索？這些問題的答案往往比「nDCG@10 提升幾個百分點」更能反映真實價值。同時，論文中「在代理中 LLM 比搜尋工具更重要」的結論提醒我們，搜尋只是整體系統的一環，過度投資於此可能邊際效益遞減。
