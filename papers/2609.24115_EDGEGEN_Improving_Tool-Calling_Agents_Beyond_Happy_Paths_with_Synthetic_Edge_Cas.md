# EDGEGEN：透過合成邊緣案例生成提升會呼叫工具的 LLM 代理超越快樂路徑的表現

**原文標題：** EDGEGEN: Improving Tool-Calling Agents Beyond Happy Paths with Synthetic Edge Case Generation  
**作者：** Harshavardhan Abichandani、Penny Chong、Jiyuan Shen 等 10 位作者  
**發布日期：** 2026-09-21

## ⚡ TL;DR

現有合成任務生成多為通用快樂路徑，忽略代理狀態與資料庫，難以評估政策違規等邊緣案例。
提出 EDGEGEN，自動萃取合規規則並列舉違規組合，生成資料庫導向的邊緣案例任務並驗證有效性。
於 tau2bench 上，微調進步 2%–42%，harness 最佳化提升 10% 與 30%。

## 摘要翻譯

會呼叫工具的 LLM 代理（Tool-Calling LLM Agent）已日益部署於企業應用（Enterprise Application）中。然而，有效的評估（Evaluation）與最佳化（Optimization）需要高品質且多樣化的任務資料集（Task Dataset），但由於隱私限制（Privacy Constraint）與其他限制，這類資料集往往難以取得。現有的合成任務生成（Synthetic Task Generation）方法通常會產生忽略代理（Agent）底層狀態（Underlying State）或資料庫的通用任務（Generic Task），無法反映真實世界使用多樣性（Real-World Usage Diversity）。我們提出 EdgeGen，這是一個合成任務生成框架，可從代理規格書（Agent Specification）中萃取合規規則（Compliance Rule），並利用這些規則生成資料庫導向任務（Database-Grounded Task）的邊緣案例（Edge Case），這些任務旨在違反上述規則。當與現有的合成資料生成（Synthetic Data Generation）技術結合時，EdgeGen 可透過微調（Finetuning）與 harness 最佳化（Harness Optimization）來改進代理。所形成的流程是一個無需人工標註（Human Annotation）的全自動化（Fully Automated）閉迴路系統（Closed-Loop System）。使用 EdgeGen 生成的資料進行微調，在 tau2bench 航空領域上可帶來穩定的 2% 至 42% 平均 progress 改善（Mean Progress Improvement），而其他基線方法（Baseline Method）則在某些模型上出現退化（Degradation）。另一方面，針對 harness 最佳化，我們的方法在 Gemma-4-e4b 模型上，相較於人工策劃的 harness（Human-Curated Harness）與基礎 harness（Base Harness）分別帶來 10% 與 30% 的平均 progress 改善。

### 核心貢獻（3～5點）
- 提出 EdgeGen，一個從代理規格書（Agent Specification）自動萃取合規規則（Compliance Rule）並生成資料庫導向任務（Database-Grounded Task）之邊緣案例（Edge Case）的合成任務生成框架。
- 結合現有合成資料生成（Synthetic Data Generation）技術，建立無需人工標註（Human Annotation）的全自動化（Fully Automated）閉迴路系統（Closed-Loop System），可同時支援微調（Finetuning）與 harness 最佳化（Harness Optimization）。
- 在 tau2bench 航空領域上，EdgeGen 生成的微調資料可帶來 2% 至 42% 的平均 progress 改善（Mean Progress Improvement），且相較於基線方法（Baseline Method）更穩定，未出現退化（Degradation）。
- 在 harness 最佳化上，針對 Gemma-4-e4b 模型，EdgeGen 相較於人工策劃的 harness（Human-Curated Harness）與基礎 harness（Base Harness）分別帶來 10% 與 30% 的平均 progress 改善。

### 適合對象
適合從事 LLM 代理（LLM Agent）開發、工具呼叫代理評估與最佳化、合成資料生成（Synthetic Data Generation）、企業應用（Enterprise Application）自動化測試，以及關注代理在政策遵循（Policy Compliance）與邊緣案例（Edge Case）下可靠性（Reliability）的研究人員與工程師。

## 深度分析

#### 方法論解析

EDGEGEN 的核心貢獻在於將「合成任務生成（Synthetic Task Generation）」從傳統的「快樂路徑（Happy Path）」導向，轉向以「規則違反（Rule Violation）」為驅動的「邊緣案例（Edge Case）」導向。其方法論可拆解為以下環節：

1. **合規規則萃取（Compliance Rule Extraction）**  
   系統從「代理規格書（Agent Specification）」或「政策文件（Policy Document）」中自動抽取出業務規則集合 \(R\)。為控制組合爆炸，論文只保留最重要的五條規則，形成最多 \(2^5=32\) 個子集合，再經可行性過濾。這一步確保後續生成的任務不是隨機的，而是有明確的「政策違規（Policy Violation）」目標。

2. **違規情境列舉（Violation Scenario Enumeration）**  
   透過對規則集合取冪集（power-set），EDGEGEN 系統性地列舉單一規則違反、多規則同時違反等組合。這種結構化列舉能夠覆蓋從簡單單一工具互動到複雜多步驟工作流程（Multi-Step Workflow）的各種難度，並明確標註每個測試案例意圖挑戰的規則子集合 \(S\subseteq R\)。

3. **資料庫導向的任務建構（Database-Grounded Task Construction）**  
   每個測試案例被形式化為四元組 \(x=\langle q,w,A,S\rangle\)：
   - \(q\)：以真實資料庫狀態（Database State）中的具體值為基礎的自然語言使用者請求（Request）；
   - \(w=\{t_i,\dots,t_k\}\)：預期的工具呼叫序列；
   - \(A=\{a_1,\dots,a_n\}\)：用於判斷代理是否成功的自然語言斷言（assertions）；
   - \(S\)：本案例意圖違反或壓力測試的規則集合。  
   這種表示法讓「預期回應（Expected Response）」——無論是執行、拒絕（Refusal）或核准／拒絕（Approval or Denial）——都變得可驗證（Verifiable）。

4. **情境感知 SQL 代理（Scenario-Aware SQL Agent）**  
   為了避免生成與底層狀態（Underlying State）脫節的通用任務（Generic Task），EDGEGEN 使用一個情境感知 SQL 代理（Scenario-Aware SQL Agent）查詢合成關聯式資料庫（Relational Database），取回能讓特定違規情境成立的具體數值。這保證了任務不僅在語意上合理，也在資料庫層面可行。

5. **有效性驗證與收錄（Validity Verification & Admission）**  
   每個生成的任務在納入資料集前都需通過有效性驗證。雖然提供的片段在「兩個條件」處中斷，但從上下文可推斷驗證至少包含：任務在當前資料庫狀態下可執行，以及相關身份或狀態條件一致。這道閘門對於防止「幻覺式」邊緣案例至關重要。

6. **閉迴路代理改進流程（Closed-Loop Agent Improvement Pipeline）**  
   EDGEGEN 與一個合成資料庫生成方法（Anonymous, 2026）結合：合成資料庫提供環境狀態（Environment State），EDGEGEN 生成資料庫導向任務（Database-Grounded Task），產生的軌跡再用於「微調（Finetuning）」與「harness 最佳化（Harness Optimization）」。整個流程無需人工標註（Human Annotation）或生產日誌（Production Log），形成全自動化的閉迴路系統（Closed-Loop System）。

整體而言，EDGEGEN 的設計重點在於把「資料多樣性」從單純的語言或工具變化，提升到「政策規則空間的結構化覆蓋」。這使得生成的資料能夠系統性地探測代理的失效模式（Failure Mode），而非僅僅重複常見的快樂路徑。

#### 實驗數據解讀

論文在兩個主要基準上進行評估：以航空公司客服為主的 τ2-Bench（airline domain）以及具狀態約束的 ToolSandbox。評估指標為「progress（progress，論文使用的評估指標）」，雖然片段未詳細定義，但可合理推測它衡量代理完成任務或滿足斷言的比例。

**微調（Finetuning）結果**  
在 τ2-Bench airline domain 上，使用 EDGEGEN 資料進行微調後，不同模型的平均 progress 改善介於 2% 至 42% 之間。其中 Qwen 2.5-3b 相對於基礎版本獲得 +42% 的平均 progress 提升。這幾個觀察值得注意：

- **小中型模型受益最明顯**：大型模型可能已經在快樂路徑上表現良好，而小型模型在面對罕見邊緣案例（Rare Edge Case）時更容易出錯，因此針對性資料帶來的邊際效益最大。
- **一致性改善 vs. 基線退化**：相較於其他基線方法（Baseline Method）在某些模型上出現效能退化（Degradation），EDGEGEN 在所有受測模型上都呈現正向改善。這暗示基線合成資料可能強化了錯誤行為或過度擬合模板化評估（Templated Evaluation），而 EDGEGEN 的違規導向資料則能穩定提升政策遵循能力。
- **對人工策劃測試集的遷移性**：儘管訓練資料完全來自合成生成，模型在人工策劃的測試集上仍有提升，顯示 EDGEGEN 生成的邊緣案例具有真實世界使用多樣性（Real-World Usage Diversity）的代表性。

**Harness 最佳化結果**  
對於 Gemma-4-e4b 模型，EDGEGEN 在 τ2-Bench airline domain 上的 harness 最佳化相較於「人工策劃的 harness（Human-Curated Harness）」提升 10%，相較於「基礎 harness（Base Harness）」提升 30%。這說明：

- 人工策劃的 harness 仍存在覆蓋率（Coverage）缺口，無法充分捕捉邊緣案例；
- EDGEGEN 不僅能產生訓練資料，也能反過來改進評估框架本身，使其對規則違反情境更敏感。

**解讀限制**  
提供的片段缺少完整表格、樣本數、變異數與 confidence interval，也沒有說明 progress 的精確計算方式。2% 到 42% 的區間相當寬，暗示效果可能高度依賴模型規模、領域與任務難度。未來若能看到更細緻的拆解（例如單一規則違反 vs. 多規則同時違反、不同難度等級），將有助於判斷 EDGEGEN 的優勢來源。

#### 與現有研究的比較

**相較於合成資料／任務生成研究**  
Self-instruct、APIGen、APIGen-MT 與 ToolACE 等研究奠定了從 LLM 自舉生成函式呼叫資料、多輪工具使用資料與複雜度控制對話資料的基礎。然而，這些方法主要關注 API 多樣性、對話流暢度與可驗證性，並未系統性地針對「業務規則（Business Rule）」違反進行生成。EDGEGEN 透過「規則萃取（Rule Extraction）」與「冪集列舉」填補了這一缺口，使合成資料能夠主動探測政策違規情境。

**相較於 TaskBench 與 FuncBenchGen**  
TaskBench 採用工具圖取樣策略（Node、Chain、DAG）來建構工作流程；FuncBenchGen 則從函式綱要以程式化方式指派數值。兩者的共同限制在於：它們不會系統性地列舉行為規則違反空間，也不會把任務扎根於真實資料庫狀態。EDGEGEN 的改進在於：第一，以規則子集合為核心進行結構化覆蓋；第二，使用情境感知 SQL 代理（Scenario-Aware SQL Agent）取回實際資料庫狀態，確保任務可執行且一致。

**相較於代理評估基準**  
τ-Bench、τ2-Bench、ToolSandbox、AgentBench、WorkArena、API-Bank、MINT、AgentBoard 等提供了高品質的人工策劃測試案例，但它們本身並不提供自動擴充測試案例的合成資料層。EDGEGEN 的定位是這些基準的互補工具：它能夠自動生成額外的訓練與評估資料，並透過 harness 最佳化提升既有評估框架的覆蓋率。

**主要限制**  
- **規則萃取品質**：整個流程高度依賴從政策文件自動抽取規則的準確率；若規則萃取有誤，後續所有違規情境都會偏離目標。
- **Top-5 規則上限**：只選擇五條最重要規則雖然控制計算量，但可能遺漏低優先級卻仍具風險的規則。
- **情境感知 SQL 代理的能力邊界**：對於涉及複雜業務邏輯或跨表約束的規則，SQL 代理可能無法保證總能找到可行解。
- **合成資料庫的真實性**：合成資料庫生成方法（Anonymous, 2026）必須準確編碼業務規則，否則生成的邊緣案例會與真實部署環境脫節。
- **領域侷限**：目前實證主要集中在航空公司與零售風格領域，對於其他企業應用（Enterprise Application）的泛化能力仍需更多驗證。

#### 未來研究方向

1. **擴展規則覆蓋範圍**  
   目前僅限於最重要的五條規則，未來可引入規則重要性排序、層次式規則分解或迭代式規則擴充，以在控制計算成本的同時提升覆蓋率（Coverage）。

2. **強化情境感知 SQL 代理**  
   可結合約束滿足問題（CSP）求解器或符號推理，讓 SQL 代理能處理更複雜的業務規則與更大規模的資料庫，並提供可行性保證。

3. **跨領域與多語言驗證**  
   將 EDGEGEN 應用於金融、醫療、法律等更多企業領域，並測試其在多語言政策文件上的規則萃取與任務生成能力。

4. **結合強化學習與偏好最佳化**  
   除了監督式微調，可將生成的邊緣案例作為正負樣本對，應用於 RLHF、DPO（Direct Preference Optimization）等方法，進一步改善代理的拒絕與執行決策。

5. **人機協作驗證**  
   引入少量人工審查來校正規則萃取錯誤與誤判的可行性過濾，在自動化與資料品質之間取得平衡。

6. **動態規則與分佈偏移研究**  
   探討當政策文件更新或真實資料庫分佈與合成資料庫存在差異時，EDGEGEN 生成資料的穩健性與遷移能力。

7. **Harness 最佳化的原則化方法**  
   發展以邊緣案例覆蓋率為目標的系統化 harness 最佳化演算法，並將其與自動化紅隊測試（Automated Red-Teaming）結合。

8. **隱私與安全導向的合成資料庫生成**  
   在保留業務規則語義的前提下，確保合成資料庫不會洩漏敏感模式，滿足企業應用中的隱私限制（Privacy Constraint）。

## 論文問答

**Q1：EDGEGEN 主要想解決工具呼叫型 LLM 代理在企業應用中的什麼問題？**
A：EDGEGEN 針對的是企業級 LLM 代理在真實部署時，必須同時處理多步驟工具呼叫、查詢資料庫並遵守複雜業務政策的挑戰。現有評估往往只涵蓋常見的「快樂路徑」，忽略了代理在罕見邊緣案例（rare edge cases）下應該執行或拒絕的判斷能力。因此，EDGEGEN 旨在自動生成多樣化且資料庫導向的邊緣案例任務，以系統性地探測代理的失效模式，特別是「何時應該拒絕」這類政策遵循問題。

**Q2：現有的合成任務生成方法為何在代理評估與改進上不足？**
A：現有方法如 Self-instruct、APIGen 或 FuncBenchGen 通常產出較為通用或模板化的任務，這些任務往往忽略了代理底層的資料庫狀態與業務規則。它們缺乏對政策違規情境的結構化列舉，因此難以覆蓋真實世界中因資料庫狀態不同而產生的邊界案例。結果是，代理可能在狹窄的評估上表現良好，卻在需要判斷核准或拒絕的實際情境中失效。

**Q3：為什麼覆蓋邊緣案例與邊界案例對穩健的代理評估如此重要？**
A：在企業應用中，同一個使用者請求（例如取消訂位）可能因資料庫狀態不同而需要核准或拒絕，這使得單純測試「能否執行流程」不足以保證可靠性。邊界案例的價值在於將請求與一致且可驗證的資料庫狀態配對，從而檢驗代理是否做出正確的合規決策。若評估資料只包含快樂路徑，代理的潛在失效模式將在部署後才暴露，導致政策違規或使用者體驗下降。

**Q4：EDGEGEN 的核心方法流程是什麼？**
A：EDGEGEN 首先從代理規格書或政策文件中自動萃取合規規則（compliance rules），然後對這些規則進行組合列舉，產生意圖違反特定規則子集的違規情境。接著，它使用情境感知 SQL 代理（scenario-aware SQL agent）在合成資料庫中尋找使該情境可行的具體數值，並在收錄前驗證每個生成任務的有效性。最終產出的任務包含使用者請求、工具執行序列、自然語言斷言（assertions）以及目標違規規則集合，形成可驗證的訓練與評估資料。

**Q5：相較於先前的合成資料方法，EDGEGEN 的關鍵創新在哪裡？**
A：EDGEGEN 的關鍵創新在於以「違規驅動」的方式生成任務，系統性地列舉業務規則的冪集組合來產生邊緣案例，而非隨機或模板化地產出通用任務。其次，它強調資料庫導向（database-grounded），每個任務都與可執行的資料庫狀態緊密結合，確保情境真實且可驗證。最後，它與合成資料庫生成方法結合，形成無需人工標註、無需生產日誌的全自動閉迴路代理改進流程。

**Q6：EDGEGEN 在規則選擇與可行性控制上做了哪些設計決策？**
A：為了控制組合爆炸，EDGEGEN 將萃取出的規則限制為最重要的五條，這樣最多只會產生 2⁵＝32 個規則子集，並在後續進行可行性過濾。對於每個選定的規則子集，情境感知 SQL 代理會在資料庫中抽樣出具體數值，確保該違規情境在當前資料庫狀態下確實可能發生。生成後還會經過有效性驗證（validity verification），只有符合資料庫一致性且斷言可驗證的任務才會被收錄進資料集。

**Q7：論文在哪些基準測試與模型上評估 EDGEGEN？**
A：實驗主要在 τ²-Bench 的航空領域（airline domain）以及 ToolSandbox 上進行，這兩個基準分別提供真實的多輪客服情境與具狀態約束的工具設備管理環境。評估涵蓋多個模型家族與不同規模，例如 Qwen 2.5-3b 與 Gemma-4-e4b，並比較基礎模型、其他合成生成基線方法以及人工策劃 harness 的表現。測試方式包括監督式微調（supervised finetuning）與 harness 最佳化（harness optimization）。

**Q8：EDGEGEN 在實驗中取得了哪些關鍵量化結果？**
A：在 τ²-Bench 航空領域上，使用 EDGEGEN 資料進行微調後，模型的平均 progress 改善幅度介於 2% 到 42% 之間，其中 Qwen 2.5-3b 相較基礎版本平均進步達 42%。相較之下，其他基線合成方法在某些模型上反而出現效能退化。在 harness 最佳化方面，針對 Gemma-4-e4b 模型，EDGEGEN 相較人工策劃的 harness 提升約 10%，相較基礎 harness 提升約 30%。

**Q9：從比較與消融的角度可以得出什麼結論？**
A：實驗顯示 EDGEGEN 能跨模型家族與基準測試帶來一致性的進步，而單純依賴現有合成技術的基線方法則無法保證穩定改善，甚至在部分模型上造成退化。這說明僅增加資料量或任務多樣性並不足夠，明確針對邊緣案例與政策違規進行覆蓋才是關鍵。此外，較小與中型模型從這類資料中獲益最明顯，顯示 EDGEGEN 對於提升資源受限企業部署模型的可靠性特別有價值。

**Q10：哪些實際企業場景最能受惠於 EDGEGEN？**
A：EDGEGEN 特別適合需要根據即時資料庫狀態判斷核准或拒絕的客服與業務流程，例如航空訂位取消、退款、換貨或會員權益查詢。在金融、醫療或電商等高度受規範的領域，代理必須嚴格遵守政策，而 EDGEGEN 能自動生成符合隱私限制的合成資料來訓練與評估這些代理。由於不需要真實生產日誌或人工標註，它也能幫助企業在資料敏感或標註成本高昂的情境下持續改進代理。

**Q11：在產品化與部署 EDGEGEN 時需要考慮哪些因素？**
A：首先，政策文件與工具 schema 的品質會直接影響規則萃取的準確性，若原始規格書含糊不清，生成的邊緣案例可能失真。其次，合成資料庫必須能夠忠實編碼業務規則，並配合有效性驗證避免將不一致的任務收錄進訓練集。雖然 EDGEGEN 省去人工標註成本，但仍需監控生成過程中可能出現的規則遺漏或幻覺，並確保與現有 harness、微調流程或強化學習管線順利整合。

**Q12：EDGEGEN 對代理評估與合成資料領域可能帶來什麼更廣泛的影響？**
A：EDGEGEN 將評估焦點從單純的「快樂路徑覆蓋」轉向系統性的「失效模式探測」，有助於建立更嚴謹的代理安全與合規評估標準。它提供了一種可擴展、隱私友善的方式來產生高品質訓練與評估資料，可能成為未來企業代理開發流程中的標準元件。此外，其全自動閉迴路設計也啟發未來基準測試加入合成資料擴充層，以持續擴展測試覆蓋率並支援代理自動最佳化。

**Q13：論文已經承認或暗示了哪些限制？**
A：EDGEGEN 目前將萃取的規則限制為最重要的五條，雖然控制了計算成本，但也可能遺漏較細微或互動複雜的政策條文。此外，整個流程高度依賴政策文件品質與合成資料庫能否正確編碼業務規則，若這些輸入有偏誤，生成的邊緣案例也會跟著偏誤。儘管有可行性過濾與有效性驗證，它仍無法保證涵蓋所有真實世界中的罕見邊緣案例。

**Q14：在哪些失效案例中，EDGEGEN 生成的任務仍可能不足？**
A：當政策本身模糊或需要常識與外部世界知識（而非單純資料庫狀態）才能判斷時，EDGEGEN 可能難以生成有意義的邊緣案例。若情境涉及動態外部環境、多輪對話中的對抗性使用者行為，或需要跨多個異質資料源推理，現有設計也可能覆蓋不足。此外，若情境感知 SQL 代理無法為高度複雜的規則組合找到可行資料庫狀態，或規則萃取不完整，則某些關鍵違規情境將被遺漏。

**Q15：未來可以朝哪些方向擴展 EDGEGEN？**
A：未來可擴展規則萃取機制，處理超過前五條規則、階層式規則以及數值型約束，以提升覆蓋率。也可引入更真實的使用者模擬與對抗性對話生成，讓邊緣案例不僅限於單輪請求，而是涵蓋多輪互動中的誤導與堅持。另外，將 EDGEGEN 應用於多代理系統、部分可觀測環境，或與強化學習結合進行線上探索，並發展更豐富的斷言語言與領域專用規則萃取，都是值得深入的研究方向。

## 實務應用指南

### 適用場景

1. **企業客服代理的合規壓力測試**  
   航空公司或零售業的客服 LLM 代理經常處理取消、退換貨、升艙等請求。EDGEGEN 可從政策文件萃取「取消前須驗證身份」「特價機票不可退」等合規規則，並自動生成資料庫導向的違規情境，例如「未驗證身份即要求全額退款」，用於補強快樂路徑以外的罕見邊緣案例。

2. **金融服務的授信與交易授權代理**  
   銀行或保險業的代理在處理貸款審批、KYC 更新或大額轉帳時，必須遵守多條業務規則。透過 EDGEGEN 可系統化生成「收入證明過期仍申請高額貸款」「跨境交易未達風險門檻卻要求即時放行」等邊界案例，提升代理在關鍵決策點的可靠性。

3. **醫療與保險理賠審查代理**  
   理賠代理需判斷申請是否符合給付條件、是否需補件或拒絕。EDGEGEN 能根據理賠政策生成「診斷碼與保單條款衝突」「重複申請同一療程」等違規情境，並將任務 grounded 於合成關聯式資料庫，確保預期回應可驗證。

4. **IT 與設備管理代理**  
   類似 ToolSandbox 的場景，企業內部代理管理裝置狀態、權限與維修流程。EDGEGEN 可生成「未解除前使用者綁定即轉移裝置」「維修狀態為進行中卻要求報廢」等狀態相依的邊緣案例，強化代理對環境狀態的敏感度。

5. **內部流程與人力資源代理**  
   請假、採購、權限申請等內部流程代理常因政策細節而失敗。EDGEGEN 可從內部規章萃取規則，生成「試用期員工申請超過天數的特休」「預算科目不符仍提交採購」等情境，作為微調與 harness 最佳化的訓練素材。

### 實作前置條件

**資料與文件**
- 代理規格書或政策文件：需清楚描述業務規則、核准／拒絕條件與多步驟工作流程。
- 工具定義與 API schema：包含每個工具的輸入輸出、可執行的資料庫操作。
- 資料庫結構描述：關聯式資料庫的表格、欄位與外鍵關係，用於合成資料庫生成與任務 grounded。

**運算資源**
- LLM API 存取：用於規則萃取、情境生成、自然語言斷言生成與情境感知 SQL 代理。
- 資料庫執行環境：可執行 SQL 並驗證任務可行性的沙箱。
- 微調或 harness 最佳化資源：根據模型規模，可能需要 GPU 叢集或雲端微調服務。

**技術能力**
- 熟悉提示工程與 LLM 代理設計。
- 具備 SQL 與關聯式資料庫知識。
- 了解工具呼叫（tool-calling）評估指標，如 progress。
- 具備微調（SFT）或測試框架最佳化的實作經驗。

### 實作步驟建議

1. **整理政策文件與工具規格**  
   將現行政策文件、系統提示詞、工具 schema 與資料庫結構彙整成可供 LLM 處理的輸入格式。

2. **自動萃取合規規則**  
   使用 LLM 從政策文件中提取結構化業務規則，例如「修改預訂前須驗證身份」「特價商品不可退換」。

3. **建立合成資料庫**  
   根據萃取出的規則與資料庫結構，生成編碼這些業務規則的合成關聯式資料庫，作為後續任務的底層狀態。

4. **列舉違規組合並生成任務**  
   對重要規則進行組合列舉，產生意圖違反一條或多條規則的違規情境，並由情境感知 SQL 代理從資料庫中抓取使任務可行的一致狀態。

5. **驗證任務有效性**  
   對每個生成的任務進行可行性與有效性驗證，確保使用者請求、資料庫狀態與預期回應（核准或拒絕）彼此一致，再收錄至資料集。

6. **微調或 harness 最佳化**  
   將收錄的合成資料用於監督式微調，或作為 harness 最佳化的評估依據，反覆迭代代理行為。

7. **在人工策劃測試集上驗證**  
   雖然整個流程無需人工標註，但仍建議在現有人工策劃的測試集或生產日誌抽樣上驗證，確認沒有過度擬合合成資料。

8. **部署與持續監控**  
   將改進後的代理部署至測試環境，並持續收集失敗案例，作為下一輪 EDGEGEN 規則更新與資料生成的輸入。

### 潛在風險與注意事項

- **規則萃取不完整**  
  若政策文件模糊或 LLM 萃取遺漏關鍵規則，生成的邊緣案例會失去代表性。建議結合領域專家審查萃取結果，並保留規則更新機制。

- **合成資料庫與真實分布落差**  
  合成資料庫雖能編碼規則，但數值分布可能與真實生產資料不同。可透過統計對齊或從去識別化樣本學習分布來緩解。

- **過度擬合合成邊緣案例**  
  模型可能學會應對合成任務的特定模式，卻在真實對話中表現不佳。建議保留一定比例人工策劃或生產日誌抽樣作為驗證集。

- **評估指標與業務目標脫節**  
  progress 等指標未必完全對應使用者滿意度或營運風險。應將 EDGEGEN 的評估結果與人工抽檢、A/B 測試結合解讀。

- **隱私與安全**  
  雖然 EDGEGEN 強調無需生產日誌，但若使用真實政策文件或部分去識別化資料，仍需確認無個資外洩風險，並對合成資料庫進行敏感資訊檢查。

### 與其他技術的整合建議

- **與 RAG 系統整合**  
  將 EDGEGEN 萃取出的合規規則與違規情境納入檢索增強生成（RAG）的知識庫，使代理在推理時能動態參考政策邊界。

- **銜接現有評估框架**  
  可將生成任務匯出為 τ-bench、τ2-bench 或 ToolSandbox 相容格式，補充現有人工策劃 harness 的覆蓋率。

- **嵌入 CI/CD 流程**  
  在每次代理或政策更新後，自動執行 EDGEGEN 生成新任務並跑回歸測試，形成持續評估的閉迴路。

- **結合監控與可觀測性工具**  
  將生產環境中發現的失敗模式回饋至規則萃取模組，讓邊緣案例資料集隨實際失效模式演進。

- **對接現有微調框架**  
  EDGEGEN 產生的軌跡資料可直接餵入 Hugging Face TRL、Axolotl 或雲端微調服務，降低從資料生成到模型改進的銜接成本。

### 給不同背景讀者的閱讀建議

**給初學者**  
這篇論文提出了一種讓 AI 代理更「守規矩」的方法：不是只測試正常流程，而是自動生成各種可能違反規定的刁鑽情境來訓練代理。你可以把 EDGEGEN 想像成一位自動出考題的老師，專門設計陷阱題，讓代理學會在複雜情況下做出正確判斷。

**給 AI 工程師**  
本文的核心貢獻在於將政策文件轉化為結構化規則，並透過規則組合列舉與情境感知 SQL 代理，生成可執行、可驗證的資料庫導向任務。建議關注第 3 節的問題形式化、規則萃取提示詞設計，以及有效性驗證機制，這些都是落地時可直接複用的工程細節。

**給研究人員**  
EDGEGEN 在合成資料生成與代理評估之間建立了一個閉迴路，並以違規驅動（violation-driven）的方式擴展覆蓋率。未來可延伸的方向包括：更細緻的規則重要性排序、跨領域遷移學習、以及將此方法與強化學習或形式化驗證結合。

**給產品經理**  
這項技術能幫助企業在缺乏生產日誌與人工標註資料的情況下，持續提升客服、金融或內部流程代理的可靠性。重點在於它能系統化地找出代理可能犯錯的邊界情境，降低上線後的合規風險，並縮短從政策更新到模型改進的週期。
