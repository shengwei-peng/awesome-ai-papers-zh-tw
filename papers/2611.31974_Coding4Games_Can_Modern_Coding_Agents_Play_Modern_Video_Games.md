Coding4Games 的核心方法論在於重新定義「遊戲代理」的評估範式：不再測試語言模型在遊戲過程中即時推理與決策的能力，而是評估**程式碼代理（Coding Agent）**能否透過與遊戲的互動，自主開發出可在無語言模型推論下獨立執行的**遊戲程式（Game-Playing Program）**。此一架構性轉變帶來三個關鍵設計要素。

**第一，標準化介面層（Standardized Interface Layer）。** 論文設計了一套 gym-like 的遊戲伺服器介面，使程式碼代理得以透過標準玩家介面（Standard Player Interface）與遊戲互動，包含視覺觀察（Visual Observation）與低階控制（Low-Level Control）兩個通道。視覺通道接收螢幕畫面，控制通道則輸出鍵盤、滑鼠等標準遊戲輸入。這種設計刻意避開遊戲專用 API（Game-Specific API），迫使代理必須自行處理感知（Perception）與動作映射，而非依賴結構化狀態抽象。

**第二，開發—測試分離協議（Development-Test Separation Protocol）。** 此協議將評估流程劃分為兩個階段。在開發階段（Development Stage），代理於持久化的沙盒（Sandbox）環境中反覆探索、撰寫、測試與除錯程式；進入測試階段（Test Stage）後，所選定的程式被「凍結」（frozen），在全新的環境中獨立執行，不再有任何語言模型推論介入。此設計的關鍵意義在於：它測試的是程式碼本身的可靠性與泛化能力，而非代理在測試期間的即時修正能力。這與 GUI 代理（GUI Agent）設定形成根本對比——後者在每次動作選擇時都需要語言模型推論，在即時遊戲（Real-Time Game）中甚至面臨「環境在推論期間持續演化」的時序錯位問題。

**第三，雙軌評估框架（Outcome and Process Evaluation）。** 論文不僅衡量最終遊戲分數，還系統性地分析開發過程中的代理行為，包含三個維度：(1) 程式基礎化程度（Program Grounding），衡量代理如何將遊戲理解轉化為可執行程式；(2) 修改深度（Modification Depth），衡量修訂幅度與策略迭代；(3) 問題解決（Problem Resolution），衡量代理是否能透過自我測試辨識失敗並有效修正策略。這種過程導向的評估揭示了結果分數無法捕捉的代理能力差異。

**遊戲選擇的策略性。** 15 款遊戲橫跨五大類別——戰鬥與時機操作（Combat & Action Timing）、3D 運動與精準控制（3D Sports & Precision Control）、移動與時機（Movement & Timing）、策略與資源規劃（Strategy & Resource Planning）、以及多步驟任務執行（Multi-step Task Execution）。此分類刻意涵蓋不同的視覺複雜度、狀態空間（State Space）大小、動作空間（Action Space）維度與規劃時序長度（Long Horizon），以系統性壓力測試代理在感知、決策與控制三個層面的整合能力。

#### 實驗數據解讀

實驗結果呈現出層次分明的能力光譜，揭示了程式碼代理在遊戲領域的當前定位。

**主要效能對比。** 在 15 款遊戲中，每款遊戲的最佳程式（best program per game）在 13 款上超越最強 GUI 基準（GUI Baseline），在 1 款上與其持平。這意味著一旦程式碼代理成功開發出可運行的遊戲程式，其表現通常能超越需要持續推論的 GUI 代理。此結果支持論文的核心理論主張：將遊戲行為編碼為可重用的程式表示，比即時語言模型推理更具效能與效率。然而，人類玩家在 10 款遊戲中仍勝過所有代理，最佳程式僅在 3 款遊戲中擊敗人類、2 款持平，顯示代理與人類頂尖水準之間仍有顯著差距。

**過程分析揭示的關鍵瓶頸。** 論文的過程評估揭露了一個深層問題：自我測試（self-testing）往往無法將回饋（Feedback）有效轉化為策略修訂（Program Revision）。換言之，代理能辨識「程式失敗了」，但難以診斷「為何失敗」並據此調整策略。這凸顯了當前程式碼代理在迭代除錯（Iterative Debugging）上的根本限制——它們擅長語法層級的修正，但在策略層級的推理上仍有不足。

**開發預算的影響。** 論文進一步檢視開發預算（Development Budget）對效能的影響，雖然具體數據需參考完整論文，但此分析指向一個重要的成本—效能權衡問題：更多的開發迭代是否帶來線性或邊際遞減的效能提升？這對於實際部署的經濟可行性至關重要。

**GUI 與程式碼代理的相關性分析。** 論文比較了同一模型在兩種設定下的表現相關性，此分析有助於釐清：模型在即時遊玩中的能力是否預示其在程式開發中的能力？若兩者高度相關，則可作為模型篩選的捷徑；若相關性低，則意味著程式碼代理需要獨特的能力組合，不能僅從 GUI 代理表現推斷。

#### 與現有研究的比較

Coding4Games 在遊戲代理與程式碼代理兩個研究脈絡中均佔有獨特位置。

**相較於 GUI 代理基準的進步。** 與 BALROG（6 款遊戲，文字/網格介面）、VideoGameBench（10 款復古遊戲）、Orak（12 款混合遊戲）、GameVerse（15 款混合遊戲）、GameWorld（34 款網頁遊戲）等 GUI 基準相比，Coding4Games 的核心差異在於：(1) 專注於現代 3A 級遊戲（AAA Games），視覺與控制複雜度遠超復古遊戲；(2) 採用即時執行模式（Live Mode），更貼近真實遊玩體驗；(3) 評估的是開發產物而非即時行為。這些基準普遍存在「推論成本（Inference Cost）過高」與「即時遊戲時序錯位」的限制，Coding4Games 透過將行為編碼為程式碼來根本性解決這些問題。

**相較於 API 型程式碼代理基準的進步。** 與 CodeClash（6 款競技場遊戲）和 ProxyWar（9 款競技場遊戲）相比，Coding4Games 拒絕使用遊戲專用 API，而是要求代理透過視覺輸入與標準控制來操作遊戲。這使得評估更貼近「通用程式碼代理」的真實應用場景——代理無法依賴遊戲提供的捷徑，必須自行建構感知管線與動作映射。CodeClash 與 ProxyWar 雖然也評估程式碼代理，但它們暴露的程式化介面（Programmatic Interface）繞過了感知與低階控制的需求，限制了結論的可遷移性。

**相對局限性。** 然而，Coding4Games 也有其侷限：(1) 15 款遊戲的規模雖具代表性，但相較於 GameWorld 的 34 款，覆蓋廣度有限；(2) 開發—測試分離協議雖然嚴謹，但無法捕捉代理在測試期間的適應能力——若允許測試期間有限度的修正，結果可能不同；(3) 過程評估的指標設計仍有改進空間，特別是「問題解決」維度的量化方式可能過於粗略。

**與深度強化學習傳統的關係。** 從更宏觀的視角看，Coding4Games 延續了 Mnih 等人（2013）開創的「將遊戲行為編碼為可重用表示」的傳統，但以程式碼取代了神經網路權重。此一架構選擇帶來可解釋性與可檢查性的優勢，但同時也帶來了表達能力上的限制——某些遊戲策略可能難以用純程式碼表達。

#### 未來研究方向

Coding4Games 的發現開啟了多條值得深入探索的研究路徑。

**策略發現的增強機制。** 過程分析揭示的核心瓶頸——「自我測試無法有效轉化為策略修訂」——指向一個關鍵的研究問題：如何讓程式碼代理具備更強的策略級推理能力？可能的方向包括：(1) 整合高層次的策略語言或規劃模組，使代理能在程式碼層級之上進行抽象推理；(2) 引入對抗性自我對弈或課程式學習（curriculum learning），讓代理在開發階段接觸多樣化的遊戲情境；(3) 借鑑 Voyager 與 Cradle 等系統的技能組合（skill composition）思想，讓代理累積可重用的策略元件。

**感知管線的專門化。** 現代遊戲的視覺介面極為複雜，通用程式碼代理可能難以從零建構高效的感知管線。未來研究可探索：(1) 預訓練的遊戲視覺模型作為代理的感知骨幹；(2) 將感知與控制邏輯解耦的模組化架構；(3) 從人類示範中學習視覺—動作映射的模仿學習方法。

**測試期間的有限適應。** 當前的開發—測試分離協議嚴格禁止測試期間的語言模型介入，但一個務實的方向是允許「有限度的測試期間適應」——例如，預先編譯的策略參數調整或有限狀態機的狀態轉換。這可能在保持程式可重用的同時，提升對環境變化的魯棒性。

**跨遊戲遷移學習。** 15 款遊戲的設定為跨遊戲遷移學習提供了天然實驗場景。一個關鍵問題是：在多款遊戲上開發經驗是否能幫助代理更快地掌握新遊戲？這涉及元學習（meta-learning）與持續學習（continual learning）的技術整合。

**經濟性與可持續性分析。** 程式碼代理的開發預算對效能的影響分析，應延伸至更全面的成本—效益研究，包含：(1) 與人類開發者的成本比較；(2) 程式碼重用帶來的長期經濟效益；(3) 在不同遊戲類別中的投資回報率差異。這對於實際部署決策至關重要。

**安全與可靠性保證。** 隨著程式碼代理在遊戲中的能力提升，其在更廣泛的軟體任務中的應用也將擴大。這引發了安全性問題：如何確保代理開發的程式在邊緣案例中行為可靠？如何驗證程式碼的正確性而不僅是經驗性測試？形式化驗證（formal verification）與神經符號方法的整合可能是值得探索的方向。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼現代電子遊戲對程式碼代理而言是個特別具挑戰性的測試環境？**

A：這篇論文聚焦的核心問題是：能否讓通用的程式碼代理透過視覺互動理解一款現代遊戲，並寫出一個僅使用標準玩家介面（鍵盤、滑鼠等）即可遊玩、且在執行階段不需語言模型推論的獨立程式。現代電子遊戲之所以構成嚴峻挑戰，是因為它們同時要求豐富的視覺感知、大型狀態與動作空間，以及即時動態反應，迫使程式必須整合感知、策略決策與精細控制。這種「在複雜動態環境中開發可靠程式」的需求，遠比傳統軟體工程任務更能考驗代理對環境的理解與迭代除錯能力。因此，現代遊戲成為評估程式碼代理是否能將高層次理解轉化為可執行行為的理想試金石。

**Q2：現有的遊戲代理評估方式（GUI Agent 設定）有哪些根本性的限制？**

A：現有的遊戲基準測試大多採用 GUI 代理設定，由語言模型在遊戲過程中反覆觀察畫面並選擇下一個動作，這種模式帶來兩個根本限制。其一，每次動作都需要語言模型推論，造成持續且高昂的推論成本；其二，在即時遊戲中，環境會在模型推論期間持續演化，可能導致代理的決策與當前畫面狀態不同步，影響反應品質。這些限制使得 GUI 代理難以產出可重複、可檢查、可系統化測試的行為，也無法真正評估代理是否「理解」遊戲並能將其轉化為可靠程式。

**Q3：為什麼作者認為「基於 API 的遊戲程式」這條路線也不足以解決問題？**

A：基於 API 的遊戲程式（如 CodeClash、ProxyWar）雖然讓程式碼代理能撰寫並迭代修改機器人，但它們依賴遊戲專用 API 來存取結構化狀態並透過程式化介面下達動作。這種設計繞過了真實遊戲中必需的視覺感知與低階控制，因此無法評估代理在「從畫面讀取資訊」與「模擬人類輸入」方面的能力。此外，遊戲專用 API 僅適用於特定遊戲，難以遷移至其他現代遊戲標的，限制了方法的通用性與跨遊戲的適用範圍。

**Q4：Coding4Games 提出的「開發—測試分離」（Development-Test Separation）機制是如何運作的？其設計理念為何？**

A：在開發階段，程式碼代理在一個持續保存狀態的沙盒環境中探索遊戲，透過遊戲伺服器提供的 gym-like 介面與遊戲互動，並可反覆執行自我測試以除錯與改進程式。當代理選定一個程式後，該程式會被「凍結」，進入測試階段時會被部署到全新的環境中獨立執行，過程中完全不允許語言模型推論。這種分離設計的理念在於：唯有當程式能在沒有語言模型輔助的情況下獨立可靠地運作，才能真正證明代理已將遊戲理解轉化為可重用的程式化行為，而非僅僅依賴即時推理。

**Q5：Coding4Games 在遊戲選擇上如何兼顧多樣性與現代性？這對評估有何意義？**

A：Coding4Games 收錄了 15 款現代遊戲，橫跨五大類別：戰鬥與動作時機、3D 運動與精準控制、移動與時機、策略與資源規劃，以及多步驟任務執行。這樣的選擇刻意避開了視覺介面與操作方式較為簡單的經典遊戲，確保每款遊戲都對感知、策略與控制提出不同面向的要求。遊戲多樣性的意義在於：它能避免評估結果被單一類型的能力（例如純反應速度或純資源管理）所主導，從而更全面地檢驗程式碼代理在不同維度上的強項與弱點。

**Q6：除了最終遊戲表現，Coding4Games 還透過哪些「過程評估」指標來分析代理行為？**

A：Coding4Games 的過程評估關注代理在開發過程中如何運用執行回饋、修改程式，以及驗證修改是否真正解決了目標問題。具體而言，它衡量「程式接地程度」（program grounding）、「修改深度」（modification depth）以及「問題解決」（problem resolution）等面向。這些指標揭示了代理是否能從自我測試的失敗中提煉出有用的訊息，並將其轉化為有效的策略調整，而非僅僅停留在「發現錯誤」卻無法「修正錯誤」的層次。

**Q7：在 15 款遊戲的實驗中，程式碼代理相較於最強 GUI 基準與人類玩家的整體表現如何？**

A：實驗結果顯示，在 15 款遊戲中，每款遊戲表現最佳的程式在 13 款上勝過最強的 GUI 基準，並在 1 款上與其持平，證明獨立程式在多數情況下能超越需要持續推論的 GUI 代理。然而，人類玩家在 10 款遊戲中仍勝過所有代理，顯示程式碼代理與人類高水平玩家之間仍有明顯差距。值得注意的是，每款遊戲的最佳程式在 3 款遊戲中擊敗了人類，並在 2 款中與人類持平，說明在特定遊戲上程式碼代理已能達到甚至超越人類水準。

**Q8：開發預算（Development Budget）的變動會如何影響程式碼代理的最終表現？**

A：論文特別檢視了開發預算對表現的影響，結果顯示增加開發預算並不一定能線性提升最終分數。雖然更多預算讓代理有更多機會嘗試與迭代，但過程分析指出，代理在自我測試中往往難以將回饋有效轉化為策略改進，導致額外的開發投入未必帶來相應的表現提升。這凸顯了「可靠地從互動中改進」本身即是程式碼代理面臨的核心挑戰，而非單純的資源堆疊問題。

**Q9：過程分析揭示了程式碼代理在自我改進上存在哪些具體弱點？**

A：過程分析揭示了一個持續存在的落差：代理雖然能透過自我測試「辨識」失敗，卻常常無法將這些失敗訊息轉譯為有效的策略修訂。換言之，代理具備一定的診斷能力，但缺乏將診斷結果轉化為具體、可執行程式碼修改的策略發現能力。這項發現指出，程式碼代理在「可靠地透過互動改進」這個面向仍有顯著不足，是未來需要突破的關鍵瓶頸。

**Q10：Coding4Games 的設計對實際應用場景（例如遊戲 AI 開發、自動化測試）有何啟示？**

A：Coding4Games 展示了一種「以程式碼作為可重用互動行為載體」的範式，這對遊戲 AI 開發意義重大：一旦代理產出可獨立執行的遊戲程式，該程式即可被檢查、重播、跨環境部署，無需持續負擔語言模型推論成本。這種模式也適用於自動化測試與品質保證，因為凍結後的程式可在標準化條件下反覆驗證，提供比 GUI 代理更穩定、可審核的行為記錄。

**Q11：將 Coding4Games 概念延伸至產品層面時，需要考量哪些工程與商業因素？**

A：在產品化層面，首先需要考量的是沙盒環境的隔離性與安全性，因為程式碼代理會在遊戲環境中執行任意程式碼，必須避免對底層系統造成影響。其次，開發預算與推論成本之間的權衡至關重要——雖然獨立程式執行階段零成本，但開發階段仍需大量語言模型呼叫，產品設計需為不同遊戲類型設定合理的預算上限。此外，跨遊戲遷移性與通用函式庫的支援程度也會直接影響方案的實用價值。

**Q12：這項研究對「程式碼代理」與「遊戲 AI」兩個領域的長遠影響為何？**

A：對程式碼代理領域而言，Coding4Games 將評估對象從靜態軟體任務拓展到複雜動態環境，迫使代理必須整合感知、決策與控制，這推動了更具通用性的程式碼代理研究。對遊戲 AI 領域而言，這項工作提供了一條介於傳統強化學習（需大量訓練）與 GUI 代理（即時推理）之間的中間路線：以程式碼形式產出可解釋、可檢查的策略。這種「程式即策略」的觀點可能啟發後續在機器人、模擬器與自動化領域的類似應用。

**Q13：論文所承認的限制有哪些？特別是在遊戲範圍與評估方式上。**

A：儘管 Coding4Games 涵蓋 15 款現代遊戲並橫跨五大類別，但相較於整個遊戲產業的龐大遊戲庫，這仍是一個有限的子集，可能無法完全代表所有遊戲類型與挑戰。此外，評估仰賴標準化的任務初始化與遊戲專屬計分方式，這雖然提升了可比性，卻也可能忽略真實玩家體驗中更細緻的面向，例如長期劇情進展或多人對戰中的社會互動。

**Q14：在實驗中觀察到哪些典型的失敗案例？這些案例透露了什麼樣的代理弱點？**

A：典型的失敗案例包括：代理在自我測試中雖然能偵測到程式表現不佳，卻無法提出有效的策略性修改，僅進行表面的參數調整或無關緊要的程式碼重構。此外，在需要長時序策略規劃的遊戲（如資源管理類）中，代理往往難以發展出超越短視反應的策略，顯示其在「長時序決策」與「策略發現」上的根本弱點。這些失敗凸顯了從「會寫程式」到「會寫對的程式」之間仍存在巨大鴻溝。

**Q15：基於這些發現，未來的研究方向可能朝哪些方向延伸？**

A：未來研究可朝幾個方向延伸：其一，開發更有效的「回饋轉譯機制」，幫助代理將執行失敗訊息映射為具體的策略性程式修改；其二，引入階層式規劃或外部記憶體，讓代理能在長時序遊戲中累積並重用策略知識；其三，將 Coding4Games 擴展至更多遊戲類型與多人對戰場景，進一步檢驗代理在社會性與對抗性環境中的表現；其四，探討如何結合傳統強化學習與程式碼代理的優勢，兼顧訓練效率與行為可解釋性。

將訓練完成的程式碼代理與其產生的遊戲程式整合至產品流程。對於 QA 應用，需建立自動化觸發機制；對於 NPC 對手應用，需將代理產生的程式碼整合至遊戲引擎。建議建立版本控制與回滾機制，確保穩定性。

### 潛在風險與注意事項

**風險一：自我測試無法有效轉化為策略改進**
論文明確指出，代理常能透過自我測試發現失敗，但難以將回饋轉化為有效的策略修訂。**緩解措施**：設計更結構化的回饋機制（如視覺差異標註、策略建議提示），或結合人類專家的示範資料輔助代理學習。

**風險二：程式可靠性不足**
獨立執行的程式可能在測試環境中遇到開發時未見過的狀態，導致崩潰或行為異常。**緩解措施**：在開發階段加入壓力測試與邊界案例覆蓋；設計降級機制（如偵測異常時切換至保守策略）；建立執行監控與自動重啟機制。

**風險三：開發成本過高**
語言模型反覆推論的成本可能遠超傳統遊戲 AI 訓練。**緩解措施**：設定嚴格的開發預算上限；採用較小的模型處理常規任務，僅在關鍵決策點使用大型模型；快取常見的程式碼片段與策略模板。

**風險四：視覺感知在複雜場景中的限制**
現代遊戲的視覺介面極為複雜，程式碼代理產生的視覺處理邏輯可能在特定場景失效。**緩解措施**：結合傳統電腦視覺技術（如模板匹配、物件偵測）作為輔助；限制遊戲類型至視覺相對穩定的範疇；提供遊戲內部狀態的有限提示（如分數顯示）。

**風險五：評估偏差與過擬合**
代理可能在開發沙盒中過度最佳化特定起始狀態，導致測試階段表現下滑。**緩解措施**：嚴格執行開發-測試分離；測試階段使用隨機化或多樣化的起始條件；採用多次獨立執行的平均表現作為最終評分。

**風險六：法律與合規問題**
使用程式碼代理操控商業遊戲可能違反服務條款。**緩解措施**：優先使用開源或授權明確的遊戲；與遊戲開發商合作取得正式授權；在自有遊戲或測試環境中部署。

### 與其他技術的整合建議

**與遊戲引擎整合**
將 Coding4Games 產生的程式碼代理整合至 Unity 或 Unreal Engine 時，建議將代理視為「策略生成器」，其輸出為可載入的腳本或行為樹。透過引擎的插件機制，將視覺觀察從引擎渲染管線擷取，將控制動作映射至引擎的輸入系統。

**與 CI/CD 流程整合**
在遊戲開發的持續整合流程中，可將程式碼代理作為自動化測試環節。每次程式碼提交後，自動觸發代理產生測試機器人並執行迴歸測試，產生平衡性與穩定性報告。建議將測試結果整合至 Jira 或 GitHub Issues。

**與電腦視覺函式庫整合**
代理產生的程式碼常需視覺處理能力，建議預先整合 OpenCV、YOLO 等成熟函式庫作為基礎工具。代理可呼叫這些函式庫完成物件偵測、文字辨識（OCR）等任務，無需從零開始實作。

**與強化學習系統整合**
Coding4Games 的程式碼代理可作為強化學習的策略初始化來源。先由代理產生可執行的策略程式，再以此為起點進行 RL 微調，可加速收斂並提供可解釋的策略起點。

**與程式碼分析工具整合**
整合 SonarQube、CodeQL 等靜態分析工具，自動檢測代理產生程式碼的安全性漏洞、效能問題與程式碼風格。這對於將程式碼部署至生產環境尤為重要。

**與版本控制系統整合**
代理的開發過程涉及大量程式碼迭代，建議將每次修改提交至 Git，並記錄對應的測試結果與回饋。這不僅利於追蹤進度，也方便日後回溯至特定版本。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀論文摘要與介紹，理解「程式碼代理」與「GUI 代理」的差異——前者產出獨立程式，後者持續呼叫語言模型。接著瀏覽圖 1 與表 1，建立對整體框架的直觀認識。實作上可從簡單的復古遊戲（如 Atari 風格）開始，使用現成的程式碼代理框架（如基於 GPT-4 的代理）體驗開發流程，無需深入理解所有技術細節。

**給 AI 工程師**：重點關注「開發-測試分離」的架構設計與「過程評估」指標的實作細節。論文揭示的「自我測試無法轉化為有效策略修訂」現象是當前技術瓶頸，建議深入分析其失敗模式，並嘗試設計更結構化的回饋機制。可將 Coding4Games 視為評估程式碼代理在動態環境中表現的標準測試集，與 SWE-bench 等靜態程式碼基準互補使用。

**給研究者**：論文的價值在於提出了一個新的代理評估範式——從「即時推論」轉向「程式合成」。建議從三個方向延伸研究：(1) 探索更有效的回饋轉化機制，解決策略發現瓶頸；(2) 研究程式碼代理在不同遊戲類型間的遷移學習能力；(3) 將框架擴展至機器人、網頁自動化等其他視覺控制領域。論文的「過程評估」設計也值得借鏡，可應用於其他代理基準。

**給產品經理**：Coding4Games 的核心商業價值在於「將語言模型的一次性開發成本轉化為可重複執行的程式」，這對成本敏感的應用場景（如遊戲 QA、自動化測試）極具吸引力。建議評估在自家產品中導入此模式的可行性：哪些任務適合由程式碼代理開發獨立程式？哪些任務仍需即時互動？開發預算與執行可靠性的權衡如何設定？論文的實驗數據（13/15 遊戲超越 GUI 基準）顯示此模式已具備實用潛力，但「人類在 10 款遊戲中仍勝出」提醒我們，現階段更適合作為輔助工具而非完全替代。
