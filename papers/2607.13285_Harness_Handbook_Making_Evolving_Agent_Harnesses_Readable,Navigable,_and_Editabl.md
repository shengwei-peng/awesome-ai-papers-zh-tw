## 摘要翻譯

現代 AI 代理（AI agent）的能力不僅取決於其基礎模型（foundation model），也取決於其 harness（控制架構），它負責建構提示、管理狀態、呼叫工具並協調執行。隨著模型、API（應用程式介面）、環境與需求不斷演變，harness 必須持續修改。在進行修改前，開發者或編碼代理（coding agent）必須識別所有與目標行為相關的實作位置。這之所以困難，是因為生產級 harness（production harnesses）龐大、緊密耦合（tightly coupled）且行為分散式（behaviorally distributed），而修改請求（modification request）描述的是系統應有的行為，程式庫則是按檔案與模組組織。程式碼搜尋（code search）、程式庫索引（repository indexing）與長上下文處理（long-context processing）雖然簡化了檢視工作，但仍需手動重建這種行為到程式碼的對應（behavior-to-code mapping）。因此，行為定位（behavior localization）是 harness 演化（harness evolution）中的核心瓶頸。

我們提出 Harness 手冊（Harness Handbook），這是一種以行為為中心的表示法（behavior-centric representation），透過靜態分析（static analysis）與大型語言模型輔助的結構化（LLM-assisted structuring），自動從 harness 程式碼庫（codebase）合成而得，並將每項行為連結至其對應原始碼。我們也提出行為導引的漸進式揭露（Behavior-Guided Progressive Disclosure, BGPD），它從高層級行為（high-level behavior）逐步引導代理至相關實作細節（relevant implementation details），並對照目前原始碼驗證候選位置（candidate location）。針對來自兩個開源 harness（open-source harnesses）的多樣修改請求，Handbook 輔助規劃（Handbook-Assisted planning）提升了行為定位與編輯計畫品質（edit-plan quality），同時減少了規劃器 token 使用量（planner tokens），且在分散的實作位置（scattered sites）、鮮少執行的路徑（rarely executed paths）與跨模組互動（cross-module interactions）方面改善最為顯著。因此，複雜代理系統（agentic systems）的演化不僅取決於產生編輯，也取決於決定應於何處進行這些編輯。

### 核心貢獻（3～5點）
- 界定 harness 演化中的核心瓶頸為行為定位（behavior localization），即如何將自然語言修改請求對應到實作該行為的程式碼位置。
- 提出 Harness 手冊（Harness Handbook），一種以行為為中心的表示法，透過靜態分析與 LLM 輔助結構化自動合成，將每項行為連結至其對應原始碼。
- 提出行為導引的漸進式揭露（BGPD），從高層行為逐步引導至相關實作細節，並驗證候選位置是否與目前原始碼相符。
- 在兩個開源 harness 的多樣修改請求上驗證，Handbook 輔助規劃可提升行為定位與編輯計畫品質，同時減少規劃器 token 使用量，且在分散實作位置、鮮少執行路徑與跨模組互動上改善最顯著。

### 適合對象
從事 AI 代理、編碼代理或代理系統開發的研究者與工程師，特別是面對大型、緊密耦合且持續演化的 harness，需要改善其可讀性、可導覽性與可編輯性的開發者；亦適合關注程式理解、行為定位、長上下文編輯與 LLM 輔助軟體維護的讀者。

## 深度分析

#### 方法論解析

本文的核心命題是：在現代 AI 代理系統中，真正決定系統能力的往往不是基礎模型（foundation model）本身，而是 harness（控制架構）——負責提示建構（prompt construction）、狀態管理（state management）、工具呼叫（tool invocation）與執行協調（execution coordination）的程式碼框架。當模型、API、執行環境（execution environment）與應用需求持續變動時，harness 必須隨之演化，而演化的首要瓶頸並非「如何改」，而是「改哪裡」。作者將此問題形式化為行為定位（behavior localization）：給定一個以自然語言描述的修改請求（modification request），找出所有實作該目標行為（target behavior）的實作位置（implementation site / location）。

為了解決這個瓶頸，作者提出 Harness Handbook（Harness 手冊），一種以行為為中心的表示法（behavior-centric representation）。與傳統以檔案（file）或模組（module）組織的程式庫地圖（repository map）不同，Harness Handbook 直接以「harness 做了什麼」為主軸，將每項高層級行為（high-level behavior）連結到其對應的原始碼（source code）。其建構流程結合了兩類技術：

1. **靜態分析（static analysis）**：透過剖析抽象語法樹（AST）、呼叫圖（call graph）、控制流與資料流，以及共享狀態（shared state）的讀寫關係，從程式碼庫（codebase）中萃取出結構化的事實。這一步能夠識別函式之間的呼叫關係、狀態傳遞路徑，以及行為可能分散在多個非相鄰區段的跡象。
2. **大型語言模型輔助的結構化（LLM-assisted structuring）**：在靜態分析的基礎上，利用 LLM 將低階程式結構歸納、命名並組織成可讀的行為條目。LLM 負責產生行為描述、推斷行為之間的層級關係，並將每個行為對應回一組候選位置（candidate location）。

最終產出的 Handbook 可視為一張「行為到程式碼的對應（behavior-to-code mapping）」表：使用者或編碼代理（coding agent）先從自然語言請求中辨識出目標行為，再順著 Handbook 的連結直接檢視相關實作細節（relevant implementation details），而無需在龐大的檔案樹中逐步摸索。

為了讓 Handbook 在實際修改流程中發揮作用，作者進一步提出 Behavior-Guided Progressive Disclosure（BGPD，行為導引的漸進式揭露）。BGPD 是一種分階段的工作流程：首先從 Handbook 中選取與修改請求最相關的高層級行為；接著逐步揭露與該行為相關的實作位置；在每一階段，系統會將候選位置與目前原始碼進行驗證（verification），確認該位置仍然存在且與描述相符；最後才基於這些經過驗證的位置產生編輯計畫（edit plan）。這種漸進式揭露（progressive disclosure）的設計特別適合輸入上下文（input context）有限的編碼代理，因為它避免了將整個程式庫一次性塞入提示，而是隨著推理過程按需載入細節。

整體而言，Harness Handbook + BGPD 將 harness 演化從「以檔案為單位的迭代式探索（iterative exploration）」轉換為「以行為為單位的導引式定位」。這不僅降低了人類開發者建立心智模型（mental model）的負擔，也讓編碼代理能在有限上下文內更精準地找到分散的實作位置（scattered sites）、鮮少執行的路徑（rarely executed paths）以及跨模組互動（cross-module interactions）。

#### 實驗數據解讀

作者在兩個開源 harness（open-source harnesses）上，使用多樣化的真實修改請求進行評估，比較兩種規劃方式：不使用 Handbook 的 Baseline 規劃，以及使用 Harness Handbook 輔助的 BGPD 規劃（Handbook-Assisted planning）。雖然提供的摘錄未包含完整的數據表格，但從摘要與引言可以歸納出以下評估維度與結果意涵：

- **行為定位（behavior localization）表現**：Handbook-Assisted 規劃能更完整地找出與目標行為相關的所有實作位置。這相當於提升了定位的召回率（recall），對於生產級 harness（production harnesses）中常見的「行為分散式」（behaviorally distributed）結構尤為關鍵。
- **編輯計畫品質（edit-plan quality）**：產生的編輯計畫在正確性與完整性上均優於 Baseline。這表示 Handbook 不僅幫助代理「找到」程式碼，也幫助它理解這些程式碼如何協同產生系統行為，從而規劃出更合理的修改步驟。
- **規劃器 token 使用量（planner tokens）**：在達成更高品質的同時，Handbook-Assisted 規劃消耗的規劃器 token 反而更少。這說明行為導引的漸進式揭露有效減少了無關程式碼的載入，讓代理把計算資源集中在真正相關的實作細節上。
- **增益最大的情境**：摘要特別指出，最大的改善出現在分散的實作位置、鮮少執行的路徑以及跨模組互動這三類困難案例。這三類情境正是傳統程式碼搜尋（code search）與長上下文處理（long-context processing）最容易遺漏或過度簡化之處。

從方法論的角度解讀，這些結果形成了一個有力的論證：單純讓編碼代理擁有更長的上下文或更強的檢索工具，並不足以解決 harness 演化的核心問題；真正重要的是建立「行為—程式碼」之間的明確對應。Handbook 相當於提供了一張語意地圖，讓代理能從「要做什麼」出發，而非從「檔案在哪裡」出發。

不過，由於目前可取得的內容未提供詳細的數值、誤差範圍、請求難度分佈或人工評分協議，我們仍須謹慎解讀。例如：「編輯計畫品質」是由自動指標還是人類專家評判？兩個開源 harness 的規模與領域是否足以代表一般生產環境？這些都是進一步檢視時需要補充的細節。

#### 與現有研究的比較

本文的研究定位介於「agent harness 的系統設計」與「編碼代理的程式庫理解」之間，並與三個方向的研究形成對話：

1. **Agent Harness 研究**：過去的工作如 AutoGen、OpenHands、Claude Code、Codex 等，主要聚焦於如何設計與建構 harness，強調模組化、協調機制與長時間執行的可靠性。本文則假設 harness 已經存在，關注的是「如何理解並演化」既有的生產級 harness，屬於互補性的下游問題。

2. **Harness Evolution 研究**：近期已有自動化 harness 優化、修復與適應性調整的研究。這些方法通常直接產生程式碼修改，但忽略了修改前必須先完成行為定位。Harness Handbook 正是填補這個前置步驟，讓後續的編輯或修復能建立在正確的位置資訊上。

3. **程式庫表示法（repository representations）**：現有工具如程式庫地圖（repository map）、程式碼搜尋（code search）、程式碼摘要（code summarization）、程式庫記憶（repository memory）與長上下文編輯（long-context editing），大多以檔案、函式或模組為單位組織資訊。它們能幫助代理「找到相關程式碼片段」，但無法直接回答「這些片段如何共同實現某項行為」以及「是否還有遺漏的實作點」。Harness Handbook 的關鍵改進在於引入明確的 operational behavior representation，將實作知識組織成行為而非結構，並透過 BGPD 的驗證機制降低幻覺風險。

**主要優勢**：
- 明確建立 behavior-to-code mapping，降低自然語言請求與程式結構之間的語意落差。
- 對於緊密耦合（tightly coupled）且行為分散式（behaviorally distributed）的 harness 特別有效。
- 漸進式揭露結合驗證，兼顧上下文效率與定位正確性。

**限制與潛在弱點**：
- **靜態分析的先天限制**：動態分派（dynamic dispatch）、反射（reflection）、執行期設定（runtime configuration）或插件機制可能無法被靜態分析完整捕捉，導致 Handbook 遺漏某些實作位置。
- **LLM 結構化的不穩定性**：行為摘要與對應關係由 LLM 產生，可能出現過度概括、命名不一致或錯誤連結，需要額外的驗證與更新機制。
- **維護成本**：隨著 harness 持續演化，Harness Handbook 必須同步更新，否則會迅速過時。目前尚不清楚更新是增量進行還是需重新生成。
- **評估規模**：僅在兩個開源 harness 上驗證，雖然已顯示顯著增益，但對於更大、更異質的工業級系統，效果與可擴展性仍需更多證據。

#### 可重現性評估

就目前已提供的內容而言，本文尚未明確說明是否釋出原始碼、資料集、模型權重或實驗腳本。對於一個結合靜態分析與 LLM 輔助結構化的方法，可重現性（reproducibility）取決於以下幾項關鍵資源：

- **開源實作**：Handbook 的自動建構流程、BGPD 的工作流程引擎、與原始碼的連結機制，都需要公開程式碼，其他研究者才能在不同的 harness 上複製結果。
- **修改請求資料集**：用於評估的 diverse modification requests 應該以標準化格式釋出，並附上預期的目標行為與正確實作位置，以便作為未來研究的基準（benchmark）。
- **生成的 Harness Handbook 實例**：釋出針對兩個開源 harness 所生成的 Handbook，可以讓社群檢視行為摘要與原始碼連結的品質，並作為方法比較的參考。
- **模型與提示**：若 LLM-assisted structuring 使用了特定的提示模板、微調模型（fine-tuned model）或模型權重（model weights），這些也應一併公開，否則難以排除提示工程差異對結果的影響。
- **評估協議與指標**：包括行為定位的評分標準、編輯計畫品質的評判方式，以及 planner tokens 的計算方法，都應詳細記錄。

在缺乏上述資源的情況下，目前只能將本文視為一個概念驗證與方法論貢獻；要讓 Harness Handbook 成為可被廣泛採用的工具，後續必須補充完整的開源釋出與可重現性文件。

#### 未來研究方向

Harness Handbook 的提出為 harness 演化開啟了多條值得後續探索的研究路徑：

1. **增量式 Handbook 更新（incremental Handbook maintenance）**：隨著 harness 持續修改，如何只針對變動部分更新 Handbook，而非每次重新生成整份手冊，是實用化的關鍵。可結合 diff 分析、版本控制資訊與依賴追蹤來降低維護成本。

2. **混合靜態與動態分析**：將靜態分析與動態執行追蹤（dynamic analysis）結合，補捉執行期才會出現的呼叫路徑、條件分支與狀態轉換，進一步提升對鮮少執行路徑與動態分派的覆蓋率。

3. **與編碼代理及 IDE 的深度整合**：將 Harness Handbook 嵌入編碼代理的觀察空間，或開發成 IDE 插件，讓人類開發者能夠以行為為單位進行導航、搜尋與重構。

4. **從編輯歷史中學習行為定位**：收集大量 harness 修改記錄，訓練模型預測「給定修改請求時最可能需要編輯的位置」，讓 Handbook 不僅反映靜態結構，也反映演化模式。

5. **跨 harness 轉移與通用行為本體**：研究不同 harness 之間是否存在共通的行為模式（例如「錯誤處理」、「重試機制」、「觀察—思考—行動循環」），並建立可重複使用的行為本體（behavior ontology），降低新 harness 的 Handbook 建構成本。

6. **人機協同驗證與回饋迴路**：讓人類開發者能夠標註 Handbook 中的錯誤或遺漏，並將這些回饋用於改進靜態分析規則與 LLM 摘要品質，形成持續改善的閉環。

7. **因果行為模型（causal behavior modeling）**：不僅描述「哪些程式碼實現了某行為」，更進一步建模「修改某處會如何影響其他行為」，從而提升編輯計畫的穩健性與可預測性。

8. **標準化評估基準**：建立涵蓋不同規模、領域與設計風格的 harness 修改任務基準，統一行為定位與編輯計畫品質的評量方式，讓後續研究能夠公平比較。

## 論文問答

**Q1：什麼是「行為定位」（behavior localization），為什麼它是 harness 演化的核心瓶頸？**

A：行為定位是指找出與修改請求中所描述目標行為相關的所有實作位置。在生產級 harness 中，單一行為往往分散在許多檔案、函式與執行階段之間，並透過共享狀態彼此連結，因此開發者或編碼代理很難一次找齊所有相關程式碼。現有工具雖然能協助搜尋與檢視程式碼，但行為到程式碼的對應關係仍須人工重建，使得定位成為 harness 演化前最耗時且容易出錯的步驟。

**Q2：程式庫地圖、程式碼搜尋與長上下文處理為何無法單獨解決這個問題？**

A：這些方法主要以檔案、函式或模組為中心來組織資訊，但修改請求通常是以自然語言描述「希望系統做什麼」，而非指出「要去哪裡改」。它們或許能找出個別相關的程式碼片段，卻無法清楚呈現這些片段如何協同產生目標行為，也無法保證所有受影響的位置都被找到。因此，編碼代理仍須自行拼湊線索、推論行為與實作之間的對應，這正是 Harness Handbook 想要補上的缺口。

**Q3：相較於人類開發者，編碼代理在 harness 演化中面臨哪些額外困難？**

A：編碼代理的輸入上下文有限，無法一次性檢視所有相關程式碼，只能透過迭代式探索逐步搜尋。這種限制使它們特別容易遺漏分散的實作位置、鮮少執行的路徑或跨模組的互動。人類開發者雖然也需要建立心智模型並追蹤行為，但能更靈活地根據經驗與領域知識進行推論，因此代理更需要結構化的行為導引來降低定位成本。

**Q4：Harness Handbook 是什麼？它與傳統的程式庫表示法有何不同？**

A：Harness Handbook 是一種以行為為中心的操作型表示法，將 harness 的系統行為直接連結到其原始碼實作。不同於傳統以檔案、函式或模組為單位的組織方式，Handbook 是依照「harness 做了什麼」來編排知識，讓開發者或代理可以先找到目標行為，再導航到對應的實作位置。這種表示法透過靜態分析與大型語言模型輔助的結構化自動產生，旨在彌補行為描述與程式碼結構之間的落差。

**Q5：什麼是「行為導引的漸進式揭露」（BGPD），它在修改規劃中扮演什麼角色？**

A：BGPD 是一種從高層級行為描述逐步引導至相關實作細節的工作流程，並會針對候選位置與目前原始碼進行驗證。它的核心精神是漸進式揭露：先呈現抽象行為，再依需求展開具體程式碼，避免一次塞入過多上下文。透過這種分階段導引與驗證機制，BGPD 能幫助編碼代理更準確地定位實作點，同時減少規劃過程中的幻覺與遺漏。

**Q6：Harness Handbook 能夠從現有程式碼庫自動建構，關鍵設計選擇是什麼？**

A：其自動建構結合了兩項技術：靜態程式分析用於擷取程式碼結構、呼叫關係與相依性，而大型語言模型輔助的結構化則負責將這些資訊整理成以行為為單元的表示法。這樣的設計選擇讓 Handbook 無需仰賴人工撰寫文件，就能從既有 harness 程式碼中萃取出可操作的行為知識。最終產生的每個行為條目都會連結到具體的原始碼位置，確保表示法與實作之間的可追溯性。

**Q7：論文使用了哪些 harness 與修改請求來評估 Harness Handbook？**

A：論文選用了兩個開源 harness，並針對它們設計了多樣化的真實修改請求進行評估。這些請求涵蓋了不同難度的行為定位情境，包括實作位置分散、鮮少執行的路徑，以及跨模組互動等挑戰性案例。實驗在同一批任務上比較了「無 Handbook 輔助的基線規劃」與「Handbook 輔助的 BGPD 規劃」，以控制變因並凸顯 Handbook 的貢獻。

**Q8：實驗的主要量化結果是什麼？**

A：Handbook 輔助規劃在行為定位準確率與編輯計畫品質上均優於基線，同時規劃器所消耗的 token 數量更少。最大的改善出現在實作位置分散、鮮少執行路徑以及跨模組互動這類困難情境，顯示 Handbook 對於傳統方法容易遺漏的案例特別有幫助。這些結果說明，將行為與實作之間的連結顯式化，能同時提升 harness 演化的正確性與效率。

**Q9：論文是否提到消融實驗或其他比較分析？**

A：根據提供的摘要與前言，論文主要呈現的是基線規劃與 Handbook 輔助規劃之間的對照比較，這本身已構成控制條件下的評估。摘要與前言並未詳細說明進一步的消融實驗，例如單獨移除靜態分析、LLM 結構化或 BGPD 驗證的影響。未來研究可以針對這些元件進行消融，以更具體地量化每一項技術對定位與規劃品質的貢獻。

**Q10：Harness Handbook 在哪些實務場景中最有價值？**

A：它特別適合用於需要頻繁因應模型、API 或執行環境變更而生產級 harness 維護工作，例如長期運行的編碼代理系統。對於新加入的開發者，Handbook 也能降低理解大型、緊密耦合程式碼庫的門檻，讓他們快速從行為描述找到對應實作。此外，在讓編碼代理自主規劃修改時，Handbook 可作為結構化的導航基礎，減少反覆搜尋與試錯的時間。

**Q11：將 Harness Handbook 部署到開發流程中時，需要考慮哪些產品化議題？**

A：首先必須確保 Handbook 能隨著 harness 程式碼的演化持續同步更新，否則過時的行為連結會誤導代理。其次，需要將 Handbook 整合到 IDE、程式碼編輯器或代理工具鏈中，並提供驗證與回饋機制來處理錯誤連結或遺漏。最後，自動產生 Handbook 所需的靜態分析與 LLM 結構化成本、延遲與可擴展性，也是在實際產品中必須權衡的因素。

**Q12：這項研究可能對代理工程領域帶來什麼更廣泛的影響？**

A：它將「行為定位」提升為 harness 演化中與編輯生成同等重要的研究問題，提醒學界與業界：知道「在哪裡改」與知道「怎麼改」同樣關鍵。以行為為中心的程式庫表示法可能成為未來編碼代理理解複雜系統的標準基礎設施。長遠來看，這種方法也有助於提升自主代理在真實軟體專案中的可靠性，減少因定位錯誤而導致的修改失敗。

**Q13：目前方法有哪些已承認或隱含的限制？**

A：雖然摘要與前言未詳細列出限制，但 Handbook 的品質明顯取決於靜態分析的覆蓋率與 LLM 結構化的準確度，若分析工具無法解析某些動態或反射式程式碼，對應的行為連結就可能不完整。此外，Handbook 本質上是一種靜態摘要，對於高度依賴執行時狀態或動態組合的行為，可能難以完整捕捉。它目前也仍需要與原始碼驗證機制搭配，無法完全取代人工或自動化測試的最終確認。

**Q14：Handbook 輔助規劃可能出現哪些失敗案例？**

A：如果 harness 使用了反射、動態分派或執行期產生的程式碼，靜態分析可能無法正確識別其實作位置，導致 Handbook 遺漏關鍵行為。LLM 在結構化過程中也可能誤標行為名稱、錯誤連結原始碼，或將多個相似行為混為一談。另外，若原始碼在 Handbook 產生後發生變更，而驗證機制未能及時更新，候選位置就可能與實際程式碼不符，進而影響編輯計畫的正確性。

**Q15：這項工作暗示了哪些未來研究方向？**

A：未來可以結合動態分析與執行追蹤來補強靜態分析的不足，特別是針對反射、條件分支與鮮少執行路徑。另一個方向是發展增量式更新機制，讓 Handbook 能在程式碼變更時快速同步，而非重新產生整份文件。此外，將 Handbook 與實際編輯執行、測試回饋迴路整合，並探索人類開發者與編碼代理如何協同使用行為導引介面，也是值得深入研究的課題。

## 實務應用指南

### 適用場景

1. **大規模代理框架的持續維護**  
   當 AutoGen、OpenHands、Claude Code 等生產級 harness 隨著模型版本、API 規格或執行環境更新而需要頻繁調整時，Harness 手冊可協助維護者先定位「目標行為」對應的所有實作位置，再進行修改，減少遺漏分散的實作點。

2. **跨模組行為的除錯與擴充**  
   若某項系統行為（例如「在工具呼叫失敗後自動重試並更新共享狀態」）分散於提示建構、狀態管理、執行協調等多個模組，開發者可利用以行為為中心的表示法追蹤跨模組互動，避免只改到局部而破壞整體流程。

3. **編碼代理的修改規劃輔助**  
   在讓編碼代理自動處理自然語言修改請求時，可先提供 Harness 手冊作為行為到程式碼的對應依據，再透過行為導引的漸進式揭露逐步揭露相關實作細節，提升編輯計畫品質並降低規劃器 token 使用量。

4. **接手遺留或高度耦合的 harness 程式碼庫**  
   新團隊成員或外部協作者面對檔案與模組組織混亂、行為分散式的大型程式碼庫時，可藉由自動產生的 Harness 手冊快速建立心智模型，從高層級行為切入，而非從零開始閱讀所有原始碼。

5. **鮮少執行路徑與邊界案例的修改**  
   當修改請求涉及錯誤處理、權限檢查、降級策略等平常不易觸及的程式路徑時，手冊能將這些 rarely executed paths 與其對應原始碼明確連結，降低改錯或改漏的風險。

### 實作前置條件

**資料準備**
- 目標 harness 的完整原始碼存取權，建議為 Python、TypeScript 等具備成熟靜態分析工具的語言。
- 現有文件或測試案例，用於驗證手冊中的行為描述是否與實際系統一致。
- 歷史修改請求或 issue 清單，作為評估行為定位成效的基準。

**運算資源**
- 執行靜態分析與建立程式庫索引的運算環境（一般伺服器或 CI 環境即可）。
- 呼叫大型語言模型進行 LLM 輔助結構化的 API 配額，規劃階段需額外消耗規劃器 token，但整體上應低於無手冊輔助的迭代探索成本。

**技能需求**
- 熟悉靜態分析工具（如 tree-sitter、AST 解析、呼叫圖分析）。
- 具備提示工程與 LLM 輸出結構化（JSON / schema）經驗，以將分析結果整理為 Harness 手冊。
- 了解目標 harness 的執行工作流程與主要元件，以便審查手冊品質並設計 BGPD 的揭露層級。

---

### 實作步驟建議

1. **解析程式碼結構**  
   對目標程式碼庫執行靜態分析，萃取函式、類別、模組、呼叫關係、共享狀態與工具呼叫點，建立初步的程式庫索引與程式庫地圖。

2. **萃取行為單元**  
   利用 LLM 輔助結構化，將程式碼單元歸納為高層級行為（例如「建構系統提示」、「觸發工具呼叫」、「處理觀察結果」），並記錄每項行為的輸入、輸出與相依關係。

3. **建立行為到程式碼的對應**  
   將每項行為連結至其實作位置，包含主要實作點與相關的分散實作位置，形成 Harness 手冊的核心：以行為為中心的表示法。

4. **設計漸進式揭露層級**  
   依據 BGPD 原則，設計從「高層級行為摘要」→「相關模組與函式」→「具體原始碼片段」→「候選位置驗證」的揭露流程，讓代理或開發者按需取得細節。

5. **整合至修改規劃流程**  
   在收到修改請求時，先讓規劃器查詢 Harness 手冊以完成行為定位，再產生編輯計畫；規劃過程中持續驗證候選位置是否與目前原始碼相符。

6. **迭代驗證與更新**  
   每次 harness 演化後，重新執行靜態分析並更新手冊，確保行為到程式碼的對應不會隨著程式碼變動而過時。

---

### 潛在風險與注意事項

- **手冊品質依賴靜態分析完整性**  
  若 harness 使用大量動態載入、反射或字串組合的函式呼叫，靜態分析可能遺漏實作位置。建議搭配執行追蹤或測試覆蓋率資料進行補強。

- **LLM 產生的行為描述可能不準確**  
  大型語言模型可能過度概括或誤解程式碼語意，導致行為定位錯誤。應保留原始碼連結並設計驗證機制，讓使用者能快速比對手冊描述與原始碼。

- **手冊過時風險**  
  Harness 手冊若未隨程式碼更新，將誤導後續修改。建議將手冊生成整合至 CI/CD，在每次合併前自動重新產生並標示差異。

- **過度揭露導致上下文膨脹**  
  若 BGPD 層級設計不當，可能一次揭露過多細節，抵消長上下文處理的優勢。應根據任務難度與行為分散程度動態調整揭露粒度。

- **對緊密耦合系統的解讀誤差**  
  在緊密耦合的 harness 中，單一行為可能牽涉大量共享狀態，手冊難以完全捕捉隱式相依。建議將共享狀態的讀寫位置也納入行為對應。

---

### 與其他技術的整合建議

- **程式庫地圖與程式碼搜尋**  
  Harness 手冊不應取代現有的 repository map 或 code search，而是作為其上層語義層：先用手冊定位行為，再用程式碼搜尋深入檢視特定函式或符號。

- **長上下文編輯工具**  
  將 Harness 手冊作為長上下文提示的前導摘要，讓模型先理解「這項行為涉及哪些實作位置」，再載入相關原始碼進行編輯，避免一次性塞入無關檔案。

- **編碼代理的記憶系統**  
  可將手冊中的行為節點與關係存入 repository memory，讓代理在多次對話間保留行為定位結果，減少重複探索。

- **自動化測試與迴歸驗證**  
  在產生編輯計畫後，結合單元測試與整合測試驗證所有被標示的實作位置是否正確反映期望行為，特別是針對分散的實作位置與跨模組互動。

- **版本控制與變更追蹤**  
  將 Harness 手冊視為衍生資產納入版本控制，並在行為定位結果與實際編輯之間建立可追溯連結，方便後續審查與除錯。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「適用場景」與「實作步驟建議」入手，理解 Harness 手冊解決的核心問題：「修改請求講的是行為，但程式碼卻按檔案組織」。不必立刻實作自動化流程，可先嘗試為自己熟悉的專案手動整理一份「行為 → 原始碼」對照表，體會行為定位的困難與價值。

**AI 工程師**  
重點閱讀「實作前置條件」、「實作步驟建議」與「與其他技術的整合建議」。本方法可直接嵌入現有的編碼代理管線中，作為規劃階段的前置模組。建議評估你目前使用的靜態分析工具能否完整解析目標 harness，並設計與現有 repository map、長上下文編輯工具的協作介面。

**研究人員**  
請關注論文對「行為定位」問題的定義、Harness 手冊的表示法設計，以及 Behavior-Guided Progressive Disclosure 的實驗設計。這些貢獻為 harness 演化研究開闢了新的前置任務，未來可延伸至多語言 harness、動態分析輔助、或與程式合成技術結合的方向。

**產品經理**  
本技術適合應用於需要頻繁迭代代理能力、且 harness 規模較大的產品。閱讀時請聚焦「適用場景」與「潛在風險與注意事項」，評估導入後能否縮短功能上線週期、降低維護成本，並留意手冊更新與驗證所需的持續投入。
