## ⚡ TL;DR

既有機器人使用代理仰賴客製化中介與專屬介面，論文質疑這些工程是否必要。
OpenRUA 以工作空間即中介架構，讓現成編碼代理透過 ROS 2 原生介面終端機操作機器人。
CaP-Bench達99%、LIBERO-PRO達87%，證明編碼代理可成零樣本視覺動作策略。

## 摘要翻譯

編碼代理透過撰寫並執行機器人控制程式，正將其能力擴展至實體世界。人們或許會預期這些代理直接採用工程師數十年來開發的成熟軟體堆疊，以存取感測器並控制運動。然而，先前研究多半建構複雜的客製化 harness（中介/協調架構）來協調機器人使用代理，尤其是透過規定專門的工作流程並提供客製化介面。這引出了一個問題：「這類額外的中介架構工程是否真的必要？」我們提出 OpenRUA，一種零抽象層的 harness（中介/協調架構），它僅讓現成的編碼代理透過終端機存取機器人的原生軟體介面 ROS 2，從而繞過客製化抽象層。OpenRUA 採用極簡的 workspace-as-harness（工作空間即中介架構）設計，只提供 ROS 2 文件與基本工具，讓編碼代理自行組織工作，而不協調任何代理工作流程。在此工作空間中，OpenRUA 將感知轉化為檔案輸入/輸出、將操作轉化為編碼。搭配由 Claude Opus 5 驅動的 Claude Code，OpenRUA 在 CaP-Bench 上達到 99.0% 的成功率，在 LIBERO-PRO 上達到 87.0% 的成功率，顯示現成的編碼代理可透過機器人的原生介面充當零樣本視覺動作策略，無需客製化基元或任務特定訓練。在這項極簡設計下，進一步分析揭示了編碼代理令人矚目的湧現行為：（1）在感知方面，代理在 96.80% 的回合中會自發性地撰寫程式，處理原始感官輸入並推導出度量測量。（2）在操作方面，代理在 95.87% 的回合中會自發性地建構運動控制客戶端（例如夾爪控制），並在 50.13% 的回合中建立閉迴路控制程式（例如根據感測器回饋調整運動）。我們的程式碼可於 https://github.com/terminalworld/OpenRUA 取得。

### 核心貢獻（3～5點）
- 提出 OpenRUA，一種零抽象層的 harness（中介/協調架構），讓現成的編碼代理僅透過終端機存取 ROS 2 原生軟體介面，即可繞過客製化抽象層來控制機器人。
- 採用極簡的 workspace-as-harness（工作空間即中介架構）設計，將感知轉化為檔案輸入/輸出、將操作轉化為編碼，無需預先編排任何代理工作流程。
- 在 CaP-Bench 與 LIBERO-PRO 上分別達到 99.0% 與 87.0% 的成功率，證明現成的編碼代理可透過機器人原生介面充當零樣本視覺動作策略，無需客製化基元或任務特定訓練。
- 發現編碼代理在極簡環境中展現顯著的湧現行為：自發性地處理原始感官輸入、推導度量測量、建構運動控制客戶端，以及根據感測器回饋建立閉迴路控制程式。

### 適合對象
本論文適合對機器人學、具身智慧（embodied AI）、編碼代理、視覺-語言-動作（VLA）模型，以及機器人軟體堆疊設計有興趣的研究人員與工程師。特別是關注如何以極簡架構銜接大型語言模型代理與真實機器人、或想探索編碼代理在感知與操作上湧現能力的讀者，將能從中獲得重要啟發。

## 深度分析

#### 方法論解析

OpenRUA 的核心主張是將「機器人使用代理（Robot-Use Agent, RUA）」還原為最原始的軟體工程情境：讓現成的編碼代理（coding agent）透過機器人的原生軟體介面（native software interface）——即 ROS 2（Robot Operating System 2）——直接與機器人互動，而不需要任何客製化抽象層（bespoke abstraction layer）或預設的代理工作流程（agentic workflow）。這種設計被稱為 workspace-as-harness（工作空間即中介架構），其本質是把傳統 RUA 系統中由人類工程師精心設計的 harness（中介/協調架構）壓縮到只剩一個工作空間（workspace）。

在這個工作空間中，OpenRUA 只提供三樣東西：(1) ROS 2 的官方文件；(2) 基本的終端機工具（terminal tools）；(3) 讓代理能讀寫檔案、執行程式的權限。代理必須自行組織工作：它要閱讀文件以理解 ROS 2 的訊息傳遞（messaging）機制、查詢可用的主題（topics）與服務（services）、撰寫控制程式、執行 `ros2` 命令列介面（ros2 CLI）指令或 `rclpy` 程式，並根據終端機回饋（terminal feedback）反覆除錯。這與傳統 CaP（Code as Policies，程式即策略）方法形成對比：後者通常會預先封裝好感知與控制的原語庫（primitive libraries），而 OpenRUA 則讓這些原語在執行時由代理自己「長出來」。

方法論上最關鍵的轉換有兩點。第一，**感知即檔案輸入/輸出（perception as file I/O）**：代理從 ROS 2 取得 RGB-D 觀測（RGB-D observation）後，將其儲存為工作空間中的影像檔案，再用 Python 腳本進行影像處理（例如裁切、加網格、從深度重建點雲），進而計算度量測量（metric measurement）如目標物的三維座標。第二，**操作即編碼（manipulation as coding）**：代理不呼叫預先寫好的運動原語，而是自己撰寫運動控制客戶端（motion-control client），例如軌跡執行、夾爪控制（gripper control），甚至閉迴路控制程式（closed-loop control program），根據感測器回饋（sensor feedback）即時調整動作或停止。

這種 zero-abstraction（零抽象）設計有幾個方法論上的優勢。首先，它消除了人類工程師為每個新任務或新環境重新設計 harness 的成本。其次，由於代理直接操作 ROS 2，它可以利用機器人社群數十年累積的完整軟體堆疊（software stack），包括驅動程式（driver）、規劃器（planner）、控制器（controller）等，而不受限於某個專案預先選定的工具集合。第三，因為策略是以顯式程式（explicit program）形式存在，代理可以自我檢查、編輯、除錯，而不需要重新訓練模型。最後，這種設計把「泛化能力」的責任從學習模型的訓練分佈（training distribution）轉移到代理的推理與程式合成能力上，從而有可能處理訓練資料中未見過的任務擾動（task perturbation）與位置擾動（position perturbation）。

然而，這種極簡主義也帶來方法論上的風險。由於沒有預設的工作流程，代理可能會在探索 ROS 2 介面時浪費大量試錯步驟；若文件不完整或機器人環境有非預期狀態，代理可能無法收斂到可行策略。此外，這種方法高度依賴底層編碼代理的能力：論文使用 Claude Code 搭配 Claude Opus 5，這代表方法論的有效性與特定 frontier 模型的推理、程式合成與自我糾錯能力緊密綁定。

#### 實驗數據解讀

論文在三個基準上進行零樣本（zero-shot）評測：CaP-Bench、LIBERO-PRO 與 RoboCasa365。所謂零樣本不僅指沒有任務特定訓練，還強調代理無法取得模擬器的特權狀態（privileged simulator state）與基準預設的成功判斷函式（success predicates），這讓實驗設定更接近真實機器人部署情境。

在 **CaP-Bench** 上，OpenRUA 達到 **99.0%** 的成功率（success rate）。CaP-Bench 是針對程式即策略（CaP）設計的基準，任務通常涉及相對明確的幾何關係與可程式化的操作邏輯。99.0% 的成績顯示，只要任務可以被分解為明確的感知—規劃—控制步驟，現成的編碼代理透過 ROS 2 幾乎可以完美解決。

在 **LIBERO-PRO** 上，OpenRUA 達到 **87.0%** 的成功率，超過 ASPIRE（69.0%）與 HarnessVLA（82.4%）。LIBERO-PRO 特別強調對位置擾動（position perturbation）與任務擾動（task perturbation）的泛化。傳統端到端視覺動作策略（end-to-end visuomotor policy）如 OpenVLA 與 π0（pi-zero）在標準 LIBERO 上雖有 90% 以上表現，但在 LIBERO-PRO 的擾動下會跌至 0.0%。OpenRUA 的 87.0% 說明，透過顯式程式推理幾何與任務結構，可以顯著提升對分佈外（out-of-distribution）變化的魯棒性。

在 **RoboCasa365** 上，OpenRUA 在已見過的複合任務（seen composite tasks）達到 26.3%，在未見過的複合任務（unseen composite tasks）達到 28.1%。雖然絕對數字不高，但相較於 HarnessVLA（未見任務降至 13.8%）與 RLDX-1（未見任務降至 5.0%），OpenRUA 在已見與未見任務之間的表現幾乎沒有衰退。這一點非常重要：它顯示不依賴學習式機器人策略（learned robot policy）的顯式程式方法，在面對組合性（compositionality）與新任務組合時具有更穩定的泛化潛力。

進一步的量化分析揭示了代理的湧現行為（emergent behavior）：

1. **感知方面**：在 96.80% 的回合（episode）中，代理會主動撰寫程式處理原始感官輸入（raw sensory input），並推導出度量測量（metric measurement）。這表示代理幾乎總是會把「看」這件事轉換成可計算、可驗證的程式碼，而不是依賴模糊的語言描述。
2. **操作方面**：在 95.87% 的回合中，代理會自行建立運動控制客戶端（motion-control client），例如夾爪控制；在 50.13% 的回合中，代理會建立閉迴路控制程式（closed-loop control program），根據感測器回饋調整動作。這說明代理不僅能開環執行動作，還能在約一半的任務中主動引入回饋機制。
3. **測試時運算（test-time computation）**：增加互動次數或推理深度可以提升成功率，但最終會飽和，且飽和水準因模型而異。這暗示 OpenRUA 的成功不僅來自介面設計，也來自底層語言模型在測試時的推理投資。

整體而言，實驗數據支持論文的核心論點：一個強大的現成編碼代理可以作為零樣本視覺動作策略（zero-shot visuomotor policy），透過機器人原生介面完成多樣化任務。然而，RoboCasa365 上絕對成功率仍偏低，顯示對於高度複合、長程、需要精細接觸物理（contact-rich manipulation）的任務，單純的終端機存取與程式合成仍有明顯瓶頸。

#### 與現有研究的比較

OpenRUA 在概念上延續了 Code as Policies（CaP）與 Robot-Use Agent（RUA）的研究脈絡，但在設計哲學上與近期多數工作形成鮮明對比。

**與 VLA / WAM 的比較**：Vision-Language-Action（VLA）模型與 World Action Model（WAM）屬於學習式端到端視覺動作策略（learned end-to-end visuomotor policy），需要大量示範資料（demonstration data），且泛化能力受限於訓練分佈。OpenRUA 不需要任何任務特定訓練，也不依賴學習式策略，而是透過顯式程式與幾何推理完成任務。在 LIBERO-PRO 的擾動場景中，OpenVLA 與 π0 的成功率跌至 0.0%，而 OpenRUA 達到 87.0%，這凸顯了顯式程式方法在分佈外泛化上的優勢。然而，VLA 模型在標準 LIBERO 等分佈內任務上仍可能更快、更穩定，因為它們不需要每次任務都重新生成與執行程式碼。

**與 ASPIRE、HarnessVLA 等 RUA 系統的比較**：ASPIRE 與 HarnessVLA 代表了目前 RUA 領域的主流方向：為代理設計專屬工具介面與原語庫，並協調（orchestrate）代理工作流程。例如 HarnessVLA 會把學習式 VLA 策略封裝為可呼叫工具，ASPIRE 則可能提供預先設計的感知與控制原語。OpenRUA 的實驗數據顯示，在 CaP-Bench 與 LIBERO-PRO 上，它分別超越 ASPIRE 18.0 百分點、超越 HarnessVLA 4.6 百分點。這挑戰了「RUA 必須依賴客製化 harness」的預設，指出許多 harness 工程可能只是在補償當時代理能力的不足，而非機器人控制的必要條件。

**與 RLDX-1 的比較**：在 RoboCasa365 上，RLDX-1 在未見複合任務上從已見任務的表現大幅滑落至 5.0%，而 OpenRUA 維持在 28.1%。這顯示學習式策略在面對組合性新任務時容易崩潰，而基於顯式程式的代理則能透過重新組合已學到的子程式或推理步驟來應對。

**定位與貢獻**：OpenRUA 的最大貢獻在於方法論上的極簡化與概念驗證。它證明了在具備強大推理能力的 frontier 編碼代理（如 Claude Code / Claude Opus 5）出現後，機器人控制可以回歸到人類工程師熟悉的原生介面（ROS 2），而不需要額外的抽象層。這不僅降低了將編碼代理移植到新機器人平台的門檻，也讓機器人研究社群可以重新思考「harness 工程」的必要性。

**限制**：首先，OpenRUA 高度依賴 Claude Opus 5 等商業 frontier 模型，成本與可取得性都是問題。其次，雖然在 CaP-Bench 與 LIBERO-PRO 上表現優異，但在 RoboCasa365 的複合任務上絕對成功率仍低，顯示對於長程規劃、精細接觸、動態環境等挑戰，單純的終端機存取可能不足。第三，論文未深入討論安全性（safety）與即時性（real-time）問題：在真實機器人上讓代理自由執行任意 ROS 2 指令，可能帶來碰撞、過載或不可預測行為的風險。第四，實驗主要在模擬環境中進行，雖然論文標題與圖示強調真實機器人，但詳細的真實世界評測數據與失敗案例分析在提供的摘要中較少。

#### 可重現性評估

OpenRUA 在可重現性（reproducibility）方面採取了相對開放的態度：論文明確表示程式碼已公開於 https://github.com/terminalworld/OpenRUA。這讓其他研究者可以檢視 workspace-as-harness 的具體實作、工作空間中的文件結構、提供的 ROS 2 文件範圍，以及代理與環境互動的介面定義。

然而，可重現性仍面臨幾個實務挑戰：

1. **模型依賴**：論文使用 Claude Code 搭配 Claude Opus 5，這是 Anthropic 的商業產品。即使程式碼開源，若沒有相同模型存取權，其他研究者難以完全複製 99.0% / 87.0% 的數據。不同模型（如 Codex、GPT-4o、Gemini）在程式合成、ROS 2 文件理解、自我糾錯能力上的差異，可能導致成功率顯著不同。論文雖提到測試時運算飽和水準因模型而異，但未詳細比較多種模型。

2. **機器人平台與 ROS 2 環境**：OpenRUA 的設計雖然號稱通用於任何 ROS 2 機器人，但實際重現需要完整的 ROS 2 軟體堆疊，包括驅動程式、控制器、感測器主題、動作伺服器等。對於沒有相同硬體或模擬環境的研究者，需要額外工程才能將 OpenRUA 移植到自己的機器人上。

3. **基準資料集與評測協定**：CaP-Bench、LIBERO-PRO 與 RoboCasa365 都是公開基準，理論上可重現。但論文強調不使用特權模擬器狀態與成功判斷函式，這意味著評測流程需要仔細設計：代理必須自己判斷任務是否完成，而不能依賴基準內建的自動評分。這種「自我驗證」機制的具體實作細節會影響可重現性。

4. **計算成本與時間**：讓編碼代理在終端機上反覆試錯、撰寫與執行程式，每個回合可能消耗大量 token 與時間。大規模重現論文結果需要可觀的 API 預算與運算資源。

5. **文件與社群支援**：由於 OpenRUA 極度依賴 ROS 2 官方文件，若文件版本與實際環境不一致，代理可能產生錯誤程式碼。開源倉庫是否包含詳細的安裝指南、Docker 映像檔、預設環境設定，將決定社群能否順利重現。

總體而言，OpenRUA 在「方法論透明性」上做得很好，程式碼公開、介面簡單。但在「結果完全可重現」上，仍受限於商業模型、硬體環境與高計算成本。未來若能提供開源替代模型（如基於開放權重模型的編碼代理）與標準化 Docker 環境，將大幅提升可重現性。

#### 未來研究方向

OpenRUA 的出現為機器人使用代理（RUA）領域開啟了多條值得探索的研究方向：

1. **開源模型版本的 OpenRUA**：目前成果高度依賴 Claude Opus 5。未來可研究如何使用開放權重模型（如 Qwen-Coder、DeepSeek-Coder、Llama 系列）或較小的專精模型來驅動 OpenRUA，並分析能力門檻與成本效益。這對學術界與工業界的廣泛採用至關重要。

2. **混合式策略：顯式程式 + 學習式原語**：OpenRUA 證明了顯式程式的泛化優勢，但在某些重複性高、反應時間要求高的操作上，學習式視覺動作策略（VLA）可能更有效。未來可研究如何讓編碼代理在需要時自動呼叫或微調學習式原語，形成「程式為骨架、學習為肌肉」的混合系統。

3. **長程複合任務與規劃**：RoboCasa365 上的低成功率顯示，對於多步驟、需要工具使用或精細接觸的複合任務，單純的終端機試錯可能不足。未來可研究如何在工作空間中嵌入更強大的任務規劃器（task planner）、記憶機制（memory）與子目標驗證（subgoal verification），同時保持 zero-abstraction 精神。

4. **安全與即時控制**：在真實機器人上運行自動生成的 ROS 2 程式具有安全風險。未來需要發展沙箱機制（sandboxing）、動作約束檢查（action constraint checking）、緊急停止（emergency stop）與人類監督介面，讓 OpenRUA 能安全地部署於實體機器人。

5. **多機器人與異質平台泛化**：OpenRUA 使用 ROS 2 作為通用介面，理論上可擴展到不同機器人。未來可研究代理如何自動適應新的 ROS 2 主題命名、座標系統、控制器介面，甚至非 ROS 機器人（透過橋接器），實現真正的跨平台機器人使用代理。

6. **測試時運算的最適化**：論文發現增加測試時運算（test-time computation）能提升成功率但會飽和。未來可研究如何動態分配推理預算：在簡單任務上快速執行，在困難任務上啟動更深層的自我反思（self-reflection）與模擬驗證（simulation-based verification）。

7. **失敗模式分析與自動修復**：OpenRUA 的顯式程式特性使得失敗案例可以被記錄、分析與修復。未來可建立大規模失敗資料庫，讓代理從過去錯誤中學習，形成可持續改進的機器人控制知識庫。

8. **真實世界長期自主運作**：目前評測多為單一回合任務。未來可探索 OpenRUA 在長時間、開放式環境中的表現，例如家庭助理機器人需要連續執行數小時、處理未預期事件並與人類互動。

9. **基準與評測標準的演進**：OpenRUA 的成功提示我們需要新的基準，不僅測試任務成功率，還要測試代理的自主介面探索能力、程式可解釋性、對分佈外擾動的魯棒性，以及不使用特權狀態時的自我驗證能力。

10. **人機協作與可解釋性**：由於 OpenRUA 生成的是顯式程式，人類可以閱讀、修改與理解代理的策略。未來可發展互動式介面，讓非專家使用者透過自然語言指導或修正代理生成的控制程式，降低機器人程式設計的門檻。

## 論文問答

**Q1：OpenRUA 主要想解決什麼問題？**
A：OpenRUA 針對的是現有機器人使用代理（RUA）系統往往需要大量客製化 harness 工程的問題，這些系統會為代理預先設計專屬的工具介面、感知與控制原語庫，甚至編排特定的工作流程。論文質疑：既然機器人領域已經有成熟數十年的原生軟體介面（如 ROS 2），這些額外的客製化抽象層是否真的必要？因此，OpenRUA 提出一種零抽象層的 harness，讓現成的編碼代理僅透過終端機存取 ROS 2，就能像人類工程師一樣直接操作機器人。

**Q2：為什麼現有的 RUA 方法會依賴客製化 harness？**
A：現有方法大致分為兩類：一類是把學習好的視覺-語言-動作（VLA）模型包裝成可呼叫工具，讓代理透過高階 API 使用；另一類則是根據人類專業知識手工打造感知與控制原語庫。這些客製化介面與原語某種程度上是在彌補當時編碼代理能力的不足，並透過預設流程降低代理出錯的風險。然而，這也帶來額外的工程負擔，並且讓系統難以泛化到新任務或新環境。

**Q3：跳過客製化抽象層為什麼重要？**
A：如果能直接利用機器人的原生介面，就可以大幅減少為每個新任務重新設計工具或原語的人力成本，並充分發揮 ROS 2 生態系長期累積的驅動程式、訊息傳遞與控制器資源。這也證明了現成的編碼代理可以在沒有任務特定訓練、也沒有學習策略的情況下，充當零樣本視覺動作策略。從更廣的層面來看，這有助於降低機器人程式設計的門檻，並可能改善端到端學習方法在訓練分佈外場景的泛化問題。

**Q4：OpenRUA 的核心方法是什麼？**
A：OpenRUA 採用「工作空間即中介架構」（workspace-as-harness）的極簡設計，只給編碼代理一個包含 ROS 2 文件與基本工具的工作空間，並透過終端機提供對機器人原生 ROS 2 介面的存取權限。在這個空間裡，感知被重新定義為檔案輸入／輸出：代理把 RGB-D 觀測存成檔案、讀取影像、計算幾何量測；操作則被重新定義為編碼：代理撰寫 ros2 CLI 指令或 rclpy 程式來發送控制命令。整個過程不預設任何代理工作流程，完全由編碼代理自行組織與迭代。

**Q5：workspace-as-harness 設計的關鍵創新在哪裡？**
A：關鍵創新在於它完全移除了傳統 RUA 系統中的客製化抽象層與預先編排的工作流程，把「使用機器人」當成一個即時、互動式的軟體專案。工作空間本身即為 harness，只提供最低限度的資源，讓代理像處理陌生程式碼庫一樣自主探索與完成任務。這種設計讓感知策略與控制策略能夠隨任務需求自然湧現，而非被人類工程師預先固定。

**Q6：哪些設計選擇讓 OpenRUA 能成為零樣本視覺動作策略？**
A：首先是選用 ROS 2 原生介面，讓代理能直接訂閱感測器主題、呼叫控制器服務；其次是將觀測轉化為檔案輸入／輸出，使代理可以用一般程式方式處理原始感官輸入；第三是將動作生成轉化為編碼，讓代理能明確地對幾何與運動進行推理。此外，實驗採用零樣本設定，不給予特權模擬器狀態或成功判斷條件，代理必須根據終端機回饋反覆修正，這些選擇共同促成了「編碼代理即策略」的可能性。

**Q7：OpenRUA 在哪些基準測試與設定下進行評估？**
A：論文在 CaP-Bench、LIBERO-PRO 與 RoboCasa365 三個廣泛使用的機器人操作基準上進行評估，並且採用零樣本設定，不讓代理接觸特權模擬器狀態或基準內建的成功判斷條件。實驗主要使用 Claude Code 搭配 Claude Opus 5 作為現成的編碼代理。比較對象包括 ASPIRE、HarnessVLA 與 RLDX-1 等領先系統，以檢驗 OpenRUA 是否能透過原生介面達到競爭力。

**Q8：OpenRUA 的關鍵量化結果是什麼？**
A：在 CaP-Bench 上，OpenRUA 達到 99.0% 的成功率；在 LIBERO-PRO 上達到 87.0%，分別領先 ASPIRE 18.0 個百分點與 HarnessVLA 4.6 個百分點。在 RoboCasa365 的未見複合任務上，OpenRUA 也取得 28.1% 的成功率，領先 HarnessVLA 13.1 個百分點。這些結果顯示，僅靠現成編碼代理與 ROS 2 原生介面，就能在零樣本設定下達到甚至超越需要客製化 harness 或學習策略的系統。

**Q9：消融與湧現行為分析揭示了什麼？**
A：分析發現代理在 96.80% 的回合中會自發撰寫程式處理原始感官輸入並推導度量測量，例如裁切影像、加入網格或從深度重建點雲；在 95.87% 的回合中會自行建立運動控制客戶端，如夾爪控制；在 50.13% 的回合中則會實作閉迴路控制程式，根據感測器回饋調整動作。此外，增加測試時計算量（更多互動或推理）能提升成功率，但最終會飽和，且飽和點因模型而異。在 RoboCasa365 上，OpenRUA 對已見與未見複合任務的成功率相近（26.3% 與 28.1%），相較於依賴學習策略的 RLDX-1 在未見任務上大幅衰退至 5.0%，顯示其泛化潛力。

**Q10：OpenRUA 適合哪些實際應用場景？**
A：OpenRUA 特別適合需要快速部署到新操作任務的場景，例如倉儲物流中的物品分揀、實驗室中的樣本搬運，或是家庭環境中的整理與擺放任務。由於不需要針對每個任務重新訓練模型或打造客製化原語，工程師或甚至非專家使用者只要透過自然語言指令，就能讓現成編碼代理生成 ROS 2 控制程式。這種方式能縮短從任務描述到實機執行的開發週期，並降低對機器人專業知識的依賴。

**Q11：若要將 OpenRUA 產品化，需要考慮哪些因素？**
A：首先必須確保終端機存取真實機器人時的安全性，包括沙箱化、動作範圍限制、緊急停止機制，以及必要時的人類在環監督。其次，系統成效高度依賴前沿編碼代理的能力與 ROS 2 文件、介面的品質，因此模型選擇與文件維護至關重要。此外，測試時計算所帶來的延遲與成本也是實際部署時必須權衡的商業與使用者體驗因素。

**Q12：OpenRUA 對機器人領域可能帶來什麼影響？**
A：OpenRUA 挑戰了「機器人代理必須仰賴客製化 harness 才能有效運作」的預設，將研究焦點轉向原生介面與編碼代理本身的能力。它可能加速「程式即策略」（Code as Policies）的發展，並減少對大規模示範資料與端到端學習策略的依賴。長遠來看，這也可能促使未來機器人軟體堆疊在設計時就更重視對代理友善的文件、介面與可觀測性。

**Q13：論文承認了哪些限制？**
A：儘管在 CaP-Bench 與 LIBERO-PRO 表現優異，OpenRUA 在更複雜的 RoboCasa365 未見複合任務上成功率仍僅 28.1%，顯示面對長期複合任務時仍有進步空間。此外，整體表現高度仰賴編碼代理的程式撰寫與推理能力，以及 ROS 2 介面與文件的完整度。論文也尚未深入探討真實世界部署中的安全保證、延遲限制與硬體異常處理等議題。

**Q14：OpenRUA 可能的失敗案例有哪些？**
A：對於需要高速閉迴路控制或精密接觸操作的任務，如果代理生成的程式存在邏輯錯誤或迭代速度過慢，就可能導致任務失敗。長期複合任務可能超出代理的規劃視野，使其難以維持正確的子目標順序與狀態追蹤。另外，感測器雜訊或觀測歧義也可能讓代理推導出錯誤的度量測量，進而產生不準確的運動目標。

**Q15：未來可以朝哪些方向發展？**
A：未來可以將 OpenRUA 與學習好的低階技能或世界模型結合，以處理更困難的接觸與動態操作任務，同時保留其可解釋與可除錯的優勢。也可以強化代理的自我驗證、錯誤恢復與長期規劃能力，讓它在失敗後能自動診斷並修正控制程式。此外，將此框架擴展到多機器人協作、真實世界安全關鍵部署，以及研究測試時計算規模與機器人控制成功率之間的縮放規律，都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **彈性製造與組裝工作站**  
   在少量多樣的生產線中，機械手臂需頻繁切換取放、鎖附、插裝等任務。OpenRUA 可讓作業員直接用自然語言下達新任務，由編碼代理透過 ROS 2 原生介面生成控制程式，無需為每項任務重新訓練視覺動作模型或撰寫專用 primitive。

2. **物流倉儲的異質機器人調度**  
   當 AGV／AMR 與機械手臂共用 ROS 2 介面時，代理可根據訂單與包裹資訊自動生成導航、對位、夾取與放置流程，並利用 RGB-D 觀測與閉迴路控制適應不同包裹形狀與位置擾動。

3. **研究實驗室的快速原型開發**  
   研究人員可用自然語言描述實驗流程（例如「將試管從 A 架移到 B 架並拍照」），讓 Claude Code 等現成編碼代理自動撰寫 rclpy 節點、處理點雲、計算目標座標並執行動作，縮短從想法到實驗的週期。

4. **農業與溫室的選採與監測**  
   面對作物形態、成熟度與戶外光線的高度變異，代理可即時生成影像處理與運動控制程式，透過原生感測器介面調整夾取策略，減少對大量示範資料的依賴。

5. **服務機器人的日常任務**  
   家用或商用機器人接收口語指令後，代理可在 workspace 中規劃並執行整理桌面、倒飲料等動作，並根據終端機回饋與 RGB-D 觀測反覆修正，直到任務完成。

### 實作前置條件

**資料準備**
- 機器人的 ROS 2 介面規格：topic、service、action 名稱與訊息型別（尤其是相機、關節狀態、夾爪、軌跡執行控制器）。
- 機器人描述檔（URDF／SDF）與座標系定義。
- 控制器與驅動程式的官方文件，作為 workspace 內的參考資料。
- 任務語言指令範本，無需大規模示範資料或成功條件的程式碼。

**運算資源**
- 可執行 ROS 2 的機器人電腦或模擬器（x86 或 ARM；模擬器建議配 GPU）。
- 執行現成編碼代理的工作站，需能呼叫 LLM API（如 Claude Code／Opus 5）並具備足夠的 token 預算。
- 真實機器人建議搭配獨立安全控制器與實體急停裝置。

**技能需求**
- 熟悉 ROS 2 基礎：node、topic、service、action、rclpy、ros2 CLI。
- 具備機器人運動學、座標轉換與基本安全操作知識。
- 能夠使用 Linux 終端機、撰寫 Python 程式，並審查代理生成的程式碼。
- 了解 LLM API 的成本、延遲與權限管理。

### 實作步驟建議

1. **建立 ROS 2 原生環境**  
   確認機器人或模擬器已正確暴露所有感測器與控制器介面，並能透過標準 ros2 topic list、ros2 service list 等指令存取。

2. **建構 workspace-as-harness**  
   建立一個工作空間目錄，內含 ROS 2 官方文件、機器人介面說明、launch 檔與基本工具腳本。只給予編碼代理終端機存取權，不預先撰寫任務專用 primitive 或代理工作流程。

3. **將感知轉化為檔案 I/O**  
   設定感測器節點定期將 RGB-D 觀測、點雲或關節狀態儲存為工作空間內的檔案，讓代理能直接讀取、顯示與處理，無需客製化視覺 API。

4. **將操作轉化為編碼**  
   讓代理透過 ros2 CLI 或 rclpy 程式發送控制指令。不封裝高階動作庫，而是讓代理自行建立夾爪控制、軌跡執行與閉迴路調整等客戶端。

5. **選擇並設定現成編碼代理**  
   以 Claude Code 等工具為例，設定其可讀寫工作空間、執行終端機指令，並限制其對系統關鍵資源的存取。撰寫簡潔的系統提示，強調只能使用 ROS 2 原生介面。

6. **零樣本任務執行與迭代**  
   用自然語言描述任務目標，讓代理自主規劃、撰寫程式、執行、觀察終端機回饋與感測器檔案，並反覆修正直到完成。

7. **驗證、記錄與部署**  
   在模擬環境中先評估成功率與安全性，再轉移至真實機器人。將生成的控制程式納入版本控制，建立回歸測試與持續整合流程。

### 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **實體安全風險** | 代理可能生成過快速度或碰撞路徑。 | 設定速度、力矩與工作空間限制；配置硬體急停與獨立安全 PLC。 |
| **程式碼幻覺** | LLM 可能呼叫不存在的 topic、service 或參數。 | 要求代理先查詢 ros2 interface，並在模擬器中驗證後才上真機。 |
| **無限迴圈與資源耗盡** | 代理可能反覆重試或產生大量檔案。 | 設定執行逾時、token 上限與磁碟配額；加入人類在環監控。 |
| **非確定性行為** | 每次執行可能產生不同策略與結果。 | 記錄每個回合的程式與觀測，建立可重現的測試案例與備用策略。 |
| **API 延遲與成本** | 長時間任務會消耗大量 LLM token。 | 評估任務複雜度與預算，必要時將常見策略快取為可重複使用的腳本。 |
| **ROS 2 介面異動** | 韌體更新可能改變 topic 名稱或訊息格式。 | 維護介面文件與自動化檢查，確保代理使用的介面始終有效。 |

### 與其他技術的整合建議

- **與現有製造／倉儲系統整合**：透過 ROS 2 topic 或 rosbridge 接收 MES、ERP、WMS 的任務指令，並將執行結果回傳，無需改寫上層系統。
- **與學習式策略互補**：可將 VLA／WAM 視為可選工具，在代理判斷需要時呼叫，而非作為必經的客製化抽象層。
- **與數位孿生結合**：在 Gazebo、Isaac Sim 或 NVIDIA Omniverse 中複製 workspace，讓代理先在模擬環境驗證程式，再部署到真實機器人。
- **與版本控制及 CI/CD 整合**：將代理生成的 rclpy 程式與 launch 檔納入 Git，建立自動化測試與程式碼審查流程。
- **與多機協作系統整合**：利用 ROS 2 的多機器人機制，讓單一編碼代理或代理群組透過原生介面協調不同機器人。

---

### 給不同背景讀者的閱讀建議

**初學者**：建議先掌握 ROS 2 基礎與機器人安全操作，再從模擬環境開始嘗試 OpenRUA。重點理解「工作空間即中介架構」與「感知即檔案 I/O、操作即編碼」這兩個核心概念，不必急著追求真機部署。

**AI 工程師**：請聚焦於 harness 的極簡設計、提示工程與代理的湧現行為，特別是代理如何自主建立閉迴路控制與運動控制客戶端。同時評估 LLM API 的成本、延遲與可靠性，並思考何時應保留傳統 primitive 作為安全後備。

**研究人員**：本論文提供了零樣本視覺動作策略的新視角，值得深入分析其與 Code as Policies、VLA、WAM 的差異與互補性。可進一步探討代理在長期任務、多模態觀測與真實世界泛化上的極限與理論基礎。

**產品經理**：OpenRUA 適合任務多樣、示範資料稀缺、但需要快速上線的場景。評估時請同時考慮對 frontier LLM API 的依賴、安全法規要求、以及與傳統自動化或學習式方案相比的總體擁有成本與彈性優勢。
