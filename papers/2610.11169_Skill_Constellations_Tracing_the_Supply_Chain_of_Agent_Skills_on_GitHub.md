# 技能星座：追溯 GitHub 上代理技能（Agent Skills）的供應鏈

**原文標題：** Skill Constellations: Tracing the Supply Chain of Agent Skills on GitHub  
**作者：** Fahd Seddik  
**發布日期：** 2026-10-08

## ⚡ TL;DR

AI代理技能在GitHub上以複製方式散佈，缺乏註冊中心、版本與溯源機制。
作者從GitSkills的SKILL.md git歷史重建帶日期的複製網路，並擬合模型排序稽核儲存庫。
少數儲存庫是幾乎所有複製的來源，稽核模型排名前100的儲存庫可阻止14.9%的高風險技能後續採用。

## 摘要翻譯

代理技能（Agent skills）是 SKILL.md 指令與腳本，由 Claude Code 與 Codex 等 AI 程式設計代理（AI coding agents）以使用者權限（permissions of their user）執行。開發者透過在儲存庫（repository）之間複製來分享技能，使這些技能成為一個無註冊中心（without a registry）、無版本、無溯源（provenance）的軟體供應鏈（software supply chain）。因此，被複製技能的來源、安全性修補（security fix）的觸及範圍（reach），以及值得審查的儲存庫皆不得而知。僅記錄單一時間點（single point in time）下哪些儲存庫持有技能的研究，無法揭示複製來源關係（who copied it from whom）。我們貢獻了首個帶日期的代理技能複製網路（dated copy network），該網路係根據 GitSkills 中每個 SKILL.md 的 Git 歷史紀錄（Git history）建構而成，橫跨整個 GitHub 涵蓋 2,193,119 次技能採用（skill adoptions），並附帶一個互動式檢視器（interactive viewer）。少數儲存庫（a few repositories）是幾乎所有複製的來源（source of almost all copies），而 GitHub 星標（GitHub stars）無法識別它們。技能複製幾乎不會隨其來源變更（almost never change），因此在來源處的修補鮮少觸及（rarely reaches）它們。我們擬合一個模型（fit a model），用以預測其他儲存庫會從哪些儲存庫複製，並據此對儲存庫進行稽核排序（rank repositories for audit）。審查模型排名最高的 100 個儲存庫，可預防（prevents）14.9% 的高風險技能（high-risk skills）後續被採用（later adoptions），相較於 100 個最多星標的儲存庫僅能預防 0.5%，這為資安工程師（security engineers）提供了一份在技能擴散前可檢查的簡短清單（short list to check before a skill spreads）。因此，平台應發布版本化參照（versioned references）而非複製（rather than copies）。專案網站：https://fahdseddik.github.io/Skill-Constellations/

### 核心貢獻（3～5點）
- **首個帶日期的代理技能複製網路（dated copy network）**：建構自 GitSkills 中每個 SKILL.md 的 Git 歷史紀錄，橫跨整個 GitHub 涵蓋 2,193,119 次技能採用，並附帶互動式檢視器，使複製來源關係（who copied it from whom）首次可被追溯。
- **揭示供應鏈集中度與星標失效現象**：發現少數儲存庫是幾乎所有複製的來源（source of almost all copies），而 GitHub 星標（GitHub stars）無法有效識別這些關鍵節點，凸顯現行以星標作為品質指標的不足。
- **量化安全性修補的擴散困境**：證實技能複製幾乎不會隨其來源變更（almost never change），導致在來源處的安全性修補（security fix）鮮少觸及（rarely reaches）下游副本。
- **提出稽核排序模型與實證效益**：擬合一個模型用以預測其他儲存庫會從哪些儲存庫複製，並據此對儲存庫進行稽核排序；審查排名最高的 100 個儲存庫可預防 14.9% 的高風險技能後續被採用，相較於 100 個最多星標的儲存庫僅能預防 0.5%。
- **政策建議**：平台應發布版本化參照（versioned references）而非複製（rather than copies），以從根本上改善代理技能供應鏈的可追溯性與安全性。

### 適合對象
本研究最適合以下讀者閱讀：
- **資安工程師（security engineers）與軟體供應鏈（software supply chain）風險管理者**：可從中取得具體的稽核排序方法與高風險技能擴散前的檢查清單。
- **AI 程式設計代理（AI coding agents）平台開發者與生態系維護者**：Claude Code、Codex、Cursor 等代理工具的設計者可參考其政策建議，思考如何以版本化參照取代直接複製。
- **軟體工程（software engineering）與挖掘軟體儲存庫（mining software repositories, MSR）研究者**：對程式碼克隆（code clones）追蹤、儲存庫網路（repository network）分析、複製級聯（copy cascade）建模等議題感興趣的學者。
- **開源治理與開源安全政策制定者**：關注無註冊中心（without a registry）生態系中溯源（provenance）與審查機制設計的研究與政策人員。

## 深度分析

#### 方法論解析

本論文提出了一套從 Git 歷史紀錄 (Git history) 中重建代理技能 (agent skills) 複製網路 (copy network) 的方法論，核心目標是解決 AI 程式設計代理 (AI coding agents) 生態系中缺乏溯源 (provenance) 機制的根本問題。

**1. 資料收集與前處理**

作者採用 GitSkills 資料集（2026 年 7 月發布，存檔於 Zenodo，DOI 10.5281/zenodo.21875637）作為起點。篩選條件相當嚴謹：
- 僅保留檔名完全為 `SKILL.md` 且具備有效 front matter 的檔案
- 首次提交日期需在 2025 年 10 月 1 日之後
- 排除 fork 儲存庫 (repositories)，避免重複計算歷史紀錄
- 將每個不同的內容視為一個獨立技能

接著從每個儲存庫的預設分支 (default branch) clone，收集所有 `SKILL.md` 路徑的完整 Git 歷史紀錄。每次「採用」(adoption) 以儲存庫首次提交該技能的日期標記，並以下界（儲存庫建立日期）約束，因為 fork 與鏡像會帶入較舊的歷史。

**2. 譜系、複製與星座的定義**

這是方法論最關鍵的概念設計：
- **譜系 (Lineage)**：將同一技能透過編輯連結的不同版本串接起來，其首次採用即為「起源」(origin)
- **複製事件 (Copy event)**：當一次提交新增 10 個以上 `SKILL.md` 檔案，且其中至少一半的既有譜系來自同一個先前的採用者時，該採用者即為「來源」(source)
- **複製事件分類**：少於 100 個檔案為「套件複製」(bundle)，100 個以上為「批次複製」(bulk)，少於 10 個檔案則歸為「個別採用」(individual)
- **星座 (Constellation)**：單一技能的所有複製所形成的網路

此設計巧妙地將「複製」與「採用」區分開來——個別採用代表開發者自行撰寫技能，而套件/批次複製則反映系統性的散佈行為。

**3. 複製網路重建演算法**

由於缺乏明確的依賴宣告，作者採用啟發式方法識別複製來源：當一次提交大量引入 `SKILL.md` 檔案，且其中多數譜系可追溯至單一既有採用者時，該採用者即被認定為來源。這種「多數譜系歸屬」規則在實務上能有效區分真正的複製與偶然的相似提交。

**4. 稽核排名模型**

作者擬合 (fit) 一個模型來預測哪些儲存庫會被其他儲存庫複製，藉此對儲存庫進行稽核排序。此模型基於複製網路中的出度 (out-degree) 與其他網路位置特徵，並以時間切分 (temporal split) 進行滯後驗證 (hindsight bound)，確保排名能預測未來而非僅解釋過去。

**5. 與安裝工具記錄的驗證**

作者將重建的複製網路與技能安裝工具（skill installers）的記錄進行比對驗證，這是方法論可信度的重要環節，因為安裝工具會記錄明確的安裝來源，可作為 ground truth 的一部分。

#### 實驗數據解讀

**1. 規模與覆蓋率**

資料集涵蓋 259,596 個儲存庫、1,612,846 個獨立技能、2,193,119 次技能採用。其中約半數的 `SKILL.md` 檔案是另一檔案的逐字複製 (verbatim copies)，這個比例極為驚人，顯示代理技能生態系高度依賴複製而非原創。

**2. 複製 vs 個別採用（Fig. 2a）**

- 套件複製 (bundle)：33.3%
- 批次複製 (bulk)：58.6%
- 個別採用 (individual)：僅 8.1%

這意味著超過 90% 的技能傳播是透過複製而非原創，徹底顛覆了「開發者各自編寫技能」的假設。批次複製佔絕大多數，顯示存在大量「技能目錄」(skill catalogs) 或「聚合器」(aggregators) 系統性地散佈技能集合。

**3. 傳播的過度離散特性（Fig. 2b）**

作者以負二項分布 (negative binomial) 擬合每次採用的傳播數，發現離散參數 k = 0.086，遠低於 1，表示傳播呈現極端的過度離散 (overdispersion)。這在實務上意味著：大多數技能被複製次數極少，但少數技能被複製極多次。

**4. 來源的高度集中（Fig. 2c）**

前 1% 的儲存庫貢獻了 94.7% 的累積傳播量。這是典型的冪律 (power-law) 或重尾分布 (heavy-tailed distribution)，與許多軟體生態系的觀察一致，但集中程度更為極端。

**5. 星標與複製出度的弱相關（Fig. 2d）**

Kendall τ = −0.10 的相關係數顯示 GitHub 星標 (GitHub stars) 幾乎無法預測哪些儲存庫會成為複製來源。負值更暗示星標高的儲存庫反而較少被複製為來源——這可能是因為熱門專案往往有更複雜的結構，不適合作為技能複製的範本。

**6. 稽核效果的量化比較（Fig. 2e）**

這是論文最具實務價值的發現：
- 複製出度 (Copy out-degree)：捕捉 27.8% 的後續傳播
- 滯後上界 (Hindsight bound)：43.8%
- 持有技能數 (Skills held)：29.3%
- 起始模板 (Starter template)：未明確標示
- PageRank：27.5%
- 自複製擁有者 (Self-copying owner)：未明確標示
- GitHub 星標：僅 7.0%

對於高風險技能 (high-risk skills)，稽核前 100 個被模型排名的儲存庫可預防 14.9% 的後續採用，而稽核前 100 個最多星標的儲存庫僅能預防 0.5%。差距約 30 倍，這對資安工程師 (security engineers) 的工作流程有直接影響。

**7. 頂級來源的組成（Fig. 2f）**

- 普通專案 (Ordinary project)：66.4%
- 聚合器目錄 (Aggregator catalog)：未明確標示
- 起始模板 (Starter template)：未明確標示
- 自複製擁有者 (Self-copying owner)：未明確標示
- 機器人生成 (Bot-generated)：未明確標示

這項發現挑戰了「主要威脅來自惡意聚合器」的直覺——大多數頂級來源其實是普通專案，這使得威脅識別更加困難。

**8. 網路結構特徵（Fig. 1a）**

- 50 個至少 100 個儲存庫的社群 (communities)
- 64.2% 的儲存庫為孤立節點 (isolates)，即未分享任何技能
- 最大複製深度 (copy depth) 達 12 世代 (generations)

**9. 案例研究：web-design-guidelines（Fig. 1b）**

該技能在 12 個世代的複製中達到 972 個採用者，其中 490 個可歸因於明確的傳播路徑。這顯示即使是單一技能也能形成複雜的傳播鏈，且部分採用無法追溯至明確來源（歸因缺失問題）。

#### 與現有研究的比較

**1. 定位差異**

相較於既有研究多採用「快照」(snapshot) 視角——即在單一時間點記錄哪些儲存庫持有特定技能——本論文的核心創新在於從 Git 歷史紀錄重建「帶日期的複製網路」(dated copy network)，能回答「誰從誰複製」這個關鍵問題。

**2. 與程式碼克隆研究的關聯**

論文引用了 [9]、[10] 等關於複製程式碼 (copied code) 的研究，這些研究同樣發現複製檔案很少被更新或標註來源。本論文將此觀察延伸至代理技能領域，並進一步量化了「修補無法觸及複製」的問題。

**3. 與技能安全研究的互補**

- 既有研究 [3]、[4]、[5]、[6]、[7]、[8] 著重於偵測危險技能本身
- 本論文則著重於「哪些儲存庫值得優先審查」(ranking repositories for review)

兩者形成互補：前者是內容分析，後者是來源定位。

**4. 與套件管理生態的對比**

傳統套件管理器（如 npm、PyPI）透過依賴圖 (dependency graph) 回答溯源、修補觸及範圍 (reach)、稽核目標等問題。代理技能缺乏這樣的基礎設施，本論文試圖從 Git 歷史中重建類似資訊，但承認這是「沒有註冊中心 (without a registry)、沒有版本 (versions)、沒有溯源 (provenance)」的環境下的權宜之計。

**5. 改進與侷限**

**改進：**
- 首次提供帶時間戳記的複製關係
- 量化證明星標無效
- 提供可操作的稽核清單

**侷限：**
- 僅依賴 Git 歷史，無法捕捉透過 GitHub UI 或外部管道進行的複製
- 「多數譜系歸屬」啟發式可能誤判小型複製事件
- 64.2% 的孤立節點與部分無法歸因的採用顯示覆蓋率仍有缺口
- 僅分析 `SKILL.md` 檔案，未涵蓋技能資料夾中的腳本與其他資源
- 模型在時間切分後的預測能力仍受未來生態變化影響

#### 未來研究方向

**1. 平台層面的基礎設施改進**

論文結論明確建議「平台應發布版本化參照 (versioned references) 而非複製 (rather than copies)」，這指向幾個具體方向：
- 設計類似 `package.json` 的技能宣告格式
- 建立技能註冊中心 (skill registry)，記錄版本與依賴
- 開發支援自動修補傳遞的技能安裝工具

**2. 動態監控與早期預警**

目前模型是基於歷史資料的靜態排名，未來可發展：
- 即時監控新技能的傳播速度
- 預測哪些新興技能可能成為高風險
- 自動化稽核工作流程整合

**3. 修補傳遞機制研究**

論文發現「修補在來源處鮮少觸及複製 (rarely reaches them)」，未來可研究：
- 如何設計激勵機制讓複製者同步更新
- 自動偵測過時複製並通知擁有者
- 區塊鏈或簽章機制確保技能完整性

**4. 跨平台擴展**

本研究僅限於 GitHub，未來可延伸至：
- GitLab、Bitbucket 等其他程式碼託管平台
- 私有儲存庫與企業內部生態
- 透過 npm、PyPI 等套件管理器散佈的技能

**5. 技能內容分析與網路分析的結合**

結合內容分析（既有 [4]、[5]、[7] 的危險技能偵測）與網路位置分析（本論文的方法）：
- 識別「高風險內容 × 高傳播位置」的雙重威脅
- 發展內容-網路聯合嵌入 (joint embedding) 模型
- 建立技能風險的綜合評分系統

**6. 經濟與社會因素**

為何 66.4% 的頂級來源是普通專案？未來可探討：
- 開發者複製技能的動機與決策過程
- 技能分享的社會網路結構
- 信任與聲譽機制在技能生態中的角色

**7. 形式化驗證與安全保證**

- 對技能指令進行形式化驗證 (formal verification)
- 開發沙箱機制限制技能的權限 (permissions)
- 設計可證明安全的技能組合語言

**8. 長期生態演化研究**

技能生態僅有十個月的歷史，但發展迅速：
- 追蹤生態從「無序複製」到「結構化依賴」的演變
- 預測何時會出現類似 npm 的中心化註冊中心
- 研究標準化（如 SKILL.md front matter 規範）的採用動態

這些方向不僅能深化學術理解，更能直接影響 AI 程式設計代理生態的安全性與可持續性。

## 論文問答

**Q1：什麼是「代理技能」(agent skills)，為什麼它們會形成一個軟體供應鏈問題？**

A：代理技能（agent skills）是指像 Claude Code、Codex、Cursor 這類 AI 程式設計代理所使用的 SKILL.md 指令檔與腳本，它們會以使用者權限執行，因此能執行 shell 指令、存取網路並修改檔案。開發者透過在儲存庫之間直接複製這些技能來分享，使得技能形成了一個沒有註冊中心、沒有版本、也沒有溯源資訊的軟體供應鏈。這意味著當一個被複製的技能存在漏洞時，我們無法得知它的來源、哪些儲存庫持有副本，以及安全性修補能否觸及這些副本。

**Q2：為什麼現有的單一時間點快照研究方法無法回答技能複製的來源問題？**

A：現有研究通常在某一個時間點記錄哪些儲存庫持有某個技能，但這種快照只能告訴我們「誰擁有這個技能」，無法揭示「誰先採用」、「誰從誰那裡複製」以及「何時發生」。由於技能是透過複製而非套件管理器傳遞，這些動態的傳播關係在快照中完全消失。為了回答供應鏈問題，我們需要的是帶有時間戳記且有方向性的複製網路，而這正是本論文從 Git 歷史中重建的對象。

**Q3：為什麼這個供應鏈問題對資安特別重要？**

A：因為代理技能會在使用者權限下執行 shell 指令、存取網路並修改檔案，一個含有惡意程式碼的高風險技能一旦被複製到許多儲存庫，就可能在不知情的情況下被大量使用者執行。本論文發現技能副本幾乎不會隨著來源更新，這代表在來源端做的安全性修補很少能觸及既有的副本，使得漏洞或後門可能長期存在於供應鏈中。此外，由於沒有溯源機制，資安團隊很難判斷哪些儲存庫最值得優先審查。

**Q4：這篇論文如何從 Git 歷史重建帶日期的複製網路？**

A：作者使用 GitSkills 資料集（2026 年 7 月發布於 Zenodo），保留所有命名為 SKILL.md 且具有有效 front matter 的檔案，首次提交日期在 2025 年 10 月 1 日之後，且所在儲存庫不是 fork。對於每個 SKILL.md 路徑，他們從預設分支的 clone 中收集完整的 Git 歷史，並以首次提交日期作為採用日期，下限為儲存庫的建立日期（因為 fork 與鏡像會帶有較舊的歷史）。接著他們定義「譜系」(lineage) 來串連同一個技能經由編輯連結的版本，並透過「複製事件」(copy event) 的規則——單一提交新增 10 個以上 SKILL.md 檔案，且單一既有採用者持有至少一半的既有譜系——來判定來源儲存庫。

**Q5：「技能星座」(skill constellations) 這個概念的核心創新是什麼？**

A：「技能星座」指的是單一技能的所有副本所形成的複製網路，這個比喻凸顯了從快照只能看到節點、而從歷史才能看到節點之間的邊。這個概念的核心創新在於把「採用」與「傳播」區分開來：快照研究只能告訴我們哪些儲存庫在某個時間點持有技能，而星座則揭示了哪些儲存庫是首位的採用者、哪些是後續透過複製傳播的採用者，以及傳播的世代深度（本研究觀察到最大複製深度達 12 個世代）。這個框架讓我們能夠回答「誰從誰那裡複製」這個供應鏈中最關鍵的問題。

**Q6：為什麼作者選擇用「複製出度」(copy out-degree) 來排序儲存庫，而不是其他指標？**

A：作者選擇複製出度是因為它直接衡量一個儲存庫被其他儲存庫複製的頻率，這正是供應鏈中「影響力」的真正指標——一個被大量複製的儲存庫，其技能的變更會影響最多下游使用者。相比之下，GitHub 星標衡量的是社會關注度而非供應鏈中的傳播角色，本論文發現星標與帶日期的出度之間的相關性極弱（Kendall τ = −0.10），且星標無法識別未來的主要來源。複製出度在預測後續傳播方面捕獲了 27.8% 的傳播量，而星標僅捕獲 7.0%，證明了基於網路位置的指標遠優於基於流行度的指標。

**Q7：這篇論文的主要資料集規模和覆蓋範圍為何？**

A：本論文使用 GitSkills 資料集（2026 年 7 月發布於 Zenodo），涵蓋 259,596 個儲存庫中的 1,612,846 個不同技能，其中半數的 SKILL.md 檔案是另一個檔案的逐字複製。從這些資料中，作者重建了涵蓋 2,193,119 次技能採用的帶日期複製網路，並提供了互動式檢視器供探索。在這個網路中，64.2% 的儲存庫是孤立節點（不與其他儲存庫共享技能），最大複製深度達 12 個世代，並識別出至少 100 個儲存庫組成的 50 個社群。

**Q8：關鍵實驗結果中，複製出度與 GitHub 星標在預測未來來源上的表現差異為何？**

A：在時間切分驗證中，作者比較了不同指標在預測未來傳播方面的表現，結果顯示複製出度捕獲了 27.8% 的後續傳播，而 GitHub 星標僅捕獲 7.0%，差距接近四倍。更令人警覺的是，後視基準（hindsight bound，能事先知道未來的最佳表現）僅為 43.8%，這意味著複製出度已經達到了理論上限的 63% 左右，而星標只達到 16%。此外，作者發現大多數未獲星標的頂級來源其實是普通專案（佔 66.4%），這進一步說明了為何僅憑流行度無法識別供應鏈中的關鍵節點。

**Q9：對於高風險技能的稽核建議，模型排名與星標排名的效果差距有多大？**

A：作者擬合了一個模型來預測哪些儲存庫會被其他儲存庫複製，並用它來對儲存庫進行稽核排序。實驗結果顯示，審查模型排名最高的 100 個儲存庫可以預防 14.9% 的高風險技能後續採用，而審查星標最多的 100 個儲存庫僅能預防 0.5%，差距高達約 30 倍。這個結果對資安工程師來說意義重大，因為它提供了一份簡短而有效的清單，讓他們能在技能擴散到大量下游儲存庫之前進行檢查，大幅提升資安資源的配置效率。

**Q10：這篇論文的研究結果對資安工程師的日常工作有何實際意義？**

A：本論文為資安工程師提供了一套可操作的稽核優先順序方法：與其盲目審查星標最多的儲存庫（效果僅 0.5%），不如根據複製網路中的位置來識別關鍵節點（效果達 14.9%）。這份「前 100 名」清單可以在技能擴散到大量下游儲存庫之前進行檢查，大幅提升資安資源的配置效率。此外，了解技能副本幾乎不會隨來源更新這一事實，提醒資安團隊不能僅依賴來源端的修補，還必須主動審查下游副本。

**Q11：平台方應該如何根據這篇論文的發現改進技能發布機制？**

A：作者明確建議平台應該發布「版本化參照」(versioned references) 而非「複製」(copies)，這能從根本上解決供應鏈問題。如果技能透過類似套件管理器的參照機制傳遞，每個副本就能自動綁定到特定版本，當來源端發布安全性修補時，所有下游副本都能立即收到更新。這也意味著平台需要建立某種形式的註冊中心或索引系統，記錄每個技能的版本、來源與採用情況，讓資安團隊能夠追蹤修補的觸及範圍。

**Q12：這篇論文對「挖掘軟體儲存庫」(MSR) 領域的更廣泛影響是什麼？**

A：本論文展示了如何從 Git 歷史中重建帶日期的程式碼傳播網路，這個方法論可以應用於其他類似的「無註冊中心複製」現象，例如設定檔、CI/CD 腳本、容器映像檔等。它也提醒 MSR 社群：單一時間點的快照研究在回答「誰從誰那裡複製」這類動態問題時有根本性的限制，必須結合歷史資料才能完整描繪軟體生態系的演變。此外，論文提出的「複製出度」等基於網路位置的指標，可能比傳統的流行度指標更能反映程式碼在生態系中的實際影響力。

**Q13：這篇論文承認哪些方法論上的限制？**

A：本研究仰賴 GitSkills 資料集，僅涵蓋 2025 年 10 月 1 日之後首次提交的 SKILL.md 檔案，因此無法追溯更早期的技能傳播歷史。此外，作者排除了位於 fork 儲存庫中的技能，這可能會遺漏一些透過 fork 機制傳播的副本。複製事件的判定規則（單一提交新增 10 個以上 SKILL.md 檔案，且單一既有採用者持有至少一半的既有譜系）雖然合理，但可能無法捕捉所有小規模的複製行為。最後，雖然作者用時間切分驗證了模型，但他們承認後視基準僅 43.8%，意味著仍有大量傳播無法被現有特徵解釋。

**Q14：在哪些情況下這個方法可能會失敗或產生誤判？**

A：當技能的複製是透過非 Git 機制（例如直接從網站下載並貼上）進行時，這個方法無法追蹤，因為 Git 歷史中不會留下複製痕跡。當開發者大幅修改技能內容後再採用，系統可能無法辨識這是同一個技能的變體，從而中斷譜系的連結。此外，對於刻意混淆來源（例如透過多層中間儲存庫轉發）的對抗性行為，簡單的複製事件偵測可能會被規避。最後，模型排名假設「被大量複製的儲存庫更值得審查」，但這忽略了某些低複製次數但內容極為危險的「長尾」技能。

**Q15：未來的研究方向有哪些？**

A：作者在結論中暗示了幾個值得探索的方向：首先是將版本化參照機制實際部署到平台中，並評估其對供應鏈安全的實際效果；其次是研究如何自動化偵測技能副本中的惡意修改，特別是那些繞過簡單相似度比對的對抗性變更；第三是將這個方法擴展到其他 AI 代理生態系（例如不同的 SKILL.md 變體或新興的代理框架）；最後是結合動態分析（實際執行技能並觀察其行為）來補充靜態的 Git 歷史分析，以更全面地評估技能風險。

## 實務應用指南

### 適用場景

1. **企業內部 AI 程式設計代理技能治理**：大型企業部署 Claude Code、Codex 或 Cursor 給工程團隊時，可利用本研究的複製網路方法，盤點內部 GitHub Enterprise 上所有 SKILL.md 檔案的來源與傳播路徑，識別哪些團隊的儲存庫是技能的「上游來源」，並建立內部技能白名單與黑名單機制。

2. **開源專案維護者的技能擴散監控**：當開發者將一個 AI 技能（例如網頁設計指南、瀏覽器自動化腳本）放入自己的開源專案，可使用本研究的時間序列分析追蹤該技能在 GitHub 上的複製級聯（copy cascade），了解技能在多少世代、幾天內擴散到多少儲存庫，並在發現異常快速擴散時提早介入。

3. **資安團隊的高風險技能稽核**：CISO 辦公室或紅隊可採用本研究的「複製出度」（copy out-degree）排名模型，取代傳統 GitHub 星標排名，找出真正會被大量複製的「超級來源」儲存庫，集中稽核資源在這 100 個關鍵節點上，可在技能擴散前阻擋 14.9% 的高風險技能採用。

4. **AI 程式設計代理平台供應商的供應鏈設計**：Anthropic、OpenAI 等平台可參考本研究的結論，將目前的「整份複製」機制改為「版本化參照」（versioned references）機制，例如類似 npm 或 pip 的依賴宣告，讓安全性修補能從源頭自動傳遞到所有下游副本。

5. **學術研究中的軟體供應鏈分析**：MSR（挖掘軟體儲存庫）領域的研究者可將本研究的「帶日期複製網路」方法論，應用於其他缺乏套件管理基礎設施的生態系（如 Jupyter notebook、VS Code extension、GitHub Actions），研究程式碼克隆的傳播動力學。

**技能門檻**
- 熟悉 Git 內部物件模型（blob、tree、commit）以理解內容定址雜湊。
- 具備 MSR（mining software repositories）基礎，能處理 fork、mirror 與歷史重寫。
- 了解圖論基本概念（出度、入度、PageRank、傳染病模型）。
- 具備時間序列切分（temporal split）與模型評估經驗，避免資料洩漏。

### 實作步驟建議

**步驟一：建立 SKILL.md 候選集**
從 GitSkills 篩選檔名完全為 `SKILL.md` 且 front matter 有效的檔案，過濾掉 fork 與 mirror 儲存庫，僅保留首次提交日期 ≥ 2025 年 10 月 1 日的紀錄。

**步驟二：重建譜系（lineage）**
對每個獨立技能內容（以內容雜湊區分），串接其所有版本編輯歷史，形成一棵譜系樹；首個採用的儲存庫即為該技能的「起源」。

**步驟三：偵測複製事件（copy event）**
定義複製事件為「單一提交新增 ≥ 10 個 SKILL.md 檔案，且其中至少一半的既有譜系來自同一個先前的採用者」。該先前的採用者即為複製的「來源」。小於 100 個檔案視為「bundle」，其餘視為「bulk」。

**步驟四：建構帶日期的複製網路**
將每筆複製事件記錄為一條有向邊（來源 → 目標，附時間戳），累積形成跨技能的儲存庫網路與單一技能的星座（constellation）。

**步驟五：擬合來源選擇模型**
以負二項迴歸或 Poisson 模型擬合「哪些儲存庫會被其他儲存庫複製」，特徵可包含：歷史出度、PageRank、技能類型、是否為彙整型目錄（aggregator catalog）、是否為起始模板（starter template）等。

**步驟六：時間切分驗證**
在 2026 年 4 月 1 日做時間切分，僅用切分前的資料訓練模型，評估模型對切分後「後續傳播」的預測能力；計算「後續採用捕獲率」（later transmissions captured %）。

**步驟七：產出稽核清單**
依模型輸出排序儲存庫，輸出前 100 名作為資安團隊的稽核短名單；同時輸出每個技能的「複製級聯視覺化」供調查使用。

**步驟八：部署互動式檢視器**
將結果發布為類似 `fahdseddik.github.io/Skill-Constellations/` 的網頁，提供儲存庫篩選、技能搜尋、級聯時間軸播放功能。

### 潛在風險與注意事項

**風險一：歷史重寫與 git 雜湊不可靠**
攻擊者可透過 force push 竄改 git 歷史，使複製關係無法重建。**緩解**：結合 GitHub Events API、Issues 時間戳與 commit 簽章作為交叉驗證；對高風險儲存庫要求 immutable 歷史。

**風險二：fork 與 mirror 造成假陽性**
fork 會繼承上游歷史，可能被誤判為「複製」。**緩解**：在資料前處理階段明確排除 fork（GitHub API 提供 `fork: false` 過濾），並對 mirror 儲存庫加上白名單/黑名單。

**風險三：模型過擬合於歷史熱門技能**
若訓練資料偏向早期流行的技能類型（如網頁設計），模型可能低估新興類型（如生物資訊）。**緩解**：採用滾動時間切分（rolling temporal split），並定期以人工標註的新技能做校準。

**風險四：誤判合法彙整者為攻擊來源**
許多「頂級來源」其實是彙整型目錄（如 awesome-* 系列），並非惡意。**緩解**：在排名中加入「類型標註」（aggregator catalog、starter template、bot-generated 等），讓稽核人員能區分。

**風險五：稽核清單的隱私與法律風險**
對企業內部儲存庫進行排名可能涉及機密資訊外洩。**緩解**：在內部部署版本中對儲存庫名稱做雜湊處理，僅顯示分類與風險分數。

**風險六：技能內容變更難以追蹤**
本研究發現副本「幾乎不會隨來源更新」，但若副本確實修改，內容雜湊會改變，譜系可能斷裂。**緩解**：除內容雜湊外，加入結構相似度（如 AST 相似度、嵌入向量距離）作為輔助特徵。

### 與其他技術的整合建議

**與套件管理系統整合**
借鏡 npm、pip、Cargo 的設計，將 SKILL.md 改為 `skill.yaml` 加上版本號與來源 URL，讓代理在執行前能解析依賴圖。可參考 [GitHub Dependency Graph API](https://docs.github.com/en/code-security/supply-chain-security/understanding-the-dependency-graph) 的 SBOM 概念，產出「技能物料清單」（Skill BOM）。

**與 SIEM/SOAR 整合**
將「複製出度排名」與「高風險技能清單」匯入 Splunk、Elastic 或 Sentinel 等 SIEM，設定規則：當新提交的 SKILL.md 內容與已知惡意技能相似度超過閾值時，自動觸發 SOAR 劇本（隔離儲存庫、通知 owner）。

**與程式碼掃描工具整合**
在 Semgrep、CodeQL 或 Snyk 的規則集中，新增針對 SKILL.md front matter 的檢查（例如偵測 `permissions: full`、`network: unrestricted` 等危險設定），並與本研究的複製網路交叉比對，找出「高風險技能被大量複製」的即時警報。

**與 AI 代理執行環境整合**
在 Claude Code、Codex 的執行沙箱中，引入「技能來源白名單」機制：代理僅執行來自已稽核儲存庫的技能；對未在白名單的技能，要求使用者明確確認。可參考瀏覽器的 HSTS preload list 設計。

**與威脅情資平台整合**
將本研究的「頂級來源儲存庫清單」與 MITRE ATT&CK、MISP 等情資平台同步，讓資安團隊能將技能供應鏈風險納入整體威脅模型。

**與學術資料集整合**
將重建的帶日期複製網路釋出為開放資料（如同論文的 GitSkills 釋出），供後續研究重現與延伸，例如研究「技能生命週期」、「技能突現」（emergence）與「技能滅絕」。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，理解「技能星座」這個核心比喻——就像夜空中的星座由星星組成，技能網路由儲存庫組成，而「複製關係」就是連接它們的線。重點掌握「為什麼沒有註冊中心會造成安全問題」這個直覺，不必急於理解負二項模型的數學細節。

**給 AI 工程師**：聚焦在第二節「資料與方法」與圖 2 的六個子圖，特別是 (d) 圖揭示的「星標與出度幾乎無關」這個反直覺發現。在自己的代理執行環境中實作「技能來源白名單」與「版本化參照」機制，並思考如何將本研究的稽核排名整合進 CI/CD 流程。

**給研究者**：仔細閱讀方法論中的「複製事件偵測規則」（≥10 個檔案、≥50% 既有譜系來自同一來源），並思考如何將此方法遷移至 Jupyter notebook、VS Code extension 或 Docker image 等其他缺乏套件管理基礎設施的生態系。負二項模型的過度離散參數 k = 0.086 是值得深入探討的統計現象。

**給產品經理**：核心訊息是「星標不是風險指標，網路位置才是」。當規劃 AI 代理平台的市集功能時，應將「來源稽核」與「版本化依賴」列為第一優先級功能，而非追求「最多星標的技能」這類表面指標。圖 2(e) 的 14.9% vs 0.5% 對比是向高層爭取資安預算時最有說服力的數字。
