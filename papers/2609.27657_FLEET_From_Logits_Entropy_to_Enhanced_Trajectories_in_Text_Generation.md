## 摘要翻譯

基於大型語言模型（Large Language Model, LLM）的解決方案通常仰賴溫度取樣（temperature sampling），透過聚合完成分佈（completion distribution）中的多個樣本以提升準確率（accuracy）與穩定性（stability）。然而，這種無記憶方法（memoryless approach）本質上是次優的：由於它無法掌握先前生成（prior generation）及其評估（evaluation）結果，隨著取樣數量增加，會產生越來越高比例的語義重複（semantic duplicate）答案，導致報酬遞減（diminishing returns）。為了解決此一限制，本研究提出 FLEET，一種將記憶機制（memory mechanism）整合至生成過程（generation process）中的新方法。FLEET 將每次生成表示為一條稀疏軌跡（sparse trajectory），軌跡所經過的狀態（state）其熵（entropy）均超過預先定義的熵閾值（entropy threshold），並利用這些軌跡推導逐詞元效用分數（per-token utility score）以調整 logits（對數機率）。基準評估（benchmark evaluation）顯示，FLEET 在維持與重複取樣基線（repeated sampling baseline）相同準確率的前提下，達到 3 倍加速比（speedup），並在相同預算下顯著提升複雜程式設計任務（complex coding task）的準確率（LiveCodeBench Pass@32 從 59.9% 提升至 66.2%）。此外，在本研究所評估的貪婪解碼（greedy decoding）設定下，此方法是確定性（deterministic）的，且僅需單一校準回合（calibration pass）即可推導其主要超參數（hyperparameter），對現有大型語言模型流程（LLM pipeline）僅需進行最小程度的修改。

### 核心貢獻（3～5點）
- 提出 FLEET，將記憶機制（memory mechanism）融入自迴歸文本生成，以解決傳統溫度取樣重複取樣所造成的語義重複與報酬遞減問題。
- 將每次生成建模為由高熵狀態構成的稀疏軌跡（sparse trajectory），並據此推導逐詞元效用分數（per-token utility score）以動態調整 logits。
- 在維持與重複取樣基線相同準確率的前提下達到 3 倍加速比（speedup），並在相同預算內顯著提升複雜程式設計任務表現（LiveCodeBench Pass@32 從 59.9% 提升至 66.2%）。
- 於貪婪解碼（greedy decoding）設定下具確定性（deterministic），僅需單一校準回合（calibration pass）即可決定主要超參數（hyperparameter），易於整合至現有 LLM 流程。

### 適合對象
對大型語言模型推論效率、測試時擴展、自迴歸生成與程式設計任務有興趣的研究者與工程師；特別適合希望在不增加推理預算的前提下提升生成品質與穩定性，或想將記憶機制整合進現有 LLM 流程的開發者。

## 深度分析

#### 方法論解析

FLEET（From Logits Entropy to Enhanced Trajectories）將文本生成重新框架為一個具有記憶（memory）的序列決策問題。傳統的自迴歸解碼（autoregressive decoding）在每一個時間步僅依據當前的 logits（對數機率）與條件機率（conditional probability）選擇下一個詞元（token），這種無記憶方法（memoryless approach）無法利用先前生成（prior generation）與其評估（evaluation）所獲得的資訊。FLEET 的核心貢獻在於引入一個輕量級的記憶機制（memory mechanism），將過去軌跡的效用回饋到未來的生成過程中。

具體而言，FLEET 將每一條完成軌跡（completion trajectory）表示為一條稀疏軌跡（sparse trajectory），僅保留那些熵（entropy）超過預設熵閥值（entropy threshold）的狀態（state）。這樣的設計基於一個觀察：在大多數自迴歸步驟中，模型面對的是低熵的語法或結構性選擇（例如標點、功能詞、確定性的程式碼語法），這些步驟並不需要額外的隨機探索；真正關鍵的是少數高熵的分岔點（branching points），在這些狀態下選擇不同的詞元可能導致截然不同的最終結果。透過只對高熵狀態建立軌跡，FLEET 將探索（exploration）限制在語義上具有決定性的位置，從而避免溫度取樣（temperature sampling）那種均勻注入雜訊所造成的穩定性下降。

為了避免重複生成語義重複（semantic duplicate）的軌跡並保留狀態的效用歷史，作者提出 VectorDSU（Vector Disjoint Set Union）。這是一種線上資料結構，能夠將隱藏狀態（hidden state）映射到統一的搜尋狀態（unified search state）。從概念上可將其理解為在隱藏狀態空間中進行動態的等價合併：當不同生成前綴到達語義上相似的狀態時，VectorDSU 將它們歸入同一搜尋狀態，從而讓後續軌跡能夠繼承先前軌跡在該狀態累積的效用分數（utility score）。這解決了傳統重複取樣（repeated sampling）中「記憶遺失」的問題——每次取樣都從頭開始，無法區分已經探索過的無效分支與仍有潛力的分支。

在獲得軌跡與狀態對應關係後，FLEET 推導逐詞元效用分數（per-token utility score），並用其調整 logits。這一過程可視為一種輕量的信用分配（credit assignment）：對於可驗證任務（verifiable tasks），當一條完成軌跡被評估為正確或獲得某種獎勵（reward）時，該獎勵會沿著稀疏軌跡上的高熵狀態反向傳播，更新相關詞元的效用。隨後的生成步驟將這些效用分數加到原始 logits 上，使得模型傾向於選擇過去導致成功結果的分支，同時在尚未充分探索的高熵狀態保留探索壓力。這種「利用過去成功經驗、引導未來軌跡」的機制，使 FLEET 在貪婪解碼（greedy decoding）設定下也能運作，並且是確定性（deterministic）的。

此外，作者強調 FLEET 在評估的貪婪配置中僅需單一校準回合（calibration pass）即可導出主要超參數（hyperparameter），對現有 LLM pipeline（大型語言模型流程）的修改極小。這意味著它不像溫度取樣（temperature sampling）、top-k 取樣、top-p（nucleus）取樣或 min-p 取樣那樣需要針對不同任務反覆調整 T、k、p、p_min 等多個參數，從而降低了部署時的參數搜尋負擔。

#### 實驗數據解讀

摘要中報告的實驗結果可從三個層次解讀：

第一，FLEET 在達到與重複取樣基線（repeated sampling baseline）相同準確率（accuracy）的前提下，實現了 3 倍加速比（speedup）。這表示 FLEET 並非單純透過增加樣本數來提升表現，而是透過記憶機制減少了無效的語義重複取樣。傳統溫度取樣隨著樣本數增加，會產生越來越多語義重複的答案，導致報酬遞減（diminishing returns）；FLEET 則因為能夠識別並避開已探索過的低效用分支，使每個額外樣本都帶來更高的邊際資訊價值。3 倍加速比意味著在相同準確率下，FLEET 所需的推論（inference）次數約為基線的三分之一，這對於測試時擴展（test-time scaling）的實際部署具有顯著的計算成本優勢。

第二，在相同預算下，FLEET 在複雜程式設計任務（complex coding task）上顯著提升準確率，LiveCodeBench 的 Pass@32 從 59.9% 提升至 66.2%。這 6.3 個百分點的絕對提升（相對提升約 10.5%）顯示 FLEET 對於需要多步驟推理軌跡（reasoning trajectory）的任務特別有效。程式設計任務通常包含大量分岔點：選擇不同的變數名稱、迴圈結構、函式呼叫或演算法步驟都可能導致最終程式正確與否。傳統溫度取樣在這些分岔點上均勻地增加變異數（sample variance），容易同時破壞語法上穩定的低熵步驟；FLEET 則將隨機性集中在高熵決策點，並透過效用分數強化成功分支，因此在 Pass@32 這類需要多樣性與正確性兼備的指標上表現突出。

第三，貪婪解碼設定下的確定性與單一校準回合降低了方法的不確定性。對於實際應用而言，確定性（deterministic）輸出有助於結果重現與錯誤分析；而單一校準回合則減少了超參數調整所需的額外計算與人工介入。這使得 FLEET 在工程落地層面具備較強的吸引力。

然而，從現有片段中無法判斷實驗涵蓋的模型規模、第二個基準測試（benchmark）的性質、各項指標的標準差或統計顯著性，也無法得知 FLEET 在開放式生成任務（無法自動驗證答案的任務）上的表現。因此，上述解讀主要針對可驗證任務與程式設計任務，推廣到其他領域時仍需更多實證支持。

#### 與現有研究的比較

FLEET 的定位介於傳統取樣策略與更複雜的搜尋或強化學習方法之間，其改進可從以下幾個對比中凸顯：

相較於溫度取樣（temperature sampling）、top-k 取樣、top-p（nucleus）取樣與 min-p 取樣等無記憶的 logits 截斷策略，FLEET 引入了狀態效用歷史與記憶機制。作者在引言中已指出，現有方法至多只能部分緩解「選擇性探索不足」（lack of selective exploration）與「跨任務泛化能力差」（poor cross-task generalization）這兩項限制，但無法解決「樣本效率低下」（sample inefficiency）的根本問題，因為它們無法區分應該探索的狀態與應該利用的狀態。FLEET 透過 VectorDSU 與逐詞元效用分數，將過去完成軌跡的評估資訊內化到生成過程中，從而彌補了這一缺口。

相較於重複取樣結合多數投票（majority voting）或最佳選擇（best-of-N）的後處理方法，FLEET 並非只在生成結束後進行聚合（aggregation）或重新排序，而是在生成過程中持續調整 logits。這使得後續樣本能夠主動避開已知的低效用分支，而不是反覆獨立地從同一分佈中抽樣。因此，FLEET 能在相同預算下達到更高準確率，或以更少樣本達到相同準確率。

相較於需要完整價值模型（value model）或大量計算樹搜尋（tree search）的方法（例如某些基於蒙地卡羅樹搜尋 MCTS 的 LLM 推理系統），FLEET 強調輕量級與最小修改。它不需要額外訓練龐大的價值網路，也不需要在推論時展開完整的搜尋樹；相反地，它僅透過稀疏軌跡與 VectorDSU 在線累積效用，並以貪婪解碼產生確定性輸出。這種設計降低了整合門檻，使其更容易嵌入現有的僅解碼器生成式架構（decoder-only generative architecture）與訓練後對齊流程（post-training alignment pipeline）。

然而，FLEET 也存在若干限制。首先，效用分數的計算依賴於可驗證的完成結果；對於沒有明確正確答案的開放式問答、創意寫作或對話任務，如何設計穩定的效用訊號仍是一個挑戰。其次，VectorDSU 將隱藏狀態映射為統一搜尋狀態的具體準則（例如基於向量相似度、語義嵌入或啟發式規則）在提供的片段中尚未詳細說明，這會影響方法在不同模型與任務間的泛化能力。第三，雖然 FLEET 減少了樣本數，但維護記憶結構與進行狀態合併可能帶來額外的記憶體與計算開銷，這在極長序列或高吞吐量服務中需要實測評估。

#### 可重現性評估

從可重現性（reproducibility）的角度來看，FLEET 具備幾項正面條件：

原始碼與實驗已公開於 GitHub 儲存庫（https://github.com/Alexiush/fleet），這為其他研究者復現演算法、檢查實作細節與進行比較實驗提供了基礎。LiveCodeBench 作為程式能力基準名稱，是公開可取得的資料集，因此相關程式設計任務的實驗結果原則上可以被獨立驗證。

方法在貪婪解碼設定下是確定性（deterministic）的，這消除了隨機種子帶來的變異，有助於結果重現。此外，作者聲稱主要超參數可透過單一校準回合（calibration pass）導出，這減少了重現時的參數搜尋空間，也降低了因參數調整差異而導致結果不一致的風險。

不過，目前提供的片段仍缺少若干關鍵細節，可能影響完全重現：

1. **VectorDSU 的實作細節**：如何定義與比較隱藏狀態的等價性、合併與查詢的時間複雜度、是否使用近似最近鄰或量化技術等，都會影響重現結果與計算開銷。
2. **效用傳播機制**：從完成結果到逐詞元效用分數的具體公式（例如是否使用折扣因子、是否對狀態訪問次數進行正規化、如何處理負向獎勵）尚未揭露。
3. **校準回合的協定**：單一校準回合如何選擇熵閥值（entropy threshold）與其他超參數，需要明確的演算法步驟與資料劃分方式。
4. **模型與硬體資訊**：實驗使用的模型權重（model weights）是否公開、模型規模、推論時的批次大小、GPU 類型等資訊，對於計算加速比與資源估算至關重要。
5. **第二個基準測試**：引言提到在兩個可驗證任務基準上進行評估，但除了 LiveCodeBench 外，另一個基準的名稱與設定未在片段中出現。

總體而言，FLEET 的可重現性條件優於許多僅提供高層概念的方法，但要達到嚴格的獨立重現，仍需等待或索取完整論文中的演算法偽代碼、超參數設定與實驗配置。

#### 未來研究方向

FLEET 的記憶增強範式開啟了多個值得後續探索的研究方向：

1. **擴展至無明確驗證器的開放式生成**：當前方法依賴可驗證任務來計算效用分數。未來可研究如何結合學習式獎勵模型（learned reward model）或 LLM-as-a-judge 的評估方式，將 FLEET 應用於創意寫作、長篇問答與對話系統等開放式文本生成任務。
2. **與先進取樣策略的協同**：FLEET 目前主要在貪婪解碼設定下運作，未來可探索將記憶機制與 top-p（nucleus）取樣、min-p 取樣或自適應溫度調度結合，在保留多樣性的同時進一步提升樣本效率。
3. **自適應熵閥值與動態稀疏化**：熵閥值的選擇可能影響稀疏軌跡的品質。研究如何根據任務難度、模型置信度或序列長度動態調整熵閥值，將有助於提升跨任務泛化能力。
4. **理論收斂與後悔界分析**：對 VectorDSU 與逐詞元效用估計進行形式化分析，探討在何種條件下 FLEET 能夠收斂到最優策略，並給出樣本複雜度或後悔界（regret bound），將為方法提供堅實的理論基礎。
5. **長期代理任務中的信用分配**：在具有稀疏獎勵（sparse reward）的多步驟自主問題解決（multi-step autonomous problem-solving）與代理任務（agentic task）中，如何將最終結果正確歸因於遙遠的早期分岔點，是強化學習與搜尋領域的經典難題。未來可研究更精細的信用分配機制，例如結合優勢估計（advantage estimation）或時序差分學習（temporal-difference learning）。
6. **與推論效率技術的整合**：將 FLEET 與推測解碼（speculative decoding）、KV-cache 共享、批次推論優化等技術結合，可進一步降低記憶機制帶來的額外開銷，使其適用於高吞吐量生產環境。
7. **多模型與多任務記憶共享**：探索 VectorDSU 是否能在不同模型或不同任務之間遷移狀態效用知識，建立跨任務的生成記憶庫，從而實現類似經驗回放（experience replay）的持續學習效果。
8. **安全性與對齊考量**：若效用訊號本身存在偏見或錯誤，記憶機制可能放大並固化這些問題。未來需要研究如何監控與校正記憶中的效用估計，確保 FLEET 在對齊（alignment）與安全性方面的穩健性。

## 論文問答

**Q1：FLEET 主要想解決大型語言模型生成過程中的什麼問題？**

A：FLEET 針對的是自迴歸解碼中「局部錯誤會引發級聯錯誤」的問題，因為只要在關鍵的推理步驟選錯詞元，整條推理軌跡就可能偏離正確答案。傳統的溫度取樣雖然能透過多次採樣來提升準確率，但它是一種無記憶方法，無法記住先前生成過的內容與其評估結果，導致隨著樣本數增加，語義重複的完成軌跡比例越來越高，出現報酬遞減的現象。FLEET 因此引入記憶機制，讓生成過程能根據過往軌跡的效用資訊來動態調整 logits，從而更有效率地探索高價值的推理路徑。

**Q2：為什麼現有的溫度取樣與 logits 截斷策略無法根本解決取樣效率低下的問題？**

A：溫度取樣會均勻地對所有生成步驟注入熵，雖然有時能讓模型選到非最高機率的最優詞元，但同時也會在低熵的穩定步驟上製造不必要的變異，反而降低整體成功率。Top-k、Top-p 與 Min-p 等截斷策略雖然能限制候選詞彙，但它們本質上仍是啟發式規則，缺乏對完成結果獎勵的感知，因此無法區分哪些狀態應該探索、哪些狀態應該利用。這些方法共同的缺陷是無法針對「分支點」進行選擇性探索，使得無效候選詞元持續佔用過多的機率質量。

**Q3：為什麼基於多次取樣的測試時擴展很重要，但它又有哪些結構性限制？**

A：多次取樣被認為是成本效益高且容易取得的測試時擴展手段，幾乎適用於任何僅解碼器生成式架構，並且能對生成軌跡進行細粒度、與任務無關的控制。然而，傳統取樣存在三大結構性限制：樣本效率低、缺乏選擇性探索，以及超參數組合對提示設計、模型架構與任務複雜度過於敏感，跨任務泛化能力差。這些限制使得實務上往往只能依賴領域導向的次優設定，難以發揮取樣策略的真正潛力。

**Q4：FLEET 的核心方法概念是什麼？**

A：FLEET 的核心是將每一次生成表示為一條稀疏軌跡，這條軌跡只保留熵超過預設閾值的狀態，從而聚焦在真正具有決策意義的步驟上。接著，它利用這些軌跡推導出逐詞元效用分數，並用這些分數來調整 logits，引導模型朝著過去被驗證為成功的方向前進。這種記憶增強的確定性搜尋範式取代了傳統無記憶的溫度取樣，使生成過程能夠根據累積經驗進行適應性決策。

**Q5：Vector Disjoint Set Union（VectorDSU）在 FLEET 中扮演什麼關鍵角色？**

A：VectorDSU 是一種線上資料結構，負責將隱藏狀態映射到統一的搜尋狀態，這樣即使不同軌跡在表面詞元序列上不同，只要它們處於語義相似的決策狀態，就會被合併到同一個搜尋狀態中。它能防止軌跡重複，避免記憶機制浪費在已經探索過的相似路徑上，同時保留每個狀態的效用歷史。透過這種設計，FLEET 得以在有限的記憶與計算開銷下，持續累積並利用過去生成的評估資訊。

**Q6：FLEET 在設計上如何確保易於整合與確定性？**

A：在本文評估的貪婪解碼配置中，FLEET 是確定性的，這意味著給定相同輸入就會產生相同輸出，有利於結果重現與除錯。它只需要一次校準回合來推導主要的超參數，減少了傳統溫度取樣與截斷策略所需的大量經驗調參工作。此外，FLEET 對現有大型語言模型流程的修改極小，主要只是在 logits 處理階段加入效用調整與記憶查詢，因此能夠相對容易地整合到現有推論管線中。

**Q7：FLEET 的實驗在哪些基準上進行？**

A：根據摘要與引言，FLEET 在兩個具有可驗證答案的基準上進行評估，其中一個是複雜程式設計任務基準 LiveCodeBench。這類可驗證任務的優點在於能夠明確判斷每條完成軌跡是否正確，從而為記憶機制提供可靠的效用訊號。實驗也與傳統的重複取樣基線進行比較，以衡量在相同計算預算下的效率與準確率表現。

**Q8：FLEET 取得了哪些關鍵量化結果？**

A：FLEET 在達到與重複取樣基線相同準確率的前提下，實現了約 3 倍的加速，顯示它能以更少的樣本獲得同等效果。在 LiveCodeBench 的 Pass@32 指標上，FLEET 將表現從 59.9% 提升到 66.2%，在相同預算下顯著改善了複雜程式設計任務的通過率。這些結果說明，記憶機制不僅能提升取樣效率，還能在高難度、多步驟推理任務上帶來實質的準確率增益。

**Q9：從實驗比較中可以得出什麼洞察？**

A：實驗結果顯示，單純增加樣本數並不能有效解決記憶less 取樣的報酬遞減問題，因為許多新增樣本只是語義重複的軌跡。FLEET 透過記憶與狀態合併，讓每一次生成都建立在過去經驗之上，因此能在較少樣本內覆蓋更多有價值的決策路徑。此外，由於 FLEET 在貪婪解碼配置下是確定性的，它也避免了傳統溫度取樣需要針對不同任務反覆調整溫度、Top-k、Top-p 等超參數的負擔。

**Q10：FLEET 最適合應用在哪些實務場景？**

A：FLEET 特別適合需要多步驟自主問題解決的代理任務，例如複雜程式設計、數學證明或工具使用規劃，因為這些任務中存在大量關鍵分支點，一旦選錯就會導致整體失敗。它也適合計算資源有限、無法負擔大量重複取樣的產品環境，因為它能在相同預算下達到更高效率。此外，對於需要可重現輸出的應用，FLEET 的確定性貪婪配置能提供比隨機溫度取樣更穩定的行為。

**Q11：在產品整合與部署上需要考慮哪些因素？**

A：雖然 FLEET 對現有 LLM 流程的修改很小，但引入 VectorDSU 記憶結構會帶來額外的記憶體與檢索開銷，需要在批次大小與狀態儲存量之間做權衡。由於主要超參數可透過單次校準回合取得，產品團隊可以減少繁瑣的 A/B 調參工作，但仍需針對不同任務驗證熵閾值與效用分數的穩定性。另外，確定性輸出雖然有助於測試與稽核，但在需要創意多樣性的應用中，可能需要進一步評估是否保留部分隨機性。

**Q12：FLEET 可能對測試時擴展領域帶來什麼影響？**

A：FLEET 將測試時擴展的研究焦點從「無記憶地多次取樣」轉向「記憶增強的軌跡搜尋」，為後續研究提供了一個結合生成歷史與驗證回饋的新框架。它示範了如何透過狀態層級的效用估計來直接調整 logits，而不僅是依賴溫度等外部啟發式參數。這種方法可能啟發更多結合獎勵模型、強化學習與解碼策略的研究，進一步縮短下一個詞元預測能力與實際多步驟問題解決成功率之間的差距。

**Q13：FLEET 目前有哪些已承認或隱含的限制？**

A：根據摘要，FLEET 目前主要在貪婪解碼配置下進行評估，這雖然帶來確定性，但也限制了它在需要多樣性探索場景中的適用性。此外，實驗聚焦於可驗證任務，這意味著在缺乏明確正確性訊號的開放式生成任務上，效用分數的推導可能會面臨挑戰。FLEET 也依賴熵閾值與校準程序，若任務的決策結構與校準分佈差異過大，可能需要重新調整這些超參數。

**Q14：FLEET 可能在哪些情況下表現不佳或失敗？**

A：如果 VectorDSU 將語義不同的隱藏狀態錯誤合併，或者將應該區分的分支點視為同一狀態，就可能導致效用分數被錯誤地傳播，進而強化錯誤路徑。在獎勵訊號稀疏或驗證標準模糊的任務中，逐詞元效用分數可能難以穩定估計，使得 logits 調整失去方向。此外，若任務的關鍵分支點並不對應於高熵狀態，FLEET 的稀疏軌跡表示可能會遺漏這些重要決策位置。

**Q15：未來可以朝哪些方向延伸 FLEET？**

A：未來可以將 FLEET 擴展到非貪婪的隨機配置，結合溫度取樣與記憶機制，在保持多樣性的同時避免語義重複。也可以引入更強大的獎勵模型或學習式驗證器，來替代單純的可驗證正確性訊號，使方法適用於更廣泛的開放式任務。此外，進一步從理論上分析 VectorDSU 的收斂性、狀態合併誤差對整體效用的影響，以及多詞元狀態聚合的可能性，都是值得探索的研究方向。

## 實務應用指南

### 適用場景

1. **程式碼自動生成與單元測試驗證**  
   在需要產生多個候選程式並以測試案例驗證的場景（如 LiveCodeBench 類的複雜程式設計任務），FLEET 可減少語義重複的完成軌跡，把採樣預算集中在真正不同的分支上，從而提升 Pass@k。

2. **數學推理與多步驟證明**  
   數學題通常只有少數關鍵詞元決定正確與否。FLEET 的記憶機制能辨識這些高熵分支點，避免反覆落入相同的錯誤推理軌跡，適合需要穩定多步驟自主問題解決的應用。

3. **代理任務規劃與工具使用**  
   代理任務中，模型需要連續選擇動作與工具呼叫。FLEET 的稀疏軌跡與逐詞元效用分數可幫助避免重複動作或迴圈，提升長軌跡的成功率。

4. **創意文案與廣告素材多樣化生成**  
   當產品需要產生大量不同風格但品質穩定的文案時，FLEET 能在維持相關性的同時降低語義重複，改善「採樣越多、重複越高」的報酬遞減問題。

5. **結構化輸出生成（SQL、JSON、表單）**  
   此類任務的低熵部分多為語法或標點，真正需要探索的是欄位選擇或條件結構。FLEET 可將隨機探索限制在高熵決策點，並以貪婪解碼確保輸出確定性與可重現性。

### 實作前置條件

- **資料需求**
  - 可驗證的獎勵訊號：例如單元測試、正確性檢查器、LLM-as-judge 或人工標註。
  - 一份具代表性的校準資料集，用於單次校準回合決定熵閾值與效用分數縮放。
  - 能夠取得模型每個解碼步驟的 logits、隱藏狀態與條件機率分佈。

- **運算需求**
  - 可執行自迴歸推論的 GPU 環境。
  - FLEET 在同預算下可達約 3 倍加速，但需額外記憶體儲存 VectorDSU 狀態與稀疏軌跡，長序列任務需預留緩衝。
  - 貪婪解碼配置為確定性，無需多次採樣的批次運算。

- **技能需求**
  - 熟悉自迴歸解碼、softmax、logits 處理與熵計算。
  - 能修改生成迴圈或實作自訂 logits processor（如 Hugging Face Transformers、vLLM）。
  - 具備基礎資料結構能力（disjoint set、雜湊或狀態聚合）。
  - 能建立端到端評估管線並計算 Pass@k、準確率等指標。

---

### 實作步驟建議

1. **建立可驗證的評估環境**  
   先定義任務專屬的獎勵函數或驗證器，確保每條完成軌跡都能產生二元或連續評估結果。

2. **接入模型 logits 與隱藏狀態**  
   在生成迴圈中攔截每一步的 logits、隱藏狀態與條件機率，計算當前詞元分佈的熵。

3. **實作 VectorDSU**  
   將高熵狀態對應到統一的搜尋狀態，設計狀態等價判斷（如隱藏狀態正規化、區域性雜湊或距離門檻），避免軌跡重複並保留狀態效用歷史。

4. **執行單次校準回合**  
   使用校準資料集，在貪婪解碼配置下決定熵閾值、效用分數縮放係數與其他超參數。此步驟應只需執行一次，除非資料分佈顯著改變。

5. **整合 FLEET logits 調整**  
   根據已觀察軌跡推論逐詞元效用分數，並在 softmax 前將其加入 logits。貪婪配置下直接選取調整後機率最高的詞元。

6. **線上記憶更新**  
   生成過程中持續更新 VectorDSU：當遇到新狀態或新軌跡時，記錄其效用；遇到已見狀態時，讀取歷史效用並調整當前 logits。

7. **評估與迭代**  
   在相同預算下與重複取樣基線比較準確率與延遲。若發現特定任務熵閾值不適用，可回到校準步驟微調，或結合任務分解改善信用分配。

### 潛在風險與注意事項

- **狀態表示的品質**  
  VectorDSU 的效果高度依賴隱藏狀態如何映射為「統一狀態」。若映射過粗，會把不同語義狀態合併；過細則無法發揮去重效果。建議先用小樣本檢查狀態碰撞率與軌跡分群結果。

- **熵閾值的任務敏感性**  
  雖然論文強調單次校準即可，但當提示設計、模型或任務複雜度改變時，原閾值可能失效。應在生產環境持續監控高熵狀態比例與完成多樣性。

- **記憶體與延遲開銷**  
  長序列或大量狀態會使 VectorDSU 膨脹。可考慮只保留近期軌跡、對低效用狀態進行剪枝，或將狀態儲存於 CPU 記憶體並以批次方式更新。

- **確定性與探索的權衡**  
  貪婪解碼配置雖可重現，但若效用分數估計有偏，模型可能過早收斂到次優分支。校準時可保留少量溫度取樣作為對照，確認 FLEET 確實優於純貪婪與純溫度取樣。

- **獎勵稀疏或延遲**  
  若任務只有最終結果能驗證，逐詞元效用分數可能受信用分配雜訊影響。對於這類任務，建議結合中間檢查點或步驟級獎勵，以提升效用估計穩定性。

- **與現有 logits 處理衝突**  
  FLEET 本身會修改 logits，若同時使用 top-k、top-p 或 min-p 截斷，需確認調整順序與 KV-cache 一致性，避免產生非預期的機率分佈。

### 與其他技術的整合建議

- **與驗證器 / 重排序器搭配**  
  使用 FLEET 產生高品質且多樣的候選完成軌跡，再交由單元測試、規則檢查器或獎勵模型進行重排序，可進一步提升最終輸出品質。

- **與推論加速技術結合**  
  FLEET 的貪婪解碼配置可與推測解碼（speculative decoding）或連續批次處理共用，但需確保狀態映射使用的是實際模型的隱藏狀態，而非草稿模型的中間結果。

- **與搜尋演算法整合**  
  VectorDSU 可作為 MCTS、束搜尋（beam search）或最佳優先搜尋中的狀態去重與效用快取，減少重複展開相同節點。

- **與獎勵模型 / RLHF 管線整合**  
  FLEET 的逐詞元效用分數可視為一種輕量 reward shaping，能與現有獎勵模型結合，特別適合沒有完整強化學習基礎設施的團隊。

- **與提示工程 / 思維鏈（Chain-of-Thought）搭配**  
  在已導入 CoT 提示的應用中，FLEET 可進一步減少推理路徑重複，讓模型在關鍵推理步驟進行選擇性探索。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先理解貪婪解碼與溫度取樣的差異，再把 FLEET 想像成「會記住過去生成經驗的貪婪搜尋」。閱讀時可跳過 VectorDSU 的實作細節，重點放在論文的動機、稀疏軌跡的概念以及實驗結果。

- **AI 工程師**  
  請聚焦於 logits 調整機制、熵閾值校準流程，以及 VectorDSU 如何與現有生成框架（如 Hugging Face Transformers、vLLM）整合。建議先以貪婪配置做最小可行實作，再逐步接入生產管線。

- **研究人員**  
  可深入分析逐詞元效用分數的理論基礎、狀態聚合的等價性假設，以及 FLEET 與測試時擴展、MCTS、reward shaping 之間的關聯。未來可探索不同的狀態表示法與更精細的信用分配策略。

- **產品經理**  
  重點關注「同預算下 3 倍加速」與 LiveCodeBench 準確率提升的商業價值。評估產品是否具備可驗證結果與多次採樣需求，並規劃校準資料、評估指標與上線後的監控機制。
