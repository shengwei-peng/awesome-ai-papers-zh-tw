## ⚡ TL;DR

現有代理網路存取模型難以兼顧資訊蒐集與瀏覽器互動，無法支援長時程任務。
本文提出 Web$hell 統一介面，透過共通結構將網頁編譯為可定址物件。
實驗顯示 Web$hell 在六項基準測試中皆達最高效能，且成本更低。

## 摘要翻譯

大型語言模型（LLM）代理正逐漸成為開放網路的直接使用者。隨著它們承擔日益複雜且資訊密集的任務，有效的網路存取正成為代理式問題解決的核心能力。現有方法已透過不同的存取模型推進代理式網路存取，包括搜尋增強代理、瀏覽器式代理，以及近期的檔案系統式代理。然而，由於使用者期望代理能完成長時程、端到端的任務，它們越來越需要在單一軌跡中進行廣泛的資訊蒐集、執行瀏覽器動作，並重新檢視已取得的證據。不過，我們的初步分析顯示，現有的存取模型難以滿足這些需求。它們主要僅支援資訊蒐集或瀏覽器互動其中之一，而整合其能力可能涉及可觀的成本或效能權衡。為此，我們提出 Web$hell，一個在單一存取模型下統一網路存取的介面。透過 WebContract 所定義的共通結構綱要，WebCompiler 將即時網頁編譯為可定址資訊與動作物件。這些物件由 WebCache 維護，並透過一組共享的操作進行處理，為代理提供一致、可操作且持久的網路存取。透過在網路搜尋、網路導航與深度研究基準測試上的大量實驗，我們證明 Web$hell 能以較低的成本達成優異的任務效能。我們的結果進一步顯示介面設計對於有效網路存取的重要性，而 Web$hell 為網路上更具能力且更高效的 LLM 代理開啟了新的可能性。

### 核心貢獻（3～5點）
- 提出 Web$hell 統一介面，將搜尋增強、瀏覽器式與檔案系統式三種存取模型整合於單一存取模型之下。
- 設計 WebContract、WebCompiler、WebCache 三大元件，透過共通結構綱要將即時網頁編譯為可定址資訊與動作物件，並提供一致、可操作且持久的網路存取。
- 透過 WebContract 的統一介面，使代理能在單一軌跡中同時進行資訊蒐集、瀏覽器互動與證據回顧，滿足長時程、端到端任務的需求。
- 在網路搜尋、網路導航與深度研究等多項基準測試中，以較低成本達成優異的任務效能，驗證介面設計對有效網路存取的重要性。

### 適合對象
從事 LLM 代理、代理式系統、網路資訊擷取與人機互動研究的學者與工程師；關注 AI 代理在開放網路上執行複雜任務之能力整合與成本權衡的研究人員；以及對深度研究、自動化資訊蒐集與瀏覽器自動化等應用場景感興趣的業界實務工作者。

## 深度分析

#### 方法論解析

Web$hell 的核心設計理念在於將異質網頁（heterogeneous webpage）轉化為統一、可操作的物件結構，並透過中介層（intermediary）標準化代理與網頁之間的互動模式。整體方法論可拆解為三個相互耦合的核心元件：

**1. WebContract：物件化表示的結構綱要（Schema）**

WebContract 是整個系統的語義基礎，定義了網頁內容如何被抽象為「物件」（object）。每個物件具備三個關鍵屬性：

- **值（value）**：物件承載的具體內容，例如一段文字、一個連結 URL、或一個可執行動作的描述。
- **位址（address）**：每個物件被賦予唯一識別碼，使代理能夠在後續請求中精準指定要檢查的資訊或要執行的動作，這是「可定址資訊」（addressable information）的核心實現。
- **關聯（associations）**：保留物件之間的語意連結，例如某段文字屬於某個區塊、某個按鈕觸發某個動作，這使得代理能理解網頁元素的上下文結構。

此設計的關鍵洞見在於：相較於傳統的純文字表示（clean-text representation）會遺失頁面控制項（page control），或瀏覽器式代理的扁平化頁面觀察（page observation）缺乏結構，WebContract 透過保留物件間的關聯性，使代理既能進行資訊蒐集（information gathering），又能執行網頁互動。

**2. WebCompiler：基於 HTML 語意的確定性編譯**

WebCompiler 負責將即時網頁（live webpage）轉換為符合 WebContract 的結構化表示。值得注意的是，作者採用「確定性規則」（deterministic rules）而非額外的模型推論來完成此轉換，規則源自 HTML 語意本身。這一設計選擇具有兩項重要意涵：

- **效率性**：避免引入額外的 LLM 推論成本，這與先前需要「額外模型推論或大量離線遍歷」（additional model inference or extensive offline traversal）的方法形成對比。
- **可預測性**：相同的 HTML 結構總是產生相同的物件表示，這有助於一致性（consistency）目標的達成。

**3. WebCache：持久化的工作空間**

WebCache 將編譯後的頁面保留在持久化儲存中，使代理能在整個任務軌跡（trajectory）中重複使用已擷取的網頁內容。這解決了傳統瀏覽器式代理需要「重複解讀同一頁面」（repeated webpage interpretation）的成本問題，也避免了檔案系統式代理在選擇性檢查（selective inspection）時遺失頁面控制項上下文的缺陷。

**4. 請求-回應迴圈（Request-Response Loop）**

整體互動模式採用請求-回應機制：代理透過物件位址指定要檢查的資訊或要執行的動作，Web$hell 中介層代為執行並回傳結果。這種設計將「理解網頁」與「執行操作」解耦，使代理能在同一個存取模型下同時支援資訊蒐集與網頁互動，達成「可操作性」（operability）的要求。

#### 實驗數據解讀

論文在六個基準測試（benchmark）上進行了廣泛實驗，涵蓋三類任務：

**1. 任務效能（Task Performance）的全面領先**

Web$hell 在所有六個基準測試上均達到最高的任務效能，橫跨網路搜尋（web search）、網路導航（web navigation）與深度研究（deep research）三個領域。這項結果的意義在於：現有的存取模型通常只能在單一任務類型上表現優異，而 Web$hell 證明了統一介面設計能夠在不犧牲專業能力的前提下達成跨任務泛化。

**2. 成本效益（Cost-Effectiveness）的雙重驗證**

論文強調 Web$hell 在「相當或更低成本」（comparable or lower cost）下達成優異效能。這對應於初步分析中揭示的兩項成本問題：
- 結合搜尋與瀏覽器式存取會因重複網頁解讀而產生大量成本。
- 雖然加入檔案系統式能力（如 grep）能降低成本，但選擇性檢查可能遺失使用頁面控制項所需的上下文。

Web$hell 透過 WebCache 的持久化機制與 WebContract 的結構化表示，同時解決了這兩個問題。

**3. 穩健性（Robustness）分析**

- **對無關內容的穩健性**：實驗顯示 Web$hell 在面對無關內容時仍能維持效能，這得益於物件的關聯結構使代理能聚焦於相關元素，而非被冗餘資訊淹沒。
- **累積文件的效率**：隨著擷取的文件累積，Web$hell 仍維持其效率，這驗證了 WebCache 的設計在長時程任務（long-horizon task）中的可擴展性。

**4. 介面設計的啟示**

分析結果指出，有效的網路介面應「清楚展示網頁元素之間的關聯」（make clear how webpage elements relate to one another）。這些關聯不僅幫助代理蒐集更多證據，也使瀏覽器動作更直觀，並可能引導代理探索已檢查內容之外的區域。

#### 與現有研究的比較

**1. 搜尋增強代理（Search-Augmented Agents）**

此類方法（如 Li et al., 2025a; Jin et al., 2025）透過搜尋 API 與清理後的文字進行操作，優勢在於資訊蒐集效率高，但劣勢在於純文字表示通常省略頁面控制項，導致無法進行網路導航。Web$hell 透過保留物件的關聯結構與動作物件（action object），克服了此限制。

**2. 瀏覽器式代理（Browser-Based Agents）**

此類方法（如 Zhou et al., 2024; Yang et al., 2025）透過頁面觀察引導動作，在網路導航上表現優異，但因觀察內容冗長且嘈雜，在廣泛資訊蒐集上效率較低。Web$hell 的結構化物件表示使代理能精準定位所需資訊，避免被冗餘內容干擾。

**3. 檔案系統式代理（Filesystem-Based Agents）**

此類方法（如 Liu et al., 2026）將網頁存入持久化工作空間，並透過 shell 操作（如 grep、read）進行選擇性檢查。雖然降低了重複讀取成本，但選擇性檢查可能遺失使用頁面控制項所需的上下文。Web$hell 透過 WebContract 的關聯設計，在保留選擇性存取優勢的同時，維持了頁面控制項的可操作性。

**4. 介面設計相關研究**

- **網頁表示簡化**（Yang et al., 2025; Zhang et al., 2026）：透過元素過濾與 DOM 剪枝降低觀察複雜度，但屬於淺層處理。
- **網頁表示增強**（Lee et al., 2025; Kwon & Lee, 2026; Hwang et al., 2026）：將網頁元素組織為區域或摘要，但需要額外模型推論或大量離線遍歷，限制了實用性。
- **WebMCP 與 NLWeb**（Steiner et al., 2026）：將介面設計責任轉移給網站提供者，雖然乾淨但需要網站配合，難以推廣至整個開放網路。

Web$hell 的定位在於：將介面設計的責任置於中介層，透過通用的結構綱要適用於任意網頁，無需網站提供者配合，也不依賴額外的模型推論。

**5. 限制與未解決問題**

- **動態內容處理**：對於高度動態或需要 JavaScript 深度互動的網頁，確定性編譯規則可能無法完整捕捉所有狀態。
- **多模態內容**：目前架構主要針對文字與結構化元素，對於圖像、影片等多模態內容的處理方式未明確說明。
- **安全性與隱私**：持久化快取可能涉及敏感資訊的儲存與處理，需進一步考量。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於 LLM 代理在開放網路上執行任務時所面臨的「存取模型碎片化」問題。隨著代理需要完成越來越複雜且資訊密集的長時程任務，單一存取模型已不足以支撐端到端的工作流程。論文的核心理念是：當代理必須在同一條軌跡中同時進行廣泛資訊蒐集、瀏覽器互動與證據回顧時，現有的搜尋增強、瀏覽器式與檔案系統式等存取模型各自存在明顯的能力缺口，因此需要重新思考如何整合這些能力。

**Q2：為什麼現有的存取模型無法滿足需求？**
A：論文的初步分析指出三個關鍵瓶頸：第一，搜尋增強與檔案系統式代理受限於純文字表示，往往省略頁面控制項，因此在網路導航任務上表現不佳；第二，瀏覽器式代理雖然能處理頁面互動，但因其觀察冗長且充滿雜訊，在廣泛資訊蒐集方面效率低落；第三，雖然結合搜尋與瀏覽器式存取能擴大任務涵蓋範圍，卻會因反覆解讀網頁而產生顯著成本，而加入 grep 等選擇性檢查雖能降低成本，卻可能遺失使用頁面控制項所需的脈絡。

**Q3：為什麼這個問題對代理式網路存取領域很重要？**
A：隨著使用者期待代理能完成端到端的真實任務，單一存取模型已無法對應實際需求。論文中以購物查詢為例，說明一個任務可能同時需要產品探索、分頁導覽尋找評論，以及保留資訊以供後續比較，這正是現有模型各自擅長卻難以整合的情境。因此，建立一個能同時支援可操作性、一致性與持久性的統一介面，已成為推動代理式網路存取發展的關鍵基礎建設。

**Q4：Web$hell 的核心方法是什麼？**
A：Web$hell 提出一個統一介面，將所有形式的網路存取整合在單一存取模型之下。其架構包含三個關鍵元件：WebContract 定義資訊與動作如何以物件形式呈現並組織成頁面；WebCompiler 依據 HTML 語意以確定性規則將即時網頁編譯為結構化表示；WebCache 則保留編譯後的頁面以供選擇性存取與重複使用。代理透過請求—回應迴圈與 Web$hell 互動，使用物件位址指定要檢查的資訊或要執行的動作。

**Q5：Web$hell 的關鍵創新點為何？**
A：Web$hell 的核心創新在於提供一個中介層，標準化網頁表示與瀏覽器動作，使代理無需協調多個存取模型。每個物件結合了「值」、「位址」與「關聯」，不僅保留自身內容，也保留與其他物件的參考關係，這使得代理能以位址精準指定後續操作，並由介面代為執行。這種設計讓資訊蒐集與網頁互動得以在同一個一致的框架下進行，突破了過去必須在不同模型間切換的限制。

### 實作前置條件

**資料需求**
- 目標網站的即時 HTML 內容（透過 headless 瀏覽器如 Playwright、Selenium 取得）
- 網頁的 accessibility tree 或 DOM 結構，作為 WebCompiler 編譯的輸入
- 預先定義的 WebContract 結構綱要（物件的 value、address、associations 欄位規範）

**運算資源**
- 中等規模 LLM（如 GPT-4 等級）作為代理推理引擎
- 網頁編譯可在 CPU 上以確定性規則執行，無需 GPU
- WebCache 需配置持久化儲存（建議 Redis 或 SQLite），容量依任務規模而定

**技能門檻**
- 熟悉 HTML/DOM 與 accessibility tree 語意
- 具備 LLM agent 框架（如 LangChain、AutoGen、ReAct 風格）的開發經驗
- 理解 request-response 迴圈與物件定址的概念
- 基本的網路爬蟲與瀏覽器自動化知識

### 實作步驟建議

**步驟一：定義 WebContract 結構綱要**
根據目標任務設計物件表示規範。每個物件需包含：
- `value`：物件的內容（如文字、URL、動作描述）
- `address`：唯一識別碼，用於後續定址存取
- `associations`：與其他物件的關聯（如「位於某分頁」、「屬於某區塊」、「執行後導向某頁」）

**步驟二：實作 WebCompiler**
編寫確定性規則將 HTML 轉為結構化物件：
- 從語意標籤（`<nav>`、`<article>`、`<button>`）推斷物件類型
- 為每個可互動元素與資訊區塊產生唯一 address
- 透過 DOM 結構推導 associations（例如父子、兄弟、觸發關係）

**步驟三：建立 WebCache 持久化層**
- 將編譯後的頁面以 address 為索引儲存
- 支援後續請求以 address 直接存取物件，無需重新編譯
- 設計淘汰策略以控制長時程任務的儲存成本

**步驟四：設計共享操作集**
定義代理可呼叫的操作，例如：
- `inspect(address)`：取得特定物件的內容
- `act(address)`：執行特定動作（點擊、輸入、提交）
- `navigate(url)`：載入新頁面並編譯
- `search(query)`：透過搜尋 API 取得結果

**步驟五：整合 LLM Agent 迴圈**
- 將 Web$hell 包裝為工具集，提供給 LLM agent
- 設計 prompt 教導代理使用 address 進行精準存取
- 實作 request-response 迴圈：代理送出操作請求，Web$hell 回傳結果

**步驟六：評估與迭代**
- 在 web search、web navigation、deep research 三類基準測試上驗證
- 監控成本（token 消耗、網頁解讀次數）與任務完成率
- 根據失敗案例調整 WebContract 設計與編譯規則

### 潛在風險與注意事項

**風險一：動態網頁與 JavaScript 渲染**
許多現代網站依賴客戶端渲染，純 HTML 抓取可能遺失內容。
*緩解措施*：使用 headless 瀏覽器等待網路閒置後再抓取；對 SPA 應用監聽關鍵 API 回應。

**風險二：WebCache 膨脹導致儲存成本上升**
長時程任務可能累積大量編譯頁面。
*緩解措施*：實作 LRU 淘汰策略；按任務重要性分級儲存；定期清理已完成任務的快取。

**風險三：address 設計不穩定**
若 address 依賴 DOM 位置，頁面更新後可能失效。
*緩解措施*：優先使用語意穩定的識別符（如 `aria-label`、穩定 class）；設計 address 重解析機制。

**風險四：代理過度信任快取內容**
快取中的網頁可能已過時，影響資訊正確性。
*緩解措施*：為每個快取物件記錄擷取時間戳；對時效性敏感任務強制重新抓取。

**風險五：操作副作用難以復原**
瀏覽器動作（如提交表單、刪除資料）可能產生不可逆影響。
*緩解措施*：在沙盒環境執行；對高風險動作要求代理二次確認；設計操作日誌供回溯。

**風險六：跨網站結構差異大**
不同網站的 DOM 結構差異可能降低 WebCompiler 規則的通用性。
*緩解措施*：以語意標籤與 ARIA 屬性為主要編譯依據；對常見網站類型（電商、新聞、論壇）建立專屬規則集。

### 與其他技術的整合建議

**與搜尋增強生成（RAG）整合**
Web$hell 的 WebCache 可作為 RAG 的外部知識來源。代理在推理時可透過 address 精準引用快取中的網頁片段，無需將整份文件塞入 context window，提升長文任務的效率。

**與既有瀏覽器自動化框架整合**
Web$hell 不取代 Playwright/Selenium，而是建構在其之上。可將 WebCompiler 實作為 Playwright 的頁面處理 middleware，將原始 DOM 轉為結構化物件後再交給代理。

**與 agent 框架整合**
在 LangChain、AutoGen 等框架中，將 Web$hell 註冊為 tool collection。每個操作（inspect、act、navigate、search）對應一個 tool，代理透過 function calling 呼叫。

**與 WebMCP / NLWeb 互補**
WebMCP 與 NLWeb 要求網站提供者主動提供結構化介面；Web$hell 則在客戶端統一處理任意網頁。兩者可並行使用：對支援 WebMCP 的網站優先使用原生介面，對未支援的網站 fallback 至 Web$hell 的編譯流程。

**與監控與可觀測性工具整合**
將 Web$hell 的操作日誌（address 存取記錄、動作執行結果）匯出至 OpenTelemetry 或 LangSmith，供後續分析代理行為與除錯。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「為什麼 LLM agent 需要專門的網路存取介面」這個問題。閱讀時聚焦在第 1 節的初步分析，了解現有存取模型（搜尋式、瀏覽器式、檔案系統式）各自的瓶頸；接著理解 Web$hell 提出的三個需求——可操作性、一致性、持久性——背後的動機。技術細節可先略過，掌握概念後再深入。

**給 AI 工程師**：重點放在第 3 節以後的系統設計。仔細研讀 WebContract 的物件結構（value、address、associations）如何對應到實際的網頁元素；理解 WebCompiler 如何用確定性規則取代模型推論，這對降低延遲與成本至關重要。建議動手實作一個最小可行版本，在小型基準測試上驗證概念，再逐步擴展到真實網站。

**給研究者**：本文的核心貢獻在於「介面設計」對代理效能的影響，這是相對未被充分探索的方向。建議從初步分析的實驗設計切入，理解作者如何拆解「搜尋 vs. 導航」的能力差距；再延伸思考：統一介面的設計原則是否能推廣到其他領域（如行動裝置、桌面應用、IoT）？WebContract 的 associations 設計是否能與知識圖譜、本體論結合？

**給產品經理**：本文展示了一個關鍵洞察——代理的瓶頸往往不在模型能力，而在於「如何讓模型有效使用工具」。Web$hell 透過統一介面同時提升效能與降低成本，這對產品化至關重要。評估導入價值時，可關注三個指標：任務完成率、單次任務成本（token 與時間）、長時程任務的可執行性。建議先在內部知識管理或客戶支援場景試點，驗證後再擴展至對外服務。
