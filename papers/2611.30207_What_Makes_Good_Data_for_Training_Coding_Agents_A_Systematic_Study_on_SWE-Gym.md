## 深度分析

#### 方法論解析

本論文的核心方法論圍繞「獎勵標籤正確性」這個被既有研究忽略的維度展開，提出了一套結合 LLM 評判與執行驗證的雙階段審核流程，用以系統性地檢驗 SWE-Gym 任務集中隱藏測試的標籤品質。

**第一階段：斷言級審核（Assertion-Level Audit）**

作者採用 Claude Opus 5.5 與 GPT-6.1 Sol 兩個 LLM 家族作為評判者（LLM judge），對每個任務的每一條「失敗轉通過斷言」（fail-to-pass assertion）進行獨立審查。評判的對象是斷言本身與對應議題（issue）之間的語意對齊程度——即該斷言是否真正反映議題所描述的修復需求。這種細粒度審核不同於既有方法（如 PAIChecker 或 LLM-as-a-judge 框架）僅對整個任務做粗粒度標註，而是將審核粒度下沉到單一斷言層級，使錯誤定位更為精準。

**第二階段：執行驗證（Execution-Backed Verification）**

僅有 LLM 評判的「疑似錯誤」（suspected error）並不足以構成真實錯誤。作者引入嚴格的執行驗證機制：對於疑似偽陰性（FN），必須實際執行一個遵循議題描述的替代修補（alternative fix），若該修補被測試拒絕，才確認為真實 FN；對於疑似偽陽性（FP），必須構造並執行一個反例（counter-example），若該反例通過原始測試，才確認為真實 FP。這種「執行支援的測量」（execution-backed measurement）大幅降低了 LLM 評判的假陽性率，確保審核結論具有可重現的實證基礎。

**第三階段：任務修復與訓練集構建**

對於確認為 FN-flawed 的任務，作者採取兩種處理策略：(1) 將缺失的需求補充進議題描述，使測試與議題對齊；(2) 若無法修復則直接移除。最終保留的 1,087 個任務構成 SWE-Gym-Verified。在此基礎上，作者構建四個難度匹配（matched difficulty）、規模相等（equal size，各 512 個任務）的訓練集：
- **Orig**：原始 SWE-Gym 任務
- **Clean**：審核後的任務
- **Clean+FP**：在 Clean 基礎上加入針對 FP 的新測試
- **Orig+Filter**：對 Orig 施加通過率過濾，移除從未被解決的任務

**第四階段：控制變數的 RL 訓練與評估**

使用 GRPO（Group Relative Policy Optimization）對 9B 基礎模型進行訓練，並在 SWE-bench Verified 與 SWE-bench Pro 兩個保留測試基準（held-out benchmark）上評估，每個實驗配置跑三個隨機種子以控制隨機性。這種「等量大小、難度匹配」的設計是本研究的關鍵方法論優勢——它隔離了獎勵標籤正確性這個單一變因，避免將資料量或任務難度的差異誤歸因於標籤品質。

**方法論的關鍵洞見**

作者提出一個重要的方法論區分：「通過率」（pass rate）衡量的是任務是否能產生獎勵訊號，而非獎勵是否正確。這一區分挑戰了 RL 配方中常見的「通過率過濾」實踐——僅依據模型能否解決任務來篩選資料，無法辨識標籤錯誤。

#### 實驗數據解讀

**RQ1：標籤錯誤的分佈**

最引人注目的數據是：在原始 SWE-Gym 中，從未被 9B 基礎模型解決的任務中，高達 74% 含有至少一個拒絕正確修補的測試（即 FN-flawed）；相比之下，偶爾被解決的任務中僅有 20% 為 FN-flawed。這一懸殊比例揭示了一個反直覺的現象：「未解決」往往不是模型能力不足，而是標籤本身有誤。這個發現在統計上極具說服力，因為它直接挑戰了 RL 訓練中「難任務即有價值」的預設。

FP 方面，數據顯示錯誤修補約佔所有通過修補的四分之一（19%–36%，視難度而定），且 FP 比例在不同難度區間（以 8 個樣本中通過數 k 衡量）並無顯著差異。這意味著 FP 並非集中在某一類任務，而是普遍存在於各難度層級。

**RQ2：哪些錯誤進入訓練訊號**

GRPO 僅在樣本群組（group of samples）存在獎勵方差時才產生梯度。實驗發現：從未被解決的 FN-flawed 任務幾乎不產生梯度，因此即使移除它們，對訓練訊號的影響微乎其微。然而，偶爾被解決的 FN-flawed 任務貢獻了約五分之一的梯度承載群組（gradient-carrying groups），無論是否施加通過率過濾。這意味著通過率過濾無法消除真正影響訓練的標籤錯誤——它只移除了「無害」的錯誤，卻保留了「有害」的錯誤。

**RQ3：審核後任務的訓練效果**

這是本研究最核心的實驗結果。在等量大小、難度匹配的控制下：
- Clean vs. Orig：在 SWE-bench Verified 上高出 2.4 點，在 SWE-bench Pro 上高出 2.7 點（三個種子的平均）
- Orig+Filter vs. Orig：在兩個基準上的平均分數差異不具統計意義

這組對比極具說服力地證明：(1) 標籤正確性是訓練資料品質的獨立且重要的維度；(2) 通過率過濾無法替代真正的標籤審核，因為它過濾掉的與保留的錯誤類型不同。

**RQ4：對抗 FP 的硬化效果**

Clean+FP 配置加入了能捕捉約四分之一 FP 的新測試。這些新測試使硬化任務的訓練獎勵降低 13 點，但用相同測試重新評分 Clean 的修補時，獎勵也降低相近幅度。最終，保留測試的 pass@1 未產生可偵測的變化。這一結果暗示：在當前 RL 設定下，FP 對最終策略的影響有限，可能因為 GRPO 的群組相對機制對絕對獎勵水準不敏感。

**數據解讀的注意事項**

需注意幾個潛在的混雜因素：(1) 9B 模型規模有限，結論是否能推廣至更大模型尚不明確；(2) 三個種子的統計檢定力有限，2.4/2.7 點的差異雖實務顯著但需更多種子驗證；(3) SWE-bench Verified 與 SWE-bench Pro 雖為獨立基準，但兩者皆源自 GitHub，可能與 SWE-Gym 存在分佈相關性。

#### 與現有研究的比較

**與 SWE-bench 系列基準的關係**

SWE-bench（Jimenez et al., 2024）採用「參考修復通過且原始程式碼失敗」作為任務收錄標準，本論文明確指出此標準僅證明獎勵可達（attainable），無法證明獎勵正確（correct）。SWE-bench Verified（Chowdhury et al., 2024）透過人工篩選移除可能拒絕有效解的任務，但後續審計（OpenAI, 2026b）發現多數模型經常失敗的 Verified 任務仍含有此類測試。SWE-bench Pro（Deng et al., 2026）雖引入人工撰寫的需求，審計估計仍有約 30% 任務存在問題。本論文將這條批評線從「評估基準」延伸至「訓練資料」，填補了文獻空白。

**與其他訓練集的比較**

R2E-Gym、SWE-smith、SWE-rebench 等訓練集均採用與 SWE-Gym 相同的收錄標準，因此本論文的審核方法論與結論對這些資料集具有直接的可推廣性。作者明確指出「代理式管線」（agentic pipelines）跨語言、跨作業系統建構環境，但仍採用相同的測試驗證邏輯，因此標籤錯誤問題是系統性的，而非 SWE-Gym 獨有。

**與 LLM-as-a-Judge 方法的比較**

既有 LLM 評判方法（Oliva et al., 2025; Badertdinov et al., 2025, 2026; Li et al., 2026）將整個任務的議題與測試作為一個整體進行標註。本論文的創新在於：(1) 將審核粒度從任務級下沉至斷言級；(2) 引入執行驗證作為必要條件，而非僅依賴 LLM 的語意判斷。這種「LLM 評判 + 執行驗證」的雙重把關大幅提升了審核的可靠性。

**與 PAIChecker 的比較**

PAIChecker（Wang et al., 2026b）對 SWE-Gym 任務進行拉取請求與議題之間的對齊標註，但未涉及測試本身的正確性。本論文聚焦於測試作為獎勵標籤的正確性，兩者互補而非競爭。

**方法論的侷限性**

(1) 審核依賴 LLM 評判，雖然有執行驗證把關，但仍可能遺漏某些需要深層語意理解的錯誤；(2) 修復策略（補充議題描述）可能引入新的不一致；(3) 9B 模型的實驗結果未必能推廣至更大規模的代理；(4) 僅研究 Python 生態的 GitHub 任務，跨語言泛化性未知。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文探討的是訓練程式碼代理（coding agent）時，訓練資料品質的根本問題——具體而言，是強化學習（RL）任務中獎勵標籤（reward label）的正確性。論文的出發點是：現有的任務集（例如 SWE-Gym）僅透過「參考修復能通過測試、原始程式碼會失敗」這個條件來收錄任務，但這個檢查無法保證所有正確的修補都會被接受，也無法保證只有正確的修補會被接受。換言之，「獎勵是否可達到」與「獎勵是否正確」是兩回事，而後者才是影響訓練策略（training policy）品質的關鍵因素。

**Q2：為什麼現有的方法無法偵測到標籤錯誤？**
A：現有方法存在兩個根本性的盲點。第一，僅檢查參考修復通過測試，並不能驗證測試是否會拒絕其他同樣正確的替代修補，因此無法發現偽陰性（false negative, FN）。第二，僅檢查原始程式碼失敗，也不能驗證測試是否會放行錯誤的修補，因此無法發現偽陽性（false positive, FP）。此外，RL 配方（RL recipe）常用的通過率過濾（pass-rate filter）只會丟掉模型從未解決的任務，卻不會檢查測試本身的正確性；LLM 評判（LLM judge）則是把議題與測試合在一起標記，無法對個別斷言（assertion）做細粒度的審核。這些方法都缺乏「執行支援」（execution-backed）的驗證，因此無法可靠地測量兩種錯誤類型在真實訓練集中的發生率。

**Q3：為什麼這個問題在實務上很重要？**
A：標籤錯誤會直接污染訓練訊號，導致學到的策略次優甚至錯誤。論文的審核結果顯示，在原始 SWE-Gym 中，高達 74% 的「從未被解決」任務含有會拒絕正確修補的測試，而「有時被解決」的任務中也有 20% 含有此類偽陰性。這意味著模型在訓練過程中會反覆收到錯誤的負面獎勵，進而學到錯誤的行為模式。更嚴重的是，偽陽性佔所有通過修補的約四分之一，這代表模型會因為錯誤修補獲得正面獎勵而被誤導。由於這個問題在評測基準中已被廣泛記錄，卻在訓練集中長期被忽視，解決它對提升程式碼代理的可靠性具有關鍵意義。

**Q4：本論文提出的核心方法（審核流程）是什麼？**
A：本論文提出了一套執行支援的審核流程（audit pipeline），用於逐一檢查 SWE-Gym 中每個任務的失敗轉通過斷言（fail-to-pass assertion）。具體而言，Claude Opus 5.5 與 GPT-6.1 Sol 兩個 LLM 家族會針對每個斷言與對應的議題進行評判；只有當測試在執行環境中拒絕了一個遵循議題的替代修補時，被標記的斷言才會被視為真正的偽陰性錯誤。同樣地，一個通過的修補只有在執行反例（counter-example）能揭露其錯誤時，才會被視為偽陽性。這種「執行支援的測量」設計避免了純 LLM 評判可能產生的誤判，使審核結論具有可重現的證據基礎。

**Q5：本論文相較於先前工作的關鍵創新是什麼？**
A：本論文有三項關鍵創新。第一，它首次在真實的 RL 訓練集中對偽陰性與偽陽性兩種錯誤類型進行系統性的執行支援測量，而非僅依賴 LLM 評判或通過率統計。第二，它不僅僅審核資料，還進行了受控的 RL 訓練實驗，比較原始任務、已審核任務、加入反 FP 測試的任務，以及僅通過率過濾的任務，從而隔離出「標籤正確性」對訓練效果的因果影響。第三，它釋出了 SWE-Gym-Verified 資料集（共 1,087 個已審核任務）、每個判定的執行證據、訓練集以及完整的審核流程，為後續研究提供了可重現的基礎設施。

**Q6：本論文在實驗設計上有哪些重要的選擇？**
A：本論文在實驗設計上做了多項嚴格的控制。首先，所有訓練集都控制在 512 個任務的等量大小（equal size），並透過難度匹配（matched difficulty）來隔離標籤正確性這個單一變數的影響。其次，採用 GRPO 演算法搭配 9B 基礎模型（base model）進行訓練，並使用三個隨機種子（seeds）以確保結果的統計穩健性。再者，評測使用 SWE-bench Verified 與 SWE-bench Pro 兩個獨立的保留測試任務（held-out task）集，避免在訓練任務上做循環驗證。這些設計選擇使得 Clean 與 Orig 之間的分數差異能夠被歸因於標籤正確性，而非其他混雜因素。

**Q7：本論文使用了哪些基準進行評測？**
A：本論文使用兩個獨立的保留測試基準來評估訓練後的策略：SWE-bench Verified 與 SWE-bench Pro。SWE-bench Verified 是經過人工篩選、移除可能拒絕有效解的任務後的版本；SWE-bench Pro 的議題則帶有人工撰寫的需求規格。這兩個基準提供了不同特性與難度的評測環境，使結果更具泛化性。此外，訓練資料本身來自 SWE-Gym 的審核版本 SWE-Gym-Verified，這種「訓練—評測」分離的設計避免了資料洩漏與過擬合的風險。

**Q8：本論文最重要的實驗結果是什麼？**
A：本論文最重要的實驗結果是：在等量大小與難度匹配的前提下，使用已審核任務（Clean）訓練的模型在 SWE-bench Verified 上比使用原始任務（Orig）訓練的模型高出 2.4 分，在 SWE-bench Pro 上高出 2.7 分，且這個差異在三個隨機種子上穩定存在。相對地，僅對原始任務套用通過率過濾（Orig+Filter）並未帶來可偵測的提升，這證明了通過率過濾無法取代真正的標籤審核。此外，審核還發現偽陽性佔所有通過修補的約 19% 至 36%，且這個比例在各種難度下都普遍存在，顯示這是一個系統性而非偶發的問題。

**Q9：本論文有哪些重要的消融實驗（ablation study）發現？**
A：本論文最重要的消融實驗是 Clean+FP 條件：在已審核任務中加入新測試以捕捉約四分之一的偽陽性。這些新測試雖然在訓練獎勵上下降了 13 分（顯示它們確實在拒絕錯誤修補），但保留測試的 pass@1 並未產生可偵測的變化。這項消融揭示了一個反直覺的發現：單純強化對偽陽性的懲罰並不會自動轉化為更好的泛化能力，因為新測試對 Clean 自身的修補也施加了類似的獎勵下降。另一項隱含的消融則是 Orig+Filter vs. Orig 的比較，結果顯示僅靠通過率過濾無法替代標籤審核，因為有時被解決的偽陰性任務仍貢獻了約五分之一的帶梯度樣本群組（gradient-carrying group）。

**Q10：本研究的成果可以應用於哪些實際場景？**
A：本研究的成果可直接應用於任何使用 RL 訓練程式碼代理的場景，特別是那些從 GitHub 議題與拉取請求（pull request）挖掘任務的訓練流程。例如，企業內部程式碼助手、開源專案的自動化維護代理、以及競賽式程式設計訓練平台，都能受益於經過審核的訓練資料。此外，這套審核流程也可以應用於其他語言或作業系統的代理訓練環境，因為其核心邏輯（執行支援的斷言檢查）與具體技術棧無關。對學術界而言，釋出的 SWE-Gym-Verified 與審核流程可作為未來研究 RL 訓練資料品質的標準基準。

**Q11：本研究對實際產品開發有哪些考量與啟示？**
A：對產品開發而言，本研究最重要的啟示是：通過率（pass rate）並不能作為訓練資料品質的可靠指標，因為它只告訴我們任務是否能產生獎勵，卻無法告訴我們獎勵是否正確。產品團隊若想提升程式碼代理的表現，應投入資源建立執行支援的審核流程，而非僅依賴通過率過濾或 LLM 評判。此外，論文中「修復或移除」二元決策的設計也提供了實務指引：對於含有偽陰性的任務，可以選擇在議題中補充缺失的需求，或直接從訓練集中移除，這兩種策略都比放任錯誤存在來得好。釋出的審核流程與證據也降低了其他團隊複製此方法的工程門檻。

**Q12：本研究對程式碼代理領域的整體影響是什麼？**
A：本研究對領域的整體影響在於重新定位了「好訓練資料」的定義——從「模型能解決的任務」轉向「獎勵標籤正確的任務」。這個觀念轉變挑戰了 RL 配方中普遍使用的通過率過濾假設，並提供了實證證據支持「標籤正確性比任務可解性更重要」的觀點。同時，論文中偽陽性佔通過修補約四分之一的發現，也提醒研究者：模型在基準上的高分可能部分來自於錯誤修補被接受，這對整個領域的評測文化具有反思意義。透過釋出 SWE-Gym-Verified 與審核流程，本研究也為建立更嚴謹的訓練資料標準奠定了基礎。

**Q13：本論文承認有哪些研究限制？**
A：本論文明確承認其研究範圍僅限於獎勵標籤的正確性，並控制了任務大小與難度這兩個變數，但並未探討其他可能影響訓練資料品質的因素，例如議題描述的清晰度、程式碼庫的代表性、或任務之間的冗餘度。此外，審核流程依賴兩個特定 LLM 家族（Claude Opus 5.5 與 GPT-6.1 Sol）的判斷，這些模型的偏誤可能會影響審核結果。論文的實驗也僅針對 9B 規模的基礎模型與 GRPO 演算法，更大規模的模型或其他 RL 演算法是否會呈現相同的趨勢，仍有待驗證。

**Q14：本研究在哪些情況下可能會失敗或產生誤導？**
A：本研究在以下幾種情況下可能會產生誤導。第一，當任務的偽陽性需要極其複雜的反例才能揭露時，論文中使用的反例生成方法可能無法涵蓋所有情況，導致部分偽陽性被低估。第二，Clean+FP 條件中新增的測試雖然能捕捉約四分之一的偽陽性，但對保留測試分數沒有可偵測的影響，這暗示單純增加測試並非提升泛化能力的有效手段，產品團隊若誤以為「更多測試 = 更好訓練」可能會浪費資源。第三，論文的結論建立在 SWE-Gym 這個特定資料集上，對於其他類型的程式碼任務（例如多檔案重構或跨語言任務）是否適用，仍需進一步驗證。

**Q15：本研究未來可以延伸的方向有哪些？**
A：本研究的未來方向可從多個層面展開。在資料層面，可以將審核流程擴展到其他訓練任務集（如 R2E-Gym、SWE-smith、SWE-rebench），並涵蓋更多程式語言與作業系統環境。在方法層面，可以探索更自動化的反例生成技術，以更全面地揭露偽陽性；也可以研究如何在訓練過程中動態識別並修正錯誤的獎勵訊號，而非僅在訓練前做靜態審核。在理論層面，可以進一步分析偽陰性與偽陽性對 RL 收斂性與泛化能力的數學影響，建立更嚴謹的理論框架。此外，將審核流程與人類專家標註相結合，建立人機協作的品質控制機制，也是值得探索的方向。

## 實務應用指南

### 適用場景

1. **強化學習程式碼代理的訓練資料準備**：團隊在準備以 GRPO、PPO 等強化學習方法訓練程式碼生成代理時，可直接採用 SWE-Gym-Verified 的 1,087 個已審核任務作為訓練集，避免原始 SWE-Gym 中高達 74% 的偽陰性任務污染獎勵訊號。

2. **既有程式碼任務集的品質稽核**：對於已部署的 SWE-Gym、R2E-Gym、SWE-smith、SWE-rebench 等訓練資料集，可套用本論文的審核流程（LLM 評判 + 執行驗證）來識別並修復偽陰性與偽陽性任務，提升資料品質。

3. **企業內部程式碼修復任務集的建構**：企業若從 GitHub issue 與 pull request 挖掘內部程式碼修復任務作為 RL 訓練資料，可採用本論文的雙階段審核方法（斷言級 LLM 評判 + 替代修補執行驗證）來建立可靠的獎勵標籤。

4. **程式碼基準測試的可靠性提升**：對於 SWE-bench Verified、SWE-bench Pro 等評測基準的擴充或客製化版本，可參考本論文的審核方法論來識別「模型常失敗但其實是測試錯誤」的任務。

5. **程式碼代理研究中的消融實驗設計**：研究人員在比較不同訓練資料策略時，可採用本論文的「難度匹配 + 等量大小」控制變項方法，確保資料品質的影響能被乾淨地分離出來。

### 實作前置條件

**資料需求**：
- 一個具備「議題—參考修復—隱藏測試」三元組結構的程式碼任務集（推薦起點為 SWE-Gym 的 2,531 個任務）
- 每個任務需具備可重現的 Docker 執行環境（與論文中 SWE-Gym 的環境配置一致）
- 議題的純文字描述、測試斷言的程式碼內容

**運算資源**：
- 至少一張能跑 9B 參數等級模型的 GPU（如 A100 80GB 或 H100），用於 GRPO 訓練
- 大規模平行任務執行環境（每個任務需執行 8 個樣本以測量通過率）
- LLM 評判 API 呼叫預算（Claude Opus 5.5 與 GPT-6.1 Sol 兩家族交叉驗證）

**技能門檻**：
- 熟悉強化學習訓練流程（GRPO 演算法、獎勵設計、群組採樣）
- 具備軟體工程背景，能理解測試斷言與程式碼修補的語意對應
- 能撰寫 Docker 環境配置與自動化測試執行腳本
- 具備 LLM-as-a-Judge 的提示工程經驗

### 實作步驟建議

**步驟一：建立任務審核管線**
- 複製論文附錄 A 釋出的審核流程程式碼
- 為每個任務的每個「失敗轉通過斷言」準備 LLM 評判 prompt，要求評判模型判斷該斷言是否與議題描述一致
- 整合兩個 LLM 家族（Claude Opus 5.5 與 GPT-6.1 Sol）的判定，僅在兩者共識時標記為疑似錯誤

**步驟二：執行驗證階段**
- 對每個被標記的疑似偽陰性斷言，產生一個遵循議題但使用不同內部名稱的替代修補
- 在任務的 Docker 環境中執行該替代修補，確認測試是否真的拒絕它
- 對每個通過的修補，產生反例並執行，確認是否暴露偽陽性

**步驟三：任務修復或移除**
- 對於確認為偽陰性的任務，將缺失的需求加入議題描述（修復）
- 對於無法修復的任務，從訓練集中移除
- 統計修復後保留的任務數量（本論文中 1,087 個任務通過審核）

**步驟四：難度匹配與訓練集切分**
- 從原始任務集（Orig）、已審核任務集（Clean）、硬化任務集（Clean+FP）各選 512 個任務
- 使用基礎模型對每個任務採樣 8 次，依通過率分桶，確保三組的難度分佈一致
- 加入 Orig+Filter 對照組：對原始任務套用通過率過濾器，丟棄從未被解決的任務

**步驟五：GRPO 訓練與評估**
- 使用相同的 9B 基礎模型與超參數，在四組訓練集上分別訓練
- 每組跑三個隨機種子以控制變異
- 在 SWE-bench Verified 與 SWE-bench Pro 的保留測試任務上評估 pass@1

**步驟六：釋出與持續維護**
- 釋出 SWE-Gym-Verified 資料集、每個判定的執行證據、訓練集與審核流程
- 建立定期重新審核機制，因為基礎模型能力提升後會揭露更多偽陰性

### 潛在風險與注意事項

**風險一：LLM 評判的可靠性**
- 單一 LLM 家族的判定可能誤判，必須採用兩個家族交叉驗證
- 緩解：僅在兩家族共識時標記，且每個判定都需附執行證據

**風險二：執行環境不一致**
- Docker 環境配置差異可能導致同一修補在不同環境下通過/失敗結果不同
- 緩解：嚴格鎖定環境版本，並在審核流程中記錄每次執行的完整日誌

**風險三：審核成本過高**
- 每個任務需多次 LLM 呼叫與多次程式碼執行，2,531 個任務的完整審核成本可觀
- 緩解：先以基礎模型通過率預篩選，僅對疑似有問題的任務進行深度審核

**風險四：難度匹配的偏差**
- 若 Clean 與 Orig 的難度分佈未嚴格匹配，效能差異可能來自難度而非品質
- 緩解：採用 8 次採樣的分桶匹配，並在論文中報告匹配前後的統計檢定

**風險五：偽陽性硬化的無效性**
- 本論文發現新增測試攔截 25% 偽陽性後，保留測試分數未顯著提升
- 緩解：不要將資源投入偽陽性硬化，應優先修復偽陰性

**風險六：通過率過濾器的誤導性**
- 丟棄從未被解決的任務並不能替代真正的審核，因為有時解決的任務也帶有偽陰性
- 緩解：通過率過濾僅作為輔助手段，不可取代斷言級審核

### 與其他技術的整合建議

**與 GRPO/PPO 等 RL 框架整合**：
- 在 TRL、OpenRLHF、verl 等開源 RL 框架中，將獎勵函數從「測試是否通過」升級為「通過且通過的是正確修補」
- 整合 SWE-Gym-Verified 作為預設訓練集，替換原始 SWE-Gym

**與程式碼代理框架整合**：
- 在 SWE-agent、OpenHands、Aider 等代理框架中，加入「修補後自我驗證」步驟，產生反例以輔助審核
- 將審核流程的執行證據整合到代理的除錯日誌中

**與評測基準整合**：
- 在 SWE-bench Verified、SWE-bench Pro 的評估管線中，加入「替代修補測試」步驟，自動標記偽陰性任務
- 將審核結果回饋給基準維護者，持續更新任務集

**與 LLM-as-a-Judge 系統整合**：
- 將本論文的雙家族共識機制整合到現有的程式碼評審系統中
- 將執行證據作為 LLM 評判的補充輸入，提升判定準確率

**與 MLOps 平台整合**：
- 將審核流程封裝為 CI/CD 中的資料驗證步驟，每次訓練資料更新時自動觸發
- 將審核結果（每個任務的判定與證據）存入特徵商店，供後續實驗追溯

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的圖 1，理解「偽陰性」與「偽陽性」兩個概念在程式碼任務中的具體意涵，再看圖 1c 的統計圖，理解為什麼「模型解不出來」不等於「任務太難」，可能是測試本身有問題。接著跳到第 5.4 節看 Clean 比 Orig 高 2.4 分的結論，建立「資料品質比資料量更重要」的直覺，最後再回頭補讀相關術語。

**給 AI 工程師**：重點閱讀第 5.3 節，理解為什麼通過率過濾器無法取代真正的審核——因為 GRPO 只從獎勵有方差的群組學習，而從未被解決的偽陰性任務根本不會貢獻梯度。實作時直接採用論文釋出的 SWE-Gym-Verified 與審核流程，將其整合到現有的 RL 訓練管線中，並以「難度匹配 + 等量大小」的控制變項方法設計後續消融實驗。

**給研究者**：本論文的核心方法論貢獻在於「LLM 評判 + 執行驗證」的雙階段審核設計，以及「獎勵標籤正確性」作為資料品質的新維度。建議深入閱讀第 5.2 與 5.5 節，思考如何將此方法論擴展到其他領域的 RL 任務集（如數學推理、工具使用），並探索「偽陽性硬化無效」背後的理論原因——可能與 GRPO 的群組相對獎勵機制有關。

**給產品經理**：本論文的核心商業意涵是「訓練資料的品質審核能直接轉化為產品效能提升」，且成本可控。SWE-Gym-Verified 的 1,087 個任務相較於原始 2,531 個任務，量更少但訓練出的代理在 SWE-bench Verified 與 SWE-bench Pro 上分別高出 2.4 與 2.7 分。建議將「獎勵標籤審核」列為程式碼代理產品開發的標準步驟，並評估將此審核流程商業化為資料品質服務的可行性。
