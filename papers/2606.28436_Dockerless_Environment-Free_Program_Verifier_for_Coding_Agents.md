# Dockerless：適用於程式設計代理的免環境程式驗證器

**原文標題：** Dockerless: Environment-Free Program Verifier for Coding Agents  
**作者：** Wenhao Zeng、Yuling Shi、Xiaodong Gu 等 13 位作者  
**發布日期：** 2026-06-26

## ⚡ TL;DR

現有驗證依賴 Docker 環境，建置成本高昂且難以規模化。
提出免環境驗證器 Dockerless，以多子代理探索儲存庫證據評估補丁。
驗證基準超越最強開源 14.3 AUC，免環境後訓練效能媲美環境式訓練。

---

## 摘要翻譯

程式驗證器在訓練程式設計代理中扮演核心角色，包括為監督式微調（SFT）選取軌跡，以及為強化學習（RL）提供獎勵。標準的基於執行的驗證需要在逐儲存庫環境（如 Docker 映像檔）內執行單元測試，帶來龐大的環境建置成本。我們提出 Dockerless，一個免環境的代理式補丁驗證器，無需執行即可評估生成的程式碼補丁。Dockerless 並非簡單地將候選補丁與參考補丁進行比對，而是透過代理式儲存庫探索所收集的證據來判斷補丁正確性。在某項驗證器評估基準中，Dockerless 的 AUC 較最強大的開源驗證器高出 14.3 點。將 Dockerless 同時作為 SFT 軌跡篩選器與 RL 獎勵，可實現完全免環境的後訓練管線。最終模型在 SWE-bench Verified、SWE-bench Multilingual 與 SWE-bench Pro 上分別達到 62.0%、50.0% 與 35.2% 的解決率。其分別超越 Qwen3.5-9B 基線 2.4、8.7 與 2.9 個百分點，表現與基於環境的後訓練相當。

### 核心貢獻（3～5點）
- 提出 Dockerless，一個無需執行環境即可評估程式碼補丁正確性的代理式補丁驗證器，透過代理式儲存庫探索收集證據進行判斷，而非僅比對參考補丁。
- 在驗證器評估基準中，AUC 較最強大的開源驗證器高出 14.3 點，顯著提升驗證效能。
- 將 Dockerless 同時應用於監督式微調（SFT）的軌跡篩選與強化學習（RL）的獎勵機制，實現完全免環境的後訓練管線。
- 在 SWE-bench Verified、Multilingual 與 Pro 三項基準上分別達到 62.0%、50.0% 與 35.2% 的解決率，超越 Qwen3.5-9B 基線且表現與基於環境的後訓練相當。

### 適合對象
從事自動化程式設計代理、程式驗證與大型語言模型後訓練之研究人員與工程師，特別是面臨私有、企業或遺留程式碼庫環境建置挑戰，或希望降低環境建置成本以加速訓練管線開發之團隊。

## 深度分析

#### 方法論解析

Dockerless 的核心貢獻在於提出一個完全免環境（environment-free）的代理式補丁驗證器（agentic patch verifier），其設計理念並非單純比對候選補丁（candidate patch）與參考補丁（reference patch）的文字差異，而是透過主動探索程式碼庫（codebase）來累積判斷所需的證據（evidence）。整體架構可分為兩個階段：問題生成與探索（Question Generation and Exploration）、以及判斷（Judgment）。

在問題生成階段，驗證器接收議題描述（issue）、參考補丁（reference patch）與候選補丁（candidate patch）後，首先衍生出 K 個驗證問題（verification questions）。這些問題的設計涵蓋多個維度：修正應於儲存庫（repository）的何處生效、修補後的程式碼預期行為為何、哪些單元測試（unit tests）或斷言（assertions）可確認正確性、以及修改是否會影響周邊模組（surrounding modules）等。此設計直接回應了既有免環境驗證器僅仰賴表層資訊（surface-level information）而缺乏深度儲存庫上下文（deep repository context）的缺陷。

接著進入探索階段，系統派發多個平行子代理（parallel sub-agents）深入程式碼庫，針對每一個驗證問題收集具備證據支持的答案。這些子代理可透過讀取工具（Read Tools）檢視原始碼結構，從而建立「證據導向（evidence-backed）」的判斷基礎，而非僅進行靜態的文字比對。最後，在判斷階段，模型將議題、兩份補丁以及所有收集到的問題-答案對（Q_k, A_k）進行聚合，輸出一個二元判決標記（binary verdict token），並利用其 logits 映射為連續的正確性分數 r_φ(x,y) ∈ [0,1]，作為監督式微調（SFT）的軌跡篩選（trajectory filter）或強化學習（RL）的獎勵（rewards）。

在訓練層面，研究團隊採用拒絕採樣（rejection sampling）策略，於 SWE-Gym 與 Multi-SWE-RL 共 3.7K 筆議題上進行採樣。僅保留那些最終判決與 ground-truth test outcome（即基於執行的驗證結果）一致的 question-answer-judge trajectories，以此確保模型在無環境（env-free）設定下仍能學習到與執行式驗證（execution-based verification）高度相關的正確性訊號。

#### 實驗數據解讀

論文在多個層面驗證了 Dockerless 的有效性，數據呈現出清晰的梯度意義。首先在驗證器本身的評估上，Dockerless 相較於最強開源基線（baseline）提升了 14.3 AUC points（AUC 曲線下面積），顯示其在區分正確與錯誤補丁的排序能力上有顯著優勢。

在監督式微調（SFT）的應用中，研究團隊從 16K 筆免環境（env-free）執行軌跡（rollouts）中，利用 Dockerless 篩選出排名前 25%（約 4K）的高品質軌跡進行訓練。結果顯示，僅使用這 4K 筆資料即超越使用完整 16K 筆軌跡的表現，在 SWE-bench Verified、Multilingual 與 Pro 上分別提升 1.8、6.4 與 3.4 個百分點。這項結果凸顯了「品質重於數量」的資料篩選邏輯：在後訓練管線（post-training pipeline）中，低品質的錯誤軌跡反而會對模型造成負面影響，而精準的環境免驗證器能有效過濾雜訊。

在強化學習（RL）獎勵層面，以 Dockerless 作為環境免獎勵訊號（environment-free reward）的設定，相較於採用 DeepSWEVerifier 的 RL 管線，在三個基準測試（benchmark）上分別提升 1.4、2.7 與 1.1 個百分點。這證明了即使沒有逐儲存庫環境（per-repository environments）的執行反饋，代理式驗證器仍能提供足夠可靠的獎勵訊號以驅動策略學習。

最終的端到端（end-to-end）結果顯示，完全免環境的後訓練管線在 SWE-bench Verified、Multilingual 與 Pro 上達到 62.0%、50.0% 與 35.2% 的解決率（resolve rate），相較於 Qwen3.5-9B 基線分別進步 2.4、8.7 與 2.9 點，且已能匹配（match）標準基於環境的後訓練（environment-based post-training）表現。其中 Multilingual 的進步幅度最大（8.7 點），暗示免環境驗證在處理多語言或跨語境程式碼庫時，可能因為避免了複雜的環境建置成本而獲得更大的邊際效益。

#### 與現有研究的比較

現有驗證方法大致可分為兩個極端：一端是基於執行的驗證（execution-based verification），透過在隔離的逐儲存庫環境（isolated per-repository environments）中執行單元測試（unit tests）來取得二元正確性訊號。這種方法雖然準確，但伴隨高昂的環境建置成本（environment setup costs）與工程開銷（engineering overhead），且在私有（private）、企業（enterprise）或遺留程式碼庫（legacy codebases）中經常因缺乏可複現環境（reproducible environments）或完整測試套件（comprehensive test suites）而無法運作。

另一端是現有的免環境（environment-free）驗證器，例如 LLM Scorer（Shum et al., 2025; Wang et al., 2026; Luo et al., 2025），這類方法僅利用表層資訊（surface-level information）對補丁進行評分，從未主動檢視儲存庫內部結構。對於需要理解功能等價性（functional equivalence）與深度儲存庫上下文（deep repository context）的複雜軟體工程（SWE）任務，此類淺層方法往往力有未逮。

近期研究如 Sun et al., 2026; Ludwig et al., 2026; Xu et al., 2025 嘗試以共享基礎映像檔（shared base image）降低代理執行軌跡（rollouts）的環境成本，但驗證器（verifier）本身仍是瓶頸。Dockerless 恰好填補了這個缺口：它保留了免環境的可擴展性（scalable），同時透過代理式儲存庫探索（agentic repository exploration）達成了儲存庫扎根性（repo-grounded）。這使得 Dockerless 在準確度上遠超表面層的 LLM Scorer，在成本與適用範圍上又優於傳統 Docker-based Tests。

然而，Dockerless 仍存在若干限制。首先，其輸入包含參考補丁（reference patch），這意味著在完全無參考答案的真實部署場景中，可能需要額外機制來生成或替代 reference patch。其次，訓練過程中的拒絕採樣（rejection sampling）仍需依賴 ground-truth test outcome 作為篩選標準，這在理論上預設了訓練資料集仍具備可執行環境；如何將此方法擴展至完全無法執行測試的企業內部程式碼庫，論文著墨較少。

#### 可重現性評估

從提供的文本脈絡來看，論文使用了公開可取得的訓練資料集，包括 SWE-Gym（Pan et al., 2025）與 Multi-SWE-RL（Zan et al., 2026），共計 3.7K 筆議題，這部分降低了資料層面的重現門檻。基礎模型採用 Qwen3.5-9B，亦為開放權重模型。實驗評估採用標準的 SWE-bench 系列基準測試（SWE-bench Verified、Multilingual、Pro），具備明確的評估協議。

然而，關於 Dockerless 本身的原始碼、模型權重（model weights）、以及完整的後訓練管線（post-training pipeline）實作細節，摘要與方法論段落並未明確提及是否開源。特別是子代理（sub-agents）的提示設計（prompt design）、問題生成（question generation）的具體策略、以及拒絕採樣的完整過濾邏輯，若缺乏官方釋出，其他研究團隊將難以精確重現其 14.3 AUC points 的增益與端到端的解決率（resolve rate）。此外，平行子代理的呼叫機制與底層讀取工具（Read Tools）的實作規格，亦是重現過程中的關鍵未公開細節。

#### 未來研究方向

第一，降低對參考補丁（reference patch）的依賴是邁向通用驗證器的關鍵。未來可探索僅以議題描述（issue）與候選補丁（candidate patch）為輸入的驗證架構，或是透過輔助代理自動生成弱參考補丁（pseudo reference patch），以提升在真實世界無參考答案場景的適用性。

第二，推論效率與成本優化。Dockerless 採用多個平行子代理（parallel sub-agents）進行證據收集（evidence collection），雖然提升了準確度，但也增加了推論延遲與計算成本。後續研究可朝模型蒸餾（distillation）方向發展，將大型代理式驗證器的知識壓縮為單一回合（single-turn）的輕量模型，或引入快取機制減少重複的儲存庫探索。

第三，混合式驗證管線（hybrid verification pipeline）。對於具備可複現環境（reproducible environments）與完整測試套件（comprehensive test suites）的開源專案，可設計動態路由機制：優先使用 Dockerless 進行快速篩選，僅對高不確定性案例啟動執行式驗證（execution-based verification），兼顧規模與準確。

第四，獎勵塑形（reward shaping）的細緻化。目前 Dockerless 輸出二元判決標記（binary verdict token）的 logits 作為連續分數，未來可探索更細粒度的密集獎勵（dense rewards），例如針對個別驗證問題（verification questions）的回應品質給予中間獎勵，以進一步提升強化學習（RL）的訓練穩定性。

第五，針對私有（private）與企業（enterprise）程式碼庫的實證研究。論文雖指出 Dockerless 適用於缺乏環境的遺留系統，但仍需更大規模的產業實驗來驗證其在無法取得 ground-truth test outcome 的場景中，作為監督式微調（SFT）篩選器與強化學習獎勵的長期可靠性。

## 論文問答

**Q1：為什麼基於執行的驗證會成為訓練編碼代理的主要瓶頸？**
A：基於執行的驗證需要為每個儲存庫建置獨立的 Docker 環境，這涉及解析相依套件、設定測試執行器與撰寫結果解析腳本，導致巨大的工程開銷。即使是先進的自動化流程，也僅能在有限的候選儲存庫上成功建置環境。更重要的是，許多私有、企業內部或遺留程式碼庫根本缺乏可複現的環境或完整的測試套件，使得執行驗證在實務上不可行或完全失效。

**Q2：現有的免環境驗證器為何在複雜的軟體工程任務中表現不佳？**
A：現有的免環境驗證器（如 LLM Scorer）僅依賴表層資訊對補丁進行評分，從未主動檢視儲存庫內部的程式碼結構與上下文。這種淺層方法無法處理複雜的軟體工程任務，例如判斷修改後的函式是否確實被失敗行為呼叫，或替代實作是否正確與周邊模組整合。缺乏深度儲存庫上下文使得這些驗證器難以準確評估功能等價性，導致驗證品質低落。

**Q3：開發可擴展的驗證器對於自動化程式設計代理的未來為何至關重要？**
A：程式驗證器在編碼代理的訓練管線中扮演核心角色，無論是用於監督式微調的軌跡篩選，或是強化學習的獎勵訊號，都直接決定了代理的學習品質。若驗證步驟無法擴展，整個後訓練流程將受限於少數擁有完善環境的熱門儲存庫，遺漏大量真實世界中的私有、企業或遺留程式碼庫。因此，開發可擴展且免環境的驗證器是釋放編碼代理在長尾應用場景潛力的關鍵。

**Q4：Dockerless 在不執行程式碼的前提下，其核心驗證機制是什麼？**
A：Dockerless 採用代理式儲存庫探索機制，透過主動探查程式碼庫來收集判斷補丁正確性的證據。具體而言，它會根據問題描述與參考補丁生成多個驗證問題，並派遣平行的子代理深入程式碼庫尋找證據支援的答案。最後，驗證器將這些證據與問題描述、補丁內容一併彙整，輸出連續性的正確性分數或二元判決，無需執行任何單元測試或建置 Docker 環境。

**Q5：Dockerless 與先前的免環境方法（如 LLM Scorer）在本質上有何不同？**
A：與僅進行文字比對或表面層評分的傳統免環境方法不同，Dockerless 將驗證過程扎根於實際的程式碼庫內容，而非僅比對候選補丁與參考補丁的文字差異。它透過多個子代理並行探索儲存庫，主動查證補丁是否正確整合於整體程式架構中，例如確認修改點是否被實際呼叫、是否影響其他模組。這種「代理式、證據導向」的驗證範式，使其在無需執行環境的前提下，仍能獲得深度儲存庫上下文。

**Q6：為何 Dockerless 選擇使用平行子代理與兩階段管線（問題生成後進行判決）的設計？**
A：採用平行子代理的設計能夠同時針對不同維度的驗證問題（如修改位置、預期行為、潛在副作用）收集證據，大幅提升探索效率與證據覆蓋率。兩階段管線首先將驗證任務分解為具體的問題生成與證據探查，再將收集到的結構化證據彙整後進行最終判決，有助於降低單一模型直接判斷的認知負荷。這種模組化設計不僅讓驗證過程更具可解釋性，也讓訓練時能透過拒絕採樣保留問題、答案與判決一致的高品質軌跡，從而提升驗證器的準確度。

**Q7：Dockerless 在哪些基準測試上進行評估，使用了什麼評估指標？**
A：Dockerless 在專屬的驗證器評估基準上接受測試，並以 AUC（曲線下面積）作為核心指標衡量其區分正確與錯誤補丁的能力。在端對端評估方面，研究團隊採用了 SWE-bench 系列的三個數據集：Verified、Multilingual 與 Pro，這些基準涵蓋了不同難度與語言的軟體工程問題。此外，研究亦比較了 Dockerless 作為監督式微調軌跡篩選器與強化學習獎勵訊號時，對最終模型解決率（resolve rate）的影響。

**Q8：論文中展示 Dockerless 有效性的主要量化結果為何？**
A：作為獨立驗證器，Dockerless 在驗證器評估基準上比最強的開源基線高出 14.3 個 AUC 點，顯示其卓越的判別能力。在後訓練管線中，使用 Dockerless 篩選前 25% 軌跡進行監督式微調，在 SWE-bench Verified、Multilingual 與 Pro 上分別比使用全部免環境軌跡提升 1.8、6.4 與 3.4 個百分點。最終的完全免環境後訓練模型達到 62.0%、50.0% 與 35.2% 的解決率，超越 Qwen3.5-9B 基線 2.4、8.7 與 2.9 點，並與標準的基於環境後訓練表現相當。

**Q9：作者如何驗證「代理式探索」元件相較於更簡單的基線是必要的？**
A：論文透過與僅使用表層資訊的 LLM Scorer 以及 DeepSWE Verifier 進行對比，證明了代理式探索的必要性。在強化學習獎勵的實驗中，使用 Dockerless 作為獎勵訊號相比 DeepSWE Verifier 在三個基準上分別提升了 1.4、2.7 與 1.1 個百分點。這些比較結果顯示，單純依賴表面特徵或較淺層的驗證器無法準確捕捉補丁的正確性，而深入儲存庫內部收集證據的設計對於複雜軟體工程任務至關重要。

**Q10：在哪些真實世界場景中，Dockerless 特別具有應用價值？**
A：Dockerless 特別適用於私有、企業內部或遺留程式碼庫，這些場景往往缺乏可複現的執行環境或完整的單元測試套件，傳統的 Docker 驗證根本無法部署。對於擁有成千上萬個長尾儲存庫的組織而言，免除逐儲存庫建置環境的需求意味著可以大規模地對冷門或歷史專案進行代理訓練與驗證。此外，在需要快速迭代後訓練管線的情境下，Dockerless 讓 rollout 收集、軌跡篩選與獎勵計算都能在單一最小化基礎映像檔上完成。

**Q11：Dockerless 在實際產品部署上提供了哪些工程優勢？**
A：Dockerless 將後訓練管線中的環境建置成本降為零，無需為每個儲存庫維護客製化的 Docker 映像檔、解析相依套件或撰寫測試執行腳本。這使得工程團隊能夠以單一共用的最小化基礎映像檔來部署整個訓練與驗證流程，大幅簡化基礎設施的複雜度與維護負擔。同時，由於驗證過程不依賴實際執行，也避免了因環境設定錯誤、相依衝突或測試不穩定導致的驗證失敗與雜訊。

**Q12：Dockerless 可能如何改變編碼代理研究與產業採用的格局？**
A：Dockerless 確立了「完全免環境後訓練」作為一條可擴展且可行的技術路徑，打破了過去認為驗證必須依賴 Docker 執行的假設。這將使研究人員與企業能夠觸及過去因環境建置成本過高而被排除在訓練數據之外的廣大長尾儲存庫，顯著擴充編碼代理的學習範圍與應用場景。長遠來看，這種降低門檻的驗證範式有望加速自動化程式設計代理在真實軟體維護任務中的落地與普及。

**Q13：免環境的靜態驗證方法存在哪些固有局限性？**
A：由於 Dockerless 不實際執行程式碼，它無法觀察到執行期的動態行為、記憶體狀態或特定邊緣案例下的執行結果，這在某些高度依賴執行語義的漏洞修復中可能構成限制。此外，驗證品質高度依賴子代理能否在龐大的程式碼庫中成功定位相關證據，若探索過程遺漏關鍵呼叫鏈或隱藏的副作用，可能導致誤判。雖然論文顯示其能匹配基於環境的後訓練表現，但在極端複雜或高度動態的系統中，靜態驗證仍可能難以完全取代實際執行測試。

**Q14：在什麼情況下 Dockerless 可能產生錯誤的判決？**
A：當問題描述過於模糊，或參考補丁本身並非最佳解甚至包含副作用時，Dockerless 生成的驗證問題可能會誤導子代理朝錯誤方向收集證據。如果候選補丁採用了與參考補丁截然不同的正確實作路徑，單純基於參考補丁導出的驗證問題可能無法公正評估其功能等價性。另外，對於需要跨檔案、跨語言或涉及複雜編譯條件的專案，子代理可能在靜態探索階段未能完整追蹤所有依賴關係，進而產生錯誤的正確性分數。

**Q15：對於免環境驗證的未來，論文暗示了哪些可能的改進與延伸方向？**
A：未來研究可朝向減少對參考補丁的依賴發展，使驗證器能僅憑問題描述與程式碼庫結構自主生成驗證標準，從而評估更多樣化的正確實作。進一步提升子代理的探索深度與策略規劃能力，例如引入符號執行或輕量級的靜態分析工具作為輔助，也有助於彌補純文字探索的不足。此外，將免環境驗證與選擇性的輕量執行結合，設計出混合式驗證架構，或許能在保持可擴展性的同時，進一步提升對執行期語義敏感任務的判斷準確度。

## 實務應用指南

### 適用場景

1. **企業內部私有程式碼庫的補丁驗證**：許多私有或企業程式碼庫難以建立可複現環境，甚至無法離線建置 Docker 映像檔。Dockerless 可在僅有基礎映像檔的情況下，透過代理式儲存庫探索驗證候選補丁的正確性，解決無法執行單元測試的困境。
2. **遺留系統與長尾儲存庫的維護**：針對缺乏完整測試套件或相依套件已不可考的遺留程式碼庫，Dockerless 以證據導向的判斷取代執行為基礎的驗證，成為維護舊系統時少數可行的自動化品質閘道。
3. **大規模後訓練資料篩選**：在訓練程式設計代理時，需要從大量執行軌跡中過濾高品質資料進行監督式微調（SFT），或提供強化學習（RL）的獎勵訊號。Dockerless 作為免環境的軌跡篩選器與獎勵模型，可顯著降低擴展後訓練管線時的環境建置成本。
4. **多語言程式碼審查與自動化合併把關**：在支援多種語言的開發團隊中，統一建置各語言的逐儲存庫環境成本高昂。Dockerless 可直接針對 SWE-bench Multilingual 等場景中的跨語言補丁進行深度語意驗證，作為合併請求（PR）的自動化審查層。
5. **教育與競賽平台的即時批改**：對於需要即時回饋但無法安全執行學生程式碼的環境（如擔心惡意程式碼或無法提供隔離容器），Dockerless 提供一條不依赖執行的驗證路徑，透過與參考補丁的語意比對與程式碼庫探索給出評分。

### 實作前置條件

**資料需求**：需準備結構化的 (Issue, Reference Patch, Candidate Patch, Ground-Truth Outcome) 四元組，建議至少 3,000–5,000 筆以上帶有地面真值標註的樣本（格式可參考 SWE-Gym 或 Multi-SWE-RL）。若用於特定企業領域，需額外收集內部問題描述與正確補丁作為參考補丁。

**運算資源**：需要可並行執行子代理探索的 LLM 推理叢集（支援多路呼叫以收集證據），以及用於拒絕採樣與微調的 GPU 資源（如訓練 7B–9B 規模的驗證器）。此外，需部署基礎的程式碼檢索工具（如 AST Parser、符號搜尋索引）以加速儲存庫探索。

**技術能力**：團隊需具備 LLM 代理架構設計經驗，能夠設計驗證問題生成策略與證據彙整邏輯；熟悉後訓練流程（SFT 資料篩選、RL 獎勵 shaping）；並具備將驗證器整合至現有 CI/CD 或代理腳手架（如 OpenHands）的工程能力。

### 實作步驟建議

1. **建立地面真值資料集**：從現有執行為基礎的管線中，彙整歷史 Issue、參考補丁、多組候選補丁及其在 Docker 環境中的實際測試結果，作為拒絕採樣的黃金標準。
2. **設計多維度驗證問題模板**：依據常見軟體錯誤類型，定義問題生成的結構化維度，例如「修改應發生在哪些檔案與函式」、「修補後的預期行為為何」、「是否會破壞周邊模組的呼叫關係」等。
3. **開發子代理工具鏈**：實作並行的程式碼庫探索工具，賦予子代理讀取檔案、搜尋符號、分析呼叫圖的能力，並規定證據必須包含可追溯的程式碼片段與檔案路徑。
4. **執行拒絕採樣訓練**：讓主驗證器針對每筆資料生成 K 個驗證問題，派遣子代理收集證據與答案，最終由主驗證器輸出二元判斷。僅保留最終判斷與地面真值測試結果完全一致的 (Question, Answer, Judge) 軌跡用於微調。
5. **部署為雙重角色元件**：將訓練完成的 Dockerless 同時掛載至後訓練管線的兩個節點——SFT 階段的軌跡篩選器（保留 Top 25% 高分軌跡）與 RL 階段的獎勵模型（提供連續型獎勵訊號）。
6. **漸進式驗證與上線**：先在免環境設定中與現有基於環境的驗證並行運作，比對兩者的 AUC 與解決率（Resolve Rate）差距；確認性能匹配後，再對長尾儲存庫逐步關閉高成本的逐儲存庫 Docker 驗證。

### 潛在風險與注意事項

- **證據幻覺（Hallucination）**：子代理在探索過程中可能捏造不存在的程式碼庫證據，導致驗證器誤判。建議強制要求所有證據必須附帶原始碼片段與檔案路徑，並在彙整階段進行來源追溯與一致性交叉驗證。
- **訓練資料偏差**：若地面真值主要來自特定語言（如 Python）或熱門框架，驗證器可能對長尾儲存庫過度自信。應定期以抽樣方式執行基於環境的驗證，校正免環境驗證器的漂移。
- **計算成本轉移而非消除**：雖然省去了 Docker 建置與維護的工程開銷，但並行子代理的多次 LLM 呼叫可能帶來可觀的推理成本。建議實作問題剪枝策略（如靜態分析預篩顯然錯誤的補丁）與證據快取機制，降低重複探索。
- **安全與隱私外洩**：代理探索過程中可能將私有程式碼傳送至外部 LLM API。若應用於企業內部，應優先採用本地部署的模型，或對敏感程式碼進行符號化遮罩（Symbol Masking）後再送出查詢。

### 與其他技術的整合建議

- **與現有 CI/CD 管線整合**：將 Dockerless 部署為合併請求（PR）流程中的品質閘道，與現有靜態分析工具（如 SonarQube、CodeQL）並行運作。靜態分析負責表面層語法與風格檢查，Dockerless 負責深度語意與功能等價性判斷，形成互補。
- **與代理框架整合**：搭配 OpenHands 等已支援免環境設定的代理腳手架，將 Dockerless 作為「生成→驗證→篩選」閉環中的驗證節點，使整個程式設計代理的運作無需任何逐儲存庫環境。
- **與執行驗證混用（Hybrid Mode）**：對於核心業務路徑或高風險補丁，保留小規模的 Docker 抽樣驗證作為人類監督的後備方案；對於長尾或環境不可行的儲存庫，則完全交由 Dockerless 處理。
- **與檢索增強生成（RAG）整合**：將子代理在探索過程中累積的證據與程式碼庫上下文索引化，不僅用於驗證分數，更可生成結構化的「驗證報告」，說明補丁為何正確或錯誤，提升開發者對自動化判斷的信任度。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從圖 1 與圖 2 的架構比較開始，理解「執行驗證」與「免環境驗證」的核心差異，以及為何表層資訊比對不足以處理複雜的軟體工程任務。暫時略過拒絕採樣的數學細節，把重點放在 Dockerless 如何像「偵探」般透過提問與蒐證來判斷補丁正確性。

**AI 工程師**：請深入研讀第 2.2 節的兩階段架構——問題生成、並行子代理探索、證據彙整判斷——並評估自身程式碼庫是否具備足夠的地面真值資料與檢索工具鏈來複現此管線。特別注意拒絕採樣階段中，如何設計有效的驗證問題以最大化與地面真值的一致性。

**研究人員**：建議關注本研究在免環境後訓練管線的端到端實驗設計，特別是 Dockerless 同時作為 SFT 軌跡篩選器與 RL 獎勵模型的雙重角色，以及其性能最終能與基於環境的後訓練達成平手的理論意涵。這對於未來擴展至更廣泛的長尾程式碼庫具有重要啟發。

**產品經理**：請從工程開銷與擴展性角度切入，對照「逐儲存庫 Docker 建置與維護成本」與「免環境驗證的效益」，評估導入 Dockerless 後對內部遺留系統、私有程式碼庫或 Multilingual 場景的覆蓋率提升，並規劃漸進式替代高成本驗證節點的產品路線圖。
