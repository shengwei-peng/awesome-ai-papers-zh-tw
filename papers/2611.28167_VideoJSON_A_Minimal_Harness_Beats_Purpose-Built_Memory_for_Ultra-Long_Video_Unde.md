## 深度分析

#### 方法論解析

VideoJSON 的核心設計哲學是「以簡馭繁」(simplicity over complexity)，透過最小化的框架設計讓編碼代理 (coding agent) 自主決定搜尋策略，而非預先定義固定的檢索管線 (retrieval pipeline)。整個系統分為兩個階段：

**索引建立階段 (Indexing Stage)**

此階段在問題出現前一次性執行。系統使用視覺語言模型 (Vision-Language Model, VLM)，具體為 Qwen-3.8-Flash-Next，以 1 fps 的取樣率處理每段 60 秒的影片片段，並結合 Qwen-3-ASR-1.7B 產生的語音轉錄 (speech transcript)（在 EgoLife 資料集上則使用官方釋出的轉錄稿）。每分鐘的影片被轉換為單一 JSON 紀錄 (JSON record)，包含以下結構化欄位 (structured field)：

- **密集描述 (dense caption)**：對該分鐘影片內容的整體文字描述
- **事件 (events)**：附帶起訖秒數的細粒度事件標註
- **實體 (entities)**：人物、物件等識別標記
- **地點 (places)**：場景資訊
- **動作 (actions)**：行為分類
- **關係 (relations)**：實體間的互動
- **意外時刻 (unexpected moments)**：異常事件標記
- **轉錄 (transcription)**：語音內容
- **螢幕文字 (on-screen text)**：可見文字
- **情緒 (mood)**：氛圍描述
- **解釋欄位 (explanation field)**：輔助推理資訊

關鍵設計在於：所有影片來源（第一人稱影片、遊戲實況、直播串流）皆使用相同的欄位結構，僅在 metadata 中標註片段識別資訊、日期與時間範圍。這種「統一結構」(uniform schema) 使得代理可以跨資料集撰寫通用的搜尋程式。

**查詢階段 (Querying Stage)**

每個問題觸發一次新的查詢流程。編碼代理在沙盒容器 (sandboxed container) 中撰寫 Python 或 Bash 程式來過濾、連結、讀取這些 JSON 紀錄，並根據每次執行的輸出決定下一步動作。論文以「這個禮拜晚餐後我通常做什麼？」為例說明：代理可能先寫一個程式找出所有用餐時間點，再寫另一個程式讀取每個用餐時段後續的活動描述，最後跨日比較活動模式。

此設計有幾個重要意涵：

1. **無任務專屬訓練 (no task-specific training)**：代理無需針對影片問答進行微調
2. **無原始影片存取 (no raw video access)**：查詢階段完全不接觸原始影像，僅操作 JSON 紀錄
3. **多步驟搜尋 (multi-step search)**：搜尋策略由代理動態決定，而非預先編碼
4. **可程式化檢索 (programmable retrieval)**：相對於相似度評分 (similarity scoring) 或鄰域過濾 (neighborhood filtering)，代理可以自由組合邏輯運算

此方法呼應了 mini-SWE-agent 與 Recursive Language Models 的設計理念——將長輸入視為外部環境的一部分，由模型透過程式碼自主分解與檢查。

#### 實驗數據解讀

**基準測試表現**

論文在四個超長影片基準測試 (benchmark) 上評估 VideoJSON，並與 MAGIC-Video 重新執行版本以及最佳先驗結果 EgoMemReason 比較：

| 基準測試 | 超越 MAGIC-Video | 超越 EgoMemReason |
|---------|-----------------|-------------------|
| EgoLifeQA | +7.0 分 | — |
| Ego-R1-Bench | +20.0 分 | — |
| MM-Lifelong Week | +24.75 分 | +12.6 分 |

這些差距在影片理解任務中屬於顯著提升，特別是 MM-Lifelong Week 上近 25 分的改進，顯示出在「跨日模式識別」(cross-day pattern recognition) 類任務上，代理式程式搜尋相較於固定檢索管線的優勢。

**策略模型擴展性 (Policy Model Scaling)**

論文測試了四個能力遞增的策略模型 (policy model)。VideoJSON 的平均分數從最弱模型到最強模型提升達 11.58 分，而 MAGIC-Video 最多僅提升 5.50 分。這項數據揭示一個關鍵現象：**VideoJSON 能更充分地利用更強的程式碼生成能力**。換言之，當底層語言模型升級時，VideoJSON 的收益放大效應更明顯，這與其「讓代理自己寫搜尋程式」的設計哲學一致——更強的模型意味著更聰明的搜尋策略。

**消融實驗 (Ablation) 結果**

消融實驗提供了三項關鍵發現：

1. **代理式程式搜尋 (agentic code search) 與結構化 JSON 紀錄皆為必要**：移除任一元件都會導致顯著效能下降
2. **每小時摘要 (hourly summary) 影響有限**：加入後平均分數變化小於 1.5 分
3. **額外工具與影片存取影響有限**：同樣小於 1.5 分變化

這顯示出 VideoJSON 的核心價值集中在「結構化紀錄 + 代理式搜尋」的組合，而非額外的輔助機制。值得注意的是，「影片存取影響有限」這項結果暗示：對於超長影片問答，純文字化的 JSON 紀錄已能捕捉足夠的視覺資訊，這對未來降低運算成本有重要意涵。

**微調實驗 (Fine-tuning)**

僅使用 64 條來自無關 100 小時直播串流的 VideoJSON 軌跡 (trajectory) 微調 Qwen-3.5-Flash，即可在 MM-Lifelong 上提升最多 8.25 分。這項結果的樣本效率極高，顯示：

- VideoJSON 軌跡本身具有可遷移性 (transferability)
- 代理式搜尋的推理模式可透過少量樣本學習
- 為資源受限場景提供了實用化路徑

#### 與現有研究的比較

**與 MAGIC-Video 的比較**

MAGIC-Video 採用多模態圖 (multimodal graph) 結合敘事鏈檢索 (narrative-chain retrieval)，並透過查詢種子擴散 (query-seeded diffusion) 在圖上進行探索。VideoJSON 的相對優勢在於：

- **靈活性**：代理可自由組合任意邏輯查詢，不受限於圖遍歷演算法
- **簡潔性**：無需預先定義圖結構與節點類型
- **可擴展性**：更強的程式碼模型帶來更大增益

但 MAGIC-Video 的圖結構在處理「實體共現」(entity co-occurrence) 等關係推理時可能仍有其結構性優勢。

**與 EgoMemReason 的比較**

EgoMemReason 在 MM-Lifelong Week 上被超越 12.6 分，顯示出對於需要跨日記憶推理的任務，VideoJSON 的「先定位後閱讀」多步驟策略比單純的記憶推理方法更有效。

**與 MERIT 的比較**

MERIT 同樣使用簡單、可查詢的索引（事件、對話、物件、摘要等專用鍵），但其檢索仍依賴相似度評分與鄰域過濾。VideoJSON 的差異在於允許模型自由查詢索引，而非受限於固定的相似度匹配機制。

**與 SAG、Orogat、A-MEM 的比較**

這些方法將代理記憶視為資料管理問題。VideoJSON 將每分鐘 JSON 紀錄視為記憶儲存，以代理的 Python/Bash 程式作為查詢介面，記憶在問題出現前固定，程式則按問題動態生成。

**限制與不足**

1. **VLM 索引品質瓶頸**：所有後續推理依賴索引階段的 JSON 紀錄品質，若 VLM 漏掉關鍵視覺細節，代理無法補救
2. **無原始影片存取**：雖然消融實驗顯示影響有限，但對於需要精確視覺細節的問題（如「某個畫面中特定物體的顏色」），可能受限
3. **每分鐘粒度**：固定 60 秒切分可能不適合所有任務，事件邊界可能跨越分鐘界線
4. **JSON 結構假設**：預先定義的欄位結構可能無法涵蓋所有問題類型所需的資訊
5. **計算成本**：雖然查詢階段無影片存取，但索引階段仍需處理全部影片

#### 未來研究方向

**1. 索引品質提升**

- **動態重新索引 (dynamic re-indexing)**：根據查詢失敗案例，針對性地重新處理特定片段

- **即時串流處理 (real-time streaming)**：將架構延伸至直播場景的即時問答

**4. 效率與可擴展性**

- **稀疏索引 (sparse indexing)**：並非每分鐘都產生完整紀錄，根據內容密度自適應調整
- **增量式索引 (incremental indexing)**：支援影片的增量添加，無需重新處理全部內容

**5. 理論分析**

- **表達能力分析**：形式化分析「JSON 紀錄 + 程式查詢」相較於「圖結構 + 固定檢索」的表達能力差異

**6. 應用領域拓展**

- **醫療手術影片分析**：跨多台手術的技術模式識別

**7. 與其他範式的結合**

這些方向中，**索引品質提升**與**代理搜尋策略最佳化**預期將帶來最直接的效能改進，而**理論分析**則有助於釐清此方法相較於其他範式的根本優勢與限制。

## 論文問答

**Q1：超長影片理解（ULVU）的核心問題是什麼？為什麼它比一般影片理解更具挑戰性？**

A：超長影片理解的核心問題在於，問題的證據可能散佈在數天甚至數週的影片時間軸上，例如「這週晚餐後我通常做什麼？」這類問題需要先定位用餐時間，再讀取後續時段的活動描述並跨日比較。一般影片問答只需在數分鐘到數小時的範圍內尋找答案，而 ULVU 必須在極長的時間跨度中搜尋分散的線索，並在有限的上下文預算下完成多步驟推理。這使得傳統的單一檢索或單一模型推理方法難以勝任，因為證據的時序關聯性與跨日模式無法從單一短片段中取得。

**Q2：為什麼現有的影片代理方法（基於複雜記憶圖與固定檢索管線）會失效？**

A：現有方法如 WorldMM、MAGIC-Video、GROVE 等，預先建構了情節記憶、語意記憶、視覺儲存、多模態圖或時間階層等複雜結構，並搭配固定的檢索管線或學習式工具選擇。這些設計在事前就決定了哪些搜尋方式容易被表達，限制了代理能進行的查詢類型。當問題需要跨層級、跨時間的靈活連結時（例如先找事件再讀取後續實體），固定管線往往無法表達或效率低落。VideoJSON 的觀察是，這些「目的導向」的記憶結構反而成為瓶頸，阻礙了代理根據每個問題動態調整搜尋策略的能力。

**Q3：為什麼這個研究方向重要？它解決了什麼實際需求？**

A：隨著穿戴式相機、智慧家庭助理與終身記錄裝置的普及，個人累積的影片資料已可達數百到數千小時，使用者自然會想對這些資料提問，例如「上個月我去過哪些餐廳？」或「孩子這週學會了什麼新詞彙？」。這類問題無法靠人工回看解決，必須由 AI 代理自動搜尋與推理。ULVU 因此成為邁向真正個人化 AI 助理的關鍵能力，也是評估長時程推理與代理式系統的重要試金石。VideoJSON 展示出以極簡框架即可達到領先效能，意味著此方向在工程與學術上都具備高度可行性。

**Q4：VideoJSON 的核心方法是什麼？請說明其兩個階段的設計。**

A：VideoJSON 是一個極簡框架，由兩個階段組成：索引建立（Indexing）與查詢（Querying）。在索引階段，一個視覺語言模型（VLM，如 Qwen-3.8-Flash-Next）以 1 fps 對每 60 秒影片片段獨立產生單一 JSON 紀錄，內含密集描述與結構化欄位（事件、實體、地點、動作、關係、語音轉錄、螢幕文字、情緒等）。在查詢階段，編碼代理在沙盒容器中撰寫 Python 或 Bash 程式，對這些紀錄進行多步驟的過濾、連結與讀取，並根據每次輸出決定下一步動作。整個記憶體在問題到達前就已建好，每個問題重複使用這份預建記憶，且代理在查詢時無需存取原始影片。

**Q5：VideoJSON 相較於先前方法（如 MERIT、VideoAgent、DoraemonGPT）的關鍵創新是什麼？**

A：VideoJSON 的關鍵創新在於「讓代理自己寫搜尋程式」，而非預先定義固定的檢索管線或相似度評分機制。MERIT 雖也使用簡單的可查詢索引，但仍依賴相似度評分與鄰域過濾；VideoAgent 與 DoraemonGPT 則以 SQL 查詢關聯式表格，限制了表達的靈活性。VideoJSON 改用巢狀 JSON 紀錄搭配 Python/Bash 程式，使代理能自由組合過濾、聚合、跨紀錄連結等操作，並在每一步根據輸出動態調整策略。這種「極簡框架＋強模型」的設計哲學，呼應了 mini-SWE-agent 與 Recursive Language Models 在程式碼任務上的成功，證明在影片領域同樣適用。

**Q6：為什麼選擇「每分鐘一筆 JSON 紀錄」與「結構化欄位」這兩個設計選擇？**

A：每分鐘一筆紀錄的設計在粒度與效率間取得平衡：太細（如每秒）會造成紀錄數爆炸且重複資訊過多，太粗（如每小時）則會遺失細節，使代理無法精準定位事件。結構化欄位（如事件的起訖秒數、實體、地點）則讓代理能用程式直接過濾與連結，而不必依賴語意相似度。例如代理可寫程式「找出所有 events 包含『晚餐』的紀錄，再讀取其後續時段的 entities」，這在純文字描述上難以表達，但在結構化欄位下僅需數行 Python。消融實驗也證實，移除結構化欄位會顯著降低效能，顯示此設計是效能增益的主要來源之一。

**Q7：實驗使用了哪些基準測試？它們各自評估什麼能力？**

A：實驗在四個超長影片基準上進行：EgoLifeQA、Ego-R1-Bench、MM-Lifelong Week，以及另一個未明確命名的基準。EgoLifeQA 與 Ego-R1-Bench 基於 EgoLife 資料集，評估第一人稱視角下跨日的生活記憶問答；MM-Lifelong Week 則評估跨週的長期記憶與模式識別能力。這些基準共同涵蓋了「跨日證據搜尋」、「實體與活動追蹤」、「長期模式總結」等 ULVU 核心子任務，能全面檢驗代理在長時程影片上的推理能力。

**Q8：VideoJSON 的關鍵實驗結果為何？它在哪些基準上領先？**

A：使用 DeepSeek V4.1 Flash 時，VideoJSON 在 EgoLifeQA、Ego-R1-Bench、MM-Lifelong Week 上分別超越 MAGIC-Video 7.0、20.0 與 24.75 分，並在 EgoMemReason 上超越最佳先前結果 12.6 分。更值得注意的是，在四個能力遞增的策略模型上，VideoJSON 的平均分數最高可提升 11.58 分（相較於最弱模型），而 MAGIC-Video 最多僅提升 5.50 分。這顯示 VideoJSON 能更充分地利用較強編碼模型的能力，展現出隨模型升級而持續擴展的潛力，這對未來採用更強的基礎模型特別有利。

**Q9：消融實驗揭示了哪些關鍵設計的貢獻？哪些看似有用的元件其實影響很小？**

A：消融實驗顯示，代理式程式搜尋與結構化 JSON 紀錄是效能增益的兩大主要驅動因素，缺一不可。然而，看似有用的額外元件——例如每小時摘要、額外工具、原始影片存取——對平均分數的影響均小於 1.5 分。這是一個反直覺但重要的發現：許多人直覺認為「更多資訊＝更好效能」，但實際上讓代理自由查詢結構化紀錄已足夠，額外的摘要或工具反而可能引入雜訊或分散代理注意力。此結果支持了「極簡框架」的核心主張。

**Q10：VideoJSON 適合哪些實際應用場景？**

A：VideoJSON 特別適合需要跨長時間搜尋與推理的場景，包括：終身記錄裝置（如穿戴式相機）的個人化問答、智慧家庭監控影片的事件回溯、線上課程與教學影片的長期知識萃取、直播或遊戲實況的內容審查與摘要，以及執法或醫療領域的長時間錄影分析。在這些場景中，使用者通常不會預先知道要問什麼問題，因此需要一個能靈活應對多樣查詢的系統，而非預先定義的固定檢索流程。

**Q11：若要將 VideoJSON 產品化，需要考量哪些工程與產品因素？**

A：產品化時需考量：索引建置成本（每分鐘影片需呼叫 VLM 一次，數千小時影片的預處理時間與費用）、JSON 紀錄的儲存與隱私保護（個人影片可能含敏感資訊）、查詢時的延遲（多步驟程式執行可能需數十秒）、以及代理程式的安全性（沙盒環境必須嚴格隔離，避免任意程式碼執行造成風險）。此外，使用者介面需設計成能讓非技術使用者理解代理的搜尋過程，以建立信任。從商業模式看，預處理可批次進行以降低成本，而查詢階段的算力則可依用量計費。

**Q12：VideoJSON 對學術與產業的整體影響為何？**

A：在學術上，VideoJSON 挑戰了「必須建構複雜記憶結構才能處理長影片」的傳統假設，展示了「極簡框架＋強模型」路徑的可行性，可能引發後續研究重新思考記憶體設計的必要性。其在四個基準上的顯著領先也將成為新的比較基準。在產業上，此方法降低了部署長影片問答系統的工程門檻，使中小型團隊也能基於現成的編碼代理與 VLM 快速搭建原型。微調實驗更顯示，僅需 64 筆來自不相關直播的軌跡即可提升模型在 MM-Lifelong 上 8.25 分，暗示資料效率極高，有利於快速客製化。

**Q13：VideoJSON 有哪些已知的限制？**

A：VideoJSON 的限制包括：依賴 VLM 的描述品質，若 VLM 漏掉關鍵細節則後續無法補救；每分鐘一筆的固定粒度可能不適用於所有場景（如動作極快的運動影片可能需更細粒度）；JSON 紀錄的結構化欄位需預先定義，若問題需要未涵蓋的欄位則無法表達；此外，代理在查詢時無法存取原始影片，意味著若索引階段遺漏資訊則無法回頭補救。論文中也提到「紀錄可被問題讀取的範圍受限於第 4.1 節所述」，暗示存在資訊可見性的限制。

**Q14：VideoJSON 可能會在哪些情境下失敗？**

A：VideoJSON 可能在以下情境失敗：當問題需要極度細粒度的視覺細節（如某幀中的微小文字）時，1 fps 取樣與每分鐘摘要可能遺漏；當問題需要跨多個非結構化線索進行複雜推理時，代理可能寫出低效或錯誤的程式；當 VLM 對影片內容產生幻覺或錯誤描述時，後續所有推理都會受影響；當問題涉及未在結構化欄位中預先定義的關係時，代理可能無法表達查詢。此外，若影片品質差（如低光照、模糊），VLM 的描述品質會下降，連帶影響整體效能。

**Q15：基於 VideoJSON 的成果，未來有哪些值得探索的方向？**

A：未來方向包括：動態調整紀錄粒度（依內容密度決定每筆紀錄的時間長度）、擴展結構化欄位以涵蓋更多關係類型、結合遞迴語言模型（Recursive Language Models）讓代理在查詢時也能呼叫語言模型處理子任務、研究更高效的索引方法以降低預處理成本、探索多模態紀錄（不僅文字，也保留視覺特徵供必要時查詢）、以及將此框架應用於其他長時程資料（如音訊日誌、感測器串流）。論文中展示的微調實驗也暗示，透過收集更多樣化的軌跡資料，可進一步提升小型模型的能力，使長影片問答系統更普及。

5. **教育影片與講座系列查詢**：數十小時的線上課程或學術演講錄影，學生想快速找到「教授何時講到某個定理？」「這門課中所有提到某位歷史人物的段落」。可結合 ASR 轉錄與視覺描述進行跨集數搜尋。

---

### 實作前置條件

**資料需求**
- 影片素材：至少數小時，建議數十至數百小時以發揮 ULVU 優勢；影片需切分為 60 秒片段。
- 音訊轉錄：使用 ASR 模型（如 Qwen-3-ASR）預先生成逐句轉錄，或使用資料集內建轉錄。
- 影片時序中繼資料：若為跨日影片，需有日期資訊以便代理進行跨日推理。

**運算資源**
- 索引階段：每分鐘一次 VLM 推論（1 fps 抽幀 + 文字 prompt），100 小時影片約需 6,000 次 VLM 呼叫；建議使用具批次推論能力的 VLM API。
- 查詢階段：可執行程式碼的沙盒容器（Docker 或同等隔離環境），以及具備長時程推理能力的編碼代理（建議 DeepSeek V4.1 Flash 等級以上）。
- 儲存：每分鐘 JSON 紀錄約數百 KB 至數 MB，100 小時影片約需數 GB 儲存空間。

**技能門檻**
- Python 與 Bash 程式設計（用於設計代理動作空間與除錯）。
- VLM prompt engineering（設計能產出穩定 JSON 結構的 prompt）。
- 基本的容器化與沙盒安全概念（防止代理執行惡意程式）。
- 對 JSON Schema 設計有基本理解，能根據領域需求調整欄位。

### 實作步驟建議

**步驟 1：定義 JSON Schema 與領域欄位**
從論文的通用 schema 開始（dense_caption、events、entities、places、actions、relations、unexpected、transcription、on_screen_text、mood、explanation），再依據應用場景新增領域專屬欄位。例如客服錄影可加入 `customer_id`、`issue_category`；教學影片可加入 `topic`、`difficulty_level`。

**步驟 2：影片前處理與切分**
將長影片以 60 秒為單位切分，保留時序中繼資料（clip_id、recording_id、day、start_time、end_time）。同步產生 ASR 轉錄並對齊至秒級時間戳。

**步驟 3：批次索引建立**
使用 VLM（如 Qwen-3.8-Flash-Next）對每個片段獨立產生 JSON 紀錄。建議：
- 採批次推論以降低成本。
- 設計嚴格的 JSON 格式 prompt，並加入驗證步驟（解析失敗時重試或標記）。
- 將所有紀錄存為單一 JSON Lines 檔案或輕量資料庫（如 SQLite），方便代理以程式讀取。

**步驟 4：建立沙盒執行環境**
部署 Docker 容器，提供：
- Python 3 與標準資料處理函式庫（pandas、json、re）。
- 預載入的 JSON 紀錄檔案路徑。
- 限制網路與檔案系統存取的權限控管。
- 訊息歷史採 append-only 設計（參考 mini-SWE-agent）。

**步驟 5：配置編碼代理**
設定代理的系統提示，明確告知：
- 可用動作（執行 Python / Bash）。
- 紀錄檔案位置與結構。
- 輸出格式規範（最終答案的包裝方式）。
- 禁止存取原始影片（強制僅透過 JSON 推理）。

**步驟 6：評估與迭代**
在目標領域準備小型評估集（數十題），測量：
- 答案正確率。
- 平均程式執行步驟數。
- 索引品質（人工抽樣檢查 JSON 欄位完整性）。
根據失敗案例調整 schema、prompt 或代理指令。

**步驟 7（可選）：軌跡微調**
若使用較弱的開源模型，可蒐集 64 條以上成功軌跡進行 SFT，論文中 Qwen-3.5-Flash 微調後 MM-Lifelong 分數提升達 8.25 分。

### 潛在風險與注意事項

**風險 1：VLM 產生幻覺或遺漏關鍵資訊**
緩解：在 prompt 中要求 VLM 對不確定的內容標註信心分數或留空；建立後處理驗證腳本檢查必填欄位；對關鍵應用保留原始影片存取作為 fallback。

**風險 2：索引成本過高**
緩解：先以抽樣（例如每 5 分鐘而非每 1 分鐘）建立原型驗證概念；使用較小或較快的 VLM；對靜態或重複性高的內容（如無人畫面）跳過索引。

**風險 3：代理陷入無效迴圈或產生過長程式**
緩解：設定最大步數上限；監控 token 使用量；設計明確的終止條件；對常見錯誤模式加入防護 prompt。

**風險 4：沙盒逃逸或資源耗盡**
緩解：使用成熟的容器隔離方案；限制 CPU / 記憶體 / 磁碟配額；禁止網路外連；定期審查代理生成的程式碼。

**風險 5：JSON Schema 過於僵硬或過於鬆散**
緩解：保留彈性欄位（如 `explanation`）容納長尾資訊；對核心欄位（events、entities）嚴格驗證；定期根據失敗案例演進 schema。

**風險 6：跨日推理的時序錯位**
緩解：確保 day、start_time 欄位精確；代理 prompt 中強調時區與日期格式；若資料無明確日期，考慮以相對時間（「第一個小時」「最後一個小時」）設計。

**風險 7：評估基準與真實應用落差**
緩解：論文基準（EgoLifeQA、MM-Lifelong）為第一人稱影片，企業應用可能差異極大；務必建立領域專屬評估集，避免僅依賴通用基準。

### 與其他技術的整合建議

**與向量資料庫整合（混合檢索）**
VideoJSON 本身是符號式記憶，可與向量資料庫（如 Milvus、Qdrant）並行運作：JSON 紀錄的 dense_caption 同步建立 embedding，代理可選擇以相似度檢索縮小範圍，再以程式精確過濾。這對「語意模糊但需精確時段」的查詢特別有效。

**與現有 RAG 管線整合**
將 JSON 紀錄視為文件庫，納入既有 RAG 框架（如 LangChain、LlamaIndex）的自訂檢索器。代理可在 RAG 提供的脈絡之外，視需要呼叫 VideoJSON 沙盒進行深層搜尋。

**與日曆 / CRM / 工單系統整合**
在企業場景中，可將外部結構化資料（如會議 ID、客戶編號）注入 JSON 紀錄的 metadata，使代理能跨系統關聯。例如「找出與客戶 X 所有會議中提到的承諾事項」。

**與影片理解模型整合**
若需對特定片段做細粒度視覺問答，可讓代理在 JSON 中標記候選片段，再呼叫視覺問答模型（如 GPT-4V）進行二次確認。論文的消融實驗顯示加入影片存取平均分數變化小於 1.5 分，因此僅在必要時啟用。

**與多代理架構整合**
可設計「規劃代理」負責拆解問題、「搜尋代理」負責執行程式、「驗證代理」負責檢查答案，進一步提升長時程任務的可靠性。

**與事件驅動系統整合**
將 JSON 紀錄中的 `unexpected` 或特定 `events` 觸發下游動作（如即時通知、自動標記），從被動查詢轉為主動監控。

### 給不同背景讀者的閱讀建議

**給初學者**：本文最值得學習的是「簡單勝於複雜」的設計哲學。與其花時間設計複雜的記憶圖譜或專屬工具集，不如先讓模型自己寫程式來搜尋。建議先閱讀第 3 節理解 VideoJSON 的兩階段流程，再動手用一個小型影片（如 1 小時的家庭錄影）實作原型，親身體驗「每分鐘一個 JSON + 代理寫程式」的工作流。

**給 AI 工程師**：重點關注第 3.1 節的索引設計、第 4 節的實驗配置，以及消融實驗的結論。工程上需特別注意：JSON schema 的設計直接影響代理能表達的查詢類型；沙盒環境的安全與資源限制；以及如何將通用 schema 客製化為領域專屬版本。論文中「加入 hourly summaries、extra tools、video access 平均變化小於 1.5 分」的結論，是重要的工程取捨依據——不要過度工程化。

**給研究者**：本文的核心論點是「minimal harness + strong coding agent」可超越 purpose-built memory，這對 long-context、agentic RAG、video understanding 三個社群的交界處都有啟發。建議延伸思考：此結論是否適用於音訊、程式碼、科學文獻等其他長序列領域？JSON 紀錄與程式搜尋的組合，與神經符號式（neuro-symbolic）方法的關聯為何？論文中 64 條軌跡即可微調出顯著提升的現象，也值得深入探討資料效率的理論基礎。

**給產品經理**：VideoJSON 展示了一條「低基礎建設、高模型依賴」的技術路線，這對產品決策有兩大意涵：第一，隨著編碼代理能力提升，過去需要大量工程投入的影片搜尋功能，現在可用極簡架構實現，應重新評估既有複雜管線的投資報酬率；第二，產品的差異化將更集中在「領域 schema 設計」與「評估集品質」，而非底層檢索架構。建議在產品規劃中，將「JSON schema 演進」與「領域評估集」列為核心迭代項目，並密切追蹤編碼代理模型的進展。
