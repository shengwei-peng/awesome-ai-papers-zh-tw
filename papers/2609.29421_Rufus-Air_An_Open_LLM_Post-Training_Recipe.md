## 摘要翻譯

Rufus-Air 是一個開放且可複現的後訓練配方（post-training recipe），建構於 GLM-4.5-Air-Base（106B-A12B）之上，並以八個管線階段（pipeline stage）組成串列管線（serial pipeline）：監督式微調（Supervised Fine-Tuning, SFT）、推理強化學習（Reasoning RL）、程式碼強化學習（Coding RL）、指令遵循強化學習（Instruction-Following RL）、通用代理（General Agent）、程式碼代理（Coding Agent）、搜尋代理（Search Agent），以及基於人類回饋的強化學習（Reinforcement Learning from Human Feedback, RLHF）。我們記載了複現此配方所需的資料、獎勵設計（reward design）、訓練基礎設施（training infrastructure）、階段順序（stage order）與逐階段結果（stagewise results）。各階段從基礎能力發展到進階能力，並從硬性可驗證獎勵（hard, verifiable rewards）過渡到較軟的裁判型訊號（softer judge-based signals）。訓練建立在開源元件（open-source components）與公開資料（public data）之上，其中多數資料直接採用其已釋出的原始形式，無需額外人工標註（human annotation）或內部蒸餾教師模型（in-house distillation teacher）。本研究的主要發現如下：(i) 多樣化且高品質的監督式微調（SFT）建立了穩固的能力下限（capability floor）；(ii) 難度篩選（difficulty filtering）使強化學習提示維持在有效學習範圍（productive learning range）內；(iii) 獎勵可靠性（reward reliability）為階段順序（stage order）的安排提供了實用原則；以及 (iv) 訓練基礎設施（training infrastructure）與工程選擇（engineering choices）是配方的一部分，而不只是實作細節（implementation detail）。Rufus-Air 優於 GLM-4.5-Air 官方後訓練釋出版本（official release），並與同等規模開放模型（similarly sized open models）具有競爭力。

### 核心貢獻（3～5點）
- 提出開放且可複現的後訓練配方 Rufus-Air，完整記載資料、獎勵設計、訓練基礎設施、階段順序與逐階段結果，使其他研究者能夠重現此配方。
- 設計由八個管線階段組成的串列管線，從基礎能力逐步發展至進階能力，並從硬性可驗證獎勵過渡到較軟的裁判型訊號，建立明確的階段安排原則。
- 僅使用開源元件與公開資料，其中多數資料直接採用已釋出的原始形式，無需額外人工標註或內部蒸餾教師模型，降低大型語言模型後訓練的研究門檻。
- 驗證 Rufus-Air 在效能上優於 GLM-4.5-Air 官方後訓練釋出版本，並與同等規模開放模型具有競爭力。
- 強調訓練基礎設施與工程選擇是後訓練配方不可或缺的一部分，而非僅是實作細節。

### 適合對象
本論文適合對大型語言模型後訓練、強化學習與開放可複現配方有興趣的研究人員與工程師，特別是關注階段順序安排、獎勵設計、難度篩選，以及希望在不依賴內部蒸餾教師模型或大量人工標註的情況下，建構具競爭力後訓練系統的實務工作者。對於想了解如何將訓練基礎設施與工程選擇納入配方設計的讀者，本研究亦提供了可重複使用的記載與工程經驗。

## 深度分析

#### 方法論解析

Rufus-Air（本研究提出的開放式後訓練配方）的核心方法論，是將一個開放權重基礎檢查點 GLM-4.5-Air-Base（106B-A12B 的 Mixture-of-Experts，MoE）透過八個串列管線（serial pipeline）階段，逐步轉化為具備廣泛對話、推理、程式碼與代理能力的後訓練模型。整個管線依序為：SFT（Supervised Fine-Tuning，監督式微調）→ Reasoning RL（推理強化學習）→ Coding RL（程式碼強化學習）→ Instruction-Following RL（指令遵循強化學習）→ General Agent（通用代理）→ Coding Agent（程式碼代理）→ Search Agent（搜尋代理）→ RLHF（Reinforcement Learning from Human Feedback，基於人類回饋的強化學習）。每個階段都以前一階段產出的檢查點（checkpoint）為起點，並針對特定能力與獎勵型態進行最佳化。

**1. SFT 作為能力建構階段，而非單純暖身**  
有別於常見將 SFT 視為「暖身（warm-up）」或對齊格式的做法，Rufus-Air 把 SFT 定位為能力下限（capability floor）的奠基階段。此階段使用約 9M samples、27B tokens 的多樣化公開資料，經過資料轉換（data transformations）後進行監督式微調。其目的不僅是讓模型學會對話格式，更是建立廣泛能力（broad capabilities），使後續 RL 階段只需精煉（refine）而非從零建構。這也解釋了為何後續各階段能夠在相對短的訓練時間內持續提升：模型已經具備解決問題的基礎行為，RL 只需要強化特定維度。

**2. 難度篩選（difficulty filtering）作為自動課程**  
幾乎每個 RL 階段都採用難度篩選：剔除模型已經能輕易解決的提示（prompts），同時也剔除幾乎永遠解不出來的提示，只保留「可學習」的樣本。這個機制讓訓練聚焦於有效學習範圍（productive learning range），形成一種隱式的自動課程（automatic curriculum）。對 RL 而言，過簡的樣本浪費梯度、過難的樣本則訊號雜訊過高，因此難度篩選是穩定訓練與提升樣本效率的關鍵工程選擇（engineering choices）。

**3. 獎勵可靠性（reward reliability）決定階段順序（stage order）**  
管線順序由兩條軸線決定：能力由基礎到進階（advanced capabilities），以及獎勵由硬性可驗證（hard, verifiable rewards）走向較軟的裁判型訊號（softer judge-based signals）與環境中介訊號。Reasoning RL 與 Coding RL 採用規則或程式執行等低雜訊驗證器，因此最先執行；General Agent、Coding Agent、Search Agent 的獎勵來自環境互動，較易被操弄，故置於中後段；RLHF 則使用 reward model（獎勵模型）處理開放式品質，放在最後。值得注意的是，Instruction-Following RL 雖然使用 rubric-based LLM judge（基於評分表的裁判型模型），卻仍排在代理階段之前，原因是指令遵循接近模型已具備的能力，裁判可遊戲的空間較小。這說明階段順序並非單純依獎勵格式，而是依「可被獎勵駭入（reward hacking）的難易程度」來安排。

**4. 代理式強化學習（Agentic RL）與環境（environment）設計**  
General Agent、Coding Agent、Search Agent 三個階段將模型放入真實或模擬環境中進行多輪互動。為了支援這些階段，作者強調訓練基礎設施（training infrastructure）本身就是配方的一部分，包括：token-in/token-out rollouts（以 token 為單位的多輪軌跡展開）以實現 on-policy 多輪 RL；從 SFT 到代理階段一致的 chat template（對話模板）處理；能夠支撐長時間代理執行的 sandbox service（沙箱服務）；以及透過 Rollout Routing Replay（軌跡路由重播）搭配大 batch 進行穩定 RL 訓練。這些工程選擇並非單純實作細節（implementation detail），而是決定管線能否收斂的關鍵。

#### 實驗數據解讀

雖然提供的上下文未列出完整數值，但從摘要與概述可歸納出以下實驗設計與結果意涵：

**1. 評測基準（evaluation benchmarks）與對照組**  
Rufus-Air 的評估目的並非要宣稱達到最前緣（frontier）效能，而是將配方置於公開模型中進行定位。主要對照包括官方釋出版本 GLM-4.5-Air、同等規模開放模型 INTELLECT-3 與 Nemotron-3-Super，以及 Arena-Hard v2 等對話評測。此外，Tau2-Bench 與不同 user simulators（使用者模擬器）被用於評估代理能力（附錄 F），Search Agent 則有獨立的軌跡分析（trajectory analysis，附錄 E）。

**2. 主要結果（main results）的意義**  
根據 Table 1，Rufus-Air 在幾乎所有回報的基準上都優於官方 GLM-4.5-Air，唯一的例外是 Arena-Hard v2 Creative Writing。這個例外值得注意：Creative Writing 屬於開放式、主觀品質導向的任務，而 Rufus-Air 的 RLHF 階段並未引入新的人工標註（human annotation），僅使用公開資料與模型裁判，可能在主觀創意維度上略遜於經過更精細偏好對齊的官方版本。整體而言，結果顯示：一個完全基於公開資料、無內部蒸餾教師模型（in-house distillation teacher）的配方，已能達到與同等規模開放模型競爭的水準。

**3. 逐階段結果（stagewise results）的解讀**  
Table 2 應呈現每個階段相對於其起點檢查點的表現變化。由於每個後續階段都會更新相同參數，作者並未假設「先訓練的能力會被保護」，而是直接測量「從該階段起點到終點」的進步。這種評估方式更貼近真實訓練動態：若某階段相對起點提升，代表該階段的資料與獎勵設計確實有效；若下降，則可能出現災難性遺忘或獎勵駭入。從論文結論推測，SFT 提供了強大的能力下限，Reasoning RL 與 Coding RL 在可驗證獎勵下穩定提升，IF RL 改善指令遵循，三個 Agent 階段逐步建立工具使用與規劃能力，最後 RLHF 進行偏好對齊。

**4. 資料與運算資源規模（compute footprint）**  
SFT 使用 9M samples / 27B tokens，RL 階段在 8–32 個節點上執行（Table 16）。對於一個 106B-A12B 的 MoE 模型而言，這樣的運算資源規模雖仍不小，但已低於許多前沿實驗室（frontier labs）的後訓練成本，使外部研究團隊有機會複現。

#### 與現有研究的比較

**1. 相對於 Tülu 3 等開源後訓練配方**  
作者明確將 Tülu 3 列為少數詳細記載後訓練細節的例外。Rufus-Air 與 Tülu 3 同樣強調可複現配方（reproducible recipe），但 Rufus-Air 更進一步將重點放在「階段順序由獎勵可靠性決定」以及「代理式 RL 環境的工程細節」。Tülu 3 提供了廣泛的 SFT 與 RL 資料混合策略，而 Rufus-Air 則以串列管線展示如何從基礎能力逐步過渡到進階代理能力，並詳細說明每個階段的獎勵設計與難度篩選。

**2. 相對於官方 GLM-4.5-Air**  
Rufus-Air 在絕大多數基準上超越官方 GLM-4.5-Air，這具有重要意義：官方版本通常擁有專有資料、人工標註與內部蒸餾教師模型，而 Rufus-Air 僅使用公開資料與開源元件。這說明後訓練的「配方設計」——包括階段順序、獎勵設計與基礎設施——對最終效能的影響可能不亞於資料來源本身。

**3. 相對於 INTELLECT-3 與 Nemotron-3-Super**  
Rufus-Air 與這些同等規模開放模型具有競爭力（competitive with）。這顯示在 100B 級 MoE 模型上，透過系統化的後訓練管線，可以在不仰賴閉源資料或教師模型的情況下，達到與其他頂尖開源模型相近的表現。

**4. 限制與待釐清之處**  
首先，作者坦承部分結論來自訓練經驗（training experience）而非完整消融實驗（full ablations），因此某些設計選擇（如確切的階段順序、各階段資料比例）的最適性仍需更多實證。其次，串列管線雖然簡潔，但每個後續階段都可能覆寫（overwrite）前面階段學到的行為，作者也明確指出「此順序不保護早期獲得的能力」。第三，雖然獎勵可靠性原則降低了 reward hacking 風險，但 judge-based 與 environment-mediated 獎勵仍可能被模型找到漏洞，尤其是在 Search Agent 這類開放網路環境中。最後，Creative Writing 的落後暗示在開放式、主觀品質任務上，缺乏新的人工標註可能會成為瓶頸。

#### 可重現性評估

**1. 開源元件與公開資料**  
Rufus-Air 強調其配方完全建立在開源元件與公開資料之上：訓練框架使用 Slime，推論與服務使用 SGLang（後者原生支援 GLM 系列），基礎模型為公開權重的 GLM-4.5-Air-Base。資料方面，作者使用大量已釋出的公開資料，並透過資料轉換產生訓練樣本，未進行新的人工標註，也未使用內部蒸餾教師模型。這大幅降低了研究門檻（barrier to research）。

**2. 文件與附錄的完整性**  
本報告介於研究論文與工程經驗報告（engineering experience report）之間，提供了相當詳細的紀錄：附錄 A 說明貢獻（contributions）；附錄 B 列出訓練設定（training configurations）；附錄 C 提供資料表與範例轉換（data tables and example transformations）；附錄 D 解釋如何閱讀公開基線數值（public baseline numbers）；附錄 E 與 F 則分別針對 Search Agent 與 Tau2-Bench 進行軌跡分析與使用者模擬器比較。這些附錄對於想要複現或改進配方的團隊極具價值。

**3. 運算資源的可及性**  
作者指出 RL 階段可在 8–32 個節點上執行，對於一個 106B-A12B 的 MoE 模型來說，這樣的運算資源規模雖非個人研究者可負擔，但已屬於學術界與中小型研究團隊可觸及的範圍，遠低於前沿實驗室的典型後訓練成本。

**4. 可重現性的潛在缺口**  
儘管配方記載詳盡，最終模型權重與完整訓練程式碼是否一併釋出，在提供的上下文中並未明確說明。若僅有報告而無可下載的檢查點與腳本，外部團隊仍需根據描述自行實作，這會在環境設定（尤其是 sandbox service 與代理環境）上帶來相當大的重現挑戰。因此，可重現性在「方法論層面」已相當高，但在「一鍵重現」層面仍取決於作者是否釋出完整 artifacts。

#### 未來研究方向

**1. 階段順序與管線結構的消融**  
未來可進行系統性的消融實驗，驗證「獎勵可靠性決定階段順序」這一原則是否為最適策略。例如，比較串列管線與部分並行管線、在不同階段間插入彈性回退（rollback）機制以保護早期能力，或探索「能力保護正則化」來減少後期階段對前期能力的覆寫。

**2. 更精細的難度篩選與自動課程**  
目前的難度篩選主要基於模型在提示上的通過率。未來可引入學習式難度估計器（learned difficulty estimator）或動態課程，根據訓練過程中的學習進度即時調整提示集合，進一步提升樣本效率。

**3. 獎勵設計的強化**  
對於 judge-based 與 environment-mediated 獎勵，未來可研究更強健的獎勵模型、對抗式裁判校準（adversarial judge calibration），或結合多個異質驗證器以降低 reward hacking 風險。特別是在 Search Agent 與 Coding Agent 等開放環境中，設計不易被操弄的獎勵仍是核心挑戰。

**4. 擴展至多模態與更長脈絡的代理任務**  
Rufus-Air 目前聚焦於文字推理、程式碼與搜尋代理。未來可將相同配方擴展至多模態輸入、更長脈絡的多輪對話，以及需要與真實世界 API 長期互動的複雜代理任務。

**5. 人工標註與無標註方法的權衡**  
雖然 Rufus-Air 證明無新人工標註也能達到競爭力，但 Creative Writing 的落後顯示主觀品質任務可能仍需某種形式的偏好資料。未來可探索「低成本偏好收集」策略，例如社群回饋、合成偏好資料，或與模型自動評估相結合的半監督 RLHF。

**6. MoE 模型的後訓練特異性**  
GLM-4.5-Air-Base 是 MoE 架構，未來可深入研究 MoE 在後訓練中的行為，例如專家活化分佈如何隨不同 RL 階段改變、路由穩定性對長軌跡學習的影響，以及針對稀疏啟動參數的最佳化策略。

**7. 開放式評估與軌跡分析**  
未來可建立更標準化的代理軌跡資料集與評估協議，讓不同團隊能夠比較代理行為的細微差異，而不僅是依賴最終答案正確率。這將有助於理解模型在 General Agent、Coding Agent 與 Search Agent 階段究竟學到了什麼規劃與工具使用策略。

## 論文問答

**Q1：Rufus-Air 試圖填補什麼樣的研究缺口？現有的後訓練文獻為何不足？**

A：雖然開放權重的基礎檢查點已經大幅降低後訓練研究的門檻，但大多數團隊公布的後訓練細節仍然相當單薄，往往更像系統卡而非可複現的配方。Rufus-Air 針對這個問題，提供了一份從資料、獎勵設計、基礎設施到階段順序與逐階段結果的完整記載。這份配方完全建立在開源元件與公開資料之上，讓非前沿實驗室的團隊也能重現並進一步發展。

**Q2：為什麼「可複現性」對後訓練研究很重要，Rufus-Air 又是如何確保可複現性的？**

A：可複現性是科學進展的基石，但許多頂尖模型的後訓練流程依賴內部蒸餾教師模型、未公開資料或大量人工標註，使外部研究者難以驗證或延伸。Rufus-Air 不使用新的內部蒸餾教師模型，也不引入額外的人工標註，而是直接運用公開資料與開源工具鏈。此外，其運算資源規模小到足以讓一般研究團隊負擔，從而讓整份配方真正可被重現。

**Q3：作者為何選擇 GLM-4.5-Air-Base 作為起點，而不是其他開源基礎模型？**

A：GLM-4.5-Air-Base 的權重對外開放，且其 MoE 架構具有 106B 總參數與 12B 啟動參數，能讓 RL 階段在 8 到 32 個節點上實際執行。同時，它與 Slime 訓練框架以及 SGLang 推論引擎原生相容，減少了工程整合的障礙。作者保留基礎模型的架構、分詞器與原生聊天格式不做修改，使整個配方能夠專注於後訓練階段的設計與分析。

**QQ4：Rufus-Air 的整體管線包含哪些階段，為什麼採用串列而非並行的設計？**

A：完整管線依序為監督式微調、推理強化學習、程式碼強化學習、指令遵循強化學習、通用代理、程式碼代理、搜尋代理，最後是 RLHF。串列設計讓每個階段都以前一階段產生的檢查點為起點，從基礎能力逐步堆疊到進階能力。這種安排也讓獎勵類型能從硬性可驗證獎勵逐步過渡到較軟的裁判型或環境型訊號，降低後期階段對前期成果的潛在干擾。

**Q5：Rufus-Air 的四個核心設計原則是什麼？它們如何貫穿整份配方？**

A：第一，SFT 不是暖身階段，而是能力建構階段，能建立廣泛的能力下限。第二，難度篩選能將 RL 提示保留在有效學習範圍內，自動形成課程。第三，獎勵可靠性決定階段順序，越難被操控的獎勵越先訓練。第四，訓練基礎設施與工程選擇本身就是配方的一部分，而非可有可無的實作細節。

**Q6：「獎勵可靠性」如何具體影響階段順序？為什麼使用裁判的指令遵循 RL 卻能排在較前面？**

A：原則上，硬性可驗證獎勵的階段會先執行，因為它們最不容易被獎勵破解；而裁判型或環境型訊號的階段則排在後面，以縮短模型暴露在可操控獎勵下的時間。指令遵循 RL 雖然使用基於評分標準的大型語言模型裁判，但它所要求的行為與模型原本的能力非常接近，裁判被鑽漏洞的空間相對有限。因此，儘管它的獎勵形式較軟，仍然可以安排在通用代理與程式碼代理等更複雜的環境互動階段之前。

**Q7：作者使用了哪些評測基準，Rufus-Air 的主要結果如何？**

A：作者使用多項公開評測基準來定位 Rufus-Air 在同等規模開放模型中的表現，並與官方 GLM-4.5-Air 釋出版本、INTELLECT-3 與 Nemotron-3-Super 等模型比較。結果顯示，Rufus-Air 在幾乎所有報告的基準上都優於官方 GLM-4.5-Air，只有在 Arena-Hard v2 Creative Writing 上例外。整體而言，Rufus-Air 與同等規模的開放模型相比具有競爭力。

**Q8：逐階段結果揭示了哪些關鍵訓練動態？**

A：監督式微調階段建立了強大的能力下限，後續的強化學習階段更多是精煉而非從零建構能力。每個 RL 階段都會針對該階段的起點檢查點進行評估，以觀察該階段帶來的獨立貢獻。難度篩選會自動剔除模型已經會解的題目以及幾乎永遠解不出來的題目，使訓練聚焦在真正可學習的範例上。

**Q9：這份研究有進行完整的消融實驗嗎？哪些結論來自訓練經驗而非嚴格對照？**

A：作者坦承部分結論來自訓練經驗，而非完整的消融實驗，這些部分在文中會特別標示。例如，階段順序的選擇、難度篩選的具體門檻，以及基礎設施細節如 token-in/token-out rollouts、聊天模板一致性、長時間代理執行的沙盒服務，還有透過 Rollout Routing Replay 實現的大批量穩定 RL，都帶有濃厚的工程經驗色彩。這也反映了後訓練研究不僅是演算法設計，更是一連串必須反覆調校的工程決策。

**Q10：Rufus-Air 最終能應用在哪些實際場景？**

A：經過八個階段訓練後的模型同時具備數理推理、競技程式設計、精確指令遵循、通用工具使用、軟體工程任務、開放網頁搜尋以及偏好對齊的開放式生成能力。這些能力可支撐程式碼輔助助手、研究代理、客戶服務機器人與複雜任務規劃系統等應用。由於配方完全公開，產品團隊可以根據自身需求調整資料與階段順序，打造特定領域的專用模型。

**Q11：在產品化與工程部署上，Rufus-Air 特別強調哪些考量？**

A：作者明確指出基礎設施與工程選擇是配方的一部分，而非單純的實作細節。關鍵包括從 SFT 到代理階段都保持一致聊天模板、支援多輪 on-policy RL 的 token-in/token-out rollouts、能穩定執行長時間代理任務的沙盒服務，以及利用 Rollout Routing Replay 維持大批量 RL 的穩定性。這些設計直接影響訓練能否收斂，以及最終模型在真實互動環境中的可靠性。

**Q12：Rufus-Air 對整個大型語言模型後訓練領域可能帶來什麼影響？**

A：它提供了一份可重複使用的完整記載，讓其他研究團隊能夠在此基礎上複製、修改與比較，提升領域的透明度。它也證明在不依賴內部蒸餾教師模型或新的人工標註下，仍能透過公開資料與開源元件建立具有競爭力的模型。這有助於降低後訓練研究的進入門檻，並促進更多樣化的開源模型發展。

**Q13：作者承認了哪些限制？**

A：首先，部分結論來自訓練經驗而非嚴格的消融實驗，因此無法保證階段順序或資料比例已達最佳。其次，串列管線意味著後期階段會更新相同參數，可能覆蓋或削弱前期階段的部分成果。最後，雖然運算規模相對 frontier labs 較小，但對於資源極度有限的團隊而言，106B-A12B 的 MoE 模型仍需要可觀的硬體投入。

**Q14：Rufus-Air 在訓練與部署中可能出現哪些失敗案例或風險？**

A：即使透過階段順序與難度篩選來降低風險，較軟的裁判型或環境型獎勵仍可能被模型找到漏洞進行獎勵破解。代理階段高度依賴沙盒與環境的穩定性與真實性，若環境設計有偏誤，模型可能學到不符合現實的策略。此外，基於大型語言模型裁判的訊號可能帶有裁判模型自身的偏好或偏見，進而影響最終對齊結果。

**Q15：未來可以朝哪些方向延伸或改進 Rufus-Air？**

A：未來可以探索並行或交錯式階段訓練，以縮短管線長度並減少後期覆蓋前期的風險。自動化獎勵驗證與更強大的難度篩選演算法也值得深入研究，以進一步降低對人工設計的依賴。此外，將配方擴展到多語言、多模態任務，或針對更小規模模型與不同基礎模型進行系統性消融，都是具有潛力的後續方向。

## 實務應用指南

### 適用場景

1. **企業級軟體工程代理**：利用 Coding RL 與 Coding Agent 階段，將模型部署為可執行單元測試、除錯、重構與小型功能開發的程式碼代理，並在沙箱環境中反覆驗證。
2. **具工具使用能力的客戶服務代理**：結合 General Agent 與 Search Agent，讓模型能查詢內部知識庫、呼叫訂單或票務 API，並在多輪對話中維持指令狀態。
3. **STEM 教育與數學輔導系統**：透過 Reasoning RL 強化數學、科學與邏輯推理能力，並以可驗證獎勵確保答案正確性。
4. **高合規要求的內容生成**：運用 Instruction-Following RL 提升對格式、長度、引用與禁止事項等精確約束的遵循度，適用法律、醫療或金融文件草稿。
5. **研究助理與開放問答**：整合 Search Agent、Coding Agent 與 Reasoning RL，讓模型能搜尋網路、執行程式碼並綜合資訊回答複雜問題。

---

### 實作前置條件

**資料**
- 可取得並整理多樣化公開資料作為 SFT 基礎（論文使用約 900 萬樣本、270 億 token），並具備資料轉換與品質篩選能力。
- 針對各 RL 階段準備可驗證獎勵：數學與程式題的標準答案、單元測試、規則檢查器；IF RL 需要評分標準（rubric）與裁判模型；Agent 階段需要環境、使用者模擬器與軌跡評分機制。
- RLHF 階段需要偏好資料或訓練好的獎勵模型。

**運算資源**
- 基礎模型為 GLM-4.5-Air-Base（106B-A12B MoE），SFT 與 RL 階段建議具備多節點 GPU 叢集；論文中 RL 階段使用 8–32 節點。
- 需要穩定的推論服務以產生 on-policy rollout，並支援長軌跡與多輪互動。

**技術能力**
- 熟悉大型語言模型後訓練流程（SFT、RL、RLHF）。
- 具備分散式訓練與推論調校經驗，能使用 Slime、SGLang 等開源元件。
- 能設計與維護沙箱環境、工具 API 與獎勵驗證器。
- 具備軌跡分析、獎勵駭入偵測與評測基準建置能力。

### 實作步驟建議

1. **建立基礎環境**
   - 載入 GLM-4.5-Air-Base，確認 tokenizer、chat template 與模型架構維持一致。
   - 部署 Slime 訓練框架與 SGLang 推論服務，確保 SFT 到 Agent 階段使用相同的對話格式。

2. **執行監督式微調（SFT）**
   - 整理多樣化且高品質的公開資料，進行必要的資料轉換。
   - 訓練 SFT 檢查點，建立廣泛能力下限與穩定輸出格式。

3. **進行可驗證獎勵的 RL**
   - **Reasoning RL**：使用數學與 STEM 題目，搭配標準答案驗證器，並透過難度篩選保留模型可學習的題目。
   - **Coding RL**：使用競技程式題目與單元測試，同樣進行難度篩選，避免過簡或過難的樣本。

4. **強化指令遵循能力**
   - **Instruction-Following RL**：建立 rubric-based 裁判模型，評估模型對格式、約束與多輪指令的遵循度。
   - 雖使用裁判型訊號，但因任務接近模型既有能力，較不易被獎勵駭入。

5. **加入代理式能力**
   - **General Agent**：在支援工具呼叫的環境中訓練規劃與工具使用。
   - **Coding Agent**：連接可執行程式碼的沙箱，訓練軟體工程任務的長軌跡互動。
   - **Search Agent**：在開放網路搜尋環境中訓練資訊檢索與綜合能力。
   - 每個 Agent 階段都應實作難度篩選與軌跡評估。

6. **進行 RLHF**
   - 使用偏好資料或獎勵模型進行最後對齊，改善開放式生成品質與風格。

7. **評估與迭代**
   - 在每個階段結束後與該階段起始檢查點比較，監控能力保留與提升。
   - 在公開評測基準與自有領域測試上驗證，再根據結果調整資料、獎勵與階段順序。

8. **部署與監控**
   - 將最終檢查點部署至推論服務，建立軌跡記錄、獎勵分數與輸出品質監控。

### 潛在風險與注意事項

| 風險 | 說明 | 因應方式 |
|---|---|---|
| **獎勵駭入（Reward Hacking）** | 模型可能利用裁判型或環境獎勵的漏洞取得高分，而非真正完成任務。 | 先執行可驗證獎勵階段，再進入較軟的裁判型訊號；限制 RL 步數；加入規則檢查與人工軌跡審查。 |
| **災難性遺忘** | 後期階段可能削弱前期建立的能力。 | 每個階段結束後測量相對於起始檢查點的表現；必要時混入保留資料或 replay。 |
| **Agent 軌跡不穩定** | 長軌跡容易因環境或工具回傳錯誤而中斷。 | 使用 token-in/token-out rollout、穩定沙箱服務、大 batch 與 Rollout Routing Replay 提升穩定性。 |
| **資料污染** | 公開資料可能與評測基準重疊，導致分數高估。 | 除了公開基準，另建置領域專屬的 held-out 測試集。 |
| **運算成本失控** | 無篩選地訓練過簡或過難樣本會浪費大量資源。 | 嚴格執行難度篩選，只保留模型處於「可學習範圍」的提示。 |
| **過度依賴公開資料品質** | 公開資料未經整理可能導致 SFT 基礎薄弱。 | 投入資料清理、去重與轉換，必要時補充領域資料。 |

### 與其他技術的整合建議

- **RAG 與向量資料庫**：Search Agent 可與企業內部向量資料庫或網路搜尋 API 整合，彌補基礎模型知識截止問題。
- **CI/CD 與程式碼沙箱**：Coding Agent 可嵌入 GitHub Actions、GitLab CI 或容器化測試環境，自動執行單元測試與靜態分析。
- **企業工具 API**：General Agent 可透過標準化工具描述（如 OpenAPI、MCP）連接 CRM、ERP、票務系統。
- **推論與監控服務**：部署時使用 SGLang 或 vLLM 加速推論，並搭配軌跡記錄、獎勵分數與輸出品質監控。
- **安全護欄（Guardrails）**：在 RLHF 後額外加入輸入輸出過濾、事實查核與拒答策略，降低幻覺與不當輸出風險。
- **持續學習管線**：將線上回饋與失敗案例回流至下一輪 SFT 與 RLHF，形成迭代改進迴路。

### 給不同背景讀者的閱讀建議

**初學者**：先從第 2 章的管線概覽與圖 1 開始，理解「SFT → 可驗證 RL → Agent → RLHF」的整體順序與每個階段的目標；技術細節可先略讀，把重點放在「為什麼要這樣安排階段」以及「難度篩選」與「獎勵可靠性」這兩個核心概念。

**AI 工程師**：建議深入第 3 章各階段的資料與獎勵設計、第 4 章的訓練基礎設施，以及附錄的訓練設定；特別留意 chat template 一致性、token-in/token-out rollout、沙箱穩定性與 Rollout Routing Replay 等實作細節，這些往往是複現成功與否的關鍵。

**研究人員**：重點閱讀第 2.1 節的階段順序論證、第 3 章的難度篩選機制與獎勵可靠性原則，並思考這些設計是否可遷移至其他基礎模型或任務；第 6 章的討論與未完整消融的結論也值得作為後續研究方向。

**產品經理**：聚焦適用場景、運算資源規模、主要結果與風險章節；理解每個階段對應的產品能力（例如 Coding Agent 對應軟體開發輔助、Search Agent 對應開放問答），並評估所需的資料、基礎設施與維護成本。
