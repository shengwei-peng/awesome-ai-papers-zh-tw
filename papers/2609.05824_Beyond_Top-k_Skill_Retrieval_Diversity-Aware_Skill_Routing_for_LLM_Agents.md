## 摘要翻譯

大型語言模型（Large Language Model, LLM）代理日益依賴外部技能，然而在大型技能註冊表（Skill Registry）中為使用者請求進行路由極具挑戰性，因為許多技能在功能上冗餘，而複雜任務通常需要互補的技能組合。現有的技能路由器（Skill Router）通常根據查詢相關性（Query Relevance）獨立地對候選技能（Candidate Skill）進行排序，這可能會將上下文預算（Context Budget）浪費在冗餘技能上。我們提出多樣性技能路由（Diverse Skill Routing, DSR），一個感知多樣性的重排序框架（Reranking Framework），使用行列式點過程（Determinantal Point Process, DPP）來平衡相關性與非冗餘性（Non-Redundancy）。DSR引入一種查詢殘差多樣性核（Query-Residual Diversity Kernel），懲罰冗餘的技能重疊（Skill Overlap），同時減少僅由共享查詢相關性所引起的懲罰。在SkillRouter基準（SkillRouter Benchmark）上，DSR在召回率（Recall）與完全覆蓋（Full Coverage）方面優於一個表現優異的逐點重排序（Pointwise Reranking）基準，且在多技能查詢（Multi-Skill Query）上獲得更大的提升幅度。這些結果表明，技能路由不應僅被視為相關性排序（Relevance Ranking），也應被視為互補集合選擇（Complementary Set Selection）。

### 核心貢獻（3～5點）
- **問題重新定位**：將技能路由從單純的相關性排序問題，重新定義為同時兼顧相關性與非冗餘性的互補集合選擇問題，凸顯冗餘技能對上下文預算的浪費。
- **方法創新**：提出多樣性技能路由（DSR），一個基於行列式點過程（DPP）的感知多樣性重排序框架，系統性地平衡候選技能與查詢的相關性以及候選技能之間的多樣性。
- **核函數設計**：引入查詢殘差多樣性核（Query-Residual Diversity Kernel），精準懲罰冗餘的技能重疊，同時避免因共享查詢相關性而產生的誤懲罰，提升路由訊號的鑑別力。
- **實驗驗證**：在SkillRouter基準上，DSR於召回率與完全覆蓋兩項指標上均超越強力的逐點重排序基準，且在多技能查詢上展現更顯著的增益，證明多樣性考量對組合任務尤為關鍵。
- **實務啟示**：研究結果鼓勵實務界在建構基於技能的代理（Skill-Based Agent）時，將技能選擇（Skill Selection）視為集合層級的決策，而非逐點檢索（Pointwise Retrieval）的獨立排序。

### 適合對象
- 研究LLM代理架構、工具使用系統（Tool-Use System）與代理框架（Agent Framework）的學者與工程師。
- 從事檢索增強生成（RAG）、重排序（Reranking）與Top-k檢索（Top-k Retrieval）演算法設計的研究人員。
- 關注技能庫（Skill Library）設計、技能註冊表（Skill Registry）管理與技能池（Skill Pool）優化的實務開發者。
- 對組合任務（Compositional Task）、多步驟工作流程（Multi-Step Workflow）規劃與資訊擷取（Information Extraction）感興趣的NLP/AI研究者。
- 需要在有限上下文窗口（Context Window）內高效整合外部API（External API）與程序性知識（Procedural Knowledge）的AI系統設計者。

## 深度分析

#### 方法論解析

本文提出多樣性技能路由（Diverse Skill Routing, DSR），其核心目標是解決大型技能註冊表（skill registry）中的冗餘選擇問題。整體方法論可從三個層次進行剖析：

**1. 問題重新定義（Problem Reformulation）**

傳統的技能路由將技能選擇視為逐點檢索（pointwise retrieval）問題——每個候選技能（candidate skill）獨立地根據查詢相關性（query relevance）評分，最終返回 top-k 結果。然而，本文論證這種框架在組合任務（compositional task）場景下存在結構性缺陷：當一個使用者請求需要多個互補技能時（如文件解析、資訊擷取、資料轉換、視覺化），獨立評分容易導致候選清單（shortlist）內部冗餘——多個功能相似的技能獲得高分，而真正互補的技能被擠出 top-k。這不僅浪費有限的上下文預算（context budget），更削弱了代理（agent）覆蓋多步驟工作流程（multi-step workflow）的能力。

因此，作者將技能路由重新定位為「互補集合選擇」（complementary set selection）問題：選出的技能集合不僅要個體相關，還必須相互非冗餘（non-redundant）。

**2. 行列式點過程（DPP）框架的引入**

行列式點過程（Determinantal Point Process, DPP）為子集選擇提供了機率論基礎，其核心特性是傾向於選擇「高品質且多樣」的子集。DPP 的機率與子集對應的核矩陣（kernel matrix）行列式成正比，因此當兩個項目相似時，其對應的核矩陣行列式下降，機率被自動壓低。

然而，直接將 DPP 應用於技能路由存在一個關鍵挑戰：兩個技能可能相似，原因有二——（a）它們功能冗餘（真正的問題），或（b）它們都與同一查詢相關但覆蓋任務的不同面向（不應被懲罰）。若對所有相似度一視同仁地懲罰，會誤刪有用的互補技能。

**3. 查詢殘差多樣性核（Query-Residual Diversity Kernel）——核心創新**

這是本文最具技術深度的貢獻。其數學直覺如下：

- 令 $q$ 為查詢表示，$s_i, s_j$ 為兩個技能的表示。
- 標準 DPP 核函數會計算 $s_i$ 與 $s_j$ 的整體相似度，無法區分「冗餘相似」與「查詢誘導相似」。
- 查詢殘差核函數先將每個技能表示投影到與查詢正交的子空間（即「殘差」），再計算殘差之間的相似度。

形式上，若技能表示可分解為 $s_i = \alpha_i q + r_i$（其中 $r_i$ 為與 $q$ 正交的殘差分量），則核函數僅基於 $r_i$ 與 $r_j$ 計算。這種設計的精妙之處在於：兩個技能即使都與查詢高度相關，只要它們覆蓋任務的不同面向，其殘差分量就會正交，相似度懲罰被自動降低；反之，若兩個技能本質上是近重複（near-duplicate），其殘差分量仍高度相似，懲罰依然生效。

**4. 整體管線（Pipeline）**

DSR 採用標準的 retrieve-and-rerank 架構：
1. **檢索階段（Retrieval）**：由基礎檢索器產生候選技能集合。
2. **品質評分（Quality Scoring）**：品質模型為每個候選技能產生查詢依賴的相關性分數。
3. **DPP 重排序（DPP Reranking）**：以品質分數作為對角項、以查詢殘差核函數作為非對角項，構造核矩陣，運行 DPP 推理選出最優子集。
4. **最終排序（Final Ordering）**：選出的技能按品質分數排序，產生最終的候選清單。

這種兩階段設計使得 DSR 可與任何現有的檢索器與品質模型組合，具有良好的模組化特性。

#### 實驗數據解讀

**1. 評估基準（Evaluation Benchmark）**

實驗在 SkillRouter 基準上進行，該基準包含約 80,000 個候選技能，並區分單技能查詢（single-skill query）與多技能查詢（multi-skill query）。這一規模顯著大於多數工具學習（tool learning）研究中的 API 數量，更貼近實際部署場景。

**2. 評估指標（Metrics）**

- **召回率（Recall）**：衡量返回的技能集合中包含多少真實相關技能。
- **完全覆蓋（Full Coverage）**：更嚴格的指標，要求返回的技能集合完整覆蓋查詢所需的所有技能。對於多技能查詢，這是衡量「集合完整性」的關鍵指標。

**3. 主要結果（Main Results）**

相較於一個強力的逐點重排序（pointwise reranking）基線（即 SkillRouter 本身），DSR 在以下維度展現優勢：

- **整體提升**：在召回率與完全覆蓋兩個指標上均優於基線。
- **多技能查詢增益更大**：這是最重要的發現——DSR 的設計初衷正是針對多技能場景，實驗結果驗證了這一假設。在多技能查詢上，DSR 的相對增益顯著高於單技能查詢，說明感知多樣性（diversity-aware）的設計在組合任務中價值最大。
- **較大切割數（cutoff）下增益放大**：當允許返回更多技能時（如 top-10 而非 top-3），DSR 的優勢更明顯。這暗示在嚴格的 top-k 限制下，冗餘問題更突出，多樣性約束的邊際效益更高。

**4. 消融實驗（Ablation Studies）**

作者進行了關鍵的消融實驗：將查詢殘差核函數替換為標準的技能間相似度核函數。結果顯示，多技能完全覆蓋率大幅下降。這直接證明了查詢殘差設計的必要性——若不區分「冗餘相似」與「查詢誘導相似」，標準 DPP 會過度懲罰互補但都相關的技能，反而損害集合完整性。

**5. 結果的深層意涵**

實驗數據揭示了一個重要的系統設計原則：在大型技能註冊表中，技能路由不應僅追求「找到最相關的技能」，更應追求「找到最相關且互補的技能集合」。這是一個從「點估計」到「集合估計」的範式轉變，與資訊檢索領域從 BM25 到神經排序、再到多樣性感知排序的演進軌跡一致。

#### 與現有研究的比較

**1. 與工具學習（Tool Learning）研究的關係**

本文與 Toolformer、HuggingGPT、ToolLLM 等工具使用系統共享同一問題空間，但定位不同：
- **Toolformer**（Schick et al., 2023）專注於教導模型「何時」與「如何」呼叫 API。
- **HuggingGPT**（Shen et al., 2023）將 LLM 作為控制器，分解任務並選擇專家模型。
- **ToolLLM**（Qin et al., 2023）將工具學習擴展到數千個真實 API。
- **Voyager**（Wang et al., 2023）研究具身代理（embodied agent）如何隨時間成長可執行技能庫。

這些工作均未直接處理「從極大規模技能庫中選擇非冗餘子集」的問題。DSR 填補了這一空白，特別是在技能庫規模達到數萬級時的路由問題。

**2. 與技能評估研究的關係**

- **SkillRouter**（Zheng et al., 2026）建立了 80K 規模的技能選擇基準，並證明完整技能實作（skill implementation）比名稱與描述包含更豐富的路由訊號（routing signal）。DSR 直接建立在該基準之上，但改變了選擇目標——從「逐點相關性」轉向「集合多樣性」。
- **SkillsBench**（Li et al., 2026）評估策展技能（curated skills）對下游代理效能的影響，發現效益高度依賴任務與技能品質。DSR 與此互補：SkillsBench 回答「技能是否有用」，DSR 回答「如何選擇有用的技能集合」。

**3. 與 LLM 路由（LLM Routing）研究的關係**

FrugalGPT 等成本感知路由系統關注如何在異質模型間分配請求以平衡成本與效能。DSR 與此平行但目標不同：DSR 不路由到不同 LLM，而是路由到不同技能模組。兩者共享「在大型選項空間中做明智選擇」的核心理念，但 DSR 引入的多樣性約束在 LLM 路由中較少被強調。

**4. 與多樣性感知檢索（Diversity-Aware Retrieval）的關係**

DPP 在文檔檢索、推薦系統、摘要生成中已有廣泛應用，但本文的貢獻在於識別出技能路由的特殊性：技能相似度具有「雙重來源」（冗餘 vs. 查詢相關），並提出查詢殘差核函數作為解決方案。這是一個領域特定的創新，而非 DPP 的通用改進。

**5. 局限性（Limitations）**

- **依賴外部品質模型**：DSR 的效能上限受品質模型準確度限制。若品質模型無法區分真正相關與不相關的技能，DPP 也無法挽救。
- **核函數設計的假設**：查詢殘差假設技能表示可線性分解為查詢相關與查詢正交分量，這在某些表示空間中可能不成立。
- **計算成本**：DPP 推理涉及行列式計算，雖然對於典型 top-k（如 k=10）規模可行，但若候選池極大或 k 很大，計算成本可能成為瓶頸。
- **缺乏下游代理效能評估**：實驗主要在路由層面（召回率、完全覆蓋）評估，未直接測量所選技能集合在實際代理執行任務中的端到端表現。

#### 未來研究方向

**1. 端到端代理效能評估（End-to-End Agent Evaluation）**

當前評估集中在路由層面的召回率與完全覆蓋，未直接測量所選技能集合在實際代理執行任務中的表現。未來工作可設計實驗，將 DSR 選出的技能集合注入實際代理框架，測量任務完成率、步驟效率、錯誤率等下游指標。這將驗證「更好的路由是否真的帶來更好的代理效能」這一核心假設。

**2. 動態技能註冊表（Dynamic Skill Registries）**

當前實驗假設技能註冊表是靜態的，但實際系統中技能會被新增、修改、刪除。未來可研究：
- 增量 DPP 更新：當技能庫變化時，如何高效更新核矩陣。
- 技能生命週期管理：如何識別應淘汰的低品質或過時技能。

**3. 多模態技能擴展（Multimodal Skill Extension）**

當前技能主要為文字與程式碼形式，未來可擴展至多模態技能（圖像、音訊、影片）。這對核函數設計提出新挑戰：如何在不同模態間定義有意義的「冗餘」與「互補」概念。

**4. 學習式核函數（Learned Kernels）**

當前的查詢殘差核函數是手工設計的。未來可探索：
- 從資料中學習核函數參數。
- 使用神經網路參數化核函數，使其能適應不同任務領域。
- 元學習（meta-learning）方法，使核函數能快速適應新技能庫。

**5. 與代理規劃的聯合最佳化（Joint Optimization with Agent Planning）**

技能路由與任務規劃（task planning）通常是分離的兩個階段。未來可探索聯合最佳化框架：代理在規劃任務分解時，同時考慮技能路由的多樣性約束，使兩者協同決策。

**6. 理論分析（Theoretical Analysis）**

DPP 在技能路由中的理論保證尚未充分探索。未來可研究：
- 在何種條件下，查詢殘差核函數優於標準核函數的理論邊界。
- DPP 子集選擇的樣本複雜度（sample complexity）分析。
- 與資訊理論的連結：多樣性約束是否對應於資訊瓶頸（information bottleneck）原則。

**7. 跨語言與跨領域泛化（Cross-Lingual and Cross-Domain Generalization）**

當前實驗在英文 SkillRouter 基準上進行，未來可探索：
- 在中文等多語言技能庫上的表現。
- 在特定領域（如醫療、法律、程式設計）的技能路由效能。
- 跨領域遷移能力。

**8. 與檢索增強生成（RAG）的整合（Integration with RAG）**

技能路由與 RAG 共享「從大型外部知識庫選擇相關內容」的核心問題。未來可探索統一的框架，將技能、文件、工具視為同一外部資源空間的不同類型，並設計通用的多樣性感知選擇機制。

**9. 人類偏好對齊（Human Preference Alignment）**

當前評估指標（召回率、完全覆蓋）是代理指標，未必完全對齊人類偏好。未來可收集人類標註，評估所選技能集合是否符合人類對「有用且互補」的直覺，並將人類反饋整合到路由決策中。

**10. 可解釋性與除錯（Interpretability and Debugging）**

當代理選擇了錯誤的技能集合時，如何診斷問題？未來可開發視覺化工具，展示 DPP 核矩陣的結構，幫助開發者理解為何某些技能被選中或排除，從而改進技能庫設計。

## 論文問答

**Q1：為什麼大型語言模型代理需要從龐大的技能註冊表中選擇技能？這個問題的核心挑戰是什麼？**

A：大型語言模型代理透過外部技能來擴展其能力，這些技能可以是工具、API、指令集或腳本等形式，使代理能夠執行超出純文字生成的任務。然而，當技能庫擴展到數千甚至數萬個技能時，不可能將所有技能都暴露給代理，因為這會受到上下文窗口的限制並分散代理的注意力。核心挑戰在於如何從龐大的技能池中精準地選擇出與用戶請求最相關且互補的子集，這就是所謂的「路由瓶頸」。這個問題的解決對於構建可擴展且實用的 LLM 代理系統至關重要，因為它直接影響代理能否在有限的上下文預算內完成複雜任務。

**Q2：現有的技能路由方法（如逐點重排序）為什麼在多技能查詢中表現不佳？**

A：現有的技能路由器通常將技能選擇視為逐點檢索或重排序問題，每個候選技能根據查詢獨立評分並選出前 k 名，這種方法對於單一技能任務是自然的，但在組合任務中卻會產生嚴重問題。具體而言，多個技能可能因描述或實作相似而獲得高分，導致返回的候選清單充滿冗餘技能；當任務需要文件解析、資訊擷取、資料轉換和視覺化等多個互補技能時，獨立評分會忽略技能間的互補性，浪費寶貴的上下文預算。因此，逐點方法無法有效區分「真正冗餘的技能」和「因共享查詢相關性而表面相似但功能互補的技能」，這正是其在多技能查詢中表現不佳的根本原因。

**Q3：為什麼技能路由應該被視為「互補集合選擇」而不僅僅是「相關性排序」？這個觀點轉變的重要性為何？**

A：將技能路由視為「互補集合選擇」意味著我們不僅要評估每個技能與查詢的相關程度，還要考慮所選技能集合作為整體是否覆蓋了任務的所有必要面向。這種觀點轉變的重要性在於它反映了真實代理任務的組合性質：許多實際任務需要多個互補技能協同工作，而非單一技能即可完成。透過強調非冗餘性，這個框架促使路由系統在有限的上下文預算內最大化技能覆蓋的多樣性，從而提升代理執行多步驟工作流程的能力。這也與感知多樣性的檢索研究趨勢一致，將路由從純粹的點對點匹配提升為結構化的集合優化問題。

**Q4：Diverse Skill Routing (DSR) 的核心方法是什麼？它如何結合相關性和多樣性？**

A：DSR 是一個基於行列式點過程（DPP）的多樣性感知重排序框架，建立在標準的「檢索-重排序」管線之上。首先，一個檢索器從大型技能池中產生候選技能，然後一個品質模型根據查詢為每個技能分配相關性分數。接著，DSR 應用 DPP 選擇來構建一個平衡相關性與非冗餘性的技能集合，其中每個技能被視為 DPP 中的「點」，而技能間的相似度則透過核函數來衡量。DPP 的數學特性使其自然地偏好高品質且彼此多樣的子集，因此能夠在保持高相關性的同時避免選擇功能重疊的技能，最終被選中的技能按其品質分數排序形成候選清單。

**Q5：什麼是「查詢殘差多樣性核」（query-residual diversity kernel）？它為什麼比標準的技能間相似度核更有效？**

A：查詢殘差多樣性核是 DSR 的關鍵創新，它在衡量技能間冗餘度時，會先從每個技能的表示中移除與查詢對齊的部分。具體而言，這個核函數測量的是「在扣除共享查詢相關性後，技能之間的剩餘相似度」，因此能夠區分真正的功能冗餘和僅僅是因共同相關性而產生的表面相似。這種設計的優勢在於：當兩個技能都與查詢相關但覆蓋任務的不同步驟時，它們的查詢對齊分量會被扣除，殘差相似度較低，因此不會被錯誤地視為冗餘；相反地，對於功能上真正重疊的技能，殘差相似度仍然很高，會受到應有的懲罰。消融研究證實，將這個核替換為標準的技能間相似度核會大幅降低多技能完全覆蓋率，凸顯了其關鍵作用。

**Q6：為什麼選擇行列式點過程（DPP）作為多樣性感知的數學工具？DPP 在這裡的優勢是什麼？**

A：行列式點過程（DPP）是一個被廣泛用於選擇高品質且多樣子集的機率模型，其數學特性使其特別適合技能路由問題。DPP 透過一個正定核矩陣來同時編碼每個項目的品質（對角元素）和項目間的相似度（非對角元素），並透過計算子集對應子矩陣的行列式來評估該子集的可能性，這個值會隨著項目品質提高和項目間多樣性增加而增大。在技能路由的應用中，DPP 提供了一個原則性的機率框架來平衡相關性和非冗餘性，避免了啟發式方法中常見的權衡困難。此外，DPP 的子集選擇問題存在有效的近似演算法，使其能夠擴展到像 SkillRouter 基準中那樣約 80K 技能的規模。

**Q7：SkillRouter 基準測試的規模和組成是什麼？為什麼選擇這個基準來評估 DSR？**

A：SkillRouter 基準測試包含約 80,000 個候選技能，是目前規模最大的技能路由評估基準之一，涵蓋了從單一技能查詢到多技能查詢的各類任務。這個基準特別強調使用完整的技能實作（包括名稱、描述、程式碼等）作為路由訊號，而不僅僅依賴簡短的元資料，這使得評估更貼近實際代理系統的需求。選擇這個基準來評估 DSR 是因為它直接針對大規模技能選擇問題，並且包含能夠凸顯多樣性重要性的多技能查詢，能夠有效展示 DSR 相對於逐點方法的優勢。此外，SkillRouter 提供了明確的評估指標（如召回率和完全覆蓋率），使得不同方法之間的比較更加公平和透明。

**Q8：DSR 在實驗中相對於強基線的關鍵結果是什麼？哪些場景的改進最為顯著？**

A：在 SkillRouter 基準上，DSR 相對於一個強大的逐點 SkillRouter 基線，在召回率和完全覆蓋率兩個指標上都取得了改進。改進最為顯著的場景包括多技能查詢和較大的截斷值（cutoff），這正是 DSR 設計目標所針對的情境：在這些場景中，傳統的逐點方法最容易因為返回冗餘技能而浪費上下文預算，而 DSR 的多樣性感知機制能夠選擇更具互補性的技能集合。這些結果驗證了「技能路由應該被視為互補集合選擇」這一核心論點，並證明了在大型技能註冊表中，相關性與多樣性的聯合優化能帶來實質性的性能提升，特別是在需要組合多個技能的複雜代理任務中。

**Q9：消融研究揭示了哪些關鍵設計選擇的重要性？查詢殘差核的具體貢獻是什麼？**

A：消融研究中最關鍵的發現是查詢殘差多樣性核的重要性：當將其替換為標準的技能間相似度核時，DSR 在多技能完全覆蓋率上的表現會大幅下降。這表明僅僅使用 DPP 框架是不夠的，核函數的設計直接決定了能否正確區分冗餘技能和功能互補的技能。標準相似度核會對所有表面相似的技能施加均勻的懲罰，這會錯誤地將那些因共享查詢相關性而相似、但實際上覆蓋任務不同面向的技能視為冗餘。查詢殘差核透過扣除查詢對齊分量，保留了對真正互補技能的識別能力，這是 DSR 能夠在多技能查詢中取得顯著改進的核心原因，也證明了「區分冗餘類型」這一設計選擇的必要性。

**Q10：DSR 在實際的 LLM 代理系統中可能應用於哪些場景？對企業級 AI 助手有何意義？**

A：DSR 在實際應用中特別適合那些需要從龐大工具庫中組合多個互補功能的複雜代理場景，例如企業級 AI 助手需要同時調用文件解析、資料轉換、視覺化和報告生成等多個工具來完成業務分析任務。在客戶支援場景中，代理可能需要結合知識庫查詢、訂單管理 API 和情緒分析工具來處理複雜的客戶請求，而 DSR 能確保這些互補技能都被納入上下文。對於企業而言，DSR 的意義在於它能夠在有限的上下文預算內最大化代理的能力覆蓋，從而提升任務完成率並降低因遺漏關鍵技能而導致的執行失敗。隨著企業內部工具和 API 數量的持續增長，這種多樣性感知的路由將成為構建高效代理系統的關鍵技術。

**Q11：從產品工程角度，部署 DSR 需要考慮哪些權衡？例如計算成本與路由品質之間的關係？**

A：從產品工程角度，部署 DSR 需要權衡的一個關鍵因素是 DPP 選擇的計算成本，特別是在技能池非常大的情況下，雖然 DPP 子集選擇有近似演算法，但仍比簡單的 top-k 排序更耗費資源。另一個權衡是檢索品質與多樣性之間的平衡：DSR 依賴一個強大的初始檢索器來產生候選集，如果檢索器遺漏了關鍵技能，後續的 DPP 重排序也無法挽回，因此需要投資於高品質的基礎檢索組件。此外，技能表示的品質也會影響 DSR 的效果，因為查詢殘差核依賴於技能和查詢的向量表示是否能夠有效區分語義相關性和功能冗餘性。產品團隊需要在這些權衡中找到適合其規模和品質需求的平衡點，並可能需要根據具體應用場景調整相關性與多樣性的權重。

**Q12：這項研究對技能路由和更廣泛的代理系統領域有何影響？它如何改變我們對代理設計的思考？**

A：這項研究對技能路由領域的影響在於它將研究焦點從「如何更好地評分單個技能」轉變為「如何選擇一個互補的技能集合」，這是一個重要的範式轉移。它促使研究者和工程師認識到，在大型技能註冊表中，僅僅追求高相關性是不夠的，還需要考慮所選技能作為整體的覆蓋能力。對更廣泛的代理系統領域而言，這項工作強調了代理設計中「集合層次優化」的重要性，這種思路可以延伸到代理工作流程設計、多代理協作和工具鏈組合等相關問題。這也與代理系統從單一模型轉向模組化、可擴展架構的趨勢一致，為未來構建能夠管理數十萬技能的代理系統提供了方法論基礎。

**Q13：這篇論文承認的限制是什麼？DPP 框架有哪些已知的計算瓶頸？**

A：雖然論文中沒有明確列出所有限制，但從方法論角度可以推斷出幾個潛在的計算瓶頸：DPP 子集選擇的精確解需要計算所有可能子集的行列式，這在技能數量很大時計算成本極高，因此實際部署中需要使用近似演算法。此外，查詢殘差核的計算需要為每對候選技能計算殘差相似度，這也會隨著候選集大小呈現二次方增長。另一個潛在限制是 DSR 依賴於高品質的技能表示和查詢表示，如果底層的編碼模型無法有效區分語義相似性和功能冗餘性，查詢殘差核的效果就會受限。論文中也未深入探討 DSR 在極大規模（如數百萬技能）或動態技能註冊表（技能持續新增和移除）中的表現，這些都是值得未來研究探索的方向。

**Q14：在什麼情況下 DSR 可能會失敗或表現不如簡單的逐點方法？**

A：DSR 在單一技能查詢中可能不會帶來顯著改進，甚至在某些邊緣情況下可能表現不如簡單的逐點方法，因為當任務只需要一個技能時，多樣性懲罰可能會干擾對最相關技能的選擇。此外，如果初始檢索器的候選集中根本沒有包含任務所需的某些關鍵技能，DSR 的重排序也無法彌補這個遺漏，因此其性能上限受限於檢索器的召回率。在技能表示品質不佳或查詢與技能之間的語義匹配模糊的情況下，查詢殘差核可能無法準確區分冗餘和互補，導致錯誤的多樣性懲罰。如果技能之間的互補性結構非常複雜（例如某些技能只有在組合時才有效），DPP 的成對相似度假設可能不足以捕捉這些高階互動，這些都是 DSR 可能失效的情境。

**Q15：未來的研究方向有哪些？這項工作如何為更通用的代理技能管理鋪路？**

A：未來的研究方向包括將 DSR 擴展到動態技能註冊表，其中技能會持續新增、更新和移除，這需要研究增量式的 DPP 更新演算法。另一個方向是探索更豐富的互補性建模，例如超越成對相似度來捕捉技能間的高階互動，這可能需要結合圖神經網路或因果推理方法。此外，將 DSR 與代理執行結果結合進行線上學習和強化學習，使路由系統能夠根據實際任務表現調整其相關性和多樣性權衡，也是重要的研究方向。這項工作還可以延伸到多代理協作場景，其中不同代理需要選擇互補的技能來共同完成任務。從更宏觀的角度看，這項工作為構建能夠自主管理數十萬技能的下一代代理系統奠定了基礎，推動代理從靜態工具使用者轉變為動態、自適應的技能組合者。

## 實務應用指南

### 適用場景

**1. 企業內部 LLM 助理的工具選擇**
大型企業常建置數千至數萬個內部 API、報表產生器、資料查詢工具。當員工透過自然語言請求「幫我整理上季華南區業績並寄給財務長」時，DSR 可避免重複選到多個相似的「業績查詢」技能，而同時納入「資料擷取」、「報表格式化」、「郵件發送」等互補技能，提升單次對話的任務完成率。

**2. 程式開發助手的函式庫/API 路由**
在大型 monorepo 或 SDK 集合（如內部 Python 工具庫）中，許多函式功能高度重疊。DSR 可協助 Cursor、Continue.dev 等 AI IDE 在面對「批次處理 CSV 並上傳到 S3」這類請求時，選出 `pandas.read_csv`、`boto3.client('s3').upload_file`、`logging` 等互補工具，而非多個變體的 CSV 讀取函式。

**3. 客戶服務代理的多步驟工單處理**
客服機器人需串接「訂單查詢」、「退款處理」、「物流追蹤」、「客戶通知」等多個技能。DSR 的查詢殘差核能避免因「退款」這個共同關鍵字而誤刪「物流追蹤」這類同樣相關但功能互補的技能，確保完整覆蓋工單處理流程。

**4. 學術研究助理的文獻與工具整合**
研究助理需同時調用「PubMed 搜尋」、「PDF 解析」、「引用格式化」、「統計分析」等技能。DSR 能在 80K 等級的技能池中，於有限的上下文窗口內挑出覆蓋整個研究工作流程的互補技能組合。

**5. 自動化資料管線（Data Pipeline）的代理編排**
在 ETL 場景中，使用者請求「從 MySQL 拉取資料、清洗、轉成 Parquet、寫入 Snowflake」。DSR 可避免重複選入多個資料庫連線技能，而同時納入清洗、轉檔、寫入等不同階段的必要技能。

### 實作前置條件

**資料需求**
- **技能註冊表（Skill Registry）**：每個技能需具備名稱、描述、完整實作（程式碼或文件），依 SkillRouter 經驗，完整實作比純名稱描述提供更豐富的路由訊號。
- **查詢-技能配對資料**：用於訓練品質模型（quality model）的逐點相關性評分；可從歷史日誌或人工標註取得。
- **多技能查詢標註**：需具備「哪些技能組合構成正解集合」的標註，用以評估完全覆蓋率（full coverage），而非僅單技能準確率。
- **嵌入模型**：用於將技能與查詢編碼為向量；可採用 BGE、E5、OpenAI text-embedding-3 等。

**計算資源**
- **GPU**：用於嵌入模型推論與品質模型評分；單張 A100/H100 足以處理 80K 技能池的批次編碼。
- **CPU 與記憶體**：DPP 的核矩陣計算涉及候選集合的 Gram 矩陣，候選數 N 建議控制在數百至數千；N 過大會使 DPP 的精確推論（MAP inference）成本急劇上升，需考慮貪婪或近似演算法。
- **向量資料庫**：Pinecone、Milvus、Qdrant 或 FAISS，用於初步候選檢索。

**技能門檻**
- 熟悉 retrieve-and-rerank 兩階段檢索管線。
- 理解 Determinantal Point Process 的基本數學（含核矩陣、子集機率分解）。
- 具備 LLM 代理框架（LangChain、AutoGen、CrewAI）的整合經驗。
- 具備評估指標設計能力（recall@k、full coverage、互補性指標）。

### 實作步驟建議

**步驟 1：盤點並標準化技能註冊表**
將內部工具、API、腳本統一抽象為「技能」結構（名稱、描述、實作、輸入輸出規格），建立可擴展的技能註冊系統。建議採用類似 Claude Skills 或 Voyager skill library 的模組化設計。

**步驟 2：建立初步檢索器（Retriever）**
使用雙編碼器（bi-encoder）對技能與查詢分別編碼，於向量資料庫中取 Top-N（例如 N=100~500）候選集合。此階段僅負責召回率，不需考慮多樣性。

**步驟 3：訓練品質模型（Quality Model）**
以交叉編碼器（cross-encoder）或 LLM-as-a-judge 為候選技能評分，輸出查詢相關性分數 $q_i$。此為 DPP 中的「品質項」。

**步驟 4：建構查詢殘差多樣性核**
對每個候選技能 $i$ 的嵌入 $\mathbf{s}_i$ 與查詢嵌入 $\mathbf{q}$，計算殘差：
$$\tilde{\mathbf{s}}_i = \mathbf{s}_i - \text{proj}_{\mathbf{q}}(\mathbf{s}_i)$$
其中 $\text{proj}_{\mathbf{q}}(\mathbf{s}_i)$ 為 $\mathbf{s}_i$ 在 $\mathbf{q}$ 方向上的投影。核矩陣元素設為 $L_{ij} = \exp(-\|\tilde{\mathbf{s}}_i - \tilde{\mathbf{s}}_j\|^2 / \sigma^2)$。此步驟是 DSR 相較標準 DPP 的核心差異。

**步驟 5：組合 DPP 核矩陣**
最終核矩陣為 $K_{ij} = q_i \cdot q_j \cdot L_{ij}$，對角線為 $q_i^2$。此矩陣同時編碼品質與去相關後的多樣性。

**步驟 6：執行 DPP 子集選擇**
於候選集合上求解 DPP 的 MAP inference（最大化 $\det(K_S)$，$S$ 為選中子集）。對大規模候選，建議使用：
- 貪婪演算法（Kulesza & Taskar, 2012）：$O(N^2 k)$，實務上常用。
- 雙重貪婪或 k-DPP：當 $N$ 極大時的近似解。

**步驟 7：以品質分數排序輸出**
DPP 選出的子集依品質分數 $q_i$ 降冪排列，作為最終送入 LLM 上下文的技能清單。

**步驟 8：建立評估管線**
採用 SkillRouter 風格的評估：對單技能查詢量測 recall@k；對多技能查詢量測 full coverage（所有必要技能皆被選入的比例）。同時監測上下文預算使用率。

**步驟 9：線上 A/B 測試與監控**
上線後監控：(a) 任務完成率、(b) 上下文 token 使用量、(c) 技能呼叫失敗率。持續收集新查詢以迭代品質模型。

### 潛在風險與注意事項

**風險 1：DPP 計算成本隨候選數平方成長**
當初步檢索的 N 過大（例如 >2000），精確 DPP 推論會變慢。**緩解**：限制 N ≤ 500，或採用 k-DPP、貪婪 DPP 等近似演算法；亦可預先以層次化分群縮小候選空間。

**風險 2：品質模型偏差導致多樣性過度補償**
若品質模型對某些技能類型系統性低估，DPP 會傾向選入「品質中等但彼此差異大」的技能，反而犧牲相關性。**緩解**：以人類標註定期校正品質模型；監控平均品質分數是否下降。

**風險 3：查詢殘差投影在小資料集上不穩定**
當查詢嵌入稀疏或技能嵌入集中在查詢方向附近時，殘差可能過小，導致多樣性懲罰失效。**緩解**：對殘差向量做 L2 正規化，並設定最小殘差範數閾值。

**風險 4：技能註冊表品質低落放大路由錯誤**
若技能描述含糊或實作過時，DSR 的多樣性機制可能選入多個低品質但「彼此不同」的技能。**緩解**：建立技能品質審核流程；對低品質技能降權或下架。

**風險 5：多技能正解集合標註成本高**
訓練與評估皆需「完整技能組合」標註，人工成本可觀。**緩解**：以 LLM 合成多技能查詢與標註，再以小樣本人工核對；採用 SkillsBench 等公開基準做標準化評估。

**風險 6：上下文預算與多樣性的權衡不易設定**
DPP 的品質-多樣性權重（核矩陣中的縮放參數）需依任務調校。**緩解**：以驗證集上的 Pareto 前緣搜尋最佳權重；提供預設值並允許 per-query 動態調整。

### 與其他技術的整合建議

**與 RAG 系統整合**
將 DSR 視為 RAG 中的「文件選擇器」：以查詢嵌入同時檢索文件與技能，DSR 統一篩選後送入 LLM。可擴展為「文件 + 技能」聯合多樣性選擇。

**與代理框架整合**
- **LangChain / LangGraph**：將 DSR 封裝為自訂 retriever tool，於 agent 決策節點呼叫。
- **AutoGen / CrewAI**：在群組代理的「技能共享池」中以 DSR 篩選，避免多個代理重複選入相同工具。
- **Claude Skills / OpenAI Assistants**：作為上層路由器，於呼叫底層技能前先做多樣性篩選。

**與向量資料庫整合**
於 Milvus/Qdrant 中預先計算技能嵌入與查詢嵌入；DPP 階段僅在記憶體中對 Top-N 候選計算核矩陣，避免重複 I/O。

**與 LLM 評分器整合**
品質分數可由 LLM-as-a-judge（如 GPT-4、Claude）批次評估產生；對延遲敏感場景，可蒸餾為小型 cross-encoder。

**與成本感知路由整合**
結合 FrugalGPT 等成本感知路由思想：在 DPP 品質項中加入技能呼叫成本因子，使選出的技能集合在滿足多樣性的同時最小化 API 費用。

**與技能版本管理整合**
當技能有多版本時，將版本視為額外維度納入嵌入空間，使 DSR 同時避免版本冗餘與功能冗餘。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）以理解「為什麼技能路由會浪費上下文預算」，特別是「多個高相關性技能其實功能重疊」這個直覺問題。接著跳到結論與應用場景，建立動機後再回頭補習「什麼是檢索」、「什麼是 rerank」。DPP 的數學可先略過，改以「選東西時不只要選好的，也要選不一樣的」這個直覺理解 DSR 的精神。

**給 AI 工程師**：重點閱讀第 3 節（Method）中的查詢殘差核設計，理解其與標準 DPP 核的差異；以及實作步驟中的「步驟 4~6」，這是工程落地核心。建議直接以 SkillRouter 基準的開源實作（若有）為起點，將雙編碼器替換為自家技能嵌入，並以內部查詢日誌做 A/B 評估。注意 DPP 的計算瓶頸，務必準備近似演算法作為 fallback。

**給研究者**：本文的核心貢獻在於「查詢殘差核」的概念——將「因查詢相關性造成的相似」與「因功能冗餘造成的相似」分離。可延伸方向包括：(1) 將殘差投影改為非線性（如以小型神經網路學習殘差空間）；(2) 結合 listwise 學習排序（LTR）端到端訓練核參數；(3) 探討 DPP 與神經多樣性機制（如 Determinantal Beam Search）的理論連結；(4) 將框架推廣至多模態技能（影像、語音工具）的聯合路由。

**給產品經理**：本文的核心訊息是「技能選擇不是只挑最相關的，而是要挑互補的組合」。在產品決策上，這意味著：(a) 技能註冊表的擴張不會自動帶來代理能力提升，反而可能因冗餘降低效率；(b) 對多步驟任務的支援需要專門優化，而非僅靠擴大 Top-k；(c) 評估指標應從「命中率」轉向「完整覆蓋率」；(d) 上下文窗口是稀缺資源，多樣性路由是降低單位任務 token 成本的關鍵技術。建議在產品 roadmap 中預留「技能品質治理」與「路由演算法迭代」兩個專項。
