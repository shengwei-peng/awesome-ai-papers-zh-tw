## ⚡ TL;DR

現有多智能體系統採用集中式編排，隨子任務增加，主智能體成為通訊與整合瓶頸。

## 摘要翻譯

多智能體系統（Multi-agent Systems, MAS）能透過將複雜問題分解為平行子任務（parallel subtasks），在測試時擴展（test-time scaling）大型語言模型（large language models）的推理能力。然而，大多數現有的 MAS 依賴集中式編排（centralized orchestration），由主智能體（main agent）分配工作、收集輸出並合併結果。隨著子任務（subtasks）數量增加，此控制器成為通訊與整合的瓶頸（bottleneck）。我們提出去中心化語言模型（Decentralized Language Models, DeLM），這是一個透過平行智能體（parallel agents）、共享已驗證上下文（shared verified context）以及任務佇列（task queue）來實現去中心化協調（decentralized coordination）的 MAS 框架。智能體以非同步方式認領子任務、讀取累積進度、執行局部推理（local reasoning），並寫回精簡的已驗證更新（verified updates）。共享上下文作為共同的通訊基底（communication substrate），使智能體能夠基於彼此的已驗證進度持續推進，而無需將每個更新都交由中央控制器轉送。實證上，DeLM 同時提升了軟體工程（software-engineering）測試時擴展與長上下文推理（long-context reasoning）的表現。在 SWE-bench Verified 上，DeLM 在 Avg.@1、Pass@2 與 Pass@4 均達到最佳表現，相較最強基線（baseline）提升最高達 10.5 個百分點，同時將每項任務的成本降低約 50%。在 LongBench-v2 Multi-Doc QA 上，DeLM 在四個前沿模型家族（frontier model families）中達到最高的平均準確率，相較最強基線提升最高達 5.7 個百分點。程式碼可於我們的專案網站 https://yuzhenmao.github.io/DeLM/ 取得。

### 核心貢獻（3～5點）
- 提出 DeLM 框架，以平行智能體、共享已驗證上下文與任務佇列實現去中心化協調，消除集中式編排中主智能體的通訊與整合瓶頸。
- 在 SWE-bench Verified 上達到最佳表現（Avg.@1、Pass@2、Pass@4），相較最強基線提升最高達 10.5 個百分點，並降低每項任務成本約 50%。
- 在 LongBench-v2 Multi-Doc QA 上於四個前沿模型家族中達到最高平均準確率，相較最強基線提升最高達 5.7 個百分點。
- 驗證去中心化多智能體架構在軟體工程測試時擴展與長上下文推理任務上的有效性與擴展性。

### 適合對象
多智能體系統（MAS）、大型語言模型（LLM）推理擴展、軟體工程自動化與長文本理解領域的研究者與工程師，以及對去中心化 AI 架構與測試時擴展（test-time scaling）有興趣的實務工作者。

## 深度分析

#### 方法論解析

DeLM 的核心貢獻在於將多智能體系統（MAS）的協調機制從「提示路由（prompt routing）」轉向「共享狀態（shared state）」。傳統集中式編排（centralized orchestration）仰賴主智能體（main agent）透過分散-收集迴圈（scatter-gather loop）不斷地將中間進度改寫為提示（prompt），並選擇性地廣播給子智能體（sub-agents）。這種架構在本質上將通訊與整合邏輯序列化，導致主智能體成為瓶頸（bottleneck）。

DeLM 透過三大元件解構此問題：

1. **平行智能體（Parallel Agents）**：多個智能體以非同步方式運作，無需等待中央控制器指派任務。
2. **任務佇列（Task Queue）**：作為全域的任務排程機制，智能體從中認領（claim）子任務（subtasks），實現自組織的負載分配。
3. **共享已驗證上下文（Shared Verified Context）**：這是 DeLM 最關鍵的設計。智能體並非透過點對點通訊交換訊息，而是將緊湊且已驗證的更新（verified updates）寫入一個共同的通訊基底（communication substrate）。一旦更新被接納（admitted），即成為所有智能體可讀取的問題狀態（problem state）。

具體運作流程為：智能體從任務佇列非同步認領子任務後，讀取共享已驗證上下文中累積的進度，執行局部推理（local reasoning），再將結果以精簡、已驗證的形式寫回。此設計確保「有用發現、失敗經驗與部分解決方案」能直接成為可重複使用的問題狀態，無需經過主智能體的合併、過濾與轉發。這不僅降低了通訊延遲，更避免了資訊在層層路由中被稀釋或扭曲。

值得注意的是，DeLM 的共享上下文並非原始日誌的堆疊，而是強調「已驗證」與「緊湊」。論文在長上下文推理實驗中提及，接納時驗證（admission-time verification）與階層式摘要（hierarchical summarization）對效能至關重要，這暗示共享上下文存在某種品質控管與壓縮機制，防止上下文過度膨脹。

#### 實驗數據解讀

論文在三個設定下驗證 DeLM，分別對應不同的協調壓力：

**1. 軟體工程測試時擴展（Software-engineering test-time scaling）**
在 SWE-bench Verified 上，DeLM 在 Avg.@1、Pass@2 與 Pass@4 三項指標皆取得最佳表現，其中 Pass@4 達到 77.4%，相較最強基線（strongest baseline）提升最高達 10.5 個百分點。更具實務意義的是，其每任務成本降至約 $0.12，僅為基線方法的大約一半。這顯示 DeLM 不僅提升探索廣度（pass@k 指標反映多軌並行探索的成功率），更透過共享已驗證上下文將「平行嘗試」轉化為「共享探索」，避免重複計算，顯著改善成本效益。

**2. 長上下文多文件問答（Long-context multi-document QA）**
在 LongBench-v2 Multi-Doc QA 上，DeLM 在四個前沿模型家族（frontier model families）中均取得最高平均準確率，相較最強基線提升最高達 5.7 個百分點。此設定強調「任務內並行（within-task parallelism）」：智能體同時檢視不同證據群集（evidence clusters），並透過共享上下文維持對全局語料庫的緊湊視圖。結果顯示，DeLM 能有效將多文件證據的並行處理與迭代式共享狀態推理結合。

**3. 聚合密集型長上下文推理（Aggregation-heavy long-context reasoning）**
在 OOLONG 基準測試上，純粹的 DeLM 表現不及 RLM（一種以程式碼媒介執行的方法），因為該基準需要精確的列級聚合（exact row-level aggregation），而對話式智能體在此較為吃力。然而，將 RLM 與 DeLM 結合後，則同時達到最佳準確率與最低成本。這項結果極具啟發性：DeLM 的去中心化協調層可與程式化推理系統互補，不僅限於對話式智能體。

綜合來看，DeLM 的效能增益來自兩個層面：一是消除了集中式編排的通訊瓶頸，使更多測試時運算（test-time computation）能真正轉化為有用進度；二是共享已驗證上下文的設計讓智能體能建立在彼此的驗證進度上，減少冗餘試錯。

#### 與現有研究的比較

**相對於集中式 MAS 框架**
現有主流框架如 Claude Code Subagents、Kimi Agent Swarm 與 AOrchestra 皆採用集中式編排。這些方法雖能平行執行子智能體，但協調邏輯本身仍是序列化的：每個有用的中間結果都必須返回主智能體，由其決定如何合併與廣播。隨著子任務數量增加，進度分享（progress sharing）成為序列化通訊瓶頸。此外，主智能體在路由過程中可能稀釋、遺漏或扭曲重要細節，導致資訊損失。DeLM 透過共享狀態完全繞過了這一層，使進度分享與任務執行同樣平行化。

**相對於長上下文基線**
在長上下文領域，ReadAgent 與 Claude Code 等基線往往由主智能體預先指派證據群集給子智能體，但在尚未確知哪些證據相關前即完成分配，導致反覆的檢索-委派迴圈。DeLM 允許智能體基於共享上下文的累積證據，動態地從任務佇列認領工作，減少來回溝通。

**侷限性**
儘管 DeLM 優勢明顯，論文也揭示了其邊界：在需要精確數值或結構化聚合的場景（如 OOLONG 的列級操作），純對話式智能體仍不如程式碼媒介執行（code-mediated execution）。這暗示 DeLM 的「緊湊文字更新」在精確符號操作上有其限制。此外，論文對於「接納時驗證」的具體機制著墨有限，若多個智能體同時寫入共享上下文，衝突解決（conflict resolution）與一致性維護的細節仍待釐清。

#### 可重現性評估

論文明確指出原始碼已釋出於專案網站（https://yuzhenmao.github.io/DeLM/），且所有實驗皆基於公開基準測試：SWE-bench Verified、LongBench-v2 Multi-Doc QA 與 OOLONG。實驗中使用的前端模型（如 Gemini-3-Flash、GPT-5.4 及其他前沿模型家族）均為商用 API 模型，無需取得模型權重（model weights）即可透過 API 重現。

然而，可重現性仍存在幾項潛在挑戰：首先，共享已驗證上下文的「驗證」與「階層式摘要」機制若未在原始碼中完整開放其提示設計與壓縮邏輯，重現者可能難以複製相同的資訊密度控制。其次，任務佇列的實作細節（如任務粒度切分策略、智能體認領任務的優先順位演算法）對效能影響重大，需仔細檢視釋出程式碼的文件完整度。整體而言，由於資料集與評估指標皆為公開標準，且使用可取得的 API 模型，本研究具備基礎可重現性，但核心協調邏輯的細節透明度將決定社群能否完全復現其成本效益曲線。

#### 未來研究方向

**1. 與程式化推理的深度整合**
OOLONG 實驗已顯示 DeLM 與 RLM 的互補性。未來可探索將共享已驗證上下文擴展為「程式碼-文字混合通訊基底」，讓智能體在共享狀態中直接交換可執行的中間表示（intermediate representations），進一步提升精確聚合場景的表現。

**2. 驗證與衝突解決機制的強化**
目前「接納時驗證」可視為一種輕量級的共識機制。未來可引入更形式化的驗證器（verifier）或基於多數決的衝突解決協議，以支援更高密度的平行寫入，並理論化分析在 N 個智能體同時更新下的收斂保證。

**3. 自動化研究工作流程的擴展**
論文提及自動化研究工作流程（automated research workflows）為重要應用場景。DeLM 的架構非常適合擴展至文獻綜述、實驗設計與假設探索，其中不同智能體可並行探索不同假設軌跡，並透過共享上下文累積實驗發現。未來可針對此場景設計專用的任務佇列語意（如優先探索高資訊增益的假設）。

**4. 超大規模智能體叢集的擴展性**
當智能體數量從數十個擴展至數百或數千個時，共享上下文的讀取開銷可能成為新的瓶頸。研究可朝向「多層級共享上下文」或「語意分片（semantic sharding）」發展，讓智能體僅讀取與其當前子任務最相關的上下文分片，兼顧全局一致性與局部效率。

**5. 動態任務分解與佇列學習**
目前的任務佇列假設子任務已預先分解或未深入探討分解機制。未來可讓智能體在執行過程中動態生成新子任務並寫入佇列，甚至透過強化學習學習最優的任務分解策略，使 DeLM 從「協調層」進化為「自組織問題求解層」。

## 論文問答

**Q1：DeLM 旨在解決現有多智能體系統中的什麼核心問題？**

A：DeLM 主要解決現有多智能體系統中因集中式編排所導致的通訊與整合瓶頸。在傳統架構中，當子任務數量增加時，主智能體必須負責分派工作、收集所有輸出並合併結果，使其成為系統效能的單一阻滯點。這種設計限制了平行運算帶來的效益，並阻礙了測試時擴展與長上下文推理場景中的可擴展性。

**Q2：為何現有的集中式多智能體系統難以有效擴展？**

A：現有的集中式多智能體系統本質上依賴提示路由機制，所有中間進展都必須經由主智能體傳遞與處理。主智能體需要將這些進展重寫為後續提示，並決定如何合併與廣播給其他子智能體，隨著智能體數量成長，這會形成序列化的通訊瓶頸。此外，主智能體在路由與彙整過程中可能會稀釋、遺漏或扭曲重要細節，導致有價值的平行進展在傳播過程中遺失。

**Q3：解決此瓶頸對於測試時擴展與長上下文推理為何至關重要？**

A：在測試時擴展中，額外智能體的效益取決於不同工作者之間能否高效且忠實地共享有用進展，而集中式架構會將這種共享序列化。在長上下文推理中，主智能體往往需要在事前指派證據群集給子智能體，當相關性不明確時，會觸發反覆的檢索與委派迴圈，使協調變得越來越慢。因此，去中心化協調是將額外運算轉化為有用平行進展、避免被單一控制器阻礙的關鍵。

**Q4：DeLM 的核心方法由哪三大元件構成？**

A：DeLM 的核心架構由平行智能體、共享已驗證上下文以及任務佇列三大元件組成。各智能體從佇列中非同步認領子任務，並從共享上下文中讀取累積的問題進展。完成局部推理後，智能體將精簡的已驗證更新寫回共享上下文，使這些進展成為其他智能體後續可直接利用的共通狀態。

**Q5：相較於點對點通訊，DeLM 的關鍵創新是什麼？**

A：DeLM 的關鍵創新在於採用共享已驗證上下文作為共通通訊基底，而非讓智能體之間進行點對點的直接訊息交換。一旦某個更新被允許進入共享上下文，便立即成為所有智能體皆可見且可重複使用的問題狀態。這種設計確保進展能夠忠實傳播，無需依賴主智能體進行合併、過濾與重新廣播，從而避免了集中式瓶頸。

**Q6：DeLM 為何強調「精簡的已驗證更新」這項設計選擇？**

A：DeLM 強調精簡的已驗證更新，是為了在大量智能體同時貢獻進展時，避免共享上下文變得過於龐雜而難以處理。在准入階段進行驗證，可確保只有高品質且經過確認的進展才會進入共通狀態，防止錯誤資訊擴散。這項設計選擇維持了通訊基底的簡潔與可信度，使後續智能體能夠安心地依賴這些資訊進行局部推理。

**Q7：作者選用哪些基準測試來評估 DeLM，各自強調什麼面向？**

A：作者選用 SWE-bench Verified、LongBench-v2 Multi-Doc QA 以及 OOLONG 三項基準測試來全面評估 DeLM。SWE-bench Verified 著重於軟體工程中跨不同推理軌跡的平行探索能力；LongBench-v2 強調任務內的平行處理，要求智能體同時檢視不同證據群集以回答問題。OOLONG 則用於檢驗重度聚合的長上下文推理，凸顯去中心化已驗證上下文與程式化執行之間的互補性。

**Q8：DeLM 在 SWE-bench Verified 與 LongBench-v2 上的關鍵量化結果為何？**

A：在 SWE-bench Verified 上，DeLM 在 Avg.@1、Pass@2 與 Pass@4 等測試時擴展指標均達到最佳表現，相較最強基線提升最高達 10.5 個百分點，同時將每項任務成本降低約 50%。在 LongBench-v2 多文件問答上，DeLM 在四個前沿模型家族中取得最高的平均準確率，相較最強基線提升最高達 5.7 個百分點。這些結果充分證明，在去中心化協調架構下，系統無論是在智能體任務或長上下文推理中都能超越集中式編排。

**Q9：OOLONG 實驗揭示了 DeLM 與程式化推理系統（如 RLM）之間的什麼關係？**

A：OOLONG 實驗顯示，單獨使用 DeLM 的表現不及 RLM，因為該基準測試需要精確的列級聚合，而這正是程式化執行特別擅長的領域。然而，將 RLM 與 DeLM 結合作為協調層，則能同時達到最佳準確率與最低成本。這項發現表明 DeLM 不僅適用於對話式智能體，更能作為程式化推理工作流程的有效協調基底，擴展其應用範圍。

**Q10：DeLM 在哪些實務應用場景中最能發揮優勢？**

A：DeLM 在需要大規模平行探索與跨來源推理的實務場景中最具優勢，例如自動化研究工作流程中，智能體必須同時探索多個假設並處理大量論文、程式碼與實驗資料。在軟體工程領域，DeLM 也適用於需要平行嘗試多種除錯或實作路徑的任務。此外，對於需要同時處理多個證據群集的多文件分析任務，DeLM 同樣能顯著提升效率與準確度。

**Q11：將 DeLM 產品化部署時，需要考量哪些關鍵因素？**

A：在產品化部署 DeLM 時，必須建立穩健的准入時驗證機制，以確保共享上下文的品質與可靠性，防止錯誤資訊污染全局狀態。產品團隊需要仔細權衡更新精簡度與資訊豐富度之間的取捨，避免過度壓縮導致遺失對複雜推理至關重要的細節。此外，由於系統採用非同步運作，生產環境中還需妥善設計任務佇列管理與衝突解決策略，以防止任務重複或飢餓現象。

**Q12：DeLM 可能對多智能體系統與大型語言模型推理領域帶來什麼影響？**

A：DeLM 將多智能體系統的典範從集中式提示路由轉向持久化共享狀態協調，有望成為可擴展 MAS 的標準架構之一。透過在效能與成本上展現顯著優勢，DeLM 促使研究社群重新思考主智能體控制器的必要性，並探索更扁平化的協調模式。這項進展可望加速更具適應性與擴展性的自動化研究及軟體工程智能體之發展，推動相關領域的典範轉移。

**Q13：DeLM 在 OOLONG 上的表現揭示了什麼樣的局限性？**

A：OOLONG 實驗揭示，在缺乏程式化執行輔助的情況下，DeLM 難以處理需要精確列級聚合的任務，因為其對話式更新機制缺乏數值運算的嚴謹性。這顯示單靠共享上下文與自然語言更新，可能不足以應對高度結構化的數值或表格推理工作。因此，在面對重度聚合的工作流程時，DeLM 需要與專門工具整合，才能彌補自身在精確計算上的不足。

**Q14：去中心化協調方法存在哪些潛在的失敗案例或風險？**

A：若准入驗證機制設計不當，錯誤或誤導性的更新可能透過共享上下文迅速傳播給所有智能體，導致系統性偏差。此外，若智能體寫回的更新過度精簡，可能導致複雜推理所需的細微線索或失敗經驗遺失，降低整體問題解決能力。另一個風險是，若任務佇列設計不當，可能出現某些子任務被過度重複認領，而其他任務則面臨飢餓的狀況，影響整體效率。

**Q15：DeLM 框架為未來的多智能體研究指出了哪些方向？**

A：DeLM 框架為未來研究指出幾個重要方向，包括探索可適性驗證閾值，以在上下文品質與更新頻率之間取得動態平衡。將 DeLM 與更多樣化的工具使用範式整合，例如程式碼解譯器、檢索系統與視覺推理模組，也是極具前景的發展路徑。此外，研究階層式共享上下文設計，同時維護全局摘要與細粒度局部狀態，將有助於應對更複雜、更大規模的多智能體協調情境。

## 實務應用指南

### 適用場景

1. **大型軟體專案自動化開發與除錯**  
   當單一程式碼庫的問題需要同時探索多種修復假設時，可將不同模組的除錯或測試撰寫任務拆為子任務放入佇列。各代理非同步認領任務，透過共享已驗證上下文傳播失敗經驗與部分修復，避免傳統集中式編排中主智能體反覆整合的瓶頸，實現如 SWE-bench Verified 所示的測試時擴展。

2. **金融與法律多文件盡職調查**  
   在併購或訴訟情境中，需同時檢視數百份合約、財報與法規。可將不同證據群集分配給平行代理並行摘要與標註，再透過共享上下文累積全局脈絡。此場景對應 LongBench-v2 Multi-Doc QA 的長上下文推理需求，能減少主智能體預先分配證據所導致的來回迭代。

3. **跨領域研究報告自動生成**  
   針對需整合大量論文、實驗數據與程式碼的自動化研究工作流程，各代理可負責不同文獻群集或實驗假設的驗證，並將已驗證的中間發現寫回共享狀態。後續代理直接基於這些精簡更新進行綜合，無需等待中央控制器合併與轉發。

4. **即時數據聚合與決策支援**  
   適用於需要精確列級或表級聚合的營運分析（如 OOLONG 情境）。DeLM 可作為協調層，讓代理並行處理不同數據分片，再搭配程式化推理工具（如 RLM）執行最終精確計算，兼顧平行探索與執行正確性。

5. **分散式技術支援與知識庫維護**  
   企業內部知識分散於多個部門文件與系統時，可部署平行代理各自負責不同領域的問題解析與文件更新，透過共享已驗證上下文確保所有代理看到的解決方案與產品規格皆為最新且一致。

### 實作前置條件

**資料準備**
- 可明確拆解為獨立子任務的問題定義與任務描述格式（如 JSON / YAML）。
- 領域專用的驗證規則或測試案例，用於准入代理寫回共享上下文的更新（例如單元測試、事實查核規則、格式檢查器）。
- 初始全局上下文，包含問題背景、限制條件與已知的部分解答。

**運算資源**
- 可支援平行呼叫的大型語言模型 API 配額（建議至少 4–8 組並行代理）。
- 低延遲的共享狀態儲存系統（如 Redis、PostgreSQL、或支援原子寫入的分散式 KV Store），用於存放共享已驗證上下文。
- 任務佇列基礎設施（如 RabbitMQ、Celery、AWS SQS），支援代理非同步認領與冪等處理。

**技術能力**
- 熟悉分散式系統設計與並行程式模型，能處理競態條件與冪等寫入。
- 具備提示工程與 LLM 應用開發經驗，能設計「讀取上下文 → 局部推理 → 寫回更新」的代理循環。
- 能為特定領域開發輕量驗證器（如 Python 測試腳本、正規表示式檢查、或小型分類模型）。

### 實作步驟建議

**步驟一：任務分解與佇列化**  
將端到端問題拆解為粒度適中的子任務，確保每個子任務可獨立執行且產出可驗證的中間結果。設計任務佇列的優先順序與依賴關係，避免過度細分導致協調開銷。

**步驟二：建立共享已驗證上下文儲存**  
設計共享上下文的資料結構，區分「全局問題狀態」與「代理局部更新」。實作讀寫介面，並導入階層式摘要機制（hierarchical summarization），防止上下文隨代理數量線性膨脹。

**步驟三：設計代理推理循環**  
為每個代理定義標準作業流程：從佇列認領子任務 → 讀取當前共享上下文 → 執行局部推理 → 產出精簡更新 → 提交驗證。更新格式應固定（如結構化 JSON），便於後續代理直接解析。

**步驟四：實作准入驗證機制**  
在寫回共享上下文前加入驗證閘道。根據領域特性選用自動測試、靜態檢查或小型驗證模型，確保只有正確且非冗餘的更新才會成為全局可見狀態，防止錯誤傳播。

**步驟五：部署平行代理與監控**  
啟動多組代理非同步消費任務佇列，設定超時與重試機制。監控指標應包含任務吞吐量、共享上下文大小、API 呼叫成本，以及代理間重複探索的比例。

**步驟六：迭代優化與人機協作**  
根據監控數據調整任務粒度與上下文摘要策略。在關鍵驗證點保留人類審核閘道，特別是在高風險領域（如法律或醫療），確保自動化流程的可靠性。

### 潛在風險與注意事項

- **共享上下文膨脹**：隨著代理數量與迭代次數增加，共享狀態可能迅速增長，反而成為新的讀取瓶頸。應導入論文提及的階層式摘要與壓縮策略，定期將早期細節歸檔為高階摘要。
- **錯誤傳播風險**：若准入驗證過於寬鬆，單一代理的錯誤更新會被所有後續代理視為已驗證事實而放大。建議採用多層驗證（如自動測試 + 語意一致性檢查）並保留版本回滾機制。
- **任務粒度與協調成本失衡**：子任務過細會導致代理頻繁讀寫上下文，抵銷去中心化帶來的效益；過粗則失去平行擴展優勢。需透過實驗找到領域特定的最佳粒度。
- **競態條件與冪等性**：多代理同時認領或更新相近任務時，可能產生衝突。任務佇列應支援原子認領（claim），共享上下文寫入應設計為冪等或基於版本向量（vector clock）合併。
- **成本估算失準**：雖然 DeLM 在論文中降低約 50% 成本，但平行代理同時呼叫 LLM 會瞬間消耗大量 token 配額。建議實作動態速率限制與預算上限，避免雲端帳單失控。

---

### 與其他技術的整合建議

- **搭配程式化推理系統（如 RLM）**：針對需要精確數值聚合或程式執行的場景（如 OOLONG 基準測試），可讓 DeLM 負責高階任務協調與證據並行探索，再將列級精確計算交由支援程式碼執行的框架處理，形成「去中心化協調 + 程式化執行」的雙層架構。
- **銜接現有 CI/CD 與 DevOps 工具鏈**：在軟體工程場景中，將 DeLM 的共享上下文對接 GitHub Issues、自動化測試框架（如 pytest）與持續整合流程，使代理的已驗證更新直接觸發測試並回寫結果。
- **結合向量資料庫與 RAG 管線**：長上下文場景中，先以檢索系統將海量文件分群為相關證據群集，再將各群集作為子任務餵入 DeLM。共享上下文則存放各群集的精簡發現，避免將原始長文本重複載入每個代理的提示。
- **保留集中式主智能體作為高階規劃器**：若現有系統已採用集中式編排，可採漸進遷移策略：讓主智能體負責目標分解與任務生成，但將子任務分派與進度整合下放至 DeLM，降低主智能體的通訊負載。

**給初學者**  
請先聚焦論文圖二，理解「集中式編排」與「去中心化協調」的核心差異：想像傳統架構是一位經理逐一收發郵件整合進度，而 DeLM 則是團隊共用一塊自動驗證的白板，任何人完成工作後直接寫上結果，其他人立刻可見。建議搭配 SWE-bench Verified 的實驗結果，建立「去中心化能同時提升效能與降低成本」的直覺。

**給 AI 工程師**  
請深入研讀第二節的設計原則與第四節的實驗設定，特別關注共享已驗證上下文的資料結構設計、代理讀寫循環的提示模板，以及准入驗證的實作細節。思考如何將現有框架（如 LangChain、AutoGen）中的集中式 scatter-gather 邏輯，重構為以共享狀態為通訊基底的非同步架構。

**給研究人員**  
本論文對測試時擴展（test-time scaling）的貢獻在於以「共享狀態」取代「同步迴圈」作為協調機制。建議細讀第 4.2.1 節的 trace-level 分析，觀察代理如何透過精簡的已驗證更新重用彼此的發現，並思考此機制對更廣泛的自動化研究工作流程（如 AlphaEvolve）的理論意涵，以及去中心化協調在一致性與收斂性上的研究空間。

**給產品經理**  
請優先評估論文中的兩項關鍵商業指標：在 SWE-bench Verified 上 Pass@4 提升達 10.5 百分點，且單任務成本降至約一半。這代表 DeLM 不僅改善效能，更具備明確的成本效益優勢。閱讀時請對照自家產品的集中式瓶頸場景（如客服分流、文件審查），評估遷移至去中心化架構的投資報酬率與漸進導入路徑。
