# EVOHARNESSBENCH：您的智慧代理能否跟上不斷演化的工具鏈？

## ⚡ TL;DR

現有基準多固定工具鏈而變動任務，忽略外部工具鏈演化對代理的挑戰。
本文提出 EVOHARNESSBENCH，以十七組工具鏈串流評估部署與自我演化適應。
結果顯示工具鏈擴張會誘發遺忘，適應成效不穩定，且保留與適應存在張力。

## 摘要翻譯

現代基於大型語言模型的智慧代理（LLM-based agents）透過由工具（tools）、可重複使用的技能（skills）與專家代理（specialist agents）組成的工具鏈（harness）運作，而此工具鏈決定了代理能觀察什麼、能執行什麼。在實務上，隨著新能力不斷加入，工具鏈會持續演化。我們提出 EVOHARNESSBENCH，一個在受控的工具鏈演化下，沿著三個能力軸向（capability axes）——工具（tools）、技能（skills）與代理（agents）——評估智慧代理的基準測試。不同於現有的智慧代理持續學習基準測試（continual-learning benchmarks）——這些測試通常將非平穩性（non-stationarity，即隨時間變化的部分）置於任務串流（task stream）中，同時保持工具鏈固定——EVOHARNESSBENCH 將非平穩性置於外部提供的工具鏈（externally supplied harness）本身。本基準包含 17 個多階段工具鏈串流（multi-stage harness streams），這些串流以確定性方式由基於驗證器的基準測試（verifier-based benchmarks）建構而成，涵蓋 802 項任務、520 個工具、42 項技能與 62 個代理。我們評估兩個互補的設定，分別對應工具鏈演化的核心挑戰：部署評估（deployment evaluation），用於在工具鏈擴展之際隔離出對先前可及能力的保留（retention）；以及自我演化適應評估（self-evolving adaptation evaluation），用於檢驗新能力引入後累積經驗（accumulated experience）是否仍然有用。我們的結果揭示了三個持續存在的落差：首先，單純的工具鏈擴展就可能降低先前已解決任務的表現，產生工具鏈誘發遺忘（harness-induced forgetting）；其次，自我演化適應所帶來的增益在工具鏈演化的各階段、不同能力軸向與環境之間仍不一致；第三，保留（retention）與適應（adaptation）可能存在張力——保留早期能力不一定能改善對新引入能力的適應，反之亦然。這些結果確立了工具鏈演化是建構能夠跟上不斷演化的工具鏈、同時保留先前有效行為的智慧代理的一項獨特挑戰。

### 核心貢獻（3～5點）
- 提出 EVOHARNESSBENCH，首個將非平穩性置於外部提供的工具鏈（harness）本身，而非任務串流（task stream）的智慧代理評估基準。
- 設計兩大互補評估設定：部署評估（deployment evaluation）檢驗工具鏈擴展後的保留能力，自我演化適應評估（self-evolving adaptation evaluation）檢驗新能力引入後的適應表現。
- 建構 17 個多階段工具鏈串流（multi-stage harness streams），涵蓋 802 項任務、520 個工具、42 項技能與 62 個代理，並以確定性方式由基於驗證器的基準測試生成。
- 揭示工具鏈誘發遺忘（harness-induced forgetting）現象：即使模型參數未變，單純擴展工具鏈也可能降低代理在既有任務上的表現。
- 發現保留（retention）與適應（adaptation）之間存在張力，兩者並非總是相輔相成，為智慧代理的持續演化設計提供重要啟示。

### 適合對象
本論文適合從事大型語言模型智慧代理、工具學習（tool learning）、持續學習（continual learning）與代理評估研究的學者與工程師，特別是關注工具鏈（harness）動態擴展、代理部署後能力保留，以及多工具／多技能／多代理系統演化問題的讀者。對於正在設計或評估 Agentforce、OpenAI 公開技能庫等真實代理生態系統的研究人員與產品開發者，本文亦具高度參考價值。

## 深度分析

#### 方法論解析

EVOHARNESSBENCH 的核心貢獻在於把「非平穩性（non-stationarity）」從傳統的任務串流（task stream）轉移到「外部提供的工具鏈（externally supplied harness）」本身。具體而言，它建構了 17 條多階段工具鏈串流（multi-stage harness streams），每條串流包含 3 到 6 個累積階段（cumulative stages），形成巢狀累積工具鏈串流（nested, cumulative harness streams）：  
H₁ ⊆ H₂ ⊆ … ⊆ H_T。  
每個 H_t 代表在第 t 階段暴露給代理（agent）的能力集合，能力可為可執行工具（tools）、程序性技能（skills）或專家代理（specialist agents），對應三個能力軸向（capability axes）。

每個任務被表示為三元組 (x_i, y_i, C_i)：使用者任務 x_i、可由驗證器（verifier）檢查的結果 y_i，以及僅用於建構與分析的隱藏真實能力標註 C_i。建構時強制滿足兩個性質：

1. 可行性（Feasibility）：C_i ⊆ H_{t_i}，即任務所需能力在指定階段已存在。  
2. 新能力壓力（New-capability pressure）：C_i ∩ (H_{t_i} \ H_{t_i−1}) ≠ ∅，即任務至少用到一個在該階段才引入的能力。

這種設計確保了任務本身不會隨時間改變，變化的是代理可用來解題的「工具箱」。這與傳統持續學習（continual learning）把新任務、新領域或新分佈當作非平穩來源的做法形成鮮明對比。

評估分為兩種互補模式：

- 部署評估（deployment evaluation）：關閉內部自我演化適應（inner self-evolving adaptation），每個階段的工具鏈版本獨立測試。其目的在於隔離「工具鏈擴張本身」對既有能力的影響，檢驗是否出現工具鏈誘發遺忘（harness-induced forgetting）。
- 自我演化適應評估（self-evolving adaptation evaluation）：開啟內部適應，允許代理在每個階段透過某種適應方法論（如記憶、學習技能、提示調整等）產生持續性產物，並把這些產物帶到下一階段。評估分割（evaluation split）始終保持未見，以衡量累積經驗（accumulated experience）對新能力的適應是否有幫助。

這種「外層工具鏈演化（outer harness evolution）＋內層自我演化適應（inner adaptation）」的雙層架構，讓研究者能夠分別測量保留（retention）與適應（adaptation）兩大挑戰，也能觀察兩者之間的張力。

#### 實驗數據解讀

雖然提供的上下文未列出完整數值表格，但從摘要與引言可歸納出三項主要發現，並可進一步推論其實驗意涵：

1. 工具鏈擴張並非免費：即使底層模型權重完全未變，僅僅增加可用工具、技能或專家代理的數量，就可能使代理在先前已能解決的任務上表現下降。這種「工具鏈誘發遺忘」並非傳統災難性遺忘（catastrophic forgetting）——後者源於模型參數更新，而前者源於選擇空間變大、提示（prompt）上下文被稀釋、以及錯誤呼叫不相關能力的機率上升。對 frontier agents 而言，這意味著在生產環境中持續擴充工具目錄可能反而損害既有服務品質。

2. 自我演化適應的成效不一致：在不同工具鏈階段、不同能力軸向（tools、skills、agents）以及不同環境設定下，適應帶來的增益差異很大。這暗示目前尚無單一適應策略能穩定地跨階段、跨軸向提升表現。可能原因包括：早期累積的經驗在新工具鏈下變成「過時捷徑」、學到的技能與新引入能力產生衝突、以及多代理協調（multi-agent coordination）的複雜度隨專家代理數量非線性成長。

3. 保留與適應可能相互拉扯：最佳保留既有能力的方法，往往不利於適應新能力；反之，最能快速利用新能力的方法，可能犧牲對舊任務的穩定性。這項發現對「持續學習＝同時提升保留與適應」的常見假設提出挑戰：在工具鏈演化的情境下，兩者可能需要不同的機制，甚至需要明確的權衡（trade-off）設計。

從方法論角度，這些結果也凸顯了「參考工具鏈（reference harnesses）」的重要性：自我演化適應評估會把代理在演化工具鏈下的表現，與針對特定任務設計的最佳化參考工具鏈相比，從而判斷適應是否真正「跟上」了新能力。若代理在參考工具鏈下表現良好，但在演化工具鏈下表現不佳，則問題不在能力本身，而在於如何從不斷膨脹的工具鏈中選擇與組合正確能力。

#### 與現有研究的比較

現有代理基準測試（agent benchmarks）大致可分為三類，EVOHARNESSBENCH 與它們的差異可總結如下：

1. 靜態工具鏈基準（Static-harness benchmarks）：如早期 WebShop、ToolBench 等，固定提供一組工具、技能或代理，既無外層演化也無內層適應。這類基準適合評估單一工具鏈下的解題能力，但無法反映真實部署中工具目錄持續擴充的現象。

2. 自我演化基準（Self-evolving benchmarks）：允許代理透過累積經驗改進，例如學習新技能或調整提示，但工具鏈本身固定。SkillLearnBench、SkillFlow 等雖然涉及技能表面（skill surface）成長，但成長來自代理內部學習，而非外部工具鏈演化，且評估重點是學到技能的品質，而非任務表現在外部演化工具鏈下的變化。

3. 持續學習基準（Continual-learning benchmarks）：同時包含外層演化與內層適應，但把非平穩性放在任務串流（task stream）上，工具鏈保持固定。CMRBench 雖然把外層演化放在外部成長的模型池（model pool）中，評估的是持續路由（continual routing），而非工具、技能、專家代理構成的工具鏈演化。

相較之下，EVOHARNESSBENCH 的獨特定位在於：把外層演化明確置於「代理的工具鏈」之中，並橫跨工具、技能、專家代理三個能力軸向。這使得它能夠研究一個過去被忽視但日益普遍的現象：當 Agentforce、OpenAI 公開技能庫（OpenAI's public skills repository）等生態系統持續新增、更新或移除能力時，代理如何在「不遺忘舊能力」與「善用新能力」之間取得平衡。

不過，EVOHARNESSBENCH 也有其侷限。首先，工具鏈串流是確定性（deterministic）建構的，雖然有利於可重複比較，但可能無法完全捕捉真實世界中能力新增順序的隨機性與相依性。其次，它主要關注「外部供給」的工具鏈演化，對於代理主動發現或創造新能力（agent-driven capability growth）的探討較少。第三，實驗中底層模型權重固定，這雖然有助於隔離工具鏈效應，但也意味著結果無法直接推論到模型本身也持續更新的場景。

#### 可重現性評估

從提供的上下文來看，EVOHARNESSBENCH 的設計在方法論上具備一定的可重現性優勢：

- 任務來自現有的 verifier-based benchmarks，並以確定性程序建構，這降低了人為挑選任務帶來的偏差。
- 工具鏈串流、階段劃分與能力標註 C_i 都是明確定義的，原則上可依相同規則重新生成。
- 評估指標基於驗證器自動判定，減少主觀評分的不一致性。

然而，關於開源釋出的具體資訊，目前上下文並未明確說明是否提供原始碼、資料集或建構腳本。若論文最終未公開這些資源，則其他研究者難以完全重現 17 條工具鏈串流、802 項任務與 1,510 個軸向特定評估範例。此外，由於實驗涉及 frontier LLM（如 GPT-4 等級模型）作為代理核心，而這些模型權重與 API 行為可能隨時間變化，即使釋出程式碼，長期可重現性仍會受到模型版本漂移的影響。建議作者至少釋出：

1. 任務與工具鏈建構腳本；  
2. 各階段 H_t 的完整能力清單；  
3. 驗證器（verifier）實作與評估分割；  
4. 所使用代理系統（SAS / MAS）的提示與配置；  
5. 原始實驗結果與統計顯著性檢定。

如此一來，社群才能驗證「工具鏈誘發遺忘」與「保留—適應張力」是否在不同模型世代與不同工具鏈排序下依然成立。

#### 未來研究方向

EVOHARNESSBENCH 揭示的現象為多個後續研究方向開啟了大門：

1. 聯合外層—內層最佳化：現有方法多把內層適應與外層工具鏈演化分開處理。未來可設計能同時感知「工具鏈即將擴張」的代理，例如透過元學習（meta-learning）或工具鏈預覽機制，在新增能力釋出前就預先調整檢索與規劃策略。

2. 工具鏈壓縮與動態檢索：隨著工具鏈膨脹，如何為每個任務動態篩選最相關的子集（sub-harness）將成為關鍵。可結合工具描述嵌入、任務意圖偵測與層級式工具索引，降低「選擇過載」對保留的負面影響。

3. 保留導向的持續學習機制：既然工具鏈擴張會誘發遺忘，未來需要專門針對「非參數更新型遺忘」的對策，例如提示層級的經驗回放（prompt-level experience replay）、技能版本控制（skill versioning）或舊工具鏈行為正則化。

4. 適應性的能力釋出排程：工具鏈新增順序會影響學習難度。可研究如何根據任務分佈與代理當前能力，設計課程式（curriculum）的能力釋出策略，以最大化保留並最小化適應衝擊。

5. 跨軸向統一理論：目前工具、技能、專家代理三軸向的演化機制不同。建立統一的數學框架——例如把工具鏈視為動作空間（action space）的結構化擴張——有助於理解為何某些軸向比另一些更容易誘發遺忘。

6. 真實世界工具鏈追蹤：EVOHARNESSBENCH 是控制環境下的基準。未來可從 Agentforce、OpenAI 公開技能庫等真實生態系統抽取能力新增/移除/更新的時間序列，建構更貼近實際部署的動態評估。

7. 多代理系統中的角色演化：當專家代理數量增加時，協調複雜度急遽上升。未來可研究如何讓多代理系統（MAS）自動學習新的協作協定，而非僅僅增加可用代理名單。

總結來說，EVOHARNESSBENCH 把「工具鏈演化」確立為一個獨立且重要的研究問題。它不僅提供了系統性的評估框架，也提醒社群：在追逐更強大工具與技能的同時，必須同時確保代理能夠在持續擴張的工具鏈中，穩定地保留並靈活地適應。

## 論文問答

**Q1：EVOHARNESSBENCH 想要解決什麼問題？為什麼「工具鏈演化」對智慧代理來說是個值得關注的挑戰？**

A：EVOHARNESSBENCH 針對的是現代基於大型語言模型的智慧代理所處的「工具鏈」會隨時間不斷擴張的現象，也就是外部提供的工具、技能與專家代理持續增加。這種非平穩性會同時帶來兩個挑戰：一是**保留**，代理必須在工具鏈變大後仍能完成過去可解的任務；二是**適應**，代理必須善用新加入的能力，而不是被舊經驗誤導。然而，過去的基準測試大多把任務串流當作變化來源，卻忽略了工具鏈本身擴張所造成的獨特影響，因此無法評估代理是否真的能跟上不斷演化的工具鏈。

**Q2：現有的基準測試為什麼無法充分評估這個問題？它們各自缺少了什麼？**

A：現有基準測試大致可分為三類，但都不足以捕捉工具鏈演化的影響。第一類是**靜態工具鏈基準測試**，它們在固定工具、技能與代理集合下評估代理，完全沒有外部演化。第二類是**自我演化基準測試**，雖然允許代理透過累積經驗進行內部適應，但工具鏈本身不會隨時間擴張，因此無法觀察舊經驗在新工具鏈下是否會變得過時。第三類是**持續學習基準測試**，雖然同時有外部演化與內部適應，但它們把非平穩性放在任務串流中，而非工具鏈本身，所以仍然無法評估工具鏈擴張所誘發的遺忘與適應困難。

**Q3：為什麼工具鏈演化不只是一個理論問題，而是實務上已經出現的現象？**

A：從 Salesforce 的 Agentforce 生態系統，以及 OpenAI 公開技能庫的歷史紀錄都可以看到，能力會持續被新增、更新或移除，這顯示工具鏈演化已經是部署中代理系統的常態。對企業產品而言，每當加入新的 API、技能或專家代理，使用者都會期待代理能立即利用這些新能力，同時不至於把原本會做的事搞砸。因此，建立能夠系統性評估工具鏈演化的基準測試，對於確保代理在真實環境中長期可靠運作至關重要。

**Q4：EVOHARNESSBENCH 的核心方法是什麼？它如何建構「工具鏈串流」？**

A：EVOHARNESSBENCH 建構了 17 條**多階段工具鏈串流**，每條串流包含 3 到 6 個逐步累積的階段，每個階段 H_t 都是前一階段 H_{t-1} 的超集合。這些串流沿著三個**能力軸向**展開：工具、技能與專家代理，並且從常用的核心能力逐步釋出到長尾能力。每個任務會被分配到「最早能解決它」的階段，同時確保該任務至少用到一個在該階段新引入的能力，從而保證每個階段都有明確的新能力壓力。

**Q5：相較於以往研究，EVOHARNESSBENCH 的關鍵創新在哪裡？**

A：它的關鍵創新在於把**非平穩性從任務串流轉移到外部提供的工具鏈本身**，這是首次有基準測試專門評估工具鏈擴張對代理表現的影響。此外，它同時設計了兩種互補的評估模式：**部署評估**用來隔離工具鏈擴張對既有能力的影響，**自我演化適應評估**則用來檢驗累積經驗在新工具鏈下是否仍然有用。這種設計讓研究者能夠分別測量「工具鏈誘發遺忘」與「在演化工具鏈下的適應能力」，並觀察兩者之間的張力。

**Q6：在建構任務與工具鏈時，作者做了哪些重要的設計選擇？**

A：首先，所有任務都來自**基於驗證器的基準測試**，因此答案可自動檢驗，確保評估客觀且可重現。其次，每個任務都滿足兩個性質：**可行性**，也就是任務所需能力在分配階段都已存在；以及**新能力壓力**，也就是至少用到一個在該階段才引入的能力。再者，每個階段內部又區分為適應分割與評估分割，讓自我演化適應評估可以在不洩漏測試資料的前提下進行。最後，工具鏈的擴張是確定性且巢狀累積的，這讓不同方法之間的比較更為公平。

**Q7：EVOHARNESSBENCH 的規模與組成為何？它評估了哪些類型的代理系統？**

A：該基準測試共包含 17 條受控的工具鏈串流、802 個獨特任務，以及 1,510 個軸向專屬的評估範例，涵蓋 520 個可執行工具、42 個潛在參考技能與 62 個專家代理。這些資源被用來評估代表性的**單代理系統**與**多代理系統**，並在部署評估與自我演化適應評估兩種模式下進行比較。如此規模讓研究者能夠觀察不同能力軸向與不同代理架構在工具鏈演化下的表現差異。

**Q8：實驗揭示了哪些關鍵結果？「工具鏈誘發遺忘」是什麼意思？**

A：實驗揭示了三大持續存在的差距。第一，**工具鏈擴張本身並非免費**：即使模型參數沒有改變，代理在先前可解的任務上也可能因為工具鏈變大而表現下降，這就是**工具鏈誘發遺忘**。第二，**自我演化適應的成效並不一致**，其提升幅度會隨著階段、能力軸向與環境而大幅變化。第三，**保留與適應可能互相拉扯**：最能保留舊能力的方法，不一定最擅長適應新能力，反之亦然。

**Q9：部署評估與自我演化適應評估各自測量了什麼？兩者的對比帶來什麼啟示？**

A：**部署評估**關閉了跨階段的內部適應，讓每個階段的工具鏈版本獨立評估，從而隔離工具鏈擴張對既有能力的直接影響。**自我演化適應評估**則允許代理在每個階段學習，並將記憶、學到的技能或提示等持久化產物帶到下一階段，測試累積經驗是否有助於適應新能力。兩者的對比顯示，單純優化適應並不足以解決問題，因為促進適應的機制可能損害保留，而強調保留的機制又可能妨礙對新能力的探索。

**Q10：在實務應用中，工具鏈演化會出現在哪些場景？**

A：工具鏈演化幾乎存在於所有會持續擴充能力的代理產品中，例如企業客服代理不斷新增查詢訂單、退貨、發票等 API；程式開發代理隨著專案成長獲得更多函式庫與工具；或是協作型多代理系統持續引入新的專家代理來處理特定領域問題。在這些場景中，使用者會期待代理能利用新功能，但同時不能忘記原本已經會的工作流程。因此，EVOHARNESSBENCH 所衡量的保留與適應能力，直接對應到產品升級時的穩定性與可用性。

**Q11：對於產品開發者來說，這篇論文帶來哪些設計與維運上的啟示？**

A：產品團隊應該把工具鏈版本化，並在每次擴張時進行回歸測試，以偵測**工具鏈誘發遺忘**。同時，設計自我演化機制時，不能只看新能力上的適應表現，還要監控舊任務的保留率，避免累積的記憶或技能變成過時的負擔。此外，由於保留與適應可能互相衝突，開發者需要權衡兩者的取捨，或採用能夠動態調整的機制，例如根據當前工具鏈版本選擇最合適的技能與提示。

**Q12：這項研究對整個代理研究領域可能產生什麼影響？**

A：EVOHARNESSBENCH 確立了「工具鏈演化」是一個獨立且重要的研究問題，而不只是持續學習或自我演化的附帶現象。它促使未來研究同時考慮外部工具鏈擴張與內部適應機制，而非孤立地優化其中一方。長遠來看，這將推動更穩健的代理架構設計，例如能夠在擴大工具鏈時自動抑制干擾、並在需要時喚起舊能力的系統。

**Q13：這篇論文承認了哪些限制？**

A：作者指出，他們聚焦於**工具鏈導向的自我演化適應**，也就是底層模型權重保持固定，只更新模型周圍的持久化元件，因此沒有探訋模型微調或權重持續更新所帶來的影響。此外，工具鏈串流是確定性建構的，雖然有利於控制變因與公平比較，但可能無法完全反映真實世界中能力新增、更新、移除的複雜動態。最後，目前的評估主要關注任務層級的正確性，對於效率、成本與可解釋性等面向的探討相對有限。

**Q14：在實驗中，代理在哪些情況下特別容易失敗？**

A：當工具目錄大幅擴張時，代理容易在眾多工具中迷失，選錯工具或產生無效的呼叫序列，導致原本可解的任務失敗。在自我演化適應評估中，代理在較早期、較狹窄工具鏈下累積的提示、記憶或技能，可能會在新階段變成誤導，讓代理堅持使用已經過時的行為模式。此外，當專家代理數量增加時，多代理系統的協調難度也會上升，容易出現路由錯誤或溝通失敗。

**Q15：未來研究可以朝哪些方向延伸這項工作？**

A：未來可以發展能夠同時優化保留與適應的聯合方法，例如根據工具鏈版本動態選擇或遺忘技能、記憶與提示。另一個方向是引入**元學習**，讓代理學會如何在不同工具鏈版本之間快速轉移，而不需要從頭適應。此外，也可以將研究擴展到更貼近真實部署的設定，例如能力會被更新或移除、工具鏈擴張速度不均、以及同時考慮延遲、成本與正確性的多目標優化。

## 實務應用指南

### 適用場景

1. **企業級 SaaS 平台擴充工具目錄**  
   當 CRM、ERP 或協作平台持續上架新 API（例如新增日曆、票務、資料分析工具）時，可用 EVOHARNESSBENCH 的「工具」軸向評估：工具鏈擴張後，原本能完成的任務是否出現工具鏈誘發遺忘，以及代理能否正確選用新工具。

2. **客戶服務多代理系統引入專家代理**  
   在客服場景中，隨著業務線增加，會不斷加入退款、技術支援、銷售等專家代理。透過「代理」軸向，可檢驗新增專家代理後，既有問題是否仍能被正確路由，以及新專家代理是否被有效利用。

3. **AI 程式輔助工具新增可重用技能**  
   當程式輔助助手從單純程式碼補充，擴展到包含測試生成、重構、文件撰寫等可重用技能時，可用「技能」軸向評估：累積的技能是否反而干擾新任務，或舊任務的保留率是否下降。

4. **內部企業助理整合成長中的 API 生態系**  
   企業內部助理會隨著部門需求增加人力資源、財務、法務等 API。此時可建立多階段工具鏈串流，在正式上線前驗證部署評估與自我演化適應評估的表現。

5. **RPA 或工作流程自動化平台的能力演進**  
   當自動化平台從固定腳本走向 LLM 驅動，並逐步加入新工具與程序技能時，可用此基準測試來量化「保留」與「適應」之間的張力，避免每次擴充都犧牲既有流程的穩定性。

### 實作前置條件

**資料準備**
- 一組具備驗證器（verifier）可自動判定正確性的任務集合，例如來自現有基於驗證器的基準測試。
- 每個任務需標註完成所需的工具、技能或專家代理（即隱藏的真實能力標註 C_i）。
- 需預先定義能力釋放順序：從核心高頻能力到長尾能力，並據此建立巢狀累積工具鏈串流 H_1 ⊆ H_2 ⊆ ... ⊆ H_T。

**運算資源**
- 可執行 LLM 推理的基礎設施（支援 OpenAI、Anthropic、開源模型等）。
- 評估成本會隨工具鏈規模與任務數量線性成長；17 條串流、1,510 個軸向特定評估範例的規模可作為參考。
- 若執行自我演化適應評估，需額外儲存與更新持久化產物（記憶、學習技能、提示詞等）的空間。

**技能與團隊準備**
- 熟悉至少一種代理框架（如 LangGraph、AutoGen、OpenAI Agents SDK 或自研框架）。
- 具備設計驗證器與評估管線的經驗。
- 理解持續學習與非平穩性概念，能區分「任務串流變化」與「工具鏈本身演化」。
- 具備提示工程與多代理協調的實作經驗。

### 實作步驟建議

1. **定義能力軸向與階段**  
   根據產品現況，選擇要演化的軸向：工具、技能或專家代理。將能力依使用頻率與依賴關係排序，建立 3–6 個累積階段。

2. **建立任務與能力對應表**  
   為每個任務標註所需能力集合 C_i，並將任務指派到「最早可解且至少使用一項新引入能力」的階段，確保滿足可行性與新能力壓力兩項條件。

3. **劃分適應集與評估集**  
   在每個階段內將任務分為適應集（用於自我演化適應）與保留的評估集（held-out），避免評估資料洩漏。

4. **選定基線代理系統**  
   同時評估單一代理系統（SAS）與多代理系統（MAS），以觀察不同架構對工具鏈擴張的敏感度。

5. **執行部署評估**  
   關閉跨階段經驗傳遞，獨立評估每個階段的工具鏈版本。記錄隨著工具鏈擴張，舊任務表現是否下降，量化工具鏈誘發遺忘。

6. **執行自我演化適應評估**  
   開啟內部適應機制，允許代理在每個階段學習並攜帶持久化產物到下一階段。比較其在參考工具鏈與演化工具鏈下的適應差異。

7. **分析保留與適應的權衡**  
   繪製各階段的保留率與新任務適應率，找出「保留最佳」與「適應最佳」的方法是否為同一方案，並據此調整適應策略。

8. **迭代工具鏈設計與上線**  
   根據評估結果調整能力釋放順序、新增路由機制、改進提示詞或記憶更新策略，再重新評估，形成持續驗證的閉環。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **工具鏈誘發遺忘被忽略** | 團隊可能誤以為新增能力只會帶來增益，卻未發現舊任務表現下滑。 | 每次擴充都執行部署評估，將舊任務保留率列為上線門檻。 |
| **混淆任務非平穩性與工具鏈演化** | 若任務內容也隨時間改變，就無法單獨歸因於工具鏈擴張。 | 保持任務實例固定，僅變更外部提供的工具鏈。 |
| **適應集過擬合** | 自我演化機制可能記住適應集細節，而非學到可遷移的能力選擇策略。 | 嚴格區分適應集與評估集，並使用多組隨機切分驗證。 |
| **持久化產物過時** | 早期累積的記憶或技能在新工具鏈下可能變成錯誤引導。 | 定期檢視並汰換陳舊產物，或設計版本化的技能庫。 |
| **驗證器過於脆弱** | 若驗證器對輸出格式要求過嚴，可能低估代理真實能力。 | 設計語意等價判斷，並輔以人工抽樣檢查。 |
| **單一軸向評估不足** | 真實產品通常同時擴充工具、技能與代理。 | 在單軸向分析後，進行組合軸向的壓力測試。 |

- **向量記憶與技能庫**  
  對於自我演化適應評估，可將累積經驗儲存於向量資料庫或結構化技能庫，並在每次工具鏈擴張時重新索引，避免陳舊產物干擾。

| accumulated experience | 累積經驗 | 代理在較早期、較狹窄工具鏈下累積的經驗或產物 |
