## ⚡ TL;DR

過往PLC程式生成僅評估獨立POU，缺乏專案整合與即時執行驗證。
本文提出SemaPLC，以專案導向生成與外部驗證閘控機制確保程式正確完成。
在兩項評測中均達最高通過率，動態執行分數顯著優於基線，證明執行驗證最關鍵。

## 摘要翻譯

可程式化邏輯控制器（Programmable Logic Controller, PLC）運行於工業廠房，而大型語言模型（Large Language Model, LLM）已能為其生成獨立的程式組織單元（Program Organization Unit, POU）。然而，這類邏輯能否整合至既有 PLC 專案並正確執行，目前僅在有限測試中受到檢驗。我們提出 SemaPLC，一個專案導向的（Project-Grounded）且驗證閘控的（Verification-Gated）智慧代理框架（Agent Harness），它由傳統工具組裝而成，但受嚴格的完成規則約束。不同於在模型自行認定輸出已足夠時便停止，SemaPLC 僅在已記錄的外部檢查確認無誤後，才宣告任務完成。這些檢查涵蓋規格、編譯（Compilation），以及即時執行環境（Live Runtime）中的行為。在 117 項與現有基準相符的獨立 POU 任務中，SemaPLC 在全部七個模型上均達到最高的嚴格驗證通過率（Verified Pass Rate）（平均 72.6%）。在一個由 65 項任務組成的專案情境任務組（Project-Context Track）中，其生成邏輯必須在實際專案內編譯並執行，SemaPLC 在整合編譯、靜態行為（Static Behavior）與動態行為（Dynamic Behavior）上均達到最高平均值。在三個層次中，動態行為最具鑑別力。我們透過將生成邏輯與參考邏輯（Reference Logic）部署至即時 PLC 執行環境，並比較兩者的執行軌跡（Executed Trace）來衡量它。所有方法的靜態分數彼此相差在 10 個靜態分點以內，而動態分數則顯著區隔各方法：基線方法介於 22.4 至 31.4 之間，SemaPLC 則達到 52.2。整體而言，我們的驗證閘控框架在每個層次都提升了平均值，且在執行階段最為顯著。執行，而非靜態評分，才是判斷生成控制邏輯是否真正有效運作的忠實測試。SemaPLC 已開源於 https://github.com/midea-ai/SemaPLC。

### 核心貢獻（3～5點）
- 提出 SemaPLC，一個專案導向且驗證閘控的智慧代理框架，以已記錄的外部檢查（規格、編譯、即時執行環境行為）作為任務完成條件，避免僅依賴模型自我評估。
- 在 117 項獨立 POU 任務中，於七個模型上均取得最高的嚴格驗證通過率，平均達 72.6%。
- 建立 65 項專案情境任務組，要求生成邏輯在真實專案中編譯與執行，並在整合編譯、靜態行為與動態行為上達到最高平均表現。
- 強調動態行為是評估生成控制邏輯最關鍵的指標：透過即時 PLC 執行環境比較生成邏輯與參考邏輯的執行軌跡，顯著區隔基線與 SemaPLC（動態分數 22.4–31.4 對 52.2）。
- 開源 SemaPLC，提供可重現的驗證閘控 PLC 程式碼生成流程。

### 適合對象
從事工業控制、PLC 程式碼生成、大型語言模型代理系統，以及形式或實證驗證的研究人員與工程師；特別適合關注如何將生成邏輯整合至真實專案，並透過實際執行層驗證其正確性的讀者。

## 深度分析

#### 方法論解析

SemaPLC 的核心並非提出一套全新的生成模型，而是設計一個「驗證閘控的（verification-gated）」智慧代理框架（agent harness），把現成的編譯、形式驗證與即時執行環境（live runtime）整合成對大型語言模型（LLM）具有約束力的回饋迴路。其方法論可從三個設計原則理解：

1. **專案導向的生成（project-grounded generation）**  
   不同於以往只給定需求就產生獨立 POU（independent POU）的做法，SemaPLC 把生成與編輯錨定在既有專案脈絡中。具體而言，模型必須參考現有的功能區塊（function block）函式庫、變數宣告、型別與介面，並遵守專案的建置（build）、重設（reset）、初始化（initialization）與安全慣例（safety convention）。這讓產出的結構化文字（ST）不是孤立的程式片段，而是能嵌入真實 IEC 61131-3 專案、與其他邏輯協同運作的元件。

2. **多來源驗證（multi-source verification）**  
   框架把三類外部結果視為「第一類證據」：  
   - **規格檢查（specification check）**：對照控制需求衍生的屬性或斷言；  
   - **編譯（compilation）**：確認整合後的專案能通過編譯；  
   - **即時執行環境驗證（live runtime validation）**：將生成邏輯與參考邏輯（reference logic）部署到真實 PLC runtime，在相同情境輸入下比較執行軌跡（executed trace）。  
   這三層分別對應「能不能放進專案」、「靜態行為（static behavior）是否看似正確」、以及「動態行為（dynamic behavior）在真實時間與狀態演變下是否正確」。

3. **驗證閘控迭代（verification-gated iteration）**  
   這是 SemaPLC 與一般「模型自評後即終止」流程的根本差異。代理不能憑自身判斷結束任務，只有在工具日誌（tool log）確認通過後才能宣告完成；若結果顯示失敗、缺漏或不確定，就必須修復或回報未完成。此外，任何編輯都會使先前的驗證裁決失效，而每一個宣稱的通過都會被交叉比對日誌。這形成一種「交付完整性保證（delivery-integrity guarantee）」：通過與否不是由模型說了算，而是由外部、可稽核的檢查紀錄決定。

在任務設計上，作者區分兩條互補的評估軌道：

- **Function track（獨立 POU 任務組）**：使用 117 個獨立 POU 任務，與現有基準（如 Agents4PLC）對齊。評分由一個不可被查詢的獨立形式評審執行，採用嚴格的 verified pass 標準：需求衍生的屬性中至少 80% 被形式驗證滿足，且任何不確定結果都視為失敗。  
- **Project-context track（專案情境任務組）**：使用 65 個來自 Spec2Control 的工業廠房任務，橫跨十座真實廠房模型。系統必須把生成邏輯整合進既有 ST 專案，並分別報告整合編譯（integrated compilation）、靜態行為與動態行為三項分數。

整體而言，SemaPLC 把 PLC 程式生成從「單次生成—靜態檢查」提升到「專案嵌入—多層驗證—執行軌跡比對」的閉環，並以嚴格的完成規則確保每一個宣稱成功的案例都經過外部工具背書。

#### 實驗數據解讀

論文在兩條軌道上都給出了具體數字，最值得關注的是「靜態分數拉不開，動態分數才顯真章」的現象。

**Function track（117 個獨立 POU 任務）**  
SemaPLC 在七個模型上都取得最高的嚴格驗證通過率（verified pass rate），平均達 72.6%。這表示即使在與既有基準對齊、只評估獨立 POU 的情境下，把編譯器回饋修復（compiler-in-the-loop repair）、形式 / 屬性驗證（formal / property checking）與迭代修復納入閉環，仍能穩定提升通過率。由於評審是 held-out 且把不確定結果視為失敗，這個數字相對保守，也更能反映真實可靠性。

**Project-context track（65 個專案整合任務）**  
這裡的關鍵是三層指標：

- **整合編譯（integrated compilation）**：生成邏輯能否無誤地併入既有專案並編譯通過。這是進入後續驗證的門檻。  
- **靜態行為（static behavior）**：根據需求在程式文字上檢查屬性，例如狀態轉換、互鎖（interlock）條件、計時器設定等。  
- **動態行為（dynamic behavior）**：將生成邏輯與參考邏輯同時部署到 live runtime，在相同情境輸入下比較執行軌跡，採用 golden-trace differential 計分。

實驗結果顯示，所有方法在靜態行為上的差距都在 10 分以內，但動態行為卻出現明顯分離：基線方法僅 22.4–31.4 分，而 SemaPLC 達到 52.2 分。這個差距說明了幾件事：

1. **靜態檢查不足以區分可靠與不可靠的方法**  
   編譯通過與形式屬性滿足，只能保證程式在語法與部分邏輯結構上沒有明顯錯誤。許多實際缺陷——例如計時器（TON timer）設定錯誤、狀態轉換時序偏差、重設條件遺漏、輸出驅動時機錯誤——只有在真實時間推進與狀態演變中才會顯現。

2. **動態行為是更忠實的品質指標**  
   論文強調「Execution, not static scoring, is the faithful test」。對於持續執行、對時間與狀態敏感的 PLC 程式而言，執行軌跡比對能捕捉靜態分析難以發現的時序與交互錯誤。

3. **SemaPLC 的優勢在 runtime 層最明顯**  
   雖然 SemaPLC 在整合編譯與靜態行為也取得最高平均分，但領先幅度最大的地方是動態行為。這驗證了「驗證閘控迭代」確實能迫使模型修復那些只在執行時才會暴露的問題。

4. **最強模型的領先幅度縮小**  
   作者提到 SemaPLC 在每個模型上都表現最好，但在最強模型上領先幅度變窄。這暗示當基礎模型本身具備較強的程式推理能力時，框架的邊際效益會下降，但即便如此，驗證閘控仍能帶來可觀的動態行為提升。

總結來說，實驗數據支持論文的核心論點：對 PLC 控制邏輯而言，執行層的評估不可或缺；只停留在編譯或靜態層面的評分，會讓方法之間的真實差距被掩蓋。

#### 與現有研究的比較

SemaPLC 與先前研究的關係可從「能力光譜」與「評估哲學」兩個維度來定位。

**能力光譜上的位置**

- **LLM4PLC** 開創了結合編譯器與 SMV 形式回饋、並由使用者引導迭代的 ST 生成。  
- **AutoPLC** 聚焦廠商整合開發環境（vendor IDE）內的編譯器驅動除錯，強調案例檢索與 API 推薦。  
- **Agents4PLC** 提出五代理閉環，引入 PLCverif 驗證與測試平台展示，並提供 117 個任務的基準。  
- **Spec2Control** 則從廠房敘述生成圖形化控制邏輯，強調從規格到控制結構的轉換。  
- 商業輔助工具（如 Siemens、CODESYS 的 copilot）則把 LLM 嵌入廠商 IDE，但評估多以獨立 POU 或有限案例為主。

相較之下，SemaPLC 不強調單一生成技術，而是把上述元素（編譯器回饋修復、形式 / 屬性驗證、多代理迭代、vendor IDE、實體 / 模擬測試平台）統整到一個受外部驗證閘控的框架中。它的貢獻不在於「有哪些工具」，而在於「這些工具如何決定任務是否完成」。

**評估哲學上的差異**

過去研究雖然也會執行生成程式以證明「可以跑」，但多半是示範性質（demonstrated, not measured）。也就是說，它們展示生成邏輯能夠執行，卻沒有在基準規模上系統性地測量「有多可靠」。SemaPLC 的區別在於：

- 把 runtime 證據從「展示」提升為「測量」；  
- 在跨方法、跨模型的層級上統一評估專案整合與動態行為；  
- 將整合編譯、靜態行為、動態行為分開計分，使每一層的失敗都清晰可見。

**與形式驗證的互補關係**

PLCverif 等工具能把 ST 與需求模式轉成模型檢查器輸入，提供強保證。但實務上，TON 計時器或過大狀態空間可能導致「不支援」或「無結論」的結果。SemaPLC 並不用 runtime 驗證取代形式驗證，而是將兩者並列：形式驗證處理可形式化的靜態屬性，runtime 驗證則直接觀察時間與狀態行為，補足形式方法難以涵蓋的時序與交互問題。

**主要限制**

儘管 SemaPLC 在方法論與評估上都有顯著進展，仍有幾項限制值得注意：

- **語言範圍**：目前主要聚焦結構化文字（ST），對於階梯圖（Ladder Diagram）、功能區塊圖（Function Block Diagram）等圖形化 IEC 61131-3 語言的適用性尚未探討。  
- **任務規模**：Project-context track 使用 65 個任務、十座廠房，雖已比過去的有限測試擴大，但相較於一般軟體工程的程式生成基準仍屬小型。  
- **參考邏輯與情境輸入**：動態行為採用 hidden reference 與預設情境輸入，若情境覆蓋不足，可能遺漏邊緣錯誤。  
- **形式驗證的保守性**：把不確定結果視為失敗雖然嚴格，但也可能低估那些因工具限制而非邏輯錯誤造成的失敗。  
- **成本與延遲**：驗證閘控迭代需要多次呼叫 LLM 與外部工具，對於實際部署的延遲與計算成本，論文未提供詳細分析。

#### 可重現性評估

可重現性是這類系統論文的關鍵。從目前資訊來看，SemaPLC 在以下幾個層面具備不錯的開放基礎：

- **原始碼開源**：論文明確指出 SemaPLC 已於 GitHub 開源（https://github.com/midea-ai/SemaPLC），這讓其他研究者可以取得智慧代理框架（agent harness）的實作、工具整合邏輯與驗證閘控流程。  
- **使用現有公開基準**：Function track 建立在 Agents4PLC 的 117 個任務上；Project-context track 使用 Spec2Control 的工業廠房資料。這些外部資料集若本身可取得，則任務定義與評分標準較易複製。  
- **模型權重無需釋出**：由於 SemaPLC 是模型無關的框架，使用的是現成 LLM（七個模型），因此不需要作者釋出模型權重，研究者可用相同 API 或開源模型重跑。

然而，可重現性也面臨一些挑戰：

- **Live runtime 與 hidden reference**：動態行為需要將程式部署到真實 PLC runtime，並與隱藏的參考邏輯比對執行軌跡。若 runtime 環境、參考邏輯或情境輸入未完整釋出，其他團隊難以完全複製動態分數。  
- **形式驗證工具鏈**：PLCverif、SMV、各廠商編譯器等外部工具的版本與設定會影響結果。論文需要清楚說明工具版本、逾時設定、屬性轉換規則等細節。  
- **日誌與隨機性**：LLM 生成具有隨機性，若論文未提供種子、溫度參數與完整工具日誌，則 exact 數字可能難以完全重現。  
- **專案模板與介面**：Project-context track 需要既有 ST 專案的函式庫、變數宣告與建置設定，這些專案資產的釋出程度會直接影響可重現性。

整體而言，SemaPLC 在「方法與框架」層面具備高可重現性，但在「動態行為評分所需的 runtime 與參考資料」層面，仍需作者進一步釋出環境設定與資料，才能讓其他研究者完全複製論文數據。

#### 未來研究方向

SemaPLC 為 PLC 程式生成建立了專案導向與驗證閘控的典範，未來可沿以下方向延伸：

1. **擴展至圖形化 IEC 61131-3 語言**  
   目前聚焦結構化文字（ST），未來可研究如何將相同框架應用於階梯圖（Ladder Diagram）、功能區塊圖（Function Block Diagram）與順序功能圖（Sequential Function Chart），並處理圖形語言的語法與語意驗證。

2. **多 POU 與全專案層級生成**  
   現階段仍是以單一需求產生單一邏輯單元為主。未來可探索跨多個 POU、功能區塊（function block）與任務的協同生成，並處理模組間介面與全域狀態的一致性。

3. **實體硬體在環（hardware-in-the-loop）驗證**  
   目前動態行為使用 live runtime，但未來可進一步結合實體 PLC 或硬體在環模擬，驗證真實 I/O 時序、通訊延遲與硬體特定行為。

4. **結合形式驗證與 runtime 驗證的混合保證**  
   針對形式驗證不支援的 TON 計時器與大狀態空間問題，可研究如何自動抽取「可形式化子性質」與「需 runtime 驗證子性質」，並讓兩者互補，減少不確定結果被過度保守地計為失敗。

5. **更豐富的需求規格語言**  
   目前需求多以自然語言或有限屬性呈現。未來可引入時序邏輯（如 STL、PSL）或工業標準（如 ISA-88、ISA-95）的結構化規格，提升需求到驗證屬性的自動轉換率。

6. **主動學習與廠商函式庫檢索增強**  
   結合檢索增強生成（RAG）從廠商函式庫、OSCAT 函式庫或企業內部專案檢索相似案例，並在驗證失敗時主動學習正確用法，減少反覆試誤。

7. **安全性、認證與可解釋性**  
   工業控制對安全完整性等級（SIL）與認證有嚴格要求。未來可研究如何讓 SemaPLC 的驗證日誌、修復歷程與執行軌跡成為可審查的證據，支援功能安全認證。

8. **線上監控與持續驗證**  
   把生成階段的驗證閘控延伸到部署後的線上監控，當現場運行軌跡偏離預期時自動告警或觸發重新生成。

9. **跨廠商與跨語言可攜性**  
   不同 PLC 廠商的編譯器、資料型別與 runtime 行為存在差異。未來可研究如何讓框架自動適應 Siemens、Rockwell、Mitsubishi、CODESYS 等不同生態系。

10. **成本—效益權衡與人機協作**  
    驗證閘控迭代會增加計算成本與延遲。未來可研究何時應讓人類工程師介入、如何優先處理高風險驗證失敗，以及在資源受限下最大化動態行為分數的策略。

總體而言，SemaPLC 不僅提出了一個更嚴謹的 PLC 程式生成框架，也為未來工業控制領域的「生成—驗證—部署」全生命週期自動化奠定了方法論與評估基礎。

## 論文問答

**Q1：SemaPLC 主要想解決什麼問題？**
A：SemaPLC 針對的是將大型語言模型（LLM）生成的可程式化邏輯控制器（PLC）程式組織單元（POU）真正整合到既有專案並在實際執行環境中正確運作的挑戰。過去的研究大多只評估獨立 POU 的生成能力，卻忽略了生產現場中控制邏輯必須與現有功能區塊、變數、型別、介面以及安全慣例相容的事實。因此，本文把「專案導向的生成」與「正確的即時執行行為」視為兩個必須被量化測量的核心需求。

**Q2：現有的 LLM PLC 程式生成方法為何不足？**
A：現有方法多半在獨立 POU 層級進行評估，並且僅以有限案例展示程式可以執行，而非在基準規模上測量其可靠度。它們通常讓模型自行判斷輸出是否足夠，缺乏統一且跨方法、跨模型的專案整合與執行期評估。結果是，編譯或靜態檢查通過的程式仍可能在計時器設定、狀態轉換、重設或互鎖等動態行為上出錯，卻無法被現有評估方式有效揭露。

**Q3：為什麼說「執行」才是檢驗生成控制邏輯是否可用的忠實標準？**
A：因為編譯成功與靜態屬性驗證只能保證語法或部分規格正確，無法發現計時器錯誤組態、錯誤狀態轉換、遺漏重設或輸出時序異常等執行期缺陷。本文的實驗顯示，所有方法在靜態行為分數上的差距都在 10 分以內，但動態行為分數卻能清楚區分方法優劣，基線僅 22.4 至 31.4 分，而 SemaPLC 達到 52.2 分。這說明若評估停在靜態層面，將無法區分可靠與不可靠的生成方法。

**Q4：SemaPLC 的核心方法是什麼？**
A：SemaPLC 是一個「專案導向、驗證閘控」的智慧代理框架，它把生成、編輯與修復錨定在目標專案情境中，並以三種外部驗證結果作為第一類證據：規格檢查、編譯檢查以及即時執行環境驗證。框架不允許代理憑自身判斷結束任務，只有在記錄下來的外部檢查確認成功後，才會宣告完成。當驗證結果顯示失敗、缺漏或不確定時，代理必須進行修復或回報未完成。

**Q5：SemaPLC 的關鍵創新在哪裡？**
A：其創新不在於引入全新的單一工具，而在於建立一套嚴格的「完成紀律」來統合既有工具。具體而言，任務終止必須有外部驗證日誌佐證，任何程式編輯都會使先前的驗證裁決失效，而每一個宣稱的通過都會被交叉比對工具日誌。這種設計提供了固定管線所缺乏的交付完整性保證，確保模型不會因自我評估過度樂觀而提前結束。

**Q6：SemaPLC 為何採用「專案導向、多源驗證、驗證閘控」三項設計原則？**
A：「專案導向」確保生成的結構化文字（ST）能夠重複使用既有功能區塊、變數與介面，並遵循專案的重設、初始化與安全慣例。多源驗證同時納入規格、編譯與即時執行環境三種證據，以彌補單一檢查的盲點。驗證閘控則防止代理在沒有外部確認的情況下終止，從而形成一個以客觀結果為依據的迭代修復迴路。

**Q7：SemaPLC 使用了哪些評估任務組？**
A：論文設計了兩個互補的任務組：功能任務組包含 117 個獨立 POU 任務，沿用既有基準以便公平比較，並由一個不可被查詢的獨立形式法官進行嚴格驗證。專案情境任務組則包含來自 Spec2Control 的 65 個任務，涵蓋十座工業廠房，要求生成的邏輯必須整合到真實的 ST 專案中並能執行。兩者分別測量獨立能力與部署能力，並非同一任務的前後階段。

**Q8：SemaPLC 的關鍵實驗結果是什麼？**
A：在功能任務組上，SemaPLC 在七個模型上都達到最高的嚴格驗證通過率，平均值為 72.6%。在專案情境任務組上，它在整合編譯、靜態行為與動態行為三項指標上都取得最佳平均表現。特別是動態行為層面，基線方法分數僅 22.4 至 31.4，而 SemaPLC 達到 52.2，顯示驗證閘控框架對執行期正確性的提升最為顯著。

**Q9：分層評分揭示了什麼重要現象？**
A：分層評分顯示，所有方法在靜態行為上的差距很小，通常不到 10 分，因此單靠靜態評估無法區分方法的可靠程度。相對地，動態行為分數能夠明顯區分基線與 SemaPLC，說明執行軌跡比較是發現真正缺陷的關鍵。SemaPLC 在每一層都提升了平均表現，但在執行期這一層的提升幅度最大，進一步證明「執行才是忠實測試」的論點。

**Q10：SemaPLC 在實務上可以應用在哪些場景？**
A：SemaPLC 適用於工廠產線、發電廠、水處理設施等需要將新控制邏輯整合到既有 PLC 專案的場景。在這些環境中，生成的程式不僅要編譯成功，還必須與現有功能區塊庫、變數宣告、介面與安全慣例相容。透過在真實即時執行環境中部署並比較執行軌跡，SemaPLC 能在交付前確認控制邏輯確實符合規格。

**Q11：若將 SemaPLC 產品化，需要考慮哪些因素？**
A：首先，SemaPLC 是開源框架，可以整合到廠商整合開發環境或持續整合／持續部署（CI/CD）管線中，作為自動化驗證閘道。其次，所有驗證結果都以日誌形式記錄，這為工業應用提供了可追溯的審計依據。最後，嚴格的完成規則能降低未經驗證邏輯被部署到現場的風險，對安全關鍵系統尤為重要。

**Q12：SemaPLC 對工業自動化領域可能帶來什麼影響？**
A：它把評估焦點從「獨立 POU 展示」轉移到「專案整合與執行期測量」，有助於建立更貼近真實部署的基準。這種轉變能促使 LLM 生成的 PLC 程式在進入現場前，先經過客觀且可重複的執行驗證。長期而言，它有助於提升工業控制系統的可靠性，並加速智慧代理在自動化領域的安全採用。

**Q13：SemaPLC 有哪些已承認的限制？**
A：動態行為評估需要隱藏的參考邏輯與即時執行環境，這增加了基準建置與維護的成本。形式驗證在面對 TON 計時器或過大狀態空間時，可能回傳不確定或無法支援的結果，這些情況會被計為失敗。此外，雖然 SemaPLC 在所有模型上都表現最佳，但在最強模型上的領先幅度會縮小，顯示仍有進步空間。

**Q14：SemaPLC 可能在哪些情況下失敗？**
A：當需求無法被形式化為可驗證屬性，或參考邏輯的執行軌跡難以取得時，驗證閘控可能無法給出明確通過裁決。若生成的邏輯與既有專案介面不匹配，例如變數型別或功能區塊簽章錯誤，整合編譯就會失敗。此外，即使編譯與靜態檢查通過，錯誤的計時器設定或狀態轉換仍可能導致動態執行軌跡與參考邏輯不一致。

**Q15：未來可以朝哪些方向延伸 SemaPLC？**
A：未來可將框架擴展到 IEC 61131-3 的其他語言，例如階梯圖或功能區塊圖，並支援更豐富的專案情境與廠商特定函式庫。結合更強大的自動修復策略、實體測試平台驗證，以及形式驗證與執行期驗證的互補使用，也能進一步提升可靠度。最後，建立更大規模、涵蓋更多工業領域的專案情境基準，將有助於持續推動 LLM PLC 程式生成技術的實務落地。

## 實務應用指南

### 適用場景

1. **既有廠區擴充新製程單元**  
   工廠已有一套運行中的 PLC 專案，需要新增一段控制邏輯（例如新增一組馬達順序啟動、溫度迴路或輸送帶站點）。SemaPLC 可將新 POU 生成於既有專案脈絡中，並透過編譯、靜態與動態驗證確認其能與現有功能區塊、變數與互鎖機制正確整合。

2. **老舊 ST 程式重構與移植**  
   面對缺乏文件、變數命名混亂或廠商停產的既有結構化文字（ST）專案，可利用 SemaPLC 以自然語言規格為輸入，在保留專案介面與安全慣例的前提下重寫控制邏輯，並以即時執行環境的軌跡比對驗證新舊邏輯行為一致性。

3. **規格變更導致的控制邏輯快速迭代**  
   當產品換線、配方調整或法規要求改變時，控制需求會頻繁變動。SemaPLC 的驗證閘控機制可在每次規格更新後自動執行編譯器回饋修復、形式/屬性驗證與即時執行環境測試，避免人為遺漏靜態檢查或動態測試。

4. **作為廠商 IDE 智慧輔助的品質閘道**  
   可將 SemaPLC 與 Siemens TIA Portal、CODESYS 等廠商整合開發環境的 LLM Copilot 串接，作為「生成後的強制檢查層」。無論模型如何生成程式碼，只有通過外部工具紀錄的編譯、靜態與動態驗證，才允許進入版本控制或下載至現場 PLC。

5. **教學與標準化控制邏輯開發**  
   在設備製造商或系統整合商內部，可用 SemaPLC 建立統一的生成—驗證流程，確保不同工程師產出的 POU 都符合公司功能區塊庫、初始化/重設慣例與安全互鎖規範，並留下可稽核的驗證紀錄。

### 實作步驟建議

1. **專案脈絡盤點與介面凍結**  
   將既有專案匯出為機器可讀格式，建立功能區塊目錄、變數命名規則、資料型態對照表與安全慣例清單。確保這些資訊能在生成階段餵入模型，避免模型虛構變數或介面。

2. **需求結構化與驗證項目定義**  
   將自然語言規格拆解為：輸入/輸出介面、狀態轉換條件、計時器/計數器設定、互鎖條件與初始化/重設行為。同步產生規格檢查腳本、形式屬性與動態測試情境。

3. **建置 SemaPLC 工具鏈**  
   將編譯器、靜態檢查器、形式驗證器與即時執行環境封裝為代理可呼叫的工具，並確保每次呼叫都會回傳結構化結果與原始日誌。設定「編輯即失效」機制：任何程式碼修改後，先前的驗證結果必須重新執行。

4. **設定驗證閘控終止條件**  
   依據應用嚴謹度定義通過門檻，例如：編譯必須成功、靜態行為分數 ≥ 80、動態行為分數 ≥ 80，且所有工具日誌必須存在。禁止模型僅憑自身判斷結束任務。

5. **執行專案導向生成與迭代修復**  
   讓代理在既有專案脈絡中生成或編輯 POU，並依序執行規格檢查、編譯、靜態驗證與動態軌跡比對。任一層失敗時，代理必須根據工具診斷訊息修復，而非自行推測。

6. **動態行為確認與黃金軌跡比對**  
   將生成後的整合專案部署至即時執行環境，在相同測試情境下同時執行參考邏輯與生成邏輯，比較輸出軌跡、狀態切換時序與計時器行為。動態分數是區分可靠與不可靠方法的關鍵指標。

7. **人工審查、簽核與部署**  
   即使通過所有自動驗證，安全相關或高風險變更仍需經過控制工程師審查。將通過的 POU、工具日誌與軌跡報告一併提交至版本控制系統，再下載至現場 PLC。

### 潛在風險與注意事項

- **模型虛構專案符號**  
  LLM 可能生成不存在的功能區塊或變數名稱。應在提示詞中強制引用專案符號表，並以編譯器回饋修復作為第一道防線。

- **形式驗證結果不確定**  
  TON 計時器、大狀態空間或翻譯失敗可能導致形式檢查回傳「不確定」。此類結果應視為失敗，並轉由動態測試補強，不可直接放行。

- **靜態分數高但執行時失敗**  
  論文顯示各方法靜態分數差距常在 10 分以內，但動態分數差距可達兩倍以上。切勿僅以編譯成功或靜態行為分數作為上線依據。

- **即時執行環境的再現性**  
  現場 PLC 掃描週期、I/O 延遲與模擬器可能不同。建議在與目標機型相同或相近的 runtime 上驗證，並記錄掃描週期與輸入時序。

- **過度迭代導致成本與延遲**  
  每次失敗都觸發 LLM 呼叫與工具執行，可能累積大量 token 與時間。應設定最大迭代次數與逾時機制，並在無法收斂時強制轉人工處理。

- **安全關鍵系統的人為把關**  
  SemaPLC 是自動化輔助工具，不能取代功能安全（如 IEC 61508/61511）要求的人員審查、風險評估與簽核流程。

- **工具日誌的真實性與完整性**  
  驗證閘控依賴外部工具日誌，應確保日誌不可被代理竄改，並採用唯讀儲存或數位簽章機制保存。

### 與其他技術的整合建議

- **廠商 IDE 與 Copilot**

- **SCADA / MES 與數位孿生**  
  透過 OPC UA 或 MQTT 將即時執行環境的測試軌跡餵入數位孿生平台，進行更長週期的行為比對與異常偵測；驗證通過的邏輯再經由 MES 下發至現場設備。

- **需求管理與追溯工具**  
  將規格檢查項目與需求管理系統（如 IBM DOORS、Siemens Polarion）連結，確保每個生成的 POU 都能追溯到原始需求，並在需求變更時自動觸發重新驗證。

- **知識庫與檢索增強生成（RAG）**  
  將公司內部功能區塊庫、過往驗證報告與常見編譯錯誤解決方案建立為向量資料庫，在生成前提供模型檢索結果，提升專案導向生成的準確度。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「適用場景」與「實作步驟建議」讀起，理解 SemaPLC 是一套「讓 AI 寫 PLC 程式，但必須通過外部檢查才能算完成」的自動化框架。不必深究形式驗證細節，重點掌握「專案導向」與「驗證閘控」兩個核心概念，以及為何動態執行比單純編譯更重要。

**AI 工程師**  
請聚焦論文中的代理框架設計、三層驗證（規格檢查、編譯、即時執行環境）與終止條件實作。特別注意「編輯會使先前驗證結果失效」與「禁止模型自行判斷完成」這兩條紀律，這是將一般程式生成代理轉化為高可靠工業控制代理的關鍵。

**研究人員**  
建議深入比較兩個任務組的評估設計：獨立 POU 任務組用於公平對照既有基準，專案情境任務組則揭示靜態與動態評估之間的落差。可進一步探索如何擴充形式驗證覆蓋率、降低不確定結果比例，以及設計更貼近真實干擾與時序變異的動態測試情境。

**產品經理**  
請將本文視為一個「可落地的品質閘道」產品雛形。關注其商業價值：縮短控制邏輯開發週期、降低現場除錯成本、建立可稽核的驗證紀錄。同時評估導入風險，包括安全關鍵應用的人為審查需求、與現有廠商 IDE 的整合成本，以及 LLM 推論與反覆驗證帶來的營運支出。
