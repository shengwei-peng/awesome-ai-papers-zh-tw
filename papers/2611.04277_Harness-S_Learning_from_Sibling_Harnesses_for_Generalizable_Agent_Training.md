Harness-S 的方法論建立在對 Harness 演化過程三個關鍵觀察之上：**局部性（Locality）**、**互補性（Complementarity）** 與**非平穩性（Nonstationarity）**。這三個特性揭示了傳統單一 Harness 優化路徑的根本侷限，並為整個方法設計提供了理論基礎。

**方向性 Harness 演化（Directional Harness Evolution）** 是整個管線的起點。與傳統的累積式 Harness 編輯不同，此方法從基礎 Harness H₀ 開始，先診斷執行軌跡（Trajectory）中的失敗模式，再讓每個子代 Harness 僅針對一組有限的相關根因進行修復。這種「分而治之」的策略避免了不同修復方向之間的相互干擾——這正是圖 1a 所展示的局部性問題的根源。透過聯合驗證覆蓋率（Joint Validation Coverage）選擇下一輪的父代集合，所有可執行且符合協議的變體都被保留，形成一個**兄弟型 Harness 池（Sibling Harness Pool）**。這個池在整個策略訓練過程中保持固定，這是一個重要的設計選擇：它將 Harness 演化與策略訓練解耦，避免了反覆生成與驗證變體的巨大成本。

**互補式 Harness 救援訓練（Complementary Harness Rescue Training）** 是核心訓練機制。當策略在 H₀ 下所有初始推演（Rollout）都失敗時，**自適應 Harness 路由器（Adaptive Harness Router）** 從兄弟型 Harness 池中選擇 Top-k 個輔助 Harness（Harness），同一策略從任務初始狀態重新生成推演。這些「救援推演」取代失敗的群組用於強化學習（Reinforcement Learning）。關鍵設計在於：學習訊號來自策略自身在不同 Harness 下的行為，而非來自不同策略。這使得共享策略能夠從互補的執行支援中學習，並在返回 H₀ 時保留所獲得的行為。

**自適應 Harness 路由器** 使用**行為特徵檔（Harness Behavior Profiles）** 與多個 LLM 的獨立投票來匹配任務與 Harness。行為特徵檔描述了每個變體在哪些任務條件下對當前策略有助益或妨礙（相對於 H₀）。為應對非平穩性，**策略感知特徵檔重新錨定（Policy-aware Profile Re-anchoring）** 會定期從當前策略的驗證軌跡刷新特徵檔，確保路由與學習中的策略保持對齊。投票機制結合了驗證證據與相似任務的表現，每個 LLM 投票者根據自身判斷給出排名，Top-k 選擇基於加權分數聚合。

整體方法論的精妙之處在於其「學習後返回」的設計哲學：訓練階段使用多樣化的 Harness 支援，但最終部署與評估仍使用原始 H₀。這使得 Harness-S 訓練出的策略具有真正的泛化能力，而非僅僅依賴特定的執行支援。

### 實作步驟建議

**階段一：基礎 Harness 與基準建立（2-4 週）**
1. 選定基礎 Harness H₀（建議從 DeepSeek Harness 或 SWE-agent 開始）
2. 在目標基準（AppWorld / SWE-Gym / DBBench）上跑出 baseline pass@K 數據
3. 收集失敗軌跡並進行初步根因分類

**階段二：方向性 Harness 演化（4-6 週）**
1. 根據根因分類設計 3-5 個「修復方向」（如：分頁處理、欄位推斷、錯誤恢復等）
2. 為每個方向生成對應的兄弟型 Harness 變體
3. 執行聯合驗證（joint validation coverage），篩選出協議合規且可執行的變體
4. 建立 Sibling Harness Pool，固定後續不再變動

**階段三：行為特徵檔與路由器建立（2-3 週）**
1. 在驗證集上跑出每個兄弟型 Harness 相對於 H₀ 的成敗對照
2. 為每個 Harness 建立 Harness Behavior Profile（描述其在哪些任務條件下有助/有害）
3. 實作多 LLM 投票機制，產出 Top-k 路由器

**階段四：互補式救援訓練（4-8 週）**
1. 整合 GRPO 訓練流程，加入「全失敗時呼叫路由器」的分支邏輯
2. 訓練過程中定期執行 policy-aware profile re-anchoring（建議每 N 個 checkpoint 一次）
3. 監控策略在 H₀ 下的表現，確保救援獲得的能力能遷移回原 Harness

**階段五：Rank-1 推論整合（1-2 週）**
1. 將訓練好的路由器複用於推論階段
2. 對單次推論失敗的任務，自動調用 Top-k 兄弟型 Harness 進行補救
3. 評估整體系統在原始 H₀ 與 Rank-1 模式下的表現差距

### 潛在風險與注意事項

**風險一：行為特徵檔漂移導致路由失效**
隨著策略學習，Harness 的相對效用會發生非平穩變化。若未及時重新錨定，路由器會把任務送往已不再有效的兄弟型 Harness。
**緩解**：嚴格執行 policy-aware profile re-anchoring 排程；監控路由器選擇的 Harness 在驗證集上的實際勝率，若低於閾值則觸發緊急重新錨定。

**風險二：救援訓練引入分布外行為**
救援 rollouts 來自兄弟型 Harness 下的軌跡，可能與 H₀ 下的軌跡分布差異過大，導致策略學習到「只在特定 Harness 下才有效」的行為。
**緩解**：定期在 H₀ 下評估訓練中的策略；若 H₀ 表現下降而救援表現上升，需降低救援比例或調整獎勵設計。

**風險三：兄弟型 Harness Pool 過大導致路由成本過高**
Pool 中變體過多時，Top-k 選擇與多 LLM 投票的計算成本可能超過訓練收益。
**緩解**：以互補性指標（如 oracle union 增益）篩選 Pool，保留真正互補的變體；對路由器做輕量化（如蒸餾成單一模型）。

**風險四：方向性演化陷入局部修復**
若根因分類不夠細緻，多個兄弟型 Harness 可能集中在同一修復方向，喪失互補性。
**緩解**：在演化階段加入「修復方向正交性」檢查；若兩個變體的修復任務集合高度重疊，僅保留表現較佳者。

**風險五：基準過擬合**
在 AppWorld、SWE-Gym、DBBench 上的表現未必能遷移到真實業務場景。
**緩解**：保留一定比例的真實業務任務作為驗證集；定期以人類評估校準基準表現。

### 與其他技術的整合建議

**與既有代理框架整合**
Harness-S 的兄弟型 Harness 可設計為既有框架（如 LangChain、AutoGen、CrewAI）的 plug-in 模組。建議將 Sibling Harness Pool 封裝為可熱插拔的執行器集合，主訓練流程僅需在「全失敗」分支呼叫路由器即可。

**與模型蒸餾流程整合**
若團隊已有將大型模型蒸餾為小型模型的流程，可在蒸餾階段將「H₀ + 訓練後策略」與「Rank-1 路由器」共同作為教師訊號，讓小型模型同時學會何時該呼叫哪個兄弟型 Harness。

**與評估與監控系統整合**
Harness Behavior Profiles 可整合進現有的模型監控平台（如 LangSmith、Phoenix），作為「任務-Harness 匹配」的視覺化儀表板，協助團隊理解模型在不同任務上的行為偏好。

**與 CI/CD 流程整合**
將兄弟型 Harness 的演化與驗證流程納入 CI/CD：每次 Harness 變更提交時，自動跑驗證集並更新行為特徵檔；策略訓練完成後自動回歸到 H₀ 評估，確保遷移效果。

**與多代理協作系統整合**
在多代理架構中，不同代理可能使用不同 Harness。Harness-S 的路由器可擴展為「任務-代理-Harness」三層路由，根據任務特性選擇最合適的代理與其對應的兄弟型 Harness 組合。
