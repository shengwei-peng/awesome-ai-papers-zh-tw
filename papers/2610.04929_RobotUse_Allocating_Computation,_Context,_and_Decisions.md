## ⚡ TL;DR

現有介面常將機器人動作選擇隱藏於預定義工具，或要求代理管理繁複執行程式與歷史。
RobotUse 讓主代理決策意圖、子代理視覺選點姿態，後端處理運動規劃，並以操作手冊累積經驗。
在 RoboLab 達 45% 成功率，較 CaP-X 高 6.7 百分點，能從執行回饋學習與遷移。

## 摘要翻譯

機器人代理（robot agents）必須將意圖中的動作（intended actions）連結到觀察結果（observed outcomes），同時保留在多次嘗試中修正決策（decisions）所需的上下文（context）。現有介面常將這些決策保留在預定義工具（predefined tools）內，或要求代理（agents）管理詳細的執行程式碼（execution code）與日益增長的執行歷史（execution history）。我們提出 RobotUse，一個以指定與修正物理動作（physical actions）為核心來組織計算（computation）、上下文（context）與決策（decisions）的機器人代理框架（robot agent harness）。代理透過視覺選擇（visual selection）目標（targets）與姿態（poses），而後端（backend）負責處理幾何（geometry）、運動規劃（motion planning）與控制（control）。子代理（subagents）保留每個子目標（subgoal）內的詳細互動，並回傳後續決策所需的資訊。持續駕馭（continual harnessing）讓代理透過更新持久化操作手冊（persistent playbook）來從執行中學習。在 RoboLab 上，RobotUse 達到 45% 任務成功率（task success），以 6.7 百分點（percentage points）超越 CaP-X，同時維持精簡決策上下文（compact decision contexts），並減少對預定義動作抽象（predefined action abstractions）的依賴。此外，我們展示 RobotUse 即使在不完美回饋（imperfect feedback）下，仍能從真實世界執行（real-world execution）中學習，並將所學遷移（transfer）到後續任務。專案頁面見 https://robotuse-team.github.io/。

### 核心貢獻（3～5點）
- 提出 RobotUse，一個以「指定與修正物理動作」為核心的機器人代理框架，將高層決策、視覺選擇與後端幾何／運動規劃／控制明確分離。
- 設計主代理與子代理的分工機制：主代理維持精簡決策上下文，子代理處理各子目標內的詳細互動並回傳決策所需資訊。
- 透過持續駕馭與持久化操作手冊，使代理能從真實世界執行中累積經驗，並將所學遷移至後續任務。
- 在 RoboLab 基準上達到 45% 任務成功率，以 6.7 百分點領先 CaP-X，同時降低對預定義動作抽象的依賴。

### 適合對象
適合機器人學、具身智能（embodied AI）、大型語言模型代理，以及視覺—語言—動作系統的研究者；對長程多步驟機器人任務、真實世界執行回饋學習與跨任務遷移感興趣的讀者亦會有所收穫。

## 深度分析

#### 方法論解析

RobotUse 的核心貢獻在於提出一個 **intent-based agent harness（基於意圖的代理框架）**，將機器人任務中的 **computation（計算）**、**context（上下文）** 與 **decision（決策）** 圍繞「指定與修正物理意圖」重新分配。以下從設計哲學、雙層代理架構、後端介面、**playbook（操作手冊）** 與 **continual harnessing（持續駕馭）** 五個層面深入解析。

##### 1. 設計哲學：重新劃分模型推理與後端計算的邊界

論文開宗明義指出，通用代理設計的關鍵並非讓模型包辦所有事情，而是決定哪些責任應由 **model reasoning（模型推理）** 承擔，哪些應交給外部程式。對機器人操作而言，**physical action（物理動作）** 涉及 **high-dimensional continuous motion（高維度連續運動）**、**geometry（幾何）**、**contact constraint（接觸約束）** 與 **motion planning（運動規劃）** 等繁複計算；若將這些細節全部塞進模型的 **active context（作用中上下文）**，會導致 **execution history（執行歷史）** 膨脹、決策難以檢視與修正。RobotUse 因此採取「分層隔離」策略：

- **主代理（main agent）** 只保留任務層級的 **task intent（任務意圖）** 與高層 **decision（決策）**；
- **子代理（subagent）** 在局部 **context（上下文）** 中處理單一 **subgoal（子目標）** 的視覺選擇與微調；
- **robot backend（機器人後端）** 負責將視覺選擇轉換為實際軌跡與 **control（控制）**。

這種劃分讓模型專注於「決定要做什麼、為什麼失敗、下一步如何調整」，而非反覆推導幾何與運動學。

##### 2. 雙層代理架構：語言決策與視覺落地的分離

RobotUse 的運作流程可視為一個迴圈：

1. **Main agent（主代理）** 根據當前 **state（狀態）**、**playbook（操作手冊）** 與子代理回傳的 **report（報告）**，以自然語言產生一條 **instruction（指令）**。
2. **Subagent（子代理）** 接收到 instruction（指令）後，在影像上進行 **visual selection（視覺選擇）**，選出 **target（目標）**、**point（點位）** 與 **pose（姿態）**。
3. **Robot backend（機器人後端）** 根據這些視覺規格執行 **motion planning（運動規劃）** 與 **control（控制）**。
4. Subagent（子代理）觀察 **observed outcome（觀察結果）**，產生 report（報告）——包含結果與原因——並回傳給 main agent（主代理）。

這裡的關鍵在於 **context（上下文）** 的隔離：子代理保留了詳細的影像選擇、嘗試與恢復歷史，但 main agent（主代理）只看精簡的 report（報告）。如此一來，main agent（主代理）維持了 **compact decision context（精簡決策上下文）**，卻仍能根據 outcome（結果）與因果解釋調整後續 **task intent（任務意圖）**。

##### 3. 機器人後端與介面設計

論文在 Problem Formulation 中將代理與後端的互動形式化為：

\[
u_t \sim \pi_\theta(\cdot \mid g, h_t), \quad u_t \in \mathcal{U}_I
\]

\[
s_{t+1} \sim P_I(\cdot \mid s_t, u_t)
\]

其中 \(g\) 為任務目標，\(h_t\) 為互動歷史，\(\mathcal{U}_I\) 是介面 \(I\) 的 **command space（命令空間）**，\(P_I\) 則代表後端執行與環境回應。RobotUse 的設計重點正是精心選擇 \(\mathcal{U}_I\)：它既不是低階關節控制，也不是完全封裝的 **high-level skill（高階技能）**，而是「語言意圖 + 視覺點位/姿態」這一中間層。這讓 **physical intent（物理意圖）** 對代理保持可見與可修正，同時把 **geometry（幾何）**、**motion planning（運動規劃）** 與 **control（控制）** 的複雜度封裝到後端。

##### 4. Playbook（操作手冊）與 Refiner（精煉器）

**Playbook（操作手冊）** 是 RobotUse 的持久記憶機制，記錄「在什麼條件下什麼做法有效、為何失敗、下次應如何嘗試」。它不同於單純的執行日誌，而是經過 **refiner（精煉器）** 在 **across episodes（跨回合）** 整理後的策略指引。Refiner（精煉器）只讀取 main-agent turn（主代理回合）的紀錄，編輯 playbook（操作手冊），而不接觸子代理的詳細影像互動歷史。這種設計再次體現了 **context（上下文）** 分配：經驗被提煉成高層指導原則，供後續任務使用，避免讓主代理被冗長的執行軌跡淹沒。

##### 5. Continual Harnessing（持續駕馭）

**Continual harnessing（持續駕馭）** 指在固定機器人後端的前提下，透過執行經驗持續更新 playbook（操作手冊）。這意味著經驗改變的是後續 **decision（決策）** 所依據的指引，而非底層 **execution code（執行程式碼）**。這種「後端固定、策略演進」的設計降低了真實世界部署的風險：即使學習過程出錯，也不會改變運動規劃與控制的核心邏輯。

#### 實驗數據解讀

論文在 **RoboLab** 環境中評估 RobotUse，衡量的指標包括 **task success（任務成功率）**、inference cost（推論成本）、token usage（token 使用量）與 execution time（執行時間）。以下針對已揭露的結果進行解讀。

##### 1. 主要結果：相對於 CaP-X 的提升

RobotUse 在 RoboLab 上達到 **45% task success（任務成功率）**，較 **CaP-X** 高出 **6.7 percentage points（百分點）**。這個差距雖然絕對數字不大，但具有重要意義：

- CaP-X 屬於 **code-based policy（基於程式碼的策略）** 路線，代理需要自行生成並管理感知與控制 API 的組合，並在 **execution history（執行歷史）** 中追蹤失敗與修正邏輯。
- RobotUse 則將幾何與運動規劃交給後端，讓代理專注於高層 **decision（決策）** 與 **visual selection（視覺選擇）**。

在這樣的對比下，+6.7 pp 說明「減少代理對低階執行邏輯的負擔、保留關鍵物理選擇」能帶來實質效能提升。同時，RobotUse 維持了 **compact decision context（精簡決策上下文）**，這通常對應較低的 token usage（token 使用量）與 inference cost（推論成本），對長程多步任務尤為重要。

##### 2. 對預定義動作抽象的依賴降低

實驗特別追蹤了對「provided grasp tool（提供的抓取工具）」的依賴程度。傳統方法常仰賴 **predefined action abstraction（預定義動作抽象）** 來完成抓取等動作，但這類 **abstraction（抽象）** 可能隱藏調整所需的關鍵選擇。RobotUse 透過讓子代理在影像上直接選擇 **point（點位）** 與 **pose（姿態）**，減少了對固定抓取工具的依賴，使代理能根據場景變化與 **observed outcome（觀察結果）** 調整接近方式。

##### 3. Playbook（操作手冊）漸進式改進

論文指出，隨著 **playbook（操作手冊）** 經過多次 **refiner（精煉器）** 更新，任務表現逐步提升。這驗證了 **continual harnessing（持續駕馭）** 的價值：經驗不是簡單堆積，而是被轉化為可重複使用的策略指引。例如，當某次抓取因「頂部被擋住」而失敗，playbook（操作手冊）可記錄「改從側面抓取」；後續遇到類似場景時，main agent（主代理）就能直接採用該策略。

##### 4. 真實世界執行與遷移

除了模擬環境，作者還展示 RobotUse 能從帶有雜訊的 **imperfect feedback（不完美回饋）** 中學習，並將學到的經驗 **transfer（遷移）** 到後續任務。這是機器人學習中極具挑戰性的環節：真實世界的感測誤差、執行失敗與因果不明確，往往使經驗難以累積。RobotUse 透過「子代理局部嘗試、主代理精簡決策、playbook 持久記憶」的架構，讓 **imperfect feedback（不完美回饋）** 仍能轉化為有用的策略更新。

##### 5. 結果的限制與詮釋

儘管有上述進展，45% 的成功率仍顯示 RoboLab 任務具有相當難度，RobotUse 距離完全可靠尚有距離。可能的瓶頸包括：

- 子代理的 **visual selection（視覺選擇）** 仍受限於影像品質與幾何理解；
- **imperfect feedback（不完美回饋）** 可能導致 playbook（操作手冊）記錄錯誤因果；
- 對後端工具的依賴雖降低，但未完全消除，某些複雜接觸行為仍需更細緻的控制。

#### 與現有研究的比較

RobotUse 的定位介於「高階語言規劃」與「低階執行控制」之間，並透過 **agent harness（代理框架）** 的設計來重新分配責任。以下與相關研究進行對比。

##### 1. 相較於 Code-as-Policies 與 CaP-X

**Code as Policies** 與其延伸 **CaP-X** 讓語言模型生成程式，透過 **perception and control tool（感知與控制工具）** 的組合來完成任務。這種 **code-based policy（基於程式碼的策略）** 雖然靈活，但要求代理同時承擔「任務分解、幾何推理、失敗診斷、程式修正」等多重責任，導致 **execution logic（執行邏輯）** 與 **execution history（執行歷史）** 快速膨脹。RobotUse 的改進在於：

- 將 **geometry（幾何）**、**motion planning（運動規劃）** 與 **control（控制）** 移出模型推理，交給專用後端；
- 透過 **subagent（子代理）** 處理單一 **subgoal（子目標）** 的局部互動，避免主代理上下文過載；
- 以 **playbook（操作手冊）** 累積經驗，而非不斷改寫 **execution code（執行程式碼）**。

##### 2. 相較於高階技能方法（SayCan）

**SayCan** 等方法透過 **high-level skill（高階技能）** 將執行細節封裝，代理只需選擇技能。然而，這種 **abstraction（抽象）** 可能隱藏調整所需的關鍵選擇，例如抓取點、接近方向或施力大小。RobotUse 保留了 **physical intent（物理意圖）** 在代理介面上的可見性，讓代理能根據 **observed outcome（觀察結果）** 修正 **target（目標）**、**point（點位）** 與 **pose（姿態）**，從而兼顧執行簡化與決策透明。

##### 3. 相較於視覺-語言-動作模型（RT-2、OpenVLA、π0）

**Vision-language-action models（視覺-語言-動作模型）** 如 RT-2、OpenVLA 與 π0 直接將影像與指令映射為機器人動作，端到端訓練。這類方法在大量資料下表現強勁，但決策過程較難解釋，且難以根據失敗進行結構化調整。RobotUse 採用模組化設計：語言模型負責高層 **decision（決策）**，視覺模型負責 **visual selection（視覺選擇）**，後端負責執行。這種分離使失敗分析與策略更新更為透明，也更容易整合 **continual harnessing（持續駕馭）**。

##### 4. 相較於 PIVOT

**PIVOT** 同樣透過在影像上渲染候選動作並進行迭代視覺選擇，讓視覺-語言模型能處理連續動作。RobotUse 可視為在此基礎上加入 **subagent（子代理）** 與 **playbook（操作手冊）** 的擴展：子代理專責單一 **instruction（指令）** 的視覺落地與局部恢復，playbook（操作手冊）則跨任務保留經驗，使系統具備持續學習能力。

##### 5. 相較於其他 Agent Harnesses（ReAct、PrimeAgent、ContinualHarness）

在通用 **agent harness（代理框架）** 領域，ReAct 強調推理與行動交錯；PrimeAgent 與 DeepAgents 強調遞迴式 **subagent（子代理）** 與上下文隔離；ContinualHarness 則從執行軌跡更新提示、子代理、技能與記憶。RobotUse 的獨特貢獻在於將這些原則具體應用於 **physical action（物理動作）**，並仔細劃分「語言決策 / 視覺選擇 / 幾何執行」的邊界。它證明了：即使在需要精確 **geometry（幾何）** 與 **contact constraint（接觸約束）** 的機器人領域，依然可以透過 **context（上下文）** 分配來降低模型負擔，同時保留可調整性。

##### 6. 相較於 ASPIRE 與 GaP

**ASPIRE** 診斷失敗、修復控制程式，並將驗證過的改進累積到技能庫；**GaP** 則透過模擬排練建構並精煉感知、規劃與控制模組圖。這些方法讓「可執行程式與技能組合」成為生成與修正的對象。RobotUse 選擇不同的路徑：它不修改底層 **execution code（執行程式碼）**，而是更新高層 **playbook（操作手冊）** 指引。這降低了學習過程中破壞後端穩定性的風險，但也意味著其上限仍受後端能力限制。

4. 實驗中使用的 **playbook（操作手冊）** 範例與更新規則。

#### 未來研究方向

基於 RobotUse 的設計與實驗結果，以下幾個方向值得進一步探索：

##### 1. 更豐富的感知與回饋融合

目前子代理主要依賴影像進行 **visual selection（視覺選擇）**。未來可整合觸覺、力覺、本體感覺與音訊等多模態資訊，讓 **report（報告）** 對失敗原因的描述更精確，進而提升 **playbook（操作手冊）** 的品質。

##### 2. 自動化且可驗證的 Playbook 更新

現有的 **refiner（精煉器）** 由語言模型擔任，可能在 **imperfect feedback（不完美回饋）** 下產生錯誤因果。未來可引入形式化驗證、對抗式審查或人類回饋機制，確保 playbook（操作手冊）更新不會引入有害策略。

##### 3. 降低對後端工具的依賴

雖然 RobotUse 已減少對 **predefined action abstraction（預定義動作抽象）** 的依賴，但仍使用後端提供的抓取等工具。未來可讓子代理學習視覺可供性（visual affordance），進一步將「如何執行」的選擇開放給代理，同時保持後端穩定。

##### 4. 跨環境與跨機器人的遷移

論文已展示初步的 **transfer（遷移）** 能力，但未來需系統性評估 RobotUse 在不同機器人平台、不同場景佈局與不同感測器配置下的泛化能力。特別是 **playbook（操作手冊）** 中的條件描述需要具備足夠泛化性，才能從模擬遷移到真實世界。

##### 5. 長程任務的動態分解

對於更長程、更開放的日常任務，main agent（主代理）需要更強的動態 **subgoal（子目標）** 分解能力。可結合階層式強化學習或規劃演算法，讓任務分解本身也能從經驗中學習與修正。

##### 6. 人機協作的持續學習

在真實部署中，人類操作者往往能提供高品質回饋。未來可設計人機協作版本的 **continual harnessing（持續駕馭）**，讓人類針對失敗案例直接編輯或確認 **playbook（操作手冊）** 更新，加速學習並提高安全性。

##### 7. 理論分析 Context 分配

RobotUse 的經驗成功來自於精心的 **context（上下文）** 分配，但目前多為工程設計。未來可從資訊理論或認知負荷角度，量化不同 **context（上下文）** 劃分對 **decision（決策）** 品質與 inference cost（推論成本）的影響，為更廣泛的 **agent harness（代理框架）** 設計提供理論指導。

## 論文問答

**Q1：RobotUse 試圖解決什麼核心問題？**
A：RobotUse 旨在解決機器人代理如何將高層意圖轉化為具體物理動作，並根據觀察結果持續修正選擇的問題。具體而言，機器人代理必須在保留足夠上下文以修正選擇的同時，連接預期動作與觀察結果。這個挑戰在於如何在不讓模型負擔所有幾何、運動規劃與控制細節的前提下，仍能根據執行回饋調整高層決策。

**Q2：現有方法在機器人操作任務上為何會失敗？**
A：現有方法主要有兩種失敗模式：一是將關鍵選擇隱藏在預定義的高階技能或動作抽象中，導致代理無法根據失敗調整所需的物理選擇；二是要求代理直接管理詳細的執行程式碼與不斷增長的執行歷史，使模型上下文膨脹且難以檢查與修復。基於程式碼的策略讓代理自行連接物理意圖、失敗與執行邏輯，而高階技能則可能遮蔽調整所需的選擇。RobotUse 試圖在兩者之間取得平衡，既委派執行複雜度，又保留可解釋與可修正的決策上下文。

**Q3：為什麼適當分配計算、上下文與決策對通用型代理設計很重要？**
A：適當分配計算、上下文與決策對於設計通用型代理至關重要，因為並非所有計算都應該透過模型推論完成。程式可以在作用中上下文之外處理資訊，子代理可以執行詳細互動並只回傳後續決策所需的資訊，從而讓主代理維持精簡決策上下文。在物理動作領域，這種分配尤其關鍵，因為高維度連續運動涉及大量幾何與接觸約束，若全部納入模型推理，將使決策變得困難且低效。

**Q4：RobotUse 的核心架構包含哪些組件，各自負責什麼？**
A：RobotUse 的核心架構包含主代理、子代理、機器人後端與精煉器四個主要組件。主代理以語言維護任務意圖，根據當前狀態、操作手冊與子代理回傳的報告來發出指令；子代理則在影像上進行視覺選擇，指定目標、點位與姿態，並由後端負責幾何計算、運動規劃與控制來執行。子代理保留每個子目標的詳細互動歷史，但只將結果與原因回報給主代理，而精煉器則在回合間讀取主代理紀錄並更新持久化操作手冊。

**Q5：RobotUse 相較於先前工作的主要創新是什麼？**
A：RobotUse 的主要創新在於提出一個基於意圖的代理框架，將物理動作的指定與修正作為組織計算、上下文與決策的核心。不同於讓模型直接生成執行程式碼或完全依賴預定義動作抽象，RobotUse 讓代理在視覺層面選擇具體物理選擇，同時將幾何實現委派給後端。此外，透過持續駕馭與持久化操作手冊，經驗可以改變後續決策而不需要重寫機器人控制程式碼。

**Q6：為什麼 RobotUse 要將主代理與子代理分開，並讓子代理進行視覺選擇？**
A：主代理與子代理的分離是為了隔離不同層次的決策責任：主代理專注於高層任務分解與意圖委派，子代理則專注於單一指令的視覺落地與執行。這種設計讓詳細的觀察、選擇與恢復歷史保留在子代理的局部上下文中，避免主代理被過多執行細節淹沒。視覺選擇則讓代理直接針對當前場景指定位置、方向與接近方式，使物理意圖與觀察結果之間的連接更加明確且可調整。

**Q7：論文使用什麼基準與指標來評估 RobotUse？**
A：論文在 RoboLab 基準上評估 RobotUse，並比較任務成功率、推論成本、token 使用量與執行時間等指標。評估也檢視了對提供抓取工具的依賴程度，並追蹤連續操作手冊修正後的任務完成率變化。此外，研究還展示了 RobotUse 能夠在真實世界執行中學習，儘管回饋不完美，並將學到的經驗遷移到後續任務。

**Q8：RobotUse 的主要實驗結果是什麼？**
A：RobotUse 在 RoboLab 上達到 45% 的任務成功率，比 CaP-X 高出 6.7 百分點。更重要的是，RobotUse 在取得較高成功率的同時，仍維持精簡的決策上下文，並減少對預定義動作抽象的依賴。隨著操作手冊持續精煉，累積的經驗進一步改善任務表現，顯示持續駕馭機制能夠有效將執行經驗轉化為更好的決策指導。

**Q9：論文進行了哪些消融研究或分析來理解不同設計選擇的影響？**
A：論文進行了多項分析來理解不同責任分配對機器人操作推理需求的影響，包括對提供抓取工具的依賴性分析，以及追蹤連續操作手冊修正如何影響任務完成率。這些消融研究檢視了當模型承擔不同程度責任時，任務表現、推論成本與執行時間之間的權衡。結果顯示，將幾何執行委派給後端並保留高層決策給代理，能夠在效能與效率之間取得良好平衡。

**Q10：RobotUse 適合應用在哪些實際場景？**
A：RobotUse 可應用於需要反覆嘗試與修正的長程機器人操作任務，例如家庭服務中的開門、放置物品、調整旋鈕等日常動作。由於框架能夠從真實執行中學習並更新操作手冊，它特別適合環境變化大、難以預先定義所有技能的場景。此外，視覺選擇與語言意圖的結合也使其適用於需要人機協作或自然語言指令的應用。

**Q11：將 RobotUse 部署為實際產品時需要考慮哪些因素？**
A：在實際部署時，需要考慮後端的穩定性、視覺感測器的可靠性，以及不完美回饋對學習效果的影響。由於 RobotUse 保持執行後端固定，只更新操作手冊，因此後端的幾何與控制能力會限制整體系統的表現上限。此外，操作手冊的品質與精煉器的設計也至關重要，因為錯誤的經驗累積可能導致後續決策偏差，需要適當的驗證與監督機制。

**Q12：這項工作對機器人學習與代理設計領域可能帶來什麼影響？**
A：這項工作對機器人學習與代理設計領域的影響在於，它明確提出並實踐了「計算、上下文與決策的分配」這一設計問題，特別是將其應用於物理動作領域。它展示了代理框架可以在不修改底層控制程式碼的情況下，透過持續駕馭累積經驗並改善決策。這為未來開發更通用、可解釋且可持續學習的機器人代理提供了重要的架構參考。

**Q13：論文可能承認哪些限制？**
A：論文可能承認的限制包括：任務成功率仍有提升空間，且系統表現受後端幾何與控制能力的限制。此外，雖然操作手冊能夠累積經驗，但在面對與過去經驗差異過大的新任務或環境時，遷移效果可能有限。不完美回饋也可能導致錯誤的經驗被寫入操作手冊，進而影響後續決策的可靠性。

**Q14：RobotUse 在哪些情況下仍可能失敗？**
A：失敗案例可能發生在子代理選擇了不適當的點位或姿態，但後端無法根據當前幾何與接觸約束成功執行時。另一種情況是主代理對任務分解或委派策略判斷錯誤，導致子代理接收到無法完成的指令。此外，當執行回饋不準確或過於模糊時，精煉器可能無法正確診斷失敗原因，從而更新出無效甚至有害的操作手冊條目。

**Q15：未來研究可以朝哪些方向延伸 RobotUse？**
A：未來研究方向包括擴展操作手冊的表示能力，使其能夠捕捉更複雜的條件與調整策略，並提升在更廣泛任務與真實場景中的遷移能力。另一個方向是結合更豐富的執行回饋來源，例如力觸覺感測或多視角觀察，以改善在不完美回饋下的學習穩健性。此外，也可以探索讓主代理具備更主動的實驗與探索能力，在面對新情境時能夠有系統地測試不同物理選擇並更新操作手冊。

## 實務應用指南

### 適用場景

1. **家庭服務機器人的多步驟整理與擺放**  
   例如將不同形狀的杯子、碗盤收拾到層架或洗碗機。RobotUse 讓主代理以語言維持「把橙色杯子放到平台上」這類任務意圖，子代理則在影像上選取點位與姿態；當杯子滑落或頂部被擋住時，操作手冊會記錄「改從側面抓取」等調整策略，並在後續類似情境中遷移使用。

2. **倉儲物流機器人的彈性揀選與裝箱**  
   面對 SKU 形狀、尺寸與擺放方向各異的揀選任務，後端負責幾何與運動規劃，代理只需決定「抓取哪一箱、以什麼方向放入貨箱」。透過視覺選擇與持續駕馭，系統能從失敗的抓取姿態中學習，減少對預定義動作抽象的依賴。

3. **製造組裝線上的精密對準與插入**  
   例如將零件插入孔位、旋轉旋鈕或對準接頭。這類任務涉及高維度連續運動與接觸約束，RobotUse 將位置、方向、接近方式等物理意圖保留在代理介面，同時把軌跡生成與低層控制交給機器人後端，讓主代理能根據觀察結果修正後續指令。

4. **醫療與照護輔助機器人的遞送與定位**  
   例如將藥杯遞至床邊、調整復健器材位置。由於真實世界回饋往往不完美，RobotUse 的精簡決策上下文與回合間精煉器能幫助系統在雜訊中學習，並透過人機協作的安全監控避免高風險動作。

5. **零售與餐飲機器人的補貨與陳列**  
   例如依據貨架空間將瓶罐以特定方向擺放。代理透過影像選擇目標與姿態，後端處理碰撞檢查與運動規劃；隨著執行經驗累積，操作手冊會記錄不同貨架高度與擁擠程度下的最佳策略。

### 實作前置條件

**資料**
- 高品質的 RGB-D 影像、相機內外參數與機器人手眼校正結果。
- 場景或物件的幾何模型（點雲、網格或 3D 邊界框），供後端進行碰撞檢查與運動規劃。
- 初始任務示範或種子策略，用於建立第一版操作手冊。
- 執行結果與失敗日誌，包含結果、原因與當下狀態，供精煉器學習。

**運算**
- 視覺語言模型（VLM）推理資源：可使用雲端 API 或本地 GPU。
- 機器人後端運算：用於感知、幾何計算、運動規劃與即時控制。
- 邊緣或雲端主代理執行環境，用於維護 playbook 與精煉器。

**技能**
- 機器人系統整合經驗（ROS 2、MoveIt、控制介面）。
- 大型語言模型與視覺語言模型的提示工程與微調能力。
- 軟體工程能力，能設計主代理／子代理／後端之間的 API 契約。
- 安全與人機協作知識，包含緊急停止、碰撞偵測與人類監督機制。

### 實作步驟建議

1. **定義任務意圖與指令介面**  
   決定主代理能發出的語言指令格式，以及每條指令對應的子目標、約束與預期回報內容（結果與原因）。

2. **建置機器人後端**  
   整合感知、幾何計算、運動規劃與低層控制模組，確保後端能接收「目標點位＋姿態」並輸出可執行軌跡。

3. **實作主代理與操作手冊**  
   讓主代理根據當前狀態、操作手冊與子代理回報決策；設計 playbook 的結構，包含「條件—策略—調整建議」。

4. **實作視覺子代理**  
   子代理接收語言指令與影像，負責選取目標、點位與姿態，並在局部上下文中處理細節互動與重試。

5. **建立精煉器**  
   精煉器只讀取主代理回合紀錄，跨回合更新操作手冊，避免將過多執行歷史塞入主代理的決策上下文。

6. **進行有人監督的封閉迴路測試**  
   在真實或模擬環境中執行多回合任務，收集執行回饋，特別記錄失敗案例與對應狀態。

7. **持續駕馭與迭代**  
   讓精煉器根據累積經驗更新 playbook，同時固定後端程式碼；定期評估任務成功率、推論成本、token 用量與執行時間。

8. **部署與監控**  
   上線後保留人機協作機制，持續監控異常動作，並讓操作手冊版本化以便回溯與比較。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **視覺定位漂移** | VLM 選取的點位或姿態可能因光照、遮擋而偏移。 | 定期校正相機與手眼關係；加入幾何後處理與人工確認閥值。 |
| **不完美回饋導致錯誤學習** | 真實世界回饋可能雜訊過大，使 playbook 記錄錯誤因果。 | 設計結果驗證機制；讓精煉器只在高信心或多人確認後更新。 |
| **上下文分離遺失關鍵細節** | 子代理的局部歷史未完整回傳，主代理可能誤判失敗原因。 | 明確定義 report 欄位，強制回傳結果、原因與未解決約束。 |
| **安全與接觸風險** | 高維度連續運動與接觸約束可能造成碰撞或夾傷。 | 設定速度／力矩上限、緊急停止、碰撞偵測與人類監督。 |
| **延遲與成本** | 每次決策都呼叫 VLM 會增加執行時間與 token 成本。 | 快取常見策略、限制重試次數、在低成本模型與高精度模型間取捨。 |
| **操作手冊膨脹** | 持續累積經驗可能使 playbook 過大，反而降低決策品質。 | 定期清理過時條目、合併相似條件、評估每條規則的實際效益。 |
| **領域遷移困難** | 在模擬或特定場景學到的策略，換到新環境可能失效。 | 保留環境特徵欄位；上線初期採用漸進式部署與持續微調。 |

### 與其他技術的整合建議

- **機器人後端**：可銜接 ROS 2、MoveIt、Pinocchio、Mujoco 或 Isaac Sim，將幾何、運動規劃與控制模組封裝成標準 API。
- **視覺語言動作模型（VLA）**：RT-2、OpenVLA、π₀ 等可作為低層策略或姿態先驗，與 RobotUse 的「語言決策＋視覺選擇」形成互補。
- **代理編排框架**：LangChain、AutoGen 或 PrimeAgent 可用於管理主代理與子代理之間的委派與上下文繼承。
- **倉儲／製造系統**：與 WMS、MES 或 ERP 整合，讓主代理根據訂單與工單產生任務意圖。
- **數位孿生與模擬**：在部署前利用模擬環境進行策略排練，並將數位孿生作為執行日誌與回放工具。
- **遠端遙操作與資料收集**：整合 VR 手柄、鍵盤或示教裝置，在初期快速建立種子示範與安全接管機制。
- **安全 PLC 與監控層**：將緊急停止、力控限制與區域偵測交由獨立安全系統處理，不應完全依賴代理決策。

### 給不同背景讀者的閱讀建議

**初學者**  
先從圖 1 的整體架構開始，理解「主代理用語言決策、子代理在影像上選點位與姿態、後端負責執行」這三層分工即可。暫時跳過數學符號，重點掌握操作手冊如何讓機器人從失敗中學習，以及為什麼要把執行複雜度留給後端。

**AI 工程師**  
請聚焦在介面設計與上下文分配：主代理的決策上下文應該多精簡、子代理的局部歷史該保留哪些細節、report 的欄位如何設計才能支撐後續決策。同時留意提示工程、後端 API 契約、精煉器的觸發條件，以及如何在推論成本與任務成功率之間取捨。

**研究人員**  
本論文的核心貢獻在於「計算、上下文與決策的分配」這個設計問題，以及持續駕馭如何在固定後端的前提下改變後續決策。建議對照 CaP-X、Code as Policies、ASPIRE 等方法，分析 RobotUse 在保留物理意圖、分離局部互動歷史與累積經驗指引上的取捨，並思考其理論限制與未來擴展方向。

**產品經理**  
請把重點放在適用場景、任務成功率（45% 相較 CaP-X 提升 6.7 百分點）、推論成本、執行時間與人機協作需求。評估時要同時看「能完成多少任務」與「每次失敗的代價」，並規劃漸進式部署：從模擬到人機共工，再到有限度的自主執行，確保安全與商業可行性並重。
