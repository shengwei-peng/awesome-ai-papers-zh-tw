## ⚡ TL;DR

解決程式碼代理中執行環境與模型生成程式碼分離，導致表達受限且易受提示注入等攻擊的安全問題。
提出LACUNA，將代理動作視為型別化洞，LLM填入Scala程式碼於執行前型別檢查。
BrowseComp-Plus達27.1%準確率，τ²-bench解決76%任務，僅8.6%被拒。

## 摘要翻譯

大型語言模型（LLM）代理越來越多地透過撰寫程式碼來行動，然而驅動代理的執行環境（runtime）與模型所撰寫的程式碼之間仍存在一道落差。執行環境掌控著代理迴圈（agent loop）、上下文與控制流程（control flow），而模型對這些幾乎無置喙餘地。若讓模型撰寫的程式碼直接塑造執行環境本身，將使代理更具表達能力（expressiveness），但同時也會加劇安全性（safety）問題。模型可能因提示注入（prompt injection）而偏離目標、呼叫錯誤的工具，或在中途失敗並留下不一致狀態（inconsistent state）；相較於僅表達單一動作，當程式碼塑造執行環境時，這些失敗的波及範圍更廣。我們提出 LACUNA，一種用於代理的程式設計模型（programming model），能在兼顧安全性的前提下消弭此落差。每個代理動作都是一個型別化的呼叫 `agent[T](task)`，大型語言模型在執行流程到達時填入程式碼，而程式碼在執行前會相對於環繞程式（surrounding program）進行型別檢查（type-checked）。由於每個動作會以整體形式被接受或拒絕，被拒絕的動作（rejected action）使環境保持不變，其編譯器診斷訊息（compiler diagnostics）會驅動重試（retry）。同一檢查也限制了動作可使用的工具與資料，以及其流動方式。我們的核心原語——型別化洞（typed hole）——能將 ReAct 迴圈、子代理（sub-agent）、技能（skill）、平行分解（parallel decomposition）與多模型規劃（multi-model planning）表達為一般的控制流程。我們在一系列測試案例、BrowseComp-Plus 與 τ²-bench 上評估 LACUNA。在 BrowseComp-Plus 上，8.6% 的生成結果（generation）在執行前被拒絕，平均每次查詢（query）重試 0.7 次，代理達到 27.1% 的準確率（accuracy）。在 τ²-bench 上，LACUNA 使用高效能模型（capable model），在涵蓋四個領域的 392 項任務中達到 76.0% 的解決率，與基線代理（baseline agent）表現相當。

### 核心貢獻（3～5點）
- 提出 LACUNA 程式設計模型，以型別化洞（typed hole）作為核心原語，讓大型語言模型在執行流程到達時填入程式碼，從而消弭執行環境與模型撰寫程式碼之間的落差。
- 透過型別檢查機制，使每個代理動作以整體形式被接受或拒絕；被拒絕的動作不影響環境，並由編譯器診斷訊息驅動重試，兼顧表達能力與安全性。
- 以單一原語統一表達 ReAct 迴圈、子代理、技能、平行分解與多模型規劃等代理模式，展現高度的表達能力。
- 在 BrowseComp-Plus 上驗證安全性機制：僅 8.6% 的生成結果在執行前被拒絕，平均每次查詢僅需 0.7 次重試，即可達到 27.1% 的準確率。
- 在 τ²-bench 上，於涵蓋四個領域的 392 項任務中達到 76.0% 的解決率，表現與基線代理相當，證明安全性設計不犧牲效能。

### 適合對象
從事大型語言模型代理系統研究與實務開發的研究者與工程師，特別關注代理安全性、程式設計模型設計、程式碼即動作（code-as-action）架構，以及需要兼顧表達能力與安全防護的 AI 系統設計者。此外，對編譯器技術、型別系統與程式語言設計感興趣的讀者，亦可從中獲得關於如何將形式化檢查機制引入代理系統的啟發。

## 深度分析

#### 方法論解析

LACUNA 的核心洞見在於重新定位 LLM 代理（LLM agent）中「執行環境（runtime）」與「模型生成程式碼」之間的關係。傳統的程式碼即動作（code-as-action）代理架構中，無論是 ReAct 框架的單一工具呼叫（tool call）迴圈，或是遞迴式語言建模（recursive language modeling, RLM）的 REPL（read-eval-print loop，互動式殼層）模式，都維持一個根本性的分裂：執行環境掌控迴圈、上下文（context）與控制流程（control flow），而模型僅能產出片段化的動作。這種架構限制了代理的表達能力（expressiveness），因為模型無法自主決定何時生成子代理（sub-agent）、如何調整上下文保留策略、或如何重塑控制流程。

LACUNA 提出一個極為精煉的核心原語（primitive）：

```scala
def agent[T](task: String): T
```

這個型別化洞（typed hole）的設計哲學值得深入剖析。`task` 是自然語言提示（natural-language prompt），而 `T` 是預期結果型別（expected result type）。當執行流程抵達此呼叫時，模型被要求填入一段 Scala 3 程式碼，這段程式碼會在環繞程式（surrounding program）的詞法作用域（lexical scope）中被編譯，並在通過型別檢查（type-checked）後執行。這種設計有三個關鍵特性：

**第一，編譯時點的型別檢查**。LACUNA 並非在執行後驗證結果，而是要求模型生成的程式碼在執行前必須通過 Scala 3 編譯器的型別檢查。這意味著若程式碼片段（snippet）使用了不存在的工具、傳遞了錯誤型別的參數、或回傳了不符合 `T` 的值，整個片段會被作為一個整體拒絕（rejected as a whole），且由於尚未執行任何副作用，環境狀態保持不變。編譯器診斷訊息（compiler diagnostics）會被回傳給模型以驅動重試（retry），形成一個閉環的自我修正機制。

**第二，能力追蹤（capability tracking）與資訊流控制**。LACUNA 利用 Scala 3 的擷取檢查（capture checking）機制來界定代理可存取的資源。這包括檔案存取、網路控制代碼（network handles）、特定工具等。透過型別系統而非執行時沙箱（sandbox）來強制執行權限邊界，這是一個根本性的安全設計選擇——它將安全保證從「執行時監控」提升至「編譯時驗證」。

**第三，遞迴即控制流程**。LACUNA 最具突破性的設計在於：代理的常見模式——ReAct 迴圈、子代理、技能（skill）、平行分解（parallel decomposition）、多模型規劃（multi-model planning）——不再是特殊的代理協議，而是普通的 Scala 控制流程。論文中展示的範例中，`topics.par.map(topic => agent[String](s"Research: $topic"))` 將平行分解表達為普通的平行集合操作，而遞迴的代理呼叫則是普通的函數呼叫。這種「模式即程式碼」的統一性消除了傳統代理框架中「控制流程在執行環境、動作在程式碼」的人為分裂。

從安全分析的角度，LACUNA 提供了三層保證：(1) 預執行拒絕（pre-execution rejection）——不可用名稱與型別不符在執行前就被捕獲；(2) 無部分執行（no partial execution）——被拒絕的片段不會留下副作用，因此環境不會進入不一致狀態（inconsistent state）；(3) 權限與資訊流控制（permissions and information-flow control）——透過擷取檢查界定代理的權限邊界。這三層保證共同回應了論文中強調的核心威脅模型：提示注入（prompt injection）、錯誤工具呼叫、以及部分失敗導致的狀態污染。

#### 實驗數據解讀

LACUNA 的實驗設計涵蓋三個層次的評估：驗證器測試案例（verifier test cases）、BrowseComp-Plus 基準（benchmark）、以及 τ²-bench 基準。

**BrowseComp-Plus 結果**顯示 27.1% 的準確率（accuracy），伴隨 8.6% 的生成結果在執行前被拒絕，平均每個查詢（query）僅需 0.7 次重試。這個數據組合極具啟發性：8.6% 的拒絕率意味著約九分之一的生成結果在第一次嘗試時就存在結構性錯誤——可能是型別不符、名稱未綁定、或資源存取違規——而這些錯誤在傳統架構中會以執行時例外（runtime exception）或靜默失敗的形式出現。0.7 次重試的平均值表明模型在收到編譯器診斷後，通常能在一次額外嘗試內產生正確程式碼，這驗證了「編譯器錯誤作為回饋訊號」這一設計假設的有效性。27.1% 的準確率本身需要與基準代理（baseline agent）對照才能完整解讀，但論文中強調此結果是在伴隨安全保證的前提下達成的，這是關鍵的權衡取捨。

**τ²-bench 結果**顯示 LACUNA 在 392 個任務中解決了 76.0%，橫跨四個領域，且達到與基線代理相當的水準。τ²-bench 涵蓋多輪對話、工具使用、與外部系統互動等場景，是衡量代理實用性的重要基準。76.0% 的解決率與基線相當這一事實尤為重要：它表明 LACUNA 的安全機制並未以犧牲效能為代價。在傳統的安全-效能權衡中，增加安全檢查通常會降低成功率，但 LACUNA 透過將安全檢查前置到編譯時，避免了執行時干預的效能損耗。

**驗證器測試案例**的設計目的在於系統性地驗證 LACUNA 的安全保證。這些案例可能涵蓋：嘗試存取未授權資源、使用錯誤型別、產生部分副作用後失敗等情境。雖然論文中未詳細列出每個案例的具體數據，但這類測試的存在表明作者意識到「安全保證的形式化驗證」與「基準效能」同樣重要。

從實驗設計的完整性來看，三個層次的評估形成了互補的證據鏈：驗證器測試案例驗證安全保證、τ²-bench 驗證實用性、BrowseComp-Plus 驗證在開放式問答任務中的表現。然而，論文中缺少對不同模型規模、不同模型家族的消融實驗（ablation study），也缺少對重試機制本身效率的深入分析（例如，重試次數分佈、診斷訊息品質對重試成功率的影響等）。

#### 與現有研究的比較

LACUNA 的定位需要在多個研究脈絡中理解。

**與 ReAct 的比較**：ReAct（Yao et al., 2023）是當前代理架構的範式基礎，其「推理-動作-觀察」交替的設計簡單有效，但限制了模型對控制流程的掌控。LACUNA 並非取代 ReAct，而是將其表達為普通程式碼——一個 `while` 迴圈搭配 `agent[T]` 呼叫即可實現 ReAct 模式。這種「模式即程式碼」的統一性是根本性的進步。

**與程式碼即動作代理的比較**：包括 CodeAct（Wang et al., 2024b）、Anthropic 的程式碼執行代理（Anthropic, 2025b）、以及 smolagents（Roucher et al., 2025）等。這些系統讓模型以程式碼作為動作空間，但維持了「執行環境掌控迴圈、模型產出片段」的分離。LACUNA 的差異在於：模型生成的程式碼本身就是執行環境的一部分，可以重塑控制流程。

**與遞迴式語言建模（RLM）的比較**：這是最直接的對比對象。RLM（Zhang et al., 2025a）同樣讓生成的程式碼更新持久執行上下文（persistent execution context）並遞迴呼叫模型，但有兩個關鍵差異。第一，RLM 的 REPL 在執行前不做檢查，因此錯誤的程式碼可能在執行中途失敗並留下不一致狀態；LACUNA 則在執行前完成型別檢查。第二，RLM 將協調與控制流程保留在執行環境中，而 LACUNA 將控制流程交給生成的程式碼本身。

**與 LMQL、DSPy 的比較**：LMQL（Beurer-Kellner et al., 2023）將 LLM 推論視為帶有約束解碼（constrained decoding）的查詢，DSPy（Khattab et al., 2024）使用型別化簽名（typed signature）描述 LLM 呼叫。兩者都將型別/約束應用於單一呼叫的輸入輸出規則，但組合多個呼叫的工作流程仍需開發者手動編寫。LACUNA 的差異在於：代理產出的是一個程式而非受限字串或欄位值，且組合是由生成的程式碼本身表達的。

**與 ChatLSP 的比較**：ChatLSP（Blinn et al., 2024）同樣以型別化洞填入 LLM 生成的程式碼，但場景是編輯時（edit-time）的程式碼完成，由人類審查。LACUNA 則將型別化洞作為遞迴執行時動作，在即時詞法作用域中進行型別檢查並於同一程序中執行。這個從「編輯時輔助」到「執行時動作」的轉變帶來了根本不同的安全語義。

**LACUNA 的限制**包括：(1) 對 Scala 3 型別系統的依賴——擷取檢查等機制在其他主流語言中並非標準，這限制了可移植性；(2) 編譯開銷——每次代理呼叫都需要編譯新生成的程式碼，這在延遲敏感場景中可能成為瓶頸；(3) 型別系統的表達力邊界——某些代理行為可能難以用型別精確表達，例如涉及副作用順序、機率性結果、或非確定性行為的場景；(4) 模型能力的依賴——LACUNA 要求模型能產生通過型別檢查的 Scala 程式碼，這對模型的程式設計能力提出了更高要求。

#### 可重現性評估

從論文中提供的資訊來看，LACUNA 的可重現性存在若干不確定性。論文標明使用 Scala 3 作為實作語言，並引用了 Scala 的官方文件（Scala, 2024a）以及擷取檢查的相關文獻（Odersky et al., 2026; Xu et al., 2025），這表明實作依賴於 Scala 3 的特定編譯器功能。論文中給出了具體的評測數據（BrowseComp-Plus 27.1%、τ²-bench 76.0%）以及重試行為的統計（8.6% 拒絕率、0.7 次平均重試），這些數據為重現提供了基準。

然而，論文中未明確提及以下關鍵的可重現性要素：(1) 開源程式碼（open-source code）的可用性——是否會釋出 LACUNA 的完整實作；(2) 使用的具體模型及其權重（model weights）——「capable model」的具體身份未明確披露；(3) 評測中使用的提示模板（prompt template）與超參數（hyperparameter）；(4) τ²-bench 四個領域的具體構成與每個領域的細粒度結果；(5) 驗證器測試案例的具體內容與評估標準。

從 arXiv 編號（2605.28617v1）與日期（2026 年 5 月）來看，這是一篇較新的預印本（preprint），後續可能會補充附錄或釋出程式碼。對於希望重現此研究的團隊，建議關注作者的後續發布，以及 Scala 3 擷取檢查功能的穩定性（這是一個仍在演進中的語言特性）。

#### 未來研究方向

LACUNA 開啟了多個值得深入探索的研究方向。

**語言可移植性與跨語言泛化**。當前實作深度依賴 Scala 3 的擷取檢查與巨集（macro）系統。一個自然的研究方向是將 LACUNA 的核心思想移植到其他語言，例如透過 Rust 的借用檢查器（borrow checker）實現能力追蹤，或透過 TypeScript 的型別系統實現較輕量的版本。這不僅能擴大 LACUNA 的適用範圍，也能幫助理解「哪些語言特性是 LACUNA 風格代理設計的必要條件」。

**更豐富的能力模型**。當前的擷取檢查主要處理資源存取的二元權限（允許/禁止）。未來可以探索更細粒度的資訊流控制（information-flow control），例如區分「可讀但不可外傳」的機密資料，或支援基於使用紀錄的動態權限調整。這對於處理涉及隱私資料或多租戶（multi-tenant）場景的代理至關重要。

**編譯效率最佳化**。每次代理呼叫都需要編譯新生成的程式碼，這在延遲敏感場景中可能成為瓶頸。未來可以研究增量編譯、片段快取、或預測性編譯等技術。此外，可以探索將部分型別檢查下放至約束解碼（constrained decoding）階段，以減少重試次數。

**形式化安全證明**。論文中提出的安全保證（預執行拒絕、無部分執行、權限界定）目前以論證方式呈現。一個重要的研究方向是為這些保證提供形式化證明（formal proof），例如使用互模擬（bisimulation）或精化型別（refinement type）來證明「被拒絕的片段不會產生可觀察的副作用」。

**代理模式的程式庫化**。論文中展示了 ReAct、子代理、技能、平行分解、多模型規劃等模式可表達為普通程式碼。未來可以建構一個「代理模式程式庫」，將常見模式封裝為可重用的程式碼片段，讓開發者能像組合普通函式一樣組合代理行為。

**與形式化驗證的整合**。LACUNA 的型別檢查提供了靜態保證，但對於涉及多步推理、機率性結果、或與外部世界互動的代理，可能需要更強的驗證技術。可以探索將 LACUNA 與神經符號驗證（neuro-symbolic verification）結合，例如對關鍵決策路徑進行形式化驗證，或對代理輸出進行後驗證（post-hoc verification）。

**基準與評測方法論**。當前的代理評測主要關注最終任務的成功率，但 LACUNA 開啟了新的評測維度：型別錯誤率、重試效率、權限違規嘗試次數等。未來可以發展專門針對「安全感知代理」的評測基準，衡量代理在維持安全保證的同時完成任務的能力。

**人機協作模式**。LACUNA 的編譯器診斷作為回饋訊號驅動重試，這一機制可以擴展至人機協作場景：當模型無法產生通過型別檢查的程式碼時，可以將診斷訊息呈現給人類開發者，由人類提供修正或額外約束。這種「模型-編譯器-人類」的三方互動可能催生新的程式設計範式。

## 論文問答

**Q1：LACUNA 試圖解決的核心問題是什麼？**
A：LACUNA 試圖解決「執行代理的程式碼」與「代理所撰寫的程式碼」之間的分裂問題。現今的 LLM 代理雖然能以程式碼作為動作（code-as-action），但執行環境（runtime）仍掌控迴圈、上下文與控制流程，而模型只能產出單一片段，對何時保留上下文、何時衍生子代理、如何調整控制流程幾乎沒有發語權。這種分裂限制了代理的表達能力，也使得模型一旦被提示注入（prompt injection）誤導或中途失敗，所造成的破壞範圍會比單一動作更大。LACUNA 透過讓模型所寫的程式碼直接塑造執行環境本身，同時以型別檢查在執行前把關，兼顧表達力與安全性。

**Q2：為何現有的程式碼即動作代理（code-as-action agent）無法提供完整的安全保證？**
A：現有的程式碼即動作代理在執行前並未對模型產生的程式碼進行整體檢查，因此一旦片段誤用了某個繫結（binding）或回傳了錯誤型別的結果，可能在執行中途失敗並留下不一致的環境狀態。雖然沙箱、受限制的直譯器、策略語言、輸入強化與調解式防禦等機制各自能擋下一部分風險，但它們都是零碎、片段式的防禦，沒有一個機制能在動作「開始之前」對整個生成動作進行檢查。此外，當代理開始塑造自己的執行環境時，攻擊所觸及的範圍會從單一動作擴大到執行環境本身，使得這些零碎防禦更加不足。

**Q3：為何這個問題對 LLM 代理領域至關重要？**
A：隨著 MCP（模型上下文協議）與可重複使用的「技能」（skill）日益普及，LLM 代理被賦予了檔案存取、網頁搜尋與 API 呼叫等強大能力，這使得代理的安全問題從學術議題升級為部署關卡。若代理能任意塑造自己的執行環境，卻缺乏執行前的把關機制，那麼提示注入、工具誤用與中途失敗等風險將直接衝擊執行環境，後果遠比單一錯誤動作嚴重。LACUNA 所提出的「執行前型別檢查」與「權限／資訊流控管」正是回應這個日益迫切的部署需求，因此對整個領域具有關鍵意義。

**Q4：LACUNA 的核心程式設計模型是什麼？型別化洞（typed hole）這個原語如何運作？**
A：LACUNA 的核心是一個型別化的代理呼叫原語 `def agent[T](task: String): T`，其中 `task` 是自然語言提示，`T` 是預期結果型別。當執行流程抵達這個呼叫時，LLM 會在該位置填入 Scala 程式碼，而 LACUNA 會在「環繞程式」（surrounding program）的當下詞法範疇（lexical scope）中編譯這段程式碼；若程式碼被證明能產出型別 `T` 的值便執行，否則將編譯器的錯誤訊息回傳給模型以驅動重試。由於每個動作會被整體接受或拒絕，被拒絕的動作不會留下任何環境副作用，這正是 LACUNA 安全保證的基礎。

**Q5：LACUNA 相較於 RLM、LMQL、DSPy 等既有框架的關鍵創新為何？**
A：相較於遞迴式語言建模（RLM），LACUNA 的第一項改進是在執行前於即時詞法範疇中對程式碼進行型別檢查，避免片段中途失敗而留下不一致狀態；第二項改進則是讓生成的程式碼本身撰寫控制流程，而非由執行環境掌控編排。相較於 LMQL 與 DSPy，LACUNA 不只是約束單一呼叫的輸入輸出，而是讓模型產出「整個程式」，並由宿主編譯器在呼叫點檢查其型別與資源使用，因此能表達分支、迴圈、子代理與多模型規劃等複雜模式，而這是輸出塑形框架所無法提供的保證。

**Q6：為何作者選擇 Scala 3 作為實作語言？相關的設計取捨為何？**
A：作者選擇 Scala 3 是因為它同時支援兩項基礎能力：在環繞程式的當下脈絡中編譯全新的程式碼片段，以及追蹤該片段可使用哪些資源（透過擷取檢查 capture checking）。這兩項特性讓 LACUNA 能即時把模型產生的程式碼嵌入宿主程式並進行精細的權限控管。設計上的取捨在於，LACUNA 將代理動作綁定到一個具備強型別與編譯期檢查的宿主語言，這雖然提升了安全性與可分析性，卻也限制了模型可使用的語言範疇，必須在 Scala 3 的表達能力與代理所需的彈性之間取得平衡。

**Q7：LACUNA 在哪些基準上進行評估？為何選擇這些基準？**
A：作者在自選的驗證器測試案例集合、BrowseComp-Plus 與 τ^2-bench 三個基準上評估 LACUNA。BrowseComp-Plus 用來測試代理在需要大量瀏覽與推理的開放式問答任務上的表現，並藉此觀察拒絕率與重試行為；τ^2-bench 則橫跨四個領域共 392 個任務，用來評估代理在多輪、跨工具的真實情境中的解決率。選擇這些基準的目的，是同時涵蓋「能否表達並執行複雜代理行為」與「能否在執行前把關安全」兩個面向。

**Q8：在 BrowseComp-Plus 與 τ^2-bench 上的關鍵量化結果為何？**
A：在 BrowseComp-Plus 上，LACUNA 有 8.6% 的生成結果在執行前即被拒絕，平均每個查詢僅需 0.7 次重試，最終達到 27.1% 的準確率，顯示型別檢查能有效攔下不合格的片段而不至於造成大量重試成本。在 τ^2-bench 上，LACUNA 在四個領域共 392 個任務中解決了 76.0%，與基線代理（baseline agent）表現相當，證明引入執行前檢查並未犧牲解決能力。這兩個結果共同顯示 LACUNA 在維持高表達力的同時，仍能透過編譯器診斷驅動的重試機制兼顧安全性。

**Q9：拒絕率與重試行為透露了 LACUNA 哪些安全特性？**
A：8.6% 的執行前拒絕率顯示 LACUNA 的編譯器診斷能有效辨識出「使用了不可用名稱」、「傳入錯誤型別參數」或「回傳錯誤型別結果」等結構性失敗，並在動作開始前就將其擋下。平均 0.7 次重試意味著大多數查詢在首次或極少數重試後即可通過檢查，重試成本可控。被拒絕的動作不會留下任何環境副作用，這正是 LACUNA「整體接受或整體拒絕」原則的具體展現，也避免了傳統代理在執行中途失敗所造成的不一致狀態。

**Q10：LACUNA 能將哪些常見的代理模式表達為普通的控制流程？**
A：LACUNA 能將 ReAct 迴圈、子代理（sub-agent）、技能（skill）、平行分解（parallel decomposition）與多模型規劃（multi-model planning）等模式全部表達為普通的程式控制流程。例如，平行分解可透過 `topics.par.map(topic => agent[String](s"Research: $topic"))` 直接寫成，而多模型規劃則可在同一段程式碼中依條件路由到不同模型。這些模式不再需要由執行環境提供特殊協定，而是由模型所寫的程式碼本身組合而成，大幅提升了代理的可組合性與可分析性。

**Q11：LACUNA 對實際部署安全代理帶來哪些產品層面的助益？**
A：在產品層面，LACUNA 讓代理的權限邊界可在編譯期透過擷取檢查與資訊流控管來設定，這意味著部署者可以明確宣告某個代理動作「能否存取特定檔案、網路 handle 或工具」，而不必依賴執行期的沙箱或政策語言。由於被拒絕的動作不會留下副作用，產品可以在不冒險污染狀態的前提下反覆重試，並透過編譯器診斷訊息持續改善模型輸出。這對需要高可靠性的企業級代理部署尤其關鍵，因為它把安全檢查從「執行期補救」前移到「執行前預防」。

**Q12：LACUNA 對代理設計領域的更廣泛影響為何？**
A：LACUNA 重新定義了「代理程式」與「代理所寫程式」之間的關係，示範了讓模型產出的程式碼直接塑造執行環境的可行性，並以型別系統作為安全護欄。這種「語言整合式代理」（language-integrated agent）思路可能會啟發後續研究探索其他強型別宿主語言（如 Rust、Haskell）上的類似設計，進一步把編譯期保證引入代理領域。長遠來看，LACUNA 推動了代理設計從「執行期防禦」走向「編譯期保證」的典範轉移，對整個領域的工程實踐與學術研究方向都可能產生深遠影響。

**Q13：LACUNA 存在哪些已自我揭露的限制？**
A：LACUNA 的安全性與表達力高度依賴 Scala 3 的強型別系統與擷取檢查機制，這使得模型可使用的語言範疇被限制在 Scala 3 內，無法直接套用至其他語言的代理。此外，編譯期檢查能擋下結構性失敗，但對於「語意上錯誤但型別正確」的程式碼（例如邏輯推理錯誤或目標誤判）並無防範能力，這類錯誤仍會被接受並執行。LACUNA 也仰賴編譯器診斷訊息的品質來驅動重試，若診斷過於隱晦或模型無法理解，可能導致重試迴圈或無謂的失敗。

**Q14：LACUNA 尚未完全處理的失敗案例或攻擊向量有哪些？**
A：雖然 LACUNA 能擋下「使用不可用名稱」或「回傳錯誤型別」等結構性攻擊，但對於型別正確但語意有害的提示注入（例如誘導模型在合法範疇內執行惡意邏輯）仍缺乏專門防禦。此外，若攻擊者能操縱編譯器診斷訊息本身（例如透過間接注入影響錯誤回饋），仍可能干擾重試流程。對於涉及跨動作狀態累積的攻擊（例如透過多個看似無害的動作逐步外洩資料），LACUNA 的資訊流控管雖提供一定保障，但具體強度仍取決於 Scala 3 擷取檢查的細粒度與設定。

**Q15：LACUNA 開啟了哪些值得探索的未來研究方向？**
A：未來可探索的方向包括：將 LACUNA 的思路移植到其他強型別語言（如 Rust、Haskell、Lean）以驗證其通用性；設計更細粒度的資訊流與權限政策語言，讓部署者能宣告更豐富的安全不變式；以及研究如何讓編譯器診斷訊息本身對模型更友善，以降低重試成本並提升修復率。此外，把 LACUNA 與形式化驗證或可執行的規範結合，使代理動作不僅型別正確且語意合規，也是值得投入的方向；最後，在多代理協作與持久執行上下文中擴展 LACUNA 的安全保證，將是推向實際大規模部署的關鍵一步。

## 實務應用指南

### 適用場景

1. **企業內部自動化助理**：需要串接多個內部 API（CRM、ERP、知識庫）並依使用者意圖動態組合工作流程的場景。LACUNA 的型別檢查能在執行前阻擋錯誤呼叫，避免污染交易系統或留下半完成狀態，特別適合金融、人資、客服等高風險流程。

2. **多步驟研究與報告生成**：例如市場分析、競品研究、技術盡職調查等需要平行蒐集多主題資料、再彙整成報告的工作。透過 `topics.par.map(topic => agent[String](...))` 這類平行分解，可同時委派多個子代理研究子題，最後再呼叫一次代理整合結果。

3. **程式碼生成與重構工具**：在 IDE 或內部開發平台中，讓 LLM 填入型別化洞（typed hole）來補完函式實作、生成測試案例或重構既有程式碼。由於編譯器診斷會驅動重試，開發者只需審閱最終通過型別檢查的程式碼，無需手動除錯 LLM 輸出。

4. **多模型協作的決策系統**：在需要依任務特性路由到不同模型（如推理用強模型、摘要用輕量模型）的場景，LACUNA 讓模型選擇本身成為可被代理程式碼控制的控制流程，而非寫死在執行環境中。

5. **受監管的產業代理人**：醫療、法律、政府等需要嚴格權限控管的領域。LACUNA 的能力追蹤（capability tracking）與資訊流控制可在編譯階段就限制代理能存取的檔案、網路與工具，符合合規審查要求。

### 實作前置條件

**資料面**
- 明確的任務描述集：用於評估代理在自身領域的表現，可參考論文中 BrowseComp-Plus 與 τ²-bench 的設計，準備具明確驗證條件的測試案例。
- 工具與資源清單：列出代理可存取的檔案路徑、API 端點、資料庫連線等，並定義其能力型別（capability types）。
- 領域詞彙與型別定義：Scala 3 的型別系統需要領域專屬的代數資料型別（ADT）來表達任務結果，例如 `case class Report(sections: List[Section])`。

**運算面**
- LLM API 存取：需具備足夠品質的模型（論文中使用「capable model」於 τ²-bench 達到 76.0%），建議準備至少一個強模型與一個輕量模型用於多模型規劃。
- Scala 3 編譯環境：LACUNA 原型仰賴 Scala 3 的巨集（macros）與能力系統（capture checking），需要 Scala 3.3 以上版本。
- 沙箱執行環境：雖然 LACUNA 在執行前已做型別檢查，仍建議搭配作業系統層級沙箱（gVisor、Firecracker）作為縱深防禦。

**技能面**
- Scala 3 進階特性：熟悉代數資料型別、隱式轉換、capture checking 與編譯器巨集開發。
- LLM 提示工程：理解如何將編譯器錯誤訊息轉換為有效的重試提示。
- 能力安全模型：理解資訊流控制（information-flow control）與最小權限原則。
- 代理系統設計：熟悉 ReAct、子代理、技能呼叫等常見模式。

### 實作步驟建議

**階段一：概念驗證（2–4 週）**
1. 安裝 Scala 3 並熟悉 capture checking 語法。
2. 複製 LACUNA 開源原型，運行論文中提供的範例（研究報告生成、平行分解）。
3. 將一個現有的單工具代理（如基於 ReAct 的客服機器人）改寫為 LACUNA 風格，比較型別檢查帶來的拒絕率與重試次數。

**階段二：領域型別化（4–6 週）**
1. 盤點目標領域的所有可能輸出，為每種輸出定義 Scala ADT。
2. 為每個工具定義能力型別（capability type），標註其副作用（讀檔、寫檔、網路呼叫）。
3. 將領域知識編碼為型別約束，例如「訂單退款」必須在「訂單存在」的證明下才能呼叫。

**階段三：安全機制整合（4–8 週）**
1. 設定 capture checking 規則，限制代理只能存取明確授予的資源。
2. 實作編譯器診斷到重試提示的轉換層，確保錯誤訊息對模型友善。
3. 加入審計日誌：記錄每次 `agent[T]` 呼叫的任務、生成程式碼、通過/拒絕狀態。

**階段四：評估與調校（持續）**
1. 建立領域專屬測試集，參考論文中 8.6% 拒絕率與 0.7 次重試的基準。
2. A/B 測試不同模型組合（單一強模型 vs. 多模型路由）。
3. 監控「不一致狀態」事件：理論上 LACUNA 應為零，但需驗證。

**階段五：產品化（8–12 週）**
1. 包裝為內部 SDK 或服務，提供 REST/gRPC 介面。
2. 整合現有監控、告警、身分驗證系統。
3. 撰寫領域專屬的「代理程式庫」，將常見任務（如「查詢訂單」、「生成週報」）封裝為可重用的技能。

### 潛在風險與注意事項

**風險一：編譯器診斷對模型不友善**
Scala 3 的錯誤訊息可能過於技術性，導致 LLM 無法有效修正。緩解：建立診斷訊息轉譯層，將型別錯誤映射為自然語言指引，例如「你回傳了 `List[String]`，但預期是 `Report` 物件，請包裝為 `Report(sections=...)`」。

**風險二：能力系統的學習曲線**
Scala 3 的 capture checking 仍在演進，團隊需要時間熟悉。緩解：先在非關鍵路徑試行，並準備 fallback 機制（傳統沙箱）作為過渡。

**風險三：重試成本**
雖然平均僅 0.7 次重試，但複雜任務可能觸發多次重試，導致延遲與成本上升。緩解：設定重試上限（如 3 次），並快取成功的程式碼片段供類似任務重用。

**風險四：型別過於嚴格導致模型無法表達**
過度細緻的型別可能讓模型找不到任何合法實作。緩解：在設計型別時保留合理的彈性，例如使用 `Either[Error, T]` 而非要求模型必定成功。

**風險五：提示注入仍可能影響生成內容**
型別檢查能阻擋結構性錯誤，但無法阻擋語意層面的攻擊（如生成誤導性報告內容）。緩解：搭配輸入強化、輸出審查與人類監督，特別是高風險決策。

**風險六：Scala 生態系人才稀缺**
相較 Python/TypeScript，Scala 開發者較少，維運成本較高。緩解：考慮將核心原型移植到其他具 capture checking 或效果系統的語言（如 Koka、Effekt），或將 LACUNA 編譯為 JVM 位元碼以降低部署摩擦。

---

### 與其他技術的整合建議

**與 LangChain / LlamaIndex 整合**
將 LACUNA 作為「程式碼代理」的後端引擎，LangChain 負責工具定義與提示管理，LACUNA 負責執行與型別檢查。可將 LangChain 的工具包裝為 Scala 能力型別，透過 JNI 或 HTTP 橋接。

**與 DSPy 互補**
DSPy 擅長單次呼叫的輸入輸出優化，LACUNA 擅長多步驟控制流。可在每個 `agent[T]` 內部使用 DSPy 優化提示，外部則用 LACUNA 表達整體工作流程。

**與 MCP（Model Context Protocol）整合**
MCP 提供標準化的工具描述，LACUNA 可將 MCP 工具動態編譯為 Scala 能力型別，使代理能自動發現並使用新工具，同時維持型別安全。

**與現有 CI/CD 整合**
將 LACUNA 代理的執行為一項 CI 步驟，例如自動生成 API 文件、執行遷移腳本或審查程式碼變更。編譯器診斷可直接整合進 PR 評論。

**與監控系統整合**
將每次 `agent[T]` 呼叫的編譯結果、執行時間、重試次數輸出至 Prometheus/Grafana，建立「代理健康度」儀表板。

**與人類審查流程整合**
對於高風險任務，設計「dry-run」模式：先編譯並顯示將要執行的程式碼，由人類批准後才實際執行。這在金融、醫療等領域尤為重要。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的動機部分，理解「為什麼代理需要寫程式碼而不只是呼叫工具」，再跳到第 5 節看具體範例（研究報告生成那段程式碼）。型別化洞的概念可以類比為「填空題」：你給 LLM 一個有明確答案格式的問題，它必須填入能通過編譯的程式碼。暫時跳過 Scala 3 的技術細節，專注在「代理動作 = 一段被型別檢查的程式碼」這個核心直覺。

**給 AI 工程師**：重點閱讀第 3 節的程式設計模型與第 4 節的安全性分析。理解 `agent[T](task)` 如何在執行點編譯 LLM 生成的程式碼，以及 capture checking 如何限制代理能使用的資源。實作上可從複製原型開始，將現有 ReAct 代理改寫為 LACUNA 風格，親身體驗「編譯器診斷驅動重試」的開發體驗。建議同時關注 Scala 3 capture checking 的最新進展，這是 LACUNA 安全保證的基石。

**給研究者**：第 4 節的安全性分析是論文最具理論深度的部分，建議仔細閱讀預執行拒絕、無部分執行保證、權限與資訊流控制的論證。第 6 節的評估設計也值得參考，特別是如何用編譯器診斷作為重試訊號。可考慮的延伸方向包括：將此模型移植到其他具效果系統的語言、形式化驗證 LACUNA 的安全性質、或探索其在多代理系統中的應用。

**給產品經理**：聚焦在第 1 節的問題陳述與第 7 節的評估結果。理解 LACUNA 解決的商業問題：代理在執行中失敗導致狀態污染、攻擊者可透過提示注入操控代理行為。關鍵數字：BrowseComp-Plus 上 27.1% 準確率、τ²-bench 上 76.0% 解決率、僅 8.6% 生成被拒絕、0.7 次平均重試——這些數字顯示 LACUNA 在表達力與安全性之間取得了務實平衡。產品化時，建議從「高風險但低頻次」的場景（如合規審查、複雜報告生成）切入，而非直接取代所有現有代理。
