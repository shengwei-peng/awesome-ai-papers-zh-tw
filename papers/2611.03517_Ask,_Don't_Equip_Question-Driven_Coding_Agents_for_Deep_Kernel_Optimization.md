KernelSeek 的核心論點建立在一個精準的診斷上：現有的 LLM 核心優化代理（不論是腳本化或開放式）都缺少「方向」（direction），即對於剩餘效能差距所在位置的假設。腳本化代理（如 Autocomp）將「該做什麼」編碼進流程中，因此在適用範圍內樣本效率高，但一旦超出預設選單即崩潰；開放式代理（如 AlphaEvolve、AVO）則讓 LLM 自由變異族群程式碼，以大量試驗（AVO 在七天內探索超過 500 個方向才提交 40 個版本）換取自由度。KernelSeek 的設計哲學是保留開放式代理的自由度，同時透過在關鍵決策點注入問題來恢復腳本化代理的效率。

**架構組成：**

1. **通用編碼代理（General-Purpose Coding Agent）**：KernelSeek 並未訓練專門的模型或預先消化上下文，而是直接使用一個通用的編碼代理。這意味著方法的可遷移性不依賴於特定模型或運算子知識。

2. **最小化測試框架（Minimal Harness）**：唯一目的導向的元件。功能包括：
   - 將每個候選核心與種子核心的輸出比對
   - 與 fp32 參考實作比對以確保正確性
   - 對每個情境（scenario）計時並與種子核心比較
   - 將目標陳述為一個**可驗證**的停止條件，而非由代理自行聲明完成

3. **問題注入機制**：在以下三類決策點提問：
   - 進度停滯時
   - 代理宣稱達到極限或完成時
   - 出現可疑的大幅提升時

4. **問題庫（Question Bank）**：反覆出現的問題會硬化成庫，代理可對自身套用。這使得 KernelSeek 能與演化搜尋結合，將同一代理包裝成 AVO 風格的族系（lineage），其指令即為問題。

**關鍵設計原則：「好問題不含答案」**

論文中強調一個重要的設計原則——一個有效的問題應該命名一個代理未曾考慮的假設，而測試該假設所需的測量是代理可用普通工具完成的。例如，「讓這個更快」是開放式的，模型會以貪婪方式回答；但「基準是在核心週期上勝出還是只在牆時鐘時間上勝出？」是有界的，為了回答它，模型會拆解並重寫核心中它原本不會觸及的部分。這種提問方式提供方向但**不限制**代理下一步可做的事，這是更多結構、更多自由度或更多工具都無法達成的效果。

**問題驅動 vs. 工具裝備（Equipping）的本質差異：**

論文的標題「Ask, Don't Equip」點明了核心對比。現有方法面對困難目標時傾向於「裝備」代理：解析後的分析器輸出、反組譯分析、文件與函式庫的檢索、經驗儲存庫等。但這些資訊只在提供模型所缺少的特定事物時才有幫助，而分析器與編譯器輸出很少能做到這一點。問題則不同——它改變了任務本身。

Autocomp（Hong et al., 2025）依賴優化選單，沒有選單時效能崩潰。固定迴圈 RL（Baronio et al., 2026; Li et al., 2026; Liu et al., 2026）在單一運算子上有競爭力，但在融合模型上失敗。KernelSeek 不預設「該嘗試什麼」，因此不受此限制。

**與人類引導代理的比較：**

### 實作步驟建議

**步驟 1：建立最小化測試框架（Minimal Harness）**
這是整個系統唯一需要自建的元件。harness 需提供三項功能：(a) 編譯候選核心並回報錯誤；(b) 在所有 scenarios 上執行正確性檢查（與 fp32 參考比對，容差可設定）；(c) 計時每個 scenario 並回報相對於 seed 的加速比。harness 的輸出必須是機器可解析的結構化資料，而非自由文字。

**步驟 2：選定通用編碼代理**
選擇一個具備長上下文、工具使用能力、且未經 CUDA 專屬微調的通用 LLM 代理。論文中強調「無運算子專屬知識」，因此不建議使用經過 CUDA 資料微調的專用模型。代理需能讀寫檔案、執行 shell 指令、解析編譯器與 profiler 輸出。

**步驟 3：定義決策點（Decision Points）**
根據論文的觀察，問題應在三個時機提出：(a) 進度停滯時（連續 N 次無加速）；(b) 代理宣稱已達極限或完成時；(c) 出現可疑的大幅提升時（需驗證是否犧牲了正確性或僅在單一 shape 有效）。將這些時機編碼為自動化觸發條件。

**步驟 4：建立初始問題庫（Question Bank）**

**步驟 5：執行迭代最佳化迴圈**

### 潛在風險與注意事項

**問題品質的長尾分佈**
並非所有問題都能產生效益。論文中明確指出「提供資訊的問題」無效，只有「改變任務定義」的問題才有效。實作時需建立問題分類機制，將「解釋型」問題（無效）與「假設檢驗型」問題（有效）區分開，否則問題庫會被低品質問題污染。

**正確性驗證的覆蓋率**
論文中 FlashAttention 在每個架構上通過 182 個 scenarios 的驗證，但這僅代表測試集中的形狀。部署到生產環境時，可能遇到未測試過的邊界條件（極短序列、非對齊維度、特殊 mask 模式）。建議在部署前擴充測試集，並加入壓力測試與長時間穩定性驗證。

**硬體特定性的轉移成本**
在 H200 上達到 1.16× FA3 的核心，未必能在 A100 或 B200 上維持相同加速比。論文中 Hopper 與 Blackwell 各需獨立最佳化流程。實作時應將硬體版本、驅動、CUDA 版本視為不可變參數，並為每個目標硬體建立獨立的 traces 與問題庫。

**代理陷入局部最優的風險**
即使有問題驅動，LLM 仍會從其先驗貪婪搜尋。論文中提到代理會「循環產生近似變體」或「提早停止」。對策是在 harness 中加入多樣性指標（程式碼差異度），當候選過於相似時自動觸發「換個方向」的問題。

**長上下文與成本控制**
11.5K 次工具呼叫、162 條人類訊息代表極長的對話歷史。實作時需設計上下文摘要機制，保留關鍵決策與程式碼版本，否則 API 成本與延遲會失控。建議每 N 輪進行一次 traces 壓縮。

**「宣稱完成」的誤判**
LLM 常在環境反駁時仍回報完成（論文中引用 Advani 2026）。harness 必須以「驗證過的停止條件」取代「代理請求的停止」，例如設定「必須在所有 scenarios 上達到 X× 加速比且正確性 100%」才視為達標。
