## ⚡ TL;DR

現今語言模型需重新訓練且輸出不確定，已驗證問題仍重複生成造成浪費。
提出凍結模型搭配持久驗證記憶，獨立驗證後永久位元精確重用解答。
九類問題一百八十例全對且零生成詞元，驗證工作成本與延遲遠低於前沿模型。

## 摘要翻譯

現今要改進語言模型（Language Model），意味著必須重新訓練（Retraining）：耗費龐大運算資源（Compute）、每個週期都產生新的不透明模型（Opaque Model），且輸出亦為非確定性輸出（Non-Deterministic Output）。我們採取相反路徑：模型維持凍結（Frozen 12B），並在其旁持續擴充一個存放已驗證解答（Verified Solutions）的持久記憶體（Persistent Memory）。一旦某個問題家族（Problem Family）被解決，並通過一個絕不參考答案鍵（Answer Key）的獨立驗證（Independent Verification）步驟，該家族的每個新實例都能以零生成 token（Zero Generation Tokens）、位元精確（Bit-Exact）、確定性（Deterministic）地回答。在橫跨九個問題家族（Problem Family）的 180 個全新實例中，來自四家廠商的四種架構——稠密架構（Dense Architecture）與混合專家模型（Mixture-of-Experts, MoE）——均達成 180/180，且每個答案皆使用零生成 token（Zero Generation Tokens）：這是與參數規模擴展（Parameter Scaling）解耦（Decoupled）的執行導向能力（Execution-Bound Capability）。陰性對照（Negative Control）證實此能力完全歸因於記憶：清空後，系統無法解出任何題目。同樣的先驗證再儲存契約也適用於開放式推理（Open-Ended Reasoning）：在四個模型上達成 88/88 的一致性閘控接受（Consistency-Gated Acceptances），以及機器檢查的形式證明（Machine-Checked Formal Proof）與 77/80 的推理方法遷移（Reasoning-Method Transfer）。記憶選取（Memory Selection）耗時 1.4 微秒；完整重用（Full Reuse）可在 6–23 毫秒（Millisecond）內完成，耗能 36 毫瓦時（mWh）。在一個擁有 4,500 個項目的已驗證儲存庫（Verified Store）上，近似相似度檢索（Approximate Similarity Retrieval）在 94.3% 的情況下選錯項目，而精確定址（Exact Addressing）則無任何錯誤。該儲存庫也作為運作上下文，規模超越任何已發布引擎（Shipped Engine）：在單張 GPU（Single GPU）上以固定記憶體（Flat Memory）提供 6,000,000 token 的可移動視窗（Movable Window），而 vLLM 在 30,399 token 處停止，SGLang 則在超過 32,000 token 後靜默截斷（Silently Truncates）。在已發布的基準測試上，前沿模型（Frontier Models）在從頭開始的原始推理（Raw From-Scratch Reasoning）方面仍遠勝任何 120 億參數模型；但在本系統已解決並驗證的所有項目上，比較結果反轉：一次前沿 API 呼叫（API Call）在每次查詢上都需付出一次全新的生成階段（Generation Pass），且永久（Forever）如此，而已驗證解答（Verified Solutions）的重用則耗費零 token（Zero Generation Tokens），並每次都回傳完全相同的位元（Identical Bits）。本報告附帶一個可免費（Free Access）但受速率限制存取（Rate-Limited Access）的公開測試台（Public Testbench）：https://corbenic-galahad-bench.hf.space

### 核心貢獻（3～5點）
- 提出「凍結小模型 + 持久已驗證記憶體」的替代路徑，使已驗證問題家族能以零生成 token、位元精確、確定性地永久重用，無需重新訓練。
- 在橫跨九個問題家族的 180 個全新實例上達成 100% 準確率，證明執行導向能力可與參數規模擴展解耦。
- 透過陰性對照確認能力完全來自已驗證記憶體，並將「先驗證、後儲存」的契約擴展至開放式推理、機器檢查的形式證明與推理方法遷移。
- 展示精確定址相對於近似相似度檢索的壓倒性優勢，並在單張 GPU 上以固定記憶體實現 600 萬 token 的可移動視窗，超越現有已發布引擎的上下文規模。
- 提供可免費、受速率限制存取的公開測試台（Corbenic-Galahad-Bench），供外界獨立驗證本系統的成效。

### 適合對象
本報告最適合大型語言模型（LLM）與推理系統的研究人員、關注推論效率與可驗證性的系統工程師，以及探索記憶體增強架構、形式驗證與模型部署成本的產業從業者與進階讀者。對於希望了解如何在不重新訓練模型的前提下提升已解決問題之準確率與確定性的技術決策者，亦具高度參考價值。

## 深度分析

#### 方法論解析

本報告提出的是一種「凍結模型（frozen model）＋持久驗證記憶（persistent memory of verified solutions）」的雙軌架構，系統命名為 Galahad，其儲存與完整性層稱為 Merlin。核心方法論並非重新訓練（retraining）模型，而是將「求解（derivation）」與「執行（execution）」解耦（decoupled）：對每個問題家族（problem family）只進行一次求解與驗證（solve-and-verify campaign），通過獨立驗證（independent verification）後存入已驗證儲存庫（verified store），之後同一家族的任何新實例都以零生成 token（zero generation tokens）、位元精確（bit-exact）、確定性（deterministic）的方式重用。

具體而言，方法論包含以下環節：

1. **模型凍結（frozen model）**：不進行微調、不更新權重。報告中使用的是 120 億參數的開源模型 Gemma-4-12B，並額外測試另外三家廠商、涵蓋稠密架構（dense architecture）與混合專家模型（mixture-of-experts, MoE）的模型。所有模型的權重在整個實驗期間保持不變。

2. **參數化驗證方法而非快取答案**：作者強調這不是傳統的 memoization（記憶化快取）。每個儲存項目是「參數化的已驗證方法」，能夠在新輸入值（fresh parameter instances）出現時重新計算答案。換言之，記憶中存放的是可執行的解題程序或形式化方法，而不是單一輸入–輸出對。

3. **獨立驗證與 verify-before-store 合約**：在存入記憶之前，每個解答必須通過一個不參考答案鍵（answer key）的獨立驗證步驟。這是避免資料污染與確保正確性的關鍵設計。對於演算法與數學問題，驗證可能對應於程式執行、單元測試或機器檢查的形式證明（machine-checked formal proof）；對於開放式推理（open-ended reasoning），則透過一致性閘控接受（consistency-gated acceptances）與形式證明來把關。

4. **精確定址（exact addressing）而非向量式檢索**：Merlin 使用精確定址存取已驗證項目，而非業界常見的近似相似度檢索（approximate similarity retrieval）。報告指出，在 4,500 個項目的儲存庫中，向量式檢索有高達 94.3% 的機率選錯項目，而精確定址的錯誤率為零。這對於需要可執行、可驗證的知識而言是設計上的必要條件，而非可妥協的偏好。

5. **零生成成本與確定性執行**：一旦問題家族被存入，後續每個新實例的回答都不需要語言模型進行自迴歸生成（autoregressive generation）。記憶選取（memory selection）僅需 1.4 微秒（microseconds），完整重用（full reuse）在 6–23 毫秒（milliseconds）內完成，每次回答能耗約 36 毫瓦時（mWh）。由於沒有隨機取樣，輸出是位元精確且可重現的，適合需要稽核軌跡（audit trail）與監管簽核的場景。

6. **大規模工作上下文（working context）**：已驗證儲存庫同時充當可移動視窗（movable window），可在單張 46 GB GPU 上支援 6,000,000 token 的上下文，且記憶體用量呈現固定記憶體（flat memory）特性；相較之下，vLLM 在約 30,399 token 處停止，SGLang 則會在超過約 32,000 token 時靜默截斷（silently truncates）。

總結來說，這套方法論把「能力增長」從參數規模擴展（parameter scaling）轉移到「已驗證知識的累積」，並透過精確定址與獨立驗證，確保執行導向能力（execution-bound capability）可以在凍結的小模型上穩定發揮。

#### 實驗數據解讀

報告的實驗設計圍繞幾個層次：核心重用正確率、跨架構不變性、陰性對照、開放式推理、延遲與能耗、檢索精確度，以及上下文視窗（context window）規模。以下逐項解讀。

**核心結果：180/180 與零生成 token**

在九個問題家族、共 180 個全新實例（fresh instances）上，Gemma-4-12B 獲得 180/180（100% 準確率），且每個答案的 generation pass（生成階段）token 數為零。九個家族中五個家族各 12 題、四個家族各 30 題，涵蓋演算法與數學領域。這個結果直接說明：對於已經被求解並驗證的問題家族，系統可以完全不依賴語言模型的即時推理，而是透過已驗證方法執行出正確答案。

**跨架構不變性（architectural invariance）**

實驗同時在四個來自不同廠商的模型上進行，包含稠密架構與 MoE。四個模型同樣達到 180/180。這是方法論中最具顛覆性的暗示：當解答被正確驗證並以可執行形式儲存後，執行能力與模型參數量或架構細節脫鉤。換句話說，「聰明」不再完全來自於模型權重，而是來自於記憶中累積的已驗證工作（verified work）。

**陰性對照（negative control）**

作者進行了一項關鍵對照：將記憶清空後，系統無法解出任何題目。這排除了「模型本身已內建這些問題的知識」這一替代解釋，把能力來源明確歸因於已驗證儲存庫。對於理解系統運作機制而言，這個對照至關重要。

**開放式推理與推理方法遷移（reasoning-method transfer）**

報告將 verify-before-store 合約延伸到開放式推理：在四個模型上達成 88/88 的一致性閘控接受，並搭配機器檢查的形式證明。此外，推理方法遷移實驗在 80 個案例中成功 77 個（96.25%），顯示儲存的方法不僅能處理同一問題家族內的參數變化，還能在不同但結構相關的問題之間遷移。這說明該方法不只適用於封閉式計算題，對於需要抽象推理的問題也具備一定潛力。

**延遲、能耗與成本結構**

記憶選取僅 1.4 微秒，完整重用 6–23 毫秒，每次回答能耗 36 mWh。相較於一次性 81.1 Wh 的求解與驗證流程，邊際成本極低。這種成本結構與 frontier models（前沿模型）的 API 呼叫形成鮮明對比：後者每次查詢都要支付新的生成階段費用，且輸出非確定性。對於高頻、可驗證的任務，這種「一次驗證、永久重用」的經濟性非常明顯。

**精確定址 vs. 近似相似度檢索**

在 4,500 個項目的已驗證儲存庫上，向量式檢索選錯項目的比例高達 94.3%，而精確定址零錯誤。這個數據對 RAG（retrieval-augmented generation）社群是強烈警示：當知識是「可執行且可驗證」時，語義相似並不等價於功能正確。兩個問題可能在語意上高度相近，但參數或約束條件的微小差異會導致完全不同的答案。因此，對於這類知識，精確定址是必要條件。

**上下文視窗與記憶體效率**

系統可在單張 46 GB GPU 上提供 6,000,000 token 的可移動視窗，且記憶體使用不隨視窗大小增長。相較於 vLLM（約 30,399 token）與 SGLang（約 32,000 token 後靜默截斷），這是一個數量級上的躍升。這暗示 Merlin 並非以傳統 KV cache 方式儲存上下文，而是採用某種更緊湊、可隨機存取的表示法。不過，由於架構細節未公開，無法判斷其與現有引擎的比較是否完全公平。

**數據解讀的限制**

需要強調的是，所有實驗都發生在「已驗證領域」內。報告本身也承認，在原始從頭推理（raw from-scratch reasoning）的公開基準上，frontier models 仍然遠勝任何 12B 模型。因此，「凍結 12B 擊敗前沿模型」這個標題必須嚴格理解為「在已驗證工作上」的比較，而非全面性的能力超越。

#### 與現有研究的比較

本報告延續了作者先前的三條研究線：檢索場景中的位元精確去重複（byte-exact deduplication in retrieval settings）[25]、Merlin 去重複引擎 [26]，以及凍結模型上的位元精確狀態重用（byte-exact state reuse on frozen models）[27]。與這些前期工作相比，本次報告將概念擴展為一套完整的已驗證知識系統，並加入獨立驗證、跨架構測試、開放式推理與大規模上下文視窗等實證。

**與 RAG / 向量檢索的差異**

傳統 RAG 系統依賴近似相似度檢索，從外部知識庫中召回相關文本片段，再交由語言模型生成答案。這種方法在開放域問答、文件摘要等場景表現良好，但無法保證答案正確性，也無法避免語義相近但功能不同的項目被混淆。Galahad 的方法則完全放棄近似檢索，改用精確定址與獨立驗證，將「可執行知識」與「語義相似知識」區分開來。這不是對 RAG 的漸進改良，而是針對可驗證工作所提出的替代典範。

**與快取 / 記憶化的差異**

傳統 memoization 儲存的是「輸入–輸出對」，只能處理完全相同的輸入。Galahad 儲存的是「參數化方法」，可以處理同一問題家族內的全新參數實例。這使其更接近「程序庫學習（library learning）」或「神經–符號系統（neuro-symbolic systems）」的概念：模型不再從頭推理，而是呼叫並執行已驗證的程序。

**與程式合成 / 工具使用的差異**

現有 LLM 程式合成流程通常是：模型即時生成程式碼，再透過解釋器執行。這仍然涉及 generation pass，且輸出可能因取樣而異。Galahad 則將「生成程式」與「執行程式」分離：程式在存入前已經過驗證，執行時無需再次生成。這降低了延遲、能耗與不確定性，但前提是問題必須屬於已經被覆蓋的家族。

**與前沿模型的差異**

Frontier models 的優勢在於廣泛的通用知識與強大的冷啟動推理能力。然而，它們每次 API 呼叫（API call）都要進行完整的生成階段，輸出非確定性，且成本隨 token 數線性增長。Galahad 的價值主張在於：對於已經被求解並驗證的問題，邊際成本趨近於零、延遲為毫秒級、輸出位元精確。這不是取代 frontier models 的通用能力，而是對「重複求解已解決問題」這一結構性浪費的糾正。

**與形式化驗證的差異**

報告中提到的機器檢查形式證明與 verify-before-store 合約，與互動式定理證明器（如 Lean、Coq）有概念上的親緣關係。不同之處在於，Galahad 將形式化驗證嵌入到一個生產系統中，並強調「不參考答案鍵」的獨立驗證，這對於防止基準資料污染具有重要意義。

**主要限制**

1. **適用範圍受限**：必須存在可機器檢查的驗證器。對於主觀判斷、創意寫作、無明確正確答案的開放式任務，此方法難以直接套用。

2. **問題家族需要被預先覆蓋**：系統無法處理完全陌生、不在儲存庫中的問題類型。冷啟動能力仍依賴 frontier models 或其他求解器。

3. **架構不透明**：作為產業經驗報告，作者刻意不公開演算法、資料結構與配置，這限制了學術界的獨立檢驗與比較。

4. **與現有引擎的比較可能不完全對等**：6M token 上下文與 vLLM/SGLang 的比較，可能涉及不同的記憶體表示與功能語義，需要更多細節才能公平評估。

5. **儲存庫維護挑戰**：隨著問題家族增加，如何管理版本、偵測衝突、更新過時方法、避免錯誤累積，都是未解的實務問題。

#### 可重現性評估

本報告明確定位為「產業經驗報告（industry experience report）」，而非方法論論文。因此，作者只報告輸入–輸出層級（input–output level）的測量結果，刻意隱藏架構、演算法與配置。這對可重現性（reproducibility）造成顯著限制，但作者也提供了兩條驗證管道：

1. **公開測試台（public testbench）**：Corbenic-Galahad-Bench 提供免費、速率限制（rate-limited access）的存取，任何人都可以直接觀察 headline behavior：零生成 token、位元精確輸出、確定性回答。這是黑箱驗證的重要管道。

2. **雜湊錨定的原始成品（hash-anchored raw artifacts）**：原始結果檔案與密碼學雜湊在 NDA（non-disclosure agreement）下提供，可供特定合作夥伴稽核。

**可重現性的優點**

- 使用的語言模型權重是公開的（如 Gemma-4-12B），其他三個模型也來自公開廠商，這降低了「模型不可取得」的障礙。
- 公開測試台讓外部使用者能夠獨立驗證核心聲稱，例如零 token 與 bit-exact。
- 實驗設計中的陰性對照、跨架構測試與獨立驗證，增強了結果的內部效度。

**可重現性的缺點**

- **無開源程式碼**：Galahad 與 Merlin 的實作細節未公開，第三方無法重建系統。
- **無公開資料集與配置**：問題家族的產生方式、驗證器的設計、精確定址的實作、記憶體管理策略均未揭露。
- **NDA 限制**：雜湊錨定成品雖然存在，但取得需要簽署保密協議，一般研究者無法自由存取。
- **無法獨立測量能耗與延遲**：公開測試台可能受限於速率與觀測能力，難以複製 1.4 µs、6–23 ms、36 mWh 等內部測量。

**改進建議**

若作者希望提升學術影響力與社群信任，可考慮釋出：
- 問題家族產生器與測試腳本；
- 驗證器規格（verifier specification）；
- 評估框架（evaluation harness）；
- 去識別化的系統協定說明；
同時保留商業敏感的實作細節。這樣可在保護專有技術（proprietary）與促進可重現性之間取得平衡。

#### 未來研究方向

本報告雖然以產業系統為主，但其所揭示的「驗證後永久重用」典範開啟了多個值得學術界與產業界共同探索的方向：

1. **自動化問題家族發現與抽象化**
   目前系統似乎依賴人工或半自動方式定義問題家族。未來可研究如何從大量範例中自動發現可參數化的問題家族，並生成對應的驗證方法，降低建置儲存庫的成本。

2. **通用驗證預言機（general-purpose verification oracles）**
   現階段方法最適合數學、演算法與可形式化領域。未來可擴展到科學計算、工程設計、法律條文檢查等領域，發展更廣泛的機器檢查標準。

3. **精確定址與近似檢索的混合架構**
   雖然報告強調精確定址的必要性，但在探索未知問題時，近似相似度檢索仍有價值。研究如何設計「探索時用近似、執行時用精確」的混合系統，並提供嚴格的錯誤界限，將是重要課題。

4. **與互動式定理證明器更深度的整合**
   將 Lean、Coq 等工具產生的證明與策略直接作為可重用方法儲存，並建立從自然語言問題到形式化證明的自動化管線。

5. **儲存庫的可擴展管理與維護**
   隨著儲存項目增長，需要研究版本控制、衝突偵測、過時方法淘汰、以及錯誤傳播抑制等機制，確保已驗證儲存庫的長期可靠性。

6. **對抗穩健性與分佈外偵測**
   精確定址的前提是輸入能被正確歸類到對應家族。未來需研究如何偵測語義等價但語法變異的輸入，以及如何拒絕處理分佈外（out-of-distribution）實例，避免錯誤重用。

7. **稽核、監管與可解釋性應用**
   位元精確、確定性輸出特別適合金融、醫療、法律等需要稽核軌跡的場景。可發展相關標準與認證流程。

8. **能源與永續性量化**
   進一步量化相較於重複呼叫 frontier API 所節省的能源與碳排放，並優化一次性 solve-and-verify campaign 的效率。

9. **與前沿模型的協作生命週期**
   建立「前沿模型負責冷啟動求解，凍結模型＋驗證記憶負責高頻執行」的混合部署模式，並研究兩者之間的知識轉移與更新策略。

10. **公開基準與競賽**
    建立專門針對 verified-work reuse 的公開基準，讓不同團隊比較精確定址、驗證效率、記憶體佔用與跨架構不變性，推動該領域的標準化。

## 論文問答

**Q1：這篇報告主要想解決什麼問題？**
A：這篇報告指出，現今提升語言模型能力的主流途徑是重新訓練，但這會帶來龐大的運算資源消耗、每次循環都產生一個需要重新審計的不透明模型，以及輸出結果仍具非確定性等結構性成本。這種非確定性輸出使得傳統生成方式難以適用於需要稽核軌跡、可重現性或法規簽核的場景。因此，作者提出一條相反的路徑：讓模型保持凍結，轉而在其旁邊建立一個持續增長的已驗證解答記憶體，以解決重複求解所造成的浪費與不可預測性。

**Q2：現有的前沿模型 API 為何在處理「已解決過的問題」時會失效？**
A：現有的前沿模型 API 本質上把每次查詢都當成全新的生成任務，即使該問題家族早已求解並驗證過，仍必須支付一次完整的生成階段與程式執行成本。這相當於把大型模型當成過度參數化且非確定性的執行引擎，反覆重新推導早已確認正確的工作。這種做法不僅浪費 token、增加延遲，也無法保證每次回傳的位元完全一致，對於可驗證的執行知識而言是結構性的低效率。

**Q3：為什麼確定性與獨立驗證對生產系統如此重要？**
A：在許多高風險或受監管的應用中，系統必須提供可稽核、可重現且一致的輸出，而非確定性輸出會直接 disqualify 普通生成模型在這些場景的使用。Galahad 採用的「先驗證、後儲存」合約確保每個解答在進入記憶體前，都經過一個不參考答案鍵的獨立驗證步驟。如此一來，後續每次重用都能以位元精確、零生成 token 的方式回傳完全相同的位元，建立可信賴且可重複的執行紀錄。

**Q4：Galahad 的核心方法是什麼？**
A：Galahad 搭配名為 Merlin 的確定性引擎，核心設計是讓語言模型保持凍結，永遠不進行微調或權重更新，並在其旁邊維護一個持久記憶體。每個問題家族只需經過一次求解與獨立驗證，驗證過程絕不參考答案鍵，通過後才存入已驗證儲存庫。當遇到同一家族的新實例時，系統並非回傳快取答案，而是從記憶中取出已驗證的參數化方法，並在新的輸入值上重新執行，最終以零生成 token 產生位元精確的結果。

**Q5：這項研究最關鍵的創新點是什麼？**
A：最關鍵的創新在於將「執行導向能力」與「參數規模擴展」解耦，證明一個凍結的 120 億參數模型在已驗證的工作上，可以勝過每次都要重新生成的前沿模型。另一項創新是展現了架構不變性：無論是稠密架構還是混合專家模型，來自四家不同供應商的四種模型在 180 個新實例上全部達到 180/180。此外，系統以精確定址取代業界預設的向量式檢索，並把「驗證後儲存」當成不可妥協的設計要求，而非可選偏好。

**Q6：為什麼系統選擇精確定址，而非近似相似度檢索？**
A：報告中的對照實驗顯示，在一份 4,500 個項目的已驗證儲存庫上，近似相似度檢索有高達 94.3% 的機率選到錯誤項目，而精確定址的錯誤率為零。對於可驗證的執行知識而言，選錯項目會導致災難性後果，因此精確性不是偏好，而是設計需求。這也說明向量式檢索雖然在語意搜尋上有效，但在需要位元精確與可執行驗證的場景中並不適用。

**Q7：實驗設計與主要結果有哪些？**
A：研究在九個演算法與數學問題家族上進行測試，共使用 180 個全新參數實例，結果凍結的 120 億參數模型以及另外三種來自不同廠商的架構全部達到 180/180，且每個答案都消耗零生成 token。在開放式推理方面，系統在四種模型上達成 88/88 的一致性閘控接受率，並在推理方法遷移測試中達到 77/80。此外，記憶選取僅需 1.4 微秒，完整重用流程在 6–23 毫秒內完成，每次驗證重用的能耗僅 36 毫瓦時。

**Q8：報告進行了哪些對照或消融實驗來支持結論？**
A：最重要的對照是陰性對照：當已驗證記憶體被清空後，系統完全無法解題，這把執行能力完全歸因於記憶體而非模型本身的從頭推理能力。第二個關鍵對照是比較精確定址與近似相似度檢索，凸顯向量式檢索在已驗證儲存庫上的災難性失敗。第三個對照則是能量與延遲測量，顯示一次性的 81.1 瓦時求解與驗證流程，能換來後續幾乎可忽略的重用成本。

**Q9：這些結果對「模型規模決定能力」的傳統觀點有何意涵？**
A：結果顯示，一旦問題家族被求解並獨立驗證，執行能力可以與參數規模脫鉤，一個凍結的 12B 模型在已驗證領域的表現不亞於任何前沿模型。這並不表示 12B 在從頭開始的原始推理上超越前沿模型，事實上報告也承認在冷啟動推理與公開基準測試上，前沿模型仍然遙遙領先。然而，在「已解決且已驗證」的領域中，比較關係反轉：規模不再是決定因素，驗證與精確重用才是關鍵。

**Q10：這套系統最適合應用在哪些實務場景？**
A：最適合的場景是那些具有可重複、可驗證執行特性的工作，例如演算法程式執行、機器檢查的形式證明、結構化資料處理、合規報告生成，以及需要一致輸出的工程計算。只要同一問題家族會被反覆查詢，系統就能以零生成 token 的方式提供確定性答案，顯著降低延遲與成本。對於需要完整稽核軌跡或法規簽核的產業應用，位元精確且可驗證的重用也特別具有吸引力。

**Q11：若要把這套系統產品化，需要考慮哪些關鍵因素？**
A：首先必須建立一個獨立且不可參考答案鍵的驗證器，確保只有正確的解答才能進入已驗證儲存庫。其次，儲存與檢索層必須支援精確定址與位元精確執行，避免近似相似度檢索帶來的災難性錯誤。此外，由於這是專有生產系統，產品化時還需考慮記憶體完整性、存取控制，以及如何透過公開測試台或雜湊錨定成品向客戶證明其宣稱的行為。

**Q12：這項研究對整個語言模型領域可能帶來什麼影響？**
A：這項研究挑戰了「提升能力就必須重新訓練更大模型」的預設思維，提出以驗證記憶體取代重複生成的替代典範。它強調對於可驗證知識而言，精確性、確定性與獨立驗證可能比單純擴大參數規模更重要。長遠來看，這可能促使更多生產系統採用「求解一次、驗證一次、永久重用」的架構，並重新審視向量式檢索在高風險執行任務中的適用性。

**Q13：作者承認了哪些限制或適用範圍？**
A：作者明確指出，這套系統的優勢僅限於「已經被求解並獨立驗證」的問題家族，冷啟動的從頭推理並不在其宣稱範圍內。在公開基準測試的原始推理上，前沿模型仍然遠勝任何 12B 模型，這一點在報告 §2.8 中以官方公開數據進行說明。此外，由於這是產業經驗報告，作者刻意不揭露架構、演算法與配置細節，因此外部研究者無法直接複製內部實作。

**Q14：在什麼情況下這套系統會失敗或無法運作？**
A：當問題家族從未被求解並驗證過時，系統沒有對應的已驗證記憶體可以重用，因此無法回答，這正是陰性對照所展示的結果。如果錯誤地採用近似相似度檢索而非精確定址，則在 4,500 個項目的儲存庫中有極高機率選到錯誤項目，導致輸出錯誤。此外，若驗證步驟不夠嚴謹或意外參考了答案鍵，整個「驗證後儲存」的信任基礎就會崩解。

**Q15：未來可以朝哪些方向延伸或改進？**
A：未來可以擴大已驗證儲存庫的覆蓋範圍，納入更多演算法、數學與形式證明問題家族，並進一步自動化求解與驗證流程以降低一次性成本。也可以探索與更多機器檢查形式證明工具的整合，讓開放式推理的驗證更加嚴謹。此外，未來研究可進一步檢驗架構不變性在更廣泛模型與任務上的適用性，並在適當條件下透過保密協議釋出更多雜湊錨定原始成品，以促進外部驗證。

## 實務應用指南

### 適用場景

1. **監管與財務報表的確定性計算**  
   審計軌跡要求「同樣輸入、同樣輸出」的場景，例如資本適足率、稅務試算、會計分錄生成。將每個計算家族求解並通過獨立驗證後存入已驗證儲存庫，後續同家族的新參數實例即可零 token、位元精確地回傳，滿足監管簽核與可重現性。

2. **軟體建置與測試的位元精確產物**  
   CI/CD 中需要反覆生成的 Makefile、測試腳本、容器映像檔描述檔或編譯命令。若這些產物屬於可驗證執行的問題家族，便可避免每次都呼叫前沿模型重新生成，改以凍結模型執行已驗證方法，達到毫秒級、確定性的建置輸入。

3. **形式驗證與數學證明的機器檢查輔助**  
   定理證明器、合約驗證或密碼學協定分析中，常需要重複套用已證明的推論樣板。透過 verify-before-store 合約，先由機器檢查形式證明，再將推理方法遷移到新實例，可在開放式推理上維持 88/88 的一致性閘控接受。

4. **醫療與科學協定的參數化運算**  
   劑量計算、基因體分析流程、實驗設計參數表等，若家族內的每個實例都能被獨立驗證（例如對照臨床公式或模擬器），便可轉為已驗證工作，避免每次都以非確定性生成重新推導，降低安全關鍵領域的變異風險。

5. **供應鏈與物流的最佳化執行**  
   排程、路徑、庫存補貨等問題，一旦求解與驗證完成，後續同類訂單或需求波動可透過精確定址直接執行已驗證方法，將延遲從數秒級降到毫秒級，同時保持能源成本在數十毫瓦時等級。

### 實作前置條件

- **資料條件**  
  必須先定義清晰的問題家族與參數化方式：每個家族要有明確的輸入空間、輸出格式，以及獨立於答案鍵的驗證器。需要保留原始成品（raw artifacts）與雜湊錨定，以備審計與陰性對照。

- **運算條件**  
  需要一個凍結模型推論節點（報告中使用單張 46 GB GPU 即可承載 6,000,000-token 可移動視窗），以及獨立的驗證執行環境。已驗證儲存庫需要低延遲精確定址，而非向量式近似檢索。

- **技能條件**  
  需要領域專家設計問題家族與驗證邏輯、MLOps/後端工程師建置儲存與執行管線、資安或合規人員確保 verify-before-store 流程確實不參考答案鍵，並有資料工程師維護雜湊錨定的審計軌跡。

---

### 實作步驟建議

1. **盤點可驗證的問題家族**  
   從業務流程中找出「重複出現、可獨立驗證、參數化後仍屬同一家族」的任務，優先處理高頻、高延遲成本或高合規風險的項目。

2. **建立獨立驗證器**  
   設計一個驗證步驟，只檢查解答是否滿足領域約束或執行結果是否正確，絕不參考答案鍵。這是 verify-before-store 合約的核心。

3. **一次性求解並驗證**  
   使用模型（可搭配程式執行或形式證明工具）產生參數化方法，通過獨立驗證後，連同雜湊錨定存入 Merlin 這類確定性儲存與完整性層。

4. **部署精確定址的執行路徑**  
   在生產環境中，讓 Galahad 先以精確定址選取記憶項目（報告中僅 1.4 微秒），再由凍結模型在新參數上重新執行，確保零生成 token 且位元精確。

5. **設定陰性對照與監控**  
   定期清空記憶進行對照，確認系統確實依賴已驗證儲存庫而非模型本身的冷啟動能力；同時監控延遲、能耗與錯誤率。

6. **與前沿模型 API 串接成階層式架構**  
   將 Galahad 作為第一線快取層：命中已驗證家族時零 token 回應；未命中或超出範圍時，再 fallback 到前沿模型進行原始推理。

7. **持續擴張已驗證領土**  
   每當業務新增可驗證家族，就執行一次 solve-and-verify campaign，讓「零 token、確定性、永久可用」的覆蓋範圍只增不減。

---

### 潛在風險與注意事項

- **過度擴張適用範圍**  
  本系統只適用於「已解決且可獨立驗證」的問題；開放式創意寫作、需即時知識更新或無法形式化驗證的任務仍應使用前沿模型。錯把未驗證問題塞入記憶會導致錯誤被永久固化。

- **驗證器本身的正確性**  
  獨立驗證雖不參考答案鍵，但驗證邏輯若有漏洞，錯誤方法會被存入並無限重用。建議對驗證器本身做形式化審查、單元測試與紅隊測試。

- **近似相似度檢索的災難性失敗**  
  報告指出，在 4,500 項已驗證儲存庫上，向量式近似檢索有高達 94.3% 的錯誤率。執行層必須使用精確定址，向量資料庫只能用於非關鍵的探索或索引，不能作為最終執行依據。

- **家族邊界的對抗輸入**  
  若輸入看似屬於某家族但帶有邊界偏移或惡意參數，可能觸發錯誤記憶。需要嚴格的輸入模式匹配、前處理驗證與異常偵測。

- **記憶規模與治理**  
  雖然單張 GPU 可承載 600 萬 token 的可移動視窗，但儲存庫持續成長仍需版本控制、生命週期管理與雜湊錨定的審計軌跡，避免「記憶債務」。

- **其他引擎的靜默截斷風險**  
  報告提到 vLLM 與 SGLang 在長上下文會停止或靜默截斷。若將本系統與其他推論引擎整合，必須確認上下文視窗與輸入長度限制，避免資料遺失。

---

### 與其他技術的整合建議

- **LLM 路由閘道器**  
  在 API Gateway 層先查詢 Galahad：命中則直接回傳零 token 答案；未命中再導向 GPT-4、Claude 等前沿模型。這樣可在不改變既有使用者介面的情況下降低延遲與成本。

- **CI/CD 與可重現建置**  
  將已驗證的建置腳本或配置生成方法整合到 CI pipeline，確保每次建置使用位元精確的輸入，減少「本機可以、線上不行」的問題。

- **形式證明工具鏈**  
  與 Lean、Coq、Isabelle 或 SMT solver 整合，讓機器檢查的形式證明成為存入記憶前的必要條件，特別適合安全關鍵系統。

- **可觀測性平台**  
  將每次記憶選取、執行、能耗與雜湊值寫入結構化日誌，對接 Prometheus/Grafana 或 SIEM，滿足合規與除錯需求。

- **向量資料庫的輔助角色**  
  可用於發現「這個問題可能屬於哪個家族」的初步分類，但最終執行必須切換到精確定址。切勿讓向量相似度直接決定回傳哪個已驗證解答。

### 給不同背景讀者的閱讀建議

- **初學者**  
  請把這份報告理解為一種「先驗證、再永久執行」的思維：不是讓模型每次重新想答案，而是把已經確定正確的解法存起來，以後同類問題零成本、零變異地回覆。重點看摘要、公開測試台與適用場景即可。

- **AI 工程師**  
  請聚焦在架構不變性、精確定址與零生成 token 的執行路徑。思考如何在你現有的推論管線中插入一層「已驗證記憶」快取，並注意向量式檢索在此不適用；同時評估陰性對照與輸入驗證該如何實作。

- **研究人員**  
  請關注 verify-before-store 的方法論限制：獨立驗證如何在不參考答案鍵的前提下保證正確性？開放式推理的一致性閘控接受、推理方法遷移與機器檢查形式證明，都是值得深入檢驗的設計選擇與研究問題。

- **產品經理**  
  請把這份報告視為成本—延遲—確定性三角的重新定義：在已驗證領域內，系統以極低能耗與毫秒延遲提供 100% 準確率與位元精確輸出，但前提是問題必須可驗證且屬於已定義家族。評估時請同時看擴張潛力與風險邊界，避免將其誤銷為通用 AGI。
