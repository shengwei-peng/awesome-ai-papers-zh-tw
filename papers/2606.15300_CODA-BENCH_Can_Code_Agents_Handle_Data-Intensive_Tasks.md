# CODA-BENCH：程式碼代理（Code Agent）能否處理資料密集任務？

**原文標題：** CODA-BENCH: Can Code Agents Handle Data-Intensive Tasks?  
**作者：** Yuxin Zhang、Ju Fan、Meihao Fan 等 5 位作者  
**發布日期：** 2026-06-13  
**HF 連結：** [https://huggingface.co/papers/2606.15300](https://huggingface.co/papers/2606.15300)  
**arXiv：** [https://arxiv.org/abs/2606.15300](https://arxiv.org/abs/2606.15300)  

---

## ⚡ TL;DR

現有基準測試將程式碼與資料能力分開評估，無法反映真實開發需同時處理大量資料的情境。
作者提出CODA-BENCH，基於Kaggle建構Linux沙盒，含1009任務與平均980檔案。
實驗顯示頂尖代理僅達61.1%成功率，凸顯其在資料探索與程式碼整合上的明顯不足。

## 摘要翻譯

先進代理（Agent）日益展現作為自主工程師（Autonomous Engineer）運作的潛力，這也催生了對評估基準測試（Benchmark）日益增長的需求，以捕捉真實世界開發的複雜度。此類環境通常涉及複雜程式碼與大規模資料（即檔案系統）。然而，現有基準測試通常各自獨立地評估程式碼中心（Code-Centric）或資料中心（Data-Centric）的能力，與真實開發情境之間存在明顯落差。在本文中，我們透過引入 CODA-BENCH 來彌補此差距，這是首個在資料密集環境（Data-Intensive Environment）中聯合評估（Joint Evaluation）程式碼智能（Code Intelligence）與資料智能（Data Intelligence）的基準測試。我們基於 Kaggle 生態系（包含數百個資料集）建構了一個資料密集的 Linux 沙盒（Linux Sandbox），其中代理必須主動探索複雜的檔案層級（File Hierarchy），以識別相關資源並產生用於資料驅動（Data-Driven）分析任務（Analytical Task）的程式碼。CODA-BENCH 包含 1,009 個任務，橫跨 31 個社群（Community），每個任務環境平均包含 980 個檔案，模擬真實的資料規模與雜訊（Noise）。對先進代理的評估顯示，即使是表現最佳的系統也難以有效整合資料探索（Data Discovery）與程式碼執行（Code Execution），成功率（Success Rate）僅達 61.1%。這些結果凸顯了當前代理式（Agentic）能力在資料密集任務上的重大落差，並指出了未來研究中具前景的研究方向。

### 核心貢獻（3～5點）
- 提出 CODA-BENCH，為首個在資料密集環境中**聯合評估程式碼智能與資料智能**的基準測試，彌補現有基準測試僅單獨評估其中一項能力的缺口。
- 基於 Kaggle 生態系建構**資料密集的 Linux 沙盒**，模擬真實世界的複雜檔案層級與大規模資料環境。
- 收錄 **1,009 個任務**，橫跨 **31 個社群**，每個任務環境平均包含 **980 個檔案**，忠實重現真實開發情境中的資料規模與雜訊。
- 實證評估揭示頂尖代理在**整合資料探索與程式碼執行**上的能力落差，最佳系統成功率僅達 **61.1%**，為未來代理式研究指明改進方向。

### 適合對象
從事大型語言模型（LLM）代理研究、自動化程式碼生成、資料科學競賽平台開發，以及關注 AI 在真實世界軟體工程與資料分析場景應用的研究者、工程師與業界從業人員。特別適合需要評估代理在「程式碼」與「資料」雙重複雜度下綜合表現的團隊與個人。

## 深度分析

#### 方法論解析

CODA-BENCH 的方法論核心在於解決一個根本性的評測缺口：現有基準測試將「程式碼智能」(Code Intelligence) 與「資料智能」(Data Intelligence) 割裂評估，無法反映真實世界中兩者緊密耦合的情境。為此，作者設計了一套三階段的基準建構流程，並以 Kaggle 生態系作為基礎素材來源。

**第一階段：資料密集環境建構 (Data-Intensive Environment Construction)**

此階段的關鍵挑戰在於：隨機生成的檔案容易被代理輕易區分（缺乏語意連貫性），而人工策展數百個相關檔案則不具擴展性。作者的創新之處在於利用 Kaggle 平台中「資料集共現圖」(dataset co-occurrence graph) 的自然結構——人類資料科學家在使用資料集時會形成特定的共現模式，這些模式反映了真實的資料使用語意。透過分析 Kaggle notebook 中資料集共同出現的頻率與關聯性，作者建構出 31 個語意連貫的「社群」(communities)，每個任務環境平均包含 980 個檔案。這種設計巧妙地模擬了真實開發環境中的「資料雜訊」(noise)——代理必須在大量無關檔案中辨識出目標資料。

**第二階段：基於解答的任務建構 (Solution-Based Task Construction)**

此階段採用「提示 LLM」(Prompting LLM) 從真實的 Kaggle notebook 中萃取任務。具體流程包含：
1. **資料流分析 (Dataflow Analysis)**：解析 notebook 中資料處理的邏輯鏈
2. **解答錨點 (Solution Anchor)**：從中提取具有封閉形式答案 (closed-form answers) 的分析任務
3. **鑑別器 (Discriminators)**：確保任務具有可驗證性

這種設計的優勢在於：任務源自真實的人類工作流程，因此具有實務意義；同時封閉形式答案確保了自動評測的可行性。

**第三階段：對抗式任務演化 (Adversarial Task Evolution)**

這是方法論中最具巧思的部分。系統會根據初步測試結果對任務進行調整：
- **高解決率任務**：自動增加難度 (make it harder)
- **低解決率任務**：診斷並精煉 (diagnose and refine it)

這種對抗式演化的目的是避免基準測試出現「天花板效應」或「地板效應」，確保任務難度分佈合理。最後由人類專家進行最終檢核 (Final Check)，兼顧自動化效率與品質控制。

整體而言，CODA-BENCH 的方法論體現了「真實性」(realism)、「可擴展性」(scalability) 與「可驗證性」(verifiability) 三者的平衡，特別是將 Kaggle 生態系作為「自然標註資料來源」的設計，是對現有基準測試建構範式的顯著突破。

#### 實驗數據解讀

**核心效能數據**

實驗評估了三個最先進的程式碼代理：Codex CLI、Claude Code 與 Openhands。結果顯示即便是表現最佳的代理，在 CODA-BENCH 上僅達到 61.1% 的執行準確率 (execution accuracy)，而在更具挑戰性的 CODA-HARD 子集上更降至 49.6%。這個數字揭示了幾個重要訊息：

1. **遠未飽和的效能天花板**：相較於 SWE-Bench 等基準測試中頂尖模型已達 60-70% 以上的水準，CODA-BENCH 的 61.1% 顯示任務仍有大量改進空間。這並非單純的「模型不夠強」，而是反映了當前代理在「資料探索 + 程式碼生成」耦合任務上的結構性缺陷。

2. **CODA-HARD 的鑑別力**：49.6% 的數字接近隨機猜測水準（視任務選項數而定），說明對抗式演化階段成功創造出真正具有區辨度的困難任務，避免了基準測試「全對或全錯」的極端分佈。

3. **代理間的相對表現**：雖然摘要未提供三個代理的個別數據，但從「top-performing systems」僅達 61.1% 的描述來看，三者之間的差距可能不大，這暗示了問題的系統性而非個別模型的缺陷。

**任務規模與複雜度指標**

- **1,009 個任務**：統計上足以支撐可靠的效能比較
- **31 個社群**：提供了跨領域的泛化性評估
- **平均 980 個檔案/任務**：這個數字特別值得關注——它意味著代理必須在約 1,000 個檔案中進行有效導航，這對「資料探索」能力提出了極高要求。相較之下，傳統資料分析基準（如 DS-1000）通常僅涉及單一或少數幾個檔案。

**數據解讀的侷限性**

摘要中未揭露的關鍵資訊包括：
- 各代理的個別表現與排名
- 失敗案例的錯誤類型分佈（例如：是資料探索失敗還是程式碼生成失敗？）
- 社群間的效能差異（某些領域是否特別困難？）
- 與人類專家表現的對比基準

這些資訊的缺乏使得我們難以精確定位代理失敗的根因，也限制了對「61.1%」這個數字的深度詮釋。

#### 與現有研究的比較

**定位於基準測試譜系中**

CODA-BENCH 在基準測試譜系中佔據獨特位置，可從兩個軸向理解：

| 軸向 | 程式碼中心基準 | 資料中心基準 | CODA-BENCH |
|------|--------------|------------|------------|
| 代表作 | SWE-Bench, Terminal-Bench | DS-1000, DA-Code, DataSciBench | — |
| 資料規模 | 小（已準備好） | 小（單一檔案） | 大（平均 980 檔案） |
| 探索需求 | 低 | 無 | 高 |
| 程式碼複雜度 | 高 | 中 | 中-高 |

**相較於程式碼中心基準的改進**

SWE-Bench 系列（Jimenez et al., 2024）及其變體雖然評估了真實的軟體工程工作流程，但通常假設所有必要資料已明確提供。CODA-BENCH 的突破在於引入了「資料發現」這一維度，迫使代理必須具備自主導航能力。這更貼近 Claude Code、Cursor 等工具在真實部署中的使用情境。

**相較於資料中心基準的改進**

DS-1000（Lai et al., 2023）、DA-Code（Huang et al., 2024b）、DataSciBench（Egg et al., 2025）等基準測試雖然評估了資料處理能力，但通常以獨立 Python 腳本形式呈現，忽略了 shell 環境中的檔案系統導航。CODA-BENCH 透過 Linux 沙盒設計，彌補了這一缺口。

**方法論上的限制**

1. **領域侷限性**：完全依賴 Kaggle 生態系可能限制了任務的多樣性。Kaggle 主要聚焦於結構化資料分析，對於非結構化資料、即時資料流、API 整合等場景的覆蓋不足。

2. **任務類型偏斜**：基於「封閉形式答案」的萃取標準，可能排除了許多需要開放式分析、視覺化判斷或敘述性回答的任務。

3. **評測指標單一**：僅使用「執行準確率」可能無法捕捉部分正確 (partially correct) 的情況，也無法區分「資料探索正確但程式碼錯誤」與「程式碼正確但資料探索錯誤」這兩種本質不同的失敗模式。

4. **對抗式演化的潛在偏誤**：自動增加難度可能引入非預期的偏誤，例如偏向特定類型的困難任務，而非全面提升難度。

#### 可重現性評估

CODA-BENCH 在可重現性方面展現了高度的開放性，這是值得肯定的：

**完整開源的資源**

1. **專案網頁** (https://coda-bench.github.io/)：提供基準測試的概述與使用指南
2. **程式碼** (https://github.com/ruc-datalab/CoDA-Bench)：完整的建構與評測流程
3. **資料集** (https://huggingface.co/datasets/RUC-DataLab/CoDA-Bench)：1,009 個任務及其對應環境

**可重現性的優勢**

- **資料公開**：將 1,009 個任務及其環境配置公開，使得其他研究者可以直接重現實驗或進行新代理的評測
- **基於既有平台**：利用 Kaggle 這個穩定運作的公開平台，降低了環境依賴性
- **Linux 沙盒標準化**：使用標準的 Linux 環境而非客製化系統，提升了跨平台的可執行性

**潛在的可重現性挑戰**

1. **Kaggle 資料集的動態性**：Kaggle 上的資料集可能隨時間變化（被刪除、更新或移動），這可能導致長期可重現性問題
2. **環境規模**：平均 980 個檔案的環境對於資源受限的研究者可能造成儲存與計算負擔
3. **對抗式演化的隨機性**：若對抗式演化過程涉及隨機性，則不同時間點重建的基準可能存在差異
4. **評測代理的版本依賴**：Codex CLI、Claude Code 等工具的版本更新可能導致結果不可直接比較

**建議的改進方向**

若能提供：
- 環境的 Docker 映像檔或完整快照
- 任務的固定版本控制（類似於軟體中的 semantic versioning）
- 評測結果的標準化記錄格式

將進一步提升基準的長期可重現性與跨實驗室的比較便利性。

#### 未來研究方向

CODA-BENCH 的發表開啟了多個值得探索的研究方向：

**1. 代理架構創新**

當前代理在「資料探索 + 程式碼生成」耦合任務上的低成功率，暗示了現有架構可能存在根本性限制。未來研究可探索：
- **階層式規劃 (Hierarchical Planning)**：先進行高層次的資料探索規劃，再進行低層次的程式碼生成
- **記憶增強機制 (Memory-Augmented Mechanisms)**：讓代理能記住已探索的檔案結構，避免重複搜尋
- **工具專門化 (Tool Specialization)**：為資料探索設計專門的工具（如檔案內容預覽、結構摘要生成器）

**2. 評測方法的擴展**

- **多模態任務**：將基準擴展至包含圖像、音訊、影片等非結構化資料的場景
- **時序資料分析**：納入需要處理時間序列、串流資料的任務
- **錯誤分析框架**：開發能區分「資料探索錯誤」與「程式碼生成錯誤」的診斷工具

**3. 訓練資料與方法**

- **合成資料生成**：基於 CODA-BENCH 的環境結構，生成大量訓練資料以提升代理能力
- **課程學習 (Curriculum Learning)**：從簡單的單一檔案任務逐步過渡到複雜的多檔案探索任務
- **強化學習獎勵設計**：設計能同時獎勵「資料探索效率」與「程式碼正確性」的獎勵函數

**4. 跨領域泛化**

- **企業級資料環境**：將評測擴展至模擬企業內部資料倉儲的情境
- **領域特定基準**：在 CODA-BENCH 框架基礎上，建立醫療、金融、法律等垂直領域的專用基準
- **多代理協作**：探索多個專門化代理（如「資料探索代理」+「程式碼生成代理」）協作解決任務的可能性

**5. 人機協作模式**

既然完全自主的代理表現仍有大幅改進空間，未來研究可探索：
- **互動式澄清 (Interactive Clarification)**：代理在資料探索過程中向使用者詢問以縮小搜尋空間
- **漸進式自動化**：根據任務難度動態調整自動化程度，困難任務保留人類介入
- **可解釋性增強**：讓代理能解釋其資料探索決策，增強人類對代理的信任

**6. 理論基礎建立**

- **資訊理論分析**：從資訊理論角度量化「資料探索」與「程式碼生成」之間的資訊流轉移
- **計算複雜度分析**：分析資料密集任務的計算複雜度特性
- **認知模型對比**：將代理的行為模式與人類資料科學家的認知過程進行對比分析

這些方向不僅能推動 CODA-BENCH 本身的演進，更能促進「代理式 AI 在資料密集場景中」這一更廣泛研究領域的發展，最終實現真正能在真實世界中自主運作的「自主工程師」(autonomous engineer) 願景。

## 論文問答

**Q1：CODA-BENCH 想要解決的核心問題是什麼？為什麼現有的基準測試無法滿足這個需求？**
A：CODA-BENCH 旨在解決現有基準測試將「程式碼智能」與「資料智能」分開評估的問題，因為真實世界的開發場景中，代理必須同時具備這兩種能力才能完成任務。現有的程式碼中心基準測試（如 SWE-Bench、Terminal-Bench）雖然評估了程式碼正確性與軟體工程工作流程，但通常假設所有所需資料都已準備好且明確提供，忽略了代理需要在龐大檔案系統中主動探索資料的挑戰。另一方面，資料中心基準測試（如 DS-1000、DA-Code、DataSciBench）雖然測試了資料處理能力，但依賴獨立的 Python 腳本，未評估代理在 shell 環境中探索與存取大規模資料的能力。這種孤立的評估方式造成了基準測試表現與真實世界效用之間的明顯落差。

**Q2：為什麼「資料探索」能力對程式碼代理如此重要？**
A：在真實世界的部署中，自主代理的價值在於與檔案系統中的大規模資料互動，而不僅僅是解決孤立的演算法問題。一個理想的代理應該能夠瀏覽目錄層級、從數百個候選檔案中識別出相關檔案，並執行適當的操作，而無需使用者明確指定目標。這種能力需要雙重智能：能夠生成語法正確且邏輯合理程式的「程式碼智能」，以及能在複雜資料環境中定位並利用正確資訊來源的「資料智能」。如果代理無法瀏覽複雜的資料環境，即使擁有先進的程式碼能力也無法發揮效用，這凸顯了聯合評估兩種智能的迫切需求。

**Q3：為什麼選擇 Kaggle 生態系統作為建構基準測試的基礎？**
A：選擇 Kaggle 生態系統是因為資料科學社群長期累積了大量相互連結的資料集與人類撰寫的解答程式碼，提供了一個理想的設定來建構真實且可擴展的基準測試。Kaggle 平台包含了豐富的資料集與競賽社群，這些資料集之間存在自然的共現模式（co-occurrence patterns），反映了真實的人類工作流程。透過分析這些共現模式，研究者可以建立資料網路並建構語意連貫的環境，這比隨機生成檔案（容易被輕易區分）更具真實性，同時也比手動策展數百個相關檔案更具可擴展性。

**Q4：CODA-BENCH 的建構方法包含哪些主要步驟？**
A：CODA-BENCH 的建構方法包含三個主要步驟：首先是「資料密集環境建構」（Data-Intensive Environment Construction），透過分析人類工作流程中的自然共現模式，從 Kaggle 策展大規模資料來源並建立資料網路；接著是「基於解答的任務建構」（Solution-Based Task Construction），透過提示大型語言模型並進行資料流分析（Dataflow Analysis），從真實的 Kaggle 筆記本中提取具有封閉形式答案的任務；最後是「對抗式任務演化」（Adversarial Task Evolution），使用生成器與判別器來調整任務難度——高解決率的任務會被改得更難，低解決率的任務則會被診斷並精煉，最終再經過人類專家進行最終檢查。

**Q5：CODA-BENCH 的核心創新是什麼？它與現有基準測試的本質差異為何？**
A：CODA-BENCH 的核心創新在於首次實現了「程式碼智能」與「資料智能」的聯合評估，在一個模擬真實世界複雜度的資料密集環境中同時測試這兩種能力。其本質差異在於：現有基準測試通常假設資料已「擺在銀盤上」（on a silver platter）提供給代理，而 CODA-BENCH 則要求代理必須主動探索複雜的檔案層級、識別相關資源，然後生成程式碼來完成資料驅動的分析任務。這種設計更貼近真實的開發場景，因為在現實中資料很少會被明確標示或預先整理好。

**Q6：在設計 CODA-BENCH 時，研究者做了哪些關鍵的設計選擇？**
A：關鍵的設計選擇包括：採用「資料共現圖」（dataset co-occurrence graphs）來建構語意連貫的環境，確保任務中的檔案之間存在自然的關聯性而非隨機組合；採用「對抗式任務演化」機制來平衡任務難度，避免任務過於簡單或過於困難而失去區辨力；以及選擇 Linux 沙盒作為執行環境，讓代理能夠進行真實的 shell 操作與檔案系統瀏覽。此外，每個任務環境平均包含 980 個檔案，這個規模是經過設計的，目的是模擬真實的資料規模與雜訊，讓評估結果更具代表性。

**Q7：CODA-BENCH 的規模與組成為何？**
A：CODA-BENCH 包含 1,009 個任務，橫跨 31 個資料社群（communities），每個任務環境平均包含 980 個檔案。這樣的規模設計是為了模擬真實的資料規模與雜訊，讓代理面對的挑戰與實際工作場景相符。此外，研究者還建立了一個更具挑戰性的子集稱為 CODA-HARD，用於更細緻地評估頂尖代理在困難任務上的表現。

**Q8：頂尖的程式碼代理在 CODA-BENCH 上的表現如何？這揭示了什麼問題？**
A：評估了 Codex CLI、Claude Code 和 Openhands 等先進代理後發現，即使是表現最好的模型，在 CODA-BENCH 上也只能達到 61.1% 的執行準確率，在更具挑戰性的 CODA-HARD 子集上更僅有 49.6%。這些結果揭示了當前代理在整合資料探索與程式碼執行方面存在明顯的不足，無法有效處理資料密集任務。這顯示出目前的代理式系統距離自主完成真實世界的資料密集任務還有相當大的改進空間。

**Q9：CODA-BENCH 的評估結果對「代理式 AI」研究領域有什麼啟示？**
A：評估結果顯示，當前的程式碼代理雖然在隔離的程式碼生成或資料處理任務上表現不錯，但當兩種能力需要整合時，表現就會大幅下降。這表明「代理式 AI」研究需要從單一能力的優化轉向多能力整合的設計，特別是如何讓代理能夠在複雜環境中自主探索、推理並執行。此外，結果也凸顯了現有評估方法的侷限性——僅在受控環境中測試單一能力無法反映真實世界的需求，未來的基準測試應該更全面地涵蓋真實工作流程中的各種挑戰。

**Q10：CODA-BENCH 能應用於哪些實際場景？**
A：CODA-BENCH 的設計理念可應用於多種需要處理大規模異質資料的實際場景，包括企業資料分析、科學研究、財務報表分析、醫療資料處理等。在這些場景中，專業人員通常需要在包含數百個檔案的複雜目錄結構中尋找相關資料，並編寫程式進行分析。CODA-BENCH 所模擬的環境與這些真實工作流程高度吻合，因此可以用來評估和改進實際部署中的 AI 助理。此外，它也能用於訓練更強健的資料處理代理，使其能在企業級的資料環境中可靠運作。

**Q11：在產品開發中，CODA-BENCH 的發現會如何影響 AI 助理的設計？**
A：CODA-BENCH 的發現提醒產品開發者，僅僅優化程式碼生成能力是不夠的，還必須重視代理的資料探索與導航能力。在設計 AI 助理產品時，應該考慮整合更強的檔案系統理解能力、語意搜尋功能，以及在複雜目錄結構中推理的能力。此外，產品設計也應該考慮到「人機協作」的模式——當代理無法確定哪個檔案是相關的時，應該能夠有效地與使用者互動以獲取指引，而不是盲目嘗試所有可能的檔案。這種設計思維的轉變將使 AI 助理在真實工作環境中更加實用。

**Q12：CODA-BENCH 對「自主工程師」這個概念的發展有何影響？**
A：CODA-BENCH 的結果對「自主工程師」的概念提出了重要的警示：目前的 AI 系統距離真正自主完成資料密集的開發任務還有明顯的距離。這促使研究者重新思考自主工程師的能力邊界，並強調未來的研究應該更專注於整合多種智能（包括程式碼智能、資料智能、推理能力等）而非單一能力的極致優化。同時，這也推動了「代理式 AI」領域向更全面、更真實的評估標準發展，有助於引導研究方向朝著真正實用的自主系統邁進。

**Q13：CODA-BENCH 存在哪些已知的限制？**
A：雖然 CODA-BENCH 在模擬真實資料環境方面取得了重要進展，但它仍存在一些限制。首先，它主要基於 Kaggle 生態系統建構，這意味著任務類型和資料特性可能無法完全代表所有領域的資料密集任務，例如企業內部系統、學術研究資料等可能有不同的特性。其次，雖然平均 980 個檔案已經是相當大的規模，但與某些真實企業環境中數十萬甚至數百萬檔案相比仍有差距。此外，封閉形式的答案設計雖然便於自動評估，但可能無法完全捕捉開放式分析任務的複雜性。

**Q14：在評估過程中，代理常見的失敗模式有哪些？**
A：根據 CODA-BENCH 的設計理念與評估結果，可以推測出幾種常見的失敗模式：代理可能無法有效瀏覽複雜的目錄結構，浪費大量時間在不相關的檔案上；可能選擇了錯誤的資料來源，導致後續分析產生偏差；可能在面對大量雜訊檔案時無法識別出真正相關的資料；以及可能在整合多個資料來源時出現邏輯錯誤。這些失敗模式凸顯了「資料探索」與「程式碼執行」之間的整合挑戰——即使兩種能力單獨表現良好，組合起來仍可能出現問題。

**Q15：基於 CODA-BENCH 的發現，未來有哪些值得探索的研究方向？**
A：基於 CODA-BENCH 的發現，未來有幾個值得探索的研究方向：首先是如何改進代理的「資料探索」能力，包括更智慧的檔案系統導航、語意理解與相關性判斷；其次是研究如何讓代理更好地整合「程式碼智能」與「資料智能」，例如透過規劃機制先確定資料來源再生成程式碼；第三是探索「人機協作」模式，讓代理能在不確定時有效地尋求使用者協助；第四是將 CODA-BENCH 的理念擴展到其他領域，如企業資料、科學研究資料等；最後是研究如何讓代理在更大規模、更嘈雜的資料環境中保持穩定表現，這對於實際部署至關重要。

## 實務應用指南

### 適用場景

**1. 企業內部資料分析助理的選型與評估**
企業資料團隊在導入 AI 程式碼代理（如 Claude Code、Cursor、Codex CLI）時，可使用 CODA-BENCH 作為標準化評測工具，判斷候選代理是否能從混雜的共享磁碟、部門資料夾中找到正確檔案並完成分析任務，避免在實際部署後才發現代理無法處理「資料探索」環節。

**2. 資料科學競賽與教育訓練平台**
Kaggle 風格的教學平台可將 CODA-BENCH 的任務設計理念移植到課程中，讓學員在模擬的「資料密集沙盒」中練習「先探索、再編碼」的真實工作流程，培養同時具備程式碼智能與資料智能的資料科學家。

**3. 金融、零售與醫療領域的自動化報表生成**
這些產業的報表任務通常需要在數百個檔案（交易紀錄、客戶資料、影像報告）中找到正確來源，再撰寫 ETL 與分析程式。CODA-BENCH 的環境建構方法（基於資料共現圖）可作為建置領域專屬基準的藍圖，用以評估代理在受監管環境下的可靠性。

**4. 程式碼代理研發團隊的回歸測試套件**
從事 AI 代理研發的團隊可將 CODA-BENCH 整合進 CI/CD 流程，每次模型或代理框架更新時自動跑過 1,009 個任務，量化「資料探索能力」是否隨版本提升或退化，避免僅以 SWE-Bench 等程式碼中心基準得出過度樂觀的結論。

**5. 企業 AI 治理與合規稽核**
在金融、醫療等高度監管的場域，稽核人員可使用 CODA-BENCH 風格的任務驗證代理是否會誤用敏感檔案、是否能正確定位授權範圍內的資料，作為「AI 自主操作可信度」的客觀證據。

### 實作前置條件

**資料面**
- 需具備 Kaggle 帳號與 API 權限，以取得原始競賽資料集與 Notebook（中繼資料可從 Hugging Face `RUC-DataLab/CoDA-Bench` 直接下載）。
- 領域應用時，需先盤點組織內部檔案系統，建立類似「資料共現圖」的索引，記錄哪些檔案常在同一工作流程中被共同使用。
- 任務題目需具備「封閉形式答案」（例如具體數值、表格、特定欄位），以便自動驗證；開放式問答不適用本框架。

**運算面**
- 執行基準測試需為每個任務啟動獨立的 Linux 沙盒（Docker 容器），平均每任務 980 個檔案，建議至少 16 GB RAM 與 50 GB 磁碟空間的執行節點。
- 評測 1,009 個任務若採平行執行（建議 32–64 容器），單次完整跑完需數小時至一天，需準備容器編排環境（Kubernetes 或 Docker Compose）。
- 呼叫受測代理（Codex CLI、Claude Code、OpenHands）需具備對應 API 金鑰與用量額度。

**技能面**
- 熟悉 Python 資料處理生態系（Pandas、JSON、PDF 解析）以理解任務內容。
- 具備 LLM 代理框架的部署經驗（工具呼叫、shell 執行、檔案系統操作）。
- 了解基準測試設計原則（任務難度分層、鑑別度分析、對抗式演化的概念）。

### 實作步驟建議

**步驟一：釐清評測目標**
先決定是要「選型採購」、「研發迭代」還是「合規驗證」，不同目標會影響後續要採用 CODA-BENCH 全集、CoDA-HARD 子集，還是自建領域基準。

**步驟二：取得基準資源**
從 Hugging Face 下載 `RUC-DataLab/CoDA-Bench` 資料集，從 GitHub `ruc-datalab/CoDA-Bench` 取得沙盒建構腳本與評測管線，閱讀論文 Figure 2 理解三階段建構流程（環境建構 → 任務抽取 → 對抗式演化）。

**步驟三：建置執行環境**
依官方文件部署 Linux 沙盒，確認每個任務容器能掛載對應的 980 個檔案、設定好檔案權限與隔離機制，並準備評測結果的儲存結構（任務 ID、代理輸出、執行日誌、評分）。

**步驟四：串接受測代理**
將候選代理（Claude Code、Codex CLI、OpenHands 或自研系統）以標準介面接入沙盒，設定最大步數、token 上限與工具白名單，避免代理跳過資料探索直接編碼造成評測失真。

**步驟五：執行基準並分析**
跑完整 1,009 個任務，記錄執行成功率、錯誤類型（找不到檔案、程式碼錯誤、邏輯錯誤），並依 31 個社群拆分表現，找出代理在特定資料類型上的弱點。

**步驟六：建立領域專屬基準（進階）**
若通用基準不足以反映業務需求，可參考論文的「資料共現圖」方法，從組織內部真實工作流程中抽取任務，採用相同的「對抗式演化」流程提升題目鑑別度，並由領域專家做最終審核。

### 潛在風險與注意事項

**風險一：基準過擬合至 Kaggle 風格任務**
CODA-BENCH 的任務源自 Kaggle Notebook，偏向競賽式分析。企業實際任務可能涉及更多內部系統、API 與權限控管，直接套用可能高估代理能力。**緩解方式**：以 CODA-BENCH 作為「下限參考」，再補上領域專屬任務。

**風險二：沙盒安全性**
代理在沙盒中可自由執行 shell 指令並讀寫檔案，若未嚴格隔離，可能造成資料外洩或系統損壞。**緩解方式**：使用 gVisor 或 Firecracker 等強隔離容器，禁用網路外連，並設定唯讀掛載點保護原始資料。

**風險三：評測成本失控**
1,009 個任務 × 多個代理 × 多次重試，token 與運算成本可能迅速攀升。**緩解方式**：先以 100 個任務的子集做煙霧測試，確認管線穩定後再跑全集；對表現明顯差的代理提早中止。

**風險四：答案驗證的脆弱性**
封閉形式答案對格式極為敏感（例如「1,234.5」與「1234.5」視為不同），可能誤判正確解答。**緩解方式**：實作容錯比對（數值容差、字串正規化），並保留人工抽樣覆核機制。

**風險五：對抗式演化可能產生偏頗任務**
論文的「高通過率則加難」機制可能使部分任務過度刁鑽，無法反映真實困難度。**緩解方式**：定期由領域專家審核新生成的任務，剔除語意不清或答案爭議的題目。

### 與其他技術的整合建議

**與 SWE-Bench、Terminal-Bench 的互補整合**
SWE-Bench 評估「程式碼修復」、Terminal-Bench 評估「終端機操作」，CODA-BENCH 補上「資料探索」一塊。三者可組成「代理能力三維雷達圖」，全面檢視代理在程式碼、系統操作、資料處理上的強弱分布。實作上可在同一評測平台共用沙盒基礎設施與評分框架。

**與 RAG（檢索增強生成）系統的整合**
CODA-BENCH 的「資料共現圖」概念可作為企業 RAG 系統的索引建構參考——先分析人類工作流程中的檔案共現關係，再據此建立語意索引，使代理在面對數百檔案時能快速縮小搜尋範圍。

**與 MLOps 平台的整合**
將 CODA-BENCH 評測管線接入 MLflow 或 Weights & Biases，每次代理版本更新自動觸發評測並記錄指標，建立「資料密集任務表現」的長期追蹤儀表板。

**與權限管理系統的整合**
在企業部署時，可將沙盒與 IAM 系統對接，讓代理在評測中學習「哪些目錄可存取、哪些需申請」，模擬真實環境的權限邊界，這也是現有基準較少涵蓋的面向。

**與領域專屬 LLM 的微調流程整合**
若組織正在微調領域 LLM，可將 CODA-BENCH 任務轉為微調資料（搭配代理執行軌跡作為思維鏈），訓練模型在「探索—編碼」循環中的策略選擇能力。

### 給不同背景讀者的閱讀建議

**給初學者：** 建議先閱讀 Figure 1 與摘要，掌握「程式碼智能」與「資料智能」是兩種不同能力，再瀏覽官方專案頁（coda-bench.github.io）看看實際任務範例，不必深入數學細節，重點理解「為什麼現有基準不夠用」這個核心問題。

**給 AI 工程師：** 應聚焦於論文 Section 2 的相關工作分類，以及 Figure 2 的三階段建構流程（環境建構、任務抽取、對抗式演化），這些方法可直接借鏡用於自建領域基準；同時關注評測結果中各代理的失敗模式，作為自家代理架構改進的參考。

**給研究者：** 建議深入閱讀「對抗式任務演化」與「資料共現圖」的設計細節，這是本論文最具方法論貢獻的部分；可進一步探索如何將此框架擴展至多模態資料（影像、PDF）、多代理協作場景，或結合強化學習進行代理訓練。

**給產品經理：** 重點理解「61.1% 成功率」這個數字背後的商業意涵——即使是頂尖代理，在資料密集任務上仍有近四成失敗率，這代表現階段不應將資料分析任務完全委派給 AI 代理，而應設計「人機協作」流程，讓代理負責探索與初稿，人類負責最終決策與例外處理。
