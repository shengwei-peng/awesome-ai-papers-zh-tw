# 從證據到動作：工具使用代理如何失敗

## ⚡ TL;DR

工具代理可能完成正確動作，但未在執行前建立所需證據。

發現靜態評估強但互動執行弱，失敗多源於調查不完整或過早動作。

## 摘要翻譯

工具使用代理會對外部狀態產生重大改變，然而，正確的結果並不保證其動作事先已由證據所支持。我們研究此證據到動作鏈在何處斷裂——從代理決定是否採取動作，到其執行單一動作及多動作相依工作流程的過程中。在十種模型框架配置中，穩健的靜態動作評估可與顯著較弱的互動式執行並存。失敗通常在執行前就已開始：代理便在調查不完整時停止，或在所需證據尚未建立前採取動作。一旦取得所需證據，單一動作執行通常可靠，而多動作工作流程則進一步暴露出未解決的先決條件與不完整的執行。為進行此分析，我們引入 SafeActBench，包含六個操作領域與五種協議中的 656 個案例，從靜態動作判斷與已調查的非動作進展到單一及多動作工作流程。一個溯源綁定的證據分類帳（Evidence Ledger）與確定性軌跡評估器，追蹤哪些資訊已建立、動作何時發生，以及下游依賴是否已滿足。這些結果顯示，失敗不僅源於資訊缺失，亦源於代理在決策與執行時對已建立證據的運用方式。

### 核心貢獻（3～5點）
- 揭示「證據到動作鏈」中的斷裂點：代理失敗不僅來自資訊缺失，更來自對已建立證據的不當運用，涵蓋從「是否行動」的決策到「單一動作執行」與「多動作相依工作流程」的三階段遞進分析。
- 提出 SafeActBench 基準測試：涵蓋六個操作領域與五種協議共 656 個案例，系統性地從靜態動作判斷、已調查的非動作，進展至單一及多動作工作流程。
- 設計溯源綁定的證據分類帳（Evidence Ledger）與確定性軌跡評估器：精確追蹤資訊建立時序、動作發生時間點及下游依賴滿足狀態，提供可重現的評估基礎。
- 揭露關鍵反直覺發現：在十種模型框架配置中，穩健的靜態動作評估能力可與顯著較弱的互動式執行能力並存，凸顯評估代理可靠性時動態測試的必要性。

### 適合對象
從事大型語言模型代理（LLM agents）研究與開發的學者與工程師，特別關注工具呼叫可靠性、代理軌跡評估方法論、自動化工作流程安全性驗證，以及 AI 系統在有狀態環境中執行多步驟任務時的可靠性挑戰之研究者；亦適合負責設計代理評測框架或關注 AI 代理部署風險的產業實務人員閱讀。

## 深度分析

#### 方法論解析

本文提出了一個名為 **SafeActBench** 的基準測試套件，旨在系統性地剖析工具使用代理（tool-using agents）在「證據到動作鏈」（evidence-to-action chain）上的失效模式。其方法論核心在於將代理行為的可觀察軌跡（observable trajectory）與任務定義的證據需求進行形式化對齊，而非僅評估最終結果的正確性。

**1. 問題形式化：證據到動作鏈**

作者將「後果性動作」（consequential actions）定義為會改變應用程式狀態或產生外部效應的工具呼叫。對於此類動作，正確性不僅取決於「做了什麼」，更取決於「在執行前已建立哪些任務相關事實」。論文以退款情境為例：代理可能使用正確工具、瞄準正確收費、指定正確金額並收到成功回應，卻未在執行前透過互動建立必要的證據——例如未驗證目標收費是否確實為重複收費（duplicate charge）或符合退款資格（refund eligibility）。這種「端點正確但軌跡無支撐」的情境，正是本文欲捕捉的核心失效模式。

**2. 評估協議的五層級設計**

SafeActBench 採用五種協議（protocols）來區分不同複雜度的代理行為：

- **靜態動作判斷（static action judgment）**：在不互動的情況下評估代理是否認為該動作應被執行。
- **已調查的非動作（investigated non-action）**：評估代理在證據不支持時是否能主動調查並正確選擇不執行。
- **單一動作執行（single-action execution）**：評估代理在已建立證據後是否能正確執行單一動作。
- **線性多動作工作流程（linear multi-action workflows）**：評估多個動作依序執行的正確性。
- **依賴約束的多動作工作流程（dependency-constrained multi-action workflows）**：評估下游動作是否正確等待並使用上游動作的實際回傳結果。

此設計的關鍵洞見在於：隨著動作結構複雜度提升，失效模式會從「調查不足」轉變為「依賴未滿足」，因此需要分層級診斷。

**3. 溯源綁定的證據分類帳（Provenance-bound Evidence Ledger）**

這是本文方法論的核心創新。證據分類帳追蹤每項證據的建立時間、來源工具呼叫、以及其綁定的實體與狀態。與傳統僅記錄「代理呼叫了哪些工具」不同，證據分類帳要求證據必須：
- 透過當前互動取得（而非假設已知）；
- 精確綁定到動作的目標實體與參數；
- 保留來源以便驗證其真實性。

此設計使得「代理是否在執行退款前驗證了正確的收費 C2」成為可機械化檢查的命題，而非依賴 LLM 裁判的主觀判斷。

**4. 確定性軌跡評估器（Deterministic Trajectory Evaluator）**

評估器採用重播（replay）方式驗證軌跡，檢查項目包括：
- 必要調查是否完成；
- 工具、目標、參數是否正確；
- 執行回執（receipt）是否被接收；
- 動作依賴（action dependencies）是否被滿足；
- 結果狀態變更是否符合預期。

值得注意的是，評估器**不檢查隱藏推理過程**，也**不依賴 LLM 裁判**，這大幅提升了評估的可重現性與客觀性。

**5. 受控證據介入實驗（Controlled Evidence Interventions）**

為了區分「代理無法取得資訊」與「代理取得資訊卻未使用」，作者設計了受控介入：在不改變任務可解性的前提下，調整環境中可取得的證據，觀察代理行為是否隨證據可得性而改變。此設計有助於分離資訊缺失與證據使用不當兩類失效。

#### 實驗數據解讀

**1. 基準規模與覆蓋**

SafeActBench 包含 656 個標準化案例（canonical cases），橫跨六個操作領域（operational domains），涵蓋退款、通知、記錄更新等典型後果性動作情境。此規模在互動式代理評估中屬於中等偏上，但案例設計強調「證據鏈的可追溯性」而非單純的數量擴張。

**2. 跨模型與框架配置的發現**

論文測試了十種模型框架配置（model-harness configurations），涵蓋不同 LLM 與代理框架的組合。最關鍵的實驗發現是：

> **強健的靜態動作評估（strong static action assessment）可與明顯較弱的互動式執行（interactive execution）共存。**

這意味著：在不實際執行的情況下，代理可能「知道」該動作是否應被執行；但在需要實際調查與執行的互動環境中，同樣的代理可能會在證據未建立時就貿然行動，或在證據不支持時未能正確選擇不行動。

**3. 失效模式的階段性分布**

實驗揭示失效並非均勻分布，而是呈現階段性特徵：

- **執行前失效（pre-execution failures）**：代理在調查不完整時停止，或在必要證據尚未建立時就採取行動。這是最常見的失效類型。
- **單一動作執行階段**：一旦必要證據已建立，單一動作的執行通常可靠，工具選擇、目標綁定與參數指定的錯誤率較低。
- **多動作工作流程階段**：此階段額外暴露未解決的先決條件（unresolved prerequisites）與執行不完整（incomplete execution）問題，特別是當下游動作需要等待上游動作的實際回傳結果時。

**4. 受控介入的意涵**

受控證據介入實驗顯示：代理有時會取得相關資訊，卻仍在決定性證據（decisive support）缺席時行動。這表明失效不僅源於「資訊缺失」，更源於「代理如何使用已建立的證據」——這是一個比單純資訊檢索更深層的認知問題。

**5. 量化指標的侷限**

雖然論文強調跨配置的差異，但具體的數字（如各協議的通過率、各失效類型的比例）需參照完整論文表格。從摘要與引言可推斷，靜態評估與互動執行之間存在顯著的性能落差，但此落差的具體幅度與是否隨模型規模縮小，仍有待完整數據驗證。

#### 與現有研究的比較

**1. 與互動式代理評估基準的關係**

SafeActBench 與 AgentBench（Liu et al., 2024）、WorkArena（Drouin et al., 2024）、OSWorld（Xie et al., 2024）、WorkBench（Styles et al., 2024）、AppWorld（Trivedi et al., 2024）等基準共享「從靜態函式呼叫準確率（function-call accuracy）轉向互動式執行評估」的趨勢。然而，這些基準主要評估「任務是否完成」或「最終狀態是否正確」，而 SafeActBench 獨特地將焦點放在「完成路徑是否由證據支撐」。

**2. 與可靠性研究的互補**

近期研究關注代理的特定可靠性挑戰，例如：
- 求助行為與釐清（help-seeking and clarification，Trinh et al., 2026; Gulati et al., 2026）；
- 對環境觀察的信任（trust in environmental observations，Sheng et al., 2026）；
- 動作克制與棄權（action restraint or abstention，Gloaguen et al., 2026; Luo et al., 2026; Liu et al., 2026）。

SafeActBench 與這些研究互補：它不直接評估「代理是否會求助」或「代理是否會棄權」，而是評估「代理在選擇行動或不行動時，是否有證據支撐其選擇」。這是一個更底層的評估維度。

**3. 相較於 LLM 裁判方法的優勢**

許多代理評估依賴 LLM 裁判來判斷軌跡品質，這引入了主觀性與不穩定性。SafeActBench 的確定性軌跡評估器（deterministic trajectory evaluator）透過重播與規則檢查繞過此問題，提供可重現的評估結果。這是其相較於 AppWorld 等基準的方法論優勢。

**4. 侷限與未覆蓋面向**

- **領域覆蓋**：六個操作領域雖具代表性，但相較於 OSWorld 的桌面操作或 AppWorld 的應用程式生態，覆蓋面仍有限。
- **規劃與推理評估**：論文明確表示不檢查隱藏推理，這雖然提升了客觀性，但也意味著無法診斷「代理推理正確但執行錯誤」與「代理推理錯誤但僥倖執行正確」的區別。
- **動態環境**：基準採用確定性重播，這雖有利於可重現性，但無法捕捉真實環境中的非確定性回應或並發問題。

#### 可重現性評估

**1. 程式碼與資料可用性**

從論文提供的資訊判斷，SafeActBench 作為一個基準測試套件，其設計強調「確定性軌跡評估器」與「證據分類帳」，這兩者本質上都是可形式化、可重現的元件。然而，論文中並未明確聲明程式碼與資料的開源狀況。基於以下考量，開源可能性較高但需驗證：

- 確定性評估器的設計邏輯清晰，適合以開源形式發布；
- 656 個標準化案例的建構需要領域專家投入，開源將有助於後續擴充；
- 作者隸屬於新加坡國立大學與 Amazon，雙方均有開源代理評估工具的先例（如 AppWorld 來自 Amazon）。

**2. 模型權重與框架配置**

論文測試十種模型框架配置，但未列出具體模型清單。為完整重現實驗，需取得對應的模型權重（若為開源模型如 Llama、Qwen）或 API 存取權限（若為閉源模型如 GPT、Claude）。框架配置（harness configurations）的細節——包括工具呼叫格式、提示模板、錯誤恢復機制——對結果有顯著影響，論文中應有詳細說明，但需查閱附錄確認。

**3. 評估協議的標準化程度**

五種協議的設計具有清晰的層級結構，每個協議的通過條件應可機械化檢查。這有利於跨實驗室的結果比較。然而，「證據分類帳」的具體資料結構、「溯源綁定」的實作細節，仍需透過附錄或補充材料確認。

**4. 重現風險**

主要重現風險在於：
- 環境模擬的保真度：若基準依賴特定版本的模擬環境，環境更新可能導致結果漂移；
- 評估器的邊界案例處理：確定性規則可能無法覆蓋所有軌跡變體；
- 模型版本的時間敏感性：閉源模型的 API 行為可能隨版本更新而改變。

#### 未來研究方向

**1. 證據使用機制的深入探究**

本文揭示「代理取得資訊卻未使用」的現象，但未深入剖析其認知機制。未來研究可探討：
- 代理在何種提示結構下能更好地整合已取得證據；
- 是否可透過思維鏈（chain-of-thought）或反思機制（reflection mechanisms）改善證據到動作的轉譯；
- 證據的「決定性」如何被代理識別——即代理是否能區分「相關資訊」與「決定性證據」。

**2. 動態與非確定性環境的擴展**

當前基準採用確定性重播，未來可擴展至：
- 包含工具回應延遲、部分失敗、並發競爭的真實環境；
- 環境狀態隨時間漂移的情境，迫使代理持續重新驗證證據；
- 多代理協作下的證據共享與責任歸屬。

**3. 證據分類帳的標準化與互通**

證據分類帳的概念可推廣為代理互動的通用記錄標準。未來可探索：
- 與 OpenTelemetry 等可觀察性框架的整合；
- 跨基準的證據需求形式化語言；
- 證據分類帳在除錯、安全審計、合規檢查中的應用。

**4. 從評估到訓練的閉環**

SafeActBench 目前僅用於評估，未來可將其轉化為訓練信號：
- 以證據鏈完整性作為強化學習獎勵；
- 透過軌跡對比訓練代理學習「何時不行動」；
- 建構證據感知的預訓練目標，使代理在內化階段即建立證據意識。

**5. 與人類決策的對齊研究**

代理的證據到動作鏈與人類專家的臨床決策、合規審查等流程有結構相似性。未來可借鑑：
- 醫療 AI 中的「臨床決策支援」對證據鏈的要求；
- 法律推理中的「證據規則」對動作觸發條件的約束；
- 航空與核能產業的「程序化檢查清單」對代理動作序列的啟發。

**6. 安全與政策合規的整合**

後果性動作常涉及政策約束（policy constraints）。未來可將 SafeActBench 擴展為：
- 內建政策規則庫的合規檢查基準；
- 評估代理在政策衝突時的證據權衡能力；
- 結合紅隊演練（red-teaming）測試代理在對抗性證據下的行為。

**7. 跨語言與跨文化的證據需求**

當前案例可能以英語與西方商業情境為主。未來可探索：
- 不同法律體系對「退款資格」等概念的差異如何影響證據需求；
- 多語言環境下證據綁定的精確性；
- 跨文化情境中「已調查的非動作」是否被正確識別為合規行為。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文聚焦於工具使用代理（tool-using agents）在執行動作時，**端點正確性（endpoint correctness）並不等於證據支持的動作**所衍生的問題。代理可能使用正確的工具、針對正確的目標、傳入正確的參數並收到成功回應，卻未在執行前透過互動建立必要的證據。這種「證據到動作鏈（evidence-to-action chain）」的斷裂，使得後續依賴於先前工具結果的動作可能建立在未被驗證的前提之上，造成難以在端點層級被察覺的系統性失敗。

**Q2：為什麼現有的代理評估方法無法捕捉這個問題？**
A：現有方法主要分為兩類，但都各有盲點：早期的函式呼叫準確率（function-call accuracy）僅評估靜態預測，無法反映互動環境中的真實行為；而新興的互動式基準（如 AgentBench、OSWorld、AppWorld）雖然評估多步驟任務完成度，卻多聚焦於最終環境狀態或中間里程碑，**未檢查每個後果性動作（consequential action）是否由代理實際觀察到的證據所支持**。因此，當代理跳過調查或基於錯誤目標的證據行動時，這些評估往往仍回報成功，無法定位失敗究竟發生在調查、證據綁定、動作時機還是多步驟執行哪個環節。

**Q3：為什麼這個問題在實務上很重要？**
A：後果性動作會改變外部狀態——例如退款、發送文件、更新記錄——這些動作一旦執行便難以逆轉，且常會觸發下游操作。當代理未先建立任務相關事實（task-relevant facts）就行動時，**錯誤的支援會沿著動作鏈向下傳播**，例如以錯誤的退款編號通知客戶，或基於未驗證的資格條件執行退款。在生產環境中，這類問題不僅影響使用者信任，更可能造成實際的財務或法律後果，因此必須從可觀察軌跡（observable trajectory）層級加以檢驗，而非僅看端點結果。

**Q4：這篇論文提出的核心方法是什麼？**
A：論文提出 SafeActBench 基準測試套件，包含 656 個案例、橫跨六個操作領域（operational domains）與五種協議（protocols），並搭配兩個關鍵組件：**溯源綁定的證據分類帳（provenance-bound Evidence Ledger）**記錄每項證據是否已為正確的實體與狀態建立，且保留觀察來源；以及**確定性軌跡評估器（deterministic trajectory evaluator）**重播代理軌跡，驗證必要調查、正確工具與參數、執行收據（receipts）、動作依賴與結果狀態變更，整個過程不依賴隱藏推理或 LLM 評判。

**Q5：這篇論文最重要的創新點為何？**
A：最重要的貢獻在於**將工具使用重新概念化為可觀察的證據到動作鏈**，把代理行為拆解為調查、執行與下游依賴三個可測量的環節，而非將任務失敗視為單一結果。這種框架使評估能夠區分「靜態動作判斷（static action judgment）」與「互動式執行（interactive execution）」的落差，並透過溯源機制確保證據與動作之間的綁定關係可被驗證，從而揭露過去被端點正確性所掩蓋的失敗模式。

**Q6：在設計 SafeActBench 時有哪些關鍵的設計選擇？**
A：設計遵循三個原則：第一，**沿著五種協議從靜態決策推進到依賴約束的多動作工作流程**，涵蓋靜態動作評估、已調查的非動作（investigated non-action）、單一動作執行，以及線性與依賴約束的多動作工作流程，以系統性測試不同動作結構下的表現；第二，**證據分類帳保留每筆觀察的來源**，確保證據與動作目標之間的綁定可追溯；第三，**評估器完全確定性且不仰賴 LLM 評判**，僅檢查可觀察的軌跡事實，使評估結果可重現且不受模型偏誤影響。

**Q7：論文中使用了哪些基準測試與模型配置進行實驗？**
A：實驗核心圍繞 SafeActBench 本身，並橫跨**十種模型框架配置（model-harness configurations）**進行評估，藉此檢驗不同模型與執行框架組合在靜態與互動式協議下的差異。這樣的設計使研究者能夠分離模型能力與框架特性對證據到動作鏈可靠性的影響，而非僅報告單一模型的整體成功率。

**Q8：實驗揭示了哪些關鍵結果？**
A：最重要的發現是**強健的靜態動作評估可與明顯較弱的互動式執行並存**——代理在靜態判斷中表現良好，卻在需要實際調查與依賴管理的互動場景中失敗。失敗往往在執行前就已開始：代理會在調查未完成時停止，或在必要證據尚未建立前就採取行動。一旦所需證據建立完成，**單一動作執行通常可靠**，但多動作工作流程會額外暴露未解決的先決條件（prerequisites）與執行不完整等問題，凸顯依賴管理是另一個獨立且困難的能力。

**Q9：論文中進行了哪些消融或受控實驗來驗證發現？**
A：論文透過**受控證據介入（controlled evidence interventions）**進一步驗證：即使代理能夠取得相關資訊，仍可能在缺乏決定性支援的情況下執行動作。這顯示問題不僅在於「資訊是否可取得」，更在於代理如何運用已建立的證據來決定與執行動作，從而把失敗模式從「遺漏資訊」擴展到「錯誤地使用資訊」這個更細緻的層次。

**Q10：這項研究適用於哪些實際應用場景？**
A：任何涉及後果性動作的代理部署都是適用對象，**最典型的場景是客戶服務自動化**，例如退款處理、訂單修改、帳戶狀態更新與客戶通知等需要多步驟且具政策約束（policy constraints）的工作流程。此外，金融交易審核、醫療記錄更新、IT 維運操作等領域同樣需要確保每個動作都有可追溯的證據支持，因為這些場景對錯誤動作的容忍度極低且難以逆轉。

**Q11：將這些發現納入產品設計時應考慮哪些事項？**
A：產品層級應建立**證據先決於動作的執行守門機制**，在代理呼叫會改變狀態的工具前，自動驗證所需證據是否已記錄於證據分類帳並綁定至正確目標。同時應設計**完整的稽核軌跡（audit trail）**，記錄每筆觀察的來源、時間與對應的動作，使事後審查能夠還原證據到動作鏈；對於多動作工作流程，則需明確表達下游依賴並在依賴未滿足時阻止執行，以避免錯誤支援的傳播。

**Q12：這項研究對整個領域會產生什麼影響？**
A：這項工作**將代理評估的典範從端點導向轉向軌跡導向**，促使後續研究與產品開發必須檢查每個後果性動作背後的證據鏈，而非僅以任務完成度作為可靠性的代理指標。它也與近期關於求助行為（help-seeking）、環境觀察信任與動作節制（action restraint）的研究形成互補，共同推動代理可靠性研究從「能不能完成任務」走向「是否以可驗證的方式完成任務」。

**Q13：論文本身承認了哪些限制？**
A：論文的評估範圍限於 656 個案例與六個操作領域，**雖然涵蓋多元情境但仍無法窮舉所有可能的後果性動作類型**；此外，評估僅檢查可觀察軌跡而不審視隱藏推理，這雖然避免了主觀判斷，但也無法區分「代理內部已正確推理但未表現於行動」與「代理根本未考慮證據」這兩種情況。實驗僅涵蓋十種模型框架配置，對其他模型與框架組合的推論需謹慎。

**Q14：論文中揭示了哪些典型的失敗案例？**
A：最具代表性的失敗案例是**代理驗證了錯誤的目標卻仍執行動作**：例如任務要求退款給 C2 並通知客戶，但代理實際調查的是 C1 的狀態並取得 C1 的退款資格證據，卻仍對 C2 發出退款，導致端點狀態滿足但觀察證據不支持該動作。其他典型失敗還包括：在必要證據未建立前就呼叫工具、未等待先前動作的實際回傳結果就執行下游動作，以及在多步驟工作流程中遺漏部分必要動作。

**Q15：基於這些發現，未來有哪些值得探索的研究方向？**
A：未來可朝幾個方向延伸：**將證據到動作鏈擴展至更複雜的非線性工作流程**，包含分支、循環與例外處理；研究如何讓代理在證據不足時主動求助或澄清（與 help-seeking 研究整合）；探索更好的證據綁定機制，使代理能更精確地區分相似但不同的目標實體；以及設計能夠在依賴未滿足時自動暫停或回退的安全護欄。此外，將此框架與動作節制（abstention）研究結合，探討代理何時應拒絕行動而非勉強執行，也是重要的開放問題。

## 實務應用指南

### 適用場景

1. **金融退款與交易處理代理**：客服代理需在退款前驗證收費是否為重複、是否符合退款資格，並在退款成功後使用實際取得的退款編號通知客戶。SafeActBench 的「退款—通知」範例直接對應此場景，可作為部署前的證據鏈驗證標準。

2. **企業內部 IT 工單自動化**：代理需先確認工單優先級、SLA 狀態、相關資產歸屬，再執行升級、關聯或關閉等動作。多動作工作流程（線性與依賴約束）協議可檢驗代理是否正確處理下游依賴。

3. **醫療與保險索賠處理**：在更新病歷或提交索賠前，必須先建立診斷碼、保險資格、預授權等證據；任何下游動作（如通知保戶）都需依賴先前動作的真實回傳結果。

4. **電商訂單與庫存異動**：退貨、補發、庫存調整等動作需先驗證訂單狀態、SKU 對應、退貨原因；批次處理時更需檢查動作間的依賴是否被滿足。

5. **法規遵循與稽核流程**：在送出合規申報或更新監管紀錄前，代理必須先取得必要的佐證文件並綁定到正確實體；證據分類帳（Evidence Ledger）的溯源特性可直接支援稽核追溯。

### 實作前置條件

**資料面**
- 任務領域的權威資料來源（API、資料庫、文件系統），需能提供「目前狀態」查詢而非僅快照。
- 每個動作的「先決條件清單」：哪些實體、欄位、狀態必須在執行前被觀察到。
- 動作結果的真實回傳值（退款編號、工單 ID、申報編號等），需可被後續動作引用。

**運算面**
- 具備工具呼叫能力的 LLM（GPT-4 級、Claude 級或同等開源模型）。
- 可重現的沙盒環境，能重放代理軌跡並比對環境狀態。
- 確定性評估器所需的儲存與運算資源（SafeActBench 656 案例 × 多模型 × 多框架配置）。

**技能面**
- 熟悉代理框架（LangChain、AutoGen、Bedrock Agents 等）的工程師。
- 能定義「證據—動作」綁定規則的領域專家。
- 具備基準測試設計與統計分析能力的研究人員。

### 實作步驟建議

**步驟一：盤點現有代理任務的證據需求**
針對每個後果性動作，明確列出執行前必須被觀察到的證據項目（實體、欄位、狀態），並標註證據來源。對齊 SafeActBench 中「先決條件」的概念。

**步驟二：建立溯源綁定的證據分類帳**
實作 Evidence Ledger：每次工具呼叫的回傳結果都需記錄「來源—內容—綁定目標—時間戳」。這是判斷「代理是否真的取得所需證據」的基礎。

**步驟三：設計確定性軌跡評估器**
不依賴 LLM 裁判，而是以規則比對代理軌跡：(a) 是否完成必要調查；(b) 工具、目標、參數是否正確；(c) 動作時機是否恰當；(d) 下游動作是否使用前序動作的真實回傳值。

**步驟四：分階段部署評估協議**
依 SafeActBench 的五層協議順序推進：
1. 靜態動作判斷（不執行的決策）
2. 已調查的非動作（有能力但選擇不執行）
3. 單一動作執行
4. 線性多動作工作流程
5. 依賴約束的多動作工作流程

每層通過後再進入下一層，避免在未確認基礎能力前測試複雜流程。

**步驟五：執行受控證據介入測試**
刻意提供「相關但非決定性」的資訊（例如查詢到 C1 而非 C2 的退款資格），觀察代理是否會在缺乏決定性證據時提前行動。這是 SafeActBench 揭示的核心失敗模式之一。

**步驟六：建立生產環境的持續監控**
將 Evidence Ledger 與軌跡評估器整合進 CI/CD 流程，每次代理更新後自動回歸測試；生產環境則採樣軌跡進行離線審查。

### 潛在風險與注意事項

**風險一：靜態評估過度樂觀**
模型在「不執行的判斷」上表現良好，不代表實際執行時也可靠。緩解：永遠以互動式執行評估作為上線門檻，不可僅憑靜態分數決策。

**風險二：調查不完整即行動**
代理可能在未取得所有先決條件時就呼叫工具。緩解：在評估器中明確標記「證據未建立即執行」為嚴重失敗，並在 prompt 中強調「未確認前不行動」。

**風險三：下游動作使用錯誤的依賴值**
代理可能憑空產生退款編號，或引用前序動作未實際取得的值。緩解：評估器強制檢查下游動作的參數是否來自前序動作的真實回傳。

**風險四：評估器本身的可繞過性**
若評估器僅檢查最終狀態，代理可能「猜對」答案但缺乏證據鏈。緩解：採用確定性、軌跡級的評估，檢查每一個中間步驟。

**風險五：領域專家與工程師對「證據」定義不一致**
同一個動作，不同人對「必要證據」可能有不同解讀。緩解：在部署前以結構化清單形式定義每個動作的證據需求，並由領域專家簽核。

**風險六：基準測試與真實環境的分布漂移**
SafeActBench 的六個操作領域無法涵蓋所有業務場景。緩解：以 SafeActBench 作為通用底盤，再依自家領域擴充案例。

### 與其他技術的整合建議

**與既有代理框架整合**
LangChain、AutoGen、Bedrock Agents 等框架已提供工具呼叫與軌跡記錄功能。建議在這些框架之上加入「證據綁定層」：每次工具回傳時自動寫入 Evidence Ledger，並在下一個動作執行前檢查先決條件。

**與函式呼叫準確率基準整合**
傳統函式呼叫基準（如 BFCL）僅檢查工具選擇與參數格式。建議將其作為「語法正確性」的第一層篩選，再以 SafeActBench 的證據鏈評估作為「語義正確性」的第二層。

**與 RLHF / 偏好資料整合**
將「未建立證據即行動」標記為負向偏好樣本，「完整調查後正確執行」標記為正向樣本，用於微調或 DPO 訓練。

**與可觀測性平台整合**
Langfuse、Phoenix、Helicone 等工具可記錄代理軌跡。建議將 Evidence Ledger 的事件流接入這些平台，讓 SRE 與 PM 都能即時看到「證據—動作」對應關係。

**與法規遵循系統整合**
證據分類帳的溯源特性可直接輸出為稽核日誌，滿足金融、醫療等產業的合規需求。

**與 A/B 測試平台整合**
新版本代理上線時，以 SafeActBench 案例子集作為影子流量，比對證據鏈完整性差異。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀摘要與圖 1 的退款範例，理解「端點正確不代表證據鏈正確」這個核心觀念。接著看 SafeActBench 的五層協議說明，建立「從靜態判斷到多動作依賴」的漸進式理解。暫時可跳過實作細節，專注於「為什麼代理會在不該行動時行動」這個直覺問題。

**給 AI 工程師**：重點放在第 3 節的評估器設計與第 4 節的實驗結果。Evidence Ledger 的資料結構、確定性軌跡評估器的規則集、以及「受控證據介入」實驗的設計，都是可直接借鏡到自家代理系統的工程模式。建議在自己的代理框架中實作一個最小可行的證據綁定層。

**給研究者**：第 5 節的失敗模式分類與跨模型—框架配置的分析是主要貢獻。建議深入比較「靜態評估強、互動執行弱」這個現象在不同模型家族中的表現，並思考如何將證據鏈概念延伸到規劃、反思、多代理協作等場景。SafeActBench 的 656 案例與五層協議也是設計新基準時可參考的樣板。

**給產品經理**：重點理解「代理失敗的成本」與「評估方式的選擇」。當代理涉及退款、通知、資料異動等後果性動作時，僅看任務完成率是不夠的；需要的是「證據鏈完整性」這個新指標。建議在產品路線圖中為代理部署加入「證據審查」這個里程碑，並與法務、風控團隊討論溯源需求。
