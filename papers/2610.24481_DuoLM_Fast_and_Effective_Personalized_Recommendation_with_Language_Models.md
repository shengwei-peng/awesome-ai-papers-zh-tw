DuoLM 的方法論設計圍繞一個核心問題展開：如何在維持語言模型推薦品質的同時，大幅降低線上服務的計算成本。整體架構採用「雙模型分工」(dual-model division of labor) 的策略，將推薦任務拆解為離線表示學習與線上個性化排序兩個階段。

**編碼器-排序器分工架構 (Encoder-Ranker Division)**

編碼器 LLM（記為 A）負責將每個物品的文字描述壓縮為單一隱狀態向量 (hidden-state vector)，這個向量是與用戶無關的 (user-independent)，意味著同一物品的表示可以被所有用戶重用。排序器 LLM（記為 B）則接收候選向量、歷史物品向量及其對應的用戶反饋文字，透過注意力機制 (attention mechanism) 為每個候選產生個性化分數。這種設計的關鍵在於「連續輸入介面」(continuous input interface)，它將編碼器的輸出向量直接轉換為排序器的輸入嵌入 (input embedding)，取代了原本的文本標記 (text tokens)。

**端到端聯合訓練 (End-to-End Joint Training)**

訓練階段採用兩種監督信號的組合：
1. **交叉熵損失 (Cross-Entropy Loss)**：基於推薦標籤，鼓勵模型選擇觀測到的目標物品
2. **KL 散度 (KL Divergence)**：蒸餾自一個凍結的全文教師模型 T，鼓勵緊湊模型的候選偏好分布與教師一致

這種雙重監督的設計確保了 DuoLM 不僅學會預測正確物品，還能模仿教師模型的細粒度偏好排序，這對於排序品質至關重要。

**運行時優化三層次 (Three-Layer Runtime Optimization)**

第一層是**虛擬標記 ID (Virtual Token IDs, VIDs)**：用戶請求僅攜帶物品 ID 和反饋文字，而非完整的物品向量。運行時將這些 ID 解析為 GPU 常駐表格中的預計算嵌入。在評分基準測試中，VIDs 將平均請求負載減少超過 90%。

第二層是**多物品評分路徑 (Multi-Item Scoring, MIS)**：基於 SGLang 構建，允許單一請求同時評分多個候選。運行時僅構建和預填充 (prefill) 用戶歷史一次，然後跨候選分支共享前綴 KV 緩存。樹狀結構的注意力遮罩 (tree-structured attention mask) 確保每個候選僅關注共享歷史和自身分支，保持評分的獨立性。

第三層是**分段預填充 CUDA 圖 (Segmented Prefill CUDA Graphs)**：捕獲 GPU 操作及其依賴關係，運行時透過重放捕獲的圖來減少 CPU 調度和核心啟動開銷。隨著模型執行速度提升，這些開銷往往成為吞吐量瓶頸。

**離線-線上分離的設計哲學**

訓練完成後，所有物品嵌入可離線預計算並儲存，線上僅運行排序器 B。這種分離使得物品表示的計算成本從線上轉移到離線，而離線計算可以批次化、預先執行，大幅降低線上延遲。

#### 與現有研究的比較

**相較於傳統 ID-based 雙塔推薦器**

傳統雙塔模型（如 YouTube DNN、DSSM）僅基於交互數據訓練，無法直接利用文本語義或預訓練世界知識，導致在冷啟動和長尾物品上泛化能力差。DuoLM 透過編碼器 LLM 保留了預訓練知識，同時透過離線預計算獲得了雙塔式的效率優勢。這是「兩全其美」的設計——既不像雙塔那樣丟失語義，也不像交叉編碼器那樣犧牲可重用性。

**相較於全文交叉編碼器**

交叉編碼器（如 Bao et al. 2023 的方法）將候選表示與用戶上下文耦合，無法跨用戶重用。DuoLM 的編碼器產生用戶無關表示，實現了跨用戶重用，這是根本性的架構差異。代價是表示必須足夠通用以適應所有用戶上下文，這對編碼器的訓練提出了更高要求。

**相較於文本壓縮方法**

Ge et al. (2024) 和 Chevalier et al. (2023) 等文本壓縮方法可減少線上計算，但可能丟失對特定用戶重要的細節。DuoLM 的解決方案是將壓縮與個性化分離——壓縮在編碼器中完成（通用性優先），個性化在排序器中完成（用戶特定性優先），兩者透過聯合訓練協調。

**相較於蒸餾技術**

Hinton et al. (2015) 的知識蒸餾框架被廣泛用於模型壓縮，但 DuoLM 的蒸餾設計獨特之處在於：蒸餾目標不僅是 logits，還包括候選分布 p(τ)，這使得學生模型學習教師的相對偏好排序，而不僅僅是絕對分數。這對於推薦任務的排序品質至關重要。

**相較於推理引擎優化**

vLLM 和 SGLang 等推理引擎透過批處理和前綴緩存提升吞吐量，但 DuoLM 指出這些優化對推薦場景不夠——推薦請求的特殊性在於「多候選共享同一歷史」，這需要 MIS 這類專門的調度策略。論文貢獻了一個運行時優化如何與模型架構協同設計的範例。

**限制與不足**

1. **教師依賴性**：DuoLM 的訓練需要一個預先訓練好的教師模型，這增加了系統複雜度和訓練成本

適用於需要即時納入新內容的媒體網站。編碼器可快速將新文章轉為向量並加入候選池，排序器結合讀者閱讀紀錄與停留時間反饋進行個人化排序。透過虛擬標記 ID 機制，新內容可在不重新訓練模型的情況下立即上線。

**4. 企業內部知識庫與文件檢索**
適用於 Notion、Confluence 等協作平台的「相關文件推薦」。將文件內容編碼後，可在使用者閱讀某文件時即時推薦相關內部資料，兼顧語意理解與回應速度。

**5. 廣告投放與即時競價（RTB）系統**
在數十毫秒的預算內需對數百個廣告候選進行評分的場景，DuoLM 的多候選評分路徑與 CUDA Graph 重放可顯著提升吞吐量，使更多候選進入精排階段以提升廣告收益。

### 實作前置條件

**資料需求**
- 具備結構化的用戶互動日誌（用戶 ID、物品 ID、反饋類型、互動時間），建議至少數十萬筆歷史互動以支撐蒸餾訓練
- 候選物品需有豐富的文字內容（標題、描述、屬性），純 ID 類資料不足以發揮 DuoLM 的語意優勢
- 需準備教師模型的訓練資料或既有教師模型輸出，用於知識蒸餾階段

**運算資源**
- 訓練階段：建議配備多張 A100/H100 等高階 GPU，編碼器與排序器需聯合訓練
- 推論階段：單張 H100 即可達到論文中 ~26,400 候選/秒的吞吐量；多張 GPU 可線性擴展
- GPU 記憶體需容納預編碼的物品向量表（依物品數量而定，每件物品一個向量）

**技術能力**
- 熟悉 PyTorch 與 Hugging Face Transformers 生態系
- 具備 LLM 訓練（LoRA、全參數微調）與知識蒸餾實務經驗
- 了解 SGLang 或 vLLM 等推論引擎的內部機制（KV cache、prefix caching、CUDA Graph）
- 具備分散式訓練與 GPU 效能調優經驗者優先

### 實作步驟建議

**階段一：資料準備與基線建立（2-4 週）**
1. 整理用戶互動序列資料，定義反饋文字格式（如「用戶給予 5 星評分」轉為自然語言）
2. 訓練或選定一個全文字教師模型 T 作為蒸餾來源（可基於既有 LLM 微調）
3. 在驗證集上評估教師模型品質，建立後續比較的基線

**階段二：模型訓練（4-8 週）**
1. 初始化編碼器 A 與排序器 B（可從同架構 LLM 衍生）
2. 實作連續介面層，將編碼器輸出映射為排序器的輸入嵌入
3. 採用聯合訓練：交叉熵損失 + 教師 KL 散度損失
4. 監控蒸餾差距與排序品質指標（NDCG@10、Hit Rate），逐步調整損失權重

**階段三：離線預計算（1-2 週）**
1. 使用訓練後的編碼器 A 對所有候選物品進行批次編碼
2. 將物品向量存入 GPU 常駐的 ID 索引表
3. 建立物品 ID → 向量的查詢介面

**階段四：服務化整合（4-6 週）**
1. 在 SGLang 上實作多候選評分（Multi-Item Scoring, MIS）路徑
2. 整合虛擬標記 ID 解析邏輯，確保請求 payload 僅含 ID 與反饋文字
3. 套用分段預填 CUDA Graph，捕捉並重放 GPU 操作序列
4. 實作共享歷史 KV cache 機制，確保同一請求內候選分支僅預填一次

**階段五：上線與監控（持續）**
1. 採用 A/B 測試，先以小流量驗證推薦品質
2. 監控吞吐量、延遲分位數（P50/P95/P99）、GPU 利用率
3. 建立回饋迴圈，定期以新互動資料微調模型

### 潛在風險與注意事項

**1. 蒸餾品質天花板**
DuoLM 的推薦品質受教師模型上限限制。若教師模型本身在某些長尾物品上表現不佳，學生模型將繼承此缺陷。**緩解方式**：定期更新教師模型，或在蒸餾損失中加入額外的標籤監督項以突破天花板。

**2. 物品向量表更新成本**
當新物品上架或既有物品內容大幅更新時，需重新編碼並更新 GPU 記憶體中的向量表。對於數百萬級物品的場景，全量重編碼可能耗時數小時。**緩解方式**：建立增量編碼管線，僅處理變更物品；或採用背景批次更新策略。

**3. 歷史長度對延遲的影響**
雖然共享歷史預填降低了重複計算，但極長的用戶歷史仍會增加單次請求的預填時間。**緩解方式**：限制最大歷史長度（如最近 50-100 次互動），或採用歷史摘要機制。

**4. 蒸餾訓練不穩定**
聯合訓練編碼器與排序器時，兩個模型的梯度可能互相干擾，導致收斂不穩定。**緩解方式**：採用較小的學習率、梯度裁剪，或先單獨預訓練編碼器再聯合微調。

**5. CUDA Graph 相容性問題**
CUDA Graph 對輸入形狀敏感，動態長度的歷史或候選數可能導致圖重放失敗。**緩解方式**：將常見輸入長度預先編譯為多個 CUDA Graph 變體，運行時依實際長度選擇。

**6. 評估指標的侷限性**
論文的評估基於 Amazon Books 與 Video Games 公開資料集，實際業務場景的用戶行為模式可能差異甚大。**緩解方式**：上線前必須在自有資料上進行離線評估與小規模線上測試。

### 與其他技術的整合建議

**1. 與傳統雙塔召回模型組成兩階段架構**
將 DuoLM 定位於精排階段，上游使用傳統 ID-based 雙塔模型（如 DSSM、YouTube DNN）從數百萬候選中快速召回數百至數千件，再交由 DuoLM 進行精排。此組合兼顧召回效率與排序品質。

**2. 與向量資料庫整合**
物品向量表可與 Milvus、Qdrant 等向量資料庫同步，支援基於語意相似度的快速候選生成。編碼器 A 可同時服務於檢索與排序兩個用途，降低維運成本。

**3. 與 RAG 系統共用基礎設施**
若組織已有基於 LLM 的 RAG 系統，DuoLM 的編碼器可作為文件嵌入器共用，排序器架構亦可借鑑 RAG 中的重排序（re-ranking）模式。

**4. 與特徵平台（Feature Store）整合**
將用戶歷史與反饋特徵統一管理於 Feast、Tecton 等特徵平台，確保訓練與推論的一致性，並簡化 MIS 路徑中的特徵注入邏輯。

**5. 與 MLOps 平台整合**
將蒸餾訓練、向量預計算、CUDA Graph 編譯等步驟納入 Kubeflow 或 Metaflow 等 MLOps 工作流，支援自動化重訓練與部署。

**6. 與多模態模型擴展**
若未來需納入圖片、音訊等非文字內容，可將編碼器 A 替換為多模態編碼器（如 CLIP、Whisper 衍生架構），排序器 B 維持不變，架構具備良好的擴展性。

**給產品經理：** 重點理解 DuoLM 的商業價值——在維持推薦品質（甚至超越教師模型）的前提下，將吞吐量提升 60 倍以上，這意味著同樣的硬體成本可服務更多用戶，或在相同延遲預算下評分更多候選以提升轉換率。論文的 Amazon Books 案例顯示 NDCG@10 從 0.5440 提升至 0.5586，這對業務指標的實質影響值得與資料科學團隊進一步討論。
