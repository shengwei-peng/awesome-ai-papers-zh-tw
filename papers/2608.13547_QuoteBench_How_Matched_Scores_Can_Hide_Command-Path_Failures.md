# QuoteBench：配對分數如何掩蓋命令路徑失效

## ⚡ TL;DR

配對分數無法區分命令生成錯誤與傳輸層引入的失效。
QuoteBench 以精確最終狀態驗證，分離生成契約與執行傳輸層的影響。
額外解析器使成功率降55.4至73.2百分點，揭露邊界可部分恢復，評估應報告完整路徑。

## 摘要翻譯

LLM 編碼代理（LLM coding agent）透過可能會序列化（serialize）、包裝（wrap）並重新解析（reparse）模型輸出的介面下達 Bash 命令（Bash command）。單靠配對分數（matched score）無法區分命令生成錯誤（command-generation error）與生成後才引入的命令路徑失效（command-path failure）。QuoteBench 以精確最終狀態驗證（exact final-state validation）衡量此邊界，涵蓋來自 14 個事件衍生族系（incident-derived family）的 56 項單次任務（one-shot task），並透過一個刻意未跳脫（unescaped）的額外解析器（parser），橫跨生成契約（generation contract）與執行傳輸層（execution transport）之間的邊界。在插值點（interpolation point）進行跳脫（escaping）可重現每個重播回覆（replayed reply）的原始路徑結果（raw-path outcome），因此已揭露邊界（disclosed boundary）下的任何恢復，必然來自模型改變其生成方式。在八種同視窗配置（same-window configuration）中，透過額外解析器重播相同回覆會使成功率下降 55.4 至 73.2 百分點（percentage point）；揭露邊界（disclosure）可讓其中六種配置恢復 30.4 至 60.7 百分點，另外兩種則為零或略為負值。原始生成能力在前沿（frontier）已近乎飽和；邊界適應（boundary adaptation）才是目前區分模型的關鍵。GPT-5.6-sol 的配對差距（matched gap）為 -3.6 百分點，背後卻隱藏了 -64.3 百分點的損害（damage）與 +60.7 百分點的補償（compensation）。部署配置（deployment configuration）會重新排序模型：在 26 個可比較配對（comparable pair）中，有一個反轉（reversal）明確無疑，另有四個僅落在單任務邊距（single-task margin）上。在評估會發出命令的代理時，應報告模型配置（model configuration）、生成契約、執行路徑（execution path）、運作點（operating point）與最終狀態驗證器（final-state validator），而非將配對分數視為模型的內在屬性。

### 核心貢獻（3～5點）
- 提出 QuoteBench，以精確最終狀態驗證區分「命令生成錯誤」與「生成後經執行傳輸／解析路徑產生的命令路徑失效」。
- 揭示單靠配對分數會掩蓋巨大的損害與補償，例如 GPT-5.6-sol 的 -3.6 百分點配對差距背後隱藏 -64.3 百分點損害與 +60.7 百分點補償。
- 發現原始生成能力在前沿模型間已趨飽和，「邊界適應」才是目前區分模型表現的關鍵能力。
- 證明部署配置會改變模型排名，在可比較配對中出現明確反轉與單任務邊距上的不穩定排序。
- 主張評估命令發出代理時應完整報告模型配置、生成契約、執行路徑、運作點與最終狀態驗證器，而非僅以配對分數作為內在屬性。

### 適合對象
適合對 LLM 編碼代理、終端機基準測試與模型評估方法學感興趣的研究者與工程師；特別推薦給關注部署配置、執行傳輸層、生成契約與命令解析邊界如何影響評估結果的讀者。

## 深度分析

#### 方法論解析

QuoteBench 的核心方法論是將「模型生成（generation contract）」與「執行傳輸層（execution transport）」這兩個原本在終端機代理（terminal agent）評測中被混為一談的階段拆開，並以固定回覆重播（fixed-reply replay）的方式，把配對分數（matched score）拆解成「傳輸損害（transport damage）」與「契約條件化補償（contract-conditioned compensation）」。

##### 任務設計：由真實事件歸納的精確最終狀態任務

論文建構了 56 個單次任務（one-shot task），來自 14 個事件衍生族系（incident-derived family）。每個族系包含一個良性對照（benign control）與三個有害載荷變體（hazardous payload variant），涵蓋多行文字（multiline text）、敵意檔名（hostile filename）、正規表示式元字元（regular-expression metacharacter）、萬用字元元字元（glob metacharacter）、文件嵌入（heredoc）、字面 argv（literal argv）、環境值（environment value）、Git 中繼資料（Git metadata），以及兩種本地類 SSH 模擬（local SSH-like simulation）。驗證器（final-state validator）不檢查命令字串本身，而是檢查最終位元組（final byte）、argv、JSON、目錄狀態（directory state）或 Git 歷史（Git history），因此只有真正達成正確最終狀態的命令才會得分。這種精確最終狀態驗證（exact final-state validation）讓論文能夠區分「命令生成錯誤（command-generation error）」與「命令在傳輸過程中被解析器破壞」。

##### 三種命令路徑：raw、native 與 nested

論文定義了三種執行路徑：

- **Raw reply（原始回覆）**：模型輸出直接作為 shell 程式執行。
- **Native command field（原生命令欄位）**：從結構化工具呼叫（structured action language）中提取命令欄位後執行。
- **Nested condition（巢狀條件）**：在 raw 或 native 的基礎上，額外加入一個下游雙引號解析器（double-quoted parser），模擬 `ssh host "..."`、`docker exec sh -c "..."` 或 CI `run:` 步驟等常見部署模式。

這個 nested condition 是論文的人為介入：在插值點（interpolation point）故意不進行跳脫（unescaped），讓同一個模型回覆經過多一層解析。由於跳脫（escaping）可以在插值點完全重現原始路徑結果（raw-path outcome），因此任何在已揭露邊界（disclosed boundary）下的效能恢復，都必須來自模型改變其生成內容，而非後處理取巧。

##### 固定回覆重播與分數拆解

這是方法論上最關鍵的設計。論文先收集模型在某一運作點（operating point）產生的回覆，然後將這些儲存下來的生成結果：

1. 以原始路徑執行，得到基準成功率；
2. 以 nested 路徑重播同一回覆，測量額外解析器造成的傳輸損害；
3. 在提示中揭露邊界後，讓模型重新生成，測量契約條件化補償。

透過這種交叉設計（crossed design），論文可以把一個看似僅有 -3.6 百分點（percentage point）的配對差距（matched gap），拆解成 -64.3 百分點的損害與 +60.7 百分點的補償。這說明單一配對分數可能掩蓋了命令路徑上兩個方向的大幅效應。

##### 運作點與 effort ladder

論文還探討了模型在不同 effort 設定（可視為推理預算或模型內部 effort 標籤）下的表現。值得注意的是，同一個 effort 標籤在不同模型間對應不同的 token 預算，而且 effort 提升對某些模型有幫助、對其他模型則無。這進一步強調：評測時必須報告運作點，而非把分數視為模型的內在屬性。

#### 實驗數據解讀

##### 整體成功率的分佈

在同視窗配置（same-window configuration）下，nested 條件的配對成功率的範圍是 14.3% 到 91.1%，顯示不同模型對額外解析邊界的適應能力差異極大。若改為挑選每個模型觀察到的最佳運作點，則有三個模型達到 100.0%，其餘則落在 14.3% 到 98.2% 之間。另外，六個供應商託管且使用原生命令欄位（native shell tool）的模型，成功率為 85.7% 到 98.0%。這說明當執行傳輸層較為「友善」時，模型看起來幾乎都能過關；但一旦加入一個刻意未跳脫的巢狀解析器，表現便急劇下降。

##### 重播介入的衝擊

實驗發現，將同一回覆透過額外解析器重播，會讓成功率下降 55.4 到 73.2 百分點。這個幅度非常大，且在所有八個同視窗配置中都穩定出現，顯示問題不是特定模型或特定任務的偶發現象，而是命令路徑本身的結構性脆弱點。

在揭露邊界資訊後，有六個配置恢復了 30.4 到 60.7 百分點，但另外兩個配置幾乎沒有恢復甚至略微為負。這表示：

- 對部分模型而言，只要提示清楚說明會經過雙引號巢狀解析，它們就能調整生成策略（例如主動跳脫）；
- 對另一些模型而言，即使知道邊界，也無法穩定產生正確的跳脫，或者其生成契約與執行傳輸層之間的對應關係過於複雜。

##### GPT-5.6-sol 的拆解案例

論文以 GPT-5.6-sol 為例，指出其配對差距僅 -3.6 百分點，看似幾乎沒有問題；但拆解後卻是 -64.3 百分點的損害與 +60.7 百分點的補償。這是全文最具說服力的數據：如果只看 aggregate 的配對分數，會誤以為該模型已經「解決」了巢狀解析問題；實際上它是在生成階段付出了極大補償才抵銷傳輸損害。這也呼應了論文標題——配對分數可以隱藏命令路徑失效（command-path failure）。

##### 部署配置下的排名反轉

在模擬實際部署配置（deployment configuration）時，模型排名出現變化：在 26 個可比較配對（comparable pair）中，有一組出現明確的反轉（reversal），另有四組處於單任務邊距（single-task margin）。這證明 leaderboard 的相對順序並非模型能力的穩定屬性，而是取決於選用的執行路徑與運作點。

##### Effort、重複取樣與跨環境穩定性

在觀察到的 trial-0 effort 階梯中，每個測量階梯內的無條件 nested-replay 通過率變化最多僅 5.4 百分點，顯示該機制在不同 effort 設定下相當穩定。此外，論文也驗證了私有載荷（private payload）與重複抽樣下問題依然存在，並且在使用者空間（userland）差異（GNU 與 BSD coreutils 環境）下也能複現。

##### ShellCheck 的局限性

論文還用 ShellCheck 對回覆進行靜態分析，發現它只標記了 34.6% 的 nested-only 失效，而對於成功通過巢狀解析的回覆則標記了 11.4%。這是因為每個命令單獨看來都語法正確，錯誤出在下游插值而非命令本身。這也說明現有靜態工具無法捕捉這類跨邊界失效。

#### 與現有研究的比較

##### 相對於廣泛型代理與終端機基準測試

現有的編碼基準測試（coding benchmark）與終端機基準測試（terminal benchmark），例如 SWE-bench、SWE-bench Verified、OSWorld、WebArena 等，強調端到端真實性，同時混雜了規劃（planning）、儲存庫導航（repository navigation）、命令建構（command construction）與修復迴圈（repair loop）等多種能力。QuoteBench 則刻意縮小範圍，把「字面量（literal）保留」從其他能力中隔離出來，讓研究者能精確定位失效發生在生成階段還是傳輸階段。

##### 相對於命令生成基準測試

NL2Bash、NLC2CMD、NL2SH-ALFA、BashBench 等工作聚焦於將自然語言轉譯為 Bash 程式，並在固定傳輸層（fixed transport）下評分。這些工作回答的是「模型能不能產生正確的 shell 程式」，但無法回答「這個正確的程式在經過代理介面、遠端包裝器或 CI 步驟後是否仍然正確」。QuoteBench 的貢獻在於固定生成的程式，然後改變執行傳輸層，從而分離「錯誤命令」與「為錯誤通道編碼的正確命令」。

##### 相對於同時期改變 harness 的研究

Zhang et al.（2026b）的同時期工作顯示，改變整個評測框架（scaffold）會導致模型排名變動，但由於整個 scaffold 被替換，無法將反轉歸因於單一機制。QuoteBench 透過只改變一個額外解析器、同時固定模型回覆，把排名反轉明確歸因於命令路徑（command path），並進一步把配對分數拆解為損害與補償。

##### 相對於長期存在的 Bash 引號安全指引

Holen（2012）與 Wheeler（2010）等文獻早已記錄敵意檔名與引號處理的危險，Free Software Foundation（2025）也公開了 Bash 解析規則（parser rule）。QuoteBench 的創新不在於發現新漏洞，而在於把這些已知風險轉化為可重複、可量化的基準測試，並證明即使在前沿模型（frontier）上，邊界適應（boundary adaptation）仍是主要瓶頸。

##### 限制

論文本身也承認若干限制：

1. **範圍狹窄**：只聚焦 Bash 引號失效（Bash quoting failure），未涵蓋 PowerShell、zsh、fish 等其他 shell，也未涵蓋網頁或桌面控制等其他代理場景。
2. **單次任務**：任務為 one-shot，未納入多輪修復迴圈與暫存指令碼（temporary script）等常見代理恢復策略的成本。
3. **人為介入的解析器**：nested condition 是刻意設計的單一未跳脫解析器，雖然能精確歸因，但不一定完全代表真實部署中所有可能的邊界組合。
4. **不估計盛行率**：事件衍生族系用於機制覆蓋（mechanism coverage），而非估計真實世界發生頻率。
5. **修復需要呼叫方控制邊界**：兩個顯而易見的修復——在插值點正確跳脫與使用臨時指令碼——都需要呼叫方掌握邊界資訊，但論文的 harness 調查發現，許多公開代理系統會在聲明的生成契約下游額外加邊界。

#### 可重現性評估

##### 有利於重現的設計

QuoteBench 在方法論上採取了多項有利於可重現性（reproducibility）的設計：

- **固定提交調查（fixed-commit survey）**：對六個公開代理系統的調查鎖定在特定程式碼提交版本，減少因版本變動導致的差異。
- **凍結基準測試（frozen benchmark）**：論文明確提到實驗是在凍結的基準上進行，並儲存了生成結果，這讓重播實驗可以在相同輸入下重複。
- **精確最終狀態驗證器**：驗證邏輯基於最終位元組、argv、JSON、目錄狀態與 Git 歷史等客觀指標，主觀判斷空間小。
- **明確的運作點報告**：論文區分同視窗配置、最佳運作點、供應商託管 native 配置與部署配置，讓後續研究能夠對照相同設定。

##### 開放資源現況

然而，從提供的上下文來看，論文並未明確聲明是否公開原始碼、資料集或模型權重。由於評估對象包含 GPT-5.6-sol 等專有模型（proprietary model），模型權重本身不可能公開。若作者後續釋出 QuoteBench 的任務定義、驗證器與儲存的回覆資料，則社群可以在不重新呼叫 API 的情況下重現重播實驗；反之，若僅發表論文而未釋出資料，則重現性會受限於他人是否能正確重建 56 個任務與驗證邏輯。

##### 重現時需注意的細節

即使資料公開，重現時仍需注意：

- **使用者空間差異**：GNU 與 BSD coreutils 環境對某些命令的行為不同，論文已發現這會影響結果。
- **模型版本與 effort 標籤**：不同模型對 effort 標籤的實作不同，重現時必須記錄確切的模型版本、API 參數與提示模板。
- **提示中的邊界揭露方式**：disclosed boundary 條件下，提示如何描述額外解析器會直接影響模型補償能力，這是重現的關鍵變因。
- **插值點實作**：nested condition 需要在插值點刻意不跳脫，任何後處理差異都會改變結果。

#### 未來研究方向

##### 1. 多輪修復與恢復成本

QuoteBench 目前採用單次任務，未來可擴展至多輪互動，測量代理在遭遇引號失效後進入修復迴圈（repair loop）的頻率、所需的額外動作數量、產生的工作區產物（workspace artifact），以及最終是否成功。這將更接近真實代理部署中的成本結構。

##### 2. 真實部署痕跡的驗證

論文的事件衍生族系來自公開 issue tracker，但未來可進一步收集真實代理系統在生產環境中的命令執行痕跡，並將其轉化為 QuoteBench 的擴充任務，以估計這類失效在實際使用中的盛行率。

##### 3. 跨 shell 與跨協議擴展

目前僅聚焦 Bash，未來可發展類似框架於 zsh、fish、PowerShell，以及遠端執行協議（如 SSH、Docker exec、Kubernetes exec、CI YAML）。不同協議的插值點與跳脫規則各異，將產生新的邊界適應挑戰。

##### 4. 結構化操作介面與型別化命令

論文提到型別化操作（typed operations）是探索性替代方案。未來可研究如何設計結構化動作語言（structured action language），讓模型不再輸出需要被重新解析的字串，而是輸出帶有型別資訊的操作物件，從根源消除插值點造成的風險。

##### 5. 自動邊界推論與契約驗證

目前需要人為在提示中揭露邊界。未來可研究如何讓代理系統自動偵測執行傳輸層的解析行為，並在生成階段自動選擇正確的跳脫策略；也可發展形式化契約驗證工具，確保生成契約與執行傳輸層一致。

##### 6. 動態運作點選擇

論文發現 effort 對不同模型效果不一。未來可研究如何根據任務難度與命令路徑不確定性，動態選擇運作點與推理預算，以在成本與成功率之間取得最佳平衡。

##### 7. 評測報告標準化

論文主張評測應報告模型配置（model configuration）、生成契約、執行路徑（execution path）、運作點與最終狀態驗證器。未來可推動社群採用標準化的報告範本，讓不同研究與產品之間的數據具有可比較性。

##### 8. 對抗性載荷生成

目前的有害載荷變體由人為設計。未來可引入對抗性方法，自動生成能夠觸發命令路徑失效的載荷（payload），並用於持續壓力測試新模型與新代理介面。

## 論文問答

【背景與動機】

**Q1：QuoteBench 想解決的命令路徑失效問題是什麼？為什麼單看配對分數無法發現？**
A：當 LLM 編碼代理透過各種介面發出 Bash 命令時，模型輸出會被序列化、包裝並重新解析，這使得原本正確生成的命令在傳輸過程中被額外的解析器破壞。傳統的配對分數只報告最終是否成功，無法區分「模型生成錯誤」與「生成後因執行傳輸層未正確跳脫而產生的失效」。QuoteBench 因此把焦點放在生成契約與執行傳輸層的交界，透過固定回覆重播來量化額外解析器造成的損害與補償。

**Q2：現有的編碼或終端機基準測試為何難以隔離 Bash 引號失效？**
A：現有代理基準測試通常把命令建構與規劃、儲存庫導航、錯誤修復等能力混在一起評估，因此無法判斷第一次發出的命令是否確實保留了字面載荷。另一方面，傳統的命令生成基準測試雖然檢驗模型輸出的程式，但只在固定傳輸層下評分，無法反映部署時可能遇到的額外解析邊界。QuoteBench 採用單次、精確最終狀態驗證的設計，把命令路徑可靠性獨立出來，從而填補這兩類基準之間的缺口。

**Q3：為什麼 Bash 引號失效對 LLM 代理特別重要？**
A：Bash 引號規則公開且嚴格，一旦跳脫或插值時機錯誤，就會腐蝕字面量、破壞常見動作，甚至引發反覆診斷與重試的修復迴圈。公開問題追蹤系統中已記錄了文件嵌入語法錯誤、過度引號運算子、以及多次修復嘗試等真實事件，顯示這類問題在實際系統中確實存在。此外，命令常需跨越遠端或容器化邊界，例如 `ssh host "..."` 或 `docker exec sh -c "..."`，這些雙引號巢狀解析會再次重新解釋命令內容，使部署風險進一步放大。

【方法與創新】

**Q4：QuoteBench 的核心方法與交叉設計是什麼？**
A：QuoteBench 同時變更生成契約與執行傳輸層，並對同一份模型回覆進行重播，藉此把「模型生成錯誤」與「傳輸層損害」分離開來。具體而言，研究者先取得模型在 raw 契約下生成的命令，再將這份固定回覆分別餵入無額外解析器與加入一個雙引號巢狀解析器的兩種路徑，比較其成功率差異。由於回覆內容完全相同，任何差異都只能歸因於命令路徑上的額外解析，從而能精確測量傳輸損害與契約條件化後的補償。

**Q5：什麼是 raw、native 與 nested 條件？它們如何對應真實部署邊界？**
A：raw 是指模型回覆直接作為 shell 程式執行，native 則是從結構化工具呼叫中提取命令欄位後再執行，這兩種生成契約在公開代理系統中都有出現。nested 條件則模擬命令被包入雙引號後再次解析的情況，例如 `ssh host "..."`、`docker exec sh -c "..."` 或 CI `run:` 步驟等遠端或容器化場景。透過在實驗中只加入一個刻意未跳脫的額外解析器，QuoteBench 能夠控制單一變因，並把觀察到的失效歸因於命令路徑而非模型能力本身。

**Q6：QuoteBench 的任務與驗證器如何設計？為何選擇精確最終狀態驗證？**
A：該基準包含 56 個單次任務，來自 14 個由真實事件衍生的操作族系，每個族系含一個良性對照與三個有害載荷變體，涵蓋多行文字、敵意檔名、正規表示式與萬用字元、文件嵌入、字面 argv、環境值、Git 中繼資料與本地類 SSH 模擬。驗證器檢查最終位元組、argv、JSON、目錄狀態或 Git 歷史等精確最終狀態，只要命令能達到正確狀態就給分。這種設計讓評估聚焦於「命令是否把載荷正確保留到最終狀態」，而非模型是否採用特定修復策略或額外規劃步驟。

【實驗與結果】

**Q7：實驗的主要量化結果是什麼？**
A：在八個同視窗配置中，把同一份回覆重播到加入一個雙引號解析器的巢狀路徑後，成功率下降了 55.4 到 73.2 百分點，顯示額外解析器幾乎必然造成嚴重損害。當提示中揭露該邊界後，有六個配置的成功率回升了 30.4 到 60.7 百分點，但另外兩個配置幾乎沒有恢復甚至略微下降。以 GPT-5.6-sol 為例，其配對差距僅 -3.6 百分點，卻隱藏了 -64.3 百分點的傳輸損害與 +60.7 百分點的邊界適應補償，說明單一配對分數會大幅掩蓋背後的兩個相反效應。

**Q8：巢狀解析器如何影響模型排名與部署配置？**
A：由於不同模型對額外邊界的適應能力不同，加入巢狀解析器後的部署配置會重新排列模型順序；研究發現在 26 個可比較配對中，有一對出現明確的排名反轉，另有四對處於單一任務邊距的臨界反轉。這表示在 raw 或 native 契約下表現較好的模型，並不一定能在真實部署的雙引號巢狀路徑中保持領先。因此，若評估只報告某一固定運作點的配對分數，可能會對實際部署選型產生誤導。

**Q9：有哪些消融或穩健性檢驗？**
A：研究者在不同 effort 等級上觀察到，每個測量階梯內的無條件巢狀重播通過率變化最多僅 5.4 百分點，顯示該現象對 effort 設定相對穩定。他們也在私有載荷與多次抽樣中複製了相同機制，並在 GNU 與 BSD coreutils 環境下進行測試，證明問題不限於特定字面值或使用者空間。此外，正確跳脫與臨時指令碼這兩種修復都能完全消除效應，但前提是呼叫端必須控制邊界，而這正是目前許多代理介面未能保證之處。

【應用與影響】

**Q10：實務上應如何改變命令發出代理的評估方式？**
A：論文主張評估報告應包含模型配置、生成契約、執行路徑、運作點與最終狀態驗證器，而不是把配對分數當成模型的內在屬性。這意味著除了公布最終成功率，還要說明命令是 raw 還是 native、是否經過額外解析器、以及驗證的是哪一種最終狀態。只有這樣，其他研究者或工程師才能判斷某個分數是在哪個命令路徑上取得，並據此進行公平的模型比較與部署選型。

**Q11：對產品團隊部署 LLM 代理與 shell／遠端工具有何啟示？**
A：產品團隊應意識到，模型在開發環境直接執行時表現良好，並不保證在經過 ssh、docker exec 或 CI 步驟等雙引號包裝後仍能正確運作。若代理介面在模型不知情的情況下於下游套用邊界，則必須由系統負責正確跳脫或改用臨時指令碼等受控傳輸方式，而非期待模型自行補償。同時，選擇模型與 effort 等級時應以目標部署路徑為準，因為同一 effort 標籤在不同模型間可能對應不同的 token 預算，且邊界適應能力才是區分前沿模型的關鍵。

**Q12：這項研究對比較前沿模型與選擇運作點有何影響？**
A：研究發現原始生成能力在前沿模型間已接近飽和，真正拉開差距的是模型能否根據已揭露的邊界調整生成內容，即邊界適應能力。因此，挑選模型時不應只看單一配對分數，而要檢視其在不同生成契約與執行傳輸層下的分解表現。此外，由於 effort 提升對某些模型有幫助、對其他模型無效，產品團隊需要針對自己的部署路徑進行路徑配對的模型與 effort 選擇，而非盲目採用最高 effort。

【限制與未來】

**Q13：QuoteBench 有哪些已承認的限制？**
A：QuoteBench 聚焦於單次回覆的 Bash 命令，並未涵蓋多輪對話、規劃、儲存庫導航或錯誤修復迴圈等更廣泛的代理能力。其 56 個任務與 14 個族系雖然能精確測量特定機制，但主要用於機制覆蓋而非估計真實世界中的發生率。此外，實驗中的巢狀邊界是單一、刻意設計的雙引號解析器，雖然能隔離變因，卻不代表所有可能的部署邊界。

**Q14：哪些失效案例仍未被現有方法解決？**
A：在八個同視窗配置中，有兩個配置在揭露邊界後幾乎沒有恢復甚至略微下降，顯示單純告知模型存在額外解析器並不足以保證正確跳脫。靜態分析工具 ShellCheck 也只能標出 34.6% 的巢狀專屬失效，同時對 11.4% 成功通過巢狀路徑的回覆發出警告，因為每個命令單獨看來都語法正確，錯誤出在下游插值。這些案例說明，即使結合現有語法檢查與邊界揭露，仍需要更根本的解決方案，例如型別化操作或讓呼叫端完全控制邊界。

**Q15：未來可以朝哪些方向延伸？**
A：未來可以探索型別化操作，讓模型輸出結構化資料而非純文字命令，從根本上避免引號與跳脫問題。也可以擴展到更多種類的部署邊界，例如 JSON、YAML、URL 參數或各種遠端程序呼叫包裝器，並建立標準的報告格式。最終，社群需要一套共識，要求任何命令發出代理的評估都透明披露生成契約與執行傳輸層，才能讓配對分數真正具有可比較性與可重現性。

## 實務應用指南

## 適用場景

1. **遠端或容器化執行的編碼代理**  
   當代理透過 `ssh host "..."`、`docker exec sh -c "..."` 或 CI `run:` 步驟下達 Bash 命令時，命令會在生成後再被一層雙引號解析。QuoteBench 的巢狀條件可直接用來驗證：同一份模型回覆在直接執行與經過遠端包裝後，是否仍能達到相同的最終狀態。

2. **採用結構化工具呼叫的 IDE / 雲端助理**  
   若代理介面從 JSON 或結構化動作語言中提取「原生命令欄位」，生成契約與執行傳輸層之間容易出現引號處理不一致。本方法可協助團隊確認：模型輸出在被序列化、包裝、重新剖析後，字面量是否仍然完整。

3. **終端機自主代理的例行動作稽核**  
   對於需要寫入精確位元組、編輯 JSON、操作 Git 中繼資料或處理敵意檔名的代理，QuoteBench 提供 14 個操作族系與對應的最終狀態驗證器，用來隔離「命令生成錯誤」與「命令路徑失效」。

4. **模型評估與排行榜建置**  
   當比較不同模型時，僅報告配對分數會掩蓋執行傳輸層造成的損害與補償。透過固定回覆重播，評估者可以把總分分拆為運輸損害與契約條件化補償，避免單一任務邊距導致的排名反轉。

5. **紅隊測試與安全把關**  
   利用有害載荷變體測試代理介面：若未跳脫的特殊字元在插值點被重新解讀，可能觸發非預期展開或命令注入。這適合在產品上線前對 harness 進行壓力測試。

## 實作前置條件

- **資料**：取得 QuoteBench 的 56 項單次任務與對應的最終狀態驗證器，或依據自身事件回報建立類似的任務家族。每項任務需包含良性對照與多個有害載荷變體，並能檢查最終位元組、argv、JSON、目錄狀態或 Git 歷史。
- **運算**：可重複執行沙箱化 Bash 的環境（容器或虛擬機），用於比較 GNU 與 BSD userland；若自行評估模型，還需足夠的 API 配額或推論資源。重播本身運算量低，重點在於可重現的執行傳輸層設定。
- **技能**：熟悉 Bash 引號規則與跳脫語義、能建構命令解析邊界（例如雙引號巢狀包裝）、具備 Python 或其他語言的 harness 開發能力，並了解 LLM API 與結構化工具呼叫流程。

## 實作步驟建議

1. **明確生成契約與執行傳輸層**  
   先決定模型輸出是直接作為 shell 程式的「原始回覆」，還是從結構化工具呼叫提取的「原生命令欄位」；再決定執行時是否經過額外包裝（如 `sh -c "..."`）。

2. **建立精確最終狀態驗證器**  
   針對每個操作族系撰寫不依賴字串比對的驗證器，只檢查最終狀態是否正確，這樣才能給予「到達正確狀態」的命令應得分數。

3. **在同視窗配置下收集模型回覆**  
   固定提示、溫度與 effort 標籤，取得每個任務的 trial-0 回覆。記錄模型配置與運作點，因為相同 effort 標籤在不同模型可能對應不同 token 預算。

4. **固定回覆重播於多條命令路徑**  
   將同一份回覆分別餵入：直接執行、加入一個刻意未跳脫的雙引號解析器、以及已揭露邊界（在提示中告知模型存在額外解析層）三種條件。

5. **分解配對分數**  
   計算「損害」＝原始路徑成功率 − 巢狀重播成功率；「補償」＝已揭露邊界成功率 − 巢狀重播成功率；「配對差距」＝原始路徑 − 配對後得分。這三個數字才能說明總分背後的機制。

6. **驗證修復方案**  
   在插值點進行正確跳脫，或改用臨時指令碼執行，觀察是否完全消除運輸損害。這兩種修復都要求呼叫端控制邊界，因此不能只靠模型本身改進。

7. **整合為回歸測試閘道**  
   將上述流程納入 CI，每次更換模型版本、agent 介面或遠端包裝器時，自動比較 raw、nested、disclosed 三條路徑的通過率。

## 潛在風險與注意事項

- **把配對分數當成模型本質屬性**  
  論文顯示 GPT-5.6-sol 的配對差距僅 −3.6 百分點，卻隱藏了 −64.3 百分點的損害與 +60.7 百分點的補償。報告時必須同時揭露模型配置、生成契約、執行路徑、運作點與最終狀態驗證器。

- **忽略下游邊界導致部署後反轉**  
  部署配置可能讓模型排名翻轉。若只比較單一設定，單任務邊距就可能造成錯誤結論。建議至少比較一組可比較配對在 raw 與 nested 條件下的表現。

- **過度依賴靜態分析工具**  
  ShellCheck 在論文中僅標出 34.6% 的巢狀專屬失效，因為每條命令單獨看都語法正確，錯誤出在下游插值。應以執行為基礎的最終狀態驗證為主。

- **已揭露邊界被過度擬合**  
  模型可能在特定提示下學會補償，但換一批私有載荷或不同 userland 後失效。需使用保留載荷、重複抽樣、並在 GNU/BSD 環境下交叉驗證。

- **安全沙箱不足**  
  有害載荷變體包含敵意檔名、萬用字元與變數展開字元，測試時必須在隔離環境執行，避免汙染工作區或意外執行危險命令。

## 與其他技術的整合建議

- **Agent 框架**  
  在 Claude Code、OpenAI Codex CLI、SWE-agent 等工具中，於工具呼叫提取與 shell 包裝之間插入 QuoteBench 的重播層，記錄原始回覆與實際送進 shell 的字串，便於事後比對。

- **CI/CD 管線**  
  將 QuoteBench 作為模型或 harness 變更前的閘道測試：若 nested 條件相對 raw 條件下降超過內部門檻，即阻擋合併，直到在插值點完成正確跳脫或改採臨時指令碼。

- **可觀測性與日誌**  
  每次工具呼叫除了記錄最終成功與否，也記錄生成契約（raw/native）、執行傳輸層（direct/nested）、運作點與 effort 設定，讓維運團隊能追蹤命令路徑失效。

- **其他基準測試**  
  可將 QuoteBench 的交叉設計併入 SWE-bench、BashBench 或終端機基準測試，作為「命令介面貢獻度」的獨立維度，避免把規劃、儲存庫導航與引號處理混為一談。

- **型別化操作探索**  
  若希望從源頭減少字串插值風險，可研究以結構化引數陣列取代單一命令字串，讓 shell 包裝器負責跳脫，而非要求模型學會邊界適應。

## 給不同背景讀者的閱讀建議

**初學者**：先從詞彙表與「為何 Bash 引號會出錯」開始，理解「模型生成一句命令」與「那句命令真正被 shell 執行」之間還隔著序列化、包裝、重新剖析等步驟。重點看適用場景與潛在風險，不必深入統計分解。

**AI 工程師**：聚焦實作步驟與整合建議，特別是固定回覆重播的 harness 實作、插值點跳脫、臨時指令碼修復，以及如何把 raw/native 與 direct/nested 的組合納入現有評估流程。論文的表 2 與交叉設計是實作時的最佳參考。

**研究人員**：仔細閱讀「生成契約 × 執行傳輸層」的交叉設計，學習如何把配對分數拆解為運輸損害與契約條件化補償。可延伸探討型別化操作、多層巢狀解析、不同 userland 的穩健性，或將此方法應用於其他命令語言。

**產品經理**：重點理解「部署配置會重新排序模型」與「配對分數可能隱藏大幅損害」這兩個結論。在要求團隊報告模型表現時，務必請他們同時提供生成契約、執行路徑、運作點與最終狀態驗證方式，避免把單一分數當成選型依據。
