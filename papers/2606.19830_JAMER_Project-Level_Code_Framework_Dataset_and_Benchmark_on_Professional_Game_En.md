## ⚡ TL;DR

現有AI遊戲開發缺乏專業引擎的專案層級資料集與確定性評估方法。
提出JamSet資料集與JamBench基準，以確定性驗證流程從遊戲開發馬拉松篩選Godot專案。
評估顯示模型隨專案規模擴大出現能力斷崖，程式碼代理僅提升編譯率而非執行行為，驗證資料集可有效訓練。

## 摘要翻譯

當前 AI 驅動的遊戲開發（AI-driven game development）在資產生成（asset generation）、遊戲玩法設計（gameplay design）與網頁遊戲程式設計（web-based game coding）方面已取得顯著進展，然而專業遊戲引擎（professional game engine）上的專案層級程式碼工程仍大多未被探索，原因在於缺乏大規模資料集與確定性評估方法（deterministic evaluation methods）。我們提出 JamSet 與 JamBench，首個建構於專業遊戲引擎之上的專案層級遊戲程式碼框架（project-level code framework）資料集與基準測試平台。我們的核心洞見在於，遊戲開發馬拉松（Game Jam）競賽——開發者在嚴苛時間限制下製作完整遊戲的社群活動——能產生數千個適合此用途的開源專案（open-source projects）。基於 Godot 引擎（Godot engine）的純文字格式（text-based format）與無頭執行模式（headless execution mode），我們設計了一條從檔案完整性（file integrity）到執行階段行為收集（runtime behavior collection）的確定性驗證流程（deterministic verification pipeline），從超過 240,000 個程式碼倉庫（repositories）中萃取出 8,133 個已驗證專案。其中，300 個人工驗證專案（manually verified projects）組成 JamBench；其餘則構成 JamSet。JamBench 定義了主題驅動生成（theme-driven generation）與程式碼補全（code completion）任務，透過一個結合編譯通過率（compilation pass rates）、結構完整性分數（Structural Completeness Score, SCS）與行為對齊分數（Behavioral Alignment Score, BAS）等指標的評估流程進行評估。對 9 個前沿模型（frontier models）的評估顯示，隨著專案規模擴大，出現能力斷崖（capability cliff），執行階段通過率（runtime pass rates）從小型專案的 80.4% 下降至大型專案的 5.7%（Task2a）。程式碼代理（Code Agents）提升了編譯通過率，卻未在執行階段行為品質（runtime behavioral quality）上帶來增益，顯示瓶頸在於架構設計（architectural design）而非語法正確性（syntactic correctness）。實驗驗證 JamSet 可作為有效的訓練資料。所有資料與程式碼均已公開釋出。

### 核心貢獻（3～5點）
- 建構首個基於專業遊戲引擎的專案層級遊戲程式碼資料集 JamSet 與基準測試平台 JamBench，填補大規模資料集與確定性評估方法的缺口。
- 設計從檔案完整性到執行階段行為收集的確定性驗證流程，從超過 24 萬個程式碼倉庫中萃取出 8,133 個已驗證專案，並以 300 個人工驗證專案建立高品質評估基準。
- 提出結合編譯通過率、結構完整性分數（SCS）與行為對齊分數（BAS）的多維度評估指標，涵蓋主題驅動生成與程式碼補全任務。
- 揭示前沿模型隨專案規模擴大而出現「能力斷崖」，並發現程式碼代理雖提升編譯通過率卻無法改善執行階段行為品質，指出瓶頸在於架構設計而非語法正確性。
- 驗證 JamSet 作為微調訓練資料的有效性，並完整公開釋出所有資料與程式碼。

### 適合對象
本論文特別適合從事大型語言模型（LLM）與程式碼代理（Code Agents）研究、專案層級程式碼生成與評估的 AI/ML 研究者；關注 AI 輔助遊戲開發、遊戲引擎自動化與開源遊戲資料挖掘的遊戲技術研究者；以及需要大規模高品質遊戲程式碼資料集進行模型訓練、微調與基準測試的開發者與研究團隊。

## 深度分析

#### 方法論解析

本研究的核心方法論建立在 **Godot 引擎（Godot engine）** 的兩項獨特性質之上：其一為 **純文字格式（text-based format）**，其二為 **無頭執行模式（headless execution mode）**。不同於 Unreal Engine 5 或 Unity 等依賴 **二進位格式（binary formats）** 與 **圖形介面（graphical interfaces）** 的專業遊戲引擎（professional game engines），Godot 的 **場景檔案（.tscn）（scene files (.tscn)）**、腳本檔案（.gd）與專案設定檔（.godot）皆為人類可讀的純文字，這使其與大型語言模型（LLM）的處理流程天然相容。更重要的是，Godot 的無頭模式允許在無圖形介面的環境中執行遊戲，從而實現大規模自動化的 **執行階段行為收集（runtime behavior collection）**。

在資料來源方面，作者選擇 **遊戲開發馬拉松（Game Jam）** 作為挖礦標的。這類社群競賽具有嚴格的時間限制（通常為 48 至 72 小時），確保參賽作品在程式碼規模上相對緊湊卻功能完整；同時，開源分享的傳統產生了大量可自由取得的真實世界 **開源專案（open-source projects）**。研究團隊從 GitHub 及 GMTK Game Jam、Godot Wild Jam 等平台蒐集了超過 240,000 個 **程式碼倉庫（repositories）**，並透過統計分析確立品質門檻：專案程式碼行數（game_lines）需大於等於 1,200 行，且第三方外掛行數（addon_lines）需小於 1,000 行，以此過濾掉過於簡陋或高度依賴外部資產的雜訊。

在此基礎上，作者設計了一套四階段的 **確定性驗證流程（deterministic verification pipeline）**：（1）**檔案完整性（file integrity）** 檢查，確保專案結構未損毀；（2）**編譯（compilation）** 正確性驗證；（3）**執行階段（runtime）** 穩定性確認；（4）**執行階段行為（runtime behavior）** 的自動化擷取與比對。這套流程從 240,000 個候選倉庫中萃取出 8,133 個已驗證專案，其中 300 個經 **人工驗證（manually verified）** 的專案構成 **JamBench**，作為標準化的 **基準測試（benchmark）**；其餘 7,833 個專案則處理為多輪對話格式的訓練資料，形成 **JamSet**。

在評估指標設計上，**JamBench** 涵蓋 **主題驅動生成（theme-driven generation）**（Task 1）與多粒度 **程式碼補全（code completion）**（Task 2）。評估維度包含三個層次：**編譯通過率（compilation pass rates）** 作為基礎門檻；**結構完整性分數（SCS）（Structural Completeness Score (SCS)）** 衡量靜態結構覆蓋率，評估生成專案在場景樹、腳本依賴與資源引用上的完整度；**行為對齊分數（BAS）（Behavioral Alignment Score (BAS)）** 則透過比對執行階段的事件日誌、節點狀態與畫面緩衝區特徵，量化生成專案與真實專案之間的 **執行階段行為相似度（runtime behavioral similarity）**。這三層指標由淺入深，從語法正確性過渡到語義與行為層次的對齊，構成了目前遊戲領域最嚴謹的客觀評估框架。

#### 實驗數據解讀

論文對 9 個 **前沿模型（frontier models）** 與 5 組 **程式碼代理（Code Agents）** 配置進行評估，結果揭示了當前 AI 在 **專案層級程式碼框架生成（project-level code framework generation）** 上的根本瓶頸。最顯著的發現是 **能力斷崖（capability cliff）** 現象：在 Task 2（程式碼補全）中，針對小型專案的 **執行階段通過率（runtime pass rates）** 高達 80.4%，但面對大型專案時（Task 2a），該數值驟降至 5.7%。這將近十五倍的落差表明，現有模型在處理跨檔案依賴、場景樹管理與全域狀態協調等複雜 **架構設計（architectural design）** 任務時，能力出現急遽崩解。

更值得深究的是 **程式碼代理（Code Agents）** 的實驗結果。儘管代理機制能顯著提升 **編譯通過率（compilation pass rates）**，卻未能在 **執行階段行為品質（runtime behavioral quality）** 上帶來任何增益。這項負面結果具有高度啟發性：它明確指出當前的瓶頸不在於 **語法正確性（syntactic correctness）**，而在於高階的架構規劃能力。換言之，模型與代理擅長「修復編譯錯誤」，卻不擅長「設計正確的遊戲架構」。這與傳統軟體工程中的觀察一致——單元測試（unit testing）可以捕捉語法與邏輯錯誤，但無法確保遊戲在專案層級的互動行為符合預期。

在資料有效性驗證方面，研究團隊以 **JamSet** 對 **基礎模型（base model）** 進行 **微調（fine-tuning）**。結果顯示，經過微調的模型不僅在編譯通過率與 SCS 上有所提升，更開始採用類似人類開發者的工程實踐，例如 **輸入抽象化（input abstraction）** 與 **全域狀態管理（global state management）**。這證明了 JamSet 並非單純的語料堆疊，而是具備結構性知識的有效訓練資料，能夠引導模型學習專業遊戲開發中的設計模式。

#### 與現有研究的比較

從研究定位來看，JAMER 填補了 **AI 驅動的遊戲開發（AI-driven game development）** 中長期存在的空白。如 Table 1 所示，現有工作在三個維度上各有明顯缺陷：**V-GameGym** 基於 Pygame 進行單一檔案生成，規模雖達 2,219 樣本，但採用 LLM 評分（LLM-based scoring），缺乏 **可重現性（reproducibility）**，且非 **專案層級（project-level）**；**OpenGame** 聚焦網頁遊戲程式設計（web-based game coding），使用 Phaser/JS 框架，同樣依賴 **基於 VLM 的評分（VLM-based scoring）**，主觀性高且僅有 150 個提示；**GameDevBench** 雖然使用 Godot 並具備 **確定性評估方法（deterministic evaluation methods）**（手寫測試腳本），但僅支援局部修改（local modifications），規模僅 132 項任務，缺乏 **可擴展性（scalability）**；**AutoUE** 雖然針對專業的 Unreal Engine 5，但僅 20 項任務且使用 LLM 評分，既不確定亦不可擴展。

相較之下，JAMER 是首個同時滿足以下四項條件的框架：（1）以 **專業遊戲引擎（professional game engine）**（Godot）為目標；（2）涵蓋從無到有的生成與多粒度補全；（3）具備 **確定性驗證流程（deterministic verification pipeline）** 且可擴展至數千專案；（4）提供大規模 **資料集（dataset）**（JamSet）與 **基準測試（benchmark）**（JamBench）。這解決了過往研究在「主觀評分 vs. 規模化」之間的兩難——透過引擎層級的無頭執行，JAMER 以客觀的執行結果取代了昂貴且不可重現的人工或模型評分。

然而，本研究亦存在侷限性。首先，Godot 的純文字格式雖是方法論成立的關鍵，但也意味著此框架難以直接遷移至以二進位格式為主的 Unreal 或 Unity。其次，**執行階段行為（runtime behavior）** 的相似度度量雖然客觀，但對於複雜的互動邏輯（如需要精確時機判斷的戰鬥系統），BAS 可能仍需更細緻的領域特定設計。

#### 可重現性評估

在 **可重現性（reproducibility）** 方面，JAMER 採取了高標準的開放科學實踐。作者明確聲明所有資料與程式碼均公開釋出，這包括 8,133 個已驗證專案的 **JamSet**、300 個 **人工驗證（manually verified）** 專案的 **JamBench**，以及完整的 **確定性驗證流程（deterministic verification pipeline）** 原始碼。這種透明度在遊戲生成領域尤為重要，因為現有替代方案多依賴 **基於 LLM 的評分（LLM-based scoring）** 或 **基於 VLM 的評分（VLM-based scoring）**，其隨機性與模型版本依賴使得實驗難以複製。

本研究的可重現性優勢根植於 Godot **無頭執行模式（headless execution mode）** 的設計。由於行為驗證是在實際引擎中執行並擷取確定的日誌與狀態，而非透過自然語言描述進行相似度判斷，不同研究者在相同版本的 Godot 環境下應能獲得一致的編譯與執行結果。此外，**結構完整性分數（SCS）（Structural Completeness Score (SCS)）** 與 **行為對齊分數（BAS）（Behavioral Alignment Score (BAS)）** 的計算邏輯若完整公開，將使社群能夠在此基礎上進行嚴格的模型比較。

潛在的可重現性挑戰主要來自執行環境的細微差異。Godot 引擎版本更新可能改變場景序列化格式或腳本編譯行為，進而影響驗證流程的跨版本穩定性。此外，無頭模式在無顯示伺服器的伺服器環境中執行時，可能因作業系統或驅動程式差異產生非確定性的執行緒調度行為，儘管這在 Godot 的官方設計中已盡量降低。最後，**JamBench** 中 300 個專案的 **人工驗證（manually verified）** 過程雖為一次性品質控制成本，但其具體的驗證準則與人工介入邊界需要詳細文件化，才能確保後續研究者理解基準測試的篩選邏輯。

#### 未來研究方向

基於 JAMER 所揭示的 **能力斷崖（capability cliff）** 與 **架構設計（architectural design）** 瓶頸，未來研究可沿以下方向展開：

第一，**架構感知生成（Architecture-aware Generation）**。當前模型在大型專案上的失敗模式顯示，單純增加參數量或延長上下文長度並不足以解決問題。未來需要設計能夠顯式規劃場景圖（Scene Graph）、腳本依賴拓撲與 **全域狀態管理（global state management）** 的專用架構，例如結合圖神經網路（GNN）來建模 Godot 節點樹的結構先驗。

第二，**進階程式碼代理（Advanced Code Agents）**。現有 **程式碼代理（Code Agents）** 僅能修復 **語法正確性（syntactic correctness）**，未來應發展具備專案層級規劃能力的代理框架，例如讓代理先產生設計文件（Design Document）或 Unified Modeling Language（UML）式的模組關係圖，再進行實作，並透過迭代式重構（Refactoring）改善 **執行階段行為品質（runtime behavioral quality）**。

第三，**跨引擎方法論遷移**。JAMER 目前僅適用於 Godot，而未來可探索如何將 **確定性驗證流程（deterministic verification pipeline）** 擴展至 Unreal Engine 5 或 Unity。這可能需要開發二進位專案檔案的反向解析工具，或透過引擎外掛將專案狀態匯出為文字格式，以維持與 LLM 的相容性與評估的 **確定性（deterministic）**。

第四，**多代理協作框架（Multi-agent Collaboration）**。鑒於遊戲專案涉及玩法設計（gameplay design）、資產生成（asset generation）與程式碼框架（code framework）等多個相互關聯的層面，可借鏡 **多代理（multi-agent）** 系統的研究，讓專精於不同領域的代理分別負責場景設計、腳本撰寫與行為驗證，透過協作提升整體專案的 **執行階段通過率（runtime pass rates）**。

第五，**規模化法則與資料擴充（Scaling Laws & Data Augmentation）**。JamSet 已驗證其作為訓練資料的有效性，但未來可進一步探究在專案層級遊戲程式碼上的規模化法則——例如，需要多少千個已驗證專案才能讓模型跨越 **能力斷崖（capability cliff）**？此外，可透過程式化內容生成（procedural content generation）或合成資料技術，自動擴充 **JamSet** 的規模與多樣性。

第六，**互動式與玩家模擬評估（Interactive & Player-simulation Evaluation）**。目前的 **行為對齊分數（BAS）（Behavioral Alignment Score (BAS)）** 主要比對執行軌跡，但未來可引入基於強化學習的玩家代理來測試生成遊戲的可玩性（Playability）與難度曲線，從而建立更貼近人類體驗的評估維度。

## 論文問答

**Q1：JAMER 旨在解決的核心問題是什麼？**
A：JAMER 旨在填補 AI 驅動遊戲開發中，針對專業遊戲引擎進行專案層級程式碼框架生成的研究空白。儘管現有技術在資產生成、玩法設計與網頁遊戲程式設計方面已有長足進展，但由於缺乏大規模資料集與確定性評估方法，專業引擎上的專案層級程式碼工程始終未能獲得系統性探索。本研究透過建構 JamSet 與 JamBench，首次為該領域提供可擴展的資料基礎與客觀的評估基準，使模型能力得以被精確衡量與比較。

**Q2：為何現有的評估方法無法滿足遊戲專案層級程式碼的需求？**
A：現有方法之所以不足，是因為遊戲行為在專案層級具有高度上下文依賴性，不存在簡單的輸入輸出對應關係，導致標準單元測試難以捕捉執行階段的互動行為。手寫測試腳本雖然精確且可重現，但成本過高，無法擴展到大規模資料集；而基於 VLM 或 LLM 的評分雖具可擴展性，卻帶入主觀性且缺乏可重現性。因此，遊戲領域亟需一種既能自動化擴展、又能客觀驗證執行階段行為的確定性評估框架。

**Q3：在專業遊戲引擎上進行專案層級程式碼框架生成為何重要？**
A：專案層級的程式碼框架是連結美術資產、玩法規則與底層系統的核心橋樑，其複雜度遠超單一檔案或輕量級網頁遊戲的程式設計。掌握此層級的生成能力，是推動 AI 驅動開發從輔助工具走向完整可執行遊戲專案自動化的關鍵一步。若缺乏相關資料集與評估基準，將嚴重限制模型在真實遊戲開發場景中的應用，並使研究者無法客觀追蹤技術進展。

**Q4：JAMER 的核心方法論是什麼？**
A：JAMER 的核心方法在於利用遊戲開發馬拉松（Game Jam）產生的大量開源專案，並基於 Godot 引擎的純文字格式與無頭執行模式，建立一套從檔案完整性、編譯正確性、執行穩定性到執行階段行為收集的確定性驗證流程。研究團隊從超過二十四萬個程式碼倉庫中，透過層層自動化篩選，提煉出 8,133 個已驗證專案，並從中選出 300 個人工驗證專案組成基準測試集 JamBench，其餘則作為訓練資料集 JamSet。此流程確保了資料品質與評估結果的客觀性，為專案層級的遊戲程式碼生成提供了可擴展的基礎建設。

**Q5：本研究的主要創新貢獻有哪些？**
A：本研究的主要創新包含三個層面：首先，首次建構了專業遊戲引擎上的專案層級遊戲程式碼框架資料集與基準測試；其次，設計了從靜態檔案到動態執行階段行為的確定性驗證流程，克服了遊戲領域長期缺乏客觀評估標準的困境；第三，提出了結構完整性分數（SCS）與行為對齊分數（BAS）等綜合評估指標，能同時衡量生成結果的靜態架構覆蓋率與動態執行相似度。這些創新不僅提供了可重現的評估框架，也為後續研究設立了明確的效能衡量標準。

**Q6：作者為何選擇 Godot 引擎與遊戲開發馬拉松作為資料來源？**
A：作者選擇 Godot 引擎是因為其採用完全純文字的專案格式，包括場景檔案（.tscn）、腳本（.gd）與專案設定皆為人類可讀的明文，極適合大型語言模型處理，且其無頭執行模式允許在無圖形介面的環境下自動化執行與收集執行階段行為。至於選擇遊戲開發馬拉松，則是因為其嚴格的時間限制確保了參賽作品既精簡又完整，而開源分享的傳統則提供了大規模且可自由取得的真實世界資料。這兩項選擇相輔相成，使得建立大規模、高品質且可自動驗證的遊戲專案資料集成為可能。

**Q7：JamBench 定義了哪些任務，評估又是如何進行的？**
A：JamBench 定義了兩大類任務：主題驅動的從零開始生成（Task 1）以及多粒度的程式碼補全（Task 2），後者涵蓋不同規模與複雜度的專案。評估透過結合編譯通過率、結構完整性分數（SCS）與行為對齊分數（BAS）的綜合流程進行，其中 SCS 測量靜態結構覆蓋率，而 BAS 則衡量執行階段行為與真實專案的相似度。這種多維度評估方式能夠區分語法正確性、架構完整性與實際執行品質，提供更全面的模型能力診斷。

**Q8：模型評估中最重大的發現是什麼？**
A：評估九個前沿模型的結果揭示了隨著專案規模擴大而出現的「能力斷崖」現象：在 Task 2a 中，執行階段通過率從小型專案的 80.4% 驟降至大型專案的 5.7%。此外，程式碼代理雖然能顯著提升編譯通過率，卻未能在執行階段行為品質上帶來任何改善，這明確指出當前的瓶頸在於架構設計能力，而非語法正確性。這些發現凸顯了現有模型在處理複雜專案層級遊戲程式碼時的根本限制。

**Q9：在 JamSet 上進行微調的實驗揭示了什麼？**
A：在 JamSet 上進行微調的實驗驗證了該資料集作為訓練資料的有效性：相較於基礎模型，微調後的模型不僅提升了編譯通過率與結構完整性，還學會了採用人類工程實踐，例如輸入抽象化與全域狀態管理。這顯示 JamSet 不僅能提供語法層面的學習信號，更能引導模型掌握更高階的軟體架構模式。此結果證明高品質的專案層級資料對於改善模型在專業遊戲引擎上的生成能力具有實質助益。

**Q10：JAMER 可應用於哪些實務場景？**
A：JAMER 可應用於多種實務場景，包括作為訓練與微調遊戲程式碼生成模型的標準化資料來源，以及作為評估 AI 代理在專業遊戲引擎上進行專案層級開發能力的客觀基準。開發者與研究人員能利用 JamBench 的確定性驗證流程，對自動生成的遊戲專案進行大規模且無需人工介入的品質檢驗。此外，該框架也適用於持續整合與持續部署（CI/CD）環境中，作為 AI 生成遊戲程式碼的自動化測試基礎設施。

**Q11：此框架具備哪些特性，使其適合實際產品開發？**
A：此框架適合實際產品開發的關鍵在於其確定性與可擴展性：Godot 的無頭執行模式允許在伺服器環境中自動化執行與驗證，無需昂貴的圖形運算資源即可進行大規模測試。從檔案完整性到執行階段行為的逐層驗證機制，提供了明確且可重現的品質閘道，有助於在生產流程中及早發現語法錯誤與行為偏差。這種自動化且客觀的評估能力，對於需要反覆迭代與快速驗證的 AI 驅動遊戲開發工具而言至關重要。

**Q12：這項工作對 AI 驅動遊戲開發的廣泛領域有何影響？**
A：JAMER 將 AI 驅動遊戲開發的研究焦點從網頁遊戲、單一檔案生成或局部修改，推進到專業引擎上的完整專案層級框架生成，大幅拓展了該領域的研究邊界。透過揭示模型在架構設計上的瓶頸而非僅限於語法層面，本研究為未來模型開發指明了關鍵的改進方向。此外，公開釋出的資料集與評估工具將促進學術界與產業界的協作，加速可執行、可互動遊戲專案自動生成技術的整體進展。

**Q13：JAMER 存在哪些主要限制？**
A：本研究的主要限制之一在於目前僅聚焦於 Godot 引擎，雖然這是出於其純文字格式與無頭模式的技术可行性考量，但 Unity 與 Unreal Engine 等主流引擎仍依賴二進位格式與圖形介面，難以直接套用相同流程。此外，遊戲開發馬拉松的限時特性雖確保了專案的完整性，但也意味著這些專案規模相對精簡，可能無法完全代表大型商業遊戲的複雜度。這些限制意味著目前的框架在處理更大型、更多樣化的專業開發場景時，仍需進一步的擴展與調整。

**Q14：失敗案例揭示了當前模型的哪些問題？**
A：失敗案例清楚地顯示，當前模型在面對大型專案時，執行階段通過率僅有 5.7%，顯示其無法有效處理複雜的專案層級架構設計。即使引入程式碼代理來輔助生成，雖能修復語法錯誤以提高編譯通過率，卻完全無法改善執行階段的行為品質，表明代理僅能進行表面性的語法修補。這些失敗模式共同指出，現有模型缺乏對遊戲系統整體架構、模組互動與狀態管理的深層理解，這正是邁向實用化必須克服的核心障礙。

**Q15：未來有哪些有前景的研究方向？**
A：未來研究可朝幾個方向拓展：首先，開發能夠理解並設計整體架構的代理程式，而非僅限於語法層級的修復，以解決目前的能力斷崖問題；其次，探索如何將此確定性驗證框架擴展至 Unity 或 Unreal 等其他專業引擎，儘管其二進位格式帶來顯著挑戰；最後，結合多模態生成技術，同時處理程式碼框架、美術資產與玩法設計，朝向端到端的完整遊戲專案自動化開發邁進。這些方向將有助於縮小 AI 輔助開發與真實商業遊戲製作之間的差距。

## 實務應用指南

### 適用場景

1. **獨立遊戲工作室之自動化原型開發**：利用主題驅動生成（theme-driven generation）能力，在遊戲開發馬拉松（Game Jam）或前期概念驗證階段，由模型根據指定主題快速產出可執行的 Godot 專案層級程式碼框架，縮短從發想到可遊玩原型的時間。
2. **Godot 引擎智慧程式碼輔助工具**：將 JamSet 微調後的模型整合至 VS Code 或 Godot 內建腳本編輯器，提供跨檔案、跨場景的程式碼補全（code completion），特別適用於需要維護全域狀態管理（global state management）與輸入抽象化（input abstraction）的中大型專案。
3. **遊戲開發教育與互動教材生成**：針對教學場景，利用確定性驗證流程（deterministic verification pipeline）自動檢驗學生產出的專案完整性，並以結構完整性分數（SCS）與行為對齊分數（BAS）作為量化學習成效的依據。
4. **開源遊戲專案品質篩選與策展平台**：借鏡本研究從二十四萬個程式碼倉庫（repositories）中篩選出八千餘個驗證專案的方法論，建立自動化的開源遊戲索引系統，協助平台過濾低品質或無法執行的專案。
5. **遊戲化企業內部工具與嚴肅遊戲（Serious Games）快速建置**：針對非娛樂用途的 2D 互動應用或訓練模擬器，透過專案層級程式碼框架生成，在 Godot 無頭執行模式（headless execution mode）下完成自動化測試與部署。

### 實作前置條件

- **資料需求**：需取得 JamSet 作為訓練資料（或自行從 itch.io、GitHub 等管道蒐集遊戲開發馬拉松之開源專案），並具備足夠儲存空間存放原始倉庫與驗證後之中繼資料。若建構自有資料集，建議參考本研究之篩選條件（如遊戲主程式碼行數 ≥ 1,200、插件依賴 < 1,000 行）。
- **運算資源**：微調前沿模型（frontier models）需具備 A100 / H100 等級之 GPU 叢集；執行確定性驗證流程需可平行化運行之 Linux 伺服器叢集，以支援 Godot 無頭執行模式進行大規模執行階段行為收集（runtime behavior collection）。
- **技術能力**：團隊需熟悉 Godot 引擎與 GDScript、具備 LLM 微調與 MLOps 實務經驗，並能設計 CI/CD 管線以串接檔案完整性檢查、編譯驗證與執行階段測試。此外，需具備沙箱化（sandboxing）任意開源程式碼之資安意識。

### 實作步驟建議

1. **環境建置與資料準備**：部署 Godot 引擎之無頭執行環境，下載 JamSet 或依據論文 3.1 節之品質門檻爬取並清洗遊戲開發馬拉松之開源專案，確保場景檔案（.tscn）、腳本檔案（.gd）與專案設定檔（.godot）皆為可讀之純文字格式（text-based format）。
2. **建立確定性驗證流程**：依序實作四階段驗證管線——檔案完整性（file integrity）檢查、編譯正確性（compilation pass rates）驗證、執行階段穩定性測試，以及執行階段行為相似度（runtime behavioral similarity）比對。此為確保資料品質與評估客觀性之核心。
3. **模型選型與領域微調**：選擇適當之基礎模型（base model），使用 JamSet 之多輪對話與專案結構資料進行微調（fine-tuning）。實驗顯示，於 JamSet 上微調可顯著提升編譯通過率與結構完整性分數（SCS）。
4. **任務對齊與評估指標落地**：依產品需求選擇主題驅動生成（Task 1）或程式碼補全（Task 2），並實作 SCS 與 BAS 評估模組。針對大型專案，建議增設階層式生成策略，以緩解論文所發現之能力斷崖（capability cliff）問題。
5. **部署與人機協作迭代**：將模型以 API 或 IDE 擴充形式部署。導入程式碼代理（Code Agents）協助語法正確性（syntactic correctness）修復，但須認知其對執行階段行為品質（runtime behavioral quality）無顯著增益；瓶頸在於架構設計（architectural design），因此應保留資深工程師進行架構複審之環節。

### 潛在風險與注意事項

- **能力斷崖與專案規模**：論文顯示，當專案規模擴大時，執行階段通過率（runtime pass rates）從小型專案的 80.4% 驟降至大型專案的 5.7%。實務上應避免直接生成超過模型能力上限之單體專案，改採模組化生成或限制初始生成範圍。
- **過度依賴程式碼代理進行語法修復**：程式碼代理雖能提升編譯通過率，但無法改善執行階段行為品質。若產品僅以「能否編譯」作為驗收標準，將導致產出大量結構完整但無法正確運作之「殭屍專案」。
- **執行任意開源程式碼之安全性**：於無頭執行模式中自動執行來自公開倉庫之遊戲邏輯，存在惡意程式碼執行風險。務必於隔離容器或虛擬機沙箱中運行，並限制網路與檔案系統權限。
- **資料雜訊與品質不均**：並非所有遊戲開發馬拉松之開源專案皆具備生產級品質。若未經嚴格篩選（如人工驗證專案之人工驗證機制）即投入訓練，可能導致模型學習到不良架構模式。
- **避免以 LLM/VLM 評分取代引擎驗證**：遊戲行為具有高度上下文依賴性（context-dependent），切勿以主觀之 LLM-based scoring 或 VLM-based scoring 作為最終品質依據，應堅持以 Godot 引擎執行結果作為確定性評估方法（deterministic evaluation methods）。

### 與其他技術的整合建議

- **整合 CI/CD 與版本控制**：將確定性驗證流程封裝為 GitHub Actions 或 GitLab CI 之 Job，於每次提交時自動執行檔案完整性檢查與無頭執行測試，作為遊戲專案之持續整合閘道。
- **結合檢索增強生成（RAG）**：以 JamSet 中驗證通過之專案作為向量資料庫，讓模型在生成專案層級程式碼框架時，能檢索並參考高品質之人類工程實踐（如輸入抽象化、全域狀態管理模式）。
- **串接資產生成管線**：將本框架與生成式模型（generative models）產出之紋理（textures）、精靈圖（sprites）結合，形成「資產生成 → 程式碼框架生成 → 確定性驗證」之端到端 AI 驅動遊戲開發（AI-driven game development）工作流。
- **多代理架構補強架構設計**：鑒於單一程式碼代理難以處理架構設計瓶頸，可導入多代理系統（multi-agent）分別負責場景規劃、腳本生成與測試驗證，以提升大型專案之生成品質。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先聚焦論文對 Godot 純文字格式與無頭執行模式之介紹，理解「專案層級」與「單一檔案程式碼生成」的差異。無需深入 SCS 與 BAS 之數學細節，重點掌握「為何遊戲行為無法用單元測試（unit testing）簡單驗證」這一核心概念即可。
- **AI 工程師**：請優先研讀確定性驗證流程之實作細節，以及程式碼代理在語法正確性與執行階段行為品質間的落差。這有助於你在設計類似系統時，避免將「編譯通過」誤設為唯一優化目標，並能針對架構設計瓶頸設計更有效的獎勵機制或後處理策略。
- **研究人員**：建議深入分析資料集建構方法論——從二十四萬個倉庫篩選至八千餘個驗證專案之過程，以及能力斷崖隨專案規模擴大之現象。論文揭示的「編譯成功不等於執行正確」對整個程式碼生成領域（從函式層級到專案層級）皆具方法論啟發，可作為後續遊戲或一般軟體工程評估研究之基石。
- **產品經理**：請著重評估本框架在縮短遊戲原型開發週期上的商業價值，同時正視 Godot 引擎在開源生態系之成長動能。導入時應將「自動化生成」定位為輔助而非取代開發者，特別是在大型專案中需保留人類架構師把關，並將確定性驗證流程視為降低技術債與維護成本之關鍵基礎建設。
