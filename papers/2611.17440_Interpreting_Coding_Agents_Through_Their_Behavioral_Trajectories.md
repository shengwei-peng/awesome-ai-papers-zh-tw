## 深度分析

#### 方法論解析

本論文提出了一套系統化的方法論框架，用於解析異質性程式碼代理（coding agent）的執行軌跡（execution trajectory），其核心方法可分為三個層次：

**一、軌跡正規化流程（Trajectory Normalization Pipeline）**

作者面對的首要挑戰在於不同代理執行框架（agent harness）所產生的執行追蹤（execution trace）具有異質性——工具名稱（tool name）、指令格式（command format）、記錄綱要（schema）皆不相同。為解決此問題，作者設計了一個確定性解析器（deterministic parser），採用基於規則（rule-based）的模式匹配方法，將原始的 shell 指令、腳本與 API 工具調用映射至四個核心屬性：

1. **主要操作（Primary Operation）**：分為十個類別，包含探索（exploration）、搜尋（search）、檔案讀取（file reading）、檔案變更（file mutation）、正式測試執行（formal test execution）等高階動作（high-level action）。
2. **目標檔案角色（Target File Role）**：區分被操作的檔案在任務中的功能定位。
3. **變更類型（Mutation Type）**：標記修改的語意性質。
4. **讀取模式（Read Mode）**：描述代理獲取資訊的方式。

此設計的關鍵在於將語意動作（semantic action）與實作細節（implementation detail）解耦，使得跨系統分析（cross-system analysis）成為可能。

**二、稽核機制（Audit Mechanism）**

為驗證解析器的準確性，作者採用六模型共識參考（six-model consensus reference）對 500 個事件進行人工稽核。這種共識標註策略有效降低了單一模型的偏誤風險，為解析器的可靠性提供了實證基礎。

**三、分析設計（Study Design）**

作者將資料結構化為三個分析集：
- **完整 Python 語料庫**：111 個配置、413 個儲存庫，用於跨儲存庫行為檢索。
- **多語言集**：16 個前沿配置（frontier configuration），用於跨語言分析。
- **受控面板**：110 個 2026 年春季 Python 任務的多輪執行結果，用於結果配對比較（outcome-matched comparison）、分割半數零控制（split-half null control）以及世代與支架比較。

值得注意的概念區分是「代理堆疊」（agent stack）的定義——指完整的部署系統，包含基礎模型、支架執行框架（如 SWE-agent-like、Claude Code、Codex）、推理強度（reasoning effort）層級與 API 解碼參數。同一基礎模型在不同支架下被視為不同堆疊，這一界定對後續分析至關重要。

#### 實驗數據解讀

**一、規模與覆蓋面**

論文分析的資料規模相當龐大：143,209 條完整執行軌跡（134,329 條 Python、8,880 條多語言），涵蓋 125 個代理配置與 117 個獨立模型。這一規模在程式碼代理行為分析領域屬於罕見的大規模實證研究，為統計結論的穩健性提供了基礎。

**二、解決率與行為的解耦**

最核心的發現是：解決率（solve rate）無法唯一刻畫代理行為。具備相似解決率的配置在工作流程（workflow）上可能存在顯著差異——包括搜尋頻率、檢查方式、編輯模式與測試驗證（verification）策略。這一發現挑戰了傳統基準測試僅以二元結果（binary outcome）排名系統的做法，揭示了「黑箱評估」（black-box evaluation）的侷限性。

**三、行為輪廓的識別能力**

聚合行為輪廓（aggregate behavioral profile）展現出驚人的識別力——即使不使用任務結果、令牌數量（token count）或原生工具名稱作為檢索特徵（retrieval feature），仍能在不相交儲存庫集合（disjoint repository set）與不同程式語言間檢索出對應的代理堆疊。這意味著行為模式本身即構成代理的「指紋」，具有跨情境的穩定性。

**四、支架與推理強度的系統性影響**

透過前沿模型與支架的比較分析，作者證實：
- **支架選擇（scaffold choice）**會系統性地改變代理的搜尋、編輯與測試行為模式。
- **推理強度（reasoning effort）**同樣會影響探索、修改（modification）與驗證行為的分佈。

這兩個發現具有重要的實務意涵：評估程式碼代理時，必須將整個部署系統納入考量，而非僅關注基礎模型的能力。

**五、潛在混淆變項的坦誠聲明**

作者明確指出任務組成（task composition）在跨儲存庫設定中未被完全控制，這是一項重要的方法論自覺。這種坦誠有助於讀者正確解讀結論的適用範圍。

作者坦誠承認的侷限包括：

- 解析器依賴規則式方法，對於高度新穎的工具調用可能失效。

相較於使用大型語言模型進行軌跡分類的方法，本論文的規則式方法在確定性與可解釋性上具有優勢，但在面對未見過的代理框架時可能需要持續更新規則庫。

- 是否能透過行為輪廓預測代理在未見任務上的表現？

**二、動態行為分析**

本論文聚焦於聚合輪廓，未來可探索：
- 軌跡內的時序模式（temporal pattern）與階段轉換（phase transition）。
- 失敗軌跡與成功軌跡在行為序列上的結構性差異。
- 代理在遭遇瓶頸時的恢復策略與行為調整。

**三、跨領域泛化**

將行為分析方法擴展至：
- 非程式碼領域的代理任務（如網頁導航、資料分析）。
- 多代理協作場景下的行為互動模式。
- 人機協作中代理行為的可解釋性。

**四、解析器的演進**

規則式解析器的維護成本是實際部署的挑戰，未來可考慮：
- 結合機器學習方法處理未見過的工具調用模式。
- 開發增量式更新機制以適應新興代理框架。
- 建立標準化的代理行為描述語言（DSL）。

**五、行為導向的代理設計**

本論文的發現對代理設計具有直接啟示：
- 是否能根據任務特性自動選擇最佳支架？
- 能否透過行為輪廓診斷代理的特定弱點並進行定向改進？
- 行為多樣性是否能作為代理穩健性的指標？

**六、評估基準的革新**

最終，本論文呼籲程式碼代理評估應從單純的二元結果轉向多維度的行為分析，這將推動：
- 結合行為指標的新一代基準測試設計。
- 代理開發中的行為優化目標設定。
- 學術界與產業界對代理品質的共識標準建立。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文聚焦於程式碼代理評估中「只看結果、不看過程」的盲點。傳統基準（如 SWE-bench）將複雜的多步互動簡化為二元結果（通過或未通過測試），僅產出解決率作為排名依據，卻無法揭示代理究竟如何完成任務。作者主張，僅憑解決率無法診斷失敗原因，也無法理解不同模型與支架設計之間的差異，因此需要一套能橫跨異質代理介面、共享的行為表示方法。

**Q2：為什麼現有的程式碼代理評估方法不足以理解代理行為？**
A：現有方法主要依賴工具名稱或原始指令進行比較，但不同代理執行框架（harness）會暴露不同的工具、使用不同的指令格式，並以不同的綱要記錄互動，這使得直接比較混雜了語意動作與實作細節。此外，僅以解決率排名會忽略支架設計對工作流程與成功率的實質影響，因為行為取決於整個系統，而非僅僅是底層模型本身。

**Q3：理解代理行為軌跡為何重要？**
A：理解行為軌跡對於診斷失敗、比較不同模型解決問題的策略，以及評估支架設計的影響至關重要。透過分析探索、修改與驗證等高階動作，研究者與工程師能識別瓶頸階段（例如搜尋、閱讀、編輯中的弱點），並針對性地改進代理系統。這種過程層級的洞察也能幫助區分「看似表現相近、實則運作方式迥異」的代理配置，避免被單一指標誤導。

**Q4：論文提出的核心方法是什麼？**
A：論文提出了一套確定性的軌跡正規化流程，核心是一個基於規則的解析器，能將異質的執行追蹤事件映射到共通分類法下的高階動作。該解析器將每個工具呼叫與其執行輸出配對，並依四個核心屬性進行分類：主要操作（十類）、目標檔案角色、變更類型與讀取模式。此方法使跨 125 個代理配置、117 個模型的 143,209 條執行軌跡得以在統一的語意層次上進行比較。

**Q5：基於規則的解析器相較於既有方法有何關鍵創新？**
A：關鍵創新在於建立一個獨立於特定執行框架的共享表示，捕捉「代理在做什麼」而非「特定執行框架如何記錄該動作」。作者以六模型共識參考對 500 個事件進行稽核，確保解析器的預測品質。此外，該解析器是確定性的，這意味著相同輸入會產生相同輸出，有助於可重現性與大規模分析，這也是論文釋出解析器、標註流程與已標註軌跡子集供社群使用的基礎。

**Q6：動作分類分類法有哪些關鍵設計選擇？**
A：分類法採用四個核心屬性的多維度設計：主要操作涵蓋探索、搜尋、檔案讀取、檔案變更、形式測試執行等十類；目標檔案角色區分原始碼、測試、設定檔等；變更類型描述修改的本質；讀取模式則捕捉代理如何檢視內容。這種設計刻意避免依賴工具名稱或令牌數量等表面特徵，而是聚焦於語意動作，使跨系統分析得以成立。

**Q7：實驗使用了哪些資料集與基準？**
A：實驗分析來自 SWE-rebench 排行榜的執行軌跡，涵蓋 860 個 Python 任務（橫跨 413 個儲存庫，時間跨度為 2025 年 1 月至 2026 年 5 月）以及 111 個多語言任務（涵蓋 Go、Java、Python、Rust、TypeScript）。總計 143,209 條完整執行軌跡（Python 134,329 條、多語言 8,880 條），來自 125 個代理配置與 117 個獨立模型。研究還設計了固定的 110 個 2026 年春季 Python 任務子集，作為結果配對比較與分裂半數零控制之用。

**Q8：論文的主要發現有哪些？**
A：主要發現有三：第一，解決率相近的代理在工作流程上仍可能有巨大且可重現的差異，特別是在搜尋、檢查、編輯與測試的頻率上；第二，在不使用任務結果、令牌數量或原生工具名稱作為特徵的情況下，聚合行為輪廓仍能在不相交儲存庫集合與不同程式語言間檢索出對應的代理堆疊；第三，支架選擇與推理強度會系統性地改變代理的探索、修改與驗證模式。

**Q9：論文進行了哪些受控比較與消融式分析？**
A：論文採用結果配對比較設計，固定任務與結果，僅比較行為差異，以隔離工作流程差異與效能及變異性。此外還使用分裂半數零控制來驗證行為輪廓的穩健性。在世代與支架比較中，作者檢視前沿模型與不同代理支架（如 SWE-agent-like、Claude Code、Codex）下的行為模式，顯示支架與推理強度對行為有系統性影響，而非隨機波動。

**Q10：這項研究的實際應用情境為何？**
A：實際應用包括：診斷代理失敗的具體階段（例如卡在搜尋或編輯），協助開發者選擇合適的支架與模型組合；用於基準設計者建立更細緻的多維度評估，而非僅依賴二元結果；以及幫助研究社群理解不同代理堆疊在跨儲存庫、跨程式語言情境下的行為穩定性，從而做出更明智的部署決策。

**Q11：對產品開發與代理設計有哪些考量？**
A：產品開發者可利用行為輪廓來評估自家代理與競爭對手的差異，識別可改進的環節（例如過度探索或測試不足）。在設計新支架時，可透過行為指標預測其對工作流程的影響，而無需等待大量任務結果。此外，確定性解析器與標註流程的釋出，使企業能在內部資料上重現分析，進行客製化的代理行為稽核。

**Q12：這項研究對程式碼代理領域的更廣泛影響是什麼？**
A：這項研究推動了從「結果導向」轉向「過程導向」的評估範式，鼓勵後續工作採用更豐富的行為分類法與過程表示。它也凸顯了代理能力與執行框架、工具定義、執行環境緊密耦合的事實，呼籲研究者在報告結果時應清楚說明完整代理堆疊。釋出的解析器與資料將成為該領域的共享基礎設施，促進可重現的跨實驗室比較。

**Q13：作者承認哪些研究限制？**
A：作者明確指出，在跨儲存庫設定中，任務組成（task composition）並未完全受控，這構成潛在的混淆變項，可能影響行為輪廓的檢索結果。此外，研究僅檢視可觀察的執行工作流程，並未深入分析代理的內部推理過程，因此結論限於「代理做什麼」而非「代理為什麼這樣做」。最後，雖然稽核了 500 個事件，但解析器在更大規模或新型代理上的表現仍待驗證。

**Q14：解析器或方法可能面臨哪些失敗案例或邊界情境？**
A：基於規則的解析器在面對高度非標準化的工具呼叫、新型代理框架的指令格式，或混合多種語意動作的複雜指令時，可能出現分類錯誤。當代理使用模糊的指令（例如同時執行搜尋與編輯的腳本）時，四個核心屬性的劃分也可能不夠細緻。此外，對於極少數或全新的代理配置，行為輪廓可能不足以穩定檢索，因為訓練樣本稀缺。

**Q15：未來的研究方向有哪些？**
A：未來方向包括：將行為分析擴展到內部推理過程，結合可觀察工作流程與思維鏈以獲得更全面的理解；發展能控制任務組成的實驗設計，以更嚴謹地驗證跨儲存庫行為穩定性；以及將此方法應用於更廣泛的軟體工程任務（如測試生成、程式碼審查），探索行為輪廓在代理選擇、除錯與教育訓練中的應用。此外，也可探索將確定性解析器與基於大型語言模型的分類器結合，以處理更複雜的邊界案例。

## 實務應用指南

### 適用場景

1. **企業內部程式碼代理選型與採購決策**：當企業要在多個程式碼代理（如 Claude Code、Codex、自建 SWE-agent 變體）之間做選擇時，僅憑解決率無法區分行為差異。導入此行為軌跡分析框架，可在相同任務集上比較各代理的探索、修改、驗證模式，找出最符合團隊工作流程的方案（例如偏好「先大量搜尋再精準修改」的代理 vs.「快速迭代修改」的代理）。

2. **代理失敗診斷與事故根因分析**：當代理在 CI/CD 或 PR 自動化流程中產生錯誤時，可使用此解析器將原始執行追蹤轉為高階動作序列，快速定位失敗發生在哪個階段（搜尋不足、編輯錯誤、測試未執行等），比直接閱讀數萬行日誌更有效率。

3. **支架（Scaffold）設計的 A/B 測試與最佳化**：研究團隊或代理開發者可透過此框架量化不同支架設計對行為的影響——例如比較「強制先讀檔再編輯」的支架 vs.「允許直接編輯」的支架，在探索、修改、驗證動作比例上的差異，作為支架迭代的客觀依據。

4. **跨模型/跨版本的回歸監控**：當組織升級底層模型（例如從 GPT-5 換到 GPT-6，或調整推理強度）時，可定期對代理堆疊做行為輪廓比對，自動偵測行為漂移（behavior drift），避免僅看解決率而忽略「模型變安靜了」或「模型不再驗證」等隱性退化。

5. **代理行為合規與安全稽核**：在金融、醫療等受監管產業，可利用此分類法檢查代理是否遵循預定的工作流程（例如「修改前必須先讀取目標檔案」、「變更後必須執行測試」），作為內部治理與合規報告的證據。

### 實作前置條件

**資料需求**
- **軌跡資料來源**：可從 Hugging Face 上的 SWE-rebench Leaderboard Trajectories 取得公開資料（134,329 條 Python 軌跡、8,880 條多語言軌跡），或自行收集代理在內部任務上的執行追蹤。原始格式需包含結構化訊息、工具呼叫與環境觀察結果。
- **代理介面規格**：需取得所用代理框架（harness）的工具呼叫綱要（schema），以便解析器能正確對應到高階動作分類。
- **標註參考集**：建議準備至少 500 筆事件的六模型共識標註作為稽核基準，可參考論文釋出的已標註軌跡子集。

**運算資源**
- 解析階段為純規則匹配，無需 GPU；單機 CPU 即可處理十萬級軌跡。
- 行為輪廓聚合與檢索分析屬於輕量統計/分類任務，標準工作站即可勝任。
- 若要擴展到更大規模或加入嵌入式檢索，則建議配置具備 16GB 以上記憶體的機器。

**技能門檻**
- **必備**：Python 程式設計、正則表達式與模式匹配、pandas 資料處理、基本統計分析。
- **建議**：熟悉至少一種代理框架（如 SWE-agent、Claude Code、OpenHands）的內部運作；具備 sklearn 或類似工具的分類/檢索經驗。
- **加分**：對軟體工程基準測試（如 SWE-bench、SWE-rebench）有實務理解，能區分任務組成（task composition）對行為的潛在混淆效應。

### 實作步驟建議

**步驟一：環境建置與資料取得**
- 複製 GitHub 倉庫 `SWE-rebench/trajectory-analyzer`，安裝依賴。
- 從 Hugging Face 下載 SWE-rebench Leaderboard Trajectories，確認涵蓋目標代理堆疊的軌跡。
- 若使用內部代理資料，確保軌跡格式與解析器相容（訊息、工具呼叫、觀察結果需有唯一識別碼對應）。

**步驟二：軌跡正規化與動作分類**
- 執行確定性解析器（deterministic parser），將每個工具呼叫對應到四個核心屬性：主要操作（10 類）、目標檔案角色、變更類型、讀取模式。
- 對解析結果進行稽核：抽取 500 筆事件，使用六模型共識進行比對，計算分類一致率（建議目標 ≥ 90%）。
- 若一致率不足，針對錯誤案例擴充規則集並重新迭代。

**步驟三：聚合行為輪廓建構**
- 為每個代理堆疊計算聚合行為輪廓，例如：探索動作佔比、檔案讀取次數、編輯動作分佈、測試執行頻率等。
- 採用結果配對比較（outcome-matched comparison）設計：固定解決率相近的代理對，比較其行為差異，避免將表現差異誤判為行為差異。

**步驟四：跨場域行為檢索驗證**
- 在不相交儲存庫集合與不同程式語言上測試行為輪廓的檢索能力——給定一段軌跡的行為輪廓，能否正確識別其所屬的代理堆疊？
- 注意：跨儲存庫設定中任務組成未完全控制，需在解讀結果時將此列為潛在混淆變項。

**步驟五：世代與支架效應分析**
- 針對前沿模型與不同支架配置，量化推理強度（reasoning effort）對行為的系統性影響。
- 產出可解釋的視覺化圖表（如動作比例熱圖、階段耗時分佈），便於決策者理解。

**步驟六：產品化整合與持續監控**
- 將解析流程包裝為 CLI 工具或 API 服務，嵌入內部 MLOps 平台。
- 設定定期排程：每當新模型或新支架上線，自動產生行為輪廓並與歷史基準比對，觸發漂移警報。

### 潛在風險與注意事項

**風險一：解析器覆蓋率不足**
- **問題**：規則式解析器對新型工具呼叫格式或自訂指令的覆蓋率有限，可能將未知動作歸類為「其他」，造成行為輪廓失真。
- **緩解**：建立持續標註回饋機制；定期以六模型共識稽核新樣本；對「其他」類別設定比例上限警報。

**風險二：任務組成混淆（Task Composition Confound）**
- **問題**：論文明確指出，跨儲存庫設定中任務組成未完全控制，行為輪廓的差異可能部分來自任務特性而非代理本身。
- **緩解**：在跨場域分析中採用固定任務子集做對照；報告結果時明確標註此限制；對關鍵決策輔以任務配對實驗。

**風險三：解決率相近不等於行為可比較**
- **問題**：結果配對比較雖控制了表現變項，但同一解決率可能來自截然不同的工作流程，差異可能源自隨機變異而非系統性行為。
- **緩解**：採用分割半數零假設檢定（split-half null control）驗證差異的穩定性；多次重複實驗取平均。

**風險四：忽略內部推理過程**
- **問題**：論文明確表示未檢查推理軌跡（reasoning traces），僅分析可觀察的執行工作流程，可能錯失模型「思考」層面的差異。
- **緩解**：若需更深入分析，應結合推理軌跡檢視工具；但需注意推理內容可能涉及隱私與安全議題。

**風險五：代理堆疊快速演進導致基線失效**
- **問題**：模型版本、支架設計、API 參數變動頻繁，歷史行為輪廓可能迅速過時。
- **緩解**：建立版本化基準資料庫；每次重大更新後重新標註參考集；採用滾動視窗比較而非靜態快照。

**風險六：隱私與資料外洩**
- **問題**：執行軌跡可能包含程式碼片段、錯誤訊息中的敏感資訊，匯聚至分析平台時有外洩風險。
- **緩解**：在解析前對軌跡進行去識別化處理；限制分析環境的網路存取；遵循組織的資料治理規範。

### 與其他技術的整合建議

**與可觀測性平台整合**
- 將解析後的高階動作事件推送至 OpenTelemetry 相容的後端（如 Grafana Tempo、Datadog APM），使代理行為可與其他系統遙測資料關聯分析。
- 在儀表板中將「探索/修改/驗證動作比例」與「解決率」並列顯示，提供更立體的代理健康度視圖。

**與 MLOps / LLMOps 流程整合**
- 將行為輪廓作為模型評估的標準指標之一，與傳統的解決率、token 使用量並列。
- 在模型註冊（model registry）中為每個代理堆疊附加行為輪廓快照，作為版本比較的依據。
- 整合至 CI/CD 流程：每次代理框架更新後自動執行行為回歸測試。

**與失敗診斷工具整合**
- 與 TrajAudit 等參考感知（reference-aware）診斷工具結合，先用本框架定位失敗階段，再用專門工具深挖該階段的錯誤細節。
- 與程序流程圖（process-flow graph）工具互補：本框架提供高階分類，流程圖工具提供細粒度路徑分析。

**與代理開發框架整合**
- 在 SWE-agent、OpenHands、Claude Code 等框架中加入「行為記錄中介層」，自動將原生工具呼叫轉為本框架的高階動作，無需後處理。
- 為框架開發者提供「行為合規外掛」，強制代理遵循預定的工作流程（例如修改前必須先讀檔）。

**與基準測試生態整合**
- 將行為輪廓檢索能力作為新一代基準測試的補充維度，與 SWE-bench、SWE-rebench 的二元結果互補。
- 與多維度評估框架（如 Kapoor 等人的工作）對接，豐富評估指標體系。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「為什麼只看解決率不夠」這個核心問題。接著瀏覽第 3.1 節的動作分類示意圖（圖 1），掌握「探索、搜尋、讀檔、修改、測試」等高階動作的意圖。實作上可先從 GitHub 倉庫的 README 與範例軌跡著手，跑通最小可行流程，再逐步深入。

**給 AI 工程師**：重點關注第 3 節的解析器設計與第 4 節的行為輪廓檢索實驗。解析器的規則式設計雖簡單，但對生產環境的覆蓋率與維護成本是關鍵工程議題；行為輪廓的檢索實驗則展示了如何用輕量特徵達成跨場域識別，值得借鏡到其他代理分析場景。建議直接閱讀程式碼，理解規則集的可擴展性設計。

**給研究者**：第 2 節的相關工作梳理與第 4 節的多項分析（結果配對比較、分割半數零假設、世代與支架效應）是方法論亮點。特別注意作者對混淆變項（任務組成）的坦誠討論，這在代理行為研究中常被忽略。建議將本框架與程序流程圖、推理軌跡分析等方法結合，探討更全面的代理行為表徵。

**給產品經理**：核心訊息是「解決率不再是唯一指標」。當團隊評估或採購程式碼代理時，應要求供應商提供行為層級的細節——代理如何探索、如何修改、如何驗證？這些資訊直接影響實際部署後的可靠性、可預測性與維運成本。建議將行為輪廓監控納入代理 SLA 的討論項目，並在內部建立跨團隊的行為基準共享機制。
