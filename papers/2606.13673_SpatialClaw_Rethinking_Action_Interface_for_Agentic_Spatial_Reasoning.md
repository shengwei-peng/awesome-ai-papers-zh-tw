## ⚡ TL;DR

現有空間智慧體的動作介面缺乏彈性，難以處理開放式複雜3D/4D空間推理。
提出SpatialClaw免訓練框架，以具狀態Python核心讓智慧體迭代撰寫程式碼組合感知工具。
在20項基準測試平均準確率達59.9%，領先既有方法11.2點並跨模型穩定提升。

## 摘要翻譯

空間推理（spatial reasoning）——判斷物體在三維空間中的位置、關係與移動的能力——對視覺語言模型（vision-language models, VLMs）而言仍是一項根本挑戰。工具增強型智慧體（tool-augmented agents）嘗試透過為視覺語言

## 深度分析

#### 方法論解析

SpatialClaw 的核心論點在於：對於 tool-augmented agents（工具增強型智慧體）而言，action interface（動作介面）的設計與其可用的 specialist perception modules（專業感知模組）同等重要，甚至更具決定性。現有 spatial reasoning（空間推理）智慧體主要採用兩種 action interface（動作介面）：其一為 single-pass code execution（單遍程式碼執行），其二為 structured tool-call interface（結構化工具呼叫介面）。前者要求智慧體在觀察任何 intermediate result（中介結果）前，即必須承諾完整的 analysis strategy（分析策略）；後者則透過 named tools（具名工具）、typed arguments（強型別引數）與 typed return values（強型別回傳值）呼叫感知功能，雖然介面規範明確，卻難以在 test time（測試時）針對任務需求即興 composing operations（組合操作）或執行 task-specific computation（任務特定計算）。

為了突破上述限制，SpatialClaw 提出 code as the action interface（以程式碼作為動作介面），並設計為 training-free framework（免訓練框架）。其技術架構圍繞一個 stateful Python kernel（具狀態 Python 核心）展開，該核心預先載入 input frames（輸入幀）、perception and geometry primitives（感知與幾何基元），以及 external scientific libraries（外部科學函式庫）如 NumPy 與 SciPy。在此環境中，specialist perception tools（專業感知工具）被實作為 Python callables（Python 可呼叫物件），其產生的 perceptual outputs（感知輸出）——包括 masks（遮罩）、depth maps（深度圖）、camera geometry（相機幾何）與 trajectories（軌跡）——皆為普通 Python 變數。

執行流程採用多 turns（回合）迭代模式：VLM-backed agent（VLM 驅動智慧體）每個回合撰寫一個 executable cell（可執行儲存格），於核心中執行後取得 intermediate text and visual observations（中介文字與視覺觀察）。由於 state preservation（狀態保存）機制，任何步驟產生的 perception results（感知結果）與 prior outputs（先前輸出）皆可在後續 turns（回合）中被 inspection（檢視）、revision（修訂）與 composition（組合）。這使得智慧體能夠根據 intermediate states（中介狀態）動態調整分析路徑，實現 open-ended, compositional reasoning（開放式組合推理），而非受限於預先註冊的工具介面。

此外，SpatialClaw 採用 unified system prompt（統一系統提示），將 spatial reasoning（空間推理）的一般原則編碼於其中，而非針對特定任務客製化指令。這確保了智慧體在面對 static and dynamic 3D/4D spatial reasoning tasks（靜態與動態 3D/4D 空間推理任務）時，皆能透過彈性編排感知基元與數值運算來建構 coherent geometric argument（連貫幾何論證），從而將程式碼視為真正的 orchestration space（編排空間）。

#### 實驗數據解讀

SpatialClaw 的評估涵蓋 20 個 spatial reasoning benchmarks（空間推理基準測試），橫跨單張影像空間推理、多視角空間推理、一般空間推理、video spatial & 4D reasoning（影片空間與 4D 推理），以及一般影片理解。在這些 static and dynamic 3D/4D spatial reasoning tasks（靜態與動態 3D/4D 空間推理任務）上，SpatialClaw 達到 59.9% 的 average accuracy（平均準確率），相較於近期的空間智慧體基線提升 +11.2 百分點。

尤具說服力的是跨 model families（模型家族）的泛化性實驗。研究團隊在兩個 model families——Qwen 與 Gemma4——共計六個 VLM backbones（VLM 骨幹模型）上進行測試，參數規模涵蓋 27B 至 397B。SpatialClaw 在絕大多數基準測試與骨幹模型上均呈現穩定增益，且完全未進行 benchmark-specific adaptation（針對特定基準測試的調適）或 model-specific adaptation（針對特定模型的調適）。這項結果強烈暗示：性能提升並非來自於對特定模型的微調或對特定資料集的工程取巧，而是源於 action interface（動作介面）本身的表達性。

從任務類型觀察，增益幅度最大的領域為動態 4D 影片推理與多視角推論。這類任務本質上需要跨幀與跨視角鏈結幾何計算，無法被任何預先指定的工具呼叫所捕捉，恰好凸顯了 code as the action interface（以程式碼作為動作介面）在執行 complex 3D/4D spatial reasoning（複雜 3D/4D 空間推理）時的結構性優勢。作者進一步提供三種 action interface（動作介面）的控制比較與 ablation studies（消融實驗），證實即使移除所有預定義的輔助包裝，SpatialClaw 的增益依然持續存在，顯示其優勢根植於介面設計所允許的 open-ended spatial reasoning（開放式空間推理）能力。

#### 與現有研究的比較

在 spatial reasoning（空間推理）的文獻脈絡中，現有方法大致可分為三類。第一類為無工具的 state-of-the-art models（最先進模型），如 Qwen 與 Gemma4 的標準版本，其本質上屬於 vision-language models（視覺語言模型），僅靠 pixels alone（僅靠像素）與自然語言思維鏈進行 structured analysis（結構化分析）。這類方法缺乏獲取中介證據的能力，難以整合 depth（深度）、camera pose（相機姿態）與 temporal correspondence（時序對應關係）等幾何線索，因此在建構 coherent geometric argument（連貫幾何論證）時可靠性不足。

第二類為 single-pass code execution（單遍程式碼執行），代表文獻包括 Luo et al. 與 Marsili et al.。此範式允許智慧體撰寫完整 Python 程式來呼叫 specialist perception tools（專業感知工具）並處理其 perceptual outputs（感知輸出），具備良好的 task-specific computation（任務特定計算）彈性。然而，其致命缺陷在於智慧體必須在觀察任何 intermediate states（中介狀態）——如執行期錯誤、視覺化圖表或部分 masks（遮罩）——之前，即承諾完整的 analysis strategy（分析策略）。這種「先承諾、後執行」的模式排除了根據 intermediate result（中介結果）進行診斷與路徑修正的可能性。

第三類為 structured tool-call interface（結構化工具呼叫介面），見於 Zeren et al.、Chen et al. 與 Ropero et al.。此類智慧體透過 named tools（具名工具）與 typed arguments（強型別引數）呼叫 detectors（偵測器）、segmenters（分割器）、depth estimators（深度估測器）或 pose estimators（姿態估測器），並接收 typed return values（強型別回傳值）。雖然介面乾淨且易於驗證，但其預先定義的指令結構難以表達 test time（測試時）才能確定的複雜組合邏輯，例如將 depth maps（深度圖）與分割遮罩以非預期的方式鏈結並進行數值運算。

相較之下，SpatialClaw 的創新在於將程式碼重新定位為 orchestration space（編排空間），而非一次性程式或預註冊工具的分派層。透過 stateful Python kernel（具狀態 Python 核心）與多 turns（回合）互動，SpatialClaw 同時保留了單遍執行的表達性與結構化呼叫的觀察-修正能力，並進一步支援 open-ended, compositional reasoning（開放式組合推理）。

然而，此設計亦伴隨若干限制。首先，迭代執行多個 executable cells（可執行儲存格）的計算與延遲成本顯著高於單次呼叫。其次，執行由 VLM 生成的程式碼涉及安全性風險，論文未詳述沙箱隔離機制。第三，智慧體的表現高度依賴 VLM 的程式碼生成與除錯能力，若生成幾何運算邏輯有誤，可能導致錯誤在 state preservation（狀態保存）的變數中持續傳播。最後，雖然 SpatialClaw 是 training-free framework（免訓練框架），這也意味著它無法從反覆試錯中學習改進其規劃策略。

#### 可重現性評估

SpatialClaw 作為一個 training-free framework（免訓練框架），在可重現性方面具備先天優勢：無需蒐集額外訓練資料，也無需微調或訓練模型權重，僅需具備適當的 VLM backbones（VLM 骨幹模型）與執行環境即可復現其推論流程。系統的核心依賴 stateful Python kernel（具狀態 Python 核心），其中預載 input frames（輸入幀）、perception and geometry primitives（感知與幾何基元），以及 external scientific libraries（外部科學函式庫）如 NumPy 與 SciPy，這些皆為現有開源資源。

從方法論描述來看，實驗所使用的 20 個 spatial reasoning benchmarks（空間推理基準測試）應為學界現有公開資料集，理論上具備外部驗證的基礎。此外，作者強調使用 unified system prompt（統一系統提示）編碼 spatial reasoning（空間推理）的一般原則，而非進行 benchmark-specific adaptation（針對特定基準測試的調適），這降低了因提示工程過度客製化而導致重現偏差的風險。

儘管如此，根據目前提供的全文脈絡，作者並未明確聲明是否公開釋出原始碼、系統提示全文、感知工具包裝細節，或模型推論腳本。缺乏這些實作細節，外部研究者將難以精確重建 stateful Python kernel（具狀態 Python 核心）的執行環境、感知模組的呼叫介面，以及 intermediate text and visual observations（中介文字與視覺觀察）的回饋組裝邏輯。特別是當實驗涉及多個 specialist perception modules（專業感知模組）的協同運作時，環境依賴、版本相容性與模型權重取得管道皆可能成為重現障礙。

另一項潛在挑戰在於 VLM backbones（VLM 骨幹模型）的版本漂移。論文使用 Qwen 與 Gemma4 系列的多個檢查點，若這些模型在釋出後持續更新，後續研究者可能難以取得完全相同的模型版本以復現 59.9% 的 average accuracy（平均準確率）。因此，雖然 SpatialClaw 的設計概念簡潔優雅，其完全可重現性仍有待作者公開完整原始碼與環境設定檔後方能確立。

#### 未來研究方向

SpatialClaw 以 code as the action interface（以程式碼作為動作介面）的設計為 agentic spatial reasoning（智慧體式空間推理）開啟了多條值得探索的路徑。

首先，在系統安全與工程層面，未來研究可針對 stateful Python kernel（具狀態 Python 核心）發展專用的受控執行環境，結合細粒度沙箱、自動化單元測試與執行期監控，以降低由 VLM 生成程式碼所帶來的潛在風險，同時維持 open-ended, compositional reasoning（開放式組合推理）的彈性。

其次，在學習機制方面，可探索 training-free framework（免訓練框架）與輕量學習的混合架構。例如，透過強化學習或少量示範微調，使 VLM-backed agent（VLM 驅動智慧體）能從執行錯誤與 intermediate states（中介狀態）中學習，逐步改善其規劃與除錯策略，而不失去跨基準測試泛化的優勢。

第三，在任務範圍擴展上，現有框架主要處理 static and dynamic 3D/4D spatial reasoning tasks（靜態與動態 3D/4D 空間推理任務）中的離線分析。未來可將此介面延伸至長時序影片串流與即時 visual perception（視覺感知）場景，強化 temporal correspondence（時序對應關係）的記憶與更新機制，並降低每 turns（回合）的延遲。

第四，在多模態整合方面，目前的 perception and geometry primitives（感知與幾何基元）主要聚焦於視覺線索。未來可納入 LiDAR、事件相機、觸覺感測等異質訊號，使 perception results（感知結果）與中介觀察更加豐富，進而支援更複雜的實體環境推理。

第五，在工具自主性方面，可讓智慧體不僅組合現有 Python callables（Python 可呼叫物件），還能在核心中動態定義新的高階抽象與輔助函式，實現真正的開放式工具發現，進一步模糊「預設工具組」與「即興程式碼」之間的界線。

最後，在認知架構層面，可嘗試將數值計算與顯式符號幾何圖表示結合，彌補純粹 NumPy/SciPy 數值運算在高等 spatial planning（空間規劃）與因果推理上的不足，從而建立更嚴謹的 coherent geometric argument（連貫幾何論證）框架。

## 論文問答

**Q1：SpatialClaw 旨在解決什麼核心問題？**
A：SpatialClaw 主要針對視覺語言模型（VLMs）在進行開放式空間推理時所面臨的根本挑戰，特別是現有工具增強型智慧體因動作介面設計不良而受限的困境。現有的單遍程式碼執行與結構化工具呼叫介面，分別因為必須在觀察中介結果前即承諾完整分析策略、以及缺乏彈性組合操作的能力，而難以應對複雜的 3D/4D 空間推理任務。因此，SpatialClaw 重新思考動作介面，提出以程式碼作為動作介面的免訓練框架，讓智慧體能夠根據中介觀察彈性地編排感知工具與幾何運算，從而提升空間推理的能力。

**Q2：現有的單遍程式碼執行與結構化工具呼叫介面為何在複雜空間推理中表現不佳？**
A：單遍程式碼執行要求智慧體在尚未觀察到任何中介結果之前，就必須撰寫並提交完整的分析策略，這使得它無法根據中間產生的遮罩、深度圖或執行錯誤來動態調整推理方向。另一方面，結構化工具呼叫介面雖然提供了乾淨的具名工具與強型別引數，但其預先定義的 API 難以表達在測試時才浮現的任務特定計算，例如將深度估測與分割遮罩以特定於問題的方式串接。這兩種設計都缺乏支援開放式組合推理所需的彈性，導致在需要多步驟幾何論證的動態 4D 或多視角場景中效能受限。

**Q3：為何動作介面的設計被視為影響智慧體式空間推理能力的關鍵因素？**
A：動作介面決定了工具如何被呼叫、輸出如何呈現、哪些中介狀態可以被觀察，以及智慧體是否能在提交最終答案前根據這些觀察修訂推理，這些因素直接界定了智慧體的能力上限。即使配備了強大的專業感知模組，如果介面無法讓智慧體自由組合感知結果並透過外部科學函式庫進行任務特定計算，這些工具的潛力也無法充分發揮。因此，SpatialClaw 將動作介面從單純的工具派遣層提升為編排空間，使程式碼成為協調感知基元與數值運算的核心媒介，進而釋放 VLM 在空間推理上的潛能。

**Q4：SpatialClaw 的核心方法論是什麼？**
A：SpatialClaw 採用「以程式碼作為動作介面」的核心方法，建立一個具狀態 Python 核心，並在啟動時預先載入輸入幀、感知與幾何基元以及科學計算函式庫。在每一回合中，VLM 驅動智慧體根據所有先前輸出撰寫一個可執行儲存格，執行後產生的變數與視覺化結果會保留在核心狀態中，供後續步驟繼續組合與操作。透過規劃、程式碼執行與回饋組裝的迭代循環，智慧體能夠在統一的系統提示引導下，針對每個問題的需求動態調整分析流程，而無需任何針對特定任務的指令或訓練。

**Q5：相較於先前的動作介面，SpatialClaw 的關鍵創新有哪些？**
A：SpatialClaw 的關鍵創新在於將動作介面從一次性程式或固定 API 派遣，轉變為具有狀態保存能力的持續性多回合 Python 執行環境，使每一步都成為組合感知結果與數值基元的機會。感知工具被設計為 Python 可呼叫物件，其輸出如遮罩、深度圖、相機幾何與軌跡等皆為普通變數，可在跨回合間持續被檢視、組合與修訂。這種設計不僅允許智慧體利用 NumPy、SciPy 等外部科學函式庫進行測試時才確定的任務特定計算，更讓中介文字與視覺觀察能夠直接參與後續的推理循環，大幅提升了介面的表達能力與彈性。

**Q6：作者為何選擇具狀態 Python 核心作為介面設計，而非其他方案？**
A：作者選擇具狀態 Python 核心，是因為複雜空間推理所需的計算往往無法在事前被固定 API 完全預期，新的空間分析通常是對感知基元與數值函式庫的即時組合，而非呼叫新的 API 條目。透過狀態保存機制，任何在先前步驟產生的物件都能持續存在於核心中，使智慧體可以根據中介證據逐步建構幾何論證，並在發現錯誤時回頭修訂。相較於單遍執行或結構化工具呼叫，這種設計讓智慧體能夠同時享有程式碼的表達彈性與互動式觀察回饋，特別適合需要鏈式幾何計算的動態 3D/4D 任務。

**Q7：SpatialClaw 在哪些基準測試上進行評估，主要結果為何？**

**Q13：SpatialClaw 目前存在哪些已知的限制？**

**Q14：SpatialClaw 可能在哪些類型的案例上遭遇失敗？**
A：SpatialClaw 可能在 VLM 產生邏輯上看似合理但幾何上錯誤的程式碼時失敗，特別是在需要複雜數學推導或細微空間關係判斷的任務中，模型可能無法正確轉換自然語言問題為精確的數值運算。當輸入場景存在嚴重遮擋、光照不足或運動模糊時，底層的偵測器、分割器或深度估測器可能輸出錯誤的中介結果，而後續的程式碼組合便會基於錯誤的感知證據進行推論。另外，在需要極長鏈式推理的任務中，VLM 的上下文長度限制或對先前步驟的注意力衰減，也可能導致智慧體遺漏關鍵中介觀察或無法有效修訂早期的錯誤決策。

## 實務應用指南

### 適用場景

1. **自動駕駛與車隊管理**：處理動態 4D 空間推理任務，例如分析連續輸入幀中多個物體的軌跡、相機姿態變化與相對深度，判斷「前車是否正在減速並偏離車道」等需要時序對應關係與幾何論證的問題。
2. **工業檢測與機器人導引**：應用於多視角幾何分析場景，讓機器人透過多個相機視角的輸入幀，判斷零件的精確位置、朝向與裝配關係，並利用具狀態 Python 核心跨回合累積測量結果，逐步修正抓取策略。
3. **智慧監控與安全分析**：針對開放式空間推理需求，例如判斷「人員是否從 A 區域經過 B 點後進入 C 禁區」，需要將偵測器、分割器產生的遮罩與深度圖進行任務特定計算，而非依賴預先註冊的固定工具呼叫。
4. **擴增實境（AR）與空間計算**：在靜態 3D 空間推理任務中，將深度估測器與分割器的感知輸出組合，即時計算虛擬物件與真實平面的接觸點與遮擋關係，並根據中介視覺觀察動態調整渲染參數。
5. **醫療影像與手術導航**：整合多視角內視鏡或 CT 影像，利用 VLM 驅動智慧體以程式碼作為動作介面，自由組合相機幾何與體積重建工具，推導腫瘤與血管的三維相對位置，輔助形成連貫幾何論證。

### 實作前置條件

**資料需求**：高品質輸入幀（單張影像、多視角圖像或影片序列），建議提供相機內參與外參等相機幾何資訊；若任務涉及度量距離，需準備經校準的深度圖或點雲作為輔助輸入。

**運算需求**：執行 VLM 骨幹模型（如 27B 至 397B 參數的 Qwen 或 Gemma4 系列）需高階 GPU（如 A100/H100 等級）；同時需額外運算資源執行專業感知模組（偵測器、分割器、深度估測器、姿態估測器）。具狀態 Python 核心建議部署於具備充足記憶體的容器或虛擬機，以維護跨回合的大型中介結果（如高解析度遮罩、點雲陣列）。

**技能需求**：團隊需熟悉 Python 與外部科學函式庫（NumPy、SciPy）的數值操作；具備電腦視覺基礎知識（相機幾何、座標轉換、齊次座標）；能設計統一的系統提示詞，並具備將現有感知工具封裝為 Python 可呼叫物件的工程能力。

### 實作步驟建議

1. **環境建置**：部署具狀態 Python 核心（如 Jupyter Kernel 或持久化 Python 執行環境），預載 NumPy、SciPy、Open3D 等外部科學函式庫，並確保核心支援跨回合的狀態保存機制，使變數不會在每次執行後被清除。
2. **感知工具鏈整合**：將現有偵測器、分割器、深度估測器與姿態估測器封裝為 Python 可呼叫物件，統一輸出格式為標準 Python 變數（遮罩、深度圖、相機幾何、軌跡點序列），避免使用強型別回傳值限制後續組合彈性。
3. **核心狀態設計**：建立跨回合狀態保存與命名空間管理機制，使每個可執行儲存格產生的中介結果能在後續步驟被直接呼叫、檢視與修訂；建議實作變數版本化或快照機制，防止狀態污染。
4. **提示詞工程**：撰寫統一的系統提示詞，編碼空間推理的一般原則（例如「先估測深度，再判斷遮罩中心點的 3D 座標」），而非針對單一基準測試的特定指令，以確保框架的通用性。
5. **VLM 骨幹選型與迭代迴路**：選定 Qwen 或 Gemma4 等 VLM 骨幹模型，建立「規劃 → 程式碼生成 → 執行 → 回饋彙整」的迭代迴路，讓 VLM 驅動智慧體根據中介文字與視覺觀察動態修訂分析策略，而非在觀察任何中介結果前即承諾完整分析策略。
6. **產品化封裝**：將核心封裝為 API 服務，加入執行沙箱、逾時控制、記憶體上限與錯誤重試機制；設計人機協作介面，允許操作人員檢視中介狀態（如疊加遮罩的視覺化結果）並在關鍵步驟介入修正。

### 潛在風險與注意事項

1. **程式碼安全性**：VLM 生成的程式碼可能包含未預期的系統呼叫或無窮迴圈，必須在嚴格隔離的沙箱中執行具狀態 Python 核心，限制網路、檔案系統與外部指令權限，並設定每回合執行時間上限。
2. **累積誤差放大**：中介結果的微小誤差（如深度估測偏差或遮罩邊界不準確）會在後續組合計算中被放大，建議在關鍵幾何運算步驟加入不確定性量化，並設置人工檢視閘門。
3. **狀態污染與記憶體洩漏**：長時間運行的核心可能因變數覆蓋、型別錯誤或大型陣列殘留導致狀態污染，需定期清理未使用變數、監控核心記憶體用量，並設計自動重啟機制。
4. **VLM 幻覺導致錯誤呼叫**：模型可能幻覺出不存在的函式名稱或強型別引數，需透過嚴格的命名空間管理（如預先注入允許函式列表）與執行期錯誤捕捉機制，將 Traceback 回饋給 VLM 進行修訂。
5. **過度依賴開放式組合**：雖然以程式碼作為動作介面提供高度彈性，但對於簡單且重複性高的任務，可能不如結構化工具呼叫介面來得穩定；建議保留結構化工具作為備援路徑，依任務複雜度動態選擇介面。

### 與其他技術的整合建議

1. **與 ROS／機器人作業系統整合**：將 SpatialClaw 的感知與幾何基元輸出為 ROS topics，使機器人根據即時空間推理結果（如物體 6D 姿態或軌跡預測）執行導航與操作，補足傳統機器人感知管線在開放式組合推理上的不足。
2. **與數位孿生平台整合**：將多視角推理結果與點雲資料餵入數位孿生系統，利用具狀態 Python 核心持續更新虛擬模型中的物件位置與相機幾何，實現物理空間與虛擬環境的即時同步。
3. **與現有 LLM 代理框架整合**：在 LangChain、AutoGen 等框架中將 SpatialClaw 作為專業感知工具節點，利用其以程式碼作為動作介面的特性，彌補結構化工具呼叫介面在空間組合與任務特定計算上的彈性限制。
4. **與邊緣運算設備整合**：將輕量級 VLM 骨幹模型與專業感知模組部署於邊緣端進行初步特徵提取，僅將需要複雜 3D/4D 空間推理的任務提交至雲端 SpatialClaw 核心，降低整體推論延遲與頻寬成本。
5. **與資料標註管線整合**：利用 SpatialClaw 產生的中介遮罩、深度圖與軌跡作為自動化標註種子，透過人工回饋強化學習（RLHF）持續優化底層專業感知模組，形成資料與模型的正向循環。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先理解「空間推理」的基本概念，以及為何單靠視覺語言模型僅靠像素無法精準判斷深度與相對位置。可將 SpatialClaw 想像成一位會寫 Python 的助手，它一邊看影像一邊用程式碼呼叫工具，逐步解題並根據中介視覺觀察修正答案，而非在第一步就承諾完整的分析策略。
- **AI 工程師**：重點關注具狀態 Python 核心的實作細節、如何將現有專業感知模組封裝為 Python 可呼叫物件，以及統一系統提示詞的設計原則。本文的核心價值在於展示「動作介面設計」本身對效能的影響，遠大於針對特定模型或基準測試的調適，這對建構低技術債的產品架構至關重要。
- **研究人員**：請聚焦於本文對動作介面的重新概念化——將程式碼視為編排空間而非單遍程式碼執行或結構化指令。可延伸探討開放式組合推理的理論邊界，以及在不同科學計算領域（如蛋白質結構預測、天文影像分析、氣候模擬）推廣「以程式碼作為動作介面」此範式的可能性。
- **產品經理**：理解本框架屬於免訓練框架，且可跨模型家族（Qwen、Gemma4）與多種空間推理基準測試通用，意味著較低的技術債與較高的模型替換彈性。評估導入時，請優先關注 GPU 運算成本、執行沙箱的安全性合規，以及人機協作檢視中介狀態的產品化需求，而非糾結於為特定客戶場景重新訓練模型。
