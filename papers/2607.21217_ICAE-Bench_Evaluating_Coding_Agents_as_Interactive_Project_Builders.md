## ⚡ TL;DR

現有基準多評估靜態完整任務，難以衡量編碼智慧體從模糊需求互動建置專案的能力。
本文提出ICAE-Bench，以使用者代理模擬互動釐清，並透過真實倉庫與多維指標評估模糊專案建置。
該基準涵蓋12種語言共480項任務，實驗顯示智慧體在隱藏約束、邊界案例與長程整合上仍具挑戰。

## 摘要翻譯

近期 vibe-coding 工作流程（vibe-coding workflows）的興起，正改變對編碼智慧體（coding agents）的期待。智慧體不再僅僅是在完整指定的指令下完成程式碼，而是越來越被期望透過結合規劃（planning）、需求釐清（requirement clarification）、工具使用（tool use）、除錯（debugging）與倉庫層級建構（repository-level construction）等多種能力，將不完整的產品意圖（incomplete product intent）轉化為可運作軟體（working software）。然而，現有的基準測試（benchmarks）尚未完全跟上這一轉變，仍是在靜態且完整指定的任務（static, fully specified tasks）上評估智慧體。

本文提出 ICAE-Bench，一個用於在互動式專案建置情境（interactive project-building settings）下評估編碼智慧體（coding agents）的基準測試（benchmark）。其基本概念是從模糊產品需求（fuzzy product requirement）出發，並以自動化使用者代理（automated User Agent）模擬此動態範式（dynamic paradigm）。為使該情境同時具備真實性（realistic）與可評估性（evaluable），ICAE-Bench 引入了三項關鍵設計。首先，為避免無約束模糊需求（unconstrained fuzzy requirement）所導致的歧義，每項任務的模糊性皆衍生自一個具有可執行行為（executable behavior）的精確真實開源倉庫（precise real open-source repository）。其次，為確保高品質且可重現的使用者模擬（reproducible user simulation），ICAE-Bench 以使用者代理資料（User Agent Data）為互動提供依據，讓使用者代理（User Agent）得以揭露隱藏約束（hidden constraints），同時不會憑空創造新需求或洩漏實作產物（implementation artifacts）。第三，為公平評估開放式倉庫（open-ended repositories），ICAE-Bench 採用標準化黑箱測試（standardized black-box tests），並輔以多維度診斷指標（multi-dimensional diagnostics），包括功能正確性（functional correctness）、語義與 API 相似度（semantic and API similarity）、結構保真度（structural fidelity）、設計品質（design quality）與互動品質（interaction quality）。

### 核心貢獻（3～5點）
- 提出 ICAE-Bench，一個專為互動式專案建置情境設計的編碼智慧體評估基準測試，彌補現有基準多聚焦於靜態且完整指定任務的不足。
- 每項任務的模糊性皆衍生自具有可執行行為的精確真實開源倉庫，使模糊產品需求既貼近真實開發情境，又能被客觀評估。
- 透過使用者代理資料支撐互動，實現高品質且可重現的使用者模擬，讓自動化使用者代理能揭露隱藏約束，同時避免憑空創造需求或洩漏實作產物。
- 採用標準化黑箱測試，並輔以功能正確性、語義與 API 相似度、結構保真度、設計品質與互動品質等多維度診斷指標，公平評估開放式倉庫的建置成果。

### 適合對象
對編碼智慧體、vibe-coding 工作流程、互動式軟體工程、自動化程式生成與基準測試設計有興趣的研究人員與開發者；特別適合關注如何在模糊需求與人機互動情境下，評估智慧體規劃、需求釐清、工具使用、除錯與倉庫層級建構等長程整合能力的讀者。

## 深度分析

#### 方法論解析

ICAE-Bench（Interactive Coding Agents Evaluation Benchmark，互動式編碼智慧體評估基準測試）的核心設計，是將傳統「靜態且完整指定的任務（static, fully specified task）」轉換為「互動式專案建置情境（interactive project-building setting）」。整個流程可拆解為三個環節：起始於一條「模糊產品需求（fuzzy product requirement）」，透過「自動化使用者代理（automated User Agent）」與「編碼智慧體（Coding Agent）」進行多輪「互動式需求釐清（interactive requirement clarification）」，最終產出「可運作倉庫（working repository）」。

為了讓這個動態範式（dynamic paradigm）既真實（realistic）又可評估（evaluable），作者提出三項關鍵設計：

1. **從精確中衍生模糊（ambiguity from precision）**  
   每個任務並非憑空撰寫模糊需求，而是先選定一個「真實開源倉庫（real open-source repository）」，該倉庫具有可執行行為（executable behavior）。研究團隊先從中萃取出完整的 Ground PRD（詳細產品需求文件）以及黑箱行為案例，再透過「模糊化（fuzzification）」逐步隱藏部分限制條件，形成 L1–L3 三個層級的 Fuzzy PRD。L1 最模糊，L3 相對豐富，Ground PRD 則作為權威參考。這種「由精確到模糊」的設計確保了任務本身有明確的客觀目標，不會因為需求過度開放而無法評判。

2. **以 User Agent Data（使用者代理資料）支撐可重現的使用者模擬（reproducible user simulation）**  
   為避免自動化 User Agent 自由發揮而產生幻覺或洩漏實作產物（implementation artifact），ICAE-Bench 預先準備結構化的 User Agent Data。這些資料記載了被隱藏的「隱藏約束（hidden constraint）」以及 Public cases（公開案例）。當 Coding Agent 提出「釐清問題（clarification question）」時，User Agent 只能從這份資料中揭示被省略的資訊，不能發明新需求，也不能洩漏原始碼或內部 API。如此一來，互動過程具有高度可重現性，同時保留了「需求釐清（requirement clarification）」的真實挑戰。

3. **標準化黑箱測試（standardized black-box test）搭配多維度診斷指標（multi-dimensional diagnostic）**  
   由於開放式倉庫（open-ended repository）沒有唯一標準答案，ICAE-Bench 不以「是否完全複製原始倉庫」為評判標準，而是強調「必須做什麼」而非「必須怎麼做」。評估協定結合：
   - **功能正確性（functional correctness）**：透過黑箱測試檢驗輸入輸出。
   - **語義與 API 相似度（semantic and API similarity）**：衡量產出與參考倉庫在介面與行為語意上的接近程度。
   - **結構保真度（structural fidelity）**：評估專案架構、檔案組織是否保留參考結構。
   - **設計品質（design quality）**：檢視程式碼設計與架構優劣。
   - **互動品質（interaction quality）**：評估對話效率與需求釐清能力。

整體而言，ICAE-Bench 包含 480 個任務，涵蓋 12 種程式語言（programming language），並提供 50 題的 ICAE-Bench-Lite 子集，方便快速實驗與迭代。

#### 實驗數據解讀

根據論文摘要與部分內文，實驗評估了六個「編碼模型（coding model）」在兩個「智慧體框架（agent framework）」——Claude Code 與 OpenHands——上的表現。雖然提供的片段未包含完整數據表格，但從作者結論可以歸納出以下關鍵發現：

1. **可見行為（visible behavior）容易被複製，隱藏約束（hidden constraint）難以掌握**  
   當需求中明確描述的輸入輸出或 Public cases 被保留時，現有 Coding Agent 通常能夠產出大致可運作的程式。然而，一旦被隱藏的邊界條件、錯誤處理邏輯或內部狀態管理未在 Fuzzy PRD 中明示，智慧體往往無法主動發現，導致功能正確性（functional correctness）下降。

2. **邊界案例（boundary case）是主要失敗來源**  
   配置解析器範例中提到的「重複項目（duplicate）是否合法」、「無效項目（invalid entry）如何報告行號」等問題，正是典型的邊界案例。由於 Fuzzy PRD 不會預先說明，Coding Agent 必須透過提問或測試推論。實驗顯示，多數模型在這類細節上表現不佳。

3. **長程整合（long-horizon integration）仍是瓶頸**  
   從模糊需求到可運作專案涉及規劃（planning）、工具使用（tool use）、除錯（debugging）與倉庫層級建構（repository-level construction）的長期協作。實驗指出，Agent 在單一步驟或局部功能上表現尚可，但跨越多個檔案、多個相依套件（dependency）與多次執行失敗（execution failure）的整合仍然困難。

4. **多維度指標有助定位失效環節**  
   傳統只用功能正確性評分，難以區分「程式可跑但介面不同」與「介面對但邏輯錯誤」。ICAE-Bench 透過 semantic and API similarity、structural fidelity、design quality 與 interaction quality 等指標，能夠更細緻地診斷：問題是出在需求釐清不足、架構設計不良、還是實作細節遺漏。

總結來說，實驗結果凸顯了「模糊專案生成（ambiguous project generation）」仍是一個高難度任務，現有模型距離真正的「互動式專案建置者（interactive project builder）」仍有顯著差距。

#### 與現有研究的比較

下表整理 ICAE-Bench 與代表性從零生成或倉庫層級編碼基準測試的差異：

| 基準測試（Benchmark） | 任務數 | 語言數 | 需求層級 | 可見資訊 | 互動 | 多語言實作 |
|---|---|---|---|---|---|---|
| Commit0 | 54 | 1 | 固定實作與測試 | 實作細節、測試腳本 | ✗ | ✗ |
| NL2RepoBench | 104 | 1 | 固定實作 | 實作細節 | ✗ | ✗ |
| PRDBench / PRDBench(free) | 50 | 1 | 固定測試或無 | 測試或無 | ✗ | ✗ |
| ProgramBench | 200 | 6 | 固定程式 | 可執行程式 | ✗ | ✗ |
| RealBench | 61 | unknown | 固定實作 | 實作細節 | ✗ | ✗ |
| **ICAE-Bench** | **480** | **12** | **Fuzzy L1–L3** | **Public cases** | **✓** | **✓** |

**相對於既有研究的主要改進：**

- **從靜態任務（static task）轉向動態範式（dynamic paradigm）**：現有基準大多一次性給定完整規格，ICAE-Bench 則模擬真實開發中需求逐步釐清的過程。
- **真實且可控的模糊性**：透過真實開源倉庫衍生 Ground PRD，再進行系統化模糊化，避免了「無約束的模糊需求（unconstrained fuzzy requirement）」導致的評估失焦。
- **可重現的使用者模擬**：User Agent Data 的設計讓自動化 User Agent 不會自由發揮，確保不同實驗間的互動內容一致。
- **多維度評估**：不僅看功能正確性，還看語義、API、結構、設計與互動品質，更貼近實際軟體工程對「可運作軟體（working software）」的要求。

**潛在限制：**

- **使用者代理的真實性**：雖然 User Agent Data 保證了可重現性，但自動化 User Agent 仍可能無法完全模擬人類使用者的模糊、矛盾或隨時間改變的需求。
- **隱藏約束的預先定義**：所有 hidden constraint 都是人為預設，可能無法涵蓋真實開發中所有可能的設計決策空間。
- **互動輪次的可擴展性**：隨著任務複雜度提升，多輪對話的計算成本與評估難度會顯著增加。
- **黑箱測試的覆蓋率**：標準化黑箱測試（standardized black-box test）雖然公平，但可能無法捕捉所有內部品質問題，例如效能、安全性或可維護性。

#### 可重現性評估

ICAE-Bench 在可重現性（reproducibility）方面採取了相對開放的策略：

- **資料集（dataset）與評估程式碼（evaluation code）已公開**：作者提供 GitHub 倉庫（https://github.com/ALEX-nlp/ICAE-EVAL），包含 480 個任務、ICAE-Bench-Lite 子集以及完整的評估程式碼。這讓其他研究者可以直接複製實驗環境並進行比較。
- **User Agent Data 的結構化設計**：由於 hidden constraint 與 Public cases 被固定下來，不同團隊執行時，User Agent 的回應應該保持一致，這是「可重現的使用者模擬（reproducible user simulation）」的關鍵。
- **模型權重（model weights）與外部依賴**：本研究並未訓練新模型，而是評估現有 coding model。因此 reproducibility 取決於所使用的外部模型（如 Claude、GPT 系列等）的版本、API 溫度參數以及 agent framework（Claude Code、OpenHands）的設定。若未來能釋出固定的容器化環境、模型版本快照與隨機種子，將進一步提升可重現性。

整體而言，ICAE-Bench 在資料與評估流程上已達到高度透明，但由於涉及多輪 LLM 互動，完全消除隨機性仍需額外的工程配套。

#### 未來研究方向

ICAE-Bench 的提出為「vibe-coding 工作流程（vibe-coding workflows）」的評估開闢了新方向，未來可從以下幾個層面延伸：

1. **更智慧的使用者代理（User Agent）**  
   目前 User Agent 主要依據預設的 User Agent Data 回應。未來可探索由 LLM 驅動、但受結構化資料約束的 User Agent，使其在保持可重現性的同時，更能模擬人類使用者的非線性、上下文相關的澄清行為。

2. **主動式需求釐清策略**  
   研究 Coding Agent 如何主動提出高品質的「釐清問題（clarification question）」，以最少輪次獲取最多資訊。這涉及資訊理論、主動學習（active learning）與對話策略最佳化。

3. **長程規劃與整合能力強化**  
   針對「長程整合（long-horizon integration）」的瓶頸，未來可發展具備長期記憶、子目標分解與跨檔案追蹤能力的 agent architecture，並以 ICAE-Bench 作為標準測試場域。

4. **從執行失敗中自動修復**  
   強化「反覆處理執行失敗（iterate over execution failure）」的能力，讓 Coding Agent 能根據測試回饋自動除錯（debugging）、安裝相依套件（install dependency）並調整專案結構。

5. **擴展評估維度**  
   除了現有的 functional correctness、semantic and API similarity、structural fidelity、design quality 與 interaction quality，未來可加入效能、安全性、可維護性、使用者體驗（UI/UX）與多模態輸入（例如從草圖或語音生成專案）。

6. **用於訓練與強化學習（RL）**  
   ICAE-Bench 不僅是評估工具，也可作為訓練資料來源。未來可嘗試透過強化學習或模仿學習，訓練專門針對互動式專案建置的 Coding Agent。

7. **人機協作（human-in-the-loop）研究**  
   最終目標是讓 Coding Agent 與真實人類開發者協作。未來可進行使用者研究，比較人類與自動化 User Agent 在需求釐清過程中的差異，並據此改進互動設計。

## 論文問答

**Q1：ICAE-Bench 主要想解決什麼問題？**

A：ICAE-Bench 旨在解決現有程式編碼基準測試無法充分評估「vibe-coding 工作流程」的問題。傳統基準大多要求編碼智慧體在靜態且完整指定的任務下完成程式碼，但現實中越來越多的使用者只會提供模糊產品需求，並期望智慧體能透過互動逐步轉化為可運作軟體。因此，本研究提出一個互動式專案建置情境，讓編碼智慧體從不完整產品意圖出發，結合規劃、需求釐清、工具使用、除錯與倉庫層級建構等能力，最終交付可運作倉庫。

**Q2：為什麼現有的基準測試無法有效評估 vibe-coding 工作流程？**

A：現有基準測試通常假設任務目標是靜態、明確且無需使用者互動即可發現的，例如函式級補全或固定測試資料的倉庫編輯任務。即使是從零開始生成的基準，也多提供詳細需求、固定骨架或特定語言限制，未能反映真實開發中需求逐步浮現的動態範式。相較之下，vibe-coding 要求編碼智慧體主動釐清隱藏約束、反覆處理執行失敗並進行長程整合，這些能力在傳統靜態任務中難以被充分檢驗。

**Q3：評估互動式專案建置者為什麼重要？**

A：隨著編碼智慧體從區域性程式碼助手演進為專案建置者，使用者越來越可能將整個軟體建構過程委託給智慧體，而非僅請求單一程式碼片段。在這種情境下，核心問題在於智慧體能否將不完整產品意圖轉化為可運作軟體，這涉及需求釐清、規劃與迭代修正等複合能力。建立針對互動式專案建置的評估標準，有助於識別目前模型的瓶頸，並推動更符合實際開發需求的編碼智慧體研究。

**Q4：ICAE-Bench 的核心方法是什麼？**

A：ICAE-Bench 的核心方法是讓編碼智慧體從模糊產品需求出發，透過與自動化使用者代理進行互動式需求釐清，逐步建構出可測試規格並最終產出可運作倉庫。每個任務都源自真實開源倉庫，研究者先從原始倉庫抽取出 Ground PRD 與黑箱行為案例，再逐步隱藏部分約束以形成模糊 PRD。編碼智慧體可在過程中提出釐清問題，由使用者代理根據結構化的使用者代理資料回答，確保互動過程既真實又可重現。

**Q5：ICAE-Bench 的三項關鍵設計是什麼？**

A：第一，為了避免無約束的模糊需求導致任務無法評估，ICAE-Bench 從精確的真實開源倉庫衍生模糊性，保留可執行行為作為評估依據。第二，為了確保高品質且可重現的使用者模擬，ICAE-Bench 透過使用者代理資料支撐互動，讓使用者代理能揭露隱藏約束，但不會憑空創造新需求或洩漏實作產物。第三，為了公平評估開放式倉庫，ICAE-Bench 採用標準化黑箱測試，並輔以功能正確性、語義與 API 相似度、結構保真度、設計品質與互動品質等多維度診斷指標。

**Q6：為什麼要從精確的真實開源倉庫衍生模糊性，而非直接撰寫模糊需求？**

A：如果直接從頭撰寫模糊需求，任務可能變得過度開放或定義不清，導致失敗難以歸因於智慧體能力的不足。透過從真實開源倉庫衍生模糊性，ICAE-Bench 能確保每個任務背後都有明確且可測試的參考行為，同時讓編碼智慧體僅能看到不完整產品意圖。這種設計既保留了 vibe-coding 的真實感，又提供了客觀評估所需的穩定標準。

**Q7：ICAE-Bench 包含哪些資料集與規模？**

A：ICAE-Bench 包含 480 個任務，涵蓋 12 種程式語言，並額外提供 50 個任務的 ICAE-Bench-Lite 子集以便快速實驗。每個任務都提供模糊 PRD、最終參考實作、使用者代理資料以及權威的黑箱行為案例。相較於現有從零生成或倉庫層級基準，ICAE-Bench 在規模、語言多樣性與互動性方面都有顯著擴展。

**Q8：實驗中的關鍵結果是什麼？**

A：研究團隊評估了六個編碼模型與兩個智慧體框架，結果顯示模糊專案生成仍然非常具有挑戰性。編碼智慧體通常能重現可見行為，但在隱藏約束、邊界案例與長程整合方面表現較弱。這些結果凸顯了僅靠擴大模型規模並不足以解決互動式專案建置中的需求理解與系統性整合問題。

**Q9：多維度診斷指標揭示了哪些失敗模式？**

A：多維度診斷指標顯示，智慧體在功能正確性上可能因遺漏隱藏約束而失分，在語義與 API 相似度上則可能產生與參考倉庫介面不一致的設計。結構保真度與設計品質指標進一步指出，智慧體傾向於產生過度簡化或組織鬆散的倉庫結構。互動品質指標則可幫助判斷失敗是否源於釐清問題不夠精準，或使用者代理的回答未能有效引導建置方向。

**Q10：ICAE-Bench 可應用於哪些實務情境？**

A：ICAE-Bench 可應用於評估與改進實際的 vibe-coding 開發工具，例如整合開發環境中的 AI 助手或自動化專案生成服務。開發團隊可利用此基準測試不同編碼模型在面對模糊產品需求時的表現，從而選擇最適合自身工作流程的智慧體。此外，研究者也能藉由多維度診斷指標定位模型在需求釐清、架構設計與除錯整合上的弱點，作為後續優化的依據。

**Q11：從產品開發角度，ICAE-Bench 帶來哪些考量？**

A：產品開發者應意識到，優秀的編碼智慧體不僅要能產出可執行程式碼，還需具備主動釐清需求與管理長程整合的能力。ICAE-Bench 的互動設計提醒產品團隊，在設計人機協作介面時，應鼓勵智慧體提出釐清問題，而非盲目猜測隱藏約束。此外，標準化黑箱測試與多維度診斷指標可作為產品上線前的品質把關機制，確保智慧體在開放式專案建置中維持穩定表現。

**Q12：ICAE-Bench 對整個研究領域可能產生什麼影響？**

A：ICAE-Bench 推動編碼智慧體研究從靜態、完整指定的任務，轉向更貼近真實軟體開發的互動式專案建置情境。它為學界與業界提供了一個統一的評估平台，使得不同模型與框架能在相同標準下比較需求釐清、規劃與倉庫層級建構能力。長遠來看，這有助於催生更懂得與人類協作、更能處理不完整產品意圖的下一代編碼智慧體。

**Q13：作者承認 ICAE-Bench 有哪些限制？**

A：雖然 ICAE-Bench 模擬了互動式需求釐清過程，但自動化使用者代理畢竟無法完全取代真實人類使用者的彈性與創意。此外，任務雖涵蓋 12 種程式語言，但某些特定領域或極大規模企業級專案的複雜度可能仍未被充分涵蓋。評估指標雖然多維度，但對於設計品質與互動品質等較主觀的面向，仍可能需要進一步的人類判斷來補充。

**Q14：實驗中觀察到哪些典型的失敗案例？**

A：實驗發現智慧體經常能處理需求中明確描述的可見行為，但容易忽略需要透過互動才能發現的隱藏約束。例如，在配置解析器範例中，智慧體可能未主動詢問重複項目是否合法或支援哪些格式，導致實作與參考行為不一致。此外，智慧體在面對需要多步驟協作的長程整合任務時，也常因早期設計決策失當而難以在後續除錯中挽回。

**Q15：未來研究可以朝哪些方向發展？**

A：未來研究可進一步提升使用者代理的真實性，例如讓其能根據對話脈絡主動提供提示或糾正智慧體的誤解。另一個方向是擴展任務規模與領域覆蓋，納入更多企業級系統、跨服務整合或長期維護情境。此外，結合人類評估與自動化診斷指標，發展出更細緻的互動品質與設計品質衡量方法，也是值得持續探索的課題。

## 實務應用指南

### 適用場景

1. **企業內部低程式碼/無程式碼平台導入**：當業務單位只能提出「我要一個能夠自動對帳的報表工具」這類模糊產品需求時，可運用 ICAE-Bench 的互動式專案建置情境，評估編碼智慧體在持續對話中釐清欄位規則、輸出格式、異常處理等隱藏約束的能力，再決定是否將其整合至內部開發平台。

2. **新創產品原型快速驗證**：創辦人或產品經理常以不完整產品意圖啟動專案，例如「做一個支援多語系的配置解析器」。透過本基準的 vibe-coding 工作流程，可驗證編碼智慧體能否在有限輪次內將模糊需求轉換為可運作倉庫，縮短從構想到可測試原型的時間。

3. **開源專案重構與跨語言遷移**：當團隊需要將既有真實開源倉庫的行為移植到新語言或新架構時，可利用 ICAE-Bench 從精確倉庫衍生模糊需求與黑箱測試，評估智慧體在僅知道外部行為、不知內部實作產物的情況下，重建出功能等價且結構合理的專案。

4. **編碼模型選型與採購評估**：企業在導入 Claude Code、OpenHands 等智慧體框架前，可使用 ICAE-Bench-Lite 進行標準化評測，比較不同編碼模型在功能正確性、互動品質、設計品質等維度的表現，作為採購與落地決策的客觀依據。

5. **軟體工程教育與訓練**：教師可將互動式需求釐清設計成課程作業，讓學生扮演使用者代理或編碼智慧體，學習如何從模糊需求收斂到可測試規格，並理解長程整合、邊界案例與設計品質在實務中的重要性。

### 實作前置條件

- **資料準備**：需蒐集真實開源倉庫作為任務來源，並為每個倉庫建立 Ground PRD（完整產品需求文件）、User Agent Data（隱藏約束與可回覆的釐清資訊），以及標準化黑箱測試案例。若從無到有建置，需投入大量領域專家工時進行需求抽取與模糊化設計。

- **運算資源**：執行編碼智慧體需要穩定的 LLM API 配額或本地 GPU/CPU 叢集；每個任務涉及多次工具呼叫、相依套件安裝與測試執行，建議以 Docker 或 Kubernetes 建立隔離且可重現的執行環境。儲存空間需足以容納多語言執行環境與生成的可運作倉庫。

- **技能組合**：團隊需具備 Python 程式開發、軟體測試設計、Docker 容器化、LLM Prompt Engineering，以及基準測試設計經驗。若涉及多語言任務，還需要各目標語言的建置與套件管理知識。

### 實作步驟建議

1. **確定評估範圍**：先選用 ICAE-Bench-Lite（50 個任務、10 種語言）進行試驗，驗證流程後再擴展到完整 ICAE-Bench（480 個任務、12 種語言）。

2. **建立任務資料管線**：從真實開源倉庫抽取可執行行為，撰寫 Ground PRD，並設計 L1 至 L3 的漸進式模糊化層級，將部分約束隱藏為 User Agent Data。

3. **建置自動化使用者代理**：讓使用者代理僅能依據 User Agent Data 回答釐清問題，避免發明新需求或洩漏實作產物；同時設計對話輪次與終止條件。

4. **整合編碼智慧體與工具鏈**：將選定的編碼模型與智慧體框架（如 Claude Code、OpenHands）接入環境，賦予檔案讀取、指令執行、相依套件安裝、測試執行等工具使用能力。

5. **執行互動式建置並收集診斷資料**：讓編碼智慧體在與使用者代理的對話中逐步建置專案，記錄每一輪的問題、回覆、程式碼變更與執行失敗。

6. **執行多維度評估與分析**：運用標準化黑箱測試評估功能正確性，並輔以語義與 API 相似度、結構保真度、設計品質、互動品質等指標，定位智慧體在規劃、需求釐清、除錯、長程整合上的弱點。

7. **迭代優化**：根據診斷結果調整模型、Prompt、工具權限或對話策略，並重新執行評估以驗證改進效果。

### 潛在風險與注意事項

- **任務定義過度開放**：若模糊需求未從精確的真實開源倉庫衍生，容易變成無約束的模糊需求，導致評估結果不具參考價值。建議嚴格遵循「從精確衍生模糊」的原則，並保留 Ground PRD 作為權威依據。

- **使用者代理回覆不一致**：自動化使用者代理若自由發揮，可能洩漏實作產物或創造新的隱藏約束，破壞可重現的使用者模擬。應將回覆範圍嚴格限制在 User Agent Data 內，並進行一致性檢查。

- **開放式倉庫評估困難**：由於沒有唯一標準答案，單純比對原始程式碼不公平。建議採用黑箱測試為主、結構與語義指標為輔的多維度診斷協議，避免過度懲罰合理的替代實作。

- **長程整合與邊界案例仍是瓶頸**：實驗顯示編碼智慧體常能重現可見行為，但對隱藏約束、邊界案例與長程整合表現較弱。評估時應特別設計這類測試，並在產品落地時保留人工審查機制。

- **多語言環境複雜度高**：12 種程式語言的編譯器、直譯器與相依套件管理差異極大，建議以容器化方式隔離每個任務的執行環境，並建立自動化的環境建置與清理流程。

### 與其他技術的整合建議

- **接軌 CI/CD 管線**：將 ICAE-Bench 的評估流程封裝為 CI 階段，在每次模型更新或框架升級後自動執行，作為品質閘道，確保編碼智慧體在互動式專案建置情境下的表現不會退化。

- **結合 RAG 與領域知識庫**：在需求釐清階段，可讓編碼智慧體透過 RAG 查詢公司內部的 API 文件、設計規範或歷史專案，提升對隱藏約束的理解，減少對使用者代理的過度依賴。

- **整合 IDE 與編輯器外掛**：將互動式需求釐清與倉庫層級建構能力嵌入 VS Code、Cursor 等開發環境，讓開發者在日常工作中直接體驗 vibe-coding 工作流程。

- **與現有基準測試互補**：ICAE-Bench 可與 SWE-bench、HumanEval、ProgramBench 等靜態且完整指定的任務並行使用，形成從函式級合成、倉庫編輯到互動式專案生成的完整能力地圖。

- **導入 LLMOps 實驗追蹤**：利用 Weights & Biases、MLflow 或自研平台記錄每次執行的對話、程式碼、測試結果與多維度診斷指標，便於後續比較不同模型與超參數設定。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從圖一的互動式需求釐清流程與「配置解析器」範例任務開始，理解 vibe-coding 與傳統靜態任務的差異；不必急著讀完整 480 個任務的細節，重點掌握「模糊需求 → 對話釐清 → 可運作倉庫」這條主軸，以及為何需要黑箱測試與多維度診斷。

- **AI 工程師**：請聚焦於 User Agent Data 的設計、自動化使用者代理的實作細節，以及多維度評估協議的程式碼實現；這些內容直接影響能否在企業環境中重現論文結果，並可借鏡來設計自己的互動式評測管線。

- **研究人員**：建議深入分析實驗結果中「可見行為 vs. 隱藏約束」、「邊界案例」、「長程整合」等發現，並思考如何擴展到更開放的多輪對話、更複雜的軟體架構，或結合主動式學習來減少對話輪次。

- **產品經理**：請將本文視為評估編碼智慧體能否承接「不完整產品意圖」的參考框架；重點關注 ICAE-Bench-Lite 的落地可行性、互動品質指標與實際開發流程的對應關係，以判斷這類技術在自家產品中適合扮演的角色與風險邊界。
