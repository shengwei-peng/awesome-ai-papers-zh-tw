## 摘要翻譯

基於嵌入的程式碼檢索（embedding-based code retrieval）是程式設計智慧代理（coding agents）與檢索增強式程式碼生成（retrieval-augmented code generation）的核心元件，在此情境中，檢索到正確的程式碼遠比檢索到詞面相似的程式碼（lexically similar code）更為重要。現有的程式碼檢索基準（code-retrieval benchmark）並未在搜尋池（search pool）中，針對每個查詢的標準實作（canonical implementation）植入受控、經執行驗證的單一編輯變體（controlled single-edit variant），因此嵌入模型是否能在檢索情境中依功能性區分（functional discrimination）正確程式碼與近似複製但錯誤的程式碼（near-clone-but-incorrect code），仍是一個未解的問題。要解決此問題，需要一個搜尋池本身即包含相關反事實樣本（counterfactual）的基準——即與每個標準實作幾乎相同、且經執行驗證的缺陷變體（buggy variant）——以便直接測試檢索器的排序是否具備功能性區分能力，而非僅仰賴主題相似度（topical similarity）或身分重疊（identity overlap）。

我們提出 ExecRetrieval，涵蓋 939 個 Python 任務，每個任務配對一個經執行驗證的標準實作，以及最多四個經執行驗證的缺陷干擾項（buggy distractor）；每個干擾項皆由機械式突變（mechanical mutation）產生，僅進行一處目標編輯。我們以提供者原生呼叫（provider-native invocation）方式評估 23 種稠密嵌入（dense embedding）設定與 BM25，並採用配對 McNemar 檢定（paired McNemar test）與查詢層級拔靴法區間（query-level bootstrap interval）。在搜尋池中加入近似複製的反事實樣本後，表現最佳的託管系統在 exec@10（前 10 執行正確率）達到 1.00，但 exec@1（前 1 執行正確率）僅為 0.331；在四個領先系統中，91.5%–99.4% 的排名第一遺漏（rank-1 miss）均為配對的缺陷變體；而在領先系統中，67%–78% 的查詢裡，標準實作的分數低於其至少一個配對干擾項。完整的資料集、執行判定器（execution oracle）、嵌入矩陣（embedding matrix）、環境快照（environment snapshot），以及成對統計檢定（pairwise statistical test）結果，均已於附錄 D 中的網址釋出。

### 核心貢獻（3～5點）
- 指出既有程式碼檢索基準無法評估「功能性區分」能力的盲點，即嵌入模型可能檢索到近似複製但錯誤的程式碼，卻無法辨識真正可執行正確的標準實作。
- 提出 ExecRetrieval 基準，包含 939 個 Python 任務，每個任務配對一個經執行驗證的標準實作與最多四個機械式單一編輯產生的缺陷干擾項，使搜尋池本身具備反事實對照樣本。
- 以提供者原生呼叫方式系統性評估 23 種稠密嵌入設定與 BM25，並採用配對 McNemar 檢定與查詢層級拔靴法區間進行嚴謹統計比較。
- 實證發現功能正確性差距：最佳託管系統 exec@10 雖達 1.00，但 exec@1 僅 0.331，且絕大多數排名第一遺漏與標準實作分數低於干擾項的現象，皆源於缺陷變體。
- 釋出完整資料集、執行判定器、嵌入矩陣、環境快照與成對統計檢定結果，供後續研究重現與改進。

### 適合對象
本論文適合從事程式碼檢索、檢索增強生成（RAG）、程式設計智慧代理、軟體工程與機器學習應用的研究人員與工程師閱讀，特別是關注嵌入模型在實際執行正確性上表現、以及希望建構或評估更可靠之檢索增強式程式碼生成系統的讀者。

## 深度分析

#### 方法論解析

ExecRetrieval（功能正確性程式碼檢索基準）的核心設計理念，是將「功能性區分（functional discrimination）」從傳統的「主題相似度（topical similarity）」與「身分重疊（identity overlap）」評估中拆離出來。具體而言，作者針對每一個自然語言查詢（query）都準備了一個標準實作（canonical implementation）以及最多四個經過機械式突變（mechanical mutation）產生的缺陷干擾項（buggy distractors）。這些缺陷變體（buggy variants）與 canonical 之間僅存在單一、目標明確的編輯差異，卻會在執行判定器（execution oracle）上失敗。整個搜尋池（search pool）因此同時包含「正確答案」與「近似複製但錯誤的程式碼（near-clone-but-incorrect code）」，從而讓研究者能直接測量嵌入模型是否具備依據執行正確性進行排序的能力。

資料集規模與結構方面，ExecRetrieval 涵蓋 939 個 Python 任務，橫跨十個演算法領域（algorithmic domains）。每個任務配備一個 canonical implementation、最多四個 buggy distractors，以及一組 7–10 個測試案例的測試套件（test suite）。最終搜尋池共有 4,694 個程式碼片段。所有 canonical 都通過全部測試，所有 distractors 至少有一個測試失敗。這種設計確保了正確性標籤並非來自人工標註，而是來自確定性執行結果，從而避免了主觀判斷與標註不一致的問題。

在建構流程（construction pipeline）上，作者採用了 GPT-5.4 的高推理強度模式（high reasoning effort）作為主要合成與驗證引擎。該流程包含五個階段的驗證閘門（validation gate）：schema 檢查、AST 語意檢查、canonical 執行驗證、distractor 執行驗證，以及語料庫完整性檢查。此外，所有程式碼都在隔離子程序（isolated subprocess）中執行，以確保安全性與可重現性。根據論文報告，該流程的首次驗證通過率達到 91%（100 個驗證批次中有 91 個一次成功），顯示出 reasoning-LLM 在產生結構化、可執行程式碼對上的高產能。

評估協定採用提供者原生呼叫（provider-native invocation），對 23 組稠密嵌入（dense embedding）設定以及 BM25 進行測試。所謂 provider-native，是指針對每一個嵌入服務商官方文件建議的任務類型、查詢與段落前綴（query/passage prefixes）、資料型別（dtype）、正規化（normalization）、批次大小（batch size）與相似度度量（similarity metric）進行設定，而非統一使用某種通用提示。這種做法讓比較更貼近實際部署情境，但也意味著不同模型之間的差異可能同時來自於模型本身與官方建議的呼叫方式。

評估指標包含 exec@k（前 k 個結果中至少有一個可執行正確的比例）、execution_precision@k（前 k 個結果中可執行正確的比例），以及 canonical-ID nDCG（Normalized Discounted Cumulative Gain，以 canonical 身分作為相關性標籤的傳統排序指標）。統計檢定方面，作者使用配對 McNemar 檢定（paired McNemar test）比較兩個系統在相同查詢上的二元成對差異，並以查詢層級拔靴法區間（query-level bootstrap interval）估計信賴區間。這種成對設計至關重要，因為它確保所有模型都在完全相同的查詢與候選集合上接受檢驗，避免了不同查詢難度分布所造成的比較偏差。

#### 實驗數據解讀

論文報告的數據呈現出一個強烈且值得警惕的訊息：現代嵌入模型在面對近似複製但錯誤的程式碼時，雖然能夠在較大的候選視窗內召回正確答案，卻難以在排名第一（rank-1）的位置做出正確判斷。具體來說，表現最佳的託管系統（hosted system）在全部 939 個查詢上達到 exec@10 = 1.00，但 exec@1 僅有 0.331。這意味著若將檢索結果直接交給下游的程式設計智慧代理（coding agents）或檢索增強式程式碼生成（retrieval-augmented code generation）系統使用，每三次查詢中就有約兩次會在第一個候選拿到錯誤程式碼。

更細緻的分解顯示，rank-1 miss（排名第一遺漏）的情況中，有 91.5% 到 99.4% 的比例是被「配對的缺陷變體（paired buggy variants）」佔據。換句話說，當模型出錯時，幾乎不是因為召回了一個主題不相關的片段，而是因為它把一個與 canonical 僅有一處編輯差異、但會導致測試失敗的程式碼排到了第一名。這直接證明了現有嵌入模型在功能性區分上的脆弱性：它們對於「語法與語意高度相似、但執行語意相反」的程式碼缺乏辨識力。

另一個關鍵數據是：在領先系統上，canonical implementation 的相似度分數低於其至少一個配對 distractor 的比例高達 67% 到 78%。這表示對於絕大多數查詢，模型並非只是「剛好」在某幾個邊界案例出錯，而是系統性地將某些錯誤版本視為比正確版本更相關。這種現象在圖 1 的 lowest_set_bit 範例中表現得淋漓盡致：canonical 使用位元運算 `n & (-n)` 來隔離最低設定位元，而一個僅將 `&` 改成 `|` 的單一符號編輯變體，卻因為餘弦相似度（cosine similarity）更高而排在第二名，導致 canonical 落到第四名。

從指標對照來看，canonical-ID nDCG 與 exec@k 之間存在明顯落差。傳統基於身分重疊的 nDCG 會將 canonical 視為唯一正例，而將所有 distractors 視為負例；但在 ExecRetrieval 的搜尋池中，distractors 與 canonical 在主題與詞彙上幾乎無法區分，因此一個「完美主題檢索器」與一個「完美功能檢索器」會在傳統基準上得到相同分數。ExecRetrieval 透過將執行驗證的 counterfactual（反事實樣本）植入搜尋池，迫使評估指標反映真正的功能性區分能力，而非僅僅是詞彙相似度（lexical similarity）或主題相似度。

BM25 的表現也值得討論。作為稀疏詞項匹配（sparse term matching）的代表，BM25 在傳統程式碼檢索中常被當作強基線。在 ExecRetrieval 中，由於 distractors 與 canonical 共享大量詞彙與識別符名稱，BM25 很可能同樣難以區分正確與錯誤版本。這凸顯了無論是稠密嵌入還是經典稀疏方法，都面臨「單一編輯即可翻轉語意」的挑戰。

統計檢定層面，配對 McNemar 檢定與查詢層級拔靴法區間的引入，讓作者能夠在相同查詢上比較不同嵌入配置，並量化系統間差異的顯著性。這對於區分「真實能力差距」與「抽樣變異」非常重要，尤其是在 exec@1 這類稀疏二元指標上，單一查詢的波動可能相當大。

#### 與現有研究的比較

ExecRetrieval 與現有程式碼檢索基準（code-retrieval benchmark）最關鍵的差異，在於它將「受控單一編輯變體（controlled single-edit variant）」直接植入搜尋池（search pool）。傳統基準如 CodeSearchNet、CodeXGLUE、CoSQA、CoIR 與 CodeRAG-Bench，主要評估的是模型能否從大型開放原始碼語料庫（open-source corpus）中召回與查詢主題相關的程式碼片段。它們的相關性標籤通常基於身分重疊（例如某個函式是否為查詢的原始實作）或人工標註的主題相關性。在這些基準中，一個完美的主題檢索器與一個完美的功能檢索器無法被區分，因為搜尋池中並不存在與 canonical 高度相似但執行錯誤的對照樣本。

Li et al. (2025b) 的研究在精神上是與 ExecRetrieval 最接近的：他們同樣關注語法相似但功能不同的程式碼，並利用 LLM 驅動的合成框架產生 Type-IV 變體（相似語法、不同功能），再以生成測試套件進行驗證。然而，ExecRetrieval 進一步將這個概念轉化為標準化的檢索基準：每個查詢都有固定數量的配對 distractors、確定性的執行判定器，以及成對統計檢定。這使得不同嵌入模型之間的比較更加嚴謹，也更容易被後續研究重複使用。

從方法論來看，ExecRetrieval 的機械式突變（mechanical mutation）與 Li et al. 的 LLM 驅動演化各有優劣。機械式突變的優點在於可控性與可解釋性：每一個 distractor 都對應到一個明確的單一編輯操作（例如運算子替換、邊界條件偏移、比較方向錯誤），便於分析模型的失效模式。缺點則是產生的錯誤類型可能較為規則化，未必涵蓋真實世界中所有複雜的語意錯誤。相對地，LLM 驅動的 Type-IV 變體可能更接近真實開發者會犯的錯誤，但較難控制變異粒度與數量。

ExecRetrieval 的另一項貢獻是強調「第一階段排序（first-stage ranking）」的重要性。在檢索增強生成（retrieval-augmented generation）與程式設計智慧代理的管線中，嵌入檢索通常扮演候選召回階段（candidate-recall stage）的角色，後續還會有重排序（reranking）、執行驗證、測試或代理式後處理（agentic post-processing）。傳統觀點認為，只要正確答案能夠進入前 k 名，下游階段就能修正錯誤。然而 ExecRetrieval 的數據顯示，即使 exec@10 達到 1.00，exec@1 仍只有 0.331，這意味著若下游階段只處理排名第一的結果，系統將頻繁地面臨錯誤起點。這對於資源受限或延遲敏感的應用場景尤其重要。

限制方面，ExecRetrieval 目前僅涵蓋 Python 語言與十個演算法領域，雖然已經比單一領域研究更具泛化性，但仍無法代表所有程式語言與應用場景。此外，所有 distractors 都是單一編輯變體，真實世界中的錯誤往往涉及多處修改與更細微的語意依賴。最後，測試套件雖然經過執行驗證，但其完備性仍可能影響 canonical 與 distractor 的標籤正確性：一個不夠強的測試套件可能無法偵測到某些語意錯誤，反之亦然。

#### 可重現性評估

ExecRetrieval 在可重現性（reproducibility）方面的承諾相當完整。根據論文所述，作者釋出了完整資料集、執行判定器（execution oracle）、嵌入矩陣（embedding matrix）、環境快照（environment snapshot）以及成對統計檢定（pairwise statistical test）結果，詳細連結見附錄 D。這些釋出內容涵蓋了從資料、程式碼到執行環境的多個層面，大幅降低了後續研究者重現實驗的門檻。

具體而言，完整資料集的釋出讓研究者可以直接使用相同的 939 個查詢與 4,694 個程式碼片段進行模型評估，無需重新執行高成本的 reasoning-LLM 合成流程。執行判定器的釋出則確保了正確性標籤的一致性，因為所有 canonical 與 distractor 都是透過相同的測試套件與執行環境驗證。嵌入矩陣的釋出尤其重要：它讓研究者能夠在不需要呼叫付費 API 的情況下，重現各模型之間的相似度排序與統計比較，這對於資源有限的研究團隊或需要進行額外後設分析的工作非常有幫助。

環境快照則進一步確保了執行結果的可重現性。Python 版本、相依套件版本、作業系統設定等細節都可能影響程式碼執行結果，尤其是在處理位元運算、浮點數精度或特定標準函式庫行為時。透過提供隔離子程序執行環境的封存，作者有效降低了「在我機器上可以跑」這類問題的發生機率。

然而，可重現性仍存在一些潛在挑戰。首先，部分嵌入模型是透過商業 API 提供，其內部權重與推論細節並不透明，未來若模型版本更新或 API 行為改變，嵌入矩陣可能無法完全對應。其次，雖然作者釋出了嵌入矩陣，但若研究者希望測試新的嵌入模型，仍需自行取得 API 存取權限並遵循 provider-native invocation 的設定，這可能涉及額外成本與設定細節。最後，論文提到 GPT-5.4 用於資料建構，但該模型的具體版本與參數設定若未完全公開，後續研究者可能難以精確複製整個建構流程，儘管釋出的最終資料集已經足以進行評估。

#### 未來研究方向

ExecRetrieval 所揭示的功能正確性差距（functional-correctness gap）為多個後續研究方向開啟了大門。首先，最直接的方向是設計能夠感知執行語意的嵌入模型。現有稠密嵌入（dense embedding）主要基於對比學習或語言建模目標進行訓練，未必能捕捉程式碼在特定輸入下的動態行為。未來可以探索將執行軌跡（execution traces）、輸入輸出對（input-output pairs）或抽象語法樹（AST）語意納入嵌入學習目標，以強化模型對單一編輯所引發語意變化的敏感度。

其次，重排序（reranking）與執行驗證的整合值得深入研究。ExecRetrieval 顯示即使 exec@10 很高，exec@1 仍很低，這暗示在第一階段排序後加入一個輕量級的執行感知重排序器，可能顯著提升實際可用性。這類重排序器可以學習預測候選程式碼通過測試套件的機率，或直接對前 k 個候選進行快速執行篩選。如何在延遲與正確性之間取得平衡，是實際部署中的關鍵問題。

第三，可以將 ExecRetrieval 的 counterfactual 設計擴展到多編輯變體與其他程式語言。真實世界中的錯誤往往不只一處修改，且不同語言的語意特性（如靜態型別、記憶體管理、並行模型）會帶來不同的挑戰。將受控缺陷變體的觀念應用於 JavaScript、Java、C++ 或 Rust 等語言，有助於檢驗嵌入模型的跨語言泛化能力。

第四，對抗性訓練（adversarial training）與反事實資料增強是另一個有潛力的方向。利用 ExecRetrieval 產生的 paired distractors 作為困難負樣本（hard negatives），可以微調現有嵌入模型，使其學會區分 canonical 與單一編輯錯誤版本。這類微調不僅可以提升 exec@1，也可能改善模型在傳統基準上的表現，因為它強迫模型關注真正影響語意的程式結構。

第五，將功能正確性評估整合到程式設計智慧代理（coding agents）的端到端評估中。ExecRetrieval 測量的是檢索階段的表現，但實際系統還會經歷生成、編輯、測試與迭代等步驟。未來可以設計基準，觀察當檢索器在第一階段提供錯誤候選時，下游代理能否透過代理式後處理（agentic post-processing）或測試回饋進行修正，以及這樣的修正需要多少額外成本。

第六，不確定性估計（uncertainty estimation）與校準（calibration）在程式碼檢索中的應用也值得探索。ExecRetrieval 的數據顯示模型經常對錯誤候選給出高於 canonical 的相似度分數，這代表模型的分數校準存在問題。開發能夠估計「此候選是否可能為錯誤版本」的不確定性指標，可以幫助下游系統決定是否啟用更昂貴的驗證機制。

最後，從方法論角度，未來可以研究缺陷干擾項密度（distractor density）對檢索性能的影響。論文已初步觸及此議題，但更系統地變化每個查詢的 distractor 數量、錯誤類型分布與搜尋池大小，有助於理解功能正確性差距如何隨環境複雜度而變化，並為實際系統設計提供理論依據。

## 論文問答

**【背景與動機】**

**Q1：什麼是程式碼嵌入檢索中的「功能正確性差距」？為什麼它很重要？**
A：功能正確性差距是指嵌入模型能夠召回語法與主題上相似的程式碼，卻無法保證召回的程式碼在執行時能通過測試、產生正確輸出的落差。在檢索增強式程式碼生成與程式設計智慧代理中，第一階段排序決定了後續重排序、執行驗證或代理式後處理所看到的候選順序；若模型把近似複製但錯誤的程式碼排在標準實作之前，後續階段可能永遠沒有機會修正。因此，這個差距直接影響下游系統的可靠性與開發者體驗，不能僅以詞彙相似度或主題相似度來衡量檢索品質。

**Q2：現有的程式碼檢索基準為何無法衡量這個差距？**
A：現有基準如 CodeSearchNet、CodeXGLUE、CoSQA、CoIR 與 CodeRAG-Bench 主要評估檢索結果是否為同一標準實作或主題相關，並未在搜尋池中為每個查詢植入受控單一編輯變體的缺陷干擾項。換言之，一個完美的主題檢索器與一個完美的功能性檢索器在這些資料集上會得到相同分數，因為它們沒有把「近似複製但錯誤的程式碼」當成反事實樣本放進候選集合。缺乏執行驗證的對照樣本，使我們無法判斷嵌入模型是僅靠身分重疊或主題相似來排序，還是真的能依功能正確性區分好壞。

**Q3：既然下游可以執行測試或重排序，為什麼第一階段排序仍然重要？**
A：第一階段排序扮演候選召回階段的角色，決定了後續模組能檢視哪些片段以及優先處理哪一個；若標準實作被擠到後面，執行判定器或重排序器可能因為預算、延遲或上下文長度限制而根本看不到它。此外，許多實際系統只取前 k 個結果，當 k 很小時，排名第一遺漏幾乎等同於最終答案錯誤。因此，把功能性區分的責任全部推給下游並不合理，測量並縮小第一階段的功能正確性差距是提升整體管線正確率的關鍵。

**【方法與創新】**

**Q4：一個功能導向的程式碼檢索基準應具備哪些性質？ExecRetrieval 如何實現？**
A：它需要四個性質：搜尋池同時包含已知正確的標準實作與少量近似複製的缺陷變體；正確性由確定性測試套件執行驗證，而非人工標註；涵蓋多個演算領域與缺陷模式以避免偏頗；並提供查詢層級的成對統計比較。ExecRetrieval 收錄 939 個 Python 任務，橫跨十個演算領域，每個任務配有一個標準實作、最多四個經機械式突變產生的缺陷干擾項，以及 7 到 10 個測試的執行判定器，總共 4,694 個片段。透過這樣的設計，研究者可以直接檢驗檢索器在相同查詢下，能否把可執行正確的標準實作排在錯誤變體之前。

**Q5：缺陷干擾項是如何產生與驗證的？**
A：作者使用以 GPT-5.4 為核心、搭配高推理強度的五階段管線：先檢查綱要與抽象語法樹語意，再執行標準實作與缺陷變體，最後確認語料庫完整性；所有執行都在隔離子程序中進行以確保安全。每個缺陷干擾項都是對標準實作進行單一標靶編輯的機械式突變，例如把位元運算 `&` 換成 `|`，並且必須至少有一個測試失敗。該管線在驗證批次中達到 91% 的一次通過率，顯示能夠穩定且大規模地產生高品質反事實樣本。

**Q6：何謂「提供者原生呼叫」？為什麼要採用這種評估方式？**
A：提供者原生呼叫是指按照各嵌入服務商官方文件所建議的最佳實務來呼叫模型，包括任務類型、查詢與篇章前綴、資料型別、正規化、批次大小與相似度度量。這種做法能讓評估結果最接近一般開發者或產品在真實環境中會得到的表現，而不是在實驗室裡用自訂提示或微調後的設定。ExecRetrieval 評估了 23 種稠密嵌入配置加上 BM25，全部採用提供者原生呼叫，以確保比較的公平性與可移植性。

**【實驗與結果】**

**Q7：論文採用哪些評估指標？主要量化結果為何？**
A：論文同時報告 exec@k、execution_precision@k 與 canonical-ID nDCG，並輔以配對 McNemar 檢定與查詢層級拔靴法區間來比較系統間的顯著差異。最佳託管系統在全部 939 個查詢上 exec@10 達到 1.00，但 exec@1 僅有 0.331；在四個領先系統中，排名第一遺漏有 91.5% 到 99.4% 的機率是配對的缺陷變體。此外，在 67% 到 78% 的查詢中，標準實作的相似度分數低於至少一個其配對的缺陷干擾項，顯示嵌入空間並未穩定地將功能正確性編碼為更高相似度。

**Q8：exec@1 與 exec@10 的巨大落差說明了什麼？**
A：exec@10 等於 1.00 表示只要看前 10 個結果，正確的標準實作幾乎一定會出現，模型在召回層面表現優異；但 exec@1 只有 0.331 表示模型很難在第一名就選出正確答案，經常被單一編輯的缺陷干擾項超越。這個落差凸顯了嵌入模型擅長捕捉主題與語法相似度，卻對細微的語意差異——例如一個運算子或邊界條件的改變——缺乏區辨力。對於只取 top-1 或上下文有限的應用來說，這意味著檢索器把大量正確性判斷工作推給了下游階段。

**Q9：除了整體指標，論文還做了哪些細部分析？**
A：論文進行配對 McNemar 檢定與查詢層級拔靴法區間，以確認不同嵌入配置之間的差異並非來自少數簡單或困難查詢的隨機波動。文中也探討了搜尋池密度對差距的影響：當近似複製的缺陷變體密度提高時，功能正確性區分的難度隨之上升。這類分析幫助研究者理解，問題不僅是模型偶爾出錯，而是在存在反事實樣本的環境下系統性地把錯誤候選排在前面。

**【應用與影響】**

**Q10：在程式設計智慧代理與檢索增強式程式碼生成中，這個差距帶來什麼實務風險？**
A：當代理或 RAG 管線從搜尋池召回程式碼時，若排名第一的是缺陷干擾項，後續生成可能直接複製錯誤邏輯，導致產生看似合理但執行失敗的程式碼。由於這些錯誤版本與標準實作僅有一個標靶編輯的差異，開發者與自動化工具都很難透過肉眼或靜態檢查快速發現。長期而言，這會降低開發者對智慧編碼輔助的信任，並增加除錯與測試成本。

**Q11：對嵌入服務商與 IDE 開發者有哪些產品層面的啟示？**
A：服務商不應僅以主題召回或詞彙相似度來宣稱模型適用於程式碼檢索，而應該在訓練與評估時加入執行驗證的功能正確性訊號。IDE 與程式碼助手在設計第一階段排序時，應該意識到 top-1 可能經常是錯誤的近似複製，因此需要保留足夠的候選給重排序器或執行判定器，並在介面中提示使用者進行驗證。此外，產品團隊可以採用 ExecRetrieval 這類基準來比較不同嵌入模型在真實錯誤樣本下的表現，避免被高 exec@10 掩蓋低 exec@1 的風險。

**Q12：這項工作可能對整個領域產生什麼影響？**
A：ExecRetrieval 把程式碼檢索的評估軸線從「找不找得到相關程式碼」推進到「找不找得到可執行正確的程式碼」，為未來的嵌入模型與檢索系統設立了更嚴謹的標準。它釋出的資料集、執行判定器、嵌入矩陣、環境快照與成對統計檢定結果，讓後續研究能夠重現與擴展實驗。隨著更多研究聚焦於縮小功能正確性差距，我們可能會看到結合執行訊號、對比學習與專用重排序器的新一代程式碼嵌入模型。

**【限制與未來】**

**Q13：作者承認 ExecRetrieval 有哪些限制？**
A：該基準目前僅涵蓋 Python 與十個演算領域，雖然已經多樣，但仍無法代表所有程式語言、框架與真實世界程式碼庫的複雜度。缺陷干擾項是機械式突變產生的單一標靶編輯，真實軟體缺陷可能涉及多處修改、語境依賴或更細微的規格誤解。此外，論文測量的是「當搜尋池中存在近似複製的錯誤變體時」的表現，並未宣稱這種情況在實際語料庫中的發生頻率。

**Q14：哪些缺陷模式或情境對現有系統最困難？**
A：從 lowest_set_bit 例子可見，僅把 `n & (-n)` 改成 `n | (-n)` 這種一個運算子的差異，就能讓最強的託管嵌入模型把錯誤版本排在標準實作前面；這類位元運算、比較運算子與邊界條件的細微改變特別難以區分。由於這些變體在詞彙與主題上幾乎與正確版本相同，模型若只學到語法共現或自然語言描述對應，就會忽略執行語意。當多個缺陷干擾項同時出現在前五名時，更會進一步壓縮標準實作的有效排序位置。

**Q15：未來研究可以朝哪些方向發展？**
A：未來可以探索將執行結果與測試通過與否作為對比學習或強化學習的訊號，直接訓練能區分功能正確性的程式碼嵌入模型。另一個方向是設計專門針對反事實樣本的重排序器，在第一階段召回後利用靜態分析、符號執行或單元測試來重新評估候選。最後，也可以將 ExecRetrieval 的建構管線擴展到更多程式語言、更大規模的開放原始碼語料庫，以及涉及多處編輯或語境化缺陷的真實錯誤樣本，從而更接近實際部署場景。

## 實務應用指南

### 適用場景

1. **企業內部程式碼庫的智慧搜尋**  
   當開發者在龐大程式碼庫中搜尋「某個功能的正確實作」時，傳統基於主題相似度或詞彙相似度的檢索可能回傳近似複製但錯誤的程式碼（例如舊版 bug、未合併的分支版本）。將 ExecRetrieval 的「受控單一編輯變體」概念移植到內部資料，可驗證嵌入模型是否會把可執行正確的標準實作排在前面。

2. **檢索增強式程式碼生成（RAG）的召回品質稽核**  
   在檢索增強式程式碼生成管線中，第一階段排序決定了後續生成模型能看到哪些候選。若搜尋池中同時存在正確片段與高度相似的缺陷干擾項，可用 ExecRetrieval 的評量框架測量嵌入模型是否會把錯誤程式碼餵給下游 LLM，導致生成結果帶有隱藏 bug。

3. **程式設計智慧代理的記憶與工具選擇**  
   程式設計智慧代理常從向量記憶庫中召回歷史程式碼片段作為參考。透過在記憶池中植入已知缺陷變體，可評估代理的第一階段檢索是否具備功能性區分能力，避免代理反覆引用「看起來對、跑起來錯」的舊程式碼。

4. **嵌入模型選型與微調驗證**  
   團隊在評估多個稠密嵌入模型或考慮領域微調時，可用 ExecRetrieval 作為功能正確性的壓力測試：不只看 canonical-ID nDCG，更看 exec@1、exec@10 與成對統計檢定，確保選出的模型在「近複製但錯誤」的邊界案例上仍穩定。

5. **程式碼審查與自動化測試優先級排序**  
   將檢索結果的執行判定器與 CI/CD 整合，對於檢索系統回傳的 Top-k 候選自動執行測試套件，並把未通過的近似複製版本標記為高風險，優先進入人工審查或自動化測試流程。

### 實作前置條件

**資料條件**
- 每個查詢必須對應至少一個經執行判定器驗證的標準實作，以及 1–4 個機械式突變產生的缺陷干擾項。
- 每個程式碼片段需配備確定性測試套件（建議 7–10 筆測試），且所有標準實作全數通過、所有缺陷變體至少失敗一筆。
- 搜尋池需同時包含 canonical implementation 與 buggy variant，才能測量功能性區分而非僅主題相似度。

**運算條件**
- 嵌入推論：需能呼叫各提供者原生 API（如 Gemini Embedding、OpenAI、Voyage 等）或本地部署模型；建議預留批次推論與快取機制，因 4,694 個片段 × 939 查詢的嵌入矩陣規模不小。
- 執行環境：需隔離子程序執行測試，避免惡意或意外程式碼影響主機；論文使用環境快照確保可重現。
- 統計分析：需能執行配對 McNemar 檢定與查詢層級拔靴法區間，評估系統間顯著差異。

**技能條件**
- 熟悉 Python AST 操作與程式碼突變規則，能設計單一目標編輯（如運算子替換、邊界條件偏移、guard 移除）。
- 具備向量資料庫與嵌入 API 實作經驗，了解任務類型、前綴、正規化、資料型態等提供者原生呼叫細節。
- 具備基礎統計檢定知識，能解讀 exec@k、execution_precision@k 與成對檢定結果。

### 實作步驟建議

1. **定義任務領域與查詢集合**  
   從目標應用場景（如字串處理、位元運算、排序、圖演算法）挑選 500–1,000 個自然語言查詢，每個查詢對應單一明確功能。

2. **產生標準實作與機械式突變**  
   使用高推理能力的 LLM（如 GPT-5.4 with high reasoning effort）生成 canonical implementation，再依預定突變原型（運算子錯誤、比較方向錯誤、off-by-one、guard 缺失等）產生 3–4 個受控單一編輯變體。

3. **建立執行判定器與測試套件**  
   為每個任務撰寫 7–10 筆確定性測試，並在隔離子程序中執行。過濾掉標準實作未全過、或缺陷變體未失敗的樣本，確保資料品質。

4. **建構搜尋池並產生嵌入矩陣**  
   將所有 canonical 與 buggy 片段放入搜尋池，依各嵌入服務商官方文件設定任務類型、前綴、正規化與相似度度量，批次產生查詢與文件的嵌入向量。

5. **計算功能正確性指標**  
   對每個系統計算 exec@k、execution_precision@k 與 canonical-ID nDCG，並以配對 McNemar 檢定比較不同模型在相同查詢上的表現，輔以查詢層級拔靴法區間估計變異。

6. **診斷並強化第一階段排序**  
   針對 canonical 排名低於其缺陷干擾項的查詢進行錯誤分析，考慮引入重排序模型、執行訊號回饋或對比學習微調，縮小功能正確性差距。

7. **部署與持續監控**  
   將通過驗證的檢索模型整合進 RAG 或 IDE 外掛，並在生產環境持續抽樣執行測試套件，監控 exec@1 與 rank-1 miss 比例是否劣化。

---

### 潛在風險與注意事項

- **過度擬合特定缺陷模式**：機械式突變若只涵蓋少數幾種 bug 類型，評估結果可能無法推廣到真實世界的多樣錯誤。建議涵蓋至少 5–8 種突變原型，並定期納入新發現的缺陷模式。  
- **執行環境安全**：在自動化執行未知或 LLM 生成程式碼時，必須使用沙箱、容器或隔離子程序，避免惡意程式碼或無限迴圈癱瘓系統。  
- **測試套件不夠強健**：若測試覆蓋率不足，可能出現「缺陷變體剛好通過所有測試」或「標準實作因環境差異被誤判為失敗」。應採用多組邊界條件測試並凍結環境快照。  
- **指標解讀陷阱**：exec@10 高並不代表系統夠好，因為 Top-10 幾乎必然包含 canonical；真正關鍵的是 exec@1 與 canonical 是否被其缺陷干擾項壓過。  
- **提供者原生呼叫的隱藏差異**：不同嵌入服務對查詢/文件前綴、正規化、資料型態的要求不同，若統一設定可能導致不公平比較。務必參照官方文件逐項調校。

### 與其他技術的整合建議

- **向量資料庫（Milvus、Pinecone、Weaviate、pgvector）**：將 ExecRetrieval 的搜尋池作為測試集合預先載入，利用向量資料庫的 metadata 標記每個片段是 canonical 或 buggy variant，便於快速篩選與分析 rank 分佈。  
- **重排序模型（Cross-Encoder、CodeBERT-based reranker）**：將第一階段嵌入檢索的 Top-k 結果餵給重排序模型，並以執行判定器作為最終標籤進行微調，彌補稠密嵌入在功能性區分上的弱點。  
- **檢索增強生成管線（LangChain、LlamaIndex、自研 RAG）**：在 RAG 的 retrieve 節點後加入「執行過濾器」，對召回候選自動跑測試，只把通過的標準實作送進生成模型的上下文。  
- **程式設計智慧代理框架（AutoGPT、SWE-agent、Devin-like 系統）**：把 ExecRetrieval 的評量邏輯嵌入代理的記憶召回單元，讓代理在選擇參考程式碼時優先考慮執行正確性，而非僅餘弦相似度。  
- **MLOps 與實驗追蹤（MLflow、Weights & Biases）**：記錄每個嵌入配置的超參數、提供者原生呼叫設定、exec@k 與成對統計檢定 p 值，方便後續模型選型與回歸測試。

### 給不同背景讀者的閱讀建議

**初學者**：先從圖 1 的 `lowest_set_bit` 範例入手，理解「看起來很像、跑起來錯」的缺陷變體如何擊敗最先進的嵌入模型；接著閱讀資料集建構與 exec@k 定義，暫時跳過統計檢定細節，重點掌握「為什麼功能正確性比主題相似度更重要」。

**AI 工程師**：請聚焦於第 3–4 節的提供者原生呼叫設定、嵌入矩陣產生方式與 exec@k 計算邏輯；特別注意不同模型在任務前綴、正規化與相似度度量上的差異，並思考如何將執行判定器整合進現有 RAG 或 IDE 外掛的召回管線。

**研究人員**：建議深入分析配對 McNemar 檢定、查詢層級拔靴法區間與 canonical-ID nDCG 的設計動機；同時關注機械式突變的多樣性與搜尋池密度實驗，這些是將 ExecRetrieval 從靜態基準延伸為動態、可擴展研究工具的關鍵。

**產品經理**：把重點放在「exec@10 = 1.00 但 exec@1 = 0.331」這個核心發現上，理解它對使用者體驗與下游代理風險的意涵；接著評估團隊是否具備產生受控缺陷變體、執行測試套件與持續監控 rank-1 miss 的資源，再決定導入範圍與優先級。
