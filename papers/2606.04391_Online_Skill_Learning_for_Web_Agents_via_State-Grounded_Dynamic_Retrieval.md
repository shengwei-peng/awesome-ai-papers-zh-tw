## 摘要翻譯

語言智能體（Language agents）日益依賴可重複使用技能（reusable skills），以提升跨相關任務的多步驟網頁自動化（multi-step web automation）表現。近期越來越多研究探討線上技能學習（online skill learning），其中智能體持續從先前的任務軌跡（task trajectories）中歸納技能，並在未來任務中即時重複使用。然而，現有方法主要在任務層級（task-level）重複使用技能：根據初始任務指令檢索一組固定的技能，並在整個執行過程中保持不變。此靜態策略（static strategy）與網頁執行（web execution）的特性不一致：適當的下一步動作不僅取決於任務目標，也取決於當前網頁狀態（current webpage state），而該狀態經常轉變為初始技能無法涵蓋的情境。為彌補此缺口，我們提出基於狀態的動態檢索（State-Grounded Dynamic Retrieval, SGDR），這是一種可實現網頁智能體（web agents）逐步技能重複使用（stepwise skill reuse）的線上技能學習方法

## 深度分析

#### 方法論解析

State-Grounded Dynamic Retrieval（基於狀態的動態檢索，SGDR）的核心貢獻在於將傳統的任務層級（task-level）一次性檢索（one-shot retrieval）轉變為基於執行狀態（execution state）的逐步技能重複使用（stepwise skill reuse）。整體方法包含三個緊密銜接的元件，共同解決互動式網頁自動化（interactive web automation）中技能粒度（granularity）與檢索時機的雙重挑戰。

首先是滑動視窗萃取（sliding-window extraction）。現有方法在萃取可重複使用技能（reusable skills）時，往往陷入兩極：要麼儲存完整軌跡技能（full-trajectory skills），導致程序過度綁定原始任務情境，難以遷移到中間執行狀態（intermediate execution states）；要麼僅記錄單一動作技能（single-action skills），喪失了程序性抽象價值。SGDR 採用滑動視窗機制，從已完成的任務軌跡（task trajectories）中截取可重複使用的子程序（sub-procedures），使其粒度恰好介於完整工作流與原子動作之間，從而能在任意中間網頁狀態（webpage state）被呼叫，而不僅限於任務起點。

其次是文字-程式碼雙重表示法（dual text-code representation）。每個技能同時具備自然語言（natural language）描述與可執行的瀏覽器動作（browser actions）程式碼。前者作為語義索引，支撐檢索（retrieval）階段的相似度匹配；後者則確保技能被選取後能直接轉譯為具體操作，橋接了「找得到」與「執行得了」之間的落差。這種表示法使技能函式庫（skill library）同時具備語義可檢索性與執行確定性。

最關鍵的是基於狀態的動態檢索機制（state-grounded dynamic retrieval mechanism）。不同於僅依據初始任務指令（initial task instruction）在開頭選定固定技能集合的靜態策略（static strategy），SGDR 在每一個決策步驟（decision step）都重新檢索技能函式庫，匹配依據同時包含任務目標與當前網頁狀態（current webpage state）。這使得智能體（agent）在執行過程中，能隨著頁面轉換動態調整所依賴的程序知識，解決「開頭適用的技能在後續頁面失效」的問題，實現真正的線上範式（online paradigm）自我增強。

#### 實驗數據解讀

作者在 WebArena 的五個網站領域進行評估，並選用兩個差異顯著的骨幹模型（backbone models）：GPT-4.1 與 Qwen3-4B。實驗結果顯示，SGDR 在 GPT-4.1 上達到 37.5% 的成功率（success rates），相較最強基線（strongest baseline）的相對提升幅度（relative gains）為 10.6%；在 Qwen3-4B 上則達到 24.3%，相對提升 10.0%。

這兩組數據具有多層意義。第一，提升幅度在絕對值與相對值上均相當一致，顯示 SGDR 的效益並非僅來自於特定大規模模型的湧現能力，而是對不同能力層級的語言智能體（language agents）皆能提供穩定助益，這對於輕量級模型的實務部署尤具價值。第二，在網頁自動化（web automation）這類長期任務中，絕對成功率仍處於中等區間（低於 40%），10% 的相對增益在實務上已屬顯著進展，代表每十個任務中約多成功一個。第三，論文提及步驟效率（step efficiency）亦同步改善，這代表檢索到的子程序確實提供了高層次抽象，減少了重複試錯的低層級動作，而非僅以更多步驟換取成功，顯示技能歸納（skill induction）具備真正的程序壓縮價值。

#### 與現有研究的比較

現有線上技能學習（online skill learning）研究，如 Wang et al. (2025b,a) 與 Liu et al. (2025)，主要將技能重複使用（skill reuse）視為任務層級（task-level）的一次性操作（one-shot operation）：智能體在收到新任務指令後，僅依據初始文字進行一次技能檢索，隨後在整段執行過程中固定使用該技能集合。這種設計假設網頁任務是靜態指令，忽略了互動式網頁自動化中網頁狀態的動態演變。SGDR 明確針對此限制，將檢索粒度從「每任務一次」推進到「每步驟一次」，並以當前網頁狀態作為檢索條件之一。

這與近期探索技能組織形式（如 workflows、executable programs、retrievable past experiences）的研究互補：前者關注「技能長什麼樣子」，SGDR 則聚焦「在何種執行狀態下呼叫哪個技能」。此外，SGDR 提出的滑動視窗萃取解決了技能函式庫的粒度挑戰（granularity challenge），避免了完整軌跡技能與單一動作技能的兩難。

然而，此方法亦存在侷限。首先，目前僅在 WebArena 模擬環境中驗證，尚未於真實世界部署（real-world deployment）場景測試動態網頁的雜訊、時變性與反爬蟲機制。其次，雖然論文提到僅從經評估器確認的軌跡中萃取技能，但在更開放的序列任務流設定（sequential task-stream setting）中，若前期任務失敗，錯誤技能可能污染函式庫，論文對此類累積誤差的處理機制著墨有限。最後，每步驟皆進行動態檢索會帶來額外的推理延遲與計算成本，對於需要即時反應的應用場景可能構成瓶頸。

#### 可重現性評估

在再現性方面，作者已將程式碼釋出於 GitHub（https://github.com/plusnli/skill-dynamic-retrieval），並採用公開評測基準 WebArena，這為其他研究者復現結果提供了基礎。骨幹模型方面，GPT-4.1 需透過 API 呼叫，雖可取得但成本較高；Qwen3-4B 則為開放權重模型，硬體需求相對親民，有利於資源有限的研究者進行驗證。

不過，仍有若干再現風險值得留意。WebArena 環境涉及真實網站的互動式實例，其網頁結構可能隨時間變化，導致數個月後的復現結果產生漂移。此外，論文摘要與內文未詳細交代滑動視窗尺寸、檢索時的 top-k 參數、相似度度量方式等實作細節，儘管開源程式碼可彌補此缺口，但若程式碼文件不足，仍可能增加復現難度。整體而言，此研究屬於中等偏高的可重現性：資料與評估框架公開，但環境動態性與部分超參數需依賴原始碼才能完全確認。

#### 未來研究方向

未來研究可沿以下數個方向延伸。第一，多模態狀態表徵：目前 SGDR 主要仰賴文字化的網頁狀態與自然語言技能描述，後續可整合視覺資訊（如網頁截圖、DOM 樹與無障礙樹），發展視覺基礎（visually grounded）的動態檢索，以處理更豐富的網頁版面變化。第二，技能函式庫的長期維護：隨著序列任務流持續累積，技能數量將不斷增長，未來需要階層式組織、去重複化或主動遺忘機制，以避免檢索噪音與儲存膨脹。第三，跨領域遷移：當前實驗侷限於 WebArena 內的五個領域，未來可探討技能在跨網站、跨領域情境下的可遷移性，以及領域適應（domain adaptation）策略。第四，錯誤軌跡的利用：目前僅從成功軌跡萃取技能，如何從失敗案例進行反事實學習或負面技能歸納，將是提升樣本效率的重要課題。第五，與參數化記憶結合：將非參數化的技能檢索與模型微調或 adapter-based 持續學習結合，可能進一步縮短檢索延遲並深化技能內化。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文聚焦於網頁智能體在「線上技能學習」過程中普遍存在的靜態任務層級技能重用問題。現有方法通常在任務開始時根據初始任務指令檢索一組固定技能，並在整個執行過程中維持不變，無法因應網頁狀態的動態變化。作者指出，這種設計忽略了互動式網頁自動化的本質，因為適當的下一步動作不僅取決於任務目標，更高度依賴當前的網頁狀態。

**Q2：為什麼現有的任務層級一次性技能重用方法在網頁自動化場景中會失效？**
A：現有方法將技能重用視為一次性操作，僅在任務初始階段根據指令檢索技能，但網頁執行過程中的互動情境會不斷改變。智能體在執行過程中可能進入表單、新頁面或不同的互動脈絡，導致初始有用的技能變得無關，而原本未被選中的技能反而變得必要。這種靜態策略的根本缺陷在於檢索發生在任務層級，而非智能體實際需要調用技能的中間執行狀態層級。

**Q3：解決這個問題為什麼對真實世界的網頁智能體部署很重要？**
A：在真實世界部署中，任務是序列式到達的，智能體必須持續從過往經驗中學習並即時改進，而非依賴離線預建的函式庫。若技能無法根據當前網頁狀態動態調整，智能體在面對複雜多步驟任務時將頻繁遇到狀態錯配，導致執行中斷或失敗。因此，讓技能檢索與調用能夠緊密貼合不斷演變的執行狀態，是提升線上範式下網頁智能體穩健性與效率的關鍵。

**Q4：SGDR 的核心方法架構包含哪三個主要元件，各自扮演什麼角色？**
A：SGDR 包含滑動視窗萃取、文字-程式碼雙重表示法，以及基於狀態的動態檢索機制三個核心元件。滑動視窗萃取負責從已完成軌跡中產出可在中間執行狀態調用的子程序，解決技能粒度的挑戰；雙重表示法透過自然語言描述支援檢索，同時以可執行程式碼對應瀏覽器動作，橋接檢索與執行之間的鴻溝。基於狀態的動態檢索機制則在每一步決策時，同時比對任務指令與當前網頁狀態，動態檢索最合適的技能。

**Q5：論文提出的「粒度挑戰」是什麼？SGDR 如何透過滑動視窗萃取來解決它？**
A：粒度挑戰指的是技能函式庫若只包含完整軌跡技能，難以適配任意的中間網頁狀態；若只包含單一動作技能，則又過於原始而無法提供有意義的程序抽象。SGDR 採用滑動視窗萃取，從已完成軌跡中提取可重複使用的子程序，產出介於完整軌跡與單一動作之間的中間粒度技能。這種設計讓技能既足夠緊湊以匹配多樣的網頁狀態，又具備足夠的結構以執行有用的瀏覽器操作。

**Q6：為什麼 SGDR 需要「文字-程式碼雙重表示法」？這個設計如何促進技能的動態重用？**
A：雙重表示法的設計是為了同時滿足技能檢索與可執行性的雙重需求，因為自然語言便於語義匹配與檢索，但無法直接操作瀏覽器，而原始程式碼可執行卻不易於根據任務目標進行語義檢索。透過將每個技能表示為文字-程式碼配對，SGDR 能夠利用自然語言描述在大量累積技能中快速定位相關子程序，同時透過可執行程式碼直接產生對應的瀏覽器動作。這種橋接確保了動態檢索出的技能不僅語義相關，更能立即在當前網頁狀態下付諸執行。

**Q7：實驗是在哪個基準上進行的？測試涵蓋了哪些領域或設定？**
A：實驗在 WebArena 基準上進行，該基準模擬真實世界的網站互動環境，是評估網頁智能體能力的標準平台。測試橫跨五個不同的網站領域，涵蓋多樣化的網頁結構與互動模式，以驗證方法的泛化能力。此外，作者採用序列任務流設定，智能體只能重用從過往任務軌跡中歸納出的技能，並在執行過程中動態更新技能函式庫，模擬真實的線上學習情境。

**Q8：SGDR 在實驗中達成了哪些關鍵數據成果？與最強基線相比表現如何？**
A：在 WebArena 的五個領域中，SGDR 使用 GPT-4.1 達到平均 37.5% 的成功率，使用 Qwen3-4B 達到 24.3% 的成功率。與最強基線相比，這分別對應了 10.6% 與 10.0% 的相對提升幅度，顯示出一致且顯著的效能增進。這些結果證明了基於狀態的動態檢索機制在不同骨幹模型上皆能有效提升多步驟網頁自動化的表現。

**Q9：實驗除了成功率之外，還評估了哪些指標？這些結果如何驗證 SGDR 各個設計選擇的有效性？**
A：實驗在 WebArena 上同時評估了成功率與步驟效率，結果顯示 SGDR 在這兩項指標上均優於強大的線上技能學習基線。雖然提供的節錄未詳細列出傳統的消融實驗表格，但論文透過跨五個領域與兩種骨幹模型的廣泛驗證，間接證明了滑動視窗萃取、雙重表示法與動態檢索三者協同運作的必要性。這種跨模型與跨領域的一致性提升，說明了狀態層級檢索與中等粒度技能表示確實是帶來效能增益的關鍵因素，而非特定模型或領域的偶然結果。

**Q10：SGDR 的方法最適合應用在哪些真實的網頁自動化場景？**
A：SGDR 特別適合需要長期互動、頁面狀態頻繁轉換的網頁任務，例如跨頁面表單填寫、電子商務網站的購物流程、或企業內部網頁應用程式的多步驟資料處理。在這些場景中，初始任務指令往往無法預測所有中間頁面的具體結構，因此需要根據當前網頁狀態動態調用過去學到的子程序。透過逐步檢索與重用技能，智能體能夠像人類一樣根據頁面變化靈活調整策略，而非僵化地遵循預設腳本。

**Q11：若要將 SGDR 整合到實際的產品或網頁智能體服務中，有哪些工程考量？**
A：在產品化過程中，需要建立高效的技能函式庫索引與檢索系統，以支援每一步決策時的即時狀態匹配，這對延遲與計算成本提出了要求。此外，由於技能是從過往軌跡中線上歸納而來，必須設計有效的品質控管與過濾機制，避免錯誤或過時的子程序被重複調用。同時，雙重表示法要求系統同時維護自然語言嵌入與可執行程式碼，這增加了儲存與版本管理的複雜度，但換來的是更高的執行靈活性與任務成功率。

**Q12：這項研究對網頁智能體與線上技能學習領域可能帶來什麼深遠影響？**
A：SGDR 將線上技能學習的焦點從「任務層級的靜態記憶」轉向「狀態層級的動態程序重用」，為後續研究開啟了新的設計範式。這項工作證明了在互動式環境中，檢索機制必須與執行時的環境狀態緊密耦合，而非僅依賴高層次指令，這可能影響未來網頁智能體的記憶體架構與工具學習框架。此外，透過展示中等粒度子程序的價值，該研究也為技能歸納的粒度選擇提供了重要的理論與實證依據。

**Q13：這篇論文有沒有提及 SGDR 的潛在限制或適用邊界？**
A：從提供的節錄可以推論，SGDR 的效能高度依賴技能函式庫的品質與覆蓋範圍，若過往任務軌跡稀少或與新任務差異過大，動態檢索可能難以找到匹配當前狀態的合適技能。此外，滑動視窗萃取產生的子程序雖然在粒度上取得平衡，但在極為複雜或罕見的網頁互動情境下，仍可能出現語義覆蓋不足的問題。論文也暗示了檢索品質同時受匹配機制與技能粒度影響，意味著在極大規模的任務流中，檢索雜訊與累積錯誤仍是需要關注的挑戰。

**Q14：在什麼樣的任務或網頁環境中，SGDR 可能會遭遇失敗或表現不佳？**
A：SGDR 可能在網頁結構高度動態且與過往經驗幾乎無重疊的環境中表現受限，例如頻繁改版且無規律的現代網頁應用程式，因為此時狀態匹配難以找到歷史對應。如果任務需要大量探索性行為而非結構化的子程序重用，動態檢索的優勢也可能被削弱，因為累積的技能庫缺乏可重用的穩定模式。此外，在骨幹模型本身對網頁狀態理解能力不足的情況下，即使檢索機制完善，錯誤的狀態表徵仍會導致技能誤配與執行失敗。

**Q15：基於 SGDR 的架構，未來研究可以朝哪些方向進一步延伸與改進？**
A：未來研究可以探索更細緻的技能組合機制，例如讓智能體在單一步驟中串接多個子程序，或根據狀態變化自動調整技能粒度。另一個方向是結合視覺資訊進行多模態狀態表徵，使檢索不僅基於文字化的網頁狀態，還能納入版面配置與視覺元素，進一步提升匹配精準度。此外，將 SGDR 的動態檢索框架擴展到網頁智能體以外的互動式環境，如行動應用程式或桌面軟體自動化，也是極具潛力的後續發展路徑。

## 實務應用指南

### 適用場景

1. **跨系統企業流程自動化**：適用於需在 ERP、CRM、HR 或財務系統間執行多步驟操作的場景。例如，客服人員需在 Salesforce 查詢客戶後，再至後台訂單系統修改地址並寄送通知；SGDR 能依據「當前網頁狀態」動態檢索對應子程序，而非僅在任務開始時固定載入一套流程。
2. **電商營運與上架作業**：賣家需在後台執行重複但情境多變的操作，如根據庫存頁面狀態決定是否調整價格、依據活動報名頁面的即時回饋填寫不同表單。逐步技能重複使用可讓智能體在面對不同互動情境時，自動叫用過去學會的局部操作片段。
3. **金融與對帳資料擷取**：銀行或證券從業人員需定期登入多個網銀或投資平台下載報表。由於各網站流程與驗證頁面經常變動，基於狀態的動態檢索能在遇到熟悉的驗證或報表頁面時，自動喚起對應的瀏覽器動作序列，提升長期維運穩定性。
4. **旅遊與訂房比價代理**：在訂房或訂票流程中，頁面狀態會隨著日期選擇、艙等變化而動態轉換。SGDR 可將過去成功的軌跡透過滑動視窗萃取為可重複使用技能，在面對類似的搜尋結果頁或付款頁時，自動重用先前學到的中間執行狀態策略。
5. **SaaS 產品內部自動化測試**：QA 團隊在進行端到端網頁測試時，可將 SGDR 作為持續學習的測試機器人。隨著測試任務流不斷執行，技能函式庫會自動累積常見的登入、表單填寫與導航子程序，降低後續測試案例的維護成本。

### 實作前置條件

**資料需求**：
- 序列任務流：需能持續產生連續到達的網頁自動化任務，並附帶明確的成功與否評估訊號（evaluator-assessed trajectories）。
- 網頁觀測紀錄：每個決策步驟需保留當前網頁狀態，建議同時收錄 DOM 結構與可視化截圖，以便建立穩定的狀態表示。
- 歷史軌跡庫：至少需有數十至數百條成功執行的軌跡作為冷啟動素材，用於初始技能歸納。

**運算資源**：
- 骨幹模型推論端點：需能呼叫 GPT-4.1 等級的模型進行高品質技能萃取，或部署 Qwen3-4B 等開源模型以控制成本。
- 向量資料庫：用於儲存技能的自然語言描述嵌入（embedding）並支援即時近似最近鄰搜尋。
- 瀏覽器自動化基礎設施：如 Playwright 或 Selenium 叢集，確保可並行執行與錄製軌跡。

**能力與人力前提**：
- 團隊需熟悉瀏覽器自動化與提示工程（prompt engineering）。
- 具備向量檢索與線上學習（online learning）基礎知識，能調整檢索粒度與相似度閾值。
- 建議配置領域專家審核初期萃取出的技能，避免錯誤操作被重複使用。

### 實作步驟建議

**步驟一：建構瀏覽器環境與狀態紀錄層**
部署無頭瀏覽器叢集，確保每個決策步驟都能輸出結構化網頁狀態（DOM + 元素屬性）與執行動作紀錄。此為後續狀態比對與技能萃取的基礎。

**步驟二：建立序列任務流與評估管線**
將業務任務設計為連續到達的任務流，並建立自動化評估器（evaluator）判斷任務是否成功完成。只有被標記為成功的軌跡才會進入後續技能函式庫更新流程。

**步驟三：實作滑動視窗萃取**
針對成功軌跡，使用滑動視窗將完整軌跡切割為長度適中的子程序。建議從視窗大小 3–5 個動作開始實驗，確保技能粒度既能對應多樣的網頁狀態，又保有足夠的程序抽象層次。

**步驟四：設計文字-程式碼雙重表示法**
每個萃取出的技能需同時具備：
- **文字面**：自然語言描述（如「在搜尋結果頁篩選價格由低到高」），用於嵌入與語意檢索。
- **程式碼面**：可執行的瀏覽器動作序列（如 Python/Playwright 腳本），確保檢索後能直接執行，無需額外生成動作。

**步驟五：建置基於狀態的動態檢索機制**
在每一步決策前，將「初始任務指令 + 當前網頁狀態」編碼為查詢向量，從技能函式庫中檢索 Top-K 最相關技能。建議採用雙塔模型或稠密向量檢索，並針對網頁狀態設計專屬編碼器（例如保留結構化 DOM 路徑與語意內容）。

**步驟六：運行線上學習迴圈**
依序執行任務 → 評估成功與否 → 從成功軌跡萃取新技能 → 更新向量資料庫。定期執行技能去重複化（deduplication）與品質過濾，避免函式庫膨脹。

**步驟七：生產環境強化**
加入技能版本控制、A/B 測試機制與人工審核閘道。對於涉及敏感操作（如付款、刪除資料）的技能，強制進入人工確認流程後才開放自動重用。

### 潛在風險與注意事項

- **粒度錯配風險**：滑動視窗過大會導致技能難以匹配中間執行狀態；過小則淪為單一動作技能，失去程序抽象價值。**緩解方式**：依據目標網站的互動複雜度動態調整視窗大小，並監控技能被成功調用的平均覆蓋步數。
- **網頁狀態漂移**：目標網站改版會使歷史技能的程式碼面失效（例如 CSS selector 改變）。**緩解方式**：狀態編碼應偏重語意結構（如元素角色、相對位置、文字內容）而非絕對路徑；同時為技能設定存活時間（TTL），定期淘汰久未命中或執行失敗的技能。
- **檢索延遲累積**：逐步技能重複使用意味著每個決策步驟都要執行一次向量搜尋，可能拖慢執行速度。**緩解方式**：導入快取層（如 Redis）儲存高頻率任務-狀態組合的檢索結果，並使用近似最近鄰（ANN）演算法降低延遲。
- **錯誤技能污染**：若評估器誤判失敗軌跡為成功，錯誤子程序將進入技能函式庫並被後續任務重用，造成錯誤放大。**緩解方式**：採用多層次評估（如結合規則檢查與 LLM 評分），並對新任務啟用「觀察模式」：先記錄技能調用效果，確認無誤後再正式寫入函式庫。
- **隱私與資安外洩**：軌跡與技能可能夾帶敏感資料（如個資、密碼、內部網址）。**緩解方式**：萃取前執行 PII 脫敏與欄位遮罩；技能函式庫應分域隔離並設置權限控管。

### 與其他技術的整合建議

- **企業 RAG 與知識庫**：將 SGDR 的技能函式庫視為 RAG 系統中的特殊文件集合。可透過現有的向量資料庫（如 Pinecone、Milvus、Weaviate）統一管理，並讓網頁智能體與其他部門的問答智能體共享底層檢索基礎設施。
- **代理協作框架（LangChain / CrewAI / AutoGen）**：把 SGDR 封裝為一個具備「記憶與學習」能力的工具模組。當多智能體協作時，SGDR 模組負責瀏覽器操作面的技能累積與調度，其他智能體則專注於任務規劃與使用者對話。
- **視覺-語言模型（VLM）**：若網站大量使用前端框架導致 DOM 語意稀疏，可將截圖輸入 VLM 以增強當前網頁狀態的表示，再與 DOM 特徵融合後進行狀態比對，提升動態檢索的準確度。
- **低程式碼 RPA 平台（UiPath、Blue Prism）**：將 SGDR 萃取出的可執行技能轉譯為 RPA 平台可讀的活動（Activity）或元件。企業可藉此把 AI 自動發現的最佳實踐，快速轉化為 citizen developer 可拖曳使用的標準化模組。
- **可觀測性與 APM 工具**：整合 Datadog、LangSmith 或自研監控，追蹤「技能檢索命中率」、「技能執行成功率」與「步驟效率」等指標，作為線上學習健康度的早期預警系統。

### 給不同背景讀者的閱讀建議

**給初學者**：請將本文想像成「會自動進化的智慧剪貼簿」。傳統做法是在任務一開始就貼上一整份固定食譜，而 SGDR 則是在你每翻開一頁新網頁時，自動從過去經驗中挑出最適合當下情境的幾個步驟來幫你。建議從圖 2 的線上學習迴圈與「任務層級 vs. 逐步重用」的對照開始理解，不必急著深入技術細節。

**給 AI 工程師**：本文的實作價值集中在滑動視窗萃取的參數調校、文字-程式碼雙重表示法的儲存格式，以及狀態編碼與向量相似度計算的設計。建議重點研讀方法章節中如何將「當前網頁狀態」與「任務指令」共同編碼為檢索查詢，並評估你目前使用的嵌入模型是否能有效區分不同互動情境下的網頁狀態。

**給研究人員**：核心貢獻在於將線上技能學習從靜態的任務層級檢索，推進到基於狀態的動態檢索。建議深入分析 WebArena 跨五個領域的實驗設計，特別關注不同骨幹模型（GPT-4.1 與 Qwen3-4B）下的相對提升幅度，思考狀態表示的泛化性與技能粒度之間的理論權衡。

**給產品經理**：請聚焦「無需重新訓練、隨著使用自動變強」的商業價值。SGDR 的線上範式意味著部署後的邊際成本會隨時間下降，而成功率會隨任務流累積上升。建議對照 WebArena 的五個評測領域，盤點自家產品中哪些高頻、多步驟的網頁操作流程最適合導入；同時評估 GPT-4.1 與 Qwen3-4B 的成本效益比，以決定初期採用雲端 API 或本地部署的策略。
