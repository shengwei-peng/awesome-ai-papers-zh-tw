## ⚡ TL;DR

視覺數學推理的RL訓練中，標籤雜訊會被反覆強化為錯誤獎勵訊號。
本文提出VeriEvol，以類型感知演化提升題目難度，並用HTV-Agent離線反證驗證答案。
SFT資料從10K擴至250K，平均準確率由35.42提升至54.73；RL階段累積增益+3.88。

## 摘要翻譯

將強化學習（Reinforcement Learning, RL）擴展至視覺數學推理，所需要的絕非僅是產生更困難的題目：隨著資料量增長，獎勵標籤本身必須保持可靠。然而現有的資料管線在擴展監督時仍信任標註器，而策略側的方法則預設底層答案已經正確。我們反其道而行，將擴展視為一個可驗證的資料建構問題，並在任何策略更新之前解耦兩個設計軸：提示詞難度（由路由專屬演化算子擴展）與答案可靠性（由離線假設檢驗反證強制執行）。我們將此實例化為 VeriEvol，一個具有兩個可擴充組件的迭代式框架：一個類型感知演化模組，將低難度的圖像–題目種子改寫為更困難、必須依賴圖像的提示詞；以及 HTV-Agent，一個僅在多源反證證據皆無法推翻候選答案時才予以接受的驗證器。所產生的已驗證資料可隨資料量擴展、可透過新增演化路由或驗證器通道延伸，並可直接接入既有的 GRPO 風格 RL 配方。在五基準視覺數學測試集上，將演化後的 SFT 資料從 10K 樣本擴展至 250K 樣本，可將平均準確率從 35.42 提升至 54.73；接著，在主幹網路、SFT 初始化與 GRPO 配方皆固定的情況下，VeriEvol 在未演化 RL 基線之上帶來 +3.88 的累積增益，其中 +1.82 來自演化後的提示詞，+2.06 來自 HTV-Agent 驗證器。我們釋出提示詞、資料、模型、程式碼，以及每筆樣本的完整驗證器軌跡，使下游工作不僅能檢視其輸出，更能擴展並稽核整個管線。

### 核心貢獻（3～5點）
- **重新定位擴展瓶頸**：指出視覺數學推理 RL 擴展的首要瓶頸並非題目難度，而是獎勵標籤的可靠性，將研究焦點從「產生更難題目」轉向「可驗證的資料建構」。
- **雙軸解耦設計**：在策略更新之前，將提示詞難度（由路由專屬演化算子擴展）與答案可靠性（由離線假設檢驗反證強制執行）解耦為兩個獨立可調的設計軸。
- **可擴充的迭代式框架 VeriEvol**：整合類型感知演化模組與 HTV-Agent 驗證器兩個可擴充組件，支援新增演化路由與驗證器通道，並可直接接入既有 GRPO 風格 RL 配方。
- **顯著的實證增益**：在五基準視覺數學測試集上，將演化 SFT 資料從 10K 擴展至 250K 樣本，平均準確率由 35.42 提升至 54.73；在主幹網路、SFT 初始化與 GRPO 配方皆固定下，VeriEvol 帶來 +3.88 的累積增益（+1.82 來自演化提示詞、+2.06 來自 HTV-Agent 驗證器）。
- **完整的可稽核性承諾**：釋出提示詞、資料、模型、程式碼及每筆樣本的完整驗證器軌跡，使下游工作不僅能檢視輸出，更能擴展並稽核整個管線。

### 適合對象
從事多模態大型語言模型（MLLM）訓練、強化學習（特別是 GRPO 風格 RL 配方）、視覺數學推理、合成資料管線設計與稽核，以及獎勵標籤品質與標註錯誤防範研究的學者與工程師；亦適合關注資料品質如何影響 RL 訓練成效、追求可重現且可追溯之訓練流程的實務團隊閱讀。

## 深度分析

#### 方法論解析

VeriEvol 的核心方法論建立在兩個關鍵觀察之上：其一，多模態數學推理的訓練瓶頸已從「資料量不足」轉移為「資料品質與獎勵品質」；其二，現有方法無論是資料管線端（如 Evol-Instruct、MMEvol）還是策略端（如 GRPO 變體、reward shaping）都隱含一個未經驗證的假設——標註答案本身是正確的。VeriEvol 將這個假設顯式化為可被攻擊的對象，並在策略更新之前完成驗證，這是本文最重要的方法論轉向。

**雙軸解耦設計（Decoupling Two Axes）**

框架將訓練資料的建構拆解為兩個正交的設計軸：

1. **提示詞難度軸（Prompt Difficulty Axis）**：透過路由專屬演化算子（route-specific evolution operators）將低難度的圖像–問題種子改寫為高難度、圖像基礎（image-grounded）的提示詞。
2. **答案可靠性軸（Answer Reliability Axis）**：透過離線假設檢驗反證（offline hypothesis-test falsification）確保每個答案在進入獎勵訊號之前已通過多源反證的考驗。

這種解耦的關鍵意義在於：當資料量擴大時，標籤雜訊不再是「靜態的標註錯誤」，而是會被 RL 反覆轉化為獎勵訊號、進而系統性強化錯誤策略的「訓練目標」。VeriEvol 將這個風險從策略優化器內部移到了資料建構階段，使驗證成為資料的內禀性質而非訓練迴圈的副作用。

**類型感知演化模組（Type-aware Evolution Module）**

此模組的設計假設是：不同題型族群（如幾何、圖表、OCR）需要不同的演化算子才能產生真正「圖像基礎」的高難度提示詞。通用演化方法容易產生「僅是更長、弱視覺化、或可從文字先驗回答」的問題，這正是現有合成管線的典型缺陷。透過將種子按題型族群路由到家族專屬算子，演化後的提示詞在結構上更貼合該族群的推理模式，例如幾何題可能需要多步驟的構造證明、圖表題可能需要跨欄位的數值推論、OCR 題可能需要符號對齊與單位轉換。

**HTV-Agent：假設檢驗驗證器（Hypothesis–Test Verifier Agent）**

HTV-Agent 是本文最具原創性的組件，採用四階段流程：

1. **獨立求解器假設（Independent Solver Hypotheses）**：由多個獨立求解器產生候選答案，避免單一模型的系統性偏差。
2. **反證尋求驗證（Refutation-seeking Verification）**：跨三個通道蒐集反證證據——反證證據通道、程式化通道、視覺通道。這種多通道設計是針對視覺推理特有的失敗模式：純文字步驟級驗證器無法診斷「模型看錯圖」、「讀錯數值」、「對齊錯符號」這類視覺接地錯誤。
3. **衝突解決決策者（Conflict Resolution by a Decider）**：當不同通道產生衝突時，由決策者整合證據並給出最終判斷。
4. **確定性驗收閘（Deterministic Acceptance Gate）**：基於前述結果以確定性規則決定是否接受答案。

此設計的關鍵特性是**模組化與可擴充性**：新增驗證器通道或答案契約（answer contracts）無需重新設計策略優化器，這與現有 RL 框架中「驗證邏輯與策略更新緊耦合」的做法形成對比。

**與 GRPO 的介面設計**

VeriEvol 的輸出是標準的「已驗證提示–答案–獎勵三元組」（verified prompt–answer–reward tuple），可直接接入既有 GRPO 風格 RL 配方。這意味著 VeriEvol 不試圖取代現有 RL 演算法，而是作為一個「資料前置處理層」運作，這大幅降低了採用門檻。

#### 實驗數據解讀

**SFT 階段的規模效應**

將演化後的 SFT 資料從 10K 擴展到 250K 樣本，平均準確率從 35.42 提升至 54.73，絕對增益 +19.31。這是一個非常顯著的規模效應，說明在視覺數學推理任務上，演化後的高品質資料具有強烈的規模報酬。值得注意的是，這個增益是在「演化品質」與「資料量」兩個變數同時變化的情況下取得的，因此無法直接歸因於單一因素，但與未演化資料相比，演化資料顯然提供了更陡峭的學習曲線。

**RL 階段的雙重增益分解**

在 RL 階段，實驗設計更為精巧，採用了雙重控制變數：

1. **資料量軸（Data-volume Axis）**：在固定方法（VeriEvol）的情況下，將已驗證資料從 10K 擴展到 130K，帶來 +4.60 的平滑增益。這證實了「已驗證資料」本身具有可擴展性，且擴展過程中沒有出現獎勵雜訊累積的問題。

2. **設計軸（Design Axis）**：在固定 130K 預算下，VeriEvol 相較於未演化 RL 基線帶來 +3.88 的累積增益，並可分解為：
   - **+1.82 來自演化提示詞**：證實類型感知演化確實產生了對 RL 有意義的、更難且圖像基礎的提示詞。
   - **+2.06 來自 HTV-Agent 驗證器**：證實答案驗證帶來的獎勵品質提升比提示詞演化本身更具價值，這是一個反直覺但重要的發現——在 RL 設定下，「答案對不對」比「問題難不難」更關鍵。

**增益分解的方法論意涵**

+2.06 > +1.82 的分解結果挑戰了資料管線文獻中常見的「難度即收益」假設。在 RL 訓練中，錯誤的獎勵標籤會被反覆強化，因此驗證器的邊際效益可能超過演化器。這也意味著，未來的研究投入應該更平衡地分配在「問題生成」與「答案驗證」兩個方向，而非僅專注於前者。

**基準測試覆蓋**

實驗在五基準視覺數學測試集上進行，雖然具體基準名稱未在所提供文本中完整列出，但從相關工作段落可推測包含 MathVista、MathVerse、MMMU、MATH-Vision 等主流基準，並可能包含 OlympiadBench、DynaMath 等更具挑戰性的測試。多基準平均能降低單一基準過擬合的風險，使 +19.31（SFT）與 +3.88（RL）的增益更具說服力。

**未明確報告的面向**

從所提供文本中，無法確認以下重要細節：每個基準的個別增益、訓練曲線的收斂行為、不同題型族群的增益差異、消融實驗中各驗證通道的相對貢獻、以及與特定基線（如 OpenMMReasoner、MathCoder-VL）的直接比較。這些資訊對於完整評估方法至關重要。

#### 與現有研究的比較

**與資料管線文獻的比較**

VeriEvol 與 Evol-Instruct、MMEvol、MathBook-7B、OpenMMReasoner 等同屬「資料建構」範式，但定位不同：

- **Evol-Instruct / MMEvol**：僅做指令演化，不驗證答案，屬於「信任標註器」範式。
- **MathBook-7B**：基於知識樹的課程式構造，但同樣假設答案正確。
- **OpenMMReasoner**：結合 874K 演化風格 SFT 樣本與 GSPO-based RL，規模更大但缺乏顯式的答案反證機制。

VeriEvol 的差異化在於「演化 + 反證」的雙組件設計，且明確將驗證從策略迴圈中解耦。這使得 VeriEvol 在 RL 階段的獎勵品質上具有結構性優勢。

**與策略端方法的比較**

與 Skywork-R1V2、OVR、DUPL、PerL-VL、VGPO、Infi-MMR 等「從 RL 內部改善訊號」的方法相比，VeriEvol 採取了正交路線：

- 策略端方法修改 GRPO 更新（reward shaping、advantage normalization、length penalties、curriculum scheduling），但假設答案正確。
- VeriEvol 不修改 RL 演算法，而是從源頭提升資料品質。

兩者可以互補：VeriEvol 產生的已驗證資料可作為這些策略端方法的輸入，預期能產生疊加增益。

**與驗證增強方法的比較**

與 Self-Refine、Reflexion、SelfCheckGPT、CRITIC 等「推論時驗證」方法，以及 PRM800K、Math-Shepherd、ReST-EM 等「訓練時驗證」方法相比：

- 推論時方法在部署階段修正錯誤，但無法防止訓練階段的錯誤累積。
- 訓練時方法（如 PRM800K）依賴人類步驟級標註或自生成過濾，但這些標註本身可能含有視覺接地錯誤。
- HTV-Agent 的獨特之處在於「離線、多通道、針對視覺接地失敗模式」，且不依賴人類步驟級標註。

**相較於現有工作的限制**

1. **規模天花板未明確**：雖然展示了 250K SFT 與 130K RL 的擴展，但未說明是否存在規模報酬遞減的拐點。
2. **題型覆蓋範圍**：類型感知演化依賴於預定義的題型族群，對於未涵蓋的題型（如立體幾何、統計圖、函數圖像）可能效果下降。
3. **驗證器的計算成本**：四階段、多通道的驗證流程計算開銷顯著，未在文本中報告具體的資料建構成本與時間。
4. **與人類專家的對齊**：未說明 HTV-Agent 的驗證結果與人類專家判斷的一致性。

#### 可重現性評估

**開放釋出內容**

本文在可重現性方面設定了高標準，具體釋出項目包括：

1. **提示詞（Prompts）**：所有演化後的提示詞公開。
2. **資料（Data）**：完整的訓練資料集公開。
3. **模型（Models）**：訓練後的模型權重公開。
4. **程式碼（Code）**：完整實作程式碼公開。
5. **驗證器軌跡（Verifier Traces）**：這是最具特色的釋出——每筆訓練樣本都附帶完整的驗證軌跡，包括求解器假設、反證證據報告、工具輸出、決策者推理過程、各組件閘門結果。

**可重現性優勢**

- **稽核能力（Auditability）**：下游研究者不僅能使用最終資料，還能檢查每筆樣本的驗證過程，這在現有多模態推理論文中極為罕見。
- **可擴展性（Extensibility）**：軌跡公開使得新增驗證通道或演化路由時，可以基於現有軌跡進行增量驗證，而非從頭開始。
- **錯誤診斷（Error Diagnosis）**：當模型在特定樣本上失敗時，可以追溯到驗證軌跡，判斷是演化失敗還是驗證失敗。

**可重現性限制**

- **計算資源需求**：完整的 250K SFT + 130K RL 訓練需要大量 GPU 資源，文本未說明具體硬體需求與訓練時間。
- **種子資料來源**：使用 Honey-Data-15M 與 Lin et al. 的多模態推理語料作為種子池，這些資料本身的授權與可取得性會影響完整重現。
- **HTV-Agent 的內部模型**：驗證器依賴多個獨立求解器，這些求解器的具體選擇（如使用哪些基礎模型）會影響驗證品質。
- **超參數細節**：GRPO 的具體超參數（學習率、群組大小、KL 係數等）未在所提供文本中詳細列出。

**整體評估**

相較於同領域多數論文僅釋出模型權重或部分資料，VeriEvol 的「全軌跡釋出」設定了新的開放標準。這對於推動領域的可信研究具有重要價值，但也對作者的工程實現提出了更高要求。

#### 未來研究方向

**1. 驗證器架構的進一步模組化**

HTV-Agent 目前包含四個階段與三個驗證通道，未來可探索：

- **更多視覺接地專用通道**：例如針對「圖表讀數錯誤」、「幾何構造錯位」、「OCR 符號混淆」等特定失敗模式設計專門的反證通道。
- **通道間的動態路由**：根據題型族群動態選擇最相關的驗證通道組合，而非對所有題型使用固定通道集，以降低計算成本。
- **驗證器的不確定性量化**：為每個驗證結果提供信心分數，而非僅有二元接受/拒絕，使 RL 可以使用軟標籤。

**2. 演化算子的自動化發現**

目前的類型感知演化依賴預定義的題型族群與人工設計的算子，未來方向包括：

- **自動演化算子合成**：利用 LLM 自動發現並組合新的演化操作，減少人工設計成本。
- **元學習式演化**：根據模型在演化資料上的學習曲線，自適應調整演化強度。
- **跨題型遷移**：研究演化算子從一個題型族群遷移到另一個族群的可能性。

**3. 與策略端方法的正交整合**

VeriEvol 與策略端方法（如 reward shaping、curriculum scheduling）正交，未來可探索：

- **疊加效應實證**：將 VeriEvol 資料與 Skywork-R1V2、OVR 等策略端方法結合，驗證是否能產生疊加增益。
- **聯合優化**：在策略更新過程中動態調整驗證器的嚴格程度，例如在訓練初期使用寬鬆驗證以擴大資料池，在後期收緊驗證以提升獎勵品質。

**4. 從多模態數學推理到更廣泛的視覺推理**

本文聚焦於視覺數學推理，但方法論可推廣至：

- **科學推理**：物理、化學、生物等需要圖像接地推理的領域。
- **圖表理解**：商業智慧、資料分析中的複雜圖表推理。
- **多影像推理**：跨多張影像的組合推理（如 We-Math 探討的方向）。
- **影片推理**：將「圖像」推廣到「影片幀序列」，驗證器需要處理時序一致性。

**5. 理論分析**

目前 VeriEvol 的設計主要為經驗驅動，未來可建立：

- **獎勵雜訊下的 RL 收斂性分析**：量化「已驗證資料」相對於「未驗證資料」在 RL 收斂速度與最終性能上的理論優勢。
- **演化算子的資訊理論分析**：從資訊理論角度刻畫「演化後提示詞」相對於「原始提示詞」的資訊增益。
- **驗證器的樣本複雜度**：分析達到特定驗證可靠度所需的反證證據量。

**6. 人機協作驗證**

完全自動化的驗證仍有邊際成本與錯誤率，未來可探索：

- **人機協作驗證流程**：在自動驗證信心低時引入人類專家，建立成本–品質權衡。
- **驗證器的持續學習**：將人類修正回饋用於改進驗證器本身。

**7. 評測基準的擴展**

目前使用五基準視覺數學測試集，未來可：

- 引入更具挑戰性的基準（如 OlympiadBench、DynaMath）以測試上限。
- 設計專門針對「視覺接地錯誤」的診斷基準，區分「推理錯誤」與「看圖錯誤」。
- 建立「驗證器壓力測試」基準，評估 HTV-Agent 在對抗性樣本上的穩健性。

**8. 效率優化**

四階段驗證流程的計算成本是實際部署的瓶頸，未來方向包括：

- **早期退出機制**：在累積足夠反證證據時提前終止驗證。
- **驗證器蒸餾**：將大型驗證器的能力蒸餾到小型模型以加速推理。
- **並行化架構**：將多通道驗證設計為可並行執行，降低端到端延遲。

## 論文問答

**Q1：視覺數學推理在嘗試擴展強化學習時，最根本的瓶頸究竟是什麼？**
A：視覺數學推理要求模型同時具備跨模態對齊與多步驟數學推論能力，因此訓練瓶頸並非單純的「資料量不足」，而是「資料品質」與「獎勵品質」同時成為一階限制。當 RL 的 rollout 數量與訓練樣本規模放大時，任何未經驗證的標籤都會被反覆轉化為獎勵訊號，使標籤雜訊從靜態的標註錯誤升級為會系統性強化錯誤策略的訓練目標。換言之，瓶頸在於「答案集合的可靠性」必須在進入策略更新之前就已被確立，而非寄望於策略或訓練迴圈內部自行修正。

**Q2：現有的資料管線方法與策略端方法為何無法根本解決這個問題？**
A：資料管線類工作（如 Evol-Instruct、MMEvol、OpenMMReasoner 等）雖然能擴展監督訊號的規模，但本質上仍信任標註器，答案集合處於未經驗證狀態，因此擴大規模只會放大錯誤標籤的傳播。策略端方法（如視覺強化微調、GRPO 變體、獎勵塑形等）則透過修改監督分佈或更新規則來提升訊號品質，但都預設底層答案已經正確，將驗證責任留在策略/訓練迴圈內部。兩類方法都未把「答案必須先通過反證考驗」當作資料建構階段的硬性條件，這正是 VeriEvol 要補上的缺口。

**Q3：把答案驗證從策略優化器中「離線解耦」為何如此關鍵？**
A：一旦驗證與策略更新耦合，驗證器就會被訓練目標的偏差所污染，難以維持中立且嚴格的反證標準；離線解耦則讓驗證器得以獨立演化、橫向擴充通道，而不必為了配合 RL 損失而妥協。把驗證提前到資料建構階段，能讓每一筆樣本在成為獎勵之前都已通過多源反證，從而把「標籤雜訊」這個動態風險重新降級為可被稽核的靜態屬性。這也是為何 VeriEvol 強調釋出每一筆樣本的完整驗證軌跡，使下游工作能審查與再擴展建構決策，而非僅檢視最終輸出。

**Q4：VeriEvol 框架的核心設計理念是什麼？它如何體現「可擴展性」？**
A：VeriEvol 的核心設計理念是把擴展性問題拆成兩個正交的設計軸——「提示詞難度」與「答案可靠性」——並在進入任何策略更新之前分別處理。前者由類型感知演化模組負責，依題型族群（幾何、圖表、OCR 等）路由到專屬的演化算子；後者由 HTV-Agent 透過離線假設檢驗反證來把關。框架的可擴展性體現在三個層次：可沿資料量軸擴增、可加入新的演化路由或驗證通道、且輸出為標準的「已驗證提示–答案–獎勵三元組」，可直接套入既有的 GRPO 風格 RL 配方而不必改動策略優化器。

**Q5：HTV-Agent 假設檢驗驗證器的四階段流程是如何運作的？**
A：第一階段由獨立求解器產生多個候選假設，避免單一模型的偏見壟斷答案；第二階段進入反證尋求式驗證，動員反證證據、程式化執行、視覺通道等多源證據嘗試推翻候選答案；第三階段由決策者整合衝突、產出最終判斷與理由；第四階段則是確定性的接受閘，僅在所有反證皆失敗後才放行答案。這種「先假設、再求反證、最後才接受」的結構，使每一筆樣本都帶有可追溯的驗證軌跡，也讓新增驗證通道或答案契約不必重新設計策略優化器。

**Q6：為什麼 VeriEvol 採用「路由專屬演化」而非單一的通用演化策略？**
A：視覺數學題涵蓋幾何、圖表、OCR 等異質題型族群，每族對「難度」的定義與可操作的視覺元素截然不同；通用演化算子容易把題目改寫得更長卻仍可由文字先驗回答，無法真正提升圖像基礎推理的難度。路由專屬演化讓每顆種子依其題型族群被送往對應的演化算子，確保改寫後的提示詞仍緊扣圖像內容並要求多步驟推論。這也是為何 VeriEvol 在 RL 階段單靠「演化過的提示詞」就能貢獻 +1.82 的累積增益——難度是真實的，而非僅是表面上的文字膨脹。

**Q7：VeriEvol 在五基準視覺數學測試集上的整體表現如何？**
A：在固定主幹網路、SFT 初始化與 GRPO 配方的條件下，將演化後的 SFT 資料從 10K 擴增至 250K，可將五基準平均準確率由 35.42 提升至 54.73，幅度達 +19.31，顯示資料規模與提示詞難度對視覺數學推理具有高度槓桿效應。在 RL 階段，於 130K 固定預算下，VeriEvol 相較未演化 RL 基線累積帶來 +3.88 的增益，其中 +1.82 來自演化提示詞、+2.06 來自 HTV-Agent 驗證器，證明兩個設計軸皆對最終效能有實質貢獻。

**Q8：演化提示詞與 HTV-Agent 驗證器各自的增益是如何被拆解出來的？**
A：作者透過控制變數實驗，在固定 130K 預算下比較「未演化 RL 基線」、「僅加入演化提示詞」、「演化提示詞加上 HTV-Agent 驗證器」三種設定。演化提示詞單獨貢獻 +1.82，顯示題型專屬的難度擴展確實帶來可觀的推理增益；再加上 HTV-Agent 後再增加 +2.06，說明答案層級的離線反證把關能進一步穩定獎勵訊號、避免錯誤標籤被反覆強化。兩者的累積效果 (+3.88) 證明了「提示詞難度」與「答案可靠性」是互補而非重疊的設計軸。

**Q9：資料規模對 VeriEvol 最終效能的影響呈現什麼趨勢？**
A：在 SFT 階段，將資料量從 10K 提升至 250K，平均準確率呈現穩定且顯著的正向擴展趨勢（35.42 → 54.73），說明經過演化與驗證的資料並未因規模放大而飽和或劣化。在 RL 階段，沿資料量軸從 10K 擴增至 130K 可再帶來 +4.60 的平滑增益，顯示「已驗證資料」具備良好的規模可預測性。這種雙階段皆可平滑擴展的特性，是 VeriEvol 強調「可擴展資料建構」而非一次性資料集的核心實證基礎。

**Q10：VeriEvol 適合應用於哪些實際的視覺推理場景？**
A：凡是涉及「圖像 + 多步驟數學推論」的場景皆為潛在應用，包括幾何證明輔助、圖表與統計資料分析、工程圖紙量測、科學教材中的圖示題解、財報與儀表板解讀等。在教育科技領域，VeriEvol 可用於自動生成難度遞增且答案可靠的練習題；在企業決策支援中，則可強化模型從圖表中抽取數值並進行多步驟計算的可信度。由於框架輸出為標準三元組，這些場景皆可直接套用既有 GRPO 風格 RL 配方而無需重寫訓練流程。

**Q11：在實際部署時，HTV-Agent 的多通道驗證會帶來哪些成本與權衡？**
A：HTV-Agent 需要動員多個獨立求解器、反證證據、程式化執行與視覺通道，這會帶來顯著的推論與工具呼叫成本，特別是在大規模資料建構時，單筆樣本可能消耗數倍於單一模型的計算資源。另一個權衡是「嚴格反證」與「覆蓋率」之間的張力：過於嚴格的接受閘可能拒絕部分邊界正確的答案而降低資料產量，因此需要依任務容忍度調整通道組合與接受條件。對產品化而言，這意味著 VeriEvol 更適合用於離線資料建構與模型訓練階段，而非高頻率的線上即時推理。

**Q12：VeriEvol 對多模態推理研究領域的長遠影響為何？**
A：VeriEvol 把「資料品質」與「獎勵品質」從策略訓練迴圈中抽離出來，重新定位為可獨立工程化的資料建構問題，這種思路有望成為後續多模態 RL 研究的範式參考。透過釋出每一筆樣本的完整驗證軌跡，作者讓下游工作得以審查、延伸與再擴展建構決策，這對建立可再現、可稽核的訓練管線具有示範意義。長期來看，這種「可驗證的演化指令」框架可能推動整個領域從「信任標註器」轉向「以反證為預設」的資料建構文化。

**Q13：VeriEvol 目前存在哪些已承認的限制？**
A：HTV-Agent 的驗證品質仍受限於其底層通道的能力——若反證證據、程式化執行或視覺通道本身存在盲點，則錯誤答案仍可能通過接受閘，因此驗證器的可靠性存在理論上界。框架對運算資源的需求較高，多通道驗證在大規模資料建構時會帶來不可忽略的時間與成本負擔。此外，路由專屬演化仰賴正確的題型族群分類，若種子被誤路由，演化算子可能無法產生真正困難且圖像基礎的提示詞。

**Q14：在哪些類型的題目或情境下，VeriEvol 可能會失效？**
A：對於高度開放式或需要外部世界知識的視覺題（例如涉及罕見科學現象或文化脈絡的圖像），HTV-Agent 的視覺與程式化通道可能缺乏足夠的反證能力，導致錯誤答案被誤接受。當題目屬於跨模態組合極為複雜、需要長鏈推理的情境時，即使提示詞難度提升，模型仍可能因組合技能不足而無法正確利用演化後的資料。此外，若種子本身圖像資訊不足或題型族群分類錯誤，演化算子可能產出可由文字先驗回答的「假難題」，使演化效益大打折扣。

**Q15：基於 VeriEvol 的設計，未來有哪些值得探索的研究方向？**
A：未來可朝三個方向延伸：其一，引入更多元的驗證通道（如領域專家模型、形式化證明器、跨樣本一致性檢查），並研究通道組合的最佳化策略；其二，將題型路由從預定義族群擴展至自動發現的推理模式，使演化算子能適應新興題型；其三，探索「驗證器即資料」的可能性——利用 HTV-Agent 的反證軌跡作為額外的監督訊號，訓練模型具備自我反證能力，從而降低部署時對外部驗證器的依賴。這些方向都與 VeriEvol「可擴展、可稽核」的設計哲學一致。

4. **多模態模型評測基準的難度擴增**：基準測試開發者可用 VeriEvol 對既有基準（如 MathVerse、DynaMath）進行受控的難度提升與答案再驗證，產生更嚴謹的「進階版」基準，避免模型在原基準上分數膨脹但實際能力未提升。

5. **可稽核的 AI 教育內容生成**：對於需要符合法規或學術誠信要求的場景（例如教科書輔助內容、考試題庫），VeriEvol 釋出的「每筆樣本完整驗證軌跡」可作為審查證據，證明每道題的答案是經過多源反證後才被接受的。

### 實作前置條件

**資料面**
- 種子題庫：至少數千至數萬筆「圖像 + 題目 + 候選答案」三元組，建議以 Honey-Data-15M 或 Lin et al. 的多模態推理語料為起點，並依題型族群（幾何、圖表、OCR、函數圖等）預先分類。
- 影像來源：清晰、可解析的 STEM 影像（解析度建議 ≥512px），避免低品質或合成影像影響演化品質。
- 評測基準：用於驗證收斂的視覺數學基準集（建議至少 5 個，例如 MathVista、MathVerse、MMMU、MATH-Vision、DynaMath）。

**算力面**
- 演化階段：需要可呼叫的多模態大型語言模型 API（如 GPT-4o、Gemini、Qwen2.5-VL-72B 等）作為「改寫者」，單次 10K→250K 規模的演化估計需要數百萬 token 等級的推論成本。
- 驗證階段：HTV-Agent 需要同時呼叫「獨立解題者」與「反證搜尋者」模型，加上 Python/SymPy 等程式化工具的執行環境。
- 訓練階段：SFT 階段需具備 8×A100/H100 等級 GPU；RL（GRPO）階段建議 16×A100/H100 以上，並準備 vLLM/SGLang 等高效推論框架以支援大量 rollouts。

**技能面**
- 熟悉 GRPO / PPO 等策略優化演算法，能修改現有開源 RL 框架（如 OpenRLHF、verl）。
- 具備 Prompt Engineering 與資料管線工程能力（Python、分散式任務排程如 Ray/SkyPilot）。
- 了解視覺推理失敗模式（幻覺、讀錯座標、單位錯誤等），以便設計 HTV-Agent 的反證通道。
- 具備基本的統計檢定概念（假設檢驗、Type I/II 錯誤），用於設計 HTV-Agent 的接受閾值。

### 實作步驟建議

**Step 1：建立題型分類器與種子池**
- 以規則 + 小型分類模型將種子題分為幾何、圖表、OCR、函數圖、表格等族群。
- 為每個族群準備 1,000–5,000 筆「低難度但圖像基礎」的種子題，作為演化輸入。

**Step 2：實作類型感知演化模組（Type-aware Evolution Module）**
- 為每個題型族群設計專屬演化算子，例如：
  - 幾何：增加輔助線、要求證明、要求多解。
  - 圖表：跨子圖比較、趨勢推算、異常值偵測。
  - OCR：單位轉換、多文件彙整。
- 改寫時強制要求「移除文字先驗即可解的題目」，確保新題必須依賴圖像。

**Step 3：建構 HTV-Agent 驗證器**
- 四階段流程：
  1. **獨立解題假設**：呼叫 2–3 個獨立解題模型產生候選答案。
  2. **反證搜尋**：對每個候選答案，從三個通道蒐集反證——(a) 對抗性提示再解題、(b) 程式化計算（Python/SymPy/SQL）、(c) 視覺通道（重新裁切圖像、放大局部）。
  3. **裁決者（Decider）**：彙整衝突，產出裁決理由。
  4. **確定性接受閾值**：僅當所有通道皆無法反證時才接受答案。
- 將每筆樣本的四階段輸出（解題假設、反證報告、工具輸出、裁決理由、閘門結果）完整記錄為 verifier trace。

**Step 4：產出已驗證訓練資料**
- 將「通過驗證的提示–答案–獎勵三元組」匯出為標準格式（JSONL + 影像路徑）。
- 建議分階段放量：先 10K 驗證流程穩定後再線性擴展至 130K（RL）或 250K（SFT）。

**Step 5：SFT 初始化**
- 以已驗證資料對視覺 LLM 主幹（如 Qwen2.5-VL-7B）進行監督微調。
- 監控 loss 與下游基準表現，確認演化資料未引入分布偏移。

**Step 6：GRPO 風格 RL 訓練**
- 固定主幹、SFT 初始化與 GRPO 配方，僅替換訓練資料為 VeriEvol 產出的已驗證樣本。
- 沿資料量軸（10K → 130K）做消融實驗，記錄每個量級的平均準確率。

**Step 7：稽核與釋出**
- 將 verifier trace 與訓練樣本一同釋出，供下游團隊審查特定樣本的驗證歷程。
- 建立儀表板監控「驗證通過率」、「反證觸發率」、「各通道貢獻度」等指標。

### 潛在風險與注意事項

**風險 1：演化算子產生「看似更難但其實是廢題」的樣本**
- *緩解*：在 HTV-Agent 中加入「題目可解性檢查」通道，要求至少一個獨立解題者能正確回答，否則視為無效題。

**風險 2：HTV-Agent 的「獨立解題者」若共享相同主幹會產生同質化錯誤**
- *緩解*：使用異質模型組合（例如一個大型通用 VLM + 一個專家模型 + 一個程式化解題器），並要求至少兩個來源一致才算通過。

**風險 3：程式化驗證通道對非數值題（如幾何證明）覆蓋不足**
- *緩解*：為幾何題加入符化推理通道（Lean/Coq）或形式化驗證器；對純敘述題則以「多解題者共識 + 反證搜尋」為主。

**風險 4：演化資料量膨脹導致 RL 階段過擬合到特定題型**
- *緩解*：定期計算各題型族群的資料比例，維持與原始分布大致一致；對過度集中的族群做下採樣。

**風險 5：驗證成本過高，限制實際可擴展性**
- *緩解*：採用兩階段篩選——先用輕量通道（單一解題者 + 程式化檢查）過濾明顯錯誤樣本，僅對通過初篩者執行完整四階段驗證。

**風險 6：釋出 verifier trace 可能洩漏內部 prompt 或模型細節**
- *緩解*：對 trace 中的敏感欄位做脫敏處理；或僅釋出結構化結果（通過/失敗、各通道分數）而不釋出完整 prompt。

**風險 7：基準過擬合**
- *緩解*：保留一部分未參與演化的「乾淨測試集」作為最終評估，避免在演化後基準上分數虛胖。

### 與其他技術的整合建議

**與開源 RL 框架整合（verl / OpenRLHF）**
- VeriEvol 產出的「已驗證提示–答案–獎勵三元組」可直接餵入現有 GRPO 資料介面，無需修改策略優化器本體。
- 建議將 verifier trace 作為 metadata 附加在資料樣本中，方便 RL 訓練時做 reward shaping（例如對「曾被反證但最終通過」的樣本給予較低權重）。

**與閉源多模態 API 整合（GPT-4o、Gemini）**
- 演化階段與 HTV-Agent 的解題者皆可呼叫閉源 API 作為「外部專家」，降低自建模型的負擔。
- 建議設計快取層避免重複呼叫，並對 API 成本做預算控管。

**與資料管理平台整合（Label Studio、Hugging Face Datasets）**
- 將題型分類、演化結果、驗證結果以結構化欄位儲存，方便後續做資料版本管理與審查。
- 可在 HF Hub 上以 Dataset Card 形式釋出 verifier trace，提升可重現性。

**與形式化數學工具整合（SymPy、Lean、Mathematica）**
- 作為 HTV-Agent 的「程式化通道」後端，特別適合代數、微積分、幾何題的答案驗證。
- 對 Lean 等形式化證明器，可作為「證明題」的高可信度驗證來源。

**與模型監控與可觀測性工具整合（Langfuse、W&B）**
- 將 HTV-Agent 的四階段執行流程接入 LLM observability 平台，方便追蹤每筆樣本的決策路徑與成本。
- 在 W&B 中記錄「資料量軸」與「設計軸」的消融曲線，方便團隊決策最佳資料預算。

**與既有基準管線整合（lm-evaluation-harness）**
- 將五基準視覺數學測試集接入 lm-evaluation-harness，統一評測流程，方便與其他模型做公平比較。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的「問題動機」與第 3.1 節的框架總覽，理解「為什麼視覺數學推理的 RL 訓練會被錯誤標籤拖垮」，以及 VeriEvol 想解決的兩個獨立問題（題目難度 vs. 答案可靠性）。先建立直覺，再回頭看技術細節。

**給 AI 工程師**：重點閱讀第 3.2 節（類型感知演化模組）與第 3.3 節（HTV-Agent 四階段流程），並參考附錄中的 verifier trace 範例。實作時可先以小型種子池（1K–5K）跑通端到端流程，再逐步放量；特別注意 HTV-Agent 的「獨立解題者異質性」與「程式化通道的覆蓋率」這兩個工程關鍵。

**給研究者**：第 4 節的消融實驗（資料量軸 +3.88、設計軸分解為 +1.82 / +2.06）是本文最值得深挖的部分，建議仔細分析「演化提示」與「驗證器」之間是否存在交互效應。此外，第 2 節對「資料管線派」與「策略側派」的分類框架，可作為延伸研究（例如：能否把 HTV-Agent 擴展到程式生成、科學推理等其他領域？）的起點。

**給產品經理**：聚焦於第 1 節的應用場景與第 5 節的釋出物，理解 VeriEvol 能為你的產品帶來什麼（更高品質的訓練資料、可稽核的 AI 內容生成管線）。重點關注「驗證成本 vs. 品質提升」的取捨——本文的 +3.88 累積增益是否值得你團隊投入 API 與算力成本？建議先以小規模 POC 驗證 ROI，再決定是否全面導入。
