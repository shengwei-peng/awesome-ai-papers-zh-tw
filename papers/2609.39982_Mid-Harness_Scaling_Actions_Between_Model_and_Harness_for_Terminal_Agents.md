## ⚡ TL;DR

終端機代理的動作雖有用，但執行可靠性不足，錯誤指令會破壞環境並阻礙後續進展。
本文提出Mid-Harness，在模型與Harness間取樣驗證候選動作，再轉交最佳者執行。
GPT-5.6Sol驗證使Pass@1從50%升至68%，且結合動作與軌跡擴展成本更低。

## 摘要翻譯

終端機代理（Terminal agents）透過隨機模型生成（stochastic model generations）來執行動作（actions），但能生成有用的動作並不保證其可靠執行。一個不良的指令（poor command）（例如錯誤的套件安裝（package install））可能以阻礙後續進展（subsequent progress）的方式改變環境（environment），即使模型本可生成更好的替代方案（better alternative）。我們探討在模型-Harness 邊界（model-harness boundary）分配測試時運算（test-time compute），是否能提升動作可靠性（action reliability）與軌跡成功率（trajectory success），以及何種因素使此分配有效。為研究這些問題，我們提出 Mid-Harness，它在轉發選定候選動作（candidate actions）供執行（execution）之前，先對其進行取樣（sampling）與驗證（verification），同時保持生成器（generator）與 Harness 不變。使用 TMAX-9B 生成器時，在弱驗證（weak verification）下增加動作取樣幾乎無益；然而，有能力的驗證器（capable verifier）能從同一生成器中利用有用的替代方案（useful alternatives）。在 TerminalBench-Lite 上，GPT-5.6 Sol 驗證器將基礎代理（base agent）的 Pass@1 從 50.00% 提升至取樣 8 個動作時的 68.03%。當同樣的 TMAX-9B 模型作為驗證器時，成對驗證（pairwise verification）在所評估的驗證機制（verification mechanisms）中表現最佳。將較強驗證器（strong verifier）的回應進行知識蒸餾（distillation）至 TMAX-9B，同時保持動作生成器（action generator）不變，可進一步提升 Pass@1。在 TerminalBench-Lite 上使用 TMAX-9B，結合動作擴展（action scaling）與軌跡擴展（trajectory scaling），相較於僅進行軌跡擴展，能以較低的估計 Token 成本（estimated token cost）達到更高的成功率。Mid-Harness 亦能在額外的模型、基準測試與 Harness（additional models, benchmarks, and harnesses）上提升表現。這些結果指出，動作擴展是終端機代理測試時運算擴展的一個有前景的方向。

### 核心貢獻（3～5點）
- 提出 Mid-Harness 架構，在模型與 Harness 之間取樣並驗證候選動作，無需修改生成器與 Harness 即可提升動作可靠性。
- 發現驗證器能力是動作擴展能否生效的關鍵：弱驗證下增加取樣無益，強驗證器能利用同一生成器的有用替代方案。
- 結合動作擴展與軌跡擴展，相較於單純軌跡擴展，能以更低 Token 成本達到更高成功率。
- 透過知識蒸餾將強驗證器能力轉移至較小模型，在保持生成器不變下進一步提升表現。
- 在額外模型、基準測試與 Harness 上驗證 Mid-Harness 的泛化性。

### 適合對象
適合對終端機代理、測試時運算擴展，以及大型語言模型在軟體工程與命令列環境應用感興趣的研究人員與工程師，特別是關注如何在不改變底層生成器與執行 Harness 的前提下提升代理可靠性的讀者。

## 深度分析

#### 方法論解析

Mid-Harness 的核心設計是在**動作生成器（action generator）**與**執行 Harness（execution harness）**之間插入一層「取樣—驗證」機制，而不修改生成器或 Harness 的內部邏輯。具體來說，原本 Harness 在每一步只向模型請求一次動作並立即執行；Mid-Harness 則把這個單次呼叫改寫為：

1. **候選動作取樣（candidate action sampling）**：針對相同的**互動歷史（interaction history）** \(h_t\)，從固定生成器 \(\pi\) 中獨立取樣 \(N\) 個候選動作 \(\mathcal{A}_t = (a_t^1, \dots, a_t^N)\)。
2. **執行前驗證（verify before execution）**：由**驗證器（verifier）** \(\psi\) 根據任務指令、過往觀測與候選動作，從中挑選一個動作 \(a_t^\star\)。
3. **轉發執行（forward chosen candidate）**：僅將被選中的動作交給 Harness 執行，環境回傳觀測 \(o_t\) 後更新歷史，進入下一步。

這樣的設計有幾個方法論上的特點：

- **解耦生成與驗證**：生成器與 Harness 保持不變，因此可以獨立研究「候選寬度（candidate width）」、「驗證機制（verification mechanism）」與「驗證器能力」對**軌跡成功率（trajectory success）**的影響。
- **動作層級運算擴展（action-level compute scaling）**：不同於傳統在完整軌跡層級進行 Best-of-\(T\) 的**軌跡擴展（trajectory scaling）**，Mid-Harness 把額外運算花在「執行前的動作比較」，只需一個環境實例即可進行。
- **驗證器輸入設計**：驗證器接收任務、觀測歷史與候選動作，但不接收生成器為各候選動作產生的推理過程。這強迫驗證器根據動作本身的語義與在當前環境中的可行性做判斷，而非依賴生成器的自我辯解。

在驗證機制方面，論文評估了多種方式，其中**成對驗證（pairwise verification）**表現最佳。成對驗證的基本思想是讓驗證器兩兩比較候選動作，判斷哪一個更有助於完成任務，再透過錦標賽或排序彙整出最終選擇。相較於對單一動作進行絕對分數的**點估驗證（pointwise verification）**，成對比較通常更穩定，因為它降低了驗證器對絕對好壞標準的依賴，更適合判斷命令語義（command semantics）與執行可行性（execution feasibility）這類相對性問題。

此外，論文還探討了**知識蒸餾（distillation）**：將強驗證器 GPT-5.6 Sol 對成對候選動作的偏好回應，蒸餾到與生成器同樣大小的 TMAX-9B 模型中，作為可部署的驗證器。這使得在無法使用強大外部模型推理的情況下，仍能在本地模型上獲得驗證增益。

#### 實驗數據解讀

論文的主要實驗圍繞 TMAX-9B 生成器在 TerminalBench-Lite 上的表現展開，並以 **Pass@1** 作為核心指標。以下分層解讀：

**1. 強驗證器揭示了生成器已具備的潛力**

基礎代理（base agent）的 Pass@1 為 50.00%。當 Mid-Harness 使用 GPT-5.6 Sol 作為強驗證器、每步取樣 8 個候選動作時，Pass@1 提升至 68.03%。這個結果說明：

- TMAX-9B 作為**固定生成器（fixed generator）**，已經能在某些步驟產生**有用的替代方案（useful alternatives）**；
- 問題不在於模型「想不出」更好的動作，而在於基礎代理缺乏機制去辨識並選擇這些更好的動作；
- **執行前驗證**能夠把生成器的潛在能力轉化為實際的**軌跡成功率**提升，而無需對生成器進行額外的**訓練後調整（post-training）**。

**2. 自驗證設定下，驗證機制與訓練同樣關鍵**

當使用同一個 TMAX-9B 模型同時擔任生成器與驗證器時，單純增加候選寬度（例如從 1 到 8）在**弱驗證（weak verification）**下收益有限。這呼應了論文的核心論點：**取樣的效益取決於驗證能力**。如果驗證器無法區分好壞，產生再多候選動作也只是雜訊。

在自驗證設定中，**成對驗證（pairwise verification）**優於其他評估的驗證機制。進一步將 GPT-5.6 Sol 的成對偏好回應蒸餾到 TMAX-9B 驗證器後，Pass@1 從 54.76% 提升到 57.14%。雖然仍遠低於強驗證器的 68.03%，但證明了：

- 驗證機制的設計（成對 vs. 點估）本身就能帶來差異；
- 透過**知識蒸餾**可以部分彌補自驗證器與強驗證器之間的能力差距；
- 離線分析顯示，蒸餾後的驗證器與教師驗證器的吻合度提高，但在**命令語義**與**執行可行性**上仍存在持續分歧。這也點出了核心挑戰：驗證器必須在不實際執行的情況下，預測一個命令在當前環境中會造成什麼影響。

**3. 動作擴展與軌跡擴展的結合具有成本優勢**

論文進一步比較了 Mid-Harness 與兩種**軌跡擴展**方法：

- **Best-of-\(T\) Trajectories**：平行取樣 \(T\) 條完整軌跡，再用 LLM-as-a-verifier 挑選最佳軌跡；
- **Sequential Refine（SR）**：依序精煉軌跡。

結果顯示，Mid-Harness 能與這兩種方法相容並帶來增益。更具體地，結合 Mid-Harness 與一輪 Sequential Refine 後，TMAX-9B 在 TerminalBench-Lite 上的表現超越了 Best-of-\(T\) 在 \(T=7\) 時的水準，而估計 **Token 成本（estimated token cost）**卻不到後者的一半。這說明：

- 把運算資源投入到「動作執行前的驗證」可能比單純增加完整軌跡數量更有效率；
- 動作層級與軌跡層級的運算擴展並非互斥，而是可以互補。

**4. 跨模型、基準與 Harness 的泛化性**

論文還報告了 Mid-Harness 在其他模型、任務與 Harness 上也能帶來性能提升，雖然具體數據在提供的上下文中未完整列出，但這暗示 Mid-Harness 作為一種「邊界層」方法，具有相當的通用性。

#### 與現有研究的比較

**定位與差異**

過去的研究大多從兩個方向提升代理性能：

1. **軌跡層級取樣與驗證**：例如 Best-of-\(N\) 軌跡、過程獎勵模型（PRM）等，這類方法通常需要多次完整執行或平行環境，成本較高。
2. **推理與精煉**：例如讓模型在產生動作前進行更多推理（Chain-of-Thought）、或透過 Sequential Refine 在失敗後重試。

Mid-Harness 的定位介於兩者之間：它在**模型-Harness 邊界（model-harness boundary）**上進行動作級別的取樣與驗證，不需要改變生成器，也不需要多次完整執行。這與過去「在執行前驗證候選動作」的工作方向一致，但 Mid-Harness 更強調系統性地分離並研究「生成器是否提供有用替代方案」與「驗證器能否識別它們」這兩個條件。

**相對優勢**

- **模組化與可解釋性**：由於生成器與 Harness 不變，研究者可以單獨替換驗證器、驗證機制或候選寬度，從而清楚定位性能提升來源。
- **環境成本較低**：相較於 Best-of-\(T\) 需要 \(T\) 個環境實例或多次執行，Mid-Harness 每步只執行一個動作，節省了環境互動成本。
- **與軌跡擴展互補**：實驗顯示 Mid-Harness 能與 Best-of-\(T\) 和 Sequential Refine 同時使用，並在 Token 成本上更具優勢。

**限制與待釐清之處**

- **強驗證器的可取得性**：GPT-5.6 Sol 作為強驗證器帶來了顯著增益，但這類模型可能並非所有團隊都能使用。蒸餾後的 TMAX-9B 驗證器雖可部署，但性能仍有明顯落差。
- **生成器必須產生有用替代方案**：如果生成器本身多樣性不足或品質太差，增加候選寬度與驗證都難以奏效。
- **驗證器無法實際執行**：核心難題在於驗證器必須僅憑文本預測命令的執行結果。對於涉及檔案系統狀態、套件依賴、網路環境等複雜情況，純語言模型的判斷可能不穩定。
- **候選動作的浪費**：除了被選中的動作外，其餘候選動作都被丟棄，雖然節省了環境執行成本，但仍消耗了生成 token。
- **成對驗證的複雜度**：隨著候選寬度增加，成對比較的次數會上升（例如 \(N=8\) 時需要較多比較），這會帶來額外的推理成本與延遲。

#### 可重現性評估

從提供的上下文來看，論文給出了 Mid-Harness 的整合虛擬碼（pseudocode），清楚說明如何在 model-call wrapper 中實作候選取樣與驗證，這對重現方法架構非常有幫助。然而，關於**開源程式碼、資料集與模型權重**的具體釋出資訊，在提供的片段中並未明確說明。

- **TMAX-9B**：作為本文主要的生成器與自驗證器，其是否公開可取得、授權方式為何，會直接影響重現難度。
- **TerminalBench-Lite**：作為評估基準，若其任務、環境與評分腳本能公開，將有助於社群驗證。
- **GPT-5.6 Sol**：作為強驗證器，若其為閉源或 API 限定模型，則其他研究者難以完全複製 68.03% 的強驗證器實驗。
- **蒸餾資料與提示詞**：成對驗證的提示模板、教師回應的收集方式、微調超參數等細節，對於重現 54.76% → 57.14% 的蒸餾結果至關重要，但片段中未詳細交代。

整體而言，方法概念與虛擬碼足夠清晰，但要達到論文報告的數字，仍需依賴模型、資料與實作細節的公開。建議作者釋出實驗框架、驗證提示模板與蒸餾資料子集，以提升可重現性。

#### 未來研究方向

基於 Mid-Harness 的發現，以下幾個方向值得進一步探索：

1. **更強大的可學習驗證器**
   發展專門針對終端機環境的驗證模型，例如結合環境狀態編碼、命令語法分析與執行結果預測，讓驗證器不僅能判斷「哪個動作比較好」，還能預測「這個動作執行後環境會變成什麼樣子」。

2. **執行模擬與輕量環境回饋**
   在驗證階段引入輕量級的執行模擬（例如 dry-run、語法檢查、靜態分析），讓驗證器能獲得部分環境回饋，而不必真正執行每個候選動作。

3. **自適應候選寬度**
   根據當前任務難度、驗證器不確定性或剩餘步數，動態調整每步取樣的候選動作數量。例如在不確定性高的步驟多取樣，在簡單步驟少取樣，以平衡成本與性能。

4. **候選動作的跨步利用**
   目前未被選中的候選動作會被丟棄。未來可研究如何將這些動作作為「備案」保留，在後續步驟中根據環境變化重新啟用，減少 token 浪費。

5. **動作擴展與軌跡擴展的聯合最佳化**
   建立統一的測試時運算配置框架，自動決定多少預算應分配給每步動作驗證、多少分配給軌跡重試或精煉，並在不同任務類型上學習最佳配置。

6. **驗證器的不確定性量化**
   讓驗證器輸出對自身判斷的信心分數，當信心不足時觸發額外取樣、執行模擬或請求人類監督，提升系統在關鍵步驟的可靠性。

7. **多模態與長上下文環境**
   將 Mid-Harness 擴展到需要處理長篇日誌、錯誤訊息、甚至圖形介面的代理場景，研究驗證器如何在更複雜的觀測條件下保持判斷準確。

8. **安全與成本導向的驗證**
   除了任務成功率，也可讓驗證器考慮動作的安全性（例如是否會刪除重要檔案、安裝惡意套件）與執行成本（例如是否會觸發昂貴的 API 呼叫），發展更實用的多目標驗證機制。

9. **建立動作層級的 ground-truth 標籤**
   目前研究缺乏**ground-truth 標籤**來直接衡量驗證器品質。未來可建構標註資料集，標記在特定歷史下哪些動作是正確的，從而更精確地診斷驗證器的弱點。

10. **強化學習訓練驗證器**
    不僅使用靜態的教師偏好進行知識蒸餾，還可透過強化學習讓驗證器直接優化最終軌跡成功率，並在與環境互動中持續改進對執行可行性的判斷。

## 論文問答

**Q1：終端機代理在執行任務時，為什麼「能產生有用動作」並不等於「能可靠完成任務」？**

A：終端機代理的每一步動作都來自模型的隨機生成，因此即使模型有能力產生正確指令，某次抽樣仍可能選到錯誤的動作。一旦執行了錯誤的指令（例如安裝錯誤套件或修改錯誤程式碼），環境狀態就會被改變，而後續決策又必須依賴這個已被破壞的環境。這種長程序列的相依性使得單一不良動作可能產生連鎖反應，最終導致整條軌跡失敗，因此動作可靠性與軌跡成功率是兩個需要分開檢視的問題。

**Q2：過去透過測試時運算提升代理表現的方法，為什麼在動作可靠性上仍顯不足？**

A：過去研究多把額外運算放在推理、完整軌跡取樣或事後驗證上，較少系統性地研究「執行前」對單一步驟候選動作的取樣與驗證。這些方法忽略了動作層級的一個關鍵特性：產生更多候選動作的好處，完全取決於驗證器能否從中辨識出真正可行的選項。如果驗證能力不足，單純增加候選寬度只會帶來邊際效益，甚至浪費 token 成本而無法提升軌跡成功率。

**Q3：為什麼在模型與 Harness 之間進行動作層級的運算擴展特別重要？**

A：因為終端機環境具有狀態持續性，每個被執行的命令都會改變環境，並影響代理後續能觀察到的資訊與可採取的行動。與其在軌跡結束後才發現某個早期錯誤已無法挽回，不如在每次執行前先過濾掉可能破壞環境的候選動作。這種「執行前驗證」的設計能夠把錯誤扼殺在發生前，從源頭提升動作可靠性並改善長程任務的完成率。

**Q4：Mid-Harness 的核心運作方式是什麼？**

A：Mid-Harness 是一個插入在動作生成器與執行 Harness 之間的中介層，它會在每一步向生成器請求多個候選動作，然後透過驗證器挑選出一個最適合目前互動歷史與任務需求的動作，最後才將選定的候選動作轉發給 Harness 執行。整個過程中，動作生成器與執行 Harness 都保持不變，不需要修改模型權重或服務架構。這種設計讓研究者能夠在固定的模型-Harness 邊界上，系統性地探討候選動作取樣與驗證對軌跡成功的影響。

**Q5：相較於傳統的軌跡層級驗證，Mid-Harness 的關鍵創新在哪裡？**

A：傳統軌跡層級驗證通常是在整條軌跡執行完畢後，再比較多條完整軌跡並選出最佳者；Mid-Harness 則把驗證粒度下放到「單一步驟的候選動作」，在動作被執行前就完成篩選。這不僅只需要一個環境實例，也能避免錯誤動作對環境造成不可逆的污染。更重要的是，它把動作擴展與軌跡擴展解耦，證明兩者可以互補而非互相取代。

**Q6：Mid-Harness 在設計上需要決定哪些關鍵因素？**

A：首先是候選寬度，也就是每一步要取樣多少個候選動作；其次是驗證機制，例如逐個評分、成對比較或排序等；最後是驗證器的能力，包括使用更強大的外部模型或同模型自我驗證。實驗發現，在自我驗證設定下，成對驗證的表現優於其他評估機制，顯示「如何比較候選動作」與「用什麼模型驗證」同樣重要。此外，驗證器只接收任務、互動歷史與候選動作，而不接收生成器為各候選動作產生的推理過程，以避免潛在的偏見干擾判斷。

**Q7：本研究主要在哪些設定與基準測試上進行實驗？**

A：核心實驗使用 TMAX-9B 作為固定的動作生成器，並在 TerminalBench-Lite 上評估軌跡成功率。驗證器方面則比較了強大的 GPT-5.6 Sol 與同樣使用 TMAX-9B 的自我驗證設定，以探討驗證器能力與驗證機制的影響。此外，作者也在額外的模型、基準測試與 Harness 上進行驗證，顯示 Mid-Harness 的效益具有一定的泛化性。

**Q8：本研究有哪些最值得注意的實驗結果？**

A：在 TerminalBench-Lite 上，使用 GPT-5.6 Sol 作為強驗證器並取樣 8 個候選動作時，Pass@1 從基礎代理的 50.00% 提升到 68.03%，顯示生成器確實產生了可被利用的有用替代方案。在自我驗證設定中，成對驗證表現最佳，而將 GPT-5.6 Sol 的成對回應蒸餾到 TMAX-9B 驗證器後，Pass@1 從 54.76% 進一步提升到 57.14%，且動作生成器完全未改變。當結合動作擴展與軌跡擴展時，Mid-Harness 加上一輪 Sequential Refine 不僅超越 Best-of-7 Trajectories 的成功率，估計 token 成本還不到後者的一半。

**Q9：消融分析揭示了哪些關於取樣與驗證的關係？**

A：消融結果顯示，在弱驗證下單純增加候選寬度幾乎沒有幫助，因為驗�器無法辨識出真正較好的候選動作。相對地，當驗證器能力足夠時，更多的候選動作能顯著提升軌跡成功率，說明「驗證能力」是動作擴展能否發揮效益的關鍵閥門。此外，離線分析發現知識蒸餾雖然提升了學生驗證器與教師驗證器的一致性，但在指令語義與執行可行性上仍存在持續分歧，這也點出了未來需要改進的核心難題。

**Q10：Mid-Harness 在實際應用場景中可能帶來什麼價值？**

A：在軟體工程、資料科學與科學發現等需要終端機代理長時間執行命令的領域，Mid-Harness 可以作為一道安全閘門，避免錯誤的套件安裝、檔案刪除或程式碼編輯污染工作環境。對於需要高可靠性的自動化流程，例如持續整合腳本或實驗管線，執行前驗證能顯著降低因單一錯誤指令導致整個任務重來的風險。由於它不需要改變底層生成模型，企業可以較快地將其部署為現有代理架構的外掛層。

**Q11：在產品化過程中，部署 Mid-Harness 需要考慮哪些取捨？**

A：首先是延遲與成本的權衡，因為每一步都要產生並驗證多個候選動作，會增加單步的推論時間與 token 消耗。其次是驗證器的選擇：使用更強大的外部模型能提升成功率，但也會提高運行成本；使用同模型自我驗證則成本較低，但表現仍有差距。最後，產品團隊需要根據任務的失敗代價來決定候選寬度與驗證機制，例如在關鍵環境中採用較寬的取樣與較強的驗證器，而在低風險場景中則可縮減以節省資源。

**Q12：這項研究對終端機代理領域可能產生什麼深遠影響？**

A：本研究明確指出「動作擴展」是測試時運算擴展中一個值得獨立研究與投資的方向，而不應只聚焦於軌跡層級的取樣。它強調了驗證器能力與驗證機制在轉化候選多樣性為實際成功率上的核心角色，可能促使未來代理架構在生成器之外專門設計更強大的驗證模組。此外，Mid-Harness 的模組化設計也為學術界提供了一個標準化的實驗框架，方便比較不同取樣與驗證策略。

**Q13：本研究有哪些已知的限制？**

A：首先，最顯著的效益來自強大的外部驗證器 GPT-5.6 Sol，而這類模型在實際部署中可能成本較高或無法取得。其次，自我驗證雖然可行，但表現仍明顯落後於強驗證器，顯示同時生成與驗證動作仍有困難。此外，實驗主要集中在 TerminalBench-Lite 等特定基準，對於更複雜、更開放或更長程的終端機任務，Mid-Harness 的效益與挑戰仍需進一步驗證。

**Q14：在什麼情況下 Mid-Harness 仍可能失敗？**

A：如果驗證器對某個候選動作的語義理解錯誤，例如誤判一個命令會修復環境而非破壞環境，那麼即使經過驗證，錯誤指令仍可能被轉發執行。同樣地，當驗證器無法準確評估指令在當前環境中的執行可行性時，也可能選出看似合理但實際會失敗的動作。這些失敗案例說明，執行前驗證的成效高度依賴驗證器對命令語義與環境狀態的掌握，而這正是目前仍有顯著改進空間之處。

**Q15：未來研究可以朝哪些方向延伸 Mid-Harness 的框架？**

A：未來可以發展更專精的環境感知驗證器，讓模型在挑選候選動作前能夠更準確地預測指令執行後的環境變化。另一個方向是將更強大的驗證器知識進一步蒸餾到輕量模型，以降低部署成本並縮小自我驗證與強驗證之間的差距。此外，也可以探索動作擴展與軌跡擴展的更緊密結合，例如讓驗證器同時考慮單步動作品質與長期軌跡規劃，並將 Mid-Harness 應用到更多工具使用或多模態代理場景中。

## 實務應用指南

### 適用場景

1. **自動化 DevOps / SRE 終端代理**  
   在伺服器維運、部署或除錯流程中，代理會產生 `kubectl`、`terraform`、`apt` 等指令。Mid-Harness 可在執行前對多組候選指令進行驗證，降低「錯誤安裝套件」或「誤刪資源」導致環境惡化的風險，提升長程序列的成功率。

2. **資料科學互動式環境代理**  
   在 Jupyter、Python REPL 或資料管道中，代理需要決定下一步要執行的資料清理、特徵工程或模型訓練程式碼。透過動作擴展與成對驗證，可避免因單一錯誤的 `pip install` 或資料覆寫操作，讓後續實驗無法復現。

3. **軟體工程程式碼編輯代理**  
   例如 SWE-agent 或類似的終端機程式碼代理，每一步可能產生不同的檔案編輯或測試命令。Mid-Harness 能在送出編輯前比較多個候選動作，選出語意正確且可執行的方案，減少「錯誤程式碼編輯」對程式碼庫的連鎖破壞。

4. **科學計算與實驗流程自動化**  
   在需要長序列命令（如模擬、批次處理、實驗腳本）的場景中，Mid-Harness 可於每個決策點驗證候選動作，確保環境狀態朝任務目標推進，避免中間步驟出錯導致整個實驗軌跡失敗。

5. **企業內部 IT 服務台代理**  
   代理接收使用者問題後，在受控終端環境中執行診斷或修復指令。執行前驗證可過濾掉可能影響系統穩定性的命令，並保留完整審計軌跡，符合企業治理需求。

### 實作前置條件

- **可抽換的模型-Harness 邊界**：現有代理必須能將「動作生成」與「執行 Harness」分離，讓 Mid-Harness 以包裝器形式插入兩者之間。
- **支援多次取樣的生成器**：動作生成模型需支援 `n=N` 取樣，能針對同一互動歷史產生多個候選動作。
- **驗證器資源**：至少需一個可用於驗證的模型。初期建議使用較強的教師驗證器（如 GPT-5.6 Sol 或同等級模型）來評估上限；若要走自驗證路線，則需準備與生成器同規模或更小的模型。
- **歷史與觀測資料**：需能取得任務指令、過往動作與終端機回饋，並以固定格式餵給驗證器。候選動作的推理過程可選擇性提供。
- **評估資料集**：建議準備與目標場景對應的基準測試（如 TerminalBench-Lite）或內部測試集，用於衡量 Pass@1 與 Token 成本。
- **沙箱與監控環境**：必須具備隔離執行環境、日誌記錄與成本監控，因為驗證過程會顯著增加推論開銷。
- **團隊技能**：需熟悉 LLM 推理流程、API 整合、成對比較資料建構，以及微調或知識蒸餾流程。

---

### 實作步驟建議

1. **將 Mid-Harness 包裝器接入現有代理**  
   在不修改生成器與 Harness 的前提下，於 `model.generate(messages)` 外層新增候選取樣與驗證邏輯。確保每次只將選定的候選動作轉發給 Harness 執行。

2. **設定候選寬度（Candidate Width）**  
   從 `N=2` 或 `N=4` 開始實驗，觀察在現有驗證器下的 Pass@1 變化。論文顯示：若驗證器能力不足，單純增加 `N` 效益有限。

3. **選擇驗證機制**  
   優先嘗試**成對驗證（Pairwise Verification）**：讓驗證器兩兩比較候選動作，再透過排序選出最佳者。論文發現此機制在自驗證設定下表現最佳。

4. **先用強驗證器測量機會上限**  
   使用較強的外部模型（如 GPT-5.6 Sol）作為教師驗證器，測量相同生成器在不同 `N` 下能達到的最佳 Pass@1。這能幫助判斷問題出在「生成器沒有好候選」還是「驗證器挑不到好候選」。

5. **收集離線驗證資料並蒸餾**  
   記錄教師驗證器對候選動作的判斷，特別關注「指令語意」與「執行可行性」上的分歧。將這些回應蒸餾到較小的驗證器（如 TMAX-9B），在不更動生成器的情況下提升成功率。

6. **結合軌跡擴展策略**  
   當單一軌跡成功率提升後，可將 Mid-Harness 與 Best-of-T 或 Sequential Refine 等軌跡擴展方法結合。論文指出，動作擴展加上軌跡精煉能在更低 Token 成本下達到更高成功率。

7. **持續監控與迭代**  
   追蹤每步驗證延遲、Token 消耗、驗證器與教師的一致性，以及實際執行後的環境狀態變化，並定期重新訓練驗證器以適應新任務分佈。

### 潛在風險與注意事項

- **驗證器仍可能選錯動作**：即使經過驗證，錯誤的套件安裝或程式碼編輯仍可能破壞環境。  
  *緩解*：對刪除、安裝、網路操作等高危指令設置允許清單或人工確認閘門。

- **Token 與延遲成本顯著增加**：每步產生並驗證多個候選動作會消耗大量 Token。  
  *緩解*：設定成本上限，對簡單步驟降回基礎代理，或只在關鍵步驟啟動 Mid-Harness。

- **過度自信與分佈偏移**：驗證器可能在未見過的任務或環境上過度自信。  
  *緩解*：保留基礎代理作為後備方案，並持續用真實執行結果更新驗證資料。

- **驗證器與教師在語意與可行性上持續分歧**：這是論文指出的核心挑戰。  
  *緩解*：針對「命令語意」與「執行可行性」設計專項訓練資料，而非僅蒸餾最終選擇。

- **安全與審計風險**：自動執行終端指令需符合企業安全規範。  
  *緩解*：在隔離沙箱中執行、記錄所有候選動作與驗證決策，並與現有資安政策整合。

### 與其他技術的整合建議

- **ReAct / Chain-of-Thought 代理**：Mid-Harness 可直接包裝在現有推理-行動循環的模型呼叫層，無需改變代理的推理格式。
- **現有終端機代理框架**：如 SWE-agent、OpenHands 等，只要框架將「生成」與「執行」分開，即可插入 Mid-Harness 包裝器。
- **平行與序列軌跡擴展**：可與 Best-of-T（平行取樣多條軌跡）或 Sequential Refine（失敗後精煉）並用，論文顯示兩者結合能在更低成本下超越單純軌跡擴展。
- **觀測與監控平台**：將每步的候選動作、驗證分數與最終選擇寫入可視化平台，協助除錯與持續優化。
- **政策與安全層**：在 Mid-Harness 之前或之後加入靜態命令檢查、權限控管與人工審批閘門，形成多層防護。

### 給不同背景讀者的閱讀建議

- **初學者**：請把重點放在「執行前驗證」這個核心概念上。Mid-Harness 就像是在代理真正下指令之前，先請另一位模型幫忙看看哪個方案比較好，避免一次錯誤操作毀掉整個任務。可以先從適用場景與風險章節讀起，理解為什麼需要這層保護。
