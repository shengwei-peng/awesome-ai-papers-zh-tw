## 摘要翻譯

AI 程式設計代理（AI coding agents）日益廣泛用於撰寫真實世界軟體，但確保其輸出的正確性仍是一項根本挑戰。形式驗證（Formal verification）提供了一條前景可期的途徑：代理同時生成程式碼與機器驗證證明（machine-checked proof），保證該程式碼滿足形式規格（formal specification）。然而，形式規格本身是否符合使用者意圖，則無法保證。在本研究中，我們探討規格自動形式化（specification autoformalization）：LLM 代理（LLM agents）是否能將非形式程式設計問題（informal programming problems）轉譯為忠實的形式規格（faithful formal specifications）。我們提出 Verus-SpecBench——一個包含 581 項規格撰寫任務的基準測試，任務衍生自 Codeforces 題目，並針對 Rust 的形式驗證器 Verus——以及 Verus-SpecGym，一個代理環境（agentic environment），讓模型與 Verus、Bash 及檔案系統（filesystem）互動以開發這些規格。核心挑戰在於評估：專家撰寫的參考規格（reference specs）成本高昂，且 LLM 評審（LLM judges）可能遺漏細微錯誤。我們透過以下方式解決此問題：（a）擴充 Verus 的 exec_spec 機制，使生成的規格可作為 Rust 程式碼執行；以及（b）將其與 Codeforces 官方測試以及從 Codeforces「Hacks」中提取的對抗案例（adversarial cases）進行比對測試——這些 Hacks 是參賽者撰寫的邊界案例（edge cases），用於破解錯誤的解題方案。在 Verus-SpecBench 上，最強的模型 Gemini 3.1 Pro 解決了 77.8% 的任務，其他前沿模型（frontier models）解決了 51.1–57.8%，而 OSS 模型（OSS models）僅達到 21.5–25.5%。我們對失效模式（failure modes）的分析顯示，模型生成的規格可能遺漏重要的輸入假設（input assumptions）、接受不正確的輸出，並拒絕有效的輸出。我們也發現，LLM 作為評審（LLM-as-a-judge）的評估方式遺漏了我們評估器所檢測到的 26% 錯誤。整體而言，我們的結果顯示，規格自動形式化對前沿代理而言是可達成的目標，但即使在他們已能生成正確程式碼的題目上，仍然脆弱。程式碼、資料與日誌可於 https://github.com/formal-verif-is-cool/verus-spec-gym 取得。

## 深度分析

#### 方法論解析

本研究的核心貢獻在於建立了一套端到端的規格自動形式化（specification autoformalization）評估體系，包含基準測試 Verus-SpecBench 與代理環境（agentic environment）Verus-SpecGym。方法論可拆解為三個層次：任務設計、代理執行迴圈，以及可執行化評估機制。

在任務設計層面，研究者從 Codeforces（競技程式設計平台）萃取 581 道題目，將其自然語言題目敘述轉換為規格撰寫任務。每個任務提供一份非形式規格（informal specification）、一份帶有函數簽名空缺的 Verus 形式骨架（formal Verus skeleton），以及 pre_spec（輸入性質）與 post_spec（輸出性質）的待填邏輯謂詞（logical predicates）。此外，任務輔以範例測試案例（sample test cases）、詳解範例（worked examples）、Verus 文件與驗證器（verifier）原始碼，以降低代理在冷啟動時的語義鴻溝。

在代理執行層面，Verus-SpecGym 作為一個代理環境（agentic environment），允許模型透過 Bash（Unix shell 環境）與檔案系統（filesystem）進行互動。代理的目標是讀取題目後，在 solve.rs 中填寫形式規格（formal specification），並可透過 verus_gym_specgen_check 指令迭代驗證。此指令會呼叫 Verus（針對 Rust 的形式驗證器）檢查規格是否能通過公開範例測試，並提供編譯錯誤或驗證失敗的回饋。這種「撰寫—檢查—修正」的迴圈模擬了真實開發者使用形式驗證（formal verification）工具鏈的工作流程。

最具方法論創新的是評估層面。傳統上，Verus 規格是給驗證器使用的邏輯謂詞，無法直接在具體輸入上執行。為此，作者擴展了 Verus 的 exec_spec 機制，將生成的規格編譯為可執行的 Rust 檢查（executable Rust checks）。這使得形式規格能被當作一般 Rust 程式碼執行，從而在隱藏測試（hidden tests）上進行動態驗證。測試資料包含兩大來源：官方 Codeforces 測試，以及從 Codeforces Hacks（Hacks）萃取的對抗案例（adversarial cases）。這些 Hacks 是由競賽參與者撰寫、用於破解錯誤解答的邊界案例（edge cases），相較於自動生成的對抗輸入，更能反映人類對於語義邊界的細膩理解。

最終評估分為兩個維度：後置健全性（post-soundness）確保 post_spec 會拒絕不正確輸出；後置完備性（post-completeness）確保 post_spec 接受正確輸出。同理可推輸入端的健全性與完備性。唯有在隱藏測試與對抗案例上同時通過，才視為生成出忠實的形式規格（faithful formal specifications）。

#### 實驗數據解讀

實驗評估了六個模型，涵蓋前沿模型（frontier models）與 OSS 模型（開源軟體模型）。在固定運算與時間預算下，Gemini 3.1 Pro 表現最佳，解決 77.8% 的任務；其他前沿模型落在 51.1%–57.8%；而 OSS 模型僅達 21.5%–25.5%。這組數據揭示了規格自動形式化領域存在顯著的「能力斷層」：頂尖商用閉源模型已展現初步的規格理解與邏輯轉譯能力，但開源模型距離實用門檻仍相當遙遠。

更值得深究的是，即使當前 AI 程式設計代理（AI coding agents）已能在部分題目上生成正確程式碼，它們在撰寫對應形式規格時依然頻繁失敗。這表示「會寫程式」並不等價於「能精確描述程式應滿足的語義約束」。作者歸納出三種主要的失效模式（failure modes）：

1. **遺漏重要輸入假設（input assumptions）**：pre_spec（輸入性質）未完整捕捉題目對輸入資料的限制，例如未宣告字串僅由特定字元組成，或忽略數值範圍邊界。
2. **接受不正確輸出**：post_spec（輸出性質）過弱，導致錯誤輸出被判定為合法，違反後置健全性（post-soundness）。
3. **拒絕有效輸出**：post_spec（輸出性質）過強，將正確解答排除在外，違反後置完備性（post-completeness）。

在評估機制的消融實驗中，作者發現增加測試案例的數量與多樣性會穩定降低測得的成功率，顯示規格的忠實度在稀疏測試下容易被高估。尤其值得注意的是，Codeforces Hacks（Hacks）所構成的對抗案例（adversarial cases）能暴露官方測試完全遺漏的規格缺陷，證明人類撰寫的對抗輸入並非冗餘覆蓋，而是評估規格強健性的必要補充。

此外，作者以 LLM 作為評審（LLM-as-a-judge）建立基線，發現其漏檢了 26% 的失敗案例。這些被漏檢的錯誤往往涉及細微的語義偏差，恰好是規格不忠實（unfaithful specification）最常發生的地方。這項數據強力佐證了執行導向評估相對於靜態模型評分的優越性。

#### 與現有研究的比較

在形式驗證（formal verification）與驗證過的程式碼生成（verified code generation）的文獻中，多數研究假設形式規格（formal specification）已經由專家提供，聚焦於如何讓代理生成可通過機器驗證證明（machine-checked proof）的程式碼。本研究則將瓶頸前移，探討當使用者僅具備非形式規格（informal specification）時，代理能否自動產出對應的形式規格。這項定位填補了「從自然語言到驗證就緒規格」的關鍵缺口。

在評估方法上，既有文獻主要依賴兩種途徑：一是聘請專家撰寫參考規格（reference specs），作為黃金標準進行比對；二是採用 LLM 作為評審（LLM-as-a-judge）進行自動評分。前者成本高昂且難以規模化；後者雖然便宜，卻容易忽略細微錯誤。本研究提出的 exec_spec 擴展與對抗案例（adversarial cases）測試，提供了第三條路徑：可擴展、可執行、且對邊界案例（edge cases）敏感的評估訊號。這不僅降低了對專家標註的依賴，也避免了 LLM 評審的近似性偏誤。

然而，本研究仍存在若干侷限。首先，任務來源侷限於 Codeforces 風格的演算法題目，語言為英文，且目標驗證器固定為 Verus（針對 Rust 的形式驗證器）。這使得基準測試尚未涵蓋真實世界軟體工程中常見的並行、I/O 或系統層級語義。其次，實驗採用固定運算與時間預算，雖確保了橫向比較的公平性，但可能低估了具備更長思考鏈或反覆試錯潛力模型的上限。最後，目前框架僅評估規格本身，尚未將「規格生成」與「程式碼生成+證明生成」整合為單一端到端管線，未能完全模擬「從自然語言題敘到驗證就緒系統」的完整流程。

#### 可重現性評估

本研究在可重現性（reproducibility）方面表現良好。作者已將程式碼、資料集與執行日誌公開於 GitHub 儲存庫（https://github.com/formal-verif-is-cool/verus-spec-gym）。Verus-SpecBench 的 581 筆任務、Verus-SpecGym 的環境腳本，以及與 Harbor 框架的整合程式碼均完整釋出，使其他研究者能夠重現代理互動環境與評估流程。

針對基準測試的持續擴充，作者設計了半自動化管線，可將新釋出的 Codeforces 題目與其 Hacks 轉換為規格撰寫任務。這降低了未來維護與擴展基準測試的門檻，也確保資料來源的可追溯性。

在模型權重方面，實驗所使用的前沿模型（frontier models）均為商用 API 服務（如 Gemini 3.1 Pro），其權重並未公開，但透過固定 API 版本與溫度參數，原則上可達到近似重現。OSS 模型（開源軟體模型）則應可透過公開權重與論文所述的推論設定完全重現。底層的 Verus 驗證器（verifier）與 Rust 工具鏈皆為開源軟體，進一步鞏固了實驗環境的可重建性。

不過，由於代理執行涉及與 Bash（Unix shell 環境）及檔案系統（filesystem）的複雜互動，不同作業系統或容器環境中的細微差異（如檔案權限、時間戳記、Verus 版本編號）仍可能導致非確定性行為。建議後續發布提供預先建置的容器映像檔（container image），以最大化跨平台重現的一致性。

#### 未來研究方向

基於 Verus-SpecGym 與 Verus-SpecBench 的基礎，未來研究可沿以下數個方向展開：

**1. 擴展任務領域與驗證目標**
當前基準測試集中於演算法競賽題目，未來應將規格自動形式化（specification autoformalization）推進至真實世界軟體，例如作業系統核心模組、分散式系統協定或智慧合約。這需要支援更豐富的語義原語，並可能涉及除 Verus 之外的其他驗證器（verifier），如 Coq、Lean 或 Isabelle，以驗證方法論的跨平台泛化性。

**2. 端到端驗證就緒系統生成**
本研究目前將規格生成獨立評估。下一步可將其與驗證過的程式碼生成（verified code generation）結合，探討「聯合推論」是否能帶來互利：例如，讓代理同時生成程式碼、形式規格（formal specification）與機器驗證證明（machine-checked proof），並在驗證器回饋下同步修正三者。這可能緩解目前規格與實作脫節的問題。

**3. 提升開源模型的規格理解能力**
前沿模型（frontier models）與 OSS 模型（開源軟體模型）之間存在超過五十個百分點的差距，暗示規格形式化需要高度成熟的邏輯推理與長脈絡理解能力。未來可針對此任務建構專屬的監督式微調（SFT）或強化學習（RL）資料集，利用 Verus-SpecBench 中執行失敗的軌跡作為負樣本，訓練開源模型縮小能力斷層。

**4. 自動化對抗測試生成**
雖然 Codeforces Hacks（Hacks）提供了高品質對抗案例（adversarial cases），但其數量與覆蓋率仍受限於既有競賽資料。未來可結合模糊測試（fuzzing）與對抗生成網路，針對已生成的形式規格主動挖掘邊界案例（edge cases），甚至建立「規格黑客」競賽機制，持續壓力測試代理產出的規格強健性。

**5. 混合式評估與人機協作**
本研究顯示 LLM 作為評審（LLM-as-a-judge）與執行導向評估各有優劣。未來可設計混合架構：以可執行測試作為第一線篩選，再以 LLM 評審針對無法執行的語義模糊地帶（如效能規格、資源消耗）進行輔助判斷。此外，引入人類專家在迴路中（human-in-the-loop）進行規格確認，並將其回饋轉化為代理的強化學習獎勵，亦是提升實用性的重要途徑。

**6. 多語言非形式規格處理**
目前題目敘述均為英文。未來若將非形式規格（informal specification）擴展至多語言情境，將能檢驗代理在跨語言語義轉譯上的穩健度，並使形式驗證（formal verification）工具鏈普及至非英語語系的開發者社群。

## 論文問答

**Q1：規格自動形式化（specification autoformalization）旨在解決 AI 程式設計代理中的什麼核心問題？**

A：規格自動形式化旨在解決非形式需求與形式規格之間的落差問題。儘管 AI 代理越來越能產出程式碼甚至機器驗證證明，這些保證僅能確認程式碼符合「形式規格」，卻無法確保該形式規格本身真實反映了使用者的原始意圖。若形式規格對非形式描述不忠實，整個形式驗證的保證將失去意義，甚至可能產生危險的誤導。

**Q2：為何現有的評估方法（專家參考規格與 LLM 作為評審）不足以評估規格的忠實度？**

A：專家撰寫的參考規格需要大量人力與領域專業知識，針對每道題目逐一製作，成本高昂且難以大規模擴展。相對地，LLM 作為評審雖然成本較低且具擴展性，但僅能提供近似判斷，容易忽略規格不忠實時最常出現的細微邏輯錯誤。論文實驗顯示，LLM 評審基線遺漏了可執行評估器所抓到的 26% 失效案例，證明其不足以作為可信賴的評估依據。

**Q3：為何隨著 AI 程式設計代理能力提升，規格自動形式化會成為新的瓶頸？**

A：當前沿模型越來越擅長生成正確的實作與形式證明後，限制因素便從「代理能否寫出正確程式碼」轉移到「代理能否精準理解非形式需求並將其形式化」。不正確的形式規格若過弱，可能使驗證器將錯誤程式碼認證為正確；若過強，則可能拒絕完全有效的正確解。因此，若缺乏忠實的規格自動形式化，驗證過的程式碼生成在實務上就無法可靠地兌現其承諾。

**Q4：Verus-SpecGym 評估代理進行規格自動形式化的整體工作流程為何？**

A：在 Verus-SpecGym 中，代理會收到來自 Codeforces 的非形式題目描述、一份帶有 pre_spec 與 post_spec 空洞的 Verus 形式骨架，以及範例測試、詳解範例與文件等資源。代理透過與 Verus、Bash 和檔案系統互動，反覆起草並精煉形式規格，並從 verus_gym_specgen_check 等工具獲得回饋。代理提交最終規格後，系統會以官方 Codeforces 測試與對抗案例組成的隱藏測試套件進行評估，判斷規格是否忠實捕捉了非形式意圖。

**Q5：本研究實現可擴展、基於執行的形式規格評估之關鍵技術創新是什麼？**

A：關鍵創新在於擴展 Verus 的 exec_spec 機制，將邏輯規格編譯為可在具體輸入上執行的 Rust 程式碼。由於 Verus 規格本質上是用於驗證器的邏輯謂詞，無法直接執行，此擴展彌補了靜態驗證與動態測試之間的鴻溝。透過將規格轉換為可執行的 Rust 檢查，作者得以自動對成千上萬筆輸入（包括對抗案例）進行測試，無需專家撰寫黃金標準即可提供可擴展且精確的評估訊號。

**Q6：作者為何選擇 Codeforces 題目與 Verus 作為基準測試與環境的基礎？**

A：Codeforces 題目具備定義清晰的非形式規格、公開的官方測試案例，以及由競賽參與者設計、用於破解錯誤解法的豐富對抗案例（hacks），非常適合評估規格忠實度。Verus 作為 Rust 的形式驗證框架，不僅針對現代系統程式語言，也提供了作者可擴展的 exec_spec 機制以實現可執行評估。此外，競技程式設計問題的結構化特性支援半自動化的基準擴充流程，同時仍要求代理對隱含語義約束進行深度理解與形式化。

**Q7：Verus-SpecBench 基準測試包含哪些內容，又是如何建構的？**

A：Verus-SpecBench 包含 581 個從 Codeforces 程式設計問題衍生而來的規格撰寫任務，每個任務要求代理在給定的 Verus 骨架中填寫 pre_spec 與 post_spec 函數。該基準不僅提供非形式題目敘述與形式骨架，還包含範例測試案例、詳解範例規格、Verus 文件與評估器原始碼，以支援代理完成任務。為確保評估的強健性，作者還提供了半自動化流程，可將新的 Codeforces 題目及其對應的 hacks 轉換為規格撰寫任務，使基準能隨時間持續成長。

**Q8：前沿模型與開源模型在 Verus-SpecBench 上的主要表現差異為何？**

A：評估中最強的前沿模型 Gemini 3.1 Pro 成功解決了 77.8% 的任務，其他前沿模型則達到 51.1% 至 57.8%，顯示頂尖商用模型在規格自動形式化上已具備相當能力。相較之下，受測的開源模型僅達到 21.5% 至 25.5%，揭示了閉源前沿系統與現有開源模型之間存在顯著的能力落差。這些結果表明，雖然規格自動形式化對最先進的代理而言已非遙不可及，但對大多數開源模型而言仍是極具挑戰性的任務。

**Q9：消融實驗揭示了對抗案例與測試套件密度的重要性為何？**

A：消融實驗顯示，增加評估所用測試案例的數量與多樣性會持續降低測得的成功率，說明在稀疏的測試套件下，規格忠實度容易被高估。從 Codeforces 提取的對抗 hacks 尤其珍貴，因為它們能暴露官方測試完全遺漏的規格失效案例，證明人類撰寫的對抗輸入是不可或缺的互補，而非冗餘的疊加。此外，與 LLM 作為評審基線的比較顯示，LLM 評審遺漏了可執行評估器所抓到的 26% 失效案例，進一步驗證了具體執行測試相對於近似語義評估的必要性。

**Q10：規格自動形式化在哪些實務軟體開發情境中最具影響力？**

A：規格自動形式化在高保證軟體開發中最具影響力，例如作業系統、密碼學函式庫與安全關鍵嵌入式系統，因為它能銜接自然語言需求與機器可檢查的證明。它也能簡化驗證過的程式碼生成流程，讓 AI 代理自動將產品經理文件或 API 規格轉譯為驗證器可檢查的形式合約。透過將形式方法中最耗時且容易出錯的步驟——撰寫規格——自動化，這項技術有望顯著降低業界採用嚴謹軟體驗證的門檻。

**Q11：在真實驗證流程中部署自動形式化代理時，會浮現哪些產品層面的考量？**

A：首要的產品考量是評估訊號的可信度，因為部署不忠實的規格可能導致錯誤程式碼被正式認證為正確，造成虛假的安全感。本研究指出，單獨依賴 LLM 評審對生產環境而言並不足夠，因為它會遺漏細微的邏輯錯誤，這意味著任何部署系統都必須整合基於全面且對抗測試套件的可執行驗證。此外，前沿模型與開源模型之間的顯著性能差距也意味著，企業若要圍繞此技術建構產品，必須謹慎選擇模型後端，並可能投資於微調或混合式人機協作審查流程。

**Q12：這項工作可能如何影響 AI 代理與形式方法領域的更廣泛研究方向？**

A：這項工作將研究社群的焦點從純粹生成驗證過的程式碼，轉移到上游挑戰：如何忠實地將非形式意圖轉譯為形式規格，並指出這是端到端驗證開發中的新瓶頸。透過提供 Verus-SpecBench 與 Verus-SpecGym 作為開放的基準與環境，它為規格自動形式化的進展建立了標準化的試驗場，如同程式碼基準推動了程式合成研究的發展。此外，它證明了邏輯規格的可執行評估既可行又必要，有望啟發針對 Verus 與 Rust 之外的其他驗證框架與程式語言採取類似方法。

**Q13：Verus-SpecBench 基準與評估方法有哪些已承認的限制？**

A：該基準目前聚焦於 Codeforces 風格的演算法問題，雖然結構明確，但可能無法完全涵蓋大型工業軟體系統中非形式需求的複雜性與模糊性。評估依賴於針對有限測試案例的具體執行，這雖能提供強烈的忠實度證據，卻無法像非形式與形式規格間的完整形式等價證明那樣提供數學確定性。此外，實驗是在固定的運算與時間預算下進行，因此結果可能無法反映模型在獲得更長推理時間或更多反覆精煉資源時的表現上限。

**Q14：模型生成的規格中觀察到哪些主要失效模式，這對現有模型能力有何意涵？**

A：分析歸納出三種反覆出現的失效模式：遺漏重要輸入假設、接受不正確輸出（違反健全性）、以及拒絕有效輸出（違反完備性）。這些失效意謂著現有模型即使在能生成正確執行程式碼的問題上，仍難以進行精確的邏輯推理並完整提取自然語言描述中的隱含約束。這種寫程式能力與規格忠實度之間的脫節顯示，模型缺乏對問題語義的深層結構化理解，往往無法從範例推廣到需求的完整邏輯邊界。

**Q15：作者建議哪些未來方向以改善規格自動形式化及其評估？**

A：作者建議透過半自動化流程持續擴充 Verus-SpecBench，隨著新 Codeforces 題目與 hacks 的釋出不斷提高評估標準。他們也暗示需要改進模型架構或訓練範式，專門強化從自然語言中進行邏輯推理與約束提取的能力，因為即使前沿代理也表現出脆弱性。最後，將可執行規格評估擴展到競技程式設計之外的更豐富領域——例如並發系統、分散式協定或大型軟體 API——是邁向讓自動形式化在真實世界驗證任務中實用的關鍵下一步。

## 實務應用指南

### 適用場景

1. **競技程式題庫的形式化**：將 Codeforces 等平台的自然語言題目自動轉為 Verus 形式規格，用於建構「驗證過的程式碼生成」資料集，確保 AI 程式設計代理產出的演算法實作符合題目隱含與顯式的邊界條件。
2. **安全關鍵 Rust 模組的需求形式化**：在區塊鏈、作業系統核心或嵌入式系統開發中，將非形式規格（如 RFC 文件或內部技術文件）轉為 pre_spec 與 post_spec，讓形式驗證成為 CI/CD 的一環，降低記憶體安全與邏輯錯誤風險。
3. **遺留系統重構與遷移**：針對缺乏完整測試的舊有程式碼，利用規格自動形式化從註解或需求文件生成邏輯謂詞，再透過 Verus 驗證新實作與原始意圖的一致性。
4. **形式驗證教育輔助**：在程式語言或軟體工程課程中，讓學生撰寫演算法實作，再由代理環境自動生成參考規格，透過 exec_spec 產生可執行的 Rust 檢查，即時驗證學生程式碼的輸入假設與輸出性質。
5. **對抗式測試管線建置**：整合 Codeforces Hacks 或內部歷史缺陷案例，建立自動化規格強化流程，確保形式規格不會因過度寬鬆而接受錯誤輸出，或因過度嚴格而拒絕正確輸出。

### 實作前置條件

- **資料準備**：需蒐集自然語言需求描述（如 Markdown 格式的問題敘述）、對應的 Rust 函數簽名、範例測試案例，以及用於壓力測試的對抗案例（如歷史 Hacks 或模糊測試產出的邊界案例）。若無現成參考規格，至少需準備一份已知正確的參考實作作為完備性基準。
- **運算資源**：本機或容器化環境需能編譯 Verus 與 Rust 工具鏈；若使用前沿模型進行規格生成，需預留足夠的 API 預算（依 581 題規模估算，單次完整評估需數百至數千次呼叫）。驗證階段建議配置多核心 CPU 以平行執行隱藏測試。
- **技術能力**：團隊需具備 Rust 中階開發能力、基礎形式驗證知識（理解前置條件、後置條件、不變量與邏輯謂詞），以及 Verus 特定語法（如 specfn、forall、exists）。此外，需熟悉代理環境設定（Bash、檔案系統操作）與 Harbor 等現代代理評估框架。

### 實作步驟建議

1. **定義規格介面**：為目標 Rust 函數建立 Verus 形式骨架，明確劃分 pre_spec（輸入性質）與 post_spec（輸出性質）的函數簽名與型別。
2. **擴充 exec_spec 支援**：評估目標問題所需的型別與運算子（如序列操作、位元運算），參考論文方法擴充 Verus 的 exec_spec 機制，使產生的邏輯謂詞能編譯為可執行的 Rust 檢查。
3. **建構代理環境**：部署 Verus-SpecGym 架構，整合 Verus 驗證器、Bash shell、檔案系統與 Harbor 框架，設定 verus_gym_specgen_check 指令以提供即時回饋。
4. **設計上下文提示**：為 LLM 提供詳解範例、Verus 官方文件、VSTD 原始碼片段以及評估器原始碼，強化模型對規格語義的理解。
5. **執行迭代生成**：讓 AI 程式設計代理讀取非形式規格，填寫骨架中的邏輯謂詞，透過範例測試案例與驗證器錯誤訊息進行多輪修正。
6. **執行雙軌評估**：以官方測試案例驗證基本正確性，再以對抗案例（Hacks）測試後置健全性與後置完備性，確保規格不會遺漏重要輸入假設。
7. **建立人工覆核閘道**：由具備形式驗證經驗的工程師抽樣審查產生的規格，特別關注 LLM 作為評審可能遺漏的細微語義錯誤，並將修正結果回饋至訓練或提示範本。

### 潛在風險與注意事項

- **健全性缺口（過弱規格）**：模型傾向生成寬鬆的 post_spec，導致錯誤輸出被接受。建議強制要求通過對抗案例驗證，而非僅依賴範例測試案例。
- **完備性缺口（過強規格）**：pre_spec 可能加入不必要的輸入假設，使合法輸入被拒絕。應以參考實作驗證所有官方測試皆能通過規格檢查。
- **LLM 評審誤判**：論文顯示 LLM 作為評審會遺漏 26% 的失效模式，因此不可將其作為唯一評估手段，必須以可執行測試為最終依據。
- **exec_spec 型別限制**：Verus 的 exec_spec 並未涵蓋所有 Rust 語法，若問題涉及複雜資料結構，需額外開發轉譯層，否則無法產生可執行的 Rust 檢查。
- **成本與規模化瓶頸**：前沿模型雖然成功率達 77.8%，但 API 成本高昂；OSS 模型成功率僅 21.5–25.5%，實務上可能需要混合策略（frontier 生成 + OSS 驗證）或大量提示工程。

### 與其他技術的整合建議

- **與 CI/CD 整合**：將 Verus-SpecGym 嵌入 Rust 專案的持續整合流程，在每次提交時自動生成或驗證關鍵函數的形式規格，並將後置健全性與後置完備性報告輸出為管線產物。
- **與 AI 程式設計代理整合**：採用「規格優先」流程——先由代理產生忠實的形式規格，再進行驗證過的程式碼生成，避免傳統「先寫程式再補證明」導致的規格與實作脫節。
- **與模糊測試（Fuzzing）整合**：將模糊測試引擎產出的邊界案例納入對抗案例庫，補充 Codeforces Hacks 的不足，特別針對企業內部專屬領域的隱藏測試。
- **與需求管理工具整合**：開發外掛程式將 Jira、Confluence 或 Notion 中的非形式需求自動擷取為 Markdown，餵入 Verus-SpecGym 作為問題敘述，並將產生的 pre_spec / post_spec 回寫至文件系統或程式碼註解。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先建立 Rust 基礎語法與形式驗證的核心概念（如前置條件、後置條件），再聚焦論文圖一與 Verus-SpecGym 的互動流程，理解「非形式題目 → 形式規格 → 可執行檢查」的端到端轉換邏輯，暫時略過 exec_spec 擴充的技術細節。
- **AI 工程師**：請重點研讀代理環境的設計決策，包括 Verus 與 Bash、檔案系統的整合方式、Harbor 框架的角色，以及 exec_spec 如何將邏輯謂詞轉為可執行的 Rust 檢查；這些是將研究原型轉為生產級系統的關鍵。
- **研究人員**：建議深入分析失效模式分類（遺漏輸入假設、接受錯誤輸出、拒絕正確輸出）與評估方法論，特別是對抗案例相對於 LLM 作為評審的獨特價值，並思考如何將此評估框架擴展至其他驗證器（如 Dafny、F*）或程式語言。
- **產品經理**：請優先關注適用場景與量化數據——前沿模型 77.8% 的成功率顯示規格自動形式化已具實用潛力，但 OSS 模型僅 21.5–25.5% 代表現階段仍需依賴商用 API；評估導入時應權衡驗證準確性提升與運算成本，並規劃人機協作覆核機制作為品質閘道。
