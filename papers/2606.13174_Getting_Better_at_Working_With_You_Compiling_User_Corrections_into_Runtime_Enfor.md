# 更懂得與你合作：將使用者修正編譯為程式設計代理的執行期強制執行

**原文標題：** Getting Better at Working With You: Compiling User Corrections into Runtime Enforcement for Coding Agents

## ⚡ TL;DR

互動式程式設計代理雖能記住使用者修正，卻無法保證後續確實遵守，導致相同錯誤反覆發生。
本文提出TRACE，將使用者修正改寫為原子規則並編譯為執行期檢查，確保代理完成任務前必須通過。
TRACE顯著降低分布內外任務的偏好違規率，同時維持任務成功率，有效解決記憶無法根治的重複摩擦問題。

## 摘要翻譯

互動式大型語言模型代理（Interactive LLM Agents）逐漸成為日常工作的一部分，但它們並不會隨著時間穩定地變得更易協作：在某個工作階段中被記住的修正，仍可能在下一個工作階段被違反。我們探討偏好存取（Preference Access）與偏好遵循（Preference Compliance）之間的落差。在去識別化的真實使用者摩擦案例（Friction Cases）所衍生的任務中，Mem0 記憶系統仍導致 57.5% 適用的偏好檢查被違反。我們提出測試時規則獲取與編譯強制執行（Test-time Rule Acquisition and Compiled Enforcement, TRACE），一個適用於程式設計代理（Coding Agents）執行環境的直接嵌入式技能層管線（Drop-in Skill-layer Pipeline），能夠挖掘使用者修正（User Corrections）、將其改寫為原子規則（Atomic Rules），並編譯為執行期檢查（Runtime Checks），代理必須在通過這些檢查後才能完成未來的任務。與開發者預先撰寫的執行期檢查不同，TRACE 技能（Skill）來自使用者自身在對話中的修正。我們在 ClawArena 程式設計代理任務與 MemoryArena 衍生之記憶密集型任務上進行模擬使用者參與迴路（Simulated User-in-the-loop）實驗以評估 TRACE。在 ClawArena 上，TRACE 將分布內任務（In-distribution Tasks）的保留偏好違規（Held-out Preference Violation）從 100.0% 降至 37.6%，並將分布外任務（Out-of-distribution Tasks）的保留偏好違規從 100.0% 降至 2.0%。在 MemoryArena 衍生任務上，TRACE 將分布內違規從 100.0% 降至 60.5%，同時在任務通過（Task Pass）方面達到或超越最強的記憶基線（Memory Baseline）。這些結果顯示，將修正編譯為執行期強制執行（Runtime Enforcement）能夠解決一種重複摩擦失效模式（Repeated-friction Failure Mode），而單靠記憶無法穩定解決此問題，從而減少使用者在未來多個工作階段中重複陳述相同修正的需求。實驗程式碼可於 https://github.com/YujunZhou/TRACE_exp 取得，可部署的技能則可於 https://github.com/YujunZhou/tellonce 取得。

### 核心貢獻（3～5點）
- 揭示互動式大型語言模型代理於偏好存取與偏好遵循之間存在顯著落差，並量化現有記憶基線 Mem0 在真實使用者摩擦案例所衍生的任務中，仍導致 57.5% 的適用偏好檢查被違反。
- 提出測試時規則獲取與編譯強制執行（TRACE），一個適用於程式設計代理執行環境的直接嵌入式技能層管線，可自動從使用者修正中挖掘並改寫為原子規則，再編譯為執行期檢查。
- 於 ClawArena 程式設計代理任務與 MemoryArena 衍生之記憶密集型任務上進行模擬使用者參與迴路實驗，顯示 TRACE 能將分布內任務的保留偏好違規從 100.0% 降至 37.6%，分布外任務從 100.0% 降至 2.0%。
- 證明將使用者修正編譯為執行期強制執行，可有效解決記憶單獨無法穩定克服的重複摩擦失效模式，從而減少使用者在跨工作階段中重複陳述相同修正的需求。

### 適合對象
從事互動式大型語言模型代理、程式設計代理、人機協作與記憶系統研究之學者與工程師，以及尋求提升代理跨工作階段一致性與使用者體驗之框架開發者。

## 深度分析

#### 方法論解析

本文的核心論點在於辨識並量化「偏好存取（Preference Access）」與「偏好遵循（Preference Compliance）」之間的結構性落差。作者指出，現有的記憶系統（如 Mem0）雖能將使用者修正（User Corrections）儲存並於後續工作階段進行記憶檢索（Memory Retrieval），但這僅讓偏好「可見」，並未強制代理「遵守」。為此，作者提出 TRACE（Test-time Rule Acquisition and Compiled Enforcement，測試時規則獲取與編譯強制執行），一套針對程式設計代理（Coding Agents）的直接嵌入式技能層管線（Drop-in Skill-layer Pipeline）。

TRACE 的運作邏輯可分為三階段：

1. **規則獲取（Rule Acquisition）**：從情境化自然語言回饋（Situated Natural-language Feedback）中萃取潛在偏好。使用者的糾正往往嵌入在特定對話脈絡中（例如「下次記得在停止前清理 debug 檔案」），系統需將其從敘事性語句轉譯為結構化意圖。
2. **原子化改寫（Atomic Rewriting）**：將萃取出的偏好改寫為原子規則（Atomic Rules）。這一步是關鍵的表徵轉換（representation change）——從被動的「建議」轉為明確的、可執行的條件敘述。原子規則的設計確保每條規則對應單一、具體的執行約束，降低語意模糊性。
3. **編譯強制執行（Compiled Enforcement）**：將原子規則編譯為執行期檢查（Runtime Checks），並嵌入程式設計代理的執行階段。這些檢查成為代理完成任務前的必要閘門（hard gate），而非僅附加於提示（prompt）中的軟性提醒。透過此機制，TRACE 將個人化從「提示側建議」轉變為「主動執行約束」。

與開發者預先撰寫的規則不同，TRACE 的技能（Skill）來自使用者自身的聊天修正，形成持續增長的每使用者規則庫。這種設計使代理能在不修改底層模型權重的情況下，透過執行期強制執行（Runtime Enforcement）動態適應使用者特定限制（User-specific Constraints）。

#### 實驗數據解讀

作者採用模擬使用者參與迴路（Simulated User-in-the-loop）的實驗協定，在 ClawArena 與 MemoryArena 兩大基準上評估 TRACE。評估指標聚焦於保留偏好違規（Held-out Preference Violation）與任務通過（Task Pass），並區分分布內任務（In-distribution Tasks）與分布外任務（Out-of-distribution Tasks）。

在 ClawArena 的程式設計代理任務中，基線方法（無強制執行）在保留測試集上的偏好違比率為 100.0%，顯示若僅依賴記憶基線（Memory Baseline），代理幾乎必然重複犯錯。引入 TRACE 後，分布內任務的違規率大幅下降至 37.6%；更值得關注的是，分布外任務的違規率從 100.0% 驟降至 2.0%。此現象暗示原子規則具備良好的抽象與遷移能力——當規則被編譯為結構化檢查後，其適用範圍可能超越原始訓練情境，對未見過的任務型態展現強韌的約束力。

在 MemoryArena 衍生的記憶密集型任務中，TRACE 將分布內違規率從 100.0% 降至 60.5%。雖然降幅不如 ClawArena 顯著，但仍顯著優於純記憶方法。更重要的是，TRACE 在降低違規率的同時，其任務通過率仍能匹配或超越最強的記憶基線。這排除了「強制執行會過度限制代理行動而損害任務完成度」的疑慮，證明執行期檢查與任務目標具有相容性。

此外，作者在真實使用者摩擦案例（Friction Cases）的初步分析中發現，Mem0 記憶系統即使成功檢索到偏好，仍有 57.5% 的適用檢查被違反。這項數據確立了「記憶不等於遵循」的命題，也為 TRACE 的必要性提供了強有力的實證基礎。

#### 與現有研究的比較

現有研究大致可分為兩條路線：記憶導向的個人化與執行期強制執行。前者包括 Mem0、ReMe、Hindsight 等系統，其核心能力在於長期記憶的儲存、更新與檢索。然而，這些方法本質上仍將使用者修正視為「自然語言建議」，透過提示注入（prompt injection）或上下文擴增來影響代理行為。本文明確指出，此範式在長上下文對話中偏好遵循會嚴重惡化，因為記憶檢索並未改變代理的執行路徑。

另一路線則聚焦執行期強制執行，如 guard agents、policy compilers 或形式化規格檢查。這些方法的共同前提是規則已由開發者預先撰寫（developer-authored rules），解決的是「給定規則後如何確保遵守」的問題。TRACE 的獨特貢獻在於填補「規則來源」的空白：它自動從使用者修正中提煉規則，並將其編譯為可執行檢查，形成「使用者回饋 → 原子規則 → 執行期閘門」的端到端閉環。

然而，本文方法仍存在若干限制。首先，ClawArena 的分布內違規率（37.6%）顯著高於分布外（2.0%），此反直覺現象可能源於分布內任務與規則庫的交互更為複雜，或原子規則在面對語意相近但結構不同的任務時出現過度泛化，但作者未深入剖析其成因。其次，MemoryArena 的違規率僅降至 60.5%，顯示在高度依賴工作區狀態（Workspace State）與長期脈絡的記憶密集型任務中，單純的執行期檢查可能不足以捕捉所有細微偏好。最後，TRACE 目前僅針對程式設計代理進行驗證，其規則編譯器對於非結構化或創意性任務的適用性仍有待檢驗。

#### 可重現性評估

本文在可重現性方面表現良好。作者已公開實驗程式碼（https://github.com/YujunZhou/TRACE_exp）與可部署的技能模組（https://github.com/YujunZhou/tellonce），使其他研究者能夠複製 TRACE 的直接嵌入式技能層管線。評估所使用的 ClawArena 與 MemoryArena 均為已發表的公開基準，且實驗採用模擬使用者參與迴路協定，具備標準化的互動流程。

不過，由於提供的摘要與引言片段未詳細說明實驗中四種程式設計代理的具體模型版本、API 參數設定或溫度（temperature）等推論超參數，若完整論文未補充這些細節，將可能影響跨平台復現的精確度。此外，從匿名化真實使用者摩擦案例衍生的任務資料集是否同步公開，亦會影響社群對「偏好存取–偏好遵循落差」的獨立驗證。整體而言，核心管線與基準環境的開源已為可重現性奠定堅實基礎。

#### 未來研究方向

基於 TRACE 的架構與實驗結果，未來研究可沿以下方向展開：

1. **規則衝突與動態管理**：隨著每使用者規則庫持續增長，不同原子規則間可能出現邏輯衝突或時效性變化。未來需發展規則優先級排序、一致性檢查與自動汰舊機制，以適應動態演化的使用者特定限制。

2. **隱性回饋的規則化**：目前 TRACE 主要處理顯性的情境化自然語言回饋。擴展至隱性訊號——例如使用者撤銷（undo）操作、編輯歷程或表情回饋——將能更全面地捕捉使用者意圖。

3. **跨領域遷移**：驗證 TRACE 是否適用於非程式設計代理領域，如資料分析、文件撰寫或科學推理。這需要開發領域特定的規則編譯器與執行期檢查語言。

4. **人機協同驗證**：在將使用者修正編譯為原子規則前，引入人類確認步驟，確保規則詮釋符合使用者真意。這對於高風險或高模糊性的修正尤為重要。

5. **形式化與理論分析**：針對 ClawArena 分布外任務違規率遠低於分布內的現象，需進行深入的理論分析，探討原子規則的泛化邊界。長期而言，可將執行期檢查與形式化驗證（formal verification）結合，以提供超越測試的保證。

6. **多模態規則萃取**：讓系統能從程式碼差異（code diffs）、執行日誌或甚至 GUI 互動中萃取規則，進一步豐富規則獲取的訊號來源。

## 論文問答

**Q1：這篇論文指出互動式程式設計代理存在什麼核心問題？為什麼這個問題會嚴重影響使用者體驗？**
A：論文指出核心問題在於「偏好存取」與「偏好遵循」之間存在明顯落差，即使代理記住了使用者的修正，在後續工作階段中仍可能再次違反相同指示。這種重複摩擦失效模式意味著使用者必須在不同會話中反覆陳述相同的糾正內容，嚴重削弱了代理應該「隨時間變得更易協作」的核心承諾。對於日常使用的程式設計代理而言，這不僅造成效率低下，更讓使用者難以建立對代理長期行為穩定性的信任。

**Q2：現有的記憶系統（如 Mem0）為何無法有效解決上述問題？其根本限制是什麼？**
A：現有記憶系統雖然能夠儲存並檢索使用者的自然語言修正，但這些修正本質上仍停留在「建議性」的語意層次，並未轉化為對代理執行流程的強制約束。論文實證顯示，即使採用 Mem0 記憶，仍有高達 57.5% 的適用偏好檢查被違反，顯示「記得」不等於「做到」。根本限制在於自然語言回饋缺乏執行期強制執行機制，隨著對話脈絡增長，代理即便檢索到過往規則，也可能因注意力分散或推理偏差而未能確實遵守。

**Q3：為什麼將使用者修正轉化為執行期強制執行對程式設計代理特別重要？**
A：程式設計代理的許多修正涉及可執行行為，例如清理除錯檔案、執行特定指令或終止前確認工作區狀態，這些都是明確的執行條件而非模糊偏好。若僅以自然語言形式儲存，代理在面對複雜程式碼庫操作時，極易因工具呼叫順序或上下文干擾而忽略這些條件。透過執行期強制執行，能確保代理在標示任務完成前必須通過具體驗證，從而將使用者的個人化需求從被動提醒提升為主動約束，這對維護工作區整潔與符合團隊規範至關重要。

**Q4：TRACE 的核心運作流程包含哪些步驟？它如何將使用者修正轉化為可執行的規則？**
A：TRACE（Test-time Rule Acquisition and Compiled Enforcement）作為一個直接嵌入式的技能層管線，首先從使用者的聊天修正中挖掘底層偏好，接著將其改寫為原子規則並配對可執行的檢查程式。這些編譯後的執行期檢查會被整合至代理後續的工作階段中，在代理宣告任務完成前強制執行。與開發者預先撰寫的規則不同，TRACE 的技能完全來自使用者自身的對話回饋，形成持續成長的個人化規則庫。

**Q5：TRACE 相較於傳統記憶增強方法，其關鍵創新為何？**
A：TRACE 的關鍵創新在於將個人化機制從「被動的提示側建議」轉變為「主動的執行期約束」，這是記憶檢索與偏好推論之外的關鍵下一步。傳統方法僅讓修正「可見」，而 TRACE 透過編譯機制讓修正成為代理必須通過的硬性檢查，從根本上改變了修正的表示形式。這種範式轉移確保了使用者修正不會因語境增長或代理推理失誤而被忽略，真正實現了跨工作階段的行為一致性。

**Q6：為什麼 TRACE 選擇將規則設計為「原子規則」並搭配「執行期檢查」？這樣的設計選擇有何優勢？**
A：將規則設計為原子規則，意味著每條規則都是最小且不可再分的執行單位，能夠精確對應到單一的可驗證行為，避免複雜自然語言描述中的歧義與耦合。搭配執行期檢查則確保這些規則能在代理實際操作環境中被客觀驗證，例如檢查特定檔案是否已清理或指令是否正確執行。這種設計優勢在於它將模糊的情境化回饋轉化為明確的真偽條件，使得代理在標示任務完成前無法迴避這些約束，大幅提升了偏好遵循的可靠性。

**Q7：論文在哪些評測基準上驗證 TRACE？實驗設計有何特點？**
A：論文選用 ClawArena 與 MemoryArena 衍生任務作為主要評測基準，並採用模擬使用者參與迴路的實驗協定來模擬真實互動場景。ClawArena 專注於程式設計代理任務，而 MemoryArena 衍生任務則用於測試記憶密集型情境下的表現。實驗設計涵蓋分布內與分布外任務拆分，並在四個不同的程式設計代理上進行評估，以確保結果的泛化性與穩健性。

**Q8：TRACE 在實驗中達成了哪些關鍵量化成果？與記憶基線相比表現如何？**
A：在 ClawArena 上，TRACE 將保留偏好違規率從 100.0% 大幅降低至分布內的 37.6% 與分布外的 2.0%；在 MemoryArena 衍生任務中，分布內違規率也從 100.0% 降至 60.5%，同時在任務通過率上匹配或超越了最強的記憶基線。相較於 Mem0、ReMe、Hindsight 等記憶對照組，TRACE 不僅顯著減少了重複違規，更證明了執行期強制執行能有效解決單純記憶無法可靠處理的重複摩擦失效模式。這些結果顯示，編譯後的規則能夠在維持任務成功率的同時，顯著提升代理對使用者偏好的遵循度。

**Q9：論文是否探討了 TRACE 在不同分布情境下的泛化能力？結果顯示什麼趨勢？**
A：是的，論文特別區分了分布內與分布外任務來評估泛化能力，結果顯示 TRACE 在分布外任務上的表現甚至優於分布內任務，例如在 ClawArena 上分布外違規率僅 2.0%。這顯示由原子規則與執行期檢查構成的強制執行機制，對於未見過但結構相似的情境具有極佳的遷移效果。相較之下，單純依賴記憶檢索的方法在面對新情境時，往往因語境差異而難以正確套用過往修正，進一步凸顯了編譯強制執行的優勢。

**Q10：在實際產品場景中，TRACE 最適合部署在哪些類型的程式設計代理互動中？**
A：TRACE 特別適合部署在需要長期維護個人化工作習慣的程式設計代理中，例如協助開發者管理程式碼庫、執行自動化腳本或進行重構任務的互動式助手。當使用者經常需要糾正代理關於「保留哪些檔案」、「執行何種指令」或「終止前確認哪些條件」等可執行行為時，TRACE 能自動將這些重複出現的回饋轉化為持久規則。這使得代理在面對相同開發者時，能夠像一位逐漸熟悉團隊規範的協作者，持續減少溝通成本。

**Q11：作為一個「直接嵌入式技能層」，TRACE 在整合到現有代理執行環境時具備哪些產品優勢？**
A：TRACE 被設計為無縫整合至現有代理執行環境的模組化管線，無需從頭改造底層模型或重新設計代理架構，降低了部署門檻與整合成本。由於規則來自使用者自身的聊天修正，產品團隊無需預先為所有可能的使用者偏好撰寫規則，實現了真正的個人化自動擴展。此外，論文已釋出可部署的技能與實驗程式碼，讓開發者能夠直接將其引入現有的程式設計代理工作流程中，加速落地應用。

**Q12：TRACE 的成功對整個互動式 AI 代理領域可能帶來什麼深遠影響？**
A：TRACE 證明了僅靠記憶與上下文擴展並不足以實現真正的個人化，將使用者回饋轉化為執行期約束才是提升長期協作品質的關鍵路徑。這一範式可能影響未來各類工具使用型代理的設計哲學，促使研究社群更重視「表示形式轉換」而非僅是「資訊儲存」。對於日常使用者而言，這意味著 AI 代理有望從「每次都要重新教」的工具，進化為「越用越順手」的長期協作夥伴，從根本上改變人機互動的效率與信任基礎。

**Q13：論文承認 TRACE 存在哪些主要限制或仍待改善之處？**
A：儘管 TRACE 顯著降低了偏好違規率，但在 MemoryArena 衍生任務的分布內測試中，違規率仍維持在 60.5%，顯示對於某些記憶密集型或高度複雜的任務，單純的執行期檢查尚無法完全消除違規。此外，論文也暗示並非所有使用者修正都能被輕易改寫為原子規則與可執行檢查，特別是那些涉及模糊語意或高度情境依賴的偏好。這些限制表明，執行期強制執行雖然強大，但仍需與更先進的記憶機制和推理能力結合，才能處理更廣泛的個人化需求。

**Q14：TRACE 在哪些類型的使用者修正或任務情境中可能遭遇失敗？**
A：當使用者的修正涉及抽象設計偏好、主觀程式碼風格判斷，或需要深層語意理解才能驗證的條件時，TRACE 可能難以將其轉化為明確的原子規則與可執行檢查。例如，若使用者要求「讓程式碼更易讀」或「遵循某種架構精神」，這類難以轉化為明確真偽檢查條件的指令就不容易編譯為執行期約束。同樣地，在需要跨多個複雜步驟進行長期規劃的任務中，若中間狀態難以精確定義檢查點，執行期強制執行的覆蓋率也可能下降。

**Q15：基於 TRACE 的框架，未來研究可以朝哪些方向進一步擴展？**
A：未來研究可以探索如何將 TRACE 的編譯強制執行框架擴展至非程式設計領域，例如文件撰寫、資料分析或網頁瀏覽代理，處理更多樣化的可執行約束。另一個方向是提升規則獲取的自動化程度，讓系統能從更隱晦、更間接的使用者回饋中推論並生成原子規則，而不僅限於明確的聊天修正。此外，結合主動學習機制，讓代理在不確定規則適用情境時主動詢問使用者，也有助於建構更精緻、衝突更少的個人化規則庫。

## 實務應用指南

### 適用場景

1. **企業內部程式碼助手**：開發團隊使用互動式代理輔助程式開發時，可將「結束前清理 debug 檔案」、「禁止修改 `package.json` 除非經過確認」、「遵循特定 lint 規則」等團隊慣例，透過使用者修正自動編譯為執行期強制檢查，避免代理在每次新對話中重複犯錯。
2. **個人開發者的長期協作代理**：個人使用者可將習慣性要求（如「優先使用 `pytest` 而非 `unittest`」、「提交前執行 `mypy` 型別檢查」、「不要在根目錄留下暫存檔」）轉為持久化規則，使代理跨工作階段保持一致行為，減少重複糾正。
3. **程式設計教學平台**：在程式導師或自動批改環境中，可將教學規範（如「先寫測試再寫實作」、「不得使用特定函式」、「變數命名必須符合 snake_case」）編譯為執行期閘門，即時阻擋學生（或代理輔助者）的違規操作，強化學習約束。
4. **多專案維運自動化代理**：維運代理在不同專案間切換時，可透過過往使用者修正建立各專案專屬的強制檢查清單（如「部署前檢查環境變數是否設定」、「備份資料庫後才能執行 migration」），避免代理將 A 專案的習慣誤用至 B 專案。
5. **需合規審查的程式碼生成流程**：在金融、醫療或資安敏感場域，可將合規要求（如「不得硬編碼金鑰」、「檔案必須包含授權聲明」、「輸出前進行 PII 掃描」）透過使用者回饋轉為執行期檢查，使代理不僅「記得」規定，更必須「通過檢查」才能標記任務完成。

### 實作前置條件

- **資料需求**：需具備歷史互動對話紀錄（特別是包含使用者糾正、負面回饋的語料）、目標程式碼庫的結構描述與執行環境狀態快照，以及用於驗證規則效果的保留測試集（held-out tasks）。
- **運算資源**：需可呼叫具備程式碼生成與遵循指令能力的大型語言模型 API（如 GPT-4、Claude 3.5 等級），用於規則萃取與檢查程式碼生成；另需隔離的沙盒環境（Docker / container）供執行期檢查安全執行。
- **技術能力**：團隊需熟悉現有代理執行框架（如 OpenHands、AutoDev 或自研框架）、具備撰寫執行期驗證程式的能力（Python、Bash 或靜態分析工具），並了解提示工程與規則引擎設計，以便將 TRACE 以 skill 形式嵌入現有管線。

### 實作步驟建議

1. **部署修正攔截層**：在現有對話介面或代理日誌系統中，識別並擷取使用者糾正語句（例如「你又忘了…」、「請不要…」、「上次說過…」），作為 TRACE 的規則來源輸入。
2. **規則萃取與原子化**：利用 LLM 將自然語言修正轉譯為原子規則（Atomic Rules），明確定義「觸發條件」（何時適用）與「期望行為」（應做或不該做什麼），避免語意模糊。
3. **生成執行期檢查**：針對每條原子規則，自動生成對應的可執行程式碼（Runtime Checks），例如檔案存在性檢查、正規表示式比對、靜態分析腳本或測試斷言，確保規則可被客觀驗證。
4. **掛載至任務完成鉤子**：在代理執行環境的任務結束前插入檢查閘道（如 `before_task_complete` hook），強制代理通過所有適用檢查；未通過則阻擋任務完成標記，並觸發代理自我修正或回報使用者。
5. **建立持久化規則庫**：將編譯後的規則與檢查程式碼按「使用者 × 專案」維度持久化儲存，支援跨工作階段載入、版本管理與規則失效機制，避免無限累積。
6. **驗證與監控迭代**：保留部分歷史修正作為分布內與分布外測試集，定期評估偏好違規率（Preference Violation）與任務成功率（Task Pass），並根據結果迭代優化規則生成提示詞與檢查邏輯。

### 潛在風險與注意事項

- **規則過度嚴格導致誤殺**：自動生成的檢查可能過於嚴格，導致代理在合理情境下被阻擋。建議設計分級機制（如「強制阻擋」vs.「警告提示」），並保留人類覆寫權限。
- **自動生成檢查程式的安全性**：Runtime Checks 會在執行期運作，若生成程式碼包含惡意或錯誤操作（如 `rm -rf /`），風險極高。務必在嚴格隔離的沙盒中執行，並限制檔案系統與網路權限。
- **規則衝突與累積膨脹**：長期使用後，新舊規則可能矛盾（例如早期要求「刪除暫存檔」、後期要求「保留暫存檔以供除錯」）。需定期執行規則一致性檢視與去重機制。
- **分布外任務的適用性**：對於與歷史修正情境差異極大的新任務，既有規則可能不適用甚至阻礙執行。建議保留記憶基線作為後備，並設計規則適用性評分機制。
- **延遲與成本**：執行期檢查會增加額外 I/O、LLM 呼叫與推理延遲。需設計快取機制與選擇性執行策略（如僅對高風險操作或特定檔案變更啟動檢查）。

### 與其他技術的整合建議

- **記憶系統（Mem0、ReMe、Hindsight）**：TRACE 並非取代記憶系統，而是將其輸出升級。建議將記憶庫中標記為「修正」或「偏好」的條目自動餵入 TRACE 的規則編譯管線，形成「記憶檢索 → 規則編譯 → 執行期強制」的三層架構。
- **現有代理框架（OpenHands、AutoDev、SWE-agent）**：以 drop-in skill 或 plugin 形式整合，透過框架提供的任務生命週期 hook（如 `pre_complete`、`on_action`）插入 TRACE 檢查層，無需重寫核心排程邏輯。
- **RAG 與專案知識庫**：將專案說明文件（README、CONTRIBUTING、API 規範）作為靜態規則來源預先編譯，使用者修正則作為動態覆寫層，兩者共同輸入至同一檢查引擎，兼顧通用性與個人化。
- **CI/CD 與測試框架**：將編譯後的 Runtime Checks 同步輸出為標準單元測試或 pre-commit hooks，使代理遵循的規則同時成為人類開發者品質閘門，達成人機協作品質一致。
- **監控與可觀測性平台**：將規則觸發次數、違規率、檢查執行時間作為結構化指標輸出至 Prometheus / Grafana 或 ELK，用於量化「代理協作體驗」的改善幅度，並驅動產品決策。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從圖一與摘要開始，掌握「記住偏好」與「強制遵循」的核心差異。將 TRACE 理解為代理的「習慣養成系統」——不只是讓代理「聽過」你的要求，而是讓它在完成任務前「必須通過考試」。
- **AI 工程師**：請聚焦於方法論中的規則原子化與檢查生成細節，以及附錄中的提示詞設計。實作時需特別關注如何將 TRACE 以 skill 形式掛載到現有代理執行環境，並處理檢查失敗時的重試與錯誤回報機制。
- **研究人員**：建議深入分析實驗設計中的模擬使用者參與迴路（simulated user-in-the-loop）與分布外（out-of-distribution）測試設定。可進一步思考規則編譯的理論完備性、與形式化驗證（formal verification）的結合可能，以及如何在偏好動態變化時更新規則庫。
- **產品經理**：請從第一節的使用者摩擦案例與量化數據（Mem0 仍有 57.5% 違規率）出發，評估 TRACE 對降低使用者重複糾正成本、提升長期留存率的商業價值。規劃產品路線圖時，可將其定位為從「被動記憶」升級為「主動遵循」的關鍵差異化功能。
