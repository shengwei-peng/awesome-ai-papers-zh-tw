## ⚡ TL;DR

現有評估僅能判斷長程智慧體執行成敗，卻難以定位數百步軌跡中最早引入決定性錯誤的負責角色與根因步驟。
LongRCA Bench 收錄五領域千餘條自然失敗軌跡；RCTA 以片段摘要回溯交接指令定位根因。
RCTA 負責角色準確率 51.1%、精確根因步驟準確率24.1%，大幅領先基線，凸顯兩者應獨立評估。

## 摘要翻譯

當長程智慧體（long-horizon agent）的執行失敗時，結果層級評估（outcome-level evaluation）僅能揭示最終結果並不成功，卻無法指出決定性錯誤（decisive error）是在軌跡（trajectory）的何處引入。開發者必須檢視完整執行過程，以識別負責角色（responsible role）並定位最早決定性根本原因步驟（earliest decisive root-cause step）。現有的失敗歸因基準（failure-attribution benchmarks）大多聚焦於較短的軌跡，使得橫跨數百個記錄步驟（recorded steps）的診斷仍鮮少被探索。本研究提出 LongRCA Bench，包含橫跨五個領域、共 1,140 條失敗軌跡，且未注入任何注入式錯誤（injected errors）。該基準針對負責角色與最早決定性根本原因步驟兩個目標，提供獨立評分（independently scored）的人工標註（human labels）。中位數軌跡（median trajectory）長度為 145 個步驟，而最強基線（baseline）僅達到 13.2% 的精確根因步驟準確率（exact root-step accuracy）。我們進一步提出 Root-Cause Trajectory Attribution（RCTA），這是一種免訓練方法（training-free method），從片段摘要（segment summaries）中檢索候選錯誤步驟（candidate error steps），並追溯至較早可用的交接指令（handoff instructions）。在相同骨幹模型（backbone）、基準實例（benchmark instances）與評分協定（scoring protocol）下，RCTA 達到 51.1% 的負責角色準確率（responsible-role accuracy）與 24.1% 的精確根因步驟準確率。這些結果凸顯出，在長軌跡的失敗診斷中，有必要將負責角色歸因（responsible-role attribution）與精確根因步驟定位視為獨立目標（separate targets）進行評估。

### 核心貢獻（3～5點）
- 提出 LongRCA Bench，一個涵蓋五個領域、共 1,140 條真實失敗軌跡的長程失敗歸因基準，中位數軌跡長度達 145 個步驟，填補了長軌跡診斷研究的缺口。
- 提供針對「負責角色」與「最早決定性根本原因步驟」兩項目標的獨立評分人工標註，支持更細緻的失敗分析。
- 提出 Root-Cause Trajectory Attribution（RCTA），一種免訓練方法，透過片段摘要檢索候選錯誤步驟並追溯較早交接指令，有效提升負責角色與根因步驟的定位準確率。
- 實證顯示最強基線僅達 13.2% 的精確根因步驟準確率，凸顯長軌跡失敗診斷的困難，並強調應將負責角色歸因與精確根因步驟定位視為獨立評估目標。

### 適合對象
本論文適合研究大型語言模型驅動智慧體、自動化失敗診斷、多角色協作系統除錯，以及長程任務可解釋性與根因分析的學者與工程師；對於建構智慧體評估基準或設計診斷智慧體的研究人員亦具高度參考價值。

## 深度分析

#### 方法論解析

本研究將長程智慧體（long-horizon agent）執行失敗後的診斷形式化為兩個**獨立預測任務（independent prediction tasks）**：

1. **根本原因定位（root-cause localization）**：找出最早引入與最終失敗相關的**決定性錯誤（decisive error）**的**記錄步驟（recorded step）**。若該錯誤在後續已被成功修復（repaired），則不能選為根因。
2. **負責角色歸因（responsible-role attribution）**：找出對該失敗負責的**工作流程角色（workflow role）**，且角色名稱必須出現在原始軌跡（source trajectory）中，可能是人類角色（human role）。

這兩個任務獨立評分：角色並非由所選步驟的發出者（emitter）推導而來，後續步驟可能傳播（propagate）或暴露（expose）錯誤，但不能取代最早引入錯誤的步驟。

針對上述任務，作者提出 **Root-Cause Trajectory Attribution（RCTA）**，其核心設計可拆解為兩個階段：

- **階段一：片段級候選錯誤召回（segment-level candidate recall）**  
  由於完整軌跡可能長達數百步，直接將全部日誌記錄（log record）餵入單一提示會超出上下文長度，也會稀釋少數**故障相關步驟（fault-relevant steps）**的訊號。RCTA 先將長軌跡切分為多個片段，利用**骨幹模型（backbone）**產生**片段摘要（segment summaries）**，再從摘要中檢索（retrieve）出一小組**候選錯誤步驟（candidate error steps）**。這相當於先做廣域搜尋，把「可能出錯」的區域濃縮出來。

- **階段二：向早期交接指令回溯（backward tracing to earlier handoff instructions）**  
  許多長程失敗並非發生在執行末端，而是源自早期某個角色交出的**交接指令（handoff instructions）**或修復計畫（repair plan），後續執行者只是照表操課。RCTA 針對每個候選錯誤步驟，向前追溯是否存在更早的交接指令包含相同錯誤。這個設計把「廣域搜尋」與「聚焦比對原始日誌文字」分開，降低模型被末端執行步驟或最終完成步驟（terminal completion step）吸引的偏誤。

RCTA 是**免訓練方法（training-free method）**，完全依賴提示工程與檢索邏輯，不額外訓練模型權重。這使其易於在不同**骨幹模型（backbone）**上複製，但也意味著其表現上限受限於基礎語言模型的長上下文理解與因果推理能力。

#### 實驗數據解讀

**LongRCA Bench** 收錄 1,140 條自然發生、非注入式錯誤的失敗軌跡，來自五個領域（domain）：SWE-bench Pro、Terminal-Bench、TravelPlanner、VitaBench 與 WebArena Verified。整體統計凸顯長程診斷的困難：

| 統計量 | 數值 |
|---|---|
| 總軌跡數 | 1,140 |
| 總記錄步驟數 | 178,137 |
| 平均軌跡長度 | 156.3 步 |
| 中位數軌跡長度 | 145 步 |
| 最長軌跡 | 728 步 |
| **根因到結尾距離（root-to-end distance）** 中位數 | 48 步 |
| root-to-end distance 90th percentile | 183 步 |
| root-to-end distance 最大值 | 605 步 |

這表示在典型案例中，**參考根因（reference root）**發生後仍有數十到數百步的下游執行，模型必須抵抗「錯誤越接近結尾越重要」的直覺偏誤。

評估指標分為三項：

- **負責角色準確率（responsible-role accuracy）**
- **精確根因步驟準確率（exact root-step accuracy）**
- **根因步驟 ±5 準確率（root-cause ±5 accuracy）**

在相同**骨幹模型（backbone）**、相同 1,140 條軌跡與相同**評分協定（scoring protocol）**下，RCTA 與五個**基線（baseline）**的比較結果如下（最強基線數值由文中差距反推）：

| 方法 | 負責角色準確率 | 精確根因步驟準確率 | 根因步驟 ±5 準確率 |
|---|---|---|---|
| 最強基線（strongest baseline） | ≈27.5% | 13.2% | ≈24.7% |
| **RCTA** | **51.1%** | **24.1%** | **37.4%** |
| 相對提升 | +23.6 pp | +10.9 pp | +12.7 pp |

數據解讀：

- **角色歸因顯著優於步驟定位**：RCTA 在負責角色（responsible role）上達到 51.1%，但在精確根因步驟（exact root-step）僅 24.1%。這符合直覺：判斷「哪個角色搞砸」可從角色職責與高層摘要推論，而「哪一步最早出錯」需要精確的時間定位。
- **±5 準確率大幅高於精確準確率**：37.4% vs. 24.1%，說明模型常能落在根因附近，但受限於片段切分與摘要粒度，難以命中確切步驟索引（step index）。
- **整體準確率仍偏低**：即使最強方法，精確根因步驟準確率也未達四分之一，顯示長程失敗歸因仍是極具挑戰的問題，不能僅靠結果層級評估（outcome-level evaluation）取代。
- **RCTA 的兩階段設計有效**：相較於直接對全軌跡做單輪推理的基線，RCTA 透過片段摘要召回與交接指令回溯，顯著降低長上下文帶來的雜訊與末端偏誤。

#### 與現有研究的比較

下表整理 LongRCA Bench 與代表性**失敗歸因基準（failure-attribution benchmark）**的差異：

| 基準 | 失敗來源 | 軌跡數 | 人工覆蓋 | 預測目標 | 平均長度 |
|---|---|---|---|---|---|
| HORIZON | Controlled | >3,100 | Sample（40） | Failure mode | – |
| Who&When | Natural | 184 | Full（184） | Agent 與決定性步驟 | 22.2 步 |
| Who&When Pro | Injected | 12,326 | Sample（100） | Agent、步驟、mode | 7.5 步 |
| RootSE | Natural | 102 | Full（102） | 最早根因步驟 | 50.9 步 |
| TraceElephant | Natural | 220 | Full（220） | Component 與 origin step | 20.5–29.3 calls |
| Failure as a Process | Natural | 1,184 | Validated subset | 四個失敗階段 | 42 步 |
| **LongRCA Bench** | **Natural** | **1,140** | **Full（1,140）** | **角色與最早根因步驟** | **156.3 步** |

相較於既有研究，LongRCA Bench 的貢獻與定位可歸納為：

1. **規模與自然性兼具**：收錄 1,140 條完全人工標註（human labels）的自然失敗軌跡，非**注入式錯誤（injected errors）**或受控任務產生，更能反映真實智慧體執行場景。
2. **同時監督角色與最早根因步驟**：多數基準只監督其中一項（如 Who&When 監督 agent 與 decisive step，RootSE 只監督 earliest root step）。LongRCA Bench 明確將**負責角色歸因（responsible-role attribution）**與**根本原因定位（root-cause localization）**設為獨立目標。
3. **強調長程與 root-to-end distance**：平均 156.3 步、中位數 root-to-end distance 48 步，遠超現有基準，迫使診斷方法處理「錯誤在很早步驟引入、在很後步驟才顯現」的延遲效應。
4. **提出 RCTA 作為強基線**：在相同設定下顯著優於五個免訓練基線，為後續研究提供可比的出發點。

**限制與待商榷之處**：

- **僅評估免訓練方法**：實驗只比較 training-free 方法，未探討微調（fine-tuning）或專用診斷模型是否能進一步提升精確根因步驟準確率。
- **人工標註的主觀性**：雖然由 22 位 CS 研究生標註，但「最早決定性錯誤」與「負責角色」仍可能因詮釋不同而產生歧義，文中未詳細報告標註者間一致性（inter-annotator agreement）。
- **角色標籤受限於原始軌跡**：角色名稱必須出現在 source trajectory 中，這雖保證可驗證性，但也限制對跨軌跡通用角色類型的分析。
- **無因果結構**：RCTA 與基線皆基於文本相似度與摘要推理，未建立明確的因果圖或執行語意模型，可能難以處理「多個錯誤交互導致失敗」的複雜案例。
- **離線設定**：僅針對已完成軌跡進行診斷，未涉及線上（online）或互動式診斷。

#### 可重現性評估

本研究已提供專案頁面與排行榜（project page and leaderboard）：https://longrca-bench.github.io/。這是正向訊號，表示作者有意開放社群追蹤進展。然而，從目前提供的上下文來看，有以下可重現性考量：

- **資料集與標註**：論文說明 LongRCA Bench 包含 1,140 條軌跡與人工標註，但未在片段中明確說明是否已釋出完整資料、標註格式與下載方式。可重現性高度依賴這些軌跡與標籤的公開釋出。
- **RCTA 實作**：RCTA 為免訓練方法，理論上只需提示模板與檢索邏輯即可復現，但片段切分策略、摘要提示、候選步驟篩選門檻、回溯比對的相似度函數等細節會顯著影響結果。若未公開原始碼，其他研究者難以完全複製 24.1% 的精確根因步驟準確率。
- **骨幹模型（backbone）**：實驗使用相同 backbone 進行比較，但文中未指明確切模型版本（例如 GPT-4、Claude 3 等）。不同模型的長上下文能力與指令遵循能力差異極大，會影響基線與 RCTA 的絕對數值。
- **評分協定（scoring protocol）**：雖然目標定義清楚，但角色比對是否區分大小寫、步驟索引是否從 0 開始、±5 的邊界條件等細節需要公開，才能確保公平比較。

綜合而言，本研究在問題定義與實驗設計上已具備高透明度，但若要達成完全可重現，仍需補充開源程式碼、資料集下載、標註說明與 backbone 版本資訊。

#### 未來研究方向

基於 LongRCA Bench 與 RCTA 的結果，以下幾個方向值得後續探索：

1. **微調與專用診斷模型**  
   目前僅評估免訓練方法。未來可收集診斷任務資料，訓練專門的 root-cause attribution 模型，或利用強化學習讓模型學習在長軌跡中選擇最相關片段。

2. **因果與執行語意建模**  
   將軌跡轉換為因果圖（causal graph）或程式依賴圖，明確建模步驟間的「導致—被導致」關係，而非僅依賴文本相似度。

3. **線上與互動式診斷**  
   從離線（offline）事後分析延伸到線上（online）診斷，讓智慧體在執行過程中即能偵測潛在根因並主動修復，或引入人類回饋進行互動式歸因。

4. **結合結果層級評估器回饋**  
   目前診斷主要使用軌跡文字。未來可將 **結果層級評估器（outcome-level evaluator）** 的失敗訊號（例如哪些測試失敗、哪個斷言被觸發）納入檢索與排序，提升定位精度。

5. **多模態與跨領域擴展**  
   現有資料以文字日誌為主。未來可納入截圖、API 回傳結構、程式 diff 等多模態資訊，並擴展到更多領域如機器人、科學實驗或醫療決策。

6. **更細緻的片段策略**  
   研究動態片段切分、基於語意轉折點的切分、或階層式摘要（hierarchical summarization），以在保留關鍵資訊的同時降低上下文負擔。

7. **不確定性量化與拒答機制**  
   當模型無法確定根因時，應能輸出置信度或選擇拒答（abstention），避免給出錯誤歸因。可研究 calibration 與選擇性預測。

8. **自動化標註驗證與擴充**  
   開發半自動工具輔助人工標註，並建立標註者一致性指標，以擴大資料規模並降低標註成本。

9. **從歸因到修復的端到端系統**  
   將 root-cause localization 與自動修復（automatic repair）串接，驗證診斷品質是否真的能提升智慧體的長程成功率。

10. **理論分析：root-to-end distance 的影響**  
    系統性地研究 root-to-end distance、軌跡長度、領域特性與模型表現之間的關係，找出目前方法的瓶頸究竟來自「長度」還是「因果延遲」。

## 論文問答

**【Background & Motivation】**

**Q1：LongRCA Bench 主要想解決什麼問題？**
A：長程智慧體（long-horizon agent）執行失敗時，傳統的結果層級評估只能告訴開發者「任務失敗了」，卻無法指出決定性錯誤最早是在哪一步出現，也無法判斷是哪個工作流程角色該負責。隨著軌跡動輒長達數百步，錯誤的發生點與最終失敗點之間可能相隔很遠，開發者必須耗費大量時間檢視完整執行紀錄。LongRCA Bench 因此提供 1,140 條自然發生、非注入式失敗軌跡，並附上負責角色與最早決定性根本原因步驟的人工標註，讓診斷能力可以被系統化地衡量。

**Q2：為什麼現有的失敗歸因方法在長軌跡上表現不佳？**
A：現有方法大多聚焦於較短的軌跡，當步驟數增加到數百步時，與故障真正相關的步驟變得非常稀疏，模型很容易被軌跡末端的最終錯誤或執行者吸引。此外，參考根因步驟往往出現在執行結束前很久，導致方法難以區分「最早引入錯誤的步驟」與「後續傳播或暴露錯誤的步驟」。在 LongRCA Bench 上，最強基線的精確根因步驟準確率僅有 13.2%，凸顯了長程診斷的困難度。

**Q3：為什麼要把「負責角色歸因」和「根本原因定位」當成兩個獨立目標？**
A：因為發出根因步驟的角色不一定就是應該對失敗負責的角色，例如 SWE-bench Pro 案例中，DiagnostAgent 在第 37 步提出的修復計畫違反任務限制，後續執行智慧體只是照計畫執行，最終卻在第 163 步才顯現失敗。如果將兩者綁定，模型可能會錯誤地把責任歸給後來的執行者，或把最終完成步驟當成根因。分開預測能讓開發者同時知道「該修正哪個角色」以及「最早該介入哪一步」，從而進行更精準的修復。

**【Method & Innovation】**

**Q4：RCTA 的核心方法流程是什麼？**
A：RCTA（Root-Cause Trajectory Attribution）是一種免訓練方法，首先對長軌跡進行分段並產生片段摘要，藉此召回少數候選錯誤步驟；接著針對每個候選步驟，向前追溯較早的交接指令（handoff instructions），找出可能已經包含相同錯誤的原始指令。這樣的設計把「在長軌跡中廣泛搜尋」與「在原始日誌文字中聚焦比對」拆成兩個階段。由於不需要額外訓練，RCTA 可以直接套用現成的骨幹語言模型，並與基線在相同條件下公平比較。

**Q5：RCTA 的關鍵創新在哪裡？**
A：RCTA 的關鍵在於結合「片段層級的候選召回」與「向交接指令的反向追溯」，前者解決長軌跡資訊過載的問題，後者則能鎖定錯誤最早被引入的決定性時刻，而非僅止於後續的傳播步驟。它直接利用原始軌跡中記錄的角色名稱與交接內容，因此能夠同時支援負責角色歸因與根因步驟定位。相較於只關注最終錯誤或簡單分類的方法，RCTA 更貼近多智慧體工作流程中「計畫→執行」的錯誤傳遞結構。

**Q6：為什麼要採用「片段摘要」與「交接指令」這樣的設計選擇？**
A：片段摘要能將數百步的長軌跡壓縮成可管理的語義單元，讓模型快速定位可能出錯的區間，而不必一次性處理全部原始紀錄。交接指令則通常承載了角色之間的任務移交、規劃決策與限制條件，是錯誤從一個角色傳遞到另一個角色的關鍵節點。透過把候選錯誤追溯到更早的交接指令，RCTA 能夠找出錯誤的真正源頭，而不是把下游執行或驗證步驟誤判為根因。

**【Experiments & Results】**

**Q7：LongRCA Bench 包含哪些領域與資料來源？**
A：LongRCA Bench 涵蓋 SWE-bench Pro、Terminal-Bench 2、TravelPlanner、VitaBench 與 WebArena Verified 五個智慧體領域，橫跨軟體工程、終端機操作、旅遊規劃、多模態任務與網頁互動。資料集共收錄 1,140 條自然發生、非注入式的失敗軌跡，總記錄步驟數達 178,137 步。平均軌跡長度為 156.3 步，中位數為 145 步，最長甚至達到 728 步，遠超過多數現有失敗歸因基準的規模。

**Q8：RCTA 在 LongRCA Bench 上的主要實驗結果為何？**
A：在相同骨幹模型、相同基準實例與相同評分協定下，RCTA 達到 51.1% 的負責角色準確率、24.1% 的精確根因步驟準確率，以及 37.4% 的根因步驟 ±5 範圍準確率。這些數字分別比最強基線高出 23.6、10.9 與 12.7 個百分點，顯示 RCTA 在角色歸因與根因定位上都有顯著優勢。即便如此，精確根因步驟準確率仍不到四分之一，說明長程失敗診斷仍是極具挑戰性的問題。

**Q9：實驗如何確保 RCTA 的改進來自方法設計而非模型或資料差異？**
A：作者使用相同的骨幹語言模型、相同的 1,140 條軌跡，以及相同的評分協定來比較 RCTA 與五個免訓練基線，從而隔離方法本身帶來的效益。所有方法都面對同樣的長軌跡、同樣的人工標註與同樣的獨立評分標準，因此性能差異可歸因於候選召回與交接指令追溯等設計選擇。這樣的控制也凸顯了「片段層級分析」與「反向追溯」對於提升負責角色與根因步驟準確率的重要性。

**【Applications & Impact】**

**Q10：LongRCA Bench 與 RCTA 在實務上可以應用在哪些場景？**
A：這套基準與方法可應用於自動化軟體工程智慧體、旅遊訂票助理、網頁操作智慧體等長程任務的除錯流程，當系統執行失敗時，開發者不再需要從頭檢視數百步紀錄。RCTA 能自動指出應該負責的角色以及最早引入錯誤的步驟，協助團隊快速定位問題所在。對於需要持續監控與維運的智慧體產品，這樣的診斷能力可以大幅縮短除錯時間並降低人工審查成本。

**Q11：若要把 RCTA 落地到產品中，需要考慮哪些因素？**
A：首先必須處理長上下文帶來的推理成本與延遲，RCTA 的片段摘要機制有助於降低一次性讀取全部軌跡的負擔。其次，產品介面應該向使用者展示根因步驟與負責角色的判斷依據，例如候選步驟與對應交接指令的對照，讓人類工程師能夠快速驗證與採信。最後，由於不同領域的日誌格式與角色命名各異，系統需要具備跨領域的日誌解析與角色名稱對齊能力，才能穩定運作。

**Q12：這篇研究對智慧體領域可能帶來什麼影響？**
A：LongRCA Bench 首次系統性地將「負責角色歸因」與「精確根因步驟定位」確立為長程失敗診斷的兩個獨立目標，推動學界與業界不再只滿足於結果層級的成敗判斷。它強調自然發生、非注入式長軌跡的重要性，讓診斷研究更貼近真實部署情境。長遠來看，這有助於開發更可靠的智慧體，因為開發者可以針對真正該負責的角色與最早出錯的步驟進行針對性修正，而非僅根據最終失敗結果盲目調整。

**【Limitations & Future】**

**Q13：這項研究有哪些可以預見的限制？**
A：儘管 RCTA 優於現有基線，其精確根因步驟準確率仍僅有 24.1%，顯示問題本身非常困難，尚有大量改進空間。此外，RCTA 依賴片段摘要的品質與交接指令的偵測，若軌跡中缺乏明確的交接結構，或錯誤並未透過指令傳遞，方法可能無法正確追溯。人工標註由 22 位資訊工程研究生完成，雖然經過審查，但仍可能受主觀判斷影響，且大規模標註的成本相當高昂。

**Q14：RCTA 可能在什麼樣的案例中失敗？**
A：當錯誤並非來自於可被追溯的交接指令，而是隱藏在執行過程中的細微狀態變化時，RCTA 可能無法正確定位最早根因。如果片段摘要遺漏了關鍵語境，候選召回階段就可能漏掉真正的錯誤步驟，導致後續追溯方向錯誤。此外，當多個角色之間的責任界線模糊，或某個錯誤經過多次轉折才顯現時，負責角色歸因的準確率也可能下降。

**Q15：未來可以朝哪些方向繼續發展？**
A：未來可以探索基於微調或專門訓練的模型，以進一步提升長程軌跡的理解與根因定位能力；也可以引入更明確的因果推理機制，讓模型不僅比對文字相似度，還能判斷步驟之間的因果影響。另一個方向是將離線診斷擴展到線上診斷與互動式除錯，讓智慧體在執行過程中就能即時偵測並修正錯誤。最後，發展更低成本、更高一致性的標註流程，並涵蓋更多領域與更長的軌跡，將有助於推動這個研究方向持續進步。

## 實務應用指南

### 適用場景

1. **多智慧體軟體工程除錯**：當程式修復智慧體（如 SWE-bench Pro 類系統）在數十到數百個步驟後回報失敗，開發團隊需要判斷是「診斷智慧體」規劃錯誤，還是「執行智慧體」實作錯誤，並定位最早引入決定性錯誤的步驟。
2. **長程旅遊與預訂規劃代理診斷**：在 TravelPlanner 這類需要多輪搜尋、預訂、驗證的領域，用於追溯最終行程不符合需求時，是哪一個規劃或驗證角色最先違反限制條件。
3. **網頁自動化任務失敗分析**：針對 WebArena Verified 等長期網頁操作軌跡，協助判斷最終頁面狀態錯誤是源自早期導航決策、表單填寫，還是後續確認步驟的誤判。
4. **終端命令序列除錯**：在 Terminal-Bench 等長命令執行場景中，用於從大量 shell 輸出裡找出最早導致最終結果錯誤的命令或參數設定步驟。
5. **研究報告與多步驟內容生成品管**：在 VitaBench 等需要資料檢索、摘要、撰寫、驗證的長流程中，用於定位哪一個角色最先引入事實錯誤或結構偏差。

### 實作前置條件

- **資料條件**：必須能取得完整的軌跡日誌，包含步驟索引、步驟名稱、訊息角色與內容；同時需要結果層級評估器的輸出，以確認哪些軌跡確實失敗。角色名稱必須在原始軌跡中有明確記錄，否則無法產生有效的負責角色標籤。
- **運算條件**：需要可呼叫的大型語言模型 API 或本地骨幹模型，用於產生片段摘要、檢索候選錯誤步驟，以及執行向較早交接指令的追溯。由於軌跡長度可達數百步，必須確認模型上下文視窗與 API 配額足以處理分段摘要與多次檢索。
- **技能條件**：團隊需具備智慧體追蹤（agent tracing）經驗、提示工程能力、以及評估指標設計能力。若需建立人工標註，則需要熟悉工作流程角色定義的領域專家，並能區分「錯誤發出者」與「負責角色」。

### 實作步驟建議

1. **建立軌跡收集與標準化管線**：將不同來源的軌跡統一為相同格式，確保每筆記錄都包含步驟索引、名稱、訊息角色與內容，並與結果層級評估器輸出對齊。
2. **定義角色名稱與交接指令格式**：列出所有可能的工作流程角色，並識別角色間移交任務時產生的交接指令，這些指令是 RCTA 追溯的關鍵錨點。
3. **實作片段摘要生成**：將長軌跡切成可管理的片段，利用骨幹模型產生片段摘要，保留與失敗相關的決策、工具呼叫與驗證結果。
4. **實作候選錯誤步驟檢索**：根據片段摘要與最終失敗訊息，召回少量候選錯誤步驟，避免直接對數百步進行窮舉比對。
5. **實作向較早交接指令追溯**：對每個候選錯誤步驟，回溯檢查是否有更早的交接指令已包含相同錯誤，以找到最早決定性根本原因步驟。
6. **分別預測負責角色與根因步驟**：角色與步驟應作為獨立預測目標處理，角色標籤必須對應原始軌跡中的角色名稱，而非直接從選定步驟的發出者推導。
7. **建立人工驗證與持續迭代迴路**：先以抽樣方式驗證 RCTA 預測與人工標註的一致性，再逐步擴大覆蓋率，並根據錯誤案例調整摘要策略與檢索提示。

### 潛在風險與注意事項

- **誤將最終失敗步驟當成根因**：長程軌跡中，最終回報失敗的步驟往往只是錯誤暴露點，真正的根因可能早數十步甚至數百步。方法必須能抵抗「靠近結尾」的偏差。
- **角色標籤與原始軌跡不一致**：負責角色必須是原始軌跡中實際記錄的角色名稱，不能自行發明新角色名稱，也不能假設步驟發出者即為負責角色。
- **忽略錯誤已被修復的情況**：若某個早期錯誤在後續步驟中被成功修復，則不應選為根因。評估時必須確認該錯誤與經評估器確認的最終失敗之間存在因果關聯。
- **長軌跡上下文限制**：直接將整條軌跡餵入模型可能超出上下文視窗，需透過片段摘要或分層摘要處理，但摘要過程可能遺漏關鍵細節。
- **摘要遺漏交接細節**：片段摘要若過度簡化，可能遺失角色間交接指令的具體內容，導致追溯失敗。建議在摘要中特別保留 handoff 相關文字。

### 與其他技術的整合建議

- **與可觀測性平台整合**：將 LongRCA Bench 的診斷流程嵌入 LangSmith、Langfuse 或 OpenTelemetry 等追蹤系統，讓開發者在既有儀表板中直接檢視負責角色與根因步驟。
- **與 CI/CD 管線整合**：在自動化測試失敗時觸發 RCTA，將根因步驟與角色歸因結果寫入 Pull Request 評論或議題追蹤系統，加速除錯迴路。
- **與檢索增強生成（RAG）整合**：將歷史失敗軌跡、根因步驟與修復方式建立索引，供後續智慧體在規劃階段查詢相似案例，降低重複犯錯機率。
- **與微調管線整合**：利用 RCTA 產生的角色與根因標註作為訓練資料，微調專屬的失敗歸因模型，進一步提升精確根因步驟準確率。
- **與告警系統整合**：針對高頻出現的負責角色或根因類型設定閾值告警，驅動智慧體工作流程的重構優先順序。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從圖一的 SWE-bench Pro 案例開始，理解「最終失敗步驟不等於根因步驟」這個核心概念，再對照詞彙表熟悉軌跡、角色、交接指令等術語，最後閱讀 RCTA 的兩階段流程（片段摘要召回候選步驟，再向較早交接指令追溯），不必急著深入各領域基準細節。

- **AI 工程師**：請重點關注 RCTA 的實作設計，包括如何切分長軌跡、設計片段摘要提示、建立候選錯誤步驟檢索機制，以及如何避免將角色預測與步驟預測混為一談；同時參考論文中的基線比較與評分協定，以便在自己的 agent 系統中複現與改良。

- **研究人員**：建議深入分析 LongRCA Bench 的三個測量維度——來源多樣性、軌跡長度與根因到結尾距離——並思考現有方法在長距離依賴與多角色責任歸因上的理論限制；可進一步探索如何將 RCTA 與微調、強化學習或因果推論方法結合，以提升精確根因步驟準確率。

- **產品經理**：請聚焦於「結果層級評估無法定位錯誤」這個診斷缺口，以及負責角色歸因與根因步驟定位作為獨立產品指標的價值；評估導入 RCTA 時，應優先盤點團隊是否已具備完整軌跡日誌、明確角色定義與可觀測性基礎建設，再規劃與現有除錯流程的整合順序。
