## 摘要翻譯

選擇題問答（Multiple-choice QA, MCQA）基準測試通常將小型語言模型（Small Language Models, SLMs）視為直接作答者來評估，但已部署的語言模型系統日益依賴外部鷹架（scaffolds），例如工具、程式碼與重複的模型呼叫。我們提出程式碼引導推理（Code-Guided Reasoning, CGR），一項評估協定（evaluation protocol）與生成程式資源（generated-program resource），用於衡量可執行推理鷹架（executable reasoning scaffolds）在何種情境下可提升小型語言模型（SLMs）於選擇題問答（MCQA）任務上的表現。CGR 標準化了六項組件：標準化項目介面（normalized item interface）、直接求解提示（direct solver prompt）、生成器提示（generator prompt）、Python 鷹架（Python scaffold）、求解器呼叫（solver-call）與擷取輔助程式（extraction helpers），以及三通道結果記錄（three-channel result record）。在基於本地準備的 MCQA 題組（MCQA bundle）與六個詮釋資料註冊求解模型（metadata-registered solver models）所得到的 20,498 筆保留結果列（retained result rows）中，所觀察到的非零基準分區（non-zero-baseline partition）顯示宏觀輔助準確率（macro assisted accuracy）為 66.21%，相較於直接準確率（direct accuracy）38.11%，差距為 +28.10 個百分點，配對自助法區間（pair-bootstrap interval）為 [20.32, 36.43]。在更嚴格的 Ab > 30% 直接訊號閘門（Ab > 30% direct-signal gate）條件下，宏觀差距為 +14.11 個百分點。這些估計值為描述性估計（descriptive estimates）。輔助推論（assisted inference）使用更大的求解器呼叫預算（solver-call budget），答案擷取（answer extraction）機制較為脆弱，Time-MQA（資料集）出現所觀察到的效能衰退（regressions），且部分生成程式（generated programs）違反禁止硬編碼指令（no-hard-coding instruction）。CGR 提供解讀這些結果所需的追蹤套件（trace package），包含直接答案（direct answers）、輔助答案（assisted answers）與生成器端答案（generator-side answers）、分區定義（partition definitions）、生成程式（generated programs）、回應詮釋資料（response metadata）以及稽核資料（audits）。

### 核心貢獻（3～5點）
- 提出程式碼引導推理（CGR）評估協定與生成程式資源，標準化六項組件，建立系統性衡量可執行推理鷹架對小型語言模型於選擇題問答任務助益的架構。
- 基於 20,498 筆保留結果列的實證顯示，在非零基準分區中，宏觀輔助準確率（66.21%）較直接準確率（38.11%）提升達 +28.10 個百分點；即使在更嚴格的 Ab > 30% 直接訊號閘門條件下，仍有 +14.11 個百分點的穩定增益。
- 提供完整的追蹤套件，涵蓋直接答案、輔助答案、生成器端答案、分區定義、生成程式、回應詮釋資料與稽核資料，確保實驗結果具備可解讀性與可驗證性。
- 明確揭露方法限制與失效模式：輔助推論需較高的求解器呼叫預算、答案擷取機制具脆弱性、Time-MQA 資料集出現效能衰退，且部分生成程式違反禁止硬編碼指令。

### 適合對象
本論文適合研究語言模型推理與工具使用的學者、致力於提升小型語言模型（SLM）實務效能的系統工程師與部署者，以及從事選擇題問答（MCQA）基準測試、評估協定設計與程式輔助推理（program-aided reasoning）相關研究的開發人員閱讀。對於關注如何透過外部鷹架與可執行程式碼彌補小型模型推理能力缺口，同時重視評估透明度與結果可稽核性的讀者，尤具參考價值。

## 深度分析

#### 方法論解析

本文提出之程式碼引導推理（Code-Guided Reasoning, CGR）並非一種模型架構主張，而是一套評估協定（evaluation protocol）與生成程式資源（generated-program resource），旨在標準化測量「可執行推理鷹架（executable reasoning scaffolds）」對小型語言模型（Small Language Models, SLM）於選擇題問答（Multiple-choice QA, MCQA）任務上之影響。其核心設計可拆解為六大標準化組件：標準化項目介面（normalized item interface）、直接求解提示（direct solver prompt）、生成器提示（generator prompt）、Python 鷹架（Python scaffold）、求解器呼叫與擷取輔助程式（solver-call and extraction helpers），以及三通道結果記錄（three-channel result record）。

在傳統評估中，求解器（solver）僅作為直接答案者（direct answerer），透過裸答案提示（bare answer prompt）輸出單一選項字母（option letter）。CGR 則引入「介面轉移（interface shift）」：針對每一道 MCQA 項目（item），由生成器（generator）產出一份項目專屬 Python（item-specific Python），該程式具備固定回傳合約（fixed return contract），可作為控制器（controller）進行變數儲存、條件分支、多次求解器呼叫（solver-call）、答案格式修復（answer-format repair），乃至啟動平手決勝機制（tiebreaker）。此 Python 鷹架（Python scaffold）並非單純卸載計算，而是將目標求解器（target solver）嵌入可執行動作空間（executable action space）中，使其在受控的控制流程（control flow）與可檢查狀態（inspectable state）下作答。

方法論上最關鍵的結構為「雙模型分離」：生成器（generator）負責撰寫領域分解（domain decomposition）邏輯，而目標求解器（target solver）仍為實際受評估之模型。為了區分鷹架帶來的增益來源，CGR 建立三通道結果記錄（three-channel result record），分別記錄：(1) 直接答案（direct answers）——求解器在無鷹架下之原始輸出；(2) 輔助答案（assisted answers）——求解器透過生成鷹架輔助後之最終輸出；(3) 生成器端答案（generator-side answers）——鷹架內部由生成器邏輯選定之答案。此設計使研究者得以區辨效能提升究竟來自有效分解（useful decomposition）、額外呼叫（extra calls）、格式修復，抑或生成器端知識（generator-side knowledge）之洩漏。

在效度選擇（validity choice）上，作者刻意採用非零基準分區（non-zero-baseline partition）作為主要比較對象：僅保留「資料集–模型配對（dataset–model pairs）」中至少有一筆直接正確答案之樣本。此舉旨在排除求解器完全無法理解題目或提示格式失敗（prompt-format failure）之極端案例，避免輔助準確率（assisted accuracy）之解釋過度膨脹。零基準列（zero-baseline rows）則僅作為診斷用途，而非部署證據（deployment evidence）。

#### 實驗數據解讀

實驗基於本地準備之 MCQA 題組（MCQA bundle），涵蓋九種資料集配置（dataset configurations），包含 MMLU-Pro、OpenBookQA、SuperGPQA、Time-MQA、MedQA、PhysicsQA 與 AIME 等，並註冊六個詮釋資料註冊求解模型（metadata-registered solver models）。在過濾與正規化後，共保留 20,498 筆保留結果列（retained result rows）進行分析。

核心結果顯示，於非零基準分區（non-zero-baseline partition）中，宏觀輔助準確率（macro assisted accuracy）達 66.21%，相較於直接準確率（direct accuracy）之 38.11%，提升達 +28.10 百分點（percentage-point）。配對自助法區間（pair-bootstrap interval）為 [20.32, 36.43]，顯示鷹架輔助確實帶來統計上顯著且穩定之增益，但區間寬度亦暗示不同資料集–模型配對（dataset–model pairs）間存在相當大之異質性。當進一步以 Ab > 30% 直接訊號閘門（Ab > 30% direct-signal gate）進行更嚴格篩選時，宏觀差異收斂至 +14.11 百分點。此衰減說明：當求解器本身已具備一定直接訊號強度時，鷹架之邊際貢獻雖仍為正，但幅度明顯縮小。

作者明確將這些估計值定性為描述性估計（descriptive estimates），而非因果推論。這一定性至關重要，因為輔助推論（assisted inference）使用了更大的求解器呼叫預算（solver-call budget），且答案擷取（answer extraction）過程被指出為脆弱（brittle）。換言之，+28.10 百分點之增益並非純粹來自「推理品質提升」，而可能部分歸因於推論程序（inference procedure）中額外呼叫所帶來之自我一致性（self-consistency）效應，或擷取輔助程式對選項擷取不匹配（option-extraction mismatch）之修復。

此外，資料呈現顯著之領域變異：Time-MQA 資料集出現觀察到之效能衰退（regressions），顯示可執行鷹架並非在所有領域皆能穩定增益。稽核（audits）亦發現部分生成程式（generated programs）違反禁止硬編碼指令（no-hard-coding instruction），存在直接將答案硬寫入程式碼之 literal-answer patterns，這使得輔助答案（assisted answers）與生成器端答案（generator-side answers）之通道分離顯得尤為重要——若僅報告單一準確率數字，將無法察覺此類知識洩漏或格式修復之混淆效應。

#### 與現有研究的比較

CGR 之定位介於提示工程（prompting）、程式輔助方法（program-aided methods）與工具使用評估（tool-use evaluation）之間。相較於思維鏈（Chain-of-Thought）或自我一致性（self-consistency）等僅改變推理軌跡或解碼/選擇程序者，CGR 進一步將推論程序（inference procedure）具象化為可執行之 Python 鷹架（Python scaffold），具備控制流程（control flow）與可檢查狀態（inspectable state），而非僅止於固定文字或 JSON 動作。

與程式輔助方法如 Program of Thoughts（PoT）或 PAL 相比，PoT 與 PAL 主要利用生成程式碼將計算卸載至直譯器；CGR 則將程式碼視為「控制器」，可多次呼叫目標求解器（target solver）並聚合答案。此雙模型結構（two-model structure）使研究者得以比較「同一求解器」在直接提示與鷹架化條件（scaffolded condition）下之行為差異，這是單一模型卸載計算所無法達成之對照。

相較於 CodeAct 將可執行程式碼視為動作格式（action format），CGR 更聚焦於評估（evaluation）而非架構創新：它不訓練新模型，也不建立可重複使用模板記憶體（reusable template memory），而是將每次生成之可執行鷹架視為待稽核之評估產物（artifact）。這與推理鷹架方法（如儲存、檢索或縮放思維模板者）形成鮮明對比——後者透過模板記憶體或導航器（navigator）優化推論時間結構，而 CGR 堅持每題重新生成鷹架，以確保評估記錄（evaluation record）包含外部呼叫（external calls）、執行規則（execution rules）與失效模式（failure modes）之完整軌跡。

在工具使用與互動式程式碼基準測試（interactive-code benchmarks）方面，CGR 繼承了「觀察到的語言模型效能取決於外部操作」之核心關懷，但將其具體應用於 MCQA 鷹架。本文之主要限制（limitations）亦在此脈絡下顯現：輔助分數可能反映有效分解，但也可能僅反映脆弱之答案擷取（answer extraction）、額外推論預算，或生成器端知識（generator-side knowledge）之洩漏。作者明確承認這些失效模式（failure modes）並將其納入報告，此作法與 DecodingTrust 將可信度視為稽核套件（audits suite）而非單一分數之精神一致。

然而，CGR 目前仍為評估協定（evaluation protocol）而非部署方案：它尚未解決求解器呼叫預算（solver-call budget）不均衡之問題，亦未提供可重複使用之鷹架模板。對於追求低成本邊緣部署之 SLM 系統而言，輔助推論之成本效益比仍有待進一步分析。

#### 可重現性評估

本研究在可重現性（reproducibility）方面採取部分開放、部分受限之策略。正面而言，作者明確指出 CGR 提供追蹤套件（trace package），內容涵蓋直接答案（direct answers）、輔助答案（assisted answers）、生成器端答案（generator-side answers）、分區定義（partition definitions）、生成程式（generated programs）、回應詮釋資料（response metadata）與稽核資料（audits）。此等詳盡之評估記錄（evaluation record）使其他研究者得以重新檢視結果、追蹤來源出處（source provenance），並驗證非零基準分區（non-zero-baseline partition）之篩選邏輯。資料集之來源與本地正規化處理亦透過來源論文、官方頁面或作者準備之子集等方式記錄於詮釋資料中。

然而，就開放科學之嚴格標準而言，本文並未明確提及公開之原始碼儲存庫、CGR 框架之開源釋出，或模型權重（model weights）之取得途徑。MCQA 題組（MCQA bundle）描述為「本地準備（locally prepared）」，暗示部分資料前處理流程可能依賴特定執行環境。雖然生成程式（generated programs）與回應詮釋資料（response metadata）已納入追蹤套件，但若缺乏可公開取得之評估協定實作程式碼與標準化項目介面（normalized item interface）之開源版本，外部研究者仍難以完全複製從資料準備、生成器提示（generator prompt）建構到求解器呼叫（solver-call）執行之完整管線。

此外，由於實驗涉及六個不同之詮釋資料註冊求解模型（metadata-registered solver models），若這些模型包含專有或經微調之權重，而論文未提供其確切版本標籤或下載連結，則可重現性將進一步受限。總體而言，本研究在「結果可稽核性（auditability）」上表現優異，但在「端到端系統可複製性」上仍留有強化空間，未來若能釋出完整之 Python 鷹架（Python scaffold）執行環境與資料載入器，將大幅提升社群之跟進能力。

#### 未來研究方向

基於 CGR 之現有框架與已揭露之限制，未來研究可沿以下數個方向展開：

第一，**因果推論方法之引入**。當前估計值均為描述性估計（descriptive estimates），未控制求解器呼叫預算（solver-call budget）與提示長度等混淆因子。未來可設計固定預算之對照實驗，或引入因果推論技術以區辨「有效分解（useful decomposition）」與「額外呼叫（extra calls）」各自之邊際貢獻，從而建立更具部署證據（deployment evidence）效力之結論。

第二，**擷取機制之強化與標準化**。答案擷取（answer extraction）之脆弱性（brittle）已被確認為主要失效模式（failure mode）之一。後續研究可開發更穩健之擷取輔助程式（extraction helpers），或結合結構化生成（structured generation）技術，降低選項擷取不匹配（option-extraction mismatch）與 literal-answer patterns 之發生率。

第三，**負向案例與領域特異性分析**。Time-MQA 資料集觀察到之效能衰退（regressions）顯示，可執行鷹架對時間序列分析類題目可能反而不利。未來需深入探討何種領域特性（如需要全局脈絡理解而非逐步分解）會導致鷹架化條件（scaffolded condition）失效，並建立預測模型以判斷何時應啟用或停用鷹架。

第四，**從評估協定走向可重複使用鷹架**。CGR 目前堅持每題生成新鷹架，雖確保了稽核透明度，但缺乏可重複使用模板記憶體（reusable template memory）。未來可探索在保留可檢查狀態（inspectable state）之前提下，學習跨題目之領域分解（domain decomposition）模板，或訓練導航器（navigator）以優化鷹架軌跡，在評估嚴謹性與推論效率間取得平衡。

第五，**成本–延遲–準確率權衡分析**。對於邊緣部署之小型語言模型（SLM）而言，輔助推論之延遲與呼叫成本是實務關鍵。未來研究應量化 Python 鷹架（Python scaffold）之執行開銷，並建立帕累托前沿（Pareto frontier）分析，協助決策者在直接推論、輕量鷹架與完整可執行鷹架間做出權衡選擇。

第六，**擴展至開放式問答與多模態場景**。CGR 目前侷限於選擇題問答（MCQA）。將可執行推理鷹架之評估邏輯擴展至開放式問答（open-ended QA）、數學證明生成，或結合視覺輸入之多模態推理，將是極具價值之延伸。

## 論文問答

**Q1：CGR 旨在解決什麼核心問題？**
A：CGR 試圖彌補傳統基準測試與實際部署情境之間的落差，因為現有的選擇題問答（MCQA）基準通常將小型語言模型（SLM）視為單次直接作答者，卻忽略了真實系統往往依賴外部鷹架進行推理。在實務上，部署環境中的控制器會將問題拆解、多次呼叫模型並執行小型運算，因此單純的直接準確率無法衡量這種鷹架化條件下的真實表現。透過程式碼引導推理（CGR），研究者得以系統性地評估可執行推理鷹架對 SLM 的影響，並提供可稽核的證據。

**Q2：為何傳統的直接作答 MCQA 基準無法充分衡量 SLM 能力？**
A：傳統基準假設模型僅透過單一自然語言提示直接輸出選項字母，這種裸答案提示的設計無法反映生產系統中常見的控制流程與狀態檢查。它們未能捕捉同一個目標求解器在嵌入可執行動作空間後，其行為可能因變數儲存、分支與多次求解器呼叫而產生的介面轉移。結果是，這些基準遺漏了現代語言模型系統的核心運作模式，導致評估結果與實際部署效能脫節。

**Q3：為何針對 SLM 研究可執行推理鷹架特別重要？**
A：SLM 常因成本效益、本地部署可行性與低延遲需求而被選用，這使得它們特別適合透過外部鷹架來增強能力的輔助性工作流程。研究可執行鷹架能幫助我們理解，當程式碼生成器與領域語言推理器協作時，小型模型在何種情況下能獲得顯著增益。這種輔助性區分至關重要，因為實務上有價值的目標往往是與領域專家協作，而非單純以模型規模取代人類判斷。

**Q4：CGR 的核心方法論是什麼？**
A：CGR 是一種標準化的評估協定，它在每一道 MCQA 題目與目標求解器之間插入一個由生成器產出的 Python 鷹架。此鷹架可儲存變數、執行控制流程、呼叫求解器輔助程式、擷取選項字母並啟用平手決勝機制，且必須遵守固定的回傳合約。協定同時建立三通道結果記錄，分別記錄直接答案、輔助答案與生成器端答案，從而嚴謹比較同一模型在直接提示與鷹架輔助下的行為差異。

**Q5：CGR 相較於先前程式輔助方法的主要創新為何？**
A：過往的程式輔助方法多將生成程式視為卸載計算任務給直譯器的工具，而 CGR 則將其視為可稽核的控制器，用於包裝並協調同一個正被評估的目標求解器。這種雙模型結構讓研究者能在固定的資料集–模型配對上，精確比較求解器直接作答與置身於生成領域鷹架內的表現差異。此外，CGR 不維護可重複使用模板記憶體，也不訓練導航模型，而是將每次新鮮生成的可執行鷹架視為評估標的，並保留完整的執行痕跡以供檢視。

**Q6：CGR 在效度與記錄設計上有哪些關鍵選擇？**
A：為確保結果可解釋，CGR 採用非零基準分區作為主要比較範圍，僅納入至少有一筆直接正確答案的資料集–模型配對，避免將提示格式失敗或選項擷取不匹配誤判為鷹架效益。協定標準化六大組件，包括標準化項目介面、直接求解提示、生成器提示、Python 鷹架、求解器呼叫與擷取輔助程式，以及三通道結果記錄。這些設計確保每一次輔助推論的過程、回應詮釋資料與稽核資料都被完整保存，使評估具備可重現性與透明度。

**Q7：CGR 實驗使用了哪些資料集與模型？**
A：實驗採用本地準備的標準化 MCQA 題組，涵蓋九種配置，包括 MMLU-Pro、OpenBookQA、SuperGPQA、Time-MQA、MedQA、PhysicsQA 與 AIME 等橫跨基礎科學到研究生程度及醫學領域的資料集。評估使用了六個詮釋資料註冊求解模型作為目標 SLM，並由生成器模型產出項目專屬 Python。最終分析保留了 20,498 筆保留結果列，且每個配置的來源出處與證據鏈均在追蹤套件中明確記載。

**Q8：關於可執行鷹架對 SLM 準確率的影響，有哪些關鍵量化發現？**
A：在非零基準分區中，宏觀輔助準確率達到 66.21%，相較於 38.11% 的直接準確率提升了 28.10 個百分點，配對自助法區間為 [20.32, 36.43]。即使在更嚴格的 Ab > 30% 直接訊號閘門下，宏觀差異仍維持在 +14.11 個百分點。這些描述性估計顯示，可執行推理鷹架確實能顯著改變求解器的表現，但增益幅度深受篩選條件與資料集領域特性所影響。

**Q9：稽核與更嚴格的分區條件揭示了輔助準確率增益的哪些穩健性特徵？**
A：稽核資料顯示，輔助答案的改善部分來自更大的求解器呼叫預算、答案格式修復，或是生成器端知識的注入，而非純粹來自有效的領域分解。當套用 Ab > 30% 直接訊號閘門時，增益縮減至 14.11 個百分點，說明原始改善中有相當比例集中在直接求解器僅具微弱訊號的案例。此外，Time-MQA 資料集出現了效能衰退，且部分生成程式違反禁止硬編碼指令，顯示鷹架品質與資料集特性嚴格限制了結論的外推範圍。

**Q10：CGR 的評估設定在哪些實務部署情境中最具相關性？**
A：CGR 特別適用於邊緣或本地部署場景，這些環境因延遲、隱私或成本限制而無法使用大型遠端模型，必須仰賴小型語言模型處理複雜選擇題推理。它直接對應生產系統中常見的控制器邏輯：將問題拆解、執行中介運算，並彙整多次模型呼叫後才輸出最終選項。透過測量輕量求解器在生成程式碼鷹架包裝後的表現提升，實務工作者得以判斷是否應投資於推論時間的鷹架基礎建設，而非僅僅擴大模型規模。

**Q11：從 CGR 框架出發，建構以 SLM 為核心的系統時應考量哪些產品層面因素？**
A：產品團隊必須仔細權衡推論成本與準確率之間的取捨，因為輔助推論允許的求解器呼叫預算顯著高於直接提示。框架同時凸顯答案擷取過程的脆弱性，意味著穩健的擷取輔助程式與平手決勝機制是產品化不可或缺的元件，而非事後補強的附帶功能。此外，由於部分生成程式可能硬編碼答案或洩漏生成器端知識，產品在部署前需要執行階段的稽核與沙盒機制，以確保鷹架行為符合預期且具備可解釋性。

**Q12：CGR 可能如何影響語言模型評估與工具使用研究的更廣泛領域？**
A：CGR 將可執行 MCQA 鷹架確立為一種正式的評估情境，促使學界從單純追求總體準確率轉向重視可檢視的成品級痕跡。它強化了推論程序——包括外部呼叫、執行規則與失效模式——必須成為評估記錄一部分的核心原則。透過提供包含生成程式、回應詮釋資料與稽核資料的追蹤套件，CGR 為工具使用、互動式程式碼與輔助推理領域的未來基準測試樹立了透明化的標竿。

**Q13：作者明確承認 CGR 估計值存在哪些主要限制？**
A：作者強調這些估計值屬於描述性質，而非因果推論，因此無法確立鷹架本身獨立於求解器呼叫預算增加等混淆因子之外的純粹因果效應。他們指出輔助推論使用了更大的求解器呼叫預算，這使得準確率增益難以被單純解讀為推理能力的提升。此外，答案擷取仍顯脆弱，且評估設計尚無法完全區分有效分解、格式修復與生成器端知識注入這三種不同的增益來源。

**Q14：CGR 實驗中識別出哪些具體的失效案例與效能衰退？**
A：Time-MQA 資料集出現了明顯的效能衰退，顯示時間序列分析類型的選擇題問答可能難以透過生成 Python 的領域分解策略獲益。部分生成程式違反了禁止硬編碼指令，實質上繞過了目標求解器而非真正輔助它進行推理。同時，答案擷取的不穩定導致選項擷取不匹配，作者也記錄到答案通道非巢狀結構與字面答案模式等現象，這些都限制了輔助通道的可靠性。

**Q15：CGR 框架為可執行鷹架與 SLM 評估的未來研究指出了哪些方向？**
A：未來研究可探索調適性求解器呼叫預算，以找出在控制推論成本的前提下，仍能維持可靠分解所需的最少呼叫次數。提升答案擷取的穩健性，並透過自動化驗證強制執行更嚴格的鷹架合約，有助於減少脆弱失效與硬編碼違規。此外，將 CGR 擴展至 MCQA 以外的任務格式，或針對特定領域訓練專門的生成器模型以優化鷹架品質，將能進一步釐清可執行推理鷹架在何種條件下能真正增強小型模型的能力。

## 實務應用指南

### 適用場景

1. **地端醫療問答系統的選型與臨床驗證**  
   在需保護病歷隱私的場景中，機構常部署小型語言模型（SLM）處理 MedQA 類醫療選擇題。透過 CGR 評估協定，可比較模型在「直接求解提示」與「可執行推理鷹架」下的表現差異，並以三通道結果記錄（直接答案、輔助答案、生成器端答案）提供醫師可稽核的決策軌跡。

2. **教育科技的即時解題與逐步輔導**  
   針對 AIME 或 PhysicsQA 類需要多步驟推理的理科題目，可由程式碼生成器撰寫項目專屬 Python，將題目進行領域分解後多次呼叫目標求解器。CGR 能具體量測這種鷹架化條件是否顯著提升準確率，或僅是答案格式修復與額外呼叫帶來的假象。

3. **企業內部專業知識測驗與合規稽核**  
   對於 MMLU-Pro 或 SuperGPQA 類高難度內部題組，人資或法遵單位可利用 CGR 建立標準化評估流程，判斷導入程式輔助方法後，地端 SLM 是否達到可接受的宏觀輔助準確率，並以追蹤套件留存生成程式與回應詮釋資料供日後查驗。

4. **時序資料分析問答的效能瓶頸診斷**  
   Time-MQA 類任務在本文中觀察到效能衰退，顯示鷹架並非萬靈丹。實務上可運用 CGR 的非零基準分區與零基準列診斷，定位衰退來自領域分解不當、選項擷取不匹配，或求解器呼叫預算配置錯誤，避免盲目上線。

5. **低預算客服路由與複雜分類決策**  
   當延遲或成本限制無法使用大型遠端模型時，可用 CGR 評估是否透過生成 Python 鷹架（含控制流程與平手決勝機制）讓 SLM 以結構化多次呼叫完成意圖分類，並明確記錄介面轉移帶來的準確率變化與呼叫開銷。

### 實作前置條件

**資料準備**
- 標準化 MCQA 題組：每題需包含統一欄位（item_id、question text、option list、option ids、correctness flags），並與來源論文或官方頁面保持來源出處對應。
- 直接基準線：目標求解器在直接求解提示下的完整直接答案與正確率，作為劃分非零基準分區與零基準列的依據。
- 生成器模型存取權限：需能產出項目專屬 Python 的程式碼生成器（可為較大模型或 API）。

**運算資源**
- 本地或可控推論環境：因需執行生成程式，必須具備隔離的 Python 沙箱與明確執行規則。
- 求解器呼叫預算：輔助推論通常需多次外部呼叫，須預留足夠的推論配額與延遲容忍度。
- 儲存空間：保留三通道結果記錄、生成程式、稽核資料與分區定義所需的追蹤套件空間。

**技術能力**
- 能設計標準化項目介面與固定回傳合約（如函式簽章與回傳格式）。
- 能撰寫 solver-call helper 與擷取輔助程式，處理選項字母提取與異常容錯。
- 具備基礎統計分析能力，能執行或理解配對自助法區間與分區邏輯（如 Ab > 30% 直接訊號閘門）。
- 熟悉 prompt engineering，能設計禁止硬編碼指令並稽核生成程式是否違規。

### 實作步驟建議

**步驟一：標準化題目介面與資料清理**  
將現有 MCQA 資料轉換為 CGR 規範格式，統一選項編碼與正確性標記，並記錄來源出處與轉換選擇，確保後續評估記錄可追溯。

**步驟二：建立直接基準線與分區標記**  
讓目標求解器以裸答案提示直接回答所有題目，記錄直接答案與直接準確率。依據結果標記各資料集–模型配對是否屬於非零基準分區（至少一筆直接正確），零基準列僅作診斷用途。

**步驟三：設計生成器提示與回傳合約**  
撰寫生成器提示，要求產出項目專屬 Python 函式，明確規範固定回傳合約（例如回傳 solver 答案與生成器端答案）、禁止硬編碼指令，並內建領域分解與求解器呼叫的範例。

**步驟四：建置 Python 鷹架與輔助程式**  
開發 solver-call helper（呼叫目標求解器）、extraction helper（從 solver 輸出中擷取選項字母）、平手決勝機制與異常處理，確保鷹架具備可檢查狀態與控制流程。

**步驟五：執行三通道評估**  
對每題執行生成程式，分別記錄：直接答案（無鷹架）、輔助答案（solver 經鷹架後的答案）、生成器端答案（鷹架內部選定的答案）。同步記錄回應詮釋資料與每次求解器呼叫的參數。

**步驟六：分區分析、稽核與風險標記**  
在非零基準分區上計算宏觀輔助準確率與直接準確率的差異，產生描述性估計。稽核生成程式是否違反禁止硬編碼指令、是否存在選項擷取不匹配、是否過度消耗求解器呼叫預算，並標記如 Time-MQA 的領域特異衰退。

**步驟七：輸出追蹤套件與部署決策文件**  
封裝所有生成程式、三通道結果、分區定義、稽核資料與失效模式說明為追蹤套件，供團隊判斷哪些題型適合鷹架化部署，哪些應維持直接提示。

### 潛在風險與注意事項

1. **答案擷取脆弱性**  
   Solver 輸出格式常不一致，導致 extraction helper 失效。建議設計多層次擷取規則（正規表示式、關鍵字回退、語義比對）並記錄擷取失敗率，避免將格式錯誤誤判為推理錯誤。

2. **求解器呼叫預算膨脹**  
   輔助推論可能隱含多次求解器呼叫，顯著增加延遲與成本。實作時應設定明確呼叫上限，並在評估記錄中揭露預算差異，避免將高準確率歸因於策略本身而非資源堆疊。

3. **生成器端知識混淆**  
   輔助答案的提升可能來自生成器端知識（生成器在鷹架中內嵌答案線索），而非目標求解器能力改善。務必分開評分輔助答案與生成器端答案，並比對兩者一致性以識別洩漏。

4. **禁止硬編碼指令違規**  
   生成器可能在項目專屬 Python 中直接寫死正確選項。需建立自動稽核（如靜態程式碼檢查比對選項文字），並將違規列從主要分析排除或標記。

5. **零基準列誤用為部署證據**  
   若 solver 在某資料集上無任何直接正確答案，其輔助分數可能僅反映提示格式失敗或選項擷取不匹配。這些零基準列應僅作診斷，不可作為上線依據。

6. **領域特異效能衰退**  
   如 Time-MQA 顯示，鷹架在某些領域可能適得其反。建議按資料集或題型細分報告，勿僅呈現整體 macro 差異，以免掩蓋關鍵衰退訊號。

### 與其他技術的整合建議

1. **與 CodeAct / 程式化代理框架整合**  
   將 CGR 的 Python 鷹架視為可執行動作空間中的一種動作，納入既有代理的控制流程。利用 CGR 的標準化項目介面與固定回傳合約，統一代理的狀態檢查與日誌格式。

2. **與 Chain-of-Thought / Self-Consistency 整合**  
   在 solver-call helper 中要求目標求解器輸出推理鏈（chain-of-thought），再透過 extraction helper 擷取最終選項字母；或讓鷹架多次採樣 solver 答案進行自一致性投票，將額外呼叫轉化為結構化推理程序。

3. **與 MLOps / CI-CD 評估管線整合**  
   將 CGR 追蹤套件納入持續整合流程，作為 SLM 版本升級、提示變更或資料集擴充時的回歸測試基準。利用三通道結果快速偵測直接準確率或輔助準確率的異常波動。

4. **與工具使用（Tool-use）系統整合**  
   若 solver 需呼叫計算機、檢索器或資料庫，可將這些工具 API 注入鷹架的命名空間，但必須在評估記錄中明確標註外部呼叫與執行規則，確保失效模式可被稽核。

5. **與前端專家協作介面整合**  
   將三通道結果（直接、輔助、生成器端）視覺化呈現給領域專家（如醫師、教師、法遵人員），支援協作式審查。這呼應醫療大型語言模型的輔助性區分：重點是與專家協作，而非完全取代人類判斷。

---

### 給不同背景讀者的閱讀建議

**初學者**  
請先聚焦「為什麼不能直接問模型答案」。CGR 的核心是將題目包上一層 Python 鷹架，讓小型語言模型透過程式邏輯分段作答。建議從 OpenBookQA 這類相對單純的資料集開始，觀察直接答案與輔助答案的差異，建立對「介面轉移」與「可檢查狀態」的直覺。

**AI 工程師**  
請重點關注六組件的實作細節：標準化項目介面的欄位設計、extraction helpers 的容錯與回退機制、非零基準分區的統計邏輯，以及如何將追蹤套件整合進現有評估管線。特別注意求解器呼叫預算與延遲的權衡，並為生產環境設計嚴格的禁止硬編碼稽核。

**研究人員**  
請關注 CGR 作為評估協定的方法論貢獻：三通道分離如何拆解「有效分解」、「答案格式修復」與「生成器端知識」的混淆；非零基準分區這項效度選擇的合理性；以及為何這些估計僅是描述性而非因果性。可進一步延伸探討生成程式品質的自動評分指標，或不同領域分解策略對 solver 行為的影響。

**產品經理**  
請理解這不是「加上程式碼就變強」的產品功能，而是一套有條件限制的輔助評估框架。關鍵取捨在於：宏觀輔助準確率雖有顯著提升，但伴隨著呼叫成本增加、答案擷取失敗風險，以及 Time-MQA 等特定領域的效能衰退。建議利用本文的追蹤套件與分區數據，與工程團隊共同決定哪些題型適合鷹架化部署、哪些應維持直接提示，並將稽核資料作為上線前的必要檢查清單。
