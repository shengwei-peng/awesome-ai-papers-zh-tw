## ⚡ TL;DR

現有文件抽取基準難以同時評估綱要引導、長記錄完整性、視覺溯源與成本。
本文提出 ExtractBench，涵蓋 370 份文件與 67 種類型，並建立可擴展標註流程。
LlamaExtract Agentic Plus 三項指標居冠，準確率媲美編碼代理且成本更低。

## 摘要翻譯

企業工作流程日益依賴智慧代理（agents）執行綱要引導式抽取（schema-guided extraction）：給定一份文件與使用者定義的綱要（schema），智慧代理忠實遵循綱要，產生正確輸出，並將來源證據（source evidence）作為溯源詮釋資料（grounding metadata）。我們提出 ExtractBench，一個綱要引導式抽取的評測基準；就我們所知，這是首個同時評估數值準確率（value accuracy）、大規模記錄完整性（record completeness）、溯源（grounding）與實測成本（measured cost）的基準。此評測系統包含 4,869 頁，涵蓋 370 份企業文件、8 個業務領域（business domains）與 67 種文件類型（document types），並以明確標籤區分各文件的挑戰情境。可擴展綱要與真實標註建置流程（scalable schema and ground-truth curation pipeline）結合了真實文件的獨立系統一致性（independent-system agreement）、合成清單（synthetic lists）的已知數值，以及表單的人工驗證（human verification）。我們以順序無關數值 F1（order-insensitive value F1）報告數值準確率，並提出兩項用於來源可追溯性的溯源指標：詞級 F1（word-level F1）與頁級 F1（page-level F1）。商業視覺語言模型（Commercial VLMs）在短文件上表現良好，但在長文件上經常截斷記錄清單；編碼代理（coding agents）雖保持較高準確率，成本卻顯著較高。LlamaExtract Agentic Plus 在三項指標上均排名第一，準確率可與編碼代理相當，成本僅為其一小部分。資料集與評估程式碼（evaluation code）已公開於 https://huggingface.co/datasets/llamaindex/ExtractBench{Hugging Face} 與 https://github.com/run-llama/ExtractBench{GitHub}。

### 核心貢獻（3～5點）
- 提出首個同時評估數值準確率、大規模記錄完整性、溯源與實測成本的綱要引導式企業文件抽取基準 ExtractBench。
- 建構大規模評測語料庫，包含 4,869 頁、370 份企業文件、8 個業務領域與 67 種文件類型，並以明確標籤區分各文件的挑戰情境。
- 設計可擴展綱要與真實標註建置流程，結合真實文件的獨立系統一致性、合成清單的已知數值，以及表單的人工驗證。
- 提出多維度評估指標，包括順序無關數值 F1，以及詞級 F1 與頁級 F1 兩項溯源指標。
- 實測比較商業視覺語言模型、編碼代理與 LlamaExtract Agentic Plus，發現 LlamaExtract Agentic Plus 在三項指標上均排名第一，且成本遠低於編碼代理。

### 適合對象
從事文件資訊抽取、企業文件自動化、大型語言模型與視覺語言模型應用，以及需要評估抽取系統之準確率、完整性、溯源能力與運行成本的研究人員與工程師。特別適合關注綱要引導式抽取、真實企業文件挑戰，以及代理系統成本效益分析的讀者。

## 深度分析

#### 方法論解析

ExtractBench 將企業文件抽取重新定義為 **schema-guided extraction（綱要引導式抽取）**：給定一份文件與一份使用者自訂的 **schema（綱要）**，**agents（智慧代理）** 必須忠實遵循綱要產出結構化 JSON，同時為每個數值附上 **source evidence（來源證據）** 作為 **grounding metadata（溯源詮釋資料）**。這個定義比傳統「把欄位填完」更嚴格：輸出必須是 schema-valid JSON、對缺漏欄位正確回傳 null、對重複記錄完整保留、並且能指出每個值在文件中的來源。這樣的設計直接對應企業落地場景——下游 **system of record（記錄系統）** 需要可稽核、可人工複查的結果，而非僅有預測值。

為了讓錯誤可被歸因，作者建立五個獨立的標籤維度：**task challenge（抽取難點）**、**perception challenge（感知挑戰）**、table structure、length 與 **business domain（業務領域）**。task challenge 涵蓋 missing rows（遺漏列）、sparse fact（稀疏事實）、dense forms（密集表單）、相似日期/金額/識別碼等；perception challenge 則包括 scan noise（掃描雜訊）、handwriting（手寫）、hierarchical headers（階層式標題）、cross-page context（跨頁上下文）與不規則大表格。由於軸線彼此獨立，研究者可以把整體分數拆解到特定難點，例如「長文件導致列表截斷」或「掃描手寫降低準確率」，而不會被 aggregate score 掩蓋。

**Benchmark corpus（評測語料庫）** 由三類資料組成：(1) 真實 born-digital 文件；(2) 基於真實版面渲染的 **synthetic lists（合成清單）**，用於控制長記錄完整性；(3) 真實監管與稅務表單，其 schema 從空白模板設計。總計 370 份文件、4,869 頁、8 個業務領域、67 種 **document types（文件類型）**，每種文件類型共享一份 schema。這種「一份 schema 對應一類文件」的設計貼近企業實務：企業會為每個新流程撰寫新 schema，系統不能被調校成只認識單一固定模板。

為了在規模化下維持高品質 **ground-truth curation（真實標註建置）**，作者提出混合管線：對真實文件採用 **independent-system agreement（獨立系統一致性）**——讓多個前沿模型各自提出預測再進行裁決；對合成清單則在渲染前即設定已知值；對掃描表單進行 **human verification（人工驗證）**，包含數值與 bounding box。這種分層策略大幅減少全人工標註成本，同時保留關鍵視覺溯源資訊。

評測指標同樣對應三個核心需求：**value accuracy（數值準確率）** 以 **order-insensitive value F1（順序無關數值 F1）** 衡量，避免記錄順序影響評分；**visual grounding（視覺溯源）** 以 **word-level F1（詞級 F1）** 與 **page-level F1（頁級 F1）** 評估正確值是否指向正確來源；最後加入 **measured cost（實測成本）**，以每頁價格計算。三者同時評測是 ExtractBench 與既有基準最明顯的區隔之一。

#### 實驗數據解讀

作者在 14 種前沿方法上進行評測，橫跨 **commercial VLMs（商業視覺語言模型）**、開源抽取模型、**coding agents（編碼代理）** 與專用 API。整體結果顯示：**LlamaExtract Agentic Plus** 同時在數值準確率、視覺溯源與成本三項指標排名第一。其準確率與 coding agents 相當（相對於 Codex GPT-5.5 為 95.6% 對 93.6%），但成本僅約三分之一（8.1¢/page 對 27.8¢/page）。這說明「高準確率」與「高成本」並非必然連動，專為抽取任務設計的 agentic 流程可以在控制成本的同時維持穩定表現。

**commercial VLMs** 呈現鮮明的長短文件落差：以 Gemini 3.5 Flash 為例，短文件準確率達 87.9%，長文件卻跌至 27.9%。這種崩潰主要來自 **long-record completeness（長記錄完整性）** 失效——模型能正確讀取局部數值，卻會截斷長列表或遺漏跨頁記錄。相較之下，LlamaExtract Agentic Plus 在短文件與長文件上分別達 96.6% 與 94.4%，顯示其對長上下文與結構化輸出的處理更為穩健。

**coding agents** 雖然準確率較高，但有兩個明顯弱點：一是成本顯著較高，二是通常不返回 word-level bounding box，因此無法提供細緻的 **grounding metadata（溯源詮釋資料）**。對於需要人工複查或合規稽核的企業流程，缺乏來源證據會大幅降低可用性。這也凸顯專用抽取 API 的價值：只有它們能同時滿足「正確抽取」與「可視化溯源」。

視覺溯源指標進一步印證上述觀察。word-level F1 要求模型把每個正確值對應到文件中的精確詞彙位置，page-level F1 則只要求頁面正確。對於需要快速人工審核的場景，word-level grounding 能讓審查者直接定位到來源，無需在整份文件中搜尋；page-level 則是較寬鬆但仍有用的替代。實驗顯示，能輸出 bounding box 的專用系統在這兩項指標上明顯優於僅輸出文字的通用模型。

成本數據同樣值得重視。作者強調，在高量文件處理中，每頁一美分的差距就可能決定 AI 專案是否財務可行。ExtractBench 將成本納入正式評分，迫使研究者與工程師在選型時同時考慮準確率、溯源能力與經濟性，而非只追求單一準確率數字。

#### 與現有研究的比較

相較於傳統 **fixed-ontology（固定本體）** 的文件資訊抽取基準如 SROIE、DocILE、RealKIE，ExtractBench 的最大進步在於支援使用者自訂 schema。固定本體基準通常針對單一文件類型設計固定欄位，無法評估系統面對新 schema 時的泛化能力，而企業場景幾乎每個流程都需要新 schema。

在 **schema-guided extraction（綱要引導式抽取）** 基準中，ContextualEB（Contextual AI's ExtractBench）、ExtendLongArray、Micro1LongExtract-50、VAREX 各自覆蓋了問題的一個切面：ContextualEB 強調 schema-conformant JSON，ExtendLongArray 聚焦合成陣列的 row completeness，Micro1LongExtract-50 處理長統計報告與申報文件，VAREX 則使用 per-doc schema。然而，這些基準都未同時涵蓋 **long-record completeness（長記錄完整性）**、**real scans（真實掃描文件）**/handwriting、word-level 與 page-level grounding，以及 measured cost。ExtractBench 是首個將這些維度整合評分的基準（見 Table 1），因此更貼近真實企業部署的複雜權衡。

方法論上，ExtractBench 的標籤化 taxonomy 也比多數基準的單一 aggregate score 更具診斷價值。過去研究者只能知道「模型 A 比模型 B 好」，現在則能進一步說明「模型 A 在長列表上領先，但在手寫掃描上落後」。這種細粒度分析對產品選型與模型改進都更有指導意義。

不過 ExtractBench 仍有侷限。首先，370 份文件雖然規模可觀，但相對於真實企業世界無窮的文件變異仍屬樣本；某些罕見版面或極端長文件可能未被充分覆蓋。其次，ground-truth 對真實文件採用 independent-system agreement，雖然節省成本，但若參與模型存在共同偏誤，仍可能傳播錯誤標註。第三，成本數據依賴特定時間點的 API 定價與模型版本，隨著商業模型更新，數字會快速變動。最後，LlamaExtract Agentic Plus 與基準來自同一組織，雖然資料與程式碼已公開，仍可能存在利益相關的觀感問題，未來需要第三方獨立驗證。

#### 可重現性評估

ExtractBench 在可重現性上採取開放策略：資料集發布於 **Hugging Face（HuggingFace）**，評估程式碼發布於 **GitHub（GitHub）**。這讓其他研究者可以取得相同的 **benchmark corpus（評測語料庫）** 與評分腳本，至少能複製數值準確率與溯源指標的計算流程。

然而，完整重現仍有挑戰。首先，許多受測系統是專有 API，包括 **commercial VLMs（商業視覺語言模型）**、LlamaExtract Agentic Plus 與 Codex GPT-5.5 等，這些模型沒有公開權重，其行為會隨 API 版本、prompt 設計與溫度參數變化。若論文未詳細披露 prompt 與呼叫版本，後續研究難以完全複製當時結果。其次，**ground-truth curation pipeline（真實標註建置流程）** 的完整實作細節（例如參與的 frontier models、裁決規則、人工驗證準則）若未全部釋出，則難以從頭重建 schema–ground-truth 配對。第三，合成清單的渲染程式碼與隨機種子若未公開，會影響資料重現。最後，成本測量依賴當時匯率與 API 計價，未來讀者只能複製「相對成本趨勢」而非絕對金額。

整體而言，ExtractBench 的可重現性優於許多僅發布論文的基準，因為核心資料與評估程式碼已公開；但要達到端到端可重現，仍需作者進一步釋出 prompt、模型版本、標註管線參數與合成資料生成腳本。對於開源抽取方法，可重現性相對較高；對於專有 API，則只能做到近似比較。

#### 未來研究方向

第一，擴充多語言與跨文化文件。目前語料以英文企業文件為主，未來可加入中文、日文、阿拉伯文等非拉丁語系，以及不同國家的發票、稅單與監管表格，測試 schema-guided extraction 的跨語言泛化能力。

第二，強化感知挑戰覆蓋。雖然已包含 scan noise、handwriting 與 hierarchical headers，但可以進一步納入極低品質掃描、印章遮蓋、水漬、摺痕、手寫與印刷混排、以及複雜嵌套表格，以更接近真實檔案室環境。

第三，發展同時優化準確率、溯源與成本的聯合模型。目前結果顯示不同方法在三個維度上各有取捨，未來可研究具備結構化輸出與來源歸因能力的長上下文 **VLMs（視覺語言模型）**，或設計「先粗抽再細驗」的 agentic 流程，在降低呼叫次數的同時維持 grounding 品質。

第四，提升 grounding 粒度與可用性。除了 word-level 與 page-level bounding box，未來可探索 token-level provenance、欄位級置信度、以及可解釋的「為何選此來源」說明，讓 human-in-the-loop 審核更有效率。

第五，自動 schema 生成與適應。企業撰寫 schema 仍是瓶頸，未來可研究從少數範例或空白模板自動推導 schema，並在文件類型漂移時動態更新欄位結構。

第六，極長文件與階層式記錄的完整性評測。目前長文件挑戰已顯示列表截斷問題，未來可擴展到數百頁的財務申報文件（financial filings）、保險理賠卷宗，並評估階層式記錄（例如表格內嵌子表格）的完整抽取。

第七，結合人工複查的端到端工作流評估。除了自動指標，未來可測量 grounding metadata 如何縮短人工審核時間、降低錯誤率，並評估不同錯誤類型對下游業務流程的實際影響。

第八，推動開源專用抽取 API。目前表現最佳的 LlamaExtract 仍屬專有服務，學術界需要開放權重與訓練流程的專用模型，才能讓整個領域在公平、可重現的環境下持續進步。

## 論文問答

**Q1：什麼是「綱要引導式企業文件抽取」，為何它對現代企業工作流程很重要？**  
A：綱要引導式企業文件抽取是指系統在收到一份文件與使用者定義的抽取綱要後，依照綱要欄位產出結構化 JSON，並為每個數值附上來源頁面與邊界框等溯源詮釋資料。這與傳統由知識工作者手動閱讀財務申報文件、保險理賠單、採購訂單或政府表單再 key-in 資料的方式相比，能顯著降低重複勞動與人為錯誤。由於企業幾乎為每個新流程都會撰寫新綱要，系統必須具備泛化到不同文件類型與版面的能力，而非只記住固定範本，因此成為自動化文件工作流程的關鍵技術。

**Q2：現有的文件資訊抽取基準或方法存在哪些主要限制，促使作者提出 ExtractBench？**  
A：傳統固定本體的基準如 SROIE 與 DocILE 只能處理預先定義的固定範本，無法評估使用者自訂綱要；而近期綱要引導式基準如 ContextualEB、ExtendLongArray 與 Micro1LongExtract-50 各只涵蓋問題的一個切面，例如僅評估綱要符合的 JSON、合成清單的列完整性或長篇報告。這些基準均未同時納入真實掃描與手寫文件、視覺溯源、長記錄完整性與實測成本。ExtractBench 因此試圖彌補缺口，提供一個同時評量數值準確率、記錄完整性、溯源能力與成本的綜合評測語料庫。

**Q3：為何視覺溯源與每頁抽取成本在企業級部署中同樣重要？**  
A：在生產環境中，抽取錯誤難以完全避免，例如長期投資明細被截斷導致基金持有多筆遺漏，此時人類審核員需要透過詞級或頁級的來源證據快速定位並修正問題。同時，文件密集型企業流程往往處理數百萬頁，每頁成本相差一美分就可能決定 AI 專案是否具財務可行性。因此，一個實用的抽取系統不僅要準確，還必須提供可稽核的溯源詮釋資料並維持可接受的單頁成本。

**Q4：ExtractBench 的核心架構包含哪些主要元件？**  
A：ExtractBench 包含一個大規模且帶標籤的評測語料庫，共 370 份文件、4,869 頁，橫跨 8 個業務領域與 67 種文件類型，並以五個獨立軸向標記挑戰情境。它還設計了一套可擴展的綱要與真實標註建置流程，針對真實文件採用獨立系統一致性、合成清單採用預設已知值、掃描表單則輔以人工驗證。評估指標同時涵蓋順序無關數值 F1、詞級與頁級溯源 F1，以及實測成本，形成對抽取任務的多維度評量。

**Q5：ExtractBench 如何在不大規模人工標註每個欄位的情況下，建立高品質的真實標註？**  
A：作者採用三種互補策略：對於真實文件，讓多個獨立系統各自提出抽取結果，再透過系統間一致性進行裁決；對於合成長清單，則在渲染前即設定好已知值，因此自動擁有完整正解；對於掃描表單，則由人工驗證數值與溯源框。這種混合式流程兼顧規模與正確性，使大量企業文件能夠以可控成本取得可信賴的綱要—真值配對。

**Q6：為何 ExtractBench 要將文件沿五個獨立軸向進行分類標籤？**  
A：五個軸向包括任務挑戰、感知挑戰、表格結構、長度與業務領域，彼此獨立可讓研究者把整體分數拆解成具體失敗原因。例如，某系統整體 F1 下降可能來自長文件截斷、掃描雜訊或階層式標題理解錯誤，而非單純模型不好。這種細粒度標籤設計支援針對特定困難情境進行診斷與改進，也讓不同方法的能力與弱點更透明。

**Q7：實驗中評測了哪些類型的方法，評估面向為何？**  
A：作者評測了 14 種前沿方法，涵蓋商業視覺語言模型、開源抽取模型、編碼代理與專門化 API。評估面向不僅有傳統的數值準確率，還包括長記錄完整性、詞級與頁級視覺溯源，以及實際呼叫 API 產生的每頁成本。這樣的廣泛比較能同時檢視通用模型與專用系統在不同挑戰維度上的取捨。

**Q8：實驗的主要結果顯示各類方法之間有什麼差異？**  
A：商業視覺語言模型在短文件上表現不錯，但在長文件上經常截斷記錄清單，例如 Gemini 3.5 Flash 的準確率從短文件的 87.9% 驟降至長文件的 27.9%。編碼代理雖然維持較高準確率，卻伴隨高昂成本。LlamaExtract Agentic Plus 在三項指標上均排名第一，不僅準確率與編碼代理相當甚至略勝 Codex GPT-5.5，每頁成本卻僅為 8.1 美分，遠低於後者的 27.8 美分。

**Q9：文件長度對不同方法的影響揭示了什麼問題？**  
A：長度是區分系統穩定性的關鍵維度，許多模型能正確讀取局部數值，卻無法完整輸出長篇排程或表格中的所有列。LlamaExtract Agentic Plus 在短文件與長文件上分別達到 96.6% 與 94.4%，顯示其對長記錄完整性有較強的處理能力。這說明未來研究需要特別關注跨頁延續、大型不規則表格與長清單的完整抽取，而非僅追求短文件的單點準確率。

**Q10：哪些實際企業場景最能受惠於具備溯源能力的綱要引導式抽取？**  
A：財務申報文件、保險理賠單、採購訂單、政府表單與統計報告等大量文件密集型流程都能受惠，因為這些文件格式各異且常包含長表格與重複記錄。下游的記錄系統需要正確且完整的結構化資料，而審核人員則需要快速確認每筆數值的來源。透過自動化抽取並附上詞級或頁級證據，企業可同時提升處理速度、降低錯誤成本並滿足合規稽核需求。

**Q11：企業在選擇抽取方案時，應如何權衡商業 VLM、編碼代理與專門化 API？**  
A：選擇時應同時考量準確率、成本與是否需要來源證據：商業 VLM 上手容易但長文件容易截斷且通常不提供詞級邊界框；編碼代理準確率較高但每頁成本顯著較高；專門化抽取 API 則能在提供視覺溯源的同時控制成本。若工作流程需要人類在迴路稽核或法規遵循，就必須優先選擇能回傳詞級來源框的解決方案，而非僅輸出純文字結果。

**Q12：ExtractBench 對文件資訊抽取領域可能帶來什麼影響？**  
A：ExtractBench 是首個同時大規模評量數值準確率、記錄完整性、視覺溯源與實測成本的綱要引導式基準，為學界與業界提供統一的比較標準。它將研究焦點從單一準確率擴展到真實部署所需的完整能力光譜，特別是長記錄、掃描手寫與成本效益。透過公開資料集與評估程式碼，它有助於加速更可靠、可稽核且經濟可行的企業抽取系統發展。

**Q13：ExtractBench 在範圍或方法上存在哪些可能的限制？**  
A：雖然語料庫涵蓋 8 個業務領域與 67 種文件類型，但仍無法窮盡所有企業文件的多樣性，特定產業或語言的覆蓋可能有限。合成清單雖然能精確控制真值，但其版面與雜訊模式未必完全反映真實世界文件的複雜度。此外，成本數據會隨 API 定價與模型版本變動，實驗結果僅代表特定時間點的實測值。

**Q14：即使是頂尖系統，目前仍常見哪些失敗案例？**  
A：常見失敗包括長篇排程或清單的列被截斷、在文件中選錯稀疏事實的出現位置、密集表單過度填寫或遺漏欄位，以及混淆相似的日期、識別碼或金額。感知挑戰如掃描雜訊、手寫字跡、階層式標題與跨頁延續也會導致結構理解錯誤。這些問題顯示，單純提升局部數值辨識仍不足以解決企業抽取，系統還需強化文件結構感知與全局一致性。

**Q15：未來研究可以朝哪些方向延伸 ExtractBench 或改進抽取系統？**  
A：未來可進一步強化長記錄與大型不規則表格的完整抽取、提升掃描與手寫文件的感知魯棒性，並發展更精細且低成本的視覺溯源機制。也可擴展到更多語言、產業領域與多頁跨文件推理，並探索如何讓自主代理在抽取過程中主動驗證與修正。最終目標是讓綱要引導式抽取在真實企業環境中同時達到高準確、高完整、可溯源與可負擔的成本。

## 實務應用指南

### 適用場景

1. **財務申報文件自動化錄入**  
   企業需從財務申報文件、資產負債表或基金持股長清單中抽取科目、金額與日期。ExtractBench 的「長記錄完整性」與「跨頁上下文」標籤特別適合驗證系統是否會遺漏長表格中的列。

2. **保險理賠與醫療表單處理**  
   不同供應商的理賠單格式差異大，且常包含手寫內容與掃描雜訊。綱要引導式抽取可讓同一份理賠綱要套用到多種版面，並透過視覺溯源快速標出爭議欄位供人工複審。

3. **採購訂單與發票對帳**  
   發票、採購訂單與收據數量龐大，欄位重複且密集。系統必須正確處理重複記錄、相似金額與階層式標題，並將抽取結果寫入記錄系統或 ERP。

4. **政府表單與稅務文件歸檔**  
   稅表與政府表單通常有固定空白範本，可據以設計綱要。透過人工驗證的詞級與頁級方框，稽核人員可直接點選抽取值查看來源證據，滿足合規需求。

5. **長格式物流與運送清單**  
   貨運提單、裝箱明細等文件動輒數十頁，容易發生截斷。評測時可同時追蹤數值準確率、記錄完整性與每頁實測成本，確保高頁量流程在財務上可行。

---

### 實作前置條件

- **資料準備**
  - 代表性文件樣本：包含短文件、長文件、掃描檔、手寫區域與不同版面。
  - 每種文件類型一份共享綱要（schema），定義欄位名稱、型別、是否可重複、允許值與是否可為 null。
  - 用於驗證的真實標註（ground truth），可透過獨立系統一致性、合成清單預設值或人工驗證取得。

- **運算與成本**
  - API 額度與預算：商業視覺語言模型成本較低，但長文件可能截斷；編碼代理準確率高但每頁成本顯著較高。
  - 可執行評估程式碼的環境，用於計算順序無關數值 F1、詞級 F1、頁級 F1 與成本追蹤。

- **技能需求**
  - 熟悉 JSON Schema 與提示工程。
  - 具備文件版面分析與領域知識，能判斷欄位是否必填、重複記錄如何定義。
  - 能建立評測管線並解讀 F1 分數在不同挑戰標籤上的表現。

---

### 實作步驟建議

1. **定義抽取任務與輸出格式**  
   參考論文第 2.1 節，將任務寫成「文件 + 使用者定義綱要 → schema-valid JSON + 來源頁碼與邊界框」。明確規定 null 的使用方式與重複記錄的輸出結構。

2. **建立綱要與挑戰標籤**  
   為每種文件類型設計一份綱要，並為每份文件標註任務挑戰、感知挑戰、表格結構、業務領域與長度。這能讓後續分析知道低分來自長記錄截斷還是掃描雜訊。

3. **建置可擴展的真實標註**  
   - 真實文件：使用多個獨立系統交叉驗證，再人工仲裁歧異處。  
   - 長清單：用真實版面渲染合成清單，預先設定值作為黃金標準。  
   - 掃描表單：人工驗證數值與詞級邊界框。

4. **選擇抽取方法並試跑**  
   從商業視覺語言模型、開源抽取模型、編碼代理與專用 API（如 LlamaExtract Agentic Plus）中挑選 2–3 種。先以短文件驗證基本數值準確率，再測長文件與掃描檔。

5. **執行完整評估**  
   使用 ExtractBench 評估程式碼計算：
   - 順序無關數值 F1（value accuracy）
   - 詞級 F1 與頁級 F1（visual grounding）
   - 每頁實測成本

6. **迭代與部署**  
   針對低分標籤補強：長文件可加強分頁策略或改用支援長記錄的代理；掃描檔可前置 OCR 或版面還原；缺乏詞級方框的模型可後接專用溯源模組。部署時保留人工複審迴路。

---

### 潛在風險與注意事項

- **長記錄截斷**  
  商業視覺語言模型在短文件表現好，但長文件常遺漏列。建議對長表格做分段或選用長記錄完整性較高的方法。

- **過度填寫與重複記錄混淆**  
  密集表單中模型可能把不屬於該欄位的值填入，或把同一筆記錄重複輸出。綱要應清楚標示欄位對應關係與唯一鍵。

- **稀疏事實與相似值錯置**  
  文件中少見的事實（如特定日期或識別碼）可能被錯誤配對。可加入欄位語境描述與鄰近文字約束。

- **掃描與手寫雜訊**  
  真實掃描檔與手寫內容會降低感知準確率。建議在資料集中保留這類樣本，並評估前置 OCR 與端到端模型的差異。

- **缺乏詞級溯源**  
  商業視覺語言模型與編碼代理通常不返回詞級邊界框。若工作流程需要稽核來源證據，應選用支援視覺溯源的專用抽取 API。

- **成本失控**  
  編碼代理雖準確，但每頁成本可能數倍於商業模型。高頁量場景應以「準確率 × 成本」作為選型依據，而非只看 F1。

- **綱要漂移**  
  企業常為新流程撰寫新綱要。避免針對單一固定範本過度調校，確保系統能泛化到同一文件類型的不同供應商版面。

---

### 與其他技術的整合建議

- **RPA / ERP / CRM**  
  將抽取出的 JSON 透過標準 API 寫入記錄系統，並在欄位信賴度低時觸發例外流程。

- **文件管理系統（DMS）**  
  把來源頁碼與邊界框儲存為詮釋資料，讓使用者在 DMS 中點選抽取值即可跳轉到原始文件位置。

- **人工複審介面**  
  對於低信賴度或長記錄截斷的欄位，自動產生審核任務。視覺溯源可讓審核員不必手動搜尋文件。

- **向量資料庫與檢索增強生成（RAG）**  
  將抽取結果與原始區塊嵌入向量庫，支援下游問答、對帳或異常偵測。

- **監控與 CI/CD**  
  把 ExtractBench 評估程式碼納入持續整合流程，當綱要更新或模型換版時自動回歸測試數值準確率、記錄完整性與成本。

- **初學者**  
  先讀摘要與第 2.1 節的任務定義，理解「綱要引導式抽取」與傳統固定範本抽取的差別；接著看表 1 的能力比較，就能快速掌握 ExtractBench 為何同時評估長記錄、視覺溯源與成本。

- **AI 工程師**  
  重點閱讀第 2.2 節的標籤設計、第 2.4 節的評估指標，以及第 3 節的 14 種前沿方法比較。實作時直接參考 GitHub 上的評估程式碼，並注意商業視覺語言模型與編碼代理在成本與溯源上的取捨。

- **研究人員**  
  深入第 2.3 節的可擴展真實標註建置流程，以及詞級／頁級溯源指標的設計。可進一步探討如何改進長記錄完整性、跨頁上下文理解，或降低高準確率方法的每頁成本。

- **產品經理**  
  聚焦摘要中的成本數據、第 3 節的短文件與長文件準確率落差，以及視覺溯源對人工複審的價值。這些資訊有助於評估不同方案在真實企業流程中的 ROI、稽核合規性與上線風險。
