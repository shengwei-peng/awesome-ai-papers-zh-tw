## ⚡ TL;DR

從自然語言生成一致的遊戲世界，需同時協調場景結構、空間佈局、遊戲目標與可執行邏輯。
本文提出 Code2Games 框架，透過共享表徵與執行導引重建，自動適配 Unreal 引擎。
實驗顯示在視覺品質、互動保真度與可玩性上皆優於基線，並提出 GameCode4D 基準。

## 摘要翻譯

從自然語言遊戲意圖（Natural-Language Game Intent）生成高品質的遊戲世界，需要對場景結構（Scene Structure）、空間佈局（Spatial Layout）、遊戲目標（Gameplay Objectives）、互動實體（Interactive Entities）以及可執行遊戲邏輯（Executable Gameplay Logic）進行聯合推理。現有的程式碼代理（Coding Agent）雖能生成個別資產、場景或腳本，但往往難以在這些組件之間維持一致性。我們提出 Code2Games，一個代理式框架（Agentic Framework），奠基於由相同遊戲意圖生成之基礎 Blender 世界（Base Scene），建構出結構化的遊戲世界。Code2Games 透過共享場景-遊戲機制表徵（Shared Scene-Gameplay Representation）與持續性元素對應（Persistent Element Correspondence），協調場景分析（Scene Analysis）、遊戲機制規劃（Gameplay Planning）、約束式遊戲世界生成（Constrained Gaming-World Generation）以及遊戲引擎客製化（Gaming-Engine Customization）。在世界生成完成後，Code2Games 將生成的世界適配至 Unreal Engine 5，並採用執行導引重建流程（Execution-Guided Reconstruction），利用編譯診斷資訊（Compilation Diagnostics）、執行階段回饋（Runtime Feedback）以及遊戲機制測試結果（Gameplay Test Results），來解決引擎適配（Engine Adaptation）過程中產生的不一致問題。為了系統性地評估遊戲世界生成，我們引入 GameCode4D 基準測試，其中包含十個跨越不同場景複雜度（Scene Complexity）與遊戲機制複雜度（Gameplay Complexity）的固定遊戲提示詞（Fixed Game Prompts）。我們從四個面向評估生成結果：視覺品質（Visual Quality）、互動保真度（Interactive Fidelity）、多模態產出品質（Multimodal Artifact Quality）以及可玩遊戲品質（Playable-Game Quality）。實驗結果顯示，與程式碼代理直接進行遊戲世界生成以及現有的基線方法（Baseline Methods）相比，Code2Games 皆能持續提升生成遊戲世界的視覺品質與互動保真度，同時也提升了引擎適配後所生成遊戲的品質。

### 核心貢獻（3～5點）
- **提出 Code2Games 代理式框架**：奠基於基礎 Blender 場景，透過共享場景-遊戲機制表徵與持續性元素對應，協調場景分析、遊戲機制規劃、約束式遊戲世界生成與遊戲引擎客製化，解決跨組件一致性問題。
- **設計執行導引重建機制**：在將生成世界適配至 Unreal Engine 5 時，利用編譯診斷資訊、執行階段回饋與遊戲機制測試結果三種信號，自動解決引擎適配過程中產生的不一致問題。
- **建立 GameCode4D 基準測試**：涵蓋十個跨越不同場景與遊戲機制複雜度的固定遊戲提示詞，提供系統性評估遊戲世界生成的標準化測試平台。
- **提出四維評估體系**：從視覺品質、互動保真度、多模態產出品質與可玩遊戲品質四個面向，全面衡量生成遊戲世界的品質。
- **實驗驗證全面優於基線**：相較於程式碼代理直接生成及現有基線方法，Code2Games 在視覺品質、互動保真度及引擎適配後的可玩遊戲品質上皆能持續提升。

### 適合對象
本論文最適合以下讀者閱讀：從事自動化遊戲開發（Automated Game Development）、互動式內容創作（Interactive Content Creation）與代理式軟體生成（Agentic Software Generation）研究的學者與工程師；關注大型語言模型（LLM）與程式碼代理（Coding Agent）在 3D 遊戲資產（3D Gaming Assets）及程序化生成（Procedural Generation）領域應用的研究人員；以及遊戲產業中對 AI 輔助遊戲世界生成、Blender 與 Unreal Engine 5 工作流程整合感興趣的技術實務者。

## 深度分析

#### 方法論解析

Code2Games 提出了一套多代理 (multi-agent) 協作的端到端框架，目標是將「自然語言遊戲意圖 (natural-language game intent)」與「對應的 Blender 基礎場景 (base scene)」轉化為可在 Unreal Engine 5 中實際運行的可玩遊戲專案。其方法論的核心在於解決「跨模態一致性」與「跨引擎可執行性」兩個長期未被同時處理的難題。

**1. 四階段代理架構**

框架由四個專責代理依序串接而成，每個代理負責一個明確子任務：

- **場景分析代理 (Scene Analysis Agent)**：從 Blender 基礎場景中萃取結構化資訊，包含空間區域劃分 (spatial regions)、物件清單、可達性關係 (accessibility relations) 與互動可能性 (interaction affordances)。此步驟將非結構化的 3D 場景轉為可被後續代理推理的符號化表徵。

- **遊戲機制規劃代理 (Gameplay Planning Agent)**：將自然語言意圖解析為結構化規格，涵蓋遊戲目標 (objectives)、角色行為者 (actors)、遊戲機制元素 (gameplay elements) 與互動規則 (interaction rules)。此代理本質上是將模糊的設計意圖 (design intent) 翻譯為可執行的邏輯規格。

- **約束式遊戲世界生成代理 (Gaming World Generation Agent)**：在場景分析與遊戲機制規劃的雙重約束下，實例化場景元素與遊戲機制元件，確保視覺佈局與互動語意同時滿足。

- **遊戲引擎客製化代理 (Gaming Engine Customization Agent)**：將生成的遊戲世界移植至 Unreal Engine 5，重建引擎端的 actors、設定檔 (configuration files) 與遊戲邏輯。

**2. 共享場景-遊戲機制表徵 (Shared Scene-Gameplay Representation)**

此為方法論的關鍵創新。框架建立一個跨階段共享的中間表徵，維持「持續性元素對應 (persistent element correspondence)」，使得從自然語言意圖 → 場景分析 → 遊戲機制規劃 → 世界生成 → 引擎適配的每一個環節中，特定物件、區域與互動規則都能被一致地追蹤與引用。這解決了既有系統中「各元件獨立生成、缺乏全域綁定」的問題。

**3. 執行導引重建流程 (Execution-Guided Reconstruction)**

引擎適配階段引入閉迴路 (closed-loop) 修復機制：將適配後的世界進行編譯、啟動與遊戲機制測試 (gameplay tests)，收集三類回饋訊號——編譯診斷資訊 (compilation diagnostics)、執行階段回饋 (runtime feedback)、遊戲機制測試結果 (gameplay test results)——用以定位並修復場景實作、actor 綁定、設定檔與遊戲規則中的不一致。此設計承認一個重要事實：許多錯誤僅在實際執行時才會顯現，因此單純靜態生成不足以保證可玩性。

**4. 複雜度光譜覆蓋**

如 Figure 2 所示，框架設計的目標場景橫跨場景實體數量 (scene entity count) 與可執行行為數量 (executable behavior count) 兩個對數刻度軸，從簡單的 Temple Run、Skiing 到複雜的 Assassin's Creed、Minecraft 等開放世界 (open world) 環境，涵蓋戰鬥 (Combat)、探索 (Exploration)、移動穿越 (Traversal)、競速 (Racing) 等多元遊戲類別 (game category)。

#### 實驗數據解讀

**1. GameCode4D 基準 (Benchmark) 設計**

作者提出 GameCode4D 基準，包含 10 個固定遊戲提示詞 (fixed game prompts)，每個提示詞明確指定遊戲類型 (game genre)、視角 (viewpoint) 與高層次目標。10 個場景涵蓋：Temple Run、Skiing、Wingsuit、Racing、TPS、FPS、Underwater、Assassin's Creed、Monster Hunt、Minecraft。這些場景在「場景結構複雜度」與「遊戲機制邏輯複雜度」兩個維度上呈現系統性差異，使基準能夠區分不同方法在不同難度下的表現。

**2. 四維度評估協議**

評估從四個互補面向進行：

- **視覺品質 (Visual Quality)**：衡量生成世界的外觀合理性，包括紋理、光照、幾何一致性等。
- **互動保真度 (Interactive Fidelity)**：衡量生成世界與指定設定及互動的一致程度，考驗物件是否被正確放置、互動是否對應正確實體。
- **多模態產出品質 (Multimodal Artifact Quality)**：評估生成產物（程式碼、設定檔、資產）的整體品質。
- **可玩遊戲品質 (Playable-Game Quality)**：在引擎適配與實際執行後，衡量預期遊戲體驗的實現程度。

此四維度設計的精妙之處在於：前三者可在生成階段靜態評估，第四者則必須經過完整的執行閉迴路才能判定，迫使方法必須真正產生可運行的遊戲，而非僅僅是視覺上合理的展示。

**3. 與基線方法的比較**

實驗將 Code2Games 與兩類基線比較：(a) 程式碼代理 (coding agent) 直接進行遊戲世界生成；(b) 既有基線方法 (baseline methods)。結果顯示 Code2Games 在視覺品質與互動保真度上持續優於基線，且在引擎適配後的可玩遊戲品質上同樣領先。這驗證了「共享表徵 + 執行導引重建」的雙重設計對於維持跨元件一致性的必要性。

**4. 結果的意涵**

值得注意的是，Figure 2 的氣泡圖 (bubble chart) 同時編碼三個維度：橫軸為場景實體數量、縱軸為可執行行為數量、氣泡大小 (bubble size) 為遊戲機制元素數量、顏色為遊戲類別。這種多變量視覺化揭示了一個關鍵觀察：Code2Games 並非僅在簡單場景表現良好，而是能夠處理高實體數、高行為數的複雜組合，這對於實務應用至關重要。

#### 與現有研究的比較

**1. 與互動式世界模型 (Interactive Video and Game World Models) 的定位差異**

既有世界模型如 Genie (Bruce et al., 2024)、DIAMOND (Alonso et al., 2024)、GameNGen (Valevski et al., 2025) 學習動作條件下的視覺動態，產生可互動的觀察序列。然而，這些方法生成的是「像素級的互動觀察」，而非「可編輯的引擎專案」。它們缺乏明確的資產、物件識別與可執行規則，因此無法支援後續的遊戲開發流程。Code2Games 明確定位於「將結構化世界轉化為可運行遊戲專案」的階段，保留了實作與驗證遊戲機制所需的場景資訊，這是與世界模型路線的本質區別。

**2. 與語言引導 3D 世界生成 (Language-guided 3D World Generation) 的互補關係**

程序化生成 (procedural generation) 與 text-to-3D 方法（如 Deitke et al., 2022; Höllein et al., 2023）提供可擴展的 3D 環境生成途徑，大型語言模型與視覺語言模型進一步支援組合式佈局規劃（Feng et al., 2023; Lin et al., 2023; Yang et al., 2024b）。然而，這些工作多聚焦於「場景生成」本身，較少關注「場景如何承載可執行的遊戲邏輯」。Code2Games 將 Blender 基礎場景視為輸入而非輸出，專注於「在已有視覺基礎上注入遊戲機制」，這與純粹的 3D 場景生成路線形成互補。

**3. 與程式碼代理 (Coding Agents) 的關係**

既有程式碼代理（如 Wang et al., 2023a; Yao et al., 2022; Shinn et al., 2023; Jimenez et al., 2024）能生成遊戲資產、靜態場景、遊戲腳本或引擎專案元件，但這些元件往往「獨立生成、獨立評估」，導致物件視覺合理但放置於不適當區域、遊戲角色未對應正確實體、目標錨定於不可達區域等問題。Code2Games 透過共享表徵與持續性元素對應機制，從根本上解決了這種「局部合理但全域不一致」的問題。

**4. 限制與未涵蓋面向**

- **引擎依賴性**：實作僅針對 Unreal Engine 5，未驗證在 Unity、Godot 等其他引擎的可移植性。
- **基礎場景依賴**：框架需要 Blender 基礎場景作為輸入，這意味著其能力受制於上游場景生成器的品質。
- **基準規模**：GameCode4D 僅含 10 個場景，雖然涵蓋了複雜度光譜，但對於統計顯著性與泛化性評估仍屬小規模。
- **評估主觀性**：視覺品質與互動保真度的評估可能涉及人工評審或視覺語言模型評分，其客觀性與可重現性需進一步驗證。

#### 可重現性評估

**1. 程式碼與框架可用性**

根據論文描述，Code2Games 框架涉及多個代理模組、共享表徵設計、執行導引重建流程以及與 Unreal Engine 5 的深度整合。論文中未明確聲明程式碼是否開源，但作為一個以 Unreal Engine 5 為後端的代理式框架 (agentic framework)，其可重現性面臨以下挑戰：

- **引擎授權**：Unreal Engine 5 雖為免費可用，但其完整功能與商業授權條款可能限制研究重現。
- **代理配置**：四個代理的提示詞設計、模型選擇、參數設定對於結果至關重要，需詳細公開。
- **執行環境**：執行導引重建需要完整的編譯、啟動與測試環境，這對硬體與軟體配置有特定要求。

**2. 基準與資料集**

GameCode4D 基準包含 10 個固定遊戲提示詞，這些提示詞本身可公開以供重現。然而，完整的評估協議（包括四維度的具體評分標準、評審流程、自動化評測腳本）的公開程度，將直接影響後續研究的可比性。

**3. 模型權重**

框架依賴底層的大型語言模型 (LLM) 與視覺語言模型，這些模型的權重可從原始提供者取得，但框架本身的微調或特定配置若未公開，將限制完全重現。

**4. 整體可重現性判斷**

考量到框架的複雜度（多代理 + 引擎整合 + 執行閉迴路），其可重現性屬於「中等偏難」。建議作者公開：(a) 各代理的完整提示詞與系統訊息；(b) 共享表徵的具體 schema；(c) 執行導引重建的錯誤分類與修復策略；(d) GameCode4D 的完整評測腳本與基準答案。

#### 未來研究方向

**1. 多引擎支援與抽象化**

目前框架鎖定 Unreal Engine 5，未來可發展引擎無關的中間表徵，使同一遊戲世界能自動適配 Unity、Godot 等引擎。這需要更抽象的「遊戲世界描述語言」，將引擎特定概念（如 Unreal 的 Actor、Component）提升為通用語意。

**2. 基礎場景生成的一體化**

現有框架將 Blender 基礎場景視為外部輸入，未來可將場景生成整合進框架本身，形成「從自然語言到可玩遊戲」的完全閉環。這需要場景生成代理與遊戲機制規劃代理之間的更深度耦合。

**3. 動態世界與敘事生成**

當前框架聚焦於靜態世界結構與基礎互動，未來可擴展至動態敘事 (dynamic narrative)、程序化任務 (procedural quests)、NPC 行為樹 (behavior trees) 等更複雜的遊戲機制元素，使生成的世界具備持續演化的能力。

**4. 玩家行為驅動的迭代優化**

執行導引重建目前依賴編譯診斷與基本遊戲測試，未來可引入真實玩家行為資料或強化學習代理 (reinforcement learning agent) 進行大規模遊戲測試，以玩家體驗指標（如參與度、難度曲線）作為優化目標。

**5. 評估協議的標準化**

GameCode4D 的四維度評估仍偏主觀，未來可發展自動化評測指標（如基於遊戲內狀態轉換圖的覆蓋率、基於模擬玩家行為的目標達成率），並擴充基準規模至數十甚至數百個場景，以支援統計顯著的泛化性評估。

**6. 多人協作與模組化遊戲機制**

當前框架以單一意圖驅動單一世界生成，未來可探索「多人協作設計」情境，讓多個使用者分別貢獻場景、機制、敘事，框架負責整合一致性，這將考驗共享表徵在並發編輯下的持續性元素對應能力。

**7. 與世界模型的融合**

世界模型擅長生成視覺動態，Code2Games 擅長生成可執行遊戲邏輯，未來可探索兩者的深度融合：利用世界模型預測的視覺演化來驅動遊戲機制狀態轉換，使生成的遊戲同時具備視覺豐富度與邏輯深度。

**8. 安全與內容審查**

自動生成的遊戲內容可能涉及不當素材、偏見或安全風險，未來需整合內容審查代理，確保生成結果符合規範，這對於教育、兒童遊戲等應用場景尤為重要。

## 論文問答

**Q1：Code2Games 試圖解決的核心問題是什麼？**
A：Code2Games 旨在解決從自然語言遊戲意圖生成高品質、一致性遊戲世界的難題。一個完整的遊戲世界並非僅僅是視覺上合理的資產集合，而是需要同時整合結構化的環境、空間一致的物件、互動實體、遊戲目標，以及反映預期體驗的可執行規則。核心挑戰在於維持「遊戲意圖」、「生成的遊戲世界」與「使用者預期進行的互動」三者之間的對應關係，這需要對場景結構、空間佈局、遊戲目標、互動實體與可執行邏輯進行聯合推理。

**Q2：為什麼現有的程式碼代理在這項任務上表現不佳？**
A：現有的程式碼代理雖然能夠生成個別的遊戲資產、靜態場景、遊戲腳本或特定引擎的專案元件，但這些元件往往是獨立生成與評估的。這種獨立性導致了嚴重的一致性問題：一個物件可能在視覺上看起來合理，卻被放置在不適合的區域；一個遊戲角色可能未對應到正確的實體；一個目標可能被設定在場景中無法到達的位置。因此，即使每個獨立元件都看似合理，組合起來仍可能形成一個與設計意圖不一致的遊戲世界。

**Q3：為什麼這個問題在學術與實務上都很重要？**
A：這個問題橫跨互動式內容創作與代理式軟體生成兩個重要領域，是 AI 代理從「生成內容」邁向「建構可執行系統」的關鍵一步。隨著大型語言模型與程式碼代理的快速發展，自動化遊戲開發已成為檢驗代理能否進行長程規劃與多模態整合的重要試金石。此外，如圖 2 所示，本研究所涵蓋的場景從簡單的滑雪、穿越類遊戲到複雜的戰鬥、探索與開放世界環境，跨越了極大的複雜度光譜，這對於推動代理在高度複雜任務中保留視覺組織與互動語意的能力具有重要意義。

**Q4：Code2Games 的核心方法架構為何？**
A：Code2Games 採用代理式框架，由多個專責代理分工合作完成遊戲世界生成。首先，**場景分析代理**從 Blender 基礎場景中萃取空間區域、物件、可達性關係與互動可能性；接著，**遊戲機制規劃代理**將自然語言意圖轉譯為包含目標、角色、遊戲元素與互動規則的結構化規格；然後，**遊戲世界生成代理**在這些約束下實例化場景元件與遊戲元件；最後，**遊戲引擎客製化代理**將生成的世界適配到目標遊戲引擎（本研究採用 Unreal Engine 5）。

**Q5：Code2Games 最關鍵的創新是什麼？**
A：Code2Games 的兩大關鍵創新在於「共享場景-遊戲機制表徵」與「執行導引重建」機制。共享表徵透過持續性元素對應，確保從場景分析、遊戲機制規劃到世界生成的每個階段中，相同的元素都能被一致地追蹤與引用，避免元件之間的對應關係在流程中斷裂。執行導引重建則是在引擎適配後，利用編譯診斷資訊、執行階段回饋與遊戲機制測試結果來定位並修復場景實現、角色綁定、設定檔與遊戲規則中的錯誤，這對於解決僅在執行階段才會顯現的不一致性特別有效。

**Q6：Code2Games 在設計上做了哪些重要的選擇？**
A：在設計上，Code2Games 選擇以「先分析、再規劃、再生成、最後適配引擎」的四階段流程取代端到端的直接生成，這降低了單一代理同時處理視覺與邏輯的負擔。框架選擇 Blender 作為基礎場景的來源，是因為它提供了結構化的 3D 場景資訊，便於後續代理進行空間分析；而選擇 Unreal Engine 5 作為目標引擎，則是因為它是業界主流的高階引擎，能夠真實驗證生成結果的可執行性。此外，框架刻意將「生成」與「驗證」分離，並透過執行回饋形成閉環，這體現了「建構-測試-修復」的工程化思維。

**Q7：GameCode4D 基準測試是如何設計的？**
A：GameCode4D 基準測試包含十個固定的遊戲提示詞，每個提示詞明確指定遊戲類型、視角與高層次目標，涵蓋了 Temple Run、滑雪、翼裝飛行、競速、第三人稱射擊（TPS）、第一人稱射擊（FPS）、水下、Assassin's Creed、怪物獵殺與 Minecraft 等多元場景。這十個場景在場景結構複雜度與遊戲邏輯複雜度上呈現多樣化的組合，從較簡單的穿越與滑雪設定，到複雜的戰鬥、探索與開放世界環境。評估則沿著四個互補的維度進行：視覺品質、互動保真度、多模態產出品質與可玩遊戲品質。

**Q8：Code2Games 的主要實驗結果為何？**
A：實驗結果顯示，相較於程式碼代理直接生成遊戲世界以及現有的基線方法，Code2Games 在視覺品質與互動保真度兩個維度上皆呈現一致的提升。更重要的是，在經過引擎適配與執行後，Code2Games 所產出的遊戲在「可玩遊戲品質」上也優於對照組，這證明了執行導引重建機制對於解決引擎層級不一致性的價值。這些結果顯示出多階段、帶有持續性對應的代理式框架，相較於單純依賴程式碼代理直接生成，能更有效地兼顧視覺合理性與互動正確性。

**Q9：Code2Games 的各元件是否都經過消融實驗驗證？**
A：雖然論文的全文細節未在所提供的段落中完整呈現，但從方法描述可以推論，共享場景-遊戲機制表徵與執行導引重建是兩個最值得進行消融驗證的關鍵元件。共享表徵的消融可以透過移除持續性元素對應、僅以獨立訊息傳遞取代來驗證其對一致性的貢獻；而執行導引重建的消融則可透過關閉編譯診斷、執行回饋或遊戲機制測試中的任一回饋來源，來量化每種回饋訊息對修復效果的相對重要性。這類消融實驗對於理解框架中各機制的必要性至關重要。

**Q10：Code2Games 的潛在實務應用場景有哪些？**
A：Code2Games 的潛在應用場景相當廣泛。在遊戲開發產業，它可作為快速原型工具，讓設計師透過自然語言描述快速生成可玩的遊戲雛型，大幅縮短概念驗證的週期。在教育領域，它能幫助學生學習遊戲設計與程式開發，透過觀察 AI 如何將抽象意圖轉化為具體實作來理解遊戲結構。此外，它也適用於獨立開發者或小型工作室，使其能在缺乏大型團隊資源的情況下產出具有基本可玩性的作品。

**Q11：若要將 Code2Games 產品化，需要考量哪些因素？**
A：產品化時需要考量多項因素：首先，使用者介面必須讓非技術背景的創作者也能輕鬆輸入自然語言意圖並理解生成結果，因此需要視覺化的預覽與迭代機制。其次，生成的資產品質與授權問題必須妥善處理，以避免智慧財產權爭議。再者，與現有遊戲引擎（不限於 Unreal Engine 5）的整合彈性、生成結果的可編輯性，以及對不同硬體平台的相容性，都是影響產品實用性的關鍵。最後，運算成本與生成時間也是商業化時必須權衡的工程問題。

**Q12：Code2Games 對相關學術領域會產生什麼影響？**
A：Code2Games 對多個學術領域都有推動作用。在代理式軟體生成領域，它示範了如何透過多代理分工與共享表徵來處理長程、多模態的複雜任務，為後續研究提供了方法論參考。在遊戲 AI 領域，它填補了「世界模型」（如 Genie、DIAMOND、GameNGen）與「可編輯、可執行的遊戲專案」之間的鴻溝，將生成從「觀察預測」推進到「系統建構」。此外，GameCode4D 基準測試本身也為遊戲世界生成提供了標準化的評估協議，有助於後續研究的公平比較。

**Q13：Code2Games 存在哪些已知的限制？**
A：Code2Games 的限制主要來自幾個方面：其一，目前僅支援 Unreal Engine 5 作為目標引擎，對於使用 Unity、Godot 等其他引擎的開發者而言適用性受限。其二，GameCode4D 基準測試僅包含十個遊戲提示詞，雖然涵蓋了多種類型，但相較於真實遊戲世界的多樣性仍屬有限。其三，框架對於極度複雜的開放世界場景（如 Minecraft、Assassin's Creed 類型）可能仍會面臨挑戰，因為這類場景的實體數量與可執行行為數量都非常龐大。

**Q14：Code2Games 可能會在哪些情境下失敗？**
A：Code2Games 可能在以下情境中遭遇困難：當自然語言意圖本身極為模糊或內部矛盾時，前期的遊戲機制規劃可能產生不一致的規格，進而影響後續生成。當遊戲場景需要高度風格化或非現實的視覺效果時，基於 Blender 基礎場景的分析可能無法準確捕捉設計意圖。此外，在引擎適配階段，若生成的遊戲邏輯過於複雜，僅靠編譯診斷與執行回饋可能不足以修復所有錯誤，特別是涉及深層語意或玩家體驗層次的問題。

**Q15：Code2Games 未來可以朝哪些方向發展？**
A：未來的發展方向可從幾個維度展開：在引擎支援上，可擴展至 Unity、Godot 等其他主流引擎，提升框架的通用性。在場景複雜度上，可進一步處理更大規模的開放世界、更細緻的 NPC 行為與更複雜的遊戲機制。在評估方法上，可發展更自動化的遊戲機制測試與玩家體驗量化指標。此外，結合強化學習或人類回饋（RLHF）來持續優化代理的決策，以及探索多模態輸入（如文字結合圖像、草圖）來豐富意圖表達，都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **獨立遊戲與原型快速驗證**：獨立開發者或小型工作室可透過自然語言描述遊戲概念（如「在懸崖寺廟中奔跑閃避障礙」），由 Code2Games 自動生成可執行的 Unreal Engine 5 原型，大幅縮短從概念到可玩版本（playable build）的時間，從原本數週縮短至數小時。

2. **教育與訓練用遊戲化教材**：教師或教育內容設計者可輸入教學情境（如「第一人稱射擊練習辨識化學元素」），自動生成具備互動邏輯的客製化學習遊戲，無需聘請專業遊戲開發團隊即可產出符合課程目標的互動教材。

3. **建築與城市規劃的可互動視覺化**：建築師與都市規劃師可將 Blender 場景模型導入框架，自動生成具備導航、探索、任務目標的可互動展示版本，讓業主或評審委員能以「遊戲化」方式體驗設計提案，而非僅觀看靜態渲染圖。

4. **VR/AR 體驗快速打樣**：沉浸式內容團隊可利用框架的「場景-遊戲機制對應」機制，確保 3D 場景中的物件與互動邏輯一致，避免出現「看得到但碰不到」或「可互動但無對應視覺物件」的不一致問題，加速 VR/AR 體驗的概念驗證。

5. **遊戲設計教學與競賽**：遊戲設計系所可採用 GameCode4D 基準的十個固定提示詞作為標準化作業或競賽題目，讓學生在統一基準下比較不同代理架構或提示工程策略所生成遊戲世界的品質差異。

### 實作前置條件

**資料準備**
- 至少一份由 Blender 產生的基礎 3D 場景（.blend 檔或可匯出的 FBX/glTF 格式），需與目標遊戲意圖在主題上對齊。
- 結構化的自然語言遊戲意圖描述，建議涵蓋遊戲類型（戰鬥/探索/移動穿越/競速）、視角（FPS/TPS）、核心目標與關鍵互動物件。
- 目標遊戲引擎（建議 Unreal Engine 5）的專案範本與必要的插件配置。

**運算資源**
- 可調用的大型語言模型 API（建議支援長上下文與工具呼叫的模型，如 GPT-4 級別或開源替代方案如 Qwen2.5-Coder、DeepSeek-Coder）。
- 執行 Unreal Engine 5 的工作站（建議具備 NVIDIA RTX 3070 以上 GPU、32GB RAM，以支援編譯與執行階段回饋）。
- 自動化測試環境（headless 或批次模式啟動 UE5 的能力），用於執行導引重建（Execution-Guided Reconstruction）流程。

**技能門檻**
- 熟悉 Blender 基本操作與場景匯出流程。
- 具備 Unreal Engine 5 的 Blueprint 或 C++ 基礎，能理解代理輸出的引擎配置。
- 具備 LLM 代理（agent）設計經驗，包括提示工程、工具呼叫與多代理協調。
- 基本的遊戲設計素養，能判斷「場景實體數量」與「可執行行為數量」是否合理（參考圖 2 的複雜度分布）。

### 實作步驟建議

1. **定義遊戲意圖與基礎場景**：撰寫結構化的自然語言遊戲意圖，並在 Blender 中產出對應的基礎場景。建議先以 GameCode4D 的十個固定提示詞之一作為起點，驗證流程可行性後再擴展至自訂場景。

2. **部署 Scene Analysis Agent**：將基礎場景輸入場景分析代理，提取空間區域、物件清單、可達性關係與互動可供性（interaction affordances）。此階段輸出將作為後續約束條件的基礎。

3. **執行 Gameplay Planning Agent**：將自然語言意圖轉換為結構化的遊戲規格，包含目標、角色（actors）、遊戲機制元素與互動規則。建議保留中間輸出以便除錯。

4. **執行 Gaming World Generation Agent**：在場景分析與遊戲規劃的雙重約束下，實例化場景元素與遊戲元件。此階段需透過共享場景-遊戲機制表徵（Shared Scene-Gameplay Representation）維持持續性元素對應（Persistent Element Correspondence）。

5. **執行 Gaming Engine Customization Agent**：將生成的遊戲世界適配至 Unreal Engine 5，重建引擎端的 actors、配置檔與遊戲邏輯，同時保留前述元素對應關係。

6. **執行導引重建迴圈**：編譯並啟動生成的 UE5 專案，收集編譯診斷資訊、執行階段回饋與遊戲機制測試結果，定位並修復場景實現、actor 綁定、配置檔與遊戲規則中的不一致。

7. **以 GameCode4D 評估協議驗證**：沿視覺品質、互動保真度、多模態產出品質、可玩遊戲品質四個維度進行系統化評估，並與基線方法（如直接由程式碼代理生成）比較。

8. **迭代與優化**：根據評估結果調整提示詞、代理分工或基礎場景品質，重複步驟 2–7 直到達到目標品質門檻。

### 潛在風險與注意事項

- **空間推理幻覺（hallucination）**：LLM 可能在判斷物件可達性或空間關係時出錯，導致遊戲目標被綁定至不可達區域。**緩解方式**：在 Scene Analysis Agent 中加入幾何驗證步驟，並對關鍵空間關係進行人工抽樣檢查。

- **引擎適配錯誤連鎖反應**：UE5 編譯錯誤可能源自上游任一代理的輸出，錯誤定位困難。**緩解方式**：建立結構化日誌系統，記錄每個代理的中間輸出與對應的編譯錯誤，便於回溯。

- **執行階段回饋的非確定性**：遊戲執行結果可能因隨機性或時序問題而不穩定，導致重建流程反覆修復同一問題。**緩解方式**：在遊戲機制測試中固定隨機種子，並設定最大重建迭代次數以避免無限迴圈。

- **基礎場景品質瓶頸**：若 Blender 基礎場景本身存在瑕疵（如破面、比例錯誤），下游所有代理都將繼承此問題。**緩解方式**：在導入前對基礎場景進行品質檢查（網格完整性、UV、比例）。

- **成本與延遲**：多代理流程涉及多次 LLM 呼叫與 UE5 編譯，單次完整生成可能耗時數小時且 API 成本不低。**緩解方式**：採用快取機制儲存可重用的中間結果，並對簡單場景使用較小的模型。

- **複雜度上限**：圖 2 顯示 Assassin's Creed 與 Minecraft 等開放世界場景的實體與行為數量極高，現有框架可能在這些場景下表現下降。**緩解方式**：採用分區生成策略，將大型場景拆分為多個子區域分別處理。

### 與其他技術的整合建議

- **與程序化內容生成（PCG）整合**：可將 Code2Games 的遊戲世界生成結果作為 PCG 系統的種子場景，進一步生成變體或擴展內容，提升內容產出的多樣性。

- **與文字生成 3D 模型整合**：在基礎場景生成階段，可整合文字生成 3D 模型（如 Shap-E、TripoSR）來補充 Blender 中缺失的特定資產，豐富場景細節。

- **與遊戲測試自動化框架整合**：將 UE5 的自動化測試輸出（如 Gauntlet、Automation Framework）整合至執行導引重建流程，提供更結構化的測試回饋。

- **與版本控制與 CI/CD 整合**：將生成的 UE5 專案納入 Git 版本控制，並建立 CI/CD 流程，在每次代理輸出變更後自動執行編譯與冒煙測試，確保可重現性。

- **與遊戲引擎適配層抽象化**：目前框架鎖定 Unreal Engine 5，建議抽象化引擎適配層，未來可擴展至 Unity 或 Godot，降低對單一引擎的依賴。

- **與遊戲分析遙測整合**：在生成的遊戲中埋點收集玩家行為資料，回饋至代理訓練或評估流程，形成資料驅動的迭代閉環。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 2，理解「從一句話生成可玩遊戲」的核心概念與不同遊戲類型的複雜度差異。接著閱讀貢獻列表，掌握框架的四個代理分工與共享表徵的概念。實作上可從 GameCode4D 的簡單場景（如 Skiing）開始，體驗完整流程後再挑戰複雜場景。

**給 AI 工程師**：重點閱讀方法章節中四個代理的具體設計、共享場景-遊戲機制表徵的結構定義，以及執行導引重建的錯誤修復機制。建議嘗試將框架中的代理替換為不同的 LLM 或調整提示詞策略，觀察對生成品質的影響，並思考如何將多代理協調模式應用至其他領域（如機器人、模擬器）。

**給研究者**：GameCode4D 基準與四維度評估協議是值得深入研究的核心貢獻。建議分析基準中十個場景的複雜度分布（圖 2），思考現有評估指標是否足以捕捉「場景-遊戲機制一致性」，並探索如何將此框架擴展至其他引擎或多模態輸出（如語音、關卡設計文件）。

**給產品經理**：Code2Games 的核心價值在於將遊戲開發的「概念到原型」時間從數週壓縮至數小時，特別適合需要快速驗證市場假設的獨立遊戲或教育內容團隊。建議評估自身產品的痛點是否落在「概念驗證」階段，並關注框架在複雜度上限（開放世界場景）與引擎依賴性（僅支援 UE5）方面的限制，判斷是否適合導入。
