## 深度分析

#### 方法論解析

本文提出之核心方法論為「持續學習考試」(Continual Learning Exam, CLE)，其設計理念在於突破既有代理基準 (agent benchmark) 僅評估單一任務表現之侷限，轉而衡量代理在長時程任務序列中透過累積經驗所產生之能力演進。以下從幾個關鍵層面剖析其方法論設計：

**1. 任務階梯化結構 (Task Ladder)**

CLE 最具創新性之設計在於將 120 個人工撰寫任務組織為「五階梯式結構」(five-level ladder)，共形成 600 個關卡 (level)。此設計之核心精神為：代理必須通過當前關卡才能解鎖下一關，且後續關卡會引用前序關卡所產生之產出物與狀態。此結構模擬了真實專業工作流程中「任務彼此相依」之特性，例如整合 Git 儲存庫中協作者之變更、依據參與者可用性協調會議時間、跨應用程式同步專案更新等情境。

**2. 五種可遷移知識形式 (Five Forms of Transferable Knowledge)**

階梯化任務之設計圍繞五種代理可在關卡間獲取、保留與重用之知識形式：

- **工具與技能 (Tools and Skills)**：捕捉工具使用方式與任務執行流程之可重用知識，例如代理可從失敗的工具呼叫中學習並精煉其工具使用流程。
- **資料依賴 (Data Dependency)**：將後續任務連結至先前資訊與產出物，確保序列性。
- **策略 (Strategy)**：引導有效方法之選擇並避免重蹈覆轍。
- **使用者情境 (User Context)**：使任務執行對齊使用者偏好。
- **領域知識 (Domain Knowledge)**：對齊專業規則與慣例。

此五種形式對應了 LLM 代理在真實工作流程中常見之學習場景，並將抽象之「持續學習」概念具象化為可評測之行為指標。

**3. 可執行環境建構**

CLE 提供一個具備狀態保存特性之可執行環境，包含：
- 23,981 個真實輸入檔案，涵蓋 77 種檔案副檔名
- 19 個有狀態模擬應用程式 (stateful mock application)，共暴露 1,024 個 API
- 16,125 個人工撰寫評估標準 (human-authored rubric)

此環境設計之關鍵在於「狀態持久化」(persistent state)——前序動作之效果會延續至後續關卡，從而保留了真實工作流程之序列性質。這與 WildClawBench 等自動化助理基準有所不同：後者雖具備持久狀態，但本身並未建立「代理透過經驗變得更具能力」之評測機制。

**4. 雙試驗設定 (Two Trial Settings)**

為區分「單純任務解決能力」與「經驗驅動改進能力」，CLE 設計兩種試驗條件：
- **試驗一 (K=1)**：每個關卡僅允許一次提交，無診斷式回饋 (diagnostic feedback)。
- **試驗二 (K=2)**：首次提交失敗後，系統根據評分規準 (rubric) 提供診斷式回饋，代理可據此修訂 (revision) 並再次提交一次。

此對照設計使研究者能夠量化「回饋迴圈」對代理表現之增益，進而推論代理從失敗中學習之能力。

**5. 評估代理機制 (Evaluation Agent)**

提交結果由一個多輪評估代理進行評分，該代理使用工具從提交產物與最終環境狀態中萃取證據，並對照預先定義之預期結果進行核驗。此設計將「評測本身」也視為一個代理任務，從而避免了傳統基準測試中常見之「答案比對過於僵化」問題。

**6. 區塊化評測支援 (Block-Based Evaluation)**

除主設定外，CLE 亦支援「區塊」(block) 評測——任務階梯之連續片段可從任意關卡開始，並提供所需支援檔案。此設計增加了基準之靈活性，使研究者可針對特定能力子集進行評測。

#### 實驗數據解讀

**1. 評測規模與配置**

研究團隊評測了 17 種框架-模型配置 (harness-model configuration)，橫跨 4 種代理框架 (agent harness) 與 11 種前沿大語言模型 (frontier LLM) 變體。所有系統均執行相同之固定任務階梯序列，模型參數凍結，僅透過框架層之持久狀態進行學習。

**2. 主要結果**

- **最佳表現系統**：Claude Code 搭配 Opus 5，僅完成 47.67% 之關卡。
- **次佳系統**：GPT-5.6-Sol 與 GPT-5.6-Terra 在 Codex 框架下各達 33.17%。
- **回饋增益**：診斷式回饋與額外提交機會帶來 5.3 個百分點 (percentage point) 之完成率中位數增益。
- **完整階梯通過率**：表現最佳系統僅在 23.3% 之任務中完成全部五個關卡。

**3. 結果之意涵**

此數據揭示了幾項重要觀察：

**(a) 持續學習仍是前沿模型之關鍵瓶頸。** 即使配備診斷式回饋與修訂機會，最佳系統仍無法通過過半數關卡，且完整階梯通過率僅約四分之一。這顯示現有代理在「跨任務經驗累積與遷移」方面存在根本性限制，而非僅是「單一任務能力不足」之問題。

**(b) 回饋機制之增益有限。** 5.3 個百分點之中位數增益雖然統計上顯著，但相對於 47.67% 之基準線僅約 11% 相對增幅。這暗示代理雖能從失敗中獲取部分資訊，但將診斷回饋轉化為有效修正之能力仍相當薄弱。

**(c) 框架設計之影響。** 不同代理框架間之表現差異（如 Claude Code vs. Codex）顯示框架層之狀態管理、記憶機制與工具整合方式對持續學習能力具有實質影響，這為未來框架設計提供了具體優化方向。

**(d) 階梯難度之累積效應。** 23.3% 之完整階梯通過率遠低於 47.67% 之單關卡通過率，顯示隨著關卡推進，代理累積錯誤之機率呈現放大趨勢，這正是「災難性遺忘」(catastrophic forgetting) 與「經驗無法有效重用」之典型徵兆。

**4. 評測方法論之效度**

值得肯定的是，CLE 之評測採用 16,125 個人工撰寫評估標準，並由多輪評估代理進行核驗，相較於單純以最終答案比對之基準，更能捕捉代理執行流程中之細微品質差異。然而，評估代理本身亦為一個 LLM，其判斷之可靠性仍需透過與人類評分之相關性分析加以驗證（此部分在所提供之文本中未詳述）。

#### 與現有研究的比較

**1. 與通用能力基準之比較 (vs. GAIA)**

GAIA 等通用能力基準評估代理解決個別問題之能力，但任務間相互獨立，其分數反映「任務解決表現」而非「透過持續學習改進之能力」。CLE 之階梯化設計明確將「經驗累積」納入評測維度，填補了「評測缺口」(evaluation gap)。

**2. 與記憶基準之比較 (vs. LoCoMo)**

LoCoMo 等記憶基準透過問答形式測試代理對互動歷史之擷取與推理能力，但並未評估「保留之知識如何改善後續任務執行」。CLE 將記憶機制內嵌於任務階梯中，使「記憶」與「任務執行」形成閉環，從而能直接衡量知識保留對實際表現之影響。

**3. 與自動化助理基準之比較 (vs. WildClawBench)**

WildClawBench 等 Claw 自動化助理基準評估代理在可執行環境中之表現，具備持久狀態、長鏈工具使用軌跡 (long tool-use trajectory) 與跨應用程式工作流程 (cross-application workflow)。然而，持久狀態雖支援工作流程之連續性，但本身並未建立「代理透過經驗變得更具能力」之評測機制。CLE 之貢獻在於將「狀態持久化」與「能力演進測量」結合，使兩者形成可量化之因果關係。

**4. 與持續學習傳統研究之比較**

在神經網路時代，持續學習研究主要關注「災難性遺忘」問題，即模型在學習新任務時遺忘舊任務之現象。CLE 將此問題重新框架為「代理在長時程任務序列中能否有效重用先前經驗」，並透過階梯化任務設計使此問題可在代理框架脈絡下被實證檢驗。

**5. 與遞迴自我改進 (RSI) 研究之關聯**

論文標題提及「長時程遞迴自我改進」(Long-Horizon RSI)，此概念源自於探討 AI 系統能否透過自身經驗持續改進自身能力之研究路線。CLE 為此路線提供了首個大規模、可控之實證評測平台，使研究者能區分「真正之自我改進」與「單純之任務執行」。

**6. 限制與不足**

儘管 CLE 在設計上具有多項創新，仍存在若干限制：
- **領域覆蓋偏差**：12 個職業領域與 89 個專業角色雖具規模，但可能無法完全代表所有專業工作流程類型。
- **模擬環境之保真度**：19 個模擬應用程式雖暴露 1,024 個 API，但與真實軟體環境相比仍有差距，可能低估或高估代理在真實部署中之表現。
- **評估代理之可靠性**：評估代理本身為 LLM，其判斷可能存在系統性偏差。

企業在部署內部 AI 助理（法務、客服、研發、財務等部門）前，可採用 CLE 的「五階梯式任務」結構設計部門專屬評測包：Level 1 為基礎操作（讀檔、查詢），Level 2–3 為單一工具熟練度，Level 4 為跨工具協作，Level 5 為需整合先前經驗的綜合任務。透過「必須過關才能解鎖下一階」的設計，能精準定位代理在真實工作流中「卡關」的具體環節。

**2. AI 代理產品的版本回歸測試**
當團隊迭代代理框架（harness）時（例如新增長期記憶模組、修改反思機制），可將 CLE 的 600 個關卡作為回歸測試套件，比較不同版本在「累積經驗後」的表現差異。論文中 K=1 與 K=2 的對照實驗（5.3 百分點中位數增益）正是此類 A/B 測試的標準範本。

**3. 持續學習（Continual Learning）研究的事後訓練資料來源**
論文明確指出 CLE 可用於「post-train LLMs to strengthen their continual learning capabilities」。研究團隊可將 120 個任務階梯的提交軌跡、診斷回饋、修訂過程整理成高品質的監督式微調（SFT）或強化學習（RL）資料集，特別針對「從失敗中學習」的能力進行優化。

**4. 客戶專屬 AI 工作流程的標註與驗收**
系統整合商（SI）或顧問公司在為客戶導入 AI 代理時，可參考 CLE 的「16,125 條人工評分規準」方法論，邀請領域專家撰寫「單一明確預期結果 + 所需證據」的驗收條目，作為專案交付的客觀驗收依據，避免「AI 看起來有做但沒做對」的爭議。

**5. 跨領域代理泛化能力的基準對標**
新創公司或研究單位若宣稱自家代理「具備跨領域專業能力」，可使用 CLE 涵蓋的 12 個職業領域（89 個專業角色）作為公開對標基準，產出可與論文中 17 種框架-模型配置直接比較的數據。

### 實作前置條件

**資料面**
- **領域專家網絡**：至少需 5–10 位具備 3 年以上實務經驗的從業者，負責撰寫任務、評分規準與核驗。論文動員 50+ 專家，規模可依產品範疇縮減，但單一領域建議不少於 3 位以避免單一觀點偏誤。
- **真實工作檔案**：CLE 使用 23,981 個真實輸入檔案（涵蓋 77 種副檔名）。實務上需取得去識別化後的客戶文件、合約、報表、程式碼等，且須符合隱私法規（GDPR、個資法）。
- **任務階梯設計**：每個任務需設計 5 個遞進關卡，且後續關卡必須引用前關卡的產出（Data Dependency），這是 CLE 的核心設計難點。
- **評分規準庫**：每個關卡需撰寫數十條「單一明確預期結果 + 證據來源」的評分條目，總量級為千筆以上。

**運算面**
- **代理執行環境**：需部署 19 個模擬應用程式（論文使用 1,024 個 API），可考慮以 Docker 容器化或 Mock Server 模擬。
- **評估代理（Evaluation Agent）**：需具備多輪對話、工具呼叫、檔案讀取能力的 LLM，用於比對提交結果與評分規準。
- **長時程推論資源**：單次完整評測（600 關 × 17 配置）涉及大量長上下文推論，建議預留 API 預算或自建 GPU 叢集。
- **狀態持久化層**：模擬應用需支援跨關卡的狀態保存（Git repo、行事曆、專案管理工具等）。

**技能面**
- **Prompt Engineering 與 Agent Loop 設計**：熟悉 ReAct、Reflexion 等代理架構。
- **領域流程拆解**：能將專業工作流拆解為「工具/技能、資料依賴、策略、使用者脈絡、領域知識」五類可遷移知識（論文 2.2 節的核心分類）。
- **評測方法論**：理解 rubric-based 評分、inter-rater reliability 等概念。
- **基礎後端工程**：能將模擬應用 API 化、容器化。

### 實作步驟建議

**Step 1：界定評測範疇與領域切片**
不要直接複製論文的 12 領域全量。先選定 1–2 個對業務最關鍵的職業領域（例如「軟體工程師」與「客戶成功經理」），參考 CLE 的五階梯結構設計 5–10 個任務階梯作為 MVP。

**Step 2：建構任務階梯與五類知識標註**
針對每個任務階梯，明確標註：
- Level 1–2 著重「工具與技能」（Tools/Skills）
- Level 3 引入「資料依賴」（Data Dependency）
- Level 4 加入「策略」（Strategy）與「使用者脈絡」（User Context）
- Level 5 整合「領域知識」（Domain Knowledge）

確保 Level N 的輸入依賴 Level 1–N-1 的產出，這是觸發「經驗重用」機制的關鍵。

**Step 3：建置模擬應用與狀態持久化**
挑選 3–5 個核心工具（檔案系統、Git、行事曆、專案管理、訊息），以 Mock API 形式實作，確保狀態在關卡間持續保留。論文使用 1,024 個 API，MVP 階段可縮減至 50–100 個。

**Step 4：撰寫評分規準並進行專家核驗**
每個關卡撰寫 20–50 條評分規準，每條格式為「預期結果 + 證據來源」。邀請至少 2 位專家獨立核驗，計算 Cohen's Kappa 確保一致性（目標 κ > 0.7）。

**Step 5：建立評估代理與雙盲評測流程**
實作一個獨立的「評估代理」，賦予其讀取提交檔案、呼叫模擬應用 API、對照評分規準的能力。採用雙盲設計：執行代理與評估代理使用不同模型，避免評估偏誤。

**Step 6：執行 K=1 與 K=2 對照實驗**
參考論文設定：
- **K=1**：每關僅一次提交機會，測試「一次性解決能力」。
- **K=2**：首次失敗後提供診斷回饋，允許一次修訂，測試「從回饋學習能力」。

比較兩種設定的完成率差異（即論文的 5.3 百分點增益指標），作為代理「持續學習潛力」的量化證據。

**Step 7：產出診斷報告與迭代建議**
針對失敗關卡，輸出「失敗模式分類」（工具誤用、資料遺漏、策略錯誤、脈絡遺失、領域知識不足），對應到五類可遷移知識，作為下一輪框架優化或後訓練的具體目標。

**Step 8：將評測套件整合至 CI/CD**
將 CLE 風格的評測套件納入代理框架的版本控制流程，每次 harness 變更自動跑回歸測試，並設定完成率門檻（例如「不得低於前一版本的 95%」）作為合併條件。

### 潛在風險與注意事項

**風險 1：評測成本失控**
CLE 完整跑完 17 種配置需大量 API 呼叫與長時程推論。**緩解措施**：採用分層抽樣（stratified sampling），先以 20% 任務子集做快速篩選，僅對通過篩選的配置跑完整 600 關。

**風險 2：評分規準的主觀性與漂移**
即使有專家核驗，rubric 仍可能隨時間漂移或在不同評估代理間產生不一致。**緩解措施**：建立「黃金標準」提交樣本（每關 1–2 個完美提交 + 1 個典型失敗提交），定期用於校準評估代理；每季重新檢視 rubric 一致性。

**風險 3：任務階梯設計的「捷徑漏洞」**
代理可能學會「跳關」或「猜測」而非真正累積經驗。**緩解措施**：在 Level N 的輸入中明確要求引用 Level 1–N-1 的具體產出（例如「基於 Level 3 產出的客戶分類結果」），並在 rubric 中驗證引用鏈。

**風險 4：模擬應用與真實環境的差距（Sim-to-Real Gap）**
論文使用 mock 應用，無法完全模擬真實軟體的邊界情況。**緩解措施**：在 MVP 通過後，於小規模真實環境（沙盒化客戶資料）進行第二輪驗證。

**風險 5：模型過擬合特定任務類型**
若將 CLE 用於後訓練，模型可能在 12 領域的特定任務上表現提升，但泛化能力下降。**緩解措施**：保留 20% 任務作為 holdout 集，並監控通用基準（如 MMLU、HumanEval）的退步幅度。

**風險 6：診斷回饋的「洩漏」問題**
K=2 設定中，回饋內容若過於詳細，等同於直接告訴代理答案。**緩解措施**：參考論文做法，僅提供「哪條 rubric 未通過」與「證據缺失位置」，不直接給出正確做法。

**風險 7：領域專家參與的持續性**
CLE 仰賴 50+ 專家撰寫與核驗，專家時間成本高且難以長期維持。**緩解措施**：建立「專家貢獻積分」制度、提供署名權、或將部分 rubric 撰寫工作交由資深從業者以顧問費形式外包。

### 與其他技術的整合建議

**1. 與既有代理評測框架整合**
- **與 GAIA、LoCoMo 的互補定位**：GAIA 測單題能力、LoCoMo 測記憶檢索、CLE 測累積改進。三者可組成「能力 × 記憶 × 學習」三維評測矩陣。
- **與 SWE-bench、HELM 整合**：SWE-bench 測程式修復能力，可作為 CLE「軟體工程師」領域的子基準；HELM 提供跨模型透明度，可作為 CLE 結果的視覺化呈現層。

**2. 與後訓練流程整合**
- **SFT 資料增強**：將 CLE 的「失敗提交 + 診斷回饋 + 修訂後成功提交」三元組整理為 SFT 資料，訓練模型「從錯誤中修正」的能力。
- **RLHF / RLHF-RLAIF 獎勵信號**：以 CLE 的完成率與 rubric 通過率作為獎勵函數，進行 RL 優化。
- **DPO（Direct Preference Optimization）**：將「失敗提交」標為 rejected、「修訂後成功提交」標為 chosen，訓練偏好對齊。

**3. 與企業知識管理系統整合**
- **與 Confluence / Notion 整合**：將 CLE 任務階梯中標註的「領域知識」與「使用者脈絡」連結至企業 Wiki，使代理在執行任務時可自動檢索相關規範。
- **與 CRM / ERP 整合**：模擬應用可改為真實系統的唯讀 API 代理層，在保護資料的前提下提供更真實的工作環境。

**4. 與可觀測性（Observability）平台整合**
- **與 LangSmith、Langfuse 整合**：記錄代理在每個關卡的工具呼叫軌跡、反思日誌、技能庫更新，支援後續錯誤分析。
- **與 OpenTelemetry 整合**：將 CLE 評測結果匯入企業 APM 平台，追蹤代理能力隨時間的演進。

**5. 與多代理（Multi-Agent）架構整合**
- CLE 預設為單一代理，可擴展為「執行代理 + 反思代理 + 評估代理」的多代理架構，其中反思代理專門負責 lesson extraction，評估代理獨立於執行代理以避免偏誤。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節，理解「為什麼需要持續學習評測」這個問題的動機（單題表現 ≠ 累積改進）。接著重點看第 2.2 節的「五類可遷移知識」分類，這是理解整篇論文任務設計的鑰匙。數學公式（2.1 節的形式化定義）可先跳過，待實際接觸代理框架後再回頭理解。

**給 AI 工程師**：直接從第 3 節（實驗設定）讀起，特別關注 K=1 與 K=2 的對照實驗設計，這是評測自家代理的標準範本。接著仔細研究 17 種框架-模型配置的差異，理解 harness 設計（長期記憶、反思、技能庫）對持續學習能力的影響。建議將論文的 5.3 百分點增益作為自家產品的 baseline 對標。

**給研究者**：第 2.1 節的形式化定義與第 2.2 節的五階能力層級是理論貢獻的核心，值得深入推敲。實驗章節的失敗模式分析（為何最佳系統僅 47.67%）是後續研究的開放問題。建議將 CLE 與 catastrophic forgetting、in-context learning、meta-learning 等既有文獻連結，思考如何擴展五階能力層級或設計新的評測維度。

**給產品經理**：重點閱讀第 1 節的「現有評測缺口」論述，理解為何 GAIA、LoCoMo 等基準無法直接回答「我們的代理是否會越用越好」這個產品核心問題。接著看實驗結果的商業意涵：即使最強代理也只能完成 47.67% 關卡，代表市場上「真正具備持續學習能力的 AI 助理」仍是藍海，產品定位可考慮聚焦於「特定垂直領域的累積改進」而非追求通用能力。
