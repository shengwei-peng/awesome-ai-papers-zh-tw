## 摘要翻譯

代理記憶體（Agent memory）通常透過離線精選示範，或透過在線部署後互動來構建。然而，無論採用何種方式，當代理首次被引入新環境且無任何任務特定經驗可用時，都會面臨冷啟動落差（Cold-start gap）。本文中，我們研究任務前記憶構建（Pre-task memory construction）：代理能否在觀察任何目標環境任務之前，僅使用自我生成合成練習（Synthetic practice）來建立程序性記憶（Procedural memory）。然而，僅靠合成互動並不足夠，因為若不控制練習內容與儲存內容，合成任務會變得冗餘、不可行，最終無資訊性，且記憶體會因未過濾軌跡而迅速退化。為克服此問題，我們提出 Preping，一個提議者引導式記憶構建框架（Proposer-guided memory construction framework）。其核心為提議者記憶體（Proposer memory）——一個結構化控制狀態（Structured control state），用於塑造未來練習。提議者（Proposer）以此狀態為條件生成合成任務，求解者（Solver）執行這些任務，驗證者（Validator）則決定哪些軌跡（Trajectory）符合記憶體插入（Memory insertion）資格，同時提供回饋以引導未來提案。在 AppWorld、BFCL v3 和 MCP-Universe 上的實驗顯示，Preping 大幅優於無記憶體基準（No-memory baseline），其效能與基於離線或在線經驗建構的強大的劇本式方法（Playbook-based methods）不相上下，且在 AppWorld 與 BFCL v3 上的部署成本分別僅為在線記憶構建（Online memory construction）的 1/2.99 與 1/2.23。進一步分析顯示，主要效益並非僅來自合成量（Synthetic volume），而是來自提議者端控制（Proposer-side control）對可行性（Feasibility）、冗餘性（Redundancy）與覆蓋率（Coverage）的控制，結合選擇性記憶體更新（Selective memory updates）。

### 核心貢獻（3～5點）
- 提出任務前記憶構建（Pre-task memory construction）的新範式，使代理能在觀察任何目標環境任務之前，僅憑自我生成合成練習建立程序性記憶，有效緩解冷啟動落差。
- 設計 Preping 框架，以提議者記憶體（Proposer memory）作為結構化控制狀態，協調提議者（Proposer）、求解者（Solver）與驗證者（Validator）三方協作，實現對練習內容與儲存內容的雙重控制。
- 在 AppWorld、BFCL v3 與 MCP-Universe 三項基準測試上驗證效能，Preping 大幅優於無記憶體基準，並達到與基於離線或在線經驗的劇本式方法相當的具競爭力的效能，同時大幅降低部署成本。
- 透過分析揭示，主要效益並非來自合成量本身，而是源於提議者端對可行性、冗餘性與覆蓋率的控制，結合選擇性記憶體更新機制。

### 適合對象
本研究適合從事大語言模型代理（LLM agents）、代理記憶體機制、工具使用學習與自動化工作流程設計的研究人員與工程師閱讀；亦適合關注代理部署效率、冷啟動問題（Cold-start problem）緩解策略，以及如何在缺乏任務特定資料時建構可重用程序性知識的實務團隊參考。

## 深度分析

#### 方法論解析

PREPING（Pre-Task Reusable Playbook Making）的核心設計動機在於解決代理記憶體（agent memory）建構中的「冷啟動落差（cold-start gap）」問題。傳統的記憶體建構方式——無論是離線（offline）依賴策展示範（curated demonstrations），還是在線（online）依賴部署後互動（post-deployment interactions）——都假設目標環境的任務經驗已存在或即將產生。然而在新連接的環境（newly connected environments）中，這類經驗往往付之闕如，使得代理在首次部署時處於「空白記憶體（empty memory）」狀態，必須承受早期失敗（early failures）與記憶體更新延遲（memory-update latency）的雙重成本。

PREPING 提出「任務前記憶構建（pre-task memory construction）」的新範式：在觀察任何目標環境任務之前，僅透過自我生成的合成練習（self-generated synthetic practice）來建立可重用的程序性記憶（procedural memory）。此設定與單純提早進行在線記憶建構有本質差異——代理缺乏任務指令作為直接信號，無法得知哪些用戶目標將出現、哪些工具應被組合、或何謂成功的任務級工作流程。

**框架架構的四個關鍵模組：**

1. **提議者記憶體（proposer memory）**：作為建構階段的結構化控制狀態（structured control state），負責追蹤先前的合成練習歷史與環境資訊。此狀態是整個框架的「記憶中樞」，決定後續練習的方向。

2. **提議者（Proposer）**：以提議者記憶體為條件，生成可行的合成任務（synthetic tasks），朝環境中尚未充分探索的面向擴展覆蓋率（coverage）。此處的設計重點在於「提議者端控制（proposer-side control）」——避免任務變得冗餘（redundant）、不可行（infeasible）或與環境脫節。

3. **求解者（Solver）**：執行提議者生成的合成任務，產生對應的軌跡（trajectories）。

4. **驗證者（Validator）**：在軌跡進入記憶體插入（memory insertion）之前進行過濾，剔除不可行的任務軌跡，並提供回饋（feedback）以引導未來提案（future proposals）。這構成「驗證者閘控的記憶體納入（validation-gated memory admission）」機制。

5. **記憶體更新模組（memory update module）**：將通過驗證的軌跡蒸餾為求解者記憶體（solver memory），即未來任務使用的可重用程序性記憶。

**方法論的關鍵洞見：** PREPING 並非將任務前記憶構建簡化為「合成任務生成問題」，而是將其定位為「聯合塑造練習內容與儲存內容」的雙重控制問題。這體現在兩個層面：（1）練習控制（practice control）——透過提議者記憶體引導任務分布；（2）儲存控制（storage control）——透過驗證者過濾軌跡品質。若僅有大量合成互動（synthetic interaction）而無控制，合成任務將變得冗餘、不可行且最終無資訊性（uninformative），而記憶體更會因未過濾軌跡（unfiltered trajectories）而快速退化（memory degradation）。

#### 實驗數據解讀

PREPING 在三個互補的基準測試上進行評估，涵蓋三種截然不同的代理執行環境：

1. **AppWorld**：有狀態的應用程式執行環境，考驗代理在多步驟互動中維持狀態一致性的能力。
2. **BFCL v3**：結構化函式呼叫（structured function calling）基準，評估精確的工具呼叫組合。
3. **MCP-Universe**：真實的 MCP 伺服器工具使用情境，測試代理在異質工具生態中的泛化能力。

**主要量化結果：**

- **相對於無記憶體基準（no-memory baseline）的提升**：AppWorld 提升 17.1 點、BFCL v3 提升 19.3 點、MCP-Universe 提升 5.4 點。這顯示 PREPING 在不同環境特性下皆能帶來實質改善，且在結構化函式呼叫（BFCL v3）上的相對增益最大，暗示程序性記憶對於精確工具組合的價值尤為顯著。
- **與劇本式方法（playbook-based methods）的競爭力**：PREPING 在無需任何目標任務經驗的前提下，效能與依賴離線或在線經驗建構的強基線相當。這是方法論層面的重要成就——證明了「零樣本任務經驗」路徑的可行性。
- **部署成本（deployment cost）降低**：相較於 ACE-Online，PREPING 在 AppWorld 上降低 2.99 倍、在 BFCL v3 上降低 2.23 倍的部署成本。此數據反映 PREPING 作為凍結式任務前記憶體（frozen pre-task memory）的實用價值——無需在部署時持續更新，大幅節省運算資源。

**工具覆蓋率（tool coverage）的縱向分析（圖 1 右側）：**

此圖揭示了 PREPING 與 ACE-Online 在工具探索效率上的根本差異：
- 在 AppWorld Test-Normal 上，PREPING 在部署前即達到 87 個唯一工具覆蓋率，而 ACE-Online 需要 58 個用戶面臨任務（user-facing tasks）才能追上此水準。
- 在 BFCL v3 Base 上，PREPING 達到 101 個唯一工具覆蓋率，而 ACE-Online 即使經過 200 個任務仍未追上。

此結果的意涵深遠：它量化了「冷啟動緩解（cold-start mitigation）」的具體效益——PREPING 不僅在最終效能上具競爭力，更在探索效率上展現數倍優勢，這對於資源受限或時間敏感的部署場景尤為關鍵。

**消融實驗的關鍵發現：**

實驗明確指出，主要效益並非來自合成量（synthetic volume）本身，而是來自兩個機制的耦合：（1）驗證者閘控的記憶體納入；（2）提議者端對可行性、工具覆蓋率與下游相關性的控制。這意味著單純增加合成任務數量並非有效策略——品質控制與分布塑造才是核心。

**PREPING+ACE 的混合模式：**

將 PREPING 作為 ACE 的初始化，在 AppWorld 上將效能從 71.3 提升至 76.3，同時減少早期冷啟動失敗與工具覆蓋率不足問題。此結果驗證了 PREPING 與在線方法的互補性——任務前記憶體提供了穩固的起點，在線更新則在此基礎上持續精煉。

#### 與現有研究的比較

**定位差異化：**

現有代理記憶體研究——包括 Agent Workflow Memory（誘導可重用工作流程）、ACE（透過結構化生成、反思與策展成長劇本式上下文）以及其他持久記憶體（persistent memory）、工作流程知識（workflow knowledge）、劇本式指引（playbook-style guidance）等形式——共同假設「目標環境任務經驗」的存在，無論其形式為策展示範、記錄軌跡、成功工作流程或在線用戶互動。PREPING 的根本差異在於研究「前述冷啟動階段」：在任何人類提供或部署時的目標任務出現之前建構可重用程序性記憶。

**相較於離線方法的優勢：**

離線記憶體建構依賴人類為每個環境設計、收集或解決任務，成本高昂且在部署前通常不可得。PREPING 完全消除了此前期投入（upfront effort），同時達到具競爭力的效能。

**相較於在線方法的優勢：**

在線方法從空白記憶體開始，僅在用戶任務到達後學習，導致用戶暴露於早期失敗、記憶體更新延遲與額外的部署時成本（deployment-time costs）。PREPING 透過預先建構記憶體，將這些問題前置消化——「記憶體最被需要的時刻，正是建構它所需的經驗尚未被收集的時刻」正是論文對此困境的精準描述。

**自我生成練習與策略更新的關聯：**

PREPING 與「自我生成練習用於策略更新（self-generated practice for policy updates）」的研究路線有交集，但後者通常聚焦於更新模型參數（如強化學習中的自我對練），而 PREPING 聚焦於建構外部可檢視、可修訂、可跨模型轉移的可重用記憶體（reusable memory）。此差異使 PREPING 更具實務部署性——無需重新訓練底層模型。

**限制與未明示的邊界：**

- 論文未深入討論提議者記憶體的具體結構與容量管理機制，若其規模隨環境複雜度線性增長，可能成為瓶頸。
- 驗證者的判斷標準與其依賴的環境回饋信號類型未充分闡述，這影響方法在不同環境間的可移植性。
- 對於極度開放或動態變化的環境（如即時演化的 API 生態），合成練習的時效性與代表性可能受限。

#### 可重現性評估

**程式碼與資料可用性：**

根據論文提供的資訊，專案頁面（project page）已標示，但具體的開源狀態需進一步確認。論文提及在三個公開基準（AppWorld、BFCL v3、MCP-Universe）上進行實驗，這些基準本身是可取得的，這有利於獨立驗證。

**模型權重：**

PREPING 的設計似乎不涉及新的模型訓練，而是建構外部記憶體結構，因此核心可重現性依賴於：（1）提議者、求解者、驗證者的提示工程（prompt engineering）細節；（2）提議者記憶體的具體表示格式；（3）記憶體更新模組的蒸餾邏輯。這些細節在論文中是否充分揭露，將直接影響第三方重現的可行性。

**實驗設定的透明度：**

論文提供了具體的數值結果（17.1、19.3、5.4 點提升；2.99×、2.23× 成本降低；71.3→76.3 的混合模式增益），但完整的超參數、隨機種子設定、評估協議細節需在附錄或程式碼倉庫中確認。對於涉及多模組互動的框架，端到端可重現性通常需要程式碼與資料的雙重釋出。

**基準測試的代表性：**

三個基準涵蓋有狀態執行、結構化函式呼叫、MCP 工具使用，但對於其他類型的代理環境（如網頁瀏覽、程式碼生成、機器人控制）的泛化性仍待驗證。

#### 未來研究方向

**1. 提議者記憶體的理論化與可擴展性：**

目前提議者記憶體作為「結構化控制狀態」的設計較為啟發式，未來可探索其資訊理論基礎——例如以資訊增益（information gain）或貝氏最優實驗設計（Bayesian optimal experimental design）原則指導任務提案，使覆蓋率擴展更具原則性。同時，需研究其在高維環境中的壓縮與層次化表示，避免規模瓶頸。

**2. 驗證者的多層次品質控制：**

當前驗證者主要過濾「不可行」軌跡，未來可擴展為多層次品質評估：（1）軌跡正確性（是否達成任務）；（2）軌跡效率（步驟數是否最優）；（3）軌跡可重用性（是否包含可泛化的程序性知識）。這將使記憶體納入標準從「二元過濾」進化為「品質分級」。

**3. 跨環境遷移學習：**

若任務前記憶體可在相似環境間遷移（如不同 MCP 伺服器、不同應用程式類別），將大幅降低新環境的部署成本。未來可研究記憶體蒸餾、抽象化與領域自適應技術，使 PREPING 建構的記憶體具備跨環境可移植性。

**4. 與在線學習的深度融合：**

PREPING+ACE 的初步結果顯示混合模式的潛力，未來可探索更緊密的耦合機制——例如讓在線更新不僅精煉記憶體，更回饋修正提議者策略，形成「建構-部署-反思-重建」的閉環。

**5. 動態環境下的時效性管理：**

對於 API 版本更新、工具介面演化的場景，合成練習可能產生過時的程序性知識。未來可研究記憶體的時效性標記、自動失效偵測與增量更新機制，使 PREPING 適用於長期部署的代理系統。

**6. 安全與對齊考量：**

自我生成的合成任務若缺乏安全約束，可能產生有害或越權的探索行為。未來需將安全驗證整合至驗證者模組，確保記憶體建構過程不違反環境政策或產生可被惡意利用的程序性知識。

**7. 理論分析與形式化保證：**

目前 PREPING 的效能保證主要來自實驗觀察，未來可探索其收斂性、樣本複雜度（sample complexity）與最優性差距的形式化分析，為方法提供理論基礎。

**8. 人機協作建構：**

在某些高風險環境中，完全自主的合成練習可能不足。未來可探索人類專家如何介入提議者記憶體的初始化或驗證者的標準設定，使 PREPING 在自主性與安全性間取得平衡。

## 論文問答

**Q1：什麼是代理記憶體建構中的「冷啟動問題」？**
A：冷啟動問題指的是當一個 LLM 代理首次被部署到一個全新的環境時，由於缺乏任何任務特定的經驗或示範資料，代理必須從空白狀態開始摸索可用工具、API 與工作流程，這使得初期執行任務時容易發生錯誤並累積昂貴的失敗成本。傳統的記憶體建構方法——無論是離線從策展示範中學習，還是在線從部署後的用戶互動中累積——都假設已有目標環境的任務資料可供使用，但這對於剛連線的新環境而言恰恰不存在。PREPING 論文正是要解決這個「記憶體最被需要時，卻恰好沒有經驗可用來建立它」的矛盾情境。

**Q2：為什麼現有的離線與在線記憶體建構方法無法有效處理冷啟動？**
A：離線方法依賴人類事先為每個環境設計、收集或解決任務，這需要大量前期投入且在部署前往往難以取得，因此無法應對新連接環境的即時需求。在線方法雖然免除了前期成本，但卻從空白記憶體開始，必須等用戶實際下達任務後才能學習，這會導致用戶在初期面臨較高的失敗率、記憶體更新延遲以及額外的部署時成本。兩種方法的共同限制在於：它們都假設目標環境的任務經驗已經存在，而 PREPING 強調的是在這類經驗出現之前就應該建構可重用的程序性記憶。

**Q3：為什麼任務前記憶體建構（pre-task memory construction）的研究具有重要性？**
A：任務前記憶體建構讓代理能在觀察任何目標環境任務之前，就透過自我生成的合成練習建立程序性知識，這對於企業級代理部署尤其關鍵，因為新環境上線時往往沒有現成的示範資料。透過提議者引導的合成練習與驗證者把關的軌跡篩選，PREPING 能夠在零人類任務資料的條件下產出與離線或在線方法相當的記憶體品質。這項研究的意義在於：它把記憶體建構從「被動等待經驗累積」轉變為「主動塑造練習分布」，從而大幅縮短冷啟動期並降低部署成本。

**Q4：PREPING 框架的核心架構為何？**
A：PREPING 框架由三個核心模組組成：提議者（Proposer）根據提議者記憶體中的結構化控制狀態生成可行的合成任務；求解者（Solver）執行這些任務並產生軌跡；驗證者（Validator）則篩選掉不可行的軌跡，僅讓合格的軌跡進入記憶體插入流程，並提供回饋給提議者以引導未來的提案方向。這種「提議—執行—驗證」的閉環設計使得練習內容與儲存內容都被主動控制，而非任由隨機探索產生冗餘或誤導性的資料。

**Q5：提議者記憶體（proposer memory）的關鍵創新是什麼？**
A：提議者記憶體是一個結構化的控制狀態，它追蹤先前的合成練習歷史與環境資訊，使提議者能夠有意識地擴展尚未充分探索的環境面向，而非重複練習已熟悉的工具組合。這個設計的關鍵創新在於：它把「該練習什麼」與「該儲存什麼」這兩個耦合的控制問題分開處理，並透過提議者端的可行性、冗餘性與覆蓋率控制來塑造未來的練習分布。實驗結果顯示，主要效益並非來自合成量本身，而是來自這種提議者端的精細控制結合選擇性記憶體更新所帶來的綜效。

**Q6：PREPING 在設計上做了哪些關鍵選擇以兼顧效率與品質？**
A：PREPING 採用了「驗證者把關」的記憶體納入機制，避免未過濾的軌跡污染記憶體並導致記憶體退化，這是相較於單純合成任務生成方法的重要設計選擇。框架同時維持兩種記憶體：建構階段使用的提議者記憶體（用於控制練習分布）與部署階段使用的求解者記憶體（用於實際任務求解），這種分離讓兩種功能得以獨立優化。此外，PREPING 設計為可與 ACE 等在線方法組合（PREPING+ACE），既能作為凍結的預先記憶體降低部署成本，也能作為初始化來減少早期冷啟動失敗。

**Q7：實驗選用了哪些基準測試？各自涵蓋什麼樣的能力？**
A：論文選用三個互補的基準測試：AppWorld 涵蓋有狀態的應用程式執行、BFCL v3 涵蓋結構化函式呼叫、MCP-Universe 涵蓋真實的 MCP 伺服器工具使用情境。這三個基準涵蓋了 LLM 代理在真實部署中會遇到的主要環境類型，從命令列介面到工具 API 與模型上下文協議伺服器，使得實驗結論具有廣泛的代表性。選擇這三個基準也讓 PREPING 的泛化能力得以驗證——它不僅在單一環境有效，而是在多樣化的代理執行場景中都能展現穩定的效益。

**Q8：PREPING 的關鍵實驗結果為何？**
A：在三個基準測試上，PREPING 相較於無記憶體基準分別提升了 17.1 分（AppWorld）、19.3 分（BFCL v3）與 5.4 分（MCP-Universe），並達到與依賴人類定義或部署時目標任務的劇本式方法相當的競爭力。特別值得注意的是，PREPING 在 AppWorld 上僅用 58 個任務就達到了 ACE-Online 需要更多用戶任務才能累積的工具覆蓋率，而在 BFCL v3 上即使經過 200 個任務 ACE-Online 仍未能追上 PREPING 的覆蓋水準。當 PREPING 與 ACE 結合時（PREPING+ACE），AppWorld 上的表現從 71.3 進一步提升至 76.3，同時減少了早期冷啟動失敗。

**Q9：消融研究揭示了哪些關鍵設計的必要性？**
A：消融研究顯示，這些效能增益並非單獨來自合成任務生成，而是來自驗證者把關的記憶體納入機制與提議者端對可行性、工具覆蓋率與下游相關性的控制。具體而言，若移除驗證者過濾或讓提議者失去對練習分布的控制，效能會顯著下降，證明了「該練習什麼」與「該儲存什麼」這兩個控制面向缺一不可。這項發現強調了 PREPING 的核心價值在於其聯合控制機制，而非單純的合成資料量擴增。

**Q10：哪些實際應用場景最能受益於 PREPING？**
A：企業內部新接的 MCP 伺服器、第三方 API 或內部工具鏈是最直接的受益場景，因為這些環境往往缺乏預先策展的示範資料，但又需要在部署初期就提供穩定的代理表現。客服代理、IT 自動化代理、資料處理代理等需要在多變環境中快速上線的應用，也能透過 PREPING 在部署前預先建立工具使用指引與工作流程規則。此外，對於需要嚴格控制部署成本的場景（例如大規模多租戶 SaaS），PREPING 作為凍結的預先記憶體可省下 2.99 倍（AppWorld）至 2.23 倍（BFCL v3）的部署成本。

**Q11：從產品化的角度，PREPING 帶來哪些設計考量？**
A：產品化時需要考慮合成練習階段的計算成本與時間，雖然 PREPING 在部署後能省下大量成本，但建構階段仍需要執行大量合成任務並進行驗證，因此需要評估「建構成本 vs. 部署節省」的取捨。另一個考量是提議者記憶體的設計——它需要追蹤練習歷史與環境資訊，這對記憶體結構與更新策略提出了工程要求。產品設計上也應考慮讓 PREPING 與既有的在線學習機制（如 ACE）無縫整合，使代理能隨著真實用戶互動持續優化，而非僅依賴靜態的預先記憶體。

**Q12：PREPING 對代理研究領域的更廣泛影響為何？**
A：PREPING 推翻了「記憶體建構必須依賴目標任務經驗」的傳統假設，開啟了「零任務經驗記憶體建構」這個新的研究方向，並為代理的冷啟動問題提供了一條系統性的解決路徑。它也凸顯了「控制練習分布」與「控制記憶體納入」這兩個面向的重要性，這對未來設計其他自監督或自訓練的代理系統具有方法論上的啟發。更廣泛地看，這項工作呼應了代理研究中「讓代理主動塑造學習環境而非被動接受資料」的趨勢，與主動學習、自我對弈等領域的精神相契合。

**Q13：PREPING 存在哪些已承認的限制？**
A：PREPING 的效能仍受限於底層 LLM 的能力——若提議者、求解者或驗證者所使用的模型能力不足，則生成的合成任務品質、軌跡執行成功率與驗證準確度都會受到影響。框架假設環境提供可執行的工具 API 與文檔，但對於無法實際執行工具或缺乏結構化文檔的環境（例如純文字模擬或缺乏回饋的環境），PREPING 的適用性會降低。此外，雖然 PREPING 在三個基準上表現良好，但其在更複雜的多步驟、長時程任務上的可擴展性仍需要進一步驗證。

**Q14：PREPING 在哪些情境下可能會失敗？**
A：當目標環境的工具組合極其龐大且高度互依時，提議者可能難以有效識別「尚未充分探索」的面向，導致合成任務的覆蓋率提升緩慢或偏向容易執行的子集。若驗證者的判斷標準過於寬鬆，可能讓含有隱性錯誤或環境特定假設的軌跡進入記憶體，進而誤導未來的任務求解。另一個潛在失敗情境是當環境的回饋訊號稀疏或具誤導性時（例如某些工具呼叫的副作用延遲才顯現），驗證者可能無法及時識別不可行的軌跡，使得記憶體品質下降。

**Q15：PREPING 的未來研究方向為何？**
A：未來可探索更智慧的提議者設計，例如結合環境模型預測或強化學習來動態調整練習策略，使提議者能更有效率地擴展覆蓋率並降低冗餘。另一個方向是研究如何讓 PREPING 與人類示範資料或少量真實任務結合，在「零經驗」與「少量經驗」之間建立連續的光譜，使框架能適應不同程度的冷啟動情境。此外，將 PREPING 擴展到多代理協作環境、持續學習情境或跨環境遷移學習，也是值得探索的延伸方向，特別是如何讓一個環境中學到的提議者記憶體能加速另一個相關環境的記憶體建構。

## 實務應用指南

### 適用場景

1. **新 MCP 伺服器冷啟動整合**：企業剛接入一個新的 Model Context Protocol 伺服器（例如內部 CRM、ERP 或資料庫閘道），尚未累積任何真實用戶互動紀錄，但需要在第一天上線時就具備穩定的工具呼叫能力。PREPING 可在部署前自動探索工具組合並建立可重用的程序性記憶，避免用戶在初期遭遇大量失敗。

2. **多租戶 SaaS 代理的預熱部署**：SaaS 平台為每位新客戶配置一個專屬代理，但每位客戶的環境配置、權限範圍與工具集都不相同。透過 PREPING 在每位客戶的環境中預先執行一次合成練習，可在客戶首次使用前就準備好量身打造的劇本式記憶體。

3. **企業內部 API 工具鏈上線**：當企業將多個內部 API（人力資源、財務、知識庫）整合給內部助理使用時，IT 團隊可在不依賴真實員工任務的情況下，先讓代理自行練習並建立工具組合的工作流程規則，降低初期支援成本。

4. **客服代理的領域轉移**：將既有客服代理從一個產品線遷移到另一個產品線時，環境工具集完全不同。PREPING 可在新產品環境中預先建立程序性記憶，使代理在第一通電話就能運用新環境的特定程序，而非從空白記憶體開始學習。

5. **邊緣裝置或離線代理的預載記憶**：在無法即時呼叫 LLM 更新記憶體的場景（如合規要求、網路受限），可使用 PREPING 在工廠端預先生成並凍結記憶體，再部署到裝置上，兼顧部署成本與離線可用性。

### 實作前置條件

**資料需求**
- 目標環境的完整工具 schema、API 規格、文件說明
- 環境的可執行介面（sandbox、staging 環境或模擬器），供 Proposer 與 Solver 實際呼叫工具並觀察輸出
- 環境狀態資訊（資料庫快照、檔案系統、用戶帳號），讓合成任務能產生有意義的軌跡
- 評估用的目標任務集（held-out），用於驗證記憶體品質（部署階段才使用，建構階段不可見）

**運算資源**
- 具備工具呼叫能力的中大型 LLM API 存取權（建議支援 function calling 的模型）
- 充足的推理預算：建構階段需執行數百至數千次合成任務，每次包含 Proposer、Solver、Validator 三個角色的推論
- 持久化儲存空間，用於保存 proposer memory、solver memory 與軌跡日誌
- 環境執行的容器化或虛擬化基礎設施，避免合成任務污染真實環境

**技能前提**
- 熟悉 LLM 代理框架（如 LangChain、AutoGen、自建 ReAct 迴圈）
- Prompt engineering 能力，特別是結構化輸出與工具呼叫的設計
- 具備環境工程經驗，能搭建隔離的執行沙箱
- 基本的評估管線設計能力，能衡量記憶體對下游任務的增益

### 實作步驟建議

**步驟一：環境偵察與 Proposer Memory 初始化**
盤點目標環境的所有工具、其參數 schema、文件說明與可觀察的環境狀態。將這些資訊編碼成結構化的 proposer memory 初始狀態，記錄「已練習過的工具組合」、「已嘗試的任務類型」、「已知的前置條件與失敗模式」等欄位。此步驟不需任何目標任務資料。

**步驟二：設計 Proposer–Solver–Validator 三角色迴圈**
- **Proposer**：讀取 proposer memory，根據目前覆蓋率缺口與可行性約束，提案下一批合成任務。任務應具備明確目標、可驗證的成功條件，並傾向探索尚未練習過的工具組合。
- **Solver**：在隔離環境中執行任務，產出完整軌跡（工具呼叫序列、中間狀態、最終結果）。
- **Validator**：根據任務規格與環境回饋，判斷軌跡是否成功且具備納入記憶體的價值，並將驗證結果回傳給 Proposer 以調整後續提案方向。

**步驟三：驗證閘控的記憶體納入**
僅將通過 Validator 篩選的成功軌跡送入記憶體蒸餾模組。蒸餾模組應從軌跡中萃取可重用的程序性知識，例如「呼叫 A 之前必須先檢查 B 的狀態」、「失敗時的恢復路徑為 X→Y」，而非保留整段冗長軌跡。設計明確的納入與淘汰規則，避免記憶體被低品質或重複內容污染。

**步驟四：迭代直到覆蓋率收斂**
持續執行步驟二與步驟三，直到 proposer memory 顯示工具覆蓋率與任務類型多樣性達到預期門檻，或新增軌跡不再帶來實質增益。記錄每次迭代的成本與品質指標，作為後續調校的基準。

**步驟五：部署與整合**
將建構完成的 solver memory 注入實際代理的系統提示或檢索管線中。可選擇兩種部署模式：
- **凍結模式**：記憶體不再更新，部署成本最低，適合環境穩定且合規要求嚴格的場景。
- **混合模式（PREPING+ACE）**：以 PREPING 記憶體作為 ACE 等在線方法的暖啟動，兼顧冷啟動緩解與持續學習。

**步驟六：建立持續監控與再訓練觸發機制**
部署後監控代理在真實任務上的成功率、工具呼叫錯誤率與記憶體檢索命中率。當監控指標顯示環境漂移或覆蓋率不足時，觸發新一輪 PREPING 重建流程。

### 潛在風險與注意事項

**風險一：合成任務偏離真實分佈**
Proposer 傾向探索「可行且新穎」的任務，但這可能與真實用戶任務的分佈有落差，導致記憶體在罕見但關鍵的情境上覆蓋不足。
*緩解措施*：保留一批真實任務的匿名化元資料（任務類型、涉及工具）作為分佈參考，定期比對 proposer memory 的覆蓋率與真實分佈的差距。

**風險二：Validator 誤判造成記憶體污染**
若 Validator 對「成功」的定義過於寬鬆，可能納入表面成功但程序錯誤的軌跡；過於嚴格則會過濾掉具學習價值的失敗恢復範例。
*緩解措施*：採用多層驗證（環境狀態檢查 + 軌跡合理性審查 + 抽樣人工覆核），並定期以 held-out 任務評估記憶體品質。

**風險三：建構階段成本失控**
若 Proposer 缺乏收斂機制，可能產生大量冗餘或不可行的合成任務，導致 LLM API 成本飆升。
*緩解措施*：設定每輪迭代的預算上限、可行性預篩選（提案後先檢查任務是否在環境中可執行，再交給 Solver）、以及覆蓋率增益的邊際成本監控。

**風險四：記憶體陳舊化與環境漂移**
凍結的記憶體在環境升級、API 變更或權限調整後可能失效。
*緩解措施*：為記憶體中的每條規則加上版本標記與來源軌跡指紋；建立環境變更偵測機制，自動觸發記憶體重建。

**風險五：Proposer Memory 本身成為瓶頸**
若 proposer memory 的結構設計不當，可能限制 Proposer 的探索空間，或使其過度集中於已熟悉區域。
*緩解措施*：定期審視 proposer memory 的狀態分佈，引入多樣性獎勵與探索噪聲，避免局部最優。

**風險六：評估管線洩漏**
在建構階段若不小心使用了目標任務資料，會高估記憶體的真實效益。
*緩解措施*：嚴格區分建構環境與評估環境，所有目標任務資料僅在最終評估時使用，並設置資料隔離的自動化檢查。

### 與其他技術的整合建議

**與 ACE（Agentic Context Engineering）整合**
PREPING 最直接的整合對象是 ACE 等在線記憶體建構方法。建議將 PREPING 產出的 solver memory 作為 ACE 的初始 playbook，再讓 ACE 在部署後根據真實用戶互動持續優化。此組合在 AppWorld 上將效能從 71.3 提升至 76.3，同時緩解早期冷啟動失敗。

**與 RAG（檢索增強生成）系統整合**
PREPING 產出的程序性記憶可作為 RAG 的知識來源之一，與文件型知識庫、API 文件檢索並存。建議設計統一的檢索路由器，根據任務類型決定應檢索程序性記憶、文件知識或兩者結合。

**與既有代理框架整合**
多數代理框架（LangChain、AutoGen、CrewAI）已支援外部記憶體外掛。PREPING 的輸出可封裝為標準化的記憶體物件，透過框架的 memory interface 注入，無需修改核心代理邏輯。

**與監控與可觀測性平台整合**
將 PREPING 建構過程的指標（覆蓋率、可行性率、記憶體成長曲線）與部署後的代理監控指標串接，形成「建構品質 → 部署表現」的因果追蹤鏈，有助於診斷記憶體衰退問題。

**與 CI/CD 管線整合**
將 PREPING 重建流程納入代理部署的 CI/CD 管線：當環境工具集變更或新版本上線時，自動觸發 PREPING 重建並通過品質門檻後才允許部署，確保記憶體與環境同步。

**與多代理系統整合**
在多代理架構中，可為每個子代理（例如「資料查詢代理」、「寫入操作代理」）分別執行 PREPING，產生專屬的程序性記憶，再由上層協調代理依任務需求載入對應記憶體，提升整體系統的模組化程度。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，理解 PREPING 試圖解決的「冷啟動問題」——也就是代理在沒有任何經驗時如何學會使用新環境。接著重點閱讀第 1 節的問題描述與第 3 節的框架總覽，掌握 Proposer、Solver、Validator 三個角色的分工。實作細節與基準測試結果可先略過，待對概念熟悉後再深入。

**給 AI 工程師**：重點閱讀第 3 節的方法細節、第 4 節的實驗設計，以及附錄中的實作細節。特別留意 proposer memory 的結構設計、Validator 的驗證標準、以及記憶體蒸餾的具體做法。建議在自己的代理框架中先以小規模環境（例如單一 API）實作 PoC，驗證三角色迴圈與驗證閘控的效果，再逐步擴展到完整環境。

**給研究者**：第 2 節的相關工作梳理了記憶體建構與自我生成練習兩條研究路線的脈絡，建議仔細對照 PREPING 與既有方法的差異，特別是「為何單純的合成任務生成不足以建構有效記憶體」這個論點。第 4 節的消融實驗是理解各元件貢獻的關鍵，可進一步思考 proposer memory 的理論性質、Validator 的最優設計、以及與在線學習理論的連結。

**給產品經理**：聚焦於第 1 節的問題動機、第 4 節的部署成本數據（AppWorld 降低 2.99 倍、BFCL v3 降低 2.23 倍），以及第 5 節的應用討論。PREPING 的核心價值在於讓代理在「第一次見到用戶」之前就具備可用能力，這對客戶體驗與支援成本有直接影響。建議評估自家產品的代理部署流程中，冷啟動階段的失敗率與成本占比，以判斷 PREPING 的導入優先順序。
