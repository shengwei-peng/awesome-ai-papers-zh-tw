## ⚡ TL;DR

本文解決LLM智能體在生產環境中因重試迴圈與缺乏預算原語而導致的預算超支問題。
作者彙編63起超支事件，並以仿射型別Rust套件將預算雙重花費等錯誤轉為編譯期錯誤。
在160次即時API測試中零違規，且多智能體委派競速在編譯階段即被拒絕，避免執行期超支。

## 摘要翻譯

LLM 智能體預算超支（LLM-agent budget overruns）是一種已記載的生產環境故障類別（production failure class）：單一重試迴圈（retry loop）可能在操作者察覺前花費數千美元，而能防止此類情況的程序內完整性屬性（in-process integrity properties）——包括無別名化（no aliasing）、無雙重花費（no double-spend）、無承載成本值（cost-bearing value）的委派後使用（use-after-delegation）——即便確有落實，亦是由特設包裝器（ad-hoc wrappers）而非型別系統（type system）來強制執行。我們的核心貢獻屬於實證性質：一份收錄來自 21 個編排框架（orchestration frameworks）（2023–2026）之 63 起確認事件（confirmed incidents）的目錄；每起事件均附有引述的 GitHub 議題（GitHub issue）為憑，並於回報資料可得時記載美元損失（dollar loss）。全體事件彙整為八群集故障分類法（failure taxonomy）（評分者間 Cohen's kappa 值（inter-rater Cohen's kappa） = 0.837，N = 113），另含 47 筆補充結構性條目（supplementary structural entries）。作為針對此分類法評估的一項緩解方案，我們建構了 token-budgets，一個 1,180 行的 Rust crate（無 unsafe），將仿射所有權（affine ownership）付諸實現，使得複製、雙重花費（double-spending），或在委派後使用預算，均成為編譯錯誤（compile errors）而非操作者必須主動記得避免的執行階段危害（runtime hazards）。美元上限（dollar cap）為基於估計器假設（estimator assumption）的執行階段算術（runtime arithmetic）；仿射層（affine layer）使該算術不可繞過（non-bypassable）。在單智能體工作負載（single-agent workloads）上，一個 4 行的 Python 計數器以 0/30 的超支（overshoot）紀錄與該 crate 表現相當，因此其區別性價值在於多智能體委派（multi-agent delegation）中操作者失誤下的不可繞過性：11 起事件所記載的委派扇出競速（delegation-fanout race），於編譯時即被借用檢查器（borrow checker）拒絕，而相同模式在 asyncio 下則 30/30 超支（overshoot），三種受控替代方案（disciplined alternatives）則為 0/30 超支。橫跨五種執行環境、三家供應商，以及一項依溫度分層的即時 API 測試（N = 160），此方法呈現零上限違規與零誤拒，在運作對等性（operational parity）上與同期工作相當。靜態過度預留（over-reservation）為 4–6 倍（自適應估計器（Adaptive Estimator）為 2.11 倍）。執行中二元檔（running binary）層級的上限穩固性（cap-soundness）仍屬開放

## 深度分析

#### 方法論解析

本文採用雙軌方法論：首先建構大規模實證故障目錄（failure catalog），其次設計並驗證一套基於型別系統（type system）的緩解機制。在實證端，作者系統性蒐集 2023–2026 年間 21 個編排框架（orchestration frameworks）、橫跨 18 個生態系的 63 起確認事件（confirmed incidents），每筆均附引述之 GitHub 議題（GitHub issue）、維護者或使用者陳述，以及（若有回報）美元損失（dollar loss）。為確保分類信度，兩位評分者獨立進行四類樣本（four-class sample）標記，完整 N=113 的評分者間 Cohen's kappa（評分者間一致性統計量）達 0.837；n=79 列雙方獨立標記為確認（confirmed）者更高達 κ=0.943。此外，47 筆補充結構性條目（supplementary structural entries）記錄預算原語缺失條件（budget-primitive-missing condition），但不計入事件總數，僅作為群集層級機制復現（mechanism recurrence）的輔助證據。八群集（eight-cluster）故障分類法（failure taxonomy）屬探索性質，其評分者間一致性為中等（κ=0.44, N=110），故本文以經驗證的四類標籤為主要推論依據。

在緩解機制端，作者開發 token-budgets——一個 1,180 行、無 unsafe 的 Rust crate（Rust 套件）——將仿射所有權（affine ownership）語義操作化。核心設計刻意區分兩層：外層為執行階段算術（runtime arithmetic），負責在估計器假設（estimator assumption）A1 下計算美元上限（dollar cap）；內層為仿射層（affine layer），透過 Rust 借用檢查器（borrow checker）在編譯期強制程序內完整性屬性（in-process integrity properties）。具體而言，承載成本值（cost-bearing value）之 Budget 型別不實作 Clone，核心 API 不使用 Arc<Mutex<_>>，從而確保無別名化（no aliasing）、無雙重花費（no double-spend）、無委派後使用（no use-after-delegation）。任何試圖複製預算、重複扣減，或在委派（delegation）後繼續使用原值的操作，均會被轉化為編譯錯誤（compile errors），而非留待執行階段由操作者手動規避的執行階段危害（runtime hazards）。

此設計針對目錄中反覆出現的預算原語缺失（budget-primitive-missing）模式提供結構性修補：框架若未內建花費上限原語，開發者可透過引入 Budget 型別，將原本依賴特設包裝器（ad-hoc wrappers）的執行期檢查，提升為型別系統層級的不可繞過（non-bypassable）保證。值得注意的是，作者刻意選用仿射型別（affine types）而非線性型別：丟棄（drop）Budget 只會造成 under-spend，這在上限安全（cap-safe）意義下是可接受的，因此宣稱的性質是「不可複製」而非「數值守恆」。命題 1（Proposition 1）的成立條件包括 A1（靜態估計器對供應商回報花費（provider's reported spend）之上界包絡）、A2（無算術溢位，透過預算型別上限將其提升至編譯期）、A6（隱藏推理權杖（hidden reasoning tokens）不受 max_output_tokens 限制，故推理模型（reasoning models）排除於主要保證外），以及 A7（供應商計費真實性，即回報值與實際帳單一致）。

#### 實驗數據解讀

實證語料庫（corpus）的規模與結構本身即為重要發現：63 起確認事件顯示 LLM 智能體預算超支（LLM-agent budget overruns）並非零星個案，而是跨獨立專案反覆出現的生產環境故障類別（production failure class）。其中，重試迴圈（retry loop）在無累積成本上限機制時，可於操作者察覺前累積數千美元損失。分類結果顯示，四類樣本的高信度（κ=0.837）支持作者將故障機制歸納為可重現模式；而八群集分類的中等信度則提示，更細緻的機制劃分仍需更多驗證。

在緩解機制的評估上，作者設計多層次實驗。首先是溫度分層（temperature-stratified）即時 API 測試，涵蓋 T∈{0.0, 0.3, 0.7, 1.0}、N=160、兩個生產級模型、三個供應商（providers）與五種執行環境（runtimes），結果為零次上限違規（cap violations）與零次錯誤拒絕（false refusals）。其次，針對 Anthropic 執行分佈進行模擬，以 30 次真實執行擬合 per-call token 分佈後，展開 2,628 次試驗，驗證執行階段算術於規模化下的正確性。此外，在區分性上限（discriminating cap）（B₀=2,000 uc, claude-haiku-4-5）下，Rust crate、Python 計數器與同期工作 AgentContracts 達到運作對等性（operational parity），顯示單純的單次呼叫上限並非仿射紀律的獨特價值所在。

關鍵區分性實驗出現在多智能體委派（multi-agent delegation）情境。目錄中記錄 11 起委派扇出競速（delegation-fanout race）事件：預算被委派後，因並行執行與別名化導致重複花費。實驗顯示，相同模式於 asyncio 下 30/30 超支（overshoot），而三種受控替代方案（disciplined alternatives）（含正確加鎖的 Python 計數器）為 0/30；相對地，Rust crate 透過仿射所有權使該模式在編譯期即被借用檢查器拒絕。作者強調此為決定性機制分割（deterministic mechanism split），而非邊際效應——這證明型別系統可提供操作者錯誤（operator error）下的不可繞過保證。

成本效率方面，靜態估計器（static estimator）的過度預留（over-reservation）為實際成本之 4–6 倍；自適應估計器（Adaptive Estimator）可壓縮至 2.11 倍（中位數）；分詞器直接估計（tokenizer-direct estimation）接近 1.0 倍，但每次花費延遲（per-spend latency）高達 939–1,749 ms。對於推理模型（如 OpenAI o-series、Anthropic extended-thinking、DeepSeek-R1），由於隱藏推理權杖（hidden reasoning tokens）計費不受 max_output_tokens 限制，命題 1 不適用，token-budgets 僅能作為縱深防禦層（defense-in-depth layer），配合供應商端控制（provider-side controls）（reasoning_effort、thinking.budget_tokens）使用，而非主要上限（primary cap）。

#### 與現有研究的比較

既有緩解方案多聚焦於執行階段監控與政策配置：特設包裝器（ad-hoc wrappers）、AgentGuard-style 回呼、LiteLLM proxy budgets，以及同期工作 AgentContracts。這些方案的共同特徵是將完整性檢查保留在執行期，依賴操作者正確配置與維護，無法防止因並發別名或邏輯錯誤導致的繞過。本文的核心進展在於將「不可繞過性（non-bypassability）」從執行階段危害（runtime hazards）前移至編譯錯誤（compile errors），利用仿射型別（affine types）將預算視為不可複製的資源，從根本上消除雙重花費與委派後使用的程式內別名化路徑。

與 AgentContracts 相比，雖然兩者在單智能體工作負載（single-agent workloads）與區分性上限測試中達到運作對等性（operational parity），但 AgentContracts 並未提供編譯期對委派扇出競速的結構性拒絕。本文的 token-budgets 因此填補了「多智能體委派（multi-agent delegation）」情境下型別層級保證的空白。然而，本文亦明確承認多項限制：其一，二元檔層級上限穩固性（binary-level cap-soundness）仍列為猜想 1（Conjecture 1），尚未建立從抽象規格到執行中二元檔（running binary）的形式精煉證明（refinement proof）；其二，靜態估計器 4–6 倍的過度預留導致資本效率偏低，雖自適應估計器可改善，但仍遜於理想精算；其三，語料庫（corpus）的取樣框選擇依賴變數（selects on the dependent variable），故 63 起事件僅能證明故障類別的跨專案復現，無法推論 LLM 智能體預算超支的盛行率（prevalence）；其四，推理模型因隱藏推理權杖的計費不透明性，無法被納入主要上限保證，僅能作為輔助防線。

#### 可重現性評估

本文在可重現性方面採取高透明度策略。原始碼與完整文物組合（artifact bundle）公開於 GitHub（github.com/sajjadanwar0/token-budgets），crate 共 1,180 行，核心 API 無 unsafe，且不使用 Arc<Mutex<_>>，降低對編譯器內部未規範行為的依賴。編譯期驗證可透過 9 組 trybuild 編譯失敗測試（compile-fail tests）重現，涵蓋 7 種 rustc 診斷碼（E0277、E0308、E0382、E0505、E0507、E0599、E0624），直接證明仿射約束在 rustc 1.93.1 下的不可違反性。

實證資料層面，63 起確認事件均附引述之 GitHub 議題與維護者/使用者陳述，具完整可追溯性；47 筆補充條目亦明確標註為結構性缺失，不混入事件總數。即時 API 測試部分，作者執行跨五種執行環境（runtimes）、三種供應商（providers）的溫度分層即時 API 測試（N=160），但重現此部分需有效 API 金鑰與實際計費成本。為降低重現門檻，作者額外提供以 30 次真實 Anthropic 執行擬合之 per-call token 分佈模擬，共 2,628 次試驗，可在無外部 API 下驗證算術正確性。附錄 B 的六變數守恆分類帳（conservation ledger）輕量規格檢查，則提供抽象規格的內部一致性證據，但作者明確指出這並非端到端源碼至二元檔的證明，二元層級宣稱應視為開放問題。

#### 未來研究方向

首先，形式化驗證是最優先的後續工作：需證明猜想 1（Conjecture 1），建立從 token-budgets 的抽象仿射規格到執行中二元檔（running binary）的上限穩固性（cap-soundness）精煉證明，補齊目前僅有經驗一致性證據的缺口。其次，估計器（estimator）的優化空間顯著：靜態過度預留（over-reservation）達 4–6 倍，未來可發展更低延遲的自適應估計器（Adaptive Estimator）或混合式分詞器直接估計（tokenizer-direct estimation），在維持完整性屬性（integrity property）的同時提升資本效率。

第三，推理模型（reasoning models）的整合亟需深化。由於隱藏推理權杖（hidden reasoning tokens）不受 max_output_tokens 限制，未來研究可探索如何將供應商端控制（provider-side controls）（reasoning_effort、thinking.budget_tokens）與仿射預算層更緊密結合，使這類模型納入命題 1（Proposition 1）的保證範圍，或發展針對隱藏鏈路思考的原生計費上界模型。第四，框架整合：將 token-budgets 的仿射預算原語嵌入 LangGraph、CrewAI、AutoGen 等編排框架（orchestration frameworks），使其從外部 crate 轉為框架內建型別，從源頭消除預算原語缺失（budget-primitive-missing）條件。

第五，盛行率研究：目前語料庫（corpus）為依賴變數取樣，未來需進行具代表性之橫斷面或縱貫研究，量化 LLM 智能體預算超支（LLM-agent budget overruns）於生產環境的實際發生率與經濟影響。最後，資源泛化：將仿射所有權（affine ownership）模式擴展至其他承載成本值（cost-bearing values），如執行時間、記憶體、外部 API 呼叫次數，建構通用的資源預算型別系統，為 LLM 智能體（LLM agents）乃至更廣泛的雲端原生應用提供編譯期資源隔離保證。

## 論文問答

**Q1：LLM 智能體預算超支問題的本質為何？為何它構成嚴重的生產環境威脅？**
A：LLM 智能體預算超支是一種已被記錄的生產環境故障類別，其本質在於單一重試迴圈可能在操作者察覺之前，於部署者帳戶上累積數千美元的費用。這類失控通常源於框架缺乏原生的預算原語，導致累積成本在無人監控的情況下持續增長。由於最終金錢後果直接由部署者承擔而非框架開發者，這使得預算超支成為影響軟體可靠性與成本控制的重大威脅。

**Q2：現有的執行階段追蹤方法為何無法有效防範預算超支？**
A：現行緩解措施大多僅在執行階段追蹤花費，並透過特設包裝器來維持程序內完整性屬性，例如禁止別名化、雙重花費或委派後使用等。然而，這些防護機制並非由型別系統強制執行，而是依賴操作者記得手動避免執行階段危害，因此在人為疏失或複雜編排情境下極易被繞過。相較之下，缺乏編譯期保證意味著相同的失敗模式會在不同框架中反覆發生。

**Q3：作者為何要建構包含 63 起確認事件的實證目錄？其重要性何在？**
A：作者建構此目錄是為了系統性地證明預算超支並非偶發個案，而是橫跨 21 個編排框架與 18 個生態系的結構性問題，且每起事件均附有引用的 GitHub 議題與實際美元損失記錄。透過八群集故障分類法與高評分者間一致性（Cohen's kappa = 0.837），該語料庫建立了失敗類別的跨專案再現性。這份實證基礎不僅凸顯問題的嚴重性，更為後續緩解措施的設計提供了具體的對標依據。

**Q4：token-budgets 的核心方法論是什麼？它如何將仿射所有權操作化？**
A：token-budgets 是一個長約 1,180 行且核心 API 無 unsafe 的 Rust crate，其將仿射所有權語義操作化，使承載成本值在型別層面具備不可複製、不可雙重花費、以及委派後不可再次使用的特性。具體而言，任何試圖複製預算、重複扣減同一筆額度，或在委派後繼續使用原始 Budget 的操作，都會被 Rust 編譯器的借用檢查器視為編譯錯誤而拒絕。這種設計將原本需要操作者記憶的執行階段危害，轉化為編譯期即被排除的型別錯誤。

**Q5：相較於簡易的 Python 計數器，token-budgets 的關鍵創新價值體現在哪裡？**
A：在單智能體工作負載中，一個僅四行的 Python 計數器即可達到與 Rust crate 相同的零超支結果，因此單純的算術正確性並非其區別所在。token-budgets 的真正價值在於多智能體委派情境下的不可繞過性：當操作者發生錯誤時，仿射層能確保預算完整性屬性不被破壞。特別是在委派扇出競速模式中，該模式在目錄中記錄了 11 起事件，Rust 的借用檢查器能在編譯期即拒絕此危險模式，而 asyncio 實作則會 30/30 全部超支。

**Q6：作者為何選擇仿射型別而非線性型別作為所有權語義的基礎？**
A：作者刻意選用仿射所有權而非線性所有權，是因為預算值若被意外丟棄（drop），其結果僅會導致花費低於上限，這在成本安全上屬於可接受的方向。因此，系統需要保證的是「不可複製」而非「數值守恆」，仿射語義恰好允許值被銷毀而不強制要求精確消耗。這項設計選擇使 crate 能針對預算原語缺失這一結構性模式提供有效的編譯期防護，同時避免過度嚴格的線性限制所帶來的實作負擔。

**Q7：實驗評估涵蓋了哪些執行環境、提供者與工作負載？**
A：評估橫跨五種生產級執行環境，包括 LangGraph、CrewAI、AutoGen、AgentGuard 風格回呼機制，以及 LiteLLM 代理預算，並覆蓋三家主要提供者的 API。除了目錄衍生的工作負載外，作者還進行了溫度分層的即時 API 測試，在溫度參數 0.0、0.3、0.7、1.0 下共執行 160 次獨立會話。此外，實驗亦與同期工作 Agent-Contracts 進行比較，以驗證運作對等性與區分性上限下的表現差異。

**Q8：實驗的關鍵結果顯示 token-budgets 在預算上限遵守方面的表現如何？**
A：在橫跨五種執行環境與溫度分層的即時 API 測試中，token-budgets 回報了零起上限違規與零起錯誤拒絕，顯示其在實際呼叫中的高度穩健性。在多智能體委派測試中，針對目錄中記錄的委派扇出競速模式，Rust crate 與三種受控替代方案（包括加鎖的 Python 計數器）均達成 0/30 超支，而 asyncio 對照組則 30/30 全部超支。這證明了仿射型別所提供的編譯期保證，能夠在操作者出錯的多智能體情境中，提供執行階段機制難以比擬的確定性防護。

**Q9：靜態估計器與自適應估計器在過度預留與延遲方面的表現有何差異？**
A：靜態估計器的過度預留程度較高，約為實際成本的 4 至 6 倍，這意味著大量預算處於閒置狀態，資本效率相對較低。自適應估計器則能將此比例收斂至中位數 2.11 倍，顯著改善資本使用效率；而分詞器直接估計雖可達到約 1.0 倍的精準度，但每次花費需額外承擔 939 至 1,749 毫秒的延遲。三種估計方式在完整性屬性上均保持一致，但開發者需在資本效率與延遲成本之間依據部署情境做出權衡。

**Q10：token-budgets 在哪些實際部署情境中最具價值？**
A：此 crate 最具價值的場景是涉及多智能體委派的複雜編排系統，因為預算必須在多個代理程式之間拆分與轉移，極易出現委派扇出競速等並發錯誤。對於缺乏原生預算原語的框架，或是需要防止操作者因疏忽而繞過執行階段檢查的生產環境，仿射型別提供的編譯期保證尤為關鍵。此外，任何將成本控制視為軟體可靠性核心一環的企業級 LLM 應用，皆可透過此機制降低人為失誤導致的財務風險。

**Q11：在產品化考量上，部署 token-budgets 涉及哪些延遲、效率與維護的權衡？**
A：從延遲角度來看，採用分詞器直接估計雖可達到近乎精確的預留，但每次花費會增加近一秒的延遲，對於高頻呼叫系統可能構成瓶頸。靜態估計器雖無額外延遲，但 4 至 6 倍的過度預留會降低資本效率，而自適應估計器則在兩者間取得平衡。由於核心 API 完全無 unsafe，且不使用 Arc<Mutex<_>> 等複雜同步原語，程式碼審計與維護的負擔相對較低，有利於在生產環境中長期運維。

**Q12：此研究對 LLM 智能體可靠性與成本控制領域帶來什麼影響？**
A：本研究首次以大型實證目錄系統性地記錄了 LLM 智能體預算超支這一生產環境故障類別，為學界與業界提供了可引用的失效模式分類架構。透過將仿射型別系統應用於成本控制的完整性屬性，作者證明了型別系統不僅能提升記憶體安全，亦能在財務安全層面發揮編譯期強制作用。這項工作為後續在軟體可靠性與成本控制的交叉領域研究，奠定了結合實證軟體工程與程式語言型別理論的典範。

**Q13：作者明確承認了哪些主要限制？**
A：作者明確指出，執行中二元檔的上限穩固性（binary-level cap-soundness）仍屬開放問題（Conjecture 1），尚未提供從原始碼到機器碼的端到端形式化證明。此外，對於 OpenAI o-series、Anthropic extended-thinking 與 DeepSeek-R1 等推理模型，由於隱藏推理權杖不受 max_output_tokens 限制，命題一的前提假設 A6 不成立，因此這些模型僅能將 token-budgets 視為縱深防禦層而非主要上限。最後，整體機制的有效性仍條件式地依賴供應商回報花費的真實性（假設 A7）與估計器假設 A1 的成立。

**Q14：在哪些情況下，token-budgets 仍可能無法防止預算超支？**
A：若供應商的計費行為違反假設 A1，例如實際 token 消耗顯著高於估計器預留的安全邊際，則執行階段算術仍可能發生超支。針對推理模型，由於其內部產生的隱藏推理權杖無法透過 max_output_tokens 或客戶端估計器精確約束，token-budgets 無法作為主要防線。此外，若編譯後的二元檔在執行期間因編譯器最佳化或執行環境問題導致仿射語義在機器碼層級被破壞，則上限穩固性將面臨風險，而這正是作者標示為未證明的 Conjecture 1。

**Q15：作者建議哪些未來研究方向以延伸此工作？**
A：未來首要方向是證明或否證 Conjecture 1，即建立從抽象規格到執行中二元檔的精煉證明，以確保上限穩固性在機器碼層級同樣成立。其次，可針對推理模型設計與供應商端控制項（如 reasoning_effort 或 thinking.budget_tokens）深度整合的混合機制，使隱藏推理權杖也能被有效約束。最後，進一步降低靜態與自適應估計器的過度預留倍數，同時維持不可繞過的完整性保證，將有助於提升資本效率並擴大此機制在高頻、大規模生產環境中的實用性。

## 實務應用指南

### 適用場景

1. **多智能體委派編排平台**：當單一使用者請求需將預算拆分給多個子智能體（如 LangGraph、CrewAI、AutoGen 架構），且存在委派扇出競速風險時。本文目錄中 11 起確認事件顯示，Python asyncio 環境下相同模式 30/30 超支，而仿射層可在編譯期拒絕此類競態。
2. **高頻重試迴圈生產管線**：客服機器人、資料擷取或自動化工作流中，單次呼叫僅花費數美分，但無累積上限的重試迴圈可在操作者察覺前累積數千美元損失。
3. **多租戶 SaaS 成本隔離**：為每個終端使用者或企業客戶設定硬式美元上限的應用，需保證程序內無雙重花費、無別名化，避免特設包裝器被繞過。
4. **金融或醫療合規場景**：承載成本值必須具備程序內完整性屬性（無委派後使用、無別名化）的系統，將執行階段危害轉為編譯錯誤以降低人為操作風險。
5. **LLM 代理閘道與邊緣代理**：在 LiteLLM Proxy 或自訂閘道層嵌入 token-budgets，作為供應商端控制之外的不可繞過執行階段算術層。

### 實作前置條件

- **資料**：至少 30 筆歷史供應商回報花費紀錄，用以校準估計器假設 A1（位元組長度或 tokenizer 對應關係）；若使用 Anthropic 模型，需準備巢狀工具結構描述樣本以驗證安全邊際。
- **運算**：Rust 工具鏈 1.93.1 以上、可編譯 Rust 的 CI/CD 環境、支援 Tokio 的非同步執行環境（若採用多智能體委派模式）。
- **技能**：團隊需熟悉 Rust 所有權與借用檢查器語義、非同步程式設計、LLM API 計費模型，並具備基礎統計驗證能力以執行溫度分層即時 API 測試。

### 實作步驟建議

1. **對照目錄進行故障模式盤點**：依論文八群集故障分類法，檢視現有系統屬於預算原語缺失、委派扇出競速或其他群集，優先處理有確認事件與美元損失紀錄的模式。
2. **校準估計器並驗證假設**：針對目標供應商與模型，以歷史資料驗證 A1 假設。預設採位元組長度估計（OpenAI/Groq）或 AnthropicEstimator（2.0× 安全邊際）；若資本效率優先，則實作自適應估計器或分詞器直接估計。
3. **以 Rust crate 取代特設包裝器**：引入 token-budgets（無 unsafe），將原本以 Python 計數器或 ad-hoc wrapper 實作的上限，改以 `Budget` 仿射型別封裝承載成本值。
4. **編譯期委派正確性驗證**：在多智能體拆分邏輯中，確保預算委派後原變數無法再被使用；讓借用檢查器在編譯期拒絕別名化、雙重花費與委派後使用，而非依賴執行階段檢查。
5. **分階段即時 API 驗證**：參照論文溫度分層設計（T ∈ {0.0, 0.3, 0.7, 1.0}），執行至少 160 次獨立會話的零超支測試，涵蓋起飛前、迴圈中與自我終止三種運作階段。
6. **漸進式部署**：先於單智能體工作負載上線（此時 4 行 Python 計數器與 crate 效果相當），驗證運作對等性後，再開啟多智能體委派路徑。
7. **監控過度預留與資本效率**：追蹤靜態估計器的 4–6× 過度預留比率，逐步導入自適應估計器（目標 2.11× 中位數）或 tokenizer-direct 估計（∼1.0×），權衡每次花費延遲與資本效率。

### 潛在風險與注意事項

- **推理模型不適用為主要上限**：OpenAI o-series、Anthropic extended-thinking、DeepSeek-R1 等模型的隱藏推理權杖不受 max_output_tokens 限制（假設 A6 不成立）。token-budgets 對這類模型僅能作為縱深防禦層，必須搭配供應商端控制（reasoning_effort、thinking.budget_tokens）。
- **過度預留壓縮資本效率**：靜態估計器預留 4–6× 實際成本，若未導入自適應或分詞器直接估計，將導致大量預算閒置。
- **執行中二元檔上限穩固性未證**：論文將 binary-level cap-soundness 列為開放命題（Conjecture 1），若需極高強度財務保證，應額外進行二進位層級稽核，而非僅依賴原始碼層級的仿射層。
- **Python 委派邏輯的混用風險**：一旦多智能體委派邏輯以 Python asyncio 實作，即使 Rust 核心為仿射型別，跨 FFI 邊界仍可能重現 30/30 超支；建議將委派扇出保留在 Rust 側完成。
- **供應商計費真實性假設**：上限僅能約束「供應商回報花費」，若供應商低報實際用量（假設 A7 失效），程序層級無法偵測真實帳單超支。

### 與其他技術的整合建議

- **LiteLLM Proxy**：在閘道層前置 token-budgets，作為程序內不可繞過的算術層，再銜接 LiteLLM 原生預算功能，形成雙層防護。
- **LangGraph / CrewAI / AutoGen**：這些編排框架多數存在預算原語缺失條件，建議在框架的 agent 呼叫層以 `Budget` 型別包裝成本值，而非依賴框架內建的特設包裝器。
- **Agent-Contracts**：論文驗證兩者具運作對等性；可並行部署，由 Agent-Contracts 處理高階合約語意，token-budgets 負責低階程序內記憶體安全與不可繞過的扣減。
- **Python 生態系**：若主程式碼必須留在 Python，單智能體場景可暫用 4 行 Python 計數器；但多智能體委派強烈建議將預算拆分邏輯編譯為 Rust crate 並以 PyO3 或類似工具暴露，避免 asyncio 競速。
- **供應商端控制**：一律將 reasoning_effort 或 thinking.budget_tokens 設為縱深防禦，而非僅依賴程式層級上限。

### 給不同背景讀者的閱讀建議

- **初學者**：請從 63 起確認事件的目錄與美元損失紀錄讀起，理解 LLM 智能體預算超支為何是反覆發生的生產環境故障類別；token-budgets 的仿射型別實作屬於進階緩解方案，現階段可先建立「執行階段計數器不足以防範委派錯誤」的認知，待熟悉 Rust 所有權後再評估導入。
- **AI 工程師**：重點研讀多智能體委派扇出競速的實證結果與論文表 1 的編譯錯誤對照；檢視你目前以 Python asyncio 或特設包裝器實作的成本控制，是否正暴露於目錄中的 11 起委派相關事件模式，並評估將核心預算邏輯遷移至仿射層的可行性。
- **研究者**：八群集故障分類法與評分者間 Cohen's kappa = 0.837 的驗證流程，可作為實證軟體工程與故障目錄研究的參考範式；此外，binary-level cap-soundness（Conjecture 1）目前為開放命題，具形式化驗證背景者可針對執行中二元檔進行精煉證明。
- **產品經理**：以 21 個編排框架跨 2023–2026 的確認事件與實際金錢損失，向利害關係人說明預算控制並非「邊際優化」而是「可靠性基建」；同時請注意，靜態估計器的 4–6× 過度預留會直接影響毛利，而推理模型需要額外的供應商端控制預算，兩者皆需在產品定價與模型選型階段納入評估。
