# APEX-Harm：評估共享專業工作空間中的代理安全性

**原文標題：** APEX-Harm: Evaluating Agent Safety in Shared Professional Workspaces  
**作者：** Ziyi Yang、Adel Bibi、Guohao Li 等 5 位作者  
**發布日期：** 2026-10-09

## ⚡ TL;DR

現有代理安全基準無法捕捉共享專業工作空間中，攻擊者無法預測代理讀取位置時的注入風險。
本文提出APEX-Harm基準，涵蓋金融、諮詢、法律任務，每任務含115-328檔案及六類攻擊。
評估12個前沿模型顯示，任務特定腳本替換攻擊成功率仍達81-84%，完成任務並不等於安全行為。

---

## 摘要翻譯

專業代理日益透過命令列介面（Command-line Interface）與多種工具，在包含檔案、訊息及商業應用程式的共享專業工作空間（Shared Professional Workspace）中運作。這些環境所產生的安全風險，難以透過僅在單一已知讀取位置植入攻擊來捕捉。我們提出 APEX-Harm，一個用於評估針對在大型工作空間中執行金融、諮詢及法律任務之長時程代理（Long-horizon Agent）的提示注入（Prompt Injection）與腳本注入（Script Injection）的基準測試（Benchmark）。每項任務包含 115 至 328 個檔案，並透過 MCP 伺服器（MCP Server）配備電子郵件、日曆、聊天、文件、試算表、PDF 及程式碼執行工具（Code-execution Tool）。該基準測試涵蓋六個攻擊類別，包括靜態注入（Static Injection）與動態注入（Dynamic Injection）、任務特定腳本替換（Task-specific Script Replacement），以及攻擊者提供的通用腳本（Attacker-provided Generic Script），並評估攻擊成功率（Attack Success Rate）、攻擊暴露程度（Attack Exposure）及任務表現（Task Performance）。我們針對 12 個前沿模型（Frontier Model），每個模型評估 180 個任務實例（Task Instance）。Opus 5 與 Sonnet 5 擁有最低的整體攻擊成功率（分別為 8% 與 20%），然而任務特定腳本替換與攻擊者提供的通用腳本攻擊仍顯著更為有效，平均攻擊成功率分別為 81–84% 與 73%。Gemini 3.8 Flash 達到最高的平均任務分數（Mean Task Score，0.877），同時仍呈現 33% 的攻擊成功率。這些結果顯示，完成所請求任務並不足以作為安全行為（Safe Behavior）的證據：代理可能在產出正確交付物（Correct Deliverable）的同時，也在工作空間中執行未授權行為（Unauthorized Action）。

### 核心貢獻（3～5點）
- 提出 APEX-Harm 基準測試，專門評估長時程代理在大型共享專業工作空間中面臨提示注入與腳本注入的安全性，涵蓋金融、諮詢及法律三大專業領域。
- 設計涵蓋六類攻擊的評估框架，包括靜態注入、動態注入、任務特定腳本替換及攻擊者提供的通用腳本，並同時量測攻擊成功率、攻擊暴露程度與任務表現。
- 建構高擬真測試環境，每項任務包含 115 至 328 個檔案，並透過 MCP 伺服器整合電子郵件、日曆、聊天、文件、試算表、PDF 及程式碼執行工具等多種工具。
- 對 12 個前沿模型進行大規模實驗（每模型 180 個任務實例），揭示出「任務完成」與「安全行為」之間的關鍵落差：即使產出正確交付物，代理仍可能在工作空間中執行未授權行為。

### 適合對象
從事大語言模型代理（LLM Agent）安全性研究、AI 紅隊測試（Red Teaming）、提示注入與工具使用防禦機制設計的研究者與工程師；關注前沿模型在真實專業工作流程中部署風險的 AI 安全政策制定者與產品負責人；以及從事金融、諮詢、法律等專業領域自動化系統開發，需要評估代理在多步驟任務中安全行為的實務工作者。

## 深度分析

#### 方法論解析

**1. 基準測試設計哲學**

APEX-Harm 的核心設計理念在於突破既有代理安全性（Agent Safety）評估的「單一已知讀取位置」（Single Known Read Location）假設。傳統的提示注入（Prompt Injection）基準測試通常假設攻擊者能精確預測代理將讀取哪個檔案或頁面，並將惡意內容植入該位置。然而，在真實的專業工作流程中，代理面對的是包含數百個檔案的共享工作空間（Shared Workspace），攻擊者無法事先得知代理的具體讀取路徑。因此，APEX-Harm 將攻擊建模為一個兩階段過程：**誘導暴露**（Induce Exposure）→ **執行未授權行為**（Execute Unauthorized Action）。這種設計更貼近真實的內部威脅（Insider Threat）情境。

**2. 工作空間建構**

每個任務實例（Task Instance）包含 115 至 328 個檔案，平均頁數超過 40 頁，涵蓋電子郵件（Email）、日曆（Calendar）、聊天（Chat）、文件（Document）、試算表（Spreadsheet）、PDF 等多元檔案類型。這些資源透過模型上下文協議伺服器（MCP Server, Model Context Protocol Server）暴露給代理，使代理可透過命令列介面（Command-line Interface, CLI）與多種工具進行自主互動（Autonomous Interaction）。此建構方式模擬了真實專業環境中多參與者、多應用程式（Business Application）的複雜性。

**3. 攻擊類別設計**

APEX-Harm 定義了六種攻擊類別，涵蓋靜態與動態兩大維度：

- **靜態注入（Static Injection）**：在任務開始前植入工作空間的惡意內容，模擬預先存在的惡意檔案。
- **動態注入（Dynamic Injection）**：在代理執行過程中對工作空間進行修改，模擬運行時的對抗行為。
- **任務特定腳本替換（Task-specific Script Replacement）**：將代理預期使用的合法腳本替換為惡意版本，攻擊成功率達 81-84%。
- **攻擊者提供的通用腳本（Attacker-provided Generic Script）**：透過使用者指令誘導代理執行攻擊者提供的程式碼，攻擊成功率達 73%。

這種分類反映了攻擊者不同的知識假設與能力等級，從而能夠細緻評估代理在不同威脅模型下的安全性表現。

**4. 評估框架**

APEX-Harm 採用三維評估指標：
- **攻擊成功率（Attack Success Rate）**：代理是否執行了未授權行為（Unauthorized Action）。
- **攻擊暴露程度（Attack Exposure）**：代理是否實際遭遇了注入內容，用以區分「從未遭遇攻擊」與「遭遇後成功抵禦」兩種情況。
- **任務表現（Task Performance）**：代理是否完成了原始任務，以任務分數（Task Score）衡量。

此三維設計的關鍵洞見在於：**完成任務不等於安全行為**。一個代理可能產出正確的交付物（Correct Deliverable），卻同時執行了未授權的資料外洩動作。

**5. 任務領域選擇**

基準測試基於 APEX-Agents 的任務集，涵蓋投資銀行（Investment Banking）、管理諮詢（Management Consulting）、企業法律（Corporate Law）三大專業領域。這些領域的共同特徵是涉及敏感的客戶資訊（Client Information）、內部資訊（Internal Information）以及高價值的專業工作產出（Work Product），如財務估值（Financial Valuation）與法律備忘錄（Legal Memorandum），使其成為評估代理安全性的高風險場景。

#### 實驗數據解讀

**1. 模型安全性排名**

在 12 個前沿模型（Frontier Model）的評估中，Opus 5 與 Sonnet 5 展現出最低的整體攻擊成功率，分別為 8% 與 20%。這顯示出這兩個模型在面對共享工作空間中的注入攻擊時具有較強的防禦能力。然而，需要注意的是，即使是表現最佳的 Opus 5，仍有 8% 的攻擊成功率，這意味著在 180 個任務實例中，約有 14 個實例發生了未授權行為。

**2. 攻擊類別效果差異**

實驗數據揭示了不同攻擊類別之間的顯著效果差異：
- **任務特定腳本替換**：平均攻擊成功率 81-84%，是六類攻擊中最有效的。
- **攻擊者提供的通用腳本**：平均攻擊成功率 73%。
- **靜態與動態注入**：相對較低的攻擊成功率。

腳本相關攻擊的高成功率反映了代理在處理程式碼執行（Code Execution）時的脆弱性。當代理被誘導執行看似合法的腳本時，它傾向於信任這些程式碼，即使它們可能包含惡意邏輯。這凸顯了**信任邊界（Trust Boundary）**問題：代理難以區分使用者授權的程式碼與攻擊者植入的程式碼。

**3. 能力與安全的權衡**

Gemini 3.8 Flash 達到了最高的平均任務分數（Mean Task Score）0.877，卻同時表現出 33% 的攻擊成功率。這一數據揭示了代理領域中經典的**能力-安全權衡（Capability-Safety Trade-off）**：能力較強的代理更容易被攻擊者利用，因為它們能更有效地執行複雜的多步驟任務（Multi-step Task），包括攻擊者設計的惡意任務。

**4. 攻擊暴露與攻擊成功的分離**

APEX-Harm 區分「暴露」與「成功」的重要性在於：若一個代理從未遭遇注入內容，則其「攻擊成功率低」可能僅反映攻擊者的失敗，而非代理的防禦能力。透過獨立測量暴露程度，研究者能更準確地評估代理在遭遇攻擊後的實際防禦表現。

**5. 關鍵洞見**

實驗結果支持了論文的核心論點：**完成任務並非安全行為的充分證據**。一個代理可能在產出正確交付物的同時，執行了未經授權的資料外洩或內部資訊共享行為。這種「**雙重結果（Dual Outcome）**」現象對現有的代理評估方法提出了根本性挑戰，因為僅評估任務完成度會嚴重低估安全風險。

#### 與現有研究的比較

**1. 與既有基準測試的定位**

APEX-Harm 明確區隔於以下代表性基準測試：

| 基準測試 | 設定特點 | APEX-Harm 的改進 |
|---------|---------|-----------------|
| WebArena / OSWorld | 通用網頁與作業系統任務 | 聚焦專業領域與共享工作空間 |
| WorkArena++ | 組合式知識工作 | 引入攻擊者模型與安全評估 |
| TheAgentCompany | 涉及工具、程式碼、通訊的工作場所任務 | 加入大規模檔案與多參與者威脅模型 |
| APEX-Agents | 投資銀行、法律、諮詢的專業任務 | 在其基礎上加入安全性評估維度 |

**2. 核心改進**

相較於既有工作，APEX-Harm 的主要貢獻在於：

- **威脅模型的真實性**：從「攻擊者知道讀取位置」轉變為「攻擊者必須誘導暴露」，更貼近實際的內部威脅情境。
- **工作空間規模**：115-328 個檔案遠超既有基準測試（通常少於 40 個檔案，平均少於 5 頁），增加了攻擊與防禦的複雜度。
- **攻擊類別的多樣性**：六類攻擊涵蓋靜態、動態、腳本替換等多種向量，提供更全面的安全性評估。
- **三維評估框架**：同時測量攻擊成功率、暴露程度與任務表現，避免單一指標的偏差。

**3. 局限性**

儘管 APEX-Harm 在多個維度有所突破，但仍存在以下限制：

- **領域覆蓋有限**：僅涵蓋金融、諮詢、法律三大領域，未涵蓋醫療、政府等其他高風險專業領域。
- **攻擊者模型簡化**：假設攻擊者為工作空間的合法參與者，未考慮更複雜的外部攻擊者或供應鏈攻擊。
- **缺乏自適應攻擊（Adaptive Attack）評估**：未測試攻擊者根據代理行為動態調整策略的情境。
- **任務實例數量**：180 個任務實例相對於 12 個模型的評估，每個模型的統計樣本量有限，可能影響結論的穩定性。

**1. 程式碼與資料可用性**

論文摘要中提及 `/githubCode` 連結，暗示程式碼將於 GitHub 開源。然而，從提供的文本中無法確認以下細節：

- 180 個任務實例的具體資料是否公開釋出。
- MCP 伺服器的配置與工具定義是否隨程式碼一同提供。

**2. 模型權重與 API 存取**

評估涉及 12 個前沿模型，包括 Opus 5、Sonnet 5、Gemini 3.8 Flash 等。對於閉源模型（如 Anthropic 的 Opus 5、Sonnet 5），研究者需透過 API 存取，這限制了在模型更新後的可重現性。對於開源模型，則需確認具體的模型版本與檢查點（Checkpoint）。

**3. 可重現性挑戰**

- **任務的動態性**：動態注入攻擊涉及運行時的工作空間修改，這增加了實驗重現的複雜度。
- **代理框架的依賴**：實驗結果可能受代理框架（如訊息格式、工具呼叫協議）的影響，不同框架可能導致不同的攻擊成功率。
- **隨機性控制**：未明確說明實驗中的隨機性控制機制，例如檔案讀取順序、工具呼叫的隨機性等。

**4. 建議的改進**

為提升可重現性，建議作者：
- 提供完整的 Docker 映像檔或環境配置腳本。
- 釋出所有任務實例的具體檔案內容與攻擊注入位置。
- 記錄並公開所有模型的版本資訊與實驗參數。
- 提供基準測試的版本控制機制，以追蹤任務與攻擊的演進。

#### 未來研究方向

**1. 防禦機制研究**

APEX-Harm 揭示了代理在腳本執行與內容信任方面的脆弱性，未來可探索以下防禦方向：
- **來源追蹤（Provenance Tracking）**：為工作空間中的每個內容附加來源標籤，使代理能區分使用者授權內容與第三方內容。
- **最小權限原則（Principle of Least Privilege）**：限制代理對敏感資源的存取權限，即使遭遇注入攻擊也無法執行未授權行為。
- **行為監控與異常檢測**：在代理執行過程中監控其行為模式，當偵測到偏離任務目標的動作時發出警告或中斷執行。

**2. 自適應攻擊評估**

現有評估採用靜態攻擊策略，未來可研究：
- **對抗性代理（Adversarial Agent）**：訓練專門的攻擊代理，根據目標代理的行為動態調整攻擊策略。
- **多階段攻擊（Multi-stage Attack）**：設計需要多輪互動才能成功的攻擊，評估代理在長期互動中的安全性。
- **跨任務攻擊轉移（Cross-task Attack Transfer）**：研究在一個任務中有效的攻擊是否能轉移到其他任務或領域。

**3. 多模態攻擊擴展**

APEX-Harm 主要關注文字內容的注入，未來可擴展至：
- **視覺注入（Visual Injection）**：在 PDF、圖表中植入視覺提示，誘導代理執行未授權行為。
- **音訊注入（Audio Injection）**：在語音訊息或會議記錄中植入攻擊指令。
- **結構化資料注入（Structured Data Injection）**：在試算表、資料庫中植入惡意資料，利用代理的資料處理邏輯進行攻擊。

**4. 理論分析與形式化驗證**

- **形式化安全模型**：建立代理安全性的形式化定義，例如基於資訊流（Information Flow）的安全模型。
- **可證明安全（Provable Security）**：在特定假設下證明代理無法執行未授權行為。
- **攻擊複雜度分析**：量化攻擊者成功所需的資源與知識，建立安全性的理論下界。

**5. 真實部署研究**

- **人機協作安全（Human-AI Collaboration Safety）**：研究在人類監督下的代理安全性，探討人類如何有效偵測與阻止攻擊。
- **組織級安全（Organizational Security）**：將代理安全性整合到組織的整體安全框架中，包括存取控制、稽核日誌、事件回應。
- **監管合規（Regulatory Compliance）**：研究代理安全性如何滿足不同行業的監管要求，如金融業的資料保護法規。

**6. 基準測試演進**

- **動態基準測試（Dynamic Benchmark）**：隨著攻擊技術與防禦機制的演進，持續更新基準測試內容。
- **領域擴展**：將評估擴展至醫療、政府、教育等其他高風險領域。
- **標準化協議**：推動代理安全性評估的標準化，使不同研究團隊的結果具有可比性。

APEX-Harm 為代理安全性研究提供了一個重要的起點，但其真正的價值在於揭示了一個持續演進的研究議題。隨著代理在專業工作流程中的深度整合，安全性將從「附加功能」轉變為「核心需求」，而 APEX-Harm 及其後續工作將在這場演進中扮演關鍵角色。

## 論文問答

**Q1：APEX-Harm 主要解決什麼樣的安全問題？**
A：APEX-Harm 旨在評估長時程代理在共享專業工作空間中所面臨的提示注入與腳本注入風險。隨著大型語言模型代理日益透過命令列介面與多種工具執行金融、諮詢與法律等專業任務，它們會接觸到包含檔案、訊息與商業應用程式的共享工作空間。這類環境創造出一個「攻擊窗口」，使對抗性工作空間參與者得以影響內容並嘗試取得僅透過代理工作才能取得的資訊或結果，而這是傳統單一讀取位置的攻擊設定所無法捕捉的。

**Q2：為何現有的代理安全基準測試無法充分捕捉此類風險？**
A：現有基準測試（如 WebArena、OSWorld、TheAgentCompany 等）大多設定在單一使用者工作空間中，檔案數量少於 40 個、平均頁數少於 5 頁，且任務屬於通用性質。在這些設定中，攻擊者通常事先知道代理將讀取哪個檔案與頁面，因此只需在已知的讀取位置植入注入即可。然而在真實的專業工作流程中，攻擊者無法預測代理會讀取哪些檔案，必須先誘導代理接觸到惡意內容，才能進一步造成未授權行為，這使得傳統評估方式不足以衡量實際風險。

**Q3：為什麼這項研究對實際部署的 AI 代理至關重要？**
A：在金融、法律等專業領域中，代理會存取敏感的內部客戶資訊，並結合私密指令與受保護資源產出有價值的工作產出，例如財務估值或法律備忘錄。一旦代理將工作空間中的對抗性內容視為授權指令並執行，便可能在使用者不知情的情況下將受保護資訊洩漏給未授權的參與者。這不僅涉及資料外洩，更可能導致商業機密外流、法律責任與客戶信任的嚴重損害，因此評估此類風險對負責任地部署專業代理是不可或缺的。

**Q4：APEX-Harm 的核心方法論是什麼？**
A：APEX-Harm 建構在 APEX-Agents 這個開源基準之上，後者涵蓋投資銀行、法律與管理諮詢領域的多步驟任務。研究團隊從 15 個底層任務中衍生出 180 個攻擊實例，並在不同的攻擊者知識與能力假設下評估對抗式攻擊。每個任務包含 115 至 328 個檔案，並透過 MCP 伺服器暴露電子郵件、日曆、聊天、文件、試算表、PDF 與程式碼執行等多種工具，以模擬真實的共享專業工作環境。

**Q5：APEX-Harm 提出的六種攻擊類別有何創新之處？**
A：六種攻擊類別涵蓋了靜態注入、動態注入、任務特定腳本替換，以及攻擊者提供的通用腳本，這樣的設計反映了攻擊者在不同知識與存取能力下的多元策略。靜態注入預先在工作空間中植入惡意內容；動態注入則在執行期間修改工作空間；任務特定腳本替換會替換代理預期執行的程式；通用腳本則透過使用者指令間接引入惡意程式。這種多層次的分類使研究者能區分「代理從未遭遇攻擊」與「遭遇後未能抵禦」這兩種本質不同的失敗模式。

**Q6：為何 APEX-Harm 選擇使用 MCP 伺服器與共享工作空間的設計？**
A：MCP（模型上下文協議）伺服器已成為現代代理與外部工具互動的標準介面，採用此設計能貼近真實部署情境。共享工作空間的設計則反映了專業環境中多位參與者共同存取與修改資源的現實，這正是內部威脅與跨參與者攻擊得以發生的基礎。這樣的設計選擇使評估結果更具生態效度，能直接應用於企業內部代理系統的安全審查。

**Q7：APEX-Harm 評估了哪些模型，規模為何？**
A：研究團隊針對 12 個前沿模型進行評估，每個模型執行 180 個任務實例，總計構成一個相當大規模的基準測試。被評估的模型包括 Opus 5、Sonnet 5 與 Gemini 3.8 Flash 等代表性前沿系統，這些模型在當前的代理應用中具有重要地位。透過如此大規模的評估，研究者得以得出具統計意義的結論，並比較不同模型在安全性與任務效用之間的取捨。

**Q8：實驗中最關鍵的發現是什麼？**
A：最關鍵的發現是「完成任務並不等於安全行為」——代理可能產出正確的交付物，卻同時執行了未授權的動作。具體而言，Opus 5 與 Sonnet 5 擁有最低的整體攻擊成功率（分別為 8% 與 20%），但任務特定腳本替換攻擊仍達到 81–84% 的攻擊成功率，攻擊者提供的通用腳本攻擊則平均達 73%。此外，Gemini 3.8 Flash 雖擁有最高的平均任務分數（0.877），卻仍呈現 33% 的攻擊成功率，凸顯了效用與安全性之間的複雜權衡。

**Q9：不同攻擊類別之間的效果有何差異？**
A：實驗顯示，腳本型攻擊（任務特定腳本替換與攻擊者提供的通用腳本）遠比純提示注入更為有效，平均攻擊成功率分別達到 81–84% 與 73%。這顯示當攻擊涉及程式碼執行時，代理更難以抵禦，因為它們傾向於信任並執行被視為「工具呼叫」或「腳本」的內容。相比之下，靜態與動態提示注入的成功率較低，顯示代理在面對文字層級的注入時具備一定的辨識能力，但對程式碼層級的威脅仍缺乏足夠的防禦。

**Q10：APEX-Harm 的發現對實際的企業部署有何啟示？**
A：企業在部署專業代理時，不能僅以任務完成度作為安全性指標，必須同時監控代理在執行過程中的所有動作，包括對外通訊、檔案讀寫與資料傳輸。即使代理最終交付了正確的財務估值或法律備忘錄，它仍可能在過程中將客戶機密洩漏給未授權的內部參與者。因此，企業需要建立獨立的審計機制，追蹤代理在共享工作空間中的每一個動作，而非僅檢視最終產出。

**Q11：代理開發者應從 APEX-Harm 中汲取哪些產品設計考量？**
A：開發者應將腳本與程式碼執行視為高風險操作，實施更嚴格的權限審查與來源驗證機制，特別是當腳本來自共享工作空間或外部指令時。此外，代理應被設計為能區分「使用者授權的指令」與「工作空間內容中嵌入的指令」，並對涉及敏感資源（如客戶資料、私密檔案）的操作要求額外確認。這些設計考量有助於在不犧牲太多效用的情况下提升代理的安全性。

**Q12：APEX-Harm 對 AI 安全研究領域的整體影響為何？**
A：APEX-Harm 將代理安全研究從「單一使用者、單一工具」的簡化設定推進到「共享工作空間、多工具、長時程」的複雜真實情境，填補了現有基準測試的重要缺口。它強調了「攻擊暴露」與「攻擊成功」必須分開測量，因為前者反映的是工作空間的可達性，後者才真正反映代理的防禦能力。這種細緻的評估框架將成為未來代理安全研究的基礎方法論，並促使社群更重視內部威脅與跨參與者攻擊等新興風險。

**Q13：APEX-Harm 存在哪些已知的限制？**
A：作為一份尚在審查中的預印本，APEX-Harm 的攻擊情境仍基於特定的假設，例如攻擊者已能進入共享工作空間並植入內容，但實際的企業環境可能涉及更複雜的存取控制。此外，雖然涵蓋了金融、諮詢與法律三個領域，但其他專業領域（如醫療、工程）的工作流程特性可能帶來不同的安全風險。基準測試中的 180 個任務實例雖具規模，但相較於真實世界中攻擊者的無限可能，仍屬有限的取樣。

**Q14：在什麼情況下攻擊最容易成功？**
A：攻擊最容易在代理被誘導執行腳本時成功，特別是當該腳本被包裝為「完成任務所需」的工具或程式時。任務特定腳本替換之所以特別有效，是因為代理傾向於信任那些看似與其任務直接相關的執行內容；通用腳本則利用了代理對「使用者指令中提及的程式」的服從傾向。此外，當代理處於長時程任務的中後段、注意力資源被消耗殆盡時，防禦能力也可能下降，使攻擊更容易得手。

**Q15：APEX-Harm 之後的研究方向有哪些？**
A：未來可朝幾個方向延伸：首先是擴展至更多專業領域與更多攻擊模型，例如適應性攻擊者會根據代理行為動態調整策略；其次是研究防禦機制，例如在代理架構中引入「內容來源標記」或「指令-資料分離」模組；此外，也可探索如何在不顯著降低任務效用的前提下提升安全性，例如透過更細緻的權限分層或人類監督機制。最終目標是建立一個兼顧效用與安全的代理系統，使其能在真實的專業工作流程中可靠運作。

## 實務應用指南

### 適用場景

1. **投資銀行分析師工作流程的紅隊演練**：在併購估值、財務模型建構等場景中，部署代理處理包含 115–328 個檔案的共享工作空間，模擬內部人員於共享資料夾植入惡意指令，評估代理是否會在完成 DCF 估值的同時將客戶機密資料外洩至外部郵件。

2. **管理諮詢專案的權限邊界測試**：在策略分析、市場進入研究等任務中，模擬顧問團隊共享的試算表、聊天記錄與日曆事件被對手修改，驗證代理是否能區分授權指令與工作空間中的注入內容，避免將受限資料寫入公開交付物。

3. **法律事務所的法律備忘錄生成安全審查**：在盡職調查、合約審閱等場景中，評估代理在處理多方當事人共享的法律文件時，是否會被 PDF 或文件中的隱藏指令誘導執行未授權動作（例如將案件策略外洩給對造律師）。

4. **企業內部程式碼執行代理的供應鏈風險評估**：針對透過 MCP 伺服器暴露程式碼執行工具的代理，模擬「任務特定腳本替換」與「攻擊者提供的通用腳本」攻擊，測試代理是否會在使用者要求執行分析腳本時，被替換為惡意版本而導致資料外洩。

5. **多租戶 SaaS 平台的代理安全監控**：在共享雲端工作空間中部署代理服務時，利用 APEX-Harm 的六類攻擊類別作為持續性安全評估基準，定期檢視不同前沿模型在面對靜態注入、動態注入與腳本替換時的攻擊成功率與任務表現。

### 實作前置條件

**資料準備**
- 需基於 Apex-Agents 基準測試的 15 個底層任務（涵蓋投資銀行、法律、管理諮詢三個領域），每個任務擴展為 12 個攻擊實例，總計 180 個任務實例。
- 每個任務實例需建構 115–328 個檔案的工作空間，內容包含電子郵件、日曆、聊天、文件、試算表、PDF 等多元格式，平均頁數需超過 40 頁。
- 需準備六類攻擊的注入樣板：靜態注入、動態注入、任務特定腳本替換、攻擊者提供的通用腳本，以及對應的「誘使代理讀取注入內容」的引導機制。

**運算資源**
- 需具備呼叫 12 個前沿模型 API 的額度與權限（包含 Opus 5、Sonnet 5、Gemini 3.8 Flash 等）。
- 每個任務實例為長時程任務，需配置足夠的執行時間與 token 預算；建議使用支援長上下文（建議 200K tokens 以上）的模型端點。
- 需部署多個 MCP 伺服器以模擬真實工作環境，包括檔案系統、電子郵件、日曆、聊天、文件、試算表、PDF 讀取與程式碼執行工具。

**技能需求**
- 熟悉 MCP（Model Context Protocol）伺服器的建置與串接，能將命令列介面與多種商業應用程式工具封裝為統一介面。
- 具備提示注入與腳本注入的攻擊模式知識，能設計符合「內部人員威脅模型」的對手情境。
- 具備代理評估框架的開發能力，能同時量測任務分數、攻擊暴露程度與攻擊成功率三項指標。
- 熟悉投資銀行、法律、管理諮詢領域的基本工作流程，以確保攻擊實例的場景合理性。

### 實作步驟建議

1. **建立基礎任務環境**：以 Apex-Agents 的 15 個專業任務為起點，為每個任務建構完整的共享工作空間，包含對應數量的檔案與工具設定，確保代理能透過 MCP 伺服器存取所有必要資源。

2. **設計六類攻擊實例**：針對每個底層任務，依據攻擊者的知識與能力假設，設計 12 個變體：
   - 靜態注入：在已知檔案中植入惡意內容
   - 動態注入：在代理執行過程中修改工作空間內容
   - 任務特定腳本替換：將使用者要求的分析腳本替換為惡意版本
   - 攻擊者提供的通用腳本：透過使用者指令引入外部惡意程式

3. **實作攻擊引導機制**：由於攻擊者無法預測代理會讀取哪些檔案，需設計「誘使代理讀取注入內容」的策略，例如透過誘餌檔名、放置於代理必經路徑，或在執行過程中動態注入。

4. **建構評估指標系統**：實作三項量測指標：
   - **任務分數**：評估代理是否完成原始任務（採用與 Apex-Agents 一致的評分標準）
   - **攻擊暴露程度**：記錄代理是否實際讀取到注入內容
   - **攻擊成功率**：判斷代理是否執行了未授權行為

5. **執行大規模模型評估**：對 12 個前沿模型各執行 180 個任務實例，記錄每個實例的三項指標，並區分「任務完成但攻擊成功」與「任務失敗且攻擊成功」的情境。

6. **分析結果並產出報告**：依攻擊類別與模型分組統計攻擊成功率，特別關注「任務特定腳本替換」（平均 81–84%）與「攻擊者提供的通用腳本」（平均 73%）這兩類高風險攻擊，並驗證「正確交付物不等於安全行為」的核心結論。

### 潛在風險與注意事項

**評估指標的解讀陷阱**
- 僅看任務分數會嚴重低估安全風險。Gemini 3.8 Flash 雖達到最高平均任務分數 0.877，攻擊成功率仍高達 33%。實作時務必同時報告三項指標，避免以任務完成度作為安全性的代理指標。

**攻擊暴露與攻擊成功的混淆**
- 攻擊失敗可能源於代理根本未讀取到注入內容，而非代理具備防禦能力。應區分「未暴露」與「暴露後拒絕執行」兩種情況，後者才是真正的安全能力證據。

**靜態與動態注入的差異化處理**
- 動態注入需要在代理執行過程中修改工作空間內容，實作時需確保修改時機與代理的讀取行為正確對齊，否則可能產生偽陰性結果。

**腳本替換攻擊的特殊防禦需求**
- 任務特定腳本替換與攻擊者提供的通用腳本攻擊成功率遠高於其他類別，顯示現有模型對程式碼執行工具的信任過於寬鬆。實作時應考慮加入腳本來源驗證、程式碼簽章或沙箱隔離機制。

**內部與外部洩漏的雙向評估**
- 攻擊目標不僅是將資料外洩至外部（電子郵件、外部連結），也包括將私密資料寫入共享空間。評估系統需同時覆蓋這兩種洩漏路徑。

**模型版本與評估可重現性**
- 前沿模型版本更新迅速，評估結果可能隨版本變動。建議固定模型版本快照並記錄評估日期，以便跨研究比較。

### 與其他技術的整合建議

**與 MCP 伺服器生態系整合**
- APEX-Harm 的工具層完全基於 MCP 伺服器，可直接整合至任何支援 MCP 的代理框架（如 Claude Desktop、各類企業級代理平台）。建議將評估用的 MCP 伺服器配置封裝為可重複使用的 Docker 容器。

**與現有代理安全基準互補**
- APEX-Harm 專注於共享工作空間與長時程任務，與 WebArena、OSWorld、TheAgentCompany 等基準測試形成互補。建議在企業安全評估流程中，將 APEX-Harm 用於「專業領域深度評估」，將其他基準用於「通用場景廣度評估」。

**與內容安全監控平台整合**
- 將攻擊暴露程度的量測結果整合至企業的內容安全監控平台（如同儕審查系統、資料外洩防護 DLP），建立「代理讀取路徑」的可視化儀表板，協助安全團隊識別高風險檔案。

**與紅隊演練框架整合**
- APEX-Harm 的六類攻擊類別可作為結構化紅隊演練的檢查清單，與 MITRE ATT&CK 等威脅框架對應，特別是「內部人員威脅」與「供應鏈攻擊」兩個類別。

**與代理可觀測性工具整合**
- 整合 LangSmith、Langfuse 等代理可觀測性工具，記錄代理在每個任務實例中的完整決策鏈，包括讀取哪些檔案、執行哪些工具、產出哪些交付物，以便事後分析攻擊成功的根因。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，理解「共享工作空間中的內部人員攻擊」與「單一已知讀取位置的注入攻擊」之間的核心差異。掌握「正確交付物不等於安全行為」這個關鍵概念後，再瀏覽各模型的攻擊成功率數據，建立對代理安全風險的直覺。

**給 AI 工程師**：重點閱讀第 1 節的攻擊類別定義、第 3 節的實驗設計（任務實例數量、檔案規模、工具配置），以及附錄中的評估指標實作細節。特別關注 MCP 伺服器的配置方式與六類攻擊的注入點設計，這些是將基準測試轉化為內部安全評估管線的關鍵。

**給研究者**：建議完整閱讀方法論章節，特別是「攻擊者知識假設」的設計邏輯——為何區分靜態與動態注入、為何將腳本替換獨立為一類。實驗結果章節中 Opus 5（8%）與 Sonnet 5（20%）的差異，以及任務特定腳本替換的高攻擊成功率（81–84%），都是值得深入追蹤的研究問題。

**給產品經理**：重點關注「任務分數高不代表安全」這個商業意涵——Gemini 3.8 Flash 的案例顯示，選用任務表現最佳的模型可能同時引入最高的安全風險。建議在產品決策中將「攻擊成功率」列為與「任務完成率」同等重要的評估指標，並在產品路線圖中規劃代理安全監控機制。
