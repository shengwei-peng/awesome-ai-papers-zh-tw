ReproBridge 的核心方法論建立在「重現知識的形式化保存」這一假設之上：當前 ML 實驗重現失敗的主要瓶頸並非程式碼本身的缺失，而是「執行過程中恢復的隱性程序與決策」未被系統性地記錄與傳遞。為驗證此假設，作者提出了一套由三個相互耦合的元件所構成的方法論框架。

**1. 精化可重現產出物（Refined Reproducible Artifact, RRA）的標準化設計**

RRA 由四個互補元件組成，每一個元件對應一種特定類型的「執行知識」：

- **精化程式碼（Refined code）**：針對原始程式碼庫中存在的依賴衝突、資料載入器錯誤、實作細節缺失等問題進行修正。此元件將「修正行為」從對話紀錄中抽離出來，使其成為可審查、可追溯的程式碼變更。
- **環境設定（Environment setup）**：將相依套件解析過程轉化為可重複執行的安裝程序，解決 Siegeletal.(2024) 所指出的「未解析依賴」問題。
- **實驗啟動器（Experiment launchers）**：將「實驗探索」——即從眾多配置中識別出論文所述意圖配置的過程——封裝為專用腳本，使後續重現者無需重新進行此項推理。
- **重現指南（Reproduction guide）**：記錄所有決策的理由（rationale）及其影響範圍，使後續重現者能理解「為何如此設定」而非僅知「如何設定」。

此設計的關鍵洞見在於：四個元件分別對應「程式碼層」「環境層」「執行層」「知識層」的執行知識保存，缺一不可。

**2. 雙階段代理工作流（Two-stage agent workflow）**

ReproBridge 採用「人類定義標準、代理執行建構」的人機協作模式：

- **建構階段（Construction phase）**：人類定義工作流、交付標準與協議；代理負責指定實驗、準備並執行實驗，並透過審查與封裝程序保存所得程序。
- **重現階段（Reproduction phase）**：在全新的代理對話（fresh sessions）中，重現者僅接收原始程式碼庫或精化產出物，獨立嘗試重現實驗。

此設計刻意將「建構」與「重現」解耦，以排除對話歷史洩漏（conversation leakage）對評估效度的污染。

**3. 測量模型：Y = μ + D + ε**

作者採用測量學中的系統效應與隨機效應區分（Joint Committee for Guides in Metrology, 2020; Taylor and Kuyatt, 1994），將重現測量值 Y 分解為：
- **μ**：忠實執行時的期望值
- **D**：因執行選擇偏離指定實驗而產生的期望偏移（系統性偏差）
- **ε**：給定執行選擇下的零均值變異（隨機變異）

此分解的關鍵意涵在於：ReproBridge 的目標是降低 |D|（透過程序保存），而非消除 ε（隨機變異無法透過程序標準化消除）。此區分避免了將「隨機性導致的數值差異」誤判為「重現失敗」。

**4. 參考分數的統計基礎**

每個任務配備 5 個人工驗證的參考觀測值，假設其為忠實且獨立的執行（D=0），則其均值估計 μ，離散度刻畫 ε。重現相容性採用預測區間（prediction interval）評估，同時結合稽核者（Auditor）的執行證據檢查——僅憑數值相近不足以證明執行了正確的實驗。

#### 實驗數據解讀

**1. 基準規模與組成**

ReproBridge-Bench 從 742 篇 ICML 2026 Spotlight 論文出發，經過「有程式碼且非純理論內容（241 篇）→ 隨機抽樣 50 篇 → 排除 14 篇（程式碼不可用 6、計算需求過高 4、閉源模型 4）」的層層篩選，最終保留 36 篇。36 篇論文產生 1,463 個策展任務，其中 1,029 個（70.3%）通過數值相容性驗證並形成下游評估集，涵蓋 387 個實驗。剩餘 434 個任務用於區分「數值不一致」與「執行/資源障礙」。

此篩選過程揭示了一個重要事實：即便在 Spotlight 論文中，僅約 32.5%（241/742）的論文同時具備程式碼與非純理論內容，而其中僅約 70.3% 的任務能產生與參考執行相容的數值——這凸顯了 ML 重現性的系統性困境。

| Sonnet 4.6 | 72.3% | 91.6% | +19.3 | 3,165 | 2,512 | −20.6% |

- **平均成功率**：76.4% → 92.6%（+16.2 pp）
- **平均 API 支出降幅**：19.7%

**3. 結果的多層次意涵**

**(a) 弱模型受益最大**：Gemini 3.8 Flash 從 67.6% 提升至 90.8%（+23.2 pp），而 Opus 5 僅從 89.2% 提升至 94.7%（+5.5 pp）。此結果支持核心假設：精化產出物實質上是將「隱性知識」外化，使能力較弱的代理無需自行重建程序，從而縮小模型間的能力差距。

**(b) 跨模型差距的收斂**：21.6 pp 的原始差距在精化條件下縮減至 3.9 pp，且四個模型均達到 >90% 的平均成功率。這意味著「模型選擇」對重現成功的影響在精化產出物存在時大幅降低——這對實務部署具有重要意涵：組織可選擇成本較低的模型而無需犧牲重現品質。

**(c) 成本與品質的雙重改善**：精化產出物不僅提升成功率，同時降低 API 支出 16.8%–23.7%。此結果反駁了「品質提升必然伴隨成本增加」的常見假設——透過減少重複的探索與試錯，總體計算成本實際下降。

**(d) 消融實驗的元件貢獻**：移除任一元件均導致成功率下降，其中程式碼與環境移除造成的損失最大。此結果驗證了四元件設計的必要性，並指出「環境設定」與「精化程式碼」是程序保存的基礎層。

**4. 稽核機制的重要性**

作者強調「僅憑數值相近不足以證明執行了正確實驗」，因此引入獨立的稽核者（Auditor）檢查執行證據。此設計回應了 ML 重現中的一個微妙風險：代理可能透過捷徑（如使用預計算結果、替換為較簡單實驗）產生數值相近但語意不同的輸出。稽核機制將「數值相容性」與「執行完整性」解耦評估。

#### 與現有研究的比較

**1. 與程式碼代理基準的關係**

ReproBridge-Bench 與既有基準（如 SWE-bench、SIEGE 等）共享「代理執行真實任務」的範式，但有三項關鍵差異：

- **任務真實性**：以 ML 論文實驗為任務，而非一般軟體工程問題，更貼近研究社群的實際需求。
- **評估嚴謹性**：採用 5 個人工驗證參考值與預測區間，而非單一參考值，承認隨機變異的存在。
- **執行完整性檢查**：透過稽核者區分「數值相近」與「執行正確」，避免評估中的偽陽性。

**2. 與可重現性研究的關係**

Stodden et al. (2016) 主張可重現研究需要「完整的產出物」，Pineau et al. (2021) 強調程式碼釋出是重現的起點。ReproBridge 將這些倡議轉化為可操作的代理工作流與可量化的評估框架，填補了「原則倡議」與「實務工具」之間的鴻溝。

**3. 與代理輔助研究的關係**

Zhao et al. (2026b) 探討代理查閱引用論文以補充缺失資訊的能力。ReproBridge 與此形成互補：前者保存「已恢復的程序」，後者探索「恢復程序的能力」。兩者結合可形成「恢復→保存→重用」的完整閉環。

**4. 優勢與限制**

**優勢**：
- 首次系統性地將「執行知識保存」形式化為可評估的產出物設計。
- 跨模型實證顯示該設計對弱模型的增益最為顯著，具有公平性意涵。
- 雙階段工作流有效隔離建構與重現，避免評估污染。

**限制**：
- 36 篇論文的規模相對有限，且集中於 ICML 2026 Spotlight，可能存在領域偏差。
- 參考分數僅 5 個觀測值，對 ε 的估計精度有限。
- 開發流程使用 10 篇 NeurIPS/ICLR 2026 論文，雖然分開報告，但可能引入基準設計的過度擬配。
- 稽核者的可靠性未充分量化——若稽核者本身存在盲點，則「執行完整性」評估的效度受質疑。

- **跨領域泛化**：將評估從 ICML Spotlight 擴展至 NeurIPS、ICLR、CVPR 等不同會議與領域，檢驗設計的泛化性。

**3. 代理能力的提升**

- **建構階段的自動化**：當前由人類定義工作流與標準，未來可探索讓代理自主學習「什麼構成好的精化產出物」。
- **重現階段的策略學習**：精化產出物使弱模型獲益最大，但強模型仍有提升空間——可研究代理如何更有效地利用產出物中的決策理由。
- **多代理協作**：讓建構代理與重現代理透過標準化介面互動，而非僅透過產出物靜態傳遞。

**4. 與科學過程的整合**

- **產出物作為引用單元**：將 RRA 提升為可獨立引用、可版本控制的科學產出，類似軟體論文的引用慣例。
- **重現性的激勵機制**：將 RRA 品質納入論文評審或獎勵機制，從制度層面推動可重現性。
- **跨實驗室的協作重現**：探索多個實驗室同時使用同一 RRA 進行重現時的一致性與差異性。

**5. 理論基礎的建立**

當前 Y = μ + D + ε 的分解是啟發式的，未來可：
- 形式化定義「忠實執行」的語意條件。
- 建立 D 的可識別性理論——在何種觀測設計下可區分 D 與 ε。
- 探討程序保存對 D 的因果效應，而非僅觀察相關性。

## 論文問答

**Q1：為什麼機器學習實驗的重現（reproduction）如此困難？**
A：機器學習實驗的重現困難來自於論文、釋出的程式碼與支援產出物之間的資訊分散——論文中描述的程序往往省略了許多實作細節，例如不相容的相依套件如何解決、預期的配置為何、資料載入器如何修正，以及執行輸出如何對應到論文中報告的分數。這些「隱性知識」通常需要重現者自行調查與推敲，即便成功重現，這些決策也常被埋沒在對話紀錄或 shell 歷史中，迫使下一位重現者必須重複同樣的調查工作。這正是 ReproBridge 論文所稱的「重建負擔」（reconstruction burden），也是程式碼代理基準測試中常見的瓶頸來源。

**Q2：為什麼僅釋出原始程式碼庫（raw codebase）不足以解決重現問題？**
A：原始程式碼庫雖然是重現的必要起點，但僅靠程式碼本身無法承載執行過程中累積的決策與修復紀錄——例如某個 bug 是如何被發現並修正的、為何選擇某個特定的超參數值、或環境設定中某個套件版本為何被替換。這些「程序性知識」若未被系統性地保存，就會在每次重現時流失，使得後續重現者必須從頭摸索。論文的實驗數據正顯示，即使能力較強的模型（如 Opus 5）在使用原始程式碼時已達 89.2% 成功率，但較弱的模型（如 Gemini 3.8 Flash）僅有 67.6%，差距高達 21.6 個百分點，說明原始程式碼對不同能力的代理差異極大。

**Q3：為何計算可重現性（computational reproducibility）對機器學習研究領域至關重要？**
A：計算可重現性是科學累積的基石——若一項研究的結果無法被獨立驗證，其結論的可信度與後續研究的延伸都將受到質疑。論文中引用 Stodden 等人的觀點指出，僅釋出程式碼是「必要起點」，但「保存執行過程中恢復的程序」才是邁向可重複使用研究產出物的下一步。在當前 LLM 代理日益普及的研究環境中，重現的成敗不僅影響人類研究者，也直接影響程式碼代理能否可靠地複製實驗結果，進而影響整個領域的研究效率與可信度。

**Q4：ReproBridge 的核心方法是什麼？**
A：ReproBridge 是一個由人類定義工作流程、交付標準與協定，並由程式碼代理負責具體實驗的代理工作流程（agent workflow），其目標是將一篇論文與其官方程式碼庫轉化為「精化可重現產出物」（Refined Reproducible Artifact, RRA）。具體而言，代理會從論文中擷取實驗規格、準備並執行實驗，並透過審查與封裝程序將恢復的程序保留下來。隨後的「重現者」（Reproducer）會在全新的對話中接收 RRA 或原始程式碼庫，並嘗試重現實驗，由獨立的「稽核者」（Auditor）檢查執行證據。

**Q5：RRA（精化可重現產出物）的關鍵創新為何？**
A：RRA 的關鍵創新在於將「執行過程中恢復的隱性知識」系統性地編碼為四個標準化元件：精化程式碼（refined code）、環境設定（environment setup）、實驗啟動器（experiment launchers）與重現指南（reproduction guide）。這四個元件分別對應論文中提到的三類程序：相依套件解析變成安裝程序、實驗探索變成專屬啟動器、修正則成為附帶理由與影響範圍的文件化決策。這種設計使得重現工作從「從零調查」轉變為「依循既有程序」，大幅降低了重建負擔。

**Q6：為何 RRA 選擇這四個元件，而非其他可能的設計？**
A：這四個元件的選擇反映了論文中假設的核心機制：重現失敗主要源於程式碼缺失、環境錯誤、實驗啟動不明確與決策缺乏記錄。論文的消融實驗（ablation study）驗證了這一設計——移除任何一個元件都會降低成功率，其中移除程式碼與環境造成的損失最大。這說明元件之間具有互補性：缺少精化程式碼會讓代理無法理解實作細節，缺少環境設定則會讓代理在安裝階段就失敗，缺少啟動器會讓代理難以發現正確的實驗配置，缺少指南則會失去決策的脈絡與理由。

**Q7：ReproBridge-Bench 是如何建構的？其規模與代表性為何？**
A：ReproBridge-Bench 從 742 篇 ICML 2026 Spotlight 論文開始篩選，先挑出 241 篇有程式碼且非純理論內容的論文，再隨機抽樣 50 篇，最終排除 14 篇（6 篇因產出物或程式碼不可用、4 篇因計算需求過高、4 篇因閉源模型限制）後保留 36 篇。這 36 篇論文涵蓋 502 個實驗與 1,463 個經策展的任務，其中 1,029 個任務（70.3%）具有數值相容的參考結果，構成下游評估集。每個任務都有五位人類重現者在獨立伺服器上產生的參考分數，並經人工驗證，確保基準的可靠性與公平性。

**Q8：ReproBridge 的主要實驗結果為何？**
A：跨四個程式碼代理的評估顯示，使用 RRA 後平均重現成功率從 76.4% 提升至 92.6%，提升幅度達 16.2 個百分點；下游 API 支出平均減少 19.7%。更具體地看，Sonnet 4.6 從 72.3% 提升至 91.6%（+19.3 pp）、Sonnet 5 從 76.5% 提升至 93.3%（+16.8 pp）、Opus 5 從 89.2% 提升至 94.7%（+5.5 pp）、Gemini 3.8 Flash 從 67.6% 提升至 90.8%（+23.2 pp）。值得注意的是，跨模型成功率差距從 21.6 個百分點縮小至僅 3.9 個百分點，且所有四個模型皆達到 90% 以上的平均成功率。

**Q9：消融實驗揭示了哪些關於各元件貢獻的洞見？**
A：消融實驗顯示，移除 RRA 中的任何一個元件都會降低重現成功率，其中移除精化程式碼與環境設定造成的損失最大。這印證了論文的假設：重現失敗的根源主要在於程式碼實作細節的缺失與環境配置的錯誤。相對而言，移除實驗啟動器或重現指南的影響較小，但仍不可忽視——這說明四個元件共同構成一個完整的「執行知識保存」系統，缺一不可。

**Q10：ReproBridge 在哪些實際情境中能發揮作用？**
A：ReproBridge 特別適用於需要重現最新機器學習論文的場景，例如學術界的研究者欲驗證某篇論文的結果、產業團隊欲基於公開研究建立產品、或程式碼代理開發者欲評估其模型在真實研究任務上的表現。對於計算資源有限的團隊，RRA 的標準化設計也能降低重現的入門門檻，因為環境設定與啟動器已預先準備好。此外，RRA 對於「重現後再延伸」的工作流程特別有價值——後續研究者可以在既有程序基礎上進行修改，而不必從零開始調查。

**Q11：若要將 ReproBridge 整合到產品中，需要考量哪些實務因素？**
A：產品化時首先需考量的是「參考分數收集」的成本——每個任務需要五位人類重現者在獨立環境中執行，這在規模化時會成為瓶頸。其次是「稽核者」機制的設計：稽核者需檢查執行證據以避免「數字相近但實驗被替換」的情形，這需要可靠的執行軌跡記錄與自動化工具支援。此外，RRA 的維護也是挑戰——當原始程式碼或論文更新時，RRA 需相應更新，否則可能成為「過時的程序」反而阻礙重現。

**Q12：ReproBridge 對機器學習研究領域的潛在影響為何？**
A：ReproBridge 的最大潛在影響在於「拉平重現能力的差距」——透過 RRA，即使是能力較弱的模型也能達到 90% 以上的成功率，這意味著重現不再高度依賴頂尖模型或專家知識。這對於資源較少的研究機構或開發中的程式碼代理特別有利。此外，論文中提出的「保存執行知識」概念可能成為新的研究產出標準，促使未來的論文發表不僅要求釋出程式碼，還要求釋出「可重現的程序」，進而提升整個領域的可信度與累積效率。

**Q13：ReproBridge 論文承認了哪些限制？**
A：論文的限制之一是基準的代表性——36 篇論文皆來自 ICML 2026 Spotlight，雖然涵蓋多個研究領域，但未必能代表所有機器學習研究的重現難度。此外，1,029 個任務中僅 70.3% 具有數值相容的參考結果，其餘 434 個任務因數值不一致或執行與資源障礙而被排除，這暗示真實世界的重現成功率可能低於論文報告的數字。最後，論文的評估僅針對四個程式碼代理，其他模型或人類重現者的表現尚未被系統性比較。

**Q14：ReproBridge 在哪些情況下可能會失敗？**
A：當原始程式碼本身存在根本性的錯誤或缺失時，RRA 無法「無中生有」——它只能保存恢復的程序，無法創造不存在的實作。此外，若論文的描述與程式碼嚴重矛盾，且人類未能介入釐清，代理可能會做出錯誤的決策並將其編碼進 RRA，反而將錯誤「固化」並阻礙後續重現。另一個失敗情境是當計算資源需求極高時，即使有完善的啟動器與指南，重現者仍可能因資源限制而無法完成實驗，這也是論文中排除 4 篇論文的理由之一。

**Q15：ReproBridge 未來可以朝哪些方向發展？**
A：未來發展方向之一是「自動化參考分數收集」——減少對人類重現者的依賴，例如透過多代理共識或統計模型估計參考值，以降低基準建構成本。另一方向是「RRA 的動態更新機制」——當原始程式碼或論文更新時，自動偵測並提示 RRA 需要重新驗證，以避免程序過時。此外，將 ReproBridge 擴展至其他類型的研究產出物（如資料集、模型權重檔）以及非機器學習領域（如科學計算、統計分析）也是值得探索的方向，這將使「保存執行知識」的概念成為更廣泛的科學實踐。

## 實務應用指南

### 適用場景

1. **學術論文的第三方重現驗證**：當期刊、會議審稿人或研究團隊需要獨立驗證 ML 論文的實驗結果時，可使用 ReproBridge 將作者釋出的原始程式碼轉化為精化可重現產出物（RRA），讓審稿人在不依賴原作者的情況下完成數值相容的重現。

2. **企業 ML 團隊的模型交接與知識保存**：當資深 ML 工程師離職或轉調時，團隊可透過 ReproBridge 工作流程將其專案中隱含的執行決策（依賴解析、配置選擇、資料載入器修復）系統化保存為 RRA，避免下一位接手者重複踩坑。

3. **ML 基準測試（Benchmark）的建構與維護**：研究機構欲建立特定領域（如醫療影像、推薦系統）的可重現基準時，可採用 ReproBridge-Bench 的任務定義、參考分數收集與稽核者（Auditor）機制，產出可信賴的評測基準。

4. **AI 程式碼代理的內部評估平台**：模型開發商（如 Anthropic、Google）在評估自家程式碼代理的 ML 重現能力時，可將 ReproBridge-Bench 的 1,029 個任務作為標準化測試集，並比較「原始程式碼」與「精化產出物」兩種條件下的表現差異。

5. **ML 教學與教材的標準化製作**：教育機構或線上學習平台可利用 ReproBridge 將頂會論文的實驗轉化為可一鍵執行的教材包（包含環境設定、啟動器、指南），降低學生重現論文的門檻。

### 實作前置條件

**資料需求**
- 目標論文的 PDF 全文與官方程式碼儲存庫（須有可訪問的 commit hash）
- 每個任務至少 5 組人工驗證的參考分數，用於建立預測區間
- 論文中主表格的「自有方法」測量結果（資料集、指標、報告統計量、表格位置四元組）

**運算資源**
- 至少 5 台獨立伺服器或容器環境，用於平行收集參考分數並避免相互污染
- 與原論文相符的 GPU 規格（如原論文使用 A100，則需配置 A100）
- 程式碼代理的 API 額度（依論文規模，單篇重現 API 成本約 USD 300–3,500）

**技能門檻**
- ML 工程：熟悉 PyTorch/JAX、依賴管理（Conda/pip）、Docker 容器化
- 代理編排：能設計多階段代理工作流程（規格制定 → 準備 → 執行 → 審查 → 打包）
- 評測設計：理解預測區間、系統性偏差（𝐷）與隨機變異（𝜀）的區別
- 領域知識：對目標論文所屬子領域（如強化學習、電腦視覺）有基本理解

### 實作步驟建議

**步驟 1：建立任務清單與參考分數**
從目標論文中識別主表格的「自有方法」測量項，每項定義為一個任務（資料集 × 指標 × 統計量 × 位置）。邀請 5 位人工重現者在獨立環境中執行同一 pinned commit，收集 5 組參考分數作為 ground truth。

**步驟 2：設計 RRA 的四元件結構**
依據論文中定義的標準化產出物，建立以下四個目錄：
- `refined_code/`：修復後的程式碼（解析依賴、修正資料載入器）
- `env/`：環境設定檔（Conda environment、Dockerfile、版本鎖定）
- `launchers/`：實驗啟動器腳本（將配置與執行分離）
- `guide/`：重現指南（記錄每個決策的理由與影響範圍）

**步驟 3：實作 ReproBridge 代理工作流程**
- **規格階段**：代理讀取論文與原始程式碼，輸出每個任務的執行規格
- **準備階段**：代理解析依賴、修復資料載入器、撰寫啟動器
- **執行階段**：代理在隔離環境中執行任務並收集輸出
- **審查階段**：代理比對輸出與參考分數，記錄偏差與修復決策
- **打包階段**：將所有決策、理由、影響任務整合進 RRA

**步驟 4：建立稽核者（Auditor）機制**
設計獨立的稽核代理，檢查執行證據（log 檔、checkpoint、隨機種子），而非僅比對數值。數值相近但實驗被替換是常見的偽重現，必須透過證據鏈防堵。

**步驟 5：執行消融實驗驗證元件價值**
依論文消融結果，程式碼與環境移除造成的成功率損失最大。建議在自家工作流程中對每個元件進行移除測試，確認四元件缺一不可。

**步驟 6：部署為可重用的產品**
將 RRA 打包為 Docker image 或 Conda pack，提供 CLI 入口（如 `reprobridge run --task <task_id>`），並整合 CI/CD 流程以支援新論文的持續接入。

### 潛在風險與注意事項

**風險 1：參考分數的隨機變異被誤判為失敗**
ML 訓練本身具隨機性（𝜀），即使正確執行也可能落在參考區間外。緩解方式：採用預測區間而非單一閾值，並在評測中報告多次重複的標準差。

**風險 2：數值相容但實驗被替換**
代理可能透過捷徑（如使用預訓練權重、簡化模型）達到相近數字，但未執行原指定實驗。緩解方式：稽核者必須檢查執行證據（log、checkpoint、隨機種子），而非僅比對最終數值。

**風險 3：依賴解析的遞移成本**
論文中常使用已棄用的套件版本，解析過程可能觸發連鎖衝突。緩解方式：使用 Docker 鎖定基礎映像版本，並在 RRA 中記錄每個依賴決策的理由。

**風險 4：跨模型表現差異被低估**
論文顯示原始程式碼條件下跨模型成功率差距達 21.6 個百分點，若僅用單一模型評估會高估或低估工作流程價值。緩解方式：至少使用 3 個不同模型（如 Sonnet、Opus、Gemini）進行交叉驗證。

**風險 5：RRA 維護成本隨論文數量線性成長**
每篇論文需要 5 組人工參考分數，規模化時成本急劇上升。緩解方式：採用抽樣策略（如每領域 10–20 篇代表論文），並建立半自動化的參考分數驗證流程。

**風險 6：代理決策缺乏可追溯性**
代理在修復過程中做出的隱含決策若未記錄，會在後續重現時遺失。緩解方式：強制要求每個決策附帶「理由」與「影響任務清單」，並寫入 `guide/`。

### 與其他技術的整合建議

**與 MLOps 平台整合**
將 RRA 的四元件結構對應到 MLflow 或 Weights & Biases 的元件：精化程式碼對應 Git repo、環境設定對應 Conda/Docker artifact、啟動器對應 MLflow Project、重現指南對應 Model Card。

**與 CI/CD 整合**
在 GitHub Actions 或 GitLab CI 中設定定期重現任務：每次 RRA 更新時自動觸發重現者代理，比較新結果與參考分數，產生差異報告。

**與程式碼代理框架整合**
ReproBridge 的工作流程可基於 LangGraph、AutoGen 或 CrewAI 等代理編排框架實作。建議將「規格 → 準備 → 執行 → 審查 → 打包」對應為獨立的代理節點，並透過共享狀態傳遞決策記錄。

**與論文管理系統整合**
可串接 Semantic Scholar、arXiv API 自動抓取新論文的程式碼儲存庫，觸發 RRA 建構流程。整合 OpenReview API 可在論文審稿階段自動產生 RRA，供審稿人使用。

**與基準測試平台整合**
ReproBridge-Bench 的任務定義可整合至 HELM、MLPerf 等基準平台，作為「重現能力」的專屬維度，補充現有基準對「執行程序」的忽略。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題陳述與圖 1，理解「為什麼釋出程式碼還不足以重現」這個核心問題。接著跳讀第 3.2 節了解 RRA 的四元件結構，嘗試用一個小型開源 ML 專案（如 MNIST 分類）手動建立迷你版 RRA，感受四元件如何分工。

**給 AI 工程師**：重點閱讀第 3.1 節的工作流程設計與第 4 節的評測結果。特別關注消融實驗（程式碼與環境移除影響最大）與跨模型差距（精化產出物將差距從 21.6 縮窄至 3.9 個百分點），這兩個發現直接指導生產環境中代理工作流程的設計權衡。

**給研究者**：建議深入閱讀第 2.1 節的測量模型（𝑌 = 𝜇 + 𝐷 + 𝜀）與第 2.3 節的參考分數收集協議。這套形式化框架區分了系統性偏差與隨機變異，是設計任何 ML 重現研究的理論基礎。附錄 D.7 的開發集（10 篇 NeurIPS/ICLR 論文）提供了工作流程迭代的具體經驗。

**給產品經理**：聚焦於圖 1 的商業價值圖表——精化產出物不僅提升成功率（76.4% → 92.6%），還降低 19.7% 的 API 成本。這意味著 RRA 不是學術奢侈品，而是直接影響 ROI 的工程投資。建議在產品路線圖中將「RRA 建構」定位為 ML 專案交付的標準環節，而非可選附加項。
