現有環境擴展方法僅在單一環境內生成任務，無法處理跨服務的工作流程。
本文提出 CompoWorld 框架，透過服務函式庫與隨機遊走依賴圖組合跨環境任務。

## 摘要翻譯

自動生成的環境為訓練通用代理提供了可擴展的互動資料來源。然而，現有方法主要在單一環境內生成任務，而真實世界的工作流程要求代理跨多個服務串接資訊與動作。我們提出組合式環境擴展（Compositional Environment Scaling，CompoWorld），透過組合一個有限的可重複使用服務函式庫來擴展任務空間。程式編寫代理（Coding Agent）將工具規格說明（Tool Specification）轉化為具有型別化狀態（Typed State）與共享介面（Shared Interface）的已驗證服務，而世界模型（World Model）則處理無法可靠實作的工具。隨機遊走程序（Random-Walk Procedure）透過依賴圖（Dependency Graph）連接服務，使需要跨服務資訊流動的任務得以生成與驗證。已驗證軌跡（Verified Trajectory）支援監督式微調（Supervised Fine-Tuning，SFT），而我們的聚焦完成度的評分獎勵（Completion-Focused Rubric Reward）透過強調每個採樣批次群組（Rollout Group）中通過率（Pass Rate）較低的評分標準，引導強化學習（Reinforcement Learning，RL）朝向完整任務完成。我們構建了 448 個服務，提供 10,130 個工具，並使用 3K 筆 SFT 軌跡與 1K 個 RL 任務來訓練 Qwen3.6-35B-A3B。實驗結果顯示，CompoWorld 在八個基準測試（Benchmark）上平均較其基礎模型（Backbone）提升 9.17 分。在 AutomationBench 上，它超越了 Claude Opus 4.6 等前沿模型（Frontier Model），並在所有參與比較的代理專用 35B-A3B 模型中領先。

### 核心貢獻（3～5點）
- 提出 **CompoWorld** 框架，透過組合有限的可重複使用服務函式庫來擴展任務空間，突破現有方法僅能在單一環境內生成任務的限制。
- 設計雙軌服務建構機制：由程式編寫代理將工具規格說明轉化為具型別化狀態與共享介面的已驗證服務，並由世界模型處理無法可靠實作的工具，兼顧覆蓋率與可靠性。
- 引入隨機遊走程序，透過依賴圖連接服務並進行驗證，使生成的任務能自然呈現真實工作流程中跨服務的資訊流。
- 提出聚焦完成度的評分獎勵，於強化學習中動態強調採樣批次群組內通過率較低的評分標準，有效引導代理朝向完整任務完成。
- 在八個基準測試上平均較基礎模型提升 9.17 分，並於 AutomationBench 超越 Claude Opus 4.6 等前沿模型，同時領先所有參與比較的代理專用 35B-A3B 模型。

### 適合對象
從事大型語言模型代理（LLM Agent）訓練、強化學習、程式編寫代理、互動式環境合成，以及對代理式強化學習（Agentic RL）、組合泛化（Compositional Generalization）與環境擴展（Environment Scaling）感興趣的研究者與工程師；亦適合關注通用代理在多應用程式基準（Multi-Application Benchmark）上表現的業界實務團隊。

## 深度分析

#### 方法論解析

CompoWorld 的核心設計理念是將「環境擴展」（environment scaling）從單一環境內部的任務生成，提升到跨服務組合的層次。其方法論可拆解為三個相互耦合的子系統：

**1. 服務建構層（Service Construction Layer）**

作者從公開的 Model Context Protocol（MCP）實作中收集工具規格說明（tool specifications），並透過「程式編寫代理」（coding agent）在受控環境（harness）中將其轉化為可執行的模擬服務（mock services）。每個服務具備三項關鍵屬性：
- **型別化狀態（typed state）**：以 Python 型別系統描述服務內部狀態，確保跨服務的狀態可序列化、可檢查。
- **共享介面（shared interface）**：所有服務遵循統一的工具呼叫介面，使代理無需為不同服務學習不同的呼叫慣例。
- **轉移邏輯（transition logic）**：明確定義每個工具對狀態的影響，便於後續驗證任務的可達性（reachability）。

對於無法可靠實作的長尾工具（long-tail tools），CompoWorld 採用「世界模型」（world model）作為模擬器。這種混合設計（hybrid design）保留了服務的完整工具介面，使部分操作被模擬的服務仍能參與組合工作流程，這是相當務實的工程取捨。

**2. 任務合成層（Task Synthesis Layer）**

任務生成採用「隨機遊走程序」（random-walk procedure）在服務函式庫中抽樣並連接成「服務級依賴圖」（service-level dependency graph）。圖中每個節點代表一個獨立可執行的服務，每條有向邊表示資訊或狀態從來源服務流向目標服務。值得注意的是，依賴圖僅描述「哪些服務之間存在因果依賴」（causal dependency），而不規定具體的工具呼叫序列，這給予代理規劃上的彈性。

給定選定的服務集合與依賴圖後，任務生成代理（task-generation agent）負責：
- 實例化初始狀態（initial states）
- 定義目標（goals）與約束（constraints）
- 透過「驗證探測」（verification probes）檢查所需轉移的可達性與成功條件的可滿足性（satisfiability）

這個「生成—驗證」（generation-and-verification）過程本身也是代理式的（agentic），意味著任務品質依賴於驗證代理的能力。

**3. 訓練層（Training Layer）**

訓練採用兩階段策略：
- **監督式微調（SFT）**：使用已驗證的成功軌跡（verified trajectories）作為示範資料，共 3K 條。
- **代理式強化學習（RL）**：採用 Group Relative Policy Optimization（GRPO）框架，搭配作者提出的「聚焦完成的評分獎勵」（Completion-Focused Rubric Reward）。

聚焦完成的評分獎勵是本論文的關鍵技術貢獻之一。在跨環境任務中，多個條件必須同時成立才算成功，部分完成的工作流程仍可能無法滿足使用者目標。傳統的二元獎勵（成功/失敗）會產生稀疏且無資訊量的梯度。評分獎勵（rubric reward）提供分級信用，即使沒有任何採樣完全成功，也能給予部分條件滿足的回饋。而「聚焦完成」的設計則在每個採樣批次群組（rollout group）內，對通過率較低的評分標準賦予更高權重，將學習訊號集中於尚未滿足的需求上，推動代理朝向完整任務完成。

#### 實驗數據解讀

**整體效能提升**

以 Qwen3.6-35B-A3B 為基礎模型（backbone），CompoWorld 在八個基準測試上平均提升 9.17 分。這個數字在當前代理訓練研究中屬於顯著改善，特別是考慮到訓練資料規模僅為 3K SFT 軌跡與 1K RL 任務，遠小於許多競爭方法。

**AutomationBench 上的突出表現**

在 AutomationBench 上，CompoWorld 達到 32.33% 的任務成功率（+22.00 分），超越：
- GPT-5.4（27.67%）
- Claude Opus 4.6（25.50%）

並接近 DeepSeek-V4-Flash（36.33%）。同時領先所有六個參與比較的代理專用 35B-A3B 模型。這項結果特別值得注意，因為：
1. 它顯示 CompoWorld 的訓練方法對跨服務工作流程具有實質價值。
2. 一個 35B 規模的開源模型能超越前沿封閉模型（frontier models），暗示組合式訓練資料的品質可能比單純的模型規模更為關鍵。
3. 在同類代理專用模型中取得領先地位，驗證了方法論的相對優勢。

**資料效率的意涵**

3K SFT + 1K RL 的資料規模相當精簡，這暗示：
- 服務函式庫（448 服務、10,130 工具）提供了豐富的組合空間，少量任務即可覆蓋多樣的依賴模式。
- 驗證機制確保了訓練資料的高品質，避免了錯誤示範的負面影響。
- 評分獎勵設計提升了 RL 階段的樣本效率。

然而，論文中未詳細說明八個基準測試的個別分數，僅提供平均值與 AutomationBench 的數據，這限制了我們對方法在不同任務類型上表現差異的深入理解。

#### 與現有研究的比較

**與環境擴展相關工作的比較**

CompoWorld 與 AgentScaler、ScaleEnv、Agent-World 等同類工作共享「自動化環境建構」的核心目標，但差異在於：
- 這些方法主要在單一環境內部生成任務，而 CompoWorld 將組合性提升到跨服務層次。
- CompoWorld 的服務是「獨立可執行」的，可重複使用於不同任務，這與 EnvScaler 等分離骨架與情境的方法有所不同。
- 與 Terminal-Universe 相比，CompoWorld 不依賴從代理軌跡重建工作區，而是從工具規格說明自下而上建構服務。

**與組合泛化研究的比較**

CompWoB 透過組合基本網頁任務研究組合泛化，AppWorld 擴展到多應用程式工作流程，Voyager 建立可重複使用的技能函式庫。CompoWorld 的定位是「訓練分布」（training distribution）層面的組合：透過重組獨立可執行的服務及其因果依賴圖，使代理學習在熟悉服務的新組合中協調資訊流。這與 Compositional Skill Routing 的「分解—檢索—組裝」規劃路徑形成互補。

**方法論優勢**

1. **可控的組合維度**：依賴圖將服務組合本身變為可控制的訓練環境生成參數。
2. **混合實作策略**：結合程式編寫代理與世界模型，兼顧可靠性與覆蓋率。
3. **聚焦完成的獎勵設計**：直接針對跨環境任務中常見的部分完成問題。

**潛在限制**

1. **服務品質依賴於程式編寫代理**：自動建構的服務可能存在未偵測的錯誤，影響下游任務的可信度。
2. **世界模型的模擬偏差**：對於無法可靠實作的工具，世界模型的行為可能與真實服務不一致，代理可能學到在真實環境中失效的捷徑。
3. **任務驗證的代理依賴性**：驗證探測本身由代理執行，其能力上限決定了任務品質的天花板。
4. **基準測試覆蓋**：八個基準測試的具體組成未在提供的文本中說明，難以判斷方法在不同領域的泛化能力。

#### 可重現性評估

根據提供的文本，CompoWorld 的關鍵資源包括：
- **服務函式庫**：448 個服務、10,130 個工具
- **訓練資料**：3K SFT 軌跡、1K RL 任務
- **基礎模型**：Qwen3.6-35B-A3B

論文中未明確說明程式碼、資料集與模型權重是否開源。從目前的描述來看：

- 訓練資料的產生涉及多個代理（任務生成代理、驗證代理、軌跡收集代理），其提示與配置對重現至關重要。
- 評分獎勵的權重計算與 GRPO 的超參數同樣需要公開。

#### 未來研究方向

**1. 服務品質的自動化改進**

目前服務建構依賴程式編寫代理的一次性生成，未來可引入：
- 自動測試生成與模糊測試（fuzzing）以發現服務中的邊界情況錯誤。
- 形式化驗證（formal verification）對關鍵轉移邏輯進行數學證明。
- 持續整合式的服務健康監控，在組合任務執行時即時偵測不一致。

**2. 世界模型的強化學習**

對於長尾工具，世界模型目前是靜態的模擬器。可探索：
- 使用代理軌跡持續微調世界模型，使其更貼近真實服務行為。
- 引入不確定性估計，讓代理在世界模型信心較低時採取保守策略。
- 結合符號推理與神經模擬，兼顧可解釋性與表達能力。

**3. 依賴圖結構的學習**

隨機遊走程序目前是均勻抽樣，未來可：
- 學習依賴圖的結構分布，使訓練任務覆蓋更重要的組合模式。
- 引入課程學習（curriculum learning），從簡單依賴逐步過渡到複雜依賴。
- 分析依賴圖的圖論性質（如樹寬、環結構）對代理學習效率的影響。

**4. 評分獎勵的理論分析**

聚焦完成的評分獎勵目前是啟發式設計，可進一步：
- 從資訊理論角度分析其與 GRPO 優勢估計的互動。
- 探索自適應權重調整策略，避免對單一評分標準過度聚焦。
- 與過程獎勵模型（process reward models）結合，提供更細粒度的學習訊號。

**5. 跨領域遷移研究**

CompoWorld 目前聚焦於數位工作流程，可探索：
- 將組合式環境擴展應用於機器人控制、科學實驗設計等領域。
- 研究服務抽象在不同領域間的可遷移性，例如將「資料庫查詢」抽象為通用的「結構化資料存取」服務。
- 結合多模態輸入（圖像、音訊）擴展服務的感知能力。

**6. 人機協作的工作流程生成**

目前任務完全由代理自動生成，未來可：
- 讓人類專家定義高階的依賴模式，由代理實例化具體任務。
- 引入人類回饋對服務組合進行偏好對齊（preference alignment）。
- 探索代理在真實企業環境中部署時的安全性與可控性邊界。

**7. 規模化的理論極限**

448 服務、10,130 工具的規模已相當可觀，但組合空間的理論上限遠未觸及。未來可研究：
- 服務數量與代理泛化能力之間的縮放定律（scaling laws）。
- 組合爆炸（combinatorial explosion）下訓練資料取樣的最優策略。
- 服務冗餘度與組合多樣性之間的權衡。

## 論文問答

**Q1：CompoWorld 想要解決的核心問題是什麼？**
A：CompoWorld 旨在解決現有自動化環境生成方法僅能在單一環境內生成任務的限制。真實世界的工作流程通常需要代理跨多個服務協調資訊與動作，例如查詢資料庫、查閱 PDF 手冊、發送電子郵件等。現有方法如 AgentScaler、ScaleEnv 和 Agent-World 主要擴展環境多樣性，但未處理跨服務依賴關係。CompoWorld 將服務組合本身視為環境擴展的可控維度，目標是訓練代理在新型組合中協調熟悉的服務。

**Q2：為什麼現有的環境擴展方法不足以應對真實世界的代理任務？**
A：現有方法主要關注單一環境內的工具互動，無法模擬真實工作流程中跨系統的狀態耦合。真實任務的成功取決於在多個系統之間傳遞正確的資訊與約束，而非僅僅執行更多工具呼叫。此外，現有方法缺乏對服務組合本身的控制，難以系統性地擴展任務空間。CompoWorld 透過可重複使用的執行服務與任務特定的因果依賴圖來解決這些限制。

**Q3：為什麼組合泛化對通用代理至關重要？**
A：組合泛化要求代理能在新的任務結構中重複使用熟悉的工具與技能，同時尊重動作與環境狀態之間的依賴關係。CompWoB 等研究顯示，單一任務上的強勁表現無法可靠地遷移到其組合上。AppWorld 等基準測試已將評估擴展到跨應用程式的工作流程，要求代理協調 API 呼叫與狀態變更。CompoWorld 透過訓練分布的重組來追求這一方向，使代理能夠處理未見過的服務組合。

**Q4：CompoWorld 的核心方法是什麼？**
A：CompoWorld 從可重複使用的執行服務建構跨環境任務，每個服務擁有型別化狀態、暴露工具集並定義轉移邏輯。服務透過隨機遊走程序組合成服務級依賴圖，其中節點代表獨立可執行的服務，有向邊表示資訊或狀態的流動需求。給定選定的服務與圖形，任務生成代理實例化初始狀態、目標與約束，而驗證探測測試所需轉移的可達性與成功條件的可滿足性。

**Q5：聚焦完成的評分獎勵（Completion-Focused Rubric Reward）的關鍵創新是什麼？**
A：聚焦完成的評分獎勵為每個採樣批次群組中通過率較低的評分標準分配較高的權重，將強化學習訊號聚焦於未滿足的需求上。這與 GRPO 結合使用，能在沒有任何採樣完全成功時仍提供分級信用。跨環境任務需要多個條件同時成立，部分工作流程的完成仍可能無法滿足使用者目標，因此這種獎勵設計能有效促進完整任務完成。

**Q6：CompoWorld 在服務建構方面有哪些關鍵設計選擇？**
A：CompoWorld 使用型別化 Python 結構來標準化服務狀態與互動介面，確保自動生成的服務能可靠執行且彼此相容。系統從公開的 MCP 實作中收集工具規格說明，並使用程式編寫代理在框架內建構可執行的模擬服務。對於無法可靠實作的長尾工具，世界模型作為模擬器介入。這種混合設計保留了每個服務的完整工具介面，使其即使在某些操作被模擬的情況下仍能參與組合工作流程。

**Q7：CompoWorld 使用哪些基準測試進行評估？**
A：CompoWorld 在八個具有挑戰性的代理基準測試上進行評估，其中 AutomationBench 是最突出的基準。在 AutomationBench 上，CompoWorld 達到 32.33% 的任務成功率（+22.00 點），超越了 GPT-5.4（27.67%）與 Claude Opus 4.6（25.50%），並接近 DeepSeek-V4-Flash（36.33%）。這些基準測試涵蓋了不同類型的代理任務，能全面評估跨服務工作流程的能力。

**Q8：CompoWorld 的關鍵實驗結果為何？**
A：CompoWorld 在八個基準測試上平均比其基礎模型提升了 9.17 點，展現了訓練方法對跨服務工作流程的顯著價值。在 AutomationBench 上，它超越了 Claude Opus 4.6 等前沿模型，並在所有比較的代理專用 35B-A3B 模型中領先。訓練使用了 3K 個監督式微調軌跡與 1K 個強化學習任務，證明了相對適中的訓練資料量即可帶來顯著效能提升。

**Q9：聚焦完成的評分獎勵如何影響整體效能？**
A：聚焦完成的評分獎勵透過強調未滿足的條件來引導強化學習，使代理更專注於達成完整任務而非部分進度。這在跨環境任務中特別重要，因為多個條件需要同時成立才能算成功。結合 GRPO，該獎勵設計在採樣群組內動態調整權重，確保學習訊號始終指向最具改進空間的面向，從而提升整體任務完成率。

**Q10：CompoWorld 能支援哪些實際應用場景？**
A：CompoWorld 能支援需要跨多個服務協調的企業自動化場景，例如從 Snowflake 資料庫查詢逾期工單、查閱 PDF 操作手冊確定所需回應，再透過電子郵件通知管理層與客戶。這類工作流程在現實商業環境中極為常見，但傳統單一環境訓練的代理難以勝任。此外，該框架也適用於需要整合 Slack、行事曆、資料庫等多種工具的複雜任務編排。

**Q11：從產品化的角度，CompoWorld 帶來哪些考量？**
A：CompoWorld 採用型別化 Python 結構與 MCP 工具規格說明，使其能與已暴露 API 的現有企業系統整合。混合設計（真實服務加上世界模型模擬）允許在不影響真實系統的情況下進行安全訓練。448 個服務與 10,130 個工具的規模展示了框架的可擴展性，但也意味著產品化時需要考慮服務維護、更新與版本控制的成本。

**Q12：CompoWorld 對代理研究領域的更廣泛影響是什麼？**
A：CompoWorld 將服務組合確立為環境擴展的可控維度，連結了環境建構與組合泛化這兩個研究方向。它提供了一個框架，用於訓練能遷移到未見任務組合的代理，對任何需要多系統協調的領域都有意義。此外，該工作強調了任務特定因果依賴的重要性，為未來研究更複雜的依賴結構與組合模式奠定了基礎。

**Q13：CompoWorld 存在哪些已承認的限制？**
A：CompoWorld 承認部分工具無法可靠實作而需要世界模型模擬，這可能引入與真實工具行為的偏差。框架的效能依賴於 MCP 工具規格說明的品質以及程式編寫代理將其轉化為可執行程式碼的能力。雖然 448 個服務與 10,130 個工具規模可觀，但仍可能無法涵蓋所有可能的真實世界服務組合，限制了某些專業領域的適用性。

**Q14：CompoWorld 可能遭遇哪些失敗案例？**
A：潛在的失敗案例包括：當世界模型模擬偏離真實工具行為時，代理可能學到錯誤的互動模式；當服務依賴過於複雜時，隨機遊走程序可能生成無法解決的任務；當驗證探測未能偵測到不可滿足的成功條件時，可能產生無法驗證的任務；以及當評分獎勵誤判部分完成度時，可能引導代理走向次優策略。

**Q15：CompoWorld 的未來發展方向有哪些？**
A：未來發展方向包括擴展服務函式庫以涵蓋更多專業領域、提升世界模型的擬真度以減少模擬偏差、探索更複雜的依賴結構（如多層級或循環依賴），以及將框架應用於當前基準測試之外的領域。此外，研究如何讓代理更好地處理部分可觀察的環境狀態、動態服務變化，以及與人類使用者的協作互動，也是值得探索的方向。

## 實務應用指南

### 適用場景

**1. 企業跨系統工作流程自動化**
適用於需要同時操作 ERP、CRM、HR 系統與內部資料庫的場景。例如：自動從 Snowflake 撈取逾期帳單、查閱 PDF 內部作業手冊、透過 Slack 通知負責人並寄送電子郵件給客戶。CompoWorld 的服務組合機制可直接對應此類多步驟、多應用程式的真實業務流程。

**2. 客服與工單協調代理**
在客服場景中，代理需同時查閱知識庫（PDF/Notion）、更新工單系統（ServiceNow/Jira）、通知工程團隊（Slack/Email）、並回覆客戶。CompoWorld 的依賴圖生成可模擬此類「資訊必須跨服務流動」的情境，訓練代理正確傳遞約束條件。

**3. DevOps 與監控自動化**
用於建構能同時操作 GitHub、CI/CD 平台、雲端監控（CloudWatch/Prometheus）與通知系統的代理。當監控告警觸發時，代理需查詢相關 commit、判斷是否為已知問題、建立 ticket 並通知值班工程師。

**4. 金融與合規審查流程**
適用於需要跨多個內部系統驗證交易合規性的場景：查詢交易紀錄（資料庫）、比對法規文件（PDF）、更新審查狀態（內部系統）、通知合規團隊（Email/Slack）。CompoWorld 的可驗證任務設計特別適合此類需要嚴格驗證的場景。

**5. 研究助理與文獻綜合**
學術研究助理需同時操作 arXiv、Zotero、PDF 閱讀器、筆記系統與參考管理工具。CompoWorld 可訓練代理在多個研究工具間正確傳遞引用、摘要與標註資訊。

### 實作前置條件

**資料需求**
- **MCP 工具規格**：需蒐集目標領域的 Model Context Protocol 工具定義（公開實作或自行撰寫）。建議至少 200–500 個工具規格以建立有意義的服務函式庫。
- **領域文件**：服務的 API 文件、狀態結構描述、轉移邏輯說明。
- **種子任務範例**：用於引導任務生成代理的少量人工撰寫範例（建議 50–100 個）。
- **驗證探針設計**：每個服務需定義可程式化檢查的成功條件。

**運算資源**
- **訓練硬體**：35B-A3B 模型的 SFT + RL 訓練建議至少 32 張 H100/A100 GPU（80GB）。
- **推理硬體**：服務執行與世界模型模擬需配置多節點 GPU 叢集。
- **儲存空間**：10,130 個工具的服務程式碼、軌跡資料、驗證日誌，建議預留 5–10 TB。
- **預估成本**：完整重現實驗約需 50,000–100,000 美元等值的雲端算力。

**技能前提**
- 熟悉 Python 型別系統（Pydantic、TypedDict）與異步程式設計。
- 具備 LLM 代理開發經驗（ReAct、Tool-Use 框架）。
- 理解 GRPO 與 PPO 等強化學習演算法。
- 具備分散式訓練經驗（FSDP、DeepSpeed）。
- 對 MCP 協定與工具呼叫格式有基本認識。

### 實作步驟建議

**步驟 1：建立服務函式庫骨架**
從目標領域蒐集 MCP 工具規格，使用程式編寫代理（建議使用 GPT-5.4 或 Claude Opus 4.6 等強模型）在隔離的執行環境中將規格轉換為可執行的 Python 服務。為每個服務定義型別化狀態（TypedDict/Pydantic Model）與共享介面（namespaced tool functions）。建議採用「服務即模組」的結構，每個服務一個獨立目錄。

**步驟 2：補強長尾工具的世界模型**
對於無法可靠實作的工具（例如涉及外部真實 API、需要付費、或邏輯過於複雜的），建立世界模型作為模擬器。世界模型應接收工具呼叫並回傳合理的狀態轉移結果。建議使用較小的專用模型（如 Qwen3.6-8B）以降低成本，並對世界模型的輸出進行單元測試。

**步驟 3：設計隨機遊走程序**
實作服務層級的隨機遊走採樣器，從服務函式庫中選取節點並透過有向邊連接成依賴圖。每條邊代表「目標服務需要來源服務的資訊或狀態」。建議設定圖的節點數（3–8 個服務）與邊密度（每節點 1–3 條邊）的合理範圍，避免過於稀疏或稠密。

**步驟 4：任務生成與驗證**
使用任務生成代理根據依賴圖實例化初始狀態、目標與約束。接著執行驗證探針：檢查所需轉移的可達性（reachability）與成功條件的可滿足性（satisfiability）。只保留通過雙重驗證的任務。建議設定自動化重試機制，針對失敗任務進行修正或丟棄。

**步驟 5：監督式微調（SFT）**
收集通過驗證的成功軌跡（建議至少 3K 條），對 Qwen3.6-35B-A3B 進行監督式微調。訓練資料應包含完整的工具呼叫序列、觀察結果與最終動作。建議使用 LoRA 或全參數微調，並監控軌跡長度分佈以避免過擬合於特定模式。

**步驟 6：強化學習與聚焦完成的評分獎勵**
準備約 1K 個 RL 任務，搭配任務評分標準（rubrics）。實作 Completion-Focused Rubric Reward：在每個採樣批次群組內，為通過率較低的評分項目分配較高權重。結合 GRPO 進行策略優化。建議設定 KL 散度約束以避免策略過度偏移。

**步驟 7：評估與迭代**
在 AutomationBench、AppWorld 等基準上評估訓練後的模型。建議建立內部評估集以追蹤特定業務流程的表現。根據失敗案例分析，迭代服務函式庫與任務生成策略。

### 潛在風險與注意事項

**風險 1：服務實作不可靠**
程式編寫代理生成的服務可能存在邊界情況錯誤或狀態不一致。
**緩解措施**：建立自動化測試套件，對每個服務執行隨機狀態轉移測試；對失敗案例進行人工審查並修正；保留服務版本控制以便回滾。

**風險 2：世界模型幻覺**
世界模型模擬的工具呼叫結果可能與真實行為偏差，導致代理學到錯誤的轉移模式。
**緩解措施**：限制世界模型的使用範圍（僅限無法實作的長尾工具）；對世界模型的輸出進行一致性檢查；定期以真實工具呼叫結果重新校準。

**風險 3：評分獎勵被hack**
代理可能學會滿足評分標準的字面條件但未真正完成任務（例如發送空訊息、寫入無意義資料）。
**緩解措施**：設計多層次評分（包含語意檢查）；加入人類專家抽樣審查；對異常軌跡進行自動異常偵測。

**風險 4：驗證盲點**
驗證探針可能無法捕捉所有失敗模式，導致「通過驗證但實際不可解」的任務進入訓練集。
**緩解措施**：採用多代理交叉驗證；保留一定比例的任務供人類專家審核；建立失敗案例回饋迴路以改進驗證邏輯。

**風險 5：過擬合於訓練服務組合**
代理可能在訓練服務組合上表現良好，但無法遷移到未見過的服務組合。
**緩解措施**：在訓練中刻意保留部分服務組合作為驗證集；定期在 AppWorld 等外部基準上評估泛化能力。

**風險 6：運算成本失控**
RL 訓練中的大量軌跡採樣與世界模型推理可能導致成本急劇上升。
**緩解措施**：設定嚴格的預算上限與早停機制；對世界模型進行快取與批次化；優先使用較小的代理模型進行初步實驗。

### 與其他技術的整合建議

**與 MCP 生態系整合**
CompoWorld 的服務設計直接基於 Model Context Protocol 規範，可無縫接入現有的 MCP 工具市集（如 Smithery、Glama）。建議將生成的服務封裝為標準 MCP Server，使其能被 Claude Desktop、Cursor 等支援 MCP 的客戶端直接呼叫。

**與現有代理框架整合**
可將 CompoWorld 訓練的代理作為外掛整合至 LangChain、AutoGen、CrewAI 等框架。建議將服務呼叫封裝為標準化的 Tool Node，並保留 CompoWorld 的型別化狀態介面以維持跨服務資訊傳遞的正確性。

**與既有基準互補**
CompoWorld 的訓練資料生成流程可與 AppWorld、Terminal-Universe 等基準互補：使用這些基準的任務作為種子，透過 CompoWorld 的依賴圖機制擴展出更多變體。建議建立基準間的任務映射表以促進遷移學習。

**與企業系統整合**
在企業部署時，建議將 CompoWorld 的服務層與真實 API 介接：保留模擬服務作為開發與測試環境，透過配置切換至生產環境的 API 端點。建議使用 API Gateway 統一管理服務呼叫並加入監控。

**與 RL 訓練基礎設施整合**
可整合至現有的 RL 訓練框架（如 verl、OpenRLHF、TRL）。Completion-Focused Rubric Reward 可作為自訂獎勵函式外掛；GRPO 訓練流程可與分散式推理引擎（如 vLLM、SGLang）結合以加速軌跡採樣。

**與人類回饋機制整合**
建議在 RL 訓練中引入人類回饋（RLHF）作為評分獎勵的補充，特別針對高風險任務（如金融合規）。可採用 Pairwise Comparison 收集人類偏好，並將其整合至獎勵模型中。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題動機，理解「為什麼需要跨環境任務」這個核心問題。接著重點閱讀第 1 節中關於「服務」、「依賴圖」、「評分獎勵」三個概念的介紹，建立直觀認識。實作層面的細節（如 GRPO 演算法、隨機遊走程序）可暫時略過，待有基礎後再深入。

**給 AI 工程師**：重點關注第 1 節中三大挑戰的對應解法（服務標準化、依賴圖生成、評分獎勵設計），這些是系統設計的核心。建議直接參考「實作步驟建議」章節，從建立小型服務函式庫（10–20 個服務）開始驗證概念，再逐步擴展。程式編寫代理與世界模型的混合架構是值得深入理解的工程模式。

**給研究者**：第 2 節的相關工作梳理了環境擴展（Environment Scaling）與組合泛化（Compositional Generalization）兩條研究路線的脈絡。Completion-Focused Rubric Reward 與 GRPO 的結合、依賴圖作為任務組合的抽象、服務層級的可重用性等議題都有進一步研究空間。建議從失敗案例分析與理論分析（如泛化邊界）兩個方向切入。

**給產品經理**：CompoWorld 的核心價值在於「讓代理學會組合熟悉的服務完成新任務」，這對企業自動化產品有直接意義。建議關注 AutomationBench 上的結果（32.33% 超越 Claude Opus 4.6），理解在哪些場景下 CompoWorld 訓練的代理具有競爭優勢。在評估導入時，優先考慮「多系統協調」需求明確的場景，並評估內部服務的標準化程度是否足以支援服務函式庫的建立。
