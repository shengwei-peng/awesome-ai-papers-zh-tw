## ⚡ TL;DR

視覺型網頁代理的失敗常非源自模型推理，而是模型與瀏覽器間中介層的錯誤。
本文提出 WebFovea，將每步操作拆解為解析、執行、回饋、觀察四階段並設置防護機制。
WebFovea 於該競賽排名第二，僅改進中介層便將分數從 31.0 提升至 57.0。

## 摘要翻譯

我們提出 WebFovea，一個基於視覺的網頁代理，在 WebRetriever Challenge 2026 中以滿分 100 中獲得 57.0 分的最終分數，排名第二。該競賽在 WebRetriever 基準測試的 Protocol III（arXiv:2607.06118）上對代理進行端到端評估：從即時網站的入口網址（Entry URL）開始，代理必須操作該網站自身的介面並回傳可驗證的答案。一個具備足夠能力的多模態大型語言模型（Multimodal Large Language Model, MLLM）對此是必要的，但並不充分。模型的決策透過執行框架（Harness，即模型與頁面之間的程式碼層）傳遞到瀏覽器。在每一步中，有四件事必須正確：模型的回覆必須被解析為預期動作、動作必須在頁面上生效、結果必須被準確回報、模型必須被展示所需的資訊。在真實網站上，我們觀察到的許多失敗發生在這四個階段中的某個階段，而非模型的推理。座標空間錯位（Coordinate-space mismatch）使每次點擊都落在預期座標的四分之三處；原生下拉選單、Iframe 內部及文字輸入框中的動作發生靜默失敗；自行生成的對話模板詞元污染了 4.9% 的任務回合。WebFovea 強化了每個階段，並圍繞循環設置防護機制（Guardrails），使代理保持在規則與資源上限（Budget）之內。四階段觀點本身並不依賴於該模型，雖然某些個別修正確實如此。因為我們在四次提交版本中都使用了相同的模型，我們的官方隱藏測試集分數從 31.0 上升到 57.0，反映了執行框架的改進（受即時網站上多次執行變異的影響）。我們描述了設計、每個元件的證據（包括負面結果）、失敗分析、限制，以及一份包含將不同步驟路由分配（Routing）給不同模型的路線圖（Roadmap）。程式碼可在 https://github.com/jianganghan/WebFovea 取得。

### 核心貢獻（3～5點）
- 提出「四階段觀點」（解析 → 執行 → 回饋 → 觀察），系統性地拆解視覺網頁代理在每一步中必須正確完成的四個環節，揭示執行框架（Harness）才是決定端到端表現的關鍵瓶頸，而非僅有模型本身。
- 量化並定位三類高頻失敗模式：座標空間錯位導致點擊偏移至預期座標的四分之三處、原生下拉選單／Iframe／文字輸入框中的靜默失敗、以及自行生成對話模板詞元造成 4.9% 的任務回合污染。
- 透過強化執行框架的四個階段並設置防護機制，在四次提交中使用同一模型的情況下，將 WebRetriever Challenge 2026 隱藏測試集分數從 31.0 提升至 57.0（滿分 100），最終排名第二。
- 提出包含步驟路由分配（將不同步驟分配給不同模型）的未來路線圖，並開源釋出程式碼，推動可重現的視覺網頁代理研究。

### 適合對象
從事多模態大型語言模型、視覺網頁代理、瀏覽器自動化、端到端資訊檢索與網頁問答系統研究的研究者與工程師；以及關注模型部署可靠性、執行框架設計與基準測試實務細節的業界實務人員。

## 深度分析

#### 方法論解析

WebFovea 的核心方法論貢獻在於提出一個**四階段來回循環（four-stage round trip）框架**，用以系統化分析視覺型網頁代理（vision-based web agent）在即時網站（live website）上的運作。這個框架將模型與瀏覽器之間的執行框架（harness）拆解為四個連續階段：

**1. 解析階段（Parsing）**：將多模態大型語言模型（MLLM）的回覆轉換為結構化的動作指令。這階段的關鍵挑戰在於模型可能輸出非預期格式的內容，例如自行生成的對話模板詞元（self-generated chat-template tokens），污染了 4.9% 的任務回合（task episodes）。

**2. 執行階段（Execution）**：將解析後的動作實際施加於頁面上。論文指出此階段存在多種靜默失敗（silent failure）模式：原生下拉選單（native dropdowns）的互動、Iframe 內部的操作、文字輸入框（text box）的輸入，這些都可能「無聲地」失敗而未被模型察覺。

**3. 回饋階段（Feedback）**：將頁面對動作的反應準確回報給模型。此階段的失敗會導致模型誤判動作是否成功。

**4. 觀察階段（Observation）**：將模型所需的資訊以視覺形式呈現給模型。座標空間錯位（coordinate-space mismatch）問題在此階段浮現——所有點擊都被放置在預期座標的 3/4 位置，這是一個典型的觀察與執行之間的對齊失敗。

**兩層級依據性（Two Levels of Grounding）**：

- **答案層級的依據性（Answer-level grounding）**：確保答案來自於本次工作階段（session）中透過介面實際到達的權威頁面（authoritative page），而非來自參數化記憶（parametric memory）、搜尋引擎或手工打造的 API 呼叫。論文以兩個案例說明此層級失敗的嚴重性：早期版本在遭遇 CAPTCHA 後從記憶中作答；另一案例中模型在單一回覆中虛構了完整的多步驟軌跡（fictitious multi-step trajectory），並在第一步就提交答案。

- **動作層級的依據性（Action-level grounding）**：確保每個動作落在預期的像素或元素上，且其效果被正確感知。

**防護機制（Guardrails）**：圍繞著四階段循環，WebFovea 設置了規則防護機制（rule guardrails）與預算防護機制（budget guardrails），確保代理在挑戰規則與資源限制內運作。

方法論的精妙之處在於：**這個四階段觀點與模型無關**——無論使用何種模型，其決策都必須通過相同的四個階段。這使得該框架成為一個通用的診斷檢核表（diagnostic checklist）：對於任何失敗，可以追問「它在哪個階段出錯？」

#### 實驗數據解讀

**核心數據**：WebFovea 在 WebRetriever Challenge 2026 中以 57.0/100 的最終分數（final score）排名第二，並在主辦方的人工審查（manual review）中未失分。

**關鍵實驗發現**：

1. **執行框架改進的影響**：在四次提交（submission）中，隱藏測試集分數（hidden-set score）從 31.0 提升至 57.0，提升幅度達 26 分。由於全程使用相同的模型（claude-opus-4-6），這個進步完全歸因於執行框架的改進，而非模型本身的強化。

2. **多次執行的變異（Run-to-run variance）**：論文明確指出，由於評測是在即時網站上進行，分數會受到每次執行間變異的影響，這意味著 31.0 到 57.0 的提升中，部分可能來自即時網站變異（live site variance），而非純粹的系統改進。

3. **與基準測試的比較**：根據表 1 的 Protocol III 基準數據（注意：這些是在不同任務集上以人工驗證評測，因此與挑戰賽分數不可直接比較）：
   - Claude Computer Use（claude-4-8-opus）：47%
   - Kimi Agent（Kimi K3）：28%
   - Google Computer Use（gemini-2.5-pro）：21%
   - Claude Computer Use（claude-4-5-sonnet）：16%
   - Browser Use（gpt-4o）：11%
   - Agent-E（gpt-4o）：9%
   - UI-TARS-1.5 7B：8%
   - SeeAct（gpt-4o）：6%

4. **網頁資料漂移（Web data drift）**：在評測時，100 個公開參考答案（public reference answers）中已有部分與即時網站不符，這凸顯了僅依賴參考答案評測的局限性——必須結合軌跡證據（trajectory evidence）與最終螢幕畫面證據（final on-screen evidence）來判斷答案的正確性。

**數據解讀的意涵**：

- 26 分的提升幅度證明了**執行框架設計對代理效能的決定性影響**——這與 SWE-agent 在軟體工程任務中發現的「代理-電腦介面設計強烈影響語言模型表現」的結論一致。
- 4.9% 的詞元污染率（token contamination rate）看似微小，但對於 100 個任務的隱藏測試集而言，可能直接導致約 5 個任務的失敗。
- 3/4 的座標偏移是一個系統性錯誤，會影響所有涉及像素點擊的動作，這種「集體性失敗」比隨機錯誤更難被模型自行修正。

#### 與現有研究的比較

**定位**：

WebFovea 在網頁代理領域中佔據獨特位置。現有研究主要分為兩大典範：

1. **視覺型代理（Vision-based agents）**：如 Claude computer use、Gemini computer use、UI-TARS，透過螢幕截圖與像素座標操作。
2. **DOM 型代理（DOM-based agents）**：如 Browser Use、Agent-E、SeeAct，將頁面序列化為索引化元素。

WebFovea 屬於視覺型代理典範，但其獨特貢獻在於**不專注於模型或頁面表示方式的改進，而是研究模型決策如何到達頁面並返回的路徑**。

**改進與差異化**：

- **相較於 SWE-agent**：SWE-agent 證明了代理-電腦介面設計對軟體工程任務的重要性；WebFovea 將此洞見延伸至視覺型網頁代理，並提供了更具體的四階段分解。
- **相較於 SeeClick**：SeeClick 證明了更好的 GUI 依據性（grounding）能提升代理表現；WebFovea 則指出即使依據性良好，執行框架的其他階段仍可能導致失敗。
- **相於 Set-of-Mark prompting**：後者在螢幕截圖上疊加元素標籤，介於視覺與 DOM 兩種典範之間；WebFovea 則強調無論採用何種表示方式，四階段循環的完整性才是關鍵。

**限制**：

1. **模型依賴性**：雖然四階段觀點與模型無關，但部分具體修復措施（如座標錯位的修正）可能與特定模型耦合。
2. **基準測試的可比較性**：WebRetriever Challenge 2026 的分數與 Protocol III 基準分數因任務集不同而無法直接比較。
3. **即時網站變異**：每次執行的結果可能因網站狀態變化而不同，這限制了實驗結果的可重現性。
4. **單一模型評測**：由於挑戰賽限制使用核准模型清單（approved model list），且全程使用同一模型，無法直接評估模型替換的效益。

#### 可重現性評估

**程式碼可用性**：WebFovea 的程式碼已在 GitHub 開源（https://github.com/jianganghan/WebFovea），這是正面因素。然而，可重現性面臨以下挑戰：

1. **隱藏測試集的限制**：WebRetriever Challenge 2026 使用 100 個隱藏任務（hidden tasks）進行評測，這些任務不公開，因此無法直接重現官方分數。
2. **即時網站的動態性**：由於評測在即時網站上進行，網頁內容可能隨時間變化，導致相同的程式碼在不同時間執行可能產生不同結果。
3. **模型 API 的可取得性**：論文使用 claude-opus-4-6，透過 OpenAI 相容 API 呼叫。雖然模型在核准清單上，但 API 的可取得性與成本可能影響重現實驗的可行性。
4. **瀏覽器環境配置**：代理透過 Chrome DevTools Protocol（CDP）驅動 Chrome 瀏覽器，1920×1080 的視窗大小與沙盒環境配置可能影響結果。
5. **缺乏完整的負面結果細節**：雖然論文提到包含負面結果（negative results），但具體哪些實驗嘗試失敗、為何失敗的細節需要從程式碼與日誌中推敲。

**評估**：整體而言，程式碼的開源是重要的第一步，但由於隱藏測試集與即時網站的特性，完全重現 57.0 的分數具有挑戰性。研究者可以使用公開的 WebRetriever 基準測試（1,550 個任務）進行部分驗證。

#### 未來研究方向

論文提出了明確的路線圖（roadmap），並暗示了多個值得探索的方向：

**1. 步驟路由（Step Routing）與模型路由（Model Routing）**：

將代理的不同步驟分配給不同模型、規則或傳統視覺工具（classical vision tools）。例如：
- 座標預測可使用專門的 GUI grounding 模型
- 文字輸入可使用專門的 OCR 或文字處理工具
- 複雜推理步驟可使用更強的語言模型
- 簡單的頁面導航可使用基於規則的系統（rule-based routing）

**2. 傳統視覺工具的整合**：

將傳統電腦視覺技術（如邊緣偵測、模板匹配、OCR）整合進執行框架，補強 MLLM 在精確定位與文字識別上的不足。

**3. 更細緻的失敗診斷**：

基於四階段框架，開發自動化的失敗定位工具，能在代理執行過程中即時識別失敗發生在哪個階段，並採取對應的恢復策略。

**4. 答案層級依據性的強化**：

鑑於模型可能從參數化記憶作答或虛構軌跡，未來可探索：
- 強制要求模型在提交答案前必須有實際的頁面互動證據
- 開發能偵測「單步提交」異常行為的監控機制
- 設計更嚴格的軌跡驗證流程

**5. 處理網頁資料漂移**：

開發能適應網頁內容變化的彈性機制，例如：
- 動態更新參考答案
- 結合多個時間點的證據進行交叉驗證
- 設計對網頁結構變更更具魯棒性的元素定位策略

**6. 跨語言與跨產業的泛化**：

WebRetriever 涵蓋多種語言與產業，未來可研究：
- 不同語言介面對視覺型代理的挑戰
- 特定產業（如金融、醫療、政府）的網頁結構特徵與對應策略

**7. 安全性與合規性**：

鑑於代理操作真實網站，未來需深入研究：
- 如何避免代理觸發安全機制（如 CAPTCHA）
- 如何在遭遇反爬蟲機制時優雅降級
- 代理行為的可解釋性與可審計性

**8. 評測方法的改進**：

鑑於即時網站變異對評測的影響，未來可：
- 開發多次執行的統計評測協議
- 結合軌跡證據與答案正確性的綜合評分機制
- 建立更穩健的基準測試更新機制

## 論文問答

**Q1：WebFovea 主要解決什麼問題？**
A：WebFovea 解決的是基於視覺的網頁代理在真實、即時網站上執行端到端檢索任務時，可信度不足的問題。具體而言，它針對 WebRetriever Challenge 2026 的 Protocol III 賽道，要求代理從入口網址出發，操作網站本身的介面，並回傳可驗證的答案。這個問題之所以困難，是因為任務涵蓋文件擷取、表單互動、多來源比較、完整資料檢索與圖表分析等多種場景，且必須在 800 個真實網站、1,550 個任務上即時執行，而非依賴離線快照或預存資料。

**Q2：為何現有的視覺型網頁代理在這類任務上會失敗？**
A：根據本文的分析，許多失敗並非源自模型的推理錯誤，而是發生在模型與瀏覽器之間的「執行框架」（harness）層。具體而言，座標空間錯位會讓每次點擊落在預期座標的四分之三處；對原生下拉選單、iframe 內部與文字輸入框的操作會發生靜默失敗；此外，模型自行生成的對話模板詞元會污染約 4.9% 的任務回合。這些問題使得即使模型本身推理正確，動作仍可能點擊空白處、重打未送達的文字，或放棄實際上已成功的動作。

**Q3：為什麼這個問題值得重視？**
A：因為人們與組織所需的許多資訊——統計入口網站、法規申報、排行榜與儀表板——都散佈在公開網站上，必須透過導航選單、設定篩選、讀取表格與圖表才能取得。若網頁代理無法被信任，其自動化價值便大打折扣。更重要的是，WebRetriever 基準測試本身已證明「導航成功率」不足以預測「任務完成率」，因此僅追求導航正確並不足夠，必須同時兼顧答案層級與動作層級的依據性，才能確保代理的回應可信。

**Q4：WebFovea 的核心方法論是什麼？**
A：WebFovea 的核心方法論是將代理的每一步操作視為一個通過四個階段的「來回循環」（round trip）：解析（將模型回覆轉為動作）、執行（在頁面上執行動作）、回饋（回報頁面反應）與觀察（向模型展示所需資訊）。這個四階段觀點不僅是診斷工具，也作為設計檢查清單——對於任何失敗，可以直接詢問它發生在哪個階段。透過在每個階段強化並在整個循環周圍設置防護機制，WebFovea 確保代理能在規則與預算限制內穩定運作。

**Q5：WebFovea 最關鍵的創新是什麼？**
A：最關鍵的創新在於將分析焦點從「模型本身」轉向「模型與瀏覽器之間的介面」，並提出一個模型無關（model-agnostic）的診斷框架。這個觀點的價值在於：即使模型固定不變，僅透過改進執行框架，分數仍可從 31.0 提升至 57.0，證明了中介層設計的重要性。此外，作者明確區分「答案層級依據性」與「動作層級依據性」兩個層次的對齊真實來源要求，並指出兩者皆須透過執行框架來實現，這為未來的研究提供了清晰的改進方向。

**Q6：WebFovea 在設計上做了哪些關鍵選擇？**
A：在設計上，WebFovea 選擇以 Claude Opus 4.6 作為唯一模型貫穿所有四次提交，以確保分數變化純粹反映執行框架的改進而非模型差異。它採用 Chrome DevTools Protocol（CDP）驅動 1920×1080 視窗的 Chrome 瀏覽器，並透過 OpenAI 相容 API 呼叫模型。此外，系統在循環外圍設置了規則防護機制與預算防護機制，確保代理不會繞過介面、使用快取答案或調用第三方資料來源，符合挑戰賽的嚴格有效性準則。

**Q7：WebFovea 在哪些基準測試上進行評估？**
A：WebFovea 主要在 WebRetriever Challenge 2026 的 Protocol III 賽道上進行評估，該賽道涵蓋 100 個隱藏任務，於指定沙箱環境中對即時網站執行端到端檢索。WebRetriever 基準測試本身包含 1,550 個任務、橫跨 800 個真實網站，涵蓋多種產業與語言。此外，作者也將其成果與 Protocol III 公開排行榜上的基線進行比較，包括 Claude Computer Use、Kimi Agent、Google Computer Use、Browser Use、Agent-E、UI-TARS-1.5 與 SeeAct 等系統。

**Q8：WebFovea 的關鍵實驗結果為何？**
A：WebFovea 在 WebRetriever Challenge 2026 中以 57.0 分（滿分 100）獲得第二名，且在主辦方的人工審查中未失分。特別值得注意的是，在四次提交過程中，由於全程使用同一個模型，分數從 31.0 提升至 57.0 完全歸功於執行框架的改進。雖然這個提升幅度部分受到即時網站多次執行變異的影響，但整體趨勢明確證明了中介層設計對代理表現的關鍵影響。

**Q9：WebFovea 進行了哪些消融或對照實驗？**
A：本文透過「配對評估」（paired evaluations）來驗證每個元件的貢獻，並輔以案例研究與負面結果來說明哪些方法無效。具體而言，作者展示了座標空間錯位如何導致每次點擊偏移至預期座標的四分之三處，並透過修正此問題來驗證其影響。對於對話模板詞元污染問題，他們也提供了量化證據（4.9% 的任務回合受影響）。此外，作者坦誠地報告了負面結果——某些嘗試的改進並未帶來預期效果，這些資訊對後續研究者極具參考價值。

**Q10：WebFovea 適用於哪些實際應用場景？**
A：WebFovea 適用於任何需要在真實、即時網站上進行自動化資訊檢索的場景，包括從統計入口網站擷取特定指標、從法規申報系統查詢合規狀態、從排行榜網站追蹤名次變化，以及從儀表板讀取即時數據。在企業環境中，這類代理可用於市場研究、競爭情報收集、監管合規監測與客戶服務自動化。對於需要從多個來源彙整資料的研究任務，WebFovea 的多步驟導航與介面操作能力也提供了實用價值。

**Q11：將 WebFovea 整合至產品時需要考量哪些因素？**
A：產品化時首先需考量的是模型成本與延遲——WebFovea 使用 Claude Opus 4.6 作為主力模型，每個任務可能涉及多輪模型呼叫，總成本不容忽視。其次是執行環境的穩定性：即時網站會持續變化，介面更新、資料漂移或 CAPTCHA 驗證碼都可能中斷代理流程，因此需要設計重試與降級機制。此外，產品的合規性也至關重要——必須確保代理遵循目標網站的使用條款、robots.txt 規範與資料保護法規，避免法律風險。

**Q12：WebFovea 對學術界與產業界的影響為何？**
A：對學術界而言，WebFovea 提出了一個模型無關的診斷框架，將研究焦點從「如何讓模型更聰明」轉向「如何讓模型與環境的介面更可靠」，這為後續研究開闢了新方向。對產業界而言，它證明了僅透過改進中介層即可大幅提升代理表現，這對資源有限的團隊特別有價值——他們無需訓練或微調更大的模型，即可從現有模型中榨取更多效能。此外，作者開源了程式碼（github.com/jianganghan/WebFovea），降低了其他研究者復現與改進的門檻。

**Q13：WebFovea 明確承認的限制有哪些？**
A：作者坦誠承認的限制包括：分數提升幅度（從 31.0 到 57.0）部分受到即時網站多次執行變異的影響，因此難以精確歸因於特定元件的改進。此外，WebFovea 依賴於核准模型清單中的模型，這限制了其使用更強大或更專門化模型的能力。系統在面對 CAPTCHA 驗證碼、網站結構重大變更或需要跨站點複雜推理的任務時仍可能失敗，且其設計假設任務可透過介面操作完成，對於需要呼叫未公開 API 的場景並不適用。

**Q14：WebFovea 記錄了哪些具代表性的失敗案例？**
A：一個值得注意的失敗案例是：早期版本的代理在遭遇 CAPTCHA 後，直接從模型的參數化記憶中回答，而非繼續嘗試通過驗證。另一個案例是模型在單次回覆中虛構了整個多步驟軌跡，並在第一步就提交了答案，跳過了實際的介面操作。此外，作者也記錄了座標空間錯位導致的「點擊空白處」問題、對原生下拉選單與 iframe 操作的靜默失敗，以及對話模板詞元污染導致的回合級錯誤。這些案例凸顯了執行框架中各個階段都可能成為失敗的源頭。

**Q15：WebFovea 未來的路線圖為何？**
A：作者提出的優先路線圖包括：將不同步驟路由到不同模型，例如讓較小的模型處理簡單的導航決策，而讓較大的模型處理複雜的推理任務；引入傳統電腦視覺工具來輔助螢幕截圖的理解，例如物件偵測與 OCR；以及進一步強化四階段中的薄弱環節。此外，他們也計劃擴展防護機制的覆蓋範圍，例如更精細的預算控制與更完善的錯誤恢復機制。長遠而言，作者期望這個四階段框架能成為視覺型網頁代理的標準診斷工具，幫助研究者系統性地定位與改進失敗模式。

- 能撰寫簡單的視覺驗證腳本（像素比對、OCR）作為輔助觀察。

### 實作步驟建議

**第一步：建立四階段管線骨架**
依照論文的 round-trip 模型，把代理的一步切成四個明確函式：`parse_reply(model_output)`、`execute_action(action, page)`、`collect_feedback(page)`、`prepare_observation(page)`。每個函式都應回傳結構化結果與錯誤代碼，方便定位失敗階段。

**第二步：實作解析階段（Parsing）的座標正規化**
論文中座標空間錯位導致每次點擊落在 3/4 預期位置，是典型災難。實作時應：
- 統一內部座標系（例如以截圖像素為基準）。
- 在送入瀏覽器前做一次 affine 轉換，驗證轉換後座標落在元素 bounding box 內。
- 對模型回傳的座標做 sanity check（必須在視窗範圍內、必須對應可點擊元素）。

**第三步：強化執行階段（Execution）對特殊元件的處理**
針對論文中提到的靜默失敗，補上：
- iframe 偵測：點擊前先檢查目標元素是否在 iframe 內，必要時切換 frame context。
- 原生下拉選單：優先用 CDP 的 `Runtime.evaluate` 觸發 `change` 事件，而非模擬鍵盤。
- 文字輸入框：送出後讀回 value，確認文字確實落入欄位。

**第四步：建立回饋階段（Feedback）的真實回報機制**
不要只回傳「動作已送出」。應回傳：
- 動作後的 URL 變化、DOM 差異摘要、HTTP 請求紀錄。
- 截圖差異（diff）以判斷頁面是否真的更新。
- 失敗時的明確錯誤訊息（被擋、逾時、元素消失）。

**第五步：設計觀察階段（Observation）的截圖策略**
- 截圖前等待關鍵元素出現或消失，而非固定 sleep。
- 對長頁面分段截圖或捲動後再截，避免模型只看到局部。
- 過濾掉對話模板詞元（chat-template tokens）混入模型輸入的問題——論文指出這污染了 4.9% 的回合。

**第六步：加上護欄（Guardrails）**
- 預算護欄：每個任務有步數上限與時間上限，超過即強制結束。
- 規則護欄：禁止呼叫搜尋引擎、禁止存取非指定網域、禁止預存答案。
- 一致性護欄：偵測模型是否在單一回覆中虛構多步軌跡並提早提交。

**第七步：建立評估與迭代循環**
- 在公開子集上做配對評估（A/B 兩個版本同時跑），量化每個改動的影響。
- 保留所有軌跡日誌，失敗案例人工標註「失敗發生在哪個階段」。
- 接受 live site 的 run-to-run 變異：單次分數波動 ±5 分是正常的，須看多次平均。

**第八步：規劃模型路由（Model Routing）**
論文建議把不同步驟路由到不同模型。實作上可從簡單規則開始：
- 導航步用較強模型，讀取值用較便宜模型。
- 圖表理解用視覺專項模型，文字解析用一般 LLM。
- 失敗重試時升級到更強模型。

### 潛在風險與注意事項

**風險一：即時網站漂移導致參考答案失效**
論文提到 100 個公開參考答案中已有部分與線上狀態不符。緩解方式：把「軌跡證據」與「螢幕畫面證據」一併存檔，當答案不符時可由人工覆核；不要把參考答案當唯一真理。

**風險二：座標錯位造成連鎖失敗**
一次座標偏移會讓模型以為按鈕無效，進而嘗試其他無意義的動作。緩解方式：在解析階段加入「點擊後驗證」——若頁面無變化且座標落在非元素區，自動重試一次並回報錯誤。

**風險三：CAPTCHA 與反自動化機制**
論文日誌顯示代理曾因 CAPTCHA 退而求其次從記憶回答，這違反規則。緩解方式：明確把 CAPTCHA 視為終止條件，誠實回報「無法完成」而非猜答案；長期可考慮整合真人介入或第三方解碼服務（須符合競賽規則）。

**風險四：對話模板詞元污染**
模型有時會在輸出中混入 `<|im_start|>` 等模板詞元，污染下游解析。緩解方式：在解析前用正則過濾；對模型設定明確的 stop tokens；定期統計污染率並設告警閾值。

**風險五：iframe 與 shadow DOM 的靜默失敗**
動作「成功送出」但實際上沒生效。緩解方式：執行階段必須做雙向驗證（送出後讀回），並把 iframe context 切換納入標準動作類型。

**風險六：單次評分的高變異**
同一份程式碼在 live site 上重跑可能差好幾分。緩解方式：不要根據單次分數做重大架構決策；至少跑三次取中位數；對每次提交保留完整設定快照以便回溯。

**風險七：模型被誤判為推理錯誤**
當 click 落空、輸入沒生效，模型會表現得像「笨」，但其實是 harness 出問題。緩解方式：建立「四階段診斷清單」文化——每次失敗先問「解析錯了？執行錯了？回饋錯了？觀察錯了？」，再考慮換模型。

### 與其他技術的整合建議

**與傳統 RPA 工具（UiPath、Automation Anywhere）整合**
把 WebFovea 當作「視覺例外處理層」：當 RPA 的 DOM 選擇器失效時，呼叫視覺代理嘗試理解畫面並繼續操作。回傳結構化動作描述後再交給 RPA 執行，可兼顧穩定性與彈性。

**與 DOM 型代理（Browser Use、Agent-E）整合**
採混合策略：優先用 DOM 代理處理結構清楚的頁面（速度、成本都較佳），遇到 canvas、圖表、shadow DOM 時切換到視覺代理。可設計一個「介面難度分類器」自動決定走哪條路。

**與傳統電腦視覺工具整合**
論文的路線圖明確提到加入傳統 CV 工具。實務上可用：
- OpenCV 做元素 bounding box 偵測，作為座標驗證的輔助。
- Tesseract / PaddleOCR 做截圖文字抽取，與模型讀取的結果比對。
- 模板比對偵測「載入中」spinner、「錯誤」彈窗等狀態。

**與模型路由系統整合**
搭配 LiteLLM、OpenRouter 或自建 gateway，依步驟類型路由到不同模型：
- 導航決策 → 強推理模型。
- 截圖理解 → 視覺專項模型。
- 答案抽取 → 便宜快速模型。
- 失敗重試 → 升級到旗艦模型。

**與觀測與審計系統整合**
所有軌跡、截圖、模型輸入輸出都應送入可搜尋的儲存（如 S3 + Athena），方便：
- 事後除錯時回放整個回合。
- 統計每階段失敗率，建立儀表板。
- 給合規團隊做軌跡審查（論文強調挑戰賽含人工審查）。

**與人類在迴圈中（Human-in-the-loop）整合**
對高風險任務（金額、醫療、法務），在代理送出最終答案前插入人工確認節點；對低風險任務則全自動。WebFovea 的四階段架構很容易在中間任何一點暫停等待人類輸入。

---

### 給不同背景讀者的閱讀建議

**給初學者**：把焦點放在論文的「四階段 round-trip」心智模型上——這是理解所有網頁代理失敗的通用框架。試著用這個模型去拆解你用過的任何一個聊天機器人或 RPA 工具，問自己「它在哪個階段最容易出錯？」這個問題會比任何技術細節都更能幫助你診斷真實世界的自動化問題。

**給 AI 工程師**：直接讀第 4 節的元件證據與負面結果，特別是座標正規化、iframe 處理、chat-template 詞元污染這三個具體修法。把這些當作 checklist 套到你自己的代理上——很可能你會發現類似的 bug 一直存在卻被歸咎於模型。論文最有價值的地方是證明了「換模型不如修 harness」。

**給研究者**：四階段框架本身值得作為一個診斷分類法繼續發展——可以擴充到更多階段（例如規劃、記憶、反思），也可以套用到非視覺型代理。論文的負面結果與失敗分析同樣重要：哪些修法沒用、為什麼沒用，這些資訊在論文中通常被忽略。此外，run-to-run 變異對 live site 評估的影響是個被低估的方法論問題，值得深入研究。

**給產品經理**：這篇論文最重要的商業訊息是：把 31 分拉到 57 分靠的不是換更貴的模型，而是修中介層。當你在評估 AI 代理產品時，別只問「底層模型是什麼」，要問「harness 的設計品質如何」、「失敗時能不能定位到具體階段」、「live site 的可靠性怎麼量測」。論文的限制章節也值得讀——它誠實列出哪些場景還沒覆蓋，幫助你設定合理的產品預期。
