## 摘要翻譯

雖然 GUI 代理（GUI Agents）已迅速發展，但它們往往缺乏從自身錯誤中恢復的穩健性（Robustness），阻礙了其在真實世界部署（Real-world Deployment）。為了同時在評測層級（Evaluation Level）與資料層級（Data Level）彌補此差距，我們提出 GUI-RobustEval，並提出穩健性驅動軌跡合成（Robustness-driven Trajectory Synthesis, RoTS）。GUI-RobustEval 包含 1,216 個可執行測試案例（Executable Test Cases），系統性地衡量在廣泛且真實的各類錯誤模式（Error Modes）下的錯誤恢復能力（Error Recovery Capabilities）。在資料層級，RoTS 是一個可擴充合成框架（Scalable Synthesis Framework），透過樹狀管線（Tree-based Pipeline）主動發現多樣的錯誤模式並合成相應的恢復步驟（Recovery Steps），進而產生 80 萬筆高品質資料。我們的兩個模型 RoTS-7B 與 RoTS-32B 於我們的資料集上微調（Fine-tuned）後，在 GUI-RobustEval 與傳統 GUI 基準測試（Traditional GUI Benchmarks）上均展現顯著提升。值得注意的是，RoTS-32B 在 OSWorld 上達到最先進的效能，成功率（Success Rate）達 47.4%，All-Pass@4 分數達 33.8%，顯示出長程錯誤恢復（Long-horizon Error Recovery）能力的提升有助於穩健性與整體表現。我們的程式碼已公開於 https://github.com/AlibabaResearch/RoTS。

### 核心貢獻（3～5點）
- 提出 GUI-RobustEval 評測基準：包含 1,216 個可執行測試案例，系統性地衡量在廣泛且真實的各類錯誤模式下的錯誤恢復能力。
- 提出穩健性驅動軌跡合成（RoTS）：以可擴充合成框架結合樹狀管線，主動發現多樣錯誤模式並合成對應恢復步驟，產生 80 萬筆高品質訓練資料。
- 微調出 RoTS-7B 與 RoTS-32B 兩個模型：在 GUI-RobustEval 與傳統 GUI 基準測試上均達成顯著效能提升。
- RoTS-32B 於 OSWorld 達到最先進水準：成功率達 47.4%、All-Pass@4 達 33.8%，驗證長程錯誤恢復能力的提升能同時增進穩健性與整體任務表現。

### 適合對象
從事 GUI 代理、自主代理與人機互動研究的學者與工程師，以及關注代理穩健性、錯誤恢復機制、長程任務規劃與大規模合成資料生成之實務應用與真實世界部署挑戰的讀者。

## 深度分析

#### 方法論解析

本研究從評測層級（Evaluation Level）與資料層級（Data Level）雙管齊下，解決 GUI 代理（GUI Agents）在面對策略引發錯誤（Policy-Induced Errors）時穩健性（Robustness）不足的問題。其核心方法論包含兩大支柱：**GUI-RobustEval** 與 **穩健性驅動軌跡合成（Robustness-driven Trajectory Synthesis, RoTS）**。

在評測層級，GUI-RobustEval 將 GUI 代理任務建模為部分可觀察馬可夫決策過程（POMDP），並針對策略引發錯誤提出兩個關鍵維度：**錯誤類型（Error Type）**與**錯誤深度（Error Horizon）**。錯誤類型定義為根因動作（Root-Cause Action）的類別；錯誤深度則是從根因動作發生後，到該錯誤可被識別所需的最少步數。GUI-RobustEval 包含 1,216 個可執行測試案例（Executable Test Cases），涵蓋 11 種具代表性的錯誤類型與 4 種可控制的錯誤深度。其評測協議設計如下：對每個任務提供一段錯誤前綴軌跡（Erroneous Prefix Trajectory），將環境與代理重置至錯誤深度 d 的目標狀態，隨後要求代理接管並完成任務。透過此設計，基準測試（Benchmarking）能量化兩項細粒度指標（Fine-grained Metrics）：**錯誤覺察率（Error-Awareness Rate）**與**錯誤後成功率（Post-Error Success Rate）**，從而診斷代理在何種錯誤模式（Error Modes）下無法偵測，以及恢復能力如何隨錯誤深度遞減。

在資料層級，RoTS 是一個可擴充合成框架（Scalable Synthesis Framework），採用樹狀管線（Tree-based Pipeline）在真實 GUI 環境中進行線上軌跡合成（Trajectory Synthesis）。該框架透過迭代擴展軌跡樹，同時關閉錯誤覆蓋率不匹配（Error Coverage Mismatch）與錯誤深度不匹配（Error Horizon Mismatch）兩大缺口。具體而言，樹狀結構包含兩類分支：（1）在成功分支上，RoTS 從脆弱狀態（Fragile States）主動分叉，重複利用正確前綴以探索多樣的失敗模式（Failure Modes），藉此提升錯誤覆蓋率；（2）在失敗分支上，框架從錯誤狀態（Erroneous State）重播並合成對應的長程恢復軌跡（Long-horizon Recovery Rollouts），產生包含恢復步驟（Recovery Steps）的訓練資料。此流程最終產出 800k 高品質資料，並用於監督式微調（Supervised Fine-tuning），訓練出 RoTS-7B 與 RoTS-32B 兩個模型。

#### 實驗數據解讀

實驗結果顯示，RoTS-7B 與 RoTS-32B 在 GUI-RobustEval 與傳統 GUI 基準測試（Traditional GUI Benchmarks）上均取得顯著提升。在 GUI-RobustEval 上，模型於 11 種錯誤類型與不同錯誤深度的組合中，錯誤恢復能力（Error Recovery Capabilities）明顯優於基線，顯示 RoTS 合成的資料確實能校準代理對策略引發錯誤的感知與處理能力。

在 OSWorld 基準上，RoTS-32B 達到 47.4% 的成功率（Success Rate）與 33.8% 的 All-Pass@4 分數，創下當時最佳表現（State-of-the-Art）。更具指標意義的是長程穩健性的變化：相較於 Pass@1，All-Pass@4 對長程一致性更為敏感，而 RoTS-7B 的 All-Pass@4 準確度降幅僅為 -10.0%，明顯低於 OpenCUA-7B（-15.7%）、UI-TARS-1.5（-17.8%）等對照模型。這項數據強烈暗示，**長程錯誤恢復（Long-horizon Error Recovery）能力的提升不僅增強穩健性，也直接貢獻於整體任務成功率（Overall Task Success）**。換言之，代理在執行過程中偵測並修復自身策略引發錯誤的能力，與其最終完成複雜長程任務的能力呈現高度正相關，而非傳統認為的兩個獨立維度。

#### 與現有研究的比較

相較於既有文獻，本研究的定位與貢獻可從評測與訓練兩個面向剖析。在評測面，現有基準主要聚焦定位準確率（Grounding Accuracy）、規劃能力（Planning Ability）或整體任務成功率（Overall Task Success）；針對穩健性的評測則多採用注入雜訊（Injected Noise）或對抗性攻擊（Adversarial Attacks）。然而，這些方法缺乏直接衡量策略引發錯誤之偵測與長程恢復的細粒度指標。GUI-RobustEval 首次系統性地將錯誤類型與錯誤深度納入可控評測協議，填補了此缺口。

在訓練面，現有代理多透過監督式微調於 GUI 軌跡（GUI Trajectories）或線上強化學習（Online Reinforcement Learning）進行訓練；即便使用反思相關資料（Reflection-related Data），也多為人工生成或離線資料（Offline Data）擴增，導致錯誤類型與錯誤深度分布產生偏誤。此外，現有代理框架（Agent Frameworks）傾向於在推理階段加入反思（Reflection）與回溯子代理（Backtracking Sub-agents），而非從訓練層級根本提升對策略引發錯誤的恢復能力。RoTS 的獨特之處在於：**透過樹狀管線在真實環境中主動發現（Proactively Discover）多樣錯誤模式，並合成對應的長程恢復軌跡**，從而同時解決錯誤覆蓋率不匹配與錯誤深度不匹配。

儘管如此，本研究仍存在若干限制。首先，樹狀線上合成需要大量環境互動，運算成本可能隨任務複雜度指數增長。其次，GUI-RobustEval 雖涵蓋 11 種錯誤類型，但策略引發錯誤本質上為組合式錯誤（Compositional Errors）與高階錯誤（High-level Errors），預定義分類可能無法窮盡真實部署中的所有失敗模式。第三，評測協議採用「重置至錯誤狀態後接管」的設計，雖具可控性，但與完全自主執行中代理自發陷入錯誤狀態（Erroneous State）並自行察覺的情境仍有微妙差異。

#### 可重現性評估

本研究已將程式碼（Code）公開於 https://github.com/AlibabaResearch/RoTS，為可重現性（Reproducibility）奠定基礎。GUI-RobustEval 的 1,216 個可執行測試案例（Executable Test Cases）理應隨程式碼釋出，使其他研究者能複現評測結果。然而，根據提供的全文脈絡，**並未明確說明是否公開 800k 合成資料集或 RoTS-7B / RoTS-32B 的模型權重（Model Weights）**。若僅釋出評測程式碼與 RoTS 合成管線，研究者仍需耗費大量運算資源與環境互動成本才能重新產生訓練資料。此外，由於評測依賴 OSWorld 等外部 GUI 環境，重現結果亦受環境版本與系統設定影響。整體而言，評測層級的可重現性較高，但訓練層級的完整重現仍取決於後續是否釋出完整資料集與模型檢查點。

#### 未來研究方向

基於本研究的成果與架構，未來研究可沿以下方向延伸：

1. **自動化錯誤分類與開放式錯誤發現**：目前 RoTS 與 GUI-RobustEval 仍依賴預定義的 11 種錯誤類型。未來可結合大型視覺語言模型（Vision-Language Models, VLMs）自動歸納與發掘新的策略引發錯誤模式，降低對人工策劃錯誤（Human-curated Errors）的依賴。

2. **與線上強化學習（Online Reinforcement Learning）的深度融合**：RoTS 目前主要服務於監督式微調。將樹狀軌跡合成與線上強化學習或偏好最佳化（如 DPO）結合，可進一步提升代理在錯誤狀態下的探索與恢復策略學習效率。

3. **跨領域遷移至 Web 與行動代理**：本研究聚焦 GUI 環境，但策略引發錯誤同樣存在於網頁代理（Web Agents）與行動裝置操作。將 RoTS 的樹狀合成框架擴展至瀏覽器與行動作業系統，並建立對應的 RobustEval 變體，是極具價值的後續工作。

4. **降低合成管線的運算開銷**：樹狀線上探索雖能產生高品質資料，但環境互動成本高昂。未來可研究基於模型預測的剪枝策略或離線世界模型（World Models），以減少不必要的真實環境呼叫，提升可擴充性（Scalability）。

5. **推理階段穩健性的協同設計**：RoTS 從訓練層級強化恢復能力，未來可進一步探索如何與推理階段的回溯（Backtracking）、反思（Reflection）或蒙地卡羅樹搜尋（Monte Carlo Tree Search）結合，形成「訓練-推理」雙向加成的穩健代理架構。

## 論文問答

**Q1：這篇論文旨在解決 GUI 代理在實際部署中的哪個核心問題？**
A：這篇論文聚焦於 GUI 代理在面對策略引發錯誤時缺乏穩健性的問題，這些錯誤是代理在執行過程中因自身動作所產生的失誤，例如錯誤的定位、對螢幕狀態的誤解或錯誤的子目標設定。當這類錯誤發生時，代理往往會陷入錯誤狀態而無法自行脫困，最終導致任務失敗。由於現有方法難以偵測並從這些高階且組合式的錯誤中恢復，這嚴重阻礙了 GUI 代理在真實世界部署中的可靠性。

**Q2：現有的基準測試與訓練方法為何無法有效處理策略引發錯誤？**
A：現有的基準測試大多著重於定位準確率、規劃能力或整體任務成功率，而針對穩健性的測試僅限於注入雜訊或對抗性攻擊，缺乏直接衡量錯誤偵測與長程恢復的細粒度指標。在訓練方面，現有的反思相關資料通常由人工策劃或透過離線資料擴增而來，這導致錯誤類型偏向低階且短程的人為錯誤。因此，無論是在錯誤覆蓋率還是錯誤時間跨度上，現有方法都與真實的策略引發錯誤存在嚴重不匹配。

**Q3：為何提升錯誤恢復能力對 GUI 代理的實際應用至關重要？**
A：在真實世界的操作環境中，GUI 代理經常會在連續執行多個步驟後才顯現出高階的組合式錯誤，這類錯誤具有延遲可偵測性。如果代理不具備識別錯誤狀態並執行長程回溯的能力，就會持續在錯誤路徑上重複無效動作，形成惡性循環。因此，強化錯誤恢復能力不僅是提升穩健性的關鍵，更是讓 GUI 代理從實驗室走向實際產品部署的必要條件。

**Q4：本文提出的兩大核心貢獻是什麼？**
A：本文首先引入了 GUI-RobustEval，這是一個包含 1,216 個可執行測試案例的基準測試，能夠系統性地評估代理在 11 種錯誤模式與 4 種錯誤深度下的錯誤覺察率與錯誤後成功率。其次，作者提出了穩健性驅動軌跡合成（RoTS），這是一個可擴充的合成框架，透過樹狀管線主動發掘多樣的錯誤模式並合成對應的恢復步驟，產生 80 萬筆高品質訓練資料。這兩項貢獻分別從評測層級與資料層級填補了現有研究的缺口。

**Q5：RoTS 資料合成框架的關鍵創新是什麼？**
A：RoTS 採用樹狀線上管線，在 GUI 環境中迭代地擴展軌跡樹，這與傳統依賴離線資料或人工策劃錯誤的方法截然不同。在成功分支上，它會從脆弱狀態主動分支以發掘新的錯誤模式，同時重複利用正確的前綴軌跡；在失敗分支上，則從錯誤狀態重播並合成長程的恢復軌跡。這種設計同時解決了錯誤覆蓋率不匹配與錯誤時間跨度不匹配的雙重問題。

**Q6：GUI-RobustEval 的設計如何精確衡量錯誤恢復能力？**
A：GUI-RobustEval 針對每個測試案例提供一段包含錯誤的前綴軌跡，並將環境重置到距離根因動作特定深度的目標狀態。接著要求代理接管並完成後續任務，藉此測量 Error-Awareness Rate 與 Post-Error Success Rate 兩項指標。這些細粒度指標能夠診斷代理在何種錯誤類型上無法偵測失誤，以及隨著錯誤深度增加，其恢復能力如何遞減。

**Q7：本文的實驗在哪些基準測試上進行評估？**
A：實驗除了在新提出的 GUI-RobustEval 上進行穩健性評估外，也在傳統 GUI 基準測試如 OSWorld 上驗證整體任務表現。GUI-RobustEval 涵蓋了 11 種具代表性的錯誤類型與 4 種可控制的錯誤深度，專門針對策略引發錯誤的偵測與恢復能力設計。透過同時在這兩類基準上測試，作者能夠證明提升長程錯誤恢復能力不僅增強穩健性，也能帶動一般任務成功率的提升。

**Q8：RoTS-32B 的主要實驗結果為何？**
A：RoTS-32B 在 OSWorld 上達到了 47.4% 的成功率與 33.8% 的 All-Pass@4 分數，創下了當時最先進的表現。無論是 RoTS-7B 還是 RoTS-32B，在 GUI-RobustEval 與傳統基準測試上相較於基線模型都展現出顯著的進步。這些結果強烈表明，透過 RoTS 合成的長程錯誤恢復資料進行微調，能夠同時提升代理的穩健性與整體任務執行效能。

**Q9：圖 1(b) 的性能比較揭示了現有代理的什麼問題？**
A：圖 1(b) 顯示，包括 UI-TARS-1.5 與 Qwen3-VL-Plus 在內的現有代理在 All-Pass@4 指標上出現了大幅的準確率下滑，反映出它們在長程執行中難以維持穩定表現。相較之下，RoTS 模型的準確率下降幅度明顯較小，顯示其具備更優異的長程錯誤恢復能力。這項比較凸顯了傳統代理在面對延遲可偵測的策略引發錯誤時，普遍缺乏有效的偵測與回溯機制。

**Q10：穩健的錯誤恢復能力在哪些實際應用場景中最具價值？**
A：這項能力對於需要執行多步驟操作的複雜工作流程自動化極為關鍵，例如作業系統管理、企業軟體操作或網頁應用程式互動。當代理不慎輸入錯誤的公式、點選錯誤的選單或誤解對話框狀態時，它必須能夠及時察覺並執行恢復步驟，而非持續重複無效動作。這種自主性大幅降低了人為介入的需求，使 GUI 代理能夠在無人值守的環境中可靠運作。

**Q11：產品團隊在部署具備錯誤恢復能力的 GUI 代理時應考量哪些因素？**
A：產品團隊必須認知到，代理在實際運作中必然會遭遇高階且組合式的錯誤，這些錯誤往往需要長程回溯才能修復，而非僅靠短程的反思就能解決。因此，系統設計應整合錯誤覺察機制，讓代理能夠在偵測到異常狀態時主動觸發恢復流程。此外，訓練資料不應僅依賴人工策劃的短程錯誤，而需透過如 RoTS 這類框架涵蓋多樣且真實的策略引發錯誤模式。

**Q12：這項研究可能對 GUI 代理領域的未來發展產生什麼影響？**
A：本研究透過引入錯誤覺察率與錯誤後成功率等細粒度指標，為評估代理穩健性建立了新的標準，超越了單純以整體任務成功率論斷的傳統做法。RoTS 框架證明了以可擴充方式合成長程恢復資料的可行性與有效性，為資料層面的創新開闢了新路徑。這將激勵後續研究在訓練與評測階段都將穩健性視為核心目標，而非僅透過外部反思子代理來事後補救。

**Q13：本文承認了哪些研究限制？**
A：本文的研究範疇主要聚焦於策略引發錯誤，並未宣稱能涵蓋 GUI 環境中所有可能的失敗模式。雖然 GUI-RobustEval 涵蓋了 11 種具代表性的錯誤類型，但這些類型仍可能無法窮盡所有真實世界中的複雜情境。此外，RoTS 的合成管線雖具可擴充性，但其運作仍基於可控制的環境設定，在面對高度動態或前所未見的應用程式時，其泛化能力可能面臨挑戰。

**Q14：哪些類型的錯誤仍可能對 RoTS 模型構成挑戰？**
A：儘管 RoTS 顯著提升了恢復能力，但對於需要複雜語意推理或外部領域知識的錯誤，模型可能仍難以獨立解決。此外，那些在極長的執行軌跡中潛伏、直到很晚才顯現的根因錯誤，可能會超出目前模型長程回溯的極限。面對非確定性環境回應或未曾出現在訓練資料中的突發彈出視窗等情況，模型的恢復表現也可能受到嚴重考驗。

**Q15：這項工作指出了哪些未來的研究方向？**
A：未來研究可進一步擴展錯誤分類學，納入更多專業領域軟體中特有的失敗模式，以提升基準測試的覆蓋率。研究者也可以探索將 RoTS 與線上強化學習結合，透過與環境的持續互動來動態優化恢復策略。另一個有潛力的方向是開發能夠根據即時信心估計動態調整規劃深度的適應性代理框架，從而在錯誤發生前就預防其擴大。

## 實務應用指南

### 適用場景

1. **企業級 RPA 與舊系統自動化**：針對缺乏 API 的 Legacy ERP／CRM，代理在填寫表單或導航選單時發生策略引發錯誤（如點擊錯誤子目標或狀態誤解），可透過長程錯誤恢復能力自動回溯並完成任務，降低人工介入頻率。
2. **跨平台軟體測試與 QA**：在自動化 UI 測試中，當遭遇非預期彈窗、頁面延遲載入或無效動作導致的錯誤狀態時，代理能偵測異常並從錯誤深度較高的狀態恢復，提升測試腳本的容錯性與覆蓋率。
3. **無障礙輔助操作代理**：為行動不便使用者操作複雜桌面環境，當代理因定位失敗點錯按鈕或陷入無效迴圈時，可即時反思並執行恢復步驟，確保輔助流程不中斷。
4. **雲端與 DevOps 儀表板管理**：自動化操作監控或部署介面時，若在多步驟流程中誤設參數或導航至錯誤頁面，代理可利用合成資料訓練出的穩健性進行長程回溯，避免系統誤配置。
5. **多應用程式資料整合**：在跨應用搬移資料的流程中，處理因視窗切換延遲或狀態誤判造成的組合式錯誤，透過錯誤模式覆蓋率高的資料強化代理在真實混亂環境中的存活率。

### 實作前置條件

- **資料**：目標 GUI 環境的可執行軌跡（含截圖與動作序列）；若採用 RoTS，需準備種子正確軌跡與可重置的容器化或虛擬機環境。
- **運算資源**：資料合成階段需大量 CPU／GPU 並行模擬 GUI 環境；微調 7B 模型建議至少 8× A100 40GB，32B 模型需 16× A100 80GB 或同等 H100 資源；推論階段單張 A100 可支援低延遲批次處理。
- **技術能力**：團隊需具備 VLM（如 Qwen3-VL）監督式微調經驗、GUI 自動化框架（Playwright、pyautogui、OSWorld）整合能力，以及錯誤分析與樹狀搜尋演算法的基礎知識。

### 實作步驟建議

1. **錯誤模式盤點與環境建置**：在目標 GUI 環境（如企業內部系統或 OSWorld）部署 GUI-RobustEval 的評測邏輯，對現有代理執行 1,216 個可執行測試案例，量化錯誤覺察率與錯誤後成功率，識別高風險錯誤類型與錯誤深度分佈。
2. **RoTS 資料管線部署**：建構樹狀合成管線，於成功分支從脆弱狀態主動分支以探索多樣錯誤模式；於失敗分支從錯誤狀態重播並合成長程恢復軌跡。實作狀態去重與剪枝機制以控制計算成本。
3. **模型微調與驗證**：使用合成的高品質資料（如 800k 規模或依領域縮減）對基礎 VLM 進行監督式微調。在 GUI-RobustEval 上驗證細粒度指標，確保長程錯誤恢復能力隨錯誤深度增加而維持可接受衰減。
4. **產品化整合**：將微調後的穩健 GUI 代理嵌入現有工作流程，搭配即時截圖與動作日誌監控，並設計人在迴路機制，當錯誤深度超過閾值或連續恢復失敗時升級至人工處理。
5. **持續迭代**：收集線上真實錯誤軌跡作為新種子，定期重新執行 RoTS 以擴充錯誤模式覆蓋率，並將 GUI-RobustEval 作為回歸測試閘道，監控模型版本更新後的穩健性退化。

### 潛在風險與注意事項

1. **錯誤覆蓋率偏差**：若種子軌跡僅來自單一代理或人工策劃，合成資料可能遺漏真實世界的組合式錯誤與高階錯誤。建議混合多個 SOTA 代理的失敗軌跡與真實使用者日誌作為 RoTS 起點。
2. **長程恢復的累積誤差**：實驗顯示隨錯誤深度增加，恢復難度顯著上升。產品端應設定最大容許錯誤深度（如 d=4），超過即觸發安全回溯或人工介入，避免代理在無法恢復的狀態中浪費步數。
3. **計算成本爆炸**：樹狀管線的狀態空間可能指數成長。需實作嚴格的剪枝策略、重複狀態偵測與環境並行上限，防止資料合成階段耗盡運算資源。
4. **環境非確定性**：真實 GUI 環境的網路延遲與非同步載入可能導致合成軌跡重播失效。建議在確定性高的容器化桌面環境（如 Docker + VNC）中合成資料，再透過領域適應遷移至目標環境。
5. **過度擬合合成錯誤**：代理可能僅記憶合成資料的特定錯誤樣態。訓練集中應保留至少 10–20% 真實離線資料或人工標註的錯誤恢復軌跡，以維持對真實錯誤的泛化能力。

### 與其他技術的整合建議

1. **與傳統 RPA 工具整合**：將 RoTS 微調後的 VLM 作為「視覺認知層」，嫁接在 UiPath、Automation Anywhere 等傳統 RPA 的「執行層」之上，由 VLM 負責錯誤偵測與恢復決策，RPA 負責底層輸入控制，形成兼具穩健性與執行效率的混合架構。
2. **與 LLM Agent 框架整合**：可將 RoTS 訓練出的長程恢復能力內化為策略本身，而非僅依賴外部反思子代理。這能減少 ReAct／Reflexion 框架中頻繁呼叫外部 API 的延遲與成本，並降低回溯子代理的系統複雜度。
3. **與 CI/CD 整合**：將 GUI-RobustEval 的 1,216 個可執行測試案例與細粒度指標嵌入持續整合管線，作為 GUI Agent 每次模型更新或程式碼合併後的自動化回歸測試閘道，確保穩健性不因新功能而退化。
4. **與知識庫／RAG 整合**：對於需要領域知識才能恢復的錯誤（如特定企業軟體的錯誤碼或內部操作規範），可將 RoTS 的恢復軌跡與外部向量資料庫結合，透過 RAG 動態檢索恢復策略，補強純粹參數記憶的不足。

### 給不同背景讀者的閱讀建議

- **初學者**：建議從圖 1 的具體錯誤範例與 RoTS 合成的恢復軌跡開始，先理解「策略引發錯誤」與注入雜訊或對抗性攻擊的本質差異，再閱讀第 2.2 節的 GUI-RobustEval 評測設計，無需深入樹狀管線的演算法細節即可掌握穩健性與長程恢復的核心概念。
- **AI 工程師**：重點關注第 3 節 RoTS 的樹狀管線實作細節與第 4 節的訓練配方，特別注意脆弱狀態（fragile states）的分支策略與錯誤深度（error depth）的定義，這些是將論文方法落地為可擴充資料工程管線的關鍵技術點。
- **研究人員**：建議深入分析 GUI-RobustEval 的細粒度指標（Error-Awareness Rate、Post-Error Success Rate）與錯誤類型、錯誤深度的關聯性，並思考如何將此評測框架擴展至行動裝置、網頁代理或更具挑戰性的部分可觀測環境。
- **產品經理**：聚焦第 1 節的部署動機與第 5 節的實驗結果，特別是 RoTS-32B 在 OSWorld 達到 47.4% 成功率與 All-Pass@4 顯著提升的數據，用以評估投入資料合成與模型微調的商業價值，並權衡真實世界部署時的錯誤恢復風險與人工介入成本。
