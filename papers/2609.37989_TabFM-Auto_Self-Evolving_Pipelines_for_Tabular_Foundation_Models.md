## 摘要翻譯

表格基礎模型（Tabular Foundation Model, TFM）透過在合成表格（Synthetic tables）上預訓練，於結構化資料（Structured data）上取得強大的零樣本準確率（Zero-shot accuracy），但它們忽略了承載資料集語義（Dataset semantics）的欄位名稱（Column names）、任務描述（Task descriptions）與輔助檔案（Auxiliary files）。與此同時，自我演化（Self-evolving）的機器學習工程（Machine Learning Engineering, MLE）代理會在每個資料集上從頭訓練模型，然而聯合搜尋（Joint search）特徵（Features）、模型架構（Architectures）與超參數（Hyperparameters）雜訊大且容易過擬合（Overfitting）。我們提出 TabFM-Auto，它將表格基礎模型 TabFM 與語言模型代理（Language model agent）結合，由後者圍繞 TabFM 演化資料管線（Data pipeline）。在資料集後設資料（Dataset metadata）與驗證回饋（Validation feedback）的引導下，TabFM-Auto 迭代精煉資料清理（Data cleaning）、特徵工程（Feature engineering）、上下文選擇（Context selection）與後處理（Post-processing），以降低 TabFM 的錯誤率（Error）。在 TabArena 基準測試的全部 51 個資料集上，五種採用不同代理與語言模型的 TabFM-Auto 配置包辦總排名前五位，最佳配置將 TabFM 的 Elo 評分（Elo）從 1785 提升至 2013。所發現的管線（Discovered pipeline, P*）也能遷移（Transfer）至其他凍結模型（Frozen model）的表格基礎模型（Elo 評分提升 +69 至 +143），無需進一步搜尋。在 MLE-Bench 的 8 場表格競賽中，TabFM-Auto 在所有 MLE 代理中總排名第一。

### 核心貢獻（3～5點）
- 提出 TabFM-Auto 框架，將凍結的表格基礎模型 TabFM 與語言模型代理結合，讓代理專注於演化資料管線而非從頭訓練模型。
- 利用資料集後設資料與驗證回饋，迭代精煉資料清理、特徵工程、上下文選擇與後處理，以降低 TabFM 的錯誤率。
- 在 TabArena 基準測試的 51 個資料集上，五種不同配置的 TabFM-Auto 包辦總排名前五位，最佳配置將 TabFM 的 Elo 評分從 1785 提升至 2013。
- 發現的管線可遷移至其他凍結的表格基礎模型，帶來 +69 至 +143 的 Elo 評分提升，且無需進一步搜尋。
- 在 MLE-Bench 的 8 場表格競賽中，TabFM-Auto 在所有機器學習工程代理中總排名第一。

### 適合對象
本論文適合對表格資料自動化機器學習、基礎模型應用、代理式資料管線搜尋，以及結構化資料預測任務有興趣的研究人員與工程師；特別是關注如何結合語言模型代理與表格基礎模型以提升零樣本與競賽表現的讀者。

## 深度分析

#### 方法論解析

TabFM-Auto 的核心設計是將「凍結（frozen）」的表格基礎模型 TabFM（400M 參數）與一個大型語言模型編碼代理（LLM coding agent）結合，讓代理在**不更動模型權重**的前提下，自動演化資料管線（data pipeline）。整體流程可視為一個**閉環代理式管線搜尋（closed-loop agentic pipeline search）**：代理根據資料集後設資料（dataset metadata）與驗證回饋（validation feedback），反覆修改候選管線（candidate pipeline, P），再由沙盒評估器（sandboxed evaluator）以三折交叉驗證（3-fold cross-validation）評分，最終選出發現的管線（discovered pipeline, P*）。

管線被結構化為五個可編輯階段，對應圖 2(a) 與 2(b)：

1. **preprocess()：資料清理（data cleaning）與目標映射（target map）**  
   代理會在此處理缺失值編碼（例如將 sentinel 0 轉為 NaN）、異常值過濾（outlier filter）、標籤轉換（y map）等。由於 TabFM 的注意力層（attention layers）只看浮點數幅度（floating-point magnitudes）與類別索引（category indices），無法辨識「0 代表遺失測量值（missing measurement）」這類語義，因此需要前置的語義感知清理。

2. **engineer()：領域與統計特徵工程（domain & statistical feature engineering）**  
   代理利用 LLM 對欄位名稱（column names）與任務描述（task descriptions）的理解，產生領域公式（domain formulas），例如天文領域的 `color_u_g = u - g` 顏色指標（color index）。同時也包含通用轉換，如成對交叉特徵（pairwise cross features）、奇異值分解投影（SVD projections）、冪次轉換（power transform）等。

3. **sample()：上下文取樣（context sampling）**  
   針對大型或不平衡表格，選取資訊豐富且乾淨的列（informative & clean rows）作為上下文學習（in-context learning, ICL）的範例，以提升凍結 TabFM 的單次前饋式上下文學習傳遞（single feedforward ICL pass）效能。

4. **TABFM_KWARGS：傳遞給凍結 TabFM 的關鍵字參數**  
   包括正規化方法（normalization methods，如 `power`）、是否啟用非負最小平方法（NNLS, `enable_nnls`）、SVD、交叉特徵等。這些參數控制 TabFM 內部的特徵視角，但模型權重保持凍結。

5. **postprocess()：後處理（post-processing）**  
   包含機率校準（calibration）與標籤反轉映射（inverse target map），以處理偏斜類別先驗（skewed class priors）與迴歸目標的尺度問題。

搜尋機制上，代理以 **diff patch** 形式修改 `pipeline.py`，每次修改後沙盒評審器（sandboxed judge）執行三折交叉驗證並回傳分數與日誌（logs）。整個過程強制**嚴格測試集隔離（strict test set isolation）**：測試集（test set）在搜尋期間完全不可見，驗證標籤（validation labels）亦以遮罩（masked val labels）方式保護，最終僅對選定管線 P* 在官方測試集上評估一次。

此方法論的關鍵優勢在於**解耦（decouple）了資料管線搜尋與模型訓練雜訊**：由於 TabFM 無需梯度更新（zero gradient updates），每個候選管線的評估成本低廉，且避免了傳統 MLE 代理同時搜尋特徵、架構與超參數（joint search over features, architectures, and hyperparameters）所帶來的訓練變異與過擬合（overfitting）。

#### 實驗數據解讀

論文在兩大基準測試上驗證 TabFM-Auto：**TabArena**（51 個資料集，其中 38 個分類、13 個迴歸）與 **MLE-Bench**（8 個表格競賽）。

##### TabArena 整體表現

表 1 顯示，五種 TabFM-Auto 配置（結合 Claude Code、Antigravity、Codex 等代理，以及 Claude Opus 5、Gemini 3.8 Flash 等語言模型）在分類與迴歸榜上佔據**總排名前五位（top five overall positions）**。最佳配置 Codex + Opus 5 將 TabFM 的 Elo 評分（Elo rating）從 1785.3 提升至 **2013.0**，提升達 **+227.7 Elo**。

分類任務（38 datasets）：
- TabFM-Auto(Codex, Opus 5)：Elo 1966.3、Wins 13.84、Improv. 1.91%、G-Mean 0.0913
- 相較 TabFM（Elo 1768.7、Improv. 3.80%）與 TabFM+（Elo 1836.7、Improv. 2.91%），錯誤率差距（Improv.）顯著縮小。
- 傳統強棒 AutoGluon 1.5 extreme（Elo 1664.6）與 TabPFN-3（Elo 1637.7）均落後。

迴歸任務（13 datasets）：
- TabFM-Auto(Codex, Opus 5) 達到 Elo 2512.9、Improv. 0.00%，表示其幾何平均測試誤差（G-Mean）已接近每個資料集的最佳模型。
- 原始 TabFM 的 G-Mean 為 16.40，TabFM-Auto 最佳配置降至 15.86，相對改善約 3.3%。

值得注意的是，**不同代理與語言模型的組合表現穩定**：Codex、Claude Code、Antigravity 搭配 Opus 5 或 Gemini 3.8 Flash 皆能進入前五，顯示「凍結模型 + 代理演化管線」的框架具有**方法論層級的強健性**，而非單一 LLM 的偶然結果。

##### 遷移性（Transfer）

論文進一步指出，在 TabArena 上發現的管線可直接轉移至其他凍結表格基礎模型，無需重新搜尋，帶來 **+69 至 +143 Elo** 的提升。這意味著 TabFM-Auto 學到的資料清理、特徵工程與後處理策略具有**模型無關（model-agnostic）的價值**，不僅服務於 TabFM，也能強化 TabPFN、TabICL 等模型。

##### MLE-Bench 競賽表現

在 8 個表格競賽中，TabFM-Auto 於 MLE-Bench 的 MLE 代理（machine learning engineering agents）中**總排名第一（rank first overall）**。這顯示在真實競賽場景下，結合凍結基礎模型與代理式資料工程，能超越從頭訓練樹集成或神經網路的傳統 MLE 代理。

#### 與現有研究的比較

##### 相較於表格基礎模型（TFMs）

現有表格基礎模型如 TabPFN、TabICL、TabFM、EXAONE-Tabular 等，雖在零樣本準確率（zero-shot accuracy）上已能匹敵甚至超越梯度提升決策樹（GBDTs），但它們的注意力層僅處理匿名化的數值與類別索引，**忽略欄位名稱、任務描述與輔助檔案（auxiliary files）中的語義**。TabFM+ 雖加入成對交叉特徵、SVD 投影與多視角集成學習（multi-view ensembling），但仍屬通用操作，無法針對特定資料集語義進行調整。

TabFM-Auto 的進步在於：以 LLM 代理作為「語義介面」，將人類可讀的資料集後設資料轉化為機器可學的資料管線，從而彌補凍結 TFM 的語義盲點。

##### 相較於 MLE 代理

現有 MLE 代理（如相關文獻 Du et al., 2026; Jiang et al., 2025; Yang et al., 2025）通常讓 LLM 編寫端到端訓練腳本，從頭擬合樹集成或神經網路。這類方法需要**聯合搜尋（joint search）特徵、模型架構與超參數**，訓練變異（training variance）會掩蓋小型特徵改進，並容易在驗證集上過擬合。

TabFM-Auto 採取不同策略：將模型固定為預訓練完成的 TabFM，只搜尋資料管線。由於無梯度更新，每次評估更快速、雜訊更低（less noisy search），使代理能更穩定地識別真正有幫助的資料轉換。

##### 相較於 AutoGluon 等 AutoML 系統

AutoGluon 透過極限集成（extreme ensembling）與長時間（4 小時）調參達到強勁表現，但在 TabArena 上仍落後於 TabFM-Auto。這顯示在表格資料上，**凍結基礎模型 + 語義感知資料工程** 的組合，可能比傳統從頭訓練的集成方法更具樣本效率與泛化能力。

##### 限制

1. **代理成本與延遲**：每次迭代都需呼叫 LLM 產生 diff patch，並在沙盒中執行交叉驗證，對於 51 個資料集的整體搜尋成本可能相當高，論文未詳細披露總運算開銷。
2. **對 TabFM 的依賴**：雖然發現的管線可遷移至其他 TFM，但搜尋過程仍圍繞 TabFM 的特定行為（如 `TABFM_KWARGS`）進行，對於與 TabFM 差異極大的模型，遷移效果可能下降。
3. **驗證集過擬合風險**：雖然模型權重凍結，但代理仍可能過度擬合三折交叉驗證的分數，特別是在資料集較小或搜尋步數較多時。論文強調嚴格測試集隔離，但交叉驗證本身的變異仍可能導致管線選擇偏差。
4. **可解釋性**：LLM 產生的特徵工程與清理邏輯可能難以審查，特別是在醫療或金融等高風險領域，需要額外的可解釋性與安全性檢查。

#### 可重現性評估

論文目前提供的資訊中，**未明確說明是否開放原始碼、模型權重或搜尋日誌**。以下是可重現性相關的觀察：

- **資料集**：TabArena（51 datasets）與 MLE-Bench（8 competitions）均為已發表的公開基準測試，理論上可由第三方複現評估流程。
- **模型**：TabFM（400M）與其他 TFM（TabPFN、TabICL 等）的權重若已公開，則凍結推論階段可重現；但 TabFM 本身是否開源，需視原始論文與釋出政策而定。
- **代理與提示工程（prompt engineering）**：Claude Code、Codex、Antigravity 等代理的具體提示模板、搜尋預算（iteration budget）、錯誤處理與日誌摘要機制，是重現結果的關鍵。論文摘要與引言未詳述這些細節。
- **沙盒環境**：嚴格測試集隔離與遮罩驗證標籤的實作，對於防止資訊洩漏至關重要，但具體的沙盒評審器程式碼未公開。

整體而言，TabFM-Auto 的**概念與流程清楚**，但要達到論文宣稱的 Elo 分數，仍高度依賴代理實作細節與模型權重取得。建議作者未來釋出：
1. `pipeline.py` 的初始模板與代理提示模板；
2. 每個資料集最終發現的管線 P*；
3. 沙盒評估器與交叉驗證協定的完整程式碼；
4. 總運算成本（LLM token 數、GPU 小時數）以評估實用性。

#### 未來研究方向

1. **多模態與結構化後設資料的深度融合**  
   目前的後設資料主要來自欄位名稱、任務描述與輔助檔案。未來可探索將資料字典（data dictionary）、外部知識圖譜（knowledge graphs）、甚至欄位值的統計分布摘要一併輸入 LLM，以產生更精準的領域特徵。

2. **層級式類別與臨床代碼的語義處理**  
   對於 ICD9/ICD10 等臨床代碼（clinical codes），可設計專門的階層編碼（hierarchy encoding）模組，讓代理能自動將代碼分群、提取上層診斷類別，並與凍結 TFM 的輸入格式相容。

3. **多管線集成與貝葉斯最佳化結合**  
   目前 TabFM-Auto 輸出單一最佳管線 P*。未來可研究如何將多個高分配對（high-scoring candidate pipelines）進行集成，或結合貝葉斯最佳化（Bayesian optimization）來減少 LLM 呼叫次數，降低搜尋成本。

4. **線上自我演化（online self-evolving）**  
   將閉環搜尋擴展至部署後的持續學習場景：當新資料流入時，代理定期重新評估並更新資料管線，同時保持凍結基礎模型不變，以適應概念漂移（concept drift）。

5. **跨語言與跨領域遷移的理論分析**  
   發現的管線能遷移至其他凍結 TFM，暗示存在某種「表格資料最適前處理」的通用結構。未來可從理論上分析何種資料轉換對於基於合成資料預訓練的 Transformer 最具增益，並建立轉移學習的 scaling laws。

6. **安全性、公平性與可解釋性**  
   隨著 LLM 代理自動生成特徵工程程式碼，可能引入資料外洩、歧視性特徵或難以察覺的錯誤。未來需要建立自動化審查機制，例如靜態程式分析、因果公平性檢驗，以及自然語言說明生成，讓 TabFM-Auto 適用於高風險應用。

## 論文問答

**Q1：TabFM-Auto 主要想解決什麼問題？**
A：TabFM-Auto 旨在解決表格基礎模型（TFM）雖然在零樣本設定下表現強勁，卻忽略了欄位名稱、任務描述與輔助檔案等資料集語義的問題。同時，現有的自我演化機器學習工程代理雖然能從頭訓練模型，但同時聯合搜尋特徵、架構與超參數會引入大量雜訊，容易過擬合驗證集。因此，本文提出將凍結的 TabFM 與大型語言模型編碼代理結合，讓代理專注於演化資料管線，以在保留模型泛化能力的同時注入領域語義並降低預測錯誤。

**Q2：為什麼現有的表格基礎模型難以利用資料集語義？**
A：現有表格基礎模型通常是在合成表格上預訓練，這些合成資料的欄位往往是匿名或僅以浮點數幅度與類別索引呈現，模型無法辨識欄位名稱的實際意義。舉例來說，模型會把 `systolic_bp` 與 `ICD9_diagnosis` 這類具有明確醫學語義的欄位，視為與 `X_17` 無異的匿名欄位。因此，它們無法根據領域知識建立公式、對臨床代碼進行階層分群，也無法識別像 `0` 這樣的哨兵值其實代表遺失測量值。

**Q3：自我演化的 MLE 代理為何會在表格任務中過擬合？**
A：這類代理通常會同時對特徵工程、模型架構與超參數進行聯合搜尋，並且在每次評估時都從頭訓練一個新模型。由於訓練過程本身具有隨機變異，微小的特徵改進很容易被訓練雜訊掩蓋，導致驗證分數無法真實反映管線品質。長期下來，代理可能會選到在驗證集上表現好、但在測試集上泛化差的組合，造成嚴重的過擬合問題。

**Q4：TabFM-Auto 的核心方法架構是什麼？**
A：TabFM-Auto 將一個凍結的 4 億參數 TabFM 模型與一個大型語言模型編碼代理配對，代理會反覆修改圍繞 TabFM 的資料管線。這個管線包含五個主要模組：預處理、特徵工程、上下文取樣、傳給 TabFM 的關鍵字參數，以及後處理。代理在沙盒評估器中透過三折交叉驗證分數與資料集後設資料獲得回饋，並以 diff patch 的形式迭代更新 `pipeline.py`，直到找出最佳管線 P*。

**Q5：TabFM-Auto 相較於先前工作的關鍵創新在哪裡？**
A：最大的創新在於將「模型」與「資料管線」的搜尋解耦：TabFM 的權重保持凍結，只讓語言模型代理演化資料清理、特徵工程與後處理等步驟。這樣每次候選管線的評估都不需要重新訓練模型，大幅減少了訓練雜訊並加速搜尋。此外，發現的管線具有可遷移性，能直接套用到其他凍結的表格基礎模型上，顯示資料管線的優化可以獨立於特定模型權重。

**Q6：TabFM-Auto 在設計上做了哪些重要選擇？**
A：作者設計了五種配置，結合三種代理框架（Claude Code、Antigravity、Codex）與兩種語言模型（Claude Opus 5、Gemini 3.8 Flash），以驗證方法的穩健性。為了避免資料洩漏，系統採用嚴格測試集隔離與遮罩驗證標籤，並在沙盒環境中執行所有候選管線。管線被模組化為 `preprocess()`、`engineer()`、`sample()`、`TABFM_KWARGS` 與 `postprocess()`，讓代理能針對不同資料集語義進行結構化且可解釋的修改。

**Q7：TabFM-Auto 在哪些基準測試上進行評估？**
A：論文主要在 TabArena 的 51 個資料集（38 個分類、13 個迴歸）以及 MLE-Bench 的 8 個表格競賽上進行評估。在 TabArena 中，作者將五種 TabFM-Auto 配置與 66 種方法進行比較，包括 AutoGluon、TabPFN、TabICL、TabFM+ 等強大對手。評估指標包含 Elo 評分、冠軍次數、相對最佳模型的誤差差距，以及幾何平均測試誤差。

**Q8：TabFM-Auto 取得了哪些關鍵實驗結果？**
A：在 TabArena 上，五種 TabFM-Auto 配置包辦了總排名的前五名，其中最佳配置（Codex 搭配 Opus 5）將 TabFM 的 Elo 從 1785.3 大幅提升至 2013.0。這些發現的管線還能直接遷移到其他凍結表格基礎模型，帶來 +69 到 +143 Elo 的顯著進步。在 MLE-Bench 的 8 個表格競賽中，TabFM-Auto 也在所有 MLE 代理中排名第一。

**Q9：實驗中有哪些結果能說明 TabFM-Auto 的泛化能力與穩健性？**
A：最值得注意的是，針對 TabFM 搜尋到的管線可以在不重新搜尋的情況下直接轉移到其他凍結模型，顯示這些管線捕捉的是資料層面的通用規律，而非僅對 TabFM 過擬合。此外，五種不同代理與語言模型組合全部進入前五名，說明框架對底層 LLM 的選擇具有相當高的穩健性。這也暗示，只要固定一個強大的表格基礎模型，資料管線的品質才是決定最終預測效能的關鍵因素。

**Q10：TabFM-Auto 適合應用在哪些實務場景？**
A：TabFM-Auto 特別適合需要快速建模且資料帶有豐富語義的場景，例如 Kaggle 競賽、醫療診斷預測、金融風險評估與企業內部的結構化資料分析。在這些情境中，欄位名稱、任務描述與輔助檔案往往蘊含大量領域知識，傳統表格基礎模型難以自動利用。透過語言模型代理自動進行資料清理與特徵工程，TabFM-Auto 能顯著降低人工特徵探索的成本。

**Q11：若要把 TabFM-Auto 產品化，需要考慮哪些因素？**
A：首先必須確保代理生成的程式碼在沙盒中安全執行，以避免惡意或錯誤程式碼影響系統。其次，LLM API 的呼叫成本與搜尋迭代次數會直接影響整體開銷，因此需要在搜尋預算與效能提升之間取得平衡。此外，生成管線的可解釋性、後設資料的品質，以及防止測試資訊洩漏的嚴格隔離機制，都是產品落地時不可忽視的設計重點。

**Q12：TabFM-Auto 對表格機器學習領域可能帶來什麼影響？**
A：這項工作將表格 AutoML 的焦點從「同時訓練模型與搜尋特徵」轉向「凍結基礎模型 + 代理式資料管線演化」，為未來的表格基礎模型系統提供了一個新的設計範式。它也凸顯了資料集後設資料的重要性，可能促使未來的基準測試更重視欄位描述、輔助檔案與任務語義的標準化。長遠來看，這種方法有望縮小自動化機器學習與領域專家手工建模之間的差距。

**Q13：TabFM-Auto 有哪些已知的限制？**
A：TabFM-Auto 的效果高度依賴語言模型理解欄位名稱與任務描述的能力，若後設資料缺失或具有誤導性，代理可能無法產生有效的特徵工程。此外，由於 TabFM 的權重完全凍結，代理無法透過微調模型來彌補資料管線的不足，這在某些極端資料分布上可能限制最終表現。最後，雖然每次評估不需要重新訓練模型，但多次 LLM 呼叫與交叉驗證仍會帶來不可忽略的計算成本。

**Q14：TabFM-Auto 在哪些情況下可能會失敗？**
A：當語言模型對領域知識產生幻覺時，可能會建立錯誤的領域公式或無意中造成資料洩漏。如果資料集中的遺失值以非標準哨兵值編碼，而代理未能正確識別，也可能導致預處理錯誤。此外，在樣本數極少或訊號極弱的資料集上，三折交叉驗證分數可能過於雜訊，使得代理難以穩定地選出真正泛化良好的管線。

**Q15：未來可以朝哪些方向延伸 TabFM-Auto？**
A：未來可以將框架擴展到多表關聯、時間序列與異質資料來源，進一步發揮語言模型在複雜結構資料上的理解能力。另一個方向是讓代理在必要時對 TabFM 進行輕量級適應，例如提示微調或選擇性層級更新，以兼顧效率與彈性。此外，建立可重複使用的發現管線資料庫、發展多代理協作機制，以及從理論上理解為何某些管線能跨模型遷移，都是值得深入探索的研究課題。

## 實務應用指南

### 適用場景

1. **醫療預測與臨床決策支援**  
   利用欄位名稱（如 `systolic_bp`、`ICD9_diagnosis`）與輔助檔案（疾病階層表、檢驗參考值），自動將哨兵值（sentinel 0）轉為遺失值、建立領域公式特徵，並針對類別不平衡進行後處理校準。

2. **金融風控與信用評分**  
   任務描述與欄位語義（收入、逾期天數、產業別）可指導 LLM 產生合理的特徵工程與異常值過濾邏輯，並透過上下文取樣處理少數違約樣本。

3. **科學與天文資料分析**  
   欄位語義明確的結構化資料（如天文波段的 `u`、`g`）適合產生領域特徵（顏色指數），再搭配凍結 TabFM 的零樣本推論加速實驗迭代。

4. **電商用戶屬性與轉換預測**  
   自動進行成對交叉特徵、SVD 投影、非負最小平方法（NNLS）等轉換，並選取資訊豐富的上下文列，提升用戶分群或購買意圖預測。

5. **企業內部結構化資料 AutoML 平台**  
   將 TabFM-Auto 作為後端引擎，為多個業務表格自動搜尋資料管線，並把發現的管線註冊為可重複使用的特徵工程範本。

---

### 實作前置條件

**資料條件**
- 結構化表格資料（CSV / Parquet），具備有意義的欄位名稱與任務描述。
- 建議提供輔助檔案或資料字典（data dictionary），以攜帶欄位語義。
- 訓練集、驗證集、測試集需明確分離，標籤完整且缺失值編碼一致。

**運算條件**
- 可執行凍結 TabFM（400M 參數）前向傳遞的 GPU / TPU 環境。
- LLM coding agent（Claude Code、Codex、Antigravity 等）的執行環境與 API 配額。
- 沙盒評估器（sandboxed evaluator）資源，每次候選管線需執行 3-fold cross-validation，需預留足夠運算預算。

**技能條件**
- 熟悉 Python、資料清理、特徵工程與交叉驗證流程。
- 能設定沙盒隔離、LLM agent 提示工程與 diff patch 管理。
- 理解 TabFM 推論 API 與關鍵字參數（如 `norm_methods`、`enable_nnls`）。
- 具備領域知識以審查 LLM 產生的特徵與轉換邏輯。

---

### 實作步驟建議

1. **準備資料與後設資料**  
   整理欄位名稱、任務描述、輔助檔案與資料字典，統一缺失值編碼（例如將 sentinel 0 對應為 NaN）。

2. **建立沙盒評估環境**  
   實作嚴格測試集隔離，確保 agent 只能接觸訓練集；建立 3-fold CV 評分、日誌記錄與錯誤回饋機制。

3. **初始化基礎管線**  
   定義 `preprocess()`、`engineer()`、`sample()`、`postprocess()` 與 `TABFM_KWARGS`，先以簡單清理與預設參數取得基準分數。

4. **啟動 LLM coding agent**  
   將資料後設資料、目前 CV 分數與日誌餵給 agent，讓其以 diff patch 形式修改 `pipeline.py`。

5. **迭代評估與篩選**  
   每個候選管線（candidate pipeline, P）都透過 3-fold CV 評分，保留驗證分數最高的發現管線（P*）。

6. **最終測試與部署**  
   選定 P* 後，僅在官方測試集上評估一次；將管線包裝為可重複執行的服務，整合至批次推論或線上 API。

7. **監控與再演化**  
   上線後追蹤預測偏移與新資料分布，定期以新的驗證回饋觸發重新搜尋或僅更新後處理校準。

---

### 潛在風險與注意事項

- **測試資訊洩漏**  
  Agent 可能無意間使用測試集統計量。必須嚴格隔離測試集，驗證標籤需遮罩，所有回饋僅來自訓練集 CV。

- **驗證集過擬合**  
  反覆搜尋會使管線過度適配 CV 分數。建議限制迭代次數、使用穩定指標，並保留 hold-out test 只做最終評估。

- **領域特徵安全性**  
  LLM 產生的公式可能語義錯誤，或利用 ID、時間戳等洩漏標籤。需建立黑名單與人工審查機制。

- **運算成本**  
  LLM 呼叫與多次 TFM 前向傳遞成本高昂。可設定預算上限、快取候選管線評估結果，並優先評估低成本變更。

- **可解釋性與合規**  
  自動產生的特徵與校準可能難以解釋。金融、醫療等場景需保留特徵血緣（lineage）與決策記錄。

- **對基礎模型依賴**  
  整體效益取決於凍結 TabFM 的品質與支援的資料類型；若 TFM 不支援某些欄位，需額外預處理轉換。

---

### 與其他技術的整合建議

- **AutoML 平台**  
  將 TabFM-Auto 作為一個 estimator，與 AutoGluon、GBDT、神經網路並列；發現的管線也可轉移至 TabPFN、TabICL 等凍結表格基礎模型。

- **MLOps 流程**  
  將 `pipeline.py` 與 P* 版本化，納入 CI/CD；沙盒評估器可整合至 Kubeflow、MLflow 或 Weights & Biases 進行實驗追蹤。

- **資料平台與特徵商店**  
  與資料目錄（data catalog）連接以自動讀取欄位描述；將穩定的特徵工程步驟註冊為可重用特徵，減少重複搜尋。

- **非結構化資料前處理**  
  對於文字或圖像欄位，先用 LLM 或 embedding 模型抽取結構化特徵，再進入 TabFM-Auto；任務描述也可由 LLM 自動生成。

- **監控與漂移偵測**  
  搭配 drift detection，當資料分布偏移時觸發重新搜尋，或僅重新校準後處理（post-processing）以節省成本。

### 給不同背景讀者的閱讀建議

- **初學者**  
  先掌握「凍結基礎模型 + LLM 自動改資料管線」的核心概念，把 TabFM-Auto 想像成會自己寫資料清理與特徵工程的 AutoML。重點看圖 2 的管線流程與 TabArena 排名，不必一開始就深入 TFM 架構細節。

- **AI 工程師**  
  關注沙盒評估器、diff patch 機制、3-fold CV 回饋迴路、嚴格測試集隔離與後處理校準。評估如何將現有 TFM 推論服務改裝為 agentic search backend，並設計運算成本與快取策略。

- **研究人員**  
  重點在於「固定模型、搜尋管線」相較於「聯合搜尋特徵、架構與超參數」如何降低雜訊與過擬合。可延伸研究上下文取樣策略、跨 TFM 管線遷移、以及 LLM agent 的搜尋空間與收斂性。

- **產品經理**  
  理解這是提升表格預測準確度的新範式，特別適合欄位語義豐富但資料量不大的場景。需同時評估 LLM 與 TFM 推論成本、合規審查流程，以及與現有資料團隊工作流的銜接方式。
