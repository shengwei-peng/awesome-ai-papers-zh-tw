## ⚡ TL;DR

傳統NL2Code僅依賴文字描述，無法處理以視覺工件為核心的程式設計任務。
本文提出以程式碼角色為基礎的分類法，涵蓋GUI、科學視覺化、結構化圖形與前沿任務四大領域。
並提出多訊號驗證、多狀態驗證等四大未來方向，推動從模仿學習邁向證據基礎的可執行系統。

## 摘要翻譯

雖然大型語言模型（Large Language Models, LLMs）已大幅推進文字到程式碼合成（Text-to-Code Synthesis），許多真實的程式設計任務透過視覺工件（Visual Artifacts）——例如螢幕截圖（Screenshots）、圖表（Charts）、向量繪圖（Vector Drawings）、影片（Video）及互動狀態（Interactive States）——來表達意圖。這些任務要求模型將視覺感知（Visual Perception）與可執行程式（Executable Programs）連結起來，因為正確性不僅取決於語法，還取決於佈局（Layout）、資料語義（Data Semantics）、互動行為（Interaction Behavior），以及於執行階段方生效的領域特定約束（Domain-Specific Constraints）。本綜述探討多模態程式碼智慧（Multimodal Code Intelligence），涵蓋在視覺基礎輸入（Visually Grounded Inputs）與視覺基礎輸出（Visually Grounded Outputs）下，進行程式碼生成（Code Generation）、程式碼編輯（Code Editing）、程式碼精煉（Code Refinement）或程式碼推理（Code Reasoning）的系統。我們首先依據程式碼在每項任務中所扮演的角色來闡述該領域，將程式碼區分為渲染工件（Rendered Artifact）、可編輯符號結構（Editable Symbolic Structure）、科學表示（Scientific Representation）、中間推理軌跡（Intermediate Reasoning Trace），或可執行策略（Executable Policy）與工具介面（Tool Interface）。接著，我們將基準測試（Benchmark）與方法組織成四個領域：圖形使用者介面（Graphical User Interface, GUI）、科學視覺化（Scientific Visualization）、結構化圖形（Structured Graphics），以及前沿任務與框架（Frontier Tasks and Frameworks）。此分類法（Taxonomy）將成熟的工件生成問題與新興的代理式設定（Agentic Settings）及統一多模態程式碼生成（Unified Multimodal Code Generation）連結起來，並使我們能夠比較不同任務對正確性證據（Evidence of Correctness）的處理方式。展望未來，我們主張未來研究宜朝以下四個以驗證（Verification）為中心的方向發展：多訊號驗證（Multi-Signal Validation）可結合互補的正確性證據；多狀態驗證（Multi-State Verification）可跨執行軌跡（Execution Trajectories）測試行為；跨任務遷移測試（Cross-Task Transfer Testing）可探測可重複使用的視覺-程式碼技能（Visual-Code Skills）；而可驗證代理軌跡（Verifiable Agent Traces）則能揭示代理（Agent）的行動是否奠基於視覺證據（Visual Evidence）。整體而言，這些方向可將該領域從單一輸出模仿（Single-Output Imitation）推向證據基礎的可執行系統（Evidence-Grounded Executable Systems）。持續進行的專案與資源可於 https://github.com/xjywhu/Awesome-Multimodal-LLM-for-Code 取得。

### 核心貢獻（3～5點）
- **提出以程式碼角色為核心的分類框架**：將多模態程式碼任務區分為五種程式碼角色——渲染工件、可編輯符號結構、科學表示、中間推理軌跡、可執行策略或工具介面——為異質任務提供統一的分析視角。
- **建立四大領域的系統性綜述**：涵蓋圖形使用者介面、科學視覺化、結構化圖形、前沿任務與框架，串連成熟的工件生成問題與新興的代理式及統一多模態程式碼生成設定。
- **比較不同任務的正確性證據處理方式**：橫向剖析各任務如何評估功能正確性、視覺保真度與語義一致性，揭示現有評估方法的不足。
- **提出四個以驗證為中心的前瞻研究方向**：包括多訊號驗證、多狀態驗證、跨任務遷移測試、可驗證代理軌跡，為未來研究從單一輸出模仿邁向證據基礎的可執行系統勾勒具體路徑。
- **彙整開源資源與持續維護的專案清單**：提供完整的基準測試、方法與資源索引（GitHub: xjywhu/Awesome-Multimodal-LLM-for-Code），促進社群後續研究。

### 適合對象
- 從事**多模態大型語言模型（Multimodal LLMs）** 與**程式碼智慧（Code Intelligence）** 研究的學者與博士生，特別是關注視覺-程式碼跨模態對齊（Cross-Modal Alignment）的研究者。
- 投入**前端開發（Frontend Development）**、**資料視覺化（Data Visualization）**、**電腦輔助設計（CAD）**、**具身控制（Embodied Control）** 等領域之工程師與技術領導者。
- 對**代理式系統（Agentic Systems）**、**視覺基礎對應（Visual Grounding）**、**視覺化程式設計（Visual Programming）** 感興趣的 AI 研究人員。
- 正在尋找**基準測試（Benchmark）**、**評估指標** 與**開源工具** 以建構多模態程式碼生成系統的實務開發者。

## 深度分析

#### 方法論解析

本論文為一篇結構化綜述（structured survey），其核心方法論並非提出單一演算法，而是建立一套系統性的領域分類法（taxonomy）與問題形式化框架（problem formulation framework），用以梳理多模態程式碼智慧（Multimodal Code Intelligence）這一快速擴張的研究領域。

**問題形式化的雙軸設計**

作者採用兩個互補的軸來形式化整個領域。第一個軸是「程式碼所扮演的角色」，將任務區分為五種語意角色：(1) 渲染工件（rendered artifact），即程式碼的執行結果本身就是視覺輸出，例如網頁或圖表；(2) 可編輯符號結構（editable symbolic structure），程式碼本身是視覺內容的符號化表示，例如 SVG 或 CAD 程式碼；(3) 科學表示（scientific representation），程式碼用於表達科學計算或模擬，例如 Matplotlib 繪圖指令；(4) 中間推理軌跡（intermediate reasoning trace），程式碼作為視覺推理的中間步驟，例如鏈條推理（chain-of-thought）中的計算；(5) 可執行策略或工具介面（executable policy or tool interface），程式碼作為代理（agent）與環境互動的動作空間。這種以「程式碼角色」為核心的形式化方式，比傳統以輸入模態分類的方式更能揭示任務的本質差異。

第二個軸是「正確性證據的來源」（evidence of correctness），涵蓋渲染後比對、執行後測試、互動後狀態檢查、重播後軌跡驗證等不同驗證信號。這一軸直接連結到後續提出的四大未來方向。

**四領域分類法**

作者將現有文獻組織為四大領域，每個領域對應不同的視覺-程式碼耦合模式：

1. **圖形使用者介面（Graphical User Interface）**：涵蓋網頁應用程式（Website Application）與行動應用程式（Mobile Application）兩子領域。此處程式碼的角色是渲染工件，視覺輸入（設計稿、截圖）需轉化為可執行的前端程式碼（HTML/CSS/JavaScript、Swift、Kotlin 等）。

2. **科學視覺化（Scientific Visualization）**：分為統計圖表（Statistical Charts）、結構化文件（Structured Document）、學術簡報（Academic Presentations）、科學展示（Scientific Demonstration）四子領域。程式碼在此既是渲染工件，也是科學表示，涉及 Matplotlib、Plotly、LaTeX、Beamer 等領域特定語言（DSL）。

3. **結構化圖形（Structured Graphics）**：涵蓋可縮放向量圖形（SVG）、圖表（Diagram，含流程圖、UML 等）、電腦輔助設計（CAD）三子領域。程式碼的角色偏向可編輯符號結構，視覺內容與程式碼之間存在近乎一一對應的關係。

4. **前沿任務與框架（Frontier Tasks and Frameworks）**：包含程式化視覺操控（Programmatic Visual Manipulation）、影片程式碼生成（Video Code Generation）、具身控制（Embodied Control）、視覺基礎程式設計（Visually Grounded Programming）、統一多模態程式碼生成（Unified Multimodal Code Generation）五子領域。此處程式碼的角色擴展到可執行策略與工具介面，呈現代理式（agentic）與統一模型的新興典範。

**敘事結構設計**

每個子章節末尾設有「範疇與軌跡」（Scope and Trajectory）段落，識別任務目標、主流證據信號與剩餘驗證缺口；每個領域章節結尾設有「重點摘要」（Takeaway）段落，總結該領域瓶頸。這種結構使讀者能在掌握具體方法的同時，理解領域層級的系統性挑戰。

**綜述方法論**

作者遵循分階段審查協議（staged review protocol），包含來源收集、候選篩選、分類指派與作者手動一致性檢查。文獻來源涵蓋 arXiv 與 AI、計算語言學、軟體工程等主要會議，文獻快照更新至 2026 年 1 月。

#### 實驗數據解讀

由於本綜述並非實驗性研究，「實驗數據」實際上指的是各子領域中被彙整的基準測試（benchmark）、評估指標（metric）與主流方法的效能比較。以下依四大領域解讀：

**GUI 領域的評估生態**

網頁應用程式子領域的核心挑戰在於視覺保真度（visual fidelity）與功能正確性（functional correctness）的雙重驗證。基準測試通常包含設計稿到程式碼（design-to-code）、截圖到程式碼（screenshot-to-code）兩類任務。評估指標從早期的 BLEU、CodeBLEU 等文字相似度指標，演進到像素級比對（pixel-level matching）、結構相似性（SSIM）、以及渲染後的視覺匹配（visual match）。然而，純視覺比對無法捕捉互動行為，因此前端任務逐漸引入執行匹配（execution match）與人類評估（human evaluation）作為補充。

行動應用程式子領域面臨額外的挑戰：iOS 與 Android 平台的元件庫差異、響應式佈局（responsive layout）需求、以及跨裝置一致性。基準測試通常以 XML 佈局檔或截圖作為輸入，目標語言涵蓋 Swift、Kotlin、Flutter 等。

**科學視覺化領域的評估生態**

統計圖表子領域是評估方法最成熟的子領域之一。基準測試包含圖表到程式碼（chart-to-code）與程式碼到圖表（code-to-chart）雙向任務。評估指標涵蓋：(1) 視覺層面的像素準確率（pixel accuracy）與結構準確率（structural accuracy）；(2) 資料層面的語義準確率（semantic accuracy），即資料值、類別、座標軸是否正確；(3) 程式碼層面的執行匹配。值得注意的是，此領域的「正確性」具有多層次意義——視覺相似但資料錯誤的圖表仍屬失敗。

結構化文件子領域涉及 LaTeX、Markdown 等標記語言的生成，評估重點在於排版正確性、數學公式渲染、引用格式等。

學術簡報子領域結合了文件生成與視覺設計，評估指標涵蓋版面配置（layout）、視覺層次（visual hierarchy）、內容完整性等。

科學展示子領域（如 TikZ 圖形、動畫）則強調精確的幾何與物理模擬。

**結構化圖形領域的評估生態**

SVG 子領域的特點在於程式碼與視覺之間存在近乎雙射的關係，因此評估可同時在程式碼層面（如語法正確性、token 序列相似度）與渲染層面（如像素比對、向量路徑比對）進行。

圖表子領域涵蓋流程圖、UML、實體關係圖等，評估重點在於節點位置、連線拓撲、語義標籤的正確性。

CAD 子領域最具挑戰性，因為 CAD 程式碼涉及三維幾何約束（geometric constraints）、參數化設計（parametric design）與工程語義。評估指標通常包含幾何精度（geometric precision）、約束滿足率（constraint satisfaction rate）與製造可行性（manufacturability）。

**前沿領域的評估生態**

程式化視覺操控子領域評估代理是否能透過程式碼精準操控圖像或影片元素，採用任務成功率（task success rate）與視覺一致性指標。

影片程式碼生成子領域評估生成的程式碼是否能重現影片中的動畫或互動，採用幀級（frame-level）視覺比對與時間一致性（temporal consistency）指標。

具身控制子領域將程式碼視為機器人策略（robot policy），評估在模擬器（如 RoboSuite、Habitat）中的任務成功率，並關注模擬到真實的遷移（sim-to-real transfer）。

統一多模態程式碼生成子領域評估單一模型跨多任務的泛化能力，通常採用跨任務平均效能與零樣本遷移（zero-shot transfer）指標。

**整體觀察**

跨領域比較顯示，評估方法的成熟度與任務的「視覺-程式碼耦合度」呈正相關：耦合度越高（如 SVG），評估越容易標準化；耦合度越低（如具身控制），評估越依賴模擬器與人類評估。此外，純視覺比對指標在所有領域都呈現「天花板效應」——當兩個視覺相似的輸出對應完全不同的程式碼時，視覺指標無法區分，這正是作者強調「多訊號驗證」的動機。

#### 與現有研究的比較

**與既有程式碼生成綜述的比較**

相較於既有 NL2Code 綜述（如 Zan et al. 2023、Yang et al. 2025d 等聚焦於文字到程式碼的工作），本綜述的獨特貢獻在於：

1. **模態擴展**：將程式碼生成的範疇從純文字輸入擴展到視覺輸入，填補了「視覺-程式碼」這一未被系統整理的研究空白。
2. **角色導向的形式化**：既有綜述多以任務類型（函數級、倉庫級、工具使用）分類，本綜述則以「程式碼扮演的角色」為核心，提供更語意化的分類軸。
3. **驗證中心的前瞻議題**：既有綜述多以「效能提升」為未來方向，本綜述則提出「驗證」作為下一階段研究的核心議題，反映領域從「模仿單一輸出」轉向「證據基礎可執行系統」的典範轉移。

**與多模態 LLM 綜述的比較**

相較於通用多模態 LLM 綜述（如 Liu et al. 2023b、Shen et al. 2025），本綜述的差異在於：

1. **領域聚焦**：通用綜述涵蓋視覺問答、圖像描述、視覺推理等多任務，本綜述則專注於「程式碼」這一特定輸出形式。
2. **正確性標準**：通用視覺任務的正確性通常以語義匹配為主，而程式碼任務要求語法正確、執行正確、視覺正確三者的統一，標準更為嚴苛。
3. **代理式視角**：本綜述將程式碼視為代理動作空間的一部分，呼應了近期 agentic AI 的發展趨勢。

**本綜述的限制**

1. **缺乏量化比較**：作為綜述，本文未提供跨基準的統一量化比較表，讀者難以直接判斷各方法的相對優劣。
2. **領域覆蓋不均**：前沿領域（Section 6）的文獻可能尚未穩定，分類可能在領域成熟後需要修訂。
3. **語言與文化偏誤**：綜述主要聚焦英語學術界與西方主流框架（如 React、Swift），對中文、阿拉伯文等非英語語境下的程式碼生成探討較少。
4. **時效性挑戰**：文獻快照截至 2026 年 1 月，但領域發展迅速，特別是統一多模態模型與代理式框架的演進速度極快。

#### 可重現性評估

**開源資源**

作者提供了持續更新的 GitHub 專案（https://github.com/xjywhu/Awesome-Multimodal-LLM-for-Code），這是本綜述最重要的可重現性資產。該專案應包含：

1. **論文清單**：按四大領域分類的相關論文清單，並持續更新。
2. **基準測試彙整**：各子領域基準測試的連結、規模、評估指標說明。
3. **方法彙整**：各方法的程式碼倉庫連結、預訓練權重（若開源）、訓練資料說明。
4. **分類索引**：依「程式碼角色」與「正確性證據」兩軸交叉索引的查詢介面。

**基準測試的可重現性**

各子領域的基準測試可重現性差異顯著：

- **高度可重現**：SVG、統計圖表等領域的基準測試通常公開資料集與評估腳本，研究者可重現報告結果。
- **中等可重現**：GUI 領域的基準測試（如 WebSight、Design2Code）通常公開資料，但評估涉及渲染引擎版本、瀏覽器差異等環境敏感因素。
- **低度可重現**：具身控制領域的基準測試高度依賴模擬器版本與物理參數，跨實驗室的結果可比性較低。

**模型權重與訓練資料**

綜述中提及的多模態程式碼模型（如基於 Llama 2 7B 微調的視覺-語言-動作模型 OpenVLA）通常開源權重，但訓練資料的開源程度不一。部分模型僅釋出推論程式碼，訓練細節未完全公開，限制了獨立重現。

**評估的可重現性**

視覺比對指標（如 SSIM、像素準確率）的實作相對標準化，但涉及 LLM 評審（LLM-as-a-judge）或人類評估的部分，由於評審模型版本、提示詞、人類評審背景的差異，重現性較低。

**整體評估**

本綜述的可重現性主要體現在「分類法」與「文獻彙整」層面，而非「實驗結果」層面。GitHub 專案的持續維護是關鍵，建議讀者定期檢視更新。

#### 未來研究方向

作者提出四大以驗證為中心（verification-centered）的未來方向，每個方向都對應當前領域的具體瓶頸：

**1. 多訊號驗證（Multi-Signal Validation）**

當前評估過度依賴單一信號（多為視覺比對），無法捕捉程式碼的多維度正確性。未來研究應結合互補證據：(1) 視覺證據（渲染後的像素比對）；(2) 結構證據（程式碼的語法樹、抽象語法樹 AST 結構比對）；(3) 語義證據（執行後的資料值、變數綁定比對）；(4) 互動證據（使用者操作後的狀態轉換比對）。例如，一個圖表生成任務應同時驗證視覺相似度、資料值的正確性、座標軸標籤的語義、以及圖例與資料系列的對應關係。

**2. 多狀態驗證（Multi-State Verification）**

當前評估多為單一靜態輸出比對，無法捕捉程式碼在執行過程中的動態行為。未來研究應測試程式碼在多個執行狀態下的表現：(1) 不同輸入下的輸出；(2) 不同時間點的狀態；(3) 錯誤處理路徑；(4) 邊界條件。這對於互動式 UI、動畫、具身控制等任務尤其關鍵。例如，一個網頁應用程式不僅要在初始渲染時正確，還要在使用者點擊按鈕、捲動頁面、調整視窗大小等操作後保持正確。

**3. 跨任務遷移測試（Cross-Task Transfer Testing）**

當前研究多在單一任務上訓練與評估，無法判斷模型是否學到可遷移的視覺-程式碼技能。未來研究應設計遷移測試協議：(1) 任務內遷移（如從長條圖遷移到折線圖）；(2) 領域間遷移（如從 SVG 遷移到 CAD）；(3) 模態間遷移（如從圖像輸入遷移到影片輸入）；(4) 語言間遷移（如從 Python 遷移到 JavaScript）。這有助於區分「任務特定過擬合」與「通用視覺-程式碼推理能力」。

**4. 可驗證代理軌跡（Verifiable Agent Traces）**

當代理透過程式碼與環境互動時，當前研究多關注最終結果，忽略中間軌跡的正確性。未來研究應驗證：(1) 代理的每一步動作是否基於視覺證據（而非幻覺）；(2) 動作序列是否邏輯連貫；(3) 失敗時是否能自我診斷；(4) 軌跡是否可重現。這對於具身控制、視覺基礎程式設計、統一多模態代理等任務尤其關鍵。例如，一個機器人代理在「擦桌子」任務中，每一步抓取、擦拭、放置的動作都應有對應的視覺觀察作為依據。

**其他潛在方向**

除作者提出的四大方向外，本綜述還暗示了若干值得探索的議題：

1. **資料效率**：高品質視覺-程式碼配對資料的收集成本高昂，未來應探索自監督學習（self-supervised learning）、合成資料（synthetic data）、弱監督學習（weakly supervised learning）等資料效率方法。
2. **可解釋性**：當模型生成複雜程式碼時，如何讓使用者理解模型的視覺-程式碼對應邏輯，是實務部署的關鍵。
3. **安全性與可靠性**：在具身控制、醫療視覺化等高風險領域，程式碼錯誤可能導致嚴重後果，需要形式化驗證（formal verification）與安全保證。
4. **人機協作**：未來系統應支援人類在迴圈中（human-in-the-loop）的迭代修正，而非一次性生成。
5. **多語言與多文化**：當前研究多以英語與西方設計慣例為主，未來應擴展到多語言註解、多文化設計風格。

**總結**

本綜述透過「程式碼角色」與「正確性證據」雙軸形式化，系統性地梳理了多模態程式碼智慧這一快速發展的領域。其核心貢獻不僅在於文獻彙整，更在於提出「從單一輸出模仿轉向證據基礎可執行系統」的典範轉移。四大驗證中心方向為未來研究提供了清晰的路線圖，而 GitHub 專案的持續維護將確保綜述的時效性。對於研究者而言，本綜述既是進入該領域的入口，也是識別研究空白的指南。

## 論文問答

**Q1：為什麼傳統的 NL2Code（自然語言到程式碼）方法不足以處理真實世界的程式設計任務？**
A：傳統的 NL2Code 方法主要依賴文字描述來傳達程式設計意圖，但在許多視覺密集型的領域中，僅靠文字無法有效表達複雜的空間佈局、幾何結構或視覺風格等資訊。論文中明確指出，在前端開發、資料視覺化、電腦輔助設計等場景中，單一張圖像能比冗長的文字描述更有效率地編碼密集的空間階層與結構資訊。這種模態落差導致人類意圖與生成程式碼之間的錯位，使得僅基於文字的 NL2Code 方法在視覺驅動的任務中表現不佳。因此，必須引入視覺感知作為核心前提，而非僅作為輔助特徵，才能真正自動化這些視覺驅動的程式設計任務。

**Q2：視覺信號相較於文字描述在程式設計任務中有何優勢？**
A：視覺信號是一種高頻寬且直觀的溝通媒介，能在單一影像中同時編碼空間階層、色彩配置、物件關係等複雜資訊，而這些資訊若用文字描述往往冗長且容易遺漏關鍵細節。論文強調，視覺資訊對於表達使用者介面佈局、精確幾何結構、互動行為等面向特別有效，這些都是純文字難以精準描述的內容。此外，視覺證據還能作為程式碼正確性的重要驗證依據，因為許多任務的最終輸出本身就是視覺工件（如渲染後的網頁、圖表、SVG 圖形）。這種「視覺即規格、視覺即驗證」的雙重角色，使視覺信號在多模態程式碼智慧中扮演不可或缺的角色。

**Q3：為什麼「多模態程式碼智慧」這個領域在當前時點特別重要？**
A：隨著多模態大型語言模型（MLLMs）的快速發展，將視覺感知與邏輯推理整合到程式碼生成中已成為技術上的可行方向，這為解決視覺驅動的程式設計瓶頸提供了新的契機。論文中提到，程式碼已從函式層級的合成擴展到儲存庫層級的工程、議題解決、程式碼中介的工具使用等更廣泛的範疇，但這些進展在視覺意圖為主的情境下仍顯不足。此外，現實世界的程式設計任務越來越多地涉及視覺工件（如螢幕截圖、設計稿、影片、互動狀態），使得純文字介面成為瓶頸。因此，建立一個系統性的多模態程式碼智慧框架，不僅能填補研究文獻中的分類缺口，也能指引未來技術發展的方向。

**Q4：這篇論文提出的核心分類法是什麼？它如何區分不同的多模態程式碼任務？**
A：論文提出了一個以「程式碼所扮演的角色」為核心軸線的分類法，將多模態程式碼任務區分為五種角色：渲染工件（rendered artifact）、可編輯符號結構（editable symbolic structure）、科學表示（scientific representation）、中間推理軌跡（intermediate reasoning trace），以及可執行策略或工具介面（executable policy or tool interface）。這個分類法的創新之處在於，它不僅關注輸入或輸出是否包含視覺元素，更深入探討程式碼在整個任務流程中的功能性角色。例如，在 GUI 生成中程式碼是渲染工件，在 SVG 生成中則是可編輯符號結構，而在具身控制中程式碼則是可執行策略。這種以角色為中心的視角能更精準地捕捉不同任務的驗證需求與瓶頸所在。

**Q5：程式碼在多模態任務中扮演哪些不同的角色？**
A：根據論文的分類法，程式碼在不同任務中扮演五種截然不同的角色。第一種是「渲染工件」，例如網頁或行動應用程式生成，程式碼經編譯或執行後產生視覺介面；第二種是「可編輯符號結構」，如 SVG、圖表、CAD 等，程式碼本身就是可被進一步編輯的結構化表示；第三種是「科學表示」，用於科學視覺化中表達資料與視覺編碼的對應關係；第四種是「中間推理軌跡」，程式碼作為模型推理過程的中間步驟，輔助視覺理解與規劃；第五種是「可執行策略或工具介面」，例如在具身控制或影片生成中，程式碼作為控制機器人或生成影片的可執行指令。這種多樣化的角色反映了多模態程式碼智慧的豐富性，也凸顯了不同任務需要不同的驗證策略。

**Q6：這篇論文如何將現有研究組織成四大領域？這樣的組織方式有何優勢？**
A：論文將現有研究組織成四大領域：圖形使用者介面（GUI）、科學視覺化、結構化圖形、前沿任務與框架。GUI 涵蓋網頁與行動應用程式生成；科學視覺化涵蓋統計圖表、結構化文件、學術簡報與科學展示；結構化圖形涵蓋 SVG、圖表與電腦輔助設計；前沿任務則涵蓋程式化視覺操控、影片程式碼生成、具身控制、視覺基礎程式設計與統一多模態程式碼生成。這種組織方式的優勢在於，它將成熟的工件生成問題與新興的代理式與統一設定連接起來，使讀者能清楚看到不同任務之間的演進脈絡與技術傳承關係。同時，每個小節結尾的「範疇與軌跡」段落與領域結尾的「重點摘要」段落，提供了任務目標、主流證據訊號與剩餘驗證缺口的系統性分析。

**Q7：這篇論文回顧了哪些主要的基準測試（benchmarks）？**
A：論文回顧了橫跨四大領域的多項基準測試。在 GUI 領域，涵蓋了網頁應用程式（如基於螢幕截圖生成 HTML/CSS 的基準）與行動應用程式（如 Android UI 生成基準）的相關評測。在科學視覺化領域，則涵蓋了統計圖表（如 ChartQA、PlotQA）、結構化文件、學術簡報生成等基準。在結構化圖形領域，則回顧了 SVG 生成、圖表（如流程圖、UML 圖）以及 CAD 相關的基準測試。在前沿任務領域，則涵蓋了程式化視覺操控、影片程式碼生成、具身控制（如 OpenVLA 等視覺-語言-動作模型）以及統一多模態程式碼生成的評測框架。這些基準測試的共同特點是，它們都強調視覺證據在評估中的關鍵作用，超越了傳統的文字匹配指標。

**Q8：在不同領域中，主要的評估指標和方法是什麼？**

**Q9：各領域中代表性的方法或模型有哪些？**

**Q10：多模態程式碼智慧有哪些實際應用場景？**
A：多模態程式碼智慧的應用場景非常廣泛。在前端開發中，設計師可以透過提供設計稿或螢幕截圖，讓模型自動生成對應的 HTML/CSS/JavaScript 程式碼，大幅縮短從設計到實作的時間。在資料視覺化中，分析師可以將圖表影像或草圖轉換為可重現的視覺化程式碼，實現視覺化作品的逆向工程與再利用。在電腦輔助設計中，工程師可以透過草圖或參考圖生成 CAD 模型，加速產品設計流程。在機器人與具身控制中，程式碼作為可執行策略，使機器人能根據視覺輸入完成複雜任務。此外，在影片生成、互動式簡報、文件自動化等領域，多模態程式碼智慧也展現出巨大的應用潛力。

**Q11：這項技術對軟體開發產業有何影響？**
A：多模態程式碼智慧對軟體開發產業的影響是深遠的。首先，它降低了程式設計的入門門檻，使非技術背景的設計師、產品經理或領域專家能透過視覺表達直接生成可用的程式碼，促進跨領域協作。其次，它提升了開發效率，特別是在前端開發、視覺化與設計相關的工作流程中，能自動化大量重複性的實作任務。再者，它推動了開發工具的轉型，從傳統的 IDE 文字編輯器轉向視覺驅動的整合開發環境，開發者可以透過視覺反饋即時調整生成結果。最後，這項技術也對軟體品質保證提出了新挑戰，因為視覺正確性與互動行為的驗證比純文字程式碼更為複雜，需要發展新的測試與驗證方法論。

A：論文在第 8 節「限制」中坦誠地承認了若干研究範疇上的限制。首先，作為一篇綜述性論文，其文獻快照更新至 2026 年 1 月，無法涵蓋所有最新的研究進展，特別是這個快速發展的領域。其次，分類法雖然提供了清晰的組織框架，但某些任務可能跨越多個領域或具有混合特性，難以嚴格歸類。再者，論文中提出的未來研究方向（如多訊號驗證、多狀態驗證）仍處於概念階段，缺乏具體的實證驗證。此外，論文主要聚焦於學術研究，對於實際部署中的工程挑戰、成本效益分析與使用者接受度等議題著墨較少。最後，跨文化、跨語言的視覺-程式碼對齊問題，以及特定領域（如醫療、法律）的合規性要求，也未在論文中深入探討。

**Q14：目前多模態程式碼智慧系統可能面臨哪些失敗案例？**
A：根據論文的分析，目前多模態程式碼智慧系統可能面臨多種類型的失敗案例。在視覺保真度方面，模型可能無法精確重現複雜的佈局細節、色彩配置或字型排版，導致生成結果與設計意圖存在視覺落差。在互動行為方面，模型可能僅生成靜態介面而忽略按鈕點擊、表單提交、動畫過渡等動態行為。在資料語義方面，圖表生成可能錯誤對應資料值與視覺編碼，導致視覺化結果傳達錯誤的資訊。在代理式任務中，模型可能產生無法執行的程式碼，或在多步驟任務中偏離原始視覺目標。這些失敗案例凸顯了單一輸出模仿的局限性，也說明了為何論文強調需要多訊號、多狀態的驗證機制。

**Q15：論文提出的未來研究方向是什麼？**
A：論文提出了四個以驗證為中心的未來研究方向。第一，「多訊號驗證」主張結合互補的正確性證據，例如將視覺相似度、執行結果、結構正確性與語義一致性等多重指標整合，形成更全面的評估體系。第二，「多狀態驗證」強調測試模型在執行軌跡中的行為，而不僅僅是單一輸出，這對於互動式介面、動畫與代理式任務尤為重要。第三，「跨任務遷移測試」旨在探測模型在不同視覺-程式碼任務之間的可重複使用技能，例如從 GUI 生成遷移到 SVG 生成，或從圖表生成遷移到 CAD 生成。第四，「可驗證代理軌跡」則關注代理的動作是否真正基於視覺證據，以避免代理在多步驟任務中產生幻覺或偏離目標。這四個方向共同指向從「單一輸出模仿」邁向「證據基礎的可執行系統」的願景。

## 實務應用指南

# 多模態程式碼智慧實務應用指南

## 適用場景

### 1. 設計稿轉前端程式碼自動化（UI-to-Code）
設計師交付 Figma 或 Sketch 設計稿後，團隊可使用視覺基礎的多模態程式碼模型（如基於 GPT-4V、Qwen-VL 的系統）自動生成對應的 HTML/CSS/React 元件程式碼。特別適用於行銷活動頁、產品介紹頁等視覺密集但邏輯簡單的場景，可將設計到開發的轉換時間從數小時縮短至數分鐘。

### 2. 資料視覺化儀表板快速建構（Chart-to-Code 與 Code-to-Chart）
資料分析師可上傳既有圖表截圖或資料表，要求模型生成對應的 Python（Matplotlib、Plotly）或 JavaScript（D3.js、Chart.js）程式碼；反之，也能將資料處理程式碼轉為視覺化圖片，用於報告或簡報初稿。適合 BI 團隊、資料新聞從業者快速產出原型。

### 3. SVG 與圖示資產批次生成（SVG Generation）
產品團隊需要大量風格統一的圖示、插圖或行銷素材時，可透過文字描述或參考圖片生成 SVG 向量圖。SVG 具備可縮放、可程式化編輯的特性，後續可由設計師微調或整合進設計系統。

### 4. 學術簡報與結構化文件輔助生成（Academic Presentations）
研究生、學者可將論文內容或研究資料輸入模型，自動生成符合學術排版規範的 Beamer/LaTeX 簡報，或將既有簡報截圖轉為可編輯的程式碼，便於版本管理與內容更新。

### 5. 機器人策略的視覺基礎控制（Embodied Control）
機器人研發團隊可利用視覺-語言-動作模型（VLA，如 OpenVLA）將示範影片或遙操作資料轉換為可執行的機器人控制策略，應用於倉儲自動化、家庭服務機器人等場景。

## 實作前置條件

### 資料準備
- **視覺-程式碼配對資料集**：需蒐集或採購如 Design2Code、ChartQA、PlotQA、SVG-Stack 等領域資料集；自建資料時應包含「輸入視覺工件 + 對應程式碼 + 執行/渲染結果」三元組。
- **領域標註**：針對 GUI、圖表、SVG 等不同子領域，需準備相應的標註規範（如 UI 元件層級、圖表資料點、SVG 元素屬性）。
- **評測基準**：建立包含視覺保真度、結構準確率、執行匹配率的多維度評測集。

### 計算資源
- **訓練階段**：完整微調 7B 參數的多模態模型需至少 4×A100（80GB）等級 GPU；若採用 LoRA/QLoRA 等參數高效微調方法，可降至單卡 A100 或 H100。
- **推論階段**：單次推論建議配備 24GB 以上顯存；若部署為 API 服務，建議使用 vLLM、TGI 等高效推論框架。
- **執行環境**：需預先部署瀏覽器自動化工具（Playwright、Selenium）用於渲染驗證，以及 Python/Node.js 沙箱用於程式碼執行驗證。

### 技能門檻
- **必備**：Python 程式設計、深度學習基礎（Transformer、視覺語言模型）、提示工程（Prompt Engineering）。
- **加分**：熟悉 React/Vue 等前端框架、LaTeX 排版、SVG 規範、機器人作業系統（ROS）。
- **團隊組成建議**：至少包含 1 名 ML 工程師、1 名領域專家（如前端工程師、設計師）、1 名負責評測與品質管控的人員。

## 實作步驟建議

### 步驟一：釐清任務定位與程式碼角色
依據論文中提出的五種程式碼角色分類——**渲染工件、可編輯符號結構、科學表示、中間推理軌跡、可執行策略**——明確目標任務屬於哪一類。例如「設計稿轉 React 元件」屬於渲染工件；「影片轉機器人動作」屬於可執行策略。不同角色對應不同的驗證標準與評測指標。

### 步驟二：選擇合適的基礎模型
- **通用場景**：Qwen2-VL、InternVL2、LLaVA-OneVision 等開源多模態模型，支援圖文理解與程式碼生成。
- **程式碼專精**：DeepSeek-Coder-VL、CodeLlama 變體等針對程式碼任務微調的模型。
- **前沿代理框架**：考慮採用 GPT-4o、Claude 3.5 Sonnet 等閉源模型作為基準，或採用開源代理框架（如 OpenVLA、ScreenAgent）進行客製化。

### 步驟三：建構領域資料管線
建立「視覺輸入 → 程式碼輸出 → 執行/渲染 → 評測回饋」的閉環資料管線。關鍵在於自動化執行與渲染驗證：對 GUI 任務使用 Playwright 截圖比對；對圖表任務執行 Python 程式碼並比對輸出圖片；對 SVG 任務使用 resvg 或瀏覽器渲染後比對像素差異。

### 步驟四：採用多訊號驗證策略
呼應論文提出的「Multi-Signal Validation」方向，結合以下互補證據：
1. **視覺相似度**：CLIP score、SSIM、像素級比對。
2. **結構正確性**：DOM 樹比對、SVG 元素層級匹配、圖表資料點對應。
3. **執行結果**：程式碼執行後的輸出是否符合預期（如資料值、互動行為）。
4. **領域約束**：透過規則引擎或專家模型檢查是否符合領域規範（如無障礙標準、學術格式）。

### 步驟五：實作多狀態驗證機制
針對互動式 GUI、動畫、機器人控制等任務，需測試程式碼在多個執行狀態下的正確性：
- **GUI 任務**：測試不同解析度、不同使用者操作（點擊、滾動、表單提交）下的渲染結果。
- **機器人任務**：在模擬器中執行多回合軌跡，檢查策略是否穩健。
- **動畫/影片任務**：檢查關鍵幀與時間軸的一致性。

### 步驟六：建立跨任務遷移評測
設計實驗評估模型在「學會一個視覺-程式碼任務後」能否遷移至相關任務。例如：訓練於網頁 UI 生成後，模型能否快速適應行動應用 UI 生成？這有助於識別模型的真實泛化能力，而非僅在單一任務上的過擬合。

### 步驟七：部署代理式系統並記錄可驗證軌跡
若任務涉及多步驟（如「給定設計稿與需求文件，自動部署網站」），需採用代理框架並記錄完整軌跡。每一步代理動作都應附帶視覺證據（如截圖、渲染結果），便於事後審計與除錯。

## 潛在風險與注意事項

### 風險一：幻覺與視覺錯位
**問題**：模型可能生成語法正確但視覺效果不符的程式碼，例如遺漏關鍵 UI 元件、錯誤的顏色配置、版面跑版。
**緩解**：
- 採用多輪迭代精煉（Iterative Refinement），將渲染結果回傳給模型進行自我修正。
- 結合視覺-語言對齊損失進行微調，而非僅依賴文字監督訊號。
- 設定像素差異、結構缺失的閾值，超過時自動觸發人工審核。

### 風險二：評測指標偏誤
**問題**：單一指標（如 BLEU、像素準確率）無法全面反映程式碼品質；視覺相似度高不代表功能正確，反之亦然。
**緩解**：
- 建立多維度評測體系，結合視覺、結構、執行、使用者體驗四類指標。
- 引入人類評估作為黃金標準，特別針對美觀度、易用性等難以自動量化的面向。
- 警惕「過度優化單一指標」導致的評測遊戲化（Goodhart's Law）。

### 風險三：領域知識缺失
**問題**：通用多模態模型對特定領域規範（如無障礙標準 WCAG、學術簡報格式、CAD 工程約束）理解不足。
**緩解**：
- 在提示中明確注入領域規範，或透過 RAG（Retrieval-Augmented Generation）引入領域知識庫。
- 對關鍵領域任務進行領域特定微調，而非僅依賴零樣本或少樣本提示。

### 風險四：執行安全性
**問題**：模型生成的程式碼若未經沙箱隔離直接執行，可能造成系統損壞、資料外洩或資安風險。
**緩解**：
- 所有程式碼執行必須在隔離沙箱（Docker、Firecracker）中進行。
- 限制網路存取、檔案系統權限、執行時間。
- 對 GUI 任務使用無頭瀏覽器並限制可訪問的 URL。

### 風險五：代理軌跡的可信度
**問題**：代理式系統可能產生「看起來合理但實際未基於視覺證據」的動作軌跡，難以審計。
**緩解**：
- 要求每個代理動作附帶視覺證據（如截圖、區域標註）。
- 採用可驗證獎勵機制（如 RLHF with visual feedback）訓練代理。
- 保留完整日誌，便於事後回溯與除錯。

### 風險六：資料偏誤與版權
**問題**：訓練資料可能包含受版權保護的設計稿、程式碼，導致生成結果涉及抄襲或法律爭議。
**緩解**：
- 使用授權或合成的訓練資料。
- 對生成結果進行版權相似度檢測。
- 在產品中明確標示 AI 生成內容。

## 與其他技術的整合建議

### 與傳統 NL2Code 系統整合
多模態程式碼智慧並非取代 NL2Code，而是其擴展。建議將視覺模型作為「前端感知器」，將提取的結構化資訊（如 UI 元素清單、圖表資料）傳遞給既有的 NL2Code 系統（如程式碼補全、倉庫級理解工具），形成「視覺感知 → 結構化表徵 → 程式碼生成」的串接架構。

### 與設計工具整合
透過 Figma Plugin API、Sketch API 等將多模態模型嵌入設計工具鏈，實現「設計即程式碼」的工作流。設計師可在 Figma 中選取元件，一鍵生成對應的 React/Vue 元件，並透過 Git 進行版本管理。

### 與 CI/CD 流程整合
將視覺迴歸測試（Visual Regression Testing）整合進 CI/CD 流程：每次程式碼變更後，自動執行多模態模型生成的視覺工件，並與基準版本比對，及早發現視覺退化問題。

### 與機器學習運維（MLOps）平台整合
使用 Weights & Biases、MLflow 等工具追蹤模型訓練、評測結果；採用 Kubernetes 部署推論服務；透過 Prometheus + Grafana 監控延遲、吞吐量、錯誤率等指標。

### 與代理框架整合
對於複雜的多步驟任務（如「根據設計稿與需求文件自動部署網站」），可將多模態模型整合進 LangChain、AutoGen、CrewAI 等代理框架，作為視覺感知與程式碼生成的工具節點。

### 與知識庫整合
透過 RAG 架構將領域知識庫（如設計系統文件、API 文件、領域規範）注入模型，提升生成結果的合規性與一致性。特別適用於企業內部場景，可確保生成程式碼符合組織的程式碼風格與架構規範。

## 給不同背景讀者的閱讀建議

### 給初學者
建議從論文的第 2 章「Task Formulation」開始閱讀，理解多模態程式碼智慧的基本問題定義與五種程式碼角色分類。接著閱讀第 3 章「Graphical User Interface」中的網頁應用程式部分，因為這是最直觀、最容易上手的子領域。實作上可從呼叫現成的多模態 API（如 GPT-4o）開始，嘗試將簡單的設計稿轉為 HTML，逐步建立對模型能力與限制的直觀理解。

### 給 AI 工程師
重點關注第 2.3 節「Code-Centric Reasoning and Acting」與第 6 章「Frontier Tasks and Frameworks」，這些章節涉及最新的代理式架構與統一模型設計。實作上建議從論文中提到的開源基準（如 Design2Code、ChartQA）出發，使用 Qwen2-VL 或 InternVL2 等開源模型進行微調實驗，並建立包含視覺、結構、執行三類指標的評測管線。特別注意論文強調的「多訊號驗證」與「多狀態驗證」理念，這是區分玩具 demo 與生產級系統的關鍵。

### 給研究者
論文的第 7 章「Future Directions」提出了四個驗證中心的研究方向，是當前領域的核心開放問題。建議從「Verifiable Agent Traces」切入，因為這是連接多模態感知、程式碼生成、代理決策的交叉點，最具研究深度與影響力。實作上可考慮設計新的基準測試，專門評估代理在視覺基礎任務中的決策可解釋性。此外，論文中反覆強調的「evidence-grounded」理念值得深入探索，如何讓模型不僅生成正確結果，還能展示其推理依據，是邁向可信 AI 的重要一步。

### 給產品經理
重點閱讀摘要、第 1 章「Introduction」與第 7 章「Future Directions」，掌握領域的整體圖景與發展趨勢。實作上建議從「設計稿轉前端程式碼」或「資料視覺化儀表板建構」這兩個 ROI 最明確的場景切入，因為它們能直接量化節省的工時與提升的效率。在評估供應商或自建團隊時，應特別關注其評測方法是否涵蓋視覺、結構、執行、使用者體驗多個維度，而非僅展示單一指標。論文中強調的「從單一輸出模仿邁向證據基礎的可執行系統」是判斷技術成熟度的關鍵指標——能展示推理過程與視覺證據的系統，遠比僅能產出漂亮 demo 的系統更具長期價值。
