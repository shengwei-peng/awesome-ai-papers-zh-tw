# UI2App：可執行網頁應用程式生成中視覺互動推論的基準測試

## ⚡ TL;DR

現有圖像到網頁生成基準多聚焦視覺逼真度，忽略從截圖推論互動行為的能力。
本文提出UI2App基準，以45組狀態一致截圖集與IIS指標評估視覺互動推論能力。
六大前沿視覺語言模型評測顯示，視覺逼真度領先者IIS僅排第四，跨頁面狀態成普遍瓶頸。

## 摘要翻譯

大型語言模型（Large Language Models, LLMs）在網頁生成方面已展現出日益提升的能力。然而，現有的文字驅動典範（Text-Driven Paradigms）仰賴複雜的提示（Prompts），對使用者提出相當高的要求，且在頁面佈局（Page Layout）與跨頁面視覺一致性（Cross-Page Visual Coherence）方面的表現力有限。以 UI 截圖作為輸入的圖像驅動典範（Image-Driven Paradigms）則更貼近實際的開發流程。然而，現有的基準測試主要聚焦於視覺逼真度（Visual Fidelity），缺乏對生成成品中互動推論（Interaction Inference）能力的系統性評估。為填補此缺口，我們提出 UI2App，這是首個針對視覺互動推論（Visual Interaction Inference）——即僅憑截圖、在無任何文字或行為引導下還原應用程式行為的能力——所設計的基準測試。UI2App 包含 327 張截圖，分為 45 個狀態一致截圖集（State-Coherent Screenshot Sets），對應可執行的多路由網頁應用程式（Multi-Route Web Applications）。我們設計了一個端到端流程（End-to-End Pipeline），從四個維度評估每個生成成品：可執行性（Executability, EXEC）、導航可達性（Navigation Reachability Score, NRS）、視覺逼真度（Visual Fidelity）與互動推論（Interaction Inference）。互動推論分數（Interaction Inference Score, IIS）依據功能正確性（Functional Correctness）與狀態管理複雜度（State-Management Complexity）來評估推論出的互動，採計任何有效的實作，而非僅比對單一參考實作（Reference Implementation）。針對六個前沿視覺語言模型（Vision-Language Models, VLMs）的實驗顯示，視覺重建與互動實現之間存在顯著的能力不匹配（Capability Mismatch）：視覺逼真度領先的模型在 IIS 上僅獲得 7.5 分，排名第四，落後 IIS 領先者達 5.2 倍。諸如跨頁面狀態（Cross-Page State）等高複雜度互動仍然是普遍的瓶頸，有一半的受評模型在該項目上恰好得到零分。整體而言，結果顯示從靜態截圖推論出完整的互動行為，對模型而言仍是一項重大挑戰。

### 核心貢獻（3～5點）
- 提出 UI2App，首個專注於視覺互動推論（Visual Interaction Inference）的可執行網頁應用程式生成基準測試，僅以 UI 截圖為輸入，無需任何文字或行為引導。
- 建構包含 327 張截圖、45 個狀態一致截圖集（State-Coherent Screenshot Sets）的資料集，涵蓋可執行的多路由網頁應用程式（Multi-Route Web Applications）。
- 設計端到端評估流程（End-to-End Pipeline），從可執行性（Executability）、導航可達性（Navigation Reachability Score, NRS）、視覺逼真度（Visual Fidelity）與互動推論（Interaction Inference Score, IIS）四個維度進行系統性評估。
- 提出互動推論分數（IIS），依據功能正確性（Functional Correctness）與狀態管理複雜度（State-Management Complexity）評估互動行為，並採計任何有效實作而非單一參考實作。
- 揭示前沿視覺語言模型（Vision-Language Models, VLMs）在視覺重建與互動實現間存在顯著能力不匹配（Capability Mismatch），特別是跨頁面狀態（Cross-Page State）等高複雜度互動仍為主要瓶頸。

### 適合對象
適合對生成式 AI、網頁應用程式自動生成、視覺語言模型評估有興趣的研究人員與工程師，特別是關注 UI/UX 設計稿轉換為可執行原型、互動行為推論與基準測試建構的讀者。

## 深度分析

#### 方法論解析

##### 任務定位：從「規格遵循」到「互動推論」
UI2App 的核心貢獻在於重新定義了 image-to-webpage generation（圖像到網頁生成）的評估對象。過去主流典範將 UI 截圖視為靜態視覺目標，模型只需輸出與參考畫面相似的 HTML/CSS 即可；UI2App 則要求模型在僅有 static UI screenshots（靜態 UI 截圖）、無任何文字說明、行為規格或操作示範的前提下，生成 runnable multi-route web applications（可執行的多路由網頁應用程式）。這意味著模型必須進行 interaction inference（互動推論）：從離散的視覺證據還原出觸發條件、狀態轉移與跨頁面資料同步等動態行為，而非單純執行已命名的規格（specification-following）。

##### 資料集設計：狀態一致截圖集
UI2App 包含 327 張截圖，組成 45 組 state-coherent screenshot sets（狀態一致截圖集）。與過去常見的「單張獨立頁面截圖」不同，每一組截圖都對應同一個應用程式的多個路由（multi-route），並且在不同畫面之間維持一致的 cross-page state（跨頁面狀態）。例如購物車應用程式可能同時提供商品列表頁、尺寸選擇後的狀態、以及購物車頁面，這些截圖共同構成「加入購物車後狀態會跨頁面傳遞」的視覺證據。這種設計強迫模型同時處理結構、視覺風格與隱含行為，而不是逐頁獨立翻譯。

##### 四維度端到端評估流程
論文提出一條 end-to-end pipeline（端到端流程），從模型輸出的程式碼開始，依序檢驗四個層次：

1. **Executability（EXEC，可執行性）**：測量生成成品能否成功建置與渲染。論文使用 EXEC@1 與 EXEC@3，分別代表單次生成與三次嘗試內可執行的比例。這是後續所有評估的前提。
2. **Navigation Reachability Score（NRS，導航可達性分數）**：檢驗預期路由是否能被實際訪問，確保應用程式至少具備基本的頁面切換能力。
3. **Visual Fidelity Score（VFS，視覺逼真度分數）**：衡量渲染後畫面與參考截圖的相似程度，承接既有 screenshot-to-code 基準的評估傳統。
4. **Interaction Inference Score（IIS，互動推論分數）**：本論文提出的核心指標，評估模型從截圖推導出的互動行為是否正確實現。

##### IIS 的評估哲學：分類學與規準導向
IIS 的設計難度在於 static screenshots（靜態截圖）對行為是 underdetermined（欠決定的）：同一個視覺狀態可能對應多種正確實作。例如搜尋框可能透過 Enter、按鈕點擊或即時輸入來觸發。為此，論文將網頁常見互動組織成七大類別的 interaction taxonomy（互動分類學），並針對每個類別設計 rubric-based protocol（規準導向評估協定）。

每個互動沿三個互補軸進行檢查：
- **Trigger（觸發條件）**：使用者操作是否被正確綁定，例如點擊、輸入、切換。
- **State transition（狀態轉移）**：內部狀態是否按照視覺證據發生預期變化。
- **Resulting interface behavior（結果介面行為）**：狀態改變後，畫面是否呈現對應的視覺回饋。

這種設計的關鍵優勢在於「credit any valid implementation（認可任何有效實作）」，不強迫模型匹配單一參考執行軌跡，而是檢驗功能正確性（functional correctness）與狀態管理複雜度（state-management complexity）。這讓 IIS 能區分出「視覺正確但互動無反應的 frozen façade（凍結外觀）」與「真正具備動態行為的應用程式」。

#### 實驗數據解讀

##### 整體發現：視覺逼真度不等於互動推論能力
論文評估了六個 frontier VLMs（前沿視覺語言模型），並額外提供 Qwen2.5-VL 的 scaling ladder（規模遞增實驗）。最引人注目的結果是 visual fidelity（視覺逼真度）與 interaction inference（互動推論）之間的 capability mismatch（能力不匹配）：

- **IIS 領先模型**的整體 IIS 僅達 **39.3**，顯示即使是最強模型，從靜態截圖推論完整互動行為仍是重大挑戰。
- **VFS 領先模型**在視覺逼真度上表現最佳，但 IIS 僅有 **7.5**，排名第四，落後 IIS 領先者達 **5.2 倍**。
- 文中圖 1 的對比極具象徵意義：Claude Sonnet 4.6 能重建具備購物車計數與跨路由狀態傳播的動態應用程式；Gemini 3.1 Pro Preview 雖然視覺更逼真，卻產生每個互動都是 no-op（無操作）的 frozen façade（凍結外觀）。

這說明目前 VLMs 在「看起來像什麼」與「實際如何運作」之間存在結構性落差。視覺重建主要依賴空間佈局與樣式辨識，而互動推論則需要理解隱含狀態機、事件語義與跨頁面資料流，兩者對模型的要求並不相同。

##### 跨頁面狀態：最普遍的瓶頸
在 IIS 分類學中，**S3-scope interactions（跨路由持久化互動，即 cross-page state）** 是最困難的維度。實驗顯示：
- 六個模型中有三個在此維度得分**恰好為零**。
- 即使表現最好的模型，cross-page state（跨頁面狀態）分數也僅達 **21.6 / 100**。

這凸顯 state management（狀態管理）與 data synchronisation（資料同步）是當前 VLMs 的普遍弱點。模型可能能正確渲染個別頁面，但無法推論出「購物車內容需要在不同路由間共享」這類需要全局狀態設計的邏輯。這也呼應了引言中的論點：cross-page interactions（跨頁面互動）難以用文字精確描述，而僅憑截圖推論則更加困難。

##### 可執行性與導航：基礎門檻已可跨越，但不足以保證可用性
雖然論文未在提供的摘要與引言片段中詳列 EXEC 與 NRS 的完整數值，但從「多個模型能產生 runnable applications（可執行應用程式）」與「VFS 領先模型具備基本導航」等描述可以推斷：現代 VLMs 在 build & render（建置與渲染）以及 route reachability（路由可達性）上已有一定水準。然而，這些基礎能力並不保證應用程式真正可用——一個能切換頁面但所有按鈕無反應的成品，對終端使用者而言仍是失敗的。

#### 與現有研究的比較

##### 相對於靜態視覺轉程式碼基準
既有研究如 Pix2Code、WebSight、Design2Code 等，主要將 screenshot-to-code（截圖轉程式碼）視為靜態渲染問題，評估重點幾乎全放在 visual fidelity（視覺逼真度）。UI2App 繼承了以截圖為輸入的傳統，但將輸出目標從「視覺複製品」提升為「可執行應用程式」，並引入 IIS 來測量 runtime behavior（執行期行為）。這是從「像不像」到「能不能用」的典範轉移。

##### 相對於文字驅動的端到端開發
近期研究如 SWE-bench、OpenHands、Devin 等展示模型能根據自然語言指令進行軟體開發，但這屬於 specification-following（規格遵循）：互動行為已經在 prompt（提示）中被命名或描述。UI2App 則完全移除文字規格，要求模型僅從視覺證據進行 interaction inference（互動推論）。這更接近真實設計師工作流程——將 mockups（設計稿）轉為 functional prototypes（功能性原型）——同時也對模型的隱含推理能力提出更高要求。

##### 主要改進與創新
- **狀態一致的多路由資料集**：45 組 state-coherent screenshot sets 提供跨頁面視覺證據，使 cross-page state 的評估成為可能。
- **參考軌跡無關的 IIS**：透過分類學與規準，避免強迫模型匹配單一正確執行路徑，更能反映真實開發中「多種實作皆可正確」的彈性。
- **四維度綜合評估**：同時測量 executability（可執行性）、navigation reachability（導航可達性）、visual fidelity（視覺逼真度）與 interaction inference（互動推論），避免單一指標造成的偏頗。

##### 限制與待釐清之處
- **輸入模態單一**：僅使用 static screenshots（靜態截圖），未納入 accessibility trees（無障礙樹）、設計稿圖層、互動規格或操作影片。雖然這是研究問題的刻意設定，但也限制了對現實開發場景的覆蓋。
- **行為欠決定**：IIS 的規準雖然緩解了單一正解問題，但 rubric 設計本身仍需人工定義，可能帶來主觀性與類別覆蓋不全的風險。
- **規模與領域**：327 張截圖、45 組應用程式在網頁應用領域仍屬中小型，且未涵蓋原生行動應用或桌面軟體。
- **模型細節有限**：摘要與引言未說明六個 frontier models（前沿模型）的確切名單、 prompting 策略、取樣溫度與重試機制，這些都會影響結果的絕對數值與可比性。

#### 可重現性評估

##### 資料集與程式碼釋出狀況
根據提供的文本，論文宣稱將釋出 UI2App 資料集，包含 327 張截圖與 45 組 state-coherent screenshot sets。然而，從摘要與引言片段中無法確認是否已提供公開的下載連結、授權條款、資料格式說明，或完整的 evaluation harness（評估框架）。作為 preprint（預印本），實際可重現性仍取決於作者後續是否公開：

- 原始截圖與對應的 metadata（應用程式類別、路由結構、預期互動）。
- 自動化建置與渲染腳本（EXEC 評估所需）。
- IIS 的 rubric 實作與評分程式，包括 trigger、state transition、resulting interface behavior 的具體檢查邏輯。
- 用於產生結果的 prompt（提示）與模型 API 設定。

##### 模型權重與推論環境
論文評估的對象為 frontier VLMs（前沿視覺語言模型），這些模型通常僅透過 API 提供服務（如 Claude Sonnet 4.6、Gemini 3.1 Pro Preview），並不公開 model weights（模型權重）。這意味著其他研究者難以在完全相同的內部模型版本上重現數值，只能依賴 API 快照。此外，API 行為可能隨時間更新，進一步影響長期可重現性。

##### 評估主觀性與自動化挑戰
IIS 的部分檢查（例如判斷互動是否「功能正確」）可能需要人工或 LLM-as-a-judge（以大型語言模型作為評審）來完成。若評分流程未完全自動化或未公開評審 prompt，則不同團隊重現時可能產生差異。建議作者提供：
- 明確的 binary/pass-fail 檢查條件。
- 自動化測試腳本（例如使用 Playwright 或 Selenium 模擬使用者操作）。
- 人工標註的一致性統計（inter-annotator agreement）。

##### 整體可重現性判斷
目前可重現性處於「概念清楚、細節待確認」的階段。方法論描述足夠詳細，讓其他研究者能理解並可能重新實作；但若缺乏開源資料與評估框架，則難以完全複製論文報告的數值。建議後續版本補充 GitHub 儲存庫連結、資料集 DOI、以及完整的實驗設定紀錄。

#### 未來研究方向

##### 1. 引入多模態行為線索
未來可放寬「僅限靜態截圖」的設定，探索結合 screen recordings（螢幕錄影）、accessibility trees（無障礙樹）、Figma/Sketch 圖層、或設計系統規格後，互動推論能力能提升多少。這將有助於區分「純視覺推論」與「視覺加結構化線索推論」的價值。

##### 2. 發展專門的 UI 狀態世界模型
Cross-page state（跨頁面狀態）是當前最大瓶頸，未來研究可針對應用程式狀態機進行顯式建模，例如訓練模型預測 state schema（狀態綱要）、state transition graph（狀態轉移圖）與 data flow（資料流），再將其轉譯為程式碼。這類 neuro-symbolic（神經符號式）方法可能比端到端生成更穩健。

##### 3. 自動化除錯與互動驗證迴圈
現有流程是一次性生成後評估。未來可結合 self-debugging agents（自我除錯代理），讓模型在執行失敗或 IIS 評分低落時，根據 runtime error（執行期錯誤）與互動測試回饋迭代修正程式碼。這需要一個能自動執行互動測試並回傳結構化回饋的 evaluation harness。

##### 4. 擴展至行動與桌面應用
UI2App 目前聚焦網頁應用。未來可將相同框架延伸至 native mobile apps（原生行動應用）、desktop applications（桌面應用程式）或跨平台框架（如 React Native、Flutter），並建立對應的 state-coherent screenshot sets 與互動分類學。

##### 5. 無參考實作的功能正確性評估
IIS 目前仍依賴人工設計的 rubric。未來可探索 reference-free functional testing（無參考功能測試），例如透過 property-based testing（基於性質的測試）或使用者模擬，自動檢驗應用程式是否滿足從截圖推導出的不變條件（invariants），從降低對人工規準的依賴。

##### 6. 互動推論的預訓練與課程學習
實驗顯示視覺重建與互動實作能力脫鉤，暗示現有預訓練資料可能缺乏足夠的 app execution traces（應用程式執行軌跡）。未來可建構大規模「截圖—程式碼—執行軌跡」三元組資料，並採用 curriculum learning（課程學習），從單一元件互動逐步過渡到跨頁面狀態管理，以提升模型的 interaction inference 能力。

##### 7. 人機協同的設計稿轉原型工具
短期內最務實的應用是將 UI2App 的評估框架轉化為互動式開發輔助工具：設計師上傳 mockups，模型生成 functional prototype（功能性原型），並透過 IIS 指標即時標示哪些互動可能未正確實現，再由人類進行修正。這種 human-in-the-loop（人機協作）模式可能比全自動生成更快落地。

## 論文問答

**Q1：UI2App 主要想解決什麼問題？為什麼現有的文字驅動典範被認為不足？**

A：UI2App 針對的是「僅憑靜態 UI 截圖生成可執行網頁應用程式」時，如何評估模型推論互動行為能力的問題。現有文字驅動典範通常需要使用者提供精心設計或極為詳細的自然語言提示，這對使用者造成很大負擔，而且文字難以精確描述頁面佈局、跨頁面視覺一致性，以及跨頁面狀態管理等複雜功能需求。因此，論文認為以截圖為輸入的圖像驅動典範更貼近實際設計流程，但現有基準多聚焦於視覺逼真度，忽略了生成成品是否真的能運作。

**Q2：現有的圖像到網頁生成基準為何無法充分評估生成結果？**

A：現有基準大多把 UI 生成視為靜態渲染問題，只比對生成畫面與參考截圖的視覺相似度，卻不檢驗按鈕、表單、狀態轉換等互動行為是否正確實現。這導致模型可能產生一個「凍結外觀」：看起來與設計稿幾乎一樣，但所有互動都是無操作，無法作為真正的應用程式使用。UI2App 因此重新框定任務，要求模型從靜態截圖推論出底層行為，並在執行時驗證這些推論是否正確。

**Q3：為什麼「互動推論」能力很重要，又特別困難？**

A：互動推論是指模型在沒有任何文字說明或行為示範的情況下，僅從截圖還原應用程式應有的動態行為，這與單純照規格實作截然不同。靜態截圖對行為的資訊是欠決定的，同一個視覺狀態可能對應多種合理的實作方式，例如搜尋框可能透過按下 Enter、點擊按鈕或即時查詢來觸發。因此，評估互動推論不僅要確認功能正確性，還必須容許多種有效實作，這使得設計評估指標變得極具挑戰性。

**Q4：UI2App 的任務設定與資料集組成是什麼？**

A：UI2App 提供 327 張截圖，組成 45 個狀態一致截圖集，每個集合對應一個可執行的多路由網頁應用程式。這些截圖不是孤立的頁面圖片，而是涵蓋多個路由並呈現一致跨頁面狀態的視覺證據，讓模型能夠推論頁面間的狀態傳遞。模型在沒有標題、指令或互動描述的情況下，必須同時重建結構、視覺風格與推論行為，產出一個可執行的多頁面成品。

**Q5：UI2App 的端到端評估流程包含哪四個維度？各自評估什麼？**

A：評估流程包含可執行性、導航可達性、視覺逼真度與互動推論分數四個維度。可執行性檢查應用程式是否能成功建置與渲染；導航可達性確認預期頁面路由是否可以到達；視覺逼真度衡量生成畫面與參考截圖的相似程度；互動推論分數則是核心指標，評估模型從截圖推論出的互動行為是否在功能上正確，並考量狀態管理複雜度。

**Q6：IIS 如何處理「同一視覺狀態可能有多種正確實作」的問題？**

A：IIS 採用基於分類學的評估方式，將網頁常見互動分為七大類別，並針對每個類別設計評分標準，檢查觸發條件、狀態轉換與結果介面行為是否正確實現。這種設計不強求模型產出唯一的參考執行軌跡，而是認任何符合功能語意的有效實作。如此一來，IIS 既能提供結構化的診斷訊號，也能避免過度懲罰合理的替代實作方式。

**Q7：實驗評估了哪些模型？整體表現如何？**

A：論文評估了六個前沿視覺語言模型，並額外進行 Qwen2.5-VL 的縮放實驗。結果顯示，即使是最強的模型，整體 IIS 也僅達 39.3，顯示從靜態截圖推論完整互動行為仍是重大挑戰。相較於視覺逼真度已有顯著進展，互動推論能力明顯落後，顯示兩者是獨立且需要分別評量的能力。

**Q8：視覺逼真度與互動推論之間出現了什麼樣的能力不匹配？能否舉例說明？**

A：實驗發現視覺逼真度領先的模型在 IIS 上僅得 7.5，排名第四，落後 IIS 領先者約 5.2 倍，顯示畫面漂亮不代表互動正確。圖一以同一組電商截圖為例：Claude Sonnet 4.6 重建出可動態更新購物車數量並跨路由傳播狀態的應用程式；而 Gemini 3.1 Pro Preview 雖然視覺逼真度更高，卻產生一個「凍結外觀」，所有互動都無法改變狀態。只有 IIS 能夠捕捉這種「看起來對但無法運作」的關鍵差異。

**Q9：哪一類互動是模型最大的瓶頸？具體數據為何？**

A：跨頁面狀態持久化是最大瓶頸，特別是 S3 範疇的跨路由狀態互動。在這個維度上，六個模型中有三個得分為零，即使表現最好的模型也僅達 21.6 分。這顯示目前前沿模型在理解與實現跨頁面狀態管理、資料同步等複雜行為方面仍有極大進步空間。

**Q10：UI2App 所評量的能力在哪些實務場景中有應用價值？**

A：這項能力最直接應用於設計師將設計稿或線框稿快速轉換為功能性原型的流程，能顯著縮短從視覺設計到可互動產品的距離。對於非技術使用者而言，他們也能直接從截圖獲得可操作的網頁應用程式，降低開發門檻。此外，在敏捷開發或使用者測試中，自動從視覺素材推論互動行為有助於快速驗證產品概念。

**Q11：若將這類技術產品化，需要特別注意哪些風險與考量？**

A：首要風險是「凍結外觀」問題：生成結果看起來正確，但互動無反應，可能誤導使用者以為產品已完成。因此產品必須搭配執行時測試與互動驗證機制，不能僅依賴視覺檢查。此外，由於截圖對行為資訊欠決定，產品應提供後續編輯或補充行為規格的功能，讓使用者能修正模型推論錯誤的互動邏輯。

**Q12：UI2App 對整個網頁生成領域可能帶來什麼影響？**

A：UI2App 將研究焦點從「視覺複製」轉向「可執行行為重建」，推動領域更重視生成應用程式的功能性而非僅是外觀。它提供第一個針對圖像輸入的互動推論基準，使不同模型能在統一標準下比較互動實現能力。長遠來看，這有助於催生真正能從設計稿產出可運作產品的模型，改變前端開發與原型設計的工作流程。

**Q13：論文承認 UI2App 有哪些限制？**

A：首先，靜態截圖本身無法完全決定互動行為，某些情況下即使人類也難以單憑截圖判斷正確行為。其次，目前資料集聚焦於網頁應用程式，尚未涵蓋行動應用程式或更複雜的桌面軟體互動模式。此外，評估雖然設計了分類學，但面對極度創意或高度客製化的互動，仍可能需要人工輔助判斷。

**Q14：模型在哪些典型失敗案例中表現最差？**

A：模型最容易在需要跨頁面狀態管理的場景中失敗，例如購物車內容在不同路由間保持同步、使用者登入狀態跨頁面持久化等。實驗中有一半模型在跨路由狀態維度得分為零，顯示它們無法從多張截圖推論出共享狀態。這類失敗往往伴隨著「行為上無反應的外殼」：介面元素存在，但點擊後不會更新全域狀態或觸發頁面間資料同步。

**Q15：未來研究可以朝哪些方向改進互動推論能力？**

A：未來可以引入更豐富的行為訊號，例如操作示範影片、互動熱點標註或部分狀態轉換說明，以補充靜態截圖的不足。另一方面，可針對狀態管理與跨路由資料同步設計專門的訓練目標或後處理驗證機制，提升模型在複雜互動上的穩健性。最終，結合視覺理解、程式合成與執行時回饋的迭代式生成流程，可能是實現從截圖到完整可執行應用程式的關鍵路徑。

## 實作前置條件

### 資料準備
- 一組**狀態一致截圖集**：同一應用程式在多個路由、不同互動狀態下的截圖，建議至少 2–5 張，能呈現跨頁面狀態變化。
- 截圖解析度與比例一致，避免浮水印、過度裁切或動態提示遮擋關鍵 UI 元素。

### 運算資源

- 評估階段建議使用無頭瀏覽器（Playwright / Puppeteer）與截圖比對工具。

### 技能需求
- 前端開發基礎（React/Vue、路由、狀態管理）。
- 能設計評估流程與自動化腳本。
- 熟悉提示工程，能將截圖轉換為結構化生成指令。
- 具備領域知識以定義互動推論的評分規則（rubric）。

## 實作步驟建議

### 步驟 1：定義任務範圍與互動分類
參考 UI2App 的互動分類法，先列出應用程式中會出現的互動類型（如導航、表單輸入、購物車狀態、跨頁面資料同步），並為每類設計評分 rubric。

### 步驟 2：收集狀態一致截圖集
針對目標應用程式，拍攝或匯出多個頁面在不同狀態下的截圖，確保同一狀態（例如「購物車有一件商品」）在多張截圖中視覺一致，提供模型足夠的互動推論線索。

### 步驟 3：設計生成提示
提示中僅提供截圖，不附加行為規格或說明文字，要求模型輸出可執行的多路由網頁應用程式原始碼。可額外要求：
- 使用單一狀態管理機制（如 Context、Pinia）。
- 保留截圖中的視覺風格與元件命名。
- 所有按鈕與連結必須有實際互動，而非空殼。

### 步驟 4：自動化建置與渲染
將模型輸出放入隔離環境執行 `npm install` 與 `npm run build`，記錄 EXEC@1 / EXEC@3（一次成功或三次內修復成功）。使用無頭瀏覽器開啟首頁並截圖，作為後續視覺比對基礎。

### 步驟 5：評估四個維度
1. **可執行性（EXEC）**：能否成功建置與渲染。
2. **導航可達性（NRS）**：預期路由是否能透過連結或按鈕到達。
3. **視覺逼真度（VFS）**：生成畫面與參考截圖的像素/結構相似度。
4. **互動推論分數（IIS）**：依 rubric 檢查觸發條件、狀態轉換與結果 UI 是否正確。

### 步驟 6：迭代優化
針對 IIS 低分的互動類別（特別是跨頁面狀態），將失敗案例整理成少樣本示例（few-shot）或加入中間推論提示（chain-of-thought），重新生成並評估。

### 步驟 7：整合進產品流程
將通過評估的生成程式碼匯入既有程式碼庫，或作為設計師與工程師協作的初稿，再由人工進行最終審查與上線。

## 潛在風險與注意事項

| 風險 | 說明 | 因應方式 |
|---|---|---|
| **凍結外觀（Frozen Façade）** | 生成畫面高度逼真，但按鈕無反應、狀態不更新。 | 不要只看 VFS，必須執行 IIS 互動測試，並設計觸發後的狀態檢查。 |
| **跨頁面狀態遺失** | 模型常在單頁互動表現尚可，但無法正確實現跨路由狀態持久化。 | 將跨頁面狀態截圖納入輸入，並在 rubric 中明確評分狀態同步。 |
| **行為過度推論** | 靜態截圖無法唯一決定互動邏輯，模型可能產生不符合預期的實作。 | 採用「任何有效實作都給分」的評分哲學，並由產品方最終確認業務邏輯。 |
| **建置失敗率高** | 模型可能輸出無法編譯的程式碼、錯誤依賴或過時 API。 | 使用 EXEC@3 機制，允許模型根據錯誤訊息自我修復；同時鎖定框架版本。 |
| **資料隱私與版權** | 上傳真實產品截圖可能洩漏機密設計或使用者資料。 | 使用去識別化、合成或公開範例截圖；企業內部優先採用本地模型。 |
| **過度依賴自動生成** | 生成程式碼可能難以維護、不符合團隊規範。 | 將輸出視為「高保真草稿」，仍需工程師重構與程式碼審查。 |

## 與其他技術的整合建議

- **設計工具（Figma / Sketch）**：透過外掛將設計稿匯出為狀態一致截圖集，直接餵入 UI2App 流程，銜接「設計 → 原型 → 程式碼」。
- **低程式碼 / 無程式碼平台**：將模型輸出轉為平台元件描述，再由平台渲染與部署，補強平台對複雜互動的推論能力。
- **自動化測試框架**：把 IIS 評估腳本整合進 CI/CD，作為視覺回歸測試的一環，特別檢測互動是否退化。
- **RAG 與設計系統知識庫**：將公司設計系統、元件庫文件作為檢索上下文，引導模型使用正確的 UI 元件與狀態管理模式。
- **多模態 Agent 工作流**：結合視覺語言模型與程式碼 Agent，讓模型先推論互動、再生成程式碼、再自我測試與修復，形成閉環。

## 給不同背景讀者的閱讀建議

**初學者**  
本論文最適合從圖 1 與「凍結外觀」概念開始理解：一個網頁看起來像真的不代表它能動。建議先掌握 EXEC、NRS、VFS、IIS 四個指標的意義，再回頭看實驗結果，就能明白為什麼「畫面漂亮」只是第一步。

**AI 工程師**  
重點關注 IIS 的 rubric 設計與評估流程：如何從靜態截圖產生可執行程式碼、如何用無頭瀏覽器驗證互動、以及如何處理「無唯一正解」的狀態轉換。這些細節直接決定你能否把論文方法落地成可上線的生成管線。

**研究人員**  
論文的核心貢獻在於將「互動推論」從「視覺重建」中獨立出來，並提供可量化的基準。建議深入分析跨頁面狀態（S3-scope）的瓶頸，以及為何視覺逼真度領先者反而在 IIS 落後，這裡蘊含未來模型架構與訓練資料的重要研究方向。

**產品經理**  
請把 UI2App 視為評估「截圖轉 App」產品能力的檢查清單：你的工具能否真正產生可運行的應用程式？跨頁面狀態是否正確？論文數據顯示目前 frontier 模型在 IIS 上仍有極大落差，產品定位應聚焦於「加速原型」而非「完全取代工程師」。
