## ⚡ TL;DR

現有研究缺乏衡量 LLM 自動化 harness 優化能力的共同標準。
本文提出 HarnessOpt-Bench，以可信執行環境與保留測試集進行端對端評估。
實驗顯示模型能力差異大於 harness，且仍有顯著進步空間。

## 摘要翻譯

隨著 LLM（大型語言模型）日益部署於 agentic systems（智慧體系統）中，其能力不僅取決於模型權重，也取決於 harness（環繞模型的提示、工具、控制流程、記憶與編排程式碼）。這使得 automated harness optimization（自動化 harness 優化）——由 AI system（人工智慧系統）透過迭代與評估引導來改進 harness——既是提升 AI system 的重要途徑，也是對 AI system 本身能力的一項嚴苛要求。然而，研究社群仍缺乏一套共同協定，以衡量 frontier LLM（前沿大型語言模型）在此任務上的表現。我們提出 HarnessOpt-Bench，一個在昂貴且隨機性評估（expensive and stochastic evaluation）下進行 end-to-end harness optimization（端對端 harness 優化）的基準。optimizer（優化器）是一個配備 coding harness（編碼 harness）的 LLM，它會接收 target agent（目標智慧體）的 seed harness（初始 harness）、graded evaluation feedback（分級評估回饋），以及固定的 target-evaluation budget（目標評估預算）。它編輯 harness 並提名 final candidate（最終候選方案），該方案會根據其在 held-out test partition（保留測試分區）上相對於 seed harness 的 normalized gain（標準化增益）來計分，而該分區在整個搜尋過程中均無法存取。trusted execution environment（可信執行環境）會強制執行 evaluation boundary（評估邊界）、計量 target-agent 的 resource use（資源使用量），並保留 candidate versions 以供 audit（稽核）。我們在 4 個 downstream tasks（下游任務）上，進行 111 次 scored runs（計分執行次數），評估 5 個 frontier LLMs 作為 optimizers 的表現，分別在 shared coding harness（共享編碼 harness）與其 native harnesses（原生 harness）下進行。實驗結果顯示，optimizer models（優化器模型）之間的差異大於其所透過的 coding harnesses，native harnesses 並未一致展現優勢，且 gains（增益）在不同任務與 seed regimes（初始設定）間存在顯著差異。這些結果確立了 harness optimization（harness 優化）是一項可衡量且具有區辨力的能力，仍有很大的改進空間。

### 核心貢獻（3～5點）
- 提出 HarnessOpt-Bench，首個針對 end-to-end harness optimization 的標準化基準，支援在昂貴且隨機性評估下進行可重現的能力測量。
- 設計包含 fixed target-evaluation budget、held-out test partition 與 trusted execution environment 的評估協定，確保優化過程公平、可稽核且避免資料洩漏。
- 在 4 個 downstream tasks 上對 5 個 frontier LLMs 進行 111 次 scored runs，系統性比較 shared coding harness 與 native harness 對優化表現的影響。
- 實證發現 optimizer model 的差異大於其所使用的 coding harness、native harness 並未一致優於 shared harness，且增益高度依賴任務與 seed regime。

### 適合對象
從事 LLM 智慧體系統、提示工程、自動化機器學習（AutoML）、以及 AI 自我改進與元優化研究的學者與工程師；特別適合需要評估或設計 harness 優化方法、建立基準測試協定，以及關注 frontier LLM 在真實端對端系統層級任務上能力的研究者與實務工作者。

## 深度分析

#### 方法論解析

HARNESSOPT-BENCH 的核心設計是把「harness 優化（harness optimization）」視為一個端對端（end-to-end）的決策問題：一個優化器（optimizer）——由大型語言模型（LLM）與其編碼 harness 組成——在固定目標評估預算（target-evaluation budget）內，反覆修改目標智慧體（target agent）的 seed harness，最後提名一個最終候選方案（final candidate），並以該候選方案在保留測試分區（held-out test partition）上相對於 seed 的標準化增益（normalized gain）作為最終分數。

整個流程可拆解為四個控制要件：

1. **固定目標與環境**：目標智慧體的模型權重、執行環境（execution environment）與驗證器（verifier）全程固定。這確保實驗結果比較的是優化器本身的能力，而非不同目標模型或不同評分器帶來的變異。

2. **分級資訊揭露（graded disclosure）**：優化器可以讀取開發集（dev）的逐案例開發追蹤記錄（development traces）與驗證集（val）的彙總驗證指標（aggregate validation metrics），但測試集（test）在搜尋期間完全不可見。這強迫優化器必須從不完整證據（incomplete evidence）中診斷故障，並避免直接擬合測試分數。

3. **可信執行邊界（trusted execution boundary）**：整個評估架構建立在可信評估沙盒（trusted evaluation sandbox）與模型 API 閘道（Model API Gateway）之上。優化器沙盒（optimizer sandbox）只能寫入目標智慧體的 harness 程式碼，無法修改評估資料、無法接觸保留資料（held-out data）、也無法取得模型提供者憑證（provider credentials）。閘道則負責強制模型允許清單（model allow-list）與各範圍預算（per-scope budget）。每個候選方案都在隔離沙盒（isolated sandbox）中以非特權方式執行，並且所有候選版本都會被保存以供稽核（audit）。

4. **預算與資源計量**：目標評估預算固定且昂貴，評估本身是隨機性評估（stochastic evaluation）。優化器必須在有限預算內區分真實改進（real improvement）與雜訊（noise），並決定何時部署（deployment）哪個候選方案。

在這個框架下，優化器的能力被拆解為三個研究問題（RQ）：
- **RQ1**：前沿大型語言模型（frontier LLM）在 harness 優化任務上是否能被區分？
- **RQ2**：它們在哪些環節仍然不足？
- **RQ3**：優化器自身的編碼 harness 對結果的貢獻，相對於模型權重本身有多大？

為了回答 RQ3，作者採用配對設計（paired design）：五個前沿優化器模型分別在共享編碼 harness（shared coding harness）與各自的原生 harness（native harness）下進行測試，從而分離「模型效應」與「harness 效應」。

#### 實驗數據解讀

論文報告了 111 次計分執行次數（scored run），涵蓋 4 個下游任務（downstream task）、5 個前沿優化器模型，並在共享編碼 harness 與原生 harness 兩種設定下進行。此外，還在一個任務上額外評估了兩個編碼 harness。

主要發現可歸納為四點：

1. **優化器模型（optimizer model）的差異大於 harness 差異**：在共享編碼 harness 下，不同模型之間的表現差距，平均而言大於同一模型使用共享 harness 與原生 harness 之間的差距。這表示在 harness 優化這類高階任務中，模型本身的推理能力（特別是從先驗證據推理與系統層級變更規劃）比外圍的編碼 harness 更為關鍵。

2. **原生 harness 並無一致優勢**：雖然直覺上每個模型搭配自己慣用的原生 harness 應該表現較好，但實驗顯示這並不成立。這暗示在 harness 優化場景中，「為一般對話或程式生成設計的 harness」未必優於「統一、受控的共享 harness」。對於基準測試與未來研究設計而言，這支持使用共享 harness 來公平比較模型。

3. **增益（gain）隨任務與 seed 設定（seed regime）高度變化**：不同下游任務的可改進空間差異很大，且同一任務在不同初始 harness（seed harness）起點下，優化器能取得的標準化增益也不相同。這凸顯 harness 優化不是單一數字能概括的能力，而必須在多重任務與多重 seed 下評估。

4. **干預廣度與診斷深度的不同影響**：在 OfficeQA 任務上，發行層級（release-level）實驗能區分連續版本模型之間的差異；而從工具化搜尋軌跡（instrumented search trajectories）觀察到，**更廣泛的干預（broader intervention）** 與更大的保留測試增益正相關，但**詳細的故障追蹤檢查（detailed failure-trace inspection）** 卻很少被使用，且與增益無正相關。這指出當前優化器傾向於做較大範圍的修改，卻未能有效利用逐案例追蹤來進行精細故障診斷（failure diagnosis）。換句話說，模型在「廣泛探索」上已有一定能力，但在「深度診斷」與「針對性修正」上仍有明顯缺口。

整體而言，實驗結果確立了 harness 優化是一個可測量且具有區辨力（discriminative）的能力維度，但同時也顯示現有前沿模型在這個維度上仍有很大的改進空間。

#### 與現有研究的比較

HARNESSOPT-BENCH 與先前研究的關係可從兩個軸向來定位：**優化空間的範圍**與**LLM 在搜尋中的角色**。

在優化空間範圍上：
- **DSPy** 與 **MetaContextEngineering** 主要優化提示（prompt）或上下文（context）工件，周圍程式固定。
- **TextGrad、Trace、LLM-AutoDiff** 將優化對象擴展到任意文字元件，透過文字層級的回饋進行反向傳播式調整。
- **STOP、ADAS、AFlow、DarwinGödel Machine、GödelAgent、SICA** 則進一步把整個智慧體程式或工作流程納入搜尋空間。

在 LLM 角色上：
- **OPRO、FunSearch、AlphaEvolve、Shinka Evolve、GEPA** 把 LLM 當作變異運算子（mutation operator），嵌入較大的演化程序（evolutionary procedure）中。
- **VERO、MetaHarness** 則讓編碼智慧體（coding agent）作為端對端優化器（end-to-end optimizer），直接讀取目標原始碼、檢視分數與執行追蹤，並決定下一步要收集哪些證據。

HARNESSOPT-BENCH 最接近 **VERO** 與 **MetaHarness** 的端對端 regime，但做出了幾項關鍵改進：

- **協議標準化**：過去方法各自使用不同的目標智慧體、seed harness、預算、揭露政策與計分協議，導致結果無法直接比較。HARNESSOPT-BENCH 把這些因素固定，讓「優化器模型」、「編碼 harness」、「目標智慧體」與「協議」四者分離。
- **保留測試分區**：許多現有方法在搜尋過程中可見驗證或測試分數，容易產生過擬合。HARNESSOPT-BENCH 把最終評估鎖在 held-out test partition 後面，確保分數反映泛化能力。
- **可信執行環境**：透過沙盒、閘道與版本控制，強制執行預算與資料隔離，並保留每個候選方案供稽核。這把「遵守規則」從優化器的指示（instruction）轉變為執行環境的屬性，降低提示工程或模型欺騙帶來的變異。
- **昂貴且隨機的評估**：不同於程式正確性可由測試套件（test suite）廉價檢驗，harness 優化必須執行隨機性智慧體多次才能估計效果。HARNESSOPT-BENCH 刻意選擇固定語料研究（fixed-corpus research）與終端使用（terminal use）這類昂貴評估任務，以測試模型在真實部署情境下的決策能力。

主要限制在於：目前僅涵蓋 4 個下游任務，任務多樣性仍有限；實驗聚焦於編碼智慧體作為優化器，雖然基準對其他設計開放，但實證覆蓋度不足；此外，native harness 的定義與實作細節若未完全公開，可能影響跨研究比較。

#### 可重現性評估

從目前可取得的摘要與引言來看，HARNESSOPT-BENCH 在可重現性（reproducibility）上採取了幾項正面措施：

- **固定 seed、固定資料切分**：開發集、驗證集與測試集（dev / val / test）被固定且互不重疊，並記錄 seed harness 與現成 harness 的基線（baseline）。
- **可信執行環境**：建立在 VERO 之上，透過沙盒、閘道與版本控制來隔離狀態、計量資源並保存候選版本。
- **明確的評分協議**：以最終候選方案在 held-out test partition 上的 normalized gain 作為單一指標，減少詮釋空間。

然而，論文摘要與引言並未明確說明以下項目是否公開：
- 原始程式碼（例如優化器 harness、評估伺服器、沙盒設定）；
- 資料集與 seed harness；
- 模型權重或 API 呼叫紀錄；
- 111 次 scored run 的完整軌跡與候選版本。

若這些資源未隨論文釋出，則外部研究者難以完全重現結果或在此基礎上進行公平比較。可信執行環境雖然在概念上能防止作弊，但其實作細節（例如閘道如何強制 per-scope budget、沙盒如何隔離 held-out data）也需要足夠文件化，才能被社群檢驗與採用。因此，目前可重現性評估為「結構設計良好，但實際開放程度需視論文附錄與釋出資源而定」。

#### 未來研究方向

基於 HARNESSOPT-BENCH 的設計與初步結果，未來研究可朝以下方向延伸：

1. **擴大任務覆蓋與領域多樣性**：目前僅 4 個下游任務，未來可納入更多需要長期規劃、多模態互動、即時決策或人機協作的任務，以測試 harness 優化在不同領域的泛化性。

2. **發展專門的故障診斷機制**：實驗顯示詳細追蹤檢查很少被使用且與增益無正相關。未來可設計能主動解析 development traces、定位錯誤來源並產生針對性 patch 的優化器，或把追蹤摘要與視覺化納入 harness 設計。

3. **自適應預算分配（adaptive budget allocation）**：當目標評估預算昂貴且隨機時，如何在探索新候選與精煉已知有潛力候選之間分配資源，是值得研究的決策問題。可結合多臂吃角子老虎機（multi-armed bandit）或貝氏最佳化（Bayesian optimization）等方法。

4. **分離「模型能力」與「搜尋演算法」**：目前優化器是 LLM 與 coding harness 的組合。未來可系統性地比較相同模型在不同搜尋策略（如演化、樹搜尋、反射迴圈）下的表現，以釐清哪部分貢獻最大。

5. **開源基準與社群提交**：將 HARNESSOPT-BENCH 的執行環境、資料集與評分伺服器開源，並建立公開排行榜，可促進不同研究團隊在相同協議下比較優化器設計。

6. **多目標 harness 優化**：現有設計主要優化單一標準化增益。未來可同時考慮延遲、成本、安全性、可解釋性等目標，發展多目標或受限優化版本的基準。

7. **跨模型與跨任務遷移**：研究一個任務上學到的 harness 修改策略，是否能遷移到不同任務或不同目標模型，這對於降低未來優化成本具有實務價值。

8. **安全與對齊考量**：當優化器被允許修改智慧體的提示、工具與記憶時，可能引入新的攻擊面或價值偏移。未來可研究如何在 harness 優化過程中嵌入安全約束與對齊檢查。

## 論文問答

**Q1：什麼是 harness 優化，為什麼它對現代 AI 系統很重要？**

A：harness 指的是圍繞大型語言模型的一整套程式架構，包括提示（prompt）、工具（tool）、控制流程（control flow）、上下文與記憶（context and memory），以及編排程式碼（orchestration code）。由於同一個語言模型在不同的 harness 下可能展現出顯著不同的能力，因此 harness 優化——也就是在固定預算內根據測量結果迭代改進 harness——成為提升智慧體系統（agentic system）效能的關鍵途徑。隨著 LLM 越來越常以智慧體形式部署，自動化 harness 優化不僅能釋放模型潛能，也成為衡量前沿模型系統級能力的重要指標。

**Q2：現有方法或基準為什麼無法有效衡量自動化 harness 優化？**

A：現有研究通常各自使用不同的目標智慧體（target agent）、初始 harness（seed harness）、評估預算、資訊揭露政策與計分協議，導致實驗結果混淆了優化器模型、編碼 harness、目標智慧體與評估協議本身的貢獻。這種缺乏統一協議的狀況，使得社群難以公平比較不同 frontier LLM 在 harness 優化上的真正能力。因此，必須把目標模型、執行環境與驗證器固定下來，並透過保留測試分區（held-out test partition）與可信執行環境（trusted execution environment）來分離各項因素。

**Q3：為什麼 harness 優化不只是一項程式編輯能力，而是對 AI 系統的嚴峻考驗？**

A：harness 優化的評估通常是昂貴且隨機的（expensive and stochastic），因為每次改動都必須執行一個隨機性智慧體（stochastic agent）在大量案例上才能估計效果。優化器必須從不完整證據（incomplete evidence）中診斷失敗原因、實作系統層級變更（system-level change）、在有限目標評估預算（target-evaluation budget）內分配資源，並區分真實改進（real improvement）與雜訊（noise）。這與廉價測試套件只需篩選大量候選方案不同，昂貴評估要求優化器具備根據先驗證據推理（reasoning from prior evidence）的能力，因此是更長遠、更複雜的能力測試。

**Q4：HarnessOpt-Bench 的核心實驗設計是什麼？**

A：在 HarnessOpt-Bench 中，優化器（optimizer）是一個配備編碼 harness 的大型語言模型，它會收到目標智慧體的初始 harness、分級的開發與驗證回饋（graded evaluation feedback），以及固定的目標評估預算。優化器可以編輯 harness 並提名一個最終候選方案（final candidate），該候選方案會在整個搜尋期間都無法存取的保留測試分區上進行評分。最終分數以相對於初始 harness 的標準化增益（normalized gain）來衡量，確保結果反映的是真正的泛化能力，而非對可見分數的過度擬合。

**Q5：HarnessOpt-Bench 在執行環境與防作弊設計上有哪些關鍵創新？**

A：本研究建立了一個可信執行環境，包含可信評估沙盒（trusted evaluation sandbox）、模型 API 閘道（Model API Gateway）與評估伺服器（evaluation server），用來強制執行評估邊界（evaluation boundary）。優化器沙盒只能寫入目標智慧體的 harness，可以讀取評估結果與任務資料，但無法修改它們；保留資料、提供者憑證（provider credentials）與預算強制執行（budget enforcement）都不在優化器沙盒內。每個候選方案都在隔離且非特權的沙盒中執行，所有模型呼叫都經過閘道以執行模型允許清單（model allow-list）與各範圍預算（per-scope budget），並且每個版本都會被保存以供稽核（audit）。

**Q6：為什麼要將測試集完全保留，並使用標準化增益作為評分指標？**

A：將測試分區在搜尋全程保持不可存取，可以避免優化器針對可見的開發集或驗證集分數進行過度擬合，從而確保測量到的是真正的泛化改進。使用標準化增益則能把不同任務與不同初始 harness 的絕對分數轉換成可比的相對進步幅度，讓研究者清楚看出優化器帶來的相對效益。這兩項設計共同把「優化器本身的能力」從「任務難度」和「初始 harness 品質」中分離出來。

**Q7：實驗中評估了哪些模型、任務與設定？**

A：研究評估了五個前沿大型語言模型作為優化器，分別在共享編碼 harness（shared coding harness）與各自的原生 harness（native harness）下進行測試，涵蓋四個下游任務（downstream task），總共進行了 111 次計分執行（scored run）。這些任務特別選擇評估本身昂貴且隨機的場景，例如固定語料研究（fixed-corpus research）與終端機使用（terminal use）。此外，研究還在其中一個任務上額外評估了兩種不同的編碼 harness，以比較 harness 設計的影響。

**Q8：實驗的主要結果有哪些？**

A：結果顯示，優化器模型之間的差異平均而言大於它們所作用的編碼 harness 之間的差異，這表示模型本身的推理能力在此任務中扮演關鍵角色。同時，原生 harness 並未呈現一致的優勢，不同任務與 seed 設定（seed regime）下的可達成增益（gain）差異相當大。在 OfficeQA 任務上，release-level 實驗甚至能區分出連續幾代優化器模型之間的能力變化，顯示 HarnessOpt-Bench 具有足夠的鑑別力。

**Q9：從搜尋軌跡的分析中，可以觀察到優化器的哪些行為模式？**

A：研究發現，對 harness 進行更廣泛的介入（broader intervention）與更高的保留測試增益有正相關，表示敢於做系統級改動的優化器往往表現較好。然而，詳細的失敗追蹤記錄（development traces）檢查卻很少被使用，而且與增益沒有顯著正相關。這暗示現有優化器尚未充分利用細粒度的診斷資訊，未來若能更好地從失敗軌跡中推理，可能還有顯著的進步空間。

**Q10：自動化 harness 優化在實務上可以應用在哪些場景？**

A：任何依賴提示設計、工具選擇、控制流程與記憶機制的 LLM 應用都可能受益，例如檢索增強生成（RAG）管線、多步驟研究智慧體、程式編寫助理、客戶服務機器人，以及需要與終端機或 API 互動的任務。在這些場景中，harness 的微小改動可能顯著影響最終任務成功率，但人工調校既耗時又難以窮盡。透過 HarnessOpt-Bench 這類自動化流程，團隊可以在控制成本的前提下持續迭代並找到更穩健的 harness。

**Q11：若要在產品中部署這類自動化 harness 優化，需要考慮哪些工程與治理問題？**

A：首先必須建立可信執行環境，確保預算強制執行、保留資料隔離，以及每個候選版本都可稽核，避免優化器意外或惡意地繞過限制。其次，由於目標評估是隨機且昂貴的，產品團隊需要監控資源使用量（resource use）並設定合理的目標評估預算，防止成本失控。最後，應保留人類對最終候選方案（final candidate）的審查與部署決策，特別是在高風險應用中，以確保改進真正泛化且不會引入未預期的行為。

**Q12：HarnessOpt-Bench 對整個研究領域可能帶來什麼影響？**

A：它把 harness 工程從個別優化器專屬的展示轉變成可重現、可比較的評估目標，讓研究者能夠系統性地測量與開發改進 AI 智慧體的系統。透過固定目標模型、環境與驗證器，並使用保留測試分區，HarnessOpt-Bench 提供了一個公平的競技場來比較不同 frontier LLM 與 harness 設計。長遠來看，這將促進更強大的端對端優化器（end-to-end optimizer）、編碼 harness 與自我改進智慧體（self-improving agent）的發展。

**Q13：作者承認 HarnessOpt-Bench 有哪些限制？**

A：雖然 HarnessOpt-Bench 對優化器設計保持中立，但本研究的實驗主要使用編碼智慧體（coding agent）作為端對端優化器，尚未全面探索其他類型的搜尋架構。此外，目前只涵蓋四個下游任務，雖然這些任務具有昂貴且隨機的評估特性，但仍不足以代表所有可能的 harness 優化領域。最後，由於每次評估都需要消耗真實的模型呼叫預算，擴大任務數量與運行次數在成本與時間上仍具挑戰。

**Q14：從實驗結果看，現有優化器在哪些情況下表現不佳？**

A：現有優化器很少深入檢查詳細的失敗追蹤記錄，導致它們可能錯過從具體錯誤案例中學習的機會。此外，不同任務與 seed 設定下的增益差異很大，顯示優化器尚未具備穩定泛化到各種情境的能力。原生 harness 也沒有帶來一致優勢，這說明單純依賴模型原廠或慣用的 harness 並不能保證更好的優化結果，harness 設計本身仍有很大的改進空間。

**Q15：未來可以朝哪些方向延伸或改進這項研究？**

A：未來可以開發更擅長從隨機證據與失敗軌跡中推理的優化器，例如結合演化程序與編碼智慧體的混合式方法。也可以擴展 HarnessOpt-Bench 到更多下游任務、更大的目標評估預算、多模態 harness，以及更接近真實部署環境的長期優化迴路。此外，改進共享編碼 harness 以支援更強大的規劃、除錯與版本管理功能，也有助於進一步提升優化器在複雜系統上的表現。

## 實務應用指南

### 適用場景

1. **企業級 RAG 智慧體調校**  
   當企業內部知識問答智慧體的表現受提示、檢索策略與重排邏輯交互影響時，可用 HarnessOpt-Bench 在固定目標評估預算下，系統化地優化整個 harness，而不是只調整單一提示。

2. **客戶服務自動化流程**  
   對需要多步工具呼叫（查詢訂單、退款政策、對話摘要）的客服智慧體，harness 優化可同時改進控制流程、記憶與工具編排，並以保留測試分區驗證最終候選方案是否真正泛化。

3. **程式碼生成與終端操作智慧體**  
   針對執行成本高、結果隨機的終端任務（如軟體建置、測試修復），透過可信執行環境與分級評估回饋，讓優化器智慧體在沙盒中迭代改進 harness，避免直接暴露生產環境。

4. **研究文獻綜合與固定語料分析**  
   在固定語料、評估昂貴的研究任務上，harness 優化可協助調整提示、上下文長度與多輪推理流程，並以標準化增益衡量相對於初始 harness 的改進。

5. **多步決策工作流程**  
   例如供應鏈預測、財務風險評估等需要長程規劃與多工具協作的情境，harness 優化能將「根據先驗證據推理」的能力納入系統設計，並在受控預算內決定最終部署版本。

---

### 實作前置條件

- **資料準備**  
  必須有明確劃分且互不重疊的開發集、驗證集與保留測試集；保留測試分區在搜尋期間必須完全不可存取。同時需要可重複的 seed harness、目標任務資料與已評分的基準線。

- **運算資源**  
  由於目標智慧體的評估通常是隨機且昂貴的，需要足夠的運算配額來執行多次目標評估；此外，優化器智慧體本身也會產生大量模型呼叫，需預先規劃各範圍預算。

- **執行環境**  
  需要可信執行環境或可信評估沙盒，能強制執行評估邊界、隔離保留資料、計量資源使用量，並保存每個候選 harness 版本以供稽核。

- **模型 API 閘道**  
  需部署模型 API 閘道以管理模型允許清單、各範圍預算與憑證，避免優化器沙盒直接接觸提供者憑證或測試資料。

- **技能需求**  
  團隊需具備軟體工程能力（能閱讀與修改編排程式碼）、提示工程經驗、評估設計與指標定義能力，以及基礎統計知識以區分真實改進與雜訊。

---

### 實作步驟建議

1. **定義目標智慧體與初始 harness**  
   將現有 agent 的提示、工具、控制流程、記憶與編排程式碼封裝成可版本控制的 seed harness，並確保其可在沙盒中獨立執行。

2. **建立評估協定**  
   設計分級評估回饋機制：開發集提供每案例的開發追蹤記錄，驗證集提供彙總驗證指標，測試集則完全隱藏。選定標準化增益作為主要評分指標。

3. **部署可信執行環境**  
   建置隔離沙盒與模型 API 閘道，設定目標評估預算、模型允許清單與存取權限，確保優化器只能寫入目標智慧體的 harness，不能修改任務資料或評估結果。

4. **選擇優化器模型與 coding harness**  
   決定要使用共享編碼 harness 還是各模型的原生 harness；建議先以共享編碼 harness 進行控制實驗，再比較原生 harness 的差異。

5. **執行迭代搜尋**  
   讓優化器智慧體讀取 seed harness、檢視歷史評估結果與執行追蹤，在固定預算內編輯 harness 並產生候選版本；過程中持續監控資源使用量與預算消耗。

6. **提名最終候選方案並進行保留測試**  
   搜尋結束後，優化器提交最終候選方案；由可信評估伺服器在保留測試分區上計算標準化增益，此分數即為正式成績。

7. **部署與持續監控**  
   將通過保留測試的 harness 部署至生產環境，並持續收集線上指標；保留所有候選版本與評估紀錄，以便未來稽核與再優化。

---

### 潛在風險與注意事項

- **過度擬合開發／驗證集**  
  若保留測試分區未嚴格隔離，優化器可能會針對可見分數調整 harness。應透過可信執行環境強制執行評估邊界，而非僅依賴指示。

- **將雜訊誤判為真實改進**  
  隨機性評估容易產生虛假增益。建議結合統計檢定、重複評估與標準化增益，並在解讀結果時考量 seed 設定與任務差異。

- **預算超支**  
  目標評估與優化器自身的模型呼叫都會消耗預算。必須在模型 API 閘道層級設定硬性上限，並區分優化器搜尋評估與保留測試評估的配額。

- **安全性與提示注入**  
  優化器編輯 harness 時可能引入不安全的提示或工具呼叫。應在隔離沙盒中執行每個候選版本，並限制其對外部系統與敏感資料的存取。

- **再現性不足**  
  不同 seed regime 與 harness 複雜度會導致結果差異極大。建議固定隨機種子、記錄完整執行軌跡，並對多個 seed 進行計分執行次數統計。

- **過度複雜化 harness**  
  優化器可能傾向加入過多控制流程或記憶機制，反而降低可維護性。應在評分指標中納入延遲、成本或程式碼複雜度等輔助指標。

---

### 與其他技術的整合建議

- **現有 agent 框架**  
  HarnessOpt-Bench 可與 LangChain、AutoGen、DSPy 等框架並用：將這些框架產生的 agent 視為 seed harness，再透過優化器智慧體修改其提示、工具編排與記憶邏輯。

- **CI/CD 與版本控制**  
  將每次 harness 編輯視為一次程式碼提交，利用 Git 或 DVC 管理候選版本；搭配 CI pipeline 自動在開發集上執行基準評估，並在合併前觸發保留測試。

- **MLOps 評估管線**  
  整合現有的模型評估平台，用於追蹤標準化增益、彙總驗證指標與資源使用量；將 harness 優化納入常規模型上線流程。

- **可觀測性與追蹤系統**  
  將開發追蹤記錄與執行軌跡匯入可觀測性工具，協助優化器診斷故障；同時也讓工程師在部署後持續監控 harness 行為。

- **模型閘道與成本管理**  
  若組織已有模型 API 閘道，可擴充其功能以支援模型允許清單、各範圍預算與稽核日誌，直接作為 HarnessOpt-Bench 的可信執行基礎設施。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦於「適用場景」與「實作步驟建議」，理解 harness 是什麼、為何不能只調提示，以及為何需要保留測試分區與固定預算；遇到專有名詞可對照詞彙表，不必一開始就深入可信執行環境的實作細節。

- **AI 工程師**  
  請重點閱讀「實作前置條件」與「潛在風險與注意事項」，特別是可信執行環境的建置、模型 API 閘道的預算強制執行，以及如何區分真實改進與雜訊；這些是將論文方法落地為產品時最關鍵的工程議題。

- **研究人員**  
  建議從「與其他技術的整合建議」與實驗設計角度切入，關注共享編碼 harness 與原生 harness 的比較、seed regime 的影響，以及如何在未來研究中將 HarnessOpt-Bench 擴展到更多下游任務與優化器架構。

- **產品經理**  
  請優先閱讀「適用場景」與「實作步驟建議」，評估 harness 優化對自家產品指標與成本的潛在影響；同時留意「潛在風險與注意事項」中的預算與安全性議題，以便在規劃產品路線圖時與工程團隊對齊風險與預期效益。
