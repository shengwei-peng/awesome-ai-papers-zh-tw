## ⚡ TL;DR

解決原生程式設計智慧體框架在策略梯度訓練中面臨的訓練-推論差異與獎勵駭取問題。
提出LEGO-RL，透過程序內LLM代理、可擴展沙箱編排與可觀測訓練，銜接原生框架與大規模強化學習。
於SWE-bench Verified，三個原生框架解題率顯著提升，機率相關性維持0.99以上。

## 摘要翻譯

程式設計智慧體（Coding Agent）的強化學習（Reinforcement Learning, RL）日益依賴長時間運作的智慧體執行框架（Agent Harness）來管理工具整合（Tool Integration）、程式碼庫上下文（Repository Context）與執行回饋（Execution Feedback）。然而，這些框架的原生執行環境（Native Execution Environment）本質上與策略梯度訓練（Policy-Gradient Training）存在錯位：環境崩潰（Environmental Crash）與獎勵駭取（Reward Hacking）會汙染結果訊號（Outcome Signal），而訓練-推論差異（Train-Inference Discrepancy）則使 Rollout 行為（Rollout Behavior）與策略更新（Policy Update）脫鉤。為解決此問題，我們提出 LEGO-RL，一個無需修改其內部控制流程（Internal Control Flow）即可銜接原生程式設計智慧體框架（Native Coding-Agent Harness）與可擴展策略梯度最佳化（Policy-Gradient Optimization）的框架。LEGO-RL 建立在三大支柱之上：(1) 透過程序內 LLM 代理（In-Process LLM Proxying）實現忠實最佳化（Faithful Optimization），擷取原始生成串流（Raw Generation Stream）以進行詞元級對齊（Token-Level Alignment）與穩健的訓練器端對數機率重算（Trainer-Side Log-Probability Recomputation），即便面臨框架端壓縮（Harness-Side Compaction）或重新序列化（Re-Serialization）；(2) 透過可擴展沙箱編排（Scalable Sandbox Orchestration）實現可靠執行（Reliable Execution），具備映像檔快取（Image Caching）與分階段防禦（Stage-Wise Defense）以抑制獎勵駭取（Reward Hacking）；以及 (3) 透過整合式外掛（Integrated Plugin）實現可觀測訓練（Observable Training），自動化驗證與監控（Validation and Monitoring），並搭配具備細粒度軌跡診斷（Granular Trajectory Diagnostics）功能的即時使用者介面（Live UI）。我們透過在三個原生程式設計智慧體框架（Native Coding-Agent Harness）上以 GSPO 訓練稀疏混合專家模型（Sparse Mixture-of-Experts Model）Qwen3.5-35B-A3B 來評估 LEGO-RL。在 SWE-bench Verified 上，LEGO-RL 使 Qwen3.5-35B-A3B 於 OpenHands SDK（從 64.0% 提升至 70.4%）、Claude Code（從 62.4% 提升至 68.2%）與 OpenCode（從 57.2% 提升至 66.6%）的表現皆獲提升，同時維持 Rollout-訓練機率相關性（Rollout-Training Probability Correlation）高於 0.99。

### 核心貢獻（3～5點）
- 提出 LEGO-RL，可在不修改原生程式設計智慧體框架（Native Coding-Agent Harness）內部控制流程（Internal Control Flow）的前提下，將其原生執行環境（Native Execution Environment）與可擴展策略梯度訓練（Policy-Gradient Training）銜接，解決訓練-推論差異（Train-Inference Discrepancy）導致的 Rollout 行為（Rollout Behavior）與策略更新（Policy Update）脫鉤問題。
- 透過程序內 LLM 代理（In-Process LLM Proxying）實現忠實最佳化（Faithful Optimization），擷取原始生成串流（Raw Generation Stream）以支援詞元級對齊（Token-Level Alignment）與訓練器端對數機率重算（Trainer-Side Log-Probability Recomputation），即使框架端進行壓縮（Harness-Side Compaction）或重新序列化（Re-Serialization）仍能保持對齊。
- 透過可擴展沙箱編排（Scalable Sandbox Orchestration）與分階段防禦（Stage-Wise Defense）提升可靠執行（Reliable Execution），並藉由映像檔快取（Image Caching）等機制抑制獎勵駭取（Reward Hacking）與環境崩潰（Environmental Crash）對結果訊號（Outcome Signal）的汙染。
- 提供整合式外掛（Integrated Plugin）與即時使用者介面（Live UI），達成可觀測訓練（Observable Training），自動化驗證與監控（Validation and Monitoring），並支援細粒度軌跡診斷（Granular Trajectory Diagnostics）。
- 在 SWE-bench Verified 上，以 GSPO 於 OpenHands SDK、Claude Code 與 OpenCode 三個框架訓練稀疏混合專家模型（Sparse Mixture-of-Experts Model）Qwen3.5-35B-A3B，顯著提升解題率並維持 Rollout-訓練機率相關性（Rollout-Training Probability Correlation）高於 0.99。

### 適合對象
從事強化學習（RL）與程式設計智慧體（Coding Agent）研究的學者與工程師，特別是關注如何將既有智慧體執行框架（Agent Harness）與大規模策略梯度訓練（Policy-Gradient Training）整合、需要解決執行環境不穩定與獎勵駭取（Reward Hacking）問題，以及希望建立可觀測、可擴展訓練管線的系統開發者與維運人員。

## 深度分析

#### 方法論解析

LEGO-RL 的核心目標是讓**原生程式設計智慧體框架（native coding-agent harness）**能夠直接接入可擴展的**策略梯度訓練（policy-gradient training）**，而不需要改動智慧體內部的控制流程。其方法論可從問題設定、系統架構與三大技術支柱三個層次理解。

**問題設定與設計哲學**  
傳統上，訓練**程式設計智慧體（coding agent）**需要處理長期軌跡：智慧體會反覆進行**模型呼叫（model call）**、**程式碼庫檢查（repository inspection）**、**工具呼叫（tool calling）**、**程式碼修改（code modification）**、**相依套件安裝（dependency installation）**與**測試執行（test execution）**，最後才得到一個稀疏的**驗證器獎勵（verifier reward）**。這些行為由原生框架（如 OpenHands SDK、Claude Code、OpenCode）管理，包括提示建構、上下文壓縮與歷史重寫。LEGO-RL 的設計哲學是：最佳化目標應該是「由原始智慧體控制流程所誘導出的策略行為（policy behavior）」，而非將智慧體改寫成訓練框架定義的介面。因此，LEGO-RL 透過一個輕量級的**框架適配器（harness adapter）**啟動智慧體、連接推論服務並回傳互動資料，其餘訓練管線則跨框架共用。

**系統架構**  
從圖 1 可看出，LEGO-RL 的架構分為幾個層次：

- **執行環境層**：以 **Kubernetes（K8S）** 為基礎，搭配 **Nydus 冷啟動映像檔快取（Nydus cold start image cache）**、**Docker** 映像檔掛載，以及部署在 EC2/ECS 上的沙箱服務，提供可擴展的**沙箱化執行 + 驗證器（sandboxed execution + verifier）**。
- **智慧體工作節點（Agent Worker）**：每個 worker 內部運行一個原生框架實例（OpenHands、Claude Code、OpenCode 等）。
- **程序內 LLM 代理（In-Process Proxy）**：位於智慧體與推論伺服器之間，提供統一 OpenAI API，負責**軌跡擷取（trajectory capture）**、**詞元進出記錄（token-in / token-out）**、負載平衡與黏性路由（sticky routing）。
- **訓練後端**：包含 **Rollout Engine**、**Trainer**、多個 **Inference Server**、**Data Buffer**，並支援 **FSDP**、**VeOmni**、同步/非同步權重同步（weight sync）、**Megatron**，以及針對稀疏混合專家模型（Sparse MoE）的 **Partial Rollout R3** 機制。

資料流如下：智慧體透過 In-Process Proxy 呼叫推論伺服器，Proxy 同時記錄原始生成串流與 metadata；完成一次 **Rollout** 後，軌跡與獎勵進入 Data Buffer；Trainer 從 buffer 取樣並更新策略，最新權重再同步回 Inference Server。

**三大技術支柱**

1. **忠實最佳化（Faithful Optimization）**  
   這是解決**訓練-推論差異（train-inference discrepancy）**的關鍵。由於框架端會進行**上下文壓縮（context compaction）**與**歷史重寫（history rewriting）**，訓練器端若僅依賴框架回傳的重建軌跡，可能無法還原 Rollout 期間實際取樣的精確詞元序列（exact token sequence）。LEGO-RL 的 In-Process Proxy 在程序內攔截並保存**原始生成串流（raw generation stream）**，讓 Trainer 能進行**詞元級對齊（token-level alignment）**與**訓練器端對數機率重算（trainer-side log-probability recomputation）**。對於 **Qwen3.5-35B-A3B** 這類**稀疏混合專家模型（sparse MoE model）**，LEGO-RL 還會在訓練時重播 Rollout 階段的**專家路由（expert routing）**決策，即所謂的 R3（rollout routing replay），避免 MoE 路由不一致造成的機率漂移。

2. **可靠執行（Reliable Execution）**  
   程式設計智慧體的執行層容易出現**環境崩潰（environmental crash）**、相依套件錯誤、驗證器設定錯誤、逾時與**獎勵駭取（reward hacking）**。LEGO-RL 透過可擴展的**沙箱編排（sandbox orchestration）**、映像檔快取與**分階段防禦（stage-wise defense）**來保護獎勵訊號的完整性。此外，終止感知過濾（termination-aware filtering）與復原機制可防止失敗軌跡干擾非同步訓練管線。

3. **可觀測訓練（Observable Training）**  
   非同步分散式訓練中的失敗訊號往往碎片化，難以定位。LEGO-RL 提供整合式外掛，自動化執行驗證與監控，並搭配 **Live UI** 進行**細粒度軌跡診斷（granular trajectory diagnostics）**，讓研究者能追蹤智慧體、環境、驗證器與最佳化過程中的異常。

#### 實驗數據解讀

LEGO-RL 的實驗以 **Qwen3.5-35B-A3B** 為策略模型，使用 **GSPO** 作為策略梯度演算法，並在三個原生框架上進行訓練與評估：**OpenHands SDK**、**Claude Code** 與 **OpenCode**。評估基準為 **SWE-bench Verified**，衡量指標為問題解決率（resolve rate）。

| 原生框架 | 基線 | LEGO-RL | 絕對提升 |
|---|---:|---:|---:|
| OpenHands SDK | 64.0% | 70.4% | +6.4 pp |
| Claude Code | 62.4% | 68.2% | +5.8 pp |
| OpenCode | 57.2% | 66.6% | +9.4 pp |

**結果意涵**

- **跨框架一致性提升**：三個框架在經過 LEGO-RL 訓練後，於 SWE-bench Verified 上均獲得顯著提升。這說明 LEGO-RL 的「框架原生」設計確實能夠適應不同智慧體控制流程，而不需要針對每個框架重新設計訓練管線。
- **低基線框架的進步空間更大**：OpenCode 的基線最低（57.2%），提升幅度也最大（+9.4 pp），顯示當原生框架的策略行為與驗證器回饋之間存在較大落差時，強化學習的邊際效益較高。
- **高基線仍有提升**：OpenHands SDK 與 Claude Code 已處於相對高水平（>60%），仍能分別提升 6.4 與 5.8 個百分點，顯示即使對於強基線模型，長期軌跡層面的策略梯度訓練仍有最佳化空間。
- **機率相關性驗證方法論**：LEGO-RL 報告 **Rollout-訓練機率相關性（rollout-training probability correlation）** 高於 0.99。這是一個關鍵的訓練忠實度指標，表示 Trainer 端重算的對數機率與 Rollout 時實際使用的機率幾乎一致，間接證明了 In-Process Proxy 與 R3 機制有效抑制了**訓練-推論差異**。

**需要注意的限制**  
由於提供的上下文未包含標準差、訓練步數、樣本數或計算資源等細節，無法評估結果的統計顯著性與成本效益。此外，實驗僅在單一模型家族與單一基準上進行，對於方法泛化性的結論仍屬初步。

#### 與現有研究的比較

LEGO-RL 在相關工作中的定位可透過表 1 的對比清楚看出。現有框架大致可分為三類：

1. **訓練框架主導型**：如 **verl**、**slime**、**MOLT**、**SkyRL**、**AReaL**。這類框架將 Rollout 納入訓練管線，提供客製化或非同步的智慧體 Rollout 支援，但通常需要將現有智慧體改寫為框架定義的互動與環境抽象，犧牲了**框架原生保真度（harness-native fidelity）**。
2. **全端共同設計型**：如 **ALE（ROLL/ROCK）**，同時設計 Trainer、Sandbox Manager 與 CLI 智慧體，透過控制整個堆疊達成一致性。這種方法效能可能很高，但無法直接利用現有成熟框架（如 Claude Code、OpenHands SDK）累積的工程優化。
3. **模型 API 觀測型**：如 **Polar**、**rLLM**、**OpenForgeRL**、**Agent Lightning**。這類方法保留原生智慧體框架，透過模型 API 或 SDK 回調觀測互動，但在訓練忠實度、執行可靠性或訓練可觀測性上往往有所欠缺。

相較之下，LEGO-RL 是少數同時滿足以下條件的框架：

- **黑箱框架相容（black-box harness）**：不修改智慧體內部控制流程。
- **詞元級對齊（token-in / token-out alignment）**：透過 In-Process Proxy 捕捉原始生成串流。
- **歷史與路由重播（history + R3）**：支援框架端歷史重寫下的機率重算，以及 MoE 專家路由重播。
- **完全非同步執行（fully async execution）**與可擴展沙箱。
- **獎勵駭取防禦（reward-hack defense）**。
- **訓練可觀測性（training observability）**。

**主要優勢**

- **降低採用門檻**：由於只需輕量級適配器即可支援新框架，研究社群與工業界可以更快將現有智慧體接入 RL 訓練。
- **高訓練忠實度**：In-Process Proxy 與 R3 機制直接針對策略梯度訓練中最棘手的機率不一致問題。
- **工程完整性**：從沙箱執行、映像檔快取到 Live UI，LEGO-RL 覆蓋了從資料收集到診斷的完整生命週期。

**限制與潛在弱點**

- **僅觀測模型 API**：雖然不改動內部流程，但也意味著無法直接控制框架內部的狀態轉換。若框架在兩次 API 呼叫之間進行了非確定性狀態更新，仍可能引入難以追蹤的變異。
- **適配器仍具框架專屬性**：雖然訓練管線共用，但每個新框架仍需開發適配器，對於封閉源或 API 不穩定的框架可能仍有挑戰。
- **防禦機制細節不足**：文中提到「分階段防禦」與「智慧體執行期防駭取（agent-runtime anti-hacking）」，但未詳細說明如何區分合法利用環境與惡意獎勵駭取，這在開放式程式設計任務中仍是開放問題。
- **評估範圍有限**：僅使用 SWE-bench Verified，未涵蓋 SWE-bench Pro、Multi-SWE-bench 等更困難或更多語言的設定，也未與其他 RL 演算法進行直接對照。

#### 可重現性評估

LEGO-RL 在可重現性方面採取了相對開放的策略。根據摘要與引言，作者承諾將**完整框架、訓練後模型與資料集**開源釋出給社群。這對於一個涉及複雜分散式基礎設施、多框架適配與大規模 MoE 訓練的工作而言，是相當積極的舉措。

**有利於重現的要素**

- **開源程式碼**：若完整釋出，研究者可直接取得 In-Process Proxy、沙箱編排、Live UI 外掛與三個框架的適配器實作。
- **開源模型與資料集**：釋出訓練後的 Qwen3.5-35B-A3B 權重與軌跡資料，可讓其他團隊驗證 SWE-bench Verified 上的數據，並作為未來研究的起點。
- **基於現有專案**：LEGO-RL 建構在 **verl** 與 **Harbor** 之上，這兩者本身已有一定社群基礎，降低了理解門檻。

**仍需確認的要素**

- **硬體與計算資源需求**：訓練 35B-A3B 的稀疏 MoE 模型需要大量 GPU 與記憶體，開源程式碼是否包含可於較小規模復現的設定（例如部分 Rollout 或較小模型）將影響可及性。
- **依賴版本與環境設定**：Nydus、K8S、Docker、EC2/ECS 等基礎設施配置複雜，需要詳細的部署文件與版本鎖定。
- **超參數與隨機種子**：策略梯度訓練對學習率、KL 懲罰、獎勵縮放等超參數敏感，完整釋出應包含 GSPO 的詳細設定。
- **授權條款**：模型權重、資料集與框架程式碼的授權是否允許學術與商業使用，將決定其實際影響力。

整體而言，LEGO-RL 在可重現性上的承諾優於許多同類技術報告，但最終評估仍取決於實際釋出內容的完整度與文件品質。

#### 未來研究方向

LEGO-RL 為框架原生強化學習建立了堅實基礎，但仍有多個值得延伸的方向：

1. **擴展至更多框架與基準**  
   除了 OpenHands SDK、Claude Code 與 OpenCode，未來可將方法應用於 **SWE-agent**、其他封閉源程式設計助手，以及 **SWE-bench Pro**、**Multi-SWE-bench**、**SWE-rebench** 等更具挑戰性的基準，驗證其泛化能力。

2. **從稀疏獎勵到過程獎勵**  
   目前訓練依賴最終的驗證器獎勵，屬於**稀疏可執行獎勵（sparse executable reward）**。引入**過程獎勵（process reward）**，例如單元測試通過率、靜態分析分數或編譯成功訊號，可能改善長期軌跡的**信用分配（credit assignment）**。

3. **更強大的獎勵駭取防禦**  
   未來可結合大型語言模型作為裁判（LLM-as-judge）、靜態分析工具與執行跡證比對，建立更細緻的**分階段防禦（stage-wise defense）**，區分合法捷徑與惡意操縱。

4. **大規模稀疏 MoE 與路由最佳化**  
   R3 機制解決了路由重播問題，但未來可進一步研究如何在訓練過程中微調或學習更高效的專家路由策略，甚至將路由本身納入策略最佳化目標。

5. **多叢集與異構運算擴展**  
   隨著模型規模與任務複雜度增加，Rollout 與 Training 的資源需求將更加分歧。研究如何跨多個 K8S 叢集、混合雲環境進行**可擴展沙箱編排（scalable sandbox orchestration）**，將是實際部署的關鍵。

6. **跨領域遷移**  
   LEGO-RL 的「模型 API 代理 + 原生框架保留」模式原則上可應用於網頁智慧體（web agent）、GUI 智慧體或機器人控制。探索這些領域的適配與挑戰，有助於建立更通用的**框架原生強化學習（harness-native reinforcement learning）**典範。

7. **結合監督式微調與強化學習的混合訓練**  
   在 RL 訓練前後，利用高品質軌跡進行監督式微調（SFT），或將 SFT 與 RL 交替進行，可能進一步穩定訓練並提升最終效能。

8. **線上評估與持續學習**  
   建立與真實軟體開發流程整合的線上評估迴路，讓模型能持續從新問題與新程式碼庫中學習，並即時偵測效能衰退與獎勵駭取行為。

## 論文問答

**Q1：LEGO-RL 主要解決的問題是什麼？為什麼原生程式設計智慧體框架與策略梯度訓練之間存在根本性的錯位？**
A：LEGO-RL 主要解決原生程式設計智慧體框架（如 OpenHands SDK、Claude Code、OpenCode）與策略梯度訓練之間的根本性錯位問題。這些框架的原生執行環境會因環境崩潰、獎勵駭取而腐化結果訊號，同時訓練-推論差異會使 rollout 行為與策略更新脫節。具體而言，框架端的提示建構、上下文壓縮和歷史重寫會導致訓練器端重建的軌跡與 rollout 期間取樣的精確詞元序列不同，從而無法忠實地重算對數機率。

**Q2：現有的通用強化學習框架在整合原生程式設計智慧體框架時，為何會失敗或需要大量修改？**
A：現有通用強化學習框架通常要求程式設計智慧體適應框架定義的 rollout 介面，例如需要覆寫初始化、替換預設工具集為任務專用工具，或自訂終止邏輯以提取獎勵。這種做法破壞了原生框架內部的控制流程，改變了智慧體原本最佳化的行為模式。此外，現有框架往往無法處理框架端的歷史重寫、稀疏混合專家模型的 rollout 階段專家路由重現，以及非同步管線中跨階段傳播的執行失敗與診斷訊號碎片化問題。

**Q3：為什麼保留智慧體框架的原生控制流程對強化學習訓練至關重要？**
A：保留原生控制流程意味著最佳化目標就是該框架實際誘導出的策略行為，而非某個被修改後的近似版本。程式設計智慧體的長期行為高度依賴於框架如何管理提示、工具、上下文和執行狀態，任何對這些機制的人為改動都會改變最佳化目標，導致訓練出的策略在真實部署時表現不一致。因此，LEGO-RL 選擇在不修改內部控制流程的前提下橋接框架與策略梯度訓練，確保訓練與推論時的智慧體工作流程完全一致。

**Q4：LEGO-RL 的三大支柱是什麼？它們如何協同運作以支援框架原生強化學習？**
A：LEGO-RL 的三大支柱分別是忠實最佳化、可靠執行與可觀測訓練。忠實最佳化透過程序內 LLM 代理捕捉原始生成串流，支援詞元級對齊與訓練器端對數機率重算，即使框架端進行壓縮或重新序列化也能保持準確；可靠執行透過可擴展沙箱編排、映像檔快取與分階段防禦來減緩獎勵駭取與環境崩潰；可觀測訓練則透過整合式外掛自動化驗證與監控，並搭配即時使用者介面進行細粒度軌跡診斷。這三者協同運作，使得 LEGO-RL 能夠在不修改智慧體框架內部控制流程的情況下，實現可擴展且穩定的策略梯度訓練。

**Q5：LEGO-RL 如何透過程序內 LLM 代理實現忠實最佳化？這對稀疏混合專家模型有何特殊意義？**
A：LEGO-RL 的程序內 LLM 代理會攔截並記錄智慧體框架與推論伺服器之間的原始生成串流，包括精確的詞元序列與生成元資料，從而讓訓練器端能夠忠實地重算 rollout 期間的對數機率。這對於框架端進行上下文壓縮或歷史重寫的情況尤為重要，因為這些操作會改變輸入提示，但代理記錄的原始輸出仍能確保訓練目標與實際取樣行為一致。對於稀疏混合專家模型，LEGO-RL 還會重播 rollout 階段的專家路由決策，避免訓練時因專家路由不一致而產生額外的訓練-推論差異。

**Q6：在執行可靠性與訓練可觀測性方面，LEGO-RL 採取了哪些關鍵設計來保護獎勵完整性並加速故障定位？**
A：在執行層面，LEGO-RL 採用可擴展沙箱編排，結合 Nydus 冷啟動映像檔快取、智慧體執行期防駭取機制，以及分階段防禦來隔離與緩解獎勵駭取行為。當發生沙箱失敗、相依套件錯誤、驗證器設定錯誤或逾時時，終止感知過濾與復原機制可防止失敗軌跡干擾非同步訓練。在可觀測性方面，整合式外掛會自動化驗證與監控整個訓練流程，並透過即時使用者介面提供細粒度軌跡診斷，讓研究人員能夠快速定位跨智慧體、環境、驗證器與最佳化階段的問題。

**Q7：LEGO-RL 在哪些原生程式設計智慧體框架與基準上進行了評估？使用了什麼模型與演算法？**
A：LEGO-RL 在 OpenHands SDK、Claude Code 與 OpenCode 三個原生程式設計智慧體框架上進行了評估，測試基準為 SWE-bench Verified。實驗使用稀疏混合專家模型 Qwen3.5-35B-A3B 作為策略模型，並採用 GSPO 演算法進行策略梯度訓練。這樣的設置能夠同時檢驗 LEGO-RL 在不同框架設計哲學下的適用性，以及其對大型稀疏模型在長期軌跡訓練中的擴展能力。

**Q8：LEGO-RL 在 SWE-bench Verified 上取得了哪些關鍵性能提升？這些結果說明了什麼？**
A：LEGO-RL 在 SWE-bench Verified 上顯著提升了 Qwen3.5-35B-A3B 的問題解決率：OpenHands SDK 從 64.0% 提升至 70.4%，Claude Code 從 62.4% 提升至 68.2%，OpenCode 從 57.2% 提升至 66.6%。這些一致的增益表明，LEGO-RL 的框架原生強化學習方法能夠有效改進不同原生框架下的程式設計智慧體行為。同時，rollout-訓練機率相關性維持在 0.99 以上，證明了訓練過程與實際 rollout 行為之間具有高度的一致性。

**Q9：rollout-訓練機率相關性高於 0.99 這一指標為何重要？它反映了 LEGO-RL 的什麼技術優勢？**
A：rollout-訓練機率相關性高於 0.99 表示訓練器端重算的動作對數機率與 rollout 期間實際取樣的機率幾乎完全一致。這是策略梯度訓練中至關重要的指標，因為一旦機率估計出現偏差，策略更新就會針對錯誤的目標進行最佳化，導致訓練不穩定或收斂到次優策略。LEGO-RL 能夠維持如此高的相關性，主要歸功於程序內 LLM 代理對原始生成串流的精確捕捉，以及對稀疏混合專家模型 rollout 階段專家路由決策的忠實重播。

**Q10：在實際軟體開發場景中，LEGO-RL 最適合應用於哪些類型的任務或產品？**
A：LEGO-RL 最適合應用於需要長期互動、多次工具呼叫與可執行驗證的軟體開發任務，例如程式碼庫級的問題修復、功能新增、重構與自動化測試生成。由於它能夠直接利用現有的原生程式設計智慧體框架，企業無需為了強化學習訓練而重新設計或大幅修改其內部使用的智慧體工作流程。這使得 LEGO-RL 特別適合需要快速將現有 Claude Code、OpenHands SDK 或 OpenCode 整合進訓練管線的產品團隊與研究機構。

**Q11：從工程部署與維運的角度來看，LEGO-RL 相較於其他框架有哪些實務優勢？**
A：LEGO-RL 的工程優勢在於其輕量級的框架適配器設計，支援新框架時只需啟動智慧體、連接推論服務並回傳互動資料，其餘訓練管線可跨框架共用。這大幅降低了整合新智慧體框架的開發與維護成本，並讓團隊能夠專注於改進策略模型而非重寫執行基礎設施。此外，其可擴展沙箱編排、映像檔快取與即時監控介面，有助於在大規模非同步訓練中維持穩定性並快速定位問題，對於生產環境中的持續訓練與迭代至關重要。

**Q12：LEGO-RL 對程式設計智慧體與強化學習領域可能帶來什麼樣的影響？**
A：LEGO-RL 展示了在不犧牲原生框架 fidelity 的前提下，依然可以進行大規模策略梯度訓練的可行性，這可能改變未來程式設計智慧體研究的方法論。它降低了將真實世界智慧體框架納入 RL 訓練循環的門檻，使更多研究團隊能夠利用現有成熟的框架進行策略最佳化。長遠來看，這種框架原生強化學習範式有望促進更通用、更可靠的編碼智慧體誕生，並推動相關開源工具與基準的進一步發展。

**Q13：LEGO-RL 目前有哪些可能的限制或尚未充分解決的挑戰？**
A：雖然 LEGO-RL 在多個框架上展現了強大的訓練能力，但其效能仍受限於底層智慧體框架本身的設計與工具集，無法超越原生框架的能力上限。此外，儘管有分階段防禦機制，針對複雜且持續演化的獎勵駭取策略，完全自動化的防禦仍然具有挑戰性。最後，大規模稀疏混合專家模型的訓練與推論基礎設施需求較高，這可能限制部分資源較少的團隊直接複製其完整實驗設置。

**Q14：在 LEGO-RL 的訓練過程中，哪些類型的失敗案例或邊緣情況仍可能發生？**
A：即使具備終止感知過濾與復原機制，某些極端情況仍可能導致軌跡失效，例如驗證器設定錯誤造成的獎勵訊號偏差、沙箱環境中罕見的相依套件衝突，或是長期軌跡中因上下文過長而觸發的框架端歷史重寫異常。此外，若程序內代理與框架之間的通訊出現延遲或中斷，也可能導致部分生成元資料遺失，進而影響訓練器端的機率重算準確度。這些邊緣情況凸顯了持續監控與細粒度軌跡診斷的重要性。

**Q15：針對框架原生強化學習在程式設計智慧體上的應用，未來有哪些值得探索的研究方向？**
A：未來研究方向包括開發更強大的自動化獎勵駭取偵測與防禦機制，以應對日益複雜的智慧體行為；探索多框架聯合訓練或跨框架遷移學習，讓單一策略能夠泛化到不同原生框架的執行環境；以及將 LEGO-RL 的方法擴展到更多程式設計任務，如多語言程式碼庫維護、安全性修補與持續整合流程自動化。此外，進一步降低大型稀疏模型訓練的基礎設施門檻，並提升訓練過程的可解釋性，也是推動該領域普及的重要課題。

## 實務應用指南

### 適用場景

1. **企業內部程式碼維護與缺陷修復自動化**  
   當組織擁有龐大且持續演化的軟體程式碼庫，需要讓程式設計智慧體在原生框架（如 OpenHands SDK、Claude Code、OpenCode）中學習修復 issue、重構程式碼或補齊測試時，LEGO-RL 可在不改動智慧體控制流程的前提下進行策略梯度訓練，直接對齊實際執行環境的回饋。

2. **多智慧體框架的統一 RL 訓練平台**  
   若團隊同時使用多種智慧體執行框架，LEGO-RL 的輕量級 adapter 與共享訓練管線能讓不同框架共用同一套推論、沙箱與訓練基礎設施，降低為每個框架個別開發 RL 整合的成本。

3. **大規模稀疏 MoE 模型的程式設計任務微調**  
   針對 Qwen3.5-35B-A3B 這類稀疏混合專家模型，LEGO-RL 透過 replay rollout-time 專家路由，解決訓練-推論階段專家路由不一致的問題，適合需要將大型 MoE 模型落地到程式設計場景的團隊。

4. **高風險執行環境下的獎勵訊號保護**  
   在涉及外部套件安裝、測試執行與驗證器評分的場景中，LEGO-RL 的分階段防駭取與沙箱編排機制可減少獎勵駭取與環境崩潰對訓練訊號的污染，適合對訓練品質與安全性要求嚴苛的應用。

5. **可解釋與可監控的程式設計智慧體開發**  
   透過整合式外掛與 Live UI，團隊可對每條 rollout 軌跡進行細粒度診斷，適合需要持續監控智慧體行為、快速定位失敗根因並進行合規審查的產品化流程。

### 實作前置條件

**資料準備**
- 具備可執行驗證的程式設計任務資料集，例如 SWE-bench Verified 格式的 issue–patch 配對。
- 每個任務需包含原始程式碼庫、重現步驟、測試指令與明確的驗證器獎勵定義。
- 建議預先收集基線軌跡，用於校驗 in-process LLM proxy 所捕捉的原始生成串流是否與框架端一致。

**運算資源**
- 至少具備多張高記憶體 GPU 的叢集，以支援 Qwen3.5-35B-A3B 等級模型的 FSDP / Megatron 訓練。
- Kubernetes（K8S）叢集用於可擴展沙箱編排，並建議搭配 Nydus 冷啟動映像檔快取以降低沙箱啟動延遲。
- 足夠的 Docker 映像檔儲存空間與網路頻寬，因 image caching 與頻繁的環境掛載會產生大量 I/O。

**技能與工具**
- 熟悉強化學習基礎，特別是策略梯度方法（如 GSPO）與 PPO 類演算法。
- 具備 LLM 推論服務部署經驗（vLLM、TGI 或自研推論伺服器），並能暴露統一 OpenAI API。
- 熟悉 Docker、Kubernetes 與沙箱化執行環境，能設計 agent-runtime anti-hacking 規則。
- 至少熟悉一種目標智慧體框架（OpenHands SDK、Claude Code 或 OpenCode），以便開發輕量級 adapter。

### 實作步驟建議

1. **選定目標智慧體框架並開發 adapter**  
   在不修改框架內部控制流程的前提下，撰寫一個 launcher：負責啟動智慧體、將模型端點導向 LEGO-RL 的 in-process LLM proxy，並在 rollout 結束後回傳互動資料與驗證器獎勵。

2. **部署 in-process LLM proxy 與推論叢集**  
   在推論伺服器前設定全域負載平衡器與黏性路由，確保同一條 rollout 的多次模型呼叫落在同一台推論伺服器；proxy 需完整記錄 token-in / token-out、生成 metadata 與 MoE 專家路由，供訓練器端重算對數機率。

3. **建立沙箱化執行與驗證管線**  
   於 K8S 上部署 sandbox runtime，啟用 Nydus 映像檔快取與分階段防駭取機制；將工具呼叫、檔案系統異動、網路存取與測試執行納入監控，並設定逾時與資源上限。

4. **連接訓練器與資料緩衝區**  
   以 verl 為基礎設定 trainer，配置 FSDP / Megatron 權重同步、partial rollout 與 async/sync 資料流；確保 rollout engine 將軌跡與獎勵寫入資料緩衝區後，trainer 能正確重組並進行策略更新。

5. **執行小規模對齊驗證**  
   在正式訓練前，先跑少量 rollout，比對 proxy 端記錄的精確詞元序列與訓練器端重算後的機率分佈，確認 rollout-訓練機率相關性達到 0.99 以上；同時檢查 MoE 專家路由是否被正確 replay。

6. **啟動完整訓練與持續監控**  
   使用 GSPO 或其他策略梯度演算法進行長期訓練，透過整合式外掛與 Live UI 即時觀察 resolve rate、獎勵分佈、沙箱失敗率與軌跡異常；定期在 SWE-bench Verified 上進行驗證，避免 overfit 到訓練任務。

7. **產品化部署與迭代**  
   將訓練後的模型權重匯出，並與現有的 CI/CD、程式碼審查或 issue 管理系統對接；保留 adapter 與監控外掛，以便後續隨著框架版本更新持續微調。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解措施 |
|---|---|---|
| **框架端歷史重寫導致機率對齊失敗** | 智慧體框架可能會壓縮上下文或重寫歷史，使訓練器端無法重現 rollout 時的精確詞元序列。 | 透過 in-process LLM proxy 在框架發出請求當下即記錄原始生成串流與最終送進模型的完整提示，而非事後從框架重建。 |
| **MoE 專家路由不一致** | 訓練時若未 replay rollout-time 專家路由，會造成訓練-推論差異。 | 在 proxy 中保存每個 token 的專家路由決策，並在 trainer 端強制使用相同路由進行對數機率重算。 |
| **獎勵駭取與環境崩潰** | 智慧體可能利用驗證器漏洞或造成沙箱不穩定，污染獎勵訊號。 | 實施分階段防駭取：限制網路與檔案系統權限、隔離測試環境、對異常高分或低分軌跡進行抽樣複驗。 |
| **非同步管線故障難以定位** | 沙箱、推論、訓練多階段並行時，錯誤會跨 worker 傳播。 | 為每條軌跡賦予唯一 trace ID，並在 Live UI 中串接各階段日誌；設定 termination-aware filtering，避免失敗 rollout 進入訓練批次。 |
| **冷啟動延遲拖慢訓練吞吐** | 頻繁建立沙箱會造成大量等待時間。 | 啟用 Nydus 冷啟動映像檔快取與映像檔掛載，並預熱常用執行環境。 |
| **過度擬合訓練任務** | 模型可能學會針對特定驗證器模式作弊，而非真正修復問題。 | 保留獨立驗證集（如 SWE-bench Verified）、定期評估、並監控軌跡長度與工具呼叫模式是否異常。 |

### 與其他技術的整合建議

- **CI/CD 系統**：將 LEGO-RL 訓練後的智慧體作為程式碼審查或 issue 自動分派的後端服務，透過 adapter 接收 Git webhook，並在沙箱中執行修復後回傳 patch 與測試結果。
- **現有 LLM 推論平台**：若已部署 vLLM、TGI 或自研推論伺服器，只需在前方加上 in-process proxy 與負載平衡器，無需替換整個推論層。
- **可觀測性堆疊**：將 LEGO-RL 的 Live UI 與既有 Prometheus / Grafana / ELK 整合，把軌跡層級指標（resolve rate、沙箱失敗率、獎勵分佈）匯出到企業監控看板。
- **資料版本控制**：使用 DVC 或類似工具管理程式碼庫快照、Docker 映像檔版本與訓練軌跡，確保每次實驗可重現。
- **模型倉庫與 MLOps**：將訓練完成的權重註冊到 MLflow、W&B 或自有模型倉庫，並與 A/B 測試平台對接，逐步灰度上線新策略。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦於「為什麼需要框架原生強化學習」以及 LEGO-RL 的三個核心支柱：忠實最佳化、可靠執行與可觀測訓練。不必一開始深入 MoE 路由或分散式訓練細節，而是把本文視為理解「程式設計智慧體如何從完整軌跡中學習」的入門地圖，並搭配 SWE-bench 與 OpenHands SDK 的官方文件建立直覺。

**AI 工程師**  
請重點閱讀 in-process LLM proxy、沙箱編排與非同步管線設計，這些是將論文轉化為可運行系統的關鍵。實作時應優先驗證 rollout-訓練機率相關性與 MoE 路由 replay，並預留監控與故障恢復機制；同時注意 adapter 的輕量性，避免為了整合而破壞原生框架的行為。

**研究人員**  
本文的貢獻在於把「不修改智慧體控制流程」與「可擴展策略梯度訓練」結合起來。建議關注 harness-native fidelity 與 trainer-side log-probability recomputation 的理論對齊條件，以及 stage-wise defense 對獎勵訊號偏差的影響；未來可延伸探討多框架聯合訓練、獎勵塑形或更強大的反駭取理論保證。

**產品經理**  
請把 LEGO-RL 理解為一個能讓現有程式設計智慧體「持續從真實執行回饋中學習」的基礎設施。評估導入時，優先考量資料品質、驗證器可信度與運維成本；本框架的價值在於提升 resolve rate 的同時保留既有智慧體工作流程，適合做為技術債清理、自動化修復或開發者輔助工具的長期投資。
