# 程式碼代理基準測試應符合其使用者的任務流程

**原文標題：** Coding-Agent Benchmarks Should Match Their Users' Task Flows  
**作者：** Igor Slinko、Yaroslav Golubev、Sergey Titov  
**發布日期：** 2026-10-07  
**HF 連結：** [https://huggingface.co/papers/2610.09633](https://huggingface.co/papers/2610.09633)  
**arXiv：** [https://arxiv.org/abs/2610.09633](https://arxiv.org/abs/2610.09633)  

---

## ⚡ TL;DR

現有程式碼代理基準測試多源自議題，無法反映真實使用者多類型任務切換的互動流程。
作者提出SWE-TaskFlow，透過提示拆分與可驗證問答，將議題任務轉為符合目標任務流程的多輪軌跡。
在700個SWE-Bench Pro任務先導中，循序求解成本翻倍但解決率未穩定，證明互動協定是關鍵變數。

---

## 摘要翻譯

程式碼代理的評估通常力求盡可能真實。本研究收集了 JetBrains 整合開發環境中真實軟體工程師的 4,782 個代理會話，我們將其命名為生產環境會話（Production Sessions）。由於我們的研究對象是互動式代理，我們研究了至少包含三則使用者訊息的會話（佔樣本的 33%）。這些長會話與議題衍生基準任務（Issue-derived Benchmark Tasks）在兩個方面有所不同：(i) 使用者請求涵蓋更廣泛的任務類型組合——關於專案程式碼的問題、規劃、審查、重構、執行——以及 (ii) 使用者在整個會話過程中會在這些類型之間切換。三個公開互動語料庫（Interaction Corpora）的長會話樣本呈現出明顯不同的任務流程（Task Flows，即會話長度、任務類型及類型間轉換的分布），因此沒有任何單一的互動分布是普遍真實的：基準測試應明確指定目標使用情境（Target Use Case），並根據其測量結果進行校準（Calibration）。我們提出了 SWE-TaskFlow，這是一種轉換任何議題衍生基準測試的方法：它保留了已驗證的任務和測試，同時透過提示拆分（Prompt Splitting）和可驗證的程式碼庫問答（Verifiable Repository QA）將互動引導至目標任務流程，並透過任務流程對齊分數（TaskFlow Alignment Score, TFAS）在生成的軌跡中進行選擇。在 700 個 SWE-Bench Pro 任務的先導研究中，以循序方式分多步求解任務會使代理成本約增加一倍，但解決率（Resolve Rate）並無穩定變化：互動協定（Interaction Protocol）本身是評估的一個重要面向。

### 核心貢獻（3～5點）
- **真實互動資料的規模化分析**：蒐集並分析了 4,782 個來自 JetBrains 整合開發環境的真實軟體工程師代理會話，揭示生產環境中互動式代理的使用模式。
- **任務流程的異質性發現**：證明長會話中的使用者請求橫跨多元任務類型（提問、規劃、審查、重構、執行），且會在類型間動態切換，與議題衍生基準任務的單一任務假設形成鮮明對比。
- **SWE-TaskFlow 方法**：提出一套可將既有議題衍生基準測試轉化為符合特定任務流程的通用框架，結合提示拆分、可驗證的程式碼庫問答與任務流程對齊分數（TFAS），兼顧任務可驗證性與互動真實性。
- **互動協定作為評估變數**：在 SWE-Bench Pro 的先導研究中，證實互動協定本身會顯著影響代理成本（約加倍）卻未必提升解決率，凸顯互動設計應成為基準測試評估的核心維度。

### 適合對象
從事程式碼代理（coding agent）研究與開發的學者與工程師，特別是關注基準測試設計、評估方法論、大型語言模型代理在軟體工程任務中的真實部署表現，以及互動式 AI 系統校準的研究團隊與產品負責人。

## 深度分析

#### 方法論解析

本論文提出了一套系統性的方法論框架，旨在解決程式碼代理（coding agent）基準測試與真實使用者互動模式之間的系統性落差。整體方法可拆解為三個相互支撐的核心組件。

**第一組件：任務流程（Task Flow）的形式化定義。** 作者將一個語料庫層級的任務流程定義為三元組 (PL, PT, PR)，分別對應：(i) 會話長度分布（session lengths distribution）、(ii) 訊息層級的任務類型分布（task types distribution over messages）、(iii) 相鄰訊息之間的有向轉換分布（directed transitions between adjacent messages）。此定義的關鍵洞見在於，僅靠任務類型的直方圖會遺失順序資訊，而轉換分布保留了「使用者如何在會話中切換意圖」的時序結構，這正是現有議題衍生基準（issue-derived benchmarks）所忽略的維度。

**第二組件：任務類型分類器（task type classifier）。** 作者採用開放權重大型語言模型（open-weight LLM）將每則使用者訊息獨立分類至 16 種類型之一，涵蓋錯誤修復（bug fix）、新功能（new feature）、解釋（explain）、規劃（planning）、程式碼審查（code review）、執行（execution）、重構（refactoring）等。分類流程經過人工審查迭代，且三個獨立分類器模型在 76.1% 的標籤上達成一致，提供了穩健性檢驗（robustness check）。同一分類管線被一致地應用於生產環境會話（Production Sessions）、公開語料庫與基準提示，確保所有分布處於可比較的基礎上。

**第三組件：SWE-TaskFlow 轉換方法。** 此方法將已驗證的 SWE 任務（verified SWE tasks）轉化為可重播的多輪軌跡候選（replayable multi-turn trajectory candidates），同時保留原始需求與測試。其核心包含兩種資料增強（dataset augmentation）策略：

1. **提示拆分（prompt splitting）**：針對議題式提示的過度規格化（overspecification）問題——SWE-bench 風格的議題將目標、脈絡、限制、甚至實作方法一次性陳述完畢，而真實使用者傾向於漸進式揭露需求。拆分器將單一議題轉為 K=3 個有序、自足的使用者輪次（相鄰部分可合併），並須滿足四項約束：保留所有原始需求、不引入新需求、保留技術細節逐字不變、每個輪次在先前輪次留下的程式碼庫狀態下皆可執行。通過檢查的議題保留為多輪，未通過者維持單輪。在 731 個公開 SWE-Bench Pro 任務中，700 個通過拆分與評估脈絡檢查。

2. **可驗證的程式碼庫問答（verifiable repository QA）**：從成功解決原始議題的代理軌跡與即時程式碼庫狀態中挖掘 0 至 3 個可驗證的問題，注入基準所缺乏的「解釋」意圖。每個候選問題皆附帶隱藏參考答案，且必須滿足：在程式碼庫中可被回答、在議題修補程式（patch）前後皆有效、不洩漏解法、並通過在乾淨程式碼庫副本中執行的可執行證明腳本（proof script）驗證。問題的擺放位置（議題輪次之前、之間或之後）決定了哪些轉換會出現，兩種增強合計產生每任務 1 至 6 個使用者輪次，其中至少 3 輪者構成長會話切片。

**第四組件：任務流程對齊分數（TaskFlow Alignment Score, TFAS）。** 為使「更接近目標任務流程」成為可優化的明確指標，作者提出 TFAS，計算目標分布 Pk 與基準分布 Qk 之間在會話長度分箱（bins）、任務類型、轉換三個維度上的對齊程度，作為從生成軌跡中選擇最佳候選的依據。

**第五組件：逐輪評估設計（per-turn evaluation design）。** 不同於傳統的單一終端分數（terminal score），此設計使單一任務產生多個可驗證訊號（verifiable signals），將互動協定（interaction protocol）本身提升為一項評估變數（evaluation variable）。

#### 實驗數據解讀

**生產環境會話的統計特徵。** 資料集包含 4,782 個代理會話（agent sessions），約 14,000 則使用者訊息，來自 JetBrains 整合開發環境（JetBrains IDEs）使用者的日常工作流程。會話長度分布呈現高度偏斜：50.9% 的會話僅含單一使用者訊息，而 33% 包含至少三則訊息（即長互動切片，long-interaction slice）。第 75 百分位數為 3 則訊息，第 90 百分位數為 8 則訊息，顯示真實使用中存在顯著的長尾互動模式。首則訊息平均 30.7 字，後續位置則降至 16–19 字，暗示使用者傾向於以較詳細的初始請求開啟會話，後續則以簡短追問延續。

**任務類型分布的關鍵落差。** 在生產環境會話中，錯誤修復佔 25.9%、新功能佔 18.9%，兩者合計僅約 44.8%，遠低於 SWE-Bench Pro 中的 93.8%（54.7% 功能 + 39.1% 錯誤修復）。其餘超過半數的訊息涉及解釋專案程式碼（6.1% 解釋請求）、一般程式設計問答（9.7% 問題）、規劃、審查、重構、執行等多元意圖。更關鍵的是，解釋意圖在會話的每個位置上皆保持常見，凸顯了議題衍生基準在「理解既有程式碼」此一核心使用者需求上的結構性缺失。

**公開語料庫的任務流程差異。** 作者將同一分類管線應用於 SWE-chat、SpecStory、DataClaw 三個公開互動語料庫（interaction corpora）的長會話樣本，結果顯示三者的任務流程在意圖分布與轉換模式上皆與生產環境會話及彼此之間存在可見差異。此結果的意涵深遠：不存在單一通用的「真實」互動分布，目標使用情境（target use case）必須在其自身場景中測量。

**SWE-Bench Pro 先導實驗的關鍵發現。** 在 700 個 SWE-Bench Pro 任務的先導研究（pilot study）中，作者發現以循序方式（sequentially）解決任務——即按拆分後的多輪順序逐步執行——相較於一次性解決，代理成本（agent cost）約增加一倍，而解決率（resolve rate）則未呈現穩定變化。此結果的解讀重點在於：互動協定本身是評估的重要維度，僅改變訊息的呈現方式與順序即可顯著影響資源消耗，卻未必帶來效能提升，凸顯了「如何與代理互動」與「代理能力本身」是兩個應被獨立考量的評估面向。

**分類器一致性指標。** 三個獨立分類器模型在 76.1% 的標籤上達成一致，雖非完美但提供了合理的穩健性邊界，特別是在處理模糊或混合意圖的訊息時。

#### 與現有研究的比較

**相對於議題衍生基準的定位。** SWE-bench 及其後續 SWE-Bench Pro、SWE-rebench、DeepSWE 等基準皆採用「一份詳細議題、評分一個最終修補程式」的範式，其基礎設施與測試極具價值，但互動層（interaction layer）——即代理接收的使用者訊息及其順序——衡量的是「從預先規格（upfront specification）進行實作」而非「適應跨會話展開的需求（adaptation to requirements unfolding across a session）」。SWE-TaskFlow 的核心貢獻在於保留這些基準的驗證基礎設施（程式碼庫狀態、執行環境、測試型驗證器），同時重新生成互動層，使其對齊至測量所得的目標任務流程。

**相對於其他轉換方法的差異化。** 附錄 D 提及的相關轉換方法亦將軌跡在推論前固定以實現精確可重播性（exact replayability），但 SWE-TaskFlow 的差異化在於將軌跡形狀校準至測量所得的任務流程，而非臨時選擇（ad hoc）。此區別使 SWE-TaskFlow 從「產生任意多輪版本」提升至「產生對齊特定使用者族群的多輪版本」。

**相對於公開互動語料庫的互補性。** SWE-chat、SpecStory、DataClaw 等語料庫提供了真實互動資料，但其任務流程各異且未附帶可驗證的測試基礎設施。SWE-TaskFlow 的優勢在於結合了議題衍生基準的驗證嚴謹性與真實互動的分布特性。

**限制與未涵蓋範圍。** 此方法目前僅在 SWE-Bench Pro 上實例化，K 值固定為 3，且僅針對 700 個通過檢查的任務。分類器的 76.1% 一致率雖合理但仍有改善空間，特別是在處理混合意圖或領域特定術語時。此外，提示拆分器依賴大型語言模型生成，其輸出可能引入細微偏差，需以四項約束進行把關。任務流程的測量本身受限於 JetBrains IDEs 使用者族群，未涵蓋命令列工具、網頁介面或其他開發環境中的互動模式。

#### 可重現性評估

**資料集公開性。** 作者明確聲明所有生成的任務以單一公開資料集（public dataset）形式釋出，詳見附錄 E。此資料集包含經 SWE-TaskFlow 轉換後的 700 個 SWE-Bench Pro 任務，每個任務附帶拆分後的多輪提示、可驗證的程式碼庫問答題目、隱藏參考答案與可執行證明腳本。

**方法管線可重現性。** 分類器採用開放權重大型語言模型（open-weight LLM），相對於封閉 API 提供了更高的可重現性。任務類型分類法（taxonomy）、分類提示（prompt）與穩健性檢查皆記錄於附錄 A，使其他研究者可在自身資料上重現分類流程。問題生成方法論（generation methodology）與完整管線記載於附錄 E，涵蓋從軌跡挖掘、問題生成到證明腳本驗證的全流程。

**評估設計的可重現性。** 逐輪評估設計使每個任務產生多個可驗證訊號，評審者可獨立驗證每個輪次的正確性，而非僅依賴單一終端分數。TFAS 的計算方式明確，使基準建構者可量化其與目標任務流程的對齊程度。

**限制因素。** 原始生產環境會話資料因隱私考量僅以匿名化聚合統計形式分析，無法公開釋放，這限制了在其他 IDE 或開發環境中重現測量的可能性。代理軌跡的生成依賴特定的大型語言模型，其行為可能隨模型版本而變化，影響可重現性。此外，700 個任務的規模相對於原始 SWE-Bench Pro 的 731 個略小，31 個被排除任務的具體原因與其代表性影響需進一步檢視。

#### 未來研究方向

**多目標使用情境的基準建構。** 本論文的立場——「不存在通用真實的程式碼代理基準」——開啟了為不同使用者族群（如初學者、資深工程師、維護者、新專案開發者）建構專屬基準的可能性。未來研究可針對命令列工具、網頁介面、團隊協作環境等不同場景測量任務流程，並產生對應的 SWE-TaskFlow 變體。

**動態 K 值與自適應拆分。** 當前 K=3 的固定設定可能不適用於所有任務類型。未來可探索根據議題複雜度、任務類型或目標使用者的偏好動態決定輪次數，甚至允許代理在評估過程中請求更多資訊，模擬真實的「需求展開」過程。

**更細粒度的任務類型分類法。** 16 種類型已涵蓋主要意圖，但可能未捕捉到細粒度的差異（如「解釋」可進一步分為「解釋 API 用法」、「解釋架構決策」、「解釋錯誤訊息」）。更細的分類法可能揭示更精確的轉換模式，並支援更針對性的基準設計。

**跨領域驗證。** 將 SWE-TaskFlow 應用於 SWE-rebench、DeepSWE 等其他議題衍生基準，檢驗方法的泛化能力。同時，將其擴展至非軟體工程領域的代理任務（如資料分析、科學計算、創意寫作），探索任務流程概念在其他領域的適用性。

**互動協定作為優化變數。** 先導研究顯示互動協定本身影響代理成本，未來可探索將「如何拆分議題」、「如何擺放問答題目」作為可優化的變數，甚至訓練專門的「互動設計器」以最大化特定指標（如 TFAS 對齊度、代理效率或最終解決率）。

**長期縱貫研究。** 當前資料為橫斷面快照，未來可進行縱貫研究，追蹤同一使用者在數週或數月內的任務流程演變，檢驗使用者如何隨經驗積累調整與代理的互動模式，進而設計能適應使用者成長的基準。

**人類與代理協作的真實測量。** 將任務流程測量從「使用者與代理的對話」擴展至「使用者、代理與其他工具（如版本控制、測試框架、文件系統）的多邊互動」，更全面地捕捉真實開發環境中的協作動態。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文指出，現有的程式碼代理基準測試（如 SWE-Bench Pro）大多源自 GitHub issue，屬於「議題衍生」形式，僅包含單一最終修補的評估，無法反映真實軟體工程師與代理互動的情境。作者透過分析 JetBrains IDE 中蒐集的 4,782 個生產環境會話，發現真實使用者會在單一會話中混合提出解釋、規劃、審查、重構、執行等多種任務類型，並在類型間不斷轉換。因此，核心問題在於：現有基準測試的「互動層」與真實使用者的任務流程之間存在嚴重落差，導致評估結果無法預測實際部署表現。

**Q2：為什麼現有的議題衍生基準測試無法捕捉真實情境？**
A：議題衍生基準測試（如 SWE-bench、SWE-Bench Pro、SWE-rebench、DeepSWE）將一個完整的 issue 一次性交付給代理，並僅以最終修補程式是否通過測試作為評分依據。然而在 SWE-Bench Pro 中，新功能（54.7%）與錯誤修復（39.1%）合計佔了 93.8% 的任務，幾乎完全忽略了 EXPLAIN（解釋專案程式碼）、QUESTION（一般提問）、PLANNING（規劃）、REVIEW（審查）、REFACTORING（重構）、EXECUTION（執行）等真實常見意圖。此外，這類基準測試假設使用者一開始就提供完整規格說明，忽略了需求在多輪對話中逐步展開的真實過程。

**Q3：為什麼讓基準測試對齊真實任務流程如此重要？**
A：作者在 700 個 SWE-Bench Pro 任務上的先導研究顯示，將任務以多步驟循序求解會使代理成本約翻倍，卻無法穩定提升解決率，這意味著「互動協定本身」是一個被低估的關鍵評估變數。若基準測試的互動模式與目標使用者的工作流程不符，不僅會高估或低估代理能力，也無法指導開發者優化真實部署中最常被觸及的多輪互動行為。因此，讓基準測試合其使用者的任務流程，是確保評估結果具備外部效度（external validity）與實用價值的必要條件。

**Q4：SWE-TaskFlow 的核心方法是什麼？**
A：SWE-TaskFlow 是一種「轉換」方法，將既有議題衍生基準（如 SWE-Bench Pro）中的已驗證任務與測試保留下來，僅重新生成其「互動層」。具體而言，它採用兩種增強手段：「提示拆分」（prompt splitting）將一個完整 issue 拆成 K=3 個有序且各自可獨立行動的使用者訊息，而「可驗證的程式碼庫問答」（verifiable repository QA）則在任務中注入 0 至 3 個關於程式碼庫行為的可驗證問題，以補上議題衍生基準缺乏的 EXPLAIN 意圖。這兩種增強組合後，每個任務可產生 1 至 6 輪使用者訊息，其中至少 3 輪的候選即構成「長會話切片」。

**Q5：本研究最重要的創新是什麼？**
A：本研究最重要的創新在於提出「任務流程對齊分數」（TaskFlow Alignment Score, TFAS），將「更貼近目標任務流程」這件事形式化為可量測、可最佳化的指標。TFAS 透過比較目標分布與基準分布在會話長度（PL）、任務類型（PT）、類型間轉換（PR）三個維度上的差異，使基準建構者能夠在多個生成的軌跡候選中系統性地選擇最對齊目標的版本。此外，作者也提出「逐輪評估設計」（per-turn evaluation design），讓單一任務產生多個可驗證訊號，而非僅有單一終端分數，這從根本上改變了代理評估的範式。

**Q6：在設計 SWE-TaskFlow 時有哪些重要的設計選擇？**
A：設計上的關鍵選擇包括：（1）保留原始已驗證任務的程式碼庫狀態、執行環境與測試，避免重複投資；（2）提示拆分器必須嚴格遵守「保留所有原始需求、不引入新需求、保留技術細節原文、每輪在當前程式碼庫狀態下皆可行動」四項檢查，未通過者退回單輪；（3）可驗證問題必須來自實際解決該 issue 的代理軌跡與當前程式碼庫狀態，並具備隱藏參考答案與可在乾淨程式碼庫中執行的證明腳本；（4）問題擺放位置（拆分之「前」、「之間」、「之後」）決定了哪些類型間轉換會出現，藉此可調控任務流程的形狀。

**Q7：本研究使用了哪些基準測試與資料集？**
A：本研究的核心資料是來自 JetBrains IDE 使用者的 4,782 個生產環境會話（Production Sessions），其中 33% 為長會話（至少 3 則使用者訊息）。在方法驗證上，作者以 SWE-Bench Pro 的 700 個任務作為先導研究對象（原始 731 個中保留 700 個）。此外，作者也將相同的分類流程套用於三個公開互動語料庫——SWE-chat、SpecStory 與 DataClaw——以驗證「不同產品的任務流程彼此不同」這項主張。

**Q8：本研究最重要的實驗結果為何？**
A：最重要的實驗結果是：在 700 個 SWE-Bench Pro 任務上，將任務以多步驟循序求解會使代理成本約翻倍，卻無法帶來穩定的解決率提升。這項結果直接證明了「互動協定本身」是一個真實且重要的評估變數——改變任務的呈現方式（單輪 vs. 多輪）會顯著影響成本與行為，即便最終修補結果相近。此外，作者也展示了不同公開互動語料庫呈現出明顯不同的任務流程分布，證實「沒有單一通用的真實互動分布」這項核心立場。

**Q9：本研究是否進行了消融實驗或對齊分析？**
A：雖然全文未呈現完整的消融表格，但 TFAS 本身即是用於在多個生成的軌跡候選間進行選擇的對齊機制，扮演了類似消融指標的角色。透過 TFAS，作者能夠量化「提示拆分」與「可驗證問題擺放」對任務流程形狀的影響，並據此挑選最貼近目標任務流程的版本。此外，作者也針對分類器的穩健性進行了檢查：三個分類器模型在 76.1% 的標籤上達成一致，顯示分類流程具備一定程度的可靠性。

**Q10：SWE-TaskFlow 在哪些實際情境中特別有用？**
A：SWE-TaskFlow 特別適用於以下情境：（1）為特定 IDE（如 JetBrains 系列、VS Code）或特定企業內部開發流程量身打造基準測試時，可直接以該環境蒐集的生產環境會話作為校準目標；（2）當既有議題衍生基準的測試基礎建設完善、但互動層與目標使用者脫節時，可低成本地將其轉換為多輪版本；（3）研究人員想比較不同互動協定（如先解釋再實作 vs. 直接實作）對代理行為的影響時，可作為受控實驗的生成工具。

**Q11：本研究對「產品」層面的考量為何？**
A：本研究最重要的產品層面訊息是：沒有任何單一互動分布是「普遍真實」的。SWE-chat、SpecStory、DataClaw 與 JetBrains 生產環境會話各自呈現出截然不同的任務流程，這意味著基準建構者必須明確聲明其目標使用情境，並以該情境下的實測分布作為校準依據。對產品團隊而言，這意味著「複製別人的基準」並不能保證評估結果適用於自家使用者，必須投入資源測量自家產品的任務流程，才能建構出具備預測力的評估體系。

**Q12：本研究對程式碼代理評估領域的整體影響是什麼？**
A：本研究的影響在於將代理評估的焦點從「單一終端分數」轉向「多輪可驗證訊號」，並把「互動協定」提升為與模型能力同等重要的評估維度。這促使未來的基準測試合約必須包含三項內容：目標使用情境的明確聲明、對應任務流程的實測數據、以及與該流程對齊的互動層設計。長期而言，這將推動領域從「誰在 SWE-bench 上分數最高」轉向「誰在使用者的真實工作流程中表現最好」，使評估結果與實際部署價值更緊密連結。

**Q13：本研究承認哪些限制？**
A：本研究承認的限制包括：（1）分類器在三個模型間僅達成 76.1% 的一致率，雖然經過人工審查迭代，仍可能存在標籤噪音；（2）SWE-Bench Pro 的 731 個任務中僅 700 個通過拆分與評估環境檢查，剩餘 31 個被排除，可能引入選擇偏差；（3）先導研究僅針對 700 個任務，樣本規模有限；（4）生產環境會話僅以匿名聚合統計形式分析，無法公開個別會話細節，限制了可重現性；（5）TFAS 假設三個維度（長度、類型、轉換）的重要性相等，但實際上不同使用情境可能賦予不同權重。

**Q14：本研究可能面臨哪些失敗案例或邊界情況？**
A：可能面臨的失敗案例包括：（1）某些 issue 過於簡單或過於耦合，無法在不遺失資訊的前提下拆分為多輪，導致退回單輪處理；（2）可驗證問題若設計不當，可能洩漏解題線索或無法在乾淨程式碼庫中通過證明腳本；（3）對於高度領域特定或冷門的程式碼庫，代理軌跡可能不足以產生有意義的 EXPLAIN 問題；（4）若目標任務流程本身測量不準（例如分類器對該領域的標籤不準），則 TFAS 校準反而會引入偏差；（5）循序求解的成本翻倍現象可能因代理架構不同而改變，不應直接外推至所有代理。

**Q15：本研究未來可以朝哪些方向延伸？**
A：未來可延伸的方向包括：（1）將 SWE-TaskFlow 推廣至其他議題衍生基準（如 SWE-rebench、DeepSWE）以及其他領域（如資料科學、機器學習工程）；（2）發展自動化、可擴展的任務流程測量流程，降低企業內部部署的門檻；（3）探索 TFAS 中三個維度的最佳權重組合，或發展任務流程相似度的替代度量；（4）研究不同互動協定對代理訓練（如 RLHF、RLAIF）的影響，將任務流程對齊從評估階段延伸至訓練階段；（5）建立跨產品的任務流程本體論（ontology），使不同基準之間能進行有意義的比較與轉換。

## 實務應用指南

### 適用場景

1. **IDE 內建 AI 程式碼助手評估**：當 JetBrains、VS Code 等 IDE 廠商要評估自家整合的 AI 代理時，可直接採用本文的「生產環境會話」分類法，將自家使用者會話標註為 16 種任務類型，再以 TFAS 校準基準測試的互動分布，避免「在實驗室很強、在使用者桌機上很弱」的落差。

2. **企業內部程式碼代理基準建置**：金融、製造等產業的內部開發團隊若想評估私有部署的程式碼代理，可先用本文方法分析自家 Jira/GitLab 議題與聊天記錄的 Task Flow，再將 SWE-Bench Pro 等公開基準透過 SWE-TaskFlow 轉換成符合內部工作流的版本，使評估結果與實際生產情境對齊。

3. **多輪互動代理 vs. 單輪代理的對標**：當團隊要在「一次給完整規格」與「逐步揭露需求」兩種互動協定下比較 Claude Code、Cursor、Aider 等代理時，可使用 SWE-TaskFlow 產生的多輪軌跡，量化互動協定本身對解決率與成本的影響（本文實測顯示成本約翻倍但解決率未穩定提升）。

4. **程式碼代理微調資料生成**：訓練或微調開源模型（如 DeepSWE、Qwen-Coder）時，可將 SWE-TaskFlow 產生的多輪軌跡作為 SFT 資料，讓模型學會處理「先解釋、再規劃、再實作、再審查」的真實對話節奏，而非只會從單一議題直衝修補程式。

5. **學術研究中的互動變數控制**：研究「對話風格對代理表現影響」的學者，可把 SWE-TaskFlow 當作受控實驗工具——固定任務與測試，僅操縱任務類型序列與訊息長度，系統性地分離「任務難度」與「互動協定」兩個變數。

### 實作前置條件

**資料前置條件**
- 至少數千筆真實代理會話（本文使用 4,782 筆），需含使用者訊息、代理回應、最終程式碼變更；建議從 IDE 遙測、企業 Slack/Teams 整合頻道、或 SpecStory、SWE-chat、DataClaw 等公開互動語料庫取得。
- 一組已驗證的議題衍生基準任務（推薦 SWE-Bench Pro 731 題，或 SWE-bench Verified、SWE-rebench），需含可執行的測試套件與乾淨的程式碼庫快照。
- 每個任務對應的「黃金解答軌跡」（golden trajectory），用於挖掘可驗證的程式碼庫問答題目。

**計算前置條件**
- 一台具備 80GB 以上 VRAM 的 GPU（A100/H100 等級），或可調用的雲端 LLM 推理服務，用於執行 16 類任務分類器、提示拆分器、QA 題目生成器。
- 沙箱化執行環境（Docker 容器或 Firecracker microVM），用於跑「proof script」驗證生成的問答題目在乾淨程式碼庫上可被正確回答。
- 預估成本：對 700 個 SWE-Bench Pro 任務做完整 SWE-TaskFlow 轉換，預估需要數百萬 token 的 LLM 呼叫與數小時的容器執行時間。

**技能前置條件**
- 熟悉 Python 與 LLM 應用開發（LangChain、LlamaIndex 或自建 prompt pipeline）。
- 具備軟體工程背景，能讀懂 diff、理解測試覆蓋率、撰寫 proof script。
- 基本的統計知識（分布比較、Jensen-Shannon 散度、Kolmogorov-Smirnov 檢定），用於計算 TFAS。
- 了解 SWE-bench 評估管線的執行細節（環境安裝、測試過濾、patch 套用）。

### 實作步驟建議

1. **步驟一：收集並清洗生產環境會話**
   從目標產品（IDE、CLI 工具、Web IDE）收集至少三個月的代理會話，過濾掉少於 3 則使用者訊息的短會話（本文定義的「長互動切片」），保留使用者側訊息與最終程式碼狀態。務必做去識別化處理，移除公司名稱、API 金鑰、個人資訊。

2. **步驟二：建立任務類型分類器**
   採用本文附錄 A 的 16 類分類法（bug fix、new feature、explain、planning、review、refactor、execution、question 等），用開源 LLM（如 Qwen2.5-Coder-32B、Llama-3.3-70B）對每則使用者訊息獨立標註。建議至少用三個不同模型投票，並以人工抽樣 200 筆驗證一致性（本文達到 76.1% 一致率）。

3. **步驟三：測量目標 Task Flow**
   計算三個分布：(PL) 會話長度分布（以訊息數分箱）、(PT) 任務類型分布、(PR) 相鄰訊息的類型轉換矩陣。將結果與 SWE-Bench Pro 的 Task Flow 並排比較，量化「議題衍生基準」與「真實使用者」之間的差距（本文顯示新功能與錯誤修復在基準中佔 93.8%，在生產環境僅約 45%）。

4. **步驟四：套用提示拆分（Prompt Splitting）**
   對每個議題衍生任務，用 LLM 將原始議題拆成 K=3 個有序、自包含的使用者輪次（可合併相鄰部分）。拆分器必須遵守四個約束：保留所有原始需求、不引入新需求、保留技術細節（檔名、行號、錯誤訊息）逐字原文、每輪在當前程式碼庫狀態下可執行。對 731 題 SWE-Bench Pro 跑一遍，預期約 700 題通過檢核。

5. **步驟五：挖掘可驗證的程式碼庫問答（Repository QA）**
   對每個任務，先讓代理跑出黃金軌跡，再從軌跡與程式碼庫狀態中挖掘 0–3 個可驗證問題（例如「在套用 patch 前，`auth.py` 第 42 行會回傳什麼？」）。每題需附隱藏參考答案，並通過四項檢查：可從程式碼庫回答、套用 patch 前後答案不變、不洩漏解法、在乾淨容器中執行 proof script 通過。

6. **步驟六：組裝多輪軌跡並計算 TFAS**
   將拆分後的議題輪次與 QA 問題按不同順序組合（QA 可置於議題前、中、後），產生多個候選軌跡（每任務 1–6 輪）。對每個候選計算 TFAS：TFAS = Σ wₖ · D(Pₖ ‖ Qₖ)，其中 D 為分布距離度量（建議用 JS 散度），wₖ 為長度、類型、轉換三項的權重。選出 TFAS 最高的軌跡作為該任務的最終互動層。

7. **步驟七：執行評估並分析互動協定變數**
   用最終軌跡評估目標代理，記錄每輪的解決率、token 成本、延遲。對比「單輪解完整議題」與「多輪循序解」的差異——本文發現成本約翻倍但解決率未穩定提升，這個結論本身就是評估報告的關鍵洞察。

8. **步驟八：釋出與持續校準**
   將生成的軌跡、QA 題目、proof script、TFAS 計算程式碼一併釋出為公開資料集（本文附錄 E 詳述）。每季重新跑一次分類器與 Task Flow 測量，確保基準不會因使用者行為漂移而失真。

### 潛在風險與注意事項

**風險一：隱私與合規**
- *風險*：生產環境會話可能包含公司內部邏輯、客戶資料、API 金鑰。
- *緩解*：在收集階段就做去識別化與敏感欄位遮罩；採用本地部署的開源 LLM 做分類，避免資料外流；遵循 GDPR、CCPA 等地區法規，必要時取得使用者明確同意。

**風險二：分類器漂移**
- *風險*：LLM 分類器會隨模型版本更新而改變標註行為，導致跨季度 Task Flow 比較失真。
- *緩解*：鎖定分類器模型版本與 prompt 模板；定期用人工標註的「錨定集」（anchor set）驗證一致性；若漂移超過閾值（如 5%），重新校準。

**風險三：QA 題目洩漏解法**
- *風險*：挖掘出的問題可能在無意中提示代理該怎麼修補，破壞評估效度。
- *緩解*：嚴格執行「不洩漏解法」檢查——問題不應包含修補方向、檔案修改建議、錯誤根因猜測；用另一個獨立 LLM 當「紅隊」嘗試從問題推導解法，若成功則淘汰該題。

**風險四：成本失控**
- *風險*：多輪互動使 token 消耗倍增（本文實測約 2 倍），對大規模評估不友善。
- *緩解*：設定每任務的 token 上限；對 QA 問題使用較小的模型評分；考慮用蒸餾模型預篩選，明顯無法通過的早期輪次直接終止。

**風險五：任務流失**
- *風險*：拆分與 QA 生成可能淘汰部分任務（本文 731 題中 31 題未通過檢核），縮小可用基準規模。
- *緩解*：保留被淘汰任務的單輪版本作為對照組；分析淘汰原因，若為拆分器過嚴則調整 prompt；若為議題本身不適合多輪，則標註後從多輪評估中排除。

**風險六：互動分布過度擬合**
- *風險*：把基準完全對齊某個產品的 Task Flow，可能讓基準在其他產品上失效。
- *緩解*：明確聲明「目標使用情境」（target use case）；同時保留原始議題版本；提供 TFAS 計算工具讓使用者自行校準到自己的分布。

### 與其他技術的整合建議

**與 SWE-bench 評估生態系整合**
SWE-TaskFlow 是 SWE-Bench Pro 的「互動層外掛」，可與現有的 Docker 評估管線（swebench-docker、swe-bench-evaluator）無縫銜接。建議將 SWE-TaskFlow 產生的多輪軌跡以 JSONL 格式輸出，餵給支援多輪的代理框架（如 SWE-agent、OpenHands），評估結果再匯入 SWE-bench 的排行榜格式。

**與 IDE 遙測系統整合**
JetBrains、VS Code 等 IDE 可在遙測 SDK 中加入「任務類型」標記欄位，由代理外掛在使用者送出訊息時自動呼叫本地分類器標註，彙整到中央分析平台。這樣 Task Flow 測量就能從「一次性研究」變成「持續產品指標」，每週自動更新。

**與 LLM 評估框架整合**
TFAS 可整合到現有的 LLM 評估平台（如 LangSmith、Weights & Biases、Promptfoo）作為自訂指標。將 JS 散度計算封裝成 plugin，使用者在跑評估時可即時看到「當前基準與目標分布的對齊程度」，作為基準品質的健康度儀表板。

**與程式碼代理框架整合**
OpenHands、SWE-agent、AutoCodeRover 等開源框架可內建 SWE-TaskFlow 模式：在 `agent.run()` 時接受 `task_flow` 參數，自動按多輪軌跡逐步揭露訊息，並在每輪收集可驗證訊號。這讓框架使用者能直接比較「單輪衝刺」與「多輪對話」兩種模式。

**與企業知識管理整合**
企業可將內部 Jira/Linear 議題透過 SWE-TaskFlow 轉換後，餵給程式碼代理做「乾跑」（dry run）評估，預測代理在真實開發流程中的表現，再決定是否導入。這比單純看 SWE-bench 分數更能預測實際投資回報率。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀第 1 節的兩個觀察（使用者任務比基準多元、會在會話中切換任務類型），這兩個直覺就能幫你理解「為什麼不能只看單一議題解題率」。第 2 節的 Task Flow 定義（長度、類型、轉換三件式）值得記住，未來看任何代理評估論文都能用這個框架檢視。第 3 節的具體方法可以先跳過，之後有需要再回頭看提示拆分與 QA 挖掘的細節。

**給 AI 工程師**：重點讀第 3 節的 SWE-TaskFlow 實作細節，特別是「提示拆分的四個約束」與「QA 題目的四項檢查」，這兩個把關機制直接決定了生成品質。附錄 E 的完整 pipeline 是你複製實作的藍圖。實務上建議先在小規模（如 50 題）跑通端到端流程，再放大到 700 題以上的規模。也要特別注意本文的關鍵發現：多輪互動讓成本翻倍但解決率未穩定提升，這對你設計代理產品的定價與效能預期有直接影響。

**給研究者**：本文的核心貢獻是「把互動協定從隱含假設變成可測量、可操縱的變數」，這對整個代理評估領域有方法論意義。建議從 Task Flow 的形式化定義出發，思考如何推廣到其他領域（網頁代理、資料分析代理、客服代理）。附錄 B 對三個公開互動語料庫的比較是很好的延伸研究起點。TFAS 的權重設計與分布距離度量選擇（JS 散度 vs. Wasserstein 距離）也值得深入探討。

**給產品經理**：本文的商業意涵很清楚：代理產品的「實驗室分數」與「使用者桌機體驗」之間存在系統性落差，原因是基準測試的互動模式與真實工作流不符。當你在評估要不要導入某個程式碼代理時，別只看 SWE-bench 分數，要問「這個分數是在什麼互動模式下測出來的？」以及「我們團隊的真實工作流是什麼樣的 Task Flow？」。本文提供的 SWE-TaskFlow 方法讓你能把公開基準「客製化」到自家工作流，這是採購決策的有力工具。也要注意成本警示：多輪互動會讓 token 消耗翻倍，這直接影響產品的單位經濟模型。
