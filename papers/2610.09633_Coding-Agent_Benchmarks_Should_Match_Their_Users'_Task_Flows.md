# 程式碼代理基準測試應符合使用者的任務流程

**原文標題：** Coding-Agent Benchmarks Should Match Their Users' Task Flows  
**作者：** Igor Slinko、Yaroslav Golubev、Sergey Titov  
**發布日期：** 2026-10-07  
**HF 連結：** [https://huggingface.co/papers/2610.09633](https://huggingface.co/papers/2610.09633)  
**arXiv：** [https://arxiv.org/abs/2610.09633](https://arxiv.org/abs/2610.09633)  

---

## ⚡ TL;DR

現有程式碼代理基準測試多源自單一議題，無法反映真實使用者多樣且多輪的任務流程。
作者提出 SWE-TaskFlow，透過提示拆分與可驗證的儲存庫問答，將議題衍生基準轉為多輪互動軌跡。
在 700 個 SWE-Bench Pro 任務的先導實驗中，多輪互動使代理成本翻倍卻未穩定提升解決率。

---

## 摘要翻譯

程式碼代理（Coding-Agent）的評估通常力求盡可能真實。本研究收集了 4,782 個 JetBrains IDE 中真實軟體工程師的代理會話（Agent Sessions），我們稱之為生產環境會話（Production Sessions）。由於我們的研究對象是互動式代理，我們研究至少包含三則使用者訊息的會話（佔樣本的 33%）。這些長會話在兩個方面不同於議題衍生基準測試（Issue-Derived Benchmark）任務：(i) 使用者請求涵蓋遠更廣泛的任務類型（Task Types）組合——關於專案程式碼的問題、規劃、審查、重構、執行——以及 (ii) 使用者在整個會話過程中會在類型之間切換。三個公開互動語料庫（Interaction Corpora）的長會話樣本呈現出明顯不同的任務流程（Task Flow，即會話長度（Session Lengths）、任務類型及類型間轉換（Type-to-Type Transitions）的分布），因此沒有任何單一互動分布能普遍代表真實情況：基準測試應標明目標使用情境（Target Use Case）並根據其測量結果進行校準。我們提出 SWE-TaskFlow，這是一種轉換任何議題衍生基準測試的方法：它保留了已驗證任務（Verified Tasks）和測試，同時透過提示拆分（Prompt Splitting）和可驗證的儲存庫問答（Verifiable Repository QA）將互動導向目標任務流程，並使用任務流程對齊分數（TaskFlow Alignment Score, TFAS）從生成的軌跡（Trajectory）中進行選擇。在 700 個 SWE-Bench Pro 任務的先導實驗（Pilot）中，分多步驟依序解決任務會使代理成本（Agent Cost）約翻倍，但解決率（Resolve Rate）並無穩定變化：互動協議（Interaction Protocol）本身是評估的重要面向。

### 核心貢獻（3～5點）
- 透過分析 4,782 個 JetBrains IDE 中真實軟體工程師的代理會話，揭示長會話中任務類型高度多樣化與類型間動態切換的特性。
- 證明不同公開互動語料庫呈現截然不同的任務流程分布，論證「無單一通用真實分布」的觀點，主張基準測試應標明目標使用情境並加以校準。
- 提出 SWE-TaskFlow 方法，透過提示拆分與可驗證的儲存庫問答將議題衍生基準測試轉換為符合目標任務流程的形式，同時保留已驗證任務與測試。
- 設計任務流程對齊分數（TFAS）作為軌跡選擇機制，量化生成互動流程與目標任務流程之間的對齊程度。
- 透過 700 個 SWE-Bench Pro 任務的先導實驗，證明互動協議本身是評估的重要維度——改變互動方式可使代理成本約翻倍，卻未帶來解決率的穩定提升。

### 適合對象
從事程式碼代理（Coding Agent）研發與評估的研究者、基準測試設計者、AI 軟體工程工具的產品經理與開發團隊，以及關注代理系統真實使用情境、互動設計與成本效益的學術界與產業界人士。

## 深度分析

#### 方法論解析

本論文提出了一套系統性的方法論框架，核心在於重新定義程式碼代理（coding agent）基準測試的設計哲學，並提供具體的轉換工具。整體方法可分為三個相互支撐的層次：觀察層、形式化層、轉換層。

**觀察層：生產環境會話（Production Sessions）的收集與分類**

研究團隊從 JetBrains IDE 收集了 4,782 個真實軟體工程師與編碼代理互動的會話，總計約 14,000 條使用者訊息。為了處理這種規模的質性資料，他們採用開放權重大型語言模型（open-weight LLM）作為分類器，將每條訊息獨立標記為 16 種任務類型（intents）之一，包含錯誤修復（bug fix）、新功能（new feature）、解釋（explain）、規劃（planning）、程式碼審查（code review）、執行（execution）等。分類定義經過人工審查迭代，且三個不同的分類器模型在 76.1% 的標籤上達成共識，這提供了分類品質的統計基礎。

值得注意的是，研究者刻意聚焦於「長互動切片」（long-interaction slice），即至少包含三條使用者訊息的會話，佔總樣本的 33%。這個切片選擇反映了論文的核心理念：互動式代理（interactive agents）的評估必須考慮多輪對話，而非單輪的「一次性問答」。

**形式化層：任務流程（Task Flow）的數學定義**

論文將「任務流程」形式化為一個三元組 $(P_L, P_T, P_R)$，包含三個分布：
- $P_L$：會話長度分布（session lengths）
- $P_T$：訊息的任務類型分布（task types over messages）
- $P_R$：相鄰訊息之間的有向轉換分布（directed transitions）

這個定義的精妙之處在於 $P_R$ 保留了順序資訊——單純的標籤直方圖會遺失「使用者先問問題、再請求實作、最後要求審查」這類時序模式。形式化使得「貼近真實」這個模糊概念變得可測量、可優化。

**轉換層：SWE-TaskFlow 方法**

SWE-TaskFlow 是將現有議題衍生基準測試（issue-derived benchmarks）轉化為多輪互動軌跡的具體方法，實作於 SWE-Bench Pro 上。其核心設計原則是「保留已驗證任務（verified tasks）與測試，僅重新生成互動層（interaction layer）」，這避免了重新建立儲存庫狀態、執行環境與測試驗證器的巨大成本。

方法包含兩個關鍵增強機制：

1. **提示拆分（Prompt Splitting）**：SWE-bench 風格的議題通常在一條精煉的訊息中陳述目標、脈絡、限制與方法，但真實使用者傾向於逐步揭示需求。拆分器將一個議題轉換為 $K$ 個有序且自包含的使用者輪次（$K=3$），相鄰部分可合併。拆分器必須滿足四個約束：保留所有原始需求、不引入新需求、保留技術工件原文、每個輪次在先前輪次留下的儲存庫狀態下皆可執行。通過檢查的議題進入多輪流程；未通過者保留為單輪。在 731 個 SWE-Bench Pro 公開任務中，700 個通過了拆分與評估脈絡檢查。

2. **可驗證的儲存庫問答（Verifiable Repository QA）**：生成 0 至 3 個關於儲存庫行為的可驗證問題，注入基準測試所缺乏的「解釋」意圖。問題來源於解決原始議題的代理軌跡，結合即時儲存庫狀態產生。每個候選問題都附帶隱藏參考答案，且必須滿足：可從儲存庫回答、在議題補丁前後皆有效、不洩漏解法、並通過在乾淨儲存庫副本中執行的可執行證明腳本（proof script）。

問題的放置位置（議題輪次之前、之間或之後）決定了哪些轉換出現。兩個增強機制共同產生每任務 1 至 6 個使用者輪次，其中至少 3 輪的候選構成長會話切片。

**對齊度量：任務流程對齊分數（TFAS）**

為了讓「更貼近目標任務流程」這個概念變得明確且可優化，論文提出了任務流程對齊分數（TaskFlow Alignment Score, TFAS）。給定目標分布 $P_k$ 與基準分布 $Q_k$（$k \in \{L, T, R\}$），TFAS 量化兩者在會話長度分箱、任務類型、轉換三個維度上的對齊程度。TFAS 的存在使得從多個生成的軌跡候選中選擇最佳者成為可能，這在多輪軌跡生成中是必要的，因為同一任務可能有多種合理的拆分與問答插入方式。

**逐輪評估設計**

論文主張一個任務應產生多個可驗證訊號（verifiable signals），而非單一終端分數（terminal score）。在 SWE-Bench Pro 的先導實驗中，每個任務除了最終的補丁驗證外，還包含中間輪次的問答正確性檢查。這種設計使得評估能夠區分「代理在多輪互動中逐步建構解法的能力」與「代理從完整規格一次性產出解法的能力」。

#### 實驗數據解讀

**生產環境會話的統計特徵**

4,782 個會話的長度分布呈現高度右偏：50.9% 為單訊息會話，33% 至少三條訊息，第 75 與第 90 百分位數分別為 3 與 8 條訊息。第一條訊息平均 30.7 字，後續位置降至 16–19 字，這反映了「初始需求較為詳細、後續互動較為簡潔」的真實模式。

在任務類型分布上，錯誤修復佔 25.9%、新功能佔 18.9%，兩者合計 44.8%，遠低於 SWE-Bench Pro 中的 93.8%。其餘超過一半的訊息涉及解釋專案程式碼（6.1%）、一般程式設計問題（9.7%）、規劃、審查、重構、執行等。這項數據直接挑戰了議題衍生基準測試的代表性假設——它們系統性地低估了「非實作類」互動的頻率。

**解釋意圖的持續性**

圖 1 顯示 EXPLAIN 意圖在會話的每個位置都保持常見，這意味著「詢問專案程式碼如何運作」並非偶發行為，而是貫穿整個開發流程的常規需求。這項觀察直接驅動了 SWE-TaskFlow 中儲存庫問答增強機制的設計。

**公開互動語料庫的差異化**

研究者將相同的分類流程應用於三個公開互動語料庫（SWE-chat、SpecStory、DataClaw），結果顯示它們的任務流程在意圖與轉換兩個維度上都與生產環境會話及彼此之間有可見差異。這個發現具有方法論意義：沒有單一的「真實互動分布」，任何基準測試的設計都必須先明確其目標使用情境（target use case），並從該情境測量任務流程。

**SWE-Bench Pro 先導實驗的關鍵發現**

在 700 個 SWE-Bench Pro 任務上的先導實驗揭示了一個反直覺的結果：以多步驟順序解決任務（而非一次性解決）使代理成本（agent cost）約翻倍，但解決率（resolve rate）沒有穩定變化。這個發現的解讀需要謹慎：

首先，成本翻倍本身是預期內的——多輪互動自然消耗更多推理資源。但缺乏穩定的解決率提升意味著，當前的代理在「從逐步揭示的需求中建構解法」與「從完整規格產出解法」之間並無實質差異。這可能反映兩種情況之一：代理確實具備等效的兩種能力，或者代理在多輪設定中未能有效利用逐步揭露的資訊。

其次，「互動協議（interaction protocol）本身是重要的評估變數」這個結論是論文的實質主張。相同的底層任務，僅改變互動協議（單輪 vs. 多輪），就足以顯著影響成本，這證明了互動層不應被視為中性的評估容器，而應作為評估設計的核心維度。

**TFAS 的選擇效應**

雖然論文中未詳述 TFAS 在 700 個任務上的具體數值分布，但 TFAS 的設計使得「對齊目標任務流程」成為軌跡生成的優化目標。這意味著 SWE-TaskFlow 生成的軌跡不是隨機的，而是朝著測量出的目標分布收斂，這提升了基準測試的內部效度。

#### 與現有研究的比較

**與議題衍生基準測試的關係**

SWE-Bench 及其後繼（SWE-Bench Pro、SWE-rebench、DeepSWE）代表了「從完整議題評估實作能力」的典範。論文的立場並非否定這些基準的價值——它們的儲存庫狀態、執行環境與測試驗證器是寶貴的基礎設施投資。論文的核心批評在於：這些基準的「互動層」測量的是「從預先規格（upfront specification）進行實作」，而非「適應跨會話展開的需求」。SWE-TaskFlow 正是為了保留前者基礎設施、替換後者互動層而設計的。

**與其他基準轉換方法的區別**

附錄 D 提到的相關轉換方法（如軌跡預先固定的精確重播方法）與 SWE-TaskFlow 的關鍵差異在於：前者選擇互動軌跡是臨時性的（ad hoc），後者則以測量出的任務流程為校準目標。這使得 SWE-TaskFlow 在「為何選擇此互動模式」這個問題上提供了可辯護的依據，而非設計者的直覺。

**與人類研究方法的互補**

論文的方法論借鑑了人機互動（HCI）研究中「以實測分布作為設計目標」的傳統。將 4,782 個生產環境會話視為「自然發生的互動分布樣本」，並以此校準基準測試，這與軟體工程實證研究中「以礦山資料（field data）取代實驗室資料」的取向一致。

**論文的限制**

第一，JetBrains IDE 使用者並非全體軟體工程師的代表性樣本。任務流程可能因 IDE 特性（如 JetBrains 的深度程式碼分析整合）而呈現特定模式。論文透過分析三個公開互動語料庫部分緩解了這個問題，但無法完全排除樣本偏差。

第二，分類器的 76.1% 一致率雖然合理，但意味著約 24% 的標籤存在模型間分歧。這些分歧訊息可能恰好是「任務流程」中最具區辨力的部分——模糊意圖的轉換模式。

第三，先導實驗僅在 700 個 SWE-Bench Pro 任務上進行，且未詳細報告不同代理模型在多輪設定下的差異。論文的結論「互動協議是評估變數」需要更多代理模型與更多任務的驗證。

第四，TFAS 的具體計算公式在擷取的文本中未完整呈現，這限制了其可重現性與可批判性。

第五，論文的立場「沒有普遍真實的編碼代理基準」雖然方法論上合理，但可能導致基準測試生態的碎片化。每個目標使用情境都需要獨立的測量與校準，這對基準測試的維護者提出了顯著的負擔。

#### 可重現性評估

**資料集與程式碼的可用性**

論文明確聲明所有生成的任務以單一公開資料集形式釋出（細節在附錄 E）。SWE-TaskFlow 的轉換方法、提示拆分器的提示模板、儲存庫問答的生成流程、TFAS 的計算邏輯，雖然在擷取的文本中未完整呈現，但論文的結構暗示這些將在附錄或配套程式碼中提供。

**可重現性的優勢**

- 基礎任務（700 個 SWE-Bench Pro 任務）來自公開基準，儲存庫狀態與測試驗證器完全可重現。
- 分類流程使用開放權重 LLM，不依賴閉源 API，這降低了重現成本。
- 儲存庫問答的「可執行證明腳本」設計使得問題的正確性可在乾淨環境中驗證，這是強健的可重現性保證。

**可重現性的挑戰**

- 4,782 個生產環境會話因隱私考量僅以匿名聚合統計形式釋出，研究者無法直接存取原始對話。這限制了其他研究者對「任務流程測量」本身的驗證。
- 提示拆分器與問答生成器依賴 LLM，其輸出具有隨機性。論文中未明確說明是否固定隨機種子或提供多次執行的標準差。
- TFAS 的完整公式未在擷取文本中呈現，需要查閱附錄才能評估其可重現性。
- 先導實驗使用的代理模型未明確指定，這使得「成本翻倍、解決率不變」這個關鍵發現難以獨立驗證。

**整體評估**

論文的可重現性處於中等偏上水準。基礎設施（任務、測試、驗證器）完全可重現；方法論（分類、拆分、問答生成）有明確的設計原則但具體實作細節需查閱附錄；實證結果（先導實驗的具體數值）需要更多細節才能完整重現。對於希望採用 SWE-TaskFlow 框架的研究者，論文的描述提供了足夠的設計藍圖，但實作層面的精細調整仍需自行探索。

#### 未來研究方向

**多代理模型與多基準的系統性驗證**

論文先導實驗僅在 700 個 SWE-Bench Pro 任務上進行，且未詳細報告代理模型差異。未來研究應系統性地評估不同代理（如 Claude、GPT 系列、開源模型）在多輪互動設定下的表現差異，特別是「哪些代理能有效利用逐步揭露的需求」與「哪些代理在多輪設定下表現退化」。此外，將 SWE-TaskFlow 應用於其他議題衍生基準（SWE-rebench、DeepSWE）將驗證方法的泛化性。

**任務流程的縱向演化**

論文的任務流程是橫斷面的（cross-sectional），反映特定時間點的使用模式。但編碼代理的能力演化會改變使用者的互動策略——例如，當代理的程式碼審查能力提升後，使用者可能更頻繁地發起審查請求。縱向追蹤任務流程的演化，並據此更新基準測試，將是重要的研究方向。

**任務流程與代理能力的因果分析**

「互動協議是評估變數」這個發現開啟了因果分析的空間：哪些互動特徵（如任務類型多樣性、轉換複雜度、會話長度）對代理表現有最大的影響？這需要更細粒度的消融實驗，例如固定任務類型分布但改變轉換模式，或固定轉換模式但改變任務類型分布。

**TFAS 的理論基礎與替代度量**

TFAS 作為對齊度量，其設計選擇（如分箱方式、距離函數）需要更堅實的理論基礎。未來研究可以探索基於最優傳輸（optimal transport）的分布距離、基於資訊理論的互資訊度量，或基於下游任務表現的間接對齊度量。此外，TFAS 與人類評估者對「真實性」判斷的相關性需要驗證。

**互動層的代理模擬**

SWE-TaskFlow 目前使用基於規則與 LLM 的拆分器生成使用者輪次，但真實使用者的行為具有隨機性與非理性。未來研究可以探索使用代理模擬器（user simulator）來生成更真實的互動軌跡，特別是包含「使用者糾正」、「需求變更」、「中途放棄」等行為模式。

**跨文化與跨領域的任務流程差異**

JetBrains IDE 使用者主要來自特定地理與技術社群。不同文化背景、不同技術領域（如資料科學、嵌入式系統、網頁開發）的軟體工程師可能有截然不同的任務流程。系統性地測量這些差異，並建立領域專屬的基準測試，將提升評估的生態效度。

**互動成本與價值的經濟分析**

論文發現多輪互動使代理成本翻倍但解決率不變，這引發了經濟學問題：在什麼樣的任務與使用者情境下，多輪互動的額外成本是值得的？未來研究可以建立成本-收益模型，量化「互動品質提升」與「代理成本增加」之間的取捨，並據此設計自適應的互動協議——在簡單任務上保持單輪，在複雜任務上啟用多輪。

**基準測試生態的標準化**

論文主張「沒有普遍真實的基準」，這可能導致生態碎片化。未來研究可以探索建立「任務流程元資料標準」，使得每個基準測試都明確聲明其目標使用情境、測量方法、適用範圍，並支援跨基準的元分析。這將在保持基準多樣性的同時，提供可比較的評估框架。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文指出，當前程式碼代理基準測試（如 SWE-Bench Pro、SWE-rebench、DeepSWE 等議題衍生基準測試）與真實軟體工程師在 IDE 中使用代理的互動模式存在嚴重落差。研究者透過分析 4,782 個 JetBrains IDE 中的生產環境會話，發現真實使用者的請求涵蓋錯誤修復、新功能、解釋程式碼、規劃、審查、重構、執行等多種任務類型，且會在單一會話中不斷切換類型，而現有基準測試卻只專注於「一次性給定完整規格、產出最終修補程式」的單輪互動模式。這種落差使得基準測試無法真實衡量代理在真實工作流程中的表現。

**Q2：為什麼現有的議題衍生基準測試無法反映真實使用情境？**
A：現有基準測試源自 GitHub issue 等議題，這類議題通常在一段精煉文字中同時陳述目標、背景、限制甚至實作方法，屬於「預先規格」式的單輪互動。然而真實使用者的提示平均僅 30.7 個字（首則訊息），且會在多輪對話中逐步揭露需求、追問現有行為、要求規劃與審查。SWE-Bench Pro 中新功能（54.7%）與錯誤修復（39.1%）合計佔 93.8%，而生產環境會話中這兩類意圖合計不到一半，其餘包含解釋、提問、規劃、審查、重構、執行等議題基準完全忽略的意圖，因此基準測試衡量的是「從完整規格實作」而非「適應逐步展開的需求」。

**Q3：為什麼「任務流程對齊」對代理評估如此重要？**
A：任務流程涵蓋會話長度分佈、任務類型分佈與類型間轉換分佈三個維度，是衡量互動真實性的核心指標。論文發現不同產品的互動語料庫（SWE-chat、SpecStory、DataClaw）呈現出明顯不同的任務流程，意味著「沒有單一通用的真實互動分佈」，基準測試必須明確指定目標使用情境並校準到該情境的測量結果。互動協議本身會顯著影響評估結果——在 700 個 SWE-Bench Pro 任务的先導實驗中，將任務依序拆解為多步驟執行會使代理成本約翻倍，卻未帶來穩定的解決率提升，證明互動層是評估中不可忽略的維度。

**Q4：SWE-TaskFlow 方法的核心設計理念是什麼？**
A：SWE-TaskFlow 的核心理念是「轉換而非重建」——保留現有已驗證 SWE 任務的儲存庫狀態、執行環境與測試基礎設施，僅重新生成互動層。這種設計避免了從頭打造新互動式基準測試的高昂成本，同時保留了多年來累積的測試型驗證器投資。方法透過兩種增強手段——提示拆分（將單一完整議題拆成 K=3 個有序、自足的使用者輪次）與可驗證的儲存庫問答（注入議題基準缺乏的「解釋」意圖）——將任務塑形為符合目標任務流程的多輪軌跡。

**Q5：「提示拆分」與「可驗證的儲存庫問答」這兩種增強手段如何運作？**
A：提示拆分針對「過度規格化」問題：基於 LLM 的拆分器必須保留原始議題中的每一項需求、不引入新需求、保留技術細節原文，且每個拆分後的輪次必須在先前輪次留下的儲存庫狀態下可執行；未通過檢查的議題則保留為單輪。在 731 個 SWE-Bench Pro 公開任務中，有 700 個通過拆分與評估環境檢查。可驗證的儲存庫問答則從解決原議題的代理軌跡與即時儲存庫狀態中挖掘 0 至 3 個關於儲存庫行為的可驗證問題，每個問題都附有隱藏參考答案，必須在議題修補前後皆可回答、不洩漏解法，並在乾淨儲存庫副本中通過可執行證明腳本驗證。

**Q6：什麼是任務流程對齊分數（TFAS），它如何用於軌跡選擇？**
A：任務流程對齊分數（TFAS）將「更接近目標任務流程」這一直觀概念形式化為可最佳化的指標。給定目標分佈 Pk 與基準分佈 Qk（k∈{L, T, R}，分別對應會話長度分箱、任務類型、類型間轉換），TFAS 衡量兩者之間的距離，使基準建構者能在多個生成的軌跡候選中，依據與目標任務流程的對齊程度進行選擇。這使得「真實性」從模糊的設計目標變為可量化、可比較的評估準則，也讓基準測試能針對不同目標使用情境靈活調整。

**Q7：實驗使用了哪些基準測試與資料集？**
A：論文的主要先導實驗基於 SWE-Bench Pro 的 700 個公開任務（從 731 個中通過拆分與評估環境檢查後保留），並與三個公開互動語料庫（SWE-chat、SpecStory、DataClaw）進行任務流程對比。生產環境會話資料來自 JetBrains IDE 使用者的 4,782 個代理會話、約 14,000 則使用者訊息，其中 33% 屬於長互動切片（至少三則使用者訊息）。所有資料集都經過相同的分類管線處理，確保任務類型分佈具有可比腳踏實地的基礎。

**Q8：先導實驗的關鍵發現是什麼？**
A：在 700 個 SWE-Bench Pro 任務上的先導實驗揭示了一個反直覺的結果：將任務依序拆解為多步驟執行會使代理成本約翻倍，卻未帶來穩定的解決率變化。這意味著「拆解任務」並非總能提升表現，代理在多輪互動中可能因為缺乏整體規格而迷失方向，或在每個輪次重複探索相似的程式碼區域。這個發現直接證明了互動協議本身是評估中的重要變數——相同的底層任務，僅改變互動層就會顯著改變成本與表現的權衡。

**Q9：任務流程在不同資料來源之間呈現哪些差異？**
A：論文將相同的分類管線應用於生產環境會話、SWE-chat、SpecStory、DataClaw 四個來源，發現它們在任務類型分佈與類型間轉換上呈現明顯差異。生產環境會話中錯誤修復（25.9%）與新功能（18.9%）雖領先但不具支配地位，解釋（6.1%）與一般提問（9.7%）在每個位置都常見；而議題衍生基準測試幾乎完全缺乏解釋意圖。這些差異表明「真實性」是相對於特定產品與使用情境的，沒有單一通用的真實互動分佈可作為基準測試的設計目標。

**Q10：SWE-TaskFlow 在實際產品開發中有哪些應用情境？**
A：SWE-TaskFlow 特別適合需要評估代理在 IDE 內互動表現的場景，例如 JetBrains、VS Code 等整合開發環境中的 AI 助手。透過將已驗證的 SWE 任務轉化為符合真實任務流程的多輪軌跡，產品團隊能更準確地衡量代理在「使用者逐步揭露需求、追問現有行為、要求規劃與審查」的真實工作流中的表現。此外，方法支援針對不同目標使用情境（如企業內部開發、開源協作、教學場景）校準基準測試，避免「一套基準走天下」的偏差。

**Q11：基準測試建構者在採用此方法時應注意哪些產品層面的考量？**
A：基準測試建構者首先必須明確指定目標使用情境，因為不同產品的任務流程差異顯著，無法直接套用。其次，應以目標情境的實測任務流程作為設計目標，而非憑直覺選擇互動模式。在實作層面，提示拆分器與問題生成器都必須經過嚴格驗證——拆分必須保留所有原始需求且不引入新需求，問題必須可驗證、不洩漏解法、在乾淨環境中可執行。最後，應使用 TFAS 在多個候選軌跡中進行選擇，使「真實性」成為可量化的設計約束。

**Q12：這項研究對程式碼代理評估領域的整體影響是什麼？**
A：這項研究挑戰了「越真實越好」的基準測試設計直覺，提出「明確目標、實測校準」的新範式。它促使領域認識到互動層是評估的重要維度，單一的終端分數無法捕捉代理在多輪互動中的真實表現。透過將議題衍生基準測試轉化為可重播的多輪軌跡候選，並以逐輪評估取代單一終端分數，研究為基準測試設計提供了更細緻、可比較的工具，也為未來針對特定使用情境打造專屬基準測試奠定了方法論基礎。

**Q13：論文承認哪些方法論上的限制？**
A：論文坦承生產環境會話資料來自單一 IDE 廠商（JetBrains），雖然規模可觀（4,782 個會話、約 14,000 則訊息），但可能無法完全代表所有開發者的互動模式。此外，分類器在三個模型間僅達到 76.1% 的一致率，意味著任務類型標註存在一定噪音。提示拆分依賴 LLM 生成，雖然設有保留需求、不引入新需求等檢查，但無法保證所有拆分結果都完美符合人類使用者的真實揭露順序。可驗證問題的挖掘同樣受限於解決軌跡的品質，若原始軌跡本身有缺陷，挖掘出的問題可能不夠精確。

**Q14：方法可能出現哪些失敗案例？**
A：當原始議題本身高度整合、無法乾淨拆分為多個自足輪次時，提示拆分可能失敗，這類議題會被退回為單輪處理，導致任務流程與目標分佈仍有落差。可驗證問題的挖掘依賴於存在一條成功解決議題的代理軌跡，若無此軌跡則無法生成問題；此外，若問題過於細節或過於模糊，可能無法在評估時可靠地判斷代理回答的正確性。在互動協議改變導致解決率不穩定的情況下，基準測試的區分力可能下降，使得不同代理之間的相對表現難以可靠比較。

**Q15：未來研究有哪些值得探索的方向？**
A：未來可朝多個方向延伸：首先是將 SWE-TaskFlow 應用於更多議題衍生基準測試（SWE-rebench、DeepSWE 等），驗證方法的泛用性；其次是針對不同目標使用情境（如企業內部、開源協作、教學場景）建立專屬的任務流程模型與對應基準測試；第三是探索更細緻的逐輪評估指標，超越單一解決率，衡量代理在每個輪次中的推理品質、需求理解與適應能力；最後，可研究如何讓代理本身學會適應不同的互動協議，使其在多輪、逐步揭露需求的真實工作流中表現更穩定。

## 實務應用指南

### 適用場景

1. **IDE 廠商內部代理評估管線**：JetBrains、VS Code 等 IDE 廠商希望評估自家整合的程式碼代理（如 JetBrains AI Assistant、GitHub Copilot Workspace），可利用生產環境會話資料建立符合真實使用者任務流程的基準測試，避免代理在「單一議題式」評估中表現良好，卻在實際多輪互動中失敗。

2. **企業內部程式碼代理部署評估**：企業 IT 團隊在導入 Claude Code、Cursor、Aider 等代理工具前，可透過 SWE-TaskFlow 方法將內部 GitLab/GitHub 議題轉換為多輪互動軌跡，模擬內部開發者真實的工作模式（提問 → 規劃 → 審查 → 執行），以評估代理在企業特定任務流程下的表現。

3. **基準測試建構者擴展既有 SWE 評估**：研究團隊或公司（如 Hugging Face、Princeton NLP）已投資 SWE-Bench Pro、SWE-rebench 等已驗證任務，可運用 SWE-TaskFlow 保留測試與環境的同時，調整互動層以匹配目標使用者族群，避免重複建置昂貴的基礎設施。

4. **學術研究中的多輪代理行為分析**：研究人員探討代理在長對話中的規劃、錯誤恢復、上下文管理能力時，可使用 SWE-TaskFlow 產生受控的多輪軌跡，並以 TFAS 量化不同互動協議對代理表現的影響。

5. **代理產品經理校準 UX 設計**：產品團隊在設計代理互動介面時，可參考生產環境會話的任務流程資料，決定何時主動詢問釐清、何時提供規劃建議、何時進入執行模式，使產品行為貼近使用者期望。

### 實作前置條件

**資料需求**
- **生產環境會話資料**：至少數千筆真實使用者與代理的對話記錄（論文使用 4,782 筆），需經隱私去識別化處理。對話需包含使用者訊息、代理回應、時間戳記。
- **已驗證 SWE 任務**：具備可執行測試的儲存庫快照（如 SWE-Bench Pro 的 731 個任務），包含問題描述、基準解答、測試案例。
- **任務類型標註資料**：用於訓練或驗證分類器，建議至少數百筆人工標註的「任務類型」標籤（論文使用 16 種類型）。
- **儲存庫程式碼與執行環境**：Docker 容器或 CI 環境以執行測試驗證與 QA 證明腳本。

**運算資源**
- **LLM 推論能力**：用於任務分類、提示拆分、QA 生成、軌跡評估。論文使用開放權重 LLM 進行分類；可選 GPT-4、Claude 等閉源模型提升品質。
- **平行執行環境**：批量執行儲存庫測試與 QA 證明腳本，建議使用 Kubernetes 或雲端批次運算。
- **儲存空間**：每個任務的儲存庫快照、軌跡記錄、評估結果，預估每任務數 GB 級。

**技能需求**
- **提示工程**：設計任務分類、提示拆分、QA 生成的提示詞，並能診斷失敗案例。
- **評估設計**：理解二元分類指標、機率分佈距離（如 JS 散度、KL 散度）、TFAS 的計算邏輯。
- **統計分析**：熟悉分布比較、轉換矩陣分析、A/B 測試方法論。
- **軟體工程**：熟悉 Git、Docker、CI/CD、測試自動化，能處理儲存庫狀態管理。
- **領域知識**：理解軟體開發工作流程（規劃、實作、審查、除錯），才能設計合理的任務類型分類法。

### 實作步驟建議

**步驟 1：收集並匿名化生產環境會話**
從 IDE 遙測或代理後端取得使用者會話資料，過濾出長互動切片（至少 3 則使用者訊息的會話，約佔 33%）。移除個人識別資訊（PII）、公司機密、API 金鑰。記錄每則訊息的時間戳記、訊息長度、會話 ID。

**步驟 2：建立任務類型分類法並訓練分類器**
定義 16 種任務類型（錯誤修復、新功能、解釋、規劃、程式碼審查、執行、重構、提問等）。使用 LLM 進行初步分類，輔以人工審查迭代定義。建議至少三個分類器模型交叉驗證，目標一致率 75% 以上（論文達 76.1%）。

**步驟 3：測量目標任務流程**
對生產環境會話計算三項分布：(i) 會話長度分布（百分位數、長尾行為）；(ii) 任務類型分布（每種類型的頻率）；(iii) 類型間轉換矩陣（從類型 A 到類型 B 的機率）。將此三項分布記錄為目標 Task Flow。

**步驟 4：套用 SWE-TaskFlow 轉換**
對每個已驗證 SWE 任務執行兩個增強：
- **提示拆分**：使用 LLM 將單一議題拆分為 K 個有序、自我包含的使用者輪次（論文 K=3）。驗證拆分後保留所有原始需求、未引入新需求、保留技術細節、每輪可在當前儲存庫狀態下執行。未通過檢查的議題保留單輪。
- **儲存庫 QA 生成**：從成功解決議題的代理軌跡中挖掘 0–3 個關於儲存庫行為的可驗證問題，每個問題附帶隱藏參考答案與可執行的證明腳本。問題放置於議題輪次之前、之間或之後，以控制轉換模式。

**步驟 5：計算 TFAS 並篩選候選軌跡**
對每個生成的軌跡計算 TaskFlow Alignment Score，比較其會話長度分布、任務類型分布、轉換矩陣與目標的距離。選擇 TFAS 最高的軌跡作為最終基準測試任務。

**步驟 6：執行先導實驗並分析**
在子集任務（如 700 個 SWE-Bench Pro 任務）上比較不同互動協議下的代理表現。記錄解決率、代理成本（token 數或 API 費用）、每輪可驗證訊號。論文發現：將任務拆分為多輪約使代理成本翻倍，但解決率變化不穩定，證實互動協議本身是重要的評估變數。

**步驟 7：發布與持續校準**
將生成的任務作為公開資料集發布。建立定期重新校準機制：每季度從最新生產環境會話重新測量 Task Flow，更新基準測試以反映使用者行為演變。

### 潛在風險與注意事項

**風險 1：分類器錯誤傳播**
分類器一致率僅 76.1%，錯誤標籤會扭曲 Task Flow 測量，進而誤導基準測試設計。
**緩解**：使用多模型投票、保留人工標註黃金集、定期審查低信心預測；對關鍵決策（如目標 Task Flow 定義）進行專家驗證。

**風險 2：QA 洩漏與答案污染**
生成的儲存庫 QA 問題可能意外洩漏議題解答，或參考答案在補丁前後皆成立而失去鑑別力。
**緩解**：每個問題必須通過「補丁前可答、補丁後可答、不洩漏解答」三項檢查；執行證明腳本於乾淨儲存庫副本驗證；定期人工抽樣審查。

**風險 3：成本爆炸**
多輪互動使代理成本顯著增加（論文實驗約翻倍），若未預算將限制評估規模。
**緩解**：建立成本-效益曲線，識別「足夠真實」的最小輪次數；對簡單任務保留單輪；使用較小模型處理早期輪次（釐清、規劃），僅在執行輪使用強模型。

**風險 4：過度擬合特定使用者族群**
從單一產品（如 JetBrains IDE）測得的 Task Flow 無法直接遷移至其他使用者族群（論文已證實 SWE-chat、SpecStory、DataClaw 三者 Task Flow 顯著不同）。
**緩解**：明確聲明目標使用情境；避免將一個族群的 Task Flow 強加於另一族群；必要時為不同族群建立獨立基準測試。

**風險 5：提示拆分破壞任務可解性**
拆分後的輪次若順序不當或上下文不足，可能使原本可解的任務變得不可解。
**緩解**：保留單輪版本作為對照；要求每輪「在當前儲存庫狀態下可執行」；對拆分後任務進行小規模試跑驗證。

**風險 6：評估指標單一化**
僅以終端解決率評估會忽略輪次級的失敗模式（如釐清失敗、規劃錯誤）。
**緩解**：採用每輪可驗證訊號（如 QA 正確率、規劃合理性評分），結合終端分數形成多維度評估。

### 與其他技術的整合建議

**與 SWE-Bench 系列基準測試整合**
SWE-TaskFlow 設計為 SWE-Bench Pro、SWE-rebench、DeepSWE 等已驗證基準測試的轉換層，無需重建基礎設施。建議在現有 Docker 環境與測試框架上加入「互動層抽象」，使同一儲存庫快照可支援單輪與多輪兩種評估模式。

**與代理框架整合**
可與 LangGraph、AutoGen、CrewAI 等多輪代理框架對接，將 SWE-TaskFlow 生成的軌跡作為標準化測試案例。建議在代理框架中加入「任務流程感知」模式：根據當前輪次類型（解釋、規劃、執行）切換不同的系統提示與工具集。

**與 IDE 遙測系統整合**
JetBrains IDE、VS Code 等可將生產環境會話的匿名化匯出管道與 SWE-TaskFlow 流程串接，形成「測量 → 校準 → 評估 → 部署」閉環。注意遵守隱私法規（GDPR、CCPA），僅使用聚合統計與使用者同意的資料。

**與 LLM 評估平台整合**
可整合 LangSmith、Weights & Biases、Phoenix 等評估平台，記錄每輪的輸入、輸出、TFAS 分數、成本。建議建立儀表板視覺化不同互動協議下的成本-解決率權衡。

**與 CI/CD 整合**
將 SWE-TaskFlow 生成的基準測試納入 CI 流程，在代理模型更新或新版本發布前自動執行，及早發現互動協議變更導致的回歸。

### 給不同背景讀者的閱讀建議

**給初學者**：本文的核心訊息是「基準測試的互動方式會影響代理表現」。建議先閱讀第 1 節了解問題動機（為何單一議題式評估不夠真實），再讀第 2 節理解「任務流程」概念（會話長度、任務類型、轉換）。第 3 節的技術細節可先跳過，專注於「提示拆分」與「儲存庫 QA」兩個直觀概念。實作上，初學者可從小規模任務（如 50 個議題）開始，體驗單輪與多輪評估的差異。

**給 AI 工程師**：重點關注第 3 節的 SWE-TaskFlow 方法論與附錄 E 的完整生成流程。TFAS 的計算公式（第 3 節末段）是工程實作的關鍵，需理解如何將分布距離轉化為可優化目標。建議在自己的代理框架中實作「互動協議切換器」，比較單輪、3 輪、6 輪設定下的成本與解決率，並將結果與論文先導實驗對照。注意分類器一致率（76.1%）對工程管線的影響，設計容錯機制。

**給研究者**：本文提供了「互動層」作為新評估維度的研究議題。可延伸方向包括：(i) 不同任務類型轉換對代理錯誤模式的影響；(ii) TFAS 與人類專家評分的相關性；(iii) 跨語言、跨框架的 Task Flow 普適性。建議重讀附錄 B 的三個公開語料庫 Task Flow 比較，思考如何為自己的研究領域定義類似的「流程測量」。論文的「無通用真實分布」立場值得深入辯論。

**給產品經理**：本文對產品決策的直接啟示是：代理的「單次完美解答」不等於「真實工作流程中的價值」。建議在產品路線圖中區分「議題式評估」（衡量實作能力）與「流程式評估」（衡量協作能力），並為後者設定專門指標。閱讀時請專注於第 1 節的兩個觀察（任務類型多樣性、類型轉換）與先導實驗結論（成本翻倍但解決率不穩定），這直接影響代理功能的優先順序與定價策略。可與工程團隊討論：當前產品的代理互動模式是否匹配目標使用者的真實任務流程。
