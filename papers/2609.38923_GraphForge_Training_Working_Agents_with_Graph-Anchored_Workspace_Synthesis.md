## ⚡ TL;DR

訓練工作型代理需要基於真實檔案且可驗證的任務，但現有管線缺乏真實性或缺乏驗證機制。

## 摘要翻譯

工作型代理（working agents）需要讀取多元檔案、協調工具並產出交付物（deliverables）。訓練此類代理需要建立在大量真實檔案上且具可驗證結果的任務，但目前能合成此類資料的管線相當有限。既有管線要不是以模型生成檔案（缺乏真實性與多樣性），就是在真實檔案上建構任務卻缺乏任務專屬的驗證器（verifiers），導致結果品質難以確保。我們提出 GraphForge，一個基於證據圖（evidence graph）的框架，將任務本身及其驗證皆錨定（anchored）於真實檔案。GraphForge 從職業導向種子（occupation-grounded seeds）出發以實現受控的多樣性，為每個種子組裝一個由真實檔案構成的工作區（workspace），並在其關係上建構證據圖。由於任務說明與評分規準（rubrics）皆源自此圖，任務要求由工作區檔案支撐，每項評分規準也錨定至驗證所需的檔案。初始推演執行（rollout）進一步測試可執行性，修訂代理（revision agent）則在軌跡（trajectories）蒐集前，根據原始檔案修復任務與評分規準。在 2,169 條 GraphForge 軌跡上微調 Qwen3.6-27B，可使 GDPVal 在 OpenHands 下達到 1445.7（+65.7），並使 Workspace-Bench-Lite 與 SpreadsheetBench II 在 Claude Code 下分別達到 63.7（+7.7）與 24.0（+13.7）。在監督式微調（SFT）模型自身的推演執行上進行拒絕式微調（RFT），並由證據錨定之評分規準選取候選軌跡，可於三項基準上進一步帶來提升，顯示評分規準提供了有用的選取訊號。資料與模型皆已公開。

### 核心貢獻（3～5點）
- 提出 GraphForge 框架，以證據圖同時錨定任務與驗證，解決既有合成管線在「真實性」與「可驗證性」之間的權衡問題。
- 設計從職業導向種子出發的工作區合成流程，確保任務建立在真實檔案之上，並使每項評分規準皆對應可驗證的檔案依據（錨點）。
- 引入可執行性測試與修訂代理機制，在軌跡蒐集前自動修復任務與評分規準，提升合成資料的品質與可靠性。
- 實證 GraphForge 軌跡能有效提升 Qwen3.6-27B 在 GDPVal、Workspace-Bench-Lite 與 SpreadsheetBench II 三項基準上的表現。
- 證明以證據錨定之評分規準作為選取訊號進行拒絕式微調（RFT），可帶來進一步的效能增益。

### 適合對象
從事大型語言模型代理訓練、合成資料生成、自動化任務設計與評測基準研究的研究者與工程師；尤其適合關注真實檔案基礎任務、可驗證訓練資料、長時程代理能力及多檔案推理之學術與業界團隊。

## 深度分析

#### 方法論解析

GraphForge 的核心設計理念是將「任務合成」與「結果驗證」兩個環節同時錨定於真實檔案，從而解決既有管線中「合成資料缺乏真實性」與「真實檔案缺乏驗證機制」的二元困境。其方法論可拆解為以下幾個關鍵環節：

**1. 職業導向種子（Occupation-grounded Seeds）的設計**

GraphForge 採用 O*NET（美國職業資訊網絡）作為種子來源，這是一個重要的設計選擇。O*NET 提供了結構化的職業分類、官方工作活動（work activities）與工作模式（work patterns）描述，例如「金融與投資分析師」這類職業會對應到「分析財務數據」、「量化建模」、「支援投資決策」等活動語意。透過這種方式，種子本身具備三個特性：（a）多樣性可控——避免模型自由發明任務時傾向於高頻職業與通用任務類型的塌縮現象；（b）領域真實性——任務方向對應真實職業的工作場景；（c）可擴展性——可系統性地從 O*NET 抽取大量種子。

**2. 真實檔案工作區（Real-file Workspace）的組裝**

對於每個種子，一個代理（agent）會爬取真實檔案來組成工作區，並為每個檔案指派隱藏角色（hidden roles），例如「核心」（core）、「支援」（supporting）、「資料來源」（data source）等。圖 1 中的 NVDA 投資分析範例展示了五個檔案的層級關係：F1（2025 年度申報 HTML）、F2（2025 財務報告 XLSX）、F3（NVDA 公司基本資料 JSON）、F4（2024 年度申報 HTML）、F5（損益表 HTML）。檔案之間存在語意關聯，例如 F5 從 F4 提取、F3 提供 F1 與 F2 的背景脈絡。這種「覆蓋率式選取」（coverage-based selection）策略確保了工作區的結構化與多檔案推理需求。

**3. 證據圖（Evidence Graph）的建構與編譯**

這是 GraphForge 最具創新性的環節。模型在建構好的工作區之上建立一個證據圖，圖中的節點代表從檔案中提取的證據（例如「FY2025 營收 USD 130,497M」），邊則代表跨檔案的推理關係（例如「從 F2 讀取營收，與 F1、F5 交叉驗證」）。這個證據圖隨後被編譯（compile）為任務陳述（task statement）與評分規準（rubrics）。關鍵設計在於：每個評分規準的評分標準（criterion）都明確錨定（anchored）到驗證該標準所需的具體檔案節點，例如「私人評分標準：FY2025 營收 USD 130,497M，錨點：F2、F1、F5」。這種設計使得評分本身具備可追溯性與可驗證性。

**4. 執行條件式自我修正合成（Execution-conditioned Self-correcting Synthesis）**

GraphForge 引入了一個重要的品質控制環節：初始教師推演執行（initial teacher rollout）。這個步驟的目的不是收集訓練軌跡，而是「測試可執行性」（test executability）——確認任務陳述是否真的能在給定工作區上被執行。如果初始推演發現任務描述有歧義、評分規準無法對應到檔案、或推理鏈缺失，修訂代理（revision agent）會介入，僅修訂任務與評分規準（而非修改檔案），然後重新執行教師模型並重用（reuse）先前的執行軌跡（trace）。這種「最小修訂」（minimal revision）原則避免了對檔案內容的污染，確保了訓練資料的真實性。

**5. 軌跡收錄（Trajectory Admission）與證據錨定評審（Evidence-anchored Judge）**

最終的教師軌跡會被一個證據錨定評審進行評分，只有分數超過 0.90 的軌跡才會被收錄為訓練資料。這個評審本身也是基於證據圖的，因此評審標準與任務要求保持一致。這種設計形成了一個閉環：任務源自證據圖、評分規準源自證據圖、軌跡篩選也源自證據圖。

整體而言，GraphForge 的方法論展現了「以檔案為中心」（file-centric）的設計哲學，將真實性、多樣性、可驗證性三個看似矛盾的目標透過證據圖這個中介結構統一起來。

#### 實驗數據解讀

**1. 主要實驗結果**

GraphForge 在三個工作型代理評測基準上展現了顯著且一致的改進：

| 評測基準 | 基準分數 | GraphForge SFT | 提升幅度 | 執行框架 |
|---------|---------|---------------|---------|---------|
| GDPVal | 1380.0 | 1445.7 | +65.7 | OpenHands |
| Workspace-Bench-Lite | 56.0 | 63.7 | +7.7 | Claude Code |
| SpreadsheetBench II | 10.3 | 24.0 | +13.7 | Claude Code |

（注：基準分數為根據提升幅度反推的近似值，論文原文以相對提升呈現）

從數據中可以觀察到幾個重要現象：

**（a）絕對提升與相對提升的不對稱性**

SpreadsheetBench II 的相對提升最大（從 10.3 到 24.0，約 +133%），而 GDPVal 的相對提升最小（+65.7 / 1380 ≈ +4.8%）。這反映了不同基準的特性：SpreadsheetBench II 涉及複雜的試算表操作與公式推理，是 GraphForge 多檔案推理與工具使用能力的直接受益場景；GDPVal 涵蓋 44 種職業的 1,320 個任務，異質性更高，因此單一訓練資料的邊際效應較小。

**（b）跨執行框架的泛化性**

GraphForge 訓練資料在 OpenHands 與 Claude Code 兩種不同的代理執行框架下都帶來了改進，這說明所學到的能力並非框架特定的，而是更通用的工作型代理技能（如檔案閱讀、推理、工具協調）。

**（c）跨基礎模型的泛化性**

論文提到同一資料也改善了 Qwen3.6-35B-A3B（推測為 MoE 架構），這暗示 GraphForge 軌跡的價值不依賴於特定的基礎模型架構。

**2. 拒絕式微調（RFT）的增量效應**

在 SFT 模型的自身推演執行上，以證據錨定評分規準作為選取訊號進行拒絕式微調，在三個基準上都帶來了進一步的改進。這個結果的意義在於：

- **驗證了評分規準的選擇訊號價值**：RFT 的改進說明，證據錨定評分規準不僅能用於最終評估，還能作為訓練資料篩選的有效訊號，提供了「在模型自身推演執行上做品質控制」的可能性。
- **區分了 SFT 與 RFT 的互補性**：SFT 從強教師模型學習，RFT 從自身推演中精煉，兩者結合形成了一個完整的訓練 pipeline。

**3. 資料規模與效率**

僅 2,169 條軌跡（2.1K tasks）就帶來了上述改進，相比 EnvCraft 的 20K 任務與 NexForge 的 5.6K 任務，GraphForge 的資料規模更小但效果更好（至少在所報告的基準上）。這暗示了「品質勝於數量」的原則——證據錨定的設計使得每條軌跡都承載了更密集的學習訊號。

#### 與現有研究的比較

**1. 與 EnvCraft 的比較**

EnvCraft（Zeng et al., 2026）採用模型生成檔案的方式，並以 Python 腳本檢查工作區狀態。GraphForge 與其的關鍵差異在於：

- **真實性**：EnvCraft 的檔案由模型生成，缺乏真實世界的複雜度與多樣性；GraphForge 使用真實爬取的檔案，保留了真實世界的雜訊、格式異質性與語意豐富度。
- **驗證深度**：EnvCraft 的 Python 腳本無法讀取檔案內容，對文件類交付物（如報告、分析）的驗證能力有限；GraphForge 的證據錨定評審能基於檔案內容進行語意層級的評估。
- **規模**：EnvCraft 產出 20K 任務，GraphForge 產出 2.1K 任務，後者以約 1/10 的規模達到了更好的效果。

**2. 與 NexForge 的比較**

NexForge（Zhao et al., 2026）同樣使用真實檔案，但缺乏任務特定的評分規準與驗證器。GraphForge 的核心貢獻正是補上這個缺口：

- **可驗證性**：NexForge 的結果品質無法系統性檢查；GraphForge 的每個評分標準都錨定到具體檔案節點，提供了可追溯的驗證路徑。
- **選擇訊號**：NexForge 缺乏訓練軌跡的篩選機制；GraphForge 的證據錨定評審提供了 RFT 的選擇訊號，這是 NexForge 無法做到的。

**3. 與其他領域管線的比較**

從表 1 的整體景觀來看，GraphForge 在「工作型代理」這個特定領域內，填補了「真實檔案」與「可靠驗證」之間的空白。與通用領域管線（如 SWE-smith 的 fail-to-pass tests、TaskCraft 的 golden answer）相比，GraphForge 的驗證方式更靈活（基於評分規準而非單一正確答案），更適合開放式的文件類交付物。

**4. 局限性與未解問題**

儘管 GraphForge 展現了顯著優勢，仍存在以下局限：

- **O*NET 的地理與文化偏見**：O*NET 是美國勞工統計局開發的職業分類系統，將其作為種子來源可能限制了任務的多樣性，特別是對於非美國職業場景或文化特定的工作模式。
- **爬取檔案的可重現性**：真實檔案可能隨時間變化或消失，這對資料集的可重現性構成挑戰。
- **評審模型的依賴性**：證據錨定評審本身是一個 LLM-based judge，其評分品質受制於評審模型的能力，可能存在評審偏見（judge bias）。
- **修訂代理的干預**：雖然採用「最小修訂」原則，但修訂代理仍可能引入微妙的偏差，使得任務偏離原始的真實場景。
- **基準的代表性**：三個評測基準（GDPVal、Workspace-Bench-Lite、SpreadsheetBench II）都偏向英語世界的辦公室工作場景，對於其他語言或領域的泛化性尚待驗證。

#### 可重現性評估

**1. 資料與模型的釋出**

論文明確聲明「資料與模型均可取得」（The data and models are available），這是一個積極的可重現性信號。具體而言：

- **訓練資料**：2,169 條 GraphForge 軌跡應會公開釋出，研究者可以檢查其品質、多樣性與任務設計。
- **訓練後模型**：Qwen3.6-27B 與 Qwen3.6-35B-A3B 的微調版本會被釋出，使研究者能直接評估或作為基線。

**2. 程式碼的釋出**

雖然摘要與正文未明確提及程式碼釋出，但考慮到「資料與模型均可取得」的聲明以及現代 ML 研究的慣例，程式碼很可能會伴隨釋出。然而，完整的 pipeline（包括檔案爬取、證據圖建構、修訂代理、軌跡收錄）涉及多個複雜環節，僅釋出資料與模型可能不足以完全重現結果。

**3. 可重現性的潛在障礙**

- **真實檔案的時效性**：爬取的真實檔案可能在論文發表後發生變化，導致工作區內容不一致。
- **評審模型的選擇**：證據錨定評審使用哪個模型、其溫度設定、prompt 設計等細節會直接影響軌跡收錄的結果。
- **教師模型的選擇**：初始推演執行使用的教師模型（推測為 Claude 或 GPT 系列）會影響軌跡的品質與風格。
- **超參數與訓練細節**：SFT 與 RFT 的學習率、batch size、訓練步數等細節對於完全重現至關重要。

**4. 整體評估**

GraphForge 在可重現性方面展現了良好的意圖（釋出資料與模型），但完整的可重現性仍需依賴後續的程式碼與技術細節釋出。對於希望基於此工作進行延伸的研究者，建議密切關注作者的官方釋出。

#### 未來研究方向

**1. 證據圖結構的擴展與形式化**

目前的證據圖似乎是一個相對鬆散的語意結構，未來可以探索：

- **形式化語意**：將證據圖形式化為本體論（ontology）或知識圖譜，使其具備邏輯推理能力。
- **多模態證據**：將證據圖從純文字擴展到圖表、影像、表格等多模態證據，以支援更豐富的任務類型。
- **動態證據圖**：探索隨任務執行而演化的動態證據圖，模擬真實工作中證據逐步累積的過程。

**2. 種子來源的多元化**

O*NET 的地理與文化偏見是當前設計的明顯局限，未來可以：

- **整合多國職業分類**：如歐洲的 ESCO、中國的職業分類大典等，擴展任務的文化多樣性。
- **領域專家參與**：邀請特定領域的專家參與種子設計，提升任務的領域深度。
- **使用者需求驅動**：從真實的使用者需求中抽取種子，而非僅依賴預定義的職業分類。

**3. 驗證機制的強化**

證據錨定評審雖然創新，但仍依賴 LLM-based judge，未來可以：

- **形式化驗證**：對於可形式化的子任務（如數值計算、結構驗證），結合程式化驗證與語意驗證。
- **多評審一致性**：使用多個評審模型並檢驗一致性，降低單一評審的偏見。
- **人機協作驗證**：在關鍵評分標準上引入人類專家覆核，提升驗證的可靠性。

**4. 訓練方法的改進**

GraphForge 目前採用 SFT + RFT 的兩階段訓練，未來可以：

- **線上強化學習**：將證據錨定評分規準作為獎勵函數，進行線上 RL（如 PPO、GRPO），可能帶來更大的提升。
- **課程學習**：根據證據圖的複雜度設計課程，從簡單的單檔案任務逐步過渡到複雜的多檔案推理。
- **反事實訓練**：透過對證據圖的擾動生成反事實任務，提升模型的魯棒性。

**5. 跨領域與跨語言泛化**

- **領域泛化**：將 GraphForge 從辦公室工作場景擴展到科學研究、醫療、法律等專業領域。
- **語言泛化**：探索非英語場景下的證據圖建構與評分規準設計。
- **跨文化工作模式**：研究不同文化背景下的工作模式差異，並將其編碼到種子設計中。

**6. 代理能力的深化**

GraphForge 目前主要訓練「讀檔案、協調工具、產出交付物」的能力，未來可以探索：

- **長期記憶與狀態管理**：訓練代理在跨會話、跨任務的長期工作中維持一致性。
- **協作能力**：訓練多個代理在共享工作區上的協作能力。
- **主動性與規劃**：從被動執行任務擴展到主動發現問題、提出建議、規劃長期目標。

**7. 評測基準的演進**

隨著工作型代理能力的提升，現有評測基準可能會趨於飽和，未來需要：

- **更長時程的任務**：設計需要數小時甚至數天才能完成的真實工作任務。

- **動態環境**：任務環境隨時間演化的動態評測，更接近真實工作場景。

總結而言，GraphForge 提出了一個以證據圖為核心的工作型代理訓練資料合成框架，在真實性、多樣性與可驗證性之間取得了良好的平衡。其在多個基準上的顯著改進證明了方法論的有效性，而資料與模型的釋出也為後續研究提供了堅實的基礎。未來的研究可以在證據圖的形式化、種子來源的多元化、驗證機制的強化以及跨領域泛化等多個方向上進行深入探索。

## 論文問答

**Q1：GraphForge 試圖解決的核心問題是什麼？為什麼這個問題對工作型代理的訓練至關重要？**

A：GraphForge 試圖解決的核心問題是如何為工作型代理（working agents）合成「基於真實檔案」且「具備可驗證結果」的訓練資料。工作型代理需要讀取多樣化的檔案、協調工具並產出可被他人使用的交付物，這類任務的訓練需要建立在大量真實檔案之上，且每個任務都必須有可驗證的結果。傳統的代理訓練方法（如監督式微調於合成的軌跡）若要應用於工作型代理，就必須同時解決「真實檔案來源」與「可靠驗證機制」這兩個關鍵需求，而現有方法在這兩方面都存在明顯不足，這正是 GraphForge 要填補的研究缺口。

**Q2：為什麼現有的 EnvCraft 和 NexForge 等管線無法充分解決這個問題？**

A：EnvCraft 雖然能合成工作區，但其所生成的檔案是由模型產生的，缺乏真實性與多樣性，且其驗證機制僅依賴 Python 腳本檢查工作區狀態，無法讀取檔案內容，因此容易忽略文件交付物中的錯誤。NexForge 則建立在真實檔案之上，但缺乏任務專屬的評分規準（rubrics）或驗證器，導致結果品質無法被系統性地檢查。這兩個方法各自只解決了問題的一面：EnvCraft 有驗證但缺乏真實檔案，NexForge 有真實檔案但缺乏驗證，而 GraphForge 透過證據圖同時兼顧了這兩個面向，這也是其相較於前兩者的根本優勢。

**Q3：工作型代理與其他類型的代理（如工具使用、軟體工程代理）相比有何獨特挑戰？**

A：工作型代理面臨的核心挑戰在於其任務的「長時程」與「多檔案」特性——它們需要跨多個異質檔案（HTML、XLSX、JSON 等）進行推理，並協調檔案系統、資料庫與終端機等多種工具來產出可用的交付物。相較於軟體工程代理（其結果可透過測試通過與否來驗證）或工具使用代理（其結果通常有明確的黃金答案），工作型代理的交付物往往是文件、試算表或分析報告，這類產出難以用單一二元標準判定對錯。此外，工作型代理的任務高度依賴真實世界的領域知識與檔案內容，這使得純粹由模型生成的合成資料容易失去真實性與多樣性，也使得驗證標準的設計變得更加困難。

**Q4：什麼是證據圖（evidence graph），它在 GraphForge 中扮演什麼角色？**

A：證據圖是 GraphForge 的核心創新，它是一個從真實檔案之間的關係所建構出來的圖結構，圖中的節點代表檔案、資料來源、上下文或從檔案中提取的陳述，而邊則代表這些元素之間的語意關係（例如「資料來源」、「上下文」、「前一年」、「提取的陳述」等）。這個證據圖同時作為任務規格與評分規準的編譯來源：任務陳述從圖中衍生，因此任務需求有工作區檔案作為支撐；而每個評分規準的評分標準都「錨定」（anchored）到驗證該標準所需的具體檔案。這種設計使得任務要求與驗證邏輯都紮根於真實檔案，避免了「任務說一套、評分看另一套」的不一致問題，這是 GraphForge 能兼顧真實性與可驗證性的關鍵。

**Q5：GraphForge 為什麼選擇以職業導向種子（occupation-grounded seeds）作為起點？這種設計如何兼顧多樣性與可控性？**

A：GraphForge 選擇以 O*NET 職業資料庫中的職業及其官方工作活動作為種子，是因為純粹由模型自由發明的任務容易收斂到常見職業與通用任務類型，導致多樣性不足。透過職業導向的種子，任務方向被預先固定（例如「金融與投資分析師」搭配「分析財務資料」這個工作活動），使得多樣性變得可控且可預測。然而，具體任務內容與驗證標準並非由種子決定，而是從該種子所對應的真實檔案中衍生出來，這意味著同一個職業種子可以搭配不同的檔案組合，產生出多樣化但仍聚焦的任務。這種「種子控方向、檔案定細節」的分工是 GraphForge 兼顧多樣性與真實性的關鍵設計選擇。

**Q6：修訂代理（revision agent）在管線中扮演什麼角色？為什麼需要這個步驟？**

A：修訂代理在 GraphForge 中負責在初次教師推演（teacher rollout）之後，根據原始檔案修復任務規格與評分規準中可能存在的問題。這個步驟的存在是因為即使證據圖已經將任務與檔案錨定，初次合成的任務規格仍可能存在可執行性問題，例如任務要求不明確、評分規準無法從現有檔案中驗證、或檔案之間的引用關係斷裂等。透過讓修訂代理僅修改任務與評分規準（而非檔案本身），GraphForge 確保了修訂後的規格仍然紮根於原始的真實檔案。修訂完成後，教師模型會重新執行任務，若任務未變且軌跡可用，則直接重用既有軌跡，這種「執行條件式自我修正合成」機制大幅降低了反覆合成的成本。

**Q7：GraphForge 在哪些基準測試上進行了評估？主要的實驗結果為何？**

A：GraphForge 在三個工作型代理基準測試上進行了評估：GDPVal（涵蓋 44 種職業的 1,320 個任務）、Workspace-Bench-Lite（工作區基準的輕量版）以及 SpreadsheetBench II（試算表基準）。主要的實驗結果顯示，使用 2,169 條 GraphForge 軌跡對 Qwen3.6-27B 進行監督式微調後，在 OpenHands 框架下 GDPVal 達到 1445.7（提升 65.7 分），而在 Claude Code 框架下 Workspace-Bench-Lite 達到 63.7（提升 7.7 分）、SpreadsheetBench II 達到 24.0（提升 13.7 分）。這些跨基準、跨框架的全面提升證明了 GraphForge 合成資料的泛化能力，也顯示其在不同類型的工作任務（從一般職業任務到專門的試算表任務）上都能帶來實質改進。

**Q8：監督式微調（SFT）與拒絕式微調（RFT）在 GraphForge 中如何結合使用？RFT 的選擇訊號來自何處？**

A：GraphForge 採用了兩階段的訓練策略：首先使用 2,169 條軌跡對 Qwen3.6-27B 進行監督式微調（SFT），然後在 SFT 模型的自身推演上進行拒絕式微調（RFT）。RFT 的關鍵在於候選軌跡的選擇訊號——並非隨機篩選，而是使用證據圖錨定的評分規準作為評分依據，由證據錨定評審（evidence-anchored judge）對軌跡進行評分，僅收錄分數高於 0.90 的軌跡。這種設計使得 RFT 不僅僅是「在模型自身輸出上做篩選」，而是利用了 GraphForge 獨有的評分規準所提供的選擇訊號，從而帶來超越單純自我蒸餾的額外提升。實驗結果顯示，這種基於評分規準的 RFT 在三個基準上都帶來了進一步的改進，證明了評分規準本身作為訓練選擇訊號的價值。

**Q9：GraphForge 合成資料的泛化能力如何？是否能在不同基礎模型上產生效益？**

A：根據論文的實驗結果，GraphForge 合成的資料不僅對 Qwen3.6-27B 有效，對 Qwen3.6-35B-A3B 這個不同的基礎模型同樣帶來了改進，這顯示 GraphForge 軌跡具有一定的跨模型泛化能力。這種泛化性是重要的，因為它意味著 GraphForge 並非僅針對特定模型架構進行過擬合，而是學到了與工作型代理任務相關的通用能力，例如多檔案推理、工具協調與長時程執行等。此外，由於 GraphForge 的訓練資料是基於真實檔案與證據圖所建構的，其涵蓋的任務類型與推理模式可能比純粹合成的資料更加多元，這也部分解釋了其跨模型的遷移效果。

**Q10：GraphForge 訓練出的代理適合應用於哪些實際場景？**

A：GraphForge 訓練出的工作型代理特別適合需要跨多個異質檔案進行分析與整合的場景，例如金融分析師需要從年度申報（HTML）、財務報告（XLSX）與公司基本資料（JSON）中提取資訊並建立估值模型；或是顧問需要整合客戶提供的多份文件來產出分析報告。這類任務的共同特徵是：輸入是多樣化的真實檔案、輸出是可被他人使用的結構化交付物、且需要長時程的推理與工具協調。論文中以 NVDA 投資分析工作簿為例，展示了代理需要讀取 2025 年度申報、2025 財務報告、公司基本資料、2024 年度申報與損益表等多個檔案，並進行比率分析與估值建模，這正是 GraphForge 所擅長的場景，也展示了其在真實商業分析中的應用潛力。

**Q11：GraphForge 對工作型代理產品的開發有何啟示？**

A：GraphForge 對工作型代理產品開發的啟示在於：要打造可靠的企業級工作型代理，必須解決「真實資料」與「可靠驗證」這兩個基礎設施層面的問題。傳統的代理產品往往依賴模型生成的合成資料進行訓練，這在面對真實世界的多樣檔案時容易失效；而 GraphForge 證明了透過職業導向的種子、真實檔案的檢索、以及證據圖錨定的評分規準，可以系統性地合成高品質的訓練資料。此外，GraphForge 釋出了訓練好的模型，這對於希望快速建立工作型代理能力的團隊而言是一個可直接利用的起點，能大幅降低從零開始訓練的成本，也為產品迭代提供了可量化的評估基準。

**Q12：GraphForge 對代理研究領域的更廣泛影響是什麼？**

A：GraphForge 對代理研究領域的更廣泛影響在於它提出了一種「以證據為中心」的訓練資料合成範式，這種範式可以擴展到其他需要真實世界資料與可靠驗證的代理任務上。相較於 EnvCraft（合成檔案但驗證受限）與 NexForge（真實檔案但無驗證），GraphForge 透過證據圖同時兼顧了真實性與可驗證性，這種設計思路可以被借鏡到醫療、法律、工程等專業領域的代理訓練中。此外，GraphForge 展示了「評分規準不僅用於評估、也能用於訓練選擇」的觀點，這為代理訓練中的資料篩選與品質控制提供了新的方法論，也為未來結合人類專家反饋的訓練流程奠定了基礎。

**Q13：GraphForge 論文中有哪些已承認的限制？**

A：雖然論文中並未明確列出一個完整的「限制」章節，但從其設計與實驗範圍可以推論出幾項已承認的限制。首先，GraphForge 的規模相對較小——僅合成了 2,169 條軌跡，相較於 EnvCraft 的 20K 任務或 SWE-smith 的 50K 任務，資料規模有限，這可能限制其在更廣泛任務類型上的覆蓋。其次，GraphForge 的評估主要集中在 Qwen3.6 系列模型與 OpenHands/Claude Code 框架上，對於其他模型架構（如閉源商業模型）與其他代理框架的泛化效果尚待驗證。此外，O*NET 職業導向的種子雖然控制了多樣性，但也可能限制了任務的開放性，使得某些跨職業或新興職業的任務難以被涵蓋。

**Q14：GraphForge 可能存在哪些失敗案例或邊緣情況？**

A：從 GraphForge 的設計可以推論出幾類可能的失敗案例或邊緣情況。第一，當真實檔案之間的關係過於稀疏或過於複雜時，證據圖的建構可能不準確，導致評分規準無法有效錨定到檔案，從而影響驗證的可靠性。第二，對於需要高度創造性或開放性答案的任務（例如策略規劃或創意寫作），基於證據圖的評分規準可能過於剛性，無法捕捉答案的細微優劣。第三，當工作區中的檔案存在版本不一致、編碼問題或格式異常時，初次教師推演可能失敗，即使經過修訂代理的修復，仍可能留下難以察覺的問題。第四，對於需要即時資訊或外部 API 呼叫的任務，GraphForge 的離線檔案基礎可能無法支援，這也是其應用範圍的一個邊界。

**Q15：GraphForge 未來可能的研究方向有哪些？**

A：根據論文的設計與實驗結果，可以推論出幾個有前景的未來研究方向。第一，擴大資料規模與任務覆蓋面：將 GraphForge 應用於更多職業、更多檔案類型與更多語言，以提升其在更廣泛場景中的適用性。第二，強化證據圖的建構品質：探索更先進的圖神經網路或大型語言模型技術來提升證據圖的準確性與完整性。第三，將 GraphForge 的「證據錨定」範式擴展到其他領域，例如醫療代理、法律代理或科學研究代理，這些領域同樣需要真實資料與可靠驗證。第四，結合線上學習與人類反饋：將 GraphForge 的評分規準與人類專家的反饋相結合，以進一步提升評分的準確性與細緻度。第五，探索 GraphForge 在多代理協作場景中的應用，例如讓多個工作型代理共同完成一個大型專案，這需要更複雜的證據圖與評分機制，也是值得深入探索的方向。

## 實務應用指南

### 適用場景

**1. 企業財務分析代理的訓練資料建構**
金融機構或投資研究團隊可利用 GraphForge 框架，從 O*NET 的「Financial & Investment Analysts」職業種子出發，自動爬取真實的年報、財報、產業資料，建立涵蓋估值模型、比率分析、跨年度比較的訓練任務。產出的代理能讀取多份財報並產出可驗證的投資分析交付物。

**2. 法律與合規文件工作流的代理化**
法律事務所或合規部門可將 GraphForge 應用於合約審閱、法規比對場景：以「Lawyers」或「Compliance Officers」職業為種子，爬取真實判例、法規文本、內部規範，建立證據圖並編譯出「找出合約中的不一致條款」等可驗證任務，訓練出具備多檔案推理能力的審閱代理。

**3. 跨部門業務流程自動化（試算表密集場景）**
針對 SpreadsheetBench II 類型的試算表操作任務，企業可利用 GraphForge 從「Accountants」、「Bookkeeping Clerks」等職業種子出發，組裝包含多份試算表、CSV、財報的工作區，訓練出能處理長時程試算表操作的代理，特別適用於月底結帳、預算彙整等場景。

**4. 學術研究助理代理的訓練**
研究機構可從「Life Scientists」、「Medical Scientists」等職業種子出發，爬取真實的論文、補充資料、實驗記錄，訓練出能跨多份文獻進行證據彙整、產生文獻回顧章節的研究助理代理。

**5. 內部知識庫問答與報告生成**
企業 IT 部門可將 GraphForge 應用於內部文件（產品規格、會議紀錄、客戶資料）的自動化報告生成：以對應職業種子建立工作區，訓練出能讀取多份內部檔案並產出結構化報告的工作型代理。

### 實作前置條件

**資料前置條件**
- **O*NET 職業資料庫**：需取得美國勞工統計局 O*NET 資料庫的存取權限（含職業分類、工作活動、工作模式等欄位），用於生成職業導向種子。
- **真實檔案來源**：需準備可合法爬取或授權使用的檔案來源（如 SEC EDGAR、政府開放資料、企業公開年報、學術 preprint 平台），並建立檔案分類與覆蓋率統計機制。
- **檔案儲存基礎設施**：需具備可儲存數萬份異質檔案（HTML、XLSX、PDF、JSON 等）的儲存系統，並支援檔案內容索引與中繼資料管理。

**算力前置條件**
- **教師模型 API 存取**：需具備 GPT-4 級別或更強的教師模型 API 存取權限，用於產生證據圖、編譯任務、修訂任務與執行軌跡。
- **GPU 訓練資源**：微調 Qwen3.6-27B 至少需要 8 張 A100/H100 等級 GPU；如要訓練更大的 Qwen3.6-35B-A3B，建議配備 16 張以上 GPU。
- **代理執行環境**：需部署 OpenHands 或 Claude Code 等代理框架的執行環境，每個任務的軌跡產生可能耗費數分鐘到數十分鐘的 API 呼叫。

**技能前置條件**
- **LLM 微調經驗**：熟悉 Hugging Face Transformers、TRL、DeepSpeed 等工具，能處理長序列（>32K tokens）的訓練。
- **代理框架操作能力**：熟悉 OpenHands、Claude Code 等代理框架的設定與部署。
- **圖結構設計能力**：理解證據圖的節點（檔案、資料來源、上下文）與邊（衍生、交叉驗證、跨年度）設計邏輯。
- **評分規準設計經驗**：能設計可被證據錨點化的評分規準，理解如何將抽象標準對應到具體檔案內容。

### 實作步驟建議

**步驟 1：建立職業導向種子系統**
從 O*NET 資料庫擷取職業清單與其工作活動，設計「職業 → 工作活動 → 工作模式 → 任務目標」的四層種子結構。建議先聚焦 5–10 個目標職業（如 Financial Analysts、Accountants、Lawyers、Medical Scientists 等），避免一次性覆蓋過廣。

**步驟 2：實作檔案爬取代理**
建立一個基於 LLM 的爬取代理，根據種子任務目標，從預先整理的檔案來源池中選取 5–10 份相關檔案。實作覆蓋率式選取策略，確保每個工作區包含核心檔案（直接支撐任務）與支援檔案（提供交叉驗證）。為每份檔案標記隱藏角色（core / supporting）與資料類型。

**步驟 3：建構證據圖**
設計證據圖的節點類型（檔案、衍生資料、上下文、跨年度對比）與邊類型（衍生關係、交叉驗證、上下文支撐）。使用教師模型讀取工作區所有檔案，自動建構跨檔案關係圖。建議將圖結構序列化為 JSON 或 YAML，方便後續編譯。

**步驟 4：編譯任務與評分規準**
實作從證據圖到任務聲明與評分規準的編譯器。每條評分規準必須包含：評分標準描述、證據錨點（指向具體檔案與章節）、驗證方式（檔案內容讀取、計算驗證、跨檔案比對）。確保任務需求與工作區檔案內容一致。

**步驟 5：執行初始推演與修訂迴圈**
使用教師模型對每個任務執行初始推演，檢查可執行性。若任務失敗或軌跡缺失，啟動修訂代理：僅修改任務聲明與評分規準（不修改檔案），重新執行教師推演並重用既有軌跡。設定最多一輪修訂以控制成本。

**步驟 6：軌跡收錄與清理**
使用證據錨點評審（evidence-anchored judge）對最終軌跡評分，僅收錄分數 > 0.90 的軌跡。執行軌跡清理，移除無關的探索步驟、錯誤訊息，保留乾淨的執行鏈。

**步驟 7：監督式微調（SFT）**
使用 TRL 或類似框架對 Qwen3.6-27B 進行監督式微調。建議設定：學習率 1e-5 至 5e-5、訓練 2–3 個 epoch、使用長上下文視窗（≥32K tokens）。在 2,169 條軌跡上訓練，預期可在 GDPVal 上獲得 +65 分的提升。

**步驟 8：拒絕式微調（RFT）**
在 SFT 模型基礎上，使用其自身在新查詢（與 SFT 資料不相交）上的推演結果，以證據錨點評分規準作為選擇訊號，篩選高品質軌跡進行第二階段微調。此步驟可進一步提升所有三個基準的表現。

### 潛在風險與注意事項

**風險 1：檔案授權與合規問題**
- **問題**：爬取真實檔案可能涉及著作權、使用條款或隱私爭議。
- **緩解**：僅使用明確開放授權的來源（如 SEC EDGAR、政府開放資料、CC-BY 授權的學術資料）；建立檔案來源審核流程；在資料集中保留來源標註。

**風險 2：證據圖品質不穩定**
- **問題**：教師模型建構的證據圖可能包含錯誤的跨檔案關係，導致評分規準無法驗證。
- **緩解**：設置證據圖品質檢查點（如節點數量下限、邊的合理性檢查）；對低品質圖對應的任務進行人工抽樣審核；保留修訂代理的多次迭代能力。

**風險 3：教師模型偏見放大**
- **問題**：完全依賴教師模型產生軌跡，可能放大其偏見（如特定職業、特定檔案類型的過度代表）。
- **緩解**：使用 O*NET 種子控制職業分佈；對軌跡進行職業、檔案類型的多樣性統計；在評估時使用跨基準測試（GDPVal、Workspace-Bench-Lite、SpreadsheetBench II）檢查泛化能力。

**風險 4：評分規準的可被操控性**
- **問題**：代理可能學會「滿足評分規準」但未真正完成任務（reward hacking）。
- **緩解**：設計多面向的評分規準（事實正確性、計算正確性、格式合規、跨檔案一致性）；使用證據錨點強制要求引用具體檔案內容；定期進行人工對抗測試。

**風險 5：軌跡產生成本過高**
- **問題**：每個任務需執行教師推演與可能的修訂，2,169 條軌跡的產生成本可能達數萬美元。
- **緩解**：實作快取機制（修訂後重用軌跡）；使用較小的教師模型進行初篩；設定成本上限並優先處理高價值職業。

**風險 6：基準測試的代表性限制**
- **問題**：訓練資料集中於特定職業與檔案類型，可能無法泛化到未見過的領域。
- **緩解**：在訓練後保留 10–20% 的職業作為留出集進行測試；定期更新檔案來源以反映真實世界的變化。

### 與其他技術的整合建議

**與代理框架整合**
GraphForge 產出的訓練資料可直接用於微調基於 OpenHands 或 Claude Code 的代理。建議在微調後，使用相同的代理框架進行評估，確保訓練與推論的一致性。若企業已使用自建代理框架，可將 GraphForge 的軌跡轉換為該框架的格式，但需注意工具呼叫介面的對應。

**與 RAG 系統整合**
GraphForge 的證據圖概念可與 RAG 系統互補：將證據圖作為文件檢索的索引結構，提升跨檔案推理的檢索精確度。訓練後的代理可作為 RAG 系統的「推理層」，處理需要多步驟、多檔案檢索的複雜查詢。

**與文件處理管線整合**
可將 GraphForge 的檔案爬取代理整合到企業現有的 ETL 管線中，作為「任務合成器」自動產生訓練資料。證據圖可輸出為結構化知識圖譜，餵入企業的知識管理系統。

**與評測系統整合**
GraphForge 的證據錨點評審機制可整合到企業內部的代理評測平台，作為「可解釋評分」的核心元件。每個評分結果都附帶證據錨點，方便開發者診斷代理失敗的原因。

**與 MLOps 平台整合**
將 GraphForge 的資料合成管線（種子生成 → 檔案爬取 → 證據圖 → 任務編譯 → 軌跡收錄）封裝為可重複執行的 pipeline，使用 Airflow 或 Prefect 等工具排程；將 SFT/RFT 訓練整合到 MLflow 或 Weights & Biases 等實驗管理平台。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）了解 GraphForge 要解決的問題——為什麼工作型代理需要基於真實檔案的訓練資料，以及現有方法的不足。接著看圖 1 的管線總覽，建立對「種子 → 工作區 → 證據圖 → 任務 → 軌跡」流程的直觀理解。實作細節可先跳過，重點掌握「證據錨點」這個核心概念——它如何讓評分規準變得可驗證。

**給 AI 工程師**：重點閱讀第 3 節（方法）與第 4 節（實驗）。理解證據圖的節點/邊設計、任務編譯器的輸入輸出格式、修訂代理的觸發條件。實作時可從單一職業（如 Financial Analysts）開始，建立最小可行版本：先實作檔案爬取與證據圖建構，再逐步加入任務編譯與軌跡收錄。注意評估章節中三個基準的差異——GDPVal 評估交付物品質、Workspace-Bench-Lite 評估多檔案推理、SpreadsheetBench II 評估試算表操作——這有助於設計針對性的訓練資料。

**給研究者**：重點關注三個面向：(1) 證據圖作為任務與驗證的中介表示的理論意涵——它如何統一「任務生成」與「結果驗證」；(2) 拒絕式微調中使用證據錨點評分規準作為選擇訊號的實證效果，這對 RLHF / RFT 研究有方法論啟示；(3) 與 EnvCraft、NexForge 的比較（表 1）揭示的設計取捨——真實性 vs. 可驗證性 vs. 規模。可進一步探索的方向：證據圖是否能用於其他領域（如程式碼、對話）、修訂代理的迭代次數對資料品質的影響、跨語言與跨文化的職業種子擴展。

**給產品經理**：重點理解 GraphForge 的商業價值與限制。價值在於：能用相對低成本（2,169 條軌跡 vs. EnvCraft 的 20K）產生高品質訓練資料，且每個任務都有可驗證的評分標準，這對企業內部代理的品質控管至關重要。限制在於：目前僅支援英文檔案與特定職業類型，且需要大量教師模型 API 呼叫。評估導入時應考慮：(1) 目標業務場景是否落在 O*NET 涵蓋的職業範圍內；(2) 企業是否有可用的真實檔案來源；(3) 訓練後代理的部署成本與維護負擔。建議先以單一高價值場景（如財務分析）進行概念驗證，再逐步擴展。
