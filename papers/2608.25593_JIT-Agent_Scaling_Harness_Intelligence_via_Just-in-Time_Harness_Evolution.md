# JIT-Agent：透過即時線束演化擴展線束智能

**發布日期：** 2026-08-26

## ⚡ TL;DR

現有代理線束多為人工預先設計，難以針對異質任務即時擴展與調整。
JIT-Agent透過三階段訓練，即時生成、修復並演化任務專屬的可執行線束，輔助任意現成LLM。
實驗顯示它讓DeepSeek-V4-Flash超越GPT-5.6，GLM-5.2提升達20.2分。

## 摘要翻譯

代理能力（agent capability）並非僅由模型決定。代理線束（agent harness，涵蓋記憶管理（memory management）、規劃策略（planning strategy）、動作協定（action protocol）與工具/技能編排（tool/skill orchestration））的貢獻可能凌駕於底層基礎模型（underlying foundation model）之上。然而，線束設計（harness design）仍仰賴人工、針對特定任務，且本質上難以擴展。我們提出 JIT-Agent，一個線束智能（harness intelligence）模型，經訓練後可針對任意現成代理式大型語言模型（off-the-shelf agentic LLM）即時合成任務適應性代理線束（task-adaptive agent harness）。我們將代理線束形式化為一種可組合（composable）、機器可生成（machine-generatable）、並受固定四模組協定（four-module protocol）所規範的人工製品（artifact）；並訓練 JIT-Agent 針對當前任務客製化（customize）線束、修復線束以達成穩定可靠執行（stable and reliable execution），並透過從擴大中的既有線束配置檔案庫（expanding archive of prior harness configurations）蒸餾效能訊號（performance signal），實現線束自我演化（harness self-evolution）。在配備 JIT-Agent 作為線束輔助器（harness helper）後，DeepSeek-V4-Flash 於 DeepSearchQA（+9.1）與 OdysseyBench（+4.3）上超越 GPT-5.6，而原本已相當強大的 GLM-5.2 更提升達 +20.2 分。在受控評估中，JIT-Agent 生成的線束於效能上足以與 OpenCode、Claude Code 等成熟代理執行環境（agent runtime）競爭，並持續提升 DeepSeek V4、Mimo-V2.5 與 Qwen3.6 等多尺度模型家族（multi-scale model family）的表現。據我們所知，JIT-Agent 是首個專為即時線束生成（just-in-time harness generation）而設計的模型，確立了線束智能作為代理能力中一個可訓練（trainable）、可遷移（transferable）且可複合（compounding）的維度，且此維度與模型規模擴展（model scaling）正交（orthogonal）。

### 核心貢獻（3～5點）
- 提出首個專為即時線束生成（just-in-time harness generation）設計的模型 JIT-Agent，將代理線束視為可組合、機器可生成的人工製品。
- 建立固定四模組協定（four-module protocol），統一形式化記憶管理、規劃策略、動作協定與工具/技能編排。
- 使 JIT-Agent 具備三大能力：針對當前任務客製化線束、修復線束以達穩定可靠執行、透過蒸餾效能訊號實現線束自我演化。
- 驗證 JIT-Agent 作為線束輔助器（harness helper）能顯著提升多個現成代理式 LLM 的效能，並與成熟代理執行環境競爭。
- 確立線束智能為代理能力中可訓練、可遷移、可複合且與模型規模擴展正交的獨立維度。

### 適合對象
適合對基礎模型、代理系統、大型語言模型工具編排與自動化機器學習感興趣的研究人員與工程師，特別是關注如何透過線束設計而非單純擴大模型規模來提升代理能力者。

## 深度分析

#### 方法論解析

JIT-Agent 的核心命題是將「代理線束（agent harness）」從傳統的 Ahead-of-Time（AOT，預先線束）人工製品，轉變為可由一個專門訓練的元代理（meta-agent）即時合成、修復與演化的機器可生成產物。作者將此定位為 **Model-as-a-Harness（模型即線束）**：不再假設存在一個跨任務泛化的固定線束，而是讓 JIT-Agent 在看到具體任務後，動態產生最適合該任務與底層骨幹模型（backbone model）的執行鷹架（scaffold）。

為了讓線束生成成為可學習的問題，作者先提出一個 **four-module protocol（四模組協定）**，將任何代理線束形式化為四個可組合、可執行的模組：

1. **Memory（記憶）**：決定哪些歷史軌跡（trajectory）與檢索證據（retrieved evidence）被保留，以及如何組織工作記憶（working memory）。
2. **Planning（規劃）**：決定局部意圖（local intent）如何形成，例如是採用並行證據探索（parallel evidence exploration）還是串列的 ReAct 迴圈（ReAct loop）。
3. **Action（動作）**：定義動作協定（action protocol），包含工具呼叫格式、執行順序與驗證／恢復（verification or recovery）條件。
4. **Capability Orchestration（能力編排）**：決定暴露哪些工具／技能（tool/skill orchestration），以及如何根據任務需求編排它們。

這個協定的關鍵在於「可執行性」：JIT-Agent 產生的不是自由格式的自然語言提示，而是符合共同介面的結構化程式碼模組。為此，作者建構了 **Harness Factory（線束工廠）**，一個統一的程式碼庫，收錄多種代表性線束鷹架（如 deep-research、terminal-use、NL2Repo-style coding 等），並讓它們共享同一個四模組介面。這使得線束生成問題被限制在一個「協定誘導的線束空間（protocol-induced harness space）」內，大幅降低合成難度，也讓後續的修復與演化有明確的語法與語意邊界。

在此基礎上，JIT-Agent 採用三階段訓練流程：

**Stage I：任務條件化客製化（Task-Conditioned Customization）**  
此階段讓 JIT-Agent 學習如何根據任務描述，從教師模型產生的協定合規範例中，生成對應的記憶、規劃、動作與能力編排模組。目標是賦予模型 **adaptivity（適應性）**：讓生成的線束能匹配任務結構與底層基礎模型（underlying foundation model）的特性。

**Stage II：回饋驅動的線束修復（Feedback-Driven Harness Repair）**  
此階段將編譯錯誤、介面不匹配、執行期失敗等失敗案例轉換為「有界修復軌跡（bounded repair trajectories）」。JIT-Agent 學習在合成失敗時，如何診斷問題並修正線束，以確保 **reliability（可靠性）**：產生可執行行為並在合成失敗時恢復。

**Stage III：透過 Evo-GDPO 的自我演化（Self-Evolution via Evo-GDPO）**  
此階段引入 **Evolutionary Group-Decoupled Policy Optimization（Evo-GDPO，演化群組解耦策略最佳化）**。其核心想法是將測試時線束改進（test-time harness improvement）內化為模型的訓練能力，而非依賴外部搜尋啟發式。Evo-GDPO 讓 JIT-Agent 提出能超越當前 **archive of prior harness configurations（既有線束配置檔案庫）** 前緣的新線束，同時將獎勵（reward）、延遲（latency）與成本（cost）分開正規化。這提供了 **evolvability（可演化性）**：把執行回饋蒸餾（distillation）成更強的未來線束。

最終訓練出的 **JIT-Agent-27B** 是一個專門的 **harness intelligence model（線束智能模型）**，能在推論時接收任務規格、協定、可執行工具／技能註冊表，以及一小段從檔案庫檢索出的先前线束上下文，然後輸出一個針對當前任務的即時線束（Just-in-Time harness）。當執行回饋與軌跡累積後，它還能修訂線束並更新檔案庫，實現測試時線束演化（test-time harness evolution），而生成器本身保持固定。

#### 實驗數據解讀

論文報告的實驗結果主要用來論證三個命題：（1）線束智能可以顯著提升效率導向的骨幹模型；（2）也能進一步擴展已經很強的模型的上限；（3）JIT-Agent 生成的線束能與成熟的固定代理執行環境（agent runtime）競爭。

**命題一：提升效率型骨幹模型**  
在 **DeepSeek-V4-Flash** 上配備 JIT-Agent 後，模型超越了 **GPT-5.6**：

- **DeepSearchQA**：+9.1 分
- **PinchBench**：+8.7 分
- **OdysseyBench**：+4.3 分

這說明即使底層基礎模型較小或較快，只要線束設計得當，就能在深度研究與多步代理任務上超越更大、更昂貴的對手。這也呼應了作者的核心主張：代理能力（agent capability）不是模型權重的單一函數，而是 **模型–線束配對（model–harness pair）** 的聯合函數。

**命題二：擴展強模型的上限**  
在已經很強的 **GLM-5.2** 上，JIT-Agent 仍能帶來顯著增益：

- **xBench-DS**：+12.0 分
- **AgentIF**：+6.9 分
- 最高可達 +20.2 分的提升

這尤其重要，因為它顯示線束智能不是只在「基線較差」時才有邊際貢獻；即使骨幹模型已經很強，針對任務即時調整執行鷹架仍能釋放額外潛能。這也暗示線束設計與模型規模擴展（model scaling）是某種程度上 **正交（orthogonal）** 的維度。

**命題三：與成熟執行環境競爭**  
JIT-Agent 生成的線束在受控評估中與 **OpenCode** 和 **Claude Code** 等成熟代理執行環境表現相當。這意味著 JIT-Agent 不僅能超越「無線束」的現成代理式大型語言模型（off-the-shelf agentic LLM），還能達到人工精心設計、經過長期迭代的專業運行時水準。

**跨模型家族一致性**  
實驗還顯示，JIT-Agent 的增益能一致地遷移到不同規模的模型家族，包括 **DeepSeek V4**、**Mimo-V2.5** 與 **Qwen3.6**。這支持了「線束智能是可遷移維度（transferable dimension）」的說法：學到的線束生成知識不只對單一模型有效，而是能跨越多尺度模型家族（multi-scale model family）發揮作用。

**潛在解讀與注意事項**  
雖然數據亮眼，但仍有幾點需要謹慎解讀。首先，這些基準（DeepSearchQA、OdysseyBench、PinchBench、xBench-DS、AgentIF）都是高度結構化的代理任務，可能特別適合四模組協定所涵蓋的線束空間。其次，論文未詳細說明成本–延遲權衡的具體數字：雖然 Evo-GDPO 聲稱將 reward、latency 與 cost 解耦正規化，但實際推論開銷（例如生成線束所需的額外 token、檢索檔案庫的延遲）對生產部署的影響仍需更多數據。最後，與 GPT-5.6 和 Claude Code 的比較若未公開其完整配置，可能難以完全複製。

#### 與現有研究的比較

JIT-Agent 與現有研究的關係可從三個軸線理解：**線束工程（harness engineering）**、**測試時最佳化（test-time optimization）** 與 **自我演化代理（self-evolving agents）**。

**相對於傳統線束工程**  
過去的代理系統通常由人工設計固定的記憶、規劃與動作協定，例如 ReAct、Reflexion、LATS 等。這些方法雖然強大，但本質上是 AOT 線束：設計者預先決定一個希望跨任務泛化的鷹架。JIT-Agent 的創新在於將這個設計過程自動化並即時化，讓線束成為任務相關（task-adaptive）且實例相關（instance-dependent）的產物。

**相對於測試時線束最佳化**  
近期研究（如 Lee et al., 2026c; Lin et al., 2026）開始從軌跡與回饋中最佳化線束程式碼、提示、工具與控制策略。這些方法仍多假設線束是一個耐用的、跨任務泛化的產物，需要累積大量經驗軌跡後再部署。JIT-Agent 則採用 Just-in-Time 觀點：不預先編譯一個通用線束，而是在看到具體任務後即時生成。這對部署分佈（deployment distribution）異質的場景特別有利。

**相對於自我演化代理**  
自我設計與自我演化代理的研究通常聚焦於提示、工具或整體系統結構的迭代。JIT-Agent 延續了作者在 **MemEvolve**（記憶模組演化）與 **TodoEvolve**（規劃模組演化）上的工作，但將層次從單一模組提升到完整線束。相較於外部搜尋啟發式（如演化演算法或貝葉斯最佳化），JIT-Agent 透過 Evo-GDPO 將「提出更好線束」的能力直接訓練進模型參數中，使測試時演化成為原生能力而非外部迴圈。

**主要改進**  
1. **形式化**：首次將代理線束明確定義為四模組協定下的可組合、機器可生成產物。  
2. **端到端訓練**：提出從客製化、修復到演化的三階段訓練配方，覆蓋 adaptivity、reliability、evolvability 三個線束智能的核心屬性。  
3. **可遷移性**：證明線束智能能跨模型家族與任務領域帶來一致增益，且與模型規模擴展互補。  
4. **實用競爭力**：生成的線束能與 OpenCode、Claude Code 等成熟運行時競爭。

**限制**  
1. **協定依賴**：四模組協定雖然降低生成難度，但也限制了可表達的線束空間。對於需要非標準模組互動的任務，JIT-Agent 可能無法產生最適解。  
2. **教師品質**：Stage I 依賴教師模型產生的協定合規範例，若教師本身對某些任務領域不熟悉，可能限制學習上限。  
3. **修復覆蓋率**：Stage II 的修復能力取決於訓練時見過的失敗類型；未見過的執行期錯誤仍可能導致系統性失效。  
4. **檔案庫偏誤**：Evo-GDPO 從 expanding archive 中學習，若檔案庫在初期偏向某些任務類型，可能產生回饋迴路偏誤。  
5. **評估透明度**：部分比較對象（如 GPT-5.6、Claude Code）的內部配置未完全公開，實驗條件的一致性有待更多細節驗證。

#### 可重現性評估

根據目前提供的論文內容，**可重現性資訊相當有限**。摘要與引言並未提及：

- 是否釋出原始碼（source code）
- 是否釋出 Harness Factory 的實作
- 是否釋出訓練資料或資料生成流程
- 是否釋出 JIT-Agent-27B 的模型權重（model weights）
- 是否提供可執行的推論腳本或評估流程

這在當前的代理研究領域並不罕見，但對於一個強調「線束生成」這種高度依賴程式碼與執行環境的系統而言，可重現性挑戰特別大。原因包括：

1. **執行環境複雜**：線束生成涉及程式碼執行、工具註冊、狀態管理與錯誤處理，缺少 Harness Factory 的詳細實作難以重現。  
2. **教師資料未公開**：Stage I 的教師生成範例與 Stage II 的失敗修復軌跡若未釋出，其他研究者難以複製訓練資料分佈。  
3. **基準與模型版本**：實驗涉及多個未來或假設性模型名稱（如 GPT-5.6、GLM-5.2、DeepSeek-V4-Flash），其實際可用性與版本對齊會影響結果。  
4. **Evo-GDPO 細節**：演算法中的群組劃分、獎勵函數、正規化權重等超參數未在摘要中說明。

若作者未來能釋出以下內容，將大幅提升可重現性：

- Harness Factory 的開源程式碼與模組介面規範  
- JIT-Agent-27B 的模型權重或 API  
- 訓練資料（至少包含去識別化的任務–線束配對與修復軌跡）  
- 評估腳本與基準資料集的確切切分  
- Evo-GDPO 的完整演算法細節與超參數

#### 未來研究方向

JIT-Agent 開啟了「線束智能（harness intelligence）」作為代理能力獨立維度的研究路線，未來可沿以下方向延伸：

**1. 線上持續演化（Online Continual Evolution）**  
目前的 Evo-GDPO 主要在一個擴大中的檔案庫上進行離線或批次演化。未來可研究如何在部署環境中進行真正的線上學習：讓 JIT-Agent 根據即時使用者回饋與執行失敗，持續更新線束生成策略，同時避免災難性遺忘與回饋偏誤。

**2. 多代理線束（Multi-Agent Harnesses）**  
四模組協定目前聚焦於單一代理的執行鷹架。未來可擴展到多代理系統，讓 JIT-Agent 同時設計多個代理的記憶、規劃、動作協定與它們之間的協作協議（coordination protocol）。

**3. 跨模態與具身任務（Cross-Modal and Embodied Tasks）**  
目前的評估集中在深度研究、程式設計與網頁互動等文本為主的任務。未來可探索 JIT-Agent 在視覺–語言–動作（vision-language-action）、機器人控制或科學實驗等跨模態領域的線束生成。

**4. 開放式線束空間（Open-Ended Harness Space）**  
四模組協定雖然實用，但仍屬於相對受限的設計空間。未來可研究如何讓 JIT-Agent 在更開放的程式空間中發明新模組或新協定，而不僅是實例化既有模組。

**5. 可解釋的線束設計（Interpretable Harness Design）**  
生成的線束是否可被人类理解與審查？未來可加入可解釋性目標，讓 JIT-Agent 在產生線束時同時輸出設計理由，便於除錯、信任與安全審查。

**6. 成本–延遲–品質的動態權衡（Dynamic Cost-Latency-Quality Trade-offs）**  
Evo-GDPO 已將 reward、latency 與 cost 解耦，但未來可進一步研究如何根據使用者偏好或服務等級協議（SLA）動態調整這些目標的權重，實現自適應的線束複雜度選擇。

**7. 安全與對齊（Safety and Alignment）**  
自動生成可執行線束帶來新的安全風險：模型可能設計出繞過安全檢查的動作協定，或產生過度激進的工具編排。未來需要研究如何將安全約束嵌入線束生成過程，例如透過形式化驗證或對抗性訓練。

**8. 開源線束智能生態系（Open-Source Harness Intelligence Ecosystem）**  
若 Harness Factory 與 JIT-Agent 能開源，將促成社群貢獻新的模組、工具與任務領域，形成類似 Hugging Face 的線束模型生態系，加速線束智能的累積與複合（compounding）。

## 論文問答

**Q1：什麼是代理線束（agent harness），為什麼它對代理能力如此重要？**

A：代理線束是支撐代理在閉環執行環境中運作的整體架構，涵蓋記憶管理、規劃策略、動作協定以及工具／技能編排等關鍵元件。它決定了模型在執行過程中保留哪些歷史資訊、如何形成局部意圖、暴露哪些工具、如何執行動作，以及何時觸發驗證或恢復機制。因此，代理能力並非僅由底層基礎模型的權重決定，而是取決於「模型–線束配對」；一個強大的模型若搭配錯誤的記憶或規劃器仍可能失敗，凸顯線束設計是一階決定因素而非實作細節。

**Q2：Ahead-of-Time（AOT）線束範式是什麼，它有哪些根本限制？**

A：AOT 線束範式將線束視為一種耐用的、可事前最佳化的人工製品，期望透過累積軌跡與回饋，使最終產出的線束能泛化到未來任務、領域或模型版本。這種方法在部署分佈穩定且同質時效果良好，但現實中的任務需求往往是異質且實例相關的，例如深度研究需要工作記憶來保存檢索證據，而終端機任務則偏好精簡的序列 ReAct 迴圈。由於 AOT 必須在尚未看到未來問題的確切結構前，就預編譯一個廣泛適用的鷹架，因此不僅設計空間龐大、需要大量軌跡累積，還容易出現單一線束無法匹配多樣化需求的困境。

**Q3：為何本文認為線束設計是代理效能的「一階決定因素」，而非單純的實作細節？**

A：因為線束直接塑造了模型與外部環境互動的方式，包括歷史保留、意圖形成、工具暴露、動作執行與錯誤恢復等關鍵環節，這些環節的優劣會主導最終的任務表現。研究顯示，代理智能並非模型權重的單一屬性，而是模型與線束緊密耦合後的整體性質；一個強大的線束只有在模型能夠理解並遵循其協定的前提下才能釋放潛能。因此，線束設計的影響力可與基礎模型本身相提並論，甚至在某些情境下超越模型規模擴展所帶來的增益。

**Q4：JIT-Agent 的核心概念是什麼？「模型即線束（Model-as-a-Harness）」與傳統做法有何不同？**

A：JIT-Agent 是一個專門訓練來即時生成任務適應性代理線束的元代理模型，它在推論時接收任務規格、四模組協定、可執行的工具／技能登錄檔，以及一小段從既有線束配置檔案庫檢索出的先驗情境，然後輸出針對當前任務量身打造的執行線束。與傳統 AOT 將線束視為預先最佳化並長期使用的耐用鷹架不同，Model-as-a-Harness 主張由訓練後的生成器動態合成線束，並讓任意現成代理式大型語言模型在該線束下執行。這種範式將線束工程從「事前打造通用人工製品」轉變為「即時原生合成」，使線束能夠隨任務結構與模型特性而變化。

**Q5：JIT-Agent 如何將線束形式化為可生成的結構？四模組協定與 Harness Factory 扮演什麼角色？**

A：JIT-Agent 將代理線束形式化為一個由記憶、規劃、動作與能力編排四個可組合模組構成的機器可生成人工製品，並透過 Harness Factory 提供統一介面下的代表性鷹架程式碼庫。這種協定誘導的設計空間讓線束生成從「無限制地撰寫完整代理程式」轉變為「在固定結構中實例化與組合模組」，大幅降低了合成難度與執行風險。由於程式碼承載了線束語義，生成器輸出的是結構化且可執行的模組，而非鬆散的描述，從而確保產出的線束能夠被現成模型直接理解與執行。

**Q6：JIT-Agent 的三階段訓練流程如何分別對應線束智能的三個核心性質？**

A：第一階段透過教師生成的協定合規範例進行任務條件化的客製化學習，賦予生成器適應性，使其能根據不同任務結構選擇合適的記憶、規劃與動作組合。第二階段將失敗的線束生成轉換為有界的修復軌跡，把編譯錯誤、介面不匹配與執行期失敗轉化為監督訊號，從而提升可靠性並學會在合成失敗時恢復。第三階段引入 Evolutionary Group-Decoupled Policy Optimization（Evo-GDPO），透過最佳化生成器提出能超越既有檔案庫前緣的線束，同時分別正規化獎勵、延遲與成本，實現可演化性，使測試時的線束改進成為模型內建能力而非外部搜尋啟發式。

**Q7：論文在哪些基準與模型上評估了 JIT-Agent？**

A：實驗涵蓋多個異質代理基準，包括 DeepSearchQA、OdysseyBench、PinchBench、xBench-DS 與 AgentIF，這些基準分別對應深度研究、多領域推理、終端操作與代理互動等不同任務型態。模型方面，研究以 DeepSeek-V4-Flash、GLM-5.2 為主要骨幹，並進一步測試 DeepSeek V4、Mimo-V2.5 與 Qwen3.6 等多尺度模型家族上的泛化效果。此外，論文也將 JIT-Agent 生成的線束與 GPT-5.6，以及成熟的代理執行環境如 OpenCode 與 Claude Code 進行對照，以檢視其競爭力。

**Q8：JIT-Agent 帶來了哪些關鍵量化結果？**

A：在 DeepSeek-V4-Flash 上搭配 JIT-Agent 後，模型在 DeepSearchQA 上超越 GPT-5.6 達 9.1 分，在 PinchBench 上領先 8.7 分，在 OdysseyBench 上領先 4.3 分，顯示線束智能能有效提升高效骨幹的表現。對於已經很強的 GLM-5.2，JIT-Agent 進一步推升天花板，在 xBench-DS 上帶來 12.0 分的絕對增益，在 AgentIF 上提升 6.9 分。這些結果一致地出現在不同規模的模型家族中，並且 JIT-Agent 生成的線束在效能上能與 OpenCode、Claude Code 等成熟執行環境相抗衡。

**Q9：控制實驗與消融結果揭示了什麼？**

A：控制評估顯示，JIT-Agent 生成的線束不僅能穩定改進未經調整的現成代理式大型語言模型，還能與已經高度成熟的固定代理執行環境達到相近甚至更好的效能水準。在多尺度模型家族上的實驗進一步證明，線束智能具有可遷移性，同一個訓練後的 JIT-Agent 能為 DeepSeek V4、Mimo-V2.5 與 Qwen3.6 等不同架構與規模的模型帶來一致增益。這些結果也暗示，透過適當的成本與延遲正規化，JIT-Agent 能將骨幹–線束配對推向更佳的成本–效能前緣，而不只是單純追求最高分。

**Q10：JIT 線束生成在哪些實際應用場景中最具價值？**

A：JIT 線束生成特別適合任務流異質、領域快速變動，或需要在有限資源下動態適配新工具與新模型的場景，例如深度研究問答、終端機自動化、NL2Repo 風格程式設計任務，以及產品生成與自主研究等開放式代理任務。在這些情境中，單一預先線束難以同時滿足並行證據探索、序列 ReAct 迴圈、檔案系統狀態維護等多樣化需求，而即時生成的線束能根據每個實例的結構選擇最合適的記憶與規劃機制。對於希望在不重新訓練底層基礎模型的前提下提升代理能力的產品團隊而言，JIT-Agent 提供了一種可擴展且可複合的增強路徑。

**Q11：在產品化部署 JIT-Agent 時，需要考慮哪些實務議題？**

A：首先，必須建立可執行且受控的工具／技能登錄檔與沙箱環境，確保生成出的線束能安全地與外部系統互動，並在編譯或執行失敗時被妥善隔離。其次，線束生成的延遲、執行成本與檔案庫管理需要納入設計，因為每次推論都涉及即時合成與可能的多次修復迭代，Evo-GDPO 中的獎勵、延遲與成本正規化機制正是為此而設。最後，產品團隊應持續監控生成線束的穩定性與安全性，避免獎勵駭取或對未見任務的過度擬合，並建立人機協作的驗證流程來確保高風險動作的正確性。

**Q12：JIT-Agent 可能對代理設計領域帶來什麼樣的影響？**

A：JIT-Agent 首次將線束智能確立為一個可訓練、可遷移且可複合的獨立維度，並證明它與模型規模擴展是互補而非替代的關係。這意味著未來的代理系統設計可以將更多心力放在如何訓練「會設計線束的模型」，而非僅僅追求更大的基礎模型或手工打造固定鷹架。長遠來看，這種能力也為遞迴式自我設計與自我演化的代理系統奠定基礎，使代理能夠持續從執行回饋中改進自身的運作架構，進而加速整個領域從手工工程走向自動化架構搜尋。

**Q13：論文可能承認哪些限制？**

A：作為一個 27B 規模的緊湊元代理，JIT-Agent 在面對極度複雜或高度創新的線束設計問題時，其推理與合成能力仍有上限。此外，生成空間受限於預先定義的四模組協定與 Harness Factory 中的代表性鷹架，這雖然提升了可靠性，卻也可能限制對全新線束範式的探索。修復能力也取決於訓練過程中見過的失敗模式分佈，對於完全超出訓練分佈的錯誤類型，穩定性可能下降；同時，即時生成與修復所帶來的延遲與計算成本，也是在實際部署中必須權衡的議題。

**Q14：JIT-Agent 可能出現哪些失敗案例？**

A：當任務規格過於模糊或工具介面描述不完整時，生成器可能產出無法編譯或執行的線束，即便第二階段的修復訓練能處理部分問題，仍可能陷入反覆修復的循環。若生成的線束與底層現成模型的理解能力或動作空間不匹配，例如規劃策略過於複雜而模型無法遵循，則執行階段會出現穩定性問題。此外，若既有線束配置檔案庫過度偏向某些任務類型，生成器可能對新領域過度擬合或複製次優設計；Evo-GDPO 在極端情況下也可能為了追求獎勵而犧牲可解釋性或安全性。

**Q15：未來研究可以朝哪些方向延伸？**

A：未來可以探索線上終身學習式的線束演化，使 JIT-Agent 在持續執行中不斷吸收新任務的回饋，而非僅依賴靜態擴大的檔案庫。另一個方向是將人類設計師的回饋納入訓練迴路，讓線束生成不僅優化自動化指標，也能符合人類對可解釋性、可控性與安全性的偏好。此外，擴展協定空間至多代理協作、跨模態感知或更動態的工具組合，並從理論上深入理解模型–線束配對的耦合機制，將有助於進一步釋放線束智能的潛力，並推動代理系統朝向真正的自我演化邁進。

## 實務應用指南

### 適用場景

1. **企業內部深度研究與跨部門問答助理**  
   不同部門的查詢結構差異極大：法規查詢需要廣泛並行證據探索，財報分析需要長程工作記憶來追蹤檢索出的證據。JIT-Agent 可為每個查詢即時合成最適的記憶管理、規劃策略與工具編排，讓單一底層模型在異質任務上都維持高表現。

2. **軟體開發與程式碼倉庫維護（NL2Repo 風格）**  
   面對 issue、PR 或重構需求時，任務實例會要求不同的檔案系統操作、測試執行與修補檔管理。JIT-Agent 可根據儲存庫狀態與問題描述，即時產生包含檔案系統狀態追蹤、動作協定與驗證恢復機制的代理線束，輔助現成代理式大型語言模型完成開發任務。

3. **終端機與雲端維運自動化**  
   故障排查任務常需要精簡的序列 ReAct 迴圈，而根因分析則可能需要並行收集多項指標。透過即時線束，系統可針對當前告警動態選擇觀測工具、執行順序與回退策略，提升穩定可靠的執行率。

4. **客戶服務與跨管道對話代理**  
   同一對話在不同階段需要不同的局部意圖形成方式與記憶保留策略。JIT-Agent 能依據對話狀態即時調整線束，例如切換從「資訊收集」到「交易執行」所需的動作協定與驗證機制。

5. **科學研究與文獻綜合**  
   深度研究任務需要在工作記憶中維護大量檢索出的證據，並隨著新資訊調整規劃。即時線束可為每個研究主題建立專屬的證據組織與推理鷹架，避免單一預先線束難以適配多元主題的問題。

### 實作前置條件

**資料條件**
- 清晰的任務規格與領域分類，能描述每個實例的結構與需求。
- 可執行的工具/技能註冊表，讓 JIT-Agent 知道有哪些能力可以編排。
- 種子線束範例：可由教師生成或人工撰寫，且符合四模組協定（記憶、規劃、動作、能力編排）。
- 歷史執行軌跡、回饋與既有線束配置檔案庫，用於修復學習與即時線束演化。

**運算條件**
- 訓練階段需要足夠的 GPU 叢集資源，以支撐類似 JIT-Agent-27B 規模的模型進行三階段訓練。
- 推理階段需要能即時執行線束生成與沙箱驗證的環境，並保留給底層代理式大型語言模型執行的運算預算。
- 持續評估與進化需要可擴展的執行叢集，用於收集效能訊號與更新檔案庫。

**技能條件**
- 熟悉代理線束設計、記憶管理、規劃策略與工具編排。
- 具備程式生成、結構化輸出與程式碼執行沙箱的實作經驗。
- 了解強化學習或偏好最佳化，能實作或調整 Evo-GDPO 這類分離獎勵、延遲與成本的訓練流程。
- 具備評測基礎建設，能穩定執行多基準測試並比較成本–效能前沿。

### 實作步驟建議

1. **定義四模組協定並建立 Harness Factory**  
   將代理線束形式化為記憶、規劃、動作、能力編排四個可組合模組，並建立統一程式介面與代表型鷹架。這讓線束生成從「自由撰寫代理程式」轉為「在受控設計空間中實例化模組」。

2. **收集種子資料與教師範例**  
   針對目標領域產生大量協定合規的線束範例，涵蓋不同任務結構。這些範例是 Stage I 客製化學習的監督訊號來源。

3. **Stage I：任務條件化的線束客製化**  
   訓練 JIT-Agent 根據任務規格與協定，生成對應的四模組線束。重點在於讓模型學會「什麼任務需要什麼樣的記憶、規劃與動作協定」。

4. **Stage II：失敗驅動的線束修復**  
   建立編譯錯誤、介面不匹配與執行失敗的修復軌跡。讓 JIT-Agent 學會在生成不可執行線束時，如何修正為穩定可靠的版本。

5. **Stage III：Evo-GDPO 即時線束演化**  
   利用執行回饋與擴大中的檔案庫，訓練 JIT-Agent 提出能超越當前檔案庫前沿的線束。透過分離獎勵、延遲與成本，避免單一目標過度優化。

6. **部署為線束輔助器**  
   在生產環境中，JIT-Agent 接收任務後即時生成線束，並將其包裝在現成代理式大型語言模型外圍執行。保持生成器固定，但允許測試時線束修訂。

7. **持續監控與檔案庫更新**  
   累積執行軌跡、追蹤紀錄與效能訊號，定期將優秀線束納入既有線束配置檔案庫，並安排週期性微調或重訓練，以維持遷移與複利效應。

### 潛在風險與注意事項

- **線束不可執行或介面不匹配**  
  即使生成結構正確，仍可能因工具版本或環境差異導致執行失敗。建議搭配沙箱測試與 Stage II 修復機制，並在正式執行前進行編譯與介面檢查。

- **任務過度擬合**  
  若訓練資料過度集中於少數領域，JIT-Agent 可能生成只適用特定實例的線束。應維持協定誘導的設計空間，並透過多領域基準與跨任務泛化測試監控。

- **延遲與成本上升**  
  即時線束生成會增加額外推理開銷。Evo-GDPO 雖然已將延遲與成本納入正規化，但產品部署時仍需設定明確的延遲預算與成本上限，並準備備用預先線束。

- **安全與權限風險**  
  動作協定與工具編排可能觸發檔案修改、API 呼叫或指令執行。必須實施最小權限原則、人機確認閘門，以及完整的執行日誌與回滾機制。

- **底層模型版本漂移**  
  當底層基礎模型更新時，原本有效的線束可能失效。應建立回歸測試與持續進化流程，讓線束能隨模型版本與任務分佈變化而調整。

---

### 與其他技術的整合建議

- **與現有代理執行環境整合**  
  JIT-Agent 可作為動態線束層，疊加在 OpenCode、Claude Code 等成熟執行環境之上，負責根據任務即時調整記憶、規劃與工具編排，而保留既有工具鏈與使用者介面。

- **與檢索增強生成（RAG）/向量資料庫整合**  
  在生成線束前，先從既有線束配置檔案庫中檢索相似任務的歷史線束作為上下文，可提升客製化品質並加速收斂。

- **與 LLMOps 管線整合**  
  將線束生成、執行、評估、A/B 測試與回滾納入標準化管線，讓線束演化成為可觀測、可複現的產品迭代環節。

- **與可觀測性工具整合**  
  透過追蹤紀錄、執行回饋與效能訊號，持續餵養 JIT-Agent 的修復與演化階段，形成資料閉環。

- **與企業知識圖譜整合**  
  將知識圖譜作為能力編排模組中的語意工具註冊，讓 JIT-Agent 在生成線束時能自動選擇最相關的企業內部資料來源。

### 給不同背景讀者的閱讀建議

**初學者**  
先把「代理線束」理解為支撐大型語言模型行動的作業系統：它決定模型記住什麼、怎麼規劃、如何呼叫工具。JIT-Agent 則是一位「任務專屬的線束設計師」，在每次任務來臨時即時畫出藍圖，再讓現成 LLM 照著執行。建議從四模組協定與 ReAct 迴圈等基礎概念開始，再進入三階段訓練。

**AI 工程師**  
重點關注 Harness Factory 的介面設計、四模組協定的實作細節，以及 Stage II 的修復軌跡如何從真實編譯與執行錯誤中構建。評估時請同時看準確率、延遲與成本三個維度，並思考如何將 JIT-Agent 嵌入現有 agent runtime 而不破壞既有工具鏈。

**研究人員**  
本文的核心貢獻在於將 harness intelligence 形式化為可訓練、可遷移且可複合的維度，並提出 Model-as-a-Harness 範式。值得深入分析即時線束演化與 Evo-GDPO 的理論特性，例如分離獎勵、延遲與成本對策略最佳化的影響，以及線束智慧是否真能與模型規模擴展正交。

**產品經理**  
請優先理解適用場景與成本–效益權衡：JIT-Agent 能讓同一個底層模型在多領域任務上獲得顯著提升，但會增加即時生成的延遲與運算成本。建議從高價值、任務異質性強的場景切入，並規劃與現有產品、RAG、LLMOps 的整合路徑，把持續進化視為長期競爭優勢。
