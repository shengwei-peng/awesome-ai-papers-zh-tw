## 摘要翻譯

使用工具的語音代理（Tool-Using Voice Agents）經常在使用者語音結束後讓使用者等待，即使可操作的資訊在請求中較早到達。推測式方法在語音期間即開始作業，但片段界定的生成（Chunk-Bounded Generation），或是更新時中斷式生成（Interrupt-on-Update Generation），可能在其參數完整之前截斷工具呼叫。這使得運算時間與語音更新耦合，限制了能預先完成的有用工作。我們提出心跳思考（Heartbeat Thinking），透過新的思考器（Thinker）呼叫處理更新輸入，同時允許進行中的呼叫和已分派工具完成。週期性呼叫讀取最新部分轉錄文字，以及已完成推理與工具結果的共用記錄。這些結果有助於解決缺失參數並啟動相依呼叫，使準備作業能在多次語音更新間持續推進。在 SpeechFCEval、FDBench v3 和 AudioCRAG 上，心跳思考相較於 SHANKS 風格的視窗式基準（Windowed Baseline），提升了整體推測式工具覆蓋率或檢索重用，並對最終任務品質產生基準相依效應。在 FDBench v3 上，其將工具覆蓋率提高了 16 個百分點，並將平均最終回應延遲降低了 36.4%。結果顯示，心跳思考典範能在語音期間保留進行中的運算，進而將聆聽時間轉化為可重用的準備作業，從而實現更快且更強大的語音代理回應。

### 核心貢獻（3～5點）
- **問題洞察**：揭示使用工具的語音代理在語音結束後仍讓使用者空等，即使可操作的資訊早在請求中段即已到達，造成不必要的回應延遲。
- **既有方法限制分析**：指出片段界定的生成與更新時中斷式生成會在工具參數尚未完整時即截斷工具呼叫，使運算時間與語音更新緊密耦合，限制了能預先完成的有用工作量。
- **方法創新**：提出心跳思考典範，透過週期性呼叫讀取最新部分轉錄文字與已完成推理及工具結果的共用記錄，使準備作業能跨越多次語音更新持續推進，同時保留進行中的呼叫與已分派工具不被中斷。
- **實驗成果**：在 SpeechFCEval、FDBench v3 與 AudioCRAG 三項基準測試中，心跳思考相較於 SHANKS 風格的視窗式基準，提升了整體推測式工具覆蓋率或檢索重用；在 FDBench v3 上，工具覆蓋率提升 16 個百分點，平均最終回應延遲降低 36.4%。
- **典範轉移**：證明將聆聽時間轉化為可重用的準備作業是可行的，為更快且更強大的語音代理回應開啟新方向。

### 適合對象
從事即時語音代理、對話式 AI、檢索增強生成（RAG）、工具增強語言模型（Tool-Augmented LLM）研究與開發的學者與工程師；對串接式管線延遲瓶頸、推測式推理與非同步執行架構設計感興趣的研究人員；以及關注語音使用者體驗優化與邊緣／雲端協同運算的業界實務者。

## 深度分析

#### 方法論解析

**核心問題與動機**

本論文針對使用工具的即時語音代理 (Realtime Voice Agents) 中一個關鍵的使用者體驗瓶頸：使用者停止說話後，代理往往需要等待模型運算 (model computation) 與外部執行 (external execution) 才能產生回應，造成可觀察的延遲。雖然資訊可能在語音早期就已具備可操作性 (actionable information)，但傳統串接式管線 (cascaded pipelines) 將準備作業 (preparation) 完全延後至語音結束後才開始，浪費了聆聽時間 (listening time) 這段寶貴的運算資源。

**推測式準備的既有困境**

先前研究已嘗試在聆聽期間進行推測式準備 (speculative preparation)，但面臨兩個結構性限制：

1. **片段界定的生成 (chunk-bounded generation)**：SHANKS 將每個生成回合 (generation episode) 限制在單一語音片段 (speech chunk) 內，可能在工具呼叫 (tool call) 的參數尚未完整時就遭截斷 (truncation)，導致無法分派 (dispatch)。
2. **更新時中斷式生成 (interrupt-on-update generation)**：SIA 在新語音事件到達時中斷進行中的生成，雖然已分派工具 (dispatched tools) 獨立管理，但呼叫本身可能在發出前就被中斷。

兩者的共同缺陷是將運算時間 (computation time) 與語音更新 (speech updates) 緊密耦合，限制了不中斷時間 (uninterrupted time) 的可用性。

**Heartbeat Thinking 的架構設計**

Heartbeat Thinking 採用「解耦並行」策略，由三個核心元件組成：

- **週期性思考器 (Periodic Thinker)**：每隔 Δ 秒啟動一次新的呼叫 (invocation)，讀取最新的部分轉錄文字 (latest partial transcript) 與共用記錄 (shared record) 中的已完成推理 (completed reasoning) 與工具結果 (tool results)。最多允許 K 個並行呼叫，當所有槽位被佔用時跳過此次觸發。
- **共用狀態 (Shared State)**：儲存已完成推理記錄、已請求呼叫及其返回結果，扮演跨呼叫的資訊交換媒介。
- **回應器 (Responder)**：在偵測到語音結束 (end-of-speech detection) 時觸發，接收完整請求 (complete request) 與交接時可用的準備結果，產出最終答案 (final answer)。

**關鍵設計原則**

1. **不中斷原則 (Non-interruption Principle)**：新語音與工具結果進入後續呼叫，但不中斷進行中的生成。這使得一個呼叫可以完成工具呼叫的構造，即使另一個呼叫正在處理更新輸入。
2. **非同步執行 (Asynchronous Execution)**：模型運算與工具執行可重疊；完成的推理在工具分派前即被記錄，使兩者解耦。
3. **累積式準備 (Accumulated Preparation)**：後續呼叫可利用已返回的結果來解決缺失參數 (missing arguments) 或啟動相依呼叫 (dependent calls)，即使轉錄文字未變化也能推進準備進度。
4. **明確交接 (Explicit Handoff)**：在語音結束時，排程器停止新呼叫、取消未完成的推測式任務（包括佇列中的呼叫），讓回應器無需等待即可開始。

**Thinker 與 Responder 的角色分離**

此分離帶來兩個重要優勢：(1) 推測式準備與回應生成 (response generation) 可使用不同模型，各自最佳化；(2) 回應器可檢查已完成工作是否適用於完整請求，重用適用結果並執行剩餘呼叫，避免重複運算。

**與 SHANKS 的本質差異**

SHANKS 透過「已完成工具結果」在解耦系統間交換準備狀態，但每個生成回合仍受語音片段邊界限制。Heartbeat 則透過「已完成推理記錄 + 工具結果」的雙重介面，連接獨立排程的呼叫，使運算能跨越語音更新持續進行。這是從「片段內完成」到「跨片段累積」的典範轉移。

#### 實驗數據解讀

**評測基準 (Benchmarks)**

論文在三個基準測試上進行實驗：
- **SpeechFCEval**：語音功能呼叫評測
- **FDBench v3**：金融領域基準測試 v3 版本
- **AudioCRAG**：音訊檢索增強生成基準

**核心指標**

- **整體推測式工具覆蓋率 (Aggregate Speculative Tool Coverage)**：衡量在語音結束前已完成的工具呼叫佔最終所需工具的比例
- **檢索重用 (Retrieval Reuse)**：推測式檢索結果在最終回應中被重用的程度
- **平均最終回應延遲 (Mean Final-Response Latency)**：從語音結束到產生最終回應的時間
- **最終任務品質 (Final Task Quality)**：最終回應的正確性/品質

**關鍵實驗結果**

在 FDBench v3 上，Heartbeat Thinking 展現最顯著的改進：
- 工具覆蓋率從 34.67% 提升至 50.67%（增加 16 個百分點）
- 平均最終回應延遲從 6.90 秒降至 4.39 秒（降低 36.4%）
- 延遲比最快的串接式基準 Pipecat 低 45.7%

**結果的基準相依效應 (Benchmark-Dependent Effects)**

值得注意的是，覆蓋率優勢在所有測試的回應器中皆持續存在，但任務品質的改善呈現基準相依：
- **FDBench v3**：任務品質優於 Window Thinking
- **SpeechFCEval 與 AudioCRAG**：任務品質略有下降

**結果的深層意涵**

1. **覆蓋率提升的機制**：Heartbeat 透過不中斷的累積式準備，使更多工具呼叫能在語音結束前完成，這是延遲降低的直接原因。
2. **品質下降的可能原因**：在 SpeechFCEval 與 AudioCRAG 上，雖然準備更多，但推測式結果可能不完全適用於完整請求（例如使用者後續新增預算限制 (budget constraint) 改變了配送問題 (delivery concern) 的需求），導致回應器需要更多修正工作。
3. **覆蓋率與品質的權衡**：結果揭示一個重要張力——更多準備不等於更好品質；推測式結果的「適用性判斷」是獨立於「準備量」的挑戰。

#### 與現有研究的比較

**定位 (Positioning)**

Heartbeat Thinking 屬於「早期準備」研究譜系中的一員，與以下工作有明確的傳承關係：

| 方法 | 準備時機 | 跨更新持續性 | 介面設計 |
|------|---------|------------|---------|
| LiveMind (Chen et al., 2024) | 前綴式推理 | 受限 | 內部狀態 |
| PredGen (Li and Grover, 2025) | 回應草稿 | 受限 | 串流輸出 |
| LTS-VoiceAgent (Zou et al., 2026) | 維持推理狀態 | 部分 | 內部狀態 |
| SHANKS (Chiang et al., 2026) | 片段內準備 | 否 | 工具結果 |
| DuplexOmni (Huang et al., 2026) | 串流輸出 | 部分 | 串流輸出 |
| AsyncReasoning (Yakushev et al., 2025) | 模型內部狀態 | 是 | 內部狀態 |
| **Heartbeat (本文)** | **週期性累積** | **是** | **推理記錄 + 工具結果** |

**相較於 SHANKS 的改進**

SHANKS 的核心限制在於「片段界定」——每個生成回合必須在語音片段邊界內完成，這使得需要較長推理鏈或複雜參數構造的工具呼叫容易被截斷。Heartbeat 透過「不中斷」原則與「共用記錄」介面，使運算能跨越多個語音更新持續進行，這是結構性的改進而非單純的工程優化。

**相較於 SIA 的改進**

SIA 採用「更新時中斷」策略，雖然已分派工具獨立管理，但呼叫本身可能在發出前被中斷。Heartbeat 透過允許舊呼叫完成、新呼叫處理更新，實現了真正的並行而非中斷-重啟模式。

**相較於 Stream RAG 的互補**

Stream RAG 探索平行檢索 (parallel retrieval) 並檢查中間結果 (intermediate results) 的適用性，Heartbeat 則將此思想擴展到一般工具呼叫，並透過共用記錄使後續呼叫能利用先前結果。

**論文坦承的限制**

作者明確指出：「interpreting and using speculative results remains a separate challenge」（詮釋與使用推測式結果仍是獨立挑戰）。這反映在 SpeechFCEval 與 AudioCRAG 上任務品質的下降，說明 Heartbeat 解決了「準備量」問題，但「準備品質」與「結果適用性判斷」仍需後續研究。

#### 未來研究方向

**1. 推測式結果的適用性判斷**

論文最明確指出的後續方向是「如何判斷已完成準備是否適用於完整請求」。可能的研究路徑包括：
- 訓練專門的「適用性分類器」評估每個推測式結果
- 在回應器中加入「驗證步驟」，主動檢查推測式結果與完整請求的一致性
- 設計「信心度標記」機制，讓 Thinker 標註每個結果的可信度

**2. 動態排程策略**

當前的固定 Δ 與 K 設定可能不是最優的。未來可探索：
- **自適應心跳間隔**：根據語音更新頻率或任務複雜度動態調整 Δ
- **彈性並行上限**：根據工具執行負載動態調整 K
- **優先級排程**：讓更可能適用的準備任務獲得更高優先級

**3. 錯誤恢復與一致性**

當推測式結果與最終請求矛盾時（例如使用者改變主意），需要優雅的恢復機制：
- 「撤銷-重做」機制：偵測矛盾後撤銷相關推測式結果
- 「增量修正」：而非完全重做，盡可能重用部分適用的結果
- 「使用者確認」：在關鍵決策點請求使用者確認

**4. 多模態擴展**

當前方法專注於語音輸入，未來可擴展至：
- 視訊串流中的推測式準備
- 多使用者對話中的準備協調
- 跨模態資訊融合（例如語音 + 螢幕分享）

**5. 理論分析**

論文的實驗結果揭示了「準備量」與「任務品質」之間的張力，但缺乏理論框架：
- 形式化定義「適用性」與「重用率」
- 分析不同任務類型的最優準備策略
- 建立覆蓋率-品質的權衡邊界

**6. 與其他典範的整合**

Heartbeat 可與其他語音代理技術整合：
- 與端到端語音模型（如 DuplexOmni）結合，探討混合架構
- 與強化學習結合，最佳化準備策略
- 與聯邦學習或邊緣運算結合，處理隱私與延遲需求

**7. 使用者體驗研究**

最終回應延遲降低 36.4% 是否帶來對應的使用者滿意度提升，需要使用者研究驗證：
- 主觀評測：使用者感知到的回應速度
- 任務效率：完成任務所需的總時間
- 認知負荷：使用者等待時的認知狀態

**8. 基準測試擴展**

現有三個基準的覆蓋面有限，未來可開發：
- 更複雜的多輪對話基準
- 需要多步推理的工具呼叫基準
- 包含矛盾或修正的基準（測試錯誤恢復）

這些方向不僅能延伸 Heartbeat 的技術貢獻，也能深化我們對「即時互動中推測式運算」這一更廣泛問題的理解。

## 論文問答

**Q1：為什麼傳統串接式語音代理在使用工具時會讓使用者等待？**
A：傳統串接式管線（cascaded pipelines）通常將準備作業（preparation）安排在使用者語音結束之後才開始進行，這意味著模型運算（model computation）與外部執行（external execution）都必須等到完整請求（complete request）抵達後才能啟動。然而，使用者語音中往往很早就包含了可操作的資訊（actionable information），例如在描述配送問題（delivery concern）時就已提及訂單編號，但代理卻無法提前利用這些資訊。這種「先聽完再行動」（listen, then act）的典範造成了不必要的等待時間，特別是在需要多次工具呼叫或檢索的情境下，使用者體驗明顯受到影響。

**Q2：SHANKS 與 SIA 等推測式方法為何無法有效解決這個問題？**
A：SHANKS 雖然會將推理向前推進，但每個生成回合（generation episode）都被語音片段（speech chunk）所界定（chunk-bounded generation），這可能導致工具呼叫的參數（tool arguments）在尚未完整時就被截斷（truncation）。另一方面，SIA 採用更新時中斷式生成（interrupt-on-update generation），雖然已分派工具（dispatched tools）會被分開管理，但呼叫本身可能在發出之前就被中斷。這兩種方法都將運算時間（computation time）與語音更新（speech updates）耦合在一起，限制了代理在不中斷時間（uninterrupted time）內形成完整工具呼叫的能力，頻繁的語音更新進一步壓縮了可用時間。

**Q3：為什麼「讓進行中的運算完成」對於語音代理如此重要？**
A：語音代理的核心挑戰在於，使用者的請求是演進中的（evolving request），早期完成的結果（completed results）可能因為使用者後續新增的限制（例如預算限制 budget constraint）而需要修訂。如果代理在每次語音更新時都中斷並重新開始，就會浪費先前已完成的準備工作，也無法累積足夠的推理步驟（reasoning steps）與工具使用步驟（tool-use steps）。讓進行中的運算（ongoing computation）跨越語音更新繼續執行，可以將聆聽時間（listening time）轉化為可重複使用的累積準備（accumulated preparation），這正是心跳思考（Heartbeat Thinking）想要實現的核心價值。

**Q4：心跳思考的核心機制是什麼？**
A：心跳思考的核心機制是將新語音的處理交由後續的呼叫（invocations）來負責，同時允許已開始的工作順利完成。系統會以週期性呼叫（periodic invocations）的方式啟動思考器（Thinker），每個思考器讀取最新的部分轉錄文字（latest partial transcript）以及一份包含已完成推理（completed reasoning）與工具結果（tool results）的共用記錄（shared record）。獨立呼叫（independent invocations）可以重疊執行（overlapping invocations），一個思考器可以完成工具呼叫的建構，而另一個同時處理更新的輸入；已分派的工具則以非同步執行（asynchronous execution）方式運作，並將回傳結果寫入共用記錄，供後續呼叫用於解析缺失參數（missing arguments）並啟動相依呼叫（dependent calls）。

**Q5：心跳思考與 SHANKS 相比，最關鍵的創新是什麼？**
A：最關鍵的創新在於將「推測式準備」（speculative preparation）與「回應生成」（response generation）明確分離，並透過共用記錄解耦思考器與回應器（Responder）。在語音結束偵測（end-of-speech detection）時，回應器會接收完整請求以及當下可用的準備成果，檢查已完成的工作是否適用於完整請求，重用可用的結果並執行剩餘的呼叫；未完成的推測任務則在此時被取消，使回應器不必等待其完成。這種設計讓思考器與回應器可以選用不同的模型，並透過明確交換推理記錄與工具結果來協調，大幅提升了系統的彈性與效率。

**Q6：心跳思考在並行控制上做了哪些設計選擇？**
A：在並行控制方面，心跳思考設定了最多 K 個思考器同時執行的上限，當所有執行位置都被佔用時，新的觸發會被跳過，以避免資源過度競爭。新語音與工具結果會進入後續的呼叫，但不會中斷正在進行的生成，這確保了每個思考器有足夠的不中斷時間來完成工具呼叫的完整建構。工具執行則與思考器的排程分離，採獨立佇列管理，這使得模型運算與外部執行可以重疊進行。提示詞中也明確指示思考器避免重複呼叫相同名稱與參數的待處理或已完成呼叫，進一步減少冗餘運算。

**Q7：實驗使用了哪些基準測試（benchmark）？**
A：實驗使用了三個基準測試：SpeechFCEval、FDBench v3 與 AudioCRAG。這些基準涵蓋了不同的語音代理任務情境，其中 FDBench v3 涉及資料庫相關的工具呼叫，AudioCRAG 則涉及檢索增強生成（RAG）任務。透過這三個多樣化的基準，研究者得以評估心跳思考在不同任務類型下的整體推測式工具覆蓋率（aggregate speculative tool coverage）與檢索重用（retrieval reuse）表現，並驗證其跨任務的泛用性。

**Q8：心跳思考在 FDBench v3 上的關鍵成果為何？**
A：在 FDBench v3 上，心跳思考將工具覆蓋率（tool coverage）從 34.67% 提升至 50.67%，增加了 16 個百分點（percentage points）。同時，平均最終回應延遲（mean final-response latency）從 6.90 秒降低至 4.39 秒，降幅達 36.4%，也比最快的串接式基準 Pipecat 低 45.7%。更重要的是，這個覆蓋率優勢在不同的回應器模型上都能持續存在，顯示心跳思考的準備策略（preparation policy）具有跨模型的泛用性，而非僅依賴特定模型的特性。

**Q9：心跳思考在不同基準上的表現是否一致？**
A：表現呈現基準相依效應（benchmark-dependent effects）。在 FDBench v3 上，最終任務品質（task quality）相較於視窗式基準（Window Thinking）有所提升，但在 SpeechFCEval 與 AudioCRAG 上則略有下降。這說明雖然心跳思考在累積準備與降低延遲方面具有跨基準的優勢，但如何解讀與運用推測式結果（speculative results）仍是一個獨立的挑戰。不同基準的任務特性可能影響回應器重用準備成果的難易度，導致最終品質出現分歧。

**Q10：心跳思考適用於哪些實際應用情境？**
A：心跳思考特別適用於需要多次工具呼叫或外部檢索的語音代理場景，例如客服中心處理訂單查詢、物流配送問題、使用者需要即時查詢帳戶資訊等情境。在這些場景中，使用者往往會先提供部分關鍵資訊（如訂單編號），再補充細節（如預算限制或時間要求），心跳思考能在聆聽過程中提前完成可重用的準備工作。此外，在需要平行檢索（parallel retrieval）多個資料來源的情境下，例如旅遊規劃需要同時查詢航班、飯店與景點資訊，心跳思考的非同步執行機制也能發揮顯著效益。

**Q11：在產品化心跳思考時需要考量哪些因素？**
A：產品化時需要考量運算資源的配置，因為最多 K 個思考器同時執行的設計會增加 GPU 或推論服務的負擔，需要根據實際流量調整 K 值與週期間隔 Δ。回應器與思考器可以使用不同模型的設計雖然提升了彈性，但也增加了系統複雜度與維運成本，需要在效能與成本間取得平衡。此外，語音結束偵測的準確性會直接影響未完成任務的取消時機，過早偵測可能浪費已完成的準備，過晚偵測則會增加使用者等待時間，因此需要謹慎調校偵測閾值。

**Q12：心跳思考對語音代理領域有何影響？**
A：心跳思考提出了一個新的典範（paradigm），將「讓進行中的運算跨越語音更新完成」作為核心設計原則，挑戰了傳統「先聽完再行動」與「更新即中斷」的思維。這項工作將聆聽時間從被動等待轉化為主動準備，證明了透過共用狀態解耦思考器與回應器的可行性，為未來更高效、更智慧的即時語音代理（realtime voice agents）奠定了基礎。同時，跨基準的覆蓋率提升與延遲降低（latency reduction）也為業界提供了具體的效能改善方向，鼓勵更多研究投入推測式準備策略（preparation policy）的探索。

**Q13：心跳思考存在哪些已知的限制？**
A：論文明確指出，在 SpeechFCEval 與 AudioCRAG 上，最終任務品質相較於視窗式基準略有下降，顯示推測式結果的解讀與運用仍是一個獨立挑戰。基準相依效應意味著心跳思考並非在所有情境下都能帶來品質提升，使用者請求的演進特性可能使早期完成的結果在最終回應時變得不相關或具有誤導性。此外，雖然覆蓋率與延遲改善顯著，但如何確保回應器能正確評估與重用準備成果，仍需要更精細的設計與驗證。

**Q14：心跳思考在哪些情況下可能會失敗？**
A：當使用者的請求在聆聽過程中發生大幅轉變時，心跳思考可能會產生大量需要被取消的推測任務，造成運算資源的浪費。例如，使用者原本在詢問某餐廳資訊，但中途改變主意詢問完全不同主題，先前完成的檢索結果將完全無法重用。在任務品質下降的基準（SpeechFCEval、AudioCRAG）上，回應器可能誤用了不相關的推測結果，導致最終答案偏離使用者真正需求。此外，若語音結束偵測過早觸發，正在進行的關鍵工具呼叫可能被取消，反而延遲了最終回應。

**Q15：心跳思考未來可以朝哪些方向發展？**
A：未來可以朝幾個方向發展：首先，可以改進回應器對推測式結果的評估機制，例如引入信心分數或相關性檢查，僅重用真正適用於完整請求的準備成果；其次，可以探索更智慧的任務取消策略，根據請求演進的程度決定是否保留或放棄進行中的工作；再者，可以將心跳思考與其他推測式方法（如 Stream RAG 的平行檢索）結合，進一步提升準備效率；最後，也可以研究如何讓思考器主動預測請求可能的演進方向，提前準備更具彈性的中間結果（intermediate results），以減少因請求變更而造成的浪費。

## 實務應用指南

### 適用場景

**1. 客服語音助理（Customer Support Voice Agents）**
當用戶描述退款申請、帳號問題或訂單查詢時，Heartbeat Thinking 可在使用者說完「我想退掉昨天訂的這筆訂單」之前，就已開始查詢訂單資料庫、驗證身份並準備退款流程的草稿。當使用者補完「因為商品有瑕疵」時，思考器（Thinker）已完成的準備可直接被回應器（Responder）重用，縮短等待時間。

**2. 外送與物流訂單處理（Food Delivery & Logistics）**
在使用者描述「我想查詢昨天訂的餐點，目前送到哪裡了」的過程中，Heartbeat 可在使用者說出訂單編號前就開始準備呼叫訂單追蹤 API；當使用者補上「而且我想改地址」時，後續的思考器呼叫可基於已完成的訂單查詢結果啟動地址修改的相依呼叫。

**3. 金融服務語音助理（Banking & Financial Assistants）**
當使用者描述轉帳需求時，Heartbeat 可在使用者說出完整收款帳號前就開始驗證帳戶狀態、查詢匯率並準備交易草稿。對於需要多步驟驗證的金融操作，這種提前準備能顯著降低最終回應延遲。

**4. 旅遊與訂位助理（Travel & Booking Assistants）**
使用者描述「我想訂下週三從台北到東京的機票，預算三萬以下」時，Heartbeat 可在使用者說出預算前就開始搜尋航班；當預算限制到達時，後續思考器可基於已檢索的航班結果進行篩選，準備符合條件的選項。

**5. 醫療掛號與查詢助理（Healthcare Scheduling Assistants）**
當使用者描述症狀並請求掛號時，Heartbeat 可在使用者說出科別前就開始查詢醫師可用時段；當科別資訊到達時，思考器可基於已查詢的時段資料啟動特定科別的篩選呼叫。

**資料需求**

- 對話歷史記錄（用於上下文組裝）

**運算資源**

- 串流處理經驗（處理部分轉錄文字與增量更新）

### 實作步驟建議

**步驟 1：建立串流 ASR 與輸入管線**
部署支援部分轉錄文字輸出的 ASR 服務，設計輸入處理器將語音片段轉換為增量轉錄文字事件。確保轉錄系統能提供時間戳記與信心分數，以便後續的語音結束偵測。

**步驟 2：設計 Thinker 的輸出結構與提示**
根據論文的輸出結構（Appendix A 提及），定義 Thinker 的結構化輸出 schema，包含：
- `noop`：無動作
- `reason`：推理記錄
- `tools`：工具呼叫請求（含完整或部分參數）

提示中應明確指示 Thinker 避免重複已分派或已完成的呼叫，並鼓勵使用已完成的工具結果來解析缺失參數。

**步驟 3：實作共用狀態儲存**
設計共用記錄（Shared Record）的資料結構，儲存：
- 已完成的推理記錄
- 已分派工具的狀態（pending、completed、failed）
- 已返回的工具結果

確保狀態更新具有原子性，避免競態條件。

**步驟 4：建立排程器與並行控制**
實作週期性觸發邏輯（每 Δ 秒觸發一次），並設計並行控制：
- 最多 K 個並行 Thinker 呼叫
- 當所有槽位被佔用時跳過新觸發
- 確保新語音更新與工具結果進入後續呼叫，但不中斷進行中的生成

**步驟 5：實作工具執行層**
建立非同步工具執行器，支援：
- 工具呼叫的佇列管理
- 結果回寫至共用記錄
- 錯誤處理與重試邏輯
- 取消機制（在語音結束時取消未完成的推測式呼叫）

**步驟 6：實作語音結束偵測與 Responder 交接**
設計語音結束偵測邏輯（可基於 VAD 靜音時間或顯式結束訊號）。偵測到語音結束時：
- 停止新 Thinker 觸發
- 取消未完成的 Thinker 與推測式工具任務
- 將完整請求與可用準備結果組裝給 Responder

**步驟 7：實作 Responder**
Responder 接收完整請求與累積準備，執行：
- 檢查已完成工作是否適用於完整請求
- 重用適用的結果
- 執行剩餘的必要呼叫
- 生成最終回應

**步驟 8：參數調校與評估**
調校關鍵參數：
- Δ（觸發間隔）：影響準備密度與計算成本
- K（並行上限）：影響吞吐量與資源使用
- Thinker 與 Responder 的模型選擇：可使用不同模型以最佳化成本與品質

在 SpeechFCEval、FDBench v3、AudioCRAG 等基準上評估工具覆蓋率、最終回應延遲與任務品質。

**步驟 9：生產環境強化**
加入監控、日誌、錯誤恢復機制；設計降級策略（例如當並行槽位不足時的行為）；實作隱私與資料保留政策。

### 潛在風險與注意事項

**風險 1：取消安全性（Cancellation Safety）**
未完成的推測式工具呼叫可能在語音結束時被取消。若工具呼叫具有副作用（如發送郵件、執行交易），需設計冪等性機制或兩階段提交，避免部分執行造成資料不一致。
**緩解**：為副作用工具設計預提交（pre-commit）與確認（confirm）兩階段；或將推測式呼叫限制在唯讀操作。

**風險 2：任務品質下降**
論文指出在 SpeechFCEval 與 AudioCRAG 上，最終任務品質略有下降。推測式準備可能產生與最終請求不一致的結果，Responder 若未妥善篩選可能誤用。
**緩解**：強化 Responder 的結果驗證邏輯；設計「結果適用性檢查」步驟；對低信心結果要求重新驗證。

**風險 3：成本增加**
並行 Thinker 呼叫會增加 LLM 推理成本。若 Δ 設定過短或 K 過大，可能導致成本失控。
**緩解**：監控每次對話的 Thinker 呼叫次數與 token 使用量；設定成本上限；根據對話類型動態調整 Δ 與 K。

**風險 4：資源競爭與延遲**
並行呼叫可能造成資源競爭，反而增加個別呼叫的延遲。在高負載時可能出現排隊現象。
**緩解**：設定並行上限；實作自適應排程（根據系統負載調整 Δ）；使用專用推理資源。

**風險 5：共用狀態一致性**
多個並行 Thinker 讀寫共用記錄時可能產生競態條件，導致狀態不一致。
**緩解**：使用樂觀鎖定或悲觀鎖定；設計冪等的狀態更新操作；定期快照備份。

**風險 6：語音結束偵測錯誤**
過早偵測語音結束會浪費已進行的準備；過晚偵測則失去 Heartbeat 的優勢。
**緩解**：使用 VAD 信心分數與靜音時間的組合閾值；設計可恢復機制（若偵測錯誤可重新觸發準備）。

**風險 7：隱私與資料保留**
累積的準備結果可能包含敏感資訊，需設計適當的保留與清除政策。
**緩解**：對話結束後清除共用記錄；對敏感欄位進行遮罩；遵守 GDPR 等隱私法規。

### 與其他技術的整合建議

**與串流 ASR 系統整合**
Heartbeat Thinking 依賴串流式 ASR 的部分轉錄文字輸出。建議整合支援增量輸出的 ASR 服務（如 Deepgram、AssemblyAI 或自建 Whisper Streaming）。注意處理 ASR 的修正機制（後續片段可能修正先前轉錄），設計版本化的轉錄文字快照。

**與現有語音代理框架整合**
可將 Heartbeat 整合至 Pipecat、LiveKit Agents 等框架中。建議將 Thinker 與 Responder 設計為可插拔元件，允許在不修改核心管線的情況下替換準備策略。論文中提到 Heartbeat 在 FDBench v3 上比 Pipecat 快 45.7%，可作為框架的進階模式。

**與 LLM 供應商整合**
Thinker 與 Responder 可使用不同模型以最佳化成本與品質。建議：
- Thinker 使用較小、較快的模型（如 GPT-4o-mini、Claude Haiku）以降低準備成本
- Responder 使用較大的模型以確保最終品質
- 透過統一介面（如 OpenAI API 相容層）抽象化模型呼叫

**與工具生態系統整合**
設計工具註冊中心（Tool Registry），統一管理工具的 schema、執行器與權限。整合現有的 API 閘道、函式呼叫框架（如 LangChain Tools、OpenAI Function Calling）。注意工具的冪等性設計，以便支援取消與重試。

**與檢索系統整合**
對於需要 RAG 的場景，整合向量資料庫（如 Pinecone、Weaviate）作為工具。Heartbeat 的累積準備特性特別適合檢索重用——早期檢索的結果可在後續呼叫中被篩選與精煉。

**與監控與可觀測性系統整合**
整合 OpenTelemetry、LangSmith 或類似工具，追蹤：
- 每次對話的 Thinker 呼叫次數與延遲
- 工具呼叫的成功率與延遲
- 準備結果的重用率
- 最終回應的端到端延遲

**與 SHANKS、SIA 等基線的整合**
Heartbeat 可作為 SHANKS 或 SIA 的增強層。建議設計抽象介面，允許在不同準備策略間切換，以便 A/B 測試與漸進式部署。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題描述與 Figure 1，理解「為什麼語音代理需要提前準備」以及「現有方法為什麼會截斷工具呼叫」。接著閱讀第 3 節的 Heartbeat 架構與 Figure 2，建立對 Thinker、Responder、共用記錄三個核心元件的直覺理解。實作上可先從簡單的單一工具場景開始，體驗週期性觸發與結果重用的效果，再逐步擴展到多工具與相依呼叫的場景。

**給 AI 工程師**：重點閱讀第 3 節的「Overlapping preparation」與「Response handoff」段落，理解並行控制、狀態管理與交接機制的設計細節。實作時特別注意共用狀態的並發安全、工具呼叫的冪等性設計、以及 Thinker 與 Responder 的模型解耦所帶來的彈性。建議先在基準測試上重現論文的實驗結果，再根據實際業務需求調整 Δ、K 與模型選擇。Appendix A 的實作細節與輸出結構是工程實作的重要參考。

**給研究者**：本論文的核心貢獻在於「讓進行中的運算跨越語音更新」的設計哲學，以及「推測式準備與回應生成分離」的架構決策。建議深入閱讀第 2 節的相關工作，理解 Heartbeat 與 SHANKS、SIA、Stream RAG、AsyncReasoning 等方法的介面差異（Appendix F 有更詳細的討論）。可進一步探索的研究方向包括：不同準備策略的理論分析、Thinker 與 Responder 的聯合最佳化、以及在多輪對話中準備結果的累積與衰減機制。

**給產品經理**：Heartbeat Thinking 的核心價值是「將聆聽時間轉化為可重用的準備」，從而降低使用者感知的等待時間並提升任務完成能力。論文的實驗結果顯示在 FDBench v3 上工具覆蓋率提升 16 百分點、平均延遲降低 36.4%，但任務品質的提升並非通用——在 SpeechFCEval 與 AudioCRAG 上略有下降。這意味著 Heartbeat 適合「準備可重用性高」的場景（如訂單查詢、資訊檢索），而對於「需要精確理解完整請求」的場景（如複雜客服問題），需謹慎評估。建議在導入前明確定義成功指標（延遲 vs. 品質），並設計漸進式部署與 A/B 測試計畫。
