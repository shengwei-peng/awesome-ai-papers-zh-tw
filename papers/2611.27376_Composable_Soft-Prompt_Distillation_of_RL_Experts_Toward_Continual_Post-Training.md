## 摘要翻譯

RL 後訓練通常會產生領域專家，這些專家接著必須被合併到單一模型中，而隨著新專家不斷湧現，這種合併便成為一個持續過程。權重合併與多教師在策略蒸餾 (MOPD) 必須在每次新增專家時重新合併整個模型，且可能削弱目標領域以外的能力。我們提出可組合軟提示蒸餾 (CSPD)，其保持 RL 前模型凍結，將每個 RL 後專家獨立蒸餾為軟提示，並透過串接其提示來組合專家，無需聯合訓練。單一軟提示即足以蒸餾一個 RL 後專家，在 23 個數學、程式碼和代理設定中的 22 個恢復了至少 90% 的教師增益。獨立訓練的提示具良好可組合性。在多專家設定中，平均值隨著每個專家的加入而上升，且完整組合與 MOPD 相當 (67.83 vs. 67.79)。該組合在六個保留測試基準上展現最佳的泛化能力。輸入空間適應增加的服務開銷微乎其微，使吞吐量與未適應主幹網路的差距維持在 1.5% 以內，並達到秩-4 LoRA 的 2.40 倍。這些結果指向在固定主幹網路上進行持續後訓練的可能性。

## 深度分析

#### 方法論解析

本文提出**可組合軟提示蒸餾 (Composable Soft-Prompt Distillation, CSPD)**，其核心思想是將 RL 後訓練專家的能力從模型參數空間遷移到輸入空間 (input space)，以解決持續後訓練 (continual post-training) 中的專家整合問題。

**1. 核心設計理念：輸入空間適應取代參數空間修改**

傳統方法如權重合併 (weight merging)、多教師在策略蒸餾 (Multi-teacher On-Policy Distillation, MOPD) 皆在參數空間操作，需重新訓練或合併整個模型。CSPD 反其道而行，將每個 RL 專家蒸餾為一個獨立的軟提示 (soft prompt) $P_j \in \mathbb{R}^{L \times d}$，其中 $L=256$ 為向量序列長度，$d$ 為主幹網路 (backbone) 的嵌入維度。預訓練模型 $p_{\theta_0}$ 始終保持凍結 (frozen)，所有適應能力完全封裝於輸入端的軟提示中。

**2. 蒸餾目標函數**

採用序列級蒸餾 (sequence-level distillation, Kim and Rush, 2016) 的標準做法：對專家 $p_{\theta_j}$ 的領域問題 $X_j$ 取樣回應，僅保留通過驗證器 (verifier) 的回應構成資料集 $D_j$，然後以長度正規化的負對數似然 (negative log-likelihood) 損失訓練軟提示：

$$P_j^\star = \arg\min_{P_j} \mathbb{E}_{(x,y) \sim D_j}\left[-\frac{1}{|y|}\sum_{t=1}^{|y|} \log p_{\theta_0}(y_t | I(P_j, x), y_{<t})\right]$$

此處 $I(P_j, x)$ 為將軟提示插入系統訊息 (system message) 的模板函數。關鍵設計在於：損失僅作用於回應詞元 (token)，軟提示向量本身透過梯度 (gradient) 反傳學習。

**3. 前綴穩健訓練 (Prefix-Robust Training)**

此為本文最具巧思的設計之一。軟提示在訓練時獨立存在，但在組合時需接續其他提示。為使每個提示對其前置上下文具有魯棒性，訓練時在 50% 的樣本中，於軟提示前放置 128–256 詞元的隨機上下文前綴 (context prefix)，該前綴取自同領域其他問題。此前綴不計入損失 (excluded from the loss)，僅在推論時移除。這種設計使提示學會「忽略前置雜訊、專注自身任務」，大幅提升組合時的穩定性。

**4. 組合機制：無需聯合訓練的直接串接**

組合 $k$ 個專家時，僅需將其軟提示向量直接串接：

$$P_{1:k} = [P_1^\star; \ldots; P_k^\star] \in \mathbb{R}^{kL \times d}$$

插入同一模板即可使用，整個過程不涉及任何聯合訓練 (joint training)。此特性使新增專家只需訓練自身提示，刪除專家僅需丟棄對應提示，計算成本與既有專家數量無關——這正是持續後訓練的理想特性。

**5. 服務架構優勢**

由於軟提示僅延長輸入上下文，不同提示的請求可在同一主幹上批次處理 (batched serving)，無需為每個專家載入獨立模型副本，也無需在每個解碼步驟 (decoding step) 計算適配器 (adapter)，這與 LoRA 類方法形成鮮明對比。

#### 實驗數據解讀

**1. 單一專家蒸餾效果**

在 23 個數學、程式碼、代理 (agent) 設定中，單一軟提示在 22 個場景中恢復了教師相對 RL 前模型至少 90% 的增益，並在 15 個場景中匹配或超越教師本身。此結果極為關鍵——它證明了軟提示作為蒸餾載體的承載能力，足以容納 RL 後訓練帶來的領域能力提升。值得注意的是，軟提示僅 256 個向量，參數量極小，卻能逼近完整 RL 訓練的效果，顯示 RL 後訓練的「有效參數變化」可能集中在低維子空間中。

**2. 多專家組合的累積效應**

在指令遵循、科學、程式碼、數學四領域設定中，隨著專家逐一加入，四領域平均分數從 50.41 單調上升至 67.83，且完整組合 (67.83) 與 MOPD (67.79) 幾乎持平，但完全無需聯合訓練。此單調遞增特性是持續學習 (continual learning) 場景的核心訴求——每個新專家的加入都應帶來增量增益而非相互干擾。

**3. 領域外泛化能力**

在六個保留測試基準 (held-out benchmarks) 上，CSPD 取得最高平均分 56.6，顯著優於 MOPD 的 53.5。此結果暗示：將能力封裝於輸入空間而非覆寫模型權重，能更好地保留模型的通用能力，避免「為訓練領域犧牲非訓練領域」的權衡。這對實際部署至關重要，因為使用者查詢往往跨越多個領域。

**4. 行為學習而非詞面學習**

在 GPT-OSS 數學專家上，軟提示縮小了 86.8% 的教師-學生 KL 散度 (KL divergence) 差距，主要透過讓學生檢查中間結果 (check intermediate results) 實現；而相同意圖的自然語言指令僅縮小至多 2.1%。此對比揭示了軟提示的深層機制：它學習的是「行為模式」而非「詞面表達」，這是自然語言提示難以企及的精細度。

**5. 服務效率**

在單張 B200 GPU 上，軟提示吞吐量在七個併發等級下皆維持在未適應主幹的 1.5% 以內；當 32 個請求各自使用不同適配器時，軟提示吞吐量達到 rank-4 LoRA 的 2.40 倍。此數據凸顯了輸入空間適應 (input-space adaptation) 的部署優勢：無需在每層引入額外計算，僅延長上下文即可。

#### 與現有研究的比較

**1. 相較權重合併 (Weight Merging) 與 MOPD**

傳統方法皆需在新增專家時重新處理整個模型集合，計算成本隨專家數量線性增長。CSPD 的增量成本僅與新專家本身相關，與既有專家數量無關。此外，權重合併透過參數運算 (parameter arithmetic) 組合專家，易產生參數空間的相互干擾；MOPD 雖效果穩定，但需學生對所有教師進行在策略蒸餾 (on-policy distillation)，訓練成本高昂。CSPD 透過獨立訓練 + 直接串接實現了「訓練解耦、推論組合」的優雅解耦。

**2. 相較專家路由 (Expert Routing)**

路由方法依賴路由器 (router) 進行專家選擇，但路由器本身難以訓練，且無法在同一請求內組合多個專家。CSPD 透過串接實現了「請求內組合」，且無需路由器訓練成本。

**3. 相較 LoRA 專家合併**

LoRA 合併方法 (Huang et al., 2023; Prabhakar et al., 2024) 雖避免了路由器，但每個解碼步驟皆需在每層計算適配器，引入顯著延遲。CSPD 的輸入空間設計僅在預填充 (prefill) 階段增加計算，且不同提示可批次處理，吞吐量優勢明顯（2.40×）。

**4. 相較序列式 RL (Sequential RL)**

序列式 RL 僅在新領域訓練，但早期能力易遭受災難性遺忘 (catastrophic forgetting)。CSPD 透過凍結主幹徹底避免了此問題——主幹永遠保留預訓練時的通用能力，所有領域適應皆封裝於獨立提示中。

**5. 局限性**

- **上下文長度限制**：每個專家佔用 256 個詞元，組合 $k$ 個專家需 $k \times 256$ 詞元的上下文預算，當專家數量龐大時可能擠壓實際查詢空間。
- **領域衝突未明確分析**：雖然實驗顯示組合效果良好，但若多個專家任務高度重疊或衝突，串接是否仍有效尚需更多消融實驗驗證。
- **軟提示對極複雜行為的承載上限**：雖然 23 個設定中表現優異，但對於需要深層推理模式改變的專家，256 向量是否足夠仍待驗證。
- **前綴穩健訓練的領域內取樣限制**：前綴僅從同領域其他問題取樣，跨領域組合時的穩健性可能受限。

#### 未來研究方向

**1. 軟提示容量擴展**

當前 256 向量的設計在 23 個設定中表現優異，但對於極複雜的代理任務或多輪對話能力，可能需要更長的提示或階層式提示結構（hierarchical prompts）。可探索：(a) 動態長度分配——根據任務複雜度自適應調整每個專家的詞元預算；(b) 提示壓縮技術——利用量化或稀疏化在固定長度內承載更多能力。

**2. 跨領域組合的理論分析**

目前實驗顯示同領域前綴訓練有助於組合穩定性，但缺乏對「為何獨立訓練的提示可直接串接」的理論理解。可從以下角度切入：(a) 軟提示在嵌入空間中是否形成某種「正交子空間」使組合不互相干擾；(b) 借鑑提示微調 (prompt tuning) 的頻譜分析理論，解釋前綴穩健訓練的作用機制。

**3. 動態專家選擇與組合**

## 實務應用指南

### 適用場景

**1. 多領域客服與企業助手整合**
企業常需將不同業務領域（帳務、技術支援、訂單處理、售後服務）的 RL 後訓練專家整合到同一個對話系統。CSPD 允許每個領域獨立蒸餾成軟提示，部署時依使用者意圖串接對應提示，無需重新訓練整個模型，且新增業務線只需訓練新提示。

**2. 程式碼生成平台的語言與框架擴充**
GitHub Copilot、Cursor 等工具需支援 Python、Java、Go、Rust 等多種語言，以及 Django、Spring、React 等框架。每個語言/框架的 RL 專家可獨立蒸餾成軟提示，使用者選擇語言時即時串接，無需合併多個 LoRA 或重新部署模型。

**3. 教育科技中的學科專家組合**
數學、科學、程式設計、寫作等不同學科的教學助手可各自訓練成軟提示，學生提問時系統自動組合相關學科提示，提供跨學科整合回答（如數學建模 + 程式設計實作）。

**4. 持續更新的內容審核與合規系統**
內容平台需持續適應新的政策、規範、攻擊模式。每當有新政策出台，僅需蒸餾新專家成軟提示加入提示庫，舊提示保持不變，避免災難性遺忘。

**5. 多代理系統中的工具與技能模組化**
AI Agent 框架中，每個工具使用技能（搜尋、計算、API 呼叫、程式碼執行）可獨立訓練成軟提示，根據任務需求動態組合，支援增量擴充新技能。

- 每個領域需有對應的驗證器（verifier），用於過濾教師回應品質（數學題需答案驗證、程式碼需執行測試、Agent 任務需環境回饋）
- 每個領域的訓練資料規模建議與原 RL 訓練資料相當或略少，蒸餾過程使用驗證器過濾後的成功回應
- 領域之間的訓練資料需有部分重疊或語意關聯，以支援 prefix-robust training 的上下文前綴採樣

**運算資源需求**
- 基礎設施：單張 B200 等級 GPU 即可支援推論階段的批次服務
- 訓練階段：每個軟提示（256 向量）訓練成本遠低於完整模型微調，建使用與原 RL 訓練相同的硬體配置
- 儲存：每個軟提示僅佔 256 × d × 4 bytes（d 為嵌入維度，如 4096 則約 4 MB），提示庫極輕量
- 記憶體：推論時需將多個提示串接後的 KV cache 載入，長度為 k × 256 + 對話長度

**技能前置要求**
- 熟悉 PyTorch 與 Transformer 架構的 embedding 操作
- 具備 RL 後訓練流程經驗（產生專家模型與驗證器）
- 理解 soft prompt tuning 原理（Lester et al., 2021）與 sequence-level distillation（Kim and Rush, 2016）
- 具備 LLM 推論優化經驗（KV cache 管理、批次處理、vLLM 或類似框架）
- 建議具備分散式訓練經驗以加速多領域並行蒸餾

### 實作步驟建議

**步驟一：建立 RL 前基礎模型與領域專家**
選定一個經過預訓練與指令微調的基礎模型 $p_{\theta_0}$ 作為凍結主幹。針對每個目標領域，使用各自的資料與驗證器獨立訓練 RL 後訓練專家 $p_{\theta_j}$。此階段沿用現有 RL 流程，不需為 CSPD 做特殊調整。

**步驟二：準備蒸餾資料集**
對每個領域 $j$，從專家 $p_{\theta_j}$ 對領域問題 $X_j$ 取樣回應，使用驗證器過濾出通過的回應，組成蒸餾資料集 $D_j$。資料量與品質直接影響軟提示效果，建議保留原 RL 訓練中表現最佳的回應。

**步驟三：實作軟提示蒸餾訓練**
初始化軟提示 $P_j \in \mathbb{R}^{L \times d}$（$L=256$，$d$ 為嵌入維度）。在系統訊息中插入 $P_j$，凍結主幹 $\theta_0$，僅訓練 $P_j$。損失函數採用長度正規化的負對數似然：
$$P_j^\star = \arg\min_{P_j} \mathbb{E}_{(x,y) \sim D_j}\left[-\frac{1}{|y|}\sum_{t=1}^{|y|} \log p_{\theta_0}(y_t \mid I(P_j, x), y_{<t})\right]$$

**步驟四：套用 Prefix-Robust Training**
為提升組合時的穩健性，在一半的訓練範例中，於軟提示前插入 128–256 詞元的上下文前綴（從同領域其他問題採樣）。前綴不計入損失，推論時不使用。此步驟是支援獨立訓練提示直接串接的關鍵。

**步驟五：建立提示庫與組合機制**
將所有訓練完成的軟提示 $P_1^\star, P_2^\star, \ldots, P_k^\star$ 存入提示庫。組合時直接串接：$P_{1:k} = [P_1^\star; P_2^\star; \ldots; P_k^\star]$，無需任何聯合訓練。新增專家只需訓練新提示並加入庫中，移除專家只需從串接中刪除。

**步驟六：部署與批次服務優化**
在推論伺服器（如 vLLM）中實作動態提示載入機制。不同請求使用不同提示組合時，可共享同一主幹批次處理。監控吞吐量，確保軟提示帶來的額外 context 長度不顯著影響延遲（論文顯示吞吐量損失 < 1.5%）。

**步驟七：建立持續後訓練流程**
設計專家生命週期管理：當新領域需求出現時，訓練新 RL 專家 → 蒸餾成軟提示 → 加入提示庫。舊提示與主幹保持不變，實現真正的持續學習，無需重新合併或重新蒸餾既有專家。

### 潛在風險與注意事項

**風險一：軟提示容量限制**
單一軟提示僅 256 個向量，可能無法完整捕捉複雜領域專家的全部能力。對於極複雜任務（如多步推理 + 工具使用），蒸餾效果可能下降。
*緩解策略*：針對高難度領域，可嘗試增加軟提示長度（如 512 或 1024 向量）；或將單一領域拆分為多個子專家，各自蒸餾成獨立提示再組合。

**風險二：領域衝突與提示干擾**
當多個領域提示串接時，潛在的語意衝突可能導致某些領域表現下降。論文雖展示平均效能隨專家增加而提升，但個別領域可能受影響。
*緩解策略*：採用 prefix-robust training 強化提示獨立性；部署後持續監控各領域基準表現；若發現特定組合下表現下降，可調整提示串接順序或設計領域感知路由器選擇性啟用提示。

**風險三：驗證器品質依賴**
蒸餾資料完全依賴驗證器過濾，若驗證器本身有偏差或漏洞，軟提示將繼承這些缺陷。
*緩解策略*：建立多層驗證機制（規則 + LLM 評審 + 人工抽檢）；定期審查驗證器在新型問題上的表現；保留未通過驗證的回應進行錯誤分析。

**風險四：主幹模型版本綁定**
軟提示與特定主幹模型深度耦合，主幹升級或更換時所有提示需重新蒸餾。
*緩解策略*：建立主幹版本管理與提示版本對應表；在主幹升級前評估提示可遷移性；考慮設計提示蒸餾的遷移學習機制。

**風險五：長上下文成本累積**
當專家數量增加，串接後的 context 長度線性增長，KV cache 與注意力計算成本隨之上升。
*緩解策略*：監控提示庫規模，設定上限閾值；採用分組或層次化組合策略；評估是否需要精簡或合併高度相關的提示。

**風險六：安全與合規風險**
新增專家提示時，若該專家訓練資料含有偏見或有害內容，組合後可能影響整體系統安全。
*緩解策略*：每個新提示上線前執行獨立安全評估；設計紅隊測試流程；建立提示層級的內容過濾機制。

### 與其他技術的整合建議

**與 LoRA 整合**
LoRA 適合需要修改模型深層行為的場景，CSPD 適合快速組合多領域專家。可採用混合策略：核心領域用 LoRA 微調主幹，邊緣領域用軟提示擴充；或將 LoRA 視為另一種「專家」，與軟提示統一管理。

**與專家路由系統整合**
對於需要根據輸入動態選擇專家的場景，可訓練輕量級路由器（如小型分類器）決定啟用哪些軟提示。路由器只需判斷領域歸屬，無需學習複雜的專家組合權重，降低訓練成本。

**與模型合併技術整合**
權重合併（weight merging）適合處理高度相關的專家（如同一領域不同訓練 run），軟提示組合適合處理互補領域。建議流程：先在領域內用權重合併產生更強的單一專家，再蒸餾成軟提示加入跨領域組合。

**與持續學習框架整合**
CSPD 天然支援持續學習，可整合到現有 MLOps 平台：每當新領域模型訓練完成，自動觸發蒸餾流程並更新提示庫；CI/CD 流程中加入各領域基準測試與安全檢查。

**與推論優化框架整合**
vLLM、TGI、TensorRT-LLM 等框架已支援動態 prompt 載入。建議利用其 prefix caching 功能快取共用前綴的 KV cache，進一步降低多提示組合的推論成本。

**與監控與可觀測性整合**
建立提示層級的監控儀表板：追蹤每個提示的呼叫頻率、組合模式、對應領域的效能指標。當發現異常組合或效能衰退時，可快速定位並調整提示庫。

**與 Agent 框架整合**
在 LangChain、AutoGen 等 Agent 框架中，將軟提示視為可插拔的「技能模組」。Agent 規劃器根據任務需求決定啟用哪些技能提示，實現模組化的 Agent 能力擴充。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「軟提示」（soft prompt）的概念——這是一組可學習的向量，插入到模型輸入的最前面，引導模型產生特定行為，而無需修改模型參數。想像它是模型的「隱形指令」，用數字而非文字寫成。接著理解「知識蒸餾」：讓小模型（學生）模仿大模型（老師）的行為。CSPD 的巧妙之處在於：學生模型完全不動，只訓練一組小向量（軟提示）來吸收老師的知識。最後理解「組合性」：不同領域的軟提示可以像積木一樣拼接，無需重新訓練。

**給 AI 工程師**：重點關注實作細節——軟提示的維度（256 × d）與插入位置（系統訊息）、prefix-robust training 的實作方式（隨機前綴採樣與損失遮罩）、蒸餾損失函數的長度正規化處理。部署面需注意 KV cache 管理與批次服務策略，論文的吞吐量數據（B200 上 2.40× rank-4 LoRA）是關鍵效能指標。建議先在單一領域驗證蒸餾效果，再逐步擴展到多領域組合。

**給研究者**：論文的理論意涵在於挑戰「專家必須存在於模型參數中」的傳統假設，證明輸入空間的組合可以達到甚至超越參數空間合併的效果。值得深入探討的方向包括：軟提示容量與表達能力的理論邊界、不同組合策略（串接 vs. 加權 vs. 注意力融合）的理論比較、prefix-robust training 的泛化性分析、以及與其他模組化方法（如 MoE、Adapter）的理論關聯。論文中「軟提示學習行為而非詞彙」的觀察（86.8% KL gap 關閉 vs. 文字指令僅 2.1%）是重要的發現。

**給產品經理**：CSPD 解決的核心問題是「如何持續擴充 AI 產品能力而不破壞既有功能」。傳統做法（合併模型、重新蒸餾）成本高且風險大，CSPD 提供「即插即用」的模組化方案：新增能力只需訓練一個小檔案（軟提示），移除能力只需刪除檔案，組合能力只需串接檔案。這大幅降低了持續迭代的成本與風險，使產品能快速響應新需求。關鍵決策點在於：哪些能力值得獨立成專家？如何設計領域劃分？如何處理領域間的衝突？建議從 2–3 個高價值領域開始驗證，逐步擴展。
