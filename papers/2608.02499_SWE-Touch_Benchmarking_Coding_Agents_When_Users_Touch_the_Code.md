## ⚡ TL;DR

現有程式修復評測忽略使用者在共享工作區中即時修改程式碼的互動情境。
本文提出 SWE-Touch，於代理觸及任務關鍵碼時注入經驗證的對抗性編輯與使用者訊息。

## 摘要翻譯

真實世界的軟體開發要求編碼代理 (coding agents) 在共享工作區 (shared workspaces) 中運作，使用者可能在任務進行期間檢視並修改程式碼；然而現有的程式庫層級基準測試 (repository-level benchmarks) 通常評估單獨運作的代理，或將使用者參與限制為基於訊息的參與 (message-based participation)。這促使我們探問：編碼代理如何理解並回應共享工作區中的程式碼變更？我們提出 SWE-Touch，一個透過經驗證的對抗性編輯 (Counter-Edits) 對此情境進行壓力測試的框架：對任務相關程式碼進行看似合理但與任務完成相衝突的修改。SWE-Touch 從多個修復軌跡 (repair trajectories) 中挖掘任務關鍵區域 (task-critical regions)，使用獨立的使用者修補程式產生器 (User Patch Generator) 建構這些編輯，並在代理觸及相關程式碼時，連同帶有上下文的使用者訊息 (user messages) 一併注入。我們在 SWE-bench Verified 上評估九個編碼模型，並在 SWE-Bench Pro 與 DeepSWE 的長程任務 (longer-horizon tasks) 上進行額外實驗。對抗性編輯 (Counter-Edits) 在 SWE-bench Verified 上使平均解決率 (resolve rate) 降低 7.7 個百分點，且此效能下降在兩個長程基準測試中亦持續存在。軌跡分析顯示這些失敗源於對不斷演變的工作區 (workspace) 感知不足：代理可能保留衝突程式碼，或直接將其替換，卻未充分重新檢視程式庫 (repository)，也未以針對性測試驗證修訂後的程式碼。這些發現顯示，強大的自主表現尚無法確保共享工作區協作所需的狀態感知 (state awareness) 與適應性行為 (adaptive behavior)，並指出偵測工作區變更、調和衝突編輯 (conflicting edits) 與任務目標，以及驗證受影響行為 (affected behavior)，是未來最佳化的關鍵能力。

### 核心貢獻（3～5點）
- 提出 SWE-Touch 框架，透過對抗性編輯 (Counter-Edits) 評測編碼代理在共享工作區中面對使用者程式碼修改時的狀態感知與適應能力。
- 設計使用者修補程式產生器 (User Patch Generator)，自動從修復軌跡中挖掘任務關鍵區域並生成看似合理但與任務目標衝突的程式碼修改。
- 在 SWE-bench Verified、SWE-Bench Pro 與 DeepSWE 上進行大規模評估，發現對抗性編輯平均降低解決率 7.7 個百分點，且長程任務的效能下降同樣顯著。
- 透過軌跡分析指出代理失敗的主因：缺乏對工作區變化的持續感知、未充分重新檢視程式庫，以及未以針對性測試驗證受影響行為。
- 明確未來編碼代理應強化的三項關鍵能力：偵測工作區變更、調和衝突編輯與任務目標，以及驗證受影響行為。

### 適合對象
從事 AI 程式設計助理、編碼代理 (coding agents) 與人機協作軟體開發的研究人員與工程師；特別是關注代理在真實共享工作區中的狀態感知 (state awareness)、適應性行為 (adaptive behavior) 與長期任務表現的讀者。

## 深度分析

#### 方法論解析

SWE-Touch 的核心貢獻在於把「使用者會動到程式碼」這個真實協作場景，轉化為可控制、可重複的評測機制。整體方法可以拆解為四個環節：**任務關鍵區域（task-critical regions）探勘**、**Counter-Edit（對抗性編輯）生成**、**編輯有效性驗證**，以及**在軌跡中適時注入編輯與使用者訊息**。

首先，針對每一個 SWE-bench Verified 的修復任務，SWE-Touch 會先蒐集多條代理修復軌跡（repair trajectories）。透過比較不同成功軌跡中反覆出現的修改位置，框架能夠定位出對任務完成最具影響力的程式碼區段。這些區域通常位於 bug 根源附近，一旦內容被改動，後續修復策略就必須跟著調整。相較於隨機挑選檔案注入雜訊，這種「任務導向」的選點方式更能反映真實協作中使用者「剛好改到相關程式碼」的情境。

接著，論文引入一個獨立的 **User Patch Generator（使用者修補程式產生器）**，專門負責在這些任務關鍵區域附近產生小範圍、局部合理但與任務目標衝突的程式碼修改。所謂「局部合理」是指：單看這段修改，它可能像是使用者為了某種意圖（例如調整 API 行為、重構變數名稱、改變條件判斷）而做的正常編輯；但從整體任務角度來看，它會讓正確修復變得更困難，甚至直接導致測試失敗。這種設計避免了把「明顯錯誤」塞進程式庫，因為過於荒謬的修改只會被代理忽略，無法測試其狀態感知能力。

為了確保 Counter-Edit 的品質，SWE-Touch 對每個生成的編輯進行兩項驗證：第一，該編輯**不能單獨解決任務**（否則會混淆評分，因為即使代理什麼都不做也會過關）；第二，該編輯**不能過於瑣碎、可被代理輕易無視**（否則無法產生區分度）。只有通過這兩道篩選的編輯才會被保留，成為正式評測用的 Counter-Edit。

在實際評測階段，SWE-Touch 並非在任務一開始就把 Counter-Edit 注入，而是採用**動態觸發**機制：當代理的執行軌跡到達相關程式碼區域時，系統才將該編輯套用至共享工作區（shared workspace），並同時附上一則帶有上下文的使用者訊息（user messages）。這則訊息模擬了真實使用者可能會說的話，例如「我剛剛調整了這邊的邏輯，請你接著處理」。這樣的設計讓評測更貼近真實開發流程——使用者通常不會在代理還沒看到某段程式碼前就搶先修改，而是在代理已經開始關注該區域後才介入。

最後，代理會在已被修改的程式庫狀態（repository state）上繼續執行，並以原本的可執行測試（executable tests）作為評分依據。透過比較「無 Counter-Edit」與「有 Counter-Edit」兩種設定下的解決率（resolve rate），研究者得以量化代理在共享工作區中的狀態感知（state awareness）與適應性行為（adaptive behavior）。

#### 實驗數據解讀

論文在 SWE-bench Verified 上評測了九個編碼代理（coding agents），並額外在 SWE-Bench Pro 與 DeepSWE 這兩個長期任務基準測試（longer-horizon benchmarks）上進行驗證。整體結果顯示，Counter-Edit 會讓平均解決率下降 **7.7 個百分點**，而且不同模型之間的損失幅度差異極大，從 1.3 到 16.5 個百分點不等。這個數字本身說明了兩件事：第一，共享工作區中的使用者編輯確實會對現有代理造成系統性傷害；第二，各模型對這類干擾的韌性並不一致，傳統自主編碼能力（autonomous coding ability）的分數無法直接推論到協作場景。

更值得關注的是模型排名的「重洗牌」現象。某些在靜態 SWE-bench Verified 上表現強勁的模型，在加入 Counter-Edit 後明顯下滑；反之，部分原本排名較後的模型反而相對穩健。這暗示目前許多代理的優化目標可能過度偏向「單人作業」情境，對於工作區狀態持續演化的互動情境缺乏足夠的泛化能力。論文特別指出，這個現象在部分開源模型（open-source models）上尤其明顯——它們在自主基準測試上能與閉源前沿模型（frontier models）競爭，但在互動條件下卻出現大幅衰退。

在長期任務方面，SWE-Bench Pro 與 DeepSWE 上的衰退同樣存在。這點很重要，因為長期任務通常涉及更多檔案、更長的推理鏈與多次測試迭代，理應給代理更多機會去察覺並修正外部修改。然而實驗結果顯示，即使任務時間拉長，代理仍然難以有效恢復，說明問題不在於「時間不夠」，而在於**根本缺乏偵測與處理工作區變更（workspace changes）的機制**。

軌跡分析進一步揭示了失敗的具體模式。在所有失敗的執行中，高達 **63.3% 保留了使用者的衝突程式碼**，也就是代理沒有識別出該編輯與任務目標矛盾，反而直接採納或無視了它。這些失敗可以細分為三類：

1. **未察覺外部修改**：代理沒有重新檢視相關檔案，仍依照原本的程式庫信念（repo belief）繼續規劃與修改。
2. **過度順從使用者編輯**：代理雖然看到了修改，但誤以為使用者編輯必然正確，因此保留衝突程式碼而未進行協調。
3. **魯莽覆蓋未驗證**：代理選擇直接覆蓋使用者編輯，但沒有針對受影響行為（affected behavior）執行目標測試，導致最終狀態仍然錯誤。

這三種模式共同指向同一個核心缺陷：當前程式設計代理缺乏對「當前差異（current diff）」與「任務規格（task specification）」之間一致性的持續監控。它們傾向把程式庫視為靜態背景，而非與使用者共同演化的共享工作區。

#### 與現有研究的比較

在 SWE-Touch 之前，互動式程式設計評測大致可以分為兩大類：一類是**基於訊息的參與（message-based participation）**，例如 Ambig-SWE、SWE-Interact、SWE-Together 等，透過對話讓使用者澄清需求或提供回饋；另一類是**環境層級或程式庫層級的靜態基準測試（repository-level benchmarks）**，例如 SWE-Bench、Terminal-Bench，讓代理在固定初始狀態下獨立完成任務。SWE-Touch 填補了兩者之間的空白：它保留了程式庫層級修復任務的真實性，但把使用者參與從「純訊息」擴展到「可改變程式庫狀態（repository state）的編輯」。

與同樣關注狀態同步的 HiL-Bench 或「恢復不同步程式庫狀態」的研究相比，SWE-Touch 的差異在於它強調**任務衝突性**。它不是單純測試代理能否偵測到「有人動過程式碼」，而是測試代理能否在「使用者改錯了關鍵區域」的極端情況下，仍然完成正確修復。這種設計更貼近真實協作中的張力：使用者和代理都可能出錯，最終必須以任務目標與可執行測試（executable tests）為準進行協調。

相較於 SWE-chat 等實證研究，SWE-Touch 的優勢在於**可控性與規模化**。SWE-chat 記錄了真實使用者與代理的互動，但這些對話無法被精確複製，也難以進行模型間的公平比較。SWE-Touch 透過自動化的 User Patch Generator 與標準化的注入時機，讓不同模型在相同的干擾條件下接受測試，從而產生可重複的量化結果。

不過，SWE-Touch 也存在一些方法論上的限制。首先，它目前注入的是**單一 Counter-Edit**，而真實開發中使用者可能連續多次修改、甚至在代理修改後再次覆蓋。其次，Counter-Edit 雖然經過驗證，但終究是「模擬」的使用者編輯，未必能完整涵蓋真實使用者意圖的多樣性。第三，注入時機是「代理到達相關程式碼區域」這個事件驅動的時刻，雖然比隨機注入更合理，但真實使用者的介入時機可能更受對話上下文與認知負荷影響，難以用單一規則概括。最後，論文主要關注「使用者編輯與任務衝突」的情境，對於「使用者編輯其實有幫助」或「使用者編輯與任務無關」這兩種常見情形著墨較少。

#### 可重現性評估

從提供的上下文來看，SWE-Touch 的實驗設計具備良好的可重現性潛力，但實際能否完全複製仍取決於作者是否公開關鍵資產。

框架底層建立在 SWE-bench Verified、SWE-Bench Pro 與 DeepSWE 這些已公開的資料集之上，因此任務定義、測試案例與評分標準都是透明的。然而，SWE-Touch 獨特的貢獻——**Counter-Edit 的生成與注入流程**——涉及三個尚未在上下文中明確說明是否開放的元件：

1. **User Patch Generator（使用者修補程式產生器）**：這是產生 Counter-Edit 的核心模組，包含如何從多條修復軌跡中萃取任務關鍵區域、如何生成局部合理但衝突的編輯、以及如何進行有效性驗證。若未公開其程式碼與提示詞設計，其他研究者難以完全重現相同的編輯集合。
2. **注入時機與訊息模板**：Counter-Edit 在「代理到達相關程式碼區域」時才注入，並伴隨上下文使用者訊息。這個觸發邏輯與訊息內容的具體實作細節，對實驗結果有顯著影響。
3. **模型軌跡與評測腳本**：論文提到分析多條 repair trajectories，若作者能釋出這些軌跡、評測腳本與原始結果表格，將大幅提升可重現性與後續研究的比較基準。

目前根據既有資訊，只能給出「**部分可重現**」的評估：基礎資料集與評分機制是公開的，但 SWE-Touch 特有的編輯生成與注入機制是否開源，仍需作者進一步確認。建議後續研究者在引用或比較時，應特別注意實驗設定中 Counter-Edit 的數量、注入時機、訊息內容與驗證標準，以避免因設定差異造成無法比較的結果。

#### 未來研究方向

SWE-Touch 揭示的問題為下一代理程式設計代理的發展指出了三個明確的優化方向：**偵測工作區變更（detecting workspace changes）**、**協調衝突編輯（reconciling conflicting edits）**，以及**重新驗證受影響行為（verifying the affected behavior）**。

首先，在偵測層面，未來代理需要更主動地監控當前差異（current diff）與自身程式庫信念（repo belief）之間的不一致。這可能涉及在每次行動前執行 `git diff` 或類似工具，並將差異資訊納入推理上下文；也可能需要發展專門的「狀態感知模組」，讓代理能夠追蹤哪些檔案被誰、在何時、以何種意圖修改過。

其次，在協調層面，代理不能簡單地「全盤接受」或「全盤覆蓋」使用者編輯，而應該具備**衝突解決（conflict resolution）**能力。這包括理解使用者編輯背後的意圖、判斷其與任務規格（task specification）的相容性，並在必要時提出詢問或替代方案。這類能力可以借鑑軟體工程中的合併衝突解決（merge conflict resolution）研究，也可以透過強化學習或偏好學習來訓練代理在協作情境中做出更穩健的決策。

第三，在驗證層面，代理需要針對被修改的區域執行**目標化測試（targeted tests）**，而非僅在最後跑一次完整測試套件。論文發現許多代理在覆蓋使用者編輯後沒有重新檢查受影響行為，這正是未來工具使用（tool use）設計可以強化之處：例如自動識別與 Counter-Edit 相關的單元測試（unit tests）、在每次編輯後執行最小化回歸測試，並根據測試回饋動態調整修復策略。

除了上述三個核心方向，還有幾個值得延伸的研究課題：

- **多輪、多編輯的互動情境**：將單一 Counter-Edit 擴展為連續多次使用者介入，測試代理在長期協作中的狀態追蹤能力。
- **真實使用者資料的對齊**：將 SWE-Touch 中模擬的使用者編輯與 SWE-chat 等真實資料進行比對，驗證 Counter-Edit 的分佈是否合理。
- **使用者意圖建模**：讓代理不僅看到程式碼差異，還能根據使用者訊息推斷修改意圖，從而做出更符合協作禮儀的決策。
- **人機協作介面設計**：研究如何透過更好的介面（例如即時 diff 標註、衝突預警）降低使用者與代理之間的認知落差。
- **可解釋性與信任**：當代理決定覆蓋使用者編輯時，應該能夠清楚說明理由，這對於實際部署中的人機信任至關重要。

總結來說，SWE-Touch 不僅提出了一個新的評測維度，更重要的是它提醒我們：在邁向真正實用的編碼代理時，「寫對程式碼」只是第一步，「在與人共享的工作區中持續理解並適應變化」才是下一個必須攻克的難題。

## 論文問答

**Q1：SWE-Touch 想要解決的核心問題是什麼？為什麼現有的程式庫層級基準測試無法充分捕捉這個問題？**

A：SWE-Touch 針對的是「使用者會在任務進行中直接修改共享工作區（shared workspace）內的程式碼」這個真實情境，而現有基準測試大多假設代理獨自作業，或僅允許使用者透過文字訊息參與。這種設定忽略了使用者編輯（User Edit）會改變後續代理動作所觀察到的程式庫狀態（repository state），使得評測結果無法反映真實的多輪協作開發。因此，SWE-Touch 提出一個新的評測框架，專門檢驗代理在共享工作區中如何理解並回應程式碼變更。

**Q2：為什麼僅有「基於訊息的參與」（message-based participation）不足以評估真實的使用者與代理互動？**

A：基於訊息的互動只能捕捉澄清需求、回答問題或提供回饋等對話行為，但無法反映使用者直接修改可執行程式碼庫（codebase）所造成的狀態變化。在真實開發中，使用者的每一次編輯都會改變代理後續讀取、規劃與修改的程式狀態（program state），這是訊息無法等價傳達的。因此，若評測僅限於訊息，將會低估代理在動態共享工作區中所需的狀態感知（state awareness）與適應性行為（adaptive behavior）。

**Q3：為什麼「使用者觸碰程式碼」這個現象值得被獨立研究與評測？**

A：根據本文對 SWE-chat 資料的分析，高達 59.0% 的對話場景中包含可歸因於使用者的程式庫變更，顯示程式碼編輯是與訊息同等重要的互動管道。這類編輯會即時改變代理所觀察到的原始碼（source code）與可執行測試（executable tests），若代理無法正確察覺與處理，就可能保留錯誤程式碼或做出與任務目標衝突的修改。因此，將使用者編輯納入評測，有助於補足現有基準測試在真實協作情境上的缺口。

**Q4：SWE-Touch 的核心方法流程是什麼？它如何產生並注入對抗性編輯（Counter-Edit）？**

A：SWE-Touch 首先從多條修復軌跡（repair trajectories）中挖掘出任務關鍵區域（task-critical regions），這些區域與完成任務密切相關。接著，獨立的使用者修補程式產生器（User Patch Generator）會在這些區域附近構造一個規模小、局部合理但與任務目標衝突的 Counter-Edit，並經過驗證確保它不會單獨解決問題，也不會被輕易忽略。在評測過中，當代理觸及相關程式碼時，系統會伴隨上下文使用者訊息（user messages）注入該編輯，直接擾動正在進行的修復流程。

**Q5：Counter-Edit 的設計理念與關鍵創新是什麼？它與一般的錯誤注入有何不同？**

A：Counter-Edit 的關鍵在於它並非隨機製造語法錯誤，而是產生一個「看似合理、卻與任務完成互相衝突」的程式碼修改，從而測試代理是否能主動檢視並協調衝突狀態。這種設計保留了使用者編輯中常見的位置與意圖訊號，迫使代理不能單純假設使用者或自己一定正確，而必須重新檢視程式庫並調整修復策略。相較於傳統錯誤注入，Counter-Edit 更貼近真實協作中「使用者給出部分正確但與最終目標矛盾的修改」這類高難度情境。

**Q6：為什麼 SWE-Touch 要將「使用者修補程式產生器」與「驗證機制」分開設計？這樣做有什麼好處？**

A：將 User Patch Generator 獨立出來，可以讓對抗性編輯的生成過程與代理的修復邏輯解耦，確保編輯是從「使用者視角」出發、而非針對特定代理弱點量身打造。驗證機制則進一步保證每個 Counter-Edit 既不會單獨完成任務，也不會過於瑣碎而被代理自然忽略，從而維持評測的公平性與挑戰性。這種分離設計讓 SWE-Touch 能夠以可控且可重現的方式，系統性地比較不同模型在共享工作區中的表現。

**Q7：SWE-Touch 在哪些基準測試與模型上進行了實驗？實驗設計有何特別之處？**

A：論文在 SWE-bench Verified 上評估了九個編碼代理（coding agents），並額外在 SWE-Bench Pro 與 DeepSWE 這兩個長期任務（longer-horizon tasks）基準上進行測試。這樣的設計不僅檢驗 Counter-Edit 對一般程式修復任務的影響，也觀察其在更長、更複雜的修復軌跡中是否持續造成效能退化。透過跨資料集與跨模型的比較，研究得以區分「單純的自主編碼能力」與「共享工作區協作所需的狀態感知能力」。

**Q8：SWE-Touch 實驗的主要結果是什麼？Counter-Edit 對各模型的影響有多大？**

A：在 SWE-bench Verified 上，Counter-Edit 使平均解決率（resolve rate）下降了 7.7 個百分點，個別模型的損失範圍從 1.3 到 16.5 個百分點不等，並且顯著改變了模型排名。這種退化在 SWE-Bench Pro 與 DeepSWE 這兩個長期任務基準上同樣存在，顯示問題不僅限於短期任務。此外，軌跡分析發現 63.3% 的失敗執行最終保留了使用者的衝突程式碼，凸顯代理缺乏對工作區變更的足夠警覺。

**Q9：從失敗軌跡分析中，可以歸納出哪些主要的失敗模式？這些模式說明了什麼能力缺口？**

A：失敗模式主要分為三類：代理未能察覺外部修改、過度順從而保留使用者的衝突程式碼，或是在修改後未重新檢視程式庫與執行針對性測試（targeted tests）。這些模式共同指向代理的「程式庫信念」（repo belief）與實際程式庫狀態之間存在落差，也就是狀態感知不足。特別值得注意的是，部分在自主基準上表現優異的開源模型，在互動情境下退化更為明顯，顯示單純優化靜態排行榜成績並不能保證真實協作中的穩健性。

**Q10：SWE-Touch 所評測的能力在哪些實際產品或開發場景中最為重要？**

A：這類能力對於整合開發環境（IDE）中的 AI 程式設計助理、即時協作編輯工具，以及持續整合（CI）回饋迴圈中的代理都至關重要。例如，當使用者在代理還在思考時手動修改了某個函式，代理必須能夠偵測到這個工作區變更（workspace changes），並決定是否採納、調整或覆寫該修改。若代理無法妥善處理這類衝突編輯（conflicting edits），就可能產生與使用者意圖相違背的程式碼，降低開發效率與信任度。

**Q11：從產品設計角度來看，開發者應該如何強化編碼代理以應對 SWE-Touch 揭示的問題？**

A：首先，代理需要具備主動偵測工作區變更的能力，例如定期檢視當前差異（current diff）或監聽檔案系統事件，以維持正確的程式庫信念。其次，代理應學會將使用者編輯與任務規格（task specification）進行比對，判斷哪些修改需要保留、哪些需要協調或回退。最後，代理在修改受影響程式碼後，應執行針對性測試來驗證受影響行為（affected behavior），確保最終狀態符合任務目標。

**Q12：SWE-Touch 對整個編碼代理研究領域可能帶來什麼樣的影響或典範轉移？**

A：SWE-Touch 將評測焦點從「代理獨立完成任務的自主編碼能力」擴展到「代理與使用者在共享工作區中協作的狀態感知與適應性行為」。這意味著未來的模型優化不能只追求靜態排行榜上的高解決率，還必須考量真實多輪互動中的穩健性。長期來看，這將促使研究社群更重視互動式評測、差異感知與衝突協調機制，進而推動更貼近實務需求的編碼代理發展。

**Q13：SWE-Touch 目前有哪些方法上的限制或適用範圍上的限制？**

A：目前 SWE-Touch 主要注入單一、經過驗證的 Counter-Edit，並搭配模擬的使用者訊息，這與真實世界中多編輯、多輪、非結構化的使用者行為仍有距離。此外，該框架聚焦於「與任務衝突的編輯」，較少探討使用者提供部分正確線索或澄清需求等建設性情境。因此，未來需要擴展到更複雜的互動模式，才能更全面地評估代理在真實協作環境中的表現。

**Q14：哪些類型的模型或任務最容易在 SWE-Touch 上失敗？這對模型選型有什麼啟示？**

A：實驗顯示，部分在傳統自主基準上表現強勁的開源模型，在 SWE-Touch 的互動情境下退化幅度較大，顯示它們的狀態感知能力相對不足。此外，任務越長、需要越多步驟的長期任務，代理越容易在過程中遺忘或忽略使用者注入的修改。這提醒產品開發者在選型時，不應僅參考單一自主排行榜，而應同時評估模型在動態共享工作區中的協作穩健性。

**Q15：基於 SWE-Touch 的發現，未來研究可以朝哪些方向進一步優化編碼代理？**

A：未來可以發展更強大的工作區變更偵測機制，例如讓代理在每次行動前主動比對當前差異並更新程式庫信念。也可以研究如何讓代理在面對衝突編輯時，進行更有效的衝突協調決策，例如透過對話向使用者確認意圖，或自動執行受影響區域的單元測試（unit tests）。此外，將 SWE-Touch 擴展到多編輯、多使用者、真實 IDE 環境，並結合真實開發者研究，將是推動編碼代理從「自動完成工具」邁向「可靠協作者」的關鍵下一步。

## 實務應用指南

### 適用場景

1. **企業內部 AI 程式設計助理與工程師協作**  
   工程師在編碼代理執行修復任務時，同時手動修改共享工作區中的程式碼，用 SWE-Touch 測試代理能否偵測外部變更並正確調解衝突。

2. **多代理／多人共享程式碼倉儲的協作開發平台**  
   模擬其他使用者或代理對任務關鍵區域（task-critical regions）的編輯，評估系統的狀態感知（state awareness）與衝突調解能力。

3. **程式碼審查與持續整合前的壓力測試**  
   在 CI 流程中注入對抗性編輯（Counter-Edit），檢驗自動修復代理是否會保留錯誤程式碼、忽略外部變更，或在未驗證的情況下覆蓋使用者修改。

4. **互動式程式設計教學與訓練環境**  
   學生或教師即時修改程式碼，觀察代理如何回應變更、解釋差異，並提供回饋，藉此強化學習者對協作除錯的理解。

5. **長期維護與大型專案的智慧化運維**  
   針對 SWE-Bench Pro、DeepSWE 等長期任務，評估代理在中途程式庫狀態（repository state）發生變化時的穩健性與適應性行為（adaptive behavior）。

---

### 實作前置條件

**資料需求**
- 可執行的程式碼倉儲與對應測試套件（例如 SWE-bench Verified 或內部專案）。
- 多條修復軌跡（repair trajectories），用於挖掘任務關鍵區域。
- 版本控制歷史與 diff 資料，作為生成 Counter-Edit 的基礎。
- 可產生上下文使用者訊息（user messages）的模板或語料。

**運算需求**
- 執行多條代理軌跡需要 GPU／TPU 或足夠 CPU 核心進行 LLM 推理。
- 執行可執行測試（executable tests）需要隔離容器／沙箱（如 Docker）。
- 儲存軌跡、中間程式庫狀態與評估結果需要足夠的儲存空間。

**技能需求**
- 熟悉 Python、Git 與軟體測試／除錯。
- 了解 LLM agent 框架（如 OpenHands、SWE-agent、AutoCodeRover）。
- 具備提示工程（prompt engineering）與評估指標設計能力。
- 具備容器化與 CI/CD 基礎，能建立安全的評估環境。

---

### 實作步驟建議

1. **選定基準任務與倉儲**  
   選擇 SWE-bench Verified 或內部專案，確保每個任務都有明確任務規格（task specification）與可執行測試。

2. **收集修復軌跡**  
   使用目標編碼代理多次執行任務，記錄其讀取、編輯、測試動作，識別任務關鍵區域。

3. **建立使用者修補程式產生器（User Patch Generator）**  
   基於關鍵區域，利用 LLM 或規則生成小範圍、局部合理且與任務衝突的 Counter-Edit，並自動驗證：
   - 不會單獨解決任務；
   - 不會被輕易忽略。

4. **設計注入時機與訊息**  
   在代理到達相關程式碼時，套用 Counter-Edit 並附帶上下文使用者訊息，模擬真實共享工作區變更。

5. **執行評估並蒐集軌跡**  
   在隔離環境中執行代理，記錄最終程式庫狀態、對話、當前差異（current diff）與測試結果。

6. **建立狀態感知與調解指標**  
   計算解決率（resolve rate）下降幅度、保留衝突程式碼比例、重新檢查次數，以及受影響行為（affected behavior）的驗證覆蓋率。

7. **迭代改善代理**  
   針對失敗模式——未偵測變更、過度遵從使用者程式碼、修改後未驗證——加入 diff 監控、衝突偵測與重新測試策略。

8. **產品化部署**  
   將評估流程整合到內部 Agent 平台或 CI，作為上線前的互動協作壓力測試閘道。

---

### 潛在風險與注意事項

- **Counter-Edit 設計不當**  
  過度困難或過度簡單的編輯都會扭曲指標。應透過自動驗證與人工抽樣，確保其「合理但衝突」。

- **代理過度防禦**  
  若代理學會忽略所有使用者編輯，反而會降低協作品質。應區分「合理協助」與「衝突編輯」兩種情境。

- **注入時機偏差**  
  過早或過晚注入會改變任務難度。建議固定在代理到達任務關鍵區域時注入，並記錄時間戳。

- **環境隔離不足**  
  Counter-Edit 可能污染真實程式碼或觸發副作用。評估必須在獨立沙箱中進行。

- **長期任務成本高昂**  
  長期任務需設定預算與超時機制，並對軌跡進行取樣分析，而非全量檢視。

- **過度優化對抗性情境**  
  過度強化對抗 robustness 可能犧牲自主任務效能。建議同時監控基準解決率與互動解決率。

---

### 與其他技術的整合建議

- **版本控制系統（Git）**  
  透過 `git diff` / `git status` 讓代理即時感知工作區變更，並在提示中納入當前差異。

- **CI/CD 與測試框架**  
  將 SWE-Touch 評估作為合併前檢查，結合 pytest、unittest 或專案自有測試驗證受影響行為。

- **Agent 框架（OpenHands、SWE-agent、AutoCodeRover）**  
  外掛化 Counter-Edit 注入與狀態監控模組，复用其工具呼叫機制。

- **對話／訊息系統**  
  把使用者訊息與程式碼修改封裝成統一事件流，讓代理能同時處理文字回饋與 executable state 變化。

- **檢索增強生成（RAG）**  
  在代理重新檢視程式碼時，提供相關測試、文件與歷史修復案例，輔助衝突調解。

- **可觀測性平台（LangSmith、Langfuse）**  
  將軌跡、程式庫信念（repo belief）與 diff 變化匯出到追蹤系統，方便事後分析與除錯。

### 給不同背景讀者的閱讀建議

**初學者**  
先理解「共享工作區」的核心概念——使用者與代理在同一程式碼庫上操作，並聚焦於圖 1 與實驗結果：即使強大的模型也會因為沒注意到使用者修改而失敗。技術細節可略讀，重點放在為何「狀態感知」比單純會寫程式更重要。

**AI 工程師**  
仔細閱讀 Counter-Edit 的生成與驗證流程、注入時機設計，以及軌跡分析中歸納的失敗模式。這些是將論文方法落地到自家代理系統時最直接的實作參考，並可對照自己的 agent 框架調整提示與工具。

**研究人員**  
關注本文對互動式程式設計評測的擴展——從訊息互動到 executable state 變更，並思考 Counter-Edit 作為壓力測試的理論邊界，例如如何量化「合理但衝突」的編輯空間、以及如何設計更細緻的狀態感知指標。

**產品經理**  
把重點放在適用場景與商業風險：當使用者在 AI 輔助編碼過程中動手改程式碼，代理若保留錯誤程式碼或覆蓋使用者意圖，將直接影響使用者信任與產品採用。可據此規劃「協作安全」與「變更確認」等產品機制。
