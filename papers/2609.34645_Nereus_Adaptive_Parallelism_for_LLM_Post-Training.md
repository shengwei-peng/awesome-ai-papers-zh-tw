## ⚡ TL;DR

強化學習後訓練中，資源、序列長度、記憶體與階段瓶頸會動態變化，使初始計畫變慢或不可行。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）的強化學習（Reinforcement Learning, RL）後訓練會在 GPU 叢集（GPU clusters）上協調多個模型，橫跨生成（generation）、推論（inference）與訓練（training）等階段（stage）。執行過程中，多項因素可能發生變化，包括資源可用性（resource availability）、序列長度（sequence length）、記憶體壓力（memory pressure）與階段瓶頸（stage bottlenecks）。因此，最初適合的執行計畫（execution plan）可能隨時間變得緩慢，甚至不可行（infeasible）。然而，調適模型彼此共享 GPU 的作業（job）面臨重大挑戰：判斷新計畫是否值得付出轉換成本（transition cost）、重複利用作業的分散式狀態（distributed state），以及協調橫跨模型與階段的 GPU 傳輸（GPU transfers）。

Nereus 作為一個成本感知執行時期（cost-aware runtime），針對上述挑戰，將強化學習後訓練（RL post-training）作業調適為高效率的執行計畫。其低開銷控制器（low-overhead controller）選出一個記憶體可行的全域計畫（memory-feasible global plan），並利用依據執行中作業校正（calibrated）的成本模型（cost model）來決定是否准許轉換（admit transition）。為了估計並執行轉換（transition），Nereus 將每個模型階段副本（model-stage replica，即某模型在某一階段的副本）的分散式狀態表示為一個彈性模型單元（Elastic Model Unit, EMU），並使用全域轉換圖（global transition graph）來排序這些單元的轉換操作與 GPU 傳輸。

在一組由真實資料（real data）建立的追蹤資料（trace）中，相較於採用資料平行擴展（DP scaling）的初始固定張量／流水線平行（Tensor Parallelism / Pipeline Parallelism, TP/PP）配置（initial fixed TP/PP layout），線上張量／流水線平行（TP/PP）自適應調整（online TP/PP adaptation）使平均步驟延遲（average step latency）降低 27.7%。在一次擴展至 1,024 個 GPU 的 1,000 步驟執行中，六次轉換耗用總執行時間（total run time）的 0.079%。在多樣化叢集（diverse clusters）上，Nereus 的端到端（end-to-end）8B 近端策略最佳化（Proximal Policy Optimization, PPO）吞吐量（throughput）相較於 OpenRLHF 提升 2.14 至 7.27 倍，相較於 Verl 提升 1.10 至 1.47 倍。

### 核心貢獻（3～5點）
- 提出成本感知執行時期（cost-aware runtime）Nereus，可在強化學習後訓練（RL post-training）執行過程中動態調整執行計畫（execution plan），以因應資源可用性、序列長度、記憶體壓力與階段瓶頸等變化。
- 設計低開銷控制器（low-overhead controller），透過依執行中作業校正的成本模型（cost model）選擇記憶體可行的全域計畫（memory-feasible global plan），並僅在轉換成本（transition cost）划算時才准許轉換（admit transition）。
- 提出彈性模型單元（Elastic Model Unit, EMU）作為分散式狀態（distributed state）抽象，並以全域轉換圖（global transition graph）協調跨模型與階段的狀態轉換與 GPU 傳輸。
- 在真實資料追蹤（trace）與大規模 GPU 叢集實驗中驗證，線上 TP/PP 自適應調整可顯著降低平均步驟延遲，且轉換開銷極低；端到端吞吐量顯著優於 OpenRLHF 與 Verl。

### 適合對象
本論文適合從事大型語言模型（LLM）後訓練、分散式深度學習系統、GPU 叢集資源調度，以及強化學習後訓練（RL post-training）框架設計的研究人員與系統工程師閱讀。特別是對於需要在大規模 GPU 叢集上動態調整模型平行策略、降低訓練延遲並提升端到端吞吐量（end-to-end throughput）的實務工作者，本研究提供了具體的系統設計與實驗驗證。

## 深度分析

#### 方法論解析

Nereus 的核心目標是將 RL 後訓練（RL post-training）作業在執行過程中持續對應到高效的執行計畫（execution plan）。由於作業同時涉及多個模型（Actor、Reference、Reward、Critic）與多個階段（generation、inference、training），且這些模型階段會共享 GPU，因此任何單一維度的調整（例如只增加 Data Parallelism, DP）都可能牽動其他模型階段的記憶體與通訊。Nereus 將問題拆解為三個層次：**何時轉換（when）**、**重複使用什麼狀態（what）**、**如何安全轉換（how）**。

##### 1. 成本感知適應策略（cost-aware adaptation policy）

系統由一個低開銷控制器（low-overhead controller）主導，包含 Monitor、Planner 與 Admission 三個元件：

- **Monitor**：持續追蹤序列長度（sequence length）、可用 GPU 數量（GPU count）、峰值記憶體（peak memory）以及各階段的計算與通訊效率。
- **Planner**：在偵測到資源飄移（resource drift）或工作負載飄移（workload drift）後，選出一個記憶體可行（memory-feasible）且預測步驟延遲（step latency）最低的目標計畫（target plan）S*。
- **Admission**：決定是否准許轉換（admit transition）。若現行計畫（current plan）已不可行（infeasible），則觸發緊急轉換（urgent transition）；否則只有在預期節省量（savings）能償還一次性轉換成本（transition cost）時才執行。轉換成本由轉換引擎（transition engine）根據線上校正（online calibration）的成本模型（cost model）估計。

這個設計的關鍵在於將「重新規劃（replan）」與「執行轉換（execute transition）」解耦：Planner 只負責搜尋目標配置，Admission 則用輕量成本模型把轉換開銷納入決策，避免頻繁切換導致總吞吐量（throughput）反而下降。

##### 2. 彈性模型單元（Elastic Model Unit, EMU）

Nereus 提出的狀態抽象（state abstraction）是 **EMU**。每個 EMU 對應一個模型階段副本（model-stage replica），也就是「某個模型在某一階段的一個 DP 副本」。EMU 內部封裝了緊密耦合的張量平行（Tensor Parallelism, TP）與流水線平行（Pipeline Parallelism, PP）配置，以及該副本的參數（parameters）、輸入與優化器狀態（optimizer state）。EMU 之間則以副本數量（replica count）表達資料平行（Data Parallelism, DP）。

這種抽象的好處在於對齊狀態邊界與模型相依性（dependency-aligned state abstraction）：同一模型階段內的 TP/PP 分片（sharding）與放置（placement）是高度相依的，因此封裝在 EMU 內部；而不同模型階段或不同 DP 副本之間的耦合較鬆，可以獨立進行擴展或縮減。相較於過粗的全局檢查點（checkpoint）式遷移，EMU 減少了冗餘傳輸；相較於過細的 shard-level 規劃，EMU 又降低了規劃複雜度。

##### 3. 四種基本轉換原語（transformation primitives）

轉換引擎將現行計畫與目標計畫的差異（plan diff）編譯為四種操作：

- **Split（拆分）**：將一個 EMU 拆成更多 TP/PP 分片或更多副本，對應資源增加時的擴展。
- **Merge（合併）**：將多個 EMU 合併，對應資源減少或序列長度（sequence length）縮短時的縮減。
- **Extend（擴展）**：新增 DP 副本，不改變單一 EMU 內部 TP/PP。
- **Destroy（銷毀）**：移除多餘副本。

這四種原語被宣稱能涵蓋計畫空間中的所有平行配置，同時保留訓練語意（training semantics）。

##### 4. 全域轉換 DAG 與安全並發轉換編排（safe concurrent transition orchestration）

轉換引擎將所有 EMU 的原語操作組織成一個全域轉換有向無環圖（global transition DAG）。DAG 的節點是 EMU 層級的操作，邊則表示兩類相依性：

- **語意相依性**：例如必須先完成某個模型階段的狀態轉移，另一個階段才能開始使用其釋出的 GPU。
- **資源相依性（resource-dependency edges）**：當暫態 GPU 重疊（transient GPU overlap）導致某個操作無法取得所需 GPU 時，引擎會動態加入額外邊以避免死結（deadlock）。

執行時，引擎會優先執行釋放資源的操作，讓獨立的狀態傳輸能夠並發進行，從而最小化轉換時間。這解決了「在沒有空閒 GPU 時，必須先讓某個模型階段釋放資源，另一個階段才能擴展」的難題。

整體架構可視為一個閉迴路：Monitor 偵測飄移 → Planner 產生 S* → Admission 用成本模型決定是否轉換 → Transition Engine 編排並執行 EMU 原語 → 作業繼續以新計畫運行。

#### 實驗數據解讀

論文提供了多組量化結果，可分為三大類：**端到端吞吐量（end-to-end throughput）**、**線上適應效益**、**轉換效率與可擴展性**。

##### 1. 端到端吞吐量

在 8B PPO（80 億參數的近端策略最佳化）設定下，Nereus 相較於現有框架的改善幅度為：

- **相較 OpenRLHF**：吞吐量提升 2.14–7.27 倍，中位數 3.99 倍。
- **相較 Verl**：吞吐量提升 1.10–1.47 倍。

這表示 Nereus 在現有 RL 後訓練框架已經能運作的前提下，仍能透過動態調整 TP/PP/DP 獲得顯著增益。對 OpenRLHF 的大幅領先可能來自後者採用固定或較粗粒度的平行配置；對 Verl 的領先則較溫和，顯示 Verl 已具備一定彈性，但 Nereus 的全域計畫與成本感知決策仍能進一步壓低延遲。

此外，Nereus 在 18 個測量設定中，所選計畫都落在經驗最佳值（empirical optimum）的 5% 以內。這說明其 Planner 的搜尋與成本模型不僅有效，而且相當穩健，不會因貪婪選擇而落入明顯次優配置。

##### 2. 線上適應效益

論文使用真實資料建構的追蹤資料（trace）進行模擬/回放：

- **線上 TP/PP 自適應調整（online TP/PP adaptation）** 相較於「初始固定 TP/PP 配置 + DP 擴展」可將平均步驟延遲（average step latency）降低 **27.7%**。
- 在三組保留追蹤資料（held-out traces）上，Nereus 的平均每步時間為 **858.7 秒**，而 DynaRL 風格的准許策略為 **928.3 秒**。

27.7% 的延遲降低是相當可觀的，因為 RL 後訓練通常需要數千到數萬步，每步延遲的累積效應會直接影響總訓練時間與成本。DynaRL 雖然也會適應資源，但只在固定資源池內進行逐元件遷移（per-component migrations），缺乏全域視角，因此其平均步驟時間較長。

##### 3. 轉換效率與可擴展性

- 在一個擴展到 1,024 GPU、共 1,000 步的執行中，六次轉換只佔總執行時間（total run time）的 **0.079%**。換算後每次轉換平均僅約 1.3 秒（假設總時間約 10,000 秒級別），顯示轉換開銷極低。
- 使用 EMU 進行狀態擴展比 Oobleck 快 **3.8–16.2 倍**，也比 Tenplex 快。
- 在資源重疊試驗（overlap trials）中，Nereus 的協調轉換全部成功；DynaRL 的逐元件遷移成功率僅 **34–62%**。

這些數據強調了 Nereus 在「轉換正確性」與「轉換速度」兩方面的優勢。特別是 0.079% 的開銷比例，意味著 Admission 的成本模型有足夠空間容許較頻繁的適應，而不會被轉換懲罰抵消。

##### 4. 綜合評估

整體而言，實驗結果支持以下結論：

- **全域適應優於僅調整 DP**：單純增加資料平行副本無法應對序列長度增長（sequence-length growth）或階段瓶頸（stage bottlenecks）帶來的記憶體壓力（memory pressure）。
- **轉換開銷可控**：成本感知策略與並發轉換編排讓適應幾乎不影響總運行時間。
- **可擴展到千卡級別**：1,024 GPU 的規模證明了方法在大型叢集（GPU clusters）上的可行性。

不過，論文未明確說明實驗是否包含真實的節點故障（node failures）情境，以及成本模型在極端飄移下的收斂速度，這些是解讀時需要留意的缺口。

#### 與現有研究的比較

Nereus 的定位介於「彈性訓練系統」與「RL 後訓練框架」之間。以下從幾個代表性工作進行比較。

##### 1. OpenRLHF 與 Verl

OpenRLHF 與 Verl 都是專注於 RL 後訓練的開源框架，但它們主要解決「如何正確實現 PPO / GRPO / ReMax」等演算法問題，對於執行計畫的動態調整支援有限。Nereus 則是在這些框架之上（或平行地）提供一個成本感知執行時期（cost-aware runtime），能夠根據序列長度、GPU 數量、記憶體壓力動態改變 TP/PP/DP。實驗顯示，即使 Verl 已具備一定彈性，Nereus 仍能提升 10–47% 吞吐量，說明「全域計畫 + 狀態重用」是關鍵差異。

##### 2. DynaRL

DynaRL 同樣針對 RL 訓練進行資源調度，但其限制在於：

- 只在固定資源池（fixed pool）內進行調度；
- 採用逐元件遷移（per-component migrations），缺乏跨模型階段的協調；
- 未考慮轉換成本（transition cost）。

Nereus 則提出全域計畫（global plan）與成本感知准許條件（savings-outweigh-cost condition），並透過 EMU 與 transition DAG 協調耦合模型（coupled models）。實驗中 DynaRL 風格策略的平均步驟時間較長，且在重疊試驗中成功率僅 34–62%，凸顯了協調的重要性。

##### 3. Oobleck 與 Tenplex

Oobleck 與 Tenplex 是通用彈性深度學習訓練系統，支援動態調整平行配置。Nereus 與它們的差異在於：

- **狀態抽象粒度**：Oobleck 使用 pipeline template，Tenplex 使用細粒度分片；Nereus 的 EMU 則對齊模型階段副本，兼顧規劃簡單性與傳輸效率。
- **應用場景**：Oobleck/Tenplex 主要針對單一模型訓練；Nereus 針對多模型、多階段的 RL 後訓練，必須處理模型間共享 GPU 與階段瓶頸。
- **轉換速度**：實驗顯示 EMU 擴展比 Oobleck 快 3.8–16.2 倍，比 Tenplex 也快，這可能歸因於 EMU 減少了不必要的狀態移動與重新初始化。

##### 4. 其他相關工作

- **vLLM / DeepSpeed / Megatron-LM**：Nereus 整合這些元件，但並未取代它們，而是作為上層執行時期協調它們的平行配置。
- **Fault-tolerance 系統**：論文提到 Nereus 可與容錯系統互補，在節點故障時從完好的 EMU 重新規劃。這是一個潛在優勢，但實驗著墨不多。

##### 5. 限制與潛在弱點

- **模型規模**：實驗主要聚焦 8B PPO，對於 70B 或更大模型的記憶體壓力與通訊模式是否仍適用，需要更多驗證。
- **演算法覆蓋**：雖然論文提到 PPO、ReMax、GRPO，但實驗數據以 PPO 為主。
- **成本模型假設**：成本模型需要線上校正（calibration），在作業初期或飄移劇烈時可能不夠準確。
- **叢集同質性**：方法假設 GPU 叢集相對同質，對於異構 GPU 或網路拓樸變化的處理未詳細討論。

#### 可重現性評估

可重現性（reproducibility）是評估任何系統研究的重要面向。根據論文提供的資訊：

##### 1. 程式碼與實作

- Nereus 以 **43,000 行 Python、C++、CUDA/HIP** 實作，整合了 vLLM、DeepSpeed 與 Megatron-LM，並使用標準 NCCL/RCCL 集合通訊。
- 論文未明確提供原始碼倉庫連結或開源授權資訊。雖然首頁提到 Creative Commons Attribution 4.0 License，但這通常指論文本身，而非程式碼。
- 由於涉及多個大型框架的緊密整合，即使未來開源，重現門檻仍然很高：需要特定版本的 vLLM、DeepSpeed、Megatron-LM，以及對應的 GPU 驅動與網路環境。

##### 2. 資料與模型權重

- 論文使用「真實資料建構的追蹤資料（trace built from real data）」進行部分實驗，但未說明是否公開這些 trace。
- 8B PPO 的模型權重、資料集、超參數等細節未在提供的摘要與片段中出現。若論文正文未詳細記載，則難以完全重現端到端吞吐量數據。

##### 3. 硬體環境

- 實驗涵蓋多樣化叢集（diverse clusters），最大規模達 1,024 GPU。這類規模的硬體資源通常超出一般研究團隊的範圍，即使程式碼開源，大規模實驗仍難以重現。
- 論文提到使用標準 NCCL/RCCL，這降低了對專有通訊庫的依賴，但網路拓樸與 GPU 型號的差異會顯著影響結果。

##### 4. 可重現性綜合判斷

目前根據提供的片段，**可重現性處於中等偏低水準**：方法論描述相對完整，但缺乏公開程式碼、資料集與詳細超參數。若作者後續釋出原始碼與 trace，並提供重現腳本，則可大幅提升可重現性。對於想要驗證的研究者，現階段最可行的方式是根據論文描述的 EMU 抽象與 transition DAG 機制，在較小規模上進行概念驗證（proof-of-concept）。

---

#### 未來研究方向

Nereus 為 RL 後訓練的動態平行性開闢了多條後續研究路徑：

##### 1. 擴展到更大規模與異構叢集

目前實驗以 8B PPO 為主，未來可驗證 70B、400B 等更大模型，並探索在異構 GPU（例如 H100 與 A100 混布）或不同網路拓樸下的計畫搜尋與轉換策略。此時 EMU 內部的 TP/PP 配置需要進一步考慮節點間頻寬與 NVLink 拓樸。

##### 2. 與容錯機制深度整合

論文提到 Nereus 可在節點故障時從完好 EMU 重新規劃，但未深入設計。未來可發展專門的故障偵測、EMU 級檢查點與快速恢復協定，讓系統在千卡級叢集上具備生產級可用性。

##### 3. 更精準的成本模型與預測

目前的成本模型仰賴線上校正。未來可結合機器學習預測序列長度增長（sequence-length growth）與資源飄移（resource drift），在飄移發生前就預先規劃目標配置，進一步降低適應延遲。

##### 4. 支援更多 RL 後訓練演算法

雖然 PPO、ReMax、GRPO 的階段結構相似，但不同演算法對 Reference、Reward、Critic 的更新頻率與記憶體需求不同。未來可針對 GRPO 的群組採樣（group sampling）或 ReMax 的單一獎勵設計專屬的計畫搜尋啟發式規則。

##### 5. 多作業叢集層級排程

Nereus 目前聚焦單一作業（single job）內的適應。未來可將其擴展到多作業共享叢集的情境，與叢集排程器（cluster scheduler）協同，動態分配 GPU 給不同 RL 後訓練作業，並在作業間遷移 EMU。

##### 6. 能源與成本最佳化

除了步驟延遲與吞吐量，未來可將能源消耗、雲端計價、 spot instance 搶占風險納入成本模型，讓 Nereus 在成本感知（cost-aware）之外也具備「經濟感知（price-aware）」能力。

##### 7. 理論保證

目前 Nereus 的准許策略基於經驗成本模型。未來可研究在給定飄移模型下，轉換決策的競爭比（competitive ratio）或遺憾值（regret bound），為線上適應提供理論保障。

##### 8. 開源與標準化

釋出 Nereus 原始碼、追蹤資料與評估腳本，並推動 EMU 抽象成為彈性 RL 後訓練的標準介面，將有助於社群驗證、改進並整合到 OpenRLHF、Verl 等框架中。

## 論文問答

**Q1：Nereus 主要想解決什麼問題？**
A：Nereus 針對的是大型語言模型強化學習後訓練（RL post-training）在 GPU 叢集上執行時，資源可用性、序列長度、記憶體壓力與階段瓶頸會隨時間飄移的問題。由於生成、推論與訓練階段涉及多個耦合模型（Actor、Critic、Reference、Reward 等），一開始合適的執行計畫可能逐漸變慢甚至不可行。傳統固定平行配置無法因應這些動態變化，因此需要一套能夠在執行期間動態調整全域執行計畫的執行時期系統。

**Q2：為什麼現有方法（例如 DynaRL 或逐元件遷移）無法妥善解決這個問題？**
A：現有方法如 DynaRL 通常只在固定資源池內對各階段做資源分配，並採用逐元件遷移（per-component migrations），缺乏對整體作業的全域觀點。這些方法難以處理多個模型階段共享 GPU 時的狀態重複使用與傳輸協調問題，容易導致死結或轉換失敗。此外，它們也未能同時考量轉換成本（transition cost）與預期效能收益，因此無法判斷何時真正值得進行計畫轉換。

**Q3：自適應平行性對 LLM 後訓練為何重要？**
A：RL 後訓練是一個多模型、多階段的長時間執行過程，不同階段的運算與通訊特性會隨序列長度增長或批次變化而改變。靜態的張量平行（TP）與流水線平行（PP）配置可能在執行初期有效，但後期會因記憶體不足或負載不平衡而變成瓶頸。透過自適應平行性，系統可以持續維持記憶體可行性並提升端到端吞吐量，避免 GPU 資源閒置或作業中斷。

**Q4：Nereus 的核心方法架構是什麼？**
A：Nereus 是一個成本感知執行時期（cost-aware runtime），由低開銷控制器、彈性模型單元（EMU）狀態抽象與轉換引擎三大部分組成。控制器內的監控器持續追蹤資源與工作負載飄移，規劃器選出記憶體可行的目標計畫（target plan），並由准許機制判斷預期節省是否大於轉換成本。轉換引擎則將現行計畫與目標計畫的差異編譯成全域轉換有向無環圖（transition DAG），並安全地執行狀態轉移。

**Q5：Elastic Model Unit（EMU）的關鍵創新是什麼？**
A：EMU 的關鍵在於將狀態邊界對齊模型相依性，使得狀態重複使用的粒度既不會過粗也不會過細。每個 EMU 封裝了一個模型階段副本（model-stage replica）內部的 TP/PP 配置與狀態，同時將資料平行（DP）視為可彈性調整的副本數量。這種設計讓轉換引擎能直接對 GPU 常駐狀態進行 Split、Merge、Extend、Destroy 四種基本操作，而無需重建整個作業狀態。

**Q6：Nereus 在轉換編排上做了哪些設計選擇以確保安全與效率？**
A：轉換引擎會將計畫差異（plan diff）轉換為 EMU 層級的基本操作，並根據資源相依性與狀態相依性建立全域 transition DAG。當暫態 GPU 重疊（transient GPU overlap）會阻礙資源取得時，引擎會額外加入資源相依邊（resource-dependency edges）以避免衝突。為了避免記憶體受限環境中的死結，協議會動態優先執行釋放資源的操作，並允許獨立的狀態傳輸並發進行，從而縮短轉換時間。

**Q7：論文使用了哪些實驗設定與比較基準？**
A：評估涵蓋了 8B PPO 在多樣化 GPU 叢集上的端到端吞吐量測試、18 種不同設定下的計畫品質驗證，以及基於真實資料建構的追蹤資料（trace）進行線上 TP/PP 自適應調整。比較對象包括現有 RL 後訓練框架 OpenRLHF、Verl，以及資源調度系統 DynaRL，另外也與狀態遷移系統 Oobleck 和 Tenplex 比較擴展效率。這些實驗同時檢驗了轉換成功率、轉換開銷與長時間執行穩定性。

**Q8：Nereus 取得了哪些關鍵量化結果？**
A：在真實資料追蹤中，線上 TP/PP 自適應調整相較於初始固定 TP/PP 配置搭配 DP 擴展，平均步驟延遲降低了 27.7%。端到端 8B PPO 吞吐量相較於 OpenRLHF 提升 2.14–7.27 倍，相較於 Verl 提升 1.10–1.47 倍，且在所有 18 個測量設定中，Nereus 選出的計畫都落在實證最佳解的 5% 以內。此外，一個擴展到 1,024 GPU、執行 1,000 步的作業中，六次轉換僅佔總執行時間的 0.079%。

**Q9：哪些消融或對比實驗凸顯了 Nereus 各元件的價值？**
A：與 DynaRL 風格的准許機制相比，Nereus 在三個保留追蹤資料上的平均步驟時間為 858.7 秒，優於 DynaRL 的 928.3 秒，顯示其成本感知准許策略更有效。在狀態擴展方面，使用 EMU 進行 scaling 比 Oobleck 和 Tenplex 快 3.8–16.2 倍，證明 EMU 抽象在狀態重複使用上的優勢。而在資源重疊情境下，Nereus 的協調轉換成功率達 100%，遠高於 DynaRL 逐元件遷移的 34–62%，凸顯全域轉換編排的必要性。

**Q10：Nereus 在哪些實際場景中特別有幫助？**
A：Nereus 特別適合長時間執行的 RL 後訓練作業，例如序列長度會隨訓練進行而增長的 PPO 或 GRPO 流程。它也適用於共享 GPU 叢集，因為節點故障或資源被其他作業搶占會造成資源飄移，Nereus 能動態重新規劃並從完好的 EMU 恢復。此外，當不同訓練階段出現負載不平衡或記憶體壓力時，Nereus 可以及時調整 TP/PP/DP 配置，避免作業因記憶體不足而中斷。

**Q11：在實際產品部署 Nereus 時需要考慮哪些因素？**
A：Nereus 已整合 vLLM、DeepSpeed 與 Megatron-LM，並使用標準 NCCL/RCCL 集合通訊，因此可部署於現有 GPU 叢集，但需確保框架版本與其 43,000 行 Python/C++/CUDA/HIP 實作相容。控制器的低開銷設計使其能在執行期間持續監控與校正成本模型，但部署時仍需考量校正頻率與觸發閾值的調校。此外，由於轉換涉及跨模型階段的 GPU 傳輸，網路拓樸與 GPU 記憶體容量會直接影響轉換成本與可行性。

**Q12：Nereus 對相關研究領域可能帶來什麼影響？**
A：Nereus 展示了如何將線上自適應平行性與多模型狀態協調結合，為 RL 後訓練與更廣泛的分散式機器學習系統提供了一個新的設計範式。它證明僅靠 DP 擴展不足以應對動態負載，動態調整 TP/PP 與全域狀態重複使用同樣重要。未來的後訓練框架與叢集排程器可能會採用類似的 EMU 抽象與成本感知准許機制，以提升長時間作業的資源效率。

**Q13：Nereus 有哪些已知的限制？**
A：目前 Nereus 主要聚焦於 TP、PP 與 DP 三種平行策略的組合，對於其他新興平行策略（如 sequence parallelism 或 context parallelism）的支援仍需擴展。其成本模型雖然會根據執行中作業進行線上校正，但在極端快速的資源飄移下，控制器決策可能會稍有延遲。此外，EMU 的設計假設同一模型階段副本內的狀態緊密耦合，對於需要更細粒度狀態操作的場景可能不夠靈活。

**Q14：Nereus 在哪些情況下可能表現不佳或失敗？**
A：如果工作負載飄移過於劇烈，導致轉換成本無法在後續步驟中回收，則 Nereus 可能會選擇不轉換而繼續使用次優計畫。當成本模型對轉換時間或新計畫效能預測不準時，也可能做出錯誤的准許決策。在記憶體極度受限且多個模型階段同時爭奪 GPU 的情境下，若資源釋放順序未妥善安排，仍可能發生死結；此外，若某個模型階段的所有副本同時故障，則無法透過 EMU 重複使用狀態恢復。

**Q15：未來可以朝哪些方向延伸 Nereus？**
A：未來可將 Nereus 擴展到更多 RL 後訓練演算法，例如 GRPO、ReMax 與 DPO，並支援異質 GPU 叢集與更複雜的網路拓樸。另一個方向是引入預測式飄移偵測，讓控制器在瓶頸發生前就預先規劃轉換，進一步降低轉換對執行的干擾。最後，可以將 EMU 抽象與成本感知准許機制推廣到一般的分散式機器學習作業，例如多模態訓練或推論服務，使其成為通用的動態平行性執行時期。

## 實務應用指南

### 適用場景

1. **長序列且動態增長的 RL 後訓練**  
   在 PPO、GRPO、ReMax 等強化學習後訓練中，若回應長度（sequence length）會隨訓練逐漸變長，靜態的張量平行（TP）/流水線平行（PP）配置很快會出現記憶體壓力或階段瓶頸。Nereus 可在執行期依據序列長度變化，線上調整 Generation、Inference、Training 各階段的 TP/PP 與資料平行（DP）副本數。

2. **GPU 資源會動態變化的多租戶叢集**  
   當叢集發生節點搶佔、故障或彈性擴縮容，導致可用 GPU 數量改變時，Nereus 能重新規劃全域執行計畫，透過 Extend/Destroy 等原語增減模型階段副本，而不是直接重啟作業。

3. **異質拓樸或跨叢集部署**  
   不同叢集的節點間頻寬、NVLink 拓樸、GPU 型號不同，初始固定的 TP/PP 布局往往不是最佳。Nereus 可針對當前拓樸選擇記憶體可行且延遲最低的全域計畫，提升端到端吞吐量。

4. **長時間執行的大規模後訓練作業**  
   對於動輒數千步、擴展到上千顆 GPU 的長期作業，Nereus 的成本感知准許機制可避免頻繁轉換，只在預期節省量高於轉換成本時才切換計畫，適合需要持續優化的生產級訓練。

5. **需要快速容錯的關鍵任務**  
   當部分節點故障時，Nereus 可從完好的彈性模型單元（EMU）重新規劃，減少從頭載入檢查點的停機時間，與現有容錯系統形成互補。

### 實作前置條件

**資料準備**
- 各模型階段（Actor、Reference、Critic、Reward）在 Generation、Inference、Training 的延遲與記憶體佔用追蹤資料。
- 序列長度分佈與未來增長趨勢的歷史 trace。
- 用於校正成本模型的微基準資料：Split、Merge、Extend、Destroy 四種轉換原語在實際叢集上的耗時。
- 可供回退的週期性檢查點（checkpoint）與優化器狀態備份。

**運算資源**
- 具備 NCCL/RCCL 支援的多節點 GPU 叢集。
- 轉換過程中需要短暫的暫態 GPU 重疊（transient GPU overlap），因此叢集需保留少量記憶體與頻寬餘裕。
- 建議先在同質性較高的叢集驗證，再推展到異質拓樸。

**技術能力**
- 熟悉 Megatron-LM、DeepSpeed、vLLM 的 TP/PP/DP 配置與狀態管理。
- 具備分散式訓練除錯、GPU 記憶體剖析與集體通訊效能分析經驗。
- 能閱讀並修改 Python/C++/CUDA/HIP 程式碼，以整合監控與轉換引擎。

### 實作步驟建議

1. **建立工作負載特徵基線**  
   在現行框架（OpenRLHF、Verl 等）上先執行固定 TP/PP 配置，收集每個模型階段的步驟延遲、峰值記憶體、通訊效率與序列長度變化。

2. **將作業建模為 EMU 集合**  
   把每個「模型階段副本」定義為一個 EMU：內部封裝 TP/PP 布局與狀態，外部以副本數量表示 DP 程度。確認 Actor、Reference、Critic、Reward 在 Generation、Inference、Training 的對應關係。

3. **部署 Nereus 監控器與控制器**  
   將監控器接入執行時期指標（序列長度、可用 GPU 數、峰值記憶體、計算/通訊效率），並設定重新規劃觸發條件，例如記憶體超過閾值或步驟延遲持續惡化。

4. **校正成本模型**  
   在真實叢集上執行各種轉換原語，測量其一次性轉換成本；同時建立穩態步驟延遲預測模型。讓控制器能計算「預期節省量 > 轉換成本」。

5. **定義計畫搜尋空間與限制**  
   根據 GPU 記憶體、節點內/節點間頻寬、模型層數，設定可行的 TP/PP/DP 組合，並排除會造成記憶體不可行的目標計畫。

6. **離線驗證轉換正確性**  
   模擬多組現行計畫 → 目標計畫的轉換，檢查全域轉換圖（transition DAG）是否無環、GPU 傳輸順序是否不會造成死結，並比對轉換前後的模型參數與優化器狀態數值一致性。

7. **啟用線上適應，採保守策略**  
   初期只允許「緊急轉換」（現行計畫不可行時），待穩定後再開啟基於節省量的准許機制。設定冷卻期（cooldown）避免轉換過於頻繁。

8. **持續監控與回退機制**  
   記錄每次轉換的實際耗時與穩態效益。若轉換失敗或數值異常，應能自動回退到檢查點重啟，而非繼續執行損壞狀態。

9. **迭代調整觸發靈敏度與搜尋空間**  
   根據線上資料調整重新規劃閾值、轉換並行度與記憶體餘裕，逐步逼近論文所述的「轉換開銷僅佔總執行時間 0.079%」等級。

### 潛在風險與注意事項

- **轉換成本低估導致震盪（thrashing）**  
  若成本模型未充分校正，可能頻繁切換計畫反而拖慢整體進度。建議加入滯後區間與最小持續步數限制。

- **暫態記憶體超載**  
  轉換過程中可能同時存在現行與目標計畫的 GPU 常駐狀態，造成短暫記憶體重疊。應預留記憶體餘裕，或在 DAG 中加入資源相依邊來序列化衝突操作。

- **狀態復用正確性**  
  重新分片（resharding）後，優化器狀態、隨機數種子、批次統計量必須正確對應。建議在啟用線上適應前，先進行數值等價性驗證。

- **後端版本相容性**  
  Nereus 整合 vLLM、DeepSpeed、Megatron-LM，版本差異可能影響狀態匯出/匯入介面。建議鎖定經過測試的版本組合，並建立持續整合測試。

- **網路壅塞**  
  大規模並發 GPU 傳輸可能壓垮節點間頻寬。可限制同時進行的 Split/Merge 數量，或利用拓樸感知排程。

- **過度適應短期波動**  
  對於執行步數較短的作業，轉換開銷可能無法攤提。建議僅在長期作業中啟動成本感知適應。

---

### 與其他技術的整合建議

- **叢集排程器（Kubernetes、Slurm）**  
  將可用 GPU 數量的變化事件傳遞給 Nereus 控制器，讓它在資源增減時自動重新規劃，而非直接終止或重啟整個作業。

- **檢查點與容錯系統**  
  Nereus 可從完好的 EMU 快速重組計畫，但仍需週期性檢查點作為最後防線。建議將控制器與檢查點管理器串接，轉換失敗時自動回退。

- **vLLM / DeepSpeed / Megatron-LM**  
  作為 Generation、Inference、Training 的後端引擎，需確保各後端能暴露模型狀態與平行配置的讀寫介面，供 EMU 進行狀態抽象與轉換。

- **監控與可觀測性（Prometheus、Grafana）**  
  將序列長度、步驟延遲、記憶體壓力、轉換事件與轉換耗時匯出為指標，方便營運團隊觀察適應行為與效益。

- **彈性訓練與自動擴縮容框架**  
  外部自動擴縮容負責決定「要給作業多少 GPU」，Nereus 負責決定「這些 GPU 內部如何切分給各模型階段」，兩者分工可提升整體資源利用率。

- **現有 RL 後訓練框架（OpenRLHF、Verl）**  
  可將 Nereus 作為底層執行計畫層，保留上層 PPO/GRPO 演算法邏輯；上線前建議以 A/B 測試比較端到端吞吐量與穩定性。

---

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從圖 1 的整體架構與圖 2 的多階段流程入手，理解為何靜態 TP/PP 配置會在 RL 後訓練中失效；接著補足張量平行、流水線平行、資料平行的基本概念，再回頭閱讀 EMU 與轉換 DAG 的設計動機。

**AI 工程師**  
重點研讀第 4 節的成本感知適應策略、第 5 節的彈性模型單元（EMU）狀態抽象，以及第 6 節的安全並發轉換編排。實作時請特別關注成本模型校正、轉換過程中的記憶體峰值，以及與 vLLM/DeepSpeed/Megatron-LM 的整合介面。

**研究人員**  
可深入分析 Nereus 與 DynaRL、Oobleck、Tenplex 的差異，特別是「全域計畫」相對於「逐元件遷移」的優勢、成本感知准許條件的形式化設計，以及 EMU 作為狀態抽象在並發轉換正確性上的理論基礎。

**產品經理**  
聚焦論文中的量化效益：相對固定布局平均步驟延遲降低 27.7%、8B PPO 端到端吞吐量提升 2.14–7.27 倍、1,024 GPU 執行 1,000 步僅耗 0.079% 時間在轉換。評估時請同時納入整合成本、維護複雜度與容錯回退需求，以判斷是否值得在現有訓練平台引入 Nereus。
