# HarnessRisk：針對智能體掛載框架安全性的生命週期導向基準

**原文標題：** HarnessRisk: A Lifecycle-Oriented Benchmark for Agent Harness Safety

**發布日期：** 2026-08-18

## ⚡ TL;DR

現有智能體安全基準多聚焦單一攻擊或有限情境，難以比較掛載框架各職責的安全失效。
提出 HarnessRisk，以 128 個沙箱案例涵蓋掛載框架六個運作階段，並評估效用與攻擊指標。
實驗顯示攻擊成功率達 12.6% 至 80.9%，掛載框架配置最脆弱，且高偵測率不保證安全行動。

## 摘要翻譯

大型語言模型越來越常透過智能體掛載框架（agent harness）部署，這類框架管理工具（tools）、擴充功能（extensions）、持久化狀態（persistent state）、權限（permissions）與外部行動（external actions）。現有的安全性基準多聚焦於個別攻擊機制（attack mechanisms）或有限的運作設定（operational settings），難以比較不同掛載框架職責中安全性失效（safety failures）的產生方式。我們提出 HarnessRisk，一個生命週期導向基準（lifecycle-oriented benchmark），將智能體掛載框架安全性劃分為六個運作階段（operational phases）：掛載框架配置（Harness Configuration）、能力擴充（Capability Extension）、執行階段運作（Runtime Operation）、狀態持久化（State Persistence）、行動控制（Action Control）與事件復原（Incident Recovery）。HarnessRisk 包含 128 個沙箱化案例（sandboxed cases），每個案例將一個良性使用者目標（benign user objective），與嵌入於不受信任工作流程產物（untrusted workflow artifact）中的對抗性指令（adversarial instruction）配對。我們使用效用（Utility）、攻擊成功率（Attack Success Rate）、持續性（Persistence）與偵測率（Detection）來評估每條執行軌跡（trajectory）。在三個掛載框架、六個語言模型，以及 14 種模型與掛載框架配置（model and harness configurations）下，攻擊成功率介於 12.6% 至 80.9% 之間，而效用則維持在 75.0% 至 97.6% 之間。掛載框架配置階段在三個掛載框架中均最為脆弱，顯示攻擊可透過修改其他方面經授權的工作流程（otherwise authorized workflows）中的安全敏感參數（security-sensitive parameters）而成功。我們也發現，明確識別風險（risk recognition）並無法可靠地轉化為安全行動（safe action），因為某些配置在超過 90% 的執行中偵測到風險，同時仍保持相當高的攻擊成功率。這些結果凸顯了在部署模型（deployed model）與掛載框架配置的層級上，跨越多個掛載框架職責評估智能體安全性（agent safety）的必要性。

### 核心貢獻（3～5點）
- 提出 HarnessRisk，首個針對智能體掛載框架安全性的生命週期導向基準，系統性地涵蓋掛載框架配置、能力擴充、執行階段運作、狀態持久化、行動控制與事件復原六個運作階段。
- 設計 128 個沙箱化案例，每個案例將良性使用者目標與嵌入不受信任工作流程產物的對抗性指令配對，以評估真實運作情境下的安全性。
- 建立效用、攻擊成功率、持續性與偵測率四項評估指標，從多維度衡量每條執行軌跡的安全性與可用性權衡。
- 發現掛載框架配置階段在三個掛載框架中均最為脆弱，攻擊可透過修改其他方面經授權工作流程中的安全敏感參數而成功。
- 揭示風險識別與安全行動之間的落差：部分配置雖在超過 90% 的執行中偵測到風險，仍維持顯著的攻擊成功率。

### 適合對象
本論文適合 AI 安全與對齊研究者、智能體系統開發者與工程師、語言模型與智能體安全性基準設計者，以及關注大型語言模型代理部署風險的資安專業人員閱讀。對於希望從生命週期角度全面評估智能體掛載框架安全性，並理解風險識別如何轉化為實際安全行動的讀者尤其具有參考價值。

## 深度分析

#### 方法論解析

**HarnessRisk** 的核心方法論是將 **agent harness（智能體掛載框架）** 的安全性從傳統的「單一攻擊機制（attack mechanism）」視角，轉換為「**生命週期導向（lifecycle-oriented）**」的系統性評估框架。具體而言，作者將智能體掛載框架的運作責任劃分為六個 **operational phase（運作階段）**：

1. **Harness Configuration（掛載框架配置）**：涉及安全敏感參數（security-sensitive parameter）的設定，例如權限（permission）、策略（policy）、Webhook、自動審批規則等。
2. **Capability Extension（能力擴充）**：涉及外掛、擴充功能（extension）或工具的安裝與更新。
3. **Runtime Operation（執行階段運作）**：智能體在執行工作流程（workflow）時處理不受信任內容的階段。
4. **State Persistence（狀態持久化）**：涉及持久化記憶體（persistent memory）或長期狀態的寫入與保存。
5. **Action Control（行動控制）**：對重大影響行動（consequential action）的授權與執行決策。
6. **Incident Recovery（事件復原）**：在發現入侵後清除污染狀態、復原系統的階段。

這六個階段構成了一個完整的攻擊鏈（attack chain），如圖 1 所示，從惡意配置、惡意外掛、執行階段操控、記憶污染（memory poisoning）、未經授權的外部行動（unauthorized external action），到最後不完整的復原。

在威脅模型（threat model）方面，作者假設攻擊者能夠在**經授權的工作流程（authorized workflow）**中嵌入對抗性指令（adversarial instruction），但無法直接控制底層語言模型（underlying language model）或掛載框架的核心程式碼。這種設定貼近真實場景：使用者下載了看似良性的文件、外掛或復原指南，但其中夾帶了惡意指令，誘導智能體在執行良性使用者目標（benign user objective）的同時，完成攻擊者想要的操作。

**HarnessRisk** 共包含 **128 個沙箱化案例（sandboxed cases）**，每個案例都設計為三輪（three owner turns）的多輪（multi-turn）工作流程，並搭配案例專屬的檔案、工具、持久化狀態（persistent state）與受控的模擬服務（mock services）。所有執行都從全新初始化的環境開始，並關閉真實外部網路存取，以確保實驗的可控性與安全性。

評估指標分為四項：

- **Utility（效用）**：衡量智能體是否成功完成良性使用者目標。
- **Attack Success Rate（攻擊成功率）**：衡量對抗性指令是否達成預期的惡意效果。
- **Persistence（持續性）**：衡量攻擊造成的污染是否殘留在持久化狀態中。
- **Detection（偵測率）**：衡量智能體是否明確識別出風險（risk recognition）。

這四項指標的關鍵設計在於**將任務完成與安全性分離**：一個智能體即使 Utility 很高，仍可能在 Attack Success Rate 上表現很差。這正是本文反覆強調的論點——**高任務效用並不等同於安全執行**。

#### 實驗數據解讀

作者在 **14 個模型與掛載框架配置（model and harness configuration）** 上進行評估，涵蓋三個掛載框架：**OpenClaw**、**Hermes**、**Nanobot**，以及六個語言模型（language model）。實驗結果顯示：

- **Attack Success Rate（攻擊成功率）** 範圍為 **12.6% 至 80.9%**。
- **Utility（效用）** 範圍為 **75.0% 至 97.6%**。

這兩個範圍的並置極具意義：即使某些配置的 Utility 接近 97.6%，其 Attack Success Rate 仍可能高達 80.9%。這強烈說明，若僅以任務完成度評估智能體，將嚴重低估實際的安全風險。

從生命週期階段的角度觀察，**Harness Configuration（掛載框架配置）** 是所有三個掛載框架中最脆弱的階段。這意味著攻擊者無需繞過複雜的執行階段防禦，只需在受信任的工作流程中修改安全敏感參數（例如放寬權限、設定惡意 Webhook、啟用自動審批），就能讓後續攻擊順利進行。這一發現對實務具有重要啟示：**配置階段的安全把關往往比執行階段的行為監控更為關鍵**。

另一個值得注意的發現是 **Detection（偵測率）** 與 **Attack Success Rate（攻擊成功率）** 之間的脫節。部分配置在超過 90% 的執行中都能明確識別風險，但攻擊成功率仍然維持在相當高的水準。這顯示：

1. 語言模型具備一定的風險識別（risk recognition）能力；
2. 但風險識別並未轉化為安全行動，可能因為掛載框架缺乏有效的阻斷機制、模型過於順從使用者指令、或安全策略與執行層之間存在落差。

這種「知道有風險卻仍執行」的現象，凸顯了單純提升模型對齊（alignment）或安全提示（safety prompting）並不足夠，必須在掛載框架層面建立「識別即阻斷」的強制機制。

此外，作者指出**模型安全性排名會因掛載框架不同而顯著變化**。這意味著脫離掛載框架談論「哪個語言模型比較安全」是片面的；安全性是**部署模型（deployed model）**與**掛載框架（agent harness）**的聯合屬性（joint property）。同一個模型在 OpenClaw 上可能表現安全，在 Nanobot 上卻因權限設計差異而變得脆弱。

#### 與現有研究的比較

本文透過表 1 清楚定位了 **HarnessRisk** 與現有基準的差異。現有研究如 **InjecAgent**、**AgentSecurityBench**、**Agent-SafetyBench**、**ClawSafety**、**PASB**、**LivePI**、**ClawTrojan**、**HarnessAudit-Bench**、**CIK-Bench** 等，大多聚焦於 **Runtime Operation（執行階段運作）** 與 **Action Control（行動控制）**，對於 **Harness Configuration（掛載框架配置）**、**Capability Extension（能力擴充）**、**State Persistence（狀態持久化）** 與 **Incident Recovery（事件復原）** 的覆蓋較不一致。

相較於這些基準，**HarnessRisk** 的主要貢獻與改進包括：

1. **生命週期全覆蓋**：首次以六個運作階段為架構，系統性地評估掛載框架在不同責任點上的安全表現。
2. **配置階段的重要性**：過去研究較少將「配置被竄改」視為主要攻擊向量，而 HarnessRisk 明確指出這是最脆弱的環節。
3. **效用與安全的分離評估**：多數基準僅關注攻擊是否成功，HarnessRisk 同時測量 Utility，揭示高任務完成度可能掩蓋不安全執行。
4. **偵測與行動的脫鉤分析**：透過 Detection 指標，區分「識別風險」與「阻止風險」，這是過去較少細緻處理的面向。
5. **多掛載框架比較**：在 OpenClaw、Hermes、Nanobot 三個不同設計的掛載框架上進行評估，強調安全性是模型與框架的聯合屬性。

然而，本文也存在若干限制。首先，128 個案例雖已涵蓋六個階段，但相較於真實世界中海量的掛載框架配置組合，仍屬有限。其次，實驗採用沙箱化環境與模擬服務，雖提升可控性，但可能簡化了真實攻擊中的某些動態因素，例如真實網路延遲、人機互動、或更複雜的社會工程學手法。第三，本文主要評估「對抗性指令嵌入工作流程產物」這類攻擊，對於其他攻擊向量（如供應鏈攻擊、模型權重本身被污染、或掛載框架程式碼漏洞）的覆蓋較少。

#### 可重現性評估

從可重現性（reproducibility）的角度來看，**HarnessRisk** 在方法設計上具備良好的可控性基礎：

- 每個案例都在沙箱化環境（sandboxed environment）中執行。
- 所有執行從全新初始化的環境開始，避免狀態殘留影響結果。
- 真實外部網路存取被關閉，改以受控的模擬服務（mock services）替代，降低外部變因。
- 評估指標（Utility、Attack Success Rate、Persistence、Detection）定義明確，便於量化比較。

然而，由於本文標示為 **Preprint. Under review.**，目前尚無法確認原始碼、資料集、模型權重與掛載框架配置是否已公開釋出。對於一個強調「部署模型與掛載框架配置」聯合影響的基準而言，若未來能公開以下項目，將大幅提升可重現性與社群採用度：

1. **128 個沙箱化案例的完整資料集與環境定義**。
2. **OpenClaw、Hermes、Nanobot 的掛載框架版本與配置檔案**。
3. **六個語言模型的確切版本、提示模板（prompt template）與呼叫參數**。
4. **評估腳本與自動化評分器（automated scorer）的實作**。
5. **執行軌跡（trajectory）的日誌與中間狀態快照**。

在這些資源公開之前，其他研究者難以完全複製實驗結果，也難以在此基礎上進行公平的後續比較。這是現階段 HarnessRisk 作為一個新興基準在可重現性上的主要不確定性。

#### 未來研究方向

基於 **HarnessRisk** 的發現，未來研究可朝以下方向延伸：

1. **配置階段的強化防禦**：由於 Harness Configuration 是最脆弱的階段，未來可發展配置檔案的靜態分析、最小權限原則（principle of least privilege）自動檢查、以及配置變更的不可否認性（non-repudiation）機制。

2. **能力擴充的供應鏈安全**：針對 Capability Extension 階段，可研究外掛簽章驗證、沙箱化外掛執行、以及基於行為的外掛風險評分。

3. **持久化狀態的完整性保護**：State Persistence 階段的記憶污染（memory poisoning）需要新的防禦機制，例如記憶體內容的來源追蹤、版本控制、以及攻擊後的完整性驗證。

4. **行動控制的強制授權機制**：針對 Action Control 階段，可發展多層次授權（multi-level authorization）、人類在迴路（human-in-the-loop）確認、以及基於風險評分的動態審批。

5. **事件復原的完整性驗證**：Incident Recovery 階段目前較少被研究，未來可探討如何確保復原指南本身未被污染、復原後狀態是否真正乾淨、以及如何驗證復原軌跡。

6. **從風險識別到安全行動的橋接**：本文發現風險識別不等於安全行動，未來可研究如何將模型的風險識別輸出轉化為掛載框架層面的強制阻斷，例如安全策略中間語言（policy intermediate language）或模型與框架間的結構化安全訊號。

7. **跨掛載框架的標準化安全評估**：建立類似 HarnessRisk 的開放 leaderboard，讓不同研究團隊在相同協議下比較模型與掛載框架組合的安全性。

8. **自動化紅隊測試（automated red teaming）**：將 HarnessRisk 的六階段框架擴展為自動化攻擊生成與防禦測試平台，持續發現新型攻擊鏈。

9. **因果性評估與歸因分析**：未來可進一步分析攻擊成功是由於模型行為、掛載框架設計、還是配置錯誤所導致，以提供更具針對性的改進建議。

10. **真實世界部署研究**：在受控的企業環境中驗證 HarnessRisk 的發現，特別是在涉及真實 API、資料庫與人機協作流程的場景中。

## 論文問答

**Q1：什麼是「智能體掛載框架安全性」，為什麼它在當前大型語言模型部署中特別重要？**

A：智能體掛載框架（agent harness）是介於大型語言模型與外部環境之間的中介層，負責暴露工具、管理狀態、載入擴充功能、執行權限控管以及實際執行模型產生的行動。因此，即使底層語言模型本身具備一定的安全對齊能力，只要掛載框架在配置、權限或狀態管理上出現漏洞，整體系統仍然可能產生資料外洩、未經授權操作或持久化後門等風險。隨著大型語言模型越來越頻繁地以智能體形式與檔案、網路服務和執行環境互動，評估與強化掛載框架安全性已成為確保部署安全的關鍵環節。

**Q2：現有的智能體安全基準為何難以充分評估掛載框架的安全風險？**

A：現有基準大多聚焦於單一攻擊機制（例如提示注入、不安全工具使用或記憶污染）或僅涵蓋少數執行設定，缺乏對智能體完整運作生命週期的系統性覆蓋。從本文表1可以看出，多數相關基準僅強調執行階段運作（Runtime Operation）與行動控制（Action Control），而對掛載框架配置（Harness Configuration）、能力擴充（Capability Extension）、狀態持久化（State Persistence）與事件復原（Incident Recovery）等階段的覆蓋並不一致。由於安全決策實際上分散在這些不同階段，僅評估局部攻擊難以比較不同掛載框架職責下安全失效的產生方式與嚴重程度。

**Q3：為什麼需要以「生命週期導向」的視角來組織掛載框架安全研究？**

A：掛載框架的風險並非只發生在模型推理的當下，而是在配置設定、擴充安裝、執行運作、狀態儲存、重大行動授權以及入侵後修復等多個時間點都可能出現安全決策。將安全責任劃分為六個運作階段，能夠提供一個共同的比較基礎，讓研究者與開發者清楚看到風險從何而來、如何在階段之間傳遞，以及應該在何處介入防禦。這種生命週期導向的觀點也強調：安全性是部署模型與掛載框架配置共同決定的聯合屬性，而非僅由語言模型本身決定。

**Q4：HarnessRisk 的核心方法與整體設計是什麼？**

A：HarnessRisk 是一個包含 128 個沙箱化案例的基準，每個案例都將一個良性使用者目標與嵌入在不受信任工作流程產物中的對抗性指令配對。每個案例會讓智能體執行三輪（three owner turns）的完整工作流程，並使用案例專屬的檔案、工具、持久化狀態與受控的模擬服務；所有執行都從全新初始化的環境開始，且真實外部網路連線會被關閉。評估指標包括效用（Utility）、攻擊成功率（Attack Success Rate）、持續性（Persistence）與偵測率（Detection），以區分任務完成度、不安全行為、持久化危害以及模型是否明確識別風險。

**Q5：相較於既有基準，HarnessRisk 的主要創新之處在哪裡？**

A：HarnessRisk 最大的創新在於首次以統一協議同時覆蓋掛載框架的六個運作階段，並將「部署的模型與掛載框架配置」視為一個整體來評估。它不僅測試模型能否完成任務，更透過不受信任的工作流程產物檢驗攻擊是否能在高任務效用的掩護下成功，並追蹤風險是否會轉化為持久化狀態或後續未經授權的行動。此外，HarnessRisk 同時測量偵測率與攻擊成功率，能夠揭示「模型雖然識別風險，卻仍執行危險行動」這類過去較少被量化的安全缺口。

**Q6：HarnessRisk 在案例設計與評估指標上做了哪些關鍵選擇？**

A：研究團隊選擇以「良性目標 + 對抗性指令」的配對方式設計案例，因為這能模擬真實情境中攻擊者將惡意內容隱藏在看似正常的工作流程產物中的情況。採用三輪對話與受控模擬服務，可以在不暴露真實外部系統風險的前提下，觀察攻擊如何在多步驟互動中逐步擴散。四項評估指標的設計則是為了將「任務是否完成」與「執行是否安全」解耦：Utility 衡量正常任務表現，Attack Success Rate 衡量攻擊是否得逞，Persistence 衡量危害是否殘留，Detection 則衡量模型是否明確指出風險。

**Q7：HarnessRisk 與現有相關基準相比，覆蓋範圍有何差異？**

A：與 InjecAgent、AgentSecurityBench、Agent-SafetyBench、ClawSafety、PASB、LivePI、ClawTrojan、HarnessAudit-Bench 與 CIK-Bench 等基準相比，HarnessRisk 是唯一同時涵蓋多輪互動（Multi-Turn）、掛載框架配置、能力擴充、執行階段運作、狀態持久化、行動控制與事件復原七個面向的基準。其他基準大多偏重執行階段與行動控制，對於配置階段的安全敏感參數篡改、擴充功能濫用以及事件後復原是否完整等問題缺乏系統性測試。這樣的差異使得 HarnessRisk 能夠更全面地比較不同掛載框架在整個生命週期中的安全表現。

**Q8：HarnessRisk 實驗中的關鍵結果有哪些？**

A：在 3 個掛載框架、6 個語言模型與 14 種模型暨掛載框架配置下，攻擊成功率介於 12.6% 到 80.9% 之間，而效用則維持在 75.0% 到 97.6% 之間，顯示高任務完成度與高攻擊成功率可以同時存在。最引人注目的發現是「掛載框架配置」在所有三個掛載框架中都是最脆弱的階段，因為攻擊者可以透過操縱經授權工作流程中的安全敏感參數來達成攻擊。此外，部分配置雖然在超過 90% 的執行中偵測到風險，卻仍保留相當高的攻擊成功率，證明單靠風險識別並不足以保證安全行動。

**Q9：不同模型與掛載框架配置的比較揭示了什麼重要現象？**

A：實驗結果顯示，模型的安全排名會因掛載框架不同而產生顯著變化，這說明脫離實際部署配置來比較語言模型安全性會得到不穩定的結論。同時，某些配置雖然具備高偵測率，卻仍無法有效阻止攻擊執行，反映出「知道有風險」與「做出安全決策」之間存在明顯落差。這些發現強調，未來的安全評估必須在模型與掛載框架的聯合配置層次進行，並且不能僅以偵測率或效用作為安全性的代理指標。

**Q10：HarnessRisk 的攻擊情境在實務上可能如何呈現？**

A：本文圖1展示了一個電商訂單退款處理的範例：攻擊者可在掛載框架配置階段植入惡意文件，誘使系統放寬政策與權限；接著透過偽裝的外掛程式或惡意規則進行能力擴充與執行階段操控；再將惡意內容寫入長期記憶體造成狀態持久化污染；最終導致未經授權的退款行動，並在事件復原階段留下未清除的後門。這類攻擊鏈說明，單一階段的防禦不足以保護整體系統，因為攻擊者可以透過多個掛載框架職責的串接來達成最終目的。對於實際產品而言，這意味著開發者必須檢視從配置到復原的每一個環節，而不只是關注模型輸出是否「看起來合理」。

**Q11：企業在部署智能體產品時，應該從 HarnessRisk 得到哪些具體啟示？**

A：首先，產品團隊不應僅依賴語言模型自身的風險識別能力，而必須在掛載框架層面強制執行安全控制，例如驗證配置來源、限制擴充功能的特權、對持久化狀態進行消毒，以及對重大影響行動要求明確授權。其次，由於高任務效用可能掩蓋高攻擊成功率，產品評估應同時測量任務完成度與安全指標，避免只看整體表現就認定系統安全。最後，事件復原機制必須被視為安全生命週期的一部分，確保在清除威脅後不會殘留惡意配置、污染記憶體或未被撤銷的權限。

**Q12：HarnessRisk 對學術界與產業界可能帶來什麼影響？**

A：HarnessRisk 提供了一個標準化的比較框架，讓研究者能夠在相同的六個運作階段上評估與比較不同掛載框架與語言模型配置的安全性。它有助於將智能體安全研究的焦點從單純的模型對齊，擴展到模型與掛載框架的共同設計，推動更安全、可審計的智能體系統發展。對產業界而言，這個基準可以作為產品上市前與持續更新時的安全測試工具，協助識別配置、擴充與復原等過去較少被檢視的弱點。

**Q13：HarnessRisk 有哪些已知的限制？**

A：HarnessRisk 目前採用沙箱化環境與模擬服務，雖然能確保實驗安全與可重現，但可能無法完全捕捉真實世界中複雜的網路拓撲、人機互動與動態威脅環境。128 個案例雖然涵蓋六個階段，但仍無法窮盡所有可能的攻擊變體與領域情境，未來需要持續擴充。此外，實驗結果主要基於當前特定的掛載框架實作與語言模型，對於未來出現的新型掛載框架或模型架構，其適用性與泛化能力仍需進一步驗證。

**Q14：在 HarnessRisk 的實驗中，有哪些典型的失效案例值得特別注意？**

A：一個典型失效案例是掛載框架配置階段的攻擊成功：即使工作流程本身經過授權，攻擊者仍可藉由修改其中的安全敏感參數來削弱政策或開啟危險權限。另一個值得注意的現象是，部分語言模型會在執行軌跡中明確表達「這可能有風險」，但由於缺乏掛載框架層級的強制阻擋機制，最終仍會執行對抗性指令所要求的危險行動。此外，在事件復原階段，系統有時只修復表面症狀，卻未能清除被污染的持久化狀態或惡意擴充，導致攻擊具備長期持續性。

**Q15：未來可以如何延伸或改進 HarnessRisk 這類生命週期導向的安全基準？**

A：未來可以擴充案例數量與領域，涵蓋更多真實服務、多智能體協作以及人類在迴路（human-in-the-loop）的互動情境，以提升基準對現實部署的近似度。另一方面，可以發展自動化的掛載框架強化工具，根據各階段的漏洞模式自動生成防禦策略或配置檢查規則。此外，將 HarnessRisk 整合到持續整合／持續部署（CI/CD）流程中，並設計能更細緻衡量因果責任與修復完整性的新指標，將有助於推動智能體安全從靜態評估走向動態、可持續改進的實務框架。

## 實務應用指南

### 適用場景

1. **企業內部 AI 助理（檔案、郵件、行事曆、程式碼工具）**  
   當員工透過 agent harness 讓語言模型讀取文件、寄送郵件或修改程式碼時，不受信任的工作流程產物（例如夾帶對抗性指令的試算表、設定檔或外掛說明）可能篡改安全敏感參數。HarnessRisk 可用來評估這類「經授權工作流程中的配置攻擊」。

2. **程式開發與 DevOps 智能體**  
   CI/CD 智能體會自動安裝擴充功能、讀取建置腳本、寫入持久化狀態並觸發部署。利用 HarnessRisk 的六個運作階段，可檢視惡意套件、記憶污染或未經授權外部行動如何在開發流程中擴散。

3. **客戶服務與 CRM 智能體**  
   客服智能體常使用長期記憶儲存客戶偏好與對話摘要。攻擊者可透過對抗性內容污染持久化狀態，使後續對話洩漏資料或執行錯誤退款。HarnessRisk 的 State Persistence 與 Action Control 階段特別適用。

4. **金融／電商交易處理智能體**  
   這類智能體涉及高風險行動（轉帳、退款、庫存調整）。透過 HarnessRisk 可測試模型是否能在完成良性使用者目標（高 Utility）的同時，阻擋未經授權的外部行動與持續性入侵。

5. **醫療／排程調度智能體**  
   當智能體依賴外部行事曆、病歷系統或通訊服務時，需確保事件復原機制能清除遭入侵狀態。HarnessRisk 的 Incident Recovery 階段可驗證復原指南是否被偽造，以及清除後是否仍有殘留風險。

### 實作前置條件

**資料準備**
- 產品領域的良性使用者目標與對應工作流程產物（文件、設定檔、擴充功能描述、規則檔等）。
- 參考 HarnessRisk 的 128 個沙箱化案例，改寫或擴充成貼近自身業務的測試案例。
- 定義每個案例的黃金標準：何謂「攻擊成功」、「持續性危害」、「偵測到風險」與「任務完成」。

**運算資源**
- 可執行多輪對話的沙箱環境（容器或虛擬機），並關閉真實外部網路。
- 受控的 mock 外部服務（郵件、行事曆、資料庫、Webhook、檔案系統）。
- 目標語言模型的推理端點（API 或本地 GPU），以及待測的 agent harness（如 OpenClaw、Hermes、Nanobot 或自研框架）。

**技能需求**
- 熟悉 agent harness 的運作：工具註冊、權限管理、記憶體機制、擴充功能安裝與行動授權。
- 具備提示注入與智能體安全基礎知識，能設計對抗性指令。
- 能使用 Python 撰寫評估腳本、解析執行軌跡，並計算 Utility、Attack Success Rate、Persistence、Detection 四項指標。
- 具備 CI/CD 與 MLOps 經驗，以便將評估流程自動化。

---

### 實作步驟建議

1. **對照六個運作階段盤點掛載框架責任**  
   將產品的 agent harness 對應到 Harness Configuration、Capability Extension、Runtime Operation、State Persistence、Action Control、Incident Recovery，找出每個階段的安全決策點。

2. **建立隔離沙箱與 mock 服務**  
   確保每次執行都從全新初始化的環境開始，真實外部網路停用，所有外部動作都導向可控 mock。

3. **設計領域專屬測試案例**  
   以「良性目標 + 嵌入對抗性指令的不受信任產物」為核心，設計三輪以上 owner turn 的工作流程。每個案例應橫跨至少一個運作階段。

4. **配置多組模型與掛載框架組合**  
   固定模型但變更 harness 設定（例如自動核准 vs. 人工確認），或固定 harness 但更換模型，以比較安全性差異。

5. **執行並記錄執行軌跡**  
   收集每次執行的工具呼叫、記憶體寫入、外部行動請求與模型回應，作為後續評估依據。

6. **計算四項指標並做階段拆解**  
   分別計算整體與各階段的 Utility、Attack Success Rate、Persistence、Detection。特別注意高 Utility 是否伴隨高 Attack Success Rate。

7. **優先修復最脆弱的階段**  
   根據論文發現，Harness Configuration 通常是攻擊成功率最高的階段。優先檢視安全敏感參數是否可被工作流程產物覆寫。

8. **建立持續回歸與紅隊演練**  
   將 HarnessRisk 案例納入每次模型或 harness 更新後的自動化測試，並定期擴充新的攻擊變體。

9. **文件化與治理**  
   記錄每個配置的風險熱區、偵測率與緩解措施，形成模型卡與安全評估報告，供產品與法遵團隊參考。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解建議 |
|---|---|---|
| **高 Utility 掩蓋高攻擊成功率** | 智能體看似完成任務，實際上已執行未經授權行動。 | 同時報告 Utility 與 Attack Success Rate，避免只看任務完成度。 |
| **風險識別不等於安全行動** | 模型可能口頭警告風險，卻仍執行危險操作。 | 將 Detection 與 Attack Success Rate 交叉分析，並強制 harness 層級攔截。 |
| **配置攻擊繞過執行階段防護** | 修改安全敏感參數後，後續行動在授權流程內被視為合法。 | 對配置變更實施獨立審查與不可被使用者產物覆寫的保護機制。 |
| **持久化狀態污染難以清除** | 遭入侵的記憶體會在後續對話中持續發揮影響。 | 定期審計長期記憶、建立版本化備份與事件復原流程。 |
| **沙箱與真實環境落差** | Mock 服務可能無法完全模擬真實 API 的邊界行為。 | 在 staging 環境進行二次驗證，並監控真實部署後的異常行動。 |
| **案例維護成本** | 模型與 harness 更新後，舊案例可能失效或被輕易繞過。 | 將案例視為動態資產，持續更新並納入版本控制。 |
| **隱私與資料外洩** | 測試案例若使用真實業務資料，可能洩漏敏感資訊。 | 全部使用去識別化或合成資料，並限制沙箱對外連線。 |

### 與其他技術的整合建議

- **CI/CD 與 MLOps 管線**  
  將 HarnessRisk 評估腳本嵌入模型或 harness 更新後的自動化閘道，設定 Attack Success Rate 與 Utility 的門檻，未通過即阻擋部署。

- **紅隊與對抗性測試平台**  
  把 HarnessRisk 案例作為紅隊演練的種子題庫，結合自動化變異工具持續產生新的對抗性工作流程產物。

- **配置即程式碼（Config-as-Code）審查**  
  針對 Harness Configuration 階段，將掛載框架配置納入版本控制與同行審查，禁止未經授權的工作流程產物覆寫安全參數。

- **Guardrails 與政策引擎**  
  在 harness 層整合政策引擎，對 Runtime Operation 與 Action Control 階段的工具呼叫、外部行動與記憶體寫入進行即時檢查。

- **SIEM 與事件回應系統**  
  將 Persistence 與 Detection 指標輸出到安全資訊與事件管理系統，協助資安團隊追蹤智能體相關事件與復原狀態。

- **模型卡與治理儀表板**  
  以 HarnessRisk 結果建立模型卡，視覺化各運作階段的風險熱區，供產品、法遵與高階管理團隊定期檢視。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從摘要與圖 1 的攻擊鏈開始，理解「智能體掛載框架安全性」不只是語言模型本身的問題，而是配置、擴充、執行、記憶、行動與復原六個階段的綜合結果。接著閱讀實驗結果中「高 Utility 與高攻擊成功率並存」的段落，建立「任務完成不代表安全」的直覺。

**AI 工程師**  
請聚焦第二節的問題形式化、評估指標設計與沙箱實作細節。重點學習如何將 128 個案例轉換為自家產品的自動化測試，並注意 harness 層的攔截點應該設在哪裡，才能避免僅依賴模型的風險識別能力。
