## ⚡ TL;DR

自動駕駛測試需將法規轉為可執行 DSL 腳本，現有方法在編譯成功率與泛化性間難以兼顧。
提出 Chat2Scenic，以迭代 RAG 與聊天介面互動精煉，生成符合法規語法的 DSL 腳本。
實驗顯示編譯成功率達 76.42%、框架準確率 58.17%，顯著優於現有方法，並開源程式碼與基準。

## 摘要翻譯

驗證自動駕駛系統（Autonomous Driving System, ADS）需要多樣化且符合法規的測試情境（Test Scenarios）。在模擬測試（Simulation-based Testing）中，情境被定義為可執行腳本（Executable Scripts）。然而，從法規描述（Regulatory Descriptions）自動生成此類腳本仍是一項開放性挑戰（Open Challenge），且現有方法面臨根本性的權衡取捨。檢索組裝（Retrieval Assemble）方法可達到合理的編譯成功率（Compilation Success Rate, CSR），但缺乏可擴展性；而檢索式完整腳本生成（Retrieval Full Script Generation）則存在編譯成功率偏低的問題。我們提出 Chat2Scenic，首個用於生成領域特定語言（Domain Specific Language, DSL）情境腳本的迭代式檢索增強生成（Retrieval-Augmented Generation, RAG）框架。具體而言，Chat2Scenic 提供聊天機器人介面（Chatbot Interface），支援互動式情境精煉（Interactive Scenario Refinement），並整合檢索增強生成（RAG），使情境生成奠基於法規知識與 DSL 語法（DSL Syntax）。此外，我們提出一個開放式情境生成基準測試（Open Benchmark），包含 123 個來自多項法規（包括美國國家公路交通安全管理局（NHTSA）與聯合國車輛法規（United Nations Vehicle Regulations））及其他來源的情境。透過最先進的（State-of-the-Art, SOTA）大型語言模型（Large Language Models, LLMs）進行廣泛評估，結果顯示 Chat2Scenic 達到 76.42% 的編譯成功率（CSR）與 58.17% 的框架準確率（Framework Accuracy, FA），優於現有方法（檢索組裝（Retrieval Assemble）為 30.08% CSR、11.03% FA；檢索式完整腳本生成（Retrieval Full Script Generation）為 16.26% CSR、10.86% FA）。為促進未來研究，我們將程式碼以開源（Open Source）形式釋出於 https://github.com/TUM-AVS/chat2scenic。

### 核心貢獻（3～5點）
- 提出首個迭代式檢索增強生成（Iterative RAG-Based）框架 Chat2Scenic，用於自動駕駛領域的 DSL 情境腳本生成，並透過聊天機器人介面支援互動式情境精煉。
- 整合檢索增強生成（RAG）技術，使情境生成同時奠基於法規知識與 DSL 語法，提升生成腳本的合規性與可執行性。
- 建立一個開放式情境生成基準測試（Open Benchmark），涵蓋 123 個來自 NHTSA、聯合國車輛法規及其他來源的情境，供後續研究評估使用。
- 在最先進的大型語言模型（SOTA LLMs）上進行廣泛評估，顯示 Chat2Scenic 在編譯成功率（CSR）與框架準確率（FA）上顯著優於現有的檢索組裝與檢索式完整腳本生成方法。
- 將原始碼以開源形式釋出，促進自動駕駛情境生成領域的後續研究與應用。

### 適合對象
本論文最適合從事自動駕駛系統驗證、模擬測試、法規符合性測試，以及大型語言模型與檢索增強生成技術應用的研究人員與工程師閱讀。對於關注如何將法規描述自動轉換為可執行測試腳本、或希望了解互動式生成框架在自動駕駛情境生成中應用的讀者，亦具有高度參考價值。

## 深度分析

#### 方法論解析

Chat2Scenic 的核心任務是將自然語言形式的法規描述（regulatory descriptions）轉換為可在模擬器中執行的 Domain Specific Language（DSL，領域特定語言）腳本（executable scripts）。從摘要與引言可歸納出以下方法論特徵：

1. **迭代式 DSL 區塊生成（iterative DSL-block generation）**  
   不同於 Retrieval Assemble（檢索組裝）方法直接拼貼資料庫中既有的 DSL components（DSL 元件），也不同於 Retrieval full script generation（檢索式完整腳本生成）一次產出整份 DSL programs（DSL 程式），Chat2Scenic 採用「Iterative Component-wise（迭代式元件級）」粒度。系統會將複雜的駕駛情境（driving situations）拆解為多個 DSL blocks（DSL 區塊），逐塊生成、編譯與修正，以降低長距離語法相依性所導致的編譯失敗。

2. **Retrieval-Augmented Generation（RAG，檢索增強生成）知識接地**  
   框架透過 RAG 同時檢索兩類外部知識：  
   - **法規知識**：例如 NHTSA（美國國家公路交通安全管理局）與 United Nations Vehicle Regulations（聯合國車輛法規）等測試規範，確保生成情境符合 regulation-compliant（符合法規的）要求。  
   - **DSL 語法與範例**：檢索 DSL syntax（DSL 語法）和正確程式片段，減少 LLMs（Large Language Models，大型語言模型）在語法細節上的幻覺。  
   根據 Table I，Chat2Scenic 同時整合了 Contextual Prompting（上下文提示）、Chain-of-Thought（CoT，思維鏈）、In-Context Learning（ICL，情境學習）以及 RAG-ICL（Retrieval-Augmented In-Context Learning，檢索增強式情境學習）等提示技術，形成多層次的知識注入機制。

3. **聊天機器人介面（chatbot interface）與互動式情境精煉（interactive scenario refinement）**  
   Chat2Scenic 提供多輪對話式 UI，允許使用者逐步澄清、修改或擴充測試需求。這種 human-in-the-loop 設計不僅提升生成結果與使用者意圖的一致性，也讓框架能在多輪互動中持續修正語意偏差。

4. **編譯器回饋驅動的迭代修正**  
   生成的 DSL blocks 會經過編譯器驗證，錯誤訊息會被回饋至 LLM 進行下一輪修正。這種「生成—編譯—修復」的迴路是提升 Compilation Success Rate（CSR，編譯成功率）的關鍵，也是 Chat2Scenic 相較於一次性 full-script generation 的主要優勢。

5. **與情境資料庫的互動**  
   引言指出 Chat2Scenic 產生的 DSL blocks 會「interact with the database」，推測其內部維護一個情境元件或參數資料庫，生成的區塊可動態查詢、組合與實例化，從而兼顧泛化能力（generalizability）與編譯正確性。

整體而言，Chat2Scenic 的方法論可視為在「檢索組裝」與「完整生成」兩個極端之間取得平衡：透過 RAG 提供語法與法規先驗，透過迭代區塊生成降低複雜度，再透過編譯回饋與人機互動確保最終腳本品質。

#### 實驗數據解讀

論文提出的 benchmark 包含 123 個來自 NHTSA、United Nations Vehicle Regulations 及其他來源的 test scenarios（測試情境），並以兩項指標評估：

- **Compilation Success Rate（CSR，編譯成功率）**：衡量生成腳本能否無誤通過 DSL 編譯，反映語法與結構正確性。  
- **Framework Accuracy（FA，框架準確率）**：衡量生成腳本是否正確對應原始法規描述，反映語意與規格符合度。

主要結果如下：

| 方法 | CSR | FA |
|---|---|---|
| Retrieval Assemble（檢索組裝） | 30.08% | 11.03% |
| Retrieval full script generation（檢索式完整腳本生成） | 16.26% | 10.86% |
| **Chat2Scenic** | **76.42%** | **58.17%** |

**數據解讀：**

1. **Full-script generation 的困境**  
   即使引入 RAG，一次性生成完整 DSL programs 的 CSR 僅 16.26%，FA 僅 10.86%。這顯示當腳本長度與結構複雜度增加時，LLMs 難以維持長距離語法一致性，且容易產生彼此不相容的程式片段。

2. **Retrieval Assemble 的瓶頸**  
   該方法 CSR 達 30.08%，明顯優於 full-script generation，顯示利用既有 DSL components 可提升語法正確性。然而其 FA 僅 11.03%，幾乎與 full-script generation 相當，說明單純拼貼既有程式碼難以應對新穎或複雜的法規描述，缺乏 generalizability（泛化能力）與 scenario diversity（情境多樣性）。

3. **Chat2Scenic 的顯著提升**  
   CSR 從 30.08% 提升至 76.42%，FA 從約 11% 提升至 58.17%。這證明「迭代式區塊生成 + RAG + 編譯回饋」的組合同時改善了語法正確性與語意準確性。FA 雖仍低於 CSR，但相較基線已有近 5 倍提升。

4. **CSR 與 FA 的差距**  
   Chat2Scenic 的 CSR（76.42%）與 FA（58.17%）相差約 18 個百分點，代表有近兩成腳本雖可編譯，卻未正確實現法規要求。這突顯「語法正確」不等於「語意正確」，未來仍需更強大的語意驗證機制。

5. **基準測試的代表性**  
   123 個情境涵蓋多國法規，對於初步驗證已具規模，但相較於真實世界駕駛情境的無窮組合，仍屬中等規模。結果顯示在該 benchmark 上 SOTA LLMs 已能達到實用水準，但離完全自動化仍有距離。

#### 與現有研究的比較

從 Table I 與文獻回顧可將相關研究分為三大類：

1. **Classical Scenario Generation（經典情境生成）**  
   包含 data-driven（資料驅動）、adversarial（對抗性）與 knowledge-based（知識導向）方法。這類方法不依賴 LLMs，難以直接從自然語言法規描述生成可執行 DSL scripts。

2. **LLM-based Retrieval-Assemble（基於 LLM 的檢索組裝）**  
   代表工作包括 TARGET、ChatScene、Text2Scenario。它們以 component-wise（元件級）方式組合既有 DSL snippets，能達到尚可的 CSR，但缺乏 iterative refinement（迭代精煉）與 RAG 法規接地，因此 generalizability 受限。

3. **LLM-based Direct/Full Generation（基於 LLM 的直接生成）**  
   代表工作包括 LEADE、LeGEND、ScenicNL、Talk2Traffic、Rubavicius、NL2Scenic。這類方法靈活性較高，但多採用 full-program 或一次性生成，導致 CSR 偏低，常見問題包括程式片段個別合法但彼此不相容。

**Chat2Scenic 的相對優勢：**

- **唯一同時具備 UI、Regulatory Test Specifications（法規測試規格）支援、Documentation RAG、Contextual Prompting、CoT、ICL、RAG-ICL 與 Iterative Component-wise 生成的方法**（Table I 中 Ours 欄位全為 ✓）。
- 在 CSR 與 FA 上均大幅領先現有方法，顯示其成功結合了檢索組裝的語法可靠性與直接生成的靈活性。
- 聊天機器人介面提升了可用性，使非程式專家也能參與 test scenarios 設計。

**限制與待強化之處：**

- **FA 仍有提升空間**：58.17% 表示近四成情境在語意層面仍有偏差，可能源於法規描述的歧義、檢索品質或 LLM 推理限制。
- **對 LLM 與檢索器的依賴**：若檢索到的法規或語法範例不準確，錯誤會被放大至生成結果。
- **物理真實性未充分驗證**：CSR 僅保證腳本可編譯，並不保證模擬中的車輛行為在物理或交通邏輯上合理。
- **DSL 範圍有限**：從相關工作推測目標 DSL 可能為 Scenic，尚未見到對其他模擬器（如 SUMO、CARLA Python API）的泛化驗證。
- **Benchmark 規模**：123 個情境雖具代表性，但對於涵蓋全球所有車輛法規仍顯不足。

#### 可重現性評估

可重現性（reproducibility）是學術研究轉化為實務應用的關鍵，Chat2Scenic 在以下方面表現良好：

1. **開源程式碼與基準測試**  
   論文明確於 https://github.com/TUM-AVS/chat2scenic 釋出原始碼，並提出包含 123 個情境的 open benchmark（開放基準測試）。這讓其他研究者能直接比較方法、驗證指標並進行後續擴充。

2. **資料集來源**  
   情境來自公開法規文件（NHTSA、United Nations Vehicle Regulations 等），原則上可公開取得，但部分法規文本的授權與格式可能影響資料集重新發布與預處理流程。

3. **模型與計算資源**  
   論文使用 SOTA LLMs 進行評估，這些模型多為商業 API（如 GPT-4 系列），其模型權重（model weights）通常不公開。因此：  
   - 實驗結果會受到 API 版本、temperature、prompt 設計與隨機取樣影響。  
   - 不同時間點呼叫相同 API 可能因模型更新而產生差異，造成「軟性不可重現」。  
   - 若論文同時測試開源權重模型（如 Llama、Qwen），則權重可下載，重現性較高，但摘要中未明確說明。

4. **依賴環境**  
   由於目標是生成 DSL scripts，重現時需確認：  
   - DSL 編譯器版本（推測為 Scenic 編譯器）。  
   - 模擬器版本（如 CARLA）。  
   - Python、LangChain 或其他 RAG 框架版本。  
   若 repository 中提供 `requirements.txt`、Docker image 或詳細安裝文件，可大幅提升重現性。

5. **提示詞與檢索語料**  
   RAG 系統的效能高度依賴提示模板（prompt templates）與檢索語料庫。若論文一併釋出這些資源，將有助於精確重現其 CSR 與 FA。

**綜合評估**：Chat2Scenic 在「開源程式碼 + 開放基準」層面具備良好可重現性基礎；然而由於依賴商業 LLM API 與可能未完全固定的隨機性，絕對數值的完全重現仍具挑戰。建議未來版本加入 deterministic seeding、API 版本紀錄與開源替代模型實驗，以強化可重現性。

#### 未來研究方向

基於 Chat2Scenic 的貢獻與限制，可延伸以下研究方向：

1. **語意層驗證強化**  
   除了編譯器回饋，可引入 formal verification（形式化驗證）或符號執行，檢查生成腳本是否真正滿足法規中的時序、空間與邏輯約束，以縮小 CSR 與 FA 之間的差距。

2. **封閉迴路 ADS 評估**  
   將生成腳本接入自動駕駛系統（Autonomous Driving System, ADS）進行 closed-loop simulation（封閉迴路模擬），評估情境能否有效觸發預期行為或暴露系統缺陷，而不僅止於靜態編譯成功。

3. **多模態輸入與數位孿生**  
   擴展框架以接受地圖、影像或影片作為輸入，結合數位孿生（digital twin）技術，從真實世界事故或行車紀錄重建 test scenarios。

4. **對抗性與安全關鍵情境生成**  
   在 RAG 基礎上加入 adversarial optimization（對抗性最佳化），主動生成 rare but high-risk situations（罕見但高風險情境），以支援 SOTIF（Safety of the Intended Functionality，預期功能安全）驗證。

5. **降低對商業 LLM 的依賴**  
   開發針對 DSL 生成任務微調的開源 LLMs，或設計專屬 small language model（SLM），在保護資料隱私的同時降低推理成本與 API 依賴。

6. **跨模擬器與跨 DSL 遷移**  
   研究如何將生成的 Scenic DSL 自動轉譯至其他模擬器語言（如 SUMO、CARLA Python API、Apollo Dreamview），提升框架的通用性。

7. **錯誤分類與針對性修復**  
   建立生成失敗的錯誤分類法（error taxonomy），例如語法錯誤、語意錯誤、物理不一致、法規衝突等，並設計對應的專家修復模組。

8. **擴充多語言與多法規 benchmark**  
   將 benchmark 擴展至歐盟、中國、日本等地區的法規，並納入非英語描述，以測試框架在多語言與跨文化交通規則下的穩健性。

9. **使用者體驗研究**  
   針對 chatbot interface 進行使用者研究，量化互動式精煉對生成品質與使用者滿意度的影響，並優化對話流程設計。

10. **結合世界模型提升真實感**  
    利用 world models（世界模型）預測其他道路使用者的合理行為，確保生成情境不僅合法、可編譯，也在統計與物理層面具備真實性。

## 論文問答

**Q1：為什麼從法規描述自動生成可執行的自動駕駛測試情境腳本被視為一項開放性挑戰？**

A：法規文本通常以自然語言撰寫，語意複雜且充滿專業術語，要將其精確轉換為領域特定語言（DSL）可執行腳本，需要同時理解法規意圖與嚴格的 DSL 語法。此外，生成的腳本必須能通過編譯並在模擬器中正確執行，這對語法正確性、語意一致性以及車輛與環境互動的細節都提出很高要求。現有方法在泛化能力與編譯成功率之間存在根本取捨，因此這個問題至今仍未被充分解決。

**Q2：現有的「檢索組裝」與「檢索式完整腳本生成」方法各有什麼根本缺陷？**

A：「檢索組裝」方法雖然能達到尚可的編譯成功率，因為它主要組合資料庫中已有的 DSL 程式碼片段，但這也限制了它對新情境的泛化能力與情境多樣性。相對地，「檢索式完整腳本生成」方法雖然具備較好的靈活性，能從頭產生完整程式，但由於一次生成大量程式碼，容易出現語法錯誤或各元件之間不相容的問題，導致編譯成功率很低。這兩種方法分別犧牲了泛化能力或編譯成功率，難以同時滿足複雜法規情境生成的需求。

**Q3：為什麼多樣且符合法規的測試情境對自動駕駛系統驗證如此重要？**

A：真實世界道路測試成本高昂且難以覆蓋所有危險邊角案例，而模擬測試能夠以較低成本重現多樣且真實的駕駛情境，因此成為自動駕駛系統驗證的關鍵手段。為了確保自動駕駛系統在設計運行範圍（ODD）內的安全性，測試情境必須符合相關法規與安全標準，例如 SOTIF 所要求的預期功能安全。只有具備足夠多樣性且法規合規的情境，才能有效評估系統在罕見但高風險狀況下的表現。

**Q4：Chat2Scenic 的核心運作方式是什麼？**

A：Chat2Scenic 是一個迭代式檢索增強生成（RAG）框架，透過聊天機器人介面讓使用者以自然語言描述法規情境，並支援互動式情境精煉。它會在生成過程中反覆檢索相關法規知識與 DSL 語法範例，並以元件為單位逐步生成 DSL 區塊，最後組合成完整的可執行腳本。這種迭代生成方式讓大型語言模型（LLM）能夠在每一階段都獲得適當的上下文與回饋，從而提升程式碼的正確性與可編譯性。

**Q5：Chat2Scenic 相較於先前方法的主要創新之處是什麼？**

A：Chat2Scenic 是第一個針對自動駕駛情境生成所提出的迭代式 RAG 框架，它結合了聊天機器人介面、互動式精煉與檢索增強生成，填補了既有方法在泛化能力與編譯成功率之間的鴻溝。不同於一次生成完整程式或單純組裝既有程式碼片段，Chat2Scenic 採用迭代式元件生成策略，讓模型逐步建構複雜駕駛情境。這種設計同時保留了直接生成方法的靈活性，也具備接近檢索組裝方法的高編譯成功率。

**Q6：為什麼 Chat2Scenic 選擇「迭代式元件生成」而非「完整腳本生成」或「檢索組裝」？**

A：完整腳本生成雖然靈活，但一次輸出過多程式碼容易產生語法錯誤與元件間不相容的問題，導致編譯失敗。檢索組裝雖然編譯率較高，但受限於資料庫中已有的 DSL 元件，難以應對新穎或複雜的法規情境。迭代式元件生成則能在每一步只處理局部程式碼，並透過 RAG 引入相關法規知識與語法範例，兼顧生成品質、泛化能力與可編譯性。

**Q7：本研究提出了什麼樣的基準測試來評估情境生成？**

A：作者提出了一個開放的情境生成基準測試，共包含 123 個來自多種法規與資料來源的情境。這些情境涵蓋美國國家公路交通安全管理局（NHTSA）法規、聯合國車輛法規（United Nations Vehicle Regulations）以及其他來源，能夠測試方法在不同法規領域與複雜度下的表現。該基準測試的開放釋出有助於學術界與產業界進行更公平、可重現的比較。

**Q8：Chat2Scenic 在實驗中達到了什麼樣的關鍵結果？**

A：在使用最先進大型語言模型進行評估時，Chat2Scenic 達到了 76.42% 的編譯成功率（CSR）與 58.17% 的框架準確率（FA）。相較之下，檢索組裝方法僅有 30.08% CSR 與 11.03% FA，而檢索式完整腳本生成方法更只有 16.26% CSR 與 10.86% FA。這顯示 Chat2Scenic 在編譯成功率與框架準確率上都顯著優於現有方法。

**Q9：哪些設計因素對 Chat2Scenic 的效能提升貢獻最大？**

A：RAG 機制讓模型能夠根據當前生成步驟檢索最相關的法規條文與 DSL 語法範例，顯著降低語法錯誤與語意偏離。迭代式生成則將複雜的完整程式拆解為可逐步驗證的 DSL 區塊，減少一次性生成所帶來的累積錯誤。此外，聊天機器人介面所提供的互動式精煉機制，讓使用者能夠在生成過程中給予回饋，進一步提升最終腳本的品質與準確率。

**Q10：Chat2Scenic 在實務上可以如何應用於自動駕駛驗證流程？**

A：安全工程師或測試人員可以透過聊天機器人介面，直接輸入法規條文或自然語言情境描述，系統會自動生成對應的 DSL 可執行腳本。若生成的情境未完全符合需求，使用者可透過對話方式逐步精煉，例如調整車輛行為、天氣條件或交通參與者數量。最終腳本可直接匯入模擬器執行，大幅縮短從法規到測試的開發週期。

**Q11：若要將 Chat2Scenic 整合到產品級的自動駕駛驗證平台，需要考慮哪些因素？**

A：首先需要與現有的 DSL 編譯器與模擬器緊密整合，確保生成的腳本能夠被正確執行與驗證。其次需要建立並持續維護高品質的法規知識庫與 DSL 語法範例資料庫，以支撐 RAG 的檢索品質。此外，由於 LLM 輸出仍可能出錯，產品化時應保留人機協作審查機制，並加入版本控制與可追溯性，以符合功能安全與法規合規要求。

**Q12：Chat2Scenic 對自動駕駛研究與產業可能帶來什麼樣的影響？**

A：Chat2Scenic 能夠顯著提升法規導向測試情境的生成效率與多樣性，幫助開發者更全面地驗證自動駕駛系統在設計運行範圍內的安全性。透過開源釋出與開放基準測試，該研究也有助於推動學術界與產業界在情境生成領域的標準化與可重現性。長遠來看，這類工具有望降低模擬測試的建置成本，加速 SAE Level 4 等級自動駕駛系統的安全部署。

**Q13：作者承認 Chat2Scenic 有哪些主要限制？**

A：儘管 Chat2Scenic 的編譯成功率與框架準確率顯著優於既有方法，但仍未達到百分之百，顯示部分複雜或罕見情境仍無法被正確生成。其效能也高度依賴大型語言模型的能力與檢索資料庫的品質，若法規描述過於模糊或資料庫中缺少對應範例，生成結果可能會下降。此外，目前框架主要聚焦於 DSL 腳本生成，對於後續在模擬器中執行時的動態行為正確性，仍需額外驗證。

**Q14：在哪些情況下 Chat2Scenic 可能會生成失敗或產出品質不佳的腳本？**

A：當法規條文語意模糊、存在多種解釋方式，或涉及資料庫中未涵蓋的新穎駕駛情境時，模型可能難以生成正確的 DSL 程式碼。如果檢索到的 DSL 元件彼此不相容，或缺少必要的語言基本元件，也可能導致編譯失敗。此外，長時間跨越多個交通參與者的複雜互動情境，對大型語言模型的推理與規劃能力仍是挑戰，容易出現語法正確但行為不合理的結果。

**Q15：未來研究可以朝哪些方向進一步改進 Chat2Scenic？**

A：未來可以將框架擴展到更多模擬器與領域特定語言，例如支援 CARLA、SUMO 等不同平台的腳本生成。進一步改進檢索機制，例如結合法規條文的細粒度語意向量檢索，也有助於提升 RAG 的準確性。此外，將編譯器回饋與模擬執行結果更深入地整合到迭代生成迴路中，並支援多模態輸入與自動化安全評估，將是提升整體系統可靠性與實用性的重要方向。

## 實務應用指南

### 適用場景

1. **法規符合性測試情境自動化產生**  
   當驗證團隊需要將 NHTSA、聯合國車輛法規或內部安全規範轉換為可執行的 DSL 測試腳本時，可使用 Chat2Scenic 作為法規知識與程式碼之間的橋樑，減少人工翻譯錯誤。

2. **模擬測試前的快速情境原型設計**  
   系統工程師或測試工程師可透過聊天機器人介面，以自然語言描述「前車緊急煞車且後方機車切入」等複雜駕駛情境，並在幾輪互動中精煉參數，快速產生可在 CARLA、SUMO 等模擬器中執行的原型腳本。

3. **ADS 回歸測試與邊角案例擴充**  
   在持續整合／持續部署（CI/CD）流程中，Chat2Scenic 可依據最新事故報告或法規更新，自動生成新的邊角案例腳本，擴充現有測試資料庫，提升自動駕駛系統的迴歸測試覆蓋率。

4. **跨部門需求對齊與審查輔助**  
   法規工程師、功能安全工程師與模擬工程師可透過互動式介面共同檢視生成結果，確認法規描述與 DSL 實作是否一致，作為需求追溯與審查的輔助工具。

5. **學術與產業開放基準測試**  
   研究者與開發者可利用論文釋出的 123 個情境開源基準，比較不同大型語言模型在法規驅動情境生成上的編譯成功率（CSR）與框架準確率（FA）。

### 實作前置條件

**資料準備**

- 法規與測試規範文件：NHTSA、聯合國車輛法規、ISO/WD PAS 21448（SOTIF）或企業內部安全需求。
- DSL 語法與範例程式庫：包含 Scenic 或其他領域特定語言的官方文件、可編譯範例、常見錯誤對照表。
- 既有情境腳本與元件庫：用於檢索增強生成（RAG）的程式碼片段，以及對應的語意描述。
- 模擬器資源：CARLA、SUMO 或支援該 DSL 的模擬環境、地圖與車輛模型。

**運算資源**

- 大型語言模型推論資源：可選擇呼叫 OpenAI GPT-4、Anthropic Claude 等 API，或在本地部署 Llama、Mistral 等開源模型，建議配備至少 24 GB VRAM 的 GPU。
- 向量資料庫：如 Chroma、Weaviate 或 Milvus，用於儲存與檢索法規條文和 DSL 程式碼片段。
- 編譯與模擬執行環境：可自動執行 DSL 編譯器並回傳錯誤訊息的容器化服務。

**技能需求**

- 熟悉 Python 與 LLM 應用開發（提示工程、RAG、向量檢索）。
- 了解自動駕駛測試流程、法規術語與設計運行範圍（ODD）。
- 具備 DSL／編譯器除錯能力，能解析編譯錯誤並設計回饋機制。
- 具備模擬器操作經驗，能驗證生成腳本在模擬環境中的可執行性。

---

### 實作步驟建議

1. **定義應用範圍與法規來源**  
   先確定目標 ODD（如高速公路、市區交叉路口）與適用法規，將相關條文轉換為結構化文件，並標註每條規範對應的測試意圖。

2. **建立 RAG 知識庫**  
   將法規條文、DSL 語法文件、可編譯範例與常見錯誤說明切分為適當區塊，嵌入向量資料庫；同時建立關鍵字與語意混合檢索策略，以提升檢索準確度。

3. **設計迭代式生成流程**  
   參考 Chat2Scenic 的迭代元件生成方式，將完整腳本拆解為多個 DSL 區塊（如道路拓樸、車輛行為、觸發條件），每個區塊依序生成並經過編譯器驗證，再進入下一區塊。

4. **整合編譯回饋迴路**  
   每次生成後自動呼叫 DSL 編譯器，將錯誤訊息與原始碼一併送回 LLM 進行修正；可設定最大重試次數，並在持續失敗時提示使用者介入。

5. **開發聊天機器人介面**  
   提供自然語言輸入、多輪對話精煉、生成結果可視化與版本比對功能，讓非程式背景的利益關係人也能參與情境設計。

6. **建立評估與持續改善機制**  
   以 CSR 與 FA 作為核心指標，定期在開源基準上評估模型表現；收集使用者回饋與編譯錯誤日誌，持續擴充 RAG 知識庫與微調提示範本。

7. **部署至模擬測試管線**  
   將通過編譯的腳本自動匯入 CARLA／SUMO 執行，並與測試管理系統、需求追溯工具串接，形成從法規到模擬執行的完整工作流。

### 潛在風險與注意事項

- **法規詮釋錯誤風險**  
  LLM 可能誤解法規條文的語境，導致生成情境與法規原意不符。建議在 RAG 中加入法規專家審閱過的詮釋說明，並保留人工核准關卡。

- **編譯成功但語意錯誤**  
  高 CSR 不代表腳本在模擬中真正符合測試意圖。應輔以模擬執行驗證、軌跡檢查與領域專家抽樣審查，避免僅以編譯與否作為唯一指標。

- **幻覺參數與不一致的 DSL 元件**  
  模型可能產生不存在於 DSL 的參數名稱，或將個別合法但彼此衝突的元件組合在一起。迭代生成與編譯回饋可緩解此問題，但仍需維護嚴謹的 DSL 語法檢查。

- **安全關鍵系統的責任歸屬**  
  自動生成腳本若直接用於安全驗證，必須明確人機協作邊界與審查紀錄，符合功能安全與 SOTIF 流程要求。

- **模型與 API 穩定性**  
  LLM 輸出具有隨機性，不同版本模型的表現可能差異甚大。建議固定模型版本、設定低溫度參數（temperature），並建立可重現的生成紀錄。

### 與其他技術的整合建議

- **模擬器整合**  
  將 Chat2Scenic 輸出的 DSL 腳本直接對接 CARLA（車輛-centric）或 SUMO（交通流-centric），並透過模擬器回傳的執行結果進一步精煉情境。

- **需求管理與追溯工具**  
  與 DOORS、Jama 或 Polarion 等需求管理系統整合，使每個生成情境都能追溯到原始法規條文與需求編號，強化合規性審查。

- **CI/CD 與測試管線**  
  在 GitLab CI／GitHub Actions 中建立「法規更新 → 自動生成腳本 → 編譯檢查 → 模擬執行 → 報告產出」的自動化流程。

- **資料驅動與對抗性情境生成**  
  結合真實駕駛資料與對抗性搜尋方法（如 LEADE、OmniTester），在 Chat2Scenic 生成合法基礎情境後，進一步自動化搜尋高風險變異。

- **知識圖譜輔助 RAG**  
  對於複雜法規關係，可將向量檢索與知識圖譜結合，提升多條文關聯與例外條款的檢索品質。
