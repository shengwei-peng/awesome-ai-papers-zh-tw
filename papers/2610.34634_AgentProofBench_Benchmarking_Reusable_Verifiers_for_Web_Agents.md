AgentProofBench 的核心方法論建立在「可重用驗證器」（Reusable Verifier）的概念之上，旨在解決網頁代理（Web Agent）任務中一個根本性挑戰：公開指令（Public Instruction）保持固定，但所需完成的具體工作卻隨初始狀態（Initial State）變化而改變。傳統的驗證器若僅記憶先前的答案，可能對錯誤的需求給出看似合理的判斷，這正是該基準測試試圖捕捉的失敗模式。

**驗收介面設計（Acceptance Interface Design）**

該基準採用了一個可執行的驗收介面，每個任務提供三項輸入：公開指令 $q_i$、API 文件 $D_i$，以及經認證的普通介面 $O_i$。驗證器的形式化定義為：

$$b_{y_{ijk}} = V_i(q_i, O_i(S^0_{ik}), O_i(S^1_{ijk}))$$

其中 $k$ 標識初始狀態條件，$j$ 標識終端結果（Terminal Outcome）。提交的介面形式為 `verify(task, before, after)`，返回 Pass、Fail、Unknown 三種結果，並可附帶檢查項目與說明。例外狀況、格式錯誤輸出與執行限制耗盡則統一歸類為 Error。

**重用合約（Reuse Contract）機制**

重用合約是該方法論的關鍵創新，它固定了公開指令與證據權限（Evidence Permission），同時允許初始業務資料變化。建構提示（Construction Prompt）明確要求程式必須從其運行時的「前狀態」（before state）推導出依賴於狀態的需求。每個評估都在一個全新的唯讀沙盒中執行凍結的源碼（Frozen Source），並使用任務行動者的 API 權限。資源限制為單次執行 1 個 CPU、1 GB 記憶體、60 秒時間，以及跨兩個快照共 80 次業務操作（GraphQL 根查詢分開計算）。

**配對重用測試（Paired Reuse Test）**

此測試保持公開指令與生成的程式固定，但改變其所需的初始狀態綁定（Initial-state Binding）。它採用兩種互補的測量方式：
- **完整面板測試（Complete-panel Test）**：使用完整的結果面板
- **決策重播測試（Decision-replay Test）**：重播先前的決策

這兩種測試共同衡量驗證器的互補義務：既要識別允許的終端結果，也要從變化的初始狀態中恢復需求。

**執行有效性測試（Execution-validity Test）**

此測試將部署狀態面板正確性（Deployment-state Panel Correctness）與配對的策略結果（Policy Outcome）連結起來。22 個執行族（Execution Family）保留了 44 個程式指派（Program Assignment），每個指派有兩個開場（Opening），共產生 352 個策略結果。這種設計使得驗證器決策的後果可被觀察。

**配對延續歷史（Matched Continuation Histories）**

這是連結測試與執行的核心機制。相同的已完成工作可在不同的停止策略（Stopping Policy）下被保留、修改或扣留。共享的行動者開場（Actor Opening）將同一個驗證器與其決策後採取的動作連結起來，從而使每個測量都與版本化的參考謂詞（Versioned Reference Predicate）、程式源碼、API 證據和可重建的業務狀態（Reconstructable Business State）相連結。

#### 實驗數據解讀

該基準的實驗結果揭示了驗證器品質與執行後果之間的強烈相關性，呈現出幾個關鍵發現：

**重用重建的一致性（Reuse-rebuild Consistency）**

在 48 個族中，完整面板與決策重播測試保留了 82/96 的 Flash 來源程式和 79/96 的 Pro 來源程式。配對重用重建的 BA（Bootstrap Agreement）區間分別為 [-5.47, 1.57] 與 [-10.16, 0.00] 百分點。這些區間跨越零的特徵表明，雖然存在個案差異，但整體而言重用驗證器在面對初始狀態變化時能維持相當的判斷一致性。值得注意的是，Pro 模型在較低端的負值更大，暗示其在某些邊緣案例上可能更脆弱。

**部署狀態面板與執行結果的關聯**

最引人注目的結果是部署狀態面板正確性對程式指派結果的強預測力：在 22 個執行族中，擁有 33 個程式指派中，**面板無誤（Error-free Panel）的指派有 32/33 正確交付了兩個已儲存開場（Saved Opening）**，而**面板有誤的指派僅有 1/11 達成此結果**。這個約 97% 對 9% 的懸殊比例，證實了驗證器測試品質與實際執行表現之間存在強烈的因果連結。

**參考定義的程式閘門迴歸（Reference-defined Program-gate Regression）**

所有參考定義的程式閘門迴歸與扣留交付（Withheld Delivery）都發生在面板有誤的群組中。這一發現具有重要的方法論意義：它表明基準測試能夠精確定位失敗的根源——不是隨機的執行波動，而是驗證器本身的結構性缺陷。

**中性延續（Neutral Continuation）的基線表現**

在測試的通用回饋（Generic Feedback）下，中性延續達到了最高的正確交付率。這為衡量閘門（Gate）所帶來的附加價值（Value Added）提供了一個具體基線（Concrete Baseline）。換言之，任何更複雜的策略若要證明其必要性，必須顯著超越這個簡單基線。

**重播證人（Replay Witness）的診斷價值**

配對重用研究解釋了這些面板所測試的需求；重播證人在三個來源程式中暴露了額外的錯誤。這顯示出單一測試方法可能遺漏某些失敗模式，而多重視角（面板 + 重播）的結合能提供更全面的診斷覆蓋。

**固定實例驗收與成本概況**

固定實例驗收（Fixed-instance Acceptance）與成本概況（Cost Profile）描述了同一驗證介面的運營權衡。這暗示在實際部署中，僅追求高準確率是不夠的，還需考慮執行成本、回應時間等運營指標。

#### 與現有研究的比較

AgentProofBench 在多個層面上區別於現有研究，並對其進行了明確的定位：

**與可執行任務環境的關係**

該基準建立在 WebArena、OSWorld、$\tau$-bench、AppWorld 等可執行任務環境的基礎之上，並使用了 Agent-Diff 提供的企業服務複本。這些環境提供了可執行的任務評估框架，但 AgentProofBench 將測量目標擴展到配對的初始狀態需求以及驗證器決策所控制的後續執行。

**與生成式驗證器研究的關係**

CodeT 與 Eureka 生成可執行的測試或獎勵；SpecGuardBench 與 WebGrader 評估生成的驗證程式碼；Rules to Tools 為程式修復提供科學需求的可呼叫實作；VerifierBench 在六個代理基準上測試可執行驗證器生成。AgentProofBench 進一步將測量擴展到配對的初始狀態需求，這是先前工作未充分覆蓋的維度。

**與證據基礎判斷研究的關係**

Agent-as-a-Judge、AJ-Bench、AgentRewardBench 研究從環境與軌跡證據進行的評估；Universal Verifier 開發基於準則的電腦使用評估；Sauron 收集狀態與追蹤證據；VAGEN 與 VeriHarness 研究代理驗證與結構化證據收集；LLM-as-a-Verifier 檢查連續分數、重複評估與準則分解。AgentProofBench 的新穎 API 判斷共享了可執行程式的凍結狀態與普通證據權限，從而能夠直接比較有效驗收、失敗拒絕與重複使用成本。

**與重用與執行期間驗證研究的關係**

SkillLearnBench 評估跨任務實例學習的工件；ControlScope 研究工作流程修訂權限如何影響後續執行；Revision or Re-Solving 使用配對條件分離第二輪改進的來源；CLIFT 重用凍結的自驗證庫進行訓練與軌跡選擇；Neuro-Symbolic Computer Use 在初始狀態與參數變化下學習可重用的執行策略，並採用驗證引導的延續；SPLIT 在採樣與不完美驗證之間分配計算；驗證器硬化結合對抗性改進與對有效解決方案的保護。AgentProofBench 透過配對驗證器測試與共享歷史的執行，提供了獨特的測量視角。

**改進與侷限性**

相較於 VerifierBench，AgentProofBench 的主要改進在於：
1. **配對設計**：透過保持指令固定但改變初始狀態，揭示了「記憶先前答案」這類微妙失敗模式
2. **執行連結**：將驗證器測試結果與實際執行後果連結，提供了端到端的評估
3. **多層級測量**：同時在需求層級（Requirement Level）與策略層級（Policy Level）進行測量

然而，該基準也存在侷限性：
- 僅使用 DeepSeek Flash/Pro 模型，結果對其他模型的泛化性需要進一步驗證
- 97 個任務、79 個族的規模雖然不小，但相較於某些大規模基準仍有限
- 思考模式（thinking mode）被停用，可能無法捕捉推理增強模型的全部能力
- 通用回饋的設計可能過於簡化，未涵蓋所有可能的回饋類型

AgentProofBench 在可重現性方面展現了高度的承諾，這是該基準的一個重要優勢：

**完整的資源釋出**

版本化的參考謂詞確保了評估的時間穩定性。隨著基準的演進，研究人員可以明確區分不同版本下的結果差異，避免「基準漂移」（benchmark drift）問題。

每個評估在全新的唯讀沙盒中執行，這保證了：
1. 執行隔離性，防止狀態洩漏
2. 可重現性，相同的輸入總是產生相同的執行環境
3. 安全性，防止驗證程式對底層系統造成損害

**可重現性的潛在限制**

儘管資源豐富，仍存在一些可重現性挑戰：
- DeepSeek API 的版本更新可能導致結果變化
- 企業服務複本（Agent-Diff）的狀態可能隨時間演進
- 通用回饋的具體實作細節需要仔細記錄

- 接受初始狀態與終端狀態作為輸入
- 回傳布林值或結構化評分
- 涵蓋所有合法替代方案（不只單一正確路徑）

**步驟 3：設計驗收程式生成 Prompt**
參考 AgentProofBench 的建構 Prompt，明確告知 LLM：
- 程式必須從執行時的 before 狀態推導需求
- 輸出格式：`verify(task, before, after) -> {Pass/Fail/Unknown, checks, explanation}`
- 限制：僅使用任務參與者的 API 權限、不可修改狀態

**步驟 4：執行配對重用測試**
對每個任務族準備至少 2 組不同的初始狀態（k=1, 2），用同一個驗收程式分別評估。記錄：
- 完整面板測試結果（所有終端結果的正確性）
- 決策重播測試結果（同一組 before/after 重跑的一致性）

**步驟 5：連結執行驗證**
將驗收決策串接到下游策略：
- Pass → 釋出狀態、執行交付
- Fail → 觸發編輯迴圈
- Unknown → 要求更多證據
收集每個分支的最終交付結果，建立「部署狀態面板」。

**步驟 6：建立基線與衡量增量**
以「中性延續」（不參考驗收結果，繼續執行直到自然結束）作為基線。比較加入驗收閘門後的：
- 正確交付率提升
- 程式閘門迴歸數量（即閘門錯誤拒絕正確結果）
- 計算成本變化

**步驟 7：部署監控與持續評測**
將測試套件整合到 CI/CD 流程，每次驗收程式更新後自動重跑配對測試與執行驗證。當新模型版本發布時，同步評估其作為驗證器生成器的表現。

### 潛在風險與注意事項

**風險 1：驗收程式記住過期需求**
若驗收程式將「當前擁有者」這類動態資訊硬編碼，會在初始狀態變動時產生誤判。**緩解措施**：在 Prompt 中明確禁止硬編碼任何狀態相關值；強制要求所有動態資訊從 `before` 參數推導。

**風險 2：沙箱逃逸或資源耗盡**
驗收程式若包含無限迴圈或過度 API 呼叫，可能影響生產環境。**緩解措施**：嚴格執行 60 秒、80 次操作的限制；使用獨立的唯讀 API token；監控並自動終止異常程式。

**風險 3：合法替代方案被誤判為失敗**
若參考規則只涵蓋單一路徑，會低估驗收器的真實表現。**緩解措施**：邀請領域專家列舉所有合法替代方案；定期審查「被拒絕但其實正確」的案例。

**風險 4：LLM 生成程式碼的安全漏洞**
生成的 Python 程式可能包含 `eval`、`os.system` 等危險函式。**緩解措施**：使用 AST 靜態分析預過濾危險呼叫；在沙箱中禁用網路與檔案系統寫入。

**風險 5：配對測試的初始狀態偏差**
若兩組開場過於相似，可能無法偵測出「記住舊需求」的問題。**緩解措施**：刻意設計差異化的初始狀態（例如不同的擁有者、不同的檔案集合）；定期更新開場資料庫。

**風險 6：閘門迴歸掩蓋真實問題**
若閘門過於嚴格，可能錯誤拒絕正確結果，反而降低整體交付率。**緩解措施**：追蹤「程式閘門迴歸」指標（即閘門拒絕但參考規則會接受的比例）；當此指標超過閾值時觸發警報。

### 與其他技術的整合建議

**與既有測試框架整合**
AgentProofBench 的驗收程式可作為 pytest 的 fixture 整合進傳統測試流程。每次部署前自動執行 `verify(task, before, after)`，將 LLM 生成的驗證邏輯與單元測試、整合測試並列執行。

**與 LangChain / AutoGen 等代理框架整合**
將驗收程式包裝為代理的工具（Tool），在代理的決策迴圈中作為「品質檢查工具」呼叫。當工具回傳 Fail 時，自動將錯誤訊息注入到代理的下一次推理中。

**與 Observability 平台整合**
將每次驗收決策（Pass/Fail/Unknown）、對應的證據快照、動作軌跡上傳至 OpenTelemetry 或 LangSmith。這樣不僅能除錯，還能建立「驗證器表現儀表板」，長期追蹤模型版本更新對驗證品質的影響。

**與 CI/CD Pipeline 整合**
在 GitHub Actions 或 GitLab CI 中加入「驗收程式回歸測試」階段：當 `verify.py` 變更時，自動重跑配對重用測試與執行驗證，確保新版本不會引入閘門迴歸。

**與人類審查流程整合**
對於 Unknown 結果或高風險操作（如刪除、付款），設計「人類在迴圈中」（Human-in-the-Loop）的升級路徑。驗收程式負責過濾明確的 Pass/Fail，僅將模糊案例路由給人類審查者。

**與向量資料庫整合**
將歷史驗收決策、錯誤案例、合法替代方案嵌入向量資料庫。當新任務的 before 狀態與歷史案例相似時，主動提示 LLM 參考過去的判斷，提升一致性。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）了解「為什麼需要可重複使用的驗證器」，再跳到第 3.1 節理解 `verify(task, before, after)` 的基本介面。核心概念是：驗證器不是給出「是/否」答案的黑盒子，而是一段可執行的程式碼，它必須在每次執行時重新從當前狀態推導需求。理解這個區別後，就能掌握 AgentProofBench 想解決的根本問題。

**給 AI 工程師**：重點關注第 3 節的「重用合約」設計與第 4 節的實驗結果。特別是「部署狀態面板正確性」如何區分出 32/33 vs 1/11 的極端差異——這告訴我們，驗證器的測試不能只看單一指標，必須串接到下游執行才能發現真實問題。實作時，建議先複製 AgentProofBench 的沙箱配置（1 CPU、1 GB、60 秒、80 操作）作為起點，再根據自家業務調整。

**給研究者**：第 2 節的相關工作分類（可執行評估、證據導向判斷、執行中的重用與驗證）提供了完整的文獻地圖。值得深入追蹤的方向包括：VerifierBench 的「合法替代方案」處理、神經符號電腦使用（Neuro-Symbolic Computer Use）的可重用執行策略、以及 DCP 的真實/中性回饋比較。AgentProofBench 的主要學術貢獻在於建立了「測試→執行」的因果鏈，這對未來研究「驗證器設計如何影響代理整體表現」提供了新的評測範式。

**給產品經理**：AgentProofBench 的核心商業價值在於「讓自動化決策可被檢查與重現」。當你向客戶解釋「為什麼這個自動化流程是可信的」時，可以展示：(1) 驗收程式的源碼（透明）、(2) 每次決策對應的證據快照（可追溯）、(3) 跨不同初始狀態的一致性測試（可驗證）。實務上，建議從單一高頻任務（例如訂單狀態更新）開始試點，用 AgentProofBench 的方法建立第一個「可驗證的自動化流程」，再逐步擴展到其他場景。關鍵指標是「正確交付率」與「閘門迴歸率」的平衡——前者衡量自動化帶來的效率提升，後者衡量品質控制的可靠度。
