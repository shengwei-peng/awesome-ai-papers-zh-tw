## ⚡ TL;DR

現有全模態標記壓縮常因跨模態顯著性不匹配，單向引導易丟棄關鍵線索。
本文提出 OmniScope，以查詢為共享語義錨點，讓音訊與視覺獨立決定壓縮策略。
於四項基準中，25% 保留率達 3.53 倍預填充加速、逾 15% 記憶體降低，平均準確率僅降 0.35 分。

## 摘要翻譯

現有的全模態大型語言模型標記壓縮（Token Compression）方法通常仰賴單一模態來決定另一模態中應保留的內容。我們發現此假設經常不成立：對於相同的查詢（Query），音訊與視訊的相關性（Relevance）往往在不同時刻達到高峰。這種跨模態顯著性不匹配（Cross-Modal Salience Mismatch）使得單向引導（Unidirectional Guidance）在激進壓縮（Aggressive Compression）下容易捨棄答案關鍵線索（Answer-Critical Cues）。我們提出 OmniScope，一個訓練無需（Training-Free）的標記壓縮框架，以查詢作為共享語義錨點（Shared Semantic Anchor），同時分別估計音訊與視訊的相關性。OmniScope 分配模態專屬標記預算（Modality-Specific Token Budgets），採用錨點-差值策略（Anchor-Delta Strategy）剪枝視覺標記（Visual Tokens），同時保留全局上下文（Global Context）與時間變化（Temporal Changes），並在每秒內合併音訊標記（Merge Audio Tokens）以減少冗餘並保持時間連續性（Temporal Continuity）。在四個音視訊基準測試（Audio-Video Benchmarks）與兩種 Qwen2.5-Omni 模型規模（Model Scales）上，OmniScope 在所有壓縮設定（Compression Settings）下均達到最佳的平均準確率（Average Accuracy）。在整體標記保留率（Overall Token Retention）為 25% 時，OmniScope 可帶來高達 3.53 倍的預填充加速（Prefill Speedup），GPU 記憶體減少（GPU Memory Reduction）超過 15%，平均準確率僅下降 0.35 分。這些結果顯示了一項適用於全模態大型語言模型推論的簡單設計原則：在模態間共享查詢，但不共享顯著性估計。程式碼可於 https://github.com/MAC-AutoML/OmniScope 取得。

### 核心貢獻（3～5點）
- 揭示並驗證「跨模態顯著性不匹配」問題：對同一查詢，音訊與視訊的關鍵時刻常不一致，單向引導容易在激進壓縮下遺失答案關鍵線索。
- 提出 OmniScope，一個訓練無需的模態解耦標記壓縮框架，以查詢作為共享語義錨點，但對音訊與視訊分別估計相關性並配置模態專屬標記預算。
- 設計錨點-差值視覺剪枝策略，同時保留全局上下文與時間變化；並以每秒為單位合併冗餘音訊標記，兼顧時間連續性。
- 在四個音視訊基準測試與兩種 Qwen2.5-Omni 模型規模上，於所有壓縮設定均達到最佳平均準確率；在 25% 整體標記保留率下，實現 3.53 倍預填充加速與超過 15% 的 GPU 記憶體減少，平均準確率僅下降 0.35 分。
- 提煉適用於 OmniLLM 推論的設計原則：跨模態共享查詢，但不共享顯著性估計。

### 適合對象
本論文適合從事全模態／多模態大型語言模型、端到端音視訊理解、模型推論加速與壓縮，以及邊緣或資源受限裝置部署的研究者與工程師閱讀。對於關注如何在不重新訓練模型的前提下降低音視訊推論成本，同時維持問答準確度的讀者尤具參考價值。

## 深度分析

#### 方法論解析

##### 核心設計原則：以 Query（查詢）作為共享語義錨點，解耦顯著性估計

OmniScope 的核心設計原則可概括為「共享 Query（查詢），但不共享顯著性（Salience）」。在全模態大型語言模型（OmniLLMs）中，使用者問題同時對音訊與視覺兩個模態提出資訊需求，因此 Query（查詢）天然適合作為跨模態的 Shared Semantic Anchor（共享語義錨點）。然而，論文指出，對於同一個 Query（查詢），音訊顯著性（Audio Salience）與視覺顯著性（Visual Salience）的峰值往往出現在不同時間點，形成 Cross-Modal Salience Mismatch（跨模態顯著性不匹配）。因此，OmniScope 讓音訊與視覺各自獨立估計與 Query（查詢）的 Relevance（相關性），再根據各自的相關性分佈進行 Token Compression（標記壓縮），避免單向引導（Unidirectional Guidance）誤刪對另一模態至關重要的 Answer-Critical Cues（答案關鍵線索）。

##### 模態專屬標記預算分配

OmniScope 在給定 Overall Token Retention（整體標記保留率）後，將總預算拆分為 Modality-Specific Token Budgets（模態專屬標記預算）。具體而言，系統會先分別計算音訊串流（Audio Stream）與視覺畫面（Visual Frames）中每個 Token（標記）對 Query（查詢）的相關性分數，再依據各模態的整體顯著性質量（salience mass）或預設比例，決定音訊與視覺各自可保留的 Token（標記）數量。這種解耦預算確保了：當 Query（查詢）主要依賴視覺答案時，視覺側不會因音訊側顯著性低而被過度壓縮；反之亦然。

##### 視覺側：Anchor-Delta Spatio-Temporal Compression（AD-STC，錨點-差值時空壓縮）

視覺 Token（Visual Tokens）的壓縮採用 AD-STC（Anchor-Delta Spatio-Temporal Compression，錨點-差值時空壓縮）。該策略同時考慮兩類資訊：

- **Anchor（錨點）**：代表影片的全局語義覆蓋（Global Context），通常選取能涵蓋整體場景或與 Query（查詢）高度相關的關鍵幀，避免高壓縮比下遺失整體情境。
- **Delta（差值）**：代表 Temporal Changes（時間變化），即相鄰幀之間的動態差異，用於保留動作、事件轉折等時序資訊。

傳統的視覺時空壓縮方法往往對所有增量幀套用相同策略，容易在激進壓縮（Aggressive Compression）時喪失全局上下文。AD-STC 則在 Token Budget（標記預算）內同時保留錨點幀與變化幀，達到 Global Context（全局上下文）與 Temporal Changes（時間變化）的平衡。

##### 音訊側：每秒標記合併（Per-Second Token Merging）

音訊編碼器通常以極高時間解析度輸出 Audio Tokens（音訊標記），導致相鄰 Token（標記）之間存在大量冗餘。OmniScope 提出在編碼器輸出後的時序嵌入（post-encoder temporal embeddings）上進行每秒二分軟匹配（per-second bipartite soft matching），將同一秒內語義相近的音訊 Token（音訊標記）合併。這種設計有兩個優點：

1. **降低冗餘**：透過 Merge Audio Tokens（合併音訊標記）減少重複的聲學資訊。
2. **維持 Temporal Continuity（時間連續性）**：以「秒」為單位進行合併，保留音訊事件的時序邊界，避免粗粒度剪枝造成時間斷裂。

##### 與跨視窗模態互動的協同效應

論文進一步觀察到，Token Compression（標記壓縮）會強化 OmniLLMs 內部的 Cross-Window Modal Interaction（跨視窗模態互動）。當壓縮後保留的 Token（標記）確實來自各模態的 Query（查詢）相關區域時，增強後的跨視窗注意力會自然聚焦在任務相關線索；反之，若單向引導誤刪了關鍵 Token（標記），注意力則會被導向次要線索。OmniScope 的模態解耦設計正是為了讓壓縮後的跨視窗注意力「對準」正確答案。

##### 訓練無需的實作優勢

OmniScope 是一個 Training-Free（訓練無需）框架，不需要額外微調壓縮模組或 LLM 解碼器。它直接利用現有編碼器（Encoders）輸出的特徵與 Query（查詢）嵌入進行相關性估計，因此可即插即用於已訓練好的 OmniLLMs，大幅降低部署門檻。

#### 實驗數據解讀

##### 評估設定與基準

論文在四個 Audio-Video Benchmarks（音視訊基準測試）上進行評估，並使用兩個模型規模（Model Scales）的 Qwen2.5-Omni：7B 與 3B。測試涵蓋不同的 Token Retention（標記保留率）設定，重點關注 45% 與 25% 兩個 Overall Token Retention（整體標記保留率）水準，分別對應溫和壓縮與激進壓縮（Aggressive Compression）。

##### 準確率與壓縮比的權衡

實驗結果顯示，OmniScope 在所有壓縮設定下均取得最佳 Average Accuracy（平均準確率）。特別值得注意的是：

- 在 **45% Token Retention（標記保留率）** 時，OmniScope 幾乎達到無損準確率（nearly lossless accuracy），顯示在壓縮掉超過一半 Token（標記）的情況下，仍能完整保留回答所需的語義資訊。
- 在更激進的 **25% Overall Token Retention（整體標記保留率）** 下，Average Accuracy（平均準確率）僅下降 0.35 分，展現出對高壓縮比的強健性。

這 0.35-point drop（分數下降）的數值極小，意味著在實際應用中，即使將音視訊 Token（標記）大幅削減至四分之一，模型仍能保持與完整序列相近的推理品質。

##### 效率收益：Prefill Speedup（預填充加速）與 GPU Memory Reduction（GPU 記憶體減少）

在 25% 保留率下，OmniScope 帶來顯著的推論效率提升：

- **Prefill Speedup（預填充加速）**：最高達 **3.53×**。由於 Transformer 的注意力機制對序列長度呈二次方複雜度，減少 Token（標記）數量能顯著降低 Prefill（預填充）階段的計算量。
- **GPU Memory Reduction（GPU 記憶體減少）**：超過 **15%**。較短的 Token Sequence（標記序列）直接減少啟動值（activations）與 KV Cache 的記憶體佔用。

這些數據說明 OmniScope 在準確率與效率之間取得了極佳的權衡，特別適合部署於資源受限裝置（Resource-Constrained Devices）或需要即時互動（Real-Time Interaction）的場景。

##### 模型規模泛化性

實驗同時涵蓋 7B 與 3B 兩種模型規模，OmniScope 在兩種規模下均表現最佳，顯示其設計不依賴特定模型容量，具有較好的跨規模泛化能力。這對於需要在邊緣裝置使用較小模型、同時在伺服器使用較大模型的應用情境尤為重要。

##### 結果意涵

整體而言，實驗結果支持論文提出的設計原則：在 OmniLLMs 中，Query（查詢）應作為跨模態共享參考，但各模態的 Salience（顯著性）估計必須獨立進行。數據也顯示，Training-Free（訓練無需）方法已能在多個基準上超越或逼近需要微調的競爭方法，降低了高效 OmniLLM 推論的門檻。

#### 與現有研究的比較

##### 相較於單向跨模態引導：OmniZip

OmniZip 是現有代表性的全模態壓縮方法，採用 Audio-to-Video Guidance（音訊引導視覺）的單向策略，以音訊重要性分數決定視覺 Token（視覺標記）的保留。然而，論文指出這種 Unidirectional Guidance（單向引導）在 Cross-Modal Salience Mismatch（跨模態顯著性不匹配）時會失效：

- 若答案關鍵線索在視覺側（例如裁判手勢），但該時刻音訊顯著性低，則音訊引導會錯誤地刪除這些 Visual Tokens（視覺標記）。
- 反之，若答案線索在音訊側（例如哨聲），但視覺引導佔主導，也會遺失 Audio Tokens（音訊標記）。

OmniScope 透過 Modality-Decoupled Token Compression（模態解耦標記壓縮）避免了這個問題，讓音訊與視覺各自決定保留內容。

##### 相較於需微調方法：OmniSIFT

OmniSIFT 採用端到端微調（end-to-end fine-tuning），需要額外訓練壓縮模組並調整 LLM 解碼器。雖然這類方法可能學到更精細的壓縮策略，但存在以下缺點：

- 需要大量計算資源與標註資料進行訓練。
- 微調後的模型可能對特定資料集過擬合，泛化能力受限。
- 部署門檻高，難以直接應用於新釋出的 OmniLLMs。

相較之下，OmniScope 是 Training-Free（訓練無需）框架，無需修改模型權重，可直接套用於現成的 Qwen2.5-Omni 等模型，具有更高的實用性與可遷移性。

##### 與純視覺／純音訊壓縮方法的關係

現有的 Vision-Only Multimodal LLMs（僅視覺多模態大型語言模型）壓縮方法（如基於相似度的 Token Merging（標記合併）、Query-Based Pruning（基於查詢的剪枝）等）僅處理視覺 Token（視覺標記），無法處理音訊串流（Audio Stream）。同樣地，現有音訊壓縮方法多受限於編碼器內部結構或採用粗粒度剪枝，難以靈活適應下游 LLM 的壓縮需求。

OmniScope 將視覺與音訊壓縮整合為統一框架，並針對各模態特性設計專屬策略：視覺側使用 AD-STC（錨點-差值時空壓縮）平衡全局與動態資訊，音訊側使用每秒標記合併維持 Temporal Continuity（時間連續性）。

##### 方法限制

儘管 OmniScope 表現優異，仍存在一些限制：

1. **模型侷限性**：實驗主要基於 Qwen2.5-Omni，雖然方法原則上可遷移至其他 OmniLLMs，但在不同編碼器架構或 Token（標記）交錯機制上的效果仍需驗證。
2. **預算分配啟發式**：模態專屬預算目前可能採用基於顯著性質量或固定比例的啟發式策略，對於極端 Query（查詢）或高度不對稱的模態重要性，可能仍有優化空間。
3. **未顯式建模跨模態互動**：OmniScope 刻意避免單向跨模態引導，但也因此未在壓縮階段利用音訊與視覺之間的相互注意力來「驗證」關鍵 Token（標記）。未來可探索如何在保留解耦優勢的同時，引入輕量級的跨模態驗證機制。
4. **極端壓縮比**：在 25% 以下甚至更低保留率時，任何壓縮方法都會面臨資訊瓶頸，OmniScope 的無損優勢可能逐漸縮小。

#### 可重現性評估

##### 開源程式碼與模型權重

論文已將程式碼釋出於 https://github.com/MAC-AutoML/OmniScope，這是提升可重現性的重要基礎。由於 OmniScope 是 Training-Free（訓練無需）框架，研究者無需重新訓練模型，只需取得公開的 Qwen2.5-Omni 模型權重即可重現主要實驗結果。

##### 資料集與評估腳本

雖然提供的摘要與引言未詳細列出四個 Audio-Video Benchmarks（音視訊基準測試）的確切名稱，但這類研究通常使用公開的影片問答（Video Question Answering）或音視訊理解資料集。若 GitHub 倉庫同時提供資料預處理腳本、評估腳本與壓縮設定檔，則可重現性將非常高。建議讀者在重現時確認以下項目：

- 資料集下載與前處理流程是否完整。
- Token Retention（標記保留率）的計算方式（是否包含特殊 Token（標記）如 Query（查詢）與系統提示）。
- Prefill Speedup（預填充加速）與 GPU Memory Reduction（GPU 記憶體減少）的測量環境（GPU 型號、批次大小、序列長度等）。

##### 訓練無需帶來的可重現性優勢

由於不需要微調，OmniScope 避免了許多可重現性問題，例如隨機種子、訓練超參數、資料增強策略等。研究者只需在相同的模型檢查點上執行壓縮演算法，即可獲得接近論文報告的結果。這對於學術界與工業界快速驗證與部署都非常有利。

##### 潛在重現挑戰

儘管方法本身簡潔，重現時仍可能遇到以下挑戰：

- **硬體需求**：7B 規模的 OmniLLMs 仍需較大 GPU 記憶體，邊緣裝置可能難以直接重現。
- **音視訊前處理**：不同資料集的取樣率、幀率、編碼格式可能影響 Token（標記）數量，進而影響保留率的計算。
- **實作細節**：AD-STC（錨點-差值時空壓縮）與每秒標記合併的具體演算法細節（如相似度度量、二分匹配閾值）若未在論文中完整揭露，可能需要參考開源程式碼才能準確重現。

#### 未來研究方向

##### 動態與語境感知預算分配

目前的 Modality-Specific Token Budgets（模態專屬標記預算）可能基於啟發式或固定比例。未來可研究如何根據 Query（查詢）類型、影片內容的語義密度（semantic density）以及各模態的即時重要性，動態調整音訊與視覺的保留比例。例如，對於「影片中的人在說什麼？」這類問題，應自動分配更多預算給音訊；而對於「裁判做了什麼手勢？」則應優先保留視覺。

##### 跨模態注意力引導的聯合壓縮

OmniScope 刻意避免單向 Unidirectional Guidance（單向引導），但未來可探索「雙向驗證」機制：在不讓任一模態主導另一模態的前提下，利用 Cross-Window Modal Interaction（跨視窗模態互動）或跨模態注意力分佈，識別那些被兩個模態共同關注或互補關注的關鍵 Token（標記）。這樣可以在保留解耦優勢的同時，進一步提升壓縮後的資訊密度。

##### 串流與長影片推論

目前的 OmniScope 似乎針對完整影片進行離線壓縮。未來可將其擴展至串流（streaming）場景，設計線上 Token Compression（標記壓縮）機制，在影片持續輸入的同時動態維護一個精簡的記憶緩衝區。這對於即時互動（Real-Time Interaction）與長影片理解至關重要。

##### 硬體感知與端側部署

未來研究可將 OmniScope 與模型量化（quantization）、KV Cache 壓縮、網路剪枝（network pruning）等技術結合，形成端到端的硬體感知推論管線。此外，針對不同裝置（手機、邊緣伺服器、雲端 GPU）設計自適應壓縮策略，可進一步推動 OmniLLMs 在 Resource-Constrained Devices（資源受限裝置）上的落地。

##### 擴展至更多模態與任務

除了音訊與視覺，OmniLLMs 未來可能整合更多模態，例如深度圖、熱成像、觸覺訊號或感測器資料。OmniScope 的「共享 Query（查詢）、解耦顯著性」原則可自然擴展至多模態設定，為每個模態設計專屬的壓縮策略。同時，也可將此方法應用於內容審核（Content Moderation）、多模態檢索、機器人感知等更廣泛的任務。

## 論文問答

**Q1：全模態大型語言模型在處理長音視訊輸入時面臨哪些效率挑戰，為什麼標記壓縮對解決這些挑戰很重要？**
A：OmniLLMs 會將影片的視覺畫面與音訊串流分別經由編碼器轉成長長的標記序列，隨著影片長度增加，整體標記數量會快速膨脹，導致計算開銷與記憶體開銷急遽上升，並嚴重削弱上下文互動的品質。標記壓縮能直接縮短這些序列長度，降低推論成本，是讓 OmniLLMs 能在資源受限裝置上即時部署的關鍵手段。然而，過度壓縮又可能遺失回答問題所需的關鍵線索，因此必須在效率與資訊保留之間取得平衡。

**Q2：什麼是跨模態顯著性不匹配？為什麼它會讓 OmniZip 這類單向引導方法在激進壓縮下失效？**
A：跨模態顯著性不匹配指的是對於同一個查詢，音訊顯著性與視覺顯著性往往在時間軸上出現不同的高峰，例如哨聲先出現在音訊，而裁判手勢稍後才出現在視覺。單向引導方法讓一個模態的重要性分數決定另一個模態該保留哪些標記，因此當某個模態的低顯著區域恰好包含另一個模態的關鍵線索時，就容易被錯誤剪除。在高壓縮比下，這種資訊遺失會導致模型無法取得回答問題所需的完整證據。

**Q3：為什麼讓一個模態決定另一個模態的保留內容是有問題的？作者從注意力分佈中觀察到什麼？**
A：作者發現標記壓縮會強化跨視窗模態互動，也就是壓縮後不同時間視窗間的音訊與視覺注意力會變得更強。如果單向引導在顯著性不匹配時丟棄了關鍵標記，這股被放大的跨視窗注意力反而會被導向次要的線索，損害任務表現。相反地，若每個模態都保留自己對查詢最相關的標記，增強後的互動自然會聚焦在雙方的任務相關線索上。

**Q4：OmniScope 的核心設計原則是什麼？它與先前全模態壓縮方法的主要差異為何？**
A：OmniScope 的核心原則是以查詢作為共享語義錨點，但讓音訊與視覺各自獨立估計對查詢的相關性並執行壓縮。這與 OmniZip 等採用單向跨模態引導的方法不同，後者會讓一個模態的顯著性分數直接決定另一個模態的保留決策。簡言之，OmniScope 主張「共享查詢，但不共享顯著性估計」，從而避免跨模態顯著性不匹配所造成的資訊遺失。

**Q5：什麼是 AD-STC？它如何同時兼顧全局上下文與時間變化？**
A：AD-STC 是 Anchor-Delta Spatio-Temporal Compression 的縮寫，是 OmniScope 在視覺端採用的錨點-差值時空壓縮策略。它會保留錨點畫面以維持全局語義覆蓋，同時保留帶有時間變化的差值畫面來捕捉動態資訊。這彌補了現有影片標記壓縮方法常對所有增量幀套用相同策略、導致高壓縮比下全局語義流失的問題。

**Q6：OmniScope 如何處理音訊標記壓縮？每秒合併音訊標記的設計有什麼好處？**
A：OmniScope 在音訊端採用每秒雙邊軟匹配（per-second bipartite soft matching），在編碼器輸出的時間嵌入上對每秒內的冗餘音訊標記進行合併。這種做法能在降低冗餘的同時維持時間連續性，避免傳統音訊壓縮粒度過粗或受限於編碼器內部結構的缺點。由於它是訓練無需的，因此能靈活適應下游大型語言模型所需的各種壓縮比例。

**Q7：OmniScope 在哪些基準測試與模型規模上進行評估？主要趨勢為何？**
A：論文在四個音視訊基準測試上，針對 Qwen2.5-Omni 的 7B 與 3B 兩種模型規模進行驗證。結果顯示 OmniScope 在所有壓縮設定下都取得了最佳的平均準確率，在 45% 整體標記保留率時幾乎無損，而在更激進的 25% 保留率下仍展現出比所有競爭方法更強的穩健性。這些趨勢在不同模型規模上保持一致，顯示其方法具有良好的泛化性。

**Q8：在 25% 整體標記保留率下，OmniScope 的效率提升與準確率代價分別是多少？**
A：在 25% 整體標記保留率時，OmniScope 可達到最高 3.53 倍的預填充加速，並減少超過 15% 的 GPU 記憶體使用量。與此同時，平均準確率僅下降 0.35 分，顯示其在激進壓縮下仍維持極佳的準確率與效率權衡。這樣的表現對於需要長音視訊推論的應用來說非常具有實務價值。

**Q9：與 OmniZip 等基線相比，OmniScope 在不同壓縮比例下的表現如何？這說明了什麼？**
A：OmniScope 在所有壓縮比例下的平均表現都優於 OmniZip 等競爭方法，因為它避免了單向引導在跨模態顯著性不匹配時遺失關鍵線索的風險。無論是音訊引導視覺或視覺引導音訊，只要兩個模態的顯著高峰不一致，就可能造成答案關鍵線索被丟棄。這些一致的實驗結果驗證了模態解耦標記壓縮設計的優越性。

**Q10：OmniScope 在哪些實際應用場景中最有價值？它解決了什麼部署限制？**
A：OmniScope 特別適合影片問答、內容審核、即時互動以及邊緣裝置上的長音視訊理解等場景。這些應用常面臨長影片產生大量音訊標記與視覺標記的問題，導致預填充延遲過高與 GPU 記憶體不足。透過訓練無需的壓縮，OmniScope 能在不重新訓練模型的情況下降低延遲與記憶體佔用，使 OmniLLMs 更容易落地於資源受限環境。

**Q11：若要將 OmniScope 整合到影片問答或內容審核的產品管線中，應如何部署？**
A：可以在音訊與視覺編碼器完成編碼後、進入大型語言模型預填充前，插入 OmniScope 模組，並根據產品的延遲與品質目標調整模態專屬標記預算。由於它是訓練無需的，因此無需額外微調壓縮模組或語言模型即可直接上線。在內容審核等需要同時理解聲音與畫面的任務中，保留雙模態的關鍵線索能顯著提升判斷準確率。

**Q12：模態解耦標記壓縮對未來 OmniLLMs 與資源受限裝置的設計有何更廣泛影響？**
A：這項研究提示未來全模態模型應將顯著性估計視為模態專屬的問題，而非強制跨模態耦合。這樣的設計原則可擴展到更多模態，例如文字、深度或感測器訊號，並啟發更輕量化的行動與嵌入式架構。它也強調以查詢為條件的壓縮是一種通用且有效的推論最佳化方向，有助於推動多模態智慧在真實世界的大規模部署。

**Q13：OmniScope 有哪些作者已指出或可從設計中推論出的限制？**
A：OmniScope 目前主要聚焦於音訊與視覺兩種模態，尚未直接處理三種以上模態的聯合壓縮。其模態專屬標記預算的分配方式可能是基於啟發式規則，而非根據每筆輸入動態學習最適比例。此外，作為訓練無需方法，它在特定領域分佈上的適應能力可能不如經過端到端微調的方法。

**Q14：儘管採用模態解耦設計，OmniScope 在哪些情況下仍可能遺失重要線索？**
A：若答案關鍵線索在兩個模態中都非常稀疏，且同時落在各自顯著性分數較低的區域，則即使模態解耦也可能被剪除。在音訊端，如果某個極短但關鍵的聲音事件被包含在一秒的合併區間內，每秒合併可能會將其平滑掉。同樣地，若視覺錨點畫面未能涵蓋罕見但重要的全局場景資訊，模型回答的準確率仍可能下降。

**Q15：未來研究可以如何延伸 OmniScope？有哪些值得探索的方向？**
A：未來可以將 OmniScope 擴展到三種或更多模態，並引入可根據輸入內容與查詢動態調整的學習式預算分配機制。另一個方向是將標記壓縮與模型量化、網路剪枝或串流分塊技術結合，進一步提升長影片與高解析度輸入的推論效率。此外，也可以研究在保持大型語言模型凍結的前提下，訓練一個輕量的壓縮策略網路，以兼顧訓練無需的便利性與領域適應能力。

## 實務應用指南

### 適用場景

1. **即時音視訊客服與互動助理**  
   處理長時間直播、會議或客服錄影時，使用者常同時詢問「畫面中出現什麼」與「背景說了什麼」。OmniScope 可在保留關鍵視覺與聲學線索的前提下壓縮標記，降低延遲，適合對話式全模態助理。

2. **智慧監控與內容審核**  
   異常事件往往由「聲音」與「畫面」在不同時間點共同決定，例如玻璃破碎聲先出現、人影後晃動。單向引導容易遺失其中一側線索；模態解耦壓縮能同時保留兩種模態的關鍵時段，提升審核準確率。

3. **教育與線上學習影片問答**  
   針對長篇教學影片，學生提問可能涉及講者語音（概念解釋）與板書/投影片變化（公式或圖表）。OmniScope 可壓縮重複畫面與背景噪音，保留講解重點與視覺變化，支撐長影片問答系統。

4. **體育賽事與電競即時解說 / 裁判回放**  
   例如「哨聲後裁判打出什麼手勢」這類查詢，音訊顯著性與視覺顯著性出現在不同時間點。OmniScope 的模態獨立預算分配能避免以音導視或以視導音時遺失答案關鍵線索。

5. **智慧會議摘要與行動項目提取**  
   長會議錄影中大量時間是靜默或重複畫面。OmniScope 可壓縮冗餘音訊與視覺標記，保留發言片段與簡報切換，加速後續摘要與任務提取。

### 實作步驟建議

1. **環境建置與模型準備**
   - 從官方倉庫取得 OmniScope 程式碼，安裝相依套件。
   - 載入 Qwen2.5-Omni（7B 或 3B），確認影像編碼器與音訊編碼器輸出格式。

2. **音視訊前處理**
   - 將影片拆為視覺畫面序列，並擷取對應音訊串流。
   - 分別通過視覺編碼器與音訊編碼器，取得視覺標記與音訊標記。

3. **接入 OmniScope 壓縮模組**
   - 以查詢作為共享語義錨點，分別計算視覺標記與音訊標記對查詢的相關性分數。
   - 依整體標記保留率（如 45% 或 25%）配置模態專屬標記預算，避免音訊與視覺互相搶佔。

4. **視覺側：Anchor-Delta Spatio-Temporal Compression（AD-STC）**
   - 選取語義覆蓋廣泛的錨點幀，確保全局上下文不遺失。
   - 再根據時間變化與查詢相關性選取差值幀，保留動態事件。
   - 對非關鍵區域進行空間或時間剪枝。

5. **音訊側：每秒 Token Merging**
   - 在每秒時間區間內，對音訊編碼器的時間嵌入執行 bipartite soft matching。
   - 合併冗餘音訊標記，同時維持時間連續性，避免短事件邊界被過度模糊。

6. **壓縮比例與預算調校**
   - 保守上線：先使用 45% 整體標記保留率，此時平均準確率接近無損。
   - 激進加速：在延遲敏感場景嘗試 25% 保留率，預期可達約 3.53 倍預填充加速與 15% 以上 GPU 記憶體減少。

7. **評估與監控**
   - 在領域基準測試上量測平均準確率、預填充時間、GPU 記憶體佔用。
   - 特別關注跨模態顯著性不匹配案例，確認答案關鍵線索未被丟棄。

8. **部署與持續迭代**
   - 對長影片採用分段或串流壓縮，避免單段序列過長。
   - 建立降級機制：當查詢涉及細節辨識時，自動切換回較高保留率或原始標記。
   - 收集失敗案例，動態調整模態預算分配。

### 潛在風險與注意事項

- **跨模態顯著性不匹配導致資訊遺失**  
  不要讓音訊分數直接決定視覺保留，也不要反過來以視覺引導音訊。應堅持「共享查詢、獨立顯著性」原則。

- **過度壓縮遺失答案關鍵線索**  
  25% 保留率雖然加速顯著，但對需要細粒度辨識的任務可能不足。建議保留可切換至 45% 或原始標記的後備方案。

- **視覺全局上下文被忽略**  
  若只保留變化大的差值幀，可能遺失整體場景資訊。AD-STC 的錨點幀選擇必須確保語義覆蓋，而非僅看幀間差異。

- **音訊時間連續性受損**  
  每秒合併雖降低冗餘，但對語音轉錄或短促事件（如敲門、警報）可能模糊邊界。語音為主的任務應審慎調整合併粒度。

- **查詢品質影響預算分配**  
  相關性分數高度依賴查詢。若查詢模糊或與影片內容關聯低，可能導致預算錯配，建議結合查詢改寫或意圖分類。

- **模型架構相依性**  
  OmniScope 目前針對 Qwen2.5-Omni 的時間視窗交錯機制設計。移植到其他全模態大型語言模型時，需重新對齊編碼器輸出與注意力層結構。

- **平均準確率無法代表所有場景**  
  基準測試的平均分數可能掩蓋少數關鍵事件遺失。上線前應針對高風險案例進行紅隊測試。

---

### 與其他技術的整合建議

- **KV Cache 壓縮與量化**  
  OmniScope 減少輸入標記數量，可再搭配 H2O、SnapKV 等 KV cache 壓縮技術，或權重量化，進一步降低記憶體與延遲。

- **串流與分段處理**  
  對極長影片，可將影片切分為數秒至數十秒的視窗，每個視窗獨立執行 OmniScope，再將壓縮後標記送入語言模型，避免上下文長度爆炸。

- **檢索增強生成（RAG）**  
  先以 OmniScope 壓縮長影片，再將高相關性的音視訊片段建立索引存入向量庫。後續查詢可先檢索關鍵片段，再進行精細推理。

- **模型量化與結構化剪枝**  
  OmniScope 與權重量化、網路剪枝互補：前者降低序列長度，後者降低單次運算成本，適合邊緣裝置部署。

- **可解釋性與審核工具**  
  將保留的視覺幀與音訊時段視覺化，讓營運與審核人員看到模型「看了什麼、聽了什麼」，提升信任度並便於除錯。

- **自動擴展與負載平衡**  
  根據壓縮後的標記數量動態選擇 GPU 實例規格，並在高峰時啟用較高壓縮率以維持服務水準。

---

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先理解全模態大型語言模型如何把影片與聲音轉成「標記」，以及「同一個問題在音訊和畫面上的重要時刻可能不同」這個直覺。把 OmniScope 想像成「各管各的精簡筆記」：查詢是大家共同的題目，但音訊和視覺各自決定要保留哪些重點。不必一開始就深入注意力數學，先看圖 1 的範例與實驗結果，會更容易掌握核心概念。

- **AI 工程師**  
  重點關注實作細節：如何計算查詢條件化的相關性分數、AD-STC 中錨點幀與差值幀的選擇邏輯，以及音訊側每秒 bipartite soft matching 的具體實現。評估時不要只看準確率，也要同時量測預填充延遲與 GPU 記憶體。此外，需特別注意與 Qwen2.5-Omni 的編碼器輸出、時間視窗交錯機制對接，確保壓縮後的標記序列能正確餵入語言模型。

- **研究人員**  
  本文的核心貢獻在於挑戰「單向跨模態引導」的既有假設，提出「共享查詢、獨立顯著性」的設計原則。可進一步探索動態模態預算分配、壓縮對跨視窗注意力分佈的理論影響、以及其他模態組合（如音訊加深度圖、多視角影片）的適用性。此外，壓縮後模型的可解釋性與錯誤分析也是值得延伸的方向。

- **產品經理**  
  請聚焦成本效益：在 25% 整體標記保留率下，OmniScope 可帶來約 3.53 倍預填充加速與超過 15% 的 GPU 記憶體減少，平均準確率僅下降 0.35 點。這對需要即時、長影片理解的產品非常有吸引力。風險在於高壓縮可能遺失關鍵線索，建議上線時從 45% 保留率開始，並保留原始標記的降級方案，以平衡使用者體驗與成本。
