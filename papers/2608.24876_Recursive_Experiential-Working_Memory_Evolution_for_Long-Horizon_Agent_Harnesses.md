## ⚡ TL;DR

長程任務中，智能體因歷史紀錄膨脹而迷失任務狀態，導致技能調用錯位，遞迴自我改進困難。
提出Recuris，以工作記憶追蹤驗證任務狀態、經驗記憶選擇技能，元智能體依軌跡局部更新技能記憶。
跨四基準與十模型，35/37配對成功率提升，最長任務進步32.2百分點，常見失敗降低八成。

## 摘要翻譯

遞迴自我改進（Recursive Self-Improvement, RSI）在長程任務（long-horizon tasks）中仍然困難，因為不斷增長的歷史會遮蔽任務狀態（task state），並使技能調用（skill invocation）失準。我們提出 Recuris，一個用於長程智能體框架（agent harnesses）的遞迴經驗–工作記憶架構（Recursive Experiential-Working Memory architecture），其中工作記憶（Working Memory, WM）追蹤任務進度（task progress），並引導從經驗記憶（Experiential Memory, EM）中進行技能選擇（skill selection），使技能使用（skill use）奠基於當前需求，而非完整歷史（full history）。這種經驗記憶–工作記憶耦合（EM–WM coupling）也將執行（execution）轉化為結構化證據（structured evidence），將失敗局部化（localized failures）至特定記憶元件（memory components）。跨任務（cross-task）地，一個固定的元智能體（Meta-Agent）將該證據轉化為針對技能記憶（Skill Memory）的局部化、驗證閘控更新（validation-gated updates），重塑執行並產生新證據，形成一個有界遞迴記憶演化迴路（bounded recursive memory-evolution loop）。橫跨四個長程基準測試（benchmarks）與十個模型，Recuris 在 37 個完成評估的模型–基準配對（model-benchmark pairs）中，於 35 個提升了任務成功率（task success），並使前沿模型（frontier models）達到最先進水準（SOTA-level）的任務成功率：在 tau-bench 上，它為 GPT-5.6 Sol 增加 17.8 百分點（points），為 Claude Opus 5 增加 15.6 百分點，使 Opus 5 達到 87.9%；在 SkillFlow 上，則為 Qwen3.6-27B/35B 分別增加 16.6/13.5 百分點。隨著互動時程（interaction horizon）增長，優勢進一步擴大，在最長的任務上達到 +32.2 百分點，而常見長程任務失敗（common long-horizon failures）則下降高達 80%。這些結果將遞迴演化的記憶定位為 RSI 的可擴展基礎（scalable foundation），使智能體（agents）能夠持續將累積經驗（accumulated experience）轉化為越來越有效的長程行為（long-horizon behavior）。程式碼：https://github.com/Gen-Verse/Recuris

### 核心貢獻（3～5點）
- 提出 Recuris，一個結合經驗記憶（EM）與工作記憶（WM）的遞迴架構，讓技能選擇奠基於當前任務狀態，而非冗長的完整歷史。
- 將執行過程轉化為結構化證據，支援基於追蹤的失敗定位（Trace-Based Failure Localization），並針對特定記憶元件進行修補（Component-Specific Patching）。
- 透過固定的元智能體（Meta-Agent）實現跨任務的驗證閘控更新（Validation-Gated Patch Admission），形成有界遞迴記憶演化迴路。
- 在四個長程基準測試與十個模型上驗證，於 37 個模型–基準配對中的 35 個提升任務成功率，並在 tau-bench 與 SkillFlow 上將多個前沿模型推至最先進水準。
- 證明遞迴演化的記憶是 RSI 的可擴展基礎，互動時程越長優勢越顯著，最長任務提升達 32.2 百分點。

### 適合對象
本論文最適合從事大型語言模型（LLM）智能體、長程任務規劃、遞迴自我改進（RSI）與記憶架構設計的研究人員與工程師閱讀；對於關注智能體如何在測試時適應（Test-Time Adaptation）、跨任務遷移（transfer across tasks）以及可擴展自我改進系統的讀者亦具高度參考價值。

## 深度分析

#### 方法論解析

Recuris 的核心貢獻在於將 **Experiential Memory（EM，經驗記憶）** 與 **Working Memory（WM，工作記憶）** 緊密耦合，並在此基礎上建立一個 **bounded recursive memory evolution（有界遞迴記憶演化）** 迴路。整體方法可拆分為「任務內（within-task）」與「跨任務（cross-task）」兩個層次。

在任務內層次，Recuris 不再讓 **agent harness（智能體框架）** 直接從不斷增長的完整對話歷史（full history）中檢索技能，而是維護一份結構化的 **Structured Working State（結構化工作狀態）**。這份狀態緊湊地記錄當前的 **task state（任務狀態）**、已完成的子目標、尚未解決的需求以及相關約束。基於此狀態，**State-Grounded Skill Invocation（基於狀態的技能調用）** 機制從 EM 中選出最貼近當前需求的技能，而非被初始指令或過時資訊牽著走。技能執行後，環境回饋會經過驗證，轉化為 **Evidence-Grounded State Update（基於證據的狀態更新）**，進而更新 WM。這形成了一個封閉迴路：Task State → Skill Selection → Execution Feedback → Updated Task State。此 **EM–WM coupling（經驗記憶–工作記憶耦合）** 的關鍵在於把「現在需要什麼」與「過去累積了什麼經驗」分離，讓 **skill invocation（技能調用）** 始終錨定在當前任務進度（task progress），而非被完整歷史中的雜訊稀釋。

在跨任務層次，Recuris 利用上述結構化執行過程所產生的 **structured evidence（結構化證據）** 來驅動記憶演化。傳統方法往往只從最終成功或失敗學習，難以判斷問題究竟出在 **Skill Memory（技能記憶）** 的內容、WM 的狀態表示、技能選擇策略，還是進度驗證器。Recuris 則透過 **Trace-Based Failure Localization（基於追蹤的失敗定位）**，將失敗軌跡（trace）對應到特定的 **memory components（記憶元件）**；接著進行 **Component-Specific Patching（元件特定修補）**，只修改被歸因的元件，而非重寫整個記憶系統。每次修補都必須通過 **Validation-Gated Patch Admission（驗證閘控修補准入）**：候選修補會先在保留任務（held-out tasks）上驗證，只有確實提升或至少不損害表現才會被納入。這個 **validation-gated updates（驗證閘控更新）** 機制與有限的修補範圍共同確保了 **Bounded Recursive Evolution（有界遞迴演化）**，避免無限制自我修改導致的漂移或災難性遺忘。此外，Recuris 還提供 **Test-Time Adaptation Mode（測試時適應模式）**，允許在孤立的測試任務上持續調整 **Skill Memory**。

總結來說，Recuris 的方法論可視為一條因果鏈：EM–WM Coupling → Structured Evidence → Failure Localization → Targeted Memory Evolution。這條鏈把執行過程轉化為可解釋、可定位、可修復的證據，從而讓遞迴自我改進（**Recursive self-improvement, RSI，遞迴自我改進**）在長程任務（**long-horizon tasks，長程任務**）中變得可行且可控。

#### 實驗數據解讀

論文在四個長程基準測試（**benchmark，基準測試**）與十個模型上進行評估，涵蓋了 37 個完整的 **model-benchmark pairs（模型–基準配對）**，其中 Recuris 在 35 個配對上提升了 **task success（任務成功率）**。這樣廣泛的覆蓋度本身就說明該架構具有相當強的泛用性，而非僅在單一設定下有效。

具體數據方面，在 **tau-bench** 上，Recuris 為 GPT-5.6 Sol 帶來 +17.8 **points（百分點）** 的提升，為 Claude Opus 5 帶來 +15.6 百分點，使 Opus 5 達到 87.9% 的 **success rate（成功率）**，已接近或達到該基準的 **SOTA-level（最先進水準）**。在 **SkillFlow** 上，Qwen3.6-27B 與 Qwen3.6-35B 分別提升 +16.6 與 +13.5 百分點。值得注意的是，這些增益不僅出現在 **frontier models（前沿模型）**，也出現在規模較小的開放模型上，顯示 Recuris 的記憶機制能夠彌補模型本身在長程追蹤與技能選擇上的不足。

更關鍵的趨勢是：隨著 **interaction horizon（互動時程）** 拉長，Recuris 的優勢明顯擴大。在最長的任務上，提升幅度達到 +32.2 百分點，而常見的長程失敗（**common long-horizon failures，常見長程任務失敗**）最高減少 80%。這強烈支持論文的核心假設：當歷史越長，傳統基於完整歷史的檢索越容易迷失，而 WM 所提供的緊湊任務狀態與狀態導向的技能調用就越有價值。換句話說，Recuris 的收益並非來自於更強大的基礎模型，而是來自於更有效地組織與調用 **accumulated experience（累積經驗）**。

至於兩個未提升的配對，可能原因包括基線已接近天花板、該領域的 **critical memory component（關鍵記憶元件）** 與 Recuris 預設結構不完全匹配，或保留任務數量不足以穩定驗證修補。這也提示未來需要針對不同領域自動調整記憶元件的設計。

#### 與現有研究的比較

在定位上，Recuris 介於三條研究線之間：**Experiential Memory and Agent Skills（經驗記憶與智能體技能）**、**Working Memory for LLM Agents（大型語言模型智能體的工作記憶）**，以及 **Recursive Self-Improvement of LLM Agents（大型語言模型智能體的遞迴自我改進）**。它同時改進了這三條線的核心瓶頸。

相較於現有的 **experiential-memory（經驗記憶）** 方法，Recuris 的差異在於檢索時機與依據。傳統方法通常根據初始指令或完整互動歷史進行檢索，但隨著執行推進，初始指令可能已無法反映當前問題，而完整歷史則混雜了已完成步驟、未解決需求與執行雜訊。Recuris 改為在執行事件發生時，依據 WM 中的當前狀態進行檢索，從根本上解決了「歷史越長、檢索越不可靠」的問題。

相較於現有的記憶演化或自我改進方法，Recuris 的優勢在於「局部化」與「閘控」。許多先前做法從單一任務的最終結果推論如何重寫整個記憶，這容易導致粗粒度更新、災難性遺忘，或難以判斷問題根源。Recuris 透過結構化軌跡將失敗定位到特定記憶元件，只對該元件進行修補，並以保留任務上的表現作為准入條件。這種 **validation-gated updates（驗證閘控更新）** 大幅降低了遞迴更新過程中錯誤累積的風險。

然而，Recuris 仍存在若干限制。首先，**Meta-Agent（元智能體）** 是固定的，其自身的歸因與修補能力決定了演化的上限；若 Meta-Agent 對某些失敗模式判斷錯誤，後續修補也可能偏離。其次，方法依賴預先定義的記憶元件結構與驗證器，對於元件設計不佳或難以取得可靠環境回饋的任務，效果可能受限。第三，**validation（驗證）** 需要額外的保留任務與計算資源，在資料稀少的場景中可能難以實施。最後，雖然稱為遞迴自我改進，但目前的「有界」設計更像是一種受控的記憶優化迴路，距離完全自主、無限制的 RSI 仍有一段距離。

#### 可重現性評估

論文已將程式碼釋出於 https://github.com/Gen-Verse/Recuris，這是提升可重現性的重要基礎。所使用的 **tau-bench** 與 **SkillFlow** 等基準測試若為公開資料集，則其他研究者原則上可復現主要實驗。實驗涉及的前沿模型（如 Claude Opus 5、GPT-5.6 Sol）與開放權重模型（如 Qwen3.6 系列）可透過 API 或開源權重取得，但執行成本與上下文長度（**context**）需求可能相當高，論文附錄 D 對此有所說明。

不過，可重現性也取決於釋出內容的完整度。理想的釋出應包含：Meta-Agent 的完整提示（prompt）、記憶元件的結構定義、驗證器實作、各基準的訓練/驗證/測試切分（splits）、統計檢定流程（附錄 A），以及消融實驗（附錄 B）的具體設定。若這些細節已在倉儲或完整論文中提供，則可重現性相當高；若僅釋出高層框架，則其他團隊可能需要大量試誤才能逼近論文結果。此外，由於部分實驗依賴商業 API，隨模型版本更新，原始數據可能難以完全復現，這是當前 LLM agent 研究的共同挑戰。

#### 未來研究方向

Recuris 為遞迴記憶演化開闢了多條後續研究路徑：

1. **自動化記憶元件與驗證器學習**：目前 WM、EM 與驗證器的結構仍由人類設計。未來可探索讓 Meta-Agent 或另一層學習機制自動發現最適合任務的記憶元件與驗證規則，降低對領域專家的依賴。

2. **層級式工作記憶（Hierarchical WM）**：對於極長或極複雜的任務，單層 WM 可能仍不足以追蹤多層子目標。引入層級式或遞迴式 WM，可進一步提升在超長 **interaction horizon** 下的穩定性。

3. **線上連續學習**：目前的跨任務演化仍區分訓練與測試階段。未來可發展真正的線上版本，使智能體在執行過程中持續更新記憶，同時維持 **validation-gated updates** 以避免漂移。

4. **多智能體 Recuris 架構**：讓多個智能體共享 EM，但各自維護獨立 WM，並透過協作產生更豐富的結構化證據，可能進一步放大累積經驗的價值。

5. **理論收斂與安全分析**：對 **bounded recursive memory evolution** 建立收斂性、樣本複雜度或錯誤傳播界限，並研究如何防止遞迴更新中的獎勵駭取（reward hacking）或能力退化，是邁向可信 RSI 的關鍵。

6. **跨領域遷移與記憶整合**：論文已初步展示跨任務與跨模型遷移。未來可探討如何將 Recuris 與外部知識庫、長期情節記憶（episodic memory）整合，並在領域轉移時進行適應。

7. **測試時計算與自適應深度**：讓 Recuris 根據任務難度動態決定遞迴演化的深度與修補強度，可在計算成本與效能之間取得更佳平衡。

總體而言，Recuris 透過把經驗記憶錨定在工作記憶、並以結構化證據驅動有界的記憶演化，為長程智能體的遞迴自我改進提供了一個可擴展且可驗證的基礎。後續研究若能解決自動化元件設計、線上適應與安全保證等問題，將有機會把這一架構推向更廣泛的實際應用。

## 論文問答

**Q1【背景與動機】：遞迴自我改進（RSI）在長程任務中面臨什麼核心挑戰？**  
A：在長程任務中，互動歷史不斷增長，導致任務狀態被遮蔽，技能調用與當前需求逐漸錯位。傳統方法雖然能累積經驗，但記憶機制本身大致固定，無法隨執行過程持續對齊經驗與當前狀態。因此，RSI 的關鍵障礙不在於缺乏經驗，而在於缺乏一個能持續反映當前任務進度的緊湊且可靠的狀態表徵。

**Q2【背景與動機】：現有的經驗記憶方法為何在長程任務中失效？**  
A：現有方法通常根據初始指令或完整互動歷史來檢索技能，但隨著執行推進，初始指令往往已無法反映當前問題。同時，不斷增長的對話脈絡混合了過時資訊、已完成步驟、未解決需求與執行雜訊，使檢索變得不可靠。這種缺乏當前任務狀態的檢索方式，最終導致技能調用逐漸偏離真正的執行需求。

**Q3【背景與動機】：為何工作記憶（WM）被視為解決上述問題的關鍵？**  
A：工作記憶能持續追蹤智能體的當前進度與未解決目標，並據此從經驗記憶中選擇最適合的技能。技能執行後，環境回饋會驗證進度並更新工作記憶，形成「任務狀態→技能選擇→執行回饋→更新任務狀態」的封閉迴路。這種狀態化的記憶控制層讓技能調用奠基於當前任務，而非整段互動歷史。

**Q4【方法與創新】：Recuris 的核心架構是什麼，EM 與 WM 在單一任務內如何互動？**  
A：Recuris 是一種遞迴的經驗–工作記憶架構，其中工作記憶負責維護經過驗證的任務狀態，並引導經驗記憶中的技能選擇。當環境回饋到達時，驗證器會將其轉化為結構化的狀態更新，而非單純信任對話內容。這種 EM–WM 耦合確保了技能使用始終以當前任務需求為依據，並為後續的記憶演化提供了結構化的執行證據。

**Q5【方法與創新】：Recuris 與先前記憶型智能體框架相比，有哪些關鍵設計轉變？**  
A：在使用記憶的方式上，先前框架是針對不斷增長的對話歷史進行檢索，容易遺失未解決目標；Recuris 則在執行事件發生時檢索，並以檢查器將環境回應轉為經過驗證的狀態更新。在記憶演化方面，先前方法常根據單一任務結果重寫整個記憶，Recuris 則讀取結構化軌跡，將失敗歸因到特定記憶元件，只修補相關元件，並透過保留任務的驗證閘控才准許修補納入。這兩項轉變使記憶的使用與演化都更為精準且可解釋。

**Q6【方法與創新】：Recuris 如何將執行過程轉化為結構化證據，並促成目標式記憶演化？**  
A：EM–WM 耦合明確連結了任務狀態、被選技能、執行動作與執行結果，使每次執行都成為關於記憶如何影響行為的結構化證據。當任務失敗時，固定的元智能體（Meta-Agent）可以根據軌跡將失敗局部化到特定記憶元件，例如技能描述、狀態追蹤或驗證規則。接著它只對該元件進行修補，並在保留集上驗證修補效果，從而形成一個有界且持續遞迴的記憶演化迴路。

**Q7【實驗與結果】：實驗使用了哪些基準測試與模型，主要結果為何？**  
A：研究在四個長程基準測試與十個模型上進行評估，Recuris 在 37 個完成的模型–基準配對中改善了 35 個的任務成功率。具體而言，在 tau-bench 上，GPT-5.6 Sol 提升 17.8 百分點，Claude Opus 5 提升 15.6 百分點並達到 87.9%；在 SkillFlow 上，Qwen3.6-27B 與 35B 分別提升 16.6 與 13.5 百分點。隨著互動時程拉長，優勢還擴大到最長任務的 +32.2 百分點，常見長程失敗更減少高達 80%。

**Q8【實驗與結果】：Recuris 在互動時程增長時的表現如何？**  
A：Recuris 的優勢隨著互動時程拉長而擴大，在最長的任務上可帶來超過 30 百分點的增益。這是因為工作記憶持續維護當前任務狀態，避免智能體在冗長歷史中迷失未解決目標。同時，基於狀態的技能調用更準確且更有效率，使長程執行保持穩定可靠。

**Q9【實驗與結果】：哪些消融實驗與分析支持 Recuris 的設計選擇？**  
A：實驗顯示結構化軌跡能顯著改善失敗定位，遞迴演化在保留集上帶來一致的增益，且兩種不同的 Meta-Agent 實作最終趨於一致。驗證閘控修補准入機制能保護既有能力，避免修補破壞已學會的技能；演化後的技能記憶還能跨任務與跨模型遷移。此外，不同領域的關鍵記憶元件各不相同，進一步說明元件特定修補的必要性。

**Q10【應用與影響】：Recuris 在哪些實際應用場景中最具價值？**  
A：Recuris 特別適合需要多步推理、目標持續演變且需反覆與環境互動的場景，例如企業流程自動化、客戶服務對話系統、複雜工具調用與自主程式除錯。在這些場景中，任務狀態會隨著新資訊不斷改變，智能體必須持續追蹤未完成的子目標並調用正確技能。透過工作記憶與經驗記憶的耦合，Recuris 能將累積經驗轉化為越來越有效的長程行為。

**Q11【應用與影響】：部署 Recuris 時需要考慮哪些產品化議題？**  
A：首先必須確保驗證閘控與有界遞迴機制運作良好，以防止未受控的自我修改或能力退化。其次，修補應限於被定位的記憶元件，並持續監控保留集表現，避免災難性遺忘。此外，結構化軌跡的品質、驗證器的可靠性以及遞迴演化帶來的計算與上下文成本，都是在實際產品中需要權衡的關鍵因素。

**Q12【應用與影響】：Recuris 對遞迴自我改進與智能體框架領域可能帶來什麼影響？**  
A：Recuris 將「遞迴演化的記憶」定位為 RSI 的可擴展基礎，顯示智能體框架不僅能使用記憶，還能讓記憶機制本身隨經驗改進。這促使研究焦點從固定的工具與提示設計，轉向能自我轉化的長程行為架構。未來這種 EM–WM 耦合與元件特定演化的思路，可能啟發更多具備持續學習與自我修正能力的智能體系統。

**Q13【限制與未來】：Recuris 有哪些已知的限制或約束？**  
A：Recuris 依賴結構化執行軌跡與可靠的環境驗證器，若回饋模糊或驗證錯誤，工作記憶的更新就會失準。Meta-Agent 的失敗定位與修補生成能力也受限於底層語言模型的推理水準，複雜或多重交互的失敗可能難以完全局部化。此外，驗證閘控與遞迴演化會增加計算開銷，且目前結果主要來自特定基準測試，對開放式真實任務的泛化性仍需驗證。

**Q14【限制與未來】：Recuris 在哪些失敗案例中仍可能表現不佳？**  
A：當環境回饋含糊不清或驗證器本身出錯時，基於證據的狀態更新可能導致錯誤的任務狀態，進而選錯技能。若失敗源自多個記憶元件的交互作用，單一元件修補可能無法徹底解決問題。此外，在與訓練領域差異極大的新任務中，關鍵記憶元件可能不同，導致局部化與遷移效果下降；測試時適應預算有限的孤立任務也可能無法充分演化。

**Q15【限制與未來】：這項工作指出了哪些未來研究方向？**  
A：未來可將此架構擴展到開放式終身學習，管理更大規模的技能記憶庫，並結合人類回饋強化驗證閘控。另一方面，可提升 Meta-Agent 的失敗歸因推理能力，降低遞迴演化的計算成本，並探索更強大的世界模型來輔助狀態驗證。此外，將 Recuris 應用於多智能體協作、跨模態長程任務，以及與外部知識庫持續整合，也是值得深入的方向。

## 適用場景

1. **企業多步驟流程自動化（IT／HR／CRM）**  
   例如員工入職流程：開帳號、申請設備、設定權限、通知主管、建立訓練計畫。Recuris 的 **工作記憶（WM）** 可持續追蹤「還有哪些子任務未完成」，並從 **經驗記憶（EM）** 調用對應技能（如「建立 AD 帳號」、「寄送歡迎信」），避免在長對話中遺漏步驟。

2. **長對話客戶服務智能體**  
   當客戶歷經數十輪互動、問題從「退貨」轉為「換貨再補差價」時，傳統基於 **完整歷史** 的檢索容易抓錯意圖。Recuris 透過 **基於狀態的技能調用**，讓智能體依據當前 **任務狀態** 而非整段對話來選擇技能，降低答非所問與重複確認。

3. **軟體工程長程代理（除錯、重構、跨檔案修改）**  
   在需要多次編輯、測試、回滾的開發任務中，WM 可記錄「已修改檔案、待修復測試、已知相依風險」，EM 提供可重複使用的重構或測試修復技能。執行後由環境回饋（編譯結果、測試輸出）進行 **基於證據的狀態更新**，避免幻覺式修改。

4. **金融合規與交易作業稽核**  
   例如 KYC 審查或交易異常調查，需要依序比對多份文件、查詢外部資料庫、記錄每步結論。Recuris 的 **結構化執行軌跡** 能將失敗歸因到特定 **記憶元件**，再由 **元智能體** 針對性地修補技能，持續提升合規準確率。

5. **醫療照護協調（非診斷性行政流程）**  
   如術前準備排程：預約檢查、確認保險、提醒禁食、安排交通。長程互動中 WM 確保每個前置條件都被標記完成，EM 提供標準化協調技能，並透過 **驗證閘控更新** 防止錯誤技能被納入未來流程。

## 實作前置條件

### 資料準備
- **任務軌跡資料**：至少數百到數千筆帶有最終成敗標記的 **執行軌跡**，愈多長程案例愈能發揮 Recuris 優勢。
- **技能庫雛形**：初步的 **技能記憶**，包含技能描述、輸入輸出規格、適用情境與範例，作為 EM 的種子。
- **驗證資料集**：區分訓練、保留驗證與測試任務，用於 **驗證閘控修補准入**，避免過擬合。
- **環境回饋介面**：能回傳結構化結果（如 API 狀態碼、資料庫變更、測試報告），以支援 **基於證據的狀態更新**。

### 運算資源
- **LLM 推理預算**：每個任務需多次調用模型（WM 更新、技能選擇、執行、驗證），長程任務成本會隨互動時程增加。
- **元智能體運算**：跨任務演化階段需額外模型呼叫來產生與評估修補，建議預留獨立批次運算資源。
- **評估與監控基礎設施**：需能重複執行任務、比較成功率、記錄延遲與 token 消耗。

### 技能與團隊前提
- 熟悉 **智能體框架** 設計與提示工程。
- 具備將業務流程拆解為可驗證子任務的能力。
- 能撰寫可靠的 **驗證函式** 或檢查器（checker），因為 Recuris 的效果高度依賴執行回饋的正確性。
- 建議有 MLOps／LLMOps 經驗，以便管理 **記憶演化迴路** 與版本控制。

## 實作步驟建議

1. **建立基線框架與任務拆解**  
   先以現有 **智能體框架** 跑通目標任務，取得基線 **成功率**。將每個任務拆解為可觀察、可驗證的步驟，並定義「完成」與「失敗」的客觀標準。

2. **設計結構化工作狀態（Structured Working State）**  
   為 WM 設計輕量但完整的狀態格式，例如：當前目標、已完成步驟、待處理需求、已知風險、最後驗證結果。狀態欄位應與業務流程一對應，避免過度冗長。

3. **建構經驗記憶與基於狀態的技能調用**  
   將既有技能或 SOP 寫入 **技能記憶**，並設計檢索機制：以 WM 中的當前 **任務狀態** 作為查詢，而非完整對話歷史。加入技能匹配分數與適用條件，減少誤調用。

4. **實作基於證據的狀態更新**  
   每次技能執行後，由環境回饋驅動 WM 更新。務必讓檢查器輸出結構化證據（例如「步驟 A 成功：回傳訂單 ID 123」），而不是讓模型自由生成狀態。

5. **加入追蹤與失敗定位機制**  
   記錄每回合的「WM 狀態 → 選取技能 → 執行動作 → 環境回饋 → 更新後狀態」。當任務失敗時，利用這份 **結構化證據** 判斷失敗來自 WM、EM、技能調用或驗證器。

6. **部署元智能體與驗證閘控**  
   讓固定 **元智能體** 讀取失敗軌跡，針對特定 **記憶元件** 產生修補（patch）。每個修補必須在保留驗證集上通過成功率門檻，才能被納入 **技能記憶**，形成 **有界遞迴記憶演化**。

7. **啟用測試時適應與持續監控**  
   上線後開啟 **測試時適應模式**，讓系統在面對新任務時仍能局部更新記憶。同時監控常見長程失敗類型、token 成本與延遲，定期將高品質軌跡回饋給元智能體。

## 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **過擬合訓練任務** | 元智能體產生的修補可能在訓練任務上有效，卻損害未見任務表現。 | 嚴格執行 **驗證閘控修補准入**，保留獨立驗證集，並監控 **保留集增益**。 |
| **修補數量爆炸** | 持續演化可能導致技能記憶膨脹、互相衝突。 | 設定修補數量上限與相似度去重；定期進行 **消融實驗** 清理無效技能。 |
| **驗證器錯誤傳播** | 若檢查器本身有 bug，會產生錯誤的 **結構化證據**，誤導 WM 更新與後續修補。 | 對關鍵驗證邏輯加強單元測試；引入人工抽樣審查與異常偵測。 |
| **延遲與成本上升** | 長程任務加上多次模型呼叫與驗證，可能顯著增加延遲與費用。 | 對 WM 狀態與技能檢索做快取；在關鍵節點才觸發完整驗證與修補。 |
| **跨模型遷移限制** | 論文顯示 **技能記憶** 可跨模型遷移，但不同模型對提示格式與狀態欄位敏感度不同。 | 在目標模型上重新評估並微調技能描述與範例，不要直接照搬。 |
| **安全與權限風險** | 自動修補可能讓智能體學到繞過授權或產生不當輸出的技能。 | 在閘控中加入安全檢查與人工核准；對高風險動作保留人機協同確認。 |

## 與其他技術的整合建議

- **與 RAG 系統整合**：可將 Recuris 的 EM 視為「程序性記憶」，與傳統 RAG 的「事實性知識」互補。RAG 負責檢索領域文件，EM 負責提供已驗證的多步驟技能。
- **與現有 API／ERP／CRM 整合**：將企業系統包裝為可驗證的工具，讓環境回饋直接來自真實 API 回應，強化 **基於證據的狀態更新**。
- **與 LangChain、AutoGen、OpenAI Agents SDK 等框架整合**：Recuris 可作為這些框架之上的「記憶控制層」，負責 WM 狀態管理與技能選擇，底層仍使用既有工具呼叫機制。
- **與可觀測性平台整合**：將結構化軌跡匯出至 LangSmith、Weights & Biases 或自架追蹤系統，方便進行 **基於追蹤的失敗定位** 與人工審查。
- **與評估平台整合**：建立自動化回歸測試，讓每次記憶演化後都能快速測量 **任務成功率** 與常見長程失敗下降幅度。

## 給不同背景讀者的閱讀建議

**初學者**：建議先從「工作記憶」與「經驗記憶」的類比開始理解——把工作記憶想成待辦清單，經驗記憶則是過去學會的食譜；Recuris 的核心就是讓智能體依據當前待辦事項選對食譜，並在失敗後只修改有問題的那一部分，而不是整本食譜重寫。閱讀時可跳過數學細節，專注第 2.1、2.2 節與案例研究。

**AI 工程師**：請重點關注 **EM–WM 耦合** 的實作細節（第 2.2 節）、**驗證閘控修補准入**（第 2.3.3 節）以及 **測試時適應模式**（第 2.3.5 節）。這些是將論文轉為產品時最關鍵的工程決策，建議同時參考附錄 B 的框架消融實驗，了解增益來源。

**研究人員**：建議深入閱讀第 2.3 節的 **有界遞迴記憶演化** 與第 3.4 節的分析，特別是 **結構化軌跡如何改善失敗定位**、**跨任務與跨模型遷移** 的證據。這些結果對於理解遞迴自我改進（RSI）的穩定性與可擴展性具有重要意義。

**產品經理**：請聚焦第 1 節的問題陳述、第 3.2 節的整體成效，以及各領域案例研究。關鍵 takeaway 是 Recuris 能將長程任務成功率顯著提升，並隨互動時程拉長而優勢擴大；在規劃產品路線圖時，應優先投資於可驗證的業務流程拆解與高品質驗證資料建設。
