## ⚡ TL;DR

電腦使用代理在 GUI 與工具混合動作空間中，常無法判斷最佳切換時機，導致執行路徑不佳。
本文提出 ToolCUA，透過交錯軌跡擴展與分階段強化學習，學習最佳 GUI-工具路徑選擇。
OSWorld-MCP達46.85%準確率，較基準提升約66%，比純GUI高3.9點。

## 摘要翻譯

電腦使用代理（CUA）可同時透過原子化 GUI 動作（例如點擊與輸入）以及高階工具呼叫（例如基於 API 的檔案操作）來執行動作，但這種混合動作空間常令其難以抉擇應繼續採用 GUI 動作或切換至工具，導致次佳的執行路徑。此困難源自於高品質交錯式 GUI-工具軌跡的稀缺、收集真實工具軌跡的高成本與脆弱性，以及缺乏 GUI-工具路徑選擇的軌跡層級監督。在本文中，我們提出 ToolCUA，一個透過分階段訓練範式學習最佳 GUI-工具路徑選擇的端到端代理。我們首先提出交錯式 GUI-工具軌跡規模化流程，重新利用豐富的靜態 GUI 軌跡，並合成一個基於實證的工具函式庫，使我們能在無需人工工程或真實工具軌跡收集的情況下產生多樣化的 GUI-工具軌跡。接著，我們執行工具引導式 GUI 拒絕採樣微調，結合預熱式監督微調（SFT）與單輪強化學習（RL），以改善在關鍵 GUI-工具切換決策點的決策品質。最後，我們在高擬真 GUI-工具環境中以線上代理式強化學習最佳化 ToolCUA，並透過工具效率路徑獎勵引導，鼓勵適當的工具使用與更短的執行路徑。在 OSWorld-MCP 上的實驗顯示，ToolCUA 達到 46.85% 的準確率，相較基準模型帶來約 66% 的相對改進幅度，在同等規模的模型中達到了新的最先進技術（SOTA）水準。相較於純 GUI 設定亦提升了 3.9%，證明了有效的 GUI-工具編排。實驗結果進一步顯示，在混合動作空間中進行訓練為真實世界數位代理提出了一個有前景的訓練範式。開源連結：https://x-plug.github.io/ToolCUA/

### 核心貢獻（3～5點）
- 提出 **ToolCUA**，一個透過分階段訓練範式學習最佳 GUI-工具路徑選擇的端到端代理，解決混合動作空間下切換決策的難題。
- 設計**交錯式 GUI-工具軌跡規模化流程**，重新利用豐富的靜態 GUI 軌跡並合成基於實證的工具函式庫，免除人工工程與真實工具軌跡收集的需求。
- 引入**工具引導式 GUI 拒絕採樣微調（RFT）**，結合預熱式監督微調（SFT）與單輪強化學習（RL），強化模型於關鍵 GUI-工具切換決策點的判斷能力。
- 提出**工具效率路徑獎勵**，於高擬真 GUI-工具環境中透過線上代理式強化學習引導模型採用適當工具並縮短執行路徑。
- 在 OSWorld-MCP 基準上達到 46.85% 準確率，較基準模型帶來約 66% 的相對改進幅度，於同等規模模型中樹立新的最先進技術（SOTA）水準。

### 適合對象
本論文最適合從事**多模態大型語言模型（MLLM）**、**代理式能力（Agentic Capabilities）**、**數位代理（Digital Agents）**與**原生桌面工作流程（Native Desktop Workflows）**研究的學者與工程師閱讀；亦適合關注 GUI 自動化、長時程任務（Long-Horizon Tasks）規劃、強化學習獎勵設計，以及如何緩解連鎖錯誤（Cascading Errors）以提升服務覆蓋率（Service Coverage）之實務應用團隊參考。

## 深度分析

#### 方法論解析

ToolCUA 的核心問題意識在於：當前電腦使用代理（CUA, Computer Use Agents）雖然被賦予了 GUI 動作與結構化工具呼叫（structured tool calls）兩種互補的執行手段，但模型本身缺乏「何時該用 GUI、何時該切換到工具」的軌跡層級決策能力。論文將此問題形式化為**最佳 GUI-工具路徑選擇**（Optimal GUI-Tool Path Selection），並指出這是一個**軌跡層級策略學習**（trajectory-level policy learning）問題，而非傳統的步驟層級動作選擇（step-level action selection）問題——因為每一次 GUI-to-Tool 或 Tool-to-GUI 的切換都會重塑整條後續軌跡的效率與可靠性。

**1. 交錯式 GUI-工具軌跡擴展流程（Interleaved GUI-Tool Trajectory Scaling Pipeline）**

此流程的設計動機在於解決高品質交錯式 GUI-工具軌跡（interleaved GUI-Tool trajectories）稀缺、且真實工具軌跡（real tool trajectories）收集成本高昂且脆弱的問題。其關鍵創新在於「**重新利用**」（repurposing）而非「從零收集」：以現有的靜態 GUI 軌跡（static GUI trajectories）為基礎，透過 MLLM 從反覆出現的 GUI 程序中合成一個**軌跡感知**（trajectory-aware）的工具函式庫（tool library），再透過工具步驟生成（tool-step generation）與下一狀態對齊（next-state grounding）將純 GUI 軌跡轉化為交錯式 GUI-工具軌跡。這種設計避免了手動工程（manual engineering）與昂貴的真實環境儀器化（environment instrumentation），同時涵蓋了多樣化的工具粒度與切換上下文。

**2. 工具引導式 GUI 拒絕採樣微調（Tool-Bootstrapped GUI RFT）**

此階段採用兩步驟的訓練策略：
- **預熱式監督微調**（Warmup SFT）：建立基本的混合動作能力（hybrid-action capabilities），讓模型熟悉 GUI 動作與工具呼叫的交錯格式。
- **單輪強化學習**（Single-turn RL）：聚焦於**顯式的 GUI-工具切換決策點**（explicit GUI-Tool switching points），透過拒絕採樣微調（RFT, Rejection sampling Fine-Tuning）改善模型在關鍵切換時刻的判斷。

此設計的精妙之處在於將「切換決策」從整條軌跡中抽離出來進行專門優化，因為這些切換點正是影響整體軌跡效率與可靠性的瓶頸。

**3. 線上代理式強化學習（Online Agentic RL）與工具效率路徑獎勵（Tool-Efficient Path Reward）**

最終階段在**高擬真 GUI-工具環境**（high-fidelity GUI-Tool environment）中進行線上訓練，並設計了一個由兩部分組成的獎勵函數：
- **工具適切性獎勵** $R_{\text{tool}}$：鼓勵代理在工具受益時呼叫工具、在不必要時避免呼叫，從而解決「過度工具呼叫」或「過度 GUI 中心化」的偏差。
- **路徑效率獎勵** $R_{\text{length}}$：鼓勵以工具呼叫取代冗餘的 GUI 動作序列，促使執行路徑（execution path）更短。

兩者結合提供了**軌跡層級回饋**（trajectory-level feedback），驅動模型學習全域最佳（globally optimal）的 GUI-工具路徑選擇，而非僅僅模仿局部動作或依賴最終任務完成獎勵。

整體而言，ToolCUA 的方法論呈現一個清晰的「**資料→監督微調→強化學習**」三階段範式，每一階段都針對前一階段的不足進行補強：擴展流程解決資料稀缺，RFT 解決切換點決策品質，最終的線上 RL 解決軌跡層級全域最佳化。

#### 實驗數據解讀

**1. 主要基準測試結果**

在 OSWorld-MCP 上，ToolCUA-8B 達到 **46.85% 準確率**（accuracy），相較 Qwen3-VL-8B-Instruct 基準模型帶來約 **66% 的相對改進幅度**（relative improvement），在同規模模型中樹立了新的最先進技術（SOTA, State of the Art）。這個數字值得從兩個角度解讀：

- **絕對效能**：46.85% 在當前 CUA 領域已屬強勁表現，且與領先的閉源模型（如 Claude 系列）具有競爭力。
- **規模效率**：以 8B 規模達到接近更大模型或閉源模型的水平，顯示出訓練範式設計的價值，而非單純依賴模型容量。

**2. GUI 與混合設定的對比（Table 1）**

此表格揭示了 ToolCUA 與其他模型在純 GUI 設定與 GUI+工具混合設定下的關鍵差異：

| 模型 | 純 GUI 準確率 | 混合設定準確率 | 步數（混合） | 工具呼叫次數 |
|------|------------|------------|------------|------------|
| Qwen3VL-8B | 29.0 | 28.2（−0.8）| 19.3 | 0.01 |
| Qwen3VL-235B | 41.1 | 38.1（−3.0）| 18.0 | 3.62 |
| EvoCUA-32B | 52.6 | 40.5（−12.1）| 26.2 | 6.23 |
| Claude-4-Sonnet | 47.7 | 43.5（−4.2）| 19.8 | 4.30 |
| Claude-4.5-Sonnet | 61.9 | 48.4（−13.5）| 19.1 | 3.81 |
| **ToolCUA-8B** | **42.9** | **46.8（+3.9）** | **14.9** | **2.11** |

從這張表可以觀察到三個關鍵現象：

- **其他模型在混合設定下普遍退化**：除了 Qwen3VL-8B（幾乎不使用工具，工具呼叫次數僅 0.01），其餘模型在加入工具後準確率反而下降 3–13.5 個百分點。這印證了論文的問題意識——僅僅暴露混合動作空間並不能帶來好處，反而會讓模型「困惑」。
- **ToolCUA 是唯一在混合設定下提升的模型**：+3.9% 的提升說明 ToolCUA 真正學會了**適切地**使用工具，而非過度或不足。
- **步數與工具呼叫的平衡**：ToolCUA 在混合設定下僅用 14.9 步與 2.11 次工具呼叫，遠少於 EvoCUA-32B 的 26.2 步與 6.23 次呼叫，顯示其路徑效率獎勵 $R_{\text{length}}$ 確實發揮了作用。

**3. 泛化能力**

- **跨任務泛化**：在未見過的 multi_apps Linux 任務上達到 23.9%。
- **跨平台泛化**：在 WindowsAgentArena 的未見 Windows 桌面應用上達到 33.8%。

這兩個泛化結果支持了論文的結論：在混合動作空間中訓練不僅提升效率，也帶來更強的**可泛化性**（generalizability），因為模型學會的是「如何選擇最佳路徑」這一更高層次的策略，而非死記特定 GUI 動作序列。

#### 與現有研究的比較

**1. 定位**

ToolCUA 定位於「**軌跡層級混合動作編排**」這一被現有研究忽略的問題。現有 CUA 工作大致可分為三類：
- **純 GUI 代理**（如 OS-Atlas、Aguvis）：泛化性強但長時程任務易累積連鎖錯誤（cascading errors）。
- **工具呼叫為主**（如 API Agent）：效率高但受限於服務覆蓋率（service coverage）與穩定性。
- **混合動作但缺乏軌跡監督**（如部分閉源模型）：如 Table 1 所示，這類模型在混合設定下反而退化。

ToolCUA 的差異化在於：它不僅提供混合動作空間，更透過分階段訓練範式提供**軌跡層級監督**（trajectory-level supervision），使模型能學習全域最佳路徑。

**2. 相較於現有方法的改進**

- **相較 EvoCUA-32B**：EvoCUA 在純 GUI 設定下表現優異（52.6%），但加入工具後嚴重退化至 40.5%，顯示其缺乏工具呼叫知識與切換決策能力。ToolCUA-8B 以更小規模在混合設定下超越 EvoCUA-32B 約 6.3 個百分點。
- **相較閉源模型 Claude-4.5-Sonnet**：Claude-4.5-Sonnet 在純 GUI 設定下達到 61.9%，但混合設定退化至 48.4%。ToolCUA-8B 在混合設定下（46.8%）已逼近 Claude-4.5-Sonnet 的混合表現，且在純 GUI 設定下（42.9%）仍有差距，顯示閉源模型在 GUI 動作的基礎能力上仍具優勢，但 ToolCUA 在混合編排上更為有效。

**3. 局限性**

- **純 GUI 能力相對較弱**：ToolCUA-8B 的純 GUI 準確率（42.9%）低於 EvoCUA-32B（52.6%）與 Claude-4.5-Sonnet（61.9%），這可能是因為訓練過程中部分 GUI 軌跡被轉化為混合軌跡，導致純 GUI 監督訊號被稀釋。
- **對基準模型的依賴**：方法建立在 Qwen3-VL-8B-Instruct 之上，其底層 GUI 感知與推理能力的天花板會限制最終表現。
- **工具函式庫的覆蓋範圍**：雖然工具是從 GUI 程序中合成的，但合成的工具是否能涵蓋所有真實場景中的工具需求，仍有待驗證。
- **泛化至未見應用程式的挑戰**：23.9% 的 multi_apps Linux 與 33.8% 的 Windows 泛化結果雖然正面，但相對較低的絕對值顯示跨平台、跨應用程式的遷移仍是開放問題。

#### 未來研究方向

**1. 工具函式庫的擴展與動態演化**

當前工具是從靜態 GUI 軌跡中合成的，未來可探索：
- **線上工具發現**：讓代理在執行過程中動態發現並整合新工具，而非僅依賴預先合成的函式庫。
- **工具組合與泛化**：研究如何讓模型將已學會的工具組合成更高層次的抽象操作，類似於程式設計中的函式組合。
- **跨應用程式工具移植**：將某一應用程式中合成的工具泛化至結構相似的其他應用程式。

**2. 軌跡層級獎勵的精細化**

$R_{\text{tool}}$ 與 $R_{\text{length}}$ 目前是相對簡潔的設計，未來可考慮：
- **可靠性感知獎勵**：將工具呼叫的失敗率納入考量，避免模型選擇「看似高效但脆弱」的工具路徑。
- **使用者偏好對齊**：不同使用者對效率與可靠性的權衡不同，可探索個人化的獎勵設計。
- **多目標最佳化**：將準確率、步數、工具呼叫次數等指標納入帕累托最佳化（Pareto optimization）框架。

**3. 推理時的計算擴展**

- **規劃階段的引入**：在執行前讓模型先產生完整的 GUI-工具路徑計畫，再逐步執行，可能進一步提升切換決策品質。
- **自我反思機制**：讓代理在切換點進行「是否應該切換」的內省，並在事後根據執行結果調整策略。

**4. 安全性與可控性**

- **工具呼叫的權限管理**：在真實桌面環境中，工具呼叫可能涉及檔案修改、網路請求等敏感操作，需要研究如何在混合動作空間中實現細粒度的權限控制。
- **可解釋性**：軌跡層級決策的可解釋性比步驟層級更困難，需要新的視覺化與分析工具來幫助使用者理解代理的切換邏輯。

**5. 跨平台與跨裝置的統一框架**

雖然 ToolCUA 已展示 Linux 與 Windows 的初步泛化能力，但 macOS、行動裝置、瀏覽器等環境的混合動作空間特性各異。未來可探索構建一個**平台無關**（platform-agnostic）的混合動作編排框架，使單一模型能在多平台上進行最佳路徑選擇。

**6. 與人類示範的結合**

當前訓練資料主要來自自動合成的軌跡，未來可探索：
- **人類專家示範**：收集人類專家在 GUI-工具切換上的示範軌跡，用於監督微調或獎勵模型訓練。
- **人類回饋強化學習**（RLHF）：讓人類對代理的切換決策進行評分，進一步對齊人類偏好。

**7. 理論分析**

目前最佳 GUI-工具路徑選擇問題缺乏理論分析框架，未來可探討：
- 切換決策的可學習性（learnability）邊界。
- 在給定 GUI 動作與工具呼叫的成本分佈下，最佳路徑的結構性特性。
- 軌跡層級強化學習的樣本複雜度（sample complexity）分析。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於電腦使用代理（CUA）在混合動作空間下的「最佳 GUI-工具路徑選擇」問題。當代理同時擁有原子化 GUI 動作（如點擊、輸入）與高階工具呼叫（如 API 檔案操作）時，往往無法判斷何時該繼續使用 GUI、何時該切換到工具，導致執行路徑不佳。這個問題之所以困難，是因為每個 GUI 切換至工具或工具切換至 GUI 的決策不僅影響當下步驟，更會重塑整個後續軌跡的效率與可靠性，因此本質上是一個軌跡層級的策略學習問題。

**Q2：為什麼現有的方法無法有效解決這個問題？**
A：現有方法在兩個根本層面上有所不足。第一，現有的 CUA 在工具使用上訓練不足，缺乏工具呼叫知識，這是因為高品質的交錯式 GUI-工具軌跡極為稀少——真實環境中的 API 經常是應用程式專屬、不完整或不穩定的，且收集 GUI-工具資料需要昂貴的環境儀器化。第二，即便具備基本的工具使用能力，現有的監督訊號也無法有效引導混合動作編排，因為訓練訊號通常來自步驟層級的模仿學習（僅捕捉局部動作合理性）或最終任務完成獎勵（無法區分及時的工具切換與冗長的 GUI 替代方案）。

**Q3：為什麼 GUI-工具混合動作空間對下一代 CUA 至關重要？**
A：GUI 動作與工具呼叫具有互補的優勢：GUI 動作提供廣泛的通用性，但在長時程任務中容易產生連鎖錯誤；相對地，結構化工具呼叫提供更高的效率與精確度，但受限於服務覆蓋率與穩定性。以 LibreOffice 為例，修改整個欄位可以透過單一 API 呼叫完成，而純 GUI 方案則需要一長串點擊與按鍵操作。因此，混合動作空間是實現真正高效且可靠桌面自動化的關鍵，也是下一代 CUA 不可或缺的能力。

**Q4：這篇論文提出的核心方法是什麼？**
A：ToolCUA 是一個透過分階段訓練範式學習最佳 GUI-工具路徑選擇的端到端代理。其方法包含三個主要組成部分：首先，提出「交錯式 GUI-工具軌跡擴展流程」，利用 MLLM 從既有靜態 GUI 軌跡中合成工具函式庫，並將純 GUI 資料轉換為交錯式 GUI-工具軌跡；其次，執行「工具引導式 GUI 拒絕採樣微調（RFT）」，結合預熱式監督微調與單輪強化學習，以改善關鍵切換決策點的判斷；最後，在高擬真 GUI-工具環境中以「工具效率路徑獎勵」進行線上代理式強化學習。

**Q5：這篇論文最重要的創新點是什麼？**
A：本論文最重要的創新在於將 GUI-工具路徑選擇視為軌跡層級的策略學習問題，而非傳統的步驟層級動作選擇。所提出的「工具效率路徑獎勵」結合了工具適切性項（Rtool）與路徑效率項（Rlength），前者鼓勵代理在有益時呼叫工具、在不必要時避免呼叫，後者鼓勵以更短的執行路徑取代冗餘的 GUI 動作。此外，從既有 GUI 語料合成工具函式庫的資料擴展流程也是一項重要創新，無需昂貴的真實工具軌跡收集即可產生多樣化的訓練資料。

**Q6：分階段訓練範式的關鍵設計選擇有哪些？**
A：分階段訓練範式包含三個精心設計的階段。第一階段是資料建構，透過工具步驟生成與下一狀態對齊，將 GUI-only 資料轉化為交錯式軌跡，涵蓋多樣化的工具粒度與切換情境。第二階段是工具引導式 GUI RFT，先以預熱式監督微調建立基本的混合動作能力，再以單輪強化學習聚焦於明確的 GUI-工具切換點進行決策校準。第三階段則是在高擬真環境中進行線上代理式強化學習，透過工具效率路徑獎勵進行軌跡層級的整體最佳化。這種由基礎能力建立到切換點校準再到全域最佳化的漸進式設計，使模型能穩定地從模仿學習過渡到強化學習。

**Q7：論文中使用了哪些基準測試進行評估？**
A：主要評估基準是 OSWorld-MCP，這是 OSWorld 與 OSWorld-MCP 的匹配可行任務集，用於評估混合 GUI-工具動作空間下的表現。此外，論文也進行了分布外泛化測試，包括未見過的 multi_apps Linux 任務（達到 23.9%）以及 WindowsAgentArena 中的 Windows 桌面應用程式（達到 33.8%），以驗證模型在不同任務與平台間的泛化能力。

**Q8：論文的關鍵實驗結果為何？**
A：ToolCUA 在 OSWorld-MCP 上達到 46.85% 的準確率，相較於 Qwen3-VL-8B-Instruct 基準模型帶來約 66% 的相對改進幅度，在同規模模型中建立了新的最先進技術（SOTA）。在純 GUI 設定下達到 42.9% 準確率，當工具可用時再額外提升 3.9 個百分點，證明了有效的 GUI-工具路徑選擇能力。此外，在未見過的 multi_apps Linux 任務上達到 23.9%、Windows 桌面應用上達到 33.8%，展現了良好的跨任務與跨平台泛化能力。

**Q9：論文中進行了哪些消融實驗或比較？**
A：表 1 提供了多個模型在純 GUI 與混合 GUI-工具動作空間下的詳細比較，涵蓋 Qwen3VL-8B、Qwen3VL-235B、EvoCUA-32B、Claude-4-Sonnet、Claude-4.5-Sonnet 與 ToolCUA-8B。關鍵發現是：多數模型在加入工具後表現反而下降，例如 Claude-4.5-Sonnet 從 61.9% 降至 48.4%、EvoCUA-32B 從 52.6% 降至 40.5%，顯示它們在工具呼叫上過於頻繁或判斷不當；而 Qwen3VL-8B 則幾乎不呼叫工具（平均僅 0.01 次），過於 GUI 中心化。唯有 ToolCUA 在加入工具後從 42.9% 提升至 46.8%，且平均步數從 19.4 降至 14.9，證明了真正有效的 GUI-工具編排能力。

**Q10：ToolCUA 在哪些實際場景中具有應用價值？**
A：ToolCUA 在需要複雜桌面自動化的場景中特別有價值，例如辦公室生產力任務（透過 API 呼叫批次修改 LibreOffice 試算表）、跨應用程式工作流程（需要同時進行 GUI 互動與結構化 API 操作）、以及長時程任務（純 GUI 方案容易產生連鎖錯誤）。對於企業內部自動化、軟體測試、數位助理等應用，ToolCUA 的混合動作能力使其能在效率與通用性之間取得更好的平衡，特別適合處理那些部分步驟有 API 可用、部分步驟只能依賴 GUI 的混合型任務。

**Q11：在實際產品部署時需要考量哪些因素？**
A：產品部署時需考量以下幾點：第一，混合動作空間需要同時維護 GUI 自動化基礎設施與工具/API 整合，增加了系統複雜度；第二，工具函式庫需要隨著應用程式演進持續更新與維護，以確保可用性；第三，代理需要能優雅地處理工具失敗，自動回退到 GUI 動作；第四，必須考量 API 存取與工具權限的安全問題；第五，由於模型在 Windows 平台表現（33.8%）低於 Linux，跨平台部署時可能需要額外的平台特定優化或微調。

**Q12：這項研究對整個領域有何影響？**
A：這項研究最重要的領域影響在於驗證了「在混合動作空間中訓練」是實現真實世界數位代理的可行且有前景的範式。它不僅在同規模模型中建立了新的 SOTA，也證明了混合 GUI-工具編排能帶來更佳的泛化能力與效率。這項工作為未來的代理式 AI 研究提供了新的方向，特別是如何在軌跡層級進行策略學習、如何設計兼顧效率與適切性的獎勵函數，以及如何從既有資料中合成高品質的訓練軌跡。

**Q13：論文中有哪些已承認的限制？**
A：根據論文內容，可辨識出以下限制：第一，工具函式庫是從反覆出現的 GUI 程序中合成的，可能無法涵蓋所有可能的工具使用情境；第二，資料建構流程依賴於既有的 GUI 軌跡語料庫，若缺乏特定領域的 GUI 軌跡，則難以產生對應的工具軌跡；第三，模型在 Windows 桌面應用上的表現（33.8%）明顯低於 Linux，顯示跨平台泛化仍是挑戰；第四，線上代理式強化學習需要高擬真環境，這在實際部署時可能難以取得或維護。

**Q14：可能會出現哪些失敗案例？**
A：潛在的失敗案例包括：第一，當工具不可用或不穩定時，代理可能無法優雅地回退到 GUI 動作而陷入停滯；第二，在最佳路徑不明確的任務中，代理可能做出次佳的切換決策；第三，對於訓練資料未涵蓋的應用程式，代理可能難以合成或使用適當的工具；第四，在高度新穎、未在訓練分布中出現的場景下，模型可能仍會出現路徑選擇的混淆；第五，當 GUI 介面發生視覺變化時，模型對螢幕截圖的理解可能受到影響，進而影響切換決策的品質。

**Q15：未來的研究方向有哪些？**
A：未來研究方向可朝以下幾個方向發展：第一，擴展工具函式庫以涵蓋更多應用程式與平台，特別是改善跨平台（Linux、Windows、macOS）的泛化能力；第二，設計更精緻的軌跡層級獎勵訊號，例如考慮任務難度、失敗恢復成本等因素；第三，探索超越 GUI 與 API 呼叫的多模態工具使用，例如結合語音、程式碼執行等；第四，研究如何在真實世界部署中處理工具失敗與動態工具可用性；第五，將此框架擴展到行動裝置、網頁瀏覽器等其他數位環境，驗證混合動作空間範式的通用性。

## 實務應用指南

### 適用場景

1. **辦公室文件批次處理**：在 LibreOffice / Microsoft Office 中處理大量表格、文件時，自動判斷何時該用 GUI 操作（開啟檔案、選取範圍）與何時該切換為 API 呼叫（批次修改欄位、套用格式），將原本數十步的 GUI 操作縮短為數次工具呼叫。

2. **跨應用程式資料搬遷**：例如從瀏覽器擷取資料後寫入試算表、或從郵件附件匯入 CRM 系統。ToolCUA 能在 GUI 互動（瀏覽器操作）與結構化工具呼叫（API 寫入）間動態切換，避免冗長且易錯的複製貼上流程。

3. **企業內部 IT 自動化助理**：處理帳號建立、權限調整、軟體安裝等桌面管理工作。當 GUI 設定介面缺乏 API 時退回 GUI，已有 API 時優先呼叫，提升 IT 工單處理效率。

4. **客戶支援與遠端桌面協作**：在無法遠端修改後端服務的情境下，透過混合動作空間完成「截圖診斷 → 工具查詢知識庫 → GUI 操作修正」的閉環。

5. **跨平台桌面自動化產品**：需同時支援 Linux 與 Windows 桌面應用程式的 SaaS 自動化平台，可借助 ToolCUA 的 OOD 泛化能力（multi_apps Linux 23.9%、WindowsAgentArena 33.8%）降低平台適配成本。

### 實作前置條件

**資料需求**
- 大量靜態 GUI 軌跡語料庫（可來自 OSWorld、OpenXLA、GUI Odyssey 等開源資料集，或自錄製的螢幕操作日誌）。
- 目標應用程式的 API 文件或可呼叫的工具介面（MCP、OpenAPI、CLI 指令）。
- 用於軌跡擴展的種子任務集（建議 ≥ 數百個任務，每任務含完整 GUI 軌跡）。

**算力需求**
- 基底模型需為多模態 LLM（建議 ≥ 8B 參數，如 Qwen3-VL-8B-Instruct）。
- 軌跡擴展階段：單機 8×A100/H100 可處理 MLLM 推理與資料合成。
- 訓練階段（SFT + 單輪 RL + 線上代理式 RL）：建議 32–64 GPU 規模，線上 RL 需額外環境池（數十至數百個並行 VM/容器）。

**技能需求**
- MLLM 微調經驗（LoRA / 全參數 SFT、GRPO / DPO 等 RL 演算法）。
- 桌面環境儀器化能力（Docker + X11/VNC、OSWorld-MCP 風格的 sandbox）。
- 工具函式庫設計與 MCP 協定整合經驗。
- 軌跡資料清洗與品質過濾流程。

---

### 實作步驟建議

1. **盤點既有 GUI 軌跡與可用工具**：先盤點企業內部或開源的靜態 GUI 軌跡，並對目標應用程式盤點既有 API / CLI / MCP 工具，標記「工具受益子集」與「純 GUI 子集」。

2. **建立交錯式 GUI-工具軌跡擴展流程**
   - 用 MLLM 從反覆出現的 GUI 程序中合成「軌跡感知」的工具函式庫。
   - 對每條 GUI 軌跡，於合適的切換決策點插入工具呼叫，並以「下一狀態 grounding」驗證插入後的螢幕狀態與原軌跡一致。
   - 過濾掉無法 grounding 或工具呼叫後狀態不一致的樣本。

3. **執行工具引導式 GUI RFT（兩階段）**
   - **預熱式 SFT**：在交錯式軌跡上做監督式微調，建立基本混合動作能力。
   - **單輪 RL**：針對 GUI-Tool 切換決策點做拒絕採樣微調，校正切換時機。

4. **建置高擬真 GUI-工具環境**：以 OSWorld-MCP 為藍圖，部署可同時執行 GUI 動作與工具呼叫的 sandbox，並實作任務成功判定器。

5. **線上代理式 RL 訓練**
   - 設計「工具效率路徑獎勵」：包含 $R_{\text{tool}}$（工具適切性，鼓勵在受益時呼叫、不必要時避免）與 $R_{\text{length}}$（路徑效率，鼓勵以工具取代冗長 GUI）。
   - 以 GRPO / PPO 等演算法在環境池中做線上策略優化。

6. **評估與部署**
   - 在 OSWorld-MCP、OSWorld、WindowsAgentArena 上做 in-domain 與 OOD 評估。
   - 監控「步數」與「工具呼叫次數」指標，確認相較純 GUI 設定有實質縮短。
   - 透過 API 化部署，並設置人工接管（human-in-the-loop）後備機制。

---

### 潛在風險與注意事項

- **工具 API 不穩定或覆蓋率不足**：部分應用程式缺乏完整 API，強行呼叫會失敗。**緩解**：保留 GUI 後備路徑，並在獎勵函數中對工具呼叫失敗施加重懲罰，避免模型過度依賴工具。

- **獎勵 hacking**：模型可能學會「為了縮短路徑而呼叫不相關工具」或「刻意提早結束任務」。**緩解**：$R_{\text{tool}}$ 必須結合任務成功驗證，而非僅看步數；並加入軌跡一致性檢查。

- **環境儀器化成本高**：線上 RL 需大量並行桌面環境。**緩解**：使用容器化 + 快照還原機制，並考慮先用離線軌跡做大量模擬，僅在最後階段做線上 RL。

- **軌跡擴展的 grounding 錯誤**：合成交錯軌跡時，若下一狀態與原軌跡不一致，會引入錯誤監督訊號。**緩解**：建立嚴格的自動驗證流程（截圖比對、DOM 結構比對），並對低信心樣本做人工抽檢。

- **跨平台泛化落差**：雖然 ToolCUA 在 WindowsAgentArena 達 33.8%，但仍低於 Linux 表現。**緩解**：針對目標平台補蒐在地化軌跡，並在 RL 階段加入平台混合採樣。

- **安全與權限**：工具呼叫可能繞過 GUI 的權限檢查。**緩解**：在工具層強制執行權限沙箱，並對敏感操作（刪除、付款）保留人工確認。

### 與其他技術的整合建議

- **與 RPA 平台整合**：將 ToolCUA 作為 RPA 的「決策大腦」，由 RPA 處理底層 GUI 驅動（UiPath、Automation Anywhere），ToolCUA 負責高層決策與工具編排。

- **與 MCP 生態系整合**：以 Model Context Protocol 統一工具介面，使 ToolCUA 可直接呼叫既有 MCP 伺服器，無需為每個應用程式重寫工具包裝。

- **與企業 API Gateway 整合**：將內部 API 註冊為 ToolCUA 可呼叫的工具，並透過 Gateway 統一認證、限流與審計。

- **與監控與可觀測性系統整合**：將每次 GUI-Tool 切換、工具呼叫結果、軌跡長度等指標串接至既有 observability 平台（Prometheus / Grafana / LangSmith），便於追蹤模型行為漂移。

- **與人類監督流程整合**：在低信心決策或高風險操作時，自動升級為 human-in-the-loop，並將人工修正回饋回流至訓練資料，形成持續學習閉環。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題描述（圖 2 與表 1），理解「為什麼單純把 GUI 與工具都丟給模型是不夠的」，再跳到結論看 46.85% 與 3.9% 這兩個關鍵數字的意義。實作細節可先略過，重點掌握「混合動作空間」與「軌跡層級獎勵」兩個核心概念。

**給 AI 工程師**：重點閱讀第 2 節的訓練流程（軌跡擴展 → 工具引導式 RFT → 線上代理式 RL），特別是「工具效率路徑獎勵」的設計（$R_{\text{tool}}$ 與 $R_{\text{length}}$ 的組合）。可直接參考 OSWorld-MCP 的環境架構作為自家 sandbox 的起點，並評估將 GRPO 套用至自家 GUI 軌跡資料的可行性。

**給研究者**：本文的核心貢獻在於將「GUI-Tool 切換」形式化為軌跡層級策略學習問題，並提出可擴展的資料合成方案。建議延伸閱讀引用文獻 [12, 18, 45, 49, 54]，比較不同 CUA 訓練範式（純模仿 vs. 純 RL vs. 分階段），並思考在更複雜的多代理協作或長時程任務中，此獎勵設計是否仍足夠引導出最佳路徑。

**給產品經理**：重點關注三組數字——46.85%（在 OSWorld-MCP 的絕對水準）、+3.9%（混合動作空間相較純 GUI 的增益）、以及 WindowsAgentArena 33.8%（跨平台泛化）。這些數字回答了「為什麼值得投資混合動作空間」與「模型在新場域的落地成本」。在規劃產品時，建議優先選擇「工具受益子集」明顯的場景（如辦公室批次處理），可最快回收投資。
