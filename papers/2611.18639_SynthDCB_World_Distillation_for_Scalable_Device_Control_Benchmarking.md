SynthDCB 的核心方法論圍繞「世界蒸餾 (World Distillation, WD)」管線展開，這是一種將裝置行為知識轉化為可重用、可執行元件的系統化流程。整體方法論可分為四個相互銜接的階段：

**1. 類型化能力規格 (Typed Capability Specifications)**

WD 管線的第一步是建立類型化的能力規格，作為整個系統的「骨架」。這些規格不僅定義了裝置的可發現工具介面 (discoverable tool interfaces)，還規範了元件實作的契約，並提供任務建構器可呼叫的操作原語。這種設計類似於軟體工程中的介面定義語言 (Interface Definition Language, IDL)，但更強調語意層面的約束，例如裝置行為的前置條件、後置條件與環境效應。

**2. 世界組合 (World Composition)**

在規格確立後，WD 將元件組裝為特定領域的配置或模組化結構。論文中實例化了三大領域：Home（家庭）、Car（汽車）、Phone（手機）。每個領域由空間 (Space)、成員 (Member)、裝置 (Device) 三類實體構成，例如圖 1 所示的「緊湊型單間 (Compact Studio)」包含 1 位成員、5 個空間、12 個裝置。這種組合式設計允許同一裝置元件跨多個世界配置重用，無需重新實作其行為。

**3. 執行基礎的任務合成 (Execution-Grounded Task Synthesis)**

任務合成階段從可用能力衍生需求，並透過「參考執行回放 (reference-execution replay)」對候選任務進行可執行性驗證。這是 WD 區別於純 LLM 生成任務的關鍵：每個任務都必須在模擬器中實際執行通過，才能被納入基準。這種「由能力驅動、由執行驗證」的合成策略，有效避免了任務漂移 (task drift) 與不可滿足需求 (unsatisfiable requirements) 的問題。

**4. 統一能力表示 (Unified Capability Representation)**

WD 透過統一的表示層將工具探索 (tool discovery)、世界執行 (world execution) 與任務合成 (task synthesis) 串接起來。這層表示同時服務於三個面向：對代理人而言，它是可發現的工具目錄；對模擬器而言，它是可呼叫的行為原語；對任務建構器而言，它是可組合的能力單元。這種「一體三面」的設計大幅降低了系統各部分之間的耦合成本。

從系統架構角度觀察，SynthDCB 的狀態模型採用「顯式狀態 (explicit states)」與「工具呼叫軌跡 (tool-call traces)」雙軌記錄：前者用於任務驗證，後者用於代理人評估。時間維度上，系統支援 95 種事件 (events) 的時序演化，這使得「在洗衣機完成前將室溫降至 22°C」這類涉及時間約束的任務得以精確評估。

#### 實驗數據解讀

**主要評估結果**

論文在 2,560 個測試任務上評估了 22 個模型，最佳模型達到 88.8% 的平均 Pass@1。這個數字看似亮眼，但需要從多個維度解讀：

- **領域異質性**：模型排名在不同領域間存在顯著差異，這暗示裝置控制能力並非單一維度，而是高度依賴領域語境。
- **能力分化**：大型模型在直接裝置控制上表現良好，但在解讀複雜使用者意圖 (complex user intent) 與協調子任務 (coordinating subtasks) 以滿足完整請求方面仍存在明顯落差。
- **小型模型瓶頸**：較小模型在更基礎的層面就已遭遇困難——遵循互動協定 (interaction protocols) 與選擇合適工具 (selecting appropriate tools) 完成單一原子任務 (atomic tasks) 的能力不足。

**建構成本分析**

建構三大領域僅消耗 19.16M tokens，估計成本 $120.09（未計快取折扣），且在數小時內完成。這相較於「超過一個月的手動工作」展現出極高的自動化效率。具體而言：

- **階段執行效率**：規格、實作、測試、修復四個階段全部由 Codex + GPT-5.6 Sol 自動化完成，無需人工介入。

**RobotVacuum 比較實驗**

在與 Codex 不同推理等級的比較中，WD 在更豐富的知識輸入下達成更廣泛的完整能力覆蓋：

- **屬性覆蓋**：22/23 個屬性 (properties)

#### 與現有研究的比較

**定位差異**

相較於現有的工具使用基準（如 Yao et al., 2024; Lu et al., 2025; Seo et al., 2026; Li et al., 2026b），SynthDCB 的獨特價值在於：

1. **可擴展性優先**：傳統基準通常在發布時即固定環境與任務集，而 SynthDCB 將「擴展性」作為一等公民設計目標，透過 WD 管線支援按需新增裝置能力。
2. **執行基礎驗證**：許多基準依賴 LLM 評判 (LLM-as-a-judge) 進行任務驗證，而 SynthDCB 透過參考執行回放提供確定性的成功判定。
3. **環境感知評估**：SynthDCB 不僅評估「代理人能否呼叫正確工具」，更評估「代理人是否理解環境狀態並據此調整行為」，這與純粹的工具呼叫基準有本質區別。

**改進幅度**

從實驗數據推斷，WD 在以下方面相較於直接使用 Codex 進行基準建構有顯著改進：

- **令牌效率提升 51.5%–86.7%**：這意味著在相同預算下，WD 可建構更大規模的基準。
- **覆蓋率提升**：在 RobotVacuum 案例中，WD 達成更廣泛的完整能力覆蓋，特別是在事件需求層面。
- **建構時間從「月」縮短至「小時」**：這對於基準的迭代更新至關重要。

**侷限性**

儘管成果亮眼，SynthDCB 仍存在以下侷限：

1. **領域覆蓋有限**：目前僅涵蓋 Home、Car、Phone 三大領域，對於工業控制、醫療裝置等專業領域尚未觸及。

4. **依賴 LLM 知識邊界**：WD 的能力上限受制於底層 LLM（GPT-5.6 Sol）的裝置知識，對於訓練資料中少見的新興裝置，蒸餾品質可能下降。

### 實作步驟建議

**階段一：能力規格設計（Specification）**
1. 定義領域的「統一能力表示」骨架：列出裝置類別、函式簽章、事件型別、狀態變數。SynthDCB 使用 114 個裝置類別、1,166 個函式、95 個事件作為參考規模。
2. 為每個裝置撰寫 typed capability specification，明確標註輸入輸出型別、前置條件（preconditions）、副作用（environmental effects）、時間動態（temporal dynamics）。
3. 設計 discoverable tool interface：讓代理人能透過 `session.get_device_tools("ac")` 動態探索可用工具，而非預先注入完整工具清單。

**階段二：元件實作與測試（Implementation）**
4. 將規格轉為可執行程式碼：每個函式實作需包含狀態更新邏輯與環境副作用（如設定冷氣目標溫度後，室溫隨時間演進）。
5. 為每個元件撰寫單元測試，覆蓋正常路徑、邊界條件、不可達狀態。
6. 引入 self-repair 迴圈：當測試失敗時，將錯誤訊息回傳給 LLM 進行自動修復，直到通過為止。

**階段三：世界組合（World Composition）**
7. 設計領域專屬的佈局模板：Home 用「空間 + 裝置」結構（如 5 spaces × 12 devices），Car 用「模組化子系統」結構（座椅、空調、娛樂），Phone 用「App + 系統服務」結構。
8. 實作世界初始化器：根據模板生成具體配置（成員人數、空間大小、裝置型號），支援任務級別的客製化。

**階段四：任務合成與驗證（Task Synthesis）**
9. 定義五大任務家族：狀態查詢、裝置控制、環境目標、協調執行、不可達任務（never reach target）。每個家族下細分子類型（SynthDCB 共 32 個子類型）。
10. 從可用能力衍生任務需求：給定世界配置，自動產生「目標屬性 + 工具呼叫序列 + 成功條件」。
11. 執行 reference-execution replay：用 ground truth 工具呼叫序列驗證任務是否可達成，過濾掉不可行或無聊的任務。

**階段五：評估與迭代（Evaluation）**
12. 部署代理人介面：標準化的 tool-call 協議，包含 `session.get_space_state()`、`session.get_device_tools()` 等探索函式。
13. 執行批次評估：SynthDCB 在 2,560 個測試任務上評估 22 個模型，記錄 Pass@1、工具呼叫次數、失敗模式分類。
14. 失敗分析：區分「環境理解失敗」、「工具選擇錯誤」、「協調失敗」、「協議遵循失敗」，指導下一輪訓練或規格改進。

**階段六：擴展與遷移（Expansion）**
15. 當新裝置上線時，重複階段一至四，預期單一裝置類別的擴展成本遠低於初始建置（SynthDCB 整體建置僅 $120）。
16. 將元件庫版本化，支援跨世界配置重用與跨任務實例重用。

### 潛在風險與注意事項

**風險一：知識來源品質直接決定覆蓋率上限**
- 現象：若輸入的裝置手冊不完整或過時，蒸餾出的元件將遺漏關鍵功能。
- 緩解：建立知識來源審核流程，優先採用官方 API 規格書；對蒸餾結果進行屬性/功能/事件三維度的覆蓋率審計（SynthDCB 達 22/23、19/29、30/39）。

**風險二：環境副作用模擬失真**
- 現象：設定冷氣目標溫度後，室溫隨時間變化的曲線若與真實物理不符，代理人會學到錯誤的時序策略。
- 緩解：使用實機量測數據校正模擬參數；對時序敏感任務加入「物理合理性」檢查。

**風險三：任務合成產生偏斜**
- 現象：LLM 傾向生成「簡單、可解」任務，導致基準過於簡單，無法區分強模型與弱模型。
- 緩解：刻意加入「不可達任務」（如要求在洗衣週期結束前將室溫降至不可能的溫度），並用 semantic coverage 對齊真實指令分佈。

**風險四：reference-execution replay 的循環依賴**
- 現象：若 ground truth 工具呼叫序列本身有 bug，會誤殺合法任務或放行非法任務。
- 緩解：對 replay 引擎本身進行獨立測試；保留人類專家抽樣審核環節。

**風險五：評估結果的領域漂移**
- 現象：模型在 Home 表現優異但在 Car 失敗（SynthDCB 觀察到模型排名跨領域不一致），單一領域評估可能誤導部署決策。
- 緩解：維持多領域並行評估；對部署目標領域加重權重。

**風險六：成本與速度的權衡**
- 現象：雖然 SynthDCB 整體建置僅 $120，但若使用更強推理模型或加入人類審核，成本會快速攀升。
- 緩解：採用分層策略——用便宜模型做初稿蒸餾，用強模型做人類審核前的最後驗證。

### 與其他技術的整合建議

**與既有代理人框架整合**
- LangChain / AutoGen：將 SynthDCB 的 discoverable tool interface 包裝為標準 Tool 物件，支援 `@tool` 裝飾器風格的動態註冊。
- MCP（Model Context Protocol）：將 `session.get_device_tools()`、`session.get_space_state()` 等探索函式實作為 MCP server，讓任何 MCP 相容客戶端可直接接入。

**與模擬器整合**
- Unity / Unreal：若需要視覺化呈現，可將 SynthDCB 的狀態變化串接至遊戲引擎的場景更新，支援沉浸式代理人訓練。
- Gazebo / Isaac Sim：機器人領域可將 SynthDCB 的環境動態作為高層任務規劃器，與低層物理模擬解耦。

**與測試基礎設施整合**
- pytest：將每個裝置元件的單元測試納入 CI，確保規格變更時自動觸發回歸測試。
- LangSmith / Weights & Biases：記錄代理人工具呼叫軌跡，支援失敗案例的可視化回放。

**與訓練資料管線整合**
- Hugging Face datasets：將通過驗證的任務實例釋出為公開資料集，供社群進行 SFT/RLHF。
- 合成資料治理框架：標註每筆任務的「來源裝置類別」、「任務家族」、「難度等級」，支援下游篩選。

**與企業系統整合**
- 裝置管理平台（如 AWS IoT、Azure IoT Hub）：將 SynthDCB 元件庫與真實裝置註冊表對接，支援「模擬 → 灰度 → 全量」的漸進式部署。
- 客服系統：將真實使用者投訴轉化為 SynthDCB 任務，持續擴展基準的覆蓋面。
