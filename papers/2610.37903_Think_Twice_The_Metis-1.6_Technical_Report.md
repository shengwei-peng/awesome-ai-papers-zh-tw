1. 優化器實例化驗證：訓練前印出實際使用的優化器類型與參數分組。
2. 注意力矩陣參數路由：確認所有矩陣是否進入預期的優化器分組。
3. 注入閘值（injection gates）監控：若使用 n-gram 記憶體，持續追蹤閘值平均值；若趨近於零，考慮移除該元件。
4. 長度獎勵符號檢查：在群組均值標準化下，當群組通過率超過 2/3 時，長解是否被懲罰？加入 `clamp` 修正。

**步驟五：執行預訓練與上下文擴展**
依序完成 804.76B tokens 預訓練與 18B tokens 上下文擴展。建議每 10B tokens 進行一次損失與下游任務抽樣評估。

**步驟六：監督式微調並避開五個失敗模式**
報告第 6 節列出五個 SFT 失敗模式（具體內容需參考原文），每個都有對應的修正方式用於 Metis-1.7。建議在微調前先閱讀並設計對照實驗。

**步驟七：強化學習階段的獎勵設計**
若進行 RL，特別注意：
- 群組均值標準化下的長度獎勵：通過率高時正確解可能因冗長被懲罰。
- 驗證器平衡：避免強化學習縮短未見過的科學題推理長度。
- 蒸餾步驟規模：過小的蒸餾資料集可能無實質效果。

**步驟八：統一評測與 Pareto 分析**
使用單一評測 harness 對所有比較模型執行相同 prompt 與評分器。繪製「分數 vs. 訓練資料量」與「分數 vs. 啟用參數」雙軸 Pareto 圖，確認自家模型位於前沿。

### 潛在風險與注意事項

**風險一：優化器配置與實際不符**
報告中 AdaMuon 從未被實例化，注意力矩陣全程以 AdamW 訓練，導致訓練效率低於預期。**緩解措施**：訓練啟動後立即印出 `optimizer.param_groups` 與每個參數的 `step()` 呼叫次數，與配置檔比對。

**風險二：元件學會自我關閉**
1.77B 參數的 n-gram 記憶體在兩個模型中閘值都趨近於零，刪除後損失變化小於 10⁻³ nats。**緩解措施**：為所有可學習的閘值元件設定監控指標；若訓練中期閘值持續下降，提前評估移除後的影響。

**風險三：長度獎勵符號反轉**
在群組均值標準化下，當群組通過率超過 2/3 時，正確但冗長的解會被懲罰。**緩解措施**：實作長度獎勵時加入 `clamp(reward, min=0)` 或類似的單行修正，並在通過率 > 0.5 時切換獎勵計算方式。

**風險四：SFT 階段的能力流失**
報告指出五個微調選擇導致能力下降。**緩解措施**：每次微調後保留基準測試快照，採用逐步微調而非一次性大幅調整；保留 base 模型權重以便回退。

**風險五：程式碼、指令遵循、長上下文為弱項**
Logos 在這些領域落後於訓練資料量遠高於它的模型。**緩解措施**：若應用場景涉及這些能力，需進行領域專項微調或採用混合管線（Logos 處理數學，其他模型處理程式碼）。

**風險六：評測的可比性陷阱**
不同模型的官方評測分數常因 prompt、評分器、上下文長度不同而不可直接比較。**緩解措施**：務必使用單一 harness 重新評測所有比較模型，而非直接引用官方數字。

### 與其他技術的整合建議

**與 RAG（檢索增強生成）整合**
Logos 的長上下文弱項可由 RAG 補強：將事實性查詢委派給檢索系統，僅將檢索結果與問題交給 Logos 進行推理。特別適合數學應用中需要查閱定理或公式的場景。

**與工具呼叫（Tool Calling）整合**
報告提到 Logos「呼叫工具」的能力已足夠實用。建議整合 Function Calling 框架（如 LangChain、LlamaIndex），讓 Logos 負責規劃與推理，工具負責執行與資料獲取。

**與程式碼執行環境整合**
雖然 Logos 在程式碼生成上偏弱，但可作為「程式碼審查者」或「除錯助手」，搭配專門的程式碼模型（如 Qwen2.5-Coder）形成分工。

**與蒸餾管線整合**
若需將 Logos 部署到資源更受限的環境，可將 Logos 作為教師模型，蒸餾至更小的學生模型。報告第 7.4 節提醒蒸餾資料集需足夠大，否則效果不彰。

**與現有 MoE 推理框架整合**
Logos 的 MoE 設計可整合至 vLLM、TGI 等推理框架。需注意啟用參數為 1.18B 而非全參數 10.23B，KV cache 與專家路由的記憶體配置需相應調整。

**與持續學習管線整合**
若應用場景的資料分布隨時間漂移，可將 Logos 的 base 版本作為起點，定期以新資料進行輕量微調。建議保留完整的訓練 lineage 與 checkpoint hash 以利審計。
