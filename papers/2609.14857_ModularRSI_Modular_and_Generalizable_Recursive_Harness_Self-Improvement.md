## 摘要翻譯

近期研究將遞迴自我改進（Recursive Self-Improvement, RSI）擴展至智能體框架（agent harness），應用於長程程式設計任務（long-horizon coding tasks）與終端機任務（terminal tasks），使智能體得以從經驗中改進執行機制（execution mechanisms）。然而，可泛化框架遞迴自我改進（generalizable harness RSI）仍具挑戰性。首先，於評估基準（evaluation benchmarks）或其子集上演化框架，會使可重用的改進與基準特定適應（benchmark-specific adaptation）難以區分。其次，單軌跡更新（single-trajectory updates）容易把系統性框架缺陷（systematic harness deficiencies）與實例特定推理（instance-specific reasoning）及解決方案細節混為一談，產生難以遷移至未見任務的修改。第三，在單體式框架（monolithic harnesses）中定位重複出現的行為缺陷（recurring behavioral deficiencies）十分困難，而整體框架最佳化（whole-harness optimization）可能使不相關的機制相互耦合，並使歸因與驗證趨於複雜。我們提出 ModularRSI，一個與基準分離的（benchmark-disjoint）、對比式（contrastive）且模組化框架（modular framework），用於可泛化框架演化。ModularRSI 對比同一任務的成功與失敗軌跡（successful and failed trajectories），並彙整跨任務的證據，以識別重複出現的行為缺陷。它將可演化的框架分解為五個功能模組（functional modules）：Agent Loop、Tool Use、Observation Management、Context Management 與 Task Completion Detection。每個模組在受限修改範圍（restricted modification scope）內獨立演化，隨後進入整合階段（integration stage），將演化後的模組組合成統一的框架，並解決潛在衝突。為了支援與基準分離的演化，我們從外部來源彙整 2,000 個可執行演化任務（executable evolution tasks），其與下游評估基準（downstream evaluation benchmarks）互不重疊。在 TerminalBench 2.0（TB2.0）與 SWE-Bench Verified 上的實驗顯示，無論是在未見的同領域任務（in-domain tasks）或跨領域任務（cross-domain tasks）上均有穩定提升，且演化後的框架亦能遷移至不同的基礎模型（foundation models）。

### 核心貢獻（3～5點）
- 提出 ModularRSI，一個與基準分離、對比式且模組化的框架遞迴自我改進方法，解決既有方法在可泛化性上的三大挑戰。
- 將智能體框架分解為 Agent Loop、Tool Use、Observation Management、Context Management 與 Task Completion Detection 五大功能模組，使各模組能在受限修改範圍內獨立演化，再經整合階段組合為統一框架。
- 透過對比同一任務的成功與失敗軌跡，並彙整跨任務證據，有效區分系統性框架缺陷與實例特定推理，識別可泛化的重複行為缺陷。
- 彙整 2,000 個與下游評估基準不重疊的可執行演化任務，支援與基準分離的框架演化，避免過度適應特定評估基準。
- 在 TB2.0 與 SWE-Bench Verified 上驗證，於未見的同領域與跨領域任務均有穩定提升，且演化後的框架可遷移至不同基礎模型。

### 適合對象
本論文適合對智能體框架、遞迴自我改進、長程程式設計任務與終端機任務有興趣的研究人員與工程師，特別是關注框架可泛化性、模組化設計、跨基準遷移，以及希望了解如何從經驗中系統化改進智能體執行機制的讀者。

## 深度分析

#### 方法論解析

ModularRSI 的核心目標是將「可泛化框架遞迴自我改進（generalizable harness RSI）」從一個單純利用任務結果進行端到端調整的問題，轉化為一個具備**對比式（contrastive）**證據聚合、**模組化（modular）**缺陷定位與**與基準分離（benchmark-disjoint）**驗證的系統性流程。整體方法可拆解為四個環節：演化資料建構、對比式缺陷識別、功能模組獨立演化，以及模組整合與衝突消解。

##### 1. 與基準分離的演化資料建構

為了避免「在下游評估基準（downstream evaluation benchmarks）」上直接演化所造成的基準特定適應（benchmark-specific adaptation），作者從外部來源獨立蒐集了 **2,000 個可執行演化任務（executable evolution tasks）**。這些任務與 TerminalBench 2.0（TB2.0）和 SWE-Bench Verified 等下游基準在資料來源與領域分布上保持分離，並透過實例層級相似度過濾與細粒度領域分析降低重疊。這樣的設計讓後續的框架改進無法直接記憶測試樣本的答案或模式，從而迫使 harness 學習到可遷移的執行機制（execution mechanisms）。

##### 2. 對比式軌跡分析與跨任務證據聚合

傳統單軌跡更新（single-trajectory updates）的問題在於：失敗軌跡中同時夾雜了系統性框架缺陷（systematic harness deficiencies）與實例特定推理（instance-specific reasoning）的雜訊。ModularRSI 針對**同一任務**同時收集成功與失敗軌跡，透過對比成功與失敗軌跡（successful and failed trajectories）來剔除任務特定細節，並將證據跨任務聚合，以識別重複出現的行為缺陷（recurring behavioral deficiencies）。這種「同任務對比＋跨任務統計」的策略，能把粗粒度的任務成敗訊號轉換為更純粹的 harness 層級改進訊號。

##### 3. 五大功能模組的獨立演化

為了解決單體式框架（monolithic harnesses）中難以定位責任元件的問題，ModularRSI 將可演化框架（evolvable harness）分解為五個功能模組（functional modules）：

- **Agent Loop（智能體迴圈）**：控制整體決策與行動循環，例如重試策略、終止條件與錯誤恢復。
- **Tool Use（工具使用）**：管理工具呼叫格式、參數解析、錯誤處理與工具選擇。
- **Observation Management（觀察管理）**：決定如何從終端機或環境回饋（environment feedback）中擷取、過濾與呈現觀察。
- **Context Management（上下文管理）**：負責提示詞（prompt）組裝、歷史軌跡壓縮與相關上下文保留。
- **Task Completion Detection（任務完成偵測）**：判斷任務是否已完成、是否該提交答案或繼續執行。

每個模組在**受限修改範圍（restricted modification scope）**內獨立演化，這大幅縮小了搜尋空間，也減少無關機制之間的糾纏。獨立演化還帶來可解釋性優勢：當某個改進生效或失效時，可以清楚歸因到特定模組。

##### 4. 整合階段與衝突消解

獨立演化後，各模組的改進可能彼此衝突，例如 Observation Management 縮減輸出長度，而 Context Management 卻希望保留更多歷史。ModularRSI 設有**整合階段（integration stage）**，將演化後的模組合併為統一框架（unified harness），並主動偵測與消解潛在衝突。此階段也會對每項修改進行正確性、可執行性與任務特定過擬合（task-specific overfitting）的驗證，只有通過驗證的改動才會被保留。這種「先分後合、驗證把關」的流程，是 ModularRSI 能同時提升同領域（in-domain）與跨領域（cross-domain）泛化能力的關鍵。

#### 實驗數據解讀

雖然提供的摘錄未列出完整數值表格，但從論文敘述可歸納出以下實驗設計與結果意涵：

##### 1. 評估基準與泛化維度

實驗選用兩個性質迥異的基準：

- **TerminalBench 2.0（TB2.0）**：長程終端機任務（terminal tasks），強調命令列介面智能體（CLI agents）在多步操作、環境回饋與錯誤恢復上的能力。
- **SWE-Bench Verified**：真實軟體工程任務（software engineering tasks），要求智能體在程式碼庫中定位、修改並驗證修補。

這兩個基準分別代表「終端機操作」與「程式碼工程」兩大領域，能同時檢驗 **unseen in-domain** 與 **cross-domain** 泛化。

##### 2. 主要結果

論文報告 ModularRSI 在兩個基準上均帶來**一致性提升（consistent improvements）**，且提升來自於未在演化階段見過的任務。這說明：

- 對比式證據聚合確實過濾掉任務特定雜訊，讓改進具備遷移性。
- 模組化演化避免整體框架最佳化（whole-harness optimization）造成的過擬合。
- 與基準分離的 2,000 個演化任務提供了足夠多樣的經驗，支撐跨領域遷移。

##### 3. 跨基礎模型遷移

另一項重要發現是演化後的框架能夠**轉移到不同基礎模型（foundation models）**。這意味著 harness 的改進並非依附於某個特定模型的偏好或能力，而是捕捉了更通用的執行機制與工具互動（tool interaction）原則。對於實務部署而言，這大幅降低了每次更換底層模型時都需重新調整 harness 的成本。

##### 4. 控制研究的意涵

論文進一步透過控制研究指出：

- **獨立演化並合併模組**顯著優於聯合或非模組化演化。這驗證了模組分解不僅是工程上的便利，更是提升泛化的演算法設計。
- 不同模組對執行可靠度（execution reliability）與互動效率（interaction efficiency）有**互補貢獻**。例如 Tool Use 與 Observation Management 可能主要減少工具呼叫錯誤，而 Context Management 與 Task Completion Detection 則提升長程軌跡的穩定性與終止判斷準確度。

##### 5. 潛在的解讀限制

由於摘錄未提供詳細數字，我們無法判斷提升幅度是否在不同難度子集上均勻分布。一個合理的後續問題是：ModularRSI 對於「簡單但容易因完成偵測錯誤而失敗」的任務，與「困難且需要複雜工具鏈」的任務，是否分別由不同模組主導改進？這將影響未來如何針對性地擴充演化資料。

#### 與現有研究的比較

摘錄中的相關工作表格顯示，現有 Harness RSI 方法大多存在三個特徵中的至少一個：使用基準資料演化、採用整體框架最佳化、缺乏模組化設計。以下從定位、優勢與限制三方面比較。

##### 1. 定位：從「在基準上調適」到「與基準分離的泛化」

- **AutoHarness、Meta-Harness、AHE、Self-Harness、RHO** 等方法直接在下游基準或其子集上進行演化，容易學到基準特定適應。
- **HarnessFix、Living-Harness、HarnessForge、HarnessBank** 等雖然具備某些診斷或演化機制，但仍未明確切斷與評估資料的關聯，或未採用模組化限制。
- **ModularRSI** 明確建立 **benchmark-disjoint evolution protocol**，將演化資料與評估基準分離，並以「能否在未見任務上提升」作為核心評價標準。

##### 2. 優勢：對比式與模組化的雙重設計

| 面向 | 現有主流做法 | ModularRSI |
|---|---|---|
| 演化資料來源 | 常取自 downstream evaluation benchmarks | 外部來源的 2,000 executable evolution tasks，與基準分離 |
| 缺陷識別 | 單軌跡更新或任務層級回饋 | 同任務成功/失敗軌跡對比＋跨任務證據聚合 |
| 修改範圍 | whole-harness optimization，大範圍重寫 | 五個 functional modules 獨立演化，restricted modification scope |
| 可解釋性 | 難以歸因 | 改進可歸因到 Agent Loop、Tool Use 等特定模組 |
| 衝突處理 | 較少討論 | 明確的 integration stage 與衝突消解 |

##### 3. 現有研究的限制與 ModularRSI 尚未完全解決的問題

儘管 ModularRSI 在設計上更嚴謹，仍有以下限制：

- **模組劃分是預先定義的**：五個功能模組雖合理，但未必適用於所有 harness 架構。若未來出現新的互動範式（例如多模態觀察、分佈式工具），固定模組可能需要重新設計。
- **演化資料規模與多樣性的天花板**：2,000 個任務已屬大規模，但是否足以覆蓋未來更廣泛的軟體工程領域仍待驗證。資料建構成本（環境完整性、任務有效性、評估器可靠性）仍是瓶頸。
- **驗證機制的開銷**：每個模組改進都需經過正確性、可執行性與過擬合驗證，這在計算資源與時間上可能相當昂貴，限制了演化迭代速度。
- **未公開完整數值**：摘錄未提供詳細消融實驗數據，因此難以量化「對比式分析」與「模組化」各自單獨帶來的增益比例。

#### 可重現性評估

##### 1. 開源資源

論文明確指出所有程式碼與資料集皆公開於：

> https://github.com/IQuestLab/ModularRSI

這包含：

- ModularRSI 的完整實作。
- 2,000 個 executable evolution tasks 的資料與環境設定。
- 用於對比式軌跡分析與模組整合的腳本。

##### 2. 資料集的可重現性

由於演化任務需要可執行環境與可靠的正確性回饋，單純釋出題目描述並不足夠。論文強調這些任務具備：

- 完整的執行環境（environment completeness）。
- 有效的任務定義（task validity）。
- 可靠的評估器（evaluator reliability）。

若 GitHub 倉庫確實提供對應的 Docker 映像檔、測試腳本與任務元資料，則其他研究者可在相同條件下重現演化過程。

##### 3. 模型權重與 API 依賴

論文未提及釋出任何基礎模型權重，這符合常態：ModularRSI 改進的是 harness 而非模型本身。實驗可能使用商用 API（如 GPT-4、Claude 等）或開源模型（如 LoopCoder、IQuest-Coder-V1）作為底層基礎模型。重現時需注意：

- 若使用 API，結果可能因模型版本更新而略有差異。
- 若使用開源模型，需確認論文是否提供所用模型版本與推論設定。
- 跨基礎模型遷移實驗的可重現性，取決於是否能取得相同型號與檢查點。

##### 4. 潛在重現挑戰

- **計算成本**：2,000 個長程任務的軌跡生成、對比分析、五模組獨立演化與整合驗證，需要大量 LLM 呼叫與環境執行。
- **隨機性**：LLM-based agent 的軌跡具有隨機性，重現時需固定隨機種子與溫度參數（temperature），並報告多次運行的統計區間。
- **環境漂移**：終端機與軟體工程任務常依賴特定作業系統、套件版本與相依庫，長期維護這些環境是重現的關鍵。

#### 未來研究方向

基於 ModularRSI 的設計與限制，可延伸出以下研究方向：

##### 1. 自動化模組發現與動態粒度調整

目前五個功能模組由人為預先定義。未來可探索**自動模組分解**：根據軌跡中錯誤發生的位置與相依關係，動態調整模組數量與邊界，讓 harness 結構隨任務領域演化。

##### 2. 線上遞迴自我改進（online RSI）

ModularRSI 目前採用「離線演化＋凍結評估」的協議。未來可研究**線上持續演化**：在部署後根據新失敗案例即時更新模組，同時避免災難性遺忘（catastrophic forgetting）與錯誤改進的累積。

##### 3. 理論化的泛化保證

現有研究多以經驗泛化為目標。未來可嘗試建立 harness 改進的泛化界（generalization bound），例如分析對比式證據聚合在多大程度上能降低分布偏移（distribution shift）風險，或模組化限制如何影響修改空間的 Rademacher 複雜度。

##### 4. 多智能體與分佈式 harness 的模組化演化

當 harness 涉及多個協作智能體（multi-agent systems）或分佈式工具時，模組間的介面與通訊協定將更加複雜。可將 ModularRSI 擴展至多智能體框架，讓不同 agent 的 harness 模組獨立演化後再進行聯合整合。

##### 5. 更廣泛的應用領域

目前聚焦於長程程式設計任務（long-horizon coding tasks）與終端機任務（terminal tasks）。未來可探索：

- 科學計算與資料分析 workflow。
- 網頁操作與 GUI 智能體。
- 機器人控制與具身智能（embodied AI）中的 harness 自我改進。

##### 6. 衝突消解的學習化

目前的 integration stage 可能仰賴規則或啟發式方法。未來可訓練專門的「衝突消解模組」，利用歷史整合案例學習如何在不同模組改進間取得平衡，甚至預測潛在衝突並提前調整演化方向。

##### 7. 演化資料規模與品質的系統性研究

2,000 個任務是一個起點，但未來需要探討：

- 演化任務數量與最終泛化性能之間的縮放律（scaling law）。
- 任務多樣性、難度分布與領域覆蓋對遷移效果的影響。
- 自動生成高品質 executable evolution tasks 的方法，以降低人工策展成本。

##### 8. 結合人類回饋與形式化驗證

未來可將 ModularRSI 與人類回饋（human feedback）或形式化驗證（formal verification）結合，特別是在 Task Completion Detection 與 Tool Use 模組中，利用單元測試、型別檢查或定理證明來強化改進的正確性保證。

## 論文問答

### 【Background & Motivation】

**Q1：ModularRSI 旨在解決什麼核心問題？**

A：ModularRSI 的核心目標是實現「可泛化的智能體框架遞迴自我改進（generalizable harness RSI）」，讓命令列介面智能體能夠從執行經驗中改進其執行機制，而不是僅僅記住特定評估基準的題型。現有方法常在下游評估基準或其子集上進行演化，導致難以區分哪些是真正可重用的框架改進、哪些只是基準特定適應。此外，單一軌跡更新與單體式框架也讓系統性缺陷的定位變得困難，ModularRSI 透過與基準分離、對比式與模組化的設計來同時解決這三個層次的挑戰。

**Q2：現有的 harness RSI 方法為何難以泛化到未見任務？**

A：現有方法面臨三個相互關聯的困難：首先在資料層面，它們往往直接使用下游評估基準的資料進行演化，使得改進容易淪為基準特定適應；其次在軌跡層面，單一成功或失敗軌跡會把系統性框架缺陷與實例特定推理、解答細節混雜在一起，產生只對少數任務有效的修改；最後在機制層面，單體式框架難以定位重複出現的行為缺陷，而整體框架最佳化又會讓不相關機制互相糾纏，導致改進難以歸因與驗證。

**Q3：可泛化的 harness RSI 對 CLI 智能體與軟體工程任務為何重要？**

A：CLI 智能體在複雜軟體工程與終端機任務上的表現，除了依賴基礎模型能力，更取決於控制執行、工具互動、上下文管理與環境回饋的框架。如果框架改進只能泛化到曾經演化的基準，就無法在真實世界多樣且持續變動的任務中穩定發揮。可泛化的 RSI 能讓智能體自主、持續且可規模化地提升執行可靠性，並在不同基礎模型間轉移，降低人工重新設計框架的成本。

---

### 【Method & Innovation】

**Q4：ModularRSI 的核心方法流程是什麼？**

A：ModularRSI 首先針對同一任務的成功與失敗軌跡進行對比，從中萃取出與任務細節無關的框架行為缺陷；接著跨任務聚合這些對比證據，以辨識重複出現的系統性問題。隨後它把可演化的框架分解為五個功能模組，每個模組在受限修改範圍內獨立演化，最後再透過整合階段將各模組合併為統一框架，並解決潛在衝突。

**Q5：ModularRSI 將框架分解為哪五個功能模組？為何要這樣模組化？**

A：五個功能模組分別是：智能體迴圈（Agent Loop）、工具使用（Tool Use）、觀察管理（Observation Management）、上下文管理（Context Management）以及任務完成偵測（Task Completion Detection）。模組化的目的在於把原本龐大的整體框架最佳化空間切分成多個受限且可解釋的修改範圍，讓每個缺陷都能被歸因到特定機制。這樣不僅能降低不相關機制間的干擾，也讓演化後的改進更容易驗證、整合與維護。

**Q6：什麼是「與基準分離的演化協定」？它為何對評估泛化性至關重要？**

A：與基準分離的演化協定是指從外部資料來源獨立蒐集 2,000 個可執行演化任務，並透過實例層級相似度過濾與細粒度領域分析，確保這些任務與下游評估基準（如 TerminalBench 2.0 與 SWE-Bench Verified）沒有重疊。這麼做可以避免演化過程中直接或間接地擬合評估基準的題型與模式。唯有在演化資料與評估資料分離的前提下，觀察到的性能提升才能真正反映框架改進的泛化能力，而非基準特定適應。

---

### 【Experiments & Results】

**Q7：論文在哪些基準上進行實驗？這些基準分別測試什麼能力？**

A：實驗主要在 TerminalBench 2.0（TB2.0）與 SWE-Bench Verified 兩個基準上進行。TerminalBench 2.0 側重長程終端機任務，考驗智能體在命令列環境中的執行、觀察與工具使用能力；SWE-Bench Verified 則是真實軟體工程任務基準，要求智能體理解程式碼庫、定位問題並產生可通過測試的修補。兩者都用來檢驗演化後的框架在未見的同領域與跨領域任務上是否仍能穩定提升。

**Q8：ModularRSI 的主要實驗結果是什麼？**

A：實驗顯示，經過 ModularRSI 演化後的框架在 TerminalBench 2.0 與 SWE-Bench Verified 上都能持續提升未見任務的表現，並且能跨不同基礎模型轉移。控制實驗進一步證明，獨立演化並整合各模組的方式顯著優於聯合或非模組化的整體框架演化。此外，不同模組對執行可靠性與互動效率帶來了互補性的改善，顯示模組化設計確實能捕捉多樣化的框架缺陷。

**Q9：消融研究揭示了哪些關鍵設計的貢獻？**

A：消融研究指出，獨立模組演化與後續整合是提升性能的關鍵，因為它能避免整體框架最佳化時不同機制互相糾纏。對比式軌跡分析與跨任務證據聚合則能有效降低任務特定過擬合，讓改進更專注於系統性行為缺陷。與基準分離的演化資料也證明不可或缺，因為一旦使用下游基準資料進行演化，性能提升往往來自基準特定適應而非可轉移的框架改進。

### 【Applications & Impact】

**Q10：ModularRSI 適合應用在哪些實務情境？**

A：ModularRSI 特別適合需要長時間執行、反覆與環境互動的任務，例如自動化終端機維運、長程程式設計、軟體缺陷修復與持續整合測試。在這些情境中，框架必須穩定地決定何時呼叫工具、如何管理觀察與上下文、以及何時判定任務完成。透過模組化自我改進，系統可以在不針對每個任務人工重寫框架的前提下，持續提升執行可靠性與工具互動效率。

**Q11：若要在產品中部署 ModularRSI，需要考慮哪些工程與維護因素？**

A：首先必須建立可執行且隔離的沙箱環境，並確保正確性評估器（evaluator）可靠，因為演化訊號高度依賴這些回饋。其次需要嚴謹的驗證管線，在接納任何框架修改前檢查其正確性、可執行性與是否對演化任務過擬合。最後，模組化設計雖然便於針對性更新與回滾，但仍需監控整合階段可能產生的模組衝突，並建立自動化測試以確保統一框架的穩定性。

**Q12：ModularRSI 對智能體研究與遞迴自我改進領域可能帶來什麼影響？**

A：ModularRSI 提供了一個系統化的信用分配（credit assignment）框架，把原本粗粒度的任務成敗轉換為局部化的框架修改訊號，這對 RSI 研究具有方法論上的參考價值。它也推動了「與基準分離」的評估典範，提醒社群在宣稱泛化能力時必須區分真正轉移與基準特定適應。未來，這套對比式、模組化的演化思路可望擴展到網頁智能體、多模態智能體或其他需要複雜執行機制的領域。

---

### 【Limitations & Future】

**Q13：作者承認 ModularRSI 有哪些主要限制？**

A：作者指出，雖然蒐集了 2,000 個演化任務，但這些任務仍無法涵蓋所有可能的領域與任務型態，某些稀有領域可能缺乏足夠的演化樣本。此外，整個流程高度依賴環境的完整性與評估器的可靠性，若環境或評估器有誤，演化訊號也會跟著偏差。最後，儘管整合階段會嘗試解決模組衝突，但在複雜改動下仍可能出現難以完全消除的交互影響，且演化過程需要可觀的運算與資料整理成本。

**Q14：在什麼情況下 ModularRSI 可能會失敗或表現不佳？**

A：當任務需要全新類型的工具使用模式或觀察管理策略，而這些模式超出目前五個模組的修改範圍時，模組化演化就難以產生有效改進。如果演化資料中某類缺陷的樣本過少，跨任務聚合也可能無法穩定識別出重複出現的系統性問題。此外，驗證管線可能過於保守而拒絕某些高風險但潛在有益的修改，或者在某些情況下未能偵測到對演化任務的微妙過擬合。

**Q15：未來可以朝哪些方向延伸 ModularRSI？**

A：未來可以擴大演化任務的規模與領域多樣性，並探索自動化模組發現或動態模組分解，以適應更複雜的框架結構。另一個方向是將 harness 層級的 RSI 與基礎模型權重層級的 RSI 結合，同時改進推理能力與執行機制。此外，也可把這套對比式模組化方法應用到網頁瀏覽、多模態互動或具身智能體等領域，並發展更強大的衝突解決與驗證技術，以進一步提升演化的穩定性與安全性。

## 實務應用指南

## 適用場景

1. **企業內部 DevOps／SRE 自動化終端機智能體**  
   用於處理線上事故排查、日誌分析、服務重啟、部署回滾等長程終端機任務。ModularRSI 可讓智能體框架從歷史成功與失敗的處置軌跡中學習，改善工具呼叫順序、觀察彙整與完成判斷，減少同類事故的重複失誤。

2. **軟體工程團隊的程式碼修復與測試代理**  
   類似 SWE-Bench Verified 的場景，讓代理自動定位 bug、撰寫修補程式並執行測試。透過模組化演化，可獨立強化「工具使用」與「任務完成偵測」模組，降低把特定 repository 的寫法過度擬合到框架行為的風險。

3. **資安滲透測試與合規稽核自動化框架**  
   在隔離沙箱中執行長程指令序列（如掃描、權限檢查、設定稽核）。對比成功與失敗軌跡有助於發現重複出現的行為缺陷，例如觀察管理模組遺漏關鍵錯誤訊息，或過早判定任務完成。

4. **資料工程與 ETL 管線除錯代理**  
   面對分散式執行、schema 變更或資料品質異常等長程任務，框架可學習如何更有效地查詢日誌、彙整多步觀察結果，並在真正修復後才回報完成，提升管線維護效率。

## 實作前置條件

**資料條件**
- 可執行的長程終端機或程式設計任務集合，具備可靠的執行環境與正確性回饋（如測試通過與否、驗證腳本輸出）。
- 與下游評估基準分離的演化資料集，建議至少數百至數千筆，並經過實例層級相似度過濾與領域分析，避免資料洩漏。
- 同一任務的成功與失敗軌跡對（contrastive trajectories），用於定位系統性框架缺陷。

**運算條件**
- 可重現、可隔離的沙箱執行環境（如容器或虛擬機），支援任意程式碼與指令執行。
- 基礎模型 API 或自有推理資源，用於產生軌跡與演化模組。
- 足夠的運算資源進行多輪演化、模組獨立驗證與整合後評估。

**技能條件**
- 智能體框架工程能力：能夠將現有 harness 拆解為 Agent Loop、Tool Use、Observation Management、Context Management、Task Completion Detection 等功能模組。
- 提示工程與大型語言模型調校經驗。
- 軟體測試與評估設計能力，能建立可靠的 correctness feedback。
- 對目標領域（如 DevOps、資安、軟體工程）有一定理解，以便設計高品質演化任務。

## 實作步驟建議

1. **模組化現有 Harness**  
   將現有智能體框架對應到五大功能模組：Agent Loop、Tool Use、Observation Management、Context Management、Task Completion Detection。定義各模組的介面與受限修改範圍，確保後續可獨立演化。

2. **建立與基準分離的演化資料集**  
   從外部來源蒐集可執行任務，並透過相似度過濾與領域分析，確保與下游評估基準（如 TerminalBench 2.0、SWE-Bench Verified）不重疊。每個任務都需配備可靠的評估器。

3. **產生對比軌跡**  
   使用基線框架在演化任務上執行，收集同一任務的成功與失敗軌跡。若任務本身無成功軌跡，可透過更強模型或人工示範產生參考成功軌跡。

4. **聚合重複出現的行為缺陷**  
   對比成功與失敗軌跡，辨識跨任務重複出現的系統性框架缺陷，例如「頻繁重複相同工具呼叫」「忽略關鍵錯誤訊息」「過早回報完成」等。

5. **獨立演化各模組並驗證**  
   針對定位到的缺陷，在受限修改範圍內獨立演化對應模組。每個模組的修改都需通過正確性、可執行性與任務特定過度擬合檢驗，未通過則捨棄。

6. **整合演化後的模組**  
   將各模組的改進合併為統一框架，偵測並解決模組間衝突（例如 Context Management 與 Observation Management 對上下文長度的不同假設）。

7. **凍結框架並進行下游評估**  
   演化完成後凍結框架，在完全未見的同領域與跨領域任務上進行評估，確認泛化能力與跨基礎模型遷移性。

8. **產品化部署與持續監控**  
   將演化後的框架嵌入 CI/CD、IDE 外掛或事件回應系統，並持續收集生產軌跡，作為下一輪模組化演化的輸入。

## 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **演化資料仍隱含下游模式** | 即使與基準分離，外部資料仍可能包含與評估任務相似的領域模式，導致基準特定適應。 | 加強實例層級相似度過濾、領域分析，並保留完全獨立的 hold-out 驗證集。 |
| **模組間衝突** | 獨立演化的模組合併後，可能因介面或假設不一致而產生非預期行為。 | 設計明確的模組介面與整合階段衝突解決機制，並進行端到端迴歸測試。 |
| **過度擬合演化任務** | 修改可能只對演化資料有效，對未見任務無效甚至有害。 | 每個模組修改都需通過未見任務驗證，並採用對比式證據聚合而非單軌跡更新。 |
| **執行安全性** | 長程終端機任務常涉及任意程式碼執行，存在資料外洩或系統破壞風險。 | 使用嚴格隔離的沙箱、最小權限原則、網路限制與人工審核閘門。 |
| **驗證成本高昂** | 每個模組修改都需多次執行與驗證，運算與時間成本可觀。 | 優先驗證高頻缺陷對應的模組，並使用輕量級 smoke test 篩選明顯錯誤的修改。 |
| **跨基礎模型遷移衰減** | 在某個基礎模型上演化的框架，換到另一模型後效果可能下降。 | 在產品上線前於目標模型進行遷移評估，必要時針對該模型進行少量適應。 |

## 與其他技術的整合建議

- **CI/CD 管線**：將演化後的框架整合至 GitHub Actions、GitLab CI 或 Jenkins，作為自動化程式碼審查、bug 修復或部署驗證的一環。模組化設計讓「工具使用」與「任務完成偵測」模組可隨著組織工具鏈演進而獨立更新。

- **可觀察性平台**：對接 Langfuse、Weights & Biases 或自研軌跡記錄系統，持續收集生產環境的成功與失敗軌跡，作為下一輪對比式演化的資料來源。

- **LLM 閘道與政策層**：透過 LLM 閘道統一管理模型呼叫、速率限制與成本，並在政策層設定禁止執行的指令清單，補強框架本身的安全邊界。

- **檢索增強生成（RAG）**：將 Context Management 模組與內部知識庫、文件檢索系統結合，讓代理在長程任務中能動態取得領域知識，而非僅依賴模型參數記憶。

- **事件管理與協作工具**：對接 PagerDuty、Slack 或 Jira，讓 DevOps／SRE 智能體在沙箱中完成初步排查後，自動產生結構化報告並移交人工處理。

- **容器編排與隔離執行環境**：使用 Kubernetes、Firecracker 或雲端沙箱服務動態建立任務專屬執行環境，確保每個長程任務都在乾淨、可重現的環境中執行。

## 給不同背景讀者的閱讀建議

**初學者**：建議先聚焦「為什麼要模組化」與「對比式學習」這兩個核心概念。把 ModularRSI 想像成「讓智能體框架像拼圖一樣，一塊一塊地改進，而不是整塊重雕」，並理解成功與失敗軌跡的對比能幫助框架找出真正的系統性問題。技術細節如模組介面設計與整合衝突解決可先略讀。

**AI 工程師**：請重點閱讀五大功能模組的劃分方式、受限修改範圍的實作細節，以及整合階段的衝突解決機制。這些內容直接影響框架能否在實際系統中穩定演化。同時建議關注驗證流程與沙箱設計，因為它們決定了產品化的可行性與安全性。

**研究人員**：建議深入分析論文提出的 credit-assignment 問題與 benchmark-disjoint 演化協定。對比式軌跡聚合、跨任務證據累積，以及模組獨立演化對泛化能力的貢獻，都是值得延伸的研究方向。也可思考如何將此框架擴展到程式設計與終端機任務以外的長程決策領域。

**產品經理**：請優先理解適用場景、潛在風險與整合建議。ModularRSI 的價值在於提升智能體框架的可維護性與跨任務泛化能力，適合需要長期運營的企業級代理產品。部署時務必預留沙箱、人工審核與 A/B 測試資源，並將「模組可獨立更新」視為降低維護成本與加速迭代的重要賣點。
