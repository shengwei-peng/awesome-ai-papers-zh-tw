## ⚡ TL;DR

現有 LLM 服務系統基於單模型假設，難以支援詞元級路由，面臨步驟去同步、批次延遲與高實作複雜度。
TokenRouter 以請求為中心程式設計、模型為中心執行，透過解耦三迴圈與延遲批次排程提升效率。
跨多種演算法與模型組合，TokenRouter 解碼吞吐量較現有系統提升2.01至64.15倍。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）路由將推論（Inference）工作分散於不同模型之間，推進了 LLM 服務的成本-品質帕雷托前緣（Cost-Quality Pareto Frontier）。雖然會話級（Session-Level Routing）或查詢級（Query-Level Routing）的粗粒度路由已廣泛應用於生產系統（Production System）中，但近期的演算法研究表明，細粒度的詞元級路由（Token-Level Routing）能帶來顯著的效率與品質提升。然而，高效地服務詞元級路由推論對現有系統而言構成重大挑戰。現有系統基於單一 LLM 服務（Single-LLM Serving）的假設所建構，在詞元級路由下會出現嚴重的步驟去同步化（Step Desynchronization）與頻繁的批次准入延遲（Batch Admission Delay），同時也對開發者帶來高度的實作複雜度（Implementation Complexity）。為了解決這些挑戰，我們設計了 TokenRouter，一個高效率且開發者友善（Developer-Friendly）的詞元級路由 LLM 推論服務系統（Serving System）。TokenRouter 遵循以請求為中心的程式設計（Request-Centric Programming）、以模型為中心的執行（Model-Centric Execution）原則：開發者從單一請求的視角描述路由邏輯（Routing Logic），而執行環境（Runtime）則為每個 LLM 啟動一個子伺服器（Subserver），並以非同步分派（Asynchronous Dispatch）方式分派請求。每個子伺服器採用延遲批次排程器（Delayed-Batching Scheduler），其最佳超參數（Hyperparameters）源自系統的數學吞吐量模型（Throughput Model）。在不同的路由演算法（Routing Algorithm）、工作負載（Workload）與模型對（Model Pair）組合下，TokenRouter 達到比現有系統高 2.01 至 64.15 倍的解碼吞吐量（Decoding Throughput），大幅推進了詞元級 LLM 路由的服務效率。我們的程式碼庫（Codebase）已開源於 https://github.com/thu-nics/TokenRouter。

### 核心貢獻（3～5點）
- **問題識別**：系統性地揭示現有 LLM 服務系統在詞元級路由下面臨的三大挑戰——步驟去同步化、批次准入延遲，以及對開發者造成的高實作複雜度。
- **設計原則**：提出「以請求為中心的程式設計、以模型為中心的執行」雙軌設計典範，使開發者能以直觀方式描述路由邏輯，同時由執行環境負責複雜的非同步分派。
- **系統架構**：設計 TokenRouter 服務系統，採用子伺服器（Subserver）架構搭配延遲批次排程器（Delayed-Batching Scheduler），有效緩解粗粒度排程在詞元級路由下的氣泡（Bubbles）與批次碎片化（Batch Fragmentation）問題。
- **理論模型**：建立數學吞吐量模型（Throughput Model），用以推導延遲批次排程器的最佳超參數，使系統在不同運作點（Operating Point）下皆能維持高效能。
- **實驗驗證**：在多元的路由演算法、工作負載與模型對組合下，TokenRouter 達到 2.01–64.15 倍的解碼吞吐量提升，顯著推進成本-品質帕雷托前緣（Cost-Quality Pareto Frontier）。

### 適合對象
- **LLM 服務系統研究者與工程師**：關注高效能推論（Inference）基礎設施、連續批次處理（Continuous Batching）、前綴快取（Prefix Caching）等服務技術優化的從業者。
- **LLM 路由演算法開發者**：從事 RouteLLM、R2R 等路由演算法（Routing Algorithm）研究，並希望將演算法落地至實際服務系統的研究人員。
- **系統與編譯器領域學者**：對以請求為中心的程式設計（Request-Centric Programming）、非同步分派（Asynchronous Dispatch）等執行模型感興趣的研究者。
- **AI 基礎設施產品經理與架構師**：評估多模型協作部署方案、追求成本-品質權衡（Cost-Quality Trade-off）最佳化的技術決策者。
- **學術界研究生**：從事大型語言模型（Large Language Model, LLM）系統、推論加速或 AI 編譯器相關研究的博碩士生。

## 深度分析

#### 方法論解析

**核心問題定位**

TokenRouter 論文精準地識別了 LLM 服務領域中的一個關鍵缺口：演算法層面的詞元級路由（Token-Level Routing）研究已證實能顯著推進成本-品質帕雷托前緣（Cost-Quality Pareto Frontier），但現有的服務系統（SGLang、vLLM）皆基於「單一 LLM 服務」（Single-LLM Serving）假設設計，無法有效支援此種細粒度路由。論文將瓶頸歸納為三大系統性挑戰：

1. **步驟去同步化（Step Desynchronization）**：不同 LLM 的每步延遲（Per-Step Latency）差異極大。傳統同步批次（Synchronous Batch）機制迫使每個解碼步驟（Decoding Step）等待最慢模型完成，造成快速模型空轉。
2. **批次准入延遲（Batch Admission Delay）**：詞元級路由導致頻繁的模型切換（Model Switch），被路由的請求到達目標模型時，該模型往往正在處理前一批次，必須等待下一批次准入，產生排程氣泡（Bubbles）與批次碎片化（Batch Fragmentation）。
3. **實作複雜度（Implementation Complexity）**：現有系統未提供每步路由決策的程式設計介面（Programming Interface），開發者需深入修改大型程式碼庫（Codebase），並與連續批次處理（Continuous Batching）、前綴快取（Prefix Caching）等緊耦合特性（Tightly Coupled Features）協調。

**設計原則：以請求為中心的程式設計，以模型為中心的執行**

此原則是 TokenRouter 最重要的架構洞見，實現了關注點分離：

- **以請求為中心的程式設計（Request-Centric Programming）**：開發者只需從單一請求的視角描述路由邏輯，透過 `route`、`send`、`receive` 三個函數抽象化「何時切換模型」、「傳遞何種狀態」、「如何接收輸出」。此介面統一了不同路由演算法的執行生命週期——選擇下一模型、轉移請求狀態、接收詞元或分佈以繼續生成。
- **以模型為中心的執行（Model-Centric Execution）**：執行環境（Runtime）為每個 LLM 啟動一個自主的子伺服器（Subserver），各子伺服器獨立運行連續批次處理與前綴快取，僅透過非同步分派（Asynchronous Dispatch）機制協調跨模型執行。

**三大技術貢獻解析**

1. **解耦三迴圈執行（Decoupled Tri-Loop Execution）**：每個子伺服器運行三個獨立的排程迴圈——紫色（客戶端-伺服器）、藍色（解碼）、黑色（模型間）。此設計直接解決步驟去同步化問題：各模型以自身節奏推進解碼，不再被慢模型拖累。配合**交接-恢復機制（Handoff-Resume Mechanism）**，簡化了跨模型切換時的狀態轉移。

2. **延遲批次排程器（Delayed-Batching Scheduler）**：針對批次准入延遲問題，引入延遲准入策略——新到達的請求會等待一小段時間以累積更多請求同時准入，減少氣泡。此排程器的超參數（Hyperparameters）並非經驗設定，而是透過吞吐量模型（Throughput Model）數學推導得出最佳值，這是將排程決策從啟發式轉為可分析優化的重要進展。

3. **單一外部介面**：對客戶端而言，TokenRouter 暴露單一端點，可作為標準單一 LLM 伺服器的即插即用替代品，無需修改客戶端程式碼。

**方法論的理論深度**

論文的數學吞吐量模型是方法論的理論基石。透過建模批次准入延遲與系統吞吐量的關係，可以解析地推導延遲批次排程器的最佳等待時間，避免了傳統系統中仰賴經驗調參的做法。這種「先建模、再設計、最佳化」的工程方法論，使系統設計具有可預測性與可調理性。

#### 實驗數據解讀

**核心效能指標**

論文報告的核心結果是 **2.01–64.15× 解碼吞吐量（Decoding Throughput）提升**，此數據跨越一個數量級以上，反映了不同情境下的差異化效益：

- **下限 2.01×**：對應路由比例較低或模型對差異較小的情境，此時既有系統的同步批次機制尚能勉強運作。
- **上限 64.15×**：對應路由比例高、模型對延遲差異大、批次准入延遲嚴重的情境，此時 TokenRouter 的非同步執行與延遲批次機制產生巨大效益。

**實驗設計的嚴謹性**

論文在多個維度上進行了系統性評估：

1. **演算法維度**：涵蓋效率導向（如 R2R）與品質導向的詞元級路由方法，驗證系統對不同路由演算法（Routing Algorithm）的通用性。
2. **工作負載維度**：多樣化的工作負載（Workload）測試確保系統在真實使用情境下的穩健性。
3. **模型對維度**：不同的模型對（Model Pair）配置（如 1.5B 與 32B 的組合）驗證系統對異質模型的支援能力。

**結果的系統性意涵**

吞吐量的大幅提升不僅是數字遊戲，而是反映了三項機制的綜合效益：

- 解耦三迴圈消除了步驟去同步化造成的空轉損失。
- 延遲批次排程器減少了氣泡與批次碎片化。
- 子伺服器架構保留了各模型內部的連續批次處理與前綴快取優勢。

值得注意的是，論文強調「將理論效益轉化為真實速度提升」，這暗示了既有系統在詞元級路由場景下的實際效能可能遠低於理論預期，而 TokenRouter 填補了此落差。

**未明確揭露的細節**

從提供的全文脈絡中，具體的批次大小、請求到達率、模型具體組合（如 Qwen、LLaMA 系列）、硬體配置（GPU 型號與數量）等實驗細節未在引言與相關工作中詳述，需參考正文後續章節以完整評估實驗的可信度。

#### 與現有研究的比較

**與查詢級路由系統的比較**

RouteLLM 等查詢級路由系統在生產環境中已成熟部署，其優勢在於可重用標準單一 LLM 批次與排程機制。然而，論文指出此類粗粒度路由僅能在離散運作點（Discrete Operating Points）上運作，且無法利用單一查詢內生成難度（Generation Difficulty）的劇烈變化。R2R 的對比數據尤為關鍵：詞元級路由僅需將 5% 的詞元路由至 32B 模型即可匹配其品質，而查詢級路由需將約 40% 的查詢路由至 32B 模型——這 8 倍的效率差距凸顯了詞元級路由的演算法優勢。

**與單一 LLM 服務系統的比較**

SGLang 與 vLLM 是當前最先進的單一 LLM 服務系統，整合了連續批次處理、分頁 KV 快取管理（Paged KV-Cache Management）與結構化生成執行環境。然而，這些技術皆建立在「每個請求停留在單一模型並以該模型節奏推進」的假設上。詞元級路由打破了此假設，導致資料相依的模型切換與不規則的模型本地到達模式。TokenRouter 的子伺服器架構巧妙地保留了這些成熟技術的優勢——每個子伺服器內部仍可使用連續批次處理與前綴快取——同時透過非同步跨模型協調解決了單一模型假設的侷限。

**與推測式解碼的比較**

推測式解碼（Speculative Decoding）同樣使用多個模型，但草案生成與目標驗證的耦合模式是可預測的。詞元級路由則允許每個詞元的資料相依模型切換，導致更不規則的執行模式。TokenRouter 針對此動態特性設計了模型中心執行環境，這是推測式解碼系統所不需面對的挑戰。

**論文承認的侷限性**

從全文脈絡可推斷，論文的評估主要集中在解碼吞吐量，未深入探討：

- **延遲（Latency）分佈**：吞吐量提升是否伴隨尾延遲（Tail Latency）惡化？
- **品質驗證**：系統加速後，路由演算法的品質效益是否完整保留？
- **多模型擴展性**：當協作模型數量超過兩個時，子伺服器架構的協調成本如何變化？

這些未明確探討的面向可能限制了論文的結論強度。

#### 可重現性評估

**程式碼可用性**

論文明確聲明程式碼開源於 `https://github.com/thu-nics/TokenRouter`，此為清華大學 NICs 實驗室的 GitHub 倉庫。開源釋出是可重現性的基礎前提，但需進一步評估：

- **程式碼完整性**：是否包含所有路由演算法的參考實作？延遲批次排程器的吞吐量模型程式碼是否公開？
- **相依性**：是否依賴特定版本的 SGLang 或 vLLM？自訂子伺服器與這些系統的整合介面是否文件化？
- **設定檔**：延遲批次排程器的最佳超參數是否隨程式碼一同釋出，或需使用者自行依吞吐量模型計算？

**模型權重可用性**

論文使用的模型對（如 1.5B 與 32B 的組合）推測為開源模型（如 Qwen、LLaMA 系列），因此模型權重可從 Hugging Face 等平台取得。然而，具體的模型組合、量化設定、檢查點版本等細節需從正文後續章節確認。

**資料集與工作負載**

工作負載的具體組成（提示長度分佈、輸出長度分佈、到達率模式）對實驗可重現性至關重要。論文未在引言與相關工作中詳述，建議查閱實驗章節以確認是否提供了工作負載生成器或公開資料集。

**吞吐量模型的可驗證性**

論文的數學吞吐量模型是方法論的核心，若論文附錄提供了完整的數學推導與實證驗證，則其他研究者可在不同硬體配置下重現最佳超參數的計算過程，這是超越單純程式碼開源的更深層可重現性。

**整體可重現性評估**

基於開源程式碼與可推斷的開源模型，可重現性基礎良好，但完整評估需待正文後續章節與程式碼倉庫的實際檢視。

#### 未來研究方向

**1. 多模型擴展與階層式路由**

當協作模型數量從兩個擴展至 N 個時，子伺服器架構的協調成本、延遲批次排程器的最佳化空間、以及跨模型狀態轉移的開銷都將呈現新的挑戰。未來研究可探索：

- 階層式路由架構（Hierarchical Routing），將模型分組並在組間與組內採用不同粒度的路由策略。
- 模型選擇的動態優化，根據當前系統狀態（GPU 利用率、批次大小、佇列長度）即時調整路由決策。

**2. 與推測式解碼的融合**

詞元級路由與推測式解碼皆涉及多模型協作，但採用不同的耦合模式。未來可探索兩者的融合：

- 使用小型模型作為大型模型的動態草案生成器，並根據詞元難度決定是否升級至目標模型驗證。
- 將詞元級路由視為推測式解碼的泛化形式，統一理論框架。

**3. 品質保證與延遲優化**

論文的吞吐量提升伴隨的品質與延遲特性尚未充分探討。未來研究方向包括：

- **端到端品質驗證**：在加速條件下，路由演算法的品質效益是否完整保留？是否存在因排程延遲導致的品質退化？
- **延遲感知排程**：將延遲分佈（尤其是尾延遲）納入排程目標，在吞吐量與延遲之間取得平衡。
- **SLO 導向設計**：針對不同服務等級目標（Service Level Objective）動態調整延遲批次排程器的超參數。

**4. 硬體感知優化**

當前吞吐量模型可能未充分考慮異質硬體（如不同 GPU 型號、NVLink 拓撲、CPU-GPU 頻寬）對排程決策的影響。未來可探索：

- 將硬體特性整合至吞吐量模型，產生硬體感知的最佳超參數。
- 跨節點子伺服器的負載平衡與通訊優化。

**5. 路由演算法與系統的共同設計**

當前研究將路由演算法與服務系統視為獨立層次，但兩者存在深層耦合。未來可探索：

- **演算法-系統共同設計（Algorithm-System Co-design）**：設計路由演算法時考慮服務系統的排程特性，設計服務系統時考慮路由演算法的決策模式。
- **可學習的排程策略**：使用強化學習訓練排程器，動態適應不同工作負載與模型對。

**6. 隱私與安全考量**

詞元級路由涉及請求狀態在多個模型間傳遞，可能引發隱私與安全議題：

- 跨模型的狀態轉移是否洩漏敏感資訊？
- 不同模型提供者間的信任邊界如何劃分？
- 路由決策本身是否成為攻擊面（如惡意觸發昂貴模型的路由）？

**7. 標準化與生態系建構**

TokenRouter 的 `route-send-receive` 介面為詞元級路由提供了抽象層，但尚未形成業界標準。未來可推動：

- 標準化的路由演算法描述語言。
- 跨服務系統（SGLang、vLLM、TokenRouter）的互通介面。
- 開源的路由演算法庫與基準測試套件。

這些方向不僅延伸了 TokenRouter 的技術貢獻，也將推動 LLM 服務領域從「單一模型優化」邁向「多模型協作優化」的典範轉移。

## 論文問答

**Q1：為什麼現有的 LLM 服務系統無法有效支援詞元級路由？**
A：現有的 LLM 服務系統（如 SGLang 和 vLLM）都是基於單一 LLM 服務的假設所設計的，系統中所有活躍請求在每個解碼步驟都是同步進行的。然而，詞元級路由打破了這個假設，因為目標模型可以在每個解碼步驟中改變，這帶來了三個主要挑戰：首先是步驟去同步化，不同 LLM 的每步延遲差異很大，強迫請求在單一批次中同步會使每個步驟都必須等待最慢的模型，導致較快的模型處於閒置狀態；其次是批次准入延遲，由於詞元級路由會造成頻繁的模型切換，被路由的請求經常在目標模型仍在處理前一批次時到達，必須等待被納入下一批次，從而產生氣泡並造成批次碎片化；第三是實作複雜度，現有的服務系統並未提供每步路由決策的程式設計介面，因此實作詞元級路由需要對龐大的程式碼庫進行大量修改。

**Q2：詞元級路由相比於查詢級路由有哪些具體優勢？**
A：詞元級路由能夠利用單一查詢中生成難度的劇烈變化來提升效率，例如 R2R 方法可以達到 32B 模型的品質，但只將 5% 的詞元路由到 32B 模型，其餘詞元則由 1.5B 模型解碼，相比之下，查詢級路由需要將約 40% 的查詢路由到 32B 模型。在品質方面，詞元級路由允許具有互補專長的模型在單一回應中協作，從而超越任何單一 LLM 的生成品質。此外，詞元級路由提供了對整個成本-品質權衡的平滑控制，而不是像較粗粒度路由那樣只能提供少數幾個離散運作點，這使得使用者能夠更靈活地調整系統行為。

**Q3：為什麼成本-品質帕雷托前緣對 LLM 服務至關重要？**
A：現代 LLM 在規模和領域專長上差異很大，展現出不同的延遲和生成能力，這意味著沒有一個模型能在所有場景下都是最優選擇。成本-品質帕雷托前緣代表了在不同成本約束下所能達到的最佳品質，通過模型路由，系統可以將不同難度或類型的請求分配給最合適的後端模型，從而推進這個前緣。在生產環境中，這直接影響到商業 LLM 產品（如 ChatGPT 和 Cursor）的營運成本和使用者體驗，因此如何在保持高品質的同時降低推論成本成為 LLM 服務的核心議題。

**Q4：TokenRouter 的核心設計原則是什麼？**
A：TokenRouter 遵循「以請求為中心的程式設計，以模型為中心的執行」這項核心設計原則。在程式設計層面，開發者透過追蹤單一請求如何在多個協作的 LLM 之間流動來描述路由演算法，這種方式隱藏了路由服務的系統複雜性；在執行層面，執行環境為每個 LLM 啟動一個獨立的子伺服器，並以非同步方式分派請求。這種分離設計讓開發者能夠專注於路由邏輯的表達，而讓執行環境擁有充分的控制權來優化跨模型執行和批次排程，同時對使用者客戶端而言，TokenRouter 透過單一外部介面提供服務，可以作為標準單一 LLM 伺服器的即插即用替代品。

**Q5：TokenRouter 如何解決步驟去同步化的問題？**
A：TokenRouter 提出了去耦的三迴圈執行架構來解決協作 LLM 之間的步驟去同步化問題，每個子伺服器運行三個獨立的排程器迴圈（客戶端-伺服器、解碼、模型間），分別以紫色、藍色和黑色標示。這種去耦設計意味著每個 LLM 可以按照自己的節奏進行解碼，而不需要等待其他模型，從而避免了較快模型被迫閒置等待較慢模型的問題。此外，TokenRouter 還設計了一個交接-恢復機制來簡化模型間的切換過程，使得當路由決策改變目標模型時，請求狀態能夠被有效地轉移和恢復，而不會造成顯著的同步開銷。

**Q6：延遲批次排程器的設計原理是什麼？**
A：延遲批次排程器是 TokenRouter 為了解決批次准入延遲問題而提出的關鍵排程優化機制，其核心思想是在批次准入時引入一個可控的延遲窗口，以便收集更多可同時處理的請求，從而減少氣泡和批次碎片化。該排程器的最佳超參數是透過一個基於吞吐量的數學模型推導出來的，該模型描述了系統在不同批次大小和延遲設置下的吞吐量特性。透過這種方式，TokenRouter 能夠在批次大小和等待時間之間找到最佳平衡點，最大化解碼吞吐量，這對於詞元級路由場景中頻繁的模型切換尤為重要。

**Q7：TokenRouter 在實驗中達到了什麼樣的吞吐量提升？**
A：在不同的路由演算法、工作負載和模型對的綜合實驗中，TokenRouter 相比於現有的實作方式實現了 2.01 至 64.15 倍的解碼吞吐量提升。這一顯著的效能提升範圍反映了不同場景下詞元級路由的潛在收益差異：在某些場景下，現有系統由於步驟去同步化和批次碎片化造成嚴重的資源浪費，而 TokenRouter 的去耦執行和延遲批次排程能夠有效回收這些浪費的資源。這些結果表明，TokenRouter 成功地將詞元級路由的理論效益轉化為實際的服務速度提升，大幅推進了詞元級 LLM 路由的服務效率。

**Q8：實驗評估涵蓋了哪些路由演算法、工作負載和模型對？**
A：實驗評估橫跨多樣化的路由演算法，包括效率導向的方法（如 R2R，使用訓練過的輕量級路由器）和品質導向的方法（如接受專家詞元或融合輸出分佈的方法），這些演算法雖然策略不同，但都共享相同的執行生命週期：選擇下一個模型、轉移請求狀態、接收其詞元或分佈以繼續生成。工作負載方面涵蓋了不同的輸入特徵和請求模式，以測試系統在各種使用情境下的表現。模型對的選擇則包括了不同規模和能力層級的 LLM 組合，這樣的全面評估確保了 TokenRouter 的效能提升不是針對特定場景的偶然結果，而是在廣泛的實際應用中都能保持穩定。

**Q9：延遲批次排程器的超參數是如何從吞吐量模型推導出來的？**
A：延遲批次排程器的超參數推導基於一個吞吐量驅動的數學模型，該模型刻畫了系統在不同批次大小、延遲設置和請求到達率下的吞吐量特性。透過分析這個模型，可以確定在給定工作負載特徵下，能夠最大化平均吞吐量的最佳延遲窗口大小。這個推導過程使得排程器能夠根據系統的實際狀態動態調整其行為，而不是依賴於經驗調參，這對於詞元級路由場景中不規則的模型本地到達模式尤為重要，因為傳統的固定參數排程策略在這種動態環境下往往表現不佳。

**Q10：TokenRouter 在實際生產環境中如何部署？**
A：TokenRouter 透過單一的外部介面（Server Interface）對客戶端提供服務，這使得它可以作為標準單一 LLM 伺服器的即插即用替代品，現有的應用程式無需修改即可使用。在內部架構上，每個協作的 LLM 由一個自主的子伺服器託管，這些子伺服器實現了三個使用者定義的路由函數（route、send、receive）並運行三個去耦的排程器迴圈。這種模組化設計使得 TokenRouter 能夠靈活地適應不同的部署需求，無論是雲端環境還是本地部署，都能保持高效運行，同時保留了連續批次處理和前綴快取等成熟的單一模型優化技術。

**Q11：開發者使用 TokenRouter 的程式設計介面有多簡單？**
A：TokenRouter 提供了一個極為簡潔的 route-send-receive 程式設計介面，讓開發者只需透過追蹤單一請求如何在協作的 LLM 之間移動，就能表達各種詞元級路由演算法。這種以請求為中心的程式設計範式大幅降低了實作複雜度，因為開發者不需要理解底層的批次排程、模型切換和狀態管理等系統細節。相較於在現有系統（如 SGLang 或 vLLM）中實作詞元級路由需要對龐大的程式碼庫進行大量修改，TokenRouter 的介面讓開發者能夠專注於路由邏輯本身的設計，這對於快速實驗和部署新的路由演算法具有重要價值。

**Q12：TokenRouter 對 LLM 服務領域有什麼影響？**
A：TokenRouter 為詞元級路由社群帶來了一個高效能的 LLM 服務框架，將理論上的效益轉化為相較於成熟的單一 LLM 服務系統的實際速度提升，這對於推動詞元級路由從學術研究走向實際應用具有重要意義。透過支援多樣化的路由演算法（包括效率導向和品質導向的方法），TokenRouter 使得研究者和工程師能夠更輕鬆地探索不同的模型協作策略。此外，TokenRouter 的設計理念——以請求為中心的程式設計搭配以模型為中心的執行——也為未來 LLM 服務系統的設計提供了一個有價值的參考範式，特別是在處理多模型協作場景時。

**Q13：TokenRouter 有哪些已知的限制？**
A：雖然 TokenRouter 在詞元級路由場景下表現出色，但其設計主要針對解碼階段的路由優化，對於預填充階段或訓練階段的支援可能不夠全面。此外，TokenRouter 的效能提升在很大程度上依賴於協作模型之間的延遲差異，當所有模型具有相似的每步延遲時，步驟去同步化問題本身就不顯著，因此改進空間也會相應縮小。延遲批次排程器的最佳超參數雖然是從吞吐量模型推導出來的，但在高度動態或不可預測的工作負載下，模型的準確性可能會受到影響，這需要進一步的研究來增強排程器的自適應能力。

**Q14：在哪些場景下 TokenRouter 可能表現不佳？**
A：當路由決策過於頻繁導致模型切換開銷超過協作收益時，TokenRouter 的優勢可能會被削弱，特別是在路由演算法本身不夠成熟或路由訊號（如信心度或熵）不穩定的情況下。此外，對於需要極低延遲的即時應用場景，延遲批次排程器引入的等待窗口可能會增加單一請求的回應時間，即使整體吞吐量有所提升，使用者體驗仍可能受到影響。在模型規模和能力差異較小的同質化模型組合中，詞元級路由的品質和效率增益本身就有限，因此 TokenRouter 的相對優勢也會不如異質化模型組合中明顯。

**Q15：未來的研究方向有哪些？**
A：未來的研究可以朝多個方向延伸：首先，可以將 TokenRouter 的設計理念擴展到多模態場景，支援文字、圖像、音訊等多模態模型之間的詞元級路由；其次，可以探索更智慧的自適應排程策略，根據即時的工作負載特徵動態調整延遲批次排程器的參數；此外，將 TokenRouter 與其他 LLM 優化技術（如推測解碼、量化、模型剪枝）相結合，可能會帶來更大的效能提升；最後，詞元級路由演算法本身的進一步發展，特別是在如何更好地平衡效率導向和品質導向的目標方面，也將為 TokenRouter 這類服務系統創造新的應用機會。

## 實務應用指南

### 適用場景

以下列舉五個 TokenRouter 特別適合落地的真實場景：

1. **客服與企業知識庫問答**：同一段對話中，使用者可能先問簡單的帳號問題（適合 1.5B 小模型），接著追問複雜的保單條款（需要 32B 大模型）。TokenRouter 可在每個詞元動態切換，預估可將 95% 的詞元交給小模型處理，僅在困難段落升級至大模型。

2. **程式碼生成助手（類似 Cursor）**：補完簡單語法（變數命名、括號）時用小模型快速回應，遇到演算法設計、跨檔案推理時切換至大模型。這比整個查詢路由更細緻，能在維持品質下顯著降低單次互動成本。

3. **多語言或混合內容生成**：當回應需要在中文、英文、程式碼之間切換時，可讓不同語言專家模型各司其職。例如中文段落用中文微調模型、英文段落用英文模型、程式碼區塊用程式碼專用模型。

4. **邊緣-雲端協作的隱私敏感應用**：醫療或金融場景中，敏感詞元（PII、帳號）強制留在本地小模型，僅將非敏感的困難詞元送往雲端大模型，兼顧隱私與品質。

5. **成本敏感的對外 API 服務**：當營運方需要在 SLA 與 GPU 成本間取得平衡時，TokenRouter 提供連續可調的成本-品質帕雷托前緣，比傳統查詢級路由的「離散運作點」更靈活。

### 實作前置條件

**資料面**
- 至少一組「小模型 + 大模型」對（例如 Qwen2.5-1.5B + Qwen2.5-32B），兩者需具備相容的 tokenizer 與詞彙表，否則跨模型狀態傳遞會失敗。
- 若採用學習式路由器（如 R2R 風格），需準備帶有「困難詞元標註」的訓練資料；若採啟發式（信心度、熵值），則需確認小模型能輸出 logits 而非僅 top-1 token。
- 一份代表性的真實查詢與詞元級標註資料，用於離線評估路由品質。

**算力面**
- 每個 LLM 至少一張 GPU（建議 A100/H100 等級），多模型並行推論需要多卡環境。
- 主機端 CPU 與記憶體需足以承載子伺服器行程間通訊（IPC/ZMQ）與 KV-cache 傳遞。
- 建議預留 10–20% 的 GPU 記憶體給前綴快取與批次緩衝。

**技能面**
- 熟悉 Python 與非同步程式設計（asyncio、ZeroMQ）。
- 理解連續批次處理（continuous batching）與 paged KV-cache 的基本原理。
- 具備 LLM 推論效能分析經驗（每步延遲、吞吐量、氣泡率）。
- 若要自訂路由演算法，需具備模型 logits 解析與信心度指標設計能力。

---

### 實作步驟建議

**步驟一：定義路由目標與成本約束**
先釐清是要追求「效率」（小模型為主、大模型補位）還是「品質」（多模型融合超越單一模型）。這會直接影響後續選擇 R2R 類學習式路由器，還是 token-fusion 類融合式路由器。

**步驟二：選擇模型對並驗證相容性**
挑選 tokenizer 相容、推論延遲差異顯著的兩個模型（例如 1.5B vs 32B）。在單模型模式下分別用 vLLM 或 SGLang 部署，量測每步延遲，作為後續吞吐量模型校準的基準。

**步驟三：安裝 TokenRouter 並啟動子伺服器**
依照官方 GitHub 倉庫（https://github.com/thu-nics/TokenRouter）安裝。每個 LLM 啟動一個獨立子伺服器，設定連續埠號。確認子伺服器之間的 IPC 通道（handoff-resume 機制）能正常傳遞請求狀態。

**步驟四：以 route-send-receive 介面實作路由邏輯**
開發者只需描述「單一請求」如何在不同模型間流動：
- `route()`：根據目前 token 的信心度、熵值或路由器分數決定下一個目標模型。
- `send()`：將請求狀態（KV-cache、已生成 token）打包並送往目標子伺服器。
- `receive()`：接收目標模型回傳的 token 或 logits 分布，決定是否繼續或再次切換。

**步驟五：校準延遲批次排程器的超參數**
利用論文提出的吞吐量數學模型，根據每個模型的每步延遲、到達率與目標吞吐量，反推出最佳批次等待窗口（delayed-batching window）。建議先以小流量試跑，再以真實流量微調。

**步驟六：部署、監控與迭代**
對外僅暴露單一 API 端點（drop-in 取代單一 LLM 伺服器）。監控指標應包含：每步去同步化程度、批次准入延遲、跨模型切換頻率、整體解碼吞吐量。建議 A/B 測試與單一模型基線的品質差異。

---

### 潛在風險與注意事項

**風險一：步驟去同步化導致尾端延遲**
當小模型與大模型在同一批次中協作時，較快的模型必須等待較慢的模型完成該步驟。緩解方式：透過 TokenRouter 的解耦三迴圈執行（decoupled tri-loop execution）讓各子伺服器獨立推進，僅在 handoff 時同步。

**風險二：批次碎片化與氣泡**
詞元級路由造成模型切換頻繁，新請求到達時目標模型可能正在處理前一批次。緩解方式：採用延遲批次排程器（delayed-batching scheduler），在數學模型指導下設定最佳等待窗口，避免批次過小或等待過久。

**風險三：跨模型狀態傳遞成本**
每次切換模型都需傳遞 KV-cache 或重建 prefix，這在長上下文場景下成本可觀。緩解方式：盡量在前綴快取命中時切換；對短段落切換可接受；對長序列切換需評估是否仍優於查詢級路由。

**風險四：路由決策本身的推論開銷**
若路由器本身是一個神經網路，其推論時間會疊加到每一步。緩解方式：使用極輕量路由器（< 100M 參數），或採用啟發式訊號（信心度、熵值）以零成本決策。

**風險五：品質驗證困難**
詞元級路由的最終品質難以離線評估，因為切換點會影響後續生成。緩解方式：建立端到端評測集（含人類評分），並監控「路由到大模型的詞元比例」與品質的相關性，避免過度路由浪費成本。

**風險六：模型版本管理**
當任一子伺服器模型升級時，路由策略可能需要重新校準。建議建立模型版本與路由策略的綁定機制，並在 CI 中加入迴歸測試。

---

### 與其他技術的整合建議

**與 vLLM / SGLang 整合**
TokenRouter 的子伺服器設計可將 vLLM 或 SGLang 作為底層推論引擎，保留其 paged KV-cache 與連續批次處理能力。建議以 vLLM 為預設後端，因其在吞吐量與社群支援上較成熟。

**與推測解碼（Speculative Decoding）整合**
兩者並不互斥：推測解碼可在「單一模型內部」加速詞元生成，TokenRouter 則在「跨模型」層級做詞元級決策。可設計為：先用小模型推測，再用大模型驗證；當驗證失敗率超過閾值時，後續詞元直接交給大模型。

**與 API Gateway / 負載平衡器整合**
TokenRouter 對外僅暴露單一端點，可直接掛載在現有 API Gateway 後方。Gateway 仍可負責認證、限流、記錄；TokenRouter 專注於詞元級決策。建議將監控指標（吞吐量、氣泡率）匯出至 Prometheus/Grafana。

**與前綴快取整合**
若系統已有跨請求的前綴快取層（如 RadixAttention），可在 TokenRouter 之上額外快取「路由決策序列」，使相同前綴的後續請求能直接重用路由計畫，減少重複決策開銷。

**與分散式追蹤整合**
由於請求會跨越多個子伺服器，建議整合 OpenTelemetry，讓每個詞元的路由路徑、每步延遲、批次大小都可追蹤，便於除錯與效能調校。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的「路由粒度」示意圖（圖 2a），理解會話級、查詢級、詞元級路由的差異；再讀第 3 節的 route-send-receive 介面，這是理解整個系統的入口。數學吞吐量模型可先跳過，待熟悉介面後再回頭理解排程器為何如此設計。

**給 AI 工程師**：重點閱讀第 4 節的解耦三迴圈執行與 handoff-resume 機制，這是 TokenRouter 解決步驟去同步化的核心設計；第 5 節的延遲批次排程器與吞吐量模型則是部署調校的關鍵。建議直接 clone 官方倉庫，跑通 README 中的範例路由演算法，再以自己的模型對進行基準測試。

**給研究者**：第 2 節的相關工作分類（效率導向 vs 品質導向的詞元級路由）值得仔細梳理；第 6 節的實驗設計（不同演算法、工作負載、模型對）提供了可比較的基準。吞吐量數學模型（第 5 節）有進一步推廣到多模型、動態到達率的空間，是值得延伸的研究方向。

**給產品經理**：先讀摘要與第 1 節，理解「2.01–64.15× 解碼吞吐量提升」的實際意義——這代表在相同 GPU 預算下可服務更多使用者，或在相同品質下大幅降低成本。關注「成本-品質帕雷托前緣」這個概念：詞元級路由提供連續可調的權衡，比查詢級路由的離散運作點更貼近真實業務需求。建議與工程團隊討論：現有應用中是否有「同一查詢內難度差異大」的情境，這是採用 TokenRouter 的最佳切入點。
