## ⚡ TL;DR

前沿編碼代理生成樂高組裝時，常產生碰撞、懸浮或斷連等無效結構。
本文提出 BrickWright 與 BrickLayer，以驗證迴圈引導代理產出物理可行樂高組裝。
測試 512 個提示詞，BrickWright 將代理物理有效率提升至 100%，並優於專用模型。

## 摘要翻譯

前沿編碼代理（frontier coding agents）在三維建模方面日益嫻熟。然而，在建構預期在物理世界中組裝的物件時，它們仍面臨挑戰，常產生包含懸浮、碰撞或斷連零件的無效組裝。我們主張，為代理提供組裝工具並驗證其物理可行性，即足以使其產出物理有效、且仍遵循輸入提示詞的組裝。聚焦於樂高積木組裝領域，我們提出 BrickWright——一個使用預訓練代理從文字或圖像提示詞生成物理可行積木組裝的框架，其中若組裝僅使用真實零件、無碰撞或懸浮零件，且在可能情況下形成連接結構，則視為物理可行。BrickWright 引導代理透過使用 BrickLayer 撰寫程式碼來創建組裝，BrickLayer 是一個 Python 工具包，包含兩個主要元件：一個人因工程化的積木組裝 API（ergonomic brick assembly API），相較於直接使用原始 LDraw，可減少一半的推論成本；以及一個提供物理可行性回饋的驗證器（validator）。基準代理的物理有效率僅介於 9%（GPT-6 Luna）至 69%（GPT-6 Astra），而 BrickWright 引導的代理在 512 個提示詞的樣本上達到 100% 有效率，同時提升輕量級代理的提示詞遵循度，並使較強代理的遵循度維持不變。此外，它們在文字轉積木任務上表現優於專用模型。程式碼可於我們的專案頁面取得：https://avalovelace1.github.io/brickwright/

### 核心貢獻（3～5點）
- 提出 BrickWright 框架，透過「組裝工具＋物理可行性驗證」機制，解決前沿編碼代理在建構實體世界物件時產生懸浮、碰撞或斷連零件的問題。
- 設計 BrickLayer Python 工具包，提供人因工程化的積木組裝 API（相較原始 LDraw 降低一半推論成本）與即時回饋的物理可行性驗證器。
- 在 512 個文字／圖像提示詞樣本上，將物理有效率從基準代理的 9%–69% 提升至 100%。
- 同步改善輕量級代理的提示詞遵循度，並維持較強代理的遵循度不變。
- 在文字轉積木任務上，整體表現優於專用模型。

### 適合對象
從事生成式 AI 與代理式系統（agentic systems）研究、3D 建模與 CAD 自動化、LLM 工具使用（tool use）與程式碼生成、樂高積木設計與數位製造、以及具物理可行性之生成內容評測的研究者與工程師。

## 深度分析

#### 方法論解析

BrickWright 的核心論點在於：對於多零件實體組裝（multi-part assemblies）的生成任務，與其從頭訓練專用模型，不如為現成的大型語言模型（LLM）代理提供一套專門的工具組（toolkit），使其能在「計畫-執行-驗證迴圈」（plan-execute-validate loop）中自主產生物理上可行的組裝結果。這種「工具增強代理」（tool-augmented agent）路線的設計哲學，與傳統的端到端學習方法形成鮮明對比。

**BrickLayer 工具包的雙核心設計：**

第一個核心是**人因工程化的積木組裝 API**（ergonomic brick assembly API）。作者觀察到，雖然 LDraw 是樂高積木的標準 CAD 檔案格式，但其低階語法對 LLM 而言過於冗長且容易出錯。直接操作 LDraw 程式碼會消耗大量 token，且需要代理自行處理座標系統、零件 ID 查詢等瑣碎細節。BrickLayer 透過抽象化層，將「在指定位置放置特定零件」、「將積木堆疊在既有結構上」等高階語意操作封裝成簡潔的 Python 函式。實驗數據顯示，這種抽象化使推論成本（inference cost）降低約一半，這對於需要多次迭代修正的代理工作流程尤為關鍵。

第二個核心是**物理驗證器**（validator）。驗證器檢查四個維度的物理可行性：（1）所有零件是否來自真實的樂高零件庫（real parts）；（2）是否存在網格相交（mesh intersections），即碰撞（colliding parts）；（3）是否存在懸浮零件（floating parts），即未與主結構連接的孤立元件；（4）整體是否形成單一連接結構（connected structure）。驗證器不僅回報布林值的通過或失敗，更提供具體的錯誤位置與類型，使代理能進行針對性的修正。

**BrickWright 框架的工作流程：**

代理接收文字或圖像提示詞後，會被引導撰寫使用 BrickLayer API 的 Python 生成程式碼。接著執行「編譯與執行測試」（compile & run tests）階段，此時 BrickLayer 的驗證器會對產生的 LDraw 檔案進行物理可行性檢查。若檢查通過（checks pass），則輸出最終組裝結果；若檢查失敗（checks fail），代理會接收驗證器的回饋，進入「檢視結果並修訂」（inspect results & revise）階段，重新調整程式碼並再次驗證。這個迭代過程持續進行，直到產出物理有效的組裝或達到最大迭代次數。

**方法論的關鍵洞察：**

作者提出一個重要觀察：即使是最先進的代理（如 GPT-6 Astra 搭配 Codex），在沒有 BrickWright 的情況下，仍有超過 80% 的機率會自行撰寫驗證腳本。這顯示代理本身已具備「自我驗證」的傾向，但缺乏有效的工具來執行這項驗證。BrickWright 並非教導代理如何驗證，而是提供驗證所需的基礎設施，使代理能專注於設計決策而非除錯細節。

此外，作者強調零件的「程式化組裝規則」（programmatic rules for assembly）是樂高系統的核心特性。樂高積木的凸粒（studs）與反凸粒（antistuds）的卡接關係具有明確的幾何與物理規則，這使得將組裝過程抽象為 API 呼叫成為可能。這種「領域規則的形式化」是 BrickWright 能成功運作的基礎，也暗示了該方法可推廣至其他具有明確組裝規則的多零件系統。

#### 實驗數據解讀

**物理有效性的顯著提升：**

實驗在 512 個提示詞的測試集上進行，涵蓋文字與圖像兩種輸入形式。結果顯示，基準代理（baseline agents）的物理有效率（physical validity rate）差異極大：輕量級的 GPT-6 Luna 僅達到 9%，而較強的 GPT-6 Astra 可達 69%。然而，配備 BrickWright 後，所有代理——包括輕量級的 GPT-6 Luna 與 Claude Haiku 5.5——皆達到 100% 的物理有效率。

這個結果的意義在於：（1）BrickWright 完全消除了物理違規，無論代理的基礎能力如何；（2）輕量級代理的提升幅度最為驚人，從 9% 躍升至 100%，代表 BrickWright 有效降低了對代理推理能力的依賴；（3）即使是 GPT-6 Astra 這類較強代理，也從 69% 提升至 100%，顯示即使是頂尖模型也無法單獨保證物理可行性。

**提示詞遵循度（prompt adherence）的雙重效果：**

BrickWright 對提示詞遵循度的影響呈現代理能力依賴性：對於輕量級代理，BrickWright 顯著提升了其遵循提示詞的能力，這是因為驗證器的回饋幫助代理識別並修正偏離提示詞的設計；對於較強代理，BrickWright 則維持了原有的高遵循度，未造成顯著下降。這意味著 BrickWright 在提升物理有效性的同時，不會犧牲語意忠實度。

**成本效益分析：**

作者特別強調 BrickWright 對輕量級代理的成本效益。GPT-6 Luna 搭配 BrickWright 後，其效能（以提示詞遵循度衡量）達到了前沿代理（frontier models）的水平，但成本僅為後者的 2%。這個數據點具有重要的實務意涵：在預算受限的部署場景中，配備 BrickWright 的輕量級代理可能是比前沿代理更具性價比的選擇。

**與專用模型的比較：**

在文字轉積木任務（text-to-brick task）上，BrickWright 引導的代理在有效性與忠實度兩個維度上皆優於現有的專用樂高生成模型（如基於最佳化的 Legolization、基於學習的圖生成模型等）。這個結果挑戰了「專用模型在特定任務上必然優於通用代理」的假設，顯示對於具有明確物理規則的領域，工具增強的通用代理可能是更優的解決方案。

**實驗設計的侷限性：**

值得注意的是，512 個提示詞的測試集規模相對有限，且未明確說明提示詞的分布（例如是否涵蓋不同複雜度、不同類型的組裝）。此外，「物理有效性」的定義聚焦於零件層級的約束（碰撞、懸浮、斷連），但未涵蓋結構穩定性（如抗震測試）或美學品質等更高層次的評估標準。

#### 與現有研究的比較

**與專用樂高生成方法的比較：**

傳統的樂高生成方法可分為三類：（1）**基於最佳化的方法**（如 Legolization），將目標形體體素化（voxelize）後合併為標準積木，但受限於小型詞彙表與顯式幾何引導；（2）**基於檢索的方法**，將圖像映射到預建模板，靈活性受限；（3）**基於學習的方法**，從資料中直接生成積木結構，但泛化能力與忠實度通常不如商業 LLM 代理。

BrickWright 的定位與上述方法截然不同：它不試圖從資料中學習積木組裝的模式，而是利用 LLM 代理的既有推理能力，透過工具組彌補其在物理約束上的不足。這種「代理 + 工具」的典範在概念上更接近於程式合成（program synthesis）領域，而非傳統的 3D 生成。

**與其他代理式 3D 生成工具的比較：**

現有的代理式 3D 生成工具（如用於關節物件、場景、CSG 模型的工具）主要針對數位資產創作，未考慮實體組裝的物理約束。BrickWright 的貢獻在於將「物理可行性驗證」整合進代理工作流程，這是現有工具所缺乏的維度。

**與程式碼生成作為 3D 表示的比較：**

「程式碼即 3D 模型」（code-as-3D-model）的範式已有先例，但 BrickWright 的獨特之處在於：（1）領域專屬的 API 設計，將樂高的組裝規則形式化；（2）內建的物理驗證機制，而非依賴代理自行實作；（3）對輕量級代理的顯著提升效果，顯示工具設計對代理能力的放大效應。

**方法論的侷限性：**

儘管結果令人印象深刻，BrickWright 仍存在幾項侷限。首先，其有效性高度依賴 BrickLayer 對樂高組裝規則的完整形式化。若遇到 API 未涵蓋的特殊零件或組裝方式，代理可能無從下手。其次，驗證器僅檢查零件層級的物理約束，未考慮更高層次的物理特性（如重力下的結構穩定性）。第三，迭代修正的過程可能消耗大量推論資源，對於極其複雜的組裝（如 15,067 個零件的香港維多利亞港場景），收斂速度可能成為瓶頸。

#### 可重現性評估

**程式碼與工具的可用性：**

作者明確聲明程式碼已開源，可在專案頁面（avalovelace1.github.io/brickwright）取得。BrickLayer 作為 Python 軟體開發套件（Python SDK），其 API 設計與驗證器實作應可供研究者直接使用與擴展。LDraw 零件庫本身是開源資源，這進一步降低了重現實驗的門檻。

**資料集與評測標準：**

論文未明確說明 512 個提示詞測試集的具體組成與來源，也未提及是否會公開釋出此測試集。對於提示詞遵循度的評估，論文未詳細說明使用的評測方法（人工評分、自動化指標或 LLM-as-a-judge），這對完全重現實驗構成挑戰。

**模型權重與代理設定：**

實驗涉及多個商業 LLM 代理（GPT-6 Luna、GPT-6 Astra、GPT-6.1 Sol、Claude Haiku 5.5）以及編碼工具（Codex、Claude Code）。這些模型的權重未開源，且 API 的可用性與版本可能隨時間變化，這對長期可重現性構成風險。建議作者在專案頁面提供具體的模型版本快照與 API 呼叫記錄。

**重現的可行性評估：**

整體而言，BrickWright 的核心方法論（工具增強代理 + 物理驗證迴圈）具有高度的可重現性，因為其依賴的是通用的 LLM 代理能力，而非特定的模型權重。然而，定量結果（如 100% 有效率、2% 成本比例）可能因模型版本更新而有所波動。

#### 未來研究方向

**推廣至其他多零件組裝領域：**

BrickWright 的方法論具有跨領域推廣的潛力。任何具有明確組裝規則的多零件系統——如家具（宜家的家具組裝）、電子電路（PCB 設計）、機械裝配——皆可受益於類似的「領域專屬 API + 物理驗證器」設計。未來研究可探索如何將 BrickLayer 的設計原則抽象化，形成通用的多零件組裝工具包框架。

**結構穩定性與力學模擬的整合：**

目前的驗證器僅檢查零件層級的約束（碰撞、懸浮、斷連），未考慮結構在重力或外力下的穩定性。未來可整合物理引擎（如 Bullet、MuJoCo）進行力學模擬，使驗證器能檢測傾倒、崩塌等動態失效模式。這將使 BrickWright 從「靜態可行性」擴展至「動態穩健性」。

**多模態提示詞的深化處理：**

雖然 BrickWright 已支援圖像提示詞，但圖像條件（image conditions）的處理方式未在論文中詳細說明。未來研究可探索更細緻的視覺理解——例如從圖像中提取風格、材質、比例資訊，並將其映射到積木設計的具體參數。

**人機協作與互動式設計：**

目前的流程是端到端的自動生成，但樂高組裝本質上具有強烈的創作性與個人化特質。未來可探索互動式版本，讓使用者在生成過程中提供反饋、調整約束、指定偏好，使 BrickWright 成為「創作助手」而非「自動生成器」。

**驗證器的形式化與可證明性：**

目前的驗證器是啟發式的（heuristic），基於網格相交偵測與連通性分析。未來可探索形式化方法（formal methods），如 SMT 求解器或定理證明器，對組裝的物理可行性進行可證明的驗證。這將使 BrickWright 在安全關鍵應用中更具可信度。

**效率與可擴展性優化：**

對於極大型組裝（如 15,067 個零件的場景），迭代驗證的成本可能成為瓶頸。未來研究可探索增量驗證（incremental validation）——僅驗證新增或修改的零件，而非每次重新驗證整個組裝。此外，可研究代理的規劃策略，使其能在單次生成中預測並避免常見的物理違規，減少迭代次數。

**評測基準的標準化：**

目前缺乏標準化的樂高生成評測基準，這使得不同方法之間的比較困難。未來可建立包含多樣化提示詞、多維度評估指標（有效性、忠實度、創造性、結構合理性）的公開基準，推動領域的系統性進展。

## 論文問答

**Q1：BrickWright 主要解決什麼核心問題？**
A：BrickWright 解決的是前沿編碼代理在生成「實體世界可組裝物件」時的失敗問題。雖然大型語言模型代理在三維建模上已相當出色，但它們在處理多零件組裝任務時，經常產生包含懸浮零件、碰撞零件或斷連零件的無效組裝。具體到樂高積木領域，這些代理即使使用 GPT-6 Astra 等高推理能力的模型，仍會產生物理上不可行的積木組裝。

**Q2：為什麼現有的前沿編碼代理在實體組裝任務上會失敗？**
A：現有代理缺乏專門用於組裝建構與驗證物理可行性的工具。雖然強大的代理（如 GPT-6 Astra 搭配 Codex）有超過 80% 的機率會自行撰寫驗證腳本，但對於複雜的物理領域，這種自我驗證往往不足，因為它們無法系統性地處理零件碰撞、懸浮與連接性等約束。此外，現有的代理式三維生成工具套件主要針對數位資產創作，並未考慮物理約束，因此無法直接用於真實世界的物件生成。

**Q3：為什麼選擇樂高積木作為研究領域？**
A：樂高是一個既普遍可得又極為複雜的系統，包含數千種零件並以數十種方式相互連接。這種複雜性使其成為測試多零件組裝生成能力的理想試金石。更重要的是，樂高積木具有明確的物理生產規則（卡扣式接合），零件可被建模為帶有局部連接器的幾何體，並具有程式化的組裝規則（例如凸粒與反凸粒的互鎖），這使得建構人因工程化的組裝 API 成為可能。

**Q4：BrickWright 的核心方法是什麼？**
A：BrickWright 採用「計畫-執行-驗證迴圈」（plan-execute-validate loop）來引導預訓練的大型語言模型代理生成物理上有效的積木組裝。代理首先根據文字或圖像提示詞撰寫使用 BrickLayer API 的生成程式碼，然後編譯並執行測試；若檢查通過則完成，若失敗則檢視結果並進行修訂。這個迭代過程讓代理能夠根據驗證器的具體反饋來修正物理違規問題。

**Q5：BrickLayer Python 工具包有哪些關鍵創新？**
A：BrickLayer 包含兩個主要元件：第一是符合人因工程設計的積木組裝 API，相比直接使用原始 LDraw 格式可減少約一半的推論成本；第二是驗證器，能夠對完成的組裝提供物理可行性的具體反饋。這種將組裝介面與驗證功能整合在同一工具包中的設計，使代理能夠以更經濟、更可靠的方式生成符合物理約束的積木組裝。

**Q6：BrickWright 的設計選擇為何如此有效？**
A：核心設計理念是將「代理式程式碼即三維模型」與「積木零件的規則性」相結合。零件被建模為帶有局部連接器的幾何體，並具有程式化的組裝規則，這種抽象方式讓代理能以高階方式思考組裝而非處理低階細節。此外，將工具包設計獨立於代理能力之外也很重要，因為即使是強大的代理也需要專門的工具來減少 token 使用量並避免重複工作。

**Q7：實驗使用了哪些基準測試與比較對象？**
A：研究使用了 512 個提示詞的測試集，比較了多個基準代理（包括 GPT-6 Luna、GPT-6 Astra、GPT-6.1 Sol 與 Claude Haiku 5.5）以及專門的積木生成模型。評估指標涵蓋物理有效率（是否使用真實零件、無碰撞、無懸浮、形成連接結構）以及提示詞遵循度（生成結果與輸入提示的契合程度）。

**Q8：主要的實驗結果為何？**
A：在 512 個提示詞的測試集上，配備 BrickWright 的所有代理都達到了 100% 的物理有效率，相比之下基準代理的表現從 GPT-6 Luna 的 9% 到 GPT-6 Astra 的 69% 不等。對於輕量級代理，BrickWright 不僅大幅提升物理有效性，也改善了提示詞遵循度；對於較強的代理，則在維持提示詞遵循度的同時達到完美的物理有效性。此外，BrickWright 在文字轉積木任務上也優於專門的積木生成模型。

**Q9：BrickWright 在成本效益方面表現如何？**
A：BrickWright 的一個重要優勢是讓輕量級模型能以極低的成本達到與前沿模型相當的品質。例如，GPT-6 Luna 搭配 BrickWright 後，物理有效率從 9% 提升至 100%，且其成本僅約為前沿模型的 2%。這顯示 BrickWright 大幅降低了生成高品質物理有效積木組裝的經濟門檻，使更廣泛的使用者能夠受益。

**Q10：BrickWright 能支援哪些實際應用場景？**
A：BrickWright 支援多種實用的積木組裝生成場景，包括可動關節組裝（如可擺姿勢的螃蟹）、大型組裝（如包含 15,067 個零件的香港維多利亞港場景）以及一般場景建構。系統接受文字或圖像提示詞作為輸入，能夠生成從小型精緻模型到大型複雜結構的各種樂高組裝，展現了廣泛的應用潛力。

**Q11：在實際產品化時需要考慮哪些因素？**
A：實際產品化時必須確保所有零件都是真實存在的樂高零件、組裝中沒有碰撞或懸浮的零件，並盡可能形成單一連接結構。這些物理可行性約束對於實際能夠組裝的樂高模型至關重要，因為任何違反這些約束的設計都無法在現實世界中實現。圖 1 中以紅色標示的網格相交區域正是這類需要避免的物理違規。

**Q12：這項研究對領域的影響是什麼？**
A：這項研究最重要的領域影響在於證明了「為代理提供適當工具」就足以讓它們產生物理上有效的組裝，而無需針對特定任務進行微調。這種「工具包驅動」的範式可望推廣到其他多零件組裝領域，例如家具、機械組裝或模組化機器人等。此外，BrickWright 也展示了代理式方法在通用性與保真度上能超越專門模型，為未來的研究方向提供了重要啟示。

**Q13：論文承認有哪些限制？**
A：論文主要聚焦於樂高積木這個特定領域，雖然展示了工具包驅動方法的有效性，但尚未將其推廣到其他多零件組裝領域。此外，雖然 BrickWright 在物理有效性上達到 100%，但對於較強代理的提示詞遵循度僅是「維持」而非「提升」，這意味著在創意保真度方面仍有改進空間。

**Q14：可能存在哪些失敗案例？**
A：即使配備 BrickWright，對於極其複雜或抽象的提示詞，代理仍可能在提示詞遵循度上表現不佳。雖然物理有效性已完全解決，但生成結果的藝術品質、細節豐富度以及與提示詞的語意契合度仍依賴底層代理的能力。此外，對於需要特殊零件或不常見組裝技巧的進階樂高技法，系統的表現可能也會受到限制。

**Q15：未來的研究方向有哪些？**
A：未來的重要研究方向包括：將 BrickLayer 的工具包設計理念推廣到其他多零件組裝領域（如家具、機械組裝、模組化機器人等）；進一步提升生成結果的創意保真度與藝術品質；支援更複雜的可動關節設計與機械傳動結構；以及探索如何讓代理更好地處理需要特殊技法或非標準零件的進階組裝任務，最終朝向通用的實體世界組裝生成邁進。

## 實務應用指南

### 適用場景

1. **AI 輔助樂高設計助理**：將 BrickWright 整合到消費端樂高設計 App 中，使用者輸入文字（如「一隻可擺姿勢的螃蟹」）或上傳參考圖，系統即時生成可實際拼砌的樂高組裝說明書，包含零件清單（BOM）與逐步組裝順序，大幅降低非專業玩家的設計門檻。

2. **教育領域的 STEAM 教材生成**：教師輸入歷史建築、自然景觀或科學模型的概念描述（如「香港維多利亞港」），系統自動產生符合物理可行性的樂高教具組裝圖，學生可實際動手拼砌，加強空間推理與工程概念，特別適合中學以下的跨領域課程。

3. **客製化積木禮品與周邊商品**：電商平台導入 BrickWright，讓消費者以文字或照片描述想要的造型（如「黑白樂高太空船配藍色座艙罩」），自動生成可下單生產的客製化積木套件，解決目前客製商品需仰賴人工設計師的高成本問題。

4. **建築與城市規劃的概念模型快速原型**：建築師或都市規劃師輸入場景描述，系統生成包含建築物、街道、植被的場景級樂高模型，用於業主溝通、公眾參與工作坊或展覽展示，比傳統 3D 列印模型更具互動性與紀念價值。

5. **積木創作社群平台的內容生產**：在 Rebrickable、BrickLink 等樂高愛好者社群中，部署 BrickWright 讓使用者將腦中構想快速轉化為可分享的 MOC（My Own Creation）作品，並透過物理驗證器確保作品真實可拼，減少社群中常見的「飄浮零件」或「碰撞零件」錯誤。

### 實作前置條件

**資料需求**
- 完整的 LDraw 零件庫（官方釋出，數千個零件的幾何與連接器定義）
- 樂高零件的 snap-fit 物理規則資料集（凸粒與反凸粒的接合規範）
- 用於評估的文字與圖像提示詞測試集（建議至少 512 筆以對齊論文基準）
- 選用領域的參考圖像資料集（若需做圖像條件生成）

**運算資源**
- 推論階段：可呼叫商業 LLM API（如 GPT-6 系列、Claude 系列），無需自建 GPU 叢集
- 驗證階段：單機 CPU 即可執行 BrickLayer 的網格相交、連通性與浮空檢測
- 批次評估：若需重現論文 512 筆提示詞的實驗，建議準備中等規模的 API 預算（輕量模型如 GPT-6 Luna、Claude Haiku 5.5 成本僅約前沿模型的 2%）
- 開發階段：Python 3.10+ 環境，建議使用 Linux 或 macOS

**技能門檻**
- 必備：Python 程式設計能力、LLM Agent 工具呼叫（function calling / tool use）概念、提示詞工程基礎
- 建議：熟悉 LDraw 檔案格式、樂高零件接合物理、3D 幾何處理（mesh intersection、connected components）
- 加分：具備 LLM Agent 框架（如 LangChain、AutoGen）使用經驗，能自訂計畫-執行-驗證迴圈

### 實作步驟建議

**階段一：環境建置與工具鏈整合（1-2 週）**
1. 從專案頁面取得 BrickLayer 原始碼，安裝 Python 套件與相依套件
2. 匯入 LDraw 零件庫，確認 BrickLayer 的零件目錄與連接器定義可正常載入
3. 撰寫最小可行測試：手動呼叫 BrickLayer API 拼出一個 2×4 磚塊，驗證輸出符合 LDraw 格式

**階段二：驗證器獨立測試（1 週）**
1. 準備已知違規的測試組裝（刻意製造碰撞、浮空、斷連）
2. 確認 BrickLayer 驗證器能正確回報違規類型與位置
3. 將驗證器包裝為 LLM 可呼叫的工具函式，回傳結構化錯誤訊息

**階段三：Agent 整合與提示詞設計（2-3 週）**
1. 選擇目標 LLM（建議從輕量模型如 GPT-6 Luna 或 Claude Haiku 5.5 開始）
2. 設計系統提示詞，明確告知 Agent：使用 BrickLayer API、必須通過物理驗證、計畫-執行-驗證迴圈的工作流程
3. 實作迴圈控制器：Agent 寫程式碼 → 執行 → 驗證 → 若失敗則將錯誤訊息回傳 Agent 進行修訂
4. 設定最大修訂次數（建議 3-5 次）以平衡成本與品質

**階段四：評估與基準對齊（1-2 週）**
1. 蒐集或建立 512 筆文字/圖像提示詞測試集
2. 實作物理有效率（碰撞、浮空、斷連皆無）與提示詞遵循度（prompt adherence）的自動評估指標
3. 對比基準 Agent（裸 LLM）與 BrickWright 輔助 Agent 的差異，目標達到 100% 物理有效率

**階段五：產品化與優化（2-4 週）**
1. 加入組裝順序生成（assembly sequence），輸出逐步說明書
2. 整合 BOM 計算與零件成本估算
3. 設計使用者介面：文字輸入框、圖像上傳、3D 預覽、零件清單匯出
4. 加入快取機制，對相似提示詞複用已生成的程式碼片段以降低推論成本

### 潛在風險與注意事項

**風險一：輕量模型在複雜提示詞下仍可能失敗**
- 現象：雖然 BrickWright 將 GPT-6 Luna 的有效率從 9% 提升至 100%，但對於極複雜的場景（如「香港維多利亞港」含 15,067 個零件），輕量模型可能在提示詞遵循度上明顯落後前沿模型
- 緩解：建立難度分級機制，簡單任務路由至輕量模型、複雜任務升級至前沿模型；或對輕量模型加入領域微調

**風險二：驗證器誤判導致 Agent 陷入修訂迴圈**
- 現象：浮空判定若過於嚴格，可能將刻意設計的「獨立裝飾零件」誤判為違規；碰撞容差設定不當會造成誤報
- 緩解：將驗證參數（如浮空容忍距離、碰撞容差）設計為可調參數；提供「豁免清單」讓使用者標記刻意設計的獨立零件

**風險三：零件庫版本與真實樂高產品脫節**
- 現象：LDraw 零件庫更新可能落後於樂高官方新品；部分稀有或限定零件在 LDraw 中缺乏完整幾何定義
- 緩解：建立零件可用性檢查機制，在生成時即時回報「此零件目前無實體可購買」；定期同步 LDraw 更新

**風險四：API 推論成本在大量修訂時失控**
- 現象：若 Agent 多次修訂仍無法通過驗證，token 消耗可能倍增
- 緩解：設定單次任務的預算上限與修訂次數上限；對常見錯誤模式建立預先修正的程式碼範本

**風險五：圖像條件生成的視覺-結構落差**
- 現象：圖像提示詞生成的組裝可能在視覺上相似，但結構上不穩定（例如使用過多單點連接）
- 緩解：在驗證器中加入結構穩定性評分（基於連接器數量與分布），並回饋給 Agent

### 與其他技術的整合建議

**與 3D 建模工具鏈整合**
- 將 BrickLayer 輸出轉換為 Blender、Studio（樂高官方 CAD）或 Stud.io 格式，匯入既有 3D 工作流程
- 透過 OpenGL 或 Three.js 將 LDraw 檔案即時渲染為網頁預覽，無需安裝桌面軟體

**與 LLM Agent 框架整合**
- 在 LangChain、AutoGen 或 CrewAI 中將 BrickLayer 包裝為標準 Tool，Agent 可自動決定何時呼叫驗證器
- 結合檢索增強生成（RAG），從樂高官方零件目錄中檢索可用零件，避免 Agent 虛構不存在的零件編號

**與電商與生產系統整合**
- 串接 BrickLink API 或 Pick a Brick 系統，自動查詢零件庫存與價格，生成可下單的 BOM
- 整合樂高代工廠的生產排程系統，將組裝順序轉換為工廠可執行的指令

**與教育平台整合**
- 嵌入 Moodle、Google Classroom 等 LMS 平台，作為 STEAM 課程的互動教材
- 結合 AR 技術（如手機相機辨識），讓學生掃描實體積木取得對應的虛擬組裝步驟

**與遊戲與模擬整合**
- 將 BrickLayer 的物理驗證邏輯擴展至 Minecraft 的方塊組合、Roblox 的零件組裝等虛擬積木系統
- 在機器人模擬環境（如 Gazebo、Isaac Sim）中導入 BrickLayer 的接合規則，用於訓練積木組裝機器人

### 給不同背景讀者的閱讀建議

**給初學者**：建議先從專案頁面的展示影片與範例組裝開始，直觀感受 BrickWright 能做什麼；接著閱讀論文的圖 1 與圖 2，理解「物理違規」與「計畫-執行-驗證迴圈」的概念；最後動手安裝 BrickLayer，跑通官方教學範例。不需要深入數學推導，重點在於體會「工具輔助 LLM」這個核心設計理念。

**給 AI 工程師**：重點閱讀 BrickLayer 的 API 設計章節與驗證器的實作細節，理解如何將領域知識（樂高接合物理）編碼為 LLM 可呼叫的工具；特別關注「人因工程化 API」如何將推論成本減半的設計取捨，這對其他領域（如電路設計、機械組裝）建立類似工具包極具參考價值。建議嘗試將 BrickWright 框架移植到自己的領域。

**給研究者**：論文的核心貢獻在於證明「提供工具 + 驗證器」比「微調更大的模型」更具成本效益，這對 agentic 3D generation 與程式化合成（programmatic synthesis）領域是重要啟示。建議深入分析 512 筆提示詞的失敗模式分布、輕量 vs. 前沿模型的行為差異，並思考此框架在更複雜物理領域（如機械加工、建築結構）的可擴展性與限制。

**給產品經理**：BrickWright 展示了如何用「工具增強」而非「模型升級」來解決 LLM 的可靠性問題，這對成本敏感的產品極具吸引力。建議評估在自家產品中導入類似工具輔助框架的可行性，特別關注三個指標：物理有效率（從 9-69% 提升至 100%）、推論成本（輕量模型僅前沿模型的 2%）、使用者體驗（從「常常失敗」到「穩定可用」）。可優先考慮在積木、拼圖、摺紙等「規則明確的物理組裝」領域試點。
