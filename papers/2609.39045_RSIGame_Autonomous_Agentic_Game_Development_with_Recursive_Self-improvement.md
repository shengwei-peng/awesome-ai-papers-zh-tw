## ⚡ TL;DR

解決LLM自動生成遊戲時，迭代精煉易過擬合測試案例，導致缺陷未解且泛化能力差的問題。
提出RSIGame框架，結合局部探索-診斷-改進迴圈與全域品質監控迴圈，並透過經驗內化訓練生成器。

## 摘要翻譯

近期大型語言模型（LLMs）的進展使自動遊戲生成日益可行，然而在達到可玩版本之後，可靠地進一步改進生成的遊戲仍具挑戰性。樸素的迭代式精煉（Iterative Refinement）容易對少量測試案例（Test Cases）過擬合（Overfit），產生脆弱的遊戲，存在未解決的缺陷（Bug）、缺失行為（Missing Behaviors），以及難以泛化（Generalization）至更廣泛的玩家互動（Player Interactions）。我們提出 RSIGame，一個具備遞迴自我改進（Recursive Self-improvement）的自主代理式遊戲開發（Agentic Game Development）框架。RSIGame 將開發組織成互補的局部迴圈（Local Loop）與全域迴圈（Global Loop）。具體而言，局部探索-診斷-改進迴圈（Explore-Diagnose-Improve Loop）廣泛探索可執行遊戲，診斷並優先排序（Prioritize）所發現的問題，並執行基於證據的修訂（Evidence-Grounded Revision），其中演化式檢核清單（Evolving Checklist）持續累積新的測試與改進指引。全域迴圈負責追蹤整體品質，保留最佳檢查點（Checkpoint），並在長時程開發（Long-Horizon Development）中偵測飽和（Saturation）或退化（Regression）。除了測試時的改進外，RSIGame 更透過訓練將成功的開發經驗內化（Experience Internalization）至生成器（Generator）中。在 140 個 GameCraft-Bench 任務、兩種遊戲引擎（Godot 與 Phaser）及五個生成器上，RSIGame 在相同的開發預算（Development Budget）下持續提升遊戲品質。值得注意的是，經驗內化使 Qwen3.8-27B 在 Godot 上達到 61.38、在 Phaser 上達到 58.53，超越 GPT-5.5 一次性生成（One-shot）的分數，同時將 Qwen 的生成詞元（Generation Tokens）減少 11 倍。

### 核心貢獻（3～5點）
- 提出 RSIGame 框架，將自主代理式遊戲開發組織為互補的局部迴圈與全域迴圈，系統性地解決樸素迭代精煉所導致的過擬合、脆弱性與泛化不足問題。
- 設計局部探索-診斷-改進迴圈，結合演化式檢核清單與基於證據的修訂機制，實現對可執行遊戲的廣泛探索、問題優先排序與持續累積式改進。
- 設計全域迴圈，負責長時程開發中的整體品質追蹤、最佳檢查點保留，以及飽和與退化的即時偵測。
- 提出經驗內化（Experience Internalization）機制，於訓練階段將成功的開發經驗吸收至生成器中，使開源模型 Qwen3.8-27B 在 Godot 與 Phaser 上超越 GPT-5.5 的一次性生成表現，並將生成詞元量縮減至原來的 1/11。
- 在 140 個 GameCraft-Bench 任務、兩種遊戲引擎與五個生成器上進行全面驗證，證明 RSIGame 在相同開發預算下能持續穩定地提升遊戲品質。

### 適合對象
從事大型語言模型與視覺語言模型（VLMs）研究的學者與工程師；關注自主代理（Autonomous Agents）、代理式工作流程與遞迴自我改進機制的研究者；遊戲開發領域中對 AI 輔助或自動化生成感興趣的實務開發者；以及從事軟體工程（Software Engineering）自動化、電腦使用自動化（Computer-Use Automation）與長時程生成（Long-Horizon Generation）研究的相關人員。

## 深度分析

#### 方法論解析

RSIGame 的核心方法論建立在「遞迴自我改進」（Recursive Self-improvement, RSI）這一概念之上，將代理式遊戲開發（Agentic Game Development）形式化為一個從初始專案 $P_0 \sim \pi_\theta(\cdot|x)$ 開始、經由多輪迭代 $P_0 \rightarrow P_1 \rightarrow \cdots \rightarrow P_T$ 逐步演化的過程。此一架構的設計動機源自一個關鍵觀察：單次生成（one-shot）雖然能產出可玩遊戲，但容易在測試案例上過擬合（overfit），導致未測試的缺陷（bugs）、缺失行為（missing behaviors）與邊界案例（corner cases）無法被妥善處理。

**雙迴圈架構的互補設計**

RSIGame 將開發流程拆分為兩個互補的迴圈，這是本方法最具特色的設計：

1. **局部迴圈（Local Loop）**：執行「探索-診斷-改進」（Explore-Diagnose-Improve）三階段流程。在探索階段，由控制器（Controller）與探索者（Explorer）兩種代理組成，前者負責決策方向，後者主動執行遊戲並收集證據。診斷階段對已發現問題進行優先排序（prioritize），改進階段則依據累積證據進行基於證據的修訂（evidence-grounded revision）。此迴圈的核心創新在於引入「演化式檢核清單」（evolving checklist），該清單隨新證據不斷擴展，持續累積新的測試與改進指引，避免開發過程陷入局部最優。

2. **全域迴圈（Global Loop）**：負責跨迭代的監控，追蹤整體遊戲品質、保存最佳檢查點（best checkpoint）、偵測飽和（saturation）與退化（regression）。當局部迴圈進展停滯時，全域迴圈會引入稀疏的高層次指引（sparse high-level guidance），驅動多階段的遊戲演化。這種設計避免了「盲目持續編輯」的陷阱，確保長期進展而非短期過擬合。

**經驗內化（Experience Internalization）的訓練策略**

除了測試時的訓練免費（training-free）改進外，RSIGame 進一步提出訓練階段的經驗內化機制：將成功的開發軌跡、診斷決策與已驗證的修訂轉化為生成器（generator）的監督訊號。這形成了一個更廣義的 RSI 迴圈——不僅在測試時改進單一遊戲，更在訓練時改進底層生成模型本身。這種「元層次的自我改進」是本方法區別於純粹測試時方法的關鍵。

**形式化目標的雙重性**

論文明確指出代理式遊戲開發需同時滿足兩個目標：遵循使用者需求（自然語言規格）與產出功能正確、無缺陷的遊戲。這種雙重目標驅動了 RSIGame 對「可玩性」與「品質」的區分——前者僅需通過基本測試案例，後者則需泛化（generalization）至更廣泛的玩家互動（player interactions）。

#### 實驗數據解讀

實驗設計在三個維度上具有相當的廣度與深度：

**評估規模與多樣性**
- **140 個 GameCraft-Bench 任務**：提供了充足的統計樣本，能可靠地反映方法效能。
- **兩種遊戲引擎（Godot 與 Phaser）**：涵蓋了不同的技術堆疊，Godot 偏向物件導向的場景樹架構，Phaser 則是基於 JavaScript 的 2D 網頁遊戲框架，兩者的程式設計範式差異顯著，能有效檢驗方法的泛化能力。
- **五種生成器（generators）**：包含 Qwen3.8-27B、Kimi-K2.6、Codex+GPT-5.5 等不同規模與架構的模型，橫跨開源與閉源系統。

**關鍵結果的解讀**

1. **Qwen3.8-27B 在 Godot 上達到 61.38 分**，超越 GPT-5.5 一次性生成（one-shot）的 50.26 分，提升幅度約 11 個絕對點數。更值得注意的是，**生成詞元（generation tokens）減少了 11 倍**，這意味著 RSIGame 不僅提升了品質，還大幅降低了推理成本——這對於實際部署具有重要意義。

2. **在 Phaser 上達到 50.24 分**，超越 GPT-5.5 的 49.44 分。雖然提升幅度較小（僅約 0.8 點），但仍證明了方法在不同引擎上的穩健性。

3. **迭代開發階段**：Qwen3.8-27B 在 Godot 上僅憑迭代開發即達到 47.77 分，超越 Kimi-K2.6 的 44.77 分。這顯示即使是訓練免費的 RSI 策略，也能讓中等規模開源模型超越其他競爭對手。

4. **經驗內化的累積效應**：從 47.77（純迭代）到 61.38（加入經驗內化），提升約 13.6 點，證明了訓練階段的經驗內化能帶來測試時迭代無法達成的額外增益。

**預算匹配設計的意義**

實驗強調「在匹配的開發預算（matched development budgets）下」進行比較，這避免了單純以「更多計算換更好結果」的不公平比較。這種嚴謹的對照設計，使 RSIGame 的效能提升更具說服力。

**仍待釐清的數據面向**

雖然摘要提供了關鍵數字，但完整實驗應包含：各生成器在不同任務類型上的細粒度表現、飽和偵測的實際觸發時機、檢核清單的演化軌跡分析、以及不同迭代輪數下的成本-效益曲線。這些細節對於理解方法的實際運作特性至關重要。

#### 與現有研究的比較

**相較於現有自動遊戲生成方法的定位**

RSIGame 與近期 VLM-based 代理遊戲生成工作（如 Luo et al., 2026; Chi et al., 2026）共享相同的願景——將自然語言規格轉化為可玩遊戲。然而，RSIGame 的差異化在於：

1. **從「可玩」到「高品質」的躍遷**：現有方法多聚焦於產出可玩遊戲，RSIGame 則明確將目標提升至泛化品質，這與 Roque et al. (2025) 觀察到的「成熟團隊仍頻繁遭遇未預期缺陷」現象相呼應。

2. **結構化迭代 vs. 樸素迭代**：論文明確指出「naive iterative refinement can easily overfit a small set of test cases」，這是對現有迭代式方法的直接批評。RSIGame 透過演化式檢核清單與全域監控機制，系統性地解決了這一問題。

3. **測試時改進與訓練時改進的整合**：相較於僅在測試時進行自我改進的方法（如 Wu et al., 2024 提出的 RSI 框架），RSIGame 進一步將成功經驗內化至生成器，形成雙層次的自我改進。

**相較於軟體工程代理的借鑑與差異**

RSIGame 借鑑了軟體工程代理（如 Yang et al., 2024; Zhu et al., 2026）中的迭代測試-修訂模式，但遊戲開發的特殊性在於：遊戲品質最終反映於「執行時行為與玩家體驗」（runtime behavior and player experience），這比傳統軟體的功能正確性更難以形式化驗證。RSIGame 透過可重播的示範軌跡（replayable demonstration traces）$\mathcal{T} = \{\tau_1, \tau_2, \ldots, \tau_N\}$ 與隱藏的任務專屬評分量表（hidden task-specific rubric）來處理此一挑戰。

**方法論的限制與未解問題**

1. **評分量表的依賴性**：使用隱藏評分量表進行評分雖然客觀，但可能無法完全捕捉玩家體驗的細微差異。

2. **檢核清單的膨脹風險**：隨著迭代進行，演化式檢核清單可能無限增長，需要更精細的剪枝或摘要機制。

3. **經驗內化的資料效率**：將開發軌跡轉化為監督訊號的具體機制（資料篩選、損失函式設計、訓練策略）需要更詳細的說明。

4. **跨引擎泛化的深度**：雖然在 Godot 與 Phaser 上都有效，但兩者同屬 2D 遊戲範疇，對 3D 遊戲或更複雜的遊戲類型（如開放世界、模擬經營）的適用性仍待驗證。

#### 可重現性評估

**正面因素**

1. **基準的公開性**：GameCraft-Bench 作為標準化評估基準，若隨論文一同釋出，將大幅提升可重現性。140 個任務的規模也提供了充足的測試覆蓋。

2. **多模型、多引擎的橫向比較**：使用五種生成器與兩種引擎的設計，使結果不依賴單一模型的特性，有助於在其他團隊復現時驗證結論的穩健性。

3. **預算匹配的控制變數**：明確的開發預算控制使後續研究能在公平條件下進行比較。

**待釐清的環節**

1. **程式碼與模型權重的釋出狀態**：論文中未明確提及程式碼倉庫、預訓練權重或訓練資料的釋出計畫。對於 RSIGame 這類涉及複雜代理互動與訓練流程的框架，僅有論文描述是不夠的——需要具體的實作細節（如控制器與探索者的提示模板、檢核清單的更新規則、經驗內化的資料處理流水線）。

2. **評分量表的透明度**：雖然使用「隱藏」評分量表能避免過擬合，但若完全不公開評分維度，將限制後續研究的針對性改進。

3. **超參數與提示工程**：迭代輪數、飽和偵測閾值、檢核清單的最大長度等關鍵超參數需要明確說明。

4. **隨機性與統計顯著性**：140 個任務的結果是否包含多次執行的平均值與變異數？不同種子下的穩定性如何？這些對於實驗的可信度至關重要。

**建議的可重現性增強措施**

- 釋出 RSIGame 的完整程式碼與配置文件
- 公開 GameCraft-Bench 的任務定義與評分量表結構（即使具體評分標準保密）
- 提供經驗內化階段的訓練資料樣本或合成流程
- 在論文中補充消融實驗（ablation study），分離局部迴圈、全域迴圈與經驗內化各自的貢獻

#### 未來研究方向

**1. 評估機制的擴展與深化**

當前評估依賴任務專屬的隱藏評分量表，未來可探索：
- **玩家中心評估**：引入人類玩家評分或行為分析，捕捉自動化評分難以量化的「遊戲感」（game feel）與沉浸感。
- **長期可玩性測試**：評估遊戲在長時間遊玩下的穩定性與吸引力，而非僅在短時間示範軌跡上的表現。
- **跨文化與跨地域適應性**：不同文化背景的玩家對遊戲機制與敘事的偏好差異。

**2. 經驗內化機制的理論化與擴展**

- **理論基礎**：為何將開發軌跡轉化為監督訊號能帶來如此顯著的提升？需要更深入的分析，可能涉及隱式課程學習（implicit curriculum learning）或自我對齊（self-alignment）的理論框架。
- **負面經驗的利用**：目前僅內化「成功」軌跡，但失敗案例同樣富含資訊——如何從失敗中學習以避免重複犯錯？
- **多任務遷移**：在一組任務上內化的經驗能否遷移至新任務？這將決定方法的實際部署成本。

**3. 檢核清單的結構化與可解釋性**

演化式檢核清單是 RSIGame 的核心創新，但目前以自然語言形式存在，未來可探索：
- **結構化表示**：將檢核清單轉化為圖結構或本體（ontology），使代理能進行更系統性的推理。
- **可解釋性分析**：追蹤檢核清單的演化軌跡，理解哪些類型的問題最常被遺漏、哪些改進策略最有效。
- **人機協作介面**：允許人類開發者檢視、編輯或擴展檢核清單，將自動化與人類專業知識結合。

**4. 從 2D 到更複雜遊戲類型的擴展**

- **3D 遊戲與物理模擬**：將方法擴展至需要 3D 資產、物理引擎整合的遊戲類型。
- **敘事驅動遊戲**：角色扮演遊戲（RPG）與敘事冒險遊戲需要複雜的對話系統與分支劇情，這對生成器的長時程一致性（long-horizon consistency）提出更高要求。
- **多人遊戲與即時系統**：涉及網路同步、伺服器端邏輯的遊戲類型。

**5. 與其他自我改進範式的整合**

- **測試時訓練（Test-Time Training, TTT）**：在迭代過程中即時更新模型參數，而非僅在訓練階段進行經驗內化。
- **強化學習整合**：將遊戲品質評分作為獎勵訊號，透過強化學習進一步優化生成器。
- **多代理協作**：引入專門化的代理（如關卡設計代理、美術代理、音效代理），模擬真實遊戲開發團隊的分工。

**6. 效率與可持續性**

- **推理成本優化**：雖然 RSIGame 已將生成詞元減少 11 倍，但迭代過程仍涉及多次執行遊戲與診斷，總計算成本仍需仔細評估。
- **環境影響**：大量代理互動的碳足跡與能源消耗值得關注。
- **邊緣部署**：將 RSIGame 輕量化，使其能在資源受限的環境中運行。

**7. 安全與倫理考量**

- **內容安全**：自動生成的遊戲可能包含不當內容，需要內容審查機制。
- **智慧財產權**：訓練資料的版權問題與生成遊戲的原創性認定。
- **對遊戲開發產業的影響**：自動化遊戲開發對人類開發者就業與產業結構的潛在影響。

這些研究方向不僅能深化 RSIGame 本身的技術內涵，也能推動整個代理式遊戲開發領域向更成熟、更實用的方向發展。

## 論文問答

**Q1：自動遊戲生成領域目前面臨的核心問題是什麼？**
A：自動遊戲生成的核心問題在於，雖然現今的大型語言模型（LLMs）與視覺語言模型（VLMs）已能將自然語言規格轉化為可玩的遊戲雛型，但要讓生成的遊戲超越「可玩」這個基本門檻、達到真正高品質的水準仍然極具挑戰。遊戲開發本質上是一個複雜的多模態工程流程，需要同時設計遊戲機制與進程、撰寫原始碼、產出多模態素材，並將這些異質元件整合成一個一致性的可執行專案。即使是成熟的人類開發團隊，在開發過程中也經常會遇到未預期的缺陷、缺失功能與被忽略的邊界案例，因此單純的一次性生成幾乎不可能產出完整且正確的遊戲專案。

**Q2：為什麼傳統的迭代式精煉方法容易失敗？**
A：傳統的迭代式精煉方法（naive iterative refinement）容易在開發過程中過擬合（overfit）一小組測試案例，導致生成的遊戲雖然表面上通過了測試，實際上卻潛藏著許多未解決的缺陷、缺失行為與未處理的邊界案例。這種現象的本質在於開發迴圈只針對有限的測試案例進行修正，而非全面性地提升遊戲整體品質，因此對於更廣泛的玩家互動情境缺乏泛化能力。換言之，這類方法雖然能讓遊戲「勉強可玩」，但無法產出真正穩健、能在各種玩家操作下都正常運作的高品質遊戲。

**Q3：為何遞迴自我改進（Recursive Self-improvement）對遊戲開發特別重要？**
A：遞迴自我改進之所以特別適合遊戲開發，是因為它模擬了人類開發團隊自然採用的迭代式開發工作流程——開發者反覆測試當前構建版本、收集回饋、並據此修訂專案，直到達成目標品質。這種「每一輪開發都基於前一輪新觀察到的證據」的過程，能讓代理在長時程生成中持續累積經驗並逐步完善遊戲。更重要的是，遊戲品質最終反映在執行時的行為與玩家體驗上，這使得遞迴自我改進不僅是技術上的便利，更是貼近真實開發需求的本質方法論。

**Q4：RSIGame 的核心方法是什麼？**
A：RSIGame 的核心方法是將遊戲開發組織成互補的「局部迴圈」與「全域迴圈」，並結合訓練時的經驗內化機制。局部迴圈遵循探索-診斷-改進（explore-diagnose-improve）的三階段流程，由代理自主探索可執行的遊戲、診斷並優先排序已發現的問題，再依據累積的證據進行基於證據的修訂（evidence-grounded revision）。全域迴圈則負責監控跨迭代的整體進度、追蹤遊戲品質、保留最佳檢查點（checkpoint），並偵測飽和（saturation）或退化（regression）現象，確保系統在長時程開發中能持續進步而非盲目地持續編輯。

**Q5：RSIGame 最重要的創新點為何？**
A：RSIGame 最重要的創新點在於引入了一個「演化式檢核清單」（evolving checklist），它會隨著新證據的發現而持續擴充，不斷累積新的測試與改進指引，從而避免開發過程陷入過擬合少數測試案例的陷阱。這個檢核清單讓代理能夠系統性地探索剩餘的失敗與潛在改進機會，將開發推向更具泛化性的整體品質提升，而非僅止於讓遊戲「可玩」。此外，RSIGame 還提出了「經驗內化」（experience internalization）的訓練策略，將成功的開發軌跡、診斷決策與已驗證的修訂轉化為生成器的監督訊號，使底層生成模型本身也能從遞迴自我改進中獲益。

**Q6：RSIGame 在設計上有哪些關鍵的選擇？**
A：在設計上，RSIGame 選擇將「自主探索」拆分為控制器（controller）與探索者（explorer）兩種互補角色的代理，使探索過程能更全面且有方向性地涵蓋遊戲的各種執行狀態。另一個關鍵設計是採用「代理式驗證」（agentic verification）來確認每次修訂是否真正改善了遊戲，避免無效或甚至有害的修改被納入。此外，RSIGame 還刻意區分訓練免費（training-free）的遞迴自我改進與訓練式（training-based）的經驗內化兩種策略，讓使用者能依據資源與需求彈性選擇——前者立即可用、後者則能從根本上強化生成器的能力。

**Q7：RSIGame 使用了哪些基準測試進行評估？**
A：RSIGame 使用了 GameCraft-Bench 作為主要評估基準，涵蓋 140 個遊戲開發任務，並橫跨兩種遊戲引擎——Godot 與 Phaser，以驗證框架在不同技術堆疊下的泛用性。在生成器的選擇上，研究團隊測試了五種不同的生成器，藉此評估 RSIGame 對不同基礎模型的適用性與提升效果。這種多任務、多引擎、多生成器的設計，使得實驗結果更具說服力，能夠反映 RSIGame 在真實多樣化開發場景中的表現。

**Q8：RSIGame 的關鍵實驗結果為何？**
A：RSIGame 在所有受測條件下都持續性地提升了遊戲品質，且在相同的開發預算（development budget）下表現優於基線方法。最引人注目的結果是，經過經驗內化後，Qwen3.8-27B 在 Godot 上達到 61.38 分、Phaser 上達到 58.53 分，皆超越了 GPT-5.5 的一次性生成（one-shot）分數；同時 Qwen 的生成詞元（generation tokens）減少了 11 倍，顯示出 RSIGame 不僅提升了品質，還大幅提升了效率。在迭代式開發方面，Qwen3.8-27B 在 Godot 上達到 47.77 分，勝過 Kimi-K2.6 的 44.77 分；在 Phaser 上則提升至 50.24 分，超過 GPT-5.5 的 49.44 分一次性生成分數。

**Q9：RSIGame 進行了哪些消融研究（Ablation Studies）？**
A：雖然論文中具體的消融研究細節需參閱完整內容，但從方法論的設計可推知，RSIGame 透過區分「訓練免費遞迴自我改進」與「訓練式經驗內化」兩種策略，得以單獨評估各元件的貢獻。實驗結果顯示，僅使用迭代式開發（不含經驗內化）就能讓 Qwen3.8-27B 在 Godot 上從一次性生成的分數提升至 47.77；而加入經驗內化後更進一步躍升至 61.38，證明了這兩個機制各自都有實質貢獻，且結合後能產生更強的疊加效果。這種層次分明的實驗設計，清楚驗證了局部迴圈、全域迴圈與經驗內化三者缺一不可。

**Q10：RSIGame 在實際應用上有哪些潛在場景？**
A：RSIGame 在實際應用上具有廣泛的潛在場景，首先適用於獨立遊戲開發者或小型工作室，他們往往缺乏足夠的人力進行多輪測試與修訂，而 RSIGame 的自主代理能大幅降低開發成本並加速迭代。其次，對於遊戲教育與程式設計學習領域，RSIGame 可作為一個能即時回饋、改進學生作品的智慧助教，幫助學習者更快掌握遊戲開發的核心概念。此外，在遊戲雛型快速生成（rapid prototyping）的場景中，設計師可以透過自然語言規格快速產出多個遊戲版本，再由 RSIGame 自動優化，大幅縮短從概念到可玩原型的時間。

**Q11：將 RSIGame 整合到產品中時需要考量哪些因素？**
A：將 RSIGame 整合到產品中時，首先需考量的是開發預算（development budget）的設定，因為 RSIGame 的遞迴自我改進機制需要多次執行與測試，計算成本會隨迭代次數增加。其次，產品的延遲容忍度也是關鍵——若使用者期望即時回饋，則需在迭代深度與回應速度間取得平衡；對於可接受較長處理時間的批次型應用，則可充分發揮 RSIGame 的長時程改進優勢。此外，遊戲引擎的相容性、評估標準的客觀性、以及如何將演化式檢核清單的累積經驗有效管理與持久化，都是產品化時必須仔細考量的工程議題。

**Q12：RSIGame 對遊戲開發領域與 AI 研究的影響為何？**
A：RSIGame 對遊戲開發領域的影響在於，它證明了 AI 代理不僅能生成可玩的遊戲，更能透過自主測試與修訂產出真正高品質的成品，這將推動遊戲開發從「人工密集」轉向「人機協作」的新典範。對 AI 研究領域而言，RSIGame 展示了遞迴自我改進在複雜多模態工程任務中的可行性，特別是「經驗內化」的概念——將測試時的成功經驗轉化為訓練時的監督訊號——為如何讓基礎模型從自身執行經驗中學習提供了嶄新的思路。這種「測試-改進-內化」的循環模式，可能會被借鏡到軟體工程、電腦使用自動化等其他需要長時程推理與多輪修正的領域。

**Q13：RSIGame 存在哪些已承認的限制？**
A：RSIGame 的限制之一在於其效能高度依賴底層生成器的能力——若生成器本身無法產出基本的可執行遊戲雛型，後續的遞迴自我改進也無從發揮作用。此外，雖然演化式檢核清單能避免過擬合少數測試案例，但遊戲品質的最終評估仍仰賴於隱藏的任務專屬評分量表（rubric），這使得評估過程本身可能存在偏差或侷限性。另一個限制是計算成本——多次執行、探索與修訂會消耗大量生成詞元與時間，雖然 RSIGame 已透過經驗內化將 Qwen 的詞元消耗降低 11 倍，但對於資源受限的應用場景仍可能是不小的負擔。

**Q14：RSIGame 在哪些情況下可能會失敗？**
A：RSIGame 在面對極度複雜或規格模糊的遊戲需求時可能會失敗，因為局部迴圈的探索-診斷-改進流程需要明確的問題回饋才能有效運作；若遊戲規格本身存在歧義或矛盾，演化式檢核清單可能會累積大量難以優先排序的問題，導致改進方向失焦。此外，當遊戲涉及高度專業的領域知識（如複雜的物理模擬、進階的 AI 行為設計）時，若底層生成器缺乏相關訓練資料，RSIGame 也難以透過迭代修正來補足這類根本性的能力缺口。最後，若全域迴圈誤判了飽和或退化的訊號，可能會過早停止開發或錯誤地保留次佳的檢查點，影響最終成果。

**Q15：RSIGame 未來可能的研究方向有哪些？**
A：RSIGame 未來的研究方向之一是將其應用擴展到更多元的遊戲類型與引擎，例如 3D 遊戲、虛擬實境（VR）遊戲或更複雜的多玩家線上遊戲，以驗證框架的泛用性。另一個方向是強化「經驗內化」的效率與品質，例如透過強化學習或蒸餾技術，讓生成器能從更大量的開發軌跡中學習，進一步縮小小型開源模型與頂級商業模型之間的差距。此外，將 RSIGame 的遞迴自我改進理念推廣到軟體工程、機器人控制、或其他需要長時程多模態推理的領域，也是極具潛力的延伸方向；同時，如何讓代理具備更強的「主動學習」能力——例如主動向使用者詢問澄清問題或請求領域專家指引——也將是提升框架實用性的重要課題。

## 實務應用指南

### 適用場景

1. **獨立遊戲工作室的快速原型開發**：小型團隊可在數小時內將自然語言遊戲規格（如「橫向捲軸射擊遊戲，含三種敵人與 boss 戰」）轉換為可在 Godot 或 Phaser 上執行的可玩原型，縮短從概念驗證到內部測試的週期。

2. **教育領域的程式設計與遊戲設計教學**：教師可讓學生以自然語言描述遊戲規則，由 RSIGame 生成基礎版本，學生再透過修改程式碼學習迭代開發流程，理解探索-診斷-改進迴圈在真實軟體工程中的運作。

3. **遊戲大賽與黑客松的自動化評審輔助**：主辦單位可在 GameCraft-Bench 類型的基準上，使用 RSIGame 作為「品質下限參考線」，評估參賽作品的相對完成度與可玩性。

4. **企業內部培訓模擬器生成**：需要客製化訓練情境（如倉儲物流模擬、客服對話演練）的企業，可透過自然語言規格快速生成 Phaser 網頁版互動教材，並透過迭代迴圈持續優化任務設計。

5. **AIGC 平台的「遊戲生成」功能後端**：AI 內容平台可整合 RSIGame 作為遊戲類別的生成引擎，結合經驗內化訓練降低推論成本（論文顯示生成詞元可減少 11 倍），使大規模商用部署更具經濟可行性。

### 實作前置條件

**資料需求**
- 遊戲規格資料集：需準備自然語言格式的遊戲描述（玩法、機制、視覺風格、關卡結構），建議至少數百至數千筆，涵蓋目標引擎（Godot/Phaser）與多種遊戲類型。
- 示範回放軌跡：每個生成遊戲需附帶可重播的示範軌跡（replayable demonstration traces），用於評分與診斷。
- 評分量測 rubric：需定義任務專屬的隱藏評分標準，作為全域迴圈品質監控與飽和偵測的依據。
- 成功開發軌跡：用於經驗內化訓練，需收集「探索→診斷→修訂→驗證」的成功序列作為監督訊號。

**運算資源**
- 推論階段：至少需支援多代理並行執行的環境（控制器 + 探索者 + 修訂者），建議配備具備充足 GPU 記憶體的工作站或雲端實例，以運行 27B 等級的開源模型。
- 訓練階段：經驗內化（experience internalization）需對生成器進行監督式微調，建議使用多節點 GPU 叢集（如 8×H100 等級）以處理長時程開發軌跡資料。
- 遊戲執行環境：需預先部署 Godot 與 Phaser 的 headless 執行環境，以便代理能自動化啟動、測試與截圖。

**技能前提**
- 熟悉 LLM/VLM 代理框架（如 LangGraph、AutoGen）以實作探索-診斷-改進迴圈。
- 具備 Godot（GDScript）或 Phaser（JavaScript/TypeScript）遊戲引擎的基礎知識，便於診斷代理理解生成程式碼。
- 具備軟體工程測試自動化經驗，能設計可程式化觸發的測試案例與回放機制。
- 對長時程代理任務的 token 預算管理與成本控制有實務經驗。

### 實作步驟建議

1. **建立基準與評估管線**：先導入或重建 GameCraft-Bench 風格的 140 個任務集，涵蓋 Godot 與 Phaser 兩種引擎；建立 headless 執行環境與 rubric 評分器，作為後續所有迭代的「地面真實」。

2. **實作局部迴圈（Explore-Diagnose-Improve）**：
   - 部署控制器（Controller）與探索者（Explorer）雙代理，控制器決定探索方向，探索者實際操作可執行遊戲並蒐集證據（截圖、日誌、狀態）。
   - 設計演化式檢核清單（evolving checklist）的資料結構，使其能隨新證據累積而擴展，並支援優先排序。
   - 實作基於證據的修訂（evidence-grounded revision）模組，僅在檢核清單有明確證據時才觸發程式碼修改，避免無根據的猜測式編輯。

3. **實作全域迴圈（Global Loop）**：
   - 建立品質追蹤器，跨迭代記錄每個版本的 rubric 分數。
   - 實作最佳檢查點保留機制（best checkpoint preservation），確保即使後續迭代退化也能回退。
   - 加入飽和偵測（saturation detection）與退化偵測（regression detection），當連續多輪無提升或分數下降時，注入稀疏的高階指引（sparse high-level guidance）以引導跨階段演化。

4. **整合訓練免費的 RSI 流程**：將局部與全域迴圈串接，設定開發預算上限（迭代次數、token 用量或時間），在預算內反覆執行直至飽和或達標。

5. **蒐集成功軌跡並進行經驗內化訓練**：
   - 在多個任務上執行 RSI 流程，記錄最終成功版本的完整開發軌跡（探索決策、診斷結論、修訂動作、驗證結果）。
   - 將這些軌跡轉換為監督資料，對底層生成器（如 Qwen3.8-27B）進行微調，使模型內化「如何有效開發遊戲」的經驗。
   - 評估微調後模型的一次性生成（one-shot）品質與 token 效率，目標是在維持或提升分數的同時大幅降低生成成本。

6. **部署與監控**：將訓練後的生成器與 RSI 迴圈封裝為 API 服務，提供自然語言規格輸入介面、迭代進度儀表板與最終遊戲下載功能；持續監控生成品質、token 消耗與使用者回饋。

### 潛在風險與注意事項

- **過擬合小測試集的風險**：論文明確指出，naive 迭代精煉容易過擬合少數測試案例，產生脆弱遊戲。緩解方式：演化式檢核清單必須持續擴展，強迫代理探索新情境而非反覆修正同一條路徑；同時維持多元的測試案例池。

- **長時程迭代的退化與振盪**：全域迴圈雖能偵測退化，但若飽和偵測門檻設得不當，可能過早停止或過晚介入。建議設定保守的早期停止條件，並允許全域迴圈注入高階指引以打破局部最優。

- **生成詞元成本失控**：雖然經驗內化可降低 11 倍 token，但訓練免費的 RSI 階段在多輪迭代下仍可能累積大量 token。緩解方式：為每個任務設定嚴格的開發預算上限，並在控制器層級加入 token 用量感知。

- **多模態資產品質不穩**：遊戲涉及程式碼、視覺與文字素材的異質整合，視覺語言模型生成的素材可能與程式碼邏輯不一致。建議在診斷階段加入專門的資產一致性檢查，並在 rubric 中權衡視覺與功能分數。

- **評估 rubric 的偏誤**：隱藏 rubric 若過於狹隘，可能誤導代理優化分數而非真實可玩性。緩解方式：rubric 應涵蓋功能完整性、穩健性、玩家體驗等多面向，並定期以人工 playtest 抽樣驗證。

- **經驗內化訓練的資料偏差**：若成功軌跡集中於少數遊戲類型，微調後模型可能對未見類型泛化不佳。建議在軌跡蒐集階段刻意平衡任務類型分佈，並保留獨立的 out-of-distribution 評估集。

### 與其他技術的整合建議

- **與程式碼生成代理整合**：RSIGame 的修訂階段可與專門的程式碼 LLM（如 Codex、Code Llama）解耦，將「決定改什麼」與「實際寫程式碼」分派給不同模型，提升診斷與實作的專業度。

- **與遊戲測試自動化工具整合**：探索者可串接成熟的遊戲測試框架（如 Godot 的 GUT、Phaser 的測試插件），將人工探索轉化為可重現的自動化測試案例，增強證據的可信度。

- **與版本控制系統整合**：將全域迴圈的最佳檢查點機制對接 Git，使每次迭代的程式碼變更可追溯、可回退，並方便團隊協作審查。

- **與 RLHF / 偏好學習整合**：rubric 分數可作為獎勵訊號，進一步對生成器進行強化學習微調，與經驗內化的監督式學習互補。

- **與 AIGC 內容平台整合**：將 RSIGame 封裝為遊戲類別的生成 API，與既有的圖像、音樂生成服務組合，提供「一站式遊戲創作」體驗；前端可串接低程式碼編輯器，讓使用者進一步客製化生成結果。

- **與 CI/CD 流程整合**：在企業內部培訓模擬器等場景中，可將 RSIGame 的迭代流程納入 CI/CD，每次規格更新自動觸發重新生成與回歸測試。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節的問題動機，理解「為什麼迭代式開發會過擬合」這個核心痛點；接著跳過技術細節，直接看圖 2 的框架總覽，建立「局部迴圈 + 全域迴圈」的直覺。最後閱讀第 3.1.1 節的探索-診斷-改進流程，嘗試在小型遊戲（如 Pong）上手體驗演化式檢核清單的運作。

**給 AI 工程師**：重點研讀第 3 節的訓練免費 RSI 架構，特別是控制器與探索者的代理分工、演化式檢核清單的資料結構設計、以及全域迴圈的飽和/退化偵測邏輯；接著深入第 3.2 節（若可取得）的經驗內化訓練流程，思考如何將成功軌跡轉換為監督資料。建議實際實作一個最小可運行版本，比較有無全域迴圈時的迭代效率差異。

**給研究者**：本論文在「代理式長時程任務」與「遞迴自我改進」兩個方向都有貢獻。建議從第 2 節的形式化定義出發，分析局部與全域迴圈的理論意涵；接著檢視 GameCraft-Bench 的任務設計與評估協議，思考 rubric 設計對代理行為的誘導效果。經驗內化部分可與現有的 self-play、RLHF、distillation 文獻對照，探討其在長時程工程任務上的獨特價值與限制。

**給產品經理**：聚焦於第 1 節的應用動機與第 4 節（若可取得）的實驗結果，特別是 Qwen3.8-27B 在經驗內化後超越 GPT-5.5 一次性生成分數、且 token 成本降低 11 倍的數據，這對成本敏感的商用部署至關重要。建議評估 RSIGame 在自身產品中的定位：是作為「全自動生成器」還是「人類開發者的加速器」？並思考如何設計使用者介面，讓非技術使用者能有效提供自然語言規格並理解迭代進度。
