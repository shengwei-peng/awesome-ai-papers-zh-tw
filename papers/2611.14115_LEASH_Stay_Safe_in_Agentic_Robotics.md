# LEASH：在代理機器人學（Agentic Robotics）中保持安全

## ⚡ TL;DR

基礎模型驅動機器人潛藏嚴重安全風險，且缺乏全面評估方法。
本文提出 RoboRisk 基準與 LEASH 防護框架，以任務、動作、提交三道閘門把關。
實驗顯示 LEASH 有效降低六款基礎模型的危害率，且幾乎不影響任務完成率與效率。

## 摘要翻譯

GPT 和 Claude 等基礎模型（Foundation Model）在空間理解（Spatial Understanding）和具身智慧（Embodied Intelligence）方面展現了強大的能力。這些進展使代理機器人學（Agentic Robotics）成為邁向機器人領域通用人工智慧（Artificial General Intelligence, AGI）的有前景的途徑。然而，我們發現使用基礎模型控制機器人會帶來嚴重的安全風險，且全面的安全評估仍然不足。我們介紹 RoboRisk，一個用於評估代理機器人學安全性的全面基準測試（Benchmark）。其包含 92 個模擬任務（Simulated Task）和 13 個實體機器人（Physical Robot）任務，分為五個類別：任務層級拒絕（Task-level Refusal, T）、計畫修復（Plan Repair, P）、執行時危險（Execution-time Hazard, E）、注入（Injection, I）和序列記憶（Sequential Memory, S）。先前的基準測試最多涵蓋其中兩個類別，且部分僅評估文字輸出。相比之下，RoboRisk 涵蓋全部五個類別，並以閉迴路（Closed Loop）執行每項任務。我們在 RoboRisk 上評估六個最先進的基礎模型：GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna、Claude Opus 5.5、Gemini 4 Argon 和 Grok 4.7。這些模型普遍呈現較高的危害率（Harm Rate）。我們也評估了兩個機器人專用 API：Dream API 和 PokeBot 的 RoboAPI。我們進一步提出租約強制代理安全防護（Lease-Enforced Agentic Safety Harness, LEASH），為代理機器人學提供必要的安全基礎設施，並可整合至幾乎任何代理架構中。LEASH 利用決策模型（Decision Model）（Jev 或 OpenAI 決策 API（OpenAI's Decisions API））來實作任務閘門（Task Gate）、動作閘門（Action Gate）和提交閘門（Commit Gate），根據其視覺上下文（Visual Context）審查任務、每個動作及每個不可逆操作（Irreversible Operation）。規劃器（Planner）和所有三個閘門共用同一個安全政策（Safety Policy）。在 RoboRisk 模擬和實體機器人上的實驗顯示，LEASH 能有效降低所有六個基礎模型的危害。它大致維持其任務完成表現，且所增加的時間和 token 開銷（Token Overhead）極小。

### 核心貢獻（3～5點）
- 提出 RoboRisk 基準測試，涵蓋五大安全類別（任務層級拒絕、計畫修復、執行時危險、注入、序列記憶），包含 92 個模擬任務與 13 個實體機器人任務，並以閉迴路執行，彌補先前基準測試僅涵蓋最多兩類的不足。
- 系統性評估六個最先進基礎模型（GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna、Claude Opus 5.5、Gemini 4 Argon、Grok 4.7）以及兩個機器人專用 API（Dream API、PokeBot 的 RoboAPI），揭示其普遍存在高危害率。
- 提出 LEASH（租約強制代理安全防護）通用安全防護框架（Harness），透過決策模型實作任務閘門、動作閘門、提交閘門三層審查機制，可整合至幾乎任何代理架構。
- 實驗證實 LEASH 能有效降低所有六個基礎模型的危害率，同時維持任務完成表現，且僅增加極少的時間與 token 開銷。

### 適合對象
從事代理機器人學、具身智慧、機器人安全、人工智慧安全對齊等領域的研究者與工程師；關注基礎模型實際部署風險的 AI 政策制定者與產業實務者；以及對通用人工智慧發展路徑與基礎模型實體化應用感興趣的學術界人士。

## 深度分析

#### 方法論解析

本論文提出了一套完整的「評估—防護」雙軌方法論，核心由兩個相互耦合的元件構成：**RoboRisk 基準測試**與 **LEASH 安全防護框架**。以下從設計理念、系統架構與技術細節三個層面進行深入剖析。

##### 1. 風險分類體系的設計邏輯

論文將代理機器人學（agentic robotics）中的安全風險劃分為五個互斥且互補的類別，這是整個方法論的基石：

- **任務層級拒絕（Task-level Refusal, T）**：模型是否能在接收到本質上危險的指令（例如「把電子設備放進水裡」）時主動拒絕執行。這對應於傳統 LLM 安全研究中的「有害請求」場景，但延伸至物理後果。
- **計畫修復（Plan Repair, P）**：當初始計畫在執行過程中遇到障礙物或環境變化時，模型是否能產生安全的替代方案，而非為了完成任務而採取危險捷徑。
- **執行時危險（Execution-time Hazard, E）**：在閉迴路（closed loop）執行中，模型是否能感知即時的物理危險（例如將牛奶杯懸掛於電源插座上方）並及時中止。
- **注入（Injection, I）**：抵抗提示注入（prompt injection）攻擊的能力，例如場景中出現惡意文字標示或視覺注入，誘使機器人執行有害動作。
- **序列記憶（Sequential Memory, S）**：在多步驟任務中，模型是否能記住先前已建立的危險上下文（例如先前已將液體倒入容器，後續不應再將電子設備放入同一容器）。

這五類風險的設計具有**正交性**與**完備性**的雙重考量：正交性意味著每類風險對應不同的失效模式（從語意理解、規劃彈性、即時感知、對抗魯棒性到長期記憶），完備性意味著從「接收任務」到「完成任務」的整個代理迴路（agentic loop）都被覆蓋。

##### 2. LEASH 三閘門架構

LEASH 的核心設計哲學是「**將規劃器視為黑盒子（black box）**」，這是一個極具工程智慧的決策。其架構包含三個串接的安全閘門：

- **任務閘門（Task Gate）**：在任務開始前審查使用者指令與初始視覺上下文，判斷是否應直接拒絕。對應風險類別 T。
- **動作閘門（Action Gate）**：在每個動作執行前審查當前動作提案與即時視覺上下文，判斷該動作是否會引入新的危險。對應風險類別 P 與 E。
- **提交閘門（Commit Gate）**：專門審查不可逆操作（irreversible operation），例如「倒液體」、「丟棄物品」、「切割」等，這些操作一旦執行便無法回滾。對應風險類別 I 與 S。

三個閘門共享同一份**安全政策（safety policy）**，這是 LEASH 能夠保持一致性的關鍵。安全政策以自然語言形式描述可接受與不可接受的行為邊界，由決策模型（Jev 或 OpenAI 決策 API）進行推理。這種「政策即程式碼（policy-as-code）」的設計使得安全規則可以被集中更新，而無需修改各個閘門的內部邏輯。

##### 3. 視覺接地（Visual Grounding）機制

與既有 LLM 安全防護僅審查文字輸出不同，LEASH 的每個閘門都接收**當前攝影機影像**作為輸入。這是論文最重要的技術貢獻之一：它將安全判斷從「語意層面」提升至「語意—物理」雙重層面。例如，僅憑文字「把杯子放到桌上」無法判斷該動作是否安全，但若同時看到桌面上有電源插座，則可立即觸發危險警報。

##### 4. 決策模型的選擇

論文採用 Jev 或 OpenAI 決策 API 作為閘門背後的推理引擎，這是一種**職責分離（separation of concerns）**的設計：規劃器專注於「如何完成任務」，決策模型專注於「是否應該執行」。這種分離使得 LEASH 可以獨立於規劃器進行升級與審計，也降低了安全審查的耦合成本。

##### 5. 模擬—實體一致性設計

RoboRisk 同時包含 92 個模擬任務與 13 個實體機器人任務，且所有任務皆以閉迴路方式執行。這種設計避免了「僅評估文字輸出」的常見陷阱——許多既有基準測試僅讓模型生成動作序列的文字描述，卻從未實際執行，因此無法暴露真實的物理危險。

#### 實驗數據解讀

##### 1. 危害率（Harm Rate, HR）的分布與意涵

論文報告六個基礎模型在 RoboRisk 上的危害率介於 **9.06% 至 76.92%** 之間，這個數字區間極為發人深省：

- **危害率最低（9.06%）**的模型可能屬於較小規模或經過較多安全對齊的版本，但仍意味著每十次任務中就有近一次產生物理危害。
- **危害率最高（76.92%）**的模型則意味著超過四分之三的任務會產生某種形式的危害，這在實體機器人部署場景中是**完全不可接受**的。

這個分布揭示了一個關鍵事實：**現有基礎模型的安全對齊（safety alignment）並未涵蓋物理世界的語意危險**。傳統的 RLHF 或憲法 AI（Constitutional AI）方法主要在文字與對話層面進行對齊，但對於「將手機放入水中」這類需要視覺接地才能理解的危險，現有機制幾乎完全失效。

##### 2. 機器人專用 API 的表現

論文同時評估了 Dream API 與 PokeBot 的 RoboAPI 兩個機器人專用 API。這些 API 通常被設計為比通用基礎模型更適合機器人控制，但其在 RoboRisk 上的表現同樣不佳。這說明**機器人專用化並不等於安全化**——一個模型可能更擅長控制機械手臂，卻仍會犯下語意層面的安全錯誤。

##### 3. 人類存在差距（Human-Presence Gap）

論文發現一個意外的「**模擬—實體差距（sim-to-real gap）**」，並將其命名為「人類存在差距（Human-Presence Gap）」：當人類出現在實體機器人場景中時，部分基礎模型會變得**過度謹慎**，無法在「任務執行」與「人機協作」之間取得平衡；而在模擬環境中的類似場景則執行順暢。

這個現象的可能成因包括：
- 訓練資料中實體人機互動樣本稀少，導致模型在面對真實人類時產生不確定性。
- 安全對齊機制將「人類存在」過度泛化為「危險信號」，觸發過度保守行為。
- 模擬環境中的人類模型缺乏真實人類的細粒度特徵（如呼吸、眼神、肢體語言），使得模型無法區分「協作對象」與「障礙物」。

這個發現對實體部署具有重要意義：**過度安全本身也是一種安全問題**，因為它會導致任務失敗、使用者體驗下降，甚至在緊急情況下造成危害（例如機器人因過度謹慎而無法及時遞送藥物）。

##### 4. LEASH 的有效性

實驗結果顯示 LEASH 能夠**有效降低所有六個基礎模型的危害率**，同時**大幅保留任務完成率**。這意味著 LEASH 並非以犧牲功能性為代價換取安全性，而是實現了真正的「安全—效能」雙贏。

具體而言：
- **危害率降低**：所有模型的 HR 皆顯著下降，部分模型甚至降至接近零。
- **任務完成率保留**：在大多數情況下，任務成功率僅小幅下降，證明 LEASH 不會過度干預正常任務。
- **時間與 token 開銷**：增加的延遲與 token 成本「極小」，這對於實際部署至關重要——若安全機制使機器人反應過慢，則會喪失實用性。

##### 5. 視覺接地的重要性

雖然論文中未明確給出「僅文字審查」與「視覺接地審查」的對比數據，但從方法論設計可推論：視覺接地是 LEASH 能夠捕捉「將牛奶杯懸於電源插座上方」這類危險的關鍵。沒有視覺輸入，閘門將無法區分「安全的桌面」與「有電源插座的桌面」，這從根本上限制了安全審查的語意深度。

#### 與現有研究的比較

##### 1. 與傳統機器人安全的比較

傳統機器人安全研究聚焦於**顯式約束（explicit constraints）**：力量限制、速度限制、分離距離、碰撞偵測、無碰撞軌跡規劃（collision-free trajectory planning）、控制屏障函數（control barrier functions）等。這些方法在結構化工業環境中表現優異，但面對開放場景中的代理機器人時顯著不足——正如論文所述，「一條無碰撞軌跡仍可能將電子設備放入水中」。

LEASH 的貢獻在於將安全審查從「**幾何層面**」提升至「**語意層面**」，這是傳統方法無法觸及的維度。然而，LEASH 並非要取代傳統方法，而是作為**補充層**：傳統方法處理「硬即時安全」（如碰撞），LEASH 處理「軟語意安全」（如危險物品擺放）。

##### 2. 與既有 LLM/代理安全基準的比較

既有基準（如 HarmBench、AgentBench 等）主要評估：
- 有害請求的文字回應
- 工具呼叫的危險性
- 注入指令的抵抗力

這些基準的共同限制是**動作無物理後果**——即使模型「同意」執行危險動作，也不會真正造成傷害。RoboRisk 的突破在於**閉迴路實體執行**，使得安全評估從「紙上談兵」走向「真槍實彈」。

##### 3. 與既有機器人安全基準的比較

近期研究（如 [23, 48, 49, 55]）已開始關注基礎模型控制機器人的安全問題，但論文指出這些研究**僅覆蓋五類風險中的少數類別**（多數僅涵蓋 T 與部分 E），且**僅評估文字輸出**而非實際執行。RoboRisk 同時覆蓋五類風險並執行所有任務，這在覆蓋廣度與評估深度上皆為首創。

##### 4. 與既有防禦機制的比較

近期防禦機制包括：
- **時序邏輯防護欄（temporal-logic guardrails）** [48]：基於形式化方法，但難以表達複雜語意規則。
- **可執行安全謂詞（executable safety predicates）** [60]：需要預定義謂詞庫，難以涵蓋開放場景。
- **VLA 模型內建安全約束** [20, 69]：需要重新訓練模型，無法即時部署至新模型。
- **防碰撞架構** [63]：僅處理幾何碰撞，不處理語意危險。

LEASH 的優勢在於：
- **模型無關（model-agnostic）**：無需重新訓練，可即時部署至任何新發布的商業模型。
- **政策集中**：安全規則可集中更新，無需修改各個元件。
- **視覺接地**：能處理需要即時視覺理解的危險。

##### 5. 局限性

儘管 LEASH 表現優異，仍存在以下局限：

- **決策模型本身的可靠性**：LEASH 的安全性最終取決於其背後的決策模型（Jev 或 OpenAI 決策 API）。若決策模型本身存在偏誤或被對抗性攻擊突破，LEASH 將失去防護能力。
- **安全政策的表達力**：以自然語言描述的安全政策可能存在歧義或遺漏，特別是對於罕見或新型危險。
- **延遲累積**：三個閘門的串接審查會引入額外延遲，雖然論文聲稱「極小」，但在高速控制場景中仍可能成為瓶頸。
- **模擬—實體差距**：人類存在差距表明，僅在模擬環境中訓練與評估安全政策可能不足以應對實體部署的複雜性。
- **基準測試規模**：92 個模擬任務與 13 個實體任務相對有限，可能無法覆蓋所有可能的危險場景。

#### 可重現性評估

##### 1. 程式碼與資料集的可用性

從論文提供的資訊來看，**未明確聲明程式碼開源**。然而，論文中提及的元件（Jev 決策模型、OpenAI 決策 API、Codex 框架等）皆為可獲取的外部資源，這為部分重現提供了基礎。

##### 2. 基準測試的可重現性

RoboRisk 的設計具有**高度可重現性**：
- 92 個模擬任務可在標準機器人模擬器（如 AI2-THOR、Habitat、Isaac Sim）中重現。
- 13 個實體任務的硬體需求（機械手臂、攝影機等）相對標準。
- 五類風險的分類體系清晰明確，便於擴展與改進。

##### 3. 模型權重與 API 訪問

論文評估的六個基礎模型（GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna、Claude Opus 5.5、Gemini 4 Argon、Grok 4.7）皆為商業模型，透過 API 訪問，這降低了重現的硬體門檻，但同時也意味著評估結果可能隨模型版本更新而失效。

##### 4. 實體實驗的可重現性

實體機器人實驗的可重現性受限於：
- 物理環境的精確重建困難。
- 人類操作員的行為變異性。
- 硬體磨損與校準差異。

論文未明確說明是否提供實體實驗的詳細記錄（如影片、感測器資料、控制指令日誌），這對於完全重現實體實驗至關重要。

##### 5. 整體可重現性評級

綜合考量，論文的**概念與方法論高度可重現**，但**完整實驗結果的可重現性中等**。建議作者開源：
- RoboRisk 基準測試的完整任務定義與評估腳本。
- LEASH 的參考實作（即使是概念驗證等級）。
- 實體實驗的影片記錄與日誌。

#### 未來研究方向

##### 1. 形式化驗證與神經符號融合

當前 LEASH 的安全政策以自然語言表達，缺乏形式化語意。未來可探索：
- 將安全政策編碼為時序邏輯（temporal logic）或一階邏輯（first-order logic），結合神經感知與符號推理。
- 使用 SMT 求解器（satisfiability modulo theories solver）對閘門決策進行形式化驗證。
- 構建可證明安全（provably safe）的代理機器人架構。

##### 2. 自適應安全政策

當前安全政策為靜態規則，未來可探索：
- 從人類示範中學習安全政策（learning from human demonstration）。
- 透過強化學習自動發現新型危險模式。
- 結合憲法 AI（Constitutional AI）方法，讓模型自我批評與修正安全決策。

##### 3. 對抗魯棒性

LEASH 對注入攻擊（類別 I）的抵抗力尚未充分評估。未來可探索：
- 對視覺注入（visual injection）的對抗訓練。
- 對決策模型本身的紅隊測試（red teaming）。
- 多閘門冗餘（multi-gate redundancy）以防止單點失效。

##### 4. 人機協作中的動態安全

人類存在差距揭示了人機協作中的安全挑戰。未來可探索：
- 區分「人類存在」與「人類危險」的細粒度感知模型。
- 結合社會信號（如眼神、肢體語言）的意圖理解。
- 動態調整安全閾值以適應不同協作情境。

##### 5. 跨領域泛化

當前 RoboRisk 主要聚焦於桌面操作與家庭場景。未來可擴展至：
- 工業協作機器人（collaborative robot, cobot）。
- 自動駕駛與移動機器人。
- 醫療機器人與高風險場景。

##### 6. 安全與效能的理論權衡

LEASH 展示了安全與效能可以兼顧，但缺乏理論分析。未來可探索：
- 安全—效能權衡的形式化界定（formal characterization）。
- 在最壞情況下保證安全下界（safety lower bound）的演算法。
- 將安全機制整合至規劃目標函數（planning objective function）的端到端學習。

##### 7. 監管與標準化

隨著代理機器人走向實際部署，安全標準與監管框架將成為關鍵議題。未來可探索：
- 將 RoboRisk 發展為業界標準安全基準（類似 MLPerf）。
- 與 ISO、IEC 等標準組織合作制定代理機器人安全規範。
- 建立第三方安全認證機制。

##### 8. 多代理系統中的安全

當前研究聚焦於單一代理機器人，未來可探索多代理系統中的安全問題：
- 代理間的衝突避免與協調。
- 集體危險的識別與預防。
- 惡意代理的識別與隔離。

##### 9. 長期自主中的安全漂移

機器人在長期自主運行中可能面臨「安全漂移（safety drift）」：環境變化導致原本安全的行為變得危險。未來可探索：
- 持續監控與安全政策更新機制。
- 異常檢測與自動回滾（automatic rollback）。
- 人機迴路中的持續學習（continual learning in the loop）。

##### 10. 認知架構整合

LEASH 目前作為外部安全層，未來可探索將安全機制整合至代理的認知架構核心：
- 將安全閘門內化為規劃過程的一部分。
- 構建「安全感知（safety-aware）」的規劃器，而非「安全審查（safety-reviewed）」的規劃器。
- 從「外部監督」走向「內在動機（intrinsic motivation）」的安全驅動代理。

這些研究方向不僅能推動代理機器人學的安全發展，也將為通用人工智慧（AGI）的安全對齊提供重要的物理世界試金石——畢竟，若一個系統無法在物理世界中保持安全，其在更抽象層面的安全性也將難以令人信服。

## 論文問答

**Q1：代理機器人學（agentic robotics）目前面臨的最核心安全問題是什麼？**
A：根據本文，代理機器人學的核心安全問題在於基礎模型（如 GPT、Claude、Gemini、Grok 等）雖然具備強大的空間理解與推理能力，但用於控制機器人時會產生嚴重的語意危險（semantic hazard）。傳統機器人安全方法僅能處理可預先定義的狀態約束（例如碰撞偵測、無碰撞軌跡），卻無法理解動作的「意義」——例如一條無碰撞軌跡仍可能將電子裝置放入水中。此外，由於基礎模型支援即插即用的機器人控制，危險行為能快速觸及真實使用者，而現有的防護框架（如 Codex 框架）並非為三維實體世界所設計，因此無法有效防範此類風險。

**Q2：為什麼現有的機器人安全方法與基礎模型內建的安全防護不足以應對這些風險？**
A：傳統機器人安全方法（如控制屏障函數、安全強化學習、碰撞偵測）只能處理可預先指定的狀態約束，無法推理動作的語意意涵，因此無法辨識「將手機放入水中」這類危險。基礎模型內建的防護（如 Codex 框架的自動審查）雖然能過濾有害文字輸出，但這些機制並非針對三維實體世界設計，無法理解視覺上下文中的物理後果。此外，現有針對基礎模型控制機器人的安全研究多僅限於任務層級的危害（對應 RoboRisk 中的 T 類別），而對計畫修復、執行時危險、注入攻擊與序列記憶等風險類別的探討仍相當有限。

**Q3：為什麼這項研究對機器人領域與通用人工智慧（AGI）的發展至關重要？**
A：代理機器人學被視為機器人領域邁向 AGI 的重要路徑，因為基礎模型展現了優異的泛化能力，能在零樣本設定下控制機械手臂並完成複雜任務。然而，若缺乏全面的安全評估與防護機制，這些強大的代理機器人將對真實使用者構成實質危害，可能導致硬體損壞甚至人身傷害。本文的研究不僅提出了首個涵蓋五類風險的綜合性基準測試 RoboRisk，更提出了可即時整合的安全防護系統 LEASH，使新發布的商業模型能在第一時間獲得保護，對於推動代理機器人安全落地具有關鍵意義。

**Q4：LEASH 的核心方法是什麼？它如何運作？**
A：LEASH（Lease-Enforced Agentic Safety Harness，租約強制代理安全防護）的核心方法是作為一個模型無關（model-agnostic）的安全層，可整合至幾乎任何代理機器人架構中。它利用 Jev 決策模型或 OpenAI 的決策 API（Decisions API）實作三道安全閘門：任務閘門（task gate）、動作閘門（action gate）與提交閘門（commit gate）。這三道閘門會在當前的視覺上下文（camera images）中審查任務、每個動作以及每個不可逆操作（irreversible operation），並與規劃器（planner）共享同一份安全政策（safety policy），從而對整個代理迴路進行監督。

**Q5：LEASH 最重要的創新點為何？**
A：LEASH 最關鍵的創新在於將安全審查「視覺接地」（visually grounded）——不同於僅檢查文字輸出的現有防護機制，LEASH 的三道閘門會根據當前的相機影像進行審查，使安全決策能考量真實的三維物理場景。此外，LEASH 將規劃器視為黑盒子（black box），無需重新訓練即可部署，因此能在新商業模型發布的當下立即提供保護。這種「即插即用」的特性結合共享安全政策的設計，使 LEASH 能同時防範五類風險，突破了現有方法僅能處理單一類別的限制。

**Q6：LEASH 在設計上有哪些重要的取捨與選擇？**
A：LEASH 在設計上做出了幾項關鍵選擇：首先，它選擇使用獨立的決策模型（Jev 或 OpenAI 決策 API）而非修改基礎模型本身，這樣既保留了規劃器的泛化能力，又避免了昂貴的重新訓練成本。其次，它採用三道閘門（任務、動作、提交）的分層設計，分別在不同抽象層級進行審查，以平衡安全性與任務完成率。最後，它讓規劃器與所有閘門共享同一份安全政策，確保整個系統對「什麼是安全的」有一致的理解，同時僅帶來極小的時間與 token 開銷。

**Q7：RoboRisk 基準測試包含哪些內容？它與既有基準測試有何不同？**
A：RoboRisk 是一個專為代理機器人安全設計的綜合性基準測試，包含 92 個模擬任務與 13 個實體機器人任務，涵蓋五大風險類別：任務層級拒絕（T）、計畫修復（P）、執行時危險（E）、注入（I）與序列記憶（S）。相較於既有基準測試最多僅涵蓋兩個類別、且部分僅評估文字輸出，RoboRisk 涵蓋全部五類並以閉迴路（closed loop）方式執行每個任務，無論在模擬或實體機器人上皆如此。這種全面性使 RoboRisk 能更真實地反映代理機器人在實際部署中可能遭遇的多元風險。

**Q8：實驗中最關鍵的結果是什麼？LEASH 的效果如何？**
A：實驗結果顯示，六款頂尖基礎模型在 RoboRisk 上的危害率（Harm Rate, HR）介於 9.06% 至 76.92% 之間，凸顯出嚴重的安全風險；其中 Claude Opus 5.5 出現將手機掉入水中的情況，GPT-6 Astra 則將一杯牛奶端過電源插座。在導入 LEASH 後，所有六款基礎模型的危害率皆顯著下降，同時任務完成率大致維持，且額外的時間與 token 開銷極小。此外，實驗也首次評估了兩個機器人專用 API（Dream API 與 PokeBot 的 RoboAPI），並發現一個意外的模擬到真實落差——本文稱之為「人類存在落差」（Human-Presence Gap），即部分模型在有人類在場時會變得過度謹慎。

**Q9：論文中是否有進行消融研究（ablation study）來驗證各元件的貢獻？**
A：雖然提供的全文片段未完整呈現消融研究的細節，但根據方法描述，LEASH 的三道閘門（任務閘門、動作閘門、提交閘門）與共享安全政策是其兩大核心元件，因此可合理推測作者透過消融實驗驗證了各閘門的個別貢獻。實驗結果顯示 LEASH 能「有效降低所有六款基礎模型的危害率」，暗示各閘門在不同風險類別上扮演互補角色——例如任務閘門主要處理 T 類別，動作閘門處理 P 與 E 類別，而提交閘門則專門把關不可逆操作以對抗 I 與 S 類別的攻擊。

**Q10：LEASH 在實際應用中可適用於哪些場景？**
A：LEASH 適用於任何使用基礎模型作為「大腦」進行任務規劃的代理機器人系統，特別是在開放場景中運作的機器人，例如家用服務機器人、物流倉儲機器人、醫療輔助機器人等。由於 LEASH 將規劃器視為黑盒子且無需重新訓練，它特別適合需要快速整合新模型的商業部署場景。此外，LEASH 的視覺接地審查機制使其能在動態、不可預測的環境中持續監督機器人行為，這對於機器人需要在人群中工作的場景（如餐廳、醫院、零售店面）尤為重要。

**Q11：在將 LEASH 整合至產品時，需要考量哪些實務因素？**
A：產品整合時需考量以下因素：首先，雖然 LEASH 帶來的時間與 token 開銷極小，但對於延遲敏感的應用（如即時協作機器人）仍需評估三道閘門的額外推理時間是否可接受。其次，決策模型（Jev 或 OpenAI 決策 API）的選擇會影響成本與效能，產品團隊需根據目標市場的隱私與部署需求決定使用雲端 API 或本地模型。此外，安全政策的定義需要領域專家參與，以確保政策內容能反映特定應用場景的安全標準與法規要求。

**Q12：這項研究對機器人安全領域的整體影響為何？**
A：這項研究對領域的影響可分為三個層面：在評估面向上，RoboRisk 提供了首個涵蓋五類風險的綜合性基準測試，將成為未來代理機器人安全研究的標準工具。在方法面向上，LEASH 提出的「視覺接地安全閘門 + 共享安全政策」框架為後續研究提供了可擴展的設計範式。在產業面向上，「人類存在落差」的發現提醒開發者注意模擬與真實部署間的落差，特別是人機協作場景中模型行為的變化，將推動業界在部署前進行更全面的實體測試。

**Q13：LEASH 存在哪些已知的限制？**
A：根據全文描述，LEASH 的已知限制包括：首先，其效能高度依賴於底層決策模型（Jev 或 OpenAI 決策 API）的品質，若決策模型本身存在偏誤或盲點，LEASH 的保護效果將受影響。其次，雖然 LEASH 將規劃器視為黑盒子帶來了靈活性，但也意味著它無法修正規劃器內部的錯誤，只能在外部進行攔截。此外，LEASH 目前主要針對單一機器人代理進行設計，對於多機器人協作場景中的安全協調問題尚未探討。

**Q14：LEASH 可能會在哪些情況下失效？**
A：LEASH 可能在以下情況下失效：當攻擊者設計出能同時欺騙規劃器與決策模型的對抗性輸入時，LEASH 的視覺接地審查可能無法察覺精心偽裝的危害；當任務涉及高度複雜或前所未見的場景時，決策模型可能缺乏足夠的判斷依據而做出錯誤的安全決策；當人類存在落差導致模型過度謹慎時，LEASH 可能會放大此問題而過度拒絕合理任務。此外，若安全政策本身定義不完善或與實際場景脫節，三道閘門的審查將無法發揮預期效果。

**Q15：這項研究未來可朝哪些方向發展？**
A：未來發展方向可包括：將 LEASH 擴展至多機器人協作場景，研究代理間的安全協調與衝突解決機制；探索更強健的決策模型，以降低對單一模型品質的依賴；將安全政策從靜態規則擴展為可學習的動態政策，使其能適應不同應用場景；針對「人類存在落差」進行深入研究，理解模型在有人類在場時過度謹慎的原因並提出解法；以及將 LEASH 與傳統機器人安全方法（如控制屏障函數）結合，形成兼顧語意安全與物理安全的混合防護架構。

### 實作前置條件

**資料需求**
- 任務場景的視覺資料：需準備涵蓋五類風險（任務層級拒絕 T、計畫修復 P、執行時危險 E、注入 I、序列記憶 S）的代表性影像與影片，作為安全政策（safety policy）的參考案例。

- 不可逆操作清單：盤點系統中所有會造成永久狀態改變的動作（例如夾爪釋放、液體傾倒、開關切換），用於配置提交閘門。

**運算資源**
- 基礎模型 API 存取權限：GPT-6 Astra、Claude Opus 5.5、Gemini 4 Argon、Grok 4.7 等規劃器模型，以及 Jev 或 OpenAI Decisions API 作為決策模型。
- 即時推論能力：閘門需在動作迴圈內完成視覺審查，建議配備 GPU 推論伺服器或低延遲 API 連線（目標單次審查 < 500 ms）。
- 模擬環境：建議先在 RoboRisk 的 92 個模擬任務上驗證，再部署到實體機器人。

**技能前提**
- 熟悉代理架構（agentic loop）設計：理解規劃器、執行器、回饋迴路的基本概念。
- 具備視覺語言模型（VLM）prompt 工程能力：撰寫安全政策時需將文字規則與視覺上下文結合。
- 機器人作業系統（ROS）整合經驗：將 LEASH 作為節點插入現有的感測–規劃–執行管線。
- 紅隊測試（red-teaming）能力：設計注入攻擊、序列記憶混淆等情境以驗證閘門有效性。

### 實作步驟建議

1. **盤點現有代理架構並定義安全政策**
   盤點機器人目前的規劃器、執行器與感測器介面。撰寫一份共享安全政策文件，明確列出禁止行為（例如「不可將電子設備置於液體中」「不可在有人員 0.5 m 內執行高速動作」）。此政策將同時供規劃器與三個閘門使用，確保審查標準一致。

2. **整合任務閘門（Task Gate）**
   在代理迴圈的最外層加入任務閘門。每次接收新任務時，將任務文字與當前相機影像一併送入決策模型（Jev 或 OpenAI Decisions API），判斷該任務是否應直接拒絕（對應 RoboRisk 的 T 類別）。若拒絕，則回傳安全替代方案或要求人類確認。

3. **整合動作閘門（Action Gate）**
   在規劃器產出每個動作後、執行前，將動作描述與當前視覺上下文送入動作閘門審查。此閘門負責偵測計畫修復需求（P）與執行時危險（E），例如偵測到「將杯子移向電源插座」時予以攔截並要求重新規劃。

4. **整合提交閘門（Commit Gate）**
   標記系統中所有不可逆操作，在執行該操作的最終瞬間再次呼叫提交閘門進行視覺確認。此閘門特別針對注入攻擊（I）與序列記憶（S）風險：即使前兩個閘門通過，仍可能在最後一刻因環境變化或被注入指令而出現危險。

5. **在 RoboRisk 模擬環境中驗證**
   將整合後的系統跑完 92 個模擬任務，記錄危害率（HR）與任務完成率。對照論文中六個基礎模型的基準數據（HR 範圍 9.06%–76.92%），確認 LEASH 有效降低 HR 且完成率下降幅度可控。

6. **實體機器人部署與人類在場差距（Human-Presence Gap）校正**
   將系統部署到實體機器人，執行 13 個實體任務。特別注意論文中提到的「人類在場差距」：部分模型在模擬中順利執行，但面對真實人類時變得過度保守。需調整安全政策的距離與速度閾值，使其在保持安全的前提下不犧牲協作效率。

7. **建立持續監控與政策更新機制**
   部署後持續記錄閘門攔截事件、誤報率與人類接管率。當新模型釋出時，由於 LEASH 將規劃器視為黑盒且無需重新訓練，可立即套用並重新評估。

### 潛在風險與注意事項

1. **過度保守導致任務失敗**
   閘門若設定過嚴，可能使機器人在安全但合理的場景下拒絕執行（例如因偵測到遠處人影而停止所有動作）。**緩解方式**：在安全政策中明確定義距離、速度、物件類型的量化閾值，並在模擬階段統計誤報率，針對高誤報情境調整 prompt。

2. **視覺盲區導致漏判**
   閘門依賴相機影像，若相機被遮擋、光線不足或視角受限，可能錯失危險。**緩解方式**：部署多視角相機或環景相機，並在安全政策中加入「視覺信心不足時要求人類確認」的 fallback 規則。

3. **注入攻擊繞過閘門**
   攻擊者可能透過語音、標籤或螢幕文字注入惡意指令，若閘門僅審查規劃器輸出而忽略環境中的可疑文字，可能被欺騙。**緩解方式**：提交閘門應同時掃描場景中出現的可疑文字與符號，並對與原任務矛盾的指令提高警覺。

4. **決策模型本身的偏誤**
   Jev 或 OpenAI Decisions API 本身可能帶有偏誤或幻覺，對某些場景做出錯誤判斷。**緩解方式**：將決策模型的輸出與簡單的硬規則（例如力矩上限、速度上限）結合，形成雙重保險。

5. **時間與 token 開銷累積**
   雖然論文中 LEASH 的開銷「極小」，但在多步驟任務中三個閘門的累積延遲仍可能影響即時性。**緩解方式**：對低風險動作使用較輕量的審查（例如僅檢查文字規則），僅對高風險或不可逆操作呼叫完整視覺審查。

6. **人類在場差距（Human-Presence Gap）**
   模擬訓練的政策可能無法直接遷移到實體場景，面對真實人類時模型行為不一致。**緩解方式**：在實體部署階段進行專門的人機協作測試，並根據實體數據微調安全政策中的距離與互動規則。

### 與其他技術的整合建議

1. **與傳統機器人安全機制互補**
   LEASH 不應取代傳統的安全機制，而應與其形成互補層。傳統的控制屏障函數（Control Barrier Functions, CBF）負責低階的即時避障與速度限制，LEASH 則在高階處理語意危險（例如「不要把這個放進水裡」）。建議將 LEASH 部署在任務規劃層，將 CBF 保留在馬達控制層，兩者透過 ROS 訊息傳遞狀態。

2. **與現有代理框架整合**
   LEASH 設計為模型無關（model-agnostic）且將規劃器視為黑盒，可輕鬆整合進 LangChain、AutoGen、CrewAI 等代理框架，或自建的 ROS 代理節點。只需在規劃器與執行器之間插入三個閘門節點，並將相機影像與任務文字作為輸入。

3. **與 VLA 模型結合**
   對於使用視覺-語言-動作模型（如 RT-2、OpenVLA）的系統，LEASH 的動作閘門可在 VLA 輸出的動作序列上加入額外審查，特別是在 VLA 模型對新場景泛化不足時提供安全網。

4. **與世界動作模型（WAM）整合**
   WAM 會預測未來觀察與動作，LEASH 可利用 WAM 的預測結果提前評估風險，在動作執行前就攔截可能導致危險的計畫。

5. **與紅隊測試與持續評估平台整合**
   將 RoboRisk 的任務集整合進 CI/CD 流程，每次規劃器模型更新後自動執行基準測試，確保 LEASH 仍能有效降低危害率。

6. **與人類監督系統整合**
   當閘門判定為高風險或不確定時，應將決策權交還人類操作員。建議整合 Slack、Teams 或專屬監控介面，讓人類能即時接管並回饋決策，這些回饋資料可用於後續安全政策迭代。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的引言與圖 1，直觀理解「為什麼聰明的機器人也需要安全防護」。重點掌握五類風險（T、P、E、I、S）的含義，以及 LEASH 三個閘門的基本概念。實作上可從閱讀 RoboRisk 的任務範例開始，嘗試在小型模擬環境（如 PyBullet）中重現其中幾個任務，體會基礎模型在缺乏安全層時的危險行為。

**給 AI 工程師**：重點閱讀第 2 節相關工作與 LEASH 的系統架構描述，理解如何將三個閘門作為獨立模組插入現有代理迴圈。建議直接參考論文中關於決策模型（Jev / OpenAI Decisions API）的整合方式，並在程式碼層面實作一個最小可行版本：先整合任務閘門，再逐步加入動作閘門與提交閘門。特別注意評估 token 開銷與延遲對實際部署的影響。

**給研究者**：重點關注五類風險的形式化定義、RoboRisk 的任務設計方法論，以及「人類在場差距」這個新發現的現象。建議深入閱讀補充材料中的基準比較表（Supp. Table S3）與 A.4 節，理解 RoboRisk 相較於既有基準的覆蓋優勢。可考慮延伸研究方向：閘門的可證明安全性、決策模型的偏誤分析、跨文化安全政策差異等。

**給產品經理**：重點理解 LEASH 的商業價值主張：無需重新訓練規劃器、可立即套用於新模型、降低危害率同時保留任務完成率、低時間與 token 開銷。建議將 RoboRisk 的五類風險對應到自家產品的潛在失效場景，盤點哪些場景可立即受益於 LEASH 整合。特別注意「人類在場差距」對家用與協作機器人產品的 UX 影響，避免因過度保守而損害使用者體驗。
