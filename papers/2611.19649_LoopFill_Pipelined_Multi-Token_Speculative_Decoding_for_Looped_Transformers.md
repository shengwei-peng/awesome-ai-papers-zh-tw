本文提出無需訓練的LoopFill，結合後綴樹多令牌草稿與淺層迴圈預測於統一草稿樹。
LoopFill在七項基準對Ouro-2.6B達5.85倍、Huginn-3.5B達5.13倍加速。

## 深度分析

#### 方法論解析

**1. 問題背景與核心動機**

LoopFill 針對的是迴圈Transformer（Looped Transformers）在自回歸解碼（Autoregressive Decoding）時的延遲瓶頸。迴圈Transformer 採用「前奏（Prelude）—權重共享區塊（Weight-Shared Block）—尾聲（Coda）」三段式架構，其中權重共享區塊 $f$ 會被重複應用 $T$ 次以精煉隱藏狀態（Hidden State）。這種設計雖然提升了參數效率（Parameter Efficiency），但每生成一個令牌（Token）都需要 $T$ 次順序通過區塊 $f$，且在小批次（Batch）下每個 pass 屬於記憶體受限（Memory-Bound）操作，導致大量計算資源閒置。

**2. 既有方法的限制**

- **LoopSpec 與 WaveFront Decoding**：利用淺層迴圈預測（Shallow-Loop Predictions）建立推測解碼（Speculative Decoding）流水線（Pipeline）。在深度 $d < T$ 時即讀取草稿令牌，下一個令牌可提前進入流水線。然而每個淺層預測僅提出一個令牌，新令牌最多每 $d$ 個迴圈步才能啟動一次，因此加速比上限為 $T/d$。被拒絕的草稿還會強制重啟，留下「氣泡（Bubbles）」浪費流水線容量。
- **LoopAhead**：引入多令牌預測（Multi-Token Prediction）並使用可訓練頭（Trainable Heads），但需要額外訓練成本。
- **SuffixDecoding**：使用後綴樹（Suffix Tree）進行無需訓練的資料驅動草稿，但無法利用模型本身的預測能力。

**3. LoopFill 的核心創新：統一草稿樹**

LoopFill 的關鍵洞見在於：淺層迴圈草稿縮短了相鄰令牌啟動之間的等待時間，而後綴樹草稿則可在不等待任何迴圈的情況下提出多個未來令牌（Future Tokens）。兩者天然互補。

具體而言，LoopFill 將兩個草稿器整合到一棵**統一草稿樹（Unified Draft Tree）**中：
- **後綴草稿（Suffix Drafts）**：從後綴樹中檢索多令牌延續，無需模型計算。
- **淺層迴圈草稿（Shallow-Loop Drafts）**：從模型自身的淺層預測取得草稿令牌。

兩個草稿器附加候選到同一棵樹，因此後綴延續可以緊接淺層草稿之後，淺層草稿之後也可以再進行後綴查找，兩者共同提出的令牌共享同一節點。

**4. 草稿樹的批次計算與剪枝**

每個草稿節點在每個迴圈步佔用批次處理（Batched Pass）中的一行，因此被丟棄的草稿會消耗其他請求的計算資源。為此 LoopFill 採用以下策略：
- **路徑評分（Path Scoring）**：每個節點的分數為其路徑上淺層預測機率與後綴頻率的乘積。
- **Top-N 計算**：每個迴圈步僅計算分數最高的 $N$ 個節點。
- **剪枝（Pruning）**：被後續淺層預測排除的分支會被剪除。

**5. 驗證機制**

當根節點完成 $T$ 個迴圈後，匹配的子樹連同其已完成的迴圈被保留。草稿僅決定哪些位置可以提前啟動，永遠不決定發射哪個令牌，因此 LoopFill 完整保留了自回歸解碼的輸出分佈（Output Distribution）。

**6. 草稿預算的取捨**

每個請求的最佳草稿預算取決於硬體與工作負載。以 Huginn-3.5B 為例，將草稿節點預算從 $N=16$ 提升至 $N=64$ 可使單請求（B=1）解碼速度提升 19.5%，但端到端吞吐量在 B=16 時下降 43%。這揭示了延遲與吞吐量之間的權衡。

#### 實驗數據解讀

**1. 迴圈命中率分析（Figure 1a）**

在 Ouro-2.6B 上（$T=4$）：
- 單迴圈命中（Single-Loop Hit）率：88.83%
- 加上第二迴圈後的累計命中率：95.63%
- 加上第三迴圈後的累計命中率：98.20%

這顯示迴圈Transformer 確實具有在不同深度都能準確預測的歸納偏置（Inductive Bias），且大部分情況下淺層預測已足夠準確。第二與第三迴圈帶來的額外命中（Additional Hit）分別為 7.89% 與 2.23%，呈現邊際遞減趨勢。

**2. 正確草稿長度分析（Figure 1b）**

在 Ouro-2.6B 上：
- 純後綴草稿的平均正確草稿長度（Correct Draft Length）：1.34
- 加入淺層迴圈草稿後（+Shallow）：1.73
- 再加上淺層草稿後的後綴重新查詢（+Requery）：2.28

這組數據清楚展示了雙草稿器組合的累積效益：後綴草稿提供基礎長度，淺層草稿填補後綴無法匹配的位置，而重新查詢（Requery）則在淺層預測之後再次利用後綴樹，產生最長的正確草稿路徑。

**3. 主要加速比結果**

在七個基準測試（Benchmark）上的平均加速比（Speedup）：
- **Ouro-2.6B**：5.85×（相對於貪婪自回歸解碼（Greedy Autoregressive Decoding））
- **Huginn-3.5B**：5.13×

相對於最強基線 LoopAhead 的提升：
- Ouro-2.6B：40%
- Huginn-3.5B：25%

**4. 端到端吞吐量**

LoopFill 達到自回歸解碼 2.50–2.81× 的端到端吞吐量，顯示其在批次場景下同樣有效。

**5. 草稿預算的影響（Figure 5）**

在 Huginn-3.5B 上：
- $N=16$ → $N=64$：單請求速度提升 19.5%，但 B=16 吞吐量下降 43%
- 這說明較大的草稿預算有利於延遲敏感場景，但會降低吞吐量

**6. 結果的實務意涵**

- 5.85× 的加速比意味著在相同硬體下可服務約 6 倍的使用者。
- 訓練免費的特性使 LoopFill 可直接部署到現有迴圈Transformer，無需重新訓練。
- 加速比隨模型規模的變化（Ouro-2.6B 優於 Huginn-3.5B）暗示模型架構特性會影響草稿品質。

#### 與現有研究的比較

**1. 方法分類定位（Table 1）**

LoopFill 在四個維度上獨特：
| 維度 | LoopFill 特性 |
|------|---------------|
| 資料驅動（Data-driven） | ✓ 使用後綴樹 |
| 模型驅動（Model-driven） | ✓ 使用淺層迴圈預測 |
| 多令牌（Multi-token） | ✓ |
| 無需訓練（Training-free） | ✓ |

這是唯一同時滿足四個條件的方法。SuffixDecoding 缺乏模型驅動；EAGLE-3 結合了兩者但需要訓練；LoopSpec/WaveFront 缺乏資料驅動；LoopAhead 與 DFlash 雖支援多令牌但需要訓練。

**2. 相對於 LoopSpec/WaveFront 的改進**

- LoopSpec 僅沿遞迴深度（Recurrent Depth）方向草稿，每個淺層預測僅一個令牌。
- LoopFill 透過後綴樹沿序列維度（Sequence Dimension）同時展開多個未來令牌，填補了 LoopSpec 的「氣泡」。
- 加速比上限從 $T/d$ 提升至更高水準。

**3. 相對於 LoopAhead 的改進**

- LoopAhead 使用可訓練頭實現多令牌預測，需要額外訓練成本與資料。
- LoopFill 以訓練免費的後綴樹達到甚至超越的效果，在 Ouro-2.6B 上領先 40%。
- 這證明了在迴圈Transformer 場景下，資料驅動的草稿器已足夠強大，無需引入額外模型。

**4. 相對於 SuffixDecoding 的改進**

- SuffixDecoding 僅使用後綴樹，無法利用模型本身的預測能力。
- LoopFill 結合淺層迴圈預測，在後綴無法匹配的位置由模型填補，顯著提升正確草稿長度（從 1.34 提升至 2.28）。

**5. 限制與不足**

- **後綴樹的依賴**：後綴樹的品質取決於提示（Prompt）與先前輸出的內容。對於高度原創性或低重複性的生成任務，後綴草稿的效益可能下降。
- **批次大小的權衡**：在較大批次下，草稿預算 $N$ 的增加會顯著降低吞吐量，限制了其在高吞吐量服務場景的應用。
- **僅適用於迴圈Transformer**：方法專為迴圈架構設計，無法直接應用於標準 Transformer。
- **草稿預算需調校**：最佳 $N$ 值依硬體與工作負載而異，缺乏自適應機制。

實作一個輕量級後綴樹資料結構（可參考 SuffixDecoding 的開源實作）。在每個請求開始時，將 prompt token 序列插入樹中；解碼過程中持續將已驗證的 token 加入樹中。建議設定最大深度（例如 8–16 個 token）以控制記憶體。

**步驟 3：設定草稿深度 d 與節點預算 N**
- 草稿深度 d：通常設為 T/2 左右。論文顯示 Ouro-2.6B（T=4）在 d=1 時單迴圈命中率 88.8%，d=2 時 95.6%。建議從 d=1 開始實驗，逐步增加。
- 節點預算 N：根據部署場景調整。低延遲單請求場景建議 N=32~64；高吞吐量批次場景建議 N=8~16。論文顯示 Huginn-3.5B 在 B=1 時 N=16→64 提升 19.5% 速度，但 B=16 時吞吐量下降 43%。

**步驟 4：實作雙草稿器草稿樹**
- 為每個請求維護一個草稿樹，根節點為當前已驗證的序列。
- 淺層迴圈草稿：在每個迴圈步驟 t，將當前批次的每個節點通過共享區塊一次，讀取輸出頭取得 top-k 候選。
- 後綴樹草稿：對每個節點查詢後綴樹，取得多 token 延續路徑。
- 路徑評分：以「淺層預測機率 × 後綴頻率」作為節點分數，僅保留 top-N 節點。
- 剪枝規則：當淺層預測在某節點產生高機率替代時，剪除被排除的子樹。

**步驟 5：實作全深度驗證**
當根節點完成 T 個迴圈後，使用 pT(·|x) 對草稿樹進行驗證。從最長的草稿路徑開始比對，接受連續匹配的 token；遇到第一個不匹配時，從該位置的替換 token 重新開始。

**步驟 6：整合到推理框架**
- 若使用 vLLM：透過其 speculative decoding 擴展介面掛載 LoopFill 邏輯。
- 若使用自建框架：將 LoopFill 包裝為一個 `SpeculativeDecoder` 類別，與現有的 KV 快取管理整合。
- 確保草稿樹的批次計算與主迴圈共用同一個 CUDA stream，以避免額外的 kernel 啟動開銷。

**步驟 7：基準測試與調校**
在七個標準基準（論文使用 MT-Bench、GSM8K、HellaSwag 等）上測量加速比。針對不同硬體與批次大小，繪製 N 與 d 的敏感度曲線，找出最佳設定。

### 潛在風險與注意事項

**風險 1：節點預算 N 設定不當**
- **現象**：N 過大時，單請求延遲降低但批次吞吐量下降；N 過小時，草稿樹過早剪枝，命中率降低。
- **緩解**：根據部署場景建立 N 的調校表；實作動態 N 機制，根據當前 GPU 利用率自動調整。

**風險 2：後綴樹記憶體膨脹**
- **現象**：長序列生成時，後綴樹節點數可能達數十萬，佔用大量 VRAM。
- **緩解**：實作滑動視窗（只保留最近 N 個 token 的後綴）；或使用 LRU 淘汰策略；對低頻節點進行合併。

**風險 3：草稿被拒絕導致的重啟成本**
- **現象**：當所有草稿候選都被拒絕時，需從替換 token 重新開始整個迴圈，造成 pipeline bubble。
- **緩解**：增加草稿多樣性（提高 top-k）；在淺層預測信心低時，提前觸發 fallback 機制。

**風險 4：模型架構不相容**
- **現象**：若模型未在訓練時支援「不同迴圈深度皆可預測」，淺層命中率可能低於 50%，導致加速比不升反降。
- **緩解**：實作前先測量單迴圈命中率；若低於 70%，考慮放棄淺層草稿，僅使用後綴樹草稿。

**風險 5：硬體差異導致的效能波動**
- **現象**：在 A100 上表現良好的 N 值，在 H100 或消費級 GPU（如 RTX 4090）上可能完全相反。
- **緩解**：為每種目標硬體建立獨立的調校設定；使用自動基準測試工具（如論文 Figure 5 的方法）找出最佳 N。

**風險 6：分佈保留性的嚴格驗證**
- **現象**：若實作錯誤（例如驗證時未使用完整 softmax），可能改變輸出分佈，破壞推測解碼的理論保證。
- **緩解**：實作單元測試，驗證在固定 seed 下，LoopFill 與貪婪自回歸解碼的輸出完全一致。

### 與其他技術的整合建議

**與 vLLM / TGI 整合**
vLLM 0.4+ 已支援自訂 speculative decoding 草稿器。建議將 LoopFill 實作為一個 `SpeculativeProposer` 子類別，複用 vLLM 的 KV 快取管理與批次排程器。注意 vLLM 的 continuous batching 機制可能與 LoopFill 的 pipeline 假設衝突，需調整每個請求的草稿樹生命週期。

**與 KV 快取最佳化結合**
LoopFill 的淺層草稿會在每個迴圈步驟讀取 KV 快取。建議結合 PagedAttention 或 Sliding Window Attention，將舊 token 的 KV 快取卸載到 CPU 記憶體，以釋放 VRAM 給更大的草稿樹。

**與量化技術結合**
對 Ouro-2.6B、Huginn-3.5B 等模型套用 INT8 或 INT4 量化（如 AWQ、GPTQ）後，LoopFill 的加速比通常會進一步提升，因為記憶體頻寬瓶頸更明顯。建議在量化後重新進行 N 與 d 的調校。

**與其他推測解碼方法比較**
- 若模型不是 Looped Transformer，改用 EAGLE-3、Medusa 或 Lookahead Decoding。
- 若 prompt 重複性極低（例如創意寫作），後綴樹草稿器效益有限，可考慮僅使用淺層迴圈草稿（類似 LoopSpec）。
- 若需要極低延遲且硬體受限，可考慮 DFlash（但需訓練）。

**與監控與 A/B 測試整合**
部署 LoopFill 時，建議同時保留貪婪自回歸解碼作為 fallback。透過 feature flag 控制，逐步放量並監控加速比、token 接受率、p99 延遲等指標。

**給 AI 工程師**：重點閱讀第 2 節 Preliminaries 與第 3 節（假設存在的方法章節），特別關注草稿樹的批次計算邏輯、節點預算 N 的取捨、以及與 vLLM 的整合介面。建議直接閱讀論文附錄的偽程式碼，並嘗試在 Ouro-2.6B 上重現 Figure 5 的 N 敏感度實驗。

**給研究者**：重點關注第 4 節以後的理論分析（若有），特別是「為什麼雙草稿器的組合優於單一草稿器」的形式化證明，以及「path-score pruning 為何不會破壞分佈保留性」的論證。Figure 1(b) 的實驗結果（從 1.34 → 1.73 → 2.28 tokens）是值得延伸研究的起點，例如探討是否可引入第三種草稿器（如 n-gram 模型）進一步提升。

**給產品經理**：只需閱讀 Abstract 與 Introduction 的前半段，理解三個關鍵數字：5.85×（Ouro-2.6B 加速比）、5.13×（Huginn-3.5B 加速比）、40% / 25%（相對於 LoopAhead 的提升）。重點關注 Figure 5 的硬體調校結論：在 B=1 時加大 N，在 B=16 時縮小 N，這對部署成本估算有直接影響。LoopFill 的「訓練-free」特性意味著可直接套用既有模型，無需額外訓練成本，是商業部署的關鍵優勢。
