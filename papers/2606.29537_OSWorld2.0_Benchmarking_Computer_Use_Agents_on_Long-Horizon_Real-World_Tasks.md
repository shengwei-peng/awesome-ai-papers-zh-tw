## 摘要翻譯

現有的電腦使用基準測試未能捕捉真實世界電腦使用的真實性、複雜度與長程（Long-Horizon）需求，限制其揭示前沿智慧體（Frontier Agents）侷限的能力。我們提出 OSWorld 2.0，一個包含 108 個長程（Long-Horizon）電腦使用工作流程（Workflows）的基準測試，涵蓋日常與專業任務（Everyday and Professional Tasks），旨在捕捉複雜且具挑戰性的真實世界現象。每項任務皆代表真實的端對端工作流程（End-to-End Workflow），人類使用者完成任務的中位數時間約為 1.6 小時，而 Claude Opus 4.7 在最大化思考（Maximum Thinking）模式下平均需要 318 次工具呼叫（Tool Calls），相較於 OSWorld 1.0 的約 30 次。OSWorld 2.0 聚焦於挑戰現象（Challenge Phenomena），這些現象在真實工作流程（Authentic Workflows）中常見，但在先前基準測試中代表性不足，涵蓋互動設計挑戰（Interaction-Design Challenges）（如串流互動（Streaming Interaction）與動態環境（Dynamic Environments）），以及智慧體模式挑戰（Agent-Pattern Challenges）（如跨來源推理（Cross-Source Reasoning）、隱含狀態推論（Implicit-State Inference）與視覺空間精確度（Visual-Spatial Precision））。任務以真實輸入產物（Authentic Input Artifacts）為基礎，並與真實的具狀態使用者設定檔（Stateful User Profile）資料交叉比對，另包含獨立的安全報告（Safety Reports）以稽核安全敏感執行（Safety-Sensitive Execution）。在我們主要採用的 500 步二元完成度指標（Binary-Completion Metric）下，使用最大化思考（Maximum Thinking）與批次工具呼叫（Batched Tool Calls）的 Claude Opus 4.8 表現最佳，但僅完成 20.6% 的任務，部分分數（Partial Score）為 54.8%；GPT-5.5 的 Token 效率高（Token-Efficient）得多，卻僅停滯於約 13%。這些結果顯示，目前的智慧體距離專業級的電腦使用仍有很大差距：它們並非在基礎的 GUI 控制（GUI Control）或撰寫程式碼上受挫，而是忽略限制條件，錯過任務進行中出現的資訊，寧可猜測也不詢問使用者，並且跳過驗證，在任務仰賴它們必須復原的隱藏狀態（Hidden State）時最為掙扎。

## 深度分析

#### 方法論解析

OSWorld 2.0 的方法論圍繞三項核心原則展開：Authentic Workflows（真實工作流程）、Long-Horizon Structure（長程結構），以及 Diverse Challenge Phenomena（多樣挑戰現象）。任務並非將多個獨立子任務串接，而是建構具備真實資訊依賴的 End-to-End Workflow（端對端工作流程），橫跨多個 Desktop Applications（桌面應用程式）與網頁服務。為確保真實性，研究團隊透過 Team Brainstorming and Expert-Style Annotation（團隊腦力激盪與專家風格標註）收集 Everyday and Professional Tasks（日常與專業任務），佔最終 108 項任務的 90%，並輔以 Semi-Structured Interviews（半結構化專家訪談）與問卷調查。

在環境建置上，OSWorld 2.0 自架 31 個 Task-Facing Web Services（面向任務的網路服務），涵蓋電子郵件、銀行與團隊聊天等系統，並確保這些服務具備 Scoreable States（可評分狀態）。每項任務都植基於 Stateful User Profile（具狀態使用者設定檔），並在執行過程中注入 Mid-Task Messages（任務中期訊息）以模擬 Dynamic Environments（動態環境）。同時，系統設置 Simulated User（模擬使用者）具備 Bounded Knowledge（有限知識），用於測試 agent 在資訊不足時的應對能力。

評估方法採用 Final-State Evaluation（最終狀態評估），每項任務平均設有 27.25 個 Fine-Grained Checkpoints（細粒度檢查點），並優先採用 Functional Checks（功能性檢查）而非 Model-Based Judgment（基於模型的判斷）。為避免 Reward Hacking（獎勵破解）與 False Negatives（偽陰性），研究團隊執行多層品質查核，包括 Generated Unit Tests（生成單元測試）、Human Re-Solving（人工重新求解），以及 Frontier-Agent Rollouts（前沿智慧體展開）。此外，針對 Safety-Sensitive Execution（安全敏感執行），每項任務皆附帶獨立的 Safety Reports（安全報告）。

挑戰現象的設計涵蓋 Interaction-Design Challenges（互動設計挑戰）——如 Streaming Interaction（串流互動）——以及 Agent-Pattern Challenges（智慧體模式挑戰）——如 Cross-Source Reasoning（跨來源推理）、Implicit-State Inference（隱含狀態推論）與 Visual-Spatial Precision（視覺空間精確度）。這些現象共同檢驗由 Vision-Language Models（視覺語言模型）驅動的 Computer-Use Agents（電腦使用智慧體）在真實長程操作中的結構性能力。

#### 實驗數據解讀

實驗採用 Cost-Aware Evaluations（成本感知評估），在 Step Budgets（步數預算）150、300、500 的設定下測試多款 Frontier Agents（前沿智慧體）。結果顯示，Claude Opus 4.8 搭配 Maximum Thinking（最大化思考）與 Batched Tool Calls（批次工具呼叫）表現最佳，但在 500 steps 的 Binary-Completion Metric（二元完成度指標）下僅達 20.6%，Partial Score（部分分數）為 54.8%。作為對照，Claude Opus 4.7 在執行這些任務時平均需發出 318 次 Tool Calls（工具呼叫），遠高於 OSWorld 1.0 的約 30 次，凸顯任務複雜度的躍升。相較之下，GPT-5.5 的完成率約 13%，卻展現極佳的 Token-Efficient（Token 效率高）特性，僅消耗 Opus 約五分之一的 token 成本。

數據揭示了一項關鍵現象：Completion 對任務長度極為脆弱。即使 Partial Score 維持在一定水準，最長工作流程的 Binary Completion 仍趨近於零。這表示 agents 並非敗於 Basic GUI Control（GUI 控制）或程式撰寫，而是無法在長時間軸中維持一致的 Task-Level Model。具體而言，agents 經常遺失 Hidden State（隱藏狀態）相關的約束、忽略執行中期送達的資訊、傾向猜測而非詢問使用者，並且跳過必要的 Verification（驗證）。研究更發現，agents 僅將不到 7% 的預算用於 Error Detection and Repair（錯誤偵測與修復）。

進一步分析顯示，弱點集中在需要恢復與維護 Hidden State 的現象：Implicit-State Inference（隱含狀態推論）、Multi-Item State Tracking（多項目狀態追蹤）、Conflict Disambiguation（衝突消歧），以及 Dynamic Environments（動態環境）。這些結果指出，當前 agents 的瓶頸不在單步執行，而在於跨步的狀態推理與工作記憶。

#### 與現有研究的比較

與 OSWorld 1.0 相比，OSWorld 2.0 的任務中位數長度達 1.6 小時的 Active Operation（實際操作），平均需要 318 個 Tool Calls（工具呼叫），相較於 1.0 的約 30 次，規模提升約 48 倍。1.0 的任務多侷限於單一或兩個應用程式內的短程動作，而 2.0 則要求真正的跨應用 End-to-End Workflow（端對端工作流程）。

與 OSWorld-Verified 的高分形成強烈對比：Claude Opus 4.8 在後者達到 83.5%，暗示 Desktop Computer Use 已接近解決；然而 OSWorld 2.0 僅 20.6% 的完成率證明，現有 Benchmarks（基準測試）因任務過於 Short and Narrow（短且狹隘），嚴重高估了真實能力。相較於 Claude Cowork、OpenAI Codex 與 OpenClaw 等現有 Computer-Use Agents（電腦使用智慧體）系統在短程示範中的亮眼表現，OSWorld 2.0 凸顯了真實長程部署的結構性落差。

OSWorld 2.0 的改進包括：引入 Authentic Input Artifacts（真實輸入產物）與 Stateful User Profile（具狀態使用者設定檔），使任務資訊分散於檔案、應用程式與網路服務中；透過 Functional Checks（功能性檢查）取代 Model-Based Judgment（基於模型的判斷），降低主觀評分風險；並針對 Safety-Sensitive Execution（安全敏感執行）提供獨立審計。

然而，其局限性亦不容忽視：任務總數僅 108，雖經嚴謹的 Trained-Annotator Research（訓練有素標註員研究）與 Expert Interviews（專家訪談）確保品質，但覆蓋領域仍有限；建構流程高度依賴人工，成本高昂；且 Self-Hosted Web Services 與真實企業級系統的複雜度仍有差距。

#### 可重現性評估

作者承諾釋出完整的 Environment、108 項 Tasks、31 個 Self-Hosted Task-Facing Web Services，以及 Agent Rollout Trajectories（智慧體展開軌跡）。這些釋出大幅提升了 Benchmark 的透明度與可重現性，使後續研究能在相同基礎上進行比較與改進。

不過，可重現性仍面臨若干挑戰。首先，Frontier Agents（前沿智慧體）如 Claude Opus 4.8 與 GPT-5.5 係透過商業 API 呼叫，並無公開的 Model Weights（模型權重），因此隨著模型版本迭代，絕對數值可能難以完全復現。其次，Input Artifacts（輸入產物）雖基於真實材料，但經過改編與去識別化，可能與原始專業情境存在細微差異。最後，部分任務依賴特定版本的 Desktop Applications（桌面應用程式）與網頁介面，長期的環境維護與相依性管理將是社群必須承接的責任。

#### 未來研究方向

1. **長程狀態維護與階層式規劃**：當前 agents 在 Long-Horizon（長程）任務中無法持續追蹤 Hidden State（隱藏狀態）。未來研究應發展具備外部記憶體與階層式規劃的架構，強化 Implicit-State Inference（隱含狀態推論）與 Multi-Item State Tracking（多項目狀態追蹤）能力，使 agent 能在數百個 Tool Calls（工具呼叫）後仍維持任務層級的目標一致性。

2. **動態環境適應與串流互動**：真實世界充斥 Streaming Interaction（串流互動）與 Dynamic Environments（動態環境）。未來需開發能即時感知 Mid-Task Messages（任務中期訊息）並動態調整計畫的機制，而非僅依賴靜態提示。

3. **自我監測與錯誤修復**：目前 agents 僅用極低比例預算進行自我修正。建立主動的 Self-Monitoring 機制，在錯誤傳播前偵測並修復，是提升 Binary-Completion Metric（二元完成度指標）的關鍵，特別是在 Cross-Source Reasoning（跨來源推理）與 Visual-Spatial Precision（視覺空間精確度）要求高的步驟。

4. **人機協商與有限知識利用**：Agents 傾向猜測而非詢問。研究應聚焦於讓 agent 認知到 Simulated User（模擬使用者）的 Bounded Knowledge（有限知識），並在資訊不足時主動發起澄清對話，而非盲目推進。

5. **成本效益優化**：GPT-5.5 展現了 Token-Efficient（Token 效率高）的優勢，但能力遇到瓶頸。未來可探索更精緻的 Action Space 設計、Batched Tool Calls（批次工具呼叫）策略，或蒸餾技術，以在有限 Step Budgets（步數預算）下同時提升完成率與效率。

6. **基準測試規模化**：OSWorld 2.0 僅 108 項任務。結合自動化工作流程探勘與半自動環境建置，降低對 Trained-Annotator Research（訓練有素標註員研究）的依賴，將是擴展 Benchmark 覆蓋率的重要方向。

7. **安全執行與對齊**：隨著 Computer-Use Agents（電腦使用智慧體）進入專業場域，Safety-Sensitive Execution（安全敏感執行）的審計機制需與能力同步演進，發展自動化的 Safety Reports（安全報告）生成與風險緩解策略。

## 論文問答

**Q1：OSWorld 2.0 旨在解決什麼核心問題？**
A：現有的電腦使用基準測試無法充分捕捉真實世界電腦使用中的真實性、複雜性與長程需求，導致其難以揭示前沿智慧體的真正限制與結構性弱點。這些基準大多由短而狹隘的任務組成，鮮少橫跨多個應用程式，並且僅獎勵完成自包含的動作，而非持續執行長時間且相互連結的端對端工作流程。因此，OSWorld 2.0 的出現是為了彌補這個重大缺口，提供一個同時具備長程特性、真實操作環境，並且富含真實工作流程複雜挑戰現象的評估平台，以準確衡量智慧體在專業級電腦使用上的實際能力。

**Q2：為何現有的電腦使用基準測試無法揭示前沿智慧體的真實能力？**
A：現有基準的任務通常過於短促且範圍狹窄，很少橫跨超過一兩個應用程式，其設計著重於完成獨立動作而非持續執行長程的端對端工作流程。舉例來說，Claude Opus 4.8 在 OSWorld-Verified 上可達到 83.5% 的準確率，但這些任務長度僅約為 OSWorld 2.0 的四十八分之一，無法反映真實部署所需的長時間連貫作業與跨工具協調。這種設計使得高準確率過度誇大了實際進展，並掩蓋了智慧體在處理跨應用程式、多步驟且相互依賴的真實工作時頻繁失敗的事實。

**Q3：為何對長程真實世界電腦使用進行基準測試如此重要？**
A：真實使用者無論是在日常或專業場景中，其電腦使用往往涉及耗時數小時、橫跨多個桌面應用程式與網路服務的端對端工作流程，而非孤立的操作或單一工具的使用。如果缺乏能夠反映這種複雜度與長程結構的評估標準，研究社群與產業將無法準確判斷智慧體是否已具備實際部署的專業水準。OSWorld 2.0 的重要性在於它揭示了當前智慧體在真實長程任務中的結構性弱點，例如遺失隱藏狀態與跳過驗證，從而引導未來研究朝向真正實用且可靠的電腦使用智慧體發展。

**Q4：OSWorld 2.0 的核心方法論是什麼？**
A：OSWorld 2.0 建構了一個包含 108 個長程電腦使用工作流程的基準測試，每個任務都是一個給定高層級使用者目標、真實輸入產物、具狀態電腦環境以及可評分最終狀態的自包含端對端工作流程。這些任務源自於專家訪談與訓練有素標註員研究所挖掘的真實專業情境，其輸入產物皆取自真實材料而非人工合成，以確保任務的真實性。評估方式採用細粒度檢查點對最終狀態進行評分，平均每個任務有 27.25 個檢查點，並優先採用功能性檢查而非基於模型的判斷，以確保評估的客觀性與可靠性。

**Q5：OSWorld 2.0 相較於先前基準測試的關鍵創新為何？**
A：其關鍵創新在於同時涵蓋真實工作流程、長程結構與多樣化的挑戰現象，包括串流互動、動態環境、跨來源推理、隱含狀態推論與視覺空間精確度等十種現象。為了實現這些挑戰，OSWorld 2.0 自行託管了 31 個面向任務的網路服務，並為每個任務設定具狀態使用者設定檔，同時在任務中期注入訊息使環境動態變化。此外，它還引入了具有有限知識的模擬使用者，並針對安全敏感執行生成獨立的安全報告，這些設計在過去的基準中均未被充分代表。

**Q6：在建構 OSWorld 2.0 任務時，有哪些重要的設計選擇？**
A：每個保留的任務都必須滿足兩項嚴格的設計準則：首先是長程特性，其難度必須來自於跨越多個應用程式的相互依賴工作流程結構，而非重複操作或無關子任務的串接；其次是真實性，任務相關資訊必須扎根於真實輸入產物與工作空間狀態，且常分散於檔案、應用程式與網路服務中，而非完全寫入提示詞。為了確保品質，建構流程採用管線式設計，包含候選工作流程收集、可重現環境實例化、最終狀態評估定義，以及多層品質保證，包括單元測試、人工重新求解與前沿智慧體展開，以審查獎勵破解與偽陰性等問題。

**Q7：OSWorld 2.0 評估了哪些智慧體與設定？**
A：研究團隊進行了成本感知評估，測試對象包含 Claude Opus 4.8 與 4.7、GPT-5.5 以及領先的開源模型，並分別在 150、300 與 500 的步數預算下進行測試。其中表現最佳的配置是 Claude Opus 4.8 搭配最大化思考與批次工具呼叫，而 GPT-5.5 則展現出最高的 Token 效率，僅用不到五分之一的 Token 預算即達到相近的表現區間。這種多模型、多預算的比較設計，讓研究者能夠同時檢視完成率與成本效益之間的權衡關係。

**Q8：實驗的主要結果為何？**
A：在主要的二元完成度指標下，即使是最強的 Claude Opus 4.8 在 500 步預算內也僅完成 20.6% 的任務，部分分數為 54.8%；而 GPT-5.5 雖然 Token 效率高，完成率卻僅約 13%，顯示更高的完成率需要急劇上升的 Token 成本。此外，完成率在面對最長的工作流程時會趨近於零，即使部分分數仍維持在較高水準，這說明單純增加步數預算並無法根本解決長程任務的脆弱性。這些結果清楚表明，當前智慧體距離專業級的電腦使用仍有極大差距，高準確率在舊基準上並不等同於真實世界的能力。

**Q9：失敗分析揭示了當前智慧體的哪些結構性弱點？**
A：失敗分析顯示，智慧體在執行局部動作與基本 GUI 控制上表現尚可，但無法在長時間範圍內維持任務層級的整體模型，導致它們遺失狀態限制條件、錯過任務中期訊息，並且在需要時選擇猜測而非詢問模擬使用者。它們幾乎不進行驗證，僅將不到 7% 的預算用於偵測與修復自身錯誤，使得失誤不斷累積並在後續步驟中放大。這些弱點集中在需要恢復與維持隱藏狀態的挑戰現象上，例如隱含狀態推論、多項目狀態追蹤、衝突消歧與動態環境，顯示問題不在於基礎操作能力，而在於長程狀態管理與自我修正機制的根本缺失。

**Q10：OSWorld 2.0 包含了哪些類型的真實世界任務？**
A：OSWorld 2.0 涵蓋了 108 個橫跨日常與專業任務的長程電腦使用工作流程，例如涉及電子郵件、銀行業務與團隊聊天等面向任務的網路服務操作。每個任務對人類使用者而言，中位數實際操作時間約為 1.6 小時，且需要跨越多個應用程式與服務進行協調與資訊整合。這些任務並非孤立的操作練習，而是需要規劃、執行與驗證完整結果的真實端對端工作流程，充分反映了現實中知識工作者所面對的複雜情境與資訊依賴結構。

**Q11：這些結果對於產品中部署電腦使用智慧體有何啟示？**
A：實驗結果顯示，當前智慧體距離能夠穩定執行專業級電腦使用仍有相當遙遠的距離，產品開發者與企業不應僅依賴短程基準的高分就認為問題已經解決。由於智慧體在長程工作流程中的完成率極為脆弱，且經常跳過驗證步驟，實際部署時必須建立強健的錯誤檢查、中間狀態確認與人機協作機制。此外，智慧體在面對隱含狀態與動態環境時的無能，意味著產品設計應避免讓智慧體獨自處理需要持續追蹤多項限制條件的高風險任務，除非有適當的監督、介入與使用者確認流程。

**Q12：OSWorld 2.0 可能對電腦使用智慧體研究領域帶來什麼影響？**
A：OSWorld 2.0 將研究焦點從短期的 GUI 控制與孤立動作，轉移到長程工作流程管理、跨來源推理與持續狀態維護等結構性挑戰。透過公開釋出環境、108 個任務、自行託管的網站以及智慧體展開軌跡，它為未來研究提供了一個可重現且真實的評估平台。這將促使學界與業界更重視智慧體在串流互動、動態環境中的行為，以及其維持任務層級記憶與自我修復的能力，從而推動真正可用於真實世界的電腦使用智慧體發展。

**Q13：OSWorld 2.0 有哪些已知的限制？**
A：儘管 OSWorld 2.0 在任務真實性與複雜度上大幅提升，但目前僅包含 108 個任務，規模相對有限，且每個任務的建構過程都極為耗時與昂貴，難以大規模擴展。由於生產級工作流程常涉及敏感資料、專有工具鏈或領域特定慣例，公開分享這些素材本身就具有挑戰性，因此任務來源仍部分依賴標註員的經驗與公開教學資料的改編。此外，為了確保可重現性與可靠評分，某些極度複雜或高度企業內部化的流程可能未被充分納入，這在一定程度上限制了基準對所有專業領域的覆蓋範圍。

**Q14：智慧體在 OSWorld 2.0 上展現了哪些具體的失敗模式？**
A：智慧體最常見的失敗模式並非基礎的 GUI 控制或編碼錯誤，而是在長程執行中無法維持任務層級的一致性，例如遺失狀態限制條件、忽略任務中期訊息所帶來的新資訊，以及在關鍵節點選擇猜測而非詢問具有有限知識的模擬使用者。它們也經常跳過完成任務所必需的驗證步驟，導致錯誤在後續步驟中不斷放大，最終使整個工作流程偏離目標。這些失敗特別集中在需要恢復隱藏狀態的挑戰現象上，包括隱含狀態推論、多項目狀態追蹤、衝突消歧與動態環境適應，顯示出當前智慧體在狀態推理與錯誤修復方面的根本缺陷。

**Q15：OSWorld 2.0 指出了哪些未來研究方向？**
A：根據研究結果，未來進展的關鍵不在於單純增加步數預算或擴大模型規模，而在於開發能夠在串流且不斷變化的介面上運作、並在長時間範圍內維持任務層級模型的智慧體。具體而言，研究社群需要設計能夠主動偵測並修復自身錯誤、在錯誤傳播前即時介入的機制，而非僅將不到 7% 的預算用於錯誤處理。此外，提升智慧體對隱藏狀態的恢復能力、強化其在動態環境與跨來源推理中的表現，以及建立更有效的人機協作詢問策略，將是邁向專業級電腦使用智慧體的核心研究課題。

## 實務應用指南

### 適用場景

1. **跨應用程式企業流程自動化驗證**  
   當組織欲部署能同時操作試算表、網頁後台、電子郵件與即時通訊的電腦使用智慧體時，可採用 OSWorld 2.0 的長程端對端工作流程作為驗收標準，確保智慧體在 300 次以上工具呼叫的尺度下仍能維持任務級推理。

2. **高擬真行政助理的壓力測試**  
   針對需處理動態環境（如任務中期訊息、新進郵件）與隱含狀態推論（如從過往對話推斷使用者偏好）的秘書型代理程式，可利用本基準的 31 組面向任務的網路服務與具狀態使用者設定檔，測試其在真實輸入產物上的穩健度。

3. **電腦使用智慧體的安全紅隊測試**  
   對於涉及安全敏感執行（如網路銀行、團隊權限管理）的場景，可參考 OSWorld 2.0 的安全報告與單元測試稽核流程，設計獎勵破解與偽陰性檢測機制，避免智慧體繞過細粒度檢查點或誤判完成狀態。

4. **長程任務訓練資料策展與弱點分析**  
   模型開發團隊可依据本基準標註的十項挑戰現象（如跨來源推理、衝突消歧、視覺空間精確度），系統性地盤點現有訓練資料的缺口，並針對智慧體模式挑戰設計專項微調資料集。

5. **多模態前沿智慧體的能力邊界測繪**  
   在評估 Claude Opus 4.8、GPT-5.5 等模型時，可借用成本感知評估框架，比較不同步數預算與批次工具呼叫設定下的二元完成度指標與部分分數，協助決策者在能力與推論成本間取得平衡。

### 實作前置條件

**資料需求**  
需蒐集或重建真實工作流程所需的多模態輸入產物（文件、截圖、網頁結構、程式碼片段），並建立具狀態使用者設定檔（如郵件歷史、銀行餘額、行事曆事件）。這些資料必須包含跨應用程式的真實資訊依賴，而非單一提示內即可取得的合成資料。

**運算需求**  
每項任務需能執行長時間桌面虛擬化環境（如 Docker 或 VM），並託管 31 種以上面向任務的網路服務。若執行前沿智慧體展開，需準備大量 API 預算：頂尖模型在單一任務上可能產生數百次工具呼叫與對應的視覺語言模型推論 token。

**技術與人力需求**  
團隊需具備 Python 自動化測試、網頁服務模擬（含電子郵件、銀行、團隊聊天）、以及 GUI 控制框架（如 pyautogui 或底層作業系統 API）的開發能力。此外，需有熟悉目標領域的標註員或領域專家，以執行人工重新求解與評估函式設計。

---

### 實作步驟建議

**步驟一：建構具狀態且可評分的環境**  
部署自託管的網路服務與桌面作業系統，確保環境能記錄並還原使用者狀態（如未讀郵件、資料夾結構）。引入模擬使用者模組，並設定其有限知識邊界，使智慧體在必須提問時無法從環境中直接撈取答案。

**步驟二：設計長程端對端工作流程**  
從專家訪談與真實工作流程出發，挑選需橫跨多個應用程式、具備真實資訊依賴的任務。避免將多個無關子任務簡單拼接；難度應來自步驟間的相互依賴與狀態傳遞。

**步驟三：標註挑戰現象與注入動態事件**  
為每項任務標註十項挑戰現象（如隱含狀態推論、動態環境、串流互動）。在任務執行過程中注入任務中期訊息（如新郵件、聊天通知），迫使智慧體處理非靜態輸入。

**步驟四：建立細粒度評估管線**  
以功能性檢查為主、基於模型的判斷為輔，設計平均每項任務約 27 個細粒度檢查點。同時建立二元完成度指標（嚴格驗收）與部分分數（進度追蹤）。

**步驟五：多層稽核與安全把關**  
透過單元測試、人工重新求解，以及前沿智慧體展開，交叉驗證評估函式是否存在獎勵破解或偽陰性。針對安全敏感執行步驟產生獨立安全報告。

**步驟六：迭代優化智慧體架構**  
在 150、300、500 步數預算下進行成本感知評估。優先導入批次工具呼叫與最大化思考模式以提升完成率；同時增設錯誤偵測與修復迴路，因研究顯示現有智慧體花費不到 7% 預算在自我修正上。

### 潛在風險與注意事項

- **長程錯誤傳播**  
  在 300 步以上的工作流程中，早期小錯誤（如截圖解析偏差、檔案路徑錯誤）會被指數放大。建議在關鍵檢查點設立「閘道驗證」，強制智慧體確認隱藏狀態與環境變數後再繼續。

- **獎勵破解與評估模糊地帶**  
  強大模型可能利用細粒度檢查點的漏洞取得部分分數，卻未完成真正的工作流程。務必以人工重新求解與單元測試雙重稽核，並定期用最新 frontier agents 進行紅隊測試。

- **Token 成本與延遲爆炸**  
  Claude Opus 4.8 搭配最大化思考與批次工具呼叫雖能達到最佳完成率，但推論成本極高；GPT-5.5 雖然 Token 效率高，卻很快遇到能力高原。實際部署前應先以部分分數與業務價值對照，決定可接受的步數預算與模型組合。

- **動態環境的不可復現性**  
  任務中期訊息與外部網路服務狀態可能導致評估結果抖動。建議將所有外部服務自託管並版本化，確保每次展開的初始狀態與事件注入時機一致。

- **過度擬合短程基準的錯覺**  
  若團隊過往只在 OSWorld 1.0 等短程任務上驗證，可能誤以為 GUI 控制已大致解決。應直接以長程任務作為主要驗收標準，因為現有模型在基礎控制上表現尚可，卻在維持任務級模型時全面潰敗。

- **使用者意圖猜測而非詢問**  
  當遇到衝突消歧或資訊不足時，智慧體傾向猜測而非向模擬使用者提問。應在系統提示中明確鼓勵「主動澄清」行為，並將提問正確性納入評分。

### 與其他技術的整合建議

- **與 RAG 與長期記憶系統整合**  
  針對跨來源推理與隱含狀態推論，可將具狀態使用者設定檔與歷史操作日誌接入 RAG 管線，讓智慧體在長程操作中能檢索過往郵件、文件版本與對話脈絡，而非僅依賴當前畫面。

- **與串流互動/觀測性平台整合**  
  動態環境與任務中期訊息需要即時事件處理。建議將智慧體接入具備串流互動能力的觀測性框架（如即時截圖 diff、WebSocket 事件推送），使其能感知連續變化的介面狀態，而非僅在離散步驟取樣。

- **與 CI/CD 及自動化測試管線整合**  
  將 OSWorld 2.0 的評估環境封裝為容器化服務，納入持續整合流程。每次模型或提示更新後，自動執行成本感知評估，追蹤二元完成度指標與部分分數的迴歸狀況。

- **與人在迴路（Human-in-the-Loop）機制整合**  
  對於涉及安全敏感執行或高風險衝突消歧的步驟，不要完全仰賴智慧體自動判斷。可在關鍵檢查點觸發人工審核，或賦予智慧體主動呼叫「請求使用者確認」的工具，降低錯誤代價。

- **與多模態資料標註工具整合**  
  在任務建構階段，利用視覺語言模型輔助標註截圖中的 GUI 元素與挑戰現象，再由人工進行品質確認，可加速真實輸入產物的準備與細粒度檢查點的設計。

### 給不同背景讀者的閱讀建議

**給初學者**  
建議先聚焦於論文的摘要與失敗案例分析。不需要深入理解所有評估函式的技術細節，但應掌握一個核心概念：現今頂尖模型在短程基準上看似表現優異，一旦面對需要 1.6 小時實際操作的長程任務，完成率會驟降至 20% 左右。這能幫助你建立對「電腦使用智慧體」真實能力邊界的正確預期。

**給 AI 工程師**  
請重點研讀任務設計（§2.1）與實驗設定章節。關注批次工具呼叫、最大化思考模式與不同步數預算下的成本感知評估數據，並仔細檢視智慧體在錯誤偵測與修復上的行為分佈。這些細節直接影響你在實際系統中如何設計工具呼叫策略、規劃記憶體機制，以及決定何時該讓模型暫停並自我驗證。

**給研究人員**  
論文對長程結構與挑戰現象的分類（如隱含狀態推論、動態環境、跨來源推理）是極具價值的貢獻。建議深入分析這些現象與模型失敗模式之間的對應關係，並思考為何單純增加步數預算或模型規模無法顯著提升二元完成度指標。這裡隱含著對現有 scaling law 在長程代理任務上局限性的重要啟示。

**給產品經理**  
請將注意力放在成本與效益的權衡圖上。Claude Opus 4.8 與 GPT-5.5 在 Token 效率與完成率之間呈現鮮明對比：前者昂貴但尚能應付部分長程流程，後者便宜卻很快觸及能力天花板。這些數據是你與客戶溝通「目前自動化能做到什麼程度」、設定合理服務水平協議（SLA），以及決定是否要在高風險步驟保留人工介入的關鍵依據。
