## 摘要翻譯

商業智慧（Business Intelligence, BI）是企業決策的基石，企業使用者廣泛透過 Power BI、Tableau 等軟體使用 BI。在傳統 BI 流程中，使用者必須先準備資料，包括（1）找出相關資料表、（2）執行資料轉換（data transformation），以及（3）建立連結關係（join relationship），才能（4）回答其商業問題。這些步驟往往複雜且耗時，使 BI 作業變得極具挑戰性。

鑑於大型語言模型（Large Language Models, LLMs）在處理資料方面的強大能力，本研究探討其端到端（end-to-end）回答 BI 問題的能力，讓使用者無需手動執行繁瑣的資料準備步驟。為此，本研究從公開來源蒐集大量真實世界的 BI 專案，並手動從真實使用者的儀表板（dashboard）中擷取（問題、真實答案（ground-truth answers））配對。所建構的基準測試 BI-Bench，是首個系統性研究大型語言模型於端到端 BI 上能力的基準測試。

本研究發現，即使是前沿大型語言模型（frontier LLMs）在 BI-Bench 上的表現也不佳，準確率（accuracy）低於 50%。為了克服這些限制，本研究設計了一個工具增強型（tool-augmented）BI-Agent，針對結構化資料（structured data）將 BI 流程拆解為搜尋（search）、連結（join）、轉換（transform）等子任務（subtasks），並在 BI 各階段間編排（orchestrate）專門的資料管理方法（data management methods）。此外，本研究開發了一個後訓練框架（post-training framework），從真實 BI 專案合成訓練軌跡（training trajectories），使 BI-Agent 能進一步透過監督式微調（Supervised Fine-Tuning, SFT）與強化學習（Reinforcement Learning, RL）進行後訓練。以原始大型語言模型（vanilla LLMs）為基礎的 BI-Agent，準確率提升高達 40 百分點（percentage points）；經過後訓練的 BI-Agent 則可提升高達 30 百分點。本研究結果凸顯了在複雜 BI 流程中，結合工具增強式推理與領域特定後訓練的重要性，並為未來研究指出具潛力的方向。

### 核心貢獻（3～5點）
- 提出 BI-Bench：首個系統性評測 LLM 端到端 BI 能力的基準測試，資料來自真實 BI 專案與使用者儀表板。
- 揭示前沿 LLM 在端到端 BI 任務上的表現瓶頸：準確率低於 50%。
- 設計工具增強型 BI-Agent：將 BI 流程拆解為 search、join、transform 等子任務，並編排專門的資料管理方法。
- 建立後訓練框架：從真實 BI 專案合成訓練軌跡，結合 SFT 與 RL 顯著提升準確率。

### 適合對象
適合對商業智慧自動化、大型語言模型應用、資料管理與智慧代理（AI Agent）有興趣的研究者與工程師，特別是關注如何將 LLM 應用於真實企業資料分析場景、以及希望透過工具增強與後訓練提升模型在結構化資料上表現的讀者。

## 深度分析

#### 方法論解析

##### BI-Bench：真實端到端 BI 基準測試（Benchmark）的建構

本研究首先指出，現有資料分析基準測試（如 NL2SQL 領域的 Spider、BIRD 等）大多聚焦於「給定資料庫與自然語言問題後產生 SQL」這單一階段，卻未涵蓋真實商業智慧（Business Intelligence, BI）工作流程中前置的資料準備步驟。為填補此缺口，作者從公開網頁爬取大量真實 Power BI 專案檔案（.pbix），並從使用者實際建立的儀表板（Dashboard）中手動挑選視覺化元件，將其標題視為自然語言商業問題（Question, 𝑄），再透過 Power BI 內建的「Export data」功能匯出該視覺化背後的結果表，作為真實答案（Ground-truth Answer, 𝐴(𝑄)）。每個 (𝑄, 𝐴(𝑄)) 配對即構成 BI-Bench 的一筆測試案例。

此建構方式有幾項關鍵特徵：

1. **真實世界來源（Real-world provenance）**：問題與答案皆來自真實使用者建立的 BI 專案，而非人工合成的資料庫與查詢。
2. **端到端評估（End-to-end evaluation）**：模型必須自行完成 (S1) 尋找相關資料表（Search）、(S2) 資料轉換（Transform）、(S3) 建立連結關係（Join）、(S4) 回答商業問題，而非僅在最後一步產生 SQL。
3. **多雪花結構（Multi-snowflake schema）**：真實 BI 專案常見多個事實表（Fact Tables）與維度表（Dimension Tables）交錯，連結路徑複雜，遠超單一資料庫的星狀或雪花結構。
4. **以 CSV 結果表為評估標準**：透過比對模型輸出表格與匯出的真實答案表來判斷正確性，較貼近 BI 使用者真正想看到的結果。

##### BI-Agent：工具增強型（Tool-augmented）端到端 BI 代理

針對 Frontier LLMs 在 BI-Bench 上準確率（Accuracy）低於 50% 的現象，作者提出 BI-Agent，其核心是將端到端 BI 流程拆解為多個結構化資料（Structured Data）上的子任務（Subtasks），並為每個子任務編排（Orchestrate）專門的資料管理方法（Data Management Methods）。整體可視為一個多階段代理（Agent），由 LLM 負責高階規劃與決策，並在關鍵步驟呼叫外部工具執行精確操作。

根據摘要與圖表資訊，BI-Agent 至少包含以下階段：

- **Search（搜尋）**：在大量資料表中辨識與問題相關的表格與欄位。此階段可能結合語義搜尋、Schema 比對或關鍵字比對，避免模型僅靠上下文推測表名。
- **Join（連結）**：自動推導資料表之間的連結關係（Join Relationships），包括主鍵（Primary Key）/外鍵（Foreign Key）偵測、連結路徑選擇、以及多事實表情境下的連結策略。
- **Transform（轉換）**：執行資料清理、格式轉換、聚合（Aggregation）、樞紐（Pivot）、衍生欄位等操作，使原始資料適合後續分析。
- **Answer（回答）**：在最後階段產生 SQL 或其他查詢語言，並執行以得到結果表。

透過這種「LLM 規劃 + 專業工具執行」的協作模式，BI-Agent 能將 LLM 的語意理解能力與傳統資料管理系統的精確性結合，顯著降低幻覺（Hallucination）與連結錯誤的風險。

##### 後訓練框架（Post-training Framework）：SFT + RL

除了工具設計，作者進一步提出一套後訓練（Post-training）框架，從真實 BI 專案中合成訓練軌跡（Training Trajectories），用於監督式微調（Supervised Fine-Tuning, SFT）與強化學習（Reinforcement Learning, RL）。具體而言：

- **軌跡合成（Trajectory Synthesis）**：從真實 BI 專案自動產生包含「觀察（Observation）→ 動作（Action）→ 獎勵（Reward）」的完整決策序列，讓模型學習如何在 Search、Join、Transform、Answer 各階段做出正確選擇。
- **SFT 階段**：先以合成軌跡進行行為複製（Behavior Cloning），讓模型熟悉 BI 領域的推理模式與工具使用格式。
- **RL 階段**：再以最終答案是否正確作為獎勵訊號，進一步優化模型在多步決策中的探索與利用（Exploration vs. Exploitation）。

值得注意的是，經過 SFT+RL 後，僅 8B 參數的 Qwen3-8B 即可在 BI-Bench 上達到與大型 Frontier 模型相近的表現，顯示領域專屬後訓練對複雜 BI 工作流程的關鍵價值。

#### 實驗數據解讀

##### 主要結果

論文報告了以下幾項核心數據：

1. **Frontier LLMs 表現不佳**：在未使用 BI-Agent 工具的情況下，即使是 GPT-5.5、GPT-5.2、GPT-4o、o4-mini、Llama-4-Maverick、DeepSeek-V4-Pro 等 Frontier LLMs，在 BI-Bench 上的準確率（Accuracy）仍低於 50%。這顯示真實端到端 BI 任務對現有通用 LLM 而言仍具高度挑戰性。
2. **工具增強帶來顯著提升**：BI-Agent 搭配 Vanilla LLMs（未經後訓練的原始大型語言模型）後，準確率最高可提升 40 個百分點（Percentage Points）。圖 1 中可見 BI-Agent (GPT-5.2)、BI-Agent (GPT-5.5)、BI-Agent (o4-mini) 等版本均明顯優於對應的裸模型。
3. **後訓練進一步提升表現**：經過 SFT+RL 後訓練的 BI-Agent (Qwen3-8B) 可再提升約 30 個百分點，品質逼近甚至超越多個 Frontier 模型，而每次查詢成本（USD per query）卻顯著降低（最高達 50 倍）。
4. **相較於 SOTA NL2SQL 系統**：包括 Kwai-AutoSQL-32B、ktx w/ Codex、XiYanSQL-QwenCoder-32B、Infly-RL-SQL-32B 等專門的 NL2SQL 方法，在 BI-Bench 上同樣表現不足，凸顯單純文字轉 SQL 無法解決端到端 BI 的資料準備難題。

##### 成本效益分析

圖 1 的橫軸為每次查詢美元成本（USD per query），縱軸為準確率。可以觀察到：

- BI-Agent 的工具增強版本（以藍綠色箭頭標示）在準確率上大幅領先同基礎模型，且成本增加相對可控。
- 後訓練的 Qwen3-8B（紫色箭頭）位於圖表左上方，代表「高品質、低成本」的最佳區域，顯示領域專屬後訓練不僅提升品質，也具備實際部署的經濟可行性。
- 相較之下，Frontier 模型雖然品質較高，但成本昂貴；而 SOTA NL2SQL 系統則在品質與成本上都未佔優勢。

##### 統計顯著性

作者強調所有提升均具有高度統計顯著性（Statistical Significance），意味著這些改進並非來自隨機波動，而是方法本身帶來的穩定效益。對於企業應用而言，這是評估是否可採用的重要依據。

##### 結果意涵

這些數據共同說明：

- **工具增強推理（Tool-augmented Reasoning）是必要條件**：單靠 LLM 內部知識無法可靠完成複雜 BI 流程，必須結合 Search、Join、Transform 等專業工具。
- **領域專屬後訓練可彌補模型規模差距**：8B 模型經過適當後訓練後，可在特定領域挑戰數百倍參數的 Frontier 模型，這對企業私有化部署與邊緣運算（Edge Computing）具有重要意義。
- **端到端評估揭露真實瓶頸**：若僅評估最終 SQL 生成，會忽略資料表選擇、轉換與連結等關鍵錯誤來源；BI-Bench 的設計讓這些問題無所遁形。

#### 與現有研究的比較

##### 相較於傳統 BI 平台

Power BI 與 Tableau 等傳統 BI 軟體要求使用者手動完成 (S1)–(S4) 四個階段，對非技術使用者門檻較高。BI-Agent 的目標是將這些步驟自動化，讓使用者僅需以自然語言提出商業問題即可獲得答案。這與「自助式 BI（Self-service BI）」的願景一致，但更進一步將資料準備工作也納入自動化範圍。

##### 相較於 NL2SQL 基準與方法

現有 NL2SQL 基準（如 Spider、BIRD、Spider 2.0 等）通常假設已給定正確的資料庫 Schema，且問題可直接由單一 SQL 回答。BI-Bench 則要求模型自行從多個可能相關的資料表中選擇、轉換、連結，再產生查詢。這使得：

- **錯誤來源更多元**：除了 SQL 語法錯誤，還可能發生表選擇錯誤、連結路徑錯誤、轉換邏輯錯誤等。
- **評估更貼近實務**：以結果表比對為標準，而非僅比對 SQL 字串或執行結果是否相等。

在方法上，SOTA NL2SQL 系統如 Kwai-AutoSQL、XiYanSQL、Infly-RL-SQL 等雖在標準 NL2SQL 基準表現優異，但在 BI-Bench 上仍落後於 BI-Agent，顯示它們未充分處理資料準備階段的挑戰。

##### 相較於通用資料分析代理

Databao Agent 等現有資料分析代理雖然也結合 LLM 與工具，但 BI-Agent 的差異在於：

- **專注於 BI 領域**：針對多雪花 Schema、事實表/維度表、儀表板語意等 BI 特有結構設計工具。
- **系統性後訓練**：從真實 BI 專案合成訓練軌跡，並結合 SFT 與 RL，而非僅使用通用指令微調資料。
- **明確的階段分解**：將流程拆解為 Search、Join、Transform、Answer，便於除錯與持續優化。

##### 研究限制

儘管成果顯著，本研究仍存在若干限制：

1. **資料來源集中於 Power BI**：BI-Bench 主要從 Power BI 專案建構，雖然 Power BI 是市場主流，但未來仍需驗證方法在 Tableau、Looker、Qlik 等其他 BI 平台的泛化能力。
2. **問題形式受限於儀表板標題**：商業問題來自視覺化標題，可能無法涵蓋所有使用者實際會問的口語化、多輪對話式問題。
3. **評估以結果表為主**：雖然貼近實務，但對於部分開放式分析問題，單一結果表可能不足以衡量答案品質。
4. **工具細節與錯誤分析未完全揭露**：由於提供的全文片段有限，BI-Agent 各工具的具體演算法、錯誤分佈與失敗案例的深入分析尚無法完整評估。

#### 可重現性評估

##### 開放資源

作者在摘要末尾明確表示已釋出程式碼與資料：

> https://github.com/Hu-Chuxuan/bi-agent

這對研究社群是正面訊號，因為：

- **BI-Bench 資料集公開**：其他研究者可直接使用該基準測試評估自己的模型與方法。
- **BI-Agent 程式碼公開**：有助於重現實驗結果、進行消融研究（Ablation Study）與進一步改進。
- **促進公平比較**：未來 NL2SQL、Agent、BI 等領域的研究可在相同資料上進行比較。

##### 模型權重與 API 依賴

- **Qwen3-8B**：屬於開源模型，理論上可取得權重並重現 SFT+RL 後訓練結果，但論文是否釋出微調後的模型權重需進一步確認。
- **GPT-5.5 / GPT-5.2 / GPT-4o / o4-mini / Codex**：均為 OpenAI 的專有 API 服務，無法完全重現其內部運作，只能透過 API 呼叫復現 BI-Agent 的組合結果。
- **Llama-4-Maverick、Mistral-Large-3、DeepSeek-V4-Pro**：部分開源、部分為 API 服務，重現難度不一。

##### 可重現性建議

為提升可重現性，建議作者未來可補充：

1. 釋出經 SFT+RL 後的 Qwen3-8B 模型權重或 LoRA 適配器（Adapter）。
2. 提供詳細的超參數（Hyperparameters）、訓練硬體配置與訓練時間。
3. 公開軌跡合成（Trajectory Synthesis）的完整流程與範例，讓社群能擴充訓練資料。
4. 提供 Docker 環境或 Colab Notebook，降低環境設置門檻。

#### 未來研究方向

基於本研究的成果與限制，以下幾個方向值得後續探索：

##### 1. 多平台與多模態 BI 支援

未來可將 BI-Bench 擴展至 Tableau、Looker、Qlik、QuickSight 等其他 BI 平台，並納入多模態（Multimodal）資訊，例如儀表板中的圖表類型、顏色編碼、篩選器（Filter）狀態等，讓代理能更精準理解使用者意圖。

##### 2. 多輪對話式 BI（Conversational BI）

目前 BI-Bench 的問題多為單輪、以視覺化標題為基礎。未來可研究多輪對話情境，讓使用者在追問（Follow-up Questions）、澄清（Clarification）、鑽取（Drill-down）等互動中逐步獲得洞察。

##### 3. 結合人機協作（Human-in-the-loop）

對於高風險商業決策，完全自動化可能不被信任。未來可設計人機協作機制，讓 BI-Agent 在不確定時主動詢問使用者，或讓使用者審核連結與轉換步驟，兼顧效率與可信度。

##### 4. 更細緻的錯誤分析與可解釋性（Explainability）

深入分析 BI-Agent 在 Search、Join、Transform、Answer 各階段的錯誤分佈，並提供自然語言解釋（Natural Language Explanation），說明為何選擇某些資料表、為何如此連結、轉換邏輯為何等，將有助於企業使用者信任與採用。

##### 5. 領域適應與企業私有資料

真實企業資料常涉及敏感資訊與領域特定 Schema。未來可研究如何以少量標註資料進行領域適應（Domain Adaptation），並在保護隱私的前提下進行後訓練，例如聯邦學習（Federated Learning）或差分隱私（Differential Privacy）。

##### 6. 結合資料品質與資料治理工具

BI 專案常面臨資料品質問題（缺失值、不一致、重複等）。未來可將資料品質偵測、資料譜系（Data Lineage）、資料目錄（Data Catalog）等資料治理工具整合進 BI-Agent，使其在自動化流程中也能識別並處理資料品質風險。

##### 7. 從 BI 專案學習更豐富的訓練訊號

除了最終答案是否正確，未來可探索更細緻的獎勵設計，例如部分正確的連結路徑、轉換步驟的合理性等，以提升 RL 的樣本效率（Sample Efficiency）與最終表現。

##### 8. 跨語言與在地化

目前 BI-Bench 可能以英文資料為主。未來可建構中文、日文、德文等多語言 BI 基準，並研究 LLM 在不同語言與文化背景下的 BI 自動化能力。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文聚焦於如何自動化端到端的商業智慧（BI）流程，讓使用者不需要手動完成繁瑣的資料準備工作。傳統 BI 工具（如 Power BI、Tableau）要求使用者先找出相關資料表、進行資料轉換、建立連結關係，最後才能回答商業問題，這對非技術使用者來說門檻很高。論文因此研究大型語言模型（LLMs）在完整 BI 流程中的能力，並提出相應的基準測試與智慧代理來降低使用難度。

**Q2：現有的 NL2SQL 方法或基準測試為什麼不足以解決真實 BI 問題？**
A：現有 NL2SQL 基準大多假設已經給定相關資料表與綱要，只評估單一步驟的 SQL 生成能力，忽略了真實 BI 中「找表、轉換、連結」等前置步驟。真實 BI 專案常採用多雪花（multi-snowflake）綱要，包含大量事實表與維度表，且需要處理廠商專屬的轉換語言或圖形介面。因此，單純的 SQL 生成無法涵蓋端到端 BI 所需的資料準備與語意理解，導致這些方法在真實場景中表現不足。

**Q3：為什麼端到端 BI 自動化既重要又困難？**
A：BI 是現代企業數據驅動決策的基石，能自動化端到端流程將大幅提升非技術使用者取得洞察的效率。然而，這個流程涉及多個複雜階段，包括從大量資料表中搜尋相關表格、執行資料清理與轉換、推導正確的連結關係，最後才能產生正確答案。每個階段都可能出錯，且需要結合領域知識與資料管理技術，因此對 LLMs 來說是極具挑戰性的任務。

**Q4：BI-Agent 的核心架構與運作方式是什麼？**
A：BI-Agent 是一個工具增強型（tool-augmented）智慧代理，它會將端到端 BI 流程拆解成多個結構化資料子任務，例如搜尋（search）、連結（join）與轉換（transform）。接著，它會編排各種專門的資料管理方法，在不同 BI 階段呼叫適合的工具來完成任務，而不是讓單一 LLM 直接產生最終答案。這種模組化設計讓 LLM 專注於規劃與決策，同時利用專業工具提升每個子任務的準確性與可靠性。

**Q5：這篇論文的主要創新貢獻有哪些？**
A：首先，作者建立了 BI-Bench，這是第一個系統性評估 LLM 在真實端到端 BI 流程能力的基準測試。其次，提出了 BI-Agent，透過工具增強與子任務拆解來彌補原始 LLM 在資料準備階段的不足。最後，論文發展了一套後訓練框架，能從真實 BI 專案合成訓練軌跡，並結合監督式微調（SFT）與強化學習（RL）進一步提升代理表現。

**Q6：為什麼 BI-Agent 選擇將流程拆解為 search、join、transform 等子任務？**
A：這樣的拆解直接對應傳統 BI 工作流程中的核心階段，讓代理的運作方式更接近人類分析師解決問題的邏輯。每個子任務可以搭配專門的資料管理演算法或工具，例如用 schema matching 找連結、用轉換工具處理資料格式，從而降低單一模型一次性推理的錯誤率。此外，模組化設計也提升了可解釋性，讓開發者能針對特定階段進行診斷與改進。

**Q7：BI-Bench 是如何建構的？資料來源與品質如何確保？**
A：BI-Bench 的資料來自於從公開網頁收集的大量真實 Power BI 專案檔案（.pbix）。研究人員會從這些專案的儀表板中，挑選標題能清楚描述商業意圖的視覺化圖表，並將其對應的問題視為測試問題；接著透過 Power BI 的「Export data」功能匯出該圖表底層的結果表格，作為真實答案（ground-truth answer）。由於這些問題與答案都來自真實使用者建立的儀表板，因此能夠反映實際 BI 場景的複雜度與多樣性。

**Q8：論文的主要實驗結果是什麼？**
A：實驗顯示，即使是當時最先進的前沿大型語言模型，在 BI-Bench 上的準確率也不到 50%，顯示端到端 BI 對現有模型而言非常困難。使用 BI-Agent 後，原始 LLM 的準確率最高可提升 40 個百分點；若進一步進行後訓練，則可再提升最多 30 個百分點。特別的是，經過後訓練的 Qwen3-8B 模型能達到與大型前沿模型相近的品質，但成本卻可低至五十分之一。

**Q9：工具增強與後訓練各自帶來什麼貢獻？有沒有消融實驗的跡象？**
A：工具增強本身就能顯著提升前沿模型的表現，平均帶來超過 10 個百分點的進步，顯示專業工具對於搜尋、連結與轉換階段至關重要。後訓練則進一步讓較小的模型（如 Qwen3-8B）學會更有效的 BI 推理策略，帶來額外高達 30 個百分點的增益。兩者結合時效果最佳，說明單靠模型規模或單靠工具都不足以解決複雜 BI 流程，必須同時強化推理能力與領域專用技能。

**Q10：這項研究在實務上可以應用在哪些場景？**
A：這項技術最直覺的應用是讓企業中的非技術使用者直接用自然語言詢問商業問題，系統便自動從原始資料中找出答案。例如，業務主管可以問「各區域本季銷售額與預算的差異」，而無需自己挑選資料表或撰寫轉換邏輯。此外，它也能減輕資料分析師在重複性資料準備工作上的負擔，讓他們更專注於高價值的策略分析。

**Q11：若要將 BI-Agent 產品化，需要考慮哪些因素？**
A：成本是重要考量，因為論文顯示小型後訓練模型能以遠低於大型前沿模型的成本達到相近品質，這對大規模企業部署非常關鍵。此外，必須考慮與現有 BI 平台（如 Power BI、Tableau）的整合、資料隱私與安全性、以及模型可能產生的幻覺或錯誤連結。最後，產品應提供可解釋的執行步驟與人工覆核機制，讓企業使用者能信任並驗證自動化產生的分析結果。

**Q12：這項研究對 BI 與資料分析領域可能帶來什麼影響？**
A：BI-Bench 的出現為學術界與產業界提供了一個標準化的端到端 BI 評估場景，有助於推動相關研究的進展。研究結果也強調，未來的資料分析系統不應只聚焦於 NL2SQL，而應將資料準備、連結發現與轉換納入整體設計。長遠來看，這可能促使 BI 產品從「輔助工具」朝向「自動化分析代理」演進，進一步降低數據驅動決策的門檻。

**Q13：論文承認了哪些限制？**
A：BI-Bench 目前主要來自公開可取得的 Power BI 專案，可能無法完全代表企業內部私有資料的多樣性與複雜度。此外，評估方式是比對視覺化底層的結果表格，而非完整儀表板或視覺呈現，因此對視覺設計能力的評估有限。資料準備過程中涉及的廠商專屬 DSL 與圖形介面轉換也未被完全涵蓋，這些都是未來可以擴充的方向。

**Q14：BI-Agent 可能在哪些情況下失敗？**
A：當問題涉及高度複雜的多表連結、需要深入的領域知識才能判斷轉換邏輯，或資料表中存在大量語意相近的欄位時，代理可能選錯工具或產生錯誤答案。如果問題本身語意模糊，或儀表板標題無法完整表達使用者的真實意圖，也會增加失敗風險。此外，當綱要過於龐大且缺乏清楚的主鍵或外鍵資訊時，連結關係的推導仍可能出錯。

**Q15：未來可以朝哪些方向繼續研究？**
A：未來可以擴展 BI-Bench 到更多 BI 平台（如 Tableau、Looker）與更多產業領域，提升資料多樣性。另一方面，可以研究如何讓代理在面對模糊問題時主動與使用者互動澄清，並結合更強大的強化學習與語意綱要理解技術。最後，將自動化分析進一步延伸到完整的視覺化儀表板生成、多模態資料處理，以及企業級的安全部署，也都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **企業自助式分析（Self-Service Analytics）**  
   業務部門（如銷售、財務、營運）可直接以自然語言提問，例如「各區域上季實際銷售額與預算、預測的比較」，由 BI-Agent 自動找出相關資料表、完成資料轉換與連結，並產出答案，降低對資料工程師或 IT 的依賴。

2. **跨部門報表自動化**  
   在大型組織中，不同部門常使用各自維護的資料表。BI-Agent 可自動探索多個資料來源、建立連結關係，並根據問題生成對應的查詢與視覺化，適合用於定期管理報表或臨時分析需求。

3. **資料資產探索與治理輔助**  
   當企業累積大量 BI 專案與資料表時，可利用 BI-Agent 的搜尋與連結能力，協助分析師快速理解資料表之間的關係、找出可用欄位，並輔助建立一致的語意層與資料字典。

4. **低程式碼／無程式碼 BI 平台強化**  
   現有 Power BI、Tableau 等工具的使用者仍需手動完成資料準備。將 BI-Agent 整合進這些平台，可讓使用者在對話介面中直接完成端到端分析，提升產品競爭力。

5. **BI 專案遷移與知識萃取**  
   企業收購或系統整合時，常面臨大量歷史 BI 專案與儀表板需要理解。BI-Agent 可協助解析既有專案結構、萃取業務問題與對應答案，加速知識傳承與系統遷移。

### 實作前置條件

**資料條件**
- 至少擁有一個以上真實 BI 專案的資料表與結構描述（schema），包含欄位名稱、資料類型與資料表間的連結關係。
- 建議具備歷史儀表板或報表，可從中萃取出（問題, 真實答案）配對，作為評估與後訓練的基礎。
- 資料應經過基本清理，避免過多缺失值、不一致命名或重複欄位，否則會影響搜尋與連結的準確率。

**運算條件**
- 推論端：可呼叫 frontier LLM API（如 GPT-5.5、o4-mini）或部署開源模型（如 Qwen3-8B、Llama-4-Maverick）。若採用開源模型，建議至少配備一張高記憶體 GPU（如 24GB VRAM 以上）進行本地推論。
- 後訓練端：若要複現論文中的 SFT + RL 流程，需準備 GPU 叢集（建議多張 A100 / H100），並具備數千至數萬條合成訓練軌跡。
- 資料庫與快取：需能執行 SQL 或 DSL 查詢，並建議設立結果快取機制以降低每次查詢成本。

**技能條件**
- 熟悉 Python、SQL 與常見資料處理工具（如 pandas）。
- 了解 LLM 提示工程、RAG、工具使用（tool use）與代理編排框架（如 LangChain、AutoGen 或自研 orchestrator）。
- 若進行後訓練，需具備監督式微調與強化學習實作經驗，並熟悉資料品質控管與評估指標設計。

### 實作步驟建議

1. **建立端到端 BI 評估基準**  
   參考 BI-Bench 的建構方式，從真實 BI 專案中選取儀表板，將視覺化標題轉為自然語言問題，並透過「匯出資料」功能取得真實答案，形成標準測試集。

2. **設計工具增強型代理架構**  
   將 BI 流程拆解為 search、join、transform、answer 等子任務，並為每個子任務開發專用工具（例如 schema 搜尋、連結路徑推薦、資料轉換 DSL 生成、SQL 生成與執行）。

3. **開發編排與錯誤修復機制**  
   讓 LLM 根據中間結果決定下一步動作，並加入驗證步驟（例如檢查 SQL 是否可執行、結果欄位是否符合問題預期）。當發生錯誤時，代理應能回溯並嘗試替代方案。

4. **合成訓練軌跡並進行後訓練**  
   從真實 BI 專案中自動生成正確的執行軌跡，先以監督式微調（SFT）讓模型學會基本流程，再以強化學習（RL）強化決策品質與成本效益。

5. **部署與持續監控**  
   將 BI-Agent 整合至現有 BI 平台或對話介面，並持續追蹤準確率、每次查詢成本與延遲。定期以新問題與新資料更新訓練軌跡，避免模型隨時間退化。

---

### 潛在風險與注意事項

- **資料品質與 schema 複雜度**  
  真實 BI 專案常包含數十張資料表與多對多連結，若 schema 文件不完整，代理容易選錯表或建立錯誤連結。建議先進行 schema 清理與語意標註，並保留人工覆核機制。

- **成本與延遲**  
  端到端 BI 涉及多次 LLM 呼叫與資料庫查詢，每次查詢成本可能快速累積。建議設立快取、限制搜尋範圍，並在準確率與成本之間取得平衡。

- **幻覺與不可解釋性**  
  LLM 可能生成看似合理但錯誤的 SQL 或轉換邏輯。應要求代理輸出每個步驟的理由（chain-of-thought），並提供可檢視的中間結果，讓使用者能夠驗證。

- **隱私與資料安全**  
  企業資料常包含敏感資訊，使用第三方 API 時需評估資料外洩風險。可考慮本地部署開源模型，並對查詢與結果進行去識別化處理。

- **過度擬合特定 BI 工具**  
  論文使用 Power BI 專案為主，若企業使用 Tableau、Looker 或其他工具，需重新設計資料轉換與連結語法，避免工具相依過強。

---

### 與其他技術的整合建議

- **與現有 BI 平台整合**  
  可將 BI-Agent 作為 Power BI、Tableau 或 Looker 的前置對話層，讓使用者以自然語言描述需求，再由代理生成對應的資料準備步驟與視覺化規格，最後呼叫平台 API 呈現結果。

- **與資料目錄（Data Catalog）整合**  
  將 BI-Agent 的搜尋能力與企業資料目錄（如 Microsoft Purview、Alation）結合，可提升資料表與欄位語意理解的準確率，並協助維護資料治理。

- **與 NL2SQL / Text-to-SQL 系統整合**  
  BI-Agent 可視為 NL2SQL 的上層架構：先解決資料表選擇、轉換與連結問題，再將簡化後的語意問題交給專門的 Text-to-SQL 模型（如 XiYanSQL、Kwai-AutoSQL）處理。

- **與向量資料庫與 RAG 整合**  
  對於大型企業，可將 schema 描述、歷史問題與轉換範例存入向量資料庫，透過 RAG 提供相似案例給 LLM，減少幻覺並加速推理。

- **與 MLOps / LLMOps 管線整合**  
  將後訓練、評估與部署流程納入 CI/CD，定期以新資料重新生成訓練軌跡、執行 SFT 與 RL，並監控線上準確率與成本指標。

**AI 工程師**

**研究人員**

**產品經理**
