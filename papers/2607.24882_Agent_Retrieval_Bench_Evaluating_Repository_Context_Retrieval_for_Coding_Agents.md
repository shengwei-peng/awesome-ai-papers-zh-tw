# Agent Retrieval Bench：評估程式設計代理的儲存庫上下文檢索

**原文標題：** Agent Retrieval Bench: Evaluating Repository Context Retrieval for Coding Agents  
**作者：** Bowen Qin、Yi Xie  
**發布日期：** 2026-07-27  
**HF 連結：** [https://huggingface.co/papers/2607.24882](https://huggingface.co/papers/2607.24882)  
**arXiv：** [https://arxiv.org/abs/2607.24882](https://arxiv.org/abs/2607.24882)  

---

## ⚡ TL;DR

現有編碼代理評估忽略補丁生成前的上下文檢索問題。
提出 Agent Retrieval Bench，以凍結基礎提交評估檔案級代理式檢索。
實證顯示無單一檢索方法全面領先，且真實代理軌跡常遺漏黃金檔案。

## 摘要翻譯

現代 coding agents（程式設計代理）通常以最終是否產生正確修補檔來評估，但 patch generation（修補檔生成）取決於較早的 context-acquisition stage（上下文獲取階段）：尋找任務所需的 repository files（儲存庫檔案）。我們提出 Agent Retrieval Bench（本論文提出的代理檢索基準），這是針對此 upstream retrieval problem（上游檢索問題）的 file-level benchmark（檔案級基準）。樣本建構自 real coding-workflow signals（真實程式設計工作流程訊號），並在 frozen base-commit repositories（凍結的基礎提交儲存庫）上進行評估；relevance（相關性）是以代理下一步所需內容來定義，而非直接的 query-file semantic similarity（查詢-檔案語義相似度）。該基準涵蓋四項 positive-retrieval tasks（正向檢索任務）：code2test、comment2context、trace2code 與 edit2ripple；第五個子集使用 natural evidence-backed no-gold cases（具自然證據支持的無黃金標準案例）與 counterfactual wrong-repository controls（反事實錯誤儲存庫對照組）來評估 selective retrieval（選擇性檢索）。Agent Retrieval Bench 包含 427 個樣本，橫跨 25 個儲存庫：345 個 positive examples（正向範例）、50 個自然無黃金標準案例，以及 32 個 counterfactual controls（反事實對照組）。語料庫包含 308 個 base-commit snapshots（基礎提交快照）、392,000 個檔案與 790 萬個 chunks（區塊）。我們評估 lexical retrieval（詞彙檢索）、RepoMap、open-source embeddings（開源嵌入模型）、selective abstention（選擇性棄權），以及 logged agent context selection（記錄的代理上下文選擇）。沒有單一檢索方法家族佔據主導地位：Qwen3-Embedding-4B 在正向樣本上有最佳的 sample-weighted MRR（樣本加權平均倒數排名），Qwen3-Embedding-8B 有最佳的 Recall@20，而 RepoMap 在 8K tokens 時有最佳的 budgeted context yield（預算上下文產出），task-level winners（任務級別最佳模型）差異顯著。以 counterfactual controls（反事實對照組）校準的 selective thresholds（選擇性閾值），無法提升自然無黃金標準案例上的選擇性成功率，揭示了 calibration gap（校準落差）。logged trajectories（記錄軌跡）在 27% 至 35% 的樣本中遺漏了所有 gold files（黃金檔案）。一項受控的 seed-intervention pilot（種子介入先導實驗）發現，相較於 random non-gold context（隨機非黃金上下文），retrieval-derived initial context（檢索衍生初始上下文）能以更少的 post-seed exploration（種子後探索）產生更高的 file F1（檔案 F1 分數），而 oracle gold context（神諭黃金上下文）仍有顯著的 headroom（改善空間）。

### 核心貢獻（3～5點）
- 提出 Agent Retrieval Bench，首個針對程式設計代理上游儲存庫上下文檢索問題的檔案級基準，以真實程式設計工作流程訊號建構，並在凍結的基礎提交儲存庫上進行評估。
- 以代理式相關性（agentic relevance）重新定義檢索目標：相關性應以代理下一步所需內容為導向，而非僅依賴查詢-檔案語義相似度。
- 設計四項正向檢索任務（code2test、comment2context、trace2code、edit2ripple）與一項選擇性檢索子集，涵蓋具自然證據支持的無黃金標準案例與反事實錯誤儲存庫對照組。
- 大規模實證評估詞彙檢索、RepoMap、開源嵌入模型、選擇性棄權與真實代理軌跡，發現沒有單一檢索方法全面主導，且存在校準落差與軌跡遺漏黃金檔案等問題。
- 透過種子介入先導實驗證明，檢索衍生初始上下文優於隨機非黃金上下文，但相較神諭黃金上下文仍有顯著改善空間。

### 適合對象
從事程式設計代理、程式碼檢索、軟體工程智慧化與大型語言模型代理評估的研究人員與工程師，特別是關注上下文獲取層、儲存庫級檢索系統，以及端到端代理效能瓶頸的讀者。

## 深度分析

#### 方法論解析

本研究提出 **Agent Retrieval Bench**，將程式設計代理（coding agents）的評估焦點從傳統的「最終補丁是否正確」向下游移動到**上下文獲取層（context-acquisition layer）**。其核心假設是：代理在生成修補檔（patch generation）之前，必須先找到正確的**儲存庫檔案（repository files）**；若此階段失敗，後續的推理與編輯都會面臨更高的成本與錯誤風險。

##### 1. 代理式相關性（agentic relevance）的形式化

傳統的**通用語義程式碼搜尋（generic semantic code search）**以**查詢-檔案語義相似度（query-file semantic similarity）**定義相關性，例如自然語言描述與函式註解或簽名的相似程度。相對地，Agent Retrieval Bench 定義的**代理式相關性（agentic relevance）**是：「對於當前工作流程的下一個有用步驟，代理需要讀取的儲存庫上下文（repository context）是什麼」。這種相關性具有三個特徵：

- **間接性（indirect relevance）**：例如 **code2test** 中，PR 描述的是實作變更（implementation change），但黃金檔案卻是相關的**迴歸測試（regression test）**。
- **結構性（structural relevance）**：例如 **comment2context** 中，審查評論（review comment）指向 A 檔案，但真正遺失的約束條件（missing constraint）卻在另一個模組（module）。
- **工作流程相依性（workflow-dependent relevance）**：例如 **trace2code** 中，失敗追蹤（failure trace）會顯示測試檔案（test file）或堆疊框架（stack frame），但根本原因（root cause）卻位於與錯誤文字（error text）語義不相似的實作檔案（implementation file）。

因此，本基準拒絕將「查詢與文件的文字相似度」直接等同於「代理需要讀取的檔案」。

##### 2. 五項檢索任務的設計

Agent Retrieval Bench 包含四項**正向檢索任務（positive-retrieval tasks）**與一項**選擇性檢索（selective retrieval）**子集：

| 任務 | 查詢訊號 | 黃金目標的語義 |
|---|---|---|
| **code2test** | PR 意圖或實作變更 | 與該變更相關的測試檔案 |
| **comment2context** | 審查評論 + 已給定檔案 | 評論所暗示、但位於其他檔案的額外上下文 |
| **trace2code** | 重現命令 + 失敗輸出 | 根本原因所在的實作檔案，而非僅是可見的測試框架 |
| **edit2ripple** | 變更意圖 + 錨定 diff/檔案 | 受該編輯連帶影響的其他檔案 |
| **selective** | 自然 issue 或錯誤儲存庫對照 | 在無本地上下文有用時輸出 ABSTAIN |

其中 **edit2ripple** 特別強調「漣漪效應」：單一檔案的修改可能透過 import、介面實作、設定檔或跨模組依賴影響其他檔案，因此代理必須具備結構性推理能力。**selective** 子集則引入 50 個**具自然證據支持的無黃金標準案例（natural evidence-backed no-gold cases）**與 32 個**反事實錯誤儲存庫對照組（counterfactual wrong-repository controls）**，用於評估系統是否能正確判斷「此時不應回傳任何檔案」。

##### 3. 凍結基礎提交（frozen base-commit）與資料衛生

每個樣本都對應到一個**凍結的基礎提交儲存庫（frozen base-commit repositories）**，這確保了：

- 不會因後續 commit 修復而導致**補丁洩漏（patch leakage）**；
- 不會因未來程式碼變動而改變語料庫內容；
- 可進行可重複的**基礎提交快照（base-commit snapshots）**評估。

作者進一步實施多項衛生控制：路徑洩漏、補丁洩漏、commit 洩漏與生成內容洩漏的檢查。這對於程式碼基準尤其重要，因為許多現有資料集會因訓練資料包含未來 commit 而膨脹表現。

##### 4. 評估指標體系

本研究設計的**代理導向評估套件（agent-oriented evaluation suite）**包含多個互補指標：

- **排序指標**：樣本加權平均倒數排名（sample-weighted MRR）、**Recall@20**；
- **預算指標**：**預算上下文產出（budgeted context yield）**曲線（BCY curves），即在固定 token 預算下能納入多少黃金檔案；
- **選擇性指標**：選擇性棄權（selective abstention）的成功率；
- **軌跡成本指標**：記錄軌跡追蹤（logged trajectory track）中首次命中黃金檔案（median first hit）的步驟、平均檔案/路徑事件數（file/path events）；
- **介入指標**：種子介入先導實驗（seed-intervention pilot）中的**檔案 F1 分數（file F1）**與**種子後探索（post-seed exploration）**量。

這種多維度設計避免了單一 top-k 分數過度簡化代理檢索的複雜性。

#### 實驗數據解讀

##### 1. 整體結論：沒有單一檢索家族全面領先

實驗結果最突出的訊息是：**沒有任何單一檢索家族（retrieval family）在所有任務與預算下都佔優勢**。這與傳統程式碼搜尋中「嵌入模型通常勝過詞彙方法」的預期不同：

- **Qwen3-Embedding-4B** 在正向樣本上取得最佳的**樣本加權平均倒數排名（sample-weighted MRR）**；
- **Qwen3-Embedding-8B** 在 **Recall@20** 上最佳；
- **RepoMap** 在 8K token 的預算下取得最佳的**預算上下文產出（budgeted context yield）**；
- 不同任務的**任務級別最佳模型（task-level winners）**差異顯著。

這顯示**詞彙檢索（lexical retrieval）**、**嵌入模型（embeddings）**與**儲存庫地圖（repository maps）**具有互補性。對於需要語義比對的查詢（如 PR 描述找測試），嵌入模型較強；對於需要結構性連結的查詢（如編輯漣漪、跨模組約束），RepoMap 等結構方法在有限預算下更有效。

##### 2. 選擇性棄權的校準落差（calibration gap）

在 **selective retrieval** 實驗中，作者使用 32 個**反事實錯誤儲存庫對照組（counterfactual wrong-repository controls）**來校準選擇性閾值（selective thresholds），希望讓模型在「查詢與當前儲存庫無關」時選擇 ABSTAIN。然而，這些閾值並未提升 50 個**自然無黃金標準案例（natural no-gold cases）**的選擇性成功率。

這揭示了重要的 **校準落差（calibration gap）**：反事實對照組的「錯誤儲存庫」訊號（查詢與整個語料庫語義脫節）與自然案例的「無本地有用上下文」訊號（查詢與語料庫部分相關，但沒有單一檔案能解決問題）並非同分布。換言之，模型學到的「棄權」規則過於粗糙，無法辨識「有語義相似檔案但無代理式有用檔案」的細微情況。

##### 3. 真實代理軌跡的上下文獲取失敗

作者分析了 287 個 code2test、comment2context 與 trace2code 樣本的**記錄軌跡追蹤（logged trajectory track）**：

- **OpenAI strict-context agent** 平均每樣本讀取 3.2 個檔案；
- **Codex CLI** 恢復的上下文（recovered contexts）平均每樣本約 6 個**檔案/路徑事件（file/path events）**；
- 但仍有 **35.2%** 的 OpenAI 樣本與 **27.2–29.3%** 的 Codex 樣本，其軌跡**從未碰到任何黃金檔案（gold file）**；
- 在「最終有碰到黃金檔案」的樣本中，首次命中（median first hit）的中位數步驟為 OpenAI 第 2 步、Codex 第 3 步。

這說明即使現代代理具備互動式探索（interactive exploration）能力，**上下文獲取階段（context-acquisition stage）**仍是顯著的**失效面（failure surface）**與**成本中心（cost center）**。它也反駁了「只要給代理足夠工具呼叫就能彌補檢索」的簡化假設：在約三分之一的樣本中，代理完全錯失了必要檔案。

##### 4. 種子介入先導實驗：檢索種子的價值與神諭上限

在 **種子介入先導實驗（seed-intervention pilot）**中，作者控制代理的初始上下文（initial context）來觀察後續影響：

- 由檢索結果構成的**檢索衍生初始上下文（retrieval-derived initial context）**，相較於隨機非黃金上下文（random non-gold context），能達到更高的 **檔案 F1 分數（file F1）**，同時需要較少的**種子後探索（post-seed exploration）**；
- 然而，相較於**神諭黃金上下文（oracle gold context）**，檢索衍生種子仍有顯著的**改善空間（headroom）**。

這項實驗具有因果解釋力：它顯示更好的初始檢索不僅提升 top-k 分數，還能減少代理後續所需的搜尋量。同時，神諭上下文與檢索上下文之間的差距，也指出仍有大量空間可透過更強的檢索器或上下文引擎（context engine）來提升。

#### 與現有研究的比較

##### 1. 相對於傳統程式碼搜尋基準

**CodeSearchNet** 與 **CodeXGLUE** 奠定了自然語言到程式碼片段（function/snippet level）的語義配對基準。這些基準的查詢通常是「描述某個函式功能」，而相關單位是單一函式或程式碼片段。Agent Retrieval Bench 的差異在於：

- **檢索單位**：從函式/片段提升到**檔案級基準（file-level benchmark）**；
- **查詢分布**：從自然語言描述轉為真實的**程式設計工作流程訊號（real coding-workflow signals）**，如 PR、審查評論、失敗追蹤；
- **相關性定義**：從語義相似度轉為**代理式相關性（agentic relevance）**，強調「下一步需要讀什麼」。

因此，本基準更貼近實際代理運作場景，而非單純的表示學習評估。

##### 2. 相對於儲存庫級上下文基準

**RepoBench** 強調跨檔案上下文對於程式碼自動完成的重要性，但其設定是「已知編輯位置，決定需要哪些額外檔案來完成程式碼」。Agent Retrieval Bench 則反過來問：「在編輯開始之前，代理應該檢查哪些檔案？」這是從**使用上下文（using context）**到**尋找上下文（finding context）**的問題轉移，對於評估**上下文引擎（context engine）**更為直接。

##### 3. 相對於端到端代理評估

**SWE-bench** 與 **SWE-agent** 評估完整 issue 解決流程的最終補丁是否正確；**Agentless** 將定位（localization）明確分離為修復前的階段；**LocAgent** 則研究圖導向的程式碼定位。Agent Retrieval Bench 的定位更上游：

- 它不評估補丁生成（patch generation）或測試通過與否；
- 它將**檢索問題（retrieval problem）**獨立出來，使研究者能診斷代理是否在編輯前找到必要檔案；
- 它提供元件級別（component-level）證據，而非端到端（end-to-end）的綜合成績。

這種隔離的價值在於：當 SWE-bench 失敗時，研究者可以區分「是檢索失敗、推理失敗、編輯失敗，還是驗證失敗」。Agent Retrieval Bench 填補了「檢索失敗」這一環的標準化評估缺口。

##### 4. 主要貢獻與限制

**主要貢獻**：

1. 將**代理式相關性（agentic relevance）**形式化，並落實為四項正向任務與一項選擇性子集；
2. 建立 427 個樣本、25 個儲存庫、308 個基礎提交快照、39.2 萬檔案、790 萬**區塊（chunks）**的規模化基準；
3. 提出結合排序、預算、選擇性、軌跡成本與種子介入的多維度評估框架；
4. 實證顯示不同檢索家族互補，並揭示真實代理軌跡中顯著的上下文獲取失敗。

**限制**：

- **元件級別而非端到端**：作者明確表示不宣稱檢索是補丁失敗的主因，也不宣稱 **檔案 F1 分數（file F1）**可替代測試通過率。要建立檢索與修補成功的因果連結，需要具備對齊結果標籤的可執行修復基準，而本基準目前的工作流程衍生樣本尚未提供這類標籤。
- **靜態評估為主**：雖然有軌跡分析與種子介入，但大部分指標仍是靜態 top-k 分數。真實代理會進行迭代式搜尋（iterative search），如何將靜態檢索分數轉換為動態成本仍待研究。
- **選擇性校準的分布偏移**：反事實對照組與自然無黃金案例之間的落差，顯示目前尚無穩健的選擇性棄權機制。

#### 可重現性評估

##### 1. 資料集與程式碼釋出狀況

從提供的上下文來看，論文並未明確說明是否已公開原始碼、資料集或評估腳本。然而，作者強調了嚴格的**資料衛生（data hygiene）**標準與**凍結基礎提交（frozen base-commit）**設定，這暗示了若未來釋出，應具備較高的可重現性。

##### 2. 可重現性的關鍵要素

若要完整重現本基準，至少需要以下內容：

- **基礎提交快照（base-commit snapshots）**：308 個凍結版本的儲存庫狀態，需包含確切的 commit hash；
- **查詢與黃金標註 schema**：每個樣本的工作流程衍生查詢（workflow-derived query）、對應的黃金檔案（gold file）清單、以及選擇性子集的證據；
- **語料切分方式**：如何將檔案切分為 7.9 百萬個**區塊（chunks）**（chunk size、overlap、tokenizer）；
- **評估腳本**：MRR、Recall@20、BCY curves、selective success、file F1 的實作細節；
- **模型權重與推論設定**：開源嵌入模型（如 Qwen3-Embedding-4B/8B）的檢索參數、RepoMap 的建構方式、詞彙檢索的索引設定；
- **代理軌跡**：OpenAI strict-context agent 與 Codex CLI 的**記錄軌跡追蹤（logged trajectory track）**，以便重現軌跡成本分析。

##### 3. 潛在重現挑戰

- **儲存庫規模**：39.2 萬檔案與 790 萬區塊需要大量儲存與計算資源，重現門檻不低；
- **嵌入模型版本**：Qwen3-Embedding 系列可能持續更新，需固定 checkpoint 與 tokenizer；
- **代理行為的非確定性**：真實代理（如 Codex CLI）的軌跡可能因溫度、工具呼叫順序而異，需記錄完整配置；
- **反事實對照組的建構**：錯誤儲存庫對照組需要人工或半自動配對，若未公開配對邏輯，難以完全重現。

##### 4. 建議

為提升可重現性，建議作者釋出：

1. 完整的 **Agent Retrieval Bench** 資料集與元資料；
2. Docker 化或 snapshot 化的基礎提交環境；
3. 標準化評估腳本與排行榜機制；
4. 已脫敏的代理軌跡日誌；
5. 詳細的附錄說明 chunking、tokenizer、閾值校準流程。

#### 未來研究方向

##### 1. 建立檢索與修補成功的因果連結

目前 Agent Retrieval Bench 是**元件級別（component-level）**評估。未來可設計**可執行修復基準（executable repair benchmark）**，將檢索品質與最終測試通過率連結，例如：比較「檢索器提供的 top-k 上下文」與「神諭黃金上下文（oracle gold context）」對補丁成功率的邊際貢獻。這需要對齊的結果標籤與可控的實驗設計。

##### 2. 動態與互動式檢索評估

現有指標多為靜態 top-k。未來可發展**多回合檢索模擬器（multi-turn retrieval simulator）**，讓檢索器或代理在每次讀取檔案後更新查詢，並以累積成本（工具呼叫次數、token 數、延遲）作為評估維度。這將更貼近真實代理的**迭代式搜尋（iterative search）**行為。

##### 3. 選擇性棄權的校準方法

針對目前 **校準落差（calibration gap）**的問題，未來可探索：

- 使用自然無黃金案例直接訓練或校準棄權閾值；
- 引入**不確定性估計（uncertainty estimation）**或**證據強度（evidence strength）**分數；
- 發展能區分「語義相似但無用」與「真正相關」的判別模型。

##### 4. 混合式檢索架構

實驗顯示沒有單一方法全面領先，因此未來可研究如何動態結合：

- **詞彙檢索（lexical retrieval）**對於精確識別符號的優勢；
- **開源嵌入模型（open-source embeddings）**對於語義比對的優勢；
- **RepoMap** 等結構方法對於預算內高產出的優勢。

例如，可依查詢類型、儲存庫大小、可用 token 預算，訓練一個**檢索路由器（retrieval router）**來選擇或融合不同檢索家族。

##### 5. 預算感知與成本最佳化

未來可將 **預算上下文產出（budgeted context yield）**擴展為完整的成本-效益分析，納入：

- 檢索本身的計算成本；
- 後續語言模型推理的 token 成本；
- 工具呼叫的延遲（latency）。

目標是發展能夠在固定資源下最大化有用上下文的**上下文引擎（context engine）**。

##### 6. 跨語言與跨領域擴展

目前基準涵蓋 25 個儲存庫，未來可擴展至更多程式語言、框架與軟體工程任務（如重構、文件更新、安全性修補）。此外，可探討**多語言儲存庫（polyglot repositories）**與**單體式架構（monorepos）**中的檢索挑戰。

##### 7. 利用真實代理軌跡改進檢索

論文發現真實代理軌跡中約 27–35% 完全錯失黃金檔案。未來可將這些軌跡作為訓練資料，發展：

- 從失敗軌跡中學習的檢索器；
- 能預測「下一步該讀哪個檔案」的策略模型；
- 結合人類或代理回饋的強化學習檢索系統。

##### 8. 神諭上下文的上限分析

種子介入實驗顯示，即使給定**神諭黃金上下文（oracle gold context）**，仍有顯著**改善空間（headroom）**。這暗示檢索並非唯一的瓶頸：語言模型可能仍無法充分利用正確上下文。未來可進一步拆解「檢索失敗」與「上下文利用失敗」的相對貢獻，從而更精準地定位代理系統的弱點。

## 論文問答

**Q1：Agent Retrieval Bench 想解決什麼上游問題？為什麼只看最終 patch 是否正確是不夠的？**

A：現代程式設計代理通常被評估最終產生的修補檔是否通過測試或滿足神諭，但這種端到端測量掩蓋了更早的上下文獲取階段。在能夠編輯之前，代理必須先找出儲存庫中真正需要的檔案，而這個檢索問題本身就可能失敗或耗費大量成本。Agent Retrieval Bench 因此把「上下文獲取層」獨立出來，測量代理在編輯前能否找到正確的儲存庫檔案，而不是只問最後 patch 是否正確。

**Q2：什麼是「代理式相關性」，它和傳統語義程式碼搜尋有何不同？**

A：傳統語義程式碼搜尋通常以查詢與文件之間的語義相似度來定義相關性，例如自然語言描述與函式內容的匹配程度。相對地，代理式相關性是以「代理下一步需要讀什麼」來定義，因此常常具有間接性、結構性或工作流程相依性。例如，PR 描述的是實作變更，但真正需要的卻是迴歸測試；審查評論指向某個檔案，但遺失的約束條件卻在另一個模組；失敗追蹤顯示的是測試堆疊框架，根本原因卻在語義不相似的實作檔案。

**Q3：為什麼上下文獲取既是「成本中心」也是「失效面」？論文提供了哪些證據？**

A：即使代理可以透過互動式探索彌補初始上下文的不足，每一次額外搜尋都會消耗工具呼叫、token 與延遲，因此上下文獲取是實際運行成本的重要來源。論文分析記錄軌跡發現，OpenAI strict-context 代理平均每次樣本讀取 3.2 個檔案，Codex CLI 則約有 6 個檔案/路徑事件，但仍有 35.2% 的 OpenAI 樣本與 27.2–29.3% 的 Codex 樣本從未觸及任何黃金檔案。這顯示上下文獲取本身就是一個可測量且常見的上游失效面，不能單靠最終 patch 結果來掩蓋。

**Q4：Agent Retrieval Bench 的核心評估協定是什麼？為什麼採用檔案級、凍結基礎提交的設定？**

A：該基準給定一個從真實程式設計工作流程衍生的查詢，以及凍結在基礎提交的儲存庫語料庫，然後要求檢索器或上下文引擎對檔案進行排序或選擇性棄權。採用檔案級而非 patch 級，是為了隔離上下文獲取問題，測量代理在編輯前能找到哪些有用檔案。凍結基礎提交則可防止固定程式碼、修補檔、提交內容或生成內容洩漏到檢索語料中，確保評估的是真正的檢索能力而非記憶能力。

**Q5：請說明四個正向檢索任務與選擇性子集的設計意涵。**

A：code2test 要求從 PR 意圖或實作變更找出相關測試；comment2context 要求從審查評論與被指出的檔案找出額外上下文，但不包括已給定的檔案；trace2code 要求從重現的失敗輸出找出根本原因原始碼，而可見的測試框架只算輔助上下文；edit2ripple 則給定一個錨定變更，要求找出受其連帶影響的其他檔案。第五個選擇性子集包含 50 個具自然證據支持的無黃金標準案例，以及 32 個反事實錯誤儲存庫對照組，用來評估系統能否在沒有有用本地上下文時正確棄權。

**Q6：論文在建構資料與防範洩漏方面做了哪些關鍵設計選擇？**

A：所有 427 個樣本都針對凍結的基礎提交語料庫進行評估，並附有黃金證據與綱要/語料檢查，以確保黃金檔案確實存在於基礎提交中。作者明確控制了路徑、修補檔、提交與生成內容等多種洩漏風險，避免模型透過非檢索途徑取得答案。此外，基準刻意不做 patch 級評估，也不宣稱檔案 F1 可替代測試通過率，從而保持元件級評估的純淨性與可解釋性。

**Q7：實驗評估了哪些方法？最重要的整體發現是什麼？**

A：實驗涵蓋詞彙檢索、RepoMap、開源嵌入模型、選擇性棄權以及記錄的代理上下文選擇等多種方法。結果顯示沒有任何單一檢索家族在所有指標或預算下都佔優勢：Qwen3-Embedding-4B 在正向樣本的樣本加權 MRR 上最佳，Qwen3-Embedding-8B 的 Recall@20 最高，而 RepoMap 在 8K token 的預算上下文產出上表現最好。這說明語義方法與結構方法具有互補性，不同工作流程訊號需要不同的檢索策略。

**Q8：選擇性檢索的實驗結果揭示了什麼問題？**

A：研究人員使用反事實錯誤儲存庫對照組來校準選擇性閾值，希望系統在無用時能正確回傳 ABSTAIN。然而，這些以反事實案例校準的閾值並未提升在自然無黃金標準案例上的選擇性成功率，顯示出明顯的校準落差。這意味著僅靠錯誤儲存庫控制來決定何時棄權，並不足以泛化到真實世界中「本地沒有相關檔案」的複雜情況。

**Q9：記錄軌跡分析與種子介入先導實驗告訴我們什麼？**

A：在 287 個 code2test、comment2context 與 trace2code 樣本上，OpenAI 代理有 35.2% 的樣本從未碰到黃金檔案，Codex CLI 則為 27.2–29.3%；即便最終找到黃金檔案，首次命中的中位數步數也分別是第 2 步與第 3 步。種子介入實驗進一步發現，以檢索結果作為初始上下文，比隨機非黃金上下文帶來更高的檔案 F1，並且需要較少的種子後探索；但相較於神諭黃金上下文，仍有相當大的改善空間。

**Q10：這個基準在實務上可以如何應用於程式設計代理或產品開發？**

A：開發團隊可以用 Agent Retrieval Bench 來診斷自家代理的上下文獲取層，找出在哪些工作流程訊號上容易漏掉關鍵檔案。它也能作為檢索器與上下文引擎的標準化比較平台，幫助產品團隊在語義嵌入、結構地圖與詞彙檢索之間做權衡。此外，選擇性子集可協助評估代理是否具備「知道何時不該檢索」的能力，減少把無關檔案塞進上下文所造成的雜訊與成本。

**Q11：在產品落地時，上下文預算與延遲會帶來哪些考量？**

A：實際產品中，模型可接收的上下文長度有限，因此不能無限制地塞入所有高排序檔案，必須在固定 token 預算下最大化有效上下文。RepoMap 在 8K token 預算下展現最佳產出，顯示結構化摘要能在低成本下提供不錯的覆蓋率。相對地，嵌入模型雖然 Recall@20 較高，卻可能需要更多 token 與延遲，產品團隊需根據使用場景在召回率、預算與回應速度之間取捨。

**Q12：Agent Retrieval Bench 對整個研究領域可能帶來什麼影響？**

A：它提供了一個統一的「代理式相關性」語義與衛生標準，讓不同檢索方法能在相同基礎上比較。它與 SWE-bench 等端到端評估互補：SWE-bench 問「代理能否修好問題」，Agent Retrieval Bench 問「代理能否先找到需要的檔案」。這種元件級隔離有助於學界與業界更精確地定位失敗來源，推動上下文獲取層的系統性改進。

**Q13：作者明確承認了哪些限制？**

A：作者強調這是元件級評估，而非端到端評估，因此不宣稱檢索是 patch 失敗的主因，也不認為檔案 F1 可以取代測試通過率。目前的樣本來自工作流程訊號，但缺乏與最終修補結果對齊的可執行修復標籤，所以無法直接估計檢索品質對 patch 成功率的因果效應。要建立這條連結，需要額外建構具備對齊結果標籤的可執行修復基準。

**Q14：哪些失敗案例最凸顯目前方法的不足？**

A：最明顯的失敗案例是真實代理軌跡中仍有約 27–35% 的樣本完全錯過黃金檔案，顯示即使經過多步互動探索，檢索能力仍有顯著缺口。另一個關鍵失敗是選擇性棄權的校準落差：用反事實錯誤儲存庫調出的閾值無法幫助系統在真實無黃金案例中正確棄權。這些案例說明，單靠提升排序分數或簡單閾值並不足以解決代理式檢索中的所有挑戰。

**Q15：未來可以朝哪些方向延伸這項研究？**

A：未來可以建立與可執行修復結果對齊的基準，以直接測量檢索品質對 patch 成功率的因果影響。另一個方向是發展更穩健的選擇性檢索校準方法，讓代理能根據自然無黃金案例的證據正確判斷何時棄權。此外，也可以探索結合語義嵌入與結構地圖的混合檢索策略，並設計能同時評估靜態排序與互動式探索成本的綜合評估框架。

## 實務應用指南

### 適用場景

1. **程式設計代理的上游檢索診斷**  
   若團隊已部署 Cursor、Codex CLI、OpenAI 編碼代理或內部代理，卻發現代理經常「找不到檔案」而產生錯誤補丁，可將 Agent Retrieval Bench 作為元件級診斷工具，量化上下文獲取層的失敗率與成本。

2. **RAG 與程式碼庫索引的選型與調校**  
   在導入向量資料庫、RepoMap、詞彙檢索或開源嵌入模型前，可用本基準比較不同檢索家族在 code2test、comment2context、trace2code、edit2ripple 等任務的表現，避免僅以語義相似度選型。

3. **選擇性檢索與棄權機制的設計**  
   當代理面對「儲存庫內根本沒有相關檔案」的情境（例如跨專案問題、需求過於籠統），可參考本基準的自然無黃金案例與反事實錯誤儲存庫對照組，設計更穩健的棄權閾值。

4. **程式碼審查輔助工具**  
   在 PR 審查或 review comment 場景中，可利用 comment2context 與 edit2ripple 的評估邏輯，自動推薦審查者應額外查看的跨模組檔案，降低遺失約束條件的風險。

5. **CI/CD 失敗追蹤的根因定位**  
   針對測試或建置失敗的 trace，可套用 trace2code 的評估方式，訓練或驗證檢索器是否能從失敗追蹤中找出根本原因所在的實作檔案，而非僅回傳可見的測試堆疊框架。

### 實作前置條件

**資料條件**
- 取得或建構與目標任務對應的「工作流程衍生查詢」：例如 PR 描述、審查評論、失敗追蹤、錨定 diff。
- 每個查詢需對應到凍結的基礎提交儲存庫快照，並有經人工或程序驗證的黃金檔案清單。
- 若要做選擇性檢索，需額外準備具自然證據支持的無黃金案例，以及反事實錯誤儲存庫對照組。

**運算條件**
- 需能對 30 萬至 40 萬個檔案、數百萬個區塊建立索引；向量嵌入模型（如 Qwen3-Embedding-4B/8B）建議使用 GPU 加速推論。
- 需支援檔案級排序與 token 預算評估，建議預留可執行多次檢索與軌跡重建的運算資源。

**技能條件**
- 熟悉 Git、儲存庫快照管理與基礎提交還原。
- 具備資訊檢索基礎，能理解 MRR、Recall@20、File F1 等指標。
- 有能力將代理軌跡轉換為可分析的檔案/路徑事件序列。
- 若要做種子介入實驗，需能控制代理初始上下文並記錄後續工具呼叫。

### 實作步驟建議

1. **定義任務語義與相關性標準**  
   先決定要解決的是 code2test、comment2context、trace2code、edit2ripple 還是選擇性檢索，並明確「相關」是指「代理下一步需要讀取的檔案」，而非單純語義相似。

2. **建立凍結的基礎提交語料庫**  
   為每個樣本還原到基礎提交，建立快照，並排除後續 patch、commit 或生成內容洩漏的可能。

3. **建構多種檢索索引**  
   同步建立詞彙索引、開源嵌入向量索引、RepoMap 結構摘要，以及代理工具呼叫可觸及的程式碼庫索引。

4. **執行檔案級排序並評估**  
   對每個查詢產生前 k 檔案排序，計算 sample-weighted MRR、Recall@20、File F1；同時繪製不同 token 預算下的 budgeted context yield 曲線。

5. **加入選擇性棄權評估**  
   使用反事實錯誤儲存庫對照組校準棄權閾值，再於自然無黃金案例上驗證，觀察是否存在校準落差。

6. **記錄並分析代理軌跡**  
   若評估真實代理，記錄檔案/路徑事件，計算首次命中中位數、從未觸及黃金檔案的比例，以及平均工具呼叫次數。

7. **進行種子介入先導實驗**  
   比較檢索衍生初始上下文、隨機非黃金上下文與神諭黃金上下文對後續探索與 File F1 的影響，確認檢索品質與探索成本之間的關係。

8. **迭代優化並整合至產品**  
   根據任務級別最佳模型與預算點，選擇最適組合；將檢索器封裝為上下文引擎 API，供程式設計代理呼叫。

### 潛在風險與注意事項

- **靜態 top-k 分數無法代表真實代理表現**  
  互動式代理可透過多次工具呼叫彌補初始檢索不足，因此產品評估應同時看軌跡成本與最終是否命中黃金檔案，避免過度優化單一 MRR。

- **選擇性閾值可能產生校準落差**  
  以反事實錯誤儲存庫對照組校準的閾值，未必能提升自然無黃金案例的表現；建議將兩類案例分開驗證，不要混為一談。

- **不同任務與預算下的最佳模型會反轉**  
  Qwen3-Embedding-4B 與 8B、RepoMap 與詞彙檢索各有所長，產品層應避免「一個模型打天下」，而採任務路由或混合排序。

- **基礎提交凍結與資料洩漏**  
  若評估語料包含未來 patch 或生成內容，會高估檢索表現；務必對每個樣本還原到正確的基礎提交，並做路徑、commit、生成內容洩漏檢查。

- **過度依賴語義相似度會錯失結構性相關檔案**  
  例如 trace2code 的根本原因檔案可能與錯誤文字語義差距很大，產品中應保留結構性與工作流程訊號（如呼叫圖、模組邊界）。

- **File F1 不等同於補丁正確率**  
  本基準測的是上下文獲取，而非最終 patch 生成；若要宣稱對修復成功率的影響，需額外建立可執行的修復基準。

---

### 與其他技術的整合建議

- **與 RAG 管線整合**  
  將 Agent Retrieval Bench 的檔案級排序作為 RAG 的第一階段檢索器，後接 chunk 級重排序與摘要，兼顧廣度與細粒度。

- **與程式設計代理的工具層整合**  
  把評估過的檢索器封裝成 `search_repository`、`find_related_tests`、`locate_root_cause` 等工具，讓代理在互動探索時優先呼叫高品質檢索，而非僅用 grep。

- **與 CI/CD 監控整合**  
  在測試失敗時，將 trace2code 檢索器嵌入建置流程，自動推薦可能相關的實作檔案給開發者，縮短根因定位時間。

- **與程式碼審查平台整合**  
  將 comment2context 與 edit2ripple 模型部署為審查機器人，於 PR 頁面標註「此評論可能還需查看這些檔案」。

- **與可觀測性平台整合**  
  記錄代理軌跡中的檔案/路徑事件，並與基準指標對齊，持續監控首次命中中位數、未觸及黃金檔案比例等上游指標。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「為什麼程式設計代理會找不到檔案」這個問題出發，理解 Agent Retrieval Bench 與傳統程式碼搜尋的差異，再聚焦圖 1 的四項任務與選擇性檢索概念；數學指標可先略讀，重點掌握「代理式相關性」與「凍結基礎提交」這兩個核心設計。

**AI 工程師**  
請重點關注實驗設計與評估指標：如何從真實工作流程訊號建構樣本、如何避免資料洩漏、如何比較詞彙檢索/嵌入/RepoMap/代理軌跡，以及如何將這些檢索器封裝成可上線的上下文引擎；選擇性棄權的校準落差是特別值得留意的落地陷阱。

**研究人員**  
本論文的貢獻在於將「代理式相關性」形式化並建立統一評估語義，建議深入閱讀與 CodeSearchNet、RepoBench、SWE-bench 的定位比較，並思考如何將本基準與端到端修復基準銜接，以進一步驗證上下文獲取對補丁成功率的因果影響。

**產品經理**  
請把本論文視為「程式設計代理的體檢報告」：它告訴你代理在找檔案這個環節有多脆弱、不同檢索技術的取捨、以及為何不能只看最終補丁是否正確。重點關注適用場景、成本中心與潛在風險章節，以評估是否該在產品中投入資源建立或採購專屬的上下文檢索層。
