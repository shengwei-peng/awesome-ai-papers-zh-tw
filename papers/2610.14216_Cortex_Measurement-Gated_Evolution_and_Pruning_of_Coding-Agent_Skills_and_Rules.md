# Cortex：測量門檻式演化 (Measurement-Gated Evolution) 與程式碼代理 (coding agent) 技能 (skill) 及規則 (rule) 的剪枝 (pruning)

## ⚡ TL;DR

程式碼代理的配置檔常憑印象累積，缺乏實證，造成雜訊與傷害。
Cortex 以可重播任務與通過率比較，僅在淨增益且無退步時保留新技能或規則。
在保留任務上，演化後配置比無規則基線提升55百分點，且未增加常駐上下文。

## 摘要翻譯

像 Claude Code 這類的程式碼代理 (coding agent) 也會遵循開發者為其撰寫的文字檔案：一個專案指令檔 (project instruction file)、代理可選擇開啟的技能 (skill)，以及當代理讀取符合條件的檔案時會自動載入的規則 (rule)。我們將這些檔案稱為代理配置 (harness)。開發者每次修正 (correction) 代理行為時都會新增內容，但單次成功意義不大：同一個代理可能這次通過任務，下次卻失敗。

我們提出 Cortex，這個工具會測試代理配置的變更，而非直接信任這些變更。它將開發者工作階段 (session) 中的修正儲存為可重播任務 (replayable task)，找出反覆出現的修正，每次撰寫一個技能或規則，且只有在有之與無之的反覆對照執行顯示出淨增益 (net gain) 且沒有任務明顯變差時，才會保留該條目 (item)。現有文字在刪除前也以同樣方式進行測試，且 Cortex 不會新增或刪除代理從未使用的文字。

我們使用 Claude Haiku 4.5 在一個為此目的所建的程式碼儲存庫 (repository) 上測試 Cortex，該儲存庫包含模型容易違反的慣例 (convention)、一個無從學習的區域，以及一個扮演開發者的腳本。在保留測試任務 (held-out tasks) 上，它所建構的代理配置讓代理遵循慣例的頻率遠高於沒有技能或規則的情況，對照區域維持不變，且未新增每個回合 (turn) 都會讀取的文字。會自動載入的規則承擔了大部分工作；技能只有在與任務相關的檔案一起提供時才有幫助，而在每個回合都提供的技能則很少被開啟。Cortex 並未保留我們植入的任何無用或有害建議，但代理從未開啟那些無用建議或有害技能，且對有害規則未做出裁決，因此該測試顯示的是 Cortex 不會保留未使用的文字，而非它能偵測損害。在使用更強的 Claude Sonnet 5 時，單次執行所建構的代理配置增益甚微；而在一個真實的開源專案 (open-source project) 中，由於代理很少被修正，Cortex 並未發現可學習之處。我們釋出該工具、實驗環境 (lab) 及其資料。

### 核心貢獻（3～5點）
- 提出 Cortex 工具，採用測量門檻式演化 (Measurement-Gated Evolution) 方法，透過有之與無之的反覆對照執行驗證每項技能或規則的淨增益 (net gain)，避免單次成功造成的誤判。
- 實作剪枝 (pruning) 機制，刪除現有文字前同樣進行測試驗證，並堅守「不新增或刪除代理從未使用之文字」的原則。
- 在保留測試任務 (held-out tasks) 上驗證：所建構的代理配置 (harness) 顯著提升慣例 (convention) 遵循率，對照區域維持不變，且未新增每回合 (turn) 都讀取的冗餘文字。
- 釐清規則 (rule) 與技能 (skill) 的角色差異：規則承擔主要工作，技能僅在隨任務相關檔案提供時有效，而每回合提供的技能極少被開啟。
- 誠實揭示方法限制：實驗僅證明 Cortex 不保留未使用文字，並未證明其能偵測損害；於較強模型 (Claude Sonnet 5) 與真實開源專案 (open-source project) 上效果有限。

### 適合對象
從事 AI 程式碼代理 (coding agent) 開發與部署的工程師、研究代理設計 (agent design) 與評估方法論的學者、關注 AI 工具可靠性與可重現性的實務工作者，以及對自動化程式碼生成系統中提示工程 (prompt engineering) 與配置管理感興趣的研究人員。

## 深度分析

#### 方法論解析

Cortex 的核心方法論建立在「測量門檻」(measurement-gated) 原則之上，將代理配置 (harness) 視為可量化、可實驗的物件，而非單純的策展產物。其架構由三個命令組成，形成一個閉環的演化-剪枝系統。

**三命令架構的分工與互補**

`/harvest` 在工作階段 (session) 結束時運作，將「從壞到好」的階段轉化為可重播任務 (replayable task)。每個任務包含三個關鍵元素：(1) 壞掉的提交 (broken commit)，作為起點；(2) 開發者的請求，作為意圖；(3) 檢查腳本 (check)，作為通過與否的客觀判定。這種設計將主觀判斷轉化為可重複執行的二元結果，避免了「看起來有效」的確認偏誤 (confirmation bias)。

`/evolve` 讀取反覆出現的修正 (recurring corrections)，為其中一個撰寫候選技能 (skill) 或規則 (rule)。其關鍵設計在於「載入層級」(loading tier) 的選擇：若修正集中在特定資料夾，候選僅在代理於該處工作時載入。這直接回應了「上下文預算 (context budget)」的成本問題——每一行永遠在上下文中的文字，都會在每個回合 (turn) 付出代價。

`/prune` 反向運作：逐一移除現行條目 (live item) 並重新測量，僅刪除從未「觸發」(fired) 的條目。「觸發」的定義是該條目確實進入代理的上下文——規則被載入，或技能被打開。

**測量門檻的統計嚴謹性**

Cortex 的核心創新在於其測量協議 (sweep protocol)。對於每個候選條目，系統在可拋棄的儲存庫副本中執行 k 次批次執行 (rollout)，分別在「現行配置」與「現行配置加上候選」兩種條件下進行。這形成一個配對實驗 (paired experiment)，其差異的統計推論比獨立樣本更為強健。

保留條件包含三項必須同時滿足的標準：(1) 淨增益 (net gain)——通過率提升；(2) 觸發——候選必須在至少一次批次執行中進入上下文，否則無法歸因；(3) 無顯著回歸——任何任務的退化不得超過設定容忍度 (tolerance)，對於現行配置從未失敗的任務，容忍度為零。被僅因零容忍度退化而淘汰的候選會被重新掃描 (sweep)，這避免了單次實驗的雜訊導致誤判。

**「歸因於上下文」的原則**

貫穿整個系統的核心原則是：「條目僅在其進入代理上下文之處被記功或記過。」這解決了代理評估中的一個根本問題：若一個技能從未被開啟，則無法判斷其是否有用；若一個規則從未載入，則其存在與否對行為沒有因果影響。這種「因果歸因」(causal attribution) 的要求，使得 Cortex 與傳統的提示工程 (prompt engineering) 拉開距離——後者往往假設所有文字都會被讀到。

**載入層級的設計空間**

Cortex 識別出至少四種載入模式：永遠載入、按路徑載入技能、按路徑載入規則、永不載入。這形成一個成本光譜：永遠載入的成本最高（每回合付費），按路徑載入的成本中等（僅在相關工作時付費），技能的成本最低（僅在代理主動開啟時付費）。Cortex 的演化過程會為每個候選選擇適當的層級，這是一種隱式的成本-效益最佳化。

#### 實驗數據解讀

**主要結果的強度與解讀**

在四個規則家族 (rule families) 上，演化後的配置比「無技能無規則」的基線高出 +55.0 百分點 (percentage points)，95% 信賴區間 (CI) 為 [+34.1, +74.1]，排列檢定 (permutation test) 的 p 值為 0.0001。這個結果的統計強度值得仔細審視：

首先，55 百分點的效應量 (effect size) 在代理評估中極為罕見。許多代理改進的論文報告的提升幅度在 5-15 百分點之間，且常伴隨寬廣的信賴區間。55 百分點的提升意味著通過率從接近隨機水平躍升至接近天花板，這暗示基準任務對模型而言具有挑戰性，且慣例 (convention) 的遵循是主要的失敗模式。

其次，信賴區間的下界 +34.1 仍然遠離零，這在多重比較 (multiple comparisons) 的情境下尤為重要。雖然 Cortex 進行了多次掃描，但主要結果是在保留測試任務 (held-out tasks) 上的一次性比較，因此無需進行嚴格的 Bonferroni 校正。

第三，p = 0.0001 的排列檢定結果考慮了「哪些執行 (run) 被測量」與「哪些情境被測量」兩層的隨機性，這比僅考慮情境層的檢定更為保守。

**控制組的設計與解讀**

控制家族 (plain bugs with no rule to learn) 的結果是 -0.8 百分點，幾乎為零，且沒有任何執行保留針對該家族的條目。這提供了重要的內部效度 (internal validity) 證據：Cortex 不會無中生有地添加條目，也不會在沒有學習信號的地方產生雜訊。

然而，-0.8 百分點的輕微負值值得注意。雖然在統計上不顯著，但它提醒我們：即使經過測量門檻，演化過程仍可能引入微小的回歸。這可能是因為某些條目在跨家族任務上產生了輕微的注意力分散 (attention dilution) 效應。

**「無永遠開啟上下文」的重要性**

Cortex 強調演化後的配置「沒有增加每回合都讀取的文字」。除了所有實驗組共享的 559 字元 CLAUDE.md 之外，唯一在每回合出現的文字是技能列表 (skill listing)。這是一個關鍵的工程成就：在代理的上下文預算極為有限的今天，能夠在不增加永遠載入成本的前提下提升性能，是 Cortex 區別於「把所有規則塞進 CLAUDE.md」這種天真方法的根本所在。

在 R1 執行中，演化配置比「將貢獻指南附加到 CLAUDE.md」的基線高出 11.1 百分點（95% CI [0.0, +22.5]）。這個比較的信賴區間下界為零，跨越了批次邊界，因此不能被視為確定性結論。但它暗示了「精準載入」可能比「全部塞入」更為有效——這與直覺一致，因為後者會稀釋模型對相關規則的注意力。

**安慰劑與有害候選的測試**

Cortex 測試了 20 個安慰劑候選 (placebo candidates)（關於儲存庫不在乎的事項的可信建議）和 5 個有害候選 (harmful candidates)。結果是「全部被拒絕」，但論文坦誠地指出這個測試比表面看來更弱：候選首先在廉價的篩選掃描 (screen) 中測試，僅運行候選所針對的任務中現行配置並非總是通過的那些。代理從未開啟安慰劑或 2 個有害技能，因此它們無法被保留——這測試的是「Cortex 不保留未使用的文字」，而非「Cortex 能偵測損害」。

對於 3 個有害規則，代理確實載入了它們，但 Cortex「未達成裁決」(reached no verdict)。這可能是因為有害規則的影響在篩選掃描中未達到統計顯著性，或因為它們在某些任務上幫助、在另一些任務上傷害，淨效應不顯著。無論如何，這凸顯了一個重要限制：Cortex 的測量協議在偵測「平均無害但偶爾有害」的條目時可能力有未逮。

**模型依賴性的發現**

在更強的 Claude Sonnet 5 上，單次執行的配置「增加甚少」。這與近期研究 [31] 一致：較弱模型往往無法啟用 (activate) 或遵循新增的內容，而較強模型本身已具備遵循隱含慣例的能力，因此從顯式規則中獲益較少。這暗示 Cortex 的價值與目標模型的「原始能力」呈反向關係——它對較弱模型更有用，因為較弱模型更需要明確的指引。

**真實開源專案的失敗**

在真實開源專案中，代理「很少被修正」，Cortex 因此「找不到可學習的東西」。這個結果看似負面，實際上極具資訊價值：它證明了 Cortex 不會在沒有信號時強行添加條目，也證明了真實開發工作（相對於合成實驗）中的修正密度可能不足以觸發學習。這對 Cortex 的部署策略有重要意涵：它最適合「開發者反覆修正同一類錯誤」的情境，而非「偶爾使用代理」的情境。

#### 與現有研究的比較

**與自動提示/程式優化的比較**

Cortex 與自動提示優化 (automatic prompt optimization) 文獻 [1, 25] 有明顯的後裔關係，但有幾個關鍵區別。傳統的提示優化通常在固定基準測試 (benchmark) 上運作，目標是最大化基準分數；Cortex 則針對單一儲存庫的特定慣例，目標是最大化開發者特定任務的通過率。這種「從通用基準到特定情境」的轉移，使得 Cortex 更貼近實際部署場景，但也使其更難以與基準分數比較。

此外，傳統提示優化通常將所有提示視為單一字串進行最佳化；Cortex 則將配置分解為多個條目，每個條目有其載入層級，並獨立評估。這種「模組化」(modularization) 使得剪枝 (pruning) 成為可能，也使得「哪個條目有用」的歸因更為清晰。

**與代理設計優化的比較**

代理設計優化 [18, 66] 關注的是代理的整體架構（如工具集、記憶機制、規劃策略），而非其文字配置。Cortex 專注於「不改變代理本身，只改變其讀取的文字」這一更窄的問題。這種範圍限制既是優勢（部署成本低，無需重新訓練或微調）也是限制（無法解決需要架構變更才能解決的問題）。

**與近期配置演化研究的比較**

最直接的比較對象是同樣處理配置演化的近期工作 [10, 27, 65, 72]。Cortex 與這些工作的關鍵區別在於其「測量門檻」的嚴格性：許多演化系統接受任何提升，無論其是否統計顯著；Cortex 要求淨增益、觸發證據、且無顯著回歸。這種嚴格性使得 Cortex 的輸出更為保守，但也更為可信。

此外，Cortex 的「載入層級」概念在現有工作中並不常見。許多系統假設所有文字都在上下文中，因此無法處理「按需載入」的情境。Cortex 明確建模了載入成本，這對於上下文預算有限的代理至關重要。

**與「技能可能有害」研究的呼應**

近期研究 [54] 報告添加技能可能使代理變差。Cortex 的設計直接回應了這一發現：通過測量門檻，它能夠拒絕有害的候選。然而，如前所述，Cortex 在偵測「平均無害但偶爾有害」的條目時可能力有未逮，這是一個需要進一步研究的開放問題。

**與「技能增益可能是雜訊」研究的呼應**

研究 [26] 發現某些技能增益在統計上無法與執行間雜訊 (run-to-run noise) 區分。Cortex 的設計明確針對這一問題：通過多次執行 (k runs) 與配對比較，它能夠分離真實效應與雜訊。論文報告同一配置兩次測量的差異為 -3.3 百分點（95% CI [-7.3, 0.0]），這正是 Cortex 試圖克服的雜訊水平。

**與模型依賴性研究的呼應**

研究 [31] 指出配置的效用取決於使用它的模型。Cortex 的實驗結果與此一致：Claude Haiku 4.5 從演化配置中獲益顯著，而 Claude Sonnet 5 獲益甚少。這暗示 Cortex 的最佳應用場景是「較弱模型 + 明確慣例」的組合，而非「最強模型 + 通用任務」。

**Cortex 的局限性**

儘管有上述優勢，Cortex 仍有幾個明顯的局限性：

1. **單條目獨立評估**：Cortex 逐一評估候選，無法捕捉條目之間的交互作用 (interaction effects)。兩個單獨無用的條目可能組合起來有用，反之亦然。

2. **靜態載入規則**：載入層級在撰寫時確定，無法根據任務動態調整。

3. **無損害偵測保證**：如前所述，Cortex 無法可靠地偵測「平均無害但偶爾有害」的條目。

4. **依賴修正密度**：在開發者很少修正代理的情境下，Cortex 無法學習。

5. **單一模型評估**：實驗僅使用 Claude Haiku 4.5 與 Sonnet 5，未涵蓋其他模型家族。

#### 可重現性評估

**程式碼與資料的釋出**

論文明確聲明釋出了工具、實驗環境 (lab) 及其資料。這是可重現性的良好起點，但需要更仔細的評估：

工具本身（Cortex）的釋出使得其他研究者可以在自己的儲存庫上重現其方法。然而，方法的成功取決於「開發者修正的密度」與「任務的可重播性」，這些在真實專案中可能難以達成。

實驗環境（合成儲存庫與腳本化開發者）的釋出使得主要結果可以完全重現。合成儲存庫的設計——四個慣例家族加一個控制家族——是一個精巧的實驗設計，使得「學習 vs. 無學習」的對比清晰可見。

資料的釋出（包括所有批次執行的結果、候選條目的文字、保留/拒絕的決策）使得二次分析成為可能。其他研究者可以檢驗 Cortex 的決策是否合理，或測試替代的統計閾值。

**可重現性的限制**

儘管有上述釋出，仍有幾個可重現性限制：

1. **模型版本依賴**：實驗使用 Claude Haiku 4.5 與 Sonnet 5，這些是 Anthropic 的專有模型，無法在其他地方取得。即使取得，模型版本更新可能導致行為變化，使得歷史結果無法重現。

2. **代理實作依賴**：Cortex 針對 Claude Code 設計，其「技能」與「規則」的語義是 Claude Code 特有的。其他代理（如開源替代品）可能有不同的載入機制，使得 Cortex 無法直接移植。

3. **任務可重播性假設**：Cortex 假設任務可以通過「壞掉的提交 + 請求 + 檢查腳本」來重播。在真實專案中，環境依賴、外部服務、隨機性等因素可能使得完全重播變得困難。

4. **統計方法的透明度**：雖然論文報告了信賴區間與 p 值，但重抽樣 (resampling) 的具體實作（抽樣單位、抽樣次數、隨機種子）需要從程式碼中推導，或在補充材料中明確說明。

5. **「腳本化開發者」的行為**：實驗使用腳本扮演開發者，其行為模式可能與真實開發者不同。特別是，「反覆出現的修正」在腳本中是預定義的，在真實中是自然產生的，這種差異可能影響 Cortex 的學習信號。

**與完全可重現的距離**

整體而言，Cortex 的可重現性處於「良好但非完美」的水平。對於擁有 Claude API 存取權限的研究者，主要結果應該可以重現；但對於無法存取這些模型的研究者，則需要尋找替代方案。論文的價值在於其方法論（Cortex 的設計原則）而非其具體結果，這使得即使模型變化，方法論仍然適用。

#### 未來研究方向

**多條目交互作用的建模**

Cortex 目前獨立評估每個候選條目，這忽略了條目之間的交互作用。未來研究可以探索：

1. **組合評估**：在保留多個條目後，重新評估整個集合，檢驗是否存在「1+1>2」或「1+1<2」的情況。

2. **冗餘偵測**：兩個條目可能表達相同的規則，合併它們可以節省上下文空間。

3. **衝突解決**：兩個條目可能給出矛盾的指引，需要某種仲裁機制。

**動態載入機制**

Cortex 的載入層級在撰寫時靜態確定。未來可以探索：

1. **任務感知載入**：根據當前任務的內容，動態決定哪些條目進入上下文。

2. **學習式載入**：將載入決策本身視為一個學習問題，最佳化上下文預算的分配。

3. **漸進式揭露**：先載入簡短摘要，僅在代理需要時才載入完整內容。

**損害偵測的強化**

Cortex 無法可靠偵測「平均無害但偶爾有害」的條目。未來可以探索：

1. **最壞情況分析**：不僅關注平均通過率，也關注最差情況的通過率。

2. **任務分層分析**：將任務按類型分層，檢驗條目是否在某些類型上系統性地有害。

3. **對抗性測試**：主動生成試圖誘發失敗的任務，檢驗條目是否會導致新的失敗模式。

**跨儲存庫遷移**

Cortex 目前為單一儲存庫演化配置。未來可以探索：

1. **慣例抽象**：將特定儲存庫的慣例抽象為更通用的模式，遷移到新儲存庫。

2. **元學習**：在多個儲存庫上學習「如何學習慣例」，使得新儲存庫的冷啟動更快。

3. **社群配置庫**：建立慣例配置的社群分享機制，使得常見慣例（如「Python 專案使用 pytest」）可以預先載入。

**與代理架構的整合**

Cortex 目前不改變代理本身。未來可以探索：

1. **配置感知的注意力**：讓模型知道哪些上下文是「配置」而非「任務」，可能改變其遵循方式。

2. **配置驗證**：在代理執行前，靜態檢查配置的一致性與完整性。

3. **配置除錯**：當代理失敗時，自動識別是哪個配置條目導致的失敗。

**理論基礎的建立**

Cortex 目前是一個實證系統，缺乏理論基礎。未來可以探索：

1. **配置學習的樣本複雜度**：需要多少修正才能可靠地學習一個慣例？

2. **配置效果的泛化界**：在保留測試任務上的提升能保證多大程度的泛化？

3. **配置與模型能力的交互**：在什麼模型能力水平下，配置最有價值？

**真實部署的縱向研究**

Cortex 的實驗是短期的（10 輪腳本化階段）。未來可以進行：

1. **長期部署研究**：在真實開發團隊中部署 Cortex 數月，追蹤其演化軌跡。

2. **A/B 測試**：將開發者隨機分組，一組使用 Cortex，一組不使用，比較長期的程式碼品質指標。

3. **修正模式分析**：分析真實開發者的修正模式，檢驗 Cortex 的假設（「反覆出現的修正」）在實務中是否成立。

**多模態配置的探索**

Cortex 目前僅處理文字配置。未來可以探索：

1. **程式碼片段配置**：配置中包含程式碼範例，而非僅自然語言描述。

2. **結構化配置**：使用結構化格式（如 JSON、YAML）而非自由文字，使得驗證與組合更為容易。

3. **視覺化配置**：對於 UI 相關任務，配置可能需要包含螢幕截圖或設計稿。

這些方向中的每一個都代表著一個獨立的研究議題，但都與 Cortex 的核心精神——「將配置視為可測量的物件」——保持一致。隨著程式碼代理在軟體開發中的角色日益重要，配置的品質將成為決定代理實用性的關鍵因素，而 Cortex 為這個新興領域提供了一個嚴謹的方法論起點。

## 論文問答

**Q1：什麼是「代理配置（harness）」，為什麼它在程式碼代理的工作流程中扮演關鍵角色？**

A：代理配置指的是開發者可以在一分鐘內透過編輯文字檔來改變代理行為的所有內容，包括專案指令檔（如 CLAUDE.md 或 AGENTS.md）、代理可選擇開啟的技能（skills）資料夾，以及在代理讀取符合條件的檔案時自動載入的規則（rules）。這些文字在每個回合都會進入模型的上下文，因此每一行都會被每一次工作階段的每一個步驟「付費」一次。隨著開發者反覆修正代理的錯誤，這些檔案會像文件一樣自然增生，但其中許多條目其實從未被驗證是否真的有用。

**Q2：為什麼「單次成功」不足以作為保留一條代理配置條目的證據？**

A：因為代理在同一個固定任務上的成功是一個帶有雜訊的隨機量——模型會對其輸出進行取樣，所以同一個代理可能在一次嘗試中通過任務，下一次卻失敗。論文的實測顯示，同一個代理配置在兩批獨立的批次執行中，通過率相差可達 −3.3 個百分點（95% CI [−7.3, 0.0]），這種差異若只看一次會被誤判為真實效應。因此，僅憑開發者目睹一次的「成功」就寫入一條新規則，等同於把雜訊當成了證據。

**Q3：未經測量、由印象累積而成的代理配置會帶來哪些具體風險？**

A：這種配置會逐漸堆積三類有害內容：完全無用的指示、被證明會拖低表現的指示，以及每一條都會佔用寶貴上下文預算的「沉默成本」。近期研究也指出，加入技能有時反而讓代理表現變差、在單一儲存庫上量測到的技能增益與執行間雜訊無法區分，且較弱的模型往往無法啟用或無法遵循新增的內容。換言之，憑直覺策展的代理配置會同時浪費 token、降低可靠性，並讓開發者誤以為自己正在「教導」代理。

**Q4：Cortex 的三個指令（/harvest、/evolve、/prune）如何分工並形成一個閉環？**

A：`/harvest` 在工作階段結束時執行，把「從壞到好」的過程儲存為可重播任務——包含壞掉的 commit、開發者的請求，以及一個判定嘗試是否成功的檢查腳本，並記錄沿途的每一處修正。`/evolve` 讀取反覆出現的修正，為其中之一撰寫一個候選技能或規則，決定其載入層級（總是載入或依路徑載入），然後在多個可拋棄的儲存庫副本上，用現行配置與「現行配置加上候選」各執行 k 次，僅在候選有淨增益、確實被觸發、且未讓任何任務惡化超過容忍度時才保留。`/prune` 反向運作：逐一移除現行條目並重新量測，從不刪除它未曾觀察到被觸發的條目；三者共同構成「測量而非策展」的循環。

**Q5：「測量門檻（measurement-gated）」這個核心原則的具體意涵是什麼？為何它比單純的 A/B 測試更嚴格？**

A：測量門檻意味著一條條目只有在「有證據顯示它有用」時才會被加入或保留，而證據必須來自多次重複執行下的通過率差異，並伴隨信賴區間與顯著性檢定。它比一般 A/B 測試更嚴格之處在於三個額外條件：候選必須在至少一次批次執行中「被觸發」（規則進入上下文或技能被開啟），必須對所有任務都未造成超過容忍度的退步（現行配置從未失敗的任務容忍度為零），且若僅因這類零容忍任務被淘汰，候選會先被重新掃描一次。這確保了 Cortex 不會把「從未進入上下文所以無害也無益」的條目誤判為可保留。

**Q6：Cortex 如何決定一個候選條目的「載入層級」，這個設計選擇為何重要？**

A：`/evolve` 會根據修正反覆出現的位置來選擇載入層級——若修正集中在某個資料夾，候選就設定為僅在代理於該處工作時才載入；只有在修正橫跨多處時才會考慮更高層級的載入。這個設計極為重要，因為每一條「總是在線」的條目都會在每一個回合、每一個工作階段中被支付一次上下文成本。論文的實驗結果顯示，所有被保留的條目都帶有 paths 欄位，因此演化後的配置除了所有分支共有的技能清單之外，唯一在每個回合都存在的文字就是 559 字元的 CLAUDE.md——這正是「不為每個回合增加無謂負擔」的具體實踐。

**Q7：Cortex 的實驗是如何設計的，以確保量測到的增益不是來自記住訓練任務？**

A：研究團隊建立了一個小型合成儲存庫，內含四條「家規」（house rules）——例如只能透過專案自有的時鐘模組讀取時間——這些慣例即使程式碼能跑也常被模型破壞；另設一組純粹的 bug 家族作為控制組，整個家族沒有可學習的規則。一支腳本扮演開發者，4 個獨立執行（R1 到 R4）各自從儲存庫的新副本開始，經歷相同的 10 回合腳本工作階段，並讓 Cortex 演化出代理配置。接著，每個代理配置會在 30 個保留測試情境上量測——這些情境屬於相同家族但從未在任何工作階段中出現過，因此保留測試上的任何增益都必須來自「學到東西能遷移」，而非記住具體任務。

**Q8：在保留測試任務上，Cortex 演化出的代理配置相較於「沒有技能與規則」的基準取得了什麼樣的量化結果？**

A：在四個規則家族上，演化後的配置比沒有技能與規則的基準高出 +55.0 個百分點的通過率（95% CI [+34.1, +74.1]，排列檢定 p = 0.0001），這個信賴區間同時考慮了「哪一輪執行」與「哪個情境」被量測的隨機性。控制家族僅變化 −0.8 個百分點，且沒有任何一輪執行為它保留了條目，顯示 Cortex 不會無中生有地添加無關內容。在 R1 中，演化後的配置也比「把專案貢獻指南附加到 CLAUDE.md」的基準高出 11.1 個百分點（95% CI [0.0, +22.5]），說明精準的依路徑規則比把所有規則一股腦塞進總是載入的檔案更有效。

**Q9：Cortex 對於安慰劑候選與有害候選的處理結果為何？這項測試的強度如何？**

A：20 個安慰劑候選（看似合理但與儲存庫無關的建議）與 5 個有害候選都沒有被保留——這是表面上令人安心的結果。然而測試本身比這個數字所暗示的更弱：每個候選會先經過一道廉價的「篩選（screen）」掃描，僅在「現行配置並非每次都通過」的相關任務上執行；代理在篩選中從未開啟安慰劑或有害技能，因此這些候選根本不可能被保留。對於有害規則，Cortex 也未能達成任何裁決。換言之，這個結果證明的是「Cortex 不會保留從未使用的文字」，而非「Cortex 能偵測出有害條目並加以拒絕」——這是論文中極為誠實的一項區分。

**Q10：在什麼樣的開發情境下，Cortex 會為開發者帶來最大的價值？**

A：當開發者在一個具有明確、可重複違規模式之慣例的儲存庫上工作，且代理反覆犯下相同錯誤時，Cortex 的價值最高——因為這正是 `/harvest` 能累積足夠「反覆出現的修正」、並讓 `/evolve` 有素材撰寫精準規則的情境。相反地，在真實的開源專案中，由於代理很少被修正，Cortex 找不到可學習的內容；這說明 Cortex 並非通用加速器，而是針對「代理在某個專案中反覆出錯」這個特定痛點的工具。

**Q11：Cortex 與既有自動提示詞或代理配置優化系統相比，定位有何不同？**

A：既有系統（如提示詞演化、代理設計搜尋、近期對代理配置本身的優化）通常以基準測試集為優化與評估對象，追求跨多個儲存庫的通用表現。Cortex 處理的問題更窄、卻在某一面向上更困難：單一儲存庫、其專屬慣例、從開發者自身工作中抽取的少量任務、固定的上下文預算，以及無法事先知道某一條指示是否值得保留。它不追求基準上的最高分，而是把「開發者一小時內能編輯的文字」當作可量測、可演化、可剪枝的對象，這是一種從「策展」轉向「測量」的典範轉移。

**Q12：若要將 Cortex 部署到實際的生產工作流程中，會浮現哪些產品化考量？**

A：首先，`/harvest` 需要可靠地偵測「從壞到好」的轉折點，這在真實開發中比腳本化情境更模糊——開發者可能同時修多個 bug、可能中途放棄、可能用自然語言而非 commit 訊息描述修正，因此需要更穩固的「成功判定」介面。其次，掃描（sweep）需要為每個候選執行多次代理批次，這在大型儲存庫上會迅速累積成本與時間，產品需要提供「成本預估」與「優先排序」機制。最後，paths 欄位與載入層級的設計雖然減少了上下文負擔，卻也意味著開發者必須理解代理配置的分層機制，工具的 UX 需要把這層抽象對使用者透明化。

**Q13：Cortex 在論文中被明確承認的限制有哪些？**

A：論文中坦承三項重要限制。第一，有害候選的測試強度不足——因為代理從未開啟它們，所以「未被保留」不能等同於「能偵測傷害」。第二，在更強的 Claude Sonnet 5 上，單一執行的代理配置幾乎沒有帶來增益，暗示 Cortex 的價值可能集中在較弱模型更需要明確指引的情境。第三，在真實的開源專案中，由於代理很少被修正，Cortex 找不到可學習的內容，這凸顯了「需要足夠、可重複的修正訊號」這個前提條件。

**Q14：Cortex 在哪些情境下會表現不佳或甚至失效？**

A：當開發者的修正極為罕見或高度異質時（每個 bug 都不同、沒有反覆出現的模式），`/evolve` 沒有足夠訊號撰寫有意義的候選，Cortex 會像在真實開源專案中一樣「找不到東西可學」。當代理本身已經很強（如 Sonnet 5），新增的規則可能被視為冗餘甚至干擾，導致單次執行的增益趨近於零。當有害規則恰好在篩選階段被載入但代理未受影響時，Cortex 也無法對其做出裁決——這代表對於「會載入但會誤導代理」的條目，目前的測試設計仍有缺口。

**Q15：這項工作為未來的研究開啟了哪些值得探索的方向？**

A：未來可朝幾個方向延伸：其一，設計能真正「偵測傷害」而不只是「偵測未使用」的測試機制，例如強制讓候選在更多任務上被觸發後再裁決；其二，把 Cortex 的測量門檻原則推廣到其他可編輯的代理元件（如工具描述、子代理設計），檢驗該原則的通用性；其三，研究如何在更強的模型上避免「冗餘指示反而干擾」的問題，可能需要根據模型能力動態調整載入層級；其四，將 `/harvest` 的「從壞到好」偵測與開發者的工作流程更緊密整合，例如從 IDE 事件或 PR 審查意見中自動抽取修正，讓 Cortex 在真實開發節奏中也能累積足夠的學習訊號。

## 實務應用指南

### 適用場景

1. **團隊內部程式碼庫的慣例固化**：當團隊有自己的命名、模組劃分或測試撰寫慣例（例如「時間一律走 `clock.ts`」、「錯誤處理必須用 `Result<T, E>`」），但 Claude Code 經常在 PR 中違反時，可用 Cortex 把開發者反覆修正的內容沉澱為規則，避免每次新人或新 session 都要重新教一遍。

2. **長生命週期專案的上下文預算管理**：在 monorepo 或大型開源專案中，`CLAUDE.md` 與 skills 容易隨時間膨脹，每個 turn 都付費。Cortex 的 `/prune` 可定期審視哪些條目其實從未被載入或從未生效，把「永遠在線但沒人讀」的文字清掉，釋出上下文預算給真正有用的內容。

3. **AI 工程團隊的 prompt 與 skill A/B 測試**：當團隊想新增一條 skill（例如「PR 描述要包含 migration note」）但不確定是否真的有效時，Cortex 提供一個有統計信賴區間的比較流程，避免「看起來有用就上線」的直覺決策。

4. **模型升級時的 harness 重新驗證**：當團隊從 Claude Haiku 4.5 升級到 Sonnet 5（或反過來）時，舊 harness 的有效性可能改變——論文顯示 Sonnet 5 從單一 run 的 harness 幾乎沒得到好處。Cortex 可在升級後重新跑 sweep，確認既有條目在新模型下仍然有效。

5. **教育訓練場域的「可重播任務」建置**：在內部訓練或評測新進工程師使用 Claude Code 時，可把 `/harvest` 累積的可重播任務（broken commit + request + check script）作為教材或評分題庫，每個任務都有可重現的失敗起點與可驗證的成功條件。

### 實作前置條件

**資料面**
- 一個 Git 儲存庫，且開發者實際用 Claude Code 在其中工作並會留下可被偵測的「從壞到好」軌跡。
- 每個被收成的任務必須能寫出一個 `check` 腳本（測試、lint、snapshot diff 皆可），用來判定單次 rollout 是否成功——這是 Cortex 唯一賴以量化的證據。
- 至少累積數輪「同樣修正反覆出現」的 session，否則 `/evolve` 沒有候選可寫。

**運算面**
- 每次 sweep 至少需要 `k` 次 × 2（base + candidate）× N 個任務的 rollout 配額。論文中 k 與 N 的具體數值依容忍度與信心需求而定，實務上每個候選可能要數十到上百次 agent 呼叫。
- 需要可丟棄的儲存庫副本（disposable clone）來隔離每次 rollout，避免狀態污染。
- 建議有排程與並行控制（背景 worker、rate limit 管理），因為 sweep 是 I/O bound 而非 GPU bound。

**技能面**
- 熟悉 Claude Code 的 harness 結構：`CLAUDE.md`、skills 目錄、rules 的 `paths` 欄位與載入時機。
- 能撰寫可靠的 `check` 腳本——這是整個系統的單一可信來源，腳本寫錯就會讓 Cortex 留下錯誤的條目。
- 基本的統計素養：理解 pass rate、信賴區間（resampling / permutation）、淨增益與「未超過容忍度退化」的意義，否則容易被單次結果誤導。

### 實作步驟建議

1. **先把「現行配置」凍結並量測一次基線**：在引入 Cortex 前，用一組固定的保留測試任務（held-out scenarios）量測目前 `CLAUDE.md` + skills + rules 的通過率，記錄 CI。這是後續所有比較的錨點。

2. **部署 `/harvest` 並累積可重播任務**：在工作流程末端掛上 `/harvest`，讓每次「從壞到好」的 session 自動產出（broken commit, request, check, corrections log）。前幾週重點是驗證 `check` 腳本的正確性與穩定性，而非立即演化。

3. **觀察「反覆出現的修正」**：當 `/evolve` 開始讀 corrections log 時，先人工檢視它提議的候選條目是否符合直覺——這是早期最便宜的人工把關點。

4. **執行 `/evolve` 的單一候選 sweep**：每次只寫一個 skill 或 rule，跑 base vs. candidate 的成對 rollout。確認三個條件同時成立：(a) 候選有淨增益、(b) 候選在至少一次 rollout 中實際「觸發」（rule 被載入或 skill 被開啟）、(c) 沒有任務退化超過容忍度。

5. **對退化剛好超標的候選做二次 sweep**：論文明確建議「只因退化被殺」的候選再跑一次，因為單次 rollout 的雜訊（論文報告同一 harness 兩批 rollout 差 −3.3 點）可能誤判。

6. **定期跑 `/prune`**：對所有 live 條目逐一做「移除後重測」，從未在 sweep 中被觀察到觸發的條目直接保留（UNMEASURED），有觸發但移除後沒變差的則進入候選刪除。

7. **建立保留測試任務池並鎖定**：把用來量測的 held-out scenarios 與訓練用的 harvested tasks 嚴格分開，論文中 +55.0 點的結論完全建立在「loop 從未看過測試題」之上。

8. **模型升級或重大重構後重跑整個流程**：把步驟 1 的基線量測與步驟 4–6 的 sweep 視為週期性任務，而非一次性設定。

### 潛在風險與注意事項

- **`check` 腳本錯誤會讓整個系統失靈**：Cortex 的所有決策都依賴 `check` 的布林輸出。若腳本本身 flaky 或對「成功」的定義過寬/過窄，會留下無用甚至有害的條目。緩解：對 `check` 腳本本身做版本控管與人工抽樣驗證。

- **「未觸發 = 安全」不等於「已驗證安全」**：論文坦承，無用與有害的 placebos 因為 agent 從未開啟它們，所以 Cortex 無法對其下「有害」的判決。換言之，Cortex 保證的是「不留下從未用過的文字」，而非「能偵測已用文字的傷害」。緩解：對高風險條目（涉及安全、權限、破壞性操作）額外做人工 review，不要只信 sweep。

- **執行間雜訊可能掩蓋真實效應**：同一 harness 兩批 rollout 差 −3.3 點（CI 含 0），單次觀察到的「改善」可能是雜訊。緩解：堅持使用 CI 與 permutation test，不要只看點估計；對小效應（< 5 點）提高 k。

- **較強模型可能從 harness 獲益極少**：論文中 Claude Sonnet 5 從單一 run 的 harness 幾乎沒得到好處，意味著把為 Haiku 調出的 harness 直接套到 Sonnet 可能浪費上下文。緩解：模型升級時重跑 sweep，或為不同模型維護不同 harness。

- **真實專案可能根本沒東西可學**：論文在真實開源專案上跑了 Cortex，因為 agent 很少被修正，所以什麼都沒找到。緩解：把 Cortex 視為「有東西可學時的工具」，而非「一定要產出東西的流程」；沒有候選被接受也是合法結果。

- **always-on 文字的隱性成本**：即使條目只在特定 `paths` 觸發，CLAUDE.md 本身仍每個 turn 載入。緩解：把 CLAUDE.md 視為最昂貴的版面，只放真正跨檔案通用的內容。

- **可重播任務的「過時」問題**：隨著儲存庫演進，舊的 broken commit 可能無法再被乾淨地重現。緩解：定期重跑 harvested tasks，淘汰已無法 replay 的項目。

### 與其他技術的整合建議

- **與既有 CI / 測試基礎設施整合**：`check` 腳本可直接呼叫專案既有的 unit test、integration test 或 lint，把「agent 通過與否」對齊到團隊既有的品質閘門，避免雙重標準。

- **與 prompt 優化框架（如 DSPy、TextGrad）互補**：這類框架優化的是「單次 prompt 內的字串」，Cortex 優化的是「跨 session 的持久化文字」。兩者可分層使用——prompt 框架處理單次互動的措辭，Cortex 處理哪些規則值得持久化。

- **與遙測與可觀測性平台整合**：把每次 rollout 的結果（pass/fail、觸發了哪些 rule、開啟了哪些 skill）匯入既有的 observability stack，方便跨團隊分析「為什麼某條 rule 在某些任務上從未觸發」。

- **與程式碼審查工具整合**：可在 PR 流程中加入「本次變更是否新增/修改了 harness 條目」的檢查，並要求附上對應的 sweep 結果摘要，把 harness 變更也納入 code review。

- **與模型評測平台整合**：把 Cortex 的 held-out scenarios 與既有 benchmark 區隔開——前者是「這個專案特有的慣例」，後者是「通用能力」，混淆會讓評估失真。

- **與版本控管的 hook 整合**：把 `/harvest` 掛在 session 結束或 commit 前，把 `/prune` 掛在定期排程（每週或每月），把 `/evolve` 保留為人工觸發，避免在開發者未注意時自動改寫 harness。

### 給不同背景讀者的閱讀建議

**給初學者**：把 Cortex 想成「給 AI 助理的 lint + autofix，但 autofix 之前要先證明有用」。先理解三件事——harness 是什麼（CLAUDE.md + skills + rules）、為什麼單次成功不算證據（模型會取樣，所以同一任務會時好時壞）、以及 `check` 腳本是唯一可信的證據來源——就能掌握全文八成的精神，不必先深究統計方法。

**給 AI 工程師**：重點讀 Section 2 的載入分層（always / by path）與 Section 4 的 sweep 設計，特別是「候選必須實際觸發才算數」這條規則——這是與一般 prompt 優化最大的差異。實作時優先把 `check` 腳本的可靠性工程做好，再來談 sweep 的統計嚴謹度，因為前者是後者的前提。

**給研究者**：論文的真正貢獻不是 Cortex 工具本身，而是把「harness 演化」從 impression-based curation 推向 measurement-based curation 的方法論轉移。值得延伸的方向包括：跨模型的 harness 可移轉性（Sonnet 5 結果暗示這是個開放問題）、`check` 腳本的可學習性、以及如何把「未觸發 = UNMEASURED」這個保守策略放鬆而不犧牲安全性。論文中 −3.3 點的執行間雜訊數字也值得在更大規模上重現。

**給產品經理**：把 Cortex 視為「管理 AI 行為設定檔的營運流程」，而非單純的開發者工具。核心決策是：哪些行為值得寫進永遠在線的 CLAUDE.md（昂貴但穩定）、哪些該放在 by-path 的 rule（便宜且精準）、哪些該做成 skill（最便宜但需要 agent 主動開啟）。論文中「skills 在每次 turn 都列出但很少被開啟」的發現，直接影響你對 skill 設計的投資報酬率預期。
