# EvoDuet：應用於科學發現之網路搜尋與任務求解雙層共同演化

## ⚡ TL;DR

LLM驅動的演化搜尋在需要外部知識時容易停滯，單純加入網路搜尋也因查詢無法隨解演化而失效。
本文提出EvoDuet雙層共同演化法，以知識落差檢索閘門連接內層查詢演化與外層解演化。
在21項任務中提升NDG，於8項任務超越先前最佳紀錄，並適用於多種搜尋支架。

## 摘要翻譯

使用大型語言模型 (LLM) 的演化式搜尋，在進展需要模型所缺乏的外部知識時，可能會陷入停滯。提供相關文件雖有所助益，但僅加入網路搜尋工具，會在候選解改變時持續回傳相同的頁面。我們提出 EvoDuet，一種雙層優化方法，在固定模型參數的條件下，共同演化候選解與搜尋查詢。在每次迭代中，檢索閘門讓 LLM 評估其知識落差，並選擇檢索新文件、重複使用已儲存的文件，或不檢索文件而繼續進行。內迴圈精煉查詢，並依據文件預期能產生的候選解分數對文件進行排序；外迴圈則從這些文件平行產生候選解，並記錄評估結果供後續搜尋使用。在 21 個優化任務中，每次迭代僅產生一個候選解的情況下，EvoDuet 將 OpenEvolve 的標準化發現增益 (NDG) 在使用 GPT-5.6-Luna 時從 74.1% 提升至 78.0%，在使用 Gemini-3.8-Flash 時從 61.3% 提升至 82.3%，而 Qwen3.5-9B 則未受惠。我們表現最佳的執行結果在八個任務上超越先前報告的最佳分數，包括 Q20 與 Rosetta 上的交換縮減，並在另外三個任務上與其持平。EvoDuet 亦在加減法與去噪任務上，與其他支架（例如 Top-K、EvoX）搭配時有所提升，展現其在不同演化式搜尋支架上的適用性。

### 核心貢獻（3～5點）
- 提出 EvoDuet 雙層共同演化方法，在固定模型參數下同步演化候選解與搜尋查詢，解決 LLM 因外部知識不足而停滯的問題。
- 設計檢索閘門機制，使 LLM 能自主評估知識落差，動態決定檢索新文件、重用既有文件或無需檢索。
- 內外迴圈分工協作：內迴圈依預期候選解分數排序文件，外迴圈平行產生候選解並回饋評估結果，形成雙層優化閉環。
- 在 21 個優化任務上驗證成效，於 GPT-5.6-Luna 與 Gemini-3.8-Fash 模型上顯著提升 OpenEvolve 的 NDG，並在八個任務中刷新最佳紀錄。
- 證明方法可跨支架通用，於 Top-K、EvoX 等不同演化式搜尋框架上同樣有效。

### 適合對象
從事自動化科學發現、LLM 驅動之程式碼演化、檢索增強生成（RAG）與最佳化搜尋演算法研究的學者與工程師；以及對 AI 輔助研究、演化計算與知識檢索整合應用感興趣的產業界實務人員。

## 深度分析

#### 方法論解析

EvoDuet 的核心設計在於將「解的演化」與「查詢的演化」解耦為兩個相互耦合的迴圈，並透過一個基於知識落差（knowledge gap）的檢索閘門（retrieval gate）來銜接二者。這種雙層共同演化（bilevel co-evolution）的設計哲學源自一個關鍵觀察：傳統的 LLM 驅動演化式搜尋（evolutionary search）是一個「封閉系統」，僅仰賴兩種知識來源——執行的演化歷史與模型的參數化知識（parametric knowledge）——當任務需要模型本身不具備的外部知識時，搜尋便會停滯（stagnation）。

**雙層架構的具體運作：**

1. **外迴圈（outer loop）**：負責候選解（candidate solution）的生成與評估。在每次迭代中，給定一組經過排序的文件，外迴圈以平行方式生成候選解，並由評估器（evaluator）給分。評估結果會被記錄下來，與對應的文件配對，作為後續內迴圈查詢的「歷史證據」。

2. **內迴圈（inner loop）**：負責查詢的精煉與文件的排序。內迴圈並不評估任何候選解，而是透過「假設性證據評分」（hypothetical evidence scoring）來預測每份文件若被用於建構候選解，可能得到的評估分數。這種設計避免了昂貴的實際評估，使查詢空間的搜尋更為高效。

3. **檢索閘門（retrieval gate）**：這是連接兩個迴圈的關鍵元件。LLM 在每次迭代時評估自身的知識落差，並在三種行動中選擇：(a) 檢索新文件、(b) 重用已儲存的文件（look-up）、(c) 不使用文件直接進行。這種動態決策機制避免了「無腦呼叫搜尋工具」的問題——論文中指出，僅僅加入網路搜尋工具往往會反覆返回相同的頁面，因為查詢本身沒有隨解的演進而調整。

**迴圈堆疊（loop packing）的設計理念：**

論文將 EvoDuet 定位為一種新的迴圈堆疊設計。現有的支架（scaffold）如 EvoX 加入了策略迴圈（strategy loop），而 EvoDuet 則加入了搜尋迴圈（search loop）。這種模組化設計使得 EvoDuet 可以與其他迴圈共存，例如論文中展示了 EvoDuet 與 Top-K 和 EvoX 結合時，在 Sums/Diffs 與 Denoising 任務上仍能帶來改善，證明了其通用性。

**知識狀態（knowledge state）的維護：**

內迴圈維護一個知識狀態，記錄已檢索文件的摘要與其預測分數。這個狀態會隨著外迴圈的評估結果而更新，形成一個持續學習的循環。值得注意的是，模型參數在整個過程中是固定的（fixed model parameters），所有「學習」都發生在外部的知識狀態中，這使得方法可以與任何 LLM 結合使用。

#### 實驗數據解讀

**整體效能提升：**

在 21 個最佳化任務上，使用 OpenEvolve 支架時，EvoDuet 將平均標準化發現增益（Normalized Discovery Gain, NDG）從以下數值提升：
- GPT-5.6-Luna：74.1% → 78.0%（提升 3.9 個百分點）
- Gemini-3.8-Flash：61.3% → 82.3%（提升 21.0 個百分點，幅度驚人）
- Qwen3.5-9B：未受益

這個結果揭示了一個重要的模型能力差異：共同演化需要模型同時具備「找到證據」與「應用證據」兩種能力。Qwen3.5-9B 雖然在使用預知文件（oracle documents）時能提升 10.3%，但在 EvoDuet 中卻未受益，因為它在 26% 的修訂中將檢索到的方法「未使用或錯誤實作」。

**SOTA 達成情況：**

EvoDuet 的最佳執行結果在 8 個任務上超越了先前報導的最佳分數，並在另外 3 個任務上與之持平。其中最引人注目的是 Q20 上的交換縮減（Swap Reduction）任務——EvoDuet 達到 14,835 個 SWAP，比 SimpleTES（WILL Team, 2026）的 15,186 少 2.31%，在相同的評估器下創下了新的 SOTA。在 Denoising 任務上，EvoDuet 以約 6.9 倍低的估計成本超越了 SimpleTES。

**預知文件實驗的啟示：**

圖 3 展示了在 31 個任務上，使用預知文件（oracle documents）對 OpenEvolve 的影響。這個實驗回答了一個關鍵問題：「如果文件是完美的，會怎樣？」結果顯示：
- 預知文件對 Qwen3.5-9B 的幫助（+10.3%）大於對 GPT-5.6-Luna 的幫助（+4.0%）
- 任務難度影響顯著：在「幾乎解決」的任務上，預知文件幾乎無效；在「部分解決」的任務上，幫助最大
- 並非所有任務都受益：Swap 受益顯著（+41.5 for Luna），但 Rosetta 反而退化（-23.3）

這個實驗說明了兩個重要現象：(1) LLM 需要「探索空間」才能利用外部知識——在 Sums/Diffs 上，預知文件只有在生成 8 個候選解（而非 1 個）時才有幫助；(2) 查詢必須隨解共同演化——在 Denoising 上，若僅在解迴圈內搜尋，88.1% 的返回 URL 是已見過的頁面，並在 50 次迭代後停止改善。

**文件使用行為分析：**

論文中分析了六種文件使用行為，其中「方法轉移」（method transfer）最為常見——模型將檢索到的方法應用於自己的解中（82 次迭代中有 55 次）。圖 2 展示了 Q20 上的兩個具體例子：在迭代 5，模型從 dSABRE 論文中學到「對靠近前端的閘門賦予更高權重」的概念；在迭代 66，模型從 SabreSwap 文件中學到「懲罰反轉最後一次 SWAP」的衰減規則。

**統計顯著性與改進預測：**

論文報告了一個有趣的統計：當檢索到的文件被預測能擊敗父代時，67.1% 的迭代中候選解確實優於父代；而無文件時僅 52.1%。這證明了假設性證據評分機制的有效性——它不僅是排序文件的工具，更是一個可靠的改進預測器。

#### 與現有研究的比較

**與 OpenEvolve 的比較：**

OpenEvolve（Sharma, 2025）是 EvoDuet 的基礎支架，僅運行解迴圈。EvoDuet 在不改變 OpenEvolve 核心機制的情況下，透過加入搜尋迴圈來擴展其能力。這種「外掛式」設計使得 EvoDuet 可以直接受益於 OpenEvolve 的未來改進。

**與 EvoX 的比較：**

EvoX（Liu et al., 2026a）加入了策略迴圈，當進度停滯時修訂搜尋策略。EvoDuet 與 EvoX 的關係是互補的——前者處理「缺乏外部知識」的問題，後者處理「搜尋策略不當」的問題。論文中展示了兩者結合的可行性，這暗示未來可能出現同時包含三種迴圈（解、策略、搜尋）的更強大支架。

**與 FunSearch、AlphaEvolve 的比較：**

Romera-Paredes et al. (2024) 的 FunSearch 與 Ouyang et al. (2025) 的 AlphaEvolve 都是 LLM 驅動的演化式搜尋系統，但它們同樣依賴封閉的知識來源。EvoDuet 的貢獻在於首次系統性地將「開放搜尋」整合進這類系統，這對於需要最新文獻支援的科學發現任務尤為重要。

**與一般 RAG 系統的比較：**

EvoDuet 與傳統的檢索增強生成（RAG）系統有本質差異。傳統 RAG 通常是單次或固定次數的檢索，而 EvoDuet 將檢索本身變成了一個被優化的對象。內迴圈中的查詢精煉與文件排序機制，使得搜尋過程能夠自我調整，這在現有的 RAG 文獻中較為少見。

**限制與不足：**

1. **模型依賴性**：Qwen3.5-9B 的失敗案例顯示，EvoDuet 並非對所有 LLM 都有效。這限制了方法的普適性。
2. **計算成本**：雖然論文中提到 Denoising 任務的成本降低，但整體上 EvoDuet 需要更多的 LLM 呼叫（內迴圈的查詢生成與文件評分），這在某些場景下可能成為瓶頸。
3. **搜尋品質依賴**：方法的效能上限受限於網路搜尋引擎返回的文件品質。對於小眾或新興領域，可能缺乏高品質的線上資源。
4. **評估器假設**：方法假設存在一個可靠的評估器，這在許多實際科學問題中並不總是成立。

#### 可重現性評估

**程式碼與資料：**

根據論文提供的資訊，EvoDuet 是建立在 OpenEvolve 之上的開源系統。論文中明確提到了多個基準任務（Q20、Rosetta、Sums/Diffs、Denoising 等），這些任務的評估器應該是可獲取的。然而，論文中並未明確提供程式碼倉庫的 URL，這對完全重現實驗結果構成了一定障礙。

**模型權重：**

實驗使用了三個 LLM：GPT-5.6-Luna（推測為 GPT-5 系列變體）、Gemini-3.8-Flash（推測為 Gemini 系列變體）、Qwen3.5-9B（開源模型）。其中 Qwen3.5-9B 的權重應該可以從 Hugging Face 等平台獲取，但前兩個模型的具體版本與權重可獲得性需要進一步確認。

**實驗細節：**

論文提供了豐富的實驗細節，包括：
- 21 個任務的具體清單
- 每個任務的迭代次數
- NDG 的計算方式
- 不同支架（OpenEvolve、Top-K、EvoX）的整合方式
- 預知文件實驗的完整設置

這些細節有助於其他研究者重現主要結果。但內迴圈中查詢精煉的具體提示詞（prompt）、假設性證據評分的計算方式等實現細節，需要從附錄或程式碼中獲取。

**可重現性的主要障礙：**

1. 缺乏明確的程式碼倉庫連結
2. 部分使用的 LLM 版本可能尚未公開
3. 網路搜尋的結果具有時效性，不同時間點的搜尋可能返回不同文件
4. 評估器的具體實作可能存在版本差異

#### 未來研究方向

**1. 多模態知識整合：**

目前的 EvoDuet 主要處理文字形式的網路文件。未來可以擴展至整合程式碼倉庫（如 GitHub）、影片教學、學術資料庫等多模態知識來源，這對於跨領域的科學發現任務尤為重要。

**2. 理論分析與收斂性保證：**

論文中缺乏對 EvoDuet 收斂性的理論分析。雖然實驗結果令人鼓舞，但建立雙層共同演化在何種條件下能保證收斂的理論框架，將有助於方法的進一步發展與應用。

**3. 與人類專家的協作：**

論文將「人工迴圈」（human loop）列為迴圈堆疊的一種可能設計，但未深入探討。未來可以研究如何讓 EvoDuet 在關鍵決策點（如檢索閘門的判斷）引入人類專家的反饋，形成真正的人機協作科學發現系統。

**4. 領域特定的知識庫整合：**

對於特定科學領域（如藥物發現、材料科學），可以建立領域特定的知識庫，並設計專門的文件排序機制。這將比通用的網路搜尋更有效率，也更能避免噪音文件的干擾。

**5. 效率優化：**

內迴圈中的假設性證據評分需要 LLM 進行多次推理，這在計算上是昂貴的。未來可以研究如何用更輕量的模型（如小型評分模型）來加速這個過程，或設計批次評分機制來減少 LLM 呼叫次數。

**6. 失敗模式分析與除錯工具：**

Qwen3.5-9B 的失敗案例（26% 的修訂未使用或錯誤實作檢索方法）揭示了方法的一個重要限制。未來可以開發專門的除錯工具，幫助研究者診斷為何某些模型無法有效利用檢索到的證據，並設計相應的補救機制。

**7. 長期演化與記憶機制：**

目前的知識狀態在單次執行中維護，但跨執行的知識累積同樣重要。可以研究如何將一次執行中學到的知識持久化，並在後續執行中重用，這將使系統能夠在更長時間尺度上進行科學發現。

**8. 安全性與偏誤考量：**

當 LLM 從網路檢索資訊時，可能引入錯誤資訊或偏誤。未來需要研究如何設計機制來驗證檢索內容的可靠性，並在面對矛盾資訊時做出合理的判斷，這對於科學發現的嚴謹性至關重要。

**9. 與其他迴圈的深度整合：**

論文展示了 EvoDuet 可以與 Top-K 和 EvoX 結合，但這種結合是相對表面的。未來可以研究更深入的整合方式，例如讓搜尋迴圈的結果直接影響策略迴圈的決策，或讓策略迴圈動態調整搜尋的頻率與深度。

**10. 基準測試的擴展：**

目前的 21 個任務雖然涵蓋了多個領域，但相對於科學發現的廣闊空間仍屬有限。建立更大規模、更多樣化的基準測試集，將有助於更全面地評估 EvoDuet 及其後續方法的效能。

## 論文問答

**Q1：為什麼基於 LLM 的演化式搜尋（Evolutionary Search）會停滯？這個問題的根本原因是什麼？**

A：基於 LLM 的演化式搜尋之所以會停滯，根本原因在於其「封閉性」（closed）特性——現有的支架（scaffold）如 OpenEvolve、EvoX 等都僅依賴兩個知識來源：執行的演化歷史以及 LLM 自身的參數化知識（parametric knowledge）。當任務進展需要這兩個來源都未涵蓋的外部知識時（例如新版本函式庫的使用方式），搜尋就會陷入停滯。這種封閉性使得 LLM 無法像人類科學家那樣，透過查閱文獻來突破知識邊界。論文中以「迴圈堆疊」（Loop Packing）的概念來描述這個問題，強調現有方法即使加入策略迴圈或人工迴圈，仍無法突破知識來源的封閉性。

**Q2：為什麼簡單地加入網路搜尋工具無法解決這個停滯問題？**

A：僅僅加入網路搜尋工具並不足夠，因為搜尋查詢本身也需要隨著解決方案的演進而調整。論文的初步分析顯示，在 Denoising 任務中，若直接在解迴圈內進行搜尋，模型有 88.1% 的機率會反覆取回已經看過的 URL，並在 50 次迭代後停止進步。此外，搜尋結果的相關性也會隨解決方案的演進而改變——同一份文件在早期可能有用，但在後期可能變得不相關。因此，搜尋必須與解決方案共同演化（co-evolve），而非作為一個靜態的附加工具，這也是 EvoDuet 設計的核心動機。

**Q3：為什麼這個問題對科學發現（Scientific Discovery）特別重要？**

A：科學發現本質上是一個需要不斷吸收外部知識的過程，人類科學家在研究過程中會反覆查閱文獻、搜尋新資訊，以填補隨進展而出現的知識落差。論文中提到 EvoDuet 在量子編譯的 Swap Reduction 任務上找到了新的 SOTA（14,835 Q20 SWAPs），比 SimpleTES 少 2.31%，這正是因為模型從 arXiv 上的 dSABRE 論文和 IBM Quantum 的 SabreSwap 文件中轉移了方法（method transfer）。如果 LLM 驅動的搜尋無法像人類一樣開放地獲取知識，那麼它在科學發現上的應用將受限於其訓練時的知識邊界，無法處理需要最新文獻支援的研究問題。

**Q4：EvoDuet 的雙層優化（Bilevel Optimization）是如何運作的？內迴圈與外迴圈各扮演什麼角色？**

A：EvoDuet 採用雙層優化架構，在 LLM 參數固定的前提下，讓解決方案與搜尋查詢共同演化。內迴圈（Inner Loop）負責演化查詢：根據當前的知識狀態（knowledge state）與知識落差，構造針對性的搜尋查詢，並透過假設性證據評分（hypothetical evidence scoring）對檢索到的文件進行排序，預測每份文件能帶來的評估器分數。外迴圈（Outer Loop）則基於這些文件平行生成候選解，並記錄實際評估結果，用於指導後續的搜尋。兩個迴圈透過檢索閘門（Retrieval Gate）相連，閘門讓 LLM 評估自身知識缺口並決定動作——檢索新文件、重用已儲存文件，或不使用文件繼續進行。

**Q5：檢索閘門（Retrieval Gate）的設計理念是什麼？為什麼這個機制是必要的？**

A：檢索閘門的設計理念是讓 LLM 自主評估其知識缺口（knowledge gap），並據此決定是否需要外部資訊。這個機制的必要性來自於一個關鍵觀察：並非每次迭代都需要新文件，過度檢索反而會引入噪音並浪費資源。閘門提供三種動作選項：Retrieve（檢索新文件）、Look-Up（重用已儲存文件）、或不檢索而直接進行，這使得搜尋過程更加靈活且高效。論文中圖 2 展示了在第 64 次迭代時，閘門選擇重用已儲存文件而非進行新搜尋，這顯示了閘門能夠辨識哪些資訊已經足夠，從而避免重複搜尋並提升整體效率。

**Q6：假設性證據評分（Hypothetical Evidence Scoring）是什麼？為什麼這個設計對 EvoDuet 至關重要？**

A：假設性證據評分是一種預測機制，用於在不實際評估候選解的情況下，預測每份檢索文件能帶來的評估器分數。這個設計至關重要的原因在於：內迴圈需要快速篩選大量檢索結果，若每份文件都要生成並評估候選解，計算成本將無法承受。透過讓 LLM 預測「基於此文件生成的候選解可能的分數」，內迴圈可以高效地對文件排序，選出最有潛力的 Top-K 文件傳遞給外迴圈。這種設計也讓查詢演化有了明確的目標——最大化預測分數，從而形成一個自我強化的學習循環，使搜尋越來越精準地針對當前瓶頸。

**Q7：實驗使用了哪些基準任務？為什麼選擇這些任務來評估 EvoDuet？**

A：實驗涵蓋了 21 個優化任務，包括量子編譯領域的 Swap Reduction（Q20、Rosetta）、生物資訊的單細胞 RNA 序列去噪（Denoising）、數學的 Erdős 最小重疊問題（Sums/Diffs）、GPU 核心設計等多樣化領域。選擇這些任務的原因在於它們都具有「可評分但無法直接計算最優解」的特性，這正是演化式搜尋的典型應用場景。此外，這些任務涵蓋了不同的知識需求——有些需要最新的函式庫知識，有些需要特定領域的演算法原理，這使得評估 EvoDuet 在不同知識落差情境下的表現更為全面。論文中特別強調 EvoDuet 在 8 個任務上超越了先前最佳紀錄，並在 3 個任務上與之持平。

**Q8：EvoDuet 在不同 LLM 上的表現差異說明了什麼？為什麼 Qwen3.5-9B 無法受益？**

A：EvoDuet 在不同 LLM 上的表現呈現顯著差異：GPT-5.6-Luna 的平均 NDG 從 74.1% 提升至 78.0%，Gemini-3.8-Flash 從 61.3% 大幅提升至 82.3%，但 Qwen3.5-9B 則未能受益。這個差異揭示了共同演化對模型能力的雙重要求——模型不僅需要能「找到」相關證據，還需要能「應用」這些證據到解決方案中。論文的分析顯示，Qwen3.5-9B 在 26% 的修訂中未使用或錯誤使用了檢索方法，這說明較小的模型可能在「方法轉移」（method transfer）的能力上有所不足。值得注意的是，即使提供預知文件（oracle documents），Qwen3.5-9B 仍能受益（+10.3% NDG），這進一步證明了瓶頸在於模型的應用能力而非檢索能力。

**Q9：預知文件（Oracle Documents）實驗揭示了哪些關於外部知識與 LLM 搜尋的洞見？**

A：預知文件實驗揭示了兩個關鍵洞見。首先，外部知識確實有助於 LLM 驅動的搜尋——在 31 個任務上，Qwen3.5-9B 的平均 NDG 提升了 10.3%，GPT-5.6-Luna 提升了 4.0%，證明了知識落差是真實存在的瓶頸。其次，將知識轉化為進展需要的不僅是文件本身，還需要兩個條件：足夠的探索空間（exploration room）以及隨解決方案演化的查詢。具體而言，在 Sums/Diffs 任務上，預知文件只有在每個迭代生成 8 個候選解而非 1 個時才有幫助；而在 Denoising 任務上，靜態的搜尋會反覆取回相同頁面（88.1% 的 URL 重複）。這些發現強調了 EvoDuet 雙層共同演化設計的必要性——單純提供好文件是不夠的，必須讓查詢與解決方案同步演進。

**Q10：EvoDuet 在實際科學發現中的應用場景有哪些？能否舉出具體例子？**

A：EvoDuet 在多個科學發現場景中展現了實際價值，其中最顯著的是量子編譯領域的 Swap Reduction 任務。論文中展示了一個具體案例：模型從 arXiv 上的 dSABRE 論文中學習到「對靠近前方的閘位賦予更高權重」的衰減原則，並將其應用於 Q20 編譯器；在第 66 次迭代時，又從 IBM Quantum 的 SabreSwap 文件中學習到「懲罰反轉最後一次 SWAP」的規則，最終達到 14,835 Q20 SWAPs 的新 SOTA。此外，在 Denoising 任務上，EvoDuet 以約 6.9 倍更低的估計成本超越了 SimpleTES，顯示其在生物資訊領域的應用潛力。這些案例表明 EvoDuet 特別適合需要跨領域知識轉移的研究任務。

**Q11：EvoDuet 對其他演化搜尋支架（如 EvoX、Top-K）的適用性如何？這代表什麼意義？**

A：EvoDuet 展現了良好的通用性，能夠與其他演化搜尋支架結合使用。論文中提到 EvoDuet 改善了 Top-K 和 EvoX 在 Sums/Diffs 與 Denoising 任務上的表現，這代表著搜尋迴圈可以被「堆疊」（packed）在現有的迴圈之上。這種模組化設計的意義在於：研究人員不需要從零開始建構系統，而是可以將 EvoDuet 作為一個外掛層，整合到他們已有的演化搜尋框架中。這也呼應了論文中提出的「迴圈堆疊」（Loop Packing）設計哲學——透過組合解迴圈、搜尋迴圈、策略迴圈等不同層級的迴圈，可以建構出更強大的科學發現系統。

**Q12：EvoDuet 對科學發現領域的整體影響是什麼？它如何改變研究方法學？**

A：EvoDuet 對科學發現領域的影響主要體現在三個層面。首先，它將「開放式搜尋」（open search）的概念引入 LLM 驅動的科學發現，使模型能夠像人類科學家一樣動態地獲取外部知識。其次，論文中提到 EvoDuet 在 Denoising 任務上以 6.9 倍更低的成本達到超越 SimpleTES 的表現，這顯示其在計算效率上的優勢——透過更精準的搜尋，減少了無效的候選解評估。最後，EvoDuet 的成功挑戰了「更大模型就一定更好」的假設——Gemini-3.8-Flash 的表現提升（+21.0% NDG）反而比 GPT-5.6-Luna（+3.9%）更為顯著，說明模型與搜尋機制的協作比單純的模型規模更為重要。

**Q13：EvoDuet 的主要限制是什麼？這些限制對實際應用有何影響？**

A：EvoDuet 的主要限制在於其對底層 LLM 能力的依賴——如前所述，Qwen3.5-9B 無法從共同演化中受益，這意味著 EvoDuet 並非對所有模型都有效。此外，論文中提到 EvoDuet 在每個迭代僅生成 1 個候選解時表現最佳，但這也限制了探索的多樣性；雖然平行生成可以進一步提升表現，但會增加計算成本。另一個潛在限制是對網路搜尋品質的依賴——若搜尋引擎無法返回相關文件，或文件品質不佳，內迴圈的預測機制也將受到影響。這些限制意味著 EvoDuet 在實際部署時需要仔細評估模型選擇、計算資源配置以及搜尋環境的品質。

**Q14：失敗案例揭示了哪些關於 LLM 應用外部知識的洞見？**

A：失敗案例揭示了 LLM 在應用外部知識時的兩個主要問題：未使用（unused）與錯誤實施（misimplemented）。論文中指出 Qwen3.5-9B 在 26% 的修訂中出現這類問題，這說明檢索到相關文件並不代表模型能正確地將其中的方法轉移到自己的解決方案中。此外，論文中也分析了「方法轉移」（method transfer）是文件被使用的最常見方式（55/82 次），這暗示了 LLM 在面對新知識時，往往傾向於借用具體方法而非抽象原理。這些洞見對未來的研究方向有重要啟示——單純提升檢索品質是不夠的，還需要增強模型對檢索內容的理解與轉化能力。

**Q15：基於 EvoDuet 的研究，未來有哪些值得探索的方向？**

A：基於 EvoDuet 的研究，未來有幾個值得探索的方向。首先，可以研究如何讓較小的模型（如 Qwen3.5-9B）也能從共同演化中受益，這可能需要新的訓練方法或專門設計的提示工程來增強「方法轉移」能力。其次，可以將 EvoDuet 的雙層架構擴展到更多類型的外部資源，例如程式碼儲存庫、實驗資料庫或科學論文資料庫，而不僅限於網頁搜尋。此外，論文中提到的「迴圈堆疊」概念暗示了未來可以探索更多層級的迴圈組合，例如加入反思迴圈（reflection loop）或驗證迴圈（verification loop）。最後，將 EvoDuet 應用於更廣泛的科學發現任務（如藥物設計、材料科學）也是一個重要的方向，這需要評估其在不同領域知識結構下的適應性。

## 實務應用指南

### 適用場景

EvoDuet 適用於「需要外部知識、且具備可量化評估函式」的程式碼或演算法優化任務。以下列舉五個具體的實務場景：

1. **量子電腦編譯器優化**：在量子線路編譯中，需要將邏輯閘映射到實體硬體並縮減 SWAP 閘數量。EvoDuet 可自動從 arXiv 與技術文件中擷取最新的 SABRE、dSABRE 等路由演算法原理，並將其移植到自有的 Rust 編譯器中（論文 Figure 2 即為此案例）。

2. **GPU 核心程式碼自動生成**：針對特定張量操作或卷積運算，自動搜尋比現有 CUDA/HIP 函式庫更快的核心實作。當模型缺乏新版硬體特性（如 Hopper 架構的 TMA 指令）時，可透過網路搜尋擷取官方文件並整合進候選解。

3. **生物資訊學中的單細胞 RNA 序列去噪**：當 scRNA-seq 去噪方法快速演進（如 MAGIC、scVI、SAUCIE 等），EvoDuet 可協助研究人員持續吸收新方法並整合到既有管線中，論文中 EvoDuet 在 Denoising 任務上以 6.9 倍低成本超越 SimpleTES。

4. **數學組合最佳化問題**：例如 Erdős 最小重疊問題、排程問題、組合設計問題等。當模型參數化知識不足以推導新構造時，可透過搜尋最新數學論文取得靈感。

5. **企業內部演算法現代化**：將舊有 C/C++ 程式碼移植到新版函式庫（例如從 OpenCV 3 升級到 OpenCV 5、或從 TensorFlow 1 升級到 PyTorch 2），EvoDuet 可自動搜尋 API 變更文件並產生可運行的候選解。

### 實作前置條件

**資料面**
- **任務評估器**：必須具備可量化評分任意候選解的函式（如編譯時間、SWAP 數量、去噪 MSE 等），且評估需在合理時間內完成（單次評估建議 < 10 分鐘）。
- **初始程式碼**：一個可執行的 baseline 程式作為演化起點。
- **領域文件來源**：可存取的網路搜尋 API（如 Serper、Bing Search、Google CSE），以及可選的領域文件庫（arXiv、官方文件、GitHub Issues）。

**運算面**
- **LLM API 存取**：需具備 GPT-5.6-Luna、Gemini-3.8-Flash 等具備足夠推理能力的模型 API。論文顯示 Qwen3.5-9B 等較小模型無法受益，需謹慎選擇。
- **平行運算資源**：外迴圈採候選解平行生成，建議配置至少 8 個並行 LLM 呼叫的配額。
- **儲存空間**：用於保存「知識狀態」（已檢索文件、預測分數、評估結果），單次任務建議預留 1–10 GB。

**技能面**
- **LLM 提示工程**：需設計檢索閘門的決策提示、查詢建構提示、文件排序提示。
- **演化演算法基礎**：理解錦標賽選擇、變異率、人口管理等概念。
- **Python 程式設計**：主要實作語言；候選解本身可用任何語言（Rust、C++、CUDA 等）。
- **領域知識**：對目標任務（如量子編譯、生物資訊）有基本理解，以便設計評估器與審查輸出。

### 實作步驟建議

**步驟 1：建立任務評估器與 baseline**
- 撰寫可重現的評估腳本，輸出單一數值分數。
- 確認 baseline 程式可被 LLM 讀取並修改（建議 < 500 行程式碼）。
- 設定迭代上限（論文使用約 100–200 次迭代）。

**步驟 2：整合 LLM 與 OpenEvolve 支架**
- 安裝 OpenEvolve 並設定 LLM API 金鑰。
- 設定每次迭代的候選解數量（論文實驗顯示 1 個即可，但 8 個在 Sums/Diffs 上表現更佳）。

**步驟 3：實作檢索閘門（Retrieval Gate）**
- 設計提示詞讓 LLM 評估「知識落差」並輸出三種決策之一：`Retrieve`（檢索新文件）、`Look-Up`（重用已儲存文件）、`None`（不需文件）。
- 將決策結果以結構化格式（如 JSON）解析。

**步驟 4：實作內迴圈（查詢演化）**
- 根據知識落差建構初始查詢，送至搜尋 API。
- 對返回的文件進行「假設性證據評分」（hypothetical evidence scoring）：讓 LLM 預測「若基於此文件產生候選解，預期分數為何」。
- 依預測分數排序，保留 Top-K 文件進入下一輪查詢（最多 3 輪）。
- 將最終文件與預測分數寫入「知識狀態」。

**步驟 5：實作外迴圈（解演化）**
- 給定 Top-K 文件，平行生成候選解。
- 評估每個候選解並記錄「文件 → 實際分數」對應關係。
- 將高分解加入錦標賽選擇池，淘汰低分者。

**步驟 6：整合到現有支架（可選）**
- 若使用 EvoX，可在策略迴圈之外再包一層 EvoDuet 的搜尋迴圈。
- 若使用 Top-K 選擇，可在選擇階段引入文件資訊。

**步驟 7：評估與調校**
- 計算 Normalized Discovery Gain (NDG) 與 baseline 比較。
- 分析檢索命中率（論文顯示 67.1% 的「預測高分文件」能產生優於父代的子代）。
- 監控文件重複率（若 > 80% 表示查詢演化失效，需調整內迴圈）。

**步驟 8：部署與監控**
- 將訓練好的最佳解部署至生產環境。
- 持續監控評估器分數，並定期重啟 EvoDuet 以吸收新知識。

### 潛在風險與注意事項

**風險 1：模型能力不足導致無法受益**
- **現象**：論文顯示 Qwen3.5-9B 即使在 oracle 文件加持下仍無法進步，26% 的修訂出現「未使用或誤用檢索方法」。
- **緩解**：僅使用 GPT-5.6-Luna、Gemini-3.8-Flash 等較強模型；或在小型模型上加裝「方法驗證步驟」，讓 LLM 在套用前先解釋文件內容。

**風險 2：檢索文件重複導致停滯**
- **現象**：在 Denoising 任務中，88.1% 的返回 URL 為已見頁面，50 次迭代後即停滯。
- **緩解**：在內迴圈加入「查詢多樣性懲罰項」，強制探索新關鍵字；或設定 URL 黑名單。

**風險 3：評估器過擬合**
- **現象**：候選解可能在評估器上分數極高，但在真實環境失效。
- **緩解**：使用多個評估指標（如速度 + 記憶體 + 正確性）；保留 holdout 測試集。

**風險 4：計算成本失控**
- **現象**：每個迭代需呼叫 LLM 數次（檢索決策 + 查詢建構 + 文件評分 + 候選生成），長任務可能耗費數千美元。
- **緩解**：設定預算上限；對簡單迭代跳過檢索（`None` 決策）；使用較小模型處理例行步驟。

**風險 5：文件版型不一致**
- **現象**：網路文件品質參差，可能包含過時或錯誤資訊。
- **緩解**：在文件評分階段加入「可信度因子」（如官方文件 > 部落格）；對預測分數低於閾值的文件直接丟棄。

**風險 6：知識狀態膨脹**
- **現象**：隨迭代增加，儲存的文件與預測分數累積，可能拖慢查詢演化。
- **緩解**：定期對知識狀態做蒸餾或摘要；只保留 Top-N 高分文件。

### 與其他技術的整合建議

**與 OpenEvolve 整合**
- EvoDuet 是 OpenEvolve 的外掛模組，可直接替換其內部的 LLM 呼叫流程。
- 建議保留 OpenEvolve 的錦標賽選擇與變異機制，僅在「產生候選解前」插入檢索閘門與內迴圈。

**與 EvoX 整合**
- EvoX 的策略迴圈負責調整搜尋策略，EvoDuet 的搜尋迴圈負責補充外部知識，兩者互補。
- 實作上可將 EvoDuet 視為 EvoX 的「知識提供者」，在策略迴圈決定「需要新知識」時觸發。

**與 RAG 系統整合**
- EvoDuet 的「知識狀態」本質上是一個動態 RAG 索引，可與企業既有向量資料庫（如 Pinecone、Weaviate）整合。
- 將「假設性證據評分」對應到 RAG 的 reranker 階段，可直接複用現有基礎設施。

**與人類專家迴圈整合**
- 當 EvoDuet 連續 N 次迭代未產生新最佳解時，可觸發「人工迴圈」通知專家審查。
- 專家的回饋可作為新的「oracle 文件」注入知識狀態，加速後續搜尋。

**與 CI/CD 整合**
- 將 EvoDuet 包裝為 GitHub Action 或 GitLab CI 階段，在每次程式碼變更後自動跑優化。
- 評估器分數可作為合併請求的品質門檻。

**與多代理系統整合**
- 可將「檢索閘門」、「查詢建構」、「文件評分」、「候選生成」拆分給不同代理，實現更細粒度的角色分工。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的「Loop Packing」概念（Figure 1）以理解 EvoDuet 在演化式搜尋中的定位，再看 Figure 2 的 Swap Reduction 範例以建立直觀印象。內迴圈與外迴圈的細節可暫時略過，重點掌握「讓 LLM 自己決定何時需要查資料」這個核心思想即可。

**給 AI 工程師**：直接從第 3 節的演算法細節讀起，特別關注「檢索閘門的提示詞設計」、「假設性證據評分的實作方式」、「知識狀態的資料結構」。建議動手實作一個最小可行版本（MVP），先在 Sums/Diffs 或 Denoising 等小型任務上驗證，再逐步擴展到量子編譯等複雜場景。注意論文中 Qwen3.5-9B 失敗的案例，避免在小型模型上浪費時間。

**給研究人員**：第 4 節的實驗結果與第 5 節的行為分析是重點。特別關注「方法轉移」（method transfer）佔 55/82 次迭代這個數據，以及「oracle 文件幫助但自動搜尋未必」的張力。可考慮的延伸方向包括：將 EvoDuet 應用於多模態任務、引入強化學習自動調整檢索閘門閾值、或理論分析內外迴圈的收斂性。

**給產品經理**：重點閱讀第 1 節的動機（為何現有方法會停滯）與第 4 節的商業價值（8 個任務超越 SOTA、Denoising 任務成本降低 6.9 倍）。理解 EvoDuet 的核心價值主張是「讓 AI 系統具備自主學習新知識的能力」，而非單純的程式碼生成工具。在評估導入時，應優先考慮「評估器明確且外部知識快速演進」的場景，例如內部工具現代化、技術債務清理等。
