AscendGYM 的方法論設計圍繞三個核心問題展開：評估任務如何設計、評估如何可靠、優化效能如何衡量。這三個問題對應了基準測試 (benchmark) 的任務定義、執行基礎設施與評分機制三個層面。

**任務設計層面**：與 KernelBench、NPUKernelBench、CANN Bench 等以「核心生成 (kernel generation)」為目標的基準測試不同，AscendGYM 採取「核心優化 (kernel optimization)」的視角——給定一個已正確的核心實作，要求代理 (agent) 在預算 (budget) 內進一步提升其在特定工作負載下的效能。這一設計反映了真實工程場景：開發者通常從現有程式碼出發，分析效能瓶頸 (performance bottleneck)，反覆修改並驗證。任務的輸入配置 (input configuration)——包括張量形狀 (tensor shape)、資料型別 (data type)、計算參數——均採集自真實的訓練與推理工作負載 (real workload)，而非合成資料。這使得基準測試的效能提升能直接對應到實際應用情境。例如，預填充 (prefill) 與解碼 (decoding) 階段的注意力運算 (attention computation) 因資料規模差異而傾向不同的計算組織方式，AscendGYM 透過從真實軌跡 (workload trace) 抽取配置來捕捉這種差異。

**執行基礎設施層面**：AscendGYM 內建 AscendForge 沙盒 (sandbox)，將候選實作的編譯 (compilation)、正確性檢查 (correctness checking) 與效能測量整合為可程式化存取的評估服務。這個設計回應了「修改後程式碼是否編譯成功、產生正確結果、執行更快」必須分別透過實際執行來驗證的需求。在 Ascend NPU 上，這個過程涉及主機端程式碼 (host code) 與裝置端程式碼 (device code) 的協調建置，AscendForge 將這些步驟封裝為統一介面，並記錄優化軌跡 (optimization trajectory) 以支援迭代式代理優化與結果驗證。

**評分機制層面**：論文提出 Speedup-Token Score (STS，加速率-代幣分數) 作為核心指標。STS 的設計動機在於：兩個系統可能達到相同的最終加速率 (speedup)，但所需的搜尋投入截然不同——一個可能在少數嘗試內找到改進，另一個則需要大量搜尋。STS 將預算內的效能提升與每次改進所累積的代幣消耗 (token cost) 結合，使評估能在資源約束下反映實際的優化能力。論文同時單獨報告效能、資源消耗與正確性三類指標，以區分「達成的提升」、「投入的資源」與「是否通過驗證」。

**評估模式層面**：AscendGYM 支援兩種模式——模型評估 (model evaluation) 與模型-框架評估 (model-harness evaluation)。前者使用預設框架 (default harness) 比較不同模型，後者將模型與自訂框架作為完整系統評估。這種區分允許研究者分別衡量模型本身的優化能力，以及模型搭配特定搜尋編排 (search orchestration) 與經驗累積 (experience accumulation) 機制後的整體表現。

#### 實驗數據解讀

論文報告了 17 個 Batch 1 任務上多個領先模型搭配常用框架的系統性評估結果。最關鍵的發現是：約 70% 的評估組合在幾何平均加速率 (geometric mean speedup) 上低於 1.2×。這個數字揭示了兩個重要訊息：首先，在現有實作基礎上取得顯著加速仍然困難——1.2× 的門檻意味著僅 20% 的效能提升，這對許多已高度優化的核心而言已是實質改進；其次，問題的難度具有普遍性，而非僅限於少數困難案例。

不同預算下的增益軌跡 (gain trajectory) 進一步說明了為何僅看最終加速率不足以刻畫優化行為。隨著預算增加，某些模型能持續發現改進，而另一些則在早期就停滯。STS 指標正是為了量化這種「在給定資源下能取得多少提升」的能力差異。效能、成本與正確性的分離報告則讓研究者能診斷失敗模式：例如，一個模型可能達到高加速率但消耗大量代幣，或在多次嘗試中產生不正確的實作。

從實驗設計的角度，48 個核心任務分為三個難度等級，這種分層有助於區分模型在不同複雜度操作上的表現。Batch 1 的 17 個任務作為初步評估子集，其結果已足以支撐基準測試設計的經驗驗證。

#### 與現有研究的比較

AscendGYM 在基準測試生態系中的定位可從三個維度理解：

**與核心生成基準測試的比較**：KernelBench 以 PyTorch 程式指定任務，要求模型生成等效的 GPU 核心；TritonBench 聚焦 Triton 核心生成；MultiKernelBench 延伸至多硬體平台；NPUKernelBench 與 CANN Bench 則將此評估擴展至 Ascend NPU。這些基準測試共同建立了「從計算需求出發生成正確且高效實作」的評估範式。AscendGYM 與之互補：它不評估生成能力，而是評估「給定正確實作後的優化能力」，這對應了真實工程流程中更常見的情境。

**與現有核心優化評估的比較**：AMD 在 TritonBench-modified 與 ROCm-bench 上評估代理對現有 Triton 核心的優化能力，要求在 AMD GPU 上提升執行效能同時保持正確性。AscendGYM 將此範式移植至 Ascend NPU，並透過從真實工作負載抽取配置來增強實用相關性。PRAGMA 將執行回饋與硬體效能分析 (profiling) 整合進迭代推理迴圈；AutoKernel 則透過效能分析優先處理瓶頸核心，再驗證並基準測試連續的 Triton 或 CUDA C++ 實作。AscendGYM 的 AscendForge 沙盒與這些工作在「整合回饋驅動迭代」的方向上一致，但更強調可程式化介面與軌跡記錄。

**與工作負載感知評估的比較**：FlashInfer-Bench 從真實推理軌跡抽取工作負載，說明了輸入配置與應用情境的關聯。SOL-ExecBench 從真實模型抽取核心任務，並以硬體效能極限評估剩餘優化空間。AscendGYM 沿襲這一脈絡，強調效能提升能直接對應到對應工作負載。

**限制與侷限**：首先，AscendGYM 目前僅涵蓋 48 個核心，雖然分為三個難度等級，但相較於實際 LLM 訓練與推理中涉及的核心數量仍屬子集。其次，STS 指標的權重設計（即加速率與代幣消耗的相對重要性）需要根據具體應用場景調整，論文未深入探討不同權重下的評分穩定性。第三，基準測試的實用價值取決於 Ascend NPU 的生態成熟度，若硬體或軟體棧快速演進，部分任務可能需要更新。

#### 可重現性評估

AscendGYM 已在 GitHub 開源（https://github.com/SLAI-AITP/AscendGYM），這為可重現性提供了基礎。開源內容應包含 48 個核心任務的定義、輸入配置、初始實作、測試案例，以及 AscendForge 沙盒的程式碼。STS 指標的計算邏輯應隨基準測試一同發布，使研究者能獨立驗證評分結果。

然而，可重現性仍面臨若干挑戰。首先，Ascend NPU 的硬體存取需要特定設備，這限制了非華為生態研究者的直接驗證能力。其次，模型評估涉及多個第三方模型（論文提及「多個領先模型」），這些模型的版本與設定會影響結果，論文中未明確列出所有評估模型的完整清單與版本資訊。第三，框架 (harness) 的具體實作細節（如搜尋編排策略、經驗累積機制）若未充分公開，將影響模型-框架評估模式的可重現性。

從正面來看，AscendForge 的設計強調「可程式化存取的評估服務」，這暗示了介面的標準化，有助於不同實作之間的比較。軌跡記錄功能也支援結果的後續驗證。

#### 未來研究方向

**基準測試擴展**：將核心數量從 48 擴展至更全面的覆蓋，特別是 LLM 訓練中涉及的高頻核心（如各種歸一化、位置編碼、損失計算等）。此外，可考慮引入動態工作負載——即輸入配置隨時間變化，更貼近真實推理服務的場景。

**指標深化**：STS 的權重設計值得進一步研究。不同應用場景對「加速率」與「代幣成本」的相對重視程度不同，例如即時推理服務可能更重視加速率，而批次訓練則可能更重視成本。此外，可探索將「正確性」更細緷地納入 STS，例如對產生錯誤實作的嘗試施加懲罰。

**代理能力分析**：論文發現約 70% 的組合加速率低於 1.2×，這提示需要深入分析失敗模式。是模型缺乏對 Ascend NPU 架構的理解？是框架的搜尋策略不夠有效？還是某些核心的優化空間本身有限？針對性研究可指導模型訓練與框架設計的改進方向。

**跨平台泛化**：AscendGYM 的方法論——從真實工作負載抽取配置、評估優化而非生成、結合效能與成本的指標——可移植至其他 NPU 或加速器平台。這將有助於建立統一的「核心優化能力」評估範式，促進跨硬體生態的比較研究。

**人機協作評估**：真實工程場景中，人類專家與代理的協作是常態。未來可探索如何評估「人機協作下的優化效能」，例如人類提供架構建議、代理負責實作與測試的混合模式。這將更貼近實際工程流程，也可能揭示純自動化評估無法捕捉的能力維度。

### 實作步驟建議

**步驟一：環境建置與基準部署**
從 GitHub（`SLAI-AITP/AscendGYM`）克隆專案，依據 README 安裝 CANN 依賴與 Python 套件。確認 Ascend NPU 驅動正常運作，並執行 `npu-smi info` 驗證裝置可被識別。

**步驟二：任務選擇與難度分級**
從 48 個核心任務中根據目標選擇對應難度等級的子集。建議初次使用從 Batch 1 的 17 個任務開始，這些任務已系統性評估過多個主流模型，可作為基準對照。

**步驟三：選擇評估模式**
- **模型評估模式**：直接評估單一模型在預設框架下的優化能力，適合快速比較不同 LLM。
- **模型-框架評估模式**：評估「模型 + 自訂框架」的組合系統，適合研究自訂搜尋編排或經驗累積機制。

**步驟四：設定預算與執行評估**
透過 AscendForge 設定 token 預算上限與最大迭代次數。執行基準測試時，AscendForge 會自動處理候選實作的編譯、正確性檢查與效能量測，並回傳結構化回饋。

**步驟五：分析 STS 與輔助指標**
重點關注 Speedup-Token Score (STS) 作為綜合指標，同時檢視加速率（speedup）、代幣消耗（token cost）與正確性（correctness）三項獨立指標，以全面理解優化行為。

**步驟六：記錄與重現**
利用 AscendForge 記錄的優化軌跡進行後續分析。所有評估應在相同硬體配置與 CANN 版本下執行，以確保結果可重現。

### 潛在風險與注意事項

**風險一：硬體可用性與成本**
Ascend NPU 並非所有地區皆易取得，且單次完整評估（48 個任務 × 多模型）需消耗大量算力與時間。
**緩解**：先以 Batch 1 的 17 個任務進行初步篩選，再對候選方案執行完整評估；考慮使用雲端 Ascend 服務以降低前期硬體投資。

**風險二：API 成本失控**
STS 雖已將代幣消耗納入考量，但若未設定嚴格預算上限，反覆迭代式優化可能產生高額 API 費用。
**緩解**：在 AscendForge 中設定硬性 token 預算上限與單次迭代成本閾值；定期監控累積消耗。

**風險三：測試案例代表性偏差**
雖然 AscendGYM 的輸入配置來自真實工作負載，但 48 個核心無法涵蓋所有可能的應用場景。
**緩解**：將 AscendGYM 結果視為通用能力指標，而非特定部署的絕對預測；針對目標應用補充自訂測試案例。

**風險四：正確性驗證的侷限性**
AscendForge 的正確性檢查基於預定義的驗證條件，可能無法捕捉所有邊界情況。
**緩解**：在生產部署前，對優化後的核心進行額外的壓力測試與長序列驗證。

**風險五：版本敏感性**
CANN 版本、驅動程式或 NPU 韌體更新可能導致基準結果波動。
**緩解**：固定所有軟硬體版本並記錄於評估報告；建立內部基準快照以便跨版本比較。

### 與其他技術的整合建議

**與現有 LLM 訓練框架整合**
AscendGYM 可作為 MindSpore、PyTorch（透過 torch_npu）等框架的補充驗證工具。在 CI/CD 流程中加入 AscendGYM 評估步驟，確保核心變更在合併前通過優化能力驗證。

**與其他基準測試的互補使用**
- **KernelBench / NPUKernelBench / CANN Bench**：用於評估「從零生成核心」的能力，與 AscendGYM 的「優化現有核心」形成互補。
- **FlashInfer-Bench**：兩者皆使用真實推理軌跡，可交叉驗證輸入配置的代表性。
- **PRAGMA / AutoKernel**：作為參考，比較迭代式優化框架在不同硬體上的設計取捨。

**與監控與可觀測性系統整合**
將 AscendForge 的優化軌跡匯入內部監控平台（如 Prometheus + Grafana），建立模型優化能力的長期趨勢儀表板。

**與內部代理框架整合**
若組織已有自訂的代理框架（如基於 LangGraph、AutoGen 的實作），可透過 AscendGYM 的模型-框架評估模式進行基準對齊，識別框架設計的改進方向。
