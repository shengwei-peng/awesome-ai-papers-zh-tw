# 受限代理：多智慧代理 AI 系統的委派安全性

**原文標題：** Bounded Agents: Delegation Security for Multi-Agent AI Systems  
**作者：** Xabier Muruaga  
**發布日期：** 2026-08-16  
**HF 連結：** [https://huggingface.co/papers/2608.15888](https://huggingface.co/papers/2608.15888)  
**arXiv：** [https://arxiv.org/abs/2608.15888](https://arxiv.org/abs/2608.15888)  

---

## ⚡ TL;DR

現有LLM代理的權限靜態且獨立審查，導致提示注入可透過組合合法動作或濫用委派造成未授權後果。
本文提出代理主體鏈APC，以六項授權檢查追蹤跨主體的委派範圍與預算，並用組合閉包防止禁止的動作序列。
評估顯示外洩率降至0%、544起資料竊取全被封阻，破壞與操縱下降，授權延遲僅0.24毫秒且效用略降。

## 摘要翻譯

基於大型語言模型的智慧代理（LLM-based agents，亦稱 LLM 代理）可代表使用者存取雲端服務（cloud services）、呼叫工具（tools），或調用其他代理。會話開始時，代理權限（permissions）雖已設定，但整個會話期間保持靜態，且每個請求均獨立評估，未考量先前的動作。在權限範圍內，代理可能做出與委派任務相悖的行為、將個別允許的動作組合成禁止的結果，或將權限委派給子代理（sub-agent）而不加以限制。提示注入（prompt injection）只有在代理有權執行此類動作時才會構成風險；因此這是授權架構（authorization architecture）的問題，而不只是模型的問題。代理主體鏈（Agentic Principal Chain，APC）會追蹤從一個主體（principal）到下一個主體的委派權限（delegated authority）。APC 使用六項授權檢查（authorization checks），根據累積會話狀態（accumulated session state）評估每個請求。APC 會延續並限制委派範圍（delegated scope）與預算（budgets）。APC 使用組合閉包（composition closure），根據先前的動作檢查請求以防止禁止組合（prohibited combinations），並在模型執行環境外部強制執行其決策。我們證明了 APC 實作的爆炸半徑單調性（Blast Radius Monotonicity）與組合健全性（Composition Soundness）；組合健全性僅在完整限制集合（complete restriction set）與序列化准入（serialized admission）的條件下，針對禁止組合成立。我們評估了 3,154 個實例，包含 InjecAgent、AgentDojo 與 ASB。我們的受損模型評估（compromised-model evaluation）在第一次合法工具呼叫後插入真實攻擊呼叫（ground-truth attack call），以獨立於模型行為的方式測試 APC。AgentDojo 的外洩（exfiltration）率在所有四個領域中從 75–100% 降至 0%；APC 阻擋了全部 544 個 InjecAgent 資料竊取（data-stealing）案例。意圖綁定（Intent binding）將破壞（destruction）率從 38.6% 降至 4.0%，並將操縱（manipulation）率從 90.5% 降至 12.1%。在閒置主機上，授權延遲（Authorization latency）在第 99 百分位數為 0.24 毫秒；在 949 個 AgentDojo 任務注入配對中，兩種設定下的效用（utility）分別降低 8.6 與 13.9 個百分點。實作、評估工具與資料均已公開釋出。

### 核心貢獻（3～5點）
- 提出代理主體鏈（APC）授權架構，用於追蹤多智慧代理系統中跨主體的委派權限與累積會話狀態。
- 引入組合閉包（composition closure）機制，防止個別允許的動作被組合成禁止的整體結果。
- 形式化證明 APC 的兩項安全性質：爆炸半徑單調性（Blast Radius Monotonicity）與組合健全性（Composition Soundness）。
- 透過受損模型評估與多項基準測試（InjecAgent、AgentDojo、ASB），驗證 APC 在阻擋提示注入、資料外洩與權限濫用上的有效性，且授權延遲極低。
- 將提示注入風險重新定位為授權架構問題，主張應在模型執行環境外部的基礎設施層級強制執行安全決策。

### 適合對象
本論文適合從事 AI 安全、多智慧代理系統設計、企業身分與授權基礎設施，以及大型語言模型應用部署的研究人員與工程師。特別是關注提示注入防禦、動態委派授權、模型外部強制執行機制，以及如何在實務系統中平衡安全性與效用的讀者，將能從 APC 的架構設計、形式化保證與大規模評估中獲得具體參考。

## 深度分析

#### 方法論解析

本文的核心論點是：提示注入（prompt injection）所帶來的安全風險，本質上是授權架構（authorization architecture）問題，而非單純的模型穩健性問題（model-robustness problem）。作者提出 **Agentic Principal Chain（代理主體鏈，APC）**，將傳統「靜態、逐請求獨立判斷」的授權模型，轉變為「會話級別（session-wide）、狀態累積、逐跳衰減」的動態授權框架。

##### 對手模型與安全目標

APC 的設計圍繞一組明確的對手能力（adversary capabilities）與信任邊界（trust boundaries）：

- **A1**：透過不可信資料來源進行間接提示注入（indirect prompt injection）。
- **A2**：完全控制鏈路中的單一主體（principal），例如子代理（sub-agent）、工具伺服器或編排器（orchestrator）。
- **A3**：觀察動作成敗以探測範圍邊界。
- **A4**：在整個任務會話期間維持影響力。

相對地，APC 假設對手無法攻破 **政策決策點（Policy Decision Point，PDP）**、**政策執行點（Policy Enforcement Point，PEP）**、證據匯集點（evidence sink）或金鑰管理基礎設施，也無法偽造密碼學簽章或雜湊，更不能跨會話邊界操作。

對應的安全目標包括：確保無超出委派範圍（delegated scope）的動作執行、禁止的動作類型組合（action-type combinations）不會在同一會話中共同出現、每次委派跳躍（delegation hop）後可達爆炸半徑（reachable blast radius）不增、高衝擊動作需具備有效核准權杖（approval tokens），以及每個被准入的動作都與基礎設施產生的證據耦合。

##### 會話級授權與六項檢查

APC 將每次工具呼叫視為由某個主體（principal）發出的請求，並根據該主體在委派鏈（delegation chain）中的位置決定其有效範圍。與傳統 OAuth 2.0 授權許可（OAuth 2.0 authorization grants）或代表（OBO）權杖交換（on-behalf-of token exchange）僅記錄「誰可代表誰」不同，APC 會在每一跳主動計算並強制執行範圍衰減（per-hop scope attenuation），同時攜帶並限制預算（budgets）。

具體而言，APC 對每個請求執行六項授權檢查（authorization checks），可歸納為：

1. **委派鏈有效性與範圍衰減**：驗證當前主體的權限確實來自上游主體的合法委派，且範圍未被擴大。
2. **範圍與預算檢查**：確認請求落在當前主體的委派範圍內，且未耗盡預算。
3. **組合閉包（composition closure）檢查**：將請求的動作類型與會話中已執行的動作歷史進行比對，防止個別允許但組合後產生禁止結果的動作序列。
4. **意圖綁定（intent binding）**：確保動作與使用者最初委派的任務意圖一致，避免代理執行雖被授權但與任務無關或相反的行為。
5. **高衝擊動作核准權杖**：對於高風險操作，要求額外的、由基礎設施核發的核准權杖。
6. **證據耦合（evidence coupling）**：每個被允許的動作都必須與 PDP/PEP 產生的證據紀錄綁定，以便事後稽核與歸責。

這六項檢查的核心特色在於：判斷是在**模型執行環境外部的基礎設施（infrastructure outside the model runtime）**中完成，因此即使 LLM 代理（LLM-based agents）已被提示注入或模型行為偏離，基礎設施仍能拒絕違規呼叫。

##### 組合閉包與形式化保證

**組合閉包（composition closure）**是 APC 提出的新形式化授權原語（formal authorization primitive）。它定義了一個會話級別的約束：某些動作類型組合（action-type combinations）在整個會話中禁止共同出現。例如「讀取機密文件」與「傳送外部訊息」個別都可能被允許，但兩者組合即構成資料外洩（exfiltration），因此必須被禁止。

為了兼顧表達力與計算可行性，APC 支援：

- **成對限制（pair-wise restrictions）**：禁止兩種動作類型在會話中共同出現。
- **k-元組擴展（k-tuple extensions）**：禁止長度為 k 的有序動作子序列，用以捕捉需要多步驟才能完成的攻擊路徑，例如分段外洩（multi-step exfiltration）可繞過單純的成對限制。

作者證明了兩個關鍵定理：

- **爆炸半徑單調性（Blast Radius Monotonicity，Theorem 4.6）**：在委派鏈中，下游主體的可達爆炸半徑（reachable blast radius）不會大於上游主體，確保權限在每次委派跳躍（delegation hop）後只會縮小或持平。
- **組合健全性（Composition Soundness，Theorem 4.7）**：在**完整限制集合（complete restriction set）**與**序列化准入（serialized admission）**的前提下，任何被 APC 准入的動作序列都不會產生禁止結果。

需要特別注意的是，組合健全性的保證有兩個前提：限制集合必須完整，且動作准入必須是序列化的。這意味著若存在並行（concurrent）工具呼叫，或限制集合遺漏了某些危險組合，則形式化保證可能不再成立。

##### 執行架構

APC 的參考實作採用標準的 PDP/PEP 分離架構：PDP 負責根據會話狀態與委派鏈做出授權決策，PEP 負責在工具呼叫實際發出前攔截並執行該決策。所有決策與動作證據都寫入證據匯集點（evidence sink），形成不可否認的稽核軌跡。這種設計讓授權狀態（authorization state）隨著會話進行而累積，並能根據「先前已做過什麼」動態調整後續請求的准駁。

#### 實驗數據解讀

本文的評估涵蓋 3,154 個實例，橫跨 **InjecAgent**、**AgentDojo** 與 **ASB** 三個基準資料集，並採用**受損模型評估（compromised-model evaluation）**方法：在第一次合法工具呼叫（legitimate tool call）之後，直接將**真實攻擊呼叫（ground-truth attack call）**注入代理管線。這種設計的關鍵在於，它獨立於模型是否抵抗操縱，專門測試基礎設施層級強制執行（infrastructure-level enforcement）的有效性。

##### 攻擊成功率

- **AgentDojo 外洩（exfiltration）**：在未使用 APC 的基準中，四個領域的外洩成功率介於 75% 至 100%；導入 APC 後，全部降至 **0%**。這顯示組合閉包與範圍衰減能有效阻斷「讀取敏感資料後傳送出去」的經典外洩路徑。
- **InjecAgent 資料竊取（data-stealing）**：APC 阻擋了全部 544 筆資料竊取案例，再次驗證基礎設施層授權對提示注入攻擊的防禦力。
- **破壞（destruction）與操縱（manipulation）**：在意圖綁定（intent binding）的輔助下，破壞率從 38.6% 降至 4.0%，操縱率從 90.5% 降至 12.1%。這說明單靠組合閉包無法完全涵蓋「動作雖被允許但違背使用者意圖」的場景，意圖綁定對此類攻擊有顯著抑制作用。

##### 效能與效用

- **授權延遲（authorization latency）**：在閒置主機上，99th percentile 延遲僅 **0.24 毫秒**，顯示 APC 的執行期開銷極低，幾乎不會影響互動式代理的回應速度。
- **效用（utility）**：在 949 組 AgentDojo 任務–注入配對中，APC 導致效用分別下降 8.6 與 13.9 個百分點。這反映了安全與可用性之間的權衡：更嚴格的範圍與組合限制可能拒絕部分合法但邊緣的工具使用路徑。

整體而言，實驗數據強而有力地支持本文論點：當授權架構正確設計時，即使模型本身已被攻破，攻擊者也難以將提示注入轉化為實際危害。不過，效用下降也提醒我們，APC 的價值取決於政策（policy）是否精準：過於寬鬆會留下攻擊空間，過於嚴格則會妨礙正常任務完成。

#### 與現有研究的比較

##### 相較於傳統授權模型

傳統 **角色導向存取控制（Role-Based Access Control，RBAC）**、**屬性導向存取控制（Attribute-Based Access Control，ABAC）** 與 **OAuth（開放授權）** 家族機制，主要回答「某個主體在靜態政策下能否對某資源執行某動作」。它們缺乏三項對代理式 AI 至關重要的能力：

1. **逐跳範圍衰減（per-hop scope attenuation）**：OAuth 2.0 的權杖交換（Token Exchange）與豐富授權請求（Rich Authorization Requests，RAR）雖能記錄委派鏈（delegation chain）中的巢狀行為聲明（nested act claims），但不會在每一跳自動縮小有效範圍（effective scope）。
2. **會話級狀態**：RBAC/ABAC 通常對每個請求獨立判斷，無法根據「同一會話中先前已執行的動作」進行決策。
3. **動作類型組合限制**：現有機制不禁止個別合法但組合後產生禁止結果的動作序列，例如「讀取文件＋傳送電子郵件」導致外洩。

APC 正好補足上述缺口，將授權從「靜態許可」提升為「動態、狀態相依、組合感知」的會話級約束。

##### 相較於模型層級的提示注入防禦

現有許多研究聚焦於提升 LLM 對提示注入的抵抗力，例如輸入過濾、提示強化、輸出監控或對齊訓練。這些方法屬於模型層級（model-level），其效果受限於模型本身的機率行為與對齊品質。APC 則採取基礎設施層級（infrastructure-level）路徑：無論模型是否被操縱，只要攻擊呼叫違反授權政策，就會在執行前被 PEP 攔截。兩者並非互斥，而是互補：模型層防禦可降低惡意呼叫產生的機率，APC 則確保即使惡意呼叫產生也無法越權執行。

##### 主要限制

儘管 APC 在形式化與實驗上都展現強大潛力，仍有以下限制：

1. **完整限制集合（complete restriction set）假設**：組合健全性要求管理者能完整列舉所有禁止組合。在複雜企業環境中，遺漏某個危險組合可能導致防禦失效。
2. **序列化准入（serialized admission）**：形式化保證目前僅適用於動作依序被准入的情境。若代理並行呼叫多個工具，則需要額外的並發控制機制。
3. **政策撰寫負擔**：APC 需要為每種工具與動作類型定義範圍、預算、限制集合與意圖綁定規則，對大型企業而言是顯著的治理挑戰。
4. **信任邊界**：APC 將安全性寄託於 PDP、PEP、證據匯集點與金鑰管理基礎設施。若這些元件被攻破，整體保證將崩解。
5. **效用代價**：實驗顯示效用下降約 8–14 個百分點，在實際部署中可能需要透過更細緻的政策調校來降低誤擋率。

#### 可重現性評估

本文在可重現性方面表現良好。作者公開了參考實作（Python，約 2,500 行原始碼與 3,000 行測試）、評估工具與實驗資料。由於 InjecAgent、AgentDojo 與 ASB 均為公開基準資料集，其他研究者可以在相同資料上重現實驗結果。

受損模型評估（compromised-model evaluation）方法本身具有高度確定性：它不依賴模型對提示注入的反應，而是直接將**真實攻擊工具呼叫（ground-truth attack tool calls）**插入管線。這降低了因模型版本、溫度參數或提示差異導致的再現變異。

不過，仍有幾個可能影響完全重現的因素：

- **部署對應（deployment mapping）**：雖然論文討論了與企業身分與政策基礎設施（identity and policy infrastructure）的對接，但具體的 OAuth、政策即程式碼引擎（policy-as-code engines）與 MCP 伺服器配置細節可能未完全公開。
- **政策定義**：APC 的防禦效果高度依賴限制集合與範圍定義。若公開資料中未包含完整的政策檔案，重現者需要自行推導或復原這些規則。
- **模型與提示細節**：雖然受損模型評估不測試模型抵抗力，但效用（utility）實驗仍可能受底層模型與提示影響，論文應盡可能提供所用模型版本與系統提示。

整體而言，本文在開源程式碼、測試與資料公開方面已達到相當高的標準，是少數同時提供形式化證明、參考實作與大規模基準評估的代理安全研究。

#### 未來研究方向

APC 為代理式 AI 的授權安全開闢了新方向，未來研究可從以下幾個維度延伸：

1. **自動化限制集合建構**：發展從歷史攻擊資料、工具語意或企業政策中自動挖掘禁止組合（prohibited combinations）的方法，降低對完整限制集合（complete restriction set）的人為依賴。
2. **並行與非序列化准入**：在真實代理系統中，工具呼叫常並行發生。未來需擴展組合健全性（Composition Soundness）至並發執行環境，並設計相應的鎖定或交易式准入機制。
3. **與企業標準深度整合**：將 APC 與 OAuth 2.0、RAR、Token Exchange、MCP（Model Context Protocol）以及政策即程式碼引擎（policy-as-code engines）無縫整合，並提出標準化的範圍衰減與證據格式。
4. **動態預算與風險評分**：目前預算（budgets）多為靜態數值，未來可結合動態風險評分，根據會話上下文、主體信任度與動作衝擊程度即時調整。
5. **形式化驗證參考實作**：雖然 APC 的代數性質已被證明，但參考實作（reference implementation）的程式碼正確性仍可透過形式化驗證或模型檢查進一步強化。
6. **結合模型層與基礎設施層防禦**：研究如何將 APC 與輸入過濾、對齊訓練、異常偵測等模型層技術協同運作，形成縱深防禦（defense in depth）。
7. **使用者意圖推論與意圖綁定強化**：提升意圖綁定（intent binding）的語意理解能力，使其能處理更模糊、多步驟或隱含的使用者目標，減少誤擋並提升效用（utility）。
8. **真實企業部署研究**：在實際生產環境中評估 APC 的可維運性、政策演化流程與對開發者體驗的影響，彌補基準測試與真實世界之間的差距。
9. **參數級與語意級政策**：目前 APC 主要針對動作類型（action types）進行限制，未來可擴展至工具參數層級（例如禁止傳送至特定網域）或更細緻的語意條件。
10. **跨會話與長期授權**：APC 聚焦單一會話內的授權狀態，未來可研究跨會話邊界的長期委派、撤銷與歸責機制。

## 論文問答

**Q1：這篇論文指出 LLM 代理系統面臨的核心安全問題是什麼？**

A：核心問題在於現有授權機制將代理的權限視為靜態且不考慮會話歷史，導致代理可能在被授予的權限範圍內執行違背使用者意圖、過度委派給子代理，或將個別合法動作組合成禁止結果的行為。這種狀態獨立的授權方式無法捕捉多步驟、動態且遞迴的代理工作流程所帶來的風險。論文強調，提示注入攻擊之所以危險，往往是因為底層授權架構允許代理執行這些高風險動作，而非單純因為模型被欺騙。

**Q2：為什麼傳統的 RBAC、ABAC 與 OAuth 無法有效保護代理式工作流程？**

A：傳統授權模型在設計上假設行為實體是人類、委派是明確且靜態的，並且每次請求都獨立評估，但 LLM 代理是非人身分、由機率模型驅動，並會在執行期動態決定工具呼叫序列。OAuth 2.0 或 OBO 權杖交換雖能記錄委派鏈，卻無法在每一跳自動衰減範圍，也無法限制「讀取文件」與「傳送電子郵件」這類個別合法動作的組合。因此，即使模型完全遵循指令，攻擊者仍可透過組合授權內的動作達成資料外洩等禁止結果。

**Q3：作者為何主張提示注入本質上是授權架構問題，而不只是模型穩健性問題？**

A：因為提示注入要能造成實質傷害，前提是代理本身擁有執行該攻擊動作的權限，例如讀取機密檔案並對外傳送；若授權架構從根本上就不允許這些動作或組合，即使模型被注入惡意提示也無法得逞。論文指出，單純提升模型對抗注入的能力無法消除這類結構性風險，因為攻擊者仍可利用合法權限的組合來規避。因此，真正的防禦重點應放在設計能隨會話狀態演變、並在模型執行環境外強制執行的授權架構。

**Q4：Agentic Principal Chain（APC）是什麼，它如何運作？**

A：APC 是一種追蹤委派權限從一個主體傳遞到下一個主體的授權機制，它會在每次請求時根據累積的會話狀態進行六項授權檢查。此機制會隨著委派跳躍逐步縮小並限制代理可執行的範圍與預算，確保子代理無法取得超出原始委派意圖的權限。透過在模型執行環境外部強制執行決策，APC 能將授權判斷與模型的機率行為分離，從而提供基礎設施層級的保證。

**Q5：組合閉包（composition closure）作為授權原語有何創新之處？**

A：組合閉包是一種會話級別的約束，用於禁止特定動作類型在整個會話中以任意順序組合出現，並由模型執行環境外部的基礎設施強制執行。這在傳統的 RBAC、ABAC 與 OAuth 中並不存在，因為這些模型只判斷單一請求是否被允許，而不考慮先前行為對當前動作安全性的影響。論文證明了組合健全性（Composition Soundness），即在完整限制集合與序列化准入條件下，不會有任何被允許的動作序列產生禁止結果。

**Q6：APC 的六項授權檢查各自扮演什麼角色？**

A：六項檢查共同確保每次工具呼叫都符合當前委派範圍、預算、意圖綁定、組合限制、審批權杖與證據綁定等要求，從而防止意圖違反、範圍擴張與不安全組合。其中條件 2a 確保動作不超出委派範圍，條件 2b 與 k-元組擴展則防止禁止的動作組合在會話中出現。高影響力動作需要有效的審批權杖，而每個被准入的動作都會與基礎設施產生的證據綁定，以利後續稽核與歸責。

**Q7：論文使用了哪些評測資料集，以及「受損模型評估」方法有何特別之處？**

A：評測涵蓋 InjecAgent、AgentDojo 與 ASB 三個資料集，共計 3,154 個測試實例，並針對資料竊取、外洩、破壞與操縱等多種攻擊目標進行測試。受損模型評估的特別之處在於，它會在第一個合法工具呼叫之後直接插入真實攻擊呼叫，從而獨立於模型行為來測試 APC 的基礎設施層級強制執行能力。這種設計確保即使模型完全被攻陷或操縱，只要 APC 正確實作，就能驗證其是否能阻擋攻擊。

**Q8：APC 在實驗中達成了哪些關鍵的攻擊緩解成效？**

A：在 AgentDojo 的四個領域中，資料外洩攻擊成功率從 75% 到 100% 全部降至 0%，而 InjecAgent 的 544 筆資料竊取案例也全部被阻擋。在意圖綁定機制方面，破壞性攻擊從 38.6% 降至 4.0%，操縱性攻擊則從 90.5% 降至 12.1%。這些結果顯示 APC 能顯著降低提示注入與代理濫用所帶來的實際風險。

**Q9：APC 的效能開銷與對任務效用的影響如何？**

A：在閒置主機上，APC 的授權延遲在 99th percentile 僅為 0.24 毫秒，顯示其基礎設施層級檢查的開銷極低。在 949 組 AgentDojo 任務與注入配對中，任務效用分別下降了 8.6 與 13.9 個百分點，代表安全性提升伴隨著一定程度的可用性權衡。整體而言，這樣的效能與效用代價對於企業級多代理系統而言是相當可接受的。

**Q10：APC 在企業代理系統中可以如何實際部署？**

A：APC 可以整合至現有的身分與政策基礎設施中，例如 OAuth、政策即程式碼引擎、MCP 伺服器與雲端服務 API 閘道，作為授權決策點與執行點之間的中介檢查層。由於 APC 的決策在模型執行環境外強制執行，企業無需修改 LLM 本身即可為代理工作流程增加會話級別的安全控制。參考實作以 Python 撰寫，僅約 2,500 行原始碼與 3,000 行測試，並已公開釋出，便於整合與驗證。

**Q11：部署 APC 時需要考慮哪些信任邊界與產品設計議題？**

A：APC 假設對手無法入侵政策決策點、政策執行點、證據接收端或金鑰管理基礎設施，也無法偽造密碼學簽章或雜湊，更不能跨越會話邊界操作。產品設計上必須確保這些元件受到妥善隔離與保護，因為一旦它們被攻破，APC 的保證將不再成立。此外，管理者需要精確定義禁止的動作類型組合與完整限制集合，否則組合健全性將無法發揮預期效果。

**Q12：APC 對多代理 AI 安全領域可能帶來什麼影響？**

A：APC 將安全焦點從單純提升模型穩健性轉向設計正確的授權架構，為業界提供了一個可形式化驗證且可實際部署的防禦範式。它證明了透過會話狀態、委派範圍衰減與組合閉包，可以在不犧牲太多效用的前提下大幅減少提示注入與代理濫用的影響。這種基礎設施層級的強制執行方式，有望成為企業部署自主代理時的標準安全元件。

**Q13：APC 的組合健全性有哪些已知的限制？**

A：組合健全性僅在「完整限制集合」與「序列化准入」的條件下成立，這意味著系統必須預先列舉所有可能導致禁止結果的動作組合，並確保授權檢查按順序逐一進行。若限制集合不完整，攻擊者仍可能透過未被涵蓋的動作序列達成惡意目標。此外，k-元組擴展雖能捕捉多步驟外洩，但其有效性仍取決於管理者能否正確識別並建模這些複雜組合。

**Q14：在哪些情況下 APC 可能無法阻擋攻擊或會產生誤判？**

A：若攻擊者能夠繞過 APC 的信任邊界，例如入侵政策決策點或偽造審批權杖，則整個安全保證將失效。此外，如果禁止組合的定義過於寬鬆，合法但高風險的動作序列可能被允許；反之，若過於嚴格，則可能降低任務效用或阻擋正常工作流程。APC 也無法防禦那些不需要違反授權規則、而是利用社會工程或資訊不對稱達成目標的攻擊。

**Q15：這項研究未來可以朝哪些方向延伸？**

A：未來研究可探索如何自動推導或學習完整限制集合，以減少對人工定義組合規則的依賴，並提升對未知攻擊模式的泛化能力。另一個方向是將 APC 擴展至非序列化或平行執行的多代理環境，因為當前組合健全性假設動作按順序准入。此外，也可進一步研究如何與形式化驗證、執行期監控及異常偵測技術結合，以提供更全面的代理安全保證。

## 實務應用指南

## 適用場景

**企業級智慧代理編排平台**
當企業部署一個中央編排器（orchestrator）將任務拆解並委派給多個專案子代理時，APC 可確保每個子代理只能在其被委派的範圍內行動。例如，財務分析代理可讀取內部報表，但不能將資料轉寄給外部郵件代理；客服代理可查詢訂單，但不能呼叫退款工具。此場景特別適合已採用 MCP 伺服器或 API 閘道暴露工具的組織。

**跨雲服務自動化工作流程**
LLM 代理需要代表使用者操作多個雲端服務（如讀取 Google Drive 文件、發送 Slack 通知、建立 Jira 工單）時，APC 的組合閉包可防止個別允許的動作被串接成資料外洩路徑。例如，「讀取文件」與「發送外部訊息」各自合法，但兩者組合可能構成機密外洩，APC 會依據會話累積狀態拒絕此類組合。

**高風險操作的人機協同審批流程**
在代理被授權執行不可逆或高影響操作（如資金轉帳、刪除資料庫、部署生產環境變更）的場景中，APC 的批准權杖機制可強制要求人類或獨立政策引擎在關鍵步驟給予明確授權。這適合金融、醫療、關鍵基礎設施等對錯誤容忍度極低的領域。

**多租戶 SaaS 平台中的代理即服務**
SaaS 平台允許終端使用者連接自己的 LLM 代理並存取平台 API 時，APC 可作為基礎設施層的授權骨幹，確保使用者建立的代理不會因提示注入而越權存取其他租戶資料，或將權限過度委派給第三方子代理。

**供應鏈與第三方工具整合**
當企業代理需要呼叫外部供應商或開源社群提供的工具與子代理時，APC 的爆炸半徑單調性可保證每經過一次委派跳躍，可達損害範圍只會縮小不會擴大，降低單一被入侵工具伺服器對整體系統的影響。

## 實作前置條件

**資料準備**
需要完整盤點所有可被代理呼叫的工具與 API，並為每個動作建立動作類型（action type）分類。接著需定義禁止組合（prohibited combinations）清單，例如「讀取機密文件」後接「發送外部訊息」即構成外洩。此外，需要建立每個委派路徑的預期範圍與預算（budgets）政策，包括可呼叫的工具集合、次數上限、資料量上限與時間窗口。

**運算資源**
論文參考實作為 Python 2,500 行原始碼與 3,000 行測試，可在標準企業伺服器或容器環境執行。授權延遲在閒置主機上 99th percentile 僅 0.24 毫秒，因此對大多數互動式代理應用而言運算開銷極低。若需處理高吞吐量，可將政策決策點（PDP）與政策執行點（PEP）水平擴展。

**技能與團隊組成**
需要具備身分與存取管理（IAM）經驗的資安工程師、熟悉 OAuth 2.0 / Token Exchange / RAR 等委派機制的後端工程師，以及能將業務規則轉譯為政策即程式碼（policy-as-code）的領域專家。同時需要至少一名成員理解形式化授權模型，以便正確定義完整限制集合（complete restriction set）並驗證組合健全性。

## 實作步驟建議

**步驟一：建立工具與動作類型目錄**
將所有工具呼叫對應到高層次的動作類型，例如 `read_confidential`、`send_external`、`transfer_funds`、`delete_resource`。這是後續組合閉包與政策定義的基礎，建議與現有 API 綱要或 OpenAPI 規格對齊。

**步驟二：定義委派範圍與逐跳衰減規則**
為每一種委派情境設計範圍衰減政策：人類主體授予編排器哪些權限、編排器可進一步傳遞給子代理的權限為何、子代理可傳遞給工具伺服器的權限為何。確保後續每一跳的權限集合都是前一跳的子集，並為每個主體綁定預算與意圖（intent binding）。

**步驟三：建立禁止組合與 k-元組擴展**
從成對限制（pair-wise restrictions）開始，列出不可在同一會話中出現的動作類型組合。接著檢視是否需要 k-元組擴展以捕捉多步驟外洩攻擊，例如 `read → anonymize → send` 雖然中間步驟看似無害，但整體仍可能洩漏資訊。

**步驟四：部署 APC 授權閘道**
在模型執行環境外部部署 PDP 與 PEP，攔截每個工具呼叫請求。PEP 負責收集請求證據並送往 PDP，PDP 依據 APC 的六項授權檢查與累積會話狀態做出准許或拒絕決策。決策必須在基礎設施層強制執行，而非僅依賴模型自我約束。

**步驟五：整合高影響操作批准權杖**
對於高風險動作，要求獨立的批准權杖（approval token）。此權杖可由人類審批流程、硬體安全模組或外部政策引擎簽發，並與特定動作證據綁定，防止重放或轉移。

**步驟六：執行受損模型評估與迴歸測試**
參考論文方法，在管線中直接注入真實攻擊工具呼叫（ground-truth attack tool calls），驗證 APC 能否在模型被操控的情況下仍然阻擋攻擊。同時建立與形式化定理對齊的測試案例，確保每次政策變更後組合健全性與爆炸半徑單調性仍然成立。

## 潛在風險與注意事項

**限制集合不完整導致組合健全性失效**
Composition Soundness 僅在「完整限制集合」與「序列化准入」條件下成立。若實務上遺漏了某些危險組合，攻擊者仍可能透過未被涵蓋的動作序列達成禁止結果。建議採用威脅建模方法定期審查限制集合，並對新工具上線執行組合風險評估。

**並行或亂序執行破壞序列化准入**
若代理架構允許多個工具呼叫並行執行，或請求到達 PDP 的順序與邏輯會話順序不一致，可能繞過組合閉包檢查。實作時應確保准入順序與會話狀態更新具有原子性，必要時強制序列化關鍵動作類型的執行。

**過度嚴格的政策影響任務效用**
論文評估顯示 APC 在某些設定下會降低 8.6 至 13.9 個百分點的任務效用。若政策過於保守，可能導致合法工作流程頻繁被拒絕。建議採用漸進式部署：先以監控模式記錄本應被拒絕的請求，調整政策後再切換為強制模式。

**忽視模型執行環境內部的繞過路徑**
APC 的保護在於基礎設施層，但若模型執行環境本身可直接存取工具或繞過 PEP，則整體安全性將崩潰。必須確保所有工具呼叫都經過 PEP，並對模型執行環境實施最小權限與網路隔離。

**委派鏈過長造成管理複雜度**
雖然爆炸半徑單調性保證每跳權限不會擴大，但過長的委派鏈會增加政策審計與除錯難度。建議設定委派深度上限，並要求每個中間主體明確記錄其被授予的範圍與意圖。

## 與其他技術的整合建議

**OAuth 2.0、Token Exchange 與 RAR**
APC 可與現有 OAuth 2.0 授權許可、代表（OBO）權杖交換及豐富授權請求（RAR）整合，將 APC 計算出的逐跳範圍衰減編碼為權杖中的授權狀態。相較於僅記錄委派鏈的巢狀 act claims，APC 進一步提供每跳的範圍縮減與動作組合限制。

**政策即程式碼引擎**
可將 APC 的禁止組合與範圍政策以 policy-as-code（如 Open Policy Agent、Cedar）表達，讓資安與合規團隊能獨立審查與版本控制授權規則。PDP 可呼叫這些引擎進行部分決策，但組合閉包與會話狀態管理仍需由 APC 核心維護。

**MCP 伺服器與 API 閘道**
對於使用 Model Context Protocol（MCP）或 REST API 暴露工具的環境，可將 PEP 部署為 API 閘道或 MCP 中介層，統一攔截所有工具呼叫。這樣無需修改個別工具後端即可套用 APC 授權檢查。

**可觀測性與 SIEM 平台**
將 APC 產生的授權決策證據（evidence）與日誌送往 SIEM 或安全資料湖，可用於事後稽核、異常偵測與合規報告。特別是記錄被拒絕的組合嘗試，有助於發現新型攻擊模式。

**LLM 護欄與對齊技術**
APC 並非取代模型層的輸入過濾或對齊訓練，而是與其互補。建議將 APC 視為「縱深防禦」的最後一道授權閘門，即使提示注入繞過模型護欄，基礎設施層仍能阻止未授權行動。

## 給不同背景讀者的閱讀建議

**初學者**
建議先從第 2 節「背景與動機」與第 3 節「威脅模型」讀起，理解為何傳統 RBAC / ABAC 無法保護多智慧代理系統，以及提示注入為何不只是模型問題。接著閱讀第 5 節的執行架構與第 6 節評估結果，建立 APC 如何運作的直覺，最後再回頭瀏覽第 4 節的形式化定義。

**AI 工程師**
請聚焦第 4 節的授權模型與第 5 節的執行架構，特別注意六項授權檢查的實作細節、意圖綁定與批准權杖的整合方式。第 6 節的受損模型評估方法值得直接複製到自家的代理管線中，以驗證基礎設施層防護是否有效。參考實作的 Python 程式碼與測試是最佳起點。

**研究人員**
核心貢獻在第 4 節的形式化模型與定理：組合閉包、爆炸半徑單調性（Theorem 4.6）與組合健全性（Theorem 4.7）。請仔細檢視其假設條件，包括完整限制集合與序列化准入，並思考如何放寬這些假設或擴展到非序列化、部分可觀測的分散式代理系統。第 8 節相關工作可協助定位 APC 在現有授權文獻中的位置。

**產品經理**
請優先閱讀摘要、第 1 節與第 6 節評估結果，掌握 APC 的商業價值：AgentDojo 外洩攻擊從 75–100% 降至 0%、InjecAgent 544 筆資料竊取案例全數阻擋、授權延遲低於 1 毫秒。接著與工程團隊討論第 5 節的部署對應與第 7 節的限制，評估導入 APC 對現有產品流程、使用者體驗與合規報告的影響。
