# Diff 與完整檔案：Flutter/Dart 程式碼模型中迭代式 diff 生成與直接生成之實證比較

**原文標題：** Diffs vs. Whole Files: An Empirical Comparison of Iterative Edit-Based and Direct Generation for Flutter/Dart Code Models  
**作者：** Andrej Andrejev

## ⚡ TL;DR

比較程式碼編輯模型中直接生成與迭代 diff 生成何者較佳。
在 Flutter/Dart 領域從頭訓練與微調兩模型，分別以直接生成與迭代 diff 步驟訓練。
直接生成整體大幅勝出，但 diff 在短程局部重構與錯誤處理任務具優勢。

## 摘要翻譯

用於程式碼編輯的大型語言模型（large language models, LLMs）在訓練與部署時至少有兩種輸出模式（output regimes）：直接生成（direct generation），即模型一次性輸出整份修改後的檔案；以及迭代式 diff 生成（iterative diff-based generation，又稱「步驟」／steps），即模型輸出一連串局部化的搜尋／取代編輯（search/replace edits），每次套用一筆，直到模型發出完成訊號或步驟預算（step budget）耗盡。diff 輸出模式的吸引力在於它反映了開發者編輯程式碼的方式，且每輪生成所需的 token（權杖）數量應顯著較少。我們在共享的 Flutter/Dart 資料集上，以這兩種模式訓練了兩個程式碼模型——一個從頭訓練（trained from scratch）的 100M 參數模型 Rainbow-Pony-100M，以及一個微調（fine-tuned）的 Qwen2.5-Coder-0.5B——並在四個最終產生的模型上，於每個模型各約 1,790 項任務的保留測試集（held-out set）中進行評估。直接生成在我們測量的每一項指標上都大幅優於 diff 生成——包括編譯／靜態分析通過率（compilation/static-analysis pass rate）、每位元組位元數（bits-per-byte, BPB）、相對於參考答案（reference）的字元層級相似度（character-level similarity），以及針對目標達成度（goal fulfillment）、正確性（correctness）與程式碼品質（code quality）的盲測 LLM 評審分數（blinded LLM-judge ratings）——而且這項差距在透過配對 ID 比較（matched-ID comparison）控制任務難度（task difficulty）後依然存在，在僅限於兩種模式都能通過編譯的程式碼時亦然。接著，我們辨識出 diff 生成確實佔優勢的情況背後，存在單一且架構無關（architecture-independent）的機制：它在簡短、空間局部化（spatially localized）的編輯上具有競爭力，而且其類別層級勝率（category-level wins）恰好集中在我們資料集中平均編輯步驟數（mean edit-step count）最低的兩類任務——重構（refactoring），以及錯誤處理／邊界案例修復（error-handling/edge-case fixes）。我們將此稱為任務局部性（task locality），並討論它對於程式碼編輯模型（code-editing model）在何時該採用、何時不該採用以編輯為基礎的訓練模式（edit-based training regime）之意涵。

### 核心貢獻（3～5點）
- 首次在相同共享資料集上，系統性比較「直接生成」與「迭代式 diff 生成」兩種輸出模式，並訓練兩個不同規模與訓練方式的 Flutter/Dart 程式碼模型，產生四個可比較模型。
- 在約 1,790 項保留測試任務上進行多維度評估，發現直接生成在編譯／靜態分析通過率、BPB、字元層級相似度與盲測 LLM 評審分數等所有指標上均顯著優於 diff 生成。
- 透過配對 ID 比較控制任務難度，並限制於兩種模式皆可編譯的程式碼，驗證上述差距並非由任務難度或編譯失敗所造成。
- 提出「任務局部性」（task locality）作為單一、架構無關的解釋機制，說明 diff 生成僅在簡短、空間局部化編輯上具競爭力，其勝率集中於重構與錯誤處理／邊界案例修復這兩類平均編輯步驟數最低的任務。
- 為生產級程式碼代理（production coding agents）與 IDE 整合工具（IDE-integrated tools）在選擇輸出模式與訓練目標時，提供實證依據與設計建議。

### 適合對象
本論文最適合從事程式碼生成與程式碼編輯模型研究的學者與工程師，特別是關注生產級程式碼代理、IDE 整合工具、拉取請求 diff（pull-request diff）自動生成，以及正在評估應採用「直接生成整份檔案」或「迭代式搜尋／取代編輯」作為模型推論介面與訓練目標的研發團隊。對於希望理解 diff 模型優勢邊界、token 效率與可靠性成本（reliability cost）之間權衡的實務工作者，亦具高度參考價值。

## 深度分析

#### 方法論解析

本研究採用 **within-domain、within-dataset** 的對照設計，核心目標是將「輸出模式（output regime）」本身從模型架構、資料分佈、tokenizer、評估框架等混淆因子（confounds）中孤立出來。具體而言，作者固定了領域（Flutter/Dart）、訓練資料、tokenization pipeline 與評估 harness，僅讓兩個差異極大的 backbone 分別以 **direct generation（直接生成）** 與 **iterative diff-based generation（迭代式 diff 生成，即 steps）** 兩種方式進行微調，從而得到四個可比較的模型。

##### 1. 兩種輸出模式的定義與實作

- **Direct generation（直接生成）**：模型在單次 forward 中，根據原始檔案（source file）與編輯指令，直接輸出修改後的完整檔案（whole files）。這種模式與常見的 code completion 或 instruction-following 設定一致，模型必須同時維持未改動區域的穩定性與修改區域的正確性。
- **Iterative diff-based generation / steps（迭代式 diff 生成 / 步驟）**：模型輸出一連串 localized 的 **search/replace edits（搜尋/取代編輯）** 或 unified-diff 格式的編輯步驟，這些步驟被機械式地逐一套用至原始檔案，直到模型發出完成訊號或達到 **step budget（步驟預算）** 上限。此模式模擬開發者實際修改程式碼的單元，也與 pull-request diff 的審查單位一致。

為了讓 steps 模式可操作，作者引入了結構化特殊 token（如 `<GOAL>`、`<CODE>` 與 steps-mode action tags），將原始檔案、目標敘述與一連串編輯動作編碼成單一序列。這意味著 steps 模型不僅要學會「改什麼」，還要學會「如何以 diff 語法表達」以及「何時停止」。

##### 2. 兩個架構迥異的 Backbone

- **Rainbow-Pony-100M**：約 100M 參數的 decoder-only transformer，完全 **trained from scratch（從頭訓練）**，預訓練語料約 26 億 token（70% Flutter/Dart 原始碼、30% 英文文本），使用 16k 詞表的 custom BPE tokenizer。該模型沒有接觸過其他程式語言或通用多語言程式碼語料，因此能夠隔離「領域外預訓練」的影響。
- **Qwen2.5-Coder-0.5B**：基於預訓練程式碼模型進行 **fine-tuned（微調）**，具備較強的先驗程式碼知識與較大的容量。

透過同時在這兩個架構上進行 direct 與 steps 訓練，作者能夠檢驗輸出模式的效應是否具備 **architecture-independent（架構無關）** 的特性。

##### 3. 資料集與評估設計

訓練與評估使用同一個 Flutter/Dart **shared dataset（共享資料集）**，保留測試集（held-out set）約每個模型 1,790 筆任務。評估指標涵蓋：

- **Compilation/static-analysis pass rate（編譯/靜態分析通過率）**：客觀的語法與靜態正確性。
- **Bits-per-byte（BPB，每位元組位元數）**：語言模型對目標輸出的機率建模能力。
- **Character-level similarity（字元層級相似度）**：相對於 reference（參考答案）的編輯後檔案相似度。
- **Blinded LLM-judge ratings（盲測 LLM 評審分數）**：由獨立 LLM 針對 **goal fulfillment（目標達成度）**、**correctness（正確性）** 與 **code quality（程式碼品質）** 進行盲測評分。

此外，作者進一步區分 steps 模型的失敗原因，包括 **apply_failed**（harness 無法套用編輯）、**malformed edits（格式錯誤的編輯）** 與在「正常完成軌跡（intrajectory）」中仍出現的語義錯誤，這對於理解 diff 模式的失效機制至關重要。

##### 4. 方法論上的關鍵優勢

本研究最大的方法論價值在於「控制變因」。過去許多比較 diff 與 whole-file 的研究橫跨不同模型、不同資料集與不同編輯格式語法（edit-format syntax），難以判斷效應來源。本文透過固定其餘條件，僅操縱輸出模式，並同時在從頭訓練與微調模型上複製結果，提供了較高的內部效度。此外，將 steps 設計為「單次軌跡、無執行反饋」的簡化版本，也讓研究範圍明確聚焦於「輸出格式作為訓練目標」本身，而非多輪 agentic repair loop。

#### 實驗數據解讀

根據摘要與引言所述，實驗結果呈現一個相當明確且反直覺的結論：**direct generation（直接生成）在幾乎所有指標上均顯著優於 iterative diff-based generation（迭代式 diff 生成）**，而且這個差距無法被簡單歸因於 steps 模型的步驟預算不足或格式錯誤。

##### 1. 整體表現：Direct generation 全面領先

無論是 Rainbow-Pony-100M 還是 Qwen2.5-Coder-0.5B，direct 變體在以下指標皆勝出：

- **Compilation/static-analysis pass rate**：直接生成產生可編譯、可通過靜態分析的程式碼比例更高。
- **BPB（bits-per-byte）**：direct 模型對正確輸出的機率建模更好，代表其對「修改後應長什麼樣子」的內在分佈掌握更精準。
- **Character-level similarity**：輸出與 reference 的字元層級相似度更高。
- **Blinded LLM-judge ratings**：在目標達成度、正確性與程式碼品質三個維度上，direct 模型均獲得較高評分。

這與業界常見直覺——「diff 更短、更便宜、更不容易污染未改動區域」——形成強烈對比。數據顯示，至少在 Flutter/Dart 這個領域，將 diff 作為訓練目標會讓模型整體變弱。

##### 2. 失敗模式分析：多數 diff 失敗並非「套用失敗」

一個重要的細節是，steps 模型的劣勢不能簡單歸咎於 **malformed edits** 或 **apply_failed**。作者指出，**多數 diff-based failures 發生在正常完成的軌跡內（intrajectory）**，也就是說模型成功產生了一連串可被 harness 套用的編輯，但最終結果仍然是錯的。這暗示問題不在於「格式語法沒學好」，而在於 diff 作為訓練目標改變了模型學習到的語義映射：模型可能學會了「如何以 diff 表達修改」，但沒有學會「修改後的完整語義應該是什麼」。

##### 3. 控制任務難度後差距仍然存在

為了排除「diff 模型剛好分到較難任務」的可能性，作者進行 **matched-ID comparison（配對 ID 比較）**：對同一筆任務比較兩種模型的表現。結果顯示差距依舊。此外，當只比較「兩邊都能編譯通過」的程式碼時，direct 模型在 LLM judge 評分上仍然領先。這說明 direct 的優勢不僅是語法層面的，也體現在語義正確性與程式碼品質上。

##### 4. Task locality：diff 模式唯一可勝出的條件

儘管整體落後，作者發現 diff-based 模型並非全無優勢。其勝出案例高度集中於兩類任務：

- **Refactoring（重構）**
- **Error-handling / edge-case fixes（錯誤處理 / 邊界案例修復）**

而這兩類任務恰好是資料集中 **mean edit-step count（平均編輯步驟數）** 最低的類別。換言之，當編輯範圍短、空間集中（spatially localized edits）時，diff 模式具有競爭力；一旦編輯需要跨越多個區域、步驟數增加，diff 模式就會迅速惡化。作者將此統一解釋變數命名為 **task locality（任務局部性）**。

這個發現具有重要的實務意義：diff 並非絕對較差，而是對「長程、非局部」的編輯任務特別脆弱。這也解釋了為何生產級工具在簡單重構時表現良好，但在複雜跨檔案修改時經常需要多次 retry。

#### 與現有研究的比較

##### 1. 與 Aider 編輯格式基準測試的關係

Aider（ongoing）的 **edit-format benchmarks（編輯格式基準測試）** 已經觀察到：diff-style formats 能降低 token 成本，但會增加 **malformed edits** 與 harness 套用失敗的機率，尤其在較弱模型上更明顯。本文的發現與 Aider 一致，但更進一步：作者證明即使排除格式錯誤與套用失敗，diff 模式在語義正確性與品質上仍然落後。這將討論從「介面可靠性」提升到「訓練目標是否改變模型學習品質」的層次。

##### 2. 與 LintSeq 的對比

LintSeq（Piterbarg et al., 2025）主張將參考程式分解為 synthetic edit sequences（合成編輯序列）作為訓練課程（curriculum），能提升下游 code synthesis 的 pass@1。本文的 steps 模型在精神上與 LintSeq 類似（皆以編輯序列作為訓練目標），但應用場景與結論方向相反：LintSeq 針對「從空白開始合成程式」，而本文針對「修改既有檔案（code editing）」。作者認為兩者並不矛盾——在既有語義約束下編輯檔案，與從無到有生成程式，對模型而言是不同分佈，因此 diff 作為訓練目標的效果也可能不同。這提醒研究者不能將 LintSeq 的結論直接外推至 code-editing model。

##### 3. 與 Adaptive-format 研究的互補

Cheng et al.（2026）提出輸出格式應該依每個編輯任務自適應選擇，並訓練 router 在不同格式間切換。本文的 **task locality（任務局部性）** 發現恰好為 adaptive-format（自適應格式）提供了獨立的實證支持：diff 在短程、局部編輯上具有競爭力，在長程、非局部編輯上則弱於 whole-file。這意味著一個能根據任務特性選擇 direct 或 steps 的 router，理論上可超越任何單一固定格式模型。

##### 4. 與 LLM Coding Agent 研究的區隔

本文明確將研究範圍限定為「單次軌跡、無執行反饋」的 steps 模型，而不同於 SWE-bench 風格的多輪迭代 agent（如 Deng et al., 2025; Zhang et al., 2026; Vallecillos Ruiz et al., 2025）。在那些 agentic 設定中，模型會根據測試回饋反覆修正 patch，而本文的 steps 模型沒有這種回饋機制。因此，本文結論不應被解讀為「diff-based agent 無用」，而應理解為「在無反饋的單次生成情境下，將 diff 作為訓練目標會整體削弱模型表現」。

##### 5. 相對於既有研究的改進與限制

**改進之處**：

- 控制變因嚴謹：固定資料集、tokenizer、harness，並跨兩種架構複製結果。
- 區分多種失敗模式，特別指出「正常完成軌跡內的語義錯誤」是 diff 模式的主要問題。
- 提出 task locality 作為統一解釋變數，連結類別層級勝率與軌跡長度。

**限制之處**：

- 領域狹窄：僅限 Flutter/Dart，結論是否適用於 Python、Java、C++ 等語言仍需驗證。
- 無反饋機制：未涵蓋多輪 agentic repair loop，而這正是許多生產級工具的核心。
- 單一檔案編輯：未探討跨檔案（multi-file）修改，而真實軟體工程任務常涉及多檔協調。
- 步驟預算與格式細節：不同 step budget、不同 diff 語法（unified-diff vs. search/replace）可能影響結果，本文雖固定但未必窮盡最佳設定。

#### 可重現性評估

##### 1. 已釋出的資產

根據文中資訊，作者釋出了 Rainbow-Pony-100M 的 **shared pretrained checkpoint（共享預訓練檢查點）**：

- Hugging Face 倉庫：`bbidpa/Rainbow-Pony-100m-Flutter-base`
- 預訓練步數：119,000 steps
- 最終訓練/驗證 loss：1.28 / 1.31
- 詞表大小經後續調整為 16,022 以容納結構化特殊 token

釋出 base checkpoint 對於重現從頭訓練的 direct 與 steps 微調變體是必要且關鍵的資產，因為該模型完全在專案內訓練，沒有公開預訓練模型可替代。

##### 2. 未明確釋出的部分

文中並未明確說明是否釋出：

- 兩個架構的 direct 與 steps **fine-tuned checkpoints（微調後檢查點）**
- 完整的 Flutter/Dart **shared dataset（共享資料集）**
- 訓練程式碼、評估 harness、LLM judge prompt
- 用於產生 synthetic edit sequences 的資料處理 pipeline

由於這些細節對於完全重現四個模型與評估結果至關重要，目前可重現性評估為「部分開放」。研究者可以取得 base model，但要完整復現論文所有數字，仍需作者進一步釋出微調權重、資料與程式碼。

##### 3. 可重現性建議

若作者希望提升可重現性，建議釋出：

1. 四個最終模型權重（Rainbow-Pony-100M direct / steps、Qwen2.5-Coder-0.5B direct / steps）。
2. 訓練與評估程式碼，包含 harness 對 diff 的套用邏輯與 stop reason 分類。
3. 資料集或至少資料產生 pipeline，讓社群能在其他語言驗證 task locality 假說。
4. LLM judge 的完整 prompt 與評分標準，確保盲測評分可被複製。

#### 未來研究方向

##### 1. 自適應格式路由模型（Adaptive-format Router）

本文的 task locality 發現強烈支持「沒有單一最佳輸出格式」的觀點。未來可訓練一個 **router（路由模型）**，在推論前根據任務特性（如預估編輯範圍、類別、程式碼結構）決定使用 direct generation 或 diff-based generation。這將結合兩者優勢：簡單局部編輯用 diff 節省 token，複雜非局部編輯用 whole-file 保證品質。

##### 2. 多輪反饋式 Diff Agent

本文的 steps 模型是單次軌跡、無執行反饋。未來可將 diff-based 輸出模式整合進具備 test feedback 的 **iterative program repair（迭代式程式修復）** agent，觀察在多輪修正情境下，diff 的 token 效率優勢是否能彌補其單次語義正確性較弱的缺點。

##### 3. 跨領域與跨語言驗證

由於本文僅聚焦 Flutter/Dart，未來應在 Python、Java、TypeScript、Rust 等語言上複製相同實驗，檢驗 task locality 是否為通用現象，以及不同語言的語法結構是否會影響 direct 與 diff 的相對表現。

##### 4. 改進 Diff 格式的可靠性

未來可研究如何降低 **malformed edits** 與 **apply_failed** 的發生率，例如：

- 設計更簡潔、對模型更友善的 diff 語法。
- 在訓練時加入「編輯套用檢查」作為輔助任務。
- 使用 constrained decoding 或 grammar-based decoding 強制產生合法 diff。

##### 5. 結合兩種目標的混合訓練課程

未來可探索「先 direct、後 steps」或「交替訓練」的 curriculum，讓模型先學會正確的完整語義映射，再學習如何以 diff 表達。這可能緩解目前 steps 模型「學會格式但學錯語義」的問題。

##### 6. Task Locality 的量化預測器

發展一個能自動衡量任務局部性的指標（例如基於 AST 編輯距離、變數依賴範圍、或預估步驟數），可用於在推論前預測哪種輸出模式較適合，也可作為資料增強與難度分層的依據。

##### 7. 擴展至 Multi-file 與跨模組編輯

真實軟體工程任務常涉及多檔案協調。未來可研究在 multi-file 情境下，diff 與 whole-file 的相對優劣，以及 task locality 是否可從單檔擴展至「跨檔案依賴範圍」。

##### 8. 探討 Token 效率與品質的權衡

雖然本文顯示 diff 在品質上整體落後，但其在 token 效率上的優勢仍具吸引力。未來可進行成本-效益分析（cost-quality trade-off），探討在 inference budget 受限的場景下，是否可透過增加 test-time compute（例如讓 diff 模型多次採樣並驗證）來彌補品質差距。

##### 9. 深入分析 Intrajectory 語義錯誤的成因

未來可使用可解釋性工具（如 attention visualization、probing）分析 steps 模型在正常完成軌跡中為何仍產生語義錯誤，特別是關注模型對「未改動區域」與「改動區域」的注意力分配，以及長程依賴追蹤能力。

## 論文問答

**Q1：這篇論文的核心研究問題是什麼？為什麼要將「直接生成」與「迭代式 diff 生成」視為訓練目標來比較？**  
A：本文探討當大型語言模型被用來修改既有原始碼檔案時，應該讓模型學習一次性輸出整份修改後檔案（直接生成），還是學習輸出一連串搜尋／取代編輯（迭代式 diff 生成，又稱 steps）。過去許多生產級工具把 diff 當作推論階段介面，但較少在同領域、同資料集、同評估框架下，系統性地檢驗它作為訓練目標是否同樣優越。本研究透過固定 Flutter/Dart 資料集與評估框架，訓練四個模型變體，以隔離輸出模式本身對程式碼編輯品質的影響。

**Q2：diff 格式在直覺上有哪些優勢？這些預期優勢是否在本研究中成立？**  
A：diff 格式通常比完整檔案短，因此理論上生成 token 更少、成本更低，也較不容易意外改動模型未被要求修改的程式碼區域；同時它更接近開發者實際提交拉取請求 diff 的工作單位。然而本研究發現，儘管 diff 模型確實生成較少 token，但在編譯／靜態分析通過率、bits-per-byte、字元層級相似度與盲測 LLM 評審分數等所有指標上，直接生成都明顯勝出。這顯示 token 效率與介面直覺並未自動轉化為更高的編輯正確性與品質。

**Q3：既有文獻對編輯格式作為訓練目標的看法為何分歧？本文如何解決這些混淆因子？**  
A：既有研究結果並不一致：LintSeq 指出在合成編輯序列上訓練可提升程式碼合成表現，Aider 的基準測試則發現 diff 格式會增加格式錯誤編輯的比例，而 Cheng 等人主張應依任務自適應選擇格式。這些研究使用不同基礎模型、資料集與編輯格式語法，難以直接比較。本文採用同領域、同資料集、同 tokenization 與同評估框架的設計，訓練從頭訓練的 Rainbow-Pony-100M 與微調的 Qwen2.5-Coder-0.5B 兩種架構，從而將輸出模式效應從其他混淆因子中分離出來。

**Q4：本研究使用了哪兩種模型架構？為什麼要同時訓練從頭訓練與微調模型？**  
A：研究使用一個約 100M 參數、專為本計畫從頭訓練的 Rainbow-Pony-100M，以及一個在預訓練程式碼模型上微調的 Qwen2.5-Coder-0.5B。兩者在容量、預訓練歷史與是否接觸過其他程式語言方面差異極大。透過在兩種架構上都觀察到一致的直接生成優勢，作者能論證該現象並非特定模型族群的偶然結果，而是與輸出模式本身較為相關。

**Q5：「迭代式 diff 生成」在本研究中是如何實作的？模型如何決定何時停止編輯？**  
A：在 steps 模式下，模型會根據原始檔案與任務指令，依序輸出帶有特殊動作標籤的搜尋／取代編輯，每個編輯被機械式地套用到目前檔案狀態上。模型持續產生新步驟，直到它主動發出完成訊號，或達到預設的步驟預算上限為止。這是一種單軌跡、無執行回饋的生成過程，與具有測試回饋的多輪代理程式修復迴路有所不同。

**Q6：什麼是「任務局部性」？它如何解釋 diff 模型何時會表現較好？**  
A：任務局部性是作者提出的單一解釋變數，指編輯是否集中在檔案中少數、短小的區域。研究發現 diff 模型只有在編輯軌跡短、空間局部化時才具有競爭力；其類別層級勝率高度集中在重構與錯誤處理／邊界案例修復這兩類任務，而這兩類正好也是資料集中平均編輯步驟數最低的類別。因此任務局部性統一了軌跡長度與任務類別兩個觀察，說明 diff 訓練適合局部改動，但不適合長程、分散的修改。

**Q7：評估使用了哪些指標與資料規模？最主要的量化結論是什麼？**  
A：研究在約 1,790 個保留測試任務上評估四個模型，指標包含編譯／靜態分析通過率、bits-per-byte、相對參考答案的字元層級相似度，以及盲測 LLM 評審對目標達成度、正確性與程式碼品質的評分。結果顯示直接生成在每一項指標、兩種架構下都大幅領先迭代式 diff 生成。這項優勢在控制任務難度與僅比較雙方都能編譯的樣本後依然存在。

**Q8：diff 模型的失敗主要來自哪些原因？是否只是因為步驟預算用完或格式錯誤？**  
A：diff 模型的失敗並非主要來自步驟預算耗盡或測試框架無法套用的格式錯誤編輯；事實上，大多數失敗發生在軌跡已正常完成的樣本中，即編輯雖然都被成功套用，最終結果卻不正確或品質較差。這意味著 diff 格式的可靠性成本不僅是「無法套用」的機械問題，更涉及模型在生成過程中累積語意錯誤。因此單純增加步驟預算或改善格式解析並無法完全彌補與直接生成的差距。

**Q9：什麼是配對 ID 比較與「雙方皆可編譯」子集分析？它們如何強化結論？**  
A：配對 ID 比較是針對相同任務 ID，直接比較直接生成與 diff 生成模型的表現，以排除 diff 模型可能剛好分配到較難任務的疑慮。「雙方皆可編譯」子集分析則只保留兩種模式產出的程式碼都能通過編譯／靜態分析的樣本，再由盲測 LLM 評審比較品質。兩項分析都顯示直接生成的優勢無法被任務難度或編譯失敗所解釋，進一步鞏固了核心發現。

**Q10：這些發現對生產級程式碼代理或 IDE 整合工具有什麼實務啟示？**  
A：研究結果提醒開發者，不能僅因 diff 格式在介面上更直覺、token 成本更低，就預設它作為訓練目標一定更好；對於涉及長程改動或複雜語意重組的 Flutter/Dart 編輯任務，直接生成可能產生更正確、品質更高的結果。產品團隊應根據任務特性選擇輸出模式，而非全盤採用單一格式。這也暗示未來的程式碼編輯模型可能需要依任務局部性動態決定輸出格式。

**Q11：根據任務局部性，自適應格式或路由模型可能如何設計？**  
A：由於 diff 模型在短、空間局部化的編輯上具有競爭力，而在長程、非局部改動上明顯較弱，一個自適應格式系統可以在推論前預測任務的局部性。若預測為局部改動，則使用 diff 格式以節省 token 並降低無謂改動；若預測為非局部改動，則改用完整檔案直接生成以確保正確性。這種依任務選擇輸出模式的路由模型，有機會結合兩種格式的優點並超越任何固定格式模型。

**Q12：本文結論是否與 LintSeq 等「編輯序列訓練有幫助」的研究互相矛盾？為什麼？**  
A：兩者並不矛盾，而是適用情境不同：LintSeq 研究的是從空白開始合成新程式，透過合成編輯序列作為課程學習；本文則聚焦修改既有、語意受約束的原始碼檔案。在程式碼編輯情境中，模型必須在保留大量未改動程式碼的前提下進行精確修改，這使得 diff 訓練的難度與風險不同於從零生成。因此不同領域與任務型態可能導致不同格式各擅勝場。

**Q13：本研究有哪些主要限制？**  
A：研究僅限於 Flutter/Dart 單一領域與相對小型的 self-contained 程式碼片段，結果是否能推廣到其他程式語言或大型真實程式庫仍需驗證。實驗中的 steps 模型是單軌跡生成，沒有測試或執行回饋，與 SWE-bench 風格的多輪代理程式修復不同。此外，兩個模型規模都偏小，未來在更大參數模型上的表現可能有所變化。

**Q14：直接生成是否也有潛在風險？本文如何檢視這些風險？**  
A：直接生成雖然整體表現較佳，但理論上存在「幻覺式」改動未要求區域的風險，因為模型必須重寫整份檔案。本文透過盲測 LLM 評審的程式碼品質與正確性評分，以及字元層級相似度等指標，間接檢視輸出是否過度偏離參考答案。結果顯示在該資料集上，直接生成並未因此產生較多無謂腐蝕，反而在品質與正確性上持續領先。

**Q15：未來研究可以朝哪些方向延伸？**  
A：未來研究可將比較擴展到更多程式語言、更大規模模型，以及具有執行回饋的多輪代理程式修復情境，以檢驗任務局部性是否仍是關鍵變數。另一方向是開發能根據任務局部性自動選擇格式的路由模型或混合訓練目標，並針對非局部改動改進 diff 模型的長程依賴與軌跡規劃能力。最後，也可探索如何在保持 token 效率的同時，降低 diff 模型在正常完成軌跡中產生的語意錯誤。

## 實務應用指南

### 適用場景

1. **Flutter/Dart IDE 即時重構輔助**  
   當開發者需要執行小範圍、空間集中的重構（例如重新命名變數、提取 Widget、調整 import 順序）時，可採用迭代式 diff 生成。這類任務的平均編輯步驟數低、修改位置集中，diff 模型在正確性與 token 效率上都較有競爭力。

2. **錯誤處理與邊界案例修復機器人**  
   在 CI 或程式碼審查流程中，針對「補上 null check」、「加入 try/catch」、「處理空列表」等局部錯誤處理任務，diff 模式能以較短軌跡完成。適合做成自動修復建議工具，減少對原始碼其他區域的干擾。

3. **大型功能改寫與跨區塊程式碼編輯**  
   當任務涉及新增多個方法、改變狀態管理架構、或同時修改多個不相鄰區段時，應優先採用直接生成。論文顯示直接生成在編譯通過率、目標達成度與程式碼品質上均顯著優於 diff 模式，特別是在長軌跡、非局部化編輯中。

4. **混合式程式碼代理的路由決策**  
   若產品需要同時支援「小修小補」與「大範圍改寫」，可根據任務局部性（task locality）動態選擇輸出模式：短軌跡、空間局部化編輯走 diff；長軌跡或分散式編輯走直接生成，以兼顧效率與品質。

5. **程式碼審查與 diff 預覽生成**  
   由於 diff 模式天然輸出搜尋/取代編輯，適合整合到程式碼審查介面，讓審查者直接看到模型建議的局部變更，並與現有版本控制 diff 格式對接。

### 實作前置條件

- **資料準備**  
  需要成對的 Flutter/Dart 編輯資料：原始檔案、編輯指令、參考修改後檔案，以及對應的編輯軌跡（用於訓練 steps 模型）。資料應涵蓋重構、錯誤處理、UI 調整、狀態管理等類別，並能計算每筆任務的編輯步驟數與修改位置分佈。

- **運算資源**  
  從頭訓練 100M 等級模型需要大量 GPU 時數；若採用微調路線，至少需準備可載入並微調 Qwen2.5-Coder-0.5B 等級模型的 GPU 記憶體。兩種輸出模式都需額外訓練與評估，建議預留足夠運算資源進行對照實驗。

- **Tokenizer 與結構化特殊 token**  
  需在 tokenizer 中加入 `<GOAL>`、`<CODE>` 以及 steps 模式專用的動作標籤（如搜尋/取代標記）。若詞彙表大小調整，記得同步調整模型嵌入層與輸出層。

- **評估框架**  
  必須建置可重複執行的評估框架（harness），包含：編譯/靜態分析檢查、bits-per-byte 計算、字元層級相似度、以及盲測 LLM 評審流程。建議同時支援配對 ID 比較與「雙方皆編譯通過」的子集分析。

- **團隊技能**  
  需要熟悉大型語言模型訓練/微調、Flutter/Dart 語法與靜態分析、資料清洗與軌跡合成，以及具備設計 LLM-as-a-judge 評分提示詞的能力。

### 實作步驟建議

1. **任務分類與局部性量化**  
   先將資料集依任務類別標註（重構、錯誤處理、UI 調整等），並計算每筆任務的平均編輯步驟數與修改區塊的空間分佈。這是後續選擇輸出模式的關鍵依據。

2. **建立共享資料集與 tokenizer**  
   為直接生成與迭代式 diff 生成準備完全相同的訓練與保留測試集，並使用統一的 tokenizer。確保兩種模式在資料與詞彙層面沒有混淆因子。

3. **訓練兩種輸出模式的模型**  
   至少選擇一個從頭訓練模型與一個預訓練微調模型，分別訓練 direct 與 steps 版本。這能驗證結論是否具架構無關性。

4. **建置編輯套用與容錯機制**  
   對於 steps 模型，必須實作穩定的搜尋/取代套用器，並記錄 `apply_failed`、`malformed` 等停止原因。建議加入「套用失敗即退回直接生成」的 fallback 機制。

5. **多維度評估與配對比較**  
   在約 1,800 筆以上的保留任務上評估：編譯/靜態分析通過率、BPB、字元相似度、盲測 LLM 評審分數。接著進行配對 ID 比較，控制任務難度，並只看雙方都編譯通過的樣本。

6. **依任務局部性部署混合策略**  
   根據評估結果，對短軌跡、空間局部化任務啟用 diff 模式；對長軌跡或非局部任務啟用直接生成。可進一步訓練一個輕量 router 自動選擇輸出模式。

7. **持續監控與迭代**  
   上線後追蹤 malformed edits 比例、步驟預算耗盡率、以及使用者接受率。定期用新資料重新校準「任務局部性」門檻。

### 潛在風險與注意事項

- **diff 格式錯誤與套用失敗**  
  論文發現 diff 模式更容易產生測試框架無法套用的格式錯誤編輯，特別是在較弱模型上。建議在套用前驗證搜尋片段是否完全匹配，並設計 fallback。

- **步驟預算耗盡導致半成品**  
  迭代式 diff 生成可能因步驟預算不足而中斷。需監控 `step_budget_exhausted` 比例，並在生產環境設定適當預算或自動切換為直接生成。

- **直接生成的「安靜污染」風險**  
  直接生成雖然整體表現較佳，但會重新輸出整份檔案，可能無意間改動未被要求的部分。建議透過字元相似度與 diff 比對工具檢查額外變更。

- **過度推論到其他領域**  
  本研究僅針對 Flutter/Dart 程式碼編輯，結論不一定適用於其他語言或從零開始的程式碼合成任務。部署前應在自身領域重新驗證。

- **LLM 評審的偏差**  
  盲測 LLM 評審可能偏好某種輸出格式或程式碼風格。建議結合編譯通過率、靜態分析與人工抽樣，避免單一指標誤導決策。

- **訓練成本與維護複雜度**  
  同時維護兩種輸出模式會增加訓練、推論與部署成本。若資源有限，可先從直接生成開始，再針對高局部性任務引入 diff 模式。

---

### 與其他技術的整合建議

- **Language Server Protocol（LSP）與 IDE 外掛**  
  將模型包裝為 LSP 伺服器或 IDE 外掛的後端，根據游標位置與選取範圍判斷任務局部性，自動選擇 diff 或完整檔案輸出。

- **版本控制與 diff 預覽**  
  diff 模式輸出可直接對齊 Git diff 格式，方便整合到 Pull Request 審查介面；直接生成則可透過後處理產生 diff 預覽，讓審查者聚焦變更。

- **檢索增強生成（RAG）**  
  對於大型專案，可先用 RAG 檢索相關檔案與範例，再餵給直接生成模型進行跨檔案改寫；對於局部任務，則只將相關程式碼區塊餵給 diff 模型。

- **多輪代理迴圈（agentic loop）**  
  本研究的 steps 模型是單軌跡、無執行回饋的簡化版本。若需整合到 SWE-bench 風格的多輪修復代理，應加入測試回饋與重試機制，而非直接套用本文的單步驟 diff 模型。

- **CI/CD 自動修復管線**  
  在 CI 中偵測到靜態分析錯誤後，可將錯誤訊息與局部程式碼片段送給 diff 模型產生修復建議，再經編譯驗證後提交為修補建議。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先聚焦在「直接生成 vs. 迭代式 diff 生成」這兩種輸出模式的概念差異，以及論文的核心結論：直接生成在大多數 Flutter/Dart 編輯任務上表現更好，但 diff 模式在短程、局部的重構與錯誤處理任務上仍有優勢。可先閱讀第 1 節與第 4.7 節，建立「任務局部性」的直覺。

**AI 工程師**  
請重點閱讀第 3 節的方法論與第 4 節的實驗設計，特別是兩種模型架構、tokenizer 設計、評估指標與配對 ID 比較的細節。這些內容能幫助你在實作時避免資料洩漏、混淆因子與評估偏差，並決定是否要在自家產品中採用混合輸出策略。

**研究人員**  
建議深入第 2 節相關工作與第 5、6 節的討論，思考本文結論與 LintSeq、Aider benchmark、自適應格式等研究之間的關係。特別值得延伸的是：任務局部性是否為跨語言通用現象？如何設計一個能根據編輯特性自動選擇輸出格式的 router？

**產品經理**  
請優先閱讀第 1 節的動機、第 4.1 節的主要結果與第 4.7 節的任務局部性發現。重點在於理解「token 效率」與「輸出品質」之間的權衡：diff 模式雖然生成 token 較少，但整體可靠性較低；產品設計上應針對高局部性場景使用 diff，並為大範圍改寫保留直接生成或人工介入機制。
