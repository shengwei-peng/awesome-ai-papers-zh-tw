# LongMemEval-V2：邁向資深同事的代理長期記憶體評估

**發布日期：** 2026-05-12

## ⚡ TL;DR

現有代理記憶基準多聚焦用戶歷史或下游任務，無法評估記憶系統能否累積環境專業經驗。
提出LME-V2基準及AgentRunbook-R與-C兩種記憶方法，評估五項核心記憶能力。
AgentRunbook-C達72.5%準確率，超越RAG基準與現成編碼代理，推進帕累托前沿。

## 摘要翻譯

長期記憶對於專門網頁環境中的代理至關重要，其成功取決於回憶介面可供性、狀態動態、工作流程以及反覆出現的失敗模式。然而，現有針對代理的記憶基準測試大多聚焦於用戶歷史、短軌跡或下游任務成功，對於如何直接評估記憶系統是否能有效內化環境特定經驗仍未有定論。為了解決此差距，我們引入 LongMemEval-V2 (LME-V2)，一個用於評估記憶系統是否能幫助代理獲取在客製化環境中成為有知識的同事所需經驗的基準測試。LME-V2 包含 451 個人工策劃的問題，涵蓋網頁代理的五項核心記憶能力：靜態狀態回憶、動態狀態追蹤、工作流程知識、環境陷阱和前提感知。問題與包含最多 500 條軌跡和 115M 詞元 (tokens) 的歷史軌跡配對。我們採用上下文收集框架：記憶系統處理歷史軌跡並為下游問答返回簡明證據。我們提出兩種記憶方法的套件：AgentRunbook-R，一個高效的基於 RAG (Retrieval-Augmented Generation) 的記憶系統，具備用於原始狀態觀察、事件和策略筆記的知識池；以及 AgentRunbook-C，它將軌跡儲存為檔案並調用編碼代理在增強沙盒中收集證據。實驗顯示 AgentRunbook-C 以 72.5% 的平均準確率達到最佳效能，優於最強的 RAG 基準（48.5%）和現成編碼代理基準（69.3%）。儘管效能提升顯著，基於編碼代理的方法具有較高的延遲成本。雖然 AgentRunbook-C 推進了準確率-延遲帕累托前沿，但仍有大幅改進空間。這些結果共同確立了 LME-V2 作為一個具挑戰性的測試平台，用於開發能累積環境經驗的長期記憶系統。

### 核心貢獻（3～5點）
- 提出 LongMemEval-V2 (LME-V2) 基準測試，填補現有代理記憶評估在「環境經驗內化」面向的研究缺口
- 涵蓋五項核心記憶能力（靜態狀態回憶、動態狀態追蹤、工作流程知識、環境陷阱、前提感知），共收錄 451 道人工策劃問題
- 設計「上下文收集框架」評估形式，使記憶系統從歷史軌跡中萃取簡明證據以支援下游問答
- 提出兩種互補的記憶方法：AgentRunbook-R（基於 RAG 的高效記憶系統）與 AgentRunbook-C（基於編碼代理的證據收集方法），其中 AgentRunbook-C 以 72.5% 平均準確率刷新效能紀錄
- 系統揭示準確率與延遲之間的權衡關係，為未來長期記憶系統的設計與改進指明方向

### 適合對象
從事大型語言模型 (LLM)、代理系統、檢索增強生成 (RAG) 與長期記憶機制研究的學者與工程師；特別適合關注網頁代理、編碼代理於專門環境中經驗累積與工作流程自動化之研究團隊，以及欲建立領域專用代理記憶評測平台的實務開發者。

## 深度分析

#### 方法論解析

LME-V2 的方法論設計體現了「以代理記憶體模擬資深同事經驗累積」的核心思想，其架構可從三個層面深入剖析。

**1. 問題形式化：上下文收集形式化 (Context Gathering Formulation)**

論文提出了一套介面簡潔但評估嚴謹的形式化框架。記憶系統僅需實作兩個 API：`Insert`（消費單條軌跡）與 `Query`（針對問題回傳多模態記憶上下文）。此設計巧妙地將記憶系統與下游推理解耦——系統只需負責「從雜亂軌跡中萃取簡明證據 (compact evidence)」，而最終問答由固定的讀取器 LLM 完成。這種設計避免了「以任務成功率間接評估記憶品質」的偏差，能直接測量記憶系統本身的證據收集能力。對於每個問題，系統需依序串流處理關聯軌跡（最多 500 條、115M 詞元），並在固定詞元預算下回傳證據，這對記憶系統的儲存效率與檢索精準度提出了雙重挑戰。

**2. 五項核心記憶能力 (Memory Abilities) 的設計**

LME-V2 將「成為資深同事」這一抽象目標分解為五項可獨立評估的能力：

- **靜態狀態回憶 (Static State Recall)**：測試代理能否記住介面可供性 (interface affordances) 等低階觀察，例如「事故表單右上角比變更請求表單多出的按鈕是什麼」。
- **動態狀態追蹤 (Dynamic State Tracking)**：測試代理能否追蹤狀態隨動作的演變，例如問題被標記為「重複」且進度從「評估」變為「已關閉」時，狀態欄位下方的欄位變化。
- **工作流程知識 (Workflow Knowledge)**：測試代理能否從多條軌跡中歸納出典型操作序列，例如「過濾並移除重複問題時，哪些欄位最關鍵」。
- **環境陷阱 (Environment Gotchas)**：測試代理能否記住反覆出現的失敗模式 (recurring failure modes) 與隱藏失敗模式 (hidden failure modes)，例如硬體資產清單中「指派給」欄位搜尋邏輯的預設行為。
- **前提感知 (Premise Awareness)**：測試代理能否識別問題中的錯誤前提並正確回應，例如當問題假設某個不存在的欄位時，代理應回答「無此欄位」而非編造答案。

這五項能力涵蓋了從低階感知到高階推理的完整光譜，特別是「前提感知」這項設計，突破了傳統基準測試僅追求「正確答案」的單一維度。

**3. 兩種記憶方法的設計哲學**

**AgentRunbook-R** 採用檢索增強生成 (RAG) 架構，靈感來自 Xu et al. [2025] 的代理記憶體工作。其核心是三個知識池 (knowledge pools)：
- **原始狀態觀察 (Raw State Observations)**：儲存低階介面狀態。
- **狀態轉換事件 (State Transition Events)**：記錄動作引發的狀態變化。
- **策略筆記 (Strategy Notes)**：儲存高階策略性知識。

LLM 控制器主動更新與查詢這三個池子，兼顧效率與覆蓋面。然而，論文明確指出此設計「未針對細粒度證據選擇最佳化」，這是其準確率受限的根本原因。

**AgentRunbook-C** 則將記憶管理重新詮釋為檔案管理問題，受 Cao et al. [2026] 啟發。它將軌跡儲存為檔案，並在增強沙盒 (augmented sandbox) 中調用編碼代理 (coding agent) 來收集證據。這種設計的優勢在於：編碼代理能撰寫程式碼進行靈活的證據過濾與聚合，而非受限於預定義的檢索模板。但代價是高延遲成本，這也是論文反覆強調的權衡點。

#### 實驗數據解讀

**1. 整體準確率對比**

實驗結果呈現清晰的層級結構：
- AgentRunbook-C：**72.5%** 平均準確率
- 現成編碼代理基準 (off-the-shelf coding agent baseline)：**69.3%**
- 最強 RAG 基準：**48.5%**

AgentRunbook-C 相較最強 RAG 基準提升 24 個百分點，這在基準測試中是相當顯著的進步。然而，相較現成編碼代理僅提升 3.2 個百分點，顯示其增益主要來自於「編碼代理範式」本身，而非 AgentRunbook-C 的特殊設計。這暗示了一個重要洞見：在高度複雜的軌跡環境中，賦予代理程式碼撰寫能力比精巧的記憶結構設計更為關鍵。

**2. 準確率-延遲帕累托前沿 (Accuracy-Latency Pareto Frontier)**

論文強調 AgentRunbook-C「推進了準確率-延遲帕累托前沿」，但同時承認「實質性改進空間仍然存在」。這意味著：
- AgentRunbook-R 在延遲維度佔優，但準確率不足。
- AgentRunbook-C 在準確率維度領先，但延遲成本高昂。
- 現成編碼代理位於兩者之間，但缺乏針對性最佳化。

這種權衡關係揭示了記憶系統設計中的根本張力：細粒度證據選擇需要更多計算資源，而即時部署需求則要求低延遲回應。

**3. 規模效應分析**

LME-V2 提供兩個規模層級：
- **LME-V2-Small**：100 條軌跡、25M 詞元，所有問題共用同一軌跡堆。
- **LME-V2-Medium**：500 條軌跡、115M 詞元，每個問題有專屬軌跡堆。

從 Small 到 Medium，詞元規模增加 4.6 倍，但問題數量相同。這種設計允許研究者隔離「規模效應」與「問題多樣性效應」。值得注意的是，115M 詞元的規模遠超現有代理記憶體基準（如 MemoryArena 的 40k+ 詞元），這對記憶系統的壓縮與檢索效率提出了極高要求。

**4. 環境覆蓋的實證意義**

基準測試涵蓋 Magento 購物、購物管理後台、Postmill 論壇、ServiceNow（來自 WebArena 與 WorkArena）四個客製化環境。這些環境的共同特徵是「專門化」——它們模擬企業內部系統，而非通用網頁。這意味著前沿 LLM 的預訓練知識覆蓋有限，必須依賴記憶系統從軌跡中學習，這正是 LME-V2 能有效區分不同記憶方法的關鍵。

#### 與現有研究的比較

**1. 與長上下文基準的比較**

從表 1 的對比可見，LME-V2 在多個維度上獨樹一幟：
- **詞元規模**：25M–115M 詞元，遠超 LongBench V2（260k）、MemoryAgentBench（285k）、CL-Bench（10k）。
- **多模態支援**：是少數同時支援上下文與問題多模態的基準。
- **能力覆蓋**：唯一同時涵蓋靜態、動態、工作流程、陷阱、前提感知五項能力的基準。

相較之下，LongMemEval-V1 雖有 115k–1.5M 詞元規模，但僅涵蓋用戶-助手對話，缺乏代理軌跡的複雜性。PersonaMem 與 BEAM 雖規模可觀，但聚焦於用戶歷史而非環境經驗。

**2. 與代理記憶體基準的比較**

在代理領域，現有基準各有局限：
- **MemoryArena**：僅 7 個會話、40k+ 詞元，規模過小。
- **AgentLongBench**：聚焦遊戲代理，僅 1 條軌跡，無法測試跨軌跡記憶。
- **EMemBench**：雖涵蓋五項能力中的四項，但同樣僅 1 條軌跡。
- **FileGramBench**：聚焦檔案系統代理，僅 12 個會話。
- **AMA-Bench**：雖有 57k 詞元，但僅 1 條軌跡。

LME-V2 的核心突破在於「跨軌跡依賴」——問題的答案往往散佈在多條軌跡中，需要記憶系統進行關聯推理，而非簡單的單軌跡檢索。

**3. 改進與侷限**

**改進**：
- 首次將「環境經驗累積」作為記憶評估的直接目標。
- 前提感知能力的引入，突破了「正確答案唯一」的傳統假設。
- 上下文收集形式化提供了實用的 API 介面，便於下游代理整合。

**侷限**：
- 451 個問題的規模相對有限，可能限制統計顯著性。
- 環境僅限於四個 WebArena/WorkArena 場域，泛化性有待驗證。
- 編碼代理方法的高延遲使其難以應用於即時互動場景。
- 評估依賴固定的讀取器 LLM，可能無法完全反映記憶系統在不同推理模型下的表現。

#### 可重現性評估

**1. 程式碼與資料集**

從論文提供的資訊判斷：
- **基準測試資料**：451 個手動策展的問題及其對應軌跡應會公開釋出，這是基準測試論文的標準做法。
- **評估框架**：上下文收集形式化的 API 介面（Insert/Query）應會提供參考實作。
- **AgentRunbook-R 與 AgentRunbook-C**：作為論文的兩種核心方法，其程式碼應會開源。

**2. 模型權重**

兩種方法均基於現有 LLM 與編碼代理構建，未訓練新模型，因此不涉及模型權重釋出問題。實驗應會詳細記錄所使用的底層模型版本，以便重現。

**3. 潛在重現障礙**

- **軌跡生成成本**：500 條軌跡的生成需要大量 API 呼叫，重現成本不低。
- **編碼代理的隨機性**：編碼代理方法可能存在較高的執行隨機性，需要多次運行取平均。
- **環境存取權限**：WebArena 與 WorkArena 環境的部署可能存在技術門檻。

**4. 評估指標透明度**

論文明確報告了準確率與查詢延遲兩項指標，並強調了帕累托前沿分析，這有助於研究者進行公平比較。

#### 未來研究方向

**1. 降低編碼代理方法的延遲**

AgentRunbook-C 的高延遲是主要瓶頸。未來研究可探索：
- **預計算策略**：對常見問題類型預先生成證據收集腳本。
- **層級化架構**：先用輕量 RAG 過濾候選軌跡，再調用編碼代理精煉。
- **並行化證據收集**：將證據收集任務分解為可並行執行的子任務。

**2. 強化細粒度證據選擇**

AgentRunbook-R 的 48.5% 準確率顯示其在證據選擇上仍有大幅改進空間。未來可研究：
- **神經符號混合方法**：結合符號推理與神經檢索。
- **強化學習最佳化**：以問題回答準確率作為獎勵信號，端到端最佳化證據選擇策略。
- **多跳推理增強**：針對需要跨軌跡關聯推理的問題設計專門機制。

**3. 擴展環境與任務多樣性**

目前僅涵蓋四個 WebArena/WorkArena 環境，未來可考慮：
- **企業 SaaS 應用**：如 Salesforce、Jira、Confluence 等。
- **專業領域工具**：如醫療資訊系統、財務軟體。
- **多語言環境**：測試記憶系統在不同語言介面下的表現。

**4. 動態環境適應**

當前基準假設環境靜態，但真實環境會持續演進。未來可研究：
- **環境漂移偵測**：自動識別介面或工作流程的變化。
- **記憶更新策略**：在保留歷史經驗的同時整合新觀察。
- **版本化記憶**：追蹤環境變化對記憶有效性的影響。

**5. 與人類專家的對齊評估**

「成為資深同事」的目標最終應以人類專家的判斷為基準。未來可：
- **收集人類專家標註**：驗證基準問題的合理性與答案正確性。
- **設計人機協作評估**：測試記憶系統在輔助人類專家時的實際效用。
- **長期縱向研究**：追蹤代理在持續使用記憶系統後的經驗累積軌跡。

**6. 理論框架的建立**

目前記憶系統設計仍以經驗為主，未來可探索：
- **資訊理論視角**：量化軌跡中的資訊量與記憶系統的資訊保留率。
- **認知科學借鑑**：從人類專家記憶機制中汲取靈感。
- **可解釋性研究**：理解記憶系統為何選擇特定證據，以及其推理過程是否合理。

**7. 安全與隱私考量**

當記憶系統儲存大量軌跡時，可能包含敏感資訊。未來需研究：
- **隱私保護記憶**：在保留經驗的同時遮罩敏感細節。
- **記憶審計機制**：追蹤記憶內容的來源與使用情況。
- **對抗性攻擊防禦**：防止惡意軌跡污染記憶系統。

總結而言，LME-V2 為代理記憶體研究建立了重要的基準測試，其「成為資深同事」的框架為未來研究提供了清晰的方向指引。然而，準確率與延遲的權衡、跨環境泛化、以及動態環境適應等挑戰，仍需學界持續探索。

## 論文問答

**Q1：為什麼現有的代理記憶體基準測試無法有效評估長期記憶系統？**
A：現有的記憶體基準測試主要聚焦於用戶歷史紀錄、短軌跡或下游任務的成功率，無法直接衡量記憶系統是否真正內化了環境特定的經驗。這類基準測試通常使用簡化的遊戲環境，或僅強調單一或少數軌跡之間的有限依賴關係，因而難以反映代理在複雜環境中長期互動所累積的整體性、專業性知識。這正是 LME-V2 試圖填補的核心缺口——它將評估焦點從「能否完成任務」轉向「是否成為該環境的資深同事」。

**Q2：LME-V2 所定義的「資深同事」概念為何重要？**
A：「資深同事」這個框架強調記憶系統的目標不僅是儲存資訊，而是要讓代理能像熟悉該環境的人類專家一樣運作。這意味著代理需要記住介面可供性、狀態動態、工作流程以及反覆出現的失敗模式等細節。透過這個視角，記憶品質可以直接被評估為「環境專業知識的累積程度」，而非僅僅是任務完成率，這對實際部署中的代理系統具有深遠意義。

**Q3：為什麼現有方法在 LME-V2 上表現不佳？**
A：流行的代理記憶體方法通常偏向處理較少雜訊的對話式上下文，或僅專注於高層次的策略性知識，因此在面對 LME-V2 中充滿雜訊的代理軌跡時顯得力不從心。LME-V2 要求記憶系統同時保留低階觀察與高階環境動態及程序性知識，這對僅設計來處理單一類型資訊的系統構成嚴峻挑戰。此外，問題的答案僅散落在大量軌跡中的少數「針」中，需要精細的證據收集能力才能正確回答。

**Q4：LME-V2 採用什麼樣的評估形式化方法？**
A：LME-V2 採用「上下文收集形式化」（context gathering formulation），記憶系統需實作兩個 API：Insert（接收軌跡並儲存）與 Query（針對問題回傳多模態記憶上下文）。每個問題會將相關軌跡依序串流注入記憶體，再呼叫 Query 取得證據，最後截斷至固定詞元預算後交由固定的讀取器 LLM 回答。這種設計提供了一個實用的介面，能直接評估記憶品質，同時模擬下游代理實際使用記憶體的方式。

**Q5：AgentRunbook-R 與 AgentRunbook-C 的核心差異為何？**
A：AgentRunbook-R 是一個高效的 RAG 流程，提示 LLM 控制器更新並主動查詢三個知識池：原始觀察、狀態轉換事件與高階策略筆記，設計上兼顧效率並涵蓋主要記憶能力。AgentRunbook-C 則將記憶管理重新詮釋為檔案管理問題，將軌跡儲存為檔案並在增強沙盒中調用編碼代理來收集證據，雖然延遲較高，但在證據選擇的細緻度上表現更佳。兩者分別針對效率與準確率進行最佳化，共同推進了準確率-延遲帕累托前沿。

**Q6：為什麼選擇「編碼代理」作為記憶體管理機制？**
A：編碼代理擅長在大型檔案系統中進行精細的證據搜尋與彙整，這正好對應 LME-V2 中需要在數百條軌跡裡找出少量相關「針」的需求。將軌跡視為檔案並讓編碼代理在沙盒環境中自主探索，能靈活運用 grep、讀取、彙整等操作，比純文字 RAG 更能處理結構化與非結構化資訊。這種設計靈感來自 Cao 等人的研究，證明了編碼代理在複雜資訊檢索任務上的潛力。

**Q7：LME-V2 與其他基準測試相比有何獨特之處？**
A：LME-V2 在多個維度上超越了現有基準測試：它擁有 25M 至 115M 詞元的深度上下文（遠高於多數基準）、涵蓋五項完整的記憶能力（靜態、動態、工作流程、陷阱、前提感知），並且是少數支援多模態（文字與影像混合）的代理記憶體基準。此外，它的問題是針對客製化環境手動策劃的，因此對近期的前沿 LLM 而言基本上是無法直接回答的，這確保了評估的鑑別力。

**Q8：實驗中各方法的表現如何？**
A：AgentRunbook-C 以 72.5% 的平均準確率奪冠，明顯優於最強的 RAG 基準（48.5%）與現成編碼代理基準（69.3%）。這個結果顯示，雖然編碼代理本身已具備不錯的能力，但透過 AgentRunbook-C 的檔案管理設計能進一步釋放其潛力。然而，編碼代理方法的延遲成本較高，這凸顯了效率與準確率之間的權衡，也說明為何需要 AgentRunbook-R 這類高效方案作為另一個選擇。

**Q9：LME-V2 的問題設計涵蓋哪些記憶能力？**
A：LME-V2 涵蓋五項核心記憶能力：靜態狀態回憶（介面元素的固定屬性）、動態狀態追蹤（狀態隨操作改變的過程）、工作流程知識（典型任務步驟）、環境陷阱（隱藏的失敗模式或反直觉行為）以及前提感知（判斷問題前提是否成立）。圖 1 中的範例清楚展示了這些能力的差異，例如「incident 表單右上角多出的按鈕」屬於靜態回憶，而「Duplicate 後 State 下方出現的欄位」則屬於動態追蹤。

**Q10：LME-V2 在實際應用中有哪些潛在場景？**
A：LME-V2 的設計直接對應企業內部系統自動化、客服代理、IT 服務管理（如 ServiceNow）等需要長期熟悉特定環境的場景。例如，一個代理在反覆處理 Magento 後台或 ServiceNow 工單後，應能記住哪些欄位容易出錯、哪些按鈕有特殊行為，從而像資深員工一樣高效處理例行工作。這種「經驗累積」能力對於降低企業部署代理的維運成本至關重要。

**Q11：在產品化部署時應考量哪些權衡？**
A：產品化時最關鍵的權衡是準確率與延遲之間的取捨——AgentRunbook-C 雖然準確率最高，但延遲成本使其未必適合即時互動場景；AgentRunbook-R 則提供了更實用的回應速度。另一個考量是記憶體的維護成本：隨著軌跡累積，儲存與索引的開銷會持續增加，因此需要設計合理的淘汰或摘要機制。此外，多模態支援（文字與影像）對於真實網頁環境是不可或缺的，這也增加了工程複雜度。

**Q12：這項研究對代理研究領域有何影響？**
A：LME-V2 將記憶體評估從「任務結果」轉向「環境專業知識」，為代理研究提供了一個更貼近真實部署需求的衡量標準。它促使研究者關注如何從大量雜訊軌跡中提煉結構化經驗，而非僅僅優化單次任務的表現。此外，透過同時推進準確率-延遲帕累托前沿，該研究也鼓勵社群在效率與效果之間尋求更細緻的平衡，而非僅追求單一指標的極致表現。

**Q13：LME-V2 存在哪些已承認的限制？**
A：LME-V2 目前僅涵蓋 WebArena 與 WorkArena 中的客製化網站（Magento、Postmill、ServiceNow 等），環境多樣性仍有限，可能無法完全代表所有類型的代理應用。此外，問題仰賴人工策劃，雖然確保了品質，但也限制了規模擴展的速度。編碼代理方法的高延遲成本則是另一個實際部署上的瓶頸，特別是對於需要即時回應的場景。

**Q14：哪些類型的問題最容易讓現有方法失敗？**
A：根據圖 1 的範例，「前提感知」類問題對現有方法特別困難，因為它們要求代理判斷問題前提是否成立（例如「沒有這樣的欄位」），這需要對環境有全面且細緻的理解，而非單純的資訊檢索。「環境陷阱」類問題同樣具挑戰性，因為它們涉及隱藏的失敗模式或反直觉行為，這些資訊往往散落在失敗軌跡中且容易被忽略。此外，跨多條軌跡進行綜合推理的「工作流程知識」問題也需要更強的證據整合能力。

**Q15：未來的研究方向有哪些？**
A：未來可朝幾個方向延伸：首先是擴展環境多樣性，納入更多類型的客製化系統以提升基準的代表性；其次是發展更高效的編碼代理記憶體方法，在維持準確率的前提下降低延遲；此外，自動化的問題生成與品質控制機制將有助於擴大基準規模；最後，結合多模態資訊（影像、點擊序列）進行更細緻的證據收集，以及探索記憶體的動態更新與遺忘機制，都是值得深入探索的方向。

## 實務應用指南

### 適用場景

**1. 企業內部系統操作助理（ServiceNow / SAP / Workday 等）**
針對企業內部 IT 服務管理、ERP、HR 系統等客製化網頁環境，部署具備長期記憶的代理。代理能記住表單欄位差異、隱藏按鈕、狀態流轉規則等「資深同事才知道」的細節，協助新進員工或缺乏經驗的操作者正確完成 Incident、Change Request、Problem 等工單流程。

**2. 電商後台管理自動化（Magento / Shopify Admin）**
在 Magento 商城管理後台、訂單處理系統、庫存管理介面等場景中，代理透過長期記憶累積對促銷規則設定、訂單狀態轉換、退款流程陷阱等領域知識，避免每次操作都需重新探索介面，顯著降低操作錯誤率。

**3. 社群論壇內容審核與管理（Postmill / Discourse）**
針對客製化論壇系統，代理可記憶版主操作流程、隱藏的審核規則、使用者權限邊界等 gotchas，協助進行內容審核、檢舉處理、版務管理等需要細緻環境知識的工作。

**4. 跨系統資料遷移與整合專案**
當企業進行系統升級或遷移時，代理可作為「經驗豐富的同事」，記錄舊系統與新系統的欄位對應、狀態差異、特殊處理邏輯，協助開發團隊快速掌握環境特性，減少試錯成本。

**5. 客服與技術支援知識傳承**
將資深客服人員的操作軌跡作為記憶來源，讓 AI 代理學習如何在特定客服系統中處理複雜案件、識別常見陷阱（如特定欄位的預設行為、隱藏的驗證規則），成為新進客服的虛擬導師。

### 實作前置條件

**資料前置條件**
- **歷史軌跡資料**：需蒐集目標環境中代理或人類操作者的完整軌跡（任務、動作序列、螢幕截圖、結果），每個問題需配對 100–500 條軌跡作為「乾草堆」
- **領域專家標註**：需具備目標系統深度使用經驗的人員，手工設計涵蓋五項記憶能力（靜態狀態回憶、動態狀態追蹤、工作流程知識、環境陷阱、前提感知）的問題與答案
- **多模態資料**：軌跡需包含文字動作與螢幕截圖（HTML / 影像），因為 LME-V2 強調多模態記憶
- **環境配置**：需部署 WebArena / WorkArena 等基準環境，或自建對應的客製化網頁沙盒

**計算資源前置條件**
- **LLM API 存取**：需使用具備長上下文處理能力的前端模型（如 GPT-4o、Claude、Gemini 等）作為 reader LLM
- **編碼代理環境**：若採用 AgentRunbook-C，需配置可執行程式碼的增強沙盒（augmented sandbox），允許代理讀寫檔案、執行 Python 腳本
- **向量資料庫**：AgentRunbook-R 需要向量檢索基礎設施（如 FAISS、Milvus、Pinecone）以支援三個知識池的檢索
- **儲存空間**：單一問題的軌跡可達 115M tokens，需準備對應的儲存與索引空間

**技能前置條件**
- **LLM 應用開發經驗**：熟悉 prompt engineering、function calling、agent orchestration
- **RAG 系統建置能力**：理解 chunking、embedding、retrieval、reranking 等技術
- **軌跡資料處理**：能將原始操作日誌轉換為結構化的「任務—動作—結果」格式
- **領域知識**：對目標企業系統（ServiceNow、Magento 等）的業務流程有基本理解
- **評估方法設計**：能設計記憶品質的評估指標（準確率、延遲、覆蓋率）

### 實作步驟建議

**步驟一：界定記憶目標與環境邊界**
明確界定代理需要「成為資深同事」的具體環境與任務範圍。建議從單一系統（如 ServiceNow Incident Management）開始，而非一開始就覆蓋所有企業系統。參考 LME-V2 的五項記憶能力框架，列出該環境中需要記憶的具體面向。

**步驟二：蒐集與標註歷史軌跡**
部署網頁代理（可基於 Browser-Use、Stagehand 等框架）在目標環境中執行大量任務，蒐集 100–500 條軌跡作為記憶原料。每條軌跡應包含：任務描述、動作序列、螢幕狀態、最終結果。邀請領域專家設計 50–100 個涵蓋五項記憶能力的問題，並標註對應答案。

**步驟三：選擇記憶方法（決策樹）**
- 若**延遲敏感**（如即時客服輔助）：選擇 **AgentRunbook-R**，其 RAG 架構延遲較低，但證據選擇精細度有限
- 若**準確率優先**（如批次資料處理、複雜決策）：選擇 **AgentRunbook-C**，其編碼代理方法可達 72.5% 準確率，但需承受較高延遲成本
- 若資源有限：可先實作 AgentRunbook-R 的簡化版（單一知識池），再逐步擴充

**步驟四：實作記憶系統的兩個 API**
按照 LME-V2 的 context gathering 形式化，實作兩個核心介面：
- `Insert(trajectory)`：將軌跡寫入記憶系統
- `Query(question, token_budget)`：回傳簡明證據（compact evidence）供下游 LLM 回答

**步驟五：建立評估管線**
建立自動化評估流程：(1) 串流注入軌跡到記憶系統 → (2) 呼叫 Query 取得證據 → (3) 截斷到固定 token 預算 → (4) 餵給固定的 reader LLM → (5) 比對答案並記錄延遲。建議同時追蹤準確率與延遲，繪製 Pareto frontier。

**步驟六：迭代優化與領域調適**
根據評估結果，調整知識池的更新策略、檢索參數、reranking 邏輯。針對環境陷阱（gotchas）類問題特別加權，因為這是 LME-V2 中最難的能力之一。持續蒐集新軌跡以擴充記憶。

**步驟七：部署與監控**
將記憶系統整合到實際代理工作流中，建立監控儀表板追蹤：記憶命中率、證據品質分數、答案準確率、查詢延遲分佈。設定定期的記憶品質審查機制。

### 潛在風險與注意事項

**風險一：軌跡品質參差不齊導致記憶污染**
- **現象**：低品質或錯誤的操作軌跡被寫入記憶，導致代理學習到錯誤的「經驗」
- **緩解**：在 `Insert` 階段加入品質過濾機制，僅保留成功軌跡或經專家驗證的軌跡；對失敗軌跡標註失敗原因，作為「環境陷阱」記憶的正面教材

**風險二：記憶膨脹與檢索效率下降**
- **現象**：隨著軌跡累積，知識池規模爆炸，檢索延遲增加、相關性下降
- **緩解**：實作記憶蒸餾（memory distillation）機制，定期將低層級觀察合併為高層級策略筆記；設定記憶生命週期，淘汰過時資訊

**風險三：編碼代理方法的延遲成本過高**
- **現象**：AgentRunbook-C 雖然準確率達 72.5%，但編碼代理的迭代執行導致單次查詢可能耗時數分鐘
- **緩解**：採用混合策略——簡單問題走 RAG 快速通道，複雜問題才啟動編碼代理；對編碼代理設定超時上限與快取機制

**風險四：環境變更導致記憶失效**
- **現象**：系統升級或介面改版後，舊軌跡中的介面可供性、狀態規則不再適用
- **緩解**：為每筆記憶加上時間戳記與環境版本標籤；建立記憶失效偵測機制，當新軌跡與舊記憶矛盾時觸發更新

**風險五：隱私與合規風險**
- **現象**：軌跡中可能包含敏感資料（客戶資訊、內部流程），長期記憶會放大洩漏風險
- **緩解**：在 `Insert` 階段實作 PII 偵測與遮罩；對記憶內容進行加密儲存；設定存取權限控管

**風險六：評估結果無法泛化到真實任務**
- **現象**：在 LME-V2 基準上表現良好，但在實際業務場景中表現不佳
- **緩解**：除基準測試外，建立業務專屬的黃金評估集；採用 A/B 測試在真實流量中驗證記憶系統價值

### 與其他技術的整合建議

**與現有 RAG 框架整合**
AgentRunbook-R 的三知識池架構（原始觀察、狀態轉移事件、策略筆記）可整合到 LangChain、LlamaIndex 等框架中。建議將三個知識池映射為三個獨立的 retriever，並在最終階段做結果融合與 reranking。

**與代理框架整合（LangGraph / AutoGen / CrewAI）**
將記憶系統封裝為代理可呼叫的工具（tool），在代理的決策迴圈中，於執行任務前先查詢記憶取得相關證據。可設計為「記憶預載」步驟，在代理啟動時自動載入與當前任務相關的環境知識。

**與觀測與監控平台整合（LangSmith / Phoenix / Helicone）**
將記憶系統的 `Insert` 與 `Query` 呼叫納入追蹤，記錄：寫入的軌跡摘要、檢索到的證據、使用的 token 數、查詢延遲。這些遙測資料對持續優化記憶品質至關重要。

**與企業知識管理系統整合（Confluence / Notion / SharePoint）**
將從軌跡提煉出的策略筆記同步到企業知識庫，讓人類員工也能受益於代理累積的經驗；反過來，人類在知識庫中的更新也可回流到代理記憶。

**與多代理系統整合**
在多代理架構中，可指定一個專門的「記憶管理代理」負責軌跡整理與證據收集，其他任務代理透過標準介面查詢。這與 AgentRunbook-C 的設計理念一致——將記憶管理視為獨立的編碼任務。

**與人類回饋機制整合（RLHF / RLAIF）**
蒐集人類對代理答案的評價，將「記憶是否提供有用證據」作為獎勵信號，用於微調記憶系統的更新與檢索策略。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀論文第 1 節（Introduction）與第 3.1 節（記憶能力定義），理解「為什麼代理需要長期記憶」以及「五項記憶能力」的具體含義。圖 1 的範例非常直觀，能幫助你快速掌握問題類型。接著可跳讀第 4 節了解兩種記憶方法的高層次設計思路，不必深究實作細節。重點是建立「記憶讓代理成為資深同事」這個核心心智模型。

**給 AI 工程師**：重點閱讀第 3.3 節的 context gathering 形式化與第 4 節的 AgentRunbook-R / AgentRunbook-C 實作細節。特別注意兩個方法的權衡：RAG 延遲低但證據選擇粗，編碼代理準確率高但成本高。建議直接從 AgentRunbook-R 開始實作，因為其架構較簡單且易於整合到現有 RAG 流程；待系統穩定後再評估是否升級到 AgentRunbook-C。實作時務必建立完整的評估管線，因為記憶品質的進步需要可量化的指標。

**給研究者**：論文的真正貢獻在於 (1) 提出「記憶讓代理成為資深同事」的新視角，區別於既有以用戶歷史或下游任務為中心的評估；(2) 設計涵蓋五項記憶能力的綜合基準；(3) 揭示編碼代理作為記憶管理工具的潛力。建議關注第 5 節的實驗分析，特別是不同記憶能力間的難度差異，以及為何 gotchas 與 premise awareness 特別具挑戰性。未來研究方向可考慮：跨環境記憶遷移、記憶蒸餾理論、結合符號與神經方法的混合記憶架構。

**給產品經理**：這篇論文的價值在於揭示了一個被低估的市場需求——企業內部系統的操作知識傳承。產品定位可考慮：(1) 企業內部系統的 AI 助手，差異化賣點是「比新人更快上手，比老人更穩定」；(2) 系統遷移期的過渡助手；(3) 客服與 IT 支援的經驗放大器。商業模式上可考慮按「記憶覆蓋的系統數量」或「查詢量」計費。技術決策上需權衡 AgentRunbook-R（成本低、延遲低、準確率中等）與 AgentRunbook-C（成本高、延遲高、準確率高）的適用場景，建議 MVP 階段採用 RAG 方案，進階服務再引入編碼代理。
