## ⚡ TL;DR

現有檢索器僅能處理單一知識來源，導致異質資料彼此割裂且難以互通。
本框架依自然語言問題自動選擇知識來源，並以各來源原生查詢語言檢索，保留其結構優勢。
跨十三個資料集與三百零九個知識庫的實驗顯示，其效能超越單一來源基線並能產生有效的原生查詢。

## 摘要翻譯

真實世界的資訊需求須存取結構多樣的知識來源（Knowledge Sources），從非結構化文本（Unstructured Text）、關聯式資料表（Relational Tables）到知識圖譜（Knowledge Graphs）與屬性圖（Property Graphs）。然而，現有的檢索器（Retrievers）一次僅能針對單一來源運作，並受限於固定的查詢語言（Query Language），使得更廣闊的可用知識版圖因介面不相容而支離破碎。直觀上，統一的作法是將這些來源收斂至單一共享空間，但這會抹除結構可供性（Structural Affordances）——例如綱要（Schemas）、本體（Ontologies）、組合運算子（Compositional Operators）——而這些正是賦予每個來源表達能力的要素。因此，對多樣知識進行有效檢索，所需的並非同質化（Homogenization），而是一個能夠依各來源自身特性與之對接的統整層。為達成此目標，我們提出 OmniRetrieval，一個能夠接受任何自然語言查詢（Natural-Language Query）、識別適當的知識來源，並將來源原生查詢（Source-Native Queries）分派至其原生執行引擎（Native Execution Engines）的框架。在一項涵蓋 13 個資料集（Datasets）與 309 個不同知識庫（Knowledge Bases）、橫跨文本、關聯式與圖結構來源的廣泛基準測試（Benchmark）中，OmniRetrieval 超越了單一來源基線（Single-Source Baselines），證明該框架可作為異質知識來源（Heterogeneous Knowledge Sources）的通用介面，同時保留使每個來源具價值的結構差異。

### 核心貢獻（3～5點）
- 提出 OmniRetrieval 框架，以統一檢索（Unified Retrieval）機制整合異質知識來源（Heterogeneous Knowledge Sources），無須犧牲各來源的結構特性與表達能力。
- 支援自然語言查詢（Natural-Language Query），具備來源識別與來源原生查詢（Source-Native Queries）自動生成與分派能力，可對接各知識來源的原生執行引擎（Native Execution Engines）。
- 在涵蓋 13 個資料集（Datasets）、309 個知識庫（Knowledge Bases）的跨來源基準測試（Benchmark）中，顯著超越單一來源基線（Single-Source Baselines），驗證其通用性與實效性。
- 確立「統一但不同質化」的設計原則，透過保留結構可供性（Structural Affordances）——如綱要（Schemas）、本體（Ontologies）與組合運算子（Compositional Operators）——維持各來源的獨特價值。

### 適合對象
從事資訊檢索、知識庫系統、自然語言處理與大規模語言模型應用之研究者與工程師，特別是關注如何整合非結構化文本、關聯式資料表與圖結構知識來源，以建構統一且保留來源特性的跨域查詢介面者。

## 深度分析

#### 方法論解析

OmniRetrieval 的方法論核心在於拒絕 homogenization（同質化），主張以 unified access layer（統一存取層）銜接各知識來源（knowledge sources），使每個來源得以保留其原生結構與查詢能力。論文將檢索任務形式化為：給定自然語言問題 𝑞 與知識來源池 ℬ={𝑏₁,…,𝑏𝑁}，每個來源 𝑏 具備 native query language（原生查詢語言，如 SQL、SPARQL、Cypher 或自由格式文本）、execution engine（執行引擎）Exec(𝑏,𝑞̂) 以及 structural context（結構化上下文）𝑐𝑏（如關聯式綱要、本體論或語料庫描述子）。檢索框架需完成三項操作：(1) source selection（知識來源選擇），決定觸及之子集 𝒮⊆ℬ；(2) native query formulation（原生查詢生成），針對每個 𝑏∈𝒮 產生可執行的 𝑞̂𝑏；(3) cross-source condensation（跨來源彙整），將各執行引擎回傳的異質結果（ passage、tuple、triple、path 等）收斂為統一證據集合 𝓔。

在 source selection 階段，作者明確批判了將所有 𝑐𝑏 與查詢投影至 shared dense embedding space（共用稠密嵌入空間）的做法。這類 homogenization 會導致 modality gap（模態差距）——嵌入依來源類型而非語義內容聚集——並喪失各來源獨有的 compositional operators（組合運算子，如 joins、traversals、property paths）。為此，OmniRetrieval 採用 long-context LLM（長上下文大型語言模型）直接讀取 heterogeneous structural contexts（異質結構化上下文），透過語言模型的 in-context reasoning（上下文內推理）判斷哪些知識庫（knowledge bases）足以回答問題，從而迴避 lossy projection（有損投影）的問題。

在查詢生成階段，框架以 𝑐𝑏 為條件，針對各來源生成 structurally valid（結構合法）的原生查詢。由於每個來源皆由自身 execution engine 執行，SQL 的 join、SPARQL 的 ontology traversal、Cypher 的 labeled path traversal 等 structural affordances（結構性功能特徵）均完整保留。最後，跨來源彙整機制過濾並合併多個後端回傳的證據，使下游 LLM 獲得統一且相關的 evidence set（證據集合）。值得注意的是，由於無需訓練共享編碼器，新增來源僅需 registration（註冊）即可，具備高度可擴展性。

#### 實驗數據解讀

根據摘要與引言所述，OmniRetrieval 的評估涵蓋 13 個公開資料集、309 個 distinct knowledge bases（獨立知識庫），橫跨四種後端類型：unstructured corpora（非結構化語料庫）、relational databases（關聯式資料庫）、RDF knowledge graphs（RDF 知識圖譜）與 labeled property graphs（標記屬性圖）。實驗設計以 single-source baselines（單一來源基線模型）為對照，這些基線被限制僅能在單一模態內運作。

實驗結果顯示，OmniRetrieval 不僅在跨來源設定下表現穩定，更 consistently exceeds（持續超越）單一來源基線。這項發現具有兩層意涵：首先，統一介面並未因通用性而稀釋各模態的檢索精度，反而透過正確的 source selection 與 native query 保留了各後端的最佳表現；其次，框架在 identifying correct knowledge bases（識別正確知識庫）與生成 structurally valid queries（結構合法查詢）上均達到高準確率，驗證了「以原生語言對話」策略的實用性。雖然提供的節錄未包含詳細的數據表格，但從宣稱的 benchmark scale（基準規模）來看，309 個知識庫的覆蓋度已足以證明方法在極度 heterogeneous（異質）環境下的穩健性。

#### 與現有研究的比較

現有檢索系統多為單一來源專家：document retrievers（文件檢索器，如 BM25、DPR）僅處理非結構化文本；text-to-SQL（文字轉 SQL）系統綁定單一關聯式資料庫；SPARQL 或 Cypher 生成器則各自服務於單一圖後端。這些方法雖在各自模態表現優異，卻無法處理跨來源的資訊需求。

另一條研究路線試圖透過 unified embedding space（統一嵌入空間）或 linearized text format（線性化文本格式）將所有來源壓平至共享表示（如 Oguz et al., Ma et al., Baek et al. 之工作）。然而，論文指出這類方法會 flatten structural affordances（壓平結構性功能特徵），造成 unified embeddings 依來源類型分群的 modality gap，並喪失各原生查詢語言的運算能力。此外，近期 LLM（如 Anthropic、Gemini、OpenAI 之模型）雖具備跨證據推理能力，但其底層檢索層仍呈碎片化，無法同時觸及異質知識來源。

OmniRetrieval 的定位介於上述兩者之間：它不提供單一後端或共享表示，而是建立協調層（coordination layer），在保留各來源結構差異的前提下實現 unified retrieval（統一檢索）。這種「federated native access（聯邦式原生存取）」策略，相較於 homogenization 方法更能維持 expressive power（表達能力），相較於單一來源方法則具備更廣的覆蓋率。

#### 可重現性評估

就提供的文本範圍而言，作者並未明確提及原始碼、模型權重或實驗腳本是否公開釋出，因此 open-source availability（開源可用性）尚無法確認。然而，實驗所採用的 13 個資料集多為公開資源（如 Spider、BEIR、FB15K、LC-QuAD 等），這降低了資料層面的重現門檻。

從方法設計來看，可重現性的主要挑戰在於：(1) long-context LLM 的具體版本與 API 設定（節錄未揭露模型名稱與上下文長度上限）；(2) structural context 𝑐𝑏 的抽取與格式化協定（例如如何將關聯式綱要或本體論呈現給語言模型）；(3) cross-source condensation 的合併與排序邏輯（如何比較 passage、tuple 與 graph path 的相關性）。由於新增來源僅需 registration，理論上實驗架構具備模組化優勢，但若缺乏 prompt template（提示模板）與執行參數的詳細記錄，第三方研究者難以完全復現其 source selection 與 query generation 行為。

#### 未來研究方向

首先，目前的框架對各來源獨立生成查詢後再彙整結果，未來可朝 cross-source query planning（跨來源查詢規劃）發展，讓單一問題能觸發涉及多後端的 join 或 semijoin 操作，而非僅是各自檢索後合併。其次，structural context 𝑐𝑏 目前仍需外部提供，未來可結合自動化 schema summarization（綱要摘要）與 ontology learning（本體學習），降低新來源註冊時的人工介入。

第三，source selection 仰賴 long-context LLM，在 309 個知識庫規模下推論成本可觀，後續研究可探索 retrieval-augmented selection（檢索增強選擇）或 caching mechanism（快取機制），在不犧牲準確率的前提下提升效率。第四，現有評估聚焦於檢索正確性，未來應納入 latency（延遲）、throughput（吞吐量）與 monetary cost（金錢成本）等系統層面指標，特別是在動態增減 knowledge sources 的場景中。

最後，cross-source condensation 目前僅簡要提及，尚未深入探討如何為異質證據（如文本段落、關聯式 tuple、知識圖譜 triple）建立統一的 relevance scoring（相關性評分）機制。發展針對 heterogeneous evidence types（異質證據類型）的 fine-grained ranking model，將是銜接檢索層與下游 LLM 推理的關鍵下一步。

## 論文問答

**Q1：OmniRetrieval 旨在解決的核心問題是什麼？**
A：OmniRetrieval 旨在解決真實世界資訊需求必須同時存取結構多樣的異質知識來源，但現有檢索器僅能在單一來源上以固定查詢語言運作的核心問題。這些知識來源涵蓋非結構化文本、關聯式資料表、知識圖譜與屬性圖等，彼此之間的介面並不相容，導致整體知識景觀呈現高度碎片化。由於使用者難以預先知道應該查詢哪個語料庫、使用何種查詢語言以及哪個執行引擎，使得跨來源的檢索成為一項重大挑戰，而 OmniRetrieval 正是為了彌補這道鴻溝而設計。

**Q2：現有的檢索方法為何無法有效處理異質知識來源？**
A：現有的檢索方法通常一次只針對單一來源設計，例如文件檢索器僅處理非結構化語料、Text-to-SQL 系統綁定單一關聯式資料庫，而 SPARQL 或 Cypher 產生器則各自侷限於特定的圖資料庫後端。另一種常見的嘗試是將所有來源投影到共享的向量空間或線性化文本格式中，但這種同質化做法會抹平每個來源獨特的結構優勢，例如綱要、本體論與組合運算子，導致嵌入表示僅能進行相似度比對而無法利用原生查詢操作。此外，統一嵌入往往會依來源類型而非語義內容聚集，產生模態差距，使檢索結果偏向與查詢形式相似的來源，而非真正能回答問題的來源。

**Q3：為何跨異質知識來源的統一檢索如此重要？**
A：在真實應用中，能夠回答問題的知識極少只存在於單一位置或單一結構中，例如臨床問題可能需要生物醫學文章、企業問題需要正規化資料表的連結查詢、事實性問題需要知識圖譜中的三元組，而供應鏈問題則需要屬性圖的多跳遍歷。即便大型語言模型已具備跨多種證據進行推理的能力，若檢索層無法觸及所有相關來源，整體知識景觀仍將無法被有效利用。因此，建立一個能夠統一檢索異質知識來源並保留其結構特性的框架，對於釋放分散知識的價值至關重要。

**Q4：OmniRetrieval 的核心方法論是什麼？**
A：OmniRetrieval 的核心方法論是建立一個統一的存取層，而非將所有知識來源同質化。具體而言，當收到自然語言查詢時，系統首先識別哪些已註冊的知識來源與問題相關，接著針對每個選定的來源，根據其暴露的結構化上下文生成該來源原生查詢語言的可執行查詢。這些查詢隨後被分派至各來源的原生執行引擎，最後將多個來源的輸出整合為單一且與問題相關的證據集，從而讓每個來源都能以其自身的術語被存取。

**Q5：相較於先前的統一化嘗試，OmniRetrieval 的關鍵創新為何？**
A：OmniRetrieval 的關鍵創新在於採取「非同質化」的策略，即保留每個知識來源的原生查詢語言與結構操作能力，而非將其壓平到共享的嵌入空間中。透過為每個來源制定原生查詢（如 SQL、SPARQL、Cypher 或自由格式文本查詢），框架能夠充分利用各來源獨特的組合運算子，例如關聯式資料表的 Join、知識圖譜的屬性路徑或屬性圖的多跳遍歷。這種設計不僅避免了統一嵌入所帶來的模態差距與資訊損失，更讓新增知識來源僅需註冊即可完成，無需重新訓練共享編碼器或重繪嵌入空間。

**Q6：OmniRetrieval 如何處理來源選擇，為何採用此設計？**
A：針對來源選擇，OmniRetrieval 並未採用將異質結構上下文與查詢嵌入共享向量空間的傳統相似度排序方法，因為這類方法會對不同形式的描述符造成損失性投影，且相似度分數無法捕捉諸如資料表名稱或關係類型等實際內容細節。相反地，該框架借鑒近期長上下文大型語言模型的能力，直接處理各來源的結構化上下文，以判斷其是否具備回答問題的潛力。這種設計能夠在面對大量且持續擴充的已註冊來源時，更精準地識別相關知識庫，避免因表示形式差異而導致的錯誤選擇。

**Q7：評估 OmniRetrieval 所使用的基準測試為何？**
A：為了全面評估 OmniRetrieval 的效能，作者建構了一個涵蓋 13 個公開資料集與 309 個相異知識庫的大規模評測基準。這些知識庫橫跨四種後端類型，包括非結構化語料、關聯式資料庫、RDF 知識圖譜以及標記屬性圖，能夠充分反映真實世界中知識來源的結構多樣性。此基準的廣泛覆蓋範圍確保了評估結果不僅限於單一模態，而是能夠檢驗框架在異質環境下的整體泛化能力。

**Q8：實驗中的關鍵結果有哪些？**
A：實驗結果顯示，OmniRetrieval 在整個評測基準上持續超越僅能於單一模態內運作的單一來源基線方法。此外，該框架在識別每個查詢所對應的正確知識庫方面展現出高準確度，並能為每種原生語言產生結構上有效的查詢語句。這些結果共同證明，透過協調各來源的原生介面進行統一檢索，不僅可行，而且能在保留各來源結構特色的同時，達到優於單一來源方法的檢索成效。

**Q9：實驗結果如何顯示保留原生查詢語言的重要性？**
A：實驗結果表明，保留原生查詢語言與各來源的結構操作能力，是實現高效跨來源檢索的關鍵因素。相較於將所有來源投影至共享空間而僅能進行相似度比對的做法，OmniRetrieval 透過 SQL、SPARQL、Cypher 等原生查詢，能夠精確利用綱要約束、圖遍歷與資料表連結等進階操作，從而取得更準確的檢索結果。這證明了同質化雖能簡化介面，卻會嚴重削弱各來源固有的表達能力，而 OmniRetrieval 的「以各來源自身術語進行檢索」策略成功克服了此一瓶頸。

**Q10：OmniRetrieval 可應用於哪些實務場景？**
A：OmniRetrieval 可應用於多種需要同時檢索異質資訊的真實場景，例如臨床醫療中需要同時查詢生物醫學文獻與藥物知識圖譜以回答複雜病症問題，或是在企業環境中整合關聯式資料庫中的交易紀錄與屬性圖中的組織關係網絡。此外，對於需要事實查核的應用，系統可同時檢索百科知識圖譜中的三元組與非結構化新聞語料，以提供更完整的證據支持。這種跨來源檢索能力使其能夠作為通用介面，連接過去因格式與查詢語言差異而彼此隔離的資料孤島。

**Q11：OmniRetrieval 的設計在實際系統部署上有何優勢？**
A：OmniRetrieval 的設計為系統部署帶來顯著的實務優勢，特別是其「註冊即可使用」的擴展性：新增知識來源時，無需重新訓練共享編碼器或重構嵌入空間，僅需將來源及其結構上下文註冊至框架中。這種模組化設計大幅降低了維護異質資料基礎設施的技術債，使企業能夠靈活地整合既有資料庫、圖譜與文件系統。同時，由於每個來源仍透過其原生引擎執行查詢，系統可充分利用各資料庫既有的查詢優化與權限控管機制，無需為了統一介面而犧牲底層效能與安全性。

**Q12：OmniRetrieval 可能對資訊檢索與知識管理領域帶來什麼影響？**
A：OmniRetrieval 為資訊檢索與知識管理領域提供了一種新的典範轉移，證明統一檢索不必以犧牲各來源結構特性為代價。這項工作挑戰了過去依賴共享向量空間或線性化文本作為萬用介面的主流思路，轉而強調透過原生查詢語言協調異質來源的價值。長遠而言，這種方法有望推動下一代檢索增強生成系統的發展，使其檢索層不再受限於單一模態，從而讓大型語言模型能夠基於更完整、更多樣的知識景觀進行推理。

**Q13：使用長上下文大型語言模型進行來源選擇可能存在哪些限制或成本？**
A：儘管 OmniRetrieval 利用長上下文大型語言模型進行來源選擇能夠有效處理異質結構描述符，但這種方法可能伴隨較高的運算成本與延遲，特別是當已註冊的知識來源數量極其龐大時。此外，即便長上下文模型能力持續提升，面對極為複雜或龐大的資料庫綱要與本體論時，仍可能存在上下文長度上限的壓力，進而影響選擇的精細度。這些因素意味著在實際部署時，需要在來源選擇的準確性與系統的擴展成本之間進行權衡。

**Q14：OmniRetrieval 在哪些情況下可能失敗或產生次佳結果？**
A：OmniRetrieval 可能在跨來源證據整合階段面臨挑戰，特別是當不同來源返回的結果格式差異極大且語義粒度不一致時，例如同時處理自由文本段落、關聯式資料表的多欄位元組以及圖譜中的多跳路徑，其相關性比對與去重可能變得異常困難。此外，若某個知識來源的結構上下文描述不完整或過時，框架在生成原生查詢時可能產生語法正確但語義偏離的查詢語句，導致檢索結果不精確。當查詢本身需要高度複雜的多來源聯合推理，而非僅是單一來源證據的彙整時，現有的來源選擇與查詢生成機制也可能力有未逮。

**Q15：這條研究路線未來有哪些有前景的發展方向？**
A：未來研究可朝幾個方向延伸，首先是開發更精細的跨來源證據整合機制，以處理不同模態結果在語義層次的深度對齊與融合，而非僅是表面上的相關性篩選。其次，可探索如何將 OmniRetrieval 擴展至更多新興知識來源類型，例如時序資料庫、向量資料庫或多媒體知識庫，進一步擴大統一檢索的覆蓋範圍。最後，結合主動式學習或回饋機制，讓框架能夠根據使用者回饋與查詢執行結果動態優化來源選擇策略與查詢生成模板，將有助於提升系統在持續演化的知識生態中的長期適應性。

## 實務應用指南

### 適用場景

1. **企業內部統一知識問答**  
   同時查詢技術文件（非結構化文本）、人事與專案關聯式資料表（SQL）、以及組織協作網絡（標記屬性圖）。例如：「參與 Alpha 專案且與 Tech 部門有跨組合作的人員有哪些？」系統需自動選擇資料表與圖譜，分別生成 SQL 與 Cypher，再將人員名單與協作路徑彙整為統一證據。

2. **臨床醫療決策支援**  
   整合生物醫學文獻（自由文本）、臨床試驗資料庫（關聯式表格）、醫學知識圖譜（RDF 三元組）、以及病人轉診關係網（屬性圖）。例如詢問某罕見藥物交互作用時，需同時檢索文獻段落、藥物-適應症表格、本體論中的副作用三元組，並透過屬性圖確認該病人在醫療網絡中的用藥歷程。

3. **供應鏈風險監控**  
   面對供應商主檔（關聯式資料庫）、物流異常日誌（非結構化文本）、以及供應鏈上下游網絡（屬性圖）。當查詢「某零件斷鏈會影響哪些二階供應商」時，系統需從資料表確認庫存，從文本提取異常事件，再於屬性圖執行多跳遍歷（multi-hop traversal）找出影響範圍。

4. **學術研究智慧檢索**  
   串接論文全文語料庫、實驗數據表、領域本體知識圖譜（如 DBpedia/Wikidata 的 RDF），以及學者引用與合作網絡（屬性圖）。研究者可使用自然語言詢問跨資料類型的問題，例如「在 GNN 領域中，與某作者有合作且發表過特定數據集實驗的團隊有哪些」，系統自動分派至各原生引擎。

5. **金融合規與盡職調查**  
   查詢法規文本（非結構化）、交易明細（關聯式資料庫）、企業間股權與擔保關係（知識圖譜或屬性圖）。合規人員以自然語言提問時，框架需識別問題涉及法條解釋、帳務數據比對，或企業關係圖遍歷，並分別生成對應查詢。

### 實作前置條件

**資料面**  
- 每個知識來源必須暴露其**結構上下文**（structural context）：關聯式資料庫需提供 schema（表、欄位、外鍵）；RDF 知識圖譜需提供本體論（ontology）與常用謂詞；屬性圖需提供節點標籤、關係類型與屬性鍵；文本語料庫需提供語料描述（主題、格式、時間範圍）。  
- 各來源需具備可呼叫的**原生執行引擎**（如 SQL 資料庫連線、SPARQL endpoint、Neo4j Bolt、文本檢索 API）。  
- 準備各查詢語言的**少量示範樣本**（few-shot examples），供 LLM 學習該來源的 schema linking 與查詢慣例。

**運算面**  
- 需能呼叫**長上下文 LLM**（論文採用長上下文模型進行來源選擇），以容納大量異質結構描述與使用者問題。  
- 各來源執行引擎需獨立運作，並預留足夠網路頻寬與查詢延遲預算；跨來源查詢為非同步派發，需有協調層（orchestrator）管理並行與超時。  
- 建議配置查詢快取與結果暫存，避免重複生成與執行昂貴的圖遍歷。

**技能面**  
- 團隊需熟悉至少一種結構化查詢語言（SQL、SPARQL、Cypher），並具備 schema 設計與資料建模能力。  
- 需具備 LLM Prompt Engineering 與 API 整合經驗，能設計條件式生成流程（根據選定的來源切換 prompt 模板）。  
- 需具備資料工程與維運能力，處理來源註冊、權限控管、schema 變更同步，以及錯誤查詢的容錯機制。

### 實作步驟建議

**步驟一：盤點與註冊知識來源**  
將現有資料資產分類為非結構化文本、關聯式資料庫、RDF 知識圖譜、標記屬性圖四大類。抽取並標準化各自的結構上下文，建立來源目錄（source registry）。每筆註冊紀錄需包含：來源類型、連線資訊、結構描述文件、以及少許代表性查詢樣本。

**步驟二：建立原生查詢生成管線**  
為每類來源設計專屬 prompt 模板，讓 LLM 根據「使用者問題 + 該來源的結構上下文」生成原生查詢。實作 schema linking 模組（將問題中的實體與屬性對應到 schema 中的表、欄位或節點類型），並加入語法驗證器（如 SQL parser、Cypher 靜態檢查）攔截無效查詢。

**步驟三：實作長上下文來源選擇器**  
將所有已註冊來源的結構上下文與使用者問題一同餵入長上下文 LLM，由模型判斷哪些來源可能包含答案。避免使用單一嵌入空間做相似度排序——論文已證實這會導致模態差距（modality gap），使檢索偏向與問題形式相似的來源，而非真正能回答問題的來源。

**步驟四：部署跨來源彙整層（Cross-Source Condensation）**  
設計證據合併邏輯，將不同來源的回傳結果（文本段落、資料元組、RDF 三元組、圖路徑）統一為**統一證據集合**（Unified Evidence Set）。實作相關性過濾機制，剔除與問題無關的欄位或節點，並保留各來源的原始結構語意，供下游生成模型使用。

**步驟五：漸進式驗證與上線**  
先以單一來源進行端到端驗證，確認查詢生成準確率與執行安全性；再擴展至多來源協同。建立查詢日誌與回饋迴路，持續監控來源選擇準確率、查詢語法正確率，以及跨來源結果的用戶滿意度。

### 潛在風險與注意事項

1. **同質化陷阱（Homogenization Pitfall）**  
   切勿為了工程簡便而將所有來源壓入單一向量空間或線性化為統一文本。這會抹除各來源的結構優勢（如 join、遍歷、屬性路徑），並造成模態差距。應堅持「原生查詢、原生執行」的原則。

2. **查詢生成失敗與安全性**  
   LLM 生成的 SQL 或 Cypher 可能包含語法錯誤，甚至在極端情況下被誘導執行惡意操作。必須實作沙箱執行環境、嚴格的唯讀權限、以及查詢白名單/黑名單機制。

3. **來源選擇的累積誤差**  
   若第一步選錯知識來源，後續查詢再精準也無法回答問題。建議設計 fallback 策略：當首選來源無結果或置信度過低時，自動擴大至次高相關來源重新檢索。

4. **結構上下文的長度與注意力瓶頸**  
   當註冊來源數量龐大時，長上下文 LLM 可能面臨上下文長度限制，或出現「遺失在中間」（lost in the middle）現象。可採用兩階段篩選：先以輕量摘要或分群縮小候選來源範圍，再將精選來源的完整 schema 餵入模型。

5. **Schema 漂移與維護負擔**  
   底層資料庫的 schema、本體論或語料範圍變更時，若結構上下文未同步更新，原生查詢將會失效。需建立自動化 schema 抽取與版本同步管線，並在來源註冊表中標註最後更新時間。

### 與其他技術的整合建議

- **作為 RAG 架構的檢索層**：OmniRetrieval 可無縫嵌入現有 RAG 流程，取代傳統單一向量檢索器。其輸出的統一證據集合可直接餵給下游 LLM 進行生成，無需改動現有生成模型或提示詞範本。  
- **銜接現有資料基礎建設**：關聯式資料庫透過 JDBC/ODBC 連接；RDF 透過 SPARQL endpoint；屬性圖透過 Neo4j Bolt 或 Gremlin Server；文本語料庫可銜接現有 Elasticsearch、OpenSearch 或 Milvus 叢集。  
- **封裝為 Agent 工具**：在 LangChain、LlamaIndex 或自研 Agent 框架中，將 OmniRetrieval 封裝為單一 Tool Action。當規劃型 Agent 判斷需要異質知識時，統一呼叫此工具，由框架內部處理來源選擇與分派。  
- **串接監控與評估系統**：整合 LangSmith、Weights & Biases 或自製儀表板，追蹤跨來源查詢延遲、來源選擇準確率、各原生查詢的語法通過率，以及最終答案的用戶回饋，形成持續優化閉環。

### 給不同背景讀者的閱讀建議

**給初學者**：請先聚焦圖 1 的架構概念，理解「為什麼不把所有資料倒進向量資料庫」這個核心命題。建議從單一來源（例如 text-to-SQL）的實作開始，體驗「自然語言轉結構化查詢」的完整流程，再逐步想像如何擴展到多種異質知識來源。

**給 AI 工程師**：請仔細研讀第 2 節的問題形式化與來源選擇機制，特別注意長上下文 LLM 在來源選擇中的角色，以及論文為何拒絕共享嵌入空間。實作時請優先處理 schema linking 的準確性與跨來源結果的型別轉換，這兩處是系統穩定性的關鍵。

**給研究人員**：請關注論文提出的「不以同質化換取統一，而以統一存取層尊重各來源原生結構」之設計哲學，以及橫跨 13 個資料集、309 個知識庫的評估規模。可延伸探討主動式 schema 對齊、跨來源語意 join、查詢成本最佳化，以及更複雜的組合式推理（compositional reasoning）課題。

**給產品經理**：請理解此框架解決的是「企業知識孤島」與「結構多樣性」問題，而非單純提升單一資料庫的檢索準確率。評估導入時，請先盤點現有資料資產的結構多樣性與業務價值，規劃分階段上線（優先整合高價值且異質的 2–3 個來源），同時預留 LLM 呼叫成本、資料權限治理與維運人力預算。
