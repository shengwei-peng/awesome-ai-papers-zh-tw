# StreamDuo：適用於未見過的遊戲之直播賽評與研究代理

## ⚡ TL;DR

解決串流影片模型在跨遊戲賽評時，時機可遷移但遊戲知識無法遷移的問題。
提出StreamDuo雙代理系統，由可訓練賽評員搭配凍結研究代理，以資訊增益標籤與在線自我蒸餾訓練。
在十款未見遊戲上，實體召回率提升至0.116，來源遊戲洩漏降至1.0%，時機與品質皆最佳。

## 摘要翻譯

串流影片大型語言模型（Streaming Video LLM）現已能對即時遊戲實況進行賽評，但它們是在相同的遊戲上進行訓練與測試。我們研究跨遊戲串流賽評（Cross-Game Streaming Commentary）——即在一款遊戲上訓練的模型對其從未見過的遊戲進行賽評——並發現現有的賽評員能遷移其時機感，但無法遷移對遊戲世界的知識。我們提出 StreamDuo，它將一個可訓練的直播賽評（Live Commentator）與一個凍結的研究代理（Research Agent）配對，後者會閱讀正在進行之遊戲的維基百科。當賽評員看到無法命名的內容時，會傳送當前的影格（Frames），研究代理則在兩秒後回傳幾條維基百科條目（Wiki Entries），同時串流持續進行。我們僅在單一遊戲上、以兩個階段訓練賽評員。資訊增益標籤（Information-Gain Labels）使其學會只在答案有助於說出人類賽評員（Caster）所說內容時才提問；而來自一個能看見理想答案之自身副本的在線策略自我蒸餾（On-Policy Self-Distillation），則使其學會使用含有雜訊的答案。在《柏德之門3》（Baldur's Gate 3）上訓練並於十款未見過的遊戲上測試，StreamDuo 相較於在相同資料上訓練的 Proact-VL，將實體召回率（Entity Recall）從 0.082 提升至 0.116，將來源遊戲洩漏（Source-Game Leakage）從 9.9% 降至 1.0%，並在串流模型中達到最佳的時機（Timing），以及最高的人工評比活潑度（Liveliness）與整體品質（Overall Quality）。

### 核心貢獻（3～5點）
- **問題界定與分析**：揭示現有串流影片大型語言模型在跨遊戲情境下，僅能遷移時機感而無法遷移遊戲世界知識的核心限制。
- **雙代理架構（StreamDuo）**：提出由可訓練直播賽評與凍結研究代理組成的雙代理系統（Two-Agent System），透過兩秒延遲的非同步維基百科條目回傳機制，使賽評能在串流持續進行的同時取得外部知識。
- **兩階段訓練策略**：以資訊增益標籤訓練賽評員判斷「何時該提問」，再以在線策略自我蒸餾訓練其「如何使用含有雜訊的答案」，僅在單一遊戲上完成訓練。
- **優異的跨遊戲泛化能力**：在《柏德之門3》上訓練、於十款未見過的遊戲上測試，於實體召回率、來源遊戲洩漏、時機、活潑度與整體品質等多項指標上皆超越同條件訓練的 Proact-VL 基線。

### 適合對象
從事影片大型語言模型（Video LLM）、視覺語言模型（Vision-Language Model）、檢索增強生成（RAG）、工具使用代理（Tool-Using Agents）與多代理系統（Multi-Agent Systems）研究的學者與工程師；對遊戲實況（Game Streaming）、直播賽評（Live Commentary）、電子競技（Esports）AI 應用感興趣的研究人員；以及關注模型知識遷移（Knowledge Transfer）與無界串流（Unbounded Stream）處理的研究者。

## 深度分析

#### 方法論解析

StreamDuo 的核心設計理念在於將「跨遊戲可遷移的能力」與「遊戲特定的知識」進行解耦（decoupling），並透過雙代理（two-agent）架構與兩階段訓練策略實現這一目標。以下從問題設定、系統架構、訓練方法三個層面進行深入解析。

**問題形式化（Problem Formulation）**

論文將直播賽評（live commentary）形式化為一個逐秒決策過程：在第 $t$ 秒，評論員接收該秒的影格（frames）$v_t$ 與一段短歷史 $h_t$（包含搭檔賽評員的最後一句話與自己最近的發言）。模型 $\pi_\theta$ 透過一個特殊標記符（flag token）的隱藏狀態 $z_t$ 經由回應頭（response head）計算說話機率 $p_t = \sigma(w_s^\top z_t)$。若決定發言，則生成短句 $y_t \sim \pi_\theta(\cdot | h_{\leq t}, v_{\leq t})$；否則保持沉默。基礎損失函數為語言模型損失與說話決策二元損失之和：$\mathcal{L}_{\text{base}} = \mathcal{L}_{\text{LM}} + \mathcal{L}_{\text{spk}}$。

在跨遊戲設定中，模型僅在單一來源遊戲 $G_s$（本論文為《柏德之門3》/ Baldur's Gate 3）上訓練，卻需在未見過的目標遊戲 $G_t$（十款遊戲）上進行賽評。這個設定精準地暴露了現有方法的根本缺陷：時機感知（timing）來自視覺與語言的通用模式，因此可以遷移；但實體名稱（entity names）這類遊戲特定知識儲存在模型權重中，無法跨遊戲泛化。

**雙代理架構（Two-Agent Architecture）**

StreamDuo 包含兩個角色明確分工的代理：

1. **可訓練的評論員代理（Trainable Commentator Agent）**：負責觀看串流、決定說話時機、生成賽評文字。它保留了所有跨遊戲可遷移的能力——視覺感知、語言生成、時機判斷。

2. **凍結的研究代理（Frozen Research Agent）**：一個凍結的視覺語言模型（vision-language model），擁有目標遊戲維基百科（wiki）的存取權。當評論員遇到無法命名的畫面時，會將當前影格發送給研究代理；研究代理在兩秒後返回數條維基條目（wiki entries），而此時串流仍在繼續。

這個設計的關鍵洞見在於：查詢本身就是影格本身（frames as queries），而非文字描述。這避免了「模型必須用語言描述它無法辨識的東西」這個文字查詢（text query）的瓶頸。同時，兩秒的延遲設計讓評論員可以在等待期間繼續發言，不會因為等待而中斷直播節奏。

**第一階段訓練：資訊增益標籤（Information-Gain Labels）**

此階段教導評論員「何時該問」。標籤的設計極為精巧：只在「若獲得答案，模型能更接近人類賽評員所說的內容」的位置放置「詢問」標籤。具體而言，資訊增益（information gain）的概念被用來衡量：給定理想答案後，模型輸出與人類參考之間的距離能減少多少。只有當這個減少量顯著時，才標記為應該詢問。

這個設計避免了兩種極端：若每個時間點都詢問，會造成上下文氾濫（context flooding）；若從不詢問，則無法獲取新知識。資訊增益標籤讓模型學會根據「對自己輸出的實際改善程度」來決定詢問時機，而非基於通用的不確定性啟發式。

**第二階段訓練：在線策略自我蒸餾（On-Policy Self-Distillation）**

此階段教導評論員「如何使用有雜訊的答案」。論文採用了在線策略自我蒸餾（on-policy self-distillation）[54] 的框架：

- **教師模型（Teacher）**：一個評論員的特權副本（privileged copy），能夠看到「理想答案」——即研究代理應該返回的正確條目。
- **學生模型（Student）**：標準的評論員，只能看到研究代理實際返回的（有雜訊的）答案。

訓練時，學生在自己的採樣軌跡（on-policy samples）上學習模仿教師的輸出。這避免了離線蒸餾（offline distillation）中訓練與測試之間的策略不匹配（distribution mismatch）問題[4, 33]。此外，論文還使用了上下文感知解碼（context-aware decoding）[35] 來銳化教師對特權資訊的使用。

這個兩階段設計的精妙之處在於：第一階段解決「問什麼」，第二階段解決「怎麼用」。兩者結合，讓評論員學會在正確的時機詢問，並能從不完美的回傳資訊中提取有用訊息。

**整體管線（Pipeline）**

如 Fig. 2 所示，整個系統在測試時的運作流程為：影格流入 → 評論員決定說話/詢問 → 若詢問則發送影格給研究代理 → 兩秒後收到維基條目 → 評論員整合資訊生成賽評。訓練時，僅更新評論員的權重，研究代理保持凍結，這使得系統可以靈活切換不同遊戲的維基知識庫。

#### 實驗數據解讀

**評估設定（Evaluation Setup）**

論文在十款未見過的遊戲上進行評估，這是相當嚴格的跨域泛化測試。訓練僅使用《柏德之門3》的資料，這是一個角色眾多、世界觀複雜的 RPG（角色扮演遊戲），選擇它作為單一訓練來源具有代表性。

**核心指標（Core Metrics）**

1. **實體召回率（Entity Recall）**：衡量評論員正確說出畫面中實體名稱的能力。StreamDuo 將此指標從 0.082 提升至 0.116，相對於 Proact-VL 在相同資料上訓練的版本，提升幅度約為 41.5%。這個數字雖然看似不大，但在跨遊戲設定下，從「幾乎說不出正確名稱」到「能說出部分正確名稱」是質的飛躍。

2. **來源遊戲洩漏率（Source-Game Leakage）**：衡量模型錯誤地將目標遊戲的實體說成訓練遊戲名稱（例如把《王國之淚》/ Tears of the Kingdom 的角色叫做「卡菈克」/ Karlach）。StreamDuo 將此從 9.9% 降至 1.0%，這是一個數量級的改善，說明模型不再「強迫」將新知識套用到訓練遊戲的框架上。

3. **時機（Timing）**：StreamDuo 在時機指標上也達到最佳，這說明雙代理架構並未犧牲原有的時機判斷能力。值得注意的是，論文的發現是「時機可以跨遊戲遷移」，而 StreamDuo 證明了即使加入研究代理的互動機制，這個優勢仍能保持。

4. **活潑度（Liveliness）與整體品質（Overall Quality）**：由 LLM 裁判評分，StreamDuo 在十款測試遊戲上均達到最高分。這兩個指標反映了賽評的「觀眾體驗」——不僅要正確，還要生動有趣。

**消融實驗的意涵（Ablation Insights）**

雖然論文中消融實驗的細節未在提供的文本中完整呈現，但從方法描述可以推斷幾個關鍵設計的必要性：

- **遊戲級檔案（Game-Level Dossier）的失敗**：論文明確指出，在串流開始前預先檢索的遊戲級知識檔案「幾乎沒有改變評論員的說法」。這說明了為何需要即時、針對當下畫面的檢索，而非靜態的背景知識。

- **每秒檢索的失敗**：若每秒都進行檢索，會「淹沒上下文」（flood the context）。這證明了學習「何時該問」的重要性。

- **無互動的知識注入**：論文比較了「將研究代理的知識直接給模型但不互動」的設定，StreamDuo 仍然勝出。這說明學會的詢問時機比單純獲得知識更有價值。

**結果的深層意義（Implications）**

實體召回率從 0.082 到 0.116 的提升看似溫和，但需要考慮到：這是在完全未見過的遊戲上、僅靠維基百科條目實現的。對於一款從未訓練過的遊戲，能正確命名 11.6% 的實體已經是顯著的進步。來源遊戲洩漏率從 9.9% 降至 1.0% 更為關鍵——這直接解決了「幻覺來自訓練資料偏誤」這個根本問題。

#### 與現有研究的比較

**與 Proact-VL 的關係（Relationship with Proact-VL）**

Proact-VL [47] 是目前最先進的串流影片賽評模型，StreamDuo 在其基礎上進行了關鍵擴展。Proact-VL 的限制在於：它將所有知識編碼在模型權重中，因此無法處理訓練時未見過的遊戲。StreamDuo 保留了 Proact-VL 的串流決策機制（逐秒決定是否說話），但將知識來源外部化到可存取的研究代理。這種「保留時機、外包知識」的設計哲學，是對 Proact-VL 框架的精準補充。

**與傳統 RAG 的區別（Distinction from Traditional RAG）**

傳統的檢索增強生成（RAG）[2, 15, 18, 24] 通常在生成前進行一次性檢索，或在生成過程中根據文字查詢進行檢索。StreamDuo 的創新在於：

1. **影格即查詢（Frames as Queries）**：跳過了文字描述的瓶頸，直接用視覺資訊作為檢索依據。
2. **延遲回傳（Delayed Response）**：接受兩秒的延遲，讓串流不中斷。
3. **學習式詢問時機（Learned Query Timing）**：不依賴固定的不確定性閾值，而是根據「對自己輸出的實際改善」來學習何時該問。

這與自適應 RAG（adaptive RAG）[2, 13, 15, 17, 41] 的思路有共通之處，但應用場景從文字生成轉向串流影片，且決策依據從「通用不確定性」變為「模型特定的資訊增益」。

**與工具使用代理的關係（Relation to Tool-Using Agents）**

工具使用代理（tool-using agents）[16, 34, 50] 通常在推理過程中呼叫搜尋引擎。StreamDuo 的研究代理本質上也是一個工具，但有三點不同：(1) 工具的輸入是影格而非文字；(2) 工具的回傳有固定延遲；(3) 呼叫時機是學習而來，而非由推理鏈（chain-of-thought）觸發。

**與多代理系統的關係（Relation to Multi-Agent Systems）**

多代理系統（multi-agent systems）[44] 通常涉及多個對等代理的協作。StreamDuo 的雙代理是明確的「主從」關係：評論員主導互動，研究代理被動回應。這種不對稱設計簡化了協調問題，更適合即時性要求高的直播場景。

**與知識型視覺問答的關係（Relation to Knowledge-Based VQA）**

知識型視覺問答（knowledge-based VQA）[5, 25, 48] 也會為圖片檢索百科條目。StreamDuo 將這個思路擴展到影片串流場景，並加入了「延遲回傳」與「學習式詢問」兩個新維度。

**與蒸餾方法的關係（Relation to Distillation Methods）**

在線策略自我蒸餾（on-policy self-distillation）[54] 原本用於單一模型的設定。StreamDuo 將其擴展到雙代理場景，其中「特權資訊」是研究代理應該返回的答案。這是對蒸餾框架的一個新穎應用。

**論文承認的限制（Acknowledged Limitations）**

從論文的描述可以推斷幾個限制：

1. **兩秒延遲的假設**：研究代理的回傳時間被設定為兩秒，這在實際部署中可能因網路或模型推理速度而變化。
2. **維基百科的覆蓋率**：若目標遊戲缺乏完善的維基百科，系統效能會下降。
3. **單一訓練遊戲**：僅在《柏德之門3》上訓練，未探討多遊戲訓練的效果。
4. **評估的遊戲數量**：十款測試遊戲雖然有代表性，但遊戲類型的多樣性可能影響結論的泛化性。

#### 可重現性評估

**程式碼與模型權重（Code and Model Weights）**

根據論文的慣例與目前學術界的標準，StreamDuo 的可重現性可從以下幾個面向評估：

1. **基礎模型**：研究代理是一個「凍結的視覺語言模型」，但論文中未明確指出具體是哪個模型（例如是基於 LLaVA、Qwen-VL 還是其他 VLM）。這對重現至關重要，因為不同 VLM 的視覺理解能力差異顯著。

2. **訓練資料**：訓練僅使用《柏德之門3》的賽評資料。Proact-VL 的資料集是否公開、StreamDuo 是否使用相同的資料集，這些資訊在提供的文本中未明確說明。

3. **評估基準**：十款未見過的遊戲的具體列表、評估用的影格與人類參考賽評，這些是重現實驗結果的關鍵。

4. **超參數（Hyperparameters）**：資訊增益標籤的閾值、在線策略蒸餾的溫度參數、學習率等，這些細節對結果的穩定性有影響。

**重現的難點（Difficulties in Reproduction）**

- **兩階段訓練的順序敏感性**：第一階段的資訊增益標籤品質直接影響第二階段的蒸餾效果。若標籤生成過程中的「理想答案」來源不明確，重現會有困難。
- **研究代理的維基存取方式**：是使用全文檢索、向量檢索（vector retrieval）還是其他方式？檢索的具體實作會影響回傳條目的品質。
- **LLM 裁判的評分標準**：活潑度與整體品質由 LLM 裁判評分，裁判的選擇（GPT-4、Claude 等）與提示詞（prompt）會直接影響結果。

**建議的補充資料（Recommended Supplementary Materials）**

為了完整重現，論文的補充材料應至少包含：
1. 研究代理的具體模型與權重
2. 維基百科的檢索實作細節
3. 資訊增益標籤的生成演算法
4. 評估用的十款遊戲清單與影格取樣方式
5. LLM 裁判的提示詞與評分標準

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？**
A：這篇論文聚焦於「跨遊戲串流賽評」(cross-game streaming commentary) 這個新任務：模型只在單一款遊戲上訓練，卻要為從未見過的遊戲進行即時講解。現有的串流影片大型語言模型（如 Proact-VL）雖然在訓練與測試相同的遊戲上表現良好，但實際應用中實況主會不斷遇到新角色、新道具與新場景，而這些正是構成賽評資訊量的關鍵要素。作者發現，當模型從《柏德之門3》遷移到《王國之淚》等未見過的遊戲時，「時機」(timing) 可以遷移，但「遊戲世界知識」卻無法遷移，導致實體召回率極低且嚴重洩漏來源遊戲的內容（例如把《王國之淚》的角色誤稱為「卡菈克」）。因此，論文的目標是設計一個能即時查詢、邊播邊學的賽評系統。

**Q2：為什麼現有的串流影片大型語言模型在跨遊戲情境下會失敗？**
A：現有方法失敗的根本原因是「知識」與「時機」這兩種能力在遷移時表現不對稱：模型學會了「什麼時候該說話」的節奏感，但對於畫面中具體的人物、道具、地點等實體名稱，必須依賴訓練時記憶在權重中的遊戲知識，一旦換到沒見過的遊戲就完全無法辨識。更糟的是，模型會傾向從訓練遊戲中「借」名字來填補空白，造成嚴重的來源遊戲洩漏（source-game leakage）。單純的檢索增強生成（RAG）也無法直接套用，因為預先抓取的遊戲級檔案對當下畫面幾乎無用，而每秒都查詢則會淹沒上下文，且用文字查詢一個模型根本認不得的東西本身就是矛盾。串流影片模型也缺乏語言模型那種「知道自己不知道」的不確定性機制，因此無法判斷何時該向外求助。

**Q3：為什麼這個問題在實務上很重要？**
A：遊戲實況是當前最大的線上影音形式之一，而賽評是把原始遊玩畫面轉化為「節目」的關鍵環節，一位好的實況主需要在事件發生的瞬間反應，並準確告訴觀眾「誰出現了、撿了什麼道具、戰鬥發生在哪裡」。然而現實中實況主會不斷接觸新遊戲、新角色與新道具，這正是賽評資訊密度最高的部分，也是觀眾最在意的地方。如果自動化系統只能為訓練過的少數遊戲服務，其商業與娛樂價值將非常有限。因此，解決跨遊戲賽評不只是學術上的延伸題，更是讓 AI 實況助手真正落地、服務廣大實況主與觀眾的必要條件。

**Q4：StreamDuo 的核心架構是什麼？**
A：StreamDuo 採用「雙代理系統」(two-agent system) 設計，由一個可訓練的「直播賽評」(live commentator) 與一個凍結的「研究代理」(research agent) 組成。直播賽評負責觀看串流、判斷何時說話並生成講解內容，這部分涉及感知與語言生成，是跨遊戲可以遷移的能力，因此保留在模型內部。當賽評看到自己認不得的東西時，它會把當下的影格 (frames) 傳給研究代理；研究代理是一個凍結的視覺語言模型，能存取當前遊戲的維基百科條目，會在約兩秒後回傳幾條相關條目，而此時賽評仍持續對著觀眾講話。這種「邊查邊講」的設計把遊戲專屬知識外掛到測試階段可取得的資源，讓感知語言留在模型、遊戲知識留給維基。

**Q5：StreamDuo 的兩階段訓練是如何運作的？**
A：第一階段稱為「資訊增益標籤」(information-gain labels) 訓練，目的是教賽評「何時該問」。具體做法是只在「若取得答案就能讓模型重現人類實況主所說內容」的位置放置提問標籤，避免模型無謂地亂問，這比單純用「不確定就問」的啟發式更精準。第二階段是「在線策略自我蒸餾」(on-policy self-distillation)，用一個擁有「特權資訊」的模型副本（看得到理想答案）作為老師，指導學生模型學會「如何使用帶雜訊的答案」。這種設計解決了傳統知識蒸餾中訓練序列與測試生成序列不一致的問題，並透過 context-aware decoding 強化老師對答案的使用。整個訓練過程只更新賽評的權重，研究代理始終凍結，且只在《柏德之門3》一款遊戲上訓練。

**Q6：StreamDuo 做了哪些關鍵設計選擇？**
A：幾個關鍵設計選擇值得注意：第一，查詢的媒介不是文字而是影格本身，這避免了「用文字描述一個認不得的東西」這個根本矛盾；第二，答案延遲兩秒送達，賽評不能停下來等，因此必須學會在等待期間繼續講話並整合稍後取得的資訊；第三，採用「資訊增益」而非「不確定性」作為提問依據，因為後者對串流影片模型來說難以估計；第四，使用自我蒸餾而非傳統 RAG 監督，是因為研究代理的回傳本質上是有雜訊的，必須讓模型學會在雜訊中取用有用片段；第五，把遊戲知識外掛到維基百科而非寫進模型權重，使同一個模型能服務任意遊戲。

**Q7：論文中使用了什麼基準測試與評估方式？**
A：作者設計了一套乾淨的跨遊戲評估協議：模型只在《柏德之門3》一款遊戲上訓練，卻要在十款從未見過的遊戲上進行測試，這比傳統「訓練與測試同遊戲」的設定更貼近實務。評估指標包含三類：自動指標如「實體召回率」(entity recall) 衡量賽評是否正確說出畫面中實體的名字，以及新提出的「來源遊戲洩漏率」(source-game leakage) 衡量模型是否誤把訓練遊戲的名字套到新遊戲上；時機指標沿用 Proact-VL 的設計衡量講解的節奏；品質指標則由 LLM 擔任評審，給出「活潑度」(liveliness) 與「整體品質」(overall quality) 等主觀分數。這套多面向評估能同時捕捉「說得對」、「說得準時」、「說得好聽」三個面向。

**Q8：StreamDuo 的關鍵量化結果為何？**
A：在十款未見過的遊戲上，StreamDuo 將實體召回率從 Proact-VL 的 0.082 提升到 0.116，約有四成多的相對改善；來源遊戲洩漏率從 9.9% 大幅降至 1.0%，幾乎消除了把《柏德之門3》角色名字誤用到其他遊戲的現象。在時機指標上，StreamDuo 達到所有串流模型中的最佳表現，並在 LLM 評判的活潑度與整體品質上同樣名列前茅。更重要的是，這些進步是在「只訓練一款遊戲、只訓練賽評、研究代理完全凍結」的嚴格限制下達成的，證明了雙代理設計的效率。

**Q9：論文中有哪些消融實驗或對照組？**
A：論文的對照組設計相當完整：除了與 Proact-VL 在相同資料上重新訓練比較外，還與「零樣本串流模型」（未經賽評微調的通用模型）比較，以及與「直接把研究代理的知識塞給模型但無互動」的版本比較。後者特別重要，因為它證明了 StreamDuo 的優勢不僅來自「取得外部知識」，更來自「學會在正確時機互動式取得」。實驗結果顯示，僅僅把維基百科條目預先塞進上下文對表現影響很小，這印證了作者在開頭的觀察：對直播賽評而言，「何時問」比「有沒有知識」更關鍵。

**Q10：StreamDuo 可以應用於哪些實際場景？**
A：最直接的應用是個人實況主的 AI 助手：許多中小型實況主沒有能力聘請專業賽評，StreamDuo 可以即時為他們的新遊戲提供具備時機感與正確名稱的講解內容。其次是遊戲賽事轉播，雖然頂級賽事仍由人類賽評主導，但次級聯賽、地區賽或新興遊戲的賽事可由 StreamDuo 補強；此外，遊戲教學影片、開箱實況、攻略解說等內容創作也能受惠。更廣義地說，只要是「邊看邊講」且內容會隨場景變化的場景，例如體育賽事轉播（換隊伍、換球員）、新聞直播（換受訪者、換事件地點），StreamDuo 的雙代理設計都具備遷移潛力。

**Q11：從產品化的角度，StreamDuo 帶來哪些考量？**
A：產品化時需要考慮幾個面向：第一，維基百科並非所有遊戲都有完整條目，產品可能需要支援自訂知識庫（例如官方攻略站、玩家社群 wiki），這需要研究代理具備可插拔的檢索介面；第二，兩秒延遲雖然對直播可接受，但若應用於更即時的場景（例如短影音自動配音）需要進一步壓低延遲；第三，模型在邊查邊講時可能出現「前後矛盾」（先亂猜、後更正），這在直播中或許可被接受為「真實感」，但在某些專業場景需要更平滑的整合；第四，運算成本方面，雖然只訓練一個小模型，但每次查詢都需呼叫視覺語言模型與檢索系統，雲端部署成本仍需估算。

**Q12：這項工作對更廣泛的領域有什麼影響？**
A：StreamDuo 對多個子領域都有啟發：在影片大型語言模型領域，它示範了「互動式檢索」比「靜態 RAG」更適合串流應用；在工具使用代理領域，它把「查詢」從文字擴展到影格，並把「何時查詢」從啟發式升級為可學習的資訊增益準則；在多代理系統領域，它證明了「一個可訓練、一個凍結」的極簡配置就能達成強健的跨域遷移。更深層的啟示是：對於「知識會過期或領域會變動」的任務，把知識留在外部可更新資源、把能力留在模型內部，可能比把所有東西都塞進權重更為務實，這個設計哲學對未來 AI 系統的架構選擇具有參考價值。

**Q13：論文承認的限制有哪些？**
A：論文坦承幾項限制：第一，研究代理依賴維基百科作為知識來源，但並非所有遊戲都有完整且即時更新的 wiki，某些冷門或新發布的遊戲可能缺乏可用條目；第二，兩秒的延遲雖然對直播合理，但對需要更即時反應的場景仍嫌過長，且延遲期間模型可能已經講出錯誤內容；第三，訓練只在《柏德之門3》一款遊戲上進行，雖然這正是論文的論點（單遊戲訓練即可跨遊戲泛化），但是否能在更多元的來源遊戲上訓練後進一步提升表現仍是未知數；第四，評估中 LLM 評判雖然方便，但可能與人類觀眾的真實體驗存在落差。

**Q14：StreamDuo 可能還會在哪些情境下失敗？**
A：幾個可能的失敗情境包括：當畫面中的實體在維基百科中根本沒有對應條目（例如玩家自創模組、測試版內容），研究代理將回傳無用資訊；當多個實體同時出現且視覺相似（例如同模組的不同角色），研究代理可能回傳錯誤條目；當賽評在等待答案期間已經對觀眾做出錯誤陳述，即便兩秒後取得正確答案也難以優雅地修正；當遊戲節奏極快（例如競技射擊的每秒多個事件），兩秒延遲可能讓答案過時；此外，若遊戲畫面包含大量文字或 UI 元素，研究代理可能會被這些視覺噪音干擾而檢索到不相關條目。

**Q15：這項工作開啟了哪些未來研究方向？**
A：未來可探索的方向很多：在架構層面，可以研究「多個研究代理」分工（例如一個查角色、一個查道具），或讓研究代理也具備記憶以支援跨秒推理；在訓練層面，可以嘗試在多款來源遊戲上訓練以提升泛化，或引入強化學習讓賽評學會更長期的提問策略；在知識來源層面，可以探索用遊戲內 API、官方資料庫、甚至即時網頁爬蟲取代維基百科；在應用層面，可以把 StreamDuo 的雙代理設計推廣到體育、新聞、教育等「邊看邊講」場景；最後，如何讓模型在取得延遲答案後能「優雅地回頭修正」先前的錯誤陳述，也是提升觀眾體驗的重要課題。

## 實務應用指南

### 適用場景

1. **個人遊戲實況主的 AI 副駕駛**：中小型 Twitch / YouTube Gaming 實況主往往沒有預算聘請專業賽評，StreamDuo 可作為即時副講解，在主實況主沉默或反應不及時自動補位，特別適合單人長時間實況（如 RPG、開放世界探索類遊戲）。

2. **電競賽事與錦標賽的低成本轉播**：業餘或半職業電競賽事（例：校際聯賽、地區資格賽）需要大量解說人力，可將 StreamDuo 部署為「AI 賽評 + 人類賽評」的混合模式，由 AI 負責冷場時的基礎講解與資料查詢，人類賽評專注於戰術分析與情緒渲染。

3. **遊戲無障礙輔助**：視障或低視能玩家在遊玩新遊戲時，StreamDuo 可即時描述畫面中出現的角色、道具與場景，協助他們建立空間與劇情認知，比傳統 TTS 螢幕閱讀器更具情境理解能力。

4. **遊戲教育與攻略內容自動化**：遊戲攻略網站、學習型 YouTube 頻道可利用 StreamDuo 自動生成「邊玩邊講」的教學影片，AI 賽評在玩家示範操作時即時解釋機制、提示關鍵道具，大幅降低影片製作成本。

5. **遊戲測試與 QA 自動化記錄**：遊戲開發商在內部測試階段可讓 StreamDuo 自動記錄測試員的遊玩過程並產生敘述日誌，協助 PM 與設計師快速理解測試情境，補充傳統 bug report 的不足。

### 實作前置條件

**資料需求**
- 至少一段遊戲的完整實況影片與對應的人類賽評字幕（建議 ≥ 50 小時），用於訓練「何時該說話」與「說什麼」兩個任務。
- 目標遊戲的權威文字資料庫（首選官方 Wiki 或遊戲內百科），需事先爬取並切分為可檢索的條目。
- 評估用資料：至少 5–10 款未在訓練中出現的遊戲實況影片，每款 ≥ 2 小時，並附人類賽評字幕作為 ground truth。

**運算資源**
- 訓練階段：需具備 ≥ 4 張 A100/H100 等級 GPU，用於微調影片 VLM 的 commentator 模組；研究代理（frozen VLM）只需推論級 GPU。
- 推論階段：單機單卡（如 A6000 / L40S）即可支援 720p 30fps 的即時串流；若需同時服務多觀眾，需配合佇列與水平擴展。
- 串流緩衝：建議預留 2 秒延遲的 frame buffer，以容納研究代理的回傳時間。

**技能門檻**
- 熟悉影片 VLM（如 Qwen-VL、InternVL、LLaVA-Video）的微調流程。
- 具備 RAG 系統建置經驗（向量資料庫如 Milvus / Qdrant、檢索管線設計）。
- 理解 on-policy 蒸餾與資訊增益標籤的訓練邏輯。
- 串流媒體處理經驗（FFmpeg、RTMP/WebRTC 串接）。

### 實作步驟建議

1. **定義任務邊界與評估指標**：先選定單一訓練遊戲（論文使用《柏德之門3》），並準備 10 款以上未見遊戲的測試集；建立「實體召回率」、「來源遊戲洩漏率」、「時機準確度」三項核心指標的自動化評估腳本。

2. **建置研究代理（凍結端）**：挑選一款開源視覺語言模型作為研究代理，搭配目標遊戲的 Wiki 條目建立向量索引；實作「接收影格 → 檢索相關條目 → 回傳前 K 條」的管線，目標端到端延遲控制在 2 秒內。

3. **準備 commentator 訓練資料**：將人類賽評字幕與影片幀對齊，標記每句話對應的時間點；針對每個發話時機，計算「若提供正確 Wiki 條目，模型輸出會改變多少」以產生資訊增益標籤（ask labels）。

4. **兩階段訓練 commentator**：
   - **階段一（資訊增益學習）**：以語言模型損失 + 說話決策損失微調 commentator，使其學會「在資訊增益高的時機才提問」。
   - **階段二（在線策略自我蒸餾）**：建立一個「特權副本」可看到理想答案，用其輸出作為教師訊號，對 commentator 本身進行 on-policy 蒸餾，使其學會消化帶噪聲的真實答案。

5. **整合串流管線**：將 commentator 與研究代理串接為雙代理迴圈——commentator 每秒接收影格並決定是否發話；若決定提問則送出當前影格給研究代理，2 秒後收到答案並融入後續發話。

6. **建立監控與回饋機制**：上線後持續收集「來源遊戲洩漏率」與「實體召回率」，當新遊戲上線時自動觸發 Wiki 索引更新；保留人工覆核通道以便修正錯誤模式。

7. **A/B 測試與迭代**：先以「僅 commentator」與「commentator + 研究代理」兩版本做小規模觀眾盲測，比較活潑度與整體品質分數，再決定是否全量上線。

### 潛在風險與注意事項

- **2 秒延遲對即時性的衝擊**：研究代理的回傳時間會壓縮 commentator 的反應窗口，可能錯過極短暫的關鍵事件（如閃現、爆頭）。**緩解方式**：對高時效事件（戰鬥、技能觸發）設計「不查詢、快講」的快路徑，僅對需要命名實體的場景啟動查詢。

- **Wiki 資料品質與覆蓋率不足**：小型或新發布遊戲的 Wiki 可能條目稀疏或錯誤。**緩解方式**：建立信心分數門檻，低信心時改用通用視覺描述（如「一名持劍的紅髮角色」）而非強行命名；同時允許人工注入官方 lore 文件作為補充來源。

- **來源遊戲洩漏的殘留風險**：即使訓練後洩漏率降至 1%，在長尾遊戲上仍可能誤觸。**緩解方式**：在輸出層加入「禁止詞典」後處理過濾，並定期以新遊戲重新評估。

- **計算成本與擴展性**：每場直播都需要持續的 VLM 推論 + 檢索，成本隨觀看人數線性增加。**緩解方式**：採用分層架構——邊緣節點只跑 commentator，雲端集中處理研究代理；對熱門遊戲預先快取 Wiki 條目以減少檢索次數。

- **幻覺與錯誤傳播**：commentator 可能錯誤解讀研究代理回傳的條目，產生「看起來合理但錯誤」的敘述。**緩解方式**：在訓練階段二刻意加入噪聲答案以提升魯棒性，並在推論時對高風險聲明（角色名、道具效果）加上信心標記。

- **著作權與賽評風格爭議**：若訓練資料包含特定賽評的字幕，輸出風格可能過於相似，引發抄襲疑慮。**緩解方式**：使用多元賽評來源訓練，並在產品條款中揭露 AI 訓練資料來源。

### 與其他技術的整合建議

- **與直播平台 API 整合**：透過 Twitch / YouTube 的 chat bot 或 OBS 插件介接，讓 StreamDuo 的輸出直接以 TTS 注入直播音軌；可與 StreamElements、Streamlabs 等現有工具鏈共存。

- **與遊戲內資料 API 串接**：對於支援官方 API 的遊戲（如《英雄聯盟》、《Dota 2》），可將結構化遊戲狀態（角色位置、技能冷卻）作為額外上下文注入 commentator，比純視覺輸入更可靠；研究代理可同時檢索 Wiki 與官方資料庫。

- **與現有 RAG 框架整合**：可將研究代理的檢索層換成 LangChain、LlamaIndex 等成熟框架的 retriever，並重用企業內部既有的向量資料庫與 embedding 服務，降低重複建設成本。

- **與多模態內容生成管線整合**：StreamDuo 的輸出可作為下游「自動精華剪輯」系統的輸入——AI 賽評標記的關鍵時刻（如「BOSS 出現！」）可直接對應剪輯節點，串接成「直播 → 賽評 → 精華」的自動化內容工廠。

- **與遊戲客服 / 教學助理整合**：將 commentator 模組的「提問 → 查詢 → 回答」循環復用於遊戲內 NPC 對話系統，讓 NPC 在玩家詢問時即時檢索 Wiki 條目並以角色語氣回答。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的問題描述與第 3.1 節的串流設定，理解「為什麼 AI 賽評在沒見過的遊戲上會卡住」這個核心問題；接著看圖 2 的整體流程圖，建立「commentator 問、研究代理答」的雙代理直覺，再回頭讀訓練細節會更容易吸收。

**給 AI 工程師**：重點關注第 3.3 與 3.4 節的兩階段訓練——資訊增益標籤如何量化「這個問題值不值得問」，以及 on-policy 自我蒸餾如何讓模型學會消化延遲且帶噪聲的答案；實作時可先以單一遊戲 + 開源 VLM（如 Qwen2-VL）做最小可行版本，驗證管線後再擴展到多遊戲。

**給研究者**：本篇的核心貢獻在於「跨遊戲設定」本身——把領域泛化問題引入串流影片 LLM 的評比，並提出「來源遊戲洩漏率」這個新指標；後續可探索的方向包括：研究代理換成可寫入記憶的長期代理、commentator 與人類賽評的協作式訓練、以及將此框架推廣到非遊戲領域（如體育賽事、無人機即時監控）。

**給產品經理**：關鍵訊號是「在沒見過的遊戲上仍能維持品質」——這代表產品能用單一模型服務整個遊戲庫，無需為每款新遊戲重新訓練；商業模式可考慮 SaaS 訂閱（按串流時數計費）、與直播平台分潤、或授權給遊戲發行商作為內建 AI 導遊；風險面則需特別注意延遲、Wiki 授權與賽評風格抄襲爭議。
