# CUA-SWE：當電腦操作代理程式遇上視覺軟體工程

## ⚡ TL;DR

現有程式代理與電腦操作代理各自獨立，難以處理需結合視覺回饋與原始碼修改的互動式軟體開發。
本文提出 CUA-SWE，整合原始碼編輯、指令執行、圖形互動與截圖觀察的基準與評測環境。
評估顯示前沿代理能結合視覺與執行回饋診斷、修復並驗證跨領域任務，並剖析成功修復的關鍵行為。

## 摘要翻譯

軟體開發不僅僅是編輯程式碼：開發者會反覆執行軟體、與其介面互動、透過視覺觀察其行為，並根據這些觀察來決定下一步該修改什麼，以及某項修改是否奏效。現有的編碼代理程式（coding agents）與電腦操作代理程式（computer-use agents）多半被分開研究，使得這種整合式開發流程尚未被充分探索。診斷執行階段的互動失敗，需要代理程式（agents）將視覺觀察對應到造成問題的程式碼，然後再次操作應用程式以驗證修復結果。我們提出 CUA-SWE，一個針對以電腦操作進行軟體工程的基準（benchmark）、環境（environment）與評估流程（evaluation pipeline）。除了研究圖形使用者介面（GUI）回饋如何支援診斷與修復之外，我們也探討：當所需的規格或操作資訊只能透過執行中應用程式的視覺介面取得時，代理程式是否仍能完成軟體工程任務。CUA-SWE 橫跨四個軟體工程領域，要求代理程式在同一項任務中修改程式碼與組態、執行指令、與執行中的軟體互動，並檢視視覺回饋。每項任務都包含確定性且針對任務設計的測試，用以驗證最終軟體是否滿足需求並保留指定行為。我們的評估描繪了前沿代理程式（frontier agents）如何結合原始碼層級的執行、應用程式截圖與圖形化互動，以產生經過驗證的軟體變更。我們檢視不同領域與任務資訊需求下的表現，以及與成功修復相關的開發行為。CUA-SWE 提供了一個統一的測試平台，用於研究代理程式如何運用視覺回饋與互動來引導軟體工程，並為最終產出的軟體提供可執行的正確性準則。

### 核心貢獻（3～5點）
- 提出 CUA-SWE，整合基準、環境與評估流程，用於研究代理程式如何透過電腦操作完成軟體工程任務。
- 設計橫跨四個軟體工程領域的任務，要求代理程式在同一任務內同時進行程式碼與組態修改、指令執行、GUI 互動與視覺回饋檢視。
- 探討當規格或操作資訊僅能透過執行中應用程式的視覺介面取得時，代理程式是否仍能完成軟體工程任務。
- 透過確定性且任務專屬的測試，驗證最終軟體是否滿足需求並保留指定行為。
- 分析前沿代理程式如何結合原始碼層級執行、應用程式截圖與圖形化互動，以產出經過驗證的軟體變更。

### 適合對象
從事大型語言模型代理、電腦操作代理、軟體工程自動化與智慧型軟體測試的研究人員與工程師；特別適合關注視覺回饋、GUI 互動，以及端對端軟體開發流程整合的讀者。

## 深度分析

#### 方法論解析

CUA-SWE 將傳統的 Coding Agent（程式碼代理）與 Computer-Use Agent（CUA，電腦使用代理）整合到同一個開發迴路中，核心貢獻在於把「修改程式碼」與「操作執行中的應用程式」視為不可分割的軟體工程（Software Engineering, SE）行為。其方法論可從以下幾個層面拆解：

**1. 任務形式化：Partially Observable Markov Decision Process（POMDP，部分可觀察馬可夫決策過程）**  
每個任務 \(u\) 被建模為有限範圍的 POMDP \(M_u = (S_u, A, O, P, \Omega_u, R_u)\)。Agent 接收指令 \(I_u\)、可編輯的程式碼庫（codebase）\(c_0\)，並在動作預算（action budget）內與環境互動，最終產出修改後的程式碼 \(c_T\)。狀態 \(s_t = (c_t, x_t, b_t)\) 同時包含當前程式碼、執行環境與應用程式的完整執行期狀態，以及剩餘動作次數。這種形式化強調：軟體開發不是靜態的檔案編輯，而是「程式碼—執行狀態—剩餘資源」共同演化的動態決策過程。

**2. 雙條件對照：Code-only（僅程式碼條件） vs. Hybrid CUA（混合式電腦使用條件）**  
為了量化 GUI 回饋的價值，CUA-SWE 設計了兩種觀察條件：
- **Code-only**：Agent 只能讀取原始碼、執行允許的指令（build、test、自訂腳本）並閱讀文字輸出。
- **Hybrid CUA**：在 Code-only 的基礎上，額外提供應用程式的截圖（screenshot）與圖形化操作（滑鼠、鍵盤、滾動、觸控等）。

兩者使用完全相同的任務需求與受保護的測試，因此任何效能差異都可歸因於「視覺化執行期回饋與互動能力」本身。

**3. 觀察邊界：以視覺介面為主要通道**  
CUA-SWE 刻意不開放結構化的 DOM、HTTP 請求或應用程式狀態查詢，而是讓 Agent 透過截圖與圖形操作來理解應用程式。這個設計對應真實開發情境：開發者看到的往往是「渲染後的畫面」，必須自行把視覺現象對應回原始碼中的邏輯。這也意味著 Agent 必須具備視覺理解（visual grounding）、動作規劃與程式碼定位的複合能力。

**4. 確定性驗證器（Deterministic Verifier）**  
每個任務都配備獨立的 \(V_u\)，透過預先定義的互動序列與斷言（assertions）檢查：
- 請求的行為是否正確實現或修復；
- 既有功能是否被保留（regression 檢查）；
- 修改是否符合允許範圍（例如只能編輯特定檔案）。

這些測試在受控環境中執行，確保結果可重現，並避免使用 LLM-as-a-judge 等主觀評分方式。

**5. 跨領域任務設計**  
CUA-SWE 涵蓋 Web 開發、遊戲開發、Mobile App 開發與 DevOps 四個領域。任務類型包括診斷互動錯誤、修復碰撞/動畫/觸控問題、從視覺介面恢復規格或操作資訊等。每個任務都提供可編輯專案與可執行的應用程式，Agent 可自由決定何時查看原始碼、執行指令、操作 GUI、檢視截圖並修改實作。

#### 實驗數據解讀

由於目前提供的上下文主要聚焦於方法論與任務設計，尚未包含完整的數據表格，因此本節先從「實驗設計邏輯」與「預期可解讀的結果模式」進行分析：

**1. 評估指標的意義**  
CUA-SWE 的主要指標是任務成功率（task success rate），由 deterministic verifier 判定。輔助指標可能包括：
- **Regression rate（迴歸率）**：成功修復目標問題但破壞既有功能的比例；
- **Valid tool use（有效工具使用）**：Agent 是否遵守允許的指令與編輯範圍；
- **Action budget efficiency（動作預算效率）**：在有限步數內完成任務的能力；
- **Trajectory analysis（軌跡分析）**：Agent 如何串接「執行指令 → 觀察截圖 → 定位程式碼 → 修改 → 再次驗證」的迴路。

這些指標比單純的「程式碼編輯正確率」更能反映真實軟體工程能力，因為它們同時衡量診斷、修復與驗證三個階段。

**2. Code-only 與 Hybrid CUA 的對照預期**  
- 對於「規格或操作資訊僅存在於視覺介面」的任務，Hybrid CUA 應顯著優於 Code-only，因為後者無法取得執行期的視覺證據。
- 對於純邏輯錯誤（例如可透過單元測試輸出診斷的問題），兩者差距可能較小，甚至 Hybrid CUA 會因為額外的視覺動作而消耗更多預算。
- 若 Hybrid CUA 在某些視覺任務上仍失敗，可能反映視覺模型無法正確把畫面現象對應到程式碼，或 Agent 缺乏「先操作再觀察」的主動探索策略。

**3. 領域差異的解讀**  
- **Web**：任務如「clipped chart」需要 Agent 觀察渲染結果、理解 CSS/Canvas 剪裁問題，並修改對應的前端程式碼。
- **Game**：碰撞錯誤或動畫異常需要時間序列上的互動（例如跳躍、移動），單張截圖可能不足，必須透過連續操作與觀察來診斷。
- **Mobile**：觸控事件、狀態錯誤、身份混淆等問題，要求 Agent 模擬觸控操作並觀察畫面狀態變化。
- **DevOps**：追蹤錯誤、告警邏輯、指標與日誌，可能需要結合指令列輸出與視覺化監控介面。

不同領域的「視覺—程式碼對應難度」不同，因此跨領域比較能揭示 Agent 在特定觀察—動作耦合上的弱點。

**4. 成功修復的行為模式**  
從軌跡分析角度，成功的 Agent 通常會展現以下迴路：
1. 啟動應用程式並取得初始截圖；
2. 執行重現問題的互動序列；
3. 根據視覺異常定位可能相關的原始碼檔案；
4. 進行最小化修改；
5. 重新編譯/執行並再次操作以驗證修復；
6. 檢查既有功能是否仍然正常。

失敗模式則可能包括：過度依賴靜態程式碼分析而忽略視覺證據、誤判截圖中的視覺狀態、修改後未進行迴歸測試、或在錯誤的檔案上浪費動作預算。

#### 與現有研究的比較

CUA-SWE 的定位在於填補兩條研究路線之間的空白：

**1. 與 Coding Agent 基準的比較**  
傳統基準如 SWE-bench 主要評估 Agent 對程式碼庫的修改能力，驗證方式多為執行單元測試或整合測試。這類基準的侷限在於：
- 測試通常基於文字輸出或 API 行為，較少涉及 GUI 狀態；
- Agent 不需要「使用」自己寫的軟體，只需讓測試通過。

CUA-SWE 的改進在於把「執行期視覺行為」納入評估，要求 Agent 不僅修改程式碼，還要透過操作與觀察來診斷與驗證。

**2. 與 Computer-Use Agent 基準的比較**  
OSWorld、VisualWebArena 等基準評估 Agent 在現有應用程式中完成使用者任務的能力，例如操作瀏覽器或辦公軟體。這些任務通常：
- 不允許修改應用程式原始碼；
- 目標是「使用軟體」而非「開發軟體」。

CUA-SWE 則要求 Agent 修改程式碼與設定檔，從源頭改變應用程式行為，並透過後續互動確認修改效果。

**3. 與視覺化軟體開發基準的比較**  
Yang et al. (2024b) 與 Chi et al. (2026) 等研究聚焦於特定領域（如 JavaScript 使用者介面或遊戲），並引入執行期視覺回饋。CUA-SWE 將這些想法擴展到四個不同領域，並提供統一的開發環境與評估流程。此外，CUA-SWE 特別關注「規格資訊僅存在於視覺介面」的情境，這是過往基準較少系統性探討的。

**4. 與視覺化 IDE 或 Agentic Judge 框架的比較**  
Aggarwal & Welleck (2025) 提供視覺化 IDE 讓 Agent 使用開發工具；Li et al. (2026) 則透過 agentic judge（代理評判器）評估跨圖形與指令列的工作流程。相較之下，CUA-SWE 的優勢在於使用 deterministic verifier（確定性驗證器），結果可重現、不依賴 LLM 評分；但其侷限是任務必須能被預先定義的測試完整覆蓋，對於開放式設計任務的適用性較低。

**5. 主要限制**  
- **觀察通道單一**：僅提供截圖與圖形操作，未納入 accessibility tree、DOM 或應用程式狀態查詢，可能讓某些本可簡化的任務變得過度困難。
- **任務設計成本**：每個任務都需要可執行專案、受保護測試與迴歸檢查，擴充規模較為昂貴。
- **動作預算壓力**：視覺互動需要額外步數，可能對長期規劃能力較弱的模型不利，即使其具備正確的診斷能力。
- **領域代表性**：雖然涵蓋四個領域，但每個領域的任務數量與錯誤類型仍可能無法代表真實世界中的所有視覺軟體工程問題。

#### 可重現性評估

CUA-SWE 在設計上具備高度可重現性的潛力，原因如下：

**1. 確定性測試與受控環境**  
每個任務使用 deterministic verifier，在固定環境中執行互動序列與斷言。只要程式碼庫、依賴版本與執行環境一致，不同研究者應能獲得相同的通過/失敗結果。

**2. 明確的動作與觀察介面**  
Code-only 與 Hybrid CUA 兩種條件都有清楚的觀察邊界：前者僅能使用原始碼與指令輸出，後者額外提供截圖與圖形操作。這種明確定義降低了實作上的歧義。

**3. 釋出狀態的不確定性**  
根據目前提供的文本，尚未明確說明 CUA-SWE 的任務倉庫、評估腳本、環境映像檔或 trajectories 是否已公開。若作者後續釋出：
- 容器化環境（如 Docker image）與版本鎖定的依賴；
- 所有任務的初始程式碼與受保護測試；
- Agent 介面與動作 API 的實作；
- 各模型評估的完整 trajectories；

則可重現性將非常高。反之，若僅釋出論文描述而無執行環境，其他研究者將難以複製結果。

**4. 模型權重與 API 變動**  
論文評估的是 frontier models（前沿模型）與 coding agents，多數可能透過 API 呼叫。API 行為與模型版本會隨時間變化，因此即使環境固定，長期重現分數仍可能受模型更新影響。建議作者記錄評估時的模型版本、API 日期與溫度（temperature）等參數。

**5. 建議的再現步驟**  
- 使用提供的容器重建開發環境；
- 在 Code-only 與 Hybrid CUA 兩種條件下分別執行相同 Agent；
- 比對 deterministic verifier 的輸出與論文報告的成功率；
- 分析 trajectories 以確認成功與失敗模式是否一致。

#### 未來研究方向

CUA-SWE 開啟了多個值得後續探索的研究方向：

**1. 更強的視覺—程式碼對齊模型**  
目前的視覺語言模型（Vision-Language Models, VLMs）在理解截圖方面已有進展，但把「畫面現象」對應到「原始碼中的特定函式或設定」仍是挑戰。未來可研究專門的 visual grounding 技術，例如把截圖中的 UI 元素與程式碼中的組件名稱、CSS selector 或遊戲物件建立連結。

**2. 結合結構化觀察通道**  
CUA-SWE 刻意限制為純視覺，但未來可探討「截圖 + accessibility tree + DOM + 應用程式狀態」的多通道觀察，研究不同資訊組合對診斷效率的影響。

**3. 長期規劃與信用分配**  
軟體工程任務通常涉及多步驟修改與多次驗證。如何讓 Agent 在長期互動中進行信用分配（credit assignment），判斷「哪一次程式碼修改」導致「哪一個視覺行為改變」，是強化學習與 Agent 規劃的重要課題。

**4. 自動化任務生成**  
目前任務需要人工設計。未來可從真實的 bug report、使用者回饋或螢幕錄影中自動生成 CUA-SWE 風格的任務，擴大基準規模並提升真實性。

**5. 跨領域遷移學習**  
研究 Agent 在 Web、遊戲、Mobile、DevOps 之間的知識遷移。例如，在遊戲中學到的「碰撞錯誤診斷」策略是否能遷移到 Mobile App 的觸控事件問題。

**6. 人機協作介面**  
CUA-SWE 目前評估全自動 Agent。未來可設計互動式開發介面，讓人類開發者與 Agent 共同操作 GUI、審查截圖並決定下一步修改。

**7. 安全性與沙箱機制**  
由於 Agent 可執行指令並操作執行中的應用程式，未來需要更強大的沙箱（sandbox）與權限控管，避免自動化過程中意外破壞系統或洩漏敏感資訊。

**8. 評估指標的擴充**  
除了通過/失敗，可引入「最小修改原則」、「修復所需互動次數」、「人類可解釋的修復說明」等指標，更全面地評估 Agent 的軟體工程素養。

## 論文問答

**Q1：CUA-SWE 要解決的核心問題是什麼？為何僅靠原始碼與命令列輸出不足以開發互動式軟體？**  
A：互動式軟體的開發需要代理實際執行軟體、操作介面，並從視覺線索診斷問題與驗證修改，但原始碼與命令列輸出無法完整呈現使用者看到的畫面以及互動後的動態行為。例如平台遊戲中角色跳上平台後會穿透落下，靜態截圖可能看起來正常，唯有實際遊玩並觀察跳躍與著陸過程，才能將異常行為對應到移動或碰撞程式碼。因此，CUA-SWE 旨在建立一個能同時進行程式碼編輯、命令執行、圖形介面互動與視覺檢查的統一評估環境。

**Q2：現有的程式設計代理與電腦使用代理為何難以單獨處理視覺軟體工程任務？**  
A：程式設計代理主要檢視程式庫、編輯檔案並執行命令與測試，但缺乏對執行中應用程式圖形介面的觀察與操作能力。電腦使用代理雖能透過截圖與滑鼠鍵盤操作介面，卻通常不具備修改原始碼並驗證修復的軟體工程流程。兩者各自的基準測試也分別只評估程式碼變更或在現有應用程式中完成任務，鮮少將「診斷—修改—透過 GUI 驗證」整合在同一回合中，因此 CUA-SWE 試圖彌補這個缺口。

**Q3：為何將視覺執行回饋與程式碼修改、驗證連結起來很重要？本文提出哪兩個核心問題？**  
A：視覺執行回饋不僅能揭露實作是否符合預期，有時還承載了僅存在於執行中應用程式介面上的規格或操作資訊，代理必須將其轉譯為可運作的程式碼。這促使研究者探問：代理如何利用 GUI 回饋來診斷、修復與驗證軟體？以及當必要規格或操作資訊只能透過執行中應用程式的視覺介面取得時，代理是否仍能完成軟體工程任務？回答這兩個問題有助於理解代理在真實開發情境中整合觀察、推理與實作的能力。

**Q4：CUA-SWE 的核心組成是什麼？它涵蓋哪些軟體工程領域？**  
A：CUA-SWE 包含一個基準測試、一個互動式開發環境，以及一個評估流程，專門用於讓電腦使用代理進行視覺軟體工程。其任務橫跨網頁開發、遊戲開發、行動應用程式開發與 DevOps 四大領域，每個任務都提供可編輯的專案與可執行的應用程式。代理必須在單一開發回合中修改程式碼與設定、執行命令、與執行中的軟體互動，並檢視視覺回饋。

**Q5：CUA-SWE 設計了哪兩種評估條件？比較它們的目的為何？**  
A：兩種條件分別是「僅程式碼」條件與「混合 CUA」條件。在僅程式碼條件下，代理只能檢視與編輯原始碼、執行允許的建置、測試與自訂指令，並閱讀其文字輸出；混合 CUA 條件則額外提供應用程式截圖與圖形操作能力。兩者使用相同的任務需求與受保護的測試，因此可以直接比較「僅靠原始碼層級執行」與「加上 GUI 視覺與互動」對任務成功率的影響。

**Q6：CUA-SWE 在環境設計上做了哪些選擇，以貼近真實開發流程？**  
A：環境允許代理自主決定何時檢視原始碼、執行命令、與應用程式互動、檢查截圖，以及重新修訂實作，而不是被強制遵循固定步驟。每個任務都提供可編輯的專案與持續執行的應用程式，讓視覺觀察能引導程式碼變更，而後續互動則用來檢查修改效果。整個互動被建模為有限範圍的部分可觀察馬可夫決策過程，並以確定性驗證器決定最終是否成功。

**Q7：本文評估了哪些模型與代理？主要從哪些維度分析結果？**  
A：作者評估了一系列前沿模型與程式設計代理，並刻畫它們在 CUA-SWE 上的任務成功率。分析維度包括不同軟體工程領域與應用程式家族之間的表現差異，以及那些需要從執行中應用程式的視覺介面還原規格或操作資訊的任務。此外，研究也透過軌跡分析，探討成功修復與哪些開發行為有關，例如如何結合執行回饋與視覺觀察來實作與驗證。

**Q8：CUA-SWE 如何判定任務成功？任務專屬測試扮演什麼角色？**  
A：每個任務都配備確定性的任務專屬測試，這些測試在受控環境中執行修改後的軟體，並透過互動序列以及對渲染介面或執行時狀態的斷言來驗證需求。測試同時檢查請求的行為是否實現，以及指定的既有功能是否被保留，從而偵測迴歸問題。最終任務成功不僅要求所有測試通過，也要求代理在開發過程中遵守有效的工具使用規範。

**Q9：從「僅程式碼」與「混合 CUA」的比較中，可以觀察到哪些關鍵現象？**  
A：比較結果顯示，當任務所需的資訊只能透過應用程式的視覺介面取得時，擁有截圖與圖形互動能力的混合 CUA 條件通常更具優勢。相對地，若資訊已充分呈現在原始碼或命令輸出中，則兩種條件的表現差距可能較小。透過軌跡分析，作者進一步指出成功修復往往伴隨著代理能夠反覆連結執行回饋與視覺觀察，並據此調整程式碼與驗證假設。

**Q10：CUA-SWE 可應用在哪些實務情境？能否舉例說明？**  
A：在網頁開發中，代理可能需要修復圖表顯示被裁切的問題；在遊戲開發中，則要診斷角色碰撞錯誤或動畫異常。行動應用程式開發情境包括身分混淆、狀態錯誤或觸控問題；DevOps 情境則涉及追蹤錯誤、警示邏輯、指標與日誌的視覺化檢查。這些例子都說明代理必須同時看懂介面、修改程式碼，並透過再次操作應用程式來確認修復。

**Q11：若要將 CUA-SWE 的評估框架轉化為實際產品，需要考慮哪些設計與安全議題？**  
A：產品化時需要讓代理能夠安全地操作整合開發環境與應用程式的圖形介面，同時限制其只能修改允許的檔案與執行允許的命令。確定性測試與受保護的驗證器可確保修復結果不會因環境差異而變動，並防止代理透過取巧方式通過評估。此外，必須設計清晰的動作預算與工具使用規範，以避免代理無限試錯或執行危險操作。

**Q12：CUA-SWE 對人工智慧與軟體工程領域可能帶來什麼影響？**  
A：CUA-SWE 提供了一個統一的測試平台，讓研究者能夠系統性地研究代理如何利用視覺回饋與互動來引導軟體工程。它打破了傳統上程式設計代理與電腦使用代理各自獨立研究的局面，促進兩種能力在同一任務中的整合。長遠來看，這類基準有助於推動能夠像人類開發者一樣「邊用邊改」的自主軟體工程代理。

**Q13：CUA-SWE 有哪些已知的限制或適用範圍上的考量？**  
A：視覺條件刻意只提供截圖與圖形操作，而不提供結構化 DOM、HTTP 或應用程式狀態查詢，這雖然貼近真實使用者經驗，但也可能讓某些任務比使用結構化觀察通道更困難。此外，代理在有限動作預算內運作，面對需要大量探索的複雜互動時可能無法完成。目前任務雖橫跨四大領域，但仍屬於受控的基準情境，與完全開放的實際開發專案仍有距離。

**Q14：代理在 CUA-SWE 上可能出現哪些典型失敗案例？**  
A：代理可能無法正確將視覺觀察到的異常對應到負責的程式碼區段，導致修改了錯誤的檔案或函式。它也可能未能從執行中應用程式的介面還原出隱藏的規格或操作資訊，因而實作出不符合需求的行為。此外，即使主要缺陷被修復，代理仍可能因忽略迴歸測試或過度修改而破壞既有功能，最終無法通過確定性驗證。

**Q15：未來研究可以如何延伸 CUA-SWE 的方向？**  
A：未來可以擴展到更多軟體工程領域與更開放的任務情境，例如需要多輪使用者回饋或長期維護的專案。結合結構化觀察通道與視覺回饋的多模態代理，也有助於理解不同資訊來源如何互補。此外，發展更強大的確定性驗證機制、自動化錯誤定位，以及將代理評判器（agentic judge）整合進評估流程，都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **前端互動缺陷的視覺化修復**  
   適用於網頁或行動應用中「畫面看起來正常、但使用者操作後行為錯誤」的問題，例如圖表裁切錯誤、按鈕狀態未同步、觸控事件誤判。代理程式可透過截圖與 GUI 互動定位問題，再回頭修改程式碼並重跑驗證。

2. **遊戲碰撞與動作邏輯除錯**  
   平台遊戲、物理模擬或動畫系統中，角色穿牆、落地判定異常等問題難以僅靠靜態程式碼發現。代理程式需要實際操作遊戲、觀察行為，再將視覺線索對應到碰撞或移動程式碼進行修復。

3. **DevOps 監控告警與可觀測性調校**  
   當追蹤（trace）、指標（metrics）或日誌的告警邏輯只能從儀表板視覺化介面確認時，代理程式可透過瀏覽監控畫面、點擊查詢、滾動時間軸來還原規格，並據此修改設定檔或查詢語句。

4. **行動應用身分與狀態錯誤修復**  
   例如使用者切換帳號後畫面仍顯示舊資料、表單狀態錯亂等，需要代理程式在模擬器或真機上重現操作序列，並以視覺回饋確認修復後狀態正確。

5. **跨領域全端任務的端到端驗證**  
   適合同時涉及後端 API、前端畫面與執行環境設定的任務，例如修改設定後必須透過 UI 觀察結果，並以確定性測試確認既有功能未被破壞。

### 實作前置條件

- **資料準備**
  - 可編輯的原始碼倉儲（git repo 或容器化專案）。
  - 每個任務需附帶：需求說明、需保留的既有行為清單、確定性驗證腳本（含互動序列與斷言）。
  - 執行應用所需的環境設定（Dockerfile、相依套件清單、啟動指令）。

- **運算資源**
  - 可執行 GUI 的容器或虛擬機（需支援 X11、VNC、noVNC 或雲端瀏覽器環境）。
  - 足夠的運算與記憶體以同時運行 IDE／終端機、應用程式與代理程式。
  - 截圖與圖形互動的延遲需控制在可接受範圍，避免代理程式因等待渲染而誤判。

- **技能與工具**
  - 熟悉電腦使用代理（CUA）框架與多模態模型 API（如支援視覺輸入的 LLM）。
  - 具備建構確定性測試的能力：能撰寫互動腳本、畫面斷言、狀態檢查。
  - 了解目標應用領域（網頁、遊戲、行動、DevOps）的開發與部署流程。

### 實作步驟建議

1. **定義任務與驗證契約**  
   將需求轉換為可執行的任務描述：明確「要修復或實作什麼行為」、「哪些既有功能必須保留」、「允許修改的檔案範圍」。同步撰寫獨立的確定性驗證器，包含互動步驟與預期結果。

2. **建構互動式開發環境**  
   部署可同時提供原始碼編輯、CLI 指令執行、GUI 截圖與滑鼠鍵盤操作的統一環境。確保代理程式能在同一個 episode 內自由切換「讀碼 → 執行 → 看畫面 → 操作 → 改碼」。

3. **建立 Code-only 基線**  
   先讓代理程式僅使用原始碼與命令輸出完成任務，作為對照組。這有助於量化「視覺回饋」與「GUI 互動」帶來的實際增益。

4. **加入 Hybrid CUA 視覺通道**  
   在基線環境上疊加截圖觀察與圖形操作能力。設計觀察頻率與動作空間（點擊、輸入、滾動、滑動），避免資訊過載或動作過於細碎。

5. **執行對照實驗與軌跡分析**  
   同時在 Code-only 與 Hybrid CUA 條件下執行相同任務。記錄成功與失敗軌跡，分析代理程式如何將視覺觀察連結到原始碼修改，以及如何透過重新互動驗證修復。

6. **迭代驗證器與環境穩定性**  
   根據實驗結果修正測試腳本，減少 flaky tests；調整環境等待時間、截圖解析度與輸入延遲，確保結果可重現。

7. **產品化封裝**  
   將任務包、環境映像檔與評估管線打包為可重複執行的 CI／CD 步驟，讓開發團隊能自動化驗證候選修復或功能實作。

### 潛在風險與注意事項

- **視覺觀察的不確定性**  
  截圖解析度、渲染延遲、動畫幀率都可能導致代理程式誤判。建議加入明確的等待條件與穩定化截圖機制，並在測試中優先驗證應用狀態而非純視覺像素。

- **動作預算爆炸**  
  同時開放編碼與 GUI 操作會大幅增加動作空間。應設定合理的步數上限，並提供高階工具（例如「執行測試」、「重啟應用」）以減少低階重複操作。

- **過度擬合驗證器**  
  代理程式可能只讓測試通過而未真正修復問題。驗證器應包含多組互動序列與回歸測試，並限制允許修改的檔案範圍，避免投機式修改。

- **環境再現性問題**  
  GUI 應用對系統字型、解析度、時區敏感。建議使用容器化環境並鎖定映像檔版本，確保不同執行之間的畫面與行為一致。

- **安全與副作用**  
  代理程式能執行指令與操作網路應用，需限制其網路權限、檔案系統存取範圍，並在沙箱中運行，避免誤刪資料或觸發外部服務。

### 與其他技術的整合建議

- **與現有 IDE／LSP 整合**  
  可將 CUA-SWE 環境嵌入 VS Code Server 或 JetBrains Gateway，讓代理程式使用語言伺服器進行符號跳轉、重構與型別檢查，提升程式碼理解效率。

- **與傳統軟體測試框架整合**  
  將確定性驗證器對接到 Playwright、Selenium、Appium 或遊戲測試框架，讓互動序列與斷言能直接沿用現有測試資產。

- **與 CI／CD 管線整合**  
  把評估管線包裝成 GitHub Actions／GitLab CI 任務，在每次提交或 PR 時自動執行視覺化軟體工程任務，作為回歸或候選修復的閘道。

- **與多模態模型服務整合**  
  透過標準 API 將截圖傳送至支援視覺的 LLM，並設計結構化的動作輸出（JSON／XML）以銜接底層自動化工具，降低解析錯誤。

- **與知識庫／規格文件整合**  
  當部分規格僅存在於運行中的 GUI 時，可搭配 RAG 檢索既有文件，輔助代理程式將視覺觀察轉譯為正確的程式碼語意。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦在「為什麼需要看著畫面寫程式」這個核心概念：許多 bug 無法從程式碼直接看出，必須實際操作應用才能發現。可先從單一領域（例如網頁前端）的簡單任務開始，理解截圖、點擊、修改程式碼、再驗證的循環，不必急著深入 MDP 或評估指標。

- **AI 工程師**  
  本論文提供了一個可落地的多模態代理評估框架，重點在於如何設計「Code-only」與「Hybrid CUA」兩種條件來量化視覺回饋的價值。建議仔細研究環境介面、動作空間與確定性驗證器的設計，並思考如何將自家模型接入該管線，同時注意截圖延遲與動作預算對實際效能的影響。

- **研究人員**  
  本文把視覺軟體工程形式化為部分可觀察馬可夫決策過程，並提出跨領域基準，適合做為後續研究的共同試驗場。建議關注任務資訊需求的分類（例如規格是否僅能從 GUI 還原）、成功與失敗軌跡的分析方法，以及如何利用此框架探討規劃、視覺推理與工具使用的交互作用。

- **產品經理**  
  這項工作描繪了「能看、能點、能改、能驗證」的下一代開發代理願景。建議從適用場景與風險章節切入，評估在貴組織的網頁、行動或 DevOps 流程中，哪些重複性的視覺化除錯任務最適合優先導入；同時留意環境穩定性、安全性與驗證器維護成本，這些都是產品化時的關鍵落地門檻。
