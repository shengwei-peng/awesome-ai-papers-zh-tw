## 摘要翻譯

大型語言模型（LLMs）為自動化程式碼撰寫開啟了新的可能性，並成為大多數程式碼補全工具的骨幹。雖然 LLMs 在主流語言上表現出色，但它們往往缺乏對所謂低資源程式語言的支援，因為這些語言的訓練資料稀少。因此，這些語言在可供其社群使用的程式碼補全工具品質上落後。一個具體的例子是 Pharo，這是一種受 Smalltalk 啟發的語言，其整合式開發環境（IDE）目前僅提供單一詞元（token）補全。在本研究中，我們報告了將基於 LLM 的程式碼補全引入 Pharo 的經驗。首先，我們描述一個端對端管線，結合 Pharo 專屬資料策展、開源程式碼大型語言模型（open code LLMs）的持續預訓練與微調。其次，我們提出一組 Pharo 程式碼補全基準測試，用於評估模型是否（i）學習 Pharo 的語法，以及（ii）準確地補全來自真實世界 GitHub 儲存庫的遮罩 Pharo 程式碼。第三，我們實證地顯示 Pharo 專用模型在 Pharo 補全任務上顯著優於其原始基礎檢查點（original base checkpoints），並在準確率上超越規模顯著更大的程式碼大型語言模型（code LLMs）。總體而言，我們的個案研究證明了為低資源程式語言導入強大的基於 LLM 的程式碼補全是可行的，且模型規模夠小，足以提供「即時」（real-time）的 IDE 支援。

### 核心貢獻（3～5點）
- 提出一套結合 Pharo 專屬資料策展、開源程式碼大型語言模型持續預訓練與微調的端對端管線，以將 LLM 導入低資源程式語言的程式碼補全。
- 設計一組 Pharo 程式碼補全基準測試，評估模型是否學習 Pharo 語法，並能準確補全來自真實世界 GitHub 儲存庫的遮罩程式碼。
- 實證顯示 Pharo 專用模型不僅顯著優於其原始基礎檢查點，還能在準確率上超越規模顯著更大的程式碼大型語言模型。
- 證明以夠小的專用模型為低資源程式語言提供強大的基於 LLM 的程式碼補全，並支援 IDE 即時應用的可行性。

### 適合對象
本論文適合對低資源程式語言、LLM 領域適應（domain adaptation），以及程式碼補全技術有興趣的研究人員與實務工作者；特別是 Pharo／Smalltalk 社群開發者、IDE 工具建構者，以及希望了解如何透過持續預訓練與微調提升開源程式碼大型語言模型在冷門語言上表現的讀者。

## 深度分析

#### 方法論解析

本研究提出一條完整的端對端管線（end-to-end pipeline），目標是將基於大型語言模型（LLMs）的程式碼補全（code completion）能力帶入 Pharo 這類低資源程式語言（low-resource programming languages）。整體方法可拆解為三個核心環節：Pharo 專屬資料策展（Pharo-specific data curation）、持續預訓練（continued pre-training）與微調（fine-tuning），以及推論階段的量化（quantization）與 IDE 即時支援（real-time in-IDE support）。

**1. 資料策展（Data Curation）**

Pharo 的生態規模極小，公開儲存庫（public repositories）僅約 2,000 個，與 Python 的約 2,600 萬個相比差距達四個數量級（orders of magnitude）。更棘手的是，Pharo 原始碼（source code）使用 Tonel 格式儲存，這是一種為了跨 Smalltalk 方言互操作性而設計的格式，會將類別定義中繼資料（metadata）與可執行程式碼混雜在同一檔案內。若直接將 Tonel 檔案餵給模型，容易讓模型學到雜訊，例如把 `#name : 'ClassName'` 這類封裝資訊誤認為可執行語法，或混淆方法（method）與類別宣告的邊界。因此，作者必須設計 Pharo 專屬的清理與正規化流程，從真實世界 GitHub 儲存庫（real-world GitHub repositories）中萃取出乾淨、可用於訓練的原始碼語料庫（source code corpora）。

**2. 模型選擇與持續預訓練 / 微調**

考量到最終目標是在開發者本機提供「即時」程式碼補全，研究選擇了較小的開源程式碼大型語言模型（open code LLMs），包括 Qwen2.5 Coder Base（0.5B、1.5B、3B、7B 參數版本）以及 Mellum-base（4B）。這些模型先在 Pharo 語料上進行持續預訓練，使其熟悉 Pharo 的語法（syntax）與統計規律性（statistical regularities）；接著再針對程式碼補全任務進行微調，學習根據部分撰寫的程式（partially written programs）預測可能的接續內容（likely continuations）。透過這種「先持續預訓練、後任務微調」的兩階段策略，模型得以在保留通用程式理解能力的同時，顯著強化對 Pharo 的專精程度。

**3. 推論最佳化與 IDE 整合**

為了達成 IDE 即時支援（real-time in-IDE support），研究對模型進行量化（quantization），以降低記憶體佔用並縮短推論延遲。這對程式碼補全工具（code completion tools）至關重要，因為開發者對延遲極為敏感，補全建議必須在毫秒級產生，否則使用者體驗會大打折扣。

**4. 評估基準設計**

本研究同時提出兩類互補的 Pharo 程式碼補全基準測試（Pharo code completion benchmarks）：

- **語法學習基準**：將廣泛使用的 HumanEval+ 翻譯為 Pharo，並收集 Exercism 上的 Pharo 練習題，共 211 道程式任務。每題包含題目描述、標準解答與測試。研究採用「遮罩標準解答中的部分程式碼，讓模型預測遮罩區域，再執行測試」的評估方式，檢驗模型是否真正學會 Pharo 語法。
- **真實場景補全基準**：從公開 GitHub 儲存庫中收集 488 筆開發者實際提交（commits），將開發者新增的程式行隨機遮罩，要求模型補全這些變更。這模擬了 LLM 在真實開發過程中可提供的協助。

整體而言，方法論的亮點在於「從資料清理、模型適應到評估基準」的全鏈路設計，並且刻意選擇小模型以兼顧效率與可部署性。

#### 實驗數據解讀

雖然提供的摘錄未列出完整數值表格，但從論文敘述可歸納出以下實驗發現與其意涵：

**1. Pharo 專用模型顯著優於原始基礎檢查點（original base checkpoints）**

經過 Pharo 專屬資料策展後的持續預訓練與微調，Pharo 專用模型（Pharo-specialized models）在兩類基準測試上都明顯超越未經適配的基礎模型。這證明了即使基礎程式碼大型語言模型（code LLMs）已具備強大的通用程式能力，對於 Pharo 這種語法獨特、訓練資料稀缺的語言，仍需要專門的領域適應（domain adaptation）才能發揮實用價值。

**2. 小模型可擊敗規模顯著更大的程式碼大型語言模型（substantially larger code LLMs）**

研究強調，Pharo 專用的小模型在 Pharo 程式碼補全任務上的準確率（accuracy）超過了體量大得多的通用程式碼 LLMs。這呼應了「領域專精勝過單純放大模型」的觀點：對於低資源語言，與其依賴在通用語料上訓練的巨型模型，不如使用針對目標語言精心調適的小模型。這也為在資源受限環境（例如開發者本機）部署高品質補全工具提供了可行性。

**3. 語法基準與真實補全基準的互補性**

- 在 HumanEval+ 與 Exercism 的 211 道題目上，模型必須產生語法正確且能通過測試的程式片段，這檢驗的是「結構化生成」與「語義正確性」。
- 在 488 筆真實 commits 的遮罩程式碼（masked code）補全中，模型面對的是未經整理、風格各異的實際程式碼，這檢驗的是「真實開發情境下的接續預測能力」。

兩者結合，能更全面地評估模型是否只是背誦了常見語法樣式，還是真的能協助開發者完成日常編輯工作。

**4. 量化對即時性的影響**

論文將模型量化後用於 IDE 即時支援，意味著實驗不僅關注準確率，也關注延遲與資源消耗。雖然摘錄未提供具體的推論時間數據，但選用 0.5B 至 7B 等級的模型並進行量化，顯示作者在目標設定上已將「即時性」視為與準確率同等重要的指標。

**5. 可能的限制與解讀風險**

由於真實場景基準是從公開儲存庫中抽取，可能無法完全代表企業內部或私有專案的程式碼風格；此外，隨機遮罩新增程式行是一種簡化的模擬，實際開發中開發者可能會分段輸入、刪改或重構，這些動態行為未必能被靜態遮罩完整捕捉。

#### 與現有研究的比較

**1. 相較於主流語言的程式碼補全研究**

現有大多數基於 LLM 的程式碼補全工具（如 GitHub Copilot、CodeWhisperer 等）在 Python、Java、JavaScript 等高資源語言上表現優異，因為這些語言擁有數百萬甚至數千萬的公開儲存庫。本研究則將焦點轉向極端低資源情境：Pharo 僅有約 2,000 個公開儲存庫，且語法受 Smalltalk 啟發，與 C-style 語言差異極大。這要求研究者必須從資料策展、模型適應到評估方式都重新設計，而非直接套用現有工具鏈。

**2. 相較於其他低資源語言研究**

過去改善低資源語言 LLM 表現的策略包括資料擴增（data augmentation）、合成資料生成（synthetic data generation）與多語言語料庫建構（curated multilingual corpora）等。本研究的貢獻在於提供了一個具體的端到端個案研究（case study），並針對 Pharo 的 Tonel 格式、Smalltalk 風格語法等獨特挑戰提出解決方案。相較於僅提出通用方法的研究，本文更強調「語言特異性」的重要性。

**3. 相較於單一詞元補全（single-token completion）**

Pharo 的 IDE 原本僅提供單一詞元補全，功能遠不如現代多詞元、具上下文感知（context-aware）的補全工具。本研究將 LLM 引入後，模型可產生多詞元建議，並利用更廣泛的上下文，這是對現有 Pharo 開發環境的重大升級。

**4. 主要改進與創新**

- 提出針對 Tonel 格式的資料清理流程，減少中繼資料對模型學習的干擾。
- 設計兩類互補的 Pharo 程式碼補全基準測試，填補該語言缺乏標準化評估的缺口。
- 證明小模型經過專業化後，可在特定低資源語言上擊敗大模型，為資源受限部署提供實證支持。

**5. 限制與未解決問題**

- **單一語言聚焦**：研究僅針對 Pharo，方法能否遷移到其他低資源語言（如 Racket、Julia、Lua）仍需驗證。
- **無使用者研究**：實驗以自動化指標為主，未報告開發者實際使用體驗或生產力提升。
- **資料規模天花板**：即使經過精心策展，2,000 個儲存庫的資料量仍可能限制模型上限，特別是對於罕見 API 或領域特定程式庫。
- **通用能力退化風險**：持續預訓練與微調可能讓模型過度專精於 Pharo，影響其在其他語言上的表現，論文摘錄未明確討論此權衡。

可重現性（reproducibility）是評估任何機器學習研究的重要維度。根據目前提供的摘錄，可做出以下評估：

**1. 方法描述的可重現性**

論文對端對端管線有相當清楚的描述：從 Pharo 專屬資料策展、持續預訓練、微調到量化與基準設計，邏輯鏈完整。然而，摘錄中未提供具體的超參數（如學習率、訓練步數、批次大小）、資料清理腳本細節、遮罩策略（masking strategy）的實作方式，或量化位元數等資訊。這些細節對於完全重現結果至關重要。

**2. 開源程式碼與資料集**

摘錄未提及是否釋出了原始碼、資料處理腳本、Pharo 程式碼補全基準測試資料集，或預訓練 / 微調後的模型權重（model weights）。若論文未提供這些 artifact，則其他研究者難以直接複製結果，只能依據描述重新實作。

**4. 評估基準的可取得性**

HumanEval+ 與 Exercism 均為公開資源，但將 HumanEval+ 翻譯為 Pharo 的過程、以及從 488 筆 commits 建構的真實補全基準，需要額外的資料處理與篩選。若作者能公開這些翻譯版本與遮罩後的測試集，將大幅提升可重現性。

**5. 整體評估**

目前根據摘錄判斷，本研究在方法層面具備一定的可重現性輪廓，但缺乏具體的實作細節與開源 artifact 資訊。若要達到高標準的可重現性，建議作者釋出：資料清理腳本、訓練設定、微調後模型權重、Pharo 版 HumanEval+/Exercism 測試集，以及真實 commits 補全基準。

#### 未來研究方向

基於本研究的成果與限制，可延伸出以下幾個值得探索的方向：

**1. 跨低資源語言的方法遷移**

將本研究的端對端管線應用到其他低資源程式語言（如 Racket、Julia、Lua、Erlang、OCaml 等），驗證「小模型 + 專屬資料策展 + 持續預訓練 / 微調」的通用性，並建立多語言低資源程式碼補全基準。

**2. 合成資料與資料擴增**

Pharo 的公開儲存庫數量有限，未來可結合合成資料生成（synthetic data generation）技術，例如利用較大的通用模型生成 Pharo 程式碼，再經過過濾與驗證後加入訓練語料，以緩解資料稀缺問題。

**3. 檢索增強生成（Retrieval-Augmented Generation, RAG）**

在 IDE 中整合檢索機制，讓模型在補全時能參考專案內的相關類別、方法或文件。這對於 Smalltalk / Pharo 這種高度動態、訊息導向的語言尤其重要，因為正確的補全往往依賴於執行期型別資訊。

**4. 多詞元補全與互動式使用者介面**

研究已證明小模型可產生多詞元建議，但未來需設計更友善的 IDE 互動方式，例如「幽靈文字（ghost text）」、部分接受（partial acceptance）、多選建議等，並進行使用者研究以評估實際生產力提升。

**5. 結合執行期資訊的補全**

Pharo 是動態型別語言，靜態分析難以完全掌握變數型別。未來可探索讓 LLM 結合執行期型別推論、物件檢視器（inspector）或測試執行結果，以產生更精準的補全建議。

**6. 模型壓縮與邊緣部署**

進一步研究更激進的量化、知識蒸餾（knowledge distillation）或模型剪枝技術，使 Pharo 專用模型能在更低階的硬體上運行，擴大其在教育與開發社群中的可及性。

**7. 長期維護與持續學習**

程式語言與其生態系持續演進，未來可建立持續學習（continual learning）機制，定期以新的 Pharo 儲存庫更新模型，同時避免災難性遺忘（catastrophic forgetting）。

**8. 人類開發者為中心的評估**

除了自動化準確率指標，未來應進行使用者研究，測量開發者接受率、完成任務時間、認知負荷與滿意度，以全面評估 LLM 補全工具在真實開發流程中的價值。

## 論文問答

**Q1：這篇論文主要想解決什麼問題？**
A：這篇論文聚焦於低資源程式語言（如 Pharo）在基於 LLM 的程式碼補全上面臨的嚴重落後問題。由於 Pharo 在 GitHub 上只有約 2,000 個公開儲存庫，與 Python 等主流語言相差數個數量級，通用程式碼大型語言模型缺乏足夠的訓練資料來學習其語法與慣用語。因此，Pharo 的 IDE 目前僅能提供單一詞元補全，無法像其他語言那樣享受多詞元、具備上下文感知的補全體驗。

**Q2：為什麼現有的通用程式碼 LLMs 在 Pharo 上表現不佳？**
A：現有通用程式碼 LLMs 主要在高資源語言的原始碼語料庫上進行預訓練，對於 Pharo 這類低資源語言的統計規律性學習不足。Pharo 繼承了 Smalltalk 的許多語法特性，例如 `ifTrue:`、`whileTrue:` 等控制流程並非語言關鍵字，而是普通方法，這削弱了從主流語言轉移學習的效果。此外，Pharo 原始碼儲存在 Tonel 格式中，該格式混合了類別後設資料與可執行程式碼，容易使模型混淆並學到無關的雜訊模式。

**Q3：改善 Pharo 的程式碼補全為什麼重要？**
A：這不僅能提升 Pharo 開發者的生產力，也能縮小低資源語言社群與主流語言之間的工具品質差距。透過建立端對端管線與專屬基準測試，本研究為其他低資源程式語言提供了一個可參考的個案研究與實作藍圖。它也證明了即使在訓練資料極度稀缺的情況下，仍然可以透過資料策展與模型特化來實現有效的 IDE 即時支援。

**Q4：作者提出的核心方法是什麼？**
A：作者提出了一個端對端管線，包含 Pharo 專屬資料策展、針對 Pharo 原始碼的持續預訓練，以及針對程式碼補全任務的微調。資料策展階段會處理 Tonel 檔案結構、過濾後設資料並整理出適合訓練的語料。模型方面則選用 Qwen2.5 Coder Base（0.5B、1.5B、3B、7B）與 Mellum-base（4B）等開源程式碼大型語言模型，並進行量化以達到可在本地執行的即時推論速度。

**Q5：這項研究的主要創新點有哪些？**
A：主要創新在於首次系統性地將持續預訓練與微調結合，應用於像 Pharo 這樣極低資源的程式語言，並設計了專屬的 Pharo 程式碼補全基準測試。研究顯示，經過 Pharo 特化的小型模型能夠在 Pharo 補全任務上超越規模顯著更大的通用程式碼 LLMs。此外，本研究也展示了如何處理 Tonel 格式與 Smalltalk 風格語法所帶來的獨特挑戰，這些都是過去主流程式碼補全研究較少觸及的議題。

**Q6：作者在方法設計上做了哪些關鍵選擇？**
A：作者刻意選擇小型開源模型，以便在開發者機器上進行量化後實現真正的即時 IDE 內支援，而非依賴雲端大型模型。訓練策略採用先持續預訓練讓模型熟悉 Pharo 語料，再進行任務導向的微調，以兼顧語言適應與補全準確率。在評估設計上，他們採用遮罩策略：隨機遮罩標準解答或真實提交紀錄中新增的程式碼行，讓模型預測缺失部分，從�而模擬真實開發情境。

**Q7：作者設計了哪些基準測試來評估模型？**
A：他們設計了兩大類互補的 Pharo 程式碼補全基準測試。第一類用於檢驗語法學習能力，包含將 HumanEval+ 翻譯為 Pharo 以及從 Exercism 平台收集的 Pharo 練習題，共 211 道編程任務。第二類則模擬真實開發場景，從 488 個公開 GitHub 儲存庫的提交紀錄中擷取開發者新增的程式碼行並進行遮罩，要求模型補全這些變更內容。

**Q8：實驗的主要結果是什麼？**
A：實驗結果顯示，經過 Pharo 特化的模型在各項基準測試上都顯著優於其原始基礎檢查點。更重要的是，這些小型 Pharo 專用模型的準確率超越了規模顯著更大的通用程式碼大型語言模型，顯示專業化訓練能彌補模型規模的不足。這些提升同時出現在語法正確性測試與真實世界提交紀錄的補全任務上，證明了方法的穩健性。

**Q9：作者是否進行了消融研究或進一步分析？**
A：雖然論文重點在於整體管線的有效性，但從設計可以推論作者比較了基礎模型、持續預訓練後模型以及進一步微調後模型的表現，以驗證每個階段的貢獻。結果通常顯示持續預訓練能幫助模型掌握 Pharo 語法，而微調則進一步提升補全任務的準確率。此外，資料策展（例如處理 Tonel 後設資料與去重）對於避免模型學到雜訊也扮演關鍵角色，這點可從特化模型優於原始檢查點的結果得到支持。

**Q10：這項技術可以應用在哪些實際場景？**
A：最直接的情境是將模型整合進 Pharo IDE，在使用者輸入程式碼時提供多詞元、上下文感知的即時補全建議。它也能協助開發者完成方法實作、修補程式碼變更，或根據現有類別結構推薦下一個可能的運算式。由於模型經過量化後可於本地執行，因此特別適合需要保護原始碼隱私或無法穩定連網的開發環境。

**Q11：在產品化時需要考慮哪些因素？**
A：首要考量是推論延遲必須夠低，才能讓開發者在打字時感受到流暢的即時回饋，因此通常需要對模型進行量化或選擇較小的模型尺寸。其次要在準確率與資源消耗之間取得平衡，因為過度量化可能會犧牲部分補全品質。最後，本地部署雖然能保護專有原始碼並降低雲端成本，但也需要考慮開發者機器的硬體限制與模型更新機制。

**Q12：這項研究對整個領域可能帶來什麼影響？**
A：本研究為低資源程式語言如何導入 LLM 工具提供了一個具體且可複製的範例，可能啟發更多針對小眾語言的專用模型研究。它也挑戰了「模型越大表現越好」的常見假設，證明在特定領域進行資料策展與持續預訓練，能讓小型模型勝過大型通用模型。長遠來看，這有助於縮小不同程式語言社群之間的開發工具差距，促進程式語言生態的多元化。

**Q13：作者承認了哪些限制？**
A：本研究主要是一個針對 Pharo 的個案研究，因此其方法與結論是否能直接推廣到其他低資源程式語言仍需進一步驗證。基準測試雖然涵蓋了語法練習與真實提交紀錄，但仍可能無法完整代表所有 Pharo 函式庫、領域或程式設計慣例。此外，評估時採用的遮罩方式雖然能模擬補全情境，但與實際 IDE 中開發者游標所在位置及意圖仍可能存在差異。

**Q14：模型可能會在哪些情況下失敗？**
A：當遇到罕見的類別庫 API、複雜的訊息傳遞鏈，或需要深度理解領域知識的程式碼時，模型仍可能產生錯誤的選擇器或無效的 Smalltalk 語法。Tonel 檔案中的後設資料若未被妥善隔離，也可能導致模型在補全時混入不該出現的類別定義資訊。此外，極小型的量化模型由於容量有限，可能在需要長距離上下文推理的任務上表現較差。

**Q15：未來可以朝哪些方向延伸？**
A：未來可以將 Pharo 專用模型直接整合進 Pharo IDE，並透過使用者研究評估實際開發效率與滿意度。也可以探索合成資料增強、跨 Smalltalk 方言轉移學習，以及結合檢索增強生成（RAG）來進一步提升對罕見 API 的補全能力。最後，將這套端對端管線應用到其他低資源程式語言，並比較不同資料策展策略的效果，將是極具價值的後續研究方向。

## 實務應用指南

### 適用場景

1. **低資源程式語言的 IDE 智慧補全**  
   當目標語言（如 Pharo、Racket、Factor 等）在公開儲存庫中的資料量遠低於 Python / JavaScript 時，可參考本研究建立「資料策展 → 持續預訓練 → 微調 → 量化部署」的端對端管線，為該語言提供多詞元、上下文感知的程式碼補全。

2. **企業內部 DSL（領域特定語言）的開發輔助**  
   公司內部自訂語言或框架通常缺乏公開語料，導致通用程式碼大型語言模型（Code LLMs）表現不佳。可蒐集內部原始碼語料庫，對小型開源模型進行持續預訓練與微調，打造符合內部編碼規範的補全工具。

3. **程式語言教學與練習平台**  
   將 Exercism、LeetCode 等平台的習題轉換為目標語言的遮罩程式碼基準測試，用於評估學習者模型是否掌握語法，並在教學 IDE 中提供即時補全與提示。

4. **遺留系統現代化（Legacy Modernization）**  
   針對 Smalltalk / Pharo 等維護中的遺留系統，利用真實世界 GitHub 儲存庫的 commit 建立「補全程式碼變更」任務，協助開發者在重構或新增功能時獲得符合專案風格的建議。

5. **邊緣裝置或本地開發環境的輕量補全**  
   由於最終模型可量化至數十億參數以下（如 0.5B–7B），適合部署於開發者筆電或私有伺服器，滿足對延遲敏感、無法連網或資料不外流的 IDE 即時支援需求。

### 實作前置條件

**資料條件**
- 目標語言的原始碼語料庫：建議至少數千至數萬個檔案，來源可為 GitHub 公開儲存庫、官方套件、文件與教學範例。
- 資料清理能力：需能辨識並過濾非執行內容。以 Pharo 為例，Tonel 檔案混雜類別後設資料（`#name`、`#superclass`、`#category` 等），必須與方法本體分離，避免模型學到虛假規律。
- 評估資料：至少 100 個以上的語法測試題（如 HumanEval+ 翻譯版）與數百筆真實 commit 變更，用於建立遮罩程式碼基準測試。

**運算條件**
- 持續預訓練：建議具備 1–4 張 NVIDIA A100 / H100 等級 GPU，或同等 VRAM 的雲端實例（如 AWS p4d、Lambda Cloud）。
- 微調：可在單張 24GB–48GB VRAM GPU 上完成 1.5B–7B 模型的 LoRA / QLoRA 微調。
- 推論：量化後（INT4 / INT8）的 0.5B–3B 模型可在消費級 GPU 或 Apple Silicon 上達到即時下一詞元建議。

**技能條件**
- 熟悉目標語言語法與生態（例如 Pharo / Smalltalk 的方法定義、區塊語法、控制流程即訊息傳遞等特性）。
- 具備大型語言模型預訓練與微調經驗，能操作 Hugging Face Transformers、TRL、DeepSpeed / FSDP、vLLM / llama.cpp 等工具。
- 具備資料工程能力，能撰寫 parser 或正規表示式進行資料策展，並建立可重現的資料處理管線。

### 實作步驟建議

1. **語料蒐集與資料策展**
   - 從 GitHub 儲存庫、套件管理器與官方範例蒐集原始碼。
   - 針對特殊檔案格式（如 Tonel）進行結構化解析，移除後設資料、註解與重複片段，保留可執行的方法與類別定義。
   - 進行去重、品質過濾（例如排除過短或無法解析的檔案），並將資料切分為持續預訓練集與微調集。

2. **建立評估基準測試**
   - **語法學習基準**：將 HumanEval+ 等通用程式設計題目翻譯為目標語言，並保留測試案例；隨機遮罩 canonical solution 的部分程式碼，讓模型預測後執行測試驗證正確性。
   - **真實場景基準**：蒐集公開儲存庫的 commit，找出開發者新增的程式碼行，將其遮罩後作為補全目標，模擬實際開發情境。

3. **選擇基礎模型**
   - 優先選用開源程式碼大型語言模型，如 Qwen2.5 Coder Base（0.5B–7B）或 Mellum-base（4B），這類模型已在大量原始碼上預訓練，具備良好的遷移學習起點。

4. **持續預訓練**
   - 使用目標語言語料對基礎模型進行持續預訓練（Continued Pre-training），學習該語言的詞彙、語法與慣用語。
   - 建議採用較長上下文長度，並監控 perplexity 與語法基準測試的通過率，避免過度擬合或災難性遺忘。

5. **監督式微調**
   - 以「遮罩程式碼 → 補全」格式建立指令資料集，對持續預訓練後的模型進行微調。
   - 可採用 LoRA / QLoRA 降低記憶體需求，並調整學習率、批次大小與遮罩比例，使模型專注於真實補全場景。

6. **量化與 IDE 部署**
   - 將微調後的模型量化為 INT4 / INT8，使用 llama.cpp、vLLM 或 ONNX Runtime 等推論引擎整合至 IDE 外掛。
   - 設計補全觸發機制（如延遲 50–200 ms、只在語句邊界或空白處觸發），確保使用者感受到「即時」回應。

7. **持續監控與迭代**
   - 在真實使用者環境中收集 accepted / rejected 比例、延遲與錯誤案例。
   - 定期將新釋出的高品質儲存庫納入語料，重新進行微調或持續預訓練，保持模型與語言生態同步。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **資料格式混淆** | 特殊檔案格式（如 Tonel）混雜後設資料與程式碼，模型可能學到非執行內容的虛假規律。 | 建立專屬 parser，在資料策展階段分離後設資料、註解與可執行程式碼。 |
| **語法差異導致遷移學習困難** | Pharo / Smalltalk 的控制流程為訊息傳遞，與 C-like 語言差異大，通用模型難以直接遷移。 | 透過持續預訓練讓模型大量接觸目標語言語法，並輔以語法基準測試監控學習成效。 |
| **資料稀缺與過度擬合** | 低資源語言的語料有限，模型可能記憶訓練集而非學習泛化。 | 使用資料增強、正則化、較小模型，並以真實 commit 基準測試評估泛化能力。 |
| **延遲與硬體限制** | 未量化的模型在消費級硬體上推論過慢，無法達到 IDE 即時支援。 | 採用量化、推論引擎優化、快取與選擇性觸發策略，必要時使用更小模型。 |
| **授權與資料隱私** | 公開儲存庫授權不一，企業內部語料可能涉及敏感資訊。 | 清理授權不符的檔案；企業場景使用私有語料與本地部署，避免資料外洩。 |
| **評估指標與使用者體驗脫節** | 高準確率不一定代表補全建議對開發者有用。 | 除了基準測試，應進行使用者研究或 A/B 測試，收集 accepted completion 比例與主觀滿意度。 |

### 與其他技術的整合建議

- **與現有 IDE 單一詞元補全整合**  
  可將 LLM 多詞元補全作為「進階建議」，與傳統單一詞元補全並存：當使用者輸入特定前綴或停頓時，才呼叫 LLM；簡單情境仍使用既有快速補全，降低運算成本。

- **與 Language Server Protocol（LSP）結合**  
  將模型包裝為 LSP 的 `textDocument/completion` provider，使補全服務可跨 IDE（VS Code、Emacs、Vim、Pharo 自帶 IDE）使用，並利用 LSP 的語義資訊過濾明顯錯誤的建議。

- **與檢索增強生成（RAG）搭配**  
  對於大型專案，可將專案內的類別、方法與註解建立向量索引，在補全時檢索相關上下文並與模型輸入拼接，提升跨檔案與專案特定慣用語的準確率。

- **與靜態分析 / 型別檢查器協同**  
  在模型產生建議後，利用目標語言的編譯器或靜態分析工具進行後置過濾，剔除語法錯誤或型別不符的補全結果，並將錯誤回饋納入微調資料。

- **與持續整合（CI）管線連動**  
  將語法基準測試與真實 commit 基準測試納入 CI，每次更新模型或資料集時自動執行回歸測試，確保補全品質不隨版本迭代下降。

本研究提供了一個可複製的低資源語言補全範本，建議重點閱讀資料策展細節、遮罩程式碼基準測試的設計，以及 Qwen2.5 Coder / Mellum 的模型選型與量化策略。實作時請特別注意持續預訓練與微調的資料比例、學習率調度，並將語法正確性測試與 perplexity 同時納入 early stopping 依據。

**研究人員**  
論文的核心貢獻在於展示「小模型 + 領域特化」能超越大模型在低資源語言上的表現。建議關注基準測試的建構方法論、遮罩策略對評估效度的影響，以及從 HumanEval+ 翻譯到 Pharo 時的語義等價性問題。未來可延伸探討跨語言遷移學習、合成資料生成或 RAG 對低資源語言的增益。

**產品經理**  
請將本研究視為「為小眾語言打造商業化補全功能」的可行性驗證。重點評估目標語言社群規模、可取得的訓練資料量、部署硬體成本與使用者對延遲的容忍度。論文證明使用 0.5B–7B 量化模型即可達到即時 IDE 內支援，這對制定最小可行產品（MVP）與定價策略具有直接參考價值。
