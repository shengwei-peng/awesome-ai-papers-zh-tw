## 摘要翻譯

大型語言模型（Large Language Model, LLM）日益應用於網路安全工作流程，人們預期它們能將分析師意圖轉譯為工具呼叫（tool invocation）。然而，現有評估多聚焦於知識型評估（knowledge-based assessment）或端對端智能體任務（end-to-end agentic task），並未直接衡量 LLM 為真實世界網路安全工具生成可執行命令（executable command）的能力。此一落差至關重要，因為網路安全作業仰賴嚴格的命令列介面（Command-Line Interface, CLI），其中微小的語法錯誤（syntax error）、不正確的旗標–數值綁定（flag-value binding）或引數順序錯誤（argument misordering）都可能導致無效執行（invalid execution）。我們提出 KaliBench，一個用於 Kali Linux 上自然語言轉命令列介面翻譯（natural-language-to-CLI translation）的細粒度基準測試（fine-grained benchmark）與資料集（dataset），包含 8,504 筆查詢–命令配對（query-command pair），涵蓋 1,642 個工具，橫跨 23 個能力維度（capability dimension）與 5 個安全階段（security phase）。KaliBench 透過基於手冊文件的管線（manuscript-grounded pipeline）建構，結合確定性正規化（deterministic canonicalization）與別名感知評估（alias-aware evaluation），實現對工具選擇（tool selection）與引數建構（argument construction）的精確且可重現評估。為確保語意正確性與實際可執行性，我們開發了一個多階段驗證管線（multi-stage verification pipeline），結合基於 LLM 的驗證（LLM-based validation）、沙箱化終端機執行（sandboxed terminal execution）與人在迴路精煉（human-in-the-loop refinement）。基於這些細粒度、確定性訊號（deterministic signal），KaliBench 進一步實現用於訓練的無執行期可驗證獎勵（runtime-free verifiable reward）。橫跨三種評估模式（evaluation mode）與 24 種通用型與安全導向型開放權重模型組態（configuration），在無限制設定（unrestricted setting）下，沒有任何開放權重模型（open-weight model）的精確命令準確率（exact-command accuracy）超過 42%，凸顯在缺乏明確工具提示（tool hint）時，準確使用以 CLI 為基礎的網路安全工具相當困難。我們進一步顯示，以源自 KaliBench 的可驗證獎勵進行監督式微調（Supervised Fine-Tuning, SFT）與強化學習（Reinforcement Learning, RL），可顯著提升 8B 模型（8B model）的效能，並達到與 685B 混合專家模型（Mixture-of-Experts, MoE）相當的表現。

### 核心貢獻（3～5點）
- 提出 KaliBench：首個針對 Kali Linux 上真實世界網路安全工具使用的大規模細粒度基準測試與資料集，包含 8,504 筆查詢–命令配對，涵蓋 1,642 個工具、23 個能力維度與 5 個安全階段。
- 設計基於手冊文件的建構管線：透過確定性正規化與別名感知評估，精確且可重現地評估工具選擇與引數建構。
- 開發多階段驗證管線：結合 LLM 驗證、沙箱化終端機執行與人在迴路精煉，確保命令的語意正確性與實際可執行性。
- 提供無執行期可驗證獎勵：將細粒度、確定性訊號轉化為可用於監督式微調與強化學習的訓練獎勵。
- 揭示開放權重模型的能力缺口與改進潛力：在無限制設定下，現有開放權重模型的精確命令準確率均未超過 42%，但透過 SFT 與 RL 可顯著提升 8B 模型效能至接近 685B MoE 模型水準。

### 適合對象
適合對 LLM 工具使用、網路安全自動化、命令列介面生成與可驗證獎勵訓練感興趣的研究人員與工程師，特別是從事網路安全智能體、開放權重模型後訓練（post-training）以及細粒度基準測試設計的學術與產業界人士。

## 深度分析

#### 方法論解析

##### 任務定位：從自然語言到可執行 CLI 的細粒度翻譯

KaliBench 將核心任務定義為 **Natural-Language-to-CLI（NL-to-CLI，自然語言轉命令列介面）翻譯**：給定分析師請求（analyst request），模型必須輸出可在 Kali Linux（Kali Linux，滲透測試用 Linux 發行版）上實際執行的精確命令（exact CLI command）。這與傳統 **schema-based function call（基於綱要的函式呼叫）** 不同——後者會把每個工具的參數以 JSON 綱要（schema）預先寫入提示，模型只需填欄位；而 KaliBench 屬於 **schema-free（無綱要）** 設定，模型必須自行推斷適當工具、旗標（flag）與引數（argument），並產生語法正確、語義等價且可執行的命令列字串。

##### 資料建構管線：以手冊文件為基礎

資料集透過 **manuscript-grounded pipeline（基於手冊文件的管線）** 建立，總計 8,504 組 query-command pairs（查詢-命令配對），涵蓋 1,642 個工具、23 個 capability dimensions（能力維度）與 5 個 security phases（安全階段）。其設計邏輯是讓每條命令都根植於真實工具文件（manual page / 手冊文件），降低幻覺風險，並確保命令與 Kali Linux 實際套件對應。相較於僅從網頁或論壇爬蟲取得的命令範例，這種做法在工具名稱、旗標語義與預設行為上更具可控性。

##### 確定性正規化與別名感知評估

為了讓評估可重現且細粒度，KaliBench 引入兩項關鍵機制：

1. **Deterministic canonicalization（確定性正規化）**：將模型生成的命令轉換為標準形式，統一處理等價語法（例如長短選項、引數順序、多餘空白、預設值省略）。這使得評分不依賴表面字串，而是比較語義結構。
2. **Alias-aware evaluation（別名感知評估）**：接受工具的合法別名（alias）與等價旗標組合，避免將正確但非預設寫法的命令誤判為錯誤。

透過這兩項機制，評估可同時檢驗 **tool selection（工具選擇）** 與 **argument construction（引數建構）** 兩個子能力，並產生 **fine-grained（細粒度）** 的錯誤診斷。

##### 多階段驗證管線

為了兼顧語義正確性與實際可執行性，KaliBench 採用 **multi-stage verification pipeline（多階段驗證管線）**：

- **LLM-based validation（基於 LLM 的驗證）**：初步檢查命令與查詢意圖是否一致。
- **Sandboxed terminal execution（沙箱化終端機執行）**：在隔離環境中實際執行命令，觀察 exit code（結束代碼）、stderr（標準錯誤輸出）與輸出結果，確認無語法錯誤（syntax errors）。
- **Human-in-the-loop refinement（人在迴路精煉）**：對 LLM 與沙箱無法自動判定邊界案例進行人工審核，提升資料品質。

這三步驟確保資料集中的每條命令都是 **executable commands（可執行命令）**，並且與對應的分析師意圖（analysts' intent）相符。

##### 無執行期可驗證獎勵與訓練應用

KaliBench 的另一項核心貢獻是將上述細粒度、確定性訊號（deterministic signals）轉化為 **runtime-free verifiable rewards（無執行期可驗證獎勵）**。由於正規化後的命令可以與標準答案進行結構化比對，因此無需每次都在沙箱中執行即可給出可靠獎勵。這使得研究者能夠進行：

- **Supervised Fine-Tuning（SFT，監督式微調）**：利用高品質 query-command pairs 直接微調模型。
- **Reinforcement Learning with Verifiable Rewards（RLVR，強化學習與可驗證獎勵）**：以確定性獎勵函數進行策略最佳化，避免傳統 RL 在網路安全環境中執行命令所帶來的成本與風險。

##### 三種評估設定

KaliBench 設計了三種評估模式，以區隔模型在不同資訊條件下的能力：

- **Unrestricted setting（無限制設定）**：模型自由選擇工具與引數，最貼近真實部署情境，也最困難。
- **Restricted setting（受限設定）**：可能限制可選工具範圍，用於檢驗引數建構能力。
- **Hinted setting（提示設定）**：提供 tool hints（工具提示），用於區分工具選擇錯誤與引數建構錯誤。

這種分層設計讓研究者能夠精確定位模型失敗來源：是選錯工具，還是選對工具但旗標-數值綁定（flag-value bindings）或引數順序錯誤（argument misordering）。

#### 實驗數據解讀

##### 整體表現：開放權重模型仍面臨重大挑戰

研究評估了 24 組 general-purpose models（通用模型）與 security-focused models（安全導向模型）的 open-weight models（開放權重模型）。在 **unrestricted setting** 下，沒有任何開放權重模型的 **exact-command accuracy（精確命令準確率）** 超過 42%。這個數字凸顯了 NL-to-CLI 翻譯在網路安全領域的困難：即使模型具備廣泛知識，要產生完全正確、可執行的命令仍然極具挑戰。

##### 引數建構是主要瓶頸

從三種評估模式的對比可以推論，當提供 tool hints 後模型表現通常會提升，這表示 **tool selection（工具選擇）** 相對較容易，而真正的瓶頸在於 **argument construction（引數建構）**。常見錯誤包括：

- 錯誤的 flag-value bindings（旗標-數值綁定）
- argument misordering（引數順序錯誤）
- 遺漏必要選項或誤用預設值
- 對工具語義理解不足導致的引數型態錯誤

這與一般 function calling 基準測試中「只要選對工具、填對欄位即可」的狀況形成鮮明對比；在 CLI 環境中，引數的語法細節會直接決定命令是否可執行。

##### SFT 與 RLVR 的顯著增益

實驗進一步展示，對一個 8B model（80 億參數模型）進行 SFT 與 RLVR 後，其表現可逼近甚至媲美 685B MoE model（6850 億參數混合專家模型）。這項結果具有兩層意義：

1. **資料效率與獎勵品質**：KaliBench 提供的 runtime-free verifiable rewards 品質足夠高，能夠在相對小的模型上透過 RL 獲得顯著提升。
2. **細粒度監督訊號的價值**：相較於單純的 end-to-end 獎勵，針對 tool selection 與 argument construction 的結構化獎勵更能引導模型學習正確的 CLI 語法。

##### 對模型選型的啟示

實驗涵蓋多種模型尺寸與安全專精程度，結果顯示單純放大參數量並不能自動解決 CLI 工具使用問題；相反地，針對性微調與可驗證獎勵所帶來的效益可能更為顯著。這對於資源有限但希望部署網路安全助手的團隊而言，是一個重要訊號。

#### 與現有研究的比較

##### 相較於知識型評估

早期網路安全基準測試多為 **knowledge-based assessments（知識型評估）**，例如多選題或結構化問答 [36, 19, 14, 3]。這類評測能檢驗模型「知道什麼」，但無法檢驗模型「能否產生可執行命令」。KaliBench 填補了這個缺口：它直接測量 LLM 將高層意圖轉換為具體 tool invocation（工具呼叫）的能力。

##### 相較於端對端智能體任務

近年來出現許多 **end-to-end agentic tasks（端對端智能體任務）** 基準，例如讓模型自主解決 CTF 挑戰 [32, 45]。這類任務雖然貼近真實工作流程，但獎勵訊號稀疏且難以診斷：模型可能因為某個中間命令錯誤而整題失敗，研究者難以判斷問題出在工具選擇、引數建構還是後續推理。KaliBench 採用隔離的 query-command pairs，提供 **fine-grained evaluation（細粒度評估）**，能夠精確定位錯誤環節。

##### 相較於函式呼叫基準測試

現有 function-calling benchmarks [17, 10, 21, 20, 28] 大多假設工具以 JSON schema 描述，模型只需產生結構化函式呼叫。然而，真實 Kali Linux 工具生態超過 2,000 個套件 [31]，不可能在提示中窮舉所有 schema。KaliBench 因此採用 **schema-free** 設定，要求模型在無明確綱要的情況下推斷工具與引數，這更貼近實際安全分析師的使用情境。

##### 主要改進與貢獻

- **大規模且 grounded 的資料**：8,504 組配對、1,642 個工具，並以手冊文件為基礎。
- **確定性且可重現的評估**：透過 canonicalization 與 alias-aware evaluation 減少表面字串變異造成的誤判。
- **無執行期獎勵**：將評估訊號轉化為訓練用 reward，支援 SFT 與 RLVR。
- **多模式評估**：unrestricted、restricted、hinted 三種設定區隔不同能力。

##### 限制與待釐清之處

- **靜態單輪任務**：目前每筆資料為獨立的 query-command pair，尚未涵蓋多輪互動、狀態追蹤與觀察回饋。
- **平台侷限**：僅針對 Kali Linux，未涵蓋其他 Linux 發行版或專有安全工具。
- **開放權重模型為主**：未報告主流 closed-weight API 模型（如 GPT-4、Claude 等）的表現，難以全面評估當前最強模型的能力上限。
- **執行期語義的近似**：runtime-free rewards 雖然高效，但可能無法完全捕捉命令在動態環境中的副作用（例如網路狀態、檔案系統變化）。
- **安全性與濫用風險**：作為網路安全工具命令生成資料集，其潛在濫用風險與安全對齊機制未在摘要中詳細討論。

#### 可重現性評估

##### 開放資源與透明度

根據論文提供的資訊，KaliBench 已釋出：

- **Project page（專案頁面）**：https://risys-lab.github.io/KaliBench/
- **GitHub**：https://github.com/RISys-Lab/KaliBench

這些資源通常會包含資料集、評估腳本、canonicalization 規則與實驗設定，對於重現結果至關重要。

##### 資料集與評估腳本

由於 KaliBench 強調 **deterministic canonicalization** 與 **alias-aware evaluation**，評估的可重現性高度依賴：

1. 標準答案的 canonical form（正規化形式）是否公開。
2. 別名對照表與等價語法規則是否完整。
3. 沙箱執行環境（例如 Docker、VM）的具體配置。

若上述內容均隨程式碼釋出，則其他研究者可以在相同環境下複製 exact-command accuracy 與細粒度指標。

##### 模型權重與訓練細節

論文提到對 8B model 進行 SFT 與 RLVR 後取得顯著進步，但摘要中未明確說明微調後的模型權重是否公開。若作者釋出微調後的 checkpoint，將大幅提升後續研究的可比較性；若未釋出，則其他團隊需要自行準備運算資源復現訓練流程。

##### 環境相依性

KaliBench 的驗證涉及 **sandboxed terminal execution**，因此重現時需要準備與論文一致的 Kali Linux 版本與工具套件版本。工具版本差異可能導致旗標行為不同，進而影響 canonicalization 與執行結果，這是未來維護資料集時需要持續追蹤的議題。

#### 未來研究方向

##### 多輪互動與狀態感知

目前的 KaliBench 聚焦單輪 query-to-command 翻譯。未來可擴展為多輪 **agentic tasks（智能體任務）**，讓模型根據前一步執行結果（stdout、stderr、exit code）調整後續命令。這將更貼近真實滲透測試與事件回應流程。

##### 動態環境與真實執行回饋

雖然 runtime-free rewards 提升了訓練效率，但動態環境中的副作用（如網路掃描結果、服務狀態變化）難以完全用靜態獎勵捕捉。未來可結合輕量沙箱執行與 runtime-free 訊號，設計混合式獎勵機制。

##### 檢索增強生成（RAG）與工具文件

由於 Kali Linux 工具眾多，未來可研究如何將 **manuscript-grounded pipeline** 與 retrieval-augmented generation（RAG）結合，讓模型在生成命令時動態檢索相關手冊文件，提升對冷門工具的處理能力。

##### 跨平台與多語言擴展

KaliBench 目前以 Kali Linux 與英文查詢為主。未來可擴展至其他滲透測試平台（如 Parrot OS、BlackArch）以及多語言分析師請求，評估模型在不同語言與文化脈絡下的 CLI 生成能力。

##### 多模態輸入

真實安全分析常涉及日誌檔案、封包擷取、記憶體傾印等。未來可將 KaliBench 擴展為多模態基準，要求模型根據原始資料（而非僅自然語言描述）產生適當命令。

##### 安全對齊與濫用防範

隨著模型越能精確生成網路安全命令，其潛在濫用風險也隨之增加。未來研究應探討如何在提升工具使用能力的同時，加入安全對齊機制，避免模型被用於未授權攻擊。

##### 獎勵設計與強化學習擴展

KaliBench 已展示 RLVR 的潛力，但未來可進一步探索：

- 更細緻的 reward shaping（獎勵塑形），例如針對部分正確的引數給予漸進獎勵。
- 結合過程獎勵（process reward）與結果獎勵（outcome reward）。
- 將 runtime-free verifiable rewards 應用於更大規模模型與更長上下文。

##### 工具版本漂移與線上適應

Kali Linux 工具持續更新，旗標與預設行為可能改變。未來可研究如何讓模型或基準測試自動適應工具版本變化，例如透過持續整合（CI）自動重新執行沙箱驗證並更新 canonical form。

## 論文問答

**Q1：KaliBench 旨在解決什麼核心問題？**

A：KaliBench 旨在填補現有評估方法無法直接衡量大型語言模型（LLM）為真實世界網路安全工具生成可執行命令之能力的研究缺口。現有基準測試多聚焦於知識型選擇題或端對端智能體任務，卻未檢驗模型是否能正確呼叫 Nmap、Metasploit 等具體工具的命令列介面（CLI）。由於網路安全作業極度依賴嚴格的 CLI，微小的語法錯誤或引數錯置都可能導致整個操作失效，因此精確命令生成能力是部署 LLM 助理的關鍵前提。

**Q2：為何現有的函式呼叫基準測試無法充分評估網路安全工具使用？**

A：現有函式呼叫基準通常假設工具具有明確的 JSON 綱要（schema），模型只需填入指定欄位即可完成呼叫。然而 Kali Linux 擁有超過兩千個預裝的安全工具，在實際部署中不可能將所有工具綱要都納入模型提示的上下文長度內。因此，網路安全領域的自然語言轉命令列介面翻譯本質上是無綱要（schema-free）的，模型必須自行推斷適當工具並建構語法正確的引數，這遠比填充結構化欄位困難。

**Q3：為何在網路安全領域生成精確 CLI 命令特別重要？**

A：網路安全作業高度依賴嚴格的命令列介面，旗標-數值綁定錯誤、引數順序錯誤或別名誤用都可能使命令完全無效或產生誤導性結果。與具備清楚錯誤處理機制的 API 不同，CLI 工具往往對語法錯誤非常嚴苛，甚至可能靜默失敗。因此，模型能否將分析師意圖翻譯為精確且可執行的命令，直接決定了 LLM 在真實安全營運場景中的可靠性。

**Q4：KaliBench 的核心建構方法是什麼？**

A：KaliBench 透過基於手冊文件的管線建構，收錄 8,504 組查詢-命令配對，涵蓋 1,642 個工具、23 個能力維度與 5 個安全階段。該管線採用確定性正規化將命令轉為標準形式，並透過別名感知評估辨識合法命令變體。為確保資料品質，研究團隊設計了結合基於 LLM 的驗證、沙箱化終端機執行與人在迴路精煉的多階段驗證管線，以同時保證語義正確性與實際可執行性。

**Q5：相較於既有基準，KaliBench 的關鍵創新為何？**

A：KaliBench 首次針對網路安全工具提出細粒度且無綱要的自然語言轉命令列介面翻譯評估，並將評估拆解為工具選擇與引數建構兩個層面。其最突出的創新在於提出無執行期可驗證獎勵（runtime-free verifiable rewards），可在不實際執行命令的情況下提供確定性訓練訊號。這項設計不僅提升訓練效率，也讓強化學習能在安全、可複現的環境中進行網路安全工具使用的最佳化。

**Q6：KaliBench 為何設計無限制、受限與提示三種評估設定？**

A：三種設定用於系統性地分析模型在不同工具資訊暴露程度下的表現。無限制設定要求模型獨立完成工具選擇與完整引數建構，而受限與提示設定則逐步提供工具名稱等資訊，以隔離特定失敗模式。這種設計能夠區分模型錯誤是來自工具選擇、引數建構，還是兩者皆有，從而為後續模型改進提供明確方向。

**Q7：論文的主要實驗發現是什麼？**

A：在 24 種通用模型與安全導向開放權重模型的設定下，沒有任何模型在無限制設定中達到超過 42% 的精確命令準確率，顯示此任務具有相當高的難度。進一步分析指出，引數建構是主要瓶頸，而非工具選擇。這些結果凸顯了當前開放權重模型在缺乏明確工具提示時，仍難以可靠地生成正確的網路安全 CLI 命令。

**Q8：監督式微調與強化學習搭配可驗證獎勵的效果如何？**

A：研究顯示，以 KaliBench 衍生的可驗證獎勵進行監督式微調（SFT）與強化學習（RLVR），能顯著提升 8B 模型的表現。經過訓練的 8B 模型甚至達到與 685B MoE 模型相當的效能，顯示細粒度確定性獎勵對於命令生成任務具有強大的訓練效益。這也說明透過針對性訓練，中小型模型有機會在網路安全工具使用上逼近大型混合專家模型的水準。

**Q9：無限制與提示設定之間的表現差距揭示了什麼模型限制？**

A：兩種設定間的準確率差距顯示，模型最大的困難在於必須獨立推斷正確工具並建構完整引數結構。一旦提供明確的工具提示，模型表現便顯著提升，這意味著現有模型對工具功能具備一定知識，但在命令語法的精確建構上仍顯不足。此發現指引未來研究應優先強化引數層級的生成能力，而非僅僅改善工具辨識。

**Q10：KaliBench 的主要實際應用場景有哪些？**

A：KaliBench 可用於驅動協助分析師將自然語言請求轉譯為可執行 Kali Linux 命令的 LLM 安全助理。它也能支援訓練自主網路安全智能體，執行滲透測試、弱點掃描與數位鑑識等工作流程。此外，KaliBench 提供了一個標準化的比較框架，讓研究人員與開發者能客觀評估不同模型在網路安全命令生成任務上的能力。

**Q11：開發者在部署基於 KaliBench 訓練的模型時應考慮哪些產品議題？**

A：開發者必須確保模型生成的命令在實際執行前經過沙箱化驗證，以避免對生產環境造成意外損害或未經授權的存取。同時應設計驗證失敗時的備援機制，並審慎評估自動化攻擊性安全工具所帶來的風險。產品介面也應清楚區分「建議命令」與「已執行動作」，並在高風險操作中保留人類監督。

**Q12：KaliBench 可能對網路安全與人工智慧研究領域產生什麼影響？**

A：KaliBench 建立了首個針對網路安全 CLI 工具使用的細粒度且可複現的基準測試，為研究社群提供了共同的評估標準。透過無執行期可驗證獎勵，它開啟了以強化學習訓練專業安全模型的新途徑。此基準也縮短了概念性網路安全知識與實務工具操作能力之間的落差，推動領域朝向更可靠、可部署的 AI 安全助理發展。

**Q13：論文承認或暗示了 KaliBench 的哪些限制？**

A：KaliBench 目前涵蓋 1,642 個工具，僅佔 Kali Linux 兩千多個預裝工具的一部分，覆蓋範圍仍有擴充空間。多階段驗證管線雖然嚴謹，但部分依賴基於 LLM 的驗證與人工精煉，可能在大規模擴展時面臨成本與一致性的挑戰。此外，無執行期獎勵雖然安全高效，但可能無法完整捕捉所有依賴執行環境的行為，例如與時間或網路狀態相關的命令效應。

**Q14：模型在 KaliBench 上的典型失敗案例有哪些？**

A：模型常見的失敗包括生成錯誤的旗標-數值綁定、引數順序錯誤，或使用不符合正規語法的無效別名。在無限制設定中，模型有時會選擇不適合描述任務的工具，顯示工具選擇仍有進步空間。另一種常見模式是模型產生語義上合理但語法上無效的命令，這凸顯了 CLI 工具呼叫對精確度的高度要求。

**Q15：基於 KaliBench 有哪些值得探索的未來研究方向？**

A：未來研究可擴充 KaliBench 以涵蓋更多 Kali Linux 工具，並加入多輪對話場景，讓分析師能根據中間輸出逐步修正請求。研究者也可將 KaliBench 與真實智能體環境整合，在更貼近實務的網路安全工作流程中評估命令執行效果。另一個方向是發展結合無執行期驗證與輕量執行回饋的混合獎勵模型，以更好地處理依賴執行環境的命令。

## 實務應用指南

### 適用場景

1. **資安分析師的智慧命令助理**  
   將 KaliBench 的查詢-命令配對與驗證機制整合到 SOC 或滲透測試團隊的內部助理中，讓分析師用自然語言描述任務（例如「對 192.168.1.0/24 執行 SMB 列舉掃描」），模型直接輸出可執行的 Kali Linux 精確命令，減少手動查閱手冊文件的時間。

2. **資安工具呼叫的模型訓練與微調**  
   利用 KaliBench 提供的無執行期可驗證獎勵（runtime-free verifiable rewards），對開放權重模型進行監督式微調（SFT）與強化學習（RLVR），打造專精於網路安全命令列介面（CLI）的工具使用模型，特別適合需要在本機或私有環境部署的場景。

3. **自動化滲透測試腳本生成**  
   結合 KaliBench 的細粒度評估維度（工具選擇、引數建構、別名處理），建立從任務意圖到多階段攻擊鏈命令的自動生成流程，用於紅隊演練、CTF 訓練或安全驗證劇本（playbook）的快速原型開發。

4. **資安教育與認證輔助教材**  
   將資料集轉換為互動式練習題，讓學習者比對自己輸入的命令與 KaliBench 經正規化、沙箱驗證的標準答案，強化對 Nmap、Metasploit、Volatility 等真實工具的語法與語意理解。

5. **LLM 資安能力評測與選型**  
   企業在導入安全導向模型或通用模型前，可使用 KaliBench 的三種評估模式（unrestricted / restricted / hinted）與別名感知評估，客觀比較不同模型在無綱要（schema-free）CLI 生成上的精確命令準確率。

### 實作前置條件

- **資料準備**：取得 KaliBench 資料集（可透過專案頁面或 GitHub 下載），並熟悉其查詢-命令配對格式、正規化規則與 23 個能力維度的標籤。若需自行擴充，需準備對應工具的手冊文件（man pages）作為生成基礎。
- **運算資源**：  
  - 推論評測：至少具備可執行 8B–70B 開放權重模型的 GPU（如 A100 / H100 或同等級），記憶體需容納模型與 Kali Linux 沙箱環境。  
  - 訓練：進行 SFT 與 RLVR 時，建議使用多卡叢集；若僅做小規模微調，8B 模型可在單張 80GB GPU 上進行 LoRA 實驗。
- **環境與工具**：部署 Kali Linux 容器或虛擬機作為沙箱執行環境，安裝資料集中涉及的 1,642 個工具套件，並確保網路隔離以避免誤觸真實目標。
- **技能需求**：團隊需具備 Python、PyTorch / Transformers、命令列工具使用經驗，以及基礎網路安全知識（掃描、列舉、漏洞利用、鑑識等階段）。若進行 RLVR，需熟悉強化學習框架（如 TRL、OpenRLHF）與獎勵函式設計。

### 實作步驟建議

1. **建立評估基線**  
   在 KaliBench 的三種模式下，對目標模型進行零樣本（zero-shot）推論，記錄精確命令準確率、工具選擇正確率與引數建構錯誤分佈，找出主要瓶頸。

2. **資料清洗與領域對齊**  
   依據自身場景篩選資料集（例如只保留掃描與列舉階段），並使用 KaliBench 的確定性正規化與別名感知評估腳本，將模型輸出轉為標準形式後再比對，避免別名或引數順序造成誤判。

3. **監督式微調（SFT）**  
   以 KaliBench 的查詢-命令配對作為訓練資料，對 8B 等中小型模型進行全參數或 LoRA 微調，重點學習工具名稱、旗標-數值綁定與引數順序。

4. **強化學習與可驗證獎勵（RLVR）**  
   將 KaliBench 的細粒度評估訊號轉為獎勵函式：命令完全正確給予高獎勵、工具正確但引數錯誤給予部分獎勵、語法錯誤給予負獎勵。透過無執行期獎勵進行 RLVR，避免每次訓練都啟動沙箱。

5. **沙箱驗證與人在迴路精煉**  
   對訓練後模型產生的命令，定期抽樣於 Kali Linux 沙箱中執行，檢查結束代碼、標準錯誤輸出與語意正確性，並將錯誤案例回饋至資料集進行迭代精煉。

6. **產品化部署**  
   將模型包裝為 API 或 VS Code / 終端機外掛，並在前端加入「工具提示」開關：當使用者開啟提示時，模型可獲得工具名稱等額外資訊以提升準確率；關閉時則考驗模型真實能力。

### 潛在風險與注意事項

- **命令誤執行風險**：模型可能產生刪除資料、對外掃描或利用漏洞的命令。務必在隔離沙箱中驗證，並在產品介面加入「僅複製不執行」或「需要二次確認」的設計。
- **過度擬合資料集**：KaliBench 雖大，但仍可能無法涵蓋所有工具版本與發行版差異。建議保留部分真實滲透測試日誌作為外部測試集，避免模型只記住資料集模式。
- **別名與版本差異**：不同 Kali Linux 版本或套件來源可能導致工具別名、旗標支援不同。部署時應以目標環境的實際手冊文件為準，定期更新正規化規則。
- **獎勵函式設計偏差**：RLVR 的獎勵若過度強調精確命令，可能抑制合理替代寫法。建議結合語意相似度與執行結果，設計多維度獎勵而非單一二元獎勵。
- **資安與法規合規**：自動生成攻擊命令可能觸及當地法律或企業政策。僅在授權環境（如自有實驗室、合約滲透測試範圍）內使用，並留存稽核紀錄。

### 與其他技術的整合建議

- **與 SIEM / SOAR 整合**：將 KaliBench 訓練出的模型嵌入 SOAR 劇本，讓告警觸發時自動建議調查命令（如記憶體傾印、網路連線檢查），再由分析師審核後執行。
- **與函式呼叫（Function Calling）框架整合**：雖然 KaliBench 聚焦無綱要 CLI，但可將其正規化後的命令轉為結構化工具呼叫格式，銜接 LangChain、AutoGen 等智能體框架，實現「自然語言 → 結構化意圖 → 精確 CLI」的兩階段流程。
- **與 RAG 知識庫整合**：搭配工具手冊文件與內部 Wiki 建立檢索增強生成（RAG）系統，讓模型在生成命令前能檢索最新工具用法，彌補訓練資料截止時間的限制。
- **與 CI/CD 安全測試整合**：在 DevSecOps 管線中，利用模型自動生成針對容器或 API 的安全掃描命令，並將 KaliBench 的驗證邏輯作為閘道，確保生成命令符合預期語法。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從「適用場景」與「潛在風險」讀起，理解 KaliBench 為什麼重要、能解決什麼問題，再透過 GitHub 上的範例資料觀察「自然語言查詢」如何對應到「精確 CLI 命令」，不必一開始就深入 RLVR 或正規化細節。

- **AI 工程師**：重點閱讀「實作步驟建議」與「與其他技術的整合建議」，關注資料正規化、別名感知評估與無執行期獎勵的實作方式；建議直接下載資料集進行 SFT/RLVR 實驗，並將驗證管線整合進現有的模型訓練流程。

- **研究人員**：建議深入分析論文中的三種評估模式與 23 個能力維度，思考如何將 KaliBench 的細粒度訊號擴展到其他作業系統或工具生態，並探索更強大的獎勵模型、執行期驗證與安全對齊方法。

- **產品經理**：建議聚焦「適用場景」與「潛在風險與注意事項」，評估將 KaliBench 技術轉化為內部助理或自動化工具的可行性與合規風險；同時注意論文中「無開放權重模型在無限制設定下超過 42% 精確命令準確率」的發現，合理設定產品上線前的準確率目標與人機協作機制。
