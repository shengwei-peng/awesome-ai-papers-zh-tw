## ⚡ TL;DR

針對串流影片生成服務，解決工作階段長短不一與使用者需求劇烈波動導致的排程與資源配置難題。
提出 TurboServe，以閉迴路排程整合放置與擴展，並支援合併區塊處理、狀態卸載及線上遷移。
實驗顯示，TurboServe 平均降低尾端每區塊延遲 37.5% 與 GPU 總成本 37.2%。

## 摘要翻譯

串流影片生成（Streaming Video Generation）是一種新興的服務工作負載，使用者與長期存續的工作階段互動，這些工作階段會逐步逐區塊（Chunk）地生成影片。不同於離線影片生成（Offline Video Generation）或典型的大型語言模型（LLM）服務，串流影片生成必須跨越活躍與閒置時期（Active and Idle Periods）持續保留工作階段狀態（Session State），反覆排程進行中的工作階段，並在嚴格的延遲目標（Latency Target）下交付每個區塊。這在多使用者、多 GPU 環境（Multi-user, Multi-GPU Environment）中帶來兩項關鍵的服務挑戰：工作階段持續時間異質性（Session Duration Heterogeneity），即長期執行的工作階段會使工作階段放置（Session Placement）決策隨時間劣化；以及時間性使用者需求異質性（Temporal User-demand Heterogeneity），即活躍工作階段數量在突發與閒置時期之間劇烈波動。

我們提出 TurboServe，首個專為串流影片生成工作負載設計的服務系統。TurboServe 將服務形式化為一個線上排程（Online Scheduling）問題，聯合協調工作階段放置（Session Placement）與 GPU 資源配置（GPU Provisioning）。其閉迴路排程演算法（Closed-loop Scheduling Algorithm）結合了遷移感知放置控制器（Migration-aware Placement Controller）與負載驅動自動擴展控制器（Load-driven Autoscaling Controller）：前者跨 GPU 重新平衡（Rebalancing）工作階段以降低最大每區塊延遲（Per-chunk Latency），後者則依據工作負載變化（Workload Variation）調整 GPU 預算以提升成本效益（Cost Efficiency）。為了在執行期支援這些決策，TurboServe 實作合併區塊處理（Coalesced Chunk Processing）以在同一 GPU 上批次處理（Batching）並行活躍工作階段、GPU-CPU 卸載（GPU-CPU Offloading）以進行工作階段的暫停與恢復（Suspension and Resumption），以及基於 NCCL 的 GPU-GPU 遷移（NCCL-based GPU-GPU Migration）以進行線上重新平衡（Rebalancing）。

我們在來自 Shengshu Technology 的真實生產環境追蹤紀錄（Production Traces）上評估 TurboServe，橫跨多種模型大小與 GPU 叢集，規模最高達 64 張 NVIDIA B300 GPU。相較於基準服務配置（Baseline Serving Configurations），TurboServe 平均可將最壞情況每區塊延遲（Worst-case Per-chunk Latency）降低 37.5%，並將總 GPU 運作成本（GPU Operating Cost）降低 37.2%。我們的程式碼已公開於 https://github.com/shengshu-ai/TurboServe。

## 深度分析

#### 方法論解析

TurboServe 將串流影片生成（streaming video generation）的服務問題形式化為一個線上排程（online scheduling）問題，其核心在於聯合決策工作階段放置（session placement）與 GPU 資源配置（GPU provisioning），並在嚴格的每區塊延遲（per-chunk latency）限制下進行最佳化。此問題的難度源於兩項異質性：工作階段持續時間異質性（session duration heterogeneity）與時間性使用者需求異質性（temporal user-demand heterogeneity）。

為解決此問題，作者設計了一套閉迴路排程演算法（closed-loop scheduling algorithm），由兩個緊密耦合的控制器組成：

1. **遷移感知放置控制器（migration-aware placement controller）**：該控制器採用事件驅動（event-driven）的 min-max 重新平衡（rebalancing）策略。當系統偵測到特定 GPU 成為瓶頸時，控制器會觸發工作階段遷移，將工作階段從高負載 GPU 移出，以降低最壞情況每區塊延遲（worst-case per-chunk latency）。此處的「遷移感知」意味著演算法在決定放置時已將遷移成本納入考量，避免因頻繁遷移而導致的額外開銷侵蝕延遲收益。

2. **負載驅動自動擴展控制器（load-driven autoscaling controller）**：該控制器依據執行期負載回饋動態調整 GPU 預算。在需求爆發時擴展 GPU 數量以保留延遲餘裕（latency headroom），在需求低點時縮減 GPU 數量以避免資源浪費。關鍵在於，此控制器與放置控制器形成閉迴路：可用的 GPU 預算限制了可行的放置方案，而當前的放置狀態又決定了該預算是否充足。將兩者視為獨立元件將遺留顯著的效能空間，因此聯合管理是必要的。

在執行期支援方面，TurboServe 實作了三項關鍵機制：

- **合併區塊處理（coalesced chunk processing）**：在同一 GPU 上將多個並行活躍工作階段（concurrent active sessions）的區塊生成進行批次處理（batching），同時保留各工作階段獨立的生成狀態（generation state）與 KV 快取（KV cache）。這提升了 GPU 利用率，並攤銷推理啟動成本。

- **GPU-CPU 卸載（GPU-CPU offloading）**：當工作階段進入閒置時期（idle periods）時，系統將其工作階段狀態（session state）——包含快取的時間狀態（cached temporal states）與提示詞上下文（prompt context）——從 GPU 記憶體卸載至 CPU 記憶體，執行暫停（suspension）；待使用者再次活躍時再恢復（resumption）。此機制釋放了寶貴的 GPU 記憶體，使更多活躍工作階段能並行執行。

- **基於 NCCL 的 GPU-GPU 遷移（NCCL-based GPU-GPU migration）**：為了支援線上重新平衡（online rebalancing），TurboServe 利用 NCCL 在 GPU 之間直接遷移工作階段狀態，無需經過 CPU 中轉，大幅降低了遷移延遲，使放置控制器能夠在毫秒級的時間尺度上調整負載分佈。

#### 實驗數據解讀

TurboServe 的評估建立在 Shengshu Technology 的真實生產環境追蹤紀錄（production traces）之上，涵蓋多種模型規模與最多達 64 張 NVIDIA B300 GPU 的叢集。這樣的實驗設計具有高度代表性，因為生產環境追蹤紀錄真實反映了工作階段持續時間分佈與時間性需求波動，遠勝於合成負載（synthetic workload）。

評估採用兩項核心指標：

- **最壞情況每區塊延遲（worst-case per-chunk latency）**：此指標對應串流服務的尾端延遲（tail latency），直接決定使用者是否會感受到卡頓。由於串流影片生成要求每個區塊（chunk）都必須在嚴格的延遲目標（latency target）內交付，最壞情況延遲比平均延遲更能反映服務品質。
- **GPU 運作成本（GPU operating cost）**：以總 GPU 使用時間或租用量衡量，反映系統的經濟性與成本效益（cost efficiency）。

實驗結果顯示，相較於基準服務配置（baseline serving configurations），TurboServe 平均將最壞情況每區塊延遲降低 37.5%，同時將 GPU 運作成本降低 37.2%。這兩項數據的意義不容小覷：在傳統的資源管理中，延遲與成本往往存在取捨（trade-off）——降低延遲通常需要過度配置（over-provisioning）資源，而節省成本則可能犧牲尾端延遲。TurboServe 透過閉迴路排程同時優化兩者，顯示其重新平衡與自動擴展機制確實能夠在正確的時機將資源調度至正確的位置，而非單純地增加資源預算。

值得注意的是，37.5% 的延遲改善主要來自於遷移感知放置控制器消除了熱點 GPU 上的排隊延遲；而 37.2% 的成本節省則歸功於負載驅動自動擴展控制器在低需求時期釋放多餘 GPU，並透過 GPU-CPU 卸載維持較高的 GPU 記憶體周轉率，避免為了保留閒置工作階段狀態而長期佔用 GPU。

#### 與現有研究的比較

現有的影片生成服務系統，如 FastVideo、xDiT、vLLM-Omni、TurboDiffusion 與 TridentServe，主要針對無狀態隔離作業（stateless isolated jobs）進行最佳化，亦即每個請求可獨立排程、資源化並在隔離環境中完成。這類系統假設每個生成任務都是一次性生成（one-shot generation），完成後即可釋放所有狀態。

然而，串流影片生成（streaming video generation）徹底顛覆了此假設。在 TurboServe 所針對的場景中，服務圍繞著有狀態串流工作階段（stateful streaming sessions）運作，必須跨活躍與閒置時期（active and idle periods）持續保留提示詞上下文（prompt context）與快取的時間狀態（cached temporal states）。現有系統未考慮工作階段持續時間異質性（session duration heterogeneity）與時間性使用者需求異質性（temporal user-demand heterogeneity），導致長時間運作的工作階段逐漸累積於特定 GPU 上，形成負載不均；同時，靜態資源配置無法應對需求爆發與閒置期的劇烈波動。

TurboServe 的貢獻在於它是首個專為多使用者、多 GPU 環境（multi-user, multi-GPU environment）設計的串流影片生成服務系統。其閉迴路設計將工作階段放置（session placement）與 GPU 資源配置（GPU provisioning）視為相互依存的聯合問題，而非獨立的最佳化子問題。

儘管如此，從現有文本可推論的潛在限制包括：

- 目前機制主要針對單一叢集內的 GPU-GPU 遷移，對於跨叢集或地理分散式部署的支援尚未明確。
- 系統依賴 NCCL 進行遷移，這在異質網路環境或不同世代 GPU 間的相容性可能構成挑戰。
- 評估集中於 NVIDIA B300 GPU，對於其他架構的適用性有待驗證。
- 生產環境追蹤紀錄來自單一公司（Shengshu Technology），雖然真實，但負載特徵可能帶有特定業務場景的偏差。

#### 可重現性評估

TurboServe 的原始碼已於 https://github.com/shengshu-ai/TurboServe 公開釋出，這對研究社群是一大助益，使其他研究者能夠檢視其閉迴路排程演算法（closed-loop scheduling algorithm）的實作細節，並進行復現或擴展研究。

然而，可重現性仍面臨若干挑戰：

- 生產環境追蹤紀錄（production traces）來自 Shengshu Technology 的內部服務，目前文本未明確指出這些追蹤紀錄是否同步公開。若僅有程式碼而無真實負載數據，第三方難以完全復現論文中的 37.5% 與 37.2% 量化結果。
- 實驗規模涉及最多 64 張 NVIDIA B300 GPU，這樣的硬體規模對於學術實驗室而言門檻極高，限制了小規模團隊進行端到端驗證的能力。
- 論文提及「多種模型規模」（multiple model sizes），但未在提供的文本中詳細說明是否包含開源模型權重（model weights）或僅為內部模型。若評估使用專有模型，則即使系統開源，端到端復現仍受限。

整體而言，TurboServe 在系統層面達到了良好的開放性，但在資料集與硬體需求方面，完全的重現仍需要社群或作者進一步釋出負載追蹤與模型配置細節。

#### 未來研究方向

基於 TurboServe 的設計與提供的文本，以下幾個方向值得深入探索：

1. **預測性自動擴展（Predictive Autoscaling）**：當前的負載驅動自動擴展控制器（load-driven autoscaling controller）屬於反應式（reactive）機制。未來可結合時間序列預測模型，根據歷史生產環境追蹤紀錄（production traces）預測需求爆發，在負載上升前預先擴展 GPU 資源，進一步壓縮最壞情況每區塊延遲（worst-case per-chunk latency）。

2. **異質 GPU 叢集支援**：目前系統評估集中於同質的 NVIDIA B300 GPU 叢集。未來可擴展至異質 GPU 環境（例如混合不同記憶體容量或算力的 GPU），並設計差異化的工作階段放置（session placement）策略，將輕量工作階段指派至低階 GPU，記憶體密集的工作階段保留給高階 GPU。

3. **模型平行（Model Parallelism）與管道平行（Pipeline Parallelism）**：當影片生成模型規模持續成長，單一 GPU 可能無法容納完整模型與多個工作階段的 KV 快取（KV cache）。未來可將 TurboServe 的放置與遷移邏輯擴展至跨多 GPU 的模型分片，處理超大模型的串流服務。

4. **記憶體壓縮與漸進式卸載**：目前的 GPU-CPU 卸載（GPU-CPU offloading）將完整工作階段狀態（session state）搬移。未來可研究針對 KV 快取的壓縮演算法（如量化或稀疏化），或設計漸進式、層級式的卸載策略，在 CPU 記憶體容量受限時仍能支援大量閒置工作階段。

5. **多模態串流服務**：隨著互動訊號（interaction signal）日益複雜，未來的串流生成可能同時涉及影片、音訊與文字模態。將 TurboServe 的排程框架擴展至多模態工作負載，統一管理跨模態的狀態遷移與資源配置，將是極具實務價值的延伸。

6. **差異化服務品質（QoS-aware Scheduling）**：目前系統以單一延遲目標（latency target）為導向。未來可引入分級服務機制，針對付費用戶與免費用戶設定不同的每區塊延遲（per-chunk latency）保證，並在重新平衡（rebalancing）決策中納入優先權權重。

## 論文問答

**Q1：TurboServe 主要針對串流影片生成服務中的哪些核心挑戰？**
A：TurboServe 主要解決多使用者、多 GPU 環境下串流影片生成所帶來的兩大異質性挑戰：工作階段持續時間異質性與時間性使用者需求異質性。不同使用者的有狀態串流工作階段長短不一，從數秒到數十分鐘不等，導致靜態放置決策隨時間劣化；同時，活躍工作階段數量會在短時間內劇烈波動，造成資源配置難以同時滿足尖峰延遲與離峰成本的需求。這些挑戰源於串流生成必須跨活躍與閒置時期保留工作階段狀態，並在嚴格的每區塊延遲目標下逐步輸出影片，與傳統無狀態的一次性生成有本質差異。

**Q2：為何現有的影片生成服務系統無法有效支援串流影片生成工作負載？**
A：現有的擴散模型加速與服務系統（如 FastVideo、xDiT、vLLM-Omni 等）主要針對無狀態隔離作業進行最佳化，將每個請求視為獨立且短暫的任務，生成完成後即釋放狀態。然而，串流影片生成以有狀態串流工作階段為核心，必須長期保留提示詞上下文、KV 快取與其他快取的時間狀態，並反覆排程同一工作階段。這種範式錯配使得現有系統無法處理工作階段在活躍與閒置之間的狀態轉換，也無法因應長期執行工作階段累積所造成的負載失衡與資源浪費。

**Q3：專為串流影片生成設計服務系統為何具有重要性與迫切性？**
A：隨著 StreamDiffusionV2、Self-Forcing 等串流管線興起，影片生成正從離線一次性生成轉向漸進式、可互動的串流範式，應用於電影製作、遊戲與個人化內容創作等即時互動場景。在離線模式下，生成延遲隨影片長度呈二次成長，使用者必須等待數秒至數分鐘才能看到結果；串流生成雖能逐區塊輸出以降低等待，但必須在嚴格的每區塊延遲目標內完成，否則使用者體驗會中斷。因此，若缺乏專門的服務系統來管理有狀態工作階段與動態資源，這類互動式應用將難以在生產環境中同時達成即時性與經濟性。

**Q4：TurboServe 的核心方法論是什麼？它如何將服務問題形式化？**
A：TurboServe 將串流影片生成服務形式化為一個線上排程問題，在滿足每區塊延遲限制的前提下，聯合決策工作階段放置與 GPU 資源配置。其核心是設計一套閉迴路排程演算法，將遷移感知放置控制器與負載驅動自動擴展控制器緊密耦合，而非將兩者視為獨立元件。這種聯合設計讓系統能根據當前負載動態重新平衡工作階段，並即時調整 GPU 預算，從而在多工作階段、多 GPU 環境中同時最佳化延遲與成本。

**Q5：TurboServe 相較於傳統獨立設計的關鍵創新為何？**
A：TurboServe 的關鍵創新在於認知到工作階段放置與 GPU 資源配置是緊密耦合的：可用的 GPU 預算決定了哪些放置方案可行，而當前的放置狀態又決定了該預算是否足以支撐負載。為此，系統引入遷移感知放置控制器，透過事件驅動的 min-max 重新平衡策略，將工作階段從瓶頸 GPU 遷出以降低最壞情況每區塊延遲；同時搭配負載驅動自動擴展控制器，依據執行期回饋在需求爆發時擴展 GPU、在離峰時縮減以提升成本效益。兩者形成閉迴路，避免了獨立設計導致的次優效能，實現延遲與成本的同步最佳化。

**Q6：為了支援執行期的排程決策，TurboServe 實作了哪些關鍵執行期機制？**
A：TurboServe 實作了三大執行期機制以支援其閉迴路排程：首先是合併區塊處理，讓同一 GPU 上多個並行活躍工作階段的區塊生成能夠批次執行，同時保留各自的每工作階段狀態以提升 GPU 利用率。其次是 GPU-CPU 卸載，用於將閒置工作階段的生成狀態與 KV 快取暫存至 CPU 記憶體，釋放寶貴的 GPU 記憶體並支援後續恢復。最後是基於 NCCL 的 GPU-GPU 遷移，使系統能夠在不停機的情況下線上重新平衡工作階段，將負載從過載 GPU 遷移至較閒置的 GPU，從而降低尾端延遲。

**Q7：TurboServe 的實驗評估使用了哪些基準與基礎設施？**
A：評估採用了來自生數科技（Shengshu Technology）的真實生產環境追蹤紀錄，涵蓋多種不同長度與活躍模式的工作階段，並在多種影片生成模型尺寸上進行測試。實驗規模擴展至多達 64 張 NVIDIA B300 GPU 的叢集，以驗證系統在多使用者、多 GPU 環境下的擴展性。比較對象為基準服務配置，透過最壞情況每區塊延遲與總 GPU 運作成本兩大指標，評估 TurboServe 在真實動態工作負載下的表現。

**Q8：TurboServe 相較於基線配置達成了哪些關鍵量化成果？**
A：實驗結果顯示，TurboServe 平均能將最壞情況每區塊延遲降低 37.5%，顯著改善使用者觀看的即時性與流暢度。同時，總 GPU 運作成本平均減少 37.2%，代表系統在維持服務品質的同時大幅提升了成本效益。這些成果證明了閉迴路排程與執行期機制在平衡延遲與成本上的有效性，特別是在具有工作階段持續時間異質性與時間性需求波動的真實生產環境中。

**Q9：TurboServe 中的放置控制器與自動擴展控制器各自對整體效能有何貢獻？**
A：根據論文所述，遷移感知放置控制器專注於降低最壞情況每區塊延遲，透過事件驅動的重新平衡與 NCCL 遷移，將工作階段從瓶頸 GPU 移出，避免單一節點過載導致的尾端延遲飆升。負載驅動自動擴展控制器則專注於成本效益，依據執行期活躍工作階段數量的變化動態增減 GPU 預算，避免在需求低谷時過度配置資源。兩者透過閉迴路緊密整合：放置決策影響了所需的最小 GPU 數量，而可用的 GPU 預算又限制了可行的放置方案，因此只有聯合運作才能同時達成延遲降低與成本節省的雙重目標，而非僅能取捨其一。

**Q10：TurboServe 在哪些實際產品場景中最具應用價值？**
A：TurboServe 特別適合需要長期互動與即時回饋的影片生成應用，例如電影製作中的分鏡迭代、廣告創意即時預覽、遊戲中的動態劇情生成，以及個人化內容創作平台。在這些場景中，使用者通常會進行數分鐘的連續提示詞調整與影片細修，工作階段會在活躍生成與閒置思考之間反覆切換。TurboServe 透過保留工作階段狀態並動態調度資源，確保使用者在每次互動後都能於嚴格延遲目標內獲得新生成的區塊，從而提供流暢的創作體驗。

**Q11：在生產環境中部署 TurboServe 需要考量哪些維運與系統層面的因素？**
A：部署時必須考量工作階段狀態的記憶體佔用與生命週期管理，因為 KV 快取與時間狀態可能非常龐大，GPU-CPU 卸載與 GPU-GPU 遷移都會消耗額外的記憶體頻寬與網路資源。維運團隊需要評估 NCCL 遷移的開銷與重新平衡的收益比，確保在負載轉移過程中不會反而增加每區塊延遲。此外，自動擴展機制需要與底層雲端或資料中心的 GPU 供給能力整合，以確保在需求爆發時能夠及時取得額外的 NVIDIA B300 等 GPU 資源，避免擴展延遲影響服務品質。

**Q12：TurboServe 對生成式 AI 服務領域可能帶來哪些深遠影響？**
A：TurboServe 標誌著影片生成服務從無狀態批次作業邁向有狀態串流工作階段管理的重要範式轉移，為互動式生成媒體的服務系統設計提供了新的參考架構。它證明了在動態工作負載下，聯合排程工作階段放置與資源配置是達成即時性與經濟性不可或缺的手段。此設計哲學未來可望延伸至其他需要長期狀態保留的生成式工作負載，例如串流 3D 場景生成、即時音訊合成或多模態互動代理，推動整個生成式 AI 服務基礎設施朝向更具互動性與資源效率的方向發展。

**Q13：TurboServe 目前面臨哪些內在限制或設計上的邊界條件？**
A：TurboServe 的效能受益於 NCCL 高速互連與 GPU-CPU 卸載頻寬，因此當工作階段狀態極為龐大或叢集網路拓撲不利於 GPU 間直接通訊時，遷移與卸載的開銷可能會侵蝕延遲改善的收益。目前的評估規模達到 64 張 GPU，雖已屬中大型叢集，但在超大規模跨機房部署時，自動擴展的反應時間與跨節點狀態同步可能會面臨新的挑戰。此外，系統假設工作負載特性可透過生產追蹤紀錄進行建模，若遇到與訓練分佈極端偏離的異常流量模式，閉迴路控制器的調節效果可能需要更長的收斂時間。

**Q14：在什麼樣的極端條件下，TurboServe 的閉迴路排程可能無法達成預期的延遲或成本目標？**
A：若使用者需求爆發過於劇烈且集中，導致自動擴展控制器來不及在下一個區塊生成週期內完成 GPU 資源配置，系統可能會暫時無法維持每區塊延遲目標。同樣地，如果絕大多數工作階段同時處於活躍狀態而幾乎無閒置期，GPU-CPU 卸載機制將無法發揮記憶體釋放與批次合併的效益，導致資源利用率下降。此外，當長期工作階段數量遠超過單一 GPU 記憶體容量且遷移頻寬飽和時，重新平衡的速度會受限，使得某些 GPU 持續處於過載狀態，進而推升最壞情況每區塊延遲。

**Q15：基於 TurboServe 的成果，未來有哪些值得探索的研究方向？**
A：未來研究可將此閉迴路聯合排程框架擴展至其他有狀態生成媒體，例如長篇音訊串流、互動式 3D 內容生成或多模態大型語言模型的會話服務。另一方向是引入基於預測的主動式自動擴展，利用工作負載預測模型在需求爆發發生前預先配置 GPU，進一步縮短反應時間。同時，針對不斷增大的模型狀態與 KV 快取，設計更輕量的狀態壓縮與增量遷移協定，以及探索異質 GPU 叢集上的成本感知放置策略，都將是提升串流生成服務效率的重要課題。

## 實務應用指南

### 適用場景

1. **互動式影片創作平台**：使用者透過對話式介面反覆調整提示詞與風格，工作階段持續時間從數秒到數十分鐘不等，且活躍與閒置時期交替出現。TurboServe 的合併區塊處理與 GPU-CPU 卸載能支撐高併發創作，同時在閒置時釋放顯示卡記憶體。
2. **即時虛擬角色與遊戲直播**：虛擬主播或 NPC 需要根據即時互動訊號生成連貫影片區塊，每區塊延遲必須低於人類感知門檻。系統需保留長期時序狀態（KV 快取）以維持角色一致性，並在觀眾湧入時自動擴展 GPU。
3. **廣告與行銷素材協作生成**：品牌團隊同時編輯多支影片腳本，需求呈現明顯的時間性使用者需求異質性（上班時段爆量、離峰時段閒置）。TurboServe 的負載驅動自動擴展可降低離峰期的 GPU 運作成本。
4. **教育與培訓模擬影片服務**：學員在長期工作階段中分段觀看生成式模擬情境，系統必須在暫停與恢復之間保留完整的生成狀態，避免重複運算。
5. **智慧城市即時場景模擬**：交通或災防單位在緊急事件期間大量調用串流影片生成進行沙盤推演，需求暴漲且不可預測，需要線上重新平衡與跨 GPU 遷移來維持最壞情況每區塊延遲。

### 實作前置條件

**資料面**：需蒐集生產環境追蹤紀錄，包含工作階段持續時間分佈、活躍工作階段數量時間序列、每區塊延遲目標（例如 500 ms 以內），以及提示詞上下文與互動訊號的狀態大小。

**運算面**：至少具備 NVLink 或高速 InfiniBand 互連的多 GPU 叢集（論文使用最多 64 張 NVIDIA B300 GPU）；CPU 記憶體需足夠容納閒置工作階段卸載後的狀態；NCCL 環境需正確配置以支援 GPU-GPU 遷移。

**技術面**：團隊需熟悉分散式系統排程、CUDA 記憶體管理、容器化部署（如 Kubernetes），並具備擴散模型推理優化經驗，能針對合併區塊處理調整模型計算圖（CUDA Graph）與記憶體池。

### 實作步驟建議

1. **工作負載特徵化**：分析內部生產環境追蹤紀錄，量化工作階段持續時間異質性與時間性使用者需求異質性，確定延遲目標與成本預算。
2. **模型串流化改造**：將既有離線影片生成模型（如 HunyuanVideo、Wan）改為逐區塊生成模式，實作 KV 快取與時間狀態的保留與更新邏輯，確保每區塊輸出後狀態可序列化。
3. **部署 TurboServe 執行期**：建置支援合併區塊處理的推理引擎，啟用 GPU-CPU 卸載機制以釋放閒置工作階段佔用的 GPU 記憶體，並驗證 NCCL-based GPU-GPU 遷移在叢集內的頻寬與穩定性。
4. **設定閉迴路排程參數**：配置遷移感知放置控制器的觸發閾值（如 GPU 記憶體使用率、每區塊排隊延遲）與負載驅動自動擴展控制器的擴縮容策略（如目標利用率 70%、冷卻時間 30 秒）。
5. **漸進式驗證**：先以 A/B 測試對比基準服務配置（如靜態配置或 xDiT），監測最壞情況每區塊延遲與總 GPU 運作成本；逐步放開自動擴展與線上重新平衡，觀察遷移次數與狀態一致性。
6. **上線與監控整合**：將每區塊延遲、工作階段狀態大小、GPU 記憶體水位、遷移事件等指標匯入監控系統，建立異常告警（如遷移失敗或狀態損毀）。

### 潛在風險與注意事項

- **遷移延遲突波**：NCCL-based GPU-GPU 遷移雖然快速，但在網路擁塞或 GPU 記憶體碎片化嚴重時，仍可能導致單一區塊延遲超標。建議設定遷移預算（migration budget），僅在預期收益大於遷移成本時執行。
- **CPU 卸載頻寬瓶頸**：大量閒置工作階段同時卸載至 CPU 記憶體時，PCIe 頻寬可能成為瓶頸。應評估卸載狀態的壓縮率，並預留足夠 CPU 記憶體與頻寬。
- **長期狀態漂移**：有狀態串流工作階段在長時間運行後，KV 快取可能累積數值誤差或語意漂移。需定期驗證時間一致性，並設計狀態重置或摘要機制。
- **自動擴展冷啟動**：GPU 實例擴容時的驅動初始化與模型載入可能耗時數分鐘，無法應對秒級需求暴漲。建議搭配預熱池（warm pool）或部分過度配置（headroom provisioning）。
- **與既有負載平衡器衝突**：若前端已部署獨立負載平衡器，其無狀態路由決策可能與 TurboServe 的閉迴路放置控制器打架。應將工作階段親和性（session affinity）與排程決策下沉至 TurboServe 層。

### 與其他技術的整合建議

- **與 vLLM / xDiT 整合**：TurboServe 專注於多工作階段排程與資源管理，可疊加在 xDiT 等分散式推理框架之上，負責單一區塊內的張量並行；vLLM-Omni 則可借鏡其 KV 快取管理，但需注意影片與文字在狀態生命週期的差異。
- **與 Kubernetes 整合**：建議以 Custom Controller 或 Operator 形式實作負載驅動自動擴展，取代原生 HPA。透過自訂指標（custom metrics）將「每 GPU 並行活躍區塊數」與「工作階段狀態記憶體總量」回報給排程器。
- **與監控可觀測性堆疊整合**：將 TurboServe 內部事件（重新平衡、暫停、恢復、遷移）以 OpenTelemetry 或 Prometheus exporter 輸出，並在 Grafana 建立專屬儀表板，特別關注最壞情況每區塊延遲的 P99 與成本歸因。
- **與模型倉儲 / 編排整合**：透過 TorchServe 或 Triton Inference Server 的 backend 介面封裝合併區塊處理邏輯，但需自行管理有狀態後端（stateful backend），因為主流推論伺服器多為無狀態設計。

- **初學者**：請先從圖 1 與圖 2 著手，理解「無狀態隔離作業」與「有狀態串流工作階段」的根本差異，以及為何長短不一的工作階段與忽高忽低的活躍數量會讓傳統 GPU 配置失效。掌握這兩項異質性後，再閱讀摘要中的兩大貢獻，即可建立整體直覺。

- **研究人員**：請聚焦於線上排程問題的形式化定義與閉迴路排程演算法的設計邏輯，分析遷移感知放置控制器如何將 min-max 重新平衡問題轉化為事件驅動決策，以及負載驅動自動擴展控制器在理論上與傳統反應式擴展（reactive autoscaling）的差異與優勢。
