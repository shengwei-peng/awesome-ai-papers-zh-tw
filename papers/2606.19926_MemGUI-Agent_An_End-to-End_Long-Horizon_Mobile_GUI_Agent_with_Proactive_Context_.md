# MemGUI-Agent：具備主動式上下文管理之端到端長程行動 GUI 代理人

## ⚡ TL;DR

現有行動GUI代理人難以完成長程任務，因ReAct式提示導致上下文爆炸與關鍵資訊遺失。
本文提出MemGUI-Agent，以ConAct將上下文管理視為策略動作，透過三欄保留UI關鍵資訊。
訓練後的8B模型在MemGUI-Bench達開源最佳表現，並成功泛化至MobileWorld基準。

## 摘要翻譯

基於多模態大型語言模型（Multimodal Large Language Model, MLLM）的行動 GUI 代理人（mobile GUI agent）在短程任務（short-horizon tasks）上已取得顯著進展，但在需要跨越多個步驟與應用程式轉換（app transitions）、並保留中繼事實（intermediate facts）的長程任務（long-horizon tasks）上仍不可靠。我們將此限制歸因於 ReAct 式提示（ReAct-style prompting），其被動地累積逐筆步驟記錄（per-step records），導致提示爆炸（prompt explosion）並稀釋關鍵的跨應用程式事實（cross-app facts）。為解決此問題，我們提出 MemGUI-Agent，一個具備主動式上下文管理（proactive context management）之端到端（end-to-end）長程行動 GUI 代理人。MemGUI-Agent 基於上下文即動作（Context-as-Action, ConAct），該方法將上下文管理視為一等公民動作（first-class actions），由選取 UI 動作（UI actions）的同一策略所發出。ConAct 並非被動地附加歷史記錄，而是維護三個結構化的上下文欄位（context fields）：折疊動作歷史（folded action history）、折疊 UI 狀態（folded UI state）與近期步驟記錄（recent step record），在保留關鍵 UI 事實（UI facts）的同時保持上下文精簡。為使主動式上下文管理可跨模型規模學習，我們建構了 MemGUI-3K，這是一個包含 2,956 筆軌跡（trajectories）的資料集，具備完整的 ConAct 標註（ConAct annotations），供監督式訓練（supervised training）與離線分析（offline analysis）使用。在 MemGUI-3K 上訓練 8B 模型可訓練出 MemGUI-8B-SFT，這是一個 8B 規模的 MemGUI-Agent，在 MemGUI-Bench 上達到開放資料 8B 規模模型中的最佳效能，並能泛化至分布外（out-of-distribution, OOD）的 MobileWorld 基準測試（MobileWorld benchmark）。程式碼、資料與訓練完成的模型將於 https://memgui-agent.github.io/ 釋出。

### 核心貢獻（3～5點）
- 提出上下文即動作（Context-as-Action, ConAct）機制：將上下文管理視為與 UI 動作同等重要的一等公民動作（first-class actions），由端到端策略主動發出，從根本解決提示爆炸（prompt explosion）與跨應用程式事實（cross-app facts）稀釋問題。
- 建構 MemGUI-3K 軌跡資料集（trajectory dataset）：收錄 2,956 筆軌跡並提供完整的 ConAct 標註（ConAct annotations），為主動式上下文管理（proactive context management）的監督式訓練（supervised training）與離線分析（offline analysis）提供基礎。
- 訓練出 MemGUI-8B-SFT 模型：在 MemGUI-Bench 上達到開放資料 8B 規模模型中的最佳效能，並成功泛化至分布外（out-of-distribution, OOD）的 MobileWorld 基準測試（MobileWorld benchmark）。
- 驗證主動式上下文管理在端到端（end-to-end）策略中的可學習性，證明無需外掛記憶模組即可透過單一策略同時學習 UI 動作選取與上下文欄位（context fields）維護。

### 適合對象
從事多模態大型語言模型（MLLM）、行動裝置自動化、長程任務規劃與記憶機制，以及端到端 GUI 代理人系統相關研究的研究人員與工程師；特別適合關注如何以單一統合策略解決長程任務中上下文遺失與提示爆炸問題的讀者。

## 深度分析

#### 方法論解析

本文提出 MemGUI-Agent 的核心創新在於將上下文管理（context management）從被動的提示工程（prompt engineering）提升為策略層級的主動式決策行為，透過 Context-as-Action（ConAct，上下文即動作）框架實現。傳統的 ReAct-style prompting（ReAct 式提示）採用逐筆步驟記錄（per-step records）的線性累積方式，導致提示爆炸（prompt explosion）與資訊遺失（information loss），特別是在跨應用程式事實（cross-app facts）需要長期保留的長程（long-horizon）任務中。ConAct 的解決方案是將上下文策展（context curation）視為與 UI 動作（UI actions）同等重要的「一等公民動作」（first-class actions），由同一個端到端（end-to-end）策略（policy）在單次前向傳播（forward pass）中聯合預測。

具體而言，MemGUI-Agent 在每個時間步 $t$ 觀察結構化狀態 $S_t = (G, H_t, M_t, L_t)$，其中 $G$ 為使用者目標（user goals），$H_t$ 為 Folded Action History（折疊動作歷史），$M_t$ 為 Folded UI State（折疊 UI 狀態），$L_t$ 為 Recent Step Record（近期步驟記錄）。MLLM policy（多模態大型語言模型策略）$\pi_\theta$ 根據螢幕截圖（screenshots）$I_t$ 與 $S_t$ 輸出五元組 $y_t = (\tau_t, \phi_t, a_t, o_t, \iota_t)$，分別對應推理（reasoning）、折疊指令（folding directive）、UI 或記憶體動作（UI / memory action）、UI 觀察（UI observation）與動作意圖（action intent）。

在動作空間（action space）設計上，ConAct 將傳統的 UI 動作集合 $A_{ui}$（如點擊、輸入、滑動）擴展為 $A = A_{ui} \cup A_{mem}$，其中 $A_{mem} = \{add, update, delete\}$ 為記憶體操作，直接更新 $M_t$。這使得持續性 UI 衍生事實（persistent UI-derived facts）——例如價格、識別碼或複製的文字——能夠被主動寫入、修改或刪除，而非被動地依賴模型從冗長歷史中隱式回憶。

歷史折疊機制（History folding）是控制工作上下文（working context）規模的關鍵。折疊指令 $\phi_t = ([s_t, t], z_t)$ 指定了需要壓縮的歷史區間 $[s_t, t]$ 與生成摘要 $z_t$。此機制支援兩種模式：當 $s_t = t$ 時執行步驟級蒸餾（step-level distillation），將最新步驟壓縮為精簡記錄；當 $s_t < t$ 時則執行跨步抽象（span-level abstraction），將完成的子任務摘要為單一可複用記錄。透過 $H_{t+1} = \text{Fold}(H_t, \phi_t)$ 的更新規則，上下文增長從線性累積轉向次線性增長（sub-linear growth），有效緩解提示爆炸。

此外，Recent Step Record $L_t$ 保留了最新互動細節（recent interaction details），確保短期內的失敗恢復與細粒度推理不受折疊操作影響。這三個結構化上下文欄位（context fields）共同構成緊湊且具語義的工作上下文，使代理人在應用程式轉換（app transitions）與多步驟進度（multi-step progress）追蹤中，能同時維持上下文的緊湊性與關鍵事實的持續性。

#### 實驗數據解讀

論文提供的數據凸顯了長程任務對現有方法的嚴峻挑戰，並驗證了主動式上下文管理的必要性。以現有最強的開放資料 8B 端對端模型 GUI-Owl-1.5-8B 為例，其在短程基準測試 AndroidWorld（平均 8.4 步）上的成功率為 71.6%，但在任務範圍（task horizons）擴展至 MobileWorld（平均 27.8 步）時驟降至 38.2%，而在更長程的 MemGUI-Bench（平均 36.2 步）上僅剩 11.7%。這種隨步數增加而近乎線性的性能衰減，明確指向被動式上下文管理策略的瓶頸：當中繼事實（intermediate facts）必須跨越數十個步驟與多個應用程式邊界（app boundaries）時，機械式的截斷或附加無法維持資訊完整性。

在零樣本（zero-shot）設定下，將 MemGUI-Agent 應用於 Qwen3-VL-235B-Thinking 後，於 MemGUI-Bench 上達到 62.5% Pass@3，超越了基於 Gemini-2.5-Pro 建構的代理人框架（agentic frameworks）。這顯示即使在不經過監督式訓練（supervised training）的情況下，ConAct 的結構化上下文欄位與主動折疊機制已能顯著釋放大型基礎模型的長程推理潛力。

針對可學習性與規模擴展性，作者建構了 MemGUI-3K 軌跡資料集（trajectory dataset），包含 2,956 筆帶有完整 ConAct annotations（ConAct 標註）的軌跡。以此進行監督式微調（SFT）後得到的 MemGUI-8B-SFT，不僅在 MemGUI-Bench 上創下開放資料 8B 模型的最佳表現，更成功泛化至分布外（out-of-distribution, OOD）的 MobileWorld 基準測試（MobileWorld benchmark）。這項結果具有雙重意義：其一，證明了主動式上下文管理無需依賴數百億級參數即可透過監督學習內化；其二，顯示 ConAct 的結構化輸出格式具備良好的跨域遷移能力，不會過度擬合於特定任務分布。

#### 與現有研究的比較

MemGUI-Agent 在現有文獻中的定位介於模組化代理人框架（modular agentic frameworks）與簡約端對端模型（simple end-to-end models）之間，並試圖同時汲取兩者的優點。傳統的代理人框架通常配備獨立的規劃（planning）、記憶（memory）與接地（grounding）模組，並依賴複雜管線（complex pipelines）與專有骨幹多模態大型語言模型（proprietary backbone MLLM）。這類系統雖然在特定任務上表現強勁，但部署成本高、模組間延遲與錯誤傳播難以控制。相較之下，MemGUI-Agent 維持端到端策略（end-to-end policy）的簡潔性，將記憶體管理內化為策略的一部分，無需外部記憶體（external memory）模組。

在端對端模型的光譜中，現有方法多採用被動策略，包括 Action-Thought（動作-思考）、Multi-turn（多輪）、Rule-based（基於規則）與 No History（無歷史）等。這些方法無論是機械式附加歷史字串、硬性截斷，或完全捨棄舊資訊，都無法根據任務需求動態決定「何者該壓縮、何者該保留、何者該即時可用」。ConAct 的根本性差異在於將上下文管理從「資料結構操作」提升為「語意決策行為」：模型必須主動判斷哪些軌跡片段已構成可摘要的子任務（span-level abstraction），哪些 UI 事實需要持久化至 Folded UI State，以及如何用 Recent Step Record 維持短期記憶。

然而，本文的比較亦存在可進一步探討之處。例如，論文雖強調 MemGUI-8B-SFT 在開放資料 8B 模型中的領先地位，但尚未與同樣採用外部記憶體的開源代理人框架（如 AndroidWorld 中的某些實作）進行相同參數量級的公平對照。此外，ConAct 的五欄位結構化輸出雖然緊湊，但對基礎模型的遵循指令能力（instruction following）與函式呼叫格式（function-calling prompt format）有較高要求，這在較小規模或較舊架構的 MLLM 上可能難以直接複製。

#### 可重現性評估

從可重現性（reproducibility）的角度觀察，MemGUI-Agent 展現了高度開放的姿態。作者明確承諾將釋出程式碼（code）、資料（data）與訓練後模型權重（trained models），並提供專案頁面 https://memgui-agent.github.io/。其中，MemGUI-3K 資料集包含 2,956 筆軌跡的完整 ConAct annotations，這對於後續的離線分析（offline analysis）至關重要——研究者得以直接檢視模型在不同任務階段選擇的折疊範圍、記憶體操作與摘要內容，從而診斷上下文策展的決策邏輯。

在技術實現層面，MemGUI-Agent 基於 Qwen3-VL 的函式呼叫提示格式（function-calling prompt format）進行擴展，該格式屬於公開文件化的介面標準，降低了復現門檻。MemGUI-8B-SFT 的訓練流程採用標準的監督式微調（supervised fine-tuning, SFT），未涉及複雜的強化學習（reinforcement learning）或搜尋演算法，這使得具備基礎 GPU 資源的研究團隊較易複製訓練過程。

不過，可重現性仍面臨若干潛在挑戰。首先，長程行動 GUI 基準測試（如 MemGUI-Bench 與 MobileWorld）的執行通常需要完整的 Android 模擬器環境與特定應用程式版本，環境建置的細節（如系統版本、App 版本、螢幕解析度）若未完整記錄，可能導致性能差異。其次，雖然模型權重與資料集將公開，但 2,956 筆軌跡相較於一般大型 MLLM 訓練資料仍屬精緻小樣本，後續研究若需擴展至其他語言或平台，可能需要額外的資料收集與標註成本。

#### 未來研究方向

MemGUI-Agent 與 ConAct 框架為長程行動 GUI 代理人開闢了數個值得深入探索的方向。第一，在訓練範式上，目前 MemGUI-8B-SFT 僅採用監督式訓練，未來可引入強化學習（reinforcement learning）或從人類回饋的強化學習（RLHF），讓模型透過環境互動學習更優的折疊時機與記憶體更新策略，而非僅模仿靜態軌跡。這可能進一步提升在失敗恢復與探索性任務中的表現。

第二，上下文品質的評估指標尚待建立。現有評估多聚焦於最終任務成功率，但對於 Folded Action History 的摘要準確性、Folded UI State 的事實保留率，以及 Recent Step Record 的資訊完整性，缺乏細粒度的自動化度量。發展這類指標將有助於診斷長程失敗的根因，並促進上下文管理機制的可解釋性研究。

第三，ConAct 的設計原則可擴展至行動 GUI 以外的領域，例如網頁導航（web navigation）、桌面應用程式自動化，或具備更長任務範圍（100+ 步）的科學計算流程。不同平台的 UI 觀察空間與動作原語（action primitives）各異，如何將記憶體操作 $A_{mem}$ 與折疊語義泛化至非觸控介面，是極具實用價值的延伸。

第四，目前的外部記憶體（external memory）研究與 ConAct 的內建記憶體呈現光譜兩端。未來可探索混合式架構：在 ConAct 框架下保留輕量外部向量記憶體，用於儲存極長期或跨會話（cross-session）的事實，同時維持端對端策略對短期工作上下文的緊密控制。這或許能在「簡潔性」與「記憶容量」之間取得更佳平衡。

最後，隨著 MLLM 規模持續擴大，驗證 ConAct 在更大模型（如 30B 或 70B）上的規律性，以及其與鏈式思考（Chain-of-Thought）、樹狀搜尋（tree search）等推理增強技術的相容性，將有助於確立主動式上下文管理作為下一代 GUI 代理人基礎設施的地位。

## 論文問答

**Q1：現有基於多模態大型語言模型的行動 GUI 代理人在處理長程任務時，主要面臨什麼樣的核心挑戰？**

A：現有代理人在長程任務中難以可靠地保留跨越多個步驟與應用程式轉換的中繼事實，導致任務成功率隨步驟數增加而急遽下降。例如，GUI-Owl-1.5-8B 在平均 8.4 步的 AndroidWorld 上可達 71.6% 成功率，但在平均 36.2 步的 MemGUI-Bench 上卻暴跌至 11.7%。這種效能崩潰顯示，當任務範圍拉長時，代理人無法有效追蹤多步驟進度與跨應用程式事實，嚴重限制了其在真實場景中的實用性。

**Q2：為何 ReAct 式提示與其他被動式上下文管理策略難以應對長程行動 GUI 任務？**

A：ReAct 式提示採用被動累積逐筆步驟記錄的方式，使得提示長度隨任務步驟線性增長，最終導致提示爆炸。這種機械式的附加或截斷歷史記錄，會使關鍵的跨應用程式事實（如價格、識別碼或複製的文字）被稀釋、改寫、截斷甚至遺忘。此外，無論是動作-思考、多輪對話、基於規則或無歷史的策略，都無法同時提供緊湊的工作上下文與持續性 UI 衍生事實，因而難以支撐涉及大量應用程式轉換的長程互動。

**Q3：為何在行動裝置上實現有效的長程 GUI 自動化，對於端到端代理人架構特別重要？**

A：長程行動 GUI 自動化需要代理人在跨螢幕、跨步驟與跨應用程式的情況下，同時維持緊湊的工作上下文與持久的 UI 衍生事實。現有的代理人框架雖透過規劃、記憶與接地模組來處理此問題，但依賴複雜管線與專有骨幹模型，難以在行動裝置上部署；而端到端模型雖更簡潔，卻缺乏主動式的上下文策展能力。因此，設計一個能由單一端到端策略同時選擇 UI 動作並管理上下文的機制，是提升開放資料模型在真實長程場景中可用性的關鍵。

**Q4：MemGUI-Agent 提出的 ConAct（上下文即動作）範式，其核心運作機制為何？**

A：ConAct 將上下文管理視為與 UI 動作同等重要的一等公民動作，由同一個端到端策略在單次前向傳播中聯合預測。具體而言，模型在每一步會發出五個結構化輸出：推理、折疊指令、UI 或記憶體動作、UI 觀察與動作意圖，並據此更新三個結構化上下文欄位。透過將上下文策展內建於策略層級，ConAct 讓代理人主動決定何時壓縮歷史、何時保存關鍵事實，而非被動地附加日誌。

**Q5：相較於被動累積歷史記錄，ConAct 的三個結構化上下文欄位如何解決提示爆炸與資訊遺失的問題？**

A：ConAct 透過折疊動作歷史、折疊 UI 狀態與近期步驟記錄三個欄位，將上下文成長從線性累積推向次線性成長。折疊動作歷史允許模型透過步驟級蒸餾或跨度級抽象，將已完成子任務壓縮為可重複使用的摘要；折疊 UI 狀態則以結構化方式持續保存關鍵 UI 衍生事實，避免跨應用程式資訊被稀釋。近期步驟記錄則保留最新互動細節，確保代理人在壓縮遠期歷史的同時，仍能掌握當前狀態，從而兼顧上下文的緊湊性與關鍵資訊的持久性。

**Q6：MemGUI-Agent 為何選擇將記憶體操作（add、update、delete）納入與 UI 動作相同的動作空間，而非使用外部記憶體模組？**

A：將記憶體操作納入端到端策略的動作空間，可確保上下文管理與 UI 決策在同一個模型內聯合學習與執行，無需依賴複雜的外部管線或專有骨幹模型。這種設計讓代理人能根據當前任務需求，主動決定要新增、更新或刪除哪些持續性 UI 衍生事實，實現策略層級的上下文策展。相較於將上下文整理移至端到端策略之外的外部記憶體，此舉保持了端到端架構的簡潔性與可部署性，同時賦予模型主動管理長程依賴的能力。

A：MemGUI-8B-SFT 在 MemGUI-Bench 上達成了最佳開放資料 8B 模型效能，並能泛化至分布外的 MobileWorld 基準測試，顯示其學到的主動式上下文管理具有跨域遷移能力。此外，將 MemGUI-Agent 以零樣本方式應用於 Qwen3-VL-235B-Thinking 時，在 MemGUI-Bench 上達到 62.5% Pass@3，甚至超越了基於 Gemini-2.5-Pro 建構的代理人工作流程。這些結果證明，無論是在監督式微調的 8B 模型還是大型思考模型的零樣本設定下，ConAct 都能顯著提升長程任務的成功率。

**Q14：在什麼樣的情況下，MemGUI-Agent 的主動式上下文管理可能會失效或產生次佳結果？**

A：當任務涉及高度動態且不可預測的 UI 變化時，模型可能誤判哪些事實需要長期保存，導致折疊 UI 狀態中記錄了過時或無關的資訊。若模型在歷史折疊時過度壓縮，可能會遺失未來步驟仍需要的關鍵中繼事實，造成任務中斷；反之，若壓縮不足，則可能重新陷入提示爆炸的困境。另外，在面對需要複雜常識推理或隱含目標拆解的任務時，8B 規模的模型可能在生成適當的折疊摘要與記憶體更新策略上出現瓶頸。

## 實務應用指南

### 適用場景

1. **跨應用程式自動化流程**：例如「在購物 App 比價後，複製優惠碼到瀏覽器結帳，再回發票 App 對獎」。這類任務需要保留跨應用程式事實（如價格、優惠碼、訂單編號），MemGUI-Agent 的折疊 UI 狀態（Folded UI State）能主動將這些關鍵資訊記入記憶，避免傳統 ReAct 式提示因逐筆步驟記錄導致的資訊遺失。

2. **企業行動裝置 RPA**：業務人員需在多個內部 App（如 ERP、CRM、簽核系統）間搬運資料。長程任務平均超過 30 步，傳統基於規則的腳本難以維護。MemGUI-Agent 可透過端到端策略學習自適應的上下文策展，將已完成子任務壓縮進折疊動作歷史（Folded Action History），讓提示保持緊湊。

3. **無障礙輔助與長輩智慧手機協助**：執行「開啟設定 → 調整字體大小 → 開啟藍牙 → 連接助聽器」等長序列導引時，代理人需持續追蹤多步驟進度。ConAct 的近期步驟記錄（Recent Step Record）能讓系統清楚知道「現在做到哪」，並在發生錯誤時快速回溯。

4. **自動化軟體測試與驗證**：針對需要跨 App 的 end-to-end UI 測試（例如「註冊帳號 → 收驗證信 → 登入 → 修改個人資料」），測試腳本常因介面改版失效。MemGUI-Agent 以視覺理解為基礎，搭配主動式上下文管理，能在介面微調時仍記住持續性 UI 衍生事實（如使用者 ID），提升測試韌性。

5. **個人數位助理執行複雜指令**：例如「查詢今晚天氣 → 傳訊息給朋友建議聚餐地點 → 開啟地圖搜尋餐廳 → 建立行事曆邀請」。這類開放域長程任務要求代理人不僅執行 UI 動作，還需主動決定哪些中繼事實（如餐廳名稱、時間）值得存入工作上下文，MemGUI-Agent 將此視為一等公民動作來學習。

### 實作前置條件

**資料**：若從頭訓練，需準備具備完整 ConAct 標註的軌跡資料集，每筆軌跡需包含螢幕截圖、目標 G、以及五項輸出（推理 τ、折疊指令 ϕ、UI／記憶體動作 a、UI 觀察 o、動作意圖 ι）。論文釋出的 MemGUI-3K（2,956 筆軌跡）可直接作為監督式訓練起點；若應用於垂直領域，建議至少蒐集 500–1,000 筆高品質領域軌跡並重新標註。

**運算資源**：8B 模型的監督式微調（SFT）建議配置至少 4× A100 80GB 或同等 H100，採用 LoRA/QLoRA 可降低至 1–2 張 A100。推論階段可在單張 RTX 4090 或高階行動晶片（如具 NPU 的旗艦平台）執行，但長程任務需注意上下文欄位更新的 I/O 延遲。

**技能門檻**：團隊需熟悉多模態大型語言模型（MLLM）的微調流程（建議基於 Qwen3-VL 系列）、Android Debug Bridge（ADB）與無障礙服務（Accessibility Service）的事件擷取，以及結構化 JSON Schema 設計（用於解析 <folding>、<tool_call> 等五欄位輸出）。此外，需具備將記憶體動作（add/update/delete）對應到外部鍵值儲存的工程能力。

### 實作步驟建議

1. **環境建置與資料蒐集**：架設 Android 模擬器或實機農場，透過 ADB 與 UI Automator 錄製螢幕截圖與操作軌跡。若使用論文開源資料，直接下載 MemGUI-3K 並檢查其 ConAct 標註格式。

2. **上下文欄位工程**：實作三個結構化上下文欄位：折疊動作歷史 H（壓縮軌跡摘要）、折疊 UI 狀態 M（持續性 UI 衍生事實）、近期步驟記錄 L（最新互動細節）。設計 Fold(H_t, ϕ_t) 函式，使其能根據模型輸出的 range 與 summary 執行步驟級蒸餾或跨步抽象。

3. **擴充動作空間**：在標準 UI 動作（點擊、輸入、滑動）之外，加入記憶體動作空間 A_mem = {add, update, delete}，並實作對應的 M_t 更新邏輯。確保 <tool_call> 解析器能區分 UI 動作與記憶體動作。

4. **監督式微調**：以 Qwen3-VL-8B（或同級 MLLM）為骨幹，使用 MemGUI-3K 進行 SFT。訓練目標需同時預測五項輸出，建議對不同欄位採用均衡的損失權重，避免模型過度偏重 UI 動作而忽略折疊指令。

5. **推論管線整合**：建構單步執行迴圈：輸入 S_t = (G, H_t, M_t, L_t) + 截圖 I_t → MLLM 生成 y_t → 解析五欄位 → 執行 UI 動作或更新 M_t+1 → 組裝 L_t+1 → 遞迴進入下一步。加入超時與異常復原機制（如當折疊指令解析失敗時，fallback 為保留最近三步原始記錄）。

6. **長程評估與迭代**：在 MemGUI-Bench 或自建的長程基準測試上評估 Pass@K，同時監控平均提示長度。若出現提示爆炸，檢查折疊策略是否過於保守；若出現資訊遺失，則加強記憶體動作的監督訊號。

### 潛在風險與注意事項

- **錯誤折疊導致關鍵事實消失**：模型可能將尚須使用的跨應用程式事實摘要掉。建議在 M_t 中對高風險欄位（如價格、ID、驗證碼）設定強制保留規則，或透過驗證器檢查記憶體動作的一致性。

- **幻覺記憶與虛構 UI 事實**：8B 模型可能生成未出現在畫面上的 UI 觀察。可在推論階段加入視覺接地（visual grounding）檢查，將 <ui_observation> 與 OCR 結果比對，降低幻覺風險。

- **提示長度與延遲權衡**：雖然 ConAct 追求次線性增長，但在極長軌跡（>50 步）下 H_t 仍會累積。建議設定硬上限（如 H_t 最多保留 20 條摘要、M_t 最多 50 項記憶），並觸發額外壓縮。

- **安全性與隱私**：行動 GUI 代理人會接觸簡訊、帳號、密碼等敏感資訊。若採用雲端 MLLM，需對截圖與記憶體內容做去識別化；若部署於邊緣裝置，需確保 M_t 儲存於安全隔區（TEE）。

- **分布外泛化瓶頸**：MemGUI-8B-SFT 在 MobileWorld 等分布外基準測試表現良好，但面對全新 App 或大幅改版介面時，仍可能失敗。建議保留傳統腳本作為高風險操作（如轉帳、刪除）的人工覆核閘道。

### 與其他技術的整合建議

- **與 RAG／外部知識庫整合**：折疊 UI 狀態適合保存「當前任務相關」的事實，但對於會動態變更的業務知識（如最新商品庫存、公司政策），建議將 M_t 作為短期工作記憶，並透過 RAG 查詢長期知識庫，避免模型幻覺。

- **與傳統 RPA／Appium 互補**：對於高度重複、步驟固定的短程任務，傳統基於規則的 RPA 成本更低、延遲更小。可將 MemGUI-Agent 作為「大腦」負責決策與上下文管理，實際點擊與斷言交由 Appium 執行，提升穩定性。

- **與語音／NLU 管線銜接**：將 ASR 與意圖解析模組的輸出作為目標 G 輸入 MemGUI-Agent，並將 <action_intent> 欄位回傳給 TTS 模組作為語音回饋，建構完整的語音助理閉環。

- **與監控可觀測性平台整合**：由於 ConAct 將上下文管理視為動作，所有折疊與記憶體決策都是可記錄的結構化資料。建議將 ϕ_t 與 M_t 變化寫入結構化日誌（如 JSON Lines），方便後續離線分析與錯誤追溯。

### 給不同背景讀者的閱讀建議

**給初學者**：請把 MemGUI-Agent 想像成一位會「邊做事邊整理筆記」的數位助理。過去的代理人只會把每步經歷流水帳式抄下來，導致本子越寫越厚、重點被淹沒；本文提出的 ConAct 則讓助理主動決定「哪些步驟可以摘要成一句話」「哪些資訊必須貼到便利貼長期保留」。先理解「被動累積 vs. 主動策展」的差別，再回頭看三個上下文欄位的設計，會更容易掌握全文脈絡。

**給 AI 工程師**：請重點關注第 2 節的單步執行流程與五欄位輸出協定。實作時需特別處理 <folding> 的解析與 Fold(H_t, ϕ_t) 的狀態更新邏輯，以及記憶體動作空間 A_mem 與 UI 動作空間 A_ui 的並行分支。建議直接參考論文釋出的程式碼，確認折疊指令的 JSON Schema 與 Qwen3-VL function-calling 格式的銜接細節，並留意近期步驟記錄 L_t 的組裝順序是否正確。

**給研究人員**：本文的核心貢獻在於將上下文管理從「提示工程技巧」提升為「策略層級的可學習行為」。請深入分析 ReAct 式提示為何在長程任務中必然遭遇提示爆炸與資訊遺失，並對照 ConAct 如何透過結構化欄位與主動折疊達到次線性上下文增長。MemGUI-3K 的標註設計與 8B 模型即可超越大型 agentic workflow 的實驗結果，也值得作為輕量級端到端代理人的參考基線。

**給產品經理**：這篇論文驗證了「無需龐大代理人框架，僅靠 8B 端到端模型就能做好長程行動任務」的商業可行性。請關注兩個數字：MemGUI-8B-SFT 在 MemGUI-Bench 的開放資料 8B 最佳表現，以及零樣本應用於 Qwen3-VL-235B-Thinking 時超越 Gemini-2.5-Pro agentic workflow 的結果。這代表團隊可以根據預算選擇「邊緣輕量模型」或「雲端大模型 + ConAct」路線，且論文承諾釋出資料與模型，能顯著降低試錯成本。評估導入時，請優先盤點產品中是否存在「跨 App、超過 20 步、需記憶中繼事實」的痛點場景。
