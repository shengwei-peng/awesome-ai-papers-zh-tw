# CoHyDE：針對工具檢索之 LLM 重寫器與稠密編碼器的迭代協同訓練

## ⚡ TL;DR

解決工具檢索中口語模糊查詢與技術API目錄詞彙落差，以及對比微調編碼器與HyDE擴展互補失效之困境。
提出CoHyDE迭代協同訓練法，以目錄感知假設描述更新編碼器，並以檢索分數對齊重寫器。
於萬級ToolBench目錄，標準查詢提升2.5百分點，模糊查詢最高提升8百分點，驗證協同訓練關鍵。

## 摘要翻譯

在大型 API 目錄（API Catalog）上進行工具檢索（Tool Retrieval）是 LLM 代理（LLM Agent）的核心瓶頸：使用者查詢多為口語化（Colloquial）且經常描述不足（Underspecified），而目錄使用技術性 API 詞彙，兩者之間的落差是任何固定編碼器皆無法獨自彌合的。兩種主流訓練方法——對比式編碼器微調（Contrastive Encoder Fine-Tuning），以及搭配凍結 LLM 的 HyDE 式查詢擴展（HyDE-style Query Expansion）——從兩個相反的端點處理此問題，呈現互補失效模式（Complementary Failure Mode）：微調後的稠密編碼器（Dense Encoder）在查詢的表面形式（Surface Form）已與目錄匹配時表現出色，但在未匹配時則效能驟降；而零樣本（Zero-Shot）HyDE 對描述不足的查詢更具穩健性，然而會產生無目錄感知（Catalog-Unaware）的假設性描述（Hypothetical Description），當查詢為格式良好查詢（Well-Formed Query）時反而降低檢索效能。我們提出 CoHyDE，一種將稠密編碼器（Dense Encoder）與 LLM 重寫器（LLM Rewriter）視為單一共同演化系統（Co-Evolving System）進行訓練的迭代協同訓練（Iterative Co-Training）程序：編碼器使用 InfoNCE 在由重寫器產生的目錄風格假設性描述上重新訓練；而重寫器則透過 DPO（Direct Preference Optimization），依據編碼器的檢索分數（Retrieval Score）進行偏好對齊（Preference-Aligned），兩者在迴圈開始前皆以工具目錄進行熱啟動（Warm-Started）。在 ToolBench 目錄中一個約含一萬個工具的子集上，三輪 CoHyDE 在標準查詢上相較於最強的單一組件基線（Single-Component Baseline）提升 +2.5 百分點（Percentage Point, pp）NDCG@5，在保留的模糊查詢（Held-Out Vague Query）上提升 +6.3 百分點，在最困難的模糊層級上增益更高達 +8 百分點。消融實驗（Ablation）證實，協同訓練是關鍵要素：單獨使用任一組件在格式良好查詢（Well-Formed Query）與模糊查詢（Vague Query）上均無法達到 CoHyDE 的表現，在模糊查詢上的效能損失高達 8 百分點（pp）。

### 核心貢獻（3～5點）
- 揭示現有兩大主流方法——對比式編碼器微調與 HyDE 式查詢擴展——在工具檢索中呈現互補失效模式，並分析其各自對表面形式匹配與目錄感知生成之依賴與局限。
- 提出 CoHyDE 迭代協同訓練架構，將稠密編碼器與 LLM 重寫器視為單一共同演化系統，透過 InfoNCE 與 DPO 雙向回饋進行聯合訓練。
- 設計熱啟動與偏好對齊機制，使重寫器產生之假設性描述與編碼器之檢索分數在訓練前即具備目錄感知基礎，並於迭代中持續互相適應。
- 於 ToolBench 大規模子集驗證，在標準查詢與保留的模糊查

## 深度分析

#### 方法論解析

本文將工具檢索（Tool Retrieval）形式化為：給定 API 目錄（API Catalog）\(T = \{t_1, \dots, t_N\}\) 與使用者查詢（Query）\(q\)，透過參數化稠密編碼器（Dense Encoder）\(f_\theta: \Sigma^* \to \mathbb{R}^d\) 將查詢與工具描述映射至共享向量空間（Vector Space），再以最近鄰查詢（Nearest-Neighbor Lookup）取回前 \(k\) 個工具候選集（Candidate Set）。核心瓶頸在於使用者查詢常為口語化（Colloquial）且描述不足（Underspecified），而 API 目錄則充斥技術詞彙，導致固定編碼器難以橋接兩端語義。

作者首先精準刻畫兩種主流訓練範式的互補失效模式（Complementary Failure Mode）：
1. **對比式編碼器微調（Contrastive Encoder Fine-Tuning）**：編碼器本質上是由錨點-正樣本對（Anchor-Positive Pair）塑造出的相似度函數。當查詢為分布內（In-Distribution）且詞彙表層（Lexical Surface）與目錄重疊時，對比訊號充足；一旦表面形式（Surface Form）偏離，編碼器缺乏世界知識（World Knowledge）與推理機制（Reasoning Machinery），只能退回殘餘詞彙線索（Residual Lexical Cue），導致檢索崩潰。
2. **HyDE 式查詢擴展（HyDE-style Query Expansion）**：以凍結模型（Frozen Model）LLM 生成假設文件（Hypothetical Document）雖具推理能力，對模糊查詢（Vague Query）較穩健，但其產出的假設性描述（Hypothetical Description）為無目錄感知（Catalog-Unaware），在格式良好查詢（Well-Formed Query）上反而造成語義偏移，傷害檢索表現。

為此，CoHyDE 提出迭代協同訓練（Iterative Co-Training）架構，將 LLM 重寫器（LLM Rewriter）\(g_\psi\) 與稠密編碼器視為單一共同演化系統（Co-Evolving System）。流程分三階段循環：

1. **熱啟動（Warm-Started）**：在迭代開始前，兩端皆先以工具目錄資料預熱，使重寫器初步熟悉 API 技術詞彙，編碼器建立基礎語義空間。
2. **編碼器重訓練**：於每輪迭代中，LLM 重寫器為每個查詢生成目錄風格的假設性描述（即模擬目錄中會出現的技術文件片段，而非單純改寫查詢）。接著，稠密編碼器以 InfoNCE（InfoNCE）損失在這些合成描述上進行對比學習，且**不使用任何真實 (query, tool) 配對**。這迫使編碼器學習將「目錄感知語言」映射到正確工具嵌入（Embedding）。
3. **重寫器偏好對齊（Preference-Aligned）**：以編碼器計算出的檢索分數（Retrieval Score）作為獎勵訊號，透過 DPO（DPO, Direct Preference Optimization, 直接偏好最佳化）更新 LLM。具體而言，針對同一查詢，若某假設性描述經編碼器檢索後獲得較高 NDCG@5（NDCG@5）或相似度排序表現，則該描述被標記為「偏好（preferred）」，反之為「拒絕（rejected）」，從而讓重寫器學會產生能最大化編碼器檢索品質的文本。

此設計的關鍵在於「回饋閉環」：重寫器產出的文本品質由編碼器評分，編碼器的訓練資料又由重寫器供給。相較於 Shao et al. (2023) 以監督方式重寫使用者指令並以 (rewritten-instruction, tool) 配對重訓編碼器，CoHyDE 有三項根本差異：(i) 重寫器透過 DPO 與編碼器分數對齊，而非單純監督微調；(ii) 輸出目標為 catalog-description style 的假設性描述，而非 query-style 的改寫；(iii) 編碼器完全脫離真實查詢-工具對，僅以合成假設文件訓練，徹底解耦表面形式依賴。

#### 實驗數據解讀

實驗於 ToolBench（ToolBench）目錄的約 10k 工具子集上進行，執行三輪（three rounds）迭代協同訓練。評估指標採用 NDCG@5（NDCG@5），並區分標準查詢（standard queries）與保留的模糊查詢（held-out vague queries）。

主要結果顯示：
- **標準查詢**：CoHyDE 相輔於最強單一組件基線（Single-Component Baseline）提升 +2.5 百分點（pp, Percentage Point）。此增益雖看似溫和，卻具重要意義：它證明即使是格式良好查詢（Well-Formed Query），零樣本（Zero-Shot）HyDE 產生的無目錄感知假設文件仍會帶來雜訊，而 CoHyDE 透過偏好對齊消除了這種語義偏移，使假設性描述成為有益的查詢擴展（Query Expansion）。
- **保留的模糊查詢**：整體提升 +6.3 pp。這顯示當使用者查詢描述不足（Underspecified）時，單靠編碼器殘餘詞彙線索完全不足以橋接語義鴻溝，而經過 DPO 訓練的重寫器能注入恰當的世界知識與推理結果，再由編碼器將其對齊至目錄技術詞彙。
- **最困難的模糊層級（hardest vague tier）**：增益高達 +8 pp。這代表在極端口語化或語意高度模糊的場景下，協同訓練的邊際效益最大。

消融實驗（Ablation）進一步驗證協同訓練的必要性：
- 單獨使用編碼器（無重寫器）：在模糊查詢上損失高達 -8 pp，確認缺乏推理機制的稠密編碼器在分布外（off-distribution）查詢前極度脆弱。
- 單獨使用凍結 LLM 重寫器（即零樣本 HyDE）：在格式良好查詢上表現劣於 CoHyDE，因為其假設性描述未與目錄共同演化，仍屬無目錄感知。

數據解讀的核心結論是：CoHyDE 的增益並非兩組件表現的簡單相加，而是乘性（synergistic）的。重寫器提供「語義橋接」的推理能力，編碼器提供「詞彙對齊」的嵌入能力，兩者在迭代中互相放大。

#### 與現有研究的比較

**定位與貢獻**
在工具檢索文獻中，既有研究大致分為兩條平行路線：一是以對比損失微調稠密編碼器（如 Karpukhin et al., 2020; Xiao et al., 2024），二是以凍結 LLM 進行查詢擴展（如 HyDE、Query2doc）。CoHyDE 首次將兩端統合為單一訓練程序，填補了「生成器輸出即為檢索輸入，且編碼器即為消費者」的聯合訓練空白。

**與近期相關工作的細緻區隔**
- **Shao et al. (2023)**：雖同樣採迭代重寫與編碼器重訓，但該工作以監督方式重寫使用者指令，並以真實 (rewritten-instruction, tool) 配對訓練編碼器。CoHyDE 則以 DPO 對齊重寫器與編碼器檢索分數，且編碼器訓練完全脫離真實查詢-工具對，改以目錄風格假設文件為正樣本，從根本上去除對查詢表面形式的依賴。
- **CSQE (Lei et al., 2024)**：在測試時（test time）注入檢索到的語句以修補語料庫不對齊問題。CoHyDE 則在訓練時（training time）即透過迭代回饋解決語料庫不對齊，無需額外推論開銷。
- **PromptAgator / RaFe / LeReT**：這些方法以 RL 或 DPO 訓練重寫器，但檢索器（retriever）維持凍結。另一派研究以凍結生成器合成查詢來訓練檢索器。CoHyDE 是少數同時解凍兩端、讓兩者共同演化的框架。
- **RAG / Atlas / REPLUG / RA-DIT / Self-RAG**：這些聯合檢索-生成框架訓練生成器以產生更優的最終答案，而非優化檢索輸入。CoHyDE 的目標函數直接作用於上游（Upstream）檢索品質，而非下游生成品質。

**局限性**
1. **規模限制**：實驗僅於約 10k 工具子集驗證。對於數萬至數十萬規模的 API 目錄，迭代協同訓練的穩定性與收斂性仍待驗證。
2. **迭代成本**：三輪交替執行 LLM 的 DPO 與編碼器的 InfoNCE 重訓，運算資源顯著高於單次微調或凍結推論。
3. **收斂分析不足**：論文未深入探討共同演化系統的理論收斂條件，例如是否存在震盪（oscillation）或模式崩潰（mode collapse）風險。
4. **架構侷限**：僅探討單一向量（single-vector）稠密檢索，未與多向量（multi-vector）或稀疏-稠密混合檢索（hybrid retrieval）比較。

#### 可重現性評估

**資料集**：實驗採用 ToolBench（ToolBench），該資料集已公開釋出，具備良好的可取得性，有利於社群復現。

**程式碼與模型權重**：就本文提供的上下文而言，作者並未明確提及是否開源釋出原始碼、訓練腳本或模型權重（model weights）。這是當前可重現性的一大缺口；由於 CoHyDE 涉及 LLM 重寫器與稠密編碼器的複雜交替訓練管線，若無官方實作，獨立復現的門檻相當高。

**熱啟動與前處理**：方法要求將工具目錄透過渲染函數（rendering function）\(\phi\) 序列化為文字串，並對兩端進行熱啟動（Warm-Started）。論文未詳述熱啟動的具體步驟（如訓練步數、學習率、正樣本採樣策略），這些超參數對復現至關重要。

**訓練細節**：DPO 的 \(\beta\) 參數、InfoNCE 的溫度係數、每輪迭代中假設性描述的生成數量、偏好對的建構方式等，在提供的節錄中均未揭露。此外，DPO 訓練 LLM 與對比學習重訓編碼器皆需大量 GPU 資源，硬體需求亦未說明。

**整體評估**：在資料層面具備可重現性，但在實作層面屬於「中高度困難」。建議作者未來釋出原始碼、訓練配置檔與至少一組檢查點（checkpoint），以降低社群復現門檻。

#### 未來研究方向

1. **超大規模目錄擴展**：將 CoHyDE 推進至 100k+ 工具的完整 ToolBench 或企業級 API 目錄，研究迭代協同訓練是否仍能穩定收斂，或需引入階層式檢索（hierarchical retrieval）與負採樣優化。
2. **共同演化的理論分析**：建立數學框架分析 Co-Evolving System 的收斂條件，探討重寫器與編碼器在何種條件下會陷入震盪，以及 DPO 獎勵訊號的 Lipschitz 性質對穩定性的影響。
3. **多輪對話與上下文檢索**：現有設定假設單輪查詢。未來可將 CoHyDE 擴展至多輪對話場景，使重寫器能利用對話歷史生成更精準的假設性描述，支援對話式 LLM 代理（LLM Agent）。
4. **跨語言工具檢索**：探討使用者以非英語口語查詢、API 目錄仍為英文技術文件的場景。重寫器可學習扮演「跨語言橋接器」，而編碼器維持在目錄語義空間對齊。
5. **效率與蒸餾（Distillation）**：研究是否能在首輪或第二輪後將重寫器知識蒸餾至輕量編碼器，或將多輪協同訓練壓縮為單輪「強熱啟動」，以降低訓練與推論成本。
6. **混合檢索架構整合**：目前僅限單一向量 Dense Encoder。未來可將 CoHyDE 與稀疏檢索（如 BM25）或多向量模型（如 ColBERT）結合，讓重寫器同時優化多路召回的輸入品質。
7. **生成式索引（Generative Indexing）結合**：近期參數化工具檢索（parametric tool retrieval）將工具視為虛擬詞元（virtual tokens）嵌入 LLM 詞表。可探索 CoHyDE 與此路線的融合，例如以重寫器輔助生成工具嵌入，或以編碼器分數監督生成式索引的學習。
8. **動態目錄適應**：真實 API 目錄頻繁更新（新增、刪除、版本異動）。未來可研究增量式 CoHyDE，使系統在無需從頭重訓的情況下，透過少數迭代將新工具納入共同演化系統。
9. **可解釋性分析**：深入探討經 DPO 訓練後的 LLM 重寫器究竟學會了哪些目錄特定模式（如端點命名規則、參數型別、錯誤處理語義），並視覺化假設性描述中的詞彙遷移軌跡。
10. **端到端任務獎勵**：目前 DPO 的偏好訊號僅來自檢索分數（Retrieval Score）。未來可引入下游工具呼叫成功率作為延遲獎勵（delayed reward），直接對齊重寫器與代理的最終任務表現。

## 論文問答

**Q1：工具檢索面臨的核心瓶頸是什麼？為何現有的固定編碼器難以獨立解決？**
A：工具檢索的核心瓶頸在於使用者查詢通常以口語化、描述不足的語言呈現，而 API 目錄則使用高度專業的技術詞彙，兩者之間存在嚴重的語義與詞彙落差。固定的稠密編碼器僅能依賴訓練時見過的詞彙表層線索進行匹配，當查詢的表層形式與目錄文件不一致時，它缺乏世界知識與推理機制來橋接這道鴻溝。因此，單靠固定編碼器無法同時處理格式良好的查詢與語意模糊的查詢，導致檢索效能在真實應用場景中大幅受限。

**Q2：對比式編碼器微調與 HyDE 式查詢擴展各自存在什麼樣的互補失效模式？**
A：對比式編碼器微調在查詢的表層形式與目錄分布一致時表現優異，因為它能精準捕捉訓練資料中的語義相似度；然而一旦查詢偏離分布，例如使用口語化或模糊的表達，編碼器便會因缺乏推理能力而崩潰，只能退回到殘餘詞彙線索。相對地，零樣本 HyDE 利用大型語言模型的世界知識來擴展查詢，對模糊查詢較為穩健，但它產生的假設性描述往往與目錄的技術詞彙不一致，反而會在查詢本身已經格式良好時降低檢索表現。這兩種方法分別從編碼器端與生成端解決問題，卻在對方擅長的場景中出現對稱性的失敗，形成互補失效模式。

**Q3：為什麼需要將編碼器與重寫器視為共同演化系統來聯合訓練，而非單獨優化？**
A：單獨優化任一組件都無法同時克服詞彙落差與分布偏移的雙重挑戰：編碼器需要目錄感知的訓練訊號來學習技術語義，而重寫器則需要編碼器的回饋來調整生成內容以符合目錄風格。將兩者視為共同演化系統，能讓重寫器產生的假設性描述逐步對齊目錄的技術詞彙，同時讓編碼器在這些高品質的合成資料上持續精進其向量空間。這種迭代協同訓練打破了單一組件的能力天花板，使系統能同時處理格式良好與語意模糊的查詢，達到單一方法無法企及的綜合效能。

**Q4：CoHyDE 的核心方法論為何？請說明其迭代協同訓練的具體流程。**
A：CoHyDE 是一個迭代協同訓練程序，在每一輪中，LLM 重寫器首先為使用者查詢生成目錄風格的假設性描述，接著稠密編碼器使用 InfoNCE 對比損失在這些描述上重新訓練。隨後，重寫器透過直接偏好最佳化（DPO）進行偏好對齊，其獎勵訊號來自編碼器對生成描述的檢索分數，形成閉環回饋。這個交替更新循環會重複多輪，兩個組件在熱啟動於工具目錄的基礎上持續互相適應，逐步提升整體檢索品質並縮小使用者語言與技術詞彙之間的鴻溝。

**Q5：CoHyDE 與現有的查詢重寫或檢索器訓練方法有何關鍵差異？**
A：與 Shao 等人（2023）的方法不同，CoHyDE 的重寫器並非重寫為查詢風格，而是生成目錄描述風格的假設性文件，且編碼器的重訓練完全不使用真實的（查詢, 工具）配對。此外，現有方法如 RAG、Atlas 或 REPLUG 通常凍結檢索器或生成器其中之一，或僅訓練生成器以產生更好的最終答案而非檢索輸入；相較之下，CoHyDE 同時訓練兩個組件，並讓重寫器的輸出直接成為編碼器的檢索輸入。這種設計精準填補了過往研究中「生成檢索輸入的生成器」與「消費該輸入的編碼器」從未被聯合訓練的空白。

**Q6：為何選擇 InfoNCE 與 DPO 作為編碼器與重寫器的訓練目標？這樣的組合有何優勢？**
A：InfoNCE 是稠密檢索中標準的對比學習損失，能有效將目錄風格的假設性描述與對應工具在向量空間中拉近，同時推開負樣本，確保編碼器學到鑑別性的語義表徵。DPO 則讓重寫器能直接利用編碼器的檢索分數作為偏好獎勵，無需額外訓練獎勵模型即可穩定更新，大幅簡化了強化學習的流程。這兩者的結合使得編碼器能從高品質合成資料中學習，同時重寫器能根據編碼器的實際檢索表現進行偏好對齊，形成高效且穩定的共同演化動力。

**Q7：CoHyDE 在 ToolBench 子集上的實驗設置為何？主要評估指標是什麼？**
A：研究人員在 ToolBench 目錄中約一萬個工具的子集上驗證 CoHyDE，並以 NDCG@5 作為主要評估指標，衡量前五位檢索結果與黃金工具集合的相關性排序品質。實驗同時涵蓋標準查詢與保留的模糊查詢，後者又進一步細分為不同難度層級，以檢驗方法在語意不明確情境下的穩健性。這樣的設置能夠嚴格檢視 CoHyDE 在分布內與分布外查詢上的綜合表現，並與最強的單一組件基線進行公平比較。

**Q8：CoHyDE 相較於最強單一組件基線取得了哪些量化的效能提升？**
A：經過三輪協同訓練後，CoHyDE 在標準查詢上的 NDCG@5 提升了 2.5 個百分點，在保留的模糊查詢上更大幅提升了 6.3 個百分點。在最困難的模糊查詢層級中，增益甚至高達 8 個百分點，顯示出協同訓練對於極具挑戰性的口語化、描述不足查詢具有顯著的改善效果。這些結果證明 CoHyDE 不僅能維持在格式良好查詢上的優勢，更能有效彌補單一方法在模糊查詢上的效能缺口，實現真正的雙贏。

**Q9：消融實驗揭示了哪些關於協同訓練必要性的關鍵證據？**
A：消融實驗明確證實，單獨使用編碼器或重寫器都無法達到 CoHyDE 的整體表現，在模糊查詢上的損失最高可達 8 個百分點。這表示僅依賴對比式微調或僅依賴 HyDE 式擴展，都無法同時兼顧格式良好與語意模糊的查詢類型。因此，迭代協同訓練並非錦上添花的設計，而是讓兩個組件互相補強、克服彼此盲點的關鍵成分，缺少任何一方都會導致系統在特定查詢類型上嚴重失效。

**Q10：在實際的 LLM 代理應用場景中，CoHyDE 能解決哪些具體的痛點？**
A：在實務上，LLM 代理經常需要面對使用者以自然口語提出的模糊指令，例如「幫我處理那個檔案」或「我想看銷售數據」，這類查詢缺乏明確的 API 名稱或技術參數。CoHyDE 能將這些口語化、描述不足的查詢轉譯為符合目錄技術詞彙的假設性描述，使代理能從數萬個 API 中精準召回正確工具。這大幅降低了代理因上游檢索錯誤而採取錯誤行動的風險，提升了企業級工具編排系統的可靠性與使用者體驗。

**Q11：若將 CoHyDE 部署於企業產品環境，有哪些實務考量與潛在優勢？**
A：企業內部的 API 目錄往往規模龐大且持續擴增，傳統固定編碼器難以適應新加入的工具與不斷變化的使用者語言習慣，而 CoHyDE 的迭代協同訓練機制能讓系統隨著目錄與查詢分布的演進持續自我優化。由於兩個組件在訓練前都會以目錄資料進行熱啟動，這使得系統在面對新領域或新客戶時具備良好的初始化基礎，縮短上線前的調適時間。此外，偏好對齊機制讓重寫器的行為可透過檢索分數進行量化監控，便於維運團隊追蹤模型表現並進行版本控制。

**Q12：CoHyDE 對工具檢索與檢索增強生成（RAG）領域可能帶來什麼樣的影響？**
A：CoHyDE 開創了「檢索輸入生成器」與「稠密編碼器」聯合訓練的新範式，打破了過往 RAG 相關研究中至少凍結一個組件的慣例。這啟發未來研究可以將上游檢索器的訓練與查詢重寫模組緊密結合，不再將兩者視為獨立的流水線階段。對於動態且專業的領域（如企業軟體、醫療或法律工具目錄），這種共同演化架構提供了一條可行路徑，讓檢索系統能同時適應使用者語言與領域詞彙的雙向漂移。

**Q13：CoHyDE 目前存在哪些已知的限制或適用範圍上的邊界？**
A：本文的實驗主要聚焦於 ToolBench 中約一萬個工具的子集，雖然已具相當規模，但對於數十萬甚至上百萬級別的超大型 API 目錄，其擴展性與訓練穩定性仍需進一步驗證。此外，CoHyDE 目前針對單向量稠密檢索架構進行設計，對於多向量或稀疏-稠密混合檢索系統的適用性尚未探討。最後，迭代訓練過程涉及多次編碼器重訓與重寫器偏好對齊，其運算成本與收斂速度在資源受限的邊緣部署場景中可能構成挑戰。

**Q14：在哪些極端或特殊的查詢情境下，CoHyDE 仍可能出現失效？**
A：當使用者查詢涉及目錄中完全不存在的新興概念或領域，且重寫器無法從熱啟動階段學得的目錄知識中推導出合理對應時，系統可能產生偏離目標的假設性描述。同樣地，若查詢具有高度歧義性且對應多種功能迥異的工具，編碼器的檢索分數可能無法提供穩定的偏好訊號，導致 DPO 更新方向震盪。此外，對於需要多步推理或跨工具組合才能滿足的複雜需求，單輪的假設性描述生成可能不足以捕捉完整的意圖，進而影響最終的檢索準確率。

**Q15：未來研究可以從哪些方向延伸 CoHyDE 的架構與應用？**
A：未來研究可探索將 CoHyDE 擴展至多輪對話情境，讓重寫器能利用對話歷史逐步釐清使用者的模糊意圖，而非僅基於單輪查詢生成假設描述。另一個方向是引入線上學習機制，使系統能根據使用者點擊或代理執行結果等真實回饋進行即時偏好更新，而非僅依賴編碼器的檢索分數。最後，將協同訓練框架應用於更廣泛的檢索場景，如程式碼檢索、科學文獻檢索或跨語言檢索，也有潛力進一步驗證其通用性與穩健性。

## 實務應用指南

### 適用場景

1. **企業內部大型微服務與 SaaS 整合目錄**：當組織內部累積數千至數萬個內部 API，開發人員與非技術人員皆以口語化方式（如「我要把客戶資料同步到財務系統」）搜尋工具時，CoHyDE 可橋接日常用語與技術文件之間的語意鴻溝。
2. **開發者入口網站或 API 商城**：面對外部開發者以自然語言探索第三方服務（如搜尋「寄送驗證簡訊」），系統需在龐大且詞彙各異的 API 目錄中精準召回工具，並同時處理專業術語查詢與模糊需求。
3. **低程式碼／無程式碼平台之智慧元件推薦**：業務使用者以描述不足的白話文輸入流程需求（如「自動發通知給主管」），CoHyDE 的重寫器可將其轉譯為目錄風格的假設性描述，再由稠密編碼器對齊技術元件的嵌入。
4. **客戶服務 LLM 代理的上游工具路由**：客服場景中，使用者客訴常為模糊查詢（如「我的訂單怪怪的」），CoHyDE 可在代理呼叫後台功能前，先將口語問題改寫為目錄感知的技術描述，提升後續工具檢索的準確度。
5. **多雲或混合雲環境的跨平台服務發現**：不同雲端供應商使用迥異的技術詞彙表層，CoHyDE 的迭代協同訓練能讓重寫器與編碼器共同適應各目錄的專有名詞，減少因詞彙漂移導致的檢索失效。

### 實作前置條件

- **資料條件**：需具備結構化 API 目錄（含工具名稱、描述、參數規格），並能透過序列化函數 ϕ 將每筆工具紀錄渲染為統一文本；同時需要歷史查詢日誌或人工建構的（口語查詢, 目標工具）配對，以建立對比學習的錨點-正樣本對與 DPO 偏好對。
- **運算資源**：稠密編碼器的 InfoNCE 重新訓練需中高階 GPU（如 A100 或 L40）；LLM 重寫器的 DPO 偏好對齊需更大顯存以載入完整模型與參考模型；此外需部署支援最近鄰查詢的向量資料庫（如 Milvus、Pinecone）以承載目錄嵌入。
- **技能組合**：團隊需熟悉對比式編碼器微調（InfoNCE、in-batch negative）、LLM 微調與直接偏好最佳化（DPO）、向量檢索系統建置，並具備將結構化工具紀錄序列化為文本、以及設計目錄風格假設文件 prompt 的工程能力。

### 實作步驟建議

1. **目錄盤點與熱啟動資料建構**：將所有工具透過 ϕ 序列化為單一文本字串，建立標準化的目錄語料；同時從查詢日誌中分離「格式良好查詢」與「模糊查詢」兩大類，作為後續雙軌評估基礎。
2. **編碼器熱啟動**：以目錄內的工具描述與合成查詢對執行第一輪對比式微調，建立初始向量空間，使編碼器具備基本的目錄詞彙感知。
3. **重寫器熱啟動**：設計 few-shot prompt，使 LLM 針對口語查詢生成符合目錄風格的假設性描述（而非查詢風格），並以少量目錄範例校準輸出格式與詞彙分布。
4. **迭代協同訓練迴圈（建議 3 輪）**：
   - **生成階段**：重寫器為所有訓練查詢產生假設文件；
   - **編碼器更新**：以這些假設描述作為查詢端，透過 InfoNCE 重新訓練稠密編碼器，強化對目錄技術語言的對齊；
   - **重寫器更新**：以編碼器計算之檢索分數作為獎勵訊號，透過 DPO 對重寫器進行偏好對齊，使其傾向產生能獲得高分檢索結果的目錄風格描述。
5. **雙軌評估與監控**：分別在格式良好查詢與保留的模糊查詢上測量 NDCG@5，確認系統未落入單一組件基線的互補失效模式；若某一輪在模糊查詢上效能衰退，應檢視 DPO 偏好對是否過度偏向分布內樣本。
6. **產品化部署**：將重寫器與編碼器封裝為獨立微服務，搭配向量資料庫與關鍵字檢索後備機制上線；對常見查詢建立重寫結果快取，以降低 LLM 生成延遲。

### 潛在風險與注意事項

- **編碼器災難性遺忘**：在反覆重新訓練過程中，稠密編碼器可能遺失前幾輪建立的語意對齊。建議保留第一輪的錨點-正樣本對作為回放（replay）資料，或在 InfoNCE 中混合原始目錄描述與假設描述。
- **重寫器過度擬合編碼器偏誤**：若編碼器存在系統性偏差（如對特定詞彙過度敏感），DPO 會將此偏差放大為重寫器的生成偏好。應定期以人工標註或離線黃金標準的偏好對進行校正，避免獎勵駭取。
- **新工具冷啟動**：當 API 目錄新增工具時，協同訓練需重新收斂。建議維護一個未參與迭代、僅以目錄熱啟動的凍結編碼器作為後備，確保新工具至少具備基礎嵌入。
- **推論延遲與成本**：LLM 重寫器生成假設文件會顯著增加端對端延遲。可透過快取常見查詢的重寫結果、或對高置信度的格式良好查詢繞過重寫器直接進行編碼，以平衡效能與成本。
- **評估偏誤與過度擬合**：避免僅以分布內的格式良好查詢作為主要評估指標；必須保留獨立且具代表性的模糊查詢測試集，以真實監控系統在口語化、描述不足情境下的檢索品質。

### 與其他技術的整合建議

- **向量資料庫與最近鄰搜尋**：將 CoHyDE 產出的單向量嵌入對接 Milvus、Weaviate 或 Pinecone 等向量資料庫，利用其近似最近鄰查詢加速大規模目錄的候選集召回，並將編碼器推理與資料庫查詢解耦以獨立擴展。
- **RAG 與代理管線**：將 CoHyDE 部署為 RAG 架構的上游工具檢索層，下游銜接 ReAct 或 Self-RAG 代理。重寫器產生的假設性描述可同時作為檢索輸入與代理推理的上下文，減少代理因詞彙落差而選錯工具的情形。
- **混合檢索架構**：與稀疏檢索（如 BM25）並行運作。對於表面形式已與目錄高度重疊的格式良好查詢，可優先採用稠密編碼器；對極度模糊查詢則啟用 CoHyDE 重寫強化後的向量搜尋，最終以 Reciprocal Rank Fusion 融合兩路結果。
- **API 閘道器與可觀測性**：在 API 閘道層攔截使用者查詢，先經 CoHyDE 重寫與編碼後再決定後端路由；同時將每輪的檢索分數、重寫器輸出與使用者點擊行為接入可觀測性平台，建立持續回饋迴路以偵測目錄詞彙漂移。
- **人類回饋閉環**：將客服或開發者對檢索結果的「採用／拒絕」行為轉化為新的偏好對，定期注入 DPO 階段，使重寫器持續對齊實際業務場景中的隱性需求。

### 給不同背景讀者的閱讀建議

- **初學者**：請先建立「口語查詢與技術目錄之間存在語意鴻溝」的核心直覺，再將 CoHyDE 理解為「翻譯員（LLM 重寫器）與圖書館員（稠密編碼器）互相學習對方語言」的過程。數學推導與損失函數細節可暫時略過，建議將閱讀重心放在論文的方法論流程圖與實驗結論，特別是單一組件基線與協同訓練的效能對比。
- **AI 工程師**：請聚焦於 InfoNCE 與 DPO 交替實作的工程細節，尤其注意重寫器必須生成「目錄風格的假設性描述」而非「查詢風格改寫」的 prompt 設計差異。實作時應特別監控編碼器在重新訓練時的災難性遺忘，並參考消融實驗決定最適迭代輪數（論文建議 3 輪）。
- **研究人員**：建議深入探討作者對互補失效模式的理論刻畫，並思考「以檢索分數作為獎勵訊號」是否會在更大規模迭代中引發強化學習常見的獎勵駭取或模式崩潰。可進一步延伸此框架至多向量表徵、參數化工具檢索（parametric retrieval），或探索除 DPO 之外的其他偏好最佳化演算法在此迴路中的收斂特性。
- **產品經理**：請掌握核心商業價值——CoHyDE 同時提升格式良好查詢（+2.5 百分點 NDCG@5）與模糊查詢（+6.3 百分點）的檢索品質，尤其在描述不足的口語情境下增益顯著。評估導入成本時，需將 LLM 重寫器的推論延遲、迭代訓練的 GPU 運算開銷，以及與現有 API 目錄維護流程的銜接納入產品路線圖規劃。
