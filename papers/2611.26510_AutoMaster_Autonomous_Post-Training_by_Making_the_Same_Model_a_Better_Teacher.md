AutoMaster 的核心方法論建立在兩個相互嵌套的概念之上：**Skill-FT（技能引導微調）** 與 **自主代理迴圈（autonomous agent loop）**。這兩個機制的設計意圖在於解決一個被既有後訓練研究普遍忽略的問題——**任務成功不等於行為正確**。

**Skill-FT 的設計原理**

傳統的 SFT（監督微調）以「任務是否成功」作為軌跡篩選的唯一標準，但作者指出，成功軌跡中可能摻雜三類問題行為：(1) 無依據假設（unsupported assumptions），即模型在缺乏證據時直接做出推測；(2) 無效重複（unproductive repetition），即反覆嘗試相同動作而未調整策略；(3) 表面驗證（superficial verification），即形式上檢查結果但未實質確認正確性。這些行為即使伴隨成功，仍會被 SFT 強化並傳遞給學生模型。

Skill-FT 的對應策略是將**自然語言技能（natural-language skills）** 附加至教師模型的系統提示（system prompt）中。技能以文字形式描述「在何種情境下應如何推理或行動」，例如抑制重複嘗試、要求實質驗證、鼓勵探索替代路徑等。這種設計的關鍵優勢在於：**不改變模型權重，僅透過提示工程改變教師的行為模式**，從而使同一教師模型產生更高品質的示範軌跡。

**雙層迴圈架構**

AutoMaster 的自主訓練流程由兩個嵌套迴圈構成：

- **內層迴圈（Inner Loop）**：代理在固定的教師模型、任務集（task pool）與初始學生權重下，決定如何引導教師（技能設計）以及選擇哪些示範用於訓練（資料選擇）。此層聚焦於「產生更好的訓練資料」。
- **外層迴圈（Outer Loop）**：代理以內層選定的示範微調學生模型，並根據學生在評估基準上的分數與軌跡，決定下一輪應修訂技能、將技能應用於不同任務，或更換示範選擇策略。此層聚焦於「根據學生表現迭代改進」。

這種設計的精妙之處在於：**評估對象不是教師，而是學生**。即使技能使教師軌跡產生顯著變化，學生能否從中受益仍是未知數。AutoMaster 透過外層迴圈直接觀察學生的學習效果，避免了「教師看起來更好但學生未受益」的錯位。

**技能保留的訓練設計**

另一個值得深入分析的方法論細節是**技能指令在 SFT 期間的保留**。學生在評估時並無技能提示，但訓練時若保留技能指令，平均效能反而更高。作者提出的解釋是：技能指令保留了「行為規則與其適用情境」的對應關係，使學生能從輸入-輸出配對中學習「在何種條件下採取何種行為」，而非僅模仿表面的動作序列。這與 in-context learning 的內化機制有關——保留上下文可降低學生推斷隱含規則的負擔。

### 實作步驟建議

**步驟 1：建立任務池與評估基準**
固定一組任務集作為整個流程的「訓練任務池」，另準備獨立的「評估任務集」避免過擬合。任務需有可程式化驗證的成功條件，並建立 baseline（Vanilla SFT）作為比較基準。

**步驟 2：產生初始軌跡**
使用固定的教師模型在任務池上產生 rollouts，記錄成功與失敗軌跡。對成功軌跡進行初步分析，標記出常見的「不良行為模式」（如重複同一指令、跳過驗證步驟等）。

**步驟 3：設計候選技能**
由 LLM 代理根據軌跡分析結果，設計自然語言形式的候選技能。每個技能應：
- 明確指出要抑制的行為（如「不要在未讀取錯誤訊息前重試」）
- 明確指出要強化的行為（如「在執行破壞性指令前先列出影響範圍」）
- 附帶適用的觸發條件

**步驟 4：內迴圈——技能測試與資料選擇**
對每個候選技能，在教師 rollouts 中測試其效果：
- 比較有／無技能引導下的成功率與軌跡品質
- 選擇能改善行為且不顯著降低成功率的技能
- 從技能引導下的成功軌跡中挑選訓練資料

**步驟 5：外迴圈——微調與評估**
使用挑選出的軌跡微調學生模型，**保留技能指令於訓練輸入中**（這是論文的關鍵發現）。微調完成後，在評估任務集上評估學生表現。

**步驟 6：迭代改進**
根據學生評估結果與軌跡分析，由代理決定下一步動作：
- 修訂現有技能
- 將技能應用於其他任務類型
- 挑選不同的示範資料
- 或停止迭代

**步驟 7：部署與監控**
將最終學生模型部署，並持續監控其在真實環境中的行為模式，必要時啟動新一輪 AutoMaster 流程。

### 潛在風險與注意事項

**風險 1：技能設計引入偏見或過度約束**
LLM 代理設計的技能可能過度具體或帶有設計者的偏見，導致教師行為過於僵化。
**緩解**：保留多樣化的技能版本；在評估集中加入「未見任務」測試泛化能力；定期人工審查技能內容。

**風險 2：訓練-評估提示不匹配**
論文明確指出「移除技能指令會降低效能」，但實務中若部署時無法保留技能，需評估此差距。
**緩解**：在部署環境中盡可能保留技能上下文；若必須移除，需在訓練階段就模擬「無技能」的評估情境，並準備對應的微調策略。

**風險 3：過擬合於任務池**
若任務池太小或過於同質，學生可能只在該任務池表現良好。
**緩解**：使用多樣化的任務池；保留獨立的「未見任務」評估集；定期用真實使用者任務做 A/B 測試。

**風險 4：迭代成本失控**
AutoMaster 的雙迴圈結構可能導致每輪都需重新微調與評估，成本快速累積。
**緩解**：設定最大迭代輪數與預算上限；使用較小的評估子集做快速篩選；只在有顯著改善時才進入下一輪。

**風險 5：技能可能強化錯誤行為**
若技能設計不當，可能讓教師「更自信地犯錯」，例如技能要求「快速給出答案」反而鼓勵跳過驗證。
**緩解**：每輪迭代都需檢視技能引導下的失敗軌跡，確認技能未引入新的錯誤模式。

**風險 6：評估指標單一化**
僅以任務成功率評估可能忽略行為品質（如推理深度、工具使用合理性）。
**緩解**：結合軌跡品質評估（可由 LLM 評審或規則式檢測）；追蹤多項指標而非單一成功率。

**與測試與 CI/CD 整合**
在 Software Engineering 場景中，可將任務池與 CI pipeline 整合：每次程式碼變更自動產生新的訓練任務，並用 AutoMaster 持續改進模型對該程式碼庫的適應能力。
