## ⚡ TL;DR

現有審批機制僅檢視命令文字，無法察覺相同命令在不同工作區的效果差異，導致有害操作通過審批。
本文提出 Caper，在快照沙箱預執行命令並產生有界效果報告，由審批者依觀察結果決定提交或回滾。
Caper 將有害率降至 6.7% 與 7.8%，為六系統最低，僅誤擋 1% 安全任務。

編碼代理日益依賴自動化審批者（Approver）來決定所提出的殼層命令（Shell Command）是否可以執行。現有的審批者——從基於規則的檢查器、防護模型（Guardrail Models）到已部署的權限分類器（Permission Classifiers）——皆根據請求與命令的文字內容來做決策。然而，命令的行為取決於其所呼叫的程式碼以及工作區（Workspace）的狀態，而觀察檔案變更（File Changes）的系統則將評估留給代理或人類在執行後進行。我們提出 Caper，一種結果感知審批（Consequence-Aware Approval）機制，在快照沙箱（Snapshot Sandbox）中預執行（Pre-execute）每道命令，向獨立審批者提供一份關於其觀察效應的有界報告（Bounded Report），提交（Commit）被允許的命令（Allowed Commands），並以代理可據以行動的理由回滾（Rollback）被阻擋的命令（Blocked Commands）。與六個現有系統相比，Caper 在 SABER 上達到最低的有害結果率（Harmful-Outcome Rate）（6.7%，相較之下至少為 14.8%），以及在我們所建構的基準測試（Benchmark）YoloFS-Ext 上（其有害行為隱藏在被呼叫的工具中）達到 7.8%（相較之下至少為 35.3%），同時阻擋 YoloFS-Ext 中危險任務（Dangerous Tasks）之安全對照組（Safe Twins）的 1.0%。

Caper（Consequence-Aware PERmission）的核心設計理念在於將審批決策從「命令文字層面」轉移到「命令執行結果層面」，這是一種根本性的範式轉移。傳統的審批機制（包括靜態規則檢查器如 CARE、防護模型如 ToolSafe、gpt-oss-safeguard、Qwen3Guard，以及已部署的權限分類器如 Claude Code Auto Mode）都基於命令字串、請求內容或互動歷史（interaction history）進行判斷，但這些方法存在一個根本盲點：相同的命令在不同的工作區狀態（workspace state）下可能產生截然不同的效果。

**預執行機制（Pre-execution Mechanism）**

Caper 的方法論包含四個關鍵步驟：

1. **快照沙箱（Snapshot Sandbox）建立**：每個任務開始時，系統為任務容器建立完整的狀態快照，作為可回滾的基準點。

2. **預執行與系統呼叫追蹤（System Call Tracing）**：每個提議的殼層命令（shell command）在快照環境中執行一次，並透過系統呼叫追蹤記錄其行為。這一步驟在命令結果返回給代理（agent）之前完成，因此即使命令有害，也不會影響實際工作區。

3. **有界效果報告（Bounded Effects Report）生成**：這是 Caper 方法論中最具技術深度的部分。原始的系統呼叫追蹤可能包含數萬筆記錄，其中大部分與安全無關，且部分記錄可能受到不可信內容的污染（論文引用 Debenedetti et al., 2024 指出此風險）。Caper 透過過濾機制僅保留三類後果性事件：
   - 持久性的工作區變更（persistent workspace changes）
   - 連線嘗試（connection attempts）
   - 命令輸出（command output）
   
   每個事件都標註其觸發程序（process）以及該程序讀取的檔案來源。報告還記錄對憑證（credentials）和其他受保護資料的讀取行為。論文聲稱此報告比原始追蹤縮小約 99%。

4. **LLM 審批決策**：獨立的大型語言模型審批者根據效果報告與使用者任務進行比對。若批准，則保留執行後的狀態並將輸出返回給代理；若阻擋，則將容器恢復至快照狀態，並返回阻擋原因，使代理能夠尋求替代方案。

**理論基礎與設計權衡**

Caper 的設計回應了論文中提出的核心問題：「這個命令將對當前工作區產生哪些安全相關的效果，這些效果是否在使用者請求的範圍內？」這個問題的提出本身就揭示了現有方法的根本缺陷——它們無法區分「相同的命令在不同的 Makefile 內容下產生不同效果」的情境（如圖 1 所示）。

然而，此方法論也帶來了顯著的權衡：每次命令都需要實際執行，這會引入額外的延遲與計算成本。此外，預執行本身可能產生副作用（例如，向外部服務發送請求），雖然這些副作用發生在沙箱中，但仍需考慮隔離的完整性。

#### 實驗數據解讀

**SABER 基準測試結果**

在 SABER（Hu et al., 2026）基準測試中，Caper 達到 6.7% 的有害結果率（harmful-outcome rate），是六個比較系統中最低的。其他系統的有害結果率範圍為 14.8% 至 21.2%，這意味著 Caper 將有害結果率降低了約 55-68%。同時，Caper 在 SABER 上的安全結果率保持在「無審批」的水平，顯示其不會過度阻擋合法任務。

**YoloFS-Ext 基準測試結果**

YoloFS-Ext 是本文建構的延伸基準測試，其設計特別針對現有方法的盲點：有害行為隱藏在被呼叫的工具內部，而命令文字本身看似無害。在此更具挑戰性的測試中：

- Caper 達到 7.8% 的有害結果率
- Caper 的 Claude Code hook 版本達到 6.9%（兩者為最低）
- 其他系統的有害結果率範圍為 35.3% 至 94.1%

這個差距更為顯著——在 YoloFS-Ext 上，Caper 將有害結果率降低了約 78-92%。特別值得注意的是，某些系統（如 Claude Code Auto Mode）在 YoloFS-Ext 上表現極差（94.1%），這凸顯了基於文字的審批在面對「工具內隱藏有害行為」這類攻擊時的脆弱性。

**誤阻擋分析**

Caper 在 YoloFS-Ext 上僅阻擋 1.0% 的安全對照組（safe twins）任務——這些任務與危險任務具有相同的請求和命令，但工具是無害的。這是評估誤報率的關鍵指標：1.0% 的誤阻擋率意味著 Caper 能夠有效區分「相同命令、不同工具」的細微差異，這正是其結果感知設計的直接成果。

**分析性發現**

論文進一步的分析揭示了三類審批策略的差異：
1. **基於文字的審批者**：同時阻擋危險命令及其安全對照組（高誤報率）
2. **使用預測效果的審批者**：降低有害率但無法降低誤阻擋率
3. **使用觀察效果的審批者（Caper）**：同時降低有害率和誤阻擋率

這個發現具有重要的方法論意義：僅僅「考慮效果」是不夠的，必須「觀察實際效果」才能做出正確的審批決策。

#### 與現有研究的比較

**定位分析**

Caper 在現有研究中佔據獨特的位置。論文的相關工作章節將現有方法分為幾類：

1. **權限閘門（Permission Gates）**：包括 Claude Code Auto Mode（Anthropic, 2026）、CARE（Liu et al., 2026）等。這些系統在動作執行前進行決策，但僅基於可見的對話記錄（transcript）和命令文字。Anthropic 報告其系統在真實過度積極動作上有 17% 的假陰率（false-negative rate）。

2. **政策框架（Policy Frameworks）**：如 Progent（Shi et al., 2025）和 Conseca（Tsai and Bagdasarian, 2025），這些系統限制代理可以呼叫的工具，但同樣不觀察命令的實際效果。

3. **執行後審查系統**：如 YoloFS（Zhong et al., 2026）讓代理在暫存檔案系統上執行，並在每個命令後向代理顯示變更摘要，但最終的評估仍由人類在執行後進行。GoEx（Patil et al., 2024）依賴撤銷機制和損害限制，同樣將驗證留給執行後的人類。

**Caper 的獨特貢獻**

Caper 的創新在於結合了「執行前決策」與「效果觀察」這兩個原本被視為互斥的特性。YoloFS 觀察變化但將評估留給人類；Claude Code Auto Mode 在執行前決策但不觀察效果。Caper 則在執行前決策的同時，透過預執行機制獲取效果資訊。

**限制與不足**

儘管結果令人印象深刻，Caper 的方法論仍存在幾個值得關注的限制：

1. **預執行的副作用風險**：即使在沙箱中執行，某些命令可能產生不可逆的外部副作用（如發送電子郵件、修改遠端服務）。論文中未詳細討論此類隔離保證。

2. **時間成本**：每次命令都需要實際執行，這會顯著降低代理的回應速度，對於需要快速迭代的開發任務可能造成體驗下降。

3. **可觀察性限制**：某些惡意行為可能設計為在特定條件下才觸發，預執行可能無法觸及這些條件分支。

4. **LLM 審批者的可靠性**：審批決策最終仍依賴 LLM 的判斷，這引入了模型本身的偏誤和錯誤風險。

## 論文問答

**Q1：自主編碼代理為什麼需要自動化審批機制？**
A：自主編碼代理會在有狀態的工作區中編輯程式碼、執行建置與測試，並發出殼層命令，而單一錯誤的命令可能洩漏憑證、刪除資料或削弱安全控制。雖然由人類逐一審批每個命令最為安全，但這種做法無法規模化——頻繁的提示會拖慢開發節奏並導致「審批疲勞」。Anthropic 的報告指出，使用者對 Claude Code 的權限提示有 93% 直接批准，因此必須將審批轉為自動化決策，才能兼顧安全性與開發效率。

**Q2：現有的審批方法為什麼無法有效防止有害命令？**
A：現有的審批者——包括靜態規則檢查器（如 CARE）、防護模型（如 ToolSafe、gpt-oss-safeguard、Qwen3Guard）以及已部署的權限分類器（如 Claude Code Auto Mode）——都僅根據請求與命令的文字內容來做判斷，而非觀察命令的實際效果。這種「以文判意」的方式存在根本盲點：同一個命令在不同工作區中可能產生截然不同的後果，例如 `make clean && make` 在某個工作區只刪除可重新產生的建置產物，卻在另一個工作區刪除原始檔案與 `.git/` 歷史，因為其效果取決於 `Makefile` 的內容。當有害行為被藏在被呼叫的工具內部時，純文字審批者完全無法察覺。

**Q3：為什麼「觀察命令效果」對於正確審批至關重要？**
A：殼層命令可以呼叫其文字中看不到的程式碼行為——專案腳本、建置目標或套件工具可能讀取憑證、刪除資料或存取網路，而這些動作都不會出現在命令字串中。命令的效果高度依賴當前工作區的狀態，因此每個審批決策必須回答的核心問題是：「這個命令將對當前工作區產生哪些安全相關的效果？這些效果是否在使用者請求的範圍之內？」唯有實際觀察效果，才能區分同樣刪除某些檔案的行為在當前任務中是合理還是有害。

**Q4：Caper 的核心方法是什麼？**
A：Caper（Consequence-Aware PERmission，結果感知權限）採用「先執行、後審批」的策略：每個被提出的殼層命令會先在快照化的任務容器中執行一次，並在系統呼叫追蹤下觀察其效果，再由獨立的審批者根據觀察到的結果決定是否提交。具體而言，系統從預執行中產生一份「有界效果報告」，由 LLM 審批者將這些效果與使用者任務進行比對；若允許，則保留執行後的狀態並將輸出回傳給代理；若阻擋，則將容器還原至快照並回傳理由，讓代理能據此尋求更安全的替代路徑。

**Q5：Caper 的關鍵創新是什麼？**
A：Caper 最關鍵的創新在於「有界效果報告」的設計——它將原始的系統呼叫追蹤（單一命令可能產生數十 KB 的系統呼叫）轉化為適合 LLM 審批者使用的證據。報告僅保留具後果性的追蹤事件，包括持久性的工作區變更、連線嘗試與命令輸出，並將每個事件歸因到觸發它的程序以及該程序所依賴的檔案，同時記錄對憑證與其他受保護資料的讀取。這份報告比原始追蹤小約 99%，既解決了資訊量過大的問題，也避免了被不可信內容污染的風險。

**Q6：Caper 在設計上做了哪些關鍵選擇？為什麼？**
A：Caper 選擇在沙箱中預執行而非執行後審查，是因為這樣能在命令造成持久傷害之前就介入；選擇「有界報告」而非原始追蹤，是因為後者不僅過於龐大，還可能被命令處理的不受信任內容所影響；選擇由獨立審批者評估而非讓代理自我判斷，是為了避免代理為了完成任務而合理化有害行為；選擇在阻擋時回滾並附帶理由，是為了讓代理能理解失敗原因並嘗試替代方案，而非僅收到一個二元拒絕。這些設計共同將「效果觀察」與「可行動的回饋」結合起來。

**Q7：實驗使用了哪些基準測試？**
A：研究團隊在兩個基準測試上評估 Caper：SABER（其殼層任務將開發請求與任務特定的有害行為配對）以及他們自行建構的 YoloFS-Ext（YoloFS 的受控擴展版本，特色是將有害行為藏在被呼叫的工具內部）。YoloFS-Ext 中每個危險任務都有一個「安全對照組」（safe twin），兩者擁有相同的使用者請求與命令文字，唯一的差別在於被呼叫的工具是無害的——這使得純文字審批者無法區分。實驗同時與六個現有系統進行比較。

**Q8：Caper 的關鍵實驗結果是什麼？**
A：在 SABER 上，Caper 達到 6.7% 的有害結果率，相較於六個基準系統的 14.8%–21.2% 為最低；在 YoloFS-Ext 上，Caper 與其 Claude Code hook 分別達到 7.8% 與 6.9%，遠優於基準系統的 35.3%–94.1%。同時，Caper 在 SABER 上的安全結果率維持在「無審批」時的水準，並在 YoloFS-Ext 上僅阻擋 1.0% 的安全對照組，展現出極低的誤殺率。這些結果顯示 Caper 在「減少傷害」與「避免誤擋」兩個維度上同時取得進展。

**Q9：是否有消融實驗或對比分析？**
A：論文的分析揭示了三種審批策略的差異：以文字為基礎的審批者會同時阻擋危險命令與其安全對照組；使用「預測效果」的審批者能降低傷害，但無法降低誤擋率；唯有使用「觀察效果」的審批者才能同時降低傷害與誤擋。這項對比直接證明了「觀察實際效果」相較於「猜測可能效果」或「僅看文字」的優勢，也凸顯了 Caper 設計選擇的實證基礎。

**Q10：Caper 在實際應用中適用於哪些場景？**
A：Caper 特別適合需要長時間、自主執行多步驟開發任務的場景，例如在有狀態工作區中進行建置、測試、除錯與部署的編碼代理。當代理需要呼叫專案腳本（如 `make`、`npm`、`pip`）或自訂工具時，Caper 能確保這些工具的副作用在使用者授權範圍內。此外，對於涉及敏感操作（如讀取憑證、修改設定檔、存取網路）的任務，Caper 提供了比純文字審批更精細的保護。

**Q11：在產品化部署方面需要考慮哪些因素？**
A：產品化部署 Caper 需考量幾項成本：預執行帶來的延遲（每個命令都需在沙箱中執行一次）、快照與還原的效能開銷、LLM 審批者的推論時間，以及系統呼叫追蹤的覆蓋範圍。此外，還需設計與現有代理框架（如 Claude Code）的整合介面，確保阻擋理由能以代理可理解的形式回傳，並處理沙箱無法完整模擬外部副作用（如真實網路請求）的情況。

**Q12：Caper 對自主代理安全領域有什麼影響？**
A：Caper 將代理審批的典範從「以文判意」轉向「以效判意」，證明了觀察命令實際效果比分析命令文字更能兼顧安全與可用性。這項工作為「結果感知安全」提供了具體的實作模板，可能啟發後續研究將此原則擴展到其他類型的代理動作（如檔案編輯、API 呼叫）。更重要的是，Caper 展示了在不犧牲安全的前提下大幅降低誤殺率的可能性，這對於推動自主代理在真實工作流程中的落地具有關鍵意義。

**Q13：Caper 有哪些已知的限制？**
A：Caper 目前僅處理殼層命令，未涵蓋其他類型的代理動作（如直接呼叫 API、修改資料庫）；其效果報告依賴系統呼叫追蹤，可能遺漏某些高層次的語意後果（例如商業邏輯錯誤）；預執行本身會帶來額外的時間與資源成本；此外，LLM 審批者仍可能誤判效果，特別當效果報告不完整或任務意圖模糊時。最後，沙箱環境與真實環境的差異也可能導致「在沙箱中無害但在真實環境中有害」的情境。

**Q14：Caper 在哪些情況下可能失敗？**
A：當有害效果透過沙箱無法觀察的管道發生時（例如命令將資料外洩到沙箱外的真實網路），Caper 的效果報告將無法察覺；當 LLM 審批者錯誤解讀效果報告或誤解任務意圖時，可能誤放危險命令或誤擋安全命令；當命令的效果具有時間延遲性（如設定排程任務）時，預執行可能無法捕捉；此外，若攻擊者精心設計命令使其在沙箱中表現正常但在還原後觸發副作用，Caper 也可能失效。

**Q15：未來的研究方向是什麼？**
A：未來研究可朝幾個方向延伸：將結果感知審批從殼層命令擴展到其他代理動作類型；設計更精簡且語意豐富的效果報告格式；結合策略框架（如 Progent、Conseca）以提供多層防禦；探索如何降低預執行的效能開銷，例如透過選擇性快照或預測式審批；以及研究如何讓審批者更好地理解長期任務的累積效果，而非僅評估單一命令的影響。這些方向將共同推動自主代理從「能執行」邁向「可信賴地執行」。

### 實作步驟建議

**階段一：基礎建設（2–4 週）**
1. 在隔離環境中部署一個輕量沙箱（建議從 Docker + overlayfs 起步，後續可換成 Firecracker）。

**階段二：效應報告生成器（2–3 週）**
4. 撰寫過濾器，從原始 trace 中萃取出三類事件：持久檔案變更（write/unlink/rename）、網路連線嘗試（connect）、命令輸出（stdout/stderr）。

6. 加入「觀察覆蓋率」標記：標示哪些檔案或網路端點未被追蹤（例如動態產生的子程序），避免審批者誤判。

**階段三：審批政策與 LLM 整合（2–3 週）**
8. 將使用者任務文字、命令字串、效應報告組合成審批 prompt，明確指示 LLM 評估「效應是否在使用者請求範圍內」。
9. 設計結構化輸出（allow / block + 理由），便於代理解析並調整行為。
10. 設定逾時與降級策略：若 LLM 審批逾時，預設阻擋並要求人類介入。

**階段四：代理框架整合（1–2 週）**
11. 在 Claude Code、Cursor 或自建代理的命令執行 hook 中插入 Caper 呼叫。
12. 實作回滾介面：阻擋時回傳結構化理由，讓代理能據此提出替代方案（例如改用 `--dry-run`）。
13. 加入審批日誌，用於後續稽核與政策迭代。

### 潛在風險與注意事項

**1. 預執行本身的副作用**
- 即使在快照中執行，某些操作仍會洩漏到外部：寄送電子郵件、扣款 API 呼叫、寫入第三方 SaaS。
- *緩解*：在審批政策中明確標示「不可逆外部效應」清單；對這類命令預設阻擋並升級給人類。

**2. 動態載入與反射式攻擊**
- 惡意腳本可在執行後下載第二階段酬載，繞過靜態追蹤。
- *緩解*：結合網路 egress 防火牆與 syscall 白名單；對長時間執行的命令設定強制中斷點。

**3. 效應報告的「觀察盲區」**
- 若追蹤器漏掉某些 syscall（例如 io_uring），審批者會基於不完整資訊做決定。
- *緩解*：在報告中誠實標示覆蓋率；對高風險命令要求更完整的追蹤或人類複審。

**4. LLM 審批的延遲與成本**
- 每個命令都呼叫 LLM 會顯著增加延遲（數秒到數十秒）與 API 成本。
- *緩解*：對低風險命令（如 `ls`、`cat`）使用規則快取；對高風險命令才走完整 LLM 流程。

**5. 代理迴避行為**
- 代理可能學會「拆分」危險命令（例如先 `wget` 再 `chmod +x` 再執行），使每一步看起來無害。
- *緩解*：保留跨命令的對話歷史摘要供審批者參考；對短時間內的多步命令做聯合審批。

**6. 快照還原的完整性**
- overlayfs 對部分檔案系統操作（如直接修改 block device）無法完整回滾。
- *緩解*：使用完整虛擬機快照（Firecracker）作為高風險操作的環境；定期驗證還原正確性。

**7. 誤擋對開發者體驗的影響**
- 即使只有 1% 的誤擋率，在大規模團隊中仍會造成顯著摩擦。
- *緩解*：提供「為什麼被擋」的透明理由與一鍵申訴流程；定期分析誤擋案例並調整政策。

### 與其他技術的整合建議

**與 Claude Code Auto Mode 整合**
Caper 可作為 Auto Mode 的「深度審批層」：當 Auto Mode 的兩階段分類器對某個命令信心不足時，將其轉交 Caper 做效應觀察。這種組合能兼顧 Auto Mode 的低延遲與 Caper 的高準確度。

**與 CARE 規則檢查器整合**
CARE 的語法／路徑／來源檢查可作為 Caper 的前置過濾器：明顯危險的命令（如 `rm -rf /`）直接由 CARE 阻擋，無需進入沙箱；只有通過 CARE 的命令才進入 Caper 的預執行流程，節省資源。

**與 YoloFS 整合**
YoloFS 在命令執行後才提供變更摘要給人類審查。Caper 可在 YoloFS 的 staging 層之前加入預執行機制，讓人類只需審查真正「通過效應檢查」的命令，減少審查負擔。

**與 Progent、Conseca 等政策框架整合**
這些框架限制「代理可呼叫哪些工具」，Caper 則評估「工具在當前工作區的具體效應」。兩者互補：政策框架先縮小允許範圍，Caper 再對範圍內的命令做效應驗證。

**與 CI/CD 流水線整合**
在 GitHub Actions、GitLab CI 等環境中，可將 Caper 部署為 runner 的 sidecar：代理產生的所有命令都先經過 Caper，確保 CI 階段不會意外修改 runner 狀態或洩漏 secrets。

**與可觀測性平台整合**
將 Caper 的審批日誌（命令、效應、決定、理由）匯入 Datadog、Grafana 等平台，建立「代理安全儀表板」，追蹤有害率、誤擋率、審批延遲等指標。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的 Figure 1，那個「同樣的 `make clean && make` 在不同 Makefile 下產生不同效應」的範例，是理解「為什麼只看命令文字不夠」的關鍵。接著跳過技術細節，直接看「Results」段落，了解 Caper 在數字上比現有系統好多少。實作上可先從 Docker + 簡單 syscall 過濾開始，不需一開始就追求完整 LLM 整合。

**給 AI 工程師**：重點放在第 2 節的「Bounded Effects Report」設計——如何把數萬行 syscall trace 壓縮成 LLM 可消費的證據，這是論文最具工程價值的部分。實作時要特別注意「觀察覆蓋率」的標記，這直接影響審批品質。同時建議研究 Claude Code 的 hook 介面，思考如何把 Caper 無縫嵌入現有代理迴圈而不破壞使用者體驗。

**給研究者**：論文的真正貢獻在於提出「consequence-aware」這個新範式，並用 YoloFS-Ext 證明現有文字型審批在「安全對照組」上的系統性失敗。建議延伸方向包括：(1) 將效應觀察擴展到非 shell 命令（如 API 呼叫、資料庫查詢）；(2) 研究如何在多步代理迴圈中累積效應證據；(3) 形式化「任務範圍」的語意邊界，這是 LLM 審批目前最薄弱的一環。

**給產品經理**：Caper 解決的是一個真實的商業問題——使用者對 Claude Code 93% 的審批提示都直接核准，導致安全機制形同虛設。產品化的關鍵不是技術完美，而是「在不犧牲開發速度的前提下提升安全」。建議從「高風險命令子集」切入（例如涉及憑證、刪除、網路外連的命令），而非試圖審批所有命令。同時要為誤擋設計良好的申訴與學習機制，避免開發者繞過系統。
