## ⚡ TL;DR

現有手機代理基準缺乏個人化，難以評估跨App的個人資料推理。

## 摘要翻譯

一個有用的手機代理程式必須具備個人智慧化能力。它應針對真實存於裝置上的使用者身分、歷史紀錄與偏好設定進行推理，而非僅僅在非個人化沙盒中遵循孤立指令。現有的行動代理程式基準測試缺乏這類個人化特性。我們提出 iOSWorld，這是第一個以持續性使用者身分為核心建構的互動式原生 iOS 模擬器基準測試，涵蓋 26 款專門建置的 iOS 應用程式。這些應用程式包含相互關聯的資料，例如交易紀錄、訊息、旅遊紀錄、社交關係與財務活動。iOSWorld 包含 133 項任務，分為三個難度遞增的類別。單一應用程式任務（27 項）測試單一應用程式，多應用程式任務（60 項）橫跨 2 至 8 個應用程式，記憶與個人化任務（46 項）則要求代理程式從個人資料中推論模式。我們在純視覺與特權視覺+XML 兩種設定下，評估前沿模型與開源電腦使用模型。最佳配置整體準確率達到 52%，但在多應用程式任務上僅為 37%。特權視覺+XML 存取權限可將前沿模型提升高達 26 百分點，而較小的模型則無法從額外的輔助功能樹輸入中獲益。我們將 iOSWorld 作為開源基準測試釋出，包含所有應用程式、種子資料、任務、評分標準與評估程式碼。

### 核心貢獻（3～5點）
- 提出 iOSWorld，首個以持續性使用者身分為核心、涵蓋 26 款專門建置應用程式的互動式原生 iOS 模擬器基準測試。
- 設計 133 項難度遞增的任務，涵蓋單一應用程式、多應用程式（橫跨 2–8 個 App）及記憶與個人化三大類別。
- 在純視覺與特權視覺+XML 兩種輸入設定下，系統性評估前沿模型與開源電腦使用模型的表現。
- 發現特權視覺+XML 存取權限可顯著提升前沿模型表現（最高達 26 百分點），但對較小模型無明顯助益。
- 完整開源釋出基準測試，包含所有應用程式、種子資料、任務、評分標準與評估程式碼。

### 適合對象
從事數位代理程式、行動裝置人工智慧、電腦使用模型與人機互動領域的研究人員與開發者；特別適合關注跨應用程式連續性、個人化推理與視覺語言模型在真實手機環境應用之讀者。

## 深度分析

#### 方法論解析

iOSWorld 將環境形式化為部分可觀察馬可夫決策過程（Partially Observable Markov Decision Process, POMDP），以四元組 \(E = (S, A, \Omega, T)\) 描述，其中狀態轉移函數 \(T\) 為確定性。觀測空間（observation space）設計了兩種模態：vision-only（純視覺）與 privileged vision+XML（特權視覺+XML）。前者僅提供螢幕截圖（解析度縮放至 702×1526），模擬無特權部署情境下 phone agent（手機代理程式）僅能取得畫面資訊的限制；後者則透過 Apple XCUITest 框架額外抽取 accessibility-tree input（輔助功能樹輸入），以結構化 XML 補充介面層級與元素屬性，用於分離視覺定位（visual grounding）、推理與特權存取對任務表現的貢獻。

本研究的核心方法論突破在於建立 persistent user identity（持續性使用者身分）。團隊為單一 persona（使用者角色）Jordan Avery 從頭開發 26 款 purpose-built applications（專門建置的應用程式），對應真實生活類比（如 Apple Clock、WhatsApp、Chase、Uber、DoorDash 等），橫跨 10 個生活領域。這些 native iOS apps（原生 iOS 應用程式）並非孤立運作，而是透過 connected data（相互關聯的資料）形成 cross-app continuity（跨應用程式連續性）：同一組聯絡人同時存在於通訊、支付與郵件 App；food order（餐點訂單）會在銀行 App 產生 bank charge（銀行扣款），並在郵件 App 觸發 receipt email（收據電子郵件）；upcoming flight（即將到來的航班）與 hotel booking（飯店預訂）及 confirmation emails（確認電子郵件）跨 App 連動。Mail 更作為資料樞紐（hub），以邊權重呈現共享資料點數量。這種設計刻意打破傳統 benchmark（基準測試）使用的 impersonal sandbox（非個人化沙盒），要求 agent 必須在真實使用者數位軌跡上運作。

任務設計分為三個遞增難度類別：single-app tasks（單一應用程式任務，27 題）測試單一 App 內的基礎操作；multi-app tasks（多應用程式任務，60 題）需橫跨 2 至 8 個 App 傳遞與整合資訊；memory and personalization tasks（記憶與個人化任務，46 題）則不提供明確查找位置，要求 agent 從 in-app data（應用程式內資料）發掘 implicit patterns（隱含模式），例如推論最常用通勤路線或消費偏好。評估採用 LLM-as-a-judge 管線，並與人類標註者驗證達到 κ=0.77 的一致性。此外，團隊提供 schema（綱要）以標準化新增任務與植入 seeded data（種子資料）的流程，並透過 AWS EC2 託管 Mac 實例（AWS-runner）解決非 Mac 研究者的執行門檻。

#### 實驗數據解讀

研究評估五個 frontier models（前沿模型）與一個 open-source computer-use models（開源電腦使用模型）Qwen3.5 35B-A3B。整體（overall）最佳配置達到 52% 準確率，但類別間落差極大：single-app tasks（單一應用程式任務）82%、memory and personalization tasks（記憶與個人化任務）54%、multi-app tasks（多應用程式任務）僅 37%。這顯示低階 GUI 互動已部分解決，但跨 App 資訊整合與長期規劃仍是瓶頸。

觀測模態的比較揭示關鍵能力門檻：privileged vision+XML（特權視覺+XML）相較於 vision-only（純視覺）可提升強大前沿模型最多 26 percentage points（百分點），顯示 accessibility-tree input（輔助功能樹輸入）能顯著降低視覺解析負擔並強化結構化推理。然而，較小的模型並未從額外 XML 輸入中獲益，推測其無法有效解析或利用結構化資訊，反而可能因上下文長度增加而產生雜訊。這暗示結構化輔助資訊的價值僅在模型具備足夠理解能力時才能兌現。

記憶與個人化任務達到 54%，說明模型具備基礎的個人資料推理能力，能在單一 App 或有限範圍內從 user history（使用者歷史紀錄）與 user preferences（使用者偏好設定）歸納規律。但 multi-app tasks（多應用程式任務）的低表現凸顯 cross-app continuity（跨應用程式連續性）的挑戰：agent 不僅需記憶先前 App 中的 financial records（財務紀錄）、travel records（旅遊紀錄）或 social relationships（社交關係），還需在正確時機切換 app states（應用程式狀態）以完成目標。82% 與 37% 之間的巨大落差表明，現有 digital agents（數位代理程式）在「執行單步操作」與「協調多應用程式工作流」之間存在明顯能力斷層。

#### 與現有研究的比較

相較於 AndroidWorld、MobileWorld、AndroidLab 等既有的互動式行動基準測試，iOSWorld 是首個針對 native iOS（原生 iOS）的互動式模擬器基準測試。iOS 與 Android 在 UI 框架、導覽模式與輔助功能基礎建設上存在本質差異：Android 可透過 UIAutomator 輕易取得無障礙資訊，而 iOS 的封閉性使第三方工具必須依賴 XCUITest 與 Mac/Xcode 環境才能取得 privileged access（特權存取）。此外，iOS 擁有超過 25 億活躍裝置（active devices）與 58–60% 的美國行動作業系統使用率（OS usage），卻長期缺乏專屬的互動式評測環境。

現有桌面或網頁基準測試（如 OSWorld、WebArena、VisualWebArena）雖評估 computer-use models（電腦使用模型），但多數處於 impersonal sandbox（非個人化沙盒），缺乏 persistent user identity（持續性使用者身分）與跨應用程式資料連貫性。作者刻意排除以 browser access（瀏覽器存取權限）為中心的網頁任務，因 web agents（網頁代理程式）已有充分評測管道。iOSWorld 填補了「個人化」缺口，要求 agent 理解使用者的 social connections（社交連結）、transactions（交易紀錄）與 financial activity（財務活動），而非僅執行 isolated instructions（孤立指令）。

然而，本研究也存在限制：26 款 App 皆為 purpose-built applications（專門建置的應用程式），而非真實 App Store 應用，可能簡化了真實世界的介面雜訊與異常處理；目前僅使用單一 persona（使用者角色）Jordan Avery，資料分布與人口統計多樣性不足；此外，privileged vision+XML（特權視覺+XML）設定需要特定硬體與開發者權限，與真實裝置端部署情境存在落差。Ferret-UI 等模型雖支援 iOS 介面理解，但並未提供如 iOSWorld 般具備 connected data（相互關聯的資料）的動態評測環境。

#### 可重現性評估

iOSWorld 在可重現性方面表現優異。研究團隊開源所有 purpose-built applications（專門建置的應用程式）、seeded data（種子資料）、133 道 tasks（任務）、rubrics（評分標準）與 evaluation code（評估程式碼），並提供 GitHub 倉庫與官方網站。針對 iOS 模擬器需依賴 Mac 硬體的門檻，作者提供 AWS runner（EC2 託管 Mac 實例），使無 Mac 的研究者亦能執行 benchmark（基準測試），這對於擴大研究社群參與至關重要。

此外，團隊釋出 schema（綱要）以標準化新增任務與植入個人化資料的方式，有利社群擴充新任務與使用者情境。不過，要重現 privileged vision+XML（特權視覺+XML）設定仍需 Mac 與 Xcode 環境以執行 XCUITest，且模擬器中的 app states（應用程式狀態）與真實裝置可能存在細微差異（如動畫延遲、背景程序限制）。整體而言，其開源程度、詳盡的種子資料與雲端執行方案大幅降低了進入門檻，為後續研究提供了堅實基礎。

#### 未來研究方向

首先，multi-app tasks（多應用程式任務）整體準確率僅 37%，顯示未來研究應優先強化跨應用程式規劃與長期記憶機制，例如透過顯式記憶模組或圖結構追蹤使用者的 financial activity（財務活動）與 social connections（社交連結），以提升 cross-app continuity（跨應用程式連續性）的推理能力。其次，目前僅基於單一 persona（使用者角色），後續可擴充至多個使用者角色與人口群體，測試模型對不同 user preferences（使用者偏好設定）與 user history（使用者歷史紀錄）的泛化能力，避免過度擬合特定資料分布。

第三，將環境從 purpose-built applications（專門建置的應用程式）遷移至真實 App Store 應用，將引入更複雜的視覺雜訊、動態廣告與非預期彈出視窗，挑戰 vision-only（純視覺）模型的穩健性。第四，由於較小模型無法從 accessibility-tree input（輔助功能樹輸入）獲益，未來可探索針對 iOS 介面結構的輕量模型蒸餾或預訓練策略，使 open-source computer-use models（開源電腦使用模型）在無特權設定下逼近 frontier models（前沿模型）表現。

最後，privacy-preserving personalization（隱私保護個人化）與 on-device inference（裝置端推理）是實際部署 phone agent（手機代理程式）的關鍵；如何在不上傳敏感 transactions（交易紀錄）與 travel records（旅遊紀錄）至雲端的前提下，實現 personally intelligent（個人智慧化）推理，將是學術與產業界必須共同面對的課題。此外，發展動態任務生成與即時資料更新機制，使 benchmark（基準測試）能反映真實使用者不斷演變的數位生活，亦是維持評測效度的重要方向。

## 論文問答

**Q1：iOSWorld 旨在解決現有手機代理程式基準測試中的什麼核心問題？**
A：現有的行動代理程式基準測試大多在缺乏個人化資料的沙盒環境中進行，無法評估代理程式理解使用者身分、歷史與偏好的能力。iOSWorld 針對這項缺口，提出「個人智慧化」的評估維度，要求代理程式必須能夠推理跨應用程式的持續性使用者身分與相互關聯的個人資料。這使得評估更貼近真實世界中使用者的數位生活樣貌，而非僅僅執行孤立的指令。

**Q2：為何現有的基準測試無法有效評估「個人智慧化」的代理程式？**
A：現有的互動式手機代理程式基準測試主要針對 Android 平台，且幾乎不在原生 iOS 環境中進行評估；更重要的是，這些測試未在應用程式中植入持續性使用者身分，也缺乏跨應用程式連續性。代理程式在這些非個人化沙盒中僅需遵循明確的孤立指令，無需理解使用者的交易紀錄、社交關係或旅遊紀錄等分散於各 App 的資料。因此，即使代理程式能正確點擊設定畫面的按鈕，也無法證明它具備尋找主人最常通勤路線等真正實用的個人化能力。

**Q3：為什麼在原生 iOS 環境上評估個人智慧化代理程式特別重要？**
A：iOS 擁有超過 25 億台活躍裝置，在美國行動作業系統使用率中佔近六成，其使用者介面框架、導覽模式與輔助功能基礎設施均與 Android 有顯著差異。現有網頁代理程式基準測試已相對成熟，但原生 iOS 應用程式中蘊含的財務活動、訊息與社交連結等個人資料，需要專門的互動式原生 iOS 模擬器基準測試才能妥善評估。建立這樣的基準有助於推動能真正理解使用者數位生活的手機代理程式發展，填補當前研究與真實應用之間的重大落差。

**Q4：iOSWorld 的核心方法論是什麼？**
A：研究團隊從頭建置了 26 款專門建置的原生 iOS 應用程式，並為單一使用者角色 Jordan Avery 植入相互關聯的種子資料，橫跨交易、訊息、旅遊與財務紀錄等生活領域。整個環境被建模為部分可觀察馬可夫決策過程，代理程式在每個時間步驟接收觀察並執行動作，以完成 133 項涵蓋單一應用程式、多應用程式與記憶個人化的任務。這種設計確保資料在 App 之間具備一致性與連續性，從而建立第一個以持續性使用者身分為核心的動態 iOS 評估平台。

**Q5：相較於先前研究，iOSWorld 的關鍵創新為何？**
A：iOSWorld 是首個以持續性使用者身分為核心、橫跨 26 款原生應用程式且包含相互關聯個人資料的互動式 iOS 模擬器基準測試。不同於既有基準僅評估代理程式在單一應用程式或孤立網頁中的表現，本研究特別設計了記憶與個人化任務，要求代理程式從應用程式內資料中自行發現隱含模式，而非僅依賴明確指令。這種跨應用程式連續性與個人資料推理的結合，重新定義了評估手機代理程式實用價值的標準。

**Q6：作者為何選擇自行建置專門的應用程式，並排除以網頁瀏覽為中心的任務？**
A：自行建置 26 款應用程式能確保所有 App 共享一致的資料綱要與相互關聯的種子資料，使同一筆交易能在銀行、電子郵件與購物 App 中呈現一致的紀錄，這在現有第三方應用程式中難以控制。排除網頁瀏覽任務則是因為網頁代理程式已有成熟的基準測試，且具備瀏覽器存取權限的手機代理程式可直接在那些平台接受評估。作者希望將研究焦點放在原生 iOS 應用程式及其所蘊含的個人資料推理能力上，而非重複評估已充分探索的網頁操作能力。

**Q7：iOSWorld 評估了哪些模型與觀察設定？**
A：研究團隊評估了五款前沿模型以及一個開源電腦使用模型基線 Qwen3.5 35B-A3B，並在純視覺與特權視覺+XML 兩種觀察模態下進行比較。純視覺設定僅提供螢幕截圖，模擬部署環境中無特權資訊的代理程式；特權視覺+XML 設定則額外提供透過 XCUITest 框架取得的輔助功能樹輸入，以探討結構化資訊對模型表現的影響。這樣的設計能夠區分視覺定位、推理能力與特權存取所帶來的效益，為不同部署情境提供參考依據。

**Q8：實驗中的關鍵結果為何？**
A：表現最佳的設定在整體準確率上達到 52%，但在單一應用程式任務中可達 82%，記憶與個人化任務為 54%，而多應用程式任務僅有 37%，顯示跨 App 推理仍是重大挑戰。特權視覺+XML 的輔助功能樹輸入能為較強的前沿模型帶來高達 26 個百分點的提升，然而較小的模型卻無法從額外的結構化資訊中獲得相同增益。這項結果暗示模型必須具備足夠的基礎能力，才能有效利用 XML 結構化輸入來改善視覺定位與決策品質。

**Q9：純視覺與特權視覺+XML 的比較揭示了什麼樣的分析洞見？**
A：這項比較成功區隔了視覺定位、高階推理與特權結構化存取三者對代理程式表現的貢獻，顯示單靠螢幕畫面不足以應對複雜的跨應用程式任務。實驗發現只有具備強大基礎能力的前沿模型能將輔助功能樹輸入轉化為顯著的性能提升，而規模較小的開源模型無法有效解析或利用這些 XML 資訊。此外，多應用程式任務的準確率明顯低於其他類別，證明在缺乏明確指示下，於 2 至 8 個 App 之間傳遞資訊並維持跨應用程式連續性，是目前代理程式最薄弱的環節。

**Q10：iOSWorld 能夠評估哪些貼近真實生活的實用情境？**
A：iOSWorld 能評估像是「根據過往訂單與電子郵件收據追蹤一筆餐點訂單的銀行扣款」、「比對即將到來的航班與飯店預訂確認信」或「從訊息與社交連結中推斷最常聯絡的對象」等真實個人助理情境。這些任務要求代理程式不僅能操作單一應用程式，還必須在多個 App 之間建立資料關聯，並從使用者的歷史紀錄中歸納出個人化偏好。相較於傳統基準測試中的機械式點擊，這類評估更能反映使用者期待手機代理程式在日常生活中提供的實際價值。

**Q11：這項基準測試對手機代理程式的產品化與部署提出了哪些考量？**
A：由於 iOS 是封閉源碼系統，最豐富的結構化使用者介面資料需透過 Apple 的 XCUITest 框架取得，而這要求代理程式必須在搭載 Xcode 的 Mac 環境中執行，與真實世界中多數使用者裝置的運行條件不同。因此，實際部署的代理程式很可能只能依賴純視覺輸入，但研究顯示這會使整體準確率顯著下降，特別是在多應用程式任務中。產品團隊必須在特權結構化存取帶來的準確率提升，與大規模部署時的技術可行性及平台限制之間做出權衡。

**Q12：iOSWorld 可能對行動代理程式與個人 AI 領域帶來什麼影響？**
A：iOSWorld 為「個人智慧化」建立了可量化的評估標準，將推動研究社群從單純的介面操作轉向更深層的使用者意圖理解與跨應用程式資料推理。由於研究團隊開源了所有應用程式、種子資料、任務、評分標準與評估程式碼，並提供 AWS 執行環境，這大幅降低了非 Mac 研究者的參與門檻，有助於加速相關技術的迭代。此外，實驗結果凸顯了前沿模型與實際可用產品之間仍存在顯著落差，特別是在多應用程式任務上，這將激勵後續研究針對記憶機制與長期個人化建模提出創新架構。

**Q13：iOSWorld 有哪些已知的限制？**
A：目前的基準僅圍繞單一使用者角色 Jordan Avery 建置，雖然涵蓋 10 個生活領域，但使用者樣貌的單一性可能無法完全捕捉不同族群、文化或行為模式的多樣性。此外，26 款應用程式皆為研究團隊專門建置，而非真實 App Store 中的第三方應用程式，其介面複雜度與資料雜訊可能低於實際商業軟體。同時，評估環境基於 iOS 模擬器而非實體裝置，在執行效能、感測器互動與真實網路延遲等方面仍存在一定程度的簡化。

**Q14：從失敗案例中可以看出代理程式在哪些方面的能力明顯不足？**
A：多應用程式任務僅 37% 的準確率顯示，代理程式在橫跨多個 App 傳遞資訊、維持任務脈絡與處理跨應用程式連續性方面存在嚴重缺陷，經常無法正確串聯不同應用程式內的相關紀錄。在記憶與個人化任務中，代理程式也難以從分散的應用程式內資料中歸納出隱含模式，例如推斷使用者的週期性偏好或社交習慣。此外，較小規模的模型即使獲得特權結構化輸入，也無法有效降低錯誤率，顯示基礎推理與視覺定位能力的不足無法單靠額外資訊彌補。

**Q15：這項研究指出了哪些未來方向？**
A：未來研究可朝向擴充更多元的使用者角色與真實 App Store 應用程式發展，以提升基準測試對真實世界複雜度的覆蓋率，並評估代理程式在實體裝置上的表現。針對多應用程式任務的低落準確率，社群需要開發更強大的長期記憶機制與跨應用程式規劃演算法，讓代理程式能主動維護與更新使用者的個人知識圖譜。另一方面，如何讓較小的開源模型也能有效利用輔助功能樹輸入，或設計無需特權存取即可達到相近表現的視覺定位技術，將是縮小前沿研究與實際部署落差的重要課題。

## 實務應用指南

### 適用場景

**跨應用程式個人生活助理**  
建構能同時讀取行事曆、郵件、通訊與財務 App 的代理程式，自動完成「查詢下週出差航班、比對飯店預訂確認信、並於行事曆建立行程」等橫跨 2–8 個應用程式的多步驟任務，而非僅在單一 App 內執行孤立指令。

**財務與消費紀錄整合代理**  
利用相互關聯的交易紀錄、收據電子郵件與銀行扣款資料，讓代理程式自動對帳、標記異常消費或產生月度支出報告。此場景特別適合需要從隱含模式（如常用通勤路線或週期性訂閱）中進行推理的記憶與個人化任務。

**企業內部 iOS 裝置流程自動化**  
針對業務人員或外勤工作者，部署能在原生 iOS 環境中自動填報表單、同步客戶通訊錄至 CRM，並於多個企業 App 間搬運資料的代理程式。透過持續性使用者身分確保跨 App 的客戶資料連續性。

**無障礙輔助與長照支援**  
結合特權視覺+XML（輔助功能樹輸入）為視障或高齡使用者提供跨 App 導航，例如自動讀取即時訊息、於銀行 App 確認轉帳對象（透過通訊錄比對），並以語音回饋操作結果。

**個人化旅遊與本地服務協調**  
代理程式根據使用者歷史偏好（如過往餐點訂單、旅遊紀錄、社交關係），自動於美食外送、餐廳訂位與共乘 App 間協調，完成「預訂晚餐並同時安排前往餐廳的 CityRide」等需要推論個人偏好的複合任務。

### 實作前置條件

**資料準備**  
需預先建立使用者角色（Persona）與跨應用程式的種子資料綱要（Schema），包含聯絡人、交易紀錄、旅遊紀錄、財務活動與社交關係，並確保這些相互關聯的資料在不同 App 間保持一致（例如同一筆餐點訂單需同時產生銀行扣款與收據電子郵件）。

**運算資源**  
由於 iOS 封閉生態特性，開發與測試需 macOS 環境（具備 Xcode 以使用 XCUITest 框架提取輔助功能樹）。若團隊無 Mac 硬體，可採用 AWS EC2 Mac 實例作為執行環境。模型推理端則需準備具備多模態能力的伺服器或 API（前沿模型或開源電腦使用模型如 Qwen3.5）。

**技術能力**  
團隊需具備原生 iOS 應用程式開發能力（Swift/SwiftUI 或 UIKit）、熟悉 Apple 輔助功能與 XCUITest 框架、能設計部分可觀察馬可夫決策過程（POMDP）環境，並具備大型視覺語言模型（VLM）的提示工程或微調經驗。

### 實作步驟建議

**步驟一：定義使用者身分與資料架構**  
先建立一個或多個持續性使用者身分，設計跨 10 個生活領域（通訊、財務、旅遊、餐飲等）的資料關聯圖譜，確定哪些資料點需要在 App 之間共享（如聯絡人、交易 ID、航班編號）。

**步驟二：建置或客製化原生 iOS 應用程式環境**  
依據目標場景選擇 2–26 個原生 iOS 應用程式進行客製化開發或改裝。每個 App 需能呈現真實的個人化資料狀態，而非空白預設值。若僅驗證概念，可從單一應用程式任務開始，再擴展至多應用程式任務。

**步驟三：設計觀測模態與動作空間**  
決定代理程式的輸入形式：純視覺（螢幕截圖）或特權視覺+XML（截圖加上 XCUITest 輔助功能樹）。後者在 iOS 上需透過 Mac 執行 XCUITest，能顯著提升前沿模型的準確率（最高達 26 個百分點），但會增加部署複雜度。

**步驟四：植入種子資料並建立跨 App 連續性**  
依照步驟一的綱要，將種子資料寫入各 App 的資料庫或後端，確保同一使用者的身分、歷史與偏好在所有應用程式中保持一致。這是實現「個人智慧化」的核心，而非僅提供沙盒化的孤立環境。

**步驟五：開發記憶與個人化推理層**  
針對記憶與個人化任務，設計讓代理程式能從應用程式內資料發現隱含模式的機制（例如透過少數範例提示或微調，讓模型推論「最常使用的通勤路線」或「偏好的付款方式」）。

**步驟六：建立評估管線與評分標準**  
採用 LLM-as-a-judge 流程並以人工標註驗證（如論文中 κ=0.77 的一致性），為單一應用程式、多應用程式與記憶任務分別設計評分標準（Rubrics），確保任務完成度的判定可自動化且可複現。

**步驟七：部署迭代與跨平台執行**  
利用論文提供的 AWS Runner 在雲端 Mac 實例上執行大規模評估，並逐步將驗證過的代理程式從模擬器遷移至實體裝置，測試真實延遲與電量消耗。

### 潛在風險與注意事項

**隱私與資料安全**  
由於個人智慧化代理必須處理真實身分、交易與通訊紀錄，任何雲端推理都可能暴露敏感資料。建議優先採用裝置端（On-device）模型或差分隱私技術，並在基準測試階段即使用去識別化的種子資料。

**iOS 封閉生態的基礎設施限制**  
不同於 Android 的 UIAutomator，iOS 的輔助功能樹需依賴 XCUITest 與 Mac/Xcode 環境，這會提高 CI/CD 與雲端部署成本。若目標為大規模商用，需預先評估 Apple 基礎設施的擴展性與授權限制。

**視覺 Grounding 與行動介面誤觸**  
手機螢幕解析度高但 UI 元素細小，純視覺設定下模型容易點擊錯誤座標。建議在動作空間中加入元素級的 XML 索引（特權設定）或採用微調過的視覺語言模型以降低誤操作率。

**長期記憶與上下文長度瓶頸**  
多應用程式任務可能橫跨 2–8 個 App 且步驟冗長，標準 LLM 的上下文視窗可能不足以保留跨 App 的狀態。需搭配外部記憶模組（如向量資料庫或摘要機制）來維持跨應用程式的連續性。

**過度擬合特定使用者角色**  
論文使用單一角色 Jordan Avery 進行評估，實際產品若僅基於單一 Persona 訓練，可能無法泛化至多樣化使用者行為。建議在產品化階段擴充多個不同背景的使用者角色與對應資料分布。

### 與其他技術的整合建議

**與現有 LLM/VLM 服務整合**  
可將 iOSWorld 的評估框架直接套用於前沿模型（如 GPT-4V、Claude）或開源電腦使用模型（如 Qwen3.5、UI-TARS）。若採用特權視覺+XML 設定，需在模型輸入層設計能同時處理圖像與結構化 XML 的多模態編碼器。

**與 RAG 及向量記憶庫整合**  
針對記憶與個人化任務，建議將跨 App 的個人資料透過嵌入式表示（Embedding）存入裝置端向量資料庫，讓代理程式在長期對話中能快速檢索使用者歷史偏好，彌補 LLM 上下文長度不足。

**與企業行動裝置管理（MDM）整合**  
在企業場景中，可將代理程式的執行環境與現有 MDM 方案結合，透過受控的 XCUITest 或私有 API 實現大規模 iOS 裝置的自動化，同時符合企業資安政策。

**與網頁代理程式分工協作**  
若產品同時涉及原生 App 與網頁操作，可讓 iOS 原生代理程式處理 App 內個人資料，而將瀏覽器任務交由現有的網頁代理程式（如 WebArena、VisualWebArena 框架），透過統一協調層分配任務。

**與 iOS Shortcuts 及 SiriKit 整合**  
對於單一應用程式或系統級操作，可先用 Shortcuts 或 SiriKit 完成低複雜度步驟，再將高階跨 App 推理交由基於 iOSWorld 方法建構的代理程式，以降低整體推理成本與延遲。

### 給不同背景讀者的閱讀建議

**給初學者**  
建議先從「適用場景」與圖 2（Jordan Avery 的數位生活）開始，理解「個人智慧化」與傳統沙盒化代理程式的差異。技術細節如 POMDP 公式或 XCUITest 實作可暫時略過，重點掌握「為何跨 App 的持續性使用者身分是手機代理程式的關鍵瓶頸」。

**給 AI 工程師**  
請聚焦於第 3 章的環境設計與觀測模態比較。特別關注純視覺與特權視覺+XML 的準確率差距（高達 26 個百分點），以及多應用程式任務僅達 37% 整體準確率所揭示的長期規劃與視覺 Grounding 挑戰。評估管線（LLM-as-a-judge）的實作細節可直接套用於你的產品驗證流程。

**給研究人員**  
本文的核心貢獻在於將「個人化」與「跨應用程式連續性」正式引入行動代理基準測試。建議深入分析 133 個任務的設計方法論，尤其是記憶與個人化任務如何強迫模型進行隱含模式推論。未來可延伸的方向包括：多使用者角色泛化、真實裝置與模擬器的差距研究，以及封閉式 iOS 生態對輔助功能資料可取得性的影響。

**給產品經理**  
請將閱讀重點放在 iOS 的市場滲透率（美國 58–60% 行動作業系統使用率）與目前 Android 導向基準測試的缺口，評估原生 iOS 代理程式的商業潛力。同時留意特權設定所需的 Mac/Xcode 基礎設施成本，以及處理真實個人資料時的隱私合規風險，這些都是產品化階段的關鍵可行性因子。
