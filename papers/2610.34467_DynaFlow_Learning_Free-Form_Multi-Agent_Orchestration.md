DynaFlow 的核心創新在於將「自由形式可執行工作流程合成」(free-form executable workflow synthesis) 整合進主代理 (main agent) 的動作空間 (action space)，使其成為與一般工具呼叫 (tool call) 並列的原生動作。這種設計突破了傳統多代理系統 (Multi-Agent Systems, MAS) 依賴預設協作結構 (predefined collaboration structures) 的限制。

**動作空間設計的三元結構**

主代理在每個決策點可選擇三類動作：(i) 直接回答 (Direct)、(ii) 呼叫工具 (Tool call)、(iii) 生成 JavaScript 工作流程程式 (Workflow action)。第三類動作最具特色——主代理透過最小化執行介面 (minimal execution interface) 定義子代理 (sub-agents) 的職責、循序或平行依賴關係，以及中間輸出如何被傳遞、聚合與驗證。這種「程式即編排」(program-as-orchestration) 的設計使工作流程表達力大幅超越基於範本的方案。

**預算受限的執行環境**

工作流程在預算受限的執行環境 (budget-constrained runtime) 中執行，並回傳輸出與執行追蹤記錄 (execution trace)。主代理利用這些回饋指導後續動作，包括合成後續工作流程以根據觀察結果調整協作。這形成一個閉環：決策 → 執行 → 回饋 → 再決策，使編排成為可隨推理進展動態演化的過程。

**兩階段監督式微調 (Two-Stage SFT)**

訓練流程分為兩個階段。第一階段使用蒸餾示範 (distilled demonstrations) 進行軌跡學習 (trajectory learning)，目標是讓主代理學會首輪推理 (first-turn reasoning) 與工作流程動作的對應關係。第二階段在策展子集 (curated subset) 上進行精煉 (refinement)，此子集排除三類有缺陷的示範：不成立的前提 (unsupported premises)、偏誤驗證 (biased verification)、以及資訊流缺陷 (information-flow defects)。這種設計使編排品質本身成為示範選擇的明確標準。

**編排學習與執行器能力解耦**

關鍵設計決策是僅訓練主代理，所有子代理保持凍結 (frozen)。這種解耦使預訓練模型可直接作為執行器重用，無需重新訓練，並將學習焦點集中在「協調現有能力」而非「提升執行能力」上。這與 AFlow 等自動化工作流程設計方法形成對比——後者通常需要對整個系統進行調整。

### 潛在風險與注意事項

**1. 成本與延遲爆炸**
多代理編排可能讓單次查詢成本增加 3-10 倍。Dynamic 模式雖然讓 47.1% 的查詢無需工作流程，但剩餘 53% 的查詢仍可能消耗大量資源。
**緩解**：實作嚴格的預算控制（最大代理呼叫次數、最大執行時間），並在 Dynamic 模式中提供明確的成本預估。

**2. 蒸餾資料的偏誤**
從更強模型蒸餾而來的軌跡可能包含該模型的特定偏誤（例如傾向使用某些子代理、忽略某些驗證步驟）。
**緩解**：使用策展過濾機制識別並排除偏誤樣本；定期由領域專家審核示範品質。

**3. 工作流程生成的安全風險**
主代理生成的 JavaScript 程式碼可能在沙箱外造成危害，特別是當沙箱實作不完善時。
**緩解**：使用成熟的隔離技術（如 gVisor、Firecracker），禁止網路與檔案系統存取，設定嚴格的資源上限。

**4. 子代理能力天花板**
DynaFlow 只訓練主代理，子代理能力固定。如果子代理在某個子任務上能力不足，整體系統表現會受限。
**緩解**：定期評估子代理在專門任務上的表現；當瓶頸出現時，考慮升級子代理骨幹或加入新子代理。

**5. 資訊流缺陷的隱蔽性**
工作流程可能在表面上正確執行，但實際上某個關鍵的中間結果未被後續階段使用，導致最終答案缺乏依據。
**緩解**：實作自動化資訊流分析工具，檢查每個工作流程中下游階段是否實際引用上游輸出。

**6. 評估指標的侷限性**
僅看最終答案正確性可能誤導——一個答案正確但編排過程有缺陷的系統，在面對新問題時可能失敗。
**緩解**：除了整體準確率，還應追蹤編排品質指標（驗證頻率、上游輸出使用率、精煉動作比例）。

### 與其他技術的整合建議

**1. 與 RAG 系統整合**
將 DynaFlow 的子代理設計為不同類型的檢索代理（向量檢索、關鍵字檢索、知識圖譜查詢），主代理可根據問題特性動態選擇並組合檢索策略。工作流程可包含「檢索 → 評估相關性 → 重新檢索」的迴圈。

**2. 與既有代理框架整合**
DynaFlow 的主代理可作為 AutoGen、LangGraph 等框架中的協調層。子代理可以是框架中既有代理的包裝。建議將 DynaFlow 視為「編排決策器」，而非取代整個代理框架。

**3. 與工具呼叫生態系整合**
主代理的動作空間應包含既有工具（網路搜尋、計算器、資料庫查詢、API 呼叫）以及工作流程生成。工作流程本身可作為「超級工具」，在需要時被呼叫。

**4. 與快取與記憶系統整合**
對於常見的工作流程模式（例如「先檢索再驗證」），可實作工作流程快取，避免重複生成。長期記憶系統可記錄過去成功的工作流程，作為未來決策的參考。

**5. 與監控與可觀測性平台整合**
整合 OpenTelemetry 等標準，將工作流程的執行追蹤匯出到既有監控系統，便於追蹤延遲瓶頸、錯誤模式、成本歸因。

**6. 與人類回饋機制整合**
對於低信心度的工作流程輸出，設計「人類在迴圈中」的介入點。編排決策本身也可成為收集人類偏好的來源，用於未來的強化學習訓練。
