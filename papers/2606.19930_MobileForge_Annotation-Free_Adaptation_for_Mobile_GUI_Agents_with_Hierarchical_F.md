# MobileForge：透過階層式回饋引導策略最佳化實現行動 GUI 智慧體之免標註適應

**原文標題：** MobileForge: Annotation-Free Adaptation for Mobile GUI Agents with Hierarchical Feedback-Guided Policy Optimization

## ⚡ TL;DR

現有行動GUI智慧體適應目標應用程式時，缺乏統一互動平台且策略最佳化訊號過於粗略。
提出MobileForge，透過MobileGym與HiFPO實現免標註適應及層級回饋策略最佳化。
AndroidWorld達77.6%、MobileWorld達41%，為最強開放資料GUI智慧體。

## 摘要翻譯

基於多模態大型語言模型（MLLM）的行動 GUI 智慧體在 UI 理解與動作執行方面已取得顯著進展，然而將其適應至真實目標應用程式仍成本高昂，因為行動應用程式數量眾多、頻繁更新，且難以透過人工撰寫任務、示範軌跡或獎勵標籤完整涵蓋。現有的免標註 GUI 學習方法雖減少了人工監督，卻缺乏一個統一底層平台來串連目標應用程式探索、課程探勘、rollout 執行與回饋；而策略最佳化往往仰賴孤立 rollout 與粗略獎勵，導致其難以轉化為可靠的改進訊號。本文提出 MobileForge，一套針對行動 GUI 智慧體的免標註適應系統。MobileForge 包含 MobileGym，其將任務生成與 rollout 評估奠基於真實行動應用程式互動，以及階層式回饋引導策略最佳化（HiFPO），其將軌跡結果、步驟層級過程回饋與修正提示轉化為提示情境化步驟層級 GRPO 更新。僅使用自動生成的免標註適應資料，MobileForge 使 Qwen3-VL-8B 在 AndroidWorld 上達到 67.2% Pass@3，接近封閉資料 GUI 專用之 GUI-Owl-1.5-8B 基礎模型的 69.0%。經 MobileForge 適應後的 ForgeOwl-8B 更在 AndroidWorld 上達到 77.6% Pass@3，並於領域外之 MobileWorld 純 GUI 分割取得 41.0% 的成功率，成為我們評估中表現最佳的開放資料行動 GUI 智慧體。程式碼、資料與訓練後模型將於 https://mobile-forge.github.io/ 公開釋出。

### 核心貢獻（3～5點）
- 提出 MobileForge 免標註適應系統，無需人工撰寫任務、示範軌跡或獎勵標籤，即可將行動 GUI 智慧體適應至真實目標應用程式。
- 設計 MobileGym 統一底層平台，將任務生成與 rollout 評估奠基於真實行動應用程式互動，串連目標應用程式探索、課程探勘、執行與回饋。
- 提出階層式回饋引導策略最佳化（HiFPO），將軌跡結果、步驟層級過程回饋與修正提示轉化為提示情境化步驟層級 GRPO 更新，解決孤立 rollout 與粗略獎勵難以產生可靠改進訊號之問題。
- 僅使用自動生成之免標註適應資料，即讓 Qwen3-VL-8B 在 AndroidWorld 上達到 67.2% Pass@3，接近封閉資料 GUI 專用模型之水準；適應後之 ForgeOwl-8B 更達 77.6% Pass@3，並於領域外 MobileWorld 純 GUI 分割取得 41.0% 成功率，樹立開放資料行動 GUI 智慧體之新標竿。

### 適合對象
從事多模態大型語言模型、行動裝置圖形使用者介面自動化、免標註學習與線上強化學習策略最佳化研究之學者與工程師；特別適合需要在真實行動應用程式環境中降低資料標註成本、建立可擴展適應流程，並將開源模型部署於實際手機互動場景之研究人員與開發者。

## 深度分析

#### 方法論解析

MobileForge 的核心貢獻在於提出一套免標註適應（annotation-free adaptation）的閉環系統，由兩個緊密耦合的元件構成：**MobileGym**（互動與評估底層平台）與 **HiFPO**（Hierarchical Feedback-Guided Policy Optimization，階層式回饋引導策略最佳化）。

**MobileGym：統一底層平台（unified substrate）的建構**
MobileGym 解決了現有方法中「探索、課程探勘（curriculum mining）、rollout 執行與回饋彼此脫節」的瓶頸。其運作分為三個階段：
1. **Target-App Exploration（目標應用程式探索）**：採用 function-aware exploration 策略，結合 APK 中宣告的結構錨點（structural anchors）與當前截圖（screenshot observation），生成目標導向的探索任務，使探索不再盲目，而是針對應用程式的可達 GUI 狀態（reachable GUI states）進行。
2. **MobileGym-Curriculum（課程探勘）**：從探索所得的應用程式軌跡（app trace）中挖掘可執行任務（executable tasks），確保生成的任務扎根於真實行動應用程式互動（real mobile app interaction），而非憑空合成。
3. **MobileGym-Critic（分層評估器）**：在 rollout 完成後（而非過程中）提供結構化的階層式回饋（hierarchical feedback），包含：(a) 軌跡層級結果（trajectory-level outcome）——任務是否成功；(b) 步驟層級過程回饋（step-level process feedback）——個別步驟的品質評估；(c) 修正提示（corrective hint）——針對錯誤步驟的具體改進建議。這種設計將環境回饋從「稀疏的純量獎勵」轉化為「可重複利用的結構化訊號」。

**HiFPO：提示情境化的策略更新**
HiFPO 負責將 MobileGym 產生的回饋轉化為可靠的策略改進訊號（improvement signal）。其創新點在於：
- **多嘗試排程與提示累積**：對於同一任務，系統會進行多次嘗試（hint-guided attempts）。第 k 次嘗試的決策狀態（decision state）s_k^(t) 不僅包含任務 x、截圖 I_k^(t) 與互動歷史（interaction history）H_k^(t)，還納入了累積修正提示情境 η_<k——即先前嘗試失敗後產生的所有 corrective hints。這使得後續嘗試能基於過往經驗進行「情境化學習」，突破初始策略的能力邊界（capability boundary）。
- **步驟層級 GRPO**：不同於傳統強化學習（reinforcement learning）僅使用軌跡層級的粗略獎勵（coarse reward），HiFPO 將軌跡結果、步驟回饋與修正提示整合，執行 hint-contextualized step-level GRPO update。透過篩選高品質的任務與步驟，系統將結構化回饋轉換為數值動作獎勵（numeric action reward）R，用於更新策略 π_θ。

**問題形式化**
論文將行動 GUI 控制建模為序列決策（sequential decision making）。動作空間（action space）為結構化 GUI 動作（structured GUI action）a = (α, ψ)，其中 α 為動作類型（如 tap、swipe、type、wait、terminate、answer、system navigation），ψ 為對應參數（座標、方向、文字等）。值得注意的是，環境在 rollout 過程中不提供密集獎勵（dense reward），所有學習訊號均來自 MobileGym-Critic 的事後評估，這降低了對人工獎勵標籤（reward label）的依賴。

#### 實驗數據解讀

MobileForge 的評估設計涵蓋領域內（in-domain）與領域外（out-of-domain）兩種情境，分別對應 **AndroidWorld** 與 **MobileWorld GUI-only split**。評估指標採用 **Pass@3**（前三次嘗試通過率）與 success rate。

**關鍵結果分析**
1. **縮小與封閉資料專用模型的差距**：以通用多模態大型語言模型（MLLM）**Qwen3-VL-8B** 為基礎模型（base model），僅使用自動生成的免標註適應資料（adaptation data）進行訓練，即可在 AndroidWorld 達到 **67.2% Pass@3**。此成績已逼近封閉資料 GUI 專用模型（closed-data GUI-specialized model）**GUI-Owl-1.5-8B** 的 69.0%。這證明了免標註適應（annotation-free adaptation）的資料效率與有效性——無需人工撰寫任務（human-written task）、專家示範（demonstration）或獎勵標籤，即可達到接近專有資料訓練的水準。
2. **開放資料行動 GUI 智慧體的新高**：將 MobileForge 應用於 GUI-Owl-1.5-8B 後，得到 **ForgeOwl-8B**，其在 AndroidWorld 的 Pass@3 提升至 **77.6%**，超越原始基礎模型近 8.6 個百分點；同時在領域外的 MobileWorld GUI-only 達到 **41.0% success**。這確立了 ForgeOwl-8B 作為目前最強開放資料行動 GUI 智慧體（strongest open-data mobile GUI agent）的地位。
3. **跨領域遷移（transfer）的意義**：MobileWorld 的測試資料在訓練階段完全未使用（no MobileWorld rollout used for training），41.0% 的成功率顯示系統具備一定的泛化能力。然而，相較於領域內的 77.6%，領域外表現仍有顯著落差，暗示真實世界中多樣化的應用程式介面與互動邏輯對策略遷移構成挑戰。

#### 與現有研究的比較

**現有文獻的分類與侷限**
論文將相關工作分為三類：
- **監督式探勘**：TongUI 從網頁教學（web tutorial）挖掘監督訊號；MobileA3gent 利用去中心化使用者手機軌跡（decentralized user-phone trajectory）；OS-Genesis 透過反向任務建構（reverse task construction）合成任務；GUI-explorer 則以轉移感知互動知識（transition-aware interaction knowledge）進行自主探索（autonomous exploration）。這些方法雖減少人工，但探索、任務生成與策略學習之間缺乏統一底層平台（unified substrate）。
- **強化學習與自動獎勵**：ZeroGUI 與 MobileGUI-RL 研究自動獎勵估計（automatic reward estimation）與線上強化學習（online reinforcement learning），但多依賴孤立 rollout（isolated rollout）與粗略獎勵（coarse reward），難以累積可重複使用的經驗。
- **自我演化與規模化**：SEAgent、ACuRL、UI-Oceanus 探索自我演化（self-evolving）、持續學習（continual learning）或合成環境擴展（synthetic-environment scaling），但同樣未將目標應用程式互動（target-app interaction）與策略最佳化緊密結合。

**MobileForge 的差異化優勢**
1. **統一底層平台**：MobileGym 首次將目標應用程式探索、課程探勘、rollout 執行與階層式評估整合於真實行動應用程式互動中，確保生成的任務扎根於實際可達狀態，且回饋直接對應策略學習需求。
2. **回饋的階層化與再利用**：MobileGym-Critic 提供軌跡結果、步驟回饋與修正提示三層訊號；HiFPO 則將這些訊號轉化為 hint-contextualized step-level GRPO updates。這克服了既有方法中「rollout 視為孤立經驗」的問題，使系統能從多次失敗嘗試中累積結構化知識。
3. **免標註的資料閉環**：整個流程無需人工撰寫任務、專家示範軌跡（demonstration）或獎勵標籤（reward label），大幅降低適應成本，特別適合數量眾多且頻繁更新的行動應用程式（mobile apps）。

**潛在限制**
- **初始策略依賴**：系統仍需一個初始 GUI 策略（initial GUI policy）作為起點，若基礎模型的 UI 理解（UI understanding）與動作執行（action execution）能力過弱，可能無法產生足夠高品質的探索軌跡。
- **探索覆蓋率**：目前的 function-aware exploration 依賴 APK 中的結構錨點（structural anchors），對於高度動態、無標準結構或深度依賴網頁內容（如 WebView）的應用程式，探索可能不夠全面。
- **領域外泛化瓶頸**：MobileWorld GUI-only 的 41.0% success 顯示，從 AndroidWorld 到未見過的應用程式集合之間，仍存在顯著的領域差距（domain gap）。

#### 可重現性評估

**開源承諾與資源可用性**
作者明確聲明將釋出程式碼（code）、資料（data）與訓練後的模型權重（trained models），並提供專案網址 https://mobile-forge.github.io/。這對於開放科學（open science）至關重要，因為：
- 採用公開基礎模型（Qwen3-VL-8B）與公開評測基準（AndroidWorld、MobileWorld），降低取得門檻。
- 免標註適應（annotation-free adaptation）的特性意味著其他研究者無需蒐集昂貴的人工示範或獎勵標註，即可重現完整的訓練流程。

**重現挑戰**
儘管資料與模型將開放，重現仍面臨實務門檻：
- **環境建置**：系統需要與真實行動應用程式互動，這要求 Android 模擬器（emulator）或實體裝置叢集，以及穩定的 ADB（Android Debug Bridge）連線，基礎建設複雜度遠高於純文字或網頁環境。
- **計算資源**：探索（exploration）、多次 hint-guided attempts、以及與真實 App 的互動 rollout 皆屬於高延遲、高計算成本的流程，大規模複製需要可觀的運算資源與時間。
- **非確定性**：行動應用程式的動態行為（如網路載入、廣告彈窗）可能引入環境隨機性，若論文未詳細記錄種子設定與環境快照（snapshot）機制，重現結果可能出現變異。

#### 未來研究方向

**1. 探索策略的語意深化**
目前的探索依賴 APK 結構錨點與畫面資訊。未來可引入大型語言模型（Large Language Model, LLM）對應用程式介面進行更深層的語意理解，例如預測功能區塊的用途，以提升對無結構錨點或高度動態應用程式的探索覆蓋率。

**2. 更細緻的過程獎勵機制**
MobileGym-Critic 已提供步驟層級回饋（step-level process feedback），但未來可進一步研究元素層級（element-level）或像素層級（pixel-level）的過程獎勵，例如精確定位哪個 UI 元件（UI element）導致錯誤，從而產生更精準的修正提示（corrective hint）。

**3. 領域外適應與元學習**
MobileWorld GUI-only 的表現顯示跨領域遷移仍有挑戰。未來可結合元學習（meta-learning）或領域對抗訓練（domain adversarial training），使策略在面對全新應用程式時能更快適應，甚至實現單次嘗試（few-shot）或零次嘗試（zero-shot）的目標應用程式遷移。

**4. 提示累積機制的理論分析**
HiFPO 中 η_<k 的設計本質上是一種 in-context learning 的延伸。未來研究可從理論角度分析其樣本效率（sample efficiency）與收斂性（convergence），並探討提示長度增長對策略梯度估計的影響，以及是否需要提示壓縮或摘要機制。

**5. 跨平台擴展**
目前 MobileForge 聚焦 Android 平台。未來可將統一底層平台（unified substrate）的概念擴展至 iOS 或跨平台 Web GUI，研究不同平台間的動作空間（action space）對齊與回饋機制移植。

**6. 人機協同的混合監督**
雖然 MobileForge 標榜免標註，但未來可研究「少量人類回饋（human-in-the-loop）」與自動化流程的協同機制。例如，在 MobileGym-Critic 無法確定軌跡結果的邊緣案例（edge cases）中引入人工仲裁，可能以極低成本進一步提升策略上限。

## 論文問答

**Q1：MobileForge 旨在解決行動 GUI 智慧體領域中的什麼核心問題？**
A：MobileForge 旨在解決 MLLM 行動 GUI 智慧體在適應真實目標應用程式時所面臨的高成本與可擴展性困境。由於行動應用程式數量龐大且更新頻繁，仰賴人工撰寫任務、專家示範軌跡或手動獎勵標籤的做法不僅所費不貲，且資料很快就會過時。因此，本研究的核心問題在於如何建構一套免標註適應系統，讓智慧體僅透過自動生成的資料就能在真實應用程式中探索、執行任務並自我改進。

**Q2：現有免標註 GUI 學習方法存在哪兩大主要瓶頸？**
A：現有免標註 GUI 學習方法主要面臨兩大瓶頸。第一，這些方法缺乏一個統一的行動底層平台來連接目標應用程式探索、課程探勘、rollout 執行與回饋，導致生成的任務與真實應用程式互動脫節，評估回饋也難以有效用於策略學習。第二，現有的策略最佳化往往將 rollout 視為孤立的經驗，僅仰賴稀疏或粗略的獎勵，即使具備步驟層級評估，也很少能將軌跡結果、過程回饋與修正提示整合為可重複利用的改進訊號。

**Q3：相較於其他領域，為何免標註適應對行動 GUI 智慧體特別重要？**
A：相較於其他領域，行動應用程式的生態系統極為龐大且變化迅速，每天都有大量更新與新應用上架，使得人工標註的成本與維護難度呈指數級增長。若智慧體只能依賴固定基準測試或封閉資料訓練，將難以應對真實世界中使用者手機裡各式各樣的應用程式與版本差異。因此，免標註適應不僅能降低擴展門檻，更是讓行動 GUI 智慧體從實驗室走向實際部署的關鍵技術路徑。

**Q4：MobileForge 的兩大核心元件是什麼，它們如何協同運作？**
A：MobileForge 由 MobileGym 與 HiFPO 兩大核心元件組成，兩者緊密耦合形成適應迴路。MobileGym 作為互動與評估底層平台，負責在真實行動應用程式中進行探索、探勘可執行任務、執行 rollout，並透過階層式評估器提供軌跡結果、步驟回饋與修正提示。HiFPO 則負責策略最佳化，它根據 MobileGym 產生的階層式回饋來排程提示引導的重試嘗試、篩選有價值的任務與步驟，並將修正提示情境化後用於步驟層級的 GRPO 更新，從而閉合整個免標註適應迴路。

**Q5：HiFPO 與傳統策略最佳化方法在利用 rollout 回饋方面有何根本不同？**
A：HiFPO 的關鍵創新在於將多層次回饋轉化為可重複利用的策略改進訊號，而非僅仰賴孤立的 rollout 與稀疏獎勵。傳統方法通常將每次 rollout 視為獨立經驗，並以粗略的最終成敗作為獎勵，難以定位具體錯誤步驟；相較之下，HiFPO 整合了軌跡結果、步驟層級過程回饋與修正提示，透過提示情境化步驟層級 GRPO 更新，讓策略能從失敗嘗試中學習到細粒度的修正方向。這種設計使智慧體能夠累積超越初始策略能力邊界的可重用經驗，實現更穩定的免標註策略提升。

**Q6：為何 MobileGym-Critic 選擇提供三種回饋（軌跡結果、步驟回饋、修正提示），而非單一純量獎勵？**
A：MobileGym-Critic 設計三種回饋是為了克服單一純量獎勵在行動 GUI 控制中的資訊稀疏問題。最終軌跡結果僅能告知任務成敗，無法指出哪個步驟出錯；步驟層級過程回饋則能標定具體的錯誤操作或狀態；而修正提示更進一步提供策略在下一次嘗試時可參考的語義指引。這種階層式設計讓 HiFPO 能夠將不同粒度的回饋轉換為細緻的訓練訊號，從而實現比傳統稀疏獎勵更精確的策略梯度更新。

**Q7：MobileForge 選用了哪些評測基準，為何如此選擇？**
A：MobileForge 選用 AndroidWorld 作為領域內評測基準，並以 MobileWorld 的純 GUI 分割作為領域外評測基準。AndroidWorld 能夠檢驗智慧體在常見行動應用程式任務上的適應成效，而 MobileWorld GUI-only 則用於評估模型在未見過領域中的泛化能力，且訓練過程中完全不使用 MobileWorld 的 rollout 資料。這種雙基準設計能同時驗證系統在熟悉環境中的效能上限，以及其免標註適應機制對全新應用程式的遷移潛力。

**Q8：論文報告的最關鍵量化結果為何？**
A：實驗結果顯示，僅使用自動生成的免標註適應資料，Qwen3-VL-8B 在 AndroidWorld 上即可達到 67.2% 的 Pass@3，已十分接近使用封閉資料訓練的 GUI-Owl-1.5-8B 基礎模型之 69.0%。更進一步地，經 MobileForge 適應後的 ForgeOwl-8B 在 AndroidWorld 上達到 77.6% Pass@3，並在領域外的 MobileWorld GUI-only 分割上取得 41.0% 的成功率。這些數據不僅證明了免標註適應能顯著縮小與專用封閉資料模型的差距，更確立了 ForgeOwl-8B 在開放資料行動 GUI 智慧體中的領先地位。

**Q9：論文提供了哪些證據來說明階層式回饋對效能至關重要？**
A：雖然提供的上下文未詳盡列出所有消融實驗數據，但從方法設計與結果論述可推論，HiFPO 透過階層式回饋將軌跡結果、步驟回饋與修正提示整合為提示情境化步驟層級 GRPO 更新，是相較於僅使用孤立 rollout 與粗略獎勵的現有方法之核心差異。正是這種多粒度回饋機制，使得 ForgeOwl-8B 能超越基礎模型達到 77.6% Pass@3，並在領域外測試中維持 41.0% 的成功率。若缺少步驟層級與修正提示的引導，策略將難以從失敗軌跡中萃取出細緻的改進方向，導致性能停滯於基礎模型的能力邊界。

**Q10：MobileForge 在哪些真實世界場景中最能發揮價值？**
A：MobileForge 最適合應用於需要快速適應大量異質行動應用程式的場景，例如個人數位助理、自動化測試框架，以及輔助無障礙操作的智慧代理。在這些情境中，應用程式種類繁多且版本頻繁更新，傳統依賴人工撰寫腳本或示範的做法難以規模化。透過免標註適應，MobileForge 能讓智慧體直接在使用者的裝置上自主探索與學習，大幅降低維護成本並提升對新應用程式的即時適應能力。

**Q11：將 MobileForge 以開放資料系統形式釋出，在實務上有何優勢？**
A：將 MobileForge 以開放資料形式釋出，能夠打破現有許多 GUI 專用模型依賴封閉資料的限制，促進學術界與產業界的可重現性研究與後續創新。開發者與研究人員無需取得昂貴的人工標註資料集，即可在真實行動應用程式上訓練與評估自己的智慧體，降低進入門檻。此外，開放生態系也有助於社群共同貢獻更多樣化的目標應用程式適應策略，加速行動 GUI 智慧體從研究原型走向實際產品化。

**Q12：MobileForge 可能如何改變行動 GUI 智慧體的研究方向？**
A：MobileForge 為行動 GUI 智慧體研究建立了一個免標註適應的新範式，將研究重心從仰賴靜態、人工標註的資料集轉向動態、自我演化的真實應用程式互動。這可能促使未來更多研究聚焦於如何設計更高效的自主探索策略、更精細的階層式回饋機制，以及更強大的線上策略最佳化演算法。長遠來看，這種方向有助於建構真正能持續學習、與時俱進的行動智慧體，而非僅在固定基準上追求高分但難以部署的模型。

**Q13：根據論文暗示，MobileForge 系統目前仍存在哪些限制？**
A：儘管 MobileForge 在免標註適應上取得顯著進展，其效能仍部分受限於初始基礎模型的能力邊界，因為系統主要透過自我收集的經驗進行改進，若初始策略完全無法觸及某些應用程式功能，則探索與課程探勘可能難以覆蓋。此外，整個適應迴路需要與真實行動應用程式持續互動，在運算資源與執行時間上相較於靜態資料集訓練仍有較高成本。最後，雖然 MobileWorld GUI-only 驗證了領域外泛化能力，但面對極度冷門或介面結構迥異的應用程式時，其適應穩定性仍有待更廣泛的驗證。

**Q14：哪些類型的任務或應用程式仍可能對經 MobileForge 適應後的智慧體構成挑戰？**
A：對於需要複雜多步邏輯推理、跨應用程式深度協作，或涉及非標準自訂 UI 元件的應用程式，MobileForge 適應後的智慧體可能仍會面臨挑戰。這類任務往往需要超越視覺感知與基本操作的高階語義理解，而僅靠自動生成的課程與階層式回饋可能難以提供足夠的學習訊號。此外，若應用程式存在動態載入、非確定性行為或需要特定背景知識才能完成的工作流程，智慧體在缺乏外部知識注入的情況下，其成功率可能顯著下降。

**Q15：MobileForge 為未來改善免標註行動 GUI 適應指出了哪些研究方向？**
A：未來研究可朝幾個方向延伸：首先，結合更強大的世界模型或應用程式知識圖譜，以輔助初始探索並減少對基礎模型先驗能力的依賴；其次，發展更細緻的獎勵塑形技術，將 MobileGym-Critic 的回饋進一步分解為更密集的訓練訊號。最後，探索持續學習與終身學習機制，使智慧體能在不遺忘先前適應經驗的前提下，不斷累積跨應用程式的通用互動知識，從而實現真正自主演化的行動 GUI 智慧體。

## 實務應用指南

### 適用場景

1. **企業內部 App 自動化測試與驗收**：針對頻繁更新的內部業務 App（如 ERP、CRM、差勤系統），無需人工撰寫測試腳本或維護 fragile 的座標腳本。MobileForge 可自動探索 UI、生成可執行任務，並透過階層式回饋持續優化測試代理程式，降低回歸測試的人力成本。

2. **長照與無障礙輔助操作**：為視障或行動不便使用者開發語音/智慧輔助代理，自動適應各種第三方 App（如醫院掛號、叫車服務、外送平台）。無需等待開發者開放 API 或提供無障礙標註，代理程式可透過視覺理解與免標註適應學會跨 App 操作。

3. **電商與內容平台自動化營運**：自動執行跨平台商品上架、庫存查詢、優惠券領取、訂單追蹤等重複性 GUI 操作。當目標電商 App 頻繁改版導致介面元素位移時，系統可自動重新探索並適應新介面，維持自動化流程不中斷。

4. **金融與保險 App 智能客服代理**：在無法取得後端 API 或開發者文件的老舊系統中，讓代理程式學會在銀行、證券或保險 App 中協助用戶查詢餘額、繳交保費或申請理賠。透過真實互動產生的適應資料，避免處理敏感金融資料的人工標註合規風險。

5. **物聯網裝置管理與設定**：適應各品牌智慧家電、路由器、監控系統的專屬 App，自動完成裝置配對、韌體更新與參數設定。解決 IoT 生態碎片化導致的「每支 App 都要重新開發自動化腳本」的痛點。

### 實作前置條件

- **資料需求**：目標應用程式的 APK 檔案或已安裝之實體裝置；一個具備基礎 GUI 理解能力的初始多模態模型（如 Qwen3-VL-8B 或 GUI-Owl-1.5-8B）。**無需**人工撰寫任務、專家示範軌跡或獎勵標籤，但需準備沙箱測試帳號與隔離環境資料。
- **運算資源**：至少具備 24GB VRAM 的 GPU（如 NVIDIA A100 或 RTX 4090）用於 8B 參數模型的 GRPO 訓練；Android 模擬器（如 Android Emulator 或 Dockerized Android）或實體手機農場用於 rollout 收集；足夠的儲存空間存放探索軌跡與自動生成之課程資料（預估每支 App 數十 GB）。
- **技能需求**：熟悉 Android Debug Bridge (ADB) 與行動裝置操作；具備強化學習（RL）與群組相對策略最佳化（GRPO）之基礎知識；能夠操作多模態大型語言模型（MLLM）的推論與微調框架（如 LLaMA-Factory、vLLM 或自訂 PyTorch 訓練腳本）；具備將畫面截圖與動作序列轉換為模型訓練格式之資料工程能力。

### 實作步驟建議

1. **環境建置與目標 App 探索**：部署 Android 模擬器或連接實體裝置，安裝目標 App。啟動 MobileGym-Explorer，利用 APK 中宣告的 activity 結構錨點與畫面截圖進行目標導向探索，收集可達成的 GUI 狀態與互動軌跡，作為後續課程探勘的證據（exploration evidence）。
2. **課程探勘與任務生成**：執行 MobileGym-Curriculum，從探索軌跡中挖掘可執行的任務（例如「開啟設定並關閉推播通知」），建立自動化生成的適應資料課程。此階段需過濾語意模糊或無法重現的任務，確保課程品質。
3. **Hint-Guided Rollout 收集**：使用 HiFPO 排程器，針對每個任務進行多次嘗試（multiple attempts）。首次嘗試無提示，後續嘗試將前次累積的修正提示（corrective hints）編碼進決策狀態，收集多組軌跡以形成對比學習所需的樣本分佈。
4. **階層式評估與回饋轉換**：透過 MobileGym-Critic 對每條軌跡進行評估，產出三層回饋：軌跡層級結果（成功/失敗）、步驟層級過程回饋（哪一步操作錯誤）以及修正提示（應如何修正）。將這些結構化回饋轉換為數值獎勵與訓練樣本。
5. **策略最佳化訓練**：將篩選後的步驟層級資料與提示情境化輸入 GRPO，更新策略模型。重複步驟 3–5 數個迭代週期，直至模型在驗證集上的 Pass@3 收斂。訓練時需監控 KL 散度，避免策略偏離基礎模型過遠。
6. **部署與持續適應**：將訓練後之 ForgeOwl-8B 部署至邊緣裝置或雲端推論服務。保留 MobileGym 探索迴路，於目標 App 更新後自動重新觸發適應流程，形成「探索—訓練—部署—再探索」的閉環。

### 潛在風險與注意事項

- **探索覆蓋率不足**：若目標 App 功能隱藏在深層選單或需要特定前置條件（如登入、地理位置權限），自動探索可能無法觸及，導致課程偏差與策略偏誤。**緩解措施**：提供半自動種子操作（seed actions）或預設帳號狀態，並在探索階段引入基於大型語言模型的功能猜測機制。
- **獎勵訊號稀疏與延遲**：雖然 HiFPO 提供步驟層級回饋，但某些任務的成敗仍只能在最後一步判定，中間步驟的過程回饋可能雜訊過高。**緩解措施**：設定保守的步驟篩選閾值，僅保留高置信度的步驟層級獎勵用於 GRPO 更新，避免錯誤訊號污染策略。
- **模擬器與真機差異**：Android 模擬器的畫面渲染、座標系統與實體裝置存在差異，可能導致適應後模型在真機上表現衰退。**緩解措施**：在訓練後期引入真機資料進行分佈對齊，或直接使用真機農場收集 rollout，避免模擬器偏差。
- **隱私與合規風險**：自動探索與 rollout 可能在無意間觸及個人資料或執行不可逆操作（如刪除帳號、發送簡訊、確認付款）。**緩解措施**：務必在隔離環境（沙箱帳號、測試機、無網路連線）中執行，建立動作黑名單與緊急停止機制。
- **計算成本膨脹**：多次 hint-guided 嘗試與 GRPO 訓練需要大量 GPU 時數與裝置互動時間。**緩解措施**：先以小規模課程（10–20 個核心任務）驗證收斂性與運算成本，再擴展至完整 App；利用雲端裝置農場平行化 rollout 收集。

### 與其他技術的整合建議

- **與現有 RPA（機器人流程自動化）整合**：MobileForge 可作為 RPA 的「視覺適應層」，補充傳統 RPA 依賴固定 XPath、resource-id 或絕對座標的脆弱性。當 App 改版導致原有腳本失效時，MobileForge 可在數小時內自動重新適應新介面，而非人工重新錄製流程。
- **與 LLM 編排框架（如 LangChain、AutoGen）整合**：將 ForgeOwl-8B 封裝為具備行動裝置控制能力的工具（Tool），由上層 LLM 編排器根據使用者自然語言意圖呼叫。MobileGym 產生的修正提示可作為短期記憶，儲存於向量資料庫供跨會話檢索，提升長期任務的連貫性。
- **與 CI/CD 流水線整合**：將 MobileGym-Curriculum 與 Critic 嵌入 App 發布前的自動化測試流水線。每次開發者提交新版 APK，系統自動執行探索、生成回歸測試任務、執行 rollout，並以 Pass@3 趨勢作為發布閘門（Quality Gate），未達門檻即阻擋發布。
- **與雲端裝置農場（如 AWS Device Farm、Firebase Test Lab）整合**：利用雲端裝置平行化 rollout 收集與探索，縮短適應週期。HiFPO 的 GRPO 更新可於中央 GPU 叢集執行，形成「邊緣裝置採樣—雲端訓練—邊緣部署」的閉環，兼顧規模化與成本效益。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先從 AndroidWorld 公開資料集與 Qwen3-VL-8B 的推論範例入手，理解「模型如何看著手機畫面決定點擊位置」的基本運作邏輯。無需立即深入 GRPO 的數學推導，重點關注 MobileGym 如何自動產生任務與回饋，建立「免標註適應」的直覺即可。
- **AI 工程師**：請著重研讀 MobileGym 的底層設計與 HiFPO 的訓練流程，特別是「修正提示（corrective hints）如何被編碼進決策狀態」以及「步驟層級 GRPO 的獎勵分配機制」。實作時需留意 ADB 延遲對 rollout 效率的影響，以及批次大小與 GPU 記憶體的平衡，並確保 hint 的 token 長度不會過度稀釋視覺特徵。
- **研究人員**：核心貢獻在於將「目標應用程式探索—課程探勘—rollout 執行—階層式回饋」統一於單一底層平台，並透過 hint-contextualized step-level GRPO 解決孤立 rollout 與粗略獎勵的問題。建議深入分析 MobileGym-Critic 的回饋顆粒度對策略最佳化收斂速度的影響，並思考如何將此框架擴展至 iOS、Web GUI 或桌面環境。
- **產品經理**：請聚焦實驗結果的商業意涵：MobileForge 僅用自動生成資料即可讓通用模型逼近、甚至超越封閉資料訓練的專用模型。評估導入時，請計算「節省的人工標註成本」與「GPU 運算成本」的權衡，並規劃「App 更新後自動重新適應」的產品流程，將技術優勢轉化為持續降低維運成本的商業價值。
