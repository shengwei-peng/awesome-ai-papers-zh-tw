## ⚡ TL;DR

空間推理代理雖能取得正確測量，卻常無法將證據轉化為最終答案。
S-Agent 2.0 以通用程式碼代理搭配命令列感知工具，閉合獲取、記憶、詮釋的證據迴圈。
在 MMSI-Bench 與 ReVSI 上大幅超越 SpatialClaw，且適用於多種程式碼代理框架。

## 摘要翻譯

空間推理（Spatial Reasoning）要求模型推算物體在三維空間（3D Space）中的位置、彼此之間的關係，以及其運動方式。代理式視覺語言模型（Agentic VLM）近來在此類任務上取得長足進展，其做法是讓模型主動以三維感知（3D Perception）工具蒐集證據，而非一次作答。然而，在許多問題中，即使工具回傳了正確的證據，模型仍無法得出正確答案：模型與工具之間的鴻溝——也就是將原始測量值（Reading）轉化為可用結論的環節——始終未被填補。我們提出 S-Agent 2.0，一種空間推理代理（Spatial Reasoning Agent），它為現成的通用程式碼代理（General-Purpose Coding Agent）配備一套命令列感知工具包（Command-Line Perception Toolkit），並圍繞一個核心原則設計介面：協助視覺語言模型（VLM）閉合證據迴圈（Evidence Loop）——獲取（Acquisition）場景證據（Scene Evidence）、將其存入持久化的場景記憶（Scene Memory）中，並以淺白的空間語言（Spatial Language）詮釋（Interpretation）每一筆測量值。此設計保留了程式碼代理（Coding Agent）的完整靈活性，且其所採用的每一筆測量值皆紮根於工具的幾何（Geometry）資訊之中。在 MMSI-Bench 與 ReVSI 上，該工具包使強大的開源模型（Open-Source Model）Qwen3.8-27B 相較於未配備工具的同一代理分別提升 +13.9 與 +20.5 分，並使強大的閉源模型（Closed-Source Model）Gemini-3.8-Flash 分別提升 +11.2 與 +9.6 分。採用開源骨幹模型（Backbone）時，S-Agent 2.0 在 MMSI-Bench 上達到 66.5、ReVSI 上達到 82.3，超越同一骨幹模型下的專用系統 SpatialClaw（62.6 與 74.5）；採用 Gemini-3.8-Flash 時則分別達到 74.1 與 90.5，而 SpatialClaw 為 67.0 與 79.7。隨著骨幹模型能力提升，雙方從工具中獲得的增益皆會縮減，但 SpatialClaw 在 ReVSI 上的縮減幅度遠大於本方法，從 +13.2 降至 +2.7，而本方法仍維持 +9.6。S-Agent 2.0 亦可相容於不同的通用程式碼代理框架（Harness），例如 Codex 與 Claude Code。

### 核心貢獻（3～5點）
- **指出並定義「證據迴圈缺口」問題**：揭示代理式視覺語言模型雖能透過三維感知工具取得正確證據，卻常無法將原始測量值轉化為正確結論，點出模型與工具之間的關鍵鴻溝。
- **提出 S-Agent 2.0 空間推理代理**：以現成的通用程式碼代理為骨幹，配備命令列感知工具包，圍繞「獲取—記憶—詮釋」三步驟的證據迴圈設計介面，兼顧程式碼代理的靈活性與測量值的幾何紮根性。
- **在多個基準上取得領先表現**：於 MMSI-Bench 與 ReVSI 上，無論搭配開源骨幹模型 Qwen3.8-27B 或閉源骨幹模型 Gemini-3.8-Flash，皆超越同骨幹下的專用系統 SpatialClaw。
- **展現骨幹模型擴展下的穩健增益**：隨骨幹模型能力提升，雙方工具增益皆縮減，但 S-Agent 2.0 在 ReVSI 上的增益縮減幅度遠小於 SpatialClaw（從 +13.2 降至 +2.7，本方法仍維持 +9.6），證明方法的泛化優勢。
- **具備代理框架的可移植性**：S-Agent 2.0 可無縫整合至不同的通用程式碼代理框架（如 Codex 與 Claude Code），展現跨代理框架的通用性。

### 適合對象
本研究最適合以下讀者閱讀：從事空間智能（Spatial Intelligence）、視覺語言模型（VLM）、AI 代理（AI Agent）與三維場景理解（3D Scene Understanding）研究的學者與工程師；關注代理式視覺語言模型（Agentic VLM）如何整合外部工具以提升推理能力的研究人員；以及對程式碼代理（Coding Agent）作為通用推理骨幹之應用感興趣的業界從業者。此外，由於論文橫跨基準評測（MMSI-Bench、ReVSI）與方法設計兩大面向，亦適合作為多模態推理與工具增強學習相關課程的進階教材。

## 深度分析

#### 方法論解析

S-Agent 2.0 的方法論核心在於一個被稱為「證據迴圈」（Evidence Loop）的設計哲學。論文作者觀察到，現有的代理式視覺語言模型（Agentic VLM）雖然配備了豐富的三維感知（3D Perception）工具，但在許多問題上，工具確實回傳了正確的測量值（Reading），模型卻仍然無法得出正確答案。這意味著問題不在於「獲取」（Acquisition），而在於「記憶」與「詮釋」（Interpretation）兩個環節的斷裂。

**三項設計需求**

論文將此診斷轉化為三項系統必須滿足的需求：

1. **獲取與模型自身感知相結合**：模型從圖像中辨識的內容與工具測量得到的數值必須進入同一個場景表示中。現有系統如 SpatialClaw 雖然提供豐富的感知與幾何（Geometry）函式庫，但將模型的視覺感知放在獨立的通道中處理，造成兩種感知之間的隔閡。

2. **持久化記憶（Persistent Memory）**：在某一步驟收集到的證據必須在後續多個步驟中保持完整且可定址（addressable），不應依賴模型將其攜帶在自己的上下文（context）中。這避免了「測量值留在工作區，但模型卻憑肉眼觀察圖片」的失敗模式。

3. **抵達即詮釋（Interpretation on Arrival）**：測量值應以問題所問的空間語言（Spatial Language）形式回傳，並附帶其詮釋。這解決了「模型正確測量了旋轉（Rotation），卻讀錯了座標系（Coordinate Frame）或方向」的失敗模式。

**系統架構**

S-Agent 2.0 由三個部分組成：

- **通用程式碼代理（General-Purpose Coding Agent）π**：作為規劃者與執行者。論文刻意採用現成的程式碼代理框架（如 OpenHands、Codex、Claude Code），而非設計專用系統。這些代理已具備空間推理所需的所有支架：shell、檔案系統、程式碼執行、長期上下文管理、成熟的工具呼叫迴圈。

- **命令列感知工具包（Command-Line Perception Toolkit）T**：設計重點所在。該工具包以 CLI 形式提供三維感知能力，每個指令都對應證據迴圈的一個環節。

- **持久化場景記憶（Scene Memory）S**：每個對話回合（episode）專屬的場景狀態儲存，由工具包讀寫。

**形式化定義**

給定一個空間問題，包含問題 q 與幀序列 I = {I₁, ..., Iₙ}，代理接收一個固定指令 u（包含工具包教學與建議工作流程）。在推理步驟 t，代理的上下文包含指令 u、問題 q 與自身的思維鏈歷史 z<ₜ、動作歷史 a<ₜ 與工具回應歷史 o<ₜ；策略 π 從中產生下一步動作。

**程式碼代理的兩個關鍵習慣**

論文特別強調通用程式碼代理的兩個習慣對空間推理的直接幫助：

1. **檢視幀或分割遮罩就是普通的檔案檢視**：模型對場景的觀察與工具的讀出（readout）交織在同一個對話串流中，兩者之間沒有獨立的影像通道。這使得兩種感知能自然地交織。

2. **檢查與修正是反射動作**：程式碼代理會檢視輸出、修正錯誤、再次執行。應用於場景時，這個反射動作正好將兩種感知結合起來——模型自身的感知在被採用為測量值之前，會先與工具記錄的內容核對。

**工具包設計的具體落實**

針對三項需求，工具包的設計如下：

- **獲取層面**：模型可以將其感知或想像的物件註冊為場景中的實例（instance），並丟棄工具測量錯誤的部分，使兩種感知落在同一個幾何基礎上。
- **記憶層面**：所有測量值持久化於場景記憶中，後續步驟以名稱查詢而非重新感知，確保已獲取的證據在答案寫出前始終在觸及範圍內。
- **詮釋層面**：每個測量值以「答案就緒」的空間語言形式回傳，並附帶其詮釋。

這種設計的精妙之處在於：它保留了通用程式碼代理的完整靈活性（因為工具包只是 CLI 指令），同時讓每個被採用的測量值都紮根於工具的幾何之中。

#### 實驗數據解讀

**基準測試（Benchmark）選擇**

論文選用兩個空間推理評測基準：MMSI-Bench（多模態空間智能基準）與 ReVSI（空間推理評測基準）。這兩個基準涵蓋了不同類型的空間推理任務，能夠全面評估系統在三維空間理解方面的能力。

**主要實驗結果**

在 Qwen3.8-27B（開源視覺語言模型，論文中的命名疑為 Qwen2.5-27B）骨幹模型（Backbone）上：

- 工具包帶來的增益：MMSI-Bench 上 +13.9 分，ReVSI 上 +20.5 分
- S-Agent 2.0 最終得分：MMSI-Bench 66.5 分，ReVSI 82.3 分
- 對比 SpatialClaw 在同一骨幹上的得分：62.6 分與 74.5 分

在 Gemini-3.8-Flash（閉源視覺語言模型，論文中的命名疑為 Gemini-2.5-Flash）骨幹模型上：

- 工具包帶來的增益：MMSI-Bench 上 +11.2 分，ReVSI 上 +9.6 分
- S-Agent 2.0 最終得分：MMSI-Bench 74.1 分，ReVSI 90.5 分
- 對比 SpatialClaw 在同一骨幹上的得分：67.0 分與 79.7 分

**數據解讀的關鍵洞察**

1. **工具增益隨模型能力提升而縮小**：這是一個重要的觀察。隨著骨幹模型從 Qwen3.8-27B 升級到 Gemini-3.8-Flash，S-Agent 2.0 的工具增益從 +13.9/+20.5 縮小到 +11.2/+9.6。這表明更強的模型本身已具備一定的空間推理能力，工具的邊際效用降低。

2. **SpatialClaw 的增益萎縮更為劇烈**：在 ReVSI 上，SpatialClaw 的工具增益從 Qwen3.8-27B 的 +13.2 萎縮到 Gemini-3.8-Flash 的 +2.7，而 S-Agent 2.0 保持在 +9.6。這說明 S-Agent 2.0 的設計在更強的模型上具有更好的可擴展性（Scalability），其證據迴圈設計能持續為強模型帶來實質幫助。

3. **跨代理框架的通用性**：S-Agent 2.0 在 OpenHands、Codex 與 Claude Code 三種不同的程式碼代理框架（Harness）上均能運作。這驗證了「將感知工具包作為 CLI 附加層」的設計選擇是成功的——它不依賴特定代理框架的內部機制。

4. **絕對性能優勢**：無論使用哪種骨幹模型，S-Agent 2.0 在兩個基準上都優於 SpatialClaw。在開源骨幹上領先 3.9 分（MMSI-Bench）與 7.8 分（ReVSI）；在閉源骨幹上領先 7.1 分（MMSI-Bench）與 10.8 分（ReVSI）。這個差距在 ReVSI 上尤為顯著，說明 S-Agent 2.0 在更複雜的空間推理任務上優勢更大。

**失敗分析**

論文對 SpatialClaw 的軌跡（Trajectory）進行了分析，發現失敗主要分為兩類：

- **第一類**：模型正確測量了某個值，卻在詮釋時讀錯（例如翻轉旋轉的符號、在錯誤的座標系中讀取正確的數字）。
- **第二類**：證據根本沒有被用於答案——測量值留在工作區，但模型憑肉眼觀察圖片；或者正確的測量值被以不相關的理由丟棄。

第二類失敗暴露了「收集證據」與「得出結論」之間的斷裂。一旦測量值進入，產生答案的推理就與它們脫節，模型退回到自身對場景的感知。S-Agent 2.0 的證據迴圈設計正是為了解決這兩類失敗。

#### 與現有研究的比較

**與 S-Agent（原始版本）的比較**

S-Agent 2.0 是 S-Agent 的後續工作。原始的 S-Agent 已經展示了代理式視覺語言模型在空間推理上的優勢——讓模型主動使用三維感知工具，而非單次回答。S-Agent 2.0 在此基礎上深化了「證據迴圈」的概念，將設計重點從「豐富的感知工具庫」轉移到「獲取-記憶-詮釋的閉環設計」。這是一個從「工具豐富度」到「工具與模型整合度」的範式轉移。

**與 SpatialClaw 的比較**

SpatialClaw 代表了「專用化」路線：設計一個自定義狀態機（State Machine），以計畫-執行-反思迴圈（Plan-Act-Reflect Loop）驅動視覺語言模型，搭配持久程式碼核心（Persistent Code Kernel）與三維感知幾何函式庫。S-Agent 2.0 則代表了「通用化」路線：使用現成的通用程式碼代理，將設計努力集中在工具介面層。

兩者的關鍵差異在於：

1. **靈活性 vs 專用性**：SpatialClaw 的狀態機是為空間推理量身打造的，可能在特定任務上更精準；但 S-Agent 2.0 保留了通用程式碼代理的全部靈活性，能跨代理框架運作。

2. **感知整合方式**：SpatialClaw 將模型的視覺感知放在獨立通道中，而 S-Agent 2.0 透過 CLI 工具包讓兩種感知交織在同一對話串流中。

3. **可擴展性**：如實驗數據所示，當骨幹模型升級到 Gemini-3.8-Flash 時，SpatialClaw 的工具增益在 ReVSI 上從 +13.2 萎縮到 +2.7，而 S-Agent 2.0 保持在 +9.6。這表明 S-Agent 2.0 的設計更能適應更強的模型。

4. **跨框架通用性**：S-Agent 2.0 明確展示了在 OpenHands、Codex、Claude Code 上的可移植性，而 SpatialClaw 作為專用系統，其可移植性受限。

**與其他空間推理方法的定位**

在更廣泛的空間推理研究領域中，S-Agent 2.0 的定位是「代理式空間推理」中的一個新分支。傳統的空間推理方法多依賴單次推理或專用模組，而 S-Agent 2.0 證明了「通用程式碼代理 + 精心設計的工具介面」這一組合的有效性。

**侷限性**

論文坦誠地指出幾項侷限性：

1. **工具增益隨模型增強而縮小**：這是所有工具增強方法面臨的共同挑戰。當模型本身已具備較強的空間推理能力時，工具的邊際效用降低。

2. **剩餘的模型-工具接地（grounding）差距**：論文的「Takeaways」第三點明確指出，模型的推理大致正確；剩下的問題是將問題接地到測量值，這在兩類情況下會失敗。這暗示了未來工作的方向。

3. **依賴通用程式碼代理的能力**：S-Agent 2.0 的成功部分建立在通用程式碼代理的成熟上。如果程式碼代理本身存在限制（如上下文視窗、工具呼叫可靠性），這些限制也會傳遞到 S-Agent 2.0。

#### 可重現性評估

**程式碼與工具包的可得性**

從論文內容來看，S-Agent 2.0 的設計強調「使用現成的通用程式碼代理」與「將感知能力作為 CLI 指令附加」。這種設計哲學本身有利於可重現性，因為：

1. **依賴的代理框架是公開的**：OpenHands、Codex、Claude Code 都是可獲取的框架（雖然 Codex 與 Claude Code 的內部細節可能不完全公開）。

2. **工具包以 CLI 形式提供**：CLI 介面比自定義狀態機更容易重現，使用者只需按照論文的教學指令操作即可。

然而，論文中並未明確提及程式碼是否已開源釋出。從論文的措辭（「我們建構了一個空間推理代理」）來看，程式碼可能會在後續釋出，但目前無法確認。

**資料集的可得性**

MMSI-Bench 與 ReVSI 都是公開的空間推理評測基準，研究者可以直接使用這些基準來驗證實驗結果。這增強了實驗的可重現性。

**模型權重的可得性**

- Qwen3.8-27B（疑為 Qwen2.5-27B）：作為開源模型，權重可公開獲取。
- Gemini-3.8-Flash（疑為 Gemini-2.5-Flash）：作為閉源模型，透過 API 存取，實驗可重現但需 API 存取權限。

**實驗細節的充分性**

論文提供了詳細的實驗數據，包括：
- 兩個基準上的絕對分數
- 工具帶來的增益（with tools vs without tools）
- 與 SpatialClaw 的直接比較
- 跨代理框架的驗證

這些細節足以讓其他研究者驗證主要結論。然而，論文中未提及的細節（如具體的提示詞模板、工具包的完整指令列表、評測時的隨機性控制）可能會影響精確的數字重現。

**軌跡分析的透明度**

論文對 SpatialClaw 的失敗軌跡進行了分析，這增加了定性結論的可信度。但這些軌跡本身是否公開釋出，論文中未明確說明。

#### 未來研究方向

**1. 縮小模型-工具接地差距**

論文明確指出，剩餘的失敗主要源於「將問題接地到測量值」的困難。未來工作可以探索：

- **更精細的問題解析機制**：將自然語言問題自動分解為對應的測量操作序列，減少模型在「該測什麼」上的歧義。
- **接地驗證機制**：在模型採用測量值之前，自動驗證該測量值是否真正回答了問題的子目標。
- **反例驅動的修正**：當模型給出錯誤答案時，自動追溯到具體哪個測量值的詮釋出了問題，而非籠統地重新推理。

**2. 擴展場景記憶的表達能力**

目前的場景記憶以「實例」為基本單位。未來可以探索：

- **層次化場景記憶**：支援物件-部件-子部件的層次結構，更貼近人類的空間認知。
- **時序場景記憶**：支援動態場景中物件隨時間變化的追蹤與記憶。
- **不確定性表達**：在場景記憶中保留測量的不確定性資訊，使推理能考慮測量誤差。

**3. 增強詮釋的空間語言**

目前的「抵達即詮釋」已是一大進步，但仍有提升空間：

- **多視角詮釋**：同一測量值可以從不同視角詮釋（例如「從觀察者角度看」vs「從世界座標系看」），讓模型能靈活切換。
- **相對與絕對空間語言的統一**：支援「在 A 的左邊」這類相對描述與「座標 (x, y, z)」這類絕對描述之間的自動轉換。
- **跨尺度詮釋**：支援從毫米級到公里級的空間描述，適應不同任務的尺度需求。

**4. 結合其他感知模態**

目前的工具包主要聚焦於三維幾何感知。未來可以整合：

- **語義感知**：將物件識別、場景理解等語義資訊整合進場景記憶。
- **物理感知**：加入重力、碰撞、支撐等物理關係的感知與推理。
- **時序感知**：追蹤物件的運動軌跡與速度，支援運動預測類任務。

**5. 從空間推理到空間行動**

S-Agent 2.0 目前聚焦於「理解」空間。未來可以擴展到「行動」：

- **機器人操作**：將空間推理結果轉化為機器人動作序列。
- **導航與路徑規劃**：基於場景記憶進行多步驟導航。
- **互動式空間探索**：讓代理主動決定下一步觀察哪裡，以最大化資訊獲取。

**6. 理論分析與形式化**

目前 S-Agent 2.0 的設計主要基於經驗觀察。未來可以：

- **形式化證據迴圈**：將「獲取-記憶-詮釋」三步驟形式化為可分析的計算模型。
- **失敗模式的理論分類**：建立更系統的失敗模式分類法，而非僅依賴軌跡觀察。
- **最優工具設計的理論指導**：探討在給定模型能力下，工具介面的最優設計原則。

**7. 與其他代理範式的融合**

S-Agent 2.0 採用了「程式碼代理 + CLI 工具」的範式。未來可以探索與其他範式的融合：

- **與思維鏈（Chain-of-Thought）結合**：在程式碼代理的推理過程中插入更細粒度的自然語言推理步驟。
- **與多代理系統結合**：讓不同代理分別負責獲取、記憶、詮釋，透過協作完成空間推理。
- **與強化學習結合**：透過環境反饋自動優化工具呼叫策略。

**8. 評測基準的擴展**

MMSI-Bench 與 ReVSI 已涵蓋了重要的空間推理任務，但仍有未覆蓋的面向：

- **真實世界複雜場景**：現有基準多為合成或受控場景，可擴展到真實世界的複雜場景。
- **多步驟空間推理**：需要多輪觀察與推理的長程任務。
- **反事實空間推理**：「如果物件 A 移動到位置 B，會發生什麼？」這類反事實推理。

這些方向不僅能推動 S-Agent 2.0 本身的演進，也能為整個空間推理領域帶來新的研究問題與方法論啟示。

## 論文問答

**Q1：什麼是空間推理（spatial reasoning），為什麼它在視覺感知與實體世界代理中如此重要？**
A：空間推理指的是模型理解物體在三維空間中的位置、彼此之間的空間關係，以及隨著觀察者移動時世界如何變化的能力。論文中引用文獻指出，空間智能是視覺感知的基礎能力（"foundational to visual perception"），也是任何在實體世界中運作的代理所必備的核心素質。從機器人到自駕車、從擴增實境到室內導航，這些應用都需要代理能準確判斷「東西在哪裡」、「它們如何相對排列」、「移動後會看到什麼」，因此空間推理被視為通往通用人工智慧的關鍵基石之一。

**Q2：現有的代理式視覺語言模型（agentic VLMs）在空間推理任務上為什麼會失敗？**
A：論文的診斷指出，現有系統（如 S-Agent 與 SpatialClaw）雖然配備了豐富的 3D 感知工具，但失敗往往不是發生在「獲取」階段，而是發生在「記憶」與「詮釋」兩個環節。具體而言，模型有時會誤讀已正確取得的測量值，例如翻轉旋轉的正負號、在錯誤的座標系中解讀數字；另一類失敗則是證據雖然被收集了，卻從未被用於最終答案——模型在寫答案時反而依賴自己對圖片的「目測」，讓工具的讀數被閒置在一旁。這顯示出模型與工具之間存在一道鴻溝：原始讀數需要被轉化為可用的結論，而現有系統幾乎把這項工作完全留給了模型本身。

**Q3：什麼是「證據迴圈」（evidence loop），為什麼它在空間推理中扮演關鍵角色？**
A：證據迴圈是論文中提出的核心概念，指的是一個空間答案要被正確建立所必須經歷的三個步驟：獲取（acquire）場景證據、記住（remember）這些證據直到答案寫出、以及詮釋（interpret）每筆讀數使其成為可用的理解。論點是，一個空間答案只有在這三個步驟都正確完成時才算「有根有據」（grounded）。現有專用系統幾乎把所有設計精力都投入在「獲取」上，提供越來越豐富的感知與幾何函式庫，卻把記憶與詮釋留給模型自行處理；這正是證據迴圈斷裂、模型最終回到「憑感覺看圖」的根本原因。

**Q4：S-Agent 2.0 的核心方法是什麼？它如何不同於先前的空間推理系統？**
A：S-Agent 2.0 的核心方法是將一個現成的通用程式碼代理（general-purpose coding agent）作為空間推理代理，並為其配上一套命令列形式的感知工具包（command-line perception toolkit）。與 SpatialClaw 等專用系統不同，S-Agent 2.0 並不設計自訂的狀態機或專屬的控制迴圈，而是直接利用程式碼代理既有的「shell、檔案系統、程式碼執行、長程上下文管理、成熟的工具呼叫迴圈」等基礎設施。設計的重點被轉移到工具介面本身：每個工具呼叫都同時完成獲取、寫入場景記憶、回傳已用空間語言詮釋過的讀數三件事，讓模型與工具的感知在同一個對話流中交織。

**Q5：S-Agent 2.0 為了「關閉證據迴圈」提出了哪三項關鍵設計要求？**
A：第一項是「獲取必須與模型自身的感知結合」：模型能將自己看到或想像到的物件註冊為場景中的實例，也能丟棄工具量錯的結果，讓兩種感知落在同一個幾何基礎上。第二項是「持久化的場景記憶」：所有量測結果都會被寫入一個跨步驟存取的場景記憶，後續步驟可以用名稱查詢，而不必重新感知整個場景。第三項是「讀數回傳時即完成詮釋」：每筆測量值在回傳時就已經用問題所用的空間語言表述，並附帶其詮釋，使模型不必再自行把數字翻譯成答案。這三項要求分別對應證據迴圈的三個步驟，是 S-Agent 2.0 設計工具介面的指導原則。

**Q6：為什麼選擇通用程式碼代理作為空間推理代理，而不是設計專用架構？**
A：通用程式碼代理已經具備空間推理代理所需的大部分基礎建設：shell、檔案系統、程式碼執行、長程上下文管理，以及成熟的工具呼叫迴圈，這些都是專用系統需要從頭打造的。更重要的是，程式碼代理有兩個對空間推理特別有價值的「習慣」：第一，看一張影像或一張分割遮罩對它而言只是普通的檔案檢視，因此模型對場景的觀察與工具的讀數能在同一個對話流中交織，沒有獨立的影像通道；第二，程式碼代理會本能地「檢查並修正」輸出，這個反射動作正好讓模型自身的感知與工具的測量互相對齊。論文的設計哲學是「保留程式碼代理的彈性，把感知能力以命令列的形式補上」，而不是從零打造一個專用代理。

**Q7：S-Agent 2.0 在哪些基準上進行了評測，主要結果為何？**
A：論文的評測涵蓋兩個空間推理基準：MMSI-Bench 與 ReVSI，並使用了兩個骨幹模型——開源的 Qwen3.8-27B 與閉源的 Gemini-3.8-Flash。在 Qwen3.8-27B 上，工具包相較於同一個代理不使用工具的版本，分別在 MMSI-Bench 與 ReVSI 上帶來 +13.9 與 +20.5 分的提升；在 Gemini-3.8-Flash 上，則分別帶來 +11.2 與 +9.6 分的提升。最終 S-Agent 2.0 以開源骨幹在 MMSI-Bench 達到 66.5 分、在 ReVSI 達到 82.3 分；以 Gemini-3.8-Flash 為骨幹則分別達到 74.1 與 90.5 分，全面超越了同骨幹下的 SpatialClaw。

**Q8：S-Agent 2.0 與專用系統 SpatialClaw 的比較結果如何？**
A：在相同的開源骨幹 Qwen3.8-27B 上，S-Agent 2.0 在 MMSI-Bench 達到 66.5 分、ReVSI 達到 82.3 分，皆優於 SpatialClaw 的 62.6 與 74.5 分；在 Gemini-3.8-Flash 上，S-Agent 2.0 達到 74.1 與 90.5 分，也高於 SpatialClaw 的 67.0 與 79.7 分。更值得注意的是，論文中強調 SpatialClaw 的工具增益在更強的骨幹上縮水得更快：在 ReVSI 上，SpatialClaw 的增益從開源骨幹的 +13.2 縮到 Gemini-3.8-Flash 上的 +2.7，而 S-Agent 2.0 仍維持 +9.6 的顯著增益。這顯示 S-Agent 2.0 的設計在更強的模型上仍保有實質價值，而非僅依賴骨幹本身的進步。

**Q9：S-Agent 2.0 的工具增益如何隨骨幹模型能力變化？**
A：論文的實驗顯示，無論是 S-Agent 2.0 還是 SpatialClaw，工具帶來的增益都會隨骨幹變強而縮小，這是合理的——更強的模型本身就有更好的空間感知能力。但兩者的縮水幅度不同：SpatialClaw 在 ReVSI 上的工具增益從 +13.2 縮到 +2.7，幾乎被骨幹進步所吸收；S-Agent 2.0 則仍維持 +9.6 的增益。這意味著 S-Agent 2.0 的設計不只是「給弱模型補工具」，而是真正在「模型與工具之間的鴻溝」上做改善，因此即使骨幹變強，工具介面所帶來的價值依然存在。

**Q10：S-Agent 2.0 適合哪些實際應用場景？**
A：任何需要在三維環境中推理的代理任務都是 S-Agent 2.0 的潛在應用場景，包括機器人操作（判斷物體在空間中的相對位置以規劃抓取）、自駕駛（理解車輛、行人與障礙物的空間關係）、擴增實境（將虛擬物件正確擺放於實體空間中）、室內導航與空間規劃（理解房間佈局與動線），以及任何需要「看圖＋量測＋推理」的工作流程。論文中強調 S-Agent 2.0 適用於「任何在實體世界中運作的代理」，這涵蓋了從工業自動化到輔助科技的廣大範圍。

**Q11：將 S-Agent 2.0 部署到實際產品時需要考量哪些因素？**
A：首先，雖然 S-Agent 2.0 使用通用程式碼代理降低了系統複雜度，但每個空間問題仍需要多次工具呼叫與推理迭代，這對延遲敏感的即時應用（如自駕車）會是挑戰，需要在推理深度與回應時間之間取捨。其次，感知工具的精準度直接決定了最終答案的可靠性，產品化時必須確保工具在各種真實環境（光線、遮擋、動態場景）下的魯棒性。最後，場景記憶的設計雖然讓證據可被重複使用，但也意味著需要管理跨步驟的狀態一致性，這在多代理協作或長時間任務中會增加系統設計的複雜度。

**Q12：S-Agent 2.0 對空間人工智慧領域的整體影響是什麼？**
A：S-Agent 2.0 的最重要貢獻在於「重新分配設計重心」：它把空間推理系統的價值從「堆積更多感知工具」轉移到「如何讓模型與工具無縫對接」。論文中提出的「證據迴圈」框架為未來空間推理系統提供了一個清晰的設計準則——必須同時解決獲取、記憶、詮釋三個問題，而非僅專注其一。此外，S-Agent 2.0 證明了通用程式碼代理可以被有效「借用」為空間推理代理，這種「以通用代理承載特定任務」的思路可能會延伸到其他需要工具輔助推理的領域（如科學推理、程式碼理解、醫療診斷），具有方法論上的啟發意義。

**Q13：S-Agent 2.0 論文自己承認了哪些限制？**
A：論文坦承，工具帶來的增益會隨骨幹模型變強而縮小，這意味著在未來更強的模型上，純粹的空間感知能力可能會逐漸內化到模型本身，使得工具介面的相對價值降低。此外，雖然 S-Agent 2.0 在多個程式碼代理框架（OpenHands、Codex、Claude Code）上都驗證有效，但每個框架的細節差異仍可能影響實際表現，需要進一步的跨框架標準化研究。論文也指出，剩餘的失敗主要集中在「將問題對接到測量」的接地（grounding）環節，這是目前方法尚未完全解決的瓶頸。

**Q14：S-Agent 2.0 在哪些情況下仍然會失敗？**
A：根據論文對軌跡的分析，剩餘的失敗可分為兩類。第一類是「詮釋錯誤」：模型雖然拿到了正確的測量值，卻在解讀時翻轉旋轉的正負號、在錯誤的座標系中讀數，或以錯誤的方向感理解數值。第二類是「證據未用於答案」：測量值已經被收集並放在工作區中，但模型在寫最終答案時並未參考，反而回頭依賴自己對圖片的目測判斷。這兩類失敗都屬於「模型到工具接地」（model-to-tool grounding）的問題，也就是模型尚未完全學會把問題語言精準對應到工具能提供的測量上。

**Q15：S-Agent 2.0 未來的研究方向有哪些？**
A：論文中暗示了幾個值得探索的方向。首先，既然「模型到工具的接地」是當前的主要瓶頸，未來可以研究如何讓模型更可靠地把自然語言問題轉譯為精確的測量請求，例如透過更結構化的工具描述或專門的接地訓練資料。其次，雖然 S-Agent 2.0 已在多個程式碼代理框架上驗證，但跨框架的標準化與最佳實踐仍待建立，這將影響方法的實際可移植性。最後，隨著骨幹模型持續變強，如何讓工具介面在「強模型時代」仍保有不可取代的價值（例如透過更深的幾何推理、更可靠的座標系管理），將是這個領域長期的核心議題。

## 實務應用指南

### 適用場景

S-Agent 2.0 的核心能力是「讓視覺語言模型主動呼叫 3D 感知工具、累積場景證據，並以空間語言得出結論」，因此最適合需要**模型自主探索場景並做出空間判斷**的任務，而非單純的圖片分類或物件偵測。以下是五個具體可落地的應用場景：

1. **機器人自主操作與導航**：在倉儲、餐飲、醫療等動態環境中，機器人需要即時判斷「杯子在桌子的左前方 30 公分」「門把手的旋轉軸方向」等細粒度空間關係。S-Agent 2.0 的場景記憶可讓機器人在多步操作中持續追蹤已測量的物件位置，避免每個動作都重新感知整個場景。

2. **建築與室內設計的 AI 助理**：設計師上傳施工現場的多角度照片或影片，代理可主動呼叫深度估計、平面偵測、體積量測等工具，回答「這面牆是否能拆除？」「這個空間是否符合無障礙法規的迴轉半徑？」等需要 3D 推理的問題。

3. **AR/VR 內容生成與場景理解**：在混合實境應用中，代理可根據使用者拍攝的場景，主動測量物件距離、估算空間尺度，並以空間語言回報「沙發距離電視 2.3 公尺，視角約 35 度」，供後續的虛擬物件擺放使用。

4. **自駕車邊角案例（corner case）分析**：將行車記錄器影片輸入代理，讓其主動呼叫物件追蹤、光流、深度估計等工具，分析「這輛車在變換車道時與後車的相對速度與角度變化」，協助團隊回放並理解事故邊角案例。

5. **工業檢測與遠距巡檢**：在工廠、橋梁、輸電塔等場域，巡檢人員拍攝多角度影像，代理可主動測量裂縫長度、鏽蝕面積、構件傾斜角度，並以空間語言產出結構化報告，輔助工程師判斷風險等級。

### 實作前置條件

**資料需求**
- **多視角影像或影片資料**：每個場景至少需要數張至數十張不同視角的影像（論文使用 MMSI-Bench、ReVSI 等基準，皆為多視角影片幀）。
- **3D 感知模型的預訓練權重**：包括深度估計（如 Depth Anything、Metric3D）、物件偵測與分割（如 SAM2、Grounded-SAM）、光流（如 RAFT）、特徵匹配（如 SuperPoint + SuperGlue）等。
- **（選擇性）場景的 ground truth 標註**：用於驗證代理輸出的正確性，例如物件的 3D 位置、旋轉角度、距離等。

**運算資源**
- **骨幹模型推論**：Qwen2.5-27B 等開源 VLM 建議至少單張 A100/H100 80GB；Gemini-2.5-Flash 等閉源模型透過 API 即可。
- **3D 感知工具**：深度估計與分割模型通常需要 16–24GB VRAM；若需即時處理影片幀，建議準備多卡環境。
- **程式碼代理框架**：OpenHands、Codex、Claude Code 等皆為雲端服務或本地部署，後者需要對應的執行環境（Docker、Python、Node.js 等）。

**技能門檻**
- **3D 計算機視覺基礎**：熟悉相機內外參、座標系轉換、旋轉表示（歐拉角、四元數、旋轉矩陣）。
- **VLM 工具呼叫設計**：理解如何設計 CLI 介面、JSON schema、錯誤處理，讓模型能穩定地呼叫工具。
- **程式碼代理框架使用經驗**：熟悉至少一種 coding agent harness 的工作流程、上下文管理、檔案系統操作。
- **（加分）機器人學或 AR/VR 開發經驗**：若目標應用涉及即時控制或渲染，需具備對應領域的整合能力。

### 實作步驟建議

從論文到產品的落地可分為五個階段：

**階段一：選擇並部署骨幹模型與代理框架（1–2 週）**
- 評估預算與延遲需求，選擇開源（Qwen2.5-27B）或閉源（Gemini-2.5-Flash）骨幹。
- 部署或訂閱至少一種 coding agent harness（OpenHands 開源可自架；Codex、Claude Code 為閉源服務）。
- 驗證骨幹模型在「看圖 + 呼叫 CLI 工具 + 讀取文字輸出」這一基本循環上的穩定性。

**階段二：盤點並封裝 3D 感知工具（2–4 週）**
- 依目標應用挑選必要的感知工具（深度、分割、光流、特徵匹配等）。
- 將每個工具封裝為 CLI 命令，統一輸入（影像路徑、參數）與輸出（JSON 或純文字）。
- 為每個工具設計「空間語言化」的輸出格式，例如 `depth_at_pixel --image frame.png --pixel 320,240` 回傳「該像素對應的實體點距離相機 2.3 公尺，位於相機前方偏右 15 度」。

**階段三：設計場景記憶與證據迴圈（2–3 週）**
- 實作一個持久化的場景記憶（檔案或小型資料庫），儲存已測量的物件、座標、屬性。
- 設計「獲取 → 記憶 → 詮釋」三步驟的 CLI 介面：每次呼叫工具時，自動將結果寫入場景記憶，並以空間語言回傳。
- 提供「查詢」指令，讓模型能以物件名稱（如「杯子」「門把手」）而非座標來存取已測量的證據。

**階段四：撰寫教學指令與工作流程模板（1 週）**
- 為代理撰寫一份固定的 system instruction，說明工具清單、呼叫語法、建議工作流程（決定需要哪些證據 → 呼叫工具取得證據 → 檢查感知輸出 → 從已取得的證據回答）。
- 準備 few-shot 範例，展示正確的證據迴圈使用方式。

**階段五：評估、迭代與部署（2–4 週）**
- 在目標領域的驗證集上評估代理的正確率、工具呼叫次數、平均延遲。
- 分析失敗案例，特別關注「模型讀錯測量值」與「證據未被使用」兩類錯誤（論文 §3.4）。
- 根據錯誤模式調整工具輸出格式、場景記憶結構或教學指令。

### 潛在風險與注意事項

**風險一：工具增益隨骨幹模型增強而縮減**
- **現象**：論文明確指出，隨著骨幹模型變強（如從 Qwen2.5-27B 換到 Gemini-2.5-Flash），工具帶來的增益會縮小（ReVSI 上 SpatialClaw 從 +13.2 縮到 +2.7）。
- **緩解**：在選用骨幹前先評估「無工具」基線；若骨幹已很強，可考慮簡化工具集，只保留高價值的感知能力。

**風險二：模型對測量值的詮釋錯誤**
- **現象**：模型可能正確取得旋轉角度，卻讀錯正負號或座標系（論文 §1 提到的第一類失敗）。
- **緩解**：在工具輸出中明確標註座標系、單位、符號約定；提供「座標系轉換」工具讓模型自查。

**風險三：證據未被使用，模型退回自身感知**
- **現象**：測量值已寫入場景記憶，但模型在最終回答時忽略，改用「肉眼判斷」（論文 §1 提到的第二類失敗）。
- **緩解**：在教學指令中強調「回答必須基於已取得的測量值」；在最終回答前加入一個「自我檢查」步驟，要求模型列出使用了哪些場景記憶中的證據。

**風險四：場景記憶膨脹導致上下文爆炸**
- **現象**：隨著測量次數增加，場景記憶可能累積大量資料，擠壓模型的推理上下文。
- **緩解**：設計「摘要」或「分頁查詢」機制；只將與當前問題相關的證據載入上下文。

**風險五：工具呼叫成本與延遲**
- **現象**：每個問題可能需要數十次工具呼叫，累積的 API 成本與延遲在生產環境中不可忽視。
- **緩解**：設計「批次呼叫」介面；對閉源骨幹使用快取；對開源骨幹考慮量化或蒸餾。

**風險六：座標系與單位混淆**
- **現象**：不同工具可能使用不同的座標系（相機座標系 vs 世界座標系）或單位（公尺 vs 英尺）。
- **緩解**：在場景記憶中統一儲存格式；提供標準化的轉換工具。

### 與其他技術的整合建議

**與機器人作業系統（ROS）整合**
- 將 S-Agent 2.0 的場景記憶對接 ROS 的 TF 座標樹，讓機器人可直接使用代理輸出的空間關係進行運動規劃。
- 將代理的「查詢物件位置」指令封裝為 ROS service，供導航與操作節點呼叫。

**與 CAD/BIM 系統整合**
- 將場景記憶中的測量結果匯出為 IFC 或 glTF 格式，匯入 Revit、ArchiCAD 等 BIM 工具。
- 反向亦可：讓代理讀取 BIM 模型，輔助現場比對施工進度。

**與 AR/VR 引擎整合**
- 透過 Unity 或 Unreal 的 plugin，將代理輸出的「物件位置 + 姿態」即時同步到虛擬場景。
- 在 AR 應用中，可將代理作為「空間問答助理」，讓使用者用語音詢問「我的鑰匙在哪裡？」，代理即時呼叫工具並回答。

**與自駕車感知堆疊整合**
- 將 S-Agent 2.0 作為「高階場景理解層」，接在現有的物件偵測、追蹤、深度估計模組之上。
- 代理可讀取這些模組的輸出，主動呼叫進一步的分析工具（如軌跡預測、風險評估），並以自然語言回報給安全員。

**與多代理系統整合**
- 將 S-Agent 2.0 作為「空間專家代理」，與其他專家（如語言代理、規劃代理）組成 multi-agent system。
- 透過標準化的 MCP（Model Context Protocol）或 function calling 介面，讓其他代理能查詢空間資訊。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀 §1 的問題診斷（圖 4 的失敗案例）與 §1.2 的三點 takeaways，建立「證據迴圈」這個核心心智模型。接著跳讀 §2.1 的形式化定義，理解「指令 u、問題 q、歷史 z<t、動作 a<t、工具回應 o<t」這些符號的意義。實作上可從「用 OpenHands + 一個深度估計 CLI」開始，逐步體會「獲取 → 記憶 → 詮釋」三步驟如何運作。

**給 AI 工程師**：重點閱讀 §2 的方法設計，特別是「場景記憶如何持久化」「工具輸出如何空間語言化」「模型自身感知如何與工具感知對齊」這三個工程細節。§3.4 的錯誤分析對除錯特別有價值——當你的代理出錯時，可對照論文的兩類失敗模式（讀錯測量值 vs 證據未被使用）來定位問題。實作上建議直接從 §3.3 的跨框架實驗切入，驗證 S-Agent 2.0 在你慣用的 coding agent（Codex 或 Claude Code）上是否同樣有效。

**給研究者**：§1 的問題診斷與 §3.4 的錯誤分析是本文最有學術價值之處——它揭示了「工具增益」並非單純來自感知能力，而來自「證據迴圈」的閉合。建議進一步追問：當骨幹模型繼續增強，證據迴圈的哪些環節會成為新的瓶頸？「空間語言化」的輸出是否能用更形式化的表示（如場景圖）取代？這些都是值得延伸的研究方向。

**給產品經理**：重點關注 §1.2 的三點 takeaways 與 §3.2、§3.3 的數字。論文的關鍵訊息是：S-Agent 2.0 在開源骨幹上已超越專用系統 SpatialClaw，且方法可移植到不同的 coding agent 框架，這代表技術風險可控、供應鏈不會被單一框架綁定。建議在產品規劃時，將「空間推理」定位為「可插拔的能力層」，而非「必須自研的核心模組」，以保留未來切換骨幹或框架的彈性。
