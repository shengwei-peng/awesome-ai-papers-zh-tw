## 深度分析

#### 方法論解析

Switch-SWE 的方法論核心在於將「任務恢復能力」(focus-task resumption) 從傳統的單一議題評估範式，轉化為可量化、可配對比較的「工作階段層級評估」(session-level evaluation)。此方法論設計包含三個關鍵支柱：

**1. 配對工作階段設計 (Matched Session Design)**

論文採用嚴格的配對控制變因設計：每個焦點任務 (focus task) 同時在「不中斷工作階段」(uninterrupted session) 與「切換式工作階段」(switched session) 中執行。兩種工作階段共享相同的焦點需求、可執行驗證器 (executable verifier) 與任務專屬的持久化簽出 (persistent checkout)，唯一差異在於切換式工作階段是否插入了來自同一儲存庫的其他未完成任務階段。這種設計巧妙地隔離了「工作階段層級恢復」與「磁碟衝突」(on-disk conflicts) 等混雜變因，使測量焦點純粹落在代理 (agent) 的任務恢復能力上。

**2. 多階段任務重建 (Multi-stage Task Reconstruction)**

不同於 SWE-bench 將任務簡化為「議題到修補段」(issue-to-patch episode)，Switch-SWE 從真實的議題歷史 (issue history)、拉取請求 (pull request) 與審查歷史 (review history) 中重建出「實質階段」(substantive stage)。每個切換式工作階段將焦點任務與同一儲存庫中的四個未完成任務交錯編排，並透過「來源局部性」(source locality) 維度——即中斷任務與焦點任務是否屬於同一子系統——來分析任務恢復的難易度差異。

**3. 外掛式上下文管理模組 (Plug-in Context-Management Module)**

針對軌跡分析 (trajectory analysis) 中識別出的兩大恢復行為缺陷——「跨任務需求混淆」(cross-task requirement confusion) 與「任務狀態遺失」(loss of task state)——論文提出了一個外掛模組 (plug-in module)，其設計哲學是「不改變代理原生執行流程」(leaves the agent's native execution workflow unchanged)。該模組包含兩個互補機制：
- **任務相關歷史選擇 (task-relevant history selection)**：從累積的對話與操作歷史中篩選與當前活躍任務相關的片段，避免不相關任務的上下文污染。
- **任務狀態摘要 (task-state summary)**：為每個任務維護精簡的進度摘要，使代理在恢復時能快速重建任務的累積狀態。

此模組的「外掛式」設計哲學值得注意：它不修改代理的核心推理或執行機制，僅在上下文層進行過濾與摘要，這使其具備良好的可移植性，但同時也意味著其效能上限受限於底層代理的基礎能力。

#### 實驗數據解讀

**1. 焦點任務解決率落差 (Focus-task Resolution Gap)**

在 7 個程式碼代理 (coding agent) 的評估中，交錯未完成工作 (interleaved unfinished work) 造成了平均 11.5 個百分點的焦點任務解決率落差，範圍從 6.0 到 15.0 個百分點。此數據揭示了一個重要現象：即使焦點需求、驗證器與工作空間完全一致，僅僅是「工作階段中插入了其他未完成任務」就足以顯著降低代理的任務完成能力。落差的範圍跨度（6.0 至 15.0 pp）暗示不同代理架構對任務切換的敏感度存在結構性差異，這可能與其上下文窗口管理策略、注意力機制或內部狀態追蹤方式有關。

**2. 成本與效能的反比關係 (Cost-Resolution Trade-off)**

圖 1(a) 呈現了一個在實務部署中極為關鍵的現象：「成本上升、解決率下降」(Cost More, Resolve Less)。各代理在切換式工作階段中的成本增幅從 +40.9% 到 +195.3% 不等，而解決率則普遍下降 6 至 15 個百分點。這意味著任務切換不僅降低品質，還大幅增加運算成本——代理在嘗試恢復任務時消耗了更多推理資源卻產出了更差的結果。這對實際部署中的成本控制構成了直接挑戰。

**3. 失敗模式分類 (Failure Mode Breakdown)**

圖 1(b) 將失敗劃分為三類：「實作失敗」(implementation failure)、「提交失敗」(submission failure) 與「執行未完成」(incomplete execution)。此分類有助於診斷問題根源：實作失敗反映代理無法正確理解或實作需求；提交失敗暗示代理在切換後未能正確定位需要提交的修補；執行未完成則可能源於上下文過長導致的推理中斷或資源耗盡。

**4. 外掛模組的改善效果**

在 OpenCode 框架上，外掛上下文管理模組使焦點任務完成率在同儲存庫任務切換 (same-repository task switching) 情境下提升了 5.5 至 15.5 個百分點。此改善幅度與前述的 11.5 pp 平均落差形成有意義的對比：模組能恢復相當比例的效能損失，但無法完全消除。這暗示任務切換的效能損失部分來自上下文管理，部分來自更深層的推理或狀態追蹤限制。

#### 與現有研究的比較

**1. 與儲存庫層級基準的比較**

Switch-SWE 與 SWE-bench、SWE-bench-Live、Multi-SWE-bench、DeepSWE 等儲存庫層級基準 (repository-level benchmark) 共享「可執行驗證」的基礎設施，但根本性地改變了評估單位：從「一個議題到一個修補」轉變為「一個儲存庫中的多任務工作階段」。SWE-Touch 關注使用者程式碼編輯的適應，Switch-SWE 則關注任務間的恢復；兩者皆處理「任務進行中的變化」，但變化來源不同——前者來自使用者編輯，後者來自代理自身的任務切換。

**2. 與長時程開發基準的比較**

SWE-Marathon、SWE-EVO、SWE-Milestone 與 ChainSWE 等基準強調「持續執行」(sustained execution)、「相依里程碑」(dependent milestones) 或「累積變更」(cumulative changes)。Switch-SWE 與這些工作的關鍵區別在於：長時程基準假設任務之間存在邏輯相依性或累積性，而 Switch-SWE 刻意將焦點任務與中斷任務設計為「同儲存庫但獨立」，以純化「恢復」這一變因。這種設計選擇使 Switch-SWE 能夠回答一個更精確的問題：在沒有任務相依性的情況下，代理是否仍能恢復？

**3. 與中斷適應基準的比較**

InterruptBench 評估網頁導航中對變更使用者目標的適應能力，與 Switch-SWE 在「目標變更」的概念上有交集，但領域與粒度截然不同。InterruptBench 處理的是使用者主動變更的目標，Switch-SWE 處理的是代理自主推進的多任務排程。

**4. 限制與侷限性**

儘管 Switch-SWE 的設計嚴謹，仍存在幾項侷限性：
- **語言侷限**：僅涵蓋 19 個 Python 儲存庫，未涵蓋多語言場景。
- **任務數量**：200 個焦點任務相較於 SWE-bench 的規模較小，統計檢定力可能受限。
- **中斷模式固定**：每個切換式工作階段固定插入四個未完成任務，未探索中斷頻率、密度等維度的影響。
- **外掛模組的通用性**：改善效果僅在 OpenCode 上驗證，未展示跨代理框架的可移植性。

**3. 可重現性的挑戰**

#### 未來研究方向

**1. 多語言與跨領域擴展**

將 Switch-SWE 從 Python 儲存庫擴展至 Java、JavaScript、Rust 等語言，以及從開源專案擴展至企業級程式碼庫，將有助於檢驗任務恢復能力是否具有語言或領域特異性。此外，跨儲存庫任務切換（而非僅限同儲存庫）將測試更極端的恢復挑戰。

**2. 中斷模式的系統化探索**

當前設計固定了中斷任務的數量（4 個）與來源（同一儲存庫）。未來研究可系統性地探索中斷頻率、中斷密度、中斷任務的相似度等維度如何影響恢復效能，並建立「恢復難度光譜」(resumption difficulty spectrum)。

**3. 深層狀態追蹤機制**

外掛模組的改善（5.5–15.5 pp）雖有意義但未完全消除落差，暗示需要更深層的狀態追蹤機制。未來方向包括：
- **結構化任務記憶**：將任務狀態編碼為結構化表示（如任務圖、依賴關係圖）而非自由文本摘要。
- **檢索增強恢復**：利用語義檢索從歷史軌跡中精確定位與當前任務相關的片段。
- **持久化任務狀態**：將任務狀態寫入磁碟而非僅依賴上下文窗口，模擬人類開發者的筆記本或 TODO 列表。

**4. 人機協作情境的延伸**

當前評估假設代理自主推進多個任務。實際開發中，使用者經常介入並重新排序任務優先級。將 Switch-SWE 擴展至「使用者介入式任務切換」將更貼近真實工作流程。

**5. 理論框架的建立**

當前的軌跡分析揭示了跨任務需求混淆與任務狀態遺失兩大模式，但缺乏統一的理論框架來解釋任務恢復失敗的機制。未來研究可借鑒認知科學中的「工作記憶」(working memory) 與「情境切換成本」(context-switching cost) 理論，建立程式碼代理任務恢復的形式化模型。

**6. 基準的縱向演進**

隨著程式碼代理能力的提升，Switch-SWE 的 11.5 pp 平均落差可能會縮小。基準需要持續演進以維持鑑別度，例如引入更複雜的多階段任務、更密集的任務切換，或結合 SWE-EVO 等的演化特性，使基準始終對前沿代理構成有效挑戰。

### 實作步驟建議

**步驟 1：建立配對工作階段規格**
從目標儲存庫的 issue/PR/review 歷史中挑選焦點任務，每個任務重建其「實質階段」序列。為每個焦點任務產生兩個配對規格：
- 不中斷工作階段：依序執行焦點任務的所有階段。
- 切換式工作階段：插入 4 個來自同儲存庫的其他未完成任務的階段，僅在最後評分焦點修補。
確保兩個規格的焦點需求、可執行驗證器、持久化簽出完全一致。

**步驟 2：設計任務切換的「來源局部性」維度**
依論文做法，將插入任務分為「同子系統」與「不同子系統」兩類。這能幫助你分析代理在跨模組切換時是否更容易遺失焦點任務狀態，並作為後續優化的診斷依據。

**步驟 3：實作基準評估管線**
對每個目標代理（建議至少 3 個以觀察落差分布）執行 400 個工作階段，記錄：
- 焦點任務解決率（pass/fail，依可執行驗證器）
- 每任務成本（USD）
- 失敗類型分類：實作失敗、提交失敗、執行未完成
- 完整 trajectory log（含每步的 prompt、tool call、回應）

**步驟 4：分析軌跡並標記恢復行為**
從 trajectory 中識別兩類反覆出現的恢復行為：
- 跨任務需求混淆：代理在焦點任務階段引用了插入任務的需求或檔案路徑。
- 任務狀態遺失：代理忘記先前已完成的子步驟、重做已修改的檔案、或遺漏先前發現的測試失敗。
這兩類標記將作為後續模組設計的需求來源。

**步驟 5：實作外掛式上下文管理模組**
依論文設計，模組應包含兩個核心元件：
- 任務相關歷史選擇器：從完整對話歷史中篩選與當前焦點任務相關的訊息（可用 embedding similarity、關鍵字比對，或 LLM 評分）。
- 任務狀態摘要產生器：為每個任務維護一段簡潔的狀態摘要（已完成步驟、待辦事項、已修改檔案、已知測試結果），在切換時更新、在恢復時注入 prompt。
模組應為 plug-in 形式，不修改代理原生執行流程與持久化簽出。

**步驟 6：在 OpenCode 上掛接模組並重跑評估**
將模組掛接到 OpenCode 的 context construction 層，確保模組在每次任務切換時自動觸發歷史選擇與摘要更新。重跑相同的 400 個工作階段，比較焦點任務解決率。論文中此模組帶來 5.5–15.5 百分點的提升。

**步驟 7：建立持續監控儀表板**
將「焦點任務解決率落差」與「每任務成本」繪成類似論文圖 1(a) 的散佈圖，並依模型分組。當新模型或新代理版本上線時，自動跑 Switch-SWE 子集並比對歷史基準，及早發現切換敏感度退化。

### 潛在風險與注意事項

**風險 1：評估成本失控**
論文圖 1(a) 顯示切換式工作階段的成本比不中斷高出 40–195%。若完整跑 7 個代理 × 400 規格，總成本可能突破六位數美元。
**緩解**：先用 50–80 個工作階段的子集做 pilot，確認代理與模組行為後再擴大；對昂貴模型（如 Claude Opus 5）僅跑代表性子集。

**風險 2：可執行驗證器的脆弱性**
許多 Python 儲存庫的 test suite 對環境依賴敏感（DB、network、特定 Python 版本），導致驗證器誤判。
**緩解**：在重建任務時優先選擇依賴少的測試；為每個任務準備 fallback behavioral verifier（論文中 DeepSWE 採用的做法）。

**風險 3：任務重建引入偏誤**
從 issue/PR 歷史重建的「實質階段」可能與開發者真實思考順序不同，導致評估偏離實際工作流程。
**緩解**：邀請原儲存庫的貢獻者審閱階段切分；保留原始 commit hash 與 PR 連結以便追溯。

**風險 4：上下文管理模組本身可能引入新錯誤**
任務相關歷史選擇器若過度裁剪，可能移除代理所需的工具輸出；摘要產生器若過度壓縮，可能遺失關鍵錯誤訊息。
**緩解**：保留「完整歷史 fallback」機制；對模組輸出做 A/B 測試，監控「實作失敗」是否反而上升。

**風險 5：來源局部性混淆結論**
若插入任務與焦點任務過度重疊，可能讓「跨任務需求混淆」變得過於容易，反而低估代理的真實能力。
**緩解**：依論文設計保留「同子系統」與「不同子系統」兩類插入任務，並分別報告結果。

**風險 6：代理框架版本漂移**
OpenCode、Claude Code 等框架更新頻繁，trajectory 格式與 tool calling 介面可能改變，導致歷史評估結果無法直接比較。
**緩解**：在每次評估時鎖定框架版本；將框架版本納入結果 metadata。

### 與其他技術的整合建議

**與 SWE-bench / SWE-bench-Live 整合**
Switch-SWE 不取代 SWE-bench，而是補充「工作階段層級」評估維度。建議在 CI 中同時跑兩者：SWE-bench 衡量單任務能力，Switch-SWE 衡量多任務恢復能力。兩者分數組合可作為代理的「綜合工程能力」指標。

**與 SWE-ContextBench 整合**
SWE-ContextBench 評估跨任務的 context reuse，Switch-SWE 評估跨任務的 context isolation。兩者看似對立，實際上互補：好的代理應同時具備「選擇性重用」與「選擇性隔離」能力。可將兩者的基準分數繪成二維圖，找出在兩個維度上都表現良好的代理。

**與 InterruptBench 整合**
InterruptBench 處理的是「使用者目標改變」，Switch-SWE 處理的是「任務切換」。兩者可共用 trajectory analysis 工具，特別是「需求混淆」的標記 schema。建議將兩類失敗模式統一編碼，便於跨基準比較。

**與 RAG / 長期記憶系統整合**
論文的上下文管理模組本質上是 task-aware 的 context retrieval，可直接借用 RAG 技術棧（如向量資料庫、reranker）。但要注意：Switch-SWE 的「任務狀態摘要」是結構化的（已完成步驟、待辦、修改檔案），而非純文字摘要，建議用結構化欄位儲存。

**與專案管理工具整合**
若企業已有 Jira、Linear 等任務系統，可將 Switch-SWE 的「焦點任務」概念映射為 ticket，「實質階段」映射為 ticket 的 sub-task。代理在切換時可自動從 ticket 系統讀取最新狀態，減少摘要維護負擔。

**與 CI/CD 整合**
將 Switch-SWE 評估管線接入 CI，每次代理框架或底層模型升級時自動跑子集並產生報告。建議設定 threshold：若焦點任務解決率落差超過 15 個百分點，阻擋合併。

### 給不同背景讀者的閱讀建議

**給初學者**：先讀摘要與圖 1，理解「為什麼切換任務會讓代理變差」這個直覺現象，再看第 1 節的問題陳述。論文的配對設計（matched uninterrupted vs. switched）是理解整篇的關鍵錨點。技術細節可先跳過，專注在「焦點任務解決率落差 11.5 個百分點」這個核心數字代表的意義。

**給 AI 工程師**：重點讀第 1 節末尾的「plug-in context-management module」設計與第 4 節的實作細節（若全文可取得）。兩個核心元件——任務相關歷史選擇器與任務狀態摘要產生器——是可直接移植到你們代理框架的元件。建議先在內部代理上重現論文的 5.5–15.5 百分點增益，再考慮擴展到更多模型。

**給研究者**：第 2 節的相關工作分類（repository-level、long-horizon、context reuse、interrupt）提供了清楚的研究地圖定位。Switch-SWE 開源了 400 個工作階段規格與 trajectory 資料，是研究「任務恢復行為」的寶貴資源。建議從 trajectory analysis 著手，特別是「跨任務需求混淆」與「任務狀態遺失」這兩類行為的量化指標設計，這是目前文獻較少觸及的方向。

**給產品經理**：這篇論文回答的核心問題是「AI 助理在真實多任務開發情境下是否可靠」。圖 1 的「成本上升、解決率下降」雙重警示，是向高階或客戶溝通 AI 助理限制時的有力證據。建議將「焦點任務解決率落差」列為產品的關鍵品質指標（KQI），並在產品文件中誠實揭露目前代理在多任務切換下的表現，避免過度承諾。
