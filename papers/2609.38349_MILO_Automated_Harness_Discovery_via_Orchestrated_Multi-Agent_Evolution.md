## 摘要翻譯

現代代理系統（agentic systems）結合了 AI 模型與控制執行及環境互動的 Harness（harness，代理執行架構）。Harness 設計對長程表現（long-horizon performance）有重大影響，然而其組合搜尋空間（combinatorial search space）龐大，需耗費大量人力，且每當模型更迭都須重新投入。現有的自動化方法僅狹隘地探索此空間，只最佳化提示（prompts）、技能（skills）等個別元件，或受困於固定且偏重利用（exploitative）的搜尋策略。我們提出 MILO（Meta-evolutionary Island Orchestration，元演化島嶼編排），一個讓代理 Harness 與其發現策略共同演化（co-evolve）的框架。MILO 結合三項核心機制：（i）在基於島嶼的樹狀結構（island-based trees）上建立階層式譜系記憶（hierarchical lineage memory），並將被拒絕的突變（rejected mutations）作為負面證據（negative evidence）；（ii）每島嶼突變代理（per-island mutator agents），利用全域搜尋歷史與針對父代的回饋來改寫完整 Harness；以及（iii）編排器（orchestrator），透過譜系嫁接（lineage grafting）、物種形成（speciation）、突變器重新分配（mutator reassignment）與課程修訂（curriculum revision）來調適搜尋。在 Terminal-Bench 2.1、PaperBench 與 DeepSWE 上，無論使用前沿模型（frontier models，Opus 4.8）或開放權重模型（open-weight models，gpt-oss-120b），MILO 發現的 Harness 均優於八個最先進的 Harness 與六個搜尋方法。以 Opus 4.8 進行實驗時，MILO 相較於初始 Harness 的解決率（resolution）分別提升 +12.0%、+28.3% 與 +10.3%，而先前最佳搜尋方法的增益僅為 +4.5%、+18.3% 與 0%。在 Terminal-Bench 2.1 上，MILO 達到 86.1 ± 2.0%，超越官方排行榜首位（83.8 ± 2.3%），同時比初始 Harness 減少 26% 的 Token 消耗量（token consumption）。在 EinsteinArena 的開放問題（open problems）上，MILO 改進了 Erdős 最小重疊問題（Erdős minimum-overlap）的最佳已知上界（從 0.3808586 降至 0.3808568），以及第一與第三個自相關不等式（autocorrelation inequalities）的最佳已知上界（分別從 1.50274365 降至 1.50274360、從 1.45081 降至 1.44889）。

### 核心貢獻（3～5點）
- 提出 MILO 框架，讓代理 Harness 與其發現策略共同演化，突破現有方法僅狹隘最佳化個別元件或受困於固定搜尋策略的限制。
- 設計三項核心機制：階層式譜系記憶（利用被拒絕的突變作為負面證據）、每島嶼突變代理（改寫完整 Harness）、編排器（透過譜系嫁接、物種形成、突變器重新分配與課程修訂動態調適搜尋）。
- 在 Terminal-Bench 2.1、PaperBench 與 DeepSWE 上，使用前沿模型（Opus 4.8）與開放權重模型（gpt-oss-120b）均顯著超越八個最先進 Harness 與六個搜尋方法。
- 在 Terminal-Bench 2.1 上達到 86.1 ± 2.0% 的解決率，超越官方排行榜首位，同時減少 26% 的 Token 消耗量。
- 在 EinsteinArena 開放數學問題上改進 Erdős 最小重疊問題與自相關不等式的最佳已知上界，展現發現新知識的潛力。

### 適合對象
對自動化機器學習、代理系統設計、演化式搜尋與大型語言模型應用有興趣的研究人員與工程師；特別適合希望減少 Harness 設計人力成本、提升長程任務表現，以及探索 LLM 驅動之組合最佳化與開放科學問題的讀者。

## 深度分析

#### 方法論解析

MILO（Meta-evolutionary Island Orchestration）將「自動化 Harness 發現（Automated Harness Discovery, AHD）」重新定義為**策略層級發現（strategy-level discovery）**：目標不是針對單一任務尋找最佳解，而是發現一個能夠跨任務分佈泛化的 solver，也就是一個完整的 Harness（代理執行架構）。這個 Harness 包含提示（prompts）、工具（tools）、記憶（memory）、控制流程（control flow）、子代理（sub-agents）生成與驗證邏輯等所有組件。MILO 的核心設計可拆解為三大模組與四項設計選擇。

##### 1. 階層式譜系記憶（hierarchical lineage memory）

MILO 的記憶結構以**基於島嶼的樹狀結構（island-based trees）**組織，每一座島嶼（island）對應一條獨立的譜系（lineage），從一個不同的初始 Harness（seed）開始生長。這棵樹完整保留了從 seed 到每個候選 Harness 的突變路徑，**包括被拒絕的突變（rejected mutations）**。這些失敗樣本被當作**負面證據（negative evidence）**：突變代理（mutator agents）在後續改寫時，可以根據「哪些編輯曾導致性能下降或 Pareto 劣勢」來避免重複無效方向。相較於傳統演化式搜尋（evolutionary search, ES）只保留倖存者（單一最佳解、Pareto 前沿或 MAP-Elites 格子冠軍），MILO 讓每一次評估——無論成功或失敗——都成為搜尋訊號，顯著提升樣本效率。

##### 2. 每島嶼突變代理（per-island mutator agents）

每座島嶼配備專屬的突變代理，負責**改寫完整 Harness**（而非僅限於 prompts 或 skills）。這些突變代理是大型語言模型（large language model, LLM），它們同時接收兩類資訊：

- **全域搜尋歷史（global search history）**：跨島嶼的成功與失敗模式，讓突變代理知道當前搜尋空間中哪些結構性修改已被驗證。
- **父代特定回饋（parent-specific feedback）**：針對即將被突變的父代 Harness，給出具體的診斷與改寫建議。

這種設計讓突變不再是盲目的局部編輯，而是帶有「譜系意識」的結構性重構。由於每座島嶼使用不同 seed 與不同突變代理，單一突變器的**利用偏誤（exploitation bias）**被侷限在島內，避免整個搜尋過程過早收斂到少數設計變體。

##### 3. 編排器（orchestrator）：共同演化搜尋策略

MILO 的關鍵創新在於**同時演化 Harness 與發現它的搜尋策略**。編排器是一個高階代理，當偵測到某座島嶼陷入區域最佳（local optimum）時，會執行以下一或多種**元演化（meta-evolutionary）**操作：

- **譜系嫁接（lineage grafting）**：將一座島嶼譜系中的成功子樹接到另一座島嶼，促進跨譜系的想法流動。
- **物種形成（speciation）**：刻意讓不同島嶼朝不同結構方向分化，維持族群多樣性。
- **突變器重新分配（mutator reassignment）**：根據各島嶼的進展狀態，動態調整突變代理與島嶼的配對。
- **課程修訂（curriculum revision）**：調整評估任務的難度順序與取樣分佈，引導搜尋朝向更具挑戰�性的泛化目標。

這使 MILO 成為一種**自我調適搜尋（self-adaptive search）**：它不僅優化 Harness，也優化「如何優化 Harness」。

##### 4. 多目標適應度（multi-objective fitness）

候選 Harness 必須同時在三個維度上推進 Pareto 前沿：**解決率（resolution / accuracy）**、**Token 消耗量（token consumption）**與**延遲（latency）**。只有當新候選在至少一個維度上更好、且在其他維度不變差時，才會被納入記憶。這避免了傳統方法只追求準確率而導致 Harness 變得昂貴、緩慢的傾向。

總結來說，MILO 的方法論可視為一個**雙層演化迴路**：內層是各島嶼內 Harness 的演化，外層是編排器對島嶼結構、突變策略與課程的演化。這種「演化演化過程」的設計，是 MILO 與先前 AHD 方法最本質的區別。

#### 實驗數據解讀

MILO 在三個軟體工程基準——**Terminal-Bench 2.1**、**PaperBench**、**DeepSWE**——以及開放數學問題平台 **EinsteinArena** 上進行評估，並同時測試了前沿模型（frontier model）**Opus 4.8** 與開放權重模型（open-weight model）**gpt-oss-120b**。以下分項解讀。

##### Terminal-Bench 2.1：準確率與效率雙贏

- MILO 發現的 Harness 達到 **86.1 ± 2.0%** 的解決率（resolution），超過官方排行榜第一名 **83.8 ± 2.3%**。
- 相較於 MILO 自己的初始 Harness，解決率提升 **+12.0%**；而先前最佳搜尋方法僅能帶來 **+4.5%**。
- 同時，該 Harness 比初始 Harness **減少 26% 的 Token 消耗量**。

這組數據特別重要，因為它證明 MILO 不是單純用更多計算或更長推理鏈換取準確率，而是透過結構性改進同時達到**更高性能與更低成本**。這正是多目標 Pareto 篩選機制的直接體現。

##### PaperBench：最大相對增益

- MILO 在 PaperBench 上相對初始 Harness 提升 **+28.3%**，而先前最佳搜尋方法為 **+18.3%**。

PaperBench 通常涉及長程、多步驟的論文複現任務，對 Harness 的記憶管理、錯誤修復與子代理協作要求極高。+28.3% 的增益暗示 MILO 發現的 Harness 在**長程規劃與失敗恢復**方面有顯著結構優勢。

##### DeepSWE：開放權重模型的戲劇性提升

- 使用 Opus 4.8 時，MILO 提升 **+10.3%**，而先前最佳搜尋方法幾乎為 **0%**。
- 使用 gpt-oss-120b 時，MILO 達到 **15.6%**，是初始 Harness 的 **20 倍**，而先前搜尋方法均低於 **1%**。

這是論文中最具衝擊力的結果之一。它表明：對於能力較弱的開放權重模型，**Harness 設計可以大幅補償模型本身的不足**。如果沒有自動化搜尋，這類模型的潛力幾乎無法被人工 Harness 工程挖掘。

##### 跨基準泛化：Frontier-Bench

- 在 Terminal-Bench 2.1 上發現的 Harness，未經額外搜尋即在更困難的 **Frontier-Bench** 上達到 **Mini-SWE-Agent** 的 **2.7 倍**。

這驗證了 MILO 確實達成**策略層級發現**——找到的 Harness 不是針對單一基準過擬合，而是具備跨任務分佈的泛化能力。

##### EinsteinArena：開放數學問題的新紀錄

MILO 在三個長期未解的數學問題上改進了最佳已知上界：

- **Erdős 最小重疊問題（Erdős minimum-overlap）**：從 0.3808586 降至 **0.3808568**。
- **第一個自相關不等式（autocorrelation inequalities）**：從 1.50274365 降至 **1.50274360**。
- **第三個自相關不等式**：從 1.45081 降至 **1.44889**。

這些改進雖然在小數點後多位，但在數學上具有意義：它們代表 MILO 發現的 Harness 能夠引導模型產生**比以往任何方法（包括 AlphaEvolve）更緊的數學上界**。這也顯示 MILO 不僅限於軟體工程，還能應用於需要創造性組合搜尋的開放科學問題。

##### 綜合評價

實驗數據傳達了三個核心訊息：

1. **Harness 設計的邊際收益可能大於模型換代**：在相同模型下，MILO 發現的 Harness 能擊敗人工設計的 SOTA Harness。
2. **自動化搜尋必須具備多樣性與自我調適能力**：固定策略的搜尋方法在 DeepSWE 上幾乎失效，而 MILO 透過島嶼隔離與編排器調適持續進步。
3. **多目標優化是實用化的關鍵**：MILO 同時提升準確率並降低 Token 消耗，這對商業部署至關重要。

#### 與現有研究的比較

##### 1. 實例層級 vs. 策略層級發現

現有演化式搜尋（evolutionary search, ES）方法可分為兩類：

- **實例層級發現（instance-level discovery）**：如 **FunSearch**、**AlphaEvolve**、**OpenEvolve**、**EvoX**，針對單一問題尋找最佳解。它們通常依賴快速 Oracle，可評估數百萬候選。
- **策略層級發現（strategy-level discovery）**：如 **GEPA**、**A-Evolve**、**Meta-Harness**、**Self-Harness**，優化 solver 本身，必須跨任務泛化。

MILO 屬於策略層級，但它的設計吸收了實例層級方法的優點（如譜系追蹤、結構化記憶），並將其擴展到完整的 Harness 空間。

##### 2. 針對現有 ES 方法的四項缺陷

| 現有缺陷 | MILO 的對應設計 |
|---|---|
| **探索不足**：突變器重複同一家族的編輯，導致多樣性衰減 | **島嶼隔離（island-based trees）**：每座島嶼從不同 seed 與突變器獨立生長，限制利用偏誤擴散 |
| **樣本效率低**：只保留倖存者，失敗方向被重複嘗試 | **階層式譜系記憶（hierarchical lineage memory）**：保留被拒絕的突變作為負面證據（negative evidence） |
| **搜尋策略固定**：選擇、突變、課程等規則事先固定 | **編排器（orchestrator）**：透過譜系嫁接（lineage grafting）、物種形成（speciation）、突變器重新分配（mutator reassignment）、課程修訂（curriculum revision）動態調適 |
| **單一目標**：多數方法只優化準確率，導致成本飆升 | **Pareto 前沿篩選**：同時考慮解決率、Token 消耗量與延遲 |

##### 3. 與近期 AHD 方法的具體對比

- **GEPA** 與 **A-Evolve** 僅優化 prompts 或 skills，未觸及控制流程（control flow）與記憶（memory）等完整 Harness 組件，搜尋空間狹窄。
- **Self-Harness** 與 **Meta-Harness** 雖然改寫完整 Harness，但依賴固定的 LLM 突變器，容易陷入局部最佳。
- **EvoX** 是現有方法中自我調適程度最高的，但它只演化「如何選擇與突變父代」，突變器、課程與其他組件仍固定。
- **MILO** 首次將「搜尋策略的各個組件」都納入演化範圍，包括記憶結構、突變代理分配與課程設計。

##### 4. 限制與潛在弱點

儘管成果顯著，MILO 仍存在以下限制：

- **評估成本高昂**：每次 Harness 評估需數小時，整體搜尋仍需要大量計算資源。雖然樣本效率提升，但總成本對小型研究團隊仍是門檻。
- **Oracle 品質依賴**：AHD 的成效取決於評分器（oracle）能否準確衡量 Harness 在任務分佈上的表現。若 Oracle 有偏或樣本不足，可能導致過擬合。
- **可解釋性挑戰**：自動生成的完整 Harness 可能包含複雜且難以理解的控制流程，工程師難以驗證其安全性與穩定性。
- **延遲優化細節未充分展開**：論文強調多目標包含延遲（latency），但摘要與引言中對延遲的具體實驗數據著墨較少，需進一步確認其在不同硬體環境下的表現。
- **元演化層的穩定性**：編排器本身也是由 LLM 驅動，其決策品質與收斂性尚未有理論保證。

#### 可重現性評估

基於目前提供的摘要與引言，**MILO 的原始碼與完整實驗腳本尚未公開**。以下從幾個面向評估可重現性：

##### 1. 資料集與模型可取得性

- **Terminal-Bench 2.1**、**PaperBench**、**DeepSWE**、**EinsteinArena**、**Frontier-Bench** 均為公開基準，原則上可重複實驗。
- **Opus 4.8** 為商業 API 模型，**gpt-oss-120b** 為開放權重模型，兩者均可取得（前者需 API 存取權，後者可下載權重）。

##### 2. 方法細節的透明度

目前可見的內容已說明高階架構（島嶼、突變代理、編排器、Pareto 篩選），但缺少以下關鍵細節：

- 初始 seed Harness 的具體內容與數量。
- 突變代理與編排器的系統提示詞（system prompts）。
- 譜系嫁接、物種形成、課程修訂的觸發條件與演算法細節。
- 每個基準的評估預算（evaluation budget）、平行化程度與總計算量。
- Pareto 前沿中三個目標的權重或聚合方式。

這些細節對於完全重現結果至關重要。若作者僅在論文附錄中提供，而未釋出程式碼，其他研究者仍需大量試誤。

##### 3. 建議的開放內容

為提升可重現性，建議作者釋出：

- 完整的 MILO 框架程式碼（包含突變代理與編排器實作）。
- 搜尋日誌（search logs），包括所有產生過的 Harness、其譜系關係與評分。
- 最終發現的 Harness 配置，供社群直接驗證與比較。
- 每個基準的確切評估設定與隨機種子。

在這些資源釋出之前，MILO 的結果屬於「可驗證但難以完全重現」的狀態。

#### 未來研究方向

MILO 開啟了多條值得後續探索的研究路徑：

1. **降低評估成本的代理模型（surrogate model）**
   由於每次 Harness 評估昂貴，可訓練一個輕量級代理模型來預測 Harness 性能，減少完整評估次數，讓 MILO 能擴展到更大規模的搜尋空間。

2. **初始 seed 的元學習（meta-learning of seeds）**
   目前 MILO 從多個不同 seed 開始。未來可研究如何從過往搜尋任務中學習「好的初始 Harness 分佈」，進一步加速收斂。

3. **人機協作的 Harness 設計**
   將 MILO 與人類專家結合：由專家提供高階設計約束或安全規範，編排器在約束空間內搜尋，提升可解釋性與可控性。

4. **跨領域遷移**
   將 MILO 應用到軟體工程以外的長程任務，例如機器人控制、科學實驗設計、藥物發現或法律文件分析，驗證其通用性。

5. **理論分析**
   對島嶼隔離、譜系嫁接與元演化層的收斂性進行理論研究，給出搜尋效率與多樣性維持的保證。

6. **安全與對齊導向的 Harness 演化**
   在 Pareto 目標中加入安全性、可解釋性與對齊指標，避免自動化搜尋發現出利用環境漏洞或產生有害行為的 Harness。

7. **知識蒸餾為可重複使用的 Harness 模板**
   將 MILO 發現的複雜 Harness 蒸餾成簡潔、可解釋的模板或設計模式，讓工程師能夠在不相關任務上快速套用。

8. **多突變代理的協作與辯論機制**
   除了重新分配突變代理，可讓多個突變代理針對同一父代 Harness 提出不同改寫方案，並透過辯論或集成投票選出最佳方向。

9. **線上持續適應（online adaptation）**
   目前 MILO 似在固定任務分佈上進行離線搜尋。未來可讓 Harness 在部署後持續收集回饋，並由編排器進行線上微調，實現真正的**遞迴自我改進（recursive self-improvement）**。

10. **建立 AHD 的標準化評估協定**
    隨著越來越多 AHD 方法出現，社群需要統一的基準、評估指標與計算成本報告標準，才能公平比較不同方法的樣本效率與最終性能。

## 論文問答

**Q1：什麼是自動化 Harness 發現（AHD），為什麼它對現代代理系統很重要？**

A：自動化 Harness 發現（AHD）是指給定一個由大型語言模型與執行架構（harness）組成的代理後，自動為該模型尋找更強大 harness 的過程。Harness 負責控制模型執行、環境互動、提示設計、工具使用、記憶管理與控制流程，其設計對長程任務的表現影響幾乎與模型本身相當。然而，現今的 harness 工程仍高度依賴專家手工調整，且由於不同模型在工具使用、錯誤模式與提示敏感性上差異甚大，針對某一模型調好的 harness 換到另一模型往往失效，導致工程團隊必須反覆投入大量心力。AHD 的目標正是把這段手工、反覆的過程自動化，使代理能隨著模型演進持續重新最佳化自身的執行架構，從而以遠低於模型訓練的成本獲得顯著效能提升。

**Q2：現有的演化式搜尋方法應用在 harness 發現時，主要存在哪些缺陷？**

A：現有方法在應用於 harness 發現時，論文歸納出四大缺陷。第一，搜尋空間探索不足：許多方法只突變提示或技能，未能改寫完整 harness，或者雖改寫完整 harness，但固定的 LLM 突變器傾向過度利用，導致多樣性衰減。第二，樣本效率低落：評分一個 harness 可能需要數小時，但多數方法只保留存活者，忽略失敗候選的負面證據，容易重複嘗試已證明無效的方向。第三，缺乏自我調適能力：搜尋策略（如親代選擇、突變方式、課程安排）通常預先固定，難以逃離區域最佳。第四，忽視多目標適應：多數方法只最佳化正確率，導致 harness 傾向使用更多 token 與更長延遲，卻未同時考慮成本與速度。

**Q3：為什麼 harness 設計被視為「策略層級發現」，而非「實例層級發現」？**

A：實例層級發現專注於為單一任務尋找最佳解，例如針對某道數學題找出最優函數；而策略層級發現則是最佳化「求解器」本身，使其能跨越多個任務泛化。Harness 並不是為了某一筆資料而存在，而是要在一整個任務分佈上穩定運作，例如同時處理多個終端機指令、論文複現或軟體工程問題。因此，harness 的設計屬於策略層級發現，其挑戰在於如何找到具備通用結構、能適應不同輸入與錯誤模式的執行架構，而非僅對單一實例進行微調。

**Q4：MILO 的核心洞察與整體架構是什麼？**

A：MILO 的全名是 Meta-evolutionary Island Orchestration，其核心洞察是同時演化「harness」與「發現 harness 的搜尋策略」。整體架構包含三大元件：首先是階層式譜系記憶，以基於島嶼的樹狀結構記錄每條血統路徑，並把被拒絕的突變保留為負面證據；其次是每島嶼突變代理，各自負責在特定島嶼內改寫完整 harness，並參考全球搜尋歷史與親代專屬回饋；最後是編排器，它會透過譜系嫁接、物種形成、突變器重新分配與課程修訂等手段，動態調整搜尋過程。這三個元件協同運作，使 MILO 能在高維且組合爆炸的 harness 空間中進行多樣、樣本高效且自我調適的搜尋。

**Q5：MILO 如何維持搜尋多樣性，並避免單一突變器的利用偏誤？**

A：MILO 將搜尋空間劃分為多個島嶼（lineage），每個島嶼從不同的初始 harness 種子出發，並配置不同的突變代理。島嶼之間會交換成功的想法，但彼此不會為了生存而競爭，因此某個突變器的利用偏誤只會侷限在它所屬的島嶼內，不會吞噬整體多樣性。這種隔離設計甚至能讓最弱的初始種子最終產出最佳 harness，因為不同島嶼可以朝不同結構方向獨立探索。透過這種「島嶼隔離＋想法交流」的機制，MILO 有效對抗了傳統演化搜尋中常見的多樣性衰減問題。

**Q6：MILO 如何利用被拒絕的突變與階層式譜系記憶來提升搜尋效率？**

A：MILO 的階層式譜系記憶會完整保存從初始種子到每個候選 harness 的路徑，包括那些被拒絕的突變。成功的候選顯示哪些編輯確實帶來效益，而失敗的候選則作為負面證據，讓突變代理知道應該避免哪些模式。當某條路徑連續失敗時，記憶會促使突變器進行更大膽的結構性改變，而不是在局部做無謂微調。這種同時利用正負面證據的設計，使每次昂貴的評估都能為後續搜尋提供資訊，顯著提升樣本效率。

**Q7：MILO 在哪些基準與模型上進行了評估？**

A：論文在四個不同性質的基準上評估 MILO，包括終端機指令任務 Terminal-Bench 2.1、論文複現任務 PaperBench、軟體工程任務 DeepSWE，以及開放數學問題競技場 EinsteinArena。模型方面同時測試了前沿閉源模型 Opus 4.8 與開放權重模型 gpt-oss-120b。這樣的設計能檢驗 MILO 發現的 harness 是否對不同能力與授權條件的模型都具備泛化能力。此外，實驗還與八個最先進的 harness 以及六個演化搜尋方法進行比較，以確認其相對優勢。

**Q8：MILO 在實驗中取得了哪些關鍵量化成果？**

A：在 Opus 4.8 上，MILO 相較初始 harness 分別在 Terminal-Bench 2.1、PaperBench 與 DeepSWE 提升了解決率 +12.0%、+28.3% 與 +10.3%，明顯優於先前最佳搜尋方法的 +4.5%、+18.3% 與 0%。在 Terminal-Bench 2.1 上，MILO 達到 86.1 ± 2.0% 的解決率，超過官方排行榜第一名 83.8 ± 2.3%，同時比初始 harness 少用 26% 的 token。使用 gpt-oss-120b 時，MILO 在 DeepSWE 上達到 15.6%，是初始 harness 的 20 倍，而先前搜尋方法幾乎無法進步。在 EinsteinArena 上，MILO 更刷新了 Erdős 最小重疊問題與兩個自相關不等式的最佳已知上界。

**Q9：MILO 的 harness 是否具備泛化能力？有哪些證據？**

A：論文顯示 MILO 發現的 harness 具備良好的跨任務泛化能力。例如，針對 Terminal-Bench 2.1 搜尋得到的 harness，在未經額外搜尋的情況下，直接應用於更困難的 Frontier-Bench，其表現達到 mini-SWE-agent 的 2.7 倍。這表示 MILO 並非僅對單一基準過度擬合，而是捕捉到了可遷移的結構性設計原則。此外，無論是在 Opus 4.8 或 gpt-oss-120b 上，MILO 都能穩定超越多個現有 harness 與搜尋方法，進一步證明其發現的策略具有跨模型適用性。

**Q10：MILO 在實際的代理產品開發中可以如何應用？**

A：在實務上，MILO 可以作為代理產品持續迭代 harness 的自動化引擎，每當底層模型更新或任務分佈改變時，自動重新發現適合的執行架構。這能大幅縮短目前需要數個月手工調整的開發週期，並讓工程團隊專注於更高層次的產品設計與安全把關。由於 MILO 同時最佳化正確率、token 消耗與延遲，產品團隊可以在 Pareto 前沿上根據商業需求選擇最合適的 harness，兼顧使用者體驗與營運成本。

**Q11：部署 MILO 發現的 harness 時，有哪些產品層面的考量？**

A：首先，自動產生的 harness 可能結構複雜，需要額外的可解釋性工具與人工審查，才能確保其行為符合產品安全與倫理規範。其次，雖然 MILO 同時考慮 token 與延遲，但實際部署時仍需在準確率、成本與回應速度之間做最終取捨，不同應用場景的權重可能不同。最後，自動化發現的 harness 需要持續監控與版本控制，因為隨著模型或環境變化，原本最佳的 harness 可能退化，必須建立再訓練與回滾機制。

**Q12：MILO 對整個代理系統與人工智慧領域可能帶來什麼更廣泛的影響？**

A：MILO 推動了「代理能改進自身執行架構」的願景，是遞迴自我改進研究的重要一步。它降低了高品質 harness 的設計門檻，使開放權重模型也能透過自動化搜尋縮小與前沿商業模型之間的差距，例如在 DeepSWE 上 gpt-oss-120b 獲得 20 倍提升。此外，MILO 在 EinsteinArena 上刷新數學開放問題的紀錄，顯示這類元演化方法不僅限於軟體工程，也能成為發現新數學結構的有力工具。

**Q13：MILO 有哪些潛在的限制或尚未完全解決的挑戰？**

A：MILO 仍然高度依賴昂貴且耗時的 oracle 評估，每個 harness 的評分可能需要數小時，這限制了在更大規模任務上的搜尋次數。此外，雖然編排器能協助逃離區域最佳，但搜尋品質仍受初始種子與突變代理能力的影響，若種子過於薄弱或突變器無法產生有效變異，某些島嶼可能過早停滯。最後，目前的框架主要針對可量化的目標（正確率、token、延遲）進行最佳化，對於更難量化的目標如使用者滿意度、可解釋性或公平性，仍需額外設計評估機制。

**Q14：MILO 在哪些情況下可能會失敗或產生不理想結果？**

A：如果某個島嶼的初始種子與突變器組合長期無法產生 Pareto 改進，且編排器未能及時介入，該島嶼可能會浪費大量評估預算。另外，自動產生的 harness 可能學會利用評估基準的漏洞或過度擬合訓練任務，導致在未見任務上表現不佳。在多目標設定中，也可能出現 Pareto 前沿停滯，所有新候選都無法同時改善正確率、token 與延遲，使得搜尋難以繼續推進。這些情況都凸顯了持續監控與適時人工介入的重要性。

**Q15：未來研究可以從哪些方向延伸 MILO？**

A：未來可以將人類回饋整合進演化迴路，讓編排器不僅依賴自動化指標，也能學習人類對 harness 可讀性與可靠性的偏好。另一個方向是讓 MILO 在部署後持續線上適應，根據真實使用者互動動態修訂 harness，而非只在離線基準上搜尋。此外，可以進一步擴展編排器自身的演化能力，例如讓多個編排器代理彼此競爭或協作，甚至將安全約束形式化為不可違反的演化邊界。最後，發展更便宜、更快速的近似 oracle，將是讓 MILO 能應用於更大規模、更複雜任務的關鍵。

## 實務應用指南

### 適用場景

1. **企業級軟體工程代理的 Harness 自動調校**  
   若組織已使用 Claude Code、Codex、mini-SWE-agent 或內部開發的代理來處理 GitHub issue、程式碼審查或端對端 ML 工程，可將 MILO 用於自動發現更適合當前模型與程式碼庫的 Harness。例如，針對 Terminal-Bench 2.1 或 DeepSWE 這類長程任務，MILO 能同時提升解決率並降低 Token 消耗。

2. **客戶服務與流程自動化代理的架構優化**  
   在需要多輪工具呼叫、子代理協作與記憶管理的客服或業務流程自動化場景中，Harness 的提示、控制流程與驗證邏輯會直接影響成功率與延遲。MILO 可透過島嶼隔離與多目標篩選，產生在「正確率—Token—延遲」上皆更優的 Harness。

3. **科學研究與開放數學問題的求解策略發現**  
   如 EinsteinArena 中的 Erdős 最小重疊問題或自相關不等式，MILO 不僅能優化單一解答，更能發現可跨問題泛化的求解策略（Strategy-level discovery）。適合需要持續改進數學上界或演算法設計的研究團隊。

4. **內部開發者工具與 DevOps 代理的持續進化**  
   對於執行部署、測試、監控或故障排除的代理，MILO 可隨著底層模型更新自動重新調校 Harness，減少人工重複調整提示與控制流程的成本。

5. **多模型代理產品的 Harness 版本管理**  
   當產品同時支援前沿模型（如 Opus 4.8）與開放權重模型（如 gpt-oss-120b）時，MILO 可針對每個模型獨立執行自動化 Harness 發現，並透過譜系記憶追蹤各模型專屬的最佳實踐。

### 實作前置條件

**資料與任務**
- 可評分的任務分佈：至少 50–200 筆具代表性的長程任務（如軟體工程 issue、論文複現步驟、終端機指令序列），並區分訓練課程與保留測試集。
- 現有 Seed Harness：2–5 個風格迥異的初始 Harness，作為不同島嶼的起點；可包含基礎 ReAct、Terminus 2、mini-SWE-agent 或內部版本。
- Oracle／評分器：能自動輸出「解決率、Token 消耗、延遲」等指標，並具備可重現的執行環境（如容器化沙箱）。

**運算資源**
- LLM 推理預算：突變代理（Mutator Agents）與編排器（Orchestrator）需呼叫大型語言模型，建議準備足夠的 API 額度或本地 GPU 叢集。
- 平行評估叢集：每個 Harness 候選解可能需要數分鐘到數小時評估，建議具備 Kubernetes / Ray / Modal 等平行執行環境。
- 儲存空間：用於保存階層式譜系記憶（Hierarchical Lineage Memory），包括被接受與被拒絕的突變紀錄。

**技能與團隊**
- 軟體工程能力：能閱讀與改寫完整 Harness 程式碼（提示、工具、控制流程、記憶）。
- LLM 與提示工程經驗：理解模型對提示的敏感性（Prompt Sensitivity）與常見錯誤模式。
- 分散式系統與 MLOps：能搭建可擴展的評估管線、版本控制與監控。
- 領域知識：針對數學或軟體工程任務，需有人能判斷 Harness 輸出的合理性，避免 Reward Hacking。

### 實作步驟建議

1. **定義目標與多目標適應函數**  
   明確要優化的指標，例如解決率（Resolution）、Token 消耗量與延遲。採用 Pareto 前沿篩選，只保留在三個維度上至少有一項進步的候選 Harness。

2. **準備 Seed Harness 與課程**  
   挑選 3–5 個差異夠大的初始 Harness，分別配置為不同島嶼（Island）的根節點。設計由易到難的課程（Curriculum），讓早期演化先學會基礎結構，再挑戰複雜任務。

3. **建立階層式譜系記憶**  
   為每個島嶼維護樹狀譜系，記錄每條 Seed→Parent→Candidate 路徑，並將被拒絕的突變（Rejected Mutations）作為負面證據（Negative Evidence）。這能避免突變代理重複無效編輯，並鼓勵更大膽的結構性改變。

4. **配置每島嶼突變代理**  
   指派不同風格的 Mutator Agent 給各島嶼，例如一個專攻提示重寫、一個專攻控制流程、一個專攻子代理設計。每個 Mutator 在改寫完整 Harness 時，需參考全局搜尋歷史與父代專屬回饋。

5. **執行演化迴圈**  
   每輪依 Pareto 前沿選擇父代，由 Mutator 產生新 Harness，經 Oracle 評分後決定是否納入譜系。失敗候選解仍寫入記憶，作為後續剪枝依據。

6. **啟動編排器的自我調適**  
   當某島嶼長期停滯（Local Optimum），由 Orchestrator 執行譜系嫁接（Lineage Grafting）、物種形成（Speciation）、Mutator 重新分配（Mutator Reassignment）或課程修訂（Curriculum Revision），主動改變搜尋策略而非僅改變 Harness。

7. **保留集驗證與泛化測試**  
   從 Pareto 前沿挑選數個候選解，在完全未見過的保留任務上驗證。例如可將 Terminal-Bench 2.1 發現的 Harness 拿到 Frontier-Bench 測試，確認其跨分佈泛化能力。

8. **部署與持續監控**  
   將選定的 Harness 納入 CI/CD，並在生產環境監控解決率、Token 消耗與延遲。當底層模型更新時，重新執行 MILO 進行自動化再調校。

### 潛在風險與注意事項

| 風險 | 說明 | 建議緩解方式 |
|---|---|---|
| **多樣性衰減（Diversity Decay）** | Mutator Agent 傾向重複類似編輯，導致所有島嶼收斂到少數設計變體。 | 透過島嶼隔離與物種形成維持多樣性；定期更換 Mutator 的系統提示或模型溫度。 |
| **局部最優（Local Optimum）** | 搜尋卡在提示微調，無法產生結構性突破。 | 讓 Orchestrator 主動執行課程修訂與譜系嫁接，並提高結構性突變的機率。 |
| **評估成本過高** | 每個 Harness 評估可能耗時數小時，導致整體搜尋預算爆炸。 | 使用課程難度分層與早期停止；先在小任務子集篩選，再對完整基準驗證。 |
| **過度擬合基準（Overfitting）** | Harness 針對訓練課程作弊，但在真實任務表現差。 | 保留獨立測試集；引入多樣化任務與對抗性範例；監控生產指標。 |
| **Reward Hacking** | Harness 利用評分器漏洞，例如透過無窮迴圈或過度呼叫工具來「刷分」。 | 設計穩健的 Oracle，加入延遲與 Token 上限；人工抽查異常候選解。 |
| **模型相依性** | 為 Opus 4.8 調校的 Harness 不一定適用 gpt-oss-120b。 | 針對每個模型獨立執行 MILO；在譜系記憶中標註模型專屬編輯。 |
| **編排器本身僵化** | 若 Orchestrator 的診斷邏輯固定，可能無法應對新類型的停滯。 | 將 Orchestrator 的決策也納入可學習空間，定期檢視其干預成效。 |

### 與其他技術的整合建議

- **現有代理框架**：可將 MILO 作為外層優化器，包裹 LangChain、AutoGen、CrewAI 或內部框架。MILO 負責改寫 Harness 的提示、工具與控制流程，底層框架負責執行。
- **CI/CD 與版本控制**：將每個被接受的 Harness 候選解視為一個版本，透過 Git 追蹤譜系變化，並在合併前於 CI 中執行保留集測試。
- **可觀測性工具**：整合 LangSmith、Weights & Biases 或自研監控，記錄每個候選解的 Token 消耗、延遲與錯誤軌跡，作為 Mutator 與 Orchestrator 的回饋。
- **MLOps / 模型註冊表**：當底層 LLM 更新時，自動觸發 MILO 重新搜尋，並將新 Harness 與模型版本綁定發布。
- **人機協作審查**：在 MILO 產生的 Pareto 前沿中，由領域專家挑選最終部署版本，避免全自動決策帶來的不可預期行為。
- **檢索增強生成（RAG）**：將階層式譜系記憶與被拒絕突變庫作為 RAG 知識庫，讓 Mutator Agent 在產生新 Harness 前檢索過往失敗經驗。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從「Harness 是什麼」與「為何它跟模型一樣重要」開始理解，接著把 MILO 想像成「用多個 AI 助理互相競爭與合作，自動改良另一個 AI 助理的工作流程」。不必一次搞懂所有演算法細節，重點是掌握「島嶼隔離保留多樣性」與「從失敗中學習」這兩個直覺。

**AI 工程師**  
請聚焦第 4 節的系統設計：階層式譜系記憶如何實作、Mutator Agent 的提示設計、Orchestrator 的診斷與干預條件，以及 Pareto 篩選的實務權衡。建議直接參考 Terminal-Bench 2.1 與 DeepSWE 的實驗設定，評估能否移植到自身代理產品。

**研究人員**  
本論文的核心貢獻在於將「搜尋策略本身也納入演化」，可與 FunSearch、AlphaEvolve、EvoX、GEPA、Self-Harness 等方法對照閱讀。建議深入分析島嶼結構對多樣性的理論保證、被拒絕突變作為負面證據的樣本效率，以及 Orchestrator 決策空間的可學習性。

**產品經理**  
請把重點放在商業價值與落地成本：MILO 能顯著降低 Harness 工程的人工投入，並隨模型更新自動再調校；但需準備足夠的評估預算與任務資料。建議從一個明確的指標（例如「降低 20% Token 消耗同時維持解決率」）開始試點，再逐步擴大到多模型與多場景。
