## 摘要翻譯

大型語言模型（LLMs）被廣泛用於以自主工作流程處理複雜任務。近年來，可重複使用的自然語言技能已成為將程序性知識注入 LLM 應用程式的熱門範式。由於熱門技能經常被反覆調用，將其完整文本納入每個上下文中會顯著增加預填充成本和延遲。雖然文本壓縮技術有潛力解決此問題，但大多數現有方法旨在壓縮文件中的事實性知識，而非程序性知識，因此不足以用於技能壓縮。於本文中，我們主張一個有效的技能壓縮方法應具備以下特性：1) 保留工作流程和工具協議之間的邏輯依賴，2) 為頻繁更新的社群技能提供輕量級的離線壓縮，3) 能適應不同技能的複雜度差異。為了解決這個問題，我們提出了 SKIM（技能壓縮），一個用於程序性技能的自適應多解析度軟標記壓縮框架。根據每個技能的複雜度，SKIM 會產生不同數量的軟標記，不僅能提升 LLM 推理的效率，還能保留技能使用的有效性。實驗表明，SKIM 能將技能壓縮至原始標記長度的 30% 至 60%，同時在任務效能上優於現有的壓縮方法。我們已在 https://github.com/bebr2/SKIM 釋出程式碼。

### 核心貢獻（3～5點）
- 提出 SKIM 框架，專為程序性技能設計的自適應多解析度軟標記壓縮方法，可依據技能複雜度動態產生不同數量的軟標記。
- 揭示現有壓縮方法的不足：多數方法針對事實性知識設計，無法有效保留工作流程與工具協議之間的邏輯依賴。
- 支援輕量級離線壓縮，使頻繁更新的社群技能能高效整合至 LLM 應用程式。
- 在效率方面，SKIM 可將技能壓縮至原始標記長度的 30% 至 60%，顯著降低預填充成本與延遲。
- 在效能方面，SKIM 在任務效能上優於現有壓縮方法，同時維持技能使用的有效性。

### 適合對象
從事 LLM 推理優化、提示工程、LLM 代理（LLM Agents）設計與技能生態系統（Skill Ecosystem）研究的學者與工程師；以及關注長上下文理解（Long-Context Understanding）、文件中心任務（Document-Centric Tasks）與下游任務（Downstream Tasks）效能提升的實務工作者。

## 深度分析

#### 方法論解析

SKIM（SKIll coMpression，技能壓縮）的核心設計理念在於將「程序性知識壓縮」（procedural knowledge compression）與傳統的「事實性知識壓縮」（factual knowledge compression）明確區分開來。論文中圖 1 的 ToolQA 範例清楚展示了這個區別：當使用 ICAE（In-Context Auto-Encoder，上下文自動編碼器）壓縮一份咖啡價格查詢技能時，雖然事實性問題（如資料庫欄位）仍可正確回答，但程序性問題（如查詢特定日期的開盤價）卻因為工作流程（workflow）的邏輯依賴（logical dependencies）被破壞而產生錯誤結果。這正是 SKIM 試圖解決的根本問題。

**雙模型壓縮架構（Dual-Model Compression Architecture）**

SKIM 採用類似 DRIFT 的雙模型架構，由兩個關鍵元件組成：

1. **壓縮器（Compressor）**：負責將原始技能文本編碼為中間表示形式。這是一個編碼器-解碼器（encoder-decoder）結構，能夠將可變長度的技能文本轉換為固定數量的軟標記（soft tokens）。

2. **投影器（Projector）**：將壓縮器輸出的軟標記映射到目標 LLM 的嵌入空間（embedding space），使其能夠被目標模型直接理解。

這種分離設計的優勢在於：壓縮器可以獨立於目標 LLM 進行預訓練，而投影器則負責橋接不同模型之間的表示差異。

**三階段漸進式訓練範式（Three-Stage Progressive Training Paradigm）**

SKIM 的訓練過程分為三個精心設計的階段，這是論文方法論的核心創新：

1. **技能重建階段（Skill Reconstruction Stage）**：此階段專注於讓壓縮器學會保留技能文本中的所有資訊。透過重建損失（reconstruction loss），壓縮器被迫將技能內容編碼到軟標記中，確保沒有資訊遺漏。

2. **程序性預熱階段（Procedural Warm-up Stage）**：這是 SKIM 區別於其他壓縮方法的關鍵階段。在此階段，模型學習保留程序性依賴關係，而不僅僅是語義內容。透過讓模型學習預測技能執行過程中的中間步驟（如工具調用順序、參數傳遞），壓縮器被迫保留邏輯依賴。

3. **技能任務對齊階段（Skill Task Alignment Stage）**：最終階段透過 LoRA（Low-Rank Adaptation，低秩適應）模組對目標 LLM 進行適應。這種設計確保了參數效率（parameter efficiency），因為只需要訓練一個輕量的 LoRA 模組，而不需要微調整個目標模型。

**多解析度設計（Multi-Resolution Design）**

SKIM 最具特色的設計之一是其多解析度能力。傳統壓縮方法通常使用固定的壓縮率，但 SKIM 允許同一個技能以多個不同的標記預算（token budgets）同時表示：

- 對於簡單技能（如單一工具調用），可以使用較高的壓縮率（更少的軟標記）
- 對於複雜技能（如多步驟工作流程），則需要較低的壓縮率（更多的軟標記）來保留所有邏輯依賴

**離線自我判斷機制（Offline Self-Judgment Mechanism）**

在部署前，SKIM 會自動選擇最低預算的解析度，同時維持執行準確性。這個機制的工作原理是：

1. 對每個技能生成多個解析度的壓縮版本
2. 在驗證集上測試每個版本的執行準確性
3. 選擇滿足準確性閾值的最低預算版本

這個設計完美契合技能的部署範式：開發者可以將技能作為輕量級、預計算的軟標記包（soft token bundles）分發，類似於軟體發行中的預建構產物（prebuilt artifact）。

#### 實驗數據解讀

**壓縮效率（Compression Efficiency）**

根據論文摘要，SKIM 能將技能壓縮至原始標記長度（token length）的 30% 到 60%。這個數據需要從兩個角度解讀：

- **下限 30%**：對於高度複雜的程序性技能，即使經過壓縮，仍需要保留相當數量的軟標記以維持邏輯依賴
- **上限 60%**：對於較簡單的技能，可以實現更激進的壓縮

這個範圍顯示了多解析度設計的實際價值——不是所有技能都需要相同的壓縮率。

**任務效能保留（Task Performance Preservation）**

論文中圖 1 的範例揭示了一個重要的實驗觀察：當使用 ICAE 壓縮技能時，雖然事實性問題的表現尚可，但程序性問題的表現完全失敗。這說明了：

1. 現有壓縮方法在程序性任務上的局限性
2. SKIM 設計的必要性——必須專門針對程序性知識設計壓縮方法

**與基線方法的比較（Comparison with Baselines）**

從表 1 的比較來看，SKIM 在三個維度上都優於現有方法：

| 維度 | SKIM 的優勢 |
|------|-------------|
| 知識類型 | 唯一支援程序性知識的輕量級方法 |
| 離線壓縮 | 支援，無需線上訓練 |
| 輕量級 | 僅需單次前向傳遞（forward pass），無需梯度反向傳播（gradient backpropagation） |

唯一在「程序性知識」維度上可比的方法是 TokMem，但它需要線上訓練（不支援離線壓縮），這使得它在實際部署中不切實可行。

**實驗設計的意涵（Implications of Experimental Design）**

論文中使用「技能型資料集」（skill-based datasets）進行評估，這比傳統的長上下文理解基準更能反映真實的代理（agent）應用場景。這種評估方式的選擇本身就說明了 SKIM 的定位——它不是要取代通用壓縮方法，而是要解決特定場景下的程序性知識壓縮問題。

#### 與現有研究的比較

**定位分析（Positioning Analysis）**

從表 1 的系統性比較來看，現有的提示壓縮方法可以分為幾個類別：

1. **硬標記壓縮方法（Hard Token Compression Methods）**：如 LLMLingua-2 和 LongLLMLingua，透過選擇離散文本標記（discrete text tokens）來實現壓縮。這些方法的優勢在於可解釋性，但對於程序性知識，它們可能會破壞邏輯依賴，因為刪除某些標記可能會切斷工作流程中的關鍵步驟。

2. **軟標記壓縮方法（Soft Token Compression Methods）**：如 ICAE、500xCompressor 和 DRIFT，使用連續表示（continuous representations）來壓縮上下文。這些方法在保留語義內容方面表現較好，但如圖 1 所示，它們在保留程序性依賴方面存在根本性缺陷。

3. **程序性知識壓縮方法**：目前只有 TokMem 和 SKIM 屬於此類別。但 TokMem 需要線上訓練，這在實際部署中是不切實際的，因為技能更新頻繁且需要在不同推理後端（inference backends）之間分發。

**相對於現有方法的改進（Improvements over Prior Work）**

SKIM 的主要改進可以歸納為：

1. **程序性依賴保留**：透過三階段訓練中的「程序性預熱階段」，SKIM 明確學習保留工作流程中的邏輯依賴，而不僅僅是語義內容。

2. **部署友好性**：離線壓縮能力使得技能可以預計算並作為輕量級產物分發，這與自然語言技能的分享和修改範式完美契合。

3. **自適應性**：多解析度設計允許系統根據技能複雜度自動選擇合適的壓縮率，避免了固定壓縮率帶來的性能損失。

4. **參數效率**：透過 LoRA 適應，SKIM 只需要訓練少量參數即可對齊目標 LLM，降低了訓練成本。

**現有方法的局限性（Limitations of Existing Methods）**

論文中明確指出了現有方法的三個主要局限：

1. **無法保留程序性依賴**：現有方法主要針對事實性知識設計，當面對需要嚴格邏輯依賴的工作流程時，它們會破壞執行鏈。

2. **不適合技能的部署範式**：許多現有方法需要線上訓練或無法支援離線壓縮，這與技能頻繁更新和跨後端分發的特性不符。

3. **缺乏自適應性**：固定壓縮率無法適應不同複雜度的技能，可能導致簡單技能過度壓縮或複雜技能壓縮不足。

**SKIM 的局限性（Limitations of SKIM）**

儘管 SKIM 在多個方面優於現有方法，但仍存在一些潛在的局限性：

1. **模型特定性**：每個目標 LLM 都需要訓練對應的投影器和 LoRA 模組，這增加了部署成本。
2. **解析度選擇的依賴性**：離線自我判斷機制依賴於驗證集的品質，如果驗證集不能代表真實使用場景，可能會選擇次優的解析度。
3. **軟標記的可解釋性**：與硬標記壓縮相比，軟標記對人類不可讀，這可能會影響除錯和審計。

#### 未來研究方向

**1. 跨模型泛化能力（Cross-Model Generalization）**

目前 SKIM 需要為每個目標 LLM 訓練專門的投影器和 LoRA 模組。未來的研究可以探索：

- 訓練一個通用的投影器，使其能夠適應多個目標 LLM
- 透過模型蒸餾（model distillation）技術，將特定模型的適應能力泛化到其他模型
- 研究模型家族內的參數共享機制，減少訓練成本

**2. 動態解析度調整（Dynamic Resolution Adjustment）**

目前的離線自我判斷機制在部署前確定解析度。未來可以探索：

- 線上動態調整解析度，根據查詢的複雜度即時決定使用哪個解析度
- 階層式軟標記設計，允許在推理過程中按需「展開」更多細節
- 結合強化學習（reinforcement learning）來優化解析度選擇策略

**3. 多模態技能壓縮（Multi-Modal Skill Compression）**

隨著多模態 LLM 的發展，技能可能不僅包含文本，還包含圖像、音訊等：

- 擴展 SKIM 框架以支援多模態技能的壓縮
- 研究跨模態的程序性依賴保留機制
- 探索視覺化工作流程的壓縮表示

**4. 安全性與可解釋性（Safety and Interpretability）**

軟標記的不可讀性帶來了安全性和可解釋性方面的挑戰：

- 研究如何檢測壓縮技能中的惡意內容
- 開發技術將軟標記轉換回可讀形式以供審計
- 探索壓縮過程中的隱私保護機制

**5. 與代理框架的深度整合（Deep Integration with Agent Frameworks）**

SKIM 目前是一個獨立的壓縮框架，未來可以探索：

- 與主流代理框架（如 LangChain、AutoGen）的原生整合
- 開發標準化的技能分發協議，包含壓縮表示
- 建立技能市場或生態系統，支援壓縮技能的發現和共享

**6. 理論分析（Theoretical Analysis）**

目前 SKIM 的設計主要基於經驗觀察，未來可以加強理論基礎：

- 分析程序性知識壓縮的資訊理論下界
- 研究不同解析度之間的理論關係
- 形式化定義程序性依賴的保留條件

**7. 持續學習與適應（Continual Learning and Adaptation）**

技能生態系統是動態發展的，新技能不斷出現：

- 研究如何在不重新訓練整個模型的情況下整合新技能
- 探索技能之間的遷移學習機制
- 開發增量式壓縮算法，支援技能庫的持續擴展

**8. 評估基準的標準化（Standardization of Evaluation Benchmarks）**

目前缺乏專門針對程序性知識壓縮的標準評估基準：

- 建立涵蓋多種類型技能的綜合評估資料集
- 定義標準化的評估指標，包括執行準確性、效率、可維護性等
- 組織共享任務（shared tasks）以促進該領域的發展

這些研究方向不僅能夠推動 SKIM 本身的改進，也能夠促進整個程序性知識壓縮領域的發展，最終實現更高效、更可靠的 LLM 代理系統。

## 論文問答

**Q1：為什麼技能壓縮對於 LLM 代理的大規模部署如此重要？**
A：隨著技能生態系統（如 OpenClaw）的興起，熱門技能會被下載並在各種系統中反覆調用，每次調用都需要將完整的技能文本放入模型的上下文視窗中，造成大量冗餘的標記消耗。這種重複的標記消耗會累積成顯著的預填充成本與延遲，即使只減少一小部分的提示標記，也能轉化為可觀的計算節省與回應速度提升。因此，技能壓縮成為降低 LLM 代理運營成本、提升使用者體驗的關鍵技術。

**Q2：現有的文本壓縮方法為什麼無法有效處理程序性知識？**
A：現有方法（如 LLMLingua-2、LongLLMLingua、ICAE、500xCompressor、DRIFT）主要為通用提示、長上下文理解或文件中心任務而設計，其目標是保留顯著語義內容或查詢相關證據。然而，技能封裝的是程序性知識，其中包含工作流程、工具協議之間的邏輯依賴，這些依賴關係無法像事實性關鍵詞那樣被簡單保留。一旦切斷條件、工具參數之間的邏輯連結，即使保留了表面語義，執行仍會失敗，如圖 1 中 ICAE 在程序性問題上的失敗案例所示。

**Q3：程序性知識壓縮與事實性知識壓縮的根本差異是什麼？**
A：事實性知識壓縮只需保留可恢復的關鍵事實或證據即可維持效用，因為查詢通常只需要從中提取資訊；而程序性知識壓縮必須嚴格保留條件、工具參數之間的邏輯依賴，因為這些依賴構成可執行的工作流程。此外，技能具有社群共享、頻繁更新、跨推理後端部署的特性，這要求壓縮過程必須是輕量級的離線壓縮（僅需單次前向傳遞），而非依賴昂貴的線上梯度反向傳播，這與靜態文本的處理範式有本質差異。

**Q4：SKIM 的核心架構是什麼？它如何運作？**
A：SKIM 採用類似 DRIFT 的雙模型壓縮架構，包含一個壓縮器（compressor）用於編碼技能文本，以及一個投影器（projector）用於將產生的軟標記映射到目標 LLM 的表示空間。根據每個技能的複雜度，SKIM 會產生不同數量的軟標記，這些軟標記在保留技能使用效能的同時提升 LLM 推理效率。部署時，預計算的軟標記套件可作為類似軟體發行中預建構件的形式分發，推理時只需載入預選的軟標記並切換到共享的 LoRA 適配器，無需額外延遲。

**Q5：SKIM 的三階段漸進式訓練是如何設計的？為什麼需要這種設計？**
A：SKIM 的訓練分為三個階段：技能重建（skill reconstruction）、程序性預熱（procedural warm-up）與技能任務對齊（skill task alignment）。技能重建階段讓模型學習保留語義內容；程序性預熱階段引入程序性範例，使模型開始理解工作流程的邏輯結構；技能任務對齊階段則透過單一 LoRA 模組對目標 LLM 進行適配，確保壓縮後的技能能正確執行下游任務。這種漸進式設計是為了確保模型在保留可執行依賴關係的同時維持參數效率。

**Q6：為什麼選擇多解析度設計？自適應機制如何運作？**
A：技能在複雜度與資訊密度上差異極大，固定的壓縮率無法同時適應所有技能，且同一技能在不同模型上的最佳壓縮率也可能不同。多解析度設計使 SKIM 能夠同時以多種標記預算表示同一技能，部署前的離線自我判斷機制（offline self-judgment mechanism）會自動選擇維持執行準確度的最低預算解析度。這種設計完美契合技能部署範式：開發者可為不同主流目標模型預計算並分發輕量級軟標記套件，當技能更新時，透過單次前向傳遞即可瞬間重新生成壓縮表示。

**Q7：SKIM 在哪些基準測試上進行了評估？**
A：根據論文，SKIM 在多個基於技能的資料集上進行了評估，並與表 1 中列出的多種代表性方法進行比較，包括硬標記壓縮方法（LLMLingua-2、LongLLMLingua）與軟標記壓縮方法（ICAE、500xCompressor、DRIFT、TokMem）。這些基準涵蓋了不同類型的技能任務，能夠全面評估 SKIM 在保留程序性知識方面的效能。具體的資料集細節在論文的實驗章節中有更詳細的描述。

**Q8：SKIM 的關鍵實驗結果是什麼？**
A：實驗結果顯示，SKIM 能將技能壓縮至原始標記長度的 30% 到 60%，同時在任務效能上優於現有的壓縮方法。這意味著 SKIM 在顯著減少標記消耗的同時，能更好地保留技能的執行邏輯，避免了如 ICAE 在程序性問題上出現的執行失敗問題。這一結果驗證了針對程序性知識設計專門壓縮框架的必要性與 SKIM 方法的有效性。

**Q9：消融研究揭示了哪些設計選擇的重要性？**
A：雖然論文中未提供完整的消融研究細節，但從方法設計可以推斷，三階段訓練中的每個階段都對最終效能至關重要：缺少技能重建會損害語義保留，缺少程序性預熱會使模型無法理解工作流程邏輯，缺少技能任務對齊則無法確保下游任務的執行正確性。此外，多解析度設計與離線自我判斷機制的組合，使得 SKIM 能夠靈活適應不同技能與模型配對，避免了固定壓縮率帶來的效能瓶頸。

**Q10：SKIM 在實際部署中的應用場景有哪些？**
A：SKIM 特別適用於技能被反覆調用的場景，例如企業內部部署的 LLM 代理系統、開發者日常使用的程式設計助手，以及需要整合多個工具協議的複雜代理工作流程。在這些場景中，熱門技能可能每天被調用數千次，每次節省的標記都會累積成顯著的計算節省。此外，對於需要頻繁更新技能的社群驅動生態系統，SKIM 的輕量級離線壓縮特性使得技能更新能即時反映，無需昂貴的重新訓練。

**Q11：從產品角度來看，SKIM 的設計如何影響開發者體驗？**
A：SKIM 將技能表示為預計算的軟標記套件，這類似於軟體發行中的預建構件，開發者可以像分發普通檔案一樣分發壓縮後的技能，大幅簡化了部署流程。當技能更新時，單次前向傳遞即可重新生成壓縮表示，無需等待耗時的訓練過程，這對於快速迭代的開發環境至關重要。同時，多解析度設計允許同一技能針對不同模型提供最佳化版本，開發者無需深入理解每個模型的壓縮特性即可獲得良好效能。

**Q12：SKIM 對 LLM 代理生態系統的影響是什麼？**
A：SKIM 透過降低技能部署成本，可能加速 LLM 代理生態系統的擴張，使更多開發者願意創建並分享技能，進而豐富整個生態系統。此外，輕量級的壓縮表示使得技能能夠在資源受限的環境（如邊緣裝置）中部署，擴大了 LLM 代理的應用範圍。從更宏觀的角度看，SKIM 將技能壓縮從事實性知識的範式轉變為程序性知識的範式，這一概念上的突破可能啟發後續更多針對特定知識類型的壓縮方法研究。

**Q13：SKIM 的局限性有哪些？**
A：SKIM 的多解析度設計需要為每個技能預計算多個版本的軟標記，這會增加儲存成本，特別是對於技能數量龐大的生態系統。此外，雖然離線壓縮是輕量級的，但首次為某個技能-模型配對生成壓縮表示仍需要一定的計算資源。論文中也提到，最佳壓縮率可能因模型而異，這意味著需要為不同的目標 LLM 分別生成壓縮表示，增加了維護負擔。

**Q14：在哪些情況下 SKIM 可能會失敗？**
A：對於極度複雜或資訊密度極高的技能，即使使用最高解析度，SKIM 也可能無法完整保留所有邏輯依賴，導致執行失敗。此外，如果技能的更新頻率極高且變更劇烈，預計算的軟標記可能會迅速過時，需要頻繁重新生成。對於包含罕見工具協議或特殊領域邏輯的技能，訓練資料中可能缺乏相應範例，導致壓縮效果不佳。

**Q15：未來的研究方向是什麼？**
A：未來研究可以探索更智慧的解析度選擇機制，例如根據技能的語義分析自動預測最佳壓縮率，而非依賴離線自我判斷。此外，可以研究跨模型通用的壓縮表示，使得同一套軟標記能夠在多個目標 LLM 上使用，進一步降低維護成本。另一個有前景的方向是將 SKIM 與其他優化技術（如 KV 快取重用）結合，實現更全面的推理效率提升，並探索其在多模態技能（如包含圖像或程式碼的技能）上的擴展。

## 實務應用指南

### 適用場景

1. **企業內部客服與 IT 自動化助理**：將「重置密碼」「查詢訂單」「建立工單」等高頻呼叫的 SKILL.md 技能預先壓縮成軟標記包，部署到內部 LLM 代理。當員工反覆觸發相同工作流程時，可省下 40–70% 的預填充成本，特別適合每週數十萬次呼叫的大型客服系統。

2. **開發者工具生態（如 OpenClaw 類技能市集）**：技能作者發布技能時，同時附帶針對主流模型（GPT、Claude、Llama 等）預先生成的多解析度軟標記包。下載者只需載入對應的軟標記並切換共享 LoRA 適配器，即可立即使用，無需重新訓練。

3. **資料分析與 BI 助理**：將「查詢咖啡價格資料庫」「產生季度財報」等需要嚴格遵循多步驟工作流程的技能壓縮後嵌入代理。實驗顯示在 ToolQA 等場景中，SKIM 能保留完整的 LoadDB → FilterDB → Finish 邏輯鏈，避免 ICAE 等方法在程序性任務上失效的問題。

4. **邊緣裝置與低延遲推論**：在資源受限的環境（如行動裝置、嵌入式系統）部署 LLM 代理時，透過預壓縮技能降低上下文長度，可顯著減少首次標記時間（TTFT）與記憶體佔用，使即時互動體驗更順暢。

5. **頻繁迭代的研究型代理框架**：當技能內容因新工具或新政策而經常更新時，SKIM 的單次前向壓縮流程可在數秒內重新產生軟標記，避免 TokMem 等需要昂貴線上梯度反傳的方法所造成的部署瓶頸。

### 實作前置條件

**資料需求**
- 目標技能的 SKILL.md 原始文本集合（建議至少數百個技能以涵蓋不同複雜度）。
- 對應技能的「程序性問答對」訓練資料：每筆包含技能文本、輸入問題、預期的多步 Thought/Action/Observation 軌跡（類似 ToolQA、API-Bank 格式）。
- 用於重建預訓練階段的純文本語料（可來自 Wikipedia、書籍或領域文件），協助壓縮器學習通用語義編碼。

**運算資源**
- 一張以上具備 24GB 以上的 GPU（如 A100、RTX 4090）以訓練壓縮器與投影器；推論階段則視目標 LLM 而定。
- 目標 LLM 的權重（建議 7B–13B 規模作為起點），以及對應的 LoRA 微調環境（peft 函式庫）。
- 儲存空間：每個技能 × 每個目標模型 × 每個解析度都會產生一份軟標記檔案，需預估數 GB 至數十 GB 不等。

**技能與系統前置條件**
- 技能本身須以結構化自然語言撰寫，明確標註工具呼叫協議（如 `LoadDB[...]`、`Finish[...]` 格式）。
- 已部署或可取得目標 LLM 的推論後端（vLLM、TensorRT-LLM、HuggingFace TGI 等），並具備載入 LoRA 適配器的支援。
- 具備評估管線：能自動執行技能、解析動作、計算任務成功率，用於離線自我判斷機制。

### 實作步驟建議

1. **技能盤點與分群**：先盤點現有 SKILL.md，根據「步驟數」「工具呼叫數」「條件分支數」等指標將技能分為簡單、中等、複雜三類，作為後續多解析度設定的依據。

2. **建立訓練資料管線**：
   - 收集或合成每個技能的「程序性問答對」，確保涵蓋所有工作流程分支。
   - 為重建階段準備通用文本語料；為程序性暖身階段準備「動作序列預測」資料；為任務對齊階段準備完整的代理軌跡。

3. **三階段漸進式訓練**：
   - **階段一（技能重建）**：訓練壓縮器與投影器，使其能從軟標記還原原始技能文本，建立基本編碼能力。
   - **階段二（程序性暖身）**：引入動作序列預測目標，讓模型學會保留工具呼叫的順序與參數依賴。
   - **階段三（技能任務對齊）**：凍結壓縮器與投影器，僅以單一 LoRA 模組微調目標 LLM，使其能正確解讀軟標記並產生預期動作。

4. **多解析度軟標記生成**：為每個技能產生 2–4 種不同標記預算的版本（例如原長度的 30%、45%、60%），儲存為可分發的工件檔。

5. **離線自我判斷機制**：在部署前，以最低成本解析度開始，逐步提升直到任務成功率通過預設閾值，記錄最佳解析度作為該技能 × 該模型組合的預設值。

6. **打包與分發**：將軟標記包、LoRA 適配器、解析度選擇表組合成「技能工件」，上傳至技能市集或內部 registry。

7. **線上推論整合**：在代理框架中新增一個「技能載入器」，根據呼叫請求自動載入對應軟標記、切換共享 LoRA，並監控 TTFT 與任務成功率。

8. **持續監控與再壓縮**：當技能被更新時，觸發單次前向壓縮重新產生軟標記；定期以新資料微調 LoRA，維持長期效能。

### 潛在風險與注意事項

- **程序性邏輯斷裂風險**：即使壓縮後整體語義看似保留，單一工具參數或條件分支的丟失仍會導致執行失敗。**緩解方式**：在階段二強化動作序列預測目標，並在自我判斷階段以「端到端執行成功率」而非「文本相似度」作為閾值。

- **跨模型可移植性受限**：軟標記與 LoRA 高度耦合於特定目標 LLM，更換模型需重新生成。**緩解方式**：為主流模型（GPT、Claude、Llama 等）分別預先生成工件，並在文件中明確標示相容性。

- **解析度選擇錯誤**：若自我判斷閾值設得太寬鬆，可能選到過低解析度而犧牲效能；太嚴格則失去壓縮意義。**緩解方式**：以驗證集掃描不同閾值的成本—效能曲線，選擇 Pareto 前緣上的工作點。

- **技能更新帶來的版本漂移**：當 SKILL.md 被修改但軟標記未及時更新時，代理可能依據過期邏輯執行。**緩解方式**：在技能管理系統中加入「內容雜湊比對」機制，偵測原始技能變更後自動觸發再壓縮。

- **評估管線偏差**：若訓練資料中的動作格式與實際部署環境不一致，模型可能產生語法正確但語意錯誤的動作。**緩解方式**：使用與生產環境相同的工具解析器與錯誤回饋機制來生成訓練軌跡。

- **儲存與分發成本**：多解析度 × 多模型 × 多技能的組合可能產生大量工件。**緩解方式**：僅為高頻呼叫技能保留多解析度，低頻技能僅保留單一最佳解析度。

### 與其他技術的整合建議

- **與 vLLM / TensorRT-LLM 整合**：將 SKIM 產生的軟標記視為「預計算的 prompt embedding」，透過這些推論引擎的 prompt embedding API 直接注入，繞過傳統 tokenizer。可在 vLLM 中以 `multi_modal_data` 或自訂輸入嵌入介面實作。

- **與 LangChain / LlamaIndex 代理框架整合**：在現有代理的「技能載入」節點插入 SKIM 壓縮器，將 SKILL.md 自動轉換為軟標記；保留原始文本作為 fallback，當壓縮版本失敗時自動降級。

- **與 LoRA 服務化平台整合**：將 SKIM 的共享 LoRA 適配器註冊至 LoRA 交換機制（如 HuggingFace PEFT 的 hot-swap），使多個技能可共用同一份 LoRA，降低記憶體佔用。

- **與快取與觀測系統整合**：把「技能 ID × 模型 × 解析度」作為快取鍵，搭配 Redis 等快取層儲存預壓縮結果；並將 TTFT、任務成功率等指標匯入既有 observability 平台（如 LangSmith、Phoenix）。

- **與 CI/CD 管線整合**：在技能市集的發布流程中加入 SKIM 壓縮步驟，每次 PR 自動產生新工件並跑回歸測試，確保更新不會破壞既有任務效能。

- **與 RAG 系統互補**：對於需要大量背景知識的任務，可將 SKIM 用於壓縮「程序性技能」，將 RAG 用於壓縮「事實性文件」，兩者分工互補。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節了解「為什麼技能需要壓縮」以及「程序性知識與事實性知識的差異」，搭配 Figure 1 的範例直觀感受 ICAE 在程序性任務上的失敗案例。接著跳到第 3 節的整體架構圖，掌握「壓縮器 → 投影器 → 目標 LLM」的雙模型設計即可，數學細節可暫時略過。

**給 AI 工程師**：重點關注第 3 節的三階段訓練流程與第 4 節的實驗設定，特別是 LoRA 模組的設計選擇與多解析度自我判斷機制的實作細節。建議直接 clone 官方程式碼（github.com/bebr2/SKIM），以一個小型技能集重現 Table 2 的結果，再逐步擴展到自家業務場景。

**給研究者**：第 2 節的相關工作分類（Table 1）值得仔細研讀，理解硬壓縮、軟壓縮、KV 快取重用等方法的取捨。第 5 節的消融實驗與不同解析度下的效能曲線，是延伸研究（例如自適應壓縮率學習、跨模型軟標記蒸餾）的良好起點。建議從「程序性知識的形式化定義」與「壓縮後的可執行性保證」兩個方向切入。

**給產品經理**：聚焦於第 1 節的動機段落與第 4 節的實驗結論，特別是「30–60% 標記長度縮減」與「任務效能不降反升」這兩個關鍵數字。理解 SKIM 的價值不在於「更小的模型」，而在於「更低的單次呼叫成本與更快的回應速度」，這對 ROI 計算與定價模型設計有直接影響。建議在內部推動時，以「高頻技能 × 多模型支援 × 快速迭代」三個維度評估導入優先順序。
