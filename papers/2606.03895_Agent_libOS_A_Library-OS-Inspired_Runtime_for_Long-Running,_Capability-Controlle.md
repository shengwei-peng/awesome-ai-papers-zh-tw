# Agent libOS：受函式庫作業系統啟發、適用於長期執行且受權能控制之 LLM 代理程式的執行階段底層

**原文標題：** Agent libOS: A Library-OS-Inspired Runtime for Long-Running, Capability-Controlled LLM Agents  
**作者：** Yingqi Zhang  
**發布日期：** 2026-06-02  
**HF 連結：** [https://huggingface.co/papers/2606.03895](https://huggingface.co/papers/2606.03895)  
**arXiv：** [https://arxiv.org/abs/2606.03895](https://arxiv.org/abs/2606.03895)  

---

## ⚡ TL;DR

現有 LLM 代理框架以工具分派為信任邊界，難以安全地支撐長期執行、權限變化與稽核需求。
提出 Agent libOS，將代理視為具權能與生命週期的行程，並以執行階段原語作為權限邊界。
建構 Python 原型並完成 123 項測試，證明代理程式可被安全排程、授權、續行與稽核。

---

## 摘要翻譯

大型語言模型（LLM）代理程式（LLM agent）正從請求回應式助理（request-response assistant）演變為長期執行的軟體行為者（software actor）：它們在多次模型呼叫之間維持狀態、分叉子任務、等待外部事件（event）、請求人類授權、產生工具，並執行副作用（side effect），且其執行過程必須支援續行與稽核。本文提出 Agent libOS，一個受函式庫作業系統（library OS, libOS）啟發、專為 LLM 代理程式設計的執行階段底層（runtime substrate）。Agent libOS 運行於傳統宿主作業系統（host operating system）之上；它不實作硬體驅動程式、核心模式隔離（kernel-mode isolation），亦不實作 POSIX 相容作業系統（POSIX-compatible operating system）。相反地，它將代理程式視為 AgentProcess：一個具備行程身分（process identity）、父子血緣（parent-child lineage）、生命週期狀態（lifecycle state）、衍生自 AgentImage 的工具表（tool table）、具型別的 Object Memory、顯式權能（explicit capability）、人類佇列（human queue）、檢查點（checkpoint）、事件（event）與稽核記錄（audit record）的可排程執行主體（schedulable execution subject）。其核心設計原則是「工具為類 libc 包裝函式（libc-like wrapper）；執行階段原語（runtime primitive）構成權限邊界（authority boundary）」。檔案系統存取、物件存取、睡眠、人工核准、JIT 工具註冊（JIT tool registration）以及外部副作用（external side effect），皆在顯式權能（explicit capability）與策略（policy）下於原語邊界接受檢查。

本文描述其設計、威脅模型、Python 原型，以及安全性導向的評估。目前的原型實作了非同步排程（async scheduling）、命名空間區域物件記憶體（namespace-local Object Memory）、執行階段整合式人工核准（runtime-integrated human approval）、一次性權限授予（one-shot permission grant）、每行程工作目錄（per-process working directory）、Shell 原語（shell primitive）與映像檔註冊原語（image-registration primitive）、透過 libOS 系統呼叫仲介（libOS syscall broker）執行之 Deno/TypeScript JIT 工具（Deno/TypeScript JIT tool）、檔案系統／物件橋接工具（filesystem/object bridge tool）、可注入的 Resource Provider Substrate、確定性展示（deterministic demo）、真實模型煙霧測試腳本（real-model smoke script），以及截至撰稿時共 123 項迴歸測試（regression test）。Agent libOS 並非旨在改善規劃器準確率（planner accuracy），而是展示一個執行階段底層（runtime substrate），使長期執行的 LLM 代理程式得以被排程、授權、續行與稽核，且無須將工具分派（tool dispatch）視為信任邊界（trust boundary）。

### 核心貢獻（3～5點）
- 提出受函式庫作業系統啟發的 Agent libOS，將 LLM 代理程式重新抽象為具備行程身分、父子血緣、生命週期與顯式權能的可排程執行主體（AgentProcess），填補長期執行代理程式在執行階段底層的設計空缺。
- 確立「執行階段原語為權限邊界」的核心設計原則，相對於傳統以工具分派為信任邊界的做法，從架構層面強化授權、稽核與安全性。
- 實作完整的 Python 原型，涵蓋非同步排程、命名空間區域物件記憶體、執行階段整合式人工核准、一次性權限授予、JIT 工具註冊、檢查點與稽核記錄等機制，並以 123 項迴歸測試與真實模型煙霧測試腳本進行驗證。
- 建立以顯式權能為基礎的授權模型，支援人類佇列、外部副作用管控與可重建狀態，確保代理程式的操作可被追蹤、恢復與審查。

### 適合對象
從事 LLM 代理程式框架設計、AI 系統安全與治理研究的學者與工程師；特別是關注長期執行代理程式之權限隔離、稽核軌跡、人機協作授權，以及作業系統層級執行階段設計的進階讀者。

## 深度分析

#### 方法論解析

Agent libOS（函式庫作業系統）的核心方法論，是將 LLM agent（LLM 代理程式）從傳統的 request-response assistant（請求回應式助理）抽象，提升為長期執行的 software actor（軟體行為者），並為其設計一套 library OS（函式庫作業系統）風格的 runtime substrate（執行階段底層）。此執行階段運行於 host operating system（宿主作業系統）之上，不實作硬體驅動程式、kernel-mode isolation（核心模式隔離）或 POSIX-compatible operating system（POSIX 相容作業系統），而是將作業系統的抽象概念——行程、權能、命名空間、阻塞裝置、稽核——移植到代理程式層級。

**AgentProcess（代理行程）** 是整個架構的中心執行主體。不同於傳統 chat loop（對話迴圈）中無狀態的 tool dispatch（工具分派），AgentProcess 是一個 schedulable execution subject（可排程執行主體），具備以下屬性：
- **process identity（行程身分）** 與 **parent-child lineage（父子血緣）**：支援代理程式的分叉與衍生，並允許權限沿著譜系衰減。
- **lifecycle state（生命週期狀態）**：管理代理程式的執行、等待、暫停與恢復。
- **tool table（工具表）**：衍生自 **AgentImage（代理映像檔）**，定義該行程可視的工具集合。
- **namespace-local Object Memory（命名空間區域物件記憶體）**：提供具型別的行程私有物件記憶體空間，隔離不同代理程式的狀態。
- **explicit capability（顯式權能）**：所有對外部資源的存取——包括 filesystem access（檔案系統存取）、object access（物件存取）、sleeps（休眠）、human approval（人工核准）、JIT tool registration（JIT 工具註冊）與 external side effect（外部副作用）——皆需持有對應權能，拒絕 ambient authority（環境權限）。
- **human queue（人類佇列）**：用於請求人類授權的阻塞型機制，允許代理行程暫停並在核准後恢復。
- **checkpoint（檢查點）** 與 **audit record（稽核記錄）**：分離 reconstructable state（可重建狀態）與 irreversible external effect（不可逆的外部效應），確保長期執行代理程式的可恢復性與事後審計能力。

**設計規則：「工具即 libc-like wrapper（類 libc 包裝函式），runtime primitive（執行階段原語）即 authority boundary（權限邊界）」**。這是 Agent libOS 相對於現有框架最根本的設計差異。在傳統架構中，model-facing action surface（面向模型的動作介面）往往同時充當存取 host resource（宿主資源）的路徑，例如「模型可以呼叫 write_file」與「執行環境有權寫入該路徑」之間僅隔著一層 wrapper convention（包裝器慣例）。Agent libOS 則將工具視為單純的類 libc 包裝函式，真正的 policy boundary（策略邊界）位於執行階段原語：當動作試圖觸及檔案系統、物件、Shell、image-registration primitive（映像檔註冊原語）或人類權威時，由執行階段的原語管理器進行顯式權能檢查與稽核，而非依賴工具層的提示工程或包裝函式自律。

原型實作採用 Python，包含 async scheduling（非同步排程器）、per-process working directory（每行程工作目錄）、runtime-integrated human approval（執行階段整合式人工核准）、one-shot permission grant（一次性權限授予），以及透過 **libOS syscall broker（libOS 系統呼叫仲介）** 載入的 Deno/TypeScript JIT tool（Deno/TypeScript JIT 工具）。此外，**Resource Provider Substrate（可注入資源提供者底層）** 允許彈性替換底層資源實作，而 filesystem/object bridge tool（檔案系統／物件橋接工具）則連接 Object Memory（物件記憶體）與宿主檔案系統。

#### 實驗數據解讀

本文明確聲稱其貢獻為架構性（architectural）而非 benchmark-driven（基準測試導向），因此並未採用 SWE-bench、WebShop 等 planner accuracy（規劃器準確率）指標。評估聚焦於執行階段的可執行性、安全性與隔離性質，包含三類實驗：

1. **deterministic demo（確定性展示）**：用於驗證系統行為的可重現性。在涉及排程、權能檢查與檢查點恢復的場景中，確定性展示確保給定相同的初始狀態與權能集合，代理行程的行為軌跡一致，這對於 audit record（稽核記錄）的可靠性至關重要。

2. **real-model smoke script（真實模型煙霧測試腳本）**：透過真實的大型語言模型進行端對端驗證，確認 Agent libOS 在實際模型驅動下的 tool dispatch（工具分派）、human queue（人類佇列）阻塞與恢復、以及 JIT 工具執行等路徑可正常運作。這類測試屬於快速驗證性質，旨在發現整合層級的明顯缺陷，而非衡量任務完成率。

3. **123 項 regression test（迴歸測試）**：這是評估的核心量化依據，涵蓋以下安全與隔離維度：
   - **Containment（隔離）**：驗證代理行程無法逾越其被授予的顯式權能範圍。
   - **Revocation（撤銷）**：測試權能在執行期被撤銷後，後續操作是否遭到正確阻擋。
   - **Fork/spawn attenuation（分叉／衍生衰減）**：驗證子行程繼承的權能是否依 parent-child lineage（父子血緣）正確衰減，防止權限提升。
   - **Exec non-escalation（執行非升權）**：確保透過 exec 類機制載入新工具表時不會意外取得額外權限。
   - **Namespace authority（命名空間權威）**：檢查 namespace-local Object Memory（命名空間區域物件記憶體）的隔離是否有效。
   - **Tool-table denial（工具表拒絕）**：確認未授權的工具無法被代理行程呼叫。
   - **JIT syscall isolation（JIT 系統呼叫隔離）**：驗證即時編譯的 Deno/TypeScript 工具透過 libOS syscall broker（libOS 系統呼叫仲介）發出的請求受到同等權能約束。
   - **Shell policy matching（Shell 策略匹配）**：測試 shell primitive（Shell 原語）是否符合預設的安全策略。
   - **Image registration authority（映像檔註冊權威）**：確認 AgentImage（代理映像檔）的註冊與工具表衍生受權能控管。
   - **Human-queue resumption（人類佇列恢復）**：驗證人工核准流程的中斷與續行機制。
   - **Wrapper purity（包裝函式純粹性）**：確保工具作為 libc-like wrapper（類 libc 包裝函式）不會繞過執行階段原語的策略邊界。

這些測試數據的意義不在於證明 Agent libOS 能「更聰明」地解決任務，而在於證明它提供了一個可執行的底層，使得長期執行代理程式能夠在明確的 authority boundary（權限邊界）內被排程、授權、恢復與稽核，而不必將 trust boundary（信任邊界）寄託於工具分派層。

#### 與現有研究的比較

**相對於工具使用與多代理框架**
現有主流系統如 ReAct、Toolformer、HuggingGPT、AutoGen、MetaGPT 與 LangGraph 等，其工程抽象多為 chat loop（對話迴圈）或圖形化工作流，聚焦於規劃、角色協議與工具選擇。Agent libOS 並不取代這些框架的規劃器，而是定位於其下方的 runtime substrate（執行階段底層）。換言之，一個基於角色或圖形的代理程式可以運行於 Agent libOS 之上，同時由後者的原語管理器強制執行權能檢查、阻塞語義與稽核。這填補了高階代理框架與宿主資源之間缺乏授權邊界的空白。

**相對於記憶體與技能累積系統**
Reflexion、Generative Agents、MemGPT 與 Voyager 等研究顯示代理程式受益於記憶、反思、virtual memory（虛擬記憶體）式的 context paging（上下文分頁）與 executable skill（可執行技能）的累積。Agent libOS 同樣採用 OS 隱喻，但焦點不同：它關注的不是「代理程式能記住或學會什麼」，而是「當代理程式試圖存取物件、路徑、人類、時鐘或工具註冊表時，哪個執行主體被授權、權限如何沿著分叉衰減、以及事後留下什麼記錄」。

**相對於 OS 風格的代理基礎設施**
AIOS 與 AOS 提出 agent operating system（代理作業系統），研究排程、上下文、記憶體、儲存與存取控制服務。Agent-OS 藍圖亦主張為安全與互操作性提供類 OS 服務。Agent libOS 的範圍更為狹窄且邊界清晰：它專注於「模型面向的動作轉化為經授權、可稽核的執行階段操作」這一交界點。此外，Agent libOS 明確區分自身與硬體面向的函式庫作業系統（如 unikernels）或核心模式隔離機制——它保護的是代理程式原生資源，而非 CPU 核心或磁碟區塊。

**相對於權能系統與安全研究**
古典系統研究如 exokernels、unikernels，以及 capability system（權能系統）如 KeyKOS、EROS、seL4、Capsicum，為 least authority（最小權限）、權限衰減與名稱和權威分離提供了理論基礎。Agent libOS 將這些概念適配於隨機性、提示敏感的代理程式環境。現有針對 indirect prompt injection（間接提示注入）、tool-output injection（工具輸出注入）與 confused-deputy problem（混淆副手問題）的研究指出，僅依賴 wrapper convention（包裝器慣例）的安全機制過於脆弱。Agent libOS 直接回應此問題，將 runtime primitive（執行階段原語）設為穩定的權威邊界，使得即使模型遭受提示攻擊，未持有對應 explicit capability（顯式權能）的操作仍會在執行階段被阻擋。

**限制**
作者明確指出若干限制：本研究不宣稱提升 planner accuracy（規劃器準確率）；原型為 Python 實作，未達 production-grade sandboxing（生產級沙箱）強度；亦未進行 formal verification（形式驗證）。此外，Agent libOS 並非 Linux、macOS、containers（容器）或 hypervisors（虛擬機器監視器）的替代品，其隔離性仰賴執行階段檢查而非硬體或核心模式保護。

#### 可重現性評估

根據本文提供的上下文，Agent libOS 以可運作的 Python 原型形式實作，並包含 deterministic demo（確定性展示）、real-model smoke script（真實模型煙霧測試腳本），以及多達 123 項的 regression test（迴歸測試）套件。這些測試涵蓋隔離、撤銷、命名空間權威、JIT 系統呼叫隔離等維度，理論上為第三方驗證系統行為提供了具體的實驗基礎。確定性展示的設計亦有助於排除模型隨機性對系統層級驗證的干擾，提升實驗的可重現性。

然而，在提供的文本片段中，**並未明確提及原始碼儲存庫連結、開源授權條款、資料集釋出或 model weights（模型權重）的取得方式**。由於 Agent libOS 屬於執行階段架構而非模型訓練研究，其核心可重現性取決於執行環境與原始碼的可用性。若論文完整版本未附帶公開的程式碼與測試套件，則其他研究者僅能依據文中描述的設計規則與介面定義進行重新實作，而無法直接複現現有的 123 項迴歸測試。建議後續發表時提供完整的開源原型、測試腳本與環境設定文件，以強化社群對此執行階段邊界設計的驗證與採納。

#### 未來研究方向

1. **形式化驗證與生產級沙箱化**
   當前原型以 Python 實作執行階段檢查，未來可朝 formal verification（形式驗證）邁進，證明權能衰減與原語邊界的正確性；或整合作業系統層級的硬體隔離（如 containers（容器）、虛擬機器、WebAssembly）以達到 production-grade sandboxing（生產級沙箱），彌補目前僅有執行階段檢查的不足。

2. **與高階規劃框架的深度整合**
   Agent libOS 作為 runtime substrate（執行階段底層），可與 ReAct、LangGraph、OpenAI Agents SDK 等框架結合。未來研究可探索如何將 explicit capability（顯式權能）與這些框架的角色（role）、圖節點（graph node）或工具選擇邏輯對接，使規劃器在編排任務時即考量權限邊界。

3. **自動化權能策略推論**
   目前權能授予與衰減可能依賴人工設定或未明示的策略。未來可發展基於任務分析或程式合成（program synthesis）的自動化權能配置，讓代理程式在分叉子任務時自動取得最小且充分的權限集合，降低人為配置負擔。

4. **分散式與多機排程**
   當代理程式的 lifecycle state（生命週期狀態）跨越單一宿主時，parent-child lineage（父子血緣）與 namespace-local Object Memory（命名空間區域物件記憶體）需要跨網路延伸。研究分散式 Agent libOS 的檢查點同步、跨機 event（事件）傳遞與全域 audit record（稽核記錄）聚合，將是長期執行代理程式規模化的關鍵。

5. **稽核記錄的合規與法律應用**
   隨著 LLM agent（LLM 代理程式）開始執行不可逆的外部副作用，audit record（稽核記錄）可能需滿足法規要求（如金融、醫療領域的不可篡改日誌）。未來可研究將稽核鏈上鏈（blockchain-based audit trail）或整合至現有資安資訊與事件管理（SIEM）系統。

6. **動態權能撤銷與即時回應**
   目前雖已支援撤銷，但未來可探索更細緻的即時權能撤銷機制，例如當 human queue（人類佇列）中發現異常請求時，立即凍結相關行程及其所有子行程，防止攻擊擴散。

7. **標準化代理程式權能協定**
   類似 MCP（模型上下文協定）標準化了 tool connectivity（工具連接性），未來可推動 Agent libOS 的顯式權能與原語介面成為跨框架標準，使不同供應商的代理程式能在統一的授權與稽核語義下互操作。

## 論文問答

**Q1：Agent libOS 旨在解決的核心問題是什麼？現有的對話迴圈抽象為何不足以應對長期執行的 LLM 代理程式？**

A：現有框架通常僅以包裝器慣例隔離「面向模型的動作介面」與「宿主資源」的存取路徑，導致兩者之間缺乏真正的權限邊界。這種設計在面對間接提示注入、工具輸出注入或混淆副手問題時顯得極為脆弱，因為模型一旦呼叫工具，往往直接獲得執行階段的全域權限。對於需要長期執行、分叉子任務、等待外部事件並產生不可逆外部副作用的軟體行為者而言，單純的對話迴圈無法提供行程身分、生命週期管理、顯式權能與稽核記錄等必要的系統層級支撐。

**Q2：為何現有的工具使用框架（如 ReAct、AutoGen）無法為長期執行的代理程式提供足夠的安全性與生命週期管理？**

A：這些框架普遍將工具分派視為信任邊界，讓 Python 包裝函式直接觸及宿主資源，卻未在執行階段原語層級進行授權檢查。這種動作暴露與資源權限的混同意味著，任何遭竄改的工具輸出或注入提示都可能繞過原本的限制，進而執行未經授權的操作。此外，它們缺乏 AgentProcess 所具備的行程身分、父子血緣、顯式權能衰減以及稽核記錄等機制，難以安全地管理會持續存在、等待事件或產生長期副作用的代理程式。

**Q3：為何將 LLM 代理程式視為「軟體行為者」而非「請求回應式助理」具有重要性？**

A：軟體行為者會在多次模型呼叫之間維持狀態、分叉子任務、等待外部事件，並產生需要被稽核與續行的外部副作用，這已超出單純提示工程所能處理的範疇。這種典範轉移揭示了身分識別、排程、最小權限、中斷與恢復等根本的系統問題，必須由執行階段底層加以解決。若缺乏類似 Agent libOS 的函式庫作業系統式執行環境，這些長期執行的代理程式將只能在臨時拼湊的環境中運作，容易導致權限升級與無法追蹤的不可逆外部效應。

**Q4：Agent libOS 的核心執行階段抽象是什麼？它如何結構化代理程式的執行？**

A：核心抽象是 AgentProcess，一個具備行程身分、父子血緣、生命週期狀態，以及衍生自 AgentImage 之工具表的可排程執行主體。每個 AgentProcess 都擁有具型別的 Object Memory 命名空間、顯式權能、人類佇列、檢查點、事件與稽核記錄，使其如同作業系統中的行程般被管理。這種結構讓執行階段能夠在清晰的權限邊界與狀態隔離下，對代理程式進行排程、授權、暫停與恢復。

**Q5：「工具為類 libc 包裝函式；執行階段原語為權限邊界」這條核心設計規則的內涵為何？**

A：這條規則意味著模型可見的工具僅是便利的包裝層，類似傳統作業系統中的 libc，真正的安全性與策略強制執行發生在執行階段原語的層次。無論是檔案系統存取、物件存取、人工核准或外部副作用，都在原語邊界接受顯式權能與策略的檢查，而非僅依賴工具包裝器進行把關。如此一來，模型能「看到」什麼動作與能「執行」什麼授權被解耦，有效防範間接提示注入與混淆副手等攻擊。

**Q6：Agent libOS 為何選擇在傳統宿主作業系統之上運作，而非實作核心模式隔離或 POSIX 相容作業系統？**

A：Agent libOS 刻意將保護範圍聚焦於代理程式原生資源，例如 Object Memory、工具表、工作區路徑、人工核准、檢查點與外部副作用，而非 CPU 核心或磁碟區塊等硬體層資源。透過以使用者空間執行階段底層的形式運作，它避免了硬體驅動程式與核心模式隔離的複雜度，同時仍能為代理程式生命週期與安全性提供作業系統式的抽象。這樣的範圍界定使其能專注於滿足隨機性、長期執行之 LLM 代理程式的獨特需求，而無需取代現有的宿主基礎設施。

**Q7：既然 Agent libOS 不以規劃器準確率為目標，它如何評估其執行階段底層？**

A：評估方式包含確定性展示、真實模型煙霧測試腳本，以及涵蓋 123 項測試的迴歸測試套件。這些測試涵蓋隔離 containment、權能撤銷、分叉／生成衰減、執行非升權、命名空間權限、工具表拒絕、JIT 系統呼叫隔離、人類佇列續行等執行階段屬性。這種以安全性為導向的評估驗證了架構邊界與權能檢查的正確性，而非衡量端對端任務的成功率。

**Q8：迴歸測試套件具體驗證了哪些執行階段屬性？**

A：123 項測試驗證了包含副作用隔離、權能撤銷、跨分叉／生成的權能衰減、執行階段非升權、Object Memory 命名空間權限、未授權工具表拒絕、JIT 系統呼叫隔離、Shell 策略比對、映像檔註冊權限、人類佇列續行，以及包裝函式純粹性等關鍵屬性。這些測試確保在各種操作情境下，執行階段原語都能落實所宣告的權限邊界。測試的成功執行證明 Agent libOS 能夠在不依賴臨時包裝器慣例的前提下，對代理程式進行排程、授權與稽核。

**Q9：本文雖未呈現傳統的模型效能消融實驗，但在架構上提出了哪些關於信任邊界的比較性主張？**

A：本文主張將工具分派視為信任邊界——正如主流對話迴圈框架所做的——在本質上是脆弱的，相較於將原語層級的顯式權能檢查作為權限邊界。透過將策略邊界從包裝函式重新定位到執行階段原語，Agent libOS 可防止間接提示注入與工具輸出注入在不被察覺的情況下提升權限。迴歸測試中確認單純的包裝函式無法繞過原語管理程式的檢查，實質上消融了「包裝器層級隔離足以保障安全」的錯誤假設。

**Q10：在哪些實際應用場景中，Agent libOS 相較於標準代理程式框架能提供關鍵價值？**

A：Agent libOS 對於需要長期執行的編碼代理程式至關重要，例如檢視程式碼倉儲、生成日誌解析工作者、等待測試完成，並在寫入修補檔前請求人工核准的場景。它為必須在多次模型呼叫間維持狀態、分叉子任務，並在異步人工或外部事件後續行的代理程式提供了不可或缺的基礎設施。任何涉及不可逆外部副作用、需要明確授權、血緣追蹤與稽核記錄的部署情境——如自動化 DevOps 或敏感資料處理——都能受益於此執行階段底層。

**Q11：將 Agent libOS 整合至現有 AI 應用堆疊時，會產生哪些產品層級的考量？**

A：產品團隊必須理解 Agent libOS 運作於規劃器與角色協定之下，因此它與 LangGraph 或 OpenAI Agents SDK 等框架是互補而非取代關係。整合時需要將現有工具包裝函式對應為類 libc 的便利層，同時確保所有觸及宿主環境的操作都經由 libOS 原語進行權能檢查。此外，執行階段整合式人工核准佇列與檢查點機制，也要求產品設計必須配套處理中斷介面、一次性權限授予的互動流程，以及跨長期會話的狀態續行體驗。

**Q12：Agent libOS 可能對 LLM 代理程式基礎設施與安全領域產生哪些更廣泛的影響？**

A：透過將行程、顯式權能與稽核記錄等作業系統式抽象引入代理程式執行層，Agent libOS 為將代理程式安全視為系統問題而非提示工程問題奠定了基礎。這可能推動標準化的執行階段邊界，使 MCP 等工具連接協定能在受強制的原語管理程式之上運作，從而降低整個生態系統的環境權限。此典範轉移鼓勵發展最小權限、可稽核的代理程式架構，提升其對注入攻擊與混淆副手漏洞的韌性。

**Q13：目前的 Agent libOS 原型有哪些已承認的限制？**

A：作者明確指出，該原型並不宣稱具備形式化驗證或等同硬體支援隔離的生產級沙箱能力。它也不以提升 SWE-bench 或 WebShop 等標準基準上的規劃器準確率為目標，因此在任務成功率指標上無法進行直接比較。此外，作為基於 Python 的使用者空間執行階段，它仰賴底層宿主作業系統提供核心模式隔離，無法獨自防禦所有類別的宿主層級入侵。

**Q14：在哪些條件或失效情境下，Agent libOS 的安全保證可能不足以抵擋威脅？**

A：若底層宿主作業系統遭到入侵，或 libOS 系統呼叫仲介本身存在實作缺陷，原語層級的權限檢查仍可能被繞過。系統亦假設人類佇列由合法的運作者處理，若操作者延遲回應或做出錯誤判斷，已授權的副作用仍可能造成損害。再者，由於執行階段未對其權能邏輯進行形式化驗證，策略強制執行或 Resource Provider Substrate 中的細微瑕疵，仍可能產生意外的權限升級路徑。

**Q15：本文建議哪些未來方向以擴展 Agent libOS？**

A：未來工作可朝向對權能強制執行邏輯與原語管理程式進行形式化驗證，以提供更强的安全性保證。將執行階段擴展至支援跨多主機的分散式 AgentProcess，並具備網路化權能委派與檢查點遷移能力，是系統演進的自然方向。此外，與 MCP 等標準協定進行更深層整合，並發展更豐富、可動態調適的上下文感知權限衰減策略語言，將有助於提升生產環境中的互通性與細緻最小權限控制。

## 實務應用指南

### 適用場景

1. **長時運行程式開發代理程式**：適用於需要持續數小時甚至數天的編碼任務，例如自動化程式碼審查、日誌解析子任務分叉、長時間測試等待，以及在寫入修補檔前透過人工佇列請求核准，並在核准後從檢查點續行，同時保留每項不可逆副作用的稽核記錄。
2. **多步驟合規資料處理流程**：在金融、醫療等需嚴格授權的領域，代理程式需跨多次模型呼叫維持狀態、等待外部事件（如資料庫批次作業完成），並依據顯式權能存取敏感物件記憶體，確保僅具備最小權限的行程能執行特定副作用。
3. **企業級自動化維運（AIOps）**：執行 Shell 指令、部署作業或動態產生專用解析工具（Deno/TypeScript JIT 工具）的代理程式，可透過每行程工作目錄與命名空間區域物件記憶體隔離不同環境，並利用執行階段整合式人工核准控制高風險操作。
4. **多代理協作與權限遞減**：當主代理程式需要衍生子代理程式（fork/spawn）處理子任務時，Agent libOS 的父子血緣與權能衰減機制可確保子行程不會繼承過多的環境權限，避免混淆副手問題。
5. **需稽核追蹤的持續性知識工作者**：例如法律文件分析或研究助理，代理程式在長期執行中產生的工具註冊、映像檔註冊與檔案系統存取，均需留下不可竄改的執行階段原語層級稽核軌跡，以供事後合規審查。

### 實作前置條件

**資料準備**：
- 定義 AgentImage 與工具表（tool table）結構，將現有工具重構為類 libc 包裝函式，明確區分「模型可見介面」與「執行階段原語」。
- 設計具型別的 Object Memory 結構描述與命名空間配置，以及顯式權能策略（如檔案路徑、Shell 指令模式、人工核准閘門）。
- 準備稽核記錄儲存方案與檢查點序列化格式，區分可重建狀態與不可逆外部效應。

**運算環境**：
- 宿主作業系統（Linux 或 macOS）與 Python 非同步執行環境。
- 若需 JIT 工具，須安裝 Deno 執行階段以支援 TypeScript 工具透過 libOS 系統呼叫仲介隔離執行。
- 足夠的儲存空間用於命名空間區域物件記憶體、檢查點快照與迴歸測試資料。

**技能需求**：
- 熟悉 Python `asyncio` 與行程生命週期管理，具備作業系統行程、權能系統（capability system）與最小權限原則的基礎知識。
- 能設計安全策略並理解間接提示注入、工具輸出注入與混淆副手問題的攻擊面。
- 具備 TypeScript/Deno 基礎（若需使用即時工具註冊功能）。

### 實作步驟建議

1. **建立 AgentImage 與工具表**：將既有工具分類為純包裝函式（libc-like wrapper），並識別哪些操作必須提升為執行階段原語（如檔案系統橋接、Shell 執行、睡眠、人工核准、JIT 工具註冊）。
2. **設計顯式權能策略**：為每個 AgentProcess 定義權能集合，包含可存取的 Object Memory 命名空間、檔案系統前綴、Shell 指令白名單、人類佇列互動權限，以及一次性權限授予的時效與範圍。
3. **實作 AgentProcess 生命週期**：建構可排程執行主體，實作行程身分識別、父子血緣追蹤、生命週期狀態機，以及每行程工作目錄隔離。
4. **部署命名空間區域 Object Memory**：依據業務邏輯劃分命名空間，確保行程間的物件記憶體隔離，並透過執行階段原語進行存取控制。
5. **整合人類佇列與續行機制**：建立阻塞型人工核准佇列，設計代理程式在等待事件時的非同步掛起與恢復流程，確保全系統不因單一行程等待而停滯。
6. **實作原語管理器（Primitive Managers）**：在檔案系統、物件存取、Shell、映像檔註冊、外部副作用等邊界設置策略檢查點，使權限邊界落於執行階段原語而非工具包裝器。
7. **啟用 Deno/TypeScript JIT 工具**：透過 libOS 系統呼叫仲介提供隔離的 JIT 工具執行環境，限制動態生成工具可發出的系統呼叫範圍。
8. **建構檢查點與稽核基礎設施**：實作週期性檢查點，僅序列化可重建狀態；所有不可逆外部效應必須寫入稽核記錄，記錄授權來源與執行主體。
9. **注入 Resource Provider Substrate**：將宿主資源（如向量資料庫、第三方 API、檔案系統後端）抽象為可注入底層，降低核心執行階段與特定基礎設施的耦合。
10. **建立安全迴歸測試**：參考論文的 123 項測試覆蓋範圍，優先實作權限撤銷、分叉衰減、執行非升權、命名空間權限、工具表拒絕、JIT 隔離等測試案例。

### 潛在風險與注意事項

- **權限提升與混淆副手**：子行程分叉或委派時，若未正確衰減顯式權能，可能導致權限意外擴散。每次 `fork`/`spawn` 後必須重新計算權能集合，並驗證 `exec` 不會繞過原語管理器。
- **間接提示注入與工具輸出注入**：模型可能因惡意工具輸出而嘗試繞過包裝函式。必須確保所有對宿主資源的存取都經過執行階段原語檢查，而非僅依賴 Python 包裝器的輸入清理。
- **人工佇列阻塞與資源耗盡**：長期等待人工核准的行程若未設計逾時或取消機制，可能累積大量休眠行程，佔用非同步排程器資源。建議設定等待上限與降級策略。
- **檢查點與外部狀態不一致**：檢查點僅應包含代理程式內部狀態與 Object Memory，不應包含已寫入宿主檔案系統的副作用。恢復後需確認外部世界狀態是否仍與檢查點邏輯相容。
- **JIT 工具隔離失效**：Deno 沙箱或 libOS 系統呼叫仲介設定錯誤時，動態生成工具可能直接存取宿主資源。部署前應透過獨立迴歸測試驗證 JIT 工具的系統呼叫攔截率。
- **效能開銷**：執行階段權能檢查、命名空間解析與稽核記錄寫入會增加延遲。對於高頻工具呼叫場景，建議在權能快取與安全嚴謹度之間取捨。

### 與其他技術的整合建議

- **現有代理框架（ReAct、AutoGen、LangGraph、OpenAI Agents SDK）**：Agent libOS 定位為執行階段底層，不取代規劃器或角色協議。可將這些框架的對話迴圈與工具選擇邏輯保留於上層，僅將工具分派導入 Agent libOS 的原語管理器，使信任邊界下移至執行階段。
- **MCP（模型上下文協定）**：利用 MCP 標準化模型上下文與工具連接，但在 MCP 介面卡下方接入 Agent libOS 的權限邊界，讓標準化連線仍受顯式權能與稽核約束。
- **容器與編排系統（Docker / Kubernetes）**：Agent libOS 不處理核心模式隔離，建議將其部署於容器內，由宿主作業系統與容器提供硬體層級隔離，Agent libOS 則專注於代理程式原生資源（物件記憶體、工具表、人類佇列）的治理。
- **記憶體與上下文系統**：可將 MemGPT 式的虛擬記憶體分頁或外部向量資料庫作為 Resource Provider Substrate 注入，透過 Object Memory 命名空間統一存取。
- **CI/CD 與可觀測性**：將論文中的確定性展示與真實模型煙霧測試腳本納入部署閘道，利用稽核記錄串流至 SIEM 或日誌平台，實現代理程式操作的即時追蹤。

### 給不同背景讀者的閱讀建議

**初學者**：請先聚焦「作業系統行程」的類比——把代理程式想像成一個需要身分證、需要被排程、需要請假（等待人工核准）的員工。重點理解為何「工具只是包裝器，真正的門禁在執行階段原語」，並從論文中的編碼代理程式範例體會檢查點與稽核的必要性， Capability 理論與非同步排程細節可暫時略過。

**AI 工程師**：請仔細研讀「tools as libc, primitives as authority boundary」這條設計規則，思考如何重構你手邊的工具使用框架。論文中的 Python 原型章節（非同步排程、命名空間區域 Object Memory、Deno/TypeScript JIT 工具透過 libOS 系統呼叫仲介執行）是可直接參考的實作模式，特別注意如何將現有的 `write_file` 或 `bash` 工具從「信任邊界」降級為「單純包裝」。

**研究人員**：請關注論文如何將傳統權能系統（KeyKOS、Capsicum、seL4）與函式庫作業系統概念適配到隨機性、提示敏感的 LLM 代理程式。威脅模型、執行階段原語作為權限邊界的架構主張，以及「不以規劃器準確率、而以執行階段可稽核性為評估目標」的方法論，都是值得延伸的研究切入點。

**產品經理**：請清楚掌握 Agent libOS 的價值主張——它提升的是**安全性、可續行性與可稽核性**，而非 SWE-bench 等任務成功率。若你的應用場景涉及長時間執行、多人協作核准、合規稽核或動態權限調整，這套執行階段底層值得投資；若僅是短回合問答或單次工具呼叫，標準對話迴圈框架可能更輕量。
