## ⚡ TL;DR

現有程式碼代理基準常以單一通過/失敗位元評斷，忽略了使用者實際感受到的完整執行過程。
AgentLens 以完整執行軌跡為評估對象，結合形式驗證與 LLM 評審評論及並排比較。
該基準已用於診斷模型行為、比較版本與夜間偵測產品迴歸，並以開源釋出。

## 摘要翻譯

我們提出 AgentLens，一個針對互動式程式碼代理（interactive code agents）的生產環境評估基準（production-assessed benchmark）。大多數程式碼代理基準將一次執行簡化為單一通過/失敗位元（pass/fail bit）——任務是否通過？——但真正使用這些代理的人所體驗的是整個執行軌跡（trajectory）：代理如何遵循指示、使用工具、驗證自身工作、從錯誤中恢復，以及在過程中如何與使用者對話。AgentLens 評估的正是整個執行軌跡。它結合了形式驗證（formal verification）（在存在客觀檢查之處）以及由 LLM 撰寫的軌跡評論（LLM-written trajectory reviews）與並排比較（side-by-side comparisons），使每次執行都能產生一份可讀的說明，解釋分數的由來。這使 AgentLens 不僅可用於模型排名（model ranking）：我們利用它來診斷模型行為、比較自身代理的後續版本，並在夜間評估流程（nightly evaluation pipeline）中偵測產品迴歸（product regressions）。我們將此基準以開放原始碼釋出於 https://github.com/agent-lens/agent-lens-bench。

### 核心貢獻（3～5點）
- 提出 AgentLens，一個在實際生產情境中驗證、以完整執行軌跡為評估對象的程式碼代理基準。
- 結合形式驗證與由 LLM 撰寫的軌跡評論及並排比較，讓每次執行都產生可讀的評分說明。
- 支援模型行為診斷、版本比較與夜間評估流程中的產品迴歸偵測，超越單純的模型排名。
- 以開放原始碼釋出完整基準，促進學界與業界對互動式程式碼代理評估的研究與應用。

### 適合對象
本論文適合從事 LLM 程式碼代理、程式設計輔助工具開發與評估的研究人員與工程師，以及需要建立或改善內部模型評估、夜間迴歸測試與產品品質監控流程的 AI 產品團隊閱讀。

## 深度分析

#### 方法論解析

AgentLens 的核心方法論是將「執行軌跡（trajectory）」本身視為主要評估對象，而非僅以「通過/失敗位元（pass/fail bit）」或「最終狀態結果（final-state outcome）」來總結一次互動。一條執行軌跡包含模擬使用者（simulated user）的訊息、代理的回覆、工具呼叫（tool calls）、檔案編輯、命令執行、驗證嘗試（verification attempts）、最終回應（final response）以及儲存庫狀態（repository state）。AgentLens 透過「軌跡層級評估協定（trajectory-level evaluation protocol）」同時檢驗這些元素，試圖貼近真實開發者對「程式設計輔助工具（coding assistant）」的主觀體驗。

在任務集（task set）設計上，作者釋出了一個初始 fold（任務折），包含 16 個程式碼代理情境（scenario），並圍繞真實工作流程（workflow）組織：每個情境都包含任務目標、一連串指令與互動步驟。這些工作流程來自對程式設計師的訪談，詢問他們當天或前一天實際完成的工作，以還原「檢視程式碼、編輯檔案、執行工具、從錯誤恢復」等日常動作。為了測試代理在不同互動風格下的表現，每個情境會搭配兩種使用者人格（persona）：中性的預設使用者（neutral default user）與有毒使用者（toxic user），因此每個受測代理會產生 32 條執行軌跡。這種設計雖然精簡，但作者指出其「run-to-run variance」很低，顯示少量但高品質的軌跡已足以穩定區分代理差異。

評估協定結合了兩大支柱。第一是「形式驗證（formal verification）」：在存在客觀檢查的任務中，執行測試、檢查儲存庫狀態或搜尋預期的程式碼變更。這些驗證可复用現有檢查器，也可針對特殊任務插入專屬驗證器。第二是「LLM 評審評論（LLM judge reviews）」：由 LLM 針對多個品質維度對整條軌跡打分，並撰寫文字評論說明分數背後的證據。這些維度涵蓋指令遵循（instruction following）、工具紀律（tool discipline）、驗證行為（validation behavior）、錯誤恢復（recovery from errors）、面向使用者的溝通（user-facing communication）以及最終答案與儲存庫狀態的品質。對於特定 fold（例如測試生成），也可加入任務專屬指標（如 mocking strategy）來取代一般性程式設計輔助行為指標。

為了將多維度分數整合為可比較的整體表現，AgentLens 設計了「品質指標（quality index）」，用於排行榜（leaderboard）與迴歸偵測。此外，「並排評論（side-by-side reviews）」讓評審直接比較兩條執行軌跡，這對模型比較（model comparison）、功能評估（feature evaluation）與迴歸分析（regression analysis）特別有用，因為它能凸顯單純分數無法呈現的細微差異，例如某個代理雖然最終通過測試，但過程中過度自信、未驗證即宣稱完成。

為了確保 LLM 評審的可信度，作者還進行了「可靠性檢查（reliability checks）」與「偏差檢查（bias checks）」，例如重複評審以檢驗一致性、比較不同評審模型、檢查並排比較中的位置偏差等。最後，AgentLens 被整合進一個「夜間評估流程（nightly evaluation pipeline）」，在真實開發中的程式碼代理上每日執行，以捕捉「產品迴歸（product regressions）」。整體而言，AgentLens 的方法論強調「可解釋的、以使用者感知為核心的軌跡評估」，並將評估從研究排行榜延伸到產品診斷與持續整合。

#### 實驗數據解讀

由於提供的全文片段未包含第 4 節的完整表格與數字，以下分析根據文中描述的實驗設計與結果趨勢進行推論。AgentLens 的初始 fold 規模雖小（16 個情境 × 2 個人格 = 32 條執行軌跡），但作者強調其「run-to-run variance」很低。這一點具有重要方法論意義：它意味著軌跡層級的 LLM 評審能夠在少量樣本上產生穩定訊號，而不需要像傳統基準那樣依賴數百個獨立任務。對於產品團隊而言，這使得「夜間評估流程」在計算成本與診斷價值之間取得平衡。

在排行榜（Section 4.1）方面，AgentLens 預期會呈現與傳統「通過/失敗位元」不同的排序。兩個在 SWE-bench 上表現相近的模型，可能在 AgentLens 上因為工具使用習慣、溝通風格或錯誤恢復能力而拉開差距。例如，一個模型可能經常在最終回應中過度宣稱「已修復」，但實際上只修改了部分檔案；另一個模型可能最終測試未通過，卻正確定位了 bug、安全地使用了工具，並在過程中清楚地向使用者說明進展。AgentLens 的評分機制會讓後者在某些維度上獲得較高分，從而提供更細緻的模型區分。

定性分析（Section 4.3）是 AgentLens 最具產品價值的部分。文字評審評論能夠具體指出失敗模式：例如「代理未執行測試就宣稱完成」、「在收到錯誤訊息後沒有回滾不完整的修改」、「對有毒使用者採取防禦性或敷衍的回應」、「生成的文件脫離實際程式碼庫」等。這些評論不僅告訴開發者「哪裡不好」，還說明「為什麼不好」，從而指導後續的模型或產品改進。

與公開基準的相關性研究（Section 4.4）則用來驗證 AgentLens 是否測量了新的、有價值的訊號。如果 AgentLens 的整體品質指標與 SWE-bench、Terminal-Bench 等「最終狀態結果」高度相關，則說明它至少保留了傳統任務成功度的判斷力；如果某些維度（如溝通品質、工具紀律）與傳統分數相關性低，則證明這些維度提供了額外且獨立的資訊。根據論文動機，後者應該是主要發現：「二元結果（binary outcome）」無法捕捉互動品質，而 AgentLens 正好填補這個缺口。

有毒使用者人格的實驗設計也值得期待。傳統基準通常假設使用者合作且禮貌，但真實產品中使用者可能沮喪、急躁或表達不清。AgentLens 透過有毒人格測試代理在壓力下的穩健性，這可能暴露出在一般情境下不會出現的問題，例如代理過早放棄、回應帶有情緒、或忽略隱藏在抱怨中的真正需求。

#### 與現有研究的比較

AgentLens 與現有研究的主要差異在於評估對象：它不是評估孤立的程式碼片段或最終儲存庫狀態，而是評估完整的執行軌跡。

相較於早期程式碼生成基準（如 HumanEval、MBPP）以單元測試作為「二元結果」，AgentLens 進入了儲存庫層級（repository-level）與互動式程式碼代理（interactive code agents）的範疇。與 SWE-bench 和 SWE-agent 相比，AgentLens 保留了形式驗證的客觀性，但額外加入了軌跡層級的 LLM 評審評論，因此能夠測量指令遵循、工具紀律、驗證行為、錯誤恢復與溝通品質等維度。SWE-bench 主要回答「代理是否修好了 issue」，AgentLens 則進一步回答「代理是如何與使用者一起工作的」。

在互動式工具使用基準方面，AgentBench、ToolLLM、WebArena 與 OSWorld 提供了多樣化的環境，但多數聚焦於代理與外部環境的互動，而非程式設計輔助工具與使用者之間的長期協作。τ-bench 與 AgentLens 最為接近，因為它同樣使用具有人格與隱藏目標的模擬使用者來評估工具代理互動。AgentLens 借鑑了這個想法，但將其專門應用於程式碼助理情境，並強調執行軌跡可被重複用於不同模型與品質維度的靈活比較。

Terminal-Bench 同樣評估終端環境中的代理，涵蓋軟體工程、系統管理、資安與資料科學等任務。AgentLens 與其不同之處在於「生產環境評估基準（production-assessed benchmark）」的定位：目標不只是測量任務是否完成，而是診斷使用者可見的產品品質，並支援夜間評估流程中的迴歸偵測。

在 LLM-as-judge 的傳統上，MT-Bench 與 Chatbot Arena 展示了 LLM 評審與並排比較在開放式助理評估中的可擴展性。AgentLens 的貢獻在於將這些技術應用到程式碼代理的執行軌跡，並要求評審提供書面證據。這使得評分結果不只是數字，而是可閱讀、可審查、可彙整的診斷報告。透過彙整所有軌跡的評論，AgentLens 能夠浮現最常見且最重要的失敗模式，幫助開發者優先修復問題。

然而，AgentLens 也有其限制。首先，LLM 評審可能帶有偏差，例如對回應長度、措辭風格或模型自身輸出的偏好。其次，16 個情境與兩種人格雖然穩定，但覆蓋範圍仍有限，未必能代表所有開發者日常工作。第三，模擬使用者畢竟是由 LLM 生成，可能無法完全重現真實人類的意圖變化、情緒波動與領域知識。第四，形式驗證僅適用於存在客觀檢查的任務，對於撰寫文件、重構程式碼等開放式任務，評估仍高度依賴 LLM 評審的主觀判斷。

#### 可重現性評估

AgentLens 在可重現性方面採取了積極的開源策略：論文釋出了基準程式碼，存放於 GitHub（https://github.com/agent-lens/agent-lens-bench）。程式碼應包含任務描述、驗證設定、可用驗證器（Table 1 所列）以及執行軌跡的收集與評審流程。對於希望複現排行榜或建立自家夜間評估流程的研究者與工程團隊而言，這是重要基礎。

不過，可重現性仍受到幾個因素影響。首先是評審模型：AgentLens 的 LLM 評審評論與並排評論依賴外部 LLM（很可能是 GPT-4 等級的模型）。若論文未明確指定模型版本、溫度（temperature）、提示詞（prompt）與取樣參數，不同實驗室復現時可能得到略有差異的分數。其次，模擬使用者與 LLM 評審都具有隨機性，因此需要設定固定亂數種子或進行多次重複評審，並報告變異範圍。文中提到已進行可靠性檢查，這有助於提升可信度，但釋出原始評審提示詞與重複評審的原始數據會更有幫助。

第三，任務環境（如儲存庫狀態、相依套件版本、容器設定）必須被妥善封裝，否則不同執行環境可能導致形式驗證結果不一致。若 AgentLens 提供 Docker 映像檔或詳細的環境設定檔，則可大幅改善這方面的可重現性。第四，雖然程式碼開源，但「資料集」——即 16 個情境的詳細任務描述、使用者人格定義與預期互動腳本——是否完整釋出，也會影響他人能否直接執行相同評估。

整體而言，AgentLens 的可重現性屬於中上水準：開源程式碼與明確的評估協定提供了良好起點，但實際分數仍會受到評審模型版本與隨機性的影響。建議作者進一步釋出：（1）完整的評審提示詞與模型版本；（2）樣本執行軌跡與對應評論；（3）人類專家標註的子集，供社群校準 LLM 評審；（4）容器化執行環境。這些措施將使 AgentLens 成為更穩健的社群標準。

#### 未來研究方向

AgentLens 開啟了多個值得後續探索的研究方向：

1. **擴大任務集與人格多樣性**：目前的 16 個情境與兩種人格雖已能穩定區分模型，但未來可增加更多日常工作流程（如程式碼審查、API 設計、效能調校、資安修補）以及更多元的人格（新手開發者、資深架構師、非英語母語者、高度注重安全的使用者），以提升基準的代表性。

2. **結合真實使用者資料**：模擬使用者雖然可控，但真實開發者的行為更複雜。未來可從經同意的產品日誌中抽取互動模式，用於校準模擬使用者與驗證 LLM 評審的判斷，縮小模擬與真實部署之間的差距。

3. **開發專用且開源的評審模型**：目前依賴通用 LLM 作為評審，成本高且版本變動會影響可重現性。未來可基於大量軌跡評論資料，訓練專門用於程式碼代理評估的開源 judge 模型，並針對偏差進行校正。

4. **將評論轉化為訓練訊號**：AgentLens 產生的多維度評分與文字評論可作為 RLHF 或 DPO 的回饋來源，直接改善代理的工具紀律、驗證行為、錯誤恢復與溝通風格，形成「評估—診斷—改進」的閉環。

5. **自動化迴歸根因分析**：目前的夜間評估流程可進一步結合評論文字的叢集分析，自動將產品迴歸連結到特定程式碼提交或模型更新，並優先排序最需要修復的失敗模式。

6. **長期與多會話評估**：真實程式設計輔助工具往往與使用者進行多輪、跨檔案、跨會話的協作。未來可將 AgentLens 擴展到多會話軌跡，評估代理的長期記憶、上下文一致性與持續學習能力。

7. **跨領域延伸**：除了傳統軟體工程，AgentLens 的軌跡評估框架也可應用於資料科學、DevOps、雲端維運、UI/UX 開發等領域，成為通用的互動式代理評估方法。

8. **對抗與安全評估**：有毒使用者人格只是第一步。未來可設計更具對抗性的測試，例如提示注入（prompt injection）、誘導代理執行危險命令、或測試代理在面對不當要求時的拒絕與恢復能力。

9. **形式驗證與 LLM 評分的加權整合**：目前兩者互補，但未來可基於人類偏好資料學習最佳加權方式，使「品質指標（quality index）」更貼近真實使用者對一次互動的整體滿意度。

10. **即時生產評估**：將 AgentLens 從夜間批次評估進化為即時或近即時的生產監控系統，結合使用者回饋與 A/B 測試，持續追蹤程式設計輔助工具的實際表現與使用者體驗。

## 論文問答

**Q1：AgentLens 想要解決什麼問題？**

A：現有的程式碼代理基準大多把一次執行簡化成單一的通過／失敗位元，無法反映開發者實際使用時感受到的完整互動品質。對於像撰寫專案文件這類沒有自然二元結果的任務，只看最終狀態尤其不足，因為重點在於內容是否準確、範圍適當、可讀且符合實際程式碼。AgentLens 因此把「執行軌跡」當作主要評估對象，以更接近使用者感知的方式衡量代理表現。

**Q2：為什麼單一二元結果不足以評估程式設計輔助工具？**

A：一次執行可能通過了狹隘的檢查，卻仍然不可靠、過度自信，或與使用者真正需求微妙錯位；相反地，失敗的執行過程中也可能正確定位問題、安全使用工具並優雅地從錯誤中恢復。對於文件撰寫等任務，有意義的問題不是檔案是否出現在磁碟上，而是文件是否準確、範圍適中、易讀且扎根於實際儲存庫。因此，僅憑二元結果會遺漏大量影響使用者體驗的關鍵細節。

**Q3：軌跡層級評估對生產環境中的程式碼代理為何重要？**

A：開發者每天與程式設計輔助工具互動時，經歷的是整段對話與工具使用過程，而不只是最後的輸出結果。執行軌跡完整記錄了使用者訊息、代理回覆、工具呼叫、檔案編輯、驗證嘗試、錯誤恢復與最終回應，能夠呈現代理如何遵循指令與溝通。AgentLens 透過評估這份完整記錄，使評量方式更貼近真實使用者對產品品質的感知。

**Q4：AgentLens 的核心評估協定是什麼？**

A：AgentLens 將完整執行軌跡視為主要評估對象，並結合形式驗證與 LLM 評審評論兩種機制。形式驗證負責客觀可自動檢查的項目，例如測試是否通過或儲存庫狀態是否符合預期；LLM 評審則針對指令遵循、工具紀律、驗證行為與溝通品質等維度撰寫文字評論。每次執行都會產生可讀的評分說明，讓開發者理解分數背後的原因。

**Q5：與既有程式碼代理基準相比，AgentLens 的關鍵創新在哪裡？**

A：SWE-bench 等基準主要衡量最終狀態的任務解決能力，AgentLens 則保留形式驗證，並額外加入軌跡層級的評論，以捕捉指令遵循、工具使用、自行驗證、錯誤恢復與使用者溝通等面向。此外，它借鏡 τ-bench 的概念，使用帶有人設與目標的模擬使用者來產生互動情境。這使得評估不只看代理是否完成任務，還看它在整段對話中如何與使用者協作。

**Q6：AgentLens 在任務集設計上有哪些重要選擇？**

A：初始釋出的任務集包含 16 個程式設計情境，每個情境分別以中性預設使用者與有毒使用者兩種人設執行，因此每個受測代理會產生 32 條執行軌跡。這些工作流程來自對程式設計師的訪談，記錄他們日常實際進行的工作步驟。任務集刻意保持精簡，以便在生產環境中頻繁執行，同時透過可重複使用的驗證器與可擴充的評審指標來維持彈性。

**Q7：AgentLens 如何進行模型比較？**

A：AgentLens 會產生排行榜，透過品質指標與各維度分數對模型進行排名，並提供並排評論讓開發者直接比較兩個代理在相同任務上的行為差異。論文報告的執行間變異很低，顯示這個精簡設定具有穩定性。此外，作者也進行了與公開基準的相關性研究，以定位 AgentLens 分數在既有評估體系中的意義。

**Q8：AgentLens 的主要實驗結果與發現是什麼？**

A：實驗顯示，AgentLens 能夠區分模型不僅在於最終通過與否，還在於它們如何遵循指令、使用工具、驗證工作以及與使用者溝通。文字評論能夠揭露最常見且最重要的失敗模式，例如工具使用不當或驗證不完整。夜間評估流程也成功偵測到產品迴歸，證明這套方法在實際開發循環中具有診斷價值。

**Q9：AgentLens 是否有可靠性或偏差相關的研究？**

A：論文納入了針對 LLM 評審評論的可靠性檢查與偏差檢查，以確保評分結果穩定且盡量不受評審模型偏好影響。低執行間變異進一步支持這個精簡設定的穩健性。這些檢查非常重要，因為 LLM 作為評審可能產生位置偏差、長度偏差或風格偏差，需要透過控制比較與重複抽樣來驗證。

**Q10：AgentLens 可應用在哪些實務情境？**

A：AgentLens 可用於診斷模型行為、比較同一代理的連續版本、評估新功能，以及透過夜間評估流程捕捉產品迴歸。可讀的評論讓開發者能快速定位問題根源，例如是工具使用不當、驗證不足，還是溝通風格不佳。這使它不只是學術排行榜工具，更是能融入產品開發週期的評估基準。

**Q11：AgentLens 如何處理使用者人設等產品面向？**

A：AgentLens 使用由 LLM 扮演的模擬使用者，並根據人設與任務目標產生互動，其中包括中性預設使用者與有毒使用者兩種版本。這種設計能夠測試代理在不同溝通風格下的反應，例如面對不耐煩或挑釁的使用者時是否仍保持協助與尊重。軌跡層級評論會記錄代理在這些情境下的互動品質，幫助產品團隊評估真實使用者體驗。

**Q12：AgentLens 對整個領域可能帶來什麼影響？**

A：AgentLens 將程式碼代理評估從最終狀態的二元指標，轉向以使用者為中心的執行軌跡品質，促使研究者更重視代理的可靠性、溝通能力與錯誤恢復行為。開源釋出讓社群能夠採用並擴展這套方法。它也為其他領域的生產環境評估基準提供了一個可參考的範本。

**Q13：AgentLens 有哪些已承認的限制？**

A：初始釋出的任務集僅有 16 個情境、32 條軌跡，雖然穩定但覆蓋的程式設計工作流程仍有限。此外，並非所有任務都有客觀的形式驗證，部分維度必須依賴 LLM 評審的主觀判斷。這表示在推廣到更廣泛任務類型與程式語言時，仍需持續擴充與驗證。

**Q14：AgentLens 可能遺漏或難以處理哪些失敗案例？**

A：對於缺乏明確客觀檢查的任務，評估高度仰賴 LLM 評審的意見，可能遺漏細微的正確性問題。模擬使用者雖然能重現部分互動風格，但無法涵蓋真實世界中所有使用者行為與領域知識。此外，精簡的軌跡長度可能不足以暴露需要長期規劃或多輪協調的失敗模式。

**Q15：AgentLens 未來可以朝哪些方向發展？**

A：未來可以擴充任務集以涵蓋更多工作流程、程式語言與框架，並進一步校正 LLM 評審的偏差。引入人類參與的驗證迴路，以及根據評論自動生成修復建議，也是值得探索的方向。夜間評估流程的概念也可推廣到其他代理應用領域，讓軌跡層級評估成為產品開發的常態工具。

## 實務應用指南

### 適用場景

1. **程式設計輔助工具的夜間迴歸偵測**  
   若團隊已在開發或維護一款互動式程式碼代理，可將 AgentLens 納入夜間評估流程，每日比較新舊版本的執行軌跡，及早發現工具呼叫異常、驗證嘗試減少或對使用者語氣變差等產品迴歸。

2. **模型選型與版本迭代比較**  
   在評估要導入哪個基礎模型或微調版本時，除了看公開基準的通過/失敗位元，也可利用 AgentLens 的並排評論，比較不同模型在相同任務集上的指令遵循、溝通風格與錯誤恢復能力。

3. **新任務或新功能的品質把關**  
   當產品新增「自動產生專案文件」、「重構程式碼」或「輔助除錯」等功能時，可為該功能設計專屬的執行軌跡評量維度，透過 LLM 評審評論確認輸出品質，而不只是檢查檔案是否生成。

4. **使用者體驗與互動品質診斷**  
   產品或 UX 團隊可透過文字評審評論，理解代理在真實對話中是否過度自信、忽略使用者提示、或未適當驗證就宣稱完成，作為改進互動設計的依據。

5. **教育或培訓場景的程式碼代理評量**  
   在教學輔助工具中，可用 AgentLens 評估代理是否引導學生理解問題、是否給出安全且可驗證的建議，並追蹤其在多輪對話中的表現。

---

### 實作前置條件

**資料準備**
- 真實或模擬的程式碼儲存庫：任務應貼近開發者日常工作，建議從團隊實際遇到的 workflow 訪談開始收集。
- 任務描述與模擬使用者設定：每個任務需有清楚的目標、指令步驟，以及至少一個模擬使用者 persona（如中性使用者與挑戰性使用者）。
- 形式驗證規則：針對可客觀檢查的項目，預先定義測試、儲存庫狀態檢查或預期程式碼變更。

**運算資源**
- 可執行代理並記錄完整執行軌跡的環境（容器或沙箱）。
- 足夠呼叫 LLM 評審的 API 額度：每個軌跡會產生多次評論與並排比較，成本隨任務數與模型規模增加。
- 排程工具（如 cron、GitHub Actions、Airflow）以支援夜間評估流程自動化。

**技能需求**
- 熟悉程式碼代理的運作方式（工具呼叫、檔案編輯、命令執行）。
- 具備設計評量維度與撰寫評審提示詞的能力。
- 基礎資料分析能力：能彙整評論、計算品質指標，並從中歸納常見失敗模式。

---

### 實作步驟建議

1. **從小規模任務集開始**  
   參考 AgentLens 的 16 個情境，挑選 3–5 個與自身產品最相關的 workflow，先建立任務描述與模擬使用者 persona。

2. **建立形式驗證與軌跡記錄**  
   為每個任務設定可自動檢查的驗證器（如測試通過、檔案存在、特定程式碼變更），並確保代理執行時完整記錄訊息、工具呼叫、驗證嘗試與最終回應。

3. **設計 LLM 評審維度與提示詞**  
   根據產品關注的品質面向（如指令遵循、工具紀律、驗證行為、錯誤恢復、溝通風格）設計評分維度，並要求評審同時產生文字評論說明給分依據。

4. **執行首次評估並校正偏差**  
   先以少量軌跡測試評審穩定性，進行可靠性檢查與偏差檢查，必要時調整提示詞或改用不同評審模型交叉驗證。

5. **建立並排比較與品質指標儀表板**  
   將每次執行結果彙整為品質指標，並提供並排評論功能，方便比較不同模型版本或功能開發前後的差異。

6. **整合至夜間評估流程**  
   將上述步驟自動化，每日或每次合併程式碼後執行，並設定告警機制，當品質指標顯著下降時通知相關團隊。

---

### 潛在風險與注意事項

- **LLM 評審的偏差與不穩定性**  
  評審模型可能偏好特定回答長度、語氣或格式。建議定期進行偏差檢查，並以人類標註樣本校正評分標準。

- **過度依賴形式驗證而忽略互動品質**  
  即使任務通過測試，仍可能出現溝通不佳、過度自信或忽略使用者指令的問題。應將軌跡層級評估與形式驗證並重。

- **任務設計偏離真實使用情境**  
  若任務集過於簡化或與日常工作脫節，評估結果將難以反映產品實際表現。建議持續從真實使用者訪談中更新任務。

- **成本隨規模快速上升**  
  每個軌跡都需要多次 LLM 評論與比較，擴充任務集時需預估 API 費用，並考慮對高優先任務優先評估。

- **模擬使用者無法完全代表真實使用者**  
  模擬使用者的行為由 LLM 產生，可能與真實開發者的反應不同。應將 AgentLens 結果與真實使用者回饋相互參照。

---

### 與其他技術的整合建議

- **與 CI/CD 管線整合**  
  將 AgentLens 作為合併前的品質閘道，與單元測試、整合測試並行執行，特別適合驗證程式設計輔助工具的新版本。

- **與現有公開基準互補使用**  
  AgentLens 不應取代 SWE-bench、Terminal-Bench 等公開基準，而是作為補充：公開基準提供可橫向比較的通過/失敗位元，AgentLens 提供軌跡層級的品質診斷。

- **與可觀測性平台串接**  
  將執行軌跡與評審評論匯入日誌或追蹤系統（如 LangSmith、Weights & Biases），方便團隊回溯特定失敗案例。

- **與人類回饋迴路結合**  
  將 AgentLens 發現的高頻失敗模式轉化為產品待辦項目，並在真實使用者測試後驗證這些問題是否確實影響體驗。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先從摘要與第 1 節讀起，理解「為什麼不能只靠通過/失敗位元評估程式碼代理」，再瀏覽第 3 節的任務設計與評估流程，最後看第 4 節的排行榜與質性分析，建立對軌跡評估的直覺。

**AI 工程師**  
重點閱讀第 3 節的軌跡層級評估協定、品質指標計算方式、可靠性檢查與偏差檢查，並參考開源實作了解如何將 AgentLens 整合進現有代理系統與夜間評估流程。

**研究人員**  
建議深入第 2 節的相關工作比較，以及第 4.4 節與公開基準的相關性研究，思考軌跡評估方法對現有程式碼代理基準研究的補充與挑戰，並關注第 5–6 節的未來研究方向。

**產品經理**  
可聚焦第 1 節的使用者體驗論點、第 3.1 節的任務來源與模擬使用者設計，以及第 4.3 節的質性分析，這些內容有助於將技術評估轉化為可執行的產品改進與優先順序決策。
