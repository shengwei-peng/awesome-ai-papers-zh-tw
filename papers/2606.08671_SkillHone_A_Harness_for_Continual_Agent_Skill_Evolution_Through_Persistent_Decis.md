# SkillHone：透過持久性決策歷史實現智能體技能持續演化的框架

**原文標題：** SkillHone: A Harness for Continual Agent Skill Evolution Through Persistent Decision History  
**作者：** Zhiwei Li、Yong Hu  
**發布日期：** 2026-06-23  
**HF 連結：** [https://huggingface.co/papers/2606.08671](https://huggingface.co/papers/2606.08671)  
**arXiv：** [https://arxiv.org/abs/2606.08671](https://arxiv.org/abs/2606.08671)  

---

## ⚡ TL;DR

現有方法僅保留最終技能產出物，丟棄決策歷史，導致後續智能體難以持續維護與演化。
本文提出 SkillHone 框架，建立持久化決策歷史，並以角色分離子智能體持續演進技能。
在深度研究基準中，SkillHone 超越商業智能體及既有方法，內部場景準確率提升 18.8 分。

## 摘要翻譯

智能體技能（Agent skills）透過任務特定程序（task-specific procedures）、腳本（scripts）與參考資料（references）擴展語言模型智能體（language-model agents）的能力，但其目標任務與環境持續變動。現有方法在有限次執行（bounded runs）中改進技能，且僅保留最終產出物（artifact），捨棄了後續智能體在詮釋先前修訂（revisions）、評估（evaluations）與被拒絕的替代方案（rejected alternatives）時所需的決策歷史（decision history）。我們提出 SkillHone，一個以持久性決策歷史（persistent decision history）為基礎的智能體技能持續演化（continual agent skill evolution）框架（harness）。SkillHone 將技能修訂（skill revisions）與提供實踐反饋（practice feedback）的評估端證據（evaluation-side evidence）相結合，記錄包含診斷（diagnoses）、修訂（revisions）、證據（evidence）與結果（outcomes）的結構化歷史。角色分離子智能體（Role-separated subagents）在實踐探針（practice probes）上執行候選技能（candidate skills）並生成刪減報告（redacted reporting），同時參考先前決策提出修訂，無需重新發現過往理據，即可實現跨工作階段精煉（cross-session refinement）。在深度研究基準測試（deep-research benchmarks）中，SkillHone 無需預整合搜尋堆疊（pre-integrated search stack）即可運行，在 GAIA 上優於具商業後援（commercially backed）的深度研究智能體（deep-research agent）15.8 分，在 WebWalkerQA-EN 上優於其 3.2 分，同時也超越先前的技能演化方法。我們進一步將 SkillHone 部署於內部工具媒介分析情境（internal tool-mediated analysis scenarios），在七個設定中平均提升準確率（accuracy）18.8 分。

### 核心貢獻（3～5點）
- 提出以持久性決策歷史為基礎的持續技能演化框架 SkillHone，解決現有方法僅保留最終產出物而丟失決策脈絡的問題。
- 透過角色分離子智能體與刪減報告機制，實現跨工作階段的技能精煉，避免重複發掘過往理據。
- 在無需預整合搜尋堆疊的條件下，於 GAIA 與 WebWalkerQA-EN 等深度研究基準測試上超越具商業後援的深度研究智能體。
- 在企業內部工具媒介分析情境中驗證實用性，平均提升準確率達 18.8 分。

### 適合對象
從事語言模型智能體與自動化技能最佳化研究的研究者，以及需要於企業內部部署持續演進之工具使用技能的系統開發者與 AI 工程師。

## 深度分析

#### 方法論解析

SkillHone 的核心貢獻在於將「以產出物為中心（artifact-centered view）」的技能開發範式，轉向「以決策歷史（decision history）為核心」的持續維護（continual maintenance）範式。傳統方法如 Skill-Creator（Skill-Creator）或 Hermes-Agent-Self-Evolution（Hermes-Agent-Self-Evolution (Hermes-SE)）透過 GEPA（GEPA）進行迭代變異（iterative mutation）、評估與選擇（selection），最終僅保留最終產出物（artifact），導致後續智能體無法追溯先前的診斷（diagnoses）、被拒絕的替代方案（rejected alternatives）或評估端證據（evaluation-side evidence）。SkillHone 透過以下機制解決此問題：

**雙庫分離與角色隔離架構**
SkillHone 維護兩個連結的儲存庫：skill repository（技能庫）儲存可載入套件（loadable bundle），即包含任務特定程序（task-specific procedures）、腳本（scripts）、參考資料（references）與輸出慣例（output conventions）的技能套件（skill bundle）；skill-evaluation repository（技能評估庫）則存放實踐探針（practice probes）、驗證器（validators）、迴歸測試集、執行軌跡與刪減報告（redacted reports）。此設計確保 optimization side（最佳化端）與 evaluation side（評估端）的嚴格分離：Evaluation Agent Team（評估智能體團隊）可檢視未刪減的探針目標與軌跡，但僅能輸出結構化的 redacted reports（刪減報告）；Optimization Agent Team（最佳化智能體團隊）則依據這些報告與 persistent decision history（持久性決策歷史）進行診斷與修訂，卻無法直接接觸探針答案或驗證邏輯，從而避免實踐反饋（practice feedback）淪為記憶化目標。

**持久性決策歷史的結構化記錄**
每一次開發步驟皆透過 agent runtime（智能體執行環境）動態派遣角色分離子智能體（role-separated subagents）。歷史記錄並非單純的日誌，而是包含四元結構的決策脈絡：diagnoses（診斷）說明失效模式（failure mode）、skill revisions（技能修訂）記錄候選技能（candidate skills）的變更、evaluation-side evidence（評估端證據）載明使用了哪些探針與報告、以及 outcomes（結果）記錄接受或拒絕的理由。這些記錄以類似 Wiki、Issue、Branch、Pull Request、Merge 的形式沉澱，使跨工作階段精煉（cross-session refinement）得以在不重新推導過去理由的情況下接續進行。

**持續演化流程**
在每一輪迭代中，Explorer 與 Diagnoser 分析 redacted reports（刪減報告）與過往決策歷史以定位 failure mode（失效模式）；Proposer 提出具類型標註的修訂；Evaluator 則在隔離環境中執行 candidate skills（候選技能）並產出新的刪減報告。此循環確保即使面臨 API changes（API 變更）、rate limits（速率限制）或 deprecations（廢棄）等環境漂移，後續智能體仍能透過歷史記錄理解「為何當初採用某項修復」，從而避免重新引入 obsolete fixes（過時修復）。

#### 實驗數據解讀

論文在兩類情境下驗證 SkillHone（SkillHone）：公開深度研究基準測試（deep-research benchmarks）與內部工具媒介分析情境（internal tool-mediated analysis scenarios）。

**公開基準測試表現**
在原始開放網路設定（raw open-web setting）下，SkillHone 未使用任何預整合搜尋堆疊（pre-integrated search stack），僅憑藉演化後的 skill bundle（技能套件）進行檢索（retrieval）與推理。在固定評估時骨幹模型（fixed evaluation-time backbone）下，其於 GAIA（GAIA）上較具商業檢索（commercial retrieval）後援的 deep-research agent（深度研究智能體）提升 15.8 分，於 WebWalkerQA-EN（WebWalkerQA-EN）提升 3.2 分。值得注意的是，15.8 分的差距顯示在需要多步推理與開放網路資訊整合的任務上，persistent decision history（持久性決策歷史）所累積的 task-specific procedures（任務特定程序）遠優於通用商業檢索的「即時生成」策略；而 WebWalkerQA-EN（WebWalkerQA-EN）上相對較小的 3.2 分領先，可能反映網頁導航任務的 failure mode（失效模式）較為集中，商業智能體已具備強勁基線，但 SkillHone 仍能透過結構化 diagnoses（診斷）進一步邊際改進。

**跨骨幹模型遷移**
實驗將訓練階段產出的 skill bundle（技能套件）直接遷移至 Claude Sonnet 4.6（Claude Sonnet 4.6）作為 execution backbone（執行骨幹模型），無需額外最佳化即可維持效能增益。這項結果至關重要：它證明 SkillHone 的改進來自 skill procedure（任務特定程序）本身的品質提升，而非對單一語言模型的過度擬合。換言之，persistent decision history（持久性決策歷史）提煉的是任務知識，而非模型特定的提示工程。

**內部部署情境**
在七個反覆出現的 internal tool-mediated analysis scenarios（內部工具媒介分析情境）中，SkillHone 平均提升 accuracy（準確率）18.8 分。這類情境通常涉及 tool-use skills（工具使用技能）與企業內部 API，其錯誤模式往往具有領域特殊性且隨時間演化。18.8 分的平均增幅顯示，即使在缺乏大規模公開探針的封閉環境中，透過持續累積 practice feedback（實踐反饋）與修訂歷史，仍能顯著強化智能體技能的穩健性。

#### 與現有研究的比較

**相對於 Skill-Creator 與 GEPA 風格方法**
現有技能建構方法如 Skill-Creator（Skill-Creator）屬於一次性生成，將任務描述轉為可載入技能（loadable skill）後即交付後續工作階段，完全不保留決策脈絡。Hermes-SE（Hermes-Agent-Self-Evolution (Hermes-SE)）等基於 GEPA（GEPA）的反思式最佳化（reflective optimization）方法雖引入 iterative mutation（迭代變異）與 selection（選擇），但仍屬有限次執行（bounded runs），最終僅輸出單一最佳化產出物。SkillHone 與其根本差異在於：它將每一次修訂與評估都視為具有決策意義的紀錄，透過 persistent decision history（持久性決策歷史）使 skill evolution（技能演化）成為開放式、跨工作階段的過程，而非封閉的 optimization run（最佳化執行）。

**相對於商業深度研究智能體**
商業 deep-research agent（深度研究智能體）通常依賴強大的 commercial retrieval（商業檢索）與預先建置的搜尋架構。SkillHone 在無 pre-integrated search stack（預整合搜尋堆疊）的劣勢條件下，仍於 GAIA（GAIA）與 WebWalkerQA-EN（WebWalkerQA-EN）雙雙超越該商業系統。這暗示：對於深度研究任務，結構化的 skill revisions（技能修訂）與累積的 evaluation-side evidence（評估端證據）所帶來的「策略性知識」，可能彌補甚至超越單純的檢索廣度。

**潛在限制與挑戰**
儘管角色分離確保了資訊隔離，redacted reporting（刪減報告）的粒度成為效能瓶頸：過度刪減可能使最佳化端難以精準診斷 failure mode（失效模式），而刪減不足則有記憶化探針答案的風險。此外，隨著決策歷史增長，歷史檢索與摘要的運算成本將持續累積，論文雖未詳述歷史壓縮機制，但這是長期部署的隱憂。最後，SkillHone 目前聚焦於單一 skill bundle（技能套件）的演化，對於多技能間的依賴關係與聯合最佳化仍待擴展。

#### 可重現性評估

就公開資源而言，論文引用的對照方法如 Skill-Creator（Skill-Creator）與 Hermes-Agent-Self-Evolution（Hermes-Agent-Self-Evolution (Hermes-SE)）已提供 GitHub 連結，但 SkillHone（SkillHone）本身的原始碼、模型權重或完整系統映像檔在提供的文本中並未明確宣告開源。這對社群重現構成一定障礙：雖然架構圖（Figure 2）與附錄 E 的派遣模式（dispatch patterns）提供了高階實作藍圖，但諸如 redacted reporting（刪減報告）的具體啟發式規則、子智能體的系統提示設計、以及技能庫與評估庫的儲存格式等關鍵細節，仍需依賴原始論文未公開的實作參數。

在資料集層面，GAIA（GAIA）與 WebWalkerQA-EN（WebWalkerQA-EN）為公開基準測試，具備可取得性；internal tool-mediated analysis scenarios（內部工具媒介分析情境）則屬企業內部資料，外部研究者無法直接複現。模型層面，論文使用 API 導向的 backbone（骨幹模型），未涉及開源權重釋出，因此重現門檻主要取決於 API 呼叫成本與 role-separated subagents（角色分離子智能體）的調度實作。整體而言，方法論層次的重現可行，但系統層次的精確復刻需等待作者群釋出程式碼。

#### 未來研究方向

**歷史壓縮與長期記憶管理**
隨著技能生命週期拉長，persistent decision history（持久性決策歷史）的規模將成指數增長。未來研究可探索分層式摘要或向量化歷史檢索，使後續智能體能在不遺失關鍵決策脈絡的前提下，有效處理數千次迭代累積的 diagnoses（診斷）與 revisions（修訂）。

**自動化探針與驗證器生成**
當前技能評估庫依賴人工或預先準備的 practice probes（實踐探針）與 validators（驗證器）。若結合對抗式生成或覆蓋率導向的合成方法，自動產生能暴露新 failure mode（失效模式）的探針，將可進一步降低人工維護成本，並提升 skill evolution（技能演化）的自主程度。

**多技能聯合演化與依賴管理**
現有框架聚焦單一 skill bundle（技能套件）的改進。實際部署中，智能體往往同時載入多項 tool-use skills（工具使用技能），彼此間存在呼叫依賴與版本衝突。未來可擴展 SkillHone 以支援多技能間的聯合診斷與介面相容性演化，並記錄跨技能的決策歷史。

**人機協同的決策歷史策展**
儘管 SkillHone 強調自動化，但在高風險領域中，人類專家可能希望審查或修正歷史中的錯誤診斷。設計可解釋的歷史視覺化介面，並允許人類標註「錯誤拒絕」或「過時脈絡」，將有助於結合人類領域知識與自動化 continual maintenance（持續維護）。

**動態環境適應的理論保證**
論文以 API changes（API 變更）與 deprecations（廢棄）為動機，但未提供在環境非穩態下的收斂或無迴歸保證。未來可建立形式化框架，分析在決策歷史輔助下，skill revisions（技能修訂）於動態環境中的長期穩定性邊界。

## 論文問答

**Q1：SkillHone 旨在解決智能體技能生命週期中的哪個核心問題？**
A：SkillHone 主要解決智能體技能必須持續演化的挑戰，因為目標任務與外部環境會隨時間不斷變動，而現有方法多將技能開發視為有限次執行的單次最佳化過程，最終僅保留靜態的產出物。這種以產出物為中心的觀點忽略了長期維護所需的決策脈絡，導致後續智能體無法理解先前的技能修訂動機與評估端證據。透過建立持久性決策歷史，SkillHone 讓後來的智能體能夠在既有基礎上繼續改進，而無需從頭重新推導過往的判斷依據。

**Q2：為何現有的 Skill-Creator 或 Hermes-SE 等方法無法滿足持續演化的需求？**
A：Skill-Creator 與 Hermes-Agent-Self-Evolution（Hermes-SE）這類方法雖然能將任務描述轉換為可載入技能，或透過迭代變異與反思式最佳化來改進技能套件，但它們本質上仍屬於單次最佳化執行，僅保留最終產出物。這些方法缺乏對診斷、被拒絕的替代方案以及評估端證據的結構化記錄，使得後續智能體繼承技能時，無法得知過去的失效模式與修訂理由。因此，當環境出現 API 變更、速率限制或廢棄等情況時，後期的最佳化過程很可能重複已經過時的修復，或重新發現先前已被排除的替代方案。

**Q3：持久性決策歷史對於智能體技能的長期維護為何至關重要？**
A：持久性決策歷史記錄了每一次技能修訂背後的診斷、候選修訂內容、實踐反饋證據與最終結果，使後來的智能體能夠精確回溯先前的決策脈絡。在實際部署中，失效模式會隨著時間改變，例如外部 API 變更或速率限制調整，過去有效的修復未必適用於當前問題，若無歷史記錄，智能體容易重新引入過時修復。SkillHone 透過連結診斷、修訂、證據與結果的結構化歷史，實現跨工作階段精煉，確保技能演化是一個可累積、可審查的持續過程。

**Q4：SkillHone 的核心方法架構為何？它如何管理技能演化流程？**
A：SkillHone 作為一個支撐持續演化的框架，維護兩個相互連結的倉庫：儲存可載入套件的技能倉庫，以及存放實踐探針、驗證器、執行軌跡與刪減報告的技能評估倉庫。在每次開發步驟中，智能體執行環境會動態分派具有明確權限邊界的角色分離子智能體，分別負責最佳化端（提出診斷與修訂）與評估端（執行候選技能並產出刪減報告）。這些互動所產生的診斷、技能修訂、評估端證據與結果會被記錄下來，形成可供後續重複利用的持久性決策歷史。

**Q5：相較於傳統最佳化，SkillHone 的關鍵創新是什麼？**
A：SkillHone 的關鍵創新在於從「以產出物為中心」轉向「以決策歷史為中心」的技能演化範式，將每一次技能修訂與其對應的評估端證據視為具有決策意義的紀錄，而非僅是產出更好的技能套件。它透過結構化地保存診斷、修訂、證據與結果，讓後來的智能體能夠繼承並理解先前的決策脈絡，避免在跨工作階段精煉時重複過去的錯誤。這種設計使得技能演化不再是一連串孤立的有限次執行，而是一個持續累積實踐反饋與決策知識的長期過程。

**Q6：SkillHone 為何採用角色分離子智能體與刪減報告的設計？**

A：SkillHone 假設底層的智能體執行環境必須支援啟動具有明確權限分離的範圍分派，並非所有現有框架都能直接滿足此需求。同時，系統需要同時維護技能倉庫與技能評估倉庫，並產生具備足夠診斷價值的刪減報告，這在初期設置與評估資產管理上會帶來額外負擔。因此，採用較簡易智能體基礎設施的團隊，可能需要先投入資源進行執行環境的客製化，才能完整發揮 SkillHone 角色分離與歷史保存的優勢。

## 實務應用指南

### 適用場景

1. **開放網路深度研究（Deep Research）**：針對無預整合搜尋堆疊的原始開放網路環境，研究團隊可利用 SkillHone 持續迭代「檢索—綜合—引用」技能。例如財經分析部門讓智能體在 GAIA 等級的複雜查詢中，不斷根據評估端證據修正搜尋策略與輸出慣例，最終產出可跨骨幹模型轉移的高品質研究技能套件。

2. **內部工具媒介分析**：企業內部反覆出現的資料分析、資安排查或財務稽核任務，通常透過特定內部工具（如專屬資料庫查詢介面、BI 平台 API）執行。SkillHone 可將這些工具使用技能（tool-use skills）作為持續演化標的，透過實踐探針與驗證器回饋，平均提升 18.8 點準確率，並保留每次診斷與修訂的決策歷史供後續維護。

3. **長期維護的業務流程自動化**：當技能所依賴的外部 API 發生速率限制變更、介面廢棄或回傳格式異動時，傳統一次性最佳化產出的技能會迅速過時。SkillHone 適合用於客服、供應鏈追蹤或法規申報等生命週期長的場景，讓後續智能體透過持久性決策歷史理解「當初為何這樣修復」，避免重新引入已失效的舊修補。

4. **跨團隊知識傳承與合規審計**：在受監管產業（如金融、醫療）中，技能修訂必須具備可審計的決策脈絡。SkillHone 的結構化歷史（診斷、修訂、證據、結果）可直接對應至企業的變更管理流程，使新進工程師或接替的智能體都能追溯每一版技能背後的失效模式與評估依據，無需重新推導。

### 實作前置條件

**資料層面**：需準備初始技能套件（包含指令、程序、腳本、參考資料與輸出慣例）作為 S₀；建置技能評估倉庫，內含實踐探針（practice probes）、oracle targets、驗證器（validators）、回歸測試集與執行軌跡（traces）；並規劃持久性決策歷史的儲存結構（如 Wiki、Issue、Branch、PR、Merge 紀錄）。

**運算層面**：需具備可動態派發角色分離子智能體（role-bounded dispatches）的運行環境（agent runtime），例如 Claude Code、Codex、Hermes 或自研框架；足夠的 LLM API 配額與運算資源以支撐多次「診斷—修訂—評估」循環；以及隔離的執行沙箱，確保評估端能在不暴露未刪減資訊的前提下執行探針。

**技能與流程層面**：團隊需具備設計初始技能指令與輸出慣例的能力；需有人定義刪減報告（redacted reporting）的規則與分級政策，防止評估端機密外洩或優化端資訊不足；並需熟悉 Git 式分支合併流程，因為 SkillHone 以 Issue、Branch、PR、Merge 作為決策歷史的原子操作單位。

### 實作步驟建議

1. **初始化雙倉庫**：建立 Skill Repository（存放 SKILL.md、Scripts、References、Templates）與 Skill-Eval Repository（存放 Probes、Validators、Regressions、Reports），並設定兩者間的權限邊界。

2. **定義角色與派發範圍**：在運行環境中配置 Optimization Agent Team（負責診斷、探索、提案）與 Evaluation Agent Team（負責報告、分析、執行），確保評估端僅能讀取探針與產出刪減報告，優化端僅能讀取刪減報告與歷史 Wiki，無法接觸未刪減的 oracle targets 與 traces。

3. **建立基準決策歷史**：執行初始技能 S₀ 於實踐探針上，由 Evaluation Dispatch 產出首份 redacted report；Optimization Dispatch 據此進行失效模式診斷，開立 Issue #1，建立 Branch 提出候選修訂，並記錄診斷依據與預期失效模式標籤。

4. **觸發候選評估與證據回傳**：透過 PR 觸發 Evaluation Dispatch，在隔離環境中運行候選技能，分析失敗模式，產出結構化證據（含失效模式分類與執行摘要），並回傳 Accept 或 Reject 的 outcome。

5. **合併與歷史鏈結**：通過評估的修訂執行 Merge，將「診斷 → 修訂 → 刪減報告摘要 → 結果」寫入 Persistent Decision History（如 Wiki #1 與 Issue #1 的雙向鏈結），形成可供後續智能體直接讀取的決策鏈。

6. **跨工作階段接續演化**：在後續開發週期中，新派發的 Optimization Agent 優先讀取歷史 Wiki 與已關閉/已拒絕的 Issue，理解先前被拒絕的替代方案與已過時的修復，再提出新修訂。

7. **產品化部署**：將收斂後的技能套件掛載至目標運行環境，並設定定期回歸測試機制，由 SkillHone 自動偵測環境變化（如 API 變更）並生成新 Issue，進入下一輪演化循環。

### 潛在風險與注意事項

- **歷史膨脹（History Bloat）**：決策歷史隨迭代次數線性增長，可能撐滿後續智能體的上下文視窗。建議實施分層摘要機制，對陳舊且已驗證穩定的決策進行壓縮歸檔，僅保留高階結論與失效模式標籤。

- **過時修復復發（Obsolete Fixes）**：若歷史未明確標記修訂所對應的環境版本（如 API 版本號、工具介面規格），後續智能體可能在環境已變遷的情況下重新引入舊修復。每筆修訂應強制記錄適用環境假設與失效模式標籤，並在環境異動時觸發歷史失效標記。

- **刪減過度或不足（Redaction Balance）**：刪減過度會使優化端缺乏診斷線索，導致提案品質低落；刪減不足則讓優化端有記憶探針答案的風險。應建立分級刪減政策，例如僅暴露錯誤類型、執行軌跡摘要與驗證器回傳碼，完全隱藏 oracle targets 與原始 traces。

- **角色隔離失效（Permission Leakage）**：若運行環境未嚴格區分讀寫權限，評估端可能間接寫入技能倉庫，或優化端透過側通道取得未刪減資訊。建議使用獨立的 repository access tokens、沙箱化執行環境，並在派發層級（dispatch level）強制檢查權限邊界。

- **評估成本飆升**：持續演化涉及大量 LLM 呼叫與探針執行。應設定單輪評估預算上限，並利用回歸測試集（regression sets）執行定向測試：僅對高風險變更執行全量探針，對微調則執行抽樣或差異探針。

### 與其他技術的整合建議

- **與現有 Agent Runtime 整合**：SkillHone 作為外掛式「技能維護層」，可疊加於 Claude Code、Codex、Hermes 或自研框架之上，無需替換底層骨幹模型。透過標準化的技能套件格式（SKILL.md、Scripts、Templates），實現跨運行環境轉移。

- **與 CI/CD 管線整合**：將 Skill-Eval Repository 的評估流程嵌入持續整合管線，利用 repository actions 在每次技能 PR 時自動觸發 Evaluation Dispatch，並將 redacted reports 與 outcome 回寫至 PR 討論串，使人機協作審查成為標準流程。

- **與現有搜尋/檢索堆疊整合**：雖然論文驗證於無預整合搜尋堆疊的環境，但在產品中可將企業內部 RAG 或搜尋 API 封裝為技能內的工具腳本。SkillHone 專注於「技能程序如何有效呼叫檢索」，而非取代底層檢索引擎。

- **與知識管理系統整合**：Persistent Decision History 可同步至 Jira、Notion 或企業 Wiki，讓人類工程師與智能體共享同一套決策脈絡。例如將 Wiki #N 對應至 Notion 頁面，Issue #N 對應至 Jira Ticket，實現雙軌治理。

- **與 GEPA / Skill-Creator 整合**：採用 Skill-Creator 作為產生初始技能套件 S₀ 的前置步驟，再以 SkillHone 接管後續持續維護；GEPA 風格的迭代變異與選擇機制則可嵌入 Proposer 角色，作為修訂提案的生成策略之一，補足 SkillHone 在「如何產生第一版技能」的空白。

### 給不同背景讀者的閱讀建議

**給初學者**：先將「技能（Skill）」理解為一份可載入的任務指令套件，再把 SkillHone 想像成「會自動記錄每次改版原因與測試結果的版本控制系統」。閱讀時請優先看論文的 Figure 2 架構圖與第 2.2 節，掌握「優化端負責改技能、評估端負責跑測試」這條核心分工，暫時無需深入 GEPA 演算法或基準測試的數學細節。

**給 AI 工程師**：請聚焦角色分離（role-bounded dispatches）與刪減報告（redacted reporting）的實作細節，評估如何在你目前的 Agent Runtime 中實現權限切換與雙倉庫設計。第 2 節的方法論與附錄 E 的 dispatch patterns 是關鍵，建議對照你現有的 prompt chaining 或 multi-agent 架構，規劃最小可行導入方案。

**給研究人員**：請關注 persistent decision history 的形式化設計與跨工作階段精煉（cross-session refinement）的機制創新。建議將 SkillHone 與現有的 artifact-centered 方法（如 Hermes-SE、GEPA）進行對照分析，探討保留決策脈絡如何從根本避免重複發現（rediscovery）與過時修復（obsolete fixes），並思考其在可解釋性與持續學習（continual learning）領域的理論延伸。

**給產品經理**：請將閱讀重心放在「適用場景」與「潛在風險」章節，評估導入 SkillHone 的維護成本與長期效益。關鍵在於理解這不是一次性自動化工具，而是需要持續投入評估資產建置、歷史治理與角色權限設計的長期基礎建設；與其追求單次最佳化，更應規劃技能生命週期管理的預算、團隊編制與風險控管機制。
