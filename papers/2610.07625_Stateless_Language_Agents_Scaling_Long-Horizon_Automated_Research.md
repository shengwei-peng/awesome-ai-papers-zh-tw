## 摘要翻譯

自動化研究系統日益以長時程方式運行大語言模型代理（LLM agents），但更多的推論（inference）本身並不會產生更多進展：代理會重播日益增長的歷史、重複彼此的工作，或在 Token 消耗持續進行的同時停止實驗。然而多數評估使用短預算或早期飽和的基準測試，使這些失敗模式未能受到測試。我們將這些失敗歸因於兩個選擇：研究狀態存放在何處，以及由誰決定下一步嘗試什麼。我們提出無狀態語言代理（Stateless Language Agents, SLAs），其奠基於「以無狀態代理進行有狀態搜尋」（stateful search with stateless agents）的原則：沒有任何代理在跨呼叫時保留其對話；取而代之的是，執行框架（harness）持有研究狀態（候選解與量測結果），並為每次呼叫重建一個全新且角色專屬的上下文。每個代理所見的內容成為一個明確的設計選擇，而非隨執行過程增長的歷史。我們在 SLA 框架中實作此原則，其中無狀態顧問（Stateless Advisor）讀取跨搜尋方向的框架彙整的證據，並指派具體實驗給平行工作代理（Parallel Workers）。我們在軟體工程、核心最佳化與演算法設計等任務上，以高達十億 Token 的預算，將 SLA 與三個近期框架（SwarmResearch、CORAL、EvoX）進行比較。SLA 在每項任務上皆達到最佳最終結果，並以減少逾 84% 的 Token 達到最強核心最佳化基線的最終效能。來自共用檢查點的消融實驗顯示，聚焦的上下文與明確指派皆對 SLA 的進展有所貢獻，其效果在完整執行過程中可產生複合效應，同時顧問代理僅消耗少於 0.6% 的 Token。這些結果支持 SLA——其將持久研究狀態排除於代理對話之外——並顯示短評估時程可能誤判研究系統及其元件。

### 核心貢獻（3～5點）
- **問題診斷**：系統性地指出長時程自動化研究中三種常見失敗模式——重播日益增長的歷史、重複彼此的工作、在 Token 消耗持續時停止實驗——並將其歸因於「研究狀態存放位置」與「下一步決策者」兩個根本設計選擇。
- **設計原則**：提出「以無狀態代理進行有狀態搜尋」的核心原則，將研究狀態完全交由執行框架持有，使代理每次呼叫皆以全新且角色專屬的上下文啟動，從根本上避免對話歷史無限增長。
- **架構實作**：在 SLA 框架中具體實作上述原則，由無狀態顧問讀取框架彙整的證據並指派具體實驗給平行工作代理，使「每個代理所見的內容」成為可明確設計的選擇。
- **實證成果**：在軟體工程、核心最佳化與演算法設計等任務上，以高達十億 Token 的預算擊敗 SwarmResearch、CORAL、EvoX 三個近期框架，於每項任務皆達到最佳最終結果，並以減少逾 84% Token 的成本達到最強核心最佳化基線的最終效能。
- **方法論啟示**：透過消融實驗證明聚焦的上下文與明確指派各自對進展皆有貢獻，且效果於完整執行中可複合累積；同時指出短評估時程可能誤判研究系統及其元件，呼籲業界採用更長的評估預算。

### 適合對象
本論文最適合以下讀者閱讀：(1) 從事自動化研究、AI for Science 或 AI4Research 系統設計的研究者，特別是正在建構或評估基於大語言模型之長時程研究代理的團隊；(2) 對代理架構、狀態管理與上下文工程（context engineering）感興趣的大語言模型應用研究者；(3) 機器學習、系統優化與軟體工程領域中，需要以大規模自動化實驗取代或輔助人工探索的工程師與科學家；(4) 關注 AI 評估方法論、基準測試設計與「短預算評估是否可靠」等議題的研究方法論學者。整體而言，本論文對學術界與工業界從事自主研究系統開發的實務工作者皆具高度參考價值。

## 深度分析

#### 方法論解析

本文提出**無狀態語言代理（Stateless Language Agents, SLAs）**，其核心設計哲學為「以無狀態代理進行有狀態搜尋（stateful search with stateless agents）」。此一架構從根本上重新定義了自動化研究系統中「狀態（state）」與「上下文（context）」的分工。

**核心概念區分：狀態 vs. 上下文**

作者明確區分了兩個易混淆的概念：
- **代理狀態（agent's state）**：跨呼叫（invocations）持續保存的資訊
- **代理上下文（agent's context）**：單次呼叫內部所見的內容

傳統的 LLM 代理系統將兩者混為一體——對話歷史（conversation history）既是狀態也是上下文，導致隨著執行時間增加，歷史不斷膨脹，代理被迫「重播日益增長的歷史（replay growing histories）」，造成 token 消耗線性增長但研究進展停滯的窘境。

**SLA 的雙層架構**

SLA 框架採用**調控層（harness）—代理（agent）**的分層設計：

1. **調控層（Harness）**：擁有全部**持久研究狀態（durable research state）**，包括所有候選解（candidate solutions）與量測結果（measured outcomes）。這是唯一具備狀態的元件。

2. **無狀態顧問（Stateless Advisor）**：每次呼叫時，由調控層為其重建一份「角色專屬上下文（role-specific context）」，內容為調控層彙整的跨搜尋方向（search directions）證據摘要。顧問的角色是閱讀證據並指派具體實驗。

3. **平行工作代理（Parallel Workers）**：每個 Worker 同樣無狀態，每次呼叫僅看見三項內容——自己的指派任務、保留的候選解、與本地回饋。Worker 之間彼此隔離，互不共享對話。

**關鍵設計選擇**

- **調控層控制的上下文重建（harness-controlled context reconstruction）**：使「代理看見什麼」成為一個明確的設計選擇，而非對話累積的副產物。
- **證據驅動的工作指派（evidence-driven work assignment）**：顧問將彙整證據轉化為具體實驗，使平行 Workers 執行的是互不重複的探索，而非彼此模仿。

此一架構的精妙之處在於：將「記憶」與「決策」分離到不同層級。調控層負責長期記憶與全局協調，代理層負責局部執行與即時推理。這種分工類似於作業系統中「核心（kernel）」與「使用者程序（user process）」的關係——核心持有系統狀態，程序則可隨時被銷毀與重建。

#### 實驗數據解讀

**評估設定**

研究在三類任務上進行長時程評估：
- **軟體工程**：FrontierSWE 基準的四個任務（libexpat、Git→Zig、Dart→Haskell、Lua 編譯器）
- **核心最佳化（kernel optimization）**：Anthropic kernel optimization
- **演算法設計**：包含 26-circle packing 等任務

預算上限達**十億 Token（one billion tokens）**，遠超以往以迭代次數或模型呼叫次數為單位的研究。基線方法包括三個近期框架：**EvoX**、**CORAL**、**SwarmResearch**，並使用 Codex（搭配 GPT-5.5）作為底層模型。

**關鍵實驗結果**

1. **更強的解、更少的 Token（Stronger solutions, fewer tokens）**

   在 Anthropic 核心最佳化任務上，SLA 達到最強基線平均最終效能時，僅使用 67.9M Token，相較基線的 986.3M Token 減少了 **14.5 倍（93.1% reduction）**。三次 SLA 執行的最終結果均優於九次基線執行（每基線三次）。

2. **排名反轉現象（Rankings reverse）**

   FrontierSWE 四個任務呈現一個極具說服力的現象：在 175M Token（25% 預算）時，SLA 落後於各任務最強基線；但在 700M Token（完整預算）時，SLA 反超所有基線。例如：
   - libexpat：SLA 從 −0.85 反轉至 +6.75
   - Git→Zig：SLA 從 −3.90 反轉至 +0.86
   - Dart→Haskell：SLA 從 −11.27 反轉至 +6.68
   - Lua 編譯器：SLA 從 −2.75 反轉至 +5.49

   此一現象直接挑戰了「短評估時程（short evaluation horizons）」的可靠性——若僅在 25% 預算下評估，SLA 會被誤判為劣於基線。

3. **早期飽和問題（Saturate early）**

   在 26-circle packing 任務上，四種方法在 5M Token 時即收斂至彼此差距僅 2.3×10⁻¹⁰ 的範圍內。這顯示許多基準在短預算下即「飽和」，只能測量方法抵達上限的速度，而非其持續將計算轉化為進展的能力。

4. **失敗模式量化**

   在一個 CORAL 執行的 GPU 核心任務中，最後一次改進發生於 231M Token；此後代理反覆宣告其解為最優，最終 1,500 個 session 中有 **98% 未發起任何工具呼叫**，但 token 消耗持續進行。這是「停止實驗（stop experimenting）」失敗模式的具體量化。

**消融實驗（Ablations）**

從共用檢查點（shared checkpoints）恢復執行的消融實驗揭示：

- 移除顧問的上下文重建、Worker 的上下文隔離、或顧問的明確指派，皆會降低平均進展。
- **效應可累積**：移除 Worker 隔離在 100M Token 延續執行中僅損失 5–11 個週期，但在完整 1B Token 執行中損失擴大至 224 個週期。
- 移除指派機制時，平行 Workers 反覆實作同一功能（詳見附錄 D.3）。

**協調成本（Coordination cost）**

顧問僅消耗 **0.24–0.51% 的 Token** 與 **1.2–2.3% 的模型成本**，遠低於 SwarmResearch 的 Shepherd（8.4–10.7% Token、6.1–7.4% 成本）。這顯示明確的協調機制並非昂貴的開銷，反而是高效的設計。

#### 與現有研究的比較

**定位**

本文定位於「自動化研究（AutoResearch）」領域，與近期多項工作形成對話：
- **CORAL**（基線之一）：採用多代理協作但未明確分離狀態與上下文
- **EvoX**（基線之一）：強調演化式搜尋
- **SwarmResearch**（基線之一）：使用 Shepherd 角色進行協調，但成本較高

**相較於現有研究的改進**

1. **理論層面的澄清**：以往研究多將「代理的對話」視為理所當然的狀態載體，卻未正視其隨時間膨脹的問題。SLA 明確區分狀態與上下文，為長時程代理系統提供了新的設計詞彙。

2. **實證層面的突破**：在十億 Token 量級的評估中，SLA 不僅達到最佳最終結果，更以數倍效率達成相同目標。這對實際部署的 AutoResearch 系統具有直接的成本意義。

3. **方法論層面的貢獻**：透過共用檢查點消融實驗，作者得以隔離各元件的貢獻，並展示其累積效應。這種實驗設計本身即為長時程研究系統評估的範式。

**限制與侷限**

1. **任務範圍**：雖然涵蓋軟體工程、核心最佳化、演算法設計三類，但每類僅有少量任務。FrontierSWE 雖有四個任務，演算法設計類的覆蓋面仍偏窄。

2. **模型依賴**：主要結果使用 Codex（搭配 GPT-5.5），不同底層模型可能呈現不同特性。論文中提及 Claude Code 的結果（84% Token 減少），但未深入分析模型間差異。

3. **調控層設計的權衡**：將所有狀態集中於調控層雖帶來清晰性，但也意味著調控層成為單點故障與瓶頸。其擴展性與容錯能力有待進一步驗證。

4. **顧問角色的能力上限**：顧問需具備跨方向證據整合與實驗指派能力。當任務極為複雜、搜尋方向數量龐大時，顧問的上下文可能成為新的瓶頸。

5. **未涵蓋的失敗模式**：本文聚焦於「重複工作」與「停止實驗」，但未深入探討其他可能的長時程失敗模式，如「探索空間坍縮」或「局部最優鎖定」。

#### 可重現性評估

**程式碼開源**

論文標題下方明確標註 **github-squareSLA**，表示程式碼已開源於 GitHub。從有限的全文脈絡可推斷，該倉庫應包含：
- SLA 框架的完整實作
- 調控層、顧問、Worker 三者的介面定義
- 評估腳本與基準任務配置

**檢查點機制的可重現性優勢**

SLA 將研究狀態集中於調控層的設計，意外地帶來一個重要的可重現性優勢：消融實驗可從**完全相同的檢查點（identical checkpointed research states）**恢復執行。這與傳統代理系統中「對話歷史即狀態」的設計形成鮮明對比——後者難以精確重現特定時刻的代理內部狀態。

**資料集與基準**

- **FrontierSWE**：作為軟體工程基準，應為公開可取得
- **Anthropic kernel optimization**：作為公開基準
- **演算法設計任務**（如 26-circle packing）：屬於經典數學最佳化問題

**模型權重**

實驗使用 Codex（搭配 GPT-5.5）與 Claude Code，皆為商業 API 服務，讀者需透過 API 存取，無法取得模型權重本身。但 SLA 框架本身應與底層模型解耦，理論上可適用於其他 LLM。

**重現所需的資源**

十億 Token 量級的評估需要相當的運算資源與 API 預算，這對獨立研究者重現完整結果構成實際障礙。然而，作者提供的檢查點機制應允許在較小預算下進行部分重現與消融驗證。

**可重現性評等**

整體而言，可重現性屬於**中高水準**：程式碼開源、檢查點機制透明、基準公開，但完整實驗的運算成本對一般研究者仍偏高。

#### 未來研究方向

**1. 調控層的擴展性與容錯**

當搜尋方向數量從數十擴展至數百甚至數千時，調控層的證據彙整與指派能力將面臨壓力。未來可探索：
- **階層式調控層**：將單一調控層拆分為多層級，每層負責特定子領域
- **調控層的自我演化**：讓調控層本身具備學習與適應能力
- **分散式調控**：在多個調控層之間引入共識機制

**2. 顧問角色的能力強化**

目前顧問僅消耗極少 Token（<0.6%），這既是優勢也是限制。未來可探索：
- **顧問的推理深度**：在關鍵決策點賦予顧問更長的推理鏈
- **多顧問辯論**：引入多個顧問進行對話式決策
- **顧問的可解釋性**：使指派決策對人類研究者透明

**3. 失敗模式的系統性研究**

本文揭示了「重複工作」與「停止實驗」兩種失敗模式，但長時程代理系統可能存在更多未被發現的失敗模式。未來可建立**長時程失敗模式分類學**，並設計對應的診斷指標。

**4. 跨任務的遷移學習**

SLA 在不同任務上皆表現優異，但每個任務的搜尋方向與證據結構各異。未來可探索：
- **跨任務的調控策略遷移**：將一個任務的調控經驗應用於新任務
- **任務特徵的自動識別**：讓系統自動判斷當前任務的結構特性

**5. 人機協作的研究模式**

SLA 的調控層與人類研究者的決策過程有結構相似性。未來可探索：
- **人類介入點的設計**：在哪些決策點引入人類判斷最有價值
- **可解釋的研究日誌**：將調控層的證據彙整與指派記錄轉化為人類可讀的研究日誌

**6. 評估方法的革新**

本文已論證「短評估時程」可能誤判研究系統。未來需要：
- **長時程基準的標準化**：建立類似 FrontierSWE 但預算達十億 Token 量級的標準基準
- **飽和抵抗基準**：設計不易早期飽和的評估任務
- **效率—品質曲線的標準化報告**：如同 SLA 圖 1(a) 所示的加速比曲線應成為標準報告格式

**7. 理論基礎的深化**

「以無狀態代理進行有狀態搜尋」這一原則的理論意涵尚未完全展開。未來可從以下角度深化：
- **資訊理論分析**：調控層應保留多少資訊、丟棄多少資訊？
- **計算複雜度**：在固定 Token 預算下，無狀態代理相較有狀態代理的理論優勢為何？
- **與搜尋演算法的連結**：將 SLA 與傳統的貝氏最佳化、演化策略等形式化搜尋演算法建立對應關係

**8. 應用領域的拓展**

目前評估集中於程式碼與演算法任務，未來可探索：
- **科學發現**：如藥物設計、材料科學
- **數學定理證明**：形式化證明的自動化探索
- **創意設計**：如遊戲關卡、工業設計

這些方向中，**長時程失敗模式的系統性研究**與**評估方法的革新**可能是最迫切的——它們將直接影響整個領域的可信度與進展速度。

## 論文問答

**Q1：為什麼在長時程自動化研究中，「更多推論」並不會自動帶來更多進展？**

A：這是本文最核心的觀察問題。隨著推論預算增加，代理往往會重播日益增長的對話歷史、重複彼此的工作，甚至在停止實驗的同時仍持續消耗 Token。換言之，單純增加計算量並不等於持續的研究進展，因為代理缺乏有效累積經驗並將其轉化為新實驗的機制。本文將此現象追溯到兩個根本設計選擇：研究狀態存放在哪裡，以及由誰決定下一步該嘗試什麼，這兩個問題若未妥善處理，再多的推論也只會放大既有的失敗模式。

**Q2：現有的自動化研究系統在長時程執行時，主要出現哪些失敗模式？**

A：本文點出三種典型失敗模式：第一，代理反覆重播日益增長的歷史，導致 Token 消耗增加但行為品質下降；第二，平行執行的代理會重複彼此的工作，造成資源浪費；第三，代理可能在聲稱解已最佳化後停止實驗，但 Token 消耗仍持續進行，例如 CORAL 在某次 GPU 核心任務中，最後一次改進出現在 231M Token，之後 98% 的 session 沒有呼叫任何工具卻仍持續燒 Token。這些失敗模式顯示，僅靠擴大推論規模並不能保證具生產力的搜尋。

**Q3：為什麼現有的評估方式無法有效衡量這些失敗模式？**

A：現有評估通常以迭代次數或模型呼叫次數而非 Token 來衡量預算，且許多基準測試會在早期就飽和，例如在 26-circle packing 任務上，四種方法在 5M Token 時彼此差距已小至 2.3×10⁻¹⁰。飽和的基準只能衡量方法多快觸及天花板，而無法判斷方法能否持續將計算轉化為進展。因此，與「經驗累積後效果會複合放大」的設計選擇（例如上下文管理與實驗選擇）有關的特性，在短預算評估中幾乎完全沒有被測試到。

**Q4：SLA 的核心設計原則「以無狀態代理進行有狀態搜尋」是什麼意思？**

A：這個原則區分了代理的「狀態」（跨呼叫持續保存的內容）與「上下文」（單次呼叫中代理所看見的內容）。在 SLA 中，代理本身是無狀態的——它累積的所有東西，包括對話本身，都不會帶到下一次呼叫；但搜尋過程是有狀態的，因為執行框架（harness）持有所有候選解與量測結果，並在每次呼叫時從中重建一個全新的、角色專屬的上下文。這樣一來，代理「看見什麼」就從一個隨執行時間自然膨脹的副產品，變成一個明確的設計選擇。

**Q5：SLA 框架中 Advisor 與 Workers 的角色分工如何設計？**

A：SLA 框架由一個無狀態的 Advisor 與多個平行的 Workers 組成。Advisor 讀取由執行框架彙整的跨搜尋方向的證據，並據此指派具體的實驗給各個 Worker；每個 Worker 則只看見自己的指派內容、保留的候選解與局部回饋，因此彼此之間不會互相干擾或重複。這種分工讓「決策該做什麼實驗」與「執行實驗」兩件事被清楚分離，也讓平行 Workers 各自執行不同的實驗而非重複彼此的工作。

**Q6：SLA 如何透過「執行框架控制的上下文重建」來解決長時程問題？**

A：執行框架掌控所有持久的研究狀態，並在每次代理呼叫時根據該狀態重建上下文，因此 Advisor 看到的是跨所有搜尋方向的結構化證據彙整，而每個 Worker 看到的則只有與其當前任務相關的精簡內容。這種設計避免了將整個對話歷史塞給代理所造成的 Token 浪費與行為退化，也讓「聚焦的上下文」成為可調控的設計變因而非歷史的副作用。

**Q7：SLA 在哪些基準任務上進行評估？為什麼選擇這些任務？**

A：SLA 在三類任務上進行評估：軟體工程（FrontierSWE，包含 libexpat、Git→Zig、Dart→Haskell、編譯 Lua 等任務）、核心最佳化（Anthropic kernel optimization）以及演算法設計。這些任務的共同特徵是擁有可量測的目標但沒有已知最佳解，屬於自動化研究的典型場景；同時它們在長預算下仍能持續區分方法的優劣，不會像 26-circle packing 那樣在早期就飽和，因此適合用來檢驗「能否將更多計算轉化為更多進展」這個核心問題。

**Q8：SLA 在 Anthropic 核心最佳化任務上的關鍵成果是什麼？**

A：在使用 Codex 的 Anthropic 核心最佳化任務上，SLA 的三次執行結果全部優於所有九次基線執行，並以少 14.5 倍的 Token（93.1% 縮減，67.9M vs. 986.3M）就達到最強基線的平均最終效能。換言之，SLA 不只在最終解的品質上勝出，在達到相同目標所需的 Token 上也有數量級的優勢，這對長時程自動化研究的成本與可行性都有重大意義。

**Q9：消融實驗揭示了哪些關於聚焦上下文與明確指派的發現？**

A：從共用檢查點出發的消融實驗顯示，移除 Advisor 上下文重建、Worker 上下文隔離或 Advisor 指派任一項，都會降低平均進展。更值得注意的是，這些設計選擇的效果會隨執行時間複合放大：移除 Worker 隔離在 100M Token 的延續執行中只損失 5–11 個週期，但在完整 1B Token 執行中卻損失 224 個週期；移除指派則會讓平行 Workers 反覆實作同一個功能。這說明短預算評估可能嚴重低估這些元件的真實貢獻。

**Q10：SLA 適用於哪些實際的研究自動化場景？**

A：SLA 特別適合需要大量平行實驗、迭代時間長、且需要持續累積證據以指導下一步行動的研究場景，例如機器學習超參數搜尋、編譯器與程式語言移植（如 FrontierSWE 中的 Git→Zig、Dart→Haskell）、GPU 核心調校、演算法設計與最佳化等。在這些場景中，研究狀態（候選解與量測結果）本身就是最有價值的資產，而 SLA 把它從代理對話中抽離出來集中管理，正好契合此類工作的本質。

**Q11：在實際部署 SLA 時，需要考量哪些產品化因素？**

A：實際部署時需考量幾個面向：第一，執行框架需要可靠的持久化層來保存候選解與量測結果，並支援從檢查點恢復以便進行消融與除錯；第二，Advisor 雖然只消耗 0.24–0.51% 的 Token 與 1.2–2.3% 的模型成本，但其決策品質直接影響整體效率，因此需要謹慎設計其證據彙整與指派策略；第三，Workers 之間的隔離機制需要工程化支援，避免共享狀態洩漏導致行為退化；最後，整體系統需要可觀測性來追蹤每個 Token 實際帶來多少進展。

**Q12：SLA 對自動化研究領域可能產生什麼影響？**

A：SLA 的最重要貢獻在於挑戰了「代理對話越長越好」的隱含假設，並提出一個可實證檢驗的替代原則：把持久的研究狀態留在代理對話之外。這可能促使後續研究重新思考自動化研究系統的架構，把注意力從「如何讓代理記住更多」轉向「如何讓執行框架更聰明地選擇代理該看見什麼」。此外，本文展示的「短評估時程可能誤判研究系統及其元件」的現象，也將促使社群建立更長、更細緻的評估標準。

**Q13：SLA 框架有哪些已知的限制？**

A：SLA 的有效性高度依賴執行框架能否正確地彙整證據並重建有意義的上下文；若證據彙整設計不當，Advisor 可能會基於失真或過度簡化的資訊做出次佳指派。此外，SLA 的設計假設任務具有可量測的目標，這對軟體工程、核心最佳化與演算法設計成立，但對於需要質性判斷或開放式探索的研究任務可能不適用。最後，本文也坦承評估僅涵蓋三類任務與三個基線框架，更廣泛的適用性仍待驗證。

**Q14：在哪些情況下 SLA 可能會失敗？**

A：當任務的進展訊號很弱或量測結果雜訊很大時，Advisor 可能難以從彙整證據中辨識出有希望的搜尋方向，導致指派品質下降。當 Workers 之間的實驗需要高度共享的中間狀態（例如共同建構一個大型程式碼基底的不同模組）時，Worker 隔離反而可能妨礙協作。此外，若候選解空間極其龐大且缺乏結構，僅靠 Advisor 的指派可能不足以有效覆蓋，系統仍可能陷入局部最佳。

**Q15：未來的研究方向有哪些？**

A：未來可朝幾個方向延伸：第一，研究更聰明的證據彙整與上下文重建策略，例如讓 Advisor 學習如何根據任務動態調整所看見的證據粒度；第二，將 SLA 原則應用於更多類型的任務，包括需要質性評估或人機協作的研究場景；第三，探索 Advisor 與 Workers 之間更豐富的互動模式，例如讓 Workers 在執行中產生新的搜尋方向提案供 Advisor 評估；第四，建立標準化的長時程評估基準，避免短預算評估誤判系統優劣；最後，研究如何讓 SLA 與人類研究者更緊密地協作，把人類的直覺與機器的規模化搜尋結合起來。

## 實務應用指南

### 適用場景

1. **大型程式碼庫的長時程重構與移植**：當團隊需要將 Git 移植到 Zig、Dart 移植到 Haskell，或重寫 Lua 編譯器等需要數百萬至數億 Token 預算的任務時，SLA 框架可讓多個 Worker 平行處理不同子模組，避免重複實作同一個功能，並由 Advisor 依證據動態分配任務。

2. **GPU 核心最佳化與高效能運算**：在 Anthropic kernel optimization 等需要反覆實驗不同實作策略的場景中，SLA 能以 14.5 倍更少的 Token 達到最強基線的最終效能，特別適合需要長時間迭代搜尋最佳化配置的 ML 系統工程團隊。

3. **演算法設計與競賽題型研究**：對於 26-circle packing 等無已知最佳解、需要持續探索的演算法問題，SLA 的「有狀態搜尋、無狀態代理」設計可避免代理陷入「宣告已達最優」而停止實驗的失敗模式。

4. **企業內部的自動化研究助理**：例如自動搜尋超參數組合、A/B 測試設計、或資料前處理管線最佳化等需要「累積證據並持續實驗」的工作流程。

5. **科學探索與假設驗證**：在藥物分子設計、蛋白質摺疊搜尋等需要長期迭代的科學計算任務中，SLA 的檢查點機制可讓研究人員從任意中斷點恢復並進行消融實驗。

### 實作前置條件

**資料需求**
- 候選解的儲存結構（程式碼版本、實驗配置、評估結果）
- 量測結果的標準化格式（benchmark 分數、執行時間、記憶體使用等）
- 搜尋方向的元資料（每個方向目前的最佳解、嘗試次數、停滯時間）
- 評估環境的介面定義（如何執行候選解並回傳分數）

**運算資源**
- 至少一個強大的 LLM API 存取權限（論文中使用 Codex 搭配 GPT-5.5，以及 Claude Code）
- 平行執行的 Worker 環境（容器、沙箱、或雲端運算實例）
- 累計預算需規劃至數億至十億 Token 級別
- 評估任務的執行環境（編譯器、測試框架、硬體加速器等）

**技能需求**
- 熟悉 LLM agent 框架設計（context 管理、tool use、function calling）
- 具備分散式系統經驗（任務排程、狀態持久化、檢查點機制）
- 了解 prompt engineering 與角色化上下文設計
- 具備軟體工程或最佳化領域的領域知識（依任務而定）

### 實作步驟建議

**步驟一：設計 Harness 層的狀態結構**
建立外部持久化層來儲存所有候選解與量測結果。建議採用結構化資料庫（如 SQLite 或 JSON 檔案系統），記錄每個候選解的程式碼、評估分數、產生時間、所屬搜尋方向等欄位。這是 SLA 框架的核心，必須先於任何代理邏輯完成。

**步驟二：實作 Advisor 的證據彙整機制**
讓 Advisor 從 Harness 讀取跨所有搜尋方向的彙整證據（harness-summarized evidence），而非從對話歷史中提取。Advisor 的 prompt 應包含：各方向的目前最佳解、最近 N 次嘗試的趨勢、停滯方向、需要新嘗試的區域。Advisor 輸出應為具體的實驗指派（包含目標方向、實驗類型、優先順序）。

**步驟三：設計 Worker 的聚焦上下文**
每個 Worker 呼叫時只接收三項資訊：(1) Advisor 指派的具體任務、(2) 該方向的目前最佳候選解、(3) 最近的本地回饋。嚴格隔離 Worker 之間的資訊，避免 Worker 看到其他 Worker 的對話歷史。

**步驟四：建立檢查點與恢復機制**
將 Harness 的狀態序列化為可恢復的檢查點。這是進行消融實驗的關鍵——所有變體必須從相同的檢查點出發，才能公平比較 context 設計與指派機制的貢獻。

**步驟五：實作平行 Worker 的任務排程**
根據 Advisor 的指派結果，將實驗分發到平行的 Worker 環境。確保每個 Worker 拿到的是「不同的實驗」而非「相同實驗的重複」，這是論文中強調避免「重複工作」失敗模式的關鍵。

**步驟六：加入停滯偵測與重新指派邏輯**
監控每個搜尋方向的進展，當某方向連續多次無改善時，Advisor 應主動重新指派探索策略。論文中 CORAL 的失敗案例（98% 的 session 沒有 tool call）正是缺乏此機制所致。

**步驟七：評估與消融實驗**
從共用檢查點出發，系統性地移除 Advisor context 重建、Worker context 隔離、或 Advisor 指派等元件，量化各元件的貢獻。論文的消融顯示，這些效應會在完整 1B Token 執行中複合放大。

### 潛在風險與注意事項

**風險一：Harness 狀態膨脹導致摘要失真**
隨著執行時間增長，候選解數量可能膨脹至數千甚至數萬筆，Advisor 看到的彙整證據可能過於粗糙或遺失關鍵細節。
**緩解**：設計多層次的摘要機制（全域摘要 → 方向摘要 → 區域摘要），並對停滯方向保留更詳細的歷史。

**風險二：Advisor 指派品質不穩定**
若 Advisor 的 prompt 設計不當，可能產生模糊或重複的指派，導致 Worker 重複實作相同功能。
**緩解**：在指派中加入明確的「禁止重複」約束，並在 Harness 中記錄已嘗試的實驗清單供 Advisor 參考。

**風險三：Worker context 隔離過於嚴格**
若 Worker 完全看不到其他方向的進展，可能錯失跨方向的可遷移洞察。
**緩解**：允許 Advisor 在指派中明確傳遞「來自其他方向的相關發現」，而非讓 Worker 直接讀取。

**風險四：評估環境不穩定**
若評估分數本身有雜訊（例如編譯時間波動、隨機種子），可能誤導 Advisor 的指派決策。
**緩解**：對每個候選解執行多次評估取平均，或使用統計顯著性檢定。

**風險五：Token 成本失控**
雖然 Advisor 僅消耗 0.6% 的 Token，但若 Worker 的 context 設計不當，仍可能在長時程執行中累積巨額成本。
**緩解**：設定每個 Worker 呼叫的 context 大小上限，並監控累計 Token 消耗的成長率。

**風險六：基準飽和導致評估失真**
論文中 26-circle packing 在 5M Token 時四個方法差距僅 2.3×10⁻¹⁰，這種早期飽和的基準無法區分方法的長期表現。
**緩解**：選擇尚未飽和的基準，或設計自訂任務以延長有意義的評估時程。

### 與其他技術的整合建議

**與既有 Agent 框架整合**
SLA 並非取代 LangChain、AutoGen 等框架，而是作為其上層的「執行模式」。可在這些框架中實作「無狀態呼叫」介面：每次呼叫時從 Harness 重建 context，而非延續對話歷史。

**與版本控制系統整合**
將 Harness 的狀態儲存層與 Git 整合：每個候選解作為一個 commit，評估結果作為 commit metadata。這讓研究人員可使用熟悉的 diff、branch、merge 工具來分析搜尋軌跡。

**與 MLOps 平台整合**
將 Advisor 的指派視為「實驗排程」，整合到 MLflow 或 Weights & Biases 等平台。每個 Worker 執行的實驗自動記錄為一次 run，Advisor 的決策記錄為 run 的 parent metadata。

**與分散式運算框架整合**
Worker 的平行執行可整合到 Kubernetes、Ray、或 AWS Batch 等排程系統。Harness 作為中央協調器，透過 API 與這些系統溝通。

**與人類專家工作流程整合**
Advisor 的指派結果可暴露給人類專家審核，允許「人在迴圈」模式：專家可覆寫指派、注入領域知識、或暫停自動搜尋進行手動實驗。

**與成本監控系統整合**
由於 SLA 的核心優勢之一是 Token 效率，建議整合成本監控儀表板，即時追蹤 Advisor 與 Worker 的 Token 消耗比例，確保 Advisor 維持在 <1% 的低成本區間。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先理解「為什麼對話歷史會成為問題」這個核心直覺——當 LLM 代理的對話越來越長，不僅成本上升，模型也更容易迷失在歷史中、忘記目標、重複已嘗試過的做法。論文的關鍵洞見是：把「狀態」從代理的腦袋裡搬到外部系統，讓代理每次都「重新開始」但「看到正確的資訊」。閱讀時可先聚焦在圖 1 的視覺化結果，理解 SLA 如何用更少的 Token 達到更好的結果。

**給 AI 工程師**：重點關注第 1 節的「兩個失敗模式」（replay growing histories 與 stop experimenting）以及第 2 節的架構設計。具體實作時，請特別注意：(1) Harness 的狀態結構設計是整個系統成敗的關鍵；(2) Advisor 的 prompt 工程需要仔細調校，論文的消融實驗顯示「明確指派」對長期表現有複合放大效應；(3) 檢查點機制不僅是工程細節，更是進行公平消融實驗的基礎設施。建議直接參考作者的 GitHub 程式碼（github-squareSLA）作為起點。

**給研究者**：這篇論文的價值不僅在於 SLA 框架本身，更在於它對「自動化研究評估方法論」的批判——短預算與早期飽和的基準會誤判研究系統的優劣。建議深入閱讀消融實驗章節，理解「context 設計」與「指派機制」如何在不同時程尺度上產生不同效果。對於從事 AutoResearch、agent 架構設計、或 LLM 評估方法論的研究者，這篇論文提出了多個值得延伸的研究方向，例如：如何自動化設計更好的 evidence summarization？Advisor 的決策品質如何形式化評估？

**給產品經理**：這篇論文的商業意涵是：自動化研究系統的 ROI 不取決於「投入多少 Token」，而取決於「如何組織這些 Token」。SLA 展示了透過架構設計，可以用 84-93% 更少的成本達到更好的結果。對於考慮導入 AI 研發助手的團隊，建議關注三個指標：(1) 系統是否會陷入「宣告已達最優而停止實驗」的陷阱；(2) 平行代理是否會重複工作；(3) 評估基準是否會早期飽和而無法反映長期表現。論文的設計原則可作為評估供應商方案的 checklist。
