# SWE-Review：以智慧體程式碼審查閉合議題解決迴路

**原文標題：** SWE-Review: Closing the Loop on Issue Resolution with Agentic Code Review  
**作者：** Ruoyu Wang、Jierun Chen、Shaowei Wang 等 10 位作者  
**發布日期：** 2026-07-07  
**HF 連結：** [https://huggingface.co/papers/2607.06065](https://huggingface.co/papers/2607.06065)  
**arXiv：** [https://arxiv.org/abs/2607.06065](https://arxiv.org/abs/2607.06065)  

---

## ⚡ TL;DR

現有 AI 生成 PR 多為一次性開環流程，缺乏系統性審查與修正機制。
本文提出 SWE-Review 框架，讓審查智慧體主動探索程式碼庫並給出決策與診斷。
實驗顯示生成-審查-修訂迴圈可持續提升 PR 解決率，並優於單輪固定上下文審查。

---

## 摘要翻譯

程式設計智慧體（Coding Agents）越來越常針對真實世界的軟體議題（Issue）生成拉取請求（Pull Requests, PR），然而一次性 PR 生成（One-shot PR Generation）仍屬開環（Open-loop）：PR 在提出時缺乏系統化的審查、診斷或修訂。本研究提出 SWE-Review，一個透過智慧體程式碼審查（Agentic Code Review）將此流程閉環（Closed-loop）的框架。給定一個議題與一個 AI 生成的 PR，審查智慧體（Reviewer Agent）會探索程式碼庫（Repository），決定是否應接受該 PR，並提供結構化回饋（Structured Feedback）以進行修訂。我們以所提出的 SWE-Review-Bench 評測此設定，衡量審查正確性（Review Correctness）與後續修訂實用性（Revision Usefulness）。我們進一步整理 SWE-Review-Traj 資料集，以研究智慧體審查的更廣泛應用，並填補開放審查者訓練（Open Reviewer Training）的資料稀缺缺口。實驗顯示，智慧體審查透過生成-審查-修訂迴圈（Generate-Review-Revise Loop）持續改進 PR，在決策準確率（Decision Accuracy, DA）與修訂後解決率（Resolve Rate after Revision, RRR）上均優於單輪固定上下文審查（Single-turn Fixed-context Review），並可遷移至審查之外以提升議題解決模型（Issue-resolution Models），同時實現有效且高效的測試時擴展（Test-time Scaling）。這些結果凸顯智慧體程式碼審查作為一項實用機制，能將 AI 程式設計智慧體從一次性 PR 生成導向閉環議題解決。

### 核心貢獻（3～5點）
- 提出 SWE-Review 框架：透過審查智慧體自動探索程式碼庫、做出接受／要求修改的二元決策，並產出結構化回饋以指導 PR 修訂。
- 建立 SWE-Review-Bench 評測基準：同時衡量審查正確性（Decision Accuracy）與修訂實用性（Resolve Rate after Revision）。
- 整理 SWE-Review-Traj 資料集：提供智慧體審查軌跡（Agentic Review Trajectories），支援開放審查者訓練與相關研究。
- 驗證閉環效益：生成-審查-修訂迴圈在決策準確率與修訂後解決率上均優於單輪固定上下文審查，並能遷移提升議題解決模型與測試時擴展效率。

### 適合對象
從事 AI 輔助軟體工程、程式設計智慧體、自動化程式碼審查與軟體議題解決研究的學者與工程師；特別適合關注如何透過審查-修訂閉環提升生成式程式碼品質、以及需要公開審查軌跡資料進行模型訓練的研究者。

## 深度分析

#### 方法論解析

##### 1. 問題設定：從一次性 PR 生成到閉環 issue 解決

SWE-Review 把傳統的 one-shot PR generation（一次性 PR 生成）從 open-loop（開環）改造成 closed-loop（閉環）的 issue resolution（議題解決）流程。輸入包含一個 repository（程式碼庫）、一個 issue（議題），以及由 coding agent（程式設計智慧體）產生的 candidate pull request（候選拉取請求）；輸出則有兩部分：一是 accept/request-changes decision（接受/要求修改決策）這類 binary decision（二元決策），二是 structured diagnosis（結構化診斷），用來在要求修改時具體指出缺陷與修正方向。這樣的設計讓審查不再只是「評分」，而是成為後續 revision（修訂）的 actionable feedback（可執行回饋）。

##### 2. Agentic reviewer（審查智慧體）的運作方式

與傳統 automated code review（自動化程式碼審查）把 diff 與少量 retrieved context（檢索上下文）一次餵給模型不同，SWE-Review 的 reviewer agent（審查智慧體）會在可執行的程式碼庫環境中主動探索：追蹤 call chains（呼叫鏈）、檢查相關實作、執行測試，並驗證 patch 是否真正解決 root cause（根本原因）。這種 agentic code review（智慧體程式碼審查）能發現「看起來正確的 diff 其實改錯位置」或「引發 regression（迴歸）」等問題。最終產出的 structured feedback（結構化回饋）通常包含缺陷描述、定位與 suggested fix（建議修正），讓 coding agent 能據此進行有方向的修改。

##### 3. Generate-review-revise loop（生成-審查-修訂迴圈）

整個流程形成一個 generate-review-revise loop（生成-審查-修訂迴圈）：coding agent 先生成 candidate PR（候選拉取請求），reviewer agent 審查後若給出 accept（接受）則合併；若給出 request changes（要求修改）則把 structured diagnosis（結構化診斷）回傳，讓 coding agent 進行 review-guided revision（審查引導修訂）。這個迴圈可反覆進行，直到 PR 被接受或達到迭代上限，從而將 AI-generated PR 從一次性產出轉為持續改善的閉環系統。

##### 4. SWE-Review-Bench 與 SWE-Review-Traj

為了系統性研究這個設定，作者提出 SWE-Review-Bench，包含 500 個 SWE-bench Verified 議題所衍生的 1,384 個 candidate pull requests（候選拉取請求），並由三個不同品質的 PR generators（PR 生成器）產生，分別對應高、中、低品質分布。這讓評測能同時檢驗 reviewer 在「好 PR」與「爛 PR」上的判別能力。評測指標有三項：

- Completion Rate（CR，完成率）：衡量 reviewer 是否能產出 parseable final review（可解析的最終審查），反映指令遵循與輸出結構穩定性。
- Decision Accuracy（DA，決策準確率）：衡量 merge decision（合併決策）是否正確，即該接受的 PR 有沒有被接受、該退回的有沒有被退回。
- Resolve Rate after Revision（RRR，修訂後解決率）：衡量經過審查回饋修訂後，final patch outcome（最終修補結果）是否真正解決 issue，是端到端的 review usefulness（審查實用性）指標。

此外，作者還釋出 SWE-Review-Traj，包含 8,914 條 agentic review trajectories（智慧體審查軌跡），用來支援 open reviewer training（開放審查者訓練），填補公開審查資料的稀缺缺口。

##### 5. 訓練策略：從審查軌跡到統一智慧體

作者利用 SWE-Review-Traj 進行 supervised fine-tuning（SFT），訓練可公開取得的 reviewer models（審查模型）。實驗顯示，僅用審查軌跡就能讓 8B 模型從幾乎不會產出可解析輸出，進步到能穩定完成審查並做出高於隨機的決策。更進一步，把審查軌跡與 issue-resolution trajectories（議題解決軌跡）做 mixed training（混合訓練），不僅能提升 direct resolve rate（直接解決率），還能訓練出統一的 generate-review-revise agent（生成-審查-修訂智慧體），在端到端 issue 解決上獲得額外增益。

#### 實驗數據解讀

##### 1. 迭代閉環顯著提升解決率

實驗中最直觀的結果是 generate-review-revise loop（生成-審查-修訂迴圈）能持續拉高 resolve rate（解決率）：

| 模型 | 一次性生成解決率 | 閉環迭代後解決率 | 絕對提升 |
|---|---|---|---|
| Qwen3-30B-A3B | 27.5% | 56.9% | +29.4% |
| Qwen3-Coder-30B-A3B | 50.9% | 68.8% | +17.9% |
| GLM-5 | 72.2% | 75.4% | +3.2% |

這組數據有幾個值得注意的意涵。首先，初始品質越低的 PR generator（PR 生成器），從審查回饋中獲得的提升越大：Qwen3-30B-A3B 幾乎翻倍，顯示 agentic review（智慧體審查）對「還不夠好的 coding agent」特別有價值。其次，即使是已經很強的 GLM-5（72.2%），閉環仍能進一步推到 75.4%，說明高品質生成器仍有邊際錯誤可透過審查修正。不過提升幅度遞減也暗示：當 PR generator（PR 生成器）本身夠強時，reviewer 必須處理的是更細微、更難診斷的殘餘錯誤。

##### 2. Agentic review 勝過單輪固定上下文審查

在所有三個 PR generator（PR 生成器）拆分上，agentic review（智慧體審查）在 Decision Accuracy（DA，決策準確率）與 Resolve Rate after Revision（RRR，修訂後解決率）都優於 single-turn fixed-context review（單輪固定上下文審查）。特別是在需要 non-local repository reasoning（非局部程式碼庫推理）的困難案例上，差距更明顯。這驗證了「僅看 diff 與固定上下文」不足以判斷 issue-resolution patch 的正確性；主動探索程式碼庫、執行測試、追蹤相關實作，是提升審查品質的關鍵。

##### 3. 審查軌跡訓練讓小模型具備可用審查能力

SFT on SWE-Review-Traj 對 8B reviewer（審查者）的效果非常顯著：

- Completion Rate（CR，完成率）從約 4% 提升到 71–84%，代表模型學會了產出符合格式、可解析的 structured final review（結構化最終審查）。
- Decision Accuracy（DA，決策準確率）從接近隨機提升到 67–72%，顯示審查決策能力可透過軌跡資料有效學習。

這填補了 open reviewer training（開放審查者訓練）的資料缺口，也證明審查不只是大模型的專利，經過適當資料訓練後，中小型模型也能擔任可用的 reviewer agent（審查智慧體）。

##### 4. 審查能力可遷移到議題解決本身

更有趣的是，review trajectories（審查軌跡）的價值不僅限於訓練 reviewer。混合審查軌跡與 issue-resolution trajectories（議題解決軌跡）後：

- direct resolve rate（直接解決率）提升最高達 5.6 個百分點；
- 統一的 generate-review-revise agent（生成-審查-修訂智慧體）最終解決率提升最高達 10.6 個百分點。

這表示審查過程中累積的「判斷什麼是對的、什麼是錯的」知識，能幫助模型在生成階段就避開錯誤，達到跨任務遷移。

##### 5. 測試時擴展：審查引導修訂比純驗證更有效率

在 test-time scaling（測試時擴展）場景中，訓練好的 reviewer（審查者）作為 verifier（驗證器）不僅比專用驗證器更有效，也更有效率。實驗顯示，review-guided iterative revision（審查引導迭代修訂）僅用 4 輪 revision（修訂）就能把解決率從 22.9% 提升到 38.4%。相較於傳統「大量採樣再選最好」的 test-time scaling（測試時擴展），這種基於結構化回饋的迭代修訂能用較少運算達到顯著進步，因為每一輪都利用診斷資訊縮小搜尋空間。

##### 6. 指標解讀與潛在限制

- CR（完成率）雖然是基礎門檻，但高 CR 不等於高 DA 或 RRR，必須三者一起看。
- DA（決策準確率）只衡量「接不接受」是否正確，但一個正確的 reject（退回）若沒有有用的 diagnosis（診斷），RRR 仍會低。
- RRR（修訂後解決率）是端到端指標，但它同時受制於 reviewer 的診斷品質與 coding agent 的修訂能力；若修訂模型不夠強，可能低估 reviewer 的價值。
- 實驗中的 candidate PR（候選拉取請求）來自三個 PR generators（PR 生成器），雖已覆蓋不同品質分布，但仍非人類開發者產生的 PR，可能遺漏某些人類常見的錯誤模式。

#### 與現有研究的比較

##### 1. 與 SWE issue resolution（議題解決）研究的關係

現有 coding agents（程式設計智慧體）如 Cursor、Claude Code、Codex、Aider、Devin 以及各類 agent scaffolds（智慧體腳手架）主要聚焦於如何產出更好的 PR，強調長程規劃、工具使用與環境互動。SWE-Review 採取互補的 post-generation（生成後）視角：不重新打造 PR generator（PR 生成器），而是研究「PR 產出後該怎麼辦」。這讓它成為 issue resolution pipeline（議題解決流程）中不可或缺的過濾器與診斷器，能夠剔除未解決 issue 的 patch 並提供可執行的修正建議。

##### 2. 與自動化程式碼審查的差異

傳統 automated code review（自動化程式碼審查）通常被建模為 single-turn fixed-context review（單輪固定上下文審查）：把 diff 與檢索到的上下文一次輸入模型，輸出標籤或評論。這種做法假設 diff 本身包含足夠證據，但對於 AI-generated issue-resolution patches（AI 生成的議題解決修補）來說，diff 可能掩蓋根本原因、改錯位置或引入程式碼庫其他地方的迴歸。SWE-Review 把 review 視為 agentic capability（智慧體能力），讓 reviewer 主動收集 repository-level evidence（程式碼庫層級證據），再做出決策與診斷，這是方法論上的重要升級。

##### 3. 與審查評測基準的差異

過去的程式碼審查評測多採用 text overlap（文字重疊）、embedding similarity（嵌入相似度）或 LLM-as-a-judge（以大型語言模型作為評判）來比對生成評論與人類參考答案。這些指標雖能衡量評論「像不像人寫的」，卻不直接回答兩個核心問題：reviewer 是否做了正確的 merge decision（合併決策）？以及它的回饋是否真的能幫助後續 revision（修訂）成功？SWE-Review-Bench 透過 Decision Accuracy（DA，決策準確率）與 Resolve Rate after Revision（RRR，修訂後解決率）進行端到端評估，更貼近實務需求。

##### 4. 與測試時驗證器的差異

在 test-time scaling（測試時擴展）領域，既有研究多訓練專用 scorer（評分器）或 verifier（驗證器），將每次嘗試壓縮為單一 scalar score（純量分數）或 binary verdict（二元裁決），再從多個候選中挑選最好的。SWE-Review 則提供豐富的 structured diagnosis（結構化診斷），讓修訂過程能針對性地修正錯誤，而不只是重新採樣。這種 review-guided iterative revision（審查引導迭代修訂）在樣本效率上更具優勢，因為它把測試時運算花在「沿著正確方向改進」而非「盲目嘗試」。

##### 5. 主要限制

- 環境依賴：agentic review（智慧體審查）需要可執行的程式碼庫環境與測試套件，對於缺乏完整測試或難以建置的專案，適用性會下降。
- 決策粒度：目前僅有 accept/request-changes（接受/要求修改）兩種決策，對於「部分正確、只需小改」的 PR 可能過於粗糙。
- 評估範圍：SWE-Review-Bench 基於 SWE-bench Verified，主要涵蓋 Python 開源專案的 issue resolution（議題解決），對於其他語言、私有程式碼庫、或重視安全性、可維護性、程式碼風格的審查場景，尚需進一步驗證。
- 診斷品質上限：reviewer 的診斷能力仍受限於底層語言模型；對於需要深度領域知識或複雜設計權衡的 issue，可能仍會給出表面化建議。

#### 可重現性評估

##### 1. 已承諾釋出的資源

作者在文中明確表示將釋出 SWE-Review-Bench、SWE-Review-Traj 以及訓練好的 reviewer models（審查模型）。若這些承諾完整兌現，將大幅提升本研究的可重現性，並為後續 open reviewer training（開放審查者訓練）提供穩定基礎。由於目前仍是 preprint（預印本），具體下載連結、授權條款與版本控制資訊尚未在提供的上下文出現，實際開放程度仍需觀察正式釋出。

##### 2. 基於公開基礎設施

SWE-Review-Bench 建立在廣為使用的 SWE-bench Verified 之上，該基準的執行環境與評分腳本已公開，這降低了重現門檻。candidate PR（候選拉取請求）來自三個 PR generators（PR 生成器），只要作者提供這些生成器的設定、prompt（提示詞）與隨機種子，其他研究者就能重新產生相同或類似的輸入分布。

##### 3. 軌跡資料的價值

SWE-Review-Traj 包含 8,914 條 agentic review trajectories（智慧體審查軌跡），記錄了 reviewer agent（審查智慧體）與環境的互動過程。這類軌跡對於重現 SFT 結果至關重要，因為它不僅包含最終輸出，也包含中間探索步驟。若軌跡中涵蓋了使用的工具呼叫、檔案檢視順序與測試執行結果，將有助於訓練與除錯。

##### 4. 潛在重現挑戰

- 運算成本：agentic review（智慧體審查）涉及多次環境互動與模型呼叫，重現完整實驗需要可觀的 GPU/API 資源。
- 隨機性與環境差異：不同容器、依賴版本或檔案系統狀態可能導致軌跡不一致，需要嚴格的 containerized environment（容器化環境）與 deterministic seeds（確定性種子）。
- 修訂模型設定：RRR（修訂後解決率）與閉環實驗的結果高度依賴於用於 revision（修訂）的 coding agent（程式設計智慧體）。若作者未完整公開該 agent 的 prompt、工具與超參數，重現端到端數字會有困難。
- 授權與模型可用性：釋出的 reviewer models（審查模型）若採用開放權重，將有利於學術界跟進；但若部分實驗依賴 proprietary APIs（專有 API），則可能限制完全重現。

整體而言，SWE-Review 在資料與模型釋出上的承諾使其具備高可重現性潛力，但實際重現仍須等待正式釋出內容與詳細實作文件。

#### 未來研究方向

##### 1. 更緊密的 reviewer-coder 協作

目前的 generate-review-revise loop（生成-審查-修訂迴圈）雖已閉環，但 reviewer 與 coder 仍是分離角色。未來可探索多智慧體協作機制，例如讓 reviewer 在 coding agent 生成過程中即時介入、提供中間檢查，或讓多個 reviewer 進行 debate（辯論）後產出共識診斷，以減少單一 reviewer 的偏誤。

##### 2. 強化學習與回饋驅動訓練

現階段主要使用 SFT on SWE-Review-Traj。未來可引入 RL（reinforcement learning，強化學習）或 DPO（Direct Preference Optimization，直接偏好最佳化），把 RRR（修訂後解決率）或最終 issue 是否解決作為 reward signal（獎勵訊號），同時優化 reviewer 的決策與診斷品質，甚至反向優化 coding agent 的生成策略。

##### 3. 擴大軌跡資料的規模與多樣性

目前軌跡主要來自 SWE-bench Verified 的 Python 專案。未來可擴展到更多程式語言（如 Java、C++、JavaScript）、更大型的私有或企業級程式碼庫，以及包含人類開發者真實 PR 與 code review（程式碼審查）互動的資料，讓訓練出的 reviewer 更具泛化能力。

##### 4. 與 CI / 測試執行更深整合

雖然 SWE-Review 已會探索環境，但未來可更緊密地整合 CI pipeline（持續整合流程）、test failure logs（測試失敗日誌）與 coverage information（覆蓋率資訊），讓 reviewer 能自動把測試失敗轉化為具體的 structured diagnosis（結構化診斷），並主動偵測 regression（迴歸）與效能退化。

##### 5. 超越二元決策的細粒度審查

accept/request-changes（接受/要求修改）的二元決策在實務中過於簡化。未來可研究 partial accept（部分接受）、severity levels（嚴重程度分級）、或針對不同檔案給出不同建議的細粒度審查輸出，讓修訂過程更靈活。

##### 6. 人機協同與可解釋性

隨著 agentic code review（智慧體程式碼審查）進入實務，如何讓人類開發者信任並有效使用 AI reviewer 的建議變得重要。未來可研究 explainable review（可解釋審查）、互動式審查介面、以及 human-in-the-loop（人類在迴路中）的決策校準機制。

##### 7. 結合搜尋與規劃的測試時擴展

未來的 test-time scaling（測試時擴展）可結合 review-guided revision（審查引導修訂）與 search-based planning（基於搜尋的規劃）或 MCTS（Monte Carlo Tree Search，蒙地卡羅樹搜尋），在「診斷 → 提出修改 → 驗證」的空間中進行更有系統的搜尋，而不只是線性迭代。

##### 8. 安全性、穩健性與對抗防護

目前評估聚焦於 issue 是否解決，但未來需要加強對 adversarial patches（對抗性修補）、test overfitting（測試過擬合）、security vulnerabilities（安全漏洞）與 subtle regressions（細微迴歸）的偵測能力，讓 agentic review（智慧體審查）在真實部署中更可靠。

##### 9. 統一端到端訓練

最終，可朝完全統一的 generate-review-revise agent（生成-審查-修訂智慧體）邁進，讓單一模型學會在生成與審查角色間切換，並透過 self-critique（自我批判）與 self-revision（自我修訂）持續提升，進一步簡化部署架構並提高整體效率。

## 論文問答

**[Background & Motivation]**

**Q1：SWE-Review 主要想解決什麼問題？**
A：SWE-Review 針對的是現有 AI 程式設計智慧體在產生拉取請求後，整個流程仍處於「開環」狀態的問題：智慧體一次性生成候選 PR，卻缺乏系統化的審查、診斷與修訂機制。這導致我們無法可靠判斷該 PR 是否真正解決了原始 issue，也難以在發現缺陷時指導後續修正。透過引入智慧體程式碼審查，SWE-Review 把單向的 PR 生成轉變為持續迭代、可驗證的閉環議題解決流程。

**Q2：為什麼傳統的單輪固定上下文審查方法，難以正確評估 AI 生成的 issue-resolution patch？**
A：傳統方法通常只對 diff 做一次判斷，並假設 diff 本身已包含足夠證據，但 AI 生成的修補可能隱藏了真正的根因、修改了錯誤位置，或在編輯區塊之外引入迴歸問題。要正確判斷這類 patch，必須進行程式碼庫層級的推理，例如追蹤呼叫鏈、檢查相關實作、執行測試以驗證行為。單輪固定上下文審查無法動態取得這些非局部證據，因此容易在複雜或高風險的案例上出錯。

**Q3：智慧體程式碼審查為什麼在當前 AI 軟體工程生態中特別重要？**
A：隨著 AI 輔助 PR 提交量快速成長，自動化審查已成為確保程式碼品質的關鍵需求，但相較於 issue resolution 等其他軟體工程任務，程式碼審查能力與相關資源都較為不足。現有研究缺乏系統化的基準、可靠的評估指標、公開的訓練資料，以及端到端的閉環評估。SWE-Review 透過填補這些缺口，讓審查不僅是事後評論工具，而成為決定是否合併、如何修訂的核心機制。

---

**[Method & Innovation]**

**Q4：SWE-Review 的核心方法架構是什麼？**
A：SWE-Review 給定一個程式碼庫、一個 issue，以及一個由 AI 生成的候選 PR，會讓審查智慧體在可執行環境中主動探索儲存庫、收集證據。接著，智慧體輸出兩項結果：一個「接受／要求修改」的二元合併決策，以及一份結構化診斷報告，用於在要求修改時指導後續修訂。這種設計把審查視為需要主動互動的智慧體能力，而非僅對固定上下文做一次推論。

**Q5：相較於既有研究，SWE-Review 的關鍵創新有哪些？**
A：首先，它將程式碼審查建模為可探索環境的智慧體任務，突破了單輪固定上下文審查的限制。其次，它提出結構化診斷作為修訂回饋，使審查結果能直接驅動生成-審查-修訂迴圈。此外，它還建立了 SWE-Review-Bench 與 SWE-Review-Traj，分別提供端到端評估基準與大規模智慧體審查軌跡資料，填補了開放審查者訓練的資料稀缺缺口。

**Q6：為什麼 SWE-Review 選擇輸出「二元決策」加上「結構化診斷」，而不是單純的分數或評語？**
A：二元決策（accept / request changes）直接對應人類程式碼審查中是否合併的實務操作，便於整合到現有開發流程。結構化診斷則把「哪裡有問題」與「該如何修正」以機器可讀的形式呈現，讓下游修訂智慧體能據此執行具體修改。兩者結合，同時滿足了「過濾錯誤 PR」與「產生可執行修訂指引」的需求，真正實現閉環 issue resolution。

---

**[Experiments & Results]**

**Q7：論文提出了哪些基準與資料集來評估智慧體審查？**
A：論文提出 SWE-Review-Bench，包含從 500 個 SWE-bench Verified issue 衍生出的 1,384 個候選 PR，並由高、中、低三種品質的 PR 生成器產生，以涵蓋不同難度分佈。同時也建構了 SWE-Review-Traj，包含 8,914 條智慧體審查軌跡，用於支援開放審查者模型的訓練與分析。評估指標則包含完成率（CR）、決策準確率（DA）與修訂後解決率（RRR），分別衡量輸出可解析性、合併決策正確性，以及審查回饋對最終修補的實用性。

**Q8：實驗中最關鍵的結果是什麼？**
A：在生成-審查-修訂迴圈中，多個模型的解決率都持續提升：Qwen3-30B-A3B 從 27.5% 提升至 56.9%，Qwen3-Coder-30B-A3B 從 50.9% 提升至 68.8%，GLM-5 從 72.2% 提升至 75.4%。相較於單輪固定上下文審查，智慧體審查在決策準確率與修訂後解決率上都表現更好，尤其在需要非局部程式碼庫推理的困難案例上差距更明顯。此外，在 SWE-Review-Traj 上進行監督式微調，可讓 8B 審查者的完成率從約 4% 提升至 71–84%，決策準確率也從接近隨機提升至 67–72%。

**Q9：論文進行了哪些對比或消融實驗來驗證方法設計？**
A：論文將智慧體審查與單輪固定上下文審查基線進行比較，證明主動探索能顯著提升 DA 與 RRR。在訓練方面，混合 SWE-Review-Traj 與 issue-resolution 資料可讓直接解決率提升最高 5.6 個百分點，並使統一的生成-審查-修訂智慧體最終解決率提升最高 10.6 個百分點。在測試時擴展方面，訓練過的審查者在效果與效率上都優於專用驗證器，僅用 4 輪修訂就將解決率從 22.9% 提升至 38.4%。

**[Applications & Impact]**

**Q10：SWE-Review 在實務上可以應用在哪些場景？**
A：它可以部署為 AI 生成 PR 的預先閘道，自動過濾無法解決 issue 或可能引入迴歸的候選修補。對於被要求修改的 PR，系統能產生結構化回饋並驅動修訂智慧體進行多輪改善，減少人工反覆審查的負擔。在 CI/CD 流程中，這種閉環機制也能持續提升自動化 issue resolution 的可靠性與最終合併品質。

**Q11：若要將 SWE-Review 產品化，需要考慮哪些因素？**
A：首先需考量審查智慧體探索程式碼庫與執行測試所帶來的延遲與運算成本，並在效果與效率之間取得平衡。其次，自動接受 PR 涉及安全與責任歸屬問題，因此應保留人類監督與最終確認機制。此外，審查輸出必須穩定可解析，並能與現有開發工具鏈整合，才能順利落地於真實軟體開發流程。

**Q12：這項研究對整個 AI 軟體工程領域可能帶來什麼影響？**
A：SWE-Review 把智慧體程式碼審查定位為從一次性 PR 生成邁向閉環議題解決的關鍵機制，改變了過去只重視生成、不重視審查的研究取向。它釋出的基準、軌跡資料與模型，有助於學界與業界共同推進開放審查者訓練與評估。更廣泛地說，這項工作顯示審查軌跡本身也能提升 issue-resolution 模型，為未來統一化的生成-審查-修訂智慧體奠定基礎。

**[Limitations & Future]**

**Q13：論文可能有哪些已承認或潛在的限制？**
A：雖然提供的上下文未詳細列出所有限制，但可推知智慧體審查的表現高度依賴探索品質與環境回饋，若探索不完整仍可能誤判。目前評估主要基於 SWE-bench Verified 與三種 PR 生成器分佈，未必能完全代表所有真實開源專案的複雜性。此外，決策準確率與修訂後解決率雖能量化核心能力，但仍可能無法完整捕捉審查意見對人類開發者的可用性與可解釋性。

**Q14：智慧體審查在哪些情況下可能失敗？**
A：當 issue 需要深入的非局部程式碼庫推理、或缺陷隱藏在未編輯的相關模組中時，審查智慧體可能無法收集到足夠證據。若原始候選 PR 品質過低，結構化診斷可能過於籠統或誤導，導致後續修訂方向錯誤。另外，對於描述模糊、測試覆蓋不足或涉及複雜並發行為的 issue，審查決策也較容易出現假陽性或假陰性。

**Q15：未來可以朝哪些方向延伸這項研究？**
A：未來可以擴大 SWE-Review-Traj 的規模與多樣性，訓練更強大的開放審查者模型，並探索更長期的多輪審查與修訂策略。也可以結合人類回饋進行強化學習，使審查意見更符合真實開發者的偏好與專案規範。此外，將智慧體審查擴展到更多程式語言、更大規模程式碼庫，以及與人機協作流程深度整合，都是值得持續發展的方向。

## 實務應用指南

### 適用場景

1. **企業內部 AI 程式設計智慧體的 PR 閘道**  
   當團隊已導入 Cursor、Codex、Aider 等程式設計智慧體自動產出候選拉取請求時，可在合併前部署 SWE-Review 作為自動化審查閘道，判斷 PR 是否真正解決 issue、是否引入迴歸，並產出結構化診斷供智慧體修訂。

2. **開源專案的 AI / 人類貢獻者 PR 預篩**  
   面對大量外部貢獻或 AI 自動提交的 PR，維護者可先用審查智慧體進行第一輪篩選：標記「接受」或「要求修改」，並附上具體診斷，減少維護者人工審查負擔，同時避免低品質 patch 被合併。

3. **CI/CD 中的 repository-level 合併前驗證**  
   將智慧體程式碼審查整合至持續整合流程，在單元測試與靜態分析之外，進行動態的程式碼庫探索、呼叫鏈追蹤與相關實作檢查，補捉 diff 本身看不出來的根因錯誤。

4. **程式碼模型訓練資料的自動生成與過濾**  
   利用 SWE-Review-Traj 這類智慧體審查軌跡資料集，或自行採集審查軌跡，進行監督式微調，訓練可公開取得的開放審查者模型，並透過混合訓練同時提升 issue 解決模型與審查模型的能力。

5. **測試時擴展與多輪修訂的 verifier**  
   在 issue 解決代理的推論階段，以訓練過的審查智慧體作為 verifier，透過生成-審查-修訂迴圈在少數幾輪內篩選並修正候選 patch，以較低成本提升最終解決率。

### 實作前置條件

**資料條件**
- 真實或模擬的軟體 issue，以及對應的程式碼庫快照。
- 由 PR 生成器產出的候選拉取請求，最好涵蓋高、中、低不同品質分佈。
- 可執行的開發環境（如 SWE-bench 風格的 Docker / sandbox），能運行測試與重現 issue。
- 黃金標註（ground-truth）：issue 是否被解決、PR 是否應被接受，用於計算決策準確率與修訂後解決率。

**運算條件**
- 推論：至少能執行中大型語言模型（如 8B–30B+）的 GPU 或 API 配額，並支援多次工具呼叫與長上下文。
- 訓練：若欲微調開放審查者，需準備數千至數萬條智慧體審查軌跡，並具備 SFT / RL 所需的 GPU 叢集與儲存空間。
- 執行環境：每個審查任務需獨立 sandbox，避免並行測試互相干擾。

**技能條件**
- 熟悉程式碼庫層級的軟體工程評估流程（如 SWE-bench）。
- 具備智慧體腳手架開發經驗：工具設計（檔案檢視、搜尋、測試執行）、提示工程、錯誤處理。
- 能設計結構化輸出格式（JSON / XML）並解析最終審查。
- 了解模型訓練與評估指標：完成率、決策準確率、修訂後解決率。

---

### 實作步驟建議

1. **界定審查範圍與輸出格式**  
   決定審查智慧體的職責：僅做二元決策（接受 / 要求修改），或同時產出結構化診斷與建議修正。設計固定輸出欄位，例如 `decision`、`defect_description`、`suggested_fix`、`confidence`。

2. **建立可執行的程式碼庫環境**  
   為每個 issue 與候選 PR 建立隔離的 sandbox，確保能安裝依賴、執行測試、重現錯誤。環境一致性是計算修訂後解決率的基礎。

3. **設計審查智慧體的工具箱**  
   提供 repository-level 探索能力：檔案讀取、grep / 符號搜尋、呼叫鏈追蹤、相關實作檢視、測試執行。避免僅把 diff 與 issue 塞入單輪固定上下文。

4. **部署生成-審查-修訂迴圈**  
   第一輪由程式設計智慧體產生候選 PR；審查智慧體探索後輸出決策與診斷；若為「要求修改」，將結構化回饋傳回程式設計智慧體進行修訂，反覆數輪。

5. **建立評估儀表板**  
   追蹤三項核心指標：完成率（CR）、決策準確率（DA）、修訂後解決率（RRR）。同時記錄每輪修訂後的解決率變化，以觀察閉環效益。

6. **採集並整理審查軌跡資料**  
   記錄審查智慧體的完整互動過程（觀察、工具呼叫、中間推理、最終輸出），建立類似 SWE-Review-Traj 的資料集，供後續訓練與可解釋性分析。

7. **微調開放審查者模型**  
   以收集的軌跡進行監督式微調，提升小模型的完成率與決策準確率。可進一步與 issue 解決資料混合訓練，打造統一的生成-審查-修訂智慧體。

8. **整合至現有開發流程**  
   將審查智慧體包裝為 GitHub / GitLab bot 或 CI 檢查，設定門檻：只有審查通過或經人類確認後才允許合併。

9. **持續監控與迭代**  
   定期抽樣審查結果進行人工稽核，更新測試案例與工具，並隨著程式碼庫演進重新評估指標分佈，避免模型老化。

---

### 潛在風險與注意事項

- **誤接受與誤拒絕**  
  審查智慧體可能錯誤接受未解決 issue 的 PR，或錯誤拒絕正確 patch。建議保留人類在關鍵合併決策中的最終確認權，並對高風險變更提高門檻。

- **診斷幻覺與無效回饋**  
  智慧體可能產出看似合理但無法執行的診斷。可透過強制結構化輸出、要求引用程式碼庫證據、並以修訂後解決率作為回饋品質的間接驗證。

- **沙箱安全與成本**  
  自動執行候選 PR 的測試存在惡意程式碼風險，需使用隔離、無網路或受限網路的容器。同時，多輪工具呼叫與測試執行會顯著增加延遲與運算成本。

- **測試不穩定與環境差異**  
   flaky test 或環境差異會影響修訂後解決率的可靠性。建議固定依賴版本、使用確定性測試、並對失敗案例進行重試與人工標註。

- **資料污染與分佈偏移**  
  若訓練資料包含未來資訊或與評估集重疊，會高估表現。應嚴格切分訓練 / 測試 issue，並監控實際部署時的分佈偏移。

- **過度依賴自動審查**  
  自動審查不應取代程式碼風格、安全性與架構層面的人類判斷。建議將其定位為「輔助過濾與初步診斷」，而非最終品質保證。

---

### 與其他技術的整合建議

- **與版本控制平台整合**  
  透過 GitHub Actions / GitLab CI 或專用 bot，在 PR 建立時自動觸發審查智慧體，並將結構化診斷以評論形式回寫，方便人類審閱與智慧體修訂。

- **與現有靜態分析 / SAST 工具互補**  
  將 SWE-Review 置於 linter、型別檢查、安全掃描之後，專注於 issue 是否被正確解決、根因是否被觸及，而非重複檢查語法或常見漏洞。

- **與程式設計智慧體協同**  
  將審查智慧體作為 Aider、Codex、Devin 等生成器的下游 verifier，形成生成-審查-修訂迴圈；也可將審查軌跡餵回生成器訓練，提升兩端能力。

- **與 MLOps / 可觀測性平台整合**  
  記錄每次審查的決策、診斷、工具呼叫與最終結果，匯入追蹤系統（如 Weights & Biases、MLflow），便於分析錯誤模式與模型迭代。

- **與 issue 追蹤系統連動**  
  自動將審查結果（接受 / 要求修改）與對應 issue 狀態同步，並在要求修改時產出子任務或評論，協助專案管理。

### 給不同背景讀者的閱讀建議

**給初學者**  
建議先從圖 1 的閉環流程圖與「生成-審查-修訂迴圈」概念入手，理解為何一次性 PR 生成不夠、為何需要審查智慧體；接著閱讀適用場景與實作步驟，建立「審查不只是打分數，而是幫助修正」的直覺，技術細節可暫時略過。

**給 AI 工程師**  
重點關注審查智慧體的工具設計、結構化輸出、三項指標（CR / DA / RRR）的計算方式，以及 SWE-Review-Traj 的微調實驗；可參考論文中的基線比較與測試時擴展結果，思考如何將其整合進現有的程式設計智慧體 pipeline。

**給研究人員**  
建議深入閱讀 SWE-Review-Bench 的建構方式、PR 生成器的三種品質分佈、以及審查軌跡資料集的設計理念；可進一步探討開放審查者訓練、多輪修訂的強化學習、以及審查能力如何遷移至 issue 解決模型等研究方向。

**給產品經理**  
請聚焦於商業價值與風險權衡：自動審查能降低多少人工審查成本、提升多少合併品質、需要哪些基礎建設與資料準備；同時注意誤接受風險與人機協作流程設計，優先從低風險、重複性高的 PR 類別開始試點。
