## 摘要翻譯

許多真實世界的程式設計挑戰皆屬開放式程式設計問題（open-ended coding problems），且不存在已知的最佳解。然而，近期大型語言模型（LLMs）在程式設計上的進展，多集中於定義明確的任務，例如功能實作（feature implementation）、漏洞修復（bug fixing）與競技程式設計（competitive programming）。開放式程式設計（open-ended coding）仍是大型語言模型（LLMs）的弱點，主因在於開放式訓練問題稀少且建構成本高昂。本研究目標為大規模合成開放式程式設計問題（open-ended coding problems），以訓練更強大的程式設計大型語言模型（LLM coders）。我們提出 FrontierSmith，一套自動化系統，能從現有的封閉式程式設計問題（closed-ended coding problems）迭代演化出開放式問題。FrontierSmith 以競技程式設計（competitive programming）問題為起點，透過目標變更（goal changing）、輸出限制（output restriction）與輸入泛化（input generalization）生成候選開放式變體；接著使用量化的想法發散度指標（idea divergence metric），篩選出能引發不同解題者（solvers）產生真正多樣化解法的問題。隨後由智慧體（agents）為通過篩選的候選題目生成測試案例（test cases）與驗證器（verifiers）。在兩個開放式程式設計基準測試（open-ended coding benchmarks）FrontierCS 與 ALE-bench 上，使用我們合成的資料進行訓練，相較於基礎模型（base models）帶來顯著提升：Qwen3.5-9B 在 FrontierCS 上提升 +8.82 分，在 ALE-bench 上提升 +306.36（基於 Elo 評分（Elo rating）的表現）；Qwen3.5-27B 則分別提升 +12.12 與 +309.12。合成的問題亦使智慧體（agents）進行更多回合（turns）並使用更多 token，與人工策劃（human-curated）的題目相似，顯示封閉式種子題目（closed-ended seeds）可作為長期程式設計資料（long-horizon coding data）的實用起點。

### 核心貢獻（3～5點）
- 提出自動化系統 FrontierSmith，從現有封閉式程式設計問題迭代演化出開放式變體，緩解開放式訓練資料稀缺與建構成本高昂的問題。
- 設計三種問題變異策略——目標變更、輸出限制與輸入泛化——並引入量化的想法發散度指標，確保合成問題能激發不同解題者產生真正多樣化的解法。
- 利用智慧體自動生成測試案例與驗證器，建立可驗證、可規模化的開放式問題資料合成流程。
- 在 FrontierCS 與 ALE-bench 兩大基準測試上驗證，證明以合成資料訓練可顯著提升 Qwen3.5-9B 與 Qwen3.5-27B 的表現。
- 證明封閉式種子題目可作為長期程式設計資料的實用起點，且合成問題在互動回合數與 token 使用量上接近人工策劃水準。

### 適合對象
從事大型語言模型程式設計能力訓練、開放式問題生成、自動化資料合成與基準測試建構研究的學者與工程師；亦適合競技程式設計、軟體工程與啟發式競賽領域中，關注如何以大規模合成資料提升模型長期推理與互動能力的研究者與實務工作者。

## 深度分析

#### 方法論解析

FrontierSmith（自動化開放式題目合成系統）的核心貢獻在於建立一套可規模化的流程（Pipeline），將現有的大量封閉式程式設計問題（Closed-ended Coding Problem）轉化為開放式程式設計問題（Open-ended Coding Problem）。其整體架構遵循 Seed（種子題目）→ Mutate（變異）→ Filter（篩選）→ Build Env（環境建構）→ Output 的五階段流程。

在種子題目階段，系統以競技程式設計（Competitive Programming）平台如 Codeforces 與 LeetCode 的題目為起點。這類題目具備離散正確性（Discrete Correctness）與已驗證解答（Verified Solution），屬於典型的封閉式任務。FrontierSmith 透過三大變異軸線進行轉化：目標變更（Goal Changing）、輸出限制（Output Restriction）與輸入泛化（Input Generalization）。以文中範例為例，最小生成樹（Minimum Spanning Tree, MST）問題原本僅要求最小化總權重，經變異後加入最大度數限制（Max-degree Constraint），使原本可處理的（Tractable）多項式時間問題轉變為不存在已知全域最佳性（Global Optimality）保證的開放式問題。此類變異的本質在於移除最佳性證書（Certificate of Optimality），迫使解題者（Solver）必須採用多樣化的啟發式策略而非單一標準演算法。

為了避免生成的候選題目仍被單一策略主導，作者提出想法發散度指標（Idea Divergence Metric）作為篩選機制。該指標估計「兩位獨立解題者採用不同核心演算法」的機率，其估計分為兩個階段：首先利用大型語言模型（Large Language Model, LLM）對採樣解答（Sample Solution）進行成對比較（Pairwise Comparison），判斷策略是否相同；其次在測試案例（Test Case）與驗證器（Verifier）建構完成後，透過執行發散度（Execution Divergence）或測試分數相似度進行交叉驗證（Cross Validation）。最終僅保留發散度最高的前 N 個候選題目，確保問題確實具備連續性品質（Continuous Quality）與多樣化解法空間。

環境建構階段由多個智慧體（Agent）協作完成：測試案例生成智慧體負責產生輸入資料，驗證器智慧體則設計連續性評分（Continuous Score）函數，取代傳統的二元通過/失敗回饋（Binary Pass/Fail Feedback）。這些智慧體彼此交叉驗證，以確保評分機制的正確性與穩健性。值得注意的是，通過驗證的開放式題目會被加回種子題目池，使後續輪次能從更多樣化的起點繼續演化，形成迭代式的資料擴增循環。

#### 實驗數據解讀

作者使用 200 道合成題目，以 GRPO 演算法對 Qwen3.5-9B 與 Qwen3.5-27B 兩個基礎模型（Base Model）進行訓練。在開放式程式設計基準測試 FrontierCS 上，9B 模型獲得 +8.82 分的提升，27B 模型則提升 +12.12 分；在另一開放式程式設計基準測試 ALE-bench 上，兩個模型分別以 Elo 評分（Elo Rating）獲得 +306.36 與 +309.12 的增長。這些數據顯示，合成資料對不同規模的模型皆能帶來實質且顯著的效能增益，且較大的 27B 模型在 FrontierCS 上的絕對進步幅度更高，暗示合成資料能有效填補大模型的訓練缺口。

為了驗證開放式題型與真實獎勵訊號的必要性，作者設計了兩組對照實驗。相較於使用封閉式題目的 HardTests，FrontierSmith 資料在 FrontierCS / ALE-bench 上分別領先 +5.24 / +236.40；相較於隨機獎勵（Random Rewards）則領先 +7.58 / +256.76。這說明單純的封閉式訓練或雜訊獎勵皆無法達成同等效果，開放式題型設計與連續性評分兩者缺一不可。

消融實驗（Ablation）進一步證實篩選（Filtering）的重要性：移除想法發散度指標後，FrontierCS 上的表現下降 2.05 分。這表示並非所有變異產生的題目都具備同等的訓練價值，若未經篩選，劣質或偽開放式題目反而會稀釋訓練訊號。此外，想法發散度指標本身也被驗證可作為問題品質分類器，能夠有效區分真正的開放式問題與傳統競技程式設計題目。

在行為層面，合成題目展現出與人工策劃（Human-curated）題目相似的長期程式設計資料（Long-horizon Coding Data）特徵：智慧體在解題過程中使用更多的回合（Turn）與 Token，顯示這些題目確實能誘發更深度的推理與多步驟互動，而非單純的單輪程式生成。

#### 與現有研究的比較

現有程式資料合成研究幾乎完全聚焦於封閉式任務。在問題合成方面，AutoCode、SWE-smith、BugPilot、Endless Terminals、GASP 與 SGS 等系統能夠自動生成新題目；在測試與驗證基礎建設方面，HardTests、CodeContests+、rStar-Coder、SWE-rebench 與 R2E-Gym 專注於建構測試案例與二元驗證器；AgentCoder 與 CURE 則透過多智慧體交叉驗證確保程式與測試的正確性。然而，這些方法皆局限於二元通過/失敗回饋，無法處理開放式問題所需的連續性評分。

這種落差凸顯了資料不對稱（Data Asymmetry）的現況：封閉式任務在 Codeforces 與 LeetCode 等平台上擁有數十萬筆資料，並已催生出可驗證獎勵強化學習（Reinforcement Learning from Verifiable Rewards, RLVR）的顯著進展；相對地，最大的開放式基準測試 FrontierCS 僅約 240 題，ALE-bench 更只有約 40 題，且人工策劃成本極高。FrontierSmith 的獨特定位在於它是首個針對開放式程式設計問題進行大規模自動化合成的系統，並且巧妙地利用現有封閉式語料作為演化起點，而非從零建構。

儘管如此，本研究仍存在若干局限。首先，種子題目目前僅來自競技程式設計領域，雖然文中以雲端叢集排程（Cloud Cluster Scheduling）等真實開放式場景作為動機，但合成流程尚未直接擴展至這些工程領域。其次，200 道合成題目的規模相對於封閉式資料集仍屬小規模驗證。最後，實驗僅針對兩個基準測試與 Qwen3.5 系列模型，跨模型家族與跨領域的泛化性仍有待檢驗。

#### 可重現性評估

就現有文本判斷，FrontierSmith 目前以預印本（Preprint）形式發表，文中並未明確提及原始碼、合成資料集或微調後模型權重的公開釋出計畫。在可重現性（Reproducibility）方面，這構成首要的不確定性因素。

方法論層面上，該系統涉及多智慧體協作、LLM 驅動的成對比較，以及帶有隨機性的變異與採樣過程，這些皆使精確復現面臨挑戰。此外，GRPO 訓練的詳細超參數、變異提示詞（Prompt）的具體設計、以及 LLM 評判者的配置等關鍵細節，在提供的摘要與導論段落中尚未完整揭露。若缺乏這些資訊，其他研究者難以完全複製從種子題目到最終訓練資料的完整流程。

較為樂觀的是，FrontierSmith 的模組化流程降低了概念複現的門檻：各階段（變異、篩選、環境建構）功能獨立，且使用 Qwen3.5 等公開基礎模型與標準強化學習演算法。若作者未來能公開變異模板、想法發散度的計算程式碼，以及建構完成的 200 題資料集，將大幅提升社群驗證與延伸應用的可能性。

#### 未來研究方向

第一，規模與領域擴展是最直接的後續工作。將合成數量從 200 題提升至數千甚至數萬筆，並引入軟體工程（如 SWE-bench 風格的已驗證問題）、終端機環境（Terminal Environments）或編譯器最佳化等多元種子來源，可有效緩解資料不對稱。第二，變異策略可超越現有的三大軸線，探索多目標組合變異或語意層級的問題融合，以產生更複雜的開放式任務。

第三，想法發散度指標本身仍有精進空間。目前的兩階段估計（LLM 策略比對與執行發散度）可進一步整合為端到端可微分訊號，或引入人類專家判斷進行閾值校正，使其更貼近真實的問題品質。第四，在訓練範式上，可探索將封閉式題目的可驗證獎勵與開放式題目的連續性評分結合，發展混合式 RLVR 框架，讓模型同時學習嚴謹正確性與啟發式優化。

第五，長期程式設計資料的特性顯示，這類開放式題目非常適合用於訓練具備多回合互動能力的程式智慧體。未來研究可深入探討回合數（Turn）與 Token 使用量的增加是否與最終解題品質呈正相關，並據此設計更長視野（Long-horizon）的代理程式訓練流程。最後，將 FrontierSmith 的應用從競技程式設計擴展至真實世界的雲端叢集排程、資料庫查詢規劃或能源使用量（Energy Use）與尾端延遲（Tail Latency）等多目標權衡場景，將是驗證其實用價值的終極試金石。開源釋出整套流程與資料集，將是推動整個領域前進的關鍵一步。

## 論文問答

**Q1：為什麼開放式程式設計問題被視為現今大型語言模型在程式領域的主要弱點？**

A：現今的大型語言模型在封閉式程式設計任務上已達到卓越表現，例如能在競技程式設計中奪得金牌水準，並解決超過八成的 SWE-bench 已驗證問題，但這些任務大多具有離散正確性與可驗證解答。相對地，開放式程式設計任務缺乏在生產規模下可處理的最佳性證書，其解答品質是以連續性品質而非二元通過或失敗來衡量，例如雲端叢集排程中需在總完工時間、尾端延遲與能源使用量之間權衡。這種本質上的差異導致模型在 FrontierCS 等基準測試中，表現遠遜於人類專家，反映出資料不對稱所造成的訓練缺口。

**Q2：現有的自動化程式資料合成方法為何無法直接解決開放式問題的資料稀缺困境？**

A：近年來的程式資料合成研究，如 AutoCode、SWE-smith、HardTests 與 Endless Terminals 等，均專注於封閉式、二元正確性的設定，依賴可驗證獎勵強化學習來驅動模型進步。然而，開放式問題沒有已知的最優解，需要全新的題目表述方式，以及能夠在連續尺度上可靠評分解答品質的驗證器，而非僅輸出通過或失敗的二元回饋。因此，這些現有方法無法直接轉移至開放式領域，因為它們缺乏處理連續性評分、多樣化策略空間與非最優解環境的設計。

**Q3：大規模合成開放式程式設計問題為何對訓練更強的 LLM 程式設計能力至關重要？**

A：許多真實世界的程式設計挑戰本質上就是開放式的，例如雲端叢集排程中存在許多可行的工作到機器分配方案，但它們在利用率與延遲等指標上呈現連續性差異，且驗證全域最佳性在計算上不可行。如果模型僅在封閉式資料上訓練，它將無法學習如何在多目標優化與啟發式策略中進行權衡與決策，導致在實際工程場景中表現不佳。因此，建立可擴展的開放式問題合成系統，是縮小模型與人類專家在複雜、模糊且長期的程式設計任務中表現差距的關鍵。

**Q4：FrontierSmith 的核心運作流程包含哪些主要步驟？**

A：FrontierSmith 的流程始於將現有的封閉式競技程式設計題目作為種子題目，透過三個軸向進行變異：目標變更、輸出限制和輸入泛化，將具有已知高效解的題目轉化為精確解難以計算的開放式變體。接著，系統使用新穎的想法發散度指標來篩選能夠引發不同解題者採用真正多樣化核心策略的候選題目，避免題目被單一策略主導。最後，由獨立的智慧體系統為通過篩選的題目生成測試案例和驗證器，並透過交叉驗證確保正確性，最終將驗證過的題目加入種子池以供後續迭代演化。

**Q5：FrontierSmith 提出的「想法發散度指標」在方法論上有何關鍵創新？**

A：想法發散度指標的核心創新在於它能夠量化一道題目引發不同核心演算法策略的機率，從而提供一個可計算的信號來客觀衡量題目的開放性程度。該指標分兩階段運作：首先利用大型語言模型進行成對比較，判斷不同採樣解答是否屬於相同策略；接著在建立測試案例和驗證器後，透過執行發散度（即解答在測試案例上的分數相似度）進行驗證。這種結合語義層面策略比對與執行層面分數驗證的雙階段方法，不僅能有效篩選高品質的開放式題目，也能作為區分真正開放式問題與封閉式競技程式設計問題的分類器。

**Q6：FrontierSmith 在設計上為何選擇從競技程式設計題目出發，而非從頭生成全新的開放式題目？**

A：競技程式設計平台如 Codeforces 和 LeetCode 提供了數十萬道經過驗證的封閉式題目，形成了一個龐大且多樣化的種子語料庫，這些題目具備明確的問題結構和正確的基礎邏輯。從這些現有題目出發進行變異，可以確保生成的開放式變體在語法和語義上保持合理，同時大幅降低從頭設計全新優化目標和驗證器的工程成本與專家判斷負擔。此外，透過系統性地移除已知最佳解的方式進行變異，能夠將可處理的封閉問題轉化為需要啟發式策略的開放問題，並使種子池在每次迭代後愈發多樣化。

**Q7：論文在哪些基準測試上評估 FrontierSmith 合成資料的訓練效果，這些測試各有何特性？**

A：論文選用了 FrontierCS 和 ALE-bench 這兩個目前最大的開放式程式設計基準測試來進行評估。FrontierCS 專注於演算法類型的開放式任務，由人類專家對解答進行評分；ALE-bench 則是基於啟發式競賽的評估平台，採用 Elo 評分來比較相對實力。這兩個基準測試共同提供了對模型在演算法設計和實務啟發式策略上能力的全面檢驗，且兩者目前分別僅有約 240 題和 40 題人工策劃的題目，凸顯了資料稀缺的問題。

**Q8：使用 FrontierSmith 合成資料進行訓練帶來了哪些具體且顯著的效能提升？**

A：實驗結果顯示，以 GRPO 在 200 道合成題目上訓練後，Qwen3.5-9B 在 FrontierCS 上提升了 8.82 分，在 ALE-bench 的 Elo 評分表現上提升了 306.36 分；而 Qwen3.5-27B 則分別提升了 12.12 分和 309.12 分。與兩個對照組相比——包括封閉式的 HardTests 和隨機獎勵——FrontierSmith 的合成資料在 FrontierCS 和 ALE-bench 上均取得了顯著領先，證明了開放式題目表述和真實獎勵信號對於訓練效果的必要性。這些結果不僅顯示分數上的進步，也代表模型在處理長期、複雜程式設計任務的能力有了實質性的增長。

**Q9：消融實驗與對照比較揭示了 FrontierSmith 哪些關鍵組件的重要性？**

A：消融實驗特別凸顯了篩選機制的關鍵性：當移除基於想法發散度的篩選器後，模型在 FrontierCS 上的表現下降了 2.05 分，顯示並非所有變異產生的候選題目都具備同等的訓練價值，低發散度的題目無法有效促進模型學習。此外，與封閉式 HardTests 和隨機獎勵控制組的比較也構成重要的驗證，證明了單純使用困難的封閉式題目或無意義的獎勵信號，都無法達到開放式合成資料的訓練效果。這些結果共同說明，題目的開放式表述與高品質的連續性驗證信號兩者缺一不可。

**Q10：FrontierSmith 合成資料在實務應用場景中可能發揮什麼具體價值？**

A：在實務上，FrontierSmith 合成資料可用於訓練專門處理雲端叢集排程、資源分配和系統優化等真實世界開放式問題的程式設計智慧體。這些場景通常涉及多目標權衡和啟發式決策，無法透過傳統的封閉式程式設計訓練來充分準備，因為它們不存在單一最佳解。透過提供大規模且多樣化的開放式訓練資料，企業和開發者能夠建構出更能適應複雜生產環境、且表現更接近人類專家水準的程式輔助系統。

**Q11：若將 FrontierSmith 應用於產品開發與部署，有哪些實際的考量因素？**

A：在產品化過程中，必須確保合成題目的驗證器能夠穩定且公平地產生連續性評分，因為這直接影響強化學習的獎勵信號品質和模型收斂行為。此外，雖然系統能自動生成測試案例，但仍需監控種子池的多樣性，避免在多次迭代後出現題目同質化或變異失效的問題。最後，由於開放式問題會促使智慧體使用更多回合和 Token，產品在部署時需要仔細評估運算成本與延遲，確保互動體驗與推理開銷在可接受的商業範圍內。

**Q12：FrontierSmith 對整個 LLM 程式設計領域可能帶來什麼深遠影響？**

A：FrontierSmith 證明了封閉式題目可以作為開放式長期程式設計資料的有效起點，這為解決資料不對稱問題提供了一條可擴展的自動化路徑，無需完全依賴昂貴的人工策劃。該研究建立的想法發散度指標也為未來評估和篩選開放式問題提供了可量化的標準，有助於學術與產業社群定義何謂「高品質」的開放式程式設計題目。長遠來看，這項工作可能推動 LLM 從「正確性導向」的程式助手，演進為能夠在複雜、模糊的真實工程環境中進行權衡與優化的協作夥伴。

**Q13：論文承認 FrontierSmith 存在哪些主要限制？**

A：儘管 FrontierSmith 展現了自動化合成開放式問題的潛力，但它仍高度依賴高品質的封閉式種子題目作為起點，這意味著種子池本身的偏見和領域限制可能會傳遞到合成的開放式變體中。此外，想法發散度指標雖然有效，但其運作仍需要透過大型語言模型進行策略比對和後續的執行驗證，這在計算資源上並非完全輕量，可能限制其極大規模應用時的效率。最後，目前評估主要聚焦於 FrontierCS 和 ALE-bench 兩個基準測試，對於更廣泛的開放式領域（如創意程式設計或未定義規格的軟體架構設計）的泛化能力仍有待更多研究驗證。

**Q14：FrontierSmith 在哪些情況下可能會失敗或產生低品質的開放式題目？**

A：如果初始的封閉式種子題目本身過於簡單或結構單薄，變異後可能產生語意不通或策略空間過於狹隘的候選題目，即使通過發散度篩選也可能缺乏實質的訓練價值。另外，當變異操作未能有效移除已知最佳解時，題目可能仍被單一策略主導，導致解題者無論如何優化都收斂到相同的核心演算法，喪失開放性本質。在驗證器或測試案例生成失準的情況下，也可能出現連續性評分無法反映真實解答品質的問題，進而誤導強化學習的訓練方向。

**Q15：未來研究可以從哪些方向延伸 FrontierSmith 的工作？**

A：未來研究可以探索將 FrontierSmith 的框架擴展到非演算法類的開放式軟體工程任務，例如使用者需求模糊的功能設計或系統架構權衡，這些領域目前仍缺乏自動化資料合成方案。另一個方向是改進想法發散度指標，使其能夠在無需執行代碼的情況下更精確地預測策略多樣性，從而降低篩選過程中的計算成本。此外，結合人類回饋或專家介入的混合式迭代管線，或許能進一步提升合成題目的品質與真實性，讓自動生成的開放式資料更貼近實際產業需求與複雜的長期程式設計情境。

## 實務應用指南

### 適用場景

1. **競技程式設計與演算法教育平台**：自動生成具有多目標權衡的開放式優化題目，用於訓練學員或模型的策略彈性。例如將最小生成樹問題改寫為同時權衡總權重與最大度數限制，迫使解題者探索不同啟發式策略。
2. **大型語言模型的程式碼強化學習後訓練**：為基礎模型提供大規模開放式訓練資料，補足現有可驗證獎勵強化學習（RLVR）僅能使用二元通過／失敗回饋的缺口，提升模型在 FrontierCS、ALE-bench 等基準測試的連續性品質評分。
3. **雲端叢集排程與系統優化**：將封閉式排程問題轉化為多目標開放式問題（同時考量總完工時間、尾端延遲、能源使用量），用於訓練實際的資源調度智慧體，模擬生產環境中無法取得全域最佳性證書的決策場景。
4. **軟體工程啟發式工具開發**：產生沒有唯一最佳解的程式碼重構或設計模式問題，評估模型在真實開發場景中的權衡與取捨能力，超越傳統 SWE-bench 的二元正確性框架。

### 實作前置條件

- **資料**：至少數千題高品質封閉式種子題目（如 Codeforces、LeetCode 題庫），以及現有開放式基準測試（FrontierCS、ALE-bench）作為品質對齊與評估標準。
- **運算**：足夠的大型語言模型推論資源進行變異與採樣解答生成；安全的程式碼執行沙箱進行交叉驗證；以及用於 GRPO 強化學習的 GPU 叢集（論文中使用 Qwen3.5-9B／27B 規模）。
- **技術**：熟悉競技程式設計題目結構與圖論／組合優化概念；具備強化學習（RLVR／GRPO）與多智慧體系統實作經驗；能設計連續性評分函數（Verifier）並處理非唯一解的評估邏輯。

### 實作步驟建議

1. **建立種子題庫**：收集並清理高品質封閉式競技程式設計題目，確保題目涵蓋多種演算法領域。
2. **設計變異策略**：實作三種變異器——目標變更（改寫優化目標）、輸出限制（增加額外約束）、輸入泛化（放寬輸入規模使精確解不可行）。
3. **批量生成候選**：對種子題目應用變異，產生大量開放式候選題目。
4. **評估想法發散度**：針對每個候選題目，採樣多組解答，透過大型語言模型進行成對比較核心策略，計算想法發散度指標。
5. **篩選高品質題目**：保留發散度高的候選，淘汰存在單一主導策略的題目；此步驟對最終訓練效果至關重要。
6. **建構驗證環境**：部署測試案例生成智慧體與驗證智慧體，交叉驗證測試案例的正確性與連續性評分函數的合理性。
7. **迭代擴充種子池**：將驗證通過的開放式題目加入種子池，進行下一輪演化，逐步提升題目多樣性。
8. **模型訓練與驗證**：使用合成資料搭配 GRPO 進行強化學習，並在 FrontierCS 與 ALE-bench 等基準測試上驗證模型增益。

### 潛在風險與注意事項

- **隱藏最優解風險**：變異後的題目可能仍存在未被發現的精確演算法，導致模型學到捷徑而非啟發式策略。必須嚴格執行想法發散度篩選，並輔以人工抽查。
- **驗證智慧體出錯**：測試案例或連續性評分函數若存在錯誤，會直接導致強化學習訓練發散或獎勵駭入（reward hacking）。交叉驗證機制與人類專家抽樣審核不可省略。
- **領域偏移**：從競技程式設計變異而來的題目可能過度偏重演算法結構，與真實軟體工程或系統優化場景的分布不一致。建議定期比對目標應用場景的任務分布。
- **計算與 Token 成本**：大規模採樣解答、成對比較與多智慧體交叉驗證消耗大量 Token。需設定預算上限、建立快取機制，並優先在高發散度候選上投入資源。

### 與其他技術的整合建議

- **與現有 RLVR 框架整合**：將 FrontierSmith 作為資料合成模組，餵入現有的可驗證獎勵強化學習流程（如 Open-Reasoner-Zero、DeepSeek-R1 的程式碼訓練管線），直接替代或擴充現有的二元正確性資料集。
- **與 SWE-bench 生態系整合**：把開放式變異邏輯應用於軟體工程任務，將功能實作或漏洞修復任務轉化為多目標權衡問題（例如同時考量效能、可讀性與相容性），補足現有二元正確性任務的不足。
- **與多智慧體程式碼評審系統整合**：利用現有的 AgentCoder、CURE 等交叉驗證機制強化 FrontierSmith 的測試案例與驗證器生成，提升環境建構的可靠性。
- **與學習管理系統（LMS）整合**：將合成題目匯入教育平台，蒐集人類學習者的解答與回饋，形成「合成生成 → 人類驗證 → 迭代演化」的閉環，持續改善題目品質與難度校準。

### 給不同背景讀者的閱讀建議

- **初學者**：建議先釐清「封閉式問題」（有標準答案）與「開放式問題」（無唯一最佳解）的核心差異，將 FrontierSmith 理解為一台「自動出題機」。閱讀時可聚焦於圖一的流程圖與實驗結果段落，暫時跳過 GRPO 與發散度指標的數學推導，重點掌握「變異→篩選→驗證」的三階段概念。
- **AI 工程師**：請深入研讀變異策略的實作細節（目標變更、輸出限制、輸入泛化）與想法發散度指標的計算方式，特別留意論文中以大型語言模型進行成對比較與以執行發散度進行交叉驗證的兩階段設計。實作時應優先確保驗證智慧體的交叉驗證管線穩定，再接入現有的強化學習訓練框架。
- **研究人員**：建議從想法發散度指標的有效性與理論基礎切入，思考該指標能否推廣至數學證明生成、機器人規劃或創意寫作等其他開放式領域。此外，可深入檢視論文中關於長期互動行為（更多回合、更多 Token、更多工具呼叫）的實證分析，探討開放式問題是否為催生長脈絡推理能力的關鍵資料型態。
- **產品經理**：請將重點放在商業應用場景與成本效益分析。相較於人工策劃每題需耗費大量專家時間，FrontierSmith 提供了規模化生成開放式題目的路徑。評估時請同時考量開放式題目對使用者體驗的影響——例如智慧體需要更長的推理鏈與更多工具呼叫——並據此規劃運算資源與產品介面的設計。
