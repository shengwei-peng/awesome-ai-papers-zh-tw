## 摘要翻譯

測試時擴展（Test-time scaling）可透過生成並結合多個候選回應（candidate responses）來提升大型語言模型（Large Language Model, LLM）的推理表現。在基於取樣的方法（sampling-based methods）中，推理預算（inference budget）通常以生成候選數量 N 來描述。然而，N 僅指出生成了多少候選，而非它們如何被執行。相同的候選預算（candidate budget）可以透過一次批次生成呼叫（batched generation call）產生，也可以拆分為數個批次大小（batch size）較小的序列呼叫（sequential calls）。我們首先使用 Phi-3-mini 與 Qwen2.5-1.5B，在 500 個 GSM8K 提示（prompts）上研究增加 N 對推理準確率（reasoning accuracy）的影響。正如預期，將 N 從 1 增加到 8，Phi-3-mini 的準確率提升了 8.4 個百分點，Qwen2.5-1.5B 則提升了 18.4 個百分點。然而，單看準確率無法反映使用較大候選預算所帶來的系統成本（systems cost）。因此我們固定 N = 8，並比較四種生成排程（generation schedules）：1×8、2×4、4×2 與 8×1，其中 a×b 表示 a 次生成呼叫（generation calls），每次呼叫產生 b 個候選。我們在保持總候選數量固定的情況下，測量延遲（latency）、吞吐量（throughput）、GPU 小時（GPU-hours）與 GPU 裝置總能耗（gross GPU-device energy）。在 A100 GPU 上，八次序列呼叫的 GPU 裝置總能耗約為一次批次生成呼叫（含八個候選）的 4.64–4.86 倍；其 P95 延遲（P95 latency）則為後者的 5.77–6.12 倍。同樣的模式也可見於每個模型各自在三個獨立排程的 A100 節點上，以及短輸出工作負載（short-output workload）的 SciQ/V100 實驗中。這些結果顯示，僅有候選數量並不足以描述多候選測試時擴展（multi-candidate test-time scaling）的系統成本。當候選彼此獨立且記憶體允許時，較少的生成呼叫次數搭配較大的批次大小會更有效率。因此，評估時不僅應報告候選數量與準確率，亦應報告生成排程與 GPU 層級系統指標（GPU-level systems metrics）。

### 核心貢獻（3～5點）
- 指出「候選數量 N」不足以完整刻畫測試時擴展的系統成本，同樣的候選預算可透過不同生成排程執行，造成顯著的能耗與延遲差異。
- 在固定 N = 8 的情況下，系統性比較四種生成排程（1×8、2×4、4×2、8×1），證明批次化呼叫遠比序列呼叫更具系統效率。
- 在 A100 GPU 上量化顯示，八次序列呼叫的總能耗為一次批次呼叫的 4.64–4.86 倍，P95 延遲則為 5.77–6.12 倍。
- 驗證上述發現具有跨節點與跨工作負載的再現性，包括三個獨立排程的 A100 節點，以及短輸出 SciQ/V100 實驗。
- 提出評估建議：未來多候選測試時擴展研究應同時報告候選數量、準確率、生成排程與 GPU 層級系統指標。

### 適合對象
本論文適合對大型語言模型推論系統、測試時擴展機制，以及 AI 系統能效與部署成本感興趣的研究人員與工程師。特別推薦給正在設計或評估取樣式推理方法（如 self-consistency、best-of-N）、進行 LLM 推論服務（serving）優化，以及關注綠色 AI 與資料中心能耗議題的讀者。對於需要將多候選生成策略實際部署於生產環境的系統工程師，本文的實證數據與評估建議尤具參考價值。

## 深度分析

#### 方法論解析

本文的核心方法論在於將 **Test-time scaling（測試時擴展）** 中的 **candidate count（候選數量）** \(N\) 與 **candidate-generation schedule（候選生成排程）** \(S=(b_1,\dots,b_C)\) 明確區分開來。其中 \(N=\sum_{c=1}^C b_c\) 表示每個提示所生成的候選回應總數，而 \(C\) 則是實際發出的 **generation call（生成呼叫）** 次數，\(b_c\) 為第 \(c\) 次呼叫的 **batch size（批次大小）**。透過這種形式化，作者得以在固定 \(N=8\) 的前提下，比較四種執行排程：\(1\times 8\)、\(2\times 4\)、\(4\times 2\) 與 \(8\times 1\)。這四種排程在演算法層面使用了完全相同的候選預算與聚合規則，但在系統層面卻對應到不同的呼叫次數與批次大小。

實驗設計採用兩階段策略。第一階段探討 \(N\) 從 1 增加到 8 對 **reasoning accuracy（推理準確率）** 的影響，使用 **Phi-3-mini** 與 **Qwen2.5-1.5B** 兩個輕量級 **LLM（大型語言模型）**，在 500 筆 **GSM8K** 提示上進行評估。第二階段則固定 \(N=8\)，系統性地量測不同排程下的 **latency（延遲）**、**throughput（吞吐量）**、**GPU-hours（GPU 小時）**、**utilization（利用率）** 與 **gross GPU-device energy（GPU 裝置總能耗）**。為了排除硬體節點差異的影響，作者還在三個獨立調度的 **A100 GPU** 節點上重複實驗，並以 **SciQ** 資料集與 **V100 GPU** 進行短輸出工作負載的驗證。

此方法論的優點在於能夠將「演算法收益」與「系統成本」解耦：第一階段確認增加候選數確實能提升準確率；第二階段則證明，在候選數相同的情況下，執行方式會顯著影響延遲與能耗。然而，此設計也建立在幾項假設之上：候選之間相互獨立、記憶體容量允許較大批次、且所有呼叫都在同一張已分配的 GPU 上序列執行。這些假設在 **HPC（高效能運算）** 的 **batch job（批次作業）** 場景中相當常見，但在連續服務或記憶體受限的部署環境中，結論可能需要進一步調整。

#### 實驗數據解讀

在準確率方面，將 \(N\) 從 1 提升到 8 可使 Phi-3-mini 在 GSM8K 上提升 8.4 個百分點，Qwen2.5-1.5B 則提升 18.4 個百分點。這再次驗證了 **multi-candidate test-time scaling（多候選測試時擴展）** 的有效性，並顯示不同模型對額外候選的敏感度差異甚大：Qwen2.5-1.5B 似乎更能從多樣化取樣中獲益。值得注意的是，在固定 \(N=8\) 且使用相同聚合規則的前提下，不同排程理論上應產生相同的推理準確率，因為候選總數與其聯合分佈並未改變；實驗的關鍵發現因此集中在系統成本。

在系統成本方面，數據呈現非常明確的趨勢：\(8\times 1\) 排程（八次序列呼叫，每次一個候選）相較於 \(1\times 8\) 排程（一次批次呼叫，八個候選），在 A100 上多消耗 4.64–4.86 倍的 **gross GPU-device energy（GPU 裝置總能耗）**，且 **P95 latency（P95 延遲）** 高達 5.77–6.12 倍。這個結果可以從以下幾個角度理解：

1. **GPU 利用率（utilization）**：單次批次呼叫能同時啟動多個候選的矩陣運算，使 GPU 計算單元更充分地被利用；相對地，每次只生成一個候選的序列呼叫會讓大量計算資源閒置。
2. **固定開銷攤銷**：每次 generation call 都伴隨核心啟動、權重載入與記憶體調度的固定成本。批次呼叫可將這些成本攤銷到八個候選上，而序列呼叫則重複支付。
3. **能耗與時間的關係**：雖然批次呼叫的瞬間功耗可能較高，但其完成時間顯著縮短，因此總能耗反而較低；序列呼叫讓 GPU 長時間處於活躍狀態，累積更多能量消耗。
4. **延遲的非線性**：P95 延遲的倍率約為 5.8–6.1 倍，低於直覺上的 8 倍，這反映單一候選呼叫的延遲雖短，但八次呼叫的總和仍遠大於一次批次呼叫的延遲，顯示批次化具有次線性的延遲擴展特性。

此外，作者在三個獨立 A100 節點以及 SciQ/V100 的短輸出實驗中都觀察到一致模式，這增強了結論的穩健性。整體而言，實驗數據強有力地說明：僅報告 **sample count（樣本數）** 或 **candidate budget（候選預算）** 無法完整描述多候選推理的系統成本，**generation schedule（生成排程）** 與 **GPU-level（GPU 層級）** 系統指標同樣不可或缺。

#### 與現有研究的比較

過往的 **test-time scaling（測試時擴展）** 研究大多聚焦於「要生成多少候選」以及「如何選擇或聚合候選」，例如 **self-consistency（自一致性）**、**best-of-N（N 選最佳）**、各種 **verifier（驗證器）** 與 **reward model（獎勵模型）** 的設計，或是自適應停止規則。這些工作雖然豐富了演算法層面的理解，卻鮮少報告 **calls per query（每查詢呼叫次數）**、**candidates per call（每次呼叫候選數）**、硬體平台或實測能耗。本文的 Table I 清楚指出，包括 Self-Consistency、Adaptive-Consistency、Universal Self-Consistency、Large Language Monkeys、Scaling Test-Time Compute 與 Difficulty-Adaptive SC 在內的代表性研究，都未完整揭露這些系統層面資訊。

另一方面，**serving（推論服務）** 領域如 ORCA、vLLM、Sarathi-Serve 等系統，已經深入研究批次化、排程與記憶體管理對推理效率的影響，但這些研究通常針對 **continuous serving workload（連續服務工作負載）**，而非多候選推理這種具有明確候選預算的 **batch job（批次作業）** 情境。本文的貢獻在於將兩個領域銜接起來：它不僅提出候選生成排程的形式化定義，還透過實測能量與效能指標，凸顯在測試時擴展研究中報告執行細節的必要性。

儘管如此，本文仍有若干限制。首先，實驗僅固定 \(N=8\)，對於更大候選預算（例如 32、64、256）下的能量與延遲倍率是否維持相同趨勢，仍待驗證。其次，研究對象為輕量模型與相對簡短的數學/科學問答資料集，尚未涵蓋長文本生成或大型模型（如 70B 以上）在記憶體壓力下的行為。第三，實驗假設候選獨立且記憶體充足，未探討 **KV-cache（鍵值快取）** 限制、動態批次或中間分析所帶來的額外成本。最後，**gross GPU-device energy（GPU 裝置總能耗）** 僅涵蓋 GPU 裝置本身，未包含 CPU、主記憶體、散熱與互連等全系統能耗，也未涉及碳足跡。

#### 可重現性評估

從資料與模型的可取得性來看，本研究具備良好的重現基礎：**Phi-3-mini** 與 **Qwen2.5-1.5B** 均為公開模型，**GSM8K** 與 **SciQ** 也是公開資料集，硬體平台 A100/V100 亦為常見設備。然而，根據目前提供的上下文，作者並未明確提及是否釋出原始碼、量測腳本或完整的實驗配置檔，這對 **reproduce（重現）** 實驗結果構成一定障礙。

要完整重現本研究，至少需要以下資訊：

- 各排程的具體實作方式（例如是否使用 Hugging Face 的 `generate`、vLLM、或其他推理框架）；
- **deterministic seeding（確定性種子設定）**、溫度、top-p 等取樣超參數；
- 聚合規則的細節（例如是否採用多數決的自一致性）；
- 能量量測工具與取樣頻率（例如 `nvidia-smi`、`nvml`、或外部電表）；
- GPU 驅動版本、CUDA 版本、批次化與記憶體管理設定；
- 原始數據與統計方法，特別是 P95 latency 的計算方式。

若作者能釋出程式碼與量測腳本，本研究的可重現性將可達到「高」；在僅有論文描述的情況下，可重現性約為「中等」，因為公開模型與資料集降低了門檻，但系統層面的實作細節與能量量測方法仍有不確定性。

#### 未來研究方向

1. **擴展候選預算與模型規模**：在 \(N=32, 64, 256\) 乃至更大的設定下，驗證能量與延遲倍率是否隨 \(N\) 呈現可預測的變化，並納入 7B、70B 等級模型。
2. **記憶體與 KV-cache 限制下的排程**：研究當批次大小受 GPU 記憶體限制時，如何設計分塊、重組或動態批次策略，以在準確率與能耗之間取得平衡。
3. **自適應與動態生成排程**：根據提示難度、中間置信度或 verifier 回饋，動態決定每次呼叫的候選數與呼叫次數，而非固定 \(N\)。
4. **準確率–延遲–能耗的聯合最佳化**：建立 Pareto frontier（帕雷托前沿），探討在不同延遲與能耗預算下，應選擇何種 \(N\) 與排程組合。
5. **全系統能耗與永續性指標**：將量測範圍從 GPU 裝置能耗擴展到 CPU、記憶體、散熱與資料中心層級，並計算碳足跡。
6. **異質叢集與多 GPU 排程**：研究在多節點、多 GPU 或不同世代 GPU 混合環境中，如何排程多候選推理以提升整體效率。
7. **結合驗證器與獎勵模型的成本分析**：將 best-of-N、學習型 verifier 或 **reward model（獎勵模型）** 的推理成本納入排程考量。
8. **理論模型與預測工具**：建立能量與延遲的解析或經驗模型，讓研究者在實驗前即可預估不同排程的系統成本。
9. **連續服務與批次作業的統一排程**：針對 **continuous serving workload（連續服務工作負載）** 設計能同時服務多使用者請求與多候選生成的排程演算法。
10. **標準化評測與報告規範**：推動社群在發表 test-time scaling 研究時，強制報告 \(N\)、\(C\)、每呼叫候選數、硬體平台、能量與延遲等系統指標，以提升可比較性與可重現性。

## 論文問答

**Q1：這篇論文核心要解決的問題是什麼？為什麼僅用候選數量 N 不足以描述推理成本？**

A：這篇論文指出，在多候選測試時擴展中，N 只告訴我們產生了多少個候選回應，卻沒有說明這些候選是如何被執行的。同樣的候選預算可以用一次批次生成呼叫完成，也可以拆成多次序列呼叫，每次使用較小的批次大小。這兩種執行方式在延遲、吞吐量、GPU 小時、利用率與能耗上會有巨大差異，因此單靠候選數量無法完整描述系統成本。

**Q2：現有的測試時擴展研究為何無法充分刻畫系統成本？**

A：代表性的研究通常只報告候選預算 N，卻經常遺漏每查詢呼叫次數、每次呼叫候選數、硬體平台以及實測能耗等資訊。這種報告缺口使得不同研究之間的結果難以重現與比較。論文因此強調，必須將生成排程形式化為 S = (b₁, ..., b_C)，才能完整描述多候選推理工作負載。

**Q3：這個問題為何在高效能運算環境中特別重要？**

A：在 HPC 環境中，大型語言模型推理常以有限批次作業的形式執行，而非連續服務工作負載。候選生成可能因日誌記錄、確定性種子設定、控制邏輯或中間分析而被拆成多次呼叫。若忽略這種排程方式，就會低估實際的延遲與能耗，導致系統成本被嚴重低估。

**Q4：論文如何形式化候選生成策略？**

A：論文將生成排程定義為 S = (b₁, ..., b_C)，其中 C 是生成呼叫次數，b_c 是第 c 次呼叫產生的候選數，且所有 b_c 總和等於 N。這個形式化把「產生多少候選」與「如何將候選分組執行」分開來。在固定 N = 8 的情況下，作者比較了 1×8、2×4、4×2 與 8×1 四種排程。

**Q5：與過去測試時擴展研究相比，本文的核心創新是什麼？**

A：過去研究主要關注要產生多少候選，或如何從中挑選最佳答案；本文則固定候選總數，研究不同分組執行方式對系統指標的影響。作者首次將 GPU 層級的效能與能耗測量引入多候選測試時擴展的評估中。此外，論文還提出了多候選推理實驗的最低報告建議。

**Q6：實驗設計上有哪些關鍵選擇？**

A：作者先讓批次化的 N 從 1 增加到 8，確認推理準確率的提升；接著固定 N = 8，比較四種生成排程。他們測量了延遲、吞吐量、GPU 小時、利用率與 GPU 裝置總能耗。實驗在 A100 與 V100 GPU 上進行，並使用了 Phi-3-mini、Qwen2.5-1.5B 以及 GSM8K、SciQ 資料集。

**Q7：實驗使用了哪些模型與資料集？**

A：主要實驗使用 Phi-3-mini 與 Qwen2.5-1.5B，在 500 筆 GSM8K 提示上進行評估。此外，作者也在 V100 GPU 上進行了短輸出工作負載 SciQ 的個案研究。為了確認穩健性，每個模型都在三個獨立排程的 A100 節點上重複測量。

**Q8：論文有哪些關鍵量化結果？**

A：當 N 從 1 增加到 8 時，Phi-3-mini 的準確率提升 8.4 個百分點，Qwen2.5-1.5B 提升 18.4 個百分點。在固定 N = 8 下，8×1 的序列排程比 1×8 的批次排程多消耗 4.64–4.86 倍的 GPU 裝置總能耗，且 P95 延遲高出 5.77–6.12 倍。整體而言，只要候選彼此獨立且記憶體允許，較少呼叫次數搭配較大批次大小會更有效率。

**Q9：作者做了哪些穩健性檢查或消融實驗？**

A：他們在三個獨立排程的 A100 節點上對每個模型重複實驗，確認結果一致。同時也在 V100 GPU 上進行了 SciQ 短輸出實驗，發現序列呼叫同樣遠比批次呼叫昂貴。這些結果顯示，生成排程對系統成本的影響在不同 GPU、模型與輸出長度下都相當穩定。

**Q10：實務上應如何選擇生成排程？**

A：當候選彼此獨立且 GPU 記憶體允許時，應盡量減少生成呼叫次數、放大批次大小，以提升利用率並降低延遲與能耗。只有在需要確定性種子、日誌記錄或中間控制邏輯時，才將生成拆成多次序列呼叫。無論如何，評估時都應同時報告排程方式與 GPU 層級系統指標，而非僅呈現準確率。

**Q11：這對 LLM 推論服務平台的產品設計有何啟示？**

A：推論服務平台應提供批次化控制選項，並記錄每筆查詢的呼叫結構，而不是只顯示總候選數。產品團隊在設計自一致性或多候選生成功能時，必須把能耗成本與延遲尾部納入考量。透過優化生成排程，可以在不改變模型準確率的前提下顯著降低營運成本。

**Q12：這項研究對測試時擴展領域有什麼更廣泛的影響？**

A：它將評估焦點從單純的準確率擴展到準確率加系統成本，促使研究更重視可重現性與效率。未來的擴展定律與方法比較，應納入生成排程與能耗等指標。這也可能改變學術論文與基準測試對推理預算的報告方式。

**Q13：論文有哪些已承認或隱含的限制？**

A：研究固定 N = 8，且主要使用相對較小的模型，結果在更大模型、更長輸出或不同聚合方法下可能有所不同。論文假設候選彼此獨立且記憶體足以批次化，若存在相依性或記憶體限制，則序列呼叫可能無法避免。此外，測量的是 GPU 裝置總能耗，尚未涵蓋整機或碳足跡層級的成本。

**Q14：在哪些情況下，較大批次不一定比較好？**

A：如果候選生成需要中間回饋、自適應推理，或受 KV 快取限制而無法安全批次化，則序列呼叫可能是必要的。過大的批次也可能超出 GPU 記憶體，或使單次呼叫延遲過高。在這些情況下，排程優化必須在記憶體、延遲與正確性之間取得平衡。

**Q15：這項研究指出了哪些未來方向？**

A：未來可以將研究擴展到更大模型、動態選擇批次大小的自適應排程，以及整機能耗與碳排放的完整核算。另一個方向是與推論服務系統共同設計，根據準確率目標自動選擇最有效率的排程。將生成排程納入擴展定律與標準基準，將有助於提升整個領域的可重現性與可比較性。

## 實務應用指南

### 適用場景

1. **HPC 批次推理作業**  
   在高效能運算中心以批次作業形式執行 LLM 推理時，候選生成排程會直接影響 GPU 小時與能耗。例如科學模擬後處理、大規模資料標註或評測基準（benchmark）跑分，都應把 `1×8`、`2×4` 等排程納入實驗設計，避免把同樣的候選預算拆成過多序列呼叫。

2. **需要 Self-Consistency / Best-of-N 的推理服務**  
   數學解題、程式合成或合規文件生成等應用，常透過多候選投票或驗證器挑選最佳答案。若服務層把 N 個候選拆成多次小批次呼叫，會顯著增加 P95 延遲與 GPU 裝置總能耗；在記憶體允許下應優先使用較大批次。

3. **能耗敏感或碳排預算有限的部署**  
   資料中心有電力或碳排上限時，單純增加候選數量 N 會讓成本線性甚至超線性上升。透過固定 N 並調整生成排程，可在維持準確率的前提下降低 4–5 倍以上的能耗。

4. **需要確定性種子或中間分析的流程**  
   當業務需要每個候選獨立種子、逐一生成日誌，或在中間步驟做控制邏輯與中間分析時，容易傾向 `8×1` 序列呼叫。此時應權衡可解釋性/除錯需求與系統成本，並考慮部分批次化（如 `2×4`）作為折衷。

5. **短輸出問答系統的邊緣/私有部署**  
   類似 SciQ 的科學問答工作負載，輸出短、批次效益明顯。在 V100 等較舊 GPU 上，仍觀察到批次呼叫比序列呼叫更高效，適合教育、企業內部知識問答等場景。

### 實作前置條件

**資料條件**
- 已準備好需要多候選推理的提示資料集，例如 GSM8K 風格的數學題、SciQ 風格的科學問答，或自有領域問答對。
- 每筆提示的輸出長度分布應可預估，因為長輸出會放大批次化效益；短輸出工作負載仍需驗證。
- 若使用 Self-Consistency，需有穩定的答案萃取規則（answer parser）與多數決邏輯。

**運算條件**
- 至少一張 NVIDIA A100 或 V100 等資料中心 GPU；若要比較不同節點，建議準備 2–3 台獨立排程的節點以驗證穩健性。
- 需能測量 GPU 裝置總能耗（gross GPU-device energy），例如透過 `nvidia-smi` 的功率取樣、DCGM、PyJoules 或機櫃級電表。
- 記憶體需足以容納目標批次大小；本文建議在候選獨立且記憶體允許下使用較大批次。

**技能條件**
- 熟悉 LLM 推理框架（如 vLLM、Hugging Face Transformers、TGI）與批次推理設定。
- 具備基準測試與效能分析能力，能測量延遲、吞吐量、GPU 利用率與能耗。
- 了解 Self-Consistency 或 Best-of-N 等測試時擴展方法的基本原理。

---

### 實作步驟建議

1. **定義候選預算與生成排程**  
   先決定總候選數量 N，再列出要評估的生成排程 S = (b₁, ..., b_C)，例如 N = 8 時比較 `1×8`、`2×4`、`4×2`、`8×1`。在實驗報告中務必同時標示「每查詢呼叫次數」與「每次呼叫候選數」。

2. **建立可重現的推理腳本**  
   使用同一模型、同一組提示、同一個答案萃取與聚合規則。固定溫度、top-p、最大生成长度等超參數；若需要確定性種子，請在呼叫層級記錄種子，而非預設拆成單一候選呼叫。

3. **測量準確率基線**  
   先從 N = 1 到 N = 8 觀察準確率變化，確認多候選確實帶來效益。例如 Phi-3-mini 在 GSM8K 上提升 8.4 百分點、Qwen2.5-1.5B 提升 18.4 百分點。

4. **固定 N 進行系統層比較**  
   在 N = 8 下，分別執行四種排程，記錄：
   - 端對端延遲與 P95 延遲
   - 吞吐量（提示數 / 秒或候選數 / 秒）
   - GPU 利用率
   - GPU 小時
   - GPU 裝置總能耗

5. **分析批次化效益與記憶體上限**  
   比較 `1×8` 與 `8×1` 的差距。若記憶體允許且候選獨立，應選擇較少生成呼叫、較大批次大小的排程。若出現記憶體不足或 KV cache 限制，再逐步降低每次呼叫候選數。

6. **跨節點與跨工作負載驗證**  
   在不同 GPU 節點與短輸出工作負載（如 SciQ）上重複實驗，確認結論穩健，而非單一節點的偶然結果。

7. **部署與監控**  
   將選定的排程整合進推論服務或批次作業排程器，並在生產環境持續監控 P95 延遲、GPU 利用率與能耗。把「生成排程」納入實驗報告與模型卡（model card）的必要欄位。

---

### 潛在風險與注意事項

- **只報告 N 而忽略排程**  
  許多研究僅標示候選數量 N，導致系統成本無法重現與比較。應同時報告呼叫次數、每次呼叫候選數、GPU 型號、批次大小與能耗指標。

- **過度序列化造成隱性成本**  
  把 N 個候選拆成多次小批次呼叫，可能讓 P95 延遲增加 5–6 倍、能耗增加 4–5 倍。若業務邏輯允許，應優先批次化。

- **記憶體與 KV cache 限制**  
  並非所有模型與 GPU 都能承受 `1×8` 大批次。當輸出長或模型較大時，需先測試最大可行批次大小，再決定排程。

- **確定性與可解釋性需求**  
  某些應用需要逐候選日誌、獨立種子或中間分析，這會傾向序列呼叫。此時應量化額外成本，並考慮「部分批次化」或「非同步批次日誌」來降低衝擊。

- **不同 GPU 與框架的批次效益差異**  
  vLLM、TensorRT-LLM、Transformers 的批次處理與排程器行為不同，實際數字會隨框架與硬體變化。建議在自身堆疊上重新測量，而非直接套用論文倍率。

- **準確率與成本的權衡**  
  增加 N 會提升準確率，但邊際效益遞減。應繪製「準確率–能耗」或「準確率–P95 延遲」帕累托前沿，選擇符合業務目標的 N 與排程組合。

---

### 與其他技術的整合建議

- **推論服務框架（vLLM / TGI / TensorRT-LLM）**  
  這些框架已內建連續批次化（continuous batching）與排程優化。在多候選測試時擴展中，應把「同一提示的 N 個候選」視為一個邏輯批次提交，而非 N 個獨立請求，以減少排程開銷與 KV cache 重複載入。

- **HPC 批次排程器（Slurm / PBS / Kubernetes Job）**  
  在 Slurm 等系統中，把多候選推理包裝成單一 GPU 作業，並在作業腳本內使用較大批次呼叫。避免把每個候選拆成獨立作業步驟，否則會因作業啟動、資料載入與 GPU 初始化而放大能耗。

- **能耗與碳排追蹤工具（DCGM、CodeCarbon、MLflow）**  
  將 GPU 裝置總能耗測量整合進 MLflow 或實驗追蹤系統，把「每正確答案能耗」作為模型選型與排程選擇的指標之一。

- **驗證器與獎勵模型（Best-of-N / RLHF verifier）**  
  若使用驗證器挑選候選，可在生成階段批次化，再在 CPU 或獨立服務上並行打分。避免讓驗證器成為新的序列瓶頸。

- **監控與可觀測性（Prometheus / Grafana）**  
  在生產環境監控每個端點的「每查詢呼叫次數」與「每次呼叫候選數」，並設定 P95 延遲與 GPU 功率異常告警，防止排程漂移導致成本暴增。

### 給不同背景讀者的閱讀建議

**初學者**  
本文核心訊息很直觀：「同樣生成 8 個候選，一次批次做完比分成 8 次做更省電、更快。」建議先閱讀摘要與第 I 節，理解「候選數量 N」與「生成排程」的差別，再對照圖 1 的 `1×8` 與 `8×1` 示意圖。技術細節如 DCGM 能耗測量可暫時略過，但務必記住：以後看到論文只寫 N = 8，要追問它是怎麼執行的。

**AI 工程師**  
重點放在第 III 節的方法與實驗設計：如何固定 N、如何測量 P95 延遲、吞吐量、GPU 利用率與 GPU 裝置總能耗。建議把本文的 `1×8`、`2×4`、`4×2`、`8×1` 實驗複製到自家 vLLM 或 Transformers 管線上，並用 `nvidia-smi` 或 DCGM 驗證能耗倍率。特別注意記憶體上限與 KV cache 行為，不要把論文結論直接套用到不同模型尺寸。

**研究人員**  
請關注本文指出的「報告缺口」：許多測試時擴展研究只報 N，卻遺漏 calls per query、candidates per call 與能耗。建議把生成排程 S = (b₁, ..., b_C) 納入未來論文的標準報告欄位，並在比較不同方法時控制排程變因。此外，可延伸研究自適應排程、動態批次化或記憶體受限下的排程優化。

**產品經理**  
本文直接影響成本與使用者體驗：同樣的準確率提升，排程不同可能讓延遲差 5–6 倍、能耗差 4–5 倍。建議閱讀摘要、第 I 節與結論，把「生成排程」加入產品規格與供應商評估清單。向工程團隊確認：我們的多候選推理是一次批次完成還是多次呼叫？這會影響雲端 GPU 帳單、碳排報告與使用者等待時間。
