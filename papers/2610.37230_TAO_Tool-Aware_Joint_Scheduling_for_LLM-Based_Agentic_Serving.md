TAO（Tool-Aware jOint scheduling）的核心設計在於重新定義「先評估後決策」（evaluate-then-decide）排程範式中的兩個關鍵環節，使其能夠同時處理代理式服務（agentic serving）中 GPU 推理與 CPU 工具執行的交錯特性。

**1. 服務場景的形式化：CGDC 模型**

論文首先將代理式服務抽象為「叢集 GPU 搭配分散式 CPU」（Clustered-GPUs with Distributed-CPUs, CGDC）場景。在此模型下，多個 GPU 節點（node）構成共享推理池，而工具呼叫（tool call）則在推理服務之外的分散式 CPU 資源上執行。代理會話（agent session）由多輪 LLM 推理請求（model turn）與外部工具呼叫交替組成，這使得 GPU 計算需求變得「可中斷」（interruptible）——當會話進入工具等待階段時，其佔用的 GPU 資源可被釋放，但對應的 KV 快取（KV cache）前綴（prefix）仍可能因其他會話的載入而被驅逐（eviction）。

**2. 會話評估：價值三元組（Value Triplet）**

TAO 為每個「會話–節點對」（session-node pair）構建一個三維價值介面（value interface），包含三個正交座標：

- **近期工具就緒度（Near-Term Tool Readiness）**：估計會話在下一個排程窗口內是否需要 GPU 推理。論文沿用 Kang 等人（2026）的做法，在工具執行期間將會話置於等待池（awaiting pool），並透過預測工具完成時間來判斷其返回就緒狀態。此信號解決了現有系統將「工具執行中」會話錯誤地視為低優先級的問題——事實上，一個即將返回的會話可能比一個仍在等待工具的會話更值得排入推理。

- **節點特定快取信用（Node-Specific Cache Credit）**：衡量會話在某節點上的 KV 前綴重用潛力，並引入時間感知衰減（time-aware decay）機制。隨著快取在節點上駐留時間增加，其重用價值因可能被驅逐而遞減。此設計避免了「快取年齡」被忽略導致的虛高評分。

- **Token 足跡（Token Footprint）**：會話在該節點上推理所需的 token 總量，作為資源消耗的代理變數。

三個座標刻意保持獨立而非以加權和（weighted sum）合併，這使得不同信號可在不同時間尺度上引導決策，且排程器無需手動調參。

**3. 決策階段：動態規劃聯合優化**

TAO 的核心創新在於將會話的「准入」（admission）與「放置」（placement）建模為一個聯合優化問題，而非現有系統的逐會話啟發式（heuristic）決策。具體而言：

- 給定等待池中所有會話的價值三元組，TAO 構建一個動態規劃（dynamic program），在節點容量約束（capacity constraint）下最大化可准入會話的三元組加總值。
- 動態規劃的狀態空間為「已使用的容量」，轉移則對應於選擇某個會話並將其放置於特定節點。這種聯合視角使得排程器能夠考慮「准入一個會話如何影響其他會話的放置選擇」，避免貪婪啟發式導致的次優解。
- 將優化程序與會話評估分離，使框架具備可擴展性（extensible）——未來新增評估信號只需擴展三元組維度，無需修改排程核心。

**4. 與現有範式的對比**

相較於 llm-d 與 SGLang 等系統的「單會話評分 + 規則路由」模式，TAO 的差異在於：(a) 將工具時序納入評估而非僅作為快取或 token 的代理；(b) 將多會話競爭視為組合優化問題而非獨立決策的集合。這兩個改進分別對應論文中 Figure 1 (Right) 所標示的兩大挑戰。

#### 實驗數據解讀

論文報告在 12 種「模型–工作負載–並發度」（model-workload-concurrency）設定下的結果，並以三項指標衡量：

**1. 端到端延遲（Latency）降低最高 26.8%**

此指標衡量代理會話完成多步任務的總時間。在 CGDC 場景下，工具呼叫延遲（tool-call latency）佔據會話總時間的顯著比例，因此降低延遲的關鍵在於「減少會話在工具返回後等待 GPU 的時間」。TAO 透過工具返回就緒度（tool-return readiness）精準預測哪些會話即將需要推理，使其能被優先排入下一個排程窗口，從而壓縮「工具完成 → 開始推理」的閒置間隔。

**2. 首 Token 時間（TTFT）降低最高 36.3%**

TTFT 反映從請求提交到模型產生第一個 token 的延遲，對互動體驗至關重要。TAO 在此指標上的最大改善暗示其 KV 快取重用策略特別有效：透過節點特定快取信用（node-specific cache credit）與時間感知衰減，TAO 能更準確地將會話路由至仍保有其 KV 前綴的節點，避免昂貴的 prefill 重新計算。36.3% 的降幅遠超延遲改善幅度，說明快取親和性（cache affinity）決策是 TAO 相對基線的主要優勢來源。

**3. 解碼吞吐量（Decode Throughput）提升最高 29.5%**

吞吐量（throughput）改善意味著在相同 GPU 資源下，系統能服務更多會話的解碼階段。TAO 透過聯合優化避免「單會話貪婪准入導致後續高價值會話無容量可用」的問題，使整體資源利用率提升。

**4. 結果的綜合意涵**

三項指標的改善幅度（26.8% / 36.3% / 29.5%）呈現「TTFT > 吞吐量 > 延遲」的遞減趨勢，這與 TAO 的設計重點一致：其核心創新在於評估階段的工具時序整合與決策階段的聯合優化，前者對 TTFT 影響最直接（因為 TTFT 高度依賴快取重用與排入時機），後者則對吞吐量與延遲產生更分散的影響。

**5. 實驗設定的侷限**

需注意「12 種設定」與「每個指標的最佳基線」的表述：論文明確指出是相對於「每個指標的最佳基線」（best evaluated state-of-the-art baseline for each metric），而非統一基線。這意味著不同指標的比較對象可能不同，讀者需謹慎解讀——TAO 在所有指標上均優於所有基線的結論需要更細緻的數據支撐。此外，論文中未明確說明 12 種設定的具體模型規模（如 7B、13B、70B）、工作負載類型（如程式碼生成、檢索增強生成）與並發度範圍，這些資訊對評估結果的泛化性至關重要。

#### 與現有研究的比較

**1. 與快取感知系統（Cache-Aware Systems）的比較**

SGLang（Zheng et al., 2024）、Preble（Srivatsa et al., 2025）、vLLM Production Stack（Qin et al., 2025）與 NVIDIA Dynamo（NVIDIA, 2025）等系統聚焦於 KV 前綴重用與推理負載平衡。TAO 的差異在於：這些系統將工具時序僅作為快取保留時間（KV-cache retention time）或 token 折扣的代理變數，而 TAO 將工具返回就緒度作為一等公民（first-class）評估信號，並透過時間感知衰減避免快取評分隨時間虛高。

**2. 與工作流感知系統（Workflow-Aware Systems）的比較**

Wadlom 等人（2026）與 Pan 等人（2026）嘗試預測未來的模型呼叫。TAO 不預測整個工作流，而是聚焦於「下一個排程窗口內是否需要推理」這一更局部、更可操作的問題，降低了預測誤差對排程決策的影響。

**3. 與延遲感知排程器（Latency-Aware Schedulers）的比較**

Choi 等人（2025）與 Chen 等人（2025）以延遲或剩餘工作量（remaining work）為優先級。TAO 的價值三元組設計避免了單特徵優先（single feature priority）或加權合併（merged with weights）的局限性——後者需要手動調整權重且對工作負載變化敏感。

**4. 與 llm-d 與 SGLang 排程器的比較**

這些系統採用「逐會話評分 + 規則路由」（per-session scoring + routing rules）的啟發式策略。TAO 的動態規劃聯合優化明確解決了「准入一個會話可能阻擋更高價值會話組合」的問題，這是 Peng 等人（2026）與 Yuan 等人（2026）所批評的次優性來源。

**5. TAO 的侷限**

- **預測依賴性**：工具返回就緒度的準確性依賴於工具執行時間預測模型。若預測誤差大，TAO 可能將 GPU 資源分配給「預期即將返回但實際仍需等待」的會話，造成閒置。
- **動態規劃的可擴展性**：隨著等待池中會話數增加，動態規劃的狀態空間呈線性增長。論文未明確討論演算法在最壞情況下的時間複雜度與實際部署中的可擴展性。
- **節點異質性假設**：論文假設節點間容量與快取結構對稱，未明確處理異質 GPU 配置（如不同型號 GPU 混合部署）的場景。
- **單一服務等級目標（SLO）**：論文的評估指標聚焦於平均延遲與吞吐量，未探討尾部延遲（tail latency）或公平性（fairness）等面向。

## 論文問答

**Q1：什麼是 CGDC 服務場景？為什麼它對基於 LLM 的代理式服務很重要？**
A：CGDC（叢集 GPU 搭配分散式 CPU）描述的是代理式服務中常見的部署情境，其中叢集式 GPU 提供共享的推理容量，而外部工具則在分散式 CPU 上執行。在這種場景下，代理會話會在 LLM 推理與外部工具呼叫之間交替進行，使得 GPU 計算需求變得可中斷。隨著語言模型從基礎聊天機器人擴展到複雜代理，CPU 端的工具執行已成為延遲的重要來源，因此高效能的代理式服務必須同時考量推理需求與工具時序，以維持吞吐量與會話響應性。

**Q2：現有的代理式服務排程系統存在哪些主要缺陷？**
A：現有系統普遍採用「先評估後決策」的排程模式，但在會話評估階段，它們往往忽略了工具返回就緒度這個關鍵訊號，僅將工具時序作為 KV 快取重用或 token 計數的替代指標。在決策階段，這些系統則依賴啟發式策略（如單特徵優先或加權合併）對每個會話進行獨立評分與路由，導致排程決策短視且次優。這種分離式的設計無法聯合考量多個會話之間的相互影響，使得接受某個會話可能阻擋了更有價值的會話組合被服務。

**Q3：為什麼「工具返回就緒度」是代理式服務排程中的關鍵訊號？**
A：工具返回就緒度能預測哪些會話在下一個排程窗口內需要 GPU 推理資源，這對於在工具執行期間釋放 GPU 容量至關重要。透過將會話在工具呼叫期間放入等待池，系統可以更靈活地重新分配推理容量，避免資源浪費。這個訊號與既有的 KV 快取親和性、token 足跡等特徵結合，能形成更全面的會話價值評估，使排程器能區分「工具即將返回且快取重用高」與「緊急但工具仍在執行」等不同情境。

**Q4：TAO 框架的核心方法是什麼？它如何運作？**
A：TAO 的核心是一個工具感知聯合排程框架，它在會話評估階段為每個會話-節點配對形成一個價值三元組，包含近期工具就緒度、節點特定快取信用（含時間感知衰減）以及 token 足跡。在決策階段，TAO 使用動態規劃演算法聯合選擇與放置等待池中的會話，在容量約束下最大化加總的評估三元組。這種設計將優化程序與會話評估分離，使框架具有可擴展性，且各座標會隨快取年齡與工具進度動態演變。

**Q5：TAO 相較於現有方法的主要創新點為何？**
A：TAO 的第一個創新在於明確將工具返回就緒度整合進會話評估介面，突破了現有系統僅將工具時序作為 KV 重用或 token 計數替代指標的限制。第二個創新是採用聯合建模與優化的方式進行決策，透過動態規劃同時考量所有等待會話的准入與放置，而非對每個會話獨立套用啟發式規則。這種聯合優化能避免「接受一個會話卻阻擋更有價值組合」的次優問題，並讓不同訊號隨時間引導決策，無需手動設定加權總和。

**Q6：TAO 在設計上做了哪些關鍵選擇？為什麼採用動態規劃？**
A：TAO 選擇將會話評估的三個座標（工具就緒度、快取信用、token 足跡）分離呈現，而非預先合併為單一加權分數，這使得不同訊號能隨時間獨立引導決策。採用動態規劃的原因在於它能在容量約束下系統性地探索所有會話-節點配對的組合，最大化整體加總價值。將優化程序與會話評估分離的設計也讓框架易於擴展，能適應不同的工作負載（如多代理編排與迴圈代理）以及非代理聊天機器人場景。

**Q7：TAO 在實驗中使用了哪些基準測試與基線系統？**
A：根據摘要描述，TAO 在 12 種模型-工作負載-並發度設定下進行評估，涵蓋了不同的部署情境。雖然具體的基準測試名稱未在提供的文本中詳列，但可推測其比較對象包括 SGLang、vLLM Production Stack、llm-d 等快取感知與工作流感知系統，以及基於延遲或剩餘工作量估計的延遲感知排程器。這些基線代表了目前代理式服務排程領域的最先進方法。

**Q8：TAO 的關鍵實驗結果為何？**
A：TAO 在三項關鍵指標上均優於各項的最先進基線：延遲最多降低 26.8%、平均首 Token 時間（TTFT）最多降低 36.3%、解碼吞吐量最多提升 29.5%。這些結果顯示 TAO 在維持會話響應性與系統吞吐量方面均有顯著改善。值得注意的是，這些改善是在 12 種不同的模型-工作負載-並發度組合下達成的，顯示其方法的穩健性與泛化能力。

**Q9：TAO 的消融研究或元件分析揭示了哪些設計選擇的影響？**
A：雖然提供的文本未包含完整的消融研究細節，但從方法描述可推測，移除工具返回就緒度訊號會使 TAO 退回到類似現有快取感知系統的行為，無法區分「工具即將返回」與「工具仍在執行」的會話。若將聯合動態規劃替換為獨立的啟發式選擇，則會失去聯合優化的優勢，可能導致次優的會話准入與放置組合。此外，時間感知衰減機制對於維持快取信用的時效性也應扮演關鍵角色。

**Q10：TAO 適用於哪些實際的代理式服務場景？**
A：TAO 特別適用於需要頻繁呼叫外部工具的代理式服務，例如程式碼生成代理（呼叫編譯器與測試工具）、檢索增強生成（RAG）系統（呼叫檢索器）、以及多代理編排系統。在這些場景中，工具呼叫延遲往往是端到端延遲的主要瓶頸，而 TAO 的工具感知排程能有效利用工具執行期間釋放的 GPU 容量。論文也指出 TAO 可推廣至迴圈代理（Looped Agents）以及非代理聊天機器人場景，顯示其通用性。

**Q11：在實際產品部署中，採用 TAO 需要考量哪些實務因素？**
A：部署 TAO 需要在排程器中維護每個會話的狀態追蹤，包括工具呼叫進度、KV 快取親和性與 token 累計量，這對排程器的狀態管理提出了更高要求。動態規劃演算法的計算複雜度需在排程延遲與解品質間取得平衡，特別是在高並發度場景下。系統整合方面，TAO 需要與底層推理引擎（如 SGLang、vLLM）以及工具執行環境進行協調，以正確實作會話中斷與恢復機制。

**Q12：TAO 對 LLM 代理服務領域的影響為何？**
A：TAO 提出了 CGDC 服務場景的明確概念框架，將研究焦點從單純的 GPU 推理排程擴展到包含外部工具執行的整體系統優化。其「工具感知」與「聯合排程」的設計理念為後續研究提供了新方向，特別是如何在異質資源（GPU 與 CPU）間進行更精細的資源分配。此外，TAO 將優化程序與會話評估分離的設計哲學，也為排程框架的可擴展性樹立了典範。

**Q13：TAO 的方法有哪些已知的限制？**
A：TAO 的動態規劃演算法在會話數量龐大或節點數量眾多時，可能面臨計算複雜度上升的挑戰，需要在解品質與排程延遲間取捨。工具返回就緒度的預測準確性依賴於工具執行時間的估計品質，若預測偏差過大，可能影響排程決策的有效性。此外，TAO 假設工具執行在分散式 CPU 上完全獨立於 GPU 排程，但若工具本身需要 GPU 資源（如某些視覺模型），則此假設可能不成立。

**Q14：TAO 在哪些情況下可能失效或表現不佳？**
A：當工具執行時間高度不可預測（例如依賴外部 API 回應時間）時，工具返回就緒度的預測可能失準，導致 TAO 的排程優勢減弱。在 KV 快取親和性極低的工作負載下，快取信用對決策的影響有限，TAO 的聯合優化可能無法充分發揮。若會話的工作負載特徵隨時間劇烈變化，固定的價值三元組結構可能需要更頻繁的重新校準。

**Q15：TAO 的未來研究方向有哪些？**
A：未來可探索將 TAO 擴展到包含 GPU 工具（如視覺模型）的異質資源場景，打破 CPU 工具獨立於 GPU 排程的假設。另一方向是結合機器學習方法預測工具返回時間，提升工具就緒度估計的準確性。此外，將 TAO 的聯合優化思想應用於多代理編排、聯邦式推理服務或邊緣-雲端協同推理等更複雜的場景，也是值得探索的方向。

## 實務應用指南

### 適用場景

1. **多輪代理式程式助理（Multi-Turn Coding Agent）**：類似 Cursor、Devin 等 AI 程式助理，會話需反覆呼叫編譯器、測試執行器、靜態分析工具與 LLM 推理。工具執行時間從數秒到數分鐘不等，TAO 的工具返回就緒度可避免 GPU 在工具執行期間空轉，並在工具返回瞬間優先排程對應會話。

2. **企業級 RAG 與研究助理系統**：當代理需要呼叫分散式檢索引擎、向量資料庫、文件解析器等 CPU 密集型工具時，TAO 的節點特定快取信用能讓重複查詢相同知識庫的會話優先命中保有其 KV 前綴的節點，降低 prefill 重算成本。

3. **多代理協作編排（Multi-Agent Orchestration）**：在主管代理分派任務給多個專門代理的場景下，每個子代理會話的工具呼叫時序各異，TAO 的聯合動態規劃可同時考量多個會話的准入與放置，避免單特徵啟發式造成的次優組合。

4. **瀏覽器自動化與 GUI 代理**：當代理需等待網頁載入、API 回應或人工確認時，工具延遲高度不確定，TAO 的時間感知衰減機制可隨時間推移自動降低長時間未返回會話的快取權重，釋放資源給活躍會話。

5. **Looped Agent 與長時推理任務**：對於需要反覆迭代推理、執行程式碼、觀察結果的循環代理，TAO 框架的價值介面可擴充以容納額外特徵（如迭代次數、錯誤率），適用於 SWE-bench 類基準的工業部署。

### 實作前置條件

**資料需求**
- 代理工作負載追蹤（agent workload traces）：包含每個會話的工具呼叫時長分佈、LLM 請求間隔、KV 前綴重用模式
- 工具執行時序資料：CPU 端工具的開始時間、預估完成時間、實際完成時間，用於校準工具返回就緒度模型
- KV 快取親和性日誌：會話與節點之間的歷史快取命中率

**運算資源**
- 至少 2 個 GPU 節點組成的叢集（建議 4 節點以上以驗證聯合排程效益）
- 分散式 CPU 工具執行環境（與 GPU 叢集網路分離或低耦合）
- 排程器本身的 CPU 與記憶體需求極低（動態規劃狀態空間為節點數 × 等待池大小）

**技能前提**
- 熟悉 LLM 推理服務（如 vLLM、SGLang、llm-d）的內部排程介面
- 具備分散式系統與動態規劃基礎
- 了解 KV 快取管理與 prefill/decode 階段特性
- 能讀懂並修改推理引擎的 session admission 與 routing 邏輯

### 實作步驟建議

**步驟一：盤點現有系統的排程瓶頸**
先以監控工具量測目前服務在 CGDC 場景下的關鍵指標：TTFT 分佈、會話端到端延遲、GPU SM 佔用率隨工具呼叫的波動、KV 快取命中率。確認是否存在「工具執行期間 GPU 空轉」或「會話准入後快取被驅逐」等可被 TAO 改善的現象。

**步驟二：建立工具返回就緒度預估模型**
收集歷史工具呼叫資料，針對每種工具類型（如 `code_executor`、`web_search`、`retriever`）擬合完成時間分佈。可採指數分佈、對數常態或基於特徵的迴歸模型。輸出為「未來排程窗口 Δt 內工具返回的機率」，作為價值三元組的第一維。

**步驟三：實作節點特定快取信用與時間衰減**
為每個 (session, node) 對計算快取重用價值，並套用時間感知衰減函數。建議衰減半衰期與工具平均執行時間同量級（例如 30 秒至 5 分鐘），可參考 Kang et al. (2026) 的折扣機制。

**步驟四：建構價值三元組與動態規劃求解器**
將每個等待會話對每個候選節點表示為 `(readiness, cache_credit, token_footprint)`。在排程器內實作動態規劃：狀態為「已分配至各節點的 token 總量」，轉移為「將某會話准入至某節點」，目標為最大化加總價值。容量約束即為各節點的 KV 快取與並行上限。

**步驟五：與現有推理引擎整合**
TAO 的價值介面與優化程序分離，可作為外掛模組接入 SGLang、vLLM Production Stack 或 llm-d。需擴充 scheduler 的 admission callback 與 placement callback，使其呼叫 TAO 的聯合求解器而非單獨評分。

**步驟六：離線回放驗證與線上 A/B 測試**
先用收集到的 workload trace 進行離線回放，比較 TAO 與現有啟發式在 TTFT、延遲、吞吐量上的差異。確認改善幅度符合預期後，以影子模式（shadow mode）上線，最後切換部分流量進行 A/B 測試。

**步驟七：監控與持續校準**
上線後持續監控工具返回就緒度預測的準確率、快取衰減參數的合理性、動態規劃求解時間（應在毫秒級）。定期以新資料重新擬合工具時間分佈。

### 潛在風險與注意事項

**風險一：工具返回就緒度預估偏差**
若工具執行時間分佈高度重尾或具多模態特性，簡單機率模型可能嚴重誤判，導致排程器高估或低估會話的緊迫性。
**緩解**：採分位數回歸或混合模型；對預估信心區間過寬的會話降權處理；保留「緊急但無法預估」會話的保底准入通道。

**風險二：動態規劃狀態爆炸**
當等待池會話數與節點數同時成長時，狀態空間可能膨脹。雖然論文未明確給出複雜度上界，但實務上若每節點容量為 C、會話數為 N、節點數為 K，狀態數為 C^K。
**緩解**：限制每節點的容量粒度（例如以 KV 區塊為單位而非 token）；對價值低的會話預先剪枝；採用啟發式初始解作為 DP 的 warm start。

**風險三：KV 快取驅逐與重建成本**
TAO 假設工具執行期間會話可安全釋放 GPU，但若快取在工具執行期間被驅逐，下次推理需完整 prefill，反而增加延遲。
**緩解**：將快取驅逐成本納入價值三元組；對高快取重用價值的會話保留其快取槽位，即使工具尚未返回。

**風險四：公平性與長尾會話餓死**
聯合優化傾向選擇高價值會話組合，可能使低快取重用、高工具延遲的會話長期等待。
**緩解**：在目標函數中加入公平性約束或老化項；為 SLO 較寬鬆的會話設定最大等待時間閾值。

**風險五：跨節點時鐘與狀態同步**
CGDC 場景下 GPU 節點與 CPU 工具執行器可能跨資料中心，時鐘偏差會影響時間感知衰減的正確性。
**緩解**：採用邏輯時鐘（如 Lamport timestamp）或集中式時間服務；衰減計算改用相對時間差。

### 與其他技術的整合建議

**與 vLLM / SGLang 推理引擎整合**
TAO 的價值介面設計為可插拔，可作為 scheduler plugin 接入 vLLM Production Stack 或 SGLang Router。建議保留引擎原生的 prefix caching 機制，僅在 admission 與 placement 決策點替換為 TAO 的聯合求解器。

**與 llm-d 分散式排程整合**
llm-d 已提供 per-session 評分與路由介面，可將 TAO 的動態規劃模組封裝為「聯合評分器」，取代其預設的單會話評分邏輯。

**與監控與可觀測性系統整合**
將 TAO 的價值三元組、求解時間、准入/拒絕決策暴露為 Prometheus 指標或 OpenTelemetry span，便於追蹤排程品質隨時間的漂移。

**與工作流編排框架整合**
LangGraph、AutoGen 等編排框架可將工具呼叫的預估時長傳遞給 TAO，作為工具返回就緒度的先驗；TAO 也可回報實際工具返回時間，用於閉環校準。

**與多租戶與配額管理整合**
在共享叢集場景下，可在 TAO 的目標函數中加入租戶權重或配額約束，使聯合優化在多租戶公平性下仍維持高效。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的 CGDC 場景介紹與圖 1，理解「為什麼代理式服務的排程與傳統聊天機器人不同」是關鍵。接著重點理解「工具返回就緒度」這個直覺概念——它回答的是「這個會話短期內會不會需要 GPU」。數學細節可先略過，掌握「TAO 同時考慮多個會話而非一個一個排」這個核心思想即可。

**給 AI 工程師**：直接從第 2 節的背景開始，理解 session interruption 與 KV cache thrashing 的權衡。接著仔細閱讀價值三元組的設計（readiness、cache credit、token footprint）與動態規劃的狀態定義，這是實作的核心。建議先在小型 vLLM 部署上以單節點模式驗證價值介面，再擴展至多節點聯合排程。注意評估求解器的延遲預算，確保排程決策本身不會成為瓶頸。

**給研究者**：本文在 evaluate-then-decide 典式下提出「聯合優化」的洞見值得深究。可進一步探索的方向包括：將動態規劃擴展為線上學習版本、考慮隨機工具延遲的穩健優化、與強化學習排程器的比較、以及在異質 GPU（如 H100 與 A100 混合）下的擴充。價值介面與優化程序分離的設計也為未來引入更複雜的特徵（如注意力親和性、推測解碼收益）提供了空間。

**給產品經理**：TAO 解決的是「代理式服務在工具執行期間浪費 GPU 資源」與「排程決策次優」兩個實務痛點。在評估導入價值時，可關注三個指標：會話端到端延遲（影響使用者體驗）、TTFT（影響互動即時感）、解碼吞吐量（影響單位 GPU 的服務容量）。論文的 26.8% / 36.3% / 29.5% 改善是相對於各指標最佳基線的數字，實際部署效益會因工作負載特性而異。建議先在內部代理產品上做小規模試點，量化對使用者留存與成本的影響後再決定是否全面導入。
