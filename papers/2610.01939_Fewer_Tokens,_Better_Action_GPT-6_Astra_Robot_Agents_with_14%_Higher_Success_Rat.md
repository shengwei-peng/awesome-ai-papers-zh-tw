## ⚡ TL;DR

現有 VLM 機器人智慧體因重複呼叫與冗餘觀測導致 token 開銷過高。
提出 PyRUA-Lean，以互動式 Python 執行結合回饋驅動基元組合與選擇性觀測。
在 700 項任務中，成功率從 63.1% 升至 71.7%，減少 49% 呼叫與 65% 輸入 token。

## 摘要翻譯

視覺語言模型（Vision Language Model, VLM）智慧體可透過視覺回饋（visual feedback）與動作基元（action primitives）控制機器人，但重複的模型呼叫（model invocations）與冗餘觀測（redundant observations）會帶來可觀的 token 開銷（token overhead）。我們提出 PyRUA-Lean，這是一個互動式程式碼執行框架（interactive code-execution framework），結合了回饋驅動的基元組合（feedback-driven primitive composition）與選擇性觀測（selective observation）：智慧體將傳統機器人基元（classical robot primitives）與學習型視覺-語言-動作（Vision-Language-Action, VLA）策略（policies）組合至 Python 程式碼儲存格（Python cells）中，執行條件檢查（conditional checks）與局部重試（local retries），並僅回傳明確請求的相機影像（requested camera images）與狀態回饋（state feedback），以進行重新規劃（replanning）。我們在來自 LIBERO-PRO、RoboTwin 2.0 與 RoboCasa365 的 700 個模擬任務實例（simulated task instances）上，以相同的 GPT-6 Astra 規劃器（planner）與底層機器人基元（underlying robot primitives），比較 PyRUA-Lean 與工具呼叫基線（tool-calling baseline）。在相同的 LLM 呼叫預算（LLM-call budgets）下，PyRUA-Lean 將整體成功率（success rate）從 63.1% 提升至 71.7%。在兩個智慧體皆能解決的任務實例上，PyRUA-Lean 使用的 LLM 呼叫減少 49%，輸入 token（input tokens）減少 65%。

### 核心貢獻（3～5點）
- 提出 PyRUA-Lean 互動式程式碼執行框架，以回饋驅動的基元組合與選擇性觀測降低重複模型呼叫與冗餘觀測所造成的 token 開銷。
- 將傳統機器人基元與學習型 VLA 策略整合至 Python 程式碼儲存格，支援條件檢查與局部重試等控制流程，提升執行彈性與錯誤恢復能力。
- 在相同 LLM 呼叫預算下，於 LIBERO-PRO、RoboTwin 2.0 與 RoboCasa365 三個模擬基準的 700 個任務實例上，將整體成功率從 63.1% 提升至 71.7%。
- 在兩個智慧體皆能解決的任務實例上，相較工具呼叫基線減少 49% 的 LLM 呼叫與 65% 的輸入 token，顯著改善上下文效率。
- 僅回傳明確請求的相機影像與狀態回饋，實現以重新規劃為導向的選擇性觀測傳遞機制。

### 適合對象
適合從事機器人操作、具身智慧（embodied AI）、視覺語言模型（VLM）與視覺-語言-動作（VLA）策略研究的研究人員與工程師，特別是關注如何以更少 LLM 呼叫與更低 token 開銷來提升機器人智慧體效率與成功率的讀者。

## 深度分析

#### 方法論解析

PyRUA-Lean（Python for Lean Robot-Use Agents）的核心設計，是將「規劃器（planner）」與「執行層」透過**互動式程式碼執行框架（interactive code-execution framework）**解耦。具體而言，它讓視覺語言模型（VLM）智慧體不再以逐次**工具呼叫（tool calling）**的方式驅動機器人，而是產生一段可執行的 Python 程式，由執行環境運行後，再把精簡過的**執行回饋（execution feedback）**回傳給模型進行下一輪決策。這個機制包含三個互補的設計支柱：

1. **回饋驅動的基元組合（feedback-driven primitive composition）**  
   機器人被包裝成一個 `robo` Python 物件，其方法對應到各種**動作基元（motion primitives）**、**感知基元（perception primitives）**、**抓取基元（grasping primitives）**以及凍結的**視覺-語言-動作（VLA）策略（vision-language-action (VLA) policies）**。VLM 可以在單一個 **Python 程式碼儲存格（Python cell）** 中串接多個基元，並根據前一步的輸出決定後續行為。由於程式具備**條件分支（conditional branches）**與迴圈，代理能夠在程式內部完成**條件檢查（conditional checks）**與**局部重試（local retries）**，而不必每次出錯都回到 VLM 進行**重新規劃（replanning）**。

2. **選擇性觀測（selective observation）**  
   傳統工具呼叫介面（tool-calling interface）往往在每次執行後自動回傳多張相機影像與大量中間狀態，導致**冗餘觀測（redundant observations）**不斷累積在**對話（conversation）**上下文中。PyRUA-Lean 改採「只回傳明確需要的資訊」：執行期只把**明確列印的輸出（explicitly printed outputs）**與代理主動請求的**請求的相機影像（requested camera images）**送回 VLM。中間變數則保留在**持久的程式狀態（persistent program state）**中，供後續程式碼儲存格繼續使用，但不進入模型上下文。

3. **錯誤處理與狀態持久化**  
   當 Python 程式發生未捕捉例外時，執行環境會把 traceback 回傳給 VLM，讓代理在下一個程式碼儲存格中修正。整個回合內的變數、輔助函式與執行歷程都保存在同一個命名空間，因此代理可以逐步累積幾何計算、物體座標或自訂恢復腳本，而不需要反覆在提示中重述。

相較於基線 RPent 的**工具呼叫介面（tool-calling interface）**，PyRUA-Lean 在相同 **GPT-6 Astra 規劃器（GPT-6 Astra planner）**、相同**底層機器人基元（underlying robot primitives）**與相同**凍結的 VLA 策略（frozen VLA policies）**下運作，且兩者皆關閉**跨回合記憶（cross-episode memory）**。這樣的對照設計讓實驗能夠孤立出「介面形式」本身對**成功率（success rate）**與 **token 開銷（token overhead）**的影響。

#### 實驗數據解讀

本研究在 700 個**模擬任務實例（simulated task instances）**上進行評估，涵蓋 LIBERO-PRO、RoboTwin 2.0 與 RoboCasa365 三個機器人基準。關鍵結果如下：

- **成功率（success rate）**：在相同 **LLM 呼叫預算（LLM-call budgets）** 下，PyRUA-Lean 將整體成功率從 63.1% 提升至 71.7%，相對提升約 13.6%（論文標題與摘要所稱的 14% higher success rate）。這表示程式化介面不僅省 token，還能改善任務完成能力。
- **LLM 呼叫次數**：在兩個代理都成功解決的任務子集上，PyRUA-Lean 減少 49% 的 LLM 呼叫。這說明把多個步驟打包進單一 Python 程式碼儲存格，能顯著降低**模型呼叫（model invocations）**次數。
- **輸入 token（input tokens）**：在同樣是兩者都解決的任務上，輸入 token 減少 65%。這來自兩個因素：一是呼叫次數變少，二是每次呼叫只攜帶被選擇性回傳的觀測，而非自動產生的多張影像與冗餘中間結果。

進一步解讀時需注意幾點：

1. **效率增益的主要來源是「更少 LLM 呼叫」**：論文指出 trace 與消融實驗顯示，token 節省主要來自於呼叫次數下降。這符合方法論預期：程式碼能夠在執行期內部處理迴圈、條件與重試，減少反覆喚醒 VLM 的需求。
2. **成功率提升的意義**：在預算相同的情況下，PyRUA-Lean 不僅更省資源，還更常成功。這可能因為程式化表達讓規劃器能一次產出較完整的 multi-step 策略，並透過**執行回饋（execution feedback）**即時修正；相較之下，工具呼叫基線容易因為每步都需重新推理而累積錯誤或陷入重複試探。
3. **子集分析的偏倚**：65% 輸入 token 的數字僅限於「兩個代理都成功解決」的實例。對於困難或失敗案例，token 消耗模式可能不同，因此不宜直接將此數字外推到所有 700 個實例。
4. **VLA 任務的差異**：論文提到，當任務主要由 VLA 策略主導時，增益會縮小。這暗示 PyRUA-Lean 的優勢在於需要幾何計算、條件判斷與腳本化恢復的任務；對於端到端 VLA 已能穩定處理的動作，程式化包裝的邊際效益較低。

#### 與現有研究的比較

PyRUA-Lean 位於三條研究脈絡的交會點，並針對「機器人操作中的推理成本」提出具體改進：

**1. 相對於 VLM 機器人控制（VLM-based robot control）**  
過去研究如 SayCan、Inner Monologue、Show-Harness 與 GPT-6 Astra，主要聚焦於如何讓語言模型選擇技能或產生動作。RPent / Harness VLA 則進一步把凍結 VLA 與分析型基元整合到記憶導向代理框架中。PyRUA-Lean 與這些工作的差異在於：它不改變底層策略，而是透過**Python 執行介面（Python execution interface）**重新包裝相同基元，從而改善**上下文效率（context efficiency）**與**控制流程（control flow）**。

**2. 相對於程式化機器人控制（code-based robot control）**  
Code as Policies、ProgPrompt、VoxPoser 等早期工作證明語言指令可以轉譯為機器人程式（robot programs）。後續的 CaP-X、VLCP、ASPIRE、RoboRSI 則探索執行回饋、程式適應與跨回合技能累積。PyRUA-Lean 的獨特之處在於「互動式」與「選擇性觀測」：它不是一次性產生完整程式，而是讓 VLM 與執行環境多輪互動，並且只把必要觀測送回模型。這與 Voyager 在 Minecraft 中累積技能庫的方向互補，但 PyRUA-Lean 目前不啟用**跨回合記憶（cross-episode memory）**，專注於單一回合內的效率與成功率。

**3. 相對於通用程式化代理介面（code-based interfaces for efficient agents）**  
ReAct、Toolformer、CodeAct、SWE-agent 等研究顯示，可執行程式碼相較於文字或 JSON 動作介面可提升效能與上下文效率。近期工作更進一步讓程式碼在模型外部組合工具呼叫並處理中間結果。PyRUA-Lean 把這套原則應用到**機器人操作（robot manipulation）**領域：觀測是視覺化的、基元執行可能失敗、且需要幾何推理與恢復。這填補了通用代理介面與具身機器人之間的缺口。

**主要改進**可歸納為：

- 在相同模型與基元下，同時提升成功率並降低 **token 開銷（token overhead）**。
- 透過**持久的程式狀態（persistent program state）**與**選擇性觀測（selective observation）**有效管理**上下文管理（context management）**。
- 支援程式內部的條件判斷與局部重試，減少不必要的**重新規劃（replanning）**。

**限制**包括：

- 不具備跨回合技能學習或程式庫累積，長期經驗無法被重用。
- 在 VLA 主導的任務上，介面帶來的增益較小。
- 依賴結構化的 `robo` API 與安全的 Python 執行環境；若基元 API 不穩定或沙箱設計不當，程式化執行可能引入新的失敗模式。
- 僅在模擬環境中驗證，真實機器人的延遲、感測器雜訊與安全議題尚未探討。
- 使用專有的 GPT-6 Astra 作為規劃器，對其他開源模型的適用性仍需驗證。

#### 可重現性評估

從提供的上下文來看，本研究的可重現性面臨幾項挑戰：

- **資料集**：LIBERO-PRO、RoboTwin 2.0 與 RoboCasa365 是既有的模擬基準，原則上可取得。然而 RoboTwin 2.0 與 RoboCasa365 的公開程度與版本一致性需要進一步確認。
- **機器人技術堆疊（robot stacks）**：PyRUA-Lean 建立在 RPent 的機器人堆疊與基元實作之上。若 RPent 未開源，或底層**底層機器人基元（underlying robot primitives）**與**凍結的 VLA 策略（frozen VLA policies）**的權重未釋出，則難以完全復現。
- **規劃模型**：實驗使用 **GPT-6 Astra 規劃器（GPT-6 Astra planner）**，屬於專有模型。即使釋出程式碼，其他研究者若無法取得相同模型版本與 API 行為，結果可能難以一比一復現。
- **PyRUA-Lean 執行環境**：論文雖描述介面機制，但執行沙箱、API 參考表（Table 1）、提示樣板、錯誤處理邏輯與追蹤資料是否公開，將直接決定可重現性。
- **無跨回合記憶**：這雖然簡化了實驗控制，但也意味著釋出時只需提供單一回合的執行腳本與環境設定即可，降低了部分重現門檻。

整體而言，若作者能釋出 PyRUA-Lean 執行環境、API 文件、提示樣板、VLA 策略檢查點以及完整實驗追蹤，將大幅提升可重現性。在目前資訊下，可重現性屬於「中等偏低」，主要受限於專有模型與未明確說明的 RPent 底層實作。

#### 未來研究方向

基於 PyRUA-Lean 的設計與實驗結果，以下幾個方向值得後續探索：

1. **跨回合技能累積與程式庫學習**  
   目前系統關閉**跨回合記憶（cross-episode memory）**。未來可借鏡 Voyager、ASPIRE、RoboRSI，讓成功的 Python 程式片段被儲存、索引並在未來任務中檢索重用，進一步降低長期學習成本。

2. **真實機器人驗證**  
   將 PyRUA-Lean 從模擬遷移到真實機器人平台，研究視覺延遲、執行失敗與安全約束下的表現，並發展對應的程式碼沙箱與緊急停止機制。

3. **自適應觀測策略**  
   目前的**選擇性觀測（selective observation）**由代理主動請求影像。未來可訓練輔助模型或啟發式規則，自動決定在哪些執行階段需要視覺確認、哪些階段只需狀態回饋，以進一步壓縮 token。

4. **與 VLA 策略的協同微調**  
   既然增益在 VLA 主導任務上會縮小，未來可研究如何讓程式化介面與 VLA 策略共同微調：例如用程式碼產生高階意圖或約束條件，再由 VLA 執行細粒度動作。

5. **開源模型與成本效益分析**  
   驗證 PyRUA-Lean 是否能搭配較小或開源 LLM 達到相近效果，並建立標準化的 **token 開銷（token overhead）** / 延遲 / 金錢成本評估基準。

6. **形式化驗證與安全保證**  
   由於代理會自動產生並執行 Python 程式，未來可引入靜態分析、型別檢查或形式化驗證，確保程式不會產生危險動作，特別是在真實機器人場景中。

7. **多代理與長期任務**  
   將程式化介面擴展到多機器人協作或數百步的長期任務，研究如何透過模組化程式碼與分層規劃維持上下文效率。

8. **觀測壓縮與語義摘要**  
   除了選擇性回傳影像，也可研究如何把多張影像或長段狀態歷程壓縮成緊湊的語義描述，進一步降低**輸入 token（input tokens）**負擔。

## 論文問答

**Q1：PyRUA-Lean 旨在解決什麼核心問題？**
A：PyRUA-Lean 主要解決視覺語言模型（VLM）智慧體在控制機器人時所面臨的高 token 開銷與推理成本問題。現有工具呼叫介面在執行機器人操作任務時，往往需要反覆進行模型呼叫，並且每次執行後自動回傳多張相機影像與狀態資訊，導致對話上下文迅速膨脹。這種冗餘觀測與頻繁的模型呼叫不僅增加輸入 token 消耗，也降低了整體系統的推理效率，因此亟需一種能夠選擇性觀測並減少模型呼叫次數的互動式程式碼執行框架。

**Q2：傳統工具呼叫介面為何會產生大量 token 開銷？**
A：在傳統工具呼叫介面中，每一個依賴前一步結果的操作通常都需要再次呼叫 VLM，這使得簡單的條件判斷或重試也必須經過完整的模型推理流程。此外，許多系統會在每次基元執行後自動回傳多張相機影像與中間結果，這些資訊會累積在對話歷史中並在後續呼叫時被重複處理。由於機器人操作任務經常需要反覆進行定位、運動與恢復，這種設計會造成可觀的推理開銷，即使個別基元本身是可靠的。

**Q3：降低 token 開銷對機器人智慧體為何重要？**
A：降低 token 開銷直接關係到機器人智慧體在實際部署時的延遲、成本與可擴展性。較少的輸入 token 與模型呼叫次數意味著更快的反應時間與更低的推理費用，這對於需要即時互動的機器人應用至關重要。此外，精簡的上下文管理也能減少模型被無關資訊干擾的機會，從而提升高階規劃與重新規劃的品質。

**Q4：PyRUA-Lean 的核心運作機制是什麼？**
A：PyRUA-Lean 是一個互動式程式碼執行框架，它讓 VLM 規劃器生成 Python 程式碼儲存格來組合機器人基元，並在執行過程中根據執行回饋進行條件檢查與局部重試。該框架透過 `python(code)` 工具與機器人互動，並在每次執行後保留持久的程式狀態，使變數與輔助函數可以在同一回合內跨儲存格重複使用。只有明確列印的輸出與請求的相機影像才會被回傳給 VLM，從而實現選擇性觀測與精簡的上下文管理。

**Q5：PyRUA-Lean 相較於既有程式碼型機器人控制方法的關鍵創新為何？**
A：PyRUA-Lean 的關鍵創新在於將回饋驅動的基元組合與選擇性觀測緊密結合，並且在同一框架下同時支援古典動作基元與凍結的視覺-語言-動作（VLA）策略。不同於早期 Code as Policies 或 ProgPrompt 主要從語言指令生成一次性機器人程式，PyRUA-Lean 允許在多輪互動中根據執行回饋動態調整程式碼。這種設計讓智慧體能夠在單次模型呼叫內完成複雜的條件分支、錯誤恢復與多步驟操作，大幅減少不必要的模型呼叫與冗餘觀測。

**Q6：PyRUA-Lean 為何選擇 Python 儲存格與選擇性觀測作為主要設計？**
A：選擇 Python 儲存格是因為可執行程式碼能夠自然地表達控制流程、條件分支與迴圈，並且可以在執行期間檢查中間結果而無需反覆呼叫模型。選擇性觀測則是為了避免傳統介面自動回傳大量相機影像與狀態資訊所造成的上下文膨脹問題。透過只將明確請求的觀測資料納入 VLM 上下文，PyRUA-Lean 能夠在保持足夠決策資訊的同時，顯著降低輸入 token 數量並提升推理效率。

**Q7：實驗使用了哪些基準測試，為何選擇它們？**
A：實驗涵蓋了 700 個模擬任務實例，分別來自 LIBERO-PRO、RoboTwin 2.0 與 RoboCasa365 三個機器人操作基準資料集。這些資料集涵蓋了不同的操作場景、物件配置與任務複雜度，能夠全面評估 PyRUA-Lean 在多樣化機器人操作任務上的表現。選擇這三個基準有助於驗證框架在長期操作、多步驟規劃與視覺回饋處理等方面的泛化能力。

**Q8：PyRUA-Lean 的主要實驗結果為何？**
A：在相同的 GPT-6 Astra 規劃器、凍結 VLA 策略與 LLM 呼叫預算下，PyRUA-Lean 將整體成功率從 63.1% 提升至 71.7%，相當於約 14% 的相對提升。在兩個智慧體都能解決的任務實例上，PyRUA-Lean 減少了 49% 的 VLM 呼叫次數與 65% 的輸入 token 數量。這些結果顯示，透過程式化基元組合與選擇性觀測，不僅能顯著降低推理成本，還能同時提升任務成功率。

**Q9：追蹤紀錄與消融實驗揭示了哪些效率來源與限制？**
A：追蹤紀錄與消融實驗顯示，token 節省的主要來源是更少的 LLM 呼叫次數，因為程式碼儲存格可以在單次呼叫中處理多個中間步驟與局部重試。這些效率增益在沒有 VLA 策略或操作指南的情況下依然存在，但在以 VLA 策略為主的任務上會有所減弱，因為這類任務較少需要條件檢查與程式化組合。此外，實驗也展示了幾何計算與腳本化恢復等機制如何進一步減少對模型推理的依賴。

**Q10：PyRUA-Lean 適合應用在哪些實際場景？**
A：PyRUA-Lean 特別適合需要反覆定位、錯誤恢復與多步驟組合的機器人操作場景，例如家庭服務機器人執行整理、烹飪輔助或清潔任務。在工業環境中，它也能用於需要視覺檢查與條件式動作的組裝或品質檢測流程。由於該框架能夠顯著降低模型呼叫次數與 token 消耗，因此對於需要長時間自主運作且受成本與延遲限制的應用特別具有吸引力。

**Q11：將 PyRUA-Lean 產品化時需要考慮哪些因素？**
A：產品化時需要確保程式碼執行環境的安全性，因為智慧體生成的 Python 程式碼會直接控制機器人動作與感知基元。此外，開發者應設計清晰的 API 參考與錯誤處理機制，讓 VLM 能夠正確理解每個基元的輸入輸出格式並妥善處理例外狀況。最後，雖然 PyRUA-Lean 降低了 token 消耗，但仍需評估在真實硬體上的延遲、穩定性與安全性，特別是在涉及人機協作的場景中。

**Q12：PyRUA-Lean 對機器人智慧體研究領域可能帶來什麼影響？**
A：PyRUA-Lean 展示了介面設計本身對機器人智慧體效能與效率的重大影響，可能促使更多研究關注如何透過程式化介面減少模型呼叫與上下文長度。它為結合古典機器人基元與學習型 VLA 策略提供了一個高效的互動範式，有助於推動更實用且可部署的機器人系統。此外，其選擇性觀測與上下文管理的經驗也可能啟發其他領域的通用型智慧體設計，例如軟體工程或網頁操作智慧體。

**Q13：論文承認了哪些主要限制？**
A：論文承認 PyRUA-Lean 的效率增益在以 VLA 策略為主的任務上會有所減弱，因為這類任務較不需要條件檢查與程式化組合。此外，實驗目前僅在模擬環境中進行，尚未在真實機器人硬體上驗證其效果與穩定性。研究也排除了跨回合記憶機制，因此未能評估長期技能累積與經驗重用對系統表現的潛在影響。

**Q14：PyRUA-Lean 在哪些類型的任務或情境下表現較差？**
A：PyRUA-Lean 的優勢在需要頻繁條件判斷、幾何計算與腳本化恢復的任務中最為明顯，但在主要由端到端 VLA 策略主導的任務上，其相對增益會降低。這是因為當大部分決策都交給學習型策略時，程式化組合與選擇性觀測能發揮的空間較小。此外，若任務需要大量視覺細節來進行每一步決策，則選擇性觀測可能會遺失關鍵資訊，進而影響重新規劃的準確性。

**Q15：未來研究可以朝哪些方向延伸 PyRUA-Lean？**
A：未來研究可以探索將跨回合記憶與技能庫整合進 PyRUA-Lean，使智慧體能夠在不同任務間累積並重用可執行程式片段。另一個方向是將框架擴展到真實機器人硬體，並研究如何在不犧牲安全性的前提下進行線上程式碼生成與執行。此外，結合主動學習或元學習來自動決定何時請求相機影像與狀態回饋，也可能進一步提升選擇性觀測的效率與決策品質。

## 實務應用指南

### 適用場景

1. **重複性高、步驟繁瑣的工業組裝與品檢**  
   在電子或汽車產線中，機器人需要反覆進行定位、抓取、插入、鎖附與視覺確認。PyRUA-Lean 可將這些動作基元與視覺-語言-動作（VLA）策略組合成帶有條件檢查與局部重試的 Python 程式，減少每次微調都呼叫 VLM 的 token 開銷，同時透過選擇性觀測只回傳關鍵影像給規劃器。

2. **倉儲物流中的動態揀選與異常排除**  
   當機器人需要在貨架間辨識目標物件、處理遮擋或滑夾後重新抓取時，傳統工具呼叫介面會因反覆重新規劃而累積大量對話上下文。PyRUA-Lean 可在單一程式碼儲存格內完成「抓取—檢查—重試」的閉環，只在需要人工或高階決策時才回傳狀態回饋。

3. **服務型機器人的多步驟家務任務**  
   例如整理桌面、將餐具放入洗碗機、依照食譜取物等任務，涉及連續的視覺回饋與動作序列。透過回饋驅動的基元組合，機器人能在本機判斷物件是否已移動、是否抓取成功，再決定下一步，降低對雲端 LLM 的依賴與延遲。

4. **醫療或實驗室自動化**  
   在樣本分裝、試劑移取或儀器上下料等場景中，動作失敗成本高且需要精確的狀態確認。PyRUA-Lean 可將感測器讀數、相機影像與機器人狀態整合進條件分支，僅在偏離預期時才觸發重新規劃，兼顧安全性與效率。

5. **農業或戶外機器人的巡檢與採摘**  
   面對光線變化、枝葉遮擋等不確定因素，機器人可利用持久的程式狀態記錄先前觀測，並在程式內執行幾何計算或腳本化恢復，只在關鍵節點請求新的相機影像，減少無線網路環境下的傳輸與推理成本。

### 實作前置條件

**資料準備**
- 任務層級的自然語言指令與對應的期望終態描述。
- 機器人基元（motion、perception、grasping）與 VLA 策略的 API 文件與輸入輸出規格。
- 關鍵觀測的定義：哪些相機影像與狀態回饋必須回傳給 VLM，哪些可留在本機程式狀態中。
- 模擬或真實環境中的失敗案例資料，用於設計條件檢查與局部重試邏輯。

**運算資源**
- 可執行 Python 程式碼的機器人運算單元或邊緣閘道器，用於承載 PyRUA-Lean 的互動式程式碼執行框架。
- 能夠呼叫 GPT-6 Astra 或同等級 VLM 規劃器的 API 配額與網路連線。
- 若使用 VLA 策略，需要可執行凍結 VLA 模型的 GPU 或加速器資源。
- 足夠的儲存空間保存對話歷史、程式狀態與關鍵觀測影像。

**技能與團隊配置**
- 熟悉機器人作業系統（如 ROS/ROS2）與機器人技術堆疊的工程師。
- 能夠設計與維護基元 API 的機器人學或感知工程師。
- 具備 Python 程式設計與提示工程經驗的 AI 工程師，負責撰寫系統提示詞與除錯程式碼儲存格。
- 領域專家協助定義任務成功準則、安全限制與異常處理流程。

### 實作步驟建議

1. **建立基元 API 與機器人物件**  
   將現有的動作基元、感知基元、抓取基元與 VLA 策略封裝成統一的 Python 物件（如 `robo`），並明確定義每個方法的回傳值，包括執行結果、物件位置與異常資訊。

2. **設計選擇性觀測機制**  
   決定哪些中間結果需要「明確列印」回傳給 VLM，哪些僅儲存在持久的程式狀態中。避免自動在每個步驟結束後回傳多張相機影像，改為由程式主動請求必要的相機影像。

3. **撰寫系統提示詞與程式碼執行規範**  
   在提示詞中說明可用的基元、錯誤處理方式、變數命名慣例，以及何時應該結束當前程式碼儲存格並將控制權交還 VLM。強調條件檢查與局部重試的使用時機。

4. **在模擬環境中進行對照實驗**  
   選用 LIBERO-PRO、RoboTwin 2.0 或 RoboCasa365 等模擬基準資料集，或自建任務實例。在相同 LLM 呼叫預算下，比較 PyRUA-Lean 與工具呼叫基線的成功率、LLM 呼叫次數與輸入 token 數量。

5. **逐步加入真實場景的異常處理**  
   從模擬中識別常見失敗模式（如滑夾、碰撞、定位偏差），將對應的腳本化恢復與幾何計算寫入 Python 儲存格，減少每次異常都觸發重新規劃。

6. **部署到邊緣並監控推理成本**  
   將 PyRUA-Lean 執行環境部署到機器人端或邊緣伺服器，持續追蹤輸入 token、LLM 呼叫次數與任務成功率，並根據實際成本調整觀測回傳策略。

7. **迭代優化提示詞與基元抽象層級**  
   參考 CaP-X 等研究的發現，根據任務複雜度調整基元抽象層級與多輪互動模式，並定期更新系統提示詞以納入新發現的失敗案例。

### 潛在風險與注意事項

- **程式碼執行安全風險**  
  讓 VLM 產生並執行 Python 程式碼可能導致非預期的機器人動作或系統呼叫。應在沙箱環境中執行程式碼、限制可呼叫的函式庫，並對機器人基元加入硬體層級的安全限制。

- **錯誤處理與無限重試**  
  局部重試雖然減少 LLM 呼叫，但若條件檢查設計不當，可能陷入無限迴圈。應為每個重試邏輯設定最大次數，並在達到上限時將控制權交還 VLM 或觸發安全停機。

- **觀測遺漏導致決策失準**  
  過度減少觀測回傳可能使 VLM 無法掌握關鍵狀態變化。建議透過消融實驗驗證「最少必要觀測集」，並在任務關鍵節點強制回傳影像或狀態回饋。

- **VLA 策略主導任務的效率增益有限**  
  若任務主要由 VLA 策略完成，程式化組合帶來的 token 節省會較小。此時應評估是否值得引入 PyRUA-Lean，或將其用於 VLA 前後的感知與恢復階段。

- **跨回合經驗無法累積**  
  本研究在無跨回合記憶的條件下進行評估。若產品需要長期學習，需額外設計技能庫或經驗回放機制，否則每個任務實例都需從頭規劃。

- **模型 API 成本與延遲波動**  
  雖然 PyRUA-Lean 減少 65% 輸入 token，但 GPT-6 Astra 等模型的 API 計價與可用性仍會影響總成本。應建立成本監控與備援規劃器機制。

### 與其他技術的整合建議

- **與現有機器人框架（ROS/ROS2）整合**  
  可將 `robo` 物件實作為 ROS 節點的封裝層，讓 PyRUA-Lean 透過服務或動作介面呼叫底層運動規劃、感知與抓取模組，無需改動既有技術堆疊。

- **與 VLA 模型（如 Harness VLA、RPent）整合**  
  將凍結的 VLA 策略視為一種高階動作基元，在 Python 程式碼中與傳統分析式基元並用。VLA 負責語言條件下的視覺動作，傳統基元負責精確的幾何計算與恢復。

- **與記憶與技能庫系統整合**  
  雖然本研究不使用跨回合記憶，但未來可參考 Voyager、ASPIRE 或 RoboRSI 的做法，將成功的 Python 儲存格或函式儲存為可重複使用的技能，進一步降低長期任務的規劃成本。

- **與低程式碼/無程式碼平台整合**  
  可將 PyRUA-Lean 產生的程式碼儲存格視為後端執行單元，前端提供視覺化流程編輯器，讓領域專家透過拖曳基元方塊生成任務，再由 VLM 轉譯為 Python 程式。

- **與雲端監控與 MLOps 平台整合**  
  將每次 LLM 呼叫、輸入 token 數量、執行軌跡與成功率紀錄到監控系統，支援 A/B 測試、提示詞版本控制與異常案例回放。

### 給不同背景讀者的閱讀建議

**給初學者**  
這篇論文的核心概念是：與其讓 AI 每次做一個動作就問一次模型，不如讓 AI 寫一小段 Python 程式，把多個動作、檢查與重試包在一起，並只把真正重要的影像或狀態回傳給模型。建議先理解「工具呼叫」與「程式碼執行」的差別，再關注實驗中成功率和 token 減少的數字，最後看一個具體的任務範例來體會為何減少 LLM 呼叫能省錢又提速。

**給 AI 工程師**  
重點在於介面設計：PyRUA-Lean 不是換一個更強的模型，而是透過互動式程式碼執行框架、持久的程式狀態與選擇性觀測來優化現有 GPT-6 Astra 規劃器的使用效率。建議仔細研究第 3 節的執行模型、錯誤處理機制與觀測傳遞策略，並思考如何將這些設計原則遷移到你的機器人平台或軟體代理系統。

**給研究人員**  
本文提供了一個乾淨的對照實驗：相同規劃器、相同凍結 VLA 策略、相同任務實例與 LLM 呼叫預算下，比較工具呼叫與程式碼執行介面。建議關注消融實驗與軌跡分析，特別是「較少 LLM 呼叫是 token 節省主要來源」這一發現，以及 VLA 主導任務中效率增益減弱的現象，這些都是後續研究的切入點。

**給產品經理**  
這項技術的直接商業價值是降低機器人 AI 系統的推理成本與延遲，同時提升任務成功率。建議將本文視為一個「介面優化」案例：在不更換底層模型與硬體的前提下，透過更好的互動設計實現 14% 成功率提升與 65% token 減少。評估導入時，請優先考慮那些步驟重複、失敗模式明確、且對延遲與成本敏感的應用場景。
