GH-AWTrace 的建構採用三階段管線 (pipeline) 設計，系統性地解決 GitHub 平台上代理工作流程 (Agentic Workflow) 執行證據 (Execution Evidence) 難以保存的問題。

**第一階段：代理工作流程識別**

研究團隊透過 GitHub REST API 的程式碼搜尋功能 [12]，以 `"This file was automatically generated by gh-aw"` 為錨點字串進行搜尋，並限制副檔名為 `.yml` 或 `.yaml`、路徑為 `.github/workflows`、且包含 `fork:true`。由於 GitHub API 每次查詢最多回傳 1,000 筆結果，研究者採用**檔案大小範圍二分搜尋法 (binary search by file size range)** 來突破此限制——當某個位元組範圍回傳滿載的 1,000 筆結果時，便將範圍對半切分並遞迴搜尋。最終從 25,227 個候選檔案中，經過嚴格的標頭驗證（確認生成器字串出現在 YAML 開頭註解中，且位於任何配置鍵之前），剔除 63 個不符標頭的檔案與 150 個無法擷取的索引 blob，最終保留 25,014 個已驗證的 gh-aw 工作流程檔案，分布於 5,051 個儲存庫 (Repository) 中。

**第二階段：執行記錄收集**

透過 GitHub REST API 以工作流程 ID 進行查詢，儲存所有執行記錄 (Run Record) 的資料欄位。執行記錄與 YAML 修訂版本透過 `repo_id` 與精確路徑進行連結，並保留 `head_sha` 以追蹤執行當下的程式碼狀態。此階段蒐集了 4,112,526 筆執行記錄，時間跨度為 2025 年 8 月 14 日至 2026 年 9 月 21 日，受限於 GitHub 400 天的執行記錄保留政策 [14]。

**第三階段：日誌封存**

考量到 GitHub 對公開工作流程執行日誌 (Execution Log) 僅保留 90 天 [14]，研究者選取 2026 年 6 月 23 日至 9 月 21 日這 90 天內產生的 2,453,263 筆執行記錄進行下載。下載過程中，每個 ZIP 封存檔以執行 ID 與嘗試次數 (attempt number) 作為唯一識別碼，並進行完整性檢查（記錄 SHA-256 雜湊值與檔案清單）。最終下載 1,633,215 個封存檔（總計 56.1 GB），其中 1,070,338 個為空 ZIP，562,877 個包含實際日誌檔案。

**資料架構設計**

資料集採用四層連結結構：儲存庫 → gh-aw 工作流程（透過 `repo_id`）→ 執行記錄（透過 `repo_id` 與 YAML 路徑）→ 日誌封存（透過 `run_id`）。此設計支援多對多關係，例如單一工作流程可有多次執行，單次執行可有多次重試嘗試。

## 論文問答

**Q1：GH-AWTrace 試圖解決的核心問題是什麼？**
A：GH-AWTrace 試圖解決的核心問題在於現有研究對於代理工作流程（Agentic Workflow）執行過程中究竟發生了什麼缺乏可追溯的證據。雖然已有研究探討工作流程的定義、輸出與安全性，但這些研究多聚焦於「意圖行為」與「最終結果」，無法解釋執行期間的具體動作。GitHub Agentic Workflows（gh-aw）讓開發者能以 Markdown 撰寫週期性任務並由 AI 代理自動執行，但由於 GitHub 對執行日誌有嚴格的保留限制（公開日誌最多 90 天、執行記錄最多 400 天），這些寶貴的執行證據會隨時間消失。GH-AWTrace 正是為了在這些證據消失前加以保存並建立連結，以支援後續對代理執行行為的研究。

**Q2：為什麼現有的工作流程研究方法無法充分捕捉執行細節？**
A：現有研究方法主要依賴工作流程定義（如 Markdown 或 YAML 檔案）以及最終輸出（如拉取請求、議題或評論），但這些資料來源僅描述「意圖行為」與「彙總結果」，無法呈現執行期間的細節。執行層級的結果（例如成功或失敗）雖然能告訴我們最終狀態，卻無法解釋代理在過程中使用了哪些工具、遭遇了哪些存取限制、發生了哪些基礎設施故障，或是如何嘗試從錯誤中恢復。此外，現有研究如 Khelifi 等人探討 gh-aw 的撰寫與維護、Valenzuela-Toledo 等人釋出 Markdown 與 YAML 的歷史連結、Sun 等人量測 AI 程式碼審查 Actions 的影響，以及 Wang 與 Isbarov 等人關注提示注入攻擊，皆未深入到執行日誌的層次。因此，僅憑工作流程定義與輸出，無法完整理解代理工作流程的真實運作情形。

**Q3：為什麼保存執行證據（Execution Evidence）特別重要？**
A：保存執行證據特別重要，因為 GitHub 的日誌保留政策會使這些資料在相對短的時間內變得無法取得——公開工作流程的執行日誌最多僅保留 90 天，執行記錄則在 400 天後被刪除。這意味著若沒有及時封存，許多珍貴的代理行為紀錄將永遠消失，而這些紀錄正是研究代理執行失敗、工具使用模式、代理間協作等議題的基礎。執行日誌能揭示工具拒絕（tool denials）、提供者失敗（provider failures）、代理方法變更（changes in approach）以及代理之間的委派（delegation）等現象，這些資訊無法從工作流程定義或最終結果推論出來。透過 GH-AWTrace 及時封存這些證據並與儲存庫元資料、生成的工作流程配置建立連結，研究者得以在 GitHub 刪除原始資料後仍能進行可追溯的分析。

**Q4：GH-AWTrace 的核心建構方法是什麼？**
A：GH-AWTrace 的核心建構方法分為三個階段：首先是識別已生成的 gh-aw 工作流程，其次是收集其執行記錄，最後是封存可取得的執行日誌。在第一階段，作者透過 GitHub REST API 的程式碼搜尋功能，以「This file was automatically generated by gh-aw」這個產生器註解作為關鍵字搜尋 .github/workflows 目錄下的 .yml 與 .yaml 檔案，並以檔案大小範圍分段處理以突破每次搜尋最多 1,000 筆結果的限制。接著對每個候選檔案進行驗證，僅接受在 YAML 設定鍵之前出現產生器片語作為開頭註解的檔案，最終從 25,227 個候選檔案中篩選出 25,014 個已驗證的 gh-aw 工作流程。第二階段透過 GitHub REST API 依工作流程 ID 收集所有執行記錄並保存所有資料欄位，再以儲存庫 ID 與精確路徑連結到索引時的 YAML 版本。第三階段則考量 90 天保留限制，僅下載 2026 年 6 月 23 日至 9 月 21 日期間的執行記錄之日誌封存檔，並驗證每個 ZIP 的完整性、記錄 SHA-256 雜湊值與檔案清單。

**Q5：GH-AWTrace 的關鍵創新為何？**
A：GH-AWTrace 的關鍵創新在於它是第一個大規模、系統性地將已驗證的 gh-aw 工作流程、執行記錄、執行日誌封存檔與儲存庫元資料相互連結的資料集。其三大貢獻分別為：（1）保存了可能因 GitHub 保留政策而消失的執行日誌封存檔；（2）提供工作流程、儲存庫、執行與日誌之間可追溯的元資料連結；（3）透過具體案例展示資料如何支援失敗分析、工具互動與代理協作等研究。相較於既有研究僅止於工作流程定義或最終輸出，GH-AWTrace 提供了「執行期間」的細粒度證據，使研究者能檢驗回報的執行結果與實際可見任務進度之間的關係。這種跨層級的連結設計讓資料集不僅是靜態的日誌集合，更是一個支援多元分析的可追溯研究基礎。

**Q6：GH-AWTrace 在資料連結與驗證上做了哪些重要的設計選擇？**
A：在資料連結方面，GH-AWTrace 採用儲存庫 ID（repo_id）作為儲存庫與工作流程之間的主要連結鍵，並以儲存庫 ID 加上 YAML 檔案的精確路徑作為工作流程與執行記錄之間的連結鍵，而執行記錄與日誌封存檔之間則以 run_id 與 attempt number 進行識別。這種多層次的連結設計保留了 head_sha 等版本資訊，使研究者即使在工作流程後續被修改的情況下，仍能追溯到執行當時的 YAML 版本。在驗證方面，作者特別注意到目標片語可能以引號文字而非產生器註解的形式出現，因此對每個檔案進行 blob 版本的實際擷取，僅接受在 YAML 設定鍵之前出現產生器片語作為開頭註解的檔案。此外，每個下載的 ZIP 封存檔都經過完整性檢查並記錄 SHA-256 雜湊值與檔案清單，以確保資料的可重現性與可信度。

**Q7：GH-AWTrace 資料集的主要規模與涵蓋範圍為何？**
A：GH-AWTrace 資料集的主要規模包含 25,014 個已驗證的 GitHub Agentic Workflows，橫跨 5,051 個儲存庫，並連結到 4,112,526 筆執行記錄與 562,877 個非空執行日誌封存檔。執行記錄的時間範圍涵蓋 2025 年 8 月 14 日至 2026 年 9 月 21 日，而日誌封存則聚焦於 2026 年 6 月 23 日至 9 月 21 日這 90 天保留期限內的執行。在 2,453,263 筆符合日誌下載條件的執行記錄中，作者下載了 1,633,215 個 ZIP 封存檔（總計 56.1 GB），其中 821,672 筆執行沒有可下載的封存檔（可能因保留、刪除、存取限制或執行未完成），1,070,338 個 ZIP 內無檔案，僅 562,877 個 ZIP 含有日誌檔案。這些含有日誌的封存檔隸屬於 561,367 筆執行，其中 18,337 個來自第一次以外的重新執行嘗試。

**Q8：GH-AWTrace 透過哪些具體案例展示其研究價值？**
A：GH-AWTrace 透過多個具體案例展示其研究價值，這些案例揭示了執行日誌所能捕捉到的豐富現象。其中包括工具拒絕（tool denials）案例，顯示代理在執行過程中遭遇權限或工具存取的阻擋；提供者失敗（provider failures）案例，呈現底層 AI 提供者或基礎設施的異常；代理方法變更（changes in approach）案例，記錄代理在執行中調整策略或重新嘗試的過程；以及代理之間的委派（delegation among agents）案例，展現多代理協作的模式。這些案例說明了僅從工作流程定義或最終輸出無法觀察到的細節，必須透過執行日誌才能加以分析。透過這些具體展示，作者論證了資料集能支援關於執行失敗、工具使用與回報結果與可見進度關係等多元研究。

**Q9：GH-AWTrace 支援哪些類型的分析或研究？**
A：GH-AWTrace 支援多種類型的分析與研究，特別是在執行失敗、工具使用與代理行為觀察等面向。在執行失敗分析方面，研究者可利用日誌中的錯誤訊息、堆疊追蹤與失敗模式，探討代理工作流程失敗的常見原因與恢復策略。在工具使用分析方面，日誌記錄了代理呼叫的工具、參數與回應，使研究者能研究代理如何選擇與使用工具、遭遇哪些工具拒絕，以及工具互動的模式。在代理行為觀察方面，資料集支援研究代理方法的變化、代理之間的委派與協作，以及回報的執行結果（如成功、失敗）與實際可見任務進度之間的落差。此外，由於資料集連結了儲存庫元資料與生成的工作流程配置，研究者還能進行跨儲存庫的比較分析，探討不同組織、開發者或專案類型如何採用與調整 gh-aw 工作流程。

**Q10：GH-AWTrace 在哪些實際應用場景中能發揮價值？**
A：GH-AWTrace 在多個實際應用場景中能發揮價值。對軟體工程研究者而言，這個資料集提供了觀察 AI 代理在真實軟體開發生命週期（SDLC）中行為的機會，可用於研究代理在處理週期性任務（如程式碼審查、議題分流、文件更新）時的表現與限制。對 DevOps 與 CI/CD 實踐者而言，資料集中的執行失敗案例與工具拒絕記錄有助於設計更穩健的工作流程與錯誤處理機制。對 AI 安全研究者而言，這些日誌提供了分析提示注入攻擊、權限提升嘗試與代理異常行為的實證素材。此外，工具開發者可利用資料集了解代理對工具的使用模式，進而優化工具設計與 API；產品經理則可從中觀察使用者如何配置與調整代理工作流程，以指導產品改進方向。

**Q11：GH-AWTrace 對產品與工程實務有何啟示？**
A：GH-AWTrace 對產品與工程實務帶來多項重要啟示。首先，從 Azure/azure-dev 的案例可見，即使代理工作流程因儲存庫設定無法直接開啟拉取請求，仍能透過儲存分支與議題的方式保存修補程式，再由維護者透過拉取請求精煉並合併，這顯示產品設計應考慮代理執行的彈性輸出機制。其次，資料集中大量的工具拒絕與提供者失敗案例提醒工程團隊應為代理工作流程設計完善的錯誤處理、重試與降級策略，以避免單一失敗導致整個工作流程中斷。再者，代理方法變更與代理間委派的案例顯示，現代 AI 代理已具備一定的自主調整與協作能力，產品設計應考慮如何讓人類開發者有效監督、介入並從這些行為中學習。最後，由於 GitHub 日誌保留期限的限制，企業若重視代理執行的可追溯性，可能需要自行建立類似的日誌封存機制，以符合稽核、除錯或合規需求。

**Q12：GH-AWTrace 對軟體工程與 AI 代理研究領域的更廣泛影響為何？**
A：GH-AWTrace 對軟體工程與 AI 代理研究領域具有多層面的更廣泛影響。在研究方法論上，它示範了如何系統性地保存與連結代理執行的多層次證據，為未來類似資料集的建置提供了可參考的流程與設計原則。在學術研究上，它填補了工作流程定義/輸出研究與代理行為觀察研究之間的缺口，使學者能進行更細緻的實證研究，例如分析代理失敗模式、工具使用效率或多代理協作模式。在產業實務上，它促使企業與開源社群正視代理執行可追溯性的重要性，可能推動相關工具、平台與標準的發展。在教育訓練上，這些真實的執行日誌可作為訓練與評估 AI 代理的素材，使模型能學習處理真實世界中常見的工具拒絕、提供者失敗與任務變更等情境。整體而言，GH-AWTrace 不只是一個資料集，更是一個推動代理式 AI 研究走向更嚴謹、更實證方向的基礎建設。

**Q13：GH-AWTrace 明確承認的限制有哪些？**
A：GH-AWTrace 在論文中明確承認了多項重要限制。首先，資料集的涵蓋範圍因工作流程而異，並非所有工作流程都有完整的執行記錄或日誌封存，這種不均勻的涵蓋可能影響某些分析的代表性。其次，執行日誌僅提供部分觀察（partial observations）而非完整的代理軌跡（complete agent trajectories），這意味著研究者無法從日誌中重建代理的完整思考與決策過程。再者，GitHub 的保留政策限制了資料的時間範圍——執行記錄最遠僅能追溯至 2025 年 8 月 14 日，而日誌封存則僅限於 90 天保留期內的執行，使得資料集無法涵蓋更早期的代理工作流程執行歷史。此外，部分執行記錄沒有對應的日誌封存檔（821,672 筆），可能原因包括保留、刪除、存取限制或執行未完成，但作者無法確定每個空 ZIP 的具體原因。最後，搜尋過程仰賴固定的產生器註解片語，可能遺漏使用非標準或修改過註解的工作流程。

**Q14：GH-AWTrace 在資料收集過程中遭遇了哪些失敗案例或邊界情況？**
A：GH-AWTrace 在資料收集過程中遭遇了多項失敗案例與邊界情況。在工作流程識別階段，25,227 個候選檔案中有 63 個因缺少必要的產生器標頭而被排除，另有 150 個索引的 blob 因無法擷取而被剔除，這顯示 GitHub 搜尋 API 回傳的結果並非全部有效。在日誌下載階段，821,672 筆符合條件的執行記錄沒有可下載的封存檔，作者推測可能原因包括 GitHub 的保留政策、記錄被刪除、存取限制或執行尚未完成。在已下載的 1,633,215 個 ZIP 中，有 1,070,338 個（佔約 65.5%）是空的，作者對其中 2,900 個空 ZIP 進行早期稽核，發現 2,699 個僅顯示被跳過的工作（skipped jobs），195 個則完全沒有列出工作，這暗示許多空 ZIP 並非真正的執行失敗，而是工作流程設計上跳過了所有工作或根本沒有可執行的工作。這些邊界情況提醒使用者在分析時需謹慎處理缺失資料與空封存檔，避免將其直接解讀為執行失敗。

**Q15：基於 GH-AWTrace，未來可能的研究方向有哪些？**
A：基於 GH-AWTrace，未來可能的研究方向相當多元。在失敗分析方面，可深入研究代理工作流程的常見失敗模式、錯誤恢復策略與失敗預測模型，協助設計更可靠的代理系統。在工具使用方面，可分析代理如何選擇、組合與切換工具，研究工具設計對代理效能的影響，並探討工具拒絕的頻率與原因。在多代理協作方面，可深入研究代理之間的委派模式、責任分配與溝通機制，理解複雜代理系統的協調行為。在安全性方面，可利用日誌分析提示注入攻擊、權限提升嘗試與異常代理行為的實際發生情形。在評估方法論方面，可研究如何從部分觀察（partial observations）推論代理的完整軌跡，或設計新的評估指標來衡量代理的真實表現。此外，隨著 GitHub Agentic Workflows 的持續演進，未來可建立類似但更專注的資料集，例如針對特定領域（如安全、測試、文件）或特定 AI 提供者的執行日誌，以支援更深入的研究。

## 實務應用指南

### 適用場景

**1. AI 代理執行失敗的根因分析平台**
建構一個診斷工具，自動分析 GH-AWTrace 中 562,877 個非空執行日誌封存，識別工具拒絕、提供者失敗、權限不足等失敗模式。產品團隊可據此建立「失敗模式知識庫」，讓 gh-aw 使用者在部署前預先避開已知陷阱。例如，分析 Azure/azure-dev 中因儲存庫設定阻擋而無法開啟拉取請求的案例，自動產生對應的權限設定建議。

**2. 代理工具使用行為基準研究**
利用 4,112,526 筆執行記錄與對應日誌，建立「AI 代理在真實軟體工程任務中的工具使用基準」。研究人員可量化代理呼叫 `git commit`、`gh pr create`、測試執行器等工具的頻率、順序與失敗率，作為評估新代理框架（如 LangChain、AutoGen）的對照組。

**3. 提示注入攻擊防禦評估**
結合 Wang 等人 [10] 與 Isbarov 等人 [11] 的提示注入研究，從 GH-AWTrace 的執行日誌中萃取真實的代理互動序列，訓練或驗證提示注入偵測器。資料集中跨 5,051 個儲存庫的多樣性可避免過度擬合單一組織的攻擊模式。

**4. 代理協作與委派模式挖掘**
針對資料集中展示的「代理之間的委派」案例，開發圖神經網路模型，分析多代理工作流程中的任務分配、責任轉移與瓶頸環節，輸出最佳實踐範本給企業內部採用。

**5. 執行結果與任務進度的落差稽核**
利用資料集中「回報的執行結果」與「可見的任務進度」之間的落差（例如：回報成功但日誌顯示部分步驟被跳過），建立 CI/CD 信任分數系統，協助維護者在合併前判斷 AI 代理產出的拉取請求是否值得信賴。

**運算資源**
- 處理 562,877 個 ZIP 封存需要平行化 I/O，建議配備 SSD 儲存與至少 16 核心 CPU
- 若進行大規模 NLP 分析（如代理軌跡重建），建議使用 GPU 加速（NVIDIA A100 或同等級）
- 記憶體需求依分析粒度而定：基礎統計 32 GB 即可，深度學習模型則需 128 GB 以上

**技能門檻**
- 熟悉 GitHub Actions YAML 結構與 gh-aw 編譯流程
- 具備 Python 資料處理能力（Pandas、Polars、Dask）
- 經驗使用日誌分析工具（grep、awk、Elastic Stack 或 Loki）
- 對 LLM 代理框架（LangChain、AutoGen、CrewAI）有基本認識
- 軟體工程研究方法論基礎（用於設計可重現的實驗）

### 實作步驟建議

**步驟一：資料取得與完整性驗證**
從論文指定的資料集託管位置下載所有檔案，使用論文中提到的 SHA-256 雜湊值驗證 ZIP 完整性。將 1,633,215 個封存依 `run_id` 與 `attempt_number` 建立索引，並過濾出 562,877 個非空封存作為主要分析對象。

**步驟二：日誌結構化與標準化**
解壓縮封存後，將異質的 GitHub Actions 日誌（包含 shell 輸出、代理推理片段、工具呼叫記錄）統一轉換為結構化格式（如 JSON Lines）。建立解析器處理常見模式：時間戳記、代理訊息、工具呼叫、錯誤堆疊。

**步驟三：建立分析維度**
依據論文的圖 2 結構，建立四層分析視圖：
1. 儲存庫層：5,051 個儲存庫的元資料與工作流程分布
2. 工作流程層：25,014 個已驗證 gh-aw 的觸發條件與權限設定
3. 執行層：4,112,526 筆執行記錄的成功率與持續時間
4. 日誌層：562,877 個封存中的工具互動序列

**步驟四：執行案例研究**
重現論文中的四個說明性案例（工具拒絕、提供者失敗、方法變更、代理委派），驗證資料集的可用性，並擴展至您關注的特定失敗模式。

**步驟五：產出可重現的分析產物**
將分析結果封裝為 Jupyter Notebook + Docker 映像，附上資料載入腳本，使其他研究者能復現您的發現。建議在 Zenodo 或 Hugging Face Datasets 發布衍生資料集。

**步驟六：整合回產品工作流**
將分析得到的失敗模式規則化為 CI/CD 檢查（例如：GitHub Action 預先掃描 gh-aw 設定檔），或包裝為 gh-aw 擴充套件供社群使用。

### 潛在風險與注意事項

**資料偏差風險**
GH-AWTrace 僅涵蓋公開儲存庫且使用 gh-aw 框架的工作流程，可能高估企業級採用率而低估小型開源專案的真實狀況。緩解方式：在解讀結論時明確標註母體限制，並與其他代理框架資料集（如 SWE-bench）交叉比對。

**時間衰減問題**
GitHub 在 90 天後刪除日誌、400 天後刪除執行記錄，論文的資料截止於 2026 年 9 月 21 日。隨時間推移，資料集將無法反映最新的代理行為演化。緩解方式：建立定期更新機制，或與 GitHub 合作取得保留協議。

**隱私與憑證外洩**
執行日誌可能包含開發者無意中輸出的憑證（論文 Azure/azure-dev 案例中即提及「從 URL 中遮罩憑證」）。處理資料時務必：
- 對所有日誌執行憑證掃描（使用 TruffleHogg 或 gitleaks）
- 在發布衍生資料集前進行脫敏處理
- 遵守 GitHub 的資料使用條款

**部分觀察的限制**
論文明確指出日誌僅提供「部分觀察」而非「完整代理軌跡」，因為 GitHub Actions 的日誌截斷、敏感資訊遮罩都可能造成訊息缺失。緩解方式：將分析結論視為「下限估計」，並在論文中誠實標註不確定性。

**儲存庫設定異質性**
5,051 個儲存庫的權限、網路設定、代理模型版本各異，跨儲存庫比較時需控制混淆變數。建議使用傾向分數匹配（propensity score matching）或分層分析。

### 與其他技術的整合建議

**與 LLM 代理框架整合**
將 GH-AWTrace 的失敗模式注入 LangChain、AutoGen 的代理提示詞中，作為「負面範例」提升代理的穩健性。例如：將工具拒絕案例轉化為 ReAct 代理的 fallback 策略。

**與可觀測性平台整合**
把 562,877 個日誌封存匯入 Elastic Stack、Loki 或 Datadog，建立「AI 代理可觀測性儀表板」，讓 DevOps 團隊即時監控 gh-aw 工作流程的健康度。

**與靜態分析工具整合**
結合 Wang 等人 [10] 的靜態分析路徑，在 CI 階段先用 Semgrep 或 CodeQL 掃描 gh-aw 設定檔，再用 GH-AWTrace 的歷史模式進行風險評分。

**與 MLOps 平台整合**
將分析結果回饋至 MLflow 或 Weights & Biases，追蹤不同代理模型（GPT-4、Claude、Gemini）在 gh-aw 工作流程中的表現差異，建立模型選型的實證依據。

**與威脅情報平台整合**
將提示注入攻擊案例整合至 MISP 或 OpenCTI，豐富 AI 代理威脅的情報來源，協助 SOC 團隊建立針對性的防禦規則。

### 給不同背景讀者的閱讀建議

**給初學者**：先閱讀摘要與第一節（Introduction），重點理解「gh-aw 是什麼」以及「為什麼執行日誌值得保存」。建議搭配官方 gh-aw 文件閱讀，並實際建立一個簡單的 gh-aw 工作流程，親身體驗觸發條件、權限設定與執行記錄的對應關係，再回頭看資料集結構會更容易吸收。

**給 AI 工程師**：直接聚焦第二節（Dataset Collection and Curation）與第三節（Dataset Characteristics），理解資料的取得流程、覆蓋範圍與已知限制。在建構代理系統時，將 GH-AWTrace 視為「真實世界的壓力測試資料」，特別關注工具拒絕與提供者失敗案例，這些都是您在設計 fallback 機制時的寶貴參考。

**給研究人員**：完整閱讀全文並特別注意論文中標註的限制（部分觀察、覆蓋變異、保留政策），這些將直接影響您研究的外部效度。建議將 GH-AWTrace 與 SWE-bench、HumanEval 等基準資料集結合使用，並考慮發表衍生資料集時如何處理時間衰減問題，這將是該領域持續發展的重要議題。

**給產品經理**：重點閱讀摘要中的四個說明性案例（工具拒絕、提供者失敗、方法變更、代理委派），這些是您在向利害關係人說明「為什麼需要 AI 代理可觀測性」時最有說服力的素材。在規劃產品時，將 GH-AWTrace 視為「競品分析與最佳實踐的寶庫」，特別是 Azure/azure-dev 的案例展示了如何將代理產出轉化為可審閱的拉取請求，這對設計人機協作流程極具參考價值。
