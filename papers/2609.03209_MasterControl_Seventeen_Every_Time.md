## ⚡ TL;DR

解決企業分析中答案意義難以固定、模型即興設計衡量方法的問題。
語言模型僅詮釋意圖，確定性策略選取預先核准的型別化分析程式，輸出結果與證據。

## 摘要翻譯

我們研究一種受治理的企業分析方法（Governed Data Analysis）：語言模型（language model）詮釋問題，而確定性策略（deterministic policy）選擇並執行預先核准的分析程式（pre-approved analytical program），同時回傳結果與證據（result and evidence）。我們證明，在已定義的分析類別（analytical class）內，這樣的限制仍保有表達能力（expressiveness），可運用關聯式運算（relational operations）以及聚合（aggregation）、比較（comparison）、視窗運算（windows）、排名（ranking）與相似度（similarity）。固定的受治理語義（governed meaning）、策略、資料與執行規則，亦使結果具有可重現性（replay）。在 440 次執行中，三個 8B 開源模型（8B open-source models）於執行期生成 SQL 程序（SQL procedure）並選擇工具（tool selection）；Qwen3-8B 僅負責詮釋意圖（intent interpretation），再由策略執行已核准的程式。在 330 個執行期規劃回合（runtime-planning episodes）中，沒有任何一回合能在所有測試資料集上完全符合答案與證據契約（answer-and-evidence contract）；策略執行的分析器（policy-executed analyzer）則在 110 次中全部符合。此結果僅適用於特定組態，並不能證明執行期智慧體（runtime agents）在其他設計下無法成功。

### 核心貢獻（3～5點）
- 提出受治理的企業分析架構：語言模型僅負責意圖詮釋，確定性策略則選擇並執行預先核准的分析程式，輸出結果與可驗證證據。
- 證明在限定的分析類別內，結合關聯式運算、聚合、比較、視窗運算、排名與相似度，仍具有充足的表達能力。
- 透過固定語義、策略、資料與執行規則，確保分析結果具備可重現性。
- 實證比較顯示：執行期規劃方法在 330 個回合中未能完全符合答案與證據契約，而策略執行的分析器達成 110/110。
- 謹慎指出此結果僅反映特定組態，並不排除其他設計下執行期智慧體成功的可能性。

### 適合對象
適合企業資料分析、AI 治理、可解釋 AI、資料庫與資料系統領域的研究者，以及關注語言模型在受監管或高風險產業中安全、可驗證部署的實務人員與政策制定者。

## 深度分析

#### 方法論解析

本研究提出一種「受治理資料分析（Governed Data Analysis）」架構，核心設計是將**語言模型（language model）**的角色嚴格限定為「意圖詮釋（intent interpretation）」，而真正的**衡量方法（measuring method）**則由**確定性策略（deterministic policy）**從**預先核准的分析程式（pre-approved analytical program）**目錄中選取並執行。這條架構邊界可概括為：模型可以解讀問題，但不能選擇分析方法。

在概念層次，作者將一次正確的分析輸出視為一個結構化契約：
\[
R=(m, v, E)
\]
其中 \(m\) 為**受治理語義（governed meaning）**，\(v\) 為**分析值（analytical value）**或表格，\(E\) 為帶角色標註的**支援記錄（supporting records）**。此外，系統還會產生一份執行憑證，記錄資料快照、策略版本、程式版本、核心版本與序列化規則，以確保結果可被事後檢驗與重現。

為了證明這種限制不會過度犧牲**表達能力（expressiveness）**，作者建構了一個「小型分析代數（Small Analytical Algebra）」，包含八個實務運算家族：

1. **RESTRICT**：決定哪些記錄符合資格，例如「已核准的溫度偏移偏差（approved temperature-excursion deviations）」。
2. **SHAPE**：決定輸出欄位與確定性衍生欄位，例如將持續時間換算為小時。
3. **RELATE**：決定如何以受控方式連結不同關聯，例如將偏差連結到場所、批次、設備或 CAPA。
4. **AGGREGATE**：決定計算粒度，例如按場所計算相異偏差數。
5. **COMPARE**：決定基準或分母，例如與網路基準比較場所比率。
6. **WINDOW**：決定時間或有序框架，例如「上週」是**日曆週（calendar week）**還是**滾動七天（trailing seven days）**。
7. **RANK**：決定全序與平手規則，例如回傳貢獻最高的場所。
8. **SIMILAR**：決定版本化的語義或數值鄰近規則，例如以固定相似度對自由文字原因分群。

這八個家族並非讓模型在執行期即興組合，而是對應到預先撰寫、審查、版本化的程式。舉例來說，「上週發生多少起已核准溫度偏移偏差？」這個問題可能對應到：
\[
\text{RESTRICT[approved population]} \to \text{WINDOW[previous calendar week]} \to \text{RESTRICT[temperature-excursion definition]} \to \text{AGGREGATE[count distinct deviation\_id]} \to \text{SHAPE[result + evidence]}
\]

在理論基礎上，作者從**有限關聯（finite relations）**與**一階滿足性（first-order satisfaction）**出發，證明對於任何有限域上的一階規格 \(q_\phi\)，都可以建構性地轉譯為由 RESTRICT、SHAPE、RELATE 組成的有限程式；反之，每個這類核心程式也都有等價的有限域一階規格。這個結果被稱為**範圍完整性（scoped completeness）**：相對於一個明確陳述的**分析類別（analytical class）**，語言是完備的，但它並非**通用程式設計系統（general-purpose programming system）**，且實際部署的**策略目錄（policy catalog）**也不必涵蓋所有可能問題。

進一步地，作者將聚合、比較、視窗、排名與**版本化相似度（versioned similarity）**納入語言，以擴展可表達的分析類別。這裡的關鍵在於「版本化」：相似度規則不是執行期由模型即興決定，而是預先固定並納入版本控制，從而避免「同樣的問題在不同時間得到不同衡量方法」的風險。

最後，作者證明了**可重現性（replay）**：若**受治理語義（governed meaning）**、**策略（policy）**、資料、**核心狀態（kernel state）**、**數值規則（numerical rules）**與**輸出契約（output contract）**全部固定，則結果與證據必然相同。這對於受監管產業（如製藥、醫療器材、航空）至關重要，因為這些場域不僅需要答案，還需要能夠被稽核的證據鏈。

#### 實驗數據解讀

本研究的實驗設計是一場**受控比較（controlled comparison）**，共進行 440 次執行。對照組採用**執行期工具規劃（runtime tool planning）**：三個獨立的 8B **開源模型（open-source models）**自行決定如何查詢資料、選擇工具，並在執行期生成 **SQL 程序（SQL procedure）**。實驗組則由 **Qwen3-8B** 僅負責詮釋使用者意圖，之後由**確定性策略（deterministic policy）**選取並執行對應的**預先撰寫分析程式（pre-written analytical program）**。

評估指標是「**答案與證據契約（answer-and-evidence contract）**」是否被完整滿足。這不僅檢查數值是否正確，還檢查結果是否附帶正確的**支援記錄（supporting records）**、是否使用正確的母體定義、時間區間與度量方式。

實驗結果非常懸殊：

- 在 330 次**執行期規劃回合（runtime-planning episodes）**中，對照組沒有任何一次在開發快照與四個**保留變體（held-out variants）**上完整滿足答案與證據契約。
- 在 110 次**策略執行的分析器（policy-executed analyzer）**回合中，實驗組全部 110 次都滿足契約。

這個 0/330 對上 110/110 的對比，是本研究最主要的實證主張：在這個特定設定下，**執行期規劃（runtime planning）**在主要指標（primary metric）上未能成功，而受治理的確定性執行則達到完全可靠。

然而，作者非常謹慎地將此結果框定為「經驗性且設定特定（empirical and configuration-specific）」。他們明確指出，這並非證明執行期代理人在其他搜尋、驗證、模型或工具設計下無法成功。這種自我限縮很重要，因為 8B 模型在複雜企業資料庫上生成正確 SQL 與選擇正確工具本來就極具挑戰性；若換用更大模型、更強的驗證器、或更豐富的 few-shot 示例，結果可能不同。

從資料解讀角度，有幾個值得注意的細節：

1. **樣本規模與統計意義**：440 次執行中，對照組佔 330 次、實驗組佔 110 次。雖然實驗組 100% 通過，但樣本量相對有限，且未報告置信區間或變異數分析。對照組的 0% 通過率雖然強烈，但我們不知道失敗模式分布：是全部卡在工具選擇、SQL 語法、JOIN 條件、時間區間詮釋、還是證據標註？
2. **保留變體的設計**：四個 held-out variants 用於測試泛化能力。對照組在開發快照與所有保留變體上都未達標，暗示問題不僅是過擬合開發集，而是根本無法穩定產出符合契約的程式。但論文未詳細說明這些變體如何構造（例如是改變資料分布、改變問題措辭、還是改變 schema），這會影響我們對泛化結論的判斷。
3. **Qwen3-8B 的角色**：實驗組中 Qwen3-8B 只負責「詮釋意圖」，並不生成 SQL。這意味著 110/110 的成功部分來自於「意圖詮釋正確」與「策略目錄涵蓋該意圖」兩個前提。若使用者問題超出目錄範圍，系統可能無法回答，這是設計上的權衡。
4. **證據契約的嚴格性**：相較於傳統 SQL 正確率評估，本研究要求「結果 + 證據」同時正確。這提高了門檻，也更能反映企業稽核需求。對照組的失敗很可能部分來自於「生成數值正確但證據不完整或標註錯誤」。

總體而言，實驗數據強力支持作者的核心論點：在需要嚴格語義治理的企業分析場景中，將分析方法從語言模型中抽離、轉交給確定性策略執行，能顯著提升可靠性與可稽核性。但讀者不應將此解讀為「所有 runtime agent 都無用」，而應理解為「在這個特定配置與評估標準下， governed execution 更可靠」。

#### 與現有研究的比較

本研究處於幾個活躍研究領域的交會點：**文字轉 SQL（Text-to-SQL）**、**工具學習（tool learning）**、**可解釋 AI（explainable AI）**、**可重現性研究（reproducibility）**以及**受監管產業的 AI 治理（AI governance in regulated industries）**。以下從定位、改進與限制三方面進行比較。

##### 定位

傳統 **Text-to-SQL** 研究（如 Spider、BIRD 基準）通常將整個問題視為「從自然語言生成 SQL」，模型同時負責語意理解與程式合成。近年來的 **tool-using agents** 與 **LLM-based data analysts**（例如使用 LangChain、AutoGPT、或專門的資料分析代理）進一步將工具選擇、查詢規劃、執行與反思都交給語言模型。這些方法追求靈活性與廣泛覆蓋，但代價是執行期行為難以預測與稽核。

本研究採取相反路線：它不是要讓模型學會更多 SQL 技巧，而是要「縮小模型能決定的範圍」。這與軟體工程中的「策略模式（policy pattern）」、資料庫領域的「儲存程序（stored procedure）」、以及監管科學中的「標準作業程序（SOP）」精神一致。作者明確將此架構與「執行期工具規劃（runtime tool planning）」對立，強調後者雖然靈活，卻在受治理場域中難以保證語義穩定性。

##### 改進與貢獻

相較於現有研究，本研究的主要貢獻包括：

1. **將「證據」納入輸出契約**：多數 Text-to-SQL 評估只檢查執行結果是否正確，少數檢查 SQL 是否等價。本研究要求輸出必須包含角色標註的支援記錄，這對於需要稽核追蹤的企業應用更為實用。
2. **明確區分「意圖詮釋」與「分析方法選擇」**：這是一條清晰的架構邊界，有助於系統設計者決定哪些部分可以交給機率模型、哪些部分必須由治理機制控制。
3. **提供理論保證**：透過有限域一階邏輯與關聯式代數的對應，作者證明了在限定分析類別內，預先撰寫的程式語言具有**範圍完整性（scoped completeness）**。這比一般經驗性 Text-to-SQL 研究多了形式化基礎。
4. **強調可重現性（replay）**：作者證明在固定條件下結果必然相同。這與機器學習領域近年對 reproducibility 的關注相呼應，但更進一步將其應用到企業分析流程。
5. **受控實驗設計**：透過同時測試三個 8B 開源模型與 Qwen3-8B + 策略執行，作者提供了相對公平的比較基準。

##### 限制

本研究也有明顯限制，作者與讀者都應正視：

1. **設定特定性（configuration-specificity）**：作者已坦承，實驗結果不能推廣到所有 runtime agent 設計。對照組使用 8B 模型，可能無法代表更大模型（如 70B 或 GPT-4 級別）的表現。
2. **策略目錄的建構成本**：預先撰寫、審查、版本化所有分析程式需要大量領域專家投入。對於快速變動的業務場景，這種成本可能過高。
3. **表達能力邊界**：雖然作者證明了範圍完整性，但「範圍」本身由作者定義。超出該分析類別的問題（例如需要迭代探索、機器學習推論、或動態資料清理的問題）可能無法被涵蓋。
4. **意圖詮釋錯誤的風險**：雖然分析方法由策略固定，但如果 Qwen3-8B 將使用者問題詮釋錯誤，系統仍會執行錯誤的程式並產生「看似正確」的結果。論文未深入討論如何偵測或緩解這類錯誤。
5. **缺乏失敗模式分析**：對照組 0/330 的失敗率雖然醒目，但論文未詳細拆解失敗原因。若能區分「SQL 語法錯誤」、「語意詮釋錯誤」、「工具選擇錯誤」、「證據缺失」等類型，將更有助於後續研究改進 runtime agent。

#### 可重現性評估

可重現性是本研究的核心主張之一，但我們必須區分「理論上的可重現性」與「實務上的可重現性」。

在理論層面，作者證明了 replay 定理：只要**受治理語義（governed meaning）**、**策略（policy）**、資料、**核心狀態（kernel state）**、**數值規則（numerical rules）**與**輸出契約（output contract）**固定，結果與證據就會相同。這是一個強形式的可重現性保證，遠超過一般機器學習實驗僅報告「隨機種子固定」的層次。

在實務層面，根據目前提供的全文脈絡，論文並未明確說明是否公開以下資源：

- 原始程式碼（例如策略執行核心、八個運算家族的實作）
- 資料集（包括開發快照與四個保留變體）
- 模型權重或推論設定（三個 8B 開源模型與 Qwen3-8B 的提示、溫度參數、解碼策略）
- 預先核准的分析程式目錄
- 評估腳本與答案與證據契約的具體定義

由於這是一篇標示為 2026 年 9 月、來自 **MasterControl AI Lab** 的論文，可能處於預印本或技術報告階段。若作者未公開上述資源，則外部研究者難以完全重現 440 次執行與 0/330 對 110/110 的結果。

不過，本研究的方法論本身具有高度可重現潛力：因為分析程式是預先撰寫且確定性的，只要取得相同資料快照與策略版本，任何人都可以重新執行並得到相同輸出。這與依賴機率模型在執行期生成程式的系統形成對比——後者即使公開程式碼，也可能因為模型隨機性、API 版本更新、或提示差異而產生不同結果。

對於希望重現此研究的讀者，建議關注以下關鍵元件是否被釋出：

1. **Governed meaning 的規格語言**：如何將自然語言問題對應到受治理語義？
2. **Policy catalog**：預先核准程式的組織方式、版本控制與選取邏輯。
3. **Kernel 實作**：八個運算家族的型別系統、錯誤行為與證據語義。
4. **評估契約**：答案與證據契約的正式定義與自動檢查機制。
5. **對照組設定**：三個 8B 模型的身份、提示工程細節、工具描述格式與執行環境。

若這些資源未公開，本研究的可重現性將主要停留在概念與方法論層次，而非實證層次。

#### 未來研究方向

基於本研究的架構與結果，以下幾個方向值得進一步探索：

1. **混合式架構（hybrid architecture）**：能否讓 runtime agent 負責探索與草案生成，再由治理層進行驗證與轉換為預先核准程式？這可能結合靈活性與可靠性，例如在發現新問題類型時，由 agent 提出程式草案，經專家審查後納入策略目錄。
2. **意圖詮釋的錯誤偵測與緩解**：既然 Qwen3-8B 只負責詮釋意圖，如何確保詮釋正確？未來可研究不確定性量化、多模型共識、或使用者確認機制，以降低「選對程式但詮釋錯問題」的風險。
3. **策略目錄的自動擴展**：如何從歷史問題與資料 schema 中自動生成或補全預先核准程式？這涉及程式合成、主動學習與領域專家回饋的結合。
4. **更大規模與更強模型的對照實驗**：本研究使用 8B 模型作為 runtime planner。未來應測試 30B、70B 乃至 GPT-4 級別模型，並引入驗證器、反思機制與單元測試，以判斷 runtime agent 的失敗是模型能力問題還是架構本質問題。
5. **失敗模式的細緻分類**：對 runtime planning 的 330 次失敗進行詳細分類，區分語法錯誤、語意錯誤、工具選擇錯誤、證據缺失等，將有助於針對性地改進 agent 設計。
6. **跨產業驗證**：本研究案例來自製藥或醫療器材領域的偏差管理。未來可在金融風控、供應鏈、醫療紀錄等其他受監管領域驗證此架構的適用性與建構成本。
7. **時間與版本語義的形式化**：論文提到「last week」可能指日曆週或滾動七天。未來可發展更完整的時間本體論與版本化語義框架，讓策略目錄能明確處理各種時間詮釋。
8. **與現有資料治理工具的整合**：如何將此架構嵌入現有的資料目錄（data catalog）、資料品質框架與 MLOps 管線中，也是實務部署的重要課題。

總結來說，本研究為「受治理的企業分析」提供了一個清晰的方法論與強而有力的實證對比。它提醒我們：在高度監管的場域中，產生正確數字固然重要，但保留「這個數字意味什麼」的證據鏈，才是值得信賴的分析系統真正的核心挑戰。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼標題強調「17 不只是一個數字」？**
A：論文指出，在受治理的企業分析中，困難不在於產生一個數值，而在於保存這個數值所代表的意義。同樣是「17」，可能因為「上週」被定義為日曆週或滾動七天、因為「溫度偏移偏差」採用受控類別或自由文字的語義相似度、或因為連結到偏差記錄或觀察列而代表完全不同的母體。因此，作者主張答案應被視為一個結構化契約，包含受治理語義、分析值與角色標註的支援記錄，而非單純的純量。

**Q2：現有的執行期語言模型生成 SQL 或工具規劃方法，為何在受治理場景中會失效？**
A：這類方法讓模型在每次請求時決定如何查詢資料、使用哪些工具、如何連結與篩選，以及何時停止，這等於是在執行期設計衡量方法。由於每次都可能選擇不同的連結、過濾條件與聚合粒度，結果的母體、時間區間與度量定義難以保持一致。此外，執行期規劃產生的程序通常缺乏版本化的輸出契約與支援記錄，導致結果難以重現與稽核。

**Q3：為什麼對受治理分析而言，「保存意義」比「生成數字」更重要？**
A：在法規嚴謹的產業中，決策者與稽核人員必須知道數字背後的對象群體、時間區間、衡量指標與定義，才能判斷答案是否可用。如果兩個系統印出相同的數字卻測量不同母體，這個數字不僅無法比較，還可能誤導決策。因此，論文將重點放在如何透過預先核准的分析程式與確定性策略，確保每次回答都附帶可檢驗的證據與執行憑證。

**Q4：論文提出的核心架構邊界是什麼？語言模型與確定性策略各自扮演什麼角色？**
A：核心邊界是「語言模型可以詮釋問題，但不能選擇分析方法」。語言模型負責將使用者的自然語言轉換為受治理語義，例如辨識出「上週的溫度偏移偏差」這個意圖。接下來，確定性策略會根據這個詮釋結果，選擇並執行對應的預先核准分析程式，整個分析過程由策略與版本化程式碼固定，而非由模型即興生成。

**Q5：什麼是「小型分析代數」？為什麼作者認為這八個運算族足以涵蓋所需的分析類別？**
A：小型分析代數包含 RESTRICT、SHAPE、RELATE、AGGREGATE、COMPARE、WINDOW、RANK 與 SIMILAR 八個運算族，每個運算都有明確的型別輸入、輸出、參數、錯誤行為與證據語義。這些運算對應到企業分析中反覆出現的需求：篩選合格記錄、決定輸出欄位、連結治理關聯、指定聚合粒度、設定比較基準、套用時間或有序視窗、定義排名規則，以及使用版本化相似度。作者進一步證明，從有限關聯與一階滿足性出發，可以建構式地轉譯為這些關聯式運算，因此在限定的分析類別內具有範圍完整性。

**Q6：什麼是「範圍完整性」與「可重現性」？它們在理論上如何被保證？**
A：範圍完整性指的是：對於限定分析類別中的每一個一階規格，都存在一個由這些運算組成的有限程式能夠精確實現它，但這並不表示該語言是通用程式設計系統，也不代表部署的策略目錄必須涵蓋所有可能問題。可重現性則來自於執行憑證：只要受治理語義、策略版本、程式版本、資料快照、核心狀態、數值規則與輸出契約都固定，就能推導出相同的結果與證據。這兩項性質讓分析從「每次可能不同」轉變為「可被審查與重播」。

**Q7：實驗如何設計？對照組與實驗組分別是什麼？**
A：實驗共進行 440 次執行，分為兩種回答相同分析問題的方式。對照組讓三個獨立的 8B 開源模型在執行期自行決定如何查詢資料、選擇工具，並生成 SQL 程序。實驗組則由 Qwen3-8B 只負責意圖詮釋，之後由確定性策略選擇並執行對應的預先核准分析程式。評估涵蓋開發快照與四個保留變體，以檢驗兩種方法是否滿足完整的答案與證據契約。

**Q8：實驗的主要結果是什麼？兩種方法的表現差距有多大？**
A：在 330 個執行期規劃回合中，沒有任何最終程序能夠在開發快照與所有四個保留變體上同時滿足完整的答案與證據契約。相對地，由策略執行的分析器在 110 個回合中全部達成契約，成功率為 110/110。這顯示在該特定設定下，執行期工具規劃在主要指標上未能成功，而確定性策略執行則能穩定提供符合契約的結果與證據。

**Q9：這個結果是否代表執行期代理完全不可行？作者如何解釋這個差距？**
A：作者明確指出，這是一個「設定特定」的經驗結果，並不是證明執行期代理在其他搜尋、驗證、模型或工具設計下無法成功。差距主要來自於執行期規劃必須同時決定查詢方式、工具選擇、連結條件、篩選條件、執行順序與停止規則，任何一個環節出錯都會破壞答案與證據契約。相較之下，策略執行的分析器把這些選擇提前納入預先核准且版本化的程式中，從而消除了執行期的不確定性。

**Q10：這套方法最適合哪些實務場景？**
A：這套方法特別適合需要嚴格稽核軌跡與一致定義的企業分析，例如製藥業的品質偏差統計、醫療器材的溫度偏移偏差追蹤，或任何受法規監管的製造數據報告。在這些場景中，「有多少已核准的溫度偏移偏差上週發生」這類問題必須附帶明確的母體、時間區間與支援記錄。透過預先核准的分析程式與執行憑證，組織可以向稽核人員證明結果是如何產生的。

**Q11：若要把這套系統產品化，需要哪些關鍵設計考量？**
A：產品化時需要建立並維護一個策略目錄，其中每個受支援問題都對應到一個經過審查與版本控制的預先核准分析程式。語言模型只應部署在語義介面層，負責將自然語言對應到治理目錄中的受治理語義，而核心分析則由確定性策略執行。此外，系統必須記錄資料快照、策略版本、程式版本、核心版本與序列化規則，以確保每次執行都可重現與審查。

**Q12：這項研究對整個領域可能帶來什麼影響？**
A：這項研究提供了一個重要的設計典範轉移：從完全由模型在執行期即興規劃的「黑箱代理」，轉向由策略與版本化程式治理的「可審查分析器」。它有助於提升企業分析的可重現性、合規性與信任度，特別是在高風險決策場景中。同時，作者謹慎地避免過度推論，強調這只是特定設定下的比較，為未來混合式設計留下空間。

**Q13：作者承認哪些限制？**
A：作者明確表示，實驗結果是經驗性且設定特定的，不能推廣為所有執行期代理都無法成功。此外，這套小型分析代數並非通用程式設計系統，部署的策略目錄也不需要、也不可能涵蓋所有可能的問題。當問題超出預先定義的分析類別時，系統可能無法提供對應的預先核准程式。

**Q14：在什麼情況下這套系統可能失敗或表現不佳？**
A：如果語言模型在語義介面層錯誤詮釋使用者意圖，後續的確定性策略就會選擇錯誤的預先核准程式，導致答案雖然可重現卻不符合使用者真正想問的問題。此外，當問題需要未經核准的衡量方法、新的資料連結方式，或超出八個運算族所能表達的分析類別時，策略目錄中可能沒有對應程式可用。這些情況顯示，系統的覆蓋範圍取決於策略目錄的完整度與模型詮釋的準確度。

**Q15：未來可以朝哪些方向延伸這項研究？**
A：未來可以擴充策略目錄，並發展自動化或輔助式的策略合成與驗證工具，以降低人工撰寫預先核准程式的負擔。另一個方向是探索受約束的執行期搜尋，例如在預先定義的程式骨架內允許有限的參數選擇，以兼顧彈性與可重現性。此外，也可以進一步強化證據語義、擴展到更多模型規模與工具設計的比較，並研究如何將這套框架應用到更廣泛的企業分析領域。

## 實務應用指南

### 適用場景

1. **製藥與生技的 GxP 品質偏差追蹤**  
   例如「上週發生多少起已核准的溫度偏移偏差？」這類問題必須同時回答數字與支援記錄。透過預先核准的分析程式，系統固定母體、時間區間、度量與定義，並回傳角色標註的證據，滿足法規稽核對「答案與證據契約」的要求。

2. **醫療機構的臨床指標監管**  
   當需要比較各院區的感染率與全網路基準線時，可用受治理語義統計「各院區 distinct 事件數」並執行比較與排名。確定性策略執行讓不同院區在相同資料快照下得到可重現的結果，避免各單位自行設計衡量方法。

3. **金融合規與反洗錢交易監控**  
   針對有界、唯讀的企業分析，例如「某客戶群在過去一週內異常交易筆數」，可將風險定義、時間視窗、聚合粒度寫入策略目錄。語言模型僅負責意圖詮釋，實際查詢由預先撰寫的分析程式執行，降低執行期工具規劃帶來的不可預測性。

4. **製造與供應鏈營運儀表板**  
   用於「本週與上週相比，前五大貢獻站點為何」這類包含視窗、排名與基準比較的問題。將視窗定義、排名規則與相似度分群版本化後，儀表板能穩定輸出結果與其證據，便於營運會議追蹤。

5. **政府與公共部門的開放資料問答**  
   針對固定資料集提供自然語言查詢介面，例如「哪些自由文字原因屬於某個版本化語義相似群組？」透過固定相似度規則與輸出契約，民眾與審查機關都能重現相同結論。

### 實作前置條件

**資料條件**
- 已清理、結構化的關聯式資料，並能產生不可變的資料快照。
- 明確的候選域（candidate domains）與型別化綱要，確保有限關聯假設成立。
- 領域專家已共同定義的受治理語義：母體、時間區間、度量、定義與支援記錄欄位。

**運算條件**
- 一部可執行 8B 等級語言模型的推論環境，僅用於意圖詮釋（如 Qwen3-8B）。
- 確定性執行核心，例如受版控的 SQL 核心或專用分析引擎，用於執行預先核准的分析程式。
- 策略目錄與版本控制系統，能記錄政策版本、程式版本、核心版本與序列化規則。

**技能條件**
- 領域專家：負責定義衡量方法與審查證據。
- 資料工程師：建立關聯式資料管線、快照機制與執行核心。
- 策略作者／治理工程師：將領域規則轉譯為八個運算家族的預先撰寫程式。
- 語言模型工程師：設計僅限意圖詮釋的提示與評估，避免模型跨越到方法選擇。
- 品質保證人員：設計開發快照與保留變體的迴歸測試。

### 實作步驟建議

1. **界定分析類別與受治理語義**  
   與領域專家一起列出系統要回答的問題範圍，並為每個問題固定母體、時間區間、度量、定義與支援記錄格式。

2. **建立策略目錄**  
   使用 RESTRICT、SHAPE、RELATE、AGGREGATE、COMPARE、WINDOW、RANK、SIMILAR 八個家族，將每個受支援問題撰寫成預先核准的分析程式，並進行同儕審查。

3. **建置確定性執行核心**  
   實作型別化輸入輸出、錯誤行為與證據語義，並確保核心狀態、數值規則與序列化規則都納入版控。

4. **開發意圖詮釋介面**  
   讓語言模型只將自然語言問題對應到標準化的 canonical request，不產生 SQL、不選擇工具、不決定連接或過濾條件。

5. **定義輸出契約與執行憑證**  
   輸出必須包含結果、角色標註的證據，以及記載資料快照、政策版本、程式版本、核心版本與序列化規則的執行憑證。

6. **受控驗證**  
   在開發快照與多個保留變體上，同時測試策略執行的分析器與執行期工具規劃基線，檢驗是否滿足完整答案與證據契約。

7. **部署與監控**  
   上線後持續記錄每次執行的憑證，定期執行重現測試，並監控意圖詮釋模型的漂移。

8. **持續治理與擴充**  
   新增問題時，必須經過審查並加入策略目錄，而非讓模型在執行期即興產生新方法。

### 潛在風險與注意事項

- **覆蓋範圍不足**  
  策略目錄無法涵蓋所有可能問題。應明確公告「限定範圍完備性」，對未涵蓋問題設計人工審查流程，而非強行讓模型即興處理。

- **意圖詮釋模型越界**  
  若提示設計不當，語言模型可能開始生成 SQL 或選擇工具。必須在提示、工具介面與輸出結構上嚴格限制其僅輸出 canonical request。

- **資料快照與版本不一致**  
  若資料快照、政策版本或核心狀態未固定，重現性會失效。建議使用不可變快照與單一版本來源，並將所有版本資訊寫入執行憑證。

- **語義漂移**  
  隨著業務演進，「溫度偏移」或「上週」的定義可能改變。每次定義變更都應產生新版本程式，並重新跑迴歸測試。

- **過度信賴確定性**  
  確定性執行不等於正確性。策略目錄中的程式仍可能因領域理解錯誤而有偏誤，因此證據必須可供人工檢視與稽核。

- **擴充瓶頸**  
  新增問題需經領域專家與策略作者審查，可能成為上線瓶頸。建議採用模組化程式元件與範本，加速策略目錄擴充。

### 與其他技術的整合建議

- **資料倉儲與湖倉**  
  可將執行核心對接 Snowflake、BigQuery、PostgreSQL 等關聯式引擎，利用其 SQL 能力執行預先撰寫的分析程式，但必須固定查詢計畫與序列化規則。

- **BI 與視覺化工具**  
  透過標準 API 將結果與證據餵給 Tableau、Power BI 或自製儀表板。證據欄位可讓使用者在圖表上直接下鑽到支援記錄。

- **LLM 聊天前端**  
  將語言模型僅作為對話介面，負責把使用者問題轉成 canonical request，後續由策略執行引擎回傳答案與證據，避免前端模型自行規劃工具。

- **資料治理目錄**  
  與 Alation、Collibra 等治理平台整合，讓受治理語義、母體定義與策略版本同步，確保分析定義與資料字典一致。

- **MLOps 與 CI/CD**  
  將策略目錄與分析程式納入版控與持續整合流程，每次變更都自動跑開發快照與保留變體的迴歸測試。

- **身分識別與存取控制**  
  確保執行憑證能記錄使用者角色，並與現有 IAM 系統整合，以支援證據中的角色標註與稽核追蹤。

### 給不同背景讀者的閱讀建議

**初學者**  
請先聚焦「17 不只是一個數字」這個核心動機：同樣的數字可能來自不同的母體、時間區間或定義。本論文提出一條簡單的架構邊界——語言模型負責聽懂問題，但衡量方法由預先核准的策略固定。理解這條邊界後，再回頭看八個分析運算家族與「結果與證據」的輸出契約會更容易上手。

**AI 工程師**  
請重點閱讀架構設計與實驗比較：語言模型僅做意圖詮釋、確定性策略執行預先撰寫程式的分工，八個型別化運算家族的合約，以及 440 次執行中策略執行分析器 110/110 達成契約、而執行期工具規劃 0/330 達成的受控結果。這會幫助您評估在企業場景中，何時應該把生成能力限制在介面層，而非讓模型在執行期規劃工具。

**研究人員**  
請關注理論貢獻：從有限關聯與一階滿足性出發的建構式轉換，證明相對於某個分析類別的「限定範圍完備性」，以及固定受治理語義、政策、資料、核心狀態、數值規則與輸出契約下的重現性證明。同時請注意作者強調這是特定配置下的經驗結果，並非對所有執行期代理設計的普遍性否定。

**產品經理**  
請把重點放在商業價值與落地風險：這套方法適合需要高可解釋性、可稽核與可重現的企業分析場景，例如製藥、醫療與金融合規。請評估您的問題是否落在「可預先定義衡量方法」的範圍內，並預留領域專家審查與策略目錄維護的成本。同時請把「答案與證據契約」設計成產品差異化功能，讓使用者能下鑽到每一筆支援記錄。
