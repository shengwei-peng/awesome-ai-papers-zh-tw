## ⚡ TL;DR

離線RAG的簽署知識包僅證明發布者身分，無法保證預計算向量對應其文本，造成文本-向量完整性差距。
提出「邊距定律」預測劫持率，並以量化碼比對、防護帶與規範化實現跨硬體的精確驗證。

本論文針對離線檢索增強生成（Offline RAG）系統中的「文本-向量完整性差距」（text-vector integrity gap）提出系統性的威脅模型、分析框架與防禦機制。其方法論可拆解為以下幾個核心層次：

**1. 威脅模型的形式化**

論文將攻擊者定位為「控制發布流程」（publishing pipeline）的內部人員或供應鏈攻擊者。攻擊者能夠產出表面合法的知識包（knowledge pack）：文字內容看似正常，但預計算嵌入向量（precomputed embedding vector）經過精心挑選，目的是在向量空間中將特定目標文件推到檢索結果的最前端，從而「操控檢索」（steer retrieval）。此威脅模型刻意排除對裝置本身或簽章金鑰的入侵，而是聚焦於「簽章有效但內容被污染」的灰色地帶，這與傳統軟體供應鏈攻擊（如惡意套件）有本質差異。

**2. 邊距定律（Margin Law）的推導**

論文最核心的理論貢獻是「邊距定律」：在最佳化攻擊者（optimal attacker）下，給定餘弦容忍度（cosine tolerance）τ，劫持率（hijack rate）等於角度檢索邊距（angular retrieval margin）在 arccos(τ) 處的經驗分布（empirical distribution）累積值。其直觀意義為：若誠實的相關文件與最近競爭者之間的角度差距小於 arccos(τ)，則攻擊者只需將向量旋轉至容忍度範圍內即可「劫持」該查詢。此定律的價值在於將攻擊模擬（attack simulation）轉化為可靜態測量的統計量，使操作員（operator）無需實際執行攻擊即可評估暴露程度（exposure）。

**3. 容忍度稽核的失敗模式分析**

論文系統性地分析了基於容忍度的稽核（tolerance-based audit）在不同向量儲存格式下的失效機制：
- **標量量化（SQ8, SQ4）**：每維度映射至 2^b 個層級，重建誤差隨位元數下降而放大。
- **乘積量化（Product Quantisation, PQ）**：將向量切分為子向量並以最近重心索引編碼，重建誤差可達數十度。
- **二元量化（binary quantisation）**：僅保留正負號，丟失大部分幅度資訊。

論文指出，任何比較「儲存向量」（stored vector）與「重新計算向量」（recomputed vector）的稽核都必須容忍重建誤差，而此容忍度恰好成為攻擊者的可操作空間。

**4. 精確碼級驗證（Exact Code-Level Verification）**

作為容忍度稽核的替代方案，論文提出直接比對量化碼（quantisation code）的策略。關鍵設計要素包括：
- **防護帶（guard band）**：根據實測浮點雜訊（floating-point noise）校準，避免誤拒誠實向量（honest vector）。
- **規範化（canonicalisation）**：消除因批次大小（batch size）、執行緒數、硬體架構差異導致的非確定性。
- **驗證者裁決（ambiguity decided by the verifier）**：當碼比對出現歧義時，由驗證器單方面決定，避免攻擊者利用模糊地帶。

此方法論的核心洞見是：與其容忍重建誤差，不如驗證「產生該碼的決定性過程」是否一致。

**5. 浮點與量化管線的非確定性分析**

論文揭示一個常被忽略的事實：浮點加法不具結合律（floating-point addition is not associative），因此歸約順序依賴於核心實作、批次大小、填充策略與硬體；動態 INT8（dynamic INT8）量化在執行時計算尺度（scale），使不同輸入可能改變彼此的計算路徑。這意味著即使在同一裝置上，相同輸入也可能產生位元不同的輸出，徹底挑戰「位元可重現性」（bit-reproducibility）的傳統假設。

#### 實驗數據解讀

**1. 邊距定律的實證驗證**

論文在五個語料庫（SQuAD 2.0 可回答問題加上四個 BEIR 測試集）與兩個嵌入模型（embedding model）上驗證邊距定律。實驗結果顯示：
- 在浮點雜訊級別的理想化容忍度下，最多 5.5% 的查詢被暴露；排除完全重複文件（exact duplicate document）後，單一語料庫的暴露率上限降至 1.2%。
- 當閾值校準自 CPU INT8-FP32 比較的誠實餘弦值（honest cosine）0.1% 分位數（quantile）時，暴露率躍升至 98–100%。

此數據揭示一個關鍵張力：容忍度若設得過寬（容納量化誤差），則幾乎所有查詢都可被劫持；若設得過窄（僅容納浮點雜訊），則仍存在可測量的暴露。邊距定律的價值在於讓操作員能根據業務風險容忍度，明確量化此權衡。

**2. 壓縮向量儲存的暴露程度**

針對 FAISS 等向量資料庫（vector database）的常見壓縮格式，實驗結果如下：
- **SQ8**：2–15% 查詢暴露。
- **SQ4**：55–89% 查詢暴露。
- **PQ**：約 100% 查詢暴露。
- **二元量化**：100% 查詢暴露。

更具警示意義的是，在真實 FAISS 索引（57,638 份文件）上執行的攻擊實驗：所有篡改向量（tampered vector）皆通過容忍度檢查，但攻擊者的文件在 25% 的目標查詢中排名第一。這證明容忍度稽核在實際部署中完全無效。

**3. 精確驗證的效能**

採用碼級驗證搭配校準防護帶與規範化規則後，在三個平台（樹莓派 5、桌面、Apple M2）與四個計算後端上，所有誠實向量樣本皆被接受，且發布者（publisher）無任何操縱空間。此結果證明精確驗證在異質硬體（heterogeneous hardware）上的可行性。

**4. 端到端影響與裝置成本**

在樹莓派 5 執行本地 Qwen2.5-3B 模型的場景下：
- 攻擊將正確答案（correct answer）比例從 0.75 降至 0.39（INT8 參考閾值下）。
- 驗證程序佔用 CPU，使並發運行的 LLM 解碼速度降低 23–31%。
- 12 種結構性更新攻擊全部被多層封包驗證機制拒絕。

此數據呈現一個務實的工程權衡：安全性提升伴隨可量化的效能成本，但相較於攻擊造成的正確率腰斬（從 75% 降至 39%），此成本顯然值得。

**5. 預先註冊的負面結果**

論文誠實報告三項預先註冊（pre-registered）的負面結果（negative result）：棄答（abstention）、上下文剪枝（context pruning）與語意篩選（semantic screening）皆無法有效防禦此攻擊。這種學術誠信值得肯定，避免後續研究者重蹈覆轍。

論文引用並延伸了近期關於 LLM 服務非確定性的研究 [19]，指出核心（kernel）對批次組成的非不變性同樣影響嵌入管線。相較於既有研究聚焦於生成階段，論文將此分析擴展至檢索階段，揭示了更廣泛的系統性風險。

A：已知的失敗案例包括：當攻擊者同時控制文字與向量時（例如完全捏造的文件），碼級驗證仍會接受，因為向量與文字在語意上確實一致；當語料庫中存在大量完全重複文件（exact duplicate document）時，邊距會被人為壓小，使攻擊更容易成功，本文也據此將最高 5.5% 的暴露率修正為排除重複後的 1.2%。此外，對於採用極度激進量化（如二元碼）的儲存格式，由於重建誤差可達數十度，即使碼級驗證也可能因正當的編碼歧義而需要更寬的防護帶，潛在增加攻擊空間。

**Q15：本文開啟了哪些未來研究方向？**
A：未來方向包括：將碼級驗證擴展至多模態嵌入（如圖文聯合向量）與極長上下文模型；研究如何在不洩漏模型細節的前提下對專有嵌入模型進行驗證；探索硬體輔助的位元可重現推論管線，以縮小防護帶並提升驗證效率。此外，將本文的供應鏈安全框架與聯邦學習、差分隱私結合，處理多方共同維護語料庫時的信任問題；以及研究自動化校準工具，使防護帶能隨硬體與驅動版本更新動態調整，都是值得探索的延伸方向。

## 實務應用指南

### 適用場景

1. **離線工業設備維護助手**：在無網路的工廠、礦場或離岸平台上，技術人員透過樹莓派等級的邊緣裝置查詢設備手冊、維修紀錄與安全規範。知識包由總部定期簽署推送，一旦向量被篡改，模型可能誤指錯誤的維修步驟，造成工安風險。本文的程式碼層級驗證可確保裝置僅接受與文字內容一致的向量。

2. **國防與戰場邊緣 AI**：軍用平板或單兵裝置搭載本地 LLM 與離線 RAG，用於查詢戰術手冊、地形情報與敵我識別規則。敵方滲透發布流程後，可在不破壞簽章的情況下植入誤導性向量，使模型在關鍵時刻回應錯誤資訊。本文提出的「邊距定律」可讓操作員在部署前量化暴露程度，並以程式碼驗證關閉此差距。

3. **醫療與法規遵循的本地知識庫**：醫院診間筆電或合署律師事務所的隔離網路環境中，運行 Qwen2.5-3B 等本地模型回答臨床指引或法條。內部人員（內容編輯、第三方廠商）若能影響向量，可使模型優先檢索過時或錯誤的指引。本文提供量化容忍度稽核的具體失敗數據（PQ 索引 25% 目標被劫持），可作為合規稽核的技術依據。

4. **多發布者車載資訊娛樂系統**：車廠、車隊營運商、地圖供應商各自簽署推送知識包至車機。向量完整性差距使任一發布者可「劫持」其他發布者的檢索結果（例如讓自家充電站資訊優先於其他業者）。本文的程式碼驗證與規範化機制可在異質硬體（車機 SoC、手機、桌面）上強制一致。

5. **隱私敏感的個人 AI 助理**：使用者將個人筆記、文件、郵件匯入本地 RAG，並透過訂閱取得第三方知識包（如新聞摘要、學術資料）。若訂閱來源的向量被污染，使用者的助理可能在不知情下被導向特定敘事。本文提供端到端的攻擊影響量化（正確答案從 0.75 降至 0.39），可作為隱私產品的安全設計參考。

### 實作前置條件

**資料需求**
- 目標領域語料庫（建議至少數千至數萬個文本塊），用於建立嵌入與索引。
- 預先標註的測試集（如 SQuAD 2.0、BEIR 子集），用於量測角度檢索邊距分布。
- 嵌入模型權重（須與發布端完全一致），建議先以 FP32 與 INT8 兩種精度備存。
- 量化校準資料集（用於動態 INT8 的執行期尺度計算）。

**運算資源**
- 邊緣裝置：樹莓派 5（或同等級 ARM Cortex-A76 平台）作為最低驗證標的。
- 桌面級 Linux 工作站，用於建立 FAISS 索引、執行攻擊模擬與邊距量測。
- 第三方平台（Apple M2 或 x86 伺服器）以驗證跨硬體位元可重現性。
- 建議至少 16 GB RAM 以容納 PQ 索引重建。

**技能前提**
- 熟悉 PyTorch / ONNX Runtime 推論管線，理解批次大小對浮點結果的影響。
- 具備 FAISS（特別是 `IndexPQ`、`IndexSQ8`、`IndexBinary`）的索引與重建經驗。
- 密碼學基礎：雜湊、簽署、TUF 風格的角色分離、Certificate Transparency 風格的透明日誌。
- 具備量測角度分布、繪製 CDF 與分位數的能力（NumPy、Matplotlib）。
- 對 LLM 解碼管線（KV cache、批次排程）有基本理解，以評估 CPU 驗證對解碼速度的影響。

### 實作步驟建議

1. **建立威脅模型與角色分離**：參考本文 §2.3 與 TUF 規範，定義內容金鑰（可新增區塊）與編輯金鑰（修改既有區塊需門檻簽署）。透明日誌用於防止回滾與衝突擴充。確認您的部署場景中「誰能影響向量」是發布流程、第三方廠商還是內部人員。

2. **量測角度檢索邊距分布（邊距定律前置）**：在目標語料庫上以 FP32 嵌入模型計算所有文本塊向量；對每個查詢計算 top-1 與 top-2 的角度差（即「邊距」）。繪製經驗 CDF，找出在 `arccos(τ)` 處的累積機率——此即理想化攻擊者在容忍度 τ 下的預期劫持率上限。本文在五個語料庫上觀察到此分布普遍偏小，這是暴露的根本原因。

3. **校準容忍度閾值**：在您的 CPU 上以 INT8 與 FP32 對同一批次計算嵌入，記錄餘弦相似度的經驗分布。取 0.1% 分位數作為「誠實餘弦」下限。本文顯示此閾值在實務上幾乎不擋下攻擊（暴露 98–100%），僅作為基線對照。

4. **評估壓縮格式的暴露**：若您使用 FAISS 或類似向量資料庫，請對 SQ8、SQ4、PQ、二元碼四種格式分別執行容忍度稽核。本文報告的暴露區間為 2–15%、55–89%、約 100%、100%。對真實 PQ 索引執行攻擊模擬，確認您的攻擊者能將多少目標的篡改向量排在第一位。

5. **改採程式碼層級驗證**：放棄容忍度比對，改為比對量化碼本身。具體做法：
   - 在發布端以確定性管線（固定批次大小、無 padding、單一執行緒）計算量化碼。
   - 在驗證端以同樣的確定性設定重算，並比對碼序列。
   - 引入「防護帶」處理浮點雜訊：對每個維度記錄誠實管線的最大偏差，作為碼比較的容錯邊界。
   - 對模糊情況（介於兩個碼之間的輸入）由驗證器單方面裁決，發布端無選擇空間。
   - 加入「驗證後規範化」步驟，將通過的碼映射到單一規範形式，杜絕發布端利用等價碼規避。

6. **驗證跨硬體位元可重現性**：在樹莓派 5、桌面、Apple M2 三平台上，分別以不同批次大小與執行緒數執行同一嵌入管線，記錄差異。本文證明浮點與動態 INT8 皆非位元可重現，這是容忍度方法的根本限制，也是程式碼驗證必須搭配規範化的原因。

7. **量測裝置端成本**：在樹莓派 5 上同時運行 Qwen2.5-3B 解碼與驗證管線，量測解碼速度損失。本文實測為 23–31%。若超過預算，可考慮將驗證卸載至背景執行緒、或僅在知識包更新時觸發。

8. **端到端評估攻擊影響**：以本文的攻擊設定（將正確答案的向量替換為攻擊者選擇的向量），量測最終正確率變化。本文在 INT8 參考閾值下觀察到正確率從 0.75 降至 0.39，作為部署前必須通過的安全門檻。

9. **整合結構性更新攻擊防禦**：本文測試了 12 種結構性更新攻擊（添加、取代、刪除操作的各種組合），層疊的封包驗證應全部拒絕。請將這些案例納入您的回歸測試套件。

10. **放棄無效的輔助防禦**：本文預先註冊的負面結果顯示，棄答、上下文剪枝、語意篩選皆無法關閉此差距。請勿將這些機制視為主要防禦，僅作為深度防禦的補充。

### 潛在風險與注意事項

- **容忍度方法的隱性陷阱**：直覺上「容忍浮點雜訊」是合理的，但本文證明此容忍度恰好落在角度邊距的密集區間，使攻擊者能以極小成本通過稽核。緩解：完全放棄容忍度，改採程式碼比對。

- **批次大小改變嵌入結果**：同一文本在不同批次大小下可能得到不同位元結果，這意味著「同一模型、同一輸入」並非良定義。緩解：在發布端與驗證端皆固定批次大小、padding 策略與執行緒數，並將此寫入知識包 manifest。

- **量化碼的等價規避**：PQ 與 SQ 的碼空間中存在多個「距離相近」的碼，攻擊者可選擇通過驗證但檢索效果不同的碼。緩解：採用「驗證後規範化」，將通過的碼強制映射到單一規範形式。

- **PQ 索引的攻擊面被低估**：本文在 57,638 文件的 FAISS PQ 索引上演示，篡改向量可全數通過稽核並使 25% 目標被劫持。許多團隊誤以為 PQ 的重建誤差自然形成保護，實際上攻擊者可逆向重建過程。緩解：對 PQ 索引必須採用程式碼層級驗證。

- **CPU 驗證對 LLM 解碼的干擾**：在樹莓派 5 上驗證管線會吃掉 23–31% 的解碼速度。緩解：將驗證卸載至專用核心、或在背景以低優先權執行；亦可在知識包更新時一次性驗證，運行期僅做輕量雜湊檢查。

- **跨平台不一致**：本文證明浮點與動態 INT8 在不同架構間不可重現。若您的裝置生態包含多種硬體，必須為每種平台單獨校準防護帶。緩解：在 manifest 中標註目標平台清單，驗證器僅接受為本平台產生的碼。

- **內部人員威脅**：簽章機制僅證明「誰」發布，不證明「內容正確」。若攻擊者是取得內容金鑰的內部編輯，簽章本身無法防禦。緩解：採用編輯金鑰門檻簽署、透明日誌稽核、定期外部審計。

- **負面結果的誤用**：棄答、上下文剪枝、語意篩選在本文實驗中皆無法關閉差距。將這些機制當作主要防禦會給予錯誤的安全感。緩解：將它們視為深度防禦層，明確記錄其無法防禦的威脅類別。

- **校準資料的代表性**：0.1% 分位數的誠實餘弦值高度依賴校準資料的分布。若您的部署語料與校準資料差異大，閾值可能過鬆或過嚴。緩解：在目標語料上重新校準，並定期隨部署資料更新。

### 與其他技術的整合建議

- **TUF（The Update Framework）**：本文的知識包設計已採用 TUF 風格的角色分離。建議直接採用 TUF 的金鑰輪替、撤銷與快照機制，並將向量完整性驗證掛載在 TUF 的角色驗證之後。

- **Certificate Transparency / 透明日誌**：將每個知識包的雜湊提交至公開透明日誌，使裝置可偵測回滾與衝突擴充。與本文的程式碼驗證互補：透明日誌處理「誰、何時」，程式碼驗證處理「內容是否一致」。

- **IETF SUIT（軟體更新物資模型）**：本文的 manifest 設計遵循 IoT 韌體更新的資訊模型。若您的裝置已採用 SUIT，可將向量驗證結果作為 manifest 中的相依性條件。

- **FAISS 與替代向量資料庫**：FAISS 的 PQ/SQ 索引是攻擊面最大的環節。若您使用 Milvus、Qdrant、Weaviate 等，請確認其底層是否同樣採用容忍度稽核——多數預設實作皆有此弱點。建議在這些系統之上加入獨立的程式碼驗證層。

- **ONNX Runtime / TensorRT**：若您將嵌入模型導出至 ONNX 以加速推論，請注意不同 runtime 的浮點語意可能不同。本文證明跨架構不可重現，因此 ONNX 導出後的驗證管線必須與發布端使用完全相同的 runtime 與版本。

- **LLM 推論框架（llama.cpp、vLLM、Ollama）**：本文在樹莓派 5 上使用 Qwen2.5-3B，建議在您的 LLM 框架中將驗證管線設為獨立的背景任務，並透過 CPU 親和性隔離避免干擾解碼。

- **每嵌入簽章（per-embedding signature）**：近期文獻提出為每個嵌入單獨簽章以防禦此攻擊。本文顯示此方法在容忍度稽核下仍可被規避；建議將每嵌入簽章與程式碼驗證結合，形成雙重保證。

- **差分隱私與聯邦學習**：若您的知識包來自多方協作（例如多家醫院共同訓練嵌入），向量完整性差距會被放大——任一方皆可植入誤導向量。建議在聯邦流程中加入程式碼驗證作為輸出閘門。

### 給不同背景讀者的閱讀建議

**給初學者**：請先閱讀 §1 與 §2.1–2.3，建立「知識包 = 文字 + 預計算向量 + 簽章」的心智模型。核心訊息是：簽章證明誰發布，但無法證明向量真的對應文字。理解「邊距定律」不需要深入數學——它只是說「攻擊成功率 = 角度邊距在容忍度以下的機率」。建議從 §5.1 的實驗數據讀起，直觀感受容忍度方法的脆弱性，再回頭讀 §3 的形式化。

**給 AI 工程師**：重點關注 §5.2（壓縮格式的暴露數據）與 §5.3（程式碼驗證實作）。前者直接影響您在生產環境中選擇向量儲存格式的決策——若您使用 FAISS PQ，請立即評估攻擊面。後者提供了可落地的驗證管線設計：確定性批次、防護帶校準、驗證後規範化。§5.4 的裝置端成本數據（23–31% 解碼速度損失）對架構設計至關重要。建議將本文的攻擊模擬整合至您的 CI/CD 流程，作為知識包發布前的安全門檻。

**給研究者**：本文的核心理論貢獻是「邊距定律」（§3），它將攻擊成功率與可量測的分布聯繫起來，使操作員能在不執行攻擊的情況下預測暴露程度。§5.3 對浮點與動態 INT8 跨平台不可重現性的實證，以及 §5.6 的預先註冊負面結果，皆是值得延伸的方向。建議探索：(1) 邊距定律在非餘弦相似度（如內積、學習式度量）下的推廣；(2) 防護帶的理論下界；(3) 對抗式嵌入防禦與程式碼驗證的組合安全性證明。

**給產品經理**：本文的商業意涵是：離線 RAG 產品的「簽章保護」並不等於「內容可信」。若您的產品涉及多發布者、第三方內容或內部編輯流程，請將向量完整性驗證列為必要功能，而非可選強化。關鍵數字：攻擊可使正確率從 0.75 降至 0.39（幾近腰斬），且攻擊者無需破壞簽章。建議在產品路線圖中明確標示「程式碼層級向量驗證」為安全里程碑，並將 §5.4 的裝置端成本納入效能預算。對客戶溝通時，避免使用「簽署即安全」的行銷話術，改為強調「文字與向量雙重驗證」。
