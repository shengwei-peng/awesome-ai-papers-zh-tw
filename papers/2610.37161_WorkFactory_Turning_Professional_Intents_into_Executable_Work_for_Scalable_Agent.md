## 深度分析

#### 方法論解析

WorkFactory 的核心目標是解決工作代理（working agent）監督式微調（SFT）訓練中的關鍵瓶頸：如何建構「資訊充足且一致」的專業任務環境，使教師代理（teacher agent）能產生可靠的專家示範（expert demonstration）。其方法論可從三個層次拆解：

**1. 意圖庫建構（Intent Library Construction）**

WorkFactory 並非從零生成任務，而是結合三類來源以擴大覆蓋面：
- **職業知識（occupational knowledge）**：來自職業分類與職責描述
- **技能文件（skill documentation）**：具體技能的標準作業流程
- **專業產物（professional artifacts）**：真實工作中產生的文件、報表、合約等

這種「組合式意圖」設計使任務能同時涵蓋「已建立的工作流程」與「真實可交付物（deliverable）」，避免合成任務過於人工化或過於狹隘。

**2. 資訊層級規劃（Information-level Planning）與資訊支援圖（Information Support Graph）**

這是 WorkFactory 最具方法論特色的設計。傳統任務建構往往直接連接產物（artifact）之間的關係，但 WorkFactory 採用**逆向規劃（backward planning）**：從預期輸出（intended output）出發，反向追溯該輸出所依賴的資訊節點。

資訊支援圖的關鍵設計原則：
- **節點代表「資訊需求」而非「檔案」**：例如「供應商選擇任務」中，輸出依賴的不只是「需求預測」與「廠商報價」這兩個檔案，而是「含運費與否的定價條件」、「生命週期成本計算結果」等資訊需求
- **明確定義資訊位置**：每個資訊需求必須在重複使用（reused）或合成（synthesized）的材料中可被找到
- **保留衍生結果給解題者**：中間計算與最終結果不應預先提供，否則會削弱教師需要執行的實質工作

這個設計解決了論文中提到的關鍵張力：若直接提供計算結果，會移除教師應執行的核心工作；若資訊不足，教師則會引入未經支援的假設或留下未完成的工作。

**3. 探測執行（Probe Execution）與修復（Repair）**

即使經過規劃，材料化（materialization）過程仍可能引入缺陷。WorkFactory 採用「隔離探測」機制：
- 一個獨立的探測代理僅從「解題者可見的輸入」嘗試執行任務
- 探測診斷（probe-diagnosed）出支援失敗（support failure）的位置與類型
- 修復機制被嚴格約束：**必須恢復資訊支援，但不得改變預期工作內容**

這個「規劃—探測—修復」的閉環設計，使 WorkFactory 能產出通過嚴格驗證的可執行任務環境，而非僅在表面上看似合理。

**4. 教師軌跡收集與模型訓練**

通過驗證的任務環境被指派給獨立的教師代理執行，產生的軌跡（trajectory）作為 SFT 訓練資料。最終在 Qwen3.5-4B、Qwen3.6-27B 與 Qwen3.6-35B-A3B（混合專家模型，MoE，3B 活化參數）三個規模上微調，得到 WorkPilot 系列。

#### 實驗數據解讀

**1. 基準測試（benchmark）效能提升**

從 Figure 1 的數據可解讀出幾個關鍵訊號：

| 基準測試 | Qwen3.6-35B-A3B 基礎模型 | WorkPilot-35B-A3B | 提升幅度 |
|---------|------------------------|------------------|---------|
| GDPval-AA (Elo) | 879 | 1565 | +686 |
| JobBench | 28.9 | 62.4 | +33.5 |
| Workspace-Bench | 47.1 | 56.5 | +9.4 |
| OmegaUse-OfficeVal | 7.1 | 21.2 | +14.1 |

- **GDPval-AA 提升最為顯著**（Elo 從 879 提升至 1565），且 WorkPilot-27B 在 GDPval-AA v2.1 上達到局部估計的 1612 Elo，進入前沿模型（frontier model）範圍
- **JobBench 提升幅度最大**（從 28.9 到 62.4，約 2.16 倍），顯示 WorkFactory 資料對職業能力評估的訓練效益
- **Workspace-Bench 提升相對溫和**（+9.4），可能因為該基準已較成熟或與訓練分布有部分重疊
- **OmegaUse-OfficeVal 從極低基線（7.1）翻倍提升至 21.2**，顯示對較弱基礎模型的相對增益更明顯

**2. 規模化分析（Scaling Analysis）的洞察**

論文揭示了「模型依賴的邊際效益遞減（model-dependent diminishing returns）」現象：
- 並非所有模型規模都能從更多資料中持續獲益
- **執行長度（execution length）呈現「先升後降」的非單調變化**：初期訓練使代理學會更完整的執行流程，隨後可能因效率優化而縮短
- 工具使用可靠性（tool-use reliability）隨訓練發生變化

這個觀察對實務部署很重要：盲目堆疊資料並非總是有效，需要針對模型容量調整訓練規模。

**3. 控制變因分析（Controlled Component Analysis）**

消融實驗（ablation study）證實了兩個核心元件的互補價值：
- **資訊層級規劃**：減少探測診斷的任務環境缺陷
- **執行式修復**：進一步降低缺陷率並提升下游效能

兩者結合產生最佳效果，說明「規劃」與「驗證修復」是 WorkFactory 不可或缺的雙引擎。

#### 與現有研究的比較

**1. 與軟體工程任務合成的比較**

SWE-Gym、SWE-smith、R2E-Gym 等系統利用程式碼儲存庫與可執行測試提供具體監督訊號。WorkFactory 處理的是更長視野（longer-horizon）、多工具（multi-tool）的專業工作，無法依賴單元測試作為自動驗證，因此必須設計「資訊支援」與「探測修復」機制。

**2. 與 NexForge 的比較**

NexForge 將能力需求轉譯為任務指令，並透過工作區藍圖（workspace blueprint）實例化。WorkFactory 採用更細粒度的「資訊節點」而非「檔案層級」規劃，並加入執行式驗證，這使其在處理需要跨檔案推理的任務時更為精確。

**3. 與 Synthetic Computers 的比較**

Synthetic Computers 規劃產物間的依賴關係以指導工作區合成。WorkFactory 的資訊支援圖進一步區分了「資訊需求」與「資訊位置」，並明確保留衍生結果給解題者，避免了「過度提供」導致的訓練訊號弱化。

**4. 與 GraphForge 的比較（並行工作）**

GraphForge 從真實檔案組裝證據圖（evidence graph），衍生任務陳述與證據錨定評分規程（rubric），再以執行回饋修訂。WorkFactory 則從預期輸出逆向工作，圖的用途是協調資訊依賴與位置，而非編譯任務與評分規程。兩者代表了「由證據到任務」與「由任務到證據」兩種互補路徑。

**5. 與 WorkGenesis 的比較（並行工作）**

WorkGenesis 圍繞檢索檔案合成配套材料，並用評分規程式失敗歸因（rubric-based failure attribution）指導請求、合成材料與評分規程的修訂。WorkFactory 則直接探測解題者可見環境，並約束修復以保留預期工作，避免了評分規程設計的複雜性與偏差風險。

**6. WorkFactory 的相對優勢與限制**

**優勢**：
- 資訊節點的細粒度設計更貼近真實專業工作的推理結構
- 探測式驗證比評分規程式審計更直接、更不易被「評分規程遊戲化」繞過
- 修復約束明確，避免改變任務本質

**限制**：
- 探測執行本身需要計算成本，112,686 個任務的規模化探測是顯著的工程開銷
- 資訊支援圖的建構品質高度依賴意圖庫的覆蓋面與品質
- 對於需要極度跨領域整合的任務，逆向規劃可能遭遇「資訊需求爆炸」的組合複雜度問題

#### 可重現性評估

**1. 程式碼與資料開放**

論文明確聲明資料與模型已於 GitHub 開源（https://github.com/IQuestLab/WorkFactory），這對學術界與工業界的後續研究至關重要。

**2. 可重現性資產清單**

- **任務資料子集**：公開釋出部分任務資料，使研究者能分析任務分布、品質與多樣性
- **模型權重**：WorkPilot-4B、27B、35B-A3B 三個規模的權重均公開，可直接用於下游評估或進一步微調
- **框架程式碼**：WorkFactory 的建構流程應可從程式碼重現

**3. 重現的潛在障礙**

- **教師代理的選擇**：論文中未明確說明教師代理的具體模型與配置，這會影響軌跡品質與訓練結果
- **探測代理的細節**：探測執行的失敗診斷標準與修復策略的具體實作需要從程式碼推導
- **基準測試的可取得性**：GDPval-AA、JobBench、Workspace-Bench、OmegaUse-OfficeVal 的評估流程與評分標準需要對齊
- **計算資源需求**：112K 規模的任務建構與三個規模的模型微調需要大量 GPU 資源，限制了中小研究團隊的完整重現

**4. 整體可重現性評級**

考慮到資料、模型與程式碼均公開，且方法論描述詳盡，WorkFactory 的可重現性屬於**中高水準**。主要不確定性在於教師代理的具體選擇與探測修復的實作細節，這些可透過檢視程式碼與補充材料釐清。

#### 未來研究方向

**1. 強化資訊支援圖的自動化建構**

目前資訊支援圖的建構可能仍需大量人工設計或高度依賴大型語言模型的推理。未來可探索：
- 從大規模專業文件自動挖掘資訊依賴模式
- 結合形式化方法（formal methods）驗證資訊完整性
- 發展可解釋的圖結構，使領域專家能審閱與修正

**2. 探測機制的理論化**

探測執行目前是啟發式設計，未來可：
- 建立「資訊充分性」的理論定義與可證明性質
- 設計更高效的探測策略，降低計算成本
- 探索多代理協作探測，提升診斷準確度

**3. 規模化規律的深入研究**

論文揭示了「執行長度先升後降」的非單調現象，但未深入解釋其機制。未來可：
- 分析訓練資料特性與執行長度變化的因果關係
- 探索「效率導向」與「完整性導向」的訓練目標平衡
- 研究不同模型架構（稠密 vs. MoE）的規模化差異

**4. 跨領域遷移與泛化**

WorkFactory 在 612 個職業上驗證，但跨職業遷移能力仍待檢驗：
- 訓練資料的職業分布是否平衡？
- 模型在未見過的職業上表現如何？
- 是否存在「職業指紋」可預測遷移效能？

**5. 與強化學習（RL）的整合**

目前 WorkFactory 僅用於 SFT，未來可：
- 在 WorkFactory 建構的環境上進行 RL 訓練，進一步提升效能
- 結合過程獎勵模型（process reward model）對教師軌跡進行品質分級
- 探索「環境—軌跡—獎勵」的聯合最佳化

**6. 真實工作流程的整合**

WorkFactory 目前處理的是「任務級」工作，未來可擴展至：
- 多任務、長期的專案級工作流程
- 多人協作場景下的任務分配與協調
- 與真實企業系統（如 ERP、CRM）的整合驗證

**7. 安全性與偏誤審查**

專業任務可能涉及敏感資訊或產生偏誤決策：
- 探測機制可擴展為「安全性探測」，識別潛在的有害輸出
- 評估 WorkPilot 模型在涉及倫理判斷任務上的表現
- 建立任務內容的偏誤審查流程

**8. 評估方法的革新**

GDPval-AA 等基準使用 Elo 評分進行成對比較，未來可：
- 發展更細粒度的「工作能力剖面圖」（competency profile）
- 結合人類專家評估與自動化指標
- 建立「過程正確性」與「結果正確性」的雙軌評估

總結而言，WorkFactory 在「任務環境建構」這個被低估的環節上做出了紮實貢獻，其「資訊支援圖 + 探測修復」的雙引擎設計為工作代理的規模化訓練提供了可借鏡的方法論範式。隨著工作代理從實驗室走向真實部署，這類「環境工程」研究的重要性將持續提升。

## 論文問答

**Q1：WorkFactory 試圖解決的核心問題是什麼？**
A：WorkFactory 試圖解決的核心問題是「如何為工作代理（working agent）規模化建構可執行且具備可靠專家示範的專業任務」。在監督式微調（Supervised Fine-Tuning, SFT）的訓練範式中，模型的表現高度依賴於教師軌跡（teacher trajectory）的品質；然而，當任務資訊缺失或不一致時，教師代理無法順利執行工作，甚至會引入未經支持的假設或遺漏關鍵步驟，進而削弱訓練監督（training supervision）的有效性。論文中以供應商選擇任務（supplier-selection task）為例，說明若未提供運費條件等前提資訊，教師便無法正確計算生命週期成本（lifecycle cost），導致示範軌跡失去教學價值。因此，WorkFactory 的核心目標是確保任務環境在「提供所有必要前提」與「保留應由求解者推導的中間與最終結果」之間取得精確平衡。

**Q2：現有的任務建構方法為何難以產生可靠的專家示範？**
A：現有方法在處理專業工作時面臨幾項根本性挑戰。首先，軟體工程領域的系統（如 SWE-Gym、SWE-smith、R2E-Gym）仰賴可執行的測試提供具體監督，但這類設定難以直接遷移到需要異質資訊整合的專業工作中。其次，NexForge 透過工作區藍圖實例化任務，Synthetic Computers 規劃產物間的依賴關係，但這些方法較少明確處理「資訊應位於何處」以及「哪些結果應留給求解者推導」的邊界問題。再者，GraphForge 雖然從真實檔案建構證據圖並利用執行回饋修訂規格，WorkGenesis 則以 rubric 為基礎進行失敗歸因，但前者聚焦於規格層級的審核，後者則以 rubric 為核心進行修訂，皆未像 WorkFactory 直接從求解者可見的環境進行探測（probe）並以保留原意工作為約束進行修復，因此難以系統性地保證任務的可執行性與示範的可靠性。

**Q3：為什麼建構連貫且可執行的專業任務對工作代理的訓練至關重要？**
A：建構連貫且可執行的專業任務之所以關鍵，是因為工作代理的價值在於能夠在真實的數位環境（digital environment）中執行跨職業的工作流程（workflow）、協調工具並產出交付物（deliverable），這類工作具有長時程、多工具整合的特性。當任務環境存在資訊缺陷時，教師軌跡會混入推測或省略步驟，使學生模型學到錯誤的工作模式，進而限制其在 GDPval-AA、JobBench 等專業工作基準測試上的表現。此外，規模化（scaling）監督式訓練需要大量且多元的任務資料，若任務建構過程無法保證品質，再多的資料也只會放大錯誤示範的負面影響。因此，連貫且可執行的任務環境是支撐工作代理從示範學習走向實際部署的基礎。

**Q4：WorkFactory 的核心方法是什麼？**
A：WorkFactory 的核心方法包含三個相互銜接的階段：意圖庫建構、資訊層級規劃（information-level planning）以及探測驅動的修復（probe-driven repair）。首先，框架結合職業知識、技能文件（skill documentation）與專業產物（professional artifact）建立多元的專業意圖（professional intent）庫，涵蓋 612 種職業。接著，對於每個意圖，WorkFactory 從預期輸出進行逆向規劃（backward planning），建構一個資訊支援圖（information support graph），用以協調被重複使用與合成的材料之間的資訊依賴與位置。最後，透過隔離的探測執行（probe execution）從求解者可見的輸入嘗試任務，根據診斷結果進行修復，但修復過程必須在不更動原意工作的前提下恢復資訊支援，僅有通過此流程的環境才會被指派給獨立的教師代理執行並收集軌跡。

**Q5：資訊支援圖（information support graph）的關鍵創新為何？**
A：資訊支援圖的關鍵創新在於它不僅僅連接產物之間的關係，而是明確表達「每個輸出依賴什麼資訊」以及「這些資訊應位於哪些被重複使用或合成的材料中」。這種設計使得任務建構者能夠系統性地追蹤從最終交付物回溯到所有必要前提的依賴鏈，同時刻意將中間計算（intermediate calculation）與判斷（judgment）保留給求解者完成。這與 GraphForge 從已組裝的真實檔案工作區編譯任務的方式形成對比——WorkFactory 從意圖出發，主動設計資訊分佈的邊界，避免將過多推導結果直接放入環境而削弱任務的教學價值。透過這種圖結構，框架得以在「資訊完備性」與「工作保留性」之間維持精細的平衡，這是過去方法較少明確處理的設計空間。

**Q6：WorkFactory 在設計上有哪些關鍵選擇值得深入理解？**
A：WorkFactory 的幾項關鍵設計選擇反映了對工作代理訓練需求的深度考量。第一，採用「從輸出逆向規劃」而非「從輸入向前組合」的策略，使框架能主動控制哪些資訊進入環境、哪些留給求解者，這對保留任務的實質工作至關重要。第二，探測執行（probe execution）採用隔離環境進行，避免探測過程汙染或洩漏任務資訊給後續的教師代理，確保診斷結果反映真實的環境缺陷。第三，修復過程被嚴格約束為「必須恢復資訊支援但不改變原意工作」，這項約束防止修復淪為簡化任務或洩漏答案。第四，僅有通過探測的環境才會被指派給獨立的教師，這種品質閘門設計確保了收集到的教師軌跡具備足夠的可靠性作為監督訊號。

**Q7：WorkPilot 模型在哪些基準測試上進行評估？**
A：WorkPilot 模型在四個專業工作基準測試上進行評估，分別是 GDPval-AA（含 v2.1 版本）、JobBench、Workspace-Bench 以及 OmegaUse-OfficeVal。這些基準測試涵蓋不同面向的專業工作能力評估：GDPval-AA 採用 Elo 評分機制進行成對比較以衡量整體專業工作表現，JobBench 評估職業任務的執行成效，Workspace-Bench 聚焦於工作區操作能力，而 OmegaUse-OfficeVal 則針對 Office 類工具的使用進行評量。論文中以 WorkPilot-35B-A3B 為代表，展示了其在四個基準測試上相較於 Qwen3.6-35B-A3B 基礎模型的一致性提升，並與 Apodex-1.1-mini、MiniMax-M3、GPT-5.6 Sol 等參考模型進行比較，以提供更全面的效能定位。

**Q8：WorkPilot 系列模型的關鍵成果為何？**
A：WorkPilot 系列模型在所有測試規模與基準測試上均展現出對基礎模型的顯著提升，其中最具代表性的成果是 WorkPilot-35B-A3B 在 GDPval-AA v2.1 上的 Elo 評分從基礎模型的 879 提升至 1565，提升幅度達 686 分。更引人注目的是，WorkPilot-27B 在 GDPval-AA v2.1 上達到局部估計的 1612 Elo，使其表現進入與前沿模型相比擬的範圍，顯示 WorkFactory 資料在中等規模模型上也能產生前沿級別的成果。此外，論文的規模化分析（scaling analysis）揭示了模型相關的邊際效益遞減（diminishing returns）現象，以及執行長度（execution length）隨資料規模先增加後減少的非單調變化，這些發現對理解工作代理的訓練動態具有重要意義。

**Q9：消融研究（ablation study）揭示了規劃與修復元件的哪些效果？**
A：控制變因分析（controlled component analysis）顯示，資訊層級規劃與執行驅動的修復對任務環境品質與下游效能具有互補性的貢獻。具體而言，這兩個元件共同作用能顯著降低由探測診斷出的任務環境缺陷（probe-diagnosed defect），意味著規劃階段從輸出逆向設計資訊分佈能預防許多缺陷的產生，而修復階段則能捕捉並修正材料化過程中引入的違規。當兩者結合時，下游基準測試的表現也獲得相應的提升，證明了「連貫的任務環境」與「有效的專家監督」之間存在直接關聯。這項分析支持了 WorkFactory 設計假設的核心：任務環境的資訊一致性是影響教師軌跡品質、進而影響學生模型表現的關鍵因素。

**Q10：WorkPilot 可應用於哪些實際場景？**
A：WorkPilot 可應用於多樣化的專業工作場景，凡是需要在數位環境中執行跨工具、跨檔案工作流程的職業皆為潛在應用領域。具體而言，模型可支援需要整合需求預測、廠商報價（vendor quotation）、成本計算等異質資訊的供應商選擇任務，也能處理涉及文件編製、資料分析、報告產出等典型辦公室工作。論文中涵蓋 612 種職業的訓練資料顯示，WorkPilot 具備跨領域的泛化能力，從工程技術類到行政文書類的工作皆在其能力範圍內。此外，由於模型在 GDPval-AA 等基準測試上展現出接近前沿模型的表現，企業在導入工作代理時可將 WorkPilot 作為基礎，進一步針對特定產業或組織的工作流程進行微調，以提升實際生產力並創造經濟價值。

**Q11：從產品化的角度，WorkFactory 與 WorkPilot 引發了哪些考量？**
A：從產品化角度，WorkFactory 與 WorkPilot 引發了多項重要考量。首先，框架能夠規模化產出高品質任務資料，這對於需要大量訓練資料的企業內部工作代理開發具有直接價值，可降低資料建構的人力成本。其次，WorkPilot-27B 達到前沿級別表現的結果顯示，中等規模模型經過 WorkFactory 資料訓練後即可具備實用能力，這對部署成本敏感的中小企業特別具有吸引力。然而，產品化時也需考量任務環境的領域特定性，雖然框架涵蓋 612 種職業，但特定產業（如醫療、法律）可能仍需額外的領域知識注入。此外，模型的工具使用可靠性隨訓練規模變化的現象提示產品設計者需要持續監控代理在實際工作流程中的執行穩定性，並設計相應的容錯機制。

**Q12：這項研究對工作代理領域的更廣泛影響為何？**
A：這項研究對工作代理領域的更廣泛影響體現在三個層面：在方法論上，WorkFactory 提出的「從輸出逆向規劃」與「探測驅動修復」範式為任務建構提供了新的設計原則，強調資訊支援與工作保留的精細平衡；在實證上，規模化分析揭示的邊際效益遞減、執行長度非單調變化等現象，深化了社群對工作代理訓練動態的理解；在生態上，公開釋出的任務資料子集與模型權重降低了後續研究的門檻，有助於加速工作代理領域的整體進展。此外，WorkPilot-27B 達到前沿級別表現的結果挑戰了「必須使用最大規模模型才能獲得頂尖表現」的假設，對模型選型與資源配置策略具有啟示意義。

**Q13：WorkFactory 的已承認限制為何？**
A：WorkFactory 的已承認限制主要體現在幾個方面。首先，雖然框架涵蓋 612 種職業並建構了 112,686 個任務，但這些任務是從職業知識、技能文件與專業產物組合而成的，可能無法完全反映真實工作環境中的所有細節與例外情況。其次，探測執行雖然能診斷明顯的資訊缺陷，但對於需要深度領域知識才能識別的細微不一致性可能力有未逮。再者，論文中觀察到的模型相關邊際效益遞減現象意味著，單純增加資料規模並不能無限提升所有模型的表現，這對追求極致效能的應用構成限制。最後，WorkPilot 的評估主要在四個基準測試上進行，這些基準雖然涵蓋多元面向，但對於特定產業或高度專業化工作流程的適用性仍需進一步驗證。

**Q14：WorkFactory 可能遭遇哪些失敗案例或邊界情況？**
A：WorkFactory 在幾類邊界情況下可能面臨挑戰。第一，當專業意圖涉及高度專業化的領域知識（如臨床醫療決策、法律條文解釋）時，資訊支援圖的建構可能難以完整捕捉所有隱含前提，導致探測無法診斷出真正的資訊缺口。第二，對於需要即時外部資訊（如市場行情、股價變動）的任務，框架難以在靜態環境中重現這些動態因素，可能使任務失去真實性。第三，當任務涉及多輪人機協作或需要根據中間結果調整策略的工作流程時，逆向規劃的假設可能不成立，因為輸出並非完全預先確定。第四，探測代理本身的限制可能導致誤診，將可執行的任務誤判為有缺陷，或將真正的缺陷視為可接受，這些錯誤會直接影響後續教師軌跡的品質。

**Q15：這項研究提示了哪些值得探索的未來方向？**
A：這項研究提示了多個值得探索的未來方向。在資料層面，可研究如何將 WorkFactory 擴展到需要動態資訊或多輪協作的任務類型，例如結合即時資料源或模擬人類回饋的互動式任務建構。在模型層面，規模化分析揭示的執行長度非單調變化與工具使用可靠性變化值得深入探究，這可能有助於設計更有效率的訓練課程或獎勵機制。在評估層面，可發展更能反映真實工作流程複雜度的基準測試，特別是針對長時程、多步驟專業工作的評量方法。在應用層面，將 WorkPilot 與特定產業的領域知識結合，探討其在醫療、法律、金融等高度專業化領域的適用性與客製化需求。此外，框架中探測驅動修復的概念可進一步延伸至其他類型的代理訓練，例如結合人類專家回饋的混合修復機制，以提升任務建構的品質與效率。

## 實務應用指南

1. **企業內部專業任務自動化訓練**：金融機構、會計師事務所或法律顧問公司可利用 WorkFactory 建構符合內部 SOP 的任務集（如供應商評選、合約審閱、財報分析），用於微調專屬的工作代理模型，使其熟悉該產業特有的判斷邏輯與交付物格式。

2. **政府或公共部門的數位勞動力建置**：針對公文撰寫、案件分派、補助審核等高重複性但需要領域知識的工作流程，可透過 WorkFactory 從既有法規文件、案例庫與表單範本中萃取意圖，產出可監督式微調的訓練資料，降低對真人公務員的依賴。

3. **教育訓練與職涯模擬平台**：可將 612 種職業的任務資料轉化為「職涯模擬器」，讓學生或轉職者在安全的數位環境中練習真實的專業工作（如行銷企劃、藥師調劑、軟體專案管理），並由 WorkPilot 系列模型擔任評分或提示角色。

4. **SaaS 工具的智慧助理升級**：CRM、ERP、BI 等企業軟體廠商可採用 WorkFactory 框架，從自家產品的工作流程與說明文件生成任務，再以 WorkPilot 蒸餾出小型化（4B 等級）的助理模型，嵌入產品中提供符合該工具操作邏輯的引導。

5. **AI 紅隊與合規測試資料生成**：資安或合規團隊可利用 WorkFactory 的資訊支援圖與探測機制，主動建構「資訊不足」或「資訊矛盾」的對抗性任務，用來評估既有代理模型在資訊不完整情境下的推理失敗模式。

### 實作前置條件

**資料面**
- 需準備目標職業領域的**職業知識庫**（如 O*NET 資料庫、產業白皮書、職位說明書）。
- 需蒐集**技能文件**（SOP、工具操作手冊、領域教科書）作為意圖生成的種子。
- 需具備**專業產物範本**（過去的交付物、報表、合約、簡報），用於支撐資訊支援圖中的素材節點。
- 建議至少有數千份真實產物以避免合成資料過度偏離實務。

**算力面**
- 教師代理（teacher agent）的軌跡蒐集需要能執行多輪工具呼叫的代理環境（建議使用支援 MCP 或類似協定的沙箱）。
- 微調 Qwen3.5-4B 至少需要單機多卡（如 8×A100/H100）；27B 與 35B-A3B 建議使用節點級 GPU 叢集，並搭配 ZeRO-3 或 FSDP。
- 探測執行（probe execution）需要可隔離、可重現的容器化執行環境（Docker/Kubernetes），以避免探測污染教師軌跡。

**技能面**
- 熟悉 LLM 代理框架（如 LangGraph、AutoGen、OpenAI Agents SDK）以搭建教師與探測代理。
- 具備資訊抽取與知識圖譜建構經驗，能將非結構化文件轉為意圖與依賴關係。
- 具備 SFT 訓練經驗（資料清洗、loss masking、對話格式設計），並理解如何隔離「教師可見資訊」與「待求解資訊」的邊界。

### 實作步驟建議

**步驟一：建立專業意圖庫**
從職業知識、技能文件與專業產物中萃取出「意圖三元組」（任務目標、預期交付物、適用情境）。可先用 LLM 進行批次抽取，再由領域專家抽樣驗證。建議初期聚焦 5–10 個高價值職業，避免一次鋪得太廣。

**步驟二：建構資訊支援圖**
針對每個意圖，從預期交付物**逆向規劃**：列出該交付物所需的最終欄位 → 推導每個欄位依賴哪些中間計算或判斷 → 標示這些資訊應位於哪份既有產物或需新合成的素材中。圖的節點建議分為「前提資訊」與「待求解結果」兩類，並明確標記邊界。

**步驟三：素材物化與任務實例化**
根據資訊支援圖，從真實產物中挑選或合成對應素材，組裝成任務環境（檔案、目錄、附件）。此階段需嚴格遵守「前提齊備、推導留白」的原則——所有必要前提必須可被代理讀取，但中間結果與最終答案必須留給代理自行產生。

**步驟四：探測執行與修復**
派遣一支**獨立的探測代理**（建議使用不同於教師的模型或不同溫度設定）嘗試從代理可見的輸入解出該任務。記錄探測失敗的模式：資訊缺失、資訊矛盾、檔案無法讀取、隱含假設未說明等。針對每個失敗觸發**修復流程**，但修復僅限於補齊或澄清前提，**不可改變意圖本身**或預先填入答案。

**步驟五：教師軌跡蒐集**
通過探測的任務才交給教師代理執行。為避免污染，建議教師代理與探測代理使用不同的模型或不同的隨機種子。蒐集完整的工具呼叫鏈、思考過程與最終交付物，作為 SFT 的訓練資料。

**步驟六：監督式微調與評估**
使用蒐集到的軌跡微調 Qwen 系列模型。建議採用**對話格式 + 工具呼叫格式**雙軌標記，並對思考過程做 loss masking 或加權處理。訓練後以 GDPval-AA、JobBench 等基準測試驗證，並針對目標職業做領域內評估。

**步驟七：規模化分析與迭代**
依據論文的規模化分析經驗，繪製「訓練資料量 vs. 下游效能」曲線，觀察邊際效益遞減點。同時監控執行長度與工具使用可靠性的變化——若執行長度先升後降，可能代表模型從「過度探索」走向「精準執行」，是健康的訊號。

### 潛在風險與注意事項

**風險一：資訊洩漏導致監督訊號弱化**
若在素材物化階段不小心把中間計算結果或最終答案放進前提，教師軌跡會變成「照抄」而非「推理」，失去訓練價值。**緩解**：在資訊支援圖中明確標記每個節點的「可見性」，並在探測階段設計「若代理直接抄到答案則視為失敗」的檢查。

**風險二：探測代理能力天花板造成誤判**
若探測代理本身能力不足，可能將「代理不會做」誤判為「環境有缺陷」，導致過度修復。**緩解**：使用比教師代理更強或至少同等能力的探測代理，並對修復紀錄做人工抽樣審查。

**風險三：修復過程偏離原始意圖**
反覆修復可能讓任務環境逐漸偏離最初的專業意圖（例如為了讓探測通過而簡化任務）。**緩解**：設定修復的「不可變更清單」（如交付物欄位、判斷標準），並在每次修復後比對意圖雜湊值。

**風險四：規模化後的執行長度膨脹**
論文中觀察到執行長度先升後降的現象，但在某些模型上可能出現**執行長度單調上升**（過度思考）或**單調下降**（過早結束）。**緩解**：監控每個 checkpoint 的平均步數與工具呼叫次數，必要時加入長度正則化或獎勵機制。

**風險五：領域偏誤與文化適用性**
論文的 612 種職業以美國勞動市場為主（O*NET 為基礎），直接套用至台灣或華語場景可能產生職業分類、術語、規範的落差。**緩解**：在地化階段應引入本土職業字典（如勞動部職業分類典）與領域專家審查。

**風險六：資料與模型釋出的授權風險**
若訓練資料中含有受著作權保護或含個資的真實產物，釋出模型權重時可能衍生法律爭議。**緩解**：在素材物化階段進行去識別化與授權審查，並在資料釋出時附上明確的授權條款。

### 與其他技術的整合建議

**與代理框架整合**
WorkFactory 產出的訓練資料可相容於 LangGraph、AutoGen、OpenAI Agents SDK 等主流代理框架。建議在 SFT 階段將工具呼叫序列化為框架原生格式（如 LangGraph 的 state graph、OpenAI 的 function calling JSON），以便部署時直接複用。

**與 RAG 系統整合**
資訊支援圖本質上是一種「任務級知識圖譜」，可與企業既有的 RAG 系統串接：將圖中的「前提資訊」節點對接到向量資料庫或知識庫，讓代理在執行時能動態查詢，而非僅依賴任務環境中的靜態檔案。

**與評測平台整合**
WorkPilot 的評估可整合 GDPval-AA、JobBench、Workspace-Bench、OmegaUse-OfficeVal 等基準測試。建議建立 CI/CD 流程，每次模型更新都自動跑完整基準，並追蹤 Elo 評分變化趨勢。

**與 RLHF / RLAIF 整合**
WorkFactory 提供的「通過探測的任務」可作為 RL 階段的環境來源——以探測診斷出的缺陷作為負回饋、以教師軌跡作為正回饋，進一步提升模型的可靠性。

**與工作流程引擎整合**
對於企業內部流程，可將 WorkFactory 的意圖庫對接到 BPMN 或流程引擎（如 Camunda、Airflow），讓代理不僅能執行單一任務，還能協調多步驟的工作流程。

**與開源生態整合**
論文已於 GitHub 釋出資料與模型（IQuestLab/WorkFactory），建議在實作初期先複現其 4B 規模的結果，作為基準線，再逐步擴展到自有的職業領域。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）與第 3.1 節（Overview），掌握「為什麼需要建構可執行的專業任務」這個核心問題。圖 1 的基準測試結果能幫助你直觀理解 WorkPilot 的能力邊界。實作上可從小規模（單一職業、約 100 個任務）開始，體驗「意圖 → 資訊支援圖 → 探測 → 修復」這個閉環。

**給 AI 工程師**：重點關注第 3 節的技術細節，特別是資訊支援圖的節點設計、探測代理與教師代理的隔離機制、以及規模化分析中觀察到的執行長度變化。在工程實作上，建議先搭建可重現的容器化環境與軌跡記錄系統，再處理資料生成的規模化問題；微調階段則應特別注意對話格式與 loss masking 的設計。

**給研究者**：第 2 節的相關工作比較（特別是與 GraphForge、WorkGenesis、NexForge 的對比）能幫助你定位 WorkFactory 在「任務合成」研究譜系中的位置。規模化分析章節（執行長度先升後降、模型依賴的邊際效益遞減）是值得延伸探討的方向，例如可進一步研究「為何不同模型出現不同的規模化曲線」以及「資訊支援圖的結構複雜度與下游效能的關聯」。

**給產品經理**：核心訊息是「資料品質決定代理能力上限」——WorkFactory 的價值不在於模型架構，而在於它如何系統性地建構「資訊齊備但保留推理空間」的任務環境。產品化時應思考：目標使用者是誰（內部員工、終端客戶、還是開發者）？需要覆蓋哪些職業？每個職業的任務深度要多細？建議從一個高 ROI 的垂直場景切入（如客服、財會、開發），驗證後再橫向擴展。
