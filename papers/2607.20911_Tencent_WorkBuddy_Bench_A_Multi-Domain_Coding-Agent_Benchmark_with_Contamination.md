## ⚡ TL;DR

WorkBuddy Bench 解決現有基準易污染或封閉難稽核的問題，以真實評估編程智慧體。
任務從真實提交、PR 與業務情境逆向工程，改寫為口語化角色扮演請求，涵蓋程式碼、網頁、辦公與安全領域。
採用統一目錄格式與隔離沙箱，在兩種智慧體框架下端到端可複現，並提供跨模型排行榜。

## 摘要翻譯

我們提出騰訊 WorkBuddy 基準測試（Tencent WorkBuddy Bench），一個用於編程智慧體（coding agent）的多領域評測套件（multi-domain evaluation suite）；本報告記載其建構方法、評分協定，以及跨模型排行榜（cross-model leaderboard）。其核心為一個統一的評測架構，用於建構與執行橫跨程式碼（Code）、網頁（Web）、辦公（Office）與安全（Security）四個工作領域（work domain）的分布感知（distribution-informed）編程智慧體任務。不同於改編公開議題文本（issue text），每項任務皆從真實提交（real commit）、拉取請求（pull request, PR）或業務情境（business scenario）以逆向工程（reverse-engineered）方式改寫而來，並改寫為簡短、口語化的角色扮演請求（role-played request），因此任務提示無法透過網路搜尋底層的議題、拉取請求或提交討論串（commit thread）來還原。由於資料集以開放方式釋出——包含任務目錄格式（task-directory format）、環境映像檔（environment image）、評測框架（evaluation harness）、測試與參考解決方案（reference solution）——其抗資料污染（contamination-resistant）能力奠基於此任務建構方式與資料集版本控制（dataset versioning），而非仰賴保密。四個子領域——儲存庫層級工程（repository-level engineering）、前端開發（front-end development）、辦公與業務流程（office and business workflows），以及紅隊／藍隊安全（red-/blue-team security）——檢驗真實工作中互補的面向，各自採用不同的驗證方式（verification style）。所有子領域皆以統一的任務目錄格式封裝，並在統一且可複現的協定（reproducible protocol）下，於兩個智慧體執行框架（agent harness）——CodeBuddy Code 與 Claude Code——上執行；完整的開放釋出使本基準測試得以端到端可複現（end to end reproducible）並可直接稽核（auditable），因為任何第三方都能重新執行每項任務並檢視其內容。由於每個子領域使用不同的評分工具（scoring instrument），分數無法跨子領域比較，因此本套件不提供整體平均。我們報告數個模型家族（model family）間的跨模型排行榜。

### 核心貢獻（3～5點）
- 提出首個橫跨程式碼（Code）、網頁（Web）、辦公（Office）、安全（Security）四大工作領域的編程智慧體多領域評測套件，並以貼近真實工作分布的任務設計檢驗不同面向的能力。
- 透過從真實提交、拉取請求或業務情境逆向工程改寫，並以口語化、角色扮演請求呈現任務提示，有效降低模型因記憶公開資料而獲得不實高分的資料污染風險。
- 完整開放釋出資料集、環境映像檔、評測框架、測試與參考解決方案，並輔以資料集版本控制，使基準測試端到端可複現且可被第三方直接稽核。
- 四個子領域各自採用獨立的驗證方式與評分工具，因此不提供跨領域的整體平均分數，確保評測結果的解讀更為嚴謹。
- 在多個模型家族間建立跨模型排行榜，並於 CodeBuddy Code 與 Claude Code 兩大智慧體執行框架上執行統一的評測協定。

### 適合對象
本論文適合從事編程智慧體、大型語言模型評測、軟體工程自動化、前端開發、辦公流程自動化及資安紅藍隊研究的學者與工程師閱讀；對於關注基準測試資料污染問題、開放可複現評測協定，以及跨領域真實工作場景評估的研究人員與實務工作者尤其具有參考價值。

## 深度分析

#### 方法論解析

Tencent WorkBuddy Bench（騰訊 WorkBuddy 基準測試）的核心方法論可概括為「分布感知（distribution-informed）的多領域任務建構」。不同於傳統靜態公開測試集（static public suite）直接採用可爬取的 issue text（議題文本）或 pull request（拉取請求）描述，本研究從真實的 real commit（真實提交）、PR 討論串、office 工作流程與安全事件出發，透過逆向工程（reverse-engineered）將原始素材改寫為簡短、口語化、角色扮演（role-played）的請求。這樣的設計使得任務 prompt 無法透過網路搜尋底層 issue thread（議題討論串）或 commit thread（提交討論串）直接還原，從而在建構層面降低資料污染（contamination）風險。

整個 benchmark 分為四個工作領域（work domain）：

- **Code（程式碼）**：儲存庫層級工程（repository-level engineering），要求 coding agent（編程智慧體）在真實開源程式碼庫中定位、修改並驗證變更。
- **Web（網頁）**：前端開發（front-end development），涵蓋頁面生成、資料視覺化、狀態互動、測試與文件轉換等。
- **Office（辦公）**：辦公與業務流程（office and business workflows），涉及多檔案讀取、跨交付物資訊傳遞與工作區狀態更新。
- **Security（安全）**：紅隊／藍隊安全（red-/blue-team security），包含漏洞分析、入侵指標（IoC）處理與攻防案例。

四個子領域採用統一的 task-directory format（任務目錄格式）封裝，並在兩種 agent harness（智慧體執行框架）——CodeBuddy Code 與 Claude Code——下執行。驗證方式則依領域特性而異：Code 主要使用 unit test（單元測試）；Web 結合 unit test 與 rubrics（評分規準）；Office 使用 rubrics 並輔以 LLM as Judge（大型語言模型評審）；Security 則以 LLM as Judge 為主。此外，每個任務設有 admission gate（准入門檻）：baseline（基線解法）得分需 ≤0.3，oracle（參考解）得分需 ≥1.0，以確保任務具鑑別度且不會過於簡單或不可能完成。

抗污染機制並不依賴「保密」，而是結合 prompt 重寫與 dataset versioning（資料集版本控制）。由於資料集完全開放，第三方可稽核每個任務內容，同時版本控制讓社群能追蹤任務變更與潛在洩漏，形成可審計的污染防護。

#### 實驗數據解讀

根據文中跨模型排行榜（cross-model leaderboard）所呈現的趨勢，模型在 Code 與 Web 兩個子領域的表現相對較高，而在 Office 與 Security 則明顯下降。這一現象反映出當前 coding agent 在以下能力上的落差：

- **Code**：雖然已有不錯的 repository-level reasoning（儲存庫層級推理）能力，但面對真實、口語化且經過改寫的需求時，仍可能因語義理解或上下文定位錯誤而失分。
- **Web**：前端任務涉及視覺、互動與程式邏輯的綜合判斷，unit test 與 rubrics 的混合評分能較客觀地捕捉生成品質。
- **Office**：業務流程需要跨多個檔案與交付物進行資訊整合，模型容易在狀態追蹤、格式轉換與長程依賴上出錯，因此分數偏低。
- **Security**：紅藍隊任務不僅需要專業領域知識，也涉及對抗性推理，LLM as Judge 的評分波動較大，顯示該領域仍具高度挑戰性。

作者明確指出，由於每個子領域使用不同的 scoring instrument（評分工具），分數不可跨領域比較，因此不報告 suite-wide average（全測試集平均）。這是實事求是的做法，避免將性質迥異的任務強行加總造成誤導。admission gate 的設計也確保了實驗數據的內部有效性：baseline ≤0.3 避免任務過於簡單，oracle ≥1.0 避免任務無解或測試有誤。

值得注意的是，兩種 agent harness 的並行執行可作為協定穩健性的參考。若同一模型在 CodeBuddy Code 與 Claude Code 下表現差異過大，則可能暗示評測結果受框架實作細節（如工具呼叫、檔案操作、錯誤處理）影響，而非純粹反映模型能力。

#### 與現有研究的比較

相較於現有 benchmark，Tencent WorkBuddy Bench 的定位介於「完全公開的靜態測試集」與「封閉的廠商生產環境基準測試（vendor production benchmark）」之間，並試圖兼取兩者之長：

- **相較於 SWE-bench / SWE-bench Verified**：這類靜態公開測試集直接使用可爬取的 issue text 與 PR 內容，存在 memorization（記憶化）風險，且範圍多侷限於單一 bug 修復。WorkBuddy 透過 prompt 重寫與多領域設計，擴大了評測範圍並降低污染。
- **相較於 CursorBench**：廠商生產環境基準測試雖能反映真實使用分布，但封閉性使外部無法檢驗任務選擇偏差（selection bias）或確認其是否泛化至其他使用者群體。WorkBuddy 以開放釋出換取可稽核性（auditable）。
- **相較於前端生成或網頁代理 benchmark**：這些測試集同樣依賴可爬取的公開儲存庫、截圖或網站。WorkBuddy 的 reverse-engineered 任務建構方式減少了 crawlability（可爬取性）帶來的污染。

然而，本研究也存在若干限制：

1. **評分工具不一致**：雖然作者已說明不可比較，但這也意味著難以回答「哪個模型在整體真實工作上最強」這一綜合問題。
2. **LLM as Judge 的主觀性**：Office 與 Security 大量依賴模型評審，可能引入評審模型自身的偏見、幻覺或對提示詞的過度敏感。
3. **逆向工程的人為偏差**：任務改寫者的風格與理解會影響 prompt 的難度與歧義程度，難以完全標準化。
4. **僅測試兩種 harness**：不同 agent harness 的工具鏈與環境互動方式差異甚大，未來需要更多框架驗證結果的泛化性。
5. **安全任務的開放性爭議**：將 red-/blue-team security 任務完全公開，雖有助於研究，但也可能引發負責任揭露（responsible disclosure）方面的疑慮。

#### 可重現性評估

本研究在可重現性（reproducibility）方面的承諾相當完整：作者開放釋出 task directories（任務目錄）、environment image（環境映像檔）、evaluation harness（評測框架）、tests（測試）與 reference solution（參考解決方案）。配合統一的 reproducible protocol（可複現協定），第三方理論上可以端到端（end to end）重新執行每個任務並檢視內容，達到直接可稽核（auditable）的標準。

進一步評估可重現性的具體要素：

- **正向因素**：統一任務格式、容器化執行環境、明確的評分規則、dataset versioning 機制，以及開放原始碼與資料集。
- **潛在障礙**：environment image 可能體積龐大且依賴特定硬體；部分模型（如 Claude Code）為商業 API，需授權與費用；LLM as Judge 若未固定隨機種子與溫度參數，可能產生非確定性結果；長時間執行的 agent 任務對計算資源要求較高。

為提升可重現性，建議後續版本提供：映像檔雜湊值、鎖定依賴版本、judge 模型固定參數（temperature=0）、自動化重跑腳本，以及詳細的硬體與成本紀錄。

#### 未來研究方向

基於 Tencent WorkBuddy Bench 的設計與初步結果，未來研究可朝以下方向延伸：

1. **擴展更多工作領域**：例如行動應用開發、DevOps、資料科學、科學計算與雲端基礎設施維運，進一步貼近企業真實場景。
2. **跨領域評分校準**：發展統一的 scoring calibration 方法，使不同 scoring instrument 之間的分數能在某種程度上可比較，而不違反各領域本質差異。
3. **動態與持續更新 benchmark**：建立自動化流程，定期從真實 commit、PR 與業務案例生成新任務，並透過 dataset versioning 管理污染風險。
4. **人機協作評測**：引入 human-in-the-loop 機制，特別針對 Office 與 Security 等難以完全自動評分的任務，提升評估效度。
5. **多智慧體協作與長程任務**：評估多個 coding agent 協同完成大型專案的能力，並納入成本、延遲與可靠性的權衡分析。
6. **污染偵測與浮水印技術**：開發主動偵測模型是否記憶特定任務內容的工具，強化 contamination-resistant 的驗證。
7. **安全性與負責任揭露框架**：針對 Security 子領域建立更嚴謹的任務分級與釋出機制，平衡研究價值與潛在濫用風險。
8. **真實部署驗證**：將 benchmark 結果與實際開發團隊使用 agent 的 A/B 測試或生產指標進行對照，驗證其預測效度。

## 論文問答

**Q1：騰訊 WorkBuddy 基準測試主要想解決什麼問題？**
A：隨著編程智慧體能力快速提升，現有評測要麼是靜態公開測試集、容易被資料污染，要麼是封閉的廠商生產環境基準測試、無法外部稽核，因此難以真實衡量智慧體在實際工作中的表現。本論文提出的騰訊 WorkBuddy 基準測試旨在建立一個多領域、分布感知且抗資料污染的評測套件，涵蓋程式碼、網頁、辦公與安全四大真實工作領域。透過統一的任務建構與評分協定，它能更準確地反映智慧體在複雜工作場景中的能力。

**Q2：為什麼像 SWE-bench 這類靜態公開基準測試不足以評量編程智慧體？**
A：SWE-bench 等公開基準的議題文本與解答通常可在網路上被爬取，模型可能透過記憶特定議題討論串或拉取請求內容來取得高分，而非真正進行儲存庫層級推理。此外，這些測試大多聚焦於單一議題的錯誤修復，範圍過於狹窄，無法涵蓋真實軟體工程中的多樣工作流程。因此，它們容易受到資料污染影響，也難以評估智慧體在真實開發情境中的綜合能力。

**Q3：為什麼抗資料污染與開放性對編程智慧體基準測試同樣重要？**
A：抗資料污染能確保分數提升來自真正的能力進步，而不是模型記憶了公開的議題或拉取請求內容；開放性則讓第三方可以檢視任務分布、重現評測流程，並確認沒有選擇性偏差。騰訊 WorkBuddy 基準測試同時滿足這兩項需求，它將真實來源改寫為口語化、角色扮演請求，並完整公開任務目錄、環境映像檔、評測框架與參考解決方案。這種設計讓評測既可信又透明，有利於學術界與產業界共同監督。

**Q4：本論文核心的任務建構方法是什麼？**
A：每一個任務都是從真實提交、拉取請求或業務情境逆向工程而來，再被改寫成簡短、口語化且帶有角色扮演的請求。這樣的建構方式讓任務提示與原始公開來源脫鉤，無法透過網路搜尋直接還原。同時，任務分布會根據真實使用情境進行調整，使評測內容更貼近實際工作需求。

**Q5：本基準測試在抗資料污染上的關鍵創新是什麼？**
A：關鍵創新在於「提示不可還原性」：角色扮演請求的表達方式與原始議題、拉取請求或提交討論串不同，因此無法透過網路搜尋找回對應內容。再加上資料集採用開放釋出與版本控制，抗污染能力來自建構方式本身，而非依賴保密。這是一種從設計層面解決污染問題的方法，比單純依靠發布時的新穎性更為穩固。

**Q6：為什麼要採用統一的任務目錄格式，並在兩個智慧體執行框架上運行？**
A：統一的任務目錄格式讓程式碼、網頁、辦公與安全四個領域的任務都能以相同結構封裝，包含環境、測試與參考解答，確保評測流程一致且可複現。在 CodeBuddy Code 與 Claude Code 兩個智慧體執行框架上運行，則能驗證協定的通用性，並降低單一框架帶來的偏差。這種設計也讓第三方可以端到端重現整個評測，並直接稽核每個任務的內容與計分結果。

**Q7：四個子領域各自採用什麼驗證與計分方式？**
A：程式碼領域主要進行儲存庫層級工程，通常以單元測試作為驗證；網頁領域涵蓋前端與圖形介面任務，會使用評分規則與大型語言模型作為評審；辦公領域處理多檔案與多交付物的業務流程，著重交付成果是否正確且可用；安全領域則包含紅隊與藍隊情境，透過漏洞驗證或攻擊利用結果來計分。每個子領域都根據自身特性設計最合適的評分工具。

**Q8：論文報告了哪些主要實驗結果？**
A：論文公布了一個跨模型排行榜，比較多個模型家族在程式碼、網頁、辦公與安全四個追蹤項目上的表現。由於各追蹤項目使用不同的評分工具，分數無法直接跨領域比較，因此結果以各領域獨立呈現，而非給出單一總分。這樣的呈現方式能清楚看出不同模型在哪些真實工作面向具有優勢。

**Q9：本研究是否進行了消融實驗或計分選擇的分析？**
A：雖然論文沒有採用傳統的消融實驗，但它在設計上進行了多項重要控制，例如明確不報告跨領域的總平均分，以避免產生誤導性的單一排名。此外，評分機制設有入門門檻，確保隨機基線分數夠低而參考解答可達滿分，從而驗證計分範圍的合理性。每個追蹤項目都選用與該領域自然驗證方式相符的評分工具，以提升結果的可解釋性。

**Q10：這個基準測試可以支援哪些實際應用場景？**
A：企業與開發團隊可以利用它來評估不同編程智慧體在真實工作情境中的表現，例如儲存庫工程、前端開發、辦公自動化與安全測試，從而選擇最適合自身需求的模型。研究人員也能將其作為標準測試平台，用於開發與驗證新的智慧體架構與推理策略。由於整個流程可重現且可稽核，它也適合用於長期追蹤模型能力演進。

**Q11：從產品設計角度，這個基準測試帶來哪些考量？**
A：因為所有資料與工具都公開釋出，廠商與企業可以自行部署評測、檢視任務內容，並根據內部工作流程調整任務分布。使用兩個不同的智慧體執行框架進行測試，也能避免智慧體過度擬合單一執行環境。資料集版本控制則讓使用者能夠追蹤更新歷程，確保不同時間點的評測結果具有可比性與公平性。

**Q12：這項工作可能對編程智慧體評估領域帶來什麼影響？**
A：它推動評測典範從靜態、依賴保密的測試集，轉向分布感知且可稽核的開放評測。透過同時涵蓋多個工作領域，它鼓勵研究者開發更具通用性的編程智慧體，而非只針對單一任務類型進行優化。此外，以提示改寫與版本控制實現抗資料污染，也為未來基準測試的建構提供了可參考的標準。

**Q13：論文承認了哪些限制？**
A：由於四個子領域使用不同的評分工具，分數無法直接比較，因此無法給出一個「最強智慧體」的單一排名。目前涵蓋的四大領域雖已相當廣泛，但仍可能無法完全代表所有真實工作場景或特定組織的內部流程。此外，抗污染設計主要針對可網路搜尋的提示，對於其他形式的資料外洩仍需要額外防範。

**Q14：這個基準測試可能面臨哪些失敗案例或挑戰？**
A：智慧體可能在需要長期規劃、跨多檔案協調或理解細微業務語境的任務上表現不佳；部分前端或辦公任務對環境細節與執行框架實作較為敏感，可能導致評分波動。若採用大型語言模型作為評審，也可能引入評審本身的偏好與偏差，需要持續檢視與校正。

**Q15：未來有哪些值得發展的方向？**
A：未來可以擴展到更多工作領域，例如行動應用開發、資料科學流程或多智慧體協作任務，以進一步貼近真實產業需求。同時可以改進自動化評分機制，降低評審模型的偏差並提升計分穩定性。定期更新與版本控制資料集，也有助於持續對抗新興的資料污染風險，並跟上智慧體能力的快速演進。

## 實務應用指南

### 適用場景

1. **企業導入編程智慧體前的選型評估**  
   在採購或部署內部編程智慧體前，利用 WorkBuddy Bench 的四個領域（Code、Web、Office、Security）比較不同模型家族在真實工作分布下的表現，避免僅憑單一公開測試集（如 SWE-bench）就做決策。

2. **模型版本上線前的迴歸測試**  
   將基準測試整合進 MLOps / CI 流程，當模型或 Agent 框架更新時自動執行，監控是否出現能力退化，特別是 repository-level reasoning、前端互動、跨文件辦公流程與安全分析等面向。

3. **紅隊／藍隊安全能力驗證**  
   使用 Security 子領域的 CVE、IoC、漏洞利用與防禦案例，在隔離沙箱中評估智慧體對安全事件的識別、分析與處置能力，作為資安演練與 SOC 流程的輔助工具。

4. **內部 Agent 框架開發的對照實驗**  
   在開發自有 harness（如 CodeBuddy Code）或調整提示工程時，以統一任務目錄與可複現協定作為控制變因，比較不同執行框架對同一組任務的影響。

5. **工程師與 AI 協作培訓教材**  
   將經過逆向工程改寫的口語化、角色扮演任務作為教學案例，幫助工程師理解如何向編程智慧體下達明確且可驗證的需求。

### 實作前置條件

**資料**
- 取得 Tencent WorkBuddy Bench 的任務目錄、環境映像檔、評測框架、測試與參考解決方案，並建立資料集版本控制機制。
- 若自建內部任務，需準備真實 commit、拉取請求或業務情境來源，並完成去識別化與口語化改寫，避免提示可直接被網路搜尋還原。

**運算**
- 可執行容器化隔離沙箱的運算叢集（CPU 為主，模型推理端視需求配置 GPU）。
- 足夠儲存空間存放環境映像檔、任務目錄與執行產出物。
- 每個任務需在乾淨、隔離、無外部帳號金鑰的環境中執行，Security 領域尤需限制網路與主機存取。

**技能**
- 熟悉 Docker / container、Python、CI/CD 與 LLM API 整合。
- 具備前端、Office 文件格式、資安測試等至少一個領域的專業知識，以便理解各領域評分工具。
- 能撰寫與維護單元測試、評分規則（rubric）或 LLM-as-judge 提示，並進行人工稽核校準。

---

### 實作步驟建議

1. **定義評測目標與模型範圍**  
   決定要比較的模型家族、智慧體執行框架（CodeBuddy Code / Claude Code）以及重點領域，避免一開始就追求全量執行。

2. **部署任務目錄與隔離環境**  
   下載或同步資料集版本，建立統一的任務目錄格式，並在沙箱中掛載環境映像檔，確保執行環境一致。

3. **設定統一可複現協定**  
   固定 timeout、token 上限、檔案系統權限與外部網路限制，讓不同模型在相同條件下執行，便於後續比較。

4. **執行分領域評測**  
   依 Code、Web、Office、Security 四軌分別執行任務，收集智慧體輸出、中間步驟日誌與最終產出物。

5. **使用對應評分工具計分**  
   Code 用單元測試、Web 用互動驗證與規則、Office 用跨文件檢查、Security 用紅藍隊指標。切記**不要跨子領域平均**。

6. **分析結果並產生排行榜**  
   產生跨模型排行榜，識別各模型在真實工作場景中的強弱項，並將發現回饋給模型訓練或產品改進。

7. **版本化與持續維護**  
   隨業務分布變化更新任務，標註資料集版本，定期重新抽樣與稽核，防止資料漂移與污染累積。

### 潛在風險與注意事項

| 風險 | 說明 | 緩解方式 |
|---|---|---|
| **資料污染與記憶化** | 模型可能因記憶公開 issue 或 PR 內容而獲得不實高分。 | 採用逆向工程改寫的角色扮演請求，並搭配資料集版本控制與定期更新。 |
| **跨領域分數誤用** | 四個子領域使用不同評分工具，分數本質不可比。 | 報告時分軌呈現，不合成單一總分或 KPI。 |
| **安全任務的執行風險** | Security 任務可能涉及惡意程式碼或漏洞利用。 | 嚴格在隔離沙箱執行，關閉外部網路，禁止存取主機敏感資源。 |
| **自動評分偏差** | LLM-as-judge 或 rubric 可能產生主觀或一致性问题。 | 定期抽樣人工稽核，建立評分者間信度，並校準 judge prompt。 |
| **任務分布與自身業務錯配** | 論文任務分布未必符合貴組織實際使用場景。 | 以論文方法為範本，補充內部真實 commit、PR 與業務情境。 |
| **運算與成本爆炸** | 全量任務 × 多模型 × 多次重跑成本高昂。 | 先抽樣試跑，建立穩定後再擴充；將非必要重跑排程在離峰時段。 |

### 與其他技術的整合建議

- **MLOps / CI 管線**  
  將 WorkBuddy Bench 包裝成 pytest 或獨立 CI job，於模型更新、框架改版或提示工程調整後自動觸發，形成標準化迴歸測試閘道。

- **內部原始碼與協作平台**  
  從企業內部的 Git 儲存庫、PR、程式碼審查紀錄自動抽取真實案例，經過改寫後納入任務目錄，讓基準測試持續貼近內部工作分布。

- **統一模型服務介面**  
  為不同模型家族建立一致 API 介面，使 CodeBuddy Code、Claude Code 或未來其他 harness 都能無縫接入同一組任務與評分流程。

- **安全運維（SOC）與演練平台**  
  將 Security 子領域的執行結果與漏洞管理、威脅情資（IoC）或紅隊演練系統對接，補充自動化安全能力評估。

- **企業文件與知識管理系統**  
  Office 子領域可延伸至 SharePoint、企業文件庫或試算表流程，驗證智慧體在真實辦公環境中處理多文件、多格式交付物的能力。

### 給不同背景讀者的閱讀建議

**初學者**  
建議先閱讀摘要與圖 1，掌握四個工作領域與統一任務目錄格式的整體概念。重點理解為何「從真實提交逆向工程改寫成口語化角色扮演請求」能提升抗資料污染能力，以及為什麼分數不能跨領域直接比較。技術細節可先略過，專注於基準測試的設計理念與應用價值。

**AI 工程師**  
請深入研讀任務建構方法、統一可複現協定，以及 CodeBuddy Code 與 Claude Code 兩種智慧體執行框架的實作細節。特別關注環境隔離、timeout 設定、權限控管與各領域評分工具（unit test、rubric、LLM-as-judge）的實作方式，並思考如何將此基準嵌入現有 CI/CD 與模型服務流程。

**研究人員**  
值得關注的是 contamination-resistant 的設計原則、distribution-informed 的取樣方法，以及資料集版本控制策略。可進一步探討不同驗證方式（單元測試、規則評分、LLM 評審）對測量效度與跨模型公平性的影響，並以此發展更嚴謹的編程智慧體評估方法論。

**產品經理**  
請聚焦跨模型排行榜與各領域分數所揭示的模型優劣，將其作為選型、採購與產品路線規劃的依據。同時要注意避免把不可比的跨領域分數合成單一 KPI，並確保評測任務的分布能反映目標用戶的真實工作場景，而非僅是技術上的高分任務。
