## ⚡ TL;DR

程式碼驅動影片生成雖能精確控制版面與時序，但渲染成功仍潛藏標籤重疊、鏡頭偏離等靜默感知缺陷。
本文提出無需訓練的VibeVideoAgent，透過七個感知基元與多時鐘表示法，在產製中提供精簡回饋。
在239項任務中，三款模型整體音視訊品質均提升，音視訊同步改善最多達0.56。

程式碼驅動影片生成（code-driven video generation）要求程式編寫代理（coding agent）撰寫並執行渲染程式（rendering program）。這能精確控制字型排版（typography）、資料視覺化（data visualizations）、同步音訊（synchronized audio）與多鏡頭場景（multi-shot scenes），並留下可編輯專案（editable project）。然而，即使程式正常結束，仍可能渲染出標籤重疊（labels collide）、偏離目標的攝影機（off-target cam）、損壞的物件互動，或不同步的旁白（narration），且這些都不會引發執行階段錯誤（runtime error）。將渲染幀與音訊回傳至編寫階段會膨脹其長程脈絡（long-horizon context），而僅批評完成的全解析度渲染（full-resolution render）則會將早期設計錯誤轉化為高成本重寫（costly rewrites）。我們提出 VibeVideoAgent，一個無需訓練的框架（training-free framework），讓程式編寫代理在整個製作過程中檢視其草稿。多模態感知（multimodal perception）在與編寫代理分離的短暫脈絡中執行，並回傳精簡且具體的發現（compact, grounded Findings）。七個基元（primitives）在統一的多時鐘表示法（multi-clock representation）上運作，涵蓋素材與草稿：由粗到細（coarse to fine）地探索媒體、以每個所需模態（required modality）的證據（evidence）驗證引用需求（quoted requirements）、在獨立時鐘（separate clocks）上比較草稿與參考素材或早期修訂版本，並局部量測（local measurement）串流訊號（stream signals）。精簡的分階段協議（staged protocol）讓代理先在最小預覽（minimal preview）上測試其風險最高的決策（riskiest decision）。在全部 239 個 VibeVideoBench 任務上，採用匹配的代理執行時間（matched agent runtimes）與固定的感知模型（fixed perception model），VibeVideoAgent 提升了 Claude Opus 5.5 的整體音視訊品質（holistic audiovisual quality, L3）（4.03 → 4.43，同時 L2 評分規程符合度（rubric compliance）從 98.87% 提升至 99.35%）、GPT-6 Astra（4.03 → 4.27），以及 Claude Sonnet 5.5（3.97 → 4.10），其中音視訊同步（audio-visual synchronization）的提升幅度最大（最高達 +0.56）。控制消融實驗（controlled ablations）顯示每個組件皆有貢獻，而軌跡稽核（trajectory audits）顯示程式碼編輯的粒度（granularity of code edits）決定了評分規程遵循度（rubric adherence）與感知品質（perceptual quality）之間的取捨（trade-off）。

### 核心貢獻（3～5點）
- **提出 VibeVideoAgent 框架**：首個無需訓練的程式碼驅動影片生成框架，將多模態感知迴路（perceptual loop）解耦於程式編寫代理之外，以短暫脈絡執行感知並回傳精簡且具體的發現（compact, grounded Findings），有效避免長程脈絡膨脹與高成本重寫。

- **建立 VibeVideoBench 基準並驗證有效性**：在 239 項任務上，於匹配的代理執行時間與固定的感知模型條件下，於 Claude Opus 5.5、GPT-6 Astra、Claude Sonnet 5.5 三款大型語言模型上均提升整體音視訊品質（L3）與評分規程符合度（L2），其中音視訊同步提升最高達 +0.56。
- **透過消融實驗與軌跡稽核揭示關鍵取捨**：控制消融實驗證實各組件均有效；軌跡稽核則揭示程式碼編輯的粒度（granularity of code edits）為評分規程遵循度與感知品質之間的核心取捨因子。

## 深度分析

#### 方法論解析

VibeVideoAgent 的核心方法論建立在「解耦感知迴路」(decoupled perceptual loop) 的設計哲學上，針對傳統程式編寫代理 (coding agent) 在影片創作中面臨的三個結構性缺陷提出系統性解決方案。

**問題診斷的三層架構**

論文首先精確識別出影片創作 (video authoring) 與軟體工程之間的本質差異。軟體工程的缺陷通常透過編譯器錯誤 (compiler errors) 或失敗測試 (failing tests) 顯現，但影片創作存在三個無法被傳統回饋機制捕捉的問題：

1. **靜默感知缺陷 (silent perceptual bugs)**：程式碼可正常退出 (exit code 0) 並產生有效 MP4，但視覺上可能出現角色背包位置錯誤、3D 攝影機偏離主角、標籤重疊 (labels collide)、旁白 (narration) 與圖表延遲兩秒等問題。
2. **脈絡污染 (context pollution)**：將原始幀與音訊附加至代理的歷史紀錄中，會以 $O(K \Delta t (f \tau_v + \tau_a))$ 詞元 (tokens) 的規模膨脹長程脈絡 (long-horizon context)，損害程式碼維護品質。
3. **延遲批評 (late critique)**：僅在最終全解析度渲染 (full-resolution render) 時審查，會將早期設計錯誤放大為全專案重寫 (full-project rewrite)。

**雙層感知架構**

VibeVideoAgent 採用兩個互補的感知層：

- **暫存式視覺語言模型工作者 (Φ, Stateless VLM worker)**：使用 Gemini 3.8 Flash，每次呼叫使用短暫存活的脈絡 (short-lived context)，避免原始媒體進入程式編寫代理的長程脈絡 $C_t$。
- **確定性訊號探針 (Ψ, Deterministic signal layer)**：基於 ffprobe/ffmpeg 的本地探測，無需模型呼叫即可量測解碼、響度、靜音、凍結幀、循環接縫等串流訊號 (stream signals)。

兩者共同產生精簡發現 (compact Findings) $f_t$，格式為 (判定 verdict, 範圍 span, 框 box)，體積遠小於原始媒體摘錄 $|E(M_t, \sigma_t)|$。

**多時鐘表示法 (Multi-clock representation)**

這是方法論的關鍵創新。影片創作涉及多種類型的媒體資產，各自運行在不同的時間軸上：

- 唯讀參考素材 (read-only reference assets)
- 零時長設計靜態圖 (zero-duration design stills)
- 位於影片偏移位置的鏡頭預覽 (shot previews placed at an offset)
- 完整粗剪 (full cuts)

統一的多時鐘表示法將這些異質資產綁定到其背後的原始程式碼雜湊值，使每個觀察都能追溯到具體的程式碼版本。

**七個感知基元 (Seven Primitives)**

七個基元分為四個功能角色：

| 角色 | 基元 | 功能 |
|------|------|------|
| 由粗到細探索 (coarse-to-fine) | describe_media | 描述媒體整體內容 |
| | locate_event | 定位特定事件 |
| | inspect_segment | 檢查特定片段 |
| | transcribe_speech | 轉錄語音 |
| 引用需求驗證 | check_requirement | 驗證簡述中引用需求，附帶模態閘控判定 (modality-gated verdict) |
| 跨時鐘比較 | compare_media | 在兩個獨立時鐘上比較媒體（參考 vs. 修訂） |
| 局部訊號探測 | probe_media | 解碼、響度、靜音、凍結、接縫量測 |

**分階段協議 (Staged Protocol)**

`plan_production` 將簡述中的引用約束連結到有序的製作拍點 (beats)，並強制代理在最小預覽 (minimal preview) 上測試風險最高的決策，再進入組裝 (assembly)、修訂 (revision)、定稿 (final) 階段。這種「先小後大」的策略避免了將錯誤決策放大到整個專案。

**與 VideoNexus 的關係**

論文明確指出此設計繼承自 VideoNexus [26] 的解耦原則——將影片感知置於規劃者脈絡之外——但擴展了三個新面向：處理隨編輯變動的草稿、跨音視訊模態的需求、以及跨版本的修復驗證。

#### 實驗數據解讀

**基準測試與評估設定**

實驗在 VibeVideoBench 的全部 239 項任務上進行，採用三個程式編寫模型（Claude Opus 5.5、Claude Sonnet 5.5、GPT-6 Astra）與其原生代理進行配對比較。感知模型固定為 Gemini 3.8 Flash，且匹配代理執行時間 (matched agent runtimes)，確保比較的公平性。

**三層評估指標**

- **L1**：基礎正確性（語法、執行成功）
- **L2**：評分規程符合度 (rubric compliance)，衡量是否滿足簡述中的具體要求
- **L3**：整體音視訊品質 (holistic audiovisual quality)，衡量觀感品質

**主要結果**

| 模型 | L3 提升 | L2 提升 | 備註 |
|------|---------|---------|------|
| Claude Opus 5.5 | 4.03 → 4.43 (+0.40) | 98.87% → 99.35% | 最大幅度提升 |
| GPT-6 Astra | 4.03 → 4.27 (+0.24) | L1 達 99.51% | |
| Claude Sonnet 5.5 | 3.97 → 4.10 (+0.13) | — | 較小幅度 |

**音視訊同步 (A-V synchronization) 的最大增益達 +0.56**，這直接驗證了「模態閘控判定」(modality-gated verdict) 機制的有效性——傳統代理最容易忽略的跨模態時序對齊問題，正是 VibeVideoAgent 改進最顯著的面向。

**消融實驗 (Controlled Ablations) 的意涵**

論文指出每個組件都有貢獻，這意味著：

- 多時鐘表示法是必要基礎，缺它則無法處理異質資產
- 七個基元缺一不可，特別是 `check_requirement` 的模態閘控機制
- 分階段協議的「最小預覽」步驟對風險隔離至關重要

**軌跡遙測 (Trajectory Telemetry) 的關鍵發現**

軌跡稽核 (trajectory audits) 揭示了**程式碼編輯的粒度 (granularity of code edits) 調控 L2 與 L3 之間的取捨 (trade-off)**：

- 過於頻繁的小幅驗證會提升 L2（嚴格符合規程）但可能犧牲 L3（整體觀感）
- 過於粗放的編輯則相反

這是一個重要的實務發現：驗證頻率與編輯粒度構成一個可調節的旋鈕，使用者可依任務性質（嚴格合規 vs. 創意品質）選擇不同的工作點。

**基準線比較的公平性**

值得注意的一點是，論文明確控制了「匹配的代理執行時間」，這避免了「VibeVideoAgent 只是因為呼叫更多次所以表現更好」的混淆變項。L3 的提升是在相同運算預算下取得的，這強化了結果的因果歸因強度。

#### 與現有研究的比較

**在程式碼驅動視覺生成譜系中的定位**

VibeVideoAgent 屬於「視覺程式設計」(visual programming) 傳統的延伸——從早期以語言模型組合視覺模組的可執行程式碼 [14, 37]，到圖表生成 [47, 51]、網頁與互動產物 [35, 55, 58]、動畫生成 [24, 38]。在影片領域，與 TheoremExplainAgent [21] 等系統共享「以程式碼取代像素生成」的哲學。

**與 MoVer 的關鍵差異**

MoVer [28] 透過邏輯規格驗證生成的動態圖形，但 VibeVideoAgent 強調三點超越：

1. **多模態覆蓋**：MoVer 專注於運動規格，VibeVideoAgent 涵蓋音視訊同步、字型排版、資料視覺化
2. **無需引擎適配器**：七個基元操作標準容器，適用於 3D WebGPU/Canvas、React/Remotion、Cairo、Manim、SVG、FFmpeg、Blender Python 等異質管線
3. **跨版本修復驗證**：透過雙時鐘差異比較 (dual-clock diff) 追蹤編輯效果

**與像素空間影片生成器的取捨**

相對於像素空間影片生成器 [20, 31, 39, 52] 及其代理式管線 [46]，VibeVideoAgent 採用根本不同的控制範式：

| 面向 | 像素空間生成器 | VibeVideoAgent |
|------|---------------|----------------|
| 控制精度 | 低（難以精確控制字型、圖表） | 高（透過程式碼） |
| 可編輯性 | 有限 | 完整原始專案 |
| 紋理與動作自然度 | 高 | 取決於渲染引擎 |
| 創作意圖保真度 | 中 | 高 |

兩者並非競爭關係，而是互補：當需要精確控制時，程式碼驅動方法勝出；當需要照片級真實感時，像素生成器更適合。

**相對於 VideoNexus 的擴展**

VideoNexus [26] 證明了將影片感知置於規劃者脈絡之外的價值，但僅處理固定影片的問答場景。VibeVideoAgent 將此原則擴展到創作場景，新增了：

- 隨編輯變動的草稿管理
- 跨音視訊模態的需求驗證
- 跨版本的修復追蹤

**限制與未涵蓋面向**

1. **感知模型依賴**：固定使用 Gemini 3.8 Flash，若該模型在特定視覺任務上表現不佳，整個系統會受影響
2. **基準測試範圍**：239 項任務的覆蓋面是否足以代表真實創作場景仍待驗證
3. **未涵蓋的創作類型**：論文未明確處理需要高度風格化或抽象表達的創作任務
4. **基準線的時效性**：Claude Opus 5.5、GPT-6 Astra 等模型版本為論文發表時的狀態，隨基礎模型演進，比較結果可能改變

#### 可重現性評估

**程式碼與工具可用性**

論文明確指出 VibeVideoAgent 透過模型脈絡協議 (Model Context Protocol, MCP) [2] 暴露七個基元，與原生代理式程式碼 CLI（Claude Code 與 Codex CLI）整合。這種標準化介面設計有利於重現：

- **MCP 標準化**：任何支援 MCP 的代理都可呼叫這些基元
- **無引擎適配器**：七個基元操作標準媒體容器，無需為特定渲染引擎客製
- **固定感知模型**：Gemini 3.8 Flash 作為唯一感知模型，簡化變數控制

**資料集可用性**

VibeVideoBench 包含 239 項任務，雖然論文中未明確聲明是否開源，但作為基準測試的標準做法，預期會伴隨論文發布。然而，論文中未提供明確的資料集授權或下載連結資訊（基於提供的文本片段），這是潛在的重現障礙。

**模型權重**

VibeVideoAgent 本身是無需訓練的框架 (training-free framework)，不涉及自有模型權重，因此這方面不構成重現障礙。系統依賴的外部模型（Claude Opus 5.5、Claude Sonnet 5.5、GPT-6 Astra、Gemini 3.8 Flash）均為商業 API，使用者需透過對應平台取得存取權。

**實驗設定的可重現性要素**

- 固定的感知模型（Gemini 3.8 Flash）
- 匹配的代理執行時間
- 統一的評估指標（L1/L2/L3）
- 跨三個程式編寫模型的對照實驗

這些設計選擇有利於獨立驗證，但完整重現仍需：

1. 取得 VibeVideoBench 完整資料集
2. 部署 MCP 伺服器實作七個基元
3. 設定三個商業 API 的存取權限
4. 實作評估流程（特別是 L3 的整體音視訊品質評分）

**軌跡遙測資料**

論文中提到的軌跡稽核 (trajectory audits) 涉及代理執行的詳細日誌，這些資料若能公開，將大幅促進後續研究對「編輯粒度 vs. 品質取捨」現象的深入分析。

#### 未來研究方向

**1. 感知模型的專門化**

當前系統依賴通用的 Gemini 3.8 Flash 作為感知模型。未來可探索：

- 為影片創作任務微調專門的感知模型
- 針對特定模態（如音視訊同步、字型可讀性）訓練專家模型
- 引入不確定性量化，讓代理在感知信心不足時主動請求更多證據

**2. 編輯粒度的自動化調控**

軌跡稽核揭示的「編輯粒度 vs. 品質取捨」是一個豐富的研究方向：

- 開發自動判斷「該做小幅驗證還是大幅重構」的策略
- 探索強化學習方法，讓代理學會在不同任務類型下選擇最佳編輯粒度
- 研究編輯粒度與任務複雜度、簡述嚴格度之間的交互作用

**3. 跨模態需求的更深層語義理解**

當前的 `check_requirement` 透過模態閘控判定確保證據覆蓋所有所需模態，但對需求之間的衝突與優先順序處理仍待探索：

- 當簡述中的需求互相矛盾時如何取捨
- 隱含需求的推斷（如「專業感」背後的具體視覺特徵）
- 跨文化、跨領域的創作慣例編碼

**4. 從粗剪到定稿的漸進式品質提升**

分階段協議目前是固定的四個階段，未來可考慮：

- 自適應階段數：根據任務難度動態決定需要幾輪修訂
- 階段間的知識累積：讓早期階段的發現能結構化地傳遞給後續階段
- 平行化探索：同時測試多個風險點，而非序列化處理

**5. 與像素空間生成器的混合管線**

VibeVideoAgent 與像素空間影片生成器各有擅長，未來可探索混合架構：

- 用程式碼驅動方法生成結構化骨架（場景、攝影機、字型、圖表）
- 用像素生成器填充紋理與細節
- 在兩者之間建立統一的感知迴路

**6. 多人協作創作支援**

當前框架假設單一代理創作，但真實創作常涉及多人協作：

- 多代理之間的感知發現如何共享與協調
- 版本控制系統與多時鐘表示法的整合
- 創作意圖的追溯與責任歸屬

**7. 評估方法的標準化**

L3 整體音視訊品質的評分仍涉及主觀判斷，未來可：

- 建立更大規模的人類標註資料集
- 開發更可靠的自動化品質評估指標
- 研究 L1/L2/L3 之間的相關性與預測關係

**8. 領域特化的擴展**

論文已展示對 3D WebGPU/Canvas、React/Remotion、Cairo、Manim、SVG、FFmpeg、Blender Python 的支援，未來可進一步探索：

- 科學視覺化（天文、生物、化學模擬）
- 教育內容（互動式教學影片）
- 遊戲原型（機制展示影片）
- 新聞圖表（資料驅動敘事）

這些方向都將延續 VibeVideoAgent「以程式碼為媒介、以感知為閉環」的核心精神，進一步推動影片創作從「一次性渲染」走向「可迭代、可驗證、可追溯」的工程化範式。

## 論文問答

**Q1：程式碼驅動影片生成（Code-driven video generation）面臨的核心問題是什麼？**
A：程式碼驅動影片生成的核心問題在於「程式成功執行」與「影片視覺品質正確」之間存在巨大鴻溝。一個渲染程式可以毫無錯誤地退出（exit code 0）並產出有效的 MP4 檔案，但畫面中仍可能出現角色把背包拿在手裡而非背上、3D 攝影機偏離主角、標籤互相重疊、或旁白比圖表慢兩秒等嚴重的感知缺陷。這些「靜默感知缺陷」（silent perceptual bugs）不會觸發任何執行階段錯誤，因此傳統軟體工程仰賴的編譯器錯誤或失敗測試等回饋機制完全無法察覺它們，使得影片創作任務對程式編寫代理而言格外困難。

**Q2：為什麼傳統的程式編寫代理在影片創作任務上會失敗？**
A：傳統程式編寫代理失敗的原因可歸納為三個層面。第一，盲目執行（blind execution）僅檢查退出碼與檔案產出，無法驗證觀眾實際看到的內容是否符合需求。第二，將原始幀與音訊直接灌入代理的長程脈絡（long-horizon context）會造成脈絡預算（context budget）膨脹，每多一次渲染就累積 O(K·Δt·(fτv + τa)) 詞元，嚴重損害長程程式碼維護能力。第三，僅在最後對全解析度渲染進行批評（late critique）來不及挽救早期設計錯誤，迫使代理進行高成本的全專案重寫（full-project rewrite），且無法追蹤跨版本的細部變更。

**Q3：為什麼這個問題在影片創作領域特別重要？**
A：這個問題之所以重要，是因為影片創作對精確度的要求遠高於一般軟體開發。當創作者需要嚴格控制字型排版、忠實的數學或資料圖表、嚴格的多鏡頭連貫性、精確的音視訊同步，或事後進行細部編輯時，像素空間影片生成器（pixel-space video generators）幾乎無法提供所需的精細控制。程式碼驅動方法雖然在控制力上具有優勢，但若無法在產製過程中即時偵測並修正感知缺陷，則其「可編輯專案」（editable project）的承諾將大打折扣——編輯後的程式碼可能引入新的視覺錯誤而無人察覺。

**Q4：VibeVideoAgent 的核心方法是什麼？**
A：VibeVideoAgent 的核心方法是一個「解耦的產製中感知迴路」（decoupled in-production perceptual loop），讓程式編寫代理能在整個產製過程中檢視其草稿，而無需將原始媒體放入自身的脈絡中。系統由兩個關鍵元件組成：暫存式視覺語言模型工作者 Φ（Gemini 3.8 Flash，採用短暫脈絡）負責多模態感知，以及確定性訊號層 Ψ（基於 ffprobe/ffmpeg 的本地探測，無需模型呼叫）負責局部訊號量測。這兩個元件回傳精簡且具體的發現（Findings），包含判定（verdict）、範圍（span）與框（box），讓代理能在輕量、精簡的脈絡中持續獲得接地於時空的回饋。

**Q5：VibeVideoAgent 的關鍵創新點有哪些？**
A：VibeVideoAgent 的關鍵創新包含三個層面。第一是統一的多時鐘草稿表示法（multi-clock draft representation），能以一致方式處理唯讀參考素材、零時長設計靜態圖、置於影片偏移位置的鏡頭預覽，以及完整剪輯，並將每個觀察綁定到其背後的原始程式碼雜湊值。第二是七個基元（primitives）服務於四種角色：由粗到細的探索（describe_media、locate_event、inspect_segment、transcribe_speech）、引用需求驗證（check_requirement）、跨時鐘比較（compare_media）、以及無需 API 呼叫的本地訊號探測（probe_media）。第三是輕量級分階段協議（staged protocol），透過 plan_production 將引用約束連結到有序的製作拍點，並要求代理先在最小預覽（minimal preview）上測試風險最高的決策，再進入組裝、修訂與定稿階段。

**Q6：為什麼採用「解耦」的感知架構而非端到端設計？**
A：採用解耦架構而非端到端設計是因為影片創作任務的特殊性——產製過程涉及參考影片、設計靜態圖、部分鏡頭預覽與多版粗剪，這些資產隨每次編輯而變化且存在於多個時鐘上。若將所有原始媒體直接餵入編碼代理的脈絡，不僅會造成脈絡污染（context pollution），還會因為媒體資料量遠大於程式碼而嚴重擠壓長程維護所需的脈絡空間。解耦設計讓密集的音視訊觀察由短暫、獨立的感知呼叫負責，僅回傳精簡的具體發現，使編碼代理的脈絡保持精簡且扁平（|Ct| 維持穩定），這正是 VideoNexus 在固定影片問答任務中已驗證有效的設計原則。

**Q7：VibeVideoBench 基準測試的設計與規模如何？**
A：VibeVideoBench 包含全部 239 個任務，涵蓋異質的渲染管線，包括 3D WebGPU/Canvas 場景、React/Remotion 介面、Cairo 與 Manim 圖形、SVG 遊戲模擬，以及多軌 TTS/FFmpeg 音訊處理。評估採用三個層級的指標：L1 為基礎規格符合度、L2 為評分規程符合度（rubric compliance）、L3 為整體音視訊品質（holistic audiovisual quality）。實驗在 Claude Opus 5.5、Claude Sonnet 5.5 與 GPT-6 Astra 三個程式編寫模型上進行，每個模型都與其原生代理（native agent）進行對比，並固定 Gemini 3.8 Flash 作為感知模型以確保公平比較。

**Q8：VibeVideoAgent 在不同模型上的關鍵實驗結果為何？**
A：在所有 239 個 VibeVideoBench 任務上，VibeVideoAgent 在三個程式編寫模型上皆穩定提升整體音視訊品質（L3）：Claude Opus 5.5 從 4.03 提升至 4.43（同時 L2 評分規程符合度從 98.87% 提升至 99.35%）、GPT-6 Astra 從 4.03 提升至 4.27（並達到 99.51% 的 L1）、Claude Sonnet 5.5 從 3.97 提升至 4.10。最顯著的進步出現在音視訊同步（audio-visual synchronization）面向，最高達 +0.56 的提升，顯示解耦感知迴路對於偵測與修正時間對齊錯誤特別有效。所有實驗均在匹配的代理執行時間（matched agent runtimes）下進行，確保效能提升並非來自於更多的計算資源。

**Q9：消融實驗揭示了哪些元件的貢獻？**
A：控制消融實驗（controlled ablations）顯示系統中的每個元件都有實質貢獻，移除任一部分都會導致效能下降。軌跡稽核（trajectory audits）進一步揭示了程式碼編輯的粒度（granularity of code edits）會調控評分規程遵循度（L2）與感知品質（L3）之間的取捨——過於頻繁的驗證或過於粗糙的編輯都會破壞兩者間的平衡。這項發現為未來系統調校提供了具體指引：驗證頻率與編輯粒度需根據任務特性進行權衡，而非採用單一固定策略。

**Q10：VibeVideoAgent 適用於哪些實際創作場景？**
A：VibeVideoAgent 適用於所有需要精確控制的影片創作場景，包括 2D 音視訊動態設計（2D audiovisual motion design）與 4D 電影預視化（4D cinematic previsualization）。具體應用包含教學影片中的數學動畫（透過 Manim）、資料視覺化報告（透過 Cairo 或自訂圖表）、多鏡頭敘事短片（透過 React/Remotion）、3D 場景預覽（透過 Blender Python 或 WebGPU）、以及需要嚴格音視訊同步的旁白解說影片。由於七個基元運作於標準的影像、音訊與影片容器之上，無需為特定渲染引擎撰寫適配器，因此同一套系統能橫跨異質管線運作。

**Q11：在產品化部署時需要考量哪些因素？**
A：產品化部署時需考量幾項關鍵因素。首先是感知模型的選擇與成本——系統固定使用 Gemini 3.8 Flash 作為感知模型，雖然屬於輕量級模型，但每次感知呼叫仍會產生 API 成本與延遲，需評估在大量任務下的總體開銷。其次是與現有代理 CLI 的整合——系統透過 Model Context Protocol（MCP）暴露給 Claude Code 與 Codex CLI，這代表部署時需確保目標環境支援 MCP 標準。此外，確定性訊號層（ffprobe/ffmpeg）需要在執行環境中預先安裝，且對於不同編解碼器的相容性需進行測試。最後，雖然系統無需訓練，但針對特定領域（如醫學影像、工業模擬）的精細調整仍可能需要領域專屬的驗證規則。

**Q12：這項研究對程式碼驅動生成領域的影響為何？**
A：這項研究對程式碼驅動生成領域的影響在於重新定義了「代理 + 程式碼」範式中的回饋機制。過去的視覺程式設計（visual programming）研究著重於讓語言模型組合視覺模組，而 MoVer 等工作則驗證動態圖形是否符合邏輯規格；VibeVideoAgent 則將感知驗證從「事後檢查」推進到「產製中即時回饋」，並證明了多時鐘表示法能有效處理創作過程中版本不斷演進的草稿。這種「解耦感知、接地回饋」的設計原則可望推廣至其他需要精確控制的程式碼驅動任務，例如互動式網頁生成、遊戲關卡設計與模擬軟體開發。

**Q13：論文承認的限制有哪些？**
A：論文承認的限制主要在於感知模型本身的固有能力邊界。雖然 Gemini 3.8 Flash 作為固定感知模型足以處理大多數任務，但對於極度細微的視覺缺陷（如特定字型渲染瑕疵、複雜 3D 物理模擬的細節）或需要專業領域知識的判斷（如醫學影像的解剖學正確性），通用 VLM 可能仍有不足。此外，雖然系統在 239 個任務上展現穩定提升，但對於極長篇影片（數十分鐘以上）或極高解析度（8K 以上）的場景，感知呼叫的成本與精確度平衡仍待驗證。最後，軌跡稽核顯示 L2 與 L3 之間存在取捨，這暗示單一固定配置無法同時最優化所有面向。

**Q14：在哪些情況下 VibeVideoAgent 可能會失敗？**
A：VibeVideoAgent 可能失敗的情境包括：當引用需求極為模糊或主觀時（例如「美觀的轉場」），check_requirement 基元難以產出明確的通過/未通過判定；當感知模型對特定文化、語言或專業領域素材缺乏足夠訓練時，transcribe_speech 或 describe_media 可能產生誤判；當創作任務涉及高度風格化或抽象的視覺效果時，VLM 的評分可能與人類觀感不一致。此外，若代理在 plan_production 階段就錯誤地拆解了製作拍點，後續所有階段的驗證都將建立在錯誤的基礎上——這凸顯了上游規劃品質對整體系統表現的重要性。

**Q15：未來的研究方向有哪些？**
A：未來研究方向可從幾個維度展開。第一，擴展多時鐘表示法以涵蓋更多類型的創作資產，例如即時互動內容、虛擬實境場景或生成式音樂。第二，發展領域專屬的驗證規則集，將通用 VLM 與可程式化的確定性檢查器結合，以處理醫學、工程等專業領域的嚴格標準。第三，探討自適應的驗證頻率與編輯粒度策略，根據任務風險動態調整感知呼叫的時機，以更精細地調控 L2 與 L3 的取捨。第四，將此解耦感知迴路原則推廣至其他程式碼驅動任務，例如網頁設計、遊戲開發與資料儀表板生成，建立更廣泛的「程式碼 + 接地感知」創作範式。

## 實務應用指南

### 適用場景

1. **教育內容自動化產製**：教師或教學設計師輸入自然語言簡述（例如「解釋微積分基本定理，搭配逐步動畫與旁白」），由 VibeVideoAgent 透過 Manim 程式碼生成可編輯的數學教學影片，並在每個拍點驗證公式排版、圖表位置與旁白時序，避免學生看到錯誤的數學符號或對不上的解說。

2. **企業財報與資料視覺化影片**：資料分析團隊將季度財報、儀表板截圖與腳本交給代理，代理以 React/Remotion 或 Cairo 撰寫動態圖表影片，自動核對 KPI 數字、標籤是否被遮擋、攝影機是否對準重點指標，並在最終輸出前以 ffprobe 確認音訊音量與無凍結幀。

3. **行銷短影片與社群內容**：品牌團隊提供產品圖、Logo、腳本與參考風格影片，代理以 HTML/Canvas 或 SVG 遊戲引擎生成多鏡頭短影片，自動比對草稿與參考素材的時鐘差異，確保品牌字型、配色與節奏一致，並在多語旁白時驗證音視訊同步。

4. **電影與遊戲預視化（Previsualization）**：導演或遊戲設計師以 Blender Python 撰寫 3D 預視化鏡頭，代理在最小預覽階段先測試最危險的攝影機曲線，再進入組裝、修訂、定稿流程，避免主角被遮擋或鏡頭偏離主體的「靜默感知缺陷」。

5. **無障礙與多模態敘事內容**：新聞媒體或公益組織輸入長篇報導文字與圖片，代理以 FFmpeg 音訊管線合成 TTS 旁白與字幕動畫，自動轉錄語音、檢查字幕時序、量測靜音區段，產出符合無障礙規範的影片。

### 實作前置條件

**資料準備**
- 領域任務集：建議先蒐集 50–200 個具備「自然語言簡述＋參考素材＋評分規程」的影片任務，作為內部基準（可參考 VibeVideoBench 的 239 題結構）。
- 參考素材庫：包含字型、Logo、配色規範、參考影片、設計靜態圖、旁白音檔等，並為每項素材建立雜湊以便多時鐘綁定。
- 評分規程檔：將每個任務拆解為可逐條驗證的需求條目（rubric items），標註所需模態（視覺／音訊／兩者皆需）。

**運算資源**
- 程式編寫代理：以 Claude Opus 5.5、Claude Sonnet 5.5 或 GPT-6 Astra 等長脈絡代理為骨幹，建議部署於具備 200K+ 脈絡的版本。
- 感知模型：固定使用 Gemini 3.8 Flash（或同級 VLM）作為無狀態感知工作者，採短生命週期呼叫以避免污染主脈絡。
- 確定性訊號層：本地安裝 ffprobe／ffmpeg，用於解碼、響度、靜音、凍結幀、循環接縫等零模型呼叫的探測。
- 渲染環境：依任務預裝 HTML/Canvas、React/Remotion、Cairo、Manim、FFmpeg、Blender Python 等執行環境。

**技能門檻**
- 熟悉 MCP（Model Context Protocol）以將七個基元掛載到 Claude Code 或 Codex CLI。
- 具備影片容器、影格取樣、音訊波形與時序對齊的基本知識。
- 能撰寫評分規程並設計「引用需求 → 證據覆蓋」的驗證邏輯。
- 具備代理軌跡日誌（trajectory telemetry）分析能力，以便調整編輯粒度。

### 實作步驟建議

1. **建立多時鐘素材表示層**
   - 為每項素材與草稿建立統一的多時鐘結構，區分唯讀參考素材、零時長設計靜態圖、偏移放置的鏡頭預覽與完整剪輯。
   - 將每筆觀察綁定到產生該草稿的源碼雜湊，確保後續可追溯到具體程式碼版本。

2. **實作七個感知基元**
   - **由粗到細探索**：`describe_media`（整體描述）、`locate_event`（事件定位）、`inspect_segment`（片段細檢）、`transcribe_speech`（語音轉文字）。
   - **需求驗證**：`check_requirement`，引用簡述中的需求條目，回傳包含判定、範圍、框的具體發現，並以確定性檢查確保證據涵蓋所有所需模態。
   - **跨版本比較**：`compare_media`，在兩個獨立時鐘上比對參考素材與草稿，或比對修訂前後版本。
   - **局部訊號探測**：`probe_media`，呼叫 ffprobe／ffmpeg 進行解碼、響度、靜音、凍結幀、循環接縫量測。

3. **設計分階段協議（plan_production）**
   - 階段一 **預覽**：先以最小切片測試風險最高的決策（例如攝影機曲線、字型排版、旁白時序）。
   - 階段二 **組裝**：將通過預覽的元件組合成粗剪。
   - 階段三 **修訂**：以雙時鐘差異比較確認修補效果，避免鄰近鏡頭產生回歸。
   - 階段四 **定稿**：執行訊號探測與規格驗證，輸出最終影片與可編輯專案。

4. **透過 MCP 對接代理 CLI**
   - 將七個基元封裝為 MCP 工具，掛載至 Claude Code 與 Codex CLI。
   - 設定代理只接收精簡發現（Findings），禁止原始影格與音訊進入主脈絡 `Ct`，維持 `|ft| ≪ |E(Mt, σt)|`。

5. **建立評估與軌跡監控**
   - 採用三層指標：L1（基本規格）、L2（評分規程符合度）、L3（整體音視訊品質）。
   - 記錄每次代理呼叫的程式碼編輯粒度、驗證頻率與 Findings 內容，進行軌跡稽核以調整編輯粒度與驗證頻率的取捨。

6. **迭代調校**
   - 依據消融實驗結果調整各元件權重，例如提高 `check_requirement` 的呼叫密度可提升 L2，但需注意避免過度驗證拖慢執行時間。
   - 觀察音視訊同步指標（最高可達 +0.56）以驗證雙時鐘差異比較的效益。

### 潛在風險與注意事項

- **靜默感知缺陷未根除**：即使採用 VibeVideoAgent，仍可能在「通過預覽但組裝後失效」的場景中遺漏問題。緩解方式：保留階段三的雙時鐘差異比較，並對鄰近鏡頭做回歸檢查。
- **脈絡污染風險**：若代理繞過 MCP 直接讀取原始媒體，將使 `Ct` 膨脹並破壞長程維護性。緩解方式：在代理系統提示中明確禁止，並於軌跡稽核中偵測違規。
- **編輯粒度取捨**：過細的編輯會提升 L2 但可能拖累 L3（感知品質），過粗的編輯則易引入回歸。緩解方式：以軌跡日誌分析編輯粒度與指標的相關性，設定每鏡頭編輯次數上限。
- **感知模型偏誤**：固定使用 Gemini 3.8 Flash 雖利於比較，但若該模型在特定領域（如中文排版、樂理圖表）表現不佳，將拖累整體品質。緩解方式：保留可替換感知模型的介面，並針對弱項領域加入領域專用探測。
- **多時鐘對齊錯誤**：參考素材與草稿若時鐘定義不一致，`compare_media` 可能誤判。緩解方式：在素材入庫時強制要求時鐘元資料，並於基元內部做時鐘正規化。
- **執行時間成本**：雖然論文強調「匹配的代理執行時間」，但增加感知呼叫仍可能延長整體流程。緩解方式：將 `probe_media`（零模型呼叫）優先用於廉價檢查，僅在需要視覺理解時才呼叫 VLM。
- **基準外任務的泛化**：VibeVideoBench 的 239 題涵蓋特定領域，遷移到全新領域（如醫學手術模擬）時可能需要重新校準評分規程與感知基元的提示詞。

### 與其他技術的整合建議

- **與像素空間影片生成器整合**：可將 Sora、Veo 等像素空間模型作為「素材提供者」，由 VibeVideoAgent 負責組裝、字幕、旁白與多鏡頭連貫性，發揮兩者互補優勢。
- **與版本控制系統整合**：將每個草稿的源碼雜湊與 Findings 綁定至 Git 提交紀錄，使審稿者能直接從影片問題跳轉到對應的程式碼版本。
- **與 CI/CD 整合**：在影片產製管線中加入「感知檢查關卡」，例如 PR 合併前自動執行 `probe_media` 與 `check_requirement`，將 L2 符合度設為合併條件。
- **與 DAM（Digital Asset Management）整合**：將多時鐘素材表示層與企業 DAM 對接，使代理能直接讀取已標註的 Logo、字型、品牌指南。
- **與無障礙工具整合**：將 `transcribe_speech` 與字幕規範檢查器串接，自動產生符合 WCAG 的字幕軌跡。
- **與代理監控平台整合**：將軌跡日誌匯入 LangSmith、Langfuse 或自建監控系統，追蹤編輯粒度、驗證頻率與指標走勢。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的圖 1，理解「盲目執行」與「解耦的產製中感知迴路」的對比；接著跳過技術細節，直接看「適用場景」與「實作步驟建議」建立直覺，最後回頭讀第 2 節相關工作以掌握領域脈絡。重點是記住核心觀念：影片創作的錯誤不會以執行階段錯誤呈現，因此需要獨立的感知層。

**給 AI 工程師**：聚焦於第 1 節後半的七個基元與多時鐘表示層，理解 MCP 整合方式與「精簡發現」的設計哲學；接著仔細閱讀「實作步驟建議」中的階段劃分與編輯粒度取捨，並參考消融實驗結果調整自家管線。建議在自己的代理框架中先實作 `probe_media` 與 `check_requirement` 兩個最關鍵的基元，再逐步擴展。

**給研究者**：第 1 節的「多時鐘表示法」與「雙時鐘差異比較」是值得深挖的理論貢獻，建議延伸思考其在影片問答（VideoQA）、影片編輯基準測試等場景的應用；軌跡稽核與編輯粒度的取捨分析則可作為「代理自我修正」研究的實證依據。建議與 VideoNexus 等「感知外置」文獻並讀，並探索將此框架應用於 3D 點雲或科學視覺化等非影片領域的可能性。

**給產品經理**：重點關注三層指標（L1/L2/L3）的商業意涵——L2 對應「是否符合客戶需求條目」，L3 對應「客戶實際觀看體驗」，兩者需平衡；音視訊同步最高 +0.56 的提升對教學、品牌內容尤為關鍵。建議將「編輯粒度」與「驗證頻率」視為可調控的成本／品質旋鈕，並在產品路線圖中預留軌跡分析儀表板，以便持續優化代理行為。
