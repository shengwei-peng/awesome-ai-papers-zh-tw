# PreciseCoder：超越單元測試獎勵、實現忠實且可泛化的除錯

## ⚡ TL;DR

僅以單元測試為獎勵的強化學習會導致程式碼模型過度編輯並在正確程式碼中幻覺錯誤。
本文提出PreciseCoder，將語意驗證的編輯精確度與召回率結合成F1獎勵。
該方法將平均編輯行數從7-15降至3，並透過推理軌跡使前沿模型編輯精確度提升4.6-12.4點。

## 摘要翻譯

從單元測試進行強化學習 (RL) 是後訓練程式碼模型的常見做法，但單元測試僅判斷最終程式是否通過。我們分析了這種僅單元測試獎勵在除錯過程中教導模型什麼，並發現雖然它提高了通過率，但也教導模型進行更多編輯，並在已經正確的程式碼中產生幻覺錯誤。我們引入了 PreciseCoder，這是一種訓練演算法，透過一個針對語意驗證之局部化編輯的信號來增強單元測試獎勵，該信號與更小的編輯和更高的通過率相關。在 4B、9B 和 27B 模型上，PreciseCoder 將平均編輯行數從 7-15 減少到 3，通過率與僅使用單元測試獎勵的訓練相當。僅在單行錯誤上訓練，PreciseCoder 便能泛化到儲存庫層級程式修復，在此任務中以更小的補丁解決更多議題。其精確度也可從較弱模型遷移到較強模型：給定 9B PreciseCoder 模型的推理軌跡，GPT-5.6 Sol 和 Qwen3.8-Max 等前沿模型在無需額外訓練的情況下，編輯精確度提升 4.6-12.4 點。對思考軌跡的語言學分析顯示，我們的獎勵鼓勵模型逐行推理、指出錯誤行，並形成一致的錯誤假設。

### 核心貢獻（3～5點）
- 揭示僅單元測試獎勵的副作用：雖然能提高通過率，卻會導致過度編輯與幻覺錯誤。
- 提出 PreciseCoder 訓練演算法：以語意驗證之局部化編輯信號增強單元測試獎勵，將平均編輯行數從 7-15 降至 3，同時維持通過率。
- 展示優異的泛化能力：僅在單行錯誤上訓練，即可遷移至儲存庫層級程式修復，以更小補丁解決更多議題。
- 實現弱到強模型的精確度遷移：9B PreciseCoder 的推理軌跡可使 GPT-5.6 Sol 與 Qwen3.8-Max 等前沿模型的編輯精確度提升 4.6-12.4 點，無需額外訓練。
- 透過思考軌跡的語言學分析，證明該獎勵機制鼓勵模型逐行推理、識別錯誤行並形成一致的錯誤假設。

### 適合對象
從事大型語言模型後訓練、自動化程式修復、強化學習獎勵設計，以及程式碼生成與除錯領域研究的研究者與工程師；亦適合關注 AI 程式設計代理可靠性與可解釋性的業界實務人員。

## 深度分析

#### 方法論解析

PreciseCoder 的核心洞見在於重新審視「僅單元測試獎勵」（unit-test-only reward）作為程式碼模型後訓練（post-training）訊號的根本缺陷。論文首先進行了一項極具啟發性的診斷性研究（diagnostic audit）：透過追蹤 GRPO（群組相對策略最佳化，Group Relative Policy Optimization）訓練 rollout（策略展開）過程中的編輯統計（edit statistics），發現僅以單元測試通過與否作為獎勵時，雖然能提升通過率（pass rate），但模型會傾向於編輯更多行，且在面對本來就正確的程式碼時產生「幻覺錯誤」（hallucinated bug）——即無中生有地修改無誤的程式。

**獎勵函式的設計**

PreciseCoder 的關鍵創新在於將獎勵函式從二元通過/失敗擴展為結合語意驗證（semantic verification）的編輯精確度與召回率的 F1 分數。具體而言：

1. **編輯精確度（Edit Precision）**：衡量模型修改的行中，有多少比例是真正必要的修改。這需要語意驗證——不僅是字面比對，而是判斷修改前後的程式語意是否等價（semantic equivalence），從而識別出「偽修改」（表面改變但語意不變的編輯）。

2. **編輯召回率（Edit Recall）**：衡量所有必要修改中，模型實際捕獲了多少。

3. **F1 組合**：將兩者結合成單一獎勵項，與單元測試獎勵共同構成總獎勵。

論文中特別強調一個關鍵設計選擇：在群組相對最佳化器（group-relative optimizer）內部對兩個獎勵項進行**獨立標準化**（separate normalization）。這避免了單元測試獎勵與 F1 獎勵因量級差異而相互干擾，使得兩個目標能夠被聯合最佳化。

**為何 F1 而非編輯距離**

論文指出，現有方法（如 EA-GRPO、OverEdit）使用編輯距離（edit distance）作為獎勵，但編輯大小與通過率的相關性較弱（weakly correlated），因此最佳化編輯距離會以犧牲通過率為代價換取更小的編輯。F1 獎勵的優勢在於它同時與單元測試結果和編輯大小相關，因此可以同時最佳化兩個目標而不產生權衡（trade-off）。

**訓練資料的設計**

值得注意的是，PreciseCoder 僅在單檔單行錯誤（single-file single-line bugs）上訓練，卻能泛化到多行錯誤、儲存庫層級程式修復（repository-level program repair），以及 SWE-Bench Verified 等複雜基準測試。這種從簡單到複雜的泛化能力是論文的重要貢獻之一。

**代理式除錯（Agentic Debugging）**

論文進一步將 PreciseCoder 擴展到五輪編輯代理（five-turn editing agent）的設定中。在這個設定下，9B 模型達到 67.4% 的編輯精確度與 56.3% 的通過率，成為所有 9B 模型在代理式除錯任務上的最佳表現。

**弱到強遷移（Weaker-to-Stronger Transfer）**

最引人注目的設計是「推理軌跡遷移」（reasoning trace transfer）：將 9B PreciseCoder 模型的推理軌跡（reasoning trace）作為提示提供給前沿模型（frontier model），無需任何權重存取、共享分詞器（tokenizer）或額外訓練，即可使 GPT-5.6 Sol 和 Qwen3.8-Max 等模型的編輯精確度提升 4.6–12.4 點。

#### 實驗數據解讀

**訓練動態分析**

圖 1b 揭示了 GRPO 與 PreciseCoder 在 Qwen3.5-4B 上的訓練動態對比：

- **通過率（左圖）**：兩種方法最終達到相近的通過率水平，說明 PreciseCoder 並未犧牲核心任務效能。
- **編輯行數（中圖）**：當測試通過時，GRPO 平均編輯 7–15 行，而 PreciseCoder 將其壓縮至約 3 行。這是 50–80% 的編輯量減少。
- **無編輯率（右圖）**：在正確程式碼上，GRPO 的「無操作率」（no-edit rate）下降至 19–31%，而 PreciseCoder 維持在 47–52%。這直接證明了 PreciseCoder 抑制了幻覺錯誤。

**跨模型規模的一致性**

實驗涵蓋 Qwen3.5-4B、Qwen3.5-9B 和 Qwen3.6-27B 三個規模，結果顯示：

- 編輯精確度提升 24–29 點（相對於基礎模型）與 26–35 點（相對於僅單元測試 GRPO）。
- 平均編輯大小從 7–15 行降至 3 行。
- 通過率與僅單元測試 GRPO 相當。

這種跨規模的一致性表明 F1 獎勵訊號具有穩健性，不依賴特定模型容量。

**泛化能力評估**

在 PDB-Wild 多行與儲存庫層級錯誤上：

- 4B、9B、27B 模型的精確度分別提升 20、17、20 點。
- 編輯大小縮減 63–71%。

在 SWE-Bench Verified 上，PreciseCoder 解決更多議題（issue resolution）而不膨脹補丁（patch）大小，且破壞已修復儲存庫的情況更少。這項結果特別重要，因為 SWE-Bench Verified 是業界標準的程式修復基準測試。

**語言學分析（Linguistic Analysis）**

論文對思考軌跡（thinking trace）進行語言學分析，揭示了 F1 獎勵鼓勵的具體推理模式：

1. **逐行推理**（reasoning about individual lines）：模型被鼓勵單獨考慮每一行程式碼。
2. **命名錯誤行**（naming the buggy ones）：明確指出哪一行有問題，而非籠統地描述。
3. **形成一致的錯誤假設**（consistent bug hypothesis）：在修改前先建立假設，而非隨機嘗試。

這項分析提供了獎勵塑形（reward shaping）如何影響模型內在推理過程的可解釋性證據。

**弱到強遷移的量化結果**

將 9B PreciseCoder 的推理軌跡提供給五個更強的接收模型，編輯精確度提升 4.6–12.4 點，且這些模型維持自身的通過率。這項結果暗示「精確推理模式」是一種可遷移的技能，不僅限於特定權重。

根據表 1，PreciseCoder 是唯一同時滿足所有七個維度的方法，特別是：

1. **診斷過度編輯與幻覺錯誤**：透過審查（audit）訓練 rollout 揭示問題根源。
2. **位置驗證（location verified）**：F1 獎勵中的精確度與召回率需要語意驗證修改位置。

## 論文問答

**Q1：PreciseCoder 想要解決的核心問題是什麼？**
A：PreciseCoder 針對的是「僅以單元測試作為強化學習獎勵」所衍生的兩個副作用——過度編輯（over-editing）與錯誤幻覺（bug hallucination）。當模型只被告知最終程式是否通過測試時，它會傾向於修改更多行，甚至在原本正確的程式碼中無中生有地「發明」錯誤。論文中以 GPT-5.1-Codex 為例：通過率高達 76%，但其編輯行中僅 40% 是真正必要的，凸顯出單元測試獎勵無法約束編輯行為的問題。

**Q2：為什麼現有的單元測試強化學習方法會失敗？**
A：單元測試只回答「最終程式是否通過」，對於模型究竟改了哪些行、改得是否必要完全不提供監督信號。論文的審查（audit）顯示，隨著 GRPO 訓練推進，通過率上升的同時，編輯行數也增加，且模型對正確程式的不編輯率（no-edit rate）持續下降，代表它學會了「亂改」。這是因為編輯大小與通過率僅有弱相關，僅以通過率作為獎勵無法鼓勵精準修改。

**Q3：為什麼過度編輯在實務上是一個嚴重的問題？**
A：過度編輯會直接放大人工審查的成本——審查者必須逐一檢視每一行被改動的程式碼，而這些成本隨著補丁大小而非錯誤大小線性成長。論文中引用研究指出，即便由程式設計代理（coding agent）合併的拉取請求，仍有 45% 需要人工修訂。更危險的是，多餘的修改可能引入測試套件未涵蓋的行為，造成迴歸（regression）缺陷，使通過測試的補丁實際上破壞了原本正確的功能。

**Q4：PreciseCoder 的核心方法是什麼？**
A：PreciseCoder 在單元測試獎勵之外，再加入一個「語意驗證後的編輯精確度與召回率」，並將兩者結合成 F1 分數作為額外獎勵信號。具體而言，模型必須對其修改的每一行進行語意驗證，確認該行是否真的需要修改，藉此同時獎勵「通過測試」與「精準定位錯誤」。在群組相對策略最佳化（GRPO）內部，這兩個獎勵項會被分開標準化，使兩者可以共同最佳化而不互相干擾。

**Q5：PreciseCoder 相較於先前文獻的關鍵創新為何？**
A：先前方法如 EA-GRPO、OverEdit、PAFT、AdaPatcher、RECAP 等，多半以「編輯距離」或「模仿最小補丁」作為約束，但編輯大小與通過率僅弱相關，最終會犧牲通過率換取較小的補丁。PreciseCoder 的關鍵創新在於使用語意驗證的 F1 分數，該指標同時與通過率及編輯大小高度相關，因此能在不犧牲通過率的前提下大幅提升編輯精確度。此外，它也是首個明確診斷並抑制「錯誤幻覺」現象的工作。

**Q6：在獎勵塑形（reward shaping）上做了哪些設計選擇？**
A：作者選擇將單元測試獎勵與編輯 F1 獎勵分開標準化後再加總，避免任一項主導梯度方向。F1 獎勵採用語意等價（semantic equivalence）驗證，而非單純的字面比對，以避免模型為了字面相似而錯失真正必要的修改。此外，訓練資料刻意只使用單行錯誤（single-line bug），刻意測試模型是否能將學到的精準編輯行為泛化到多行與儲存庫層級的程式修復任務。

**Q7：實驗使用了哪些基準測試（benchmark）？**
A：訓練階段使用單檔單行錯誤資料；評估階段涵蓋 PDB-Wild 的多行與儲存庫層級錯誤，以及 SWE-Bench Verified 這個業界標準的儲存庫級程式修復基準。此外還包含 PDB 資料集以衡量「在正確程式上不編輯」的能力，並設計了代理式（agentic）RL 評估，模擬五輪編輯代理的工作流程，以測試模型在多輪互動下的精準度。

**Q8：最重要的實驗結果為何？**
A：在 Qwen3.5-4B、Qwen3.5-9B 與 Qwen3.6-27B 三種規模的模型上，PreciseCoder 將編輯精確度相較基礎模型提升 24–29 點，相較僅用單元測試的 GRPO 提升 26–35 點；平均編輯行數從 7–15 行降至約 3 行，且通過率與僅用單元測試的 GRPO 持平。在正確程式輸入上，不編輯率從基礎模型的 31–37% 提升至 47–52%，證明錯誤幻覺被有效抑制。

**Q9：有哪些消融實驗（ablation study）支持其設計？**
A：作者對獎勵項進行了相關性分析，證明 F1 分數同時與通過率及編輯大小高度相關，而單元測試獎勵僅與通過率相關、與編輯大小幾乎無關，從而支持將兩者結合的必要性。此外，語言學分析顯示，僅有 PreciseCoder 的獎勵會促使模型在思考軌跡中「逐行推理」、「指出錯誤行」並「形成一致的錯誤假設」，說明 F1 獎勵對模型內部推理過程產生具體可觀察的影響。

**Q10：PreciseCoder 適用於哪些實務情境？**
A：在企業內部程式碼審查流程中，精準的補丁能大幅縮短審查時間，因為審查者只需關注真正必要的修改行。在大型開源專案的維護上，儲存庫層級的程式修復任務（如 SWE-Bench Verified）能受益於更小的補丁，降低引入迴歸的風險。此外，對於已正確的程式碼，模型傾向「不動」的特性使其更適合作為程式碼助手，避免在自動補完或重構時無端修改原本正確的邏輯。

**Q11：將 PreciseCoder 整合到產品中需要考量哪些因素？**
A：首先，語意驗證需要執行測試或靜態分析，這會帶來額外的推論（inference）成本與延遲，產品設計上需要在精準度與回應速度間取捨。其次，F1 獎勵依賴於「參考補丁」來判定編輯是否必要，這在真實開發流程中往往不存在，需要設計替代方案（如以測試覆蓋率或靜態分析器作為代理指標）。最後，模型遷移（model transfer）特性意味著即使是無法微調的前沿模型，也能透過讀取 9B PreciseCoder 的推理軌跡來提升精準度，這為產品提供了「以小模型引導大模型」的實用部署策略。

**Q12：這項研究對程式碼 LLM 領域的更廣泛影響是什麼？**
A：這項工作挑戰了「單元測試即足夠獎勵」的傳統假設，示範了獎勵設計必須同時考慮「正確性」與「精準性」兩個維度。它也為「弱到強模型遷移」提供了新範例——透過推理軌跡而非權重遷移，使得小模型的精準行為能傳遞給無法訓練的前沿模型如 GPT-5.6 Sol 與 Qwen3.8-Max，使其編輯精確度提升 4.6–12.4 點。這種「以推理模式作為遷移媒介」的思路，可能會影響未來程式碼 LLM 的後訓練方法設計。

**Q13：論文中承認的限制有哪些？**
A：作者明確指出 F1 獎勵依賴於「參考補丁」的存在，這在真實世界除錯情境中並不總是可得。此外，語意驗證的計算成本會隨著程式碼規模上升，特別是在儲存庫層級任務中，驗證所有編輯行的語意正確性可能成為瓶頸。訓練資料僅涵蓋單行錯誤，雖然展示了良好的泛化能力，但對於極端複雜的多檔跨模組錯誤，模型的表現仍可能受限。

**Q14：PreciseCoder 在哪些情境下可能會失敗？**
A：當錯誤並非以「行」為單位存在時（例如涉及跨行邏輯、狀態機或並行程式碼的錯誤），F1 獎勵的「逐行驗證」假設可能無法正確反映真實的修改需求。在缺乏參考補丁或測試覆蓋不足的情境下，語意驗證本身可能不可靠，導致獎勵信號失真。此外，若模型面對的是全新領域的程式語言或框架，訓練時學到的「精準推理」模式可能無法直接套用，仍需要領域適應。

**Q15：未來的研究方向有哪些？**
A：未來可探索無需參考補丁的獎勵機制，例如以測試覆蓋率變化、靜態分析警告或程式碼語意嵌入距離作為代理指標。另一個方向是將「推理軌跡遷移」的形式化，研究哪些特徵（如指出錯誤行、形成假設、權衡編輯）對於弱到強遷移最為關鍵，以設計更高效的引導提示。此外，也可將 PreciseCoder 的獎勵設計擴展到其他程式碼任務，如重構、測試生成或漏洞修復，探討「精準性」原則的普適性。

## 實務應用指南

### 適用場景

1. **IDE 程式碼助手外掛（VS Code、JetBrains 等）**：當開發者提交一段壞掉的函式時，外掛可即時呼叫 PreciseCoder 產生最小化補丁。相較於只追求通過率的模型，PreciseCoder 平均只改動 3 行，能直接以「diff 預覽」形式呈現，開發者只需 review 真正必要的變更，大幅降低審查疲勞。

2. **CI/CD Pipeline 中的自動化程式修復機器人**：在 pull request 階段自動偵測失敗的單元測試並提出修補建議。論文顯示在 SWE-Bench Verified 上能解決更多議題且不擴大補丁範圍，特別適合需要嚴格控制變更範圍的金融、電信等受監管產業。

3. **程式設計代理（Coding Agent）的除錯模組**：以 5 輪編輯代理形式整合進長任務代理（如 SWE-Bench 風格的 agent），讓代理在多步驟除錯中保持精準。論文報告 9B 模型在代理式除錯中達到 67.4% 編輯精確度與 56.3% 通過率，是 9B 等級中兩項指標的最佳組合。

4. **大型 monorepo 的維護與錯誤修復**：對於擁有數萬檔案的程式碼庫，過度編輯會引發大量迴歸風險。PreciseCoder 在「正確程式碼」上的 no-edit 率從 31–37% 提升至 47–52%，代表它能避免在已經正確的程式碼上幻覺出錯誤，特別適合需要高穩定性的遺留系統維護。

5. **跨模型協作除錯工作流**：將 9B PreciseCoder 的推理軌跡（reasoning trace）作為提示注入到 GPT-5.6 Sol、Qwen3.8-Max 等前沿模型，無需任何訓練或權重存取即可提升 4.6–12.4 點的編輯精確度。適合企業內部以小模型產生「精準除錯草稿」、再由強模型做最後驗證的兩階段流程。

### 實作前置條件

**資料需求**
- 訓練資料：建議以 PDB（Program Database Benchmark）的單行錯誤子集作為起點，論文證明僅在單行錯誤上訓練即可泛化到儲存庫層級。
- 評估資料：PDB-Wild（多行與儲存庫層級）、SWE-Bench Verified，以及自有的單元測試套件。
- 語意驗證工具：需要能判斷「編輯是否語意正確」的執行環境（沙箱、容器化測試執行器），用於計算編輯的 precision/recall/F1。

**運算資源**
- 模型規模：4B、9B、27B 參數量級的程式碼模型（論文使用 Qwen3.5 系列）。
- 訓練框架：需支援 GRPO（Group Relative Policy Optimization）的 RL 框架，例如 verl、TRL、或自建實作。
- 推論資源：每個訓練步驟需要對每個 prompt 採樣多個 rollout（GRPO 的群組相對比較需要），建議配備多 GPU 叢集（4B 模型至少 8×A100，27B 模型需要 32+ GPU）。

**技能門檻**
- 熟悉 RL 後訓練流程（rollout、reward shaping、policy gradient）。
- 具備程式碼分析能力，能實作語意等價檢查與 diff 比對工具。
- 了解程式碼模型評估指標（pass@k、edit precision、edit recall、F1）。
- 具備分散式訓練除錯經驗。

### 實作步驟建議

1. **建立獎勵函數管線**
   - 單元測試獎勵：執行候選補丁的測試套件，給予二元獎勵（通過/未通過）。
   - 編輯 F1 獎勵：以語意驗證（執行測試或抽象語意比對）判定每個編輯是否「必要」，計算 precision 與 recall，組合成 F1。
   - 群組相對正規化：在 GRPO 內部對兩個獎勵項分別做組內正規化，避免尺度差異干擾策略更新。

2. **準備訓練資料**
   - 從 PDB 抽取單行錯誤實例，確保每個實例都有可執行的單元測試。
   - 為每個錯誤實例產生「黃金補丁」（gold patch），用於計算編輯 precision/recall 的 ground truth。
   - 切分訓練/驗證集，特別保留一部分「正確程式碼」用於監測 bug hallucination 指標（no-edit rate）。

3. **啟動 GRPO 訓練**
   - 初始化策略模型（Qwen3.5-4B/9B 或 Qwen3.6-27B）。
   - 每個 prompt 採樣 G 個 rollout（論文未明確指定 G，建議 8–16）。
   - 計算組合獎勵：`R = α · R_unit_test + β · R_edit_F1`，α 與 β 需在驗證集上調整。
   - 監控三個關鍵指標：pass rate、edit lines、no-edit rate on correct code。

4. **評估與迭代**
   - 在 PDB-Wild 與 SWE-Bench Verified 上測試泛化能力。
   - 若 pass rate 下降，調高 α；若 edit size 仍過大，調高 β。
   - 進行語言學分析：抽取思考軌跡，檢查模型是否「指出錯誤行」、「形成錯誤假設」、「權衡每個編輯」。

5. **部署與整合**
   - 將訓練好的模型封裝為 API 服務。
   - 對接 IDE 外掛、CI/CD 鉤子、或代理框架。
   - 開啟「推理軌跡輸出」選項，供前端展示或供強模型二次驗證。

6. **（進階）跨模型遷移**
   - 將 PreciseCoder-9B 的推理軌跡整理成 few-shot 範例。
   - 注入到 GPT-5.6 Sol、Qwen3.8-Max 等強模型的 prompt 中。
   - 評估強模型的編輯精確度提升幅度，預期可達 4.6–12.4 點。

### 潛在風險與注意事項

- **獎勵權衡失衡**：F1 獎勵權重過高可能導致模型傾向「不編輯」以換取 precision，但 pass rate 會下降。建議維持 pass rate 與 baseline 相當（論文強調「on par」），僅以 F1 抑制過度編輯。
- **語意驗證成本**：每個 rollout 都需要執行測試或語意檢查，計算開銷是純單元測試獎勵的數倍。建議使用容器化沙箱與平行化執行，並快取重複測試結果。
- **訓練資料偏差**：若訓練資料偏向特定語言或框架，泛化能力可能受限。論文在單行錯誤上訓練即泛化到儲存庫層級是強烈證據，但仍建議在目標領域資料上做輕量微調。
- **Bug Hallucination 監控**：即使訓練資料中沒有正確程式碼，模型仍可能學會「不亂改」。建議在驗證集中保留 20–30% 的正確程式碼，持續監控 no-edit rate。
- **代理式部署的狀態管理**：5 輪編輯代理需要正確的狀態傳遞（每輪的程式碼版本、測試結果），實作不慎會導致代理在錯誤的程式碼基礎上繼續編輯。
- **跨模型遷移的相容性**：推理軌跡中的程式碼片段可能使用與強模型不同的風格或 API，需做格式正規化以避免強模型誤解。

### 與其他技術的整合建議

- **與 GRPO 變體整合**：可與 EA-GRPO（編輯距離懲罰）、RECAP（最小補丁模仿）等方法結合，但需注意獎勵項之間的冗餘與衝突。建議先以 PreciseCoder 的 F1 為主，其餘作為輔助。
- **與程式碼審查工具整合**：將 PreciseCoder 輸出與 SonarQube、CodeQL 等靜態分析工具結合，靜態分析標記「可疑行」，PreciseCoder 專注於「必要行」，兩者互補。
- **與 RAG 系統整合**：在產生補丁前，先以 RAG 檢索相似錯誤的歷史修補模式，提供給模型作為參考，可進一步提升 precision。
- **與測試生成工具整合**：若單元測試不足，可先用 LLM 產生測試，再以 PreciseCoder 除錯，形成「測試-除錯」閉環。
- **與版本控制整合**：以 Git hook 形式觸發，在 commit 前自動檢查是否有「不必要的編輯」，作為守門員（gatekeeper）。
- **與監控系統整合**：將 edit precision、no-edit rate 等指標納入模型效能儀表板，持續追蹤部署後的表現漂移。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節的「問題動機」與 Figure 1，直觀理解「過度編輯」與「bug hallucination」是什麼問題。接著看第 3 節的獎勵設計，理解「為什麼 F1 比編輯距離好」。不需要深入數學推導，重點是掌握「精準比貪婪更重要」這個核心觀念。

**給 AI 工程師**：重點閱讀第 3 節的訓練演算法細節、第 4 節的實驗設定（特別是獎勵權重與群組相對正規化），以及第 5 節的代理式 RL 實作。注意論文中 GRPO 的兩個獎勵項是「分別正規化」而非「線性相加」，這是訓練穩定的關鍵。可直接參考論文的程式碼倉庫（Webpage 與 Code 連結）進行復現。

**給研究者**：第 2 節的相關工作分類（Table 1）提供了清晰的定位地圖；第 5 節的語言學分析是值得深挖的方向——「推理軌跡中的哪些語言特徵對應到編輯精確度」。此外，「弱到強遷移」現象（無需訓練即可提升前沿模型）是個有趣的研究問題，建議探索軌跡中具體哪些元素（指出錯誤行、形成假設、權衡編輯）在遷移中扮演關鍵角色。

**給產品經理**：核心訊息是「通過率高不代表好用」——一個會把正確程式碼改壞的除錯工具，會讓開發者付出更高的審查成本與迴歸風險。PreciseCoder 的價值主張是「在不通過率的前提下，大幅降低編輯範圍」，這對企業的 ROI 計算很重要：審查成本隨編輯行數線性成長，而 bug 修復的價值主要來自正確性而非修補大小。建議在採購或自建除錯工具時，將「編輯精確度」與「no-edit rate on correct code」列為必要評估指標。
