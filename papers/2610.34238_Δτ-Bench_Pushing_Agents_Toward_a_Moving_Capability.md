## 深度分析

#### 方法論解析

**Δτ-Bench 的整體設計理念**

Δτ-Bench 的核心設計在於建構一個「動態能力前沿」（moving capability frontier）的評測環境，用以檢驗 LLM 代理在大型工具生態系（tool ecosystem）持續演進下的適應能力。與既有基準測試將工具結構視為靜態不同，Δτ-Bench 透過「能力保留轉換」（capability-preserving transformation）主動生成六個連續的生態系狀態（ecosystem state），模擬真實企業環境中各部門獨立維護與更新工具的情境。

**任務形式化（Task Formulation）**

作者將代理互動建模為部分可觀察序列決策過程 $M = (U, S, A, O, P, R)$，其中狀態空間 $S = S^E \times S^H$ 結合外部環境狀態與代理—使用者互動狀態，動作空間 $A = A_{tool} \cup A_{resp}$ 同時涵蓋工具呼叫與自然語言回應。此形式化的關鍵在於：使用者意圖 $u \in U$ 對代理不可直接觀察，必須透過多輪對話逐步釐清，這使得任務具備真實的不確定性與互動性。

**基準建構的四階段流程**

1. **任務基礎（Task Foundation）**：定義 42 個領域的服務藍圖（service blueprint），建立實體與關係模型，並實作為有狀態的 MCP（Model Context Protocol）服務，包含可執行函式、資料庫與策略層。

2. **能力轉換（Capability Transformations）**：這是 Δτ-Bench 最具創新性的設計，包含三種基本轉換型態：
   - **介面適配（Adapt Interface）**：重新命名、新增參數或改變格式（如 $f \rightarrow f'$）
   - **功能拆分（Split Function）**：將單一功能拆解為多個協調呼叫（如 $f \rightarrow g_1, g_2$）
   - **工作流合併（Merge Workflow）**：將連續步驟整合為單一介面（如 $f_2, f_3 \rightarrow m$）
   
   每種轉換都通過一致性測試（conformance tests）驗證，確保輸入輸出與狀態效果等價，從而「保留能力」但改變達成路徑。

3. **生態系抽樣（Ecosystem Sampling）**：在每個狀態中抽樣局部變化，包含淘汰工具（retired tools）、新增替代方案（alternative）、保留原始工具或替換介面等組合，並進行驗收檢查確保所有基礎能力仍可達成。

4. **參考路徑搜尋（Reference Path Search）**：針對每個生態系狀態，識別最有效率的任務達成路徑作為評測基準，這使得評估不僅關注「是否完成」，更關注「是否採用最優路徑」。

**Steward 生態系管理器**

Steward 的設計理念在於將「工具」與「程序性知識」（procedural knowledge）視為耦合資源系統（coupled resource system），而非獨立管理。其核心機制包含：

- **技能—工具依賴追蹤**：維護技能庫（skill library）中每項程序性知識與其依賴工具的對應關係，當工具變更時能精準定位受影響的技能。
- **增量式技能維護（Incremental Skill Maintenance）**：當生態系演進時，僅更新受影響的技能而非重建整個技能庫，保留可重用的經驗。
- **動態配置（Dynamic Provisioning）**：在任務執行過程中，根據當前狀態聯合提供相關工具與程序性指引，並隨任務進展調整資源選擇。

此設計的關鍵洞見在於：既有技能學習方法（skill-learning methods）的初始增益無法在生態系演進中持續轉化為更好的適應，因為累積經驗（accumulated experience）會滯後於工具變化，而 Steward 透過耦合管理打破了這種滯後。

#### 實驗數據解讀

**基準規模與覆蓋面**

Δτ-Bench 包含 1,588 個經驗證的多輪任務（multi-turn task），橫跨 42 個領域，並生成六個連續的生態系狀態。這樣的規模在工具使用基準測試中屬於較大規模，且「六個狀態」的設計使得評估能夠追蹤代理在多次演進下的累積表現，而非僅評估單一時間點。

**核心評測結果**

最強的受評模型或評測框架（harness）僅達到 42.3% 的任務成功率（task success），這是一個相當低的數字，揭示了當前 LLM 代理在動態生態系中的根本性弱點。具體而言：

- **42.3% 上限的意涵**：即便是最先進的代理，在面對工具持續演進的情境下，仍有超過半數任務無法可靠完成。這與在靜態基準（如 $\tau$-bench）上常見的 60–80% 成功率形成鮮明對比，凸顯「動態能力前沿」帶來的額外難度。

- **技能學習方法的侷限**：既有技能學習方法雖能帶來初始增益，但這些增益無法在生態系演進中持續轉化為更好的適應。這意味著「學會經驗」與「在變化中保持經驗有效」是兩個不同的能力，而現有方法僅解決前者。

- **技能維護成本**：技能維護本身會產生顯著的負擔（overhead），這暗示了簡單地「重建技能庫」並非可持續的策略。

**Steward 的實驗表現**

Steward 在三個維度展現優勢：

1. **跨生態系變化的穩定性**：在多次狀態轉換中維持較高的任務成功率，顯示其增量式維護機制有效避免了經驗流失。

2. **降低維護成本**：相較於重建式方法，Steward 的增量更新策略減少了不必要的計算與儲存開銷。

3. **雙重效益**：不僅能從中斷的工作流程（disrupted workflow）中復原（recovery），更能主動採用（adoption）新出現的高效替代方案（efficient alternative）。這意味著 Steward 不只是「維持現狀」，而是能「把握機會」。

**消融分析的啟示**

進一步分析顯示：
- 保留並選擇性更新累積知識比反覆重建更有效，驗證了「程序性記憶」（procedural memory）的價值。
- 聯合提供工具與技能所帶來的效益超越任一資源單獨提供的效果，證明了「耦合管理」設計的必要性。

#### 與現有研究的比較

**與既有基準測試的定位差異**

Δτ-Bench 明確區隔於以下三類既有研究：

1. **大規模工具檢索與有狀態執行基準**（如 $\tau$-bench、ToolBench 等）：此類基準假設工具集固定，專注於檢索準確度與多輪執行正確性。Δτ-Bench 則將「工具演進」納入核心變數。

2. **成本感知重規劃研究**（如 Liu et al., 2026e；Valmeekam et al., 2023）：此類研究關注執行過程中的成本變化（如 API 失敗、預算限制），但通常假設工具本身不變。Δτ-Bench 將成本概念延伸至「機會成本」——錯過高效替代方案的隱性損失。

3. **工具演進穩健性研究**（如 Liu et al., 2026c；Chen et al., 2025b）：此類研究探討代理對工具變化的容忍度，但通常限制工具發現的範圍或僅考慮小規模變化。Δτ-Bench 則要求代理在大型生態系中主動發現新路徑。

**相較於既有研究的改進**

- **整合性評測**：既有基準將「工具發現」「有狀態執行」「成本感知」分開評測，Δτ-Bench 首次將這些能力置於同一動態環境中聯合考察。
- **參考路徑機制**：透過搜尋最優路徑作為評測基準，能識別「任務成功但路徑次優」的情況，這是靜態基準無法捕捉的細粒度差異。
- **耦合管理視角**：Steward 提出的「工具—技能耦合」概念超越了既有研究中將兩者獨立處理的典範。

**限制與未涵蓋面向**

- **轉換型態的覆蓋**：目前僅考慮三種基本轉換（介面適配、功能拆分、工作流合併），真實生態系中可能出現更複雜的變化（如語意漂移、跨服務依賴重組）。
- **領域多樣性**：42 個領域雖具規模，但可能無法完全代表所有產業的工具生態特性。
- **演進速度假設**：六個狀態的設計隱含了離散式演進，現實中工具更新可能是連續且非同步的。
- **使用者行為模型**：任務中的使用者行為基於預設劇本，未必能完全模擬真實使用者的多樣性與隨機性。

- **資料集**：於 Hugging Face 公開（`zjunlp/delta-tau-bench`），包含 1,588 個驗證任務與六個生態系狀態的完整配置。

**可重現性的優勢**

1. **確定性建構流程**：四階段建構流程（任務基礎、能力轉換、生態系抽樣、參考路徑搜尋）皆有明確的演算法描述與驗證機制（一致性測試、驗收檢查），第三方可依相同流程重建基準。

2. **MCP 標準化**：採用 Model Context Protocol 作為服務實作基礎，這是一個業界標準化的協議，降低了環境配置的歧異性。

3. **任務驗證機制**：每個任務都經過執行驗證，確保參考路徑確實可達成，這為評測結果的可信度提供了基礎。

**潛在的可重現性挑戰**

- **模型版本敏感性**：實驗結果依賴於特定 LLM 版本（如 GPT-4、Claude 等），這些模型的 API 行為可能隨版本更新而變化，影響結果的可重現性。
- **評測框架差異**：不同評測框架（harness）的實作細節可能影響代理表現，論文中雖評測多種框架，但完整對比所有框架的開銷可能較大。
- **隨機性控制**：生態系抽樣階段可能涉及隨機過程，需確認論文中是否提供固定種子（seed）以確保結果可重現。

**模型權重與訓練細節**

Steward 作為一個生態系管理器，其設計基於既有 LLM 而非訓練新模型，因此不涉及模型權重釋出問題。然而，若 Steward 包含特定的提示工程（prompt engineering）或微調（fine-tuning）策略，這些細節的完整公開將有助於重現其增益。

#### 未來研究方向

**基準擴展方向**

1. **更複雜的轉換型態**：未來可考慮納入語意漂移（semantic drift）、跨服務依賴重組、工具鏈斷裂等更細緻的演進模式，以更貼近真實生態系的動態特性。

2. **連續式演進模擬**：將離散式狀態轉換擴展為連續時間軸上的非同步更新，模擬現實中各部門獨立發布工具更新的情境。

3. **跨領域遷移評測**：探討代理在一個領域學到的程序性知識能否遷移至另一個領域，這將考驗「元技能」（meta-skill）的泛化能力。

**Steward 的延伸研究**

1. **理論基礎強化**：目前 Steward 的設計以經驗驅動為主，未來可從資訊理論或決策理論角度分析「技能—工具耦合」的必要性與最優維護策略。

2. **自動化技能發現**：當前 Steward 仰賴既有技能學習方法產生程序性知識，未來可探索自主發現新技能並評估其與工具生態契合度的機制。

3. **多代理協作情境**：在大型企業中，多個代理可能共享同一生態系，未來可研究 Steward 如何支援代理間的技能共享與衝突解決。

**與其他研究方向的結合**

1. **與持續學習（Continual Learning）結合**：生態系演進本質上是持續學習問題，可借鑑災難性遺忘（catastrophic forgetting）的研究成果來改進技能維護。

2. **與形式化驗證結合**：利用形式化方法驗證轉換後的能力保留性，並對代理行為進行可證明的安全性分析。

3. **與人類反饋強化學習（RLHF）結合**：在生態系演進中，使用者偏好可能隨新工具出現而改變，未來可探索如何將人類反饋整合至 Steward 的決策機制。

**產業應用探索**

1. **真實企業部署案例研究**：與企業合作，在真實的工具生態中部署 Steward，評估其在生產環境中的實用性與經濟效益。

2. **工具生命週期管理**：將 Steward 的設計理念應用於軟體工程領域的工具生命週期管理，建立從開發、部署到淘汰的完整治理框架。

3. **API 經濟下的代理設計**：隨著 API 經濟的成熟，代理將面對更龐大且更動態的服務市場，Δτ-Bench 與 Steward 的設計可為此類代理的設計提供方法論基礎。

**長期願景**

Δτ-Bench 與 Steward 的提出，揭示了一個根本性的研究議題：在能力持續演進的世界中，代理如何維持並提升其競爭力？這不僅是技術問題，更涉及代理設計哲學——從「靜態專家」轉向「動態學習者」，從「獨立執行者」轉向「生態系參與者」。未來研究可進一步探索代理在開放式環境中的自主演化機制，以及人類與代理在動態生態系中的協作模式。

## 論文問答

**Q1：這篇論文要解決的核心問題是什麼？為什麼「動態能力前沿」（moving capability frontier）這個概念對 LLM 代理如此關鍵？**

A：這篇論文要解決的核心問題是：當大型工具生態系持續演進時，LLM 代理能否同時「主動發現高效工具使用路徑」並「及時修正其累積的程序性知識」。在真實場景中，企業各部門會獨立維護與更新自家服務，造成熟悉工具被淘汰、新工具出現、功能重疊與文件雜訊等問題，使得代理過去學到的工作流程可能失效或錯失更高效的替代方案。「動態能力前沿」之所以關鍵，是因為它強調代理的勝任標準並非固定，而是隨著生態系演進不斷移動；若僅以「任務是否成功」來評估，會掩蓋代理其實正在使用次優路徑的問題，因此必須將「能否跟上能力前沿」納入評測。

**Q2：現有的工具使用基準測試（如 ToolBench、τ-bench 等）為何無法捕捉這個挑戰？它們各自只涵蓋了哪些面向？**

A：現有基準測試大致只涵蓋三個獨立面向：其一是大規模工具檢索與有狀態執行（如 ToolBench、τ-bench），但其服務結構通常固定不變；其二是成本感知重規劃（cost-aware replanning），關注執行條件變化下的重新計畫，但對工具發現的限制較嚴；其三是工具演進的穩健性測試，但多半將「發現新工具」與「修正既有程序性知識」分開評估。這些設定都未能同時檢驗「主動發現高效路徑」與「及時更新累積經驗」這兩項需求的耦合，因此無法回答代理在生態系持續變動下能否維持持續勝任能力這個問題。

**Q3：為什麼「任務成功」本身不足以作為代理勝任的指標？論文中所謂「成功掩蓋了錯失機會」的現象具體是什麼意思？**

A：在生態系演進下，代理可能沿用舊有的工作流程仍然把任務完成，但實際上生態系已出現更高效的工具組合或更短的呼叫鏈；此時單看任務成功率會得到「代理表現良好」的假象，卻忽略代理從未探索過這些新機會。論文中以「任務成功可能隱藏錯失的機會」來描述這種現象，並主張必須將代理實際採取的路徑與「當前生態系下最優參考路徑」進行比對，才能揭露這種「表面勝任、實則落後」的落差。這也是 Δτ-Bench 設計「參考路徑搜尋」步驟的核心理由。

**Q4：Δτ-Bench 的整體建構流程包含哪些主要階段？每個階段分別負責什麼？**

A：Δτ-Bench 的建構分為四個階段：(1) 任務基礎建立，定義領域與服務藍圖，並將其實作為有狀態的 MCP 服務，搭配可執行的函式、資料庫與政策；(2) 能力保留轉換（capability-preserving transformations），透過「介面調適」、「功能拆分」、「工作流合併」三種操作產生新的生態系狀態，並以一致性測試確保底層能力等價；(3) 生態系抽樣，從每個狀態中抽樣局部變化（淘汰、替換、新增替代工具、描述偏移等），並通過驗收檢查；(4) 參考路徑搜尋，在每個狀態下找出完成任務的最短路徑作為評測參考，用以衡量代理是否採用了高效解。

**Q5：Steward 這個「生態系管理器」的核心設計理念是什麼？它如何同時管理「工具」與「程序性知識」？**

A：Steward 的核心設計理念是將「工具」與「技能（程序性知識）」視為耦合的資源系統來共同管理，而非讓技能庫獨立於工具演進之外。它透過追蹤「技能—工具依賴關係」，在工具變動時以增量方式維護技能庫，保留可重用的經驗並淘汰失效部分；在任務執行階段，則根據當前情境「動態配置」相關工具與程序性指引，使兩種資源的供給隨任務進程同步調整。這種「聯合管理」避免了傳統做法中技能庫與工具目錄脫鉤所導致的維護成本高昂與適應遲滯問題。

**Q6：Δτ-Bench 中所謂「能力保留轉換」（capability-preserving transformations）包含哪三種操作？為什麼必須保證「能力等價」？**

A：三種操作分別是：(A) 介面調適（adapt interface），例如重新命名、新增參數、改變輸出格式；(B) 功能拆分（split function），將單一工具拆成多個需協調呼叫的工具；(C) 工作流合併（merge workflow），將多個連續步驟整合為單一介面。必須保證「能力等價」是因為 Δτ-Bench 的目的是評測「代理能否跟上能力前沿」，而非「代理能否完成底層本來就做不到的事」；若轉換後能力不等價，則無法區分代理失敗是因為生態系變動還是因為任務本質改變，因此每個新狀態都需通過一致性測試與 MCP 測試，確保輸入輸出與狀態效果一致。

**Q7：Δτ-Bench 的規模與覆蓋面如何？為什麼選用「六個連續生態系狀態」這個設計？**

A：Δτ-Bench 涵蓋 42 個領域、1,588 個經驗證的多輪任務，並由六個連續的生態系狀態組成。選用六個狀態是為了模擬真實世界中工具生態系「逐步演進」的節奏，而非一次性大幅翻修；這種設計讓評測能區分代理在不同變動幅度下的表現——例如在第一、第二次變動後仍可勉強沿用舊經驗，但到了第三、四次變動後累積落差會被放大，從而更細緻地檢驗代理的「持續適應」能力，而非僅看單次變動後的恢復力。

**Q8：實驗中最關鍵的數字結果是什麼？它揭示了哪些現象？**

A：最關鍵的數字是「即使是最強的受測模型或評測框架，任务成功率也只有 42.3%」，這顯示現有代理在動態生態系下的勝任能力遠低於預期。此外，實驗還揭示兩個現象：(1) 現有技能學習方法雖然能帶來初期增益，但這些增益無法在生態系持續演進中穩定轉化為更好的適應表現；(2) 技能維護本身會帶來顯著負擔。相對地，Steward 在生態系變動下能維持更高的任務成功率、降低技能維護成本，並同時改善「從中斷工作流中復原」與「採用更高效替代方案」兩項能力。

**Q9：Steward 的消融實驗或進一步分析揭示了哪些設計選擇的必要性？**

A：進一步分析顯示兩個關鍵設計選擇的必要性：其一，「保留並選擇性更新累積知識」比「反覆從頭重建」更有效，這驗證了增量式技能維護的價值；其二，「聯合提供工具與技能」所帶來的效益是「單獨提供任一資源」都無法達成的，這證明了將工具與程序性知識視為耦合資源進行聯合管理的設計是必要的，而非可拆解的附加功能。這兩項發現共同支持了 Steward 的整體架構，而非僅是其個別元件。

**Q10：在實際企業部署中，Δτ-Bench 所模擬的情境最可能出現在哪些場景？**

A：最典型的場景是大型企業將 LLM 代理作為統一入口對接內部各部門服務時的情境——例如 IT、人力資源、財務、客戶支援等部門各自維護與更新自家 API，導致代理面對的是一個持續變動的目錄。具體應用包含：客服代理需要適應客服系統的新功能、內部 IT 助理需要跟上 SaaS 工具的版本更新、開發者代理需要跟上雲端服務與 SDK 的演進。在這些場景中，代理若無法跟上能力前沿，不僅效率低落，更可能因沿用過時流程而觸發錯誤或資安風險。

**Q11：若要將 Steward 落地為產品，需要考量哪些工程與產品面的權衡？**

A：產品化 Steward 需考量三個權衡：(1) 技能—工具依賴追蹤的精度與成本，需要決定追蹤粒度（單一工具、工具版本、還是呼叫鏈）以及對應的儲存與索引成本；(2) 動態配置的回應延遲，因為在任務執行中即時挑選相關工具與技能會增加延遲，需設計快取與預取機制以兼顧即時性與相關性；(3) 技能庫的可解釋性與可控性，產品需提供管理者檢視、更新、撤銷技能的介面，以避免「代理學到錯誤經驗卻無人察覺」的風險。這三項權衡共同決定了 Steward 在真實部署中的可用性。

**Q12：這項研究對「代理工程」（agent engineering）這個新興領域會產生哪些影響？**

A：這項研究的影響體現在三個層面：在觀念上，它將「代理勝任」從「單次任務完成」提升為「對動態能力前沿的持續追蹤」，重新定義了評測與部署的標準；在方法上，它示範了「工具管理」與「知識管理」必須聯合設計，催生「生態系管理器」這一新元件類別；在實務上，它提醒業界單純堆疊技能學習方法並不足以應對真實世界的工具演進，必須從系統層級思考資源生命週期。整體而言，這篇工作推動了代理工程從「單點能力優化」走向「持續性勝任工程」的轉向。

**Q13：論文中所承認的限制有哪些？例如領域覆蓋、轉換類型或評測指標方面？**

A：雖然 Δτ-Bench 已涵蓋 42 個領域與六個連續狀態，但相較於真實世界中工具生態系的規模與多樣性，仍屬於受控環境；論文中所定義的三種能力保留轉換（介面調適、功能拆分、工作流合併）雖具代表性，但無法窮舉所有可能的演進模式（例如顛覆性的能力新增或政策變更）。此外，參考路徑搜尋仰賴於建構出的解空間，若該空間本身未能涵蓋所有合理路徑，則「最優參考」可能只是「已知最優」而非「全域最優」，這是評測指標上的一個內在限制。

**Q14：在實驗中觀察到哪些典型的失敗案例？這些失敗透露出代理的哪些弱點？**

A：典型的失敗案例包含三類：(1) 代理沿用已被淘汰工具的工作流程，直到錯誤發生才嘗試修正，顯示其缺乏對工具可用性的主動偵測；(2) 代理在功能被拆分後無法協調多個新工具完成原本單一工具的工作，顯示其缺乏對「能力等價但介面變動」的推理能力；(3) 代理在出現更高效替代方案時仍選擇熟悉路徑，顯示其缺乏對「效率機會」的探索動機。這些失敗共同指向同一弱點：現有代理將「工具」與「技能」視為靜態資源，缺乏對其生命週期的主動管理。

**Q15：基於這些發現，未來有哪些值得探索的研究方向？**

A：未來值得探索的方向包括：(1) 更細粒度的「能力前沿偵測」機制，讓代理能在任務執行前就預判哪些既有路徑可能已非最優，而非僅在被動失敗後才修正；(2) 結合線上學習與終身學習的技能庫，使程序性知識能隨生態系演進持續演化而非依賴外部維護；(3) 將 Δτ-Bench 擴展至多代理協作場景，觀察代理間的技能共享與工具協商如何受到生態系變動影響；(4) 探索「顛覆性能力變動」（非能力保留的轉換）下的代理行為，這將挑戰現有「能力等價」假設並推向更真實的部署場景。這些方向共同指向「持續勝任代理」（continually competent agents）這一長期研究目標。

## 實務應用指南

### 適用場景

1. **企業內部統一 AI 助理入口**：大型企業有多個部門（HR、IT、財務、客服等）各自維護內部 API 與工具。當某部門淘汰舊工具或推出新工具時，AI 助理需要自動發現替代路徑並更新內建的工作流程知識，避免使用者察覺到服務中斷。

2. **SaaS 平台整合型代理**：代理同時串接多個第三方 SaaS（如 Salesforce、Slack、Jira、Notion）。當任一服務改版、調整 API 或被新服務取代時，代理需在不停機的情況下重新規劃任務路徑，並提示使用者採用更高效的新工具組合。

3. **DevOps 與 CI/CD 自動化助手**：CI/CD 工具鏈（GitHub Actions、Jenkins、ArgoCD、Terraform 等）版本演進快速。當某個 action 或 provider 被棄用，代理需自動改寫 pipeline 並保留已驗證的部署模式知識。

4. **客服與工單自動化系統**：客服代理需在 CRM、知識庫、訂單系統、付款系統間切換。當後端服務整合（如合併退款與發票流程為單一介面）或拆分時，代理需主動發現更短的解決路徑，而非沿用舊的多步驟流程。

5. **程式開發輔助代理**：當開發者使用的函式庫（如 LangChain、Pandas、ORM）發布重大改版，代理需識別棄用 API、推薦新寫法，並在累積的程式碼範例庫中標記需要更新的片段。

### 實作前置條件

**資料需求**
- 工具 schema 與 API 文件（OpenAPI、JSON Schema、MCP 定義等）
- 各領域的服務藍圖（entities、relations、policies）
- 歷史任務軌跡與對話紀錄，用於建立程序性記憶
- 工具變更日誌（retire / replace / add 事件）
- 至少 6 個時間點的生態系快照，用於模擬能力保留轉換

**計算資源**
- LLM 推理服務（建議 GPT-4 等級以上，根據論文中 42.3% 上界）
- 向量資料庫（如 Milvus、Qdrant）儲存工具與技能 embedding
- 工具執行的沙盒環境（隔離的 MCP server）
- 評測用的狀態比對器（state diff 與 conformance test 執行環境）

**技能前提**
- LLM 應用工程（prompt design、function calling、agent loop）
- 工具整合經驗（MCP、REST/gRPC、schema 設計）
- 評測方法論（task success 定義、reference path 標註）
- 基本的搜尋與規劃演算法知識（A*、BFS 用於 reference path 搜尋）

### 實作步驟建議

**階段一：建立基準生態系（對應論文 Task Foundation）**
1. 盤點目標領域的服務藍圖，明確 entities、relations 與 policies。
2. 將服務實作為有狀態的 MCP server，確保 tool call 會真實改變環境狀態。
3. 為每個工具撰寫可執行的函式與對應的資料庫 schema。
4. 採樣並驗證基準任務：給定輸入與約束，確認存在可達成的黃金狀態 $s^{gold}_E$。

**階段二：設計能力保留轉換（Capability Transformations）**
1. 定義三類轉換規則：介面調整（rename / add parameter / change format）、功能拆分（1→many）、流程合併（many→1）。
2. 為每個轉換撰寫 conformance test，確保新介面與原介面在相同輸入下產生相同狀態效果。
3. 自動化轉換流程，產生 6 個連續的生態系狀態 $A^{(0)}_{tool}, A^{(1)}_{tool}, \dots, A^{(5)}_{tool}$。

**階段三：採樣生態系狀態（Ecosystem Sampling）**
1. 在每個狀態下，決定哪些工具 retire、哪些新增、哪些保留。
2. 引入描述偏移（description shift）模擬雜訊文件。
3. 執行 acceptance check：所有基準能力仍可被達成，且 MCP 測試通過。

**階段四：建立參考路徑（Reference Path Search）**
1. 在每個生態系狀態下，對每個任務搜尋最有效率的路徑（最短步數或最低成本）。
2. 將參考路徑作為評測基準，用於判斷代理是否「錯失高效替代方案」。

**階段五：部署 Steward 風格的生態系管理器**
1. 為每個技能標註其依賴的工具集合（skill–tool dependency graph）。
2. 實作增量式技能維護：當工具 retire 時，自動標記相關技能為待更新；當新工具出現時，檢查是否有技能可被更高效版本取代。
3. 在任務執行階段，動態配置（dynamic provisioning）相關工具與技能給代理，而非靜態注入整個目錄。
4. 設計恢復機制：偵測到工作流中斷時，主動搜尋替代路徑而非沿用失敗步驟。

**階段六：持續評測與迭代**
1. 部署 Δτ-Bench 風格的評測管線，定期量測 task success 與 skill maintenance overhead。
2. 追蹤兩個指標：從中斷工作流的 recovery rate、從高效替代方案的 adoption rate。
3. 根據失敗案例更新技能庫與轉換規則。

### 潛在風險與注意事項

**風險一：技能維護成本失控**
- *現象*：每次工具變動都觸發大量技能重驗證，導致維護開銷超過效益。
- *緩解*：採用增量式維護而非全量重建；設定變更影響半徑閾值，僅更新直接依賴的技能；定期清理低使用率技能。

**風險二：參考路徑偏差**
- *現象*：搜尋出的「最優路徑」並非實際最優，導致代理被錯誤標記為低效。
- *緩解*：使用多個成本指標（步數、token、API 費用、延遲）並取交集；保留次優路徑作為容錯集合。

**風險三：雜訊描述導致工具誤選**
- *現象*：工具描述過時或誤導，代理選到錯誤工具。
- *緩解*：在技能庫中記錄工具的「實際行為 fingerprint」（輸入輸出樣本），比對描述與實際行為的偏差。

**風險四：能力保留轉換破壞語義**
- *現象*：介面調整後，雖然 state effect 相同，但語意已改變，導致代理在跨任務遷移時失敗。
- *緩解*：在 conformance test 之外，加入語意相似度檢查；保留轉換前後的對映表供代理查詢。

**風險五：評測集過擬合**
- *現象*：代理在 1,588 個任務上表現良好，但面對真實世界的長尾變化時失效。
- *緩解*：定期引入未見過的領域與工具組合；採用 rolling evaluation 而非固定測試集。

**風險六：動態配置延遲**
- *現象*：每步都重新選擇工具與技能，造成額外推理延遲。
- *緩解*：快取常用組合；只在狀態變化或失敗時觸發重新配置。

### 與其他技術的整合建議

**與 RAG 系統整合**
將工具目錄與技能庫視為兩個獨立的 retrieval corpus。Steward 在執行階段聯合檢索（joint retrieval），而非分開調用。可使用 ColBERT 或 SPLADE 等支援 late interaction 的模型，提升工具與技能的匹配品質。

**與 Model Context Protocol（MCP）整合**
論文中已將服務實作為有狀態 MCP server。實作時應將 MCP 視為工具的標準介面層，使生態系轉換（介面調整、拆分、合併）可在 MCP 層級透明完成，下游代理無需感知。

**與監控與可觀測性平台整合**
串接 OpenTelemetry 或 LangSmith，記錄每次工具呼叫的 (skill_id, tool_id, outcome) 三元組。這些資料是增量式技能維護的輸入，也是評測 adoption rate 的依據。

**與 CI/CD 整合**
將 Δτ-Bench 評測管線納入 CI/CD：每次工具 schema 變更時，自動跑 conformance test 與任務成功率回歸測試，避免破壞性變更直接上線。

**與版本管理系統整合**
工具的 retire / replace / add 事件應與 Git tag 或 semantic version 對齊，使技能庫能精確定位到特定生態系狀態，方便除錯與回溯。

**與人類回饋機制整合**
對於代理採用的「非參考路徑」，若實際執行成功且成本更低，應將其回饋至技能庫，逐步讓參考路徑隨真實使用演化，而非永遠靜態。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先讀第 1 節的 Figure 1 與動機段落，理解「為什麼工具會變、變了會怎樣」這個直覺問題，再看第 2 節的任務形式化。重點掌握「能力保留轉換」這個核心概念——它保證了評測的公平性，因為新舊工具都能完成同一件事，只是路徑不同。技術細節可以先跳過。

**給 AI 工程師**：重點關注 Steward 的系統設計（增量式技能維護 + 動態配置）。論文中「jointly manages tools and procedural knowledge」的設計哲學值得在自家 agent 系統中實作：把技能庫與工具目錄視為耦合資源而非兩個獨立模組。實作時可從小規模開始，先處理「工具 retire」這一最常見的場景，再擴展到「新增高效替代方案」。

**給研究者**：第 2 節的形式化與第 3 節的 benchmark 建構流程是主要貢獻。特別注意 capability-preserving transformation 的三種類型（adapt / split / merge）與 conformance test 的設計，這套方法論可應用於其他動態環境的 benchmark 建構（例如動態網頁、演進中的程式語言 API）。42.3% 的上界與 skill-learning 方法無法穩定轉換為適應能力，是值得深入追問的現象。

**給產品經理**：核心訊息是「成功的任務執行不等於高效的任務執行」。當前代理即使完成任務，也可能錯過更短的解法，且累積的經驗會在工具變動時失效。產品設計上應考慮：暴露「替代方案建議」給使用者、對工具變動設立變更預告期、為代理的技能庫設計可審查的更新機制。Steward 的價值主張是「sustains higher task success with lower maintenance overhead」，這對營運成本敏感的平台尤其關鍵。
