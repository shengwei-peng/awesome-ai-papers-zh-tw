## ⚡ TL;DR

現有框架演化評估與測試時搜尋基線比較不公，且易過擬合同一基準。
本文提出統一預算協定，比較框架演化與平行取樣、序列精煉，並以保留任務驗證泛化。
在 Terminal-Bench 2.1 上，自動框架演化未穩定勝過簡單測試時縮放，泛化能力亦有限。

## 摘要翻譯

我們重新審視針對 LLM 智慧代理之自動框架演化（automatic harness evolution）的評估。現有的框架演化（harness evolution）方法使用單元測試案例來搜尋框架配置（harness configurations），然後在同一個公開基準（benchmark）上報告最終效能。此評估協定（evaluation protocol）引發兩個根本疑慮。首先，框架演化本身就是一種反覆搜尋程序，會利用任務回饋（task feedback）不斷評估並修正候選框架（candidate harnesses）。如同代理式測試時擴展（agentic test-time scaling），它應在對等的回饋與推論預算（inference budgets）下，與簡單的任務層級搜尋基線（task-level search baselines）進行比較，以判斷其增益是源自框架設計（harness design）的改善，還是僅來自額外搜尋（additional search）。其次，由於搜尋與最終評估使用相同的基準，所報告的增益可能有過度擬合（overfitting）至該特定任務集合的風險。為解決這些疑慮，我們進行了大規模評估，在可比的回饋與推論預算下比較框架演化與簡單的測試時擴展（test-time scaling）及探索基線（discovery baselines），並在保留任務（held-out tasks）上評估演化後的框架，以檢驗所發現的改進是否可泛化（generalize）。在 Terminal-Bench 2.1 上，使用 GPT-5.4 與 Claude Opus 4.6 的實驗顯示，自動框架演化並未一致地優於簡單的測試時擴展方法，且泛化能力有限。我們的結果對自動框架演化的有效性提出了重要質疑，並強調建立更公平的評估協定（evaluation protocols）與基準，以進行自動框架設計的必要性。我們的程式碼可於 https://github.com/rethinking-harness-evolution 取得。

### 核心貢獻（3～5點）
- 指出現行框架演化評估協定的兩大根本疑慮：與簡單任務層級搜尋基線在回饋與推論預算上不對等所導致的不公平比較，以及搜尋與最終評估共用同一基準所帶來的過度擬合風險。
- 在可比的回饋與推論預算下，系統性地比較框架演化與簡單測試時擴展及探索基線，提供更具對照性的實證分析。
- 透過保留任務評估演化後的框架，檢驗所發現改進的泛化能力，降低對單一基準過度擬合的疑慮。
- 在 Terminal-Bench 2.1 上結合 GPT-5.4 與 Claude Opus 4.6 的實驗顯示，自動框架演化並未穩定優於簡單測試時擴展方法，且泛化能力有限。
- 強調未來需要建立更公平的評估協定與基準，以推動自動框架設計領域的健全發展。

### 適合對象
本論文最適合從事 LLM 智慧代理、自動框架設計（automatic harness design）、測試時擴展（test-time scaling）以及代理評估協定研究的學者與實務工作者；特別是關注如何進行嚴謹基準測試、公平比較方法論，以及避免評估流程過度擬合的研究者。對於正在開發或評估自動化代理框架演化系統的讀者，本文亦提供了重要的方法論反思與實證參考。

## 深度分析

#### 方法論解析

本研究的核心貢獻在於提出一套 **unified budget view（統一預算觀點）**，將 harness evolution（框架演化）與 test-time scaling（測試時擴展）放在同一個評估維度下比較。作者指出，過去許多 harness evolution 方法雖然宣稱改進了 agent（代理者）的整體表現，但其實驗設計並未區分「框架設計本身的進步」與「在評估任務上投入更多搜尋預算」這兩種效應。為此，論文將所有方法都視為對固定 compute budget（運算預算）的不同分配策略，並明確規範每個方法能觀察到的 feedback（回饋）、能消耗的 inference budget（推論預算），以及能修改的對象是 trajectory（軌跡）還是 harness（框架）。

在這個框架下，作者定義了四種對照方法：

1. **Parallel Sampling（平行取樣）**：針對單一任務，使用固定 harness 獨立生成 K 條 trajectory，再透過 verifier（驗證器）或投票機制選出最終答案。這種方法屬於「橫向擴展」，只增加取樣數量，不改變 harness。

2. **Sequential Refinement（序列精煉）**：同樣針對單一任務，但將 K 次推論預算用於迭代式修正。每次生成新的 trajectory 時，都會參考前一次的失敗經驗，逐步修正推理過程。這屬於「縱向擴展」，仍然只修改單一任務的 trajectory。

3. **Harness Evolution（框架演化）**：將預算用於修改共享的 harness。具體流程是：在多個任務上執行 agent，收集 trajectory、score（分數）與 failure pattern（失敗模式），由 meta-agent（元代理者）提出 harness 修改，再在新的任務批次上驗證，反覆迭代。這裡的關鍵在於 harness 是跨任務共享的，理論上應該學到可遷移的設計改進。

4. **Harness Scaling（框架縮放）**：可視為 harness evolution 的變形，但允許針對不同任務維護 task-specific harness（任務專屬框架）。這種方法雖然也修改 harness，但修改不具備跨任務通用性，更接近於把 test-time scaling 的預算花在「為每個任務客製化框架」上。

為了讓不同方法之間的比較更公平，作者引入了一個 **summarization map Φ（摘要映射 Φ）**，由與 agent policy（代理策略）π_θ 相同的底層模型實現。Φ 的作用是把過往的 experience store（經驗儲存）壓縮成可讀取的摘要，例如重複出現的失敗、冗餘嘗試或成本資訊，讓後續的 refinement（精煉）或 editing（編輯）步驟能夠診斷先前嘗試為何表現不佳，並避免重複無效的修改。這個設計讓 sequential refinement 與 harness evolution 都能利用歷史軌跡資訊，從而在比較時減少因「資訊不對稱」造成的偏差。

整體來說，這套方法論的精髓在於把「框架演化」從一個單純的「搜尋更好框架」的問題，重新框架化為「在固定預算下，應該把資源花在任務級搜尋還是框架級搜尋」的資源配置問題。這種視角不僅讓實驗比較更嚴謹，也直接挑戰了過去文獻中「evolved harness 必然優於固定 harness」的預設。

#### 實驗數據解讀

論文在 **Terminal-Bench 2.1** 上進行實驗，測試模型包含 **GPT-5.4**、**Claude Opus 4.6** 與 **GPT-5.4 mini**。主要評估指標為 **pass@1**，也就是在單次推論下任務通過的比例。實驗分為兩大情境：一種是在 harness search（框架搜尋）與 final evaluation（最終評估）使用相同任務集合；另一種則是使用 held-out tasks（保留任務）來檢驗演化後框架的 generalization（泛化能力）。

從圖 1 可以看出，在沒有 unit-test feedback（單元測試回饋）的情況下，四種方法的平均 pass@1 表現如下：

- **Parallel Sampling（平行取樣）**：約 74%，表現最佳。
- **Sequential Refinement（序列精煉）**：約 72.3%，略低於平行取樣但仍優於框架演化。
- **Harness Evolution（框架演化）**：約 69.3%，明顯低於前兩者。
- **Harness Scaling（框架縮放）**：約 67.4%–68.2%，與框架演化接近，但同樣未超越簡單的 test-time scaling baseline（基線）。

這組數據的直接含義是：當 inference budget 與 feedback budget 被控制為相當時，把預算花在生成更多獨立軌跡或迭代修正單一軌跡，往往比把預算花在修改共享 harness 更有效。這與過去 harness evolution 文獻中常見的「演化後框架顯著提升」形成鮮明對比。

進一步分析實驗 4.3 的結果，作者發現當 harness evolution 的搜尋過程與最終評估使用同一組任務時，報告的增益往往被高估。這是因為演化過程中的 meta-agent 可能學到的是「針對特定任務實例的捷徑」，例如記住某些常見錯誤模式或利用 task-specific verifier feedback 進行過度擬合，而非學到真正可遷移的 harness design（框架設計）。當把演化後的框架拿到 held-out tasks 上測試時，這些「虛胖」的增益便會大幅縮水，顯示出 limited generalization（有限泛化）。

值得注意的是，論文也區分了「有 unit-test feedback」與「無 unit-test feedback」的情境。在無 unit-test feedback 時，harness evolution 的劣勢更為明顯，因為此時 meta-agent 難以獲得精確的錯誤定位訊號，導致提出的 harness 修改方向不穩定。這也暗示：harness evolution 的有效性高度依賴 verifier 的品質與 feedback 的顆粒度，而這在真實世界任務中往往難以保證。

整體而言，實驗數據傳達了一個重要訊息：**automatic harness evolution（自動框架演化）並非萬靈丹**。在相同預算下，它不一定能打敗簡單的 test-time scaling，而且其報告的增益可能包含大量對評估任務的 overfitting（過度擬合）。這對未來研究者在宣稱 harness evolution 的優勢時，提出了更高的舉證標準。

#### 與現有研究的比較

在相關文獻方面，作者將現有工作分為兩大類：**test-time scaling（測試時擴展）** 與 **automatic harness evolution（自動框架演化）**。

在 test-time scaling 領域，parallel sampling（平行取樣）與 sequential refinement（序列精煉）已經是相對成熟的方向。前者透過多條獨立軌跡與 verifier reranking（驗證器重排序）來提升正確率；後者則透過迭代式自我修正來深化推理。本研究的貢獻在於首次系統性地將這兩種方法視為 harness evolution 的「強基線」，並在 matched budget（匹配預算）下進行公平比較。過去 harness evolution 文獻往往只與固定 harness 或簡單 prompt tuning（提示調整）比較，忽略了「額外搜尋預算」本身就能帶來的增益。

在 automatic harness evolution 領域，作者回顧了幾個代表性工作：

- **Meta-Harness（Lee et al., 2026）**：直接對 harness code（框架程式碼）進行搜尋，利用 source code（原始碼）、score 與 execution trace（執行軌跡）作為回饋。
- **Agentic Harness Engineering（Lin et al., 2026）**：透過 observability-driven loop（可觀測性驅動迴圈）演化 prompts、tools、middleware、skills 與 long-term memory（長期記憶）。
- **AEVO（Zhang et al., 2026）**：將 agentic evolution 本身視為一個互動式環境，修改控制未來搜尋的程序或 agent context（代理上下文）。

相較於這些工作，本研究的定位並非提出一個新的 harness evolution 演算法，而是重新檢視其評估方式。作者指出，上述方法雖然在各自設定的 benchmark（基準測試）上報告了顯著進步，但它們的實驗協定往往存在兩個問題：第一，沒有與 test-time scaling baseline 在相同 feedback 與 inference budget 下比較；第二，搜尋與最終評估使用相同任務集合，導致無法區分「任務特定適應」與「通用框架改進」。

本研究的優勢在於：

1. **提出 controlled budget protocol（控制預算協定）**：明確定義每個方法能觀察什麼回饋、能消耗多少推論資源、能修改什麼對象，讓比較具備科學嚴謹性。
2. **引入 held-out evaluation（保留評估）**：透過分離搜尋任務與測試任務，檢驗 evolved harness 是否具備真正的泛化能力。
3. **強調 simple baselines（簡單基線）的重要性**：提醒研究者，在宣稱某種複雜方法有效之前，必須先證明它優於簡單的資源重分配策略。

然而，本研究也存在一些限制。首先，實驗僅在 **Terminal-Bench 2.1** 上進行，這是一個以終端機操作為主的 benchmark，其任務特性可能與網頁瀏覽、科學推理或開放式問答等領域不同。其次，實驗使用的模型（GPT-5.4、Claude Opus 4.6、GPT-5.4 mini）均為專有模型，研究者無法完全控制其內部行為，這可能影響結果的可解釋性與可遷移性。第三，論文對 harness evolution 的搜尋空間、mutation operator（變異運算子）與 meta-agent 的設計細節著墨有限，讀者難以判斷不同演算法設計對結果的影響。最後，雖然作者強調 generalization，但 held-out tasks 仍來自同一個 benchmark distribution（基準測試分布），對於跨領域遷移的檢驗仍顯不足。

#### 可重現性評估

在可重現性方面，作者公開了研究程式碼，存放於 **https://github.com/rethinking-harness-evolution**。這對於希望驗證結果或延伸研究的人來說是重要的一步。然而，可重現性不僅取決於程式碼是否公開，還取決於以下幾個層面：

1. **Dataset availability（資料集可取得性）**：本研究使用 Terminal-Bench 2.1，根據文中描述這是一個 public benchmark（公開基準測試）。只要該資料集持續維護並開放下載，其他研究者原則上可以複製實驗。

2. **Model availability（模型可取得性）**：實驗使用的 GPT-5.4、Claude Opus 4.6 與 GPT-5.4 mini 均為商業 API 模型，並非開源權重。這意味著即使程式碼公開，其他研究者仍需取得相應的 API 存取權，並且可能面臨 model version drift（模型版本飄移）的問題。若 OpenAI 或 Anthropic 在未來更新模型行為，過去的實驗結果可能難以完全復現。

3. **Hyperparameter transparency（超參數透明度）**：論文雖然描述了 high-level 的方法論，但對於 K 的具體數值、verifier 的實作細節、meta-agent 的 prompt 設計、以及 harness mutation 的搜尋空間等關鍵超參數，提供的資訊相對有限。這會增加外部復現的難度。

4. **Computational cost（運算成本）**：Harness evolution 與 test-time scaling 都需要大量 API 呼叫。對於資源有限的研究團隊而言，完整復現所有模型與所有預算設定的實驗可能成本高昂。

5. **Evaluation protocol clarity（評估協定清晰度）**：作者提出的 controlled budget protocol 是本文最重要的方法論創新之一。若程式碼中能清楚實作並文件化這個協定，將大幅提升未來研究的可比較性。

總體而言，本研究在可重現性上達到了「程式碼公開、資料集公開」的基本門檻，但由於依賴專有模型且部分實作細節未完全揭露，完整復現仍具挑戰。建議作者在未來版本中補充 hyperparameter 表格、verifier 實作細節，以及估算的實驗成本，以進一步提升可重現性。

#### 未來研究方向

基於本研究的發現，未來可以從以下幾個方向繼續深入：

1. **更嚴謹的 evaluation protocol（評估協定）設計**：未來的 harness evolution 研究應該強制採用「搜尋任務與評估任務分離」的協定，並且在所有比較中納入 test-time scaling baseline。可以進一步發展標準化的 budget accounting（預算核算）方法，讓不同研究之間的結果可以直接比較。

2. **跨領域 generalization（泛化）研究**：本研究的 held-out tasks 仍來自 Terminal-Bench 2.1。未來應該在更多樣化的環境（例如網頁代理、科學計算、軟體工程、多模態任務）上測試 evolved harness 的遷移能力，以判斷 harness evolution 是否只在特定任務類型上有效。

3. **Hybrid search（混合搜尋）策略**：既然單純的 harness evolution 不一定優於 test-time scaling，未來可以探索如何同時在「任務級搜尋」與「框架級搜尋」之間動態分配預算。例如，根據任務難度或失敗模式，決定何時該進行 parallel sampling、何時該修改 harness。

4. **Meta-learning（元學習）與 transfer learning（遷移學習）**：如果 harness evolution 的目標是學到可遷移的設計原則，那麼可以借鑑 meta-learning 的觀點，讓 meta-agent 從多個不同領域的任務中學到「如何設計 harness」，而不只是記住特定任務的解題模式。

5. **Verifier 與 feedback 機制設計**：本研究顯示 harness evolution 在缺乏 unit-test feedback 時表現較差。未來可以研究如何設計更強健的 verifier，例如結合執行軌跡分析、自然語言批評模型（critic model）或人類回饋，來提供更精確的錯誤定位訊號。

6. **開源 harness evolution 平台**：目前許多 harness evolution 方法依賴專有模型與特定 benchmark。建立一個開放、模組化、可擴充的 harness evolution 平台，將有助於社群進行更公平的比較與更快速的迭代。

7. **理論分析**：除了實證研究，未來也可以從理論上分析 harness evolution 與 test-time scaling 的樣本複雜度與計算複雜度，幫助研究者理解在什麼條件下框架級搜尋會優於任務級搜尋。

8. **長期記憶與持續學習**：Harness evolution 本質上是一種持續改進外部 scaffold（鷹架）的過程。未來可以探討如何讓 evolved harness 具備 catastrophic forgetting（災難性遺忘）抗性，並在接觸新任務時持續累積有效經驗。

總結來說，本研究為 automatic harness evolution 領域敲響了警鐘：在宣稱某種框架演化方法有效之前，必須先回答一個根本問題——這些增益究竟來自更好的 harness design，還是僅僅來自更多的搜尋預算？未來的研究應該在更公平的評估協定、更多樣的 benchmark 與更強大的 baseline 下，重新檢視這個問題。

## 論文問答

**Q1：這篇論文重新檢視了什麼核心問題？**
A：這篇論文重新檢視了大型語言模型代理人的自動框架演化（automatic harness evolution）之評估方式。作者指出，現有方法通常使用單元測試案例在公開基準上搜尋框架配置，然後又在同一個基準上報告最終效能，這種評估協議可能誇大了框架演化的真正效益。因此，本文的核心問題在於：自動框架演化所帶來的效能提升，究竟來自於框架設計本身的通用化改進，還是僅僅來自於在相同任務上進行更多次搜尋與取樣。

**Q2：現有的框架演化評估方法為何存在根本性問題？**
A：現有方法存在兩個根本性的問題。第一，框架演化本身就是一個反覆搜尋的過程，會不斷利用任務回饋來評估並修正候選框架，這與測試時擴展（test-time scaling）非常相似，因此若不與簡單的任務層級搜尋基線在相同回饋與推論預算下比較，就無法判斷其增益是否來自更好的框架設計。第二，由於搜尋過程與最終評估使用的是同一組基準任務，報告的效能提升可能反映對特定任務集的過度擬合，而非可遷移到新任務的通用框架改進。

**Q3：為何與測試時擴展基線比較如此重要？**
A：與測試時擴展基線比較的重要性在於，它能幫助研究者區分「框架設計改進」與「額外搜尋帶來的統計增益」。平行取樣與序列式精煉等方法同樣可以在固定框架下，透過增加推論時的計算量與驗證器回饋來提升任務表現，因此如果框架演化無法在相同預算下穩定勝過這些簡單基線，那麼其宣稱的優勢就可能只是搜尋預算重新分配的結果。這種比較更能揭示自動框架演化是否真正發現了可重複使用的結構性改進，還是僅僅適應了評估任務的特定模式。

**Q4：本文提出的核心評估方法是什麼？**
A：本文提出了一個統一預算觀點（unified budget view）來評估框架演化，將不同方法放在可比較的回饋與推論預算下進行對照。具體而言，作者比較了四種方法：平行取樣、序列式精煉、框架演化與框架擴展（harness scaling），並明確規定每種方法能獲得什麼回饋、如何分配推論計算、以及是否修改任務軌跡或框架本身。透過這種控制變因的協議，研究人員可以更公平地判斷框架演化是否真正帶來了可泛化的框架設計改進。

**Q5：本文在評估協議上的關鍵創新是什麼？**
A：關鍵創新在於將「優化回饋」與「最終測量」分離，並要求框架演化與簡單的測試時擴展基線在匹配預算下競爭。傳統協議讓框架演化在公開基準上搜尋，又在同一基準上評估，導致搜尋與評估重疊；本文則強調應使用保留任務（held-out tasks）來檢驗演化後框架的泛化能力。此外，作者還引入了框架擴展作為第四種對照，進一步探討任務專屬的框架更新是否優於跨任務共享的框架更新。

**Q6：本文在實驗設計上做了哪些重要選擇？**
A：本文在實驗設計上的重要選擇包括嚴格匹配回饋預算與推論預算、區分有無單元測試回饋的情境，以及比較共享框架與任務專屬框架的更新策略。作者明確定義每種方法可以觀察到的回饋類型，例如驗證器回饋或執行軌跡，並控制每種方法消耗的總計算量，以避免因預算不對等而產生偏差。這些設計選擇使得實驗能夠更精確地分離出「框架設計改進」與「任務層級搜尋」各自對效能的貢獻。

**Q7：實驗使用了哪些基準測試與模型？**
A：實驗主要在 Terminal-Bench 2.1 上進行，這是一個針對終端機環境的代理人基準測試，並使用了 Claude Opus 4.6、GPT-5.4 以及 GPT-5.4 mini 等多個模型。作者透過這個設定來檢驗不同框架演化方法在真實終端任務上的表現，並比較它們與簡單測試時擴展基線的差異。這樣的模型與基準組合有助於評估結果是否跨模型穩定，並提升研究結論的外部效度。

**Q8：實驗的主要發現是什麼？**
A：實驗發現，自動框架演化並未穩定地超越簡單的測試時擴展基線，尤其是在沒有單元測試回饋的情況下，其平均表現甚至低於平行取樣與序列式精煉。此外，當搜尋與最終評估使用相同任務集時，框架演化所報告的增益往往反映了對評估實例的適應，而非可遷移到保留任務的通用改進。這些結果挑戰了自動框架演化必然優於簡單推論時搜尋的假設，並凸顯了現有評估協議可能誇大其效益的風險。

**Q9：本文進行了哪些額外的消融或泛化分析？**
A：本文除了比較四種主要方法外，還特別評估了演化後框架在保留任務上的泛化表現，以檢驗其改進是否真正來自於框架設計而非任務過度擬合。作者也分析了當單元測試案例可用與不可用時，不同方法的相對表現差異，進一步揭示驗證器回饋對各種搜尋策略的影響。這些分析顯示，框架演化的優勢在跨任務遷移時相當有限，提醒未來研究必須區分「在已知任務上調參」與「發現通用框架原則」。

**Q10：這些發現在哪些實際場景中具有重要意義？**
A：這些發現對於任何希望透過自動化方式改進代理人框架的實務應用都至關重要，特別是在軟體工程、資料分析與終端機自動化等需要穩定且可遷移框架的領域。如果企業僅根據公開基準上的搜尋結果來部署框架演化系統，可能會發現其在真實、未見過的任務上表現不如預期。因此，這項研究提醒實務者在採用自動框架演化前，應先確認其相對於簡單推論時擴展的淨效益，並在保留任務上驗證泛化能力。

**Q11：產品團隊在部署框架演化時應考慮哪些因素？**
A：產品團隊在部署框架演化時，首先應該評估其是否能在與平行取樣或序列式精煉相同的推論預算下提供額外價值，而不是直接假設框架層級的搜尋必然更好。其次，團隊需要建立獨立的保留測試集，將優化回饋與最終評估分開，以避免在內部基準上過度擬合。最後，由於框架演化涉及反覆修改提示詞、工具、記憶體與控制邏輯，團隊也應監控演化後框架的可解釋性與維護成本，確保其不會為了短期效能而犧牲長期穩定性。

**Q12：這項研究可能如何影響自動框架設計領域？**
A：這項研究可能促使自動框架設計領域建立更嚴謹、更公平的評估標準，要求未來研究在宣稱框架演化優勢時，必須與適當的測試時擴展基線進行比較並展示保留任務上的泛化能力。這將有助於減少因評估協議缺陷而產生的誇大宣稱，並引導研究者開發真正具有通用性的框架改進方法。長遠來看，這種更嚴格的評估文化也有助於區分「任務專屬調校」與「可重複使用的框架設計原則」，從而推動整個領域朝向更成熟、更可靠的工程化方向發展。

**Q13：本文承認了哪些限制？**
A：本文主要聚焦於 Terminal-Bench 2.1 這一特定終端機環境，因此其結論是否能推廣到其他類型的代理人任務或環境，仍需更多研究來驗證。此外，實驗雖然比較了多種方法，但預算匹配與回饋控制的具體實作方式可能會影響結果，不同的實作選擇可能會帶來不同的結論。作者也指出，他們的目標並非否定所有框架演化方法，而是強調現有評估協議不足以證明其優越性，因此未來需要更多樣化的基準與更嚴格的對照實驗。

**Q14：框架演化在哪些情況下會失效或表現不佳？**
A：根據本文結果，框架演化在沒有單元測試回饋的情況下表現特別不佳，其平均效能低於簡單的平行取樣與序列式精煉基線。此外，當搜尋過程與最終評估使用相同任務集時，框架演化容易過度擬合到特定任務模式，導致在保留任務上的泛化能力有限。這意味著如果應用場景缺乏可靠的驗證器回饋，或者目標任務與訓練搜尋時使用的任務分佈有顯著差異，自動框架演化可能無法帶來預期效益。

**Q15：本文提出了哪些未來研究方向？**
A：本文建議未來研究應開發更公平的評估協議與更多樣化的基準測試，特別是能夠清楚分離優化回饋與最終測量的設計。研究者也可以探索如何讓框架演化發現更具通用性的設計原則，而不僅是適應特定任務集的表面模式。此外，未來工作可以進一步比較不同回饋類型與預算分配策略對框架演化的影響，並發展能夠同時兼顧效能、泛化能力與可維護性的自動框架設計方法。

## 實務應用指南

## 適用場景

1. **終端機 / 命令列自動化代理**  
   需要讓 LLM 在 shell、檔案系統、版本控制等環境中執行多步驟任務，並持續改善提示詞、工具呼叫與驗證邏輯的場景，例如 Terminal-Bench 類型的程式碼維護任務。

2. **企業內部流程自動化**  
   跨系統填單、資料查詢、報表生成等重複性工作流程，可透過自動化框架演化來調整記憶體、工具鏈與錯誤處理規則，減少人工維護提示詞的成本。

3. **客戶支援與對話代理**  
   當代理需要根據對話歷史、外部知識庫與驗證規則反覆修正回應時，可利用框架演化來優化檢索策略、事實查核流程與回覆模板。

4. **資料擷取與轉換代理**  
   從非結構化文件、網頁或 API 中擷取結構化資訊，並需要隨資料格式變化自動調整解析工具與驗證規則的應用。

5. **持續整合 / 持續部署（CI/CD）中的智慧測試代理**  
   在軟體開發流程中自動生成、執行與修正單元測試或整合測試，並透過框架演化來改進測試生成策略與失敗分析邏輯。

## 實作前置條件

- **可驗證的任務資料集**：需要具備單元測試或明確驗證器（verifier）的任務集合，才能產生穩定的回饋訊號供框架搜尋使用。
- **明確的推論與回饋預算**：在實驗設計階段就要定義每種方法可使用的 API 呼叫次數、token 數量與可取得的回饋類型。
- **可編輯的代理框架（harness）**：提示詞、工具定義、記憶體機制、驗證常式與控制流程必須能被程式化修改，而非寫死的靜態模板。
- **執行日誌與軌跡追蹤能力**：需要記錄完整 trajectory（狀態、動作、觀察結果），才能讓後續的 meta-agent 分析失敗原因。
- **具備程式碼生成能力的 LLM**：用於自動提出框架修改建議，例如 GPT-5.4、Claude Opus 4.6 等級的模型。
- **評估基礎建設**：需能區分「搜尋回饋任務」與「最終評估任務」，並支援 pass@1、held-out generalization 等指標。

## 實作步驟建議

1. **建立穩定的初始框架**  
   先以人工設計一個可運作的基礎 harness，確保代理能完成部分任務，並記錄所有執行軌跡。

2. **設計公平的預算協議**  
   明確規範平行採樣、序列精煉、框架演化與框架縮放各自可使用的推論次數、回饋來源與修改對象（trajectory vs. harness）。

3. **實作簡單的測試時間縮放基線**  
   在投入框架演化前，先實作平行採樣（parallel sampling）與序列精煉（sequential refinement），作為後續比較的效能天花板與成本基準。

4. **實作框架演化迴圈**  
   讓 meta-agent 分析歷史軌跡與分數，提出 harness 修改建議，並在開發集上驗證，保留表現較佳的版本。

5. **區分搜尋集與最終評估集**  
   絕對不要讓框架搜尋與最終報告使用完全相同的任務實例。應保留 held-out 任務以評估真正的泛化能力。

6. **進行控制變因比較**  
   在相同回饋與推論預算下，比較框架演化與測試時間縮放基線。若框架演化未顯著勝出，應優先採用較簡單的基線。

7. **驗證泛化性後再部署**  
   將演化後的框架在全新任務、不同模型或不同環境上測試，確認改善來自可重用的框架設計，而非對特定任務的過擬合。

8. **建立持續監控與回滾機制**  
   部署後持續追蹤框架版本效能，當新任務分布改變或效能衰退時，能夠快速回滾到穩定版本。

## 潛在風險與注意事項

- **對基準測試過擬合**  
  若搜尋與評估使用同一組任務，報告的增益可能只是記住特定任務模式。務必使用 held-out 任務驗證。

- **額外搜尋 vs. 真正框架改善**  
  框架演化的提升可能僅來自「花了更多推論預算在評估任務上」。必須與同等預算的測試時間縮放方法比較。

- **推論成本快速膨脹**  
  自動演化需要反覆呼叫強大模型來生成與評估修改，實際部署成本可能遠高於簡單基線，需預先設定成本上限。

- **獎勵駭入（reward hacking）**  
  框架可能學會利用驗證器漏洞或單元測試的特定模式來取得高分，而非學會解決真實問題。建議搭配人工抽樣檢查。

- **維護與可解釋性下降**  
  自動生成的框架可能變得複雜難懂，導致除錯困難。應保留修改歷史與人可讀的修改說明。

- **泛化能力有限**  
  論文顯示自動框架演化在 Terminal-Bench 2.1 上並未穩定勝過簡單基線，且泛化能力有限。不要預設框架演化一定優於測試時間縮放。

## 與其他技術的整合建議

- **與現有代理框架整合**  
  可將演化後的提示詞、工具定義與控制流程匯出為 LangChain、AutoGen 或自研 agent framework 的模組，避免從頭重建基礎建設。

- **與 CI/CD 管線結合**  
  把框架演化與評估流程納入持續整合，每次程式碼或提示詞變更時自動執行 held-out 評估，確保新框架不會退化。

- **與可觀測性平台整合**  
  將 trajectory、分數與框架版本資訊寫入可觀測性系統（如 LangSmith、Weights & Biases、自研 tracing），方便後續分析與審計。

- **與模型服務層整合**  
  在模型服務層統一管理 API 金鑰、速率限制與成本追蹤，讓框架演化與基線方法在相同推論預算下公平競爭。

- **與人工回饋迴路整合**  
  對於難以自動驗證的任務，可將人工標註結果作為額外回饋來源，但需注意這會改變預算協議，應在比較時一併揭露。

## 給不同背景讀者的閱讀建議

**初學者**：這篇論文主要在討論「如何公平比較自動優化代理框架的方法」。你可以先理解「框架（harness）」就是代理的提示詞、工具與控制流程，「測試時間縮放」則是在同一個框架下讓模型多試幾次。重點結論是：自動優化框架不一定比單純讓模型多試幾次更好，而且容易對特定題目過擬合。

**AI 工程師**：建議聚焦於第 3 節的統一預算框架與實驗設計。論文提醒你在導入 harness evolution 前，一定要先實作 parallel sampling 與 sequential refinement 作為基線，並嚴格區分 search set 與 test set。這對你設計公司內部的 agent evaluation protocol 非常實用。

**研究人員**：本文的核心貢獻在於重新檢視 automatic harness evolution 的評估方式，指出現有文獻可能混淆了「框架設計改善」與「額外搜尋帶來的增益」。建議深入閱讀實驗設計與 held-out generalization 的分析，並思考如何設計更嚴謹的 benchmark 與評估指標。

**產品經理**：這篇論文對你的啟示是「不要輕易相信自動優化框架能帶來顯著效益」。在規劃產品路線時，應優先投資簡單且可解釋的測試時間縮放策略，並要求工程團隊在相同成本下比較不同方法，同時驗證在新任務上的泛化表現，避免被過度優化的基準數字誤導。
