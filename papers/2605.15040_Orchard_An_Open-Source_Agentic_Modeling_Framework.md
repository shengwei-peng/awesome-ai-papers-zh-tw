## 摘要翻譯

智能體建模旨在將大型語言模型（Large Language Model, LLM）轉化為自主智能體，使其能夠透過規劃（Planning）、推理（Reasoning）、工具使用（Tool use）以及與環境的多輪互動（Multi-turn interaction）解決複雜任務。儘管投入了大量資源，開放研究仍受到基礎設施與訓練方面不足的限制。許多高效能系統依賴專有的程式碼庫、模型或服務，而大多數開源（Open-source）框架則專注於編排（Orchestration）與評估，而非可擴展的智能體訓練（Scalable agent training）。我們提出了 Orchard，一個用於可擴展智能體建模的開源框架。其核心是 Orchard Env，一個輕量級（Lightweight）環境服務，提供可重用原語（Reusable primitive），用於跨任務領域、智能體執行框架（Agent harness）與流水線階段（Pipeline stage）的沙盒生命週期管理（Sandbox lifecycle management）。在 Orchard Env 之上，我們建構了三個智能體建模方案。Orchard-SWE 面向程式碼智能體（Coding agent）。我們從 MiniMax-M2.5 與 Qwen3.5-397B 蒸餾出 107K 條軌跡（Trajectory），引入信用分配監督微調（Credit-assignment SFT）以從未解決軌跡（Unresolved trajectory）的有效片段中學習，並應用平衡自適應採樣（Balanced Adaptive Rollout）進行強化學習（Reinforcement Learning, RL）。以 Qwen3-30B-A3B-Thinking 為起點，Orchard-SWE 於 SWE-bench 驗證集（SWE-bench Verified）上，經監督微調（Supervised Fine-Tuning, SFT）後達 64.3%，再經監督微調加強化學習（SFT+RL）後達 67.5%，在規模相當的開源模型中創下新的最先進水平（State of the art）。Orchard-GUI 僅以 0.4K 條蒸餾軌跡（Distilled trajectory）與 2.2K 個開放式任務（Open-ended task），訓練出一個 4B 參數的視覺語言（Vision-Language Model, VLM）電腦使用智能體（Computer-use agent）。它在 WebVoyager、Online-Mind2Web 與 DeepShop 上分別達到 74.1%、67.0% 與 64.0% 的成功率（Success rate），使其成為最強的開源模型，同時仍與專有（Proprietary）系統保持競爭力。Orchard-Claw 面向個人助理智能體（Personal assistant agent）。僅使用 0.2K 個合成任務（Synthetic task）進行訓練，它在 Claw-Eval 上達到 59.6% 的 pass@3，搭配更強的 ZeroClaw 執行框架時達到 73.9%。綜合而言，這些結果表明，一個輕量級、開放、與執行框架無關（Harness-agnostic）的環境層（Environment layer）能夠實現跨領域的可重用智能體數據（Reusable agentic data）、訓練方案（Training recipe）與評估。

### 核心貢獻（3～5點）
- **提出 Orchard 開源框架與 Orchard Env 環境層**：以輕量級、與執行框架無關的設計，提供跨任務領域、智能體執行框架與流水線階段的可重用沙盒生命週期管理原語，填補開源生態在「可擴展智能體訓練基礎設施」上的關鍵缺口。
- **Orchard-SWE 程式碼智能體方案**：透過 107K 條蒸餾軌跡、信用分配監督微調與平衡自適應採樣強化學習，在 SWE-bench 驗證集上以 67.5% 的成績刷新同規模開源模型的最先進水平。
- **Orchard-GUI 圖形介面智能體方案**：僅以 0.4K 條蒸餾軌跡與 2.2K 個開放式任務，即訓練出在 WebVoyager、Online-Mind2Web、DeepShop 三項基準上皆為最強的開源 4B 視覺語言電腦使用智能體，並與專有系統具競爭力。
- **Orchard-Claw 個人助理智能體方案**：僅以 0.2K 個合成任務，即在 Claw-Eval 上達到 59.6% pass@3，搭配 ZeroClaw 執行框架更提升至 73.9%，驗證極少量合成數據亦能驅動有效的個人助理能力。
- **跨領域可重用性驗證**：以單一環境層同時支撐軟體工程（Software engineering）、網頁導航（Web navigation）、通用電腦使用（General computer use）與個人助理四類任務，證明「環境層抽象」是實現跨域智能體數據、訓練方案與評估共享的關鍵設計。

### 適合對象
- 從事大型語言模型智能體化（Agentic modeling）研究，特別關注**訓練基礎設施、強化學習與監督微調結合、可擴展採樣**的研究者與工程師；
- 需要建構**程式碼智能體、GUI 智能體或個人助理智能體**的應用開發者與產品團隊；
- 關注**開源 vs. 專有智能體系統差距**、希望評估前沿混合專家模型（Frontier MoE）與開源方案實際表現的業界決策者；
- 對**沙盒執行環境（Sandboxed execution environment）、容器化訓練、評測基準設計**感興趣的機器學習系統與基礎設施研究者。

## 深度分析

#### 方法論解析

Orchard 的方法論核心在於提出一個「環境層解耦」(environment layer decoupling) 的系統設計哲學，將傳統上與訓練框架、推理後端、任務領域緊密耦合的沙盒管理抽象為獨立的微服務。這一設計選擇源於作者對現有系統瓶頸的精準識別：當環境管理被嵌入垂直整合的訓練堆疊（如 ProRL Agent、MegaFlow）或受限於託管沙盒平台（如 E2B、Daytona、Modal）時，上層的軌跡數據、訓練方案、評測流水線都會繼承這些約束，導致跨領域、跨執行框架 (harness)、跨訓練階段的可重用性喪失。

**Orchard Env 的架構設計**

Orchard Env 採用 Kubernetes 原生 (Kubernetes-native) 架構，透過 REST API 對外暴露五個通用原語 (generic primitives)：

1. **沙盒生命週期管理** (Sandbox lifecycle management)：負責容器 (container) 的建立、銷毀與狀態追蹤
2. **命令執行** (Command execution)：在沙盒內執行 shell 命令
3. **檔案 I/O** (File I/O)：雙向檔案傳輸
4. **網路策略** (Network policy)：控制沙盒的網路隔離
5. **REST API**：標準化介面

兩個關鍵的工程創新值得深入分析：

- **執行階段代理注入** (Runtime agent injection)：允許任意任務特定的 Docker 映像檔 (image) 獨立運行，避免將所有環境配置硬編碼到框架中。這使得同一個環境服務能同時支援程式碼倉庫、網頁瀏覽器、桌面應用、行動裝置等異質環境。
- **直接路由到沙盒 Pod IP**：繞過 Kubernetes 預設的 exec/WebSocket 機制，直接將執行與檔案請求路由到沙盒 Pod 的 IP 位址。這項設計將平均命令執行延遲降至 0.28 秒，並在 1,000 個沙盒的壓力測試中維持 100% 成功率。

此外，網路隔離、非同步生命週期管理、心跳清理 (heartbeat cleanup)、基於 watch 機制的就緒追蹤等設計，共同確保了系統在大規模環境互動下的可組合性 (composability) 與實用性。

**三個智能體建模方案 (Agentic Modeling Recipes)**

在 Orchard Env 之上，作者構建了三個領域特定的訓練方案，每個都採用 SFT+RL 的兩階段訓練範式：

**Orchard-SWE（軟體工程智能體）**

從 MiniMax-M2.5 與 Qwen3.5-397B 蒸餾 (distill) 出 107K 條軌跡，並引入兩個關鍵技術：

- **信用分配監督微調** (Credit-assignment SFT)：傳統 SFT 僅從完全成功的軌跡學習，但這會浪費大量「部分正確」的軌跡。信用分配 SFT 識別未解決軌跡 (unresolved trajectory) 中的「有效片段」(productive segments)，從中學習，從而大幅提升數據利用率。
- **平衡自適應採樣** (Balanced Adaptive Rollout)：用於強化學習階段，平衡不同難度或類型的任務採樣比例，避免策略坍縮 (policy collapse)。

以 Qwen3-30B-A3B-Thinking 為基礎模型，Orchard-SWE 在 SWE-bench Verified 上達到 SFT 後 64.3%、SFT+RL 後 67.5% 的解決率，引入價值模型 (value model) 後更達到 73.0%，在同規模開源模型中達到最先進水平 (state of the art)。

**Orchard-GUI（電腦使用智能體）**

訓練一個 4B 參數的視覺語言模型 (VLM)，僅使用 0.4K 蒸餾軌跡與 2.2K 開放式任務 (open-ended tasks)。在 WebVoyager、Online-Mind2Web、DeepShop 三個基準上分別達到 74.1%、67.0%、64.0% 的成功率，平均 68.4%，成為最強的開源 GUI 智能體。

**Orchard-Claw（個人助理智能體）**

僅使用 0.2K 合成任務 (synthetic tasks) 訓練，在 Claw-Eval 上達到 59.6% 的 pass@3，搭配更強的 ZeroClaw 執行框架時達到 73.9%。

#### 實驗數據解讀

**SWE-bench Verified 性能分析**

從 Figure 1（左）可觀察到 Orchard-SWE 的關鍵定位：35B-A3B 規模的模型達到 73.0% 的解決率，接近參數量為其 10-30 倍的前沿混合專家模型 (frontier MoE)。具體而言：

- 超越同類開源模型：SWE-Master-32B-RL (61.4%)、OpenSWE-32B (62.4%)、SWE-Mirror-LM (52.2%)、SWE-Lego-32B (52.6%)、FrogBoss (54.6%)、daVinci-Dev-32B (56.1%)、SWE-Compressor (57.6%)、CoderForge-32B (59.4%)、Scale-SWE-Agent (64.0%)
- 接近更大模型：SWE-Fixer-72B (32.8%)、daVinci-Dev-72B (58.5%)、Kimi-Dev (60.6%)、OpenSWE-72B (66.0%)、MiniMax-M2 (69.4%)、MiniMax-M2.1 (74.0%)
- 與前沿模型差距縮小：Qwen3-Coder-Max (67.0%)、GLM-4.7 (73.8%)、DeepSeek-V3.2 (73.1%)、Kimi-K2-Think (71.3%)、Qwen3.5-A17B (76.4%)、GLM-5 (77.8%)

值得注意的是，價值模型的引入帶來 +3.3 個百分點的提升（從 69.7% 到 73.0%），這顯示在 RL 階段引入價值估計能有效緩解信用分配問題，與信用分配 SFT 的設計理念形成互補。

**GUI 智能體性能分析**

Figure 1（右）顯示 Orchard-GUI 在三個 GUI 基準上的平均表現：

- 超越所有開源 VLM：Qwen3-VL-4B-Thinking (38.1%)、UI-TARS-1.5-7B (36.4%)、GLM-4.1V-9B (44.2%)、Fara-7B (44.6%)、MolmoWeb-4B (47.4%)、MolmoWeb-8B (51.9%)
- 與專有系統競爭：GPT-5 Axtree (51.1%)、OpenAI CUA (51.3%)、o3 SoM (61.5%)、GPT-5 SoM (65.8%)、Gemini-3 (61.9%)、Gemini CUA (69.3%)

4B 模型能達到 68.4% 的平均成功率，與 GPT-5 SoM (65.8%) 和 Gemini CUA (69.3%) 相當，這在參數效率上是驚人的表現。SFT+RL 相較於僅 SFT 帶來 +16.4 個百分點的提升（從 52.0% 到 68.4%），顯示 RL 階段對 GUI 智能體的決策品質有顯著增益。

**個人助理智能體性能分析**

Orchard-Claw 的數據點較少但具啟發性：僅用 0.2K 合成任務即從 31.7% 提升至 59.6% pass@3，搭配 ZeroClaw 執行框架更達到 73.9%。這顯示：(1) 合成任務在個人助理領域具有足夠的訓練信號；(2) 執行框架的選擇對最終性能有顯著影響（+14.3 個百分點）。

**基礎設施性能數據**

- 平均命令執行延遲：0.28 秒
- 1,000 沙盒壓力測試：100% 成功率
- 成本效益：相較 E2B 和 Daytona 低 2 倍（使用 spot 實例時低 10 倍）
- 與直接 Docker 基準相比：無性能回歸

這些數據共同支撐了「輕量級、開放、與執行框架無關的環境層」的實用性主張。

#### 與現有研究的比較

**與託管沙盒平台的比較**

E2B、Daytona、Modal 等託管平台提供便利的託管執行環境，但研究者對基礎設施配置、成本、可重現性的控制有限。Orchard 的優勢在於：(1) 完全開源，可本地部署；(2) Kubernetes 原生，易於水平擴展；(3) 成本降低 2-10 倍。然而，託管平台的「零設定」優勢在中小規模實驗中仍有吸引力。

**與垂直整合訓練堆疊的比較**

ProRL Agent 和 MegaFlow 將環境管理作為更大採樣或訓練系統的一部分，與推理排程、獎勵計算、訓練迴圈編排緊密耦合。這種設計在單一團隊內可能更高效，但限制了跨團隊的可重用性。Orchard 的「薄服務邊界」(thin service boundary) 設計明確將環境層與訓練層解耦，使數據、訓練方案、評測流水線可在不同執行框架間移植。

**與通用環境框架的比較**

ROCK 提供豐富的平台功能，但未將環境層隔離為最小服務邊界。Orchard 的設計哲學更接近「Unix 哲學」：做一件事並做好它。這使得 Orchard Env 能作為基礎設施被多個訓練框架共享。

**與特定領域智能體的比較**

在 SWE 領域，Orchard-SWE 的 73.0% 超越了所有同規模開源模型，但需注意 MiniMax-M2.1 (74.0%) 和 GLM-4.7 (73.8%) 等更大模型仍略佔優勢。在 GUI 領域，Orchard-GUI 是最強的開源模型，但 Gemini CUA (69.3%) 仍略高於其 68.4%。這些差距可能源於：(1) 專有系統使用更大規模的內部數據；(2) 專有系統可能有更精細的執行框架整合。

**方法論的局限性**

1. **信用分配 SFT 的依賴**：需要可靠的「有效片段」識別機制，若識別錯誤可能引入噪聲
2. **平衡自適應採樣的調參**：採樣平衡策略需要領域知識，可能不通用
3. **環境層的抽象成本**：薄服務邊界雖帶來靈活性，但也增加了部署複雜度
4. **評測的單一性**：主要在 SWE-bench Verified、Claw-Eval 等基準上評估，泛化性需更多驗證

#### 可重現性評估

Orchard 在可重現性方面展現了明確的承諾：

**開源承諾**

論文標題明確標示「Open-Source」，並在多處強調框架的開放性。Orchard Env 作為核心基礎設施組件，其 Kubernetes 原生設計和 REST API 介面有利於社群部署與審查。

**數據可重用性**

由於環境層與訓練層解耦，從 Orchard-SWE 蒸餾的 107K 軌跡、Orchard-GUI 的 0.4K 軌跡與 2.2K 任務、Orchard-Claw 的 0.2K 合成任務，都可在不同執行框架下重用。這是相較於垂直整合系統的重要優勢。

**模型權重可用性**

雖然摘要未明確說明模型權重的釋出計畫，但作為 Microsoft Research 的開源框架，預期會在 Hugging Face 或 GitHub 上釋出 Orchard-SWE、Orchard-GUI、Orchard-Claw 的模型權重。建議作者在正式版本中明確聲明權重釋出時間表與許可證。

**評測可重現性**

SWE-bench Verified、WebVoyager、Online-Mind2Web、DeepShop、Claw-Eval 均為公開基準，評測結果可被獨立驗證。Orchard Env 的標準化介面使得評測流水線可在不同基礎設施上重現。

**待改進之處**

1. 應提供完整的部署文檔與 Docker Compose / Helm Chart
2. 應釋出訓練數據的具體格式與採樣腳本
3. 應提供基準測試的詳細配置（如隨機種子、硬體規格）
4. 應說明 RL 訓練的超參數與獎勵設計細節

#### 未來研究方向

**環境層的進一步抽象**

當前的 Orchard Env 支援程式碼、網頁、桌面、行動裝置等環境，但個人助理領域涉及更複雜的權限管理與多應用協調。未來可探索：(1) 統一的身分與權限管理原語；(2) 跨應用的狀態共享機制；(3) 持久化環境狀態以支援長時任務。

**信用分配機制的理論深化**

信用分配 SFT 的成功引發了更深層的問題：如何自動識別軌跡中的「有效片段」？這涉及：(1) 基於反事實推理 (counterfactual reasoning) 的片段重要性估計；(2) 結合過程獎勵模型 (process reward model) 的細粒度信用分配；(3) 將信用分配思想擴展至多智能體協作場景。

**平衡自適應採樣的理論基礎**

Balanced Adaptive Rollout 的經驗成功需要理論支撐。未來可探索：(1) 採樣策略與策略熵 (policy entropy) 的動態平衡；(2) 基於課程學習 (curriculum learning) 的難度調度；(3) 多任務 RL 中的採樣比例優化。

**跨領域遷移學習**

三個領域的方案各自獨立訓練，但程式碼、GUI、個人助理之間存在結構性相似性（如工具調用、規劃推理）。未來可探索：(1) 跨領域的軌跡蒸餾；(2) 共享的規劃與推理模組；(3) 統一的智能體基礎模型。

**價值模型的進一步利用**

Orchard-SWE 中價值模型帶來 +3.3 個百分點的提升，顯示其在 RL 中的潛力。未來可探索：(1) 將價值模型蒸餾至策略模型以加速推理；(2) 結合樹搜索 (tree search) 與價值估計；(3) 在多輪對話中維護長期價值估計。

**安全與對齊**

智能體在沙盒中執行任意程式碼、操控 GUI、存取個人數據，這帶來新的安全風險。未來可探索：(1) 沙盒內的行為監控與異常檢測；(2) 基於形式化驗證 (formal verification) 的安全約束；(3) 對齊微調 (alignment fine-tuning) 與智能體能力的平衡。

**基準與評測的擴展**

現有基準（如 SWE-bench Verified）可能無法完全反映真實場景的複雜度。未來可探索：(1) 多步驟、長時程的真實任務基準；(2) 對抗性測試以評估魯棒性；(3) 人類專家對比的細粒度評估。

**與其他開源生態的整合**

Orchard 可與現有的開源生態（如 Hugging Face Transformers、vLLM、DeepSpeed）整合，降低採用門檻。同時，可探索與 OpenHands、AutoGen 等智能體框架的互操作性，形成更豐富的開源智能體生態。

## 論文問答

**Q1：這篇論文試圖解決的核心問題是什麼？**
A：這篇論文聚焦於「智能體建模」（agentic modeling）領域中基礎設施與訓練流程的瓶頸問題。隨著大型語言模型被賦予規劃、推理、工具使用與多輪互動的能力，訓練這類自主代理需要產生大量採樣軌跡，每條軌跡都涉及在隔離容器中執行的數十次連續互動。作者指出，當環境層封閉或與特定訓練堆疊緊密耦合時，上層的訓練方案、評測流水線與軌跡資料都會繼承這些限制，導致研究難以重現、比較或重用。

**Q2：為什麼現有的開源框架無法有效解決這個問題？**
A：現有方案在環境管理的位置上各有取捨，但都未能將環境層隔離為一個輕量、可重用的服務邊界。託管沙盒平台（如 E2B、Daytona、Modal）雖提供便利的託管執行環境，但研究人員對基礎設施配置、成本與可重現性的控制有限；垂直整合的訓練堆疊（如 ProRL Agent、MegaFlow）將環境管理與推理調度、獎勵計算、訓練迴圈編排耦合在一起；更廣泛的環境框架（如 ROCK）雖然功能豐富，但並未將環境層抽象為最小化的服務介面。因此，軌跡資料集、訓練方案與評測流水線往往被綁定在特定的執行框架或基礎設施實作上，難以跨領域重用。

**Q3：為什麼作者認為「環境層」是基礎性的瓶頸？**
A：作者主張環境層應是一個「薄而獨立的服務」，並在三個軸向上可重用：跨任務領域、跨領域內的智能體執行框架、以及跨流水線階段（包括軌跡蒸餾、在策略強化學習採樣與評測）。當這個邊界乾淨清晰時，上層的資料、訓練方案與評測就能彼此解耦——例如資料可在一個執行框架下收集、在另一個執行框架下評測；SFT 與 RL 方案可共用同一個執行後端；新領域也能直接複用既有基礎設施，而無需從頭重建。這種解耦對於學術研究的可重現性與跨實驗室比較至關重要。

**Q4：Orchard Env 的核心設計是什麼？它提供了哪些可重用原語？**
A：Orchard Env 是一個 Kubernetes 原生的輕量級環境服務，透過 REST API 對外暴露通用的原語，包括沙盒生命週期管理、命令執行、檔案 I/O、網路政策以及輕量級的代理注入機制。其核心設計理念是「不與任何智能體執行框架、訓練器、推理後端或任務領域耦合」，因此可以同時支援異質的任務環境（程式碼倉庫、網頁、桌面、行動裝置、個人助理工作流等）。在效能上，它達到了 0.28 秒的平均命令執行延遲，並在 1,000 個沙盒的壓力測試中維持 100% 成功率。

**Q5：Orchard 在可擴展性上有哪些關鍵的設計選擇？**
A：Orchard Env 透過兩個關鍵機制實現高效擴展。第一是「執行階段代理注入」（runtime agent injection），允許任意任務特定的 Docker 映像檔獨立運作，從而支援異質環境；第二是將執行與檔案請求直接路由到沙盒 Pod 的 IP 位址，避免 Kubernetes exec/WebSocket 帶來的額外負擔。此外，系統還結合了網路隔離、非同步生命週期管理、心跳清理機制與基於 watch 的就緒追蹤，使整體架構在大規模環境互動下既靈活又實用。成本方面，相較於 E2B 與 Daytona 等替代方案，Orchard Env 估計可降低約 2 倍成本，搭配 spot 執行個體更可達到約 10 倍的成本優勢。

**Q6：論文中提出的三個智能體建模方案分別針對什麼任務？它們如何與 Orchard Env 組合？**
A：三個方案分別針對不同的應用領域：Orchard-SWE 針對軟體工程智能體，從 MiniMax-M2.5 與 Qwen3.5-397B 蒸餾 107K 條軌跡，並引入信用分配 SFT 與平衡自適應採樣進行強化學習；Orchard-GUI 訓練 4B 參數的視覺語言電腦使用智能體，僅使用 0.4K 蒸餾軌跡與 2.2K 開放式任務；Orchard-Claw 則針對個人助理智能體，僅用 0.2K 合成任務訓練。三者都以「與環境服務組合但不緊密耦合」的方式構建，共享同一套基礎設施，卻能在資料準備、訓練策略與評測指標上各自獨立演化，展現了 Orchard 框架的模組化與可重用性。

**Q7：論文中使用了哪些主要的評測基準？**
A：論文在三個領域分別採用了對應的標準評測。Orchard-SWE 使用 SWE-bench Verified 來衡量軟體工程任務的解決率，並在後續版本中也評測了 SWE-Bench Multilingual；Orchard-GUI 在 WebVoyager、Online-Mind2Web 與 DeepShop 三個基準上測試網頁導航與電腦使用能力；Orchard-Claw 則使用 Claw-Eval 評測個人助理任務，並透過 pass@3 與搭配 ZeroClaw 執行框架的方式呈現結果。這些基準橫跨程式碼、GUI 與個人助理三大領域，驗證了 Orchard 框架的跨領域適用性。

**Q8：Orchard 在各領域取得了哪些關鍵成果？**
A：在 SWE-bench Verified 上，從 Qwen3-30B-A3B-Thinking 起步的 Orchard-SWE 在 SFT 後達到 64.3%，SFT+RL 後達到 67.5%，搭配價值模型後更達到 73.0%，在相近規模的開源模型中創下新紀錄，並逼近規模大 10–30 倍的前沿混合專家模型。Orchard-GUI（4B）在 WebVoyager、Online-Mind2Web 與 DeepShop 上分別達到 74.1%、67.0% 與 64.0% 的成功率，平均 68.4%，成為最強的開源 GUI 智能體，並與 OpenAI、Google 的專有系統相當。Orchard-Claw 在 Claw-Eval 上達到 59.6% 的 pass@3，搭配 ZeroClaw 執行框架後更提升至 73.9%，相較基礎模型帶來 +19.9 的顯著改進。

**Q9：論文中有哪些消融實驗或經驗性驗證？**
A：論文透過多項實證來支撐設計選擇。在基礎設施層面，Orchard Env 報告了 0.28 秒的平均命令執行延遲、1,000 沙盒壓力測試 100% 成功率，以及相較於 E2B/Daytona 約 2 倍的成本優勢（搭配 spot 執行個體可達 10 倍）。在訓練方法層面，Orchard-SWE 比較了 SFT、SFT+RL 與加入價值模型後的差異，顯示 RL 與價值模型對最終效能都有明顯貢獻；Orchard-GUI 同樣比較了 SFT 與 SFT+RL 的結果（52.0% vs 68.4%），驗證了強化學習階段的價值。此外，Orchard-Claw 透過搭配不同強度的執行框架（基礎 vs ZeroClaw）展示了執行框架對最終表現的影響。

**Q10：Orchard 框架適用於哪些實際應用場景？**
A：Orchard 適用於任何需要大規模產生採樣軌跡並進行監督微調或強化學習的智能體訓練場景。具體而言，它已驗證於三大場景：軟體工程（自動修復程式碼倉庫中的 issue）、網頁與 GUI 自動化（跨網站導航、線上購物等開放式任務）、以及個人助理任務（涵蓋生產力工具的操作）。由於環境層與任務領域解耦，研究人員也可以將其推廣到桌面應用自動化、行動裝置控制、機器人等更廣泛的領域，只需提供對應的 Docker 映像檔即可複用整個訓練與評測基礎設施。

**Q11：在工程實作上，Orchard 考慮了哪些產品化與可維運性因素？**
A：Orchard Env 在設計上明確考慮了可維運性與成本效益。它採用 Kubernetes 原生架構以支援自動擴展，並透過直接路由到 Pod IP 避免額外開銷，使平均命令執行延遲僅 0.28 秒。系統還內建網路隔離、非同步生命週期管理、心跳清理與基於 watch 的就緒追蹤等機制，以確保大規模部署下的穩定性。在成本方面，相較於商業託管沙盒平台可節省約 2 倍開銷，搭配 spot 執行個體更可達 10 倍成本優勢，這對於需要數千個並行環境的學術研究尤其重要。

**Q12：Orchard 對智能體研究領域的整體影響是什麼？**
A：Orchard 的核心貢獻在於將「環境層」確立為一個獨立、可重用的服務邊界，從而打破現有開源生態中資料、訓練方案與評測彼此綁定的困境。這種解耦使得跨實驗室的研究比較與重現變得更容易，也降低了新領域進入智能體研究的門檻——研究者只需專注於資料策略與訓練演算法，而無需從頭建置沙盒基礎設施。從更宏觀的角度看，Orchard 推動了智能體建模領域走向「基礎設施共用、創新發生在上層」的成熟分工模式，有助於加速整個領域的迭代速度。

**Q13：論文承認了哪些限制？**
A：雖然 Orchard 框架在三大領域都取得了領先成果，但論文也坦誠存在若干限制。首先，雖然環境層被設計為與執行框架無關，但實際驗證僅限於三個特定領域（軟體工程、GUI、個人助理），尚未涵蓋機器人、嵌入式系統或更複雜的多模態環境。其次，蒸餾軌跡的品質高度依賴來源模型（MiniMax-M2.5、Qwen3.5-397B 等），若來源模型在特定領域表現不佳，下游模型的表現也會受到限制。此外，雖然成本估算顯示 Orchard 比商業方案更便宜，但實際部署仍需 Kubernetes 叢集資源，對小型研究團隊可能仍有進入門檻。

**Q14：Orchard 在哪些情況下可能會失敗或表現不佳？**
A：從實驗結果可以推論出幾個潛在的失敗情境。在軟體工程任務中，Orchard-SWE 雖然在 SWE-bench Verified 上表現優異，但對於需要極長推理鏈或跨多個檔案複雜重構的問題，可能仍會受限於基礎模型（Qwen3-30B-A3B-Thinking）的容量。在 GUI 任務中，Orchard-GUI 僅有 4B 參數，雖然在多項基準上表現出色，但對於高度視覺化或需要精細操作的場景（如複雜圖表編輯、CAD 軟體），可能仍不如更大的專有系統。此外，當任務環境需要特殊硬體（如 GPU 加速、特殊周邊裝置）或非標準網路政策時，現有的環境原語可能需要進一步擴充。

**Q15：基於這篇論文，未來有哪些值得探索的方向？**
A：未來的研究方向可從幾個維度展開。在基礎設施層面，可以將 Orchard Env 擴展到更多異質環境（如機器人模擬器、遊戲引擎、IoT 裝置），並探索更細粒度的資源排程與成本優化策略。在訓練方法層面，信用分配 SFT 與平衡自適應採樣的組合已被證明有效，可以進一步研究其在多輪對話、長序列推理等更複雜任務中的泛化能力。此外，跨領域的遷移學習（例如將軟體工程的能力遷移到 GUI 操作）也是一個值得探索的方向。最後，建立標準化的跨領域評測基準與共享軌跡資料庫，將有助於整個社群進行更公平、更可重現的比較研究。

### 實作前置條件

**資料需求**
- 領域任務定義與評估腳本（建議至少 1K 筆種子任務）
- 蒸餾來源模型存取權限（Orchard-SWE 使用 MiniMax-M2.5 與 Qwen3.5-397B；GUI 領域需視覺語言教師模型）
- 基礎模型權重（Qwen3-30B-A3B-Thinking、Qwen3-VL-4B-Thinking 等）
- 任務環境映像檔（Docker image，含相依套件、測試套件）

**運算資源**
- Kubernetes 叢集（建議 ≥50 節點，每節點 8+ GPU）以支撐 1,000 並發沙盒
- 訓練用 GPU 叢集：30B 級 SFT/RL 建議 ≥64 張 H100；4B VLM 建議 ≥16 張 A100/H100
- 物件儲存（用於軌跡、檢查點、容器映像快取）
- 內部映像檔倉庫（避免依賴外部 registry）

**技能門檻**
- Kubernetes 與容器編排（Pod、Service、NetworkPolicy）
- 分散式訓練經驗（FSDP、DeepSpeed、vLLM/SGLang 推論）
- 強化學習基礎（PPO/GRPO、獎勵塑形、信用分配）
- 領域任務設計能力（環境建構、評估指標定義）

### 實作步驟建議

**階段一：環境層部署（2–4 週）**
1. 在 Kubernetes 叢集部署 Orchard Env，啟用 spot instance 與自動擴縮。
2. 設定 NetworkPolicy 隔離沙盒網路，避免資料外洩與外部攻擊。
3. 整合內部映像檔倉庫，預先建置任務專用 Docker image。
4. 執行 1,000 沙盒壓力測試，驗證延遲（目標 <0.3s）與成功率（目標 100%）。

**階段二：軌跡收集（3–6 週）**
1. 選定教師模型與目標領域，定義任務 schema 與評估函式。
2. 透過 Orchard Env 的 REST API 並行採集軌跡（Orchard-SWE 107K、Orchard-GUI 0.4K 蒸餾 + 2.2K 開放式）。
3. 過濾失敗軌跡，標記「未解決但有有效片段」的軌跡供信用分配 SFT 使用。
4. 建立資料版本控制與可重現的資料切分。

**階段三：監督微調（2–4 週）**
1. 採用 credit-assignment SFT，從未解決軌跡中萃取有效片段進行學習。
2. 設定學習率、排程與檢查點策略；對 30B 級模型使用 FSDP。
3. 在驗證集上監控，並與基準模型（如 Qwen3-30B-A3B-Thinking）比較。

**階段四：強化學習（2–4 週）**
1. 採用 Balanced Adaptive Rollout 平衡採樣難度分布。
2. 整合獎勵訊號（SWE 任務用測試通過率；GUI 任務用任務完成度）。
3. 監控 KL 散度與獎勵 hacking 跡象，必要時加入價值模型（Orchard-SWE 達 73.0%）。

**階段五：評估與上線（2–3 週）**
1. 在領域標準評測集（SWE-bench Verified、WebVoyager、Claw-Eval）上驗證。
2. 與既有執行框架（如 ZeroClaw）解耦測試，確認 harness-agnostic 特性。
3. 灰度上線，設置人工審核與回退機制。

| **訓練成本失控** | 使用 spot instance、自動擴縮、軌跡去重、優先使用小型蒸餾資料集（Orchard-GUI 僅用 0.4K 軌跡即達 SOTA） |
| **獎勵 hacking** | 多樣化獎勵訊號、定期人工抽樣、價值模型輔助、限制單一指標優化 |
| **評估過擬合** | 保留未見過的 hold-out 評測集、跨執行框架評估、實務任務 A/B 測試 |
| **軌跡品質不均** | 教師模型篩選、難度分層、自動品質評分（成功率、步驟效率） |
| **環境映像檔膨脹** | 多階段建置、定期清理、共享基礎層、版本標籤管理 |
| **模型幻覺導致破壞性操作** | 限制可呼叫工具、強制人類確認關鍵動作、執行前 dry-run |

### 與其他技術的整合建議

**與 CI/CD 整合**
- 將 Orchard-SWE 接入 GitHub Actions/GitLab CI，作為自動 PR 修復機器人
- 透過 webhook 觸發，僅在特定標籤（如 `auto-fix`）的 Issue 上啟動
- 評估結果回寫為 PR 評論與檢查狀態

**與推論框架整合**
- 訓練後匯出為 vLLM/SGLang 相容格式
- 使用 OpenAI 相容 API 對接既有應用
- 對 GUI 領域採用視覺 token 壓縮以降低延遲

**與監控系統整合**
- 整合 Prometheus + Grafana 監控沙盒延遲、成功率、GPU 使用率
- 軌跡與評估結果寫入 MLflow 或 Weights & Biases
- 異常行為告警（重複失敗、異常長軌跡）

**與企業系統整合**
- 透過 MCP（Model Context Protocol）或自訂工具層串接 ERP、CRM、知識庫
- 使用 SSO 與權限控管限制可存取資源
- 審計日誌符合合規要求（GDPR、ISO 27001）

**與其他智能體框架整合**
- 因 Orchard Env 為 harness-agnostic，可同時搭配 LangChain、AutoGen、OpenHands 等框架評估
- 資料可在不同 harness 間復用，降低遷移成本

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀第 1 節（Introduction）理解「為什麼需要獨立的環境層」，再跳讀圖 2 的 Orchard 總覽。實際操作上，可先在個人電腦用 Docker 跑通單一沙盒範例，再逐步理解 Kubernetes 部署。暫時跳過 RL 章節，專注 SFT 與軌跡收集流程。

**給 AI 工程師**：重點關注 Orchard Env 的架構設計（runtime agent injection、Pod IP 直連、heartbeat 清理），這些是支撐 1,000 並發沙盒的關鍵工程決策。仔細研究 credit-assignment SFT 與 Balanced Adaptive Rollout 的實作細節，這兩個是論文的核心方法論貢獻。建議直接閱讀程式碼並在內部環境復現壓力測試。

**給研究者**：論文的核心論點是「環境層應為薄而獨立的服務」，這對智能體基礎設施研究有方法論意義。建議深入分析三個領域（SWE、GUI、Claw）的資料效率差異——為何 GUI 僅需 0.4K 軌跡而 SWE 需要 107K？這與任務結構、獎勵稀疏度、視覺模組複雜度有關，是值得延伸的研究方向。

**給產品經理**：聚焦圖 1 的效能對比與圖 2 的成本數據（比 E2B/Daytona 低 2 倍成本）。Orchard-SWE 以 30B 模型逼近 10–30 倍大的前沿 MoE 系統，代表極佳的性價比。Orchard-GUI 在 4B 等級即與 GPT-5、Gemini-3 等專有系統持平，意味著可在邊緣裝置部署。建議評估自家場景的任務複雜度，選擇對應的領域方案，並預留 3–6 個月導入週期。
