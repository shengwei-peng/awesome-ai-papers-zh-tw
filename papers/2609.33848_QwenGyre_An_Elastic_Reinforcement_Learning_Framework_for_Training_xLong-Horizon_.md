## ⚡ TL;DR

本文解決極長期線上 RL 智慧體因執行變異與分支軌跡導致的 GPU 閒置與訓練冗餘問題。
提出 QwenGyre 框架，以彈性 GPU 排程與軌跡處理器重構分支歷史並控制訓練成本。
在 NL2RepoBench 上使 Qwen 3.8 2.4T 絕對提升 6.0%，並較基線加速達 1.85 倍。

## 摘要翻譯

大型語言模型（Large Language Model, LLM）智慧體日益承擔 xLong-Horizon（極長期）任務，單次執行可長達數小時、包含數百次模型–環境互動（model–environment interactions），且每條 rollout（軌跡展開）處理近百萬個 token（詞元）。將線上強化學習（Online Reinforcement Learning, RL）應用於此類執行帶來兩項根本挑戰：（1）嚴重的執行變異性（execution variance）與漫長的 rollout 延遲（rollout delays）導致大量 GPU 閒置（GPU idling）；（2）複雜的非線性分支（non-linear branching）產生大量軌跡冗餘（trajectory redundancy），嚴重削弱訓練效率。為解決這些問題，我們提出 QwenGyre，一個用於 xLong-Horizon 線上 RL 的端到端框架（end-to-end framework）。QwenGyre 能在 rollout 與訓練之間進行彈性 GPU 重新分配（elastic GPU reallocation），且不中斷進行中執行（live executions）；其軌跡處理器（trajectory processor）則重建分支歷史（branching histories）、對部分進度（partial progress）進行評分，並去除冗餘路徑（deduplicate redundant paths）以控制訓練成本。規模擴展至我們的旗艦模型 Qwen 3.8 2.4T，每條 rollout 達 70 萬個 token，QwenGyre 在 NL2RepoBench 上於 48 個步驟內帶來 6.0% 的絕對提升（absolute gain）（從 52.5% 提升至 58.5%）。在橫跨多個訓練資料集領域的評估中，QwenGyre 相較於 Colocate（同地部署基線）與 Async（非同步基線）分別帶來最高 1.85 倍與 1.78 倍的加速比（speedup）。

### 核心貢獻（3～5點）
- 提出 QwenGyre，一個端到端（end-to-end）的 xLong-Horizon 線上強化學習框架，能在 rollout（軌跡展開）與訓練之間彈性 GPU 重新分配（elastic GPU reallocation），且不中斷進行中執行（live executions），顯著降低 GPU 閒置。
- 設計軌跡處理器（trajectory processor），可重建分支歷史（branching histories）、評分部分進度（partial progress），並去除冗餘路徑（deduplicate redundant paths），從而控制訓練成本並提升訓練效率。
- 將方法擴展至旗艦模型 Qwen 3.8 2.4T，在 NL2RepoBench 上僅用 48 個步驟即達成 6.0% 的絕對提升（absolute gain）（52.5% → 58.5%）。
- 在橫跨多個訓練資料集領域的評估中，相較 Colocate（同地部署基線）與 Async（非同步基線）分別取得最高 1.85 倍與 1.78 倍的加速比（speedup）。

### 適合對象
適合對大型語言模型（LLM）智慧體、線上強化學習（RL）、長期決策與軟體工程任務（如儲存庫生成、issue 修復）感興趣的研究者與系統工程師，特別是關注大規模分散式訓練、GPU 排程與軌跡效率最佳化的讀者。

## 深度分析

#### 方法論解析

QwenGyre（彈性強化學習框架）的核心設計可拆解為兩大支柱：**彈性排程器（elastic scheduler）** 與 **軌跡處理器（trajectory processor）**。兩者分別對應 xLong-Horizon（極長期）線上強化學習（online RL）在系統層與資料層的瓶頸。

##### 1. 彈性排程器：解耦 harness 執行、GPU 角色與訓練樣本的生命週期

傳統的 **Colocate（同地部署基線）** 設計讓 GPU 池在 rollout（軌跡展開）與訓練之間交替：所有 rollout 完成後才進行訓練。這在 xLong-Horizon 下會因 **執行變異性（execution variance）** 產生嚴重的 **GPU 閒置（GPU idling）**——少數 trailing rollout 卡住，整個訓練批次被迫等待。相對地，**Async（非同步基線）** 將 GPU 靜態劃分為專屬 rollout 池與訓練池，但當訓練批次等待時間超過一個訓練步（training step）時，訓練 GPU 同樣會空轉，且剛性分割使兩邊無法互相借用容量。

QwenGyre 的彈性排程器採取三項機制：

- **依未完成 rollout 工作量動態調整 GPU 分配**：監控 **未完成的 rollout 工作（unfinished rollout work）** 數量，將閒置 GPU 從 rollout 轉為訓練，或反向支援正在進行的 rollout。
- **進行中執行（live executions）的模型呼叫不中斷**：由於黑箱智慧體 harness（black-box agent harness）不提供通用 checkpoint/resume 機制，若模型呼叫無法被服務，harness 可能停擺或逾時，導致任務結果與策略決策無關。因此排程器在重新分配 GPU 角色時，必須持續維持 inference 服務。
- **集中式資料平行訓練（centralized data-parallel training）與串流訓練（streaming training）**：新釋出的 GPU 可即時加入正在進行的訓練批次；訓練工作依各 **資料平行群組（data-parallel group）** 的進度動態分配，使各群組盡可能在相近時間完成同一批次，縮小 **閒置間隙（idle gaps）**。

這種「彈性 GPU 重新分配（elastic GPU reallocation）」本質上把 rollout 與訓練從同步閘道（synchronization barrier）中解放出來，讓 GPU 利用率成為首要最佳化目標，而非固定階段順序。

##### 2. 軌跡處理器：從非線性分支執行中重建可訓練資料

xLong-Horizon 任務（如 repository generation、system reimplementation、codebase-wide refactoring）通常由黑箱 harness 驅動，會進行歷史壓縮（compaction）、子任務委派（sub-agent delegation）、重試（retry）等操作。這使得單次任務執行不再是一條線性序列，而是一棵 **軌跡樹（trajectory tree）**：每個 **模型呼叫（model call）** 是節點，工具呼叫或子代理觸發則產生分支。

軌跡處理器的工作流程：

- **保留條件化上下文（conditioning context）**：將每次模型呼叫與其產生時所依據的原始上下文綁定，避免把分支後的錯誤上下文當成生成目標的條件。
- **評估部分進度（partial progress）**：任務可能逾時或被終止，此時仍須給出 **任務專屬評估分數（task-specific evaluation scores）**，以保留已完成的有效工作。
- **角色優先順序（role priority）** 選擇軌跡：每個執行只選出固定數量的軌跡，控制訓練成本。優先順序可依主代理軌跡、子代理軌跡、摘要呼叫等角色區分。
- **訓練目標與損失聚合**：
  - 僅使用 **策略生成的目標（policy-generated targets）** 進行訓練；
  - **共享前綴（shared prefixes）** 對應的輸出只計算一次損失，避免重複 token 造成梯度膨脹；
  - 對每個執行內的 **token 損失（token losses）** 做 **執行層級平均（execution-level averaging）**，防止路徑較多的執行在批次中佔據過高權重。

這套設計把「軌跡冗餘（trajectory redundancy）」從指數級壓回到可控範圍，同時維持每個模型輸出與其原始生成條件的一致性。

##### 3. 整體訓練流程

論文採用 **burst（爆發訓練區間）** 概念：每個 burst 執行 µ 個連續 **訓練步驟（training steps）**，然後發布新權重。每個訓練步驟消耗 B 個 **rollout group（rollout 群組）**，並將策略（policy）版本推進一次。一個 rollout group 可展開為多條訓練軌跡（training trajectories）。QwenGyre 在 burst 內部透過彈性排程器與軌跡處理器，把長時間、高變異的 harness 執行轉換為穩定、低冗餘的訓練批次。

#### 實驗數據解讀

##### 1. 評測基準與模型

論文在以下基準進行評估：

- **NL2RepoBench**：自然語言到程式碼儲存庫生成（repository generation）任務，屬於典型 xLong-Horizon 場景。
- **DeepSWE**：軟體工程問題解決任務，延伸自 SWE-bench 的長期決策設定。
- **TerminalBench**：終端機環境下的長期互動任務。

模型方面：

- **Qwen 3.6 122B**：用於多領域比較實驗。
- **Qwen 3.8 2.4T**：旗艦模型，用於展示大規模 xLong-Horizon RL 的最終效益。

##### 2. 主要結果

| 指標 | 數值 | 意義 |
|---|---|---|
| NL2RepoBench 分數（Qwen 3.8 2.4T） | 52.5% → 58.5% | **絕對提升（absolute gain）** 6.0%，僅用 48 個訓練步驟 |
| 相對於 Async 加速比 | 1.38×–1.78× | 在相同 staleness 限制與相等 GPU 預算下，端到端時間縮短 |
| 相對於 Colocate 加速比 | 1.21×–1.85× | 同樣條件下，彈性調度優於同步交替與靜態分割 |
| 訓練分數匹配 | 與基線相當 | 加速並未犧牲策略品質 |

##### 3. 數據意涵

- **6.0% 絕對提升在 48 步內達成**：對於每條 rollout 高達 700K token、總互動可達數百步的任務，這顯示 online RL 仍能快速收斂。這可能歸因於軌跡處理器有效保留了高品質的 policy-generated targets，並透過執行層級平均避免少數長軌跡主導梯度。
- **加速比範圍寬（1.21×–1.85×）**：差異反映不同工作負載的 **執行變異性** 與分支程度。當 rollout 時間長尾越嚴重、分支越多，Colocate 與 Async 的閒置與冗餘問題越突出，QwenGyre 的優勢越大。
- **相同 staleness 限制**：這點很重要——Async 通常以允許較高 staleness 換取吞吐，但論文在相同 staleness 下仍勝出，說明彈性排程器提升的是「有效吞吐」而非犧牲梯度新鮮度。

##### 4. 潛在實驗限制

- 僅報告 48 個訓練步驟的結果，長期收斂曲線與過擬合風險未完全揭露。
- 主要旗艦實驗集中在 NL2RepoBench，DeepSWE 與 TerminalBench 的詳細數據與誤差範圍未於摘要中呈現。
- 未明確說明「角色優先順序」的具體規則與超參數（如每執行選取軌跡數量），這影響方法的可移植性。

#### 與現有研究的比較

##### 1. 相較於 Colocate 與 Async 基線

- **Colocate（Sheng et al., 2025; Mei et al., 2025）**：同步交替 rollout 與訓練，實作簡單，但在 xLong-Horizon 下被長尾 rollout 嚴重拖累。QwenGyre 透過彈性 GPU 重新分配與串流訓練，把等待時間轉為有效訓練。
- **Async（Fu et al., 2025）**：靜態分割 GPU 池，雖可部分解耦 rollout 與訓練，但無法動態借用容量，且訓練 GPU 等待批次準備時仍會閒置。QwenGyre 的集中式資料平行與動態加入機制填補了這個缺口。

##### 2. 相較於其他 agentic RL 研究

- **SWE-bench / issue resolution（Jimenez et al., 2024; Deng et al., 2026）**：這些工作聚焦數十次互動的長期任務，QwenGyre 則把規模推到數百次互動、近百萬 token 的 **xLong-Horizon** 範疇。
- **Luo et al., 2025a; Golubev et al., 2025; Song et al., 2026b; Du et al., 2026b**：這些研究顯示 online RL 在軟體工程任務上的潛力，但未系統性處理多小時執行中的排程與分支問題。
- **He et al., 2026b; Song et al., 2026a**：提出黑箱 harness 與子代理/重試機制，QwenGyre 則進一步把這類非線性執行轉為可訓練的軌跡樹。

##### 3. 相較於軌跡處理相關工作

傳統 RL 假設軌跡是線性的（Yao et al., 2023; Yang et al., 2024）。QwenGyre 明確把執行視為 **分支歷史（branching histories）**，並透過共享前綴去重、執行層級平均等機制控制訓練成本。這與多路徑搜尋或 MCTS 中的軌跡壓縮概念有相似之處，但應用於黑箱 harness 的不可控分支。

##### 4. 主要限制與待釐清處

- **無通用 checkpoint/resume**：論文坦承黑箱 harness 不提供 checkpoint 機制，因此排程器必須持續服務模型呼叫。這也意味著若 GPU 節點故障，進行中執行可能無法恢復。
- **僅使用純策略目標與純量獎勵（scalar rewards）**：未引入學習的 value function（Shao et al., 2024），這可能限制對長期信用分配（long-term credit assignment）的細緻建模。
- **軌跡選擇的角色優先順序未公開細節**：不同任務可能需要不同選擇策略，泛化性有待驗證。

#### 未來研究方向

##### 1. 通用 checkpoint/resume 機制

當前設計受限於黑箱 harness 無法暫停與恢復執行。未來可探索：

- 在 harness 與 RL 框架之間建立標準化 checkpoint API；
- 對持久工作區進行版本化快照，使 rollout 可在不同 GPU 間遷移；
- 結合彈性排程器實現真正的 fault-tolerant xLong-Horizon RL。

##### 2. 學習 value function 與長期信用分配

目前僅使用純量獎勵與 policy-generated targets。引入學習的 value function 或 return decomposition，可更精細地評估部分進度，並改善多步決策中的信用分配。

##### 3. 更智慧的軌跡選擇與壓縮

角色優先順序可進一步發展為：

- 基於獎勵貢獻度或梯度影響力的軌跡選擇；
- 在軌跡樹上進行剪枝（pruning）與合併（merging）；
- 利用軌跡相似度進行主動去重，而非僅依賴共享前綴。

##### 4. 跨任務與跨領域泛化

論文主要聚焦軟體工程任務。未來可驗證：

- QwenGyre 在科學實驗、機器人控制、長文件生成等其他 xLong-Horizon 領域的適用性；
- 不同 harness 設計（如開放式 vs. 封閉式環境）對彈性排程與軌跡處理的影響。

##### 5. 理論與系統共同設計

- 建立 xLong-Horizon RL 的吞吐模型，量化執行變異性、分支度與 GPU 數量對收斂速度的影響；
- 設計自適應 burst 長度 µ 與批次大小 B，根據線上監控指標動態調整；
- 探索異構 GPU（inference-optimized vs. training-optimized）在彈性排程中的角色分工。

##### 6. 結合推論時間運算（inference-time compute）與 RL

xLong-Horizon 任務常涉及搜尋與規劃。未來可將 QwenGyre 與 test-time search、MCTS、best-of-N 取樣結合，並在軌跡處理器中統一管理搜尋樹與訓練軌跡，進一步提升樣本效率與最終效能。

## 論文問答

**Q1：什麼是 xLong-horizon 任務，為什麼它會讓線上強化學習變得困難？**  
A：xLong-horizon 任務指的是單次執行可能長達數小時、包含數百次模型與環境互動、並處理近百萬 token 的極長期智慧體任務，例如儲存庫生成或跨程式碼庫重構。這類任務的執行時間具有極大的長尾變異性，導致訓練必須等待最慢的 rollout 完成，GPU 因此長時間閒置。此外，執行過程中會因重試、子智慧體委派與歷史壓縮而產生大量非線性分支，使軌跡與 token 數量爆炸，進一步壓垮訓練管線。

**Q2：現有的 Colocate 與 Async 方法為何在 xLong-horizon 設定下失效？**  
A：Colocate 設計讓 GPU 池在 rollout 與訓練之間交替使用，但在 xLong-horizon 中，訓練會被阻塞到所有進行中的 harness 執行結束，少數長尾任務就會造成大量 GPU 閒置。Async 則把 GPU 靜態劃分為專屬池，但等待一個可訓練批次的時間可能遠超過單步訓練時間，而且剛性劃分使兩個階段無法利用彼此的閒置容量。這兩種方法都缺乏隨需求動態重新分配 GPU 的能力，也無法處理複雜的分支軌跡。

**Q3：為什麼需要專門針對 xLong-horizon 的線上 RL 框架？**  
A：隨著基礎模型的推理與長上下文能力快速進步，智慧體正朝向全自動端到端軟體開發發展，例如系統重實作、儲存庫生成與大規模重構，這些都是專案規模的長期執行。若沒有高效率的線上 RL 訓練管線，不僅 GPU 會因等待 rollout 而嚴重閒置，分支軌跡帶來的冗餘也會讓訓練成本變得難以負擔。QwenGyre 這類框架因此是讓大型智慧體能夠在真實軟體工程任務上持續迭代學習的關鍵基礎設施。

**Q4：QwenGyre 的核心設計理念是什麼？**  
A：QwenGyre 是一個端到端的線上 RL 框架，專門針對黑箱智慧體 harness 的極長期執行。它的核心設計是將 harness 執行的生命週期、GPU 角色與訓練樣本三者解耦，使進行中的執行狀態能夠跨越 GPU 角色變更而持續存在，而模型呼叫記錄則按需物化為訓練樣本。透過彈性排程器與軌跡處理器的協同運作，它同時解決了 GPU 閒置與軌跡冗餘兩大挑戰。

**Q5：QwenGyre 的彈性排程器如何減少 GPU 閒置？**  
A：彈性排程器會根據尚未完成的 rollout 工作量，動態調整 GPU 在 rollout 與訓練之間的分配，並確保進行中 harness 執行的模型呼叫持續被服務。它採用集中式資料平行訓練，讓新釋出的 GPU 能即時加入正在進行的訓練批次。同時，串流訓練會依據各資料平行群組的進度動態分配工作，使不同群組盡可能在相近時間完成同一批次，從而縮小閒置間隙。

**Q6：軌跡處理器如何處理非線性分支並控制訓練成本？**  
A：軌跡處理器把每次執行記錄到的模型呼叫組織成軌跡樹，利用共享前綴保留每個輸出的原始條件化上下文，避免重複展開相同路徑。它還會根據任務專屬評估分數，在任務終止或超時後評估可衡量的部分進度。當有效獎勵可用時，系統會依角色優先順序從每次執行中選出有限數量的軌跡，並對執行內的 token 損失取平均，防止路徑較多的執行過度影響策略更新。

**Q7：論文在哪些基準與模型上評估 QwenGyre？**  
A：論文在 NL2RepoBench、DeepSWE 與 TerminalBench 三個軟體工程相關基準上進行評估，主要使用 Qwen3.6 122B 模型。此外，作者還將 QwenGyre 應用於旗艦模型 Qwen3.8 2.4T，並在 NL2RepoBench 上進行極長期 RL 訓練。所有比較都在相同 GPU 預算與相同陳舊性約束下，與 Colocate 和 Async 兩種基線進行對照。

**Q8：QwenGyre 在實驗中取得了哪些關鍵結果？**  
A：在各種配置下，QwenGyre 相較 Async 達到 1.38 至 1.78 倍的端到端加速，相較 Colocate 達到 1.21 至 1.85 倍的加速，同時維持與基線相當的訓練分數。在 NL2RepoBench 上，Qwen3.8 2.4T 經過 48 個訓練步驟後，分數從約 52.5% 提升到 58.5%，帶來 6.0% 的絕對提升。這些結果顯示 QwenGyre 同時顯著提升了訓練效率與模型效能。

**Q9：這些實驗結果如何驗證 QwenGyre 各個設計選擇的價值？**  
A：與 Colocate 和 Async 的比較可視為對彈性排程器的消融驗證，證明動態 GPU 重新分配能有效減少因執行變異性造成的閒置。軌跡處理器則透過軌跡樹、共享目標只計算一次、以及執行層級平均等機制，證明它能控制非線性分支帶來的訓練成本。整體而言，這些設計共同確保了大量路徑與 token 不會壓垮訓練管線，同時仍保留有效的策略學習訊號。

**Q10：QwenGyre 適合應用在哪些實際場景？**  
A：QwenGyre 特別適合需要長時間、具狀態工作區與複雜決策的智慧體任務，例如 issue 修復、儲存庫生成、系統重實作與跨程式碼庫重構。任何使用黑箱 harness、執行過程會產生重試或子智慧體分支的 xLong-horizon 環境，都可以受益於它的彈性排程與軌跡處理。在實務上，這相當於為自主軟體工程智慧體提供可規模化的線上學習後端。

**Q11：在產品化部署時，QwenGyre 有哪些需要特別注意的考量？**  
A：由於黑箱 harness 通常不支援通用的檢查點與恢復機制，排程器必須持續為進行中的執行提供推論服務，否則模型呼叫中斷可能導致 harness 停擺或超時，進而改變任務結果。集中式資料平行訓練與串流負載平衡需要穩定的網路與路由機制，才能讓新加入的 GPU 順利參與正在進行的批次。此外，每個任務都需要定義適當的評估分數與部分進度衡量方式，才能讓軌跡處理器正確篩選訓練樣本。

**Q12：QwenGyre 對整個 LLM 智慧體與 RL 領域可能帶來什麼影響？**  
A：QwenGyre 把線上 RL 的適用範圍從相對短期的任務延伸到數小時、近百萬 token 的極長期執行，填補了現有框架在專案規模智慧體訓練上的空白。它透過解耦執行、GPU 角色與訓練樣本的生命週期，為未來更大規模、更複雜的智慧體訓練提供了可擴展的系統範式。這有助於加速自主程式設計、自動化軟體維護與其他需要長期規劃的 LLM 智慧體落地。

**Q13：QwenGyre 有哪些已知的限制？**  
A：論文假設 harness 是黑箱且無法進行通用檢查點與恢復，因此排程器必須持續維護進行中執行的推論服務，這限制了進一步縮短閒置時間的可能性。軌跡處理器需要任務專屬的評估分數來衡量部分進度，這意味著每個新任務都可能需要額外的評測基礎建設。此外，實際加速比會受到 rollout 變異性、GPU 總量與網路延遲等因素影響，並非在所有工作負載下都能達到最大值。

**Q14：在什麼情況下 QwenGyre 可能表現不佳或遇到失效案例？**  
A：如果所有 rollout 的執行時間非常接近、變異性很低，那麼彈性排程相較於同步基線的優勢就會明顯縮小。當執行分支極度密集且獎勵訊號稀疏時，依角色優先順序選擇有限軌跡可能會遺漏對策略學習有價值的路徑。另外，若網路或路由出現故障，導致進行中的 harness 執行無法持續獲得模型回應，這些執行可能會超時或產生與策略決策無關的失敗樣本，進而影響訓練品質。

**Q15：未來可以朝哪些方向進一步改進 QwenGyre？**  
A：未來可以為黑箱 harness 引入通用的檢查點與恢復機制，讓進行中的執行能夠在 GPU 角色切換後更安全地暫停與重啟，進一步降低閒置成本。也可以發展跨任務通用的部分進度估計器，減少對任務專屬評估分數的依賴。此外，將彈性排程擴展到異質 GPU 叢集、多智慧體協作場景，或結合離線經驗回放與世界模型來提升樣本效率，都是值得探索的方向。

## 實務應用指南

### 適用場景

1. **全自動端到端軟體開發**：適用於需要從自然語言需求直接生成完整程式碼儲存庫的任務，例如根據規格書產生可執行的專案結構、測試與文件。QwenGyre 能處理單次執行達數小時、近百萬 token 的專案規模執行。
2. **跨程式碼庫重構與系統重實作**：當智慧體需要在大型既有程式碼庫中進行多檔案修改、API 遷移或將舊系統重實作為新架構時，非線性分支與長期狀態管理是核心挑戰，QwenGyre 的軌跡處理器可有效組織分支歷史。
3. **複雜 Issue 修復（如 SWE-bench 類任務）**：針對需要定位 bug、修改程式碼、執行測試並驗證修復的長期軟體工程問題，框架可透過任務專屬評估分數與部分進度評估，在超時後仍能萃取訓練訊號。
4. **多步驟科學或資料分析工作流**：例如自動化實驗設計、大規模資料清理與特徵工程，這類任務具有高度執行變異性與環境互動，適合彈性 GPU 重新分配機制。
5. **需要持續線上學習的代理服務**：當產品中的 LLM 智慧體需要根據真實使用者環境回饋持續迭代策略，且無法中斷進行中執行時，QwenGyre 的彈性排程器可兼顧服務可用性與訓練效率。

### 實作前置條件

**資料條件**
- 可穩定執行的黑箱智慧體 harness（測試/執行架構），能提供模型呼叫介面並回傳環境狀態。
- 清晰的任務專屬評估分數與獎勵訊號，最好包含可評估的部分進度，以便在超時或執行中斷時仍能產生訓練目標。
- 足夠多樣的種子任務與初始策略產生的 rollout 資料，作為線上 RL 冷啟動基礎。

**運算條件**
- 大規模 GPU 叢集：論文使用 Qwen 3.8 2.4T 旗艦模型，每條 rollout 約 700K token，建議至少具備數百至數千張高效能 GPU。
- 高速叢集網路與低延遲 inference serving，以支援模型呼叫在 GPU 角色切換時不中斷。
- 分散式儲存系統，用於持久化 harness 狀態、模型呼叫記錄與軌跡樹。

**技能條件**
- 熟悉線上強化學習（RL）與策略梯度方法，理解 policy-generated targets 與執行層級平均等訓練技巧。
- 具備分散式訓練與 LLM inference serving 經驗，能部署集中式資料平行訓練與串流訓練。
- 能設計與整合軟體工程任務 harness，並處理非線性分支、共享前綴與冗餘路徑去重。

### 實作步驟建議

1. **任務與 harness 介面定義**：選定目標任務（如儲存庫生成、issue 修復），確保 harness 能透過代理接收模型輸出、執行工具呼叫並回傳新上下文，同時記錄每個模型呼叫與工具呼叫。
2. **獎勵與部分進度評估建置**：設計任務專屬評估分數，包含最終獎勵與可評估的部分進度，讓軌跡處理器在執行超時後仍能產生有效訓練樣本。
3. **部署彈性 GPU 資源池**：將 GPU 叢集設定為可動態切換 rollout 與訓練角色的資源池，部署彈性排程器監控未完成的 rollout 工作量，並在閒置時將 GPU 轉為訓練用途。
4. **整合軌跡處理器**：將每次 harness 執行的模型呼叫組織為軌跡樹，保留每個輸出的條件化上下文，並依角色優先順序選擇有限數量的訓練軌跡，對共享輸出只計算一次損失。
5. **啟動線上 RL 訓練循環**：設定 burst 長度 µ 與每步 rollout 群組數 B，執行集中式資料平行訓練，讓新加入的 GPU 能參與進行中批次，並透過串流訓練平衡各資料平行群組進度。
6. **監控、診斷與迭代**：追蹤 GPU 使用率、執行變異性、軌跡冗餘比例與訓練收斂曲線，持續調整排程策略與軌跡選擇規則。

### 潛在風險與注意事項

- **進行中執行無法 checkpoint**：黑箱 harness 通常不支援一般化的狀態檢查點，若模型呼叫中斷可能導致 harness 停擺或超時，改變任務結果。排程器必須確保 inference 服務不中斷，並避免在關鍵模型呼叫時切換 GPU 角色。
- **執行變異性造成 GPU 閒置**：少數長尾 rollout 會阻塞整個訓練批次。建議設定合理的超時機制、優先完成接近結尾的執行，並讓彈性排程器將等待期間的 GPU 用於訓練。
- **分支軌跡爆炸與 token 冗餘**：非線性分支會產生大量共享前綴的軌跡，若全部展開會壓垮訓練管線。務必啟用軌跡處理器的去重與角色優先順序篩選，並對每個執行內的 token 損失取平均。
- **獎勵稀疏或延遲**：xLong-horizon 任務常在結尾才給予最終獎勵，中間訊號不足。應盡可能設計部分進度指標，避免策略在長期探索中無法收斂。
- **條件化上下文遺失**：訓練時若未保留模型輸出時的原始上下文，會導致策略學習到錯誤的條件機率。軌跡樹必須精確記錄每個輸出對應的完整上下文。

### 與其他技術的整合建議

- **CI/CD 與 issue tracking 系統**：將 harness 與現有 Git 流程、測試框架（如 pytest）、issue 追蹤工具整合，讓智慧體在真實開發環境中執行並取得可驗證的獎勵。
- **LLM serving 框架**：可結合 vLLM、TensorRT-LLM 或 TGI 提供高效模型呼叫，並透過 QwenGyre 的代理層統一管理請求路由與記錄。
- **分散式訓練框架**：底層訓練可基於 Megatron-LM、DeepSpeed 或 FSDP 實現資料平行與模型平行，QwenGyre 負責上層的彈性排程與串流訓練協調。
- **可觀測性與實驗管理**：整合 Prometheus/Grafana 監控 GPU 使用率與 rollout 延遲，並使用 MLflow、Weights & Biases 記錄訓練步數、策略版本與評估分數。
- **資料版本控制**：由於軌跡樹與模型呼叫記錄體積龐大，建議使用物件儲存與資料版本控制，方便回溯特定策略版本的訓練樣本。

### 給不同背景讀者的閱讀建議

**初學者**：這篇論文聚焦於非常前沿的長期 LLM 智慧體強化學習系統，若你剛接觸 RL 或 LLM，建議先理解「rollout」「獎勵」「策略」等基礎概念，再將重點放在 QwenGyre 解決的兩個直覺問題：為什麼 GPU 會因為少數慢任務而閒置，以及為什麼分支執行會讓訓練資料爆炸。不必一開始就深入分散式系統細節。

**AI 工程師**：你應關注彈性排程器與軌跡處理器的實作細節，包括集中式資料平行訓練如何讓新 GPU 加入進行中批次、串流訓練如何平衡資料平行群組進度，以及軌跡樹如何保留條件化上下文並對共享輸出去重。這些設計直接影響大規模部署時的吞吐量與收斂穩定性。

**研究人員**：本論文的核心貢獻在於將線上 RL 推向 xLong-horizon 範疇，並提出彈性資源調度與分支軌跡建模的系統性方法。建議深入分析其與 Colocate、Async 基線的比較，並思考這些機制能否泛化到其他長期決策領域，例如機器人控制、科學發現或開放世界遊戲。

**產品經理**：請將本技術視為「讓自主程式設計代理能持續從真實執行中學習」的基礎設施。評估導入時，重點關注適用場景是否具備可量化的任務獎勵、是否能承受長時間執行的運算成本，以及預期效能提升（如 NL2RepoBench 上 6% 絕對提升與 1.38–1.85 倍加速比）是否值得投入。
