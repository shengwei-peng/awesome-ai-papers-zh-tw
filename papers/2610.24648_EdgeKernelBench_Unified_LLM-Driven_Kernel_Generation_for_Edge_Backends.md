## ⚡ TL;DR

現有LLM核心生成基準僅針對伺服器GPU，無法處理邊緣裝置硬體碎片化與嚴格資源預算的挑戰。

## 摘要翻譯

近期研究顯示 LLM 能在伺服器 GPU 上產生高效能的核心。邊緣部署面臨獨特挑戰，因為硬體具異質性、軟體堆疊呈碎片化，且資源預算嚴格。跨多種邊緣後端的 LLM 核心生成尚未被系統性地研究。我們提出 EdgeKernelBench，結合統一中間表示 (IR) 部署框架與邊緣工作負載的層次化基準。統一 IR 擷取可重用計算、排程與記憶體決策，並透過編譯器介面連接至各目標後端。此基準橫跨具代表性的邊緣應用領域，涵蓋漸進擴展的程式範圍，從個別運算子到小型模型圖。我們以 TVM 作為參考編譯器實例化此設計，並在異質邊緣後端上進行驗證。在單次生成嘗試下，最佳模型達到 64.5% Correct@1，但僅有 25.5% Fast@1.0。此差距凸顯功能正確性並未一致地轉化為效能增益。因此我們提出層次化邊緣核心代理 (LEKA)，透過層次化中間表示組織最佳化。在代理評估子集上，LEKA 達到 43.5% Fast@1.0，相較之下直接生成為 13.0%，Claude Code 為 26.1%。LEKA 與 Claude Code 使用相同的基礎模型與最佳化預算。EdgeKernelBench 與 LEKA 共同支援 LLM 所生成的核心於跨邊緣後端之統一評估與層次化最佳化。

### 核心貢獻（3～5點）
- 提出 EdgeKernelBench，結合統一中間表示 (IR) 部署框架與層次化基準，系統性地評估 LLM 於邊緣後端的核心生成能力
- 設計統一 IR 以擷取可重用計算、排程與記憶體決策，並透過編譯器介面連接至各目標後端
- 實證揭示功能正確性（Correct@1 達 64.5%）與效能增益（Fast@1.0 僅 25.5%）之間的顯著落差
- 提出層次化邊緣核心代理 (LEKA)，透過層次化中間表示組織最佳化，在代理評估子集上將 Fast@1.0 提升至 43.5%，顯著優於直接生成（13.0%）與 Claude Code（26.1%）
- 以 TVM 為參考編譯器，於異質邊緣後端上完成設計實例化與驗證

### 適合對象
從事邊緣運算、編譯器設計、LLM 程式碼生成及高效能運算子開發的研究人員與工程師；特別適合關注 LLM 自動生成核心於資源受限裝置上部署與最佳化、跨後端可移植性，以及碎片化邊緣生態系整合議題之研究者與實務工作者。

## 深度分析

#### 方法論解析

本文提出了一套針對邊緣裝置 (Edge Devices) 的 LLM 核心生成 (Kernel Generation) 系統設計，核心由兩個互補的元件構成：**EdgeKernelBench** 統一部署框架與層次化基準，以及 **LEKA** (Layered Edge Kernel Agent) 代理架構。

**統一中間表示 (Unified IR) 設計哲學**

傳統伺服器端核心生成方法（如 KernelBench、TritonBench）要求 LLM 直接產出各後端的原生程式碼（CUDA、Triton、OpenCL 等），這導致三個問題：(1) 模型必須記住每個後端的程式語言語法與合法性規則 (Legality Rules)；(2) 計算與排程 (Scheduling) 知識被綁定在特定後端，難以跨裝置遷移 (Transfer across Devices)；(3) 記憶體決策 (Memory Decisions) 與效能決策被分散在不同抽象層級。

EdgeKernelBench 的核心創新在於引入**後端無關 (Backend-Independent) 的統一中間表示 (Unified IR)**。LLM 不再產出目標原生核心 (Target-Native Kernel)，而是表達「計算意圖」與「最佳化選擇」，再由確定性的後端適配器 (Backend Adapter) 透過**漸進式降階 (Progressive Lowering)** 將 IR 編譯到具體後端。這種設計將可重用計算 (Reusable Computation) 與後端特定介面解耦，使同一份 IR 可同時映射到 CPU/LLVM、GPU/CUDA、GPU/OpenCL 三種執行路徑。

**層次化基準 (Hierarchical Benchmark) 的雙軸設計**

基準沿兩個正交軸組織任務：

- **組合複雜度軸**：分為三個層級——Level 1「基礎計算模式」(Basic Compute Patterns)、Level 2「組合運算子圖」(Composed Operator Graphs)、Level 3「緊湊模型圖」(Compact Model Graphs)。此設計使評估能區分「單運算子最佳化能力」與「跨運算子資源規劃能力」。
- **應用領域軸**：涵蓋行動與個人智慧 (Mobile and Personal Intelligence)、具身機器人 (Embodied Robotics)、智慧物聯網 AI (Smart AIoT)，反映邊緣部署的真實場景多樣性。

所有任務皆為帶有可追溯出處的 PyTorch 參考程式，這保證了基準的可驗證性與可重現性。

**LEKA 代理架構的層次化解耦**

實驗揭示了一個關鍵現象：隨著程式範圍 (Program Scope) 擴大，單次生成 (One-shot Generation) 的 Fast@1.0 在 Level 3 跌至 0.0%–4.0%。這顯示跨層級的耦合決策（如張量層級的排程與圖層級的記憶體分配）超出單一 LLM 推理的協調能力。

LEKA 透過**層次化中間表示 (Layered IR)** 將耦合的跨層級決策分解：每個代理專注於 IR 層次中的一個表示層級，同時透過層級間介面保持協調。這種「分而治之」策略借鑑了編譯器設計中「多層 IR」的概念，但將其應用於 LLM 代理的工作流編排。

**與 TVM 的整合**

本文以 TVM 作為參考編譯器 (Reference Compiler) 實例化設計。TVM 本身具備 Schedule-based 最佳化空間與多後端程式碼生成能力，這使其成為承載統一 IR 的天然選擇。LLM 產生的 IR 經由 TVM 的編譯流程降階至 LLVM IR、CUDA 或 OpenCL。

#### 實驗數據解讀

**基準評估結果（650 個任務實例）**

最強模型在三項指標上的表現形成鮮明對比：
- **Compile@1 = 73.5%**：語法可編譯率尚可，說明 LLM 對後端程式語言有一定掌握。
- **Correct@1 = 64.5%**：功能正確率下降約 9 個百分點，反映語意正確性比語法正確性更困難。
- **Fast@1.0 = 25.5%**：效能加速比僅為四分之一，暴露「功能正確不等於效能增益」的核心問題。

這個 39 個百分點的落差（Correct@1 與 Fast@1.0 之間）是本文最重要的發現之一。它量化說明：在邊緣嚴格預算 (Tight Budget) 下，僅僅「能跑」遠不足以滿足部署需求。

**層級退化現象**

Level 3（緊湊模型圖）的 Fast@1.0 在三個後端皆跌至 0.0%–4.0%。這暗示隨著程式範圍擴大，所需協調的決策維度呈現超線性增長，單次推理的上下文窗口與注意力機制難以承載。

**LEKA 代理評估（69 實例子集）**

在控制基礎模型 (Base Model)、任務契約與時鐘預算相同的前提下：
- Correct@1：42.0% → **100.0%**（提升 58 個百分點）
- Fast@1.0：13.0% → **43.5%**（提升 30.5 個百分點）

與 Claude Code 基線比較：Fast@1.0 從 26.1% 提升至 43.5%（提升 17.4 個百分點）。這個對照尤其關鍵，因為 Claude Code 本身已是成熟的程式碼生成代理，LEKA 的優勢證明了**領域專屬的層次化架構**比通用代理更適合邊緣核心最佳化。

**指標設計的意涵**

- **Correct@1**：衡量單次生成的功能正確性，傳統 KernelBench 協議的核心指標。
- **Fast@1.0**：要求生成的核心達到參考實作的加速比 ≥ 1.0，這是部署可行性的關鍵閾值。
- **Compile@1**：作為前置篩選，區分「語法錯誤」與「語意錯誤」失敗模式。

三層指標的設計使失敗分析得以細粒度進行，這對診斷 LLM 在邊緣核心生成中的瓶頸至關重要。

#### 與現有研究的比較

**與 KernelBench 系列基準的比較**

KernelBench 及其衍生工作（TritonBench 等）主要針對伺服器 GPU，採用「LLM 直接產出原生 CUDA/Triton 程式碼」範式。本文指出此範式在邊緣場景的三個不適配：(1) 邊緣硬體碎片化使單一後端假設失效；(2) 邊緣最佳化需同時考慮效能與記憶體預算；(3) 單運算子任務無法評估跨運算子最佳化能力。

**與 MobileKernelBench 的比較**

MobileKernelBench 雖延伸至行動裝置，但任務僅涵蓋單一運算子及其屬性變體。本文將任務擴展至運算子圖與模型圖層級，並引入統一 IR 框架，使評估能反映真實部署中的資源規劃需求。

**與 KernelBench 協議的關係**

本文沿用 KernelBench 的評估協議（Correct@1、Fast@1.0），這保證了指標的可比性，但同時透過統一 IR 改變了生成範式。這種「協議相容、範式革新」的策略降低了領域轉換的阻力。

**與通用程式碼生成代理的比較**

Claude Code 代表通用代理的強基線。LEKA 在相同預算下以 17.4 個百分點的 Fast@1.0 優勢勝出，證明領域專屬架構的價值。但需注意：Claude Code 並非專為核心最佳化設計，此對比更應理解為「通用 vs 專用」的論證，而非「LEKA 優於所有代理」的宣稱。

**本文的侷限性**

1. **後端覆蓋有限**：僅實例化 CPU/LLVM、GPU/CUDA、GPU/OpenCL 三條路徑，未涵蓋 NPU、DSP、FPGA 等邊緣常見加速器。
2. **基準規模**：650 個任務實例相較 KernelBench 的數百題規模相近，但邊緣場景的多樣性可能需要更大規模。
3. **代理評估子集僅 69 實例**：統計顯著性需更大樣本驗證。
4. **未探討訓練-時間最佳化**：LEKA 是推理-時間 (Inference-time) 代理，未涉及如何透過邊緣核心資料微調基礎模型。

#### 可重現性評估

**程式碼與框架可用性**

本文以 TVM 作為參考編譯器實例化，這是一個開源且成熟的編譯器基礎設施，有利於重現。統一 IR 的設計若公開實作，將使其他研究者能在不同編譯器堆疊上重現框架。

**基準任務的出處可追溯性**

所有任務皆為帶有可追溯出處的 PyTorch 參考程式，這是優於許多「合成任務」基準的設計。出處可追溯使研究者能驗證任務的代表性與難度分布。

**模型權重與評估細節**

本文評估了五個 LLM，但未明確列出所有模型名稱與版本。對於可重現性而言，公開以下資訊至關重要：
- 評估模型的完整清單與版本
- 提示詞 (Prompt) 模板與任務契約格式

**資料集釋出**

若 EdgeKernelBench 的 650 個任務實例能以標準格式（如 JSON + PyTorch 參考實作）公開，將大幅提升基準的可重複使用性。任務的「層級 × 領域」雙軸組織也便於研究者選取子集進行專項評估。

**LEKA 代理的開源**

LEKA 的層次化代理架構若公開實作，將使其他研究者能在不同基礎模型上測試其泛化性。代理間的通訊協議與層級介面定義是重現的關鍵。

#### 未來研究方向

**1. 擴展後端覆蓋至異質加速器**

當前實例僅涵蓋 CPU 與 GPU 路徑。邊緣裝置的關鍵加速器——NPU（如 Qualcomm Hexagon、Apple ANE）、DSP、FPGA——尚未納入。統一 IR 框架的價值在於其後端無關性，未來工作應驗證其在這些加速器上的可降階性，並探討 LLM 是否能學習跨加速器的最佳化模式。

**2. 記憶體感知最佳化的形式化**

本文指出邊緣核心需在嚴格預算下平衡效能與記憶體。未來可將記憶體預算作為 IR 的一階約束 (First-class Constraint)，使 LLM 在生成階段即考慮記憶體峰值，而非僅在後處理階段驗證。這需要新的 IR 結構與評估指標（如 Memory@1）。

**3. 層次化代理的理論分析**

LEKA 的層次化解耦啟發自編譯器多層 IR 設計，但缺乏對「為何有效」的理論解釋。未來可研究：(a) 各層級決策空間的維度與耦合度；(b) 層級劃分對代理效能的影響；(c) 自適應層級劃分（而非預設固定層級）的可能性。

**4. 訓練-時間與推理-時間的聯合最佳化**

當前 LEKA 為純推理-時間方法。未來可探索：(a) 使用 EdgeKernelBench 資料微調 (Fine-tune) 基礎模型，使其原生具備層次化推理能力；(b) 結合搜尋式方法（如 MCTS）與 LLM 推理的混合最佳化；(c) 從人類專家核心中蒸餾 (Distill) 最佳化策略。

**5. 跨裝置遷移學習**

統一 IR 的核心承諾是「一次生成、多後端部署」。未來應系統性研究：(a) 在某一後端上學習的最佳化策略如何遷移至其他後端；(b) 哪些決策是後端無關的（如計算圖結構），哪些是後端特定的（如執行緒配置）；(c) 遷移效率的量化指標。

**6. 與部署系統的端到端整合**

當前評估聚焦於單一核心的生成與最佳化。實際邊緣部署涉及模型量化、圖最佳化、記憶體規劃等多階段。未來可將 EdgeKernelBench 擴展為端到端部署基準，評估 LLM 在完整部署流程中的角色。

**7. 失敗模式的細粒度分析**

實驗顯示 Level 3 的 Fast@1.0 接近零。未來應深入分析失敗模式：(a) 是排程錯誤、記憶體錯誤、還是後端特定合法性錯誤？(b) 錯誤是否集中在特定運算子類型？(c) 視覺化 LLM 的「最佳化推理鏈」能否揭示失敗根源？

**8. 安全性與可驗證性**

邊緣裝置的核心錯誤可能導致系統級故障。未來應研究：(a) 如何驗證 LLM 生成核心的數值穩定性與安全性；(b) 形式化驗證 (Formal Verification) 與 LLM 生成的結合；(c) 失敗回退機制的設計。

**9. 基準的演化與社群維護**

EdgeKernelBench 應建立持續演化的機制：(a) 隨新模型、新後端出現而擴展任務；(b) 防止「過擬合基準」——模型在公開任務上表現優異但泛化不足；(c) 建立難度分級與反污染機制。

**10. 與其他領域的交叉**

邊緣核心生成的挑戰與其他領域（如傳統編譯器最佳化、自動程式碼生成、神經架構搜尋）有共通點。未來可探索跨領域的方法遷移，例如將 NAS 中的搜尋策略應用於核心排程空間，或將編譯器中的成本模型整合至 LLM 的推理過程。

## 論文問答

**Q1：邊緣裝置的核心生成面臨哪些獨特挑戰？**
A：邊緣裝置的核心生成面臨三大核心挑戰。首先，硬體與軟體生態高度碎片化，邊緣裝置橫跨異質處理器、廠商執行環境與部署引擎，不像伺服器端僅需支援少數主流加速器。其次，邊緣工作負載與系統其他部分共享運算與記憶體資源，記憶體容量往往決定模型是否可部署，因此最佳化目標必須同時兼顧執行效能與記憶體成本。最後，邊緣裝置的資源預算極為嚴格，無法像伺服器 GPU 般擁有充裕的專屬記憶體與寬鬆的資源配置，這使得核心生成必須在緊縮的預算下做出權衡。

**Q2：為什麼現有的伺服器端核心生成方法無法直接應用於邊緣裝置？**
A：現有伺服器端方法（如 KernelBench、TritonBench）主要針對資料中心 GPU 設計，其軟體堆疊成熟且單一，無法處理邊緣裝置的異質性。直接生成各後端的原生程式會將可重用的計算與排程知識綁定到特定後端的語言、介面與合法性規則上，使得支援新後端時模型必須重新適應整個程式設計與部署環境，嚴重限制跨裝置遷移能力。此外，伺服器端最佳化主要追求執行速度，但邊緣裝置必須在固定資源預算下同時最佳化效能與記憶體使用，這種目標差異使得現有方法難以直接套用。

**Q3：為什麼現有的基準測試（如 KernelBench、MobileKernelBench）不足以評估邊緣核心生成？**
A：KernelBench 等基準測試主要針對伺服器 GPU，其任務導向與硬體特性都與邊緣場景不符。雖然 MobileKernelBench 將評估延伸至行動裝置，但其公開任務主要由個別運算子及其屬性變體組成，僅評估基本的程式碼生成能力，無法涵蓋跨運算子最佳化或圖層級的資源規劃。這類基準測試的產出物仍是原生程式碼，要求模型自行滿足各後端的語言與合法性規則，因此在模型較少見的硬體上正確性會大幅下降。EdgeKernelBench 正是為了填補這些缺口，引入層次化任務設計與統一中間表示來更全面地評估邊緣核心生成。

**Q4：EdgeKernelBench 的統一中間表示（Unified IR）框架是如何運作的？**
A：EdgeKernelBench 的統一 IR 框架讓 LLM 不再為每個後端產出獨立的原生程式，而是先在統一的中間表示中表達對目標裝置的最佳化選擇。這個 IR 捕捉可重用的計算、排程與記憶體決策，將這些與後端無關的知識從特定介面中抽離出來。接著，確定性的後端適配器（backend adapter）會以漸進式降階（progressive lowering）的方式將程式分階段降至目標後端。這種分離設計使模型能夠跨後端重用最佳化知識，同時在部署約束下平衡執行效能與記憶體成本。

**Q5：LEKA 的層次化代理架構有什麼核心創新？**
A：LEKA 的核心創新在於將跨層級耦合的決策沿著 IR 層次結構進行分解，讓每個代理專注於單一層級的表示，同時保留跨層級的協調能力。這種層次化設計解決了一次性生成在程式範圍擴大時難以協調日益耦合決策的問題。在實驗中，LEKA 將 Correct@1 從 42.0% 提升至 100.0%，Fast@1.0 從 13.0% 提升至 43.5%，展現出層次化最佳化相較於直接生成的顯著優勢。值得注意的是，LEKA 與 Claude Code 使用相同的基礎模型與最佳化預算，但 Fast@1.0 從 26.1% 提升至 43.5%，證明了架構設計本身的價值。

**Q6：為什麼選擇 TVM 作為參考編譯器？這種設計選擇帶來哪些權衡？**
A：選擇 TVM 作為參考編譯器是因為它是一個成熟且廣泛使用的開源編譯器框架，支援多種後端（包括 CPU/LLVM、GPU/CUDA、GPU/OpenCL），能夠驗證統一 IR 框架在異質後端上的可行性。這種設計選擇的權衡在於：雖然 TVM 提供了良好的後端覆蓋，但將參考編譯器綁定到特定框架可能限制對其他編譯器生態（如 MLIR、Halide）的探索。此外，TVM 的特定抽象層級與降階路徑可能影響統一 IR 的通用性，但作為概念驗證，TVM 足以展示統一 IR 框架與層次化基準測試的設計理念。

**Q7：EdgeKernelBench 的基準測試是如何設計的？包含哪些維度？**
A：EdgeKernelBench 的基準測試沿著兩個正交軸進行組織：組合複雜度與應用領域。複雜度軸包含三個層級——基礎計算模式（Basic Compute Patterns）、組合運算子圖（Composed Operator Graphs）與精簡模型圖（Compact Model Graphs），涵蓋從個別運算子到小型模型圖的漸進式程式範圍。應用領域則涵蓋行動與個人智慧、具身機器人與智慧物聯網（AIoT）三大代表性邊緣應用領域。所有任務都是具有可追溯出處的 PyTorch 參考程式，這種分離設計使得針對不同邊緣部署場景的最佳化能力評估得以精準進行。

**Q8：實驗中各 LLM 在不同後端上的表現如何？關鍵數據是什麼？**
A：實驗在 650 個任務實例上評估了五個 LLM，涵蓋 CPU/LLVM、GPU/CUDA 與 GPU/OpenCL 三種執行路徑。最強模型在單次生成嘗試下達到 73.5% Compile@1 與 64.5% Correct@1，但 Fast@1.0 僅有 25.5%，顯示功能正確性並不能穩定轉化為效能增益。在 Level 3（精簡模型圖）層級，三個後端的最高 Fast@1.0 分數進一步下降至 0.0% 到 4.0% 之間，說明隨著程式範圍擴大，一次性生成難以協調日益耦合的跨層級決策。這些數據清楚地揭示了邊緣核心生成中正確性與效能之間的巨大鴻溝。

**Q9：LEKA 相比直接生成和 Claude Code 有哪些具體優勢？**
A：LEKA 在代理評估子集（69 個實例）上展現出顯著優勢：Correct@1 從直接生成的 42.0% 提升至 100.0%，Fast@1.0 從 13.0% 提升至 43.5%。在與 Claude Code 的比較中，兩者使用相同的基礎模型與最佳化預算，但 LEKA 將 Fast@1.0 從 26.1% 提升至 43.5%，提升幅度達 17.4 個百分點。這些結果證明了層次化代理架構在處理複雜邊緣核心生成任務時的優勢，特別是在需要跨層級協調決策的情境下。LEKA 的成功表明，僅僅增加生成嘗試次數或使用通用程式碼代理是不夠的，必須採用結構化的最佳化策略。

**Q10：EdgeKernelBench 和 LEKA 在實際邊緣部署場景中有哪些應用？**
A：在行動與個人智慧領域，這項技術可用於加速智慧型手機、平板等裝置上的 AI 應用，例如即時影像處理、語音辨識與個人化推薦，同時滿足嚴格的記憶體與功耗限制。在具身機器人領域，LEKA 可協助生成高效的核心，使機器人能夠在資源受限的嵌入式平台上即時執行感知、決策與控制演算法。在智慧物聯網（AIoT）場景中，這項技術能幫助感測器、攝影機與其他邊緣裝置在本地執行 AI 推理，減少網路依賴並保護資料隱私，同時適應各種異質硬體平台。

**Q11：從產品化角度，這項研究對邊緣 AI 部署有何影響？**
A：從產品化角度來看，這項研究有助於降低邊緣 AI 部署的成本與時間。傳統上，新運算子與後端的自訂核心需要手動實作、驗證與維護，是部署流程中的持續性瓶頸；EdgeKernelBench 與 LEKA 提供了一個統一框架，使得核心生成與最佳化能夠自動化並跨後端遷移。這意味著企業可以更快地將新模型部署到多樣化的邊緣裝置上，無需為每個硬體平台單獨投入大量工程資源。此外，統一 IR 框架也簡化了部署工具鏈的整合，有助於建立更靈活、可擴展的邊緣 AI 產品線。

**Q12：這項研究對 LLM 驅動的系統程式設計領域有何更廣泛的影響？**
A：這項研究將 LLM 驅動的核心生成從伺服器端擴展到邊緣裝置，填補了該領域的重要空白。它提出的統一 IR 框架為跨後端程式碼生成提供了一個新範式，將可重用的計算知識與後端特定介面分離，這種設計理念可應用於其他系統程式設計任務（如驅動程式、編譯器優化）。層次化代理架構（LEKA）則展示了如何將複雜的系統最佳化問題分解為可管理的子問題，這對未來 LLM 在系統程式設計中的應用具有示範意義。此外，該研究強調了正確性與效能之間的鴻溝，提醒研究社群不能僅關注功能正確性，還必須深入研究效能最佳化。

**Q13：論文承認哪些局限性？**
A：論文坦承在 Level 3（精簡模型圖）層級，最佳模型的 Fast@1.0 分數僅在 0.0% 到 4.0% 之間，顯示一次性生成在處理較大程式範圍時仍有嚴重不足。此外，雖然統一 IR 框架在概念上具有後端無關性，但目前的實作仍以 TVM 作為參考編譯器，可能無法完全代表所有編譯器生態的特性。代理評估僅在 69 個實例的子集上進行，雖然這個子集是隨機抽樣的，但樣本規模相對有限。論文也未深入探討統一 IR 對於更複雜的邊緣場景（如多核心處理器、分散式邊緣運算）的適用性。

**Q14：在實驗中觀察到哪些失敗案例或邊界情況？**
A：實驗中觀察到的主要失敗模式包括：功能正確但效能不佳的情況——最強模型達到 64.5% Correct@1 但僅 25.5% Fast@1.0，顯示正確性無法穩定轉化為效能增益。在 Level 3 層級，三個後端的 Fast@1.0 幾乎歸零，說明跨層級決策的協調對一次性生成而言過於困難。此外，不同後端之間的表現存在差異，模型在某些硬體上可能因為訓練資料中較少見而正確性大幅下降。這些失敗案例凸顯了邊緣核心生成中跨後端泛化與效能最佳化的雙重挑戰。

**Q15：未來的研究方向有哪些？**
A：未來研究方向包括：擴展統一 IR 框架以支援更多編譯器生態（如 MLIR、Halide）與更複雜的邊緣場景（如多核心處理器、分散式邊緣運算）。進一步發展 LEKA 的層次化代理架構，探索更細粒度的任務分解與代理協調機制，以處理 Level 3 及更複雜的程式範圍。研究如何將記憶體與效能的聯合最佳化更系統地整合到生成流程中，以更好地適應邊緣裝置的嚴格資源預算。此外，建立更全面的評估指標，涵蓋能源效率、即時性保證與長期部署穩定性等邊緣特有的考量，也是重要的研究方向。

## 實務應用指南

### 適用場景

1. **行動裝置 AI 應用的自訂運算子部署**：智慧型手機上的相機 ISP、即時翻譯、語音喚醒等場景，需要在 ARM CPU 與行動 GPU 上部署新興運算子（如 Flash Attention 變體、動態形狀卷積）。團隊可使用 EdgeKernelBench 的統一 IR 表達運算子的計算與排程意圖，由後端適配器自動降階至 LLVM 或 OpenCL，避免為每個 SoC 重寫核心。

2. **機器人即時控制系統的低延遲核心**：人形機器人、無人機的運動規劃與感測融合模型，常需要在 Jetson Orin、RK3588 等邊緣 SoC 上以毫秒級延遲執行。LEKA 的層次化代理可分層處理張量層級的 tile 切分與圖層級的運算子融合，在嚴格記憶體預算下取得比直接生成更高的 Fast@1.0。

3. **AIoT 裝置的模型容量規劃**：智慧門鈴、工業感測器等裝置的快閃記憶體與 RAM 極為有限（通常 < 512MB）。EdgeKernelBench 將排程與記憶體決策置於同一最佳化空間，適合用於在部署前評估「此模型在此硬體上是否放得下、跑得動」。

4. **跨廠商後端的單一程式碼庫**：車用、智慧家庭等場景常同時面對 Qualcomm、MediaTek、Apple 等不同 NPU/GPU 後端。統一 IR 讓 LLM 只需學習一種表示法，由後端適配器處理各廠商執行環境的合法性規則，降低核心維護成本。

5. **LLM 編譯器研究團隊的能力評估**：學術與工業研究單位可使用 EdgeKernelBench 的 650 個任務實例，系統性地比較不同基礎模型在邊緣後端的核心生成能力，並透過 LEKA 架構探索代理式最佳化的設計空間。

### 實作前置條件

**資料準備**
- PyTorch 參考程式：所有任務需具備可追溯來源的 PyTorch 實作，作為正確性比對基準。
- 硬體設定檔：目標裝置的計算能力、記憶體容量、支援的執行路徑（CPU/LLVM、GPU/CUDA、GPU/OpenCL）。
- 應用領域標註：將任務分類至行動裝置、機器人、AIoT 三大領域，並標註其運算特徵（延遲敏感、記憶體受限、批次大小等）。

**運算資源**
- 邊緣裝置或模擬環境：至少一組 ARM/x86 CPU、CUDA GPU、OpenCL GPU 的執行環境。
- LLM API 存取：需具備 GPT、Claude、Gemini 等模型的 API 金鑰；LEKA 評估子集需 69 個任務實例的生成預算。
- TVM 編譯環境：作為參考編譯器堆疊，需預先安裝並驗證三條後端路徑皆可運作。

**技能門檻**
- 編譯器基礎：理解 IR、lowering、合法性規則、tile 排程等概念。
- TVM 使用經驗：熟悉 Schedule、Pass、Module 結構，能讀懂後端適配器的程式碼。
- 邊緣部署經驗：理解記憶體預算、核心啟動成本、裝置驅動特性。
- LLM 代理設計：若要實作 LEKA，需具備多代理協作、工具呼叫、預算控制的工程能力。

### 實作步驟建議

**步驟一：建立統一 IR 與後端適配器**
從 TVM 的 TensorIR 與 Relay IR 開始，定義可表達計算、排程、記憶體決策的中間表示。為每個目標後端（LLVM、CUDA、OpenCL）撰寫確定性的降階介面，確保同一 IR 輸入在不同後端產生等價語意但原生實作的核心。

**步驟二：建構層次化基準**
依照三個複雜度等級組織任務：Level 1（基本計算模式，如 GEMM、Softmax）、Level 2（組合運算子圖，如 LayerNorm + GELU）、Level 3（緊湊模型圖，如 MobileNet 區塊、EfficientFormer）。每個任務需附上 PyTorch 參考實作與正確性驗證腳本。

**步驟三：執行一次性生成評估**
使用五個目標 LLM 對 650 個任務實例各執行一次生成，記錄 Compile@1、Correct@1、Fast@1.0 三項指標。預期結果：最佳模型約 64.5% Correct@1，但僅 25.5% Fast@1.0，凸顯正確性與效能之間的落差。

**步驟四：部署 LEKA 層次化代理**
將代理拆分為對應 IR 層級的角色：張量層級代理負責 tile 大小、向量化；圖層級代理負責運算子融合、記憶體規劃。代理間透過共享的 IR 狀態協調決策，並在統一的時脈預算下迭代。

**步驟五：在代理評估子集上驗證**
從 650 個任務中隨機抽樣 69 個實例作為代理評估子集。比較 LEKA、Claude Code、直接生成三種模式在相同基礎模型與時脈預算下的 Fast@1.0。預期 LEKA 可達 43.5%，顯著優於 Claude Code 的 26.1% 與直接生成的 13.0%。

**步驟六：整合至部署管線**
將 EdgeKernelBench 的 IR 生成流程接入 CI/CD，在每次模型變更時自動評估新運算子在目標邊緣裝置上的可行性與效能，並將通過驗證的核心推送至裝置端 OTA 更新。

### 潛在風險與注意事項

**正確性與效能的巨大落差**
一次性生成在 Level 3 的 Fast@1.0 可能降至 0%–4%，即使 Correct@1 看似合理。緩解方式：將 LEKA 設為預設路徑，並在管線中加入「正確性通過但效能未達標」的告警閾值。

**後端合法性規則的隱性違規**
LLM 生成的 IR 可能在某些後端通過編譯，但在其他後端違反合法性規則（例如 OpenCL 的工作群組大小限制）。緩解方式：在後端適配器中加入合法性檢查 Pass，於降階前攔截違規決策並回饋給代理。

**記憶體預算的隱性超支**
LLM 可能選擇效能最佳但記憶體用量過大的排程策略，導致模型在裝置上無法載入。緩解方式：在 IR 中明確標註記憶體預算約束，並在代理評分函數中加入記憶體懲罰項。

**代理迭代的時脈成本**
LEKA 的多代理迭代會消耗更多 LLM 推理時間與裝置量測時間。緩解方式：設定每個任務的硬性時脈上限，並在代理間共享量測結果以避免重複編譯。

**基準任務的代表性偏差**
650 個任務實例無法涵蓋所有邊緣場景。緩解方式：保留任務擴充介面，允許團隊依自身應用領域新增任務並貢獻回基準。

### 與其他技術的整合建議

**PyTorch 生態**
EdgeKernelBench 的所有任務皆為 PyTorch 參考程式，可直接整合 TorchScript、torch.compile 與 PyTorch Mobile 的部署流程，作為其後端的補充驗證層。

**TVM / MLC-LLM**
TVM 已作為本文的參考編譯器，MLC-LLM 的裝置端 LLM 部署可借用 EdgeKernelBench 的統一 IR 與後端適配器，加速新運算子在行動裝置的落地。

**ONNX Runtime**
可將 ONNX 模型轉換為 EdgeKernelBench 的 IR 表示，利用其層次化基準評估 ONNX 算子在邊緣後端的效能特性，並透過後端適配器產生 ONNX Runtime 的自訂運算子實作。

**廠商 SDK（Qualcomm Neural Processing SDK、MediaTek NeuroPilot、Apple Core ML）**
統一 IR 可作為廠商 SDK 的前端介面，由後端適配器將 IR 降階至各廠商的圖表示（如 QNN 圖、Core ML 模型），減少為每個廠商重寫核心的工作量。

**CI/CD 與 MLOps**
將 EdgeKernelBench 評估整合至模型訓練管線，在模型合併前自動檢查新運算子在目標邊緣裝置上的正確性與效能，避免將無法部署的模型推送至生產環境。

### 給不同背景讀者的閱讀建議

**初學者**：建議先閱讀第 1 節的圖 1，理解伺服器端與邊緣端核心生成的根本差異（寬鬆預算 vs 嚴格預算、單一後端 vs 碎片化後端），再閱讀抽象中 EdgeKernelBench 的統一 IR 概念。跳過編譯器細節，專注於「為什麼邊緣部署需要不同的最佳化目標」這個核心問題。

**AI 工程師**：重點閱讀第 1 節的問題陳述與第 3 節的實驗結果，特別是 Correct@1 與 Fast@1.0 的落差數據（64.5% vs 25.5%）。理解 LEKA 的層次化代理設計如何將跨層級的耦合決策分解，並評估將其整合至現有邊緣部署管線的成本與效益。

**研究者**：聚焦於統一 IR 的設計空間、層次化代理的協作機制，以及 650 個任務實例的基準建構方法。實驗章節中 Level 1 至 Level 3 的能力衰減曲線，以及 LEKA 與 Claude Code 的對比，是值得深入分析的代理式最佳化研究議題。

**產品經理**：重點理解 EdgeKernelBench 解決的商業問題——跨廠商後端的維護成本、新運算子的部署週期、邊緣裝置的記憶體規劃風險。LEKA 將 Fast@1.0 從 26.1% 提升至 43.5% 的數據，可作為評估此技術對產品上市時間與裝置覆蓋率影響的依據。
