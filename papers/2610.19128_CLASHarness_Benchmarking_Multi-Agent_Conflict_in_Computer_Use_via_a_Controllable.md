## ⚡ TL;DR

現有多代理基準假設環境一致且合作，無法評估真實世界中代理間的衝突解決能力。
CLASHarness以階層式合成與執行編譯驗證，自動生成600個可解的多代理衝突任務。
評測15個前沿模型發現：弱模型盲信誤導資訊、修復衝突比偵測更難、收尾協調失敗率逾58%。

## 摘要翻譯

視覺語言模型（VLM）日益被部署於多代理系統中以自動化複雜的電腦使用工作流程，然而現有基準大多假設環境是一致且合作的。相較之下，現實世界的協作鮮少基於一致資訊運作：同儕代理（Peer Agent）或子代理（Sub-Agent）經常回報過時狀態（Outdated State）、發出矛盾指令（Contradictory Instruction），或爭奪共享權限（Shared Permission）與檔案，迫使代理必須檢查其他代理的輸出並在環境中驗證基準事實（Ground Truth）。評估此類衝突解決（Conflict Resolution）仍具挑戰性：人工撰寫無法在複雜系統中擴展，而無約束的大型語言模型提示（Unconstrained LLM Prompting）則會產生敘事漂移（Narrative Drift）、答案洩漏（Answer Leakage）及無法滿足的評分標準（Unsatisfiable Rubric）。我們提出 CLASHarness（Conflict-Loaded Agent Scenario Harness，衝突載入代理情境測試框架），這是一個可控框架，用於在電腦使用情境中生成可驗證的多代理衝突，並附有 600 個多輪任務（Multi-Round Task）的基準。透過結合階層式情境規劃（Hierarchical Phased Synthesis／Macro Scenario Planning）與八步驟驗證式微觀管線（Verified Micro-Pipeline），CLASHarness 在渲染前預先提交決定性視覺事實（Decisive Visual Fact），並直接從已執行的參考軌跡（Reference Trajectory）編譯混合評分器（Hybrid Grader），保證每個任務在構造上即可解（Solvable by Construction）。在 CLASHarness 上評估 15 個前沿模型（Frontier Model），揭示出三個核心瓶頸（Bottleneck）。首先，當子代理輸出與環境衝突時，較弱的模型會盲目遵循誤導性資訊（Misleading Information），而較強的模型則會檢視視覺證據（Visual Evidence）以驗證基準事實。其次，解決衝突比發現衝突困難得多：雖然代理能察覺不一致之處，但主動修復系統狀態（System State）會顯著降低任務成功率（Task Success）。第三，協調協議（Coordination Protocol）仍是普遍性的瓶頸：即便是前沿模型，其超過 58% 的收尾動作（Closing Action）仍會失敗，經常忘記釋放共享鎖（Shared Lock）或進行任務交接（Task Handoff）。CLASHarness 為建構可靠的多代理系統提供了可擴展且可驗證的基礎。

### 核心貢獻（3～5點）
- **提出 CLASHarness 框架**：一個可控且可驗證的生成管線（Controllable Generation Pipeline），專門用於在電腦使用（Computer Use）情境中系統性地產生多代理衝突（Multi-Agent Conflict）任務，解決人工撰寫無法擴展、無約束 LLM 生成易產生敘事漂移與答案洩漏的問題。
- **建構 600 個多輪任務的基準測試集**：採用階層式情境規劃結合八步驟驗證式微觀管線，透過預先提交多模態對齊（Pre-Committed Multimodal Grounding）與執行編譯式驗證（Execution-Compiled Verification），保證每個任務在構造上即可解。
- **設計混合評分機制**：直接從已執行的參考軌跡編譯混合評分器（包含程式碼評分器 Code Grader 與語義評分器 Semantic Grader），涵蓋精確程式碼檢查（Exact Code Check）與範圍式語義檢查（Scoped Semantic Check），確保評估的可驗證性。
- **揭示前沿模型的三大核心瓶頸**：① 弱模型盲目遵循誤導資訊而強模型能透過視覺證據驗證基準事實；② 解決衝突遠比發現衝突困難，主動修復系統狀態會顯著降低任務成功率；③ 協調協議為普遍性瓶頸，前沿模型在超過 58% 的收尾動作中失敗，常忘記釋放共享鎖或進行任務交接。

### 適合對象
從事多代理系統（Multi-Agent System）、視覺語言模型（VLM）、AI 代理基準建構（Benchmark Construction）與代理能力（Agent Capability）評估的研究人員與工程師；特別適合關注代理在真實作業環境（Operating Environment）中衝突解決、協調失敗（Coordination Failure）與協作工作流程（Collaborative Workflow）設計的研究者與實務團隊。

## 深度分析

#### 方法論解析

CLASHarness 的核心方法論建立在三大設計原則之上，試圖從根本上解決多代理衝突基準建構中長期存在的「可控性」與「可驗證性」雙重難題。

**第一原則：階層式分階段合成（Hierarchical Phased Synthesis）**

傳統的無約束大型語言模型提示（unconstrained LLM prompting）在生成多輪衝突情境時，常因上下文溢位（context overflow）與敘事漂移（narrative drift）導致任務邏輯崩潰。CLASHarness 將生成流程拆分為兩個層級：

- **宏觀情境規劃（Macro Scenario Planning）**：以宣告式綱要（declarative outline）形式定義 10 輪任務套件（10-round package）的整體結構、領域背景、代理角色與衝突軸線，確保跨輪次的一致性。
- **驗證式微觀管線（Verified Micro-Pipeline）**：每輪任務透過八個獨立驗證步驟（eight-step verified micro-pipeline）逐步產出，每一步皆需通過形式化檢查才進入下一步，杜絕答案洩漏（answer leakage）與無法滿足的評分標準（unsatisfiable rubric）。

**第二原則：預先提交的多模態對齊（Pre-Committed Multimodal Grounding）**

此原則是 CLASHarness 區別於既有基準的關鍵設計。系統在渲染視覺環境（儀表板、終端輸出、系統架構圖等）之前，先以結構化形式提交「決定性視覺事實」（decisive visual fact, 𝑣★）。這意味著：

- 視覺證據（visual evidence）並非裝飾性元素，而是任務可解性的必要條件。
- 代理必須主動觀察螢幕、解析圖表、讀取遙測數據，才能取得真實標籤（ground truth）。
- 杜絕了「未對齊的視覺素材」（ungrounded visual asset）問題——即視覺內容與任務邏輯脫節。

**第三原則：執行編譯式驗證（Execution-Compiled Verification）**

CLASHarness 的混合評分器（hybrid grader, Φ = {𝜙₁,...,𝜙ₘ}）並非由人類事後撰寫，而是直接從已執行的參考軌跡（reference trajectory）編譯而成，混合精確程式碼檢查（exact code check）與範圍式語義檢查（scoped semantic check）。此設計保證了「構造上可解」（solvable by construction）——每一個任務在生成時已被證明存在一條可達成的解決路徑。

**形式化框架**

任務被定義為衝突輪（conflict round）元組 R = (W₀, I, T, v★, Φ)：
- W₀：初始電腦使用工作空間（作業系統狀態、檔案樹、非同步多代理通訊記錄、視覺證據）。
- I：操作目標指令，明確框定同儕代理（peer agent）的競爭性主張，但不揭露何者為真。
- T：型別化動作空間（typed action space），執行動作 c ∈ T 會轉移環境狀態並附加至稽核日誌（audit effect log, E_log）。
- v★：解決矛盾的基準事實。
- Φ：混合評分套件。

此形式化將衝突解決重新定位為「主動調查與決策」而非「被動文字分類」，迫使代理必須自主跨模態搜證、識別 v★，並執行操作狀態變更（如協議交接、組態修補、回退）。

#### 實驗數據解讀

CLASHarness 構建了橫跨 20 個操作領域、600 個可執行衝突輪、7,970 個預先提交視覺素材、3,760 個混合評分器的基準規模，並對 15 個前沿模型（frontier model）進行系統性評估，揭示出三項結構性瓶頸。

**瓶頸一：視覺對齊 vs. 盲目信任（Visual Grounding vs. Blind Trust）**

當子代理（sub-agent）輸出與環境事實衝突時，較弱模型傾向於盲目遵循誤導性資訊（misleading information），而較強模型會主動檢查視覺證據以驗證真實標籤。這項發現凸顯了多代理系統中「信任校準」的重要性——代理不能將同儕報告視為預設真值，必須發展出基於環境觀察的證據優先級排序能力。實驗數據顯示，這一差距在跨模型比較中呈現明顯梯度，而非二元分化。

**瓶頸二：解決 vs. 偵測（Resolution vs. Detection）**

這是 CLASHarness 最具啟發性的發現之一：代理能夠「發現」不一致，但「修復」系統狀態（system state）的任務成功率顯著下降。這意味著現有視覺語言模型（VLM）的衝突處理能力存在嚴重的「偵測—執行鴻溝」——它們具備識別矛盾的感知能力，卻缺乏將認知轉化為操作動作的閉環執行能力。這項瓶頸對實際部署影響深遠，因為僅偵測而不修復等同於無效的衝突解決。

**瓶頸三：協調崩潰（Coordination Breakdown）**

即使前沿模型在收尾動作（closing action）上仍有超過 58% 的失敗率，常見錯誤包括忘記釋放共享鎖（shared lock）或未將任務交接（task handoff）給子代理。這項數據揭示了協調協議（coordination protocol）在當前模型中的普遍脆弱性——代理在完成主要操作後，往往忽略「清理」與「移交」這類元動作（meta-action），導致資源死鎖或工作流斷裂。

**整體意涵**

三項瓶頸共同勾勒出當前多代理電腦使用系統的能力剖面：感知層（偵測衝突）相對成熟，但決策層（選擇正確動作）與協調層（管理共享資源）仍存在系統性缺陷。CLASHarness 的 600 輪任務設計使得這些瓶頸得以在統計上穩定呈現，而非個別案例的偶然觀察。

#### 與現有研究的比較

**與電腦使用基準的比較**

既有電腦使用基準（如 OSWorld、WebArena、ScreenAgent 等）大多假設內部一致、合作的單代理環境（single-agent environment），代理無需處理同儕矛盾或過時資訊。CLASHarness 的差異化定位在於：它明確引入「事實性矛盾」與「時序性矛盾」，橫跨工具、檔案、視覺證據與同儕對話四個維度。這填補了「純執行基準」與「純文字多代理基準」之間的空白地帶。

**與多代理基準的比較**

現有多代理評估（如 MultiAgentBench、AgentVerse 等）多侷限於純文字對話（pure-text dialogue），缺乏視覺與操作維度。CLASHarness 將多代理衝突從抽象對話推進到具體的電腦使用情境，使衝突解決成為可觀察、可驗證的操作行為，而非僅是文字回應品質。

**與知識衝突研究的比較**

既有知識衝突（knowledge conflict）研究主要探討模型記憶與檢索文字之間的矛盾，屬於純文字 QA 範疇。CLASHarness 將此概念擴展至多模態操作領域，並引入時序動態——過時證據與即將到期的授權要求代理採取基於視覺的行動，而非僅依賴文字推理。

**改進與侷限性**

改進方面，CLASHarness 透過「預先提交基準事實」與「執行編譯驗證」雙機制，從根本上解決了基準建構中長期困擾研究社群的「任務不可解」問題。其階層式管線也為後續基準的可擴展性提供了範本。

侷限性方面，CLASHarness 的衝突類型仍以「二元對立」為主（兩個競爭主張中擇一），尚未涵蓋更複雜的多方衝突或動態演化的衝突鏈。此外，雖然涵蓋 20 個領域，但每個領域的深度可能受限於生成管線的自動化程度，人工策展的細緻度仍難以完全複製。最後，評估集中於「任務成功率」單一指標，對代理推理過程的可解釋性分析仍較有限。

#### 可重現性評估

從論文提供的資訊評估 CLASHarness 的可重現性：

**程式碼與框架**

論文描述了完整的八步驗證式微觀管線與階層式合成架構，理論上支援重建。然而，論文中並未明確聲明程式碼是否開源，也未提供 GitHub 儲存庫連結。作為 Google 內部研究，部分實作細節（如具體的領域模板、衝突軸線分類法、評分器編譯邏輯）需依賴附錄或補充材料才能完整重現。

**資料集**

600 輪任務、7,970 個視覺素材與 3,760 個評分器的規模是可量化的，但論文中未明確說明資料集是否公開釋出、釋出格式為何、以及是否包含環境渲染所需的底層基礎設施（如作業系統快照、應用程式狀態）。

**模型權重與評估結果**

15 個前沿模型的評估結果在論文中以瓶頸分析形式呈現，但具體的逐模型數據表、任務層級成功率、錯誤分類細目等需仰賴附錄。對於希望重現或延伸實驗的研究者而言，這些細節至關重要。

**整體可重現性評級**

基於現有資訊，CLASHarness 的概念與方法論具有高度可重現性，但實作層面的可重現性受限於程式碼與資料集的釋出狀態。建議作者在最終版本中明確聲明開源計畫，或至少釋出基準子集與評估腳本，以利社群驗證與延伸。

#### 未來研究方向

**方向一：動態衝突演化**

CLASHarness 目前的衝突設計偏向靜態預設——基準事實在生成時即固定。延伸方向可探索「動態衝突鏈」，即基準事實隨代理動作或環境時間推移而演變，使代理必須在多輪互動中持續重新校準信任。這將更貼近真實世界中「滾動式不確定性」的情境。

**方向二：協調協議的形式化與學習**

鑑於「收尾動作失敗率超過 58%」的發現，未來研究可聚焦於將協調協議（共享鎖釋放、任務交接、資源回收）形式化為可學習的策略，或將其整合至代理的動作空間中作為一等公民。這需要結合程序語意學（process semantics）與強化學習，以訓練出協議感知的代理。

**方向三：測試階段推理計算的邊際效應**

CLASHarness 提供了一個絕佳的實驗場域，可系統性研究測試階段推理計算（test-time compute scaling）對多輪衝突解決的影響。初步文獻指出，在開放式代理環境中，過度推理可能誘發「過度思考」（overthinking）與重複動作迴圈。CLASHarness 可用於繪製「推理計算—任務成功率」曲線，識別最佳推理深度。

**方向四：跨模態信任校準**

「視覺對齊 vs. 盲目信任」的瓶頸暗示需要發展更精緻的信任校準機制——代理應能根據來源可靠性（視覺觀察、同儕報告、自身記憶）動態調整證據權重。這涉及不確定性量化、貝氏推理與多源資訊融合等技術的整合。

**方向五：基準建構範式的擴散**

CLASHarness 的「預先提交基準事實 + 執行編譯驗證」範式可推廣至其他代理基準建構場景（如機器人操作、嵌入式系統、網路安全），解決長期存在的「任務不可解」與「評分標準漂移」問題。這將是對整個代理評估社群的結構性貢獻。

**方向六：人機協作中的衝突解決**

CLASHarness 目前聚焦於代理間衝突，但真實部署中常涉及「人機衝突」——人類指令與環境事實或代理觀察相矛盾。延伸研究可探索代理在面對人類錯誤指令時的行為模式，以及如何設計「禮貌但正確」的反饋機制。

## 論文問答

**Q1：CLASHarness 主要解決什麼核心問題？**
A：CLASHarness 旨在解決視覺語言模型（VLM）在多代理電腦使用情境中，面臨「衝突解決」能力缺乏系統性評估的問題。傳統基準多假設環境資訊一致且代理間完全合作，但真實協作中常出現子代理回報過時狀態、發出矛盾指令、或爭奪共享權限等情況。CLASHarness 透過建構 600 個多輪衝突任務，迫使代理必須主動檢查同儕輸出、查驗視覺證據並修正系統狀態，從而將衝突解決從被動的文字分類轉變為主動的調查與決策過程。

**Q2：為何現有的基準無法有效評估多代理衝突？**
A：現有基準存在兩大根本缺陷：其一，電腦使用類基準（如 OSWorld、WebArena）多假設單代理、單一一致環境，未涵蓋代理間的資訊矛盾；其二，多代理評估多侷限於純文字對話，無法反映視覺儀表板、即時遙測等多模態證據的角色。此外，手工策展任務難以擴展，而無約束的 LLM 提示生成則會產生敘事漂移、答案洩漏、未對齊的視覺素材及無法滿足的評分標準等問題，使得任務在構造上即不可解。

**Q3：為什麼衝突解決能力在真實多代理系統中至關重要？**
A：在真實部署環境中，子代理常依賴過時快取回報部署成功並催促路由生產流量，但即時遙測卻顯示健康檢查失敗；若代理盲目信任同儕報告，將導致嚴重的營運事故。因此，代理必須能交叉查驗視覺證據、執行組態回退或任務交接，才能避免災難性決策。這種「不能盲從、必須查證」的需求，正是 CLASHarness 試圖系統化量化的核心能力。

**Q4：CLASHarness 的核心方法論是什麼？**
A：CLASHarness 採用「階層式分階段合成管線」，將情境生成拆解為宏觀情境規劃與驗證式微觀執行兩個層次，以避免長程生成中的上下文溢位與敘事漂移。每個衝突輪次被形式化為五元組 (W₀, I, T, v★, Φ)，其中 v★ 為預先提交的決定性視覺事實，Φ 為從參考軌跡編譯出的混合評分器集合。這種「先承諾、後渲染、再驗證」的設計，從構造上保證每個任務皆可解。

**Q5：CLASHarness 在生成管線上有哪三大關鍵創新？**
A：第一是「階層式分階段合成」，將巨觀情境規劃與微觀執行分離，防止跨輪次的上下文溢位；第二是「預先提交的多模態對齊」，在環境渲染前即決定視覺真實標籤，確保視覺證據是推理的必要條件而非裝飾；第三是「執行編譯式驗證」，將精確程式碼檢查與範圍式語義檢查直接從已執行的參考軌跡編譯而成，杜絕無法滿足的評分標準。

**Q6：CLASHarness 透過哪些設計選擇來保證任務可驗證性？**
A：CLASHarness 透過「solvable by construction」（構造上可解）原則實現驗證保證：所有評分器皆從實際執行的參考軌跡編譯而來，而非由 LLM 自由撰寫；視覺資產在渲染前即預先提交決定性數值，使代理必須透過觀察才能取得真實標籤；同時採用 10 輪一組的「任務包裹」設計，讓工作空間在多輪間持續演化，模擬真實的時序累積效應。這些設計共同排除了答案洩漏與無解任務的可能性。

**Q7：CLASHarness 評估了哪些模型與基準規模？**
A：研究團隊評估了 15 個前沿模型，涵蓋不同規模與架構的視覺語言模型。基準規模包含 20 個操作領域、600 個可執行的衝突輪次、7,970 個預先提交的視覺資產，以及 3,760 個強制進行對齊視覺推理的混合評分器。這是目前規模最大、且唯一專注於多代理衝突解決的電腦使用基準。

**Q8：實驗揭示了哪三大系統性瓶頸？**
A：第一是「視覺對齊 vs. 盲從」：弱模型盲目遵循誤導性資訊，而強模型會主動檢查視覺證據以驗證真實標籤；第二是「解決 vs. 偵測」：代理雖能識別矛盾，但主動修復系統狀態時任務成功率顯著下滑；第三是「協調崩潰」：即便是前沿模型，在收尾動作上仍有超過 58% 的失敗率，常忘記釋放共享鎖或將任務交接給子代理，凸顯協調協議是普遍性瓶頸。

**Q9：CLASHarness 是否進行了消融實驗或診斷分析？**
A：CLASHarness 透過分層評分器設計本身就內建了診斷能力：精確程式碼檢查可定位代理是否執行了正確的系統狀態變更，而範圍式語義檢查則評估代理的推理品質。此外，實驗將「偵測衝突」與「解決衝突」分開計分，得以量化「看得到但修不好」的能力落差；對收尾動作的獨立分析則揭示了協調協議這一獨立於核心推理的瓶頸維度。

**Q10：CLASHarness 適用於哪些實際應用情境？**
A：CLASHarness 涵蓋 20 個操作領域，模擬的場景包括部署協調（子代理回報部署成功但健康檢查失敗）、組態管理（多代理競爭編輯同一檔案）、權限交接（共享鎖未釋放導致死鎖）等。這些情境對應於 DevOps、IT 營運、雲端基礎設施管理、軟體工程協作等真實工作流程，對於建構可靠的企業級多代理系統具有直接參考價值。

**Q11：從 CLASHarness 的發現中，產品開發應注意哪些考量？**
A：產品設計者應避免過度信任子代理的自我回報，必須在系統中內建「視覺查證」機制，例如強制代理在執行高風險動作前截圖確認儀表板狀態。同時，應將「釋放共享鎖」與「任務交接」等收尾動作設計為一階的、可被驗證的工作流程步驟，而非隱性行為。此外，產品應區分「偵測能力」與「修復能力」，因為兩者在現有模型上存在顯著落差。

**Q12：CLASHarness 對多代理系統研究領域有何更廣泛的影響？**
A：CLASHarness 將多代理評估從純文字對話推進到多模態電腦使用領域，填補了「知識衝突」研究在視覺與時序維度上的空白。它提出的「預先提交視覺真實標籤」與「執行編譯式驗證」範式，可被推廣至其他需要構造性可解保證的基準建構。此外，其揭示的「協調協議瓶頸」為未來研究指明了新方向：僅提升推理能力不足以建構可靠的多代理系統，必須同步發展協調機制。

**Q13：CLASHarness 存在哪些已承認的限制？**
A：CLASHarness 的衝突場景雖涵蓋 20 個領域，但仍屬於受控合成情境，與真實生產環境的複雜度可能存在落差。其評分器依賴於參考軌跡的執行，這雖保證可解性，但也限制了任務的多樣性上限。此外，基準聚焦於「衝突解決」單一維度，未涵蓋長期規劃、創造性協作等其他多代理能力面向。

**Q14：實驗中觀察到哪些典型的失敗案例？**
A：典型失敗包括：弱模型在子代理回報「部署成功」後直接路由生產流量，未查證健康檢查儀表板；代理雖注意到檔案版本矛盾，卻未執行組態回退；以及代理完成核心任務後忘記釋放共享鎖或未將任務正式交接給下一個子代理，導致工作流程中斷。這些案例凸顯了「偵測後未行動」與「行動後未收尾」兩類系統性失誤模式。

**Q15：CLASHarness 為未來研究指出了哪些方向？**
A：未來方向包括：發展專門的「衝突解決」訓練方法，以縮小偵測與修復之間的能力落差；設計更強健的協調協議，使代理能可靠地執行收尾動作；將 CLASHarness 的可控生成範式擴展至長期、多日級的協作情境；以及探索測試時推理計算（test-time compute）對多輪衝突解決的影響，因為在開放式代理環境中，過度推理可能引發重複動作迴圈而非提升表現。

## 實務應用指南

### 適用場景

1. **企業 IT 自動化中的多代理協作評估**：在 CI/CD、雲端基礎設施管理、監控告警等場景中，多個子代理（部署代理、監控代理、配置代理）需要協作。CLASHarness 可用於評估主代理是否能正確識別子代理回報的過時狀態，並依據即時遙測（live telemetry）做出正確決策，例如拒絕將生產流量（production traffic）路由到健康檢查失敗的部署。

2. **客服與內部工作流程中的衝突解決訓練**：當多個自動化代理同時處理工單、文件審核或權限申請時，常會出現矛盾指令或重複鎖定共享資源的情況。CLASHarness 的 600 輪任務可作為訓練環境，幫助代理學會釋放共享鎖（shared lock）並完成任務交接（task handoff）。

3. **AI 程式碼助手的多檔案協作測試**：在大型軟體專案中，多個編碼代理可能同時修改共享檔案、產生衝突的程式碼建議。CLASHarness 的視覺儀表板（visual dashboard）與終端輸出場景可延伸用於測試代理是否能透過視覺證據（visual evidence）驗證同儕代理（peer agent）的輸出。

4. **機器人流程自動化（RPA）中的權限競爭評估**：在多代理 RPA 系統中，代理常需競爭檔案、API 配額或資料庫鎖。CLASHarness 的收尾動作（closing action）失敗率（>58%）揭示了此類場景的關鍵瓶頸，可作為 RPA 廠商改進協調協議（coordination protocol）的基準。

5. **學術研究中的多代理衝突基準**：對於研究多代理系統、視覺語言模型（VLM）推理、或測試時間計算（test-time compute）的研究者，CLASHarness 提供了一個可重現、可驗證的基準，避免手動策展（manual task curation）的擴展性問題。

### 實作前置條件

**資料需求**
- 至少 20 個操作領域的領域知識（雲端、資料庫、CI/CD、監控等），用於建構宏觀情境規劃（macro scenario planning）的種子資料庫。
- 視覺素材庫：儀表板截圖、終端輸出、系統架構圖等，需支援預先提交（pre-committed）的決定性視覺事實（decisive visual fact）。
- 參考軌跡（reference trajectory）資料：每個任務需有一條可執行的正解路徑，用於編譯混合評分器（hybrid grader）。

**運算資源**
- 視覺渲染環境：需具備可程式化生成並截圖的 GUI 環境（瀏覽器、桌面應用、終端模擬器）。
- 沙盒執行環境：每個任務需在隔離環境中執行，以避免代理動作污染其他任務狀態。
- 評估算力：15 個前沿模型（frontier model）的評估需大量 GPU 時間，建議使用雲端彈性運算。

**技能需求**
- 熟悉視覺語言模型的提示工程與多模態對齊（multimodal grounding）。
- 具備程式碼評分器（code grader）與語義評分器（semantic grader）的設計能力，能從參考軌跡自動編譯檢查邏輯。
- 理解多代理系統的協調協議設計，例如鎖管理、任務交接、狀態同步。
- 具備階層式分階段合成（hierarchical phased synthesis）的系統設計經驗，以避免上下文溢位（context overflow）。

### 實作步驟建議

**步驟一：建立領域種子庫**
從 20 個操作領域出發，定義每個領域的典型衝突模式（過時快取、矛盾指令、權限競爭）。每個領域至少準備 30 個情境種子，作為 10 輪任務包（package）的起點。

**步驟二：設計階層式生成管線**
將生成流程分為兩層：上層做宏觀情境規劃（macro scenario planning），定義任務包的整體劇情與衝突演進；下層做驗證式微觀執行（verified micro-execution），每輪任務獨立生成並驗證。這個分離避免了敘事漂移（narrative drift）與答案洩漏（answer leakage）。

**步驟三：實作預先提交的多模態對齊**
在渲染視覺環境之前，先決定每輪任務的決定性視覺事實（decisive visual fact），例如「健康檢查失敗的 HTTP 500 狀態碼」。然後據此生成對應的儀表板截圖，確保視覺證據是解題的必要線索，而非裝飾性的未對齊視覺素材（ungrounded visual asset）。

**步驟四：執行參考軌跡並編譯評分器**
由人類專家或強模型執行每個任務的正解路徑，記錄完整的動作序列與最終狀態。從這條參考軌跡自動編譯混合評分器：精確程式碼檢查（exact code check）用於驗證系統狀態變更，範圍式語義檢查（scoped semantic check）用於評估開放性決策品質。這保證了每個任務在構造上即可解（solvable by construction）。

**步�驟五：執行八步驟驗證式微觀管線**
對每輪任務執行驗證流程：(1) 確認指令明確無歧義；(2) 確認視覺證據與決定性事實一致；(3) 確認參考軌跡可執行；(4) 確認評分器可通過正解；(5) 確認無自動洩漏；(6) 確認評分器可區分錯誤動作；(7) 確認多輪間狀態隔離；(8) 確認收尾動作可驗證。

**步驟六：批次評估並分析瓶頸**
在 600 輪任務上評估目標模型，記錄三類瓶頸指標：視覺對齊 vs 盲目信任（visual grounding vs. blind trust）、解決 vs 偵測（resolution vs. detection）、協調失敗率（coordination breakdown）。根據結果調整訓練資料或提示策略。

**步驟七：建立持續更新機制**
定期新增領域與衝突模式，避免模型過擬合特定情境。收集評估中發現的新失敗案例，反向豐富種子庫。

### 潛在風險與注意事項

**風險一：評分器過於嚴格導致誤判**
混合評分器從參考軌跡編譯，可能無法涵蓋所有合理的解題路徑。緩解方式：在範圍式語義檢查中設定容忍度，並定期抽樣人工覆核低分案例。

**風險二：視覺渲染成本過高**
每輪任務都需生成並截圖視覺環境，600 輪任務的渲染時間可能成為瓶頸。緩解方式：使用快取機制重用相似情境的視覺素材，並優先渲染高價值場景。

**風險三：模型過擬合特定衝突模式**
若評估結果用於訓練，模型可能學會「看到子代理回報就反轉」的捷徑，而非真正理解視覺證據。緩解方式：在評估中加入「無衝突」的控制組，確保模型不會對所有子代理輸出產生不信任偏差。

**風險四：參考軌跡本身存在偏誤**
若參考軌跡由強模型生成，可能帶有特定模型的解題偏好。緩解方式：由多元背景的人類專家審核參考軌跡，並定期輪換生成來源。

**風險五：協調協議評估的可重現性**
收尾動作（釋放鎖、交接任務）的評估依賴系統狀態的精確記錄，若審計日誌（audit effect log）不完整，可能誤判。緩解方式：強化審計日誌的結構化記錄，並對收尾動作設計獨立的檢查點。

**風險六：領域覆蓋的不平衡**
20 個操作領域的難度與代表性可能不均，導致某些領域的評估結果不具統計意義。緩解方式：在報告結果時按領域分層呈現，並對小樣本領域進行 bootstrap 信賴區間估計。

### 與其他技術的整合建議

**與現有多代理框架整合**
CLASHarness 的任務格式可適配 LangGraph、AutoGen、CrewAI 等多代理框架。建議將 CLASHarness 的工作空間（workspace）抽象為框架的環境介面，並將評分器封裝為框架的回呼函式，使現有代理可直接在 CLASHarness 上評估。

**與視覺語言模型評估套件整合**
可將 CLASHarness 的視覺證據場景整合到 MMBench、MMStar 等 VLM 評估套件中，作為「多模態對齊」維度的補充測試。特別是 CLASHarness 揭示的「盲目信任」問題，可與現有 VLM 的幻覺評估互補。

**與 CI/CD 與監控系統整合**
在企業環境中，可將 CLASHarness 的衝突場景映射到真實的 Prometheus、Grafana、ArgoCD 等系統的模擬環境，使評估結果直接反映生產環境的風險。建議建立一個「衝突注入器」，在 staging 環境中重現 CLASHarness 的場景。

**與測試時間計算（test-time compute）研究整合**
CLASHarness 提供了測試推理努力對多輪執行影響的實驗場域。可與現有的推理模型（如 o1、DeepSeek-R1）結合，評估「過度思考」（overthinking）與重複動作迴圈（repetitive action loops）在衝突場景中的表現。

**與知識衝突（knowledge conflict）研究整合**
CLASHarness 的多模態衝突場景可與純文字的知識衝突研究（如 ECQA、KIE）互補。建議建立一個統一的衝突分類法，涵蓋記憶 vs 檢索、視覺 vs 文字、子代理 vs 環境等維度。

**與安全與合規工具整合**
CLASHarness 揭示的協調失敗（如未釋放鎖、未交接任務）可能導致安全風險。建議將 CLASHarness 的評估結果與 SAST、SCA 等安全工具的輸出關聯，建立「協調安全」指標。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與第 1 節的「三個核心瓶頸」段落，建立對多代理衝突問題的直覺理解。接著閱讀第 3.1 節的問題形式化，理解一個衝突任務的數學結構（工作空間、指令、動作空間、決定性值、評分套件）。最後瀏覽第 5 節的實驗結果，觀察 15 個模型的具體失敗模式，例如「盲目信任誤導性資訊」與「忘記釋放共享鎖」。初學者應專注於理解問題的直覺，而非實作細節。

**給 AI 工程師**：建議從第 3 節的生成管線開始，重點理解「階層式分階段合成」、「預先提交的多模態對齊」、「執行編譯式驗證」三個設計原則如何避免敘事漂移與答案洩漏。接著閱讀第 4 節的基準統計（600 輪、20 領域、7,970 視覺素材、3,760 評分器），評估將 CLASHarness 整合到現有評估管線的可行性。最後參考第 5 節的瓶頸分析，設計針對性的提示工程或微調策略，特別是針對收尾動作失敗率（>58%）的問題。

**給研究者**：建議完整閱讀第 3 節的形式化與管線設計，特別是「驗證式微觀管線」如何保證構造上可解（solvable by construction）。接著深入第 5 節的消融實驗與錯誤分析，尋找可延伸的研究問題，例如：測試時間計算對衝突解決的影響、視覺對齊能力的可遷移性、多代理協調協議的理論建模。CLASHarness 也可作為新方法（如強化學習、憲法 AI、形式化驗證）的實驗平台。

**給產品經理**：建議先閱讀摘要與第 1 節的動機段落，理解「真實協作很少建立在一致資訊上」這個核心問題。接著閱讀第 5 節的三個瓶頸，將其映射到自家產品的風險場景：子代理是否會回報過時狀態？代理是否能識別視覺證據與同儕回報的矛盾？代理是否會忘記釋放資源或交接任務？最後參考「實作步驟建議」，規劃將 CLASHarness 整合到產品評估流程的時程與資源。產品經理應關注瓶頸的相對優先級，而非技術細節。
