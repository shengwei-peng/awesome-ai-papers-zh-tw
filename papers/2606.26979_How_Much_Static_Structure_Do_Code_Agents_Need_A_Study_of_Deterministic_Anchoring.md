# 程式碼代理需要多少靜態結構？確定性錨定之研究

**原文標題：** How Much Static Structure Do Code Agents Need? A Study of Deterministic Anchoring  
**作者：** Zhihao Lin、Mingyi Zhou、Yizhuo Yang 等 4 位作者  
**發布日期：** 2026-06-25  
**HF 連結：** [https://huggingface.co/papers/2606.26979](https://huggingface.co/papers/2606.26979)

## ⚡ TL;DR

基於LLM的程式碼代理僅靠關鍵字搜尋，忽略結構關係，導致導航行為隨機且難以重現。
提出CodeAnchor，以輕量靜態分析提取結構事實，並以純文字註解注入程式碼作為確定性錨點。
實驗顯示此法提升定位準確率與單次可靠性，縮短互動回合，並顯著降低執行間變異。

## 摘要翻譯

基於 LLM 的程式碼代理（LLM-based code agents）透過關鍵字搜尋（keyword search）在儲存庫中導航，卻忽略了諸如呼叫圖（call graphs）、繼承階層（inheritance hierarchies）與組態相依性（configuration dependencies）等定義軟體實際運作方式的結構關係（structural relationships）。這使得代理導航具有隨機性，且難以在執行間重現。我們探討輕量級靜態分析（lightweight static analysis）是否能為這些代理提供確定性錨點（deterministic anchors）：以純文字註解（plain-text comments）形式注入的穩定的結構性事實，用以約束機率性探索（probabilistic exploration）並使導航更具可預測性。我們以 OpenAI 的 Codex 這一強大基線為起點，系統性地注入不同粒度（granularity）的結構性註釋（structural annotations），並衡量其對定位（localization）、軌跡行為（trajectory behavior）與執行間穩定性（run-to-run stability）的影響。我們的研究發現了所謂的確定性錨定效應（deterministic anchoring effect）：靜態結構的助益較少來自於讓代理「更聰明」，而更多來自於使其導航更具紀律性且可重現。三項觀察支持此發現：(1) 錨定有效：輕量級呼叫/繼承拓樸（lightweight call/inheritance topology）提升了函式層級定位（function-level localization）（+2.2pp Func@5）並縮短軌跡（平均減少 1.6 個互動回合（interaction rounds））；(2) 錨定具有規模敏感性（scale-sensitive）：最佳粒度（granularity）與方向性（directionality）取決於儲存庫特性（repository characteristics），其中更密集的語義（denser semantics）呈現報酬遞減（diminishing returns），而樞紐密集型專案（hub-heavy projects）受益於僅逆向連

## 深度分析

#### 方法論解析

本文的核心命題在於解決以 grep 為優先的檢索（grep-first retrieval）與真實軟體結構之間的表徵不匹配（representation mismatch）。當前基於 LLM 的程式碼代理（LLM-based code agents）——無論是商業系統如 Copilot Workspace、Claude Code、Gemini Code Assist，或是開源研究代理如 SWE-agent、SWE-Gym——皆高度依賴關鍵字搜尋（keyword search / grep/rg）進行儲存庫（repository）導航。這類方法雖具備跨語言（language-agnostic）、對損壞程式碼具有穩健性（robust to broken code）、無需重量級索引基礎設施（heavyweight indexing infrastructure）等優勢，卻本質上無視結構的檢索（structure-blind retrieval）：grep 僅按詞彙準則（lexical criteria）回傳行級匹配，無法暴露呼叫圖（call graphs）、繼承階層（inheritance hierarchies）、組態相依性（configuration dependencies）等結構關係（structural relationships）。

作者由此提出確定性錨點（deterministic anchors）概念：針對給定程式碼快照（code snapshot）為固定不變的結構事實（structural facts），以輕量級靜態分析（lightweight static analysis）離線萃取後，注入為原始碼中的純文字註解（plain-text comments）。這些結構性註釋（structural annotations）被稱為 CodeAnchor tags（標籤），與函式、類別、組態項目共位（colocated）。執行期（runtime）代理仍維持原有以 grep 為優先的檢索迴路，但檢索結果中夾帶的標籤可實現檢索短路化（retrieval short-circuiting）：當代理檢視某一實體時，周圍標籤已直接揭示其結構拓樸（structural topology）中的鄰近連結（如呼叫者/被呼叫者、組態讀寫、繼承關係），無需再透過額外的多跳查詢（multi-hop queries）重新發現這些連結。

具體而言，CodeAnchor 框架的離線階段採用 PyCG 生成呼叫圖（call graphs）並輔以 AST extractors 萃取繼承、資料流與組態使用等關係；隨後將這些關係編碼為緊湊的結構性註釋區塊注入原始碼。如圖 1 所示，標籤分為多個類別：檔案層級後設資料（File Annotation）、函式層級語義（Function Annotation，包含 invokes、reads、writes、handles、globals、contexts 等），並以圖示與文字並陳的方式提升可讀性。這種設計的巧妙之處在於完全不改變代理的控制邏輯或推理架構，僅透過環境塑型（environmental scaffolding）約束機率性探索（probabilistic exploration），使隨機的（stochastic）LLM 控制器在結構導引下產生更有紀律的導航行為。

在變因設計上，作者進一步區分粒度（granularity）與方向性（directionality）兩個維度。粒度控制語義密度，從輕量級呼叫/繼承拓樸（lightweight call/inheritance topology）到更密集的語義（denser semantics）；方向性則區分正向邊（forward edges，如「我呼叫誰」）與僅逆向連結（inverse-only links，如「誰呼叫了我」）。這使得研究能夠回答：不同儲存庫特性（repository characteristics）下，何種結構資訊的邊際價值（marginal value）最高，而非一概而論地堆砌圖結構。

#### 實驗數據解讀

本研究以 Codex 作為強基線（strong baseline），在 SWE-bench Lite 與 SWE-bench Verified 上進行評估，並將軌跡品質與穩定性（trajectory quality and stability）視為與正確性同等重要的首要成果（first-class outcomes）。三個研究問題（RQ1–RQ3）的數據呈現出高度一致的敘事：確定性錨定效應（deterministic anchoring effect）的本質並非讓代理「更聰明」，而是透過穩定的結構線索使其導航行為更可預測、可重現。

在 RQ1（拓樸是否有幫助）中，注入基礎呼叫與繼承拓樸後，函式層級定位（function-level localization）指標 Func@5（函式定位指標）提升 2.2 個百分點（+2.2pp），同時互動回合（interaction rounds）減少 1.6 輪。這顯示輕量級結構資訊不僅提升定位準確率（localization accuracy），更顯著改善互動效率——每一輪減少都意味著一次 LLM 呼叫與檢索延遲的節省，對於端到端修復基準（end-to-end repair benchmarks）的實用價值不容小覷。

RQ2（粒度與方向性）揭示出關鍵的規模敏感（scale-sensitive）現象。實驗發現更密集的語義（denser semantics）呈現報酬遞減（diminishing returns），並非越多越好；而在樞紐密集型專案（hub-heavy projects）中，僅保留僅逆向連結（inverse-only links）反而優於包含正向邊（forward edges）的完整拓樸。這項發現極具工程洞察力：當某些函式被大量呼叫時，正向邊會產生過長的 callee 列表，反而成為雜訊；而逆向連結能精準暴露「誰依賴此元件」，對缺陷定位的訊噪比（signal-to-noise ratio）更高。這意味著結構資訊的價值高度依賴儲存庫特性（repository characteristics），不存在放諸四海皆準的最優標籤策略。

RQ3（行為改變與穩定性）則是本文最具軟體工程意涵的貢獻。數據顯示，結構標籤將連結追隨率（link-following rate）從 0.15–0.18 提升至 0.21–0.24，證明代理確實會利用這些確定性錨點（deterministic anchors）進行導航，而非忽略註解。更重要的是，執行間變異（run-to-run variance）大致減半，且在中等規模儲存庫上單次執行可靠性指標 Pass@1（單次執行通過率指標）提升 3.4 個百分點（+3.4pp）。這直接回應了軟體工程實務對可檢視且可重現（inspectable and reproducible）代理行為的需求——即使最終修復結果相同，穩定的軌跡（stable trajectories）能大幅降低除錯與審查成本。當然，這些收益伴隨約 10% 的輸入詞元（input tokens）增長，屬於可接受的邊際成本。

綜合解讀，確定性錨定效應（deterministic anchoring effect）應被理解為一種「行為約束」而非「能力增強」。基線代理已足夠強大，甚至勝過諸多基於圖的方法（graph-based approaches）；結構性註釋（structural annotations）的價值在於降低隨機性（stochasticity）導致的早期分支（early branching）與探索決策（exploration decisions）差異，從而抑制脆弱的軌跡（brittle trajectories）。

#### 與現有研究的比較

相較於既有文獻，本研究的定位清晰且具差異化。首先，在檢索典範上，多數端到端修復基準（end-to-end repair benchmarks）中的頂尖系統已收斂於以 grep 為優先的檢索（grep-first retrieval）搭配強 LLM 推理。本文並未拋棄這一成功架構去建構基於圖的方法（graph-based approaches）或圖導引控制器（graph-guided controller），而是證明透過輕量級靜態分析（lightweight static analysis）與純文字註解（plain-text comments）即可在保留原有優勢（速度、跨語言、穩健性）的前提下，補強其結構盲點。這與過往需要 heavyweight indexing infrastructure 的圖導引方案形成鮮明對比。

其次，在評估指標上，現有研究多聚焦於聚合正確率（如最終修復率），而本文將軌跡行為（trajectory behavior）與執行間穩定性（run-to-run stability）提升為首要成果（first-class outcomes）。近期雖有文獻指出工具使用代理對探索決策（exploration decisions）與早期分支（early branching）高度敏感，但鮮少提出低成本、高相容性的結構性解方。CodeAnchor 的設計本質上是一種確定性錨點（deterministic anchors），直接針對此痛點，並以連結追隨率（link-following rate）與執行間變異（run-to-run variance）等行為指標量化其效益。

然而，本研究亦存在可辨識的限制。其一，實驗僅於 Codex 上進行，未涵蓋 Claude 3.5 Sonnet、GPT-4o 或其他開源權重模型，因此確定性錨定效應（deterministic anchoring effect）在不同 LLM 世代間的泛化性尚待驗證。其二，靜態分析（static analysis）工具鏈以 PyCG 為核心，目前實質上聚焦 Python，雖然概念上語言無關（language-agnostic），但要複製到其他語言仍需額外工程。其三，作者提出的實務準則（中等專案預設輕量拓樸、大型儲存庫修剪正向邊、隱性相依案例保留密集標籤）仍屬啟發式規則，尚未自動化，意味著使用者需具備對儲存庫特性（repository characteristics）的先驗判斷。

#### 可重現性評估

從可重現性角度檢視，本研究具備部分有利條件，亦存在明確缺口。資料集方面，SWE-bench Lite 與 SWE-bench Verified 均為公開基準，任何研究者皆可取得。模型方面，Codex（OpenAI）雖為商業 API，但具備可取得性（accessibility），只要擁有 API 權限即可復現基線與實驗組。靜態分析（static analysis）所使用的 PyCG 與 AST extractors 亦為學界已知工具，理論上可依論文描述重建離線標籤生成流程。

然而，根據目前提供的全文脈絡，作者並未明確宣告 CodeAnchor 框架的原始碼釋出狀態，亦未提供模型權重（model weights）——後者對 Codex 這類閉源商業模型本就預期之中，但前者（開源框架與實驗腳本）的缺位會顯著提高獨立復現門檻。儘管方法論描述詳盡，包含標籤格式、注入位置、粒度（granularity）與方向性（directionality）的定義，但缺乏官方實作仍可能導致復現者在細節（如標籤排序、截斷策略、與 grep 結果的拼接方式）上產生偏差。建議作者群於正式出版時釋出原始碼與標籤生成管線，以符合 ISSTA 對 artifact evaluation 的期待。

#### 未來研究方向

基於本文確定性錨點（deterministic anchors）的框架與發現，以下幾個方向值得深入探索：

第一，**語言無關（language-agnostic）的靜態分析（static analysis）擴展**。目前 PyCG 侷限於 Python，未來可整合 Tree-sitter、Language Server Protocol（LSP）或 LLVM/Clang 前端，將 CodeAnchor 推廣至多語言儲存庫，驗證結構性註釋（structural annotations）在 Java、C++、Rust 等靜態類型語言中的錨定效果是否更強（因此類語言的繼承階層與呼叫圖通常更為明確）。

第二，**自適應粒度（adaptive granularity）與方向性選擇**。本文發現最適粒度（granularity）與方向性（directionality）取決於儲存庫特性（repository characteristics），未來可訓練輕量級分類器或啟發式評分函數，依據儲存庫的模組耦合度、樞紐集中度（hub concentration）與程式碼規模，自動決定是否修剪正向邊（forward edges）或採用密集語義（denser semantics），從而消除人工準則的負擔。

第三，**動態與靜態混合錨點**。確定性錨點（deterministic anchors）雖穩定，卻無法捕捉執行期行為。結合動態分析（dynamic analysis）或執行期剖析（runtime profiling）——例如失敗測試案例的覆蓋路徑、變數值流——可生成「動態標籤」，與靜態標籤互補，特別適用於隱性相依（implicit-dependency）與反射/依賴注入等靜態分析難以處理的情境。

第四，**詞元效率（token efficiency）最佳化**。當前標籤以純文字註解（plain-text comments）形式注入，導致輸入詞元（input tokens）增加約 10%。未來可研究結構化壓縮格式（如簡潔符號系統、階層式標籤編碼）或選擇性注入策略（僅於檢索結果 top-k 中注入標籤），在維持執行間穩定性（run-to-run stability）的前提下降低上下文長度。

第五，**與嵌入檢索（embedding-based retrieval）的協同**。本文聚焦於強化以 grep 為優先的檢索（grep-first retrieval），但未來可探討將確定性錨點（deterministic anchors）融入向量語義搜尋：例如將結構性註釋（structural annotations）納入 chunk 後設資料，或在重排序（reranking）階段利用結構拓樸（structural topology）打破語義相似度平局，進一步提升定位準確率（localization accuracy）。

第六，**多代理系統中的錨定同步**。在多重基於 LLM 的程式碼代理（LLM-based code agents）協作場景中，確定性錨點（deterministic anchors）可作為共享的結構參照框架，減少不同代理間因隨機性（stochasticity）產生的探索路徑發散，提升協作一致性與可檢視性（inspectability）。

## 論文問答

**Q1：基於 grep 的程式碼代理在導航儲存庫時面臨什麼根本性問題？**
A：現有的基於 LLM 的程式碼代理普遍採用以 grep 為優先的檢索架構，這種方法僅依賴詞彙準則進行關鍵字搜尋，無法暴露組織真實軟體運作的結構關係，例如呼叫圖、繼承階層與組態相依性。這種表徵不匹配使得代理必須透過臨時性的多跳查詢重新發現結構連結，導致上下文碎片化且局部短視。因此，代理難以理解程式碼在結構拓樸中的實際位置，進而影響其定位準確率與導航效率。

**Q2：為何純粹的關鍵字檢索系統在程式碼代理中難以達成可重現性與穩定性？**
A：LLM 控制器本質上是隨機的，早期搜尋中的微小擾動會層層放大，最終導致質性上完全不同的導航路徑。當這種隨機性與無視結構的檢索結合時，就會產生脆弱的軌跡，使得同一任務的兩次執行可能造訪不同檔案、採取不同步數，甚至產生不同修補。這種行為不可預測性對實務工作者而言是嚴重的品質疑慮，因為他們需要代理行為是可檢視且可重現的，而非僅在統計上正確。

**Q3：為何軌跡穩定性與可重現性被視為與正確性同等重要的首要成果？**
A：從軟體工程的觀點來看，開發者與維護人員需要能夠檢視並重現代理的決策過程，才能對自主代理建立信任並進行除錯。如果代理的行為在不同執行間大幅擺盪，即使最終結果正確，也會增加驗證成本並降低實用價值。因此，將執行間穩定性提升為首要成果，有助於推動這類系統從研究原型走向實際的生產環境部署。

**Q4：CodeAnchor 的核心方法是什麼？它如何強化現有的 grep-first 代理？**
A：CodeAnchor 是一個輕量級框架，它透過離線靜態分析提取儲存庫中的結構關係，例如函式呼叫、繼承、資料流與組態使用情況。接著，這些結構事實會被注入原始碼中，成為與函式、類別及組態項目共位的純文字註解，即「確定性錨點」。在執行階段，代理仍維持原有的關鍵字查詢流程，但檢索結果會同時包含原始程式碼與鄰近的結構性註釋，使代理能夠在原地感知跨檔案的結構拓樸。

**Q5：什麼是「確定性錨定效應」？它與「讓代理變得更聰明」有何不同？**
A：確定性錨定效應是指靜態結構對代理的幫助主要並非來自於提升其推理能力或讓它「更聰明」，而是透過提供穩定的結構事實來約束機率性探索，使其導航行為更有紀律且可重現。這些確定性錨點對於給定的程式碼快照是固定的，因此不應隨著不同執行而變化，能有效減少代理透過臨時搜尋重新發現連結的需求。這項洞見的關鍵在於，改善 grep-first 代理並不需要放棄文字檢索或建構全新的圖導引控制器，而是透過輕量級的結構性註釋來穩定行為。

**Q6：作者為何選擇將結構性註釋以帶內純文字註解的形式注入，而非建構獨立的圖檢索系統？**
A：選擇純文字註解作為載體，是因為它能讓代理在無需重量級索引基礎設施的情況下，繼續使用現有且已相當強大的 grep-first 架構。由於標籤是帶內文字，它們能同時影響代理著陸的位置以及開啟檔案後的導航決策，從而實現檢索捷徑。此外，這種設計具有語言無關性，對損壞程式碼具有穩健性，並避免了維護獨立圖資料庫所帶來的系統複雜度。

**Q7：CodeAnchor 在哪些基準測試上進行評估？使用了什麼基線模型？**
A：本研究將 CodeAnchor 實例化於 OpenAI 的 Codex 模型之上，並在 SWE-bench Lite 與 SWE-bench Verified 兩個端到端修復基準上進行評估。所採用的基線本身已經大幅領先基於圖的方法，因此能夠精確衡量輕量級結構性註釋所帶來的邊際價值。這些基準測試涵蓋了真實的軟體缺陷修復任務，要求代理必須在完整儲存庫中進行導航與修改。

**Q8：注入確定性錨點後觀察到哪些主要的量化改善？**
A：實驗顯示，輕量級的呼叫與繼承拓樸能將函式層級定位指標 Func@5 提升 2.2 個百分點，並將互動回合縮短 1.6 輪。結構性標籤將連結追隨率從 0.15–0.18 提升至 0.21–0.24，同時將執行間變異大致減半。在中等規模儲存庫上，單次執行可靠性指標 Pass@1 也提升了 3.4 個百分點，代價則是輸入詞元數量增加約 10%。

**Q9：結構性註釋的粒度與方向性變化，如何影響不同規模儲存庫上的代理表現？**
A：研究發現確定性錨點具有規模敏感性，其最佳粒度與方向性取決於儲存庫特性，而非一成不變。更密集的語義雖然提供更多資訊，但往往出現報酬遞減現象，顯示過度註釋並不會帶來等比例效益。在樞紐密集型專案中，僅提供「誰呼叫了我」的逆向連結而不加入正向邊，反而能讓代理更有效率地導航，這意味著在大型儲存庫中修剪正向邊是一項有效的策略。

**Q10：在哪些類型的專案或情境中，確定性錨點最能發揮效益？**
A：確定性錨點在中等規模專案上效益最為顯著，因為輕量級拓樸能在不過度佔用上下文視窗的前提下，顯著改善定位與穩定性。對於存在大量隱性相依、難以透過單純關鍵字搜尋發現的程式碼庫，結構性註釋能直接揭示這些隱藏連結。此外，在呼叫關係高度集中的樞紐密集型專案中，適當裁剪後的逆向連結標籤能幫助代理快速識別關鍵呼叫者，避免在龐大正向邊中迷失。

**Q11：實務工作者在商業代理系統中部署確定性錨點時，應考量哪些權衡？**
A：部署時必須權衡軌跡品質與穩定性的提升，以及約 10% 的輸入詞元增加所帶來的推論成本與延遲上升。由於最佳註釋策略會隨儲存庫規模與結構而異，實務上需要針對不同專案調整粒度與方向性，而非採用單一通用設定。此外，雖然靜態分析相對輕量，但仍需隨著程式碼演進持續更新，以確保錨點所反映的結構關係不會過時。

**Q12：這項研究可能如何影響未來自主程式碼代理與檢索系統的設計？**
A：這項工作表明，未來的代理架構無需為了結構資訊而完全捨棄簡潔的文字檢索，轉而擁抱複雜的圖導引系統；相反地，透過輕量級結構性註釋增強文字視圖即可達到良好效果。將軌跡穩定性與執行間穩定性提升為首要成果，可能促使研究社群更重視有紀律、可重現的探索行為，而非僅追求端到端正確率的最大化。這樣的典範轉移有助於開發出更值得信賴、更易於維護的代理系統，使軟體工程師能更安心地將其整合進開發流程。

**Q13：本文承認的確定性錨點方法主要限制為何？**
A：此方法需要額外的輸入詞元來承載結構性註釋，這不僅增加計算開銷，在極大型程式碼庫中也可能逼近上下文視窗的上限。其效益呈現規模敏感性，同一套註釋策略無法均勻地適用於所有類型與規模的儲存庫。此外，本研究聚焦於特定的結構關係，對於某些無法透過輕量級靜態分析捕捉的語意相依性，錨點方法可能力有未逮。

**Q14：在什麼條件下，確定性錨點可能無法改善甚至損害代理表現？**
A：在超大型儲存庫中，過於密集的結構性註釋可能會引入雜訊並佔用寶貴的上下文空間，導致報酬遞減甚至負面效果。若靜態分析因動態語言特性或複雜建置系統而提取到錯誤或過時的關係，這些錯誤的錨點反而會誤導代理的導航決策。此外，對於結構耦合度極低或架構相對扁平的專案，拓樸資訊的價值有限，注入過多標籤可能只是徒增詞元負擔。

**Q15：這項工作為改善程式碼代理導航與穩定性指出了哪些未來研究方向？**
A：未來研究可探索自適應粒度機制，根據儲存庫特性與任務需求動態調整註釋的密度與類型。結合確定性錨點與動態分析以捕捉靜態分析無法觸及的執行期關係，也是極具潛力的方向。此外，發展更高效的結構資訊壓縮方法，在降低詞元開銷的同時保留導航效益，將有助於把這項技術推廣到更大規模的工業級程式碼庫。

## 實務應用指南

### 適用場景

1. **中型企業內部程式碼庫的缺陷自動定位**：針對數萬至數十萬行規模的中型儲存庫，團隊已採用基於 LLM 的程式碼代理進行缺陷修復，但苦於代理每次執行路徑不同、難以預測。注入輕量級呼叫／繼承拓樸作為確定性錨點，可在不更換檢索架構的前提下，將函式層級定位準確率（Func@5）提升約 2.2 個百分點，並縮短互動回合（-1.6 輪）。
2. **金融、醫療等合規場景的可審計自動維護**：在需要軌跡可檢視且可重現的產業中，代理的隨機探索與執行間變異是導入障礙。結構性註釋能將連結追隨率從 0.15–0.18 提升至 0.21–0.24，並大致減半執行間變異，使兩次執行在同一任務上造訪的檔案與步驟趨於一致，滿足審計需求。
3. **樞紐密集型微服務或單體架構的影響分析**：對於呼叫關係高度集中（hub-heavy）的專案，傳統 grep 檢索容易在核心模組附近迷失。此時僅注入逆向連結（inverse-only links，即「誰呼叫了我」），避免正向邊帶來的雜訊，可讓代理更有效率地收斂至關鍵函式。
4. **遺留系統現代化中的隱性相依性梳理**：老舊程式碼常存在組態相依性與跨模組資料流等難以透過關鍵字搜尋發現的結構。針對這類隱性相依區段，保留較密集的語義標籤（dense tags），可減少代理透過多跳查詢重新發現結構的機率，降低碎片化且局部短視的上下文風險。
5. **多工程師共用的 AI 輔助開發環境**：當團隊共用同一套代理服務時，若不同成員對同一缺陷描述得到截然不同的導航軌跡，將大幅增加協作成本。透過離線靜態分析產生的結構性註釋，能讓機率性探索受到穩定的事實約束，提升單次執行可靠性（Pass@1 +3.4 pp）。

### 實作前置條件

- **資料條件**：目標儲存庫需能通過基礎編譯或解析，以產生抽象語法樹（AST）與呼叫圖；若為 Python 專案，需確保 PyCG 等輕量級靜態分析器可處理其 import 結構。動態生成或過度損壞的程式碼區段需先標記排除。
- **運算資源**：離線分析階段無需 GPU，但需足夠記憶體建構儲存庫層級的結構拓樸（建議預留建置主機 2–4 倍原始碼大小的記憶體緩衝）。線上推論階段需額外承擔約 10% 的輸入詞元（input tokens）成本，並預留 LLM API 配額。
- **技能需求**：團隊需具備目標語言的 AST 基礎知識、能維護 grep/rg 檢索管線的 DevOps 能力，以及調整提示工程（prompt engineering）的經驗，以確保標籤在代理的上下文視窗中被正確解讀。若需整合至現有 CI/CD，則需具備基礎靜態分析工具鏈的腳本撰寫能力。

### 實作步驟建議

1. **建立強基線並量化不穩定性**：在現有以 grep 為優先的檢索管線上，先對標準任務集（如內部缺陷報告）執行多次，記錄 Pass@1、Func@5 與執行間變異，確認代理確實存在軌跡品質與穩定性問題。
2. **離線標籤生成**：選用輕量級靜態分析器提取呼叫圖、繼承階層、組態相依性與資料流，產生結構性註釋。避免重量級索引基礎設施，維持與現有文字檢索的相容性。
3. **依規模設計注入粒度**：
   - 中型專案：預設採用輕量級呼叫／繼承拓樸，完整注入雙向連結。
   - 大型儲存庫：裁減正向邊（forward edges），僅保留逆向連結與檔案層級中繼資料，避免標籤過度膨脹。
   - 隱性相依模組：針對組態傳播或反射式呼叫等難以搜尋的區域，才啟用更密集的語義標籤。
4. **管線整合與檢索短路**：將標籤以純文字註解形式嵌入原始碼旁，確保 grep/rg 無需修改即可檢索到。設計提示範本，讓代理在開啟檔案時優先閱讀鄰近的結構性註釋，實現檢索短路（retrieval short-circuiting）。
5. **穩定性驗證**：對同一任務執行至少 5–10 次，測量連結追隨率、互動回合數與執行間變異。若未觀察到確定性錨定效應，檢查標籤是否被截斷或提示設計未引導代理利用標籤。
6. **成本與維護盤點**：監控輸入詞元增量。若超過 15%，則回退至更稀疏的拓樸；同時在 CI/CD 中設定標籤自動重建流程，防止程式碼更新後結構事實過期。

### 潛在風險與注意事項

- **詞元與上下文長度膨脹**：結構性註釋雖僅增加約 10% 輸入詞元，但在大型檔案中可能擠壓實際程式碼的上下文空間。建議設定單一實體的標籤上限，或採用分層降級（先拓樸、後詳細語義）。
- **靜態分析誤報與過期**：損壞程式碼、動態生成或大量使用反射的區段，可能導致呼叫圖錯誤。需建立容錯機制，並在每次提交或夜間建置時重建標籤，避免過期錨點誤導代理。
- **規模敏感的過度泛化**：本文明確指出最適粒度與方向性取決於儲存庫特性。切勿將中型專案的成功配置直接套用到大型儲存庫，否則可能遭遇報酬遞減。
- **代理過度依賴標籤**：LLM 可能因標籤的存在而忽略實際程式碼邏輯，產生「幻覺轉移」。提示設計應強調原始碼優先，標籤僅作為導航輔助。
- **維護成本低估**：雖然標籤是純文字，但其與程式碼的同步需要持續的離線建置流程。若團隊缺乏 CI/CD 維護資源，反而會累積技術債。

### 與其他技術的整合建議

- **向量檢索與 RAG**：將 CodeAnchor 標籤同時寫入向量資料庫的中繼資料欄位，讓語意搜尋與 grep 檢索互補。標籤提供確定性結構，向量提供語意彈性。
- **圖資料庫（CodeKG）**：不建議用靜態分析標籤取代圖導引控制器，而是將其作為圖資料庫的輕量快取層。當代理需要深度多跳查詢時，再呼叫圖資料庫；日常導航則仰賴內嵌標籤。
- **CI/CD 與 DevOps**：在 pre-commit 掛鉤或夜間建置中執行離線靜態分析，自動重新生成並注入標籤。可結合 Language Server Protocol（LSP），讓標籤同時以 CodeLens 形式呈現給人類開發者，達成人機共享的結構視圖。
- **可觀測性平台**：將軌跡行為、連結追隨率與執行間變異匯出至 OpenTelemetry 或內部監控系統，建立代理導航的即時儀表板，協助維運團隊觀察確定性錨點的實際效益。

### 給不同背景讀者的閱讀建議

- **初學者**：請將「確定性錨點」想像成在迷宮中為自動駕駛車輛畫上的穩定道路標線。閱讀時可先跳過 PyCG 與 AST 的技術細節，專注理解論文的三項核心觀察：錨定有效、規模敏感、以及穩定軌跡的價值。重點看圖 1 的標籤示意與 RQ1 的結論，建立「為何 AI 代理會在程式碼中迷路」的直覺。
- **AI 工程師**：請深入研讀 RQ2 的粒度與方向性實驗。在實作前，先評估你手邊儲存庫的拓樸密度與樞紐集中程度；導入時優先驗證執行間變異與連結追隨率，而非僅追求最終正確率。請預留 10–15% 的詞元緩衝，並在提示中明確引導代理利用標籤進行檢索短路。
- **研究人員**：本文的核心貢獻在於揭示「確定性錨定效應」的因果機制——靜態結構並非讓代理變得更聰明，而是透過穩定事實降低隨機探索的熵。建議延伸思考動態分析標籤的邊際價值、跨語言拓樸的一致性問題，以及在人機協作情境中，結構性註釋如何影響開發者對代理決策的信任與可解釋性感知。
- **產品經理**：請將本文視為一份「可預測性」的投資報酬率分析。重點閱讀 RQ3 的行為改變數據與成本估算：以約 10% 的詞元增量與離線建置成本，換取 Pass@1 提升與執行間變異減半。在合規導向或需要可審計軌跡的商業場景中，這種確定性本身就是可定價的產品特性。
