## ⚡ TL;DR

參數式工具檢索會破壞模型既有工具知識，且束搜尋解碼延遲過高，不利於生產部署。
提出 TRACE 兩階段訓練：LoRA 多格式記憶建立工具知識，再依業務規則輸出思考軌跡與工具詞元。
TRACE 在 8,300 多個工具上保留並提升工具知識，以單束貪婪解碼達到高召回率與生產級延遲。

## 摘要翻譯

參數式檢索（Parametric retrieval）透過為每個應用程式介面（API）分配唯一的虛擬詞元（virtual token），並訓練模型以受限束搜尋（constrained beam search）生成該詞元，使大型語言模型（LLM）得以隱式地檢索工具。ToolSense 指出此機制有兩個關鍵缺點：訓練過程會破壞參數式工具知識（parametric tool knowledge），且其束搜尋解碼（beam-search decoding）速度過慢，無法滿足即時部署需求。我們提出 TRACE（Tool Retrieval via Augmented Chain-of-thought and Enterprise rules，透過增強思維鏈與企業規則進行工具檢索），這是一個兩階段訓練課程（curriculum），用以解決此知識-檢索分離（knowledge-retrieval dissociation）問題。第一階段沿用 ToolSense 的多格式記憶（multi-format memorization）監督式微調（SFT），並利用低秩適應（LoRA）為工具知識奠定基礎。第二階段是我們的核心貢獻：模型被訓練成在產出 JSON 格式工具詞元（tool tokens）列表之前，先輸出一段思考軌跡（thinking trace）；此階段使用兩種資料來源——來自 ToolSense 的真實檢索基準配對（RRB pairs），以及針對領域專家（domain experts）整理之業務規則（business rules）所合成的查詢——兩者皆以推理軌跡（reasoning traces）進行增強。此訓練目標在保留第一階段選擇題（MCQ）與問答探測（QA probing）準確度的同時，也能在生產延遲（production latency）要求下實現單束貪婪解碼（single-beam greedy decoding）。

我們在橫跨兩條企業產品線、包含超過 8,300 項工具的整合企業目錄上進行評估。TRACE 的第二階段訓練不僅保留、更提升了工具理解能力：相較於第一階段，選擇題（MCQ）準確度提高 3.2 個百分點，問答探測（QA probing）提高 9 個百分點。在檢索方面，TRACE 在 Domain A 達到約 86% 的召回率（recall），在 Domain B 達到約 60%——相較於嵌入基線（embedding baseline）的約 27% 與約 52%——且 TRACE 在兩個領域皆使用單束貪婪解碼（single-beam greedy decoding），使其可直接部署於符合生產延遲（production latency）要求的環境。

### 核心貢獻（3～5點）
- 提出兩階段訓練課程 TRACE，解決參數式工具檢索中「知識-檢索分離」的問題，同時保留工具知識並實現可部署的檢索效能。
- 第一階段沿用多格式記憶監督式微調（SFT）搭配低秩適應（LoRA），為模型建立穩固的參數式工具知識基礎。
- 第二階段訓練模型在輸出 JSON 工具詞元前先產生思考軌跡，並結合真實檢索基準配對（RRB pairs）與針對業務規則合成的查詢，以推理軌跡進行增強。
- 在超過 8,300 項工具的企業目錄上驗證，第二階段訓練不僅未損失工具理解能力，反而提升選擇題與問答探測準確度。
- 以單束貪婪解碼達到高召回率（Domain A 約 86%、Domain B 約 60%），顯著優於嵌入基線，並可直接滿足生產延遲部署需求。

### 適合對象
本論文適合從事大型語言模型工具檢索、企業 AI 助理（AI copilots）、函式呼叫（function calling）與參數式檢索研究的學者與工程師；特別是關注如何在實際生產延遲限制下，同時保留模型工具知識、融入業務規則，並以思維鏈推理提升檢索準確度的讀者。

## 深度分析

#### 方法論解析

TRACE 的核心設計是將「工具知識保留（knowledge preservation）」與「高效工具檢索（tool retrieval）」從原本互相牴觸的目標，轉化為一個兩階段課程（two-stage curriculum）。整體可視為「先記憶、再推理檢索」：第一階段先把工具目錄（tool catalog）的知識穩固地寫入模型參數；第二階段則在不解碼空間受限的前提下，教模型先產生一段思考軌跡（thinking trace），再輸出 JSON 格式的工具詞元（tool tokens）列表。

**問題設定與資料結構**  
給定企業工具目錄 \(C=\{t_i=(name_i,desc_i)\}_{i=1}^{|N|}\)，共 \(|N|=8{,}283\) 個工具，分為 Domain A（HR，918 個工具）與 Domain B（Finance，7{,}365 個工具）。每個工具 \(t_i\) 被賦予一個唯一的虛擬詞元（virtual token）\(v_{t_i}\)，這延續了 ToolGen／ToolSense 的參數式檢索（parametric retrieval）設定。不同於一般公開基準，TRACE 還額外引入由領域專家（domain experts）整理的業務規則目錄 \(B=\{r_j=(T(r_j), text(r_j))\}_{j=1}^{|M|}\)，共 \(|M|=123\) 條。每條規則 \(r_j\) 包含一組易混淆工具集合 \(T(r_j)\subseteq C\) 與自然語言規則本文 \(text(r_j)\)，用於描述 API 棄用、版本差異、產品線路由限制等無法從工具描述直接推得的細節。

檢索任務被重新定義為條件生成：對於查詢 \(q\)，模型須產生 \((\hat z, \hat y)\)，其中 \(\hat z\) 是自由形式的推理軌跡（reasoning trace），\(\hat y=[v_x:x\in \hat A(q)]\) 則是對應正確工具集合的虛擬工具詞元（virtual tool tokens）有序列表。

**Stage 1：多格式記憶監督式微調（Multi-Format Memorization SFT）**  
第一階段直接沿用 ToolSense 的「多格式記憶（multi-format memorization）」配方，以低秩適應（Low-Rank Adaptation, LoRA）進行監督式微調（Supervised Fine-Tuning, SFT）。此階段不使用檢索目標，而是讓模型從多種互補視角學習每個工具的名稱、描述、功能與使用情境。選用 LoRA 的理論依據來自於相關研究：LoRA 相較於全參數微調能顯著減少災難性遺忘（catastrophic forgetting），因此可作為後續 Stage 2 的知識緩衝層。Stage 1 的產出是一個已具備紮實工具知識的種子模型，並以選擇題（Multiple-Choice Question, MCQ）與問答探測（QA probing）作為知識掌握度的診斷指標。

**Stage 2：業務規則導向的推理檢索訓練**  
第二階段是 TRACE 的主要貢獻。訓練目標是讓模型在輸出 JSON 工具詞元列表之前，先產生一段思考軌跡。該階段訓練資料 \(D_{\text{train}}\) 來自兩大來源：

1. **真實檢索基準配對（RRB pairs）**：取自 ToolSense 的 Realistic Retrieval Benchmark（RRB），並為每對查詢-目標（query-target pair）增強生成推理軌跡。
2. **規則目標合成查詢（rule-targeted queries）**：針對業務規則（business rules）中的易混淆工具集合，合成專門觸發該規則的查詢，並同樣附上推理軌跡。

資料生成管線（如圖 1 所示）包含多個品質檢驗（quality check）與驗證（validation）步驟：從種子資料（seed data）產生查詢-目標配對，再經由思維鏈（Chain-of-Thought, CoT）軌跡生成，接著進行程式化驗證（programmatic validation）與大型語言模型（Large Language Model, LLM）驗證。針對 RRB 資料，還進行分層生成（tier-wise generation）：Easy／Medium／Hard，並搭配困難負例（hard-negative）取樣，以強化模型對語意重疊工具的區辨能力。針對業務規則資料，則從規則目錄中抽樣，生成會觸發該規則的硬負例查詢-目標配對，再納入訓練。

**推理軌跡的雙重功能**  
思考軌跡不僅提升可解釋性，也扮演知識保留的關鍵角色：模型必須在參數記憶中「重述」工具語意與適用規則，才能正確輸出虛擬詞元。這種「先說明理由再給答案」的生成目標，避免了傳統參數式檢索直接把查詢壓縮成工具詞元所造成的知識-檢索分離（knowledge-retrieval dissociation）。

**推論階段：單束貪婪解碼（single-beam greedy decoding）**  
訓練完成後，TRACE 在推論時僅需單束解碼（single-beam decoding）即可產出思考軌跡與 JSON 工具詞元列表，無需外部檢索器（external retriever），也無需 ToolGen 的受限束搜尋（constrained beam search）。這使得延遲符合生產環境（production latency）要求，且吞吐量（throughput）相較於受限束搜尋提升約 200 倍。

#### 實驗數據解讀

TRACE 的實驗設計同時評估「知識保留」與「檢索效能」兩個維度，並在兩個真實企業產品線上進行端到端驗證。

**評測指標**

- **選擇題準確率（MCQ accuracy）**：探測模型對工具功能、參數、使用情境的細節掌握。
- **問答探測準確率（QA probing accuracy）**：以事實性是非問答（factual yes/no question answering）評估參數化工具知識。
- **檢索召回率（recall）**：衡量模型輸出的工具詞元列表與 ground-truth 工具集合的覆蓋程度。
- **延遲／吞吐量**：對比單束貪婪解碼與受限束搜尋的推論效率。

**知識保留結果**  
Stage 2 不僅沒有破壞 Stage 1 建立的知識，反而進一步提升：MCQ 準確率相較 Stage 1 提升 3.2 百分點（percentage points, pp），QA probing 提升 9 pp。這直接反駁了 ToolSense 觀察到的現象——傳統參數式檢索訓練會災難性地摧毀工具知識。TRACE 透過引入推理軌跡，把檢索目標重新框架為「知識驅動的生成」，因此能同時維持甚至強化 MCQ 與 QA 表現。

**檢索召回結果**  
在單束貪婪解碼（single-beam greedy decoding）下，TRACE 的檢索表現如下：

- Domain A（HR）：約 86% 召回率（recall）
- Domain B（Finance）：約 60% 召回率
- 綜合兩域：約 73% 召回率

相較之下，嵌入基線（embedding baseline）在 Domain A 僅約 27%、Domain B 約 52%。TRACE 在 Domain A 的領先幅度極大（+59 pp），顯示對於語意重疊但規則導向的 HR 工具，推理軌跡能有效區辨。Domain B 雖然絕對召回率較低，但仍優於嵌入基線，且考量其工具數量（7{,}365）遠大於 Domain A（918），語意重疊與規則複雜度更高，60% 已屬顯著進展。文中亦指出，業務規則注入（business rule grounding）可在語意重疊工具上將召回率提升最高達 23 pp。

**效率結果**  
TRACE 以單束解碼達成生產延遲，吞吐量約為受限束搜尋（constrained beam search）的 200 倍。這意味著過去因解碼速度而無法上線的參數式檢索，現在具備實際部署條件。

**綜合解讀**  
實驗數據支持 TRACE 的三項主張：（1）知識保留與檢索效能可以兼得；（2）業務規則導向推理（rule-grounded reasoning）能顯著改善語意重疊工具的檢索；（3）單束貪婪解碼足以在生產規模目錄上取得可部署的效能。然而 Domain B 的召回率顯示，當目錄規模放大、領域規則更繁雜時，仍有明顯的改善空間。

#### 與現有研究的比較

**相對於 ToolGen**  
ToolGen 開創了以虛擬詞元（virtual token）與受限束搜尋（constrained beam search）進行參數式檢索（parametric retrieval）的路線，在分布內（in-distribution, ID）的 ToolBench 資料上可達 90% 以上召回。然而其推論必須在 prefix trie 上進行受限束搜尋，延遲高，且未處理知識保留問題。TRACE 保留了「每個工具對應唯一虛擬詞元」的優點，但用思考軌跡取代受限束搜尋，使推論變為單束貪婪解碼（single-beam greedy decoding），並以兩階段課程避免知識被破壞。

**相對於 ToolSense**  
ToolSense 首次系統性地指出參數式檢索會造成知識-檢索分離（knowledge-retrieval dissociation），並提出 RRB、MCQ、QA probing 等評測。TRACE 直接沿用 ToolSense 的 Stage 1 多格式記憶配方與 RRB 資料，但進一步提出 Stage 2 的推理檢索訓練與業務規則注入，把 ToolSense 的診斷轉化為可解決的方案。

**相對於嵌入檢索（Embedding Retrieval）**  
以語意匹配（semantic matching）為基礎的嵌入檢索（如 Karpukhin et al., 2020）在企業場景中容易遇到瓶頸：工具描述高度相似、分布外（out-of-distribution, OOD）查詢與訓練分布差異大。本文顯示嵌入基線在 Domain A 僅 27% 召回，Domain B 約 52%，而 TRACE 分別達到 86% 與 60%。TRACE 不需要維護外部向量索引，也避免了檢索與生成階段之間的語意斷層。

**相對於函式呼叫（Function Calling）與 API 生成研究**  
現有函式呼叫（function calling）或 API 呼叫生成研究通常假設正確工具已在上下文（context）中給出，或僅從少數候選中挑選，未處理「從數千個未知工具中找出正確答案」的檢索問題。TRACE 明確定位為大規模目錄檢索（large-catalog retrieval），並以參數化方式完成路由。

**主要限制**

- **Domain B 召回率仍有缺口**：60% 雖優於基線，但對金融場景的高風險應用仍可能不足。工具數量多、語意重疊高、規則複雜是主因。
- **業務規則覆蓋有限**：僅 123 條規則，對 8{,}283 個工具而言覆蓋密度不均，未觸及規則的查詢可能仍依賴模型自身知識。
- **資料合成品質依賴 LLM**：推理軌跡與規則目標查詢皆由 LLM 生成並經驗證，若生成器本身對領域理解不足，可能引入錯誤訓練訊號。
- **未與混合式檢索比較**：文中未探討 TRACE 與「參數式檢索 + 輕量嵌入召回」混合架構的相對優劣。

#### 可重現性評估

從目前可得的上下文判斷，本研究的可重現性（reproducibility）面臨顯著挑戰：

- **資料與模型權重未公開**：實驗使用兩個企業產品線的 8{,}283 個專有工具（proprietary tools）與 123 條由領域專家整理的業務規則，這些資料無法公開取得。文中亦未提及釋出模型權重或訓練後檢查點。
- **程式碼未釋出**：上下文未提到開源程式碼（open-source code）、訓練腳本或資料生成管線的實作細節。雖然方法論圖示與流程描述相對清楚，但實際復現仍需大量實作細節（提示詞設計、負例採樣比例、LoRA 秩與學習率、JSON 解析與驗證邏輯等）。
- **匿名引用**：文中引用「Anonymous, 2026」指稱 ToolSense，暗示該論文可能仍處於匿名審查階段，相關基線方法與資料集尚未公開。
- **可近似復現的途徑**：研究者可使用公開的 ToolBench 資料集與自行定義的業務規則，模仿 TRACE 的兩階段課程與資料生成管線進行概念驗證。但這僅能驗證方法有效性，無法完全重現論文中的企業數據與絕對數字。

總體而言，TRACE 在方法層面具備足夠細節供社群參考與改作，但在資料與程式碼開放上仍屬封閉，獨立第三方難以完全重現其企業規模實驗。

#### 未來研究方向

**1. 超大規模與動態工具目錄**  
當工具數量從 8{,}K 擴展到 100{,}K 甚至百萬級時，虛擬詞元（virtual token）數量與詞彙表膨脹將成為挑戰。未來可研究階層式詞元（hierarchical tokens）、工具分群（tool clustering）、或動態詞彙擴展機制，以支援動態新增／刪除工具而不需全量重訓。

**2. 混合式檢索架構**  
TRACE 完全捨棄外部檢索器以換取低延遲，但未來可探索「輕量嵌入召回先縮小候選集合，再由 TRACE 進行規則導向推理」的混合架構，以兼顧速度、覆蓋率與可解釋性。

**3. 強化學習驅動的推理**  
目前 Stage 2 使用監督式微調（SFT）學習合成推理軌跡。可借鏡 DeepSeek-R1 等研究，以群體相對策略最佳化（GRPO）或類似強化學習（Reinforcement Learning, RL）方法，讓模型自主探索更簡潔、更忠實的推理路徑，減少對合成軌跡品質的依賴。

**4. 多輪對話與上下文檢索**  
企業 AI 副駕駛（AI copilots）常處於多輪互動。未來可將 TRACE 擴展至多輪檢索，讓模型在對話歷史中累積線索，並在必要時主動詢問澄清問題以降低誤檢索。

**5. 不確定性量化與拒答機制**  
Domain B 的召回率顯示模型仍會遺漏正確工具。引入不確定性估計（uncertainty estimation）與拒答（abstention）機制，可在信心不足時回退到人工路由或其他檢索系統，提升生產可靠性。

**6. 自動化業務規則挖掘**  
目前 123 條業務規則（business rules）由領域專家手工整理。未來可從 API 文件、程式碼變更紀錄、使用者回饋或服務日誌中自動挖掘規則，降低維護成本並擴大規則覆蓋率。

**7. 推理軌跡的忠實性與幻覺問題**  
思考軌跡雖提升可解釋性，但模型可能產生看似合理卻與實際規則不符的推理。需要發展專門的忠實性（faithfulness）評測與訓練目標，抑制推理軌跡中的幻覺（hallucination）。

**8. 跨領域遷移與領域適應**  
Domain A 與 Domain B 的表現差距顯示領域特性對檢索難度影響甚大。未來可研究如何將 Stage 1 學到的通用工具理解能力，透過領域適應（domain adaptation）或少樣本規則學習快速遷移到新產品線。

**9. API 組合與相依性檢索**  
現階段 TRACE 輸出單一 JSON 工具詞元列表。未來可擴展至多工具組合（tool composition）與相依 API 呼叫圖（dependency graph）的推理檢索，支援更複雜的企業工作流程。

**10. 更高效的解碼策略**  
雖然單束貪婪解碼（single-beam greedy decoding）已顯著降低延遲，仍可結合推測解碼（speculative decoding）、虛擬詞元提前終止（early exit）或推論時快取（KV-cache）優化，進一步提升吞吐量以服務高並發場景。

## 論文問答

**Q1：企業級大型語言模型在工具檢索上面臨的核心挑戰是什麼？為何傳統的嵌入檢索不足以解決？**  
A：企業內部常擁有數千至上萬個專有 API，這些工具的語意描述高度重疊，導致查詢與正確工具之間的對應極為困難。傳統嵌入檢索將問題視為語意匹配，但當工具僅在細微的業務規則、版本或棄用狀態上有所區別時，其召回率會明顯停滯。此外，目錄規模龐大使得在提示中列舉所有候選工具變得不可行，因此需要一種能夠在模型參數中隱式檢索、同時兼顧速度與知識保留的方法。

**Q2：現有的參數式檢索方法（如 ToolGen）與 ToolSense 的分析揭示了哪些關鍵缺陷？**  
A：ToolGen 透過為每個 API 分配唯一虛擬詞元（virtual token）並以受限束搜尋（constrained beam search）生成，雖然在分布內資料可達高召回，但 ToolSense 發現這種訓練會災難性地破壞模型對工具目錄的參數化知識。具體而言，經過檢索訓練後，模型在 MCQ 與 QA 探測任務上的表現顯著下降，顯示檢索能力與工具知識出現分離。此外，受限束搜尋在推理時需要維護龐大的前綴 Trie 與多束擴展，延遲過高，難以滿足生產環境的即時要求。

**Q3：為什麼在工具檢索過程中保留參數化工具知識如此重要？**  
A：參數化工具知識是模型理解每個 API 的功能、限制與使用情境的基礎，若因檢索訓練而遺失，將影響問答探測、選擇題判斷以及後續任何依賴工具理解的下游任務。這種災難性遺忘也會降低系統的可解釋性與可信度，因為模型可能只學會將查詢對應到詞元字串，卻無法真正掌握工具語意。因此，設計一個能同時維持知識完整性並具備高召回檢索能力的訓練課程，是企業 AI 副駕駛能否穩定上線的關鍵。

**Q4：TRACE 的兩階段課程包含哪些核心步驟？**  
A：第一階段採用 ToolSense 的多格式記憶監督式微調（multi-format memorization SFT），並以 LoRA（Low-Rank Adaptation）進行參數高效調整，讓模型先內化整個工具目錄的名稱、描述與功能。第二階段是 TRACE 的核心貢獻：模型被訓練在輸出 JSON 格式的虛擬工具詞元列表之前，先生成一段自由形式的思考軌跡（thinking trace），這段軌跡會參酌候選工具與企業業務規則。透過這種「先推理、再檢索」的生成方式，TRACE 將檢索目標從單純的查詢—詞元映射轉換為保留知識的推理任務。

**Q5：TRACE 相較於先前方法最關鍵的創新是什麼？**  
A：最關鍵的創新在於將企業業務規則（business rules）注入推理軌跡，並以單束貪婪解碼（single-beam greedy decoding）取代傳統的受限束搜尋。具體來說，領域專家整理的規則會被用來合成針對語意重疊工具的查詢與對應推理軌跡，使模型學會依據版本、棄用狀態或產品線限制等細微條件進行判斷。這不僅顯著提升對高度混淆工具的召回率，也讓推理過程本身成為可解釋的檢索依據，並使生產部署的延遲大幅降低。

**Q6：TRACE 在方法設計上做了哪些重要選擇，這些選擇各自解決什麼問題？**  
A：首先，第一階段使用 LoRA 而非全參數微調，因為既有研究顯示 LoRA 的災難性遺忘較輕，能在後續階段保留已習得的工具知識。其次，要求模型先輸出思考軌跡再輸出 JSON 工具詞元，可把檢索決策轉化為顯式推理過程，避免直接記憶查詢到詞元的狹隘映射。最後，第二階段同時使用 RRB（Realistic Retrieval Benchmark）真實檢索配對與針對業務規則合成的查詢，並搭配困難負例（hard-negative）與分層生成策略，確保模型既能處理真實用戶查詢，也能掌握專家規則所涵蓋的邊界案例。

**Q7：論文在實驗中使用了哪些評測資料與基線？**  
A：實驗使用一個包含 8,283 個專有企業工具的目錄，分為 Domain A（人力資源，918 個工具）與 Domain B（財務，7,365 個工具），並搭配 123 條由領域專家整理的業務規則。評測指標包括真實檢索基準（RRB）的召回率、MCQ 選擇題探測與 QA 是非問答探測，用以分別衡量檢索能力與參數化工具知識。對照基線包含傳統的嵌入檢索方法（embedding baseline），以及未加入推理軌跡的非推理基線模型。

**Q8：TRACE 的主要實驗結果有哪些？**  
A：在檢索召回率方面，TRACE 在 Domain A 達到約 86%、Domain B 約 60%，整體約 73%，遠高於嵌入基線在 Domain A 僅約 27%、Domain B 約 52% 的表現。在知識保留方面，第二階段不僅沒有破壞第一階段的成果，反而使 MCQ 準確率提升 3.2 個百分點、QA 探測提升 9 個百分點，相較於非推理基線更有約 28 個百分點的 MCQ 提升。此外，由於採用單束貪婪解碼，TRACE 的吞吐量比受限束搜尋高出約 200 倍，能直接滿足生產延遲需求。

**Q9：業務規則導向的資料擴增對結果產生了什麼影響？**  
A：業務規則導向的資料擴增專門針對語意高度重疊、僅靠描述難以區分的工具群組，將領域專家規則轉化為推理軌跡中的判斷依據。實驗顯示，這種機制能將此類困難工具的召回率提升最高達 23 個百分點，顯著縮小嵌入檢索在細微業務條件上的落差。這也驗證了單靠語意匹配無法捕捉的企業知識，可以透過顯式規則注入與推理訓練有效編碼到模型參數中。

**Q10：TRACE 在實際企業場景中適合哪些應用？**  
A：TRACE 特別適合需要將用戶自然語言查詢路由到正確後端 API 的企業 AI 副駕駛，例如人力資源領域的請假、薪資、績效查詢，或財務領域的報銷、預算、付款處理。由於它能根據業務規則區分版本、棄用狀態與產品線限制，因此對於經歷頻繁 API 演進的大型組織尤為重要。此外，TRACE 的單束貪婪解碼使其可直接部署於對延遲敏感的對話系統，無需額外檢索索引或外部召回模組。

**Q11：在產品化與部署層面，TRACE 有哪些優勢與需要考量的因素？**  
A：TRACE 的最大部署優勢在於推理時僅需單束貪婪解碼，無需維護外部嵌入索引或執行高成本的受限束搜尋，從而簡化系統架構並顯著降低延遲。使用 LoRA 也讓模型能以較少參數進行階段式更新，便於隨著工具目錄與業務規則演進而迭代。然而，產品團隊仍需持續維護由領域專家整理的業務規則，並監控規則覆蓋範圍，因為未納入規則的語意重疊工具仍可能成為檢索失敗的來源。

**Q12：這項研究對工具檢索與企業大型語言模型領域可能帶來什麼影響？**  
A：TRACE 證明了「推理式檢索」可以同時兼顧高召回與參數化知識保留，為過去被視為魚與熊掌不可兼得的問題提供了一條可行路徑。它也將企業業務規則從靜態文件轉化為可訓練的推理信號，開啟了領域專家知識與模型參數深度融合的新方向。未來，這套方法可能影響大型工具目錄的檢索範式，促使更多研究關注可解釋、低延遲且知識安全的參數式檢索系統。

**Q13：論文承認了哪些主要限制？**  
A：儘管 TRACE 在 Domain A 表現優異，Domain B 的召回率約 60%，顯示在規模更大或語意更複雜的財務工具目錄上仍有進步空間。此外，目前實驗僅涵蓋兩個企業產品線與 123 條業務規則，規則的覆蓋度與代表性可能不足以推廣到所有產業場景。資料生成過程也高度依賴大型語言模型合成與程式化驗證，若合成品質不足或驗證規則設計不周，仍可能引入錯誤的推理軌跡。

**Q14：在哪些情況下 TRACE 可能出現檢索失敗？**  
A：當查詢涉及未被業務規則覆蓋的語意重疊工具時，模型可能缺乏足夠的判斷依據而選錯 API。多工具組合或需要多步推理的複雜查詢，也可能因思考軌跡過長或中間步驟出錯而導致最終工具詞元不正確。此外，若企業規則頻繁變動卻未及時更新訓練資料，模型會依據過時的規則進行推理，進而產生版本或棄用狀態錯誤的檢索結果。

**Q15：未來研究可以朝哪些方向延伸 TRACE？**  
A：未來可將 TRACE 擴展到更大規模的工具目錄，並結合強化學習或過程獎勵模型來進一步提升推理軌跡的穩健性與正確性。另一方向是發展自動化或線上學習機制，使模型能隨著新業務規則與 API 變更持續更新，而無需完全重新執行兩階段課程。此外，探索多輪對話中的工具組合、與外部驗證器或執行回饋結合，以及將規則導向推理應用於其他企業知識密集型檢索任務，都是值得深入研究的課題。

## 實務應用指南

## 適用場景

1. **大型企業 AI 副駕駛（AI Copilot）的 API 路由**  
   當企業內部有數千支應用程式介面（API），員工以自然語言查詢時，系統必須從 8,000+ 工具中快速找出正確工具。TRACE 適合需要「單束貪婪解碼」即可上線、同時保留工具知識的場景，例如 HR 請假/薪資查詢或財務報銷/應付帳款助理。

2. **語意高度重疊的工具分群**  
   同一領域中多支工具描述相似（例如不同版本的「取得預測」API），僅靠嵌入基線（embedding baseline）難以區分。此時可引入領域專家整理的業務規則（business rules），透過規則導向推理（rule-grounded reasoning）提升召回率。

3. **低延遲生產環境的即時檢索**  
   傳統受限束搜尋（constrained beam search）雖然召回高，但延遲過高無法上線。TRACE 在 Stage 2 訓練模型先輸出思考軌跡（thinking trace），再以單束貪婪解碼產生 JSON 工具詞元（tool tokens），適合對生產延遲（production latency）敏感的對話系統。

4. **多租戶 SaaS 平台的工具目錄**  
   平台同時服務多個產品線或客戶，每個租戶擁有各自的工具目錄（catalog）與業務規則。TRACE 的兩階段課程可先以多格式記憶（multi-format memorization）建立通用工具知識，再以各租戶規則進行第二階段微調。

5. **舊系統遷移與 API 版本消歧**  
   企業常面臨 API 棄用、版本變更或「2024 年以後走 A API、之前走 B API」等路由限制。將這些規則寫入推理軌跡（reasoning trace）訓練資料，可讓模型在輸出工具詞元前先做正確判斷。

## 實作前置條件

### 資料條件
- **工具目錄**：至少需包含工具名稱、描述，並為每支工具分配唯一虛擬詞元（virtual token），建議採用階層式詞元（hierarchical tokens）如 «WeatherAPI»«GetForecast»。
- **業務規則目錄**：由領域專家（domain experts）整理，每條規則需包含（1）易混淆工具集合（confusible tool set）與（2）自然語言規則本文，說明如何消歧、版本限制或路由條件。
- **訓練查詢資料**：可沿用或仿照 ToolSense 的真實檢索基準（RRB）配對，並針對業務規則合成查詢—目標配對（query-target pair）。
- **知識探測資料**：準備選擇題（MCQ）與問答探測（QA probing）資料，作為監控模型是否遺失工具知識的診斷工具。

### 運算條件
- **訓練**：需支援 LoRA（低秩適應）微調的 GPU 叢集；Stage 1 與 Stage 2 皆為監督式微調（SFT），可使用單卡或多卡進行數個 epoch。
- **推理**：單束解碼（single-beam decoding）對硬體要求較低，但仍需評估生產延遲；建議準備推理服務框架（如 vLLM、TGI）與 JSON 輸出驗證機制。
- **資料生成**：合成推理軌跡與困難負例（hard-negative）時，需呼叫大型語言模型進行批次生成，並有程式化驗證（programmatic validation）流程。

### 技能條件
- 熟悉 LLM 監督式微調、LoRA 與參數高效微調。
- 具備資料擴增（data augmentation）與合成資料品質檢驗經驗。
- 了解企業 API 目錄結構與至少一個目標領域（如 HR、財務）的業務邏輯。
- 具備推理服務部署與延遲/召回監控能力。

## 實作步驟建議

### 步驟 1：盤點與詞元化工具目錄
將所有工具整理成統一格式，為每支工具產生唯一虛擬詞元。建議使用階層式命名，並建立工具名稱、描述、輸入輸出規格的多格式視圖，供 Stage 1 記憶使用。

### 步驟 2：與領域專家共建業務規則
針對語意重疊、版本差異、產品線限制等情境，整理業務規則（business rules）。每條規則應明確標註適用工具集合與判斷條件，作為後續規則導向推理的依據。

### 步驟 3：Stage 1 — 多格式記憶 SFT
使用 ToolSense 的多格式記憶配方，以 LoRA 對基礎模型進行監督式微調。目標是讓模型掌握工具事實知識，而非檢索。訓練後以 MCQ 與 QA probing 確認工具知識已內化。

### 步驟 4：合成 Stage 2 訓練資料
結合兩大資料來源：
- **RRB 配對**：來自 ToolSense 的真實檢索基準查詢—目標配對。
- **規則目標合成查詢**：針對業務規則生成查詢，並加入困難負例。

對每筆資料產生思考軌跡（thinking trace），軌跡內容應包含候選工具比較、適用規則引用與最終決策理由，再銜接 JSON 格式的工具詞元列表。

### 步驟 5：Stage 2 — 推理檢索 SFT
在 Stage 1 的 LoRA 基礎上繼續訓練，目標為：給定查詢，模型先輸出推理軌跡，再輸出 JSON 工具詞元。訓練時同時監控 MCQ/QA 探測分數，確保不發生災難性遺忘。

### 步驟 6：評估與迭代
- **知識保留**：比較 Stage 1 與 Stage 2 的 MCQ / QA probing 分數，應維持或提升。
- **檢索效能**：在分布外（out-of-distribution）查詢上評估召回率（recall），並與嵌入基線比較。
- **延遲驗證**：確認單束貪婪解碼可滿足生產延遲要求。

### 步驟 7：部署與監控
將模型部署至推理服務，輸出經 JSON 解析後轉發至 API 閘道或函式呼叫（function calling）執行器。上線後持續監控召回率、軌跡品質與規則命中率，並定期以新規則與新工具重新微調。

## 潛在風險與注意事項

| 風險 | 說明 | 因應措施 |
|---|---|---|
| **災難性遺忘** | Stage 2 的檢索目標可能破壞 Stage 1 習得的工具知識。 | 全程使用 LoRA；以 MCQ/QA probing 作為早期預警；必要時混合 Stage 1 資料進行回放訓練。 |
| **推理軌跡幻覺** | 模型可能生成看似合理但引用錯誤規則的軌跡。 | 加入程式化驗證，檢查軌跡中引用的工具與規則是否確實存在；對高風險決策加設後置信度門檻。 |
| **規則過時** | 業務規則、API 版本或棄用狀態會變動。 | 建立規則版本控制與定期重新整理機制；上線前以最新目錄驗證。 |
| **合成資料偏頻** | 過度依賴 LLM 合成查詢可能導致分布與真實用戶查詢不一致。 | 分層生成（tier-wise generation）涵蓋 Easy/Medium/Hard；並以真實查詢日誌校正。 |
| **領域不平衡** | Domain A 與 Domain B 的工具數量與規則密度差異大，可能導致某一領域召回偏低。 | 分領域評估召回率；對資料較少的領域加強規則目標合成與過採樣。 |
| **延遲與品質權衡** | 雖然單束解碼快，但過長的思考軌跡仍會增加延遲。 | 限制軌跡長度；對簡單查詢使用捷徑提示；在生產環境進行端到端延遲測試。 |

## 與其他技術的整合建議

- **與嵌入檢索並行作為後備**：TRACE 可取代或輔助嵌入基線。對於模型信心較低的查詢，可將嵌入檢索結果作為後備或重新排序（re-ranking）候選，提升整體穩健性。
- **對接 API 閘道與函式呼叫執行器**：模型輸出的 JSON 工具詞元可轉換為實際 API 呼叫，並經由 API 閘道進行權限驗證、速率限制與參數檢查。
- **結合向量資料庫管理業務規則**：雖然 TRACE 將規則內化於模型參數中，但仍建議在向量資料庫中維護規則全文，便於版本追蹤、檢索增強生成（RAG）後備與審計。
- **整合可觀測性平台**：記錄每筆查詢的思考軌跡、選中工具與實際執行結果，便於後續分析規則命中率、錯誤模式與模型漂移。
- **納入 CI/CD 的模型再訓練管線**：當工具目錄或業務規則更新時，自動觸發 Stage 1/Stage 2 資料重新生成、微調與 MCQ/QA 迴歸測試，確保知識保留與檢索效能不下降。

## 給不同背景讀者的閱讀建議

**初學者**：建議先掌握「工具檢索」與「參數式檢索」的基本概念，再聚焦本文的兩階段課程：第一階段像讓模型「背誦」工具知識，第二階段則教它「先想後答」。重點理解為何「先輸出思考軌跡再輸出 JSON」能同時提升速度與正確率，不必一開始就深入 LoRA 或束搜尋的數學細節。

**AI 工程師**：請重點關注 Stage 2 的資料合成流程與訓練目標設計，特別是如何將 RRB 配對與業務規則轉換為帶推理軌跡的訓練樣本。實作時請把 MCQ/QA probing 當作必備的迴歸測試，並在部署前驗證單束貪婪解碼的延遲與召回是否達標。

**研究人員**：本文的核心貢獻在於解決「知識—檢索分離」（knowledge-retrieval dissociation）問題。建議深入分析多格式記憶 SFT 與推理軌跡 SFT 之間的交互作用，並思考此方法能否推廣到其他需要保留世界知識的參數式檢索任務，例如知識庫問答或結構化資料查詢。

**產品經理**：請把 TRACE 視為一個「可上線的企業級工具路由方案」。關鍵賣點是它能以單束解碼達到生產延遲，同時透過領域專家規則處理語意重疊工具。評估導入時，請優先盤點內部 API 目錄規模、是否有現成業務規則，以及團隊能否持續維護這些規則。
