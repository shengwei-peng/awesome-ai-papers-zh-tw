## 摘要翻譯

OpenClaw 已成為複雜任務自動化（Complex Task Automation）的領先代理框架（Agent Framework），然而其跨平台（Cross-platform）圖形使用者介面（GUI, Graphical User Interface）互動支援不足，且缺乏完善的自演化機制（Self-Evolution Mechanism）。這些缺陷限制了其適應多樣化裝置生態系統（Device Ecosystems）的能力，也使其無法透過執行經驗（Execution Experience）持續學習（Continuous Learning）以提升效能。為解決這些問題，我們針對個人圖形使用者介面助理（Personal GUI Assistant）提出深知篤行（Know Deeply, Act Perfectly）典範，主張累積的使用者互動與任務執行經驗能直接提升執行準確率（Execution Accuracy）與效率，並統一認知理解（Cognitive Comprehension）與操作執行（Operational Execution）。基於此典範，我們提出 KnowAct-GUIClaw，一個新穎的知-路由-行-反思框架（Know-Route-Act-Reflect Framework），旨在彌補 OpenClaw 在圖形使用者介面操作上的不足，並突破其跨平台與遞迴式自我改善的限制。首先，主控代理（Host Agent）利用累積的互動經驗與任務相關知識進行長程任務分解（Long-horizon Task Decomposition）與分配（Know）。其次，藉由可插拔（Pluggable）的圖形介面子代理（GUI Subagent），搭配可歸因經驗的記憶系統（Experience-Attributable Memory System, Know）與自演化技能庫（Self-Evolving Skill Library, Act），實現無縫跨平台遷移（Seamless Cross-Platform Migration）與快速路徑整合（Fast-path Integration）。特別是，本框架持續儲存使用者輪廓（User Profiles）與回饋，以提升任務分解與工具呼叫（Tool Calls）的準確率。我們在 Android、iOS、HarmonyOS 與 Windows 上進行大量實驗，結果顯示 KnowAct-GUIClaw 在效率、執行準確率與跨平台適應性（Adaptability）方面均表現優異。特別值得一提的是，採用開源模型（Open-Source Models）Kimi-2.6 的 GUIClaw 在長程 MobileWorld 基準測試（MobileWorld Benchmark）中取得最佳表現（64.1%），超越所有代理框架與閉源代理模型（Closed-Source Agentical Models），例如 Seed-2.0-Pro 與 GPT-5.5。此外，本框架所支援的知識化記憶與執行技能（Skill）可遷移至不同的基礎模型（Base Models），使 Kimi-2.6 的效能提升 8.5%。

### 核心貢獻（3～5點）
- 提出「深知篤行（Know Deeply, Act Perfectly）」個人圖形使用者介面助理典範，統一認知理解與操作執行，並以累積互動經驗驅動執行準確率與效率提升。
- 設計 KnowAct-GUIClaw 知-路由-行-反思（Know-Route-Act-Reflect）框架，彌補 OpenClaw 在跨平台圖形使用者介面操作與自演化機制上的不足。
- 引入可插拔（Pluggable）圖形介面子代理（GUI Subagent），結合可歸因經驗的記憶系統（Experience-Attributable Memory System）與自演化技能庫（Self-Evolving Skill Library），支援無縫跨平台遷移與快速路徑整合。
- 驗證記憶與技能可遷移至不同基礎模型（Base Models），並在 MobileWorld 基準測試中以開源 Kimi-2.6 達到 64.1% 的最佳表現，超越 Seed-2.0-Pro 與 GPT-5.5 等閉源代理模型。

### 適合對象
適合對個人助理、圖形使用者介面自動化、跨平台代理框架、長程任務分解、自演化記憶與技能學習，以及大型語言模型在實際裝置生態系統中應用感興趣的研究人員與工程師閱讀；特別適合關注開源模型在複雜行動裝置任務上如何超越閉源代理模型的讀者。

## 深度分析

#### 方法論解析

KNOWACT-GUICLAW（深知篤行 GUI 助理框架）的核心方法論建立在「Know Deeply, Act Perfectly（深知篤行）」這一典範之上：代理必須在執行動作前充分檢索與任務相關的知識，並在執行後持續將經驗轉化為可重複使用的記憶（memory）與技能（skill）。整體架構採用主控中心式多代理系統（Host-Centric Multi-Agent Systems），由一個能力較強的主控代理（host agent）負責高階規劃、情境整合與工具調度，再搭配一個輕量級且可插拔（pluggable）的圖形使用者介面子代理（GUI subagent）負責螢幕感知與動作執行。

在形式層面，作者將 GUI 自動化建模為部分可觀察馬可夫決策過程（POMDP, Partially Observable Markov Decision Process）。這個選擇非常關鍵：螢幕截圖（screenshot）、無障礙樹（accessibility tree）、前景應用程式 ID、歷史動作軌跡（action trajectory）與模型內部推理日誌，每一種觀測模態都只揭露裝置真實狀態的片段，因此必須透過結構化記憶與軌跡證據來補足觀測不足。

方法論上，KNOWACT-GUICLAW 以 Know–Route–Act–Reflect（知–路由–行–反思）四階段堆疊運作：

1. **Know（情境收集與主控）**：主控代理從可歸因經驗的記憶系統（experience-attributable memory system）中檢索使用者輪廓（user profile）、應用程式候選清單、工具政策與 GUI 提示。此處的「可歸因」強調每一筆記憶都能追溯到具體的執行軌跡或使用者回饋，降低幻覺風險。
2. **Route（任務分解與資訊契約）**：主控代理將使用者指令分類為單一應用程式任務或跨應用程式工作流（cross-app workflow）。對於跨應用程式的長程任務，每個子任務都明確定義輸入與輸出資料契約（information contract），並透過臨時共享資料板（shared data board）傳遞結構化數值，同時由持久化路由記憶提供固定的候選應用程式集合。
3. **Act（混合 GUI–快速路徑執行）**：GUI 子代理在需要時才介入視覺互動，並優先使用快速路徑（fast path），例如網頁搜尋工具、Android Deep Link、系統意圖（system intent）或預先定義的動作序列。技能庫（skill library）中的可執行技能在呼叫前會針對即時介面頁面進行驗證，避免將過時捷徑誤用為持久技能。
4. **Reflect（軌跡蒸餾與技能演化）**：任務結束後，系統將成功與失敗的軌跡轉換為結構化證據，透過軌跡蒸餾（trajectory distillation）產生或更新技能，形成自演化技能庫（self-evolving skill library）。這使得後續執行能直接運用操作知識，而非重複探索性行為。

此外，作者提出兩層式主控–執行器協作（two-tier host–executor collaboration）：主控可指派有限 GUI 任務給執行器，並接收標準化輸出（完全完成、部分完成或阻塞），讓中斷的長時間工作流（interrupted long-duration workflows）能作為可恢復檢查點（checkpoint）繼續執行。同時，主控會依據自適應參與規則（adaptive host involvement rule），直接以工具處理符合條件的資訊收集子任務，減少不必要的 GUI 子代理呼叫，從而提升成功率並降低計算開銷。

#### 實驗數據解讀

作者在 Android、iOS、HarmonyOS 與 Windows 四個作業系統平台上進行廣泛實驗，涵蓋長程行動裝置任務基準 MobileWorld Benchmark、日常 Android 任務（AndroidDaily）、跨平台驗證（Cross-Platform Checks）以及消融與效率分析（Ablation and Efficiency Analysis）。

最引人注目的結果是：搭載開源大型語言模型（LLM, Large Language Model）Kimi-2.6 的 GUIClaw 在長程 MobileWorld 基準上達到 **64.1%** 的成功率，不僅超越所有代理框架（agent frameworks），也擊敗 Seed-2.0-Pro 與 GPT-5.5 等閉源代理模型（closed-source agent models）。這個數據具有多重意義：

- **開源模型競爭力**：在 GUI 自動化這類需要多模態感知與序列決策的任務上，開源模型（open-source models）Kimi-2.6 結合結構化記憶與技能後，能夠超越參數與訓練規模可能更大的閉源模型，顯示「知識組織」與「執行機制」對於基礎模型（base models）效能的放大作用。
- **記憶與技能的可遷移性**：作者指出，由框架支援的知識化記憶（knowledgeable memory）與執行技能可在不同基礎模型間轉移，並使 Kimi-2.6 提升 **8.5%**。這暗示記憶與技能並非單一模型專屬，而是可累積、可共用的資產。
- **效率改善**：透過快速路徑整合與技能重複使用，系統能減少重新啟動應用程式、重複導航與重複學習已知失敗模式的成本。雖然提供的上下文未給出詳細步驟數或延遲數據，但從設計邏輯可推論，主控代理直接處理資訊子任務與技能驗證機制應能顯著降低平均執行步數與 API 呼叫次數。
- **跨平台適應性（cross-platform adaptability）**：在 Android、iOS、HarmonyOS、Windows 上的驗證顯示，可插拔的 GUI 子代理與後端抽象層能夠實現無縫跨平台遷移（seamless cross-platform migration）。

然而，由於提供的全文上下文未包含完整表格、標準差、樣本數與統計顯著性檢定，我們無法判斷 64.1% 相較於次佳方法的領先幅度是否穩定，也無法評估不同難度任務上的表現分布。此外，MobileWorld 作為基準測試（benchmark）是否能充分代表真實世界中登入保護環境、動態彈窗與網頁視圖（webview）等挑戰，仍需更多案例研究佐證。

#### 與現有研究的比較

相較於現有研究，KNOWACT-GUICLAW 的定位介於通用自主代理框架（general autonomous agent frameworks）與專用 GUI 代理（GUI agents）之間，並試圖同時解決兩者的缺陷：

- **相對於 OpenClaw、Nanobot、Hermes 等本地優先助理平台（local-first assistant platforms）**：這些平台具備通道路由（channel routing）、工具擴充（tool extensions）、可配置技能（configurable skills）、會話持久化（session persistence）與結構化記憶儲存（structured memory storage），但缺乏對跨平台 GUI 操作的深度支援，也缺乏從執行經驗持續學習的自演化機制（self-evolution mechanism）。KNOWACT-GUICLAW 透過引入 GUI 子代理與 Reflect 階段填補了這兩項缺口。
- **相對於 ReAct（推理與行動整合範式）**：ReAct 將邏輯推理（logical reasoning）與環境動作執行（environmental action execution）統一，但多為一次性、無狀態（stateless）的互動。KNOWACT-GUIClaw 進一步將其擴展為有狀態（stateful）、長時間執行（long-running）的個人助理，並加入可歸因記憶與技能演化。
- **相對於 AppAgent、Mobile-Agent、CogAgent、OS-Atlas、ShowUI、UI-TARS、Aguvis 等專用 GUI 代理**：這些方法主要依賴螢幕截圖進行多模態動作生成，屬於單體式（monolithic）視覺代理。KNOWACT-GUICLAW 的差異在於採用主控–執行器兩層協作，將高階規劃與低階視覺執行解耦；同時引入快速路徑、技能驗證與跨平台後端，提升效率與適應性。
- **相對於記憶與技能重複利用（memory and skill reuse）文獻**：過去研究多聚焦於對話記憶或固定技能庫。KNOWACT-GUICLAW 強調「可歸因經驗」與「即時介面驗證」，使技能不僅能被儲存，還能隨環境變化持續演化。

儘管如此，本研究仍存在若干限制：

1. **主控代理的品質瓶頸**：長程任務分解（long-horizon task decomposition）與應用程式分配的準確性高度依賴主控代理的推理能力，對於語意模糊的使用者指令仍可能產生應用程式分配幻覺（app-allocation hallucination）。
2. **技能驗證成本**：每次呼叫技能前都需針對即時介面頁面驗證，雖提升穩健性，卻可能增加額外延遲與計算開銷。
3. **使用者輪廓隱私**：持續儲存使用者輪廓與回饋雖能改善任務分解與工具呼叫準確率，但也帶來隱私保護與資料治理挑戰。
4. **跨平台 UI 碎片化**：雖然框架宣稱無縫跨平台遷移，但不同平台在無障礙樹結構、權限對話框與導航模式上的差異，仍可能限制技能的可遷移性。
5. **閉源模型比較的公平性**：與 Seed-2.0-Pro、GPT-5.5 的比較可能受 API 版本、提示工程（prompt engineering）與呼叫成本限制，未必完全公平。

#### 可重現性評估

從提供的上下文來看，作者在第 5.7 節提及可重現性（reproducibility），但並未給出具體細節，例如原始碼倉庫連結、環境配置檔、硬體規格、隨機種子（random seed）或評估腳本。這使得目前無法對本研究的可重現性給出高度肯定的評價。

- 框架設計強調結構化記憶與技能庫，若作者釋出記憶模式（memory schema）與技能格式，將有助於社群重現與擴展。

為提升可重現性，建議作者釋出以下資源：

1. KNOWACT-GUICLAW 的完整原始碼，特別是作為 OpenClaw 擴充的實作細節。
2. GUI 子代理的後端介面與 Android、iOS、HarmonyOS、Windows 的裝置連接配置。
3. 記憶與技能庫的資料結構、產生流程與版本控制機制。
4. 實驗所使用的提示模板（prompt templates）、超參數與模型推論設定。
5. 詳細的消融實驗表格，包含標準差與統計檢定結果。
6. 預先蒸餾的技能範例與對應軌跡，以便驗證技能演化效果。

#### 未來研究方向

基於 KNOWACT-GUICLAW 的設計與現有局限，未來研究可朝以下方向延伸：

1. **更強大的多模態 GUI 感知模型**：將目前以螢幕截圖與無障礙樹為主的觀測，擴展至影片序列、聲音回饋與觸覺回饋，提升對動態介面與動畫過渡狀態的理解。
2. **持續學習（continuous learning）與線上適應**：發展無需人工標註的線上學習機制，讓代理能從每日互動中自動發現新任務模式，並在保護隱私的前提下更新使用者輪廓與技能庫。
3. **隱私保護記憶機制**：引入聯邦學習（federated learning）或差分隱私（differential privacy），讓個人化記憶可在不洩漏敏感資訊的情況下進行模型更新與知識共享。
4. **跨平台 UI 抽象標準化**：建立通用的 UI 元素語義描述格式，降低技能在不同作業系統與應用程式版本間遷移時的適配成本。
5. **結合強化學習與人類回饋**：將 GUI 自動化視為序列決策問題，利用強化學習（reinforcement learning）與人類回饋強化學習（RLHF, Reinforcement Learning from Human Feedback）來優化長期獎勵，而非僅依賴大型語言模型的上下文推理。
6. **技能庫的版本控制與衝突解決**：當技能數量成長時，需建立自動化的技能去重、衝突偵測與版本回溯機制，避免過時技能互相干擾。
7. **真實世界部署研究**：在實際使用者裝置上進行長期田野研究，評估系統穩定性、電池消耗、延遲感知與使用者滿意度。
8. **動態與封閉環境的處理**：加強對登入保護、網頁視圖、動態載入內容與權限對話框的處理能力，並建立安全中斷與恢復機制。
9. **能源與邊緣運算最佳化**：針對行動裝置與個人電腦的資源限制，設計輕量化模型與選擇性雲端卸載策略，降低延遲與能耗。
10. **更廣泛的基準測試**：擴展 MobileWorld 等基準，涵蓋更多跨應用程式、跨裝置協作情境，並納入可解釋性、安全性與公平性指標。

## 論文問答

**Q1：OpenClaw 作為現有框架，究竟存在哪些限制，促使作者提出 KnowAct-GUIClaw？**
A：OpenClaw 雖然是複雜任務自動化的領先代理框架，但它在跨平台圖形使用者介面互動與自演化機制方面仍顯不足。許多真實世界的個人助理任務——例如檢視行動應用程式、跨應用遷移資料或處理權限彈窗——都必須操作 GUI，而非僅呼叫結構化的應用程式介面。由於缺乏從執行經驗中持續學習的能力，OpenClaw 難以適應多樣的裝置生態系統，也無法隨著使用次數提升執行準確率與效率。

**Q2：為什麼直接把現成的 GUI 代理嵌入 OpenClaw 式框架會失敗？**
A：單純整合獨立的 GUI 代理會導致效率低落與執行脆弱，原因有四：首先，高階指令常橫跨多個不相關的應用程式，簡短自由文字摘要容易遺失跨應用操作所需的中繼資料值；其次，螢幕截圖、無障礙樹、前景應用程式 ID 等觀察各自只呈現裝置狀態的片段，無法完整反映真實環境；第三，成功或失敗的軌跡通常在任務結束後就被丟棄，導致類似任務重跑時必須重新探索；最後，多數 GUI 流程未善用網頁搜尋、Android 深層連結、系統意圖等非視覺快速路徑，而這些捷徑若未經即時介面驗證也無法安全地轉為長期技能。

**Q3：「深知篤行」（Know Deeply, Act Perfectly）這個典範為何重要？**
A：該典範主張累積的使用者互動與任務執行經驗能直接提升執行準確率與效率，並將認知理解與操作執行統一起來。對個人助理而言，這意味著代理不應每次遇到相同任務都從頭探索，而應在執行前檢索相關知識、執行中記錄結構化證據、執行後把有用軌跡蒸餾成可重複使用的技能。如此一來，助理能從「有狀態的長時間執行者」進化為會自我改進的系統，顯著降低重複勞動與錯誤率。

**Q4：KnowAct-GUIClaw 的核心方法「知—路由—行—反思」框架包含哪些階段？**
A：Know 階段由主控代理進行情境收集與主控，彙整對話、使用者輪廓、工作區記憶與外部工具；Route 階段負責長程任務分解，並透過資訊契約明確定義每個子任務的輸入與輸出；Act 階段則結合可插拔的圖形介面子代理執行視覺操作，並在可能時啟用快速路徑；Reflect 階段將執行軌跡蒸餾為經驗可歸因的記憶與自演化技能，供未來任務直接呼叫。

**Q5：主控代理與 GUI 執行器之間的雙層協作有何關鍵創新？**
A：KnowAct-GUIClaw 把 GUI 自動化視為主控代理與輕量 GUI 執行器之間的協作，而非單一龐大的 GUI 代理。主控代理掌握使用者面向的情境，決定要做什麼以及使用哪個 CLI 工具；GUI 執行器則專注於螢幕感知、動作正規化、裝置後端、技能驗證與軌跡記錄。兩者透過結構化、可恢復的 GUI 任務介面溝通，執行器回傳已完成、部分完成或受阻等標準化狀態，讓主控代理能接續執行或重新安排後續流程，從而提升成功率並降低運算開銷。

**Q6：可歸因經驗的記憶系統與自演化技能庫在設計上如何支援執行？**
A：記憶系統持續儲存使用者輪廓與回饋，並透過歸因機制讓主控代理在任務分解與工具呼叫時參考過往經驗，提升決策準確率。技能庫則保存經過驗證的操作序列與快速路徑，例如 Android 深層連結或可重複使用的多步動作，並在執行前對即時介面頁面進行驗證，避免誤用。這兩者不僅能跨平台遷移，也能在不同基礎模型之間轉移，實驗顯示可讓 Kimi-2.6 再提升 8.5%。

**Q7：論文在哪些基準測試與平台上進行評估？**
A：實驗涵蓋長程行動裝置任務基準 MobileWorld、日常 Android 任務基準 AndroidDaily，以及在 Android、iOS、HarmonyOS 與 Windows 上的跨平台驗證。評估指標除了任務成功率與執行準確率外，也包含效率分析，例如完成任務所需的步驟數、時間與運算成本。這樣的設計能同時檢驗 KnowAct-GUIClaw 在準確度、效率與跨平台適應性上的表現。

**Q8：MobileWorld 基準測試的主要結果是什麼？**
A：搭載開源 Kimi-2.6 模型的 GUIClaw 在 MobileWorld 上達到 64.1% 的最佳表現，超越了所有代理框架以及 Seed-2.0-Pro、GPT-5.5 等閉源代理模型。這項結果顯示，只要具備結構化知識與可重複使用技能，開源大型語言模型也能在長程 GUI 任務上擊敗閉源模型。它也證明了「深知篤行」典範在實際複雜任務自動化中的有效性。

**Q9：消融與效率分析揭示了哪些重要發現？**
A：實驗顯示，可轉移的知識記憶與執行技能能跨不同基礎模型發揮作用，對 Kimi-2.6 帶來 8.5% 的準確率提升。此外，主控代理適時介入資訊收集子任務、GUI 子代理僅在真正需要視覺操作時才被喚起，以及快速路徑的整合，都顯著減少了不必要的探索步驟與運算開銷。軌跡蒸餾與技能演化則讓後續類似任務能直接呼叫已驗證技能，避免重複從頭學習。

**Q10：KnowAct-GUIClaw 在實際應用場景中適合做什麼？**
A：它適合擔任需要頻繁操作圖形使用者介面的個人助理，例如檢查手機應用程式內容、在不同 App 之間搬移資料、處理權限彈窗對話框，或在需要登入的多步驟環境中執行工作流程。由於支援 Android、iOS、HarmonyOS 與 Windows，它也能統一管理使用者跨裝置的日常任務。對企業或個人使用者而言，這種能記憶偏好並持續自我改進的助理，可顯著減少重複性手動操作。

**Q11：若要把 KnowAct-GUIClaw 產品化，需要考量哪些部署與設計議題？**
A：可插拔的 GUI 子代理設計讓框架能無縫跨平台遷移，但仍需針對不同作業系統實作對應的裝置後端與動作正規化層。技能庫中的捷徑必須在執行前對即時介面頁面進行驗證，才能安全地重複使用，避免在介面更新後產生錯誤操作。此外，由於系統儲存使用者輪廓與執行軌跡，隱私保護、資料歸因與本地優先儲存都是產品落地時不可忽視的議題。

**Q12：這項研究對個人助理與 GUI 代理領域可能帶來什麼影響？**
A：KnowAct-GUIClaw 架起了自主個人助理與專用 GUI 代理之間的橋樑，讓 OpenClaw 式框架具備視覺互動與持續學習能力。它提出的自演化記憶與技能庫概念，可能成為未來長時間執行代理的標準設計元素。同時，開源模型在 MobileWorld 上擊敗閉源模型的結果，也挑戰了「閉源模型必然更強」的預設，推動學界與業界更重視知識工程與執行經驗的再利用。

**Q13：作者承認 KnowAct-GUIClaw 有哪些限制？**
A：GUI 觀察本質上是部分的，即使結合螢幕截圖、無障礙樹與歷史軌跡，仍無法完整掌握裝置狀態。技能的驗證與再利用高度依賴即時介面頁面，若應用程式版面大幅更新，既有技能可能失效。此外，當裝置環境資訊不足時，主控代理在應用程式分配上仍可能出現幻覺，需要更豐富的裝置感知與使用者回饋來抑制。

**Q14：在哪些情況下，KnowAct-GUIClaw 可能會失敗？**
A：當遇到記憶與技能庫中未曾見過的全新介面布局、動態產生的權限對話框，或需要人機驗證與 CAPTCHA 的步驟時，系統可能無法正確處理。若跨應用子任務之間的資訊契約定義不清，中繼資料在傳遞過程中遺失或錯誤，也會導致後續操作失敗。另外，環境狀態快速變化可能使先前驗證過的技能不再適用，進而引發錯誤的點擊或輸入。

**Q15：未來可以朝哪些方向進一步發展？**
A：未來可將框架擴展到更豐富的網頁與桌面生態系統，並強化視覺基礎模型以提升對複雜介面的感知能力。記憶系統可進一步研究歸因壓縮與長期遺忘機制，在保留重要經驗的同時降低儲存與檢索成本。此外，結合更緊密的使用者回饋迴路、線上持續學習，以及針對個人隱私資料的安全保證，將是讓這類個人 GUI 助理真正普及的關鍵下一步。

## 實務應用指南

### 適用場景

1. **跨應用個人助理流程**：例如使用者說「把今天會議摘要寄給主管」，系統需開啟行事曆 App 擷取會議標題與時間、切換到郵件 App 撰寫內容、再返回通訊軟體確認主管帳號。KnowAct-GUIClaw 的資訊契約與共享資料板可確保跨 App 資料不遺失，避免傳統單一 GUI 代理在切換應用時遺漏中繼值。

2. **長時間、可中斷的行動裝置任務**：例如「幫我在電商平台比價並下單」，過程涉及搜尋、比較、登入、付款權限對話框，且可能因驗證碼或人為確認而中斷。主控代理可將子任務交給 GUI 子代理，並以標準化輸出（完成／部分完成／阻塞）作為檢查點，稍後再接續執行。

3. **企業內部舊版系統自動化**：許多內部系統沒有現代化 API，只能透過圖形介面操作。KnowAct-GUIClaw 可將重複性登入、表單填寫、報表匯出流程蒸餾為自演化技能庫，並透過可歸因經驗的記憶系統記錄不同使用者帳號與權限情境。

4. **跨平台裝置管理與資料遷移**：例如協助使用者在 Android、iOS、HarmonyOS、Windows 之間同步聯絡人、相片或設定。可插拔的 GUI 子代理與裝置後端抽象層，讓同一套操作知識可在不同平台間遷移，降低為每個作業系統重新開發自動化腳本的成本。

5. **持續學習的個人化操作輔助**：例如記錄使用者偏好的導航路徑、常用濾鏡設定、或特定遊戲的日常任務流程。系統透過軌跡蒸餾將成功與失敗經驗轉為技能，並依使用者輪廓動態選擇快速路徑（如 Android Deep Link、系統 Intent）。

### 實作前置條件

**資料準備**
- 蒐集目標裝置平台的螢幕截圖、無障礙樹（accessibility tree）、前景 App ID 與歷史操作軌跡，作為 GUI 子代理的感知輸入。
- 建立使用者輪廓資料庫，包含常用 App、偏好設定、常見任務類型與回饋記錄。
- 準備領域知識庫，例如各平台常見權限對話框、Deep Link 格式、系統 Intent 規格，以及企業內部系統的操作手冊。

**運算資源**
- 至少具備多模態大型語言模型推理能力的 GPU 或 API 端點；論文以 Kimi-2.6 開源模型達到最佳表現，建議準備可執行 7B–70B 等級多模態模型的運算環境。
- 主控代理與 GUI 子代理可分開部署：主控代理負責長程規劃與記憶檢索，需要較強的語言推理能力；GUI 子代理需低延遲執行，可部署在靠近裝置的邊緣節點。
- 持續儲存軌跡與記憶的向量資料庫與結構化資料庫，例如用於技能檢索與相似任務比對。

**技能與團隊前提**
- 團隊需熟悉部分可觀察馬可夫決策過程（POMDP）概念、ReAct 範式與多代理系統設計。
- 需具備目標平台的自動化測試經驗，例如 Android adb、iOS XCTest、Windows UI Automation 或 HarmonyOS 對應工具。
- 建議具備資安與隱私合規知識，因為系統會持續記錄使用者互動與螢幕內容。

### 實作步驟建議

1. **建立主控代理與裝置後端**：先以 OpenClaw 風格的主控執行時期為基礎，整合對話、工作區記憶、外部工具與多代理對話能力；接著為 Android、iOS、HarmonyOS、Windows 建立可插拔的裝置後端，統一截圖、無障礙樹與動作執行介面。

2. **設計 Know 階段的情境收集**：讓主控代理在每次任務開始時，從可歸因經驗的記憶系統中檢索使用者輪廓、相關 App 候選、工具政策與 GUI 提示；同時建立適應性主控介入規則，讓資訊收集型子任務優先使用 CLI 工具或網路搜尋，而非一律交給 GUI 子代理。

3. **實作 Route 階段的任務分解與資訊契約**：將使用者請求分類為單一 App 任務或跨 App 工作流；為每個子任務明確定義輸入與輸出資料欄位，並以臨時共享資料板傳遞結構化數值，避免自由文字摘要遺漏關鍵資訊。

4. **開發 Act 階段的混合執行引擎**：GUI 子代理負責視覺感知、動作正規化與螢幕執行；同時整合快速路徑，包括網頁搜尋、Android Deep Link、系統 Intent 與預定義動作序列。每次執行前需驗證當前介面頁面是否符合技能啟動條件。

5. **建置 Reflect 階段的軌跡蒸餾與技能演化**：任務結束後，將成功與失敗軌跡轉換為結構化證據，並蒸餾成可重複使用的技能；技能庫需支援版本控制、有效性標記與跨平台遷移，並定期以新執行經驗進行迭代優化。

6. **部署持續回饋迴路**：讓使用者在任務完成後提供簡短回饋，系統據此更新使用者輪廓、調整任務分解策略與工具呼叫準確率，並將改進結果寫回長期記憶。

7. **進行跨平台驗證與基準測試**：在 MobileWorld 等長程行動裝置基準測試上評估，並於 Android Daily、iOS、HarmonyOS、Windows 真實環境中執行跨平台檢查，確認技能與記憶在不同基礎模型間可遷移。

### 潛在風險與注意事項

- **隱私與資料安全**：系統持續記錄螢幕畫面、操作軌跡與使用者輪廓，必須在裝置端或受信任環境中進行敏感資料去識別化，並提供使用者可檢視、刪除記憶的機制。
- **幻覺與錯誤的技能泛化**：大型語言模型可能將某個 App 的成功路徑錯誤套用到不同版本或不同平台。建議在技能啟動前加入當前頁面驗證，並保留人工審核高風險技能（如付款、刪除資料）的閘門。
- **過度依賴快速路徑**：Deep Link 與系統 Intent 可能因作業系統更新而失效，需定期回歸測試；當快速路徑失敗時，系統應優雅降級為 GUI 操作。
- **長程任務的錯誤累積**：跨 App 工作流中任一子任務失敗都可能導致後續步驟無法進行。應為每個子任務設定明確的完成條件與阻塞回報，並讓主控代理能夠重新規劃而非單純重試。
- **記憶膨脹與檢索品質下降**：隨著使用時間增長，記憶庫可能變得龐大。需定期進行記憶摘要、去重與遺忘策略，確保檢索到的知識與當前任務高度相關。

### 與其他技術的整合建議

- **與現有 RPA 或低程式碼平台整合**：可將 KnowAct-GUIClaw 作為前端智慧層，負責理解自然語言指令與跨 App 規劃；底層仍呼叫既有 RPA 腳本或低程式碼流程來執行穩定、重複性高的操作，降低全面替換成本。
- **與企業知識庫和 LLM 代理生態系整合**：透過標準化工具呼叫介面，讓主控代理能夠查詢企業內部文件、CRM、ERP 或票務系統；GUI 子代理則處理這些系統中無 API 支援的視覺化操作。
- **與裝置管理與 MDM 系統整合**：在企業部署情境中，可將 GUI 子代理的裝置後端與行動裝置管理（MDM）或端點管理系統對接，統一管理權限、憑證與合規政策。
- **與觀測與可解釋性工具整合**：將操作軌跡、記憶檢索結果與技能啟動紀錄匯出至可視化平台，協助開發者與使用者理解代理為何選擇特定動作，並加速除錯與審計。
- **與開源多模態模型生態整合**：論文顯示 Kimi-2.6 等開源模型已可達到領先表現，建議設計模型抽象層，讓團隊能夠根據成本、延遲與準確率需求，在開源與閉源模型之間切換，同時保持記憶與技能的可遷移性。

### 給不同背景讀者的閱讀建議

**初學者**：建議先從「深知篤行」這個核心概念入手，理解系統如何在「行動前先檢索知識、行動後再反思學習」；接著閱讀第 4 節的 Know–Route–Act–Reflect 架構概覽，把主控代理與 GUI 子代理想像成「經理與現場操作員」的合作關係，最後再看實驗章節的 MobileWorld 與 Android Daily 結果，建立對實際成效的直覺。

**AI 工程師**：請重點研讀第 3 節的 POMDP 形式化建模與第 4 節的四個機制，特別是資訊契約、共享資料板、可歸因經驗記憶與軌跡蒸餾的實作細節；實驗章節的消融與效率分析能幫助你判斷哪些設計對準確率與延遲影響最大，並據此規劃自己的落地優先順序。

**研究人員**：建議深入探討本文如何將 OpenClaw 風格的主控中心式多代理系統擴展到 GUI 領域，並關注自演化記憶與技能庫在跨平台遷移與基礎模型間轉移的理論意涵；第 5.7 節的可重現性說明與跨平台驗證設計，也可作為後續研究設計基準測試與比較實驗的參考。

**產品經理**：請聚焦於適用場景與商業價值，思考哪些使用者痛點最適合先用 KnowAct-GUIClaw 解決；同時評估隱私合規、使用者回饋機制與技能審核流程的產品設計，並參考實驗結果中的效率與準確率數據，向利害關係人說明導入此技術後在任務完成率與平均步驟數上的預期改善。
