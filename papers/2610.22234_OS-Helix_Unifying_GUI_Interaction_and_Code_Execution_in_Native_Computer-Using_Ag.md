## 摘要翻譯

真實桌面自動化既非純視覺亦非純程式化。代理必須理解使用者面向介面，同時高效操作檔案、腳本與系統狀態。然而，原生 GUI/程式碼協調無法透過提示層級工具組合獲得。在我們的初步實驗中，天真地加入程式碼工具會降低 GUI 代理的表現，這顯示出 GUI/程式碼路由必須透過高品質混合資料的訓練加以內化。我們提出 OS-Helix，一個端到端訓練的多模態電腦使用代理，在統一動作空間中整合 GUI 動作與程式碼執行。為建構所需監督，我們引入應用程式-產物組合（Application-Artifact Composition），將桌面應用程式與真實檔案產物配對以實例化可執行 Ubuntu 狀態，並提出解耦指令/評估器生成管線（Decoupled Instruction/Evaluator Generation Pipeline），產生環境基礎任務，其最終狀態在任何解決方案模態下皆可驗證。我們以篩選後的混合資料進行監督式微調（SFT），以此冷啟動策略，並透過即時桌面環境中的線上強化學習（Online RL）進一步改進。針對強化學習，我們提出步驟平衡 GSPO（Step-balanced GSPO），其以動作步驟而非原始助手標記彙總重要性權重，以防止長程式碼動作主導異質動作最佳化。在 OSWorld-Verified 上，OS-Helix-27B 與 OS-Helix-35B-A3B 相較其匹配 Qwen3.5 混合基線分別達成 35.0% 與 33.7% 的相對改進，而 OS-Helix-27B-RL 進一步改進 42.9%，達到 66.44% 成功率。消融實驗提供與學習式 GUI/程式碼協調、可擴展可驗證監督及動作步驟平衡最佳化貢獻一致的證據，同時展示在 WindowsAgentArena 上的跨平台遷移。我們的專案首頁位於 https://os-copilot.github.io/OS-Helix/。

### 核心貢獻（3～5點）
- 提出 OS-Helix，一個端到端訓練的多模態電腦使用代理，於統一動作空間中整合 GUI 動作與程式碼執行，突破提示層級工具組合的限制。
- 引入應用程式-產物組合（Application-Artifact Composition）與解耦指令/評估器生成管線，建構可擴展可驗證監督，使最終狀態在任何解決方案模態下皆可驗證。
- 提出步驟平衡 GSPO（Step-balanced GSPO），透過以動作步驟而非原始助手標記彙總重要性權重，防止長程式碼動作主導異質動作最佳化。
- 在 OSWorld-Verified 上達成顯著相對改進（最高 42.9%），並展示於 WindowsAgentArena 上的跨平台遷移能力，驗證方法泛化性。

### 適合對象
從事電腦使用代理（CUA）、多模態大型語言模型、桌面自動化、強化學習及 GUI/程式碼混合代理研究的學者與工程師；亦適合關注 AI 代理於真實數位環境中部署應用、數位自動化產品研發，以及人機互動前沿技術探索的業界研發團隊與研究生。

## 深度分析

#### 方法論解析

OS-Helix 的核心方法論圍繞「原生混合 (native hybrid)」設計理念展開，試圖從根本上解決 GUI 與程式碼兩種動作模態在單一策略中協調的問題。其方法論可分為三個相互支撐的層次：資料建構層、策略初始化層、以及策略最佳化層。

**1. 統一動作空間設計 (Unified Action Space)**

論文最關鍵的設計選擇是將 GUI 動作（如 click(x, y)、type）與程式碼動作（透過 shell 執行的命令）整合至同一個動作空間中，並由單一策略直接輸出。這與傳統的「框架中心系統 (framework-centric systems)」截然不同——後者依賴外部協調器在 GUI 代理與程式碼代理之間切換。OS-Helix 的統一動作空間設計使得「模態路由 (modality routing)」成為策略本身的可學習行為，而非由提示工程 (prompt engineering) 或外部邏輯決定。

**2. 應用程式-產物組合 (Application-Artifact Composition)**

此方法解決了桌面環境資料合成中的「真實性」問題。具體做法是將版本化的桌面應用程式（如特定版本的 LibreOffice、GIMP、VS Code 等）與真實的檔案產物（file artifacts，如試算表、文件、圖片）配對，藉此實例化可重現且多樣化的 Ubuntu 桌面狀態。這種設計的關鍵洞見在於：桌面任務的複雜性不僅來自應用程式本身，更來自應用程式與具體檔案內容的互動。透過組合而非單獨採樣，OS-Helix 能產生更貼近真實使用者情境的訓練環境。

**3. 解耦指令/評估器生成管線 (Decoupled Instruction/Evaluator Generation Pipeline)**

此管線包含兩個獨立代理：
- **探索代理 (Exploration Agent)**：透過對初始化環境的簡短探索，提出基於環境狀態的指令 (instructions)。這確保任務指令與實際可操作的桌面狀態對齊。
- **評估器代理 (Evaluator Agent)**：獨立建構任務特定的、以規則為主的評估器。

此解耦設計的核心優勢在於「可驗證性 (verifiability)」：無論解決方案採用 GUI 動作還是程式碼動作，最終狀態都能被驗證。這解決了混合模態任務中最棘手的獎勵設計問題——傳統基於軌跡比對的方法會偏好特定模態，而基於最終狀態的驗證則對模態無偏。

**4. 監督式微調冷啟動 (SFT Cold-Start)**

策略初始化採用過濾後的混合軌跡資料進行監督式微調，目的是讓模型內化基本的動作語意與初步的模態路由能力。論文強調「過濾 (filtered)」的重要性——從 83K 未過濾樣本中篩選至約 31K 高品質樣本，顯示資料品質對混合協調能力學習的關鍵作用。

**5. 步驟平衡 GSPO (Step-balanced GSPO)**

這是論文在強化學習階段的核心技術貢獻。標準 GSPO (Group Sequence Policy Optimization) 以原始助手標記 (raw assistant tokens) 數量作為重要性比率 (importance ratio) 的聚合單位。然而，在混合動作空間中，GUI 動作通常很短（如 click(x, y)），而程式碼動作可能包含數十甚至數百個標記。這種「標記計數不對稱性 (token-count asymmetry)」會導致最佳化訊號被程式碼步驟主導，造成程式碼動作比例上升但整體效能下降的現象。

步驟平衡 GSPO 的解決方案是：以「動作步驟 (action step)」而非「標記數量」作為重要性權重的聚合單位。這使得每個動作（無論是短 GUI 動作還是長程式碼動作）在策略梯度中獲得平等的權重，從而實現異質動作最佳化 (heterogeneous-action optimization) 的平衡。

#### 實驗數據解讀

**1. OSWorld-Verified 主要結果**

在 OSWorld-Verified 基準測試上，OS-Helix 展現了顯著的效能提升：
- **OS-Helix-27B**：相較於匹配的 Qwen3.5 混合基線，達到 35.0% 的相對改進
- **OS-Helix-35B-A3B**：相對改進 33.7%
- **OS-Helix-27B-RL**：進一步提升 42.9%，達到 66.44% 的成功率

這些數據的解讀重點在於：
- 「相對改進」是相對於「匹配基線 (matched baselines)」而非絕對值，這意味著對照組本身已具備一定混合能力，因此 35% 的相對提升代表的是在已有混合基線上的實質突破
- 66.44% 的成功率在 OSWorld-Verified 上是極具競爭力的結果，顯示原生混合訓練的策略已接近實用化水準
- RL 階段相對於 SFT 階段的額外提升（從約 46% 至 66.44%）證明了線上強化學習在混合動作空間中的價值

**2. 初步實驗的關鍵發現**

論文報告了一個極具說服力的對照實驗：Qwen3-VL-32B-Instruct 在僅使用 GUI 動作時於 OSWorld-Verified 達到約 34% 成功率，但當程式碼執行被「天真地 (naively)」暴露後，成功率下降至約 32%。這個看似反直覺的結果——增加能力卻降低效能——是支撐整篇論文論點的核心證據。它證明了「提示層級組合 (prompt-level composition)」無法產生真正的協調行為，反而會擾亂已有的 GUI 策略。

**3. 消融實驗 (Ablation Studies)**

論文聲稱消融實驗提供了三方面貢獻的證據：
- 學習式 GUI/程式碼協調 (learned GUI/code coordination)
- 可擴展可驗證監督 (scalable verifiable supervision)
- 動作步驟平衡最佳化 (action step balanced optimization)

雖然具體數字未在提供的文本中，但這三個維度的消融設計邏輯上是完整的：分別移除協調訓練、移除可驗證獎勵、使用標準 GSPO 而非步驟平衡版本。

**4. 跨平台遷移 (Cross-Platform Transfer)**

在 WindowsAgentArena 上的結果證明了策略的跨平台泛化能力。這是一個重要的驗證：雖然訓練資料基於 Ubuntu 環境，但學到的混合協調能力並非 Ubuntu 特定的，而是可遷移至 Windows 環境的通用能力。這暗示了 OS-Helix 學到的是「何時使用 GUI、何時使用程式碼」的高階策略，而非特定作業系統的介面細節。

#### 與現有研究的比較

**1. 相較於 GUI 中心 CUA (GUI-Centric CUAs)**

傳統 GUI 中心代理（如基於 Qwen3-VL、UI-TARS 等）受限於視覺定位 (visual grounding) 的脆弱性，特別是在小型或模糊介面元素上。OS-Helix 透過允許程式碼動作作為「逃生通道」，繞過了視覺定位的瓶頸。然而，OS-Helix 並未放棄 GUI 能力——對於依賴視覺佈局 (visual layout)、應用程式特定 UI 狀態 (application-specific UI state) 或僅透過介面暴露的軟體行為 (software behavior) 的任務，GUI 動作仍是必要的。

**2. 相較於程式碼代理 (Code Agents)**

純程式碼代理（如命令列代理）在處理需要視覺理解或應用程式特定 UI 操作的任務時存在「視覺未定位 (visually ungrounded)」的問題。OS-Helix 透過保留 GUI 動作解決了這一限制，使其能處理桌面任務的「長尾 (long tail)」場景。

**3. 相較於框架中心系統 (Framework-Centric Systems)**

以 Aria-UI、OpenCUA 等為代表的框架中心系統透過外部協調器組合 GUI、程式碼、記憶體與恢復機制。OS-Helix 的差異在於：
- **效能耦合性**：框架中心系統的效能與昂貴的推理成本和手工編排緊密耦合；OS-Helix 的協調能力內化於模型本身
- **可隔離性**：框架中心系統難以隔離「模型本身的混合協調能力」與「框架編排的貢獻」；OS-Helix 的端到端設計使協調能力成為可測量、可消融的組件
- **部署成本**：OS-Helix 部署時無需維護複雜的外部協調邏輯

**4. 相較於工具呼叫方法 (Tool-Call Approaches)**

以 OS-Atlas、UI-Voyager 等為代表的工具呼叫方法透過預定義的、應用程式特定的介面暴露程式化操作。OS-Helix 的優勢在於：
- **覆蓋範圍**：工具呼叫方法的覆蓋受限於可用整合與工具架構；OS-Helix 的程式碼動作透過 shell 執行，覆蓋範圍更廣
- **遷移性**：新增應用程式支援時，工具呼叫方法需要新增工具定義；OS-Helix 可透過通用 shell 指令處理新應用程式

**5. 相較於模型融合方法 (Model-Fusion Approaches)**

以 UFO、Agent-S 等為代表的模型融合方法透過預定義設計組合互補能力。OS-Helix 的關鍵差異在於「透過混合訓練學習的協調」vs「預定義融合」。後者依賴設計者的先驗知識，而前者允許策略從資料中發現最優的協調模式。

**6. 與 Qwen-UI-Agent 的關係**

論文承認 Qwen-UI-Agent 也探索了混合 GUI 與類程式碼動作的訓練，但其資料建構、可執行環境等細節描述有限。OS-Helix 在此基礎上提供了更系統的方法論，特別是在可驗證監督與 RL 最佳化方面。

**7. 現有方法的侷限性**

儘管 OS-Helix 取得了顯著進展，仍存在以下侷限：
- **資料規模**：31K 過濾後 SFT 樣本相對於通用預訓練資料規模仍較小，可能限制泛化能力
- **環境多樣性**：訓練主要基於 Ubuntu，雖然展示了 Windows 遷移，但 macOS 等其他平台的表現未驗證
- **任務複雜度**：OSWorld 任務雖然多樣，但相對於真實企業工作流程仍較為簡化

#### 可重現性評估

OS-Helix 在可重現性方面展現了值得肯定的開放態度：

**1. 將釋出的研究產物 (Research Artifacts)**

根據論文摘要與介紹章節，作者承諾將釋出：
- **OS-Helix 模型家族**：包括 OS-Helix-27B、OS-Helix-35B-A3B、OS-Helix-27B-RL 等變體
- **桌面資料合成環境**：支援應用程式-產物組合的可重現環境
- **RL 環境**：用於線上強化學習的可執行桌面環境
- **任務與軌跡收集管線**：包含探索代理與評估器代理的完整實作
- **約 9K 生成的指令 (instructions)**：涵蓋多樣化的桌面任務
- **83K 未過濾 SFT 樣本**：完整的訓練資料集
- **約 31K 成功過濾 SFT 樣本**：高品質的子集

**2. 專案主頁**

論文提供了專案主頁 https://os-copilot.github.io/OS-Helix/，這通常包含模型權重下載連結、程式碼儲存庫、以及可能的示範影片。

**3. 可重現性優勢**

- **環境可重現性**：透過應用程式-產物組合，桌面狀態可被精確重現，這對於 RL 環境尤為重要
- **評估可驗證性**：解耦的評估器管線提供了獨立的獎勵訊號來源
- **基準測試公開**：OSWorld-Verified 與 WindowsAgentArena 均為公開基準

**4. 潛在的可重現性挑戰**

- **計算資源需求**：27B 與 35B-A3B 模型的訓練與推理需要大量 GPU 資源，可能限制中小研究團隊的重現能力
- **環境設定複雜性**：Ubuntu 桌面環境的精確配置（特定版本的應用程式、依賴項等）可能難以完全重現
- **評估器實作細節**：雖然論文描述了評估器代理的設計，但具體的規則實作細節對於重現至關重要

#### 未來研究方向

**1. 動作空間的進一步擴展**

OS-Helix 目前統一了 GUI 與程式碼兩種模態。未來可探索的方向包括：
- **多模態動作整合**：將語音輸入、觸控手勢、相機視覺等納入統一動作空間
- **高階動作抽象**：在統一動作空間之上引入「技能 (skills)」或「巨集 (macros)」，使策略能學習可重用的動作序列
- **跨裝置動作**：將動作空間擴展至行動裝置、IoT 裝置等異質環境

**2. 更精細的模態路由機制**

雖然步驟平衡 GSPO 解決了最佳化層面的不平衡問題，但模態路由本身仍是一個開放問題：
- **可解釋路由**：使策略能夠解釋「為何選擇 GUI 而非程式碼」或反之，增強使用者信任
- **成本感知路由**：考慮不同模態的執行成本（時間、資源、副作用）進行路由決策
- **安全性感知路由**：在涉及敏感操作時，自動選擇更安全的模態

**3. 資料效率與樣本複雜度**

31K 高品質 SFT 樣本雖然有效，但資料收集成本高昂：
- **自監督資料增強**：利用環境的確定性自動產生更多訓練樣本
- **遷移學習**：從相關領域（如網頁自動化、遊戲 AI）遷移知識
- **課程學習 (Curriculum Learning)**：設計由簡至複的任務序列，提升學習效率

**4. 安全與對齊考量**

隨著代理能力增強，安全問題日益重要：
- **動作驗證**：在執行程式碼動作前進行靜態分析或沙箱驗證
- **使用者意圖確認**：對於不可逆操作（如刪除檔案、發送郵件）要求確認
- **對抗性魯棒性**：防禦提示注入 (prompt injection) 攻擊，特別是在處理網頁內容時

**5. 多代理協作 (Multi-Agent Collaboration)**

OS-Helix 專注於單一策略的內部協調，未來可探索：
- **專家混合 (Mixture of Experts)**：不同代理專精於不同模態或任務類型，透過路由器協調
- **對話式協作**：多個 OS-Helix 代理透過自然語言對話協作完成複雜任務
- **人機協作**：將人類使用者納入迴圈，代理在關鍵決策點請求指導

**6. 評估方法的演進**

OSWorld-Verified 與 WindowsAgentArena 雖是重要基準，但評估方法本身需要演進：
- **長期任務評估**：現有基準的任務通常可在數十步內完成，真實工作流程可能涉及數百步
- **多步驟依賴評估**：評估代理在任務中途失敗後的恢復能力
- **使用者滿意度評估**：超越二元成功/失敗，評估解決方案的品質與優雅性

**7. 理論基礎的建立**

OS-Helix 的方法論目前主要為經驗驅動，未來可建立更堅實的理論基礎：
- **混合動作空間的表示學習理論**：理解統一動作空間中不同模態的表示結構
- **模態路由的資訊理論分析**：量化不同模態在特定任務中的資訊貢獻
- **RL 收敛性分析**：在異質動作空間中建立策略最佳化的收敛性保證

**8. 應用領域的垂直整合**

將 OS-Helix 的能力應用於特定垂直領域：
- **軟體工程自動化**：IDE 操作、程式碼重構、測試生成
- **資料分析與視覺化**：試算表操作、圖表生成、報告撰寫
- **創意工作流程**：文件排版、圖片編輯、影片製作
- **企業流程自動化**：ERP、CRM 等企業系統的操作

這些方向不僅能推動技術進步，也能創造實際的商業價值，使 OS-Helix 類技術從學術研究走向產業應用。

## 論文問答

**Q1：OS-Helix 試圖解決的核心問題是什麼？**
A：OS-Helix 試圖解決真實桌面自動化中 GUI 互動與程式碼執行無法有效協調的問題。現有的電腦使用代理（CUA）通常僅依賴 GUI 操作（如點擊、輸入），這在處理小型或模糊介面元素時容易失敗，且對結構化狀態的操作效率低落；反之，純程式碼代理雖然能精確操控檔案與系統狀態，卻無法處理依賴視覺佈局或應用程式特定 UI 狀態的任務。因此，OS-Helix 旨在建立一個能夠原生協調兩種模態的單一策略，而非僅僅在提示層級組合工具。

**Q2：為什麼現有的混合方法無法有效整合 GUI 與程式碼？**
A：現有方法大致可分為三類：框架中心系統透過外部協調器整合 GUI、程式碼、記憶體與恢復機制，但其效能高度依賴昂貴的推理與手工編排的編排邏輯；工具呼叫式方法透過預定義的應用程式特定介面暴露程式化操作，限制了覆蓋範圍與遷移能力；而模型融合方法則透過預定義設計結合互補能力，而非讓單一策略內部學會協調。本文的初步實驗更顯示，僅僅將程式碼工具附加到 GUI 模型（如 Qwen3-VL-32B-Instruct）反而會使其在 OSWorld-Verified 上的成功率從約 34% 下降至約 32%，證明提示層級的組合無法教會模型「何時」與「為何」使用哪種模態。

**Q3：為什麼這個問題在學術與實務上都很重要？**
A：在學術上，此問題挑戰了「單一策略能否內部學會異質動作協調」的基礎研究問題，超越了傳統 GUI 中心或程式碼中心代理的範式。在實務上，真實桌面工作流程本質上就是混合的——例如「更新銷售資料並將圖表格式化為符合參考樣式」這類任務既需要視覺理解參考圖，也需要透過程式碼精確處理資料檔案。若無法原生協調這兩種模態，自動化系統將在效率、可靠性與覆蓋範圍上遭遇根本性瓶頸，限制了電腦使用代理在企業與個人場景中的實際部署。

**Q4：OS-Helix 的核心方法是什麼？**
A：OS-Helix 的核心方法是將原生 GUI/程式碼混合電腦使用重新定義為端到端的策略學習問題，並透過統一的動作空間讓單一多模態策略同時學會 GUI 動作與程式碼動作。具體而言，模型透過監督式微調（SFT）在高品質混合資料上進行冷啟動，以內化基本的動作語意與模態路由；接著在即時桌面環境中進行線上強化學習（RL），使策略進一步最佳化。這種端到端訓練方式使得 GUI/程式碼的協調能力成為模型自身的內在屬性，而非依賴外部編排。

**Q5：什麼是「應用程式-產物組合」（application-artifact composition）？**
A：應用程式-產物組合是 OS-Helix 提出的基礎設施層級方法，用於建構多樣化且可重現的桌面狀態。它將版本化的桌面應用程式與真實的檔案產物（如文件、試算表、圖表等）配對，以實例化可執行的 Ubuntu 狀態。在此基礎上，一個探索代理（Exploration Agent）透過對初始化環境的簡短探索來提出基於環境的指令，而一個獨立的評估器代理（Evaluator Agent）則建構任務特定的、主要是基於規則的評估器。這種解耦的指令/評估器生成管線支援可擴展的合成、過濾與收集高品質 GUI/程式碼軌跡，為模型訓練提供了必要的資料基礎。

**Q6：什麼是「步驟平衡 GSPO」（Step-balanced GSPO），為什麼需要它？**
A：步驟平衡 GSPO 是 OS-Helix 針對異質動作最佳化所提出的強化學習演算法改良。傳統的群組序列策略最佳化（GSPO）以原始助手標記（raw assistant tokens）數量來聚合重要性權重，但由於 GUI 動作通常很短（如點擊座標），而程式碼動作可能非常長，這會導致最佳化訊號被程式碼步驟主導。步驟平衡 GSPO 改為以動作步驟（action step）而非助手標記數量來建構樣本層級的重要性比率，從而實現兩種模態的更平衡最佳化。本文觀察到，在早期 RL 實驗中，程式碼動作比例持續上升伴隨著效能下降，這正是該方法所要解決的核心問題。

**Q7：OS-Helix 使用了哪些基準測試進行評估？**
A：OS-Helix 主要在 OSWorld-Verified 上進行評估，這是一個用於衡量桌面自動化代理效能的標準基準。此外，本文也展示了在 WindowsAgentArena 上的跨平台遷移結果，以驗證方法的泛化能力。為了進行消融實驗與對比分析，文中還引用了 Qwen3-VL-32B-Instruct 等基線模型在相同基準上的表現，並與匹配的 Qwen3.5 混合基線進行相對改進的比較。

**Q8：OS-Helix 的關鍵實驗結果為何？**
A：在 OSWorld-Verified 上，OS-Helix-27B 相較於其匹配的 Qwen3.5 混合基線達到了 35.0% 的相對改進，而 OS-Helix-35B-A3B 則達到了 33.7% 的相對改進。更值得注意的是，經過 RL 訓練的 OS-Helix-27B-RL 進一步提升了 42.9%，最終達到 66.44% 的成功率。這些結果顯示了從 SFT 冷啟動到線上 RL 的完整訓練流程都能帶來穩定的效能提升，且跨平台遷移實驗也證明了方法在 Windows 環境上的有效性。

**Q9：消融實驗揭示了哪些關鍵發現？**
A：消融實驗提供了與三項貢獻一致的證據：學習式 GUI/程式碼協調、可擴展可驗證監督、以及動作步驟平衡最佳化各自都對最終效能有正向貢獻。具體而言，移除任何一個元件（如改用提示層級組合、降低監督品質、或回到原始的標記級 GSPO）都會導致效能下降。這些消融結果支持了本文的核心論點：唯有透過端到端訓練內化混合協調能力，並配合適當的資料與演算法設計，才能實現可靠的原生混合代理。

**Q10：OS-Helix 適用於哪些實際應用場景？**
A：OS-Helix 適用於任何需要視覺理解與程式化操作相結合的桌面工作流程，例如：辦公室自動化中的試算表資料處理與圖表格式化、軟體測試中的 UI 互動與後端狀態驗證、系統管理中的應用程式配置與檔案處理、以及需要參考視覺範本進行精確操作的設計任務。對於企業而言，這類代理可以大幅降低重複性桌面工作的時間成本；對於個人使用者，則能處理跨應用程式的複雜任務，如「根據截圖中的參考樣式重新格式化文件並匯出為特定格式」。

**Q11：在將 OS-Helix 部署為產品時需要考慮哪些因素？**
A：產品化部署需要考量以下因素：首先，安全性至關重要，因為程式碼執行能力可能被濫用於執行惡意指令，需要建立沙箱環境與權限控制；其次，延遲與成本，雖然 OS-Helix 透過單一策略避免了外部編排的推理成本，但 RL 訓練與即時環境互動仍需顯著運算資源；第三，使用者體驗，需要設計清晰的任務描述介面與錯誤恢復機制；最後，可擴展性，雖然本文展示了 Ubuntu 與 Windows 的跨平台遷移，但實際部署到 macOS 或其他作業系統仍需進一步驗證。

**Q12：OS-Helix 對電腦使用代理領域的影響是什麼？**
A：OS-Helix 對該領域的影響體現在三個層面：在研究範式上，它將混合電腦使用從「系統編排問題」轉變為「策略學習問題」，為後續研究開啟了新的方向；在資料建構上，應用程式-產物組合與解耦指令/評估器管線提供了可擴展的高品質混合資料生成範式；在開源生態上，本文釋出的模型家族、訓練環境、約 9K 生成的指令、83K 未過濾的 SFT 樣本與約 31K 成功過濾的 SFT 樣本，將大幅降低後續研究的門檻。這些貢獻共同推動了原生混合代理從概念驗證走向實際應用。

**Q13：OS-Helix 存在哪些已承認的限制？**
A：本文承認的限制包括：首先，雖然展示了跨平台遷移，但主要訓練與評估仍在 Ubuntu 環境上進行，macOS 等其他平台的支援仍需驗證；其次，RL 訓練需要即時桌面環境，這對運算資源與基礎設施要求較高，可能限制研究的可重現性；第三，雖然步驟平衡 GSPO 解決了標記不對稱問題，但 GUI 與程式碼動作之間仍存在更細粒度的協調挑戰，例如在單一任務中動態切換模態的時機選擇；最後，釋出的資料規模（約 31K 過濾 SFT 樣本）相對於真實世界任務的多樣性仍屬有限。

**Q14：OS-Helix 在哪些情況下可能會失敗？**
A：OS-Helix 可能在以下情況下失敗：當任務需要極度精細的視覺定位（如設計軟體中的像素級操作）時，GUI 動作仍可能不夠精確；當任務涉及未在訓練資料中出現的新應用程式或非標準介面時，模型的泛化能力可能受限；當程式碼動作與 GUI 動作的切換時機判斷錯誤時，可能導致效率低下或任務失敗；此外，在涉及敏感系統操作（如權限變更、系統設定修改）時，模型可能缺乏足夠的安全判斷能力，需要額外的防護機制。

**Q15：OS-Helix 的未來研究方向有哪些？**
A：未來研究方向可從以下幾個層面展開：在演算法層面，可探索更精細的動作層級獎勵設計，以及多模態動作空間的理論分析；在資料層面，可擴展應用程式-產物組合至更多作業系統與應用程式類型，並研究自動化的任務難度分級；在能力層面，可將 OS-Helix 擴展至多代理協作、長時程任務規劃、以及與人類使用者的互動式修正；在應用層面，則可探索其在企業自動化、軟體測試、無障礙輔助等垂直領域的專門化版本。這些方向共同指向一個更通用、更可靠的原生混合電腦使用代理的願景。

### 適用場景

1. **企業內部桌面流程自動化**：將重複性高、跨應用程式的桌面工作（如報表彙整、ERP 資料更新、CRM 資料搬運）交由 OS-Helix 處理。當任務涉及視覺化操作（如開啟特定 UI 視窗、按下按鈕）與程式化操作（如批次修改 CSV、執行 shell 腳本）時，統一策略可依情境自動切換 GUI 動作與程式碼動作，減少人工介入。

2. **IT 技術支援與系統管理**：技術支援人員常需在終端機、檔案總管、設定介面之間切換。OS-Helix 可用於自動化診斷流程、安裝設定、修補組態檔，並透過 GUI 完成需要視覺確認的步驟（如勾選授權條款、按下「下一步」），同時用程式碼動作快速處理大量檔案或系統狀態。

3. **資料處理與視覺化工作流**：研究人員或資料分析師常需從多個來源擷取資料、清理轉換、並產出符合特定格式的圖表。OS-Helix 可在 LibreOffice Calc、GIMP、瀏覽器等應用程式中，混合使用 GUI 操作（拖曳欄位、調整圖表樣式）與 Python/shell 腳本（pandas 處理、檔案批次轉檔），完成端到端工作流。

4. **跨平台桌面代理部署**：基於 WindowsAgentArena 的遷移驗證，OS-Helix 可部署於 Windows 環境執行企業既有桌面自動化任務，例如 Office 文件批次處理、瀏覽器表單填寫、舊版桌面應用程式整合，協助組織在不更換基礎架構的前提下導入 AI 代理。

5. **GUI/程式碼混合任務的研究與教學**：學術界與教育訓練機構可利用釋出的資料合成管線、9K 指令集、31K 過濾 SFT 樣本與即時桌面 RL 環境，進行電腦使用代理的後續研究、基準測試建構，或作為學生實作多模態代理的教材。

### 實作前置條件

**資料準備**
- 需具備可重現的 Ubuntu 桌面環境（建議使用容器化或虛擬化方案，如 Docker + VNC/X11 forwarding），以執行 application-artifact composition 產生可驗證的桌面狀態。
- 需準備多樣化的桌面應用程式版本（LibreOffice、GIMP、Thunderbird、VS Code、檔案管理器等）與對應的真實檔案產物（文件、試算表、圖片、程式碼專案）。
- 評估器建構需具備撰寫規則式檢查腳本的能力（檔案存在性、內容比對、UI 狀態檢查），以便驗證任務最終狀態。

**運算資源**
- SFT 階段：對 27B 規模模型進行監督式微調，建議配備至少 8 張 A100/H100 等級 GPU（80GB 記憶體），並使用 ZeRO-3 或 FSDP 進行分散式訓練。
- RL 階段：需在即時桌面環境中並行 rollout 多條軌跡，建議配置 32 張以上 GPU 加上對應數量的 Ubuntu 桌面容器實例（每個環境約 2–4GB RAM）。
- 推論部署：可使用 vLLM 或 SGLang 等高效推論框架，單一 27B 模型推論建議至少 1 張 A100/H100。

**技能需求**
- 熟悉多模態模型訓練流程（VLM 微調、視覺編碼器整合）。
- 具備強化學習實作經驗，特別是策略最佳化演算法（GSPO、GRPO、PPO 等）以及重要性取樣、長序列處理等概念。
- 熟悉 Linux 系統管理、容器化技術、桌面環境自動化（xdotool、PyAutoGUI 等）。
- 具備資料管線工程能力，能建構探索代理（Exploration Agent）與評估代理（Evaluator Agent）的協作流程。

### 實作步驟建議

**步驟一：建立可重現的桌面環境基礎設施**
依據論文的 application-artifact composition 概念，設計容器化的 Ubuntu 桌面環境模板，每個模板預先安裝特定版本的桌面應用程式組合。準備對應的真實檔案產物庫（文件、圖片、資料集），並建立版本控制機制以確保狀態可重現。建議使用 Ansible 或類似工具自動化環境建構。

**步驟二：建構解耦的指令/評估器生成管線**
實作兩個獨立代理：
- **探索代理（Exploration Agent）**：在初始化後的桌面環境中進行短暫探索，根據觀察到的狀態產出環境基礎的任務指令。
- **評估代理（Evaluator Agent）**：根據任務指令產生任務特定的驗證器（以規則式為主），用於檢查最終狀態是否符合預期。
兩個代理的解耦設計可避免評估器洩漏答案，並支援跨模態（GUI 或程式碼）解法的驗證。

**步驟三：收集並過濾混合軌跡資料**
讓具備 GUI/程式碼能力的基礎模型（如 Qwen3-VL-32B-Instruct）在環境中執行任務，收集完整軌跡。依據任務成功率、軌跡合理性、動作多樣性等指標進行過濾，最終保留約 31K 高品質 SFT 樣本（從 83K 未過濾樣本中篩選）。建議保留 GUI 動作與程式碼動作的合理比例，避免單一模態過度主導。

**步驟四：執行 SFT 冷啟動**
使用過濾後的混合資料對基礎 VLM 進行監督式微調，目標是讓模型內化基本的動作語意與 GUI/程式碼路由能力。訓練時應保留視覺編碼器的能力，並適當調整學習率與訓練步數，避免過擬合到特定動作模式。

**步驟五：實作 Step-balanced GSPO 進行線上 RL**
在即時桌面環境中部署策略，收集 rollout 軌跡並計算獎勵。實作 Step-balanced GSPO 時，關鍵在於將重要性比率（importance ratio）以「動作步驟」而非「原始助手標記數」為單位進行聚合，避免長程式碼動作主導異質動作的最佳化訊號。建議監控 GUI 動作與程式碼動作的使用比例，防止程式碼動作過度膨脹。

**步驟六：評估與跨平台遷移**
在 OSWorld-Verified 上評估模型效能，目標對齊論文的 66.44% 成功率。接著在 WindowsAgentArena 上測試跨平台遷移能力，必要時進行平台特定的微調。建議建立自動化的回歸測試套件，持續監控模型在 GUI 動作、程式碼動作與混合任務上的表現。

**步驟七：部署與監控**
將訓練完成的模型透過高效推論框架部署為服務，設計任務排程與錯誤恢復機制。生產環境中應監控動作分佈、任務成功率、平均完成步數等指標，並建立人工介入的 fallback 流程，處理模型無法解決的邊界案例。

### 潛在風險與注意事項

**風險一：程式碼動作過度膨脹導致效能退化**
論文中明確指出，在 RL 早期實驗中觀察到程式碼動作比例持續上升伴隨效能下降。這是因為程式碼動作的標記數遠多於 GUI 動作，導致重要性權重被程式碼主導。**緩解措施**：採用 Step-balanced GSPO，以動作步驟而非標記數聚合重要性比率；監控動作分佈並設定獎勵塑形（reward shaping）以維持模態平衡。

**風險二：提示層級組合無法產生協調行為**
單純將程式碼工具附加到 GUI 模型上，不僅無法提升效能，反而會降低表現（Qwen3-VL-32B-Instruct 從 ~34% 降至 ~32%）。**緩解措施**：必須透過混合資料的端到端訓練內化協調能力，不可依賴提示工程或外部編排層。

**風險三：評估器設計不當導致獎勵漏洞**
若評估器過於寬鬆或過於嚴格，可能讓模型學到錯誤行為或無法學習。**緩解措施**：以規則式檢查為主、LLM 評估為輔；建立評估器的健全性測試，確保其能正確區分成功與失敗的軌跡。

**風險四：桌面環境的可重現性與版本漂移**
不同版本的應用程式可能產生不同的 UI 狀態或行為，導致訓練與推論不一致。**緩解措施**：嚴格版本控制應用程式與系統套件；使用容器化環境確保訓練與部署一致；定期更新資料集以涵蓋新版本。

**風險五：安全性與權限風險**
程式碼動作可執行任意 shell 命令，存在資料外洩、惡意操作或系統損壞的風險。**緩解措施**：在沙箱環境中執行；限制可存取的目錄與網路；實施動作白名單與人工審核機制；記錄所有執行的程式碼以供稽核。

**風險六：跨平台遷移的效能落差**
雖然論文中展示了 WindowsAgentArena 的遷移能力，但跨平台效能通常會低於原生平台。**緩解措施**：準備平台特定的微調資料；建立平台特定的評估基準；考慮在目標平台上進行少量 SFT 以縮小落差。

### 與其他技術的整合建議

**與 RPA（機器人流程自動化）平台整合**
OS-Helix 可作為傳統 RPA 工具的「智慧層」，處理傳統規則式 RPA 難以應對的開放式任務。建議將 OS-Helix 部署為獨立的決策服務，透過 API 接收任務描述並回傳動作序列，再由 RPA 平台（如 UiPath、Automation Anywhere）執行底層操作，或反過來由 RPA 平台呼叫 OS-Helix 處理例外情況。

**與 LLM 代理框架整合**
可將 OS-Helix 整合到 LangChain、AutoGen、CrewAI 等代理框架中，作為專門處理桌面任務的工具。建議設計清晰的介面契約（輸入：任務描述 + 螢幕截圖；輸出：動作序列），並提供同步與非同步兩種呼叫模式。

**與企業系統整合**
透過 OS-Helix 的程式碼動作能力，可直接與企業系統的 CLI 工具、API、資料庫進行互動。建議建立企業專屬的動作模板庫，封裝常用的內部系統操作，並透過身份驗證與權限管理確保安全性。

**與監控與可觀測性系統整合**
將 OS-Helix 的動作軌跡、決策日誌、成功率等指標整合到 Prometheus、Grafana、Datadog 等監控平台。建議設計結構化的日誌格式，包含任務 ID、動作類型（GUI/程式碼）、執行時間、錯誤訊息等欄位，以便進行後續分析與除錯。

**與 CI/CD 與測試自動化整合**
將 OS-Helix 整合到 CI/CD 流程中，用於自動化桌面應用程式的回歸測試。建議將測試任務以程式碼形式描述，並透過 OS-Helix 在標準化桌面環境中執行，產生測試報告。

### 給不同背景讀者的閱讀建議

**給初學者**：建議先閱讀摘要與圖 1，理解 GUI-only、Code-only 與 Hybrid 三種範式的差異。接著閱讀第 1 節的「Existing Paradigms」與「Hybrid Paradigm」段落，掌握為什麼需要混合代理。實作上可從釋出的資料集與小型模型變體開始，使用預訓練權重進行推論測試，觀察模型在不同任務上的動作選擇，逐步建立直覺。

**給 AI 工程師**：重點閱讀第 1 節的訓練方法論（application-artifact composition、解耦指令/評估器管線、Step-balanced GSPO）以及相關工作章節中對框架中心、工具呼叫、模型融合三類方法的比較。實作上建議先重現 SFT 流程，理解混合動作空間的設計；接著實作 Step-balanced GSPO，特別注意重要性比率的聚合方式如何影響異質動作的最佳化。論文中釋出的 31K 過濾 SFT 樣本與即時桌面 RL 環境是寶貴的起點。

**給研究者**：重點關注三個面向：(1) 為何提示層級組合無法產生協調行為的初步實驗分析（表 14），這對理解代理學習的本質有重要啟示；(2) application-artifact composition 與解耦評估器設計如何支援可擴展的可驗證監督，這對資料合成研究有廣泛參考價值；(3) Step-balanced GSPO 處理異質動作最佳化的理論與實證分析，這對 RL 方法論有貢獻。建議進一步探索 GUI/程式碼路由的可解釋性、跨平台遷移的理論基礎，以及與其他模態（如語音、觸控）的統一。

**給產品經理**：重點理解 OS-Helix 的能力邊界與商業價值。論文的 66.44% OSWorld-Verified 成功率代表了當前原生混合代理的先進水準，但仍非完美，產品設計上應保留人工介入的 fallback。OS-Helix 的核心價值在於「單一策略自適應選擇 GUI 或程式碼動作」，這對企業自動化場景的覆蓋率與維護成本有顯著影響。建議評估組織內部桌面流程的自動化潛力，優先選擇 GUI 與程式碼動作都能發揮互補優勢的場景進行試點，並關注安全性、權限管理與可觀測性等生產化議題。
