## ⚡ TL;DR

現有基準難以衡量 AI 在真實客戶專案條件下建構並交付可用代理的能力。
提出 ττ-bench，讓開發者代理在沙盒中根據真實業務紀錄、客戶需求與成本限制端到端建構客服代理。
最強配置僅通過 23.9% 評估模擬，遠低於專家上限 82.2%，凸顯規格還原與設計探索等關鍵缺口。

## 摘要翻譯

LLM 代理（LLM agents）正迅速成為生產級軟體（production software），被部署來處理客戶服務、裁決爭議，以及操作內部系統。值得注意的是，建構它們的工作正逐漸交給編碼代理（coding agents），但現有的基準測試幾乎無法說明 AI 系統（AI system）是否能在真實客戶專案的條件下交付一個代理。我們提出 ττ-bench（ττ-bench），一個以代理建構（agent construction）為任務的基準測試。開發者代理（developer agent）會獲得企業實際保存的紀錄、一位掌握需求的客戶、一個營運操作必須經過的生產 API（production API）、一個需要繼承的程式碼庫（codebase），以及服務成本與可用模型清單（model menu）的限制：這正是真實專案所提供的起點。它必須從這些條件中交付一個完整的客服代理（customer-service agent），並透過部署該代理、使其與保留的（held-out）模擬使用者（simulated users）互動來評分。在四個領域共 53 項任務中，最強的組態——搭配 Claude Code 使用的 Claude Opus 5——僅在 23.9% 的評估模擬（evaluation simulations）中成功。與此同時，由專家撰寫的參考上限（reference ceiling）得分為 82.2%。這些失敗與人類代理開發者所見的問題如出一轍：模型以淺層查詢（shallow queries）取代對紀錄的深入理解（deep comprehension）、幾乎不與客戶溝通，且鮮少在代理架構與服務成本上進行實驗，便直接交付第一個可運作的設計。我們期望 ττ-bench 能將協作式代理建構的工作轉化為編碼代理可衡量的目標。

### 核心貢獻（3～5點）
- 將「代理建構（agent construction）」本身設計為可衡量的基準測試任務，填補現有基準測試無法評估真實客戶專案交付能力的缺口。
- 提供貼近真實專案的起點：企業實際紀錄、掌握需求的客戶、生產 API（production API）、既有程式碼庫（codebase），以及服務成本與可用模型清單（model menu）的限制。
- 透過部署所建構的客服代理（customer-service agent）並與保留的模擬使用者（held-out simulated users）互動來進行端對端評分。
- 揭示當前最強組態的失敗模式：淺層查詢（shallow queries）取代深入理解（deep comprehension）、缺乏與客戶溝通，以及鮮少實驗代理架構與服務成本。

### 適合對象
從事 LLM 代理（LLM agents）開發、代理系統評估、AI 輔助軟體工程，以及對真實客戶專案交付感興趣的研究人員與工程師。

## 深度分析

#### 方法論解析

ττ-bench（發音為 hyper-tau-bench）的核心設計是將 **agent construction（代理建構）** 本身變成可量化的任務，而非僅評估一個已經建構好的 **LLM agents（大型語言模型代理）**。整體流程可分為三個階段：**specification recovery（規格還原）**、**agent construction（代理建構）**、**deployment evaluation（部署評估）**。

##### 1. 從原子事實到真實業務文物（Artifacts）

作者首先將每個領域的 **standard operating procedures（標準作業程序）** 拆解為一組原子事實（atomic facts），再將這些事實轉換成企業實際會保留的雜亂資料形式，包括：

- 手冊與政策文件（如 `policy.md`、`op.md`）
- **support transcripts（客服對話紀錄）**
- 試算表形式的 **fee schedules（費用表）**
- 電子郵件往來（email threads）
- 會議錄音轉寫（meeting transcript，如 `.vtt`）
- 圖片與簡報（如 `process_map.png`、`slide_deck.pdf`）

這些資料彼此可能衝突、過時或不完整，開發者代理必須像真人工程師一樣，從中還原出正確的業務規則。

##### 2. 互動式客戶（Simulated Client）

規格不僅存在於文件中，有一部分只存在於人類利害關係人腦中。ττ-bench 提供一個 **simulated client（模擬客戶）**，開發者代理可以透過 `talk_to_client` 等工具進行詢問。這模擬了真實專案中需求必須透過對話挖掘、且會隨時間變動的特性。

##### 3. 真實開發環境與限制

開發者代理在一個 **sandbox（沙盒）** 環境中工作，面對的條件與真實客戶專案一致：

- 必須繼承既有的 **codebase（程式碼庫）**，並保留其既有行為
- 必須整合由客戶提供的 **production API（生產 API）**，該 API 可能含有 subtle defects（細微缺陷）
- 必須在 **model menu（可用模型清單）** 限制下運作
- 必須滿足 **serving cost（服務成本）** 與 **latency（延遲）** 的硬限制（例如每任務成本 ≤ $0.05、p95 latency ≤ 10 秒）

這些限制迫使開發者代理必須做工程權衡，例如選擇單一 **policy-following model（遵循策略的模型）** 還是 **orchestrated sub-agents（協調式子代理）**，以及如何將 **action space（動作空間）** 切割成適當的 **tools（工具）**。

##### 4. 端到端評估：部署後對抗模擬使用者

建構完成的 **customer-service agent（客服代理）** 不會被靜態測試，而是實際部署並與 **held-out（保留的）** **simulated users（模擬使用者）** 互動。每個模擬使用者帶有 **hidden goal（隱藏目標）**，例如「卡片遺失，詢問補發費用」或「帳戶被盜用，要求免除費用」。最終系統會比對對話結束後的狀態（如案件狀態、費用是否免除）與 **expected final state（預期最終狀態）**，匹配則給予 reward r = 1。最終分數為所有任務 reward 的平均值。

這種設計確保了評估對象是「能夠上線的代理」，而非「能通過單元測試的程式碼」。

#### 實驗數據解讀

##### 主要結果

在橫跨四個領域、共 53 個任務的測試中：

- 最強配置 **Claude Opus 5** 搭配 **Claude Code**：僅通過 **23.9%** 的 **evaluation simulations（評估模擬）**
- **reference ceiling（參考上限）**（由專家撰寫的參考代理）：達到 **82.2%**

這個差距非常顯著：目前最強的 AI 開發系統僅達到專家水準的約 29%，顯示 **agent construction（代理建構）** 仍遠未解決。

##### 失敗模式分析

作者將失敗歸因於以下幾個開發者代理普遍缺乏的能力：

1. **規格還原不足（Shallow Specification Recovery）**  
   開發者代理傾向於對業務紀錄做 **shallow queries（淺層查詢）**（例如關鍵字搜尋），而非進行 **deep comprehension（深入理解）**。它們沒有系統性地閱讀手冊、交叉比對衝突文件、或從對話紀錄中推導隱含規則。

2. **不與客戶對話（Poor Client Communication）**  
   許多關鍵需求只能透過 **simulated client（模擬客戶）** 挖掘，但開發者代理幾乎不進行訪談。一個簡單的問題就能浮出的需求，卻因為缺乏提問而被遺漏，導致最終代理行為偏離預期。

3. **缺乏設計空間探索（No Design Space Exploration）**  
   開發者代理傾向於「第一個能跑的架構就提交」。它們沒有比較單一模型與多 **sub-agents（子代理）**、沒有嘗試不同的工具切分方式、也沒有針對 **serving cost（服務成本）** 與 **latency（延遲）** 做最佳化。

4. **預算管理不當（Mismanaged Serving Budget）**  
   開發者代理在成本與模型使用上兩個方向都出錯：有時過度節省而選用過弱模型導致表現不佳，有時又過度花費而超出每任務成本上限。

5. **驗證方式錯誤（Validation Against Self-Authored Tests）**  
   開發者代理傾向於撰寫自己的測試來驗證，但這些測試往往編碼了它們自己的盲點，而非真正模擬部署後的使用者行為。這導致「測試通過但上線失敗」的經典工程問題。

##### 數據意涵

23.9% 與 82.2% 的對比說明，當前 AI 系統在「寫出能執行的程式」方面已有一定能力，但在「理解業務、挖掘需求、做工程權衡、並交付可部署產品」方面仍處於早期階段。這也呼應了論文的核心論點：**agent construction（代理建構）** 不僅是傳統軟體工程的延伸，還需要額外的能力，例如規格還原、互動式需求訪談、以及以部署為導向的驗證。

#### 與現有研究的比較

ττ-bench 的定位可以從兩條研究脈絡來理解：**coding benchmarks（程式設計基準測試）** 與 **agent benchmarks（代理基準測試）**。

##### 相較於程式設計基準測試

早期的 **coding benchmarks** 多聚焦於自包含的競賽題目（如 HumanEval、MBPP），後來進展到在既有 **codebase（程式碼庫）** 中修復特定問題（如 SWE-bench），再到從零建構軟體（如 SWE-bench-style 的擴展）。ττ-bench 與這些工作的關鍵差異在於：

- 任務目標不是修復 bug 或實作函式，而是建構一個能服務真實使用者的 **customer-service agent（客服代理）**
- 輸入不是清晰的規格文件，而是雜亂、衝突、分散的業務紀錄
- 輸出必須滿足成本、延遲、模型限制等部署條件
- 評估不是靜態測試，而是動態部署後與 **simulated users（模擬使用者）** 互動

作者特別將 ττ-bench 類比為 **ProgramBench** 的代理對應版本：ProgramBench 給定文件與參考執行檔要求重建系統；ττ-bench 則給定企業紀錄與業務 API，要求重建一個代理。

##### 相較於代理基準測試

ττ-bench 建立在 **τ-bench family（τ-bench 系列）** 之上。τ-bench 系列原本評估的是「已建構好的代理在模擬使用者面前的表現」，而 ττ-bench 將任務往前推進一步：評估「AI 是否能建構出那個代理」。這類似於：

- 從「考試」變成「出題並教出能通過考試的學生」
- 從「評估代理」變成「評估代理的建造者」

這使得 ττ-bench 能夠測量傳統代理基準無法觸及的能力，例如：

- **specification recovery（規格還原）**
- 與人類利害關係人的互動式溝通
- 在有限資源下的架構設計
- 以部署為導向的驗證與迭代

##### 優勢與局限

**優勢：**

- 高度貼近真實客戶專案的條件，包含衝突文件、有限預算、缺陷 API
- 端到端評估直接測量「可部署性」
- 明確指出當前 AI 系統在需求工程與設計探索上的瓶頸

**局限：**

- 目前僅涵蓋四個領域與 53 個任務，規模相對有限
- 模擬客戶與模擬使用者的真實性仍有簡化，無法完全取代真人專案
- 評估成本較高，因為每次評估都需要完整部署一個代理並進行多輪對話
- 對於「何謂正確的業務規則」有時依賴人工定義的 ground truth，可能無法涵蓋所有合理的業務解釋

#### 可重現性評估

根據目前提供的論文內容，ττ-bench 的具體開源狀態尚未明確說明。論文為 **preprint（預印本）**，文中並未提供公開的程式碼倉庫、資料集下載連結或 **model weights（模型權重）** 資訊。

從可重現性的角度來看，一個完整的基準測試通常需要釋出以下元件：

1. **Sandbox（沙盒）環境**：包含檔案系統、業務文物、API 伺服器與模擬客戶/使用者
2. **Dataset（資料集）**：53 個任務的領域定義、原子事實、文件與預期最終狀態
3. **Evaluation harness（評估框架）**：部署代理、執行模擬對話、計算 reward 的程式碼
4. **Reference implementation（參考實作）**：專家撰寫的 82.2% 參考代理
5. **Developer agent configuration（開發者代理配置）**：例如 Claude Code 的 prompt、工具呼叫介面、成本追蹤機制

目前這些資訊在提供的摘要與前兩節中尚未出現。因此，現階段的可重現性評估為：**理論上方法論描述足夠詳細以支持復現，但實際復現仍需等待作者釋出官方 artifacts**。若未來能開源，將大幅提升社群在此基準上的研究速度；若僅釋出部分元件（例如僅釋出評估框架但無完整資料集），則可重現性會受到限制。

此外，由於評估涉及商業領域知識與多輪對話，即使釋出程式碼，復現者仍需要仔細校準 **simulated client（模擬客戶）** 與 **simulated users（模擬使用者）** 的行為，以確保不同實作間的分數具有可比性。

#### 未來研究方向

ττ-bench 揭示的瓶頸為多個研究方向提供了具體的著力點：

##### 1. 主動式規格還原（Active Specification Recovery）

開發者代理需要更像資深工程師，能夠系統性地閱讀文件、偵測衝突、提出假設並驗證。未來研究可探索：

- 基於資訊增益的文件閱讀策略
- 自動化矛盾偵測與澄清問題生成
- 將業務規則結構化為可驗證的中間表示（如知識圖譜或規則庫）

##### 2. 互動式需求訪談（Interactive Requirement Elicitation）

目前開發者代理幾乎不與 **simulated client（模擬客戶）** 對話。未來可發展：

- 主動提問策略，根據已還原的規格與不確定性選擇問題
- 多輪對話中的信念更新機制
- 將客戶回答與文件證據進行交叉驗證

##### 3. 設計空間自動探索（Automated Design Space Exploration）

未來的 **developer agent（開發者代理）** 應具備類似 AutoML 的能力，自動嘗試不同架構：

- 單一模型 vs. **orchestrated sub-agents（協調式子代理）**
- 不同的 **tools（工具）** 切分粒度
- 不同的提示工程策略與記憶機制
- 在 **serving cost（服務成本）** 與 **latency（延遲）** 限制下進行多目標最佳化

##### 4. 部署導向驗證（Deployment-Oriented Validation）

避免開發者代理只驗證自己寫的測試，未來可研究：

- 自動生成貼近真實使用者行為的對抗性測試案例
- 在模擬部署環境中進行壓力測試與邊界案例測試
- 將評估回饋直接納入開發迭代迴圈

##### 5. 成本與延遲感知規劃（Cost-Latency-Aware Planning）

開發者代理需要內建預算意識，例如：

- 在模型選擇上建立 cost-accuracy-latency 的 Pareto frontier（帕雷托前沿）
- 動態路由簡單查詢至便宜模型、複雜查詢至強大模型
- 在開發階段就估算並監控 **cost per task（每任務成本）**

##### 6. 從 ττ-bench 到真實專案

未來可將 ττ-bench 擴展至更多領域、更長的開發時間軸、以及與真人客戶的混合評估。也可研究如何將 ττ-bench 作為訓練環境，透過強化學習或模仿學習提升 **developer agent（開發者代理）** 的建構能力。

總結來說，ττ-bench 不僅是一個新的基準測試，更是一個研究議程：它將「AI 能否建造出可部署的代理」這個問題，轉化為一系列可測量、可改進的具體能力目標。

## 論文問答

**Q1：ττ-bench 想要解決什麼問題？**
A：ττ-bench 針對的是現有基準測試無法評量「端到端代理建構」的問題，因為它們多半只評估已完成的代理或孤立的程式任務，而非在真實客戶合作條件下從零打造代理。在實務中，開發者代理必須從企業實際保存的雜亂紀錄與利害關係人處還原規格，繼承既有程式碼庫，串接生產 API，並在成本、延遲與可用模型清單的限制下交付可部署的客服代理。ττ-bench 把這整個過程變成可量測的任務，讓研究社群能具體評估 AI 系統建構代理的能力。

**Q2：為什麼現有的基準測試無法忠實反映真實的代理建構情境？**
A：現有代理基準通常直接給定完整的領域政策與工具，然後評分完成後的代理表現，卻忽略了規格還原、客戶溝通、預算限制與部署驗證等關鍵環節。真實的代理開發起點是散落、衝突甚至過時的業務文件，以及只把需求藏在腦中的模擬客戶，而不是乾淨的提示詞。此外，現有程式競賽或程式修復基準也很少要求整合可能帶有缺陷的生產 API，或管理每任務服務成本與 p95 延遲。

**Q3：代理建構為什麼既重要又困難？**
A：企業正快速把大型語言模型代理部署到客服、爭議裁定與內部系統等生產級軟體中，因此代理建構具有高度經濟價值。其困難來自兩個軸線：一是規格還原，必須從標準作業程序、客服對話紀錄、費用表與人類利害關係人處重建需求；二是實際建構，往往要繼承既有程式碼庫、保留既有行為，並在服務成本、延遲與模型清單等硬限制下做設計決策。這些決策包括是否採用單一遵循策略的模型或協調式子代理、如何切分動作空間與工具，以及如何向客戶提問以揭露隱藏事實。

**Q4：ττ-bench 的核心方法是什麼？**
A：ττ-bench 先把每個領域的作業程序拆解成原子事實，再轉換成企業實際會持有的各類文件，例如手冊、客服對話紀錄、試算表、電子郵件、圖片、音訊以及會議逐字稿。開發者代理在沙盒中只能接觸這些業務紀錄、一個模擬客戶、繼承的程式碼庫與生產 API，並受成本與延遲限制，最終必須實作出完整的客服代理。完成後的代理會在保留的評估模擬中與模擬使用者互動，以其達成預期結果的比例作為分數。

**Q5：相較於 τ-bench 家族，ττ-bench 的關鍵創新是什麼？**
A：τ-bench 家族評估的是「已經建構好的代理」在領域政策下服務模擬使用者的表現，而 ττ-bench 把「建構過程本身」變成被評估的對象。它新增了從散落文件與互動式客戶中還原規格、繼承程式碼庫、整合生產 API，以及在固定模型清單與服務成本下部署等挑戰。這使得協作式代理建構成為一個可測量的研究目標，而不只是代理行為的評量。

**Q6：ττ-bench 的設計選擇如何塑造評估難度？**
A：ττ-bench 刻意混合多種真實業務文件格式，並引入必須主動詢問才能揭露需求的模擬客戶，迫使開發者代理進行深入理解而非淺層查詢。它同時設定固定的可用模型清單、每任務服務成本上限與 p95 延遲限制，要求代理在預算與效能之間取捨。最終分數來自於把建構好的代理部署到保留測試任務上，並與專家撰寫的參考上限比較，確保評估貼近真實上線標準。

**Q7：實驗評估了哪些配置，關鍵結果是什麼？**
A：研究橫跨四個領域、共 53 個任務，測試了多種開發者代理配置，其中最強配置是 Claude Opus 5 透過 Claude Code 執行，但僅通過 23.9% 的評估模擬。相較之下，專家撰寫的參考上限達到 82.2%，顯示現今 AI 系統能做出「會動」的代理，卻離可部署的代理還很遠。這個巨大差距凸顯了規格還原、設計探索與部署驗證等能力仍是重大瓶頸。

**Q8：23.9% 對上 82.2% 的結果代表什麼意義？**
A：這個差距說明即使是最先進的模型，仍缺乏真實代理開發所需的紀律，例如仔細閱讀業務紀錄、主動訪談客戶、實驗不同架構，以及針對部署情境進行驗證。參考上限證明了這些任務在人類開發者採取正確流程時是高度可解的，因此問題不在任務本身過難，而在於 AI 系統尚未內建這些開發實務。ττ-bench 因此為未來模型與工具提供了明確的改進方向。

**Q9：研究發現了哪些主要的失敗模式，類似什麼樣的消融觀察？**
A：分析發現開發者代理常以關鍵字進行淺層查詢，而沒有深入理解業務紀錄；它們幾乎不與模擬客戶溝通，導致關鍵需求未被揭露；在服務成本管理上不是過度浪費就是過度節省。此外，它們很少探索設計空間，往往把第一個能跑的架構直接出貨，並用自行撰寫的測試驗證，而這些測試反而編碼了自身的盲點。這些失敗模式與人類代理開發者常見的錯誤如出一轍，也成為 ττ-bench 希望逐一量化的目標。

**Q10：ττ-bench 代表哪些實務應用場景？**
A：它代表企業在實際客戶合作中，要求 AI 從真實業務紀錄建構客服代理的情境，例如處理掛失卡片與補發費用、帳戶爭議裁定或內部系統操作。這些場景涉及繼承的程式碼庫、可能含有缺陷的生產 API、衝突的文件，以及只存在於人類腦中的隱藏需求。ττ-bench 透過模擬這些複雜條件，讓研究者能在受控環境中評估代理建構的端到端能力。

**Q11：對於開發 coding agent 的產品設計，ττ-bench 帶來哪些啟示？**
A：產品必須把深度文件理解、互動式利害關係人訪談、設計空間探索、預算感知模型選擇，以及部署導向驗證視為核心功能，而非附加功能。開發者代理不能只滿足於「第一個能跑的設計」，而應迭代尋找更穩健、更符合成本與延遲限制的架構。服務成本與延遲必須和正確性一樣成為一等公民，否則建構出的代理難以真正上線。

**Q12：ττ-bench 可能對整個領域產生什麼影響？**
A：它把研究焦點從「代理如何行動」轉移到「AI 如何建構代理」，使協作式代理建構成為具體可測的研究目標。透過量化規格還原、客戶溝通、設計實驗與部署驗證等缺失紀律，它能引導模型與開發工具朝真實客戶合作所需的能力演進。長遠來看，ττ-bench 有望成為評估端到端、真實情境 coding agent 的重要標竿。

**Q13：ττ-bench 有哪些已經存在或隱含的限制？**
A：目前 ττ-bench 僅涵蓋四個領域與 53 個任務，雖然已具代表性，但仍無法涵蓋所有產業或更複雜的法規環境。模擬客戶與模擬使用者雖然設計得貼近真實，但本質上仍是腳本化角色，可能無法完全重現真實人類利害關係人的細微互動。此外，82.2% 的參考上限來自專家手寫版本，它反映的是人類開發者的表現，而非自動化建構的理論最佳值。

**Q14：哪些失敗案例最令人擔憂？**
A：最令人擔憂的是開發者代理直接把第一個能跑的設計出貨，卻沒有針對部署情境進行驗證，這會導致代理在生產環境中靜默失敗。對業務紀錄的淺層理解可能使代理套用錯誤政策，而忽視模擬客戶則會讓關鍵需求從未被揭露。這些問題顯示現有系統在高風險、需要正確性的部署場景中仍缺乏足夠可靠性。

**Q15：ττ-bench 指向哪些未來研究方向？**
A：未來可以擴展更多領域、加入更豐富的多利害關係人互動，甚至讓需求隨時間動態變化，以更接近真實企業環境。研究者可以設計會主動規劃規格還原、執行對照實驗、管理服務預算，並以模擬部署為依據進行驗證的開發者代理。最終目標是讓 coding agent 能夠在真實客戶合作的條件下，穩定交付可上線的生產級客服代理。

## 實務應用指南

### 適用場景

1. **企業內部客服代理的委外/自動開發**  
   當企業需要將分散在 SOP、試算表、Email 與會議紀錄中的客服知識，轉換成可上線的客服代理時，可用 ττ-bench 的框架來檢驗開發者代理（developer agent）是否能正確還原規格、繼承既有程式碼庫，並在成本與延遲限制下交付可用系統。

2. **金融/保險/電信等高度監管產業的理賠或爭議處理代理**  
   這些領域的業務規則常散落在費用表、政策文件與過往對話紀錄中，且必須透過生產 API 操作。ττ-bench 的設定適合驗證代理能否在「規格不完整、需詢問模擬客戶」的真實條件下，建構出符合法規與政策的代理。

3. **新創或中小企業的快速概念驗證（PoC）**  
   當團隊沒有足夠工程人力，想讓 AI 自動從現有文件與 API 文件長出第一版客服代理時，可採用本文的任務拆解方式：先還原規格、再設計工具與子代理、最後用模擬使用者評分。

4. **大型企業的代理開發流程稽核與人才評量**  
   可將 ττ-bench 的保留測試任務（held-out tasks）作為內部評量基準，比較不同開發團隊或 AI 輔助工具所產出代理的部署分數，找出規格還原、設計探索與預算控管上的弱點。

5. **AI 輔助程式碼工具（如 Claude Code、Cursor 等）的能力邊界測試**  
   若你正在評估或採購 coding agent 工具，可用 ττ-bench 的任務格式來測試它們在「從業務紀錄到可部署代理」這段端到端流程中的實際表現，而非只看單純的程式碼生成能力。

---

### 實作前置條件

- **資料準備**  
  需要蒐集並整理企業真實會持有的紀錄：標準作業程序（SOP）、客服對話紀錄（support transcripts）、費用表（fee schedules）、會議錄音/逐字稿、Email 往來、產品圖片或流程圖，以及可互動的業務窗口（client）聯絡窗口或訪談腳本。

- **技術基礎建設**  
  需要一個隔離的沙盒（sandbox）環境，內含檔案系統、待繼承的程式碼庫（codebase）、生產 API 的模擬或測試版本，以及可執行模擬使用者（simulated users）的評估環境。

- **運算與模型資源**  
  建議準備多種可用模型（model menu）以測試不同配置，並設定每任務成本上限（cost per task）與 p95 延遲限制。若僅用單一最強模型，容易忽略預算與延遲的實務約束。

- **技能需求**  
  團隊需具備：LLM 代理設計經驗、REST API 整合能力、軟體工程與測試能力、領域知識（domain expertise）以判斷規格還原是否正確，以及資料工程能力將非結構化業務紀錄轉為可檢索格式。

---

### 實作步驟建議

1. **建立業務紀錄沙盒**  
   將企業文件轉換為 ττ-bench 定義的原子化事實（atomic facts），並以真實企業會使用的格式存放：Markdown 手冊、JSON/CSV 費用表、VTT 逐字稿、PDF 簡報等。同時建立可互動的模擬客戶（client）腳本，用於回答開發者代理的詢問。

2. **定義約束條件與評分標準**  
   明確設定每任務服務成本上限、可用模型清單、p95 延遲限制，以及保留測試任務（held-out tasks）的期望最終狀態（final state expected）。這些條件應與真實上線環境一致。

3. **讓開發者代理進行規格還原（specification recovery）**  
   引導代理先閱讀所有業務紀錄、進行深入理解（deep comprehension），而非只做關鍵字查詢（shallow queries）。同時鼓勵代理主動訪談模擬客戶，將隱藏在人類利害關係人腦中的需求浮出檯面。

4. **設計代理架構與工具（tools）**  
   根據還原出的規格，決定要採用單一遵循策略的模型（policy-following model）還是協調式子代理（orchestrated sub-agents），並將動作空間（action space）切割成適當的工具，例如查詢帳戶、回報遺失卡片、驗證費用減免等。

5. **整合生產 API 與既有程式碼庫**  
   讓代理在繼承的程式碼庫上開發，並透過生產 API 執行營運操作。注意 API 可能含有細微缺陷，需設計錯誤處理與驗證機制。

6. **進行設計探索與預算實驗**  
   不要讓代理只交付第一個能跑的版本。應鼓勵其嘗試不同模型組合、子代理架構與工具切分方式，並在每次實驗後測量成本與延遲。

7. **部署並對抗模擬使用者評估**  
   將建構好的客服代理部署至評估環境，與模擬使用者進行多輪對話。評分應以對話結束後的最終狀態是否符合預期為主，而非僅看代理是否回覆流暢。

8. **迭代修復與人機協作審查**  
   針對失敗案例進行根因分析，補強規格還原、工具設計或預算配置。關鍵決策點應保留人類專家審查，避免全自動代理盲目上線。

---

### 潛在風險與注意事項

- **規格還原不足**  
  開發者代理可能只做淺層查詢，未深入理解業務紀錄，導致遺失關鍵規則。建議強制要求代理產出規格摘要，並由領域專家抽樣驗證。

- **忽略客戶訪談**  
  部分需求只存在於人類利害關係人腦中。若代理不主動與模擬客戶對話，會遺失隱藏規則。可在流程中加入「必須訪談客戶」的檢查點。

- **預算與延遲失控**  
  代理可能過度使用最強模型，或反過度節省導致效能不足。建議在開發初期就將 cost per task 與 p95 延遲納入獎勵函數或硬性約束。

- **設計空間探索不足**  
  代理傾向修補第一個能跑的架構。可設定多輪實驗機制，要求至少比較 2–3 種架構（單一模型 vs. 子代理）並留下實驗紀錄。

- **用自我編寫的測試驗證自己**  
  代理可能根據自己的盲點設計測試，導致誤判。應使用獨立的保留測試任務與模擬使用者進行最終評估，並由人類檢視失敗案例。

- **生產 API 的細微缺陷**  
  真實 API 常有不一致或邊界行為。建議在沙盒中注入常見缺陷，訓練代理進行防禦式整合與錯誤回報。

---

### 與其他技術的整合建議

- **RAG 與知識庫系統**  
  將業務紀錄轉為向量知識庫，輔助開發者代理進行規格還原。但需注意：ττ-bench 強調「深入理解」而非「關鍵字匹配」，因此 RAG 應搭配摘要與推理步驟，而非直接作為答案來源。

- **MLOps / LLMOps 平台**  
  將代理建構流程接入現有的實驗追蹤、模型版本控制與部署管線，例如追蹤每次設計實驗的成本、延遲與評估分數，便於後續迭代。

- **現有客服系統（CRM、工單系統）**  
  最終交付的客服代理應透過生產 API 與現有 CRM、工單系統整合，而非獨立運作。建議將工具（tools）設計為對應到現有系統的操作介面。

- **人機協作審查工具**  
  在關鍵步驟（規格確認、架構選擇、上線前評估）加入人類審查閘門，可與現有 DevOps 或 ITSM 流程結合，降低全自動部署風險。

- **評估與監控系統**  
  將 ττ-bench 的模擬使用者評估機制延伸至上線後的持續監控，定期用新生產資料產生新的 held-out tasks，確保代理隨業務變化持續符合規格。

### 給不同背景讀者的閱讀建議

- **初學者**  
  建議先聚焦在圖 1 與「適用場景」段落，理解 ττ-bench 為何把「建構代理」本身當成任務，而非只評估代理會不會回答問題。接著可閱讀實作步驟建議，將其視為一個「AI 幫你開發客服機器人」的專案流程圖，不必急著深入模型架構細節。

- **AI 工程師**  
  請特別關注規格還原、設計空間探索與預算控管這三個瓶頸。本文指出 Claude Opus 5 + Claude Code 僅達 23.9%，顯示現有 coding agent 在端到端代理建構上仍有明顯缺口，可作為你設計開發者代理架構時的風險檢查清單。

- **研究人員**  
  本文的核心貢獻在於將代理建構任務形式化，並提供 53 個跨領域任務與專家參考上限（82.2%）。建議深入閱讀評估設計、原子化事實轉換方法，以及失敗模式分析，這些可作為未來在自動軟體工程、人機協作與代理評估領域的研究起點。

- **產品經理**  
  請把本文當作評估 AI 開發工具與規劃客服代理產品路線圖的參考依據。重點不在技術細節，而在於理解：自動化代理開發目前仍需要人類在規格確認、設計審查與上線把關等環節介入，且成本與延遲限制是產品化不可妥協的條件。
